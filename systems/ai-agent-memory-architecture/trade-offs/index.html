Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust edition 2021, MSRV 1.78

Rejected

Python, Go, C++

When the rejected choice is right

Python wins when iteration velocity outweighs correctness (early-stage research prototype, ≤1k memories, no durability requirement). Go wins when a small team maintains a microservice that uses an existing Postgres-backed store (no custom WAL needed, GC latency acceptable). C++ wins when the team needs to embed in an existing C++ agent runtime with shared-memory zero-copy to GPU.

Why: Storage-engine correctness (WAL, mmap, crash safety); ownership model prevents data races in concurrent retrieval + consolidation; no GC pauses; safe FFI for embedding/rerank backends

ADR-02

Build system

Chosen

Cargo workspaces (13 crates)

Rejected

Bazel, Buck, CMake

When the rejected choice is right

Bazel wins when this project is one module among hundreds in a large monorepo requiring hermetic, cross-language (Rust + Python + Proto) builds, remote cache, and deterministic sandboxed CI. CMake wins if the final artifact must be linked into a C/C++ host system with system-level packaging requirements.

Why: Native Rust toolchain; workspace unifies deps; cargo build --release for production

ADR-03

Async runtime

Chosen

Tokio (current-thread or multi-thread, configurable)

Rejected

async-std, smol, blocking threads

When the rejected choice is right

async-std wins if the embedding of this library into a downstream codebase already uses async-std exclusively and runtime mixing is prohibited by policy. Blocking threads wins when the subsystem is embedded in a synchronous CLI tool (mem-cli standalone mode) where no async executor exists and spawn_blocking semantics are cleaner than a full Tokio runtime.

Why: Ecosystem fit; structured concurrency; background tasks (consolidation, decay, compaction) as tokio tasks; select! for timeout-guarded LlmIface calls

ADR-04

Serialization (WAL + store)

Chosen

bincode (v2, deterministic)

Rejected

serde_json, protobuf, flatbuffers, rkyv

When the rejected choice is right

protobuf wins when forward/backward compatibility is required across independently versioned services that exchange MemoryRecord over a network boundary (e.g., read-replica replication in PhaseDeferred 16.x). rkyv wins when profiling shows deserialization dominates hot-path latency and the record schema is stable enough to justify zero-copy unsafe read. serde_json wins for human-readable diagnostic dumps and migration tooling where byte efficiency is irrelevant.

Why: Compact binary; deterministic encoding required for CRC32c; zero-copy reads via rkyv considered but bincode simpler for variable-length types

ADR-05

On-disk format versioning

Chosen

bincode + manual schema version field in file headers

Rejected

serde with version tags, protobuf field evolution

When the rejected choice is right

protobuf field evolution wins when the deployment model requires rolling upgrades where multiple versions of the reader may access the same WAL simultaneously (e.g., blue/green deployment of an agent host that reads old WAL entries during the transition window).

Why: Explicit migration code per version bump; no magic format evolution; migration tested in CI

ADR-06

ANN / vector index

Chosen

Built-in HNSW (mem-index); pluggable AnnBackend trait

Rejected

FAISS via FFI, hnswlib via FFI, Annoy, ScaNN

When the rejected choice is right

FAISS via FFI wins when corpus exceeds ~10M vectors and GPU IVFPQ or IVF-Flat compression is required to keep index memory below hardware limits. ScaNN wins when quantization-aware retrieval (asymmetric distance) is the primary latency lever and a C++ interop cost is acceptable. hnswlib via FFI wins when benchmark evidence shows the pure-Rust HNSW implementation is the retrieval bottleneck and the team accepts unsafe FFI under a sandboxed build.

Why: Avoid unsafe FFI as default; pure-Rust HNSW sufficient for ≤10M vectors; FAISS backend available via feature flag for production scale

ADR-07

Full-text index

Chosen

BM25 inverted index (hand-rolled, mem-index)

Rejected

tantivy, meilisearch, Lucene FFI

When the rejected choice is right

tantivy wins when requirements expand to include fielded queries, phrase proximity, fuzzy match, facets, or multi-language analysis — features that would require re-implementing significant portions of tantivy's query layer. If the BM25 keyword workload grows beyond simple unigram scoring and requires a full query parser, tantivy's battle-tested segment architecture pays off.

Why: tantivy is heavy dep; our BM25 only needs score + posting list; keeps dep surface minimal

ADR-08

Embedding provider

Chosen

Abstract LlmIface::embed() trait; no default provider

Rejected

OpenAI hard-coded, HuggingFace Transformers, ort (ONNX)

When the rejected choice is right

ort (ONNX) hard-coded wins when the deployment environment is air-gapped, latency to a remote API is unacceptable (< 5 ms embedding budget), and the embedding model is fixed for the lifetime of the deployment. HuggingFace Transformers hard-coded wins in a research prototype where model fine-tuning iteration velocity matters more than provider flexibility.

Why: Provider-neutral; embedding cache (mem-embed) hides latency; allows local ONNX runtime or remote API

ADR-09

LLM interface (summarize, extract, reflect, rerank)

Chosen

LlmIface trait (mem-embed + mem-consolidate)

Rejected

Hardcoded OpenAI/Anthropic SDK, langchain

When the rejected choice is right

Hardcoded OpenAI SDK wins when the agent product exclusively targets the OpenAI platform, zero provider switching is planned, and the team prefers reduced abstraction layers to simplify debugging. LangChain wins when the agent orchestration layer already depends on LangChain and adding another abstraction boundary over an existing one increases rather than decreases complexity.

Why: Dependency inversion; tests inject mock LlmIface; production implementations are separate crates

ADR-10

WAL / durability

Chosen

Append-only WAL with CRC32c per entry; configurable fsync policy

Rejected

SQLite WAL, RocksDB, sled, redb

When the rejected choice is right

SQLite WAL wins when the team needs a mature, audited, full-ACID embedded store with SQL query access for migration tooling, and is willing to accept SQLite's opacity in exchange for eliminating the custom WAL maintenance burden. RocksDB wins when write amplification at high memory-record throughput (>100k writes/s) makes a single-file WAL a bottleneck, and LSM-tree compaction parallelism is needed.

Why: Custom WAL gives exact control over op semantics needed for OP_CONSOLIDATED, OP_EVICT; SQLite too opaque for partial-entry recovery

ADR-11

Record store mmap

Chosen

memmap2 crate for mmap read; pwrite for writes

Rejected

read() syscalls, SQLite blobs

When the rejected choice is right

read() syscalls win when the deployment environment prohibits mmap (certain seccomp sandbox profiles, strict WASM targets, or operating under SELinux policies that deny mmap of file-backed regions). SQLite blobs win when the record access pattern is highly random-access with no spatial locality, making mmap pre-fetching wasteful, and SQL indexing over blob metadata is preferable.

Why: mmap amortizes read cost over repeated record fetches in retrieval hot path; writes via pwrite avoid mmap-write complexity

ADR-12

Memory-safe concurrency

Chosen

tokio::sync::{RwLock, Mutex} for index guards; Arc for shared state

Rejected

std::sync, crossbeam

When the rejected choice is right

std::sync wins when the subsystem is embedded in a synchronous, non-async context (e.g., an FFI call from C) and tokio primitives would require spawning an executor. crossbeam wins when profiling identifies the RwLock as a contention hotspot and epoch-based lock-free data structures provide measurable throughput gains.

Why: Async-aware locks avoid blocking tokio threads; RwLock allows concurrent readers on HNSW during retrieval

ADR-13

Metrics

Chosen

metrics crate (facade) + metrics-exporter-prometheus

Rejected

OpenTelemetry metrics only, statsd, custom

When the rejected choice is right

OpenTelemetry metrics only wins when the operator requires a single unified telemetry pipeline (metrics + traces + logs via OTLP) and running both a metrics exporter and an OTel metrics exporter is redundant overhead. statsd wins in a legacy infrastructure where the central metrics aggregator is a statsd-compatible collector and Prometheus scraping is unavailable.

Why: metrics facade allows swap of backend; Prometheus pull model suits sidecar deployment

ADR-14

Distributed tracing

Chosen

tracing + tracing-opentelemetry + opentelemetry-otlp

Rejected

log crate only, slog, structured println

When the rejected choice is right

log crate only wins in an embedded microcontroller or resource-constrained environment where the OTel SDK binary footprint (hundreds of KB) is prohibitive. slog wins in a legacy Rust codebase already built around slog where adding a second structured logging framework would fragment log aggregation pipelines.

Why: tracing spans correlate across remember/recall/consolidate; OTLP export to Jaeger/Tempo

ADR-15

Logging

Chosen

tracing (unified with tracing above); JSON formatter for prod

Rejected

env_logger, slog

When the rejected choice is right

env_logger wins in a standalone CLI tool (mem-cli in debug mode) where structured JSON logs add noise for an operator reading output at the terminal; env_logger's human-readable output is more ergonomic for interactive use.

Why: Single framework; tracing::instrument decorates every public API call

ADR-16

Testing framework

Chosen

cargo test (unit + integration); tokio::test for async

Rejected

nextest (used in CI for parallelism), pytest

When the rejected choice is right

pytest wins if the test surface that matters most is a Python binding layer (e.g., a PyO3-exposed mem-api), where pytest fixtures, parametrize, and the Python ecosystem's test libraries provide richer integration testing than Rust tests against the Python ABI.

Why: Standard; nextest used in CI for speed; proptest for property tests

ADR-17

Fuzzing

Chosen

cargo-fuzz (libFuzzer) targeting WAL parser, bincode deserializer, query parser

Rejected

AFL++, Honggfuzz

When the rejected choice is right

AFL++ wins when the team needs grey-box fuzzing with mutation dictionaries tuned for binary protocol formats (custom WAL frame grammar) and finds libFuzzer's mutation engine insufficient for navigating deep state in the WAL parser. Honggfuzz wins when persistent mode and hardware performance counters (branch coverage via perf) are available and show measurably better coverage than libFuzzer on the bincode deserializer target.

Why: Integrates with LLVM coverage; fuzz targets in fuzz/ dir; run in CI nightly

ADR-18

Property testing

Chosen

proptest

Rejected

quickcheck

When the rejected choice is right

quickcheck wins when the property test suite is simple (no complex strategy composition) and the team is already familiar with Haskell-style Arbitrary type class derivation; quickcheck's simpler API reduces onboarding friction in that case.

Why: proptest shrinking; strategy composition for Query, MemoryRecord; used in mem-retrieve, mem-store

ADR-19

Benchmark harness

Chosen

criterion (micro); custom soak harness in mem-bench

Rejected

hyperfine (CLI only), divan

When the rejected choice is right

hyperfine wins for wall-clock benchmarking of mem-cli subcommands where the unit under test is a process invocation (e.g., mem-cli compact --dry-run) and micro-level in-process benchmarking via criterion is inapplicable. divan wins if compile times become a significant CI friction point and divan's lighter footprint reduces the benchmark build step measurably.

Why: criterion for regression detection; mem-bench for retrieval quality (nDCG, MRR) + throughput

ADR-20

Dependency policy

Chosen

Minimal; each new dep requires ADR entry; cargo deny enforces license + advisory

Rejected

permissive / no policy

When the rejected choice is right

Permissive policy wins in a rapid-prototype phase where engineering velocity is the only metric, audits are deferred, and the dep surface will be trimmed before production hardening. Permissive policy also wins when the consuming organization has an established SBOM and vulnerability scanning pipeline that makes fine-grained dependency restrictions redundant.

Why: Attack surface; compile time; license compliance (MIT/Apache-2.0 only)

When the rejected choice is right

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Postgres-Backed Memory Store

Architecture sketch:

Agent
  └─ remember() / recall()
       └─ mem-api
            ├─ Postgres WAL (ACID, MVCC) ← records, provenance, salience
            ├─ pgvector extension          ← HNSW ANN inside Postgres
            └─ pg full-text search        ← tsvector / GIN BM25-like index

Regime where this wins: Small teams (<5 engineers), corpus ≤ 5M records, existing Postgres expertise, SLA on recall latency ≥ 50 ms p99, and no embedded-library constraint. A Postgres-backed design eliminates custom WAL maintenance, provides SQL for flexible migration tooling, and pgvector's HNSW matches Faiss quality at moderate scale.

Real system using this approach: getzep/graphiti (Zep v2) — Postgres + pgvector for fact graph; production deployments with agent memory.

Why rejected here: This design's embedding constraint (co-located library, no separate process) and latency target (p99 recall = 25 ms) are incompatible with Postgres round-trip overhead (typically 1–5 ms per query on local socket, 10–30 ms over network). Additionally, Postgres's MVCC and lock model is over-engineered for the single-writer WAL pattern; the custom WAL's OP_CONSOLIDATED and OP_EVICT operation types have no natural SQL analog without complex triggers.

Alt-2 — Pure In-Process SQLite with WAL Mode

Architecture sketch:

Agent
  └─ remember() / recall()
       └─ mem-api
            └─ SQLite (WAL mode, memory-mapped, single-file .db)
                 ├─ records table (content, salience, provenance)
                 └─ FTS5 virtual table (BM25 natively supported)
            (ANN: external hnswlib FFI linked in-process)

Regime where this wins: Projects that need ACID durability, crash recovery, and full-text BM25 (FTS5 is mature) without maintaining a custom WAL. SQLite WAL mode achieves concurrent readers + single writer with O(1) recovery time. FTS5 provides production BM25+ scoring. Deployment simplicity: single .db file.

Real system using it: The majority of mobile/desktop apps with local memory (iOS Core Data SQLite backend, Android Room). Not used in agent memory specifically, but SQLite's WAL is battle-tested at far larger scale than this system requires.

Why rejected here: SQLite's schema is a fixed-column relational model. MemoryRecord's Vec<f32> embedding cannot be stored natively (must serialize to BLOB and deserialize on every read). FTS5 uses SQLite's own tokenizer pipeline which cannot be swapped for our custom BM25+ implementation without forking SQLite. Most critically, SQLite's WAL provides durability but cannot express the custom operation types (OP_CONSOLIDATED, OP_EVICT) needed for recovery of consolidation and decay state without stored procedures or trigger chains — both of which add invisible complexity.

Alt-3 — RocksDB LSM-Tree as the Storage Backend

Architecture sketch:

Agent
  └─ remember() / recall()
       └─ mem-api
            └─ RocksDB (via rust-rocksdb FFI)
                 ├─ CF: records     ← MemoryRecord (bincode value, MemoryId key)
                 ├─ CF: embeddings  ← EmbeddingId → Vec<f32>
                 ├─ CF: metadata    ← salience, ttl, access_count (separate CF for fast update)
                 └─ CF: wal_ops     ← OP_CONSOLIDATED / OP_EVICT log
            (HNSW: in-process as current design; RocksDB replaces custom WAL+mmap)

Regime where this wins: High sustained write throughput (>10K records/s), large corpus (>50M records), multi-thread write concurrency. RocksDB's LSM-tree with Leveled compaction handles high write amplification gracefully; parallel compaction threads maintain read performance. Column Families allow independent compaction and tiering of hot vs cold data. This is the architecture used by production ML feature stores (Feast, Tecton) at massive scale.

Real system using it: Facebook AI Similarity Search (FAISS) integrations at Meta use RocksDB as the metadata backend for billion-scale vector systems.

Why rejected here: RocksDB is a C++ library accessed via unsafe FFI (rust-rocksdb). This introduces build complexity (CMake, clang, C++ ABI), unsafe code surface, and a dependency that dwarfs the entire rest of the project. The custom WAL gives exact semantics for the 8 operation types this system needs; RocksDB's WAL is implicit and not directly replayable at the application level. At the target scale (≤10M records), RocksDB's throughput advantages are not needed, and its operational complexity (tuning block_cache, write_buffer_size, compaction triggers) would require significant engineering.

Alt-4 — Stateless Memory via External Vector Database

Architecture sketch:

Agent
  └─ remember() / recall()
       └─ mem-api (thin client library)
            ├─ Qdrant / Pinecone / Weaviate (external gRPC service)
            │    └─ Dense vector search + metadata filters + optional BM25
            └─ No local WAL; no local store; provider handles durability

Regime where this wins: Agent frameworks that treat memory as a cloud service, not an embedded library. Horizontal scaling of the vector store is the provider's problem. Teams without Rust experience can use Python clients. Provider SLAs cover durability. Weaviate offers native BM25+vector hybrid search in a single deployment.

Real system using it: LangChain + Pinecone, LlamaIndex + Qdrant — the dominant pattern in the current LLM ecosystem.

Why rejected here: This design's core constraint is an embedded library with co-located storage — no network hop on the hot path. An external vector database adds 5–50 ms per call, making the p99 recall = 25 ms target impossible. Additionally, external services provide no control over WAL semantics, consolidation ordering, or decay/eviction policy — the exact features that differentiate this design from generic RAG pipelines. The custom operation types (OP_CONSOLIDATED, OP_EVICT), the namespace-scoped compaction, and the decay model are all incompatible with a provider-opaque external service.
