1. Goal & Scope

The Deoptimization Engine is a from-scratch, embeddable speculative-optimization and deoptimization subsystem for a tiered, bytecode-driven managed runtime. It is the safety net underneath an optimizing JIT: it lets the optimizer compile aggressively on unproven assumptions (a call site is monomorphic, a variable is a small integer, a class has no subclasses, a field is never null) and it guarantees correctness by transferring control from optimized machine code back to the interpreter — precisely, safely, and at exactly the bytecode point the interpreter would have reached — the instant any assumption is falsified. The engine owns four load-bearing concerns: (1) the speculation/assumption framework and its guard representation, (2) the dependency tracker linking assumptions to the compiled methods that rely on them, (3) the safepoint/debug-info model that maps every live optimized value back to an interpreter location, and (4) the deoptimizer runtime that reconstructs interpreter frames — including rematerializing scalar-replaced and eliminated objects — with correctness defined as observational equivalence to a fully-interpreted execution.

Phase-0 deliverable (crates):

  1. deopt-core — assumption/guard/safepoint type definitions (ADR-01..ADR-05 anchored).
  2. deopt-interp-toy — a minimal bytecode interpreter used as the canonical semantics oracle.
  3. deopt-opt-toy — a trivial optimizer (constant fold + one speculative transform) to exercise guards.
  4. deopt-statemap — the debug-info/state-map encoder and decoder.
  5. deopt-runtime — the deoptimizer: frame capture, lookup, rebuild, resume.
  6. deopt-deps — the assumption-dependency tracker and invalidation engine.
  7. deopt-remat — the rematerialization engine for scalar-replaced/eliminated values.
  8. deopt-osr — on-stack replacement, both directions.
  9. deopt-tiers — the tiered-compilation and recompilation controller.
  10. deopt-harness — the differential (interpreted-vs-deoptimized) correctness fuzzer, CI-gated.
  11. deopt-telemetry — deopt-rate, latency, and state-map-size instrumentation.

Boundaries — provides:

  • the speculation/assumption registry and its catalogue of speculation types (§8.1).
  • guard and uncommon-trap representation, attached to a FrameState at insertion time (§8.7).
  • the safepoint/debug-info/state-map model mapping every live optimized value to an interpreter location (§8.2).
  • the deoptimizer: frame reconstruction, rematerialization, and resume (§8.3).
  • OSR in both directions — interpreter-to-optimized and optimized-to-interpreter (§8.5).
  • the dependency tracker and bulk invalidation on class load (§8.6).
  • the tiered-compilation lifecycle state machine, including reprofiling, recompilation, and the deopt-thrashing guard (§8.8).

Boundaries — delegates:

  • bytecode design and the interpreter's execution semantics, assumed given and exposed only via InterpreterFrame/BytecodeIndex contracts.
  • the optimizer's general optimization passes (inlining heuristics, scheduling, register allocation) beyond the guard-insertion and state-map-emission obligations they must satisfy.
  • machine-code emission and calling-convention plumbing beyond the deopt-boundary ABI itself.

Boundaries — does NOT provide:

  • a garbage collector (only the safepoint/GC-interaction contracts a GC would consume, §8.9, T8).
  • a full VM or language frontend.
  • a parser, bytecode verifier, or class loader.

Non-goals, by sibling project:

  • Not the JIT-Compiler project — that project owns the optimizer's general transformation passes, scheduling, and code generation; this project owns only the speculative-assumption/guard/deopt machinery that makes those transformations sound.
  • Not JavaScript-Engine (126) — that project owns a full managed-language runtime (parser, object model, GC, embedding API); this project is the deopt subsystem such a runtime would embed.
  • Not Bytecode-Verifier (247) — that project proves bytecode safety ahead of execution; this project assumes verified bytecode and instead proves that optimized execution can always be unwound to verified-interpreter-equivalent state.
  • Not a full register allocator.
  • Not a class-hierarchy analysis engine — CHA facts are consumed as an input to speculation (§8.1), not computed here.
  • Not a profiler — profile data (ProfileData, §11) is a consumed input to speculation and tiering decisions, not produced by this project.

Host-runtime model assumed: a tiered interpreter executing a stack-based or register-based bytecode, feeding an optimizing JIT that compiles hot methods through this engine's guard/state-map contracts, with a GC that cooperates via safepoints this engine defines.

Deployment model: a library/subsystem statically linked into a managed runtime process; no network service, no external API surface; all interaction is in-process function calls and shared data structures (assumption registry, code cache, debug-info tables).

Users/operators: VM engineers building or maintaining JIT compilers, compiler researchers prototyping speculation strategies, and runtime SREs operating production JIT-backed services who consume its telemetry (deopt rate, thrashing events) for capacity and incident response.

What later phases unlock:

  • Phase 1 (safepoint/state-map) unlocks all deopt from Phase 2 onward — nothing downstream is buildable without it.
  • Phase 3 (speculation framework) unlocks type-feedback speculation in Phase 6.
  • Phase 4 (dependency tracking) unlocks safe class-hierarchy speculation.
  • Phase 7 (OSR-in) unlocks compiling hot loops without waiting for method re-entry.
  • Phase 9 (thrashing guard) unlocks safe aggressive speculation in production without pathological deopt storms.
  • Phase 11 (differential harness) unlocks the correctness claim this whole engine exists to make.

Language: Rust. Rationale: precise ownership for frame/metadata lifetime (a Deoptimizer must never alias a live optimized frame it is unwinding), unsafe-isolated boundaries for stack walking and register-state capture, zero-cost tagged enums for ValueLocation/AssumptionKind variant dispatch, and a mature fuzzing/property-testing ecosystem needed for the differential correctness harness (§28). Rejected: C++ (no ownership discipline at the deopt/GC boundary, historically a major source of HotSpot and V8 deopt CVEs — see §24); Zig (immature ecosystem for the property/fuzz tooling this project's correctness claim depends on); Go (GC pauses and no precise control over stack-frame layout, which this project must own directly).

Prerequisites: compiler construction (SSA, CFG, dataflow — Appel, Cooper & Torczon), VM internals (frame layout, calling conventions, bytecode dispatch — Smith & Nair), inline-cache and type-feedback theory (Deutsch & Schiffman 1984), the foundational deoptimization literature (Hölzle, Chambers & Ungar 1992).

Users/operators, expanded: VM engineers use this project as the deopt subsystem they embed beneath their own optimizer. Compiler researchers use it as a testbed for new speculation strategies without re-deriving the safety net from scratch. Runtime SREs consume only its telemetry surface (§26) and never its internal APIs.

Timeline:

  • Phases 1-5 (safepoint model through rematerialization): 10 weeks.
  • Phases 6-10 (type feedback through tiering): 12 weeks.
  • Phase 11 (correctness hardening): 4 weeks.
  • Total: approximately 29 weeks to god-bar completion.

2. Why Build This

  • speculative optimization correctness under aggressive rewriting
  • the interpreter-optimizer seam as a precise systems boundary
  • guard and uncommon-trap design
  • dependency-driven bulk invalidation on class load
  • rematerialization of eliminated/scalar-replaced objects
  • on-stack replacement in both directions
  • the tiered-compilation lifecycle as an explicit state machine
  • deopt-storm/thrashing containment under production load
  • the debug-info/state-map size-vs-reconstruction-speed tradeoff
  • calibration: this is the exact subsystem separating a toy JIT from a production one — HotSpot, V8, GraalVM, SpiderMonkey, and LuaJIT all build one
  • related systems: database query re-optimization plans, hypervisor live-migration state capture/restore, WASM tiering (Liftoff → TurboFan), kernel checkpoint/restore
  • engineering muscles this project specifically builds: precise ABI/calling-convention reasoning, dataflow-level correctness proofs, differential-testing methodology, and telemetry-first system design
  • calibration signal for hiring/self-assessment: an engineer who can explain why HotSpot, V8, and LuaJIT all made different debug-info encoding choices (§33) has internalized this project's core tradeoff, not just its mechanics

What Mastery Looks Like

  • Can explain, from Phase 1, why every live optimized value needs a debug-info entry before a single guard can be inserted safely.
  • Can design, from Phase 3, a new speculation type (its guard + uncommon trap + deopt reason) without consulting a reference implementation.
  • Can diagnose, from Phase 4, why a stale dependency let invalidated code execute, and correct the invalidation ordering.
  • Can rebuild, from Phase 5, a scalar-replaced object's exact pre-optimization identity from a rematerialization recipe.
  • Can trace, from Phase 7, an OSR-in transition without corrupting loop-carried state.
  • Can tune, from Phase 9, a deopt-thrashing blacklist threshold from first principles rather than a magic number.
  • Can prove, from Phase 11, that optimized and interpreted execution are observationally identical using the differential harness as evidence, not assertion.

The Tiered-Compilation Manager owns the Interpreted→Profiling→Tier1→Optimized state machine (§8.8) and the reprofiling/recompilation controller that reacts to deopts by adjusting profile data and re-issuing compiles. It is the only box in this diagram permitted to mutate a method's Tier (I13), and every other box's trigger reaches it as a request, never a direct mutation.

The Speculation/Assumption Registry is the per-method catalogue of active speculative facts (§8.1) that the optimizer consulted while compiling. It is append-only per method (P11) — an assumption once registered is never silently withdrawn, only explicitly invalidated (§8.6) or blacklisted (§8.8).

The Guard/Uncommon-Trap Inserter lowers each registry entry into an IR guard node with an attached trap target (§8.7). Following Duboscq et al. 2013, the trap target always carries a FrameState snapshot captured at insertion time, never synthesized lazily at trap time.

The Dependency Tracker indexes assumption → dependent-nmethod sets so a class load can find every method to invalidate (§8.6). It is the sole authority for bulk invalidation (ADR-09) and is consulted before, not after, a speculative compile is trusted (P13).

The Safepoint + Debug-Info/State-Map Generator emits, at every safepoint the optimizer creates, a complete mapping from live optimized values to interpreter locations (§8.2). Its output is checksummed (I8) and is the single artifact every other box downstream of the seam depends on for correctness.

The Deoptimizer Runtime is invoked at a guard failure or uncommon trap: it captures machine state, looks up debug info, and drives frame reconstruction (§8.3). It is implemented as a stateless service (§14.2) so its correctness is a pure function of the SafepointId and captured frame it is given.

The Rematerialization Engine consumes RematRecipes to rebuild scalar-replaced/eliminated objects (§8.4). It runs strictly between frame construction and GC-root relinking in the deopt procedure (§8.3, steps 5-6), never before or after.

The Interpreter-Frame Builder turns reconstructed values into real InterpreterFrames, outermost inline frame first (ADR-11). It is the box that ultimately hands control back to canonical bytecode execution.

The OSR-in/OSR-out Machinery is the dual transition crossing the same seam in the opposite direction — entering optimized code from a live interpreter loop, or leaving it via deopt (§8.5). OSR-out is structurally identical to the Deoptimizer Runtime's ordinary procedure; OSR-in is its mirror image (P12).

The central seam — marked in the diagram — is the boundary this entire project exists to make safe: everything above it is optimized machine code trusting speculative facts; everything below it is the interpreter, the ground truth those facts must always reduce back to (P9). No box in this diagram is permitted to cross that seam except through the Deoptimizer Runtime or the OSR machinery — there is no back-channel.

6. Design Principles

P1. Speculation is only sound if every assumption has a guard and every guard has a correct deopt path — an unguarded assumption is a miscompilation, not an optimization (Hölzle, Chambers & Ungar 1992).

P2. Deoptimization must reconstruct state observationally identical to what the interpreter would have produced — the program cannot tell it was ever optimized, which licenses the optimizer to be aggressive.

P3. Deopt is for the uncommon case: it may be slow, but it must be correct; the common path pays only the safepoint tax, never the deopt cost.

P4. Every live optimized value at a safepoint must be describable — register, stack, constant, or rematerialization recipe — or the safepoint cannot exist (I1).

P5. A deopt resumes at exactly the bytecode index whose state the debug info describes, never mid-bytecode.

P6. An invalidated assumption deoptimizes every dependent compiled method before that method executes again — partial invalidation is a correctness bug, not a performance one.

P7. Guards are data, not control-flow accidents: the uncommon-trap target is always reachable and always carries enough state to deoptimize (Duboscq et al. 2013).

P8. Rematerialization must preserve object identity exactly where source-language semantics require it — scalar replacement is an optimization illusion, never a semantic change.

P9. The interpreter is the ground truth for execution semantics; the optimizer's IR must always be provably reducible back to it via the state map.

P10. Deopt-thrashing is a design failure, not an acceptable steady state — a speculation that fails repeatedly must be blacklisted, not retried forever.

P11. Debug-info density is a deliberate size/speed tradeoff (ADR-04), never accidental — every byte of state-map is justified by a reconstruction requirement.

P12. OSR-in and OSR-out are dual operations over the same state-map contract; one cannot be correct while the other is broken.

P13. A dependency edge (assumption → nmethod) must be created before the guard it backs can be trusted — dependency registration precedes speculative compilation, never follows it.

P14. Tiered compilation is a state machine with explicit failure edges — there is no tier transition without a defined rollback.

P15. Telemetry is not an afterthought bolted onto a working mechanism — every invariant in §7 is paired with a named counter from the moment it is enforced, because an invariant nobody can observe firing is an invariant nobody can operationally trust.

P16. A speculation type's guard and its deopt path are designed together, never separately — a guard designed without its uncommon trap in mind risks being unrecoverable, and an uncommon trap designed without its guard in mind risks handling a case that can never actually occur.

Debugging methodology exercising these invariants: every conformance fixture in Phases 1–10 is run once fully interpreted and once optimized-then-deoptimized-at-every-safepoint (§28); a violation of I1–I13 fails the fixture, not merely a log line, and blocks CI (§29). 8.1 Speculation Catalogue

Each row's guard is inserted atomically with its speculative transform (§15.2) — the optimizer never has a window where the transform exists without its guard, which is the concrete mechanism behind P1 rather than a documentation convention. The DeoptReason column is the field every downstream telemetry counter in §26 keys on, so a new speculation type added after Phase 11 (§37's deferred polymorphic inline-cache generalization, for example) must extend this table before it extends any code.

8.3 Deoptimization Procedure — Named Steps

  1. Hit guard (runtime check fails), or an uncommon trap is taken unconditionally.
  2. Capture optimized machine state (registers + stack) at the trap PC.
  3. Look up debug info for that PC via SafepointId.
  4. Build interpreter frame(s) — one per InlineFrameChain entry, outermost first.
  5. Rematerialize eliminated/scalar-replaced objects per RematRecipe.
  6. Relink GC roots into the new interpreter frames.
  7. Resume in the interpreter at BytecodeIndex.

Worked end-to-end trace: a monomorphic-call speculation fails (the receiver's class changed) inside an inlined callee two frames deep.

Step 1: the receiver-class guard at the call site fails, taking DeoptReason::MegamorphicCall.

Step 2: the deoptimizer captures rax/rbx/spill-slots at the trap PC.

Step 3: SafepointId for that PC resolves to a state map describing two InlineFrameChain entries (caller, inlined callee).

Step 4: the outer caller's InterpreterFrame is built first from its slice of the state map, then the inlined callee's.

Step 5: no eliminated objects on this path — rematerialization is a no-op.

Step 6: the receiver reference is relinked as a GC root in the new callee frame.

Step 7: execution resumes in the interpreter at the callee's BytecodeIndex for the call instruction, which then dispatches virtually instead of monomorphically.

8.4 Rematerialization Model

RematRecipe carries, per virtual object, its ClassId and a field-by-field reconstruction list — each field either a direct ValueLocation or a nested recipe.

Worked example: a scalar-replaced Point{x, y} where x lives in rax and y is spilled at fp-24. The recipe is { class: Point, fields: [ (x, Register(rax)), (y, Stack(fp-24)) ] }.

Rematerialization allocates a new Point, assigns x and y from their locations, and installs the fresh object at the VirtualObjectDescriptor's slot in the reconstructed frame.

This is a fresh heap identity, valid because the source language never observed the pre-elimination identity while the object was scalar-replaced (P8) — the identity that matters is the one visible to the program from this point forward, not any hypothetical identity the eliminated allocation would have had.

8.5 On-Stack Replacement — Sequence Tables

OSR-in (interpreter loop → optimized code at a back-edge):

Step Actor Action
1 Interpreter back-edge counter for the loop crosses threshold (§9 ADR-10)
2 Tiered-compilation manager triggers an OSR-specific compile of the loop body
3 OSR machinery builds an OsrEntry state map matching current interpreter locals
4 Deoptimizer-adjacent OSR entry stub transfers live locals into optimized register/stack locations
5 Optimized code resumes execution at the loop back-edge in optimized form

OSR-out (the deopt itself, from optimized loop back to interpreter):

Step Actor Action
1 Optimized loop guard fails or uncommon trap taken mid-loop
2 Deoptimizer runtime runs the standard procedure (§8.3) at the loop's safepoint
3 Interpreter-frame builder rebuilds the loop's locals into an InterpreterFrame
4 Interpreter resumes the loop body at the corresponding BytecodeIndex

Both directions share the same DebugInfo-shaped state map (§8.2); OSR-in's step 3 and OSR-out's step 2 are the only steps that differ in direction of value transfer, not in format — a design choice that lets Phase 7 (§19) reuse Phase 1's encoder/decoder wholesale rather than building a parallel OSR-specific format.

8.7 Guard / Uncommon-Trap IR Representation

Following Duboscq et al. 2013, each guard is an IR node carrying a reference to a FrameState node — a full debug-info snapshot at that program point captured at compile time. The guard's condition edge falls through on success; its trap edge targets a shared trap-stub keyed by DeoptReason (ADR-17), which invokes the deoptimizer runtime with the guard's attached FrameState. This makes the trap target always reachable (I6) and always self-describing (I1) — the FrameState is not derived at trap time, it is carried since compilation.

Sharing trap stubs by DeoptReason rather than emitting one unique trap per guard (ADR-17) means the guard node itself is small — a condition plus two edges — while all of the actual deopt-invocation logic lives once, in the shared stub, rather than being duplicated at every guard site. This is what keeps guard density (M8) a code-size-cheap property rather than one that scales with the number of speculations a method carries.

8.9 Malformed / Hard Examples

  • A deopt is attempted at a PC with no debug info — this is a fatal build-time bug (I9); it must never occur at runtime, and any occurrence aborts with diagnostics rather than attempting silent recovery.
  • A rematerialization recipe graph contains a cycle (I12) — rejected at compile time by the recipe-graph cycle check.
  • A deopt storm: a speculation fails on nearly every invocation, driving the method repeatedly through Optimized→Deoptimized→Recompiled — caught by the thrashing guard (§8.8, I11) before it becomes a sustained performance collapse.
  • OSR-in is attempted into a loop whose live-variable set cannot be expressed in the optimized entry's expected state map (e.g., a value's type diverged between iterations) — rejected by I10, the loop remains interpreted.
  • A guard references a value the debug info does not describe — a compiler bug caught by the registry-guard cross-check (I7) before the nmethod is installed.
  • Two DeoptCounter entries collide on the same key for unrelated speculations (I16) — a counter-key derivation bug, caught by the key-collision audit before an unrelated speculation is wrongly blacklisted.
  • An exception unwind and a guard-triggered deopt target the same safepoint simultaneously on two different threads sharing a not-yet-invalidated nmethod — must resolve deterministically per-thread rather than racing on shared reconstruction state.

8.10 Failure-Path Example

A dead-code-elimination bug drops a live value v5 from a FrameState after a guard referencing it was already inserted.

At runtime the guard fails; the deoptimizer looks up the state map and finds no entry for v5 where the guard's snapshot expects one.

This violates I1 and is detected by the state-map completeness validator before any register/stack data is trusted.

The runtime aborts the deopt with a fatal trap rather than reconstructing a partially-wrong frame — a partial, silently-wrong reconstruction is strictly worse than a loud abort, per P2's observational-equivalence requirement.

The runtime emits statemap_completeness_gauge telemetry identifying the offending SafepointId.

The offending nmethod's compilation is rejected in the next build once the fixture reproducing this failure is added to the permanent regression suite (§12.5, §28).

// deopt-core: assumptions, guards, traps, deopt semantics — hot compile-time path
// Assumption is immutable once registered (I7); mutation only via new registration.
struct Assumption { id: AssumptionId, kind: AssumptionKind, class_dep: Option<ClassId> }
enum AssumptionKind { TypeSpeculation(TypeId), MonomorphicCall(MethodId), NullCheckElision, BoundsCheckElision, ClassHierarchyLeaf(ClassId), IntegerRange(RangeBounds) }
struct Guard { id: GuardId, assumption: AssumptionId, frame_state: FrameStateId, trap: UncommonTrapId }
struct UncommonTrap { id: UncommonTrapId, reason: DeoptReason, action: DeoptAction }
enum DeoptReason { TypeMismatch, MegamorphicCall, NullCheckFailed, BoundsCheckFailed, ClassHierarchyChanged, IntegerOverflow, ExplicitInvalidation }
enum DeoptAction { ReinterpretAndRecompile, ReinterpretOnly, Blacklist(AssumptionKind) }

Ownership: Assumption/Guard/UncommonTrap are owned by the CompiledMethod that emitted them, immutable post-publish (I7). Concurrency: read-shared across mutator threads, written only during compilation (single-writer). Persistence: none beyond process lifetime; not serialized across restarts. Hot path: guard evaluation only (the check itself, ADR-03); everything else is cold/compile-time or cold/deopt-time.

Compatibility: AssumptionKind is additive-only across minor versions (§27) — a new variant is a compatible change, a semantic change to an existing variant is not. Mutation of DeoptAction's Blacklist payload is the one place this type family is mutated post-compile, and it is mutated only by the Phase-9 thrashing guard through the single-choke-point tiered-compilation manager (§22.2), never directly by a guard-evaluation call site.

// deopt-core: safepoints and debug info — cold deopt-time path, hot-path adjacent
struct SafepointId(u64)
struct Safepoint { id: SafepointId, pc: MachinePc, debug_info: DebugInfoId }
struct DebugInfo { bytecode_index: BytecodeIndex, inline_frames: Vec<InlineFrameDescriptor>, values: Vec<ValueLocation>, live_refs: BitSet }
enum ValueLocation { Register(RegId), Stack(StackOffset), Constant(ConstValue), Rematerialize(RematRecipeId) }
struct StateMap { entries: Vec<(SafepointId, DebugInfo)>, checksum: u64 }
struct BytecodeIndex(u32)

Ownership: StateMap owned by its CompiledMethod, one per nmethod, immutable and checksummed (I8) once compiled. Serialization: compact compressed encoding (ADR-04) inside the nmethod's metadata region; not shared cross-process. Compatibility: versioned alongside the nmethod format (§27). Hot path: none — DebugInfo is read only on the deopt-time cold path; the safepoint poll itself (not shown here) is the only hot-path cost (§4).

Mutation: strictly none after the checksum (I8) is computed and stored — any subsequent change to a StateMap's bytes, whether malicious or accidental, is detectable by definition, which is exactly the property T1 and FM-1 rely on for detection.

// deopt-core: virtual objects and rematerialization — cold deopt-time path
struct VirtualObject { id: VirtualObjectId, class_id: ClassId, fields: Vec<(FieldId, ValueLocation)> }
struct RematRecipe { id: RematRecipeId, target: VirtualObject, deps: Vec<RematRecipeId> }
struct ScalarReplacement { original_alloc: AllocSiteId, recipe: RematRecipeId }

Ownership: RematRecipe owned by the DebugInfo entry referencing it; the dependency list forms a DAG, verified acyclic at compile time (I12). Mutation: none post-compile. Hot path: never — rematerialization only executes during an actual deopt.

Concurrency: a RematRecipe is read by exactly one thread — the thread performing its own deopt — and is never shared across threads even though the underlying CompiledMethod it belongs to may be executing concurrently on many threads; each thread's deopt reads the same immutable recipe data independently.

// deopt-core: frames — the interpreter/optimized seam representation
struct InterpreterFrame { function: MethodId, bytecode_index: BytecodeIndex, locals: Vec<Value>, operand_stack: Vec<Value>, caller: Option<Box<InterpreterFrame>> }

struct FrameState { id: FrameStateId, safepoint: SafepointId, debug_info: DebugInfoId }

Ownership: InterpreterFrame is the reconstruction target, owned by the executing thread's stack once built (thread-local, no sharing). OptimizedFrame is a transient capture, dropped once reconstruction completes (I5 — nothing may be lost in that transition). Concurrency: single-threaded per deopt event; a thread only ever deoptimizes its own frame.

Persistence: neither type is ever serialized to disk or shared across process boundaries; both exist only for the duration of one deopt event on one thread's call stack, consistent with §1's deployment model of an in-process, no-durable-state subsystem.

// deopt-core: the deoptimizer, OSR, and compiled-method bookkeeping
struct Deoptimizer { /* capture, lookup, rebuild, resume — drives §8.3 */ }

12. Phase 0 — Skeleton, Toy Tiered Runtime, and CI

12.1 Objectives

Stand up the repository skeleton (§10), the deopt-core types (§11), a minimal toy interpreter (deopt-interp-toy) that serves as the semantics oracle, a trivial optimizer (deopt-opt-toy) that performs one speculative transform, and a CI pipeline that can run both.

12.2 Detailed Implementation Steps

The interpreter implements a small stack-based bytecode (arithmetic, locals, conditional jumps, calls) whose execution model is treated as ground truth per P9. The toy optimizer performs constant folding plus exactly one speculative transform — monomorphic-call inlining guarded per P1 — so that Phase 0 already exercises the guard/UncommonTrap types from §11 end-to-end, even though the deoptimizer itself (Phase 2) is still a stub that just aborts. CI (ADR-24) runs the interpreter's own unit suite and a placeholder differential job (ADR-22) that will grow into §28's primary gate.

The repository skeleton itself is not incidental scaffolding: the crate boundaries chosen here (§10, §11) are the ones every later phase extends in place rather than restructures, because a mid-project crate reorganization would invalidate the fixture corpus's stability guarantees (§23.9's permanent-regression-fixture discipline depends on file paths staying put). The deopt-core crate is deliberately kept dependency-free of both deopt-interp-toy and deopt-opt-toy at this stage, enforcing at the crate-graph level that the core types (§11) are genuinely host-agnostic rather than accidentally coupled to this one toy runtime — a discipline that pays off once a real host JIT (outside this project's boundary, §1) needs to depend on deopt-core without pulling in the toy interpreter.

12.3 Deliverable

A runnable interpreter, a toy optimizer producing guarded optimized code that the (stubbed) deoptimizer can detect but not yet fully recover from, and a green CI pipeline.

12.4 Acceptance Criteria

  • Interpreter passes ≥95% branch coverage on its own opcode suite.
  • Toy optimizer's guard-insertion rate matches the ≤1-guard-per-8-IR-nodes target (§4).
  • CI wall-clock ≤10 minutes per run.

12.5 Conformance Fixtures

  • arithmetic.bc — baseline opcode coverage.
  • recursive.bc — recursive call depth handling.
  • malformed_jump.bc — verifier-reject fixture.
  • monomorphic_call.bc — exercises the one speculative transform.
  • guard_stub_trip.bc — guard fails, deoptimizer stub aborts cleanly rather than corrupting state.

12.6 Pitfalls

  • Interpreter and optimizer silently diverge on integer-overflow semantics — caught only by later differential testing unless a Phase-0 unit test pins the behavior explicitly.
  • Guard insertion in the toy optimizer forgets to register the Assumption with anything (dependency tracker doesn't exist yet) — acceptable for Phase 0 but must be flagged as a TODO tied to Phase 3/4, not silently forgotten.
  • CI green on a broken interpreter because the fixture set is too shallow — mitigated by requiring the malformed-input fixture to fail loudly.
  • The toy optimizer's one speculative transform silently degenerating into a no-op transform under a compiler refactor, giving a false sense that guard machinery is being exercised when it is not — mitigated by asserting a nonzero guard-insertion count in CI, not just a passing test.
  • Bytecode verification (delegated per §1 to Bytecode-Verifier 247 in the real system) being informally reimplemented ad hoc inside the toy interpreter rather than kept as a clearly-labeled stand-in — risks the project quietly growing scope it explicitly disclaimed in §1's non-goals.

12.7 Performance Concerns

None yet load-bearing; establish the benchmark harness (benchmarks/) now so Phase 1+ has a baseline to regress against.

12.8 Edge Cases

  • Empty method body.
  • A call site with zero call history (cannot yet be monomorphic).
  • Recursive calls exceeding a small fixed depth.
  • A bytecode program that is syntactically well-formed but semantically degenerate (an infinite loop with no side effects, used later to bound soak-test runtime rather than to test correctness).

12.9 Failure Analysis

An incorrect interpreter contaminates every later correctness claim, since it is the oracle the entire differential harness (§28) depends on — this is the single highest-leverage risk in the whole project and is treated as a blocking gate before Phase 1 begins. Concretely, the gate is operationalized as a requirement that the interpreter's own unit suite (12.4) and a hand-verified trace of at least one non-trivial fixture's full execution (opcode-by-opcode, cross-checked against a manually computed expected trace) both pass before any Phase-1 work starts, rather than trusting suite-green alone.

12.10 Operational Notes

  • Export opcode-dispatch counters from day one.
  • Export guard-insertion counters from day one (ADR-20, ADR-21).
  • Wire both into the same telemetry pipeline §26 will later depend on, so it does not have to be retrofitted.

13. Phase 1 — Safepoints and the Debug-Info / State-Map Model

13.1 Objectives

Implement Safepoint, DebugInfo, ValueLocation, and StateMap (§11) for real: every safepoint the toy optimizer creates must carry a complete, checksummed state map satisfying I1, I8, and I9.

13.2 Detailed Implementation Steps

Following the HotSpot OopMap/debug-info model and ADR-04's compressed encoding, each safepoint records, per live SSA value, its ValueLocation and whether it is a GC root (LiveRefSet). The safepoint-placement verifier (I9) runs at compile time and rejects any method whose optimizer-inserted guard or call site lacks an attached safepoint — this is the concrete mechanism satisfying P4. InlineFrameChain construction begins here even though the toy optimizer's inlining is trivial, because the field's shape (§8.2) must be right before Phase 2 builds real interpreter frames from it.

The encode/decode split is itself a deliberate boundary: encoding happens once, at compile time, and may spend more CPU than decoding, which happens on the latency-bounded deopt path (§4). This phase therefore builds two distinct benchmarks from day one — encode throughput (amortized against compile time, generous budget) and decode latency (amortized against deopt latency, tight budget) — rather than a single combined "state-map performance" number that would obscure which side of the asymmetry a future regression actually lands on. The compression scheme itself (ADR-04) is implemented behind a trait boundary specifically so a future ADR-04 revision (§37's deferred delta-encoding feature) can swap the encoding without touching any of the ValueLocation/DebugInfo call sites built in later phases.

13.3 Deliverable

A deopt-statemap crate that encodes/decodes StateMaps with checksums (I8), plus a build-time verifier enforcing I9.

13.4 Acceptance Criteria

  • State-map size ≤64 bytes/safepoint typical (§4).
  • Checksum validation rejects 100% of injected corruption in the fixture set.
  • Safepoint-placement verifier rejects 100% of fixtures with a deliberately omitted safepoint.

13.5 Conformance Fixtures

  • safepoint_complete.bc — baseline positive case.
  • safepoint_missing.bc — I9 violation, must reject at build time.
  • checksum_corrupt.meta — I8 violation, must reject at decode time.
  • deep_inline_statemap.bc — stresses InlineFrameChain depth.

13.6 Pitfalls

  • Off-by-one BytecodeIndex recorded at the safepoint versus the index the interpreter would actually resume at (violates I2 in Phase 2, but the bug is planted here).
  • Register/stack location aliasing: two ValueLocations claiming the same physical register at one safepoint.
  • Checksum computed over the pre-compression buffer but validated over the post-compression buffer — an encoding-order bug, not a data bug.
  • LiveRefSet under-approximation — a GC root silently omitted, invisible until a Phase 8-style GC-interaction test exists.
  • InlineFrameChain ordering reversed (innermost-first instead of outermost-first, or vice versa) relative to what Phase 2's frame builder expects — a pure convention mismatch that produces plausible-looking but semantically inverted frames.
  • Compression (ADR-04) applied non-deterministically (e.g. iteration order over a hash map affecting byte layout), breaking the reproducible-build guarantee (§29) even though the decoded semantics are correct.

13.7 Performance Concerns

State-map encode time must not dominate compile time; decode time (cold path) is allowed to be slower but must stay ≤50 µs (§4) since Phase 2's deopt latency budget depends on it.

13.8 Edge Cases

  • A safepoint with zero live values (empty method prologue).
  • A safepoint at maximal supported inline depth (§4's 4096-frame ceiling, exercised at a much smaller scale here).
  • A value that is both a GC root and a rematerialization target.

13.9 Failure Analysis

Any bug in this phase is invisible until Phase 2 attempts to use the state map for real reconstruction — this phase's fixtures must therefore include synthetic "read-back" checks that decode a freshly-encoded map and assert field-for-field equality, rather than relying solely on Phase 2 to surface bugs.

13.10 Operational Notes

  • Emit statemap_size_bytes per compiled method.
  • Emit statemap_encode_latency_ns per compiled method.
  • Retain both from this phase forward — they are the numeric basis for the §34 capacity model's debug-info-size formula.

14. Phase 2 — Basic Deopt: Guard Failure to Rebuilt Interpreter Frame

14.1 Objectives

Implement the Deoptimizer (§11) end-to-end for the simplest case: a single, non-inlined frame, no eliminated objects — a guard fails, and the runtime rebuilds one correct InterpreterFrame and resumes.

14.2 Detailed Implementation Steps

This phase implements the seven named steps of §8.3 for real, following Hölzle, Chambers & Ungar 1992's foundational procedure and satisfying I2 (precise BytecodeIndex resumption) and I5 (no observable value lost). The deoptimizer captures the OptimizedFrame (registers + stack slots) at the trap PC, resolves its SafepointId to the Phase-1 StateMap, and drives the interpreter-frame builder (ADR-11, top-down — trivial here with only one frame) to produce an InterpreterFrame. No rematerialization or dependency tracking exists yet (P6, P8 land in later phases); this phase's guards are limited to the type-speculation and integer-range rows of §8.1, which never require rematerialization.

The Deoptimizer (§11) is implemented as a stateless service specifically so that its correctness can be reasoned about one call at a time: given a SafepointId and a captured OptimizedFrame, its output is a pure function of the corresponding DebugInfo, with no hidden dependency on prior deopt history (that history lives in DeoptCounter, owned elsewhere, and is irrelevant to whether this reconstruction is correct). This separation is what lets Phase 9's thrashing guard be added later without touching the reconstruction logic itself — the counter is bolted on around the outside of a Deoptimizer call, never threaded through it.

14.3 Deliverable

A working deopt-runtime crate that turns a guard failure into a resumed interpreter execution, matching interpreted output on every Phase-2 fixture.

14.4 Acceptance Criteria

  • Deopt latency p99 ≤50 µs (§4) on the single-frame fixture set.
  • 100% of fixtures produce interpreter state observationally identical (I5) to a fully-interpreted run of the same input — the first real application of the §28 differential property, in miniature.

14.5 Conformance Fixtures

  • type_guard_fail.bc — type-speculation guard failure.
  • int_range_overflow.bc — integer-range speculation failure.
  • guard_never_fires.bc — regression: optimized path must stay fast when the guard holds.
  • resume_bci_exact.bc — pins I2 precisely.

14.6 Pitfalls

  • Register capture races with a concurrent safepoint poll from another mechanism, corrupting the snapshot.
  • Off-by-one resumption (the planted Phase-1 bug, if not caught, surfaces here as wrong output on the very next bytecode).
  • Stack-slot offsets computed relative to the wrong frame pointer after a calling-convention (ADR-12) mismatch between the toy optimizer's codegen and the deoptimizer's assumptions.
  • Guard-fires-but-deopt-succeeds masking a different latent bug (a false positive "it works" outcome) — mitigated by requiring the fixture to also assert the reason recorded matches expectation.
  • Heap allocation performed inside the capture step (violating the "capture must not itself require a safepoint" rule) causing a re-entrant safepoint poll mid-capture.
  • The Deoptimizer's statelessness assumption (14.2) violated by an implementation detail that caches a stale DebugInfo lookup across calls, reintroducing hidden state the design explicitly rejected.

14.7 Performance Concerns

The capture step must not itself require a safepoint (it is the safepoint); avoid unnecessary heap allocation on the deopt path since it is intentionally the cold path but still latency-bounded (§4).

14.8 Edge Cases

  • A guard failing on the very first invocation (immediately after Tier1→Optimized transition).
  • A guard failing during the optimized prologue before any locals are live.
  • Two guards on the same safepoint (must produce identical DebugInfo lookups regardless of which fired).

14.9 Failure Analysis

A broken reconstruction here invalidates every later phase's correctness claim, since Phases 3–10 add speculation types and complexity on top of this base procedure — this phase is gated with the same severity as Phase 0's interpreter.

14.10 Operational Notes

  • Introduce deopt_latency_ns (histogram) now (ADR-21).
  • Introduce deopt_count_total{reason} now (ADR-21).
  • Both become the first two production metrics in §26's dashboard set — every later phase's counters are added alongside these, never replacing them.

15. Phase 3 — The Speculation / Assumption Framework

15.1 Objectives

Generalize Phase 2's single-guard mechanism into the full Assumption/AssumptionKind/Guard registry (§11), covering all six §8.1 speculation types except class-hierarchy (which needs Phase 4's dependency tracker to be safe) and type-feedback-driven monomorphic calls (Phase 6).

15.2 Detailed Implementation Steps

Following Chambers & Ungar 1991's SELF customization work and Duboscq et al. 2013's guard/FrameState IR model, each speculation type in §8.1 becomes a first-class AssumptionKind variant with its own guard-insertion rule and DeoptReason. The assumption registry (P1, P4) is per-method and append-only (P11 discipline: every registered assumption is deliberate). Guards attach a FrameState (§8.7) at insertion time, not lazily, so I1 holds by construction rather than by later patching.

Each speculation type's guard-insertion rule is implemented as a small, independently testable function taking the pre-speculation IR and returning either an unmodified IR (assumption not applicable) or an IR with the guard node and its attached FrameState inserted atomically — "atomically" meaning no intermediate IR state exists where the speculative transform has happened but the guard has not, closing off an entire class of P1-violating bugs by construction rather than by later review. This mirrors the template Phase 6 and Phase 7 will reuse for their own speculation types, so getting the shape right here is disproportionately valuable to every later phase.

15.3 Deliverable

A deopt-core extension plus toy-optimizer integration exercising null-check elision, bounds-check elision, and integer-range speculation, each with its own guard and correct DeoptReason.

15.4 Acceptance Criteria

  • Guard density stays ≤1/8 IR nodes (§4) across the expanded fixture set.
  • Each of the three new speculation types has ≥1 fixture proving both the "assumption holds" fast path and the "assumption fails" deopt path.

15.5 Conformance Fixtures

  • null_check_elide.bc — null-check elision speculation.
  • bounds_check_elide.bc — bounds-check elision speculation.
  • int_range_speculate.bc — integer-range speculation.
  • multi_guard_same_safepoint.bc — two guards sharing one safepoint.
  • assumption_registry_overflow.bc — stress: many assumptions on one method.

15.6 Pitfalls

  • Two guards for logically the same assumption registered twice, doubling deopt bookkeeping without doubling safety.
  • A guard inserted after the safepoint it should be attached to, violating P4's ordering requirement.
  • Bounds-check elision hoisted incorrectly outside a loop whose bound is itself loop-variant — a classic LICM/speculation interaction bug.
  • DeoptReason chosen generically ("Unknown") instead of precisely, which silently degrades §26's per-reason telemetry.
  • The "atomically inserted" guard-and-transform discipline (15.2) violated by a refactor that splits guard insertion and transform application across two optimizer passes, reopening the intermediate-state window it was designed to close.
  • An assumption registered for a value that is not actually live at the attached FrameState's safepoint, producing a guard that references dead data.

15.7 Performance Concerns

Guard evaluation cost on the hot path must stay ≤3 ns (§4) per guard; bounds-check-elision guards in particular must not reintroduce the cost of the checks they were meant to eliminate.

15.8 Edge Cases

  • A method with zero eligible speculations (falls through to plain Tier1 semantics).
  • A method whose every value is speculated on (guard-density ceiling stress).
  • Nested elided bounds checks in a doubly-nested loop.

15.9 Failure Analysis

An incorrectly-guarded speculation is, per P1, a miscompilation — this phase's fixtures must include intentionally-adversarial inputs (e.g. an out-of-bounds index right at the elided check's boundary) specifically designed to falsify each assumption, not just inputs that happen to hold it.

15.10 Operational Notes

  • Add a guard_density_ratio gauge.
  • Add an assumption_registry_size gauge.
  • Feed both into the §30 performance-engineering methodology and the §31 scalability bottleneck analysis from this phase forward.

16. Phase 4 — Dependency Tracking and Invalidation

16.1 Objectives

Implement Dependency/DependencyTracker/Invalidation (§11) so that class-hierarchy speculation (§8.1) becomes safe, satisfying I3, I7, and I13.

16.2 Detailed Implementation Steps

Following Click & Rose 2002's fast-subtype-checking work and the general CHA-dependency pattern used in HotSpot, every class-hierarchy Assumption (e.g. "class C is a CHA leaf") is registered with the DependencyTracker (ADR-08's hash-map-keyed structure) before any guard trusting it compiles (P13). A class load walks the assumption's dependent-nmethod set and eagerly bulk-invalidates (ADR-09) every one, forcing each through Optimized→Deoptimized→Reprofiled (§8.8) before it can execute again — this is the concrete mechanism enforcing I3. Bulk invalidation is safepoint-serialized (ADR-19): no dependent nmethod's tier field changes outside a global safepoint.

Registration and invalidation are deliberately kept as two halves of one atomic-feeling operation from the compiler's point of view: DependencyTracker::register returns a handle the compiler must hold until the nmethod is fully published, and a class load occurring while that handle is outstanding blocks publication of the in-flight nmethod rather than racing it (closing the exact ordering gap named as the first pitfall in 16.6). This is more conservative than some production JVMs' generation-counter-only approaches, but is the correct choice for this project's Phase-4 scope (§9 ADR-09), with generation counters layered on top as a fast-path re-check rather than as the sole mechanism.

16.3 Deliverable

A deopt-deps crate: registration API, O(1)-amortized invalidation on class load, and the safepoint-serialized tier-mutation path.

16.4 Acceptance Criteria

  • 100% of dependent nmethods deoptimized before next invocation post-class-load (I3, zero tolerance).
  • Dependency-tracker memory ≤200 bytes/assumption (§4).
  • Invalidation-to-safepoint-serialized latency within the recompilation-latency budget (§4, ≤20 ms).

16.5 Conformance Fixtures

  • cha_leaf_speculate.bc — baseline CHA-leaf speculation.
  • class_load_invalidate.bc — the core scenario: speculate, then load a subclass, then verify deopt.
  • concurrent_class_load.bc — invalidation racing live mutator threads.
  • dependency_fanout_stress.bc — one assumption, many dependent methods.

16.6 Pitfalls

  • A dependent method compiled between the class load and the invalidation sweep, sneaking in with a stale assumption — an ordering race that P13 exists specifically to prevent; must be closed by holding the registry lock across the whole class-load-to-invalidation window.
  • Invalidation walks the dependent set but forgets to also blacklist candidate future recompiles of the same now-false assumption, causing an immediate re-speculate-and-refail cycle (a preview of Phase 9's problem, but a correctness gap here if not handled).
  • Dependency-tracker memory unbounded growth when methods are never explicitly evicted from the code cache.
  • A stale dependency executes invalidated code due to a safepoint being skipped (ADR-19 violated by a rogue polling omission) — this is also T9 in §24.
  • The registration handle (16.2) held indefinitely by a compile that never completes (e.g. a crashed compiler worker), permanently blocking future publications for the same assumption — must be paired with a timeout/cleanup path.
  • Two class loads targeting overlapping dependent sets processed out of order, leaving a brief window where a method reflects only one of two now-false assumptions.

16.7 Performance Concerns

Bulk invalidation fan-out cost is O(dependents) (§31) — must not block unrelated mutator threads longer than the safepoint-synchronization budget (§4, ≤20 ms referenced from the parent constraint table).

16.8 Edge Cases

  • An assumption with zero dependents (registered speculatively, never actually relied upon).
  • A class load that invalidates its own compiling-in-progress method.
  • Simultaneous invalidation from two unrelated class loads touching overlapping dependent sets.

16.9 Failure Analysis

A missed invalidation is silent data corruption from the program's perspective — the method keeps running on a false assumption with no crash, which is why I3's detection (nmethod generation-counter check) must be unconditionally enforced on every entry, not just as a debug-build assertion.

16.10 Operational Notes

  • Add a dependency_invalidation_fanout gauge.
  • Add stale_nmethod_exec_total (I3's telemetry counter, §7).
  • Treat a nonzero stale_nmethod_exec_total as a page-immediately correctness event per §26 — no severity downgrade.

17. Phase 5 — Rematerialization of Eliminated / Scalar-Replaced Objects

17.1 Objectives

Implement VirtualObject/RematRecipe/ScalarReplacement (§11) so that a deopt through a point where escape analysis eliminated an allocation correctly rebuilds that object, satisfying I4, I5, and I12.

17.2 Detailed Implementation Steps

Following the virtual-object-recovery approach used in PyPy's meta-tracing and HotSpot's escape-analysis-integrated deopt, each scalar-replaced allocation gets a RematRecipe attached at the safepoints where it would otherwise be live (§8.4). Recipes form a DAG (I12) — a field of one virtual object may itself be another virtual object — and are rebuilt eagerly (ADR-07) during interpreter-frame construction, immediately after step 4 and before step 6 of §8.3's procedure. Object identity (P8) is preserved by allocating the rematerialized object fresh only once per deopt event and reusing that single instance for every subsequent field reference within the same reconstruction, never allocating duplicates for the same VirtualObjectId.

The single-instance-per-VirtualObjectId-per-deopt-event guarantee is implemented via a reconstruction-local table keyed by VirtualObjectId, consulted before every allocation the recipe walk would otherwise perform: a cache hit returns the already-rematerialized instance, a cache miss allocates and populates the table before recursing into that object's own field recipes. This table is scoped strictly to one deopt event — it is not a cross-deopt cache — which is what keeps I12's acyclicity requirement sufficient for termination (a per-event cache plus a DAG guarantees the walk visits each node exactly once).

17.3 Deliverable

A deopt-remat crate integrated into the Phase-2 deoptimizer's step 5, handling both leaf scalar values and nested virtual-object graphs.

17.4 Acceptance Criteria

  • 100% object-identity preservation on fixtures requiring it (I4, zero tolerance, differential-harness-gated).
  • Rematerialization cost within the §34 capacity-model formula (fields × store cost).
  • Zero cycles reach runtime (I12, caught at compile time in 100% of fixtures).

17.5 Conformance Fixtures

  • scalar_replace_point.bc — the canonical two-field example from §8.4.
  • nested_virtual_objects.bc — recipe DAG with nested objects.
  • remat_cycle_reject.ir — compile-time rejection fixture.
  • shared_field_identity.bc — two references to the same virtual object must remat to the same instance.
  • partial_escape.bc — an allocation that escapes on one control-flow path but not another.

17.6 Pitfalls

  • Rematerializing the same virtual object twice under two different field references, breaking identity (I4) even though each individual field value is correct.
  • A recipe dependency ordering bug rebuilding a nested object before its own fields are available.
  • Partial escape analysis interacting badly with rematerialization: the object escaped on the taken path, so it already exists on the heap, but the recipe naively allocates a duplicate.
  • Recipe DAG depth unbounded, risking stack overflow in the (recursive, naturally expressed) rematerialization walk — must be iterative or explicitly depth-bounded.
  • The per-deopt-event cache (17.2) accidentally scoped too broadly (e.g. reused across two different deopt events on the same thread), reintroducing cross-event identity aliasing the design specifically avoids.
  • A RematRecipe referencing a ValueLocation that was itself supposed to be rematerialized, but the dependency edge was omitted from the DAG — producing an incomplete rather than a cyclic graph, which I12's cycle check does not catch.

17.7 Performance Concerns

Rematerialization is allowed to allocate (it is the deopt cold path, P3) but must avoid triggering a GC cycle mid-reconstruction if at all avoidable, since a GC during an in-progress frame rebuild is exactly the safepoint/GC-interaction hazard flagged in §8.9 and T8 (§24).

17.8 Edge Cases

  • A virtual object with zero fields (a marker/singleton pattern).
  • A recipe referencing a location that is itself a constant (no computation needed, pure copy).
  • A virtual object whose class has since been redefined (interacts with Phase 4's invalidation — must deopt before remat is even attempted, not race with it).

17.9 Failure Analysis

Rematerialization bugs are the "silent semantic corruption" failure mode (§24 T1's clearest concrete instance) — wrong field values or broken identity produce a program that keeps running with wrong data rather than crashing, which is why the differential harness (§28) treats every remat fixture as a first-class correctness gate, not a secondary check.

17.10 Operational Notes

  • Add remat_bytes_total.
  • Add remat_identity_mismatch_total (I4's counter).
  • Track remat latency separately from overall deopt latency, since it is additive on top of §14's base budget rather than a substitute for it.

18. Phase 6 — Type-Feedback Speculation: Monomorphic Calls and Inline Caches

18.1 Objectives

Implement monomorphic-call speculation for real, backed by runtime type feedback (profile-driven, not compile-time-only), following Hölzle & Ungar 1994 and the Deutsch & Schiffman 1984 inline-cache model.

18.2 Detailed Implementation Steps

The ProfileData.type_feedback table (§11) records, per call site, the observed receiver classes during Profiling/Tier1 execution. When a call site is monomorphic in the profile, the optimizer speculates AssumptionKind::MonomorphicCall (§8.1) with a receiver-class guard — an inline cache in spirit (Deutsch & Schiffman 1984) but backed by this project's general guard/FrameState machinery (P7) rather than a bespoke mechanism. A call site that becomes polymorphic-then-megamorphic during profiling is not speculated at all (avoiding a guaranteed-fail guard); one that is monomorphic in the profile but proves wrong at runtime deopts via DeoptReason::MegamorphicCall and feeds Phase 9's thrashing guard.

A polymorphic (2-4 receiver classes, per the conventional inline-cache taxonomy) call site is deliberately left unspeculated in this phase rather than compiled as a small dispatch table with N guards — that generalization (a polymorphic inline cache proper) is PhaseDeferred("Phase 6") (§37), since it multiplies guard density (M8) per call site and this phase's exit criteria only require the monomorphic case to be correct and profitable. The receiver-class guard's placement is chosen to be the very first instruction of the inlined callee's FrameState window, which is what makes the §8.3 worked trace's two-inline-frame example (written against this exact phase) resume cleanly at the call instruction rather than partway into the callee.

18.3 Deliverable

Profile-driven monomorphic-call speculation integrated into the toy optimizer, plus the receiver-class guard and its deopt path (reusing Phase 2's single-frame procedure, now inlined per Phase 3's InlineFrameChain).

18.4 Acceptance Criteria

  • 100% of monomorphic-in-profile call sites in the fixture set correctly speculate.
  • 100% of receiver-class-guard failures correctly deopt to the exact call-site BytecodeIndex (I2) with the pre-call receiver and arguments intact (I5).

18.5 Conformance Fixtures

  • monomorphic_stable.bc — never fails.
  • monomorphic_then_polymorphic.bc — the §8.3 worked-trace scenario.
  • megamorphic_never_speculate.bc — regression: must not even attempt the guard.
  • inline_depth_2_call_guard.bc — guard inside an inlined callee.

18.6 Pitfalls

  • Speculating monomorphic on a call site whose profile sample size was too small, causing near-certain immediate deopt (a Phase-9-relevant tuning problem, but a Phase-6 fixture must at least detect it).
  • Receiver-class guard placed after a side-effecting instruction that should not re-execute on deopt (a preview of Phase 8's exception/control-flow complexity, must be avoided here by placing the guard strictly before any side effect).
  • Guard failure inside a doubly-inlined call chain resuming at the wrong inline-frame level.
  • Type-feedback table itself becoming stale relative to the currently-compiled speculation (a data-freshness bug distinct from the invalidation model of Phase 4).
  • A polymorphic call site misclassified as monomorphic due to an undersized profiling sample window, speculating too early (a specific instance of the general sample-size pitfall above, worth its own fixture because it is the single most common real-world cause of Phase-9-relevant thrashing).
  • The deliberately-unspeculated polymorphic case (18.2) accidentally falling through to a default monomorphic guess rather than staying genuinely unspeculated, silently reintroducing the guaranteed-fail-guard problem the design avoids.

18.7 Performance Concerns

Guard cost for a monomorphic call must be cheaper than the megamorphic dispatch it replaces, or the speculation has negative value even when it holds — measure both paths in benchmarks/.

18.8 Edge Cases

  • A call site invoked exactly once (no meaningful profile).
  • A call site whose receiver class is the same object every time (monomorphic by identity, not just by class).
  • Recursive monomorphic self-calls.

18.9 Failure Analysis

An incorrect deopt reason or resumption point on a call-site guard failure is especially costly because call sites are typically hot — this is where a subtle Phase-2/Phase-3 bug is most likely to surface first under real workloads, making this phase's differential coverage disproportionately important.

18.10 Operational Notes

  • Add a per-call-site monomorphic_hit_rate metric.
  • Add megamorphic_guard_reject_total.
  • Treat both as the primary signals Phase 9's thrashing guard will consume — do not let them drift or get renamed without updating that downstream consumer.

19. Phase 7 — OSR-In: Interpreter to Optimized Code at a Loop Back-Edge

19.1 Objectives

Implement OsrEntry (§11) and the OSR-in half of §8.5, following Fink & Qian 2003 and Lameed & Hendren 2013, so a long-running interpreted loop can transition into optimized code mid-execution without waiting for method re-entry.

19.2 Detailed Implementation Steps

A back-edge counter (ADR-10) crossing threshold triggers an OSR-specific compile of the loop body. The OSR entry stub builds an OsrEntry.entry_state_map describing exactly the interpreter locals live at the loop header, then transfers them into the optimized code's expected register/stack locations — the mirror image of Phase 2's deopt procedure, satisfying P12's duality requirement. I10 governs admission: if the live-variable set cannot be expressed in the optimized entry's state map (e.g. divergent types across iterations), OSR-in is rejected and the loop stays interpreted rather than entering unmappable state.

Because OsrEntry.entry_state_map is structurally a DebugInfo (§8.2) describing an entry point rather than an exit point, this phase reuses the Phase-1 encoder/decoder wholesale rather than building a parallel format — the only new logic is the admission check (I10) and the value-transfer direction (interpreter-to-optimized instead of optimized-to-interpreter). This structural reuse is deliberate: any bug found in the Phase-1 decoder by this phase's fixtures is a real Phase-1 bug worth backporting, and any OSR-specific bug is, by construction, confined to the small amount of genuinely new code (admission check plus transfer direction), which keeps this phase's fixture set focused rather than needing to re-verify the whole state-map format from scratch.

19.3 Deliverable

A deopt-osr crate implementing OSR-in, integrated with the Phase-1 state-map format (an OsrEntry is structurally a DebugInfo describing an entry rather than an exit).

19.4 Acceptance Criteria

  • OSR-in trigger latency ≤5 ms (§4).
  • 100% of admitted OSR-in fixtures produce output identical to continued interpretation — the differential property applied to a mid-loop tier transition.
  • 100% of I10-violating fixtures are correctly rejected rather than corrupting state.

19.5 Conformance Fixtures

  • osr_simple_loop.bc — baseline OSR-in.
  • osr_divergent_type.bc — I10 rejection case.
  • osr_nested_loop.bc — nested-loop OSR admission.
  • osr_threshold_tuning.bc — regression: verify the back-edge counter threshold itself, ADR-10.

19.6 Pitfalls

  • Transferring a loop-carried value into the wrong optimized-code location, corrupting the very first optimized iteration silently.
  • Racing the back-edge counter against a concurrent class-load invalidation targeting the same method (Phase 4 interaction) — OSR-in must not admit into a method that is simultaneously being invalidated.
  • Rejecting OSR-in too conservatively (I10 overly strict), losing the performance benefit for loops that are actually mappable — a tuning bug, not a correctness one, but tracked as a pitfall since it silently defeats the phase's purpose.
  • Nested loops OSR-ing at the wrong header, entering optimized code partway through an outer loop's setup.
  • The structural-reuse assumption (19.2) breaking silently because a Phase-1 decoder change assumed exit-only usage (e.g. an optimization that is only valid for optimized-to-interpreter direction) and was never re-validated against the entry-direction use introduced here.
  • A back-edge counter shared incorrectly between two textually-identical but distinct loop instances (e.g. inside two different inlined copies of the same source loop), causing one loop's OSR trigger to misfire for the other's iteration count.

19.7 Performance Concerns

OSR-in compile must be fast enough that the loop has not already finished by the time it completes (ADR-10's rationale) — track compile-to-entry latency as a distinct metric from steady-state Optimized-tier compile latency.

19.8 Edge Cases

  • A loop that OSRs and then immediately hits a guard failure on its very first optimized iteration (OSR-in immediately followed by OSR-out).
  • A loop with a back-edge count that crosses threshold mid-iteration inside a nested call.
  • An outer method that is never itself hot enough to reach Optimized except via its inner loop's OSR.

19.9 Failure Analysis

OSR-in bugs are uniquely dangerous because they transfer state in the opposite direction from every other phase's machinery — a bug here can corrupt a loop's very first optimized iteration, and because the loop was hot enough to trigger OSR, the corrupted state is likely to be exercised heavily before anyone notices.

  • Add osr_entry_reject_total (I10's counter).
  • Add osr_success_rate.
  • Cross-reference all three against the deopt-rate dashboards, since an OSR immediately followed by a deopt is a strong thrashing signal (§21).

20. Phase 8 — Deopt at Exceptions and Complex Control Flow

20.1 Objectives

Extend the deoptimizer to handle exception dispatch and irregular control flow (try/catch regions, finally blocks, loop-exit-via-exception) without violating I2, I5, or I6.

20.2 Detailed Implementation Steps

Following ADR-18's unified model, an exception thrown through optimized code routes through the same state-map/guard machinery as any other deopt trigger: an exception edge is treated as an uncommon trap with DeoptReason::ExplicitInvalidation-adjacent semantics scoped to exception handling, carrying its own FrameState per §8.7. ADR-11's frame-build ordering matters acutely here — an exception handler lookup needs the innermost frame's locals first, so the interpreter-frame builder's top-down default is special-cased to build the innermost frame early enough to resolve the handler before continuing outward. Side-effecting instructions that ran before the exception must not re-execute on resumption (a sharper version of the Phase-6 pitfall).

The idempotency property this phase introduces — no side effect observed twice across a deopt — is strictly stronger than I5's "no value lost," and is treated as a distinct, separately-tested correctness property rather than a corollary of I5, because a naive implementation can satisfy I5 (every value correctly present) while still violating idempotency (a value correctly present and a side effect re-applied). The guard-placement discipline from Phase 6 (guard strictly before any side effect) is generalized here to every uncommon trap, exception-triggered or not: this phase's fixtures specifically probe every earlier phase's trap sites for a side effect sitting on the wrong side of the guard, since exception handling is where such a placement bug's consequences become externally visible (a double-logged event, a double-decremented counter) rather than merely internally wrong.

20.3 Deliverable

Exception-aware deopt paths integrated into deopt-runtime, handling try/catch, finally, and exception-driven loop exits.

20.4 Acceptance Criteria

  • 100% of exception-triggering fixtures resume with the correct handler selected and correct live state (I2, I5).
  • No double-execution of side effects in any fixture — a new, exception-specific correctness property beyond the base differential check.

20.5 Conformance Fixtures

  • exception_simple_catch.bc — baseline try/catch deopt.
  • exception_finally_unwind.bc — finally-block unwind.
  • exception_through_inlined_call.bc — interacts with Phase 6's InlineFrameChain.
  • exception_loop_exit.bc — exception-driven loop exit.

20.6 Pitfalls

  • Handler-lookup ordering bug (ADR-11's special case implemented backwards) resolving the wrong catch block.
  • A side effect re-executed because the guard/trap was placed after it rather than before (same class of bug as §18.6, now with exception semantics making the consequence worse — an idempotency violation, not just a wrong value).
  • Finally-block state incorrectly duplicated or dropped across the exception-driven unwind.
  • Rematerialization (Phase 5) invoked during exception unwind racing with the exception object's own allocation.
  • The idempotency check (20.2) implemented only for the exception path and not retrofitted onto Phases 2-7's existing trap sites, leaving the generalization aspirational rather than actually enforced project-wide.
  • An exception's own allocation itself becoming a candidate for scalar replacement, then being rematerialized incorrectly because the rematerialization engine (Phase 5) was never tested against exception-object shapes specifically.

20.7 Performance Concerns

Exception-triggered deopt is allowed to be the slowest path in the system (P3) but must not become disproportionately slower than guard-triggered deopt merely due to unnecessary generality in the unified path (ADR-18's chosen tradeoff).

20.8 Edge Cases

  • An exception thrown from within a rematerialization recipe's implicit allocation (should not happen by construction, but must fail loudly if it does).
  • Nested try/catch with an exception crossing three inline-frame boundaries.
  • A finally block that itself triggers a guard failure.

20.9 Failure Analysis

Exception paths are exercised far less frequently than the guard-failure paths of Phases 2–6, which means bugs here survive longer in a real deployment before triggering — this phase's fixture set is deliberately adversarial (deeply nested, multiply-inlined) rather than representative of "typical" exception usage, to compensate for that lower natural exercise rate.

  • Add exception_deopt_total.

  • Flag any nonzero double-execution detector reading — a new correctness assertion specific to this phase — as page-immediately per §26.

21. Phase 9 — The Deopt-Thrashing Guard and Reprofiling

21.1 Objectives

Implement the thrashing guard (I11) and the reprofiling controller (ADR-14) so that a repeatedly-failing speculation is blacklisted rather than recompiled forever, closing the loop opened by Phase 6's megamorphic-guard-reject counter.

21.2 Detailed Implementation Steps

Each DeoptCounter (§11) tracks per-method, per-reason deopt counts. Crossing the thrashing ceiling (§4: >1 deopt/10,000 invocations sustained) transitions the method to Tier::Blacklisted for that specific AssumptionKind (I11) — the method still runs, but recompilation for that speculation type is permanently disabled (ADR-15's chosen regime) while other speculation types on the same method remain eligible. Reprofiling (ADR-14) retains and decays prior profile counters rather than resetting them, so a genuinely-transient cause (e.g., warm-up polymorphism) does not permanently poison a site that would otherwise re-monomorphize.

The "sustained" qualifier in the §4 ceiling is implemented as a sliding-window rate rather than a lifetime total, specifically to distinguish a burst of deopts concentrated in a short warm-up interval (which should decay out per ADR-14) from a steady drip that never lets up (which should trip the ceiling even though its lifetime total might look identical to the burst case at any single snapshot). The window width is itself a tunable the reprofiling controller exposes, and this phase's fixtures pin both a too-narrow and a too-wide window as explicit boundary cases, since the threshold arithmetic in §34 assumes a specific window shape that a differently-tuned window would invalidate.

DeoptCounter granularity is per-(method, AssumptionKind) rather than per-(method, Guard) — two distinct receiver-class guards on the same method speculating the same AssumptionKind::MonomorphicCall variant share one counter — a deliberate simplification justified by Phase 6's observation that call-site-level thrashing and assumption-type-level thrashing correlate strongly enough in practice that finer granularity was not worth the added bookkeeping for this project's scope.

21.3 Deliverable

A deopt-tiers-integrated thrashing guard and reprofiling controller, wired to Phase 6's monomorphic-call speculation as the first blacklist-eligible speculation type.

21.4 Acceptance Criteria

  • 100% of synthetic deopt-storm fixtures trigger blacklisting within the §4 threshold window.
  • Zero fixtures blacklist a speculation that stabilizes within the decay window — false-positive blacklist rate = 0 on the regression set.

21.5 Conformance Fixtures

  • deopt_storm_megamorphic.bc — the canonical thrashing scenario.
  • transient_polymorphism_recovers.bc — must NOT blacklist.
  • blacklist_persists_across_recompile.bc — blacklist durability check.
  • decay_window_boundary.bc — regression pinning the exact threshold arithmetic.

21.6 Pitfalls

  • Blacklist threshold miscounted per-method instead of per-(method, speculation) pair, over-blacklisting unrelated speculations on the same hot method.
  • Decay applied too aggressively, causing a genuinely-thrashing site to escape blacklisting by resetting its counter before the ceiling is reached.
  • A blacklisted speculation's dependency-tracker registration (Phase 4) not cleaned up, causing a phantom invalidation attempt on a speculation that no longer exists.
  • Reprofiling racing a concurrent recompilation request, applying decayed counters to the wrong compile generation.
  • The sliding-window rate (21.2) implemented as a fixed-size ring buffer whose window boundary aliases with the invocation-count sampling interval, producing an aliasing artifact that under- or over-counts near the boundary.
  • Per-(method, AssumptionKind) granularity (21.2) masking a genuinely call-site-specific thrashing pattern where one of several same-AssumptionKind guards on a method is pathological and the others are fine, since the shared counter blacklists all of them together — finer call-site-level granularity is PhaseDeferred("Phase 9") pending production evidence this masking is a real, not merely theoretical, problem (§37).

21.7 Performance Concerns

The counter-check itself must be cheap enough to run on every deopt without becoming a new hot-path cost (it lives entirely on the already-cold deopt path, so this is a soft rather than hard constraint, but still measured).

21.8 Edge Cases

  • A method blacklisted for every one of its speculation types (falls back to permanent Tier1).
  • A blacklist boundary exactly at the threshold count (off-by-one regression risk).
  • A method that never deopts at all (blacklist logic must be a true no-op).

21.9 Failure Analysis

An under-aggressive thrashing guard reproduces the exact pathology this phase exists to prevent — a live deopt storm degrading production throughput — while an over-aggressive one forfeits real optimization upside; both failure directions are measured explicitly against the §4 ceiling rather than judged qualitatively.

21.10 Operational Notes

  • Add thrash_blacklist_total (I11's counter, already declared in §7).
  • Add deopt_rate_per_10k_invocations.
  • Add blacklist_active_speculations_gauge.
  • §26 alerting treats a rising deopt_rate_per_10k_invocations approaching the §4 ceiling as a warning.
  • §26 alerting treats the blacklist counter firing as informational — expected steady-state behavior, not an incident.

22. Phase 10 — The Tiered-Compilation Lifecycle and Recompilation

22.1 Objectives

Implement the full §8.8 state machine end-to-end — Interpreted → Profiling → Tier1 → Optimized → Deoptimized → Reprofiled → Recompiled → Blacklisted — with every failure edge, following Paleczny, Vick & Click 2001's HotSpot server-compiler tiering model.

22.2 Detailed Implementation Steps

The tiered-compilation manager (§3) owns Tier transitions exclusively (I13); every transition is safepoint-serialized (ADR-19) and every state has an explicit rollback per P14. Recompilation (post-Reprofiled) reuses the Phase-3 speculation framework and Phase-4 dependency tracker to compile a fresh nmethod that either omits the invalidated/blacklisted speculation or incorporates updated type feedback (Phase 6). This phase is where all nine prior phases' machinery composes into the single lifecycle the rest of the system has been building toward.

Because Tier transitions are exclusively owned by one manager, every other phase's trigger (a guard failure from Phase 2, an invalidation from Phase 4, an OSR admission from Phase 7, an exception trap from Phase 8, a blacklist event from Phase 9) is implemented as a request to this manager rather than a direct mutation of a method's tier — this indirection is what makes I13's rollback guarantee enforceable at a single choke point instead of needing to be independently proven at every call site that might otherwise have mutated Tier directly. The manager processes requests strictly at safepoints, batching same-safepoint requests from multiple methods into one coordinated transition sweep, which is also what makes the concurrent-tier-transition stress fixture (22.5) a meaningful test of real contention rather than an artificial one.

22.3 Deliverable

A deopt-tiers crate implementing the complete state machine with instrumented transitions, integrated with every earlier phase's triggers (guard failure, invalidation, OSR, exception, thrashing).

This is also, functionally, the delivery of the full engine's steady-state behavior: from this phase onward, the project can be exercised end-to-end as a single coherent lifecycle rather than as eleven separate mechanisms demonstrated in isolation.

22.4 Acceptance Criteria

  • 100% of state-machine transitions in the fixture set match the §8.8 table exactly, including every failure edge.
  • Recompilation latency ≤20 ms p99 (§4).
  • Zero invalid transitions (I13) detected across the full regression suite.

22.5 Conformance Fixtures

  • full_lifecycle_happy_path.bc — Interpreted through Optimized with no deopt.
  • lifecycle_with_deopt_recompile.bc — full deopt-to-recompile cycle.
  • lifecycle_blacklist_terminal.bc — terminal blacklist state.
  • concurrent_tier_transitions.bc — stress: multiple methods transitioning simultaneously under one safepoint sweep.

22.6 Pitfalls

  • A transition applied without holding the required safepoint serialization, letting a mutator thread observe a torn Tier value.
  • Recompilation producing a new nmethod that re-registers a dependency (Phase 4) the old nmethod never cleaned up, double-counting the dependent set.
  • Reprofiled state feeding a recompile decision before decay (Phase 9) has stabilized it, causing premature or oscillating recompilation.
  • A rollback edge (P14) implemented as a no-op instead of an actual state reversion, silently leaving a method in an inconsistent tier.
  • The single-choke-point design (22.2) bypassed by a well-intentioned "fast path" that mutates Tier directly for an allegedly-trivial case, reintroducing exactly the distributed-mutation risk the design was meant to eliminate.
  • A batched transition sweep (22.2) processing two methods' requests in an order that matters (e.g. a dependency-tracker invalidation for method A must be visible before method B's recompile request reads the dependent set) but the batching implementation does not preserve that ordering.

22.7 Performance Concerns

Recompilation must not compete unboundedly with mutator threads for CPU — bound the compiler-worker budget (a scalability lever revisited in §31) and measure recompilation's effect on foreground latency, not just its own completion time.

22.8 Edge Cases

  • A method that cycles Optimized→Deoptimized→Recompiled→Optimized many times without ever crossing the Phase-9 thrashing threshold (legitimate adaptive behavior, must not be conflated with thrashing).
  • A method recompiled while its old nmethod is still executing on another thread's stack (must not evict code still in use).
  • Simultaneous OSR-triggered and invocation-count-triggered compiles racing for the same method.

22.9 Failure Analysis

This phase is the integration point where a latent bug in any earlier phase is most likely to finally surface under realistic, sustained load — the fixture set therefore deliberately runs long (soak-style, tens of thousands of invocations per fixture) rather than the single-shot style of earlier phases.

22.10 Operational Notes

  • Add time_in_tier_seconds{tier}.
  • Add recompilation_latency_ms.
  • Together these form the backbone of the §26 "time in interpreter vs. optimized" operational metric.

23. Phase 11 — Differential Correctness Harness, Conformance, and Perf Hardening

23.1 Objectives

Build the CI-gated differential harness that is this entire project's terminal correctness proof: for every fixture accumulated across Phases 0–10, run fully interpreted and run optimized-with-deopt-forced-at-every-safepoint, and assert identical observable results (the defining property of §28).

23.2 Detailed Implementation Steps

The harness (deopt-harness, ADR-22 as primary oracle) instruments every safepoint from Phase 1 with a forced-deopt hook: for a given run, at each safepoint in turn, it triggers a deopt regardless of guard state, reconstructs the interpreter frame, and continues fully interpreted from there — then compares final program state and output against a pure-interpreted baseline. This directly operationalizes P2 ("the program cannot tell it was ever optimized") as an executable test rather than an aspiration. A coverage-guided fuzzer (ADR-23) generates new random programs, compiles them, forces deopt at every safepoint, and feeds any mismatch back as a new named regression fixture.

Running the forced-deopt sweep "at each safepoint in turn" rather than at a single randomly-chosen safepoint per run is a deliberate exhaustiveness choice: a program with K reachable safepoints is run K+1 times per fuzz iteration (once fully interpreted as the baseline, once per safepoint with a forced deopt at that specific point), which is more expensive than sampling but is the only way to make "100% of safepoints" (§4, M13) a literal, checked claim rather than a statistical one. This exhaustive-sweep cost is exactly why §23.7 splits the harness into a fast per-push subset and a nightly full sweep — the exhaustiveness is preserved end-to-end (every safepoint is eventually swept) even though no single CI run pays the full cost.

23.3 Deliverable

A CI-gated differential/fuzz harness covering 100% of safepoints across the full Phase 0–10 fixture corpus, plus perf-regression gates on safepoint overhead and deopt latency (§4, §30).

23.4 Acceptance Criteria

  • State-reconstruction correctness = 100% (§4, zero tolerance) across the full corpus and a minimum 24-hour fuzz soak with zero mismatches.
  • Safepoint-overhead perf gate fails the build on any regression beyond the §4 ≤2 ns target.

23.5 Conformance Fixtures

  • The full accumulated fixture corpus from 12.5 through 22.5, run through the forced-deopt-at-every-safepoint harness.
  • fuzz_generated_regressions/ — auto-populated by the fuzzer on any discovered mismatch, per ADR-23.
  • zero_safepoint_program.bc — degenerate case, §23.8.
  • dead_safepoint_program.bc — safepoint reachable only in eliminated dead code, §23.8.

23.6 Pitfalls

  • A forced deopt at a safepoint that legitimately never fails in practice (e.g., an always-true guard) reveals a latent I1/I9 gap that normal execution never exercises — treated as a real finding, not a harness artifact.
  • Fuzzer-generated programs that are not valid per the (assumed, delegated) bytecode verifier, producing false-positive mismatches unrelated to deopt correctness — must be filtered by re-validating fuzzer output against the verifier contract before compiling.
  • Flaky mismatches traced to non-determinism in the toy interpreter itself (a Phase-0 assumption violated late) rather than a real deopt bug.
  • Perf-regression gate false-triggering on CI-runner noise rather than a real safepoint-overhead regression — mitigated by running the perf gate on dedicated, pinned-clock runners (ADR-24 exception).
  • The exhaustive per-safepoint sweep (23.2) silently degraded into a sampled sweep under time pressure, quietly weakening the "100% of safepoints" claim (M13) without anyone noticing until a since-untested safepoint's bug ships.
  • The fast-subset/nightly-full split (23.7) drifting so that the fast subset stops being representative of the full corpus's failure modes, making a green fast-subset push a false signal of health.

23.7 Performance Concerns

The differential harness itself must not become so slow (forcing deopt at every safepoint is inherently expensive) that it cannot run on every CI push — split into a fast-subset gate on every push and a full-corpus soak nightly (ADR-24).

23.8 Edge Cases

  • A program with zero safepoints reachable at all (degenerate, must still pass trivially — zero_safepoint_program.bc).
  • A program whose only safepoint is inside dead code eliminated by the optimizer (must not be silently skipped by the harness, which should detect and flag the reduction as its own fixture — dead_safepoint_program.bc).
  • A fuzz-discovered program that triggers Phase-9 blacklisting mid-harness-run.

23.9 Failure Analysis

Any mismatch surfaced by this phase is, by construction, a real correctness bug somewhere in Phases 1–10 — there is no such thing as a harmless differential mismatch in this project's model, since I5's "no observable value lost" is an unconditional invariant; every mismatch becomes a named regression fixture before the underlying bug is fixed, permanently growing the corpus.

  • Add differential_mismatch_total — must be zero on every green build; this is the single most important dashboard number in §26.
  • Add fuzz_soak_hours_since_last_mismatch.
  • Add safepoint_overhead_regression_delta_ns.
  • Wire the mismatch counter to the same page-immediately alerting class as I1/I4/I5 violations (§26).

26. Operational Readiness

Named metrics:

  • deopt_count_total{reason} — deopts by DeoptReason, the primary rate signal.
  • deopt_latency_ns (histogram) — guard-fail to resumed-interpreter timing.
  • safepoint_overhead_ns — the hot-path tax, tracked against the M1 target.
  • statemap_size_bytes — per-safepoint and aggregate, tracked against M4-M6.
  • osr_success_rate — OSR-in admissions vs. rejections (I10).
  • recompilation_latency_ms — invalidation/deopt to new-nmethod-installed timing.
  • thrash_blacklist_total — I11's counter, expected to be nonzero in steady state.
  • time_in_tier_seconds{tier} — the backbone of the "time in interpreter vs. optimized" operational view.
  • differential_mismatch_total — must be zero in production; any nonzero value is the single most important number this system exposes.

Tracing: a deopt event is the key trace. Every deopt emits a tracing span (ADR-20) carrying SafepointId, DeoptReason, and the resulting BytecodeIndex, so a single trace reconstructs the full guard-fail-to-resume timeline end to end.

Structured logging: every deopt log line carries the deopt reason and the offending assumption's AssumptionId/AssumptionKind. A bare "deopt occurred" log line without both fields is treated as a logging defect, not an acceptable minimal log.

Dashboards:

  • a deopt-rate-by-reason panel
  • a deopt-latency histogram panel
  • a state-map-size-vs-code-size ratio panel
  • an OSR success/reject panel
  • a time-in-tier panel
  • a thrashing/blacklist events panel

Alerting philosophy: a state-reconstruction mismatch (differential_mismatch_total > 0 in production, or any I1/I4/I5 violation counter firing) is a page-immediately correctness event. It is treated with the same severity as data corruption in a database, because that is precisely what it is — no severity downgrade is permitted for a "small" or "rare" mismatch.

A rising deopt_rate_per_10k_invocations approaching the §4 thrashing ceiling is a warning-level alert, escalating to page-level only if the ceiling is actually crossed without the thrashing guard engaging (itself a bug, since I11 should have engaged first). The thrashing-guard counter firing on its own is informational — expected, protective, steady-state behavior, not an incident.

SLOs:

  • 100% state-reconstruction correctness (non-negotiable, §4).
  • deopt latency p99 ≤ 50 µs.
  • recompilation latency p99 ≤ 20 ms.
  • zero page-immediately correctness events per release.

Incident response: any page-immediately event freezes further optimized compilation of the affected method(s) — a forced Tier1 fallback — while forensics proceed. The relevant runbook under docs/runbooks/ is selected by symptom: deopt-storm-triage.md for rate-based incidents, state-mismatch-response.md for correctness incidents, thrashing-blacklist.md for blacklist-tuning incidents, and osr-failure-debug.md for OSR-specific incidents.

Backup/restore: the engine holds no durable state of its own beyond the process lifetime (§1 deployment model). "Restore" means restarting the host process and letting all methods re-enter Interpreted; no data migration is needed, since every piece of compiled state (nmethods, state maps, dependency graph) is reconstructible from source and profile data alone.

Deployment topology: statically linked into the host runtime binary, so deployment topology is the host's. Canary rollout is a canary of the whole runtime binary, and rollback is a binary rollback — this project introduces no independent deployment surface of its own.

Migration: a state-map/assumption-catalogue format version bump (§27) requires the host runtime's code cache to be cold-started, never hot-migrated in place, since I1's completeness guarantee cannot be verified across an unversioned in-place transition.

27. Compatibility & Versioning

Debug-info/state-map format versioning: the format (§8.2, ADR-04) is versioned independently of the engine's public API. A version bump requires all nmethods to be recompiled — no cross-version state-map interpretation is supported, since I1's completeness guarantee cannot be verified across an unversioned boundary.

Assumption-catalogue versioning: the catalogue (§8.1, §11 AssumptionKind) is additive-only across minor versions. New speculation types may be added freely, but an existing AssumptionKind variant's guard/deopt-reason semantics never change without a major version bump, since a silent semantic change would be indistinguishable from the miscompilation class described in T1.

Host-IR interface stability: the guard/FrameState node contract (ADR-02/ADR-03) is the primary integration surface with a host JIT and is held SemVer-stable at the crate level. A host JIT compiled against one minor version's guard contract must keep working against any later minor version.

Interpreter-frame-layout compatibility: the InterpreterFrame layout (§11) is versioned alongside the host runtime's bytecode format, since it must match the interpreter's own frame model exactly (P9). A bytecode-format change that alters frame shape forces a coordinated version bump on both sides.

ABI/calling-convention dependence: pinned per target triple (ADR-12). A new target triple is an additive compatibility surface, not a breaking one — existing triples' ABI contracts are never altered to accommodate a new one.

API stability: follows Rust SemVer at the crate boundary. A breaking change to any public type in §11 requires a major version bump of the owning crate.

Migration: a state-map/assumption-catalogue major version bump requires a cold-started code cache (§26); there is no in-place hot migration path, by design, since correctness cannot be verified mid-transition.

Deprecation: a two-minor-version cycle, with a #[deprecated] annotation and a migration note in CHANGELOG.md accompanying the first deprecating release, and removal only in the version after that.

28. Testing & Verification Strategy

Unit testing covers each crate's internal invariants in isolation — for example deopt-statemap's checksum roundtrip (I8), or deopt-deps's registration-before-trust ordering (P13, in isolation from any real class load).

Integration testing exercises cross-crate flows that no single crate's unit suite can see — a guard failure originating in deopt-core, flowing through deopt-runtime's capture-and-lookup, and landing in a rebuilt InterpreterFrame.

Property testing encodes the defining property of this entire project: for any program and any safepoint, running fully interpreted and running optimized-then-deoptimized-at-that-safepoint produce identical observable state and results. This is differential testing of optimized-vs-interpreted execution with deopt injected at every safepoint (§23), and it is the primary CI gate (deopt-harness, ADR-22 as the primary oracle) — every other testing layer in this section is secondary to it.

The fuzzer as a named CI gate: a coverage-guided fuzzer (ADR-23) generates random programs, compiles them, forces a deopt at every safepoint, and checks state equivalence against the same property. Any mismatch becomes a permanent named regression fixture (§23.9), never a transient failure that is silently retried away.

Differential testing uses the host interpreter as the oracle throughout Phases 2–11, not merely in Phase 11 — every phase's N.5 fixtures are run differentially from the moment a deopt path exists for them, tying directly back to I5.

Fuzzing targets two distinct surfaces: the debug-info decoder (deopt-statemap, guarding I8's checksum contract) and the program generator itself (guarding against generating unverifiable programs that would produce false-positive mismatches, per §23.6).

Chaos testing forces deopts under load, injects GC cycles at safepoints (T8), and manufactures deopt storms (FM-3) to validate the thrashing guard under adversarial conditions rather than only against synthetic single-shot fixtures.

Deterministic replay: every deopt event's captured OptimizedFrame and resolved DebugInfo are replayable offline from the forensics artifacts named in §25, tied to I2 and I5.

Soak testing runs the full lifecycle (§22) for tens of thousands of invocations per fixture, specifically to surface integration-only bugs that no single-shot fixture can (§22.9).

Fault injection deliberately corrupts state-map checksums (I8), truncates debug info (I9), and races invalidation windows (T9) — each fault-injection target maps to a named threat in §24.

Conformance testing is the full accumulated fixture corpus, §12.5 through §23.5, run unmodified on every release candidate.

Perf-regression gating fails the build on any safepoint-overhead regression beyond the §4 ≤ 2 ns target (M1) or any deopt-latency regression beyond the p99 ≤ 50 µs target (M2), both tied directly to the §30 performance-engineering targets table.

29. Build & Release Engineering

Reproducible builds: pinned Rust toolchain (ADR-25), locked Cargo.lock, byte-identical artifacts verified across two independent build runners per release.

Artifact signing: every release artifact is signed; signatures are verified before the host runtime links against a new engine version, closing off the T10/FM-11 supply-chain surface at the consumption side.

SBOM generation: produced per release and diffed against the prior release's SBOM, the primary detection mechanism for T10.

Release channels: nightly (every green main-branch commit), staging (weekly, gated on the full §28 soak), and stable (monthly, gated on a zero-mismatch fuzz-soak window per §23.4).

CI/CD topology: a fast differential-subset gate on every push (ADR-24), a full-corpus differential/fuzz soak nightly, and a dedicated deopt-at-every-safepoint differential job as a required check before any merge to main. This last job is the single most important job in the pipeline — it mirrors §23's terminal correctness proof, and no merge bypasses it.

Version stamping: embeds the state-map format version and the assumption-catalogue version (§27) into every build artifact, so any deployed binary's compatibility surface is directly queryable.

Provenance/attestation: build provenance (SLSA-style) is attached to every signed artifact, giving the SBOM diff (above) something concrete to verify against.

Dependency auditing: cargo audit runs on every CI push, blocking on any known-vulnerable transitive dependency before it can reach even the nightly channel.

30. Performance Engineering

Methodology.

The safepoint tax on the hot path is the cost that must stay tiny — every optimization decision is evaluated against whether it grows per-poll overhead past the §4 ≤2 ns ceiling.

Debug-info size is weighed against reconstruction speed (ADR-04/ADR-16's explicit tradeoff): a denser encoding costs code-cache memory but saves decode-time cycles on the (latency-bounded, but still measured) deopt path.

Guard cost is measured per-guard, not just in aggregate, since guard density (§4) compounds across a hot method — a single expensive guard can dominate a method's steady-state overhead even when the aggregate guard count looks reasonable.

The cold deopt path is allowed to be slow relative to the hot path (P3) but is still latency-bounded (§4's p99/worst-case figures), because a slow-but-correct deopt still stalls the calling thread for its duration.

Avoiding deopt thrashing (§21) is treated as a performance concern as much as a correctness one, since a thrashing method's aggregate throughput collapses well before any invariant is technically violated.

Tail latency (p99, worst-case) is tracked separately from mean latency throughout, since the worst-case deep-inline-tree deopt (§4) is the figure that determines whether the engine is safe to deploy under a strict RTO — a good mean with a bad tail is not acceptable.

31. Scalability Analysis

What stays constant: per-guard steady-state cost (M7) and per-poll safepoint overhead (M1) — both are per-site costs independent of program size, which is what makes the hot-path tax bounded regardless of how large the host program grows.

What grows with Big-O:

  • Debug-info total size grows O(safepoints × live-values-per-safepoint) with optimized-code size and safepoint density (M4–M6).
  • Dependency-tracking memory grows O(assumptions × average-dependents-per-assumption) (M12).
  • Invalidation cost on a class load is O(dependents) for the affected assumption — bulk by design (ADR-09) rather than incremental.
  • Deopt cost is strictly per-event, not per-instruction: a program with a million optimized instructions and zero deopts pays zero deopt cost, only the constant per-poll safepoint tax.

Named bottlenecks:

  • The dependency-tracker's invalidation fan-out (§16.7) under a class-load-heavy workload.
  • State-map decode latency under very deep inline trees (M3's worst case).
  • The differential harness's own runtime under the full fixture corpus (§23.7), mitigated by the fast-subset/nightly-soak split (§29).

The metadata-size-vs-code-size tradeoff at scale: as optimized code size grows, state-map size grows proportionally (M6's 1.0×–2.0× ratio). At very large code-cache scale this becomes a memory-capacity lever (ADR-16's dense-vs-sparse choice) rather than a latency one.

The deopt-thrashing pathology and its guard: §21's thrashing pathology is the sharpest non-linear scalability risk in the system — a single pathological speculation can, absent the thrashing guard, drive unbounded recompile/deopt cycling that scales with invocation rate, not program size. This is exactly why I11 exists as a hard ceiling rather than a tunable-only mitigation.

Practical ceilings: the code-cache's total nmethod capacity bounds how many methods can hold Optimized-tier state-maps simultaneously. The assumption-registry's per-method size (§15.8's stress fixture) bounds how many simultaneous speculations one method can carry before guard density (M8) forces a compile-time rejection.

Levers beyond these ceilings: code-cache eviction of cold nmethods frees state-map memory directly. ADR-16's sparse-plus-recompute regime is the lever traded in specifically when memory, not CPU, becomes the binding constraint — the two levers are not used simultaneously, since they optimize for opposite resources.

32. Mental Models & First Principles

MM1. Speculative optimization is a bet, deoptimization is the insurance, and the debug-info state map is the contract that lets you always pay out — the optimizer can be as reckless as the deopt path is correct (Hölzle et al. 1992).

MM2. Deopt makes the program unable to observe that it was optimized, which is exactly why the optimizer is allowed to delete, inline, and scalar-replace freely (P2, P8).

MM3. A deopt is cheap only if it is rare, so the real engineering is in guarding well enough that the common case never bails, and in not thrashing when it does (P3, P10).

MM4. The safepoint is the only place optimized and interpreted state are ever compared — everywhere else, the optimizer's internal representation is free to diverge arbitrarily from the interpreter's, as long as it converges again at the next safepoint.

MM5. A guard is a promise with a fallback, not a hope — every promise (assumption) is backed by a concrete, reachable, self-describing fallback (uncommon trap), never an implicit "this probably won't happen."

MM6. Rematerialization is time travel for values the optimizer already threw away — it does not "undo" the optimization, it proves the optimization was always observationally safe by reconstructing what would have existed anyway.

MM7. Invalidation is a broadcast, not a poll — a class load does not wait to be asked whether it broke an assumption; the dependency tracker (P13) already knows exactly who to tell.

MM8. Tiering is a ratchet with an escape hatch — each tier transition commits to more speculation, but every commitment has a rollback (P14, I13), so the ratchet can always run backward when reality disagrees with the bet.

MM9. The debug-info state map is a translation dictionary between two languages that must never drift apart — the optimizer's internal vocabulary of registers and eliminated values, and the interpreter's vocabulary of locals and operand-stack slots — and every safepoint is a checkpoint proving the dictionary is still complete.

MM10. Correctness in this system is not "the program produces the right answer" in the abstract; it is "the program cannot distinguish the optimized run from the interpreted one at any observation point," which is a strictly checkable, differential property (§28) rather than a matter of code review confidence.

HotSpot's deoptimization (Hölzle, Chambers & Ungar 1992's lineage, Paleczny/Vick/Click 2001) is the canonical method-based design this project's core procedure (§8.3) is modeled on: dense per-safepoint debug info, CHA-dependency-driven bulk invalidation, and a mature tiered-compilation lifecycle that is §8.8's direct ancestor.

GraalVM/Truffle (Duboscq et al. 2013, Würthinger et al. 2013/2017) generalizes the same guard/FrameState idea into a framework any Truffle-hosted language gets for free via partial evaluation. The key contrast with HotSpot is generality: Truffle's deopt machinery is not JVM-specific, it is a property of the interpreter-writing framework itself, which is why §36 treats it as a distinct alternative architecture rather than a HotSpot variant.

V8's TurboFan deoptimizer uses compact translation-array encoding — the direct inspiration for ADR-04 — and a well-documented bailout-reason taxonomy this project's DeoptReason enum echoes closely.

SpiderMonkey's Ion bailouts share V8's method-based model but differ in bailout frame-reconstruction sequencing, informing this project's ADR-11 ordering choice specifically around exception-handler resolution (§20).

LuaJIT and PyPy represent the fundamentally different trace-based family: the unit of compilation and of bailout is a linear trace, not a method, and a "deopt" is a trace exit or guard-triggered bridge compile rather than a full method deoptimization. The key contrast with HotSpot's method-based model is the granularity of what gets thrown away and rebuilt on a speculation failure — this contrast is explored in depth as an alternative architecture in §36 rather than adopted here.

34. Back-of-Envelope Capacity Model

Debug-info size as a fraction of code size: safepoints × live-values-per-safepoint × location-encoding-bytes ÷ optimized-code-bytes. Assume 1 safepoint per 20 optimized-code bytes, 6 live values per safepoint average, 8 bytes per compressed ValueLocation (ADR-04): (code_bytes/20) × 6 × 8 ÷ code_bytes = 48/20 = 2.4× worst-case-ish, reconciled downward by compression toward the M6 1.0×–2.0× target — matching the published HotSpot OopMap+DebugInfo ratio this project's §4/§30 targets are anchored to.

Safepoint overhead on the hot path: assume 1 safepoint poll per loop iteration, poll cost 2 ns (M1), average loop iteration cost 200 ns → overhead = 2/200 = 1% of loop time, well inside an acceptable hot-path tax.

Deopt-thrashing threshold derivation: assume a deopt costs 50 µs (M2) and an optimized-vs-interpreted speedup of 5× on a method costing 100 ns interpreted per invocation (500 ns saved per invocation optimized correctly, net 20 ns saved per invocation after amortizing the 5x). Break-even deopt rate = savings-per-invocation ÷ cost-per-deopt = 20 ns ÷ 50,000 ns ≈ 1 deopt per 2,500 invocations before optimization becomes a net loss — this is the arithmetic basis for M9's conservative 1-per-10,000 blacklist ceiling, set well below the theoretical break-even to leave margin.

Rematerialization cost for a scalar-replaced object: fields × store-cost. Assume a 4-field object, 5 ns per field store (register/stack read + heap write) → 20 ns per rematerialized object, negligible against the ≥50 µs total deopt-latency budget (M2) — confirming rematerialization is not the dominant cost on the deopt path.

Dependency-invalidation cost on a class load: dependent-methods × relink-cost. Assume 50 dependent nmethods for a commonly-subclassed base class, 10 µs relink cost per nmethod (deopt-triggering, not full recompilation) → 500 µs total invalidation sweep, well inside the §4 recompilation-latency budget (M11, ≤20 ms) even before any recompilation begins.

Number of safepoints for a method of N bytecodes: assuming roughly 1 safepoint per basic block and 1 basic block per 8 bytecodes on average, safepoints ≈ N/8 — a 400-bytecode method carries roughly 50 safepoints, each ≤64 bytes (M4) → ≈3.2 KB of state-map data for that one method, consistent with the M6 code-size-ratio target once compared against typical optimized code size for a 400-bytecode method.

OSR trigger overhead: assume the OSR-specific compile takes 2 ms (well inside M10's 5 ms budget) and the entry-state transfer itself costs roughly the same as one deopt's frame-build step minus rematerialization (no eliminated objects exist yet at OSR-in time) — approximately 10 µs, negligible against the compile time that dominates the 5 ms budget.

Dependency-tracker memory at scale: assumptions × bytes-per-assumption (M12's ≤200 bytes). A large host program with 50,000 live speculative assumptions across its hot methods costs 50,000 × 200 = 10 MB of tracker memory — a small fraction of a typical managed-runtime heap, confirming the tracker is not a binding memory constraint at realistic scale.

Recompilation latency budget decomposition: M11's 20 ms ceiling is spent as roughly 2 ms dependency/registry bookkeeping (ADR-08 lookup) plus 15 ms actual compilation (the dominant term, bounded by the optimizer's own cost model, outside this project's boundary per §1) plus 3 ms safepoint-serialized installation (ADR-19) — the arithmetic shows compilation itself, not this project's machinery, is the dominant cost, which is why M11's target is set generously relative to M2's much tighter deopt-latency target.

Guard-density ceiling in absolute terms: M8's ≤1-per-8-IR-nodes ratio applied to a 400-node optimized method (roughly the 400-bytecode method from the safepoint-count derivation above, post-expansion into IR) yields a ceiling of 50 guards for that one method — comfortably above the handful of guards a typical monomorphic-call/null-check/bounds-check mix would insert, leaving headroom before the ceiling forces a compile-time rejection (§15.8).

35. Hard Questions (Self-Examination)

  1. If the debug-info generator (§13) has a bug that under-approximates LiveRefSet, will the differential harness (§23, §28) actually catch it, or does it require a GC-interaction test (§8.9, T8) that Phase 1 alone cannot exercise?
  2. Why does the dependency tracker (§16) register assumptions before compilation trusts them (P13) rather than after — what specific race does registering-after allow, concretely (see §16.6)?
  3. Is the thrashing guard's per-(method, speculation) granularity (§21.6) actually sufficient, or could two unrelated speculations on the same hot method still starve each other under ADR-15's blacklist regime?
  4. Does the unified exception/deopt path (ADR-18, §20) actually simplify correctness, or does it just relocate the exception-specific double-execution risk (§20.6) into a more general and therefore harder-to-reason-about code path?
  5. Why is OSR-in (§19) admission-gated on state-map expressibility (I10) rather than simply attempting the transfer and deopting immediately if it fails — what would break if OSR-in were allowed to "try and bail"?
  6. Given that rematerialization (§17) is eager (ADR-07), what is the actual cost paid for objects that are rematerialized but never subsequently accessed on the interpreted continuation — does §34's capacity model account for this waste?
  7. If the debug-info encoding (ADR-04) is compressed, does decode latency ever approach the deopt-latency budget (M2) closely enough that a future compression scheme change could silently regress correctness-adjacent timing assumptions elsewhere (e.g. §20's exception-handler resolution ordering)?
  8. Is 100% state-reconstruction correctness (§4, M13) actually falsifiable by the differential harness, or are there classes of divergence (e.g. non-deterministic host-runtime behavior outside this engine's control) the harness cannot distinguish from a real bug?
  9. Why does class-hierarchy invalidation (§16) choose eager bulk (ADR-09) when V8 and others sometimes use lazier strategies — what workload characteristic in this project's assumed host-runtime model (§1) makes eager bulk the right default here specifically?
  10. Does the tiered-compilation state machine's rollback guarantee (I13, P14) actually hold under Phase 22's concurrent-tier-transition stress fixture, or only under the simpler single-method fixtures?
  11. If a fuzzer-discovered mismatch (§23.6) turns out to be caused by non-determinism in the toy interpreter itself rather than the deopt machinery, how does the project distinguish "harness found a real bug" from "harness found its own oracle's bug" systematically rather than case-by-case?
  12. Given the guard-density ceiling (M8, §4), what happens to a method that legitimately needs more speculation than the ceiling allows — does it silently lose optimization opportunity, or does §15's registry surface that tradeoff explicitly to the tiered-compilation manager?
  13. Why is the deopt-thrashing ceiling (M9) set at roughly 4× below the §34 break-even arithmetic rather than at the break-even point itself — is the margin justified by a specific risk, or is it an arbitrary safety factor?
  14. Does the JIT-spraying threat (T3) actually require anything beyond memory-safe Rust (ADR-01) to mitigate, or does the threat model overstate a risk that Rust's ownership model already forecloses at the language level?
  15. If the host-IR interface (ADR-02, §27) is held SemVer-stable, but the debug-info format (§27) requires a cold-start recompile on version bump, is the API-stability guarantee actually meaningful to a host runtime that cannot tolerate cold-starting its code cache?
  16. How does the project's non-goal boundary with JIT-Compiler (§1) hold up in practice — when a guard-insertion heuristic (§15) turns out to depend on an optimizer scheduling decision, which project's blueprint actually owns fixing it?
  17. Does §36's trace-based alternative architecture's rejection rationale still hold if the host-runtime model (§1) later changes from method-based to a tracing JIT — would this entire blueprint need to be re-derived rather than amended?
  18. Given that Phase 9's thrashing guard (§21) and Phase 4's dependency tracker (§16) both react to runtime events by disabling future speculative compilation, could a class-load invalidation followed immediately by a thrashing-threshold crossing double-count against the same method in a way §21.6/§16.6 don't individually anticipate?
  19. If the differential harness (§23) exhaustively sweeps every safepoint (§23.2), does the harness itself scale linearly with program size, and if not (per §31's Big-O analysis), does the nightly-soak mitigation (§29) actually keep pace as the fixture corpus grows across all eleven phases?
  20. Why does §9's ADR-07 lock eager rematerialization when §17.7 explicitly flags eager remat's cost-on-unused-objects as a known waste — is the correctness-simplicity argument strong enough to justify never revisiting this ADR, or does it warrant an explicit deferred re-evaluation trigger the way §37 tracks other deferrals?
  21. Does the unified guard/exception trap path (ADR-18, §20) make T3's JIT-spraying threat surface larger by giving an attacker one more general-purpose trap-dispatch mechanism to target, compared to keeping exceptions on a narrower dedicated path — is that tradeoff weighed explicitly anywhere, or only assumed?
  22. If a host runtime's bytecode format changes in a way that only affects rarely-executed opcodes, does §27's interpreter-frame-layout compatibility rule really require a full cold-started code cache migration, or is there a narrower compatible-subset rule this blueprint has not yet specified?
  23. Does the exhaustive per-safepoint differential sweep (§23.2) actually prove I5 ("no observable value lost") in full, or does it only prove I5 for values that are live at some safepoint — could a value be lost in a way that never crosses any safepoint at all, and would this harness even notice?
  24. Is the strict boundary drawn between this project and JIT-Compiler in §1 actually enforceable in practice once guard-insertion heuristics (§15) and general optimizer scheduling decisions (delegated to JIT-Compiler) start interacting, or does §35's question 16 already show the boundary is aspirational rather than mechanically checkable?
  25. Given §34's arithmetic sets the thrashing ceiling (M9) well below the theoretical break-even point specifically for safety margin, would a host runtime with a measured, stable, much cheaper deopt cost than M2's budget be justified in tuning that margin down — and if so, does anything in this blueprint make that tuning knob a first-class, supported operation rather than an unsupported hack?

36. Alternative Architectures (Roads Not Taken)

Trace-based deoptimization (LuaJIT / PyPy meta-tracing). Instead of method-based deopt, the unit of compilation and bailout is a linear trace recorded from an actual hot loop execution; a guard failure is a trace exit, not a full-method deoptimization.

// trace-based: linear recorded trace with inline guards
Trace: [op1, op2, GUARD(g1), op3, op4, GUARD(g2), op5, ... , loop-back]
  guard fail at g2 -> trace EXIT -> resume interpreter at recorded point
  repeated exit at g2 -> compile a trace "bridge" starting from g2

Winning regime: workloads dominated by a small number of extremely hot, simple loops with low control-flow diversity, where recording a linear trace captures nearly all the relevant behavior.

Real embodying system: LuaJIT and PyPy's RPython meta-tracing.

Why rejected here: this project's host-runtime model (§1) assumes a general tiered method-based JIT, and a linear trace's exit-and-bridge model does not map cleanly onto this project's method-based Nmethod/dependency-tracking design (§11, §16) without effectively becoming a different project. The dependency tracker's assumption-to-nmethod fan-out (§8.6) in particular has no clean trace-based analogue, since a trace is not a stable compilation unit that a class load can look up and invalidate the way an nmethod is.

Conservative, provably-safe-only optimization (no speculation at all). The optimizer performs only transforms provable safe without runtime assumptions — no guards, no deopt, no state maps beyond what a non-speculative optimizer already needs for exceptions.

// no-speculation: optimizer restricted to provably-safe transforms
optimize(method) -> only: constant-fold, DCE, provably-safe inlining
  (no type speculation, no CHA leaf assumption, no monomorphic-call guess)

Winning regime: safety-critical or highly-adversarial environments where any speculative-optimization attack surface (T3) is unacceptable regardless of performance cost.

Real embodying system: early, conservative bytecode JITs and many embedded/AOT compilers that forgo profile-guided speculation entirely.

Why rejected here: this project's entire reason for existing (§2) is the speculation/deopt machinery — a conservative optimizer forfeits the type-feedback and CHA-driven wins (Hölzle & Ungar 1994) that motivate building a tiered JIT in the first place. Choosing this architecture would not simplify the project, it would eliminate the project's subject matter.

Recompile-and-patch instead of deopt-to-interpreter. Stay in compiled code entirely: on assumption failure, patch in a freshly recompiled, de-speculated version of the same compiled method in place, rather than dropping to the interpreter.

// recompile-and-patch: no interpreter fallback, compiled-to-compiled patch
guard fail -> pause thread at safepoint -> recompile method (no speculation X)
  -> patch code pointer -> resume in NEW compiled code at equivalent PC

Winning regime: an environment with no interpreter tier at all (compile-only VMs), where dropping to an interpreter isn't an option.

Real embodying system: some ahead-of-time/compile-only WASM engines use patch-based de-optimization in a limited sense.

Why rejected here: this project's host-runtime model (§1) assumes a tiered interpreter as the ground truth (P9). Recompile-and-patch requires synthesizing an equivalent PC in freshly compiled code, which is strictly harder than resuming in an already-correct interpreter, and it duplicates most of this project's state-map machinery without the interpreter's benefit as a stable oracle for the differential harness (§28).

Framework/partial-evaluation-provided deopt (Truffle). Deopt is not built per-VM; it is provided generically to any interpreter written against a partial-evaluation framework, which derives guards and FrameStates automatically from the interpreter's own AST-walking structure.

// framework-generic: deopt derived from partial evaluation of ANY interpreter
HostInterpreter (AST-walking) --partial-eval--> optimized graph
  framework auto-inserts FrameState at every partial-eval boundary
  any HostInterpreter gets deopt "for free" via the framework

Winning regime: a multi-language runtime hosting many different interpreters that all need deopt without each reimplementing it (Würthinger et al. 2013).

Real embodying system: GraalVM/Truffle.

Why rejected here: this project is scoped (§1) to be the deopt subsystem for one specific host-runtime model, not a general partial-evaluation framework for arbitrary hosted interpreters. Building the framework-generic version is a substantially larger and differently-shaped project than the one specified here — it would require deriving guards and FrameStates automatically from an arbitrary interpreter's AST-walking structure rather than from this project's fixed bytecode/IR model, which is a different problem than the one §1 scopes this blueprint to solve. §33 notes Truffle as the generality-maximizing point of comparison precisely because this project deliberately does not attempt that generality.

38. Glossary

Assumption — a speculative fact the optimizer relies on (§8.1), registered before any guard trusts it (P13). AssumptionKind — the tagged variant identifying which speculation type an Assumption represents (§11). Bailout — general term for leaving optimized/compiled execution due to a failed speculation; this project's specific mechanism is deoptimization. Bytecode index (BCI) — the interpreter resumption point a deopt must land on precisely (I2). Calling convention — the ABI contract (ADR-12) governing register/stack layout at the deopt boundary. Class-hierarchy analysis (CHA) — static analysis of the class hierarchy backing the "no subclasses" leaf-class speculation (§8.1). Debug info — the per-safepoint metadata mapping optimized values to interpreter locations (§8.2). Dependency — an edge from an Assumption to a CompiledMethod that relies on it (§11, §16). Dependency tracker — the registry indexing assumptions to their dependent nmethods for bulk invalidation (§16). Deoptimization (deopt) — the transition from optimized machine code back to interpreter execution when a speculative assumption fails. Deopt reason — the tagged cause of a deoptimization (DeoptReason, §11), e.g. TypeMismatch, MegamorphicCall. Deopt storm / thrashing — pathological repeated compile/deopt cycling on the same speculation (§21, FM-3). Escape analysis — the optimizer analysis determining whether an allocation's lifetime is provably confined, enabling scalar replacement (§8.4). FrameState — the IR node (Duboscq et al. 2013) attaching a debug-info snapshot to a guard (§8.7). GC safepoint — a safepoint where the garbage collector may safely scan roots (§8.9, T8). Guard — a runtime check backing a speculative assumption, always paired with an uncommon trap (§11). Inline cache — the dynamic-dispatch specialization technique (Deutsch & Schiffman 1984) generalized here into monomorphic-call guards (§18). InlineFrameChain — the ordered list of inlined logical frames a debug-info entry describes (§8.2). Interpreter frame — the reconstructed, interpreter-native representation of a logical call frame post-deopt (§11). Invalidation — the act of deoptimizing every method dependent on a falsified assumption (§16). Live reference / GC root — a value that must be visible to the garbage collector at a safepoint (§8.2 LiveRefSet). Megamorphic — a call site with more distinct receiver classes than can be usefully speculated on (contrast monomorphic/polymorphic). Monomorphic — a call site observed to always dispatch to exactly one method (§8.1, §18). Nmethod — a native (compiled) method installed in the code cache (§11 CompiledMethod). OSR (on-stack replacement) — transitioning execution between interpreter and optimized code mid-method, without a fresh call (§8.5). OSR-in — OSR from the interpreter into optimized code at a loop back-edge (§19). OSR-out — OSR from optimized code back to the interpreter; structurally the deopt procedure itself (§8.5). Optimized frame — the transient captured machine-state representation (registers + stack) at a deopt trigger point (§11). Polymorphic — a call site observed to dispatch to a small bounded set of methods (contrast monomorphic/megamorphic). Profile data — runtime-collected invocation/backedge counters and type feedback driving tiering and speculation decisions (§11). Rematerialization — reconstructing a value the optimizer eliminated or scalar-replaced, from its RematRecipe, during a deopt (§8.4). RematRecipe — the field-by-field reconstruction instructions for a VirtualObject (§11). Reprofiling — updating profile counters after a deopt, feeding the recompilation decision (§21, ADR-14). Safepoint — a program point where optimized and interpreted state are guaranteed comparable and reconstructable (§8.2). Scalar replacement — replacing a heap allocation with its constituent scalar values when escape analysis proves it safe (§8.4). Sea of nodes — the graph-based IR style (ADR-02) representing both data and control flow as nodes. Speculation — compiling on an unproven-but-likely-true runtime assumption, backed by a guard (§8.1). State map — the aggregate structure of all debug-info entries for a compiled method (§8.2, StateMap). Tier — a stage in the tiered-compilation lifecycle (Tier enum, §8.8, §11): Interpreted, Profiling, Tier1, Optimized, Deoptimized, Reprofiled, Recompiled, Blacklisted. Tiered compilation — the multi-stage compilation strategy escalating a method's optimization level as it proves hot (§8.8). Trace exit — the trace-based-JIT analogue of a deopt: leaving a recorded linear trace on a guard failure (§33, §36). Translation array — V8's compact state-map encoding style (§5 Reference Implementations, ADR-04). Uncommon trap — the reachable, self-describing control-flow target a guard transfers to on failure (§11, §8.7). ValueLocation — the tagged description of where a live value resides: Register, Stack, Constant, or Rematerialize (§11). Virtual object — the optimizer's internal representation of an eliminated/scalar-replaced allocation, materialized only on deopt (§11). Bailout reason — the taxonomy of causes attached to a trace exit or deopt event, echoed in this project's DeoptReason (§33, V8 terminology). Blacklist (speculation) — the terminal state (I11) preventing a specific AssumptionKind from being recompiled for a given method after sustained thrashing (§21). Code cache — the region holding installed nmethods and their attached state maps; a practical scalability ceiling (§31). Cold path — a code path (the deoptimizer, rematerialization) allowed to be slow relative to the hot path, but still latency-bounded (P3, §4). Hot path — the steady-state execution path (interpreter dispatch, guard checks, safepoint polls) whose per-operation cost is tightly bounded (§4). Thrashing threshold — the deopt-rate ceiling (M9) above which a speculation must be blacklisted rather than retried (§21, §34).
