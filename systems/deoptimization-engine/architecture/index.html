The Tiered-Compilation Manager owns the Interpreted→Profiling→Tier1→Optimized state machine (§8.8) and the reprofiling/recompilation controller that reacts to deopts by adjusting profile data and re-issuing compiles. It is the only box in this diagram permitted to mutate a method's Tier (I13), and every other box's trigger reaches it as a request, never a direct mutation.

The Speculation/Assumption Registry is the per-method catalogue of active speculative facts (§8.1) that the optimizer consulted while compiling. It is append-only per method (P11) — an assumption once registered is never silently withdrawn, only explicitly invalidated (§8.6) or blacklisted (§8.8).

The Guard/Uncommon-Trap Inserter lowers each registry entry into an IR guard node with an attached trap target (§8.7). Following Duboscq et al. 2013, the trap target always carries a FrameState snapshot captured at insertion time, never synthesized lazily at trap time.

The Dependency Tracker indexes assumption → dependent-nmethod sets so a class load can find every method to invalidate (§8.6). It is the sole authority for bulk invalidation (ADR-09) and is consulted before, not after, a speculative compile is trusted (P13).

The Safepoint + Debug-Info/State-Map Generator emits, at every safepoint the optimizer creates, a complete mapping from live optimized values to interpreter locations (§8.2). Its output is checksummed (I8) and is the single artifact every other box downstream of the seam depends on for correctness.

The Deoptimizer Runtime is invoked at a guard failure or uncommon trap: it captures machine state, looks up debug info, and drives frame reconstruction (§8.3). It is implemented as a stateless service (§14.2) so its correctness is a pure function of the SafepointId and captured frame it is given.

The Rematerialization Engine consumes RematRecipes to rebuild scalar-replaced/eliminated objects (§8.4). It runs strictly between frame construction and GC-root relinking in the deopt procedure (§8.3, steps 5-6), never before or after.

The Interpreter-Frame Builder turns reconstructed values into real InterpreterFrames, outermost inline frame first (ADR-11). It is the box that ultimately hands control back to canonical bytecode execution.

The OSR-in/OSR-out Machinery is the dual transition crossing the same seam in the opposite direction — entering optimized code from a live interpreter loop, or leaving it via deopt (§8.5). OSR-out is structurally identical to the Deoptimizer Runtime's ordinary procedure; OSR-in is its mirror image (P12).

The central seam — marked in the diagram — is the boundary this entire project exists to make safe: everything above it is optimized machine code trusting speculative facts; everything below it is the interpreter, the ground truth those facts must always reduce back to (P9). No box in this diagram is permitted to cross that seam except through the Deoptimizer Runtime or the OSR machinery — there is no back-channel.

8. Domain Model

8.1 Speculation Catalogue

Speculation Type Assumption Guard Deopt Trigger / Reason
Type speculation value has runtime type T type-check guard at use site DeoptReason::TypeMismatch
Monomorphic call call site always dispatches to method M receiver-class guard (inline-cache guard) DeoptReason::MegamorphicCall
Null-check elision reference never null at this point null guard hoisted above the elided checks DeoptReason::NullCheckFailed
Bounds-check elision index within array bounds for the region range guard hoisted out of loop DeoptReason::BoundsCheckFailed
Class-hierarchy assumption class C has no (further) subclasses CHA leaf-class dependency, no runtime guard — invalidated on class load DeoptReason::ClassHierarchyChanged
Integer-range assumption variable stays within a fixed-width range range/overflow guard DeoptReason::IntegerOverflow

Each row's guard is inserted atomically with its speculative transform (§15.2) — the optimizer never has a window where the transform exists without its guard, which is the concrete mechanism behind P1 rather than a documentation convention. The DeoptReason column is the field every downstream telemetry counter in §26 keys on, so a new speculation type added after Phase 11 (§37's deferred polymorphic inline-cache generalization, for example) must extend this table before it extends any code.

8.2 Debug-Info / State-Map Model

Field Meaning
SafepointId unique id of the safepoint/PC this state map describes
BytecodeIndex interpreter resumption point
InlineFrameChain ordered logical frames, outermost to innermost
ValueLocation[] per live value: Register(reg) / Stack(offset) / Constant(value) / Rematerialize(recipe)
LiveRefSet subset of ValueLocation entries that are GC roots

Worked example — optimized frame with three live SSA values mapped to interpreter locals:

Optimized location Value Interpreter local
Register(rax) v1 (int) slot 0
Stack(fp-16) v2 (int, spilled) slot 1
Rematerialize(recipe_Point) v3 (eliminated Point{x,y}) slot 2

8.3 Deoptimization Procedure — Named Steps

  1. Hit guard (runtime check fails), or an uncommon trap is taken unconditionally.
  2. Capture optimized machine state (registers + stack) at the trap PC.
  3. Look up debug info for that PC via SafepointId.
  4. Build interpreter frame(s) — one per InlineFrameChain entry, outermost first.
  5. Rematerialize eliminated/scalar-replaced objects per RematRecipe.
  6. Relink GC roots into the new interpreter frames.
  7. Resume in the interpreter at BytecodeIndex.

Worked end-to-end trace: a monomorphic-call speculation fails (the receiver's class changed) inside an inlined callee two frames deep.

Step 1: the receiver-class guard at the call site fails, taking DeoptReason::MegamorphicCall.

Step 2: the deoptimizer captures rax/rbx/spill-slots at the trap PC.

Step 3: SafepointId for that PC resolves to a state map describing two InlineFrameChain entries (caller, inlined callee).

Step 4: the outer caller's InterpreterFrame is built first from its slice of the state map, then the inlined callee's.

Step 5: no eliminated objects on this path — rematerialization is a no-op.

Step 6: the receiver reference is relinked as a GC root in the new callee frame.

Step 7: execution resumes in the interpreter at the callee's BytecodeIndex for the call instruction, which then dispatches virtually instead of monomorphically.

8.4 Rematerialization Model

RematRecipe carries, per virtual object, its ClassId and a field-by-field reconstruction list — each field either a direct ValueLocation or a nested recipe.

Worked example: a scalar-replaced Point{x, y} where x lives in rax and y is spilled at fp-24. The recipe is { class: Point, fields: [ (x, Register(rax)), (y, Stack(fp-24)) ] }.

Rematerialization allocates a new Point, assigns x and y from their locations, and installs the fresh object at the VirtualObjectDescriptor's slot in the reconstructed frame.

This is a fresh heap identity, valid because the source language never observed the pre-elimination identity while the object was scalar-replaced (P8) — the identity that matters is the one visible to the program from this point forward, not any hypothetical identity the eliminated allocation would have had.

8.5 On-Stack Replacement — Sequence Tables

OSR-in (interpreter loop → optimized code at a back-edge):

Step Actor Action
1 Interpreter back-edge counter for the loop crosses threshold (§9 ADR-10)
2 Tiered-compilation manager triggers an OSR-specific compile of the loop body
3 OSR machinery builds an OsrEntry state map matching current interpreter locals
4 Deoptimizer-adjacent OSR entry stub transfers live locals into optimized register/stack locations
5 Optimized code resumes execution at the loop back-edge in optimized form

OSR-out (the deopt itself, from optimized loop back to interpreter):

Step Actor Action
1 Optimized loop guard fails or uncommon trap taken mid-loop
2 Deoptimizer runtime runs the standard procedure (§8.3) at the loop's safepoint
3 Interpreter-frame builder rebuilds the loop's locals into an InterpreterFrame
4 Interpreter resumes the loop body at the corresponding BytecodeIndex

Both directions share the same DebugInfo-shaped state map (§8.2); OSR-in's step 3 and OSR-out's step 2 are the only steps that differ in direction of value transfer, not in format — a design choice that lets Phase 7 (§19) reuse Phase 1's encoder/decoder wholesale rather than building a parallel OSR-specific format.

8.6 Assumption-Dependency and Invalidation Model

// assumption -> dependent-nmethod fan-out, invalidated on class load
Assumption("Leaf(ClassC)")
      |
      +--> Dependency --> Nmethod(Method A, tier=Optimized)
      +--> Dependency --> Nmethod(Method B, tier=Optimized)
      +--> Dependency --> Nmethod(Method C, tier=Optimized)

ClassLoad(Subclass of ClassC)
      |
      v
DependencyTracker.invalidate("Leaf(ClassC)")
      |
      +--> deopt Nmethod(A)  --> Deoptimized --> Reprofiled
      +--> deopt Nmethod(B)  --> Deoptimized --> Reprofiled
      +--> deopt Nmethod(C)  --> Deoptimized --> Reprofiled

The fan-out shown above is exactly what ADR-08's hash-map-keyed structure makes O(1) to look up and O(dependents) to walk (§31); a per-nmethod-list alternative would require scanning every compiled method's assumption list on every class load, which does not scale with code-cache size.

8.7 Guard / Uncommon-Trap IR Representation

Following Duboscq et al. 2013, each guard is an IR node carrying a reference to a FrameState node — a full debug-info snapshot at that program point captured at compile time. The guard's condition edge falls through on success; its trap edge targets a shared trap-stub keyed by DeoptReason (ADR-17), which invokes the deoptimizer runtime with the guard's attached FrameState. This makes the trap target always reachable (I6) and always self-describing (I1) — the FrameState is not derived at trap time, it is carried since compilation.

Sharing trap stubs by DeoptReason rather than emitting one unique trap per guard (ADR-17) means the guard node itself is small — a condition plus two edges — while all of the actual deopt-invocation logic lives once, in the shared stub, rather than being duplicated at every guard site. This is what keeps guard density (M8) a code-size-cheap property rather than one that scales with the number of speculations a method carries.

8.8 Tiered-Compilation Lifecycle State Machine

State Entry Condition Failure Edge
Interpreted method's first invocation —
Profiling invocation counter crosses profiling threshold none — always advances or stays
Tier1 (baseline-compiled) profiling data sufficient for a first compile compile failure → remain Profiling
Optimized Tier1 invocation/backedge counters cross optimizing threshold compile failure → remain Tier1
Deoptimized guard failure, uncommon trap, or invalidation — (always reachable from Optimized)
Reprofiled deopt completes, profile counters updated (ADR-14) —
Recompiled reprofiled data triggers a fresh Optimized compile repeated deopt on same speculation → Blacklisted
Blacklisted thrashing threshold exceeded (I11) permanent for that speculation; method still runs Tier1

Every arrow in this table is owned exclusively by the tiered-compilation manager (§3, I13) — no other subsystem in §3's diagram is permitted to write a Tier value directly, which is what makes the "failure edge" column enforceable as a single-choke-point invariant rather than a convention every caller must independently honor (§22.2).

8.9 Malformed / Hard Examples

  • A deopt is attempted at a PC with no debug info — this is a fatal build-time bug (I9); it must never occur at runtime, and any occurrence aborts with diagnostics rather than attempting silent recovery.
  • A rematerialization recipe graph contains a cycle (I12) — rejected at compile time by the recipe-graph cycle check.
  • A deopt storm: a speculation fails on nearly every invocation, driving the method repeatedly through Optimized→Deoptimized→Recompiled — caught by the thrashing guard (§8.8, I11) before it becomes a sustained performance collapse.
  • OSR-in is attempted into a loop whose live-variable set cannot be expressed in the optimized entry's expected state map (e.g., a value's type diverged between iterations) — rejected by I10, the loop remains interpreted.
  • A guard references a value the debug info does not describe — a compiler bug caught by the registry-guard cross-check (I7) before the nmethod is installed.
  • Two DeoptCounter entries collide on the same key for unrelated speculations (I16) — a counter-key derivation bug, caught by the key-collision audit before an unrelated speculation is wrongly blacklisted.
  • An exception unwind and a guard-triggered deopt target the same safepoint simultaneously on two different threads sharing a not-yet-invalidated nmethod — must resolve deterministically per-thread rather than racing on shared reconstruction state.

8.10 Failure-Path Example

A dead-code-elimination bug drops a live value v5 from a FrameState after a guard referencing it was already inserted.

At runtime the guard fails; the deoptimizer looks up the state map and finds no entry for v5 where the guard's snapshot expects one.

This violates I1 and is detected by the state-map completeness validator before any register/stack data is trusted.

The runtime aborts the deopt with a fatal trap rather than reconstructing a partially-wrong frame — a partial, silently-wrong reconstruction is strictly worse than a loud abort, per P2's observational-equivalence requirement.

The runtime emits statemap_completeness_gauge telemetry identifying the offending SafepointId.

The offending nmethod's compilation is rejected in the next build once the fixture reproducing this failure is added to the permanent regression suite (§12.5, §28).
