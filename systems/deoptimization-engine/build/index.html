⬜ Phase 0 — Skeleton, Toy Tiered Runtime, and CI §12

Objectives

Stand up the repository skeleton (§10), the deopt-core types (§11), a minimal toy interpreter (deopt-interp-toy) that serves as the semantics oracle, a trivial optimizer (deopt-opt-toy) that performs one speculative transform, and a CI pipeline that can run both.

Deliverable

A runnable interpreter, a toy optimizer producing guarded optimized code that the (stubbed) deoptimizer can detect but not yet fully recover from, and a green CI pipeline.

Acceptance
  • Interpreter passes ≥95% branch coverage on its own opcode suite.
  • Toy optimizer's guard-insertion rate matches the ≤1-guard-per-8-IR-nodes target (§4).
  • CI wall-clock ≤10 minutes per run.
Fixtures
  • arithmetic.bc — baseline opcode coverage.
  • recursive.bc — recursive call depth handling.
  • malformed_jump.bc — verifier-reject fixture.
  • monomorphic_call.bc — exercises the one speculative transform.
  • guard_stub_trip.bc — guard fails, deoptimizer stub aborts cleanly rather than corrupting state.
Pitfalls
  • Interpreter and optimizer silently diverge on integer-overflow semantics — caught only by later differential testing unless a Phase-0 unit test pins the behavior explicitly.
  • Guard insertion in the toy optimizer forgets to register the Assumption with anything (dependency tracker doesn't exist yet) — acceptable for Phase 0 but must be flagged as a TODO tied to Phase 3/4, not silently forgotten.
  • CI green on a broken interpreter because the fixture set is too shallow — mitigated by requiring the malformed-input fixture to fail loudly.
  • The toy optimizer's one speculative transform silently degenerating into a no-op transform under a compiler refactor, giving a false sense that guard machinery is being exercised when it is not — mitigated by asserting a nonzero guard-insertion count in CI, not just a passing test.
  • Bytecode verification (delegated per §1 to Bytecode-Verifier 247 in the real system) being informally reimplemented ad hoc inside the toy interpreter rather than kept as a clearly-labeled stand-in — risks the project quietly growing scope it explicitly disclaimed in §1's non-goals.

⬜ Phase 1 — Safepoints and the Debug-Info / State-Map Model §13

Objectives

Implement Safepoint, DebugInfo, ValueLocation, and StateMap (§11) for real: every safepoint the toy optimizer creates must carry a complete, checksummed state map satisfying I1, I8, and I9.

Deliverable

A deopt-statemap crate that encodes/decodes StateMaps with checksums (I8), plus a build-time verifier enforcing I9.

Acceptance
  • State-map size ≤64 bytes/safepoint typical (§4).
  • Checksum validation rejects 100% of injected corruption in the fixture set.
  • Safepoint-placement verifier rejects 100% of fixtures with a deliberately omitted safepoint.
Fixtures
  • safepoint_complete.bc — baseline positive case.
  • safepoint_missing.bc — I9 violation, must reject at build time.
  • checksum_corrupt.meta — I8 violation, must reject at decode time.
  • deep_inline_statemap.bc — stresses InlineFrameChain depth.
Pitfalls
  • Off-by-one BytecodeIndex recorded at the safepoint versus the index the interpreter would actually resume at (violates I2 in Phase 2, but the bug is planted here).
  • Register/stack location aliasing: two ValueLocations claiming the same physical register at one safepoint.
  • Checksum computed over the pre-compression buffer but validated over the post-compression buffer — an encoding-order bug, not a data bug.
  • LiveRefSet under-approximation — a GC root silently omitted, invisible until a Phase 8-style GC-interaction test exists.
  • InlineFrameChain ordering reversed (innermost-first instead of outermost-first, or vice versa) relative to what Phase 2's frame builder expects — a pure convention mismatch that produces plausible-looking but semantically inverted frames.
  • Compression (ADR-04) applied non-deterministically (e.g. iteration order over a hash map affecting byte layout), breaking the reproducible-build guarantee (§29) even though the decoded semantics are correct.

⬜ Phase 2 — Basic Deopt: Guard Failure to Rebuilt Interpreter Frame §14

Objectives

Implement the Deoptimizer (§11) end-to-end for the simplest case: a single, non-inlined frame, no eliminated objects — a guard fails, and the runtime rebuilds one correct InterpreterFrame and resumes.

Deliverable

A working deopt-runtime crate that turns a guard failure into a resumed interpreter execution, matching interpreted output on every Phase-2 fixture.

Acceptance
  • Deopt latency p99 ≤50 µs (§4) on the single-frame fixture set.
  • 100% of fixtures produce interpreter state observationally identical (I5) to a fully-interpreted run of the same input — the first real application of the §28 differential property, in miniature.
Fixtures
  • type_guard_fail.bc — type-speculation guard failure.
  • int_range_overflow.bc — integer-range speculation failure.
  • guard_never_fires.bc — regression: optimized path must stay fast when the guard holds.
  • resume_bci_exact.bc — pins I2 precisely.
Pitfalls
  • Register capture races with a concurrent safepoint poll from another mechanism, corrupting the snapshot.
  • Off-by-one resumption (the planted Phase-1 bug, if not caught, surfaces here as wrong output on the very next bytecode).
  • Stack-slot offsets computed relative to the wrong frame pointer after a calling-convention (ADR-12) mismatch between the toy optimizer's codegen and the deoptimizer's assumptions.
  • Guard-fires-but-deopt-succeeds masking a different latent bug (a false positive "it works" outcome) — mitigated by requiring the fixture to also assert the reason recorded matches expectation.
  • Heap allocation performed inside the capture step (violating the "capture must not itself require a safepoint" rule) causing a re-entrant safepoint poll mid-capture.
  • The Deoptimizer's statelessness assumption (14.2) violated by an implementation detail that caches a stale DebugInfo lookup across calls, reintroducing hidden state the design explicitly rejected.

⬜ Phase 3 — The Speculation / Assumption Framework §15

Objectives

Generalize Phase 2's single-guard mechanism into the full Assumption/AssumptionKind/Guard registry (§11), covering all six §8.1 speculation types except class-hierarchy (which needs Phase 4's dependency tracker to be safe) and type-feedback-driven monomorphic calls (Phase 6).

Deliverable

A deopt-core extension plus toy-optimizer integration exercising null-check elision, bounds-check elision, and integer-range speculation, each with its own guard and correct DeoptReason.

Acceptance
  • Guard density stays ≤1/8 IR nodes (§4) across the expanded fixture set.
  • Each of the three new speculation types has ≥1 fixture proving both the "assumption holds" fast path and the "assumption fails" deopt path.
Fixtures
  • null_check_elide.bc — null-check elision speculation.
  • bounds_check_elide.bc — bounds-check elision speculation.
  • int_range_speculate.bc — integer-range speculation.
  • multi_guard_same_safepoint.bc — two guards sharing one safepoint.
  • assumption_registry_overflow.bc — stress: many assumptions on one method.
Pitfalls
  • Two guards for logically the same assumption registered twice, doubling deopt bookkeeping without doubling safety.
  • A guard inserted after the safepoint it should be attached to, violating P4's ordering requirement.
  • Bounds-check elision hoisted incorrectly outside a loop whose bound is itself loop-variant — a classic LICM/speculation interaction bug.
  • DeoptReason chosen generically ("Unknown") instead of precisely, which silently degrades §26's per-reason telemetry.
  • The "atomically inserted" guard-and-transform discipline (15.2) violated by a refactor that splits guard insertion and transform application across two optimizer passes, reopening the intermediate-state window it was designed to close.
  • An assumption registered for a value that is not actually live at the attached FrameState's safepoint, producing a guard that references dead data.

⬜ Phase 4 — Dependency Tracking and Invalidation §16

Objectives

Implement Dependency/DependencyTracker/Invalidation (§11) so that class-hierarchy speculation (§8.1) becomes safe, satisfying I3, I7, and I13.

Deliverable

A deopt-deps crate: registration API, O(1)-amortized invalidation on class load, and the safepoint-serialized tier-mutation path.

Acceptance
  • 100% of dependent nmethods deoptimized before next invocation post-class-load (I3, zero tolerance).
  • Dependency-tracker memory ≤200 bytes/assumption (§4).
  • Invalidation-to-safepoint-serialized latency within the recompilation-latency budget (§4, ≤20 ms).
Fixtures
  • cha_leaf_speculate.bc — baseline CHA-leaf speculation.
  • class_load_invalidate.bc — the core scenario: speculate, then load a subclass, then verify deopt.
  • concurrent_class_load.bc — invalidation racing live mutator threads.
  • dependency_fanout_stress.bc — one assumption, many dependent methods.
Pitfalls
  • A dependent method compiled between the class load and the invalidation sweep, sneaking in with a stale assumption — an ordering race that P13 exists specifically to prevent; must be closed by holding the registry lock across the whole class-load-to-invalidation window.
  • Invalidation walks the dependent set but forgets to also blacklist candidate future recompiles of the same now-false assumption, causing an immediate re-speculate-and-refail cycle (a preview of Phase 9's problem, but a correctness gap here if not handled).
  • Dependency-tracker memory unbounded growth when methods are never explicitly evicted from the code cache.
  • A stale dependency executes invalidated code due to a safepoint being skipped (ADR-19 violated by a rogue polling omission) — this is also T9 in §24.
  • The registration handle (16.2) held indefinitely by a compile that never completes (e.g. a crashed compiler worker), permanently blocking future publications for the same assumption — must be paired with a timeout/cleanup path.
  • Two class loads targeting overlapping dependent sets processed out of order, leaving a brief window where a method reflects only one of two now-false assumptions.

⬜ Phase 5 — Rematerialization of Eliminated / Scalar-Replaced Objects §17

Objectives

Implement VirtualObject/RematRecipe/ScalarReplacement (§11) so that a deopt through a point where escape analysis eliminated an allocation correctly rebuilds that object, satisfying I4, I5, and I12.

Deliverable

A deopt-remat crate integrated into the Phase-2 deoptimizer's step 5, handling both leaf scalar values and nested virtual-object graphs.

Acceptance
  • 100% object-identity preservation on fixtures requiring it (I4, zero tolerance, differential-harness-gated).
  • Rematerialization cost within the §34 capacity-model formula (fields × store cost).
  • Zero cycles reach runtime (I12, caught at compile time in 100% of fixtures).
Fixtures
  • scalar_replace_point.bc — the canonical two-field example from §8.4.
  • nested_virtual_objects.bc — recipe DAG with nested objects.
  • remat_cycle_reject.ir — compile-time rejection fixture.
  • shared_field_identity.bc — two references to the same virtual object must remat to the same instance.
  • partial_escape.bc — an allocation that escapes on one control-flow path but not another.
Pitfalls
  • Rematerializing the same virtual object twice under two different field references, breaking identity (I4) even though each individual field value is correct.
  • A recipe dependency ordering bug rebuilding a nested object before its own fields are available.
  • Partial escape analysis interacting badly with rematerialization: the object escaped on the taken path, so it already exists on the heap, but the recipe naively allocates a duplicate.
  • Recipe DAG depth unbounded, risking stack overflow in the (recursive, naturally expressed) rematerialization walk — must be iterative or explicitly depth-bounded.
  • The per-deopt-event cache (17.2) accidentally scoped too broadly (e.g. reused across two different deopt events on the same thread), reintroducing cross-event identity aliasing the design specifically avoids.
  • A RematRecipe referencing a ValueLocation that was itself supposed to be rematerialized, but the dependency edge was omitted from the DAG — producing an incomplete rather than a cyclic graph, which I12's cycle check does not catch.

⬜ Phase 6 — Type-Feedback Speculation: Monomorphic Calls and Inline Caches §18

Objectives

Implement monomorphic-call speculation for real, backed by runtime type feedback (profile-driven, not compile-time-only), following Hölzle & Ungar 1994 and the Deutsch & Schiffman 1984 inline-cache model.

Deliverable

Profile-driven monomorphic-call speculation integrated into the toy optimizer, plus the receiver-class guard and its deopt path (reusing Phase 2's single-frame procedure, now inlined per Phase 3's InlineFrameChain).

Acceptance
  • 100% of monomorphic-in-profile call sites in the fixture set correctly speculate.
  • 100% of receiver-class-guard failures correctly deopt to the exact call-site BytecodeIndex (I2) with the pre-call receiver and arguments intact (I5).
Fixtures
  • monomorphic_stable.bc — never fails.
  • monomorphic_then_polymorphic.bc — the §8.3 worked-trace scenario.
  • megamorphic_never_speculate.bc — regression: must not even attempt the guard.
  • inline_depth_2_call_guard.bc — guard inside an inlined callee.
Pitfalls
  • Speculating monomorphic on a call site whose profile sample size was too small, causing near-certain immediate deopt (a Phase-9-relevant tuning problem, but a Phase-6 fixture must at least detect it).
  • Receiver-class guard placed after a side-effecting instruction that should not re-execute on deopt (a preview of Phase 8's exception/control-flow complexity, must be avoided here by placing the guard strictly before any side effect).
  • Guard failure inside a doubly-inlined call chain resuming at the wrong inline-frame level.
  • Type-feedback table itself becoming stale relative to the currently-compiled speculation (a data-freshness bug distinct from the invalidation model of Phase 4).
  • A polymorphic call site misclassified as monomorphic due to an undersized profiling sample window, speculating too early (a specific instance of the general sample-size pitfall above, worth its own fixture because it is the single most common real-world cause of Phase-9-relevant thrashing).
  • The deliberately-unspeculated polymorphic case (18.2) accidentally falling through to a default monomorphic guess rather than staying genuinely unspeculated, silently reintroducing the guaranteed-fail-guard problem the design avoids.

⬜ Phase 7 — OSR-In: Interpreter to Optimized Code at a Loop Back-Edge §19

Objectives

Implement OsrEntry (§11) and the OSR-in half of §8.5, following Fink & Qian 2003 and Lameed & Hendren 2013, so a long-running interpreted loop can transition into optimized code mid-execution without waiting for method re-entry.

Deliverable

A deopt-osr crate implementing OSR-in, integrated with the Phase-1 state-map format (an OsrEntry is structurally a DebugInfo describing an entry rather than an exit).

Acceptance
  • OSR-in trigger latency ≤5 ms (§4).
  • 100% of admitted OSR-in fixtures produce output identical to continued interpretation — the differential property applied to a mid-loop tier transition.
  • 100% of I10-violating fixtures are correctly rejected rather than corrupting state.
Fixtures
  • osr_simple_loop.bc — baseline OSR-in.
  • osr_divergent_type.bc — I10 rejection case.
  • osr_nested_loop.bc — nested-loop OSR admission.
  • osr_threshold_tuning.bc — regression: verify the back-edge counter threshold itself, ADR-10.
Pitfalls
  • Transferring a loop-carried value into the wrong optimized-code location, corrupting the very first optimized iteration silently.
  • Racing the back-edge counter against a concurrent class-load invalidation targeting the same method (Phase 4 interaction) — OSR-in must not admit into a method that is simultaneously being invalidated.
  • Rejecting OSR-in too conservatively (I10 overly strict), losing the performance benefit for loops that are actually mappable — a tuning bug, not a correctness one, but tracked as a pitfall since it silently defeats the phase's purpose.
  • Nested loops OSR-ing at the wrong header, entering optimized code partway through an outer loop's setup.
  • The structural-reuse assumption (19.2) breaking silently because a Phase-1 decoder change assumed exit-only usage (e.g. an optimization that is only valid for optimized-to-interpreter direction) and was never re-validated against the entry-direction use introduced here.
  • A back-edge counter shared incorrectly between two textually-identical but distinct loop instances (e.g. inside two different inlined copies of the same source loop), causing one loop's OSR trigger to misfire for the other's iteration count.

⬜ Phase 8 — Deopt at Exceptions and Complex Control Flow §20

Objectives

Extend the deoptimizer to handle exception dispatch and irregular control flow (try/catch regions, finally blocks, loop-exit-via-exception) without violating I2, I5, or I6.

Deliverable

Exception-aware deopt paths integrated into deopt-runtime, handling try/catch, finally, and exception-driven loop exits.

Acceptance
  • 100% of exception-triggering fixtures resume with the correct handler selected and correct live state (I2, I5).
  • No double-execution of side effects in any fixture — a new, exception-specific correctness property beyond the base differential check.
Fixtures
  • exception_simple_catch.bc — baseline try/catch deopt.
  • exception_finally_unwind.bc — finally-block unwind.
  • exception_through_inlined_call.bc — interacts with Phase 6's InlineFrameChain.
  • exception_loop_exit.bc — exception-driven loop exit.
Pitfalls
  • Handler-lookup ordering bug (ADR-11's special case implemented backwards) resolving the wrong catch block.
  • A side effect re-executed because the guard/trap was placed after it rather than before (same class of bug as §18.6, now with exception semantics making the consequence worse — an idempotency violation, not just a wrong value).
  • Finally-block state incorrectly duplicated or dropped across the exception-driven unwind.
  • Rematerialization (Phase 5) invoked during exception unwind racing with the exception object's own allocation.
  • The idempotency check (20.2) implemented only for the exception path and not retrofitted onto Phases 2-7's existing trap sites, leaving the generalization aspirational rather than actually enforced project-wide.
  • An exception's own allocation itself becoming a candidate for scalar replacement, then being rematerialized incorrectly because the rematerialization engine (Phase 5) was never tested against exception-object shapes specifically.

⬜ Phase 9 — The Deopt-Thrashing Guard and Reprofiling §21

Objectives

Implement the thrashing guard (I11) and the reprofiling controller (ADR-14) so that a repeatedly-failing speculation is blacklisted rather than recompiled forever, closing the loop opened by Phase 6's megamorphic-guard-reject counter.

Deliverable

A deopt-tiers-integrated thrashing guard and reprofiling controller, wired to Phase 6's monomorphic-call speculation as the first blacklist-eligible speculation type.

Acceptance
  • 100% of synthetic deopt-storm fixtures trigger blacklisting within the §4 threshold window.
  • Zero fixtures blacklist a speculation that stabilizes within the decay window — false-positive blacklist rate = 0 on the regression set.
Fixtures
  • deopt_storm_megamorphic.bc — the canonical thrashing scenario.
  • transient_polymorphism_recovers.bc — must NOT blacklist.
  • blacklist_persists_across_recompile.bc — blacklist durability check.
  • decay_window_boundary.bc — regression pinning the exact threshold arithmetic.
Pitfalls
  • Blacklist threshold miscounted per-method instead of per-(method, speculation) pair, over-blacklisting unrelated speculations on the same hot method.
  • Decay applied too aggressively, causing a genuinely-thrashing site to escape blacklisting by resetting its counter before the ceiling is reached.
  • A blacklisted speculation's dependency-tracker registration (Phase 4) not cleaned up, causing a phantom invalidation attempt on a speculation that no longer exists.
  • Reprofiling racing a concurrent recompilation request, applying decayed counters to the wrong compile generation.
  • The sliding-window rate (21.2) implemented as a fixed-size ring buffer whose window boundary aliases with the invocation-count sampling interval, producing an aliasing artifact that under- or over-counts near the boundary.
  • Per-(method, AssumptionKind) granularity (21.2) masking a genuinely call-site-specific thrashing pattern where one of several same-AssumptionKind guards on a method is pathological and the others are fine, since the shared counter blacklists all of them together — finer call-site-level granularity is PhaseDeferred("Phase 9") pending production evidence this masking is a real, not merely theoretical, problem (§37).

⬜ Phase 10 — The Tiered-Compilation Lifecycle and Recompilation §22

Objectives

Implement the full §8.8 state machine end-to-end — Interpreted → Profiling → Tier1 → Optimized → Deoptimized → Reprofiled → Recompiled → Blacklisted — with every failure edge, following Paleczny, Vick & Click 2001's HotSpot server-compiler tiering model.

Deliverable

A deopt-tiers crate implementing the complete state machine with instrumented transitions, integrated with every earlier phase's triggers (guard failure, invalidation, OSR, exception, thrashing).

This is also, functionally, the delivery of the full engine's steady-state behavior: from this phase onward, the project can be exercised end-to-end as a single coherent lifecycle rather than as eleven separate mechanisms demonstrated in isolation.

Acceptance
  • 100% of state-machine transitions in the fixture set match the §8.8 table exactly, including every failure edge.
  • Recompilation latency ≤20 ms p99 (§4).
  • Zero invalid transitions (I13) detected across the full regression suite.
Fixtures
  • full_lifecycle_happy_path.bc — Interpreted through Optimized with no deopt.
  • lifecycle_with_deopt_recompile.bc — full deopt-to-recompile cycle.
  • lifecycle_blacklist_terminal.bc — terminal blacklist state.
  • concurrent_tier_transitions.bc — stress: multiple methods transitioning simultaneously under one safepoint sweep.
Pitfalls
  • A transition applied without holding the required safepoint serialization, letting a mutator thread observe a torn Tier value.
  • Recompilation producing a new nmethod that re-registers a dependency (Phase 4) the old nmethod never cleaned up, double-counting the dependent set.
  • Reprofiled state feeding a recompile decision before decay (Phase 9) has stabilized it, causing premature or oscillating recompilation.
  • A rollback edge (P14) implemented as a no-op instead of an actual state reversion, silently leaving a method in an inconsistent tier.
  • The single-choke-point design (22.2) bypassed by a well-intentioned "fast path" that mutates Tier directly for an allegedly-trivial case, reintroducing exactly the distributed-mutation risk the design was meant to eliminate.
  • A batched transition sweep (22.2) processing two methods' requests in an order that matters (e.g. a dependency-tracker invalidation for method A must be visible before method B's recompile request reads the dependent set) but the batching implementation does not preserve that ordering.

⬜ Phase 11 — Differential Correctness Harness, Conformance, and Perf Hardening §23

Objectives

Build the CI-gated differential harness that is this entire project's terminal correctness proof: for every fixture accumulated across Phases 0–10, run fully interpreted and run optimized-with-deopt-forced-at-every-safepoint, and assert identical observable results (the defining property of §28).

Deliverable

A CI-gated differential/fuzz harness covering 100% of safepoints across the full Phase 0–10 fixture corpus, plus perf-regression gates on safepoint overhead and deopt latency (§4, §30).

Acceptance
  • State-reconstruction correctness = 100% (§4, zero tolerance) across the full corpus and a minimum 24-hour fuzz soak with zero mismatches.
  • Safepoint-overhead perf gate fails the build on any regression beyond the §4 ≤2 ns target.
Fixtures
  • The full accumulated fixture corpus from 12.5 through 22.5, run through the forced-deopt-at-every-safepoint harness.
  • fuzz_generated_regressions/ — auto-populated by the fuzzer on any discovered mismatch, per ADR-23.
  • zero_safepoint_program.bc — degenerate case, §23.8.
  • dead_safepoint_program.bc — safepoint reachable only in eliminated dead code, §23.8.
Pitfalls
  • A forced deopt at a safepoint that legitimately never fails in practice (e.g., an always-true guard) reveals a latent I1/I9 gap that normal execution never exercises — treated as a real finding, not a harness artifact.
  • Fuzzer-generated programs that are not valid per the (assumed, delegated) bytecode verifier, producing false-positive mismatches unrelated to deopt correctness — must be filtered by re-validating fuzzer output against the verifier contract before compiling.
  • Flaky mismatches traced to non-determinism in the toy interpreter itself (a Phase-0 assumption violated late) rather than a real deopt bug.
  • Perf-regression gate false-triggering on CI-runner noise rather than a real safepoint-overhead regression — mitigated by running the perf gate on dedicated, pinned-clock runners (ADR-24 exception).
  • The exhaustive per-safepoint sweep (23.2) silently degraded into a sampled sweep under time pressure, quietly weakening the "100% of safepoints" claim (M13) without anyone noticing until a since-untested safepoint's bug ships.
  • The fast-subset/nightly-full split (23.7) drifting so that the fast subset stops being representative of the full corpus's failure modes, making a green fast-subset push a false signal of health.
