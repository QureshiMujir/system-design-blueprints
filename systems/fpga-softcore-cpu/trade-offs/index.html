Decisions (§9) · 30 ADRs

1

HDL

Chosen

SystemVerilog (synth subset)

Rejected

VHDL, Chisel, SpinalHDL, Amaranth, Verilog-2005

When the rejected choice is right

Chisel/SpinalHDL wins when a parameterized generator family (dozens of microarch variants) amortizes the Scala build overhead; VHDL wins in DO-178C/DO-254 avionics/defense flows where VHDL toolchains are mandated.

Why: Open-tool + RISC-V-verif native; typed; interfaces/assertions; one source sim+synth.

2

First core

Chosen

Single-cycle golden reference (core_sc)

Rejected

Start directly at pipeline

When the rejected choice is right

Start at pipeline wins when time-to-demo is the constraint and an external golden ISS (Spike) is trusted from day one as the sole oracle — e.g. a commercial project with a licensed RTL diff harness already in place.

Why: Obvious correctness baseline to diff the pipeline against.

3

Main core

Chosen

Classic 5-stage in-order (core_p5)

Rejected

2-stage (Ibex), multi-cycle FSM (PicoRV32), OoO

When the rejected choice is right

2-stage (Ibex-style) wins when minimum area and Fmax matter more than textbook coverage — e.g. a deeply embedded IoT microcontroller constrained to < 10 K LUTs. Multi-cycle FSM (PicoRV32) wins when every LUT counts on the smallest iCE40 or in an ASIC gate-count budget.

Why: Textbook clarity; exercises forwarding/hazards/precise traps.

4

ISA

Chosen

RV32I + optional M, Zicsr/Zicntr

Rejected

RV64, MIPS, custom, ARM

When the rejected choice is right

RV64 wins when hosting a 64-bit OS (Linux) or running pointer-heavy workloads; custom ISA wins for a domain-specific accelerator (DSP, crypto) where standard toolchain conformance is irrelevant and encoding density dominates.

Why: Open, modular, royalty-free, huge toolchain + conformance ecosystem.

5

Sim (primary)

Chosen

Verilator (cycle-accurate C++)

Rejected

Icarus-only, commercial (VCS/Questa)

When the rejected choice is right

Commercial VCS/Questa wins when the design uses UVM or IEEE 1800-2017 SV constructs Verilator does not support (e.g. packed unions, DPI-C with complex types), or when full-system SoC simulation with encrypted vendor IPs requires a compliant simulator.

Why: Fast, free, scriptable; drives differential harness in C++.

6

Sim (quick)

Chosen

Icarus Verilog

Rejected

none

When the rejected choice is right

Icarus is the only choice in this role; it wins anywhere Verilator's C++ compilation overhead is too slow for sub-second interactive feedback on small module changes.

Why: Fast event-driven smoke runs, SVA support.

7

Sim (high-level)

Chosen

cocotb (Python) — optional

Rejected

UVM (SV)

When the rejected choice is right

UVM wins in large ASIC verification teams where a common, reusable VIP library (PHY, PCIe, DDR) demands UVM-compliant drivers/monitors and scoreboards; industry SoC verification is nearly all UVM.

Why: Lightweight Python TBs; UVM is heavy for this scale.

8

Synthesis

Chosen

Yosys

Rejected

Vivado, Quartus

When the rejected choice is right

Vivado wins on Xilinx 7-series/UltraScale targets where Yosys-to-nextpnr loses significant Fmax vs the vendor back-end, or when hard IPs (SERDES, PCIe core) require vendor tool integration.

Why: Open, scriptable, multi-fabric; pairs with nextpnr.

Place & route

Chosen

nextpnr

Rejected

vendor PnR

When the rejected choice is right

Vendor PnR (Vivado/Diamond/Quartus) wins on any target fabric outside the nextpnr-supported set, or when the open PnR cannot close timing that the vendor router achieves through fabric-specific optimizations.

Why: Open, supports iCE40 + ECP5; timing-driven.

Formal

Chosen

When the rejected choice is right

Hand-written SVA only wins when the design has no RVFI interface and retrofitting it is impractical — e.g. a legacy closed-source core being post-hoc audited — or when bespoke liveness/safety properties go beyond the riscv-formal check set.

24

Reset

Chosen

Synchronous, active-high internal

Rejected

async reset

When the rejected choice is right

Async reset wins in ASIC flows where power gating requires instant reset assertion independent of the clock (clock may be off), or when a power-down domain needs immediate state clearing before the clock restores.

Why: Avoids reset-recovery/CDC issues; cleaner timing.

25

Clocking

Chosen

Single domain + PLL; 2-flop sync for UART RX

Rejected

multi-clock

When the rejected choice is right

Multi-clock wins when peripherals run at intrinsically different rates that cannot be PLL-combined — e.g. a USB 48 MHz PHY plus a 100 MHz core — requiring a full CDC crossing and FIFO per domain boundary.

Why: Simplicity; one CDC point only.

26

Multiplier (M-ext)

Chosen

DSP-inferred (MULT18/MAC16); multi-cycle divider

Rejected

fully combinational mul/div

When the rejected choice is right

Fully combinational mul/div wins on small ASIC nodes (180 nm and below) where combinational area is cheap and latency tolerance is zero — e.g. a hard-macro ALU in a single-cycle microcontroller at low Fmax.

Why: Fits fabric, closes timing; comb divider blows the critical path.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A: Multi-cycle FSM (PicoRV32-style)

+------------------------------------------+
|  soc_top                                 |
|                                          |
|  +------------------+                   |
|  |  core_fsm         |  One register     |
|  |  PC reg           |  file, one ALU,   |
|  |  state: FETCH ->  |  reused each      |
|  |  DECODE -> ALU -> |  micro-step by    |
|  |  MEM -> WB        |  an FSM counter   |
|  +------------------+                   |
|  Single shared BRAM (instr + data)       |
|  Wishbone or direct memory port          |
+------------------------------------------+

Regime where it wins. When die area or FPGA LUTs are the primary constraint (< 2 000 LUT4) and IPC is irrelevant — sensor microcontrollers, clock-domain isolation logic, custom ASIC under 10 K gates. The FSM's tiny critical path yields very high Fmax on small fabric (PicoRV32 exceeds 100 MHz on iCE40) despite CPI of 3–6.

Real system that embodies it. PicoRV32 (Clifford Wolf) — see Ref-impl #2; also the original 8051 core.

Why this blueprint rejected it. The pedagogical goal (§2.1) is to build the canonical 5-stage pipeline that every architecture course teaches — forwarding networks, hazard detection, and pipeline registers are load-bearing learning outcomes. A multi-cycle FSM eliminates all of those; it also makes formal verification of timing-sensitive hazard logic impossible. Correctness over area was the explicit choice (Design Principle 1).

Alt-B: 2-stage in-order pipeline (Ibex/zero-stage style)

+------------------------------------------+
|  soc_top                                 |
|                                          |
|  +------------------+                   |
|  |  stage_if         |  Fetch + partial  |
|  |  (fetch + decode) |  decode in one    |
|  +------------------+  stage; no        |
|         |              IF/ID register    |
|  +------------------+                   |
|  |  stage_ex         |  Decode + EX +    |
|  |  (full ALU, MEM,  |  MEM + WB in     |
|  |  WB, CSR, trap)   |  one wide stage   |
|  +------------------+                   |
+------------------------------------------+

Regime where it wins. When area is tighter than ~5 K LUT4 but a complete machine-mode CSR set and M-extension are needed — i.e., the use case is an embedded microcontroller with a certified firmware stack (Ibex targets OpenTitan, a security processor). The 2-stage design eliminates most pipeline hazards (no load-use stall in the classic sense) and simplifies trap logic while retaining reasonable Fmax.

Real system that embodies it. Ibex (lowRISC) — see Ref-impl #4; also the ARM Cortex-M0 (2-stage). See Comparative Architecture Table.

Why this blueprint rejected it. A 2-stage design does not exercise the forwarding network, the load-use hazard, or the 2-cycle branch flush — the three hardest concepts in pipelining. The five-stage structure (ADR-3) was chosen specifically to make those mechanisms explicit and verifiable (Phase 3, Phase 4). The 2-stage alternative is documented in the Comparative Architecture Table and referenced in cross-link #188.

Alt-C: Generator-style parameterized core (VexRiscv / Chisel approach)

+-------------------------------------------------------+
|  generator.scala (SpinalHDL / Chisel)                 |
|                                                       |
|  Pipeline = new Pipeline(                             |
|    stages = [IF, ID, EX, MEM, WB],                   |
|    plugins = [DecoderPlugin, HazardPlugin,            |
|               BranchPlugin, CachePlugin, ...]         |
|  )                                                    |
|  // Each plugin injects signals into the pipeline     |
|  // Generates Verilog/FIRRTL as output               |
+-------------------------------------------------------+
         | (generated Verilog)
         v
+----------------------+
|  Yosys + nextpnr     |
+----------------------+

Regime where it wins. When a team ships multiple SKUs from one codebase — a minimal RV32I, an RV32IMC with a BHT, and an RV64GC with caches and an MMU — that differ only in plugin composition. The generator amortizes RTL authoring cost across variants and enforces interface contracts automatically. SiFive uses a similar approach (Rocket/BOOM in Chisel) to generate a family of cores.

Real system that embodies it. VexRiscv (SpinalHDL) — see Ref-impl #3; Rocket Chip generator (Chisel) — see Ref-impl #5.

Why this blueprint rejected it. The Scala/SpinalHDL/Chisel build chain adds a large non-RTL dependency (JVM, sbt, Scala toolchain) with significant learning overhead for an audience whose primary goal is mastering SystemVerilog HDL and pipeline micro-architecture. Generated Verilog is harder to read and debug than hand-written SV; waveform debugging requires navigating generated names. For a single-core teaching project, the generator overhead is all cost and no benefit. This is documented in §1.10 rejected alternatives and ADR-1.
