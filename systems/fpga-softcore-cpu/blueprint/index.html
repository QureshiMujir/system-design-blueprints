290 — FPGA Softcore CPU from Scratch

Goal: Build a from-scratch, synthesizable RV32I soft processor core in SystemVerilog — single-cycle reference, then a classic 5-stage in-order pipeline with forwarding, hazard detection, and branch handling — wired to a Wishbone B4 bus fabric with BRAM, UART, timer, and GPIO, machine-mode CSRs and trap handling, fully verified against riscv-tests, a Spike differential oracle, RISCOF conformance, and riscv-formal, then closed for timing and brought up on iCE40 (UP5K) and ECP5 FPGAs with an on-board blink + UART-hello bring-up.

1. Goal

1.1 Precise scope

A synthesizable soft CPU, verified in simulation and proven on real fabric:

  • ISA: RV32I base (RV32 unprivileged, integer). Optional M (mul/div) and Zicsr/Zicntr (CSR access + base counters) gated as later phases. Encoding formats R/I/S/B/U/J implemented exactly per the RISC-V spec.
  • Microarchitecture: single-cycle golden reference (core_sc), then a classic 5-stage in-order pipeline (core_p5): IF → ID → EX → MEM → WB, with a 32×32 register file (x0 hardwired zero, 2R/1W), an ALU, immediate generation, a control/decode unit, and PC-next logic.
  • Hazards: data hazards via a forwarding/bypass network (EX→EX, MEM→EX) + a load-use stall; control hazards via branch resolution in EX, IF/ID flush, static not-taken default with an optional simple predictor seam; structural hazards eliminated by a split (Harvard-ish) instruction/data memory.
  • Memory & bus: split I/D into on-chip BRAM; a Wishbone B4 (classic then pipelined) bus fabric (wb_fabric) with an address decoder; memory-mapped peripherals — UART (TX/RX, programmable baud divisor), mtime/mtimecmp timer, and GPIO.
  • Privileged/CSR: machine mode only initially — mstatus, mtvec, mepc, mcause, mie, mip, mscratch, mtval; trap/exception/interrupt entry+return (mret); misaligned-access, illegal-instruction, ecall/ebreak handling.
  • Verification: riscv-tests (rv32ui) self-checking ISA suite; instruction-set differential testing against Spike (golden ISS) and optionally QEMU; RISCOF (riscv-arch-test) conformance flow; riscv-formal SymbiYosys formal ISA-compliance checks; self-checking assembly fixtures; simplified randomized instruction generation (riscv-dv style).
  • Physical: Yosys synthesis → nextpnr place-and-route → bitstream for iCE40 UP5K and ECP5; timing closure to documented Fmax targets; on-board blink + UART-hello bring-up; area budgets (LUT/FF/BRAM/DSP).
  • Tooling: Verilator (cycle-accurate C++ sim) + Icarus (quick sim); cocotb optional; GTKWave for waveforms; riscv-gcc/llvm + binutils for test programs; SymbiYosys for formal.

1.3 Explicit non-goals

  • No RV64; the datapath is fixed 32-bit (XLEN=32).
  • No floating point, atomics, compressed, or vector extensions in the core arc; gated PhaseDeferred("FINAL_BLUEPRINT §1.3").
  • No supervisor/user privilege, no MMU/TLB/page tables; machine mode only.
  • No cache hierarchy (BRAM is single-cycle, zero-wait by default; a wait-state model exists for bus realism) — caches are a separate study (→ #187).
  • No external memory controller (DDR/SDR) — PhaseDeferred.
  • No RISC-V Debug Module (DMI/JTAG halt/resume) — bring-up uses UART + LEDs.
  • No vendor (Xilinx Vivado / Intel Quartus) flow; open-source toolchain only.
  • No multi-core / cache coherence; single hart.

1.4 Deployment model

  • Synthesizable RTL — rtl/ SystemVerilog (synthesizable subset: no initial in synth path except BRAM init, no delays, no dynamic arrays) targeting Yosys/nextpnr for iCE40 + ECP5, and any other FPGA via portable inference.
  • Simulation models — Verilator (C++ harness, cycle-accurate, fast) is the primary verification substrate; Icarus Verilog for quick event-driven runs; cocotb (Python) optional for high-level tests. All share the same RTL.
  • Memory image — programs assembled by riscv-gcc → .elf → objcopy → hex/$readmemh image preloaded into BRAM at build (sim) or packed into the bitstream (FPGA).
  • Seam — a mem_if interface and the wb_fabric decode table decouple the core from memory/peripherals; BRAM now, external controllers later behind the same Wishbone seam.

1.5 Target users

Computer-architecture learners; FPGA/RTL engineers; embedded SoC integrators building a small control core; RISC-V toolchain/verification engineers; students studying pipelining, hazards, and timing closure; anyone needing a small, auditable, open soft core.

2. Why Build This

2.1 Unique systems knowledge

  • The hardware/software contract made physical — an ISA is not an abstraction here; every instruction encoding bit drives real muxes and wires; you implement the exact thing a compiler targets.
  • Pipelining and hazards in silicon — forwarding networks, stall logic, and flush control are the canonical reason a CPU is hard; you build them and prove them, not just draw them.
  • Cycle-accurate determinism — RTL has no "undefined later"; every flip-flop has a value every cycle; X-propagation and reset discipline are unforgiving teachers.
  • Timing closure — the gap between "simulates correctly" and "runs at 50 MHz on real fabric" is critical-path analysis, retiming, and Fmax — a skill no pure-software project develops.
  • Verification at three rigor levels — directed (riscv-tests), differential (Spike lockstep), and formal (riscv-formal) — the same correctness question attacked from three independent angles.
  • Trap/interrupt machinery — precise exceptions in a pipeline (which mepc? flush what? when does mtval latch?) is subtle and load-bearing for any OS.

2.2 Historical / architectural significance

The stored-program von Neumann/Harvard machine (1945–48) → RISC pipelines (MIPS/SPARC, Patterson & Hennessy, 1980s) → the classic 5-stage textbook pipeline that every architecture course teaches → RISC-V (Berkeley, 2010) as an open, modular, royalty-free ISA now spanning microcontrollers to supercomputers. A softcore on an FPGA is how RISC-V cores are actually prototyped (Rocket, BOOM, PicoRV32, VexRiscv, Ibex) before silicon. Building one is building the central artifact of computer architecture.

2.3 Engineering muscles

RTL design discipline; pipeline hazard reasoning; FSM + datapath co-design; clock/reset/CDC hygiene; static timing analysis + critical-path optimization; FPGA synthesis/PnR flow; cycle-accurate + formal verification; differential testing against a golden ISS; toolchain/linker/objcopy fluency; reading and implementing a formal ISA spec to the bit.

2.5 Calibration value

Forces correctness-first hardware engineering where a one-bit forwarding mux error corrupts a value three cycles later, a missing flush executes a wrong-path instruction, and "it simulates" means nothing until it closes timing and runs on real silicon. Builds the rare full-stack-down ability to take an ISA spec to a verified, formally-proven, timing-closed, physically-running processor — a permanent step-up in architecture and digital-design capability.

What Mastery Looks Like

  • RTL hazard reasoning (Phases 3–4): given any producer–consumer pair in a pipeline diagram, state the forwarding path used, the stall cycles incurred if forwarding is absent, and the exact pipe-register fields involved.
  • Formal verification fluency (Phase 10): configure riscv-formal RVFI wires, write a SymbiYosys task file, interpret a counterexample waveform, and distinguish bounded BMC proofs from k-induction proofs.
  • Precise-exception design (Phase 7): for each RISC-V trap cause, specify which in-flight instructions are committed vs flushed, what value is latched into mepc/mtval, and how mret restores the privilege state.
  • Differential testing at scale (Phase 8): build a Spike lockstep harness, align RVFI retire records with the ISS commit log, and bisect a divergence to the exact failing instruction retire.
  • FPGA timing closure (Phase 11): read a nextpnr timing report, identify the critical path through the EX forwarding + ALU chain, apply path-balancing or retiming, and verify positive slack without regressing correctness.
  • Wishbone bus design (Phase 5): specify a new memory-mapped slave (base, size, byte-enable policy, wait-state count), wire it into wb_fabric, write the protocol SVA assertions, and prove there is no deadlock.
  • RISC-V conformance methodology (Phase 9): write a RISCOF DUT plugin, configure the ISA string honestly, run the arch-test suite, and interpret signature-comparison failures as spec gaps vs configuration mismatches.
  • ISA-to-RTL traceability (Phases 1–2): for any RV32I instruction, trace the encoding bits through imm_gen, decoder, alu, and the WB mux to the regfile write without consulting the code.

3.2 Per-box detail

Clock/reset gen. Single synchronous clock domain (system clock from PLL/oscillator, e.g. 12 MHz on iCE40 UP5K, optionally multiplied). Synchronous active-high (internally) reset asserted N cycles after power-on / config done, released synchronously. The only asynchronous input is UART RX; it crosses into the clock domain via a 2-flop synchronizer (the sole CDC). Reset strategy and clocking are frozen in rv_pkg/soc_top and referenced everywhere.

IF stage (PC logic). Holds the program counter; pc_next selects pc+4, a branch/jump target (from EX), or a trap vector / mepc (from csr_file). Issues an instruction fetch (Wishbone read or direct BRAM read) and latches the fetched instruction into the IF/ID register. On flush, injects a bubble (NOP) instead. PC is 32-bit, byte-addressed; misaligned-fetch detection lives here.

ID stage (decoder + imm_gen + regfile read). decoder cracks the 32-bit instruction into opcode/funct3/funct7 → control signals (ALU op, operand selects, mem read/write, reg-write enable, branch type, CSR op, illegal flag). imm_gen produces the sign-extended immediate per format (I/S/B/U/J). regfile reads rs1/rs2 combinationally (with a write-first bypass on same-cycle WB). Results latch into the ID/EX register.

EX stage (ALU + branch_unit + forward mux). The alu computes the arithmetic/logic/address result. The forwarding muxes select rs1/rs2 from EX/MEM or MEM/WB when a hazard is detected (else from ID/EX). The branch_unit evaluates the branch condition (EQ/NE/LT/GE/LTU/GEU) and computes the target; on a taken branch/jump it signals the hazard unit to redirect PC and flush IF/ID and ID/EX (the wrong-path instructions). Results latch into EX/MEM.

MEM stage (data memory access + align). Drives the data-side Wishbone master for loads/stores; handles sub-word access alignment (byte/half/word, signed/unsigned load extension, store byte-enables), and detects misaligned data access (→ trap). For BRAM the access is single-cycle; with wait states the pipeline stalls via the bus ack. Latches load data / ALU result into MEM/WB.

WB stage (writeback mux). Selects the value written back to the register file: ALU result, load data, pc+4 (for JAL/JALR link), or a CSR read value. Writes rd (suppressed if rd==x0). The regfile write port lives here; a write-first/forwarding path feeds ID reads in the same cycle.

Hazard unit. The pipeline's brain. Computes forwarding selects (EX/MEM→EX, MEM/WB→EX) by comparing source registers against in-flight destination registers with write-enable + non-x0 guards. Detects load-use hazards (a load in EX whose rd feeds the next instruction's source) → inserts one stall cycle (freeze PC + IF/ID, bubble ID/EX). Handles branch/trap flushes by killing fetched/decoded wrong-path instructions. The single source of truth for all stall/flush/forward control.

csr_file. Machine-mode CSRs (mstatus, mtvec, mepc, mcause, mie, mip, mscratch, mtval, mcycle, minstret). Implements CSR read/modify/write (csrrw/s/c[i]), trap entry (latch mepc/mcause/mtval, set mstatus.MPIE/MPP, jump to mtvec), and trap return (mret restores mstatus, jumps to mepc). Aggregates interrupt-pending bits (timer mtip, external, software) into mip, gated by mie/mstatus.MIE. The privilege/trust boundary between architectural and microarchitectural state.

wb_fabric. Wishbone B4 interconnect. An address decoder maps the 32-bit address space into regions [IMEM | DMEM | UART | TIMER | GPIO] (base/mask table in rv_pkg), routes a master's cycle to the selected slave, returns dat_i/ack/err, and arbitrates instruction-fetch vs data access (split buses by default → no arbitration; shared bus → round-robin/priority). Classic handshake first, pipelined mode later. The bus/peripheral seam.

bram (IMEM/DMEM). Synchronous block RAM inferred onto FPGA BRAM primitives. IMEM is read-only to the core (initialized via $readmemh in sim / packed in bitstream on FPGA); DMEM is read/write with byte-enables. One-cycle read latency (registered output) — the pipeline accounts for this. Size-parameterized (e.g. 64–256 KB depending on fabric BRAM budget).

uart. Memory-mapped UART: a TX shift register + baud-rate generator (divisor = f_clk / baud) and an RX with start-bit detection, mid-bit sampling, and a 2-flop input synchronizer. Registers: TX data, RX data, status (TX-ready, RX-valid), and a baud-divisor register. The console for "hello" bring-up and a debug channel.

timer. RISC-V machine timer: a free-running 64-bit mtime counter (memory-mapped) and a mtimecmp compare register; when mtime >= mtimecmp it raises the timer-interrupt pending bit (mtip) into csr_file.mip. The basis for preemptive scheduling (RTOS) and a deterministic interrupt source.

gpio. Memory-mapped general-purpose I/O: an output data register driving pins (LEDs) and an input register sampling pins (synchronized). The simplest peripheral and the blink target; also used to signal test pass/fail on hardware.

soc_top. Top-level: instantiates the core, fabric, BRAM, and peripherals; connects clock/reset; exposes UART pins, GPIO/LEDs, and (on FPGA) the board's physical pins via the constraints file. The synthesis root and the simulation DUT.

6. Design Principles

  1. Correctness before speed; the single-cycle core is the golden reference. core_sc is dead simple and obviously correct; the pipeline must match it (and Spike) instruction-for-instruction. Tradeoff: building two cores. Ops: any pipeline bug is localized by diffing against the reference. Violation: optimizing the pipeline before it's correct hides bugs in performance noise.

  2. One ISA spec, implemented to the bit. Every encoding, immediate sign-extension, and edge case follows the ratified RISC-V manual exactly. Tradeoff: rigidity. Violation: a wrong immediate field or shift-amount mask fails conformance and breaks real compiled code silently.

  3. Synchronous single-clock, synchronous reset, X-clean after reset. All sequential logic on one clock edge; reset defines all architectural state; assertions forbid X in committed state. Tradeoff: none material at this scale. Violation: async-reset races or X-propagation cause sim/FPGA mismatch — the worst class of bug.

  4. Nonblocking assignments in sequential blocks, blocking in combinational; no mixing. Cummings' rule. Tradeoff: discipline. Violation: simulation/synthesis mismatch and race conditions that pass in sim and fail on fabric.

  5. The hazard unit is the single source of stall/flush/forward truth. No ad-hoc stalls scattered across stages. Tradeoff: one module sees everything (coupling). Violation: duplicated/conflicting stall logic deadlocks or double-issues.

  6. Forward maximally, stall minimally. Bypass EX/MEM→EX and MEM/WB→EX; stall only for load-use. Tradeoff: forwarding muxes add area/critical-path. Violation: missing a forwarding path silently reads a stale register value.

  7. Precise exceptions. A trap reports the exact faulting instruction; in-flight younger instructions are flushed, older ones complete; mepc/mcause/mtval are exact. Tradeoff: flush + commit-point bookkeeping. Violation: imprecise traps make any OS/RTOS impossible to debug.

  8. x0 is hardwired zero, everywhere. Reads return 0; writes are discarded — enforced in the regfile and writeback. Tradeoff: a guard on every write. Violation: addi x0,x0,0-as-NOP and canonical zero break; conformance fails.

  9. Bus access goes through the Wishbone seam. The core talks to memory/peripherals only via wb_if; BRAM/UART/timer/GPIO are slaves behind the decoder. Tradeoff: handshake latency. Violation: a core that pokes BRAM directly can't be retargeted to external memory or a cache.

  10. Assertions encode invariants; they run in sim and formal. SVA for one-hot control, no-X-after-reset, single-writer regfile, legal opcodes. Tradeoff: assertion authoring. Violation: invariants that live only in comments rot and are silently broken.

  11. Verification is three independent angles: directed, differential, formal. riscv-tests (directed), Spike lockstep (differential), riscv-formal (formal). Tradeoff: three harnesses. Violation: any single method has blind spots; agreement across all three is the bar.

  12. Synthesizable subset only in rtl/. No behavioral-only constructs in the datapath; testbench-only code stays in tb/. Tradeoff: less syntactic sugar. Violation: code that simulates but won't synthesize wastes a PnR cycle to discover.

  13. Parameterize, don't fork. Memory sizes, reset vector, optional M-ext, fabric target are parameters/ifdefs — not copied files. Tradeoff: parameter plumbing. Violation: divergent forks drift and double the bug surface.

  14. Timing closure is a first-class deliverable, not an afterthought. Critical path is measured and reported every synthesis; Fmax targets are acceptance criteria. Tradeoff: iterating the datapath for timing. Violation: "simulates fine" cores that can't hit a usable clock are not done.

  15. Determinism + replay. Same image + same seed → identical cycle-by-cycle behavior; every failing test replays exactly (waveform + Spike trace). Tradeoff: no nondeterministic shortcuts. Violation: flaky tests are unfixable and erode trust in the suite.

7. System Invariants

Each: statement → why → enforced where → detection → telemetry → recovery → debugging.

  1. x0 always reads as 0; writes to x0 are discarded. Why: ISA contract, canonical zero/NOP. Where: regfile read mux + write guard. Detect: SVA rd==0 |-> regfile[0]==0; differential vs Spike. Telemetry: regfile write trace. Recover: N/A (compile-time guard). Debug: dump regfile after each commit.

  2. The pipeline commits in program order; results match the single-cycle core and Spike. Why: correctness. Where: WB commit + differential harness. Detect: lockstep PC+regfile mismatch. Telemetry: RVFI retire record (pc, insn, rd, wdata). Recover: bisect to first divergent instruction. Debug: dump both traces, diff.

  3. Every register read sees the most recent write (via forwarding or stall). Why: data-hazard correctness. Where: hazard forwarding + load-use stall. Detect: differential value mismatch; SVA on forward-select one-hotness. Telemetry: forward-select signals in waveform. Recover: add/fix forwarding path. Debug: trace producer/consumer cycles in GTKWave.

  4. A taken branch/jump flushes exactly the wrong-path instructions (IF/ID and ID/EX), no more, no less. Why: control-hazard correctness. Where: branch_unit + hazard flush. Detect: wrong instruction retires after a branch (differential). Telemetry: flush signal + redirected PC. Recover: fix flush mask/timing. Debug: branch-redirect waveform.

  5. Loads complete before a dependent instruction reads the loaded register (load-use stall inserted). Why: 1-cycle load latency. Where: hazard load-use detection. Detect: stale value read after a load (differential). Telemetry: stall signal, load-use detect. Recover: insert stall. Debug: load→use cycle trace.

  6. Traps are precise: mepc = faulting PC, younger instructions flushed, older committed. Why: precise-exception requirement. Where: csr_file + hazard trap redirect. Detect: wrong mepc/mcause (differential vs Spike CSR). Telemetry: trap event (cause, epc, tval). Recover: fix commit-point/flush. Debug: trap-entry waveform + Spike CSR diff.

  7. mret restores mstatus.MIE from MPIE and resumes at mepc. Why: trap-return semantics. Where: csr_file. Detect: wrong resume PC or interrupt-enable state. Telemetry: mret event, mstatus before/after. Recover: fix mstatus-stack logic. Debug: nested-trap test trace.

  8. Wishbone handshake is well-formed: every cyc&stb is eventually ack'd (or err); no stuck cycles. Why: bus liveness. Where: wb_fabric + slaves. Detect: SVA bus-handshake property; watchdog timeout. Telemetry: bus cycle counters, stall cycles. Recover: bus reset / fix slave. Debug: bus waveform, decode-region check.

  9. Memory accesses respect alignment; misaligned access raises the correct trap (or is handled per config). Why: ISA load/store semantics. Where: MEM-stage align/check. Detect: misaligned address without trap (differential). Telemetry: misaligned-access counter, trap cause. Recover: raise trap. Debug: address LSBs vs access size in trace.

  10. Only one source drives the regfile write port per cycle (single writer). Why: structural correctness. Where: WB stage. Detect: SVA single-writer; X on regfile if multi-driven. Telemetry: write-enable + rd. Recover: fix writeback mux. Debug: writeback-control waveform.

  11. No X (unknown) in architectural state after reset deassertion. Why: determinism, sim/FPGA parity. Where: global SVA. Detect: assert (!$isunknown(state)). Telemetry: X-origin (first offending signal). Recover: add reset value. Debug: trace X back to its source signal.

  12. Illegal instructions raise the illegal instruction trap with mtval=the bad insn. Why: ISA robustness. Where: decoder illegal flag + csr_file. Detect: undecoded opcode doesn't trap (differential/fuzz). Telemetry: illegal-insn counter, mtval. Recover: trap. Debug: opcode vs decode table.

8.10 Worked examples + edge cases

  • addi x5, x6, -1 → I-type, opcode 0010011, funct3 000, rs1=6, rd=5, imm=0xFFFFFFFF; ALU = rs1 + imm = x6 − 1.
  • sw x3, 8(x10) → S-type, addr = x10+8, store x3 word; byte-enable 1111; address LSBs must be 00 else misaligned trap.
  • beq x1, x2, +16 → B-type, immB=+16 (LSB forced 0); if x1==x2, PC=PC+16, flush 2.
  • jal x1, +2048 → J-type, rd(x1)=PC+4, PC=PC+immJ; immJ LSB=0, ±1 MiB range.
  • csrrw x5, mscratch, x6 → atomic: x5=old mscratch, mscratch=x6 (if rd=x0, suppress read side-effects on some CSRs; if rs1=x0 for CSRRS/C, no write).
  • Edge: SLLI/SRLI/SRAI shamt → only imm[4:0] (5 bits for RV32); imm[11:5] must be 0000000 (SLLI/SRLI) or 0100000 (SRAI), else illegal.
  • Edge: JALR → target=(rs1+imm) with LSB cleared (& ~1); rd=PC+4; rd=x0 ⇒ return-style jump.
  • Edge: load from MMIO (UART RXDATA) → side-effecting read; must not issue on a wrong path (flush before MEM commit).
  • Malformed: opcode 1111111 → not in decode table → illegal-instruction trap, mtval=insn.
  • Malformed: misaligned lw at 0x...3 → load-address-misaligned trap (cause 4), mtval=addr.
  • Edge: mtime rollover → 64-bit counter; mtimecmp compare must be 64-bit to avoid spurious/missed interrupts near rollover.

6 Sim (quick) Icarus Verilog none Fast event-driven smoke runs, SVA support. Icarus is the only choice in this role; it wins anywhere Verilator's C++ compilation overhead is too slow for sub-second interactive feedback on small module changes.
7 Sim (high-level) cocotb (Python) — optional UVM (SV) Lightweight Python TBs; UVM is heavy for this scale. UVM wins in large ASIC verification teams where a common, reusable VIP library (PHY, PCIe, DDR) demands UVM-compliant drivers/monitors and scoreboards; industry SoC verification is nearly all UVM.
8 Synthesis Yosys Vivado, Quartus Open, scriptable, multi-fabric; pairs with nextpnr. Vivado wins on Xilinx 7-series/UltraScale targets where Yosys-to-nextpnr loses significant Fmax vs the vendor back-end, or when hard IPs (SERDES, PCIe core) require vendor tool integration.
9 Place & route nextpnr vendor PnR Open, supports iCE40 + ECP5; timing-driven. Vendor PnR (Vivado/Diamond/Quartus) wins on any target fabric outside the nextpnr-supported set, or when the open PnR cannot close timing that the vendor router achieves through fabric-specific optimizations.
10 FPGA targets iCE40 UP5K + ECP5 Xilinx 7-series, Intel Cyclone Fully open flow end-to-end; cheap dev boards. Xilinx 7-series/Intel Cyclone wins when the target application demands a specific external interface (SATA, PCIe, high-speed transceiver) available only on larger Xilinx/Intel families, or when the project must co-exist with vendor hard IPs.
11 Waveforms GTKWave (+ FST/VCD) commercial viewers Free; integrates with Verilator/Icarus dumps. Commercial viewers (Verdi, DVT) win on multi-million-gate SoC waveforms where hierarchical cross-probing, schematic back-annotation, and protocol-decode plugins exceed GTKWave's capacity.
12 Toolchain riscv64-unknown-elf-gcc (RV32 multilib) + binutils LLVM-only Standard; LLVM secondary; assembles tests + Dhrystone. LLVM-only wins when the project targets a custom ISA extension that GCC does not yet support (LLVM's back-end is more pluggable) or when clang's diagnostics / sanitizers are needed for the test-program C code.
13 Differential oracle Spike (riscv-isa-sim) QEMU-only, custom ISS Reference golden model; RVFI-style lockstep. QEMU wins when the full-system simulation (OS + devices) is needed as the oracle — e.g. differentially testing an SoC with a complex interrupt controller or PCI bus against Linux-booted behavior.
14 Conformance RISCOF + riscv-arch-test hand-rolled suite Official architectural conformance methodology. Hand-rolled suite wins for a custom or proprietary ISA where no official conformance framework exists, or in early prototyping before the RISCOF plugin infrastructure is worth the setup cost.
15 Directed ISA tests riscv-tests (rv32ui) custom only Canonical self-checking ISA suite. Custom-only wins when targeting a strict subset or extension not covered by riscv-tests (e.g. a vendor-specific SIMD extension) where every test must reflect exact microarchitectural behavior.
16 Formal SymbiYosys + riscv-formal hand-written SVA only Proves ISA compliance via BMC; standard RV harness. Hand-written SVA only wins when the design has no RVFI interface and retrofitting it is impractical — e.g. a legacy closed-source core being post-hoc audited — or when bespoke liveness/safety properties go beyond the riscv-formal check set.
17 Build/orchestration Make + Python (+ optional FuseSoC) bare shell, vendor projects Portable, CI-friendly; FuseSoC optional for packaging. FuseSoC wins when managing a large IP library with versioned, multi-vendor cores that need reproducible dependency resolution across teams — the overhead pays off at > ~10 IPs.
18 Lint Verilator --lint-only + Verible lint none Catch width/latch/comb-loop issues early. A "none" policy only wins (temporarily) in the very first hours of a prototype where iteration speed matters more than correctness; production projects always benefit from lint.
19 Format Verible format manual Consistent RTL style. Manual wins when the team has a legacy style enforced by a different formatter (e.g. a project-specific vim/emacs hook) that conflicts with Verible's defaults, or when Verible does not yet support a needed SV construct.
20 CI/CD GitHub Actions (build/lint/sim/formal/synth) self-hosted only Reproducible gates; nightly formal/long sim. Self-hosted wins when jobs require physical FPGA boards (hardware-in-the-loop), GPU-accelerated simulation, or large on-premise EDA tool licenses that cannot run on hosted GitHub runners.
21 Memory init $readmemh (sim) / bitstream pack (FPGA) bootloader-only Simple deterministic preload; bootloader is #152/later. Bootloader-only wins when the program must be updateable in the field without re-programming the bitstream — e.g. a deployed embedded product with firmware OTA updates via UART or SPI flash.
22 Bus Wishbone B4 (classic → pipelined) AXI4-Lite, custom Lightweight, open, FPGA-friendly. AXI4-Lite wins when the SoC must interface with Xilinx/Intel vendor IPs (DDR controller, PCIe root complex, Ethernet MAC) that exclusively expose AXI4 ports, making a Wishbone bridge a liability.
23 (Bus rejected) — AXI4-Lite More signals/handshake complexity, vendor-IP-oriented; overkill for a teaching SoC; documented for portability. AXI4-Lite wins in any ARM Cortex-M ecosystem SoC where CoreLink interconnect IPs and vendor subsystems are AXI-native; the signaling complexity is amortized by reusing vendor VIP.
24 Reset Synchronous, active-high internal async reset Avoids reset-recovery/CDC issues; cleaner timing. Async reset wins in ASIC flows where power gating requires instant reset assertion independent of the clock (clock may be off), or when a power-down domain needs immediate state clearing before the clock restores.
25 Clocking Single domain + PLL; 2-flop sync for UART RX multi-clock Simplicity; one CDC point only. Multi-clock wins when peripherals run at intrinsically different rates that cannot be PLL-combined — e.g. a USB 48 MHz PHY plus a 100 MHz core — requiring a full CDC crossing and FIFO per domain boundary.
26 Multiplier (M-ext) DSP-inferred (MULT18/MAC16); multi-cycle divider fully combinational mul/div Fits fabric, closes timing; comb divider blows the critical path. Fully combinational mul/div wins on small ASIC nodes (180 nm and below) where combinational area is cheap and latency tolerance is zero — e.g. a hard-macro ALU in a single-cycle microcontroller at low Fmax.
27 Versioning / release semver tags, signed; CHANGELOG ad-hoc Stable RTL/IP contract. Ad-hoc versioning is acceptable only for a single-person prototype that will never be integrated as an IP block; any SoC integration or IP reuse requires the semver contract.
28 Coverage Verilator coverage (line/toggle) + functional none Closes verification gaps. None only makes sense for a 30-line combinational module with exhaustive formal proof; any RTL with stateful paths and corner-case sequences needs coverage to find blind spots in the directed test suite.
29 Reproducibility Pinned tool versions (Docker), seeded RNG floating Bit-for-bit replay of sim + synth. Floating tool versions win in the very earliest exploration phase where cutting-edge nightly Verilator/Yosys features are needed and re-running a specific failure is tolerated — temporary until any CI gate is established.
30 Licensing Apache-2.0 OR MIT (RTL) GPL for RTL Permissive, IP-reuse-friendly. GPL wins when the project's explicit goal is copyleft propagation — ensuring any product that incorporates the RTL must open-source its full design — common in academic or activist open-hardware contexts.

11.1 Global package (rv_pkg)

package rv_pkg;
  parameter int XLEN = 32;
  parameter logic [31:0] RESET_VECTOR = 32'h0000_0000;
  typedef enum logic [6:0] { OP_R=7'h33, OP_I=7'h13, OP_LOAD=7'h03, OP_S=7'h23,
    OP_B=7'h63, OP_JAL=7'h6F, OP_JALR=7'h67, OP_LUI=7'h37, OP_AUIPC=7'h17,
    OP_SYSTEM=7'h73, OP_FENCE=7'h0F } opcode_e;
  typedef enum logic [3:0] { ALU_ADD, ALU_SUB, ALU_SLL, ALU_SLT, ALU_SLTU,
    ALU_XOR, ALU_SRL, ALU_SRA, ALU_OR, ALU_AND, ALU_PASS_B /*LUI*/ } alu_op_e;
  typedef enum logic [2:0] { IMM_I, IMM_S, IMM_B, IMM_U, IMM_J, IMM_NONE } imm_sel_e;
  typedef enum logic [1:0] { WB_ALU, WB_MEM, WB_PC4, WB_CSR } wb_sel_e;
  typedef enum logic [2:0] { BR_NONE, BR_EQ, BR_NE, BR_LT, BR_GE, BR_LTU, BR_GEU, BR_JAL } br_e;
  parameter logic [3:0] CAUSE_IADDR_MISALIGN=0, CAUSE_ILLEGAL=2, CAUSE_EBREAK=3,
    CAUSE_LADDR_MISALIGN=4, CAUSE_SADDR_MISALIGN=6, CAUSE_ECALL_M=11, CAUSE_MTIMER_IRQ=7;
endpackage
// Compatibility: enum encodings frozen at v1; new ALU ops appended, never renumbered.

11.2 Decoded control bundle (ctrl_t)

typedef struct packed {
  rv_pkg::alu_op_e   alu_op;
  logic              alu_src_imm;   // 1 => second ALU operand = immediate
  logic              alu_src_pc;    // 1 => first operand = PC (AUIPC/branch target)
  rv_pkg::imm_sel_e  imm_sel;
  logic              mem_read, mem_write;
  logic [2:0]        mem_funct3;    // size + sign for load/store
  logic              reg_write;
  rv_pkg::wb_sel_e   wb_sel;
  rv_pkg::br_e       branch;
  logic              jump;          // JAL/JALR
  logic              csr_en;
  logic [2:0]        csr_op;        // RW/RS/RC (+imm variants)
  logic              is_mret, is_ecall, is_ebreak, illegal;
} ctrl_t;
// Ownership: produced by decoder, flows ID->EX->MEM->WB in pipe regs. Pure data, no state.
// Mutation: immutable once decoded. Concurrency: per-instruction copy in each pipe reg.

11.3 Pipeline registers (pipereg, stage structs)

typedef struct packed { logic [31:0] pc, pc4, insn; logic valid; } ifid_t;   // valid=0 => bubble
typedef struct packed { logic [31:0] pc, pc4, rs1_val, rs2_val, imm;
  logic [4:0] rs1, rs2, rd; ctrl_t ctrl; logic valid; } idex_t;
typedef struct packed { logic [31:0] pc4, alu_result, rs2_val; // rs2 for store data
  logic [4:0] rd; ctrl_t ctrl; logic valid; } exmem_t;
typedef struct packed { logic [31:0] pc4, alu_result, mem_data, csr_data;
  logic [4:0] rd; ctrl_t ctrl; logic valid; } memwb_t;

module pipereg #(parameter type T=logic) (
  input logic clk, rst, stall, flush, input T d, output T q);
// Contract: flush -> q.valid=0 (bubble); stall -> hold q; else q<=d (NBA).
// flush has priority over stall. Reset -> q=0/invalid.
endmodule

11.4 Datapath leaf modules

module regfile (input logic clk, we, input logic [4:0] ra1, ra2, wa,
  input logic [31:0] wd, output logic [31:0] rd1, rd2);
// rd1/rd2 combinational; write on posedge if we & wa!=0. x0: read=0, write ignored.
// Write-first bypass: if (we & wa==raN) rdN=wd. Single write port (single-writer invariant).

module alu (input rv_pkg::alu_op_e op, input logic [31:0] a, b,
  output logic [31:0] y, output logic zero);
// Pure comb. SLL/SRL/SRA shift by b[4:0]. SLT/SLTU set 0/1. zero=(y==0).

module imm_gen (input logic [31:0] insn, input rv_pkg::imm_sel_e sel, output logic [31:0] imm);
// Pure comb sign-extension per §8.3. IMM_NONE => 0.

module decoder (input logic [31:0] insn, output ctrl_t ctrl, output logic [4:0] rs1, rs2, rd);
// Pure comb. ctrl.illegal=1 for any unmapped opcode/funct. rd/rs from fixed fields.

module branch_unit (input rv_pkg::br_e br, input logic [31:0] a, b, pc, imm, rs1,
  output logic taken, output logic [31:0] target);
// Comb. target = (JALR)?(rs1+imm)&~1 : pc+imm. taken per compare. JAL/JALR => taken=1.

module hazard (input idex_t idex, input exmem_t exmem, input memwb_t memwb,
  input logic [4:0] ifid_rs1, ifid_rs2, input logic branch_taken, trap, mret,
  output logic [1:0] fwd_a, fwd_b,  // 00=regfile,01=EX/MEM,10=MEM/WB
  output logic stall_pc, stall_ifid, flush_ifid, flush_idex, flush_exmem);
// Comb. Single source of truth (Design Principle 5, §8.6). One-hot fwd asserted via SVA.

11.5 CSR file (csr_file)

module csr_file (input logic clk, rst,
  input logic csr_en, input logic [11:0] csr_addr, input logic [2:0] csr_op,
  input logic [31:0] csr_wdata, output logic [31:0] csr_rdata, output logic csr_illegal,
  input logic trap, mret, input logic [31:0] trap_pc, trap_tval, cause,
  output logic [31:0] mtvec_o, mepc_o, output logic trap_taken,
  input logic timer_irq, soft_irq, ext_irq, output logic irq_pending,
  input logic instr_retire);
// State: mstatus,mtvec,mepc,mcause,mtval,mie,mip,mscratch,mcycle,minstret (architectural).
// trap latches mepc=trap_pc, mcause=cause, mtval=trap_tval, mstatus.MPIE<=MIE, MIE<=0,
//   trap_taken=1, redirect=mtvec. mret: MIE<=MPIE, redirect=mepc. Precise (Invariant 6).
// irq_pending = |(mip & mie) & mstatus.MIE. mcycle++ /cycle; minstret++ /retire.

11.6 Wishbone interface + fabric (wb_if, wb_fabric)

interface wb_if #(parameter AW=32, DW=32) (input logic clk, rst);
  logic [AW-1:0] adr; logic [DW-1:0] dat_m, dat_s; logic we, stb, cyc, ack, err;
  logic [DW/8-1:0] sel;
  modport master (output adr,dat_m,we,sel,stb,cyc, input dat_s,ack,err, input clk,rst);
  modport slave  (input adr,dat_m,we,sel,stb,cyc, output dat_s,ack,err, input clk,rst);
endinterface
// Contract (Invariant 8): every (cyc&stb) -> ack|err; classic handshake first,
//   pipelined later. sel = byte enables for sub-word access.

module wb_fabric (wb_if.slave imaster, dmaster /*from core*/,
  wb_if.master imem, dmem, uart, timer, gpio);
// Decode by rv_pkg mem map (§8.9). Split I/D => no arbitration; shared => priority/round-robin.
// err on unmapped address (-> access fault). One master per slave at a time.

module bram #(parameter SIZE=65536, INIT="") (input logic clk, wb_if.slave wb);

module uart #(parameter CLK_HZ=12_000_000) (input logic clk, rst, wb_if.slave wb,

module timer (input logic clk, rst, wb_if.slave wb, output logic mtip);

typedef struct packed {

13. Phase 1 — Single-cycle RV32I golden reference core (core_sc)

13.1 Objectives

  • Implement core_sc: a combinational-datapath single-cycle RV32I core executing one instruction per clock — the golden simplicity model and the behavioral oracle for the pipeline.
  • All RV32I base instructions (R/I/S/B/U/J) functional; split (Harvard) BRAM for I and D; no CSRs/traps yet (illegal/ecall → halt marker).

13.2 Detailed Implementation Steps

  • core_sc.sv: PC reg; instruction fetch from ibus; decode (inline or via decoder, Phase 2); regfile read; ALU (Phase 2 leaf or inline); branch compare; data access on dbus; writeback mux; pc_next = PC+4 / branch target / jump target. (P&H §4.1 single-cycle datapath; Harris & Harris Ch 7; RISC-V Unprivileged ISA Paper #1)
  • Datapath leaves used inline first, then swapped to the normative §11.4 modules in Phase 2 (keep behavior identical). (ADR-2 golden reference rationale)
  • Memory: synchronous BRAM read (1-cycle) tolerated by stretching the single-cycle clock model, or async-read sim BRAM for the pure single-cycle reference; document the choice. (ADR-21 memory init; §4.5 determinism contract)
  • Halt protocol: a known instruction (ebreak or a magic store to tohost) latches halted; tb stops + dumps regfile. (riscv-tests tohost/fromhost convention Ref-impl #7)
  • Observability: $display retire trace (pc insn rd=val) gated by a +trace plusarg; regfile dump on halt. (Bergeron Book #9 self-checking TB)
  • Harness: hand-written .S fixtures (one per opcode class) that compute a known value and store it to tohost. (ADR-15; RISC-V Unprivileged ISA Paper #1)

13.3 Deliverable

  • core_sc runs small assembly programs to completion and produces correct architectural state; the retire trace matches hand-computed expectations.

13.4 Acceptance Criteria

  • All R/I/S/B/U/J opcode-class fixtures produce the expected tohost value.
  • x0 reads as 0 after any write attempt; PC alignment respected.
  • Retire trace is deterministic across sims.

13.5 Conformance Fixtures

  • verif/sc/op_*.S + .expected — one per opcode class (add/sub/and…, lw/sw, beq/bne/blt…, lui/auipc, jal/jalr).
  • verif/sc/x0_write.S — write to x0, assert still 0.
  • Malformed: an unaligned jalr target → defined behavior (clear low bit per spec).

13.6 Pitfalls

  • JALR low-bit clear — spec mandates target = (rs1+imm) & ~1; forgetting it mis-jumps; signal: odd PC.
  • Branch offset shift / B-imm assembly — B/J immediates are scrambled in encoding; a wrong imm_gen mis-targets every branch; cross-check vs objdump.
  • Sign vs zero extension on loads — lb/lbu confusion corrupts byte loads; fixture each width × signedness.
  • Async vs sync BRAM in single-cycle — a sync read needs the value the same cycle in pure single-cycle; mismatch reads stale data; document + assert.

13.7 Performance Concerns

  • Single-cycle Fmax is low (long combinational path through mem+ALU+regfile) — acceptable; this core is a reference, not the synthesis target. No pipelining here.

13.8 Edge Cases

  • auipc/lui immediate placement; jal with max-range offset; load/store at the top BRAM address; back-to-back dependent ops (trivially correct in single-cycle).

13.9 Failure Analysis

  • A golden-model bug poisons every later differential test. Detection: hand-computed fixtures + later Spike cross-check. Blast radius: all verification. Recovery: fix + re-baseline. Forensic: retire trace diff vs objdump expectation.

13.10 Operational Notes

  • core_sc is the in-tree oracle until Spike lands (Phase 8); keep it bit-exact to the spec, never "optimized." The tohost halt + regfile-dump convention is reused by every later test harness.

14. Phase 2 — Normative datapath leaves: regfile / alu / imm_gen / decoder

14.1 Objectives

  • Factor the inline single-cycle datapath into the four normative, reusable modules consumed by both cores; freeze their interfaces so core_sc and core_p5 share identical combinational semantics.

14.2 Detailed Implementation Steps

  • regfile.sv: 32×32, 2 read ports / 1 write port, x0 hardwired 0; write-first vs read-first behavior documented (write-first for pipeline forwarding-through-regfile in WB→ID same-cycle, or rely on EX/MEM forwarding — pick + assert). (P&H §4.4 register file; Design Principle 8 x0-zero invariant; §7 Invariant 1)
  • alu.sv: alu_op_e → result; ADD/SUB/AND/OR/XOR/SLT/SLTU/SLL/SRL/SRA; shift amount = [4:0]; SLT signed vs SLTU unsigned. (RISC-V Unprivileged ISA Paper #1 §2; Harris & Harris Ch 7.3)
  • imm_gen.sv: I/S/B/U/J immediate extraction + sign-extension exactly per §8.3; one combinational block selected by opcode. (RISC-V Unprivileged ISA Paper #1 §2.3 immediate encoding)
  • decoder.sv: instruction → ctrl_t (§11.2): regfile write enable, ALU op, ALU src selects, mem read/write + width/sign, branch/jump kind, CSR/illegal flags. (Harris & Harris Ch 7.4; ADR-1 SV enum typing)
  • Swap core_sc to instantiate these; assert identical fixture results pre/post refactor (regression gate). (ADR-2; Design Principle 1 correctness-first)
  • SVA: x0-is-zero assertion in regfile; one-hot control assertions in decoder. (Bergeron Book #9 SVA; Design Principle 10)
  • Harness: directed leaf tests (ALU truth tables, imm_gen vs objdump immediates, decoder vs a golden control table CSV). (ADR-15; Cummings SNUG Book #6)

14.3 Deliverable

  • Four standalone modules + a refactored core_sc that passes all Phase-1 fixtures unchanged; leaf-level unit tests pass.

14.4 Acceptance Criteria

  • ALU matches a reference truth table over directed + random operands; shifts mask to [4:0].
  • imm_gen matches objdump immediates for every format across a fixture program.
  • decoder matches the golden ctrl_t table for all RV32I opcodes; illegal opcodes flagged.

14.5 Conformance Fixtures

  • verif/leaf/alu.csv — (op,a,b) → result.
  • verif/leaf/imm.csv — (insn) → immediate per format.
  • verif/leaf/decode.csv — (insn) → expected ctrl_t fields.
  • Malformed: reserved funct7/funct3 combos → illegal=1.

14.6 Pitfalls

  • SRA arithmetic shift — using >> instead of >>> on a signed operand zero-fills; signal: wrong sign on sra.
  • Regfile write-first/read-first mismatch — wrong choice breaks WB→ID forwarding later; decide now, assert, document.
  • Decoder default/illegal fall-through — an unlisted opcode silently doing something; force illegal=1 default.
  • Shift-amount width — using full rs2 instead of [4:0] shifts wrong; mask explicitly.

14.7 Performance Concerns

  • These leaves sit on the critical path; keep the ALU a single level of muxing, imm_gen parallel selects. Decoder is pure comb — fine. Regfile maps to LUT-RAM/FF; 2R/1W may need a duplicated array or BRAM — note for Phase 11 timing.

14.8 Edge Cases

  • slt/sltu boundary (signed −1 vs unsigned max); shift by 0 and by 31; immediate at min/max sign-extension; decode of fence/fence.i (NOP-ish here, defined).

14.9 Failure Analysis

  • Leaf bugs corrupt both cores. Detection: leaf unit tests + the Phase-1 regression. Blast radius: all execution. Recovery: fix leaf, re-run. Forensic: failing CSV row + waveform.

14.10 Operational Notes

  • These modules are the normative contract reused by core_p5; freeze interfaces (CHANGELOG). The golden ctrl_t table is the decode spec of record for reviewers.

15. Phase 3 — 5-stage in-order pipeline (core_p5) + forwarding + load-use stall

15.1 Objectives

  • Build core_p5: IF → ID → EX → MEM → WB with the §11.3 pipeline registers, reusing the Phase-2 leaves; add the hazard unit (EX→EX, MEM→EX forwarding) and the load-use stall. Branches handled minimally (resolve + flush, refined in Phase 4).
  • Establish the RVFI retire emission at WB so the differential/formal harnesses have their contract.

15.2 Detailed Implementation Steps

  • core_p5.sv: instantiate stage regs (if_id, id_ex, ex_mem, mem_wb); thread ctrl_t + operands through; WB writeback to regfile. (P&H ch. 4.8 pipelined datapath; §11.3 pipeline registers; ADR-3)
  • hazard.sv: forwarding muxes — compare id_ex.rs1/rs2 against ex_mem.rd / mem_wb.rd (with rd!=0 + write-enable); select forwarded value into EX. Load-use: if id_ex is a load and its rd matches the next instr's source in ID → stall 1 cycle (bubble into EX, freeze IF/ID + PC). (P&H ch. 4.8 forwarding unit; §8.6 hazard table; Design Principle 6)
  • Stall/flush plumbing: stall_if, stall_id, flush_id_ex control signals; bubble = inject NOP ctrl_t. (P&H ch. 4.8.3; Design Principle 5 single hazard-unit truth)
  • RVFI: assemble rvfi_t (§11.9) at WB commit — one valid retire per committed instruction, in program order. (Wolf riscv-formal Paper #4; §11.9 RVFI contract)
  • SVA: no double-write to the same rd in a cycle; PC monotonic except on redirect; a forwarded value equals the eventual regfile value (formalizable later). (Bergeron Book #9; §7 Invariant 10)
  • Harness: dependency-chain fixtures (back-to-back ALU deps, load-then-use, the classic forwarding hazard patterns); compare final state vs core_sc. (ADR-2 golden reference; ADR-13)

15.3 Deliverable

  • core_p5 executes RV32I correctly with forwarding + load-use stall; final architectural state matches core_sc on all Phase-1/2 fixtures; RVFI trace emitted.

15.4 Acceptance Criteria

  • All single-cycle fixtures pass on core_p5; state bit-identical to core_sc.
  • Load-use hazard inserts exactly one bubble (verified by cycle count + waveform).
  • Forwarding eliminates stalls for ALU-ALU dependencies (no bubble where forwarding suffices).
  • RVFI emits exactly one valid retire per instruction, in order.

15.5 Conformance Fixtures

  • verif/p5/fwd_exex.S, fwd_memex.S, load_use.S — hazard patterns + expected cycle/bubble counts.
  • verif/p5/state_equiv.S — long mixed program; assert state == core_sc.
  • Malformed: a chain that looks like a hazard but writes x0 (no forward needed) — assert no spurious stall.

15.6 Pitfalls

  • Forwarding from an x0 write — forwarding a write-to-x0 injects a wrong 0/value; gate forwards on rd!=0.
  • Load-use detected one stage too late — must detect in ID against the load in EX; detecting in EX is too late → wrong data; signal: corrupted load result.
  • Stall vs flush priority — simultaneous stall (load-use) + flush (branch) must resolve deterministically; define precedence.
  • Forward source precedence (EX/MEM over MEM/WB) — newer result must win; wrong priority forwards stale data.
  • Regfile write/read same cycle (WB→ID) — depends on the Phase-2 write-first decision; mismatch needs an extra forward path.

15.7 Performance Concerns

  • Forwarding muxes add EX-stage delay (critical path candidate — flag for Phase 11). Load-use stall costs 1 cycle/occurrence → measured in IPC (Phase 13). Keep bubble injection cheap (control-signal clear, not data shuffling).

15.8 Edge Cases

  • Dependent on the instruction two ahead (MEM→EX forward); triple back-to-back dependents; load feeding a store address vs store data (different stages); a stall coincident with a redirect.

15.9 Failure Analysis

  • Forwarding/stall bugs cause silent data corruption (not crashes). Detection: state-equivalence vs core_sc + RVFI + (later) formal. Blast radius: any data-dependent program. Recovery: fix hazard logic; regression. Forensic: RVFI diff + waveform at the divergent retire.

15.10 Operational Notes

  • RVFI is now the single verification contract; keep its emission exactly at commit. The core_sc-equivalence harness is the primary pipeline regression for every later change.

16. Phase 4 — Branch / jump resolution + flush + predictor seam

16.1 Objectives

  • Resolve branches/jumps in EX, flush the wrongly-fetched IF/ID instructions, and redirect the PC; default static not-taken with a clean seam for a later simple predictor (BHT). Establish the branch penalty as a measured quantity.

16.2 Detailed Implementation Steps

  • branch_unit.sv: evaluate the branch condition (BEQ/BNE/BLT/BGE/BLTU/BGEU) on the EX operands; compute taken target; for JAL/JALR compute target + link. (P&H ch. 4.8.4 branch resolve; RISC-V Unprivileged ISA Paper #1 §2.5 branch encoding)
  • Redirect: on taken/mispredicted branch or jump, set pc_redirect + redirect_target, flush IF/ID + ID/EX bubbles already in flight (kill 2 fetched instrs for EX-resolve). (P&H ch. 4.8 control hazard; §8.5 worked example; Design Principle 4)
  • Predictor seam: a predict_taken/predict_target interface defaulting to not-taken (constant 0); a bht module stub (direction table, gshare-ready) gated PhaseDeferred — wiring present, logic minimal. (H&P App C branch prediction; ADR-3 predictor-seam rationale; cross-link #189)
  • Account branch penalty: counters for branches, taken, mispredict, flush_cycles. (§4.2 CPI model; Scalability Analysis branch-flush bottleneck)
  • SVA: after a redirect, the next committed PC equals the redirect target; no instruction past a taken branch commits. (Wolf riscv-formal Paper #4 pc_fwd check; §7 Invariant 4)
  • Harness: branch-heavy fixtures (loops, nested branches, JALR through a table); compare state vs core_sc; assert flush counts. (ADR-2 golden reference; ADR-15)

16.3 Deliverable

  • Correct control flow with EX-stage branch resolution + flush; measured branch penalty; predictor seam present (not-taken default). State matches core_sc on branch/loop programs.

16.4 Acceptance Criteria

  • All branch/jump fixtures match core_sc state.
  • Taken branch flushes exactly the 2 instructions fetched after it (cycle-accurate, 2-cycle penalty per §4.2).
  • JALR target masks bit 0 to 0; link register correct.
  • Mispredict counters increment correctly under a not-taken predictor.

16.5 Conformance Fixtures

  • verif/p5/branch_*.S — each condition taken + not-taken.
  • verif/p5/loop.S — counted loop; assert iteration count + flush count.
  • verif/p5/jalr_table.S — computed-goto.
  • Malformed: branch to an unaligned target → defined trap-or-mask behavior documented.

16.6 Pitfalls

  • Off-by-one flush count — flushing too few leaves a wrong instruction committing; too many drops a valid one; verify cycle-exact.
  • JALR using stale rs1 (no forward) — JALR target depends on a forwarded reg; missing forward jumps wrong.
  • Redirect vs load-use stall same cycle — precedence must kill the right instructions; define + assert.
  • Predictor seam accidentally active — a half-wired BHT mispredicting silently; keep default provably not-taken until Phase 13.
  • Link value (PC+4) computed from the wrong stage PC — corrupts ra; pin to the branch's own PC.

16.7 Performance Concerns

  • EX-resolve = 2-cycle penalty per taken branch → the dominant IPC loss on branchy code (quantify in Phase 13). The predictor seam exists precisely to recover this later. Branch compare adds EX delay.

16.8 Edge Cases

  • Branch in the delay shadow of another branch; a loop whose backedge is the last BRAM word; JALR to address 0; maximum-range forward/backward branch offsets.

16.9 Failure Analysis

  • Control bugs cause wrong-path execution (often silent until a data check). Detection: state-equiv + flush counters + formal. Blast radius: all control flow. Recovery: fix branch_unit/redirect; regression. Forensic: RVFI PC stream vs golden.

16.10 Operational Notes

  • mispredict_rate + flush_cycles are the headline branch metrics. The predictor seam is the documented extension point for #189; keep its default neutral. Cross-link Phase 13 for predictor enablement.

17. Phase 5 — Memory subsystem: BRAM + Wishbone B4 fabric + decoder

17.1 Objectives

  • Replace ad-hoc memory with a real subsystem: synchronous bram (I + D), a wb_fabric Wishbone B4 interconnect (classic, then pipelined), and an address decoder routing to BRAM + a peripheral region. Adapt the pipeline MEM stage to bus handshake (stall on no-ack).

17.2 Detailed Implementation Steps

  • bram.sv: synchronous 1-cycle read, byte-enable writes (sel), parameterized depth; init via $readmemh. (ADR-21 memory init; §4.1 XLEN/address space; Chu Book #5 BRAM patterns)
  • wb_if/wb_fabric.sv: classic Wishbone B4 (cyc/stb/ack), single-master (core) → multi-slave; decoder maps the address map (§8.9) to slave selects; mux read data + ack/err back. (Wishbone B4 spec Paper #12; ADR-22; §11.6)
  • MEM-stage adaptation: a load/store asserts cyc/stb; the pipeline stalls (freeze IF..MEM) until ack; err → bus-fault (feeds Phase-7 trap). (P&H ch. 4.8 structural hazard; §7 Invariant 8; ADR-24 sync reset)
  • Pipelined Wishbone variant: allow outstanding requests; gate behind a parameter; default classic for simplicity. (Wishbone B4 spec Paper #12 §4 pipelined; Deferred Features Register)
  • Misalignment: detect unaligned word/half accesses → flag for trap (Phase 7) or handle per policy. (RISC-V Privileged ISA Paper #2 §3.1.15; §8.8 trap causes)
  • SVA: Wishbone protocol assertions (stb implies cyc; ack only when stb; no ack without a request); single outstanding in classic mode. (Bergeron Book #9; §7 Invariant 8)
  • Harness: a Wishbone bus-functional checker; memory tests (word/half/byte, aligned + unaligned); back-to-back load/store. (ADR-15; Chu Book #5)

17.3 Deliverable

  • Core executes from BRAM over Wishbone; loads/stores of all widths work; the fabric routes by address; protocol assertions hold. State matches core_sc (now also bus-driven).

17.4 Acceptance Criteria

  • All 8 width/sign load-store fixtures (LB/LH/LW/LBU/LHU + SB/SH/SW) pass over the bus; byte-enables correct.
  • Wishbone protocol assertions pass under directed + random bus traffic (0 protocol violations).
  • Pipeline stalls exactly while awaiting ack; resumes correctly (no lost/duplicated access).
  • Address decode routes BRAM vs peripheral region correctly across the 5-region map (§8.9); out-of-map → err.

17.5 Conformance Fixtures

  • verif/mem/ldst_widths.S — lw/lh/lhu/lb/lbu/sw/sh/sb round-trips.
  • verif/mem/wb_protocol.json — bus traces → assertion pass/fail.
  • verif/mem/decode_map.json — address → expected slave select.
  • Malformed: unaligned access, out-of-range address → err/trap.

17.6 Pitfalls

  • Byte-enable (sel) for sub-word stores — wrong sel corrupts neighbor bytes; map width+offset → sel carefully.
  • Stall while awaiting ack lets a younger instr advance — must freeze the whole front; signal: duplicated memory effects.
  • Combinational ack loop — slave ack combinationally fed from stb can create a path/loop; register appropriately.
  • Endianness of $readmemh vs byte addressing — image byte order mismatch reads garbage; pin little-endian convention + test.
  • Single-outstanding violated in classic mode — issuing a second stb before ack breaks classic slaves; assert.

17.7 Performance Concerns

  • Synchronous BRAM read adds a MEM-stage cycle (already in the 5-stage model). Classic Wishbone is 1 access at a time → memory-bound loops stall; the pipelined variant + (deferred) caches recover throughput. Bus mux depth affects timing (Phase 11).

17.8 Edge Cases

  • Store then load same address back-to-back (RAW through memory); access at the exact map boundary; unaligned at a region edge; zero-length / no sel write (defined no-op).

17.9 Failure Analysis

  • Bus/memory bugs corrupt data or deadlock the pipeline (stuck awaiting ack). Detection: protocol assertions + ldst fixtures + a bus watchdog. Blast radius: every memory op. Recovery: fix fabric/handshake; regression. Forensic: bus trace (cyc/stb/ack/adr) + the stall-cycle log.

17.10 Operational Notes

  • The memory map (§8.9) is the SoC contract; document base addresses. A bus watchdog (timeout → err) is the deadlock safety net. Cross-link #187 (caches) and Phase-5 DRAM PhaseDeferred.

18. Phase 6 — Peripherals: UART + mtime/mtimecmp timer + GPIO

18.1 Objectives

  • Add memory-mapped peripherals over the fabric: a uart (TX/RX, programmable baud divisor), the timer (mtime/mtimecmp 64-bit machine timer driving a timer interrupt), and gpio. This makes the SoC observable (console) and blinkable, and provides the timer-interrupt source for Phase 7.

18.2 Detailed Implementation Steps

  • uart.sv: TX shift-out at baud = clk/divisor; RX oversample (16×) start-bit detect + sample; FIFO-less or small FIFO; status (TX-ready, RX-valid) + data registers; memory-mapped per §8.9. (Chu Book #5 UART chapter; ADR-25 CDC: 2-flop sync for RX; Cummings SNUG Book #6 CDC)
  • timer.sv: free-running mtime (64-bit, increments at a defined tick), mtimecmp; mtime >= mtimecmp → mtip (timer interrupt pending) into the CSR/trap logic (Phase 7 consumes it). (RISC-V Privileged ISA Paper #2 §3.2.1 mtime; §8.7 CSR map)
  • gpio.sv: output/input/direction registers; drives board LEDs/pins. (Chu Book #5 GPIO chapter; §8.9 memory map)
  • Wire all three as Wishbone slaves through wb_fabric/decoder. (ADR-22; Wishbone B4 spec Paper #12)
  • Bare-metal driver headers (uart.h, timer.h) in sw/ for test programs. (RISC-V ABI §5.4 normative spec; Design Principle 9 bus seam)
  • SVA: UART baud-divisor bit timing; mtime monotonic; mtip asserts exactly when mtime>=mtimecmp. (§7 Invariant 8; Bergeron Book #9)
  • Harness: UART loopback (TX→RX) in sim with a UART BFM; timer-fire fixture; GPIO write/read-back. (ADR-13 differential oracle for timer; ADR-15)

18.3 Deliverable

  • A SoC that prints over UART, ticks a 64-bit timer that raises mtip, and toggles GPIO — all via memory-mapped accesses from a C program. UART-hello runs in sim.

18.4 Acceptance Criteria

  • UART TX bytes match the BFM-decoded output at 115 200 baud (±2% tolerance, C5); RX captures injected bytes.
  • mtime increments at the specified rate; mtip asserts exactly when mtime >= mtimecmp; clearing mtimecmp deasserts within 1 cycle.
  • GPIO write reflects on outputs; input sampled correctly across all pins.

18.5 Conformance Fixtures

  • verif/periph/uart_loopback.S + BFM expected byte stream.
  • verif/periph/timer_fire.S — set mtimecmp, spin, assert mtip + handler entry (with Phase 7).
  • verif/periph/gpio_rw.json — register writes → pin states.
  • Malformed: UART access with a zero divisor (defined: minimum 1) ; write to a read-only status reg (ignored).

18.6 Pitfalls

  • UART baud rounding error — divisor truncation accumulates phase error over a byte → framing errors at high baud; compute divisor with rounding; signal: garbled chars.
  • RX metastability — sampling an async RX line without a 2-FF synchronizer → glitches; add synchronizers.
  • mtime read tearing (64-bit over 32-bit bus) — reading hi/lo non-atomically across a rollover gives a bogus time; read-lo-then-hi-then-recheck-lo pattern.
  • Timer tick rate vs clk — documenting mtime in clk cycles vs real time confuses software; pin + document the tick.
  • GPIO direction default — undriven inputs floating; define reset direction.

18.7 Performance Concerns

  • UART is slow (baud-limited) — never on a hot path; poll vs interrupt documented. Timer is cheap. Peripheral region behind the bus mux adds a little decode delay. Avoid busy-poll burning the bus where an interrupt suffices.

18.8 Edge Cases

  • mtime/mtimecmp rollover at 2^64; UART back-to-back bytes (TX-ready timing); RX overrun (no FIFO) → overrun flag; GPIO simultaneous read+write same cycle.

18.9 Failure Analysis

  • Peripheral bugs garble I/O or break interrupts. Detection: loopback + timer-fire + GPIO fixtures. Blast radius: console/timer-driven software. Recovery: fix the slave; regression. Forensic: UART byte trace, mtime/mtip waveform.

18.10 Operational Notes

  • UART is the primary bring-up console (Phase 11 prints "hello"); mtip is the preemption source for any future scheduler. Document baud, tick rate, and the register map as the SoC ABI. GPIO drives the blink liveness signal.

19. Phase 7 — CSRs + traps / interrupts (machine mode) + mret

19.1 Objectives

  • Add the csr_file (machine-mode CSRs §8.7) and full trap machinery: exception detection (illegal instr, misaligned, ecall/ebreak), interrupt taking (timer mtip, software, external), trap entry (save mepc/mcause/mtval, jump mtvec) and mret. The core can now run trap handlers.

19.2 Detailed Implementation Steps

  • csr_file.sv: CSR read/write via csrrw/csrrs/csrrc (+ imm variants); mstatus (MIE/MPIE/MPP), mtvec, mepc, mcause, mie, mip, mscratch, mtval; side effects on trap entry/mret. (RISC-V Privileged ISA Paper #2 §3.1; §8.7 CSR map; §11.5 module signature)
  • Trap controller: priority-ordered cause selection (interrupts vs exceptions, §8.8); on trap — mepc←pc, mcause←cause, mtval←faulting value, mstatus.MPIE←MIE, MIE←0, redirect to mtvec. On mret — MIE←MPIE, redirect to mepc. (Smith & Pleszkun Paper #11 precise interrupts; RISC-V Privileged ISA Paper #2 §3.1.6; §7 Invariant 6)
  • Interrupt wiring: mip.MTIP from timer, MSIP (software), MEIP (external/CLINT-lite); taken only when MIE + per-bit mie + globally enabled, at an instruction boundary. (RISC-V Privileged ISA Paper #2 §3.1.9; §8.8 trap causes; Design Principle 7)
  • Exceptions from earlier phases now route here: illegal-instruction (decoder), misaligned load/store/fetch (Phase 5), bus err. (§7 Invariant 12; RISC-V Privileged ISA Paper #2 §3.2)
  • SVA: exactly one trap taken per triggering event; mepc points at the right instruction (re-executable vs next); mret restores MIE precisely; CSR side-effects atomic. (Wolf riscv-formal Paper #4 CSR checks; §7 Invariant 7)
  • Harness: trap fixtures (ecall, illegal, misaligned, timer interrupt with a handler that increments a counter + mrets); compare against Spike's trap behavior (Phase 8). (ADR-13 Spike oracle; RISCOF Paper #10)

19.3 Deliverable

  • A machine-mode core that takes precise traps + interrupts, runs handlers via mtvec, and returns via mret; timer interrupts drive a handler. CSR semantics correct.

19.4 Acceptance Criteria

  • ecall/ebreak/illegal/misaligned each set the correct mcause/mepc/mtval and enter mtvec.
  • Timer interrupt taken at an instruction boundary when enabled; masked when MIE=0; handler runs + mret resumes correctly.
  • CSR read/write (incl. WARL fields) matches the spec; set/clear bit ops correct.
  • Traps are precise (no partial instruction effects committed).

19.5 Conformance Fixtures

  • verif/trap/ecall.S, illegal.S, misalign_ld.S, misalign_fetch.S — cause/mepc/mtval expected.
  • verif/trap/timer_irq.S — enable, fire, handle, count, return.
  • verif/csr/csr_rw.S — read/write/set/clear across all M-CSRs; WARL behavior.
  • Malformed: write to a read-only CSR (misa if RO), access a non-existent CSR → illegal-instruction trap.

19.6 Pitfalls

  • mepc off by one (re-execute vs skip) — ecall re-executing loops forever; the handler must advance mepc+4; faults re-execute; document per-cause policy.
  • Interrupt taken mid-instruction — taking an IRQ between pipeline stages commits partial state → imprecise trap; take only at a commit boundary.
  • mstatus MIE/MPIE stack on nested traps — wrong save/restore re-enables interrupts early → reentrancy bug; follow the spec stack exactly.
  • CSR set/clear with rs1=x0 — csrrs x0,... must not write (read-only side-effect rules); honor the zero-rs1 special cases.
  • mtval content per cause — wrong value (e.g. PC vs address) misleads the handler; tabulate per cause.

19.7 Performance Concerns

  • CSR ops are rare — not hot-path. Trap entry/exit add a redirect (flush) penalty like a branch. Interrupt latency = cycles from mip to handler entry; bound + document. The CSR file is small; keep it off the critical datapath.

19.8 Edge Cases

  • Interrupt + exception same cycle (priority); nested trap (trap inside a handler before re-enabling); mret with MPP set; an interrupt arriving exactly at a branch redirect; misaligned access that also has a pending interrupt.

19.9 Failure Analysis

  • Trap bugs cause hangs (wrong mepc), silent corruption (imprecise traps), or missed interrupts. Detection: trap fixtures + Spike differential on traps + formal. Blast radius: any handler-driven or interrupt-driven software. Recovery: fix CSR/trap logic; regression. Forensic: CSR + RVFI trace at the trap boundary.

19.10 Operational Notes

  • Interrupt latency + trap-cause distribution become observable counters. The CSR/trap contract is what an OS/RTOS port (future) depends on — freeze + document. Debug Module (JTAG) is PhaseDeferred (§19.10). Cross-link Phase 8 (Spike validates trap behavior).

20. Phase 8 — riscv-tests (rv32ui) + Spike differential lockstep

20.1 Objectives

  • Bring up the official riscv-tests rv32ui self-checking suite (green = ISA-correct on directed tests), then build a Spike differential harness running the same program in lockstep, comparing RVFI retire records against Spike's commit log to catch any divergence.

20.2 Detailed Implementation Steps

  • Build riscv-tests rv32ui (+ mi/si machine tests for traps) with the pinned toolchain + the project linker script; load via $readmemh; use the tohost/fromhost pass/fail protocol. (ADR-15; riscv-tests Ref-impl #7; ADR-12 toolchain)
  • Spike oracle: run Spike with --log-commits (or libspike via the differential harness); extract per-retire PC/insn/reg-write/mem-effect. (ADR-13; Spike Ref-impl #1; §4.4 differential oracle constraint)
  • Differential harness (verif/diff/): drive core_p5 in Verilator, capture RVFI per retire, step Spike one instruction, compare {pc, insn, rd, rd_val, mem_addr/data/mask}; first mismatch → dump both, fail. (ADR-5 Verilator primary sim; §11.9 rvfi_t; Design Principle 11 three-angle verification)
  • Synchronization: align on retire order (RVFI order); handle traps (both must trap with same cause/mepc). (RISC-V Privileged ISA Paper #2 trap model; §7 Invariant 2)
  • CI: run the full rv32ui suite + a differential run over a program corpus on every push. (ADR-20 CI/CD; ADR-29 reproducibility)
  • Harness extras: a corpus of small C + asm programs (sorts, CRC, string ops) for differential coverage beyond directed tests. (ADR-28 coverage; cocotb Book #10)

20.3 Deliverable

  • Green rv32ui suite; a Spike differential harness that runs arbitrary programs in lockstep and flags the first divergent retire; both wired into CI.

20.4 Acceptance Criteria

  • 100% rv32ui (and the chosen machine/trap tests) pass.
  • Differential harness reports zero divergence across the program corpus.
  • A deliberately injected RTL bug is caught by the differential harness (negative test) at the correct retire.

20.5 Conformance Fixtures

  • verif/diff/corpus/*.elf + Spike commit logs (golden).
  • verif/tests/rv32ui-*.hex — the official suite images.
  • verif/diff/inject_bug.patch — a known bug + the expected divergence point.
  • Malformed: a program that traps → both models must trap identically.

20.6 Pitfalls

  • Spike config mismatch — different reset PC / memory map / misa than the core → spurious divergence; align Spike's config to the SoC exactly.
  • Comparing mem effects on different timing — RVFI commits at WB; align to Spike's architectural commit, not bus timing.
  • tohost protocol differences — HTIF semantics; ensure the core's halt matches the test harness expectation.
  • Uninitialized memory/regs differ — both models must start from identical state (zeroed); else divergence on first read.
  • Trap-cause/mtval subtle mismatch — Spike's mtval policy must match the core's; reconcile per cause.

20.7 Performance Concerns

  • Differential lockstep is slow (Spike step + sim cycle + compare per retire); run a curated corpus in CI, the full sweep nightly. Verilator sim throughput is the limiter; batch + parallelize across programs.

20.8 Edge Cases

  • Programs that hit every trap cause; self-modifying-ish (fence.i) — defined; long-running loops (cap retire count); programs that exercise mtime (nondeterministic timer — pin/inject a deterministic time source for diff).

20.9 Failure Analysis

  • A divergence is a real ISA bug. Detection: the harness pinpoints the first mismatched retire. Blast radius: depends on the instruction. Recovery: fix RTL, re-baseline. Forensic: side-by-side RVFI vs Spike commit dump at the divergence.

20.10 Operational Notes

  • The differential harness is the highest-value regression — every RTL change re-runs it. Pin Spike's version + config in TOOLVERSIONS. Make the timer deterministic for differential runs (inject mtime). Cross-link Phase 10 (formal complements differential).

21. Phase 9 — RISCOF architectural conformance

21.1 Objectives

  • Pass the official RISCOF (riscv-arch-test) conformance flow: the core as DUT, Spike as the reference model, run the architectural test suite, and produce a signed conformance report — the standardized statement that the core implements RV32I (+ enabled extensions) per the ratified spec.

21.2 Detailed Implementation Steps

  • Write RISCOF plugins: a DUT plugin (compile arch-test, run on core_p5 via Verilator, dump the signature region) and the reference plugin (Spike). (RISCOF Paper #10; riscv-arch-test Ref-impl #8; ADR-14)
  • Configure config.ini (ISA string RV32I + Zicsr etc., platform spec, mtvec/memory layout) matching the SoC. (RISC-V Privileged ISA Paper #2 §3.1.1 misa; §8.9 memory map)
  • Signature protocol: the test writes results to a signature memory region; the harness dumps begin_signature..end_signature to a file; RISCOF diffs DUT vs reference signatures. (RISCOF Paper #10 signature protocol; ADR-13 Spike reference)
  • Run the suite; triage failures (often unimplemented optional behavior or config mismatch); iterate. (ADR-14; Design Principle 2 one ISA spec to the bit)
  • CI: a riscof run job producing the HTML/JUnit report as an artifact. (ADR-20; ADR-29 reproducibility)
  • Gate: enabled extensions only (RV32I now; M/Zicntr added in Phase 12 re-run). (§1.2 in-scope ISA; RISC-V Unprivileged ISA Paper #1)

21.3 Deliverable

  • A green RISCOF run for the enabled ISA, with an archived conformance report; the DUT + reference plugins committed and reproducible.

21.4 Acceptance Criteria

  • 100% of applicable arch-test signatures match the Spike reference.
  • The conformance report is reproducible in CI from a clean checkout.
  • ISA string in config.ini matches the core's actual misa/capabilities.

21.5 Conformance Fixtures

  • verif/riscof/config.ini, plugin dirs, the generated signature/*.sig files (golden via reference).
  • The RISCOF database of applicable tests for the ISA string.
  • Malformed: claiming an extension not implemented → tests fail (negative check that the ISA string is honest).

21.6 Pitfalls

  • Signature region placement — wrong begin/end_signature linkage dumps garbage → all-fail; align the linker symbols.
  • ISA-string overclaim — listing M before it exists → real failures; keep the string honest per phase.
  • Platform CSR mismatch — mtvec mode (direct vs vectored), reset PC, alignment must match the test environment.
  • Reference model version drift — Spike version must match the RISCOF-pinned reference; mismatched signatures look like DUT bugs.
  • fence/fence.i semantics — arch-tests may assert ordering; ensure the (simple) implementation satisfies the required visibility.

21.7 Performance Concerns

  • RISCOF runs many small programs through Verilator + Spike; parallelize across tests. Not a runtime concern — a CI-time one; cache compiled tests.

21.8 Edge Cases

  • Tests for misaligned behavior (implementation-defined → declare the choice); CSR WARL fields; counters (deferred to Phase 12 re-run); reserved-encoding handling.

21.9 Failure Analysis

  • A conformance failure is either a real spec gap or a config/honesty mismatch. Detection: per-test signature diff. Blast radius: the failing instruction class. Recovery: fix RTL or correct the (honest) ISA string/config. Forensic: signature diff + the failing test's disassembly.

21.10 Operational Notes

  • The conformance report is the portfolio-grade artifact ("passes riscv-arch-test"). Re-run after Phase 12 (M/Zicntr) with the updated ISA string. Keep plugins + config under version control as the conformance contract.

22. Phase 10 — riscv-formal SymbiYosys ISA proof

22.1 Objectives

  • Apply riscv-formal (RVFI-based, SymbiYosys/bounded-model-checking) to prove (within a bound) ISA-compliance properties — per-instruction correctness, register/PC consistency, causality, liveness — catching bugs differential testing can miss (rare corner states).

22.2 Detailed Implementation Steps

  • Wire the core's rvfi_t (§11.9) to the riscv-formal check harness (the RVFI wires it expects). (Wolf riscv-formal Paper #4; riscv-formal Ref-impl #6; §11.9 RVFI contract)
  • Configure checks.cfg: enable insn_* checks (per-opcode result correctness), reg, pc_fwd/pc_bwd, liveness, causal, unique (one retire per order), bounded depth. (Wolf riscv-formal Paper #4; RISC-V Unprivileged ISA Paper #1 normative encodings)
  • Run SymbiYosys (BMC + optionally k-induction) per check; triage counterexamples (waveform from the solver). (ADR-16; Bergeron Book #9 formal methodology)
  • Constrain inputs legally (bus model that always eventually acks, legal interrupt assertion) so liveness is provable. (§7 Invariant 8; Wishbone B4 spec Paper #12 liveness; Design Principle 11)
  • CI: a formal job running the check matrix (depth-bounded) on every push; deeper proofs nightly. (ADR-20; ADR-29)
  • Document any check that is bounded-only vs fully proven (k-induction). (H&P App C; ADR-16 formal rationale)

22.3 Deliverable

  • A passing riscv-formal check matrix for the enabled ISA at a documented bound; SymbiYosys configs committed; CI-integrated.

22.4 Acceptance Criteria

  • All enabled insn_*, reg, pc_*, liveness, causal, unique checks pass to a BMC depth ≥ 20 (M11).
  • A seeded RTL bug produces a formal counterexample (negative test) within the same depth-20 bound.
  • Liveness proven under the legal-input constraints (no spurious deadlock).

22.5 Conformance Fixtures

  • verif/formal/checks.cfg, per-check .sby files; solver logs/traces archived.
  • A seeded-bug branch + its expected counterexample trace.
  • Malformed: an over-constrained environment (vacuous proof) → a sanity cover check must still be reachable.

22.6 Pitfalls

  • Vacuous proofs from over-constraint — constraining inputs so tightly nothing happens "passes" everything; add cover properties to prove reachability.
  • RVFI not matching real commit — if RVFI lies about what committed, formal proves the wrong thing; assert RVFI consistency against actual regfile/mem writes.
  • Unbounded liveness without fairness — bus that never acks makes liveness fail; add fairness/eventual-ack assumptions.
  • Depth too shallow — a bug deeper than the BMC bound escapes; document the bound; use k-induction where feasible.
  • State explosion — large memories blow up the solver; abstract memory (riscv-formal's memory model) rather than the full BRAM.

22.7 Performance Concerns

  • Solver runtime grows with depth/state; abstract memory, bound depth, parallelize checks, run deep proofs nightly. Not a DUT runtime concern. Keep the formal-friendly core size modest (machine mode only helps).

22.8 Edge Cases

  • Interrupt arrival at every pipeline position; CSR side-effects under formal; misaligned/illegal in formal; forwarding corner states the solver finds that no test program reached.

22.9 Failure Analysis

  • A counterexample is a guaranteed bug (or a wrong assumption). Detection: SymbiYosys trace. Blast radius: the property's instruction class. Recovery: fix RTL or correct the (justified) assumption; re-prove. Forensic: the solver-produced waveform — the minimal failing trace.

22.10 Operational Notes

  • Formal + differential are complementary: differential covers realistic programs deeply, formal covers all inputs shallowly. Document proven-vs-bounded status per check. Re-run after Phase 12. This is the strongest correctness artifact in the project.

23.1 Objectives

23.2 Detailed Implementation Steps

  • Synthesis: yosys script (synth_ice40/synth_ecp5) reading the SoC; resolve any non-synthesizable constructs (sim-only $display, async-read mem); map regfile to LUT-RAM/BRAM appropriately. (ADR-8 Yosys; Sutherland Book #7 synthesizable subset; Design Principle 12)

  • PnR: nextpnr-ice40/nextpnr-ecp5 with the timing constraint; read the timing report for Fmax; iterate on the critical path (the EX forwarding/branch path flagged earlier). (Weste & Harris Book #8 critical-path analysis; ADR-9; §4.3 Fmax targets)
  • Bitstream: icepack/ecppack; program via iceprog/openFPGALoader. (ADR-10; iCE40/ECP5 fabric docs normative spec)

23.3 Deliverable

  • A bitstream that boots on iCE40 UP5K and ECP5, blinks an LED, and prints "hello" over UART; a timing report meeting the documented Fmax; an area report within budget.

23.4 Acceptance Criteria

  • Timing closes at ≥ the target Fmax (documented per board) with positive slack.
  • Area within budget (LUT/FF/BRAM/DSP under the §4.3 ceilings).
  • On-board blink + UART-hello observed (logic-analyzer/terminal capture).
  • Synth/PnR reproducible in CI; area/Fmax regressions flagged.

23.5 Conformance Fixtures

  • fpga/ice40/*.pcf, fpga/ecp5/*.lpf — pin/clock constraints.
  • fpga/reports/timing.expected — Fmax/slack thresholds (CI gate).
  • fpga/reports/area.expected — resource ceilings.
  • sw/helloblink.hex — the bring-up program image.
  • Malformed: an over-constrained clock (target above achievable Fmax) → PnR fails to close → documented expected failure.

23.6 Pitfalls

  • Non-synthesizable RTL slips through sim — initial/$display/async-read mem synth-fails or infers latches; lint for synthesizability; signal: Yosys warnings/latch inference.
  • Latch inference from incomplete case/if — missing default infers a latch → timing chaos; full case + default; assert no latches.
  • Critical path = forwarding/branch in EX — fails timing; mitigations: balance the path, register a stage, or accept lower Fmax; the flagged path from Phases 3–4.
  • Reset not synchronized — async reset release causes metastable startup; add a reset synchronizer.
  • BRAM init not carried to bitstream — $readmemh init may not synthesize identically; use the toolchain's BRAM-init path; verify the on-board program matches.
  • Clock constraint missing — PnR with no constraint "passes" but runs slow/unreliable; always constrain.

23.7 Performance Concerns

  • Fmax is set by the longest combinational path (EX forwarding + ALU + branch compare, or the bus mux). Area set by regfile (2R/1W duplication), BRAM, and the bus. Trade Fmax vs area vs IPC explicitly; this is the input to Phase 13.

23.8 Edge Cases

  • Maximum BRAM utilization (program fills it); UART at the board's max baud (timing margin); multiple LEDs/GPIO; the board's actual clock frequency vs the constraint; brown-out / power-on reset behavior.

23.9 Failure Analysis

  • Synthesis/timing/board bugs manifest only on fabric (passed sim). Detection: timing report + on-board observation (LA/scope) + a UART self-test. Blast radius: the physical build. Recovery: fix RTL/constraints, re-synth; if on-board only, capture with an LA + an on-chip RVFI-to-UART trace. Forensic: timing report, PnR log, LA capture.

23.10 Operational Notes

  • The timing + area reports are CI-gated regressions (no silent Fmax/area creep). Document the board(s), clock, baud, pinout as the deployment contract. Debug Module (JTAG/DMI) for on-board debugging is PhaseDeferred. Vendor (Vivado/Quartus) flow is PhaseDeferred. Cross-link Phase 13 (the timing report drives optimization).

24. Phase 12 — M extension (mul/div) + Zicsr/Zicntr counters

24.1 Objectives

  • Add the M extension (MUL/MULH/MULHU/MULHSU/DIV/DIVU/REM/REMU) and Zicntr base counters (cycle/instret via mcycle/minstret), update the ISA string, and re-run conformance/formal/differential with RV32IM_Zicsr_Zicntr enabled.

24.2 Detailed Implementation Steps

  • mul_div.sv: a multiplier (single-cycle DSP-mapped or multi-cycle iterative on iCE40 which lacks DSP) + an iterative (restoring/non-restoring) divider; multi-cycle ops stall EX until done (a busy/valid handshake into the hazard logic).   • Division-by-zero + overflow semantics per spec (DIV by 0 → −1/all-ones; REM by 0 → dividend; signed overflow INT_MIN/-1). (RISC-V Unprivileged ISA Paper #1, M extension, ch. 7.2; ADR-15 directed tests)
  • csr_file: implement mcycle/minstret (+ mcycleh/minstreth) counting; cycle/instret read mirrors; mcountinhibit. (RISC-V Privileged ISA Paper #2 Zicntr; §8.7 CSR map; Phase 7 csr_file)

24.3 Deliverable

  • A core executing RV32IM with correct counters; green rv32um tests; RISCOF/formal/differential pass at RV32IM_Zicsr_Zicntr. Multi-cycle ops stall correctly.

24.4 Acceptance Criteria

  • All 8 MUL/DIV/REM variants match a reference (incl. div-by-zero + overflow corner cases).
  • mcycle/minstret count correctly; mcountinhibit gates them; cycle/instret mirror.
  • Multi-cycle stall is cycle-exact; DIV/REM latency ≤ 34 cycles (XLEN+2, M13), no lost forwarding.
  • Conformance/formal/differential green with M enabled (100% rv32um pass, M8).

24.5 Conformance Fixtures

  • verif/tests/rv32um-*.hex; verif/m/divzero.S, overflow.S (INT_MIN/-1), mulh_signs.S.
  • verif/csr/counters.S — count, inhibit, read mirrors.
  • Malformed: M-opcode when M is disabled → illegal-instruction trap.

24.6 Pitfalls

  • Div-by-zero / signed-overflow corner semantics — spec mandates specific results (not a trap); wrong values fail conformance; tabulate + fixture each.
  • MULHSU sign handling — mixed signed×unsigned high-half is easy to get wrong; reference-check.
  • Multi-cycle op + interrupt — taking an IRQ mid-divide must be precise (restart or complete); define + assert.
  • Counter overflow / hi-lo atomicity — 64-bit counters over a 32-bit bus tear at rollover (same as mtime); careful read protocol.
  • DSP-less iCE40 multiplier — inferring a big combinational multiplier wrecks timing; use multi-cycle/iterative on UP5K; DSP on ECP5.

24.7 Performance Concerns

  • DIV/REM are multi-cycle (iterative, ~XLEN cycles) → big IPC hit on div-heavy code; document the latency. MUL single-cycle on DSP, multi-cycle without. Counters add small CSR cost. These ops affect Fmax (multiplier) + IPC (divider) — feed Phase 13.

24.8 Edge Cases

  • INT_MIN / -1 (overflow → INT_MIN, REM → 0); div/rem by zero; back-to-back divides; an interrupt arriving during a long divide; MULH of two negatives; counter read exactly at rollover.

24.9 Failure Analysis

  • M/counter bugs corrupt arithmetic or break timekeeping. Detection: rv32um + corner fixtures + differential + formal. Blast radius: any mul/div/counter user. Recovery: fix mul_div/CSR; regression. Forensic: differential dump at the failing op; the busy-handshake waveform.

24.10 Operational Notes

  • instret/cycle are the on-core performance counters Phase 13 uses to measure IPC. Update the published ISA string + conformance report. Document div latency for software. Cross-link Phase 13 (multiplier/divider are area/Fmax knobs).

25. Phase 13 — Microarchitecture optimization: IPC / Fmax / area tuning

25.1 Objectives

  • With a correct, conformant, formally-checked core, optimize the engineering metrics: enable the branch predictor seam (simple BHT/gshare), tune the critical path for higher Fmax, and trade area — all without regressing correctness (every change re-runs the full verification suite).

25.2 Detailed Implementation Steps

  • Enable the predictor: implement the bht (direction table, optionally gshare with a global history register) behind the Phase-4 seam; add a BTB or compute target on predict; measure mispredict-rate reduction. (H&P App C branch prediction; ADR-3 predictor seam; cross-link #189)
  • Critical-path tuning: from the Phase-11 timing report, attack the longest path (EX forwarding mux + ALU, or the bus mux) — rebalance logic, consider an extra register stage, retime; re-measure Fmax. (Weste & Harris Book #8 critical-path; ADR-9 nextpnr timing report; Phase 11 timing closure)
  • Area tuning: regfile implementation (LUT-RAM vs BRAM vs duplicated), multiplier strategy (DSP vs iterative), peripheral trimming; re-measure LUT/FF/BRAM/DSP. (ADR-26; §4.3 area budgets; iCE40/ECP5 fabric docs primitives)
  • Benchmarks: a CoreMark-like / Dhrystone-ish workload + the program corpus; measure IPC (instret/cycle), mispredict rate, memory-stall cycles. (Phase 12 minstret/mcycle counters; §4.2 IPC targets; Scalability Analysis bottlenecks)
  • Each optimization is gated: re-run Phases 8–10 (differential + RISCOF + formal) green before keeping it; record the Fmax/area/IPC delta. (ADR-13; ADR-14; ADR-16; Design Principle 1)
  • SVA: predictor correctness (a misprediction is always recovered → state still matches core_sc); retiming preserves RVFI. (Wolf riscv-formal Paper #4; ADR-2; §11.9 RVFI)

25.3 Deliverable

  • A measurably faster core: higher IPC (predictor), higher Fmax (path tuning), and/or smaller area, with a before/after metrics table — and zero correctness regression (full suite still green).

25.4 Acceptance Criteria

  • Predictor reduces mispredict rate on branchy benchmarks by a documented margin; correctness unchanged (state-equiv + formal).
  • Fmax improved (or area reduced) vs the Phase-11 baseline, documented with the timing/area report delta.
  • IPC measured on the benchmark corpus; reported with the configuration.
  • Full verification suite (Phases 8–10) green after every kept optimization.

25.5 Conformance Fixtures

  • verif/perf/corpus/*.elf + baseline IPC/mispredict numbers.
  • fpga/reports/{timing,area}.tuned vs .baseline — the delta gate.
  • verif/p5/predictor_recovery.S — mispredict + recovery → state correct.
  • Malformed: a predictor that mispredicts must never commit wrong-path state (assert).

25.6 Pitfalls

  • Predictor that corrupts state on mispredict — recovery must flush + redirect exactly; a leak commits wrong-path effects; assert state-equiv after every mispredict.
  • Retiming that breaks RVFI commit point — moving a register can shift where "commit" is; re-validate RVFI vs actual writes.
  • Optimizing the wrong path — tuning a non-critical path yields no Fmax gain; always drive from the timing report.
  • Area/Fmax/IPC tradeoff misread — a "faster" change that lowers Fmax nets slower wall-clock; compare IPC×Fmax (effective throughput), not IPC alone.
  • BHT aliasing — gshare index aliasing degrades accuracy; size + index thoughtfully; measure.

25.7 Performance Concerns

  • The whole phase is performance. Headline metrics: IPC (predictor + stall reduction), Fmax (critical path), area (resource usage), and effective throughput (IPC×Fmax). Memory-stall cycles (classic Wishbone) bound memory-bound code → motivates caches (#187, deferred).

25.8 Edge Cases

  • Pathological branch patterns (alternating taken/not-taken) defeating a simple BHT; very tight loops (predictor warmup); a benchmark that's memory-bound (predictor irrelevant); retiming at a stage boundary with a hazard.

25.9 Failure Analysis

  • An optimization that regresses correctness is the worst outcome (fast + wrong). Detection: the full suite gate (differential + formal) on every change. Blast radius: whatever the optimization touched. Recovery: revert the optimization (it's gated, so it never merges red). Forensic: the metrics delta + the failing verification trace.

Operational Readiness

  • Metrics (on-core counters): instret, cycle, branches, mispredict, flush_cycles, stall_cycles, trap_cause{...}, bus_err, watchdog_fire, irq_latency. Exported via UART/JTAG-trace; the perf counters (Phase 12) are the IPC source.
  • Tracing: RVFI retire stream (the canonical trace) — dumpable to a file in sim, to UART on board; per-instruction PC/insn/reg/mem.
  • Structured logging: sim $display retire trace (plusarg-gated); on-board UART log with a defined line format ([cyc] pc insn).
  • Dashboards: CI artifacts — timing/area trend, IPC/mispredict trend across commits, conformance pass-rate, formal proof status; a per-PR metrics delta.
  • Alerting philosophy: CI gates (fail-closed) on correctness (differential/formal/conformance must be green), timing (Fmax ≥ target, positive slack), area (≤ budget), reproducibility (hash match). No silent regression merges.
  • SLOs (engineering, not service): Fmax ≥ target per board; area ≤ budget; rv32ui/rv32um 100%; RISCOF 100%; formal matrix green to depth; zero differential divergence on the corpus.
  • Incident response / runbooks: "core hangs on board" → check WDT + bus trace; "differential divergence" → bisect to the retire, compare RVFI vs Spike; "timing fails" → read PnR report, attack the critical path; "garbled UART" → check baud divisor vs board clock.
  • Backup/restore: the source + pinned toolchain is the artifact; bitstreams + .hex archived per release with hashes; restore = rebuild from the pinned tag (reproducible).
  • Deployment topology: single-board (iCE40 UP5K / ECP5); programmed via iceprog/openFPGALoader; UART console + LEDs. No fleet/orchestration (single-device).
  • Canary / rolling / rollback: "canary" = bring up the new bitstream on one board, run the UART self-test + a smoke program before adopting; rollback = re-flash the last known-good bitstream (versioned). RTL changes roll out only after the full verification suite is green.
  • Migration: ISA-string changes (adding M/Zicntr) are additive; programs built for RV32I still run; document the misa/capability bump.

Compatibility & Versioning

  • ISA compatibility: the core implements ratified RV32I (+ optional M, Zicsr, Zicntr) per the unprivileged + privileged specs; any RV32I[M] binary built with a conforming toolchain runs. ISA string (misa) is the honest capability statement; never overclaimed.
  • ABI: standard RISC-V calling convention (ilp32); the linker script (link.ld) + memory map (§8.9) are the platform contract programs link against.
  • Bus compatibility: Wishbone B4 (classic; pipelined variant gated) — any B4-compliant slave attaches via the fabric; the interface (wb_if) + modports are the wire contract.
  • Peripheral/register-map stability: UART/timer/GPIO register layout (the SoC ABI) is versioned; additive changes only within a major version.
  • RVFI contract: the rvfi_t shape is the verification wire format consumed by the differential + formal harnesses — frozen.
  • Deprecation/versioning: SemVer on the SoC (major = memory-map/ABI break, minor = additive peripheral/ISA-extension, patch = bugfix). Deferred extensions (RV64/F/D/A/C/V, S/U mode, MMU) are explicitly not guaranteed and gated via PhaseDeferred.
  • Rolling upgrade: new bitstreams are drop-in for the same board/pinout; a pinout/clock change is a major (documented) break.

Testing & Verification Strategy

  • Unit (leaf): ALU truth tables, imm_gen vs objdump, decoder vs the golden ctrl_t table, regfile x0/port behavior.
  • Integration (core): core_sc fixtures, core_p5 state-equivalence vs core_sc, hazard/branch/memory/trap fixtures.
  • Differential: lockstep vs Spike over a program corpus (the highest-value regression); first-divergence pinpointing.
  • Conformance: RISCOF (riscv-arch-test) signatures vs the Spike reference — the standardized statement.
  • Formal: riscv-formal / SymbiYosys — per-instruction, reg/PC consistency, causality, liveness, uniqueness; bounded + (where feasible) k-induction.
  • Property: randomized instruction sequences (riscv-dv-style) feeding the differential harness; property checks on leaves (ALU/rescale-like identities).
  • Fuzzing: randomized legal + malformed instruction streams; randomized bus traffic against the protocol assertions; depacketizer-style fuzz N/A (no network).
  • Chaos / fault injection: seeded RTL bugs (negative tests) that the differential + formal harness must catch; injected bus stalls/err; interrupt-at-every-position.
  • Deterministic replay: RVFI traces + pinned mtime injection make every failing run reproducible bit-for-bit.
  • Soak: long-running programs (millions of retires) under the differential harness nightly; on-board burn-in (LED/UART running for hours).
  • Compatibility: rebuild + re-run the suite across the pinned toolchain; re-run conformance after each ISA-string change.
  • Regression / perf-regression: every fixture is permanent; CI gates correctness + timing/area/IPC deltas (no silent Fmax/area/IPC creep).

Scalability Analysis

  • Bottlenecks: Fmax bound by the longest combinational path (EX forwarding/ALU, bus mux, multiplier); IPC bound by branch flushes (2-cycle EX-resolve penalty), load-use stalls, multi-cycle divide, and classic-Wishbone memory stalls.
  • Scaling ceilings: single-issue in-order → IPC ≤ 1; the realistic ceiling is set by hazards + memory; area ceiling is the FPGA fabric (UP5K is small — BRAM + LUT bound).
  • "Horizontal" scaling: out of scope here — multi-core/SMP, superscalar, OoO are explicit non-goals (cross-link #188); the seam is a clean single-core SoC.
  • "Vertical" scaling: higher Fmax (timing tuning), higher IPC (predictor, deferred caches), wider memory (pipelined Wishbone) — the Phase-13 + deferred levers.
  • Sharding/partitioning analog: the SoC address map partitions the bus; adding slaves scales the peripheral side (decode + mux depth is the cost → affects Fmax).
  • Replication/coordination: N/A (single core); a future multi-core would add a coherent interconnect (out of scope).
  • Network fanout: N/A (no network).
  • Scheduler saturation analog: interrupt storm / tight loops → liveness pressure, bounded by the WDT + rate-limiting.
  • Storage/metadata growth: program/data bound by BRAM size; external DRAM is PhaseDeferred; the memory map reserves room for growth.

Mental Models & First Principles

MM1. A pipeline register is a contract, not a wire. Each stage-boundary register (if_id, id_ex, ex_mem, mem_wb) is an explicit snapshot of architectural state at a specific pipeline position. What it predicts: if a field is missing from a stage register, the downstream stage must re-derive it — usually wrongly. Bug class: using a stale operand from a prior instruction because the correct value was not captured in id_ex. Applied in: Phase 3 (pipereg, §11.3 pipeline-register structs) and Phase 4 (branch flush via flush_idex).

MM2. Forwarding is register-file bypass, not a side channel. The forwarding network is a combinational shortcut from a pipeline stage's output to a downstream stage's input, controlled entirely by the hazard unit. What it predicts: every forwarding bug is a register-comparison error (rd != 0 guard, wrong stage priority, wrong mux select). Bug class: reading a stale regfile value when the correct value is in-flight in ex_mem or mem_wb. Applied in: Phase 3 (§8.6 hazard table, hazard.sv) and Design Principle 6.

MM3. A trap is a synchronous pipeline redirect with side effects. Trap entry is mechanically identical to a taken branch (flush younger stages, redirect PC) but additionally saves three pieces of architectural state (mepc, mcause, mtval) and modifies mstatus. What it predicts: imprecise traps arise when the flush point and the side-effect capture point are in different stages. Bug class: mepc pointing at the wrong instruction or mtval capturing the wrong faulting address. Applied in: Phase 7 (csr_file §11.5, Smith & Pleszkun Paper #11) and §7 Invariant 6.

MM4. Formal verification proves the ISA contract, not the implementation intent. riscv-formal's checks verify that the RVFI output matches the spec semantics for every instruction under every input sequence — it does not verify the internal microarchitecture. What it predicts: a core can have internal redundancy bugs (e.g. an ALU that computes two answers and picks one) that pass formal but would be caught by differential. Bug class: over-constrained formal environments producing vacuous proofs. Applied in: Phase 10 (§22.2, Wolf riscv-formal Paper #4) and Design Principle 11.

MM5. Static timing analysis measures paths, not probabilities. The PnR timing report shows the longest combinational path — if it exceeds one clock period the design has a timing violation regardless of what inputs are exercised. What it predicts: a design that "works in sim" at a frequency that violates timing is running on luck (metastability). Bug class: intermittent on-board failures under varied temperature/voltage. Applied in: Phase 11 (§23.2, Weste & Harris Book #8) and Design Principle 14.

MM6. The Wishbone handshake is a liveness contract, not a throughput one. Classic Wishbone guarantees every cyc&stb is eventually ack'd — it says nothing about when. What it predicts: a missing ack path or a bus watchdog absent from the design creates an infinite stall. Bug class: the pipeline freezes forever when a slave fails to assert ack (e.g. an out-of-map address with no err response). Applied in: Phase 5 (wb_fabric §11.6, §7 Invariant 8) and Threat Model.

MM7. Differential testing is a relative oracle; it cannot prove absolute correctness. Comparing DUT RVFI against Spike's commit log proves the DUT matches Spike — if Spike has a bug, both would agree on the wrong answer. What it predicts: differential testing has high sensitivity for implementation deviations but zero coverage of spec-level Spike bugs. Bug class: a subtle CSR WARL-field misunderstanding shared between the DUT and Spike passes differential but fails a hand-computed spec cross-check. Applied in: Phase 8 (§20.2, ADR-13) and Phase 10 (formal complements differential).

MM8. Parameterize the seam, not the logic. The Wishbone interface, the memory map in rv_pkg, and the predictor seam in branch_unit are the extension points. Widening a mux inside a module is a local change; adding a slave to the fabric or swapping a predictor through a defined interface is a seam change. What it predicts: any design change that bypasses a seam creates a fork that doubles the maintenance surface. Bug class: a core-P5-specific memory assumption that breaks when a cache is substituted behind the same Wishbone seam. Applied in: Design Principle 9, §1.4 deployment model, and Deferred Features Register.

PicoRV32. Wolf's core chose a multi-cycle FSM that eliminates the classic 5-stage pipeline entirely, resulting in a ~1750 LUT4 footprint on iCE40 — roughly half this design. The FSM sequencing means every instruction takes 3–6 cycles, but the critical path is tiny and Fmax on iCE40 approaches 100 MHz. PicoRV32 wins in the tightest area/power-budget embedded applications (sensor nodes, custom ASICs under 5 K gates) where IPC is irrelevant but code density and clock speed matter.

Ibex (lowRISC). A 2-stage RV32IMC core with machine + user mode, a formal + lint verification discipline comparable to this project, and ASIC-grade hardening. Its 2-stage design achieves competitive area vs 5-stage while maintaining in-order semantics. Ibex wins in production silicon tape-outs or FPGA SoCs that need a formally verified, user-mode-capable core with a hardened CSR set and a permissive license for commercial integration.

VexRiscv (SpinalHDL). A parameterized pipeline built from composable plugins; the same RTL source can be configured as a minimal 2-stage or an aggressive 5-stage with caches, MMU, and FPU. VexRiscv regularly achieves 80–100 MHz on ECP5 with full RV32IMA. It wins when a team needs a generator that produces multiple microarchitecture variants from one codebase — e.g. a chip that ships in both a low-power and a high-performance SKU — or when LiteX SoC integration (Python-based) is attractive.

Rocket (UCB/SiFive). A production-quality in-order 5-stage RV32/64GC core with supervisor mode, Sv39 MMU, and TileLink interconnect, implemented in Chisel. Rocket is the foundation of SiFive's commercial product line. It wins when the target is a Linux-capable SoC with an MMU and a rich peripheral ecosystem, or when the team has Chisel expertise and needs a mature in-order baseline to extend or productize.

BOOM (UCB). An out-of-order, superscalar RISC-V core also written in Chisel, with a reorder buffer, register renaming, a 2-wide issue, and advanced branch predictors. BOOM wins in server or HPC workloads where IPC×Fmax is the primary metric and the 10× area cost relative to an in-order core is acceptable. This blueprint rejects OoO at this phase because the hazard logic complexity grows non-linearly (cross-link #188).

Back-of-Envelope Capacity Model

All numbers derived from §4 System Constraints.

C1. Instruction memory footprint (IMEM BRAM)

  • BRAM size (§4.3): 64–256 KB parameterized.
  • RV32I instruction density: 4 bytes/instruction (fixed-width, no compressed).
  • 64 KB IMEM → 64 × 1024 / 4 = 16 384 instructions capacity. 256 KB → 65 536 instructions.
  • Rule: a Dhrystone / CoreMark-class benchmark in C compiles to ~5 K–20 K instructions with riscv-gcc -O2 → 64 KB IMEM is tight; 128 KB is the comfortable target.

C2. Data memory footprint (DMEM BRAM)

  • BRAM size (§4.3): 64–256 KB.
  • Stack frame size (typical bare-metal): 128–512 bytes; heap allocations for Dhrystone: ~8 KB.
  • 64 KB DMEM → supports up to ~128 deeply-nested stack frames at 512 bytes each, or 8 K × 8 B = 64 K entries in a 1-byte array.
  • Rule: 64 KB DMEM is sufficient for all Phase 0–13 workloads; DRAM is needed only when working set > 256 KB (Deferred Features Register).

C3. Pipeline cycle budget per instruction (CPI model)

  • Ideal IPC = 1.0, CPI = 1.0 (§4.2).
  • Load-use stall contribution: ~15–20% of instructions are loads; of those, ~30% have an immediate use → stall rate ≈ 15% × 30% = 4.5% of cycles wasted; CPI from load-use ≈ 1.045.
  • Branch flush contribution: ~15% of instructions are branches; ~40–60% taken (Dhrystone) → penalty cycles = 0.15 × 0.5 × 2 = 0.15 cycles/instruction; total CPI ≈ 1.045 + 0.15 = ≈ 1.20.
  • Matches the §4.2 target CPI ≤ 1.3 with headroom for rare mul/div stalls.

C4. Branch predictor table sizing (BHT)

  • BHT entries (Phase 13 predictor): 256–1024 2-bit saturating counter entries (gshare).
  • Memory cost: 1024 entries × 2 bits = 256 bytes (tiny; fits in LUT-RAM on iCE40).
  • Global history register: 10-bit GHR → 2^10 = 1024 index space; aliasing rate ≈ number-of-static-branches / 1024 → for < 200 static branches (Dhrystone) aliasing is low.

C5. UART baud divisor and bit timing

  • Clock (§4.3): 12 MHz (iCE40 UP5K).
  • Target baud: 115 200 baud.
  • Divisor = 12 000 000 / 115 200 = 104.17 → round to 104.
  • Actual baud = 12 000 000 / 104 = 115 384; error = (115 384 − 115 200) / 115 200 = 0.16% (well within the ±2% UART tolerance).
  • Bit time = 1 / 115 200 ≈ 8.68 µs; at 12 MHz that is 104 clocks/bit; mid-bit sample at clock 52.

C6. Timer interrupt latency

  • Clock period at 25 MHz: 40 ns.
  • Pipeline depth: 5 stages; IRQ taken at an instruction boundary → worst-case latency = 1 instruction completing + 5-cycle redirect = 6 cycles = 240 ns at 25 MHz.
  • Handler prologue (save context, 8 CSR writes): ~12 instructions × CPI 1.2 = ~14.4 cycles ≈ 580 ns.
  • Total interrupt response (IRQ assert → first handler instruction execute): ≈ 820 ns at 25 MHz, ≈ 330 ns at 50 MHz (ECP5).

C7. LUT budget for core_p5 (iCE40 UP5K)

  • Register file (32 × 32): iCE40 LUT-RAM inference for 2R/1W → ~512 LUT4 (duplicated for 2 read ports).
  • ALU (32-bit ripple-carry equivalent, all ops): ~200 LUT4.
  • Decoder + control muxes: ~150 LUT4.
  • Hazard unit + forwarding muxes: ~100 LUT4.
  • Pipeline registers (4 × ~100-bit): ~400 FF (not LUT).
  • CSR file (~10 × 32-bit registers + logic): ~350 LUT4.
  • Branch unit: ~50 LUT4.
  • Total core estimate: ~1 362 LUT4 → plus wb_fabric (~200), peripherals (~300) → ≈ 1 900–2 200 LUT4 (vs §4.3 budget ≤ 3 000 LUT4 — comfortable margin).

C8. Fmax critical path estimate

  • Forwarding mux → ALU → branch compare: each mux level ≈ 0.5 ns, 32-bit carry-propagate ALU ≈ 8 ns (iCE40 carry chain), branch compare ≈ 2 ns → EX-stage total ≈ 10.5 ns → max Fmax ≈ 95 MHz unbuffered.
  • iCE40 UP5K routing overhead: 2–3× vs raw logic delay → realistic Fmax ≈ 30–40 MHz (matches §4.3 target ≥ 25 MHz, stretch 40 MHz).
  • ECP5 routing is faster: realistic Fmax ≈ 60–80 MHz (matches §4.3 target ≥ 50 MHz, stretch 75–100 MHz).

C9. riscv-formal solver memory

  • State space per check: ~200-bit architectural state × 2^depth pipeline states.
  • At BMC depth 20: 200 bits × 20 cycles × ~10 K logic gates → solver peak RAM ≈ 500 MB–2 GB (typical SymbiYosys/Yices2 run on a modern workstation — fits comfortably in 8 GB CI runner memory).

C10. Differential harness throughput

  • Verilator sim rate (§4.4): ≥ 1 × 10^6 instructions/s (conservative).
  • Spike step rate: ~5 × 10^6 instructions/s (single-threaded).
  • Combined differential throughput (limited by Verilator): ~1 × 10^6 retires/s.
  • rv32ui suite size: ~400 tests × ~5 000 instructions each = 2 × 10^6 instructions → ~2 seconds wall-clock per push (parallelized across tests → sub-second).

  1. Forwarding priority conflict. In ex_mem.rd == id_ex.rs1 AND mem_wb.rd == id_ex.rs1 both hold simultaneously, both with regwrite=1. Which stage wins and why? Where does this decision live, and what §7 invariant would be violated if you got it wrong? (§8.6 hazard table + Phase 3 hazard unit + §7 Invariant 3)

  2. Load-use stall + branch same cycle. A lw is in EX and the instruction being decoded in ID is a beq that uses the loaded register. The hazard unit must simultaneously insert a stall and evaluate whether to flush. Which action has priority and why? How does the commit-point behave? (Phase 3 load-use stall + Phase 4 branch flush + §8.6 decision table)

  3. Precise exception at a store. A sw instruction in MEM causes a store-address-misaligned trap. At this moment, newer instructions are in IF and ID. What is mepc? Which instructions must be flushed? Why must the store's memory effect NOT have committed? Trace through Phase 5 MEM-stage, Phase 7 trap controller, and §7 Invariant 6.

  4. mret during a pending timer interrupt. An interrupt handler calls mret. At the same cycle, mip.MTIP is asserted and mie.MTIE=1. Does the interrupt re-fire before or after the first instruction at mepc executes? Trace through §11.5 csr_file, §8.7 CSR map, and the §7 Invariant 7 mret invariant.

  5. RVFI retire ordering vs BRAM latency. The rvfi_t.valid fires at WB. A load instruction's mem_rdata is available only after the MEM stage completes. Is rvfi_t.mem_rdata in the MEM/WB register or re-read from BRAM at WB? Why does the answer matter for the riscv-formal mem channel? (§11.9 RVFI contract + Phase 5 BRAM latency + Phase 10 formal checks)

  6. Branch predictor mispredict and a load-use stall in the shadow. The pipeline predicts not-taken on a branch. Two instructions into the wrong path, there is a load-use hazard. The branch resolves taken in EX. How many wrong-path instructions were fetched, and how many of those were in a stall state? What does the hazard unit do? (Phase 3 + Phase 4 + Phase 13 predictor recovery + §8.5 worked example)

  7. Timing closure vs IPC tradeoff. The Phase-11 report shows the EX forwarding mux is the critical path. One fix is to pipeline the forwarding decision (add a register stage).   8. RISCOF ISA string and CSR misa. If you configure RISCOF with RV32IMC but the core's misa reads RV32I (M/C not set), will conformance pass or fail? Which Phase 9 pitfall is triggered, and how does Phase 12 re-run change the ISA string? (Phase 9 §21.2 + Phase 12 §24.2 + §8.7 misa CSR)

  9. mtime read tearing across the Wishbone bus. Software reads mtime_lo at address 0x2000_1000 then mtime_hi at 0x2000_1004. Between the two reads, mtime increments and carries from lo to hi. What value does software see? How does the read-lo-then-hi-then-recheck-lo pattern fix this? Where is this pattern documented in this blueprint? (Phase 6 §18.6 mtime tearing + §8.9 memory map + §8.10 edge cases)

  10. Formal vacuity check. You constrain the riscv-formal environment to assume(rst == 1) for all time. All checks pass immediately. How do you detect this is vacuous? What cover property must you add, and in which file does it live? (Phase 10 §22.2 + §22.6 pitfalls + Wolf riscv-formal Paper #4)

  11. DSP-less iCE40 multiplier and interrupt. The iterative divider for divu x3, x1, x2 takes 32 cycles on iCE40. A timer interrupt fires on cycle 17 of the divide. The core must present a precise exception. Does mepc point at the divu instruction or the next one? Is the divide result written to x3 before the trap? (Phase 12 §24.2 multi-cycle op + Phase 7 trap machinery + §7 Invariant 6)

  12. Spike config delta and differential divergence. The DUT resets at 0x0000_0000. Spike is invoked without --isa and defaults to a different reset PC.   13. Fmax regression from a peripheral addition. A new Wishbone slave is added behind wb_fabric. The fabric's address decode mux grows from 5 to 6 inputs. (Phase 5 wb_fabric + Phase 11 timing + Build & Release Engineering CI gates)

  14. X-propagation through reset. A flip-flop in csr_file has no reset assignment. After reset deassertion, it holds X in simulation.   15. JALR forwarding dependency. addi x1, x0, handler is followed immediately by jalr x0, x1, 0. The addi is in MEM when jalr is in EX. The forwarding unit must supply x1 to the branch_unit's rs1 input. Which forwarding path (EX/MEM or MEM/WB) applies? What is the branch target if forwarding is absent? Alternative Architectures (Roads Not Taken)

Alt-A: Multi-cycle FSM (PicoRV32-style)

+------------------------------------------+
|  soc_top                                 |
|                                          |
|  +------------------+                   |
|  |  core_fsm         |  One register     |
|  |  PC reg           |  file, one ALU,   |
|  |  state: FETCH ->  |  reused each      |
|  |  DECODE -> ALU -> |  micro-step by    |
|  |  MEM -> WB        |  an FSM counter   |
|  +------------------+                   |
|  Single shared BRAM (instr + data)       |
|  Wishbone or direct memory port          |
+------------------------------------------+

Regime where it wins. When die area or FPGA LUTs are the primary constraint (< 2 000 LUT4) and IPC is irrelevant — sensor microcontrollers, clock-domain isolation logic, custom ASIC under 10 K gates. The FSM's tiny critical path yields very high Fmax on small fabric (PicoRV32 exceeds 100 MHz on iCE40) despite CPI of 3–6.

Real system that embodies it. PicoRV32 (Clifford Wolf) — see Ref-impl #2; also the original 8051 core.

Why this blueprint rejected it. The pedagogical goal (§2.1) is to build the canonical 5-stage pipeline that every architecture course teaches — forwarding networks, hazard detection, and pipeline registers are load-bearing learning outcomes. A multi-cycle FSM eliminates all of those; it also makes formal verification of timing-sensitive hazard logic impossible. Correctness over area was the explicit choice (Design Principle 1).

Alt-B: 2-stage in-order pipeline (Ibex/zero-stage style)

+------------------------------------------+
|  soc_top                                 |
|                                          |
|  +------------------+                   |
|  |  stage_if         |  Fetch + partial  |
|  |  (fetch + decode) |  decode in one    |
|  +------------------+  stage; no        |
|         |              IF/ID register    |
|  +------------------+                   |
|  |  stage_ex         |  Decode + EX +    |
|  |  (full ALU, MEM,  |  MEM + WB in     |
|  |  WB, CSR, trap)   |  one wide stage   |
|  +------------------+                   |
+------------------------------------------+

Regime where it wins. When area is tighter than ~5 K LUT4 but a complete machine-mode CSR set and M-extension are needed — i.e., the use case is an embedded microcontroller with a certified firmware stack (Ibex targets OpenTitan, a security processor). The 2-stage design eliminates most pipeline hazards (no load-use stall in the classic sense) and simplifies trap logic while retaining reasonable Fmax.

Real system that embodies it. Ibex (lowRISC) — see Ref-impl #4; also the ARM Cortex-M0 (2-stage). See Comparative Architecture Table.

Why this blueprint rejected it. A 2-stage design does not exercise the forwarding network, the load-use hazard, or the 2-cycle branch flush — the three hardest concepts in pipelining. The five-stage structure (ADR-3) was chosen specifically to make those mechanisms explicit and verifiable (Phase 3, Phase 4). The 2-stage alternative is documented in the Comparative Architecture Table and referenced in cross-link #188.

Alt-C: Generator-style parameterized core (VexRiscv / Chisel approach)

+-------------------------------------------------------+
|  generator.scala (SpinalHDL / Chisel)                 |
|                                                       |
|  Pipeline = new Pipeline(                             |
|    stages = [IF, ID, EX, MEM, WB],                   |
|    plugins = [DecoderPlugin, HazardPlugin,            |
|               BranchPlugin, CachePlugin, ...]         |
|  )                                                    |
|  // Each plugin injects signals into the pipeline     |
|  // Generates Verilog/FIRRTL as output               |
+-------------------------------------------------------+
         | (generated Verilog)
         v
+----------------------+
|  Yosys + nextpnr     |
+----------------------+

Regime where it wins. When a team ships multiple SKUs from one codebase — a minimal RV32I, an RV32IMC with a BHT, and an RV64GC with caches and an MMU — that differ only in plugin composition. The generator amortizes RTL authoring cost across variants and enforces interface contracts automatically. SiFive uses a similar approach (Rocket/BOOM in Chisel) to generate a family of cores.

Real system that embodies it. VexRiscv (SpinalHDL) — see Ref-impl #3; Rocket Chip generator (Chisel) — see Ref-impl #5.

Why this blueprint rejected it. The Scala/SpinalHDL/Chisel build chain adds a large non-RTL dependency (JVM, sbt, Scala toolchain) with significant learning overhead for an audience whose primary goal is mastering SystemVerilog HDL and pipeline micro-architecture. Generated Verilog is harder to read and debug than hand-written SV; waveform debugging requires navigating generated names. For a single-core teaching project, the generator overhead is all cost and no benefit. This is documented in §1.10 rejected alternatives and ADR-1.

Glossary

  • RV32I — the base 32-bit integer RISC-V instruction set (unprivileged).
  • M / Zicsr / Zicntr — multiply/divide extension; CSR-access extension; base performance counters.
  • Single-cycle core (core_sc) — reference core executing one instruction per clock; the in-tree behavioral oracle.
  • 5-stage pipeline (core_p5) — IF→ID→EX→MEM→WB in-order pipeline; the synthesis target.
  • Forwarding / bypass — routing an in-flight result (EX/MEM, MEM/WB) to a dependent's EX inputs to avoid a stall.
  • Load-use hazard — a load feeding the immediately following instruction; requires a 1-cycle stall (data not ready until MEM).
  • Flush — squashing wrongly-fetched instructions after a taken/mispredicted branch.
  • Hazard unit — logic computing forwarding selects + stall/flush signals.
  • CSR — Control/Status Register (e.g. mstatus, mtvec, mepc, mcause).
  • Trap — synchronous exception or asynchronous interrupt transferring control to mtvec.
  • mret — machine-mode trap return (restores MIE, jumps to mepc).
  • Precise trap — no architectural effects of instructions past the trapping one are committed.
  • mtime/mtimecmp — 64-bit machine timer + compare driving the timer interrupt (mtip).
  • Wishbone B4 — the open bus protocol (classic + pipelined) used for the interconnect.
  • cyc/stb/ack/err/sel — Wishbone cycle/strobe/acknowledge/error/byte-select signals.
  • Fabric / decoder — the interconnect routing the core's bus to BRAM + peripherals by address.
  • BRAM — FPGA block RAM (the on-chip instruction + data memory).
  • RVFI — RISC-V Formal Interface; the per-retire record (rvfi_t) consumed by differential + formal harnesses.
  • Spike — the official RISC-V ISA simulator; the differential golden oracle.
  • Differential testing — running the DUT + Spike in lockstep, comparing per-retire state.
  • RISCOF — the official architectural-conformance test framework (riscv-arch-test).
  • riscv-formal — RVFI-based formal ISA-compliance checks run under SymbiYosys.
  • SymbiYosys / BMC / k-induction — the formal flow; bounded model checking; unbounded proof by induction.
  • Yosys / nextpnr — open-source synthesis / place-and-route.
  • iCE40 UP5K / ECP5 — the target Lattice FPGA families (the latter has DSP/larger fabric).
  • Fmax — maximum clock frequency at which timing closes (positive slack).
  • Slack — timing margin (negative = a failing path).
  • Latch inference — accidental level-sensitive storage from an incomplete combinational case/if.
  • IPC — instructions per cycle (retired); ≤ 1 for single-issue in-order.
  • BHT / gshare / BTB — branch history table / global-history-indexed predictor / branch target buffer.
  • tohost/fromhost (HTIF) — the test pass/fail + console protocol used by riscv-tests.
  • misa — the CSR encoding the implemented ISA (the honest capability string).
  • WARL — Write-Any-Read-Legal CSR field semantics.
  • WDT — watchdog timer (resets a hung core).
  • PhaseDeferred — an explicitly out-of-scope feature gated behind a documented marker.
  • Verilator / Icarus / cocotb / GTKWave — C++ cycle sim / event sim / Python testbench framework / waveform viewer.
