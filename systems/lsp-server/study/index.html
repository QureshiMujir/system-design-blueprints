Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does the early-cutoff rule (§16.2) make verify-hit cheaper than recompute even when both walk the dependency list? (§16.2, §16.7)
  2. Under what workspace shape does gopls's package-granularity invalidation (§31) actually outperform this design's per-module edges? (§17.7, §31)
  3. Why is Utf16Index dropped and lazily rebuilt on every edit instead of incrementally patched? (§8.3, §11.2, §14.2)
  4. What would break if Durability::High inputs were allowed to be invalidated by a Low-durability edit? (§16.2, I1)
  5. Why must the parser's synchronization points guarantee token consumption, and what invariant would a violation break? (§15.2, I4)
  6. Why does partial-information correctness (P5) require a complete flag on TypeContext rather than simply omitting incomplete facts? (§8.6, §11.6)
  7. Why is the dispatcher single-threaded while query execution is multi-threaded, instead of both being one or the other? (§3, P7, ADR-13)
  8. What is the actual mechanism that prevents a cancelled query from writing a memo entry, and why does that matter for I2? (§16.2, I4, I2)
  9. Why does rename need one atomic WorkspaceEdit instead of per-file edits sent as separate requests, given both eventually touch the same files? (§20.2, P9, I11)
  10. Why is the green/red tree split (immutable green, ephemeral red) needed at all instead of one mutable tree with parent pointers? (§11.5, §15.2, MM3)
  11. Under what real-world workspace does clangd's preamble strategy (§31) become necessary rather than merely different? (§31, §29)
  12. Why does the semantic-tokens delta protocol require bit-stability (I10) specifically, rather than just "produces a correct delta"? (§20.2, I10, §26)
  13. Why is MAX_MESSAGE_BYTES checked before body allocation instead of after parsing, and what threat does the ordering defend against? (§8.7, T1)
  14. How does the durability model (§16.3) let typing in one file avoid re-verifying workspace-wide facts, concretely? (§16.3, MM5)
  15. Why does the 30-day chaos canary gate release instead of a shorter fixed-duration test, given the invariants are checked continuously either way? (§21.10, §27, §23)
  16. What is the practical ceiling this architecture hits before a packages-graph model would have scaled further, and why? (§29, §31)
  17. Why does configuration convergence (pull vs. push, P12) need to produce byte-identical internal state rather than "equivalent behavior"? (§21.2, §25)
  18. Why is the workspace symbol/reverse-reference index shared between references and rename instead of built independently for each? (§19.2, §20.2, §29)

30. Mental Models & First Principles

  1. MM1 — A query is a pure function from (key, world-revision) to value; the db is a giant lookup table you're allowed to skip filling in. What it predicts: any query is safe to call from anywhere, any number of times. The bug class without it: hidden mutable state smuggled through a "helper" that isn't itself a query. Applied in §16.
  2. MM2 — The revision counter is a Lamport clock for one process. What it predicts: two facts computed at the same verified_at are mutually consistent even if computed at different times. The bug class without it: comparing facts from different edits as if they described the same world state. Applied in §16.2, I1 (§7).
  3. MM3 — A green tree is a Merkle-tree-shaped cache key. What it predicts: identical subtrees really are identical objects, so pointer equality is a valid fast-path everywhere. The bug class without it: redundant structural comparison of trees that are already known-equal by construction. Applied in §15.2, I7 (§7).
  4. MM4 — Cancellation is cooperative, so a computation's "unwind points" are part of its public contract, not an implementation detail. What it predicts: any code path with no unwind point is a latent hang. The bug class without it: a "fast" tight loop that is actually an uncancellable 50 ms stall under the p99 completion budget. Applied in §16.2, §21.9, I4 (§7).
  5. MM5 — Durability is a coarse-grained version number layered on top of the fine-grained revision counter. What it predicts: most edits (Low durability) never need to re-touch workspace-wide facts (High durability). The bug class without it: every keystroke re-verifying facts that provably cannot have changed. Applied in §16.2, §16.3.
  6. MM6 — Partial information is a first-class value, not an error state. What it predicts: a correct handler always has a truthful answer to give, even mid-computation. The bug class without it: a completion or hover that confidently lies because the "real" computation hasn't finished. Applied in §8.6, P5 (§6).
  7. MM7 — The wire protocol and the internal model are different languages; the dispatcher boundary is the translator, and translation errors are the single biggest LSP conformance bug class. What it predicts: any type that crosses the boundary unconverted (a UTF-16 position leaking past PositionConverter) is a live bug. Applied in §8.3, §11.1, P15 (§6).
  8. MM8 — An LSP server's real "users" are the six client capability matrices (§1.1), not one editor. What it predicts: a feature that works in VSCode and nowhere else is unfinished, not done. The bug class without it: capability-assumption bugs that surface only in production, filed by users of the client you didn't test against. Applied in §21.2, §21.5.

5. Required Reading

Books

  • Terence Parr. Language Implementation Patterns, 2nd ed. (Pragmatic Bookshelf). Chapter on error-recovering, hand-written parsers. Applied in Phase 3, §15 (parser/CST error recovery).
  • Benjamin C. Pierce. Types and Programming Languages (MIT Press, 2002). Chapter 22, Type Reconstruction (Hindley-Milner, unification, occurs-check). Applied in Phase 5, §17 (type inference).
  • Andrew W. Appel. Modern Compiler Implementation in ML/Java/C. The symbol-table and lexical-scoping chapters. Applied in Phase 5, §17 (name resolution).
  • Martin Kleppmann. Designing Data-Intensive Applications (O'Reilly, 2017). Ch. 3 (storage/indexing engines) and ch. 11 (stream processing, debouncing, backpressure). Applied in Phase 4, §16 (the memo table as an index) and Phase 6, §18 (diagnostic debouncing).
  • Jon Gjengset. Rust for Rustaceans (No Starch Press, 2021). The chapters on Send/Sync, concurrency primitives, and API design for libraries. Applied in Phase 1, §13 (dispatcher/worker-pool split) and §11 (type concurrency annotations).
  • Alex Petrov. Database Internals (O'Reilly, 2019). The MVCC/consistency chapters. Applied in Phase 4, §16 (the revision counter as an MVCC-style global clock).

Papers

  • Pugh, W. (1989). Incremental Computation via Function Caching. PhD thesis, Cornell University. The formal model of demand-driven memoization Salsa is the modern embodiment of. Applied in Phase 4, §16.
  • Acar, U., Blume, M., Harper, R. (2006). Adaptive Functional Programming. ACM TOPLAS 28(6). The theoretical underpinning of self-adjusting computation. Applied in Phase 4, §16 (dependency-edge tracking).
  • Wagner, T. A., Graham, S. L. (1998). Efficient and Flexible Incremental Parsing. ACM TOPLAS 20(5). The foundational recovery strategies every modern error-recovering LR-family parser implements. Applied in Phase 3, §15.
  • Bourdoncle, F. (1993). Efficient Chaotic Iteration Strategies with Widenings. Formal Methods in Programming and their Applications, LNCS 735. Required for cyclic type-inference convergence. Applied in Phase 5, §17.6.
  • Kladov, A. ("matklad") (2020). Why is the Rust Compiler So Slow? (matklad.github.io). Motivates the query-graph architecture over a parse-on-keystroke design. Applied in §3.1, §31.
  • Kladov, A. (2020). Three Architectures for a Responsive IDE (matklad.github.io). The one-page taxonomy this blueprint's roads-not- taken analysis is checked against. Applied in §34 and §31.
  • Matsakis, N. et al. Salsa: A Generic Framework for On-Demand, Incrementalized Computation (design notes, salsa-rs/salsa). The revision counter / durability / early-cutoff model. Applied in Phase 4, §16.
  • Bracha, G., Ungar, D. (2004). Mirrors: Design Principles for Meta-level Facilities of Object-Oriented Programming Languages. OOPSLA '04. The conceptual basis for AnalysisDb (§11.4) as a "mirror" of program facts rather than a mutated model. Applied in §11.4.

Reference Implementations

  • rust-analyzer (rust-lang/rust-analyzer) — crates/base-db, crates/hir. Lesson: query-graph incrementality end to end. Pitfall: do not copy its crate count verbatim — split at real cohesion boundaries (§10). Applied in Phase 4, §16 and §10.
  • gopls (golang.org/x/tools/gopls) — internal/lsp/cache, internal/lsp/source. Lesson: packages-graph incrementality. Pitfall: package-granularity invalidation is coarser than file-granularity; do not adopt uncritically for a per-file-module language. Applied in Phase 5, §17 and §31.
  • clangd (llvm/llvm-project, clang-tools-extra/clangd) — TUScheduler, Preamble. Lesson: preamble-as-separate-compilation-unit for a language with expensive header re-parsing. Applied in §31.
  • Roslyn (dotnet/roslyn) — src/Compilers/Core/Portable/Syntax. Lesson: red-green tree structural sharing. Applied in Phase 3, §15.
  • TypeScript tsserver (microsoft/TypeScript, src/server) — lesson: single-threaded server design tradeoffs, deliberate not accidental. Applied in §31.
  • tree-sitter (tree-sitter/tree-sitter) — lib/src/parser.c. Lesson: GLR-style error recovery and lossless tree shape. Applied in Phase 3, §15.
  • pyright (microsoft/pyright) — lesson: gradual-typing-aware incremental binder/checker. Applied in Phase 5, §17.

RFCs / Specifications

  • Microsoft. Language Server Protocol Specification, version 3.17 (and the in-flight 3.18 draft), microsoft/language-server-protocol. The normative document for every method, parameter shape, notification, and capability flag; pin to a specific commit and bump explicitly. Applied throughout §8, §11, §12–§21.
  • JSON-RPC 2.0 Specification (jsonrpc.org). Notifications carry no ID; batch requests exist in JSON-RPC but LSP 3.17 forbids them; error codes −32700…−32099 are reserved; $/-prefixed methods are implementation-defined and may be ignored. Applied in §8.1, Phase 1 (§13).

Glossary (§36) · 33 terms · site-wide glossary

AstId
a stable identifier for an AST node across edits, keyed by (file, syntax kind, sibling index); the unit lsp-db dependency edges are expressed in terms of (§11.5).
Backpressure
a mechanism that slows a producer when a consumer cannot keep up; here, the bounded inbound mpsc channel (§13.2, ADR-26).
Cancellation token
a shared, atomically-set flag a query polls to detect that its enclosing request has been cancelled (§11.11, I4).
CST (Concrete Syntax Tree)
a lossless parse tree retaining every source byte including whitespace and comments (§11.5, I6).
Debounce
delaying a reactive computation until input has settled for a window, to avoid recomputing on every intermediate event (§18.2).
Delta encoding
expressing a new value as a diff against a previously-sent baseline, identified by result_id (§11.8, I10).
Dispatcher
the single-threaded component that routes incoming JSON-RPC messages to handlers and tracks in-flight requests (§13.2).
Durability
a coarse staleness tier (Low/Medium/High) attached to db inputs, used to short-circuit dependency verification (§11.4, MM5).
Early cutoff
the optimization of confirming a memoized result is still valid without re-running its computation (§16.2).
FileId
an interned, per-workspace integer identifier for a file (§11.2, I14).
Green tree
the immutable, parent-less, structurally-shared syntax tree representation (§11.5, MM3).
HIR (High-level IR)
the name-resolution/type-inference-ready representation derived from the AST (§6, P6).
Incremental sync
applying only the changed text range of a document rather than replacing it wholesale (§8.4, ADR-11).
Invariant
a property the system must never violate, with a defined detection and recovery path (§7).
JSON-RPC 2.0
the remote-procedure-call wire protocol LSP is layered on (§8.1).
Lexical scope
a region of source code within which a name resolves to a specific declaration (§17.2).
LSP (Language Server Protocol)
the JSON-RPC-based protocol connecting an editor to a language-analysis backend (§1).
Memoization
caching a function's result keyed by its input, to avoid recomputation (§11.4).
Memo entry
one cached (result, dependency set, revision metadata) tuple in the analysis database (§11.4).
Module exports
the set of publicly visible declarations a module makes available to importers (§17.2).
Partial result
a response marked incomplete, allowing the client to request a refinement later (§8.6, P5).
PositionEncodingKind
the negotiated unit (UTF-8/16/32) for wire Position.character offsets (§8.3, P15).
Query (in the db sense)
a memoized, dependency-tracked function over lsp-db state (§11.4, MM1).
Query graph
the directed graph of dependency edges between live memo entries (§16.2).
Red tree
the ephemeral, parent-pointer-bearing view built on demand from a green tree (§11.5).
Revision counter
the monotonic integer that is lsp-db's global clock (§11.4, I1, MM2).
Semantic tokens
a per-token classification (type/modifiers) used for editor syntax highlighting beyond what a grammar alone provides (§11.8).
Structural sharing
reusing the same underlying allocation for unchanged parts of a data structure across versions (§11.5, I7).
Text edit
a (range, replacement text) pair describing one document mutation (§11.3).
Unification
the type-inference algorithm that solves a set of type-equality constraints (§17.2).
Watched file
a file the server monitors for external changes via notify or client-side registration (§21.2, P10).
Worker pool
the fixed-size thread pool executing db queries off the dispatcher thread (§11.4, P7, ADR-13).
WorkspaceEdit
a set of per-file edits applied atomically by the client (§11.9, P9, I11).
