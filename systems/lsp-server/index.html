lsp-transport: owns the byte stream; enforces MAX_MESSAGE_BYTES before any deserialization (§8.7); the only crate allowed to touch stdout.

lsp-dispatcher: the single re-entrancy boundary (I12, §7); every request's RequestId is registered before the handler is spawned, so $/cancelRequest can always find it.

lsp-lifecycle: enforces the handshake state machine (§8.2); any request outside its legal state is rejected, never silently accepted.

Feature handlers: stateless — they issue lsp-db queries and shape the response; no handler caches a derived fact itself (P2, §6).

lsp-db: the single source of truth for every fact about the user's program (P2); revision counter is the server's global clock (I1, §7).

Sync + analysis pipeline: one-way — parse → resolve → infer → diagnose; each stage is an independent, memoized query (§16), so an edit that does not touch name resolution never re-runs inference.

lsp-workspace: resolves multi-root layout and file-watch events into lsp-db input changes; never queries lsp-db directly for facts, only feeds it.

lsp-progress: cross-cutting — every long-running handler registers with it before starting real work.

Three properties hold everywhere else in this document. First, the request data path is one-way: transport → dispatcher → handler → db (query, possibly streaming partial results) → serialize → transport; handlers never reach into the transport, the db never reaches into a handler. Second, lsp-db's revision counter (I1) is the only global clock; there is no second cache holding an older view of a fact. Third, cancellation is cooperative and propagates through the query graph (I4): a cancelled query unwinds, and every query that consumed its (now-unwound) result unwinds too — no orphaned computation survives past a request's cancellation point (verified by the conformance suite, §26).

3.1 Why a query database, not a graph of cached objects

Every production LSP past the toy stage hits the same wall: a feature works in isolation, then breaks under interactive editing because something cached a handle to a derived object and the handle now points at a stale tree. The fix is to stop holding derived objects and hold keys into a query database that re-derives on demand (P2). The cost is a query call per access; the benefit is every access sees a view of the world consistent with the revision the request started at. rust-analyzer, gopls, and Roslyn all pay this cost; the literature (§5) is unanimous that the alternative does not survive contact with real interactive editing.

3.2 Why an error-recovering CST, not a bail-on-error AST

A parser that stops at the first syntax error gives a correct tree only when the user has stopped typing — roughly never, mid-edit. An error-recovering CST that reports errors as tree nodes (§8, I6) gives a tree at every keystroke; the recovery logic is harder to write, but "features that work mid-edit" is the entire reason this server exists — partial-information correctness (P5, §6) is load-bearing throughout, formalized as the complete flag in TypeContext (§11.6).

8. Domain Model / Protocol

8.1 Wire message grammar

JSON-RPC 2.0 over Content-Length framing (LSP 3.17 §Base Protocol):

Message   ::= Header+ CRLF Body
Header    ::= "Content-Length:" DIGIT+ CRLF
            | "Content-Type:" TOKEN CRLF        (optional, tolerated on read)
Body      ::= JSON-RPC-Object                    (exactly Content-Length bytes)

JSON-RPC-Object ::= Request | Response | Notification
Request      ::= { jsonrpc: "2.0", id: RequestId, method: String, params?: Value }
Notification ::= { jsonrpc: "2.0",                method: String, params?: Value }
Response     ::= { jsonrpc: "2.0", id: RequestId, (result: Value | error: ErrorObj) }
ErrorObj     ::= { code: Int, message: String, data?: Value }
RequestId    ::= Int | String                     (LSP never uses null)

No batching (LSP 3.17 forbids the JSON-RPC batch-array form, P11). Method names beginning $/ are implementation-defined and MAY be dropped without error (e.g. $/cancelRequest, $/progress).

8.2 Request/notification lifecycle state machine

WaitingForInitialize --initialize(params)--> Initialized --capabilities-->
Initialized --initialized()--> Running
Running --shutdown()--> ShuttingDown --null-->
ShuttingDown --exit()--> Terminated(code=0)
any --exit() while not ShuttingDown--> Terminated(code=1)
any state, any request before Running (except initialize) --> error -32002

Illegal transitions are rejected with -32002 ServerNotInitialized (pre- handshake) or -32600 InvalidRequest (post-shutdown protocol violation); see FM-2 (§23).

8.3 Position encoding

LSP 3.17 negotiates PositionEncodingKind (utf-8 | utf-16 | utf-32) in initialize; default is utf-16 for backward compatibility. Internally every Position (wire, §11.1) is converted to ByteRange (internal, UTF-8 bytes, I13) by the PositionConverter at ingress, and back at egress. A document's Utf16Index is built lazily, only when the negotiated encoding is utf-16 and only on first use, and is invalidated wholesale on every edit (cheap because it is rebuilt from the already-current LineIndex, §11.1).

8.4 Document synchronization model

textDocument/didOpen seeds a document at version 1 with full text. textDocument/didChange carries an ordered array of TextDocumentChangeEvent (§11.1) — each applied to the result of the previous one, per spec, never reordered (P4). textDocument/didSave raises durability Low → Medium (§11.4). textDocument/didClose removes the document; the on-disk version becomes authoritative for lsp-db inputs. A stale (version <= current) didChange is dropped (I5) — logged, not fatal.

Query Depends on Durability floor Invalidated by

8.6 Worked example — completion mid-edit

Source (cursor at │): let x: Vec<u32> = v.it│ — user typed it after .. CompletionContext (§11.11) resolves kind = DotAccess, prefix = "it", node = the smallest enclosing MethodCallExpr. The candidate generator asks type_context(region) for the type of v; if that query is still complete: false (cold workspace), the handler returns syntactic candidates only (iter, into_iter — string-matched against every method name in scope) with isIncomplete: true in the CompletionList, and the client re-requests on the next keystroke once the type-aware ranking (Iterator::next, etc.) is ready — P5 and P1 acting together.

8.7 Malformed-input example

Input: Content-Length: 99999999999\r\n\r\n{...}. The framing reader (§13.1) parses the header, compares against MAX_MESSAGE_BYTES (default 64 MiB, ADR-04 §9), and rejects with FrameError::TooLarge before allocating a body buffer — the defense against a "claim a 4 GiB body" resource-exhaustion attempt (T3, §22). The client sees a JSON-RPC -32700 ParseError with data.reason = "content-length exceeds maximum".

8.8 Failure-path example — cancellation mid-inference

A textDocument/completion request triggers type_context(region) for a 200-line function; 30 ms in, the user types another character, the client sends $/cancelRequest for the in-flight request ID. The dispatcher (§13.3) sets that ID's CancellationToken; the next db.check_cancelled() poll inside the unification loop (§17.1) observes it and raises Cancelled, which unwinds through every caller (I4) without writing a memo entry (so the next request recomputes cleanly). The dispatcher, having already registered the ID, sends {error: {code: -32800, message: "RequestCancelled"}} — never leaves the client hanging (FM-1, §23).

Design principles (§6)

  • P1 — Latency budgets are first-class types. Every request handler receives a Budget describing remaining time; the handler picks full vs. partial result, blocking vs. streaming, based on it. Default budgets: §4. Violating it: a handler that ignores its budget produces late=true responses that silently degrade perceived editor responsiveness with no telemetry signal to act on.
  • P2 — The database is the sole source of truth. No fact about the program lives outside lsp-db (§11.4). Handlers issue queries; they never cache derived results. Violating it: a handler-local cache is the single most common root cause of "stale after edit" bugs across every LSP that has shipped past the toy stage (§3.1).
  • P3 — Cancellation is cooperative and pervasive. Every query, handler, and parser pass polls a cancellation flag at defined boundaries (I4, §7). Tradeoff: cooperative cancellation cannot preempt a tight loop that forgets to poll; the conformance suite (§26) fuzzes cancel/re-request storms to catch this class.
  • P4 — Incremental sync is mandatory; there is one code path. Full- document sync is supported for weak clients, but internally it is reduced to one text-edit replacing the whole buffer, so lsp-db sees the same edit shape either way (§14). Violating it (two code paths) doubles the surface for sync bugs.
  • P5 — Partial information is reportable, never silently absent. A query that completes with degraded inputs returns its answer plus a partial marker (TypeContext.complete, §11.6); the handler, not the db, decides whether to send partial, withhold, or block. Violating it produces a confident wrong answer instead of an honest partial one (§8.6).
  • P6 — The CST is lossless and immutable; the AST and HIR are derived. Every byte — whitespace, comments, error tokens — has a home in the green tree (I6, §7); the AST is for syntactic queries, the HIR for name resolution/inference. Violating layering (e.g. mutating a tree in place) breaks structural sharing (I7) and every downstream memo.
  • P7 — One thread is the dispatcher; everything else is a worker. The transport reader, dispatcher, and response writer share a thread (I12, §7); lsp-db queries run on a fixed worker pool (ADR-02, §9). A handler that blocks synchronously on the dispatcher thread stalls every other request.
  • P8 — The semantic-token delta protocol is opt-in but preferred, and must be bit-stable. Re-running the delta computation on identical inputs must produce an identical delta (I10, §7); non-determinism here breaks the conformance suite's replay tests (§26).
  • P9 — Workspace edits are atomic from the client's perspective. A twelve-file rename produces one WorkspaceEdit with twelve TextDocumentEdit entries (I11, §7); the server never applies edits in stages. Apply-failure is the client's decision, not the server's.
  • P10 — File watching is the server's responsibility, with a polling fallback. Prefer client-side dynamic registration for workspace/didChangeWatchedFiles; fall back to notify (inotify/ FSEvents/ReadDirectoryChangesW) with polling for filesystems that support neither (network mounts, some Docker bind mounts).
  • P11 — The transport is loyal to the spec. Content-Length framing, no batching, case-sensitive method names, JSON-RPC 2.0 error codes only (§8.1). Non-conformant input is rejected with the matching error code, not a different response shape (§8.7).
  • P12 — Configuration is pulled when possible, pushed when not. Prefer workspace/configuration (server-initiated pull); fall back to workspace/didChangeConfiguration (client-initiated push) and cache the last snapshot; both paths converge on the same internal state.
  • P13 — Errors are structured and never silent; cancellations are never errors. Every error path returns a numeric JSON-RPC code, a human message, and an optional machine-actionable data field. A silent error path is a debugging dead end for the on-call engineer (§24).
  • P14 — Determinism is the default for everything except timing. A given (workspace state, request sequence) produces the same (response sequence, diagnostic sequence) across runs and hosts, modulo timing-dependent progress-update counts. This is the property that keeps the test suite (§26) honest.
  • P15 — Position encoding is normalized once, at the dispatcher boundary. Every internal type carries UTF-8 byte offsets (§11.1); the PositionConverter (§11.1) converts at the edge in both directions. Violating it — leaking UTF-16 offsets past the boundary — is the single most common LSP conformance bug across shipped servers (§8.3).
