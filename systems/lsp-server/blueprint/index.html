1. Goal & Scope

Build a Language Server Protocol (LSP 3.17) server in Rust for a statically-typed, module-and-import source language with a Rust-like surface grammar, exposing JSON-RPC 2.0 request/notification/response semantics over stdio or TCP, backed by a Salsa-style demand-driven incremental analysis database, so that every editor-facing query — completion, hover, diagnostics, go-to-definition, rename — performs only the recomputation its answer logically depends on, never a whole-workspace re-parse or re-typecheck per keystroke.

Phase-0 deliverable (crates, named per Repository Layout §10):

  1. lsp-transport — Content-Length framing + JSON-RPC 2.0 codec (stdio, TCP).
  2. lsp-types — wire-format structs mirroring the LSP 3.17 spec.
  3. lsp-dispatcher — method routing, request-ID → cancellation-token registry.
  4. lsp-lifecycle — initialize/initialized/shutdown/exit state machine.
  5. lsp-sync — full-document synchronization (incremental sync lands Phase 2, §14).
  6. lsp-trace — structured tracing wiring, stderr-only (stdout carries JSON-RPC).
  7. A stub textDocument/hover handler returning a fixed string — the walking skeleton that proves transport → dispatcher → handler → transport round-trips.

System boundaries.

  • Provides: transport, lifecycle, document sync, error-recovering parse, an incremental semantic index, the language features enumerated in §2, workspace multi-root handling, cancellation, and conformance verification against the LSP spec (§26).
  • Delegates: build-system integration (Cargo/Bazel/etc. dependency-graph resolution) to a pluggable WorkspaceLoader trait implemented per host language (§11.9); the server consumes whatever file set the loader reports and never resolves a build graph itself.
  • Does NOT provide: a debugger (DAP is a separate protocol), a build system, a package manager, an editor UI, or a compiler backend (codegen). This is the "answer questions about the program as currently typed" tier only.

Non-goals: sub-50 ms cold start on 5M-LOC workspaces (cold indexing is background work, §21.7); cross-language polyglot analysis in one process; a runtime plugin ABI for third-party analyzers (the crate boundaries in §10 are the extension points, not a dynamically-loaded plugin system).

Deployment model: single OS process per workspace, spawned by the editor over stdio (default) or attached via TCP for remote/container development (--socket <port>); no server-side persistence beyond an optional on-disk warm cache (PhaseDeferred("§9"), ADR-04).

Target users/operators: the language's tooling team builds and ships the server; every editor user of that language is the transitive end user. For §24 Operational Readiness, "operator" means the tooling team running CI conformance gates and triaging user-filed hangs/crashes.

What later phases unlock: Phase 0 (§12) unlocks a server that attaches to an editor and answers nothing useful yet; each phase through §21 unlocks one more feature surface, ending in a server with full incremental semantic tokens, code actions, cross-file rename, and a 30-day chaos-soaked cancellation path (§21.10).

Recommended language: Rust (stable, MSRV = current − 2 minor releases). Rationale: no GC pause on the hot completion path (P1, §6); a mature async runtime (Tokio, ADR-07 §9) with a clean dispatcher/worker-pool split; Send + Sync enforced structural sharing for the immutable green tree (§11.7); and rust-analyzer as a living reference implementation of every hard problem this blueprint solves. Rejected: OCaml — no mature async ecosystem for the dispatcher/worker split, though excellent for the compiler-writing half; C++ — memory-safety risk on a process that parses untrusted, adversarially shaped user input all day (the CVE class in §22); Go — GC pauses interact badly with the p99 latency budget in §4 (gopls documents fighting GC-pause tails); TypeScript/Node — the single-threaded event loop forecloses the worker-pool split (§11.7, ADR-02) short of a worker-threads rewrite; a defensible choice for tsserver's simpler design point (§31), not for this one.

Prerequisites (systems knowledge required before Phase 0): JSON-RPC 2.0; recursive-descent parsing and error recovery; the dispatcher/actor concurrency pattern; async Rust (Send, Future, cooperative vs drop-based cancellation); Hindley-Milner unification (§17).

Estimated timeline: Phase 0 — 1 week (1 engineer) / 3 days (2 engineers). Full system (§12–§21, 10 phases) — 7 months (2 engineers) to the point every Acceptance Criterion in §12–§21 passes and the 30-day chaos canary (§21.10) is green.

Deferred features (full register at §35): call hierarchy PhaseDeferred("§21"); type hierarchy PhaseDeferred("§21"); notebook-document sync PhaseDeferred("§11"); moniker PhaseDeferred("§21"); linked-editing-range PhaseDeferred("§21"); inline completion PhaseDeferred("§21"); SIMD JSON parsing PhaseDeferred("§9"); on-disk cross-session memoization cache PhaseDeferred("§9").

1.1 Editor agnosticism as a load-bearing property

LSP exists because N editors × M languages = N×M bespoke integrations does not scale; hard-coding one editor's quirks into this server would ship a plugin, not a language server. Every behavior is gated behind a capability the client advertises in InitializeParams.capabilities or the server advertises in ServerCapabilities (§11.10) — never assumed. Where a capability is absent, the server degrades gracefully: plain-text hover instead of Markdown, full-document push instead of semantic-token delta (§20), silent long operations instead of WorkDoneProgress (§21). The conformance suite (§21.2, §26) carries a fixture matrix for six client capability profiles — VSCode, Neovim built-in LSP, Emacs lsp-mode, Helix, Sublime LSP, Zed — and a fixture failing on any one of them is a failing build, not a known limitation.

2. Why Build This

  • Unique systems knowledge taught: demand-driven incremental computation (Salsa/Adapton-style query graphs) under adversarial, continuously mutating input — a harder version of "incremental build system," because the input changes every keystroke instead of every commit.
  • Why it matters architecturally/historically: LSP (2016, Microsoft) solved the N-editors × M-languages tooling problem the way LLVM solved N-frontends × M-backends — by fixing a protocol boundary. Every serious language's tooling story since 2018 (rust-analyzer, gopls, clangd, pyright, tsserver-as-LSP) is a variation on this blueprint's architecture (§31).
  • Engineering muscles built: cooperative cancellation under load; lossless parsing with structural sharing; demand-driven memoization with correct invalidation; conformance testing against a normative spec instead of a vague requirements doc; latency-budgeted API design (§4).
  • Cross-links to sibling systems (by name): the query-graph engine is the same shape as an incremental build system's action graph (Bazel, Buck2/dice — §31); the cancellation model is the same shape as a database's statement-timeout machinery; the wire transport is the same shape as any JSON-RPC microservice, minus batching (§8.1).
  • Calibration value: an engineer who ships this system can judge, for any "respond to a UI event with a computed answer over mutable state" problem, whether a cache-of-objects design or a query-database design is the right call — the single most transferable judgment in this domain.

What Mastery Looks Like (competencies gained, each tied to a phase):

  1. Design a wire-protocol dispatcher with cooperative cancellation that never leaks a running computation past its cancellation point — Phase 1 (§13).
  2. Build a lossless, error-recovering CST with red/green structural sharing and prove byte-exact round-trip — Phase 3 (§15).
  3. Build a demand-driven query database with revision-based invalidation and durability-gated early-exit — Phase 4 (§16).
  4. Reason about cross-file name resolution and on-demand type inference as independent, cacheable, dependency-tracked regions — Phase 5 (§17).
  5. Design a latency-budgeted, partial-result-capable handler for a feature whose "correct" answer is itself time-varying (completion) — Phase 7 (§19).
  6. Implement the semantic-tokens delta protocol and prove bit-stability — Phase 8 (§20).
  7. Run a workspace-scale conformance and chaos harness certifying the cancellation and multi-root invariants under adversarial timing — Phase 9 (§21).
  8. Explain, with numbers, why a packages-graph (gopls), a preamble-split (clangd), and a query-graph (rust-analyzer, this design) architecture diverge, and which regime favors each — §31.

lsp-transport: owns the byte stream; enforces MAX_MESSAGE_BYTES before any deserialization (§8.7); the only crate allowed to touch stdout.

lsp-dispatcher: the single re-entrancy boundary (I12, §7); every request's RequestId is registered before the handler is spawned, so $/cancelRequest can always find it.

lsp-lifecycle: enforces the handshake state machine (§8.2); any request outside its legal state is rejected, never silently accepted.

Feature handlers: stateless — they issue lsp-db queries and shape the response; no handler caches a derived fact itself (P2, §6).

lsp-db: the single source of truth for every fact about the user's program (P2); revision counter is the server's global clock (I1, §7).

Sync + analysis pipeline: one-way — parse → resolve → infer → diagnose; each stage is an independent, memoized query (§16), so an edit that does not touch name resolution never re-runs inference.

lsp-workspace: resolves multi-root layout and file-watch events into lsp-db input changes; never queries lsp-db directly for facts, only feeds it.

lsp-progress: cross-cutting — every long-running handler registers with it before starting real work.

Three properties hold everywhere else in this document. First, the request data path is one-way: transport → dispatcher → handler → db (query, possibly streaming partial results) → serialize → transport; handlers never reach into the transport, the db never reaches into a handler. Second, lsp-db's revision counter (I1) is the only global clock; there is no second cache holding an older view of a fact. Third, cancellation is cooperative and propagates through the query graph (I4): a cancelled query unwinds, and every query that consumed its (now-unwound) result unwinds too — no orphaned computation survives past a request's cancellation point (verified by the conformance suite, §26).

3.1 Why a query database, not a graph of cached objects

Every production LSP past the toy stage hits the same wall: a feature works in isolation, then breaks under interactive editing because something cached a handle to a derived object and the handle now points at a stale tree. The fix is to stop holding derived objects and hold keys into a query database that re-derives on demand (P2). The cost is a query call per access; the benefit is every access sees a view of the world consistent with the revision the request started at. rust-analyzer, gopls, and Roslyn all pay this cost; the literature (§5) is unanimous that the alternative does not survive contact with real interactive editing.

3.2 Why an error-recovering CST, not a bail-on-error AST

A parser that stops at the first syntax error gives a correct tree only when the user has stopped typing — roughly never, mid-edit. An error-recovering CST that reports errors as tree nodes (§8, I6) gives a tree at every keystroke; the recovery logic is harder to write, but "features that work mid-edit" is the entire reason this server exists — partial-information correctness (P5, §6) is load-bearing throughout, formalized as the complete flag in TypeContext (§11.6).

6. Design Principles

  1. P1 — Latency budgets are first-class types. Every request handler receives a Budget describing remaining time; the handler picks full vs. partial result, blocking vs. streaming, based on it. Default budgets: §4. Violating it: a handler that ignores its budget produces late=true responses that silently degrade perceived editor responsiveness with no telemetry signal to act on.
  2. P2 — The database is the sole source of truth. No fact about the program lives outside lsp-db (§11.4). Handlers issue queries; they never cache derived results. Violating it: a handler-local cache is the single most common root cause of "stale after edit" bugs across every LSP that has shipped past the toy stage (§3.1).
  3. P3 — Cancellation is cooperative and pervasive. Every query, handler, and parser pass polls a cancellation flag at defined boundaries (I4, §7). Tradeoff: cooperative cancellation cannot preempt a tight loop that forgets to poll; the conformance suite (§26) fuzzes cancel/re-request storms to catch this class.
  4. P4 — Incremental sync is mandatory; there is one code path. Full- document sync is supported for weak clients, but internally it is reduced to one text-edit replacing the whole buffer, so lsp-db sees the same edit shape either way (§14). Violating it (two code paths) doubles the surface for sync bugs.
  5. P5 — Partial information is reportable, never silently absent. A query that completes with degraded inputs returns its answer plus a partial marker (TypeContext.complete, §11.6); the handler, not the db, decides whether to send partial, withhold, or block. Violating it produces a confident wrong answer instead of an honest partial one (§8.6).
  6. P6 — The CST is lossless and immutable; the AST and HIR are derived. Every byte — whitespace, comments, error tokens — has a home in the green tree (I6, §7); the AST is for syntactic queries, the HIR for name resolution/inference. Violating layering (e.g. mutating a tree in place) breaks structural sharing (I7) and every downstream memo.
  7. P7 — One thread is the dispatcher; everything else is a worker. The transport reader, dispatcher, and response writer share a thread (I12, §7); lsp-db queries run on a fixed worker pool (ADR-02, §9). A handler that blocks synchronously on the dispatcher thread stalls every other request.
  8. P8 — The semantic-token delta protocol is opt-in but preferred, and must be bit-stable. Re-running the delta computation on identical inputs must produce an identical delta (I10, §7); non-determinism here breaks the conformance suite's replay tests (§26).
  9. P9 — Workspace edits are atomic from the client's perspective. A twelve-file rename produces one WorkspaceEdit with twelve TextDocumentEdit entries (I11, §7); the server never applies edits in stages. Apply-failure is the client's decision, not the server's.
  10. P10 — File watching is the server's responsibility, with a polling fallback. Prefer client-side dynamic registration for workspace/didChangeWatchedFiles; fall back to notify (inotify/ FSEvents/ReadDirectoryChangesW) with polling for filesystems that support neither (network mounts, some Docker bind mounts).
  11. P11 — The transport is loyal to the spec. Content-Length framing, no batching, case-sensitive method names, JSON-RPC 2.0 error codes only (§8.1). Non-conformant input is rejected with the matching error code, not a different response shape (§8.7).
  12. P12 — Configuration is pulled when possible, pushed when not. Prefer workspace/configuration (server-initiated pull); fall back to workspace/didChangeConfiguration (client-initiated push) and cache the last snapshot; both paths converge on the same internal state.
  13. P13 — Errors are structured and never silent; cancellations are never errors. Every error path returns a numeric JSON-RPC code, a human message, and an optional machine-actionable data field. A silent error path is a debugging dead end for the on-call engineer (§24).
  14. P14 — Determinism is the default for everything except timing. A given (workspace state, request sequence) produces the same (response sequence, diagnostic sequence) across runs and hosts, modulo timing-dependent progress-update counts. This is the property that keeps the test suite (§26) honest.
  15. P15 — Position encoding is normalized once, at the dispatcher boundary. Every internal type carries UTF-8 byte offsets (§11.1); the PositionConverter (§11.1) converts at the edge in both directions. Violating it — leaking UTF-16 offsets past the boundary — is the single most common LSP conformance bug across shipped servers (§8.3).

8. Domain Model / Protocol

8.1 Wire message grammar

JSON-RPC 2.0 over Content-Length framing (LSP 3.17 §Base Protocol):

Message   ::= Header+ CRLF Body
Header    ::= "Content-Length:" DIGIT+ CRLF
            | "Content-Type:" TOKEN CRLF        (optional, tolerated on read)
Body      ::= JSON-RPC-Object                    (exactly Content-Length bytes)

JSON-RPC-Object ::= Request | Response | Notification
Request      ::= { jsonrpc: "2.0", id: RequestId, method: String, params?: Value }
Notification ::= { jsonrpc: "2.0",                method: String, params?: Value }
Response     ::= { jsonrpc: "2.0", id: RequestId, (result: Value | error: ErrorObj) }
ErrorObj     ::= { code: Int, message: String, data?: Value }
RequestId    ::= Int | String                     (LSP never uses null)

No batching (LSP 3.17 forbids the JSON-RPC batch-array form, P11). Method names beginning $/ are implementation-defined and MAY be dropped without error (e.g. $/cancelRequest, $/progress).

8.2 Request/notification lifecycle state machine

WaitingForInitialize --initialize(params)--> Initialized --capabilities-->
Initialized --initialized()--> Running
Running --shutdown()--> ShuttingDown --null-->
ShuttingDown --exit()--> Terminated(code=0)
any --exit() while not ShuttingDown--> Terminated(code=1)
any state, any request before Running (except initialize) --> error -32002

Illegal transitions are rejected with -32002 ServerNotInitialized (pre- handshake) or -32600 InvalidRequest (post-shutdown protocol violation); see FM-2 (§23).

8.3 Position encoding

LSP 3.17 negotiates PositionEncodingKind (utf-8 | utf-16 | utf-32) in initialize; default is utf-16 for backward compatibility. Internally every Position (wire, §11.1) is converted to ByteRange (internal, UTF-8 bytes, I13) by the PositionConverter at ingress, and back at egress. A document's Utf16Index is built lazily, only when the negotiated encoding is utf-16 and only on first use, and is invalidated wholesale on every edit (cheap because it is rebuilt from the already-current LineIndex, §11.1).

8.4 Document synchronization model

textDocument/didOpen seeds a document at version 1 with full text. textDocument/didChange carries an ordered array of TextDocumentChangeEvent (§11.1) — each applied to the result of the previous one, per spec, never reordered (P4). textDocument/didSave raises durability Low → Medium (§11.4). textDocument/didClose removes the document; the on-disk version becomes authoritative for lsp-db inputs. A stale (version <= current) didChange is dropped (I5) — logged, not fatal.

8.6 Worked example — completion mid-edit

Source (cursor at │): let x: Vec<u32> = v.it│ — user typed it after .. CompletionContext (§11.11) resolves kind = DotAccess, prefix = "it", node = the smallest enclosing MethodCallExpr. The candidate generator asks type_context(region) for the type of v; if that query is still complete: false (cold workspace), the handler returns syntactic candidates only (iter, into_iter — string-matched against every method name in scope) with isIncomplete: true in the CompletionList, and the client re-requests on the next keystroke once the type-aware ranking (Iterator::next, etc.) is ready — P5 and P1 acting together.

8.7 Malformed-input example

Input: Content-Length: 99999999999\r\n\r\n{...}. The framing reader (§13.1) parses the header, compares against MAX_MESSAGE_BYTES (default 64 MiB, ADR-04 §9), and rejects with FrameError::TooLarge before allocating a body buffer — the defense against a "claim a 4 GiB body" resource-exhaustion attempt (T3, §22). The client sees a JSON-RPC -32700 ParseError with data.reason = "content-length exceeds maximum".

8.8 Failure-path example — cancellation mid-inference

A textDocument/completion request triggers type_context(region) for a 200-line function; 30 ms in, the user types another character, the client sends $/cancelRequest for the in-flight request ID. The dispatcher (§13.3) sets that ID's CancellationToken; the next db.check_cancelled() poll inside the unification loop (§17.1) observes it and raises Cancelled, which unwinds through every caller (I4) without writing a memo entry (so the next request recomputes cleanly). The dispatcher, having already registered the ID, sends {error: {code: -32800, message: "RequestCancelled"}} — never leaves the client hanging (FM-1, §23).

12. Phase 0 — Foundations & Correctness Kernel

12.1 Objectives

Stand up the repo skeleton (§10) and the correctness kernel: every crate compiles, CI runs, the snapshot/conformance-fixture test patterns exist, and logging is wired so no future phase can accidentally corrupt stdout (P11). No LSP behavior yet — this phase is the scaffold everything else builds on.

12.2 Detailed Implementation Steps

Initialize the Cargo workspace exactly per §10's tree; every crate gets an empty lib.rs and a Cargo.toml listing only its direct dependencies (ADR-02). Pin rust-toolchain.toml (MSRV, ADR-01), rustfmt.toml, clippy.toml (clippy::print_stdout deny, enforcing P11's "transport owns stdout"), deny.toml (ADR-03). Wire tracing + tracing-subscriber in lsp-trace (ADR-17) to stderr only, env-configurable (LSP_LOG=debug,lsp_db=trace). Establish the insta-snapshot pattern (ADR-19) and the conformance-fixture directory convention tests/conformance/<feature>/<scenario>/{requests, expected}.jsonl that every later phase's N.5 fixtures live under. Stand up CI workflow skeletons (§10, .github/workflows/) running an empty cargo check per crate.

12.3 Deliverable

A clean-clone cargo check --all-targets that passes, a green no-op CI run, and one passing snapshot test: a stub handler returning ServerCapabilities::default().

12.4 Acceptance Criteria

cargo check --all-targets completes in < 90 s cold, < 5 s incremental (single-file edit) on the reference CI runner (§4). CI workflow ci.yml passes on a no-op PR. Fixture tests/conformance/lifecycle/stub_capabilities/ passes with insta snapshot match.

12.5 Conformance Fixtures

stub_capabilities/requests.jsonl — one initialize request; expected.jsonl — response with Default::default() capabilities. malformed_workspace_root/ — initialize with a non-existent rootUri; expected: InitializeResult still returns (server does not fail workspace resolution at this phase).

12.6 Pitfalls

Letting the workspace collapse to one crate "for now" (§10's crate split is the compile-time isolation unit — retrofitting it later is a multi-week rewrite). Defaulting to tokio = { features = ["full"] } (pulls the entire runtime; enable only rt, io-util, macros, sync per ADR-07). A stray println! anywhere corrupting the JSON-RPC stream on stdout (P11) — caught only if the clippy deny-lint is wired in this phase, not later.

12.7 Performance Concerns

Compile-time is the only "performance" concern in Phase 0: serde-derive macros on large wire-format structs (lsp-types) are the typical culprit for slow cold cargo check; feature-gate derives consumers don't need.

12.8 Edge Cases

A crate with a circular dev-dependency (test-only) breaking cargo check. A CI runner with a cold cargo registry cache exceeding the 90 s budget — mitigated by caching ~/.cargo/registry in CI (§27).

12.9 Failure Analysis

A broken crate split (a high-churn crate depended on by everything) makes every subsequent phase's incremental builds slow — the symptom shows up as a regression in the Phase 0 build-time acceptance criterion re-run in every later phase's CI, so it is caught, not silent.

12.10 Operational Notes

LSP_LOG is the one operational knob this phase introduces; document it in docs/runbooks/logging.md. No deployment yet — Phase 0 ships nothing an operator runs in production.

13. Phase 1 — Transport & Lifecycle

13.1 Objectives

Implement the JSON-RPC 2.0 / Content-Length transport (§8.1) over stdio and TCP, the dispatcher's request routing and cancellation registry, and the initialize/initialized/shutdown/exit handshake state machine (§8.2). End state: a client can attach, negotiate capabilities, and cleanly detach.

13.2 Detailed Implementation Steps

lsp-transport::framing implements read_message/write_message per the grammar in §8.1, enforcing MAX_MESSAGE_BYTES (ADR-05 §9's serialization choice; the size check is independent of the JSON library) before any deserialization (P11, malformed-input example §8.7). lsp-transport::jsonrpc parses/serializes Message by structural inspection (id+method → Request; id+result-xor-error → Response; method-only → Notification). lsp-dispatcher implements the single-thread dispatch loop (P7, I12): on Request, register RequestId → CancellationToken in requests_in_flight (§11.11) before spawning the handler onto the worker pool (ADR-07, ADR-13), so a $/cancelRequest racing the spawn cannot miss it. lsp-lifecycle implements the state machine of §8.2 as an AtomicU8 with compare_exchange transitions; illegal transitions return the matching JSON-RPC error code.

13.3 Deliverable

A server binary that: accepts stdio or --socket <port> TCP, completes the full handshake against the vscode-languageclient reference client, and responds -32800 RequestCancelled to a cancelled in-flight request.

13.4 Acceptance Criteria

10,000 random valid LSP messages round-trip through framing byte-exact (I6 is not yet in scope but the framing round-trip is analogous and tested here). A malformed header (missing Content-Length, non-numeric, truncated body) is rejected with -32700 ParseError. An oversized message (> MAX_MESSAGE_BYTES, default 64 MiB) is rejected without allocating the body (§8.7). Handshake round-trip completes in < 100 ms p99 cold start (§4). A cancel/re-request fuzz run of 10,000 pairs (lsp-fuzz, ADR-20) leaves zero orphaned worker threads (I4).

13.5 Conformance Fixtures

transport/oversized_content_length/ — header claims 4 GiB; expected: -32700 before body read. transport/multibyte_utf8_body/ — a message whose body contains multi-byte UTF-8 near the Content-Length boundary; expected: byte-exact parse. lifecycle/double_initialize/ — two initialize requests; expected: second rejected -32600. lifecycle/premature_shutdown_second/ — two shutdown calls; expected: second rejected.

13.6 Pitfalls

Reading Content-Length as characters instead of bytes (multi-byte clients miscount otherwise, P11). Forgetting to flush the buffered writer after every message — the most common cause of "the server seems to hang" (§13.2). Sending a notification before initialized is received — the spec forbids it (§8.2). Not tracking processId and leaving an orphan server running a long inference after the editor crashes (I12's stall detection helps here too).

13.7 Performance Concerns

Framing throughput target ≥ 1 GiB/s single-core (10 MiB stream of small messages, §28 M-table). Per-message overhead < 5 µs at framing, < 50 µs at JSON-parse for messages < 4 KiB. Dispatcher routing is O(1) — a hashmap lookup keyed by method string (I12 depends on this staying true; a linear scan here would itself become a latency-budget violation, P1).

13.8 Edge Cases

A TCP second-connection attempt while one is active — rejected (LSP's one-editor-per-server model). A client that sends exit without shutdown — exit code 1 per spec (§8.2). A half-written message from a panicking writer task — caught, logged, server shuts down cleanly rather than continuing half-broken (FM-1, §23).

13.9 Failure Analysis

A stuck reader (peer closed the stream, reader hasn't noticed) is detected via TCP keepalive (TCP mode) or the exit-notification contract (stdio mode, no OS-level signal available) — see FM-1 (§23) for the full recovery path. Blast radius is one server process; the editor's own auto-restart is the operator-visible recovery.

13.10 Operational Notes

LSP_LOG=transport=trace logs every received/sent message; the tracing span hierarchy is transport → message → request_id. A tshark capture (TCP) or a fake-stdio test harness (stdio) is the ground-truth debugging tool when a client report doesn't match server-side logs.

14. Phase 2 — Document Synchronization

14.1 Objectives

Track every open document's text, version, and position-encoding indices (§8.4, §11.2). Apply incremental and full-document edits through one code path (P4, ADR-11). Detect stale/out-of-order edits (I5).

14.2 Detailed Implementation Steps

lsp-sync maintains the open-document map (FileId → TextDocument, §11.2). textDocument/didOpen inserts at version 1. textDocument/didChange reduces its contentChanges array to a sequence of internal TextEdits applied in array order (never reordered, P4) — a Full variant is itself reduced to one edit spanning the whole buffer so the applier has exactly one code path regardless of client capability. The applier (named algorithm: "sequential range-splice") rebuilds Arc<String> + Arc<LineIndex> per edit and drops Utf16Index for lazy rebuild (§8.3, §11.1). textDocument/didSave raises durability Low→Medium (§11.4, ADR-04's durability model). textDocument/ didClose removes the document; lsp-db's source_text input reverts to on-disk truth. Every applied edit increments AnalysisDb.revision (I1) — this is the sync layer's sole write into lsp-db.

14.3 Deliverable

An edit sequence (didOpen, didChange ×100, didSave, didClose) on a 10,000-line file produces state identical whether driven incrementally or via full-document replacement.

14.4 Acceptance Criteria

Single-character incremental edit: < 10 µs end-to-end (notification parse → applier → revision bump, §4). 1000-line full-document didOpen: < 5 ms. A stale didChange (version <= current, I5) is rejected and logged, never applied. UTF-8/UTF-16/UTF-32 position encodings converge to the same internal byte-offset state after a multi-byte-character edit (fixture below).

14.5 Conformance Fixtures

sync/multi_edit_nonoverlapping/ — a didChange with edits at three non-overlapping ranges; expected: all three applied in array order. sync/stale_version_rejected/ — a didChange with version < current; expected: dropped, current text unchanged. sync/emoji_utf16_boundary/ — an edit adjacent to a 4-byte-UTF-8/2-UTF-16-unit emoji; expected: identical byte-offset result across all three negotiated encodings.

14.6 Pitfalls

Applying array edits out of order (spec is explicit: each applies to the post-previous-edit state, P4). Computing a byte range against a stale LineIndex version when a prior edit in the same array deleted a line. Forgetting to invalidate Utf16Index after an edit — silently wrong positions on files with multi-byte characters (caught by the emoji fixture).

14.7 Performance Concerns

LineIndex build is O(text length) with a SIMD-accelerated newline scan on large files (§28). The incremental path must stay the hot path; full-document resync is the deliberately slow path (ADR-11) and is never on the p99 completion budget (§4).

14.8 Edge Cases

A 4 GiB document open attempt — rejected by a configurable max-document-size cap (default 256 MiB, §4). An edit that would produce invalid UTF-8 — should be impossible per spec guarantee, but validated post-apply; a violation marks the document corrupt rather than panicking (FM-4, §23). A race between didOpen and an in-flight initialize — structurally impossible because the dispatcher serializes lifecycle before sync messages (§13.2), but covered by a regression fixture anyway.

14.9 Failure Analysis

An out-of-memory condition on a pathologically large document is bounded by the max-document-size cap; detection is immediate (open rejected), recovery is client-visible (-32602 InvalidParams with a data.reason). A corrupted document (post-edit UTF-8 validation failure) is quarantined — the document is marked corrupt, no further edits are applied, and diagnostics report a server-internal error rather than analyzing garbage.

14.10 Operational Notes

The applier emits a tracing::trace! per applied edit with before/after byte ranges; LineIndex has a Debug impl printing its line→byte table, the primary debugging aid when "the edit landed on the wrong line" is reported.

15. Phase 3 — Error-Recovering Parser & CST

15.1 Objectives

Parse document text into a lossless concrete syntax tree (I6, P6). Recover from syntax errors via ERROR nodes rather than aborting (Wagner & Graham 1989-family recovery strategies, §5). Share unchanged subtrees across edits via green-node interning (I7).

15.2 Detailed Implementation Steps

lsp-syntax implements a hand-written recursive-descent parser (ADR-10) as a sequence of per-production functions over a Parser holding a token stream, position, and event buffer; start()/complete() bracket node events, and a tree builder consumes the event buffer into GreenNodes (§11.5). On a parse error, the parser (named algorithm: "panic-mode synchronization," Wagner & Graham 1998, §5) emits an ERROR node over the offending tokens, skips to a per-grammar-rule synchronization point (statement boundary, closing brace, or top-level-item start), and resumes — every recovery branch must consume ≥ 1 token or hit a definite terminator (else I4-adjacent: an infinite recovery loop, §15.6). The lexer is itself error-recovering: an unterminated string literal yields a token flagged error: true, not a lex failure. Green nodes are interned (identical (kind, children) → identical Arc, I7) rather than built via specialized reparse-diffing — simpler to implement correctly, at the cost of a full re-parse per edit (Phase 3 tradeoff; true incremental re-parse is PhaseDeferred("§15"), revisited only if §28 benchmarks demand it). syntax_tree(file: FileId) is wired as an lsp-db query (§16) whose only dependency is source_text(file) (P2).

15.3 Deliverable

syntax_tree(file) returns a SyntaxNode for any input, including adversarial or empty input, without panicking; a --dump-tree CLI flag prints it.

15.4 Acceptance Criteria

Byte-exact round-trip (I6) on any input, verified over a 10,000-file fuzzed corpus. A curated 1,000-file corpus parses with zero panics. Green-tree share ratio on single-character edits > 95% (I7, §4's memory-amplification budget depends on this). A 10,000-line file parses in < 50 ms single-core (§4).

15.5 Conformance Fixtures

parser/roundtrip_corpus_10k/ — fuzzed inputs, byte-exact round-trip required. parser/unterminated_string/ — malformed input; expected: one ERROR token, parse continues. parser/deeply_nested_parens_1000/ — pathological input; expected: ERROR node at the recursion-limit cut point (default limit 256), no stack overflow. parser/share_ratio_benchmark/ — representative single-character edits; expected: share ratio > 0.95.

15.6 Pitfalls

A parser that panics on adversarial bytes (an assert! in the parser body is a CVE-class bug, T2 §22) — the fuzz corpus above exists specifically to catch this. A recovery rule that doesn't consume a token, looping forever (I4-style non-termination, distinct from cancellation but caught the same way: a watchdog timeout in the fuzz harness). Whitespace/comment attachment rules that misattach trailing vs. leading trivia — subtle and load-bearing for formatting (§20) and rename (§20).

15.7 Performance Concerns

Full re-parse-per-edit (this phase's chosen tradeoff) costs ~50 ms on a 10,000-line file even for a one-character edit — identical to a cold parse; this is acceptable only because green-node interning still gives structural sharing for downstream query invalidation (I3) even though the parser itself redoes the work. If profiling under §28 shows this dominating the completion p99 budget (§4), the deferred true-incremental reparse is triggered.

15.8 Edge Cases

Tokens that would span a UTF-8 codepoint boundary — forbidden by construction (lexer only emits boundaries at codepoint starts). A grammar production whose synchronization point is itself inside a string literal — resolved by lexing before synchronizing, never re-lexing raw bytes. An empty file — parses to an empty root node, not an error.

15.9 Failure Analysis

A grammar bug (wrong tree shape for a valid input) is caught by the 100-file hand-curated snapshot suite (insta, ADR-19) before it reaches the fuzzed corpus; fixed via an ADR amendment + a permanent regression fixture. A parser stack overflow on pathological nesting is prevented, not merely detected, by the recursion-limit cut (§15.5) — the failure mode is graceful (ERROR node), not a process crash.

15.10 Operational Notes

--dump-tree <file> and a pre-tree-construction event-stream dump are the two CLI debugging aids; tracing spans separate lex/parse/tree-build phases so a performance regression can be attributed to the right stage.

16. Phase 4 — Incremental Analysis Database

16.1 Objectives

Implement lsp-db (§11.4): memoized queries, tracked dependencies (I3), revision-based invalidation (I1, I2), durability-gated early exit, and cooperative cancellation propagation (I4) through the query graph (Pugh 1989; Acar/Blume/Harper 2006; Matsakis et al. Salsa design notes — all §5).

16.2 Detailed Implementation Steps

Every derived fact is a Query (§11.4 trait) memoized by (TypeId, key) in a DashMap (ADR-09). While execute runs, a thread-local "current query" stack records every nested db.query(...) call as a dependency edge (I3) — the mechanism Salsa calls dependency tracking (§5). Each MemoEntry records computed_at and verified_at revisions (I2); the early-cutoff rule (rust-analyzer's central optimization, §5) is: if verified_at == current_revision, return memoized; else walk deps, and if every dep is itself verified-fresh (or provably unchanged since computed_at), bump verified_at and return memoized without re-running execute — only a genuinely changed dependency triggers recompute. Durability (Low/Medium/High, §11.4, ADR-04's storage-adjacent model) lets the verification walk short-circuit: a query depending only on High-durability inputs need not be re-walked on every Low-durability (in-edit) change (P2 in service of P1). Cancellation (P3, I4): every query call polls db.cancel at entry and at every nested db.query call; a cancelled query raises a Cancelled unwind, caught by the top-level handler, which responds -32800 (§8.8's worked failure path) — no memo entry is written for a cancelled execution. A periodic sweep (every 100 revisions) evicts memo entries with verified_at < current_revision − 10,000 to bound table growth (§16.9).

16.3 Deliverable

AnalysisDb with dump_graph (DOT-format dependency-graph export) and a --trace-queries flag reporting memo-hit / verify-hit / recompute per request.

16.4 Acceptance Criteria

A stable-dependency query's second call is a verify-hit, not a recompute (unit test, memo-hit ratio ≥ 0.9 under a synthetic edit-replay workload, §28 M-table). A changed-dependency query's second call recomputes (unit test). A cancelled query leaves zero memo entries (property test, 10,000 cancel/re-request pairs, I4). A logical cycle (query A → B → A) is detected via the thread-local stack and resolved by the query's on_cycle recovery callback, never a stack overflow.

16.5 Conformance Fixtures

db/early_cutoff_verify_hit/ — two calls, unchanged dep; expected: verified_at bump only, no execute re-run. db/cycle_recovery/ — mutually recursive queries; expected: on_cycle value returned, no panic. db/cancel_no_memo_leak/ — 10,000 cancel/re-request pairs; expected: memo table size bounded, check_cancelled observed at every nested call. db/sweep_bounds_table_growth/ — 20,000 synthetic revisions; expected: memo table size plateaus after the sweep threshold.

16.6 Pitfalls

A query that is non-deterministic (HashMap iteration order, Instant::now() inside execute) breaks the memoization contract — two calls with the same key must return the same value; clippy lints catch the common cases, but the contract itself is enforced only by discipline plus the determinism property (P14, §6). Holding a query result across a cancellation-check point when the result type contains a reference into lsp-db internals (clone aggressively instead, per §6 P2's stateless-handler discipline). Unbounded memo growth if the sweep is disabled or mistuned (§16.9's failure mode).

16.7 Performance Concerns

Memo lookup < 200 ns (fast-hasher DashMap, §28 M-table). Verify-path cost is O(deps) hashmap lookups — the early-cutoff rule means this is rarely the long pole versus a full recompute. Recompute cost is dominated by the query's own body; db overhead per query call is < 1 µs (§4, §28).

16.8 Edge Cases

A query whose dependency set is empty (a pure input read) — trivially always verify-hit unless the input itself changed. A dependency cycle with no on_cycle handler registered — this is a server bug (not a user-triggerable condition), and is a panic by design, distinct from the recoverable cycle case (§16.4). A revision counter overflow at u64::MAX — deferred as practically unreachable (§4's scaling assumption; would require ~5×10^11 years of edits at the fastest observed edit rate to overflow).

16.9 Failure Analysis

Cancellation during a critical in-flight query propagates cleanly (I4); the request returns RequestCancelled, and the next request triggers a fresh recompute — expected, not a failure. Stale memo entries after a long session are bounded by the periodic sweep (§16.2); if the sweep is misconfigured (interval too long), symptom is unbounded RSS growth over a multi-hour session, detected via the db_memo_table_size gauge (§24) crossing an alerting threshold.

16.10 Operational Notes

LSP_LOG=lsp_db=trace logs every query enter/exit tagged memo-hit / verify- hit / recompute; dump_graph renders the live dependency graph via graphviz for debugging "why did this recompute" reports; db_memo_hit_ratio and db_memo_table_size are the two dashboard metrics an operator watches (§24).

17. Phase 5 — Name Resolution & Type Inference

17.1 Objectives

For every identifier reference, determine its declaration (lexical scopes, modules, imports, glob handling) via lsp-nameres; for every typeable expression, compute its inferred type on demand via lsp-types-inference (Hindley-Milner-style, Pierce ch. 22, §5), both as independent, cacheable, per-region lsp-db queries (§8.5).

17.2 Detailed Implementation Steps

scope_tree(file) builds a scope tree (Appel's symbol-table model, §5) whose lookup algorithm walks declarations, then imports, then the parent scope (textbook lexical scoping). module_exports(module) computes a module's public declaration set; resolve_reference(ref) depends on the referencing file's scope_tree and every module_exports in the import chain (§8.5) — a change to a foreign module's source invalidates its module_exports, which transitively invalidates every resolution that crossed into it (I3). Type inference operates per-region (function body, top-level expression, const initializer): type_context(region) walks the AST assigning a type variable per subexpression, collects constraints from operators/calls/ control-flow, and solves by unification (Pierce ch. 22); cross-region references consult a declared type if annotated, else the other region's inferred type, forming a cross-region dependency edge tracked the same way as any other lsp-db dependency (I3). A cyclic cross-region dependency (mutual recursion with both return types inferred) is resolved via chaotic-iteration widening (Bourdoncle 1993, §5) or, failing convergence, requires an explicit annotation and reports a typed cycle error. Partial inference (P5): an unresolved dependency yields a ? placeholder, TypeContext.complete = false propagates to every consumer (§11.6).

17.3 Deliverable

For a 100-file hand-curated corpus with known reference→declaration and expression→type ground truth, both resolve_reference and type_context match ground truth exactly.

17.4 Acceptance Criteria

Per-reference resolution < 5 µs after warm-up (memoized, §4). Per-file scope- tree construction < 5 ms for a 1,000-line file. A 100-line function's cold inference completes < 10 ms, < 1 ms memoized (§28 M-table). Cross-file: an edit to a declaration in file A causes a hover in file B (§19) to reflect the new type on the next request — verified by fixture, not asserted.

17.5 Conformance Fixtures

nameres/glob_import_ambiguity/ — two glob imports exporting the same name; expected: resolution follows the host language's documented precedence rule. nameres/cyclic_module_imports/ — module A imports B imports A; expected: on_cycle returns an empty partial exports set, no panic (mirrors I3's cycle-recovery contract from §16). typeinfer/mutual_recursion_cycle/ — two functions with inferred return types calling each other; expected: a typed cycle diagnostic naming both functions. typeinfer/cross_file_type_change/ — edit a declaration's type in file A; expected: file B's dependent hover result changes on next query.

17.6 Pitfalls

Glob-import ordering ambiguity resolved inconsistently with the host language's own rule (§17.2). Shadowing within a single scope (let x = 1; let x = 2;) returning the wrong (non-most-recent) declaration. Inference that explodes exponentially on nested conditionals without collect-then-solve staging (Pierce's warning, §5) — the constraint-collection pass must complete before unification starts, never interleaved per-branch. Type interning omitted, making equality structural instead of pointer-comparison (a TypeId-per-distinct-type table is mandatory, §11.6).

17.7 Performance Concerns

Cross-file invalidation cost is bounded by the reverse-import count of the changed file (§4's O(open files) scaling assumption depends on the workspace symbol index, §21, keeping this bounded). A 1,000-function workspace's cold inference runs in the background worker pool (ADR-13) in < 60 s total, never blocking the request-serving path (P1).

17.8 Edge Cases

A reference resolving to a declaration the parser emitted as an ERROR node — treated as unresolved, not a crash (P6 CST-error-as-node paying off here). A module whose parse errors are severe enough that its exports can't be computed — exports map is partial; downstream resolutions see an empty set (P5). Conditional/cfg-gated imports — the import set becomes a function of configuration, and the lsp-db query key includes the configuration value.

17.9 Failure Analysis

An unresolvable constraint system (Type mismatch with no valid substitution) is reported as a typed diagnostic naming the conflicting types and their spans — not silently dropped. An unbounded constraint (infinite type, e.g. x = [x] without a recursive-type feature) is caught by an occurs-check in the unifier before it can loop forever.

17.10 Operational Notes

--dump-resolves <file> prints every reference's resolution; --dump-types <file> prints every expression's inferred type; tracing spans separate constraint-collection from unification so a slow-inference report can be attributed to the right phase.

18. Phase 6 — Diagnostics Pipeline

18.1 Objectives

Compute diagnostics (lsp-diagnostics) from the parse/resolve/infer pipeline (§8.5) and publish via textDocument/publishDiagnostics (push model), debounced so a typing storm produces one push per settling window, never one push per keystroke (Kleppmann ch. 11 stream-processing debounce, §5).

18.2 Detailed Implementation Steps

diagnostics(file) aggregates parser ERROR nodes, unresolved-reference errors (§17), and type-mismatch diagnostics (§17) into one Vec<Diagnostic> (§11.9), tagged with the lsp-db revision it was computed at (I9). The publisher debounces on a per-file timer (default 500 ms, §4): a new edit resets the timer; the timer firing triggers a fresh diagnostics(file) query and a publish only if the result's tag is not older than the file's current revision at send time (I9 prevents publishing a diagnostic set the user has already invalidated by further typing). Severity mapping follows LSP's DiagnosticSeverity (§11.9); DiagnosticTag::Unnecessary/Deprecated drive editor-side dimming/strikethrough. textDocument/diagnostic (pull model, LSP 3.17+) is wired as an alternate entry point returning the same diagnostics(file) query result synchronously, for clients preferring pull.

18.3 Deliverable

Editing a file with a syntax error and an unresolved reference produces exactly one publishDiagnostics notification per settling window, carrying both findings with correct ranges and severities.

18.4 Acceptance Criteria

Diagnostics publish latency p99 ≤ 300 ms measured from the last keystroke in the debounce window (§4). A rapid-typing simulation (50 keystrokes in 400 ms) produces exactly 1 publish, not 50 (debounce fixture below). No published diagnostic set is ever tagged with a revision older than the revision current at send time (I9, property test).

18.5 Conformance Fixtures

diagnostics/debounce_typing_storm/ — 50 rapid didChange notifications; expected: exactly one publishDiagnostics after the settling window. diagnostics/stale_tag_dropped/ — an edit arrives after diagnostics(file) computed but before publish; expected: publish is dropped/recomputed, not sent stale (I9). diagnostics/pull_matches_push/ — a textDocument/ diagnostic request and the most recent push for the same revision; expected: identical diagnostic sets.

18.6 Pitfalls

Publishing a diagnostic set computed against a now-superseded revision — the classic "diagnostic shows up after the user already fixed it" bug (I9 exists specifically to prevent this). Debouncing per-workspace instead of per-file, which delays diagnostics on an untouched file behind a busy one. Forgetting that -32601 MethodNotFound-shaped silence on textDocument/diagnostic for a client that only expects push is a capability-negotiation bug, not a diagnostics bug (§11.10's over-advertising contract).

18.7 Performance Concerns

The debounce timer itself must not hold a lock across the settling window (would block concurrent edits to other files); each file's timer is independent, keyed by FileId, so the O(open files) scaling assumption (§4) holds here too.

18.8 Edge Cases

A file closed while its debounce timer is pending — the pending publish is cancelled, not sent (no diagnostics for a document the client no longer has open). A workspace-wide edit (e.g. a rename, §20) that touches hundreds of files simultaneously — debounce timers fire independently per file; the publish storm is bounded by the outbound backpressure alarm (ADR-26).

18.9 Failure Analysis

A diagnostics computation that itself panics (a bug in the type-inference layer, §17) is caught at the lsp-diagnostics boundary and converted to a single synthetic "internal analysis error" diagnostic on the offending file, never crashing the server process — contained blast radius, operator-visible via an elevated diagnostics_internal_error_total counter (§24).

18.10 Operational Notes

diagnostics_publish_latency_ms (histogram) and diagnostics_stale_dropped_total (counter) are the two dashboard signals; an SLO burn on the first indicates a debounce-tuning or db-performance regression (§24, §28).

19. Phase 7 — Completion, Hover & Navigation

19.1 Objectives

Implement textDocument/completion (with two-phase resolve), textDocument/hover, textDocument/definition, textDocument/references, and textDocument/documentSymbol — the core "answer a question about the cursor position" feature surface (§8.6's worked example).

19.2 Detailed Implementation Steps

lsp-completion builds a CompletionContext (§11.7) at handler entry (kind gates candidate generators, P1/P5 combine here, §8.6). Candidate generation is staged: syntactic candidates (scope-visible names matching prefix) are always available synchronously; type-aware ranking candidates (method-completion after .) depend on type_context(region) (§17) and, if not yet complete, the response is returned with isIncomplete: true and CompletionList marks itself for client re-request (P5's canonical application). The two-phase resolve protocol (completionItem/resolve) defers expensive per-item work (doc-comment rendering, auto-import edit computation) to a second request, keeping the initial list response cheap (P1). lsp-hover renders the type_context result (falling back to syntactic info if complete: false) as Markdown or plain text depending on negotiated client capability (§1.1's editor-agnosticism contract). textDocument/definition/references both resolve through resolve_reference/the reverse declarations map (§11.6) — references additionally needs a workspace-wide reverse-index scan (§21's workspace symbol index feeds this).

19.3 Deliverable

A completion request after obj. on a cold workspace returns syntactic candidates within budget and a refined type-aware list on re-request; hover, definition, and references all resolve correctly against the 100-file corpus from §17.3.

19.4 Acceptance Criteria

Completion p50 ≤ 15 ms, p99 ≤ 50 ms (§4); a late=true tag is present on every response exceeding budget (P1, telemetry-visible). Hover p99 ≤ 60 ms. Go-to-definition p99 ≤ 80 ms. A cold-workspace completion returns isIncomplete: true with ≥ 1 syntactic candidate rather than an empty list (P5 — never lie that there are no completions).

19.5 Conformance Fixtures

completion/dot_access_cold_workspace/ — completion right after . before type inference warms; expected: syntactic candidates + isIncomplete: true. completion/resolve_two_phase/ — initial list then a completionItem/ resolve for one item; expected: resolved item carries the doc comment the initial list omitted. hover/degrades_to_syntactic/ — hover while type_context.complete == false; expected: syntactic info only, no lie. references/cross_file_reverse_index/ — a symbol referenced from 3 files; expected: all 3 locations returned.

19.6 Pitfalls

Returning an empty completion list instead of a partial one with isIncomplete: true — the single most common partial-information-integrity bug (P5). Blocking the completion handler synchronously on a slow type_context computation instead of returning the syntactic tier and streaming/re-requesting (violates P1 and P7 simultaneously). Over-advertising referencesProvider before the reverse-index (§21) is actually wired, producing InternalError on every call (§11.10's contract).

19.7 Performance Concerns

The candidate-ranking pass (fuzzy-match scoring against every scope-visible name) is the dominant cost in the syntactic tier — bounded by scope size, not workspace size, keeping it within the p99 budget (§4). Two-phase resolve moves the expensive per-item work off the latency-critical initial-list path (P1).

19.8 Edge Cases

A completion request at a position inside a string literal or comment — CompletionKind::String/Comment suppress code-completion candidates entirely (§11.7). A references request on a symbol with zero references — returns an empty array, not an error. A hover request racing a didClose for the same file — the handler observes the closed document and returns null gracefully rather than operating on stale state.

19.9 Failure Analysis

A completion handler that panics mid-ranking is caught at the dispatcher boundary (I12) and converted to an empty-but-valid CompletionList plus an internal-error log line — never an unhandled JSON-RPC timeout from the client's perspective.

19.10 Operational Notes

completion_late_total (counter, tags late=true responses) and completion_latency_ms (histogram, p50/p95/p99) are the primary completion SLO dashboards (§24, §28); a sustained rise in completion_late_total without a corresponding db-performance regression usually indicates a candidate-set size regression (a scope leak) rather than a latency bug.

20. Phase 8 — Semantic Tokens, Code Actions & Rename

20.1 Objectives

Implement textDocument/semanticTokens/{full,delta} with the bit-stable delta protocol (I10, P8), the code-actions/quick-fix pipeline with two-phase resolve, cross-file rename via atomic WorkspaceEdit (I11, P9), and document/range/on-type formatting.

20.2 Detailed Implementation Steps

lsp-semtok encodes a TokenSet (§11.8) into the wire SemanticTokens.data flat array (deltaLine, deltaStart, length, tokenType, modifiersBitmask per 5-tuple); the delta variant computes a diff against the client's last result_id cache entry, re-run and asserted byte-identical on repeated identical input (I10 — bit-stability is a conformance-suite-enforced contract, §26). lsp-codeaction builds CodeActions (§11.9) from diagnostics (quick fixes) and from cursor-context analysis (refactors); resolve defers edit/command computation the same way completion defers item detail (§19.2's two-phase pattern reused, P1). Rename (textDocument/rename) resolves the symbol at the cursor via resolve_reference, collects every reference across the workspace (the same reverse-index used by references, §19.2), and emits one WorkspaceEdit with a TextDocumentEdit per affected file — document_changes preferred over changes so the client can detect a stale-file conflict via per-edit version (§11.9, P9). Formatting wraps an external or in-tree formatter, returning a single full-document TextEdit (document formatting) or a scoped one (range/on-type formatting).

20.3 Deliverable

A rename that touches 12 files across a workspace produces one WorkspaceEdit applied atomically by the reference client; re-running semantic-tokens delta on an unedited document is byte-identical to the previous response.

20.4 Acceptance Criteria

Semantic-tokens delta bandwidth reduction ≥ 50× vs. full encoding on a representative 2,000-line file (§4, §28 M-table). Rename across a 200-file workspace completes p99 ≤ 1.5 s (§4). Delta bit-stability: 1,000 repeated identical-input delta computations produce byte-identical output (I10, property test). Code-action resolve latency p99 ≤ 40 ms.

20.5 Conformance Fixtures

semtok/delta_bitstable_repeat/ — 1,000 repeated encodes; expected: byte- identical data array every time. codeaction/quickfix_resolve/ — a diagnostic-attached quick fix, initial list then resolve; expected: resolved edit matches golden. rename/twelve_file_atomic/ — a symbol referenced in 12 files; expected: one WorkspaceEdit, 12 TextDocumentEdit entries, each version-stamped. format/on_type_indent/ — a single on-type-formatting trigger character; expected: exactly the expected indentation TextEdit.

20.6 Pitfalls

A semantic-tokens delta implementation that is not bit-stable across identical inputs due to hashmap-iteration-order leakage into the token stream — breaks I10 and the conformance replay test (§26). Applying a workspace-wide rename edit in stages instead of one atomic WorkspaceEdit — violates P9 and can leave a workspace half-renamed if the client rejects a stale file mid-sequence. Advertising delta support without honoring result_id correctly, causing the client to apply a delta against the wrong baseline (a spec-conformance regression the fixture above catches).

20.7 Performance Concerns

Delta encoding cost is O(changed tokens), not O(total tokens) — the whole point of the optimization (§4's bandwidth target). Rename's reference-collection pass reuses the same reverse-index as references (§19), so its cost scales with reference count, not workspace size (§21's scaling story).

20.8 Edge Cases

A rename target that resolves to a declaration in a file currently unsaved in the editor (dirty buffer) — the WorkspaceEdit still targets the correct in-memory version via document_changes' version stamp (P9). A semantic-tokens request for a file with zero tokens (empty file) — returns an empty data array, not an error. A code action whose edit would conflict with an as-yet-unapplied prior action — is_preferred/disabled fields (§11.9) let the client sequence multiple actions safely.

20.9 Failure Analysis

A rename that partially fails on the client side (one file's version mismatched) is entirely the client's responsibility to reconcile (P9 — the atomicity contract is that the server never stages, not that the client can't reject); server-side, this shows as a client-reported apply-failure, not a server bug, and is logged as informational, not an error.

20.10 Operational Notes

semtok_delta_mismatch_total (I10 violations, should be permanently zero — any nonzero value is a release-blocking regression, §27) and rename_files_touched (histogram) are the phase's key metrics (§24, §28).

21. Phase 9 — Workspace, Cancellation, Progress & Conformance

21.1 Objectives

Implement multi-root workspace resolution, file watching (notify + polling fallback, P10), configuration pull/push (P12), the $/cancelRequest/$/progress/WorkDoneProgress* machinery end to end (P3), and the full spec-conformance + 30-day chaos-canary harness that certifies every invariant in §7 under adversarial timing.

21.2 Detailed Implementation Steps

lsp-workspace resolves workspaceFolders (§8.2's InitializeParams) into a set of WorkspaceLoader-discovered files (§11.9's delegation boundary, §1); it registers workspace/didChangeWatchedFiles dynamic registration when the client supports it, else runs a notify-backed watch loop with a polling fallback for filesystems lacking native events (P10, ADR-15) — both paths feed the same lsp-db input-write API (set_input), so downstream invalidation (I1) is watch-source-agnostic. Configuration resolution prefers server-initiated workspace/configuration pulls; for clients without pull support, workspace/didChangeConfiguration push snapshots are cached and treated identically by every consumer (P12) — the two paths converge before reaching any handler. lsp-progress implements $/cancelRequest (sets the CancellationToken registered in §13.2's requests_in_flight map) and $/progress/WorkDoneProgress{Begin,Report,End} for any handler that opts in via a ProgressToken (used by cold-workspace indexing, §16, and workspace-wide rename, §20). lsp-conformance runs the fixture corpus from every phase's N.5 against a matrix of client capability profiles (VSCode, Neovim built-in LSP, Emacs lsp-mode, Helix, Sublime LSP, Zed — §1.1); a failing fixture on any profile is a failing build. lsp-chaos runs the fault-injection harness (randomized cancel timing, randomized watch-event reordering, simulated client disconnects) continuously for 30 days in a staging environment before a release is cut (§27).

21.3 Deliverable

A multi-root workspace with an unsupported-pull-capability client still converges on correct configuration; a 30-day chaos run completes with zero I4 violations (leaked computation past cancellation) and zero I1 violations (revision non-monotonicity).

21.4 Acceptance Criteria

File-watch event → lsp-db invalidation latency p99 ≤ 50 ms (polling fallback: ≤ 2 s, the polling interval, §4). Configuration convergence (pull vs. push path) produces byte-identical internal state, verified by fixture. The 30-day chaos canary (§21.10) reports zero invariant violations across all 14 invariants in §7. Conformance suite passes on all 6 named client capability profiles (§1.1).

21.5 Conformance Fixtures

workspace/pull_push_converge/ — same configuration delivered via both paths; expected: identical internal state. workspace/watch_reorder_fuzz/ — randomized file-watch event ordering; expected: lsp-db state converges to the correct final on-disk state regardless of event order. progress/ work_done_cancel_midway/ — a long-running indexing operation cancelled at a random point via $/cancelRequest; expected: WorkDoneProgressEnd sent, no orphaned worker (I4). conformance/capability_matrix_full_run/ — the complete fixture corpus replayed under each of the 6 client profiles; expected: 100% pass on each.

21.6 Pitfalls

Treating client-side dynamic-registration failure as fatal instead of falling back to the server-side watch loop (P10 exists precisely because many clients implement watcher registration unreliably). Polling too aggressively on network-mounted filesystems, causing the FD/syscall budget (§4) to blow out — the polling interval must be configurable and defaults conservatively (2 s). Running the chaos canary against a single client profile only, missing a capability-negotiation bug that only manifests against, e.g., Emacs lsp-mode's stricter capability assumptions (§1.1).

21.7 Performance Concerns

Cold-workspace indexing (background, worker pool, ADR-13) must never starve the request-serving path — a WorkDoneProgress-reported background job runs at lower scheduling priority than foreground request handlers (P7, P1). The workspace symbol index (feeding references/rename reverse-lookup, §19, §20) is built incrementally per-file, not rebuilt wholesale per edit — cost scales with edited-file count, not workspace size (§4's scaling assumption).

21.8 Edge Cases

A workspace folder removed while the server is running (workspace/ didChangeWorkspaceFolders) — every file under that root is evicted from lsp-db inputs, and every dependent memo entry is invalidated on the next touch (I1). A client that never sends workspace/didChangeConfiguration and does not support pull — the server falls back to hardcoded defaults, logged once at startup, never silently guessing per-request. A watched-file event for a file the server has never opened — a fresh lsp-db input is created, not ignored, so workspace-symbol search (§19) stays complete.

21.9 Failure Analysis

A chaos-canary failure (any invariant violation over the 30-day run) blocks the release per §27's gate; the forensic artifact is the lsp-chaos seed and event-replay log, which reproduces the exact interleaving deterministically (P14) for root-cause analysis. A file-watch subsystem crash (e.g. notify's underlying OS API erroring) degrades to the polling fallback automatically rather than silently stopping all invalidation (P10's fallback is also the runtime failure-recovery path, not just the startup-capability path).

21.10 Operational Notes

The 30-day chaos canary runs in a dedicated staging environment gated in chaos.yml (§10, §27); workspace_watch_fallback_active (gauge) tells an operator whether a deployment silently degraded to polling; chaos_invariant_ violation_total (must stay at zero) is the release-blocking metric watched by perf.yml/chaos.yml CI gates (§27, §24).

25. Compatibility & Versioning

Wire compatibility: locked to LSP 3.17; a 3.18-draft feature is adopted only behind a capability flag the server advertises after implementing it, never assumed present. Storage compatibility: not applicable in v1 (no persistent storage, ADR-04); once the deferred on-disk cache (§35) lands, its schema carries an explicit version tag and a mismatched version triggers a full rebuild rather than a crash. Schema evolution: internal lsp-types structs may add Option<T> fields freely (additive); removing or repurposing a field requires a major-version bump and a migration note in CHANGELOG.md. API stability: the crate boundaries in §10 are a Rust-internal API, SemVer'd independently per crate; the wire API (LSP methods) is stable per the spec, not per this project's release cadence. Migration: none required client-side — the server is a drop-in replacement for any spec- conformant LSP server from the editor's perspective. Deprecation policy: a deprecated internal API is marked #[deprecated] for one minor release before removal; a deprecated wire capability follows the LSP spec's own deprecation timeline (e.g. rootUri remains supported alongside workspaceFolders indefinitely, per spec). SemVer policy: this project follows SemVer 2.0 for its own release artifacts (ADR-24); a breaking change to any crate's public Rust API is a major bump even if the wire behavior is unchanged. Rolling-upgrade guarantees: because each session is a fresh process, there is no in-place upgrade guarantee to maintain — every session start gets the currently-installed binary version, which is the simplest possible compatibility story for this deployment topology (§24).

Unit: per-crate, covering pure logic (position conversion, unification, scope lookup). Integration: full transport→dispatcher→handler→response round-trips per feature (§12–§21's N.5 fixtures). Fuzzing: cargo-fuzz (libFuzzer, ADR-20) on four targets — JSON-RPC input (§13.5), document sync (§14.5), the parser (§15.5), and name resolution (§17.5); AFL++ as a secondary engine for corpus diversity. Chaos: the 30-day canary (§21.10) — randomized cancel timing, watch-event reordering, simulated disconnects. Deterministic replay: every conformance fixture (§12–§21 N.5) is a recorded request/response sequence, replayed byte-exact in CI (P14 is what makes this possible). Soak: an 8-hour continuous-editing simulation checks db_memo_table_size and RSS stay bounded (FM-6). Fault injection: lsp-chaos (§10) injects cancel-race, watch-reorder, and disconnect faults on a schedule. 29. Scalability Analysis

Stays constant (per-request): CompletionContext/TypeContext construction cost is bounded by the enclosing scope/region, not workspace size (§11.7, §17). Grows: steady-state memory is O(open files), not O(total workspace files) — the defining scaling assumption of §4 — because lsp-db only holds inputs and memo entries for files that have actually been touched by a query. Named bottlenecks, in order: (1) full-reparse-per- edit cost on very large single files (§15.7) — O(file length) per edit, dominant above ~50 KLOC single files; (2) cross-file invalidation fan-out — O(reverse-import count) per edit to a widely-imported module (§17.7); (3) memo-table growth without an effective sweep — O(distinct query keys seen) without bound (§16.9); (4) worker-pool contention under concurrent request bursts — O(in-flight requests / pool size) queueing delay (§4's max- concurrency ceiling). Horizontal scaling: not applicable within one workspace (single process per session, §24); the analogous lever for a very large monorepo is splitting by crate/package boundary into independent lsp-db instances behind a workspace-level router — not built in v1. Vertical scaling: worker-pool size grows with num_cpus up to the §4 ceiling (16); beyond that, contention on the memo-table DashMap (ADR-09) becomes the limiter, not core count. Sharding/partitioning: the natural partition boundary is the module/crate graph — module_exports queries already scope invalidation to a module, so a future multi-instance design would shard along the same boundary (§34's Alternative Architectures explores this explicitly). Coordination overhead: cross-file dependency edges (I3) impose synchronization cost at every DashMap boundary crossing; this is the cost lsp-db pays instead of a coarser packages-graph model (§31's gopls comparison). Practical ceiling: ~5M LOC before M5's cold- index budget (400 ms/KLOC × 5,000 KLOC ≈ 33 minutes) becomes operator- unacceptable — this is why §1 names sub-second cold start on 5M-LOC workspaces a non-goal. Levers beyond the ceiling: the deferred on-disk warm cache (§35, PhaseDeferred("§9")), package-boundary sharding into multiple db instances, or a genuinely distributed indexing tier — all out of this blueprint's scope (§1).

30. Mental Models & First Principles

  1. MM1 — A query is a pure function from (key, world-revision) to value; the db is a giant lookup table you're allowed to skip filling in. What it predicts: any query is safe to call from anywhere, any number of times. The bug class without it: hidden mutable state smuggled through a "helper" that isn't itself a query. Applied in §16.
  2. MM2 — The revision counter is a Lamport clock for one process. What it predicts: two facts computed at the same verified_at are mutually consistent even if computed at different times. The bug class without it: comparing facts from different edits as if they described the same world state. Applied in §16.2, I1 (§7).
  3. MM3 — A green tree is a Merkle-tree-shaped cache key. What it predicts: identical subtrees really are identical objects, so pointer equality is a valid fast-path everywhere. The bug class without it: redundant structural comparison of trees that are already known-equal by construction. Applied in §15.2, I7 (§7).
  4. MM4 — Cancellation is cooperative, so a computation's "unwind points" are part of its public contract, not an implementation detail. What it predicts: any code path with no unwind point is a latent hang. The bug class without it: a "fast" tight loop that is actually an uncancellable 50 ms stall under the p99 completion budget. Applied in §16.2, §21.9, I4 (§7).
  5. MM5 — Durability is a coarse-grained version number layered on top of the fine-grained revision counter. What it predicts: most edits (Low durability) never need to re-touch workspace-wide facts (High durability). The bug class without it: every keystroke re-verifying facts that provably cannot have changed. Applied in §16.2, §16.3.
  6. MM6 — Partial information is a first-class value, not an error state. What it predicts: a correct handler always has a truthful answer to give, even mid-computation. The bug class without it: a completion or hover that confidently lies because the "real" computation hasn't finished. Applied in §8.6, P5 (§6).
  7. MM7 — The wire protocol and the internal model are different languages; the dispatcher boundary is the translator, and translation errors are the single biggest LSP conformance bug class. What it predicts: any type that crosses the boundary unconverted (a UTF-16 position leaking past PositionConverter) is a live bug. Applied in §8.3, §11.1, P15 (§6).
  8. MM8 — An LSP server's real "users" are the six client capability matrices (§1.1), not one editor. What it predicts: a feature that works in VSCode and nowhere else is unfinished, not done. The bug class without it: capability-assumption bugs that surface only in production, filed by users of the client you didn't test against. Applied in §21.2, §21.5.

rust-analyzer made the same architectural bet this blueprint makes — a query-graph engine — but built it as a general-purpose crate (salsa) used far beyond one server; it wins wherever multiple consumers need the same incrementality engine, at the cost of a heavier abstraction than an in-tree implementation needs (ADR-12's rationale for not depending on it directly).

gopls made a coarser bet: invalidate at the package boundary, not the file boundary. It wins for Go's package-oriented module system, where package-level granularity matches the language's own compilation unit and the coarseness costs little; it would cost more for a language with large, loosely-cohesive modules (§17.7's cross-file fan-out concern).

clangd solved a different problem: C++'s preprocessor makes a "file" an unstable unit (the same file expands differently per translation unit). Its preamble-as-separate-compilation-unit split wins specifically for header-heavy, macro-heavy languages; it is not a lesson this blueprint's import-based module language needs to copy, but the general principle — identify the unit that is actually stable and cache at that granularity — recurs everywhere.

tsserver rejected the multi-threaded query-graph bet entirely and stayed single-threaded by design (a real, load-bearing engineering decision, not legacy debt — see the Required Reading note, §5). It wins when the language's own analysis is cheap enough that single-threaded throughput is not the bottleneck, and the simplicity of "no concurrent-mutation bugs, ever" pays for itself; it is the regime this blueprint's Alternative Architectures (§34, Alternative 1) revisits explicitly.

32. Back-of-Envelope Capacity Model

  1. Bandwidth for full-document sync on a 2,000-line file (~60 KB): at a 200 req/s throughput ceiling (§4, M8) with 10% of requests being full-document syncs → 20 syncs/s × 60 KB = 1.2 MB/s sustained.
  2. Bandwidth savings from incremental sync (ADR-11): a typical single-character edit is ~200 bytes on the wire vs. 60 KB full — 300× reduction, consistent with §4's "~20× on long files" floor (conservative estimate; single-char edits do better than the floor).
  3. Memory for 500 open files at the §4 per-file ceiling (≤ 3× source bytes, avg file 30 KB): 500 × 30 KB × 3 = 45 MB for CST+indices alone; well under the 1.5 GiB workspace ceiling (M7), leaving headroom for memo-table entries and type-inference state.
  4. Memo-table size at steady state: assume 500 files × ~50 queries/file (parse, scope, per-function inference, per-reference resolution) = 25,000 live entries; at ~200 bytes/entry (key + small Arc + metadata) = 5 MB — negligible against the 1.5 GiB ceiling.
  5. Cold-index time for a 500-file, 150 KLOC workspace at M5's 400 ms/KLOC → 150 × 400 ms = 60 s total background indexing — background-only (§21.7), never blocking the p99 request path.
  6. FD budget check: 500 open files + ~50 directory watches (one per workspace subdirectory cluster, not per file) + a handful of transport/log FDs ≈ 560 FDs, well under the 4,096 ceiling (§4).
  7. Worker-pool queueing delay at peak load: M8's 200 req/s against a 16-worker pool (§4) with a 5 ms average handler time → offered load = 200 × 0.005 = 1.0 utilization at exactly 16 workers; the pool sizing formula is workers ≥ throughput_target × avg_handler_time_s, so 16 workers is the correct floor for M8, not headroom — justifying the "min 2, max 16" sizing rule (§4) as throughput-derived, not arbitrary.
  8. Rename fan-out at M4's 1.5 s / 200 files: 1.5 s ÷ 200 files = 7.5 ms per file's edit application, consistent with the per-edit cost implied by M6 (5 ms/file warm re-index) plus serialization overhead.
  9. Semantic-token delta bandwidth on a 2,000-line file: full encoding ≈ 2,000 tokens × 5 × 4 bytes = 40 KB; at M12's ≥ 50× reduction, a typical single-edit delta ≈ ≤ 800 bytes.

Every number above chains from the §4 System Constraints table with the formula shown; none is asserted without derivation.

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Single-threaded, request-serialized (tsserver-style).

Editor <--JSON-RPC--> [ single event loop: transport, dispatch, analysis ]
                              (no worker pool, no query graph;
                               per-file cache invalidated wholesale)

Regime where it wins: a language whose full-file analysis is cheap enough (milliseconds, not tens of milliseconds) that a single core never becomes the bottleneck — TypeScript's checker is fast enough per-file that tsserver never needed the concurrent-query-graph complexity this blueprint pays for. Real system: tsserver (§31, §5). Rejected here because: this blueprint's target language's type inference (§17) is expensive enough per-region that serializing all analysis behind one thread would blow the p99 completion budget (§4, M1) under any nontrivial concurrent-editing load.

Alternative 2 — Package/module-granularity invalidation (gopls-style).

File edit --> invalidate whole containing Package --> re-typecheck Package
                        (coarser than per-declaration, cheaper to track)

Regime where it wins: a language whose own compilation unit already is the package (Go), so package-granularity invalidation loses little precision while dramatically simplifying dependency tracking. Real system: gopls (§31, §5). Rejected here because: the target language's modules are finer-grained and more loosely cohesive than Go packages, so package-level invalidation would re-typecheck far more than necessary on a typical edit (§17.7's fan-out concern), missing the O(open files) scaling assumption (§4).

Alternative 3 — Compiler-as-a-library with a snapshot-per-request model.

Request --> fork/snapshot immutable compiler state --> answer against
            the frozen snapshot --> discard

Regime where it wins: a language whose full-program analysis is already fast enough to redo from scratch per request (small compilers, small programs) and where "snapshot and discard" is simpler to reason about than incremental invalidation at all. Real system: early Elm compiler tooling and several small-language LSP implementations built directly atop a batch compiler. Rejected here because: full re-analysis per request violates the p99 completion budget (§4) on any workspace above a few thousand lines — the entire motivation for a query graph (§3.1) is avoiding exactly this cost.

Alternative 4 — Distributed/sharded analysis across multiple processes.

Editor --> [ router process ] --> shard 1 (crate A's lsp-db)
                               --> shard 2 (crate B's lsp-db)
                               --> shard N ...

Regime where it wins: monorepo-scale workspaces (multi-million LOC, §29's practical ceiling) where a single process's cold-index time and memory ceiling are structurally insufficient regardless of tuning. No single mainstream LSP server ships this today; the closest real-world analogue is Bazel/Buck2's distributed remote-execution model for builds (§2's cross-link), applied here only as a design pattern, not a shipped LSP. Rejected here because: it multiplies operational complexity (cross-shard consistency, a router protocol) for a scale this blueprint's non-goals (§1) explicitly place out of scope.

36. Glossary

  • AstId — a stable identifier for an AST node across edits, keyed by (file, syntax kind, sibling index); the unit lsp-db dependency edges are expressed in terms of (§11.5).
  • Backpressure — a mechanism that slows a producer when a consumer cannot keep up; here, the bounded inbound mpsc channel (§13.2, ADR-26).
  • Cancellation token — a shared, atomically-set flag a query polls to detect that its enclosing request has been cancelled (§11.11, I4).
  • CST (Concrete Syntax Tree) — a lossless parse tree retaining every source byte including whitespace and comments (§11.5, I6).
  • Debounce — delaying a reactive computation until input has settled for a window, to avoid recomputing on every intermediate event (§18.2).
  • Delta encoding — expressing a new value as a diff against a previously-sent baseline, identified by result_id (§11.8, I10).
  • Dispatcher — the single-threaded component that routes incoming JSON-RPC messages to handlers and tracks in-flight requests (§13.2).
  • Durability — a coarse staleness tier (Low/Medium/High) attached to db inputs, used to short-circuit dependency verification (§11.4, MM5).
  • Early cutoff — the optimization of confirming a memoized result is still valid without re-running its computation (§16.2).
  • FileId — an interned, per-workspace integer identifier for a file (§11.2, I14).
  • Green tree — the immutable, parent-less, structurally-shared syntax tree representation (§11.5, MM3).
  • HIR (High-level IR) — the name-resolution/type-inference-ready representation derived from the AST (§6, P6).
  • Incremental sync — applying only the changed text range of a document rather than replacing it wholesale (§8.4, ADR-11).
  • Invariant — a property the system must never violate, with a defined detection and recovery path (§7).
  • JSON-RPC 2.0 — the remote-procedure-call wire protocol LSP is layered on (§8.1).
  • Lexical scope — a region of source code within which a name resolves to a specific declaration (§17.2).
  • LSP (Language Server Protocol) — the JSON-RPC-based protocol connecting an editor to a language-analysis backend (§1).
  • Memoization — caching a function's result keyed by its input, to avoid recomputation (§11.4).
  • Memo entry — one cached (result, dependency set, revision metadata) tuple in the analysis database (§11.4).
  • Module exports — the set of publicly visible declarations a module makes available to importers (§17.2).
  • Partial result — a response marked incomplete, allowing the client to request a refinement later (§8.6, P5).
  • PositionEncodingKind — the negotiated unit (UTF-8/16/32) for wire Position.character offsets (§8.3, P15).
  • Query (in the db sense) — a memoized, dependency-tracked function over lsp-db state (§11.4, MM1).
  • Query graph — the directed graph of dependency edges between live memo entries (§16.2).
  • Red tree — the ephemeral, parent-pointer-bearing view built on demand from a green tree (§11.5).
  • Revision counter — the monotonic integer that is lsp-db's global clock (§11.4, I1, MM2).
  • Semantic tokens — a per-token classification (type/modifiers) used for editor syntax highlighting beyond what a grammar alone provides (§11.8).
  • Structural sharing — reusing the same underlying allocation for unchanged parts of a data structure across versions (§11.5, I7).
  • Text edit — a (range, replacement text) pair describing one document mutation (§11.3).
  • Unification — the type-inference algorithm that solves a set of type-equality constraints (§17.2).
  • Watched file — a file the server monitors for external changes via notify or client-side registration (§21.2, P10).
  • Worker pool — the fixed-size thread pool executing db queries off the dispatcher thread (§11.4, P7, ADR-13).
  • WorkspaceEdit — a set of per-file edits applied atomically by the client (§11.9, P9, I11).
