Decisions (§9) · 27 ADRs

ADR-01

Language

Chosen

Rust (stable, MSRV N−2)

Rejected

OCaml, C++, Go, TypeScript

When the rejected choice is right

a small internal tool with no adversarial input and a 2-week deadline — OCaml ships faster

Why: no GC pause on hot path; rust-analyzer as reference (§1)

ADR-02

Build / workspace

Chosen

Cargo workspace, one crate per bounded context (§10)

Rejected

single monolithic crate

When the rejected choice is right

a < 5k-LOC prototype, where crate-split overhead exceeds the benefit

Why: keeps incremental cargo check < 15 s (§10)

ADR-03

Dependency policy

Chosen

cargo-deny gate (license + advisory + duplicate versions) in CI

Rejected

no automated policy

When the rejected choice is right

an internal-only fork never distributed — policy overhead without the legal exposure

Why: catches GPL-incompatible transitive deps before merge

ADR-04

Storage (warm cache)

Chosen

none in v1; deferred on-disk cache PhaseDeferred("§9")

Rejected

persistent sled/redb-backed memo table from day one

When the rejected choice is right

a workspace so large (>2M LOC) that cold-start dominates every session — persistent cache wins immediately

Why: avoids a schema-migration problem before the in-memory model is proven

ADR-05

Serialization

Chosen

serde_json (no SIMD)

Rejected

simd-json, sonic-rs

When the rejected choice is right

sustained > 5k msg/s where JSON parse is the measured bottleneck (§28, M-table)

Why: ecosystem-default correctness and tooling; SIMD is a deferred optimization (§9 register)

ADR-06

Networking / transport

Chosen

stdio + TCP

Rejected

named pipes (Windows-only), WebSocket

When the rejected choice is right

a browser-hosted editor (e.g. a web IDE) — WebSocket is then mandatory

Why: LSP spec names stdio and TCP; named pipes are a Windows-only stretch

ADR-07

Async runtime

Chosen

Tokio, current-thread dispatcher + multi-thread worker pool

Rejected

async-std, smol, raw std::thread

When the rejected choice is right

a CPU-bound batch tool with no I/O concurrency — raw threads avoid the runtime overhead

Why: Tokio is the ecosystem default; current-thread keeps the dispatcher single-threaded (P7)

ADR-08

Async/concurrency (cancellation)

Chosen

cooperative CancellationToken, polled at query boundaries (I4)

Rejected

OS-thread interrupts / Future drop-cancellation only

When the rejected choice is right

a pure-compute sandboxed worker process — OS-level SIGKILL isolation is simpler and sufficient

Why: portable, propagates through the query graph; drop-cancellation alone cannot express partial-unwind semantics needed for I4

ADR-09

Concurrency primitive

Chosen

parking_lot mutexes/DashMap

Rejected

std::sync::Mutex

When the rejected choice is right

a low-contention single-threaded build where std::sync avoids the extra dependency

Why: measurably lower contention overhead under the memo-table access pattern (§28)

ADR-10

Parser model

Chosen

Rejected

When the rejected choice is right

Why: recovery quality and lossless-tree control (§15); tree-sitter kept as a reference, not the engine

ADR-11

Document sync

Chosen

incremental, unified code path with full-sync fallback (P4)

Rejected

always-full sync

When the rejected choice is right

a client that can only do full sync and files are consistently small (< 1 KLOC)

Why: incremental cuts bandwidth ~20× on long files (§4)

ADR-12

Incremental engine

Chosen

in-tree Salsa-style query graph (own implementation)

Rejected

the salsa / salsa-2022 crate directly

When the rejected choice is right

a smaller team without capacity to own the memoization engine — the crate is the right call

Why: avoids a hard dependency on a fast-moving external crate while the model is well understood (§5)

ADR-13

Threading model

Chosen

single dispatcher thread + fixed worker pool (P7)

Rejected

fully single-threaded (tsserver-style)

When the rejected choice is right

a language with cheap, fast inference where single-threaded simplicity outweighs parallel throughput (tsserver's regime, §31)

Why: inference benefits from parallelism (§28); dispatcher stays single-threaded for ordering guarantees

ADR-14

Semantic tokens

ADR-23

Security

Chosen

sandboxed workspace/executeCommand, path-traversal checks on every file op

Rejected

no sandboxing (trust the workspace)

When the rejected choice is right

a strictly single-user, air-gapped, fully-trusted-workspace deployment — sandboxing overhead without a threat actor

Why: the server parses adversarially-shaped input from any file in the workspace root (T1–T3, §22)

ADR-24

Release / reproducibility

Chosen

cargo --locked + cargo-auditable + pinned SOURCE_DATE_EPOCH

Rejected

unpinned release builds

When the rejected choice is right

a throwaway internal fork with no distribution — pinning overhead not justified

Why: reproducible builds are required to audit a supply-chain compromise (§27)

ADR-25

Time source

Chosen

Instant (monotonic) for all budgets/timeouts; wall-clock only in log timestamps

Rejected

wall-clock (SystemTime) for budgets

When the rejected choice is right

a deadline shared across processes via an externally supplied absolute timestamp (e.g. a distributed trace's wall-clock SLA) — there, wall-clock is the only basis two hosts can agree on, jitter notwithstanding

Why: NTP adjustments and clock skew must not affect a cancellation deadline (I4)

ADR-26

Backpressure

Chosen

bounded inbound mpsc (transport→dispatcher), unbounded outbound with a high-water-mark alarm

Rejected

bounded both directions

When the rejected choice is right

a request/response-only protocol (no server-push notifications) — bounding both directions is then safe and preferred

Why: outbound can't apply backpressure to the client without violating the notification-delivery contract; the alarm substitutes (§13.7)

Licensing

Rejected

GPL-family, proprietary-only

When the rejected choice is right

a product-differentiating proprietary extension layer built on top of the open core — that layer alone may be proprietary

Why: matches the ecosystem's expectation for a tooling library that other projects embed

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Single-threaded, request-serialized (tsserver-style).

Editor <--JSON-RPC--> [ single event loop: transport, dispatch, analysis ]
                              (no worker pool, no query graph;
                               per-file cache invalidated wholesale)

Regime where it wins: a language whose full-file analysis is cheap enough (milliseconds, not tens of milliseconds) that a single core never becomes the bottleneck — TypeScript's checker is fast enough per-file that tsserver never needed the concurrent-query-graph complexity this blueprint pays for. Real system: tsserver (§31, §5). Rejected here because: this blueprint's target language's type inference (§17) is expensive enough per-region that serializing all analysis behind one thread would blow the p99 completion budget (§4, M1) under any nontrivial concurrent-editing load.

Alternative 2 — Package/module-granularity invalidation (gopls-style).

File edit --> invalidate whole containing Package --> re-typecheck Package
                        (coarser than per-declaration, cheaper to track)

Regime where it wins: a language whose own compilation unit already is the package (Go), so package-granularity invalidation loses little precision while dramatically simplifying dependency tracking. Real system: gopls (§31, §5). Rejected here because: the target language's modules are finer-grained and more loosely cohesive than Go packages, so package-level invalidation would re-typecheck far more than necessary on a typical edit (§17.7's fan-out concern), missing the O(open files) scaling assumption (§4).

Alternative 3 — Compiler-as-a-library with a snapshot-per-request model.

Request --> fork/snapshot immutable compiler state --> answer against
            the frozen snapshot --> discard

Regime where it wins: a language whose full-program analysis is already fast enough to redo from scratch per request (small compilers, small programs) and where "snapshot and discard" is simpler to reason about than incremental invalidation at all. Real system: early Elm compiler tooling and several small-language LSP implementations built directly atop a batch compiler. Rejected here because: full re-analysis per request violates the p99 completion budget (§4) on any workspace above a few thousand lines — the entire motivation for a query graph (§3.1) is avoiding exactly this cost.

Alternative 4 — Distributed/sharded analysis across multiple processes.

Editor --> [ router process ] --> shard 1 (crate A's lsp-db)
                               --> shard 2 (crate B's lsp-db)
                               --> shard N ...

Regime where it wins: monorepo-scale workspaces (multi-million LOC, §29's practical ceiling) where a single process's cold-index time and memory ceiling are structurally insufficient regardless of tuning. No single mainstream LSP server ships this today; the closest real-world analogue is Bazel/Buck2's distributed remote-execution model for builds (§2's cross-link), applied here only as a design pattern, not a shipped LSP. Rejected here because: it multiplies operational complexity (cross-shard consistency, a router protocol) for a scale this blueprint's non-goals (§1) explicitly place out of scope.
