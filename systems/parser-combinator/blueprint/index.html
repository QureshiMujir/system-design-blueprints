Project Name: Parser Combinator

1. Goal & Scope

mini-comb is a zero-copy, error-tree-aware parser combinator library in Rust implementing PEG (Ford 2004) ordered-choice semantics over interchangeable byte-slice, &str, and token-stream backends, with an explicit Error/Failure commit-point discipline (ported from Parsec's try), opt-in packrat memoisation with left-recursion support (Frost/Hafiz/ Callaghan seed-and-grow + Warth head-set tracking), a Pratt-style operator-precedence climbing combinator, streaming Incomplete semantics for partial buffers, and a shipped corpus of seven reference parsers that double as the conformance suite.

Phase-0 deliverable (numbered crates):

  1. mini-source — span/error-rendering primitives shared with the Lexer-Tokenizer project.
  2. mini-comb-core — Parser/Stream traits, primitives, branching, repetition, mapping/recognition combinators, ParseError and commit-point machinery.
  3. mini-comb-memo — packrat memoisation and left-recursion seed-and-grow.
  4. mini-comb-pratt — Pratt-style operator-precedence climbing.
  5. mini-comb-erased — BoxedParser type-erasure escape hatch.
  6. mini-comb-cli — smoke-test CLI driving the above.

Full-system unlocks (post-Phase-0): mini-comb-macros (parser! grammar macro), the seven parsers-* reference-parser crates, the SIMD literal fast path, and 30-day fuzz/soak infrastructure gating Sealed.

System boundaries. Provides: combinator algebra, position-tagged error tree, opt-in packrat + left recursion, Pratt climbing, streaming Incomplete. Delegates: lexing/token production to the Lexer-Tokenizer project (consumed through Stream::Item = Token); asynchronous IO to the Event-Loop project; span/rendering internals to the shared mini-source crate. Does not provide: a parser generator with a separate grammar file (rejected, §37 A3); LALR/GLR parse tables (rejected, §37 A2/A4); a full simdjson structural pre-pass (deferred, PhaseDeferred("§22.4")); a regex engine.

Non-goals: Unicode grapheme-cluster segmentation beyond UTF-8 validity; async-native combinators (sync only — async wrapping is the Event-Loop project's job); a hosted parser-as-a-service control plane (deferred, PhaseDeferred("§38")).

Deployment model: library crate(s) embedded in a host binary; the CLI is a debugging/ demonstration entry point, not a service. Target users/operators: Rust systems engineers building protocol/format parsers who would otherwise reach for nom or chumsky; the "operator" persona is a developer debugging a bad parse via the error-tree reporter, not an SRE running a service.

Later phases unlock: the SIMD literal fast path (§22 Phase 10), grammar-macro ergonomics (§21 Phase 9), the erasure escape hatch (§23 Phase 11), and the shipped reference-parser conformance corpus (§24 Phase 12) that downstream teams adopt directly.

Recommended language: Rust, stable toolchain, edition 2024 — ADR-01. Rejected: C++ (Boost.Spirit's expression-template macros obscure the Parser<I,O,E> algebra and complicate the zero-copy lifetime story — see §34 for the comparative regime where Boost.Spirit wins); Haskell as an implementation language for this library (Parsec/ Megaparsec remain load-bearing prior art, §5), rejected only because the target surface is byte-slice/zero-copy systems Rust code, not a managed runtime.

Prerequisites: Rust generics/trait bounds, lifetime propagation through nested combinator types, and parsing theory at the level of Required Reading (§5).

Estimated timeline: Phase 0 (crates 1–6 above) — 8 weeks. Full system (macro, SIMD, all seven reference parsers, 30-day fuzz Sealed gate) — 5–6 months.

Deferred features (register in full at §38): full simdjson structural pre-pass PhaseDeferred("§22.4"); async streaming driver PhaseDeferred("§18.4"); hosted parser-as-a-service PhaseDeferred("§38"); GLR ambiguity mode PhaseDeferred("§37"); incremental re-parsing PhaseDeferred("§38").

2. Why Build This

Rust's combinator ecosystem split, deliberately, into two camps: nom, which monomorphises every combinator chain into a concrete type and pays compile time for hot-path throughput; and chumsky, which type-erases combinators via dyn dispatch and pays throughput for compile-time and ergonomics. Both are well-engineered; both trade-offs are inherited by every downstream user, and most teams eventually wish they had the other library's properties on the surface they care about. mini-comb is the smallest library that still teaches the full surface: the Parser/Stream split, the position-tagged error tree, the Error/Failure commit-point discipline (Megaparsec/Parsec try), packrat memoisation with the Frost/Hafiz/Callaghan/Warth left-recursion trick, Pratt-style operator-precedence climbing, and the Incomplete streaming return that lets a parser run on a half-arrived TCP buffer.

Architecturally this project sits at the intersection of functional-programming parsing theory (Hutton & Meijer's monadic derivation) and systems-engineering throughput concerns (zero-copy spans, SIMD literal scanning, monomorphisation vs. erasure) — a rarer combination than either alone. Historically, every general-purpose language ends up with a combinator library once its ecosystem matures (Haskell → Parsec/Megaparsec, Rust → nom/ chumsky/pest, Scala → fastparse, Python → pyparsing/parsy); understanding why they converge on the same handful of primitives (sequencing, ordered choice, repetition, mapping) — and diverge on error handling, memoisation, and dispatch strategy — is the calibration value here.

Engineering muscles built: trait-based zero-cost abstraction design, lifetime propagation through deeply nested generic types, fixed-point algorithms (seed-and-grow), amortized-cost reasoning (packrat's space/time trade), and building a structured (not stringly-typed) error model that a UI can render. Cross-links to sibling systems: Lexer-Tokenizer supplies the token stream mini-comb consumes through the same Stream trait as byte slices; JSON-Parser supplies the JSONTestSuite conformance corpus mini-comb's JSON sub-parser is held to; Event-Loop supplies the async IO machinery the streaming Incomplete return integrates with.

What Mastery Looks Like (after building this, the reader can):

  • Derive the Parser<I,O,E> trait from the bind/return algebra (Hutton & Meijer 1996) and explain why flat_map is the monadic bind (§16 Phase 4).
  • Explain, from first principles, why PEG ordered choice is directional and non-commutative, and predict the output of any alt(a, b) vs alt(b, a) pair (§14 Phase 2, §6 P6).
  • Design a commit-point discipline (Error/Failure/cut) for a new grammar and place cut at the correct minimal-discriminator boundary (§17 Phase 5).
  • Implement packrat memoisation and seed-and-grow left recursion, and reason about their O(input×rules) space cost quantitatively (§19 Phase 7, §35).
  • Implement a Pratt operator-precedence climber from a binding-power table, including mixed prefix/infix/postfix operators (§20 Phase 8).
  • Choose, with justification, between monomorphisation and type erasure for a given rule count and compile-time budget (§23 Phase 11, §9 ADR-02/ADR-07).
  • Evaluate a competing combinator library (or a table-driven/GLR parser) against this design's trade-off space and name the regime where it wins (§34, §37).

Reference Parsers (top box). Seven crates under parsers-*; each is simultaneously a demonstration and a conformance-corpus producer. Trust boundary: input here is untrusted network/file bytes (§25 T1–T4).

Pratt Climber / Packrat+Left-Rec / Grammar Macro (middle row). Three independent accelerators over the combinator core — none is required to use the others. Concurrency boundary: each has its own owned state (MemoTable, climber operator tables) per top-level parse invocation, never shared across threads.

Combinator Core. The one-way data path: bytes/tokens flow up through Stream into the combinator chain; IResult<I,O,E> flows down. All primitives, branching, repetition, mapping, recognition, and the error tree live here (§13–§17); streaming semantics (§18) are a mode switch on the same combinators, not a separate crate.

Stream backends / ParseError tree. Persistence boundary: Stream impls borrow from the caller's buffer (zero-copy); nothing is owned except the Vecs repetition combinators allocate. Protocol boundary: ParseError<I> is the sole channel between a parse failure and a human-readable diagnostic.

mini-source. Shared position/rendering substrate; a single source-position type across this project and Lexer-Tokenizer is non-negotiable (P2, §6).

Erased escape hatch. Cuts across every layer above; a caller boxes at exactly the recursion boundary that needs compile-time relief (§23), never library-wide.

6. Design Principles

  1. The byte slice is the ground truth (P1). Every combinator has an implementation against &[u8]; &str and token-iterator backends are derived. Conformance compares against the byte-slice path. Tradeoff: derived backends may lag the ground truth briefly during development. Operational implication: a bug fixed only in &str and not back-ported to &[u8] is a conformance-suite failure by construction. Violating it: backend drift, silently different parse results per backend.
  2. One trait, two-plus backends (P2). Parser<I,O,E> is defined once; Stream is implemented per backend. Tradeoff: one extra associated type/type parameter vs. a BytesParser/StrParser hierarchy. Operational implication: the shipped reference parsers (§24) work unmodified against any backend. Violating it: combinator duplication across backends, doubling the maintenance surface.
  3. Monomorphisation is the default; erasure is opt-in (P3). Hot-path chains monomorphise (nom-style); BoxedParser (chumsky-style) is opt-in at the boundary the caller picks. Tradeoff: compile time vs. throughput, paid only where chosen (ADR-02, ADR-07). Operational implication: a 50-rule grammar can choose 12 s compile / 500 MB/s or 8 s compile / 180 MB/s per boundary (§35 row 7). Violating it (erasing by default): silent throughput loss with no compile-time benefit for small grammars.
  4. Errors are values; failures are commit points (P4). IResult returns Ok, Err::Error (recoverable — alt retries), or Err::Failure (committed — alt propagates). Only cut converts Error→Failure (I2, I10). Tradeoff: the caller must place cut correctly (§17 Phase 5). Operational implication: error-message quality is a direct function of cut placement. Violating it: garbage "expected one of: [50 items]" messages (FM3).
  5. Spans are everywhere (P5). Every combinator output can carry a ByteSpan cheaply (recognize_with_span); every error carries a span at the failure point. Tradeoff: one u32 pair per span. Operational implication: IDE/reporter tooling never needs the user to thread positions by hand. Violating it: unrecoverable loss of provenance (MM6).
  6. PEG semantics, deterministic ordered choice (P6). alt tries alternatives in declaration order (Ford 2004); it is not the CFG |. Tradeoff: alt(short, long) can make long unreachable. Operational implication: documented three times (rustdoc, docs/commit-points.md, README gotchas) because it is the dominant support load. Violating it (assuming commutativity): silently wrong parses on overlapping alternatives.
  7. Packrat is opt-in (P7). memoize(rule) wraps a rule in a packrat table; the rest of the grammar allocates no memo table. Tradeoff: O(input×rules) memory only where chosen (ADR-05, C4). Operational implication: left-recursive rules require left_recursive(rule) (Frost/Hafiz/Callaghan + Warth). Violating it (memoising everything): the memory blow-up quantified in §35 row 1.
  8. No allocation on the combinator hot path (P8). The chain itself is zero-allocation; many0/many1/separated_list allocate a Vec because they must — fold0/fold1 are the zero-allocation alternative. Tradeoff: the caller chooses allocation explicitly. Operational implication: an allocation-counting CI job gates every combinator (I12). Violating it: a 30% throughput regression per historical measurement (§28 Phase pitfall lineage).
  9. Compile-time grammars where ergonomic (P9). The parser! macro (§21 Phase 9) is sugar over the explicit chain, adding no runtime cost beyond it. Tradeoff: macro-expansion diagnostics are harder to author than plain Rust errors (ADR-16, ADR-21). Operational implication: a 50-rule grammar via macro compiles in ≤ 12 s (M7) vs. ≈ 90 s hand-written. Violating it (skipping the macro): 20-rule grammars balloon to hundreds of lines of boilerplate.
  10. Streaming is first-class but not default (P10). Incomplete(Needed) is a third return variant; Streaming/Complete modes are per-call-site (nom-7 style), not per-library. Tradeoff: two combinator variants to maintain per streaming-capable primitive. Operational implication: a grammar can mix modes ("streaming until the top-level value, complete inside it"). Violating it (streaming-only): forces every caller to pay the Incomplete-handling cost even for in-memory-only inputs.
  11. Reference parsers are conformance, not demos (P11). Every shipped grammar (§24) is simultaneously documentation and a conformance-corpus producer; there is no "example code" that conformance does not also gate. Tradeoff: shipped parsers must stay in lock- step with their RFC/spec even when a demo-only parser would not. Operational implication: a parsers-json regression is caught by conformance.yml, not manual review. Violating it: bit-rotting examples that no longer reflect the library's actual behavior.
  12. Errors are rendered, not stringly-typed (P12). The error tree (ParseError/ ErrorKind/Expected/Context) is structured; reporters (ariadne, codespan- reporting) are pure functions over it, never string concatenation inside combinators. Tradeoff: one extra type layer between "a combinator failed" and "text on screen". Operational implication: swapping reporters (ADR-09) costs zero combinator changes. Violating it: reporter-specific formatting leaking into the combinator core.
  13. Composability over completeness (P13). The library ships primitives sufficient to build any PEG grammar rather than special-casing every grammar shape (no built-in regex engine, no built-in JSON-specific fast path outside parsers-json). Tradeoff: some grammars need more combinator composition than a bespoke tool would require. Operational implication: the seven shipped parsers (§24) are proof the primitive set is sufficient. Violating it: feature creep turning the core into a grammar-specific tool.

8. Domain Model / Protocol / Data Model

8.1 The grammar formalism

Every grammar in this document is written as EBNF-like PEG notation: / is ordered choice (alt), juxtaposition is sequence (seq), */+/? are many0/many1/opt, &e/!e are peek/not. This notation is used identically in phase prose and the parser! macro (§21).

8.2 The result-state algebra

IResult<I,O,E> = Result<(I,O), Err<E>>. State-transition table for alt(p1, p2):

Current state (running p1) alt action Resulting state
Ok((rest, out)) return immediately Ok((rest, out))
Err(Error(e)) try p2 on original input whatever p2 returns
Err(Failure(e)) propagate, do not try p2 Err(Failure(e))
Err(Incomplete(n)) propagate, do not try p2 Err(Incomplete(n))

cut(p) state transition: Ok(_) passes through unchanged; Err(Error(e)) becomes Err(Failure(e)); Err(Failure(e)) and Err(Incomplete(n)) pass through unchanged.

8.3 Worked example — JSON object grammar (EBNF)

value    = ws (object / array / string / number / "true" / "false" / "null") ws
object   = "{" ws members? ws "}"
members  = member ("," ws member)*
member   = string ws ":" ws value
array    = "[" ws elements? ws "]"
elements = value ("," ws value)*

Commit points (§17): after object consumes "{", the remainder of that alternative is cut — there is no other alternative once { is seen, so a malformed body is a Failure, not an Error alt could route around.

8.4 Malformed-input trace

Input {"a": } (missing value). Trace: object matches "{" → commits (cut) → members → member matches "a", ":" → value tries object(Error, next char is }) → tries array (Error) → tries string (Error) → tries number (Error) → tries literals (Error) → all of value's alternatives exhausted → Err::Error(merged expected-set) at position 7 → because this is inside the cut from object, the enclosing member/ members/object chain converts it to Err::Failure at the object boundary → reported as "expected a value after : at line 1 column 8" (Context chain: object → members → member).

8.5 Failure-path example — left-recursive expression

Grammar expr = expr "+" term / term on input 1+2+3 (§19 Phase 7 seed-and-grow): seed expr at position 0 with Err::Error(LeftRecursion); non-recursive alternative term matches 1 (length 1); grow: re-run with seed = 1, recursive alternative now matches expr "+" term = 1+2 (length 3, longer) → replace seed; grow again: 1+2+3 (length 5, longer) → replace seed; grow again: no longer match → stop. Final parse: left-associative (1+2)+3, matching invariant I6.

11.1 Stream (input abstraction)

pub trait Stream<'a>: Copy {
    type Item: Copy + Eq + 'a;
    type Position: Copy + Ord + 'a;
    type Slice: 'a;
    fn position(&self) -> Self::Position;
    fn is_empty(&self) -> bool;
    fn first(&self) -> Option<Self::Item>;
    fn split_at(&self, n: usize) -> Option<(Self::Slice, Self)>;
    fn strip_prefix(&self, expected: &[Self::Item]) -> Option<Self>;
    fn split_while<F: Fn(Self::Item) -> bool>(&self, pred: F) -> (Self::Slice, Self);
    fn span(&self, range: core::ops::Range<Self::Position>) -> ByteSpan;
}

Ownership: &self-only, no interior mutation. Concurrency: Copy ⇒ trivially Send+ Sync for the byte-slice/&str impls (I11). Persistence: borrowed view, nothing owned. Serialization: N/A. Compatibility: adding a method is a breaking change post-Phase-0 (no default bodies) — the surface is locked at Phase 1 exit.

11.2 Result algebra

pub type IResult<I, O, E = ParseError<I>> = Result<(I, O), Err<E>>;

pub enum Err<E> {
    Error(E),
    Failure(E),
    Incomplete(Needed),
}

pub enum Needed {
    Unknown,
    Size(core::num::NonZeroUsize),
}

Ownership: E and O owned by value. Concurrency: Send+Sync iff E/O are. Persistence: none. Serialization: none by default (opt-in serde feature deferred, §38). Compatibility: adding an Err variant is breaking (I2 depends on exhaustive matching by callers); adding a Needed variant is additive-safe if callers match non-exhaustively.

11.3 Error tree

pub struct ParseError<I> {
    pub input: I,
    pub expected: SmallVec<Expected, 4>,
    pub contexts: SmallVec<Context, 4>,
    pub kind: ErrorKind,
}

pub enum ErrorKind {
    Char(char), Tag(&'static [u8]), TakeWhile, TakeUntil, Eof, Digit, HexDigit, Alpha,
    Alphanumeric, Space, Multispace, OneOf, NoneOf, SeparatedList, ManyMN(usize, usize),
    RecursionLimit, Custom(u32),
}

pub enum Expected { Char(char), Bytes(&'static [u8]), Description(&'static str), EndOfInput }

pub struct Context { pub label: &'static str, pub span: ByteSpan }

pub trait FromError<I, X>: Sized {

    fn append(input: I, kind: ErrorKind, other: Self) -> Self;

}

Ownership: ParseError<I> owns its expected/contexts inline up to 4 entries each (C14), spilling to heap beyond. Concurrency: Send+Sync iff I is. Persistence: none. Serialization: Debug/Display only in Phase 0; serde deferred (§38). Compatibility: ErrorKind/Expected are #[non_exhaustive] post-Phase-0 to allow additive variants.

11.4 Parser trait

pub trait Parser<I, O, E> {
    fn parse(&mut self, input: I) -> IResult<I, O, E>;
    fn map<F: FnMut(O) -> O2, O2>(self, f: F) -> Map<Self, F, O> where Self: Sized;
    fn and<P2: Parser<I, O2, E>, O2>(self, p2: P2) -> And<Self, P2> where Self: Sized;
    fn or<P2: Parser<I, O, E>>(self, p2: P2) -> Or<Self, P2> where Self: Sized;
    fn cut(self) -> Cut<Self> where Self: Sized;
    fn labelled(self, label: &'static str) -> Labelled<Self> where Self: Sized;
}

Ownership: &mut self on parse (combinators may hold internal mutable state, e.g. a MemoTable reference). Concurrency: not Sync in general (mutable internal state); per-thread instances only (C10). Persistence: none. Compatibility: adding a provided method without Self: Sized would break object-safety for BoxedParser (§11.7) — checked in CI.

Ownership: ByteSpan/FileId/LineColumn are Copy. MultiFileSource owns the file table. Concurrency: Send+Sync. Persistence: MultiFileSource lives for the process duration of a parse session. pub struct Memo<O, E> { pub result: IResult<u32, O, E>, pub generation: u32 }

13. Phase 1 — Primitives & Stream Backends

13.1 Objectives

Implement the five foundational primitives — char, tag, take, take_while, take_until — and the byte-slice and &str Stream impls (P1, P2) from which every later combinator is expressed.

13.2 Detailed Implementation Steps

  • Implement Stream<'a> (§11.1) for &'a [u8] (the ground-truth backend, P1) and &'a str (UTF-8-aware, guarding split points per I8). Both are Copy, satisfying I3/I11.
  • char(c) matches one item equal to c; on mismatch emits ErrorKind::Char into Expected (§11.3, P12). Named algorithm: single-item equality test against Stream::first.
  • tag(literal) matches a literal prefix via Stream::strip_prefix — the single-call fast path documented in ADR-17's SIMD lineage (used later in §22).
  • take(n) returns the next n items via Stream::split_at; short input is Err::Error(Eof) in complete mode, Err::Incomplete(Needed::Size(_)) in streaming mode (§18 Phase 6 introduces the mode split; Phase 1 implements only the complete-mode path).
  • take_while/take_while1 use Stream::split_while; the "longest prefix" algorithm is named, not coded, here — the property (take_while(p) monotone in p) is proptest- verified (I3).
  • take_until(needle) returns the longest non-needle-containing prefix, leaving the needle unconsumed; single-byte needles route through the memchr fast path from Phase 1 onward (ADR-17), multi-byte needles use a scalar scan until §22.

Conformance buckets primitive.char, primitive.tag, primitive.take_while all report Pass with ≥ 200 cases each (§29). Proptest property take_while(p) monotone in p holds over 10,000 generated cases. tag("") is a documented no-op (zero-length match, Ok).

corpora/primitive/char.jsonl (256 single-byte cases, boundary at 0x00/0xFF). corpora/primitive/tag.jsonl (exact-match, partial-prefix, empty-literal cases). corpora/primitive/take_while.jsonl (empty match, full-consume, malformed-UTF-8-in-&str- mode rejection cases).

13.6 Pitfalls

The &str backend must reject take(n) at a non-codepoint boundary — return None from split_at, never panic (I8, T4); an alternate take_chars(n) takes n characters instead of bytes. take_while returns impl Fn, not impl FnMut, to keep the resulting combinator Copy-compatible for alt's I: Clone bound (§14). tag with an empty literal must not be rejected — shipped grammars occasionally emit it deliberately.

13.7 Performance Concerns

Zero allocation on all five primitives (I12). Stream::strip_prefix/split_while must compile to a single bounds-checked loop with no intermediate Vec; verified via the allocation-counting CI job introduced in Phase 0.

13.8 Edge Cases

Empty input to every primitive; single-item input at exactly the match boundary; a take_while predicate that matches the entire remaining input (no natural stopping point); non-UTF-8 bytes fed to the &str backend's constructor (rejected before any combinator runs).

13.9 Failure Analysis

A Stream impl that violates I3 (rewinds position on Ok) silently breaks every downstream combinator's assumptions — detected by the proptest monotonicity check, not by any single primitive's own test. Blast radius: every combinator built on top, not just the primitive. Recovery: fix the Stream impl; no combinator-level workaround exists.

13.10 Operational Notes

docs/parser-trait.md is the canonical source for the trait shape; every later phase's documentation cross-references it rather than re-deriving the trait. No runtime observability yet (no streaming, no error tree beyond ErrorKind/Expected stubs).

14. Phase 2 — Branching & Ordered Choice

14.1 Objectives

Implement alt, seq, opt, peek, not, eof — the PEG ordered-choice and sequencing primitives (P6, Ford 2004) — establishing I1 and I2's Error-vs-Failure propagation rule for the first time.

14.2 Detailed Implementation Steps

  • alt(p1, p2, …) tries each parser in declaration order (I1); retries only on Err::Error(_), propagating Err::Failure(_) and Err::Incomplete(_) immediately (I2, Ford 2004 §3). A variadic tuple-impl covers up to 16 alternatives.
  • seq((p1, p2, …)) runs parsers in order into a tuple; any failure fails the whole sequence with that parser's error, unchanged (no error-merging at this layer).
  • opt(p) runs p; Err::Error(_) becomes Ok(None) with rewound input; Err::Failure propagates (I10 — opt never absorbs a commit).
  • peek(p) runs p and returns the original input as the remainder on success (lookahead without consumption).
  • not(p) succeeds iff p fails, consuming nothing (PEG's !p); its own error position is reported independently of p's internal failure position.
  • eof succeeds iff Stream::is_empty(); used as the top-level "consumed the whole input" assertion in every shipped grammar (§24).

14.3 Deliverable

All six combinators implemented and documented; examples/lisp_repl.rs gains a partial calculator skeleton demonstrating alt+seq composition (completed in §20).

14.4 Acceptance Criteria

Conformance buckets branch.alt, branch.peek, branch.not report Pass. A test asserts alt(tag(b"foo"), tag(b"foobar")) matches only "foo" out of "foobar" (documenting the non-commutativity of I1/P6 with a named, checked example, not prose alone).

14.5 Conformance Fixtures

corpora/branch/alt.jsonl (ordered-choice precedence cases, incl. the foo/foobar gotcha). corpora/branch/peek.jsonl (lookahead-does-not-consume assertions). corpora/branch/not.jsonl (negative-lookahead success/failure pairs).

14.6 Pitfalls

alt requires I: Clone; free for Copy byte-slice inputs, real cost for owned/buffered streaming inputs (§18) — Stream deliberately requires Copy to keep this cheap. The PEG ordered-choice surprise (alt(short, long) makes long unreachable) is the largest single support load across every PEG library (chumsky, nom); documented in the alt rustdoc, docs/commit-points.md, and the README gotchas section, per P6.

14.7 Performance Concerns

alt's input.clone() before each branch attempt is the only extra work over a hand- written match; for Copy backends this compiles to a register copy. seq's tuple-impl must not box intermediate tuples — verified by the allocation-counting job (I12).

14.8 Edge Cases

alt over zero alternatives (a construction-time error, not a runtime one). not(p) where p itself returns Err::Incomplete — not must propagate Incomplete, not convert it to a success (streaming interacts with negative lookahead in a documented way, revisited in §18). peek inside many0 (potential zero-width match — guarded in §15).

14.9 Failure Analysis

A grammar author who reorders alt alternatives introduces a silent semantic change, not a compile error — the largest single class of "why did my parser suddenly behave differently" bug reports historically seen in nom/chumsky issue trackers. Detection: the branch.alt conformance bucket pins the expected precedence per fixture; a reorder that changes an existing fixture's outcome fails CI (§29).

14.10 Operational Notes

docs/commit-points.md gains its first entry (the ordered-choice surprise); this document is extended again in §17 (Phase 5) once cut exists. No metrics beyond the conformance report — this phase has no streaming/production runtime surface yet.

15. Phase 3 — Repetition

15.1 Objectives

Implement many0/many1, separated_list0/separated_list1, delimited/preceded/ terminated, fold0/fold1, count, many_m_n — establishing I4's infinite-loop guard, the load-bearing safety property of every repetition combinator.

15.2 Detailed Implementation Steps

  • many0(p)/many1(p) run p repeatedly until Err::Error(_), collecting a Vec<O> (many1 requires ≥ 1 success). Named algorithm: repeat-while-Ok-and-progressing; the progress check is I4 — a zero-width successful match converts the combinator's own result to Err::Failure(ManyMN(0,0)) rather than looping.
  • separated_list0(sep, p)/separated_list1 parse zero/one-or-more p separated by sep; the trailing separator is not consumed (documented gotcha, §15.6).
  • delimited(open, body, close) / preceded(prefix, body) / terminated(body, suffix) discard the non-body outputs — the three most-composed combinators in the library.
  • fold0(p, init, f)/fold1 are the zero-allocation cousins of many0/many1 (P8): the caller supplies an accumulator and fold function instead of receiving a Vec.
  • count(n, p) matches exactly n occurrences; many_m_n(m, n, p) matches between m and n (used by every shipped reference parser to cap adversarial repetition, T3).

15.3 Deliverable

All seven repetition combinators implemented with the I4 guard; a property test asserts many0(p) and fold0(p, Vec::new, push) produce identical output.

15.4 Acceptance Criteria

Conformance buckets repetition.many0, repetition.fold0, repetition.sep_list report Pass. many0(opt(p)) on any input completes in bounded time (I4 regression test, explicit timeout assertion at 100 ms).

15.5 Conformance Fixtures

corpora/repetition/many0.jsonl (empty-input, single-element, zero-width-match cases). corpora/repetition/fold0.jsonl (output-equivalence-with-many0 cases). corpora/repetition/sep_list.jsonl (trailing-separator-present/absent cases).

15.6 Pitfalls

The I4 infinite-loop guard is mandatory: many0(opt(p)) matches the empty input forever without it. separated_list0 has the trailing-separator gotcha — shipped grammars (§24) universally use terminated(separated_list0(...), opt(sep)) when a trailing separator must be accepted. count(0, p) must succeed with Vec::new(), not error.

15.7 Performance Concerns

many0/many1 allocate a Vec (P8's documented exception); fold0/fold1 allocate nothing. The Vec's amortized growth factor (≈1.5×) is quantified in §35 row 10 as the argument for preferring fold0 on the JSON literal fast path (§22).

15.8 Edge Cases

A repetition combinator whose inner parser succeeds without consuming (I4); count(n, p) where n exceeds the remaining input length; separated_list0 on a single element with no separator present (must still succeed with a one-element list).

15.9 Failure Analysis

A missing I4 guard manifests as a process hang under adversarial input — detected only by a CI timeout (no natural error), the most expensive-to-diagnose failure class in the whole library because there is no crash, no log line, just a stalled process. Forensics: attach a debugger and observe the same (rule, position) pair recurring in the call stack.

15.10 Operational Notes

docs/commit-points.md documents the "infinite-loop guard" pattern alongside the ordered- choice entry from §14. No new runtime observability; the guard's Err::Failure surfaces through the existing error-tree machinery.

16. Phase 4 — Mapping & Recognition

16.1 Objectives

Implement map, map_res, flat_map, recognize, recognize_with_span, value, verify — the transformation layer between "matched some input" and "produced a typed AST node with provenance" (P5, Hutton 1992's higher-order-function view).

16.2 Detailed Implementation Steps

  • map(p, f) is Functor-style output transformation (Hutton & Meijer 1996 §2).
  • map_res(p, f) runs p, then f: O -> Result<O2, X>; on Err(x) converts to Err::Error(E::from_external(saved_input, x)) — the bridge from "matched a digit string" to "have a u32" without losing the pre-parse position for error reporting (§11.3 FromError).
  • flat_map(p, f) is the monadic bind (Hutton & Meijer 1996, P1): p's output selects the next parser to run. Used for length-prefixed payloads where an integer determines how many subsequent bytes to read.
  • recognize(p) runs p, discards its output, returns the consumed slice — computed once from the position delta (entry.position()..exit.position(), I7), never by re-running p.
  • recognize_with_span(p) returns (O, ByteSpan) — the canonical hook for AST nodes that need provenance (P5, MM6).
  • value(constant, p) and verify(p, pred) are the remaining two: constant substitution and post-hoc predicate rejection (Err::Error(Custom) on predicate failure).

16.3 Deliverable

All seven combinators implemented; recognize unit-tested against tag+take_while for slice equality with the consumed prefix (I7).

16.4 Acceptance Criteria

Conformance bucket recognize.span reports Pass: every fixture's ByteSpan.start/end equals the parsed byte range exactly (I7). map_res's error carries the pre-parse position, verified by a dedicated regression fixture.

16.5 Conformance Fixtures

corpora/recognize/span.jsonl (span-equals-consumed-range assertions across primitive, branch, and repetition combinators). A map_res regression fixture asserting the error span points before, not after, the parsed prefix.

16.6 Pitfalls

recognize must compute the consumed length from the position delta, not by re-running p a second time — re-running risks side-effect divergence if p is stateful (e.g. wraps a memoised rule, §19) and is a documented historical regression class. flat_map's second parser's type depends on the first's output — this occasionally requires BoxedParser (§23) to keep the surface compilable in recursive grammars. map_res must save the input position before running f, or the error span points past the parsed prefix.

16.7 Performance Concerns

recognize is zero-allocation (returns a Stream::Slice reference); map_res/flat_map allocate only if E::from_external or the callback closure does. The position-delta computation is O(1) for byte-slice/&str backends (subtraction), O(1) amortized for token streams (index subtraction).

16.8 Edge Cases

recognize wrapping a zero-width successful match (empty slice, valid); map_res whose callback panics (documented as a caller bug, not a library failure mode — callbacks must return Result, never panic); flat_map whose second parser itself returns Err::Incomplete (propagates untouched).

16.9 Failure Analysis

A recognize that re-runs its inner parser (instead of using the position delta) silently diverges from a memoised rule's cached result if the rule has any hidden non-determinism (e.g. RNG-seeded test doubles) — extremely rare in production grammars but a documented historical bug class from early combinator libraries. Detection: the recognize.span conformance bucket compares against the position-delta ground truth.

16.10 Operational Notes

docs/parser-trait.md gains the map/map_res/flat_map distinction section. No new telemetry; this phase is purely combinator-level.

17. Phase 5 — Error Tree & Commit Points

17.1 Objectives

Implement ParseError/ErrorKind/Expected/Context (§11.3), the cut/labelled combinators, and the ariadne/codespan-reporting reporter integrations — the center of gravity of the whole library (P4, P12; Leijen & Meijer 2001; Wadler 1985).

17.2 Detailed Implementation Steps

  • Thread Stream::position() through every combinator so errors tag the position at point of failure, not the top-level entry (I7's provenance requirement extended to errors).
  • Every leaf combinator (char, tag, take_while, …) emits its own Expected entry; alt merges Expected sets across branches on failure, with dedup (a triple-alt of digit-matchers must not emit "expected: digit, digit, digit").
  • cut(p) converts every Err::Error(_) from p into Err::Failure(_) (I2, I10; Leijen & Meijer 2001's try-inverse). Convention: combinators wrap cut immediately after consuming a distinctive discriminator prefix (worked example §8.4's object rule).
  • labelled(p, "name") pushes a Context{label, span} onto the error's context stack on failure; the reporter renders the chain as "while parsing X > while parsing Y > …" (Megaparsec's labelled-error discipline, §5 Required Reading).
  • Two reporters, feature-flagged on mini-source (ADR-09): ariadne_report(&error, &source) and codespan_report(&error, &source). Both are pure functions over ParseError — no combinator ever formats a string directly (P12).

17.3 Deliverable

ParseError<I>, Err<E> variants, cut, labelled all implemented; a config-file key-value grammar in examples/url_normalize.rs exercises the full discipline end to end.

17.4 Acceptance Criteria

insta snapshot tests (ADR-15) pass on 5 canonical error scenarios (truncated JSON, missing comma, mismatched bracket, unexpected character, unexpected EOF) for both reporters — 10 snapshots total, zero unreviewed diffs. Conformance buckets commit.cut, commit.labelled report Pass.

17.5 Conformance Fixtures

corpora/commit/cut.jsonl (Err::Failure propagates past alt — 20 fixtures spanning 1–4 nesting levels). corpora/commit/labelled.jsonl (context-chain-matches-recorded-chain fixtures). tests/snapshots/error_{truncated_json,missing_comma,mismatched_bracket, unexpected_char,unexpected_eof}.snap × 2 reporters.

17.6 Pitfalls

cut is a one-way door — indiscriminate use produces unrecoverable error positions, arguably worse than no cut at all; the rule is "cut at the minimal-discriminator boundary" (documented in docs/commit-points.md, not earlier, not later). The Expected set must dedupe or alt of three digit-matchers emits a triple-repeated message (§36 Q7). Context.label is &'static str, never String — the per-error allocation cost of a String would violate P8/I12 on the error path, which is exercised on every malformed input.

17.7 Performance Concerns

Error-tree construction only happens on the failure path (never on Ok), so I12's zero-allocation guarantee is unaffected on success; SmallVec<_,4> (C14) keeps the common case (≤4 expected items, ≤4 context labels) stack-resident. Reporter rendering (ariadne/codespan) is explicitly out of the hot path — invoked only when a human requests a formatted report.

17.8 Edge Cases

An error at position 0 (empty input); an alt whose every branch fails with a distinct ErrorKind (the dedup logic must not conflate different kinds); a cut immediately followed by another cut (idempotent — the error is already Failure, converting again is a no-op); a labelled context whose span is zero-width (entry position == failure position).

17.9 Failure Analysis

Failure class FM3 (error-message quality collapse) originates here: a missing cut at the correct boundary means alt keeps trying alternatives that can never succeed once a discriminator has been seen, producing a diluted "expected one of: [50 items]" message. Detection: insta snapshot diff on PR (ADR-15) is the only reliable signal — the bug produces no test failure by itself, only a worse message. Recovery: add cut at the correct boundary per docs/commit-points.md's checklist.

17.10 Operational Notes

docs/error-tree.md and docs/commit-points.md are the canonical long-form references; every later phase that introduces a new commit point (§20's Pratt climber) cross-links here rather than re-deriving the discipline. cargo insta accept/review is the CI-integrated workflow for reviewing snapshot diffs.

18. Phase 6 — Streaming & Incomplete Semantics

18.1 Objectives

Implement the Streaming/Complete per-call-site mode split (P10, ADR-08; nom-7 lineage) and the Incomplete(Needed) return variant, establishing I9 (non-consumption on Incomplete) for the first time.

18.2 Detailed Implementation Steps

  • Two parallel combinator sets: complete::tag/complete::take_while/… (missing bytes at end = Err::Error(Eof)) and streaming::tag/streaming::take_while/… (missing bytes = Err::Incomplete(Needed)). Default exports are complete (the common case, P10).
  • Needed::Size(n) when the exact additional byte count is known (e.g. take(n) short by a known amount); Needed::Unknown otherwise (e.g. take_while running off the buffer end with no natural stopping point yet observed).
  • The streaming driver contract (documented, not shipped as a runtime — the Event-Loop project owns the async wrapper, §2): on Err::Incomplete, the caller appends more bytes and re-invokes the same top-level parser from the same position (I9 guarantees no input was consumed on the Incomplete path).
  • recognize (§16) is statically forbidden in streaming mode via a sealed-trait bound — "the consumed slice" is undefined while a parser is still waiting for more input.
  • examples/streaming_jsonl.rs demonstrates the discipline end to end on a JSONL stream read one chunk at a time from stdin.

18.3 Deliverable

The streaming submodule of mini-comb-core with streaming variants of tag, take, take_while, take_until, char; examples/streaming_jsonl.rs runs against a multi-chunk synthetic JSONL input.

18.4 Acceptance Criteria

Conformance bucket streaming.tag reports Pass: every fixture's Needed::Size(n) value matches the exact byte shortfall. examples/streaming_jsonl.rs processes a 1 GB synthetic JSONL stream fed in 4 KB chunks with zero panics (M9 soak precursor). PhaseDeferred("§18.4: async streaming driver wrapping this synchronous core; owned by Event-Loop project") is registered (§38) rather than implemented here — this phase ships the synchronous Incomplete contract only.

18.5 Conformance Fixtures

corpora/streaming/tag.jsonl (partial-buffer fixtures at every truncation point of a multi-byte tag, each asserting the exact Needed::Size). A soak fixture: 10,000-line JSONL file split at 4 KB boundaries, replayed through the streaming driver contract.

18.6 Pitfalls

Err::Incomplete is neither Err::Error nor Err::Failure — alt propagates it unconditionally (never retries the next branch), a distinct rule from I2 worth restating because it is easy to conflate the three-way split with a two-way one. A driver that feeds zero new bytes between Incomplete responses spins forever — the discipline (documented, not enforced by the type system) is "never feed less than one byte"; violating it is a caller bug, not a library bug, but the library's docs must say so explicitly.

18.7 Performance Concerns

The streaming variant of each primitive has an identical hot path to its complete counterpart except for the trailing-boundary check — verified by a benchmark (benchmarks/streaming_chunked.rs) showing < 5% overhead versus the complete-mode equivalent on non-truncated input.

18.8 Edge Cases

A tag whose literal spans exactly the chunk boundary (must return Incomplete, not a false Error); a take_while predicate matching zero bytes at the exact end of an otherwise-full buffer (ambiguous between "done" and "need more" — resolved by requiring streaming take_while1 semantics to distinguish the two, documented per-primitive); a driver that never terminates because the peer never sends the final byte (bounded by a caller-level timeout, outside this library's scope, T10).

18.9 Failure Analysis

FM4 (streaming stall) is native to this phase: a combinator that returns Incomplete without ever converging as more bytes arrive is either a peer that stopped sending or a bug where the combinator's boundary condition never resolves. Detection: parse_incomplete_ retry_count metric threshold at the driver layer (owned by the caller, e.g. Event-Loop); this library documents the metric name but does not itself emit it (no runtime, P-library distinction, §4).

18.10 Operational Notes

docs/runbooks/why-incomplete.md walks an operator through diagnosing a stuck streaming parse: check the Needed value history, confirm the peer is still sending, confirm the driver isn't re-parsing from a stale position (I9 violation would show as forward progress the driver doesn't expect).

19. Phase 7 — Packrat Memoisation & Left Recursion

19.1 Objectives

Implement memoize(rule) (Ford 2002 packrat) and left_recursive(rule) (Frost, Hafiz & Callaghan 2007 seed-and-grow + Warth & Piumarta 2007 head-set tracking for indirect recursion), establishing I5 and I6.

19.2 Detailed Implementation Steps

  • memoize(rule_id, p) wraps p in a MemoTable lookup keyed by (rule_id, position) (§11.6); on a table hit, replay the cached IResult in O(1); on a miss, run p and insert the result (Ford 2002's linear-time argument — total work is O(input × rules), C4, §35 row 6).
  • left_recursive(rule_id, p) implements seed-and-grow: (1) seed the table at (rule_id, pos) with Err::Error(LeftRecursion); (2) run p — the recursive alternative hits the seed and fails immediately (Err::Error), so the non-recursive alternative succeeds first, producing an initial parse r0; (3) grow: re-run p with the seed replaced by r0; the recursive branch now succeeds — if the result r1 is strictly longer than r0 (I6), replace the seed and grow again; (4) stop when growing produces no longer parse — the final seed is the answer.
  • Indirect left recursion (rule A's first alternative calls rule B whose first alternative calls A) requires Warth's head-set tracking: each left-recursive entry records which other rule IDs are "involved" in its recursion so the grow step re-evaluates the whole mutually-recursive cluster, not just the entry rule.
  • rule_id collision detection (I5): a debug-mode assertion on MemoTable::insert checks that a re-inserted (rule_id, pos) doesn't map to a structurally different rule (a copy-paste bug signature).

19.3 Deliverable

memoize/left_recursive implemented in mini-comb-memo; a benchmark (benchmarks/packrat_left_rec.rs) compares memoised vs. naive recursion on a 1,000-token arithmetic expression.

19.4 Acceptance Criteria

The classical left-recursive grammar expr = expr "+" term / term; term = term "*" factor / factor; factor = number / "(" expr ")" parses 1+2+3 as left-associative (1+2)+3 (§8.5 worked trace). Conformance bucket packrat.left_rec reports Pass. benchmarks/ packrat_left_rec.rs shows linear (not exponential) scaling from 100 to 10,000 tokens (≤ 2× wall-clock per 10× input, the packrat linearity signature).

19.5 Conformance Fixtures

corpora/packrat/memo.jsonl (repeated-position hit fixtures — second hit at the same (rule, pos) must be O(1), verified by an instruction-count budget via iai-callgrind). corpora/packrat/left_rec.jsonl (direct and indirect left-recursion fixtures, incl. the four-alternative arithmetic grammar of §8.5).

19.6 Pitfalls

Two distinct rules sharing a rule_id (a hand-written, non-macro-generated collision) conflates their memo entries — caught only by the I5 debug assertion, not by any type-level mechanism (the parser! macro of §21 avoids this by auto-assigning unique IDs). Growing must terminate because each grow step consumes strictly more input (I6); a left-recursive rule with an empty-matching alternative violates this and is rejected at construction, not at parse time. Memo entries hold outputs by Clone — expensive-to-clone ASTs defeat the speedup; the recommendation (docs/packrat-and-leftrec.md) is to memoise rules whose output is Rc<AstNode>, not AstNode by value.

19.7 Performance Concerns

Packrat memory is O(input × memoised-rule-count) — C4, quantified concretely in §35 row 1 (a 1M-token expression with 4 memoised rules costs ≈128 MB). This is the reason memoize is opt-in (ADR-05, P7): a grammar with no left recursion and no shared sub-parses pays zero memo-table cost by default.

19.8 Edge Cases

A left-recursive rule whose only alternative is left-recursive (no non-recursive base case — must be rejected at construction, since seed-and-grow has no base parse to grow from). Mutually indirect left recursion three rules deep (A→B→C→A) exercises Warth's head-set tracking beyond the two-rule case. A memoised rule whose output type is not Clone (rejected at compile time — MemoTable<O,E> requires O: Clone).

19.9 Failure Analysis

FM1 (left-recursion non-termination) is native here: a grow step that fails to strictly increase consumed length (an implementation bug in leftrec.rs, not a grammar bug) hangs or OOMs. Detection: the CI benchmark timeout (M8-adjacent) on packrat_left_rec.rs. Forensics: dump the MemoTable::generation counter's history — a generation that repeats without the seed's result length increasing pinpoints the bug.

19.10 Operational Notes

docs/packrat-and-leftrec.md documents the seed-and-grow algorithm and the Rc<AstNode> memoisation recommendation. tools/memo-table-visualizer/ (§10) renders a MemoTable's (rule_id, pos) -> generation history for debugging a suspected non-termination.

20. Phase 8 — Pratt Operator-Precedence Climbing

20.1 Objectives

Implement PrattClimber (§11.7) — Pratt 1973's operator-precedence algorithm in its recursive "precedence climbing" formulation (Nystrom 2021 Ch. 17) — supporting mixed prefix, infix, and postfix operators with configurable associativity.

20.2 Detailed Implementation Steps

  • Binding-power table: each operator carries a Power(left, right) pair (§11.7); a left-associative operator has left < right (e.g. + = Power(10,11)); right- associative has left > right (e.g. ^ = Power(20,19)); the comparison "current operator's left power < caller's minimum" is what selects the correct parse tree (Pratt 1973, Norvell's recursive reformulation). Named algorithm: parse_expr(min_bp) — parse one atom, then loop: peek an operator, stop if its left power < min_bp, otherwise consume it and recurse with its right power as the new minimum, combining via the operator's builder.
  • PrattClimber::new(atoms) then .prefix(matcher, power, builder) / .infix(matcher, power, assoc, builder) / .postfix(matcher, power, builder) build the operator tables fluently; the climber sorts internally by power on first parse call.
  • After consuming an operator's matcher, the climber applies cut (§17, ADR-04) before parsing the right-hand operand — past the operator, the operand is mandatory, and a missing one is Err::Failure, not a retriable Err::Error (I2 applied at the Pratt boundary).
  • Mixed prefix/infix sharing a token (e.g. - as both negation and subtraction) is disambiguated by climber-internal context: prefix - when there is no left-hand-side yet, infix - otherwise.

20.3 Deliverable

PrattClimber implemented in mini-comb-pratt; the calculator in examples/lisp_repl.rs (started in §14) is completed using it.

20.4 Acceptance Criteria

The calculator produces the correct AST for 1 + 2 * 3 (Add(1, Mul(2,3)), precedence), 2 ^ 3 ^ 4 (Pow(2, Pow(3,4)), right-associativity), and -3! (Neg(Fact(3)), prefix binds looser than postfix). benchmarks/pratt_expression.rs parses a 1,000,000-token arithmetic expression and reports ≥ 80,000,000 tokens/s (M5).

20.5 Conformance Fixtures

corpora/pratt/calc.jsonl (full power-table coverage: left-assoc, right-assoc, prefix, postfix, and the mixed---disambiguation case, ≥ 30 fixtures).

20.6 Pitfalls

Right-associative operators have inverted power triples ((20,19), not (19,20)) — an off-by-one here is the single most common Pratt bug; tests must cover both associativity directions explicitly (§20.4's 2^3^4 case). The cut after an operator match is critical for correctness, not just message quality: without it, an outer alt can swallow a "missing right operand" Error and silently produce a wrong-but-plausible shorter parse (§36 Q15 connects this to I2).

20.7 Performance Concerns

The climber's operator-table lookup on each loop iteration is a linear scan over ≤ 20 operators in the shipped grammars — negligible versus the recursive-descent cost; a sorted-by-power table (built once per PrattClimber instance) avoids re-sorting per call. Zero allocation on the parse path beyond the AST nodes the builder closures construct (P8's Vec/AST-allocation boundary, not a combinator-hot-path violation).

20.8 Edge Cases

An operator appearing in both the prefix and infix tables with conflicting associativity metadata (rejected at PrattClimber construction). A right-associative operator at the weakest possible binding power interacting with a left-associative operator of equal apparent precedence (must be disambiguated by explicit power values, not by table order). An empty atom stream (zero tokens — Err::Error, not a panic).

20.9 Failure Analysis

A missing cut after an operator match (§20.6) is a correctness bug, not merely a message-quality one — it can silently produce a different, wrong parse tree rather than an error, making it the hardest Pratt bug class to detect via testing alone. Mitigation: the conformance fixtures explicitly assert full AST shape (not just "parses successfully") for every operator combination.

20.10 Operational Notes

docs/pratt.md documents the binding-power table convention and the mixed-prefix/infix disambiguation rule referenced by every future grammar that adds a new operator.

21. Phase 9 — Grammar Macro Ergonomics

21.1 Objectives

Implement the parser! declarative macro (P9, ADR-16, ADR-21) — a peg-style grammar DSL that expands to plain combinator chains with zero added runtime cost, easing the boilerplate of 20+-rule grammars (motivated in §5's pest reference-implementation entry as the build-time-codegen alternative this macro avoids, §37 A3).

21.2 Detailed Implementation Steps

  • Grammar DSL rules (documented, not coded, per the No-Code Rule): / is ordered choice (alt); juxtaposition is sequence (seq); */+/? are many0/many1/opt; &e/ !e are peek/not; a literal string is tag(literal.as_bytes()); name:expr binds expr's result for the action block; { action } is the rule's result expression.
  • Implemented via syn 2 + proc-macro2 + proc-macro-error (ADR-16): parse the grammar block into a syn-derived AST, then emit one Rust function per rule, auto-assigning unique rule_ids (closing the I5 collision risk that hand-written memoize calls carry, §19.6).
  • Rules wrapped in memoize!/left_recursive! directives thread a MemoTable parameter through the generated chain automatically — the user-visible surface never sees the table parameter (§19's memoize/left_recursive remain the underlying primitives).
  • Mutually recursive rules require a forward-declaration pass: the macro emits a struct whose methods are the rules, so the type checker accepts the cycle (a technique shared with pest's and combine's macro designs, §5).
  • proc-macro-error attaches diagnostic spans to the offending grammar token — an expansion_limit (10,000 AST nodes) aborts with a compile error rather than hanging the compiler (T5).

21.3 Deliverable

The parser! macro implemented in mini-comb-macros; an ergonomic rewrite of the JSON grammar (anticipating parsers-json, §24) demonstrates a 20-rule grammar in macro form.

21.4 Acceptance Criteria

A 50-rule synthetic grammar compiles via the macro in ≤ 12 seconds, cold cache (M7). Macro-expansion golden-output test (I13) confirms byte-identical expansion across the two oldest and newest compiler versions in rust-toolchain.toml's supported range. A deliberately malformed grammar (missing () on a rule head) produces a pinpointed proc-macro-error diagnostic, not a multi-hundred-line generic trait-bound error.

21.5 Conformance Fixtures

tests/macro/small_grammar.rs (5-rule grammar, exercises every DSL operator once). tests/macro/json_grammar.rs (20-rule grammar, exercises memoize!/mutual recursion). tests/macro/malformed_grammar.rs (5 deliberately malformed fragments, asserts diagnostic text via insta, per ADR-15's discipline extended to macro diagnostics).

21.6 Pitfalls

Macro hygiene around bound names: name:expr binds name only in that rule's action block — the action block must not incidentally see other macro-internal identifiers (historical bug class in syn-based macros with careless hygiene). Recursive expansion of mutually recursive rules needs the forward-declaration struct-of-methods pattern or the type checker rejects the cycle outright. Diagnostic spans must point at the offending grammar fragment, not the macro invocation as a whole, or debugging a 50-rule grammar becomes a linear scan (FM8).

21.7 Performance Concerns

The macro's expansion is a compile-time cost only — the emitted combinator chain has identical runtime characteristics to the hand-written equivalent (P9's "zero added runtime cost" guarantee, verified by a benchmark comparing macro-generated vs. hand-written parsers-json in §24).

21.8 Edge Cases

A grammar with a single rule that is both left-recursive and wrapped in memoize! (both directives compose — left_recursive! implies memoisation, §19). A grammar fragment exceeding the 10,000-node expansion_limit (T5, compile error not a hang). A rule name that collides with a Rust keyword (escaped via raw identifiers r#... in the emitted code).

21.9 Failure Analysis

FM8 (macro-expansion type-error avalanche) is native here: a small grammar typo without a correctly attached proc-macro-error span produces a 200-line generic trait-bound error instead of a pinpointed one. Detection: the malformed_grammar test suite asserts on diagnostic text, not just pass/fail, catching span-attachment regressions specifically.

21.10 Operational Notes

docs/parser-trait.md gains the macro-grammar reference section. The macro crate ships no runtime component — its entire operational surface is the compile-time diagnostic quality tracked by tests/macro/malformed_grammar.rs.

22. Phase 10 — SIMD Literal Fast Path

22.1 Objectives

Accelerate literal-byte scanning via memchr/bytecount (ADR-17) without porting the full simdjson structural pre-pass (Langdale & Lemire 2019) — the Phase-0-appropriate slice of that paper's throughput argument.

22.2 Detailed Implementation Steps

  • take_until(needle) for single-byte needles routes through memchr::memchr (AVX2/ SSE4.2/NEON-dispatched at runtime by the crate) instead of a scalar per-byte scan.
  • take_while(pred) for byte-class predicates that map to a memchr2/memchr3 pattern (e.g. take_while(|c| c != b'"' && c != b'\\'), the JSON string-body scan) becomes one vectorised call; the fast path is opt-in via an explicit take_while_byteclass API, since a user-supplied closure cannot be statically classified as SIMD-eligible. Whitespace-run skipping (ws()) uses a bytecount-based skip for long runs.
  • mini-comb-core takes an optional memchr dependency; when absent (e.g. no_std builds without the feature, ADR-11), the relevant combinators fall back to scalar code — behavior is bit-identical, only throughput differs (verified by FM6's differential test).
  • The full simdjson-style structural classification pass (byte-level SIMD pre-pass producing a structural-index before any combinator runs) remains out of scope: PhaseDeferred("§22.4: full simdjson-style structural pre-pass; ~3x throughput at input > 64 KB; required for M11").

22.3 Deliverable

memchr-backed take_until/take_while_byteclass; benchmarks/json_throughput.rs confirms the literal fast path's throughput on the citm_catalog.json fixture (used identically in §24's parsers-json).

22.4 Acceptance Criteria

benchmarks/json_throughput.rs reports ≥ 500 MB/s on citm_catalog.json (1.7 MB, M1). A differential test (FM6) runs the same corpus with the memchr feature on and off, byte-comparing every output — zero divergence permitted.

22.5 Conformance Fixtures

benchmarks/results/json_throughput.json (recorded throughput number, gated in CI per §31). A differential-test corpus of 500 JSON documents run through both the SIMD and scalar code paths.

22.6 Pitfalls

memchr operates on &[u8]; the &str backend must slice via as_bytes() and re-validate UTF-8 on the way out — the validation cost is negligible because core::str::from_utf8 is itself vectorised on common targets. The fast path applies only to static byte-class predicates; a user-supplied closure does not qualify and must use the explicit take_while_byteclass API rather than being silently un-accelerated (ADR-17).

22.7 Performance Concerns

This phase's entire purpose is a performance concern: memchr's vectorised scan is "most of the win at a tenth of the code" versus a full simdjson port (ADR-17's rationale), quantified in the Capacity Model (§35) via the JSON-throughput-vs-link-rate calculation.

22.8 Edge Cases

A needle byte that also appears as a UTF-8 continuation byte in a multi-byte codepoint (the &str backend's re-validation must catch a false-positive split, T4). An input shorter than memchr's internal vector width (falls back correctly to a scalar tail loop inside the memchr crate itself — not this project's concern, but tested at the boundary regardless).

22.9 Failure Analysis

FM6 (SIMD/scalar divergence) is native here: an undiscovered edge case (e.g. a multi-byte needle miscount, though single-byte needles are the only SIMD-accelerated case in Phase 0) would show as a differential-test failure between the two code paths, bisectable via the memchr feature flag.

22.10 Operational Notes

docs/performance/ records the benchmark methodology and the historical throughput trend per release (tracked against M1 in benchmarks/results/).

23. Phase 11 — Erased Combinators & Compile-Time Relief

23.1 Objectives

Implement BoxedParser (§11.8, ADR-02, ADR-07) — the opt-in dynamic-dispatch escape hatch that trades one indirect call per combinator boundary for dramatically shorter compile times on large or deeply recursive grammars (chumsky's headline design, §5, §34).

23.2 Detailed Implementation Steps

  • BoxedParser::new(p) wraps any Parser<I,O,E> + 'a in a heap-allocated dyn FnMut(I) -> IResult<I,O,E> closure (§11.8, ADR-02, ADR-07); Parser::parse on BoxedParser is one indirect call.
  • Parser<I,O,E> is not object-safe in general (methods like map<F,O2> require Self: Sized, Klabnik & Nichols Ch. 19) — BoxedParser wraps only the object-safe subset (parse itself), so callers see an identical Parser impl regardless.
  • Recursive grammars must box at the recursion boundary or the type system rejects the infinite type (a combinator chain that calls itself without indirection has unbounded compile-time type size); the parser! macro (§21) auto-inserts a BoxedParser at detected recursive entry points by default, with an opt-out for callers who accept the compile-time cost of full monomorphisation.
  • The 'a lifetime on BoxedParser is the closure's captured-environment lifetime; combinators capturing by reference must outlive the box.

23.3 Deliverable

BoxedParser<'a,I,O,E> implemented in mini-comb-erased; benchmarks/erased_vs_mono.rs compares monomorphised vs. erased dispatch on the JSON fixture.

23.4 Acceptance Criteria

A 50-rule grammar compiles in ≈ 90 s monomorphised vs. ≈ 8 s erased (cold cache, matching M6/C12's worked numbers). benchmarks/erased_vs_mono.rs reports erased-mode JSON throughput ≥ 180 MB/s (M12) against the monomorphised path's ≥ 500 MB/s (M1) — both recorded, neither regresses silently.

23.5 Conformance Fixtures

benchmarks/results/erased_json.json (recorded ≥ 180 MB/s). A compile-time regression fixture: a fixed 50-rule grammar's compile-time is tracked release-over-release in benchmarks/results/ for both dispatch modes.

23.6 Pitfalls

Recursive grammars that omit BoxedParser at the recursion boundary fail to compile with a type-size error, not a runtime bug — easy to misdiagnose as a macro bug rather than a missing erasure boundary (§21.2's auto-insertion mitigates this for macro-authored grammars only; hand-written recursive chains must box manually). The 'a lifetime mismatch between a captured reference and the box's lifetime is a common first-attempt compile error for new contributors.

23.7 Performance Concerns

One indirect call per combinator boundary is the entire cost model here — quantified precisely in §35 row 7 (compile-time-per-rule) and via the M1/M12 throughput comparison (500 vs. 180 MB/s, a ≈2.8× throughput cost for the compile-time relief).

23.8 Edge Cases

A grammar mixing monomorphised and erased sections (fully supported — erasure is a per-boundary choice, P3); a BoxedParser whose captured closure itself panics (propagates as a Rust panic, not a ParseError — documented as caller responsibility, same as map_res's callback contract, §16.8).

23.9 Failure Analysis

A core combinator in mini-comb-core that internally returns BoxedParser (rather than a concrete monomorphised type) has "lost the throughput argument" (P3) — caught by code review and by the M1 benchmark regressing toward M12's number unexpectedly, which signals an accidental erasure creeping into the hot path.

23.10 Operational Notes

docs/parser-trait.md documents when to choose erasure (rule count, compile-time budget) versus monomorphisation, cross-referencing ADR-02/ADR-07 and the §35 capacity numbers.

24. Phase 12 — Shipped Reference Parsers & Conformance Corpus

24.1 Objectives

Ship seven reference parsers — HTTP/1.1 request line, JSON (RFC 8259), CSV (RFC 4180), IPv4/IPv6, RFC 3339/2822 date-times, URL (WHATWG), S-expressions/Lisp — each simultaneously documentation and a conformance-corpus producer (P11), proving the combinator set sufficient for real-world grammars (P13) and delivering the library's success criterion: replacing a downstream nom/chumsky user.

24.2 Detailed Implementation Steps

  • parsers-http: Request-Line = Method SP Request-URI SP HTTP-Version CRLF (RFC 7230); a companion header parser handles RFC 7230 line-folding (obsolete-fold rejected).
  • parsers-json: the full RFC 8259 grammar (§8.3's worked EBNF); string parsing routes through the §22 SIMD literal fast path; \uXXXX escapes handle surrogate pairs (combining a high/low pair into one U+1F600-class codepoint before emitting UTF-8). Cites the JSONTestSuite corpus (Nicolas Seriot) mirrored under third_party/ with attribution (P11 conformance-as-documentation).
  • parsers-csv: RFC 4180 strict mode plus a tolerant mode (unquoted commas inside fields, mismatched quote counts, trailing newlines) — the tolerant mode is a separate entry point, never silently blended with strict parsing.
  • parsers-net: IPv4 (four decimal octets, many_m_n-capped per T3) and IPv6 (RFC 4291, including :: zero-run elision — exactly one :: per address, embedded IPv4 ::ffff:1.2.3.4, zone identifiers fe80::1%eth0); url.rs implements the WHATWG subset [scheme:]//[user[:pass]@]host[:port]/[path][?query][#fragment], with rfc_3986.rs as the RFC-3986-flavoured sibling for callers who need the older spec (documented divergence in percent-encoding and userinfo handling).
  • parsers-rfc-dates: RFC 3339 (1996-12-19T16:39:57-08:00) and RFC 2822 (Wed, 19 Dec 1996 16:39:57 -0800) date-times, plus ISO 8601 basic as a sibling.
  • parsers-sexp: atoms, lists, dotted pairs, quote forms ('x, `x, ,x, ,@x), strings, numbers, ;-to-newline comments; the Lisp variant adds reader macros (#t, #f, #\char, #'fn).
  • The conformance runner (conformance/runner.rs) executes all corpora across all seven parsers plus the combinator-level buckets from §13–§19, emitting conformance.report.json with a Pass/Fail/Deferred outcome per bucket (§29).

24.3 Deliverable

All seven parser crates compile, pass their conformance corpora, and carry rustdoc with a runnable example each; every crate has ≥ 1 cargo-fuzz target (fuzz/fuzz_targets/).

24.4 Acceptance Criteria

parsers-json hits ≥ 500 MB/s on the literal fast path (M1); parsers-http hits ≥ 100 MB/s (M2); parsers-csv hits ≥ 250 MB/s (M3); parsers-net::ipv6 sustains ≥ 3,000,000 addresses/s on a 10M-address corpus (M4). Every JSONTestSuite fixture's accept/reject vector matches exactly (json.suite bucket). Conformance suite aggregate wall-clock ≤ 90 s (M8).

24.5 Conformance Fixtures

conformance/corpora/{http,json,csv,net,rfc-dates,sexp}/ — 23 buckets total (§29 lists all), including json.suite (JSONTestSuite mirror, ~300 fixtures), net.ipv6 (::- elision, embedded-IPv4, zone-ID cases), net.url (WHATWG accept/reject), dates.rfc_3339 (parse+format round-trip).

24.6 Pitfalls

JSON \uXXXX surrogate-pair mishandling (decoding a lone \uD83D as U+D83D instead of combining with its low surrogate) is the single most common JSON-parser bug and produces invalid UTF-8 if unguarded. IPv6 :: elision must enforce "exactly one :: per address" — a naive many0(group) accepts multiple :: and produces ambiguous addresses. RFC 3339 and RFC 2822 differ in time-zone notation; the two crates must not share parsing code without a pinned differential test. WHATWG URL and RFC 3986 disagree on percent-encoding and userinfo handling — the default (WHATWG) must be documented as a deliberate, not accidental, divergence from the RFC.

24.7 Performance Concerns

Each shipped parser's throughput target (M1–M4) is gated in CI via benchmarks/*.rs; a regression below target blocks release (§31's phase-gating discipline). The JSON literal fast path (§22) is the only SIMD-accelerated shipped parser in Phase 0 — the others rely on combinator-core throughput alone.

24.8 Edge Cases

A JSON document nested 10,000 levels deep (bounded by recursion_limit, T1, C2). An IPv6 address with the maximum legal group count and no elision. A CSV file with a BOM and mixed line endings. A URL with a percent-encoded userinfo containing a colon. An RFC 2822 date-time with a two-digit year (obsolete but RFC-legal, must be accepted per the spec's own obsolete-syntax section).

24.9 Failure Analysis

FM9 (conformance regression) is native to this phase: a refactor that silently breaks one JSONTestSuite fixture shows as a bucket-level Pass→Fail transition in conformance.report.json; conformance.yml blocks merge automatically on any such transition (no manual review gate needed for this class).

24.10 Operational Notes

docs/runbooks/why-bad-error-message.md walks a downstream integrator through diagnosing a shipped parser's error output using the reporters from §17. Each parsers-* crate's rustdoc links back to the RFC/spec section it implements and to the conformance bucket that gates it, closing the loop between specification, implementation, and proof.

27. Operational Readiness

Because mini-comb is a library, not a service (§4's defining property), "operational readiness" means release-engineering and integrator-facing readiness rather than an on-call SRE surface.

  • Metrics (test/benchmark-scoped, not production telemetry): parser_recursion_depth, combinator_alloc_bytes, parse_incomplete_retry_count, fuzz_crash_count, dependency_advisory_count — all emitted by CI harnesses (§25/§26), never by the library at runtime.
  • Tracing: none in the library itself; a host application that wraps mini-comb in a service is responsible for its own span/trace correlation around Parser::parse calls.
  • Structured logging: ParseError's Debug impl is structured (field-per-field); the ariadne/codespan-reporting reporters (§17) are the human-facing rendering layer.
  • Dashboards / alerting: N/A at the library layer; benchmarks/results/ is the release-over-release dashboard equivalent, reviewed at every release (§30).
  • SLOs: the closest analogue is the M-table (§31) — each target is a release gate, not a live SLO.
  • Incident response: a fuzz-discovered panic (FM10) or a conformance regression (FM9) is the library's "incident"; docs/runbooks/ holds the response procedure for each.
  • Named runbooks: docs/runbooks/debugging-a-parse.md, docs/runbooks/why-incomplete.md, docs/runbooks/why-bad-error-message.md (§10).
  • Backup/restore: N/A (no persisted state; MemoTable is per-invocation and cleared on entry, §11.6).
  • Deployment topology: embedded-library only; the CLI (mini-comb-cli) is a single-binary debug tool, not a deployed service.
  • Canary / rolling-upgrade / rollback / migration: governed entirely by SemVer (§28); a downstream crate pins a mini-comb version and upgrades on its own schedule — there is no server-side rollout to coordinate.

28. Compatibility & Versioning

  • Wire compatibility: N/A — mini-comb has no network wire format of its own; the shipped parsers (§24) implement external wire formats (HTTP, JSON) whose compatibility is governed by their respective RFCs, not by this project.
  • Storage compatibility: N/A — no persisted state.
  • Schema evolution: ErrorKind/Expected are #[non_exhaustive] (§11.3) — new variants are additive-safe; removing or renaming a variant is a breaking (major) change.
  • API stability: the Core Schema types of §11 are the locked public surface as of Phase-0 exit; Parser/Stream gaining a new required method is breaking (no default bodies, §11.1/§11.4's compatibility annotations).
  • Migration: a major-version bump ships a MIGRATION.md documenting every breaking Err/ErrorKind/trait-signature change, cross-referenced to the ADR that motivated it.
  • Deprecation policy: a deprecated combinator carries #[deprecated(since, note)] for ≥ 1 minor version before removal in the next major version.
  • SemVer policy: standard Cargo SemVer; the ByteSpan/FileId u32 field widths (§11.5) are the one place a seemingly-internal change (widening to u64 for inputs > C1's 4 GiB ceiling) is explicitly called out as major-version-only, since it changes the shared mini-source crate's on-wire size for any caller that has serialized a ByteSpan.
  • Rolling-upgrade guarantees: since there is no service to roll, "rolling upgrade" means two downstream crates (e.g. Lexer-Tokenizer and mini-comb) pinning different mini-source minor versions during a transition window — guaranteed compatible within the same major version by the #[non_exhaustive] discipline above (FM11's mitigation).

29. Testing & Verification Strategy

  • Unit tests: per-combinator, colocated with each module (§10); assert on IResult shape, not just success/failure.
  • Integration tests: the seven shipped parsers (§24) against their RFC/spec grammars.
  • Property-based tests (proptest, ADR-14): take_while(p) monotonicity (I3), UTF-8-boundary safety (I8), many0/fold0 output equivalence (§15.3), backend equivalence between &[u8] and &str (I11).
  • Differential testing: byte-slice vs. &str backend over a shared corpus (I11); SIMD vs. scalar code path (FM6, §22.6).
  • Fuzzing (cargo-fuzz, ADR-14): targets for json, http, url, ipv6 (fuzz/fuzz_targets/); 30-day continuous campaign is the Sealed precondition (M10, T9).
  • Chaos / fault injection: streaming driver fed truncated buffers at every possible byte boundary (§18.5's soak fixture) — the closest analogue to chaos testing for a synchronous, stateless-per-call library.
  • Deterministic replay: the conformance runner (conformance/runner.rs) is itself deterministic — same corpus, same binary, same conformance.report.json, enabling git bisect-driven regression hunting (FM9).
  • Soak testing: examples/streaming_jsonl.rs run for 24 hours against a synthetic multi-GB JSONL stream, zero panics/leaks (M9).
  • Conformance testing: 23 buckets (§24.5) with a Pass/Fail/Deferred trichotomy (§21/§38); every bucket ties back to a named System Invariant (§7) or shipped-parser RFC.
  • Performance-regression gating: every M-table target (§31) is checked in benchmarks.yml; a regression below target blocks merge, not just release.
  • Mutation testing (cargo-mutants, ADR-19): nightly job over the combinator core, surfacing untested-but-passing code paths in the algebra itself.
  • Snapshot testing (insta, ADR-15): error-message wording (§17), macro diagnostics (§21.5) — both treated as user-facing API requiring explicit review on change.

Every test class above ties back to a named System Invariant (§7) or a Conformance Fixture (each phase's N.5); there is no test whose purpose isn't traceable to one of the two.

30. Build & Release Engineering

  • Reproducible builds: rust-toolchain.toml pins an exact stable version (§12.2); Cargo.lock is committed and reviewed on every dependency bump (ADR-18).
  • Artifact signing: release tarballs (source + mini-comb-cli binary) are signed with the maintainers' PGP key referenced in SECURITY.md.
  • SBOM: generated via cargo-deny list / cargo-cyclonedx at release time, attached to every GitHub release artifact.
  • Release channels: crates.io for the library crates; GitHub Releases for the CLI binary and the whitepaper (papers/whitepaper/).
  • CI/CD topology: ci.yml (build/test/lint) on every push; conformance.yml and benchmarks.yml on every push to main and every release tag; fuzz.yml nightly; security.yml nightly (cargo-deny).
  • Version stamping: mini-comb-cli --version embeds the crate version, the git commit hash, and the rustc version used to build it (via built/vergen-style build script).
  • Provenance/attestation: release workflow emits a SLSA-style provenance attestation binding the published crate to the exact CI run and commit that produced it.
  • Dependency auditing: cargo-deny (ADR-18) runs on every push and nightly; a new advisory affecting a pinned dependency blocks the next release until triaged.

32. Scalability Analysis

Stays constant regardless of input size: per-combinator stack frame cost (C3); error- tree inline budget (C14, SmallVec<_,4>); Stream trait dispatch cost (monomorphised, O(1) per call).

Grows with input size (Big-O): packrat memo table, O(input × memoised-rule-count) (C4, Ford 2002); many0/separated_list0's Vec allocation, O(matches) with ≈1.5× amortized growth overhead (§35 row 10); parse wall-clock, O(input) for a PEG grammar with no pathological shared-prefix backtracking (T2's mitigated case), O(input²) worst case if memoize is withheld from a grammar that needs it (§35 row 6's derivation).

Named bottlenecks, in order: (1) memory bandwidth on the byte-slice hot path — the dominant cost once allocation is eliminated (P8); (2) the packrat memo table's hash/lookup cost when memoisation is used heavily (ADR-12's xxhash choice targets this); (3) Vec reallocation in many0-heavy grammars (mitigated by fold0, §15.7); (4) compile time for large monomorphised grammars (mitigated by BoxedParser, §23).

Horizontal scaling: trivial — each parse invocation is independent, embarrassingly parallel across threads/processes with zero shared mutable state (C10, I5/I11); scaling JSON ingestion to saturate a 10 GbE link requires ≈ 3 cores at the M1 throughput rate (§35 row 2's derivation).

Vertical scaling: throughput scales with single-core memory bandwidth and SIMD width (§22); the library does not itself use multiple threads internally.

Sharding/partitioning: N/A at the library layer — a caller partitions work (e.g. one MemoTable per connection) at the application layer; the library imposes no partitioning scheme of its own.

Coordination overhead: zero at steady state (no shared state); the only coordination point is the mini-source crate version pin shared with Lexer-Tokenizer (FM11), which is a build-time, not runtime, coordination cost.

Practical ceiling and the levers beyond it: the practical single-core ceiling is memory-bandwidth-bound (§35 rows 2/7); the lever beyond it is horizontal scaling across cores/hosts (trivial, above) or the deferred full-simdjson pre-pass (M11, PhaseDeferred("§22.4")) for a further ≈ 3× on JSON specifically.

33. Mental Models & First Principles

  • MM1 — A parser is a function from input-state to (output, new-state) or failure. Predicts: any two parsers compose via bind without special-casing success/failure threading (Hutton & Meijer 1996). Bug class without it: hand-threading position/ remaining-input manually, causing off-by-one span bugs. Applies in §11 (Parser/ IResult), §13 (Phase 1).
  • MM2 — Ordered choice is a function, not a set union. alt(a,b) is deterministic and directional (Ford 2004). Predicts: reordering alternatives changes which one wins on overlapping input. Bug class: assuming alt commutes like the CFG |. Applies in §14 (Phase 2), §6 (P6).
  • MM3 — Error vs. Failure is a commitment protocol, not a severity level. Error means "I haven't decided what I am yet"; Failure means "I know what I am and this input is wrong for it." Predicts where to place cut. Bug class: cutting too early (loses legitimate backtracking) or too late (garbage error messages, FM3). Applies in §17 (Phase 5), §7 (I2).
  • MM4 — Memoisation trades space for eliminating re-derivation, not for correctness. Packrat doesn't change what parses, only how fast (Ford 2002). Predicts: a grammar's result set is identical with or without memoize; only wall-clock changes. Bug class: assuming memoize fixes a semantically wrong grammar. Applies in §19 (Phase 7), §9 (ADR-05).
  • MM5 — Left recursion is a fixed-point computation. Seed-and-grow is iteration toward a least fixed point over "parse length" (Frost, Hafiz & Callaghan 2007). Predicts: growth is monotonic and terminates because input length is finite. Bug class: an empty- alternative left-recursive rule that never strictly grows (non-terminating fixed point). Applies in §19 (Phase 7), §7 (I6).
  • MM6 — A span is a claim about provenance, not just a range. Every ByteSpan asserts "this exact byte range produced this exact value" — the foundation of error messages and IDE tooling. Predicts: a combinator that discards spans downstream loses debuggability permanently. Bug class: writing a combinator that returns O without a span and being unable to add error-highlighting later without a breaking change. Applies in §11 (ByteSpan), §6 (P5).
  • MM7 — Streaming Incomplete is "not yet", never "no". The third IResult outcome is a temporal statement, not a correctness one. Predicts: a correct streaming driver never treats Incomplete as failure. Bug class: catching Incomplete in a generic error handler and surfacing it to the user as "parse error." Applies in §18 (Phase 6), §7 (I9).
  • MM8 — Monomorphisation vs. erasure is a compile-time/run-time cost swap, not a feature difference. Both produce identical parse results; only where the cost is paid differs. Predicts: a correctness benchmark comparing them is meaningless — only compile time and throughput differ. Bug class: choosing erasure "for safety" (there is no safety difference) instead of for compile-time relief. Applies in §23 (Phase 11), §9 (ADR-02, ADR-07).

35. Back-of-Envelope Capacity Model

  1. Packrat memory, worked case. Formula: input_bytes × memoised_rules × bytes_per_entry. The §20 Pratt/arithmetic benchmark's 1,000,000-token expression, memoising 4 rules (expr/term/factor/one auxiliary) at ≈ 32 bytes/entry (C5): 1,000,000 × 4 × 32 = 128 MB. This is why packrat is opt-in (P7, ADR-05) — memoising indiscriminately on a 4 GiB input (C1) at even 5 rules would be 4.29×10⁹ × 5 × 32 ≈ 687 GB, obviously infeasible.
  2. Cores to saturate a 10 GbE link with JSON parsing. Formula: link_bytes_per_sec / single_core_throughput. 10 GbE ≈ 1.25 GB/s; M1's 500 MB/s per core ⇒ 1.25×10⁹ / 5×10⁸ = 2.5 → 3 cores, each independent (C10, I5/I11 — no shared state needed).
  3. HTTP request-rate ceiling from parse throughput alone. Formula: throughput_bytes_per_sec / avg_request_bytes. At M2's 100 MB/s and a ≈700-byte average request-line+headers: 10⁸ / 700 ≈ 142,857 requests/s of pure parse work per core (excludes IO/syscall overhead, which dominates in practice).
  4. Error-tree stack footprint at concurrency. Formula: C14_bytes × thread_count. At 192 bytes/error (C14) × 64 threads = 12.3 KB aggregate — negligible; confirms the error-tree design does not bound concurrency.
  5. Recursion stack budget vs. a pathological JSON blob. Formula: depth × bytes_per_ frame. Default limit 256 × 2 KiB (C3) = 512 KiB, comfortably under an 8 MiB thread stack (15× headroom); an unguarded 10,000-level-deep blob would need 10,000 × 2 KiB = 20 MiB — 2.5× the default stack, which is exactly why T1's 256 default exists.
  6. Left-recursion cost collapse from memoisation. Formula (unmemoised worst case): rules × input_length² (each grow step re-parses from scratch, Frost/Hafiz/Callaghan 2007). For the 1M-token benchmark with 4 rules: 4 × (10⁶)² = 4×10¹² operations unmemoised. With packrat (Ford 2002): rules × input_length = 4×10⁶ operations — a 10⁶× reduction, the entire point of combining Ford's linear-time packrat with Frost/Hafiz/Callaghan's seed-and-grow.
  7. Compile-time scaling, mono vs. erased. From §23's worked numbers (90 s mono / 8 s erased at 50 rules): per-rule compile cost ≈ 1.8 s (mono) vs. 0.16 s (erased). Extrapolating to a 200-rule grammar (total ≈ per_rule × rule_count): mono ≈ 360 s (6 min — likely CI-unacceptable), erased ≈ 32 s — the concrete argument behind ADR-02's "past ~40 rules, prefer erasure" guidance.
  8. Fuzzing execution budget for Sealed. Formula: days × seconds_per_day × execs_per_sec. At 30 days (M10) and an assumed ≈2,000 execs/s (typical libFuzzer throughput on a small grammar target): 30 × 86,400 × 2,000 ≈ 5.18×10⁹ executions before Sealed.
  9. Conformance suite per-bucket time budget. Formula: total_budget / bucket_count. M8's ≤90 s aggregate over 23 buckets (§24.5) ⇒ ≤ 3.9 s/bucket average — flags any single bucket consuming disproportionate wall-clock for investigation.
  10. many0 vs. fold0 allocation churn. Formula: N × sizeof(O) × growth_factor. For N=10,000 matches of an 8-byte output with Vec's ≈1.5× amortized geometric growth: 10,000 × 8 × 1.5 ≈ 120 KB transient Vec churn per parse for many0; fold0's accumulator lives in a register/local ⇒ ≈0 bytes — the concrete argument for P8's JSON-literal-fast-path preference (§22).

37. Alternative Architectures (Roads Not Taken)

A1 — Hand-written recursive descent (no combinator abstraction).

                     dispatch on next input byte
                                  |
        +----------+----------+----------+----------+----------+
        |          |          |          |          |          |
       '{'        '['        '"'      digit/'-'   't'/'f'    'n'
        |          |          |          |          |          |
  parse_object parse_array parse_string parse_number parse_bool parse_null
        |          |          |          |          |          |
        +----------+----------+----------+----------+----------+
                                  |
                            Value (one AST node)

Regime: a single, small, stable grammar where maximal throughput and zero dependency overhead matter more than reuse across grammars. Real system: rustc_parse (rustc's own parser is hand-written recursive descent); CPython's pre-3.9 parser. Why rejected: this project ships seven grammars (§24); a combinator abstraction pays for itself once you have more than one, since every hand-written grammar would otherwise re-derive its own error-tree/span discipline from scratch (§2's "why build this" thesis directly).

A2 — LALR/yacc-style table-driven parsing (grammar file → generated shift-reduce automaton).

+--------+  shift/reduce   +---------------+
| State  | --------------> | Parse Table   |
| Stack  | <-------------- | (generated)   |
+--------+   pop/goto      +---------------+

Regime: large, static, unambiguous CFGs where the grammar file itself is valuable documentation and generation happens once at build time. Real system: yacc/bison; lalrpop (Rust). Why rejected: LALR grammars are strictly less expressive at the "local, ad hoc lookahead" tasks this library targets (e.g. distinguishing RFC 2822 from RFC 3339 date-times by peeking a few bytes, §24.6), and shift-reduce conflict debugging is a worse authoring experience than PEG's deterministic-by-construction semantics (§6 P6); it also loses the "the grammar is the parser" readability that makes §24's corpus legible.

A3 — Compile-time PEG-to-code generator (grammar in a separate file, codegen at build time, no runtime combinator trait).

grammar.pest --[build.rs codegen]--> generated_parser.rs --[compile]--> binary

Regime: teams wanting the grammar reviewable by non-Rust-literate stakeholders as a standalone artifact, or zero per-call dynamic-dispatch/monomorphisation bloat in the compiled binary. Real system: pest (§5 Reference Implementations). Why rejected: couples the grammar's evolution to a code-generation build step (slower dev-loop iteration than an in-crate macro or plain combinators, §21) and makes runtime introspection (e.g. a REPL that inspects the grammar) harder because the grammar is not a first-class Rust value.

A4 — GLR/Earley general parsing (ambiguity-preserving, all derivations returned).

      /--- derivation A
input ---- derivation B   (parse forest, not a single tree)
      \--- derivation C

Regime: genuinely ambiguous grammars (natural language, some markup dialects) or incremental/error-tolerant editor parsing where "return every valid interpretation" beats "return the first one." Real system: tree-sitter (GLR-derived, incremental, error- tolerant); Marpa (Earley). Why rejected: none of the seven shipped grammars (§24) are ambiguous; paying Earley's/GLR's worse-than-linear worst case for grammars that are unambiguous by construction is a pure loss, and a multiple-parse-forest output doesn't match the "one AST in, one AST out" contract downstream projects depend on (§2).

39. Glossary

  • Parser combinator — a higher-order function that builds a parser from smaller parsers.
  • Stream trait — the input abstraction (§11.1); byte-slice, &str, and token-iterator backends all implement it.
  • IResult<I,O,E> — the canonical combinator return type: Ok, Err::Error, Err::Failure, or Err::Incomplete.
  • Err::Error — a recoverable parse failure; alt retries the next alternative.
  • Err::Failure — a committed parse failure; alt propagates it without retrying.
  • Err::Incomplete — a streaming-mode signal that more input is needed; not a failure.
  • Needed — the payload of Incomplete: Unknown or Size(n).
  • ParseError<I> — the structured error tree: position, expected set, context chain, kind.
  • ErrorKind — the closed (per-version) enum naming which leaf combinator failed.
  • Expected set — the deduplicated list of what would have made the current position succeed.
  • Context (label chain) — the stack of named rules a failure occurred inside, rendered as "while parsing X > Y".
  • cut — the combinator that converts Error to Failure, marking a commit point.
  • Commit point — the position past which a grammar is "known" and backtracking should not occur.
  • Ordered choice (PEG) — alt's deterministic, directional alternative-selection rule (Ford 2004).
  • Ambiguity — a grammar where more than one derivation matches the same input; deliberately out of scope here (§37 A4).
  • Backtracking — re-trying an alternative after a recoverable failure.
  • Packrat parsing — memoising every rule at every position for linear-time PEG parsing (Ford 2002).
  • Memoisation — caching a computation's result keyed by its inputs.
  • Left recursion — a rule that (directly or indirectly) calls itself as its first alternative.
  • Seed-and-grow — the algorithm that resolves left recursion inside a packrat parser (Frost, Hafiz & Callaghan 2007).
  • Head-set (Warth) — the tracked set of mutually left-recursive rules re-evaluated together during growth (Warth & Piumarta 2007).
  • Pratt parsing — operator-precedence parsing via binding powers (Pratt 1973).
  • Binding power — the pair of numbers (Power(left,right)) that determines operator precedence and associativity direction.
  • Associativity (Assoc) — whether repeated same-precedence operators group left, right, or not at all.
  • Fixity — whether an operator is prefix, infix, or postfix.
  • BoxedParser — the type-erased, dynamically-dispatched combinator wrapper (§11.8).
  • Monomorphisation — compiling a generic function once per concrete type instantiation.
  • Type erasure — hiding a concrete type behind a trait object (dyn), paying an indirect-call cost for compile-time/binary-size relief.
  • ByteSpan — a half-open byte range plus file identifier (§11.5).
  • FileId — an opaque handle identifying a source file within a MultiFileSource.
  • LineColumn — a 1-based line/column pair resolved on demand from a ByteSpan.
  • MultiFileSource — the shared source-text registry spans are resolved against.
  • recognize — the combinator returning the consumed slice instead of the inner parser's output.
  • flat_map — the monadic-bind combinator: the first parser's output selects the next parser.
  • map_res — maps a parser's output through a fallible function, preserving position.
  • Streaming mode — the combinator variant returning Incomplete on a partial buffer.
  • Complete mode — the combinator variant treating the buffer as final (Eof on shortfall).
  • Conformance suite — the corpus-driven test harness gating every combinator and shipped parser (§29).
  • Fixture — a named input/expected-output pair in a conformance corpus.
  • Snapshot testing — pinning a rendered output (e.g. an error message) and reviewing diffs explicitly (insta, ADR-15).
  • Fuzz target — an entry point cargo-fuzz drives with generated/mutated input.
  • recursion_limit — the configurable ceiling on nested combinator call depth (T1, C2).
  • rule_id — the integer key identifying a rule inside a MemoTable.
  • MemoTable — the per-invocation cache mapping (rule_id, position) to a cached IResult.
  • Generation counter — the Memo field tracking which seed-and-grow iteration produced an entry.
  • EBNF — Extended Backus-Naur Form, the grammar notation used throughout this document (§8.1).
  • parser! macro — the declarative grammar DSL that expands to plain combinator chains (§21).
  • Reference implementation — an existing, real library studied for lessons and pitfalls, not copied (§5).
  • Tail latency — the p99/worst-case latency tail, here derived from throughput rather than measured against a live SLO (§4 C9).
  • Throughput — bytes parsed per second, the primary performance axis for this library (§31).
  • Sealed — the release gate certifying all M-table targets, 30-day fuzz-clean status, and outside whitepaper review are met (§30).
  • Whitepaper — the outside-reviewed design document required for Sealed (papers/whitepaper/whitepaper-v1.0.md).
