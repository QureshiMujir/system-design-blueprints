Decisions (§9) · 22 ADRs

ADR-01

Core implementation language

Chosen

Rust, stable, edition 2024

Rejected

C++ (Boost.Spirit); Haskell (as impl language)

When the rejected choice is right

Haskell wins for a pure-functional research prototype where throughput is secondary; Boost.Spirit wins when the codebase is already all-C++ and cannot add a Rust toolchain

Why: Rust's trait system expresses Parser<I,O,E> without macro-metaprogramming abuse; zero-copy &[u8] lifetime story is native

ADR-02

Combinator dispatch strategy

Chosen

Monomorphised generics, opt-in erasure

Rejected

Always-dynamic dispatch (chumsky-style); macro-generated match tables (pest-style)

When the rejected choice is right

Dynamic dispatch wins past ≈40 grammar rules where compile time dominates iteration speed (§35 row 7); macro tables win when the grammar is fixed at build time and zero runtime overhead is required

Why: Hot-path throughput by default; erasure is a per-boundary opt-in (ADR-07)

ADR-03

Choice semantics

Chosen

PEG ordered choice (Ford 2004)

Rejected

CFG nondeterministic union; GLR ambiguity-preserving

When the rejected choice is right

GLR/CFG wins for genuinely ambiguous grammars (natural language, some markup dialects) — tree-sitter's regime (§37 A4)

Why: Deterministic backtracking composes cleanly with alt/cut; unambiguous by construction for all 7 shipped grammars

ADR-04

Error discipline

Chosen

Error/Failure + explicit cut (Parsec try ported)

Rejected

Single Result<T,String>; exception-based errors

When the rejected choice is right

Result<T,String> wins for a throwaway one-off parser where error quality is irrelevant

Why: Error-tree quality past 2 levels of nesting requires the commit-point protocol

ADR-05

Packrat memoisation default

Chosen

Opt-in memoize(rule)

Rejected

Always-on full packrat; disable memoisation entirely

When the rejected choice is right

Always-on wins for grammars known to be heavily ambiguous with shared sub-parses and unconstrained memory (natural-language parsers); disabling memoisation entirely wins for simple LL(1)-shaped grammars with no left recursion, where the memo table has no offsetting benefit

Why: O(input×rule) memory is wasted on non-shared, non-left-recursive rules

ADR-06

Left-recursion strategy

Chosen

Frost/Hafiz/Callaghan seed-and-grow + Warth head-set tracking

Rejected

Hand grammar rewriting; disallow left recursion entirely

When the rejected choice is right

Grammar rewriting wins for a small, static grammar (rewrite once, zero runtime cost); disallowing wins for no_std targets where the memo table is unaffordable

Why: Composes with the existing Parser/alt surface without forcing users to rewrite grammars

ADR-07

Erasure escape hatch

Chosen

BoxedParser, opt-in per boundary

Rejected

Mandatory boxing; no boxing ever

When the rejected choice is right

Mandatory boxing wins for a plugin system loading grammar fragments across a dynamic-library ABI boundary

Why: Lets a caller trade throughput for compile time exactly where needed

ADR-08

Streaming semantics

Chosen

Per-call-site Streaming/Complete split (nom-7 style)

Rejected

Whole-library streaming-only; whole-library complete-only

When the rejected choice is right

Streaming-only wins for a protocol library with no concept of a final buffer (a long-lived TCP framer); complete-only wins for config-file parsers with the whole file already in memory

Why: A grammar mixes modes ("streaming to the top-level value, complete inside it")

ADR-09

Diagnostic reporter integrations

Chosen

ariadne + codespan-reporting, both feature-flagged

Rejected

Pick one; build a custom renderer

When the rejected choice is right

A custom renderer wins when the host app already has a diagnostic pipeline (e.g. its own LSP) neither crate integrates with

Why: Both crates have downstream users; feature-flag rather than force migration

37. Alternative Architectures (Roads Not Taken)

A1 — Hand-written recursive descent (no combinator abstraction).

                     dispatch on next input byte
                                  |
        +----------+----------+----------+----------+----------+
        |          |          |          |          |          |
       '{'        '['        '"'      digit/'-'   't'/'f'    'n'
        |          |          |          |          |          |
  parse_object parse_array parse_string parse_number parse_bool parse_null
        |          |          |          |          |          |
        +----------+----------+----------+----------+----------+
                                  |
                            Value (one AST node)

Regime: a single, small, stable grammar where maximal throughput and zero dependency overhead matter more than reuse across grammars. Real system: rustc_parse (rustc's own parser is hand-written recursive descent); CPython's pre-3.9 parser. Why rejected: this project ships seven grammars (§24); a combinator abstraction pays for itself once you have more than one, since every hand-written grammar would otherwise re-derive its own error-tree/span discipline from scratch (§2's "why build this" thesis directly).

A2 — LALR/yacc-style table-driven parsing (grammar file → generated shift-reduce automaton).

+--------+  shift/reduce   +---------------+
| State  | --------------> | Parse Table   |
| Stack  | <-------------- | (generated)   |
+--------+   pop/goto      +---------------+

Regime: large, static, unambiguous CFGs where the grammar file itself is valuable documentation and generation happens once at build time. Real system: yacc/bison; lalrpop (Rust). Why rejected: LALR grammars are strictly less expressive at the "local, ad hoc lookahead" tasks this library targets (e.g. distinguishing RFC 2822 from RFC 3339 date-times by peeking a few bytes, §24.6), and shift-reduce conflict debugging is a worse authoring experience than PEG's deterministic-by-construction semantics (§6 P6); it also loses the "the grammar is the parser" readability that makes §24's corpus legible.

A3 — Compile-time PEG-to-code generator (grammar in a separate file, codegen at build time, no runtime combinator trait).

grammar.pest --[build.rs codegen]--> generated_parser.rs --[compile]--> binary

Regime: teams wanting the grammar reviewable by non-Rust-literate stakeholders as a standalone artifact, or zero per-call dynamic-dispatch/monomorphisation bloat in the compiled binary. Real system: pest (§5 Reference Implementations). Why rejected: couples the grammar's evolution to a code-generation build step (slower dev-loop iteration than an in-crate macro or plain combinators, §21) and makes runtime introspection (e.g. a REPL that inspects the grammar) harder because the grammar is not a first-class Rust value.

A4 — GLR/Earley general parsing (ambiguity-preserving, all derivations returned).

      /--- derivation A
input ---- derivation B   (parse forest, not a single tree)
      \--- derivation C

Regime: genuinely ambiguous grammars (natural language, some markup dialects) or incremental/error-tolerant editor parsing where "return every valid interpretation" beats "return the first one." Real system: tree-sitter (GLR-derived, incremental, error- tolerant); Marpa (Earley). Why rejected: none of the seven shipped grammars (§24) are ambiguous; paying Earley's/GLR's worse-than-linear worst case for grammars that are unambiguous by construction is a pure loss, and a multiple-parse-forest output doesn't match the "one AST in, one AST out" contract downstream projects depend on (§2).
