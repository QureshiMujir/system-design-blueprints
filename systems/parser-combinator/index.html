In one paragraph

A parser combinator library lets you build a parser for a file format or protocol by snapping small parsers together with ordinary function calls, instead of generating code from a grammar file (§1, §2). This design, mini-comb, is a Rust library that reads bytes, &str or tokens without copying them, tries alternatives in a fixed order, and returns a structured error tree that reporters render as a readable message (§1, §3). It adds opt-in caching with left-recursion support, operator-precedence parsing, and resumable parsing of half-arrived buffers (§1). It is embedded in a host program, not run as a service (§1, §4). Its users are Rust engineers who would otherwise reach for nom or chumsky (§1).

The problem, concretely

Rust already has two good combinator libraries, and they disagree. nom turns every chain of combinators into one concrete type, which runs fast but compiles slowly. chumsky hides the types behind dynamic dispatch, which compiles quickly but runs slower. Every downstream user inherits whichever trade the library made (§2).

Hand-writing a parser has its own traps, each of which the blueprint names:

  • Alternatives in the wrong order. Trying foo before foobar means foobar can never match in full, and nothing at compile time warns you (§14.6, §14.9, P6).
  • A loop that matches nothing. Wrap an optional parser in "repeat zero or more times" and it matches the empty string forever: a hang with no crash and no log line (§15.6, §15.9).
  • A useless error message. A parser that keeps trying alternatives after it has already seen a distinctive prefix reports a diluted "expected one of: [50 items]" (P4, §17.9, FM3). With a commit point after the { of a JSON object, the blueprint's trace of the input {"a": } reports "expected a value after :" with a line and column (§8.4).
  • Left-recursive grammars. A rule like expr = expr "+" term / term needs special handling. The blueprint uses seed-and-grow, and the alternatives are rewriting by hand or banning it (§8.5, ADR-06).
  • A half-arrived TCP buffer. The parser must say "not yet" rather than "no" (§2, MM7).
  • Memory. Caching every rule at every position costs memory in proportion to input size times the number of cached rules (C4, P7).

How it works, end to end

Follow one parse call through the boxes of §3. The names are the blueprint's own crates (§1, §10). This diagram is adapted from §3, with the labels shortened:

 Reference parsers: parsers-http, -json, -csv, -net, -rfc-dates, -sexp   (Phase 12, §24)
      |                       |                         |
 mini-comb-pratt        mini-comb-memo           mini-comb-macros
 (Phase 8, §20)         (Phase 7, §19)           (Phase 9, §21)
      |                       |                         |
 mini-comb-core: primitives | branch/repetition | mapping/recognition | error tree
      |                                          |
 Stream<'a> backends: &[u8] / &str /        ParseError<I> tree:
 token iterator / partial buffer            Expected + Context + Err::{Error,Failure,Incomplete}
      |                                          |
 mini-source: ByteSpan, LineColumn, FileId, MultiFileSource, Reporters
 mini-comb-erased::BoxedParser cuts across every box above (Phase 11, §23)
  1. Reference parsers. The top box is a set of parsers-* crates, each both a demonstration and a source of test fixtures. Input here is untrusted network or file bytes (§3, §24, P11).
  2. Three optional accelerators. mini-comb-pratt (operator precedence), mini-comb-memo (caching and left recursion) and mini-comb-macros (a grammar macro) each sit on the core. None needs the others, and each keeps its own state per top-level parse, never shared across threads (§3).
  3. Combinator core. mini-comb-core holds the Parser and Stream traits, the primitives, branching, repetition, mapping, the error tree and the streaming variants. Bytes flow up through Stream, and an IResult flows back down (§3, §11, §13-§18).
  4. Stream backends. &[u8] is the ground truth, and &str and token backends are derived from it. They borrow the caller's buffer, so nothing is copied (§3, P1, P2).
  5. Error tree and spans. ParseError<I> is the only channel from "a parser failed" to a human message, and reporters are pure functions over it (§3, P12). mini-source is shared with the Lexer-Tokenizer project, and one position type across both is "non-negotiable" (§3, P2).
  6. Erased escape hatch. mini-comb-erased::BoxedParser cuts across every box. The caller boxes at exactly the recursion boundary that needs compile-time relief, never library-wide (§3, §23).

The blueprint's own unit of work is the input {"a": } against a JSON object grammar. object matches { and commits, then member reads "a" and :. value tries object, array, string, number and the literals, and each recoverably fails on }. Because that happened after the commit, the failure is reported at the object boundary as "expected a value after :", with the context chain object, members, member (§8.3, §8.4). The core ideas below take that trace apart.

The core ideas

One success, three kinds of "no" (§8.2, §11.2, P4)

A parser takes input and returns either success (rest, output) or one of three kinds of "no" (IResult, §11.2):

Outcome Plain meaning What alt does with it (§8.2)
Ok((rest, out)) matched return immediately
Err::Error "this alternative did not match" try the next alternative on the original input
Err::Failure "I know what this is and it is wrong" (committed) propagate, do not try the next
Err::Incomplete "I need more bytes" propagate, do not try the next

The reason there are three failure shapes and not one is that Error means "I haven't decided what I am yet", Failure means "I know what I am and this input is wrong for it", and Incomplete means "not yet" (MM3, MM7). Each backend implements the one Stream trait, which must be Copy so that retrying an alternative stays cheap (§11.1, §14.6, P2).

Ordered choice: first match wins (§8.2, §14, I1, P6)

Ordered choice (PEG, Ford 2004) is the rule that alt(a, b) tries a first and only tries b if a recoverably failed. It is a function, not a set union, so reordering changes the answer (MM2, I1). The blueprint's own test is alt(tag(b"foo"), tag(b"foobar")) on the input "foobar", which matches only "foo" (§14.4). Three rules explain it:

  1. alt tries tag(b"foo") first, and on Ok it returns immediately (§8.2, §14.2).
  2. So tag(b"foobar") is never tried. This is the surprise that alt(short, long) makes long unreachable (§14.6).
  3. Reordering alternatives is a silent behaviour change, not a compile error (§14.9, MM2).

opt turns Error into "nothing" but never absorbs a Failure (§14.2, I10).

Commit points: cut and the error tree (§17, §8.4, I2, I10, MM3)

A commit point is the place after which backtracking is no longer allowed. The combinator cut turns a recoverable Error into a committed Failure, and it is the only thing that does (I2). Place it "immediately after consuming a distinctive discriminator prefix", such as the { of a JSON object (§17.2, §8.3). After a cut, no descendant alt in the same rule may silently absorb a later Failure (I10).

The error tree (ParseError) records the failure position, a set of what was expected and a stack of named contexts (§11.3, §17.2). Three rules make messages good:

  1. Every leaf adds its own Expected entry, and alt merges the sets across branches and removes duplicates, so three digit-matchers do not say "digit, digit, digit" (§17.2).
  2. labelled(p, "name") pushes a context on failure, so the reporter can show "while parsing X > Y" (§17.2).
  3. cut is a one-way door: too early loses legitimate backtracking, too late gives the 50-item message (§17.6, MM3, FM3).

In the §8.4 trace, value exhausts its alternatives with a recoverable Error. That Error sits inside the cut from object, so the enclosing chain converts it to a Failure (§8.4).

Left recursion as growing a seed (§8.5, §19, I5, I6, MM5)

Left recursion is a rule that calls itself as its first step, such as expr = expr "+" term / term. Packrat caching (memoisation, Ford 2002) stores each rule's result per (rule_id, position) so that revisiting is O(1), and seed-and-grow (Frost/Hafiz/Callaghan) handles the recursion on top of it (§19.2, I5). The blueprint's trace on 1+2+3:

  1. Seed expr at position 0 with Err::Error(LeftRecursion). The recursive branch hits the seed and fails, so the non-recursive term matches 1 (length 1) (§8.5, §19.2).
  2. Grow: re-run with the seed set to 1. The recursive branch matches 1+2 (length 3, longer), so it replaces the seed (§8.5).
  3. Grow again: 1+2+3 (length 5, longer), so it replaces the seed again. One more grow finds nothing longer and stops (§8.5).

The result is the left-associative (1+2)+3 (§8.5). Growth terminates because each step must consume strictly more input than the last (I6, MM5). For indirect recursion, Warth's head-set tracking re-evaluates the whole cluster of mutually recursive rules (§19.2). One gap: the seed's LeftRecursion kind (§8.5, §19.2) is not among the ErrorKind variants that §11.3 lists (§11.3).

Streaming: "not yet" is not "no" (§18, I9, MM7, P10)

Streaming mode is a variant of each primitive that returns Incomplete(Needed) when the buffer ends too soon, where the complete mode variant returns an Eof error. The choice is per call site, not per library, so a grammar can stream up to the top-level value and be complete inside it (P10, §18.2, ADR-08). The driver contract has three steps:

  1. A primitive hits the end of the buffer and returns Incomplete, with Needed::Size(n) when the shortfall is known and Needed::Unknown otherwise (§18.2). It has consumed nothing (I9).
  2. The caller appends more bytes and re-runs the same top-level parser from the same position (§18.2).
  3. alt never retries the next branch on Incomplete. A driver that feeds zero new bytes spins forever, which the blueprint calls a caller bug (§18.6).

Operator precedence by binding power (§20, §11.7, ADR-02)

A Pratt climber parses expressions like 1 + 2 * 3 using a pair of numbers per operator called a binding power, Power(left, right) (§11.7, §20.2). A left-associative operator has left < right (the blueprint's example is + = Power(10,11)), and a right-associative operator has left > right (^ = Power(20,19)) (§20.2). The algorithm parse_expr(min_bp) reads one atom, then loops: peek an operator, stop if its left power is below min_bp, otherwise consume it and recurse with its right power as the new minimum (§20.2). The acceptance test pins three results (§20.4):

Input Expected tree What it checks
1 + 2 * 3 Add(1, Mul(2,3)) precedence
2 ^ 3 ^ 4 Pow(2, Pow(3,4)) right-associativity
-3! Neg(Fact(3)) prefix binds looser than postfix

Writing a right-associative pair the wrong way round, (19,20) instead of (20,19), is "the single most common Pratt bug" (§20.6).

The climber applies cut after each operator, because without it an outer alt can swallow a missing right operand and return a wrong but plausible shorter parse (§20.2, §20.6).

The trade-offs — where engineers disagree

Monomorphise by default, erase on request (ADR-02, ADR-07)

Chosen: monomorphised generics, with BoxedParser as an opt-in erasure per boundary, giving hot-path throughput by default (§9, P3). Rejected: always-dynamic dispatch (chumsky-style) and macro-generated match tables (pest-style) for ADR-02; mandatory boxing and no boxing ever for ADR-07 (§9). When the rejected choice is right: dynamic dispatch wins "past ≈40 grammar rules where compile time dominates iteration speed", and macro tables win when the grammar is fixed at build time and zero runtime overhead is required (§9, §35 row 7). For ADR-07, mandatory boxing wins for a plugin system loading grammar fragments across a dynamic-library ABI boundary (§9).

PEG ordered choice (ADR-03)

Chosen: PEG ordered choice (Ford 2004), which is deterministic, composes with alt and cut, and is unambiguous by construction for all seven shipped grammars (§9). Rejected: CFG nondeterministic union, and GLR ambiguity-preserving parsing (§9). When the rejected choice is right: "GLR/CFG wins for genuinely ambiguous grammars (natural language, some markup dialects)", the regime of tree-sitter (§9, §37 A4).

Errors and failures with an explicit cut (ADR-04)

Chosen: the Error/Failure split with an explicit cut, ported from Parsec's try, because error quality past two levels of nesting needs the commit-point protocol (§9, P4). Rejected: a single Result<T,String>, and exception-based errors (§9). When the rejected choice is right: Result<T,String> wins for a throwaway one-off parser where error quality is irrelevant (§9).

Packrat is opt-in (ADR-05)

Chosen: an opt-in memoize(rule), because O(input x rule) memory is wasted on rules that are neither shared nor left-recursive (§9, P7, C4). Rejected: always-on full packrat, and no memoisation at all (§9). When the rejected choice is right: always-on wins for heavily ambiguous grammars with shared sub-parses and unconstrained memory, such as natural-language parsers. Disabling it wins for simple LL(1)-shaped grammars with no left recursion (§9). The blueprint's cost illustration is a 1,000,000-token expression with 4 memoised rules at about 128 MB (§35 row 1).

Streaming chosen per call site (ADR-08)

Chosen: a per-call-site Streaming/Complete split in the style of nom 7, so one grammar can mix modes (§9, P10). Rejected: a whole-library streaming-only or complete-only design (§9). When the rejected choice is right: streaming-only wins for a protocol library with no concept of a final buffer, like a long-lived TCP framer. Complete-only wins for config-file parsers whose whole file is already in memory (§9).

Roads not taken (§37, §38)

Hand-written recursive descent (§37 A1) wins for a single, small, stable grammar where throughput and zero dependencies matter more than reuse. rustc_parse and the CPython parser before 3.9 are examples. It loses here because the project ships several grammars, and each would re-derive its own error and span discipline (§37 A1, §24).

LALR/yacc-style tables (§37 A2) win for large, static, unambiguous grammars where the grammar file is valuable documentation (yacc, bison, lalrpop). They lose here on ad hoc local lookahead, and on the authoring experience of debugging shift-reduce conflicts (§37 A2).

Build-time PEG-to-code generation (§37 A3) wins when non-Rust stakeholders must review the grammar as a standalone file (pest). It loses here because it couples grammar evolution to a build step and makes the grammar harder to inspect at runtime (§37 A3).

GLR/Earley parsing (§37 A4) wins for genuinely ambiguous grammars and for incremental, error-tolerant editor parsing (tree-sitter, Marpa). It loses here because none of the shipped grammars are ambiguous and a parse forest does not match the "one AST in, one AST out" contract (§37 A4).

Deferred features (§38) wait for triggers: the full simdjson-style pre-pass when M11's 3 GB/s becomes a hard requirement, the async driver when Event-Loop needs it, and a hosted service when a customer asks for a non-Rust-host API. Incremental re-parsing and GLR mode are "not currently planned" (§38).

What must never be false

  • I1: alt tries branches in declaration order, first success wins. Noticed by the branch.alt bucket; no telemetry (§7).
  • I2: Error is recoverable and Failure is committed; only cut converts one to the other. Noticed by the commit.cut bucket; parser_commit_count, test harness only (§7).
  • I3: a successful combinator's remainder never sits before its input. Noticed by a proptest on split_at monotonicity (§7).
  • I4: a zero-width match inside many0/fold0/separated_list0 becomes Err::Failure(ManyMN(0,0)). Noticed by the repetition.many0 bucket (§7, FM2).
  • I5: (rule_id, position) identifies exactly one memo entry. Noticed by a debug-mode assertion on insert (§7).
  • I6: each grow step consumes strictly more input than the last. Noticed by the packrat.left_rec bucket (§7).
  • I7: every ByteSpan satisfies start <= end <= source length. Noticed by the recognize.span bucket (§7).
  • I8: the &str backend never splits mid-codepoint; split_at returns None. Noticed by a proptest over random split points (§7).
  • I9: a combinator returning Incomplete has consumed nothing. Noticed by the streaming.tag bucket; parse_incomplete_retry_count (§7).
  • I10: after a cut, no descendant alt in the same rule silently absorbs a later Failure. Noticed by the commit.cut bucket; its recovery is a code-review rule (§7).
  • I11: both backends give span-equivalent results on input valid in both. Noticed by a differential test over a shared corpus (§7).
  • I12: core combinators do zero heap allocations per successful call, excluding Vec growth in the many0 family and the error path. Noticed by an allocation-counting CI job; combinator_alloc_bytes (§7).
  • I13: the parser! macro's expansion of a fixed grammar is byte-identical across supported compilers. Noticed by a golden-output test (§7).

What breaks in production

A library has no production traffic, so the blueprint's "incident" is a fuzz-found panic or a conformance regression (§27). The failure classes below are the instructive ones.

FM1: left-recursion non-termination. The symptom is a parser that hangs or runs out of memory on a left-recursive rule. The root cause is a grow step that does not strictly lengthen the parse, which is a bug in leftrec.rs and not a grammar bug. It is detected by a benchmark timeout in CI. There is no automatic recovery. Kill the process and inspect the MemoTable::generation trace, where a generation that repeats without the seed growing points at the bug (§26, §19.9).

FM2: infinite loop on a zero-width match. The symptom is a spinning process. The cause is a combinator inside many0 or fold0 that succeeds without consuming input. The guard from I4 converts it into Err::Failure(ManyMN(0,0)) automatically, and the error carries the offending position (§26). Without the guard it is "the most expensive-to-diagnose failure class in the whole library" (§15.9).

FM3: error-message quality collapse. The symptom is "expected one of: [50 items]". The cause is a cut missing at the discriminator boundary. The only reliable signal is an insta snapshot diff on a pull request, because the bug produces no test failure. The recovery is to add the cut at the right place (§26, §17.9).

FM4: streaming stall. The symptom is a driver that keeps re-requesting input and never completes. The cause is a combinator that returns Incomplete without converging, or a peer that stopped sending. Detection is a threshold on parse_incomplete_retry_count, which the caller emits and the library does not (§26, §18.9). Recovery is a connection-level timeout.

FM5: packrat memory blow-up. The symptom is climbing RSS. The cause is too many rules wrapped in memoize, which the blueprint says is "inherent" cost and not a bug. It is detected by RSS sampling in benchmarks/packrat_left_rec.rs, and there is no automatic recovery. The manual fix is to memoise only left-recursive or shared-prefix rules (§26).

Threats worth knowing (§25):

  • T1, stack overflow from 10,000+ nested delimiters, is stopped by a recursion_limit of 256 by default (C2), which returns a bounded Err::Failure(RecursionLimit) and not a crash.
  • T2, quadratic backtracking when alternatives share a long common prefix, is met by opting in to memoize on those rules. Its detection is listed as a "benchmark regression gate (M8)", although M8 is the conformance-suite timing row (§25, §31).
  • T3, unbounded memory from many0 or separated_list0 on adversarial input, is stopped by many_m_n(0,max,p) caps in every shipped parser, returning Err::Error(ManyMN) past the cap.
  • T10, a peer sending one byte at a time to force a per-byte re-parse, is met by driver discipline: feed chunks of at least a minimum size, with backpressure delegated to the Event-Loop project.

The blueprint disagrees with itself in three places here. Both sides are given, unresolved:

  • Compile time of a 50-rule grammar. P3 offers "12 s compile / 500 MB/s or 8 s compile / 180 MB/s" for a 50-rule grammar (P3). C12 puts 12 s on the macro grammar and about 90 s on the hand-written monomorphised equivalent, and §23.4 and §35 row 7 use 90 s monomorphised against 8 s erased (C12, §23.4, §35 row 7).
  • Which phase owns the gates. §31 says "Phase-0 gates: M1, M2, M3, M5, M6, M8", but its own table gates M1 at §22 and §24, M5 at §20, and M2, M3, M6 and M8 at §24 (§31).
  • Phase 0 duration. §1 gives "Phase 0 (crates 1–6 above) — 8 weeks", while Appendix B gives Phase 0 as 1 week and describes it as the skeleton and smoke parser (§1, §41, §12).

How it compares

The comparison table (§34) covers six real libraries; each paragraph names the niche where one wins.

  • nom chose monomorphisation only, with no erasure hatch. That is right when compile time never matters and throughput at minimal binary size is the only axis, as in embedded protocol parsers (§34).
  • chumsky chose dynamic dispatch by default plus an error-recovery DSL. That is right past about 40 rules, where compile-time iteration speed dominates (§34, ADR-02).
  • pest chose build-time code generation from a .pest file. That is right when non-Rust stakeholders must review the grammar as a standalone file, at the cost of a build-step coupling (§34, §37 A3).
  • Megaparsec / Parsec chose Haskell with typeclass dictionary passing. That is right in a lazy pure-functional codebase where algebraic clarity beats zero-copy throughput, and it is the ancestor of the commit-point discipline (§34, §5).
  • ANTLR chose adaptive LL(*) lookahead and generated table-driven code. That is right for grammars too complex for bounded-lookahead PEG, or when one grammar must generate parsers in several languages (§34, §1).
  • Boost.Spirit chose C++ expression templates. That is right only in a legacy C++ codebase that cannot add a Rust toolchain, and its compile times are the cautionary tale behind ADR-02 (§34, §36 item 17).

Questions to test yourself

  1. Why does alt(tag(b"foo"), tag(b"foobar")) never match "foobar" fully, and which two design decisions — not just "PEG" — force that outcome? — Hint: P6 and §14.4, then ADR-03.
  2. Why is Err::Incomplete neither retried by alt nor converted by cut — what invariant would break if it were? — Hint: §8.2, §18.6 and MM7.
  3. Trace exactly how cut interacts with a nested alt two levels deep — does an inner alt's Err::Failure escape an outer alt untouched, and which invariant guarantees that? — Hint: §8.2 and §17.2, then I2 and I10.
  4. Why does packrat + left recursion need Warth's head-set tracking in addition to Frost/Hafiz/Callaghan's seed-and-grow, and what grammar shape (indirect left recursion) exposes the gap? — Hint: §19.2 and §19.8.

If you only remember three things

A parse has three outcomes, and Error, Failure and Incomplete are different promises, so cut is the one deliberate way to say "no turning back" (I2, MM3, MM7). Every costly feature, namely packrat caching, type erasure and streaming mode, is opt-in per rule or per call site because the cost is only worth paying where you choose it (P3, P7, P10). The conformance corpus is the proof, since the shipped parsers double as the test suite and the byte-slice backend is the ground truth the others are compared against (P1, P11, I11).

Words used here

  • Parser combinator: a function that builds a bigger parser out of smaller parsers (§39).
  • Ordered choice (PEG): try alternatives in written order and stop at the first success (§39, I1).
  • Err::Error: a recoverable failure, where alt tries the next alternative (§39, I2).
  • Err::Failure: a committed failure that alt passes up without retrying (§39, I2).
  • Err::Incomplete: "more input needed", which is not a failure (§39, I9).
  • Commit point / cut: where backtracking stops, and the combinator that marks it (§39, I2).
  • Expected set: the deduplicated list of what would have let the parse continue (§39, §17.2).
  • Packrat / memoisation: caching each rule's result per position for linear-time parsing (§39, MM4).
  • Seed-and-grow: resolving left recursion by re-parsing with a longer seed each time (§39, I6).
  • Binding power: the Power(left, right) pair fixing precedence and associativity (§39, §20.2).
  • Monomorphisation vs type erasure: one compiled copy per concrete type, against hiding the type behind dyn and paying an indirect call (§39, MM8).
  • ByteSpan: a half-open byte range plus a file identifier (§39, MM6).
  • Sealed: the release gate: all M-table targets, 30 fuzz-clean days, an outside whitepaper review and zero failing buckets (§39, §30).
