Hard questions (§36)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does a shape-tree transition for an attribute change preserve the slot index while a property-add transition allocates a new one — and what would break if it didn't? (§8.2, §16.2)
  2. Trace exactly what happens, tier by tier, when add(1,2) is called the 1st, 100th, and 1,000,000th time — which subsystem owns each transition? (§8.7, §20, §21)
  3. Why is a write barrier described as "part of the pointer-store instruction" rather than a separate step, and what invariant would silently break if it were merely "best-effort"? (§8.6, §18.5, MM6, I7)
  4. What is the concrete mechanism by which a monomorphic IC becomes unsound the instant a shape's prototype chain mutates, and how does the version-tag scheme prevent it? (§16.2, §17.2, I5)

  8. Contrast the failure mode of a missed write barrier (FM-1) with the failure mode of an unsound type-lattice narrowing (§21.9) — why are both "memory-safety bugs wearing performance- bug disguises" rather than simple correctness bugs? (§18.9, §21.9, T2)

  13. Why is the microtask queue engine-owned but host-drained, rather than either fully engine- managed or fully host-managed? (P10, §19.2, ADR-10)
  14. Trace how an adversarial script exploiting T4 (shape-tree exhaustion) is contained without a crash — what telemetry fires first, and what is the operator's diagnostic path? (T4, §16.10, §27)
  15. Why does the Comparative Architecture Table conclude that QuickJS's zero-JIT design is a legitimate "win" in some regime rather than simply an inferior, unfinished design? (§34, §37)

  17. Why must background optimising-tier compilation observe a "consistent snapshot" of IC feedback rather than the live, possibly-mid-update feedback vector? (§21.6, §16.2 version-tag)
  18. What is the precise difference between the Megamorphic IC state and the Generic state, and why does a Proxy force the latter rather than merely the former? (§8.3, §16.7, §17.2)
  19. Why does the design choose an in-tree assembler over Cranelift (ADR-16), and under what growth condition would that decision reverse? (ADR-16 6th column, §9)

33. Mental Models & First Principles

  • MM1 — "A shape is a type, not a value." The compressed insight: an object's shape describes its structure (which properties, in what order, with what attributes), never its property values (I6). Predicts: two objects can share a shape while holding entirely different data. Bug class without it: engineers "optimize" by trying to key caches on value type, producing shape-tree explosions or missed sharing. Applied in §16 (Phase 4), §8.2.
  • MM2 — "An inline cache is a bet, not a fact." The compressed insight: every IC fast path is a speculation validated by a guard, never an assumption baked in unconditionally (P3). Predicts: IC state can and will degrade; code that "assumes" monomorphism without a guard is unsound. Bug class without it: engineers skip the guard "because it's always this shape in practice" — exactly the CVE-class bug this design prevents structurally. Applied in §17 (Phase 5), §8.3.
  • MM3 — "Deoptimisation is the price of admission for speculation, not a failure." The compressed insight: every profitable speculative optimization requires an equally engineered bailout path (P4, ADR-08). Predicts: a design with speculation but no deopt path is unsound by construction, not merely incomplete. Bug class without it: "we'll add the safety net later" — the exact trap Hölzle/Chambers/Ungar's 1992 paper (§5) was written to prevent. Applied in §22 (Phase 10).
  • MM4 — "Most objects die young — design the collector around the exception, not the rule." The compressed insight: the generational hypothesis (Lieberman & Hewitt 1983, §5) means a collector optimized for short-lived objects wins on typical workloads even though it looks "wasteful" for the rare long-lived object. Predicts: naive flat mark-sweep loses to generational GC on allocation-heavy code despite conceptual simplicity. Bug class without it: over-engineering for the long-lived case at the cost of the common case. Applied in §18 (Phase 6), §8.6.
  • MM5 — "The bytecode is the seam; never let a tier reach across it." The compressed insight: every tier (interpreter, baseline, optimising) must derive its behavior from the same bytecode contract (P1) — never from the AST or from another tier's internal state directly. Predicts: any tier that reads the AST directly (bypassing bytecode) will eventually diverge from the others (I2 violation). Bug class without it: "just have the optimising tier peek at the AST for this one case" — a seam violation that compounds silently. Applied in §3, §14, §21.
  • MM6 — "A write barrier is not optional insurance — it is part of the pointer-store instruction." The compressed insight: in a moving generational collector, a bare pointer store is not a complete operation; the barrier is the second half of that operation (P6, I7). Predicts: any code path that stores a pointer "for efficiency" without the barrier is not faster, it is incorrect. Bug class without it: FM-1, the single worst class of bug in the codebase. Applied in §18 (Phase 6), §8.6.
  • MM7 — "OSR is a frame translation, not a restart." The compressed insight: promoting or demoting a running function mid-execution (P9) must preserve exact program state — it is a bijective mapping between two representations of the same point in execution, not a fresh start. Predicts: any OSR implementation that "just re-runs from the top" is unsound for functions with observable side effects before the promotion point. Bug class without it: double-executed side effects or lost state across a tier transition. Applied in §21 (Phase 9), §22 (Phase 10).
  • MM8 — "The embedder boundary is the only place untrusted code becomes trusted, and vice versa." The compressed insight: JS source is untrusted input; a registered native callback is trusted host code; the FFI boundary (§23) is where that trust level flips in both directions, and both directions need their own discipline (bytecode validation inbound, catch_unwind outbound). Predicts: a design that only guards one direction (e.g., validates bytecode but doesn't catch host panics) is asymmetrically unsafe. Applied in §23 (Phase 11), §8.8.

5. Required Reading

Books

  • Jones, Hosking, Moss — The Garbage Collection Handbook. Chs. 4 (mark-sweep), 5 (mark- compact), 6 (copying), 9 (generational), 11 (incremental). Applied in §18 (Phase 6, GC) and §8.6.
  • Drepper — What Every Programmer Should Know About Memory. All sections on cache lines and prefetch. Applied in §17.9 (IC stub locality) and §31 (Performance Engineering).
  • Aho, Lam, Sethi, Ullman — Compilers: Principles, Techniques, and Tools (2nd ed). Chs. 4 (parsing), 6 (IR), 8 (code generation). Applied in §13 (Phase 1, parser) and §14 (Phase 2).
  • Appel — Modern Compiler Implementation in ML. Chs. on SSA and register allocation. Applied in §21 (Phase 9, SSA IR + linear-scan allocator).
  • Muchnick — Advanced Compiler Design and Implementation. Chs. on CSE, LICM, bounds-check elimination. Applied in §21.5 (optimising-tier passes).
  • Cooper & Torczon — Engineering a Compiler (2nd ed). Chs. on lowering and dataflow. Applied in §14.2 (AST-to-bytecode lowering) and §21.3 (type inference dataflow).

Papers

  • Chambers, Ungar, Lee, 1989, OOPSLA — An Efficient Implementation of SELF. The maps (hidden-classes) paper. Applied in §16 (Phase 4, shape tree) and §8.2.
  • Deutsch & Schiffman, 1984, POPL — Efficient Implementation of the Smalltalk-80 System. The original inline-cache paper. Applied in §17 (Phase 5) and §8.3.
  • Hölzle, Chambers, Ungar, 1991, ECOOP — Optimizing Dynamically-Typed Object-Oriented Languages with Polymorphic Inline Caches. Applied in §17.2 (polymorphic IC design).
  • Hölzle, Chambers, Ungar, 1992, ECOOP — Debugging Optimized Code with Dynamic Deoptimization. Applied in §22 (Phase 10, deopt machinery).
  • Hölzle & Ungar, 1994, PLDI — Optimizing Dynamically-Dispatched Calls with Run-Time Type Feedback. Applied in §21 (Phase 9, feedback-driven speculation).
  • Gal et al., 2009, PLDI — Trace-based Just-in-Time Type Specialization for Dynamic Languages. (TraceMonkey.) Applied in §37 (Alternative Architectures, trace-JIT road not taken) and discussed in §21.7.
  • Cheney, 1970, CACM — A Nonrecursive List Compacting Algorithm. Applied in §18.3 (young-gen copying collector).
  • Lieberman & Hewitt, 1983, CACM — A Real-Time Garbage Collector Based on the Lifetimes of Objects. The original generational-GC hypothesis paper. Applied in §18.1 (generational heap layout) and MM4 (§33).

Reference Implementations

  • V8 (chromium.googlesource.com/v8/v8) — src/objects/ (maps), src/ic/, src/maglev/, src/compiler/ (TurboFan). Lesson: hidden-class transition trees at scale. Pitfall not to copy: V8's map has ~15 years of micro-tuned special cases; do not chase parity, chase the shape. Applied in §16, §17, §20, §21.
  • SpiderMonkey (Mozilla firefox-source-docs.mozilla.org/js/) — js/src/vm/, js/src/jit/, js/src/gc/. Lesson: the clearest production write-barrier implementation. Pitfall: its "shape" terminology collides with ours by coincidence, not design — do not assume identical semantics. Applied in §16, §18, §20.
  • JavaScriptCore (github.com/WebKit/WebKit, Source/JavaScriptCore/) — runtime/, bytecode/, dfg/, ftl/. Lesson: the four-tier LLInt/Baseline/DFG/FTL design that justifies our two-tier subset. Pitfall: do not adopt FTL's B3 backend complexity at our scale. Applied in §14, §15, §20, §21.
  • QuickJS (bellard.org/quickjs/) — single-file bytecode interpreter. Lesson: the smallest legible register-bytecode design in production. Pitfall: its single-tier (no JIT) design trades away exactly the speed this project targets — do not copy the no-JIT choice. Applied in §14, §15, and §37 (Alternative Architectures, single-tier road).
  • Hermes (github.com/facebook/hermes) — AOT bytecode compiler, no JIT. Lesson: correctness- kernel-first design discipline. Pitfall: Hermes's AOT-only model is a legitimate but different trade (mobile cold-start); do not conflate its goals with ours. Applied in §12 (Phase 0 design discipline) and §37.

RFCs / Specifications

  • ECMA-262 — the ECMAScript Language Specification (TC39, current edition). The canonical normative reference for every production and abstract operation. Applied throughout §13 (parser productions), §16 (object semantics), and gated by §24 (Test262).
  • Test262 (github.com/tc39/test262) — the conformance corpus; every phase gate cites it. Applied in §24.1 (bucket table) and every phase's N.5.
  • WHATWG HTML — Microtask Queuing — the host-integration model for Promise jobs. Applied in §19 (Phase 7, microtask queue) and I11.

Glossary (§39) · 39 terms · site-wide glossary

Atom
An interned string; canonical pointer used for O(1) identifier comparison (P7, §16.4).
Baseline JIT
Tier 1 of the JIT pyramid; template code-generator emitting patchable IC stubs (§20).
Bytecode
The versioned intermediate representation between the AST and every execution tier; the sole cross-tier contract (P1, §8.4).
Card table
A page-granularity (1 B / 512 B) marker of old-to-young pointer stores, the generational write barrier's remembered set (§18.5, ADR-26).
Compaction
The mark-compact pass that evacuates live objects to defragment the old gen (§18.2).
Deoptimisation (deopt)
Falling back from optimising-tier machine code to the interpreter on a speculation-guard failure, reconstructing an exact interpreter frame (P4, §22).
Dictionary shape
An out-of-line, non-transition-tree fallback shape used after a property delete, trading structural sharing for flexibility (§8.2).
ECMA-262
The ECMAScript Language Specification; the canonical normative reference (§5).
Elements backing store
The array-specific storage kind (packed, holes, dictionary) tracked independently of the object's shape (§16.2).
Feedback vector
A per-function array of FeedbackSlots, one per call site, recording observed shapes/callees for IC and optimising-tier consumption (§8.3, §11).
Generational GC
A collector exploiting the hypothesis that most objects die young, distinguishing a young and an old generation with different collection strategies (P5, §18).
Hidden class
A V8-coined synonym for "shape" — the type describing an object's property structure, shared across structurally identical objects (§8.2, Chambers/Ungar/Lee 1989).
Inline cache (IC)
A per-call-site stub that speculatively fast-paths a property/call operation based on previously observed shapes/callees (P3, §8.3, §17).
Incremental marking
A GC marking pass that runs in bounded slices interleaved with mutator execution rather than stopping the world (§18.2, ADR-06).
JIT
Just-in-time compiler; here, the baseline (tier 1) and optimising (tier 2) code generators (§20, §21).
Major GC
A collection pass over the old generation (mark-compact, §18.2).
Megamorphic
An IC state reached after 5+ distinct shapes/callees observed at one site; degrades to a shared, hashed slow-path stub (§8.3, §17.2).
Microtask
A queued unit of work (Promise reactions, etc.) drained by Context ::run_microtasks(), engine-owned, host-drained (P10, §19).
Minor GC
A collection pass over the young generation (Cheney copy, §18.2).
Monomorphic
An IC state where exactly one shape/callee has been observed at a site — the fastest, most common steady-state IC state (§8.3).
NaN-boxing
A 64-bit value encoding that repurposes IEEE-754 NaN payload space to tag non-double value kinds (§8.1, ADR-04).
Oddball
The spec term for the four singleton non-numeric primitive values: undefined, null, true, false (§8.1).
On-stack replacement (OSR)
Converting a running function's execution state between tiers mid-execution, in either direction (entry or exit/deopt) (P9, §21, §22).
Optimising tier
Tier 2 of the JIT pyramid; SSA-IR-based, type-feedback-driven, speculative compiler (§21).
Polymorphic
An IC state where 2–4 distinct shapes/callees have been observed at a site (§8.3, §17.2).
Promotion
Moving a young-gen object that has survived a threshold number of minor GCs into the old gen (§18.2).
Prototype chain
The linked sequence of prototype objects consulted during property lookup when the receiver's own shape lacks the property (§8.2, §16.2).
Realm
A complete, isolated set of intrinsics and globals; one per Context (§11, §23).
Rope string
A tree-shaped string representation used to amortise repeated concatenation to O(n log n) rather than O(n²) (§8.6-adjacent, ADR-27).
Shape
A node in the shared transition tree describing an object's property structure; synonym for hidden class in this document (§8.2, I3, I4).
SMI (small integer)
A tagged 31/32-bit integer fast path within the NaN-boxed Value encoding, avoiding double-boxing for common integer arithmetic (§8.1, P14).
Speculation
A type or shape narrowing made by the optimising tier based on observed feedback, always paired with a guard and a deopt path (P3, P4, §21).
Stack map
A per-safepoint table of live GC-relevant values and their locations, enabling precise (non-conservative) root scanning (I9, §20.2).
Test262
The TC39 conformance test corpus; the binding conformance oracle for this engine (ADR-19, §24).
Tiering
Promoting a function from a slower to a faster execution tier based on call-count or loop-back-edge thresholds (§20.2, §21.2).
Transition tree
The shared tree of shapes connected by property-add/change/delete edges; the data structure hidden classes are built from (§8.2, P2).
Tri-colour marking
The white (unvisited) / grey (queued) / black (scanned) marking discipline used by the incremental old-gen marker (§18.2).
Version tag
A per-shape counter bumped on any mutation affecting dependent IC validity, used to detect stale prototype-chain caches (§16.2, §17.2, I5).
Write barrier
A code sequence executed before/after a pointer store to maintain GC invariants (generational + SATB), inlined at every JIT site and interpreter handler (P6, I7).
