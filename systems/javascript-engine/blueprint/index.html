1. Goal & Scope

Comet is a from-scratch ECMA-262-conformant JavaScript engine in Rust: lexer, recursive-descent parser, register-bytecode compiler, threaded bytecode interpreter, a hidden-class (shape) object model with monomorphic → polymorphic → megamorphic inline caches, a generational moving garbage collector, a two-tier JIT (template baseline + speculative optimising tier) with deoptimisation, a promise/microtask/async/generator runtime, and a documented embedding API — engineered to reach Test262 pass-rate ≥ 99% on language/ + built-ins/ at v1.0 while staying small enough (< 15 MB resident at idle, §4) to embed in a desktop app, a server workload, or an edge function.

Phase-0 deliverable (numbered modules/crates, full detail §12):

  1. comet-frontend — lexer + recursive-descent parser + typed, span-tagged AST.
  2. comet-bytecode — register bytecode format + AST-to-bytecode lowering.
  3. comet-interpreter — threaded-dispatch bytecode interpreter.
  4. comet-object — NaN-boxed Value, Shape tree, atom table.
  5. comet-gc — young-gen copying collector + old-gen mark-sweep (mark-compact lands §18).
  6. comet-ic — monomorphic inline cache only (polymorphic/megamorphic land §17).
  7. comet — embedder facade (Engine, Context, Value, Error).
  8. conformance/ — Test262 runner wired into CI from commit 1.

System boundaries. Provides: full ECMA-262 execution, embedding API, conformance harness, GC, tiered JIT (from §20), deopt (§22). Delegates: regex execution to the portfolio's rank-61 regex engine via a documented trait (ADR-11); host event-loop scheduling to the embedder (P15); ICU/Intl to the embedder's ICU if present (PhaseDeferred("§38")). Does NOT provide: a DOM, a module bundler/package manager, TypeScript type-checking, a WebAssembly runtime (PhaseDeferred("§38")), a debugger UI.

Non-goals: browser-grade sandboxing against OS-level exploits (V8/JSC own that budget, §34); matching V8 peak throughput (§34 concedes the gap explicitly); every Annex B legacy quirk beyond the documented ≥ 70% bucket (§24.1 row annexB).

Deployment model: linked as a Rust crate (rlib/cdylib) or via the C ABI (comet-c-abi) into a host process. No engine-managed network or disk I/O. One Engine hosts N Context realms.

Target users/operators: embedders needing a small, auditable JS runtime (desktop apps, edge functions, IoT, server-side script sandboxes), and the on-call engineer debugging a GC pause or deopt storm in production via the runbooks (§27).

What later phases unlock: §17 → polymorphic/megamorphic ICs; §18 → old-gen compaction + incremental marking; §20–§22 → the full JIT + deopt safety net; §24 → 99% Test262 + a 30-day fuzz-canary sign-off.

Language + rationale: Rust 2021 edition (ADR-01). A GC-plus-JIT system is dominated by manual-memory and type-confusion bugs in C/C++ — V8's, SpiderMonkey's, and JSC's own CVE histories are majority memory-safety defects in exactly this kind of code. Rust's ownership model catches the non-unsafe majority at compile time and confines genuinely unsafe code (raw heap pointers, JIT code emission, NaN-boxing bit tricks) to small, audited modules (P16). Rejected languages: C++ (no compile-time aliasing discipline — rejected on the CVE evidence above); Go (a GC hosting a GC'd runtime cannot bound its own pause time independently, defeats P5); Zig (no mature concurrent-GC or JIT-assembler ecosystem at project start).

Prerequisites: compiler front-end theory (grammars, recursive descent, precedence climbing), IEEE-754 bit layout, generational-GC theory (Cheney copying, mark-compact, write barriers), SSA form and dataflow analysis, cache-line-level performance intuition (Drepper, §5), calling- convention-level ABI knowledge for x86-64 and aarch64.

Estimated timeline: Phase 0 — 1 week. Full system (Phase 0–12) — 34–36 weeks (~8–9 months), per the milestone table (Appendix B, §41).

Deferred features (each PhaseDeferred("§38"), registered in the Deferred Features Register, §38): ECMA-402 (Intl); a documented WebAssembly host bridge; a fully concurrent (no-stop-the- world) old-gen marker; a Chrome-DevTools-compatible heap-snapshot format; V8-style source maps for stack traces; Stage-3 Decorators; a Maglev-style mid-tier JIT.

2. Why Build This

A JavaScript engine is the canonical system whose spec is open-ended (ECMA-262 grows yearly), whose performance contract is adversarially competitive (V8/SpiderMonkey/JSC spend six-figure compiler-engineer-years on milliseconds), and whose attack surface is the entire web. A tree- walking interpreter is a weekend; a production engine is a multi-year exercise in keeping the parser's lookahead bounded, the interpreter's dispatch fast, the GC's pause time low, the object model's allocation cheap (hidden classes + ICs, P2/P3), the optimising tier's speculation profitable and its deoptimisation correct (P4, ADR-08), and JIT-emitted machine code memory- safe (P16).

Teams that embed JavaScript in production reach for V8, SpiderMonkey, JavaScriptCore, QuickJS, or Hermes and discover, often mid perf-audit, that V8 is 50 MB resident and needs ICU at runtime, SpiderMonkey's embed API is thin, JSC drags WebKit, QuickJS is small but slow, and Hermes is small and fast but omits the Proxy trap surface. Teams on a focused engine (V8 for browsers, Hermes for React Native, QuickJS for small embeds) get a binary sized to their use case and a predictable perf profile (§34 compares all four). That tight focus is the deliverable here.

Cross-links: this project shares the "small, speculative, tiered execution engine" shape with the portfolio's WASM runtime (stack-machine + validated bytecode) and the SQL query planner (cost- model-driven tiering); it differs from both in owning a mutable, shape-changing object model — the single hardest invariant in this class of system (I3–I6).

What Mastery Looks Like (5–8 competencies, each tied to a phase):

  • Derive why hidden classes turn property access from O(chain-length) hashing into O(1) slot loads, and reproduce the SELF team's 1989 argument from first principles — §16 (Phase 4).
  • Explain exactly why an inline cache is speculation, not optimisation, and trace a site's monomorphic → polymorphic → megamorphic degradation on real feedback — §17 (Phase 5).
  • Reconstruct, from a guard failure, the exact register-to-slot map an optimising compiler must emit to resume correctly in the interpreter — §22 (Phase 10).
  • Explain why a generational hypothesis (most objects die young) justifies a Cheney copying young gen and a mark-compact old gen, and compute the promotion-threshold trade-off — §18 (Phase 6).
  • Diagnose a live deopt-storm or megamorphic-call-site regression from tracing telemetry alone, using the runbooks — §27 (Operational Readiness).
  • Defend, with real numbers, why this design trades V8's peak throughput for a 15 MB footprint — §34 (Comparative Architecture) and §35 (Back-of-Envelope Capacity Model).

Embedder API. The only host-facing surface; owns lifetime of Engine/Context, exposes Value coercions and native-function registration (§23). Trust boundary: the host is trusted, script content is not.

Frontend. Concurrency boundary: none — single-threaded, per-Context. Produces the typed AST that is the sole input to §14; owns the only place Unicode/ASI/regex-disambiguation ambiguity is resolved (I1).

Bytecode Compiler. Persistence boundary: bytecode may be cached to disk by the embedder (content-hashed, ADR-19-adjacent); the compiler itself is stateless per compilation unit.

Interpreter. The GC-root scanning boundary: every interpreter frame is a conservative (Phase 0–7) or precise (Phase 8+, I9) root set. It is the only tier required for correctness; JITs are speed, never correctness, overlays (P8).

Object Model / Inline Caches. The mutation boundary: shapes are immutable and shared (P2); an IC site is local, per-call-site, mutable state that is speculative (P3) and must be sound under concurrent mutation of the shape it caches (I5).

Garbage Collector. The memory-safety boundary: every heap pointer crossing a generation or GC-safepoint must go through a write barrier (P6, I8); this is the design's single largest correctness surface.

Baseline JIT / Optimising Tier. The codegen trust boundary: JIT-emitted machine code executes with the same privileges as the interpreter; a codegen bug is a memory-safety bug, not just a perf regression (T2, threat model).

Host Bridge. The queue boundary between engine-internal semantics (Promise reactions, await) and the host's own scheduler; the host drains microtasks explicitly (§19.2, I11).

Consistency rule: every later section (Domain Model §8, Repository Layout §10, phases §12–§24) must name these same eight boxes and no others; a new subsystem requires updating this diagram.

6. Design Principles

  1. P1 — The bytecode is the only contract. AST is internal to the frontend; machine code is internal to the JITs; bytecode is the sole boundary crossed by every consumer tier. Opcode re-ordering is a major-version bump. Tradeoff: any bytecode change is expensive to review. Operational implication: bytecode caches must be invalidated on version bump. Violating it (letting a tier read the AST directly) collapses the tiering discipline entirely.
  2. P2 — Shapes are immutable and shared. A shape is (parent, transition-key, attributes, slot-table); objects move along the shape tree as structure evolves. Tradeoff: shape-tree growth is unbounded under adversarial property churn (T4). Operational implication: shape-tree size is a monitored metric. Violating it (mutating a shared shape in place) corrupts every object sharing that shape.
  3. P3 — Inline caches encode feedback, not optimisation. An IC records "what has been seen here"; the optimising tier reads that as type hints, never bypasses the IC discipline. Tradeoff: IC state adds a memory cost per call site. Violating it (hard-coding a shape assumption without a guard) removes the deopt safety net (P4) and is a memory-safety bug.
  4. P4 — Speculation requires deopt. Every optimising-tier speculation emits a guard plus a compensation path that reconstructs an interpreter frame. Tradeoff: every guard is a branch cost in the hot path. Operational implication: deopt rate is a monitored metric (M8). Violating it makes JITted code unsafe under any input the speculation didn't anticipate.
  5. P5 — Generational GC is the default. Most objects die young (Lieberman & Hewitt, §5); young gen is a semi-space Cheney copier, old gen is mark-compact. Tradeoff: promotion is a tunable that trades minor-GC frequency against old-gen pressure (§31). Violating it (flat mark-sweep only) costs 30–50% more collector time on allocation-heavy workloads (§34).
  6. P6 — Write barriers are pervasive and cheap. Every heap-pointer write goes through a barrier, inlined at every JIT site and interpreter handler. Tradeoff: ~3–5 cycles per pointer store (§18.10). Violating it (a missed barrier) produces a silent use-after-free at the next GC — the single worst class of bug in this system (FM-1).
  7. P7 — Strings are interned aggressively. Identifiers and short literals are atoms; atom comparison is pointer comparison. Tradeoff: the atom table itself needs GC-rooting and a reclaim pass (§16.10). Violating it makes every identifier comparison an O(n) string compare.
  8. P8 — The JITs are tiered, never load-bearing for correctness. Interpreter is tier 0 (always correct); baseline (tier 1) and optimising (tier 2) exist purely for speed and must produce results identical to tier 0 (I2, cross-tier fuzzing). Violating it (a JIT-only semantic) is an automatic correctness bug.
  9. P9 — OSR is bidirectional. A hot interpreter loop promotes mid-loop (OSR entry, §21); a guard failure demotes mid-execution (OSR exit / deopt, §22). Tradeoff: both directions need a register/slot mapping kept in lockstep with the bytecode's local-slot layout. Violating either direction strands execution in an inconsistent frame.
  10. P10 — The microtask queue is engine-owned, host-drained. Context::run_microtasks() is the only drain point; the engine never runs its own event loop. Tradeoff: an embedder that forgets to drain starves all promises. Violating it (engine self-scheduling) removes the host's ability to interleave engine work with its own I/O.
  11. P11 — No global state. Engine and Context are values; many coexist. Tradeoff: every subsystem must be parameterised by context, costing an extra pointer indirection. Violating it (a process-global atom table, e.g.) makes multi-tenant embedding unsafe.
  12. P12 — The regex engine is a bridge, not an implementation. Rank-61's regex engine is consumed via a documented trait (ADR-11). Tradeoff: a version mismatch between the two projects is a real integration risk (FM-9). Violating it (embedding a second regex engine) doubles the maintenance and conformance-testing surface.
  13. P13 — Strict mode is the default; sloppy-mode quirks are opt-in and phase-gated. Tradeoff: legacy scripts relying on sloppy semantics need an explicit compatibility flag. Violating it (defaulting to sloppy) reintroduces with, unscoped var-hoisting surprises, and arguments aliasing bugs into the default path.
  14. P14 — Numerics are IEEE-754 double, SMI-optimised, BigInt separate. SMI packs 31-bit integers in the tagged representation; overflow falls to double; BigInt is its own heap type. Tradeoff: SMI-to-double transitions are a shape-invariant, not value-invariant, concern (I6). Violating it (always-boxed numbers) costs an allocation per arithmetic op.
  15. P15 — The host owns the event loop. This engine never runs setTimeout; the Phase-0 demo embeds a trivial scheduler only for smoke tests. Violating it re-implements a competing event loop against the host's, guaranteeing scheduling conflicts.
  16. P16 — No surprises in API shape. Every public type is #[non_exhaustive]; every panic path is documented and exists only on contract violation; errors are typed, never Box<dyn Error>. Violating it breaks embedder forward-compatibility on any internal refactor.

8. Domain Model

8.1 Value Representation

64-bit NaN-boxed Value. A double's IEEE-754 quiet-NaN payload space is repurposed to encode every non-double type; a canonical double is never itself a NaN-boxed-tag collision because the tag range is chosen inside the signalling-NaN payload space unreachable by real arithmetic.

bit 63..48: tag (16 bits)         bit 47..0: payload (48 bits)
tag 0x0000..0xFFF8  -> IEEE-754 double (untagged, direct bit pattern)
tag 0xFFF9          -> SMI          payload = i32 in low 32 bits
tag 0xFFFA          -> Oddball      payload = {Undefined, Null, True, False}
tag 0xFFFB          -> HeapObject   payload = 48-bit pointer (Object)
tag 0xFFFC          -> HeapString   payload = 48-bit pointer (String)
tag 0xFFFD          -> HeapSymbol   payload = 48-bit pointer (Symbol)
tag 0xFFFE          -> HeapBigInt   payload = 48-bit pointer (BigInt)
tag 0xFFFF          -> HeapFunction payload = 48-bit pointer (Function)

Type-test predicates are a mask + compare on the tag (P14). SMI range is [-2^31, 2^31-1]; arithmetic overflow falls through to the double encoding (ADR-04). A 48-bit payload covers every production 64-bit host's user-space address range (no host ships > 2^48 B of address space today).

8.2 Object Model: Hidden Classes (Shapes)

An object's header holds a shape pointer + an in-object slot array; a shape is a node in a shared transition tree: (parent, transition-key: (name, attrs), slot-table) (P2, I3, I4). Property lookup is: compute the shape's slot index for name (O(1) via the shape's own small hash map, not a rehash of the whole object) → read the in-object slot, or the out-of-line property bag if the index exceeds the in-object budget (8 slots, Phase-0 default, §16.2).

Transition discipline (I3):

Operation Transition label Slot effect
Add property (full attrs known) (name, attrs) New child shape; new slot index appended
Change attribute (e.g. freeze) (name, new-attrs) New shape; slot index preserved
Delete property (name, DELETE) New shape; slot becomes a hole; object may fall to a dictionary (out-of-line) shape
Change prototype n/a — invalidates the whole shape lineage Forces a full re-walk (documented slow path, T4)

8.3 Inline Caches

A feedback vector holds one slot per call site. State machine (I5, P3):

Uninitialised --(1st shape seen)--> Monomorphic
Monomorphic  --(2nd distinct shape)--> Polymorphic (holds 2-4 shape+slot tuples)
Polymorphic  --(3rd..4th distinct shape)--> Polymorphic (append)
Polymorphic  --(5th distinct shape)--> Megamorphic (global hashed lookup, no per-site growth)
Any          --(semantics defeat IC, e.g. Proxy)--> Generic (spec [[Get]]/[[Set]] slow path)

Progress-only: an IC never regresses to a lower state absent function recompilation (I5). A LoadIC stub layout: (1) load feedback-slot pointer, (2) branch on state tag, (3) per-state shape check(s) + slot load, (4) tail-call the slow path on miss. Stub budget: < 256 B/site (§17.9); megamorphic sites share one stub to bound code growth.

8.4 Bytecode ISA & Interpreter

Register-based, three-address, 1-byte opcode + register-index operands + optional constant-pool immediate (P1). Selected opcode family (illustrative signatures, not exhaustive):

LoadIC   dst, obj_reg, feedback_slot          ; I5 fast path: shape check + slot load
StoreIC  obj_reg, src, feedback_slot
LoadElem dst, obj_reg, idx_reg, feedback_slot
Call     dst, callee_reg, argc, arg_base
Add | Sub | Mul | Div | Mod | Pow  dst, lhs, rhs   ; SMI fast path, double fall-through
Jump / JumpIfFalse / JumpIfNullish  target
NewObject dst, shape_hint

Interpreter dispatch: computed-goto threaded where the host supports asm goto; switch-threaded otherwise (P8). Each handler ends in the next-opcode dispatch; the frame is (return PC, function ptr, this, local-slot array, captured-env ptr) laid out contiguously (§8.7 worked example below).

8.5 JIT Tiers

Tier Trigger Codegen strategy Correctness role
0 — Interpreter always active threaded dispatch over bytecode sole correctness authority (P8)
1 — Baseline JIT ≥ 10 calls per-bytecode template codegen, patchable IC stubs speed only; must match tier 0 (I2)
2 — Optimising ≥ 1000 loop back-edges or 100 baseline calls SSA IR, type-feedback-narrowed, inlined, linear-scan alloc speed only; guarded by deopt (P4)

Deoptimisation (§22) is the mandatory compensation path any time tier 2's speculation (on shape, callee identity, element kind, bounds, integer-ness — §21.10) proves wrong at runtime: unwind the optimised frame, reconstruct an interpreter frame via the compile-time register-to-slot map, and resume at the recorded bytecode offset (I10).

8.6 Garbage Collector

Generational, moving (P5). Young gen: two semi-spaces, bump-pointer allocation, Cheney copy on minor GC (Cheney 1970, §5). Old gen: mark-compact with a free-list sweeper. Card table: 1 byte / 512 B of heap, dirtied by the generational write barrier (P6, I7) on every young-into-old pointer store. Incremental marking runs in < 1 ms slices interleaved with the mutator (SATB pre-barrier combined with the generational post-barrier into one inlined sequence, ~5 cycles steady state, §18.10).

8.7 Worked Example — function add(a,b){return a+b} called 1, 100, 1e6 times

  • Call 1 (interpreter, tier 0): LoadIC/Add bytecode executes; the Add handler observes both operands are SMI, computes the sum, checks for SMI overflow (falls to double if so); the feedback slot for this call site records "SMI+SMI" as the first observation (Uninitialised → Monomorphic per §8.3).
  • Call 100 (tier 1, baseline JIT): the call-count threshold (10) has tiered the function up; the baseline JIT emits a template sequence for Add that inlines the SMI fast path directly, consulting the now-Monomorphic feedback slot; a shape check is not needed here (no property access), but the type check (SMI-ness) is the analogous guard. emits, plus IC stubs for any property access add might contain (none, in this example).
  • Call 1,000,000 (tier 2, optimising): the loop/call-count threshold (1000) has tiered the function to the optimising tier; the SSA IR carries a CheckType(SMI) guard node before an unguarded Int32Add, narrowed from the accumulated feedback (§21.3); the emitted machine code is a single hardware add instruction plus an overflow-check branch — no dispatch, no IC probe. If a later call passes a Double or a String (defeats the SMI narrowing), the guard fails, triggering a deopt (§8.5, §22) back to the interpreter with a/b reconstructed from the optimising tier's register allocation.

8.8 Malformed-Input Example

Input: a bytecode module supplied directly to the embedder API (pre-compiled bytecode path, ADR- 19) with an out-of-range constant-pool index in a LoadIC operand. The loader validates every opcode's operand against the constant-pool bound at Bytecode::load time (I13); an out-of-bound index is rejected before any interpreter frame is constructed, surfaced as Error::InvalidBytecode { offset, reason: "constant pool index out of range" }. This is a hard reject, not a runtime trap — accepting an unchecked index would let adversarial bytecode read arbitrary heap memory (T2, threat model).

8.9 Failure-Path Example

A megamorphic property-access site inside a hot loop (adversarial shape churn, T4): the IC degenerates Monomorphic → Polymorphic → Megamorphic within the first 5 distinct shapes (§8.3); the optimising tier, observing a Megamorphic feedback slot, declines to speculate on shape at all and emits the generic [[Get]] slow path instead of a guarded fast path — a documented, intentional performance cliff rather than a correctness failure. Telemetry (ic.megamorphic.site_count) surfaces the site; the runbook (docs/runbook/megamorphic-call.md, §27) walks the operator through identifying the offending call site via JitStats and recommends a monomorphising code change (e.g. splitting a polymorphic helper into per-shape variants) — the engine does not auto-remediate.

None load-bearing yet — Phase 0 has no performance acceptance criterion by design; premature optimisation here risks locking in a data layout (e.g. Value, §8.1) before its full shape is known from later phases.

A red CI at this phase blocks every subsequent phase — the blast radius is the whole project timeline. Detection: ci.yml red on main. Containment: no phase work merges until green. Recovery: revert the offending commit; the skeleton has no persistent state to corrupt.

13. Phase 1 — Lexer & Parser

13.1 Objectives

Full UTF-8 lexer (UAX #31 identifiers) and recursive-descent parser producing a typed, span- tagged AST for ES2024-base scripts and modules, strict mode by default (P13).

13.2 Detailed Implementation Steps

  • Lexer: keywords, identifiers, punctuators, numeric literals (decimal/binary/octal/hex, BigInt n suffix, _ separators), string literals (\uXXXX, \u{X}), template literals (nested ${…}), regex literals disambiguated by parser context (not lexer-alone — ECMA-262 §12.9 is transcribed, never invented, per P13's sibling discipline and Required-Reading ECMA-262, §5).
  • ASI (automatic semicolon insertion) consults the line-terminator stream per spec; no heuristic invented locally.
  • Parser: cover grammar for arrow-vs-paren and async-vs-identifier (ECMA-262 §13.3/§15.4); typed AST nodes under comet-frontend/src/ast/, every node span-tagged (feeds §8.8's malformed-input discipline one layer up, at the bytecode loader).
  • Class lowering groundwork: private-name slot table allocated at parse time, consumed at lowering (§14).

13.3 Deliverable

Lexer + parser producing snapshot-tested ASTs for a 50-script corpus; disassemblable via comet disasm --ast script.js (debug-only flag).

13.4 Acceptance Criteria

  • Test262 language/ parser-tier subset ≥ 99% pass rate (named bucket, §24.1).
  • A 5 MB script parses in < 100 ms p50 on the reference host (§4).
  • AST snapshot fixtures for the 50-script corpus are byte-reproducible across two runs.

13.8 Edge Cases

13.9 Failure Analysis

A parser bug surfaces downstream as a confusing bytecode-compiler or interpreter error, not at the parser itself — the lexer/parser boundary is the contract (P1's frontend analogue). Detection: Test262 parser-tier regression. Containment: bisect via the AST-snapshot corpus. Recovery: fix at the parser; never patch around a parser bug in the bytecode compiler.

13.10 Operational Notes

Parse errors surface to the embedder as Error::SyntaxError { message, span } (§11); the span is carried through to any host-side source-map tooling. No tracing spans yet beyond parse duration (frontend.parse.duration_ms), consumed by §31's cold-start budget.

14. Phase 2 — Bytecode Compiler

14.1 Objectives

Lower the typed AST to the register bytecode defined in §8.4, honoring P1 (bytecode is the only contract) and I1 (deterministic, stable output for a given AST + EngineConfig).

14.2 Detailed Implementation Steps

  • Scope analysis: resolve every identifier to parameter / local / captured / global / intrinsic; TDZ tracking for let/const (spec-mandated); hoisting per spec (var to function/script scope, function decls hoist with value in strict mode, P13).
  • Lowering (compile/lower.rs): statement lowering to jumps; expression lowering to typed arithmetic/comparison opcodes (§8.4); optional-chaining/nullish-coalescing to skip-evaluation jump patterns; class lowering to a function + explicit prototype wiring + private-name slots (ADR-24 arena backs the AST these steps consume).
  • Constant-pool construction with dedup (numbers, atoms, regex patterns resolved at bind time, shape hints for known-shape call sites feeding §17's IC design).
  • Local-slot allocation: Phase-0-simple (one slot per AST temporary); liveness-aware coalescing is an explicit Phase-2+ stretch, not required for this phase's acceptance (I1 does not require optimality, only determinism).
  • Constant folding + dead-store elimination at lowering time (Muchnick, §5, applied here).
  • Source-position map: SLEB128 + delta-encoded bytecode-offset → (line, col).
  • Version-stamp every emitted Bytecode module (I13); a version bump is a documented ADR-level event (P1).

14.3 Deliverable

comet-bytecode produces deterministic, versioned bytecode for the Test262 language/ corpus; comet disasm script.js emits a human-readable listing with constant-pool resolution.

14.4 Acceptance Criteria

  • Bytecode compiler output is byte-identical across two compiles of the same AST + config (I1), verified over a 200-fixture snapshot corpus.
  • Constant-pool dedup ratio ≥ 90% on the SunSpider corpus (a proxy for compiler correctness on repeated literals, not a hard perf target).
  • Every snapshot fixture round-trips through disasm without a decode error.

14.5 Conformance Fixtures

Fixture Purpose Expected Output

corpora/bytecode/const_fold_literal_add.js constant folding single LoadConst opcode, no Add emitted

14.6 Pitfalls

  • Constant-pool without dedup blows up atom-table pressure on string-heavy scripts (P7).
  • Source-position maps are size-sensitive; the SLEB128+delta scheme is required, not optional — a naive (line, col) pair per offset roughly doubles bytecode-module size.
  • Reordering opcodes mid-version invalidates every snapshot fixture in one commit (P1) — pin the opcode table before Phase 2 exits.

14.7 Performance Concerns

Lowering must be single-pass where possible; a two-pass "collect scopes, then lower" design is acceptable but a third pass is a compile-latency budget violation (feeds the < 50 ms cold-start target, §4, gated fully at §20).

14.8 Edge Cases

A var declared inside a catch block interacting with hoisting; a computed class-field name that throws during evaluation; a destructuring pattern with a default value referencing an earlier-destructured binding (TDZ-adjacent); deeply nested optional chains (a?.b?.c?.d).

14.9 Failure Analysis

A non-deterministic bytecode compile (I1 violation) breaks the embedder's bytecode-cache correctness silently — a cached-then-reloaded function could execute stale semantics. Detection: the I1 snapshot-diff CI job. Containment: revert the offending compiler-pass commit. Recovery: invalidate any content-addressed bytecode cache keyed by the broken compiler version.

14.10 Operational Notes

tracing span bytecode.compile.duration_ms per function; bytecode.constants.dedup_ratio gauge. Compatibility: the bytecode version tag (I13) is the sole compatibility contract between this crate and comet-interpreter/comet-baseline/comet-opt — bump it, and every consumer crate's minimum-supported-version bumps in lockstep (§28).

15. Phase 3 — Bytecode Interpreter

15.1 Objectives

A correct, threaded-dispatch bytecode interpreter — the sole correctness authority (P8) that every later JIT tier is validated against (I2).

15.2 Detailed Implementation Steps

  • Frame layout (§8.4): (return PC, function ptr, this, local-slot array, captured-env ptr) contiguous on the interpreter stack.
  • Dispatch (dispatch.rs): computed-goto threading via asm goto where the host supports it; switch-threaded fallback otherwise (ADR-03's register design pays off here — fewer dispatches per operation than a stack machine).
  • Handlers (handlers/): arithmetic (SMI fast path, double fall-through, BigInt branch, P14); property (LoadIC/StoreIC/LoadElem — Phase 3 ships these as plain slow-path handlers; the IC fast path itself is §17's work, this phase only reserves the feedback-slot layout, I5); call (Call/CallNative/Construct — push frame, transfer, return); control (Jump/ JumpIfFalse/JumpIfNullish/Switch).
  • Conservative stack scanning for GC roots (I9's precise variant is Phase 8, ADR-25): any pointer-shaped word on the interpreter stack is a possible root at this phase.
  • "JS calling JS" fast path avoids re-entering the outer dispatch loop's setup cost.

15.3 Deliverable

The interpreter executes the full Test262 language/ corpus (not yet built-ins) end to end; a SunSpider-1.0 micro-benchmark subset runs without errors (not yet gated on speed, §20 gates that).

15.4 Acceptance Criteria

  • Test262 language/ ≥ 90% pass rate (named bucket language/expressions, language/statements, §24.1).
  • Zero panics across the full Test262 language/ corpus (a panic is always a Sev-0 defect at this phase — the interpreter must return Err, never unwind past its own boundary).
  • Frame-layout fixture corpus (corpora/interpreter/frame_*) passes for recursion depth ≥ 500.

15.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/interpreter/recursion_depth_500.js frame-stack correctness at depth correct return value, no corruption
corpora/interpreter/smi_overflow_to_double.js SMI→double arithmetic fallthrough (P14) correct Number result
corpora/interpreter/closure_capture.js captured-environment correctness closures observe correct captured values
corpora/interpreter/stack_overflow.js adversarial unbounded recursion Err(RangeError) at the documented depth ceiling, not a native stack overflow

15.6 Pitfalls

  • Computed-goto is unavailable on MSVC-class toolchains; the switch-threaded fallback is not optional, it is a required build target (§4 x86-64/aarch64 hosts include MSVC-toolchain aarch64 Windows).
  • Conservative stack scanning produces false retentions; document the impact now — the fix (I9, precise stack maps) is explicitly deferred to §20, not silently absent.
  • A latent lexer/parser bug (§13) surfaces here as a confusing interpreter-side error; the interpreter is not the place to patch a frontend defect.

15.7 Performance Concerns

Dispatch overhead dominates interpreter-tier throughput; the handler-table layout must keep hot opcodes (LoadIC, Add, Call, Jump) cache-resident — this is the baseline every later JIT tier is measured as a multiple of (§4's "≥ 2× interpreter" / "≥ 5× interpreter" targets, M2/M6).

15.8 Edge Cases

Recursive function without a base case (must hit the documented stack-depth ceiling as RangeError, never a native SIGSEGV); a for-in loop over an object whose shape changes mid- iteration; an arithmetic operation on NaN/Infinity/-0 (IEEE-754 edge values must round-trip exactly, P14); a closure capturing a let binding inside a loop (per-iteration binding semantics).

15.9 Failure Analysis

An interpreter panic is the single worst correctness regression at this phase — it means P8 (tier 0 is always correct) is violated. Detection: Test262 zero-panic gate in CI. Blast radius: total — every later tier assumes tier 0 is a safe fallback (I2, I10's deopt target). Containment: the offending opcode handler is reverted, not patched around, until root-caused. Recovery: no runtime recovery — this is a build-time gate, not a production failure mode.

15.10 Operational Notes

tracing spans: interpreter.dispatch.opcode_count, interpreter.frame.depth_max. The recursion depth ceiling is a configured EngineConfig value (default 10,000 frames), surfaced to the operator via HeapStats-adjacent InterpreterStats (not yet defined as a public type — deferred naming decision, tracked as a Phase-2+ stretch, not a Phase-3 blocker).

16. Phase 4 — Object Model: Values, Shapes, Atoms

16.1 Objectives

Build the shape tree (P2), the NaN-boxed Value encoding (§8.1), and the atom table (P7) — the central data structure the entire engine's performance flows from (Chambers/Ungar/Lee 1989, §5).

16.2 Detailed Implementation Steps

  • Value per §8.1's bit layout (ADR-04); type-test predicates as mask+compare.
  • Object header: shape pointer, hash, in-object slot array (8 slots default, Phase-0 constant); out-of-line property bag beyond that budget; element backing store variants (holes-allowed, packed, typed-array).
  • Shape construction per §8.2's transition discipline (I3, I4): property add walks the parent's transition table (a small per-shape hash map keyed on (name, attrs)), following an existing edge or allocating a child shape; attribute change and delete each produce distinct transition labels (never collapsed with name-only transitions, per the §16.9 pitfall below).
  • Atom table (atom.rs): per-Context interned-string table (P7); identifiers always interned; short literals (≤ 8 B) interned aggressively; GC-rooted via the Context (I12).
  • Prototype-chain caching groundwork: each shape carries a version_tag: u64, bumped on any mutation reachable from that shape's prototype position (feeds §17's IC validation, I5).
  • Special object kinds: Array (holes-allowed / packed / dictionary backing, magic length accessor), Function (bytecode ref + closure env + [[FunctionKind]]), String (exotic string object per spec), Arguments (mapped/unmapped per spec).

16.3 Deliverable

A shape system passing the shape-determinism corpus (N objects with an identical property-add history share one shape pointer, I3); an atom table passing the atom-canonicalisation corpus (I12); Test262 built-ins/Object subset ≥ 90%.

16.4 Acceptance Criteria

  • Shape-determinism corpus: 100% of objects constructed via an identical property-add sequence share exactly one shape pointer (I3, hard requirement, not a percentage).
  • Shape transition-table cache hit rate ≥ 99% on the SunSpider corpus (cache misses are the expected cost of genuine new-shape generation, not a defect).
  • Atom table: zero canonical-pointer collisions across a 1M-atom corpus (I12).

16.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/shape/identical_history_convergence.js I3 shape sharing one shape pointer for N objects
corpora/shape/attribute_change_preserves_slot.js attribute-change transition slot index unchanged, shape pointer changed
corpora/shape/delete_then_readd.js delete → dictionary fallback → re-add object migrates to out-of-line bag, documented heuristic honored
corpora/shape/prototype_change_invalidation.js setPrototypeOf invalidation version_tag bump observed on every dependent IC

16.6 Pitfalls

  • Attribute-change transitions must be a separate transition from name-only additions — collapsing them corrupts the slot-preservation guarantee (§8.2 table).
  • A shape's IC-keying hash must be stable across a GC move; carry it as a field, never the raw pointer address (interacts with §18's moving collector).
  • Out-of-line property bags must migrate back to in-shape storage on a delete-then-re-add pattern; document the exact heuristic threshold, don't leave it as an undocumented tuning knob.
  • A property whose value flips SMI↔double must never produce a new shape (I6) — the shape carries name+attributes, not runtime value type (P14).
  • Adding a property to Object.prototype invalidates every shape rooted there — a documented anti-pattern surfaced in the runbook (§27), not silently absorbed.

16.7 Performance Concerns

In-object slot budget (8) trades per-object memory against out-of-line-bag indirection cost; raising it reduces indirection for wide objects at the cost of larger empty-object footprint — tunable, not hard-coded past Phase 4 (§32 scalability note).

16.8 Edge Cases

Object.freeze/Object.seal attribute-change cascades across every own property in one call; Object.defineProperty changing a data property to an accessor (shape transition, not an in-place mutation); a Proxy-wrapped object interacting with shape lookups (defeats shape caching entirely by spec, documented not "fixed").

16.9 Failure Analysis

A shape-tree corruption (I4 violation — mutating a published shape) corrupts every object sharing it silently; the failure surfaces far downstream as an inexplicable property-value mismatch. Detection: miri + the shape-determinism corpus catch it at CI time, not in production (I4 is structurally enforced, no runtime detection needed). Recovery: not applicable in production — this class of bug must never ship; the type system (no &mut Shape post-construction) is the primary defense.

16.10 Operational Notes

Telemetry: shape.tree.node_count (monitors T4's adversarial-churn threat), shape.transition .cache_hit_rate, atom.table.size. The runbook documents diagnosing a shape-tree blowup via shape.tree.node_count growth rate.

17. Phase 5 — Inline Caches

17.1 Objectives

Monomorphic → polymorphic → megamorphic inline caches for property load/store/call/element sites (§8.3), the single most important performance feature in the engine (P3) — must land before tiering (§20+) has any feedback to consume.

17.2 Detailed Implementation Steps

  • Feedback vectors: one FeedbackSlot per call site per function (§11); state machine per §8.3 (Uninitialised → Monomorphic → Polymorphic → Megamorphic → Generic, I5 progress-only).
  • LoadIC: monomorphic stub = shape check + slot load; polymorphic stub = chain of 2–4 shape checks (ordered by observed frequency, Hölzle/Chambers/Ungar 1991 ECOOP, §5); megamorphic degrades to a hashed global property-table lookup, sharing one stub across sites to bound code growth.
  • StoreIC: property-add records (current shape, transition shape, slot index); property-replace is shape check + slot write; sloppy-mode attribute-change sites degrade straight to megamorphic (documented, not optimized further).
  • CallIC: records callee identity; direct-call on match; informs the inliner (§21.4) on stability.
  • ElementIC: records backing-store kind (packed/holes/dictionary) and element type uniformity.
  • Prototype-chain caching: chain of (shape, version_tag) pairs validated on every probe (§16.2); a version-tag mismatch forces IC re-derivation, never a stale fast path (I5).

17.3 Deliverable

LoadIC/StoreIC passing the IC-state-transition corpus; a 1M-iteration monomorphic property-access loop reading exactly one shape pointer per iteration in the steady state.

17.4 Acceptance Criteria

  • IC-state-transition corpus: 100% of transitions match the §8.3 state table exactly (no skipped or premature transitions).
  • Monomorphic IC hit rate ≥ 99% on the SunSpider corpus's property-access-dominated subset (M9, §31).
  • IC stub size < 256 B per site (measured on the baseline-JIT-emitted stub, §20.4).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/ic/mono_to_poly_second_shape.js monomorphic → polymorphic transition state = Polymorphic after 2nd distinct shape
corpora/ic/poly_to_mega_fifth_shape.js polymorphic → megamorphic transition state = Megamorphic after 5th distinct shape
corpora/ic/proxy_defeats_ic.js Proxy site degrades to Generic state = Generic, slow-path [[Get]] invoked
corpora/ic/prototype_mutation_invalidation.js version-tag invalidation dependent IC re-derives after prototype mutation

17.6 Pitfalls

  • Polymorphic stub chain order matters for cache locality; sort by observed frequency, not insertion order (Hölzle/Chambers/Ungar 1991).
  • A megamorphic site inside a hot loop is a documented perf cliff, not a bug — the runbook (docs/runbook/megamorphic-call.md) is the diagnostic path, not an auto-fix.
  • Concurrent IC compilation (once §20's baseline JIT exists) must observe a consistent shape snapshot; the version-tag is the synchronization point, not a lock.
  • The IC slow path must never be inlined into the fast path — the perf model assumes it is always a tail call (§8.3).

17.7 Performance Concerns

IC-state-transition corpus timing feeds M9 (§31); the feedback vector's memory layout (one FeedbackSlot per site, contiguous per function) must keep the common monomorphic case cache- resident — this is the P3/I5 discipline's entire performance payoff.

17.8 Edge Cases

An IC site that alternates between exactly 2 shapes forever (stays Polymorphic, never degrades — correct per the progress-only rule, I5); a delete producing a dictionary-shape object that then hits a previously-monomorphic IC site (forces Polymorphic, correct); an array index access past the packed-array bound (ElementIC transitions backing-store kind to holes, not a shape change).

17.9 Failure Analysis

A missed shape-version invalidation is a correctness bug, not merely a perf regression — an IC executing its fast path against a stale shape reads the wrong slot (I5 violation). Detection: the IC-state-transition corpus plus cross-tier fuzzing (I2) once JITs exist. Blast radius: silently wrong values, not a crash — the worst kind of defect in this subsystem. Recovery: none at runtime; this is a CI-gated class of bug, never shipped.

17.10 Operational Notes

Telemetry: ic.state.transitions_total{from,to}, ic.megamorphic.site_count, ic.fastpath .guard_fail_total. The megamorphic-call-site runbook is the primary on-call artifact for this phase's failure mode (§27).

18. Phase 6 — Generational Garbage Collector

18.1 Objectives

A generational, moving collector (P5, ADR-05): young-gen semi-space Cheney copier (Cheney 1970, §5), old-gen mark-compact with incremental (SATB) marking, write barriers pervasive and cheap (P6, I7).

18.2 Detailed Implementation Steps

  • Heap layout (heap.rs): young gen = two semi-spaces, bump-pointer allocation in to-space; old gen = mark-compact pages with a free-list-per-size-class allocator; large-object space for objects above a size threshold, allocated directly old-gen.
  • Minor GC (young.rs): scan roots (globals, stack, card-table remembered set) → copy reachable young objects to from-space → update forwarding pointers → promote survivors of N (default 2) minor GCs to the old gen.
  • Major GC (old.rs, marker.rs): tri-colour (white/grey/black) incremental marking in < 1 ms slices interleaved with the mutator (I7's SATB pre-barrier is the correctness mechanism); sweep builds a free list; compaction evacuates live pages when fragmentation crosses a threshold.
  • Write barriers (barrier.rs, card_table.rs): generational post-barrier dirties the card table (1 B / 512 B, ADR-26) on young-into-old pointer stores; SATB pre-barrier enqueues overwritten pointers in grey objects; the two combine into one inlined ~5-cycle sequence (§8.6, P6).
  • Weak references + finalisation (weak.rs, finalisation.rs): WeakRef target cleared by the marker when otherwise unreachable (I14); FinalizationRegistry enqueues (held-value) on clear, drained by the host at a documented checkpoint (best-effort per spec).
  • String deduplication: periodic background pass; atom table adopts new canonical pointers.

18.3 Deliverable

Young-gen GC < 1 ms pause / 100 MB heap; old-gen incremental slice < 5 ms / 1 GB heap; a WeakRef correctness corpus passes; a 24-hour stress run on the canonical workload shows zero leaks.

18.4 Acceptance Criteria

  • Young-gen pause: p50 < 0.3 ms, p95 < 0.8 ms, p99 < 1 ms @ 100 MB heap (§4).
  • Old-gen incremental marking slice: p50 < 2 ms, p95 < 4 ms, p99 < 5 ms @ 1 GB heap (§4).
  • 24 h stress run: zero gc.uaf.detected events, zero unbounded RSS growth (I8).
  • WeakRef/FinalizationRegistry corpus: 100% pass, including the best-effort-timing caveat documented as expected (not a flake).

18.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/gc/weakref_clear_on_unreachable.js I14 clearing semantics deref() returns undefined post-GC
corpora/gc/finalization_registry_ordering.js best-effort finalisation callback observed after host checkpoint
corpora/gc/promotion_after_two_survivals.js promotion threshold object present in old-gen page after 2 minor GCs
corpora/gc/card_table_dirty_on_old_write.js write-barrier correctness (I7) card marked dirty; object found on next minor GC scan

18.6 Pitfalls

  • Clearing the entire card table per cycle is too slow; clear incrementally, scoped to the region scanned.
  • A missed write barrier produces a silent use-after-free discovered only at the next GC — the worst debugging experience in the codebase (FM-1); there is no runtime detection short of ASan.
  • A FinalizationRegistry callback can run at any safepoint; never assume a particular timing window in application code or tests.
  • The atom table's strings must be marked even when the atom-table-gc pass isn't running, or live atoms are reclaimed incorrectly.
  • The card table (remembered set) is sized for steady-state; a transient allocation burst can overflow its assumptions — document the bound and the recovery path (FM-2).

18.7 Performance Concerns

Young-gen size (default 16 MB/semi-space, 32 MB total) is the most-tuned parameter: too small raises promotion rate (perf-disastrous, §31); too large grows minor-GC pause. Promotion threshold (2 minor-GC survivals) trades young-gen vs old-gen pressure (§31 derives the full tuning table).

18.8 Edge Cases

An allocation larger than the entire young-gen semi-space (must route directly to large-object space, not fail); a WeakRef to an object created in the same GC cycle that hasn't yet been observable to the marker (spec-mandated: cannot be cleared prematurely); concurrent mutator writes during an incremental marking slice (SATB must capture the pre-write snapshot correctly).

18.9 Failure Analysis

A missed write barrier (P6/I7 violation) is FM-1 in the Failure Modes table (§26) — detection is delayed to the next GC cycle, at which point the corrupted object may already have been read. Blast radius: any code path that touched the corrupted object between the missed barrier and the next GC. Containment: miri and ASan in CI are the primary defenses; no runtime containment exists once shipped. Recovery: process-level — the runbook documents capturing a heap snapshot before restart for postmortem (§27).

18.10 Operational Notes

Telemetry: gc.young.pause_ms (histogram), gc.old.marking_slice_ms, gc.promotion.rate, gc.card_table.dirty_ratio. Runbook: docs/runbook/gc-pause.md walks a pause-time regression from telemetry to root cause (young-gen undersized vs. an old-gen compaction storm).

19. Phase 7 — Promises, Async Functions, Generators, Microtasks

19.1 Objectives

The Promise/async/generator triple as a coherent unit on top of the interpreter (§8, P10), with the engine-owned, host-drained microtask queue (I11).

19.2 Detailed Implementation Steps

  • Promise (comet-runtime/src/promise.rs): state machine pending/fulfilled/rejected per spec; then/catch/finally register callbacks; resolution enqueues a microtask (WHATWG HTML microtask-queuing model, §5).
  • Async function: the bytecode compiler (§14) lowers async function to a resume function plus a frame-state-saved structure; await x desugars to yield Promise.resolve(x) internally.
  • Generator function: function* lowers to a state machine; yield saves frame state and returns; next(value) resumes from the saved state; the for-of protocol consumes next() returning { value, done }.
  • Async iterator + for-await-of: async iterators return promises from next(); consumed sequentially via await; early exit must dispose the iterator per spec (§19.7 pitfall).
  • Microtask queue (Context::run_microtasks, I11): FIFO drain; microtasks enqueued during a drain are appended to the same drain, never dropped, per the HTML checkpoint model.

19.3 Deliverable

Promise/async/generator machinery passing their respective Test262 subsets; a 60-second-duration async script hosted in the Phase-0 demo embedder drains microtasks correctly throughout.

19.4 Acceptance Criteria

  • Test262 built-ins/Promise ≥ 95%, built-ins/AsyncFunction ≥ 95%, built-ins/Generator ≥ 95% (named buckets, §24.1).
  • Microtask FIFO ordering corpus: 100% pass (I11 is a hard, not statistical, requirement).
  • for-await-of early-exit disposal corpus: 100% pass (spec-mandated iterator cleanup).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/promise/then_chain_ordering.js FIFO microtask ordering callbacks fire in enqueue order
corpora/promise/reentrant_enqueue_during_drain.js I11 append-not-drop reentrant microtask still executes this drain
corpora/generator/yield_resume_state.js generator state save/resume correct value sequence across next() calls
corpora/async/for_await_early_break.js async-iterator disposal on early exit iterator's return() invoked

19.6 Pitfalls

  • Microtask drain order is strictly FIFO; never batch microtasks across a host-scheduler yield — that reorders observable Promise-callback timing (I11 violation).
  • for-await-of early exit must call the iterator's return() method; skipping it leaks resources the iterator holds (documented per spec, not an engine invention).
  • Async-function lowering interacts with the bytecode compiler's local-slot allocation (§14) — the saved frame state must capture every live local at the await point.

19.7 Performance Concerns

Promise-chain-heavy code (deeply nested .then()) allocates one microtask object per link; comet-runtime pools small Promise-reaction objects in the young gen to keep this cheap (feeds §18's young-gen sizing assumptions).

19.8 Edge Cases

A Promise.resolve() on a thenable that throws when its then method is read (must reject, not propagate a native error past the boundary); a generator that never terminates but is dropped without exhausting (must run any finally block via forced-return semantics); a microtask that enqueues 100,000 further microtasks (must not overflow the queue — memory-bounded only, I11).

19.9 Failure Analysis

An FIFO-order violation (I11) is subtle and only surfaces as flaky Promise-ordering tests, not a crash — the hardest class of bug in this phase to catch by inspection. Detection: the microtask- ordering conformance subset run every commit. Containment: revert the queue-implementation commit. Recovery: none needed in production — the fix must land before merge; this is a CI, not runtime, gate.

19.10 Operational Notes

Telemetry: microtask.queue.depth (gauge), microtask.drain.duration_ms. Compatibility: the async/generator lowering scheme is an internal implementation detail with no wire-format exposure — it may change across minor versions without a compatibility break (§28).

20. Phase 8 — Baseline JIT

20.1 Objectives

A template code-generator (tier 1, P8, ADR-07): per-bytecode handcrafted machine-code sequences that capture IC feedback and emit patchable IC stubs; the first tier where precise (not conservative) GC stack maps land (I9, ADR-25).

20.2 Detailed Implementation Steps

  • Architecture (jit.rs, emit.rs): each interpreter opcode handler (§15.2) has a corresponding code-emitter; emitted code is the handler inlined into function prologue + per-bytecode sequence
    • epilogue (P1's bytecode contract is what makes this table-driven).
  • Tiering trigger: per-function call count tracked; ≥ 10 calls (default, ADR-07-adjacent threshold) triggers baseline compilation; the function-pointer dispatch table swaps to native code for subsequent calls.
  • Calling convention: bespoke Phase-0 convention — call frame laid out as the interpreter expects plus target-architecture calling-convention registers; the JIT/interpreter boundary is documented and cross-tier-fuzz-tested (I2).
  • IC stub emission (stub.rs, patch.rs): a LoadIC stub is the shape-check chain from §17.2, followed by a load; tail-calls the slow path on miss; patching a running stub serialises by briefly suspending mutators (documented, not lock-free at this phase).
  • Precise stack maps (cache.rs-adjacent): each baseline-JIT site emits a stack map (live values + stack/register locations, LLVM stack-map format, ADR-16's in-tree-assembler choice is what makes this format controllable); the GC consults it at every safepoint (I9), eliminating the Phase-3 conservative-scan false retentions.
  • Deopt entries (comet-opt/deopt.rs groundwork): every baseline site depending on a speculation emits a deopt entry — target bytecode offset + register-to-slot map (I10 groundwork; full deopt execution lands §22).

20.3 Deliverable

Baseline JIT runs ≥ 2× interpreter speed on the SunSpider corpus (M2, §31); tiering up does not regress Test262; precise stack maps eliminate the Phase-3 conservative-scan false retentions.

20.4 Acceptance Criteria

  • SunSpider total time with baseline tier enabled ≤ 50% of interpreter-only time (≥ 2× speedup, M2).
  • Test262 language/ + built-ins/Object pass rate unchanged (± 0%) with tiering enabled vs. interpreter-only (I2 cross-tier equivalence).
  • IC stub size < 256 B/site (§17.4); measured via JitStats.
  • Zero missing stack-map entries across the Test262 corpus under a debug-build coverage assertion (I9).

21. Phase 9 — Optimising Tier: SSA IR, Type Feedback, Inlining

21.1 Objectives

Tier 2 (ADR-07, ADR-09): an SSA-based IR consuming bytecode + accumulated IC feedback, producing speculatively-typed machine code — correct only in conjunction with the deopt machinery landing next phase (P4, §22).

21.2 Detailed Implementation Steps

  • SSA IR (ir.rs): typed nodes over the finite type lattice defined below; phi nodes at loop heads and join points (Appel, §5).
  • Bytecode → IR build (build.rs): walk bytecode, emit IR per opcode; a LoadIC with a single recorded shape narrows the receiver's type to Object{shape}; a CallIC with a single recorded callee narrows the call target (Hölzle & Ungar 1994, §5, applied directly here — P3's "feedback, not optimisation" principle is what makes this narrowing sound).
  • Type inference (type_inference.rs): forward dataflow over a finite lattice (bottom → top): None → SMI → Int32 → NumberOrInt32 → Double → Number → Boolean/Null/Undefined/ Oddball → String → Symbol → BigInt → Object{shape:S} → Object{shape:any} → Callable → Array{elements:T} → Any. A join-semilattice with bounded height, so forward dataflow provably terminates (Appel, §5). A CheckType guard node precedes any speculative- typed use (P4).
  • Inlining (inlining.rs): CallIC-stable small callees inlined under a cost model — inline_size_budget = 200 bytecode-equivalent units, inline_depth_budget = 5, recursion-depth bound = 2; a trip-count estimate from loop iteration counts favors aggressive inlining past 100 iterations; the inliner is greedy (largest-benefit-per-cost first, ties broken by CallIC- recorded call frequency, §17.4).
  • Optimisations (Muchnick, §5): common-subexpression elimination, loop-invariant code motion, bounds-check elimination for arrays with statically-known length, escape analysis for stack- allocatable short-lived objects.
  • Backend (reg_alloc.rs, codegen.rs): linear-scan register allocation; per-architecture instruction selection (x86-64, aarch64, ADR-18); compilation runs on a background thread, installed when ready (does not block the mutator).
  • Tiering trigger: loop-back-edge count or call count crossing 1000 (default) triggers compilation.

21.3 Deliverable

Optimising tier runs ≥ 5× interpreter speed on the shipped Octane subset (M6, §31); background compilation never blocks the mutator; type-narrowed code emits exactly the guards speculation requires (no un-guarded speculative use, I5/I10 groundwork for §22).

21.4 Acceptance Criteria

  • Octane subset total time with optimising tier enabled ≤ 20% of interpreter-only time (≥ 5× speedup, M6).
  • Zero un-guarded speculative type uses across a static analysis pass over the emitted IR (a CheckType must precede every use of a narrowed type).
  • Background-compile thread never observed blocking the mutator for > 0.1 ms (measured via tracing span overlap analysis).

21.6 Pitfalls

  • The IR's type lattice must be sound — an unsoundness here is a memory-safety bug, not a perf bug (mirrors T2).
  • Inlining must provably terminate; the recursion-depth bound (2) is the only safety net — do not rely on "the cost model will naturally stop it."
  • Background compilation must observe a consistent snapshot of IC feedback; concurrent IC updates require the version-tag discipline from §16/§17, not ad hoc locking.
  • Speculating on a shape from a single observed call is a perf disaster if wrong immediately — the IC must accumulate feedback in the baseline tier (§20) before the optimising tier compiles at all (tiering-order dependency, not a shortcut to skip).
  • Escape analysis interacts with allocation: an object that escapes cannot be stack-allocated; the escape lattice is a separate sub-analysis, not folded into the type lattice.

21.7 Performance Concerns

The inliner's cost model (200-bytecode-equivalent budget, depth 5, recursion bound 2) directly trades compile latency against runtime speedup; loops executing > 100 times (a trip-count estimate) merit more aggressive inlining — greedy, largest-benefit-per-cost first, ties broken by call frequency (§21.2).

21.8 Edge Cases

A polymorphic call site that becomes monomorphic only after the optimising tier has already compiled against stale feedback (must deopt cleanly, §22, not silently miscompute); a function whose loop body contains a try/catch (escape analysis must treat any exception edge as an implicit escape point); recursive inlining hitting exactly the depth-2 bound (must stop, not approximate).

21.9 Failure Analysis

An unsound narrowing in the type lattice (§21.2) — a value observed under a type narrower than it can actually take at runtime — is the single most dangerous class of bug in the optimising tier: a memory-safety bug wearing a performance-bug disguise (mirrors T2). Detection: cross-tier fuzzing (I2, fuzz_targets/cross_tier.rs) plus the static CheckType-coverage pass (§21.4) that verifies every narrowed use is preceded by a guard. Blast radius: any script whose hot function was compiled by the affected optimising-tier build — potentially memory corruption, not just a wrong value. Containment: EngineConfig exposes a global optimising-tier kill switch, falling back to baseline+interpreter only (§27 operational lever). Recovery: root-cause via the lattice's join rules, patch, re-fuzz the full corpus before re-enabling in any release channel.

21.10 Operational Notes

Speculation discipline (consumed by §22's deopt machinery): the compiler may speculate on receiver shape (LoadIC/StoreIC sites), callee identity (Call sites), element kind (packed-SMI/double/object, holey variants), array bounds (enables bounds-check elimination), integer-ness of an arithmetic operand (enables the SMI fast path), and string-ness of a concatenation operand (enables rope construction, ADR-27). Telemetry: jit.opt.compile_duration_ms, jit.tier2.function_count, jit.opt.inline_count. The optimising-tier kill switch (§21.9) is the primary incident-response lever documented in the runbook set (§27).

22. Phase 10 — Deoptimisation & On-Stack Replacement

22.1 Objectives

Wire the deopt machinery end to end (P4, ADR-08) — the mandatory safety net for every speculation introduced in §21 — plus bidirectional OSR (P9): entry (interpreter → optimising mid-loop) and exit (optimising → interpreter mid-execution, the deopt path itself).

22.2 Detailed Implementation Steps

  • Deopt entries (deopt.rs): each optimising-tier speculation point carries a bytecode offset, a register-to-slot map, and a DeoptReason tag (ShapeGuardFailed/TypeGuardFailed/ CalleeGuardFailed/BoundsGuardFailed, §11); built in §20.2's groundwork, executed here. Directly implements I10.
  • Deopt action: on guard failure, unwind the optimising-tier frame, reconstruct an interpreter frame from the register-to-slot map, resume interpreting at the recorded bytecode offset — the program continues as if no JIT compilation had ever occurred (P4).
  • Deopt-loop detection: repeated deopts at the same site within a sliding window (default 10) trigger permanent fallback — the function's optimising-tier code is invalidated and not recompiled (protects against a pathological speculation that is always wrong, T6).
  • OSR entry (osr.rs): a long-running interpreter loop is promoted to optimising-tier code mid- iteration; the interpreter frame's local slots convert to the optimising tier's register allocation at the loop's back-edge (P9).

22.3 Deliverable

Speculation works end to end: a polymorphic call site optimises the dominant case and deopts cleanly on the rare case; a while(true) accumulator loop OSR-enters and runs at JIT speed within 100 ms; deopt-loop detection halts a pathological speculation permanently.

22.4 Acceptance Criteria

  • Deopt-fixture regression corpus: 100% pass — every reconstructed interpreter frame's locals exactly match the bytecode's expected slot layout at the resume offset (I10, hard requirement).
  • OSR-entry benchmark: a tight accumulator loop reaches JIT-tier throughput within 100 ms of loop start (M10, §31).
  • Deopt-loop detector: fires and permanently disables optimisation within exactly 10 repeated deopts at one site (configurable, default asserted in the fixture).

22.6 Pitfalls

  • The register-to-slot map must cover every live value at every speculation point; a missing value is undefined behaviour on resume, not a graceful degradation (I10).
  • OSR entry must preserve the interpreter's exact local-slot layout; the conversion is mechanical but easy to get subtly wrong across architectures (x86-64 vs. aarch64 register conventions, ADR-18).
  • A deopt at very high frequency ("deopt storm") is the canonical speculation-gone-wrong failure — the runbook (docs/runbook/deopt-storm.md) is the required diagnostic path, not ad hoc log reading.

22.7 Performance Concerns

Deopt itself must be rare-path-cheap-enough-to-ignore but correctness-critical: the guard check on the hot path (§21.10) costs a branch; the reconstruction cost on the (rare) failure path is allowed to be comparatively expensive (a full frame rebuild) since it happens off the fast path.

22.8 Edge Cases

A deopt occurring while another deopt from the same function is still unwinding (must serialise correctly, not corrupt the interpreter stack); an OSR entry racing a concurrent background optimising-tier compilation for the same function (must not install two competing native-code versions); a deopt at the very first bytecode offset of a function (edge of the register-to-slot map's domain).

22.9 Failure Analysis

A malformed register-to-slot map (I10 violation) reconstructs an interpreter frame with wrong local values — a silent correctness bug, potentially memory-unsafe if a value is reconstructed as the wrong Value tag (§8.1). Detection: the deopt-fixture regression corpus (§22.5) plus cross- tier fuzzing (I2). Blast radius: any function whose deopt path is exercised — could be silent (wrong result) or a crash (tag confusion). Containment: the deopt-loop detector limits repeat exposure to one function; the optimising-tier kill switch (§21.9) is the global mitigation. Recovery: root-cause against the offending speculation's guard emission code, re-fuzz before re-release.

22.10 Operational Notes

Telemetry: deopt.count_total{reason}, deopt.storm.detected (fires the sliding-window detector), osr.entry_count, osr.exit_count. Runbook: docs/runbook/deopt-storm.md walks the operator from a deopt.count_total spike to identifying the offending call site via JitStats and recommends a code-level fix (stabilising the speculated type/shape), mirroring the megamorphic-call runbook's structure (§17.10).

23. Phase 11 — Host Embedding API

23.1 Objectives

The documented embedder surface (§1 boundaries, P11, P16): a C ABI, native-function registration, microtask-drain integration, and Promise host-adoption — the contract every downstream embedder (desktop app, edge function, IoT firmware) is built against.

23.2 Detailed Implementation Steps

  • C ABI (comet-c-abi): cbindgen-generated header (include/comet.h); opaque C-side handles for Engine/Context/Value/Object/Function; error handling via out-parameter error codes (no panics may cross the FFI boundary, P16).
  • Native-function registration: Context::define_native_function(name, fn); callback signature fn(&mut Context, this: Value, args: &[Value]) -> Result<Value, Error>; the boundary wraps every call in catch_unwind — a panicking Rust callback surfaces as Error::InternalError, never unwinds into engine internals.
  • Microtask integration: the host calls Context::run_microtasks() after every external event handler dispatch (P10); the Phase-0 demo embedder ships a trivial single-threaded blocking drain as a reference, not a mandated scheduler.
  • Promise host adoption: Promise::to_host_future bridges a JS promise into the host's own impl Future ecosystem, for embedders integrating with tokio/async-std-style runtimes.
  • Console/diagnostic hook: Engine::install_console(impl ConsoleHandler); the Phase-0 demo installs a stderr console.

23.3 Deliverable

The embedder runs a "hello world" script calling a registered Rust callback that returns a value; the demo embedder hosts a 60-second async script draining microtasks correctly throughout (reuses §19.3's fixture).

23.4 Acceptance Criteria

  • C ABI header (comet.h) compiles cleanly under -Wall -Wextra in a reference C99 host program.
  • Zero panics cross the FFI boundary across a 10,000-call adversarial-callback fuzz run (fuzz_targets extension, T9).
  • Promise::to_host_future round-trips a resolved and a rejected promise correctly into a reference tokio runtime.

23.6 Pitfalls

  • Crossing the embedder boundary with raw pointers and no handle table leaks memory — the handle table (owned by comet-c-abi) is the contract, not an implementation detail embedders may bypass.
  • A Rust callback that panics must be caught; skipping catch_unwind at this boundary turns any embedder-side bug into full engine UB.
  • The C header must stay in lockstep with the Rust ABI; a cbindgen regeneration step is required in CI, not a manual habit.

23.7 Performance Concerns

The FFI boundary's catch_unwind wrapper adds a small fixed cost per native call; acceptable given native calls are orders of magnitude rarer than interpreted bytecode dispatch in typical embedding workloads.

23.8 Edge Cases

A native callback that re-enters the engine (calls back into JS synchronously) — must not deadlock or corrupt the call stack; a native callback registered under a name that collides with a built-in global (must shadow per normal JS scoping, not silently no-op); an embedder that never calls run_microtasks() (documented as "promises never settle," not an engine hang).

23.9 Failure Analysis

A missing catch_unwind at the FFI boundary turns a host-side callback bug into undefined behaviour inside the engine — the single highest-severity embedding-layer defect (T9). Detection: the adversarial-callback fuzz target. Blast radius: total process — a Rust panic crossing an FFI boundary without catch_unwind is UB per the Rust reference. Containment: the wrapper is structural (every registration path goes through one function); there is no per-callback opt-out. Recovery: none at runtime — this must be caught in CI before any release.

23.10 Operational Notes

Telemetry: embed.native_call.count, embed.native_call.panic_caught_total (should be non-zero only under genuine embedder bugs — alert on any nonzero rate in production). Compatibility: the C ABI is versioned independently of the Rust crate API per cbindgen.toml; a C-ABI-breaking change is a major-version bump (§28).

27. Operational Readiness

Metrics & tracing. All telemetry is tracing spans/events (ADR-15), namespaced per phase: gc.* (§18), ic.* (§17), jit.* (§20, §21), deopt.*/osr.* (§22), embed.* (§23), test262.*/fuzz.* (§24). Structured logging carries context_id on every span for multi- Context embedders (P11).

Dashboards. Per-embedder recommended panels: GC pause histogram (§18.4 SLO overlay), IC-state distribution (mono/poly/mega ratio, §17), deopt rate + top offending sites (§22.10), JIT tier population (jit.tier1.function_count/jit.tier2.function_count).

Alerting philosophy. Alert on rate of change, not absolute value, for shape.tree .node_count, microtask.queue.depth, jit.codecache.evictions_total — these are workload-shape- dependent, not universally-thresholdable (§32). Hard-threshold alerts are reserved for SLO breaches with fixed numeric targets (§4's GC-pause and cold-start rows).

SLOs. GC pause p99 < 1 ms (young) / < 5 ms (old, §4); cold start p50 < 50 ms (§4); zero gc.uaf.detected events ever (I8, a correctness SLO, not a latency one).

Incident response. Named runbooks (docs/runbook/): gc-pause.md (FM-1, FM-2), deopt-storm.md (FM-3, T6), megamorphic-call.md (FM-4, T4), slow-startup.md (cold-start budget regressions, §20.7). Each runbook: symptom → telemetry query → root-cause branch → fix.

Backup/restore. N/A at the engine layer (no persistent state owned, §1 boundaries); an embedder-managed bytecode cache is the only durable artifact and is content-addressed (safe to delete and regenerate at any time, ADR-19-adjacent).

Deployment topology. Linked into the host process (§1); no independent deployment unit. A version upgrade is a host-process rebuild/redeploy, gated by §28's compatibility guarantees.

Canary/rollback. The 30-day fuzz canary (§24.4) is the pre-release gate; a post-release regression is mitigated by embedder-side pinning to the prior Cargo version (Cargo.lock) — the engine itself has no independent rollback mechanism beyond the host's own deployment tooling.

28. Compatibility & Versioning

Bytecode versioning (I13). Opcode encoding is versioned; a re-ordering or semantic change to an opcode is a major-version bump (P1, ADR-01 area). Bytecode::load rejects a version mismatch outright (§8.8) — there is no cross-version bytecode compatibility shim.

API stability (SemVer). The comet crate follows SemVer; every public type is #[non_exhaustive] (P16) so new enum variants/struct fields are additive within a minor version. A breaking change to Engine/Context/Value's public surface is a major-version bump.

C ABI versioning. comet-c-abi versions independently per cbindgen.toml; a C-ABI-breaking change is a major-version bump on that crate specifically, decoupled from the Rust crate's own SemVer (embedders using only the C ABI are insulated from pure-Rust-API churn).

Wire/storage compatibility. No engine-owned persistent storage (§1); the only "wire" format is the bytecode module itself, governed by I13 above. An embedder's bytecode cache is invalidated wholesale on any version bump — no partial-migration path is offered or needed (content-addressed regeneration is cheap, §27).

Rolling-upgrade guarantees. None required at the engine layer — each Context is independent (P11) and stateless across process restarts; a host performing a rolling upgrade simply restarts processes with the new engine version, no live-migration protocol exists or is needed.

Deprecation policy. A deprecated public API is marked #[deprecated] for one full minor- version cycle before removal in the next major version; deprecation notices are logged in CHANGELOG.md with the replacement API named.

29. Testing & Verification Strategy

Unit tests. Per-crate, colocated (#[cfg(test)]), covering each module's local invariants (e.g. shape-transition table lookups in isolation, §16).

Integration tests. Cross-crate: comet-frontend → comet-bytecode → comet-interpreter round trips (the AST-snapshot corpus, §13; the bytecode-snapshot corpus, §14).

Property testing. proptest (ADR-13) over shape-transition sequences (I3/I4), NaN-boxing round-trips (I1-adjacent: encode/decode idempotence), and IC state-machine transitions (I5) — each tied to a named invariant, not a generic "fuzz everything."

Differential testing. Cross-tier (I2): identical bytecode through interpreter, baseline JIT, optimising tier must agree — the single most valuable test class in this codebase given P8's correctness discipline.

Fuzzing. cargo-fuzz targets per §24.2/§10.6: parser, compiler, interpreter, shape, GC, baseline JIT, optimising JIT, cross-tier. Seeded from the Test262 corpus and the conformance corpora/adversarial/ set.

Chaos / fault injection. Simulated allocation-failure injection in comet-gc (tests the heap-ceiling path, T5/FM-7); simulated FFI-panic injection in comet-c-abi (tests T9/FM-8).

Deterministic replay. The cross-tier fuzz target is deterministic given a fixed seed — required for bisecting a discovered divergence (I2) without needing to reproduce non-deterministic GC timing.

Soak testing. The 24-hour GC stress run (§18.3) and the 30-day fuzz canary (§24.4) are the two soak-test gates; both are release blockers, not advisory.

Conformance. Test262 is the binding conformance oracle (ADR-19); every phase's N.5 fixtures are the phase-local conformance gate, and §24.2's bucket table is the aggregate v1.0 gate.

Performance-regression gating. Every M-table row (§31) is checked in CI on every commit to main (not just at release) via criterion (ADR-14); a regression beyond the row's threshold fails the build (§30).

Tie-back to invariants. Every row in §7's invariant table names its enforcement point and detection mechanism; this section is the aggregate view of how those individual mechanisms compose into the CI pipeline as a whole.

30. Build & Release Engineering

Reproducible builds. rust-toolchain.toml pins the exact compiler version; Cargo.lock is committed and CI-verified unmodified; a release build from a clean clone is byte-reproducible given the same toolchain and target triple.

Artifact signing. Release cdylib/rlib artifacts are signed via cosign (keyless, OIDC- backed) before publication; the signature is verifiable independently of the crates.io registry.

SBOM. cargo-cyclonedx generates a Software Bill of Materials per release, published alongside the artifact; cargo-deny (ADR-17) gates on license and advisory compliance before SBOM generation.

Release channels. stable (SemVer-tagged, full gate passed), nightly (main-branch build, Test262-gated but not fuzz-canary-gated), experimental (Stage-3-proposal-flagged builds, §38).

CI/CD topology. GitHub Actions (§10.1): ci.yml (build/unit/clippy/fmt, every PR), test262.yml (conformance, every PR), fuzz.yml (scheduled canary, continuous on main), miri.yml/security.yml (UB + advisory scanning, every PR), perf.yml (M-table gate, every PR to main), release.yml (tag-triggered, requires all above green plus the 30-day canary counter).

Provenance/attestation. SLSA-style build provenance attached via GitHub Actions' built-in attestation (no external service dependency) — verifiable against the exact CI run that produced the artifact.

Dependency auditing. cargo-audit runs on every PR and on a daily schedule against the published advisory database; a new advisory against a pinned dependency fails the daily job and pages the on-call rotation (not silently deferred to the next PR).

31. Performance Engineering

Methodology. Benchmarking via criterion (ADR-14, statistical-significance reporting); profiling via perf/Instruments (platform-native) plus tracing-derived flamegraphs; cache- miss and lock-contention analysis via perf stat/cachegrind on the reference host (§4's single-NUMA-node assumption is what makes this profiling methodology valid without cross-socket noise).

Hot path. The single biggest contributor is monomorphic property access from JITted code (§8.7 worked example): LoadIC → shape check → slot load, ~3 cycles steady state (§17). Anything adding a branch or cache miss to this path is a measurable regression, tracked by M9.

GC tuning. Young-gen size (default 32 MB total) trades minor-GC frequency against pause size; promotion threshold (2 survivals) trades young-gen vs. old-gen pressure (§18.7 derives the mechanism; the numbers here are the tuned defaults).

JIT tier-up thresholds. Baseline trigger: 10 calls. Optimising trigger: 1000 loop back-edges OR 100 baseline-tier calls. Lowering either increases compile-time cost and hurts cold start (§4); raising either keeps cold paths in a slower tier longer.

Allocation-site tuning. The JIT inlines the young-gen bump allocator (§18.2); inline-allocation cost ~5 cycles vs. ~1000 cycles for a minor GC amortised over hundreds of allocations — the ratio that makes bump allocation the correct default (P5).

SIMD opportunities (Phase-2+ stretch, not v1.0-gated): ASCII string concat/compare/slice (~16× with AVX2); typed-array numeric ops (~8× with AVX2); the atom-table hash function is SIMD-able on long strings. Phase-0–12 ship scalar implementations only.

32. Scalability Analysis

What stays constant. Per-Value size (8 B, NaN-boxed, §8.1) regardless of heap size; IC stub size (< 256 B/site) regardless of program size; shape-lookup cost (O(1) via the transition table) regardless of object count, so long as I3's sharing property holds.

What grows, and the Big-O. Heap live-set: O(reachable objects), bounding GC pause via the generational hypothesis (most die young, so the scanned set per minor GC stays small, O(young- gen survivors) not O(heap)). Shape-tree size: O(distinct property-add histories) — pathological under T4's adversarial churn, bounded only by the heap ceiling (§4). Old-gen mark-compact pass: O(live old-gen bytes), amortised via incremental slicing (§18.4) rather than eliminated.

Named bottlenecks in order. (1) Old-gen mark-compact pause under heavy long-lived-object churn — the largest single latency contributor once the young-gen hypothesis partially fails. (2) Megamorphic IC sites in hot loops — a documented perf cliff (§17.9), not auto-remediated. (3) JIT code-cache pressure under pathological function counts (T7). (4) Deopt-storm sites under adversarial or poorly-typed hot code (T6).

Horizontal vs. vertical. No horizontal scaling within one Engine/Context — this is a single-address-space, single-logical-thread-of-JS-execution system per Context (P11, ECMA-262's own single-threaded-per-realm model). Horizontal scaling is achieved by running N independent processes (or N Contexts within one process, up to the 256-soft-cap, §4), each embarrassingly parallel with no cross-Context coordination required.

Sharding/partitioning. Not applicable at the engine layer — an embedder sharding workload across Contexts does so entirely at its own layer; the engine provides no built-in partitioning primitive (consistent with P11's no-global-state principle).

Coordination overhead. Zero cross-Context coordination inside one Engine beyond a shared bytecode-cache read lock (read-mostly, low contention by construction — bytecode is immutable post-compile, I1).

Practical ceiling and levers beyond it. The practical ceiling for one Context is the heap ceiling (§4, default 512 MB, configurable to 4 GB) combined with the old-gen mark-compact pause budget — beyond ~4 GB live-set, old-gen pause time exceeds most latency SLOs even with incremental marking. The lever beyond that ceiling is the deferred fully-concurrent marker (PhaseDeferred ("§38")) — a research-grade Phase-2+ item, not a v1.0 commitment.

33. Mental Models & First Principles

  • MM1 — "A shape is a type, not a value." The compressed insight: an object's shape describes its structure (which properties, in what order, with what attributes), never its property values (I6). Predicts: two objects can share a shape while holding entirely different data. Bug class without it: engineers "optimize" by trying to key caches on value type, producing shape-tree explosions or missed sharing. Applied in §16 (Phase 4), §8.2.
  • MM2 — "An inline cache is a bet, not a fact." The compressed insight: every IC fast path is a speculation validated by a guard, never an assumption baked in unconditionally (P3). Predicts: IC state can and will degrade; code that "assumes" monomorphism without a guard is unsound. Bug class without it: engineers skip the guard "because it's always this shape in practice" — exactly the CVE-class bug this design prevents structurally. Applied in §17 (Phase 5), §8.3.
  • MM3 — "Deoptimisation is the price of admission for speculation, not a failure." The compressed insight: every profitable speculative optimization requires an equally engineered bailout path (P4, ADR-08). Predicts: a design with speculation but no deopt path is unsound by construction, not merely incomplete. Bug class without it: "we'll add the safety net later" — the exact trap Hölzle/Chambers/Ungar's 1992 paper (§5) was written to prevent. Applied in §22 (Phase 10).
  • MM4 — "Most objects die young — design the collector around the exception, not the rule." The compressed insight: the generational hypothesis (Lieberman & Hewitt 1983, §5) means a collector optimized for short-lived objects wins on typical workloads even though it looks "wasteful" for the rare long-lived object. Predicts: naive flat mark-sweep loses to generational GC on allocation-heavy code despite conceptual simplicity. Bug class without it: over-engineering for the long-lived case at the cost of the common case. Applied in §18 (Phase 6), §8.6.
  • MM5 — "The bytecode is the seam; never let a tier reach across it." The compressed insight: every tier (interpreter, baseline, optimising) must derive its behavior from the same bytecode contract (P1) — never from the AST or from another tier's internal state directly. Predicts: any tier that reads the AST directly (bypassing bytecode) will eventually diverge from the others (I2 violation). Bug class without it: "just have the optimising tier peek at the AST for this one case" — a seam violation that compounds silently. Applied in §3, §14, §21.
  • MM6 — "A write barrier is not optional insurance — it is part of the pointer-store instruction." The compressed insight: in a moving generational collector, a bare pointer store is not a complete operation; the barrier is the second half of that operation (P6, I7). Predicts: any code path that stores a pointer "for efficiency" without the barrier is not faster, it is incorrect. Bug class without it: FM-1, the single worst class of bug in the codebase. Applied in §18 (Phase 6), §8.6.
  • MM7 — "OSR is a frame translation, not a restart." The compressed insight: promoting or demoting a running function mid-execution (P9) must preserve exact program state — it is a bijective mapping between two representations of the same point in execution, not a fresh start. Predicts: any OSR implementation that "just re-runs from the top" is unsound for functions with observable side effects before the promotion point. Bug class without it: double-executed side effects or lost state across a tier transition. Applied in §21 (Phase 9), §22 (Phase 10).
  • MM8 — "The embedder boundary is the only place untrusted code becomes trusted, and vice versa." The compressed insight: JS source is untrusted input; a registered native callback is trusted host code; the FFI boundary (§23) is where that trust level flips in both directions, and both directions need their own discipline (bytecode validation inbound, catch_unwind outbound). Predicts: a design that only guards one direction (e.g., validates bytecode but doesn't catch host panics) is asymmetrically unsafe. Applied in §23 (Phase 11), §8.8.

35. Back-of-Envelope Capacity Model

All numbers derived step-by-step from §4's System Constraints table; formulas shown.

  1. Idle footprint budget check. Target ≤ 15 MB (§4). Value = 8 B; a 512 MB default heap holding entirely 64 B objects has a theoretical max of 512 MB / 64 B ≈ 8.4M objects — the 15 MB idle figure is measured with zero live JS objects (engine machinery only: atom table seed, bytecode-cache scaffolding, JIT code-cache reservation), so it is independent of this object count and must be validated by direct measurement (§24.4), not derived from heap size.
  2. Heap-to-object-count ratio (default 512 MB heap). Assuming an average live object size of ~48 B (header + 4 in-object slots, typical of SunSpider-class code): 512 MB / 48 B ≈ 11.2M live objects addressable before hitting the default ceiling (§4).
  3. Young-gen survivor bound. Young-gen = 32 MB total (2×16 MB semi-spaces, §18.7). At a promotion threshold of 2 survivals and an assumed 10% young-object survival rate per minor GC (typical generational-hypothesis figure): expected steady-state promotion volume per minor GC = 16 MB (to-space) × 10% ≈ 1.6 MB promoted to old-gen per cycle.
  4. Minor-GC frequency under a 200 MB/s allocation rate (a moderately allocation-heavy workload): 16 MB to-space / 200 MB/s = 80 ms between minor GCs — cross-checked against the M4 target (young-gen pause p99 < 1 ms, §31): a collector doing useful work for < 1 ms every 80 ms is < 1.25% mutator overhead from young-gen collection alone, well inside the throughput budget (M1).
  5. Old-gen incremental-marking throughput requirement. To mark a 1 GB old-gen heap (§4's 1 GB reference size) within the M5 target (< 5 ms slices, §31) using 1 ms marking slices (§18.2): at an assumed marker throughput of ~500 MB/s (typical single-threaded tri-colour marking rate), a full mark pass takes 1000 MB / 500 MB/s = 2 s spread across 2000 ms / 1 ms slice = 2000 slices — validating that incremental marking, not stop-the-world, is required at this heap size to hit the pause budget (directly justifies ADR-06).
  6. IC feedback-vector memory overhead. At ~8 B per FeedbackSlot entry (shape ptr + slot index) and an assumed average of 20 call sites per function (typical of hand-written JS): 20 sites × 8 B × 4 (max polymorphic entries) = 640 B worst-case feedback-vector overhead per function — negligible against the 15 MB idle-footprint budget (item 1) even at 10,000 loaded functions (10,000 × 640 B ≈ 6.4 MB, within budget but a real contributor worth tracking via jit.tier1.function_count, §20.10).
  7. JIT code-cache sizing. At baseline-tier code size of ~200 B/function-equivalent (template codegen, §20.2) and a 10-call tiering threshold (§20.2): a workload with 5,000 hot functions produces 5,000 × 200 B ≈ 1 MB baseline code-cache footprint — well inside the code-cache eviction threshold implied by T7's mitigation (bounded, LRU-evicted).
  8. Cold-start budget decomposition. Target < 50 ms for a 100 kB script (§4, M3). At the §13.4 parse-speed target (5 MB in < 100 ms ⇒ ~50 MB/s effective parse throughput), a 100 kB script parses in 100 kB / 50 MB/s ≈ 2 ms; the remaining ~48 ms budget covers bytecode compilation (§14) and top-level interpreted execution (§15) — a rough 2 ms / 48 ms split that flags bytecode compilation + interpretation, not parsing, as the dominant cold-start cost to optimise first if M3 regresses.
  9. Deopt-rate ceiling in absolute terms. M8 targets < 0.1% of guarded call sites deopting in steady state (§31). At the item-6 estimate of 20 call sites/function × 10,000 loaded functions = 200,000 guarded sites, the M8 ceiling permits at most 200,000 × 0.1% = 200 steady-state deopts — a concrete number the deopt-storm detector's sliding window (default 10 per site, §22) is calibrated well below.
  10. Fuzz-canary statistical confidence. 30 days continuous fuzzing (M12) at an assumed ~10,000 executions/second aggregate across all fuzz/fuzz_targets/ (§10.6): 30 × 86,400 × 10,000 ≈ 2.6 × 10^10 total fuzz executions before sign-off — the scale at which rare timing-dependent GC/JIT races (the entire reason for a 30-day, not 30-minute, window) become statistically likely to surface at least once.

37. Alternative Architectures (Roads Not Taken)

A1 — Tree-walking AST interpreter (no bytecode).

Source -> Parser -> AST -> [direct recursive tree-walk evaluator] -> Value

Regime where it wins: extremely short-lived scripts (single evaluation, discard) where compiling to bytecode is pure overhead relative to walking the AST once — configuration-DSL-style embeds. Real system: early SpiderMonkey (pre-2008) and most textbook interpreters. Rejected here because every later phase (§14–§24) depends on a stable bytecode contract (P1) as the seam between tiers; an AST-walker has no comparable seam, so every tier would need its own AST-consuming logic, multiplying the correctness surface (I2) rather than sharing one bytecode oracle.

A2 — Dictionary-based property storage (no hidden classes).

Object -> HashMap<Atom, Value>   (every object independently keyed, no shared structure)

Regime where it wins: workloads dominated by objects used as bags with high per-instance property churn and low structural repetition (e.g., a JSON-blob cache where every object's key set is effectively unique) — hidden classes buy nothing when no two objects share a shape anyway. Real system: Python's default object __dict__, and pre-2009 JS engines generally. Rejected here because typical JS workloads (object-literal-heavy, class-instance-heavy) have massive structural repetition that hidden classes exploit for O(1) access (P2); a dictionary model would forfeit the entire IC-speedup story (§17) this project exists to teach.

A3 — AOT-only bytecode compilation, no JIT.

Source -> Parser -> AST -> Bytecode (ahead-of-time) -> Interpreter only, forever

Regime where it wins: mobile/cold-start-dominated workloads where JIT warm-up cost exceeds total script runtime (a React Native screen that runs for 200 ms total) — JIT compilation is pure overhead if the function never gets hot enough to amortise it. Real system: Hermes (Facebook, React Native). Rejected here because the project's explicit teaching goal (§2) is the tiered-JIT

  • deopt discipline (P4, P8) — an AOT-only design would forfeit §20–§22 entirely, the largest single engineering-lesson surface in the blueprint.

A4 — Trace-based JIT (record a hot loop's actual path, compile the trace).

Interpreter -(hot loop detected)-> Trace recorder -> Linear trace IR -> Compiled trace
                                                         |
                                                    trace-exit guard -> back to interpreter

Regime where it wins: tight, loop-dominated, type-stable numeric code (the historical TraceMonkey sweet spot, Gal et al. 2009, §5) — a trace captures exactly the executed path with no need for a general-purpose SSA IR covering every control-flow shape. Real system: TraceMonkey (Mozilla, 2008–2011). Rejected here (and, notably, by Mozilla itself, which replaced it with IonMonkey) because trace-based JITs degrade badly on polymorphic, branch-heavy code with many distinct hot paths through the same function — exactly the property-access-heavy, shape-changing JS this project's IC/hidden-class design (§16, §17) is built to handle well; a method-based tiered JIT (ADR-07) generalizes better across that workload shape.

39. Glossary

  • Atom. An interned string; canonical pointer used for O(1) identifier comparison (P7, §16.4).
  • Baseline JIT. Tier 1 of the JIT pyramid; template code-generator emitting patchable IC stubs (§20).
  • Bytecode. The versioned intermediate representation between the AST and every execution tier; the sole cross-tier contract (P1, §8.4).
  • Card table. A page-granularity (1 B / 512 B) marker of old-to-young pointer stores, the generational write barrier's remembered set (§18.5, ADR-26).
  • Compaction. The mark-compact pass that evacuates live objects to defragment the old gen (§18.2).
  • Deoptimisation (deopt). Falling back from optimising-tier machine code to the interpreter on a speculation-guard failure, reconstructing an exact interpreter frame (P4, §22).
  • Dictionary shape. An out-of-line, non-transition-tree fallback shape used after a property delete, trading structural sharing for flexibility (§8.2).
  • ECMA-262. The ECMAScript Language Specification; the canonical normative reference (§5).
  • Elements backing store. The array-specific storage kind (packed, holes, dictionary) tracked independently of the object's shape (§16.2).
  • Feedback vector. A per-function array of FeedbackSlots, one per call site, recording observed shapes/callees for IC and optimising-tier consumption (§8.3, §11).
  • Generational GC. A collector exploiting the hypothesis that most objects die young, distinguishing a young and an old generation with different collection strategies (P5, §18).
  • Hidden class. A V8-coined synonym for "shape" — the type describing an object's property structure, shared across structurally identical objects (§8.2, Chambers/Ungar/Lee 1989).
  • Inline cache (IC). A per-call-site stub that speculatively fast-paths a property/call operation based on previously observed shapes/callees (P3, §8.3, §17).
  • Incremental marking. A GC marking pass that runs in bounded slices interleaved with mutator execution rather than stopping the world (§18.2, ADR-06).
  • JIT. Just-in-time compiler; here, the baseline (tier 1) and optimising (tier 2) code generators (§20, §21).
  • Major GC. A collection pass over the old generation (mark-compact, §18.2).
  • Megamorphic. An IC state reached after 5+ distinct shapes/callees observed at one site; degrades to a shared, hashed slow-path stub (§8.3, §17.2).
  • Microtask. A queued unit of work (Promise reactions, etc.) drained by Context ::run_microtasks(), engine-owned, host-drained (P10, §19).
  • Minor GC. A collection pass over the young generation (Cheney copy, §18.2).
  • Monomorphic. An IC state where exactly one shape/callee has been observed at a site — the fastest, most common steady-state IC state (§8.3).
  • NaN-boxing. A 64-bit value encoding that repurposes IEEE-754 NaN payload space to tag non-double value kinds (§8.1, ADR-04).
  • Oddball. The spec term for the four singleton non-numeric primitive values: undefined, null, true, false (§8.1).
  • On-stack replacement (OSR). Converting a running function's execution state between tiers mid-execution, in either direction (entry or exit/deopt) (P9, §21, §22).
  • Optimising tier. Tier 2 of the JIT pyramid; SSA-IR-based, type-feedback-driven, speculative compiler (§21).
  • Polymorphic. An IC state where 2–4 distinct shapes/callees have been observed at a site (§8.3, §17.2).
  • Promotion. Moving a young-gen object that has survived a threshold number of minor GCs into the old gen (§18.2).
  • Prototype chain. The linked sequence of prototype objects consulted during property lookup when the receiver's own shape lacks the property (§8.2, §16.2).
  • Realm. A complete, isolated set of intrinsics and globals; one per Context (§11, §23).
  • Rope string. A tree-shaped string representation used to amortise repeated concatenation to O(n log n) rather than O(n²) (§8.6-adjacent, ADR-27).
  • Shape. A node in the shared transition tree describing an object's property structure; synonym for hidden class in this document (§8.2, I3, I4).
  • SMI (small integer). A tagged 31/32-bit integer fast path within the NaN-boxed Value encoding, avoiding double-boxing for common integer arithmetic (§8.1, P14).
  • Speculation. A type or shape narrowing made by the optimising tier based on observed feedback, always paired with a guard and a deopt path (P3, P4, §21).
  • Stack map. A per-safepoint table of live GC-relevant values and their locations, enabling precise (non-conservative) root scanning (I9, §20.2).
  • Test262. The TC39 conformance test corpus; the binding conformance oracle for this engine (ADR-19, §24).
  • Tiering. Promoting a function from a slower to a faster execution tier based on call-count or loop-back-edge thresholds (§20.2, §21.2).
  • Transition tree. The shared tree of shapes connected by property-add/change/delete edges; the data structure hidden classes are built from (§8.2, P2).
  • Tri-colour marking. The white (unvisited) / grey (queued) / black (scanned) marking discipline used by the incremental old-gen marker (§18.2).
  • Version tag. A per-shape counter bumped on any mutation affecting dependent IC validity, used to detect stale prototype-chain caches (§16.2, §17.2, I5).
  • Write barrier. A code sequence executed before/after a pointer store to maintain GC invariants (generational + SATB), inlined at every JIT site and interpreter handler (P6, I7).
