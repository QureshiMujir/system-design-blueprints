⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives
  • Stand up the workspace skeleton (§10) and the CI gates every later phase depends on.
  • Implement the correctness kernel: Buf/BufBacking (§11), Ethernet parse + VLAN detect, ARP request/reply skeleton, IPv4 parse + checksum verify, ICMP echo, UDP parse + single-socket dispatch, and the TUN/TAP DriverShim.
  • Constraints introduced: single-threaded loop (P5), no_std/std split (ADR-02), zero-copy cursor buffer (P3, ADR-10).
Deliverable
  • make build && make test exits 0 on a clean checkout.
  • examples/01_ping.rs brings up TUN 10.0.0.2/24, peers with host 10.0.0.1, replies to a kernel-originated ping 10.0.0.2, prints round-trip latency.
  • CI workflows (ci.yml, security.yml) green on the initial commit.
Acceptance
  • ping 10.0.0.2 round-trips in ≤ 5 ms on loopback TUN (10× the eventual M2 target, acceptable for an unoptimized Phase-0 path).
  • conformance/positive/icmp/echo_basic.yaml and conformance/positive/udp/echo_basic.yaml both report Pass.
  • Zero heap allocations observed on the ICMP reply path post-startup (track-allocator harness; I9 precursor).
  • cargo clippy --all-targets -- -D warnings exits 0.
Fixtures
Fixture Purpose Expected Output
positive/icmp/echo_basic.yaml ping round-trip echo reply, id/seq echoed
positive/udp/echo_basic.yaml UDP socket path datagram echoed to sender
negative/malformed/ipv4_short_header.yaml IHL > actual length ParseError::Truncated
negative/truncated/ethernet_runt_frame.yaml frame < 14 bytes rejected pre-dispatch
Pitfalls
  • The Internet checksum is one's-complement with end-around carry; naive implementations drop the final carry, producing off-by-one mismatches at odd boundaries — mitigated by a reference-vector unit test (ADR-18).
  • TUN devices deliver raw IP on macOS but can be IP-mode or Ethernet-mode (TAP) on Linux — branch on link_state(), never assume one mode.
  • Network byte order is big-endian; every multi-byte field must go through WireParse/encode (§11), never a native-endian cast.

⬜ Phase 1 — ARP Cache, Gratuitous ARP & VLAN Tagging §13

Objectives
  • Promote ARP from request/reply-only to a full aging cache with a pending-request queue; add gratuitous ARP and 802.1Q VLAN tag handling.
  • Constraint introduced: cache trust model is trust-on-first-use in v1.0, an explicit, documented weakness (T5), not silently ignored.
Deliverable
  • arp -a-equivalent introspection command in crates/diag shows the live cache.
  • A pcap of a full ARP request/reply exchange committed as a regression artifact.
Acceptance
  • Cache lookup latency ≤ 100 ns (M9, benchmarked via crates/bench).
  • conformance/positive/arp/gratuitous.yaml and .../resolve_and_expire.yaml both Pass.
  • Pending-queue overflow at 100 queued misses triggers the documented drop path (not an unbounded-growth crash).
Fixtures
Fixture Purpose Expected Output
positive/arp/gratuitous.yaml bringup announce gratuitous ARP observed on wire
positive/arp/resolve_and_expire.yaml TTL aging entry evicted after 60 s + 1 tick
negative/malformed/arp_bad_hlen.yaml HLEN ≠ 6 rejected, no cache mutation
Pitfalls
  • Replying to ARP requests for IPs not assigned to the interface is proxy-ARP — off by default; enabling it accidentally turns the host into an unintended router (ADR-08 boundary).
  • Soft vs. hard TTL update logic is easy to invert, silently extending a poisoned entry's life — covered by a dedicated unit test.

Objectives

  • Forwarding/router mode is explicitly out of scope for v1.0: PhaseDeferred("§14") (Deferred Features Register, §36).
Deliverable
  • conformance/positive/ipv4/ and .../icmp/ buckets both Pass.
  • A reassembly fuzz fixture committed under fuzz/fuzz_targets/fuzz_ipv4.rs.
Acceptance
  • Fragmented ICMP echo (3-fragment split of a 4000-byte payload) reassembles and round-trips correctly — named fixture positive/ipv4/fragmented_echo.yaml.
  • Reassembly cache honors the 60 s timeout within ±1 tick (timer-wheel granularity, I7).
  • RouteTable::lookup resolves a /24-scale table (≤1,000 entries) in ≤ 500 ns.
Fixtures
Fixture Purpose Expected Output
positive/ipv4/fragmented_echo.yaml 3-fragment reassembly echo reply after reassembly
positive/icmp/dest_unreachable.yaml route-miss error ICMP type 3 with 28-byte quote
negative/malformed/ipv4_reassembly_bomb.yaml fragmentation-bomb (T1) quota-denied, no OOM
Pitfalls
  • The IP identification field is per-source-per-protocol, not per-flow; mis-keying the reassembly cache produces silent cross-flow corruption (guarded by the exact 4-tuple key above).
  • ICMP errors must include exactly 28 bytes of the original packet (RFC 1122); truncating breaks PMTUD's eventual implementation (§19).

⬜ Phase 4 — TCP Three-Way Handshake §16

Objectives
  • Implement the eleven section 3.3.2 of RFC 9293 states and the handshake-relevant transitions of §8.3's state-transition table; this is the load-bearing phase (§2) — every later phase assumes a correct handshake.
Deliverable
  • examples/03_tcp_echo_server.rs accepts a connection from nc.
  • conformance/positive/tcp_handshake/ bucket Pass; a capture of the three-way handshake committed as a regression artifact.
Acceptance
  • Connections per second (accept loop, single-threaded) ≥ 50,000/s (M3).
  • Time to first byte after connect() on loopback ≤ 200 µs (M5).
  • ISS entropy ≥ 24 bits measured across 10,000 trials (I11's build-time fixture).
  • Memory per established connection (typical default sizing) ≤ 144 KiB (§4/§33 #1).
Fixtures
Fixture Purpose Expected Output
positive/tcp_handshake/passive_open.yaml listen→established state==Established, rcv_nxt matches
positive/tcp_handshake/simultaneous_open.yaml both sides connect both reach Established via SynRcvd
negative/spoofed/syn_retransmit_after_established.yaml duplicate SYN ignored, state unchanged
Pitfalls
  • Sequence arithmetic is modular over u32 (§8.4, I1); naive comparisons wrap incorrectly — use core::tcp::seq::{lt,le,gt,ge} everywhere, never native operators.
  • A retransmitted SYN may arrive after the handshake completes; the "SYN duplicates" path (section 3.10.7.2 of RFC 9293) must be handled or the connection silently resets.

⬜ Phase 5 — TCP Data Transfer, Sliding Window, Nagle & Delayed ACK §17

Objectives
  • Implement the data-transfer path: segmentation against the send window, the sliding window itself (§8.5), zero-window probing, Nagle, delayed ACK, out-of-order reassembly, and PSH/URG handling.
Deliverable
  • examples/04_tcp_client_curl.rs completes a full bidirectional exchange.
  • conformance/positive/tcp_data/ bucket Pass.
Acceptance
  • A 100 MiB stream completes at ≥ 800 Mbps sustained (interim gate toward M1's 1 Gbps, reached fully once Phase 7's congestion control lands).
  • Loopback throughput on 64 KiB writes ≥ 1 Gbps (M1, fully gated here since no loss is present on loopback).
  • Persist-timer probe fixture (persist_timeout.yaml, §8.8) demonstrates bounded recovery, not infinite retry.
Fixtures
Fixture Purpose Expected Output
positive/tcp_data/bulk_transfer_100mib.yaml throughput gate ≥800 Mbps, byte-identical payload
positive/tcp_data/persist_timeout.yaml zero-window recovery (§8.8) bounded probe/backoff, ETIMEDOUT on exhaustion
negative/malformed/window_shrink_attempt.yaml I2 violation attempt update rejected, old window kept
Pitfalls
  • Nagle + delayed ACK together can cause 200 ms latency spikes on small writes — an application-level fix (TCP_NODELAY), documented in docs/protocols/tcp.md, not "fixed" by silently disabling Nagle by default (P1).
  • A receive window must never shrink (section 3.8.6.2 of RFC 9293, I2) — violating this stalls legitimate senders holding stale window state.

⬜ Phase 6 — TCP Retransmission, RTO Estimation & Karn's Algorithm §18

Objectives
  • Implement RFC 6298 RTO estimation, Karn's algorithm (I4), exponential backoff, fast retransmit, the persist-timer/keepalive wiring, and their shared home in the timer wheel (ADR-04, P9).
Deliverable
  • conformance/positive/tcp_retransmit/ bucket Pass.
  • A network-loss simulation (drop 10% of packets at the TUN driver) demonstrates convergent recovery, captured as a benchmark artifact.
Acceptance
  • TCP retransmit recovery time after a single loss ≤ 2 RTT (M6).
  • Under the 10%-loss simulation, throughput converges within 10% of the Mathis-model theoretical prediction (feeds M7, fully validated in Phase 7 once cwnd exists).
  • Karn-guard fixture demonstrates zero RTT-sample contamination from a retransmitted segment across 1,000 trials.
Fixtures
Fixture Purpose Expected Output
tcp_retransmit/karn_violation.yaml retransmit RTT-sample guard sample discarded, tcp_karn_guard_hits_total increments
tcp_retransmit/fast_retransmit_triple_dup.yaml 3 dup ACKs retransmit fires on the 3rd, not earlier/later
tcp_retransmit/loss_10pct_convergence.yaml 10% loss simulation recovery ≤2 RTT (M6)
Pitfalls
  • Karn's algorithm is mandatory; skipping it produces RTT estimates that drift wildly after a single loss event (MM4).
  • Tahoe-style behavior (collapse cwnd to 1 on any loss) is wrong for Reno — ship Reno's fast-recovery from the start (ADR-06), not a Tahoe stepping-stone.
  • A triple-duplicate-ACK counter that fires on every duplicate rather than strictly the third, or that fails to reset on progress, causes spurious retransmit storms (FM-1).

⬜ Phase 7 — TCP Congestion Control (Reno, SACK, ECN, CUBIC-Flagged) §19

Objectives
  • Implement Reno (RFC 5681) as the default CongestionControl (ADR-06, ADR-19), SACK (RFC 2018, ADR-20), basic ECN negotiation (RFC 3168), and a feature-flagged CUBIC (RFC 8312) stub satisfying the pluggable trait.
Deliverable
  • conformance/positive/tcp_congestion/ bucket Pass.
  • A loss-vs-throughput plot committed under benchmarks/results/phase7_reno.svg.
Acceptance
  • Reno cwnd convergence under 1% loss / 100 ms RTT within 10% of the Mathis-model theoretical prediction (M7, §33 capacity chaining).
  • Loopback throughput on 64 KiB writes sustains ≥ 1 Gbps under zero loss (M1, fully gated with congestion control active).
  • The cwnd time-series visibly matches the RFC 5681 sawtooth shape (named fixture tcp_congestion/reno_sawtooth.yaml).
Fixtures
Fixture Purpose Expected Output
tcp_congestion/reno_sawtooth.yaml AIMD shape cwnd sawtooth matches RFC 5681 pattern
tcp_congestion/sack_multi_loss.yaml 2+ losses per window single RTT recovery via SACK, not 2 timeouts
tcp_congestion/app_limited_cwnd_growth.yaml RFC 7661 bound cwnd growth capped at app send rate
Pitfalls
  • Application-limited senders growing cwnd indefinitely (violating RFC 7661) causes a burst-loss event on the next real demand spike.
  • ABC (RFC 3465) byte-based cwnd increase is subtle to get right; this stack ships the simpler segment-based variant by default, documented as a deliberate simplification.

⬜ Phase 8 — TCP Close, TIME_WAIT & Simultaneous Close §20

Objectives
  • Implement active/passive/simultaneous close, RFC 6191 TIME_WAIT-assassination-safe reuse (I10), and the RST-generation rules of section 3.10.7.5 of RFC 9293.
Deliverable
  • conformance/positive/tcp_close/ bucket Pass.
  • A pcap of active close, passive close, and simultaneous close, each committed as a named regression artifact.
Acceptance
  • TIME_WAIT eviction occurs at exactly 2×MSL within ±1% (M10).
  • A TIME_WAIT-reuse fixture demonstrates safe 5-tuple reuse per RFC 6191's sequence check, rejecting a non-conforming reuse attempt (T12).
  • Simultaneous-close fixture reaches Closed on both sides within 3×RTT of the last FIN.
Fixtures
Fixture Purpose Expected Output
tcp_close/active_close.yaml active close path 2×MSL TIME_WAIT, then freed
tcp_close/simultaneous_close.yaml both sides close both reach Closed via Closing
tcp_close/time_wait_reuse_valid.yaml RFC 6191 reuse new TCB accepted
negative/spoofed/time_wait_reuse_invalid.yaml non-conforming reuse rejected (T12)
Pitfalls
  • Re-using a 5-tuple before TIME_WAIT expires without the RFC 6191 sequence check is the classic source of spurious "connection reset by peer" errors (FM-4).
  • RST generation that ignores RFC 5961's window check turns the stack into an off-path-attacker oracle (T4) — every RST path must consult the window check.
