35. Back-of-Envelope Capacity Model

1. Vote message volume per block (prevote + precommit phases):

Messages/block = n × 2 (prevote + precommit) × (n−1) (gossip to all peers)
              = 150 × 2 × 149 = 44 700 messages/block
Each message = 120 B (§4) ⇒ 44 700 × 120 B = 5.36 MB/block/validator
At 1 s blocks: 5.36 MB/s per validator egress; 10.7 MB/s (+ ingress) per validator.
Cluster total: 150 × 5.36 MB/s ≈ 804 MB/s (sum of all validator egress).

2. All-to-all message count per height:

Proposals: 1 (from proposer)
Prevotes:  n × (n−1) = 150 × 149 = 22 350 (total gossip events in cluster)
Precommits: n × (n−1) = 22 350
Cluster total messages per height (min, 1 round): 1 + 22 350 + 22 350 ≈ 44 701.

3. Commit certificate size (Ed25519 vs BLS):

Ed25519 commit cert:
  CommitSig per validator: 20 B addr + 8 B timestamp + 64 B sig + 1 B flag = 93 B
  Quorum = ⌈⅔ × 150⌉ = 100 validators minimum (minimum Commit-flagged)
  Total: 100 × 93 B + 16 B header = ~9 316 B ≈ 9.1 KB (quorum only)
  Full cert (all 150 slots incl. Absent/Nil): 150 × 93 B ≈ 14 KB

BLS aggregate commit cert:
  Aggregate sig: 96 B (G2 point, BLS12-381)
  Bitfield:      ⌈150/8⌉ = 19 B
  Header:        ~16 B
  Total:         ≈ 131 B — a 107× reduction vs the full Ed25519 cert.

4. Block tree memory (Casper FFG variant):

Non-finalized frontier: at most 2 epochs × E blocks/epoch.
Example: E = 32 slots, each slot 1 block ⇒ 64 non-finalized blocks max.
BlockNode struct: ~120 B (hash + parent + children + weight fields).
64 × 120 B ≈ 7.7 KB for the frontier nodes.
Full tree (including justified but not finalized): ≤ 3 × E ≈ 96 blocks ≈ 11.5 KB.
Negligible; the bounded concern is n → ∞ without pruning (DP15).

5. WAL write amplification per height:

Entries per height (happy path, 1 round):
  1 × Step{H,R,Prevote}   + 1 × SignedVote(prevote)   = 2 writes
  1 × Step{H,R,Precommit} + 1 × SignedVote(precommit) = 2 writes
  1 × Commit(cert)                                     = 1 write
  Total: 5 WAL entries per height; 2 fsync (coalesced write+fsync per step).
Entry size: ~200 B avg ⇒ 5 × 200 B = 1 KB/height WAL write.
At 1 block/s: 1 KB/s WAL write rate; trivial for any modern NVMe.

6. FD budget:

Peer connections: n−1 = 149 (TCP sockets)
RPC server socket: 1 + up to 10 concurrent connections = 11
WAL file:          1
Block store files: ~3 (sled/redb internal)
Misc (log, metrics, config): ~5
Total at n=150: 149 + 11 + 1 + 3 + 5 = 169 FDs.
Safety margin to 512 budget: 343 FDs remaining.
Peak (during block sync with additional peer connections): 169 + 50 = 219.
Hard limit `max_peers = 149` enforces this stays below 512 (§4, T12).

7. Memory for HeightVoteSet:

Per round VoteSet (prevotes + precommits):
  votes: Vec<Option<Vote>> = n = 150 slots × ~200 B/Vote = 30 KB per VoteSet.
  Two VoteSets (prevote + precommit) per round: 60 KB.
  Active rounds in memory: typically 1–3 (current + last 2 for catch-up).
  HeightVoteSet total: 3 × 60 KB = 180 KB per height.
  With evidence + proposals: ≈ 250 KB per height.
Freed on height commit; bounded to 2 heights in memory (current + prior).

8. Tx throughput upper bound:

Block size: 1 MiB = 1 048 576 B.
kv-app tx size: set(key=32B, value=64B) + overhead = ~120 B/tx.
Max txs/block: 1 048 576 / 120 ≈ 8 738 txs/block.
At 1 block/s: theoretical max = 8 738 tx/s.
Actual measured target: 1 000 tx/s (M3); limited by DeliverTx + Merkle update.
Bottleneck: Merkle tree update O(log n_keys) per tx; not block transport.

9. Ed25519 verify throughput bottleneck:

Ed25519 verify latency: ~70 µs/sig (single-threaded, no batch).
Inbound votes per height: n = 150 prevotes + 150 precommits = 300 verifies.
Sequential: 300 × 70 µs = 21 ms — longer than 10% of a 1 s round.
With batch verify (groups of 32): 300 / 32 ≈ 10 batches × ~700 µs/batch = 7 ms.
With full batch (all 150): ~2 ms — achieved by collecting the batch across a tick.
CPU budget: 1 000 ms round − 2 ms WAL − 2 ms sig verify ≈ 996 ms for app + network.

10. Unbonding window as long-range attack defense:

Long-range attack: attacker buys N unbonded validators' keys and rebuilds a competing chain
from past height H where those validators were bonded.
Defense: any new node (or one offline > U) must obtain a trusted checkpoint from within the
last U days (weak subjectivity); attacker cannot re-use keys from > U days ago.
Quantitative: U = 21 days = 1 814 400 s; at 1 s/block = 1 814 400 blocks between checkpoints.
A syncing node checks: |trusted_checkpoint_age| < U.  See DP13, §23.
