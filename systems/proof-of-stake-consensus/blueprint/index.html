414 — Proof-of-Stake / BFT-Finality Consensus (Tendermint/Casper-style) from Scratch

Project Number: 414 Project Name: Proof-of-Stake / BFT-Finality Consensus (Tendermint/Casper-style) from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build a stake-weighted Byzantine-fault-tolerant consensus engine with economic finality — peer class to Tendermint (CometBFT) + Casper FFG (Gasper/Ethereum). Two finality regimes in one codebase: (a) Tendermint single-slot BFT — instant absolute finality via locked precommits; (b) Casper FFG finality gadget — checkpoint justification/finalization over an LMD-GHOST fork-choice block-tree. Correctness-first, observability-second, maintainability-third, performance-fourth.

Core capability surface:

  • Stake-weighted validator set — Vec<Validator { addr, pubkey:Ed25519, power:u64 }>; total power P = Σ power_i; Byzantine tolerance f < P/3; quorum threshold Q = ⌊2P/3⌋ + 1 (strictly > 2P/3).
  • HRS state machine — (height H:u64, round R:u32, step ∈ {Propose, Prevote, Precommit}); deterministic transitions on quorum/timeout events.
  • Deterministic proposer selection — stake-weighted round-robin via accumulating-priority algorithm; proposer(H,R,set) is pure.
  • Tendermint round flow — Proposal → Prevote → Precommit; +⅔ prevotes = "polka"/PoLC; lock+precommit; +⅔ precommits = commit (absolute finality).
  • Locking / PoLC / unlock — validator locked on block b at round r prevotes only b unless it sees PoLC for b' ≠ b at round > r (unlock/relock). Safety mechanism under f < P/3.
  • Round-skip / view-change — timeoutPropose/Prevote/Precommit, each += Δ per round; nil-votes; proposer rotation; liveness after GST (partial synchrony, DLS).
  • Commit certificate — the +⅔ precommit set for (H, block); portable proof of finality; optionally BLS-aggregated.
  • Casper FFG overlay — epochs/checkpoints; FFG votes (source→target) with stake weight; +⅔ link justifies target; two consecutive justified checkpoints finalize the earlier.
  • Two slashing conditions — (1) no two distinct votes same target height (double-vote/equivocation); (2) no surround vote. Accountable safety: conflicting finalization ⇒ ≥⅓ stake provably slashable.
  • LMD-GHOST fork-choice — Latest-Message-Driven Greedy-Heaviest-Observed-SubTree; weight subtrees by validators' latest votes; descend heaviest child. (Casper variant only; Tendermint locking makes its fork-choice trivial.)
  • Validator lifecycle — bonding/deposit; active-set selection (top-N by stake); unbonding period + withdrawal delay; jailing; tombstoning. Defends long-range attacks via weak subjectivity.
  • Slashing subsystem — evidence = two conflicting signed votes; gossip + on-chain submission + verification + slash fraction + reporter reward + tombstone.
  • Crypto — Ed25519 per-vote signatures (cross-link #90); BLS12-381 aggregation for compact certificates; light-client skipping verification.
  • ABCI-like app interface — CheckTx / BeginBlock / DeliverTx / EndBlock / Commit (app_hash); validator-set updates returned by app.
  • BFT time — block timestamp = stake-weighted median of precommit Timestamps.
  • Mempool + gossip reactors — tx gossip + CheckTx admission; vote/block-part/evidence propagation (cross-link #72).
  • Deterministic simulation — Byzantine fault injection (equivocation, withholding, partition); safety/liveness/accountability checkers over randomized histories.

System boundaries: a standalone replicated consensus node (bftd) + a client/RPC library (bft-client) + a CLI (bft-ctl) + a deterministic simulator (bft-sim). The application state machine is pluggable behind the ABCI-like boundary; a reference kv-app ships for testing.

Explicit non-goals:

  • NOT a smart-contract VM — app logic is opaque behind ABCI; EVM/WASM execution → PhaseDeferred("FINAL_BLUEPRINT §19") (kv-app only).
  • NOT Nakamoto PoW / longest-chain — probabilistic finality is explicitly contrasted, never implemented (see #182 and §38).
  • NOT a generic CFT consensus library — Raft/Paxos are non-Byzantine; that's #37 / #93. This is f < n/3 Byzantine + stake + incentives.
  • NOT a P2P transport stack — uses TCP + an internal gossip reactor; full libp2p/Noise handshake → PhaseDeferred("FINAL_BLUEPRINT §18").
  • NOT a token-economics / monetary-policy engine — inflation, fees, reward curves modelled minimally; full tokenomics out of scope.
  • NOT a production light-client-as-a-service / bridge — light-client verification core is built; hosted relay → out of scope.
  • NOT clock discipline — node reads wall-clock for proposal timestamps; NTP/PTP sync = #394; consensus never trusts a single clock for safety.

Deployment model: 4–150 validator nodes (BFT messaging is O(n²)); each node single-threaded deterministic consensus core + async I/O reactors; one process per validator; WAL-backed consensus-state persistence (cross-link #69).

Target users: blockchain protocol engineers, validator-infrastructure operators, distributed-systems engineers who need accountable Byzantine consensus with economic finality (slashing) rather than crash-only consensus.

2. Why Build This

  • Byzantine quorum mechanics — why f < n/3 (not n/2 as in CFT Raft/Paxos): a Byzantine node both lies and equivocates, so safety needs two honest-overlapping ⅔ quorums; 2(2f+1) − n ≥ f+1 intersection argument.

  • Locking as a safety device — Tendermint's lock/PoLC/unlock is the mechanism that makes single-slot finality safe; building it teaches how to prevent two correct validators committing different blocks without a leader-driven view-change log.

  • Economic finality vs. cryptographic finality — Casper FFG converts "honest majority" into "rational majority": violating finality costs ≥⅓ of total stake (accountable safety). This is the conceptual leap from PBFT.

  • Accountable safety proof, mechanised — the slashing-condition design (no double-vote, no surround) is the operational form of the accountable-safety theorem; you implement the detector that turns a safety violation into cryptographic evidence.

  • Two finality regimes, contrasted — Tendermint (couples consensus + finality, blocks if <⅔ online) vs. Gasper (decouples: LMD-GHOST keeps producing blocks; FFG finalizes lazily). Building both in one repo teaches the availability/finality tradeoff directly.

  • Fork-choice under dynamic validator latest-messages — LMD-GHOST subtree weighting, latest-message bookkeeping, equivocation handling in fork-choice.

  • Cryptoeconomic lifecycle — bonding, unbonding delay, weak subjectivity as the defence against long-range/costless-simulation attacks (the nothing-at-stake problem).

  • Signature aggregation — BLS aggregation to compress a 100-of-150 commit certificate from ~6 KB of Ed25519 sigs into one 96-byte BLS sig; the light-client bandwidth lever.

  • Tendermint (Buchman 2016; Buchman, Kwon, Milosevic 2018) — first widely-deployed PoS BFT with instant finality; basis of Cosmos/CometBFT; clean PoLC-based safety.

  • Casper FFG (Buterin & Griffith 2017) — finality gadget atop a fork-choice; introduced accountable safety + plausible liveness + the two slashing conditions; basis of Ethereum's PoS.

  • Gasper (Buterin et al. 2020) — Casper FFG + LMD-GHOST = Ethereum's beacon-chain consensus; the production reference for the Casper variant here.

  • PBFT (Castro & Liskov 1999, #94) — the BFT ancestor; permissioned, no stake, no incentives; Tendermint adds stake + simpler view-change.

  • DLS (Dwork, Lynch, Stockmeyer 1988) — partial synchrony model; the formal home of "liveness after GST".

Engineering muscles: Byzantine reasoning; safety/liveness proof intuition; cryptoeconomic mechanism design; signature aggregation; deterministic fault-injection testing; gossip protocol design. Production concepts: validator key management; double-sign protection (the operator's slashing nightmare); evidence gossip; weak-subjectivity checkpoint distribution; rolling upgrades under live consensus.

Cross-links:

  • #182 Bitcoin / Nakamoto PoW — probabilistic finality, longest-chain, no committee, no slashing. Contrast: this project = stake-weighted BFT voting, absolute/economic finality (see §38 for the architecture contrast).
  • #94 PBFT — permissioned CFT-adjacent BFT; no stake, no incentives, no slashing. This adds stake-weighting + economic finality + accountable safety.
  • #37 Raft / #93 Paxos — crash-fault-tolerant (n/2), leader-based, no Byzantine tolerance. Contrast: f < n/3, adversarial nodes.
  • #71 Merkle Trees — block tx-root, app-state-root, vote-set Merkleization for light-client proofs.
  • #90 Ed25519 — per-vote signature scheme; deterministic, fast verify.
  • #72 Gossip / Epidemic Broadcast — vote/block-part/evidence/tx propagation reactors.
  • #95 Vector Clocks / Lamport — causal reasoning about gossip message ordering; not used for safety, used for diagnostics.
  • #69 WAL — consensus-state durability (last (H,R,step) + signed votes) so a crashed validator never double-signs on restart.

Calibration value: BFT + cryptoeconomics is the highest-stakes correctness domain in distributed systems — a single safety bug can finalize two conflicting blocks (chain split) or, worse, a slashing bug can destroy honest validators' stake. Building this permanently raises an engineer's bar for Byzantine reasoning, accountable-safety design, and adversarial testing.

What Mastery Looks Like

  • Derive the f < n/3 bound from quorum intersection unaided — and know exactly where the >2P/3 (not ≥) strictness is load-bearing (built in §12, proven in §24).
  • Reason about locking as the safety device that replaces a view-change log — explain why a locked validator prevotes nil rather than a competing block (built in §15).
  • Distinguish economic from cryptographic finality and implement the converter — the two slashing conditions that mechanise accountable safety (built in §22).
  • Build two finality regimes and articulate the availability/finality tradeoff — Tendermint halts, Gasper stays available; you can choose per deployment (built in §14–§17 vs §20–§21, contrasted in §38).
  • Implement LMD-GHOST subtree weighting with incremental proto-array updates and know the balancing-attack failure mode (built in §21).
  • Defend a PoS chain against long-range attacks via weak subjectivity — explain why genesis-only sync is unsafe and what the unbonding window buys (built in §23).
  • Aggregate a commit certificate with BLS and defeat the rogue-key attack with proof-of-possession — the light-client bandwidth lever (built in §23).
  • Find consensus safety bugs with deterministic Byzantine fault injection — write the three checkers (safety/liveness/accountability) that gate every merge (built in §24).

Client / RPC Layer — bft-client issues broadcast_tx, state query, validators, and commit-cert requests over RPC. bft-ctl is the operator CLI (cluster status, validator bond/unbond, evidence submission, WAL/state inspection). bft-light is a light client that verifies commit certificates + validator-set transitions without running full consensus.

bft-net (Gossip Reactors + Mempool) — maintains PeerSet (per-peer round-step state); Mempool admits txs via app CheckTx and gossips them; VoteReactor gossips prevotes/precommits driven by peer HRS state; BlockPartReactor propagates erasure-split block parts; EvidenceReactor gossips slashing evidence. All inbound messages are signature-checked before reaching consensus.

bft-consensus (Tendermint HRS State Machine) — the single-threaded deterministic core. Holds ConsensusState{H,R,Step,locked_value,locked_round,valid_value,valid_round,votes:HeightVoteSet}. Drives proposal, prevote (lock-aware), precommit (PoLC-driven), commit detection, and timeout-driven round advancement. The only place consensus decisions are made; every signed vote is persisted to the WAL before it leaves the node.

bft-abci — application connection. BeginBlock (per-block app setup + evidence delivery for slashing), DeliverTx (apply each tx), EndBlock (returns validator-set updates), Commit (returns app_hash folded into the next block header). The kv-app reference implements a Merkleized key-value store for testing; real apps plug in here.

bft-wal — consensus-state WAL. Persists (H,R,step) transitions and every signed vote before gossiping it; on crash, replays to reconstruct exact pre-crash consensus state so the validator never double-signs (the #1 slashing cause). Cross-links #69.

bft-slashing — EquivocationDetector (two distinct votes, same (H,R,step) or same FFG target) and SurroundDetector (FFG surround). EvidencePool holds verified evidence pending inclusion; SlashExecutor applies the slash fraction + reporter reward + tombstone via the validator set.

bft-validators (Stake-weighted Set + Lifecycle) — ValidatorSet (sorted, with cached total power P); ProposerPriority implements the accumulating-priority weighted round-robin; lifecycle: bond/deposit → active-set selection → unbond (with delay) → jail (temporary) → tombstone (permanent, post-slash).

bft-ffg (Casper FFG) — checkpoint tree at epoch boundaries; FFGVote{source, target}; +⅔ link justifies target; two consecutive justified checkpoints finalize the earlier. Tracks justified/finalized checkpoints; feeds slashing the FFG vote stream.

bft-forkchoice (LMD-GHOST) — BlockTree of all known blocks; LatestMessages map (validator → latest attestation); GHOST head selection by descending the heaviest-stake-weighted subtree. Used by the Gasper/Casper variant. Contrasted with Tendermint, whose locking eliminates competing chains so its "fork choice" is trivially "the committed block".

bft-crypto — Ed25519 sign/verify (deterministic, malleability-resistant), SHA-256 + BLAKE3 hashing, Merkle trees (#71) for block roots + vote-set proofs, BLS12-381 aggregate-verify for compact commit certificates.

Internal validator gossip (TCP 26656) — authenticated peer connections; consensus + mempool + evidence multiplexed over per-reactor channels.

6. Design Principles

DP1 — Safety over liveness, always. When in doubt the node halts rather than risks finalizing two conflicting values. Tendermint blocks under <⅔ availability by design. Tradeoff: a stalled chain (no progress) is acceptable; a forked finalized chain is catastrophic. Violation: relaxing the quorum from >2P/3 to ≥2P/3 admits two disjoint quorums under Byzantine equivocation ⇒ conflicting commits.

DP2 — Determinism in the consensus core. bft-consensus is a pure state machine over (state, event) → (state', actions); no wall-clock reads, no RNG, no map-iteration-order dependence inside decisions. Tradeoff: timeouts are injected as explicit events, not read from a clock inside the core. Violation: nondeterminism ⇒ divergent decisions across honest nodes / non-reproducible simulator failures.

DP3 — Never double-sign. A validator MUST persist (H,R,step, signed vote) to the WAL and fsync before the vote leaves the process. On restart it refuses to sign anything at-or-below the last persisted (H,R,step). Tradeoff: one fsync per vote on the critical path. Violation: double-sign after crash ⇒ self-slashing; the operator's worst outcome.

DP4 — Accountable safety is non-negotiable. Every safety-relevant vote is a signed, attributable commitment. Any safety violation MUST be reducible to cryptographic evidence implicating ≥⅓ of stake. Tradeoff: votes cannot be anonymous/aggregated before the evidence window closes. Violation: unattributable equivocation ⇒ no slashing ⇒ the economic-finality guarantee collapses to PBFT-level honest-majority.

DP5 — Locking before precommitting. A validator precommits a value only after observing a PoLC (+⅔ prevotes) for it, and stays locked until a higher-round PoLC unlocks it. Tradeoff: extra round state (locked_value/round, valid_value/round). Violation: precommitting without a polka lets a Byzantine proposer split honest precommits across two values.

DP6 — Stake-weight everything; never count nodes. Quorums, proposer selection, fork-choice weight, and slashing are all in units of power, never count. Tradeoff: one whale ≥ ⅓ can halt liveness (acceptable, by design). Violation: counting nodes lets a Sybil with many low-stake keys subvert quorum.

DP7 — Crash-only consensus state. No graceful "drain"; crash = process exit; restart = WAL replay to exact pre-crash (H,R,step). Tradeoff: all volatile peer/gossip state is rebuilt from scratch on restart. Violation: a "clean shutdown" path that skips WAL fsync risks double-sign on the next start.

DP8 — Backpressure on every reactor. Mempool, vote, block-part, evidence channels are bounded; full ⇒ drop-oldest (mempool) or stall-peer (consensus). Tradeoff: a slow peer is throttled, not allowed to OOM us. Violation: unbounded vote buffering under a flood ⇒ OOM ⇒ node death ⇒ liveness loss.

DP9 — Observability by default. Every HRS transition, every vote add, every timeout, every evidence detection emits a structured event + metric. Tradeoff: log volume at high block rates. Violation: a silent liveness stall (stuck at round R) is undebuggable without round-step telemetry.

DP10 — Validate signatures at the boundary. Every inbound vote/proposal/evidence is signature-checked in bft-net before it reaches consensus; the core trusts its inputs are authentic (but still adversarial in content). Tradeoff: sig verify is the CPU hot path. Violation: forged votes reaching the core ⇒ fake quorums.

DP11 — Evidence is verifiable and self-contained. A piece of slashing evidence carries both conflicting signed votes; any node (or light client) can verify it independently against the validator set, without trusting the reporter. Tradeoff: evidence is larger than a single vote. Violation: trusting a reporter's claim ⇒ griefing (slash honest validators).

DP12 — Finalized is forever. A committed (Tendermint) or finalized (FFG) block is never reverted. Fork-choice and round-skip operate strictly above the finalized frontier. Tradeoff: the finalized prefix cannot be rolled back even to fix a bug (must hard-fork). Violation: reverting finality breaks the absolute-finality contract that distinguishes this from Nakamoto.

DP13 — Weak subjectivity over naive trustlessness. New/long-offline nodes sync from a recent trusted checkpoint within the unbonding window, not from genesis. Tradeoff: a trusted checkpoint source is required (a known limitation of PoS). Violation: trusting genesis-only sync ⇒ long-range / costless-simulation attacks (nothing-at-stake).

DP14 — Separate the two finality regimes cleanly. Tendermint single-slot finality and Casper FFG live behind distinct modules with a shared validator-set + crypto layer; a node runs in one mode. Tradeoff: two code paths to maintain. Violation: entangling locking (Tendermint) with lazy FFG finalization produces an unsound hybrid with neither's guarantees.

DP15 — Bounded resource usage per height. Vote sets, block parts, and peer state are bounded per height; the block tree is pruned below the finalized checkpoint. Tradeoff: explicit pruning logic. Violation: unbounded block-tree growth (Casper) ⇒ memory exhaustion under long non-finalization.

8.1 Core wire types (EBNF-ish)

Vote       ::= { typ:Step', height:u64, round:u32,
                 block_id: Option<BlockId>,     -- None = nil vote

                 validator_index:u32, signature:Ed25519Sig }

Evidence ::= DuplicateVote { vote_a:Vote, vote_b:Vote }    -- same (H,R,step), block_a ≠ block_b

8.5 Tendermint HRS state machine

ConsensusState ::= {
  height:u64, round:u32, step:Step,
  locked_value: Option<Block>, locked_round:i32,   -- -1 = unlocked
  valid_value:  Option<Block>, valid_round:i32,    -- -1 = none
  proposal: Option<Proposal>,
  votes: HeightVoteSet,                              -- prevotes+precommits per round
  commit_round:i32
}

8.6 Casper FFG state machine

Epoch boundary every E slots. Checkpoint(epoch, root) = block at first slot of epoch.
FFG vote (source → target): source = current justified checkpoint; target = current epoch checkpoint.

JUSTIFY(target):   power of FFGVotes with this (source→target) link  > 2P/3
FINALIZE(source):  source is justified AND target = source.epoch+1 is justified
                   (two consecutive justified checkpoints ⇒ earlier finalized)

State-transition table (FFG):

Current Event Guard Next
justified=C0 collect FFG votes (C0→C1) power > 2P/3 C1 justified
C1 justified C0→C1 was the link AND C1.epoch = C0.epoch+1 — C0 finalized
any FFG vote received passes slashing checks add to vote set, update justification_bits

8.7 Slashing condition state-transition (detector)

Stored votes (validator v) New vote Condition Evidence
prevote/precommit (H,R,step, b) (H,R,step, b') with b'≠b duplicate-vote DuplicateVote{a,b}
FFG (s1→t1) FFG (s2→t2), t2.epoch = t1.epoch, t1≠t2 double FFG vote DuplicateFFG{a,b}
FFG (s1→t1) FFG (s2→t2) with s2<s1 ∧ t1<t2 surround (new surrounds old) SurroundFFG{inner=old,outer=new}
FFG (s1→t1) FFG (s2→t2) with s1<s2 ∧ t2<t1 surrounded (new inside old) SurroundFFG{inner=new,outer=old}

8.8 Proposer selection (accumulating-priority, deterministic)

Priority recurrence (accumulating-priority weighted round-robin), given ValidatorSet with total_power P:
  priority'(v)          = priority(v) + power(v)        over all v ∈ ValidatorSet   (one step)
  proposer(step)        = argmax_v priority'(v)          (ties broken by address; deterministic)
  priority''(proposer)  = priority'(proposer) − P        (centering applied to the selected proposer only)
Distribution invariant: over P steps, v is selected ≈ power(v)/P of the time — deterministic given (set, #steps).
Reseeding: the recurrence's carried `priority` state is re-derived deterministically per height from the
prior height's ending state plus that height's slashing/bonding deltas.

8.9 LMD-GHOST fork-choice (Casper variant)

LatestMessage[v] = the highest-epoch attestation (block vote) by validator v.
weight(block)     = Σ { v.power : block is ancestor-or-self of LatestMessage[v].block }
head              = the deepest descendant of finalized_checkpoint.block reachable by always
                    taking the child argmax_{c ∈ children(node)} weight(c)  (ties: higher hash);
                    a leaf (no children) is its own head.

Contrast: Tendermint never has competing children at the finalized frontier (locking + single-slot commit), so its "fork choice" is trivially the last committed block; LMD-GHOST exists only because Gasper decouples block production from finalization (see §38 for the regime contrast).

8.10 Worked examples

Happy path (Tendermint, n=4, equal power, f=1, Q=3):

H=10, R=0, proposer = V0.
1. V0 proposes Block B (pol_round=-1).
2. V0,V1,V2,V3 (unlocked) prevote B.        -> prevotes(B) power = 4 > 2P/3=2.66  -> polka.
3. All lock on B (locked_round=0), precommit B.
4. precommits(B) power = 4 > Q.             -> COMMIT B at (H=10,R=0).
Commit certificate = {B, [V0,V1,V2,V3 precommit sigs]}.  Absolute finality. Block time = median(timestamps).

Round-skip / proposer failure (liveness after GST):

H=11, R=0, proposer = V1 but V1 is offline.
1. V0,V2,V3 wait; no proposal -> timeoutPropose(0) fires -> each prevote nil.
2. prevotes(nil) power = 3 > Q -> each precommit nil.
3. precommits(nil) power = 3 > Q (or timeoutPrecommit) -> start_round(1).
H=11, R=1, proposer = V2 (next by priority).
4. V2 proposes B'; V0,V2,V3 prevote B' -> polka -> precommit B' -> COMMIT B'.
Liveness restored within ~2 timeouts. (Guaranteed only after GST.)

Conflicting-proposal / locking safety (why no fork):

H=12, R=0: Byzantine proposer V3 sends Block X to {V0,V1} and Block Y to {V2}.
1. V0,V1 prevote X; V2 prevotes Y; V3 equivocates (prevotes both).
   prevotes(X)=V0,V1,V3 = 3 ≥ Q ? With f=1, V3 lying: honest prevotes(X)=2 < Q.
   No honest-only polka for X OR Y -> no honest validator locks -> all precommit nil.
2. precommits(nil) reaches Q among honest -> start_round(1) with honest proposer.
Safety (I1) held: Q > 2P/3 requires the honest ⅔ to agree; Byzantine f < P/3 cannot complete a quorum alone.

FFG justification + finalization:

Epoch boundaries C0(e=5), C1(e=6), C2(e=7).
1. FFG votes (C0->C1) accumulate to power 0.70P > ⅔ -> C1 JUSTIFIED.
2. FFG votes (C1->C2) accumulate to power 0.68P > ⅔ -> C2 JUSTIFIED, and C1.epoch+1 = C2.epoch
   -> C1 FINALIZED.   (Two consecutive justified checkpoints finalize the earlier.)

Slashing — surround vote (malformed validator behaviour):

Validator V5 earlier cast FFG (source=e3 -> target=e4).
Later V5 casts FFG (source=e2 -> target=e7).  Here 2<3 (src) and 4<7 (tgt): the new vote SURROUNDS the old.
Detector emits SurroundFFG{inner=(e3->e4), outer=(e2->e7)}.
SlashExecutor: slash V5 (fraction f_s), reward reporter, TOMBSTONE V5 (permanent set removal).

Malformed inputs (rejected at boundary, never reach core):

- Vote with bad Ed25519 signature              -> drop; metric net.invalid_sig.
- Vote for height < current finalized           -> drop (stale).
- Precommit block_id not matching any block part -> stash until parts arrive; else drop on round end.
- Evidence whose two votes are identical         -> reject (not conflicting); slashing.invalid_evidence.
- ValidatorSet update making Σpower ≠ P bookkeeping -> reject app response; halt (I6).
- FFG vote with target.epoch < source.epoch      -> reject (malformed link).

11. Core Schema and Core Types

Vote (bft-core):

struct Vote {
  typ: Step,                 // Prevote | Precommit (Propose is a Proposal, not a Vote)
  height: u64,
  round: u32,
  block_id: Option<BlockId>, // None encodes a nil vote
  timestamp: i64,            // unix nanos; for BFT-time median
  validator_address: Address,
  validator_index: u32,      // index into the height's ValidatorSet
  signature: Ed25519Sig,     // over canonical_sign_bytes(self) with domain tag
}
fn canonical_sign_bytes(&self, chain_id:&str) -> Vec<u8>;  // deterministic; domain-separated
fn verify(&self, set:&ValidatorSet) -> Result<(), VoteError>;

Ownership: created by bft-consensus for self-votes (and persisted to WAL before release); received votes are owned by HeightVoteSet. Mutation: immutable post-signature. Concurrency: single-threaded core; received votes cross the net→core channel by value. Persistence: self-votes WAL-logged; commit-cert votes stored in the finalized Commit. Serialization: protobuf-canonical (A09); the sign bytes are domain-separated and chain-id-scoped to prevent cross-chain replay. Compatibility: vote encoding frozen; new fields appended with default-zero.

BlockId / Block / Header (bft-core):

struct PartSetHeader { total: u32, hash: Hash }
struct BlockId { hash: Hash, part_set: PartSetHeader }   // None-able as "nil"
struct Header {
  height:u64, time:i64, last_block_id:BlockId,
  last_commit_hash:Hash, data_hash:Hash,
  validators_hash:Hash, next_validators_hash:Hash,
  app_hash:Hash, proposer_address:Address,
}
struct Block { header:Header, txs:Vec<Tx>, last_commit:Commit, evidence:Vec<Evidence> }
fn Block::hash(&self) -> Hash;   // Merkle root over header fields (#71)

Ownership: proposer creates; gossiped as parts; reassembled by receivers. Persistence: finalized blocks → block store (A11). The app_hash is the previous block's committed app state (lagged by one) — a Tendermint determinism subtlety. Compatibility: header layout frozen; validators_hash/next_validators_hash bind the valset into the chain so light clients verify transitions.

Commit (bft-core) — the finality certificate:

struct CommitSig { flag: CommitSigFlag, validator_address:Address, timestamp:i64, signature:Ed25519Sig }
enum CommitSigFlag { Absent, Commit, Nil }
struct Commit { height:u64, round:u32, block_id:BlockId, signatures:Vec<CommitSig> }
fn power(&self, set:&ValidatorSet) -> Power;     // sum of Commit-flagged sig powers
fn verify(&self, set:&ValidatorSet) -> Result<(), CommitError>;  // power > 2P/3 AND all sigs valid

The portable proof a block is final. A light client needs only Commit + the validator set. Optionally BLS-aggregated (§23) into a 96-byte sig + bitfield. Persistence: included as last_commit in the next block ⇒ committed into the chain.

ValidatorSet + Validator (bft-validators):

enum ValidatorStatus { Bonded, Unbonding, Unbonded, Jailed, Tombstoned }
struct Validator {
  address:Address, pubkey:Pubkey, power:Power,
  proposer_priority:i64, status:ValidatorStatus, unbonding_completion_time:i64,
}
struct ValidatorSet { validators:Vec<Validator>, total_power:Power, proposer:Address }
fn ValidatorSet::quorum(&self) -> Power;                 // ⌊2*total_power/3⌋ + 1
fn ValidatorSet::proposer(&self, round:u32) -> Address;  // deterministic priority algo
fn ValidatorSet::update(&mut self, changes:&[ValidatorUpdate]) -> Result<(), ValsetError>; // EndBlock
fn ValidatorSet::hash(&self) -> Hash;                    // bound into Header

Ownership: one per height; transitions on EndBlock. Mutation: only via update (validated for power conservation I6). Concurrency: single-threaded. Persistence: validator sets stored keyed by height (light clients fetch). Determinism (I9): proposer(round) MUST be identical across nodes — the accumulating-priority state is part of the deterministic per-height seed.

ConsensusState (bft-consensus):

struct ConsensusState {
  chain_id:String,
  height:u64, round:u32, step:Step,
  validators:ValidatorSet,
  proposal:Option<Proposal>, proposal_block:Option<Block>,
  locked_value:Option<Block>, locked_round:i32,   // -1 = unlocked
  valid_value:Option<Block>,  valid_round:i32,    // -1 = none
  votes:HeightVoteSet,
  commit_round:i32,
  wal:WalHandle,
}
fn handle_event(&mut self, ev:Event) -> Vec<Action>;   // pure-ish: only WAL + emitted actions are side effects
fn add_vote(&mut self, v:Vote) -> Result<AddVoteOutcome, VoteError>;

The deterministic heart. handle_event maps (state, Event) → (state', [Action]); Actions (sign-vote, broadcast, set-timeout, commit) are executed by the outer reactor. Self-votes are WAL-fsynced inside the handler before the broadcast action is emitted (DP3). No clock reads, no RNG (DP2).

HeightVoteSet / VoteSet (bft-consensus):

struct VoteSet {
  height:u64, round:u32, typ:Step,
  set:ValidatorSet,
  votes:Vec<Option<Vote>>,        // indexed by validator_index
  votes_by_block: HashMap<BlockId, Power>,
  sum: Power, maj23: Option<BlockId>,  // maj23 = the +⅔ block, if any
}
struct HeightVoteSet { height:u64, rounds: HashMap<u32, RoundVoteSet> }  // prevotes+precommits per round
fn VoteSet::add(&mut self, v:Vote) -> Result<(), VoteError>;  // rejects 2nd vote ⇒ flags equivocation
fn VoteSet::has_two_thirds_majority(&self) -> Option<BlockId>;
fn VoteSet::has_two_thirds_any(&self) -> bool;   // ⅔ voted (for anything) ⇒ timeout trigger

Detects PoLC (maj23) and equivocation (second distinct vote from same index). Persistence: transient per height; cleared after commit. The bit-array/by-index layout bounds memory to O(n) per round.

FFGState / Checkpoint / FFGVote (bft-ffg):

struct Checkpoint { epoch:u64, root:Hash }
struct FFGVote { source:Checkpoint, target:Checkpoint, validator_index:u32, signature:Ed25519Sig }
struct FFGState {
  justified:Checkpoint, finalized:Checkpoint,

Ownership: one per node. Mutation: only on_vote (after slashing checks). Persistence: justified/finalized checkpoints persisted (they gate fork-choice and pruning). Determinism: justification is a pure function of the accumulated link powers.

Evidence + EvidencePool (bft-slashing):

enum Evidence {

Ownership: one pool per node. Mutation: add (verify-then-store) + drain-on-block-inclusion. Persistence: included evidence committed into blocks. DP11: verify is self-contained — verifies both signed votes against the historical valset; never trusts the reporter.

ConsensusWAL (bft-wal):

enum WALEntry { Step{h:u64,r:u32,step:Step}, SignedVote(Vote), SignedProposal(Proposal), Commit(Commit) }
struct ConsensusWAL { file:File, last_signed:HRS }   // HRS = (height,round,step)

12.6 Pitfalls

  • Quorum off-by-one: 2P/3 integer truncation; Q = 2P/3 + 1 is correct (strictly > ⅔) but verify P=3 ⇒ Q=3, P=4 ⇒ Q=3. Getting ≥⅔ instead of >⅔ is a safety bug (admits two disjoint quorums).
  • Sign-byte ambiguity: missing length prefixes let a Prevote's bytes collide with a Precommit's ⇒ a signature valid for both ⇒ accidental equivocation framing. Length-prefix + type-tag every field.
  • Step ordering: Propose < Prevote < Precommit must hold so can_sign monotonicity works; an incorrect Ord derive breaks DP3.
  • Power as node count: never store "1 vote = 1 node"; Power is stake; tests must use unequal powers.

12.7 Performance Concerns

  • canonical_sign_bytes: allocates a Vec; pre-size from field sizes; called once per vote (cheap relative to the Ed25519 sign that follows).
  • Power arithmetic: u64 checked ops; negligible.

12.8 Edge Cases

  • P = 0 (empty set): quorum undefined; reject at construction (ValsetError::Empty).
  • Single validator (n=1): Q = quorum(P) = P (that one validator's full power); trivially Byzantine-intolerant but must not panic.
  • Nil vote (block_id = None): sign-bytes must encode "nil" unambiguously (not an empty hash that collides with a real block).

12.9 Failure Analysis

  • CI fmt/clippy failure: style; fix before merge.
  • cargo audit advisory on a crypto dep: block merge; pin/patch; document in SECURITY.md.
  • Sign-byte fixture mismatch: canonical encoding drifted; this is a consensus-breaking change — bump chain protocol version.

12.10 Operational Notes

  • No runtime components in P0; pure library + CI.
  • rust-toolchain.toml pins stable; bumps go in a dedicated PR.
  • Document the quorum intersection lemma in notes/byzantine-quorum.md (referenced by I1/I4).

  • ValidatorSet::hash() identical for identical sets regardless of insertion order (sorted-by-address).
  • Ed25519: sign→verify roundtrip; tampered message/sig fails; small-order pubkey rejected.
  • Power conservation: update rejects changes that would make Σpower ≠ recomputed total (I6).
  • Tombstoned validator cannot be re-bonded.

13.5 Conformance Fixtures

  • conformance/fixtures/happy_path/proposer_sequence.json — set (unequal powers) ⇒ proposer for rounds 0..20.
  • conformance/fixtures/happy_path/valset_hash.json — set ⇒ expected hash (order-independent).
  • conformance/fixtures/malformed/valset_power_mismatch.json — update breaking power sum ⇒ rejected.
  • conformance/fixtures/happy_path/merkle_proof.json — leaves ⇒ root + valid/invalid proofs.

13.6 Pitfalls

  • Priority drift / overflow: repeated += power without centering grows priorities unboundedly; center by subtracting the average each increment; clamp to avoid i64 overflow. Drift also breaks cross-node determinism if centering differs.
  • Non-deterministic tie-break: argmax on equal priorities must break ties by address (stable), never by hash-map iteration order (I9 violation).
  • Address from pubkey: must hash the canonical pubkey encoding; a different encoding ⇒ different address ⇒ valset-hash divergence.
  • Unbonding without delay: immediately removing power on begin_unbond enables long-range attacks; power stays until completion_time (and remains slashable in the window).
  • Merkle leaf ambiguity: domain-tag leaves vs interior nodes (RFC 6962 0x00/0x01) to prevent second-preimage attacks.

13.7 Performance Concerns

  • increment_priority: O(n) per round; n ≤ 150 ⇒ negligible.
  • ValidatorSet::hash: O(n) Merkle build per set change; cache and only recompute on update.
  • Ed25519 verify: ~50–70 µs/sig; this is the CPU hot path under high vote volume (batched in later phases).

13.8 Edge Cases

  • Single validator: always the proposer; priority algorithm degenerates gracefully.
  • Two validators with equal power: alternate strictly; tie-break by address must be stable.
  • Validator with power = 0: reject at bonding (ValsetError::ZeroPower); a zero-power validator never proposes and dilutes nothing.
  • Set change mid-round: the proposer for height H uses the set as of H's start (frozen per height).

13.9 Failure Analysis

  • Proposer mismatch across nodes (I9): priority-centering bug or tie-break nondeterminism; detect via consensus.proposer_mismatch; halt and compare priority vectors; this is a valset-divergence emergency.
  • Valset-hash divergence: pubkey-encoding or sort-order bug; light clients reject the chain; compare canonical leaf bytes.

13.10 Operational Notes

  • metrics::gauge!("validators.total_power"), gauge!("validators.count"), gauge!("validators.jailed").
  • tracing::info! on every bond/unbond/jail/tombstone with addr + power delta.
  • bft-ctl validators power-table for operators to audit stake distribution (whale ≥ ⅓ = liveness risk).

14. Phase 2 — Tendermint State Machine: Happy Path (Single-Round Commit)

14.1 Objectives

  • Implement the HRS state machine core: Propose → Prevote → Precommit → Commit, no locking yet (added §15), no round-skip yet (added §16).
  • Implement HeightVoteSet / VoteSet with +⅔ majority (maj23) and equivocation flagging.
  • Implement CommitDetector: +⅔ precommits for a block ⇒ commit.

14.2 Detailed Implementation Steps

  • bft-consensus/src/events.rs: enum Event { StartRound(u32), Proposal(Proposal), AddVote(Vote), Timeout(Hrs) }; enum Action { SignVote(Step,Option<BlockId>), Broadcast(Msg), SetTimeout(Hrs,Duration), Commit(Block) } — actions executed by the outer driver (DP2: core has no I/O; the (state,event)→(state',actions) shape follows the Tendermint paper, P1, and CometBFT, R1).
  • bft-consensus/src/vote_set.rs: VoteSet indexed by validator_index; add rejects a 2nd distinct vote (returns DoubleVote{a,b} for §22, foundation for I3); votes_by_block power accumulation (DP6); has_two_thirds_majority() (I4) and has_two_thirds_any().
  • bft-consensus/src/state.rs: ConsensusState::handle_event (DP2):
    • StartRound(R): set step=Propose; if proposer(H,R)==me (I9) ⇒ emit Broadcast(Proposal(new_block)); else nothing (timeout added §16).
    • Proposal(p): validate proposer + signature + height/round (DP10); store; if valid ⇒ emit SignVote(Prevote, Some(block_id)); step=Prevote.
    • AddVote(v): route to the round's prevote/precommit VoteSet; on prevote maj23(b) ⇒ emit SignVote(Precommit, Some(b)); step=Precommit. On precommit maj23(b) ⇒ emit Commit(b) (I4).
  • bft-consensus/src/commit.rs: CommitDetector builds the Commit certificate from the +⅔ precommit VoteSet.
  • bft-consensus/src/propose.rs: create_proposal (proposer) + validate_proposal (receiver: proposer match, sig, round).
  • Driver loop (outer, in bft-sim for now): executes Actions, signs via bft-crypto, feeds resulting votes back as AddVote events; synchronous virtual network delivers to all peers.
  • examples/four_validator.rs: 4 honest validators; commit 100 blocks; assert all commit the same block per height (I1).

  • 100-block run (n=4, honest, synchronous): all validators commit identical blocks (I1 trivially holds — no Byzantine yet).
  • A block commits only with precommit power > 2P/3 (I4) — assert in CommitDetector.
  • VoteSet::add flags a second distinct vote from the same index as DoubleVote (foundation for §22).
  • handle_event is pure: same (state, event) ⇒ same (state', actions) across runs (DP2) — golden-trace test.
  • No clock read inside bft-consensus (grep-asserted in CI, A17).

14.5 Conformance Fixtures

  • conformance/fixtures/happy_path/commit_n4_round0.json — full event trace ⇒ committed block + commit cert.

14.6 Pitfalls

  • Counting power, not votes, for maj23: maj23 must sum validator.power, not increment a counter; a +1 per vote is a safety bug with unequal stake (DP6).
  • Applying a vote before signature check: net layer verifies sigs (DP10); but the core must still reject votes from indices outside the set (defensive).
  • Committing on +⅔ any instead of +⅔ for a block: has_two_thirds_any triggers timeouts (§16), not commits; commit requires maj23 on a specific block_id.
  • Proposal/block decoupling: the proposal references a BlockId; the block parts may arrive separately (§18). In §14 (synchronous) they arrive together; do not bake that assumption into the core.

14.7 Performance Concerns

  • VoteSet::add: O(1) index insert + power add; the maj23 check is O(1) by maintaining a running max per block_id.

  • The Ed25519 sign per self-vote (~50 µs) dominates a round's CPU at small n.

14.8 Edge Cases

  • All validators propose-and-prevote identically: clean single-round commit.
  • Proposal for a different round than current: stash if round > R (relevant §16); reject if stale.
  • Empty block (no txs): valid; commits normally (heartbeat-style progress).
  • Duplicate identical vote (same index, same block): idempotent — not equivocation (only distinct block_ids equivocate).

14.9 Failure Analysis

  • Non-deterministic trace: a HashMap iteration leaked into a decision; golden-trace test catches it; replace with sorted/indexed iteration (DP2).
  • Premature commit: maj23 computed with a Byzantine-inflated count (future phases) — but in §14, a power-sum bug; assert commit_power > 2P/3 (I4).

15. Phase 3 — Locking, PoLC, and Unlock Rules (Safety Under Conflicting Proposals)

15.1 Objectives

  • Implement LockState (locked_value, locked_round, valid_value, valid_round).
  • Implement lock-aware prevote: locked validators prevote only their locked value (or nil).
  • Implement PoLC (Proof-of-Lock-Change) detection and the unlock/relock rule.
  • Prove (by test + simulator) Agreement (I1) holds under a Byzantine proposer sending conflicting proposals, given f < P/3.

15.2 Detailed Implementation Steps

  • bft-consensus/src/lock.rs: LockState (DP5; the locking mechanism from the Tendermint paper, P1); on_polka(round, block_id) updates valid_value/valid_round always, and unlocks if block_id ≠ locked_value ∧ round > locked_round (I5).
  • bft-consensus/src/prevote.rs: lock-aware prevote logic (DP5):
    • if locked_round == -1 (unlocked): prevote the proposal's block if valid, else nil.
    • if locked on b: prevote b if proposal == b OR proposal carries a pol_round > locked_round justifying a different block (then unlock first); else prevote nil.
  • bft-consensus/src/precommit.rs: on prevote maj23(b) (polka): locked_value=b; locked_round=R; valid_value=b; valid_round=R; precommit b. On polka-nil or timeout: precommit nil (do NOT unlock on nil).
  • Proposal extension: pol_round field — a proposer re-proposing a previously-locked value cites the round it saw the polka, letting locked validators verify the unlock is legitimate.
  • bft-consensus/src/state.rs: integrate LockState; enforce I5 (locked_round monotone increasing).
  • bft-sim Byzantine hook: a proposer that sends Block X to half the validators and Block Y to the other half (the classic safety test for I1).
  • Tests + fixtures: conflicting proposals never produce two commits; locked validator refuses to prevote a competing block without a higher-round PoLC.

15.3 Deliverable

examples/proposer_failure.rs extended with a conflicting-proposal Byzantine proposer; cluster never forks. bft-sim conflicting-proposal scenario passes the safety checker.

15.4 Acceptance Criteria

  • Under a Byzantine proposer (f=1, n=4) sending conflicting blocks: no two correct validators commit different blocks at the same height (I1).
  • locked_round strictly increases across locks (I5); assert on every lock.
  • A validator locked on b at round r prevotes nil (not a competing b') absent a PoLC for b' at round > r.
  • Unlock occurs iff a PoLC for b' ≠ b at round > locked_round is observed.
  • valid_value/valid_round updated on every polka, even when locked (used by the proposer to re-propose).

15.5 Conformance Fixtures

  • conformance/fixtures/locking/conflicting_proposal_no_fork.json — Byzantine proposer trace ⇒ both honest validators commit same-or-nothing.
  • conformance/fixtures/locking/lock_then_prevote_nil.json — locked validator sees competing proposal ⇒ prevotes nil.
  • conformance/fixtures/locking/unlock_on_higher_polc.json — higher-round PoLC ⇒ unlock + relock.
  • conformance/fixtures/locking/lock_round_monotonic.json — sequence asserting locked_round only increases.

15.6 Pitfalls

  • Unlocking on a nil polka: a +⅔ prevote-nil must NOT unlock (only a polka for a different block unlocks); unlocking on nil reintroduces fork risk.
  • Accepting an unjustified re-proposal: a proposer claiming pol_round=r for block b' must actually have a polka at r; a locked validator should verify (or at minimum the safety argument relies on honest majority not having locked otherwise) — document the trust assumption precisely.
  • valid_round vs locked_round confusion: valid_value tracks the latest polka (for re-proposing); locked_value gates prevoting. Conflating them breaks both safety and liveness.
  • Lock surviving across heights: locks are per-height; reset on StartRound of a new height. A leaked lock stalls the next height.
  • Off-by-one in pol_round = -1 sentinel: -1 means "no PoLC"; using 0 as the sentinel collides with a real round 0 polka.

15.7 Performance Concerns

  • Lock checks are O(1) per prevote; no measurable cost.
  • The safety-critical path adds no allocation; LockState is a few scalar fields + Option<Block> (the block is shared by Arc to avoid copies).

15.8 Edge Cases

  • Validator locked on b, then b is re-proposed at a later round: prevote b (consistent); commit proceeds.
  • All honest validators locked on different rounds' values: liveness may stall until a common PoLC emerges at a higher round (resolved by round-skip §16 after GST).
  • Byzantine validator equivocates in prevote (votes both X and Y): counts toward neither honest polka; VoteSet flags equivocation (slashing §22).
  • Single honest validator locked while others unlocked: that validator prevotes nil; if others form a polka on a new value at a higher round, it unlocks.

15.9 Failure Analysis

  • Two conflicting commits (I1 breach): the gravest failure; almost always a quorum-math (≥⅔ vs >⅔) or lock-rule bug. Halt; dump all votes for the height; this is reducible to slashing evidence (≥⅓ equivocated) only if the protocol is sound — if honest nodes forked, it's a code bug, not a slashable event.
  • Liveness stall from over-locking: validators locked on incompatible values never converge; detect via consensus.round climbing without commit; resolved by §16 round-skip + the proposer re-proposing valid_value.

15.10 Operational Notes

  • metrics::gauge!("consensus.locked_round"), gauge!("consensus.valid_round").
  • metrics::counter!("consensus.unlocks"), counter!("consensus.prevote_nil") (high nil rate ⇒ contention/Byzantine activity).
  • tracing::warn! on every lock/unlock with old/new locked_round + block_id.
  • Runbook docs/runbooks/liveness-stall.md: diagnosing over-locking vs proposer failure.

16. Phase 4 — Round-Skip / View-Change: Timeouts, Nil Votes, Liveness After GST

16.1 Objectives

  • Implement TimeoutScheduler with round-increasing timeouts (timeoutPropose/Prevote/Precommit).
  • Implement nil-vote paths (no proposal ⇒ prevote nil; no polka ⇒ precommit nil).
  • Implement round advancement: +⅔ precommit-nil or timeoutPrecommit ⇒ StartRound(R+1) with the next proposer.
  • Demonstrate liveness after GST: a failed/Byzantine proposer is skipped within ~2 timeouts; the chain makes progress.

16.2 Detailed Implementation Steps

  • bft-consensus/src/timeout.rs: timeout(step, round) = base[step] + round * Δ (I14; the round-increasing timeout is the DLS partial-synchrony liveness device, P5/B4, that sidesteps FLP, P6); emits Timeout(Hrs) events (the driver arms real timers; the core only reasons about timeout events — DP2/A17).
  • bft-consensus/src/state.rs extensions:
    • StartRound(R), not proposer: emit SetTimeout(Propose, R). On Timeout(Propose,R) with no valid proposal: SignVote(Prevote, nil); step=Prevote.
    • Prevote step: on has_two_thirds_any() (any +⅔ prevotes, mixed) and no maj23: SetTimeout(Prevote,R). On Timeout(Prevote,R): SignVote(Precommit, nil).
    • Precommit step: on has_two_thirds_any() precommits, no maj23: SetTimeout(Precommit,R). On Timeout(Precommit,R) or maj23(nil): StartRound(R+1).
  • Skip-to-round: on receiving +⅓ messages from a higher round R' > R (peers ahead) ⇒ jump to R' (catch-up). On +⅔ precommits for a block at any round ⇒ commit (skip-to-commit, I4).
  • Proposer re-proposal: at StartRound(R+1), if proposer and valid_value set ⇒ re-propose valid_value with pol_round = valid_round (§15 integration, DP5) — this is what lets a locked majority converge.
  • bft-sim: deterministic virtual clock; advance time to fire timeouts in a reproducible order; model GST as "after virtual time T, all messages delivered within Δ".

16.3 Deliverable

examples/proposer_failure.rs: kill the round-0 proposer; cluster round-skips to round 1's proposer and commits within ~2 timeouts. bft-sim liveness checker confirms eventual commit after GST.

16.4 Acceptance Criteria

  • Proposer failure (offline): chain commits the height within ≤ 2 round timeouts after GST.
  • timeout(step, R+1) > timeout(step, R) for all steps (I14) — strictly increasing (DLS liveness requirement).
  • No proposal ⇒ all honest prevote nil ⇒ all precommit nil ⇒ advance to R+1 (clean nil round).
  • Skip-to-commit: a validator lagging behind that receives a +⅔ precommit set for a block at round r commits it directly (catch-up).
  • Liveness checker (sim): every height eventually commits given GST + f < P/3.

16.5 Conformance Fixtures

  • conformance/fixtures/round_skip/proposer_offline_skip.json — proposer silent ⇒ nil round ⇒ R+1 commit.
  • conformance/fixtures/round_skip/timeout_growth.json — timeout values per round (assert monotone).
  • conformance/fixtures/round_skip/skip_to_commit.json — lagging validator receives +⅔ precommits ⇒ direct commit.
  • conformance/fixtures/round_skip/catch_up_higher_round.json — +⅓ from round R+2 ⇒ jump forward.

16.6 Pitfalls

  • Constant (non-increasing) timeouts: violates DLS; under asynchrony before GST, a constant timeout can starve liveness forever. Timeouts MUST grow per round (I14).
  • Clock in the core: arming a real Instant/sleep inside bft-consensus breaks determinism; the core emits SetTimeout actions, the driver arms timers and feeds back Timeout events (A17).
  • Skipping rounds on +⅓ of the wrong message type: only +⅓ at a strictly higher round triggers catch-up; +⅓ at the current round does not.
  • Re-proposal forgetting pol_round: re-proposing valid_value without citing valid_round leaves locked validators unable to justify unlocking ⇒ permanent stall.
  • Double-arming timeouts: arming a new timeout for a step already armed ⇒ duplicate Timeout events ⇒ premature nil votes; arm once per (H,R,step).

16.7 Performance Concerns

  • Timer churn: one timer per step per round; cancel on transition; n ≤ 150 ⇒ trivial.
  • Under sustained asynchrony (rounds climbing), each round re-broadcasts votes ⇒ O(n²) bandwidth per round; the round-increasing timeout naturally throttles this.

16.8 Edge Cases

  • All proposers in a height Byzantine/offline (up to f): skip through f rounds; the first honest proposer commits (guaranteed since honest > ⅔ of proposer slots over rounds).
  • Network partition (minority isolated): minority cannot reach +⅔; rounds climb indefinitely; no commit (safety preserved, liveness lost) until partition heals — correct CP behaviour (DP1).
  • Timeout fires after the event it was waiting for already arrived: ignore stale Timeout(Hrs) if Hrs < current (a late timer).
  • Clock skew between validators: BFT-time median (§17) tolerates skew; consensus timeouts are local (each validator's own timer), so skew doesn't break round-skip.

16.9 Failure Analysis

  • Liveness stall (rounds climbing, no commit): (1) partition / <⅔ online ⇒ expected, wait/heal; (2) over-locking ⇒ check proposer re-proposes valid_value; (3) timeout-not-growing bug ⇒ check I14. Diagnose via consensus.round gauge climbing + consensus.commit_latency stalling.
  • Round explosion: round number climbs to thousands ⇒ a persistent partition or a proposer-selection bug repeatedly selecting an offline validator (shouldn't happen with weighted round-robin); alert at round > 20.

16.10 Operational Notes

  • metrics::histogram!("consensus.rounds_per_height") (ideally 0; >0 ⇒ proposer issues / contention).
  • metrics::counter!("consensus.timeouts{step}"), gauge!("consensus.current_round").
  • tracing::warn! when round > threshold (liveness concern).
  • Runbook docs/runbooks/liveness-stall.md: partition vs over-locking vs proposer-down decision tree.

17. Phase 5 — Commit + Block Finalization + Commit Certificate (Instant Finality)

17.1 Objectives

  • Formalize block finalization: a committed block is absolutely final, never reverted (I8).
  • Build the portable Commit certificate (the +⅔ precommit set) and persist it as last_commit in the next block.
  • Implement BFT time: block timestamp = stake-weighted median of precommit timestamps.
  • Implement block-store persistence; the chain is a hash-linked sequence of finalized blocks.

17.2 Detailed Implementation Steps

  • bft-consensus/src/commit.rs: on maj23 precommits for b (I4), assemble Commit{height,round,block_id, signatures:[CommitSig]}; CommitSig per validator: Commit flag + sig if it precommitted b, Nil/Absent otherwise (encoding per Tendermint spec).
  • bft-consensus/src/bft_time.rs: median_time(precommits, set) = the timestamp t such that validators with timestamp ≤ t hold > P/2 power (stake-weighted median, DP6); used as the next block's time if the proposer's proposed time is out of bounds.
  • Finalization (DP12/I8): on commit, (1) persist block + commit cert to block store; (2) advance to StartRound of H+1; (3) the new block's last_commit = this Commit, last_block_id = this block's id; (4) reset LockState.
  • bft-core/commit.rs: Commit::verify(set) — every Commit-flagged sig valid + summed power > 2P/3 (I4); this is the light-client's core check (§23).
  • Block store: embedded KV (A11) keyed by height; stores (Block, Commit).
  • bft-net/src/rpc.rs: commit(height) RPC returns the Commit certificate (for light clients / explorers).
  • Tests: commit-cert verifies independently; BFT-time median correct under skewed timestamps; finalized block never reverts even if a late higher-round proposal arrives.

17.3 Deliverable

A finalized hash-linked chain in the block store. bft-ctl inspect block <H> shows the block + its commit certificate. Commit::verify passes for every committed block. BFT-time monotonic across heights.

17.4 Acceptance Criteria

  • Every committed block carries a Commit cert that independently verifies (power > 2P/3, all sigs valid).
  • Block time is monotonically non-decreasing across heights (BFT-time guarantee).
  • BFT-time median is within [min, max] of honest validators' timestamps and resistant to ≤f Byzantine timestamps (a Byzantine minority cannot drag the median outside the honest range).
  • A finalized block at height H is never replaced (I8) — a late round-(R+1) proposal for H is rejected (height already committed).
  • last_commit in block H+1 equals the commit cert of block H (chain linkage).

17.5 Conformance Fixtures

  • conformance/fixtures/happy_path/commit_certificate.json — committed block ⇒ verifiable commit cert.
  • conformance/fixtures/happy_path/bft_time_median.json — skewed precommit timestamps ⇒ expected median.
  • conformance/fixtures/malformed/bft_time_byzantine_skew.json — f validators with extreme timestamps ⇒ median still in honest range.
  • conformance/fixtures/malformed/late_proposal_after_commit.json — proposal for an already-committed height ⇒ rejected (I8).

17.6 Pitfalls

  • Median by count not power: BFT-time median must be stake-weighted (the timestamp where cumulative power crosses P/2); a count median lets many small-stake Byzantine validators skew time (DP6).
  • Including only Commit-flagged sigs but verifying against full set power: power threshold is over the whole set's total power, not the included sigs' power; a cert with ⅔ of a subset is invalid.
  • Reverting on a higher-round message: once maj23 precommits commit a block, the height is closed; higher-round proposals for that height are stale (I8). A bug here = finality revert = catastrophic.
  • app_hash lag: the committed app_hash reflects state after applying this block's txs but is written into the next block's header (Tendermint's one-block lag); off-by-one here diverges the chain.
  • Timestamp from last_commit: BFT-time uses the precommit timestamps from the commit that finalized the previous block; sourcing them from the wrong commit breaks monotonicity.

17.7 Performance Concerns

  • Commit-cert verification: O(n) Ed25519 verifies (~50 µs each) ⇒ n=150 ⇒ ~7.5 ms; batch-verify (ed25519-dalek batch API) cuts this ~3–4×; BLS aggregation (§23) makes it one pairing check.
  • Block-store write: one KV put per height; batch fsync acceptable (the WAL already guarantees durability of the decision).
  • BFT-time median: O(n log n) sort by timestamp; negligible at n ≤ 150.

17.8 Edge Cases

  • Exactly +⅔ precommits (power == quorum): commits (quorum is > 2P/3, so == quorum is already strictly over).
  • Commit cert with some Nil/Absent sigs: valid as long as Commit-flagged power > 2P/3.
  • All validators propose the same timestamp: median = that timestamp.
  • Genesis block (height 1): no last_commit; special-cased.

17.9 Failure Analysis

  • Finality revert (I8 breach): a finalized block replaced ⇒ the absolute-finality contract is broken ⇒ light clients and the FFG layer become unsound. Halt; this is a P0 incident; almost always a "closed height" check missing.
  • Commit-cert verification failure on a self-produced block: sign-byte/canonical-encoding drift between sign and verify; compare canonical bytes; consensus-breaking ⇒ protocol-version bump.

17.10 Operational Notes

  • metrics::histogram!("consensus.time_to_finality_ms") (the headline number; target < 2 s single-round).
  • metrics::gauge!("consensus.finalized_height"), counter!("consensus.commit_cert_verify_failures") (must be 0).

18.6 Pitfalls

  • Send what peer already has: without tracking peer HRS state, reactors flood every vote to every peer; at n=150, O(n²) redundant sends kill bandwidth (A13). Track per-peer (H,R,step) and send only votes ≥ peer's state.
  • Unbounded vote channel: a fast sender overruns a slow peer's channel ⇒ OOM crash ⇒ liveness loss (DP8 violation). Bound all channels; apply backpressure or drop-oldest.
  • Sig check skipped for performance: never delay sig check past the I/O boundary; forged votes reaching the core produce fake quorums (DP10). Pay the ~50 µs per vote at the reactor.
  • Block-part re-request storms: if a node misses one part, it may request it from all peers simultaneously; implement a single re-request per missing part with backoff.
  • FD exhaustion at n=150: n−1 peer connections + WAL + block store + mempool file ≈ 155+ FDs; ulimit must be configured; alert on FD usage > 400.

18.7 Performance Concerns

  • Vote gossip at n=150: O(n²) = 22 500 vote messages per round (prevote + precommit × 150 validators); each ~120 B ⇒ ~2.7 MB/round. At 1 s blocks this is ~2.7 MB/s per node; manageable on 1 Gbps NIC.
  • Ed25519 boundary verify: 150 inbound votes × ~70 µs ≈ 10.5 ms per round per validator; the dominant CPU cost. Batch-verify in the reactor (ed25519-dalek batch API, §17.7).
  • Block-part framing: 1 MiB block ÷ 64 KiB = 16 parts; TCP write-per-part; coalesce where possible (Nagle off for latency).
  • Mempool CheckTx: in-proc ABCI call; ~1 µs; bounds throughput only at very high tx rate.

18.8 Edge Cases

  • Peer restarts and reannounces a lower HRS: reset peer state; resend from its new (H,R,step).
  • Evidence delivered after the block that includes it: EvidencePool deduplicates by evidence hash; idempotent.
  • Peer claims step=Precommit but sends prevotes: stash; send when the peer advances.
  • Mempool full (max_mempool_bytes reached): drop-oldest strategy; emit mempool.eviction metric.

18.9 Failure Analysis

  • Gossip reactor deadlock: reactor holds a lock waiting for the consensus core, while the core waits for the reactor's channel ⇒ detect via consensus.step stuck + net.reactor_lag histogram; fix by making the core ↔ reactor boundary channel-based (never shared locks).
  • FD exhaustion crash: all inbound peers accepted without limit ⇒ EMFILE ⇒ node crash ⇒ liveness loss; set max_peers = min(150, (ulimit-n - 50) / 2); monitor net.fd_usage.
  • Evidence flood (griefing): an attacker sends thousands of invalid evidence items ⇒ EvidencePool.add verifies each (expensive); rate-limit inbound evidence per peer to prevent CPU exhaustion.

19.6 Pitfalls

  • app_hash one-block lag: app_hash in block H's header is the state root after applying block H−1's txs, committed during block H−1's Commit call. Using the current block's state root leads every node to disagree with the header (§11 note).
  • Non-deterministic map iteration: if deliver_tx applies state changes via a HashMap iterated in insertion order, different validators may get different orders under the same tx set ⇒ app_hash divergence (DP2). Use BTreeMap or sort keys.
  • Validator update power overflow: EndBlock returns Vec<ValidatorUpdate>; if the update sets a validator's power to 0 (removal), the ValidatorSet::update must remove the validator and recompute total_power (I6).
  • Evidence delivery timing: evidence is delivered in BeginBlock of the height after it was included; the valset used for slash-fraction computation must be the valset at the height when the offense occurred, not the current height (the validator may have partially unbonded).
  • CheckTx does not execute tx: check_tx is admission control (signature check, nonce, basic validity); it MUST NOT mutate app state; only deliver_tx mutates.

19.7 Performance Concerns

  • deliver_tx for kv-app: one BTreeMap::insert + Merkle leaf update; O(log n_keys) per tx. At 1 000 tx/s this is the hot path.
  • Merkle root recomputation: sparse update — only recompute the path from the updated leaf to root; O(log n_keys) not O(n_keys).
  • check_tx in the mempool path: in-proc call latency ~1 µs; dominates only if the mempool is the bottleneck.
  • EndBlock valset diff: full set rehash on every change; cache hash and invalidate only on changes.

19.8 Edge Cases

  • EndBlock returns an empty ValidatorUpdate list (no changes): idempotent; next_validators_hash unchanged.
  • Genesis block (H=1): BeginBlock receives no evidence; app_hash in header comes from the genesis AppState hash.
  • deliver_tx returns an error (invalid tx after passing check_tx due to state change): the tx is included in the block but marked as failed; app_hash still advances (the error is deterministic and agreed on by all nodes).
  • kv-app query for a key that was never set: returns (value=None, proof=non-membership proof).

19.9 Failure Analysis

  • app_hash divergence (I13): the chain-halting event; detected by validators rejecting a block whose app_hash differs from their own committed state. Root causes: (a) non-deterministic state access; (b) off-by-one lag; (c) a tx that reads system time. Forensics: replay the diverged height deterministically; diff the kv state after each tx.
  • EndBlock valset update rejected (I6): power-sum violation; reject the update, halt the node; the app has a bug (cosmos-sdk pattern: never let the app produce an invalid power sum).

20.6 Pitfalls

  • Justification threshold ≥⅔ vs >⅔: identical to the Tendermint quorum issue; the FFG spec (P2) uses >⅔; integer arithmetic must use ⌊2P/3⌋ + 1 (I4).
  • Epoch boundary off by one: if the checkpoint is the last block of epoch E rather than the first block of E+1, finalization epochs desynchronize across validators ⇒ divergent finalized_checkpoint.
  • FFG vote for non-ancestor source: source must be a finalized or justified ancestor of target in the block tree; votes with invalid ancestry must be rejected before counting toward a link.
  • Justification bits width: justification_bits has a fixed width (e.g., 4 bits per Ethereum spec); bits shift left each epoch; accessing out-of-bounds is a panic risk.

20.7 Performance Concerns

  • FFG vote accumulation: O(n) power sum per link; one pass per received vote; n ≤ 150 ⇒ trivial.
  • Checkpoint storage: one entry per epoch; epoch = E blocks ⇒ bounded by num_epochs × sizeof(Checkpoint); prune epochs older than finalized + safety_window.
  • justification_bits update: O(1) bit operation per epoch.

20.8 Edge Cases

  • Less than ⅔ of power votes in an epoch: no justification; justification_bits bit for that epoch = 0; liveness stalls at FFG (but LMD-GHOST keeps producing blocks — the Casper availability property, §4).
  • Validator set changes mid-epoch: the valset for an epoch's FFG votes is the valset at the epoch-boundary block; do not use the current-height valset for historical link power sums.
  • Source checkpoint not yet justified when votes arrive: accept the votes; justification is checked lazily when the source becomes justified (accumulation order-independent).
  • Finalized checkpoint pruning: never prune the finalized_checkpoint itself; only prune ancestors more than safety_epochs before finalized.

20.9 Failure Analysis

  • FFG non-finalization (liveness): < ⅔ power participating in FFG votes; bft-ffg emits ffg.participation_ratio gauge; if < 0.67 ⇒ alert. Runbook: check validator FFG vote broadcast; check peer connectivity.

  • app_hash vs FFG root mismatch: if Checkpoint.root is the block's app_hash root (implementation choice), any app_hash divergence (I13) propagates into FFG ⇒ divergent justified sets ⇒ double-chain-halt.

  • conformance/fixtures/happy_path/ghost_head_worked1.json — linear chain; all latest messages on tip ⇒ head = tip.
  • conformance/fixtures/happy_path/ghost_head_worked2.json — fork at height 5; latest messages split ⅔/⅓ ⇒ head on the ⅔ branch.

  • conformance/fixtures/malformed/balancing_attack.json — Byzantine equivocator alternates ⇒ head deterministic.

21.6 Pitfalls

  • Counting all attestations, not just latest: LMD-GHOST weights each validator by its latest message only; counting all historical attestations inflates subtree weights and makes the algorithm gameable (a validator can "double-vote" weight into a branch by casting multiple attestations — prevented by "latest message" semantics).
  • Subtree weight includes the block itself: weight of block B = power of validators whose latest message is in B's subtree including B; forgetting the self-inclusion underweights leaf blocks.
  • Descending from wrong root: head() must start from the finalized checkpoint (not genesis, not chain tip); starting from genesis on a long chain means exploring already-finalized branches (memory + correctness issue).
  • Pruning removing finalized blocks from the block store: BlockTree::prune_below removes them from the in-memory tree cache, not from the block store (A11). The store retains finalized blocks for sync; the tree retains only the unfinalized frontier.
  • Proto-array staleness: if a block is pruned but still referenced in LatestMessages, the weight update must handle tombstoned / pruned references gracefully (treat their contribution as 0).

21.7 Performance Concerns

  • head() descent: O(depth × branching_factor) per call; in practice depth ≤ 2 × epoch_length blocks before next finalization; branching factor ≤ f < n/3 (Byzantine proposers only); O(1) in practice.
  • Proto-array incremental update: O(1) amortized weight update per update_latest_message; O(path_length) for subtree propagation upward; path_length ≤ epoch_length ≤ 32 slots (illustrative).
  • prune_below: O(pruned_nodes) one-time cost at each finalization; not on the critical path.
  • head() at 100K block tree (M12): must complete in < 10 ms; proto-array achieves O(1) per query after O(n_nodes) build.

21.8 Edge Cases

  • Empty tree (genesis only): head() returns the genesis / finalized checkpoint block.
  • All validators equivocate (Byzantine majority — excluded by f < P/3): head is undefined; guard: if head() would select below finalized, return finalized.
  • Two branches with identical subtree weight (tie): deterministic tie-break by higher block hash (lexicographic); ensures all honest nodes select the same head.
  • A validator's latest message references a block not yet in the tree (out-of-order delivery): stash the message; apply once the block is inserted.

21.9 Failure Analysis

  • Memory unbounded growth (DP15/I8 violation): pruning not called after finalization; block tree grows without bound; detect via forkchoice.tree_size_blocks gauge; alert at > 2×epoch_length blocks; runbook: force prune + restart.
  • Head divergence between honest nodes: a bug in latest-message bookkeeping where one node applies an update the other doesn't (e.g., an out-of-order message) ⇒ different proposers selected ⇒ two competing chains; detected by consensus.proposer_mismatch (I9); force full recompute from the tree + known messages.

  • metrics::gauge!("forkchoice.tree_size_blocks"), gauge!("forkchoice.finalized_epoch"), gauge!("forkchoice.head_height").
  • metrics::histogram!("forkchoice.head_computation_us") — must stay < 10 ms even under adversarial tree.

  • DP4 (accountable safety non-negotiable: every safety violation must be reducible to signed evidence implicating ≥⅓ stake).
  • DP11 (evidence verifiability: evidence is self-contained; verified against the valset at offense height).
  • R4 (prysmaticlabs/prysm beacon-chain/slashing/ — production surround-vote detection; min-source/max-target tracking per validator index).
  • R5 (cosmos/cosmos-sdk x/slashing/, x/staking/ — slash fraction application; reporter reward; tombstone lifecycle).
  • I2 (accountable safety: conflicting finalization ⇒ ≥⅓ stake slashable; the invariant slashing enforces).
  • I3 (one vote per HRS: equivocation = violation; the VoteSet flag from §14 feeds the detector).
  • I10 (evidence verifiability: every accepted evidence independently verifiable against the valset).

22.3 Deliverable

bft-slashing crate fully operational: EquivocationDetector, SurroundDetector, EvidencePool, SlashExecutor. examples/equivocation_slash.rs demonstrates: Byzantine equivocates ⇒ evidence gossiped ⇒ included in block ⇒ validator slashed + tombstoned. bft-sim accountability checker validates I2.

22.4 Acceptance Criteria

  • DuplicateVote detected and verified: two distinct votes at same (H,R,step) from same validator; evidence independently verifies against the valset at height H (I10).
  • SurroundFFG detected: outer FFG vote surrounds an inner FFG vote; both directions detected (new surrounds old, new surrounded by old).
  • Evidence outside the unbonding-period validity window rejected by EvidencePool.add.
  • Slash fraction applied correctly: single equivocation ⇒ slash fraction = 1/32 of stake; power updated in ValidatorSet; total_power conserved (I6).
  • Tombstone is terminal: a tombstoned validator cannot be unbonded, jailed, or re-bonded.
  • bft-sim accountability checker: for a seeded double-finalization scenario, ≥⅓ of stake is provably slashable (I2) in 100% of runs.

  • conformance/fixtures/slashing/surround_ffg.json — outer (e2→e7) surrounds inner (e3→e4) ⇒ SurroundFFG.

22.6 Pitfalls

  • Slashing a validator using the wrong (current) valset: the slash fraction computation must use the validator's power at the offense height, not the current height; a partially unbonded validator would be over-slashed with the current power.
  • Evidence deduplication by hash only: two evidence items for the same offense may serialize differently (field order) ⇒ different hashes ⇒ double-slash; normalize evidence before hashing (canonical form).
  • Griefing with invalid evidence: a malicious reporter submits forged evidence ⇒ EvidencePool.add must verify() before accepting (DP11); the verify path checks both votes' signatures against the valset at the offense height.
  • Surround detector min/max tracking: the SurroundDetector tracks per-validator the minimum source.epoch and maximum target.epoch seen; a new vote with source < min_source OR target > max_target may surround or be surrounded; a more precise check is needed (see R4 for the min-max-target array approach).
  • Tombstone vs jail confusion: jail is temporary (unjail exists); tombstone is permanent (no unjail). Applying a tombstone when only a jail is warranted is a severe irreversible operator loss.

22.7 Performance Concerns

  • EquivocationDetector.check: O(1) per vote if the last vote is cached per (validator_index, height, round, step); the full set is only needed if the cache misses.
  • SurroundDetector: O(1) per FFG vote with the min-source/max-target per-validator array (R4 approach).
  • EvidencePool.add with verify: O(2) Ed25519 verifies + O(1) hash lookup in seen set; dominates; rate-limit inbound evidence per peer (§18.9).
  • SlashExecutor: O(n) ValidatorSet::update + one Merkle rehash; on the critical block-processing path but amortized over many blocks.

22.8 Edge Cases

  • Multiple evidence items for the same validator in one block: apply both; slash fraction may compound (cosmos-sdk: slash fractions are additive up to 100%).
  • Evidence submitted for a validator that was already tombstoned: idempotent; no additional slash (already 100% slashed or tombstoned); do not double-count.
  • Proposer submits evidence against itself: valid; apply self-slash + tombstone; the proposer is removed from the active set starting next block.
  • Evidence for a validator not in the current set (fully unbonded): if within the validity window, slash from the unbonding balance; if outside, reject.

22.9 Failure Analysis

  • Double-slash from non-deduplication (I6 violation): power goes negative or total_power is inconsistent ⇒ quorum math breaks; detect via I6 power-conservation check after every EndBlock; this is a slashing bug, not a validator bug.
  • Invalid evidence accepted (I10 violation): a griefing node submits forged evidence; an honest validator is slashed; this is catastrophic — detect in CI by the evidence-verify fuzz target (fuzz_evidence_verify); always verify before add.
  • Tombstone not applied after slash: validator double-signs again in the next block because tombstone was not set; the second evidence is valid again; detect via slashing.double_slash_detected counter > 0.

22.10 Operational Notes

  • metrics::counter!("slashing.equivocation_detected"), counter!("slashing.surround_detected"), counter!("slashing.evidence_applied").

23. Phase 11 — BLS Aggregation + Light-Client Verification + Weak Subjectivity (bft-light + bft-crypto BLS)

23.1 Objectives

  • Implement BLS12-381 aggregate signing and aggregate_verify in bft-crypto/src/bls.rs (using blst, R7).
  • Implement proof-of-possession (PoP) key registration to defeat the rogue-key (subkey aggregation) attack.
  • Produce compact commit certificates: one 96-byte BLS aggregate sig + bitfield, replacing O(n) Ed25519 sigs.
  • Implement light-client skipping verification with ⅓-overlap trust threshold in bft-light.
  • Implement validator-set-change safety: verify new valset transitions with ≥⅓ trust overlap.
  • Distribute weak-subjectivity checkpoints; bound the unbonding period as the defense window.
  • Full VRF-based committee-sampling validator rotation and a hosted weak-subjectivity-sync relay remain deferred ⇒ PhaseDeferred("FINAL_BLUEPRINT §23") (registered in §38); this phase ships the fixed full-validator-set BLS + light-client path only.

23.2 Detailed Implementation Steps

  • P8 (Boneh, Lynn, Shacham 2001, ASIACRYPT — BLS short signatures from the Weil pairing; foundational for aggregate verify).
  • B7 (Boneh & Shoup, A Graduate Course in Applied Cryptography, Ch. 15 — pairing-based signatures; rogue-key attack; proof-of-possession counter-measure).
  • A06 (BLS12-381 ADR; blst library chosen, R7; PoP mandatory per A30).
  • R7 (supranational/blst — production BLS12-381 aggregate verify implementation; the rogue-key attack example in the README is required reading).
  • R6 (informalsystems/tendermint-rs light-client/ — skipping verification; ⅓-overlap trust threshold; validator-set transition safety checks).
  • IRTF draft-irtf-cfrg-bls-signature — BLS Signatures over BLS12-381; PoP scheme; message-augmentation alternative.
  • DP13 (weak subjectivity over naive trustlessness: new/long-offline nodes sync from a recent trusted checkpoint within the unbonding window).

23.3 Deliverable

bft-crypto BLS path: bls_sign, bls_aggregate, bls_aggregate_verify, bls_pop_verify. bft-light crate: verify_commit_cert, verify_skipping, verify_valset_transition. Compact commit cert demo: n=150, BLS cert = 96 B + bitfield vs ~18 KB Ed25519 cert. Light-client test: skipping 10 heights with ≥⅓ overlap passes; < ⅓ overlap rejected.

23.4 Acceptance Criteria

  • BLS aggregate verify correct for 150-of-150 signers: one blst::AggregatePublicKey + 96-byte sig; verify returns Ok(()) when all 150 signatures present, Err on any missing or forged (M5: < 5 ms for n=150).
  • PoP defeats rogue-key attack: a validator registering a public key pk_evil = pk_honest1^{-1} * pk_evil_base (the classic rogue-key construction) fails PoP verification and is rejected at bonding time.
  • Light-client verify: given a Commit cert (BLS) + valset, verify_commit_cert passes iff aggregate sig is valid AND bitfield power > 2P/3 (I4).
  • Skipping verification: trust a header at height H+1000 from trusted H iff the overlap power between valset@H and valset@H+1000 ≥ P/3 (the ⅓-overlap threshold from R6); reject < ⅓ overlap.
  • BLS cert size: for n=150, cert = 96 bytes (aggregate sig) + ⌈150/8⌉ = 19 bytes (bitfield) = 115 bytes vs 150 × 120 B = 18 000 bytes Ed25519.
  • Weak subjectivity checkpoint: a node that has been offline for longer than unbonding_period is informed it requires a trusted checkpoint; bft-light enforces this gate.

23.5 Conformance Fixtures

  • conformance/fixtures/light_client/bls_aggregate_verify_n150.json — 150 BLS pubkeys + aggregate sig ⇒ verify Ok.
  • conformance/fixtures/light_client/rogue_key_pop_rejection.json — rogue-key pubkey ⇒ PoP verify fails.
  • conformance/fixtures/light_client/skipping_threshold.json — ⅓ overlap: accept; < ⅓: reject.
  • conformance/fixtures/light_client/valset_transition.json — valset change by ≤⅔ in one step ⇒ accept; > ⅔ in one step ⇒ reject (must skip in multiple steps).
  • conformance/fixtures/light_client/weak_subjectivity_gate.json — node offline > unbonding_period ⇒ requires trusted checkpoint.

23.6 Pitfalls

  • Skipping the PoP check: BLS aggregate verify passes even for a rogue-key attack if PoP is not enforced at bonding time (R7 README demonstrates this attack). Every public key submitted in a bond tx MUST have a valid PoP before the validator is added to the set (A30).
  • Bitfield-power mismatch: the bitfield marks which signers contributed; power must be summed over those signers from the current valset; using total power or bitfield-count-as-power causes quorum math errors.
  • Aggregate public key ordering: BLS aggregate pubkey = product of individual pubkeys; the product must be computed in a deterministic order (sorted by validator address); any different order yields a different aggregate pubkey ⇒ verify fails non-deterministically.
  • Message uniqueness for aggregate verify: blst aggregate verify requires each signer signs a distinct message (per the IRTF spec); in the "basic" scheme this means each message has the signer's pubkey prepended. The PoP scheme is cleaner: same message, different PoP scheme variant.
  • Weak-subjectivity window = unbonding period, not a hard-coded constant: the window must be configurable (consensus parameter) and match the deployed unbonding period; hard-coding a number that diverges from the live chain's unbonding breaks the security argument.

23.7 Performance Concerns

  • BLS aggregate verify: one Miller loop + final exponentiation per sig ≈ 1–2 ms for n=150 with blst; target M5 < 5 ms (CPU-dependent). Batch all 150 sigs into one AggregateSignature; never verify individually.
  • PoP verification at bonding: one additional pairing check per bonding event; amortized over the bonding tx; negligible.
  • Light-client skipping: O(|valset|) pubkey lookups; O(1) aggregate verify; dominated by BLS pairing, not the bookkeeping.
  • Ed25519 commit cert (n=150, Phase 5 baseline): 150 × ~70 µs ≈ 10.5 ms for individual verify; batch Ed25519 ≈ 3–4 ms. BLS aggregate ≈ 1–2 ms ≈ 5× improvement.

23.8 Edge Cases

  • Validator with BLS key absent from bitfield (did not sign): their power is NOT included; cert is still valid if remaining bitfield power > 2P/3.
  • Partial validator-set rotation (some old + some new validators): skipping verification ⅓-overlap is computed over the union of old and new sets; overlap = power of validators in both sets.
  • Light-client receives a commit cert for a block at height H with a stale valset (validator set changed at H−50): must verify against the valset valid at height H, fetched from the block header's validators_hash.
  • Weak-subjectivity checkpoint from an untrusted source: light client MUST verify the checkpoint against a trusted genesis or a prior trusted checkpoint; accepting an unverified checkpoint re-introduces the long-range attack.

23.9 Failure Analysis

  • BLS rogue-key attack succeeds (A30 violation): caused by skipping PoP at bonding; a carefully crafted malicious key aggregates to cancel honest validators' keys ⇒ fake commit cert verifies. Detect with the rogue_key_pop_rejection fixture in CI; add PoP verify to the bonding admission path.
  • Light-client trust expired (weak subjectivity failure): node offline > unbonding period; it cannot safely sync from a stored checkpoint (long-range attacks become possible). The bft-light weak-subjectivity gate returns Err(TrustExpired); operator must obtain a checkpoint from a trusted channel (docs, social consensus).

23.10 Operational Notes

  • metrics::histogram!("bls.aggregate_verify_ms") — track against M5 target; alert if > 5 ms (CPU regression or n growing).
  • metrics::counter!("light_client.skipping_rejected") — non-zero ⇒ someone is trying to skip too far; alert.
  • metrics::gauge!("light_client.trusted_height"), gauge!("light_client.trusted_age_seconds") — alert if age > 0.5 × unbonding_period (weak-subjectivity proximity warning).
  • tracing::info!(aggregate_power, cert_bytes) on every BLS commit cert generation; compare cert_bytes to the Ed25519 baseline in logs.
  • Runbook docs/runbooks/weak-subjectivity.md: light-client trust expiry detection; checkpoint distribution; resync procedure.

24. Phase 12 — Deterministic Simulator: Byzantine Fault Injection + Safety/Liveness/Accountability Checkers (bft-sim)

24.1 Objectives

  • Implement a virtual network with deliver/delay/drop/partition primitives over a deterministic event scheduler.
  • Implement Byzantine validator behaviours: equivocation, message withholding, surround vote, conflicting proposals.
  • Implement three correctness checkers: Safety (I1), Liveness (I14+), Accountability (I2).
  • Use xoshiro256** seeded PRNG (A18, DP2); failed-run output includes the seed for byte-identical reproduction.
  • Gate nightly CI on 10 000 randomized histories; any violation ⇒ CI failure with seed.

24.2 Detailed Implementation Steps

  • A18 (PRNG: xoshiro256** seeded; reproducibility over security; DP2 determinism).
  • A22 (testing strategy: bft-sim is the primary correctness gate for all three checkers).
  • DP2 (determinism in the consensus core; the simulator exercises this by replaying identical seeds).
  • I1 (Safety: no two correct validators commit different blocks at the same height).
  • I2 (Accountability: conflicting finalization ⇒ ≥⅓ stake slashable).
  • P5 (DLS liveness — every height eventually commits after GST; the liveness checker operationalises this).
  • All invariants I1–I14 are checked or exercised by the simulator across the three checker categories.

24.3 Deliverable

bft-sim crate: Simulator, VirtualNetwork, ByzantineHook, SafetyChecker, LivenessChecker, AccountabilityChecker. Nightly CI: .github/workflows/sim.yml runs 10 000 histories with random seeds. bft-ctl sim run --seed N --iterations K allows manual replay.

24.4 Acceptance Criteria

  • 10 000 randomized histories (varying n, f, Byzantine modes, partition schedules) pass all three checkers in nightly CI; any failure emits the seed and exits with non-zero status.
  • A seeded double-sign Byzantine mode is detected by the accountability checker in 100% of runs (0 false negatives).
  • Liveness: every height commits within 5 × (GST + timeoutPrecommit(max_round)) virtual-time periods across all 10 000 histories (DLS liveness bound, P5, I14).
  • False-positive rate for the accountability checker = 0: honest-only histories (f=0 Byzantine validators) never trigger an accountability violation across 1 000 runs.
  • The safety checker detects two conflicting commits at the same height in 100% of seeded two-commit scenarios (I1 violation injected directly for regression testing).

24.5 Conformance Fixtures

  • conformance/fixtures/happy_path/sim_honest_n4_100blocks.json — seed → 100-block honest run → all three checkers pass.
  • conformance/fixtures/happy_path/sim_equivocation_detected.json — seeded Byzantine double-sign → accountability checker flags ≥⅓ slashable.
  • conformance/fixtures/happy_path/sim_partition_liveness.json — partition before GST; healed after GST; all heights eventually commit.
  • conformance/fixtures/malformed/sim_false_positive_zero.json — honest-only f=0 run; accountability checker must NOT fire.

24.6 Pitfalls

  • Non-deterministic event scheduling: any HashMap or BTreeMap iteration that affects message delivery order can cause the simulator to be non-deterministic even with a fixed seed; audit every collection type in the scheduler loop.
  • Byzantine validator reading honest node's internal state: the Byzantine hook must only inject observable behaviors (forge a vote, withhold a message, delay delivery); it must not call into honest nodes' internal state (would break the adversarial model boundary).
  • Safety checker checking too late: if the safety checker only runs at the end of a history, it misses a transient fork that was then overwritten; check after every commit event across all validators.
  • Liveness checker timeout too tight: liveness is only guaranteed after GST; the checker must add a GST offset to the expected commit time; checking absolute virtual-time without the GST offset produces false liveness failures.
  • Seeded PRNG isolation: the xoshiro256** instance must be thread-local or explicitly passed; any global/shared PRNG state breaks reproducibility under concurrent test runs.

24.7 Performance Concerns

  • 10 000 histories in nightly CI: each history runs ~100 heights with n=4; overhead is proportional to n × heights × messages_per_height; target < 60 s wall time on a 4-core CI runner.
  • Byzantine mode overhead: equivocation doubles the vote send count; partition/drop modes add filter overhead O(n_peers × messages_in_flight); both are O(1) per message.
  • Checker overhead: safety checker is O(1) per commit (hash lookup in committed-block-per-height map); liveness is O(1) per height close; accountability is O(|evidence|) at the end of each history.

24.8 Edge Cases

  • f = 0 (all honest): all three checkers MUST pass trivially; false positives here are CI-breaking.
  • f = ⌊(n-1)/3⌋ (maximum Byzantine): the strongest Byzantine scenario; safety holds but liveness may take more rounds; checker must tolerate more rounds before declaring liveness failure.
  • Partition where Byzantine minority is isolated (not the honest majority): liveness stalls for the isolated minority; the majority still commits; the checker applies only to the majority partition post-partition-heal.
  • Simulator run with n=1: trivially commits; no Byzantine tolerance; checkers must not divide by zero in the accountability fraction computation.

24.9 Failure Analysis

  • Simulator non-determinism (seed fails to reproduce): a shared global state is corrupted across concurrent test runs; run simulator single-threaded; use per-instance PRNG.
  • Safety checker false negative (misses a real fork): the checker compares committed-block-per-height; if the two conflicting commits happen at different virtual-network partitions not merged in the checker's view ⇒ add a global committed-block registry shared across all simulated validators.
  • Liveness false positive (honest-only history incorrectly flagged): a timing bug where the checker fires before GST is added to the deadline; fix the GST offset in the liveness deadline computation; re-run the false_positive_zero fixture.

24.10 Operational Notes

  • .github/workflows/sim.yml: cargo test --release -p bft-sim -- --test-threads=1 --iterations 10000; set SIM_SEED=<CI_RUN_ID> for reproducibility from CI run logs.
  • metrics not relevant inside the sim; the sim uses its own SimReport struct with per-history statistics.
  • bft-ctl sim run --seed N --iterations K --byzantine equivocation for operator-driven adversarial replay.
  • Seed + violation summary written to sim_failure_<timestamp>.json on any checker violation; include in the bug report.
  • Runbook docs/runbooks/sim-failure-replay.md: given a seed, reproduce the exact Byzantine history; isolate the offending event sequence.

27.10 Deployment Topology

  • n-validator cluster: n validator nodes (4 ≤ n ≤ 150); each one process with single-threaded consensus core + async I/O reactors (A03/A04).
  • Sentry architecture: validators use private inbound connections from "sentry" nodes that handle public peer gossip; protects against DDoS (T11).
  • Rolling upgrade: upgrade at most ⌊n/3⌋ − 1 validators simultaneously to remain below the Byzantine threshold (§28).
  • Canary: upgrade one validator; monitor for 10 blocks; if all metrics nominal, proceed with the rest.
  • Rollback: if a new version causes a liveness stall, restart with the previous binary; WAL is version-agnostic as long as the entry encoding is stable.
  • Key rotation: new Ed25519 keypair; submit bond(new_pubkey, same_power) + begin_unbond(old_pubkey); wait for unbonding delay; confirm new validator active. BLS PoP must be registered for the new key before activation.

28. Compatibility & Versioning

28.1 Wire Protocol Versioning

  • Wire protocol version encoded in the connection handshake as a u16 major.minor. Breaking changes (new fields in Vote, Proposal, FFGVote) increment major; backwards-compatible additions increment minor.
  • Canonical sign bytes are frozen per major version: changing the sign-byte layout is consensus-breaking; requires a coordinated hard-fork with a new chain_id suffix (e.g., "mychain-v2"). Any sign-byte change invalidates all historical commit certificates.
  • Proto-compatible serialization (A09, prost): new optional fields may be added with default-zero values; removed fields become unknown fields (silently ignored by older versions for minor bumps). Adding a required field is a major bump.
  • Version negotiation: on connection, both peers exchange their ProtocolVersion; if major differs, the connection is rejected with Err(IncompatibleVersion).

28.2 Storage / Schema Evolution

  • WAL entry encoding (bft-wal): WALEntry variants are length-prefixed + CRC; new variants added at the end of the enum are backwards-compatible for replay (old binaries skip unknown variant IDs). Never reuse a variant ID. WAL format version stored in the WAL header; mismatch ⇒ refuse to open.
  • Block store (bft-abci + A11): blocks stored as (height → serialized Block + Commit); new block header fields added with defaults; light clients and old readers skip unknown fields. Height-keyed access is append-only; no in-place updates.
  • Validator set on-disk format: serialized ValidatorSet stored per height for light-client lookup; format evolution uses the same proto-compatible approach; old heights are never re-serialized.

28.3 API Stability

  • Application trait (ABCI interface): check_tx / begin_block / deliver_tx / end_block / commit signatures are frozen for the 1.x series. Adding a new lifecycle method (e.g., prepare_proposal) is a trait extension (a separate trait) to preserve object safety. Breaking the Application trait is a SemVer 2.0.0 bump.
  • bft-core types (Vote, Block, Commit, ValidatorSet): public fields that participate in sign bytes or consensus hashes are frozen; other fields may be added in minor versions with #[non_exhaustive] on structs.
  • RPC API (bft-net/src/rpc.rs): broadcast_tx / query / validators / commit-cert endpoints are stable in 1.x; new endpoints are additive; removing or changing an endpoint's response shape is a major bump.
  • bft-light verification API: verify_commit_cert, verify_skipping, verify_valset_transition — stable in 1.x; inputs and outputs version-tagged.

28.4 Migration Strategy for Validator Set Changes

  • Hard-fork validator set replacement: new genesis with updated validator set; requires social consensus + all nodes upgrading to a new binary that recognizes the new chain_id; the old chain continues in parallel.
  • Soft validator set rotation (gradual, within unbonding rules): EndBlock updates add/remove up to ⌊n/3⌋ validators per epoch to stay below the Byzantine threshold change limit; verified by bft-validators::update which rejects changes > ⌊P/3⌋ power delta in one block.
  • Slashed validator replacement: a tombstoned validator is removed from the active set by the next EndBlock after slash execution; a replacement bonding tx can be included in the same block.

28.5 Deprecation Policy

  • A feature is deprecated with a #[deprecated(since = "1.x.0", note = "...")] attribute and a CHANGELOG.md entry.
  • Deprecated features are removed after two minor releases (e.g., deprecated in 1.3.0, removed in 1.5.0).
  • Consensus-critical types (Vote, Block, Commit wire format) are never deprecated within a major version; removal requires a major bump + migration guide.

28.6 SemVer Policy for the Crates

  • bft-core, bft-crypto, bft-validators: 1.x.y — the most stable; breaking changes increment major only.
  • bft-consensus, bft-ffg, bft-forkchoice, bft-slashing, bft-wal, bft-abci, bft-net, bft-light: 1.x.y — stable public API; internal implementation details not part of the SemVer guarantee.
  • bft-sim, bft-ctl: 0.x.y — tooling; CLI flags and simulator behavior may change in minor versions.
  • Workspace Cargo.lock checked in; all crates pinned together as a release train.

28.7 Rolling-Upgrade Guarantees

  • Validators may upgrade one at a time without a chain halt, provided < ⌊(n−1)/3⌋ validators are simultaneously running a different major wire-protocol version.
  • The in-flight guarantee: a validator upgrading from v1 to v2 (same major) can join the active set without halting the chain; its votes are accepted by v1 nodes if the sign-byte format is stable.
  • For major version upgrades (wire-protocol break): coordinate a flag-height (a block height at which all nodes switch simultaneously); validators must be upgraded before the flag height; nodes at the flag height reject peers running the old major version.
  • Maximum simultaneous upgrading validators: ⌊(n−1)/3⌋ − 1; upgrading ≥ ⌊n/3⌋ validators simultaneously may drop honest power below ⅔ ⇒ liveness stall.

29.6 Chaos Tests

  • Kill proposer: kill the current-round proposer mid-proposal; assert chain commits within 3 rounds.
  • Partition: isolate ⌊n/3⌋ − 1 validators for T seconds (T < GST equivalent); assert: (a) majority partition continues; (b) minority cannot commit; (c) after healing, minority catches up without double-sign.

31. Performance Engineering

31.1 Benchmarking Methodology

  • Micro-benchmarks (criterion via benchmarks/): latency + throughput per operation; 100 warm-up iterations; 200 measurement samples; statistical analysis (mean, std dev, p99); baselines committed; 10% regression threshold gated in bench.yml.
  • End-to-end benchmark: benchmarks/ttf.rs runs an in-process n-validator cluster with the real consensus + WAL + app pipeline; measures wall time from broadcast_tx to the block containing that tx being committed and verified.
  • Profiling: cargo flamegraph (via cargo-flamegraph) generates flame graphs per benchmark; perf record + perf report on Linux for cycle-level profiling of hot paths (Ed25519 verify, WAL fsync, BLS pairing).
  • Allocation analysis: heaptrack or dhat for per-operation heap profiling; target: zero heap allocation in the consensus state machine hot path per vote add.
  • Lock contention / syscall analysis: consensus core is single-threaded (A04); no locks in the core; reactor ↔ core channels are bounded tokio::sync::mpsc. strace -c counts fsync per block; target: one fsync per self-signed vote (DP3); only WAL and block-store issue fsync.
  • Tail-latency analysis: all histograms expose p50/p95/p99/p999 in Prometheus; tail latency (p999 TTF) is the operator SLO metric for validator infrastructure.
  • Batching / IO amplification: Ed25519 verify_batch (16–64 votes) for ~3–4× throughput. WAL fsync count per height = 2 minimum (prevote + precommit); reduce via write coalescing (single buffer + one fsync).

31.3 Known Bottlenecks and Mitigations

  1. Ed25519 verify throughput (dominant at n > 20): boundary verify for all inbound votes; use ed25519-dalek verify_batch in the reactor with batch size 32; measured improvement 3–4×. Beyond n=150, BLS aggregation (Phase 11) makes this O(1) for commit cert verify.
  2. WAL fsync per vote: each self-signed vote requires one fsync for DP3; on spinning disk this is ~10 ms (unacceptable); NVMe target 2 ms p99; coalesce prevote + precommit into a single write+fsync when possible (2 writes/height in the happy path = 2 fsync minimum).
  3. O(n²) vote gossip at n > 50: each validator sends up to (n−1) × 2 votes per round; bandwidth = n² × 240 B/round; at n=150, 1 s blocks ≈ 5.4 MB/s per node ≈ feasible on 100 Mbps NIC. BLS aggregation collapses the per-round broadcast to 1 aggregate msg + bitfield but does not change the gossip pattern before aggregation.
  4. Block-part gossip bandwidth: a 1 MiB block split into 16 parts × (n−1) peers = 15 MiB/round at n=16; dominated by NIC bandwidth at large n; default block size cap 1 MiB (§4).
  5. Tokio reactor overhead: the async reactor adds ~1–2 µs per message dispatch; at 1 000 tx/s this is < 2 ms total overhead; not the bottleneck.

32.2 Named Bottlenecks (Priority Order)

  1. O(n²) vote gossip (dominant at n > 50): at n=150 each validator sends ~300 vote messages per round (prevote + precommit × 150); total cluster traffic = 150 × 300 × 120 B = 5.4 MB/round. This is the fundamental BFT messaging complexity bottleneck. Mitigation: committee sampling (beyond n=150) or BLS aggregation to reduce the gossip payload, though not the message count.
  2. Ed25519 sig verify throughput: at n=150, each validator must verify up to 300 inbound votes per round × ~70 µs = 21 ms per round. With batch verify: ~5 ms per batch of 150. Target: verify all inbound votes in < half the round time. Mitigation: verify_batch (Phase 5 §17); BLS single pairing check (Phase 11 §23).
  3. WAL fsync per vote: 2 fsync per height (prevote + precommit) on the critical path; on NVMe ~1 ms each ⇒ 2 ms baseline WAL overhead per height. On spinning disk this is ~20 ms, making sub-1-second block times impossible. Mitigation: NVMe mandatory for production validators; write coalescing (one fsync per height if both votes fit in one buffer).
  4. Block-part gossip bandwidth: 1 MiB block → 16 parts → each node sends 16 × 150 parts (at n=150) in the worst case = 2 400 parts × 64 KiB = 153 MB/round in the naive case. Mitigation: per-peer part tracking (send only parts the peer lacks); erasure coding to allow reassembly from any 8-of-16 parts.

32.3 Horizontal / Vertical Scaling Options

  • Vertical scaling (bigger single validator machine): linear improvement in Ed25519 batch throughput (more CPU cores for the reactor); WAL fsync latency improves with better NVMe; memory ceiling raised for block tree.
  • Horizontal scaling (more validators): directly worsens O(n²) messaging; the BFT ceiling at n ≈ 150 is a hard design constraint, not a tuning parameter.
  • Committee sampling (Phase 12 deferred §38): randomly select a committee of k < n validators per height/slot; consensus messages = O(k²) not O(n²); n can grow without bound at the cost of per-slot safety guarantees degrading to probabilistic.
  • Geographic sharding: shard the validator set into geographic sub-committees; each shard finalizes a range of heights; cross-shard finality requires an inter-shard protocol (HotStuff pipelining; out of scope).

32.4 Practical Ceiling: n ≈ 150 for All-to-All BFT

  1. Bandwidth: O(n²) messages × 120 B × 2 sides ≈ 5 MB/round per validator at n=150 on a 1 s block; approaches 100 Mbps at n=200.
  2. CPU: Ed25519 batch verify for 300 votes/round × 70 µs ≈ 21 ms without batching; with batching ~5 ms; acceptable up to n≈200 before verify time dominates the 1 s round.
  3. FD budget: n−1 TCP connections = 149 FDs at n=150; approaching the 512 FD budget.

33. Mental Models & First Principles

MM1 — Consensus under partial synchrony: "Safety is asynchronous; liveness requires GST." Safety (no two conflicting commits) must hold even in fully asynchronous networks; liveness is guaranteed only after the unknown GST when the network becomes synchronous. A liveness stall is expected under asynchrony — not a bug; a safety violation indicates a code bug or f ≥ P/3 Byzantine stake. Bug class: treating slow delivery as a protocol error. Resolving §: §16 (timeouts, I14), §33 (MM models), P5, P6. MM2 — Byzantine quorum intersection: "Two ⅔-quorums overlap in > ⅓ of power; this is the f < n/3 boundary." Two quorums of >⅔P must overlap in > ⅓P power; since f < P/3, that overlap is > f, so > 0 honest validators are in both — any two honest decisions share at least one honest witness. Bug class: implementing ≥ 2P/3 instead of > 2P/3 in CommitDetector ⇒ two disjoint quorums possible ⇒ silent safety violation. Resolving §: §12 (I4), §14 (CommitDetector), §7 (I1/I4), P4/P11. MM3 — Locking as a one-way ratchet: "A lock ratchets forward only via PoLC; it never moves backward." locked_round is monotonically increasing (or −1); it advances only when a PoLC (+⅔ prevotes) arrives at a strictly higher round (I5). A validator stays locked until a higher-round PoLC for a different block arrives. Bug class: permitting lock decrease lets Byzantine proposers force locked validators to prevote a different block ⇒ fork risk. Resolving §: §15 (LockState, DP5, I5), §8.5. MM4 — Accountable safety theorem: "Any two conflicting finalizations imply ≥⅓ of stake violated a slashing condition." Two conflicting finalizations require two >⅔ quorums whose intersection (> P/3) must contain validators that double-voted or cast surround votes — all provably slashable. Bug class: a protocol where safety violations leave no slashable evidence makes economic finality illusory. Resolving §: §22 (slashing, I2), §24 (accountability checker), P2/P10, DP4. MM5 — WAL as the double-sign fence: "A validator's signed commitment is durable before it propagates; crash-restart replays the fence before any new signing." The WAL fsyncs each signed vote before broadcast; on restart it replays to reconstruct the last (H,R,step) and the can_sign guard rejects re-signing at or below that point. Bug class: crash-restart without WAL replay ⇒ validator signs a different block at the same (H,R) ⇒ DuplicateVote ⇒ self-slash (the most common real-world slashing incident). Resolving §: §12 (WAL, DP3, I7), §22, runbook double-sign-incident.md. MM6 — Stake-weight vs node-count: "A Sybil with 100 zero-power keys contributes nothing to any quorum; only power matters." All consensus thresholds — quorum, fork-choice weight, proposer selection — are computed over voting power, not validator count. Zero-power nodes buy no quorum influence and only consume FDs and bandwidth. Bug class: using node count for quorum ⇒ a Sybil with 100 low-stake keys can reach a ⅔ count majority without ⅔ power ⇒ fake commit. Resolving §: §13 (DP6, I6), §12 (I4), §25 (T7). MM7 — LMD-GHOST's latest-message bookkeeping: "The subtree weight of a block is the stake of validators whose LATEST attestation is in its subtree; older attestations are voided." Each validator's power is counted at most once — in the subtree of its most recent attestation; attesting to a later block moves the weight to the new subtree. The balancing attack (T4) fails because equivocating weight can only be in one subtree. Bug class: counting all historical attestations ⇒ subtree weights inflate ⇒ fork-choice diverges. Resolving §: §21 (§21.6 pitfall), §8.9. MM8 — Epoch finality lag: "Casper FFG finalizes two epochs behind the present; blocks between justified and finalized can be orphaned." FFG finalizes epoch E only when epochs E and E+1 are both justified; the LMD-GHOST head is always ≥ 2 epochs ahead of the finalized frontier. Blocks between finalized and justified are not yet final and can be orphaned (but never past the finalized frontier). Bug class: treating a justified checkpoint as final ⇒ a client accepts a payment that later gets orphaned. Resolving §: §20 (finalization rule), §8.6, P2, P3.

CometBFT (Go)

The direct ancestor of this design, implementing identical Tendermint BFT with the same locking/PoLC/round-skip machinery. Key differences: written in Go (GC pauses), uses a reactive gossip model with per-peer HRS round-step state, ships with Cosmos SDK integration. This Rust design uses CometBFT as the conformance reference (R1) but avoids Go GC nondeterminism in the deterministic replay simulator.

Ethereum Gasper

Gasper (P3) merges LMD-GHOST fork-choice with Casper FFG finality on the Ethereum beacon chain. This design implements a faithful subset — the FFG + LMD-GHOST variant — with a simplified validator model (no committees, no sharding). The Ethereum production version scales via committee sampling across 500 000+ validators; this design targets n ≤ 150 and defers committee sampling (§38).

HotStuff / LibraBFT

HotStuff (P7) solves Tendermint's O(n²) message complexity by having the leader collect threshold signatures and broadcast a single quorum certificate, reducing view-change to O(n). This design stays with Tendermint's all-to-all voting because: (a) no single per-round failure point; (b) n ≤ 150 makes O(n²) tractable; (c) the locking/PoLC model is simpler to analyze and implement correctly.

Algorand BA*

Algorand uses VRFs for sortition-based committee selection and two-phase soft-vote/certify-vote Byzantine agreement, achieving O(n log n) message complexity for open participation. It targets liveness under synchrony with honest supermajority rather than the partial-synchrony DLS safety model, giving per-block finality in one round under synchrony — a different safety/liveness tradeoff from Tendermint's CP model.

GRANDPA (Polkadot)

GRANDPA is Polkadot's finality gadget that finalizes prefixes of chains rather than individual blocks: validators vote on the highest justifiable block and the protocol finds the common ⅔-power prefix. Running asynchronously over BABE (as Casper FFG runs over LMD-GHOST), a single GRANDPA round can finalize multiple blocks, but the voting-on-chains model is harder to reason about than FFG's voting-on-checkpoints and requires richer fork-choice integration.

35. Back-of-Envelope Capacity Model

1. Vote message volume per block (prevote + precommit phases):

Messages/block = n × 2 (prevote + precommit) × (n−1) (gossip to all peers)
              = 150 × 2 × 149 = 44 700 messages/block
Each message = 120 B (§4) ⇒ 44 700 × 120 B = 5.36 MB/block/validator
At 1 s blocks: 5.36 MB/s per validator egress; 10.7 MB/s (+ ingress) per validator.
Cluster total: 150 × 5.36 MB/s ≈ 804 MB/s (sum of all validator egress).

2. All-to-all message count per height:

Proposals: 1 (from proposer)
Prevotes:  n × (n−1) = 150 × 149 = 22 350 (total gossip events in cluster)
Precommits: n × (n−1) = 22 350
Cluster total messages per height (min, 1 round): 1 + 22 350 + 22 350 ≈ 44 701.

3. Commit certificate size (Ed25519 vs BLS):

Ed25519 commit cert:
  CommitSig per validator: 20 B addr + 8 B timestamp + 64 B sig + 1 B flag = 93 B
  Quorum = ⌈⅔ × 150⌉ = 100 validators minimum (minimum Commit-flagged)
  Total: 100 × 93 B + 16 B header = ~9 316 B ≈ 9.1 KB (quorum only)
  Full cert (all 150 slots incl. Absent/Nil): 150 × 93 B ≈ 14 KB

BLS aggregate commit cert:
  Aggregate sig: 96 B (G2 point, BLS12-381)
  Bitfield:      ⌈150/8⌉ = 19 B
  Header:        ~16 B
  Total:         ≈ 131 B — a 107× reduction vs the full Ed25519 cert.

4. Block tree memory (Casper FFG variant):

Non-finalized frontier: at most 2 epochs × E blocks/epoch.
Example: E = 32 slots, each slot 1 block ⇒ 64 non-finalized blocks max.
BlockNode struct: ~120 B (hash + parent + children + weight fields).
64 × 120 B ≈ 7.7 KB for the frontier nodes.
Full tree (including justified but not finalized): ≤ 3 × E ≈ 96 blocks ≈ 11.5 KB.
Negligible; the bounded concern is n → ∞ without pruning (DP15).

5. WAL write amplification per height:

Entries per height (happy path, 1 round):
  1 × Step{H,R,Prevote}   + 1 × SignedVote(prevote)   = 2 writes
  1 × Step{H,R,Precommit} + 1 × SignedVote(precommit) = 2 writes
  1 × Commit(cert)                                     = 1 write
  Total: 5 WAL entries per height; 2 fsync (coalesced write+fsync per step).
Entry size: ~200 B avg ⇒ 5 × 200 B = 1 KB/height WAL write.
At 1 block/s: 1 KB/s WAL write rate; trivial for any modern NVMe.

Peer connections: n−1 = 149 (TCP sockets)
RPC server socket: 1 + up to 10 concurrent connections = 11
WAL file:          1

Misc (log, metrics, config): ~5

Peak (during block sync with additional peer connections): 169 + 50 = 219.
Hard limit `max_peers = 149` enforces this stays below 512 (§4, T12).

Per round VoteSet (prevotes + precommits):
  votes: Vec<Option<Vote>> = n = 150 slots × ~200 B/Vote = 30 KB per VoteSet.
  Two VoteSets (prevote + precommit) per round: 60 KB.
  Active rounds in memory: typically 1–3 (current + last 2 for catch-up).
  HeightVoteSet total: 3 × 60 KB = 180 KB per height.
  With evidence + proposals: ≈ 250 KB per height.
Freed on height commit; bounded to 2 heights in memory (current + prior).

8. Tx throughput upper bound:

Block size: 1 MiB = 1 048 576 B.
kv-app tx size: set(key=32B, value=64B) + overhead = ~120 B/tx.
Max txs/block: 1 048 576 / 120 ≈ 8 738 txs/block.
At 1 block/s: theoretical max = 8 738 tx/s.
Actual measured target: 1 000 tx/s (M3); limited by DeliverTx + Merkle update.
Bottleneck: Merkle tree update O(log n_keys) per tx; not block transport.

9. Ed25519 verify throughput bottleneck:

Ed25519 verify latency: ~70 µs/sig (single-threaded, no batch).
Inbound votes per height: n = 150 prevotes + 150 precommits = 300 verifies.
Sequential: 300 × 70 µs = 21 ms — longer than 10% of a 1 s round.
With batch verify (groups of 32): 300 / 32 ≈ 10 batches × ~700 µs/batch = 7 ms.
With full batch (all 150): ~2 ms — achieved by collecting the batch across a tick.
CPU budget: 1 000 ms round − 2 ms WAL − 2 ms sig verify ≈ 996 ms for app + network.

10. Unbonding window as long-range attack defense:

Long-range attack: attacker buys N unbonded validators' keys and rebuilds a competing chain
from past height H where those validators were bonded.
Defense: any new node (or one offline > U) must obtain a trusted checkpoint from within the
last U days (weak subjectivity); attacker cannot re-use keys from > U days ago.
Quantitative: U = 21 days = 1 814 400 s; at 1 s/block = 1 814 400 blocks between checkpoints.
A syncing node checks: |trusted_checkpoint_age| < U.  See DP13, §23.

36. Hard Questions (Self-Examination)

Q1 — WAL crash/restart safety: A validator crashes mid-broadcast after signing a prevote but before all peers receive it. On restart, should it resend the same prevote, a different prevote, or no prevote? How does the WAL ensure it never double-signs? Answer requires synthesis of: §12 (WAL can_sign guard, DP3, I7), §15 (lock state on restart), §11 (ConsensusWAL schema). On restart WAL is replayed; can_sign returns false for any (H,R,Prevote) with a different block_id; the node re-broadcasts the same vote. If no WAL entry exists (crash before WAL write), the node signs a new prevote for the same block (valid_value and locked_value also replayed). A different block_id is impossible: the WAL records the step before broadcast, so the vote either matches the WAL or never left the node.

Q2 — Conflicting-proposal quorum-intersection argument: A Byzantine proposer sends Block X to 2 validators and Block Y to 1 validator in an n=4, f=1 system. Why can neither X nor Y commit in round 0? Answer requires synthesis of: §8.5 (HRS state machine), §12 (quorum math I4, MM2), §15 (locking). Quorum Q = ⌊2×4/3⌋ + 1 = 3. Honest validators for X: V0, V1 (power = 2); for Y: V2 (power = 1); Byzantine V3 equivocates (not counted as honest). Neither X nor Y reaches Q=3 honest prevotes. No polka ⇒ all honest precommit nil ⇒ round 0 ends without a commit. Safety (I1) is preserved because the Byzantine validator's equivocation cannot complete a quorum alone.

Q3 — Re-proposal with pol_round: The proposer at height H, round 1 re-proposes valid_value = B with pol_round = 0, citing the round-0 polka. V1 is locked on block B' ≠ B at locked_round = 0. Should V1 prevote B or nil? Answer requires synthesis of: §15 (unlock rule: unlock iff PoLC for b' ≠ locked_value at round > locked_round), §8.5 (state machine, Propose step). pol_round = 0 equals V1.locked_round = 0; the unlock rule requires round > locked_round; 0 > 0 is false. V1 stays locked on B' and prevotes nil. A pol_round = 1 (higher round) would allow unlocking.

Q4 — BFT-time median Byzantine timestamp resistance: With n=4, f=1, one Byzantine validator submits a timestamp 1 year in the future in its precommit. How does BFT-time median handle this? Answer requires synthesis of: §17 (BFT-time median, stake-weighted), §8 (domain model, CommitSig.timestamp), §25 (T13 time-manipulation attack). The BFT-time is the stake-weighted median: the timestamp t where cumulative power of validators with timestamp ≤ t exceeds P/2. With n=4 equal power, P/2 = 2 units. The Byzantine validator's extreme timestamp is at the tail; the median is determined by honest validators (power = 3 > P/2). The Byzantine outlier cannot shift the median outside the honest range. In the §4 example: honest timestamps T, T+100ms, T+200ms, Byzantine = T+365days; median = ~T+100ms.

Q5 — High rounds_per_height in production: An operator observes consensus.rounds_per_height averaging 3 in production for 24 hours. What are the root causes and how do you diagnose each? Answer requires synthesis of: §16 (round-skip causes: proposer failure, partition, over-locking), §27 (operational readiness, runbooks), §26 (failure modes: liveness stall, proposer censorship). Root causes: (a) one or more proposers offline — check validators.jailed and per-validator vote inclusion; (b) network partition during proposal — check net.connected_peers drops; (c) over-locking (§15.9) — check consensus.locked_round histogram; (d) clock skew causing timestamp rejections — check consensus.bft_time_delta_ms. Runbook: docs/runbooks/liveness-stall.md has the decision tree. A sustained 3-round average under honest conditions suggests a proposer with high latency; consider adjusting timeoutPropose or jailing the slow proposer.

Q6 — Catching up on a missed height: A validator was offline for height H and comes back online at height H+5. It receives a +⅔ precommit set (a commit cert) for block B at height H from a peer. How does it process this? Answer requires synthesis of: §16 (skip-to-commit: +⅔ precommits for b at any round ⇒ commit), §17 (Commit::verify), §19 (ABCI lifecycle for the missed height). The validator calls Commit::verify (power > 2P/3 + all sigs valid), applies the block through bft-abci (BeginBlock/DeliverTx/EndBlock/Commit) to advance app state and get app_hash, then replays H+1 through H+4. The WAL for H has no entries; can_sign returns true but the cert tells the node H is committed — it moves to H+6.

Q7 — valid_value vs locked_value: A validator has locked_value = B, locked_round = 2 and valid_value = B', valid_round = 3. The proposer at round 4 is this validator. What does it propose and with what pol_round? Answer requires synthesis of: §15 (valid_value tracks latest polka; locked_value gates prevoting), §16 (re-proposal: propose valid_value ?? new_block with pol_round = valid_round). The proposer re-proposes valid_value = B' with pol_round = 3 — sharing the polka with the network, not breaking its own lock. Since valid_round = 3 > locked_round = 2, the proposer's own subsequent prevote (justified by pol_round=3) unlocks it from B.

Q8 — Two validators finalizing conflicting FFG checkpoints: Validators V1 and V2 both observe FFG finalization: V1 sees checkpoint C1 finalized, V2 sees checkpoint C2 finalized (C1 ≠ C2 at the same epoch). What does the accountable safety theorem guarantee? Answer requires synthesis of: §20 (FFG finalization rules), §22 (SurroundFFG slashing), §33 (MM4), P2 (accountable-safety proof). Two conflicting finalizations require two +⅔ justification chains; by quorum intersection (MM2), their ⅔ sets overlap in > P/3 power. Each overlapping validator either double-voted (same target epoch ⇒ DuplicateFFG) or cast surround votes — both slashable. The accountable safety theorem (I2, P2 §3) guarantees ≥⅓P slashable stake.

Q9 — Equivocating validator's effect on LMD-GHOST subtree weight: Byzantine validator V5 attests to block A at slot 10 (weight goes to A's subtree), then attests to block B at slot 11 in A's competing chain (weight moves to B's subtree). How does LatestMessageStore handle this? Answer requires synthesis of: §21 (LatestMessages: latest attestation per validator; older attestations voided), §21.6 pitfall. update_latest_message(V5, B, epoch=11) replaces (A, epoch=10) (epoch 11 > 10). V5's power moves to B's subtree; VoteSet flags the equivocation (I3, T1) and emits DuplicateVote evidence. Fork-choice uses only the latest message — V5 cannot simultaneously contribute to both branches.

Q10 — Long-range attack with 21-day unbonding: An attacker acquires private keys of 100 validators that unbonded 30 days ago (power was 40% of the chain at that time). The current unbonding period is 21 days. Can the attacker create a valid competing chain from 30 days ago? Answer requires synthesis of: §23 (weak subjectivity, DP13), §35 (capacity model), §25 (T2). Yes — technically the attacker can rebuild from 30 days ago using old keys (≥⅓ power at that height). However, any node online within the last 21 days holds the canonical chain and rejects the fork. A new or long-offline node must obtain a trusted checkpoint within the 21-day window (DP13); bft-light enforces Err(TrustExpired) for nodes offline > unbonding_period.

Q11 — BLS proof-of-possession and rogue-key attack: What is the rogue-key attack on BLS aggregate signatures, and how does PoP prevent it? Answer requires synthesis of: §23 (BLS PoP, A30, A06, R7), §25 (T10), B7 (Ch. 15 rogue-key attack). The attack: V_evil registers pk_evil = pk_honest^{-1} × pk_own; aggregate pubkey becomes pk_own — V_evil forges a cert that appears to include V_honest's sig. PoP counter-measure: at bonding time, V_evil must sign pk_evil under sk_evil; this requires computing sk_evil = log(pk_evil) (intractable discrete log). PoP check gates all validator registrations (A30), blocking rogue-key construction.

Q12 — Casper FFG conflicting forks and accountable safety: Under what exact voting configuration do two conflicting FFG finalizations become possible, and which validators are slashable? Answer requires synthesis of: §20 (FFG state machine, §8.6), §22 (SurroundFFG slashing condition), P2 (Casper FFG §3–4 accountable safety proof). Two conflicting finalizations require: (1) a ⅔+ justification chain leading to checkpoint C1, and (2) a ⅔+ justification chain leading to conflicting checkpoint C2 at the same epoch. The two ⅔ sets for C1 and C2's justification links overlap in > P/3 validators (MM2). Each overlapping validator either (a) voted for both C1 and C2 as the target of a link ⇒ DuplicateFFG slashing condition, or (b) voted (s1→t1) and (s2→t2) where one surrounds the other ⇒ SurroundFFG. The P2 proof shows at least one of these conditions must hold for every validator in the overlap, making ≥⅓P slashable.

Q13 — O(n²) message complexity vs HotStuff: This design uses O(n²) vote gossip. HotStuff (P7) achieves O(n) per view-change. When does the O(n²) cost become the deciding factor against this design, and what would need to change? Answer requires synthesis of: §32 (scalability analysis), §34 (comparative table: message complexity), P7 (HotStuff). The O(n²) cost becomes deciding at approximately n > 150 (§32.4) where bandwidth exceeds 100 Mbps per validator. The HotStuff alternative requires: (a) a threshold-signature scheme (BLS t-of-n) for the quorum certificate; (b) a leader-centric protocol where the leader collects all n votes and broadcasts one QC; (c) view-change complexity O(n) because only the leader broadcasts. The tradeoffs: single point of failure per round (the leader); added latency for the leader to collect all votes; implementation complexity of threshold BLS. For n ≤ 150, O(n²) is tractable and the simpler locking/PoLC model is preferred (design decision rationale in §1, A04).

Q14 — WAL entry with incomplete fsync: A WAL entry for a prevote is written to the OS page cache but fsync has not returned when the process crashes. On restart, is this entry recoverable? Does it cause a double-sign risk? Answer requires synthesis of: §12 (WAL, DP3, I7, DP7), §26 (WAL corruption failure mode). If fsync did not complete, the entry may or may not be on disk; the WAL CRC check detects a partially written entry (CRC mismatch ⇒ Err(Corruption)); truncate at the last valid CRC and restart. The prevote is not replayed; the node may re-sign the same prevote (same block at same HRS — no double-sign risk). append_and_fsync blocks until fsync returns before broadcast; a crash before fsync completes means no peer has seen the vote, so no evidence can be formed.

Q15 — Single-threaded deterministic core vs async reactors: The consensus core is single-threaded (A04). The gossip reactors are async (A03/tokio). How do they communicate, and does the async runtime affect the determinism of consensus decisions? Answer requires synthesis of: §3 (architectural overview), A03, A04, DP2. Communication: reactors push events (inbound votes, proposals, timeouts) into a bounded tokio::sync::mpsc channel; the consensus core reads sequentially via handle_event. The async runtime controls when messages arrive (affects liveness/timing) but not the core's decision logic (safety). handle_event is a pure function of (state, event) independent of wall time (DP2, A17). The simulator (§24) replaces the reactor with a virtual network + deterministic scheduler, proving the core decisions are independent of async scheduling.

Q16 — Proposer priority algorithm centering: The accumulating-priority algorithm adds power to each validator's priority each round and subtracts P from the proposer's priority. Without centering, what goes wrong? Answer requires synthesis of: §13 (proposer algorithm, §13.6 pitfalls), §8.8 (accumulating-priority spec). Without centering, priorities grow as O(K × max_power) per round. Two risks: (a) i64 overflow after ~2^63/max_power rounds (e.g., max_power = 10^12 ⇒ overflow after ~104 days at 1 round/s); (b) a validator with the highest accumulated priority may be selected too many consecutive times, breaking fairness. Centering (subtracting the mean from all after each increment) bounds priorities to [−P, P] and restores correct rotation.

Q17 — app_hash one-block lag: Block H's header contains app_hash. Which block's transactions contributed to this app_hash? What would go wrong if the consensus engine used the current block's app_hash instead? Answer requires synthesis of: §17 (app_hash lag pitfall §17.6), §19 (ABCI Commit, §19.6), §11 (Block schema). Block H's app_hash is the state root after applying block H−1's transactions (previous Commit call). This is the "one-block lag." If the current block's app_hash were used: the proposer would need to execute all transactions before creating the proposal; validators would re-execute before prevoting — serializing execution + proposal creation, adding one full execution round to block latency and eliminating pipelined execution. The one-block lag lets validators prevote based only on the transaction list.

Q18 — Network partition for 48 hours longer than unbonding period: The chain has a 21-day unbonding period. A major network partition lasts 22 days (longer than the unbonding period). What happens to the minority partition and the weak subjectivity guarantee? Answer requires synthesis of: §23 (weak subjectivity, DP13), §25 (T2 long-range attack), §26 (FFG non-finalization), §35 (Q10). During the 22-day partition: (a) Tendermint — neither partition commits if minority < ⅓ (safety holds; liveness lost); (b) Casper — LMD-GHOST continues on both sides; FFG may finalize on the ≥⅔ majority side. After healing: minority nodes offline > 21 days ⇒ bft-light returns Err(TrustExpired); they need a new trusted checkpoint (DP13). Validators that completed unbonding during the partition now hold usable old keys for a long-range attack on the minority chain — the unavoidable PoS consequence when partition duration exceeds the unbonding period.

Q19 — Finality model comparison: 40% stake offline for 10 minutes: Compare how Tendermint BFT and Gasper (Casper FFG) behave when 40% of stake goes offline for exactly 10 minutes. Answer requires synthesis of: §34 (comparative table: finality type, liveness model), §4 (availability), §20 (FFG non-finalization), §26 (liveness stall failure mode). Tendermint: 60% < ⅔ (66.7%), so Tendermint halts — cannot achieve +⅔ quorum; CP behaviour (DP1): zero blocks for 10 minutes; resumes immediately when the 40% returns. Gasper: BABE keeps producing blocks (60% online); LMD-GHOST selects a head; FFG stalls (< ⅔ for justification) — no new finalizations for 10 minutes; after healing FFG resumes and catches up. Key contrast: Tendermint = zero blocks during stall (pure CP); Gasper = unfinalized blocks during stall (liveness-favouring) then finalization catches up.

Q20 — Adding a new field to Vote struct wire compatibility: A new required field sequence_number: u64 must be added to the Vote struct. Nodes are upgrading one at a time (rolling upgrade). How is this handled without a chain halt? Answer requires synthesis of: §28 (§28.1 wire protocol versioning, §28.7 rolling upgrade), §11 (Vote struct, canonical sign-bytes). A required field changes canonical sign bytes ⇒ major version bump (§28.1). Process: (1) bump major; (2) coordinate a flag height; (3) all validators upgrade before the flag height; (4) at the flag height, all nodes switch and reject old-major peers. Rolling upgrade per §28.7 is only safe for minor bumps (optional field, default=0); major bumps require a coordinated flag height — NOT a rolling upgrade.

37. Alternative Architectures (Roads Not Taken)

Alt 1 — Nakamoto-Style Longest-Chain PoS (Probabilistic Finality)

  Genesis → B1 → B2 → B3 → ... (canonical)
                    ↘ B3' → B4' (orphaned fork, less work/stake)

Block producers selected by VRF proportional to stake.
"Finality" = deep enough burial (e.g., 32 confirmations ~ probabilistic).

Mechanism: validators are selected via VRF per slot proportional to stake; the longest/heaviest chain wins; safety converges probabilistically as blocks are buried under more blocks (no rounds, no prevotes, no precommits). Regime where it wins: n → 10 000+ where O(n²) BFT messaging is infeasible; open/permissionless participation; when probabilistic finality is acceptable (e.g., 64 confirmations ≈ 6-nines in Ouroboros Praos). Real system: Ouroboros (Cardano), Ouroboros Praos, NXT PoS, early Peercoin. Why rejected: probabilistic finality is insufficient for this design's goal of absolute finality per block; the absence of slashing makes nothing-at-stake viable, so economic finality (accountable safety) requires a slashing-based BFT protocol (DP4, I2).

Alt 2 — Leader-Based Pipelined BFT with Linear Message Complexity (HotStuff-Style)

  Leader L collects n votes → sends one QC (quorum certificate) to all peers.
  View k:  [Leader proposes] → [collect votes] → [broadcast QC] → commit.
  O(n) messages/view (leader sends QC); O(1) view-change with threshold sig.

Mechanism: a designated leader per view collects n votes and produces a single threshold-signature quorum certificate (QC), then broadcasts it; receivers do one pairing check (BLS). View-change is O(n) because the new leader collects prepare-votes and broadcasts one QC. Regime where it wins: large committees (n > 500) where O(n²) bandwidth is infeasible; when threshold-BLS complexity is acceptable and tail-latency matters more than resilience to a slow leader. Real system: HotStuff (P7), LibraBFT / DiemBFT, Aptos BFT, Tendermint2 (proposed linear variant), Bullshark. Why rejected: single point of failure per view — if the leader is slow, all validators wait. The locking/PoLC model achieves safety via all-to-all voting without a leader aggregation step; for n ≤ 150 O(n²) is tractable (§32) and the added complexity of threshold BLS is not justified. Choose HotStuff if n > 200 or bandwidth is the hard constraint.

Alt 3 — Proof-of-Work Longest-Chain (Nakamoto Consensus, No Stake)

  Genesis → B1 → B2 → B3 → ... (highest cumulative PoW)
  Miners compete by burning CPU/ASIC energy; block validity requires valid nonce.
  Sybil resistance via energy cost, not stake.

Mechanism: block validity requires a valid PoW nonce; the chain with highest cumulative difficulty wins; no validators, no slashing; finality is probabilistic (orphan probability 2^{-k} under 50% adversarial hash rate). Regime where it wins: fully permissionless participation with no trusted genesis; when energy-based Sybil resistance is acceptable and a 13-year proven security model outweighs probabilistic finality. Real system: Bitcoin (#182), Ethereum (pre-Merge), Litecoin, Monero. Why rejected: no absolute finality (§1, DP12); no accountable safety — a 51% attacker loses nothing slashable (I2 impossible without stake); no stake-based validator lifecycle; energy expenditure is an explicit non-goal. This project is specifically the BFT+staking alternative to PoW.

Alt 4 — DAG-Based BFT Consensus (Narwhal + Bullshark/Shoal)

  Each validator continuously broadcasts DAG vertices (batches of txs); each vertex
  references ≥⌈⅔n⌉ prior-round vertices.
  Round r+1: [V0] ← [V1] ← [V2] ← [V3]   (cross-links to round r)
  Round r:   [V0]    [V1]   [V2]   [V3]
  Bullshark selects anchor vertices ⇒ total ordering without blocking consensus.

Mechanism: each validator continuously broadcasts signed DAG vertices (batches); each vertex references ≥⌈⅔n⌉ vertices from the prior round. Bullshark/Shoal selects anchor vertices to produce a total order on batches — transactions are ordered without blocking the consensus path, achieving amortized O(n) message complexity per batch. Regime where it wins: very high throughput (tens of thousands tx/s) where ordering rate, not finality latency, is the bottleneck; large validator sets with committee sampling. Real system: Narwhal+Bullshark (Aptos), Shoal (Aptos 2.0), DAG-Rider, Mysticeti. Why rejected: much higher implementation complexity (DAG vertex tracking, causal ordering, anchor selection); finality latency typically 2–3 rounds vs Tendermint single-slot finality; the design goal is a clean, auditable Tendermint+Casper FFG engine — correctness and simplicity over maximum throughput.

39. Glossary

Accountable Safety — The property that any two conflicting finalizations imply ≥⅓ of total stake can be identified as having violated a slashing condition. Defined formally in P2 (Casper FFG §3); implemented via DuplicateVote, DuplicateFFG, and SurroundFFG evidence types (§22). Guarantees economic finality beyond honest-majority assumptions. See I2, MM4.

Active Validator Set — The subset of bonded validators eligible to propose and vote in the current height. Selected as the top-N validators by stake (or all bonded validators up to the set capacity). Excludes jailed and tombstoned validators. Managed in bft-validators/src/set.rs.

ABCI (Application BlockChain Interface) — The interface between the consensus engine and the application state machine. Defines lifecycle methods: check_tx, begin_block, deliver_tx, end_block, commit. Implemented in bft-abci. The kv-app is the reference implementation. See §19, A15.

BFT Time — The block timestamp computed as the stake-weighted median of precommit Timestamp fields in the commit certificate. Resistant to up to f Byzantine timestamp manipulation because the median is outside the honest validators' range only if f ≥ P/2 (impossible under f < P/3). See §17, §8.1, DP6.

BLS Aggregation — BLS12-381 aggregate signature scheme allowing n individual signatures to be combined into a single 96-byte aggregate signature. bls_aggregate_verify requires one Miller loop + final exponentiation per call (O(1) regardless of n), replacing O(n) Ed25519 verifications. Requires proof-of-possession (PoP) to prevent the rogue-key attack. See §23, A06, P8, B7.

Bonding — The process by which a validator deposits stake (submits a bond(pubkey, power) transaction) to join the active set. Power becomes active after the next EndBlock validator-set update (one-block lag). During bonding and the unbonding period, stake is slashable. See §13, bft-validators/src/bonding.rs.

Byzantine Fault — A fault where a process behaves arbitrarily: it may crash, send conflicting messages, equivocate, withhold messages, or collude with other Byzantine processes. The strictest failure model. f < n/3 Byzantine validators can be tolerated (MM2, P4, P11). Distinguished from crash faults (f < n/2 tolerant in CFT Raft/Paxos).

Casper FFG (Friendly Finality Gadget) — The finality gadget defined in P2 (Buterin & Griffith 2017). Operates on top of a fork-choice rule; validators cast FFGVote{source, target} checkpoint votes; a +⅔ link justifies the target; two consecutive justified checkpoints finalize the earlier. Two slashing conditions: no double-vote, no surround vote. Accountable safety guaranteed. See §20, §8.6, §33 (MM4, MM8).

Certificate (Commit Certificate) — The Commit struct: a set of +⅔ precommit signatures for a specific (height, block_id). A portable proof that a block is final. Verifiable by any party holding the validator set (the light-client's core check). Optionally BLS-aggregated to 96 bytes + bitfield. See §11 (Commit schema), §17, §23.

Chain ID — A string identifier (e.g., "mychain-v1") included in the canonical sign bytes of every vote, proposal, and FFG vote. Provides domain separation to prevent cross-chain signature replay (T9, §25). Changing the chain ID constitutes a hard fork.

Checkpoint — A (epoch: u64, root: Hash) pair representing the first block of an epoch. The atomic unit of FFG justification and finalization. root is the block hash at the epoch-boundary height. See §8.2, §20.

CommitSig — One entry in a Commit certificate: { flag: CommitSigFlag, validator_address: Address, timestamp: i64, signature: Ed25519Sig }. Flag is Commit (voted for the block), Nil (voted nil), or Absent (no prevote received). Only Commit-flagged sigs contribute to the quorum power count. See §11.

CometBFT — The Go implementation of Tendermint BFT (formerly tendermint/tendermint; renamed CometBFT). The primary conformance reference (R1) for this Rust design. Shares the same HRS state machine, proposer-selection algorithm, and vote-set gossip model. See §34.

Domain Separation — The practice of prefixing messages with a type tag before signing to prevent cross-type signature reuse. E.g., a vote's sign bytes begin with "\x00vote" and a proposal's with "\x01proposal". Implemented in bft-crypto/src/domain.rs (A09, A30). Prevents a valid vote sig from being interpreted as a valid proposal sig.

Double Sign / Equivocation — A validator signing two distinct votes at the same (H, R, step) (Tendermint) or two FFG votes for the same target epoch (Casper FFG). The primary slashable offense. Detected by the EquivocationDetector (§22). The operator's primary slashing risk (I3, I7, DP3).

Ed25519 — The deterministic elliptic-curve signature scheme over Curve25519 (RFC 8032, P9). Used for per-vote and per-proposal signatures in this design. Key properties: deterministic nonce (no random-nonce-reuse risk); fast batch verify; malleability-resistant with strict encoding (A05, A30). ~70 µs/verify single-threaded.

Epoch — A fixed number of slots/blocks (e.g., E = 32) used as the granularity for Casper FFG checkpoint boundaries and validator-set-update application. At the end of each epoch, the FFG state is updated and a new checkpoint is defined. See §20, §8.6.

Evidence — A self-contained proof of a slashing offense: two conflicting signed votes (or FFG votes) attributed to the same validator. Types: DuplicateVote, DuplicateFFG, SurroundFFG, LightClientAttack. Independently verifiable against the historical validator set (DP11, I10). See §8.3, §22.

Evidence Pool — The in-memory store of verified, pending slashing evidence. Evidence is deduped by hash, validity-window checked (≤ unbonding period), and drained into blocks for on-chain processing. Managed in bft-slashing/src/pool.rs. See §22, §25 (T8 evidence griefing).

FLP Impossibility — Fischer, Lynch, Paterson (1985, P6): in a fully asynchronous system, no deterministic protocol can solve consensus with even one crash-faulty process. Motivates the partial-synchrony (DLS) model: consensus is achievable after GST. See §16 (timeouts), §33 (MM1).

Fork Choice — The rule that selects the canonical chain head when multiple competing chain tips exist. In Tendermint: trivially the last committed block (locking prevents competing chains). In the Casper/Gasper variant: LMD-GHOST (heaviest-subtree descent). See §21, §8.9, bft-forkchoice.

Gasper — The combination of LMD-GHOST fork choice and Casper FFG finality gadget, used by Ethereum's beacon chain (P3). This design implements a faithful subset of Gasper for the Casper variant. See §20, §21, §34.

Genesis — The first block (height 0 or 1) of the chain; contains the initial ValidatorSet, ChainID, and initial AppState hash. All validators must have identical genesis.json for consensus to start. Template in templates/genesis.json.

GST (Global Stabilization Time) — The unknown but finite time after which the network becomes synchronous (all messages delivered within a known bound Δ). The DLS partial-synchrony model assumes GST exists but is not known in advance. Safety holds before GST; liveness (eventual commit) only holds after GST. See §16, P5, MM1.

HeightVoteSet — The in-memory collection of all prevote and precommit VoteSets for the current height, indexed by round. Bounded to O(n) memory per round. Cleared after commit. Source of equivocation detection (the second distinct vote from the same validator_index triggers DuplicateVote). See §11, §14.

HRS State Machine — The (Height, Round, Step) triplet that defines a validator's consensus position. Step ∈ {Propose, Prevote, Precommit}. Transitions are driven by events (proposals, votes, timeouts). The HRS is persisted in the WAL and gossiped to peers for routing efficiency. The fundamental state atom of Tendermint. See §8.5, §11.

Justification — The FFG state where a checkpoint has received +⅔ power of FFG votes on the link (source → target). A justified checkpoint is a prerequisite for finalization. Two consecutive justified checkpoints ⇒ the earlier one is finalized. See §20, §8.6.

Liveness — The property that honest validators eventually commit a block at every height (given GST and f < P/3). Guaranteed only after GST (DLS). Endangered by: validator downtime, partitions, too many Byzantine proposers, constant timeouts (I14). Monitored via consensus.height advance rate. See §16, §26, MM1, P5.

LMD-GHOST (Latest-Message-Driven Greedy-Heaviest-Observed-SubTree) — The fork-choice rule used in the Casper/Gasper variant. Weights each block's subtree by the stake of validators whose latest attestation is in that subtree. Descends the heaviest child from the finalized checkpoint to select the canonical head. See §21, §8.9, §33 (MM7), P3.

Locking (PoLC) — The mechanism by which a validator associates itself with a specific value at a specific round. A locked validator prevotes only its locked value unless a Proof-of-Lock-Change (PoLC, +⅔ prevotes for a different value at a higher round) unlocks it. locked_round is monotonically increasing (I5). The safety device that prevents forks under conflicting proposals. See §15, §8.5, §33 (MM3), DP5.

Long-Range Attack — An attack where an adversary acquires old (unbonded) validator keys and reconstructs a competing chain from a past height. Defended against by the weak-subjectivity requirement: nodes must sync from a checkpoint within the unbonding period. See §23, §25 (T2), DP13, §35 (Q10).

Nil Vote — A vote with block_id = None, indicating the validator is voting "no block" at this step. Nil prevotes trigger timeoutPrevote; +⅔ nil precommits trigger round-skip. A correct validator prevotes nil if it receives no valid proposal or if it is locked on a different value. See §8.5, §16.

Nothing-at-Stake — The incentive problem in naive PoS where a validator has no cost to vote on every fork (unlike PoW where the same hash rate must be split). Slashing solves nothing-at-stake: voting on multiple forks risks a DuplicateVote slash. See §25 (T3), §2 (historical significance), B5.

Partial Synchrony — The network model (DLS, P5) where message delivery times are unbounded before some unknown GST, and bounded by Δ after GST. Tendermint achieves safety asynchronously and liveness after GST within this model. See §16, §33 (MM1), P5, P6.

PoLC (Proof of Lock Change) — A +⅔ prevote quorum for a specific value at a specific round, justifying a locked validator to unlock from its prior locked value and relock on the new value. Referenced in Proposal.pol_round. The cryptographic justification for an unlock. See §15, §8.5.

Precommit — The second voting step in a Tendermint round. A validator precommits a block only after observing a PoLC (+⅔ prevotes) for that block; otherwise precommits nil. +⅔ precommits for a block ⇒ commit. Precommits are included in the Commit certificate. See §8.5, §14, §17.

Prevote — The first voting step in a Tendermint round. A validator prevotes the proposed block (if valid and consistent with its lock) or nil (if no valid proposal or locked on a different value without a justifying PoLC). +⅔ prevotes for a block = a polka (PoLC). See §8.5, §15, §16.

Proposer — The validator selected to create and broadcast the block proposal for a given (height, round). Selected deterministically by the accumulating-priority weighted round-robin algorithm (I9). Rotates each round on failure. See §8.8, §13, bft-validators/src/proposer.rs.

Quorum — The minimum voting power required for a decision: Q = ⌊2P/3⌋ + 1 (strictly > ⅔ of total power P). The >⅔ (not ≥⅔) strictness is critical: two disjoint quorums must overlap in > P/3 power (MM2, I4). Computed by ValidatorSet::quorum(). See §12, §8.

Quorum Certificate (QC) — In HotStuff-style protocols: a single threshold-signature over a block, produced by aggregating n votes. In this design: the Commit struct (a set of +⅔ precommit sigs, not a threshold sig). The BLS-aggregated Commit (§23) approaches a traditional QC in size (96 B + bitfield). See §17, §23, §34.

Round — A phase of Tendermint consensus: Propose → Prevote → Precommit within a given (height, round). If no commit, a new round begins with a different proposer. Rounds are numbered from 0; timeout grows with round (I14). See §8.5, §16.

Safety — The property that no two correct validators commit different blocks at the same height (I1, Agreement). Guaranteed asynchronously under f < P/3 Byzantine stake. Safety holds before GST; liveness requires GST (MM1). A safety violation is a chain split — the catastrophic outcome (DP1). See §7 (I1), §15, §33 (MM2).

Slashing — The penalty mechanism where a validator loses a fraction of its bonded stake for provable protocol violations (equivocation or surround vote). Evidence is self-contained (DP11). Slash fraction: 1/32 (single equivocation), up to 1/2+ (coordinated). Followed by tombstoning. The implementation of economic finality. See §22, §25, DP4.

Stake — Bonded native tokens that give a validator proportional voting power and that are at risk of slashing for protocol violations. The stake-weight (power) is the unit for all consensus thresholds (DP6). Bonded during active participation; subject to an unbonding delay before withdrawal.

Tombstone — A permanent, terminal validator status applied after a slashing event. A tombstoned validator cannot be unjailed, re-bonded, or restored to the active set. Its power is removed from the set. Terminal by design to prevent a validator from re-entering after a proven safety violation. See §13, §22, bft-validators/src/lifecycle.rs.

Unbonding Period — The delay (e.g., 21 days) between a begin_unbond() request and when the stake is fully released and no longer slashable. During this period the stake remains at risk from slashing for offenses within the validity window. The unbonding period is the defense window against long-range attacks (DP13, §23, T2). See §4, §13, §35 (Q10).

Validator — A bonded participant in the consensus protocol with associated Ed25519 public key, voting power (proportional to stake), and a lifecycle status (Bonded/Unbonding/Unbonded/Jailed/Tombstoned). The consensus unit of participation. Identified by address = hash(pubkey)[..20]. See §8.4, §11, §13.

ValidatorSet — The sorted collection of active Validator structs with cached total_power and a computed proposer address. Bound into the block header via validators_hash (Merkle root) for light-client verification. Updated per height via EndBlock validator-set changes. See §11, §13.

Voting Power — The stake-derived weight of a validator in consensus decisions. All thresholds (quorum, BFT-time median, fork-choice weight) are computed in units of voting power, never node count (DP6, MM6). Represented as u64 in Power newtype; conservation enforced by I6.

WAL (Write-Ahead Log) — The append-only, fsync-per-write log in bft-wal that records (H,R,step) transitions and every signed vote before it is broadcast. On crash, replaying the WAL reconstructs the exact pre-crash consensus state, preventing double-signing (DP3, I7). The double-sign fence (MM5). See §11, §12, §17.

Weak Subjectivity — The requirement that new or long-offline nodes sync from a recent trusted checkpoint (within the unbonding period) rather than from genesis alone. PoS chains cannot be fully trustless for genesis-only sync (unlike PoW) because old validator keys are re-usable after unbonding. The "weak" in the name: some initial trust is unavoidable, but only for the most recent checkpoint (not the entire history). See §23, DP13, §25 (T2, T14), MM8.
