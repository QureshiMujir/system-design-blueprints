36. Hard Questions (Self-Examination)

Q1 — WAL crash/restart safety: A validator crashes mid-broadcast after signing a prevote but before all peers receive it. On restart, should it resend the same prevote, a different prevote, or no prevote? How does the WAL ensure it never double-signs? Answer requires synthesis of: §12 (WAL can_sign guard, DP3, I7), §15 (lock state on restart), §11 (ConsensusWAL schema). On restart WAL is replayed; can_sign returns false for any (H,R,Prevote) with a different block_id; the node re-broadcasts the same vote. If no WAL entry exists (crash before WAL write), the node signs a new prevote for the same block (valid_value and locked_value also replayed). A different block_id is impossible: the WAL records the step before broadcast, so the vote either matches the WAL or never left the node.

Q2 — Conflicting-proposal quorum-intersection argument: A Byzantine proposer sends Block X to 2 validators and Block Y to 1 validator in an n=4, f=1 system. Why can neither X nor Y commit in round 0? Answer requires synthesis of: §8.5 (HRS state machine), §12 (quorum math I4, MM2), §15 (locking). Quorum Q = ⌊2×4/3⌋ + 1 = 3. Honest validators for X: V0, V1 (power = 2); for Y: V2 (power = 1); Byzantine V3 equivocates (not counted as honest). Neither X nor Y reaches Q=3 honest prevotes. No polka ⇒ all honest precommit nil ⇒ round 0 ends without a commit. Safety (I1) is preserved because the Byzantine validator's equivocation cannot complete a quorum alone.

Q3 — Re-proposal with pol_round: The proposer at height H, round 1 re-proposes valid_value = B with pol_round = 0, citing the round-0 polka. V1 is locked on block B' ≠ B at locked_round = 0. Should V1 prevote B or nil? Answer requires synthesis of: §15 (unlock rule: unlock iff PoLC for b' ≠ locked_value at round > locked_round), §8.5 (state machine, Propose step). pol_round = 0 equals V1.locked_round = 0; the unlock rule requires round > locked_round; 0 > 0 is false. V1 stays locked on B' and prevotes nil. A pol_round = 1 (higher round) would allow unlocking.

Q4 — BFT-time median Byzantine timestamp resistance: With n=4, f=1, one Byzantine validator submits a timestamp 1 year in the future in its precommit. How does BFT-time median handle this? Answer requires synthesis of: §17 (BFT-time median, stake-weighted), §8 (domain model, CommitSig.timestamp), §25 (T13 time-manipulation attack). The BFT-time is the stake-weighted median: the timestamp t where cumulative power of validators with timestamp ≤ t exceeds P/2. With n=4 equal power, P/2 = 2 units. The Byzantine validator's extreme timestamp is at the tail; the median is determined by honest validators (power = 3 > P/2). The Byzantine outlier cannot shift the median outside the honest range. In the §4 example: honest timestamps T, T+100ms, T+200ms, Byzantine = T+365days; median = ~T+100ms.

Q5 — High rounds_per_height in production: An operator observes consensus.rounds_per_height averaging 3 in production for 24 hours. What are the root causes and how do you diagnose each? Answer requires synthesis of: §16 (round-skip causes: proposer failure, partition, over-locking), §27 (operational readiness, runbooks), §26 (failure modes: liveness stall, proposer censorship). Root causes: (a) one or more proposers offline — check validators.jailed and per-validator vote inclusion; (b) network partition during proposal — check net.connected_peers drops; (c) over-locking (§15.9) — check consensus.locked_round histogram; (d) clock skew causing timestamp rejections — check consensus.bft_time_delta_ms. Runbook: docs/runbooks/liveness-stall.md has the decision tree. A sustained 3-round average under honest conditions suggests a proposer with high latency; consider adjusting timeoutPropose or jailing the slow proposer.

Q6 — Catching up on a missed height: A validator was offline for height H and comes back online at height H+5. It receives a +⅔ precommit set (a commit cert) for block B at height H from a peer. How does it process this? Answer requires synthesis of: §16 (skip-to-commit: +⅔ precommits for b at any round ⇒ commit), §17 (Commit::verify), §19 (ABCI lifecycle for the missed height). The validator calls Commit::verify (power > 2P/3 + all sigs valid), applies the block through bft-abci (BeginBlock/DeliverTx/EndBlock/Commit) to advance app state and get app_hash, then replays H+1 through H+4. The WAL for H has no entries; can_sign returns true but the cert tells the node H is committed — it moves to H+6.

Q7 — valid_value vs locked_value: A validator has locked_value = B, locked_round = 2 and valid_value = B', valid_round = 3. The proposer at round 4 is this validator. What does it propose and with what pol_round? Answer requires synthesis of: §15 (valid_value tracks latest polka; locked_value gates prevoting), §16 (re-proposal: propose valid_value ?? new_block with pol_round = valid_round). The proposer re-proposes valid_value = B' with pol_round = 3 — sharing the polka with the network, not breaking its own lock. Since valid_round = 3 > locked_round = 2, the proposer's own subsequent prevote (justified by pol_round=3) unlocks it from B.

Q8 — Two validators finalizing conflicting FFG checkpoints: Validators V1 and V2 both observe FFG finalization: V1 sees checkpoint C1 finalized, V2 sees checkpoint C2 finalized (C1 ≠ C2 at the same epoch). What does the accountable safety theorem guarantee? Answer requires synthesis of: §20 (FFG finalization rules), §22 (SurroundFFG slashing), §33 (MM4), P2 (accountable-safety proof). Two conflicting finalizations require two +⅔ justification chains; by quorum intersection (MM2), their ⅔ sets overlap in > P/3 power. Each overlapping validator either double-voted (same target epoch ⇒ DuplicateFFG) or cast surround votes — both slashable. The accountable safety theorem (I2, P2 §3) guarantees ≥⅓P slashable stake.

Q9 — Equivocating validator's effect on LMD-GHOST subtree weight: Byzantine validator V5 attests to block A at slot 10 (weight goes to A's subtree), then attests to block B at slot 11 in A's competing chain (weight moves to B's subtree). How does LatestMessageStore handle this? Answer requires synthesis of: §21 (LatestMessages: latest attestation per validator; older attestations voided), §21.6 pitfall. update_latest_message(V5, B, epoch=11) replaces (A, epoch=10) (epoch 11 > 10). V5's power moves to B's subtree; VoteSet flags the equivocation (I3, T1) and emits DuplicateVote evidence. Fork-choice uses only the latest message — V5 cannot simultaneously contribute to both branches.

Q10 — Long-range attack with 21-day unbonding: An attacker acquires private keys of 100 validators that unbonded 30 days ago (power was 40% of the chain at that time). The current unbonding period is 21 days. Can the attacker create a valid competing chain from 30 days ago? Answer requires synthesis of: §23 (weak subjectivity, DP13), §35 (capacity model), §25 (T2). Yes — technically the attacker can rebuild from 30 days ago using old keys (≥⅓ power at that height). However, any node online within the last 21 days holds the canonical chain and rejects the fork. A new or long-offline node must obtain a trusted checkpoint within the 21-day window (DP13); bft-light enforces Err(TrustExpired) for nodes offline > unbonding_period.

Q11 — BLS proof-of-possession and rogue-key attack: What is the rogue-key attack on BLS aggregate signatures, and how does PoP prevent it? Answer requires synthesis of: §23 (BLS PoP, A30, A06, R7), §25 (T10), B7 (Ch. 15 rogue-key attack). The attack: V_evil registers pk_evil = pk_honest^{-1} × pk_own; aggregate pubkey becomes pk_own — V_evil forges a cert that appears to include V_honest's sig. PoP counter-measure: at bonding time, V_evil must sign pk_evil under sk_evil; this requires computing sk_evil = log(pk_evil) (intractable discrete log). PoP check gates all validator registrations (A30), blocking rogue-key construction.

Q12 — Casper FFG conflicting forks and accountable safety: Under what exact voting configuration do two conflicting FFG finalizations become possible, and which validators are slashable? Answer requires synthesis of: §20 (FFG state machine, §8.6), §22 (SurroundFFG slashing condition), P2 (Casper FFG §3–4 accountable safety proof). Two conflicting finalizations require: (1) a ⅔+ justification chain leading to checkpoint C1, and (2) a ⅔+ justification chain leading to conflicting checkpoint C2 at the same epoch. The two ⅔ sets for C1 and C2's justification links overlap in > P/3 validators (MM2). Each overlapping validator either (a) voted for both C1 and C2 as the target of a link ⇒ DuplicateFFG slashing condition, or (b) voted (s1→t1) and (s2→t2) where one surrounds the other ⇒ SurroundFFG. The P2 proof shows at least one of these conditions must hold for every validator in the overlap, making ≥⅓P slashable.

Q13 — O(n²) message complexity vs HotStuff: This design uses O(n²) vote gossip. HotStuff (P7) achieves O(n) per view-change. When does the O(n²) cost become the deciding factor against this design, and what would need to change? Answer requires synthesis of: §32 (scalability analysis), §34 (comparative table: message complexity), P7 (HotStuff). The O(n²) cost becomes deciding at approximately n > 150 (§32.4) where bandwidth exceeds 100 Mbps per validator. The HotStuff alternative requires: (a) a threshold-signature scheme (BLS t-of-n) for the quorum certificate; (b) a leader-centric protocol where the leader collects all n votes and broadcasts one QC; (c) view-change complexity O(n) because only the leader broadcasts. The tradeoffs: single point of failure per round (the leader); added latency for the leader to collect all votes; implementation complexity of threshold BLS. For n ≤ 150, O(n²) is tractable and the simpler locking/PoLC model is preferred (design decision rationale in §1, A04).

Q14 — WAL entry with incomplete fsync: A WAL entry for a prevote is written to the OS page cache but fsync has not returned when the process crashes. On restart, is this entry recoverable? Does it cause a double-sign risk? Answer requires synthesis of: §12 (WAL, DP3, I7, DP7), §26 (WAL corruption failure mode). If fsync did not complete, the entry may or may not be on disk; the WAL CRC check detects a partially written entry (CRC mismatch ⇒ Err(Corruption)); truncate at the last valid CRC and restart. The prevote is not replayed; the node may re-sign the same prevote (same block at same HRS — no double-sign risk). append_and_fsync blocks until fsync returns before broadcast; a crash before fsync completes means no peer has seen the vote, so no evidence can be formed.

Q15 — Single-threaded deterministic core vs async reactors: The consensus core is single-threaded (A04). The gossip reactors are async (A03/tokio). How do they communicate, and does the async runtime affect the determinism of consensus decisions? Answer requires synthesis of: §3 (architectural overview), A03, A04, DP2. Communication: reactors push events (inbound votes, proposals, timeouts) into a bounded tokio::sync::mpsc channel; the consensus core reads sequentially via handle_event. The async runtime controls when messages arrive (affects liveness/timing) but not the core's decision logic (safety). handle_event is a pure function of (state, event) independent of wall time (DP2, A17). The simulator (§24) replaces the reactor with a virtual network + deterministic scheduler, proving the core decisions are independent of async scheduling.

Q16 — Proposer priority algorithm centering: The accumulating-priority algorithm adds power to each validator's priority each round and subtracts P from the proposer's priority. Without centering, what goes wrong? Answer requires synthesis of: §13 (proposer algorithm, §13.6 pitfalls), §8.8 (accumulating-priority spec). Without centering, priorities grow as O(K × max_power) per round. Two risks: (a) i64 overflow after ~2^63/max_power rounds (e.g., max_power = 10^12 ⇒ overflow after ~104 days at 1 round/s); (b) a validator with the highest accumulated priority may be selected too many consecutive times, breaking fairness. Centering (subtracting the mean from all after each increment) bounds priorities to [−P, P] and restores correct rotation.

Q17 — app_hash one-block lag: Block H's header contains app_hash. Which block's transactions contributed to this app_hash? What would go wrong if the consensus engine used the current block's app_hash instead? Answer requires synthesis of: §17 (app_hash lag pitfall §17.6), §19 (ABCI Commit, §19.6), §11 (Block schema). Block H's app_hash is the state root after applying block H−1's transactions (previous Commit call). This is the "one-block lag." If the current block's app_hash were used: the proposer would need to execute all transactions before creating the proposal; validators would re-execute before prevoting — serializing execution + proposal creation, adding one full execution round to block latency and eliminating pipelined execution. The one-block lag lets validators prevote based only on the transaction list.

Q18 — Network partition for 48 hours longer than unbonding period: The chain has a 21-day unbonding period. A major network partition lasts 22 days (longer than the unbonding period). What happens to the minority partition and the weak subjectivity guarantee? Answer requires synthesis of: §23 (weak subjectivity, DP13), §25 (T2 long-range attack), §26 (FFG non-finalization), §35 (Q10). During the 22-day partition: (a) Tendermint — neither partition commits if minority < ⅓ (safety holds; liveness lost); (b) Casper — LMD-GHOST continues on both sides; FFG may finalize on the ≥⅔ majority side. After healing: minority nodes offline > 21 days ⇒ bft-light returns Err(TrustExpired); they need a new trusted checkpoint (DP13). Validators that completed unbonding during the partition now hold usable old keys for a long-range attack on the minority chain — the unavoidable PoS consequence when partition duration exceeds the unbonding period.

Q19 — Finality model comparison: 40% stake offline for 10 minutes: Compare how Tendermint BFT and Gasper (Casper FFG) behave when 40% of stake goes offline for exactly 10 minutes. Answer requires synthesis of: §34 (comparative table: finality type, liveness model), §4 (availability), §20 (FFG non-finalization), §26 (liveness stall failure mode). Tendermint: 60% < ⅔ (66.7%), so Tendermint halts — cannot achieve +⅔ quorum; CP behaviour (DP1): zero blocks for 10 minutes; resumes immediately when the 40% returns. Gasper: BABE keeps producing blocks (60% online); LMD-GHOST selects a head; FFG stalls (< ⅔ for justification) — no new finalizations for 10 minutes; after healing FFG resumes and catches up. Key contrast: Tendermint = zero blocks during stall (pure CP); Gasper = unfinalized blocks during stall (liveness-favouring) then finalization catches up.

Q20 — Adding a new field to Vote struct wire compatibility: A new required field sequence_number: u64 must be added to the Vote struct. Nodes are upgrading one at a time (rolling upgrade). How is this handled without a chain halt? Answer requires synthesis of: §28 (§28.1 wire protocol versioning, §28.7 rolling upgrade), §11 (Vote struct, canonical sign-bytes). A required field changes canonical sign bytes ⇒ major version bump (§28.1). Process: (1) bump major; (2) coordinate a flag height; (3) all validators upgrade before the flag height; (4) at the flag height, all nodes switch and reject old-major peers. Rolling upgrade per §28.7 is only safe for minor bumps (optional field, default=0); major bumps require a coordinated flag height — NOT a rolling upgrade.

33. Mental Models & First Principles

MM1 — Consensus under partial synchrony: "Safety is asynchronous; liveness requires GST." Safety (no two conflicting commits) must hold even in fully asynchronous networks; liveness is guaranteed only after the unknown GST when the network becomes synchronous. A liveness stall is expected under asynchrony — not a bug; a safety violation indicates a code bug or f ≥ P/3 Byzantine stake. Bug class: treating slow delivery as a protocol error. Resolving §: §16 (timeouts, I14), §33 (MM models), P5, P6. MM2 — Byzantine quorum intersection: "Two ⅔-quorums overlap in > ⅓ of power; this is the f < n/3 boundary." Two quorums of >⅔P must overlap in > ⅓P power; since f < P/3, that overlap is > f, so > 0 honest validators are in both — any two honest decisions share at least one honest witness. Bug class: implementing ≥ 2P/3 instead of > 2P/3 in CommitDetector ⇒ two disjoint quorums possible ⇒ silent safety violation. Resolving §: §12 (I4), §14 (CommitDetector), §7 (I1/I4), P4/P11. MM3 — Locking as a one-way ratchet: "A lock ratchets forward only via PoLC; it never moves backward." locked_round is monotonically increasing (or −1); it advances only when a PoLC (+⅔ prevotes) arrives at a strictly higher round (I5). A validator stays locked until a higher-round PoLC for a different block arrives. Bug class: permitting lock decrease lets Byzantine proposers force locked validators to prevote a different block ⇒ fork risk. Resolving §: §15 (LockState, DP5, I5), §8.5. MM4 — Accountable safety theorem: "Any two conflicting finalizations imply ≥⅓ of stake violated a slashing condition." Two conflicting finalizations require two >⅔ quorums whose intersection (> P/3) must contain validators that double-voted or cast surround votes — all provably slashable. Bug class: a protocol where safety violations leave no slashable evidence makes economic finality illusory. Resolving §: §22 (slashing, I2), §24 (accountability checker), P2/P10, DP4. MM5 — WAL as the double-sign fence: "A validator's signed commitment is durable before it propagates; crash-restart replays the fence before any new signing." The WAL fsyncs each signed vote before broadcast; on restart it replays to reconstruct the last (H,R,step) and the can_sign guard rejects re-signing at or below that point. Bug class: crash-restart without WAL replay ⇒ validator signs a different block at the same (H,R) ⇒ DuplicateVote ⇒ self-slash (the most common real-world slashing incident). Resolving §: §12 (WAL, DP3, I7), §22, runbook double-sign-incident.md. MM6 — Stake-weight vs node-count: "A Sybil with 100 zero-power keys contributes nothing to any quorum; only power matters." All consensus thresholds — quorum, fork-choice weight, proposer selection — are computed over voting power, not validator count. Zero-power nodes buy no quorum influence and only consume FDs and bandwidth. Bug class: using node count for quorum ⇒ a Sybil with 100 low-stake keys can reach a ⅔ count majority without ⅔ power ⇒ fake commit. Resolving §: §13 (DP6, I6), §12 (I4), §25 (T7). MM7 — LMD-GHOST's latest-message bookkeeping: "The subtree weight of a block is the stake of validators whose LATEST attestation is in its subtree; older attestations are voided." Each validator's power is counted at most once — in the subtree of its most recent attestation; attesting to a later block moves the weight to the new subtree. The balancing attack (T4) fails because equivocating weight can only be in one subtree. Bug class: counting all historical attestations ⇒ subtree weights inflate ⇒ fork-choice diverges. Resolving §: §21 (§21.6 pitfall), §8.9. MM8 — Epoch finality lag: "Casper FFG finalizes two epochs behind the present; blocks between justified and finalized can be orphaned." FFG finalizes epoch E only when epochs E and E+1 are both justified; the LMD-GHOST head is always ≥ 2 epochs ahead of the finalized frontier. Blocks between finalized and justified are not yet final and can be orphaned (but never past the finalized frontier). Bug class: treating a justified checkpoint as final ⇒ a client accepts a payment that later gets orphaned. Resolving §: §20 (finalization rule), §8.6, P2, P3.

Glossary (§39) · 51 terms · site-wide glossary

Accountable Safety
The property that any two conflicting finalizations imply ≥⅓ of total stake can be identified as having violated a slashing condition. Defined formally in P2 (Casper FFG §3); implemented via DuplicateVote, DuplicateFFG, and SurroundFFG evidence types (§22). Guarantees economic finality beyond honest-majority assumptions. See I2, MM4.
Active Validator Set
The subset of bonded validators eligible to propose and vote in the current height. Selected as the top-N validators by stake (or all bonded validators up to the set capacity). Excludes jailed and tombstoned validators. Managed in bft-validators/src/set.rs.
ABCI (Application BlockChain Interface)
The interface between the consensus engine and the application state machine. Defines lifecycle methods: check_tx, begin_block, deliver_tx, end_block, commit. Implemented in bft-abci. The kv-app is the reference implementation. See §19, A15.
BFT Time
The block timestamp computed as the stake-weighted median of precommit Timestamp fields in the commit certificate. Resistant to up to f Byzantine timestamp manipulation because the median is outside the honest validators' range only if f ≥ P/2 (impossible under f < P/3). See §17, §8.1, DP6.
BLS Aggregation
BLS12-381 aggregate signature scheme allowing n individual signatures to be combined into a single 96-byte aggregate signature. bls_aggregate_verify requires one Miller loop + final exponentiation per call (O(1) regardless of n), replacing O(n) Ed25519 verifications. Requires proof-of-possession (PoP) to prevent the rogue-key attack. See §23, A06, P8, B7.
Bonding
The process by which a validator deposits stake (submits a bond(pubkey, power) transaction) to join the active set. Power becomes active after the next EndBlock validator-set update (one-block lag). During bonding and the unbonding period, stake is slashable. See §13, bft-validators/src/bonding.rs.
Byzantine Fault
A fault where a process behaves arbitrarily: it may crash, send conflicting messages, equivocate, withhold messages, or collude with other Byzantine processes. The strictest failure model. f < n/3 Byzantine validators can be tolerated (MM2, P4, P11). Distinguished from crash faults (f < n/2 tolerant in CFT Raft/Paxos).
Casper FFG (Friendly Finality Gadget)
The finality gadget defined in P2 (Buterin & Griffith 2017). Operates on top of a fork-choice rule; validators cast FFGVote{source, target} checkpoint votes; a +⅔ link justifies the target; two consecutive justified checkpoints finalize the earlier. Two slashing conditions: no double-vote, no surround vote. Accountable safety guaranteed. See §20, §8.6, §33 (MM4, MM8).
Certificate (Commit Certificate)
The Commit struct: a set of +⅔ precommit signatures for a specific (height, block_id). A portable proof that a block is final. Verifiable by any party holding the validator set (the light-client's core check). Optionally BLS-aggregated to 96 bytes + bitfield. See §11 (Commit schema), §17, §23.
Chain ID
A string identifier (e.g., "mychain-v1") included in the canonical sign bytes of every vote, proposal, and FFG vote. Provides domain separation to prevent cross-chain signature replay (T9, §25). Changing the chain ID constitutes a hard fork.
Checkpoint
A (epoch: u64, root: Hash) pair representing the first block of an epoch. The atomic unit of FFG justification and finalization. root is the block hash at the epoch-boundary height. See §8.2, §20.
CommitSig
One entry in a Commit certificate: { flag: CommitSigFlag, validator_address: Address, timestamp: i64, signature: Ed25519Sig }. Flag is Commit (voted for the block), Nil (voted nil), or Absent (no prevote received). Only Commit-flagged sigs contribute to the quorum power count. See §11.
CometBFT
The Go implementation of Tendermint BFT (formerly tendermint/tendermint; renamed CometBFT). The primary conformance reference (R1) for this Rust design. Shares the same HRS state machine, proposer-selection algorithm, and vote-set gossip model. See §34.
Domain Separation
The practice of prefixing messages with a type tag before signing to prevent cross-type signature reuse. E.g., a vote's sign bytes begin with "\x00vote" and a proposal's with "\x01proposal". Implemented in bft-crypto/src/domain.rs (A09, A30). Prevents a valid vote sig from being interpreted as a valid proposal sig.
Double Sign / Equivocation
A validator signing two distinct votes at the same (H, R, step) (Tendermint) or two FFG votes for the same target epoch (Casper FFG). The primary slashable offense. Detected by the EquivocationDetector (§22). The operator's primary slashing risk (I3, I7, DP3).
Ed25519
The deterministic elliptic-curve signature scheme over Curve25519 (RFC 8032, P9). Used for per-vote and per-proposal signatures in this design. Key properties: deterministic nonce (no random-nonce-reuse risk); fast batch verify; malleability-resistant with strict encoding (A05, A30). ~70 µs/verify single-threaded.
Epoch
A fixed number of slots/blocks (e.g., E = 32) used as the granularity for Casper FFG checkpoint boundaries and validator-set-update application. At the end of each epoch, the FFG state is updated and a new checkpoint is defined. See §20, §8.6.
Evidence
A self-contained proof of a slashing offense: two conflicting signed votes (or FFG votes) attributed to the same validator. Types: DuplicateVote, DuplicateFFG, SurroundFFG, LightClientAttack. Independently verifiable against the historical validator set (DP11, I10). See §8.3, §22.
Evidence Pool
The in-memory store of verified, pending slashing evidence. Evidence is deduped by hash, validity-window checked (≤ unbonding period), and drained into blocks for on-chain processing. Managed in bft-slashing/src/pool.rs. See §22, §25 (T8 evidence griefing).
FLP Impossibility
Fischer, Lynch, Paterson (1985, P6): in a fully asynchronous system, no deterministic protocol can solve consensus with even one crash-faulty process. Motivates the partial-synchrony (DLS) model: consensus is achievable after GST. See §16 (timeouts), §33 (MM1).
Fork Choice
The rule that selects the canonical chain head when multiple competing chain tips exist. In Tendermint: trivially the last committed block (locking prevents competing chains). In the Casper/Gasper variant: LMD-GHOST (heaviest-subtree descent). See §21, §8.9, bft-forkchoice.
Gasper
The combination of LMD-GHOST fork choice and Casper FFG finality gadget, used by Ethereum's beacon chain (P3). This design implements a faithful subset of Gasper for the Casper variant. See §20, §21, §34.
Genesis
The first block (height 0 or 1) of the chain; contains the initial ValidatorSet, ChainID, and initial AppState hash. All validators must have identical genesis.json for consensus to start. Template in templates/genesis.json.
GST (Global Stabilization Time)
The unknown but finite time after which the network becomes synchronous (all messages delivered within a known bound Δ). The DLS partial-synchrony model assumes GST exists but is not known in advance. Safety holds before GST; liveness (eventual commit) only holds after GST. See §16, P5, MM1.
HeightVoteSet
The in-memory collection of all prevote and precommit VoteSets for the current height, indexed by round. Bounded to O(n) memory per round. Cleared after commit. Source of equivocation detection (the second distinct vote from the same validator_index triggers DuplicateVote). See §11, §14.
HRS State Machine
The (Height, Round, Step) triplet that defines a validator's consensus position. Step ∈ {Propose, Prevote, Precommit}. Transitions are driven by events (proposals, votes, timeouts). The HRS is persisted in the WAL and gossiped to peers for routing efficiency. The fundamental state atom of Tendermint. See §8.5, §11.
Justification
The FFG state where a checkpoint has received +⅔ power of FFG votes on the link (source → target). A justified checkpoint is a prerequisite for finalization. Two consecutive justified checkpoints ⇒ the earlier one is finalized. See §20, §8.6.
Liveness
The property that honest validators eventually commit a block at every height (given GST and f < P/3). Guaranteed only after GST (DLS). Endangered by: validator downtime, partitions, too many Byzantine proposers, constant timeouts (I14). Monitored via consensus.height advance rate. See §16, §26, MM1, P5.
LMD-GHOST (Latest-Message-Driven Greedy-Heaviest-Observed-SubTree)
The fork-choice rule used in the Casper/Gasper variant. Weights each block's subtree by the stake of validators whose latest attestation is in that subtree. Descends the heaviest child from the finalized checkpoint to select the canonical head. See §21, §8.9, §33 (MM7), P3.
Locking (PoLC)
The mechanism by which a validator associates itself with a specific value at a specific round. A locked validator prevotes only its locked value unless a Proof-of-Lock-Change (PoLC, +⅔ prevotes for a different value at a higher round) unlocks it. locked_round is monotonically increasing (I5). The safety device that prevents forks under conflicting proposals. See §15, §8.5, §33 (MM3), DP5.
Long-Range Attack
An attack where an adversary acquires old (unbonded) validator keys and reconstructs a competing chain from a past height. Defended against by the weak-subjectivity requirement: nodes must sync from a checkpoint within the unbonding period. See §23, §25 (T2), DP13, §35 (Q10).
Nil Vote
A vote with block_id = None, indicating the validator is voting "no block" at this step. Nil prevotes trigger timeoutPrevote; +⅔ nil precommits trigger round-skip. A correct validator prevotes nil if it receives no valid proposal or if it is locked on a different value. See §8.5, §16.
Nothing-at-Stake
The incentive problem in naive PoS where a validator has no cost to vote on every fork (unlike PoW where the same hash rate must be split). Slashing solves nothing-at-stake: voting on multiple forks risks a DuplicateVote slash. See §25 (T3), §2 (historical significance), B5.
Partial Synchrony
The network model (DLS, P5) where message delivery times are unbounded before some unknown GST, and bounded by Δ after GST. Tendermint achieves safety asynchronously and liveness after GST within this model. See §16, §33 (MM1), P5, P6.
PoLC (Proof of Lock Change)
A +⅔ prevote quorum for a specific value at a specific round, justifying a locked validator to unlock from its prior locked value and relock on the new value. Referenced in Proposal.pol_round. The cryptographic justification for an unlock. See §15, §8.5.
Precommit
The second voting step in a Tendermint round. A validator precommits a block only after observing a PoLC (+⅔ prevotes) for that block; otherwise precommits nil. +⅔ precommits for a block ⇒ commit. Precommits are included in the Commit certificate. See §8.5, §14, §17.
Prevote
The first voting step in a Tendermint round. A validator prevotes the proposed block (if valid and consistent with its lock) or nil (if no valid proposal or locked on a different value without a justifying PoLC). +⅔ prevotes for a block = a polka (PoLC). See §8.5, §15, §16.
Proposer
The validator selected to create and broadcast the block proposal for a given (height, round). Selected deterministically by the accumulating-priority weighted round-robin algorithm (I9). Rotates each round on failure. See §8.8, §13, bft-validators/src/proposer.rs.
Quorum
The minimum voting power required for a decision: Q = ⌊2P/3⌋ + 1 (strictly > ⅔ of total power P). The >⅔ (not ≥⅔) strictness is critical: two disjoint quorums must overlap in > P/3 power (MM2, I4). Computed by ValidatorSet::quorum(). See §12, §8.
Quorum Certificate (QC)
In HotStuff-style protocols: a single threshold-signature over a block, produced by aggregating n votes. In this design: the Commit struct (a set of +⅔ precommit sigs, not a threshold sig). The BLS-aggregated Commit (§23) approaches a traditional QC in size (96 B + bitfield). See §17, §23, §34.
Round
A phase of Tendermint consensus: Propose → Prevote → Precommit within a given (height, round). If no commit, a new round begins with a different proposer. Rounds are numbered from 0; timeout grows with round (I14). See §8.5, §16.
Safety
The property that no two correct validators commit different blocks at the same height (I1, Agreement). Guaranteed asynchronously under f < P/3 Byzantine stake. Safety holds before GST; liveness requires GST (MM1). A safety violation is a chain split — the catastrophic outcome (DP1). See §7 (I1), §15, §33 (MM2).
Slashing
The penalty mechanism where a validator loses a fraction of its bonded stake for provable protocol violations (equivocation or surround vote). Evidence is self-contained (DP11). Slash fraction: 1/32 (single equivocation), up to 1/2+ (coordinated). Followed by tombstoning. The implementation of economic finality. See §22, §25, DP4.
Stake
Bonded native tokens that give a validator proportional voting power and that are at risk of slashing for protocol violations. The stake-weight (power) is the unit for all consensus thresholds (DP6). Bonded during active participation; subject to an unbonding delay before withdrawal.
Tombstone
A permanent, terminal validator status applied after a slashing event. A tombstoned validator cannot be unjailed, re-bonded, or restored to the active set. Its power is removed from the set. Terminal by design to prevent a validator from re-entering after a proven safety violation. See §13, §22, bft-validators/src/lifecycle.rs.
Unbonding Period
The delay (e.g., 21 days) between a begin_unbond() request and when the stake is fully released and no longer slashable. During this period the stake remains at risk from slashing for offenses within the validity window. The unbonding period is the defense window against long-range attacks (DP13, §23, T2). See §4, §13, §35 (Q10).
Validator
A bonded participant in the consensus protocol with associated Ed25519 public key, voting power (proportional to stake), and a lifecycle status (Bonded/Unbonding/Unbonded/Jailed/Tombstoned). The consensus unit of participation. Identified by address = hash(pubkey)[..20]. See §8.4, §11, §13.
ValidatorSet
The sorted collection of active Validator structs with cached total_power and a computed proposer address. Bound into the block header via validators_hash (Merkle root) for light-client verification. Updated per height via EndBlock validator-set changes. See §11, §13.
Voting Power
The stake-derived weight of a validator in consensus decisions. All thresholds (quorum, BFT-time median, fork-choice weight) are computed in units of voting power, never node count (DP6, MM6). Represented as u64 in Power newtype; conservation enforced by I6.
WAL (Write-Ahead Log)
The append-only, fsync-per-write log in bft-wal that records (H,R,step) transitions and every signed vote before it is broadcast. On crash, replaying the WAL reconstructs the exact pre-crash consensus state, preventing double-signing (DP3, I7). The double-sign fence (MM5). See §11, §12, §17.
Weak Subjectivity
The requirement that new or long-offline nodes sync from a recent trusted checkpoint (within the unbonding period) rather than from genesis alone. PoS chains cannot be fully trustless for genesis-only sync (unlike PoW) because old validator keys are re-usable after unbonding. The "weak" in the name: some initial trust is unavoidable, but only for the most recent checkpoint (not the entire history). See §23, DP13, §25 (T2, T14), MM8. ---
