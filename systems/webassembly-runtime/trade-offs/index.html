Decisions (§9) · 24 ADRs

ADR-01

Host language

Chosen

Rust 2021, MSRV 1.78

Rejected

C/C++, Go, Zig

When the rejected choice is right

C/C++ wins when targeting existing VM codebase (e.g., V8 plugin) or bare-metal with no alloc; Go wins when shipping a WASM runtime as a microservice where GC pauses are acceptable and deploy velocity beats raw throughput

Why: Memory safety on untrusted bytecode; enums+match for opcode dispatch; no GC pauses; strong ecosystem

ADR-02

Crate decomposition

Chosen

Six-crate workspace: wrt-types, wrt-decoder, wrt-validator, wrt-runtime, wrt-jit, wrt-cli

Rejected

Monolith; two-crate split

When the rejected choice is right

Monolith wins for a one-person prototype that will never be published to crates.io; two-crate split wins when only one internal boundary matters (decode+validate in one crate vs. execute in another) and compile time is constrained

Why: Enforce layering at compile boundary; no_std crates compile for embedded; isolated test surface

ADR-03

no_std+alloc boundary

Chosen

wrt-types, wrt-decoder, wrt-validator are no_std+alloc

Rejected

All std; all no_std

When the rejected choice is right

All-no_std wins when targeting bare-metal microcontrollers with no heap allocator at all (e.g., Cortex-M0 with alloc unavailable); all-std wins when the runtime will only ever run on Linux/macOS servers and embedded targets are out of scope

Why: Decoder/validator are pure transforms (no I/O, no threads); runtime/JIT need mmap, threads → std

ADR-04

Instr representation

Chosen

Single flat enum Instr { … } covering all opcodes

Rejected

Per-category enums (ControlInstr, NumericInstr, …); bytecode byte-array

When the rejected choice is right

Per-category enums win when adding proposal opcodes incrementally without recompiling all match arms; bytecode byte-array wins for an interpreter optimized purely for memory footprint (e.g., wasm3's token-threaded model) where decoding speed matters more than type safety

Why: Flat enum: exhaustive match across all phases; no downcasting; Box<[Instr]> body is cache-friendly

ADR-05

Float storage

Chosen

F32(u32) / F64(u64) bit-patterns in Val

Rejected

Native f32/f64 fields

When the rejected choice is right

Native f32/f64 fields win when NaN payload preservation is explicitly out of scope (e.g., an approximate-compute runtime that canonicalizes all NaNs) and the performance cost of bit-cast round-trips is measurable

Why: Rust f32/f64 NaN-canonicalize on load; Wasm requires NaN payload preservation; bit-pattern → arithmetic via from_bits/to_bits

ADR-06

Validation gate

Chosen

ValidatedModule(Module) newtype; only path to instantiation

Rejected

Runtime type checks on every op

When the rejected choice is right

Runtime type checks win when distributing a runtime that must also execute partially-trusted modules under a capability system that may insert dynamic type annotations at runtime (e.g., a capability-security VM where runtime narrowing is intentional)

Why: Validation proof eliminates per-op type guards in interpreter/JIT; correctness enforced at API boundary

ADR-07

Execution strategy

Chosen

Interpreter first (correctness oracle), then baseline JIT (fast path)

Rejected

JIT-only; interpreter-only

When the rejected choice is right

JIT-only wins when targeting a serverless FaaS platform where cold-start is below 5 ms budget and an interpreter oracle is maintained by a separate team; interpreter-only wins for embedded targets (WASI on microcontrollers) where mmap/mprotect is unavailable

Why: Interpreter is simple, obviously correct, and serves as differential oracle; JIT layered on top for performance

ADR-08

JIT tier

Chosen

Single-pass baseline JIT, no IR, no SSA

Rejected

Multi-tier (Cranelift-class); tree-lowering with IR

When the rejected choice is right

Multi-tier wins when peak throughput must approach native C within 2× (e.g., compute-intensive Wasm workloads like video encoding or cryptography in a production edge runtime); IR+SSA enables register allocation and loop-invariant code motion that single-pass cannot

Why: Cranelift out-of-scope; single-pass keeps wrt-jit <5 KLOC; deopt to interpreter for unhandled opcodes

ADR-09

JIT target ISA

Chosen

x86-64 only (baseline)

Rejected

AArch64 (deferred phase); RISC-V

When the rejected choice is right

AArch64 wins when deploying to AWS Graviton / Apple Silicon fleets where x86-64 is not available; RISC-V wins for open-hardware embedded (e.g., SiFive boards) where a native JIT avoids the overhead of running the interpreter tier

Why: x86-64 covers dominant server/desktop targets; SysV ABI well-documented; AArch64 in future

ADR-10

x86-64 assembler

Chosen

Hand-written Assembler subset in wrt-jit

Rejected

dynasm crate; iced-x86 emitter

When the rejected choice is right

dynasm wins when the instruction set being emitted is too large or too complex to maintain by hand (e.g., a full-feature JIT with AVX-512 + BMI2 + VNNI); iced-x86 wins when both encoding and decoding are needed (JIT + jit-dump disassembly in one library)

Why: dynasm adds proc-macro complexity; iced-x86 is decode-focused; a small emit-only subset is <1 KLOC and zero extra deps

ADR-11

W^X enforcement

Chosen

mmap(RW) emit → mprotect(RX) before first exec; never both simultaneously

Rejected

mmap(RWX) always

When the rejected choice is right

mmap(RWX) wins in a fully trusted, air-gapped embedded environment (e.g., a bare-metal RTOS running verified Wasm only) where the attacker model excludes code injection and the mprotect syscall overhead is measurable on a real-time deadline

Why: OS-level security policy (macOS + SELinux enforce W^X); avoids JIT-spraying attack surface

ADR-12

Linear memory backing

Chosen

Vec<u8> with guard pages via mmap for JIT fast-path bounds

Rejected

Pure Vec<u8> only; WASM-specific mmap

When the rejected choice is right

Pure Vec<u8> only wins for no_std embedded targets where mmap is unavailable and all bounds checks must be explicit; WASM-specific mmap wins for a high-frequency JIT where the extra cmp+jae per memory access measurably bottlenecks throughput (e.g., a memory-bandwidth-bound matmul kernel)

Why: JIT emits mov [base+offset] without explicit bounds check if guard pages catch OOB via SIGSEGV→trap; interpreter still checks explicitly

ADR-13

Memory bounds strategy (interp)

Chosen

Explicit addr + N > len check in u64 before every access

Rejected

Hardware fault + signal handler everywhere

When the rejected choice is right

Hardware fault + signal handler wins for a production JIT where every memory instruction is a hot path and the extra cmp is measurably slow; guard pages make OOB a SIGSEGV caught by a registered handler — used by Wasmtime for its compiled functions

Why: Signal handler approach requires setjmp/longjmp or pthread_attr hacks; not portable to no_std; explicit check in interpreter is safer

ADR-14

Stack depth cap

Chosen

Engine.fuel + static depth counter; cap = 65536 frames

Rejected

Unbounded recursion; OS stack overflow

When the rejected choice is right

Unbounded recursion wins only when the host process is configured with an enormous stack (e.g., ulimit -s unlimited) and the workload is a deeply recursive functional language transpiled to Wasm where the guest developer controls and trusts the recursion depth

Why: Predictable CallStackExhausted trap before OS SIGSEGV; host can configure cap

ADR-15

Interruption mechanism

Chosen

Support both: fuel: Option<u64> (decrement per op) AND epoch counter (shared atomic, checked at call/loop back-edge)

Rejected

Fuel only; epoch only; neither

When the rejected choice is right

Fuel-only wins for deterministic replay and blockchain-style metered execution (gas) where a fixed instruction budget is the product requirement; epoch-only wins for interactive use cases (IDE plugins, game scripting) where a wall-clock timeout is more user-meaningful than an instruction count

Why: Fuel = deterministic instruction budget; epoch = low-overhead async signal from host thread; both used in wasmtime, justified by different use cases

ADR-16

Trap propagation

Chosen

Result<T, Trap> — traps are Err values; no Rust panic

Rejected

std::panic unwinding; setjmp/longjmp

When the rejected choice is right

setjmp/longjmp wins in a C-ABI embedding (e.g., a runtime called from a C plugin host) where Result types cannot cross the FFI boundary and the call sites are already using longjmp-based exception handling

Why: Panic = abort in no_std; longjmp crosses FFI unsafely; Result composes naturally and keeps host code clean

ADR-17

Spec test runner

Chosen

wast text-format parser (own lightweight impl or wast crate from wasm-tools) over official .wast files

Rejected

Ignore spec tests; only unit tests

When the rejected choice is right

Ignoring spec tests wins for a research prototype that intentionally deviates from the spec (e.g., a Wasm variant with deterministic NaN semantics for reproducible ML inference) where the spec testsuite would be all red by design

Why: Official spec testsuite is ground truth for conformance; .wast runner enables assert_trap, assert_return, assert_invalid

ADR-18

Differential oracle

Chosen

wasmtime (via wasmtime crate) in test harness

Rejected

wasm3; browser engine; our own interpreter as oracle

When the rejected choice is right

wasm3 wins as oracle when a minimal-footprint comparison is needed (e.g., checking that a new embedded runtime matches wasm3 on a microcontroller target); browser engine wins when the target deployment is the browser and conformance with V8/SpiderMonkey semantics is the product requirement

Why: wasmtime is Wasm 2.0 conformant, production-grade, easily embedded in Rust tests; our interpreter is the candidate, not the oracle

ADR-19

Fuzzing

Chosen

cargo-fuzz (libFuzzer) — four fuzz targets: decoder, validator, interpreter, JIT

Rejected

AFL++; property-based proptest only

When the rejected choice is right

AFL++ wins for grey-box fuzzing across a polyglot codebase (C/Rust mix) where AFL++'s persistent mode and CmpLog add coverage that libFuzzer misses; proptest-only wins for early-stage development where the corpus is thin and model-based generation produces more interesting inputs per second

Why: cargo-fuzz integrates natively; corpus sharing with OSS-Fuzz; structured mutation covers LEB128 edge cases well

ADR-20

Benchmarks

Chosen

criterion with wall-time + instruction counts

Rejected

bencher; custom harness

When the rejected choice is right

Custom harness wins when the benchmark needs to measure metrics criterion cannot (e.g., JIT compilation latency with sub-microsecond breakdowns using rdtsc directly, or peak RSS per invocation using /proc/self/status)

Why: criterion: stable stats, HTML reports, easy CI integration; targets: decode/validate/interp/JIT throughput vs wasmtime

ADR-21

Dependency policy

Chosen

Minimal: zero runtime deps in wrt-types/wrt-decoder/wrt-validator; no wasmparser dep (self-decode)

Rejected

Pull in wasmparser from wasm-tools

When the rejected choice is right

Pulling in wasmparser wins when time-to-market for a production runtime is paramount and the team's value is in the runtime semantics + JIT, not the binary parser (e.g., a startup building a plugin execution platform where decoder correctness is not the differentiator)

Why: Decoding is core to the project's educational + research value; wasmparser would replace a major deliverable

ADR-22

Licensing

Chosen

MIT OR Apache-2.0 (SPDX dual)

Rejected

MIT only; GPL

When the rejected choice is right

GPL wins when the goal is to require derivative runtimes to contribute back improvements (copyleft); MIT-only wins when Apache-2.0's patent termination clause creates friction with corporate adopters whose legal teams require a simpler license

Why: Matches Rust ecosystem norm; Apache-2.0 adds patent clause; dual allows downstream GPL projects

ADR-23

MSRV policy

Chosen

Rust 1.78 (stable); no nightly features

Rejected

Track latest stable; use nightly for SIMD intrinsics

When the rejected choice is right

Nightly wins when the project requires features not yet stabilized — e.g., portable_simd for cross-arch SIMD abstraction, or asm_goto for threaded-dispatch interpreter — and the CI can tolerate pinning to a weekly nightly

Why: 1.78 provides std::hint::black_box, stabilized asm!, Box<[T]> coercions needed; nightly = fragile CI

ADR-24

wrt-cli binary name

Chosen

wrtc

Rejected

wasm-run, wrt, wrtime

When the rejected choice is right

wasm-run wins when the project is positioned as a user-facing script runner (comparable to node or python) rather than a runtime engineering tool; wrt wins when the project is the canonical runtime for a domain (e.g., the only Wasm runtime for a custom embedded OS) where brevity beats disambiguation

Why: Short; no collision with wasm-tools binaries; c suffix signals "compiler/consumer" CLI

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A — Register-Based Bytecode VM (JVM-class)

Guest bytecode                   Host
─────────────────────────────────────────────
.wasm → [Wasm→RegBC Lowering] → .rbc
.rbc  → [RegBC Interpreter]   → Vec<Val>
         (fixed register file
          RAX/RBX/../R15 map
          to virtual regs v0..v15)

Regime where it wins: If the host ISA is register-rich (AArch64 has 31 GP registers) and the guest programs are long-lived (many calls to the same function), a register-based IR amortizes the load/store overhead vs stack-based dispatch. Spill-free small functions run faster because operands stay in registers between instructions. Used by: Dalvik VM (Android) — deliberately chose register-based bytecode over JVM stack bytecode for mobile performance.

Why this blueprint rejected it: Wasm's specification is defined in terms of a stack machine; re-encoding to register-based IR requires a lowering pass (Wasm → RegBC) that is as complex as an SSA front-end — this contradicts the single-source-of-truth principle (DP-13, ADR-04) and doubles the attack surface on untrusted input. The spec testsuite tests Wasm semantics, not RegBC semantics; conformance becomes indirect. The teaching value of this project is implementing the spec algorithm, not implementing a separate ISA.

Alt-B — Ahead-of-Time (AOT) Compilation to Native Binary

.wasm → [AoT Compiler] → .so / ELF
                          (native shared library)
         import stubs                 export stubs
         ┌──────────────────────────────────────┐
         │  native code (fully optimized)       │
         │  no interpreter; no JIT at runtime   │
         └──────────────────────────────────────┘
host ──dlopen──→ wasm_module.so ──call──→ result

Regime where it wins: Serverless platforms with cold-start SLA < 1 ms cannot afford JIT compilation at invocation time. If the .wasm is compiled to a native .so at deploy time, the cold-start is just dlopen + relocation (~100 µs). Optimizing AOT (with full LLVM pipeline) can match hand-written C. Used by: Fastly Compute@Edge (AOT with Cranelift), Cosmopolitan/WasmEdge AOT mode, wasm-opt → wasm2c pipeline.

Why this blueprint rejected it: AOT requires a persistent compiled artefact with a versioned format, cross-compilation toolchain, and a code-signing / trust chain. The resulting .so is no longer portable Wasm — it is target-CPU-specific and loses the "run anywhere" guarantee. The educational value is in the runtime pipeline (decode → validate → execute); AOT would outsource that to an LLVM backend, reducing the project to a thin wrapper. The differential-testing discipline (INV-8) also requires a live interpreter oracle during execution — incompatible with pure AOT.

Alt-C — Capability-Based Sandbox with Per-Object Permissions

Guest objects (typed GC values, references, capabilities)
 │
 ▼
┌──────────────────────────────────────────────────────┐
│  Capability VM                                       │
│  Each memory region / table / function is a          │
│  capability handle with {read, write, call} bits.    │
│  Cross-capability access checked by handler table.   │
│  OOB → capability fault, not linear-memory trap.     │
└──────────────────────────────────────────────────────┘

Regime where it wins: The Wasm GC proposal and component model move toward capability-oriented isolation where multiple components share an address space with fine-grained access control per object — not the coarse "one flat memory per module" sandbox. If the workload is multi-tenant with many small modules sharing a GC heap, capability-based isolation reduces per-tenant overhead. Used by: Wasm GC proposal (V8 experimental), WebAssembly Component Model (WASI-preview2 interface types).

Why this blueprint rejected it: The component model and GC proposal are explicit NON-GOALs (§1). The Wasm 2.0 core spec has linear memory as the only memory model; capability-based sharing requires a fundamentally different Store design (typed heap, handle tables, GC roots). Implementing this as an extension would invalidate the existing MemInst-centric bounds-check invariants (INV-3, INV-4) and require replacing the Val enum with a capability-tagged union — a complete redesign, not an extension.
