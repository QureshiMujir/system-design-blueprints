Recovery invariants

Input condition Required behavior
Malformed .wasm (bad magic, truncated LEB128, unknown section) Err(DecodeError) — no panic, no UB
Semantically invalid module (type mismatch, undefined import) Err(ValidateError) — never reaches Store
Guest trap at runtime (OOB memory, integer divide-by-zero, unreachable) Err(Trap) returned to host — host process continues
call_indirect type mismatch Err(Trap::IndirectCallTypeMismatch) — not a validator failure
memory.grow exceeding cap Returns -1 (Wasm spec); host sees no error
Frame stack overflow Err(Trap::CallStackExhausted) — not a Rust stack overflow
JIT code fault (bad emit) Caught by trap-stub handler; Err(Trap) — never SIGSEGV the host
Fuel exhausted Err(Trap) (or a distinct OutOfFuel variant) — deterministic interruption

Concurrency constraints

  • Store: !Send, !Sync by default; a Store must not be shared across threads.
  • Multiple independent Stores may exist in separate threads with no synchronization.
  • ValidatedModule is Send + Sync (immutable after validation); multiple Engines may reference the same ValidatedModule.
  • CodeBuffer pages are !Send until PROT_READ|PROT_EXEC flip; after flip, read-only → safe to share across threads (future multi-instance JIT).

Back-of-Envelope Capacity Model

All numbers derived from the System Constraints table (§4) and standard hardware constants. Formula shown for each.

C1 — Interpreter throughput ceiling (single thread): Constraint: ≥ 100 M simple integer ops/sec (§4 table). Each interpreter dispatch is: array-index on Instr slice + match arm (~5 ns on a 3 GHz OOO core at ~2 IPC for a data-dependent dispatch). Formula: 1 / 5 ns = 200 M ops/s raw; with fuel decrement branch and value-stack push/pop overhead, effective ~120–150 M ops/s. Target ≥ 100 M is achievable with no exotic optimization.

C2 — Baseline JIT speedup budget: Constraint: ≥ 5× interpreter (§4). At 150 M interp ops/s, JIT must reach ≥ 750 M ops/s. A tight JIT numeric loop on x86-64 (register-allocated ADD/IMUL with no memory traffic) runs at ~1–3 GHz / 1 op = 1–3 G ops/s. 5× is well within reach for integer-intensive loops; the bottleneck will be memory-bound loops, not compute.

C3 — Module IR size in RAM: Constraint: Module IR ≤ 4× compressed .wasm (§4). A typical real-world .wasm is 1–5 MB (e.g., sqlite3.wasm ≈ 1.3 MB, a game engine ≈ 3–5 MB). Formula: Module_RAM ≤ 4 × 5 MB = 20 MB. With Box<[Instr]> and Box<[ValType]>, each Instr costs 8–16 bytes (enum + payload). A 1 MB .wasm decodes to ~200 K instructions × 12 bytes avg = 2.4 MB — well within 4×.

C4 — Default instance peak RAM (decode + validate + 256 MiB memory): Module IR (C3): 2.4 MB. ValidatedModule = same Module re-wrapped: +0. MemInst::data: 256 MiB (§4 default cap). Frame/label/value stacks at 1024 call depth: 1024 × sizeof(Frame) ≈ 1024 × 64 bytes = 64 KB. Total peak: ~258 MB. Formula: Module_IR + MemInst_data + stacks ≈ 2.4 MB + 256 MB + 0.064 MB ≈ 259 MB.

C5 — Decode + validate throughput ceiling: Constraint: ≥ 50 MB/s (§4). A 50 MB/s decoder must process one byte in 1 / (50 × 10^6) = 20 ns. On a 3 GHz core: 20 ns × 3 GHz = 60 cycles per byte budget. LEB128 decode: ~3 branches + 2 shifts + 1 OR ≈ 10–15 cycles/byte. Section framing + instruction decode: ~20–40 cycles/instruction. Average instruction = ~1.5 bytes compressed; 40 cycles / 1.5 bytes ≈ 27 cycles/byte — within the 60-cycle budget. Validation adds ~10 cycles/instruction (push/pop on OperandStack). Total: ~50 cycles/byte → ~60 MB/s. ≥ 50 MB/s is reachable without hand-tuning.

C6 — JIT compilation throughput ceiling: Constraint: ≥ 10 MB/s of Wasm bytecode → x86-64 (§4). 10 MB/s means 1 / (10 × 10^6) = 100 ns per byte. An average Wasm instruction ≈ 1.5 bytes; 100 ns × 1.5 = 150 ns/instruction budget. x86-64 encoding of one instruction (MOV/ADD/CMP/Jcc): ~20–60 bytes emitted, ~5–10 ns per emit call (just writes to a buffer). With single-pass overhead (value-stack state tracking, patch-site recording): ~30–50 cycles/instruction → ~10–16 ns on a 3 GHz core. Budget is 150 ns — 10× headroom. Target easily met.

C7 — JIT code size: From C6: a 1 MB .wasm input → x86-64 output. Empirically, x86-64 baseline JIT produces 3–8× expansion (each Wasm instruction → 4–15 x86 bytes). Formula: JIT_code = 1 MB × 5 (median) = 5 MB. For the 5 MB .wasm case: 25 MB JIT cache. CodeBuffer uses mmap(MAP_ANONYMOUS) — this comes from virtual address space, not the heap.

C8 — call_indirect type-check cost: One call_indirect requires: table bounds check (1 compare), null check (1 compare), FuncType equality (compare two Box<[ValType]> slices). Slice compare: params.len() == other.len() (1 compare) + memcmp(params, other.params) (≤ 8 bytes for typical arities = 1–2 cache-hit word compares). Total: ~5 ns at cache-warm. Constraint: call latency < 200 ns (§4); 5 ns type check is 2.5% of budget.

C9 — Fuel decrement overhead: Constraint: ≤ 2% throughput penalty (§4). At 150 M ops/s, one op takes ~6.7 ns. 2% of 6.7 ns = 0.13 ns. The fuel path: Option<u64> check (branch predicted-taken for Some) + u64::saturating_sub(1) (1 cycle) + branch on zero (predicted not-taken). Total overhead: ~1–2 cycles ≈ 0.5 ns at 3 GHz. 0.5 ns / 6.7 ns = 7.5% — above the 2% target. Mitigation: use fuel: u64 with a sentinel u64::MAX for unlimited rather than Option<u64> — removes the None branch, reduces to 1 extra instruction per op (~0.3 ns, ~4%).

C10 — Frame stack memory at max depth: Constraint: 1024 frames cap (§4). sizeof(Frame) = sizeof(Vec<Val>) + sizeof(ModuleAddr) + sizeof(usize) = 24 + 4 + 8 = 36 bytes on x86-64. Locals Vec content: avg 8 locals × 16 bytes/Val = 128 bytes. Total per frame: ~164 bytes. At 1024 frames: 1024 × 164 bytes = 168 KB. Small: L2 cache (512 KB typical) holds the entire frame stack.

C11 — Spec-testsuite conformance run time: Official spec testsuite: ~18 000 test cases (core + proposals, as of Wasm 2.0). Each test: decode + validate + instantiate + ≤10 invoke calls. At 50 MB/s decode + 50 MB/s validate + 1 ms instantiate + 200 ns/invoke: avg test ≈ 2–5 ms. Formula: 18 000 × 3 ms = 54 s wall-clock in a single-threaded runner. With parallelism (8 cores): ~7 s. Target: CI conformance run < 5 min — met.

C12 — Differential fuzzer throughput: One differential fuzz iteration: generate via wasm-smith (~1 ms) + interpret + JIT-compare. Interpret 100 K instructions: 100 K / 150 M ops/s ≈ 0.67 ms. JIT call: ~1 µs (post-compile). Total: ~3 ms/iteration. Formula: 1000 ms / 3 ms = 333 fuzz iterations/second per core. On 8 cores: ~2 666/s. In a 5-minute fuzz CI run: 2666 × 300 s = 800 K iterations — sufficient to cover common divergence classes.
