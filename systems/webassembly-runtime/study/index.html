Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. A fuzzer produces a Wasm module where a function contains unreachable followed by i32.add. Your validator rejects it with TypeMismatch. Is that correct? Walk through pop_operand post-unreachable. Which §§ are involved? (§8.5 + §7 INV-2 + §15 Phase 3)
  2. You decode a .wasm file with a DataCount section of 3 but only 2 Data sections. At which stage does this error? What is the exact error type? What property of the module format makes DataCount load-bearing for streaming? (§8.1 + §13 Phase 1 + §5.4 Bulk Memory spec)
  3. An embedder calls invoke() on a function that triggers memory.grow which succeeds (returns old size), then hits an OOB memory access in the same call. After the Trap is returned, what is the state of MemInst::data? Is Store corrupted? Cite the invariant. (§7 INV-7 + §6 DP-12 + §17 Phase 5)
  4. Your JIT emits call_indirect(type_idx=5, table_idx=0). Walk through all three runtime checks the trampoline must perform before the indirect call, identifying the Trap variant for each failure. Then explain how the single-pass compiler records the patch sites for the forward branch to each trap stub. (§7 INV-6 + §9 ADR-08 + §22 Phase 10 + §8.7 error taxonomy)
  5. Val::F32(0x7FC0_0000u32) and Val::F32(0x7F80_0001u32) are two NaN representations. After f32.add of two NaN inputs, which payload does the interpreter produce? What does the spec require? What does this mean for the differential fuzzer's comparison strategy? (§6 DP-6 + §7 INV-10 + §9 ADR-05 + §5.2 "NaN Canonicalization" paper)
  6. Explain why CtrlFrame.start_types and CtrlFrame.end_types must both be stored, not just end_types. Give the concrete case where start_types ≠ end_types and where br(depth) must use start_types instead of end_types. (§8.5 + §8.6 + §15 Phase 3 label_types() function)
  7. You are implementing memory.copy(dst, src, len). The spec says behavior is as if copying byte-by-byte. When dst < src but regions overlap, is memmove or memcpy correct? Cite the spec section. What bulk-memory proposal section defines the overlap semantics? (§17 Phase 5 + §5.4 Bulk Memory proposal + §7 INV-3)
  8. The JIT emits a direct call for Call(FuncIdx). What ABI must the callee follow? Sketch the prologue the Assembler must emit (push rbp; mov rbp, rsp; sub rsp, N) and explain how N is computed for a function with K locals. Where in the single-pass compiler does this happen? (§9 ADR-10 + §5.1 CS:APP Ch 3 + §21 Phase 9)
  9. wrt-jit::CodeBuffer::seal() calls mprotect. On macOS Apple Silicon (future AArch64 target), is mprotect(RW→RX) sufficient? What additional step is required for instruction cache coherence? What does this mean for the seal() implementation on a multi-arch build? (§6 DP-5 + §7 INV-9 + §9 ADR-09 + §5.1 CS:APP Ch 9)
  10. A guest calls table.grow(funcref, 1000) on a table that already has max = Some(500). What does table.grow return? What is the state of TableInst::elem after the call? Compare to memory.grow exceeding cap — same return convention? (§8.3 Table ops + §17 Phase 5 + §7 INV-4 analog for tables)
  11. Your spec-testsuite runner encounters (assert_trap (invoke "foo") "integer divide by zero"). Which crate surfaces the trap? How does the .wast runner map the string "integer divide by zero" to your Trap enum variant? What would happen if your Trap enum used IntDivByZero instead of the spec-mandated message string? (§25 Phase 13 + §9 ADR-17 + §8.7 error taxonomy)
  12. The wrt-validator sees br_table [2, 5, 0] 1 when the ctrl stack has depth 4. Which label depths are valid? What ValidateError fires on depth 5? After br_table — regardless of which target is taken — what is the operand-stack state? (§8.3 control opcodes + §8.5 validation algorithm + §7 INV-2)
  13. Explain the "transactional batch commit" (DP-12) in instantiation. Sketch the rollback path: if the start function traps, exactly which Store fields may have been mutated and which must be rolled back. Why does Wasm spec permit partial memory writes from active segment initialization before a trap? (§6 DP-12 + §7 INV-7 + §18 Phase 6 instantiate.rs)
  14. The differential fuzzer finds a divergence: interpreter returns Val::I32(0) for a call_indirect, JIT returns Trap::IndirectCallTypeMismatch. Both are deterministic for the same input. What are the three most likely root causes? Which ADR governs the oracle relationship and what is the prescribed resolution? (§7 INV-8 + §9 ADR-18 + §9 ADR-07 + §22 Phase 10 call_indirect trampoline)
  15. cargo-fuzz discovers a crash in the validate fuzz target. The sanitizer log shows a panic at Vec::index out-of-bounds. Is this a validator bug or a decoder bug? Walk through the invariant chain from wrt-decoder's index-space cross-reference check to wrt-validator's Context construction to identify where the pre-condition was violated. (§13 Phase 1 + §15 Phase 3 + §7 INV-1 + §6 DP-10)
  16. You want to host 1 000 Wasm plugin instances simultaneously. Each uses the default 256 MiB memory cap. What is the total virtual-address-space commitment? What is the resident set size if each instance only touches 1 MiB? Why does mmap(MAP_ANONYMOUS) make this feasible even on a 64 GB machine? (§4 System Constraints + §C4 capacity model + §17 Phase 5 MemInst)
  17. The JIT must emit bounds-check code for every Load(MemArg { offset: 4294967292, .. }) (i.e., offset = 0xFFFFFFFC). With a 4-byte load, the max effective address is i + 0xFFFFFFFC + 4 = i + 0x100000000. What happens to a u32-based bounds check vs a u64-based one? What is the precise x86-64 instruction sequence the Assembler must emit? (§7 INV-3 + §9 ADR-13 + §21 Phase 9 + §5.2 Lehmann et al. USENIX 2020)
  18. Fuel is set to 500 instructions. The guest calls a host function. Does the host function consume fuel? What happens if the host function calls back into Wasm (re-entrant invoke)? Trace the fuel counter through a host→Wasm→host→Wasm call chain. (§6 DP-7 + §9 ADR-15 + §23 Phase 11 + §7 INV-12)
  19. The engine encounters select (result f32) when the top-three stack values are [F32, F32, I32] (cond on top). Validation already proved this is correct. Write the exact interpreter steps: pop order, condition evaluation, which value to push. Now explain the JIT emission: two registers holding the f32 values, one holding the condition i32 — which x86-64 instruction sequence implements a conditional select without a branch? (§8.3 parametric ops + §18 Phase 6 + §21 Phase 9)
  20. Your wrtc bench shows the JIT version of fibonacci(40) is only 2× faster than the interpreter, not the expected 5×. Diagnose the three most likely causes, ordered by likelihood. Which Back-of-Envelope Capacity Model number is inconsistent with this observation? (§4 System Constraints + §C1/C2 capacity model + Performance Engineering + §9 ADR-08) ---

Mental Models & First Principles

MM1 — A Wasm module is a proof certificate, not executable code. The ValidatedModule newtype encodes this: validation produces a type-correctness proof; instantiation and execution consume it. What it predicts: runtime type errors are structurally impossible after the validation gate; the interpreter needs no per-opcode type guards. Bug class without it: "validate-bypass" bugs where a raw Module reaches the JIT — one wrong ValType in a binary-op could produce a Val::F32 where the assembler assumes Val::I32, yielding corrupt x86-64 immediate encoding and a silent wrong result. Resolving §: §6 DP-2, §7 INV-1, §9 ADR-06, §15 Phase 3.

MM2 — The operand stack is a static proof trace, not a runtime value stack. During validation (wrt-validator) the stack holds OperandType (Known/Unknown), never Val. After unreachable, pop_operand returns Unknown for any request — this is the polymorphic-stack rule; the validator accepts any type pop in an unreachable code region. What it predicts: dead code after unreachable + br is always valid; select in polymorphic region does not require identical top-two types. Bug class without it: rejecting valid dead-code branches (false TypeMismatch), or — worse — failing to propagate unreachable through nested blocks, silently accepting a type-unsafe frame exit. Resolving §: §8.5, §15 Phase 3, §7 INV-2.

MM3 — Every effective address is u64; u32 wrap is an exploit vector. Wasm i32 indices are unsigned when used as addresses, but i32::MAX + large memarg.offset wraps in u32 arithmetic to a small positive number, bypassing the intended bounds check. The fix is: ea = (i as u64) + memarg.offset as u64; if ea + access_width > mem.data.len() as u64 { trap }. What it predicts: no attacker-controlled address can silently wrap; the worst case is an OutOfBoundsMemory trap. Bug class without it: classic "64-bit index truncation" OOB read/write where (0xFFFF_FFFF_u32 + offset) % 2^32 hits a low address in guest memory — Lehmann et al. (USENIX 2020) document this class in production runtimes. Resolving §: §7 INV-3, §17 Phase 5, §6 DP-4.

MM4 — A baseline JIT is a streaming code translator, not a compiler. Unlike an optimizing compiler with IR/SSA, a single-pass JIT visits each opcode exactly once, left-to-right, and emits machine code immediately. Forward branches require label backpatching (record the patch site; fill in the relative offset once the target is known). What it predicts: JIT compilation is O(N_instructions) with no fixpoint iteration; deopt is the only recourse for opcodes that need global analysis. Bug class without it: attempting to implement "just a bit of optimization" (e.g., constant folding) in the single pass creates correctness hazards when the fold depends on type context that appears later in the stream. Resolving §: §9 ADR-08, §21 Phase 9 (single-pass Compiler<'a>), §22 Phase 10 (backpatch CtrlEntry list).

MM5 — W^X is a memory-permission state machine, not a policy flag. CodeBuffer transitions one-way: PROT_READ|PROT_WRITE (emit) → PROT_READ|PROT_EXEC (sealed). The state machine has no reverse; re-emitting requires a new CodeBuffer. What it predicts: any attempt to "patch" a compiled function in place will fail; the Assembler panics on a Sealed buffer. Bug class without it: holding PROT_RWX maps means any guest-controlled write to the host heap that reaches the code region can redirect execution — JIT-spraying attacks (Payer et al., Oakland 2010). Resolving §: §6 DP-5, §7 INV-9, §9 ADR-11, §21 Phase 9 (CodeBuffer::seal()).

MM6 — Traps are values; panics are bugs. Result<T, Trap> is the contract. Every guest fault — OOB memory, integer divide-by-zero, stack exhaustion — must be caught in wrt-runtime or wrt-jit's trap stub and returned as Err(Trap). Any Rust panic! or unwrap that fires because of guest data is a host-level bug, not a trap. What it predicts: invoke() is safe to call in a loop; the host process never crashes on malformed guest input. Bug class without it: a guest integer divide that reaches i32::MIN / -1 triggers Rust's debug-mode overflow panic, killing the embedder process — the spec requires Trap::IntegerOverflow. Resolving §: §6 DP-3, §7 INV-7, §9 ADR-16, §8.7 error taxonomy.

MM7 — Structured control flow makes br depth-indexed, not label-addressed. Wasm has no arbitrary goto. All br/br_if/br_table take a relative depth into the ctrl stack (LabelIdx), not an absolute target address. Depth 0 = innermost enclosing block. For loop, branching to it re-enters at the top (back-edge); for block/if, branching exits to after the end. What it predicts: a single-pass JIT must maintain a CtrlEntry stack that mirrors the ctrl-frame stack; forward branches get patch sites filled on end, backward branches (loop) get the target recorded on entry. Bug class without it: confusing label_types() for loop vs block — loop branch target is start_types (back-edge carries inputs), block branch target is end_types (forward-edge carries outputs) — incorrect arity leads to value-stack corruption. Resolving §: §8.5 validation algorithm, §8.6 execution, §21 Phase 9, §22 Phase 10.

MM8 — Fuel is a monotone counter; epochs are a monotone generation. Fuel decrement per instruction is O(1) and deterministic: given the same fuel budget, the same execution always traps at the same instruction. Epochs are coarser: the host increments a shared atomic; the engine checks at function entries and loop back-edges. Both mechanisms cooperate — fuel for deterministic gas budgeting (blockchain semantics), epoch for wall-clock async interruption. What it predicts: a high-frequency call pattern cannot "bank" fuel across calls; each invoke() deducts from the shared budget. Bug class without it: a deeply-recursive guest exhausts native stack before fuel fires — the check must be a pre-push guard, not a post-call check. Resolving §: §6 DP-7, §9 ADR-15, §7 INV-12, §23 Phase 11.

Glossary · 46 terms · site-wide glossary

abstract interpretation
Validation algorithm over types: runs the module without concrete values; OperandStack holds OperandType (Known/Unknown), not Val.
active segment
Element or data segment with a memory/table index + offset init-expr; copied at instantiation, then effectively dropped.
baseline JIT
Single-pass, no-IR, no-SSA compiler (wrt-jit::Compiler) that emits x86-64 machine code in one forward scan; correctness over throughput.
block type
BlockType in wrt-decoder: empty (no result), ValType (one result), or TypeIdx (multi-value via the type section).
call_indirect
Opcode: read table[i] (trap UndefinedElement if OOB, UninitializedElement if null-ref), compare funcref's FuncType to static TypeIdx (trap IndirectCallTypeMismatch), then call.
canonical NaN
NaN bit pattern with sign=0, all mantissa bits = 1 (f32: 0x7FC0_0000, f64: 0x7FF8_0000_0000_0000). Wasm canonicalises after arithmetic ops on NaN-producing paths.
CodeBuffer
wrt-jit::CodeBuffer — mmap-backed byte buffer; written with PROT_WRITE, then mprotect→PROT_EXEC before first call (W^X invariant).
control frame
wrt-validator::CtrlFrame — tracks opcode, start_types, end_types, operand-stack height, and unreachable flag for one structured block.
control stack
CtrlStack in wrt-validator — stack of CtrlFrame; push on block/loop/if, pop on end; depth = label depth for br.
data segment
DataSegment in Module — raw bytes; active variant patches linear memory at instantiation; passive variant awaits memory.init.
declarative segment
Element segment used only to declare ref.func reachability; no runtime table initialisation.
deopt/bailout
wrt-jit path: when an opcode is unhandled by the JIT (e.g., v128 in Phase 9), fall back to wrt-runtime interpreter for that function.
effective address
base_i + memarg.offset computed in u64 arithmetic; traps OutOfBoundsMemory if addr + access_size > mem.data.len().
element segment
ElemSegment in Module — sequence of Ref values (or init exprs); active initialises a table, passive/declarative do not.
epoch interruption
Cooperative yield point: Engine checks a monotonic epoch counter; host increments it to request a trap/yield without polling fuel.
externref
RefType::ExternRef — opaque host reference; cannot be dereferenced by Wasm; passed through tables and locals.
fuel
Option<u64> in Engine; decremented per instruction; reaching 0 raises Trap::CallStackExhausted (configurable semantic).
function instance
FuncInst in wrt-runtime — either Wasm{ty, module, code} (offset into decoded body) or Host{ty, host} (Rust closure).
function type
FuncType { params: Box<[ValType]>, results: Box<[ValType]> } — the static signature of a function; multi-value allowed.
funcref
RefType::FuncRef — reference to any function in the store; used in tables for call_indirect.
host function
HostFunc — Rust closure registered via Linker; called through FuncInst::Host; may return Trap.
index space
Per-module flat u32 address space for each entity kind: TypeIdx, FuncIdx, TableIdx, MemIdx, GlobalIdx, ElemIdx, DataIdx, LabelIdx. Imports precede definitions.
label
wrt-runtime::Label { arity, cont } — branch target; arity = result count, cont = instruction offset (loop → header, block/if → end).
LEB128
Variable-length integer encoding (ULEB = unsigned, SLEB = signed); used throughout the Wasm binary for all integers. Max 5 bytes for u32/i32, 10 for u64/i64.
linear memory
MemInst { data: Vec<u8>, max: Option<u32> } — byte-addressable contiguous buffer; length always a multiple of PAGE (65536); one per module in MVP.
memarg
MemArg { align: u32, offset: u64 } — static operand of load/store opcodes; align is log2 of expected alignment (hint only, never traps).
module
Module — the decoded IR produced by wrt-decoder; holds all sections as typed Rust structures; not yet type-checked.
module instance
ModuleInst in wrt-runtime — resolved address vectors (func/table/mem/global addrs) + export map; produced by instantiate.
operand stack
OperandStack in wrt-validator — stack of OperandType; abstract type values during validation; distinct from the runtime value Stack.
page
65 536 bytes (64 KiB) — the unit of memory.grow; MemInst.data.len() is always n * 65536.
passive segment
Element or data segment not tied to a specific index/offset at instantiation; initialised on demand via table.init/memory.init.
polymorphic stack
State after unreachable: the validator marks the ctrl frame unreachable=true and truncates the operand stack to frame.height; subsequent pop_operand may return Unknown matching any expected type.
reference type
RefType — either FuncRef or ExternRef; nullable; the coarser ValType::Ref(RefType) appears on the operand stack.
saturating truncation
trunc_sat conversions (CvtOp): float→int without trapping; clamps to int min/max on overflow or NaN (returns 0 for NaN).
section
Binary-format top-level framing unit identified by a 1-byte id (0–12) + u32 length; custom section id=0 carries a name string.
single-pass
JIT property: each opcode is visited exactly once, left-to-right; no backward analysis passes; label targets are back-patched.
store
Store in wrt-runtime — global arena of all allocated instances (funcs, tables, mems, globals, elems, datas); address = index into the relevant Vec.
structured control flow
