334 — Disassembler from Scratch

Project Number: 334

Project Name: Disassembler from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a machine-code disassembler: turn a region of bytes (from a BinaryImage, project #333) into a stream of decoded instructions with mnemonics, operands, lengths, and addresses, then recover basic blocks and a control-flow graph (CFG) with symbolized targets. Primary ISA: x86-64 (the hard case — variable length, prefixes, ModRM/SIB/REX/VEX). Output: decoded Instruction stream + Cfg + a textual listing (Intel & AT&T) matching objdump/llvm-mc (the differential oracle).

In scope: x86-64 decode (legacy + REX + a useful VEX/SSE/AVX subset), full operand/addressing-mode decode (ModRM, SIB, displacement, immediate, RIP-relative), instruction-length determination, linear-sweep and recursive-descent disassembly, basic-block + CFG construction, jump-table heuristics, symbolization via #333 (symbol_at), Intel+AT&T printers, byte/address annotation. AArch64 fixed-length decode as a secondary, schedule-permitting track behind the same Decoder trait.

Explicit non-goals (each tracked as a PhaseDeferred row in the Deferred Features Register): full SSE/AVX-512/AMX coverage (PhaseDeferred("FINAL_BLUEPRINT §12.x")); semantics/lifting to IR — that is #335 Decompiler (§1 non-goal); assembling (encode) beyond round-trip checks (Deferred Features Register); deobfuscation of anti-disassembly tricks beyond detection+diagnostics (Threat Model); debugging/single-step — that is #74 (§1 non-goal).

Deployment model: library crate (disasm-core) + disasm CLI (objdump-like). Consumes #333's BinaryImage; feeds #335 (decompiler), #74 (debugger), #228 (exploitation), #75 (profiler symbolization).

Target users: RE / security engineers; compiler/JIT engineers verifying codegen (#51/#143); learners building the 333→334→335 pipeline.

Phase 0 deliverable (crates/modules):

  1. dis-types — Instruction, Operand, Reg, Mnemonic, DecodeError, Cursor.
  2. dis-decode — decode driver + table dispatch interface (Decoder trait).
  3. dis-x64 — x86-64 prefix/opcode/ModRM/SIB decode (initial integer subset).
  4. dis-print — Intel/AT&T formatter.
  5. dis-cli (disasm) — read #333 image, linear-sweep .text, print listing.

Later phases unlock: full operand decode (Phase 1), length-only fast path (Phase 2), recursive descent + CFG (Phase 3–4), jump-table + symbolization (Phase 5–6), SSE/VEX subset (Phase 7), AT&T+round-trip (Phase 8), AArch64 secondary (Phase 9), hardening/fuzz/differential (Phase 10–12).

Timeline: Phase 0 = 6–14 weeks; full = 5–8 months (x86-64 decode tables are the long pole).

Recommended language: Rust (edition 2021, ≥1.78). Rationale: (a) decodes untrusted bytes → memory safety without GC; (b) exhaustive enum/match model opcode maps + operand kinds precisely; (c) zero-cost slices for the byte cursor; (d) cargo fuzz/Miri cover the never-panic-on-arbitrary-bytes surface; (e) shares the BinaryImage model with #333 and the IR with #335 in one workspace. Locked ADR-001.

Prerequisites: x86-64 instruction encoding (Intel SDM Vol. 2: prefixes, REX, ModRM, SIB, VEX); two's-complement + sign-extension; basic-block/CFG theory; #333 model (sections/symbols/entry); Rust ownership + slices.

2. Why Build This

  • Unique knowledge: how raw bytes become instructions — the inverse of an assembler and the front end of every RE tool, profiler, and decompiler. x86-64's variable-length, prefix-laden encoding is one of computing's great puzzles.
  • Historical/architectural: x86 encoding accreted from 8086 → 80386 → AMD64 → AVX; decoding it teaches the archaeology of the world's dominant ISA. Linear-sweep vs recursive-descent is the classic disassembly dichotomy (and its security pitfalls).
  • Engineering muscles: table-driven decoding; defensive byte parsing; length determination without full decode; CFG recovery from unstructured jumps; jump-table analysis; differential testing against objdump/llvm-mc.
  • Production concepts: decode determinism, never-panic on arbitrary bytes, symbolization, address arithmetic, anti-disassembly resilience.
  • Cross-links: #333 ELF/PE Parser (input: bytes+symbols+entry), #335 Decompiler (consumer: instructions→IR), #51 JIT / #143 SSA (codegen counterpart), #31 VM / #247 Bytecode Verifier (sibling decoders), #74 Debugger / #75 Profiler (symbolized disasm), #228 Binary Exploitation (gadget finding).
  • Calibration: after this you can read a hex dump as code, reason about instruction boundaries, and debug "why did the disassembler desync here."

What Mastery Looks Like

  • After Phase 0: can read a hex dump, identify instruction boundaries manually, and explain why REX.W=1 forces a 64-bit operand even when the default is 32-bit; can trace through ModRM/SIB by hand and reproduce objdump's operand output for any integer instruction.
  • After Phase 1: can decode any integer x86-64 instruction byte-by-byte, including all SIB special cases (index=100 = no index, base=101+mod=00 = disp32-no-base) and all operand-size/address-size combinations; can explain every field in Appendix D.
  • After Phase 2: understands why a length-only fast path exists separately from full decode (I4/P2), can implement Decoder::length sharing the prefix/opcode/ModRM walk, and can explain why byte-granular resync (advance 1) is unbiased vs. "skip to next valid opcode."
  • After Phase 3: can build a recursive-descent worklist from scratch, explain why the visited set is keyed by address (not decoder state), and enumerate what seeds are needed for a stripped binary vs. a symbol-rich one.
  • After Phase 4: can construct a CFG from an instruction stream using the Dragon §8.4 leader algorithm, explain every edge type (FallThrough/Taken/NotTaken/Call/Ret/Indirect), and identify why a fall-through edge after jmp is a phantom (I7 violation).
  • After Phase 5: can pattern-match a compiler jump table, explain why the guard compare bounds the table size, and articulate the difference between absolute-address and RVA-delta table entries; knows when to leave an indirect as unresolved.
  • After Phase 7: can explain mandatory-prefix disambiguation (0x66 as group-3 vs. SSE selector), VEX vvvv 1's-complement inversion, and the difference between VEX.L=0 (XMM) and VEX.L=1 (YMM); can decode a VEX-encoded instruction byte-by-byte.
  • After Phase 11: can run the full differential harness, interpret structured mismatches vs. objdump/llvm-mc, distinguish coverage gaps from decode bugs, and certify the decoder to the ≥99.9% parity SLO.

Per-box: Cursor — bounds-checked byte reader (trust boundary: bytes are hostile). Decode driver — orchestrates prefix→opcode→operand stages, ISA-agnostic via Decoder. dis-x64 — the heart: prefix groups, REX/VEX, 1/2/3-byte opcode maps, ModRM/SIB/displacement/immediate, RIP-relative. dis-arm64 — fixed-width field extraction (secondary). Instruction — the decoded record (addr, length, mnemonic, operands, control-flow class). Linear sweep — decode straight through (fast; desyncs when data is interleaved). Recursive descent — follow control flow from known entries (accurate; needs jump-table reasoning). CFG — leaders→basic blocks→typed edges→functions. Symbolizer — #333::symbol_at turns target addresses into names. Printer — Intel/AT&T text, objdump-parity.

6. Design Principles

  1. Never panic on arbitrary bytes. Any &[u8] decodes to a valid Instruction or a typed DecodeError → printed as (bad); the cursor resyncs. Violation: a crafted byte crashes every downstream tool.
  2. Length before semantics. A fast path determines instruction length without full operand decode (needed for sweep + patching). Violation: can't skip/realign on data.
  3. Two strategies, explicit tradeoff. Linear sweep (fast, desyncs on inline data) and recursive descent (follows flow, needs jump-table reasoning) are both first-class; the CLI exposes both. Violation: one-strategy tools silently mis-disassemble.
  4. Determinism. Same bytes+base ⇒ same instructions+CFG+text; ordered output. Violation: non-reproducible diffs vs objdump.
  5. Table-driven, not ad-hoc branches. Opcode→handler via curated tables. Tradeoff: table maintenance. Violation: unmaintainable nested match swamp.
  6. Bounds + overflow checked. Cursor reads and displacement/immediate math are checked. Violation: OOB read past the region.
  7. Symbolization is a join, not guessing. Targets resolved via #333 symbols/relocs; unknown → raw address. Violation: fabricated names.
  8. Resync over abort. On a bad byte, emit .byte and advance one byte; never stop the whole region. Violation: one bad byte blanks the listing.
  9. CFG edges are typed + sound w.r.t. decode. Fall-through/jump/cond/call/ret/indirect; an edge implies a decoded terminator. Violation: phantom edges mislead #335.
  10. Differential correctness. Mnemonics+operands validated vs objdump/llvm-mc. Violation: subtle operand misdecodes ship.
  11. Bounded recursive descent. Worklist + visited set guarantee termination; indirect targets bounded by heuristics. Violation: infinite loops on crafted CFGs.
  12. Stable Instruction/CFG API + IR-ready. #335 depends on these types; SemVer'd. Violation: breaks the decompiler.

8. Domain Model

8.1 x86-64 instruction encoding (the grammar)

instr   := prefix* [REX|VEX] opcode [ModRM [SIB]] [disp] [imm]
prefix  := group1(lock/rep/repne) | group2(seg/branch-hint) | group3(0x66 opsize) | group4(0x67 addrsize)
REX     := 0100 W R X B            ; W=64-bit operand, R/X/B extend ModRM.reg/SIB.index/rm
VEX     := (0xC5 2-byte | 0xC4 3-byte) → map, vvvv, L, pp   ; AVX
opcode  := 1-byte | 0x0F 2-byte | 0x0F38/0x0F3A 3-byte
ModRM   := mod(2) reg(3) rm(3)     ; mod=11 register-direct; 00/01/10 memory (+disp)
SIB     := scale(2) index(3) base(3)  ; present when rm=100 in memory forms
disp    := 0 | i8 | i32 ( | RIP-relative when mod=00,rm=101 )
imm     := i8 | i16 | i32 | i64 (depending on opcode + opsize)

8.2 Instruction model (normative)

Instruction { addr: u64, len: u8, mnemonic: Mnemonic, operands: SmallVec<Operand;4>,
              prefixes: Prefixes, flow: Flow, bytes: &[u8] }
Operand := Reg(Reg) | Imm(i64) | Mem{base:Option<Reg>, index:Option<Reg>, scale:u8,
                                     disp:i64, seg:Option<Reg>, rip_rel:bool} | Rel(i64)
Reg     := Gpr(size, idx) | Xmm(idx) | Ymm(idx) | Seg(idx) | Rip | Flags
Flow    := Seq | Jump(target) | CondJump{taken:target, fall:u64, cc} | Call(target)
         | Ret | IndirectJump(Operand) | IndirectCall(Operand) | Int | Unknown
Prefixes{ lock, rep, repne, seg, opsize, addrsize, rex:Option<Rex>, vex:Option<Vex> }

8.3 CFG model

BasicBlock { start: u64, end: u64, instrs: Range, term: Flow }
Edge       := FallThrough | Taken | NotTaken | CallEdge | RetEdge | IndirectEdge
Cfg        { blocks: Vec<BasicBlock>, edges: Vec<(BlockId,BlockId,Edge)>, functions: Vec<Function> }
Function   { entry: u64, blocks: Vec<BlockId>, name: Option<String> }   // name from #333

Leaders = entry, branch targets, instructions after a branch/ret/call (per Dragon §8.4).

8.4 Worked example (x86-64)

bytes  55 48 89 e5 48 83 ec 10 e8 12 00 00 00 c9 c3
0x0: 55               push rbp                          (len1, Seq)
0x1: 48 89 e5         mov  rbp, rsp                      (REX.W;ModRM 11 100 101; Seq)
0x4: 48 83 ec 10      sub  rsp, 0x10                     (REX.W;grp1 /5;imm8)
0x8: e8 12 00 00 00   call 0x1f                          (Rel32 +0x12 → target=0x8+5+0x12=0x1f; Call)
0xd: c9               leave                              (Seq)
0xe: c3               ret                                (Ret)
CFG: one block [0x0..0xe] term=Ret, plus CallEdge→0x1f (symbolized via #333 → "helper")

8.5 Malformed / anti-disassembly examples

  • Truncated instruction at region end (opcode needs 4 imm bytes, 2 left) → DecodeError::Truncated → (bad), advance 1, resync (I2).
  • 0xFF /7 (reserved ModRM.reg) → Unknown opcode → (bad), not a guessed mnemonic (I12).
  • Overlapping instructions (jump into the middle of another) → recursive descent decodes both interpretations; sweep sees one (documented divergence, §4).
  • jmp into inline data → linear sweep desyncs (length mismatch I4 flagged); recursive descent avoids by following flow.
  • Infinite jmp $ self-loop → recursive descent visited-set terminates (I6).
  • Indirect jmp [rax*8+table] → target unknown without jump-table analysis → IndirectJump, bounded heuristic (Phase 5).
  • lock prefix on a non-lockable op → decode + diagnostic (lenient), flagged.

11. Core Schema and Core Types

Signatures only (no bodies).

pub struct Cursor<'a> { /* &'a [u8] + pos */ }                 // all reads checked (I1/I6)
impl<'a> Cursor<'a> {
    pub fn u8(&mut self) -> Result<u8, DecodeError>;
    pub fn i8(&mut self) -> Result<i8, DecodeError>;
    pub fn i32(&mut self) -> Result<i32, DecodeError>;         // sign-extended by caller (I5)
    pub fn peek(&self, n: usize) -> Result<&'a [u8], DecodeError>;
    pub fn pos(&self) -> usize;
}

pub enum DecodeError { Truncated, UnknownOpcode(u8), Reserved, BadModRM }   // → (bad), resync (I2)

pub enum Reg { Gpr{size:u8, idx:u8}, Xmm(u8), Ymm(u8), Seg(u8), Rip, Rflags }
pub enum Operand { Reg(Reg), Imm(i64), Rel(i64),
    Mem{ base:Option<Reg>, index:Option<Reg>, scale:u8, disp:i64, seg:Option<Reg>, rip_rel:bool } }
pub enum Flow { Seq, Jump(u64), CondJump{taken:u64, fall:u64, cc:Cc}, Call(u64),
                Ret, IndirectJump(Operand), IndirectCall(Operand), Int, Unknown }

pub struct Instruction<'a> {                                   // immutable, Send+Sync (I11)
    pub addr: u64, pub len: u8, pub mnemonic: Mnemonic,
    pub operands: SmallVec<[Operand;4]>, pub prefixes: Prefixes, pub flow: Flow, pub bytes: &'a [u8] }

pub trait Decoder {                                            // ISA seam (x64 / arm64)
    fn decode(&self, cur: &mut Cursor, addr: u64) -> Result<Instruction, DecodeError>;
    fn length(&self, bytes: &[u8]) -> Result<u8, DecodeError>; // fast path (I2/principle 2)
}

pub struct BasicBlock { pub start:u64, pub end:u64, pub term:Flow }
pub struct Cfg { pub blocks: Vec<BasicBlock>, pub edges: Vec<(u32,u32,Edge)>, pub functions: Vec<Function> }
pub fn sweep(bytes:&[u8], base:u64, d:&dyn Decoder) -> Vec<Instruction>;        // linear (principle 3)
pub fn recursive_descent(img:&BinaryImage, d:&dyn Decoder) -> (Vec<Instruction>, Cfg);  // from entry+symbols

Compatibility: Instruction/Operand/Flow/Cfg are SemVer-stable (ADR-022); #[non_exhaustive] enums allow additive opcodes/operands as minor. bytes/Instruction<'a> borrow the region; an owned variant wraps the buffer.

Phase 0 — Skeleton, Cursor, x86-64 Integer Decode, Linear Sweep, Intel Printer, CLI

0.1 Objectives

Bounds-checked Cursor (I1), a Decoder for the common integer x86-64 subset (mov/add/sub/push/pop/lea/cmp/test/jmp/jcc/call/ret + ModRM/SIB/disp/imm/REX), linear sweep, Intel printer, disasm sweep over a #333 .text. Constraint: never panic on any byte from day one.

0.2 Detailed Implementation Steps

  • dis-cursor: checked u8/i8/i32/peek. [P1, I1, ADR-004]
  • dis-x64: prefix scan → REX → 1-byte opcode map → ModRM/SIB/disp/imm; the ~40 most common integer opcodes + Jcc/jmp/call/ret. [P5, ADR-002, ADR-003; Intel SDM Vol.2 §2.1]
  • Flow classification (Seq/Jump/CondJump/Call/Ret) with Rel target = addr+len+disp. [P9, I8, I5]
  • dis-sweep: decode region start→end, emit (bad)+advance-1 on error. [P1, P8, I2, ADR-006]
  • dis-print::intel; dis-cli sweep <file> [--section .text] using #333 BinaryImage. [P4, ADR-010, ADR-017]

0.3 Deliverable

disasm sweep <elf-or-pe> prints an Intel listing of .text for real binaries; recognizable function prologues.

0.4 Acceptance Criteria

  • Decodes a hand-assembled fixture exactly (mnemonics+operands+lengths).
  • On gcc -O0 .text, ≥ 95% of instructions match objdump -d (integer subset).
  • Fuzz smoke (1M execs) → 0 panics (I2).
  • Σ lengths = region for the clean fixture (I4).

0.5 Conformance Fixtures

conformance/x64/{prologue,arith,branches,lea_rip}, malformed/{trunc_imm,reserved_modrm}, differential/*.objdump.txt.

0.6 Pitfalls

  • ModRM mod=00,rm=101 = RIP-relative (not [rbp]) in 64-bit → wrong operand if treated as 32-bit [disp32].
  • REX.W vs default 32-bit operand size confusion.
  • SIB base=101 + mod=00 = disp32 no base → special case.
  • Sign-extension of i8/i32 disp/imm to i64 (I5).
  • Prefix vs opcode ambiguity (0x66 as operand-size vs mandatory prefix).

0.7 Performance Concerns

Table dispatch (array index by opcode), no allocation per instruction (SmallVec), single pass. Target ≤ 200 ns/instr.

0.8 Edge Cases

Region ends mid-instruction; instruction longer than 15 bytes (x86 max → (bad)); redundant prefixes; 0x0F two-byte escape; nop variants.

0.9 Failure Analysis

A decode bug = wrong listing for #335/#74. Detection: differential vs objdump on first byte. Resync limits blast radius to one instruction (I2).

0.10 Operational Notes

Metrics: decode_ns, bad_insns, unknown_opcode, length_mismatch. disasm --version prints decoder + table-coverage %. Exit 0/2.

Phase 1 — Full ModRM/SIB/Displacement/Immediate + Operand-Size/Address-Size Matrix

1.1 Objectives

Complete the integer operand decoder across all addressing forms and operand/address-size combinations (16/32/64), making operand bytes exact for the whole integer ISA.

1.2 Detailed Implementation Steps

  • ModRM × mod(00/01/10/11) × rm(0..7) full matrix, incl. SIB (scale/index/base) and all disp sizes. [P5, I5, ADR-003; Intel SDM Vol.2 Table 2-1/2-2]
  • Operand-size resolution: default 32, REX.W→64, 0x66→16; address-size 0x67. [P5, I5; §8.1 grammar; Appendix J.1/J.2]
  • Immediate sizing per opcode (ib/iw/id/io) + sign vs zero extension. [P6, I5; Appendix J.3/J.4]
  • Segment-override + implicit operands (e.g., rax for mul). [P5, ADR-003]

1.3 Deliverable

disasm prints exact memory operands ([rip+0x...], [rax+rcx*4+0x10], [rsp+disp8]) matching objdump.

1.4 Acceptance Criteria

Operand strings match objdump on a broad integer corpus (≥ 99%); SIB/RIP-relative exact; differential pass.

1.5 Conformance Fixtures

conformance/x64/{sib_all,rip_rel,opsize16,addrsize,seg_override}, roundtrip/operand_*.

1.6 Pitfalls

  • scale=0 vs index=100 (none) SIB special.
  • 16-bit addressing legacy forms ([bx+si]) — rare in 64-bit but must not misdecode.
  • Default operand size in 64-bit for push/pop/call (forced 64).
  • immediate vs displacement confusion in group ops.

1.7 Performance Concerns

Operand decode is branchy → keep tables flat; avoid per-operand heap (SmallVec).

1.8 Edge Cases

Double prefixes; rex with no effect; [rip+0] ; negative disp; max-length instruction.

1.9 Failure Analysis

Operand misdecode → wrong addresses for #335 data-flow; differential gate.

1.10 Operational Notes

Metrics: operand_mismatch. Encoding notes in docs/encoding/x86-64.md.

Phase 2 — Length-Only Fast Path + Resync Strategy

2.1 Objectives

A length(bytes) path that determines instruction size without full decode (for sweep speed, patching, and robust resync), plus a principled resync after (bad).

2.2 Detailed Implementation Steps

  • Decoder::length shares the prefix/opcode/ModRM walk but skips operand materialization. [P2, I4, ADR-002; Zydis length-path design]
  • Resync: on (bad), advance 1 byte (byte-granular) — document why not "skip to next valid" (which biases). [P8, I2; Kruegel 2004 §3.1; Appendix F]
  • Optional superset-decode mode (decode at every offset) for analysis (Threat Model). [P3, ADR-007; Bauman 2018]
  • Share a single LengthWalk state struct between length() and decode() so the two entry points cannot silently diverge (I4). [P2, ADR-002]

2.3 Deliverable

disasm len <file> byte-accounts a region; sweep uses length for skipping; resync recovers after data.

2.4 Acceptance Criteria

Σ lengths = region on clean code (I4); length matches full-decode length for all fixtures; resync recovers within ≤ 15 bytes after inline data; length-path throughput ≥ 150 MB/s (M2-adjacent, faster than full decode since no operand materialization).

2.5 Conformance Fixtures

conformance/x64/length_*, malformed/inline_data_desync, roundtrip/length_eq_decode.

2.6 Pitfalls

  • Length path diverging from decode path → two sources of truth; share code.
  • Resync heuristic bias → prefer simple byte-advance.
  • Prefixes counted twice in length.
  • Forgetting the 15-byte cap in the length walk lets a malformed prefix run report an unbounded length, corrupting downstream byte accounting (T7).

2.7 Performance Concerns

Length path is the sweep hot loop → no operand alloc; ≥ 100 MB/s (M2), target ≥ 150 MB/s standalone (M9 fuzz path also benefits from the shared walk being allocation-free).

2.8 Edge Cases

Lone prefix bytes; 0xF3 0x0F (rep + escape); padding (0xCC/0x90 runs); a length walk that hits the 15-byte cap exactly on the last byte of the region (boundary must not overrun).

2.9 Failure Analysis

Length≠decode → desync/patch corruption; roundtrip/length_eq_decode gate.

2.10 Operational Notes

Metrics: resync_events, bytes_per_instr. Length path reused by #228 gadget scanning.

Phase 3 — Recursive Descent + Worklist + Function Discovery

3.1 Objectives

Follow control flow from known entries (image entry + #333 function symbols), decoding only reachable code; build the instruction set per function; guarantee termination (I6).

3.2 Detailed Implementation Steps

  • Worklist of addresses (seed: entry, exported/symbol funcs, call targets). [P3, P11, I6, ADR-007; Eagle §3]
  • Decode → on branch/call, enqueue targets; on ret/unknown, stop the path. [P9, I6, I8; §8.3 CFG model]
  • Visited set keyed by address (I6); handle overlapping decodes (record both, flag). [I6, P8; Kruegel 2004 §3.2]
  • Function boundaries from call targets + symbols (#333). [P7, I9, ADR-009]
  • endbr64 (0F 1E FA) recognized as an additional function-entry seed on CET-enabled binaries. [ADR-024; Appendix N.2]

3.3 Deliverable

disasm rd <file> disassembles reachable code per function; lists discovered functions.

3.4 Acceptance Criteria

On gcc/clang binaries, recovered functions ⊇ symbol functions; terminates on all fixtures incl. self-loops (I6); fewer desync artifacts than sweep on data-interleaved code; worklist drains to empty within a bounded number of iterations proportional to reachable instruction count (M5-scale parallelism across seeds).

3.5 Conformance Fixtures

conformance/cfg/{rd_reachable,self_loop,overlap,switch_stub}, malformed/rd_cycle.

3.6 Pitfalls

  • Missing indirect targets → unreachable real code (under-approximation) → combine with symbols + sweep gap-fill.
  • Decoding data as code when following a bad target → bound + validate.
  • Non-termination on crafted CFG → visited set (I6).
  • Tail calls (jmp func) misclassified as intra-function.
  • Recursion implemented as actual call recursion instead of an iterative worklist risks a native stack overflow on deep/cyclic CFGs (T4, FM-7) — the worklist must be a heap-allocated queue, never the Rust call stack.

3.7 Performance Concerns

Worklist O(reachable instrs); visited set hash. Parallelize per seed function.

3.8 Edge Cases

No symbols (entry-only seed); functions reached only via jump tables (Phase 5); noreturn calls; padding between functions.

3.9 Failure Analysis

Under/over-approximation of reachable code → #335 misses/duplicates functions; differential vs objdump's recursive mode + symbol coverage.

3.10 Operational Notes

Metrics: functions_found, rd_revisit, unreached_bytes. disasm rd --seed <addr> for manual seeding.

Phase 4 — Basic Blocks + Control-Flow Graph

4.1 Objectives

Partition decoded instructions into basic blocks and build a CFG with typed edges; sound w.r.t. decode (I7). Constraint: a block ends exactly at a control-flow terminator or a leader boundary.

4.2 Detailed Implementation Steps

  • Compute leaders: entry, every branch target, instruction after every branch/call/ret (Dragon §8.4). [P9, I7; Dragon §8.4; Cooper/Torczon §7.2]
  • Form blocks between leaders; set term = last instruction's Flow. [I7, P9; §8.3 CFG model]
  • Add edges: FallThrough, Taken/NotTaken (Jcc), CallEdge, RetEdge, IndirectEdge. [P9, I7, I8; ADR-008]
  • Group blocks into functions (reachable from a function entry, not crossing call edges). [P7, ADR-009; Appendix M.3]

4.3 Deliverable

disasm cfg <file> [--func name] emits the CFG (text + Graphviz .dot).

4.4 Acceptance Criteria

Block/edge counts consistent with instruction flow; every edge has a decoded terminator (I7); .dot renders; matches manual CFG on fixtures.

4.5 Conformance Fixtures

conformance/cfg/{if_else,loop,switch,nested,tailcall} + golden block/edge sets.

4.6 Pitfalls

  • Fall-through after call is a real edge (call returns) but after jmp/ret is not → flow-class drives it.
  • Targets mid-instruction (overlap) → block split at unaligned address; record + flag.
  • noreturn calls (exit/abort) leave a dead fall-through → mark via #333 symbol hints.
  • Phantom edges from misclassified indirect (I7).

4.7 Performance Concerns

Leaders via sorted set; block build O(n); edges O(branches). Per-function CFG parallel.

4.8 Edge Cases

Single-instruction blocks; block ending at region boundary (implicit); unreachable blocks (sweep mode); back-edges (loops).

4.9 Failure Analysis

Wrong CFG → #335 structuring breaks. Detection: edge audit (I7) + differential vs a reference CFG. Blast radius: that function.

4.10 Operational Notes

Metrics: blocks, edges, phantom_edge(0), indirect_edges. .dot export for inspection; CFG is the #335 hand-off artifact.

Phase 5 — Jump-Table / Switch Recovery + Indirect-Branch Heuristics

5.1 Objectives

Resolve common compiler jump tables so indirect jmp targets become concrete edges, improving CFG completeness (the hardest accuracy problem in disassembly).

5.2 Detailed Implementation Steps

  • Pattern-match the canonical bounded-switch idiom: cmp idx,N; ja default; jmp [base + idx*8] (or *4) → recover table base + size. [P3, P5, I7; Andriesse 2016 §4.2]
  • Read the table from #333 data sections (rodata) via the BinaryImage; bound entries by the compare. [P7, I8, I9, ADR-009]
  • Add resolved Taken edges per table entry; mark unresolved indirects honestly. [P9, I7, P7; §8.3]
  • Heuristics scoped + flagged (no unbounded guessing). [P7, P1; Flores-Montoya/Ddisasm §3]

5.3 Deliverable

disasm cfg resolves switch tables into concrete edges; reports resolved vs unresolved indirects.

5.4 Acceptance Criteria

Recovers clang/gcc switch tables on fixtures; bounded by the guard compare; 0 fabricated targets (unresolved stay IndirectEdge).

5.5 Conformance Fixtures

conformance/cfg/{switch_jumptable_gcc,switch_clang,sparse_switch,unresolved_indirect}.

5.6 Pitfalls

  • Reading the table from the wrong section → garbage targets; require RVA→offset via #333 (I8/I9).
  • Unbounded table (no guard found) → do NOT guess; leave indirect (principle 7).
  • Relative vs absolute table entries (offsets from base).
  • PIC jump tables (entries are deltas).

5.7 Performance Concerns

Pattern match is local (a few instructions); table read is O(entries). Cap table size vs section bounds.

5.8 Edge Cases

Multi-level tables; tables in .text vs .rodata; hand-written asm jumps (no pattern → unresolved); tail-call thunks.

5.9 Failure Analysis

A wrong table read injects phantom edges/blocks (high blast radius for #335) → conservative: only well-matched, bounded patterns resolve.

5.10 Operational Notes

Metrics: jumptables_resolved, indirect_unresolved. Unresolved indirects are surfaced for manual annotation; never silently guessed.

Phase 6 — Symbolization (#333 join: symbols, relocs, PLT/IAT, call graph)

6.1 Objectives

Turn target addresses into names using #333's symbols/relocations only (I9): direct calls→function names, PLT/IAT→imported APIs, data refs→symbol names, build a call graph.

6.2 Detailed Implementation Steps

  • dis-sym: BinaryImage::symbol_at(target) for call/jump targets; nearest defined function + offset. [P7, I9, ADR-009; §8.3]
  • PLT (ELF) / IAT (PE) resolution: map stub→imported symbol via relocs (JUMP_SLOT) / import table. [I9, ADR-009; SysV ABI §5.1; Appendix M.3]
  • RIP-relative data refs → symbol/section names. [I8, I9, P7; §8.1 RIP-relative grammar]
  • Build call graph (function→called functions) from Call edges. [P9, ADR-008; Cifuentes §3]

6.3 Deliverable

disasm listing shows call printf@plt, lea rax, [rip+x] # &message; disasm callgraph emits the call graph.

6.4 Acceptance Criteria

Symbolized names match objdump on direct calls + PLT/IAT; unknown targets show raw address (no fabrication, I9); call graph nodes ⊇ symbol functions.

6.5 Conformance Fixtures

conformance/x64/{plt_call,iat_call,rip_data_ref}, cfg/callgraph_*.

6.6 Pitfalls

  • PLT stub vs real function confusion → resolve through .rela.plt.
  • Local vs global symbol preference; nearest-symbol-below for offsets.
  • Fabricating names for unknown addresses (I9 violation) → raw addr only.
  • Thunk/ICF-merged functions (identical-code folding) share an address.

6.7 Performance Concerns

symbol_at is O(log n) (#333 sorted index); call-graph build O(call edges).

6.8 Edge Cases

Stripped binary (addresses only); weak/aliased symbols; imports by ordinal (PE); PIE base-relative.

6.9 Failure Analysis

Wrong symbolization misleads analysts but doesn't corrupt structure; differential vs objdump symbol output.

6.10 Operational Notes

Metrics: symbolized, unknown_sym, plt_resolved. Symbolization quality tracks #333 symbol completeness.

Phase 7 — SSE/AVX (VEX) Subset + Floating/Vector Operands

7.1 Objectives

Decode a practically-useful SSE/AVX subset (movaps/movups/addps/mulps/xorps, common VEX-encoded AVX) so real .text (which is full of SIMD) disassembles without large (bad) gaps.

7.2 Detailed Implementation Steps

  • Mandatory prefixes (0x66/0xF2/0xF3) selecting opcode variants in the 0x0F map. [P5, ADR-002; Intel SDM Vol.2 §2.1.1; Phase 0.6 Pitfalls]
  • VEX (2- and 3-byte) decode: map, vvvv, L, pp; XMM/YMM operands. [P5, ADR-003; Intel SDM Vol.2 §2.3; §8.1 VEX grammar]
  • 0x0F38/0x0F3A three-byte opcode maps (subset). [P5, ADR-003; Intel SDM Vol.2 Appendix A]
  • XMM/YMM register operands + memory forms. [P5, I5; §11 Reg enum; Appendix D.1]

7.3 Deliverable

disasm decodes common SSE/AVX in real binaries; SIMD-heavy functions no longer desync.

7.4 Acceptance Criteria

≥ 99% instruction coverage on gcc -O2 -mavx2 .text (combined with integer); decoded SSE/AVX matches objdump; unknown SIMD → (bad) not misdecode (I12).

7.5 Conformance Fixtures

conformance/x64/{sse_mov,avx_vex2,avx_vex3,three_byte_op}.

7.6 Pitfalls

  • Mandatory prefix as opcode selector (not a real prefix) → wrong opcode if treated as group3.
  • VEX vvvv inversion (1's complement) → wrong source reg.
  • VEX.L (128 vs 256) → XMM vs YMM.
  • EVEX (AVX-512) out of scope → (bad), not partial decode.

7.7 Performance Concerns

Three-byte maps add a dispatch level; keep tables flat. SIMD operands still alloc-free.

7.8 Edge Cases

Scalar vs packed variants; nop multi-byte via 0x0F1F; legacy SSE without VEX; mixed REX+VEX (illegal → (bad)).

7.9 Failure Analysis

SIMD desync blanks large code regions; coverage % tracked; differential gate on AVX fixtures.

7.10 Operational Notes

Metrics: simd_coverage_pct, vex_decoded. AVX-512/AMX explicitly deferred (PhaseDeferred §12.x).

Phase 8 — AT&T Syntax + Re-encoder Round-Trip (I10)

8.1 Objectives

Add AT&T output (operand order, sigils, suffixes) for objdump parity, and a re-encoder for the decidable subset to prove decode fidelity via round-trip (I10).

8.2 Detailed Implementation Steps

  • dis-print::att: reversed operands, %reg/$imm, size suffixes (movq), (%rip) forms. [P4, ADR-010; SysV ABI AT&T conventions; Appendix O normalization]
  • dis-encode: assemble decoded Instruction → bytes for the supported subset. [I10, ADR-016; Intel SDM Vol.2 encoding tables]
  • Round-trip harness: decode→encode→compare bytes; flag mismatches. [I10, P10, ADR-012; Testing & Verification Strategy]
  • Canonical-form table: for each opcode with multiple valid encodings, mark exactly one as the re-encoder's target so I10 has a single well-defined answer. [ADR-016, I10]

8.3 Deliverable

disasm sweep --att matches objdump -d (AT&T default); disasm roundtrip reports re-encode fidelity.

8.4 Acceptance Criteria

AT&T listing matches objdump on the corpus; round-trip byte-identical for the supported subset (I10); mismatches enumerated; roundtrip_fail = 0 on the canonical-subset conformance suite (M12-adjacent release gate).

8.5 Conformance Fixtures

conformance/x64/att_*, roundtrip/reencode_*, differential/*.objdump-att.txt.

8.6 Pitfalls

  • AT&T operand reversal + suffix rules (ambiguous sizes need suffix).
  • Encoding ambiguity (multiple byte sequences decode same) → round-trip only for canonical forms.
  • RIP-relative AT&T syntax (x(%rip)).
  • Implicit operands shown differently across syntaxes.
  • Redundant REX bytes (W=R=X=B=0) are legal but meaningless; the re-encoder drops them, so naive byte-for-byte comparison against the original must first classify the input as canonical or non-canonical (Q9).

8.7 Performance Concerns

Printing is off the hot decode path; re-encode used only in tests, never in the sweep/RD hot loop (M1/M2 unaffected by AT&T or round-trip cost).

8.8 Edge Cases

Instructions with no AT&T suffix needed; prefixes in AT&T; segment overrides; non-canonical encodings (decode-only, no round-trip).

8.9 Failure Analysis

Round-trip mismatch reveals a decode/operand bug → I10 gate. Print mismatch caught by differential.

8.10 Operational Notes

Metrics: roundtrip_fail(0 on subset), att_mismatch. Two-syntax parity strengthens the differential oracle.

Phase 9 — AArch64 Secondary Decoder (fixed-width)

9.1 Objectives

Validate the Decoder trait as a real multi-arch seam by adding a useful AArch64 (A64) subset: fixed 32-bit instructions decoded by field extraction. Schedule-permitting; proves the architecture generalizes beyond x86-64.

Scalability Analysis

The unit of work is a region/function; scaling is fan-out across functions/sections (decoder is pure + Send/Sync → embarrassingly parallel; a fleet disassembles many binaries concurrently). Bottlenecks: (1) decode CPU (table dispatch — already O(1)/instr); (2) recursive-descent worklist for huge functions (bounded by reachable instrs + visited set); (3) CFG/jump-table analysis (local, cheap); (4) symbolization (#333 O(log n) lookups). Ceilings: single huge function's CFG is O(instrs) memory; superset-disassembly mode (decode every offset) is O(region) and used only for analysis. No shared mutable state, no persistence → linear scaling with cores. Memory grows with instruction-stream + CFG size (≤ 3× region), not unboundedly.

Mental Models & First Principles

Mental models predict how bugs arise and which tests catch them. Each model is stated as a claim, a prediction, and the bug class that appears without it.

MM1 — The decode state machine. An x86-64 instruction is a micro-FSM over prefix/opcode/ModRM/SIB/disp/imm bytes; the decoder is that FSM's interpreter. Predicts: every decode ambiguity maps to a state transition — mandatory prefix vs. group prefix is a fork at the opcode-map entry, not at the prefix byte. Bug class without it: treating 0x66 as always operand-size when it is a mandatory SSE prefix (produces wrong mnemonic for movdqu, movdqa). Applies: §8.1, Phase 0/1, Appendix N.1.

MM2 — Length-before-semantics. Knowing instruction length requires only the prefix/opcode/ModRM/SIB walk, not full operand materialization. Predicts: a separate fast path exists and is correct by design if it shares the prefix/opcode/ModRM walk with the full decoder. Bug: diverging length path and decode path create two sources of truth — a length of 5 while decode yields 4 is a latent desync. Applies: Phase 2, I4, ADR-002.

MM3 — Linear sweep vs. recursive descent as over/under approximation. Sweep is a superset (may include data bytes decoded as instructions); RD is a subset (may miss code reachable only via indirect branches). Predicts: neither is complete alone; best accuracy = RD plus gap-fill sweep. Validation: Andriesse 2016 measures exactly this tradeoff on real compiler output. Applies: Phases 3–5, Appendix N.4.

MM4 — CFG edges are typed and sound. An edge only exists if a decoded terminator implies it. Predicts: phantom edges from misclassified indirects are detectable by auditing every edge's source block terminal. Bug class: emitting a FallThrough edge after jmp (the block's Flow is Jump, not Seq) misleads #335's structuring. Applies: Phase 4, I7, ADR-008.

MM5 — Symbolization is a join, not inference. Names come only from #333's symbol table and relocation records. Predicts: stripped binaries show raw addresses, never invented names. Bug: guessing function names from prologue patterns (push rbp; mov rbp,rsp) produces plausible-looking but incorrect names — violates I9 and makes differential comparison unstable. Applies: Phase 6, I9, ADR-009.

MM6 — Resync is byte-granular and unbiased. Advance exactly 1 byte on bad decode. Predicts: recovery within ≤15 bytes (x86 max instruction length) once past the offending region. Failure mode: skipping to "next valid opcode" biases toward the obfuscator's intent — the byte that looks like a valid opcode after the junk may itself be a data byte placed there intentionally. Applies: Phase 0/2, P8, Appendix F.

MM7 — Differential correctness as the primary oracle. Self-tests cannot catch subtle misdecodes (wrong register index, off-by-one in sign-extension); only structured comparison to objdump/llvm-mc can. Predicts: any mnemonic/operand divergence from the oracle is a real bug, not a cosmetic difference. Implication: the conformance test suite is necessary but not sufficient; differential is the primary gate. Applies: Phase 11, ADR-015, Appendix O.

MM8 — Invariants as the decode contract. I1–I12 collectively define what "correct decode" means; a decoder that satisfies all 12 is correct by construction for the defined scope. Predicts: the fuzz + differential + round-trip suite is exactly the minimal set of tests that covers all 12 invariants (I2→fuzz, I4→length-resum, I7→edge-audit, I9→join-check, I10→round-trip, I12→differential). Applies: all phases; §7 Invariants.

Back-of-Envelope Capacity Model

All numbers derived from §4 System Constraints and §8 Domain Model. Formulas shown so the reader can re-derive for different assumptions.

1. Decode throughput (target validation)

  • Target: ≥100 MB/s linear sweep; ≥30 M instr/s.
  • Average x86-64 instruction in integer-heavy code ≈ 3.5 bytes (measured on gcc -O2 binaries); in mixed SIMD code ≈ 4.5 bytes.
  • At 3.5 B/instr: 100 MB/s ÷ 3.5 B = 28.6 M instr/s ✓ (meets the 30 M target at 3.33 B/instr average).
  • At 200 ns/instr p99: throughput = 1 ÷ 200 ns = 5 M instr/s on a single core — but this is the tail latency; the average is ≤50 ns/instr, giving 20 M instr/s single-core.
  • Parallelizing across 4 cores (per-function): 20 M × 4 = 80 M instr/s; 8 cores → 160 M instr/s, well above target.

2. Memory per instruction (Instruction struct)

  • addr(8) + len(1) + padding(3) + mnemonic(4 enum) + SmallVec<[Operand;4]> inline (4 × ~28 B = 112 B) + flow(~24 B) + prefixes(8 B) ≈ 160 B/instr (worst case: 4 non-trivial operands).
  • Typical instruction (1-2 operands, SmallVec inline): ≈ 80 B/instr.
  • A 1 MB .text region ≈ 285k instrs (at 3.5 B/instr); at 80 B/instr = 22 MB instruction stream ≈ 2.2× region.
  • §4 target: ≤3× region → 22 MB ÷ 1 MB = 2.2× ✓.

3. CFG memory overhead

  • A typical function: ~50 basic blocks × (start u64 + end u64 + term Flow) ≈ 50 × 32 B = 1.6 KB blocks.
  • ~60 edges × (src u32 + dst u32 + Edge u8 + padding) ≈ 60 × 12 B = 720 B edges.
  • Per-function CFG ≈ 2.3 KB.
  • For 10k functions: 23 MB CFG overhead on top of the instruction stream (within the 3× budget for a 10 MB binary).

4. Recursive descent visited set

  • A 1 MB binary ≈ 285k instructions; at 50% reachability (typical for symbol-rich binaries) ≈ 143k addresses.
  • HashMap<u64, ()> at ~50 B/entry (ahash): 143k × 50 B ≈ 7 MB visited set.
  • HashSet<u64> with a more compact repr (e.g., sorted Vec<u64> + binary search): 143k × 8 B = 1.1 MB.
  • Design choice: use a HashSet<u64> (fast insert/lookup) but size-cap it at 10× region size to prevent pathological growth.

5. Jump table reads

  • Average switch has ~8 entries × 8 B = 64 B per table (x86-64 absolute 64-bit entries).
  • 1k switch tables in a 10 MB binary = 64 KB data reads from .rodata (negligible vs. I-cache pressure).
  • Table bound from guard compare limits reads: cmp idx, N → read at most N+1 entries.

6. CLI startup budget

  • §4 target: ≤30 ms for a 10 MB binary (incl. #333 parse).
  • #333 ELF parse (headers + symbol table): ≈10–15 ms for 10 MB (mmap + index build).
  • Linear sweep decode: 10 MB ÷ 100 MB/s = 100 ms — exceeds budget alone.
  • Resolution: CLI default = recursive descent (decodes only reachable code ≈ 50% of bytes at 50% reachability) → 5 MB ÷ 100 MB/s = 50 ms; still borderline.
  • Further: lazy decode (decode on demand per function, not whole binary upfront) brings startup to #333-parse + first-function-decode ≈ 15 ms ✓.
  • Length-only path (Phase 2) at ≥150 MB/s reduces sweep cost: 10 MB ÷ 150 MB/s = 67 ms — still over; confirms lazy RD is the right default.

7. Fuzz throughput

  • Decode call overhead: ≈50 ns/instr average; a 1 KB fuzz input ≈ 285 instrs (at 3.5 B/instr) → 285 × 50 ns ≈ 14 µs/exec → ~70k execs/s per core.
  • 24h × 70k = 6 billion executions per core → with 4 cores = 24 billion → well above the "meaningful coverage" threshold for a ≤1 KB input space.
  • Seed corpus from real binaries with edge-case encodings (REX+VEX, max-length, SIB specials) is more valuable than raw exec count.

8. Table size (compiled-in opcode tables)

  • 1-byte map: 256 entries × ~16 B (handler ptr + operand template) = 4 KB.
  • 2-byte (0F) map: 256 entries × 16 B = 4 KB.
  • 3-byte (0F38, 0F3A) maps: 2 × 256 × 16 B = 8 KB.
  • Group extensions (Grp1–Grp15, ~15 groups × 8 entries × 8 B): ~1 KB.
  • Total curated tables: ≈17 KB — fits in L1 cache (typically 32–64 KB), confirming the table-dispatch hot-path assumption.

Hard Questions (Self-Examination)

These 20 questions each require synthesizing ≥2 sections of this document. They are the questions a staff engineer would ask during a design review.

Q1. "Why does treating 0x66 as always group-3 (operand-size) break SSE decoding, and where in the decode pipeline must mandatory-prefix disambiguation occur?" (Resolves via: §8.1 Domain Model + Phase 7.2 Steps + ADR-002) 0x66 is a group-3 prefix for integer ops (changes operand size from 32→16) but is the mandatory prefix selecting the 66 variant in the 0x0F map for SSE (e.g., 66 0F 6F = movdqa, not movdqu). Disambiguation must occur after the opcode byte is consumed: the opcode-map entry must carry a mandatory_prefix field, and the prefix is consumed as part of the opcode selection, not as a standalone operand-size modifier. Without this: movdqa misdecodes as a 16-bit integer op on whatever opcode follows 0x0F 0x6F — wrong mnemonic, wrong operands, wrong length.

Q2. "An attacker supplies a binary where every jmp lands 1 byte into the previous instruction. How does each of the three strategies handle this, and what is the blast radius of each?" (Resolves via: Phase 2 resync + Phase 3 steps + Appendix F + Threat Model)

  • Linear sweep: decodes the first byte of each instruction correctly, then the jmp target (mid-instruction byte) as the start of the next instruction → desync; length-mismatch I4 flagged; entire region after the first jmp is misaligned. Blast radius: full region downstream of the first overlap.
  • Recursive descent: follows the jmp target (mid-instruction address) → decodes from that offset, which is a valid (different) instruction interpretation; visited-set ensures termination; the "canonical" instruction at the earlier address is also decoded if reachable from its own entry. Blast radius: function-local; both interpretations recorded and flagged as overlap.
  • Superset: decodes at every offset → both interpretations appear in the output; analyst must disambiguate. Blast radius: none structurally, but output is noisy (O(region) instructions).

Q3. "The §4 startup budget is ≤30 ms for a 10 MB binary, but the capacity model shows sweep takes ~100 ms. What architectural choices resolve this, and what do they trade?" (Resolves via: §4 + Back-of-Envelope Capacity Model + Phase 2 + Phase 3) Three choices: (a) Lazy decode — decode per function on first access, not eagerly; trades memory locality for startup time. (b) RD as default — at 50% reachability, decodes half the bytes, halving the time to ~50 ms; further improved by lazy first-function. (c) Length-only fast pass — the Phase 2 length path at ≥150 MB/s can index all instruction boundaries in ~67 ms, then operand decode is lazy. The traded cost: the listing is not fully pre-decoded at startup; first-render latency per function is ~1 ms (acceptable for interactive use).

Q4. "How does RIP-relative addressing in mod=00, rm=101 differ from the 32-bit [disp32] case, and what bug does a decoder that confuses them introduce in the CFG?" (Resolves via: §8.1 + Phase 0.6 Pitfalls + Phase 4 CFG) In 64-bit mode, mod=00, rm=101 means [RIP + disp32] where RIP = address of the next instruction (addr + len). In 32-bit mode the same encoding means [disp32] (absolute address). A decoder that uses the 32-bit interpretation in 64-bit mode produces a wrong target address — typically pointing into unmapped memory. In the CFG, any RIP-relative data reference (lea rax, [rip+0x...]) with a wrong target fails symbolization (I9) and may cause the CFG builder to misidentify the operand as a branch target if the instruction is a jmp [rip+x] (indirect jump through a GOT slot) — wrong CFG edge, phantom or missing function call.

Q5. "Explain the precise sequence of bytes and decode states that makes VEX.vvvv 1's-complement (not direct). What bug class emerges if you forget the inversion?" (Resolves via: §8.1 VEX grammar + Phase 7.6 Pitfalls + Appendix E.4) In VEX encoding, the vvvv field is stored as the bitwise NOT of the register index. A 2-byte VEX prefix stores ~vvvv in bits [6:3] of byte 2; a 3-byte VEX stores ~vvvv in bits [6:3] of byte 3. To decode: src_reg = (~vvvv) & 0xF. If the decoder uses the raw field directly (no inversion): a vaddps ymm0, ymm1, ymm2 where vvvv encodes ymm1 as ~1 = 0b1110 would be read as register index 14 (ymm14) instead of ymm1. Bug class: silent wrong-register operand — the instruction length and mnemonic are correct, but the second source register is wrong. Differential testing (ADR-015) catches this immediately because objdump inverts correctly.

Q6. "Why is the visited set in recursive descent keyed by address and not by (address, decoder_state)? Under what obfuscation does address-keying cause false non-termination prevention (missed real code)?" (Resolves via: Phase 3.2 + Phase 10 + Threat Model + I6) Address-keying is sufficient because x86-64 decode is deterministic given the byte sequence (I3): the same address always produces the same instruction. Decoder-state keying would only matter if two different (address, state) pairs produced different instructions — which cannot happen in a stateless byte-to-instruction mapping. The obfuscation that breaks address-keying: a self-modifying code region where the bytes at an address change between visits. In a static disassembler this is a documented non-goal (Threat Model: self-modifying code is a fundamental limit). In a dynamic context (#74 debugger), address+execution-count keying would be needed.

Q7. "I7 requires every CFG edge to have a decoded terminator at the source block's end. Name three instruction classes that could generate phantom edges if misclassified." (Resolves via: §7 Invariants + Phase 4.6 Pitfalls + §9 ADR-008) (a) call instructions: a call emits a CallEdge and a FallThrough to the instruction after it (the return site). If the call is to a noreturn function (e.g., exit, abort) and the decoder does not know this, it emits a phantom FallThrough edge to dead/data bytes. (b) jmp instructions classified as Seq: if a direct or indirect jmp is misclassified as a sequential instruction, the block continues past it, generating a spurious fall-through edge to the next instruction (which is not reachable). (c) int3 or ud2 traps: these are unconditional terminators (the program does not continue past them), but if decoded as Unknown without setting Flow = Int/Unknown, the block may emit a fall-through edge to data or padding bytes.

Q8. "A jump table uses entries that are RVA deltas (offsets from the table base, not absolute addresses). Walk through how Phase 5's pattern matcher must differ from the absolute-address case." (Resolves via: Phase 5.2 + Phase 5.6 Pitfalls + §8.3 CFG model) Absolute entries: target = table[idx] (read a u64 directly as an address). RVA-delta entries: target = table_base + table[idx] (read a i32/u32 delta, add to table base address). The pattern matcher must: (1) detect the delta form by recognizing the add instruction before the jmp (e.g., lea rax, [table]; movsxd rcx, [rax+idx*4]; add rcx, rax; jmp rcx); (2) read entries as i32/u32 (not u64); (3) add the table base VMA (not just the file offset) to each delta. If the matcher reads raw u32 as absolute addresses, every target points into low memory (near address 0) → phantom CFG edges to invalid addresses, failing I8.

Q9. "Why does the round-trip invariant I10 only apply to the 'decidable subset' and not all decoded instructions? Name three x86 instruction classes that cannot round-trip." (Resolves via: Phase 8 + §7 I10 + §8.1 grammar) Round-trip requires re-encoding to produce identical bytes. This fails when: (a) Non-canonical encodings: an instruction can be encoded multiple ways (e.g., xchg eax, eax as 0x90 vs. 87 C0; nop as 0x90 vs. multi-byte 0F1F/00). Re-encoding produces the canonical form, not the original. (b) Redundant REX prefixes: a REX byte with W=0, R=0, X=0, B=0 is legal but meaningless; the re-encoder drops it. (c) Segment overrides on 64-bit code: a CS: prefix on a mov in 64-bit mode is ignored but present in the original bytes; re-encoding omits it. The "decidable subset" is the set of instructions where canonical encoding is unique — approximately all common integer and SSE instructions without redundant prefixes.

Q10. "Explain how the call graph built in Phase 6 differs from the CFG, and why #335 needs both." (Resolves via: Phase 4 CFG + Phase 6 call graph + §1 Goal) The CFG has basic blocks as nodes and intra-function control flow (branches, falls) as edges; it is intra-procedural. The call graph has functions as nodes and call edges as edges; it is inter-procedural. #335 needs the CFG for structuring (if/loop/switch recovery) — the CFG within each function. It needs the call graph for inter-procedural analysis: dead-function elimination, inline candidates, call-chain depth, and noreturn propagation (a function that only calls exit is itself noreturn, which feeds back into CFG edge pruning). An edge that appears in the call graph (A calls B) does not appear in A's CFG (the CallEdge exits A's function scope); the RetEdge is elided in the call graph. Together they form the complete inter+intra-procedural program structure #335 needs.

Q11. "A stripped binary has no symbols. How does the disassembler discover function boundaries, and what is the precision/recall tradeoff vs. a symbol-rich binary?" (Resolves via: Phase 3.2 seeds + Phase 6.8 Edge Cases + Phase 10.2 + Appendix M) Seeds without symbols: (a) binary entry point (ELF e_entry or PE AddressOfEntryPoint); (b) call targets discovered during RD (every call rel32 target is a probable function entry); (c) endbr64 markers (CET-enabled binaries — Appendix N.2); (d) prologue patterns (push rbp; mov rbp,rsp — Appendix M.3, heuristic). Precision: high for (a)/(b) — a call target is almost certainly a function entry (tail calls are the exception). Recall: lower than symbol-rich — indirect calls (via PLT stubs or function pointers) may not be seeded; functions called only via virtual dispatch are missed entirely. Symbol-rich binary: recall approaches 100% (every exported symbol is a seed); stripped binary: recall ≈ 60–80% depending on indirect-call frequency (Andriesse 2016 §5 measures this).

Q12. "The SIB special case base=101 + mod=00 means disp32 with no base. What happens if you implement this as [rbp+disp32] instead, and which invariant does it violate?" (Resolves via: §8.1 + Phase 0.6 + Phase 1.6 + I8) [rbp+disp32] adds the current value of rbp (a frame pointer) to disp32 — a runtime-dependent address. [disp32] (the correct interpretation) is an absolute address (zero-extended to 64-bit in 64-bit mode — effectively a 32-bit absolute). The wrong implementation produces a memory operand whose target address is wrong at decode time (it depends on the unknown rbp value). This violates I8: the decoded operand value does not equal the actual memory target. In the CFG, if the instruction is a jmp [SIB], the CFG builder sees a wrong IndirectJump operand, making it impossible to resolve the jump table correctly (Phase 5). Detection: any fixture with [array_base + 0] (disp32=base address, no base register) will produce a wildly wrong address in the listing — caught by differential in Phase 0.

Q13. "Describe how Kruegel 2004's findings about linear-sweep vs. recursive-descent accuracy directly shaped design principle P3 and Phase 3's acceptance criteria." (Resolves via: §5 Required Reading + §6 P3 + Phase 3.4) Kruegel 2004 (USENIX Security) demonstrates that linear sweep misdisassembles obfuscated code by decoding data bytes as instructions, and that recursive descent avoids this by following only reachable paths — but at the cost of missing code reachable only via indirect branches. This finding directly justifies P3 ("Two strategies, explicit tradeoff") by showing neither strategy is universally superior — the right choice depends on the binary (firmware vs. obfuscated userspace). It shapes Phase 3's acceptance criteria: "recovered functions ⊇ symbol functions" is the recall metric (RD must cover everything a symbol table claims); "fewer desync artifacts than sweep on data-interleaved code" is the precision metric derived directly from Kruegel's measurement. The gap-fill sweep in N.4 is the synthesis: RD for accuracy, sweep for coverage.

Q14. "What makes the differential harness (ADR-015) structurally different from text-diff of objdump output, and why does the structured comparison catch more real bugs?" (Resolves via: §9 ADR-015 + Phase 11.2 + Appendix O) Text-diff compares full output lines including formatting, spacing, symbol names, and hex address formatting — a cosmetic difference (e.g., 0x0000000000001149 vs. 1149) appears as a failure. The structured harness (ADR-015): (1) parses both outputs into (addr, mnemonic, operand[]) tuples; (2) applies the Appendix O normalization rules (hex case, spacing, RIP-relative resolution); (3) compares field-by-field. Bugs caught only by structured comparison: a wrong register index (e.g., rcx vs. rdx) in a correct-looking line — text-diff catches it only if the field offset differs; if objdump prints %rcx and we print %rdx, a text-diff on Intel syntax (no sigils) with rcx at the same column catches it, but structured comparison catches it regardless of formatting. More critically: wrong sign-extension of a displacement (0x-4 vs. 0xfffffffffffffffc) normalizes to the same i64 value in structured comparison, avoiding false positives, while text-diff would flag it as a mismatch.

Q15. "If you had to add RISC-V as a third ISA, list every file/type/phase that changes and every file/type/phase that is unchanged. What does this reveal about the Decoder trait seam?" (Resolves via: §3 Architecture + Phase 9 + §11 Core Types + ADR-024) Changes: crates/dis-rv64/ (new crate, new Decoder impl); Cargo.toml workspace (add crate); dis-cli/main.rs (add --arch riscv64 dispatch); Mnemonic enum (add RV64 mnemonics — minor version bump per ADR-022); Reg enum (add RISC-V registers — minor bump); conformance/rv64/ (new fixtures); fuzz/fuzz_targets/decode_rv64.rs; docs/encoding/rv64.md; CI matrix (add rv64 differential). Unchanged: dis-types (Flow, Operand, BasicBlock, Cfg structures unchanged — RISC-V fits the same model); dis-cursor (ISA-agnostic byte reader); dis-sweep, dis-rd (work off Decoder trait — no change); dis-cfg (works off Flow + Instruction — no change); dis-sym (works off addresses + #333 — no change); dis-print Intel/AT&T formatters for x86 (unchanged; a new dis-print-rv64 would be added). Reveal: the Decoder trait seam is real — the CFG, RD, sweep, and symbolization pipeline is ISA-agnostic. Adding an ISA requires only: a new decoder crate, new mnemonics/registers, and new fixtures. The pipeline above the seam is zero-change.

Q16. "The capacity model shows ≥30 M instr/s is achievable. What three low-level implementation choices produce most of this throughput, and which phase validates them?" (Resolves via: Back-of-Envelope Capacity Model + Performance Engineering + Phase 0.7 + Phase 11.7) (1) Flat array-indexed opcode tables: OPCODE_MAP_1[opcode] is a single array dereference — O(1), branch-free, cache-hot (17 KB fits in L1). Versus a match tree with N branches: the array avoids branch mispredictions on the hot path. Validated: Phase 0.7 performance note + Phase 11.7 criterion bench. (2) SmallVec<[Operand;4]> inline storage: typical instructions have ≤4 operands; the SmallVec stores them on the stack frame of the decode call, eliminating heap allocation per instruction. At 50 ns/instr, a malloc (~30 ns) would consume 60% of the budget. Validated: Phase 0.7, ADR-011. (3) Zero-copy byte cursor (&[u8] slice): the cursor reads directly from the mmap'd region without copying. The decode function borrows a reference to the original bytes for Instruction::bytes. Validated: Phase 0 design (ADR-004) + soak memory check Phase 11.

Q17. "Explain why (bad) + advance-1 (not advance-to-next-valid-opcode) is the principled resync choice. What adversarial scenario does 'skip-to-valid' enable?" (Resolves via: P8 + Phase 2.2 + Appendix F + Threat Model) (bad) + advance-1 is unbiased: it makes no assumptions about the intent of the byte stream. "Skip to next valid opcode" scans forward until it finds a byte that could start a valid instruction — but in x86-64, nearly every byte value is a valid opcode start (0x00 = add [rax],al; 0xFF = inc/dec/call/jmp r/m). An attacker who knows the skip heuristic can craft a byte stream where the "next valid" byte after each trap lands on their chosen instruction, effectively controlling the disassembler's view of the code while the actual execution path (via the attacker's jmp) differs. Advance-1 limits blast radius to a single byte per (bad) and guarantees recovery within x86's 15-byte max instruction length — provably bounded, provably unbiased.

Q18. "Why are PLT stubs a symbolization challenge, and how does Phase 6's JUMP_SLOT relocation walk resolve them without parsing the dynamic linker?" (Resolves via: Phase 6.2 + Phase 6.6 Pitfalls + §8.3 + I9) A PLT stub is a small code sequence in .plt that looks like: jmp [GOT+offset]; push N; jmp PLT0. The first jmp is an indirect call through the GOT (Global Offset Table); the GOT slot is initially populated by the dynamic linker with the stub address itself (lazy binding). The target of a call to the PLT stub is the PLT's virtual address — which has no direct symbol in the static symbol table. Resolving it requires reading .rela.plt (the relocation section): each JUMP_SLOT relocation entry maps a GOT offset to an imported symbol name. Phase 6 walks .rela.plt (available from #333's BinaryImage::relocations()) to build a map {plt_stub_addr → symbol_name}. When symbolizing a call target that lands in .plt, the map is consulted. This avoids parsing the dynamic linker: the relocation records are static, present at link time, and fully sufficient to resolve PLT stubs without runtime information.

Q19. "The CFG model says a block ends exactly at a control-flow terminator or a leader boundary. What happens to a block that ends at a leader boundary induced by a call target (not a branch)? Does it emit a fall-through edge?" (Resolves via: Phase 4.2 + Phase 4.6 + §8.3 CFG model + I7) A call target induces a leader (the instruction at the call target is the start of a new block in the callee's function). But the instruction after the call in the caller is also a leader (the return site). The block in the caller that contains the call instruction ends at the call terminator: its Flow is Call(target), which generates a CallEdge to the callee's entry block and a FallThrough edge to the return-site block (the block starting at the instruction after the call). This fall-through is correct: it models the fact that if the callee returns, execution continues at the return site. The fall-through is not emitted after jmp or ret (I7). The distinction: call is a returning terminator (FallThrough + CallEdge); jmp is a non-returning terminator (Jump edge only); ret is a non-returning terminator (RetEdge, no fall-through).

Q20. "How does the fuzz corpus seed strategy interact with the coverage % metric, and what would it mean for the project if fuzz found 0 panics but differential parity was 94% (below the 99.9% target)?" (Resolves via: Phase 10 + Phase 11 + §7 I2 + §4 constraints) Fuzz corpus seeds determine which code paths are exercised: seeds from real binaries (with REX+VEX, SIB specials, max-length instructions) give the fuzzer a head start on covering the decode state machine's edge transitions. Coverage % (of corpus instructions decoded to a known mnemonic, not fuzz code coverage) measures ISA completeness. The two metrics are orthogonal: 0 panics means I2 is satisfied (no crash on any bytes — robustness); 94% differential parity means I12 is violated for 6% of instructions (wrong mnemonic/operand — correctness). This state is a valid pre-release state (robustness is a hard gate; correctness is a coverage gap) but does NOT satisfy §4's ≥99.9% parity SLO. The project must identify which 6% of instructions are mismatched: if they are all (bad) for unimplemented opcodes, the problem is coverage (add table entries); if they are wrong mnemonic/operands for implemented opcodes, the problem is decode bugs (fix the decoder). The honest accounting rule (Appendix H.3) distinguishes these: (bad) counts as "not covered," not as a mismatch — so 94% parity on the covered set is a coverage gap, while 94% parity on the total set may mix coverage gaps with real bugs.

Alternative Architectures (Roads Not Taken)

Alt-A: Superset Disassembly (Decode Every Offset)

BinaryImage .text region
│
└─► for offset in 0..region.len():
      decode(region[offset..])  →  Instruction (or bad)
│
SmallVec<Option<Instruction>>  (one slot per byte offset)
│
└─► deduplicate + annotate: "instruction at 0x1000 also interpreted at 0x1001"

Winning regime: malware analysis and gadget search (#228) where completeness matters more than noise. A binary that uses overlapping instructions to hide a gadget is fully exposed by superset decode. Used by: Angr's CFGFast with force_complete_scan=True; BAP's superset_disasm module (Bauman 2018).

Why rejected as default: O(region) memory (one instruction slot per byte, not per instruction); output is ~3× larger than linear sweep; the CFG built on superset output contains phantom edges from data-decoded-as-code. Suitable as a flag (disasm --superset) exposed in Phase 10 for analyst use, not as the default pipeline.

Alt-B: LLVM TableGen / Automated Table Generation

x86.td (LLVM TableGen source, ~200k lines)
│
└─► llvm-tblgen ──► Rust codegen bridge
                         │
                         └─► OpcodeTables.rs  (500k+ lines generated)
                                  │
                                  └─► dis-x64 (generated decoder)

Winning regime: full ISA coverage including AVX-512, AMX, CET, APX (Intel's latest extensions) — all 1800+ x86-64 encodings. Used by: LLVM MCDisassembler (the differential oracle); iced (generates its Rust tables from a custom TableGen-like spec).

Why rejected: generated tables are opaque — a contributor cannot reason about an individual opcode's encoding without understanding the generator. The curated-subset-first approach (ADR-002) lets an implementer understand every row of the table and every decision in it. Full table-gen is the natural Phase 12+ growth path once the curated subset is validated and a table-coverage tool (tools/table-coverage) identifies the highest-frequency gaps.

Alt-C: Interpreted Bytecode / Aho-Corasick Opcode Matching

opcode_patterns.spec  (DSL: "0F 28 /r → movaps xmm, xmm/m128")
│
└─► pattern compiler ──► bytecode  ──► pattern VM
                                             │
                                             └─► decode(bytes) → Instruction

Winning regime: scripting-extensible disassemblers where users can add new opcodes without recompiling — Binary Ninja's LLIL lifter architecture uses a similar plugin-pattern approach; IDA Pro's processor modules are a compiled variant of this idea.

Why rejected: significant runtime overhead (VM dispatch per byte vs. single array index for table-driven); adds a bytecode VM to maintain and secure (a malformed opcode spec could crash the VM); and Rust's enum + match already provides compile-time pattern-matching at zero runtime cost — the "pattern matching" power is already native to the language. If a plugin/extensibility story is needed post-release, a DynDecoder trait impl loaded from a shared library is the Rust-idiomatic path without a custom VM.

Appendix F — Anti-Disassembly Catalog & Resync Analysis

Technique How it fools a sweep Our handling
Inline data after a jump bytes decoded as instructions recursive descent skips (not reachable); sweep flags length desync (I4)
Jump into the middle of an instruction two valid decodings overlap rd records the reachable interpretation; report overlap diagnostic
Opaque predicate (xor eax,eax; jz real) dead branch decoded both edges decoded; structuring (#335) prunes
Prefix padding / redundant prefixes length confusion 15-byte max-length cap; count prefixes once
jmp $+1 overlap traps desync byte-granular resync recovers within ≤15 bytes
Push/ret obfuscated call hides call edge flow-class sees ret; indirect edge flagged
Self-modifying code static view wrong documented limit; combine with #74 dynamic

Resync policy (principle 8): on (bad), advance exactly one byte and retry. Rationale: skipping to the "next plausible opcode" biases toward the obfuscator's intent and can hide real instructions; one-byte advance is unbiased and provably recovers alignment on x86 within at most 15 bytes (max instruction length) once past the offending region. Linear sweep + recursive descent disagreements are surfaced, not silently reconciled — the analyst (or #335) decides.

Appendix R — Pipeline Contract & Consumer Guarantees
