Language

Chosen

Rejected

Alt-A: Superset Disassembly (Decode Every Offset)

BinaryImage .text region
│
└─► for offset in 0..region.len():
      decode(region[offset..])  →  Instruction (or bad)
│
SmallVec<Option<Instruction>>  (one slot per byte offset)
│
└─► deduplicate + annotate: "instruction at 0x1000 also interpreted at 0x1001"

Winning regime: malware analysis and gadget search (#228) where completeness matters more than noise. A binary that uses overlapping instructions to hide a gadget is fully exposed by superset decode. Used by: Angr's CFGFast with force_complete_scan=True; BAP's superset_disasm module (Bauman 2018).

Why rejected as default: O(region) memory (one instruction slot per byte, not per instruction); output is ~3× larger than linear sweep; the CFG built on superset output contains phantom edges from data-decoded-as-code. Suitable as a flag (disasm --superset) exposed in Phase 10 for analyst use, not as the default pipeline.

Alt-B: LLVM TableGen / Automated Table Generation

x86.td (LLVM TableGen source, ~200k lines)
│
└─► llvm-tblgen ──► Rust codegen bridge
                         │
                         └─► OpcodeTables.rs  (500k+ lines generated)
                                  │
                                  └─► dis-x64 (generated decoder)

Winning regime: full ISA coverage including AVX-512, AMX, CET, APX (Intel's latest extensions) — all 1800+ x86-64 encodings. Used by: LLVM MCDisassembler (the differential oracle); iced (generates its Rust tables from a custom TableGen-like spec).

Why rejected: generated tables are opaque — a contributor cannot reason about an individual opcode's encoding without understanding the generator. The curated-subset-first approach (ADR-002) lets an implementer understand every row of the table and every decision in it. Full table-gen is the natural Phase 12+ growth path once the curated subset is validated and a table-coverage tool (tools/table-coverage) identifies the highest-frequency gaps.

Alt-C: Interpreted Bytecode / Aho-Corasick Opcode Matching

opcode_patterns.spec  (DSL: "0F 28 /r → movaps xmm, xmm/m128")
│
└─► pattern compiler ──► bytecode  ──► pattern VM
                                             │
                                             └─► decode(bytes) → Instruction

Winning regime: scripting-extensible disassemblers where users can add new opcodes without recompiling — Binary Ninja's LLIL lifter architecture uses a similar plugin-pattern approach; IDA Pro's processor modules are a compiled variant of this idea.

Why rejected: significant runtime overhead (VM dispatch per byte vs. single array index for table-driven); adds a bytecode VM to maintain and secure (a malformed opcode spec could crash the VM); and Rust's enum + match already provides compile-time pattern-matching at zero runtime cost — the "pattern matching" power is already native to the language. If a plugin/extensibility story is needed post-release, a DynDecoder trait impl loaded from a shared library is the Rust-idiomatic path without a custom VM.
