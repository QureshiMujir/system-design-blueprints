Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. "Why does treating 0x66 as always group-3 (operand-size) break SSE decoding, and where in the decode pipeline must mandatory-prefix disambiguation occur?" (Resolves via: §8.1 Domain Model + Phase 7.2 Steps + ADR-002) 0x66 is a group-3 prefix for integer ops (changes operand size from 32→16) but is the mandatory prefix selecting the 66 variant in the 0x0F map for SSE (e.g., 66 0F 6F = movdqa, not movdqu). Disambiguation must occur after the opcode byte is consumed: the opcode-map entry must carry a mandatory_prefix field, and the prefix is consumed as part of the opcode selection, not as a standalone operand-size modifier. Without this: movdqa misdecodes as a 16-bit integer op on whatever opcode follows 0x0F 0x6F — wrong mnemonic, wrong operands, wrong length.
  2. "An attacker supplies a binary where every jmp lands 1 byte into the previous instruction. How does each of the three strategies handle this, and what is the blast radius of each?" (Resolves via: Phase 2 resync + Phase 3 steps + Appendix F + Threat Model) - Linear sweep: decodes the first byte of each instruction correctly, then the jmp target (mid-instruction byte) as the start of the next instruction → desync; length-mismatch I4 flagged; entire region after the first jmp is misaligned. Blast radius: full region downstream of the first overlap. - Recursive descent: follows the jmp target (mid-instruction address) → decodes from that offset, which is a valid (different) instruction interpretation; visited-set ensures termination; the "canonical" instruction at the earlier address is also decoded if reachable from its own entry. Blast radius: function-local; both interpretations recorded and flagged as overlap. - Superset: decodes at every offset → both interpretations appear in the output; analyst must disambiguate. Blast radius: none structurally, but output is noisy (O(region) instructions).
  3. "The §4 startup budget is ≤30 ms for a 10 MB binary, but the capacity model shows sweep takes ~100 ms. What architectural choices resolve this, and what do they trade?" (Resolves via: §4 + Back-of-Envelope Capacity Model + Phase 2 + Phase 3) Three choices: (a) Lazy decode — decode per function on first access, not eagerly; trades memory locality for startup time. (b) RD as default — at 50% reachability, decodes half the bytes, halving the time to ~50 ms; further improved by lazy first-function. (c) Length-only fast pass — the Phase 2 length path at ≥150 MB/s can index all instruction boundaries in ~67 ms, then operand decode is lazy. The traded cost: the listing is not fully pre-decoded at startup; first-render latency per function is ~1 ms (acceptable for interactive use).
  4. "How does RIP-relative addressing in mod=00, rm=101 differ from the 32-bit [disp32] case, and what bug does a decoder that confuses them introduce in the CFG?" (Resolves via: §8.1 + Phase 0.6 Pitfalls + Phase 4 CFG) In 64-bit mode, mod=00, rm=101 means [RIP + disp32] where RIP = address of the next instruction (addr + len). In 32-bit mode the same encoding means [disp32] (absolute address). A decoder that uses the 32-bit interpretation in 64-bit mode produces a wrong target address — typically pointing into unmapped memory. In the CFG, any RIP-relative data reference (lea rax, [rip+0x...]) with a wrong target fails symbolization (I9) and may cause the CFG builder to misidentify the operand as a branch target if the instruction is a jmp [rip+x] (indirect jump through a GOT slot) — wrong CFG edge, phantom or missing function call.
  5. "Explain the precise sequence of bytes and decode states that makes VEX.vvvv 1's-complement (not direct). What bug class emerges if you forget the inversion?" (Resolves via: §8.1 VEX grammar + Phase 7.6 Pitfalls + Appendix E.4) In VEX encoding, the vvvv field is stored as the bitwise NOT of the register index. A 2-byte VEX prefix stores ~vvvv in bits [6:3] of byte 2; a 3-byte VEX stores ~vvvv in bits [6:3] of byte 3. To decode: src_reg = (~vvvv) & 0xF. If the decoder uses the raw field directly (no inversion): a vaddps ymm0, ymm1, ymm2 where vvvv encodes ymm1 as ~1 = 0b1110 would be read as register index 14 (ymm14) instead of ymm1. Bug class: silent wrong-register operand — the instruction length and mnemonic are correct, but the second source register is wrong. Differential testing (ADR-015) catches this immediately because objdump inverts correctly.
  6. "Why is the visited set in recursive descent keyed by address and not by (address, decoder_state)? Under what obfuscation does address-keying cause false non-termination prevention (missed real code)?" (Resolves via: Phase 3.2 + Phase 10 + Threat Model + I6) Address-keying is sufficient because x86-64 decode is deterministic given the byte sequence (I3): the same address always produces the same instruction. Decoder-state keying would only matter if two different (address, state) pairs produced different instructions — which cannot happen in a stateless byte-to-instruction mapping. The obfuscation that breaks address-keying: a self-modifying code region where the bytes at an address change between visits. In a static disassembler this is a documented non-goal (Threat Model: self-modifying code is a fundamental limit). In a dynamic context (#74 debugger), address+execution-count keying would be needed.
  7. "I7 requires every CFG edge to have a decoded terminator at the source block's end. Name three instruction classes that could generate phantom edges if misclassified." (Resolves via: §7 Invariants + Phase 4.6 Pitfalls + §9 ADR-008) (a) call instructions: a call emits a CallEdge and a FallThrough to the instruction after it (the return site). If the call is to a noreturn function (e.g., exit, abort) and the decoder does not know this, it emits a phantom FallThrough edge to dead/data bytes. (b) jmp instructions classified as Seq: if a direct or indirect jmp is misclassified as a sequential instruction, the block continues past it, generating a spurious fall-through edge to the next instruction (which is not reachable). (c) int3 or ud2 traps: these are unconditional terminators (the program does not continue past them), but if decoded as Unknown without setting Flow = Int/Unknown, the block may emit a fall-through edge to data or padding bytes.
  8. "A jump table uses entries that are RVA deltas (offsets from the table base, not absolute addresses). Walk through how Phase 5's pattern matcher must differ from the absolute-address case." (Resolves via: Phase 5.2 + Phase 5.6 Pitfalls + §8.3 CFG model) Absolute entries: target = table[idx] (read a u64 directly as an address). RVA-delta entries: target = table_base + table[idx] (read a i32/u32 delta, add to table base address). The pattern matcher must: (1) detect the delta form by recognizing the add instruction before the jmp (e.g., lea rax, [table]; movsxd rcx, [rax+idx*4]; add rcx, rax; jmp rcx); (2) read entries as i32/u32 (not u64); (3) add the table base VMA (not just the file offset) to each delta. If the matcher reads raw u32 as absolute addresses, every target points into low memory (near address 0) → phantom CFG edges to invalid addresses, failing I8.
  9. "Why does the round-trip invariant I10 only apply to the 'decidable subset' and not all decoded instructions? Name three x86 instruction classes that cannot round-trip." (Resolves via: Phase 8 + §7 I10 + §8.1 grammar) Round-trip requires re-encoding to produce identical bytes. This fails when: (a) Non-canonical encodings: an instruction can be encoded multiple ways (e.g., xchg eax, eax as 0x90 vs. 87 C0; nop as 0x90 vs. multi-byte 0F1F/00). Re-encoding produces the canonical form, not the original. (b) Redundant REX prefixes: a REX byte with W=0, R=0, X=0, B=0 is legal but meaningless; the re-encoder drops it. (c) Segment overrides on 64-bit code: a CS: prefix on a mov in 64-bit mode is ignored but present in the original bytes; re-encoding omits it. The "decidable subset" is the set of instructions where canonical encoding is unique — approximately all common integer and SSE instructions without redundant prefixes.
  10. "Explain how the call graph built in Phase 6 differs from the CFG, and why #335 needs both." (Resolves via: Phase 4 CFG + Phase 6 call graph + §1 Goal) The CFG has basic blocks as nodes and intra-function control flow (branches, falls) as edges; it is intra-procedural. The call graph has functions as nodes and call edges as edges; it is inter-procedural. #335 needs the CFG for structuring (if/loop/switch recovery) — the CFG within each function. It needs the call graph for inter-procedural analysis: dead-function elimination, inline candidates, call-chain depth, and noreturn propagation (a function that only calls exit is itself noreturn, which feeds back into CFG edge pruning). An edge that appears in the call graph (A calls B) does not appear in A's CFG (the CallEdge exits A's function scope); the RetEdge is elided in the call graph. Together they form the complete inter+intra-procedural program structure #335 needs.
  11. "A stripped binary has no symbols. How does the disassembler discover function boundaries, and what is the precision/recall tradeoff vs. a symbol-rich binary?" (Resolves via: Phase 3.2 seeds + Phase 6.8 Edge Cases + Phase 10.2 + Appendix M) Seeds without symbols: (a) binary entry point (ELF e_entry or PE AddressOfEntryPoint); (b) call targets discovered during RD (every call rel32 target is a probable function entry); (c) endbr64 markers (CET-enabled binaries — Appendix N.2); (d) prologue patterns (push rbp; mov rbp,rsp — Appendix M.3, heuristic). Precision: high for (a)/(b) — a call target is almost certainly a function entry (tail calls are the exception). Recall: lower than symbol-rich — indirect calls (via PLT stubs or function pointers) may not be seeded; functions called only via virtual dispatch are missed entirely. Symbol-rich binary: recall approaches 100% (every exported symbol is a seed); stripped binary: recall ≈ 60–80% depending on indirect-call frequency (Andriesse 2016 §5 measures this).
  12. "The SIB special case base=101 + mod=00 means disp32 with no base. What happens if you implement this as [rbp+disp32] instead, and which invariant does it violate?" (Resolves via: §8.1 + Phase 0.6 + Phase 1.6 + I8) [rbp+disp32] adds the current value of rbp (a frame pointer) to disp32 — a runtime-dependent address. [disp32] (the correct interpretation) is an absolute address (zero-extended to 64-bit in 64-bit mode — effectively a 32-bit absolute). The wrong implementation produces a memory operand whose target address is wrong at decode time (it depends on the unknown rbp value). This violates I8: the decoded operand value does not equal the actual memory target. In the CFG, if the instruction is a jmp [SIB], the CFG builder sees a wrong IndirectJump operand, making it impossible to resolve the jump table correctly (Phase 5). Detection: any fixture with [array_base + 0] (disp32=base address, no base register) will produce a wildly wrong address in the listing — caught by differential in Phase 0.
  13. "Describe how Kruegel 2004's findings about linear-sweep vs. recursive-descent accuracy directly shaped design principle P3 and Phase 3's acceptance criteria." (Resolves via: §5 Required Reading + §6 P3 + Phase 3.4) Kruegel 2004 (USENIX Security) demonstrates that linear sweep misdisassembles obfuscated code by decoding data bytes as instructions, and that recursive descent avoids this by following only reachable paths — but at the cost of missing code reachable only via indirect branches. This finding directly justifies P3 ("Two strategies, explicit tradeoff") by showing neither strategy is universally superior — the right choice depends on the binary (firmware vs. obfuscated userspace). It shapes Phase 3's acceptance criteria: "recovered functions ⊇ symbol functions" is the recall metric (RD must cover everything a symbol table claims); "fewer desync artifacts than sweep on data-interleaved code" is the precision metric derived directly from Kruegel's measurement. The gap-fill sweep in N.4 is the synthesis: RD for accuracy, sweep for coverage.
  14. "What makes the differential harness (ADR-015) structurally different from text-diff of objdump output, and why does the structured comparison catch more real bugs?" (Resolves via: §9 ADR-015 + Phase 11.2 + Appendix O) Text-diff compares full output lines including formatting, spacing, symbol names, and hex address formatting — a cosmetic difference (e.g., 0x0000000000001149 vs. 1149) appears as a failure. The structured harness (ADR-015): (1) parses both outputs into (addr, mnemonic, operand[]) tuples; (2) applies the Appendix O normalization rules (hex case, spacing, RIP-relative resolution); (3) compares field-by-field. Bugs caught only by structured comparison: a wrong register index (e.g., rcx vs. rdx) in a correct-looking line — text-diff catches it only if the field offset differs; if objdump prints %rcx and we print %rdx, a text-diff on Intel syntax (no sigils) with rcx at the same column catches it, but structured comparison catches it regardless of formatting. More critically: wrong sign-extension of a displacement (0x-4 vs. 0xfffffffffffffffc) normalizes to the same i64 value in structured comparison, avoiding false positives, while text-diff would flag it as a mismatch.
  15. "If you had to add RISC-V as a third ISA, list every file/type/phase that changes and every file/type/phase that is unchanged. What does this reveal about the Decoder trait seam?" (Resolves via: §3 Architecture + Phase 9 + §11 Core Types + ADR-024)
  16. "The capacity model shows ≥30 M instr/s is achievable. What three low-level implementation choices produce most of this throughput, and which phase validates them?" (Resolves via: Back-of-Envelope Capacity Model + Performance Engineering + Phase 0.7 + Phase 11.7) (1) Flat array-indexed opcode tables: OPCODE_MAP_1[opcode] is a single array dereference — O(1), branch-free, cache-hot (17 KB fits in L1). Versus a match tree with N branches: the array avoids branch mispredictions on the hot path. Validated: Phase 0.7 performance note + Phase 11.7 criterion bench. (2) SmallVec<[Operand;4]> inline storage: typical instructions have ≤4 operands; the SmallVec stores them on the stack frame of the decode call, eliminating heap allocation per instruction. At 50 ns/instr, a malloc (~30 ns) would consume 60% of the budget. Validated: Phase 0.7, ADR-011. (3) Zero-copy byte cursor (&[u8] slice): the cursor reads directly from the mmap'd region without copying. The decode function borrows a reference to the original bytes for Instruction::bytes. Validated: Phase 0 design (ADR-004) + soak memory check Phase 11.
  17. "Explain why (bad) + advance-1 (not advance-to-next-valid-opcode) is the principled resync choice. What adversarial scenario does 'skip-to-valid' enable?" (Resolves via: P8 + Phase 2.2 + Appendix F + Threat Model) (bad) + advance-1 is unbiased: it makes no assumptions about the intent of the byte stream. "Skip to next valid opcode" scans forward until it finds a byte that could start a valid instruction — but in x86-64, nearly every byte value is a valid opcode start (0x00 = add [rax],al; 0xFF = inc/dec/call/jmp r/m). An attacker who knows the skip heuristic can craft a byte stream where the "next valid" byte after each trap lands on their chosen instruction, effectively controlling the disassembler's view of the code while the actual execution path (via the attacker's jmp) differs. Advance-1 limits blast radius to a single byte per (bad) and guarantees recovery within x86's 15-byte max instruction length — provably bounded, provably unbiased.
  18. "Why are PLT stubs a symbolization challenge, and how does Phase 6's JUMP_SLOT relocation walk resolve them without parsing the dynamic linker?" (Resolves via: Phase 6.2 + Phase 6.6 Pitfalls + §8.3 + I9) A PLT stub is a small code sequence in .plt that looks like: jmp [GOT+offset]; push N; jmp PLT0. The first jmp is an indirect call through the GOT (Global Offset Table); the GOT slot is initially populated by the dynamic linker with the stub address itself (lazy binding). The target of a call to the PLT stub is the PLT's virtual address — which has no direct symbol in the static symbol table. Resolving it requires reading .rela.plt (the relocation section): each JUMP_SLOT relocation entry maps a GOT offset to an imported symbol name. Phase 6 walks .rela.plt (available from #333's BinaryImage::relocations()) to build a map {plt_stub_addr → symbol_name}. When symbolizing a call target that lands in .plt, the map is consulted. This avoids parsing the dynamic linker: the relocation records are static, present at link time, and fully sufficient to resolve PLT stubs without runtime information.
  19. "The CFG model says a block ends exactly at a control-flow terminator or a leader boundary. What happens to a block that ends at a leader boundary induced by a call target (not a branch)? Does it emit a fall-through edge?" (Resolves via: Phase 4.2 + Phase 4.6 + §8.3 CFG model + I7) A call target induces a leader (the instruction at the call target is the start of a new block in the callee's function). But the instruction after the call in the caller is also a leader (the return site). The block in the caller that contains the call instruction ends at the call terminator: its Flow is Call(target), which generates a CallEdge to the callee's entry block and a FallThrough edge to the return-site block (the block starting at the instruction after the call). This fall-through is correct: it models the fact that if the callee returns, execution continues at the return site. The fall-through is not emitted after jmp or ret (I7). The distinction: call is a returning terminator (FallThrough + CallEdge); jmp is a non-returning terminator (Jump edge only); ret is a non-returning terminator (RetEdge, no fall-through).
  20. "How does the fuzz corpus seed strategy interact with the coverage % metric, and what would it mean for the project if fuzz found 0 panics but differential parity was 94% (below the 99.9% target)?" (Resolves via: Phase 10 + Phase 11 + §7 I2 + §4 constraints) Fuzz corpus seeds determine which code paths are exercised: seeds from real binaries (with REX+VEX, SIB specials, max-length instructions) give the fuzzer a head start on covering the decode state machine's edge transitions. Coverage % (of corpus instructions decoded to a known mnemonic, not fuzz code coverage) measures ISA completeness. The two metrics are orthogonal: 0 panics means I2 is satisfied (no crash on any bytes — robustness); 94% differential parity means I12 is violated for 6% of instructions (wrong mnemonic/operand — correctness). This state is a valid pre-release state (robustness is a hard gate; correctness is a coverage gap) but does NOT satisfy §4's ≥99.9% parity SLO. The project must identify which 6% of instructions are mismatched: if they are all (bad) for unimplemented opcodes, the problem is coverage (add table entries); if they are wrong mnemonic/operands for implemented opcodes, the problem is decode bugs (fix the decoder). The honest accounting rule (Appendix H.3) distinguishes these: (bad) counts as "not covered," not as a mismatch — so 94% parity on the covered set is a coverage gap, while 94% parity on the total set may mix coverage gaps with real bugs. ---

Mental Models & First Principles

Mental models predict how bugs arise and which tests catch them. Each model is stated as a claim, a prediction, and the bug class that appears without it.

MM1 — The decode state machine. An x86-64 instruction is a micro-FSM over prefix/opcode/ModRM/SIB/disp/imm bytes; the decoder is that FSM's interpreter. Predicts: every decode ambiguity maps to a state transition — mandatory prefix vs. group prefix is a fork at the opcode-map entry, not at the prefix byte. Bug class without it: treating 0x66 as always operand-size when it is a mandatory SSE prefix (produces wrong mnemonic for movdqu, movdqa). Applies: §8.1, Phase 0/1, Appendix N.1.

MM2 — Length-before-semantics. Knowing instruction length requires only the prefix/opcode/ModRM/SIB walk, not full operand materialization. Predicts: a separate fast path exists and is correct by design if it shares the prefix/opcode/ModRM walk with the full decoder. Bug: diverging length path and decode path create two sources of truth — a length of 5 while decode yields 4 is a latent desync. Applies: Phase 2, I4, ADR-002.

MM3 — Linear sweep vs. recursive descent as over/under approximation. Sweep is a superset (may include data bytes decoded as instructions); RD is a subset (may miss code reachable only via indirect branches). Predicts: neither is complete alone; best accuracy = RD plus gap-fill sweep. Validation: Andriesse 2016 measures exactly this tradeoff on real compiler output. Applies: Phases 3–5, Appendix N.4.

MM4 — CFG edges are typed and sound. An edge only exists if a decoded terminator implies it. Predicts: phantom edges from misclassified indirects are detectable by auditing every edge's source block terminal. Bug class: emitting a FallThrough edge after jmp (the block's Flow is Jump, not Seq) misleads #335's structuring. Applies: Phase 4, I7, ADR-008.

MM5 — Symbolization is a join, not inference. Names come only from #333's symbol table and relocation records. Predicts: stripped binaries show raw addresses, never invented names. Bug: guessing function names from prologue patterns (push rbp; mov rbp,rsp) produces plausible-looking but incorrect names — violates I9 and makes differential comparison unstable. Applies: Phase 6, I9, ADR-009.

MM6 — Resync is byte-granular and unbiased. Advance exactly 1 byte on bad decode. Predicts: recovery within ≤15 bytes (x86 max instruction length) once past the offending region. Failure mode: skipping to "next valid opcode" biases toward the obfuscator's intent — the byte that looks like a valid opcode after the junk may itself be a data byte placed there intentionally. Applies: Phase 0/2, P8, Appendix F.

MM7 — Differential correctness as the primary oracle. Self-tests cannot catch subtle misdecodes (wrong register index, off-by-one in sign-extension); only structured comparison to objdump/llvm-mc can. Predicts: any mnemonic/operand divergence from the oracle is a real bug, not a cosmetic difference. Implication: the conformance test suite is necessary but not sufficient; differential is the primary gate. Applies: Phase 11, ADR-015, Appendix O.

MM8 — Invariants as the decode contract. I1–I12 collectively define what "correct decode" means; a decoder that satisfies all 12 is correct by construction for the defined scope. Predicts: the fuzz + differential + round-trip suite is exactly the minimal set of tests that covers all 12 invariants (I2→fuzz, I4→length-resum, I7→edge-audit, I9→join-check, I10→round-trip, I12→differential). Applies: all phases; §7 Invariants.

Glossary · 48 terms · site-wide glossary

Disassembler
Tool that decodes machine-code bytes into instructions.
Linear sweep
Decode bytes sequentially from a start; fast, desyncs on inline data.
Recursive descent
Decode by following control flow from known entries; accurate, needs target resolution.
Superset disassembly
Decode at every offset; over-approximates, used for analysis.
Desync
Loss of instruction alignment (decoding data as code or wrong length).
Resync
Recovering alignment after a bad decode (advance one byte).
Opcode
The byte(s) selecting the operation.
ModRM
Byte encoding addressing mode + register/operand (mod, reg, rm).
SIB
Scale-Index-Base byte for complex memory operands.
REX
x86-64 prefix extending operand size/register fields (W,R,X,B).
VEX
AVX encoding prefix (2-/3-byte) selecting map/vvvv/L/pp.
Prefix
Modifier byte (lock/rep/segment/operand-size/address-size).
Displacement
Constant offset in a memory operand (i8/i32).
Immediate
Constant operand encoded in the instruction.
RIP-relative
x86-64 addressing relative to the next instruction pointer.
Mnemonic
Human-readable operation name (mov, add).
Operand
An instruction argument (register/immediate/memory/relative).
Instruction length
Byte size of an instruction (≤ 15 on x86).
Basic block
Maximal straight-line instruction sequence (one entry, one exit).
Leader
First instruction of a basic block.
CFG
Control-Flow Graph: blocks + typed edges.
Edge
CFG transition (fall-through/taken/not-taken/call/ret/indirect).
Fall-through
Sequential edge to the next block (after non-jump / after call).
Jump table
Compiler-generated indirect-branch dispatch table (switch).
Indirect branch
jmp/call through a register/memory (target not in the opcode).
Symbolization
Resolving target addresses to symbol names (via #333).
PLT/GOT
ELF lazy-binding stubs/tables; calls resolve through them.
IAT
PE Import Address Table; imported-call targets.
Call graph
Functions as nodes, calls as edges.
AT&T / Intel syntax
Two textual conventions (operand order, sigils, suffixes).
Round-trip
Re-encoding a decoded instruction to its original bytes (I10).
Anti-disassembly
Code crafted to mislead a disassembler (overlap, traps).
Cc
Condition code for conditional branches/sets.
Tail call
jmp to another function (no return) — a call-like terminator.
Decoder trait
The ISA seam letting x86-64/AArch64 share the pipeline.
Worklist
The pending-address queue driving recursive descent (§3).
Visited set
Addresses already decoded; guarantees rd termination (I6).
Gap-fill
A sweep pass over executable bytes recursive descent never reached.
Reachable code
Instructions reachable by following control flow from seeds.
Over-/under-approximation
Including data-as-code / missing real code in the recovered set.
Terminator
The control-flow instruction ending a basic block.
Dominator
A block on every path from entry to a given block (feeds #335).
Back-edge
A CFG edge to a dominating block (loop indicator).
Thunk
A tiny stub forwarding to another routine (e.g., PLT entry).
endbr64
CET landing-pad marking a valid indirect-branch target (entry hint).
Red zone
128 bytes below rsp usable by leaf functions (System V).
Shadow space
32 bytes reserved by the caller (Microsoft x64).
Coverage %
Fraction of corpus instructions decoded to a known mnemonic.
