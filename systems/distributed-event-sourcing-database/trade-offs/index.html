Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust (stable toolchain, MSRV pinned)

Rejected

Go, C++, Java

When the rejected choice is right

Go wins when team velocity matters more than allocation control and GC pauses are acceptable (< 50k events/s); C++ wins in embedded/kernel contexts where no runtime is allowed; Java/GraalVM wins when JVM ecosystem integrations dominate.

Why: Memory safety without GC; zero-cost abstractions; Tokio async; rich ecosystem for low-level I/O

ADR-02

Build system

Chosen

Cargo workspace (single Cargo.toml at root)

Rejected

Bazel, Buck

When the rejected choice is right

Bazel wins when the repo spans multiple languages (Rust + Go + Java) in a single monorepo requiring hermetic cross-language builds and remote caching at Google/Meta scale.

Why: Standard for Rust; monorepo support; no extra toolchain

ADR-03

Async runtime

Chosen

Tokio (multi-thread scheduler)

Rejected

async-std, smol, single-thread

When the rejected choice is right

Single-threaded runtime wins for latency-sensitive embedded systems where deterministic scheduling and zero cross-thread migration overhead outweigh parallelism; smol wins when binary size is paramount (IoT targets).

Why: Mature, production-proven; tokio::fs for async I/O; wide ecosystem compatibility

ADR-04

gRPC framework

Chosen

tonic + prost

Rejected

grpc-rs (C bindings), tarpc

When the rejected choice is right

grpc-rs (C bindings to grpc-core) wins when conformance with the official gRPC C-core interceptors and proxy integrations (Envoy xDS) is required; tarpc wins for internal trusted-boundary RPC where schema evolution is unnecessary.

Why: Pure Rust; code-gen from proto3; streaming support; H2 multiplexing

ADR-05

HTTP/REST layer

Chosen

axum (atop hyper)

Rejected

actix-web, warp

When the rejected choice is right

actix-web wins at extreme HTTP/1.1 throughput benchmarks (TechEmpower) where its actor model and per-core thread affinity outperform axum's composable extractors; warp wins for tiny codebases preferring a filter-combinator DSL over macros.

Why: Composable middleware; shares Tokio runtime; low overhead

ADR-06

Serialization — event payload framing

Chosen

Custom length-prefix + CRC32C (esdb-log)

Rejected

Cap'n Proto, FlatBuffers for WAL

When the rejected choice is right

Cap'n Proto wins when zero-copy in-place parsing of structured events (without a CRC scan) is the primary concern and a code-gen schema is acceptable in the hot path; FlatBuffers wins for shared-memory IPC where mmap is the transport.

Why: Direct control over binary layout; no schema dependency in hot path; CRC in frame

ADR-07

Serialization — RPC wire format

Chosen

Protocol Buffers 3 (prost)

Rejected

JSON, MessagePack, FlatBuffers

When the rejected choice is right

JSON wins when human-readable wire traffic is a hard requirement (debug-ability over a telnet/curl session without tooling); MessagePack wins for schema-less event stores where no code-gen step is tolerable and payload size matters more than field evolution.

Why: Compact; schema-versioned; field evolution; tonic native

ADR-08

Serialization — internal config/state

Chosen

TOML (config files), JSON (projection state)

Rejected

YAML, CBOR

When the rejected choice is right

YAML wins when the config DSL must support multi-document files, anchors, and inheritance (e.g., Kubernetes-style cluster config with complex override layers); CBOR wins when projection state is binary-heavy (embedding image bytes) and JSON base64 overhead is unacceptable.

Why: TOML: human-editable; JSON: projection state is user-facing

ADR-09

On-disk segment format

Chosen

Custom fixed-structure segments (esdb-log)

Rejected

RocksDB, LMDB, SQLite

When the rejected choice is right

RocksDB wins when the workload is mixed read/write with frequent point lookups and range scans across arbitrary keys (not sequential event numbers); LMDB wins for read-heavy workloads where copy-on-write B-tree with MVCC provides serializable reads without a write lock.

Why: Append-only by construction; no external lock manager; full control over fsync and CRC

ADR-10

Index persistence

Chosen

Custom sorted binary index files (per segment)

Rejected

BTreeMap serialized, SQLite

When the rejected choice is right

SQLite wins when the index must support ad-hoc SQL queries over event metadata (e.g., SELECT * FROM events WHERE event_type = 'X' AND created > T) that would require custom secondary-index logic otherwise.

Why: Co-located with segment; rebuild-from-scan on crash; no separate index daemon

ADR-11

Consensus / replication

Chosen

Raft (from-scratch in esdb-replication, using raft-rs or openraft crate)

Rejected

Paxos, Viewstamped Replication, Zab

When the rejected choice is right

Paxos (Multi-Paxos) wins in systems requiring decoupled leader election and log entry assignment (e.g., Chubby, Spanner) where flexibility in phase ordering matters; Zab wins when total-order broadcast with primary-backup semantics (ZooKeeper's model) is more natural than Raft's log abstraction.

Why: Understandable; strong safety proofs; log matching maps directly to esdb-log

ADR-12

Raft library dependency

Chosen

openraft (optional dependency) or bespoke thin layer

Rejected

raft-rs (etcd port), ratis

When the rejected choice is right

raft-rs wins when exact etcd behavioral compatibility (joint consensus wire format, pre-vote protocol version) is required for cross-cluster federation; ratis (Java) wins when the rest of the system is JVM-based and sharing an event loop with Netty is the goal.

Why: openraft actively maintained, pluggable storage; bespoke keeps binary lean

ADR-13

Stream concurrency control

Chosen

Per-stream RwLock + version compare in esdb-stream

Rejected

MVCC table, global lock, CRDT

When the rejected choice is right

MVCC wins when concurrent reads vastly outnumber writes and readers must never block on writers (e.g., analytics workloads scanning millions of versions simultaneously); CRDTs win for geo-distributed eventual-consistency scenarios where merge semantics replace conflict rejection.

Why: Optimistic concurrency per stream; no cross-stream contention; aligns with P3

ADR-14

Snapshot storage

Chosen

Separate key-value store (sled or custom B-tree file) keyed by (stream_id, version)

Rejected

Same segment log, SQLite

When the rejected choice is right

Storing snapshots in the same segment log wins when the snapshot store must be replicated via Raft (log-structured replication) and isolation from the event log is operationally complex; SQLite wins when snapshot metadata queries (list by schema_version, size) outweigh the simplicity of flat files.

Why: Snapshots are large blobs; random access by key; separate from append-only log

ADR-15

Projection state storage

Chosen

sled or RocksDB per projection (pluggable backend)

Rejected

In-memory only, PostgreSQL

When the rejected choice is right

In-memory wins for ephemeral projections that are always rebuilt from scratch on restart and never need durability; PostgreSQL wins when the projection read model must be queryable by external services via SQL joins without an additional service boundary.

Why: Pluggable; projection state is disposable (P9); sled is pure Rust

ADR-16

Dependency policy

Chosen

Minimal curated deps; no transitive dep on openssl by default (use rustls)

Rejected

Permissive transitive deps

When the rejected choice is right

Permissive deps win when developer velocity and ecosystem breadth are the priority (e.g., rapid prototyping, internal tooling where supply-chain auditing is not required).

Why: Avoid supply-chain surface; compile time; no C deps in core

ADR-17

TLS

Chosen

rustls

Rejected

openssl, native-tls

When the rejected choice is right

openssl wins in FIPS-140-2 certified environments where the only approved path is an OpenSSL FIPS module (US federal, healthcare, finance); native-tls wins on macOS/Windows where integrating with the OS certificate store is a hard requirement (enterprise MDM).

Why: Pure Rust; no C FFI; FIPS-adjacent path via aws-lc-rs

ADR-18

Logging

Chosen

tracing crate (structured, async-aware)

Rejected

log + env_logger, slog

When the rejected choice is right

log + env_logger wins for simple CLI tools and libraries where async span context is unnecessary and binary size matters; slog wins in high-frequency logging scenarios where compile-time key-value drain selection (no dynamic dispatch) shaves measurable nanoseconds per log call.

Why: Span-based; integrates with tokio; pluggable subscriber (JSON for prod)

ADR-19

Metrics

Chosen

metrics crate + prometheus exporter

Rejected

OpenTelemetry metrics, statsd

When the rejected choice is right

OpenTelemetry metrics win when the observability pipeline must emit metrics, traces, and logs through a single vendor-neutral SDK to multiple backends (Datadog, Honeycomb, Grafana Cloud) without per-backend exporters; statsd wins in legacy environments where Graphite/InfluxDB pipelines already exist.

Why: Lightweight; runtime-agnostic registry; Prometheus scrape standard

ADR-20

Distributed tracing

Chosen

opentelemetry-rust + OTLP exporter

Rejected

Jaeger native, Zipkin

When the rejected choice is right

Jaeger-native wins when the deployment mandates Jaeger's internal data model (baggage, references) and OTLP conversion loses fidelity; Zipkin wins in Java-heavy microservice environments where the ecosystem already standardizes on Zipkin B3 propagation headers.

Why: Vendor-neutral; correlates gRPC spans to Raft and log I/O

ADR-21

Testing framework

Chosen

cargo test (unit/integration); proptest (property); tokio-test

Rejected

pytest, JUnit, criterion alone

When the rejected choice is right

pytest wins for cross-language protocol conformance testing (e.g., testing the gRPC server from a Python test harness using the official Python client); JUnit wins in Java-centric organizations sharing a single test infrastructure with Spring-based services.

Why: Proptest: QuickCheck-style; cargo test: zero config; criterion: micro-benchmarks

ADR-22

Fuzzing

Chosen

cargo-fuzz (libFuzzer) on segment reader, framing parser, concurrency paths

Rejected

AFL++, honggfuzz

When the rejected choice is right

AFL++ wins when multi-language fuzzing (C FFI boundary + Rust) is needed because AFL++ has broader language support and QEMU-based binary fuzzing for closed-source components; honggfuzz wins for persistence-mode fuzzing with custom mutators requiring tighter control than libFuzzer's API.

Why: Native Rust integration; coverage-guided; Phase 14 crash-recovery fuzz

ADR-23

Global position across partitions

Chosen

Per-partition independent position space; $all merge by position

Rejected

Single global position arbiter, hybrid logical clocks

When the rejected choice is right

A global arbiter wins when strict total order across all partitions is a hard client requirement (e.g., external auditing systems that must process every event in a single deterministic sequence); HLC (Hybrid Logical Clocks) wins for geo-distributed multi-datacenter deployments where a central arbiter's RTT is unacceptable.

Why: Arbiter = bottleneck; merge-sort is linearizable per-partition; cross-partition total order is advisory

ADR-24

Stream partitioning hash

Chosen

FNV-1a 64-bit of stream_id bytes mod num_partitions

Rejected

Consistent hashing (rendezvous), jump hash

When the rejected choice is right

Consistent hashing (rendezvous) wins when partition count changes frequently (scaling up/down in a cloud environment) and minimizing key remapping on topology change is critical; jump hash wins when partition count is known to be a power-of-two and uniform distribution across hardware is more important than minimal remapping.

Why: Simple; predictable; rebalancing is explicit reassignment, not ring movement

ADR-25

Benchmark harness

Chosen

criterion (microbenchmarks) + custom throughput bench (append/read p99)

Rejected

perf, hyperfine

When the rejected choice is right

perf + flamegraphs win when the primary goal is identifying hardware-level bottlenecks (cache misses, branch mispredictions) rather than tracking regression in a CI gate; hyperfine wins for command-line tool benchmarking where process-spawn overhead is the measurement target.

Why: Criterion: stable; statistical confidence intervals; HTML reports

ADR-26

CI/CD

Chosen

GitHub Actions; matrix over (stable, beta Rust); cargo clippy --deny warnings; cargo test

Rejected

Jenkins, CircleCI

When the rejected choice is right

Jenkins wins in air-gapped on-premises environments where GitHub Actions runners cannot reach the internet and a self-hosted CI server is required; CircleCI wins when Docker layer caching and parallelism controls are more sophisticated than GitHub Actions' current cache API.

Why: Standard open-source choice; caching via actions/cache

ADR-27

Container packaging

Chosen

Docker multi-stage (builder = rust:slim, runtime = distroless/debian-slim)

Rejected

Alpine, nix

When the rejected choice is right

Alpine wins when image size is the single priority and musl-libc compatibility is guaranteed (no glibc dynamic linking); Nix wins for fully reproducible builds with hermetic dependencies where the Nix store hash must match across all environments including developer laptops.

Why: Multi-stage: small image; distroless: minimal attack surface

ADR-28

Licensing

Chosen

MIT OR Apache-2.0 (dual)

Rejected

GPL, BSL

When the rejected choice is right

GPL wins when the goal is to require all derivative works to be open-source (copyleft protection for a community project); BSL (Business Source License) wins for a commercial event store that wants to prevent cloud providers from offering it as a managed service without a commercial agreement.

Why: Rust ecosystem standard; permissive for downstream use

ADR-29

Build reproducibility

Chosen

Cargo.lock committed; MSRV in Cargo.toml; pinned Docker base image digest

Rejected

Floating toolchain

When the rejected choice is right

Floating toolchain wins during rapid prototyping when always-latest dependencies are desired and reproducibility is not yet a requirement; this should be converted to pinned before any production release.

Why: Deterministic builds across CI and developer machines

ADR-30

Scavenge algorithm

Chosen

Offline segment rewrite with live-range bitmap (RoaringBitmap)

Rejected

In-place edit, log-structured merge

When the rejected choice is right

In-place edit wins in space-constrained environments where writing a second copy of the segment before swapping is impossible (disk < 2× segment size); log-structured merge (Kafka-style compaction by key) wins when the workload is key-value with updates (keep-last semantics) rather than append-only event sourcing.

Why: Append-only constraint preserved; bitmap compact; online scavenge via background task with pause

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Single-Node Relational Event Store (PostgreSQL + Append-Only Table)

  Client
    |
    v
 PostgreSQL
  ┌─────────────────────────────────────────────────────┐
  │  events(stream_id, event_number, global_seq, data)  │
  │  index on (stream_id, event_number)                 │
  │  index on global_seq                               │
  │  SERIAL global_seq (or sequences)                  │
  └─────────────────────────────────────────────────────┘
  Projections: polling SELECT WHERE global_seq > $cursor
  OCC: UPDATE streams SET version=N+1 WHERE version=N

Regime where it wins: teams with < 5,000 events/s, existing PostgreSQL operational expertise, no dedicated storage budget, and a requirement for ad-hoc SQL queries over event history. ACID transactions allow transactional outbox patterns without a separate inbox table. Schema migrations are familiar. Operational tooling (pg_dump, point-in-time recovery) is mature.

Real system embodying it: Marten (https://martendb.io/) — a .NET event store and document database built on top of PostgreSQL. Also used by many teams rolling their own events table.

Why this blueprint rejected it: PostgreSQL's WAL is not optimised for append-only workloads at high event rates. At ≥ 20,000 events/s, table bloat, VACUUM pressure, and index maintenance overhead become dominant concerns. The global sequence via SERIAL or sequences is a single serialisation point that caps append throughput. Sequential scan of an events table is far slower than direct segment-file scan at 500 MB/s (C11). Most critically, this architecture cannot achieve the §4.1 throughput targets without significant PostgreSQL tuning that brings it back toward the custom storage approach.

Alt-2 — Kafka-Backed Event Store (Kafka as Storage + Consumer Groups as Subscriptions)

  Client
    |
    v
  Event Store Service (thin wrapper)
    |         |
    v         v
  Kafka     State Store
  Topics    (RocksDB or Redis)
  ┌──────┐  ┌──────────────┐
  │stream│  │stream_versions│
  │ per  │  │(OCC checks)  │
  │topic │  └──────────────┘
  └──────┘
  Projections: Kafka Streams / consumer groups
  OCC: External lock service or optimistic CAS in state store

Regime where it wins: organisations already operating Kafka at scale, with existing Kafka expertise and tooling investment. Kafka's consumer group model provides competing-consumer subscriptions out of the box. At very high throughput (> 500,000 events/s), Kafka's partition-level write path (no per-stream lock) outperforms a per-stream-locked event store. Kafka's log.retention.ms and log.compaction provide time-based and key-based retention without custom scavenge logic.

Real system embodying it: several production DDD/CQRS implementations use Kafka as the underlying storage with a thin service layer for OCC and stream-level ordering. Confluent's "Event Sourcing with Kafka" reference architecture is a documented example.

Why this blueprint rejected it: Kafka has no native per-stream ExpectedVersion; implementing OCC requires an external state store (RocksDB, Redis, or PostgreSQL), introducing a second system and a new failure mode. Kafka's cross-partition ordering guarantees are weaker: there is no global position across topics/partitions without an external sequencer. Event replay for aggregate loading requires reading a full topic partition rather than a stream slice, which is expensive for streams with many events spread across a large partition. Kafka's operational model (Zookeeper/KRaft, broker configuration, ISR management) is significantly more complex than a purpose-built event store for teams that do not already operate Kafka.

Alt-3 — LSMT-Based Event Store (RocksDB as Storage Engine)

  Client
    |
    v
  Event Store Service
    |
    v
  RocksDB (embedded)
  ┌──────────────────────────────────────────────┐
  │  CF: events   key=(stream_id, event_number)  │
  │  CF: global   key=global_seq                 │
  │  CF: meta     key=stream_id, value=head_ver  │
  └──────────────────────────────────────────────┘
  Compaction: RocksDB native LSM compaction
  Replication: RocksDB + Raft via Tikv-style replication

Regime where it wins: workloads with high point-lookup rates (random reads by stream_id + event_number dominate over sequential scan), large numbers of small streams (RocksDB's bloom filters amortise point lookup cost), and teams that want to leverage RocksDB's battle-tested compaction logic rather than writing a custom scavenge. Also wins when the event payload is small (< 128 bytes) and the overhead of a custom framed log would be disproportionate.

Real system embodying it: TiKV (Rust + RocksDB + Raft) uses this architecture for general-purpose transactional key-value storage. CockroachDB uses a similar pattern (Pebble, a Go RocksDB port, as storage engine).

Why this blueprint rejected it: RocksDB's LSM compaction is not aware of event-sourcing access patterns. Sequential segment scan (the dominant access pattern for catch-up subscriptions) is faster on a custom append-only log than on RocksDB's SST files, which are optimised for random access. RocksDB's write amplification (typically 10–30×) is a poor fit for an append-only workload where the write amplification target is ≤ 1.05× (§4.1 storage amplification). Embedding RocksDB also couples the storage engine's version and build system to this project; the custom segment log (Phase 2) provides full control over the storage format and crash-recovery semantics without a dependency on a large C++ library (ADR-09).

Alt-4 — Immutable Ledger with Merkle-Chained Segments (Blockchain-Adjacent)

  Client
    |
    v
  Append Service
    |
    v
  Segment Chain
  ┌──────────────────────────────────────────────────────┐
  │  Segment N:  hash(events) + prev_segment_hash       │
  │  Segment N+1: hash(events) + hash(Segment N header) │
  │  ...                                                │
  │  Root hash published to external notarisation log   │
  └──────────────────────────────────────────────────────┘
  Audit: any client can verify chain integrity from genesis

Regime where it wins: regulated industries (finance, healthcare, supply chain) where tamper-evidence of the event log must be provable to a third party without trusting the operator. The Merkle chain allows an auditor to verify that a specific event was present in the log at a specific time using only the root hash and an inclusion proof, without downloading the full log. Also wins when the threat model includes a malicious administrator.

Real system embodying it: Amazon QLDB (Quantum Ledger Database) uses a cryptographically verifiable journal with a Merkle tree over all committed transactions. Hyperledger Fabric uses a similar ledger model for permissioned blockchains.

Why this blueprint rejected it: the Merkle chaining overhead is non-trivial: each segment seal requires a hash over all entries, adding O(segment_size) CPU cost per roll-over. More critically, the threat model for this blueprint (§ Threat Model) does not include a malicious operator; the adversaries are hardware failures, software bugs, and network partitions — not internal tampering. Adding Merkle proofs would increase segment roll-over latency (violating §4.1 p99.9 ≤ 50 ms under high roll frequency), complicate scavenge (deleting an event invalidates all subsequent segment hashes), and add implementation complexity with no benefit for the in-scope threat model. The CRC32C per-entry integrity check (Phase 2, ADR-09) addresses the actual threat (bit-rot, torn writes) without these costs.
