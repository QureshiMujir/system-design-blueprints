Back-of-Envelope Capacity Model

All numbers are derived step-by-step from the §4 System Constraints table. No number is asserted without derivation.

Input parameters (from §4.1):

  • Target sustained append rate (cluster leader): W = 10,000 events/s
  • Target sustained read/catch-up rate: R = 200,000 events/s
  • Average event payload: P = 512 bytes (typical domain event; §4 max = 4 MB, typical << 64 KB)
  • Event record wire overhead: H = 64 bytes (§4.4)
  • Global index entry size (position → offset): G = 12 bytes (§4.4)
  • Stream index entry size: S_entry = 16 bytes (§4.4)
  • Memory per idle stream: M_stream = 256 bytes (§4.1)
  • Segment file size: SEG = 256 MB (§4.1 default)
  • Scavenge I/O budget: ≤ 20% of append bandwidth (§4.1)

C1 — Raw write bandwidth (single node, no replication)

Bytes per event = H + P = 64 + 512 = 576 bytes
Sustained write bandwidth = W × 576 = 10,000 × 576 = 5.76 MB/s

At NVMe sequential write ≥ 500 MB/s (§4.1 recommendation): 5.76 MB/s uses ~1.15% of disk bandwidth. The disk is not the bottleneck at this event rate; fsync batching (group-commit window = 1 ms) dominates latency, not throughput.

C2 — Segment roll frequency

Time to fill one 256 MB segment = SEG / write_bandwidth
  = 256 MB / 5.76 MB/s ≈ 44.4 seconds

Segments roll approximately every 44 seconds at the sustained target rate. At peak double-rate (20,000 events/s): ~22 seconds. Segment roll-over adds at most one extra fsync (§4.1 p99.9 ≤ 50 ms accounts for this).

C3 — Global index RAM at 10^8 events

Index entries = 10^8
Memory = 10^8 × G = 10^8 × 12 bytes = 1,200 MB ≈ 1.2 GB

§4.1 target: ≤ 1 GB for 10^8 events at 10 bytes/entry. At 12 bytes/entry (§4.4 exact figure) this is 1.2 GB, slightly over the 1 GB target. The discrepancy is resolved by the sparse-index mitigation: one entry per 256 events reduces to 4.7 MB — well within budget.

C4 — Stream head index RAM at 10^7 streams

Memory = 10^7 streams × M_stream = 10^7 × 256 bytes = 2,560 MB = 2.5 GB

§4.1 target: ≤ 500 MB for 10^7 streams at ~50 bytes/stream. The §4.4 definition uses 16 bytes/entry (index entry only). The 256 bytes/stream in §4.1 covers the full in-memory stream-head record (version + segment pointer + dedup ring slice). At 10^7 streams, LRU eviction of cold streams to disk is required to meet the 500 MB target; active cold-stream eviction threshold ≈ 10^7 × 50 bytes = 500 MB.

C5 — Daily storage growth

Daily events = W × 86,400 s = 10,000 × 86,400 = 8.64 × 10^8 events/day
Daily bytes   = 8.64 × 10^8 × 576 bytes ≈ 497 GB/day ≈ 0.5 TB/day

At §4.1 storage amplification ≤ 1.05×: actual disk consumed ≤ 0.5 TB × 1.05 = 525 GB/day. At target retention of 30 days (configurable): ~15.75 TB of raw disk required before scavenging. Scavenge at 70% deleted-byte watermark can reclaim up to 70% of segments where events are tombstoned.

C6 — Scavenge I/O budget

Scavenge read+write bandwidth = 20% of append bandwidth
  = 20% × 5.76 MB/s = 1.15 MB/s
Segments scavenged per second = 1.15 MB/s / (2 × 256 MB) ≈ 1 segment per 445 seconds

One segment takes approximately 7.4 minutes to scavenge at the I/O-budget-limited rate. At daily roll rate of ~1,964 segments/day, the scavenger must process 1,964 segments/day = ~1.4 segments/minute to keep up. At the budget cap (1 segment per 7.4 minutes), scavenge lags production rate by ~10×. The mitigation is to widen the scavenge I/O budget during off-peak hours or to lower the 70% trigger watermark to reduce scavengeable segments.

C7 — Raft replication bandwidth (3-node cluster)

Replication bandwidth per follower = W × 576 bytes = 5.76 MB/s
Total replication bandwidth (leader → 2 followers) = 2 × 5.76 = 11.52 MB/s

On a 1 Gbps LAN (125 MB/s): replication uses ~9.2% of available bandwidth. At 10× burst (100,000 events/s): 115 MB/s — near saturation. NIC bonding or 10 Gbps interconnect is required above ~130,000 events/s.

C8 — Election timeout impact on availability

Leader failure window = election_timeout_max + quorum_ack_time
  = 300 ms + 500 µs ≈ 300.5 ms

Per §4.1 RTO ≤ 2 min (node failure): election adds ≤ 300 ms unavailability, well within RTO. At 10,000 events/s: events lost during election window (in-flight, not yet committed) ≈ 10,000 × 0.3 = 3,000 events that must be retried by clients (RPO = 0 for committed events per §4.1).

C9 — Subscription fan-out memory

Memory per active subscription = 64 KB (§4.1)
At 10,000 concurrent subscribers: 10,000 × 64 KB = 640 MB

This is a significant allocation. Per §4.1 target of 10,000 concurrent subscriptions per node, the subscription layer alone consumes 640 MB RAM. Combined with stream-head index (500 MB) and global index (sparse: 4.7 MB), total process RSS target ≈ ~1.5–2 GB for the steady-state server process.

C10 — Projection catch-up time for 10^8 events

Catch-up rate = 100,000 events/s (§4.1)
Time to replay 10^8 events = 10^8 / 100,000 = 1,000 s ≈ 16.7 minutes

A cold-start projection rebuild from 10^8 events takes ~17 minutes without snapshots. With snapshots at interval I = 1,000 events: worst-case tail replay = 1,000 events = 10 ms — negligible. Snapshot storage cost per aggregate: one snapshot per 1,000 events × (application-defined snapshot size ≤ 1 MB) = bounded by active-aggregate count.

C11 — Index rebuild on crash recovery (10^8 events)

Sequential scan bandwidth = 500 MB/s (NVMe, §4.1)
Total log size for 10^8 events = 10^8 × 576 bytes = 57.6 GB
Scan time = 57.6 GB / 500 MB/s = 115.2 s ≈ 1.9 minutes

§4.1 cold startup target ≤ 30 s for 10^8 events. A raw sequential scan at 500 MB/s takes 115 s, which exceeds the 30 s target. The resolution is the persisted index file: if the index file is valid (verified by tail-segment CRC check), startup uses the file directly, taking ≤ 5 s (§4.1 warm startup). The 30 s cold target therefore requires that the index file covers all but the last segment's tail (the tail-scan covers the remainder in ≤ 256 MB / 500 MB/s = 0.5 s).

C12 — Cross-partition $all merge overhead (P partitions)

Merge cost per delivered event = O(P log P), P = number of partitions
At P = 64 partitions, P log₂ P = 64 × 6 = 384 comparisons per event
At R = 200,000 events/s: 200,000 × 384 = 76.8 × 10^6 comparisons/s
At ~10^9 comparisons/s per core: 76.8 × 10^6 / 10^9 ≈ 0.077 cores

Cross-partition merge at 64 partitions and 200,000 events/s consumes < 0.1 CPU cores — negligible. The §4.1 cap of ≤ 1,024 partitions at 200,000 events/s: 1,024 × 10 × 200,000 / 10^9 ≈ 2 cores — still acceptable on an 8-core server.
