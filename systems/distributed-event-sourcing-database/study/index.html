Hard Questions (Self-Examination)

These questions require synthesis across two or more sections. They are the questions a staff-level reviewer would ask during a design review or on-call handoff.

HQ1 — If a leader crashes immediately after writing to its own log but before sending AppendEntries to followers, what happens to that entry, and where in the codebase is the resolution handled? The entry is uncommitted (commit_index has not advanced); after election, the new leader will have a higher term. The Log Matching Property (MM5, Phase 10, I7) ensures the new leader will overwrite this entry if its own log is authoritative. The resolution is in Phase 10's RaftLog::reconcile_with_leader() — followers truncate divergent tail entries on receiving AppendEntries with a conflicting prev_log_term.

HQ2 — Can a subscription deliver the same event twice without a client crash? Under what conditions, and which invariant governs this? Yes, during the catch-up/live transition (Phase 7) if the live-latch buffer is not drained before the subscriber's catch-up cursor reaches the transition point. This is governed by I3 (commit positions strictly increasing) and the live-latch design (Phase 7.2). The subscriber's idempotent EventId dedup (I6, Phase 1) is the client-side defence; the server cannot prevent the overlap without a per-subscriber ack protocol.

HQ3 — The §4.1 table claims append p99 ≤ 10 ms. The §4.2 latency budget sums to ~900 µs for p50. What accounts for the 10× gap to p99, and which phases are responsible for the tail? The p99 tail is dominated by fsync jitter (group-commit window ≤ 1 ms, but OS flush scheduling adds variance), segment roll-over (Phase 2, Phase 9), and lock contention under concurrent writers on the same stream (Phase 3, ADR-13). The 50 ms p99.9 includes segment roll-over (new segment creation + index flush). ADR-09 (custom segment format) and ADR-13 (per-stream lock) are the primary ADR decisions that constrain this budget.

HQ4 — If the scavenge operation (Phase 9) is interrupted mid-rewrite, what prevents data loss or a corrupted segment from being served to readers? Scavenge writes to a new segment file atomically renamed over the old one only after the new file is fully written and fsynced (Phase 9, I10, ADR-30). The RoaringBitmap live-range (Phase 9.2) is computed before the rewrite begins; any event present in the live-range bitmap is written to the new segment. An interrupted rewrite leaves the old segment intact (the rename never executes); on restart, the scavenge resumes from the last committed segment boundary.

HQ5 — How does the system ensure that a snapshot loaded for aggregate reconstruction is not stale with respect to the current projection schema? What happens if a stale snapshot is loaded? Snapshots carry a schema_version field (Phase 6, I9, ADR-14). On load, the aggregate loader compares snapshot.schema_version against the projection's compiled SCHEMA_VERSION constant. A mismatch causes the snapshot to be discarded and a full tail-replay to be performed from EventNumber(0). Without this check, folding new events onto a snapshot built from an incompatible state shape produces silently wrong aggregate state (MM7).

HQ6 — The capacity model (C4) shows the stream-head index at 2.5 GB for 10^7 streams but §4.1 targets ≤ 500 MB. What is the reconciliation mechanism and where is it implemented? LRU eviction of cold stream heads to disk (Phase 5, §4.1 mitigation column). The in-memory stream-head map evicts the least-recently-used entries when RSS exceeds the configured threshold. Evicted entries are serialised to the stream index file (Phase 5.2). On next access, the entry is promoted back to the in-memory map. This means a cold-stream read incurs one additional random disk seek (≤ 500 µs per §4.1 stream read p50 latency). See also C4 derivation in the Capacity Model.

HQ7 — What prevents two Raft leaders from simultaneously accepting writes (split-brain) after a network partition? Raft's quorum requirement (I7, Phase 11): a leader can only commit an entry if a majority of nodes (≥ 2 of 3) acknowledge it. During a network partition, the minority partition cannot form a quorum; its stale leader cannot advance commit_index. The majority partition elects a new leader with a higher term; the old leader's uncommitted entries are overwritten via the Log Matching Property (Phase 10, ADR-11). Leader leases (ADR-22) must be bounded by the election timeout to prevent stale leaders from serving reads after partition.

HQ8 — If a projection worker crashes after writing a read-model record but before checkpointing its cursor, what happens on restart, and which invariant makes this safe? On restart the worker loads the last committed checkpoint (Phase 8, I8). It replays from the checkpointed position, re-processing the already-applied events. I8 (deterministic projection replay) and I6 (EventId idempotency key) guarantee that re-processing the same events produces the same output. If the projection handler is side-effect-free with respect to external systems (§6 P9), the replay is safe. MM9 identifies non-deterministic handler state as the primary violation risk.

HQ9 — How does the consistent-hash ring in Phase 12 handle stream routing after a node leaves the cluster? What is the worst-case window of unavailability for streams owned by the departing node? On node departure, the virtual nodes assigned to it are redistributed to the remaining physical nodes (Phase 12, ADR-25). During redistribution, streams owned by the departing node's virtual nodes are unavailable until ownership transfer is complete (Phase 12.2 incremental rebalancing). Worst-case unavailability = time to elect a new Raft leader for the migrated partition + log catch-up time ≤ RTO = 2 min (§4.1). Active clients receive a PartitionMoved gRPC error and retry routing.

HQ10 — Can the global index become inconsistent with the segment log? Under what failure scenario, and how is it detected and repaired? Yes: if the process crashes after writing a segment entry but before updating the in-memory global index, the index will be behind the log. Recovery detects this via the tail-scan in Phase 9 (crash recovery, §4.1 crash recovery time ≤ 60 s): the recovery scanner reads the segment tail from the last known index entry, reconstructs missing index entries, and truncates any entry whose CRC32C is invalid (P3, Phase 2, ADR-09). The global index file is then rewritten from the in-memory reconstruction before the server opens for writes.

HQ11 — The system targets RPO = 0 for quorum-committed events. What is the RPO for an event that has been acked to the client but not yet replicated to a quorum follower? RPO = 0 applies only to quorum-committed events (§4.1: "Committed = quorum-durable"). An ack is sent to the client only after quorum commit (Phase 10, I7, ADR-11). Therefore there is no window where a client-acknowledged event is not quorum-durable. The single-node configuration (no Raft) has a different contract: ack-after-fsync only, RPO = 0 for single-node failure but positive RPO for total hardware failure.

HQ12 — What is the space complexity of the dedup ring per stream, and when does it fail to prevent duplicates? The dedup ring (Phase 1, I6, ADR-17) is a fixed-size circular buffer of recently-seen EventIds per stream. Its space is O(ring_size × UUID_size) = O(ring_size × 16 bytes). It fails to prevent duplicates when the retry interval exceeds the ring's time window (ring wraps before the duplicate arrives) — typically when a client retries after a delay longer than (ring_size / write_rate_per_stream). For a 1,000-entry ring and 100 writes/s per stream, the window is 10 s. Retries beyond 10 s after the original write may succeed as duplicates; clients are responsible for not retrying beyond this window or for using application-level idempotency.

HQ13 — Phase 4 assigns GlobalPosition values. Who assigns them in a multi-partition cluster, and how does this interact with the Raft leader? In a single-Raft-group deployment (Phases 1–11), the Raft leader assigns GlobalPosition as entries are committed to the Raft log (Phase 4, Phase 10, ADR-23). In a multi-partition cluster (Phase 12), each partition has its own independent position space; there is no globally unique position across partitions. The cross-partition $all subscription merges per-partition positions using a vector-clock-like tuple (Phase 12.2, C12). Clients that require strict cross-partition total order must use an external sequencer not in scope for this blueprint.

HQ14 — What distinguishes a "persistent subscription" from a "catch-up subscription" in this blueprint, and what additional failure mode does the persistent variant introduce? A catch-up subscription is stateless from the server's perspective: the client provides its starting position and the server streams from there (Phase 7). A persistent (competing-consumer) subscription has server-side state: the server manages the group's cursor, ack state, and message assignment among competing consumers (Phase 13). The additional failure mode is ack-loss: if a consumer crashes after processing but before acking, the event is re-delivered to another consumer in the group. This requires consumer-side idempotency (I6, I8) and a server-side nack/park mechanism (Phase 13.2).

HQ15 — The §5 Required Reading includes Ongaro's Raft paper (P1) and the Fisher-Lynch-Paterson impossibility result (via B1). How does the FLP impossibility constrain the election timeout design, and where is this reflected in the blueprint? FLP proves that in an asynchronous system with even one faulty process, no deterministic consensus algorithm can guarantee termination. Raft's resolution is randomised election timeouts (150–300 ms, §4.1): randomisation makes the probability of livelock arbitrarily small but does not eliminate it theoretically. The blueprint reflects this in Phase 11 (election timeout range chosen per Ongaro sec. 9.3 practical guidance) and ADR-11 (the 150–300 ms range is explicitly justified by Raft's empirical convergence, not by a theoretical bound).

HQ16 — If the segment index file is present but its last entry does not match the last entry in the segment log's tail, which takes precedence and why? The segment log (WAL) is the source of truth per MM1 and I1. The index file is a cache. On startup, the recovery scanner reads the segment tail from the index's last recorded offset and verifies each subsequent entry's CRC32C (Phase 2, Phase 9 crash recovery, ADR-09). Valid tail entries are added to the index; invalid entries cause truncation at the last valid entry. The index is then persisted. This means the index file's stale/corrupted tail is always overwritten by the ground truth in the segment log.

HQ17 — The blueprint targets 99.9% availability. What is the maximum permissible downtime per month, and does the RTO budget support it? 99.9% availability = 0.1% downtime = 43.8 minutes/month. RTO ≤ 2 min per node failure (§4.1). If failure frequency ≤ 21 failures/month ≈ 1 failure every 34 hours, the availability target is met. In practice, planned maintenance windows (rolling restarts during Phase 13 rolling upgrade) add to this budget; each node restart = 1 leader election (≤ 300 ms) + follower catch-up (bounded by RTO). The budget is tight for frequent deployments; blue/green partition rolling (Phase 14) is recommended to avoid consecutive elections.

HQ18 — Can two writers to the same stream both receive a success ack? Under what conditions would this be a correctness violation vs. expected behaviour? Yes — if both use ExpectedVersion::Any, both writes succeed regardless of the stream's current version. This is expected behaviour: Any explicitly opts out of OCC. It is a correctness violation only if the application's domain invariant requires a single-writer contract (e.g., aggregate state mutation). The distinction is documented in Phase 3 (I5, ADR-13): ExpectedVersion::Exact(N) enforces single-writer; Any is for append-only event logs where ordering doesn't matter for a given logical entity.

HQ19 — How does the blueprint handle backward-incompatible changes to the protobuf event schema across a rolling cluster upgrade? ADR-08 (semantic versioning for wire format) and Phase 13.2 (rolling upgrade protocol): protobuf wire-format compatibility requires that new fields use new field numbers (never reuse), old fields are never removed (only deprecated), and the schema_version field on AppendRequest gates deserialization behavior. During a rolling upgrade, nodes running old and new versions coexist; the leader must accept writes from clients using either schema version. Phase 14 (compatibility testing) validates this with a multi-version integration test harness.

HQ20 — The scavenge operation uses an atomic rename to replace a segment. What happens to readers that have an open mmap handle to the old segment file at the moment of rename? On Linux, rename(2) is atomic at the filesystem level; existing open file handles to the old inode remain valid until the last close (POSIX inode reference semantics). Readers with open mmap handles continue to access the old inode's data; no data is lost. After all readers close their handles, the old inode is reclaimed. This is the deliberate design in Phase 9 (ADR-30): the atomic rename + inode persistence makes scavenge transparent to concurrent readers without a read-lock on the segment.

HQ21 — What is the mechanism by which a newly elected leader discovers the GlobalPosition of the last committed event, and how long does this take? On election, the new leader reads its own Raft log to find the highest log_index with commit_index set by the previous leader (Phase 10, Phase 11, I7). The GlobalPosition is embedded in each Raft log entry (Phase 10.2). Discovery is O(1) — the leader reads commit_index from its persistent Raft state, then looks up the corresponding log entry. Total time: one disk seek to the Raft log index + one entry decode ≈ 500 µs (§4.1 stream read p50). The leader does not need to contact followers before advertising its GlobalPosition.

HQ22 — Why does the blueprint choose per-stream striped locks (ADR-13) over a single global lock or a lock-free approach? A single global lock serialises all stream writes, capping throughput at one writer regardless of CPU count — it would cap at far below the 20,000 events/s target (§4.1). Lock-free CAS (e.g., atomic compare-and-swap on a shared GlobalPosition counter) is feasible but requires careful ABA-protection and cannot easily enforce the full ExpectedVersion enum semantics (particularly NoStream and StreamExists checks). Per-stream striped locks (one RwLock per stripe bucket) allow O(cores) parallel writes across different streams while preserving the atomic CAS contract per stream. ADR-13 documents the lock-free alternative as the "When the Rejected Choice Wins" case for extreme write fan-out where per-stream lock overhead dominates.

HQ23 — How does the system ensure that a subscription does not consume unbounded memory if the subscriber is slow? Bounded channels between the log layer and each subscriber's delivery task (Phase 7, ADR-03). When the channel fills, the sender (log tail push) applies backpressure: it blocks on send rather than buffering. Each subscriber's channel is bounded at a configurable size (default: matches the 64 KB ack-window per §4.1). A subscriber that falls far behind triggers flow-control on the subscription worker, not on the append critical path. The subscriber receives a SlowConsumerWarning notification (Phase 13) and may be disconnected at the operator's configured lag threshold.

HQ24 — The blueprint mentions io_uring as optional. What is the specific performance advantage of io_uring for this workload, and why is it not the primary path? io_uring (Linux 5.1+) enables submission-queue-based async I/O that avoids per-syscall context switches for high-IOPS workloads. For the sequential-append workload (Phase 2), the primary bottleneck is fsync latency, not syscall overhead; io_uring's advantage is marginal for sequential writes. For random-read catch-up (Phase 5), io_uring can batch multiple segment reads and reduce latency at high concurrency. It is not the primary path because: (1) it requires Linux ≥ 5.1, reducing portability (§4.1 OS target: Linux primary, macOS dev); (2) the tokio-uring crate is not yet stable enough for production use (ADR-03).

HQ25 — If the blueprint's consistent-hash ring assigns stream S to partition P, but a client routes to partition Q (due to a stale ring view), what happens? The receiving node Q detects the ownership mismatch by checking its local ring state (Phase 12.2). It returns a PartitionMoved { correct_partition: P } gRPC error. The client's routing layer refreshes its ring view from the cluster metadata service and retries on partition P. The stale-ring window is bounded by the ring gossip propagation delay (Phase 12, gossip interval configurable). No data is written to the wrong partition; writes are always rejected on routing mismatch, never silently rerouted.

Mental Models & First Principles

These distilled models are the conceptual load-bearing beams of the system. Each is stated as a compressed expert insight; violation of any one produces a predictable class of bugs.

MM1 — The Log Is the Database Insight: the append-only segment log is not a transport for a "real" database elsewhere; it is the source of truth. Every other data structure (stream-head index, snapshots, projections) is a disposable cache of the log. Prediction: any path that loses a committed log entry is a correctness bug, not a consistency bug. Bug class without it: engineers treat the projection state store as authoritative and skip log replay on recovery, silently dropping events. Applied in: §7 I1–I4, §6 P2, Phase 2, Phase 9.

MM2 — Optimistic Concurrency Is a Contract, Not a Hint Insight: ExpectedVersion is a compare-and-swap published in the API contract. The server must atomically compare and append under the stream lock; relaxing this to "usually check, then write" creates a TOCTOU race that violates the DDD aggregate consistency boundary. Prediction: under concurrent writers the only serialisation errors should be WrongExpectedVersion; spurious successes are impossible if the CAS is atomic. Bug class without it: two concurrent writers both read version N, both pass the check, both write EventNumber N+1 — stream history branches. Applied in: §7 I5, Phase 3, ADR-13.

MM3 — Global Position Is a Clock, Not a Key Insight: GlobalPosition is a strictly monotone counter that acts as a logical clock for the whole cluster. Subscribers use it as a cursor; ordering across streams is established only through this counter. Prediction: any gap in GlobalPosition values signals a lost commit; any non-monotone position signals a replication safety violation. Bug class without it: read-model builders interleave events from different streams using wall-clock timestamps, producing non-deterministic projections. Applied in: §7 I3, Phase 4, Phase 7, ADR-23.

MM4 — fsync Before Ack Is Non-Negotiable Insight: an append that has been acknowledged to the client must survive a subsequent process crash. This requires fsync/fdatasync to complete before the ack is returned, not after. Group-commit amortizes the cost across a batch; the invariant cannot be traded away for throughput. Prediction: removing the pre-ack fsync converts a durable store into a lossy buffer; RPO becomes nonzero. Bug class without it: power-cycle under load loses the tail of the log silently; crash recovery finds a truncated segment with no evidence of the lost writes. Applied in: §7 I4, §4.2 latency budget, Phase 2, ADR-09.

MM5 — Raft Safety Requires Log Matching, Not Just Quorum Insight: Raft's quorum commit alone is insufficient; the Log Matching Property (if two logs have an entry with the same index and term, all preceding entries are identical) is what guarantees that a newly elected leader does not overwrite committed entries. Any deviation from Raft's AppendEntries consistency check breaks this. Prediction: a follower that accepts out-of-order entries will diverge silently; the cluster appears healthy until a leader election exposes the inconsistency. Bug class without it: follower accepts batch at log_index=N without verifying prev_log_index/prev_log_term; after election, new leader's log conflicts with durable committed entries. Applied in: §7 I7, Phase 10, Phase 11, ADR-11.

MM6 — The Catch-Up/Live Boundary Is a Safety Transition, Not a Convenience Switch Insight: the transition from catch-up replay (sequential scan) to live delivery (push from in-memory tail) must be gapless and overlap-free. The transition buffer (live-latch) must hold in-flight events during the handoff; neither dropping nor duplicating events is acceptable at this boundary. Prediction: a subscriber that misses the transition window sees a gap; one that does not drain the buffer sees duplicates. Idempotency alone does not cover gaps. Bug class without it: projection built on top of a gapped subscription computes a wrong aggregate count permanently, silently. Applied in: §7 I3, Phase 7, ADR-03.

MM7 — Snapshots Are Caches With Schema Versions Insight: a snapshot is a compressed replay of events up to a version; it is valid only if the projection's schema_version matches the snapshot's recorded schema_version. An incompatible snapshot loaded as if it were current silently corrupts the aggregate's in-memory state. Prediction: changing a projection's state shape without invalidating snapshots causes silent wrong reads until a full replay is forced. Bug class without it: after a schema migration, stale snapshots are loaded for existing aggregates; new events are folded onto wrong base state. Applied in: §7 I9, Phase 6, ADR-14.

MM8 — Scavenge Must Preserve Event Numbers and Positions Insight: scavenge rewrites segments to remove deleted events but must preserve the EventNumber and GlobalPosition of all surviving events unchanged. Subscribers and cursors are keyed to these values; renumbering surviving events after scavenge would invalidate all active cursors. Prediction: scavenge that renumbers events invalidates the O(10^4) active cursor checkpoints stored in subscriber state stores. Bug class without it: post-scavenge read returns event at position N where N was previously a deleted event; cursor-advancing logic skips or replays an event. Applied in: §7 I10, Phase 9, ADR-30.

MM9 — Determinism Is the Foundation of Exactly-Once Projection Insight: a projection achieves exactly-once semantics through idempotent deterministic handlers plus checkpointed cursors, not through deduplication locks. If the handler function produces the same output for the same input every time, replaying from checkpoint is safe. Any external side-effect or non-deterministic state in the handler breaks this contract. Prediction: a projection handler that generates a UUID on each call will produce different output on replay, corrupting the read model. Bug class without it: after a projection worker crash, checkpoint rollback triggers replay of the last N events; non-idempotent handler double-writes records. Applied in: §7 I8, Phase 8, §6 P9.

MM10 — Consensus Does Not Substitute for Idempotency at the Application Layer Insight: Raft guarantees that a committed entry is not lost; it does not prevent a client from retrying an append after a timeout (before it knows whether the previous attempt was committed). The server must therefore honour EventId-based deduplication at the storage layer to make client retries safe. Prediction: removing EventId dedup converts a retry into a duplicate append that violates the client's intent. Bug class without it: a network timeout causes a client to retry an AppendEvents call; the server appends the event twice; a projection counting events over-counts. Applied in: §7 I6, Phase 1, Phase 3, ADR-17.

Glossary · 40 terms · site-wide glossary

$all stream
The virtual stream comprising every event in the store in commit order; cursor is GlobalPosition.
Aggregate
A domain object reconstituted by replaying a StreamId's events; state = fold(events) or fold(snapshot + tail).
Append-only log
The fundamental storage primitive; records are written sequentially and never overwritten in place — see esdb-log.
At-least-once delivery
Subscription/projection guarantee: an event is delivered at minimum once; idempotency + checkpoint converts this to exactly-once effect.
Catch-up subscription
A subscription that first reads historical events from a stored Checkpoint position then transitions to live without gap; see esdb-subscribe.
Category
The StreamId prefix before the first - delimiter (e.g. order for order-1234); used for category streams and projection filters.
Changefeed
A live stream of committed events exposed to external consumers; implemented via catch-up + live subscription.
Checkpoint
{ subscription_or_projection, position: GlobalPosition } — the durable resume point ensuring a consumer can restart without re-reading from position 0.
Commit index
Raft term: the highest log index known to be quorum-durable; entries at or below this index are committed and GlobalPosition-assigned.
Commit position
The GlobalPosition assigned to an event when its Raft log entry reaches the commit index; the universal cursor for all readers.
Competing consumers
Multiple subscriber instances in a persistent subscription group sharing delivery load; each event is sent to exactly one consumer.
Compaction / Scavenging
Rewriting segments in esdb-storage to drop deleted, expired, or maxcount-exceeded events while preserving numbers/positions of live events.
CQRS
Command-Query Responsibility Segregation; append path (command) is separate from read-model path (query); natural fit with event sourcing.
Event
An immutable fact that has happened; represented as EventRecord; identified by EventId; versioned within its stream by EventNumber.
Event sourcing
Persisting aggregate state as an ordered log of domain events; state is derived by replaying the log, never stored as a mutable snapshot row.
Event store
A database optimised for event sourcing; core operations are append-with-version, read-stream, and subscribe-from-position.
EventRecord
{ event_id, stream, number, event_type, data: Bytes, metadata: Bytes, position, created } — the canonical persisted event; fields are immutable post-commit.
ExpectedVersion
enum { Any, NoStream, StreamExists, Exact(EventNumber) } — the caller's declaration of the stream version it expects; enforces optimistic concurrency.
Fold / Replay
Applying an ordered sequence of events to an initial state via a reducer function to produce aggregate state; state = fold(init, events).
fsync
Kernel call flushing dirty pages to durable storage; called after every segment append in esdb-log to satisfy P8 / I4.
GlobalPosition
u64 monotonic, unique commit offset in the global log; strictly increases; gap-free within a single-partition store; the merge key across partitions.
Idempotent handler
A projection/subscription event handler whose repeated application of the same event yields the same read-model state; required for at-least-once delivery.
Leader election
Raft mechanism: on heartbeat timeout a follower increments its term and requests votes; first node with quorum votes becomes leader.
Log matching
Raft safety property: if two log entries share the same index and term, all preceding entries are identical; guarantees follower convergence.
Optimistic concurrency
Concurrency strategy in which a writer declares its expected version; no pessimistic lock is held; a conflicting concurrent append is rejected by esdb-stream.
Partitioning / Sharding
Distributing stream ownership across cluster nodes (or Raft groups) by hashing StreamId; handled in esdb-partition.
Persistent subscription
A checkpointed subscription whose position survives restarts; supports competing consumers and ack/nack/park/retry.
Projection
A continuously-maintained read model built by applying an idempotent handler to events from $all or a category; checkpointed by GlobalPosition.
Quorum
(N/2)+1 nodes in an N-node Raft group; both elections and commit decisions require quorum acknowledgment.
Raft
Distributed consensus algorithm (Ongaro & Ousterhout 2014) used in esdb-replication to replicate the global log and elect a leader.
Read model
Derived queryable state produced by a projection; disposable and rebuildable from the log (P9).
Segment
A fixed-size file in esdb-log holding a contiguous slice of log records; rolled over at a size threshold; the unit of scavenging.
Snapshot
{ stream, version: EventNumber, state: Bytes, position } — a fold checkpoint stored by esdb-snapshot; loading uses newest snapshot + tail replay.
Soft delete / Tombstone
Marking a stream as deleted via a metadata event; the stream is inaccessible to normal reads; scavenging later removes the physical records.
Stream
A named, ordered, append-only sequence of events belonging to one logical aggregate; identified by StreamId; versioned by EventNumber.
StreamId
The logical stream / aggregate identity string; category is the prefix before -; hashed for partition routing.
Term
Raft monotonic election counter; incremented on each new election; guards against stale leaders and split-brain.
Volatile subscription
An in-memory subscription with no checkpoint; delivers only events appended after subscription creation; lost on subscriber restart.
WAL
Write-Ahead Log semantics; in esdb-log, each append is persisted (fsynced) before the write is acknowledged, enabling crash recovery.
WrongExpectedVersion
The error returned by esdb-stream when the current stream version does not match the caller's ExpectedVersion; write is rejected, nothing committed.
