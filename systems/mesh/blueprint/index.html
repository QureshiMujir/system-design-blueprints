9 — Mesh

Project Number: 9

Project Name: Mesh

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Mesh is a cross-application permission graph and OAuth-grant control plane. It enumerates a tenant's third-party authorizations — OAuth scopes, API keys, service-account credentials, agent delegations — across every connected SaaS provider, normalizes them into a single Permission Graph Schema (PGS, §8), detects drift between granted and actually-needed access, supports reviewable bulk revocation, and exposes an open publish/subscribe protocol so downstream applications can consume permission state without re-deriving it. Mesh is an observational and remedial system: it reconciles what providers report, it never decides who is allowed to do what at request time (P1).

Phase-0 deliverable (in-scope, minimum viable slice):

  1. Connector runtime + SDK conformance harness (no live connectors yet).
  2. Two reference connectors (Google Workspace, GitHub) implementing enumerate + incremental cursor only — no revoke, no write scopes.
  3. Permission Graph Schema v0 store (Postgres) with tenant isolation.
  4. A CLI query surface (meshctl query) sufficient to answer "what does identity X hold."
  5. CI + conformance suite gate (a connector cannot merge without passing it).

System boundaries:

  • Provides: enumeration of existing grants, canonicalization of provider-specific scope strings, a queryable graph of identity → grant → resource, drift signals, revocation execution with confirmation receipts, a versioned wire protocol for permission-state publish/subscribe.
  • Delegates: authentication of end users (to the customer's IdP — Okta, Entra ID, Google); the authorization decision at request time (to the resource owner's own access-control layer); secret generation and rotation policy (to the customer's secrets manager); network segmentation (to the customer's ZTNA/firewall layer).
  • Does NOT provide: a service mesh (no request-time L4/L7 proxying, no mTLS sidecar, no east-west traffic control — despite the name collision with the service-mesh category); identity-provider functionality (no password storage, no primary-factor authentication, no SSO issuance); secrets-manager functionality (no secret generation, no dynamic secret leasing — Mesh stores only encrypted handles to credentials it observes, §11 CredentialHandle).

Non-goals, explicit: this is not a service mesh; not an IdP; not a secrets manager. Mesh observes and revokes access relationships that other systems already administer.

Deployment model: multi-tenant hosted control plane (default) or single-tenant self-hosted appliance (enterprise, PhaseDeferred("Phase 11")). Connectors run as isolated worker processes per tenant-connector pair, no shared execution context across tenants (I10, I11).

Target users/operators: security/IT teams operating the control plane console; connector authors (first-party and community) building against the connector contract (§8); downstream application engineers consuming the publish/subscribe protocol (§8.6) to react to grant changes without polling providers directly.

What later phases unlock: Phase 5 (drift detection) unlocks continuous over-grant signal; Phase 6–7 (revocation, bulk revoke) unlock remedial action; Phase 8 (protocol server) unlocks third-party consumption without direct provider polling; Phase 10 (agent identities) unlocks delegation-chain accountability for autonomous agents, the fastest-growing class of grantee.

Language: TypeScript (Node.js LTS runtime) for the connector framework, protocol server, graph-store access layer, and SDK. Rationale: the Permission Graph Schema must be a single set of types shared, without cross-language codegen drift, between the core engine and every connector author (first-party or community); the OAuth/SCIM client ecosystem across the providers Mesh must speak to (Google, GitHub, Slack, Microsoft Graph, Notion, Okta) is TypeScript/JavaScript-first, minimizing per-connector translation cost. Rejected: Go — excellent for a single static binary, but no shared-schema story across a plugin ecosystem without a code-generation step per connector language, which raises the bar for community contribution (ADR-01 rejects this at the same tradeoff point OpenFGA's Go core accepts). Rust — best raw throughput and memory safety for the graph-traversal hot path, rejected in Phase 0 because it triples connector-author onboarding cost for the community-contribution goal of Phase 8; revisited only if M4/M5 (§30) are missed on the TypeScript implementation. Python — fastest prototyping, rejected because its OAuth/SCIM client ecosystem for enumeration workloads is weaker than Node's and its type system does not enforce the PGS contract at compile time the way TypeScript's structural typing does.

Prerequisites: none upstream — Phase 0 has no dependency on any other blueprint in this portfolio. Downstream: the protocol server (Phase 8) becomes a dependency for any future blueprint wanting permission-state subscription.

Timeline: Phase 0 — 3 weeks. Full system (Phase 0 through Phase 11) — approximately 14 months of continuous build effort at steady velocity, matching the ≥40/≤120-line phase bodies in §12–§23.

Deferrals: full-content deep resource scans PhaseDeferred("Phase 11"); on-prem/air-gapped appliance PhaseDeferred("Phase 11"); cross-tenant global analytics PhaseDeferred("Phase 8"); unattended (non-reviewed) bulk-revoke execution PhaseDeferred("Phase 7"); sub-second synchronous revoke-confirm SLA PhaseDeferred("Phase 7"); FedRAMP/government-cloud posture PhaseDeferred("Phase 11"). All resolved in the Deferred Features Register.

2. Why Build This

  • Unique systems knowledge: ReBAC data modeling (Zanzibar-style tuple stores vs relational adjacency), OAuth grant lifecycle mechanics beyond the textbook happy path (scope drift, refresh-token survival past revocation, pagination-cursor integrity), eventual-consistency reconciliation between an external system of record and a local materialized view, and safe bulk-mutation design (plan/diff/confirm/audit) under partial failure.
  • Why it matters: every organization running more than a handful of SaaS tools already has an unanswerable "who can see this" question; the failure mode is not hypothetical — see the 2018 Google+ API exposure (undetected over-broad scope grant to third-party apps), the 2022 Okta/Lapsus$ incident (support-tool credential compromise cascading through delegated access), the 2023 CircleCI OAuth-token incident (stolen session tokens used to pull customer secrets via still-valid OAuth grants), and the 2021 Codecov supply-chain incident (a compromised script exfiltrating credentials through legitimately-granted CI access).
  • Muscles built: designing a schema that must remain honest about staleness (I1, I6); building idempotent, verifiable distributed mutations (I2, I9) instead of fire-and-forget RPCs; reasoning about consistency models under multi-tenant, multi-provider skew (ADR-11); writing a wire protocol meant to outlive its first three implementations (§8.6, P9).
  • Cross-links: shares the tenant-isolation and audit-log discipline of any multi-tenant control-plane blueprint in this portfolio; shares graph-storage tradeoffs with any blueprint touching relationship-heavy data models; the connector-sandboxing discipline (P6) generalizes to any plugin-architecture blueprint.
  • Calibration value: this is the canonical "observe an ecosystem you don't own, act on it safely" problem — the same shape as a monitoring system, a compliance scanner, or a cost-governance tool, but with the added hazard that the acted-upon side (identity access) is also the highest-value attack surface in the system itself (T1).

What Mastery Looks Like

  • Can explain, without notes, why Mesh's own token store is designed to survive a breach of the graph database without leaking a usable third-party credential (Phase 2, I3).
  • Can derive the full-sync wall-clock budget for a given tenant size from first principles (rate-limit budget × page size × connector count), matching the Back-of-Envelope Capacity Model (§34).
  • Can trace, for any PGSAccessEdge, its complete provenance chain back to the raw provider response that produced it (Phase 2, I1).
  • Can explain why revocation is confirmed by a subsequent read, not by the write call's return code, and name the real incident class this defends against (Phase 6, I2, the CircleCI 2023 pattern).
  • Can design a new connector against the conformance suite (Phase 1, Phase 11) without reading any other connector's implementation, using only the connector contract (§8.4).
  • Can explain why the drift detector is read-only and never itself mutates the graph (Phase 5, I12, P1) and what would break if it did.
  • Can reason about the tradeoffs between a Zanzibar-style tuple store and Mesh's relational adjacency-table approach (ADR-04, Comparative Architecture §33) and state the tenant-scale threshold at which the tradeoff flips.

Provider Adapters wrap one SaaS API each behind the connector contract (§8.4); they hold no cross-connector state and cannot write outside their own namespace (I11). Scope Normalizer maps a provider's raw scope string to a CanonicalCapability and RiskClass (§8.2), recording the mapping version used so a later provider redefinition is detectable (P7). Permission Graph Store is the materialized view of provider truth (I1); every row carries lastSyncedAt and a provenance pointer. Consent/Audit Log is append-only, separately keyed from the graph store, and is the only place a human-readable "who did what, why" narrative lives (P8). Drift Detector runs read-only scans (I12) and emits DriftEvent records; it never mutates the graph. Risk Scorer annotates grants and drift events with a computed severity used for alert ranking and blast-radius sizing. Revocation Executor turns a RevocationOrder into provider API calls and does not consider an order complete until a subsequent read confirms absence (I2, P3). Bulk Revoke Planner computes a reviewable diff before any executor call is issued (P11). Protocol Server exposes canonicalized (never raw-provider) state to subscribers over a versioned wire protocol (§8.6, P9, I14). Client SDK and Telemetry are the external-interface and observability boundary respectively; the queue/job system (BullMQ-class, ADR-12) sits between the graph store and both the drift/revoke and protocol paths, absorbing backpressure (P12).

6. Design Principles

  1. P1 — Mesh observes and revokes; it never becomes the authorization decision point. Rule: no Mesh component sits in the request path of a protected resource. Tradeoff: Mesh cannot block access in real time, only after-the-fact. Operational implication: revocation latency is bounded by provider propagation, not Mesh's own clock. Violating this recreates the confused-deputy hazard (Hardy 1988) — Mesh's own authority becomes ambiguous relative to the provider's.
  2. P2 — Every grant is reconciled from the provider, never inferred. Rule: a PGSAccessEdge may only be created or updated from a connector's enumerate/ incrementalCursor response. Tradeoff: no representation of hypothetical or not-yet-observed grants. Violating this produces phantom edges that desync from ground truth — a drift false-negative.
  3. P3 — Revocation is idempotent and verifiable. Rule: a RevocationOrder is not RevokeConfirmed until a subsequent provider read shows absence. Tradeoff: adds a read-after-write round trip to every revoke. Violating this reproduces the CircleCI 2023 pattern — revoked at the provider console, but a long-lived token elsewhere still works.
  4. P4 — The graph is a materialized view with provenance, not ground truth. Rule: every node/edge carries lastSyncedAt and an evidence pointer to the raw response. Tradeoff: staleness is always possible and must be surfaced, never hidden. Violating this creates false confidence in stale data (I1, I6).
  5. P5 — No third-party credential is stored in reusable plaintext form. Rule: every CredentialHandle is an encrypted reference, never the bearer secret itself in the clear. Tradeoff: added envelope-encryption/KMS operational complexity on every read path. Violating this makes Mesh the highest-value breach target in the customer's estate — the 2022 Okta/Lapsus$ pattern, at Mesh's own scale.
  6. P6 — Connectors are sandboxed and mutually distrusting. Rule: a connector process has its own network egress allowlist and cannot write to another connector's node/edge namespace (I11). Tradeoff: per-connector resource overhead. Violating this lets a single compromised connector cascade — the 2021 Codecov supply-chain pattern.
  7. P7 — Scope normalization is lossy by design, and the loss is recorded. Rule: a CanonicalCapability is coarser than the raw provider scope string; the mapping version used is stamped on the edge. Tradeoff: two provider scopes may canonicalize to the same capability even if their real semantics diverge slightly. Violating this (by silently re-mapping without a version bump) hides the day a provider redefines a scope string's meaning — a documented pitfall class (Phase 1 N.6).
  8. P8 — Every mutation is audit-logged with actor and reason, append-only. Rule: no in-place update or delete on the audit log; every entry references the acting principal. Tradeoff: monotonic storage growth. Violating this makes incident response forensically blind (T6, Consent-Log Tampering).
  9. P9 — The protocol is additive-only; breaking changes require a new major version. Rule: no field is repurposed or removed within a major version of the publish/subscribe wire format (§8.6). Tradeoff: N and N+1 consumers must be served simultaneously during any migration window. Violating this causes downstream apps to silently misinterpret grant state — an RFC 9396-scale ambiguity, at protocol scope.
  10. P10 — Discovery prefers push over pull, but never assumes push is complete. Rule: webhook-driven connectors still reconcile on a longer poll cadence. Tradeoff: dual-path complexity even when webhooks are fully supported. Violating this creates a webhook-gap blind spot (Phase 4 N.6, "pagination cursor drift" class).
  11. P11 — Bulk operations require a pre-computed, reviewable blast-radius plan before execution. Rule: no RevocationOrder batch executes without a prior diff shown to an operator. Tradeoff: added latency and UI friction before any bulk action. Violating this turns bulk revoke into an accidental or malicious denial-of-service vector (T7).
  12. P12 — Backpressure is applied at the connector, never at the tenant's provider account. Rule: a connector self-throttles to I4's budget rather than retrying past the provider's own limit. Tradeoff: Mesh's sync throughput is capped below the provider's true ceiling. Violating this can trip the provider's own anti-abuse system, locking the tenant out of their own account.
  13. P13 — Consistency is tenant-scoped and read-your-writes for the acting operator, not globally linearizable. Rule: a query issued immediately after a write by the same operator sees that write; cross-tenant aggregate queries may lag. Tradeoff: no globally-consistent snapshot across tenants at any instant. Violating this creates false precision claims about cross-tenant analytics (PhaseDeferred("Phase 8")).
  14. P14 — Every connector implements the identical interface; there is no privileged first-party code path. Rule: first-party and community connectors pass the same conformance suite (§8.4, Phase 11). Tradeoff: first-party connectors cannot take shortcuts unavailable to the community. Violating this creates a two-tier ecosystem that defeats the credibility of the open protocol (§2).

I13 Every DriftEvent references the specific Grant and evidence that triggered it. No unattributed alerts. Drift Detector emission schema. DriftEvent missing grantId/evidenceRef. unattributed_drift_event_total Reject emission; re-run detector.
I14 The protocol publishes only Mesh-canonicalized state, never raw provider payloads. P9; subscribers must not see provider-format drift. Protocol Server serializer. Raw provider field name detected in outbound payload. raw_payload_leak_total (should be 0) Block publish; patch serializer.

Debugging methodology exercising these invariants: reproduce against a replayed provider cassette (Phase 11 fixtures) rather than the live provider; walk the suspect edge's evidence chain back to the exact raw response (I1); check whether the corresponding RevocationOrder/DriftEvent carries its required references (I2, I9, I13); confirm the SyncCursor advanced only with a matching committed upsert count (I8); run the adversarial cross-tenant query suite (I10) before concluding a bug is single-tenant scoped.

8.4 Connector Contract (Interface Table)

Operation Purpose Idempotency Rate-Limit Semantics
enumerate(cursor?) Full or resumed listing of identities/resources/grants Idempotent — replay from any valid cursor reproduces the same logical state Bound by I4's steady-state budget; opt-in 60% ceiling for initial sync only
incrementalCursor(cursor) Delta since last cursor Idempotent — re-applying the same delta page is a no-op upsert Same budget tier as enumerate

A connector that cannot implement incrementalCursor declares this in its ConnectorSpec capability flags and is restricted to a low poll-cadence tier (§4).

8.5 Worked Example, Malformed Input, Failure Path

Worked example: GitHub connector enumerates an org; Principal "alice-gh" receives Grant g-441 via App "internal-ci-bot" with Scope repo → canonical code.readwrite.all / high. RESOLVES_TO edge merges "alice-gh" into canonical Identity "alice@acme.com" (email + SSO-subject match, I7). Drift detector later observes g-441's lastUsedAt is 97 days stale against a 90-day dormant-identity threshold (§17.2.1) → emits DriftEvent referencing g-441 and its evidence (I13); grant transitions Active → Drifted.

Malformed input example: GitHub API returns a scope string repo:invalid-legacy not present in the normalizer's mapping table for the connector's declared pgsVersion. Per P7, this is not silently dropped or best-effort-guessed: the edge is written with canonicalCapability = "unmapped", riskClass = "unknown", and a DriftEvent-adjacent ScopeMappingGapEvent is queued for the normalizer maintainers — never silently downgraded to a known-safe class.

Failure-path example: A RevocationOrder for grant g-441 calls GitHub's collaborator -removal endpoint, receives HTTP 204, but the next scheduled sync (15 min later, medium-tier cadence) still enumerates the grant — the provider's edge cache had not yet propagated the removal. Per I2, the order stays RevokeRequested, not RevokeConfirmed; a forced synchronous re-poll is issued at t+20 min (§4 p95 propagation budget); on confirmation the order transitions to RevokeConfirmed and the receipt is audit-logged (I5).

8.6 Protocol Wire Format (Publish/Subscribe)

Envelope fields (all publish/subscribe messages): protocolVersion (semver major.minor), eventType (grant.created | grant.revoked | grant.drifted | identity.merged | heartbeat), tenantId, sequenceNumber (monotonic per-tenant, gap-detectable), canonicalPayload (a serialized PGS node/edge subset — never raw provider JSON, I14), emittedAt. Subscribers detect gaps via sequenceNumber and may request a bounded replay from the Protocol Server's retained window; beyond that window a full resync via the query API is required (P9's additive-only guarantee applies to canonicalPayload field evolution only, not to delivery guarantees, which are documented separately per Phase 8).

11. Core Schema & Types

// Identity & Principal — owned by Identity Resolution (I7); mutable via merge only.
type IdentityId = string;                 // stable, Mesh-assigned, cross-connector
type PrincipalRef = { connectorId: string; externalId: string };
type AppRef = { connectorId: string; appId: string; publisher?: string };

// Scope & capability — owned by Scope Normalizer; append-only mapping versions (P7).
type ScopeToken = { connectorId: string; rawScope: string; pgsVersion: string };
type CanonicalCapability = string;        // e.g. "file.readwrite.all"; serializable, stable
type RiskClass = "low" | "medium" | "high" | "unknown";

// Grant — owned by Normalization Layer write path; concurrency via I8 cursor-txn coupling.
type Grant = {
  id: string;
  principal: PrincipalRef;
  app: AppRef;
  scopes: ScopeToken[];
  state: GrantState;                      // §8.3 state machine
  lastUsedAt?: string;                     // ISO 8601; drift-detector input
};
type GrantState =
  | "Discovered" | "Active" | "Drifted"
  | "RevokeRequested" | "RevokeFailed" | "RevokeConfirmed"
  | "Expired" | "Orphaned";
// Provenance — owned by connector write path; immutable once written (I1).
type GrantProvenance = {
  grantId: string;
  connectorId: string;
  rawResponseRef: string;                 // pointer into evidence store, not inline payload
  observedAt: string;                     // ISO 8601, connector-reported
  syncedAt: string;                       // ISO 8601, Mesh-stamped (I6)
};

// Credential — owned by KMS envelope layer; never serialized with a usable secret (P5, I3).
type CredentialHandle = {
  id: string;
  grantId: string;
  kmsKeyRef: string;
  encryptedBlobRef: string;               // opaque pointer, not the ciphertext inline
  rotatedAt?: string;
};

// Connector contract types — owned by connector authors; versioned per ConnectorSpec.pgsVersion.
type ConnectorSpec = {
  connectorId: string;
  version: string;
  pgsVersion: string;
  capabilities: { incrementalCursor: boolean; revoke: boolean; verify: boolean; webhooks: boolean };
};
type SyncCursor = { connectorId: string; opaqueToken: string; committedAt: string };
// Drift & risk — owned by Drift Detector; write-only from a read-only DB role (I12).
type DriftEvent = {
  id: string;
  grantId: string;                        // I13 — always attributed
  evidenceRef: string;
  detectorKind: "dormant" | "unusedPermission" | "privilegeCreep" | "orphanResource"
              | "phantomIdentity" | "crossAppAdmin" | "groupCycle" | "sensitivityEscalation";
  riskClass: RiskClass;
  detectedAt: string;
};

// Revocation — owned by Revocation Executor; idempotent by dedupe key (I9).
type RevocationOrder = {
  id: string;                             // also the idempotency dedupe key
  grantIds: string[];
  reason: string;                         // audited, free-text (P8)
  state: "Planned" | "RevokeRequested" | "RevokeFailed" | "RevokeConfirmed";
};
type RevocationReceipt = {
  orderId: string;
  grantId: string;
  confirmedByReadAt: string;              // I2 — the confirming read, not the write's response
};
// Audit & query — owned by Audit Log writer (append-only) and Query Engine respectively.
type AuditEntry = {
  id: string;
  actorId: string;
  action: string;
  reason?: string;
  targetRef: string;                      // grantId | identityId | connectorId, etc.
  occurredAt: string;
};
type GraphQuery = { tenantId: string; pattern: string; asOfCursorFloor?: string };

// Error enums — owned by shared-types; every connector/engine boundary raises one of these.
type MeshError =
  | "ScopeMappingGap" | "RateLimitBudgetExceeded" | "CursorMismatch"
  | "RevocationUnconfirmed" | "CrossTenantIsolationViolation" | "WeakSignalAutoMergeRejected";

Ownership/mutation/concurrency/persistence/serialization/compatibility notes: Grant and GrantProvenance are connector-write-owned, immutable-append except state (I8-coupled transaction); CredentialHandle is KMS-layer-owned, rotates via rotatedAt, never serialized outbound with the underlying secret (I3); ConnectorSpec is author-owned, checked for capability-flag consistency at connector registration; DriftEvent is detector-owned, write-only from a read-only role (I12); RevocationOrder/RevocationReceipt are executor-owned, idempotent by id (I9); AuditEntry is append-only, no update/delete path exists in the schema (P8); GraphQuery is transient, tenant-scoped, never persisted beyond telemetry; all wire-serializable types are additive-only across pgsVersion majors (P9).

12. Phase 0 — Skeleton, CI, Connector SDK Harness

12.1 Objectives

Stand up the monorepo, CI gate, and a connector conformance harness capable of validating a connector against ConnectorSpec (§11) before any live provider integration exists. Prove the harness against a mock/fixture provider, not a real one.

12.2 Detailed Implementation Steps

Scaffold the repository layout (§10) with packages/pgs, packages/connector-sdk, packages/connector-conformance, apps/cli. Define ConnectorSpec, SyncCursor, and the capability-flag schema (§11) as the harness's contract surface (P14 — the harness must not special-case any future first-party connector). Wire CI (ADR-19) to run: lint, unit tests (ADR-17), and the conformance suite against a mock provider fixture. Build a mock-provider test double implementing a minimal enumerate/incrementalCursor pair with deliberately introduced pagination gaps, to exercise I8 (cursor-txn coupling) from day one. Establish the audit-log append-only table (P8) even before any real mutation exists, so every later phase inherits the invariant rather than retrofitting it.

12.3 Deliverable

A CI pipeline that fails a PR introducing a connector violating ConnectorSpec's capability contract, plus a passing conformance run against the mock-provider fixture.

12.4 Acceptance Criteria

Conformance suite completes in under 90 seconds against the mock fixture; CI blocks merge on any of 3 seeded violation fixtures (fixtures/mock-provider/cursor-gap.json, fixtures/mock-provider/missing-capability-flag.json, fixtures/mock-provider/malformed-scope.json); zero flaky runs across 20 consecutive CI executions.

12.5 Conformance Fixtures

fixtures/mock-provider/happy-path.json — clean enumerate + 2-page incrementalCursor, expected output: 2 identities, 1 resource, 1 grant, cursor advances twice. cursor-gap.json — page 2 of 2 dropped mid-stream, expected output: harness FAILs with CursorMismatch. missing-capability-flag.json — connector claims revoke: true but implements no revoke export, expected: harness FAILs at registration. malformed-scope.json — scope string absent from any mapping, expected: harness reports ScopeMappingGap, not a silent pass.

12.6 Pitfalls

Treating the mock provider as "good enough forever" and never revisiting fixture realism once live connectors exist (Phase 1 must re-validate against real cassettes). Building the conformance harness with hidden first-party shortcuts that community connectors in Phase 11 cannot pass (violates P14) — catch this by having the harness itself be provider-agnostic from day one, never importing anything from connectors/.

12.7 Performance Concerns

CI wall-clock budget for the full suite (lint + unit + conformance) must stay under 5 minutes at Phase 0 scale to keep the weekly-release cadence (ADR-22) from becoming a bottleneck; re-measure at each phase boundary as fixture count grows.

12.8 Edge Cases

A connector declaring zero capabilities (a stub) must still pass registration but fail any enumeration-dependent conformance check with a clear "no capabilities declared" error, not a crash. A SyncCursor with a malformed opaqueToken must be rejected at read time, not silently treated as "start from scratch."

12.9 Failure Analysis

Root cause class: harness accepts a connector whose declared capability flags do not match its actual exports — detected only at conformance run time, not at TypeScript compile time, because capability flags are runtime metadata. Detection: the missing-capability-flag.json fixture (§12.5). Recovery: harness rejects registration; no partial pass state exists.

12.10 Operational Notes

CI failure on the conformance suite is a hard merge-block, not a warning (ADR-19); the harness itself is versioned in lockstep with pgsVersion (§11) so a future PGS major bump requires an explicit harness update, never a silent behavior change.

13.6 Pitfalls

Provider scope strings silently changing meaning across an API version bump — a real recurring hazard (P7's reason for versioned mapping) — manifests as a canonicalCapability that no longer matches observed behavior; root cause: provider deprecates a scope's semantics without renaming the string; debug via cassette diff against the provider's changelog; signal: a spike in ScopeMappingGap events post-provider-release; recovery: bump the normalizer's mapping version and re-tag affected edges. Pagination-cursor drift causing phantom deletions: an API returns pages in a different order across retries, and a naive "resource missing from this page = deleted" heuristic wrongly orphans live resources; root cause: treating page absence as deletion evidence instead of requiring full-cycle absence; debug via the orphan_resource_total metric spiking correlated with a retry burst; recovery: require two consecutive full syncs before any orphan transition (§8.3), never a single page.

13.7 Performance Concerns

Each connector's enumerate must page at the provider's documented page-size ceiling (100 records/page assumed in §34) to avoid needlessly multiplying request count against the I4 budget; GitHub's GraphQL cost-based limiting requires batching multiple entities per query to stay within the same effective req/sec envelope as the REST-based connectors.

13.8 Edge Cases

A GitHub organization with > 10,000 outside collaborators (pagination depth stress); a Google Workspace domain with nested groups exceeding 5 levels (feeds Phase 4's cycle detection early); a Slack workspace with > 50,000 archived channels that must not be enumerated as active resources.

13.9 Failure Analysis

Root-cause class: rate-limit-induced partial syncs interpreted as revocations — if a 429 truncates an enumerate pass and the resulting partial resource set is naively diffed against the previous full set, resources present before but absent now look "revoked" when they were simply never re-fetched. Detection: correlate rate_budget_exceeded_total spikes with orphan_resource_total spikes in the same sync window. Recovery: a truncated sync (any page failing after budget exhaustion) is marked partial and excluded from any orphan/diff computation entirely — orphan detection only runs against full-cycle syncs (I8 extended).

13.10 Operational Notes

Each connector ships with a per-provider runbook entry (docs/runbooks/) covering: known rate-limit tier, OAuth app review lead time (Google/Microsoft app verification can take weeks — track separately from engineering timeline), and the cassette-recording procedure for capturing new regression fixtures from production incidents.

15. Phase 3 — Scope Normalization + Risk Scoring

15.1 Objectives

Formalize the scope normalizer (§8.2, ADR-05, P7) as a versioned, testable component; add the risk-scoring layer that annotates every Grant and later every DriftEvent with a RiskClass.

15.2 Detailed Implementation Steps

Extract the per-connector mapping tables (§8.2) into a single versioned lookup module keyed by (connectorId, pgsVersion); implement the unmapped fallback path (P7) with a ScopeMappingGapEvent emission, never a silent best-guess. Implement risk scoring as a function of RiskClass plus resource sensitivity (§8.1) plus AccessPath breadth (direct vs. group vs. inherited) — informed by the ReBAC-vs-RBAC-vs-ABAC framing of NIST SP 800-162 (applied per §5). Build the Zero Trust Networks-informed (§5 Required Reading #4) context-aware scoring adjustment: a high-risk capability granted via a nested group (MEMBER_OF chain depth > 2) scores higher than the same capability granted directly.

15.3 Deliverable

A risk-scoring service producing a deterministic, replayable score for any Grant given its scope set and resource context, exposed via the query API.

15.4 Acceptance Criteria

100% of the Phase-1 cassette corpus's grants receive a non-unknown RiskClass except the deliberately-injected malformed-scope-response.cassette.json case (§13.5), which must receive exactly unknown; risk-score computation for a 1.8M-edge fixture completes in under 45 minutes on a single worker (bounding a full re-score after a mapping-version bump).

15.5 Conformance Fixtures

conformance/risk-scoring/direct-vs-group-grant.fixture.json — same capability, one direct one via 3-deep group nesting, expected: group-path grant scores strictly higher. conformance/risk-scoring/mapping-version-bump-replay.fixture.json — a mapping-version bump mid-corpus, expected: pre-bump edges retain their original score until re-synced, never silently re-scored in place (P9-adjacent — no retroactive mutation without a new sync).

15.6 Pitfalls

Conflating "the provider calls this scope 'admin'" with "this is actually high-risk" — providers name scopes inconsistently (Slack's admin app-management scope is a different risk tier than GitHub's admin:org); the canonical capability, not the raw provider label, must drive the score (this is exactly what P7's normalization exists to prevent). Recomputing risk scores in place on a mapping-version bump instead of treating it as a new observation — violates the "graph is a materialized view" principle (I1) by mutating historical scoring retroactively.

15.7 Performance Concerns

Risk scoring must not become a per-query-time computation on the hot path (§4's p50/p95/p99 budgets are for graph queries, not scoring); scores are computed at write time and stored on the edge, read-only thereafter.

15.8 Edge Cases

A grant whose scope set spans multiple RiskClass tiers (e.g., one low + one high scope in the same Grant.scopes[]) — the grant's overall score is the maximum across its scopes, never an average (a single high-risk scope makes the whole grant high-risk).

15.9 Failure Analysis

Root-cause class: a provider redefining an existing scope string's underlying permission without renaming it (P7's core hazard) silently changes real-world risk while the canonical mapping stays stale; detection: no automatic signal exists for this class without provider changelog monitoring — documented as a known limitation, mitigated by periodic manual mapping-table review (Operational Readiness runbook).

15.10 Operational Notes

Every mapping-table change is itself an audited mutation (P8) with a required reason field citing the provider changelog entry or incident that prompted it.

16.9 Failure Analysis

Root-cause class: pagination-cursor drift causing phantom deletions under sustained incremental sync (extends the Phase-1 pitfall to the long-running case) — over many incremental cycles, a provider's opaque cursor token can silently invalidate (provider-side TTL), causing the next incrementalCursor call to silently restart from an unexpected point; detection: cursor committedAt age exceeding the provider's documented token TTL; recovery: treat cursor-TTL expiry as a forced full re-enumerate, never a silent delta from an unknown base state.

16.10 Operational Notes

The 7-day soak is a release gate for this phase specifically (not a one-time check) — re-run before every subsequent phase's connector-affecting change ships, per the performance-regression-gating discipline (§29).

17. Phase 5 — Drift Detection

17.1 Objectives

17.2 Detailed Implementation Steps

Implement each detector as a scheduled, read-only scan emitting DriftEvent (§11) records attributed to a specific Grant and evidenceRef (I13): dormant identity (lastUsedAt > 90 days, configurable), unused permission (per-edge lastUsedAt > 60 days where the provider exposes usage telemetry), privilege creep (> 5 new edges in 30 days against high-sensitivity resources), orphan resource (owned by a deleted/suspended identity, TTL-purged only after two full-cycle absences per Phase-1's pitfall lesson), phantom identity (bot/service account created > 180 days ago by a departed identity), cross-app admin concentration (admin/owner on

3 connected apps), group-nesting cycle (surfaced at sync time per Phase 4, promoted to a critical DriftEvent here), sensitivity escalation (first-time write access to a restricted resource). Enforce I12 via a database role with read-only grants for the detector process — not merely a code-review convention.

17.3 Deliverable

Eight running detectors producing attributed DriftEvent records against the Phase-2 store, verifiably incapable of mutating the graph (I12 enforced at the DB-role level).

17.4 Acceptance Criteria

Detector precision ≥ 90% against a synthetic labeled fixture (conformance/drift/synthetic-labeled-1000.fixture.json, 1,000 seeded known-positive/negative cases); zero writes attempted from the detector's DB role, verified by drift_write_attempt_blocked_total staying at 0 across the full detector suite run; every emitted DriftEvent carries a non-null grantId and evidenceRef (100% attribution, I13).

17.5 Conformance Fixtures

conformance/drift/synthetic-labeled-1000.fixture.json — 1,000 synthetic grants with known ground-truth drift labels across all 8 classes, expected: ≥ 90% precision per class. conformance/drift/read-only-role-violation.fixture.json — attempts a write from the detector's connection role, expected: hard rejection at the database permission layer, not just application-level refusal.

17.6 Pitfalls

Shadow admin via transitive grants — an identity with no direct admin grant but reachable admin-equivalent access through a chain of group memberships and app-level roles; naive per-edge detectors miss this because no single edge looks dangerous. Root cause: detectors scoped to single-edge risk instead of transitive reachability; debug via the resolution/ group-membership graph traversal (Phase 4's cycle-safe traversal, reused here); signal: cross -app-admin detector count seems low despite known org sprawl; recovery: extend the cross-app detector to traverse MEMBER_OF chains, not just direct Grant records, bounded by the same depth cap as Phase 4.

17.7 Performance Concerns

Detector scan cadence (daily for dormant/unused, hourly for the rest, §12.2 original cadence design retained) must stay within the read-query latency budget (§4) even at the 10M-edge ceiling — batch detectors process in tenant-sized chunks, never a single unbounded cross-tenant scan (P13).

17.8 Edge Cases

A grant with no lastUsedAt at all because the provider never exposes per-edge usage telemetry (Notion, partial support) — such grants are excluded from the "unused permission" detector entirely rather than defaulting to "always flagged" or "never flagged," and this exclusion is itself surfaced to the operator as a coverage gap.

17.9 Failure Analysis

Root-cause class: detector false positives from a resource whose sensitivity was mis-classified upstream (a resource heuristically tagged restricted that is actually low-sensitivity) cascading into spurious sensitivityEscalation events; detection: an unusually high dismiss-without-action rate on one detector class (Operational Readiness threshold, §16.2 original concept retained as a signal, not a business KPI here); recovery: tune the sensitivity-classification heuristic, not the detector logic itself.

17.10 Operational Notes

Detector precision is reviewed monthly against the labeled fixture corpus; any detector class falling below the 90%/70% (synthetic/real, §28) thresholds triggers a detector-specific audit before its alerts are surfaced to operators again.

18.9 Failure Analysis

Root-cause class: a revoke() call racing a concurrent provider-side grant change (the human grants themselves new access moments after Mesh's revoke order was planned but before it executed) — detection: the confirming read shows a different grant present, not the exact one revoked; recovery: the executor treats this as RevokeConfirmed for the original grant (it is gone) plus a new Discovered grant on the next sync — never silently merges the two.

18.10 Operational Notes

19.1 Objectives

Implement the Bulk Revoke Planner (P11): a reviewable, diffed plan computed before any batch of RevocationOrders executes.

19.2 Detailed Implementation Steps

Implement plan computation accepting a pattern (a set of (principalId, appId, scopeToken) matches or a graph-query-engine pattern) and producing a flattened diff: edge count, affected identity count, affected app count, per-edge exclusion toggles. Enforce P11's ordering: no RevocationOrder batch reaches RevokeRequested without a prior plan shown to an operator. 19.3 Deliverable

A plan-diff-confirm-execute pipeline for bulk revocation, with per-plan audit trail (P8) and a rate-capped batch executor built on the Phase-6 idempotent order primitive.

19.4 Acceptance Criteria

A 500-edge bulk plan completes end-to-end (plan → diff → confirm → execute → all receipts confirmed) in ≤ 90 seconds on the fixture corpus (benchmarks/bulk-revoke/500-edge-plan.json); zero service-account/agent-kind edges included in a plan without an explicit override flag, verified across 50 randomized fixture plans; batch execution never exceeds the distinct bulk-revoke rate cap (§4) even when the underlying connectors have separate spare read-budget.

19.5 Conformance Fixtures

conformance/bulk-revoke/500-edge-diff-accuracy.fixture.json — expected diff matches actual post-execution graph state exactly. conformance/bulk-revoke/service-account-default- exclusion.fixture.json — a plan pattern that would match 3 service accounts, expected: those 3 excluded by default, present in the diff as "excluded, override required." conformance/bulk-revoke/partial-batch-failure.fixture.json — 2 of 500 orders fail mid-batch, expected: the other 498 still confirm independently (I9's idempotency applied per-order, not per-batch).

19.6 Pitfalls

A blast-radius preview computed against a graph snapshot that goes stale between plan computation and execution confirmation (an operator reviews a plan, takes 20 minutes to approve, and the underlying grant set has shifted) — root cause: no staleness check on plan execution; debug via comparing the plan's snapshot cursor against current state at execute time; signal: executed diff differs from previewed diff; recovery: re-diff at execute time and require re-confirmation if the delta exceeds a small tolerance, rather than executing a stale plan blindly.

19.7 Performance Concerns

Diff computation for a plan touching a large fraction of a 10M-edge tenant's graph must itself stay within a bounded wall-clock budget (target: ≤ 10 seconds for a 50,000-edge plan) to keep the review experience interactive, distinct from the execution-phase's 90-second budget.

19.8 Edge Cases

A plan whose pattern matches zero edges (operator error, overly narrow pattern) — the system must clearly report "0 edges match" rather than silently no-op-ing the confirm step, so an operator does not mistake an empty match for a successful revoke of something they intended.

19.9 Failure Analysis

Root-cause class: malicious or accidental mass-revocation as a denial-of-service vector (P11's core hazard, T7 in the Threat Model) — an overly broad pattern or a compromised operator account triggers a plan touching far more of the estate than intended; detection: the batch rate cap (§4) itself throttles the blast radius even under a worst-case broad pattern, and any single plan exceeding a configurable edge-count threshold requires a second-operator confirmation (a Recovery control, not merely detection).

19.10 Operational Notes

Every executed bulk plan's audit record retains the full diff (not just a summary count) so a post-incident review can reconstruct exactly which edges were touched, matching the receipted-per-order discipline from Phase 6.

A SCIM Update that changes a user's group memberships without an accompanying Delete/ Create for the affected MEMBER_OF edges — the connector must diff the full membership set on any Update, not assume additive-only semantics from the SCIM payload itself.

21.9 Failure Analysis

Root-cause class: SCIM and poll paths disagreeing transiently (SCIM says deleted, the next poll — running on a longer cadence — still reports the identity active) creates a brief window of ambiguous state; detection: a state-disagreement counter between push-derived and poll-derived observations for the same identity; recovery: the more recent observedAt timestamp wins (I1's provenance timestamp is exactly the tiebreaker mechanism), never the push path unconditionally.

21.10 Operational Notes

SCIM-connector runbooks document the specific IdP's SCIM delivery guarantees (Okta's documented retry behavior, for instance) so operators know precisely how much to trust push alone, per provider.

22. Phase 10 — Machine / Agent Identities

22.1 Objectives

Make the agent identity kind (§8.1) first-class: delegation chains (DELEGATES_TO), capability-scope declarations, and expiry-aware drift signals for autonomous agent credentials.

22.2 Detailed Implementation Steps

Implement DELEGATES_TO edge population from OIDC-based agent-token issuance (a customer's IdP issues an agent token with an embedded delegation claim; Mesh observes via introspection, RFC 7662, reusing Phase 9's verification path, itself an extension of I2's confirming-read discipline). Extend the risk-scoring model (Phase 3) with a delegation-depth factor, informed by the SDSI/SPKI delegation literature (Rivest & Lampson 1996, applied here) — an agent's effective risk is a function of both its own capability scopes and its delegation chain's transitive reach (P2 — reconciled from the provider/IdP, never inferred). Add an accessExpiresAt field to time-bound agent grants and a drift-detector extension (Phase 5) flagging agents nearing expiry (I13 — attributed to the specific grant and evidence). Implement "cross-agent blast radius" as a graph-query pattern (not a new node/edge type) computing the union of resources reachable through a compromised agent's delegation chain, reusing Phase 4's cycle-safe traversal.

22.3 Deliverable

Agent-identity support with populated DELEGATES_TO chains for at least one OIDC-based agent platform integration, plus the expiry-aware drift extension and the blast-radius query pattern.

22.4 Acceptance Criteria

100% of ingested agent identities carry a non-null delegatedFrom-equivalent (DELEGATES_TO edge to a human or service account) or are flagged as an unattributed-agent drift signal (never silently accepted as ownerless); blast-radius query for a 5-level delegation chain completes within the same p95 budget as any other 2-hop-class traversal extended proportionally (§4), verified on benchmarks/agent/5-level-delegation-chain.json.

22.5 Conformance Fixtures

conformance/agent/unattributed-agent-flag.fixture.json — an agent identity with no resolvable DELEGATES_TO target, expected: flagged, not silently accepted. conformance/agent/expiry-approaching-drift.fixture.json — an agent grant with accessExpiresAt inside a configurable warning window, expected: DriftEvent emitted before expiry, not after. conformance/agent/blast-radius-5-level-chain.fixture.json — expected output: the exact resource set reachable transitively, matching a hand-computed reference set.

22.6 Pitfalls

Treating an agent identity's declared capability scopes as equivalent to its observed behavior — an agent that only ever exercises a fraction of its granted scopes still carries the full risk of what it could do, and the risk score must reflect declared capability, not observed restraint (a documented distinction from Phase 3's scoring model, made explicit here because agents are the class most likely to be over-provisioned "just in case").

22.7 Performance Concerns

Delegation-chain traversal depth must be bounded identically to Phase 4's group-nesting cap, for the same reason (unbounded traversal risk) — reuse the cycle-safe, depth-capped traversal utility rather than writing a second one.

22.8 Edge Cases

An agent that delegates to another agent (chain depth > 1 before reaching a human/service- account root) — supported, but any chain exceeding the depth cap is itself a DriftEvent ("excessive delegation depth"), since a very long chain is itself a risk signal independent of what's at the end of it.

22.9 Failure Analysis

Root-cause class: an agent's OIDC token surviving past its human delegator's own account deactivation (the delegator is offboarded but the agent's token was issued with independent validity) — detection: cross-reference the delegator Identity.status against active DELEGATES_TO edges on each sync; recovery: any agent delegated from a suspended/deleted identity is immediately flagged as a critical drift event, not merely a routine expiry warning.

22.10 Operational Notes

Agent-platform integrations are documented per-platform in docs/runbooks/ identically to provider connectors, since an agent-token-issuing platform is architecturally another provider from Mesh's perspective, not a special case.

23. Phase 11 — Conformance + Performance Hardening

23.1 Objectives

Bring the full connector conformance suite, fuzzing corpus, and performance-regression gate to the standard required for third-party (community) connector authorship (P14) and for production SLO confidence across all prior phases.

23.2 Detailed Implementation Steps

Extend the Phase-0 conformance harness with the full fixture corpus accumulated across Phases 1–10, formalized as the public conformance suite (ADR-19's public-repo CI target). Implement structured fuzzing (ADR-18) over scope strings and provider payload shapes, seeded from the real malformed-input cases discovered in Phases 1–9 (§13.6, §16.9). Wire performance-regression gating into CI: every PR touching a connector, the query engine, or the revocation executor re-runs the relevant benchmarks/ fixture and fails the build on any regression past the §30 M# targets. Publish the connector-authoring documentation and the mesh connector new scaffold (templates/) so an external author can build and conformance- test a connector without reading any first-party connector's source (verifying P14 in practice, not just in principle).

23.3 Deliverable

A public conformance suite, fuzzing corpus, and CI performance gate, plus a documented, scaffold-driven path for third-party connector authorship.

23.4 Acceptance Criteria

An external test author (a team member with no prior exposure to any first-party connector source) builds and conformance-passes a sixth connector (Notion excluded, a genuinely new one — e.g., Linear) using only the scaffold and public docs, in under 3 days; fuzzing corpus (fuzz/scope-strings/, fuzz/provider-payloads/) runs 4 hours per CI cycle with zero unhandled-exception crashes; all M# performance targets (§30) pass in CI on every merge to main for 30 consecutive days pre-declaring the phase done.

23.5 Conformance Fixtures

conformance/full-suite/all-phases-regression.suite.json — the complete accumulated fixture corpus from Phases 0–10, run as a single gate. fuzz/scope-strings/corpus/ — seeded with every real malformed scope string discovered in production cassettes to date. fuzz/provider-payloads/corpus/ — seeded with every recorded pagination-drift and partial-sync cassette from Phases 1 and 4.

23.6 Pitfalls

Declaring "conformance-complete" based on suite size alone rather than external-author success — a suite that only ever validates against first-party connectors' own assumptions can pass green while still being unusable by a real community author; the §23.4 external- author acceptance test exists specifically to catch this. Under-resourcing the fuzzing corpus with only synthetic cases instead of real recorded malformed input, missing the exact class of bug (provider redefining scope semantics, §13.6) that fuzzing is meant to catch.

23.7 Performance Concerns

The full regression suite's CI wall-clock time must stay bounded (target: ≤ 25 minutes for the complete gate) even as the fixture corpus grows across 11 prior phases — parallelize fixture execution across CI runners rather than letting suite growth silently erode the weekly-release cadence (ADR-22).

23.8 Edge Cases

A community-contributed connector that passes conformance but declares capabilities its provider's API cannot actually sustain at the documented rate-limit budget (§4) in production — caught not by the conformance suite (which runs against fixtures) but by a staged production canary requirement before full release (Operational Readiness).

23.9 Failure Analysis

Root-cause class: a performance regression introduced by a seemingly-unrelated change (e.g., an index change in Phase 2's schema silently degrading the Phase 7 bulk-diff query) — caught only because the CI performance gate re-runs all benchmarks/ fixtures on every relevant PR, not just the fixtures the PR's author thought were affected; detection: the gate's cross-phase benchmark coverage; recovery: bisect via the benchmark history to the introducing commit.

23.10 Operational Notes

Conformance-suite and fuzzing-corpus maintenance is an ongoing responsibility documented in CONTRIBUTING.md, not a one-time Phase-11 deliverable — every subsequently discovered production incident's root cause is expected to add a fixture here, closing the loop between Failure Modes & Recovery (below) and the suite that should have caught it.

26. Operational Readiness

Metrics: every counter/gauge named in §7 (Invariants), §24 (Threat Model), and §25 (Failure Modes) is exported Prometheus-compatible (ADR-16). Tracing: OpenTelemetry spans (ADR-15) cover every connector sync cycle, every query-engine execution, every revocation-order lifecycle transition. Structured logging: JSON, PII-scrubbed at ingestion (ADR-14), correlated by tenantId + traceId. Dashboards: per-tenant sync health, per-connector rate-budget consumption, drift-detector precision trend, revocation propagation-time distribution. Alerting philosophy: page only on invariant violations (I-prefixed metrics that "should be 0" crossing above 0) or SLO-threshold breaches sustained past a debounce window — never on transient single-sample noise. SLOs: sync success rate ≥ 99.5% (Phase 4), query p95 ≤ 350 ms (§4), revocation propagation p95 ≤ 20 min (§4). Incident response: named runbooks per connector (docs/runbooks/{connector}.md) and per invariant-violation class (docs/runbooks/invariant-violations.md); a T5 (tenant-isolation) incident triggers the highest-severity runbook, including mandatory tenant notification. Backup/restore: Postgres WAL-streamed replica (RPO ≤ 5 min, §4), point-in-time recovery tested quarterly against a restored-tenant fixture. Deployment topology: multi-AZ within a region for the hosted control plane; single-region only through Phase 11 (multi-region PhaseDeferred("Phase 8") for the cross-tenant-analytics case, otherwise out of scope for Phase 0–11). Canary/rollback: every release deploys to a canary tenant subset first, auto-rolled-back on any SLO breach within a 30-minute observation window; migrations are always additive-first (expand/contract pattern) to keep rollback safe.

27. Compatibility & Versioning

Permission Graph Schema evolves via additive-only majors (P9); a major bump requires the graph store to support the current and previous major simultaneously for at least the duration of one full connector-release cycle. Connector API versioning: ConnectorSpec. pgsVersion pins a connector to the schema major it was built against; the conformance harness (Phase 11) rejects a version mismatch at registration. Protocol versioning: the publish/subscribe envelope's protocolVersion follows the same additive-only discipline; breaking changes ship as a new major with parallel-serving during migration (P9). Provider API pinning: each connector documents the provider API version it targets in its README (§20, original doc's discipline retained); a provider deprecating that version triggers a tracked migration, not a silent break. API stability: the query API and protocol are both public-committed surfaces (§1) — no retroactive breaking change without a documented 30-day deprecation notice. Migration: schema majors ship with a migration guide; connector-author migration is tested via the external-author acceptance criterion (§23.4) applied to the new major. Deprecation: a 30-day minimum notice window on any public-surface removal. SemVer: strictly applied across packages/pgs, packages/connector-sdk, packages/protocol. Rolling-upgrade guarantees: a connector on major N and the graph store on major N+1 can coexist for the overlap window defined above; no connector is force-upgraded without its author's release.

28. Testing & Verification Strategy

Unit tests (Vitest, ADR-17) cover PGS types, scope-normalization mapping tables, and the risk-scoring function in isolation. Integration tests exercise a full connector against a recorded cassette end-to-end (enumerate → normalize → store → query). Property tests verify revocation idempotence (I9 — replaying any confirmed order is provably a no-op across randomized order sequences) and graph-reconciliation convergence (repeated sync of a stabilized fixture converges to the same edge set regardless of page-order permutation). Differential testing compares Mesh's graph view against the provider's own admin-console export for a subset of design-partner-equivalent fixtures, catching normalization drift the unit suite alone would miss. Fuzzing (ADR-18, Phase 11) targets scope strings and provider payload shapes. Chaos testing injects rate-limit throttling, connection drops, and out-of-order webhook delivery into the Phase 4 soak harness. Deterministic replay of recorded provider cassettes (§10 conformance/) is the primary regression-reproduction mechanism — every fixed production incident adds a cassette (§23.10's closed loop). Soak testing: the 7-day multi-tenant run (§16.4) is a standing release gate, re-run before any connector- affecting change. Fault injection: the partial-sync (§13.9), provider-lag (§18.5), and stale-plan (§19.6) fixtures are fault-injection tests specifically. Conformance suite for connector authors (§8.4, Phase 0, Phase 11) is the acceptance gate for any new connector, first-party or community (P14). Perf-regression gating (§23.2) ties every benchmarks/ fixture to a M# target (§30), enforced in CI. Every test class above ties back to at least one I# invariant or one phase's N.5 fixture set — no test exists that does not verify a named invariant or a named acceptance criterion.

31. Scalability Analysis

What stays constant: per-connector rate-limit budget percentage (I4, always ≤ 20%/60% regardless of tenant size); tenant isolation guarantees (I10, independent of scale). What grows: edge count (O(identities × connectors × grants/app), §34); query latency at fixed index structure (O(log n) point lookup, but 2-hop traversal cost grows with average fan-out — the reason for the 10M-edge ceiling in §4/ADR-04). Named bottlenecks, in order: (1) provider rate limits dominate — no amount of Mesh-side scaling increases the ceiling imposed by a provider's own published quota (I4); this is the hard floor beneath every other optimization. (2) Graph-store write amplification on high-churn tenants (frequent grant creation/revocation) — bounded by the storage-growth model (§34). (3) Recursive-CTE traversal cost for deep resolution/delegation chains — bounded by the depth cap (Phase 4, Phase 10). Horizontal scaling: connector-sync workers scale horizontally per tenant-connector pair (embarrassingly parallel up to the rate-limit ceiling); the graph store scales via per-tenant sharding once a single Postgres instance's aggregate tenant load exceeds its practical ceiling (ADR-04's stated flip point to a Zanzibar-style tuple store). Vertical scaling: the query engine benefits from vertical scaling (more RAM for hot-index caching) up to the point where provider rate limits, not query latency, are the binding constraint for most workloads. Sharding: by tenant_id, the natural isolation boundary already enforced by RLS (I10) — no cross-shard query is required for any Phase 0–11 use case (cross-tenant analytics is explicitly deferred, PhaseDeferred("Phase 8")). Coordination overhead: minimal by design — P13's tenant-scoped consistency model avoids any cross-tenant coordination protocol. Practical ceiling: the 10M-edge/50k-identity tenant (§4); levers beyond it are ADR-04's tuple-store migration and ADR-11's zookie-based consistency token adoption, both explicitly named as "when the rejected choice wins" in §9.

32. Mental Models & First Principles

  1. MM1 — A permission graph is a cache of other people's databases. Staleness is the product's core risk, not an incidental bug. Predicts: every UI surface must show freshness, never hide it. Bug class without it: silent trust in stale data leading to a revoke-that-didn't-happen incident. Resolved in §7 (I1, I6), §3.
  2. MM2 — A write's success response is not proof of its effect. Predicts: every mutating operation needs an independent confirming read. Bug class without it: the CircleCI-2023 pattern, generalized (T10, FM-4). Resolved in §18 (I2, P3).
  3. MM3 — Provider rate limits are a hard physical constraint, not a tuning parameter. Predicts: no amount of Mesh-side engineering raises the ceiling on how fast a tenant can be synced; the only lever is what you do within the budget. Bug class without it: chasing sync-speed improvements that hit a wall no code change can move. Resolved in §31, §34.
  4. MM4 — A scope string is a label a provider chose, not a stable contract. Predicts: normalization must be versioned and re-checkable, because the same string can mean something different tomorrow. Bug class without it: silent risk misclassification after a provider API change (§13.6). Resolved in §8.2, P7.
  5. MM5 — Observation and action must be architecturally separate, not just conventionally separate. Predicts: a read-only database role, not a code-review rule, is what actually stops a detector from mutating state. Bug class without it: scope creep in a "read-only" component that quietly gains a write path over time. Resolved in §7 (I12), §17.
  6. MM6 — Identity resolution errors are asymmetric in cost. A missed merge is an inconvenience; a false merge can revoke the wrong human's access. Predicts: the default must always be conservative, even at the cost of more manual review. Bug class without it: an aggressive fuzzy-matcher causing a security incident instead of preventing one. Resolved in §7 (I7), ADR-27.
  7. MM7 — A grant with no usage signal is not the same as a grant with confirmed non-use. Predicts: "unused permission" detection must explicitly model missing telemetry as a coverage gap, not a default answer either way. Bug class without it: false-positive drift alerts on providers with partial usage-API support. Resolved in §17.8.
  8. MM8 — A protocol outlives its first implementation; treat every field as a public promise the moment it ships. Predicts: additive-only evolution is cheaper across the protocol's lifetime than any amount of "we'll fix it in v2" flexibility. Bug class without it: downstream consumers silently misinterpreting a repurposed field. Resolved in §8.6, P9.

34. Back-of-Envelope Capacity Model

  1. Total edges, typical large tenant. identities(8,000) is the §4 "typical" row, but the derivation below sizes for the stress case: I_MAX(50,000) × C_TYP(12 connectors) × G_AVG(3 grants/app) = 1,800,000 edges. This is the fixture size used throughout §12–§23.
  2. Graph-store bytes for edges. 1,800,000 edges × ~180 bytes/row (tuple + 2 btree index entries at ~60 B each, plus row overhead) = 324,000,000 bytes ≈ 309 MiB per large tenant's edge table (§4 storage-growth row).
  3. Blended effective enumeration rate, steady state. Representative per-connector published quota ≈ 1 req/sec (blended across Slack Tier 3 ~0.83/sec, Notion ~3/sec, Google Admin SDK ~40/sec/user but shared, GitHub cost-based — weighted toward the stricter providers). At I4's 20% steady-state budget: 0.2 req/sec/connector × 12 connectors (running in parallel) = 2.4 req/sec tenant-wide, × 100 records/page = 240 records/sec.
  4. Blended effective rate, opt-in initial sync. Same base, at I4's 60% initial-sync budget: 0.6 req/sec/connector × 12 = 7.2 req/sec, × 100 records/page = 720 records/sec.
  5. Raw enumeration wall clock. 1,800,000 edges ÷ 720 records/sec ≈ 2,500 sec ≈ 42 min for a single enumeration pass at initial-sync budget.
  6. Full-sync wall clock with pass multiplier. Each connector runs 3 dependent enumeration passes (identities → resources → permissions, not fully overlapped) ≈ 42 min × 3 ≈ 126 min; with a 1.5× retry/backoff overhead factor: 126 × 1.5 ≈ 189 min ≈ 3.15 h, matching §4's stated ≤ 3.2 h target (M4).
  7. Storage churn, large tenant. Assume 2% daily edge churn (creation + revocation): 0.02 × 1,800,000 = 36,000 mutated edges/day × 180 B/row ≈ 6.48 MB/day graph delta.
  8. Audit-log growth, large tenant. 36,000 mutations/day × ~300 B/audit entry ≈ 10.8 MB/day. Combined with (7): ≈ 17.3 MB/day/tenant (§4's storage-growth row).
  9. Platform-wide storage growth (1,000-tenant illustrative fleet). Blended average (mix of small/large tenants, large tenant weighted at ~2 MB/day effective blended average) × 1,000 tenants ≈ 2 GB/day platform-wide.
  10. FD budget check. 2,048 concurrent connector-sync coroutines/worker-node × ~2 FDs each (1 HTTP/2 connection + 1 DB-pool connection) = 4,096 FDs, well within the 32,768 ulimit (§4), leaving headroom for connection-pool overhead and the protocol server's subscriber connections.
  11. Blast-radius query cost, 5-level delegation chain. Assuming average fan-out of 20 edges/hop (a typical group/delegation branching factor), a 5-hop traversal touches up to 20⁵ = 3,200,000 candidate edges before dedup; the depth cap (Phase 4, Phase 10) and index-assisted CTE keep the realized traversal cost within the p99 900 ms budget (§4) for the actually-connected subgraph, which is orders of magnitude smaller than the naive upper bound in any real org-chart-shaped graph.
  12. Webhook burst absorption. At the 500 events/sec burst ceiling for 10 s (§4) = 5,000 burst events, absorbed by the ADR-12 queue's backpressure before graph-store commit, confirming the queue sizing requirement referenced in §20.7.

36. Alternative Architectures (Roads Not Taken)

A1 — Authoritative Zanzibar-style Policy Decision Point, apps call Mesh synchronously at request time to authorize each action.

App Request ──▶ Mesh PDP (tuple store, zookie-consistent) ──▶ Allow/Deny ──▶ App
                        ▲
                Sync from providers (background, same as today)

Winning regime: a single organization willing to route all authorization decisions through one PDP, accepting the availability coupling that implies. Real embodying system: Google's internal Zanzibar deployment, and SpiceDB/OpenFGA for external adopters. Rejected here because it collapses P1 — Mesh would become the confused deputy the whole design exists to avoid, and it requires every downstream app to accept Mesh as a hard runtime dependency rather than an observational side-channel.

A2 — Browser-extension client-side-only discovery, no backend, purely local enumeration of a single user's own grants via the browser's authenticated sessions.

Browser Extension ──▶ reads provider consent-management pages (DOM) ──▶ local-only report
        (no server, no cross-user graph, no revoke automation)

Winning regime: an individual-consumer, zero-trust-of-any-vendor use case where even Mesh itself must not see the data. Real embodying system: browser-based personal-privacy extensions (ad-blocker-adjacent privacy tools). Rejected here because it cannot support tenant-wide graph queries, drift detection across an organization, or receipted bulk revocation — the core enterprise value Mesh exists to provide.

A3 — IdP-native model, the customer's identity provider (Okta/Entra) owns the permission graph natively, and Mesh is a thin plugin surfacing IdP-native data.

Okta/Entra (owns graph natively) ──▶ Mesh Plugin (read-only view + drift/revoke UI layer)

Winning regime: an organization fully consolidated on one IdP with no significant non-IdP-federated SaaS sprawl. Real embodying system: Okta's and Entra ID's own native governance modules (Okta Identity Governance, Entra ID Governance). Rejected here because Mesh's entire value proposition is cross-provider normalization across IdPs and non-IdP SaaS apps alike (§1); an IdP-native model cannot observe grants the IdP itself never brokered (e.g., a Notion integration authorized directly by a user, bypassing SSO-mediated OAuth).

A4 — Event-sourced pure-webhook design, no polling at all; the graph is purely a projection of an append-only webhook event log.

Provider Webhooks ──▶ Event Log (append-only) ──▶ Graph Projection (rebuilt from log)
                (no enumerate(), no incrementalCursor(), no poll floor)

Winning regime: a closed ecosystem where every provider guarantees at-least-once, ordered webhook delivery with no gap possibility — an assumption no real multi-provider SaaS estate satisfies today. Real embodying system: internal event-sourced microservice architectures within a single company's own infrastructure, where delivery guarantees are engineered end-to-end. Rejected here because P10 exists precisely because real third-party webhook delivery is not reliably gap-free (§16.6, §21.6) — a pure-webhook Mesh would silently drift from ground truth with no reconciliation mechanism to catch it.

38. Glossary

  • Access Path — how a grant reaches an identity: direct, via group, via role, or inherited.
  • Agent (identity kind) — an autonomous, often LLM-backed identity with a delegation chain back to a human or service account.
  • App (node type) — the third-party application that was granted access.
  • Audit Entry — an append-only, immutable record of a mutation, its actor, and its reason.
  • Blast Radius — the set of edges/identities/resources affected by a proposed or executed bulk action.
  • Bot (identity kind) — a SaaS-issued automation principal scoped to one application.
  • Canonical Capability — the normalized, provider-agnostic name for a permission (§8.2).
  • Cassette — a recorded provider API interaction sequence used for deterministic replay testing.
  • Confused Deputy — the hazard of a system with legitimate authority being tricked into misusing it on an attacker's behalf (Hardy 1988).
  • Connector — a module implementing the Mesh connector contract for one provider.
  • Connector SDK — the shared library providing rate limiting, OAuth, pagination, and audit-emission helpers to connector authors.
  • Credential Handle — an opaque, encrypted reference to a third-party credential; never the credential itself.
  • Delegation Graph — the network of DELEGATES_TO edges tracing an agent's authority back to its human or service-account root.
  • Drift — divergence between granted access and actually-needed/actually-used access.
  • Drift Event — an attributed, read-only-emitted record of a detected drift condition.
  • Envelope Encryption — encrypting data with a data-encryption key that is itself encrypted by a key-management-service key.
  • Grant — a lifecycle-tracked authorization from a principal to a resource via a set of scopes.
  • Grant Provenance — the immutable record of which provider response produced a given grant, and when.
  • Identity Resolution — merging per-connector shadow identities into one canonical identity.
  • Idempotency — the property that repeating an operation has the same effect as performing it once.
  • Incremental Cursor — an opaque pointer marking where a connector's last delta sync stopped.
  • Introspection (RFC 7662) — a provider endpoint reporting a token's current validity and metadata.
  • Materialized View — a stored, queryable snapshot derived from an external system of record, not itself the source of truth.
  • OAuth Scope — a provider-defined string denoting a bounded permission requested/granted during an OAuth flow.
  • PKCE (RFC 7636) — Proof Key for Code Exchange, an OAuth extension preventing authorization-code interception.
  • Permission Graph Schema (PGS) — the canonical, provider-agnostic representation of identities, resources, scopes, and grants.
  • Principal — the connector-local acting subject, prior to identity resolution.
  • Protocol Server — the component publishing canonicalized permission-state events to subscribers.
  • Provenance — the traceable origin of a piece of data back to its source observation.
  • ReBAC — Relationship-Based Access Control, the Zanzibar-style model of expressing permissions as relations in a graph.
  • Resolution Graph — the network of RESOLVES_TO edges merging per-connector shadow identities into canonical ones.
  • Resource (node type) — anything access can be granted to.
  • Revocation Executor — the component turning a RevocationOrder into confirmed provider-side removal.
  • Revocation Order — a request to revoke one or more grants, idempotent by its own ID.
  • Revocation Receipt — the confirmed, audited record that a revocation was verified via a subsequent read.
  • Rich Authorization Requests (RAR, RFC 9396) — an OAuth extension allowing structured, fine-grained authorization detail objects instead of flat scope strings.
  • Risk Class — a coarse severity tier (low/medium/high/unknown) attached to a capability or grant.
  • RLS (Row-Level Security) — a database feature restricting row visibility by a policy predicate, used here for tenant isolation.
  • SCIM (RFC 7643/7644) — System for Cross-domain Identity Management, a standard protocol for provisioning/deprovisioning identities.
  • Scope Normalizer — the component mapping raw provider scope strings to canonical capabilities and risk classes.
  • Sensitivity (resource attribute) — a classification of how confidential a resource is.
  • Service Account (identity kind) — an identity with customer-managed credentials, often used by automation or backend systems.
  • Shadow Identity — a per-connector identity record prior to resolution into a canonical identity.
  • SPKI/SDSI — Simple Public Key Infrastructure / Simple Distributed Security Infrastructure, a decentralized delegation-certificate model.
  • Sync Cursor — see Incremental Cursor.
  • Tenant Isolation — the guarantee that one tenant's data is never visible to another.
  • Token Revocation (RFC 7009) — the OAuth standard for invalidating a previously issued token.
  • Trust Boundary — a point in the architecture where data crosses between differently trusted components.
  • Tuple Store — a Zanzibar-style storage model representing relations as tuples, optimized for consistent, low-latency authorization checks.
  • UCAN — User-Controlled Authorization Networks, a capability-based, decentralized authorization token format (referenced for delegation-model contrast, not adopted).
  • Zookie / Zedtoken — Zanzibar's consistency token mechanism for bounding staleness in authorization checks.
