Provider Adapters wrap one SaaS API each behind the connector contract (§8.4); they hold no cross-connector state and cannot write outside their own namespace (I11). Scope Normalizer maps a provider's raw scope string to a CanonicalCapability and RiskClass (§8.2), recording the mapping version used so a later provider redefinition is detectable (P7). Permission Graph Store is the materialized view of provider truth (I1); every row carries lastSyncedAt and a provenance pointer. Consent/Audit Log is append-only, separately keyed from the graph store, and is the only place a human-readable "who did what, why" narrative lives (P8). Drift Detector runs read-only scans (I12) and emits DriftEvent records; it never mutates the graph. Risk Scorer annotates grants and drift events with a computed severity used for alert ranking and blast-radius sizing. Revocation Executor turns a RevocationOrder into provider API calls and does not consider an order complete until a subsequent read confirms absence (I2, P3). Bulk Revoke Planner computes a reviewable diff before any executor call is issued (P11). Protocol Server exposes canonicalized (never raw-provider) state to subscribers over a versioned wire protocol (§8.6, P9, I14). Client SDK and Telemetry are the external-interface and observability boundary respectively; the queue/job system (BullMQ-class, ADR-12) sits between the graph store and both the drift/revoke and protocol paths, absorbing backpressure (P12).

8. Domain Model

8.1 Node and Edge Types

Node Type Key Fields Notes
Identity id, kind (human/bot/service_account/agent/group), externalIds[], resolvedTo?, status Canonical or per-connector shadow identity (§8.2).
Principal identityId, connectorId The connector-local acting subject; distinct from canonical Identity until resolved.
App id, connectorId, name, publisher The third-party application that was granted access.
Resource id, kind, parent?, sensitivity Anything access can be granted to.
Scope rawName, connectorId, canonicalCapability, riskClass The raw provider scope string plus its normalization (§8.2).
Grant id, principalId, appId, scope[], state The lifecycle-tracked authorization (§8.3).
Credential id, grantId, handleRef, kind Opaque reference to the encrypted secret backing a grant (never the secret itself, P5).
Edge Type From → To Semantics
DELEGATES_TO Identity → Identity Agent's authority chain back to a human/service account (Phase 10).
GRANTS Principal → Grant The act of a provider reporting this authorization.
AUTHORIZES Grant → Resource What the grant permits access to.
RESOLVES_TO Identity → Identity Per-connector shadow → canonical identity (§8.2).
OWNS Identity → App Who registered/owns the third-party app (when knowable).
MEMBER_OF Identity → Identity (group) Group/team nesting, cycle-detected at sync time (Phase 4).

8.2 Scope Normalization — Worked Mapping

Provider Raw Scope String Canonical Capability Risk Class
Google OAuth https://www.googleapis.com/auth/drive file.readwrite.all high
Google OAuth https://www.googleapis.com/auth/drive.readonly file.read.all medium
GitHub OAuth repo code.readwrite.all high
GitHub OAuth read:org org.read.metadata low
Slack OAuth chat:write messaging.write medium
Slack OAuth channels:history messaging.read.content medium
Microsoft Graph Mail.ReadWrite email.readwrite high
Microsoft Graph User.Read identity.read.self low

Normalization is versioned per (connectorId, pgsVersion) pair (P7). RFC 9396 Rich Authorization Requests inform the target shape for providers that support structured authorization_details instead of flat scope strings — the normalizer treats a RAR object as a pre-structured input requiring no string-heuristic mapping.

8.3 Grant Lifecycle State Machine

From Event To Notes
— first confirmed enumeration read Discovered Provenance recorded (I1).
Discovered second consecutive confirming sync Active Two-sync confirmation avoids one-shot API flukes.
Active drift detector flags (unused/creep/dormant) Drifted Read-only transition (I12); no side effect yet.
Drifted subsequent sync shows renewed usage Active Re-confirmed; drift was a false positive or usage resumed.
Active or Drifted operator/plan issues RevocationOrder RevokeRequested P11 diff must precede this transition for bulk plans.
RevokeRequested connector revoke() call fails (network/5xx) RevokeRequested Retried with backoff; stays pending (I9 idempotent retry).
RevokeRequested connector revoke() returns success but next read still shows grant RevokeFailed I2 — write success is not proof; escalate.
RevokeFailed manual operator retry or provider-side fix RevokeRequested Re-enter the confirm loop.
RevokeRequested subsequent provider read shows absence RevokeConfirmed Terminal success state.
Active, Discovered, or Drifted identity no longer enumerated (2 consecutive full syncs) Orphaned TTL-based; distinct from a deliberate revoke.
Active grant carries a provider-declared expiry that elapses Expired No action taken by Mesh; observational only (P2).

8.4 Connector Contract (Interface Table)

Operation Purpose Idempotency Rate-Limit Semantics
enumerate(cursor?) Full or resumed listing of identities/resources/grants Idempotent — replay from any valid cursor reproduces the same logical state Bound by I4's steady-state budget; opt-in 60% ceiling for initial sync only
incrementalCursor(cursor) Delta since last cursor Idempotent — re-applying the same delta page is a no-op upsert Same budget tier as enumerate
revoke(grant, reason) Request removal of a specific grant at the provider Must be safe to call twice for the same grant (I9) Capped separately from read traffic; bulk plans additionally capped (P11, §4)
verify(grant) Read-after-write confirmation of a prior revoke Idempotent by construction (pure read) Counts against the same steady-state budget as enumeration

A connector that cannot implement incrementalCursor declares this in its ConnectorSpec capability flags and is restricted to a low poll-cadence tier (§4).

8.5 Worked Example, Malformed Input, Failure Path

Worked example: GitHub connector enumerates an org; Principal "alice-gh" receives Grant g-441 via App "internal-ci-bot" with Scope repo → canonical code.readwrite.all / high. RESOLVES_TO edge merges "alice-gh" into canonical Identity "alice@acme.com" (email + SSO-subject match, I7). Drift detector later observes g-441's lastUsedAt is 97 days stale against a 90-day dormant-identity threshold (§17.2.1) → emits DriftEvent referencing g-441 and its evidence (I13); grant transitions Active → Drifted.

Malformed input example: GitHub API returns a scope string repo:invalid-legacy not present in the normalizer's mapping table for the connector's declared pgsVersion. Per P7, this is not silently dropped or best-effort-guessed: the edge is written with canonicalCapability = "unmapped", riskClass = "unknown", and a DriftEvent-adjacent ScopeMappingGapEvent is queued for the normalizer maintainers — never silently downgraded to a known-safe class.

Failure-path example: A RevocationOrder for grant g-441 calls GitHub's collaborator -removal endpoint, receives HTTP 204, but the next scheduled sync (15 min later, medium-tier cadence) still enumerates the grant — the provider's edge cache had not yet propagated the removal. Per I2, the order stays RevokeRequested, not RevokeConfirmed; a forced synchronous re-poll is issued at t+20 min (§4 p95 propagation budget); on confirmation the order transitions to RevokeConfirmed and the receipt is audit-logged (I5).

8.6 Protocol Wire Format (Publish/Subscribe)

Envelope fields (all publish/subscribe messages): protocolVersion (semver major.minor), eventType (grant.created | grant.revoked | grant.drifted | identity.merged | heartbeat), tenantId, sequenceNumber (monotonic per-tenant, gap-detectable), canonicalPayload (a serialized PGS node/edge subset — never raw provider JSON, I14), emittedAt. Subscribers detect gaps via sequenceNumber and may request a bounded replay from the Protocol Server's retained window; beyond that window a full resync via the query API is required (P9's additive-only guarantee applies to canonicalPayload field evolution only, not to delivery guarantees, which are documented separately per Phase 8).

Design principles (§6)

  • P1 — Mesh observes and revokes; it never becomes the authorization decision point. Rule: no Mesh component sits in the request path of a protected resource. Tradeoff: Mesh cannot block access in real time, only after-the-fact. Operational implication: revocation latency is bounded by provider propagation, not Mesh's own clock. Violating this recreates the confused-deputy hazard (Hardy 1988) — Mesh's own authority becomes ambiguous relative to the provider's.
  • P2 — Every grant is reconciled from the provider, never inferred. Rule: a PGSAccessEdge may only be created or updated from a connector's enumerate/ incrementalCursor response. Tradeoff: no representation of hypothetical or not-yet-observed grants. Violating this produces phantom edges that desync from ground truth — a drift false-negative.
  • P3 — Revocation is idempotent and verifiable. Rule: a RevocationOrder is not RevokeConfirmed until a subsequent provider read shows absence. Tradeoff: adds a read-after-write round trip to every revoke. Violating this reproduces the CircleCI 2023 pattern — revoked at the provider console, but a long-lived token elsewhere still works.
  • P4 — The graph is a materialized view with provenance, not ground truth. Rule: every node/edge carries lastSyncedAt and an evidence pointer to the raw response. Tradeoff: staleness is always possible and must be surfaced, never hidden. Violating this creates false confidence in stale data (I1, I6).
  • P5 — No third-party credential is stored in reusable plaintext form. Rule: every CredentialHandle is an encrypted reference, never the bearer secret itself in the clear. Tradeoff: added envelope-encryption/KMS operational complexity on every read path. Violating this makes Mesh the highest-value breach target in the customer's estate — the 2022 Okta/Lapsus$ pattern, at Mesh's own scale.
  • P6 — Connectors are sandboxed and mutually distrusting. Rule: a connector process has its own network egress allowlist and cannot write to another connector's node/edge namespace (I11). Tradeoff: per-connector resource overhead. Violating this lets a single compromised connector cascade — the 2021 Codecov supply-chain pattern.
  • P7 — Scope normalization is lossy by design, and the loss is recorded. Rule: a CanonicalCapability is coarser than the raw provider scope string; the mapping version used is stamped on the edge. Tradeoff: two provider scopes may canonicalize to the same capability even if their real semantics diverge slightly. Violating this (by silently re-mapping without a version bump) hides the day a provider redefines a scope string's meaning — a documented pitfall class (Phase 1 N.6).
  • P8 — Every mutation is audit-logged with actor and reason, append-only. Rule: no in-place update or delete on the audit log; every entry references the acting principal. Tradeoff: monotonic storage growth. Violating this makes incident response forensically blind (T6, Consent-Log Tampering).
  • P9 — The protocol is additive-only; breaking changes require a new major version. Rule: no field is repurposed or removed within a major version of the publish/subscribe wire format (§8.6). Tradeoff: N and N+1 consumers must be served simultaneously during any migration window. Violating this causes downstream apps to silently misinterpret grant state — an RFC 9396-scale ambiguity, at protocol scope.
  • P10 — Discovery prefers push over pull, but never assumes push is complete. Rule: webhook-driven connectors still reconcile on a longer poll cadence. Tradeoff: dual-path complexity even when webhooks are fully supported. Violating this creates a webhook-gap blind spot (Phase 4 N.6, "pagination cursor drift" class).
  • P11 — Bulk operations require a pre-computed, reviewable blast-radius plan before execution. Rule: no RevocationOrder batch executes without a prior diff shown to an operator. Tradeoff: added latency and UI friction before any bulk action. Violating this turns bulk revoke into an accidental or malicious denial-of-service vector (T7).
  • P12 — Backpressure is applied at the connector, never at the tenant's provider account. Rule: a connector self-throttles to I4's budget rather than retrying past the provider's own limit. Tradeoff: Mesh's sync throughput is capped below the provider's true ceiling. Violating this can trip the provider's own anti-abuse system, locking the tenant out of their own account.
  • P13 — Consistency is tenant-scoped and read-your-writes for the acting operator, not globally linearizable. Rule: a query issued immediately after a write by the same operator sees that write; cross-tenant aggregate queries may lag. Tradeoff: no globally-consistent snapshot across tenants at any instant. Violating this creates false precision claims about cross-tenant analytics (PhaseDeferred("Phase 8")).
  • P14 — Every connector implements the identical interface; there is no privileged first-party code path. Rule: first-party and community connectors pass the same conformance suite (§8.4, Phase 11). Tradeoff: first-party connectors cannot take shortcuts unavailable to the community. Violating this creates a two-tier ecosystem that defeats the credibility of the open protocol (§2).
