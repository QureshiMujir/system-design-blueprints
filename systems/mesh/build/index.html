⬜ Phase 0 — Skeleton, CI, Connector SDK Harness §12

Objectives

Stand up the monorepo, CI gate, and a connector conformance harness capable of validating a connector against ConnectorSpec (§11) before any live provider integration exists. Prove the harness against a mock/fixture provider, not a real one.

Deliverable

A CI pipeline that fails a PR introducing a connector violating ConnectorSpec's capability contract, plus a passing conformance run against the mock-provider fixture.

Acceptance

Conformance suite completes in under 90 seconds against the mock fixture; CI blocks merge on any of 3 seeded violation fixtures (fixtures/mock-provider/cursor-gap.json, fixtures/mock-provider/missing-capability-flag.json, fixtures/mock-provider/malformed-scope.json); zero flaky runs across 20 consecutive CI executions.

Fixtures

fixtures/mock-provider/happy-path.json — clean enumerate + 2-page incrementalCursor, expected output: 2 identities, 1 resource, 1 grant, cursor advances twice. cursor-gap.json — page 2 of 2 dropped mid-stream, expected output: harness FAILs with CursorMismatch. missing-capability-flag.json — connector claims revoke: true but implements no revoke export, expected: harness FAILs at registration. malformed-scope.json — scope string absent from any mapping, expected: harness reports ScopeMappingGap, not a silent pass.

Pitfalls

Treating the mock provider as "good enough forever" and never revisiting fixture realism once live connectors exist (Phase 1 must re-validate against real cassettes). Building the conformance harness with hidden first-party shortcuts that community connectors in Phase 11 cannot pass (violates P14) — catch this by having the harness itself be provider-agnostic from day one, never importing anything from connectors/.

⬜ Phase 1 — First Five Provider Connectors + Enumeration §13

Objectives

Implement enumerate/incrementalCursor (read-only, no revoke) for five real providers: Google Workspace, GitHub, Slack, Microsoft Graph, Notion. No write scopes requested (P5, P6).

Deliverable

Five connectors passing the Phase 0 conformance harness against recorded real-provider cassettes, each enumerate-only (capabilities.revoke = false).

Acceptance

Each connector completes a 1,000-identity fixture cassette sync in under its declared per-connector time budget (Google Workspace ≤ 30 min, GitHub ≤ 20 min, Slack ≤ 15 min, Microsoft Graph ≤ 25 min, Notion ≤ 15 min); zero scope strings map to unmapped on the recorded cassette corpus (conformance/cassettes/{provider}/happy-path.cassette.json); I4's 20%-budget ceiling never exceeded during any fixture run, verified via rate_budget_exceeded_total staying at 0.

Fixtures

conformance/cassettes/github/1000-identity-org.cassette.json (recorded, real GitHub org enumeration, redacted) — expected: 1,000 identities, correct bot/human split. conformance/cassettes/github/malformed-scope-response.cassette.json — a scope string repo:invalid-legacy injected — expected: ScopeMappingGapEvent, not silent drop. conformance/cassettes/slack/rate-limited-partial.cassette.json — simulated 429 mid-sync — expected: cursor does not advance past the last successfully committed page (I8). conformance/cassettes/notion/replay-regression.cassette.json — a previously-fixed pagination bug's exact recorded sequence, replayed to prevent regression.

Pitfalls

Provider scope strings silently changing meaning across an API version bump — a real recurring hazard (P7's reason for versioned mapping) — manifests as a canonicalCapability that no longer matches observed behavior; root cause: provider deprecates a scope's semantics without renaming the string; debug via cassette diff against the provider's changelog; signal: a spike in ScopeMappingGap events post-provider-release; recovery: bump the normalizer's mapping version and re-tag affected edges. Pagination-cursor drift causing phantom deletions: an API returns pages in a different order across retries, and a naive "resource missing from this page = deleted" heuristic wrongly orphans live resources; root cause: treating page absence as deletion evidence instead of requiring full-cycle absence; debug via the orphan_resource_total metric spiking correlated with a retry burst; recovery: require two consecutive full syncs before any orphan transition (§8.3), never a single page.

⬜ Phase 2 — Permission Graph Schema + Store §14

Objectives

Freeze PGS v1 (§8, §11) as SQL DDL and TypeScript/Zod types; stand up the tenant-isolated Postgres graph store (ADR-04) backing all five Phase-1 connectors' output.

Deliverable

A running Postgres graph store accepting all five Phase-1 connectors' upserts, with RLS verified via an adversarial cross-tenant query suite (I10).

Acceptance

Cross-tenant query suite (conformance/rls/cross-tenant-adversarial.suite.json, 25 attack queries) returns zero leaked rows; a 1.8M-edge synthetic tenant fixture (benchmarks/fixtures/large-tenant-1.8m-edges.json, matching §34's derivation) sustains p95 query latency ≤ 350 ms on the point + 2-hop traversal benchmark; identity resolution on the same fixture produces zero weak-signal auto-merges (weak_signal_automerge_total = 0, I7).

Fixtures

conformance/rls/cross-tenant-adversarial.suite.json — 25 queries attempting to read tenant B's data while authenticated as tenant A, expected: 0 rows for all 25. conformance/identity-resolution/soft-merge-review-queue.fixture.json — same email, no SSO subject match, expected: proposed merge in review queue, not auto-merged. conformance/identity-resolution/cross-domain-reject.fixture.json — different email, matching display name and domain, expected: flagged for review, never auto-merged (I7).

Pitfalls

Building indexes only against the "happy path" query shape and discovering under load that the resolution-graph traversal (resolvedTo chain) requires a separate covering index not originally planned — budget an index-tuning pass against the 1.8M-edge fixture before declaring the phase done, not after. Treating RLS as sufficient alone without a query-engine tenant filter as the first line of defense (I10 requires both — RLS is the second line, not the only line).

⬜ Phase 3 — Scope Normalization + Risk Scoring §15

Objectives

Formalize the scope normalizer (§8.2, ADR-05, P7) as a versioned, testable component; add the risk-scoring layer that annotates every Grant and later every DriftEvent with a RiskClass.

Deliverable

A risk-scoring service producing a deterministic, replayable score for any Grant given its scope set and resource context, exposed via the query API.

Acceptance

100% of the Phase-1 cassette corpus's grants receive a non-unknown RiskClass except the deliberately-injected malformed-scope-response.cassette.json case (§13.5), which must receive exactly unknown; risk-score computation for a 1.8M-edge fixture completes in under 45 minutes on a single worker (bounding a full re-score after a mapping-version bump).

Fixtures

conformance/risk-scoring/direct-vs-group-grant.fixture.json — same capability, one direct one via 3-deep group nesting, expected: group-path grant scores strictly higher. conformance/risk-scoring/mapping-version-bump-replay.fixture.json — a mapping-version bump mid-corpus, expected: pre-bump edges retain their original score until re-synced, never silently re-scored in place (P9-adjacent — no retroactive mutation without a new sync).

Pitfalls

Conflating "the provider calls this scope 'admin'" with "this is actually high-risk" — providers name scopes inconsistently (Slack's admin app-management scope is a different risk tier than GitHub's admin:org); the canonical capability, not the raw provider label, must drive the score (this is exactly what P7's normalization exists to prevent). Recomputing risk scores in place on a mapping-version bump instead of treating it as a new observation — violates the "graph is a materialized view" principle (I1) by mutating historical scoring retroactively.

⬜ Phase 4 — Incremental Sync + Cursors §16

Objectives

Harden the incremental-sync path across all five connectors for 7-day unattended operation; implement the poll-cadence tiers (§4) and the webhook-opportunistic layer (P10, ADR-08).

Deliverable

Continuous scheduled sync running unattended for 7 days across a 5-connector, multi-tenant fixture deployment with zero manual intervention.

Acceptance

Sync success rate ≥ 99.5% per connector-tenant pair over the 7-day soak (benchmarks/soak/7-day-multi-tenant.json); webhook-triggered syncs complete within 90 seconds of webhook receipt for GitHub/Slack; zero MEMBER_OF cycle causing unbounded traversal (verified via a synthetic 6-level-deep group-cycle fixture terminating cleanly).

Fixtures

conformance/cycles/group-nesting-6-deep-cycle.fixture.json — a deliberately cyclic group structure, expected: cycle detected, traversal terminates, group_nesting_cycle_total incremented, no stack overflow. conformance/webhooks/github-push-to-resync.fixture.json — simulated GitHub webhook payload, expected: targeted incrementalCursor call scoped to the affected resource only, not a full re-sync.

Pitfalls

Webhook payloads arriving out of order relative to the poll cursor's view of the world, causing a moment of apparent inconsistency (a webhook says "revoked" but the next scheduled poll hasn't caught up) — mitigated by treating webhook-triggered updates as provisional until the next confirming poll (extends I2's read-after-write discipline to the webhook path). A group-nesting cycle causing unbounded recursive traversal if cycle detection is implemented as a depth counter alone rather than a visited-set check — a sufficiently large cycle can exceed a naive depth counter's assumptions; use a visited-set, not a counter.

⬜ Phase 5 — Drift Detection §17

Objectives

Implement the read-only Drift Detector (I12) covering the eight detector classes from the original operational experience, re-scoped to the observational, non-mutating contract.

Deliverable

Eight running detectors producing attributed DriftEvent records against the Phase-2 store, verifiably incapable of mutating the graph (I12 enforced at the DB-role level).

Acceptance

Detector precision ≥ 90% against a synthetic labeled fixture (conformance/drift/synthetic-labeled-1000.fixture.json, 1,000 seeded known-positive/negative cases); zero writes attempted from the detector's DB role, verified by drift_write_attempt_blocked_total staying at 0 across the full detector suite run; every emitted DriftEvent carries a non-null grantId and evidenceRef (100% attribution, I13).

Fixtures

conformance/drift/synthetic-labeled-1000.fixture.json — 1,000 synthetic grants with known ground-truth drift labels across all 8 classes, expected: ≥ 90% precision per class. conformance/drift/read-only-role-violation.fixture.json — attempts a write from the detector's connection role, expected: hard rejection at the database permission layer, not just application-level refusal.

Pitfalls

Shadow admin via transitive grants — an identity with no direct admin grant but reachable admin-equivalent access through a chain of group memberships and app-level roles; naive per-edge detectors miss this because no single edge looks dangerous. Root cause: detectors scoped to single-edge risk instead of transitive reachability; debug via the resolution/ group-membership graph traversal (Phase 4's cycle-safe traversal, reused here); signal: cross -app-admin detector count seems low despite known org sprawl; recovery: extend the cross-app detector to traverse MEMBER_OF chains, not just direct Grant records, bounded by the same depth cap as Phase 4.

⬜ Phase 6 — Revocation Executor + Receipts §18

Objectives

Implement the revoke/verify connector operations (§8.4) and the Revocation Executor's idempotent, receipted order lifecycle (§8.3, I2, I9, P3).

Deliverable

A working revoke path for all five Phase-1 connectors, receipted, idempotent, and conformance-tested against both success and provider-lag failure paths (§8.5's failure-path example).

Acceptance

100% of conformance/revoke/*.fixture.json cases pass; replaying an already-RevokeConfirmed order is a verified no-op (duplicate_revoke_side_effect_total = 0, I9); p95 revocation propagation stays within §4's 20-minute budget on the 5-connector fixture corpus.

Fixtures

conformance/revoke/happy-path-per-connector.fixture.json (×5, one per connector) — expected: RevokeConfirmed within the connector's declared propagation budget. conformance/revoke/ provider-lag-partial-propagation.fixture.json — mirrors §8.5's failure-path example exactly (204 response, grant still enumerable next sync) — expected: order stays RevokeRequested, forced re-poll issued, eventual RevokeConfirmed. conformance/revoke/idempotent-replay. fixture.json — the same order submitted twice — expected: second submission is a verified no-op, no duplicate provider-side call.

Pitfalls

Revocation that succeeds at the identity/membership layer but leaves a long-lived refresh token functioning elsewhere — the exact CircleCI 2023 pattern (cited per §5, applied here); root cause: treating "removed from group/channel" as equivalent to "credential invalidated" when the provider's OAuth token lifecycle is independent of membership state; debug via explicit verify() calls against the token/session layer, not just the membership API; signal: a RevokeConfirmed grant whose underlying credential (CredentialHandle) still authenticates in a later, unrelated connector call; recovery: extend verify() per connector to check both membership absence and, where the provider's API supports it, token validity.

⬜ Phase 7 — Bulk Revoke + Blast-Radius Preview §19

Objectives

Implement the Bulk Revoke Planner (P11): a reviewable, diffed plan computed before any batch of RevocationOrders executes.

Deliverable

A plan-diff-confirm-execute pipeline for bulk revocation, with per-plan audit trail (P8) and a rate-capped batch executor built on the Phase-6 idempotent order primitive.

Acceptance

A 500-edge bulk plan completes end-to-end (plan → diff → confirm → execute → all receipts confirmed) in ≤ 90 seconds on the fixture corpus (benchmarks/bulk-revoke/500-edge-plan.json); zero service-account/agent-kind edges included in a plan without an explicit override flag, verified across 50 randomized fixture plans; batch execution never exceeds the distinct bulk-revoke rate cap (§4) even when the underlying connectors have separate spare read-budget.

Fixtures

conformance/bulk-revoke/500-edge-diff-accuracy.fixture.json — expected diff matches actual post-execution graph state exactly. conformance/bulk-revoke/service-account-default- exclusion.fixture.json — a plan pattern that would match 3 service accounts, expected: those 3 excluded by default, present in the diff as "excluded, override required." conformance/bulk-revoke/partial-batch-failure.fixture.json — 2 of 500 orders fail mid-batch, expected: the other 498 still confirm independently (I9's idempotency applied per-order, not per-batch).

Pitfalls

A blast-radius preview computed against a graph snapshot that goes stale between plan computation and execution confirmation (an operator reviews a plan, takes 20 minutes to approve, and the underlying grant set has shifted) — root cause: no staleness check on plan execution; debug via comparing the plan's snapshot cursor against current state at execute time; signal: executed diff differs from previewed diff; recovery: re-diff at execute time and require re-confirmation if the delta exceeds a small tolerance, rather than executing a stale plan blindly.

⬜ Phase 8 — Open Protocol Server + Subscriptions §20

Objectives

Implement the publish/subscribe Protocol Server (§8.6, ADR-10, P9, I14) so downstream applications consume canonicalized permission state without direct provider polling.

Deliverable

A running Protocol Server accepting subscriptions and emitting gap-detectable, replayable events for grant.created/grant.revoked/grant.drifted/identity.merged, with a reference Client SDK.

Acceptance

A subscriber disconnected for up to the retention window (target: 1 hour) recovers via bounded replay with zero missed events, verified by sequence-number continuity across 10 simulated disconnect/reconnect cycles (benchmarks/protocol/disconnect-reconnect-10x.json); zero raw provider field names detected in canonicalPayload across the full Phase-1–7 event corpus (I14, automated scan, not manual review).

Fixtures

conformance/protocol/gap-replay-within-window.fixture.json — disconnect for 30 minutes (within the 1-hour window), expected: full replay, zero gaps. conformance/protocol/ gap-replay-beyond-window.fixture.json — disconnect for 2 hours, expected: replay unavailable, subscriber correctly instructed to fall back to a full resync via the query API. conformance/protocol/raw-payload-leak-scan.fixture.json — a deliberately malformed serializer that leaks a raw GitHub field name, expected: I14 scan catches it, build fails.

Pitfalls

Treating the protocol's sequenceNumber as globally monotonic instead of per-tenant, creating false gap-detection across tenant boundaries when in fact P13's tenant-scoped consistency model never promised global ordering. Allowing a "just this once" raw payload field to leak into canonicalPayload under time pressure — the single most likely way I14 gets violated in practice; caught only by the automated scan, never by code review alone, which is why the scan is a build-time gate, not a checklist item.

⬜ Phase 9 — SCIM / Webhook Ingest §21

Objectives

Add SCIM 2.0 (RFC 7643/7644) as a first-class discovery mechanism alongside polling and ad-hoc webhooks (ADR-08), for providers/IdPs that push provisioning events natively (Okta, Entra ID via SCIM).

Deliverable

A SCIM-receiving connector (Okta) live alongside the five poll-based connectors, verified to reconcile correctly when a SCIM push is missed or arrives out of order.

Acceptance

100% of SCIM Delete operations against a test tenant result in the corresponding Identity's Orphaned transition within 5 minutes (SCIM push path) or within the connector's poll cadence as a fallback (verified by disabling the push path in a fixture run); introspection-based verify() reduces the false-RevokeConfirmed rate to zero on the conformance/revoke/provider-lag-partial-propagation.fixture.json case reused from Phase 6 with introspection enabled.

Fixtures

conformance/scim/create-update-delete-roundtrip.fixture.json — a full SCIM lifecycle sequence, expected: matching Identity state transitions at each step. conformance/scim/missed-push-poll-fallback.fixture.json — a SCIM Delete deliberately dropped, expected: the poll-cadence reconciliation still catches the orphaning within its tier's window. conformance/introspection/stronger-verify-signal.fixture.json — reuses Phase 6's provider-lag case, expected: introspection catches the still-valid token that a membership-API read alone would have missed.

Pitfalls

Trusting SCIM push exclusively and disabling the poll floor "since SCIM is push-based and therefore complete" — directly violates P10; SCIM delivery is not guaranteed exactly-once or even at-least-once in every IdP implementation, and Mesh must never assume it. Confusing "introspection says the token is valid" with "the token is being used" — introspection verifies validity, not usage; the two are different signals feeding different detectors (revocation-confirmation vs. drift's lastUsedAt).

⬜ Phase 10 — Machine / Agent Identities §22

Objectives

Make the agent identity kind (§8.1) first-class: delegation chains (DELEGATES_TO), capability-scope declarations, and expiry-aware drift signals for autonomous agent credentials.

Deliverable

Agent-identity support with populated DELEGATES_TO chains for at least one OIDC-based agent platform integration, plus the expiry-aware drift extension and the blast-radius query pattern.

Acceptance

100% of ingested agent identities carry a non-null delegatedFrom-equivalent (DELEGATES_TO edge to a human or service account) or are flagged as an unattributed-agent drift signal (never silently accepted as ownerless); blast-radius query for a 5-level delegation chain completes within the same p95 budget as any other 2-hop-class traversal extended proportionally (§4), verified on benchmarks/agent/5-level-delegation-chain.json.

Fixtures

conformance/agent/unattributed-agent-flag.fixture.json — an agent identity with no resolvable DELEGATES_TO target, expected: flagged, not silently accepted. conformance/agent/expiry-approaching-drift.fixture.json — an agent grant with accessExpiresAt inside a configurable warning window, expected: DriftEvent emitted before expiry, not after. conformance/agent/blast-radius-5-level-chain.fixture.json — expected output: the exact resource set reachable transitively, matching a hand-computed reference set.

Pitfalls

Treating an agent identity's declared capability scopes as equivalent to its observed behavior — an agent that only ever exercises a fraction of its granted scopes still carries the full risk of what it could do, and the risk score must reflect declared capability, not observed restraint (a documented distinction from Phase 3's scoring model, made explicit here because agents are the class most likely to be over-provisioned "just in case").

⬜ Phase 11 — Conformance + Performance Hardening §23

Objectives

Bring the full connector conformance suite, fuzzing corpus, and performance-regression gate to the standard required for third-party (community) connector authorship (P14) and for production SLO confidence across all prior phases.

Deliverable

A public conformance suite, fuzzing corpus, and CI performance gate, plus a documented, scaffold-driven path for third-party connector authorship.

Acceptance

An external test author (a team member with no prior exposure to any first-party connector source) builds and conformance-passes a sixth connector (Notion excluded, a genuinely new one — e.g., Linear) using only the scaffold and public docs, in under 3 days; fuzzing corpus (fuzz/scope-strings/, fuzz/provider-payloads/) runs 4 hours per CI cycle with zero unhandled-exception crashes; all M# performance targets (§30) pass in CI on every merge to main for 30 consecutive days pre-declaring the phase done.

Fixtures

conformance/full-suite/all-phases-regression.suite.json — the complete accumulated fixture corpus from Phases 0–10, run as a single gate. fuzz/scope-strings/corpus/ — seeded with every real malformed scope string discovered in production cassettes to date. fuzz/provider-payloads/corpus/ — seeded with every recorded pagination-drift and partial-sync cassette from Phases 1 and 4.

Pitfalls

Declaring "conformance-complete" based on suite size alone rather than external-author success — a suite that only ever validates against first-party connectors' own assumptions can pass green while still being unusable by a real community author; the §23.4 external- author acceptance test exists specifically to catch this. Under-resourcing the fuzzing corpus with only synthetic cases instead of real recorded malformed input, missing the exact class of bug (provider redefining scope semantics, §13.6) that fuzzing is meant to catch.
