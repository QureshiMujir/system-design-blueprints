32. Mental Models & First Principles

  1. MM1 — A permission graph is a cache of other people's databases. Staleness is the product's core risk, not an incidental bug. Predicts: every UI surface must show freshness, never hide it. Bug class without it: silent trust in stale data leading to a revoke-that-didn't-happen incident. Resolved in §7 (I1, I6), §3.
  2. MM2 — A write's success response is not proof of its effect. Predicts: every mutating operation needs an independent confirming read. Bug class without it: the CircleCI-2023 pattern, generalized (T10, FM-4). Resolved in §18 (I2, P3).
  3. MM3 — Provider rate limits are a hard physical constraint, not a tuning parameter. Predicts: no amount of Mesh-side engineering raises the ceiling on how fast a tenant can be synced; the only lever is what you do within the budget. Bug class without it: chasing sync-speed improvements that hit a wall no code change can move. Resolved in §31, §34.
  4. MM4 — A scope string is a label a provider chose, not a stable contract. Predicts: normalization must be versioned and re-checkable, because the same string can mean something different tomorrow. Bug class without it: silent risk misclassification after a provider API change (§13.6). Resolved in §8.2, P7.
  5. MM5 — Observation and action must be architecturally separate, not just conventionally separate. Predicts: a read-only database role, not a code-review rule, is what actually stops a detector from mutating state. Bug class without it: scope creep in a "read-only" component that quietly gains a write path over time. Resolved in §7 (I12), §17.
  6. MM6 — Identity resolution errors are asymmetric in cost. A missed merge is an inconvenience; a false merge can revoke the wrong human's access. Predicts: the default must always be conservative, even at the cost of more manual review. Bug class without it: an aggressive fuzzy-matcher causing a security incident instead of preventing one. Resolved in §7 (I7), ADR-27.
  7. MM7 — A grant with no usage signal is not the same as a grant with confirmed non-use. Predicts: "unused permission" detection must explicitly model missing telemetry as a coverage gap, not a default answer either way. Bug class without it: false-positive drift alerts on providers with partial usage-API support. Resolved in §17.8.
  8. MM8 — A protocol outlives its first implementation; treat every field as a public promise the moment it ships. Predicts: additive-only evolution is cheaper across the protocol's lifetime than any amount of "we'll fix it in v2" flexibility. Bug class without it: downstream consumers silently misinterpreting a repurposed field. Resolved in §8.6, P9.

Required reading (§5)

Books

  • Ross Anderson, Security Engineering (3rd ed.), Ch. 4 (Access Control) and Ch. 6 (Distributed Systems) — the protection-matrix framing and the confused-deputy hazard. Applied in §8 Domain Model and P1.
  • Justin Richer & Antonio Sanso, OAuth 2 in Action, chapters on token lifecycle, scope design, and revocation — grounds the connector OAuth flow and RFC 7009 handling. Applied in Phase 1 and Phase 6.
  • Yvonne Wilson & Abhishek Hingnikar, Solving Identity Management in Modern Applications, chapters on federation and SCIM provisioning — grounds the SCIM/webhook ingest design. Applied in Phase 9.
  • Evan Gilman & Doug Barth, Zero Trust Networks, chapter on the trust engine and context-aware access — informs the risk-scoring model (§8, Phase 3). Applied in Phase 3.
  • Martin Kleppmann, Designing Data-Intensive Applications, Ch. 5 (Replication) and Ch. 9 (Consistency and Consensus) — grounds the graph store's consistency model. Applied in ADR-11 and Phase 2.
  • Google SRE team, Site Reliability Engineering, chapters on monitoring distributed systems and incident response — grounds Operational Readiness. Applied in Operational Readiness.
  • Alex Petrov, Database Internals, chapters on B-trees and LSM trees — grounds the graph-store storage-engine ADR. Applied in ADR-04.

Papers

  • Ruoming Pang, Ramon Caceres, et al., "Zanzibar: Google's Consistent, Global Authorization System," USENIX ATC 2019 — tuple-based ReBAC and zookie/zedtoken consistency tokens. Applied in ADR-04, ADR-11, §33 Comparative Architecture.
  • Arnar Birgisson et al., "Macaroons: Cookies with Contextual Caveats for Decentralized Authorization," NDSS 2014 — bearer-credential attenuation informs CredentialHandle design. Applied in §11, Phase 6.
  • Butler Lampson, "Protection," ACM Operating Systems Review, 1974 — the access matrix that underlies every node/edge type in §8. Applied in §8 Domain Model.
  • Norm Hardy, "The Confused Deputy Problem," ACM SIGOPS Operating Systems Review, 1988 — the exact hazard P1 exists to prevent. Applied in P1, §24 Threat Model.
  • Ravi Sandhu, Edward Coyne, Hal Feinstein, Charles Youman, "Role-Based Access Control Models," IEEE Computer, 1996 — the RBAC baseline Mesh's RiskClass/capability model is contrasted against. Applied in ADR-05, §33.
  • Vincent Hu, David Ferraiolo, D. Richard Kuhn et al., NIST SP 800-162, "Guide to Attribute Based Access Control (ABAC) Definition and Considerations," 2014 — the ReBAC-vs-RBAC-vs-ABAC frame used throughout §8 and ADR-05. Applied in §8, ADR-05.
  • Ronald Rivest & Butler Lampson, "SDSI: A Simple Distributed Security Infrastructure," 1996 — decentralized naming and delegation, informs the agent delegatedFrom chain. Applied in Phase 10.
  • Carl Ellison et al., RFC 2693, "SPKI Certificate Theory," 1999 — capability-oriented certificate delegation, an alternative model discussed in Alternative Architectures. Applied in §36 Alternative Architectures.

Reference Implementations

  • SpiceDB (authzed/spicedb) — dirs internal/datastore/, pkg/tuple/. Lesson: tuple-based relation storage with zookie/zedtoken consistency tokens for read-your-writes across a distributed store. Pitfall not to copy: SpiceDB's tuples are the authorization decision surface; Mesh's edges are observational facts with provenance — treating a provider-reported grant as a first-class relation without a provenance pointer loses drift detection entirely. Applied in ADR-04, Phase 2.
  • OpenFGA (openfga/openfga) — dirs pkg/typesystem/, storage/. Lesson: versioned authorization models per store, type-safe relation definitions. Pitfall: OpenFGA is designed to be called at request time as the Policy Decision Point; copying that request-time check API would violate P1 — Mesh is never in the request path. Applied in ADR-04, ADR-10.
  • Cedar (cedar-policy/cedar) — dirs cedar-policy-core/src/ast/, cedar-policy-validator/. Lesson: a policy language with schema-validated, formally verified semantics. Pitfall: Cedar assumes a closed, single-authority schema; Mesh's scope normalizer must tolerate an open-world assumption (a provider can introduce an unrecognized scope string mid-sync). Applied in §8.2, ADR-05.
  • Keycloak (keycloak/keycloak) — dirs services/.../authorization/, federation/. Lesson: the federation/broker pattern for aggregating multiple upstream IdPs. Pitfall: Keycloak is itself an IdP; Mesh must not grow authentication responsibilities (non-goal, §1). Applied in Phase 9 (SCIM/webhook ingest).
  • Hydra / ORY (ory/hydra) — dirs oauth2/, consent/. Lesson: consent-flow state machine and a reference RFC 7662 introspection endpoint. Pitfall: Hydra issues tokens; Mesh never issues third-party tokens, only observes and revokes them — copying its issuance code path would violate P3. Applied in Phase 1, Phase 6.
  • Casbin (casbin/casbin) — dirs model/, rbac/, persist/. Lesson: a pluggable storage-adapter pattern usable for ConnectorSpec pluggability. Pitfall: Casbin's enforcement is synchronous, in-process; revocation must instead be async, retryable, and receipt-based (I9). Applied in Phase 6, ADR-06.

Glossary (§38) · 51 terms · site-wide glossary

Access Path
how a grant reaches an identity: direct, via group, via role, or inherited.
Agent (identity kind)
an autonomous, often LLM-backed identity with a delegation chain back to a human or service account.
App (node type)
the third-party application that was granted access.
Audit Entry
an append-only, immutable record of a mutation, its actor, and its reason.
Blast Radius
the set of edges/identities/resources affected by a proposed or executed bulk action.
Bot (identity kind)
a SaaS-issued automation principal scoped to one application.
Canonical Capability
the normalized, provider-agnostic name for a permission (§8.2).
Cassette
a recorded provider API interaction sequence used for deterministic replay testing.
Confused Deputy
the hazard of a system with legitimate authority being tricked into misusing it on an attacker's behalf (Hardy 1988).
Connector
a module implementing the Mesh connector contract for one provider.
Connector SDK
the shared library providing rate limiting, OAuth, pagination, and audit-emission helpers to connector authors.
Credential Handle
an opaque, encrypted reference to a third-party credential; never the credential itself.
Delegation Graph
the network of DELEGATES_TO edges tracing an agent's authority back to its human or service-account root.
Drift
divergence between granted access and actually-needed/actually-used access.
Drift Event
an attributed, read-only-emitted record of a detected drift condition.
Envelope Encryption
encrypting data with a data-encryption key that is itself encrypted by a key-management-service key.
Grant
a lifecycle-tracked authorization from a principal to a resource via a set of scopes.
Grant Provenance
the immutable record of which provider response produced a given grant, and when.
Identity Resolution
merging per-connector shadow identities into one canonical identity.
Idempotency
the property that repeating an operation has the same effect as performing it once.
Incremental Cursor
an opaque pointer marking where a connector's last delta sync stopped.
Introspection (RFC 7662)
a provider endpoint reporting a token's current validity and metadata.
Materialized View
a stored, queryable snapshot derived from an external system of record, not itself the source of truth.
OAuth Scope
a provider-defined string denoting a bounded permission requested/granted during an OAuth flow.
PKCE (RFC 7636)
Proof Key for Code Exchange, an OAuth extension preventing authorization-code interception.
Permission Graph Schema (PGS)
the canonical, provider-agnostic representation of identities, resources, scopes, and grants.
Principal
the connector-local acting subject, prior to identity resolution.
Protocol Server
the component publishing canonicalized permission-state events to subscribers.
Provenance
the traceable origin of a piece of data back to its source observation.
ReBAC
Relationship-Based Access Control, the Zanzibar-style model of expressing permissions as relations in a graph.
Resolution Graph
the network of RESOLVES_TO edges merging per-connector shadow identities into canonical ones.
Resource (node type)
anything access can be granted to.
Revocation Executor
the component turning a RevocationOrder into confirmed provider-side removal.
Revocation Order
a request to revoke one or more grants, idempotent by its own ID.
Revocation Receipt
the confirmed, audited record that a revocation was verified via a subsequent read.
Rich Authorization Requests (RAR, RFC 9396)
an OAuth extension allowing structured, fine-grained authorization detail objects instead of flat scope strings.
Risk Class
a coarse severity tier (low/medium/high/unknown) attached to a capability or grant.
RLS (Row-Level Security)
a database feature restricting row visibility by a policy predicate, used here for tenant isolation.
SCIM (RFC 7643/7644)
System for Cross-domain Identity Management, a standard protocol for provisioning/deprovisioning identities.
Scope Normalizer
the component mapping raw provider scope strings to canonical capabilities and risk classes.
Sensitivity (resource attribute)
a classification of how confidential a resource is.
Service Account (identity kind)
an identity with customer-managed credentials, often used by automation or backend systems.
Shadow Identity
a per-connector identity record prior to resolution into a canonical identity.
SPKI/SDSI
Simple Public Key Infrastructure / Simple Distributed Security Infrastructure, a decentralized delegation-certificate model.
Sync Cursor
see Incremental Cursor.
Tenant Isolation
the guarantee that one tenant's data is never visible to another.
Token Revocation (RFC 7009)
the OAuth standard for invalidating a previously issued token.
Trust Boundary
a point in the architecture where data crosses between differently trusted components.
Tuple Store
a Zanzibar-style storage model representing relations as tuples, optimized for consistent, low-latency authorization checks.
UCAN
User-Controlled Authorization Networks, a capability-based, decentralized authorization token format (referenced for delegation-model contrast, not adopted).
Zookie / Zedtoken
Zanzibar's consistency token mechanism for bounding staleness in authorization checks.
