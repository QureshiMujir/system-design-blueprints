Decisions (§9) · 28 ADRs

ADR-01

Primary language

Chosen

TypeScript (Node.js LTS)

Rejected

Go, Rust, Python

When the rejected choice is right

Rust wins for a memory-constrained on-prem appliance with hard sub-ms latency SLOs; Go wins for a single-binary ops CLI with no shared-schema requirement

Why: Shared PGS types across core + community connectors without codegen; strong OAuth client ecosystem

ADR-02

Monorepo build tool

Chosen

pnpm workspaces + Turborepo

Rejected

Bazel, Nx, Lerna

When the rejected choice is right

Bazel wins once the connector count exceeds ~80 and hermetic, remote-cached builds dominate CI cost

Why: Lower operational overhead at Phase-0 team size; incremental adoption path

ADR-03

Dependency policy

Chosen

Locked lockfile + automated npm audit/Snyk gate on every PR

Rejected

Unpinned ranges, manual review only

When the rejected choice is right

Manual-only review wins in a single-maintainer prototype with < 10 dependencies total

Why: Reproducibility (§29) requires exact resolution; automation scales past one reviewer

ADR-04

Graph storage model

Chosen

Postgres relational adjacency tables + recursive CTEs

Rejected

Neo4j/graph-native DB, Zanzibar-style tuple store (SpiceDB/OpenFGA)

When the rejected choice is right

A Zanzibar-style tuple store wins once a tenant exceeds the 10M-edge ceiling and 2-hop traversal latency (§4 p99) cannot be met by index-assisted CTEs

Why: Operational maturity, SQL tooling, and RLS tenant isolation outweigh graph-native traversal ergonomics below the 10M-edge ceiling (§4)

ADR-05

Scope canonicalization strategy

Chosen

Versioned lookup-table normalizer (per-connector, per-pgsVersion) with explicit unmapped fallback (P7)

Rejected

ML-based scope-string classifier, ABAC-only attribute model (NIST 800-162)

When the rejected choice is right

An ML classifier wins once the provider catalogue exceeds hundreds of long-tail scope strings and manual table maintenance cannot keep pace

Why: Determinism and auditability of a table beat a classifier's opacity for a security-relevant mapping

ADR-06

Connector sandboxing

Chosen

Per-tenant-connector isolated process, capped egress allowlist

Rejected

Shared in-process plugin execution, full VM per connector

When the rejected choice is right

Full VM isolation wins once a connector runs untrusted, community-submitted native code rather than sandboxed TypeScript

Why: Process isolation is cheap enough at Phase-0 connector counts and stops cross-connector namespace writes (I11) without VM cost

ADR-07

Token/credential storage

Chosen

Envelope encryption, per-tenant DEK wrapped by KMS

Rejected

Plaintext at rest, HSM-backed hardware key per tenant

When the rejected choice is right

Per-tenant HSM wins once a regulated-enterprise customer contractually requires hardware-backed key custody

Why: Matches P5 without HSM cost at Phase-0/1 scale

ADR-08

Discovery mechanism

Chosen

Poll (cursor-based) primary, webhook opportunistic accelerant

Rejected

Webhook-only, SCIM-push-only

When the rejected choice is right

Webhook-only wins for a provider with a contractually guaranteed at-least-once delivery SLA that Mesh can rely on without any poll floor

Why: P10 — webhooks alone leave undetectable gaps; poll is the reconciliation floor

ADR-09

Revocation strategy

Chosen

Async order + read-after-write confirmation receipt

Rejected

Synchronous revoke-and-trust-response

When the rejected choice is right

Synchronous trust-response wins only for a provider with a documented, verifiable strongly-consistent write-then-read guarantee

Why: I2/P3 — a 200 response is not proof of provider-side propagation

ADR-10

Protocol design

Chosen

Event-stream publish/subscribe (append-only log semantics)

Rejected

REST polling API only, gRPC bidirectional streaming

When the rejected choice is right

gRPC bidirectional streaming wins when subscribers require sub-100ms push latency and can maintain a persistent connection pool

Why: Matches the additive, replayable delivery model (P9) subscribers need without a persistent bidirectional connection

ADR-11

Consistency model

Chosen

Tenant-scoped read-your-writes (P13)

Rejected

Zanzibar zookie-style global consistency tokens

When the rejected choice is right

Zookie-style tokens win once cross-region tenant replicas are required (multi-region GA beyond Phase 11 scope)

Why: Global linearizability is unneeded overhead below the 10M-edge/single-region ceiling (§4)

ADR-12

Queue/job system

Chosen

BullMQ on Redis

Rejected

Kafka, SQS, Postgres-native job table

When the rejected choice is right

Kafka wins once the protocol server (Phase 8) must fan out to thousands of subscribing consumers with replay-from-offset semantics

Why: Lowest operational cost matching Phase-0/1 team size while meeting the sync-fanout concurrency budget (§4)

ADR-13

Secrets management

Chosen

Cloud KMS + per-tenant DEK, no application-level secret store

Rejected

HashiCorp Vault, customer-managed HSM only

When the rejected choice is right

Vault wins once dynamic, short-lived secret leasing for Mesh's own internal service credentials is required at Phase-4+ scale

Why: KMS envelope encryption meets P5 without operating a separate secrets-manager service (non-goal, §1)

ADR-14

Logging

Chosen

Structured JSON logs, PII-scrubbed at ingestion

Rejected

Free-text logs, no scrubbing

When the rejected choice is right

Free-text wins only in a throwaway local-dev harness, never in any deployed environment

Why: Auditability (P8) and privacy defaults require structured, greppable, safe-to-retain logs

ADR-15

Tracing

Chosen

OpenTelemetry, vendor-neutral exporter

Rejected

Vendor-locked proprietary tracing SDK

When the rejected choice is right

A vendor-locked SDK wins only when that vendor's tracing feature set is otherwise unreachable and no migration is ever planned

Why: Avoids re-instrumentation cost if the backend changes (Operational Readiness)

ADR-16

Metrics

Chosen

Prometheus-compatible metrics, pull-based scrape

Rejected

StatsD push-based

When the rejected choice is right

Push-based StatsD wins in a short-lived serverless execution model where scrape targets churn faster than the scrape interval

Why: Pull-based scrape simplifies cardinality control for the per-connector-per-tenant metric space

ADR-17

Testing framework

Chosen

Vitest (unit), Playwright (E2E)

Rejected

Jest, Cypress

When the rejected choice is right

Jest wins when inheriting a large pre-existing Jest suite from an acquired connector codebase

Why: Faster cold start and native ESM support matching the TypeScript-first stack (ADR-01)

ADR-18

Fuzzing

Chosen

Structured fuzzing of scope strings and provider payload shapes (Phase 11)

Rejected

No fuzzing, property-based testing only

When the rejected choice is right

Property-based testing alone wins for pure functions with no external-input attack surface (e.g., the MeshQL-successor grammar's parser core)

Why: Malformed provider input (§8.5) is a real, recurring failure class worth adversarial coverage

ADR-19

CI/CD

Chosen

GitHub Actions, conformance suite gate on every PR

Rejected

Jenkins, CircleCI, GitLab CI

When the rejected choice is right

Jenkins wins for an air-gapped on-prem build pipeline (PhaseDeferred("Phase 11")) with no external network access

Why: Matches the OSS connector-contribution model (public repo, no self-hosted runner burden)

ADR-20

Packaging (SDK distribution)

Chosen

npm-published @mesh/connector-sdk package, semver

Rejected

Git-submodule vendoring, private registry only

When the rejected choice is right

A private registry wins once proprietary, closed-source connectors must never be resolvable by a public npm install

Why: Standard npm semver resolution is the lowest-friction path for community connector authors

ADR-21

Containers

Chosen

OCI-compliant Docker images per service

Rejected

Bare-metal process deployment, Nix-only builds

When the rejected choice is right

Bare-metal wins for a single-tenant, single-machine constrained appliance where container overhead is unacceptable

Why: Portability across the hosted and future on-prem deployment models (§1)

ADR-22

Release process/versioning

Chosen

Changesets-driven semver, weekly minor cadence

Rejected

Continuous rolling release with no version tags

When the rejected choice is right

Continuous rolling release wins for an internal-only tool with zero external consumers

Why: Downstream connector authors and protocol subscribers need a stable version to pin against (P9)

ADR-23

Build reproducibility

Chosen

Deterministic, pinned-lockfile builds with provenance attestation

Rejected

Non-reproducible builds ("works on my machine")

When the rejected choice is right

Non-reproducible builds are acceptable only in a disposable local prototyping branch never shipped

Why: Supply-chain integrity (P6) requires verifiable build provenance, echoing the Codecov 2021 lesson

ADR-24

Time source

Chosen

NTP-synced monotonic clock for cursor/timestamp comparisons

Rejected

Wall-clock-only comparisons, vector clocks

When the rejected choice is right

Vector clocks win once true multi-region, multi-writer graph replicas are required (beyond Phase 11 scope)

Why: NTP-synced monotonic timestamps are sufficient given tenant-scoped consistency (ADR-11) and avoid vector-clock operational complexity

ADR-25

Backpressure/rate-limiting

Chosen

Per-connector token-bucket RateLimiter capped at I4's budget

Rejected

Global tenant-wide single rate limiter, no rate limiting

When the rejected choice is right

A single global limiter wins for a tenant with exactly one connector installed, where per-connector granularity adds no value

Why: Per-connector budgets isolate one slow/limited provider from starving others (P12)

ADR-26

Licensing

Chosen

Apache 2.0 for connector contract, PGS, conformance suite, reference connectors; proprietary hosted control plane

Rejected

Fully proprietary, fully copyleft (AGPL)

When the rejected choice is right

AGPL wins if the strategic goal shifts to forcing all derivative hosted competitors to open their modifications

Why: Apache 2.0 lowers the bar for community connector contribution (§2) without copyleft obligations on consumers

ADR-27

Identity-resolution merge strategy

Chosen

Conservative two-signal auto-merge (email + SSO subject), soft-merge review otherwise (I7)

Rejected

Single-signal (email-only) auto-merge, ML-based fuzzy matching

When the rejected choice is right

Single-signal auto-merge wins only in a small, single-domain tenant where email uniqueness is contractually guaranteed

Why: Mis-merge is catastrophic (wrong-human revocation); conservative-by-default is the only safe default

ADR-28

Query surface design

Chosen

Purpose-built graph query language over the PGS, plus a REST read API

Rejected

GraphQL-only public surface, SQL-direct access

When the rejected choice is right

GraphQL-only wins when the primary consumers are web frontends with existing GraphQL tooling and no need for graph-pattern queries

Why: A purpose-built language expresses the resolution-graph traversal (identity → resolvedTo → grants) more naturally than generic GraphQL resolvers

36. Alternative Architectures (Roads Not Taken)

A1 — Authoritative Zanzibar-style Policy Decision Point, apps call Mesh synchronously at request time to authorize each action.

App Request ──▶ Mesh PDP (tuple store, zookie-consistent) ──▶ Allow/Deny ──▶ App
                        ▲
                Sync from providers (background, same as today)

Winning regime: a single organization willing to route all authorization decisions through one PDP, accepting the availability coupling that implies. Real embodying system: Google's internal Zanzibar deployment, and SpiceDB/OpenFGA for external adopters. Rejected here because it collapses P1 — Mesh would become the confused deputy the whole design exists to avoid, and it requires every downstream app to accept Mesh as a hard runtime dependency rather than an observational side-channel.

A2 — Browser-extension client-side-only discovery, no backend, purely local enumeration of a single user's own grants via the browser's authenticated sessions.

Browser Extension ──▶ reads provider consent-management pages (DOM) ──▶ local-only report
        (no server, no cross-user graph, no revoke automation)

Winning regime: an individual-consumer, zero-trust-of-any-vendor use case where even Mesh itself must not see the data. Real embodying system: browser-based personal-privacy extensions (ad-blocker-adjacent privacy tools). Rejected here because it cannot support tenant-wide graph queries, drift detection across an organization, or receipted bulk revocation — the core enterprise value Mesh exists to provide.

A3 — IdP-native model, the customer's identity provider (Okta/Entra) owns the permission graph natively, and Mesh is a thin plugin surfacing IdP-native data.

Okta/Entra (owns graph natively) ──▶ Mesh Plugin (read-only view + drift/revoke UI layer)

Winning regime: an organization fully consolidated on one IdP with no significant non-IdP-federated SaaS sprawl. Real embodying system: Okta's and Entra ID's own native governance modules (Okta Identity Governance, Entra ID Governance). Rejected here because Mesh's entire value proposition is cross-provider normalization across IdPs and non-IdP SaaS apps alike (§1); an IdP-native model cannot observe grants the IdP itself never brokered (e.g., a Notion integration authorized directly by a user, bypassing SSO-mediated OAuth).

A4 — Event-sourced pure-webhook design, no polling at all; the graph is purely a projection of an append-only webhook event log.

Provider Webhooks ──▶ Event Log (append-only) ──▶ Graph Projection (rebuilt from log)
                (no enumerate(), no incrementalCursor(), no poll floor)

Winning regime: a closed ecosystem where every provider guarantees at-least-once, ordered webhook delivery with no gap possibility — an assumption no real multi-provider SaaS estate satisfies today. Real embodying system: internal event-sourced microservice architectures within a single company's own infrastructure, where delivery guarantees are engineered end-to-end. Rejected here because P10 exists precisely because real third-party webhook delivery is not reliably gap-free (§16.6, §21.6) — a pure-webhook Mesh would silently drift from ground truth with no reconciliation mechanism to catch it.
