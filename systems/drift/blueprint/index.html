3 — Drift

Project Number: 3

Project Name: Drift

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Drift is an autonomous dependency and CVE remediation bot: it ingests vulnerability disclosures (OSV-shaped) and dependency-drift signals for a tracked repository, builds a dependency graph, prioritizes risk, plans a fix (initially a semver-constrained version bump, later a source-level patch or backport), applies the fix as a diff, validates it by running the repository's own build and test suite inside a hardened sandbox (namespace isolation, seccomp filtering, no network egress), generates a machine-checkable justification artifact (signed, referencing the advisory ID, the patch diff hash, and the validation run ID), and opens a pull request through a forge adapter (initially GitHub). Drift never merges: every fix is proposed, never applied outside the sandbox, and a human approves the merge.

Phase-0 deliverable — five services:

  1. ingester — polls osv.dev and GitHub Security Advisories, normalizes into internal Advisory records, deduplicates by (advisory ID, ecosystem, repo SHA).
  2. planner — given an Advisory and the repo's lockfile, computes the minimal semver-compatible bump satisfying the fixed-in range; emits a FixPlan.
  3. sandbox-runner — spawns an OCI-runtime container (gVisor runtime) per validation, applies the patch, runs the existing test command, captures exit code and logs, enforces CPU/memory/wall-clock ceilings.
  4. justifier — serializes advisory ID, patch diff hash, validation run ID, and planner version into a canonical justification document, signs it with an in-toto/Sigstore-compatible attestation.
  5. pr-emitter — opens a pull request via the forge adapter, attaches the justification as a PR artifact, labels it.

Boundaries: Drift acts on exactly one forge (GitHub) and one ecosystem manifest format in Phase 0 (npm package-lock.json); it never executes repository code outside sandbox-runner; it never auto-merges. Non-goals for Phase 0: multi-language support (PhaseDeferred("Phase 8 — Multi-Language Support")), source-level patching beyond version bump (PhaseDeferred("Phase 7 — Source-Level Patching & Backports")), fleet scale-out across many repos concurrently (PhaseDeferred("Phase 10 — Fleet Scale-Out & Rate-Limit Governor")), and reachability-aware prioritization (PhaseDeferred("Phase 9 — Call-Graph Reachability Context")).

Deployment model: a single-tenant, single-repo daemon set (ingester, planner, sandbox-runner, justifier, pr-emitter, event store) deployable as a docker-compose stack for Phase 0, later a Kubernetes-scheduled fleet (Phase 10). Users/operators: the security or platform engineer who installs Drift against a repo and reviews its PRs; later, a fleet operator managing hundreds of repos.

Language: Go for all long-running services (ingester, planner, sandbox-runner control plane, pr-emitter) — rationale: strong concurrency primitives fit the queue/worker topology, a single static binary simplifies the sandbox-runner's own supply chain, mature OCI/runc/gVisor client libraries exist, and there is no GC-pause profile concern at this scale. Rejected: Python (the interpreter's own dependency footprint becomes attack surface for a security tool; a static-binary sandbox controller is easier to reason about without a runtime); Rust (the memory-safety benefit is real but the team-velocity cost of a 12-phase spec-first build is too high, and the OCI/runc ecosystem tooling is more mature in Go). The justification signing and verification CLI is also Go, sharing the in-toto/Sigstore Go libraries.

Prerequisites: network egress to osv.dev reachable from the ingester only (never from the sandbox); a GitHub App installation with contents:write and pull-requests:write scope; an OCI-compatible container runtime with gVisor (runsc) installed on the sandbox host.

Timeline: Phase 0 targets a 3-week build (skeleton, advisory ingest, CI). The full 12-phase arc (Phase 0 through Phase 11) targets approximately 30 weeks at roughly 2–3 weeks per phase.

Deferrals: multi-ecosystem manifest parsing is PhaseDeferred("Phase 8 — Multi-Language Support"); source-level patch generation beyond version bump is PhaseDeferred("Phase 7 — Source-Level Patching & Backports"); call-graph reachability filtering is PhaseDeferred("Phase 9 — Call-Graph Reachability Context"); multi-repo fleet scheduling and rate-limit governance is PhaseDeferred("Phase 10 — Fleet Scale-Out & Rate-Limit Governor").

2. Why Build This

  • Supply-chain compromise is now a systemic risk surface: SolarWinds (2020 build compromise), the event-stream npm compromise (2018), and the 2021 Codecov bash-uploader compromise all originated in dependency trust boundaries, not application logic.
  • CVE and advisory volume outpaces human triage capacity; OSV's machine-readable schema exists specifically to make automated remediation tractable.
  • Version-bump remediation is a narrow, well-specified form of automated program repair — a tractable entry point into the automatic-software-repair literature (GenProg, SapFix, Getafix) without the open-ended search-space problem of general repair.
  • A validated fix is only as trustworthy as its proof: building the justification and attestation pipeline forces direct engagement with in-toto, TUF, and Sigstore — the same primitives underlying SLSA provenance.
  • Sandboxed execution of untrusted repository code is a first-class kernel/systems problem (the seccomp/systrace lineage from Provos 2003, gVisor's user-space kernel, the OCI runtime spec) — this project is a forcing function to build one, not merely read about one.
  • Building a real fix-planning pipeline surfaces the gap between "compiles" and "is correct" — the test-suite-as-oracle design is a direct encounter with the flaky-test/false-positive problem that dominates real CI systems.
  • Direct architectural comparison against production systems (Dependabot, Renovate, Snyk Fix PRs) is possible because their design choices are publicly documented, enabling an honest benchmark against real prior art rather than an imagined one.

What Mastery Looks Like

  • Can explain, from Phase 3, why sandbox escape is prevented by user-space kernel interception rather than reliance on the host kernel's syscall table alone.
  • Can justify, from Phase 5, why the justification format is a machine-checkable artifact and not a prose PR description, and name the verification step that consumes it.
  • Can defend, from Phase 4, the choice of minimal semver-compatible bump as the initial fix strategy over synthesizing a source patch, including the operational failure modes both share.
  • Can walk through, from Phase 9, how reachability analysis changes risk prioritization without changing the fix strategy itself.
  • Can explain, from Phase 10, why a fleet-wide rate-limit governor is a distinct component from the per-repo planner, and what invariant it protects.
  • Can reproduce, from Phase 11, the exact conformance fixture set that gates a release, and why each fixture exists.

Advisory ingester — polls osv.dev and GitHub Security Advisories on a bounded schedule, normalizes payloads into the internal Advisory schema, deduplicates by (advisory ID, ecosystem, repo SHA), and appends a Detected event to the event store. It is the only component with outbound network access to public advisory feeds.

Dependency-graph builder — parses the repo's lockfile at the SHA under evaluation into a DependencyNode graph (direct and transitive edges), joins it against incoming advisories to find affected nodes, and emits a DependencyGraph keyed to (repo, SHA).

Risk prioritizer — scores each (advisory, affected node) pair using CVSS v3.1 base metrics plus graph position (direct vs transitive), producing a RiskScore that orders the fix queue.

Fix planner — given a prioritized advisory and the dependency graph, computes a FixPlan: the minimal semver-compatible version bump satisfying the advisory's fixed-in range, or a PhaseDeferred marker if no such bump exists.

Patch applier — materializes the FixPlan into a concrete PatchSet (lockfile and manifest diff), never touching working-tree state outside a scratch checkout.

Sandboxed validator (build + test runner) — spawns a gVisor-backed OCI container per validation, applies the PatchSet to a disposable checkout, runs the repo's declared build and test command, and enforces CPU, memory, and wall-clock ceilings; it has no network egress and no access to forge credentials.

Justification generator — assembles a Justification document binding advisory ID, repo SHA, patch diff hash, and ValidationRun ID, signs it via Sigstore keyless signing, and stores the attestation alongside the event.

PR emitter — turns an accepted FixPlan plus its Justification into a PullRequestDraft and hands it to the forge adapter.

Forge adapter — the only component holding forge credentials; translates a PullRequestDraft into forge-specific API calls (GitHub REST/GraphQL in Phase 0), isolating the rest of the system from forge-specific detail.

Event store — an append-only log of every EventRecord (Detected, Planned, Patched, Validating, Justified, Proposed, Merged, Abandoned) keyed by (repo, SHA, advisory ID); the single source of truth for idempotency and audit.

Telemetry — collects metrics, traces, and structured logs from every component via OpenTelemetry, feeding the dashboards and alerts described in Performance Engineering.

6. Design Principles

P1 — Propose, never merge. Rule: every fix Drift produces terminates in an open pull request awaiting human review; no code path merges automatically. Tradeoff: slower time-to-remediation vs eliminated blast radius from a bad automated fix. Operational implication: PR review SLAs become part of the security posture, not Drift's own SLOs. Violating this collapses Drift into an unreviewed code-injection vector — precisely the SapFix lesson (Marginean et al. 2019).

P2 — No fix ships without a green sandboxed validation. Rule: a FixPlan transitions to Proposed only after a ValidationRun records a pass. Tradeoff: flaky repo tests cause false negatives that block correct fixes. Operational implication: flaky-test detection (§15, Phase 3) is load-bearing, not optional. Violating this turns Drift into a diff generator with no correctness signal at all.

P3 — The justification is a machine-checkable artifact, not prose. Rule: every Justification is a signed, schema-validated document a verifier can check without reading English text. Tradeoff: authoring cost for the schema and signer up front. Operational implication: PR descriptions become human summaries generated from the artifact, never the other way around. Violating this makes "why was this merged" unanswerable after key personnel turnover.

P4 — No untrusted repo code executes outside the sandbox. Rule: lockfile parsing, patch application, and test execution touching repo content run only inside the gVisor-isolated sandbox-runner. Tradeoff: every operation on repo bytes pays sandbox-spawn latency. Operational implication: sandbox spawn latency (§4) is a first-class SLI. Violating this reopens the exact class of compromise SolarWinds and Codecov exploited — arbitrary code execution in the build pipeline.

P5 — Every emitted PR is reproducible from (repo SHA, advisory ID, planner version). Rule: given those three values, the exact FixPlan and PatchSet can be regenerated byte-for-byte. Tradeoff: the planner must be pure and versioned, forbidding hidden mutable state (e.g. "latest available version" without a pinned resolution timestamp). Operational implication: planner releases are tagged and referenced by ID in every Justification. Violating this makes forensic replay of a disputed fix impossible.

P6 — No advisory is processed twice for the same SHA. Rule: the event store's (advisory ID, ecosystem, repo SHA) key is the sole deduplication authority. Tradeoff: correcting a wrongly-processed advisory requires an explicit reprocessing event, not a silent retry. Operational implication: reprocessing is an audited operation with its own event type. Violating this produces duplicate PRs and forge-quota waste.

P7 — Secrets never enter the sandbox. Rule: forge tokens, registry credentials, and signing keys are held only by the pr-emitter, forge adapter, and justifier; sandbox-runner starts with an empty credential environment. Tradeoff: any fix requiring authenticated registry access to resolve (private packages) needs a pre-resolution step outside the sandbox. Operational implication: private-registry support is explicitly scoped and reviewed per ADR-19. Violating this converts a sandbox escape into a credential-theft event.

P8 — Risk prioritization is a pure function of (advisory, dependency graph, telemetry signal), never of forge state. Rule: the risk prioritizer never queries PR status or merge history to decide what to fix next. Tradeoff: cannot deprioritize based on "we already tried this and it failed" without an explicit outcome signal fed back as telemetry. Operational implication: failed-attempt feedback is modeled explicitly (§8 state machine), not inferred from forge side effects. Violating this creates non-deterministic prioritization that cannot be replayed for audit.

P9 — The fix planner never widens a constraint beyond the advisory's fixed-in range without an explicit policy override. Rule: default behavior is the minimal satisfying bump. Tradeoff: does not opportunistically pick up unrelated newer features. Operational implication: "upgrade to latest" is a named policy, not the default. Violating this causes unreviewed scope creep in every generated PR, eroding reviewer trust.

P10 — Every failure path emits a distinguishable event, never a silent drop. Rule: each state-machine failure edge (§8) has a named terminal or retry state. Tradeoff: more event types to define and document up front. Operational implication: on-call dashboards can distinguish "advisory malformed" from "sandbox timed out" from "no fix exists" at a glance. Violating this makes root-causing a stalled remediation queue a manual log-archaeology exercise.

P11 — The dependency graph is rebuilt per SHA, never incrementally mutated in place. Rule: a new commit triggers a fresh DependencyGraph build keyed to the new SHA; old graphs are retained, not patched. Tradeoff: higher storage cost for graph history. Operational implication: graph diffing across SHAs becomes possible for drift analysis. Violating this risks stale-graph false negatives after a manifest change.

P12 — Telemetry is structured and named consistently with the domain model. Rule: metric and span names reuse the exact type and state names from §8/§11 (e.g. a span named Validating, not run_tests). Tradeoff: renaming a domain concept requires a coordinated telemetry migration. Operational implication: dashboards can be generated mechanically from the state machine. Violating this causes telemetry drift where dashboards silently stop reflecting the real state machine.

8. Domain Model

Advisory (OSV-shaped). Fields: id (string, e.g. GHSA-xxxx or OSV-2024-xxxx), ecosystem (enum: npm, PyPI, ...), package (string), affected (list of AffectedRange), severity (CVSS v3.1 vector string), summary, references (list of URL), withdrawn (nullable timestamp), modified (timestamp). AffectedRange: introduced (version), fixed (nullable version), last_affected (nullable version), events (ordered list mirroring the OSV ranges[].events structure).

Dependency-graph model. DependencyNode: name, ecosystem, resolved_version, requested_range, depth (0 = direct), parents (list of node IDs), children (list of node IDs). The graph is a DAG keyed by (repo, SHA); cycles are rejected at build time as a malformed-manifest condition.

Fix-plan IR. FixPlan: advisory_id, target_node, from_version, to_version, strategy (enum: SemverBump, SourcePatch [Phase 7], Backport [Phase 7]), planner_version, constraint_check (proof that to_version satisfies both the advisory's fixed-in range and the repo's declared semver range).

Patch/diff representation. PatchSet: files (list of unified-diff hunks), base_sha, diff_hash (content hash of the concatenated unified diff), manifest_ deltas (structured before/after version pairs, redundant with the diff for fast-path verification).

Justification format. Fields: advisory_id, repo_sha, patch_diff_hash, validation_run_id, planner_version, risk_score, issued_at, signature (Sigstore bundle), verification_steps (ordered list: recompute diff hash, recheck CVSS vector against advisory, re-verify signature against Rekor transparency log). A verifier consumes only these fields — no prose is authoritative.

Forge/PR contract. PullRequestDraft: repo, base_branch, head_branch (named deterministically from advisory ID + repo SHA), title, body_summary (human-readable, generated from Justification, never authoritative), justification_ ref (attached artifact), labels. The forge adapter guarantees idempotent PR creation: re-submitting an identical draft for the same (repo, SHA, advisory ID) is a no-op if an open PR already exists.

Worked end-to-end example. Advisory GHSA-example-1234 (npm, package left-pad, affected <1.3.0, fixed 1.3.0) is detected for repo acme/web at SHA abc123. Graph join finds left-pad@1.2.0 at depth 2 (transitive). Planner computes FixPlan{from: 1.2.0, to: 1.3.0, strategy: SemverBump}. Patch applier produces a PatchSet touching package-lock.json. Sandbox validator applies the patch, runs npm test, exits 0 in 4m12s. Justifier signs a Justification binding all four IDs. PR emitter opens acme/web#4821 titled "Bump left-pad to 1.3.0 (fixes GHSA-example-1234)".

Malformed-advisory example. An OSV record missing affected[].events entirely (no introduced and no fixed) fails schema validation at ingest; the ingester emits Detected with a malformed: true flag and routes to Abandoned (MalformedAdvisory) without ever reaching graph join — see fixture fixtures/advisories/malformed_missing_events.json (§12, Phase 0).

Malformed-manifest example. A package-lock.json with a dependency cycle (package A requires B requires A at identical resolved versions with no version-based tie-break) fails graph construction; the builder emits GraphBuildFailed and the advisory is routed to Abandoned (MalformedManifest) — see fixture fixtures/manifests/cyclic_lockfile.json (§13, Phase 1).

Failure-path example. A validation run exceeds the 15-minute test-suite budget (§4) due to a genuinely slow but passing test suite (not a hang); Timeout fires at 20 minutes wall-clock, the run is marked Abandoned (ValidationTimeout), and a distinct telemetry counter (sandbox.timeout.slow_suite_suspect) is incremented separately from a hang-suspect counter, disambiguated by CPU-utilization trace during the run (§15, Phase 3, Pitfalls).

11. Core Schema & Types

// Advisory: owned by internal/advisory; immutable after ingest; persisted in
// event store as part of Detected event; serialized as OSV-compatible JSON;
// forward-compatible via unknown-field passthrough.
type Advisory struct {
    ID         string
    Ecosystem  string
    Package    string
    Affected   []AffectedRange
    Severity   string // CVSS v3.1 vector
    Summary    string
    References []string
    Withdrawn  *time.Time
    Modified   time.Time
}

// AffectedRange: owned by internal/advisory; immutable; embedded in Advisory;
// no independent persistence; serialization mirrors OSV ranges[].events.
type AffectedRange struct {
    Introduced   string
    Fixed        *string
    LastAffected *string
    Events       []RangeEvent
}
// DependencyNode: owned by internal/graph; mutated only during graph build,
// immutable once a DependencyGraph is sealed for a (repo, SHA); persisted as
// Postgres jsonb; concurrency: single-writer per (repo, SHA) build.
type DependencyNode struct {
    Name            string
    Ecosystem       string
    ResolvedVersion string
    RequestedRange  string
    Depth           int
    Parents         []NodeID
    Children        []NodeID
}

// RiskScore: owned by internal/risk; recomputed per (advisory, node) pair on
// each graph rebuild; not independently persisted, embedded in FixPlan input;
// serialization: flat struct, no versioning needed (recomputed, not replayed).
type RiskScore struct {
    CVSSVector    string
    BaseScore     float64
    Reachable     *bool // nil until Phase 9
    GraphDepth    int
    ComputedAt    time.Time
}
// FixPlan: owned by internal/planner; immutable once emitted (P5); persisted
// keyed by (advisory ID, repo SHA, planner version); serialization must be
// byte-stable for replay (I2); compatibility: additive fields only.
type FixPlan struct {
    AdvisoryID      string
    TargetNode      NodeID
    FromVersion     string
    ToVersion       string
    Strategy        FixStrategy // SemverBump | SourcePatch | Backport
    PlannerVersion  string
    ConstraintCheck ConstraintProof
}

// PatchSet: owned by internal/patch; immutable once generated; persisted keyed
// by DiffHash; serialization: unified diff text plus structured deltas;
// concurrency: generated single-threaded per FixPlan.
type PatchSet struct {
    Files          []DiffHunk
    BaseSHA        string
    DiffHash       string
    ManifestDeltas []VersionDelta
}
// ValidationRun: owned by internal/sandbox; append-only once started, sealed
// on completion; persisted as an EventRecord payload; concurrency: one run
// per sandbox container instance, no shared mutable state across runs.
type ValidationRun struct {
    ID          string
    PatchSetRef string
    StartedAt   time.Time
    EndedAt     *time.Time
    Result      ValidationResult // Passed | Failed | Timeout | SandboxError
    Logs        LogRef
    CPUUsed     time.Duration
    MemPeakMiB  int
}

// Justification: owned by internal/justify; immutable once signed (P3);
// persisted alongside PullRequestDraft; serialization: canonical JSON, signed
// via Sigstore bundle; compatibility: schema version field, additive only.
type Justification struct {
    AdvisoryID       string
    RepoSHA          string
    PatchDiffHash    string
    ValidationRunID  string
    PlannerVersion   string
    RiskScore        RiskScore
    IssuedAt         time.Time
    Signature        SigstoreBundle
    VerificationSteps []string
}
// PullRequestDraft: owned by internal/forge; immutable once handed to
// ForgeAdapter; not persisted beyond the event store's Proposed event;
// serialization: forge-agnostic struct translated per adapter.
type PullRequestDraft struct {
    Repo            string
    BaseBranch      string
    HeadBranch      string
    Title           string
    BodySummary     string
    JustificationRef string
    Labels          []string
}

// SandboxHandle: owned by internal/sandbox; mutable only by the owning
// sandbox-runner process; never persisted (ephemeral, process-local);
// concurrency: exactly one goroutine controls a handle's lifecycle.
type SandboxHandle struct {
    ContainerID string
    CgroupPath  string
    NetNS       string // always isolated, no egress
    ExpiresAt   time.Time
}
// ForgeAdapter: owned by internal/forge; interface, stateless per call;
// implementations hold credentials, never exposed to callers; concurrency:
// implementations must be safe for concurrent use.
type ForgeAdapter interface {
    OpenPullRequest(ctx context.Context, draft PullRequestDraft) (PRRef, error)
    FindExistingPR(ctx context.Context, repo, headBranch string) (*PRRef, error)
}

// EventRecord: owned by internal/eventstore; append-only, never mutated (I8);
// persisted as the canonical Postgres table; serialization: versioned
// envelope wrapping a typed payload; compatibility: payload schema versioned
// independently per event type.
type EventRecord struct {
    Repo        string
    SHA         string
    AdvisoryID  string
    EventType   string // Detected | Planned | Patched | ... | Abandoned
    Payload     json.RawMessage
    RecordedAt  time.Time
}

// Error enums (internal/errors), owned centrally, immutable constants.
type FailureReason string

    NoFixAvailable      FailureReason = "NoFixAvailable"

    SandboxUnavailable  FailureReason = "SandboxUnavailable"
    ValidationFailed    FailureReason = "ValidationFailed"
    ValidationTimeout   FailureReason = "ValidationTimeout"
    SigningFailed       FailureReason = "SigningFailed"
    RejectedByReviewer  FailureReason = "RejectedByReviewer"
)

12. Phase 0 — Skeleton, Advisory Ingest & CI

12.1 Objectives

Stand up the five Phase-0 services as separate binaries sharing internal/ libraries; implement the ingester against osv.dev and GitHub Security Advisories; persist Detected events to the event store; establish CI (lint, unit test, conformance fixtures) as the release gate for every subsequent phase.

12.2 Detailed Implementation Steps

Implement internal/advisory to parse OSV JSON payloads into Advisory/ AffectedRange per the schema in §11, validating against the OSV Schema (section 4 of the OSV schema, defining affected[].ranges[].events). Implement the poller in cmd/ingester with a bounded-rate HTTP client (respecting P4's "only ingester has egress" boundary, I1). Implement internal/eventstore as a Postgres append-only table enforcing the (advisory ID, ecosystem, repo SHA) unique key from I3/ADR-15; reject duplicate inserts at the database constraint level, not in application logic, per I8. Wire OpenTelemetry (ADR-20) into every service per the naming discipline in P12. Stand up .github/workflows/ci.yml running make lint test conformance.

12.3 Deliverable

A running ingester binary that polls osv.dev on a fixed interval, normalizes at least one real advisory end-to-end into a Detected EventRecord, and a CI pipeline that fails the build on any conformance fixture regression.

12.4 Acceptance Criteria

Ingesting the fixture conformance/advisories/ghsa_example_1234.json produces exactly one Detected event within 2s (p95, §4-adjacent local target); re-ingesting the identical advisory a second time produces zero new events (I3); CI blocks merge on any fixture in conformance/advisories/ failing; event-store schema migration runs idempotently via make migrate.

12.5 Conformance Fixtures

conformance/advisories/ghsa_example_1234.json — well-formed OSV advisory, expected: one Detected event. conformance/advisories/malformed_missing_events.json — missing affected[].events, expected: Detected{malformed:true} routed to Abandoned(MalformedAdvisory) per §8. conformance/replay/ingest_replay_001.json — replays an already-ingested advisory, expected: zero new events (I3 regression guard).

12.6 Pitfalls

Treating osv.dev pagination cursors as stable across polls (they are not guaranteed stable under concurrent updates) causes silent advisory loss — manifestation: gaps in Detected events for advisories confirmed present on osv.dev; root cause: cursor invalidated mid-page by an upstream update; debug method: replay the poll window against the OSV export snapshot; signal: ingester.poll.cursor_reset_total; recovery: re-poll the full window on cursor reset rather than resuming from the stale cursor.

Deduplicating only on advisory ID (ignoring ecosystem) causes cross-ecosystem collisions (e.g. an npm and a PyPI advisory sharing an upstream CVE ID) to be merged incorrectly — manifestation: one ecosystem's advisory silently suppresses the other's; root cause: I3's compound key implemented as a partial index; debug: query the unique index definition; signal: ingester.dedup.rejected_total spiking for a benign case; recovery: fix the index to the full compound key, backfill missing events.

12.7 Performance Concerns

Advisory ingest must sustain the 500/hour steady-state and 5,000/hour burst targets from §4 without blocking the event-store writer; batch inserts in groups of ≤100 to bound transaction size; poll interval must not exceed 5 minutes to keep fix-attempt latency p50 (§4) achievable downstream.

12.8 Edge Cases

An advisory withdrawn after being ingested but before being planned; an advisory whose affected[].introduced is "0" (meaning "always affected until fixed"); an advisory referencing an ecosystem Drift does not yet support (must be recorded but not routed to graph join, not silently dropped).

12.9 Failure Analysis

osv.dev unreachable for an extended window: the ingester must not crash-loop; back off exponentially, emit ingester.poll.failure_total, and resume from the last successfully committed poll cursor on recovery — no Detected events are lost or duplicated (I3, I8).

12.10 Operational Notes

Runbook docs/runbooks/ingester-poll-stall.md covers diagnosing a stalled poller via ingester.poll.last_success_timestamp; alert if that gauge is older than 15 minutes (3x the poll interval).

13. Phase 1 — Dependency-Graph Extraction

13.1 Objectives

Build internal/graph to parse an npm package-lock.json at a given repo SHA into a DependencyNode DAG, join it against ingested advisories, and persist a sealed DependencyGraph per (repo, SHA) per P11.

13.2 Detailed Implementation Steps

Implement a deterministic lockfile parser (ADR-16) that never shells out to npm; walk packages entries in package-lock.json v3 format, building DependencyNode records with depth computed via BFS from the manifest's direct dependencies. Detect cycles during BFS (a node reachable from itself via children edges at identical resolved versions) and reject the graph as MalformedManifest per §8. Join the sealed graph against Advisory.package/Advisory.ecosystem to find affected nodes, emitting a GraphJoined event per node match (Le Goues et al.'s patch-space framing does not apply here — this is exact matching, not search).

13.3 Deliverable

A graph builder library invoked by the planner binary, producing a DependencyGraph for a given (repo, SHA) reproducibly (P11) and persisting it as Postgres jsonb (ADR-06).

13.4 Acceptance Criteria

Building the graph for conformance/manifests/lockfile_v3_valid.json yields 47 nodes at expected depths (0–4) matching a golden fixture; cyclic_lockfile.json is rejected within 500ms with MalformedManifest; rebuilding the same (repo, SHA) twice yields byte-identical serialized graphs.

13.5 Conformance Fixtures

conformance/manifests/lockfile_v3_valid.json — expected: 47-node DAG, golden depth map. conformance/manifests/cyclic_lockfile.json — expected: GraphBuildFailed → Abandoned(MalformedManifest). conformance/manifests/ empty_lockfile.json — expected: zero-node graph, no crash.

13.6 Pitfalls

Monorepo lockfiles with multiple package-lock.json files (workspaces) cause double-counting of shared dependencies if each workspace is graphed independently without a merge step — manifestation: the same advisory produces duplicate GraphJoined events across workspaces; root cause: no canonical (repo, SHA)-wide graph identity for workspace roots; debug: diff node counts against npm ls --workspaces; signal: graph.workspace.duplicate_node_total; recovery: merge workspace subgraphs under one graph ID before persisting.

Confusing resolved_version with requested_range when joining against AffectedRange causes false negatives for ranged advisories — manifestation: an advisory whose introduced/fixed bracket the resolved version is not flagged; root cause: join logic compared the range string, not the resolved semver; debug: unit test with a known-affected resolved version; signal: none automatic (silent false negative) — mitigated by conformance fixture lockfile_v3_valid.json's golden affected-node list; recovery: fix comparator to use AffectedRange against resolved_version only.

13.7 Performance Concerns

Graph build for a 5,000-node lockfile must complete within 3s p95 to keep the fix-attempt latency budget in §4; BFS is O(nodes + edges), bounded by lockfile size, not advisory count.

13.8 Edge Cases

A lockfile with a dependency present at two different resolved versions in different subtrees (legitimate npm behavior, not a cycle); a manifest with zero dependencies; a lockfile referencing a package removed from the registry (unresolvable but not itself a graph-build failure).

13.9 Failure Analysis

A lockfile parse failure mid-file (truncated JSON) must not partially persist a graph; the builder wraps the parse in a single transaction and emits GraphBuildFailed with the byte offset of the parse error for debugging.

13.10 Operational Notes

driftctl graph show <repo> <sha> dumps the sealed graph for manual inspection; used in incident response when a fix appears to target the wrong node.

14. Phase 2 — Risk Prioritizer

14.1 Objectives

Implement internal/risk to compute a RiskScore per (advisory, affected node) pair from CVSS v3.1 base metrics and graph depth, and order the fix queue by that score (ADR-14, prior to reachability in §21).

14.2 Detailed Implementation Steps

Parse the CVSS v3.1 vector string per the CVSS v3.1 Specification, computing the base score via the documented formula (Impact, Exploitability sub-scores). Combine base score with DependencyNode.Depth using a documented weighting (direct dependencies weighted 1.0, each additional depth level discounted) — this weighting is the Tricorder lesson (Sadowski et al. 2015) applied: surface only actionable, prioritized findings rather than a flat list. Persist RiskScore per P8 as a pure function with no forge-state input (I10).

14.3 Deliverable

A risk library producing a total ordering of pending advisories per repo, exposed via driftctl queue show.

14.4 Acceptance Criteria

A CVSS 9.8 direct dependency outranks a CVSS 9.8 depth-3 transitive dependency in the queue; recomputing RiskScore for an unchanged (advisory, graph) pair is idempotent (identical BaseScore to 2 decimal places); prioritizer.forge_call_ total remains 0 across the full conformance suite (I10).

14.5 Conformance Fixtures

conformance/risk/cvss_vector_critical.json — CVSS vector AV:N/AC:L/PR:N/UI:N/ S:U/C:H/I:H/A:H, expected base score 9.8. conformance/risk/depth_ordering.json — two advisories, same base score, different depths, expected: depth-0 ranked first.

14.6 Pitfalls

Misreading the CVSS v3.1 Scope (S:C vs S:U) inverts the Impact sub-score formula — manifestation: changed-scope vectors produce scores lower than expected; root cause: applying the unchanged-scope formula uniformly; debug: recompute by hand against the FIRST.org worked examples; signal: golden-fixture mismatch in cvss_vector_critical.json's sibling changed-scope fixture; recovery: branch the formula on Scope per section 4 of the CVSS v3.1 Specification.

14.7 Performance Concerns

Scoring must not itself query the forge (I10) or the network; a full-repo re-prioritization (thousands of pending advisories) must complete in under 1s to avoid becoming the bottleneck ahead of planning.

14.8 Edge Cases

An advisory with a malformed or missing CVSS vector (score defaults to a conservative "unscored, treat as high" placeholder, never silently dropped); an advisory affecting the same node at two different AffectedRange entries with different severities (max severity wins).

14.9 Failure Analysis

If CVSS parsing throws on an unexpected vector token, the prioritizer must not crash the queue for other advisories — isolate per-advisory scoring failures and emit risk.score.parse_failure_total per advisory, defaulting that one advisory to the conservative placeholder score.

14.10 Operational Notes

driftctl queue show --explain <advisory-id> prints the full score derivation (base score inputs, depth discount) for audit during a "why wasn't this fixed first" review.

15. Phase 3 — Sandbox & Validator

15.1 Objectives

Implement internal/sandbox: spawn a gVisor-backed OCI container per validation, apply a PatchSet to a disposable checkout, run the repo's declared test command, and enforce the CPU/memory/wall-clock ceilings from §4 (P4, I1, I7).

15.2 Detailed Implementation Steps

Use the OCI Runtime Specification to define the container bundle; configure runsc (gVisor) as the runtime handler per ADR-03, applying the seccomp/namespace lineage described by Provos (2003) at the user-space-kernel layer gVisor provides. Mount a fresh checkout of the repo at the target SHA (I13); apply the PatchSet inside the container, never on the host. Enforce cgroup CPU/memory ceilings (§4) at container spawn; enforce wall-clock timeout via a supervisor goroutine that issues SIGKILL and records Timeout per §8. Ensure zero credential environment variables are passed into the container (P7, I4) — verified by an allowlist check at spawn per I4's Detection column.

15.3 Deliverable

A sandbox-runner binary accepting a (repo SHA, PatchSet) pair and returning a ValidationRun with Result in {Passed, Failed, Timeout, SandboxError}.

15.4 Acceptance Criteria

A known-good PatchSet against fixture repo conformance/replay/fixture-repo-a validates Passed in under 5 minutes; a PatchSet that breaks a test validates Failed with the failing test name captured in Logs; a container exceeding 4 GiB memory is OOM-killed and recorded Timeout/SandboxError, never silently hangs past the 20-minute ceiling (§4).

15.5 Conformance Fixtures

conformance/replay/fixture-repo-a — a minimal npm repo with a deterministic test suite, used for Passed/Failed fixtures. conformance/replay/flaky_suite_repo — a repo with one intentionally flaky test (10% failure rate), used to exercise flaky-test detection in §15.6. conformance/replay/secret_leak_probe — a container image that attempts to read AWS_SECRET_ACCESS_KEY from its environment, expected: env is empty (I4 regression guard).

15.6 Pitfalls

Flaky tests defeating validation — manifestation: an otherwise-correct FixPlan is marked Failed nonstop due to a pre-existing flaky test unrelated to the bump; root cause: the test suite is the only oracle available (Weimer et al. 2009's fitness-function framing), so its flakiness becomes Drift's false-positive rate; debug method: re-run the identical PatchSet N times and compare pass-rate against a baseline run of the unpatched SHA; signal: sandbox.validation.flaky_suspect_total; recovery: quarantine the specific test name in repo policy config (ADR-21), not the whole suite.

Bumps that compile but break at runtime — manifestation: npm install and a type-check pass, but an integration test exercising the bumped package's changed runtime behavior fails; root cause: semver-compatible does not guarantee behavior-compatible (SemVer 2.0.0 only promises no intentional breaking API change); debug: diff the failing test's stack trace against the bumped package's changelog; signal: sandbox.validation.result{result="Failed"} correlated with a runtime (not build-time) failure; recovery: no automatic recovery — routed to Abandoned(ValidationFailed), left for source-level patch (Phase 7) or manual review.

Advisory range mis-parsing causing the wrong PatchSet to be validated — manifestation: validation passes but the applied bump does not actually satisfy the advisory's fixed-in range; root cause: an off-by-one in half-open vs closed-range interpretation of OSV events; debug: recheck ConstraintCheck proof against the raw OSV events array; signal: none from the sandbox itself (it only sees the PatchSet) — caught by planner-level fixture, not here; recovery: fixed in §16 (Phase 4), not §15.

Sandbox spawn latency spikes under concurrent load — manifestation: p95 exceeds the 2.5s target in §4; root cause: gVisor's user-space kernel init cost is per-container, not shared; debug: profile runsc startup trace; signal: sandbox.spawn.latency_ms histogram; recovery: pre-warm a pool of idle sandboxes (Phase 10 concern, deferred: PhaseDeferred("Phase 10 — Fleet Scale-Out & Rate-Limit Governor")).

15.7 Performance Concerns

Sandbox spawn latency p95 ≤ 2.5s (§4); per-validation ceilings (2 vCPU, 4 GiB, 20 min wall-clock) must be enforced by the kernel/cgroup layer, not application-level polling, to avoid a slow-loop detection race.

15.8 Edge Cases

A repo whose declared test command itself spawns a network call (must fail closed — no egress, per P4 — rather than hang); a repo with zero tests declared (validation trivially "passes", flagged with a distinct NoTestsDeclared note in Logs so it is not confused with a real green run); a patch that fails to apply at all inside the sandbox (routed to PatchApplyFailed, not ValidationFailed, per §8's state machine — patch application is a Phase-1-adjacent precondition, not a validation outcome).

15.9 Failure Analysis

Sandbox host process crash mid-validation: the supervising sandbox-runner control plane must detect the orphaned container (via a heartbeat file inside the checkout, per I13's disposable-checkout design), reap it, and re-emit Sandbox Started from scratch rather than resuming — partial validation state is never trusted (I7, I13).

15.10 Operational Notes

docs/runbooks/sandbox-timeout-triage.md distinguishes slow-but-passing suites from genuine hangs using the CPU-utilization trace captured for the run's duration (§8's failure-path worked example); on-call checks this before assuming a hang.

16. Phase 4 — Fix Planner (Version Bump)

16.1 Objectives

Implement internal/planner: given a prioritized Advisory and DependencyGraph, compute the minimal semver-compatible bump satisfying the advisory's fixed-in range, emitting a versioned, replayable FixPlan per P5/I2.

16.2 Detailed Implementation Steps

Parse AffectedRange.events per the OSV Schema's range-events model to derive the concrete fixed-in floor version. Solve for the minimal to_version satisfying both that floor and the repo's own requested_range (SemVer 2.0.0 precedence rules) — this is the ADR-07 default strategy, deliberately narrower than the GenProg/SapFix search-space framing (Monperrus 2018's taxonomy: Drift is generate-and-validate with a single deterministic candidate, not a search). Stamp every FixPlan with a planner_version tied to the release tag (P5); if no version in the resolvable range satisfies the advisory, emit NoFixAvailable and mark PhaseDeferred("Phase 7 — Source-Level Patching & Backports") as the escape hatch. Enforce I12/P9: never select a version beyond the minimal satisfying one without an explicit drift.yml policy override (ADR-21).

16.3 Deliverable

A planner library producing a FixPlan for any (Advisory, DependencyGraph) pair, with driftctl plan show <advisory-id> printing the derivation.

16.4 Acceptance Criteria

For GHSA-example-1234 (left-pad <1.3.0 fixed 1.3.0) against a graph resolving left-pad@1.2.0, the planner emits FixPlan{from:1.2.0, to:1.3.0} in under 50ms; replaying the same inputs at the same planner_version twice yields byte-identical FixPlan serialization (I2); an advisory with no satisfying version in the repo's declared range yields NoFixAvailable, never a partial or best-effort bump.

16.5 Conformance Fixtures

conformance/planner/minimal_bump.json — golden FixPlan for the left-pad case above. conformance/planner/no_fix_available.json — an advisory whose fixed-in version violates the repo's own major-version pin, expected: NoFixAvailable. conformance/replay/planner_replay_001.json — same (advisory, graph, planner version) run twice, expected: identical output hash (I2 regression guard).

16.6 Pitfalls

Advisory range mis-parsing: OSV events arrays can express multiple disjoint affected ranges (e.g. introduced 1.0.0, fixed 1.2.0, introduced 1.5.0, fixed 1.5.3) — manifestation: the planner picks a bump that satisfies only the first range, still landing in the second affected range; root cause: treating events as a single (introduced, fixed) pair instead of an ordered event sequence; debug: replay conformance/planner/multi_range_advisory.json; signal: golden-fixture mismatch; recovery: fully implement the OSV event-sequence walk per section 4 of the OSV schema.

Transitive-only vulnerabilities with no direct override path — manifestation: the affected package is a transitive dependency of a dependency the repo does not directly declare, and no to_version of the direct dependency exists that resolves to a fixed transitive version; root cause: semver bump of a leaf node is not always achievable by bumping only that node — the parent may need to bump too; debug: walk DependencyNode.Parents from the affected node to find the nearest bumpable ancestor; signal: planner.transitive_unfixable_total; recovery: NoFixAvailable with a blocked_by field naming the parent, or attempt a parent-level bump if the parent's own requested_range allows it.

Monorepo lockfile churn: bumping one package in a workspace lockfile can shift unrelated resolved versions elsewhere in the same lockfile (npm's deduplication algorithm) — manifestation: the resulting diff touches far more lines than the single intended bump, obscuring review; root cause: lockfile resolution is holistic, not per-package; debug: diff ManifestDeltas against the raw unified diff line count; signal: planner.diff.unexpected_delta_count; recovery: document in the PR body summary which deltas are direct vs incidental resolution noise.

16.7 Performance Concerns

Constraint solving for a single advisory must complete in well under the 8-minute p50 fix-attempt budget (§4) — target ≤50ms per plan so the sandbox validation step (§4's dominant cost) remains the bottleneck, not planning.

16.8 Edge Cases

An advisory fixed-in version that does not exist in the registry (withdrawn or yanked release) — must not select it; a repo pinned to an exact version (no range) where any bump is itself a manifest policy violation; an advisory whose fixed version requires a Node.js engine bump the repo does not declare support for.

16.9 Failure Analysis

If the semver library itself throws on a malformed version string in the lockfile (pre-semver legacy version tags), the planner must not crash the whole queue — isolate the failure to that one advisory, emit planner.version_parse_failure_ total, route to Abandoned with a distinct reason distinguishable from NoFixAvailable in dashboards.

16.10 Operational Notes

driftctl plan replay <advisory-id> --at <planner-version> reproduces a historical FixPlan exactly for dispute resolution (I2); used whenever a reviewer questions why a specific version was chosen.

17. Phase 5 — Justification Generator & Signing

17.1 Objectives

Implement internal/justify: assemble a canonical Justification document binding advisory ID, repo SHA, patch diff hash, and ValidationRun ID, sign it via Sigstore keyless signing (ADR-10), and persist the attestation per P3/I6.

17.2 Detailed Implementation Steps

Serialize Justification fields to canonical JSON (stable key ordering, no floating-point ambiguity) before signing, per the in-toto attestation model (Torres-Arias et al. 2019) wrapping an SLSA provenance predicate (ADR-11). Obtain a short-lived signing certificate from Fulcio using the service's OIDC identity, sign the canonical payload, and record the signature plus a Rekor transparency-log inclusion proof in the Sigstore bundle — this is the TUF lineage (Samuel et al. 2010) applied: the signing key itself is never long-lived, so its compromise window is bounded. Implement a justify verify path in driftctl that independently recomputes the diff hash from the PatchSet and confirms the signature and Rekor inclusion before trusting a Justification (I6).

17.3 Deliverable

A justifier binary producing a signed Justification for any (FixPlan, PatchSet, ValidationRun) triple where the run Result is Passed, plus a standalone driftctl verify CLI usable by a reviewer offline.

17.4 Acceptance Criteria

Signing a Justification for the worked example in §8 completes in under 2s; driftctl verify on a tampered PatchSet (single byte changed) fails closed with a clear "diff hash mismatch" error, never a silent pass; justification.verify. failure_total is 0 across the full conformance suite on unmodified fixtures.

17.5 Conformance Fixtures

conformance/justify/golden_justification.json — signed Justification for the §8 worked example, expected: verifies clean. conformance/justify/tampered_diff.json — identical Justification but with patch_diff_hash mutated, expected: verify fails with HashMismatch. conformance/justify/expired_cert.json — a signature using an expired Fulcio certificate, expected: verify fails with CertificateExpired, not a crash.

17.6 Pitfalls

Signing before the ValidationRun is fully sealed — manifestation: a Justification references a ValidationRunID whose Result later changes (e.g. a race where EndedAt is set after signing begins); root cause: missing a hard barrier between "ValidationRun sealed" and "justification signing starts"; debug: check EventRecord ordering for the affected run; signal: justify.race.unsealed_run_total (must stay 0); recovery: add a database-level check constraint that a ValidationRun must be terminal before any Justification referencing it can be inserted.

PR spam from re-signing on every planner rebuild — manifestation: a minor, behavior-neutral planner release (e.g. a logging change) bumps planner_version and causes every pending FixPlan to be re-justified and re-proposed, flooding reviewers; root cause: planner_version conflated build metadata with semantic planning-behavior changes; debug: diff the two planner versions' ConstraintCheck outputs on a fixed input set; signal: pr.reopen_rate spike correlated with a deploy; recovery: version the planner's semantic behavior separately from its build identifier, only re-justify on a semantic-version bump.

17.7 Performance Concerns

Signing must not become the bottleneck ahead of PR emission; Fulcio/Rekor round-trip latency (typically sub-second, network-dependent) is budgeted within the 8-minute p50 fix-attempt target (§4) as a small fixed cost.

17.8 Edge Cases

A ValidationRun result of Passed but with non-zero warnings in Logs (still justifiable, warnings are informational only); a repo requiring an air-gapped signing path with no OIDC provider reachable (ADR-10's rejected-alternative regime: falls back to long-lived GPG, a distinct code path, not a silent Sigstore skip).

17.9 Failure Analysis

Rekor transparency-log unavailability at signing time: the signer must fail closed (no Justification without an inclusion proof) rather than persist an unverifiable signature; retry with backoff up to a bounded attempt count, then route to Abandoned(SigningFailed) per §8.

17.10 Operational Notes

docs/runbooks/justification-verify-failure.md walks a reviewer through manually re-running driftctl verify against a disputed PR's attached artifact before escalating to security on-call.

18. Phase 6 — Forge / PR Emitter

18.1 Objectives

Implement internal/forge and cmd/pr-emitter: translate an accepted FixPlan plus its Justification into a PullRequestDraft, open it idempotently via the GitHub App forge adapter (ADR-12), and enforce the PR-per-advisory strategy (ADR-13).

18.2 Detailed Implementation Steps

Implement ForgeAdapter (per §11's interface) for GitHub, authenticating via a GitHub App installation token scoped to contents:write and pull-requests:write only (P7 boundary: the forge adapter, not the sandbox, holds this token). Derive HeadBranch deterministically from (advisory ID, repo SHA) per §8's contract; before opening, call FindExistingPR to enforce idempotent creation (I9's "no-op if already open" rule). Render BodySummary from the Justification's fields via the templates/ PR-body renderer — never the reverse (P3). Attach the Justification artifact as a PR check-run annotation or comment, never omit it (I9).

18.3 Deliverable

A pr-emitter binary that, given a Proposed-eligible FixPlan, opens exactly one GitHub PR carrying the rendered body and the attached Justification.

18.4 Acceptance Criteria

Emitting a PR for the §8 worked example produces a PR titled "Bump left-pad to 1.3.0 (fixes GHSA-example-1234)" with the Justification attached; re-invoking emission for the same (repo, SHA, advisory ID) with an already-open PR performs zero additional forge API calls beyond the idempotency check (§4's forge-quota budget); pr.missing_justification_total remains 0 across the conformance suite.

18.5 Conformance Fixtures

conformance/forge/golden_pr_draft.json — expected PullRequestDraft for the §8 example. conformance/forge/idempotent_reopen.json — second emission attempt for an already-open PR, expected: FindExistingPR short-circuits, zero new API calls. conformance/forge/missing_justification.json — a FixPlan handed to the emitter without an attached Justification, expected: emission blocked, pr.missing_ justification_total incremented.

18.6 Pitfalls

PR spam from ungrouped advisories on the same package — manifestation: five advisories against the same transitive package in one week each open a separate PR, overwhelming the reviewer (the Renovate lesson: config-driven grouping exists precisely to prevent this); root cause: ADR-13's per-advisory PR strategy, deliberately chosen for justification traceability (I9), has this as a known tradeoff; debug: count open PRs per (repo, package) over a rolling week; signal: pr.open_count{repo} exceeding the §4 governor default (10/day); recovery: apply the governor (Phase 10) to throttle, or adopt a grouped-update policy override (ADR-13's rejected-alternative regime) if the team prefers it.

Branch name collisions across re-processed advisories — manifestation: a ReprocessRequested event (P6) regenerates a FixPlan whose deterministic HeadBranch collides with a stale, already-merged-or-closed branch from a prior attempt; root cause: branch naming used only (advisory ID, repo SHA) without a processing-attempt discriminator; debug: check for an existing branch ref before push; signal: forge.branch.collision_total; recovery: include a monotonic reprocess counter in the branch name derivation.

18.7 Performance Concerns

Forge API quota (§4: ≤400 calls/repo/day) must be respected; FindExistingPR calls are cached per (repo, SHA, advisory ID) for the duration of a single emission attempt to avoid redundant GraphQL queries.

18.8 Edge Cases

A PR opened by Drift that a human manually edits (title/body) before merge — Drift must never force-push over manual edits (ADR-13); a repo with branch protection rules requiring a specific PR template — the renderer must be overridable per drift.yml without breaking Justification attachment.

18.9 Failure Analysis

GitHub API returns a transient 5xx during PR creation: retry with exponential backoff up to 3 attempts; if all fail, route to Abandoned with a distinct ForgeUnavailable reason (extending §8's enumerated failure reasons), never silently drop the FixPlan.

18.10 Operational Notes

docs/runbooks/forge-quota-exhaustion.md covers diagnosing and recovering from a GitHub API quota exhaustion event using the x-ratelimit-remaining response header captured in telemetry.

19. Phase 7 — Source-Level Patching & Backports

19.1 Objectives

Extend internal/patch beyond version bumps: synthesize a source-level patch (SourcePatch strategy) or a backported fix (Backport strategy) when no semver-compatible bump satisfies an advisory (the NoFixAvailable escape hatch from §16), using pattern-mined fix templates (Getafix, Bader et al. 2019).

19.2 Detailed Implementation Steps

Implement a template-matching engine over a curated library of fix patterns keyed by advisory class (e.g. prototype-pollution guard insertion, regex denial-of-service bound insertion) — this is Getafix's learned-template approach (Bader et al. 2019) applied narrowly, not GenProg's open-ended genetic search (Le Goues et al. 2012), keeping the search space bounded and each candidate individually justifiable (Monperrus 2018's taxonomy places this firmly in "template-based" repair). Extend FixPlan.Strategy handling in the planner to attempt SourcePatch only after SemverBump is exhausted (ADR-07's ordering). Backport strategy: cherry-pick the fix commit identified by the advisory's references (if a GitHub commit URL is present) onto the repo's currently pinned version, producing an AST-level patch (ADR-08's rejected-alternative regime now applies).

19.3 Deliverable

A patch library extension producing a SourcePatch- or Backport-strategy PatchSet for advisories that fail the Phase-4 semver-bump path, still validated through the unchanged §15 sandbox.

19.4 Acceptance Criteria

For a fixture advisory with no satisfying semver bump but a known Getafix-style template match, the planner emits a SourcePatch FixPlan that validates Passed; an advisory with no template match and no cherry-pickable commit reference correctly falls through to NoFixAvailable, never a fabricated patch.

19.5 Conformance Fixtures

conformance/patch/template_match_redos.json — a ReDoS advisory with a known bound-insertion template, expected: SourcePatch FixPlan, sandbox Passed. conformance/patch/backport_cherry_pick.json — an advisory with a GitHub commit reference and a pinned older major version, expected: Backport FixPlan applying cleanly. conformance/patch/no_template_no_commit.json — expected: NoFixAvailable, no fabricated patch.

19.6 Pitfalls

Template over-application — manifestation: a template matches syntactically but changes program semantics in a way the test suite does not cover, producing a Passed validation that is not actually safe; root cause: templates are pattern matches, not proofs (the exact caveat Monperrus 2018 raises about generate-and- validate repair); debug: manual review flagged explicitly in the PR body when Strategy != SemverBump (never silently treated like a bump); signal: none automatic — mitigated by policy requiring human review weight on non-bump PRs; recovery: drift.yml can disable SourcePatch/Backport strategies entirely, falling back to NoFixAvailable.

Cherry-pick conflicts on a heavily-forked pinned version — manifestation: the upstream fix commit does not apply cleanly due to unrelated drift between the pinned version and the fix's origin commit; root cause: backport assumes minimal divergence; debug: git apply --check failure output; signal: patch.backport.conflict_total; recovery: fall through to NoFixAvailable rather than attempting a fuzzy/partial apply.

19.7 Performance Concerns

Template matching over a moderate-size fix-pattern library must not add more than ~1s to planning latency, keeping the Phase-4 planning budget roughly intact.

19.8 Edge Cases

A template matching multiple candidate insertion points in the same file (ambiguous — must not guess, routes to NoFixAvailable with an ambiguous_match note); a backport commit that itself references a CVE fix bundled with unrelated refactoring (must isolate the security-relevant hunk only).

19.9 Failure Analysis

A SourcePatch that applies but fails sandbox validation must not be silently retried with a different template without an explicit next-candidate step recorded as a distinct EventRecord, preserving I11 (every failure-path transition is named).

19.10 Operational Notes

docs/runbooks/source-patch-review.md mandates a second human reviewer for any PR where Strategy != SemverBump, distinct from the standard single-reviewer bar for version-bump PRs.

21. Phase 9 — Call-Graph Reachability Context

21.1 Objectives

Extend internal/risk with static call-graph reachability analysis: determine whether the affected function in a vulnerable package is actually reachable from the repo's own entrypoints, refining RiskScore (ADR-14) without changing the fix strategy itself (§2's mastery bullet).

21.2 Detailed Implementation Steps

Build a call graph from the repo's own source (not the dependency's, initially — depth-1 reachability: does the repo call the vulnerable package's exported symbol at all) using static analysis over the import graph. Join the vulnerable symbol (extracted from the advisory's references or a curated symbol-level OSV extension where present) against the call graph; set RiskScore.Reachable to a concrete boolean, replacing the nil placeholder from §14. Deprioritize (not discard) unreachable-affected advisories — they remain in the queue at a lower weight, never silently dropped, per P10's "no silent failure path" discipline extended to prioritization.

21.3 Deliverable

A risk library extension setting RiskScore.Reachable for advisories where symbol-level data is available, with the fix queue re-ordered accordingly.

21.4 Acceptance Criteria

A fixture advisory against a package imported but never called from the repo's entrypoints is deprioritized below an otherwise-lower-CVSS but reachable advisory; RiskScore.Reachable remains nil (not false) when symbol-level advisory data is absent, distinguishing "known unreachable" from "unknown."

21.5 Conformance Fixtures

conformance/risk/reachable_direct_call.json — vulnerable symbol directly called, expected: Reachable: true, no priority discount. conformance/risk/unreachable_ imported_only.json — package imported, symbol never invoked, expected: Reachable: false, priority discounted per the documented weighting. conformance/risk/unknown_reachability.json — no symbol-level advisory data, expected: Reachable: nil, unchanged Phase-2 behavior.

21.6 Pitfalls

Reflection or dynamic dispatch defeating static reachability analysis — manifestation: a symbol invoked only via require(variableName) or reflection is marked unreachable when it is actually called at runtime; root cause: static call graphs are inherently incomplete under dynamic language features; debug: compare against a runtime coverage trace from the sandbox's test run (if available); signal: no automatic signal — this is a known soundness gap, documented, not silently assumed complete; recovery: Reachable: false from static analysis alone must only discount priority, never suppress the advisory from the queue entirely (I-level guarantee: no advisory is dropped based on reachability alone).

Over-trusting nil as false in downstream consumers — manifestation: a dashboard or the fix queue's sort comparator treats nil and false identically, silently deprioritizing advisories Drift has no actual reachability opinion on; root cause: *bool was introduced but consumers were not audited for the three-state distinction; debug: grep all Reachable reads for direct boolean coercion; signal: risk.reachability.nil_coerced_total; recovery: require explicit three-way handling (true/false/nil) at every consumption site, enforced by a lint rule.

21.7 Performance Concerns

Call-graph construction for a moderate repo (10k LoC) must complete within a few seconds to avoid blocking the Phase-2 prioritization step; reachability is computed once per (repo, SHA) and cached, not recomputed per advisory.

21.8 Edge Cases

A vulnerable symbol reachable only through a test-only code path (not production code) — must be flagged distinctly from production-reachable; a monorepo where only one of several packages actually imports the vulnerable dependency.

21.9 Failure Analysis

Call-graph construction timing out on a pathologically large repo must not block Phase-2 prioritization for that repo indefinitely — fall back to Reachable: nil (unknown) after a bounded analysis budget, emit risk.reachability.analysis_ timeout_total, never block the queue.

21.10 Operational Notes

driftctl risk explain --reachability <advisory-id> prints the call path (or absence of one) used to set Reachable, for reviewer audit when reachability discounting is questioned.

22. Phase 10 — Fleet Scale-Out & Rate-Limit Governor

22.1 Objectives

Scale Drift from single-repo (Phase 0–9) to a multi-repo fleet (up to 500 repos, §4) via Kubernetes Job scheduling (ADR-04), introducing a rate-limit governor enforcing per-repo and fleet-wide forge-quota and PR-volume ceilings (§4).

22.2 Detailed Implementation Steps

Migrate sandbox-runner invocation from direct OCI control to Kubernetes Jobs (ADR-04's Phase-10 branch), each Job requesting the §4 CPU/memory ceilings as resource requests/limits. Introduce a governor component sitting between the risk-prioritized queue and the planner/PR-emitter, enforcing the §4 PRs/day-per- repo ceiling and the fleet-wide forge API quota via a token-bucket algorithm keyed per repo and per fleet — this is the SRE load-shedding pattern (Beyer et al., ch. 22) applied at the governor boundary, distinct from the per-repo planner (P8: the planner remains a pure function, the governor is where fleet-wide scheduling policy lives). Shard the event store by repo for write throughput at fleet scale (still single-writer per repo, satisfying I8's append-only guarantee).

22.3 Deliverable

A governor component and Kubernetes Job-based sandbox-runner deployment supporting 500 concurrently tracked repos within the §4 concurrency and FD budgets.

22.4 Acceptance Criteria

Under a simulated fleet-wide advisory burst (5,000/hour, §4), no single repo exceeds its 10 PRs/day governor ceiling; fleet-wide GitHub API quota consumption stays within documented limits with zero 403 rate-limit responses in the conformance load test; a single repo's sandbox Job failure does not affect other repos' concurrent Jobs.

22.5 Conformance Fixtures

conformance/governor/burst_500_repos.json — simulated fleet-wide burst, expected: per-repo PR ceiling respected, no forge 403s. conformance/governor/ single_repo_starvation.json — one repo with an unusually high advisory volume, expected: governor throttles that repo without starving others (fair-share token bucket).

22.6 Pitfalls

A single noisy repo consuming the entire fleet-wide forge quota — manifestation: other repos' PRs stall while one repo's advisories dominate API calls; root cause: token-bucket keyed only per-repo without a fleet-wide fair-share ceiling; debug: compare per-repo forge-call telemetry against the fleet total; signal: governor. fairness.starvation_detected_total; recovery: add a fleet-wide secondary bucket enforcing max-share-per-repo independent of the per-repo bucket.

Kubernetes Job scheduling latency defeating the sandbox-spawn-latency target (§4: 2.5s p95) — manifestation: Job pod scheduling adds seconds of overhead beyond gVisor's own container-init cost; root cause: no pre-warmed node pool or Job template caching; debug: compare sandbox.spawn.latency_ms before/after the Kubernetes migration; signal: latency regression in the same histogram used in §15; recovery: maintain a warm pool of pre-scheduled idle pods (referenced as the deferred mitigation in §15.6).

22.7 Performance Concerns

Fleet-wide event-store write throughput must scale with repo count via per-repo sharding (ADR-05's Kafka rejected-alternative regime becomes relevant here if sharding proves insufficient); governor decision latency must stay under 100ms to avoid becoming the new bottleneck ahead of planning.

22.8 Edge Cases

A repo removed from the fleet mid-processing (in-flight FixPlans must drain or be explicitly abandoned, never orphaned); a fleet-wide GitHub App installation token rotation event occurring mid-burst (must not drop in-flight PR emissions).

22.9 Failure Analysis

Governor process crash: token-bucket state must be reconstructable from the event store alone (no governor-local state is authoritative) so a restarted governor does not simply reset every repo's throttle to zero and cause a burst.

22.10 Operational Notes

23. Phase 11 — Conformance & Performance Hardening

23.1 Objectives

Consolidate the full conformance fixture suite across all prior phases into a single release gate, and drive every §4 quantified target to a measured, load- tested pass under the §16.2 harness methodology (Performance Engineering).

23.2 Detailed Implementation Steps

Aggregate every fixture referenced in §12.5 through §22.5 into conformance/'s CI-run suite; add regression fixtures for every previously-fixed bug found during Phase 0–10 hardening. Build benchmarks/ load-generation harnesses exercising each §4 row directly (advisory burst, sandbox concurrency, fix-attempt latency percentiles) using the SRE monitoring framing (Beyer et al., ch. 6) to define SLI/ SLO pairs per metric. Fuzz internal/advisory and internal/graph parsers (fuzz/) against malformed OSV and lockfile inputs beyond the hand-written malformed fixtures, per the Tricorder lesson of surfacing only actionable findings — fuzz-found crashes become new named conformance fixtures, not just bug tickets.

23.3 Deliverable

A green run of the full conformance suite plus a benchmarks report demonstrating every §4 target met at the documented percentile, published to docs/ performance/.

23.4 Acceptance Criteria

100% of conformance fixtures pass; fix-attempt latency p50/p95/p99 measured at or better than 8/25/45 minutes (§4) under the burst load profile; zero fuzz-found crashes remain unfixed at release tag time; make conformance and make bench both exit 0 in CI.

23.5 Conformance Fixtures

conformance/regression/ — one fixture per historically-fixed bug across Phase 0–10, named by issue reference. conformance/fuzz-regressions/ — minimized crash-inducing inputs promoted from fuzz/ runs. conformance/replay/full_suite_ smoke.json — end-to-end smoke fixture exercising Detected → Merged across all phases in one run.

23.6 Pitfalls

Conformance suite growing slow enough to itself violate CI time budgets — manifestation: make conformance exceeds a reasonable CI wall-clock ceiling as fixtures accumulate across 11 phases; root cause: fixtures run serially by default; debug: profile make conformance wall time per fixture directory; signal: CI job duration trend; recovery: parallelize fixture execution by phase directory, keeping the aggregate gate but not the aggregate latency.

Load-test results not reflecting production topology (e.g. benchmarking on a single powerful machine when production runs Kubernetes Jobs, §22) — manifestation: measured latencies look better in benchmarks than in the field; root cause: benchmarks/ harness predates the Phase-10 Kubernetes migration and was never updated; debug: compare sandbox.spawn.latency_ms distributions, benchmark vs production telemetry; signal: divergence between the two histograms; recovery: re-run benchmarks/ against a Kubernetes-Job-backed environment matching production, not a bare-metal stand-in.

23.7 Performance Concerns

The full §4 target table is the acceptance bar for this phase; any target not met blocks the release tag, per the Performance Engineering gate.

23.8 Edge Cases

A regression fixture that only reproduces under specific timing (a real flaky regression, distinct from a flaky repo test in §15) — must be marked explicitly as timing-sensitive in its fixture metadata, not silently skipped.

23.9 Failure Analysis

A conformance regression discovered post-release: docs/failure-analysis/ receives a postmortem entry per the template, and the causing gap is closed with a new named fixture before the next release tag, per the debugging methodology in §7.

23.10 Operational Notes

27. Compatibility & Versioning

Advisory, FixPlan, PatchSet, and Justification schemas are versioned independently (per §11's per-type compatibility notes) using additive-only field changes; a breaking change requires a new planner_version or justifier_version major bump, never an in-place field reinterpretation (P5's replay guarantee depends on this). The EventRecord envelope carries its own schema version distinct from its payload version (§11), allowing the event store's storage format to evolve without invalidating historical replay. ForgeAdapter implementations version independently per forge (GitHub v1, future GitLab adapter v1) behind the shared interface (§11); a forge API deprecation is handled by a new adapter version, not a change to the interface contract. drift.yml policy schema follows its own semver, with unknown keys ignored (forward compatible) rather than rejected, so older Drift versions do not break on newer config files.

28. Testing & Verification Strategy

Four layers: unit tests per internal/ package (parsers, constraint solvers, signing, forge adapter, each mocked at its boundary); the fixture-driven conformance suite (§12.5 through §23.5, aggregated in §23) as the release gate; fuzz testing (fuzz/) over internal/advisory and internal/graph parsers against malformed and adversarial inputs (§23.2); and load/benchmark testing (benchmarks/) validating every §4 quantified target end-to-end under the SRE SLI/SLO framing (Beyer et al., ch. 6). Conformance fixtures are the source of truth for behavior — a bug fix without an accompanying regression fixture in conformance/regression/ (§23.5) is considered incomplete. Sandbox isolation itself (I1, T1) is verified by a dedicated secret_leak_probe and escape-attempt fixture suite run in an isolated CI runner with no production credentials present, so a successful escape in testing cannot itself cause a real compromise.

31. Scalability Analysis

Single-repo (Phase 0–9) scaling is bounded by sandbox concurrency (§4: 8 concurrent validations per host) and advisory volume (500/hour steady state); this ceiling is reached long before event-store or forge-quota limits become binding for one repo. Fleet scale-out (Phase 10, §22) shifts the bottleneck to three places in order: forge API quota (mitigated by the governor's fleet-wide fair-share bucket), Kubernetes Job scheduling latency (mitigated by a warm pod pool, §22.6), and event-store write throughput (mitigated by per-repo sharding, ADR-05). Beyond roughly 500 repos, the append-only Postgres event store's single-writer-per-repo model begins to approach the point where ADR-05's rejected Kafka alternative becomes the better regime — this is an explicit, anticipated migration trigger, not an unbounded scaling promise. The sandbox pool itself scales horizontally (each Kubernetes node hosts a bounded number of concurrent gVisor containers per its own CPU/memory budget), so fleet growth translates linearly into additional nodes, not additional contention on a shared resource, as long as the governor's per-repo and fleet-wide ceilings are correctly tuned (§22.6's starvation pitfall being the primary failure mode to watch during that scaling).

32. Mental Models & First Principles

MM1 — The repo's own test suite is the only oracle Drift has; its flakiness is Drift's false-positive rate.

  • Predicts: fix-attempt latency and correctness both degrade as repo test flakiness rises, independent of planner quality.
  • Bug class without it: treating TestsFailed as ground truth and abandoning a correct fix permanently, or worse, retrying blindly and burning sandbox budget.
  • Resolves: §15.6 (Pitfalls), §28 (flaky-test taxonomy, Winters et al. ch. 22).

MM2 — A signature only proves the artifact wasn't tampered with; it does not prove the artifact's claims are true.

  • Predicts: a Justification can verify cleanly while still encoding a wrong risk_score if the CVSS vector parse was already corrupted upstream.
  • Bug class without it: conflating "signature verifies" with "advisory data was correct," collapsing T2 and T8 into a single (wrong) mitigation.
  • Resolves: §17 (Justification generator), T2, T8, I6.

MM3 — Isolation is a boundary you enforce, not a property you inherit from "it's in a container."

  • Predicts: a plain-runc sandbox with a shared host kernel remains exploitable by any syscall gVisor would have intercepted; "containerized" is not "isolated."
  • Bug class without it: shipping runc alone and believing P4 is satisfied, when ADR-03 specifically chose gVisor because runc shares the host kernel's syscall table.
  • Resolves: §15 (Phase 3), ADR-03, T1.

MM4 — Reproducibility is a function signature (repo SHA, advisory ID, planner version) → (FixPlan, PatchSet), and any hidden input breaks it.

  • Predicts: "latest available version" resolved without a pinned timestamp makes two runs of the same planner produce different bumps for the same three inputs.
  • Bug class without it: an unreplayable fix that cannot be forensically defended after a disputed PR, silently violating P5/I2.
  • Resolves: §11 (FixPlan/PatchSet schema), P5, I2.

MM5 — The minimal satisfying bump is a deliberately narrow point in the automatic program-repair search space, not a limitation to apologize for.

  • Predicts: Drift will refuse fixes GenProg/SapFix-style search could find (a source patch when no semver bump satisfies the range), by design, until Phase 7.
  • Bug class without it: silently widening the search (e.g. speculatively patching source) without the sandboxed-validation and justification infrastructure Phase 7 requires, reintroducing an unvalidated blast radius.
  • Resolves: §16.2, ADR-07, §19 (Phase 7), Monperrus 2018 taxonomy.

MM6 — Every failure edge needs a name before it needs a handler.

  • Predicts: an unnamed failure path (a silent catch/drop) becomes an invisible stalled-queue cause that on-call cannot query from the event store.
  • Bug class without it: FM-3-style "stalled remediation queue" incidents where the root cause requires log archaeology instead of a state-machine query.
  • Resolves: §8 (state machine), P10, I11.

MM7 — Secrets and untrusted execution must never share a process boundary, even transiently.

  • Predicts: any code path that injects a forge token or registry credential into the sandbox-runner's environment — even for one call — turns a sandbox escape (T1) into a credential-theft event (T3) in a single step.
  • Bug class without it: a "just this once" private-registry credential injection that silently violates I4/P7 and is never caught because it "worked."
  • Resolves: §7 (I4), P7, ADR-19, T1, T3.

MM8 — A dependency graph is a snapshot keyed to a SHA, not a mutable live object.

  • Predicts: reusing a graph across commits without rebuilding produces false negatives the moment a manifest changes underneath the cached graph.
  • Bug class without it: an incremental-mutation optimization that silently reintroduces P11's rejected failure mode to save graph-build latency.
  • Resolves: §13 (Phase 1), P11, ADR-06.

MM9 — Telemetry names are part of the domain model, not an afterthought bolted on after the state machine is built.

  • Predicts: renaming a domain state without a coordinated telemetry migration makes dashboards silently stop reflecting the real state machine (telemetry drift), an outage that produces no alert.
  • Bug class without it: a dashboard rebuilt from stale span names that reports a healthy queue while the real state machine has changed underneath it.
  • Resolves: §8 (state machine), P12, §26 (Operational Readiness).

MM10 — At fleet scale, fairness is a resource-allocation problem before it is a throughput problem.

  • Predicts: an aggregate-only rate limiter starves a subset of repos (FM-10) long before the fleet's total forge-quota ceiling is reached.
  • Bug class without it: a single shared token bucket with no per-repo fair-share floor, correctly bounding total throughput while silently failing individual repos.
  • Resolves: §22 (Phase 10), T10, FM-10, ADR-05's Kafka-migration trigger.

34. Back-of-Envelope Capacity Model

Weekly validation wall clock (single repo, Phase 0–9): advisories/repo/week = 500/hour steady state × 24 h × 7 d ÷ 1 repo, but bounded by risk-filtered volume, not raw ingest — using the M3 p50 fix-attempt latency (8 min) as the per-validation wall-clock proxy: 1 repo × ~50 advisories/week (typical risk-filtered rate, not raw 500/hour ingest) × 8 min ÷ 8 sandbox slots (§4 max concurrency) = 400 sandbox-minutes ÷ 8 = 50 minutes of wall-clock queue time/week at typical load — negligible against the 5 min RTO (§4) and far below saturation.

Sandbox host RAM: per-validation RSS ceiling (§4: 4 GiB) × 8 concurrent validations (§4 max concurrency, single host) = 32 GiB minimum host RAM provisioned for the sandbox pool alone, before control-plane and OS overhead (add ~4 GiB operational headroom → 36 GiB target host size).

Event-store bytes (single repo, steady state): 5 MiB/day (§4, M13's per-repo basis) × 90-day retention (default operational retention window) = 450 MiB/repo retained; at 500-repo fleet scale (§4) with per-repo sharding (ADR-05): 500 × 450 MiB = 225 GiB fleet-wide steady-state retained event data.

Forge API budget: ≤ 400 calls/repo/day (§4, M11) vs 10 PRs/day/repo governor default (§4) → 40 calls/PR budget; GitHub's REST default quota is 5,000 calls/hour/installation, i.e. 120,000 calls/day — 400 calls/repo/day means a single installation token could in principle serve up to 300 repos before hitting the raw GitHub quota ceiling, well above the Phase 0–9 single-repo scope and consistent with the 500-repo fleet target needing the governor's fair-share allocation (§22) rather than raw quota headroom.

Advisory ingest rate vs feed size: 500/hour steady state (§4) × 24 h = 12,000 advisories/day processed; osv.dev's full export is on the order of low hundreds of thousands of records fleet-wide across all ecosystems — at 12,000/day a full re-ingest of a 300,000-record snapshot would take 25 days, confirming the ingester (§12) must be cursor/delta-based, not full-rescan, for steady state.

Dependency-graph memory: a 5,000-node lockfile (§4/M8 basis) × ~200 bytes/node (name + ecosystem + version strings + depth int, excluding parent/child edge lists) ≈ 1 MiB base node storage; edges at an average fan-out of 4 children/node × 5,000 nodes × 8 bytes/edge (int64 node ID) ≈ 160 KiB; total in-memory DependencyGraph for one (repo, SHA) ≈ 1.2 MiB, well within the 3 s p95 graph- build latency target (§4/M8) for a single-pass build.

Sandbox spawn throughput vs M6/M7 target: 8 concurrent validations (§4) × 1 spawn/2.5 s (§4/M6 p95) = a sustained sandbox-pool spawn rate of ~3.2 spawns/second at full saturation — this is the ceiling a warm-pod pool (§22.6) must absorb during a Kubernetes Job-scheduled burst before M7's 2.5 s p95 target degrades.

Justification signing throughput: 12,000 advisories/day ingested (above) but only a small risk-filtered fraction (~50/week per repo, above) ever reach Justified; at M10's < 2 s signing latency, even the full 5,000/hour burst ingest rate (§4) converted 1:1 to signings (worst case, never actually reached given the funnel) would demand 5,000 × 2 s ÷ 3,600 s ≈ 2.8 signer-seconds of work per wall-clock second — comfortably parallelizable across a small signer pool, confirming signing is never the bottleneck relative to sandbox concurrency.

36. Alternative Architectures (Roads Not Taken)

(a) CI-plugin model — runs inside the customer's own pipeline, no hosted sandbox.

customer CI pipeline
┌─────────────────────────────────────┐
│ existing build stage                │
│         ↓                           │
│ drift-ci-plugin (installed step)    │
│   - fetches advisories               │
│   - plans fix, applies patch         │
│   - runs existing CI test stage      │
│     (no separate sandbox — reuses    │
│      the pipeline's own runner)      │
│         ↓                           │
│ opens PR via pipeline's git creds    │
└─────────────────────────────────────┘

Winning regime: customers who already trust their CI runner and refuse to grant a third-party hosted sandbox any repo access. REAL embodying system: Renovate's self-hosted mode and GitHub Actions-based Dependabot updates. Rejected because: P4/I1 require a hardened, zero-egress, namespace/seccomp-isolated sandbox Drift controls end-to-end; a customer's CI runner is typically not gVisor-isolated, has network egress, and often holds unrelated deploy credentials — reusing it collapses T1's mitigation and reopens exactly the SolarWinds/Codecov build- compromise class §2 cites as motivation.

(b) Report-only scanner — never patches, detection only.

advisory feed → ingest → graph join → risk score → SARIF/JSON report
                                                          ↓
                                              (no patch, no PR, no sandbox)

Winning regime: CI-gate use cases (fail the build on a critical CVE) and polyglot environments needing broad ecosystem coverage over remediation depth. REAL embodying system: OSV-Scanner + Trivy (§33). Rejected because: §2's thesis is that CVE/advisory volume outpaces human triage capacity specifically — a report without a validated fix still requires a human to plan, patch, test, and PR by hand, leaving the actual bottleneck (§2) unaddressed.

(c) LLM-agent repair loop — test suite as reward signal, agentic patch search.

advisory → LLM agent proposes patch → run test suite → pass? → done
                          ↑_______________|  fail: revise, retry (bounded)

Winning regime: source-level fixes with no available semver bump, where a search over patch space (GenProg/SapFix lineage) can find a fix a deterministic bump-solver cannot. REAL embodying system: research agentic-repair systems built on the GenProg/SapFix lineage (§2, §33). Rejected for Phase 0–6: P5's reproducibility guarantee (byte-for-byte regeneration from repo SHA + advisory ID + planner version) does not hold for a non-deterministic search process without heavy additional constraints (seed pinning, bounded iteration recording); this is exactly why Phase 7 (§19) scopes source-level patching as a separate, later, explicitly-justified capability rather than folding it into Phase 0's planner.

(d) Registry-side "fixed fork" distribution — a patched package variant published to the registry, no PR to the tracked repo at all.

vulnerable pkg@1.2.0 in registry
        ↓ (Drift-maintained fork)
patched pkg-fixed@1.2.0+drift1 published
        ↓
consuming repos silently resolve to the fork via override/alias

Winning regime: ecosystem-wide remediation of a single widely-depended package (e.g. a left-pad-class transitive dependency) where patching every consuming repo individually doesn't scale. REAL embodying system: no direct production analog at Drift's scope; closest real precedent is npm's own registry-side deprecation/advisory flagging (not a fix-fork). Rejected because: it bypasses P1/P3 entirely — there is no PR to review and no Justification bound to a specific repo SHA, so a consuming repo silently inherits a change with no human-reviewed approval gate, which is the exact blast-radius Drift's core design exists to avoid (§2, P1).

38. Glossary

Advisory — an OSV-shaped vulnerability disclosure record ingested by Drift; see §8, §11.

Advisory ID — the unique identifier (GHSA-xxxx, OSV-2024-xxxx) used as part of the dedup key (P6, ADR-15).

AffectedRange — the OSV ranges[].events-shaped substructure of an Advisory describing introduced/fixed/last-affected version boundaries; §8.

Attestation — a signed, machine-verifiable claim about a build or validation step; the in-toto wrapper around Drift's Justification (ADR-11).

Backport — porting a fix from a later version into an older version line without adopting all intervening changes; a Phase 7 fix strategy (§19).

Base score (CVSS) — the environment-independent severity component of a CVSS v3.1 vector; §14, T9.

Blast radius — the scope of harm a failure or compromise can cause; used throughout the Threat Model (§24) and P1's rationale.

Cgroup — a Linux kernel mechanism for bounding a process group's CPU/memory/IO; enforces per-validation ceilings (§4, I7).

Constraint solve — the semver range-satisfaction computation the planner performs to find the minimal to_version; §16, M9.

CVSS vector — the FIRST.org Common Vulnerability Scoring System string encoding severity metrics; §8, T9, ADR-14.

Dedup key — the (advisory ID, ecosystem, repo SHA) tuple enforcing exactly-once advisory processing; P6, ADR-15, I3.

Dependency confusion — an attack where a build resolves to an attacker-controlled package instead of the intended one; T4.

Dependency graph — the DAG of DependencyNodes built from a repo's lockfile at a given SHA; §8, §13, ADR-06.

Detection window — the interval between advisory publication and Drift's AdvisoryDetected event; bounded by ingest throughput (§4, M1/M2).

Diff hash — the content hash of a PatchSet's concatenated unified diff, bound into the Justification; §8, I6.

Dependency-graph memory — the in-memory footprint of a sealed DependencyGraph for one (repo, SHA); quantified in §34.

Escape (sandbox) — untrusted repo code breaking out of its isolation boundary; T1, MM3.

Event store — the append-only Postgres log of EventRecords, the sole audit and replay authority; §8, I8, ADR-05.

Exactly-once processing — the guarantee that no advisory is planned/patched twice for the same SHA; P6, I3, Kleppmann ch. 11 (§5).

Fair-share bucket — a per-repo token-bucket allocation preventing one repo from starving another's forge quota at fleet scale; §22, T10, FM-10.

Fix plan (FixPlan) — the versioned, replayable intermediate representation of a proposed remediation; §8, §16.

Fixed-in range — the version boundary in an AffectedRange at or above which an Advisory no longer applies; §8, §16.2.

Flaky test — a test whose pass/fail outcome varies across identical runs, undermining the test-suite-as-oracle design; §15.6, §28, MM1.

Forge — the code-hosting platform (GitHub, later others) Drift integrates with via a ForgeAdapter; §11, ADR-12.

Fulcio — the Sigstore certificate authority issuing short-lived signing certificates bound to an OIDC identity; ADR-10, T8.

Governor — the Phase 10 component enforcing per-repo and fleet-wide PR/forge-call rate limits; §22.

Head branch — the deterministically-named git branch a Drift PR is opened from, derived from advisory ID + repo SHA; §8.

Idempotent PR creation — the guarantee that resubmitting an identical draft is a no-op if an equivalent open PR exists; §8, ADR-18.

Justification — the signed, schema-validated artifact binding advisory ID, patch diff hash, validation run ID, and planner version; §8, §17, P3.

Justifier — the service that generates and signs a Justification; §1, §17.

Lockfile — the ecosystem-specific manifest of resolved dependency versions (e.g. package-lock.json); §1, §13, ADR-16.

OSV — Open Source Vulnerabilities, the machine-readable advisory schema Drift ingests; §2, ADR-02.

OSV range — the events-based structure OSV uses to express introduced/fixed version boundaries within an AffectedRange; §8, §16.2.

Patch apply — the sandbox-internal step of applying a PatchSet to a checkout before validation; §8 (PatchApplyFailed).

PatchSet — the unified-diff representation of a proposed fix, with a content hash and structured manifest deltas; §8, §11, ADR-08.

Planner version — the versioned identity of the planner release that produced a given FixPlan, load-bearing for replay; P5, I2, §27.

Provenance — the verifiable record of how a build artifact was produced; SLSA provenance predicate, ADR-11, §17.

Pull request draft (PullRequestDraft) — the forge-agnostic representation of a proposed PR before forge-specific emission; §8.

Reachability — whether a vulnerable code path is actually invoked by the consuming repo, a Phase 9 risk-scoring refinement; §21, ADR-14.

Rekor — the Sigstore transparency log recording every signing event for public auditability; ADR-10, T8, FM-9.

Repo-declared test command — the build/test invocation the repo itself specifies (Makefile/package.json script), used verbatim by the sandbox validator rather than inferred; ADR-09.

Reprocessing — the explicit, audited operator action re-entering an Abandoned advisory back to Detected; P6, §8.

Risk score (RiskScore) — the computed prioritization value combining CVSS base score, graph depth, and (from Phase 9) reachability; §8, §14.

Sandbox — the gVisor-isolated, zero-egress execution environment for all untrusted repo code; §1, §15, ADR-03, P4.

Sandbox-runner — the service that spawns, monitors, and tears down sandboxed validations; §1, §15.

Sandbox spawn latency — the time from validation request to a running, patch-applied sandbox; M6, M7, §34.

SemVer — Semantic Versioning 2.0.0, the version precedence and range semantics the planner solves against; §5, §16.

Signed keyless signing — Sigstore's Fulcio/Rekor-based signing scheme requiring no long-lived private key; ADR-10.

Test-suite-as-oracle — the design premise that the repo's own test suite is the sole correctness signal for a proposed fix; §2, P2, MM1.

Un-defer trigger — the measurable condition under which a PhaseDeferred feature is promoted into active scope; §37.

Validation run (ValidationRun) — the recorded execution of a sandboxed test- suite attempt against a PatchSet, terminal in a pass/fail/timeout outcome; §8, §15.
