⬜ Phase 0 — Skeleton, Advisory Ingest & CI §12

Objectives

Stand up the five Phase-0 services as separate binaries sharing internal/ libraries; implement the ingester against osv.dev and GitHub Security Advisories; persist Detected events to the event store; establish CI (lint, unit test, conformance fixtures) as the release gate for every subsequent phase.

Deliverable

A running ingester binary that polls osv.dev on a fixed interval, normalizes at least one real advisory end-to-end into a Detected EventRecord, and a CI pipeline that fails the build on any conformance fixture regression.

Acceptance

Ingesting the fixture conformance/advisories/ghsa_example_1234.json produces exactly one Detected event within 2s (p95, §4-adjacent local target); re-ingesting the identical advisory a second time produces zero new events (I3); CI blocks merge on any fixture in conformance/advisories/ failing; event-store schema migration runs idempotently via make migrate.

Fixtures

conformance/advisories/ghsa_example_1234.json — well-formed OSV advisory, expected: one Detected event. conformance/advisories/malformed_missing_events.json — missing affected[].events, expected: Detected{malformed:true} routed to Abandoned(MalformedAdvisory) per §8. conformance/replay/ingest_replay_001.json — replays an already-ingested advisory, expected: zero new events (I3 regression guard).

Pitfalls

Treating osv.dev pagination cursors as stable across polls (they are not guaranteed stable under concurrent updates) causes silent advisory loss — manifestation: gaps in Detected events for advisories confirmed present on osv.dev; root cause: cursor invalidated mid-page by an upstream update; debug method: replay the poll window against the OSV export snapshot; signal: ingester.poll.cursor_reset_total; recovery: re-poll the full window on cursor reset rather than resuming from the stale cursor.

Deduplicating only on advisory ID (ignoring ecosystem) causes cross-ecosystem collisions (e.g. an npm and a PyPI advisory sharing an upstream CVE ID) to be merged incorrectly — manifestation: one ecosystem's advisory silently suppresses the other's; root cause: I3's compound key implemented as a partial index; debug: query the unique index definition; signal: ingester.dedup.rejected_total spiking for a benign case; recovery: fix the index to the full compound key, backfill missing events.

⬜ Phase 1 — Dependency-Graph Extraction §13

Objectives

Build internal/graph to parse an npm package-lock.json at a given repo SHA into a DependencyNode DAG, join it against ingested advisories, and persist a sealed DependencyGraph per (repo, SHA) per P11.

Deliverable

A graph builder library invoked by the planner binary, producing a DependencyGraph for a given (repo, SHA) reproducibly (P11) and persisting it as Postgres jsonb (ADR-06).

Acceptance

Building the graph for conformance/manifests/lockfile_v3_valid.json yields 47 nodes at expected depths (0–4) matching a golden fixture; cyclic_lockfile.json is rejected within 500ms with MalformedManifest; rebuilding the same (repo, SHA) twice yields byte-identical serialized graphs.

Fixtures

conformance/manifests/lockfile_v3_valid.json — expected: 47-node DAG, golden depth map. conformance/manifests/cyclic_lockfile.json — expected: GraphBuildFailed → Abandoned(MalformedManifest). conformance/manifests/ empty_lockfile.json — expected: zero-node graph, no crash.

Pitfalls

Monorepo lockfiles with multiple package-lock.json files (workspaces) cause double-counting of shared dependencies if each workspace is graphed independently without a merge step — manifestation: the same advisory produces duplicate GraphJoined events across workspaces; root cause: no canonical (repo, SHA)-wide graph identity for workspace roots; debug: diff node counts against npm ls --workspaces; signal: graph.workspace.duplicate_node_total; recovery: merge workspace subgraphs under one graph ID before persisting.

Confusing resolved_version with requested_range when joining against AffectedRange causes false negatives for ranged advisories — manifestation: an advisory whose introduced/fixed bracket the resolved version is not flagged; root cause: join logic compared the range string, not the resolved semver; debug: unit test with a known-affected resolved version; signal: none automatic (silent false negative) — mitigated by conformance fixture lockfile_v3_valid.json's golden affected-node list; recovery: fix comparator to use AffectedRange against resolved_version only.

⬜ Phase 2 — Risk Prioritizer §14

Objectives

Implement internal/risk to compute a RiskScore per (advisory, affected node) pair from CVSS v3.1 base metrics and graph depth, and order the fix queue by that score (ADR-14, prior to reachability in §21).

Deliverable

A risk library producing a total ordering of pending advisories per repo, exposed via driftctl queue show.

Acceptance

A CVSS 9.8 direct dependency outranks a CVSS 9.8 depth-3 transitive dependency in the queue; recomputing RiskScore for an unchanged (advisory, graph) pair is idempotent (identical BaseScore to 2 decimal places); prioritizer.forge_call_ total remains 0 across the full conformance suite (I10).

Fixtures

conformance/risk/cvss_vector_critical.json — CVSS vector AV:N/AC:L/PR:N/UI:N/ S:U/C:H/I:H/A:H, expected base score 9.8. conformance/risk/depth_ordering.json — two advisories, same base score, different depths, expected: depth-0 ranked first.

Pitfalls

Misreading the CVSS v3.1 Scope (S:C vs S:U) inverts the Impact sub-score formula — manifestation: changed-scope vectors produce scores lower than expected; root cause: applying the unchanged-scope formula uniformly; debug: recompute by hand against the FIRST.org worked examples; signal: golden-fixture mismatch in cvss_vector_critical.json's sibling changed-scope fixture; recovery: branch the formula on Scope per section 4 of the CVSS v3.1 Specification.

⬜ Phase 3 — Sandbox & Validator §15

Objectives

Implement internal/sandbox: spawn a gVisor-backed OCI container per validation, apply a PatchSet to a disposable checkout, run the repo's declared test command, and enforce the CPU/memory/wall-clock ceilings from §4 (P4, I1, I7).

Deliverable

A sandbox-runner binary accepting a (repo SHA, PatchSet) pair and returning a ValidationRun with Result in {Passed, Failed, Timeout, SandboxError}.

Acceptance

A known-good PatchSet against fixture repo conformance/replay/fixture-repo-a validates Passed in under 5 minutes; a PatchSet that breaks a test validates Failed with the failing test name captured in Logs; a container exceeding 4 GiB memory is OOM-killed and recorded Timeout/SandboxError, never silently hangs past the 20-minute ceiling (§4).

Fixtures

conformance/replay/fixture-repo-a — a minimal npm repo with a deterministic test suite, used for Passed/Failed fixtures. conformance/replay/flaky_suite_repo — a repo with one intentionally flaky test (10% failure rate), used to exercise flaky-test detection in §15.6. conformance/replay/secret_leak_probe — a container image that attempts to read AWS_SECRET_ACCESS_KEY from its environment, expected: env is empty (I4 regression guard).

Pitfalls

Flaky tests defeating validation — manifestation: an otherwise-correct FixPlan is marked Failed nonstop due to a pre-existing flaky test unrelated to the bump; root cause: the test suite is the only oracle available (Weimer et al. 2009's fitness-function framing), so its flakiness becomes Drift's false-positive rate; debug method: re-run the identical PatchSet N times and compare pass-rate against a baseline run of the unpatched SHA; signal: sandbox.validation.flaky_suspect_total; recovery: quarantine the specific test name in repo policy config (ADR-21), not the whole suite.

Bumps that compile but break at runtime — manifestation: npm install and a type-check pass, but an integration test exercising the bumped package's changed runtime behavior fails; root cause: semver-compatible does not guarantee behavior-compatible (SemVer 2.0.0 only promises no intentional breaking API change); debug: diff the failing test's stack trace against the bumped package's changelog; signal: sandbox.validation.result{result="Failed"} correlated with a runtime (not build-time) failure; recovery: no automatic recovery — routed to Abandoned(ValidationFailed), left for source-level patch (Phase 7) or manual review.

Advisory range mis-parsing causing the wrong PatchSet to be validated — manifestation: validation passes but the applied bump does not actually satisfy the advisory's fixed-in range; root cause: an off-by-one in half-open vs closed-range interpretation of OSV events; debug: recheck ConstraintCheck proof against the raw OSV events array; signal: none from the sandbox itself (it only sees the PatchSet) — caught by planner-level fixture, not here; recovery: fixed in §16 (Phase 4), not §15.

Sandbox spawn latency spikes under concurrent load — manifestation: p95 exceeds the 2.5s target in §4; root cause: gVisor's user-space kernel init cost is per-container, not shared; debug: profile runsc startup trace; signal: sandbox.spawn.latency_ms histogram; recovery: pre-warm a pool of idle sandboxes (Phase 10 concern, deferred: PhaseDeferred("Phase 10 — Fleet Scale-Out & Rate-Limit Governor")).

⬜ Phase 4 — Fix Planner (Version Bump) §16

Objectives

Implement internal/planner: given a prioritized Advisory and DependencyGraph, compute the minimal semver-compatible bump satisfying the advisory's fixed-in range, emitting a versioned, replayable FixPlan per P5/I2.

Deliverable

A planner library producing a FixPlan for any (Advisory, DependencyGraph) pair, with driftctl plan show <advisory-id> printing the derivation.

Acceptance

For GHSA-example-1234 (left-pad <1.3.0 fixed 1.3.0) against a graph resolving left-pad@1.2.0, the planner emits FixPlan{from:1.2.0, to:1.3.0} in under 50ms; replaying the same inputs at the same planner_version twice yields byte-identical FixPlan serialization (I2); an advisory with no satisfying version in the repo's declared range yields NoFixAvailable, never a partial or best-effort bump.

Fixtures

conformance/planner/minimal_bump.json — golden FixPlan for the left-pad case above. conformance/planner/no_fix_available.json — an advisory whose fixed-in version violates the repo's own major-version pin, expected: NoFixAvailable. conformance/replay/planner_replay_001.json — same (advisory, graph, planner version) run twice, expected: identical output hash (I2 regression guard).

Pitfalls

Advisory range mis-parsing: OSV events arrays can express multiple disjoint affected ranges (e.g. introduced 1.0.0, fixed 1.2.0, introduced 1.5.0, fixed 1.5.3) — manifestation: the planner picks a bump that satisfies only the first range, still landing in the second affected range; root cause: treating events as a single (introduced, fixed) pair instead of an ordered event sequence; debug: replay conformance/planner/multi_range_advisory.json; signal: golden-fixture mismatch; recovery: fully implement the OSV event-sequence walk per section 4 of the OSV schema.

Transitive-only vulnerabilities with no direct override path — manifestation: the affected package is a transitive dependency of a dependency the repo does not directly declare, and no to_version of the direct dependency exists that resolves to a fixed transitive version; root cause: semver bump of a leaf node is not always achievable by bumping only that node — the parent may need to bump too; debug: walk DependencyNode.Parents from the affected node to find the nearest bumpable ancestor; signal: planner.transitive_unfixable_total; recovery: NoFixAvailable with a blocked_by field naming the parent, or attempt a parent-level bump if the parent's own requested_range allows it.

Monorepo lockfile churn: bumping one package in a workspace lockfile can shift unrelated resolved versions elsewhere in the same lockfile (npm's deduplication algorithm) — manifestation: the resulting diff touches far more lines than the single intended bump, obscuring review; root cause: lockfile resolution is holistic, not per-package; debug: diff ManifestDeltas against the raw unified diff line count; signal: planner.diff.unexpected_delta_count; recovery: document in the PR body summary which deltas are direct vs incidental resolution noise.

⬜ Phase 5 — Justification Generator & Signing §17

Objectives

Implement internal/justify: assemble a canonical Justification document binding advisory ID, repo SHA, patch diff hash, and ValidationRun ID, sign it via Sigstore keyless signing (ADR-10), and persist the attestation per P3/I6.

Deliverable

A justifier binary producing a signed Justification for any (FixPlan, PatchSet, ValidationRun) triple where the run Result is Passed, plus a standalone driftctl verify CLI usable by a reviewer offline.

Acceptance

Signing a Justification for the worked example in §8 completes in under 2s; driftctl verify on a tampered PatchSet (single byte changed) fails closed with a clear "diff hash mismatch" error, never a silent pass; justification.verify. failure_total is 0 across the full conformance suite on unmodified fixtures.

Fixtures

conformance/justify/golden_justification.json — signed Justification for the §8 worked example, expected: verifies clean. conformance/justify/tampered_diff.json — identical Justification but with patch_diff_hash mutated, expected: verify fails with HashMismatch. conformance/justify/expired_cert.json — a signature using an expired Fulcio certificate, expected: verify fails with CertificateExpired, not a crash.

Pitfalls

Signing before the ValidationRun is fully sealed — manifestation: a Justification references a ValidationRunID whose Result later changes (e.g. a race where EndedAt is set after signing begins); root cause: missing a hard barrier between "ValidationRun sealed" and "justification signing starts"; debug: check EventRecord ordering for the affected run; signal: justify.race.unsealed_run_total (must stay 0); recovery: add a database-level check constraint that a ValidationRun must be terminal before any Justification referencing it can be inserted.

PR spam from re-signing on every planner rebuild — manifestation: a minor, behavior-neutral planner release (e.g. a logging change) bumps planner_version and causes every pending FixPlan to be re-justified and re-proposed, flooding reviewers; root cause: planner_version conflated build metadata with semantic planning-behavior changes; debug: diff the two planner versions' ConstraintCheck outputs on a fixed input set; signal: pr.reopen_rate spike correlated with a deploy; recovery: version the planner's semantic behavior separately from its build identifier, only re-justify on a semantic-version bump.

⬜ Phase 6 — Forge / PR Emitter §18

Objectives

Implement internal/forge and cmd/pr-emitter: translate an accepted FixPlan plus its Justification into a PullRequestDraft, open it idempotently via the GitHub App forge adapter (ADR-12), and enforce the PR-per-advisory strategy (ADR-13).

Deliverable

A pr-emitter binary that, given a Proposed-eligible FixPlan, opens exactly one GitHub PR carrying the rendered body and the attached Justification.

Acceptance

Emitting a PR for the §8 worked example produces a PR titled "Bump left-pad to 1.3.0 (fixes GHSA-example-1234)" with the Justification attached; re-invoking emission for the same (repo, SHA, advisory ID) with an already-open PR performs zero additional forge API calls beyond the idempotency check (§4's forge-quota budget); pr.missing_justification_total remains 0 across the conformance suite.

Fixtures

conformance/forge/golden_pr_draft.json — expected PullRequestDraft for the §8 example. conformance/forge/idempotent_reopen.json — second emission attempt for an already-open PR, expected: FindExistingPR short-circuits, zero new API calls. conformance/forge/missing_justification.json — a FixPlan handed to the emitter without an attached Justification, expected: emission blocked, pr.missing_ justification_total incremented.

Pitfalls

PR spam from ungrouped advisories on the same package — manifestation: five advisories against the same transitive package in one week each open a separate PR, overwhelming the reviewer (the Renovate lesson: config-driven grouping exists precisely to prevent this); root cause: ADR-13's per-advisory PR strategy, deliberately chosen for justification traceability (I9), has this as a known tradeoff; debug: count open PRs per (repo, package) over a rolling week; signal: pr.open_count{repo} exceeding the §4 governor default (10/day); recovery: apply the governor (Phase 10) to throttle, or adopt a grouped-update policy override (ADR-13's rejected-alternative regime) if the team prefers it.

Branch name collisions across re-processed advisories — manifestation: a ReprocessRequested event (P6) regenerates a FixPlan whose deterministic HeadBranch collides with a stale, already-merged-or-closed branch from a prior attempt; root cause: branch naming used only (advisory ID, repo SHA) without a processing-attempt discriminator; debug: check for an existing branch ref before push; signal: forge.branch.collision_total; recovery: include a monotonic reprocess counter in the branch name derivation.

⬜ Phase 7 — Source-Level Patching & Backports §19

Objectives

Extend internal/patch beyond version bumps: synthesize a source-level patch (SourcePatch strategy) or a backported fix (Backport strategy) when no semver-compatible bump satisfies an advisory (the NoFixAvailable escape hatch from §16), using pattern-mined fix templates (Getafix, Bader et al. 2019).

Deliverable

A patch library extension producing a SourcePatch- or Backport-strategy PatchSet for advisories that fail the Phase-4 semver-bump path, still validated through the unchanged §15 sandbox.

Acceptance

For a fixture advisory with no satisfying semver bump but a known Getafix-style template match, the planner emits a SourcePatch FixPlan that validates Passed; an advisory with no template match and no cherry-pickable commit reference correctly falls through to NoFixAvailable, never a fabricated patch.

Fixtures

conformance/patch/template_match_redos.json — a ReDoS advisory with a known bound-insertion template, expected: SourcePatch FixPlan, sandbox Passed. conformance/patch/backport_cherry_pick.json — an advisory with a GitHub commit reference and a pinned older major version, expected: Backport FixPlan applying cleanly. conformance/patch/no_template_no_commit.json — expected: NoFixAvailable, no fabricated patch.

Pitfalls

Template over-application — manifestation: a template matches syntactically but changes program semantics in a way the test suite does not cover, producing a Passed validation that is not actually safe; root cause: templates are pattern matches, not proofs (the exact caveat Monperrus 2018 raises about generate-and- validate repair); debug: manual review flagged explicitly in the PR body when Strategy != SemverBump (never silently treated like a bump); signal: none automatic — mitigated by policy requiring human review weight on non-bump PRs; recovery: drift.yml can disable SourcePatch/Backport strategies entirely, falling back to NoFixAvailable.

Cherry-pick conflicts on a heavily-forked pinned version — manifestation: the upstream fix commit does not apply cleanly due to unrelated drift between the pinned version and the fix's origin commit; root cause: backport assumes minimal divergence; debug: git apply --check failure output; signal: patch.backport.conflict_total; recovery: fall through to NoFixAvailable rather than attempting a fuzzy/partial apply.

⬜ Phase 8 — Multi-Language Support §20

Objectives

Generalize internal/advisory, internal/graph, and internal/sandbox beyond npm to at least one additional ecosystem (Python/pip), per ADR-22's rollout order, without breaking existing npm conformance fixtures.

Deliverable

A graph/planner/sandbox extension supporting pip-ecosystem repos end-to-end, with all existing npm conformance fixtures still passing unmodified.

Acceptance

A pip fixture repo with a known-vulnerable requests pin validates an end-to-end fix (Detected → Proposed) in under the §4 fix-attempt p95 budget; PEP 440 pre-release version ordering (1.0.0a1 < 1.0.0) is resolved correctly per a golden fixture; zero regressions in conformance/manifests/lockfile_v3_valid.json (npm) after the plugin-seam refactor.

Fixtures

conformance/manifests/pip_requirements_valid.txt — golden dependency list for a pip fixture repo. conformance/planner/pep440_prerelease_ordering.json — version ordering edge case, expected: correct PEP 440 precedence. conformance/manifests/ malformed_requirements.txt — a requirements file with an unparseable version specifier, expected: MalformedManifest, mirroring the npm behavior in §13.

Pitfalls

Silently reusing SemVer 2.0.0 comparison logic for PEP 440 versions — manifestation: a valid PEP 440 pre-release bump is rejected as "not satisfying" when it actually does; root cause: the EcosystemPlugin seam was added but the planner's constraint solver was not parameterized by version scheme; debug: unit-test the comparator against the PEP 440 spec's worked ordering examples; signal: golden-fixture mismatch on pep440_prerelease_ordering.json; recovery: inject VersionScheme as an explicit planner dependency, never a global default.

Test-command heuristic inference guessing wrong on ambiguous repos (both a Makefile and a tox.ini present) — manifestation: the wrong test command runs, producing a misleading Passed/Failed result unrelated to the actual bump; root cause: heuristic priority order undocumented and inconsistently applied; debug: compare sandbox.test_command_source telemetry tag (declared vs inferred) against repo contents; signal: sandbox.test_command.ambiguous_total; recovery: require an explicit drift.yml override whenever more than one candidate test command is detected, never guess silently.

⬜ Phase 9 — Call-Graph Reachability Context §21

Objectives

Extend internal/risk with static call-graph reachability analysis: determine whether the affected function in a vulnerable package is actually reachable from the repo's own entrypoints, refining RiskScore (ADR-14) without changing the fix strategy itself (§2's mastery bullet).

Deliverable

A risk library extension setting RiskScore.Reachable for advisories where symbol-level data is available, with the fix queue re-ordered accordingly.

Acceptance

A fixture advisory against a package imported but never called from the repo's entrypoints is deprioritized below an otherwise-lower-CVSS but reachable advisory; RiskScore.Reachable remains nil (not false) when symbol-level advisory data is absent, distinguishing "known unreachable" from "unknown."

Fixtures

conformance/risk/reachable_direct_call.json — vulnerable symbol directly called, expected: Reachable: true, no priority discount. conformance/risk/unreachable_ imported_only.json — package imported, symbol never invoked, expected: Reachable: false, priority discounted per the documented weighting. conformance/risk/unknown_reachability.json — no symbol-level advisory data, expected: Reachable: nil, unchanged Phase-2 behavior.

Pitfalls

Reflection or dynamic dispatch defeating static reachability analysis — manifestation: a symbol invoked only via require(variableName) or reflection is marked unreachable when it is actually called at runtime; root cause: static call graphs are inherently incomplete under dynamic language features; debug: compare against a runtime coverage trace from the sandbox's test run (if available); signal: no automatic signal — this is a known soundness gap, documented, not silently assumed complete; recovery: Reachable: false from static analysis alone must only discount priority, never suppress the advisory from the queue entirely (I-level guarantee: no advisory is dropped based on reachability alone).

Over-trusting nil as false in downstream consumers — manifestation: a dashboard or the fix queue's sort comparator treats nil and false identically, silently deprioritizing advisories Drift has no actual reachability opinion on; root cause: *bool was introduced but consumers were not audited for the three-state distinction; debug: grep all Reachable reads for direct boolean coercion; signal: risk.reachability.nil_coerced_total; recovery: require explicit three-way handling (true/false/nil) at every consumption site, enforced by a lint rule.

⬜ Phase 10 — Fleet Scale-Out & Rate-Limit Governor §22

Objectives

Scale Drift from single-repo (Phase 0–9) to a multi-repo fleet (up to 500 repos, §4) via Kubernetes Job scheduling (ADR-04), introducing a rate-limit governor enforcing per-repo and fleet-wide forge-quota and PR-volume ceilings (§4).

Deliverable

A governor component and Kubernetes Job-based sandbox-runner deployment supporting 500 concurrently tracked repos within the §4 concurrency and FD budgets.

Acceptance

Under a simulated fleet-wide advisory burst (5,000/hour, §4), no single repo exceeds its 10 PRs/day governor ceiling; fleet-wide GitHub API quota consumption stays within documented limits with zero 403 rate-limit responses in the conformance load test; a single repo's sandbox Job failure does not affect other repos' concurrent Jobs.

Fixtures

conformance/governor/burst_500_repos.json — simulated fleet-wide burst, expected: per-repo PR ceiling respected, no forge 403s. conformance/governor/ single_repo_starvation.json — one repo with an unusually high advisory volume, expected: governor throttles that repo without starving others (fair-share token bucket).

Pitfalls

A single noisy repo consuming the entire fleet-wide forge quota — manifestation: other repos' PRs stall while one repo's advisories dominate API calls; root cause: token-bucket keyed only per-repo without a fleet-wide fair-share ceiling; debug: compare per-repo forge-call telemetry against the fleet total; signal: governor. fairness.starvation_detected_total; recovery: add a fleet-wide secondary bucket enforcing max-share-per-repo independent of the per-repo bucket.

Kubernetes Job scheduling latency defeating the sandbox-spawn-latency target (§4: 2.5s p95) — manifestation: Job pod scheduling adds seconds of overhead beyond gVisor's own container-init cost; root cause: no pre-warmed node pool or Job template caching; debug: compare sandbox.spawn.latency_ms before/after the Kubernetes migration; signal: latency regression in the same histogram used in §15; recovery: maintain a warm pool of pre-scheduled idle pods (referenced as the deferred mitigation in §15.6).

⬜ Phase 11 — Conformance & Performance Hardening §23

Objectives

Consolidate the full conformance fixture suite across all prior phases into a single release gate, and drive every §4 quantified target to a measured, load- tested pass under the §16.2 harness methodology (Performance Engineering).

Deliverable

A green run of the full conformance suite plus a benchmarks report demonstrating every §4 target met at the documented percentile, published to docs/ performance/.

Acceptance

100% of conformance fixtures pass; fix-attempt latency p50/p95/p99 measured at or better than 8/25/45 minutes (§4) under the burst load profile; zero fuzz-found crashes remain unfixed at release tag time; make conformance and make bench both exit 0 in CI.

Fixtures

conformance/regression/ — one fixture per historically-fixed bug across Phase 0–10, named by issue reference. conformance/fuzz-regressions/ — minimized crash-inducing inputs promoted from fuzz/ runs. conformance/replay/full_suite_ smoke.json — end-to-end smoke fixture exercising Detected → Merged across all phases in one run.

Pitfalls

Conformance suite growing slow enough to itself violate CI time budgets — manifestation: make conformance exceeds a reasonable CI wall-clock ceiling as fixtures accumulate across 11 phases; root cause: fixtures run serially by default; debug: profile make conformance wall time per fixture directory; signal: CI job duration trend; recovery: parallelize fixture execution by phase directory, keeping the aggregate gate but not the aggregate latency.

Load-test results not reflecting production topology (e.g. benchmarking on a single powerful machine when production runs Kubernetes Jobs, §22) — manifestation: measured latencies look better in benchmarks than in the field; root cause: benchmarks/ harness predates the Phase-10 Kubernetes migration and was never updated; debug: compare sandbox.spawn.latency_ms distributions, benchmark vs production telemetry; signal: divergence between the two histograms; recovery: re-run benchmarks/ against a Kubernetes-Job-backed environment matching production, not a bare-metal stand-in.
