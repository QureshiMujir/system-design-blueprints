219 — DDoS Mitigation System

Project Number: 219

Project Name: DDoS Mitigation System

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a from-scratch, multi-layer distributed DDoS mitigation platform in Rust that filters L3/L4 volumetric attacks (SYN floods, UDP/amplification floods, reflection) at line rate, tracks flow state, detects anomalous traffic statistically (baselining, entropy analysis, rate-of-change, heavy-hitter sketches), defends the TCP handshake with SYN cookies and challenge-response, defends the application layer against HTTP floods and slow-loris with fingerprinting and JS/proof-of-work challenges, rate-limits per source/prefix with token buckets, and diverts traffic to a scrubbing center over BGP/anycast when inline capacity is exceeded. The central engineering problem is not "can we drop packets" — it is classifying legitimate traffic from attack traffic at line rate under an adversary actively shaping traffic to evade the classifier, where a false positive is a self-inflicted outage on real users. Every subsystem is designed around that constraint: the fast path is O(1) per packet and never blocks on the slow path; detection is statistical, not signature-based, because the attacker is adaptive.

Phase-0 deliverable (crates):

  1. pktparse — zero-copy Ethernet/IPv4/IPv6/TCP/UDP header parser, attacker-controlled-input hardened.
  2. xdp-hook — XDP program loader/attacher and the eBPF fast-path filter program (verifier-safe).
  3. flowtrack — bounded flow table (five-tuple keyed), eviction policy, SYN-state machine.
  4. synguard — SYN-cookie construction/validation (Bernstein cookies).
  5. detect-baseline — rolling baseline and threshold detector.
  6. detect-entropy — Shannon-entropy anomaly estimator over source-IP/port distributions.
  7. detect-sketch — count-min sketch heavy-hitter/elephant-flow detector (Cormode & Muthukrishnan 2005; Estan & Varghese 2002).
  8. ratelimit — per-source/prefix/ASN token-bucket rate limiter.
  9. l7defend — HTTP request inspection, fingerprinting, JS-challenge and proof-of-work issuance/verification.
  10. reputation — allowlist/blocklist and decaying reputation store.
  11. diversion — BGP-announcement and anycast diversion controller, GRE back-haul tunnel manager.
  12. telemetry — sFlow/IPFIX-class sampling export and structured event pipeline.
  13. mitigation-fsm — the Baseline→Detecting→Mitigating→De-escalating→Clear state machine and control API.
  14. xdp-runtime — orchestrates 2–8 as a single line-rate binary; the only crate compiled into the kernel-adjacent hot path.

Boundaries:

  • Provides: L3/L4 volumetric filtering, flow tracking, statistical detection, SYN-flood defense, L7 flood/challenge defense, rate limiting, reputation, scrubbing-center diversion, traffic-engineering shed.
  • Delegates: upstream BGP announcement propagation to the network's routers/route-reflectors (this system emits the announcement intent, not the routing fabric); origin-side TLS termination and application logic to the protected service; source-side spoofing prevention to ingress-filtering routers (BCP 38/BCP 84 — this system can only detect, not fix, spoofing at the source).
  • Does NOT provide: application content serving (not a CDN), full WAF rule-engine semantics (no generic request-body rule DSL, no OWASP-CRS-class ruleset), general-purpose reverse-proxying, or a routing control plane of its own.

Non-goals, named against siblings:

  • Not API-Gateway-165: that project owns per-route auth, transformation, and API-lifecycle concerns; this project only asks "is this packet/request part of an attack," never "is this request authorized for this route."
  • Not Rate-Limiter-39: that project is a general-purpose reusable rate-limiting library/service for any caller; this project's rate limiter is a narrow, line-rate-bound, attack-mitigation-specific instance with prefix/ASN granularity and reputation coupling — it is not meant to be embedded as a generic dependency.
  • Not NAT-Firewall-158: that project owns stateful connection tracking for policy/NAT purposes; this project's flow table exists only to support attack detection, not general firewalling.
  • Not a WAF's full rule engine: no signature/rule DSL for injection/XSS-class payloads.
  • Not a CDN: no content caching, no origin shielding beyond scrubbing.

Deployment model — two supported topologies, selected per ADR-11:

  • Inline always-on: the XDP hook sits on every ingress NIC path at the edge, all traffic passes through the fast path continuously (Cloudflare's model); adds path latency to 100% of traffic but has zero activation delay.
  • On-demand scrubbing-center diversion: traffic is normally routed directly to origin; on attack detection, a BGP announcement pulls traffic through a smaller number of scrubbing-center anycast sites, cleaned traffic is GRE-tunneled back to origin (the traditional Arbor/Prolexic model); adds zero latency at baseline but has a diversion-convergence delay (§4, §34) during which the attack is only partially mitigated.
  • Both are implemented; the choice between them is a deployment-time policy, not a code fork.

Users/operators: infrastructure/hosting providers, ISP-scale network operators, platform SRE teams running their own edge, and security operators tuning mitigation policy through the control API.

What later phases unlock:

  • Phase 4–6 unlock automated detection (no more manual threshold-setting).
  • Phase 8 unlocks self-defense against application-layer floods.
  • Phase 10 unlocks capacity beyond a single site's line rate via scrubbing-center diversion.
  • Phase 11 unlocks confidence that the system holds under an adversary actively trying to defeat it.

Rust + rationale:

  • Predictable ownership eliminates a whole class of memory-safety bugs in a component that parses fully attacker-controlled bytes at line rate.
  • No GC pause is acceptable on the fast path.
  • Strong FFI to eBPF/XDP C-ABI tooling (libbpf) and to DPDK's C API when the DPDK backend is selected (ADR-02).
  • A type system that can encode "this value came from the network and is unvalidated" as a distinct type from "this value is validated," catching a class of parser bugs at compile time.

Rejected languages:

  • C/C++: memory-unsafe in a parser that must survive adversarial fuzzing — this is exactly the class of bug DDoS-adjacent CVEs come from.
  • Go: GC pause and goroutine-scheduler jitter are incompatible with the per-packet nanosecond budget in §4.
  • Python: throughput floor, unusable for the fast path; acceptable nowhere in this system.

The XDP/eBPF hot path itself (the actual dropping decision on the highest-volume traffic) runs as a restricted eBPF bytecode program (Høiland-Jørgensen et al., CoNEXT 2018), not as ordinary Rust — Rust owns the loader, the control plane, the detection engine, and the L7 path; the eBPF verifier owns correctness of the innermost drop loop.

Prerequisites:

  • TCP/IP and the SYN handshake state machine.
  • Packet parsing under adversarial input.
  • Basic queueing theory and token-bucket math.
  • Shannon entropy and probabilistic counting (count-min sketch).
  • BGP path-attribute basics and anycast routing.
  • Linux kernel networking (NAPI, softirq, XDP hook points).

Timeline:

  • Phase 0 (skeleton + parser + XDP hook + CI): 3–4 weeks.
  • Phases 1–7 (flow tracking through heavy-hitter detection): 4–6 months.
  • Phases 8–10 (L7 defense, reputation, scrubbing diversion): 3–5 months.
  • Phase 11 (adaptive red-team hardening): 2–3 months ongoing.

Deferrals (see §37 for the full register):

  • PhaseDeferred("Phase 11 adaptive-attacker suite") for ML-based classification as a detector upgrade path (§36 names it as an alternative architecture, not adopted here).
  • PhaseDeferred("Phase 10 scrubbing diversion") for multi-cloud/multi-anycast-site federation beyond a single scrubbing provider.
  • PhaseDeferred("Phase 8 L7 defense") for CAPTCHA-class challenges (JS-challenge and PoW are the Phase-8 scope; CAPTCHA is deferred as a fallback tier).
  • PhaseDeferred("Phase 3 SYN-cookie defense") for QUIC/UDP-based handshake-flood defense (this blueprint's SYN-cookie scope is TCP only).

Ingress tap / XDP hook: attaches to the NIC receive path before the kernel allocates an sk_buff; runs a verifier-checked eBPF program that makes the drop/pass/redirect decision for the overwhelming majority of packets without leaving kernel space (I1). L3/L4 filter: applies static ACLs, BCP 38 ingress-spoofing checks, and protocol-sanity rejection (malformed headers) before any stateful work happens. Flow tracker: a bounded five-tuple-keyed table recording per-flow counters and TCP state, sharded to avoid cross-CPU contention; existence is required for every other stateful subsystem. SYN-cookie/challenge module: answers the handshake without allocating flow state until a cookie validates (I3), eliminating SYN-flood state exhaustion. Detection engine: three cooperating estimators — a rolling baseliner (threshold on deviation), a Shannon-entropy estimator over source distributions (catches distributional attacks a rate threshold misses), and a count-min sketch for heavy-hitter/elephant-flow detection at fixed memory. Rate limiter: per-source/prefix/ASN token buckets, invoked only after a flow is not already provably legitimate (I2). Reputation/allowlist store: decaying score keyed by source, consulted by every other subsystem to short-circuit repeat offenders and never-block-again legitimate sources. L7 defense: HTTP-level inspection, request fingerprinting, and challenge issuance (JS challenge or proof-of-work) for flows that pass L3/L4 but look like an application-layer flood. Diversion controller: on sustained overload, announces the protected prefix via BGP to pull traffic into a scrubbing center over anycast, and GRE-tunnels cleaned traffic back to origin. Traffic-engineering/shedder: the last-resort load-shedding decision when even scrubbing capacity is at risk of saturation. Telemetry pipeline: samples and exports metadata (sFlow/IPFIX-class) for every verdict, feeding both dashboards and the baseliner's training data — never gates the fast path (I6).

6. Design Principles

  • P1 — the fast path drops in the kernel at line rate and never allocates on the hot path; a mitigation that cannot keep up with the attack's packet rate is not a mitigation (XDP; Høiland-Jørgensen et al.).
  • P2 — the goal is to drop attack traffic while passing legitimate traffic, so the false-positive rate is the primary quality metric; over-blocking is a self-inflicted outage.
  • P3 — detection is statistical and adversarial; the attacker adapts, so baselines and challenges must assume the traffic mix is deliberately shaped to fool them.
  • P4 — no per-packet state is allocated before cryptographic proof of a legitimate handshake exists (SYN cookies; I3).
  • P5 — every mitigation rule has a bounded lifetime; a transient attack must never produce a permanent block.
  • P6 — the fast path and the detection/control path are separated by a verdict boundary; the control path can be arbitrarily slow without threatening line rate.
  • P7 — a defense's cost to the attacker must exceed the attacker's cost to attack, or the defense is not economically viable (proof-of-work; DDoS is fundamentally an economics problem).
  • P8 — every classification decision is backed by evidence that is logged, so a false positive is diagnosable after the fact, not just observable.
  • P9 — bounded memory always; every data structure (flow table, sketch, reputation store) has a fixed ceiling and a documented eviction/decay policy, because unbounded state is itself a DoS vector.
  • P10 — a legitimate flow that has passed a challenge is never re-blocked by a later volumetric rule targeting the same source (I2).
  • P11 — the system degrades gracefully under load beyond its own capacity (shed load deterministically) rather than failing catastrophically.
  • P12 — detection algorithms are chosen for O(1) or O(log n) per-packet cost; anything requiring per-packet global state does not belong on the fast path.
  • P13 — ingress-filtering assumptions (BCP 38) are treated as probabilistic, not guaranteed; the system must still function when spoofing is present.
  • P14 — every challenge (JS or PoW) is single-use and bound to a specific nonce/seed; a defense that can be answered once and replayed indefinitely is not a defense.

8. Domain Model

Attack Taxonomy (Mirkovic & Reiher 2004)

Class Mechanism Signature Defense
Volumetric raw packet/byte-rate flood (UDP flood, ICMP flood) sustained rate >> baseline, low protocol diversity rate limiting, XDP drop, scrubbing diversion
Protocol exploits a protocol state machine (SYN flood, ACK flood, fragment flood) half-open-connection spike, malformed protocol fields SYN cookies, protocol-sanity filtering

SYN-Flood / SYN-Cookie Mechanism (Bernstein; RFC 4987)

Steps: (1) client sends SYN; (2) server does not allocate connection state; (3) server computes cookie C as a MAC over the connection tuple and a coarse timestamp, encodes it in the SYN-ACK sequence number; (4) server discards all per-connection memory; (5) if client's ACK returns with the correct derived sequence number, the server reconstructs connection state from the tuple alone — no state existed between steps 2 and 5.

Cookie construction (display equation):

cookie = ( MAC_k(src_ip, dst_ip, src_port, dst_port, t_coarse) mod 2^24 ) || t_coarse(5 bits) || mss_encoding(3 bits)

where k is a secret rotated key and t_coarse is a low-resolution timestamp bounding cookie replay validity (I3).

Cookie replay window bound: an attacker capturing a single valid client ACK can replay it only within t_coarse's validity window (typically low tens of seconds), and only against the exact tuple the MAC was computed over — the replay produces at most one spurious FlowState reconstruction per capture, not a flood, because the MAC does not generalize across tuples (Phase 3, §15.6).

Backscatter inference: unsolicited response traffic arriving at a spoofed source address (the address the attacker forged, not the real attacker) is itself observable evidence of ongoing spoofed-source attack activity elsewhere on the Internet (Moore et al. 2006) — this system does not rely on backscatter for its own detection (it defends a specific protected prefix, not the whole Internet), but backscatter-informed threat intelligence about actively-abused reflector pools feeds the reputation store's protocol-level rate-cap tuning (Phase 2, Phase 9).

Detection Model

Baselining: rolling mean/variance of per-metric traffic (pps, bytes, SYN rate) over a trailing window; an alert fires when a metric exceeds mean + k·stddev for a sustained interval.

Entropy-based anomaly detection (Lakhina et al. 2005; Shannon entropy over the source-IP distribution):

H(X) = − Σ p(x_i) · log2(p(x_i))

Normal traffic: many distinct sources, each a small share ⇒ H near log2(N) (high entropy). Spoofed/botnet flood: either extreme concentration (few sources, low entropy) or extreme dispersion beyond legitimate client diversity (near-uniform spoofed sources, entropy spikes toward the address-space maximum) — the contrast that a raw rate threshold cannot see, because total rate can look identical to a flash crowd while the entropy signature differs.

Count-min-sketch heavy-hitter detection (Cormode & Muthukrishnan 2005) with error bound:

estimate(x) ≥ true_count(x), and P[ estimate(x) > true_count(x) + ε·N ] ≤ δ, for sketch width w = ⌈e/ε⌉ and depth d = ⌈ln(1/δ)⌉.

Rate-limiting / token-bucket math: bucket capacity B, refill rate r tokens/sec; a packet of cost c is admitted iff current tokens ≥ c, then tokens -= c; tokens accrue as min(B, tokens + r·Δt). Sustained admitted rate converges to r; burst tolerance is bounded by B.

L7 challenge model: JS challenge imposes negligible legitimate-client cost (sub-ms compute) but requires a JS-capable client, filtering non-browser bots cheaply. Proof-of-work imposes a deliberate cost asymmetry: difficulty d requires the client to find a nonce n such that hash(challenge || n) has d leading zero bits, expected client cost O(2^d) hash operations, server verify cost O(1) — the cost-asymmetry argument (§34) is that raising d costs the server nothing but costs every concurrent attacking client 2^d work, making distributed floods economically unattractive relative to legitimate single-request traffic.

Attack/Failure Examples

  • Spoofed-source flood: random source IPs, no BCP 38 upstream — defended by SYN cookies (protocol) + rate caps (volumetric), not by per-source reputation (sources are not repeated).
  • Low-and-slow L7 attack: sub-baseline packet rate, high connection-hold time — invisible to volumetric detectors, caught by L7 connection-duration fingerprinting (Phase 8).
  • Legitimate flash crowd mistaken for attack: high rate, high entropy, valid cookies — classification table above must weight entropy over raw rate to avoid the false positive.
  • Adaptive attacker probing the threshold: attacker ramps rate just under the baseliner's alert bound — defended by the entropy detector and the sketch, which respond to distributional shape, not just rate.
  • Reflection attack: amplification factor exceeds link capacity even at moderate attacker upload — defended by protocol-specific rate caps keyed to the amplification table (§34).
  • Cache-busting HTTP flood: unique query strings defeat any caching layer, forcing full request processing — defended by fingerprinting request shape independent of the cache-busting parameter.
  • Failure path: diversion BGP withdrawal issued without traffic having actually normalized (I10 violated by a race) → traffic returns to direct path while attack is still active → detected by re-triggering the Detecting state within the hold-down window → recovery is re-announcement, not a new detection cycle.

  • CI green on all stub jobs; SBOM present in build artifacts.

12.6 Pitfalls

  • Verifier rejects a bounds check that is provably safe to a human but not to the verifier's linear scan — requires restructuring, not just annotation.
  • A parser that is memory-safe in Rust userspace can still be rejected in the eBPF verifier subset (no unbounded loops, no arbitrary pointer arithmetic) — the two safety models are not identical.
  • Jumbo frames exceeding the eBPF program's MTU assumption silently truncate rather than error.
  • A CI runner's kernel version silently lacking CO-RE support passes local verifier checks but fails to load on a production kernel with a different BTF layout — motivating the documented version floor in 12.2.
  • SBOM generation succeeding on a dirty (uncommitted-change) working tree produces a provenance record that does not match the actual released artifact — must be a CI-only step, never a local convenience command.

12.7 Performance Concerns

  • Any allocation inside the eBPF program is a hard verifier failure, not just a slowdown — must be checked at load time, not benchmark time.
  • Tail-call chains in eBPF have a bounded depth; excessive chaining silently fails at runtime.
  • Even at XDP_PASS-only (no filtering), a poorly bounds-checked parser adds measurable per-packet overhead that must be profiled now, before Phase 2 adds real filtering logic on top of it.

12.8 Edge Cases

  • IPv6 extension header chains of maximal length.
  • Zero-length UDP payloads.
  • Non-standard EtherType values (unrecognized, must pass through, not crash parser).
  • Double-tagged (QinQ) VLAN frames exceeding the parser's assumed single-tag depth.
  • Truncated captures ending mid-header, exercising the parser's bounds-check path rather than its happy path.

12.9 Failure Analysis

A verifier-rejected program fails closed (does not load) rather than loading with undefined behavior — Phase 0's CI gate exists specifically so this failure surfaces before merge, not at deploy time.

12.10 Operational Notes

Every later phase's crate depends on pktparse, common-types, and the xdp-hook attach lifecycle established here — treat this phase's fixtures as a permanent regression suite, never removed.

  • Eviction-storm cache-line bouncing when many flows expire simultaneously at a shared timer boundary.
  • NAT rebinding on the legitimate side causing a flow that "looks new" to be double-counted against a rate limit.
  • Reordered packets arriving before the SYN, causing the state validator to reject a legitimate flow as an illegal transition.
  • A shard-assignment function with a subtly non-uniform hash distribution concentrates load on a minority of shards under real (not just adversarial) traffic, defeating ADR-04's per-shard O(1) assumption without any attacker involved.

13.7 Performance Concerns

  • Cache-line layout of FlowState — packing counters to avoid false sharing across cores touching adjacent shards.
  • Eviction policy must not become O(n) under sustained overflow (batched, amortized eviction, not full-table scan).

13.8 Edge Cases

  • Simultaneous SYN from both ends (simultaneous open) — a legal but rare TCP transition.
  • A five-tuple reused immediately after a prior flow's TTL expiry (source port reuse under NAT).
  • A flow spanning a mid-session shard-count change (node scale-up/down) requiring rehash-safe migration rather than silent state loss.

13.9 Failure Analysis

Flow-table corruption manifests as either false-positive drops (state looks like an attack when it is not) or as failed detection (state looks clean when it is under attack) — detected via replay-divergence testing against a known-good capture (Phase 11 harness).

13.10 Operational Notes

Expose flow-table occupancy and per-shard eviction-rate as first-class dashboard metrics (§26) — an occupancy metric pinned near the ceiling is the earliest signal of either a real flow-table-exhaustion attack or an undersized table for legitimate load.

14. Phase 2 — L3/L4 Volumetric Filtering and BCP 38

14.1 Objectives

Implement static ACL/protocol-sanity filtering and spoofing-aware ingress checks in the fast path, ahead of any stateful detection.

14.2 Detailed Implementation Steps

  • Implement protocol-sanity rejection: malformed header lengths, impossible checksums, invalid flag combinations (RFC 793/768) — rejected before flow-table insertion (P1).
  • Implement static ACL matching (allow/deny by prefix) as the first fast-path stage.
  • Implement BCP 38/BCP 84-aware heuristics: flag traffic whose source prefix is not plausible for the ingress interface (RFC 2827, RFC 3704) — probabilistic, not absolute (ADR-17).
  • Implement fragment-handling per RFC 791/8200: reject overlapping fragments, bound fragment reassembly state.
  • Wire volumetric rate-cap rules per protocol into ratelimit (early integration ahead of full Phase 7 scope) to give amplification-protocol coverage a first foothold (Rossow 2014).
  • Populate attack-replay.yml with the first real PCAP fixtures (spoofed UDP flood, SYN flood without cookies yet active).
  • Implement bounded fragment-reassembly state sized and evicted using the same shard/eviction discipline as flowtrack (Phase 1), rather than a separate unbounded structure.
  • Add per-interface plausible-prefix tables (the BCP-38 heuristic's reference data) with a documented refresh cadence, since ingress topology changes over time.

14.3 Deliverable

A fast-path stage that rejects malformed/spoofed-implausible/ACL-denied traffic before any stateful subsystem sees it.

14.4 Acceptance Criteria

  • Sustains ≥ 10 Mpps/core drop throughput on malformed/ACL-denied traffic (§4).
  • Zero false-positive drops on the legitimate-traffic regression corpus (Phase 0 fixtures replayed).
  • Detects and caps at least the 5 amplification protocols in §34's table.

14.5 Conformance Fixtures

  • conformance/phase2/spoofed-udp-flood.pcap
  • conformance/phase2/overlapping-fragments.pcap
  • conformance/phase2/dns-amplification.pcap
  • conformance/phase2/legitimate-multihomed-asymmetric.pcap
  • conformance/phase2/ntp-memcached-amplification.pcap

14.6 Pitfalls

  • A legitimate multi-homed network's asymmetric routing triggers the BCP-38 heuristic as a false positive — this is exactly why ADR-17 makes the check probabilistic, not a hard uRPF reject.
  • Fragment reassembly state itself becomes a memory-exhaustion vector if unbounded (must be sized and evicted like the flow table).
  • An ACL rule ordering bug causes a broad allow to shadow a narrower deny (rule-shadowing, general policy-engine pitfall).
  • Per-protocol amplification rate caps set from published factors (§34) can still be evaded by an attacker chaining multiple under-the-cap protocols simultaneously against the same target — a documented residual gap closed only partially until Phase 6's heavy-hitter view aggregates across protocols.

14.7 Performance Concerns

  • Fragment reassembly adds per-packet state that competes with the flow table for the same memory budget.
  • ACL matching on large rule sets must stay O(log n) (trie-based, not linear scan) to preserve P12.

14.8 Edge Cases

  • IPv6 extension-header-based evasion of protocol-sanity checks.
  • Legitimate CDN/multi-homed sources with naturally asymmetric routing.
  • A fragment train arriving out of order, requiring reassembly-state matching independent of arrival sequence.

14.9 Failure Analysis

Over-aggressive BCP-38 heuristics are the primary false-positive risk introduced by this phase — contained by staged rollout (ADR-16) and by always weighting the heuristic as one signal among several (P2, P8), never a sole drop decision.

14.10 Operational Notes

Track false-positive-suspect drops (BCP-38 heuristic hits on traffic later reputation-confirmed legitimate) as a distinct metric from confirmed-attack drops — this is the earliest operational signal that the heuristic threshold needs tuning.

15. Phase 3 — SYN-Cookie Defense

15.1 Objectives

Implement synguard: stateless SYN-flood defense via cryptographic cookies, satisfying I3.

15.2 Detailed Implementation Steps

  • Implement the cookie MAC construction per §8's display equation, with key rotation on a fixed interval (bounding replay validity via t_coarse).
  • Implement SYN-ACK emission with the cookie encoded in the sequence number, with zero FlowState allocation at this step (I3, P4).
  • Implement ACK validation: recompute expected cookie from the returning tuple, accept only on exact match within the coarse-timestamp window.
  • On validated ACK, reconstruct FlowState and hand off to flowtrack (Phase 1) — this is the only path by which a TCP flow's state is created under active SYN-flood posture.
  • Add a policy toggle: cookies active only above a SYN-rate threshold (ADR-05 default), full syncache below it, to avoid unnecessary TCP-option loss (window scaling) during normal operation.
  • Add synguard-specific metrics: cookies issued/validated/rejected, feeding I3's detection column.
  • Implement a two-generation key-overlap window (current key + immediately prior key both accepted) to close the key-rotation-boundary rejection gap named in 15.6.
  • Add an MSS-encoding fallback path that preserves a coarse window-scale hint inside the cookie's spare bits, bounding (not eliminating) the TCP-option information loss named in 15.6.

15.3 Deliverable

A SYN-flood defense that issues and validates cookies at the target rate with zero pre-validation state allocation.

15.4 Acceptance Criteria

  • Sustains ≥ 5M SYN/s per core cookie issue+validate throughput (§4).
  • Zero FlowState entries created for unvalidated SYNs under a sustained flood fixture.
  • TCP options requiring syncache (e.g., full window scaling) degrade gracefully, not silently, when cookies are active.

15.5 Conformance Fixtures

  • conformance/phase3/syn-flood-5msyn.pcap
  • conformance/phase3/cookie-replay-attempt.pcap
  • conformance/phase3/legitimate-handshake-under-cookie-mode.pcap

15.6 Pitfalls

  • Key-rotation boundary: a legitimate ACK arriving just after rotation is rejected as invalid — requires a grace window overlapping two key generations.
  • MSS/window-scaling information loss under cookie mode causes legitimate high-BDP connections to under-perform, not fail — a latent legitimate-traffic quality regression, not a drop.
  • An attacker who captures a valid cookie exchange and replays the ACK within the coarse-timestamp window can force one spurious state reconstruction — bounded by I3 to a single flow-table entry, not a flood, because the MAC still binds to the original tuple.

15.7 Performance Concerns

  • MAC computation cost per SYN is the binding constraint on cookies/sec (§34) — algorithm choice (fast keyed hash, not a general-purpose MAC with heavier setup cost) matters.
  • Key rotation must not require a global lock across cores issuing cookies concurrently.

15.8 Edge Cases

  • SYN retransmission from a legitimate client whose first SYN's cookie validation raced a key rotation.
  • Simultaneous-open (both ends send SYN) under cookie mode.
  • A client that retries with a different source port after a lost SYN-ACK, producing a fresh cookie exchange rather than a retransmission match.

15.9 Failure Analysis

A cookie-validation bug that accepts forged ACKs reintroduces state-exhaustion risk silently — caught by the cookie-replay-attempt fixture asserting zero FlowState growth under replay.

15.10 Operational Notes

Cookies-issued vs cookies-validated ratio is the primary operational signal of an active SYN flood; a sustained high issue-rate with low validate-rate is the detection signal for the mitigation-fsm's Detecting state transition (§8).

16. Phase 4 — Baselining and the Threshold Detector

16.1 Objectives

Implement detect-baseline: a rolling-window statistical baseline and threshold detector feeding the mitigation-fsm's Baseline→Detecting transition.

16.2 Detailed Implementation Steps

  • Implement the rolling mean/variance estimator (Welford's online algorithm for numerical stability) over a trailing window per tracked metric (pps, bps, SYN rate) (P3, P12 — O(1) per update).
  • Implement the mean + k·stddev alert rule with a configurable k and a sustained-interval requirement (avoid single-sample noise triggering Detecting).
  • Wire alert output into mitigation-fsm's state-transition input (§8 state machine).
  • Add per-metric, per-prefix baselines (a global baseline alone cannot localize an attack to a specific prefix).
  • Implement baseline warm-up handling (cold-start: do not alert during the first window-fill interval).
  • Add baseline reset-on-legitimate-change hooks (e.g., operator-declared traffic-profile change) to prevent permanent false-positive drift after a real growth event.
  • Implement per-metric alert-confidence scoring (distinct from a bare boolean crossing) so downstream signal combination (Phase 5 onward) can weight a marginal crossing differently from a gross one.
  • Add a baseline-parameter versioning field (window size, k) so a later tuning change is auditable against the conformance fixture set that validated the prior parameters (§27).

16.3 Deliverable

An operational baseline detector that raises a Detecting-state transition within the target detection latency on the flash-crowd-vs-attack fixture set.

16.4 Acceptance Criteria

  • Detection latency ≤ 2 s from threshold-crossing onset (§4).
  • False-positive rate on flash-crowd fixture ≤ ceiling in §4 when combined with entropy signal (Phase 5) — pure-threshold-alone FP rate is documented separately and expected higher (motivating Phase 5).
  • Cold-start produces zero spurious alerts across a 10-minute warm-up fixture.

16.5 Conformance Fixtures

  • conformance/phase4/gradual-ramp-attack.pcap
  • conformance/phase4/flash-crowd-legitimate.pcap
  • conformance/phase4/baseline-cold-start.json
  • conformance/phase4/diurnal-burst-near-boundary.pcap

16.6 Pitfalls

  • Pure-threshold detection cannot distinguish a flash crowd from a volumetric attack when both present as a rate spike — this is the motivating gap Phase 5's entropy detector closes (§8 classification table), documented here as a known Phase-4-alone limitation, not a bug.
  • An adaptive attacker who ramps slowly enough to stay under k·stddev per window defeats pure-threshold detection — motivates Phase 6's sketch-based heavy-hitter signal as a complementary detector.
  • A baseline reset triggered by an in-progress attack (mistaken for a legitimate profile change) would raise the tolerated-rate ceiling mid-attack — reset must require operator confirmation, not be fully automatic.

16.7 Performance Concerns

  • Per-prefix baselining multiplies memory by tracked-prefix count — must stay bounded (fixed prefix-aggregation granularity, not per-/32).
  • Welford's algorithm avoids the numerical-stability issues of naive variance accumulation under sustained high-volume updates.

16.8 Edge Cases

  • A legitimate traffic source with naturally bursty diurnal pattern near the baseline's window boundary.
  • Multiple simultaneous prefix-level anomalies competing for mitigation-fsm attention.
  • A metric that oscillates just above and below the alert threshold repeatedly, requiring the sustained-interval requirement (16.2) to avoid alert flapping.

16.9 Failure Analysis

A baseline detector alone is insufficient (by design, per 16.6) — its failure mode of missing adaptive/distributional attacks is a known, accepted gap closed by Phases 5–6, not a defect requiring rework of this phase.

16.10 Operational Notes

Expose the raw metric, the rolling mean, and the current k·stddev bound on the same dashboard panel — an operator diagnosing a false positive needs to see how close normal traffic runs to the alert boundary.

17. Phase 5 — Entropy-Based Anomaly Detection

17.1 Objectives

Implement detect-entropy: Shannon-entropy estimation over source-IP/port distributions, closing the flash-crowd-vs-attack gap left by Phase 4 (Lakhina et al. 2005).

17.2 Detailed Implementation Steps

  • Implement the Shannon entropy computation per §8's display equation over a periodic-reset source-distribution counter (bounded memory, P9).
  • Implement the two-tailed anomaly rule: alert on entropy collapse (concentration — few sources dominate) and on entropy spike beyond legitimate-diversity range (near-uniform spoofed sources) (I6 — both directions logged with evidence).
  • Combine the entropy signal with the Phase-4 baseline signal in the classification table (§8) before raising Detecting-state confidence — no single signal alone crosses the confidence bound (P8).
  • Add source-port entropy alongside source-IP entropy (protocol-attack signature differs from volumetric-flood signature in which dimension collapses).
  • Tune the legitimate-diversity reference range against the flash-crowd fixture corpus (Phase 4's fixtures reused here as the entropy ground truth).
  • Implement overlapping-window smoothing (rather than a single hard periodic reset) to preserve cross-window attack-persistence signal at reset boundaries (closes 17.6's reset-boundary gap).
  • Add a NAT-heavy-traffic reference-range override, tunable per deployment, so carrier-grade-NAT-served legitimate traffic does not require reputation cross-check for every request (partial mitigation of 17.6's NAT false-positive risk).

17.3 Deliverable

An entropy detector that correctly distinguishes the flash-crowd fixture from the volumetric-attack fixture where Phase 4 alone could not.

17.4 Acceptance Criteria

  • Correctly classifies 100% of the flash-crowd-vs-attack fixture pairs (§16.5 reused) as distinct.
  • Entropy computation update cost stays within the near-fast-path batching budget (not full per-packet fast path — batched per collection interval).
  • Combined baseline+entropy false-positive rate meets the §4 ceiling.

17.5 Conformance Fixtures

  • conformance/phase5/entropy-collapse-syn-flood.pcap
  • conformance/phase5/entropy-spike-spoofed-flood.pcap
  • conformance/phase5/flash-crowd-high-entropy.pcap (reused from Phase 4)
  • conformance/phase5/carrier-nat-legitimate-low-entropy.pcap

17.6 Pitfalls

  • A botnet large enough to itself approximate legitimate source diversity partially defeats entropy collapse detection — this is the adaptive-attacker regime Phase 11's red-team suite specifically targets.
  • Periodic-reset counters lose cross-window attack persistence signal at the reset boundary — mitigated by overlapping-window smoothing, not a single hard reset.
  • NAT-heavy legitimate traffic (many users behind few source IPs) naturally has lower entropy than the reference range — a documented false-positive risk requiring reputation-signal cross-check (Phase 9) before hard action.

17.7 Performance Concerns

  • Entropy computation requires a log operation per distinct source per window — batched and bounded, never per-packet.
  • Distinct-source cardinality itself can grow large under a spoofed flood — the counter map needs its own bounded-memory eviction, independent of the flow table.

17.8 Edge Cases

  • Legitimate carrier-grade-NAT traffic with low natural source diversity.
  • IPv6 source-address diversity assumptions differing from IPv4 (much larger address space changes the "spike" reference range).
  • A legitimate multi-tenant SaaS platform whose aggregate source diversity looks like two overlapping populations (its own users plus its downstream customers' traffic).

17.9 Failure Analysis

An entropy false positive on NAT-heavy legitimate traffic is contained by never letting the entropy signal alone cross the Detecting→Mitigating confidence bound — it always combines with at least one other signal (P8), consistent with the classification table in §8.

17.10 Operational Notes

Dashboard the entropy time series alongside the raw rate time series on the same timeline — the visual signature of a flash crowd (rate up, entropy flat/high) versus an attack (rate up, entropy collapses or spikes) is the fastest operator diagnostic.

18. Phase 6 — Count-Min-Sketch Heavy-Hitter Detection

18.1 Objectives

Implement detect-sketch: fixed-memory heavy-hitter/elephant-flow detection via count-min sketch (Cormode & Muthukrishnan 2005; Estan & Varghese 2002), satisfying I7.

18.2 Detailed Implementation Steps

  • Implement the sketch data structure: width w, depth d, d independent hash functions, fixed at construction time per §8's error-bound equation (I7 — memory never grows with cardinality).
  • Implement increment-on-packet and query-for-estimate operations, both O(d) per operation (P12).
  • Implement heavy-hitter extraction: periodically scan tracked candidate keys (not the full sketch, which has no per-key enumeration) against a candidate list maintained by the flow table's top-occupancy entries.
  • Tune w/d against the target ε/δ accuracy stated in §34, validated by benchmarks/sketch_accuracy.rs.
  • Wire heavy-hitter output into mitigation-fsm as a distinct evidence type from baseline/entropy (adaptive attackers ramping slowly under threshold are still visible as a heavy hitter, closing the Phase-4 gap named in 16.6).
  • Implement empirical hash-independence validation in CI (chi-squared-class test across the d rows) to catch the correlation risk named in 18.6 before it reaches production.
  • Add a per-protocol sketch partition (rather than one global sketch) so a heavy hitter in one protocol's traffic does not dilute detection sensitivity for another's.

18.3 Deliverable

A fixed-memory heavy-hitter detector that identifies elephant flows within the stated error bound regardless of total flow cardinality.

18.4 Acceptance Criteria

  • Sketch memory footprint fixed and matches §34's derivation regardless of fixture flow cardinality (1K vs 10M distinct flows).
  • Heavy-hitter estimate error within the derived ε bound at stated δ confidence (benchmark-verified).
  • Correctly flags the slow-ramp adaptive-attacker fixture that Phase 4 alone misses.

18.5 Conformance Fixtures

  • conformance/phase6/slow-ramp-adaptive-attacker.pcap
  • conformance/phase6/high-cardinality-legitimate.pcap
  • conformance/phase6/sketch-accuracy-benchmark.json
  • conformance/phase6/hash-independence-chi-squared.json

18.6 Pitfalls

  • Hash-function correlation across the d rows (if not truly independent) collapses the error bound in practice below its theoretical guarantee — must be validated empirically, not just by construction.
  • An attacker who spreads volume across many distinct low-rate flows (the inverse of a heavy hitter) is invisible to this detector by design — it complements, not replaces, the entropy detector (Phase 5), which catches that distributional shape instead.
  • Sketch reset cadence trades detection latency against accuracy-window relevance — too frequent a reset loses persistent-attacker signal, too infrequent stales the estimate.

18.7 Performance Concerns

  • d independent hash computations per packet is the dominant per-packet cost added by this phase — must stay within the overall per-packet budget in §4/§34 even summed with Phases 0–5's costs.
  • Candidate-list scanning for heavy-hitter extraction must remain periodic/batched, never per-packet.

18.8 Edge Cases

  • Exactly-at-threshold heavy hitters oscillating in and out of the flagged set across sketch resets.
  • Two distinct legitimate elephant flows (e.g., a large backup transfer) coinciding with attack detection window.
  • A sketch reset occurring mid-attack, momentarily losing accumulated evidence for an ongoing heavy hitter until the next accumulation window completes.

18.9 Failure Analysis

A degraded error bound (from hash correlation, per 18.6) manifests as either missed heavy hitters or spurious flags on legitimate elephant flows — detected via the accuracy benchmark's regression gate (§28) before it reaches production traffic.

18.10 Operational Notes

Report sketch-estimated heavy hitters with their error bound attached (not a bare count) so operators can distinguish "definitely large" from "possibly large within ε" when deciding on manual mitigation escalation.

19. Phase 7 — Rate Limiting per Source/Prefix

19.1 Objectives

Implement ratelimit: layered per-source/prefix/ASN token-bucket rate limiting, satisfying ADR-10, invoked as the primary enforcement action once detection has classified traffic.

19.2 Detailed Implementation Steps

  • Implement the token-bucket data structure and refill math per §8's equations, keyed by LimitKey (Source/Prefix/Asn).
  • Implement layered lookup: check source-level bucket, then prefix-level aggregate, then ASN-level aggregate, applying the most restrictive applicable limit (ADR-10 rationale — spoofed/distributed sources need aggregation).
  • Wire reputation lookups (early integration ahead of full Phase 9 scope) so an allowlisted source bypasses rate limiting entirely (I2, P10).
  • Add mitigation-rule generation from sustained rate-limit hits, feeding mitigation-fsm with expiring MitigationRules (I5).
  • Tune default bucket capacity/refill rate against the legitimate-traffic-latency budget in §4 (a limiter that is too aggressive at baseline defeats P2).
  • Implement a prefix-to-ASN mapping table refresh job (periodic, bounded memory) supporting ASN-level aggregation without requiring a live lookup service on the near-fast path.
  • Add per-LimitKey-type rule-count telemetry as a first-class metric ahead of §19.10's operational use, so the dashboard exists before the first production rollout.

19.3 Deliverable

A layered rate limiter enforcing per-source/prefix/ASN caps with reputation bypass, generating expiring mitigation rules on sustained violation.

19.4 Acceptance Criteria

  • Legitimate-traffic-latency impact stays within p50/p95/p99 budgets in §4 with rate limiting active at baseline.
  • A distributed-source attack aggregated at the prefix/ASN level is capped even when no single source exceeds its individual bucket.
  • Every generated MitigationRule carries a non-empty RuleExpiry (I5, enforced by type construction, per §11).

19.5 Conformance Fixtures

  • conformance/phase7/distributed-low-rate-per-source.pcap
  • conformance/phase7/legitimate-burst-within-capacity.pcap
  • conformance/phase7/allowlisted-source-bypass.json
  • conformance/phase7/enterprise-nat-shared-prefix.pcap

19.6 Pitfalls

  • Aggregating at the prefix level can conflate distinct legitimate users behind the same CIDR (e.g., a large enterprise NAT) with attack traffic sharing that prefix — a direct instance of the false-positive-as-outage risk (P2).
  • Token-bucket burst-tolerance tuned too generously reopens the volumetric-flood window the limiter exists to close.
  • A rule expiry set too short causes rapid rule churn (thrash) against a sustained low-grade attack that just outlasts each expiry.

19.7 Performance Concerns

  • Layered lookup (source → prefix → ASN) triples the per-packet lookup cost versus a single-level limiter — must still fit the per-packet budget (§34).
  • ASN-level aggregation requires a prefix-to-ASN mapping table, itself a bounded-memory structure requiring periodic refresh.

19.8 Edge Cases

  • A legitimate source migrating IP mid-session (mobile carrier NAT reassignment) resetting its bucket state unexpectedly.
  • Overlapping prefix aggregates of different granularity matching the same source simultaneously.
  • A prefix-to-ASN mapping table entry going stale between refresh cycles, briefly misattributing a source's ASN-level bucket.

19.9 Failure Analysis

Prefix-level false positives (19.6) are contained by requiring prefix/ASN-level limiting to activate only after source-level signals have already crossed a lower confidence bound — never as a first-line, unconditional block (P2, P8).

19.10 Operational Notes

Expose active-rule count by LimitKey type (Source vs Prefix vs Asn) — a sudden shift toward prefix/ASN-level rules signals a distributed attack pattern distinct from a single-source flood, useful for operator situational awareness.

20. Phase 8 — The L7 HTTP-Flood Defense and Challenge/PoW

20.1 Objectives

Implement l7defend: HTTP request inspection, fingerprinting, and JS-challenge/proof-of-work issuance for application-layer floods and slow-loris that pass L3/L4 filtering undetected.

20.2 Detailed Implementation Steps

  • Implement the L7 request parser (L7Request) over HTTP/1.1 and HTTP/2 framing, hardened against the same adversarial-input discipline as pktparse (fuzz-first, ADR-24).
  • Implement Fingerprint: header-order hash, User-Agent classification, optional TLS JA3-class fingerprint — used to cluster requests by likely-client-software independent of source IP (defeats cache-busting query-string variation, §8 example).
  • Implement slow-loris detection: connection-hold-time distribution monitoring, independent of packet/byte rate (closes the low-and-slow gap named in §8's attack examples).
  • Implement Challenge: JS challenge (near-zero legitimate cost, filters non-browser bots) and ProofOfWork (difficulty function per §8's equation, monotonic in load, clamped per I11).
  • Implement challenge issuance/verification flow: issue on suspect fingerprint cluster, verify on return, escalate difficulty on repeated failure from the same fingerprint (not the same source IP, since L7 attacks often rotate IPs).
  • Wire successful-challenge sources into reputation (early integration ahead of full Phase 9) so I2/P10 holds at the L7 layer too.
  • Implement per-fingerprint-cluster difficulty scoping (not aggregate-load-driven) to close the over-punishment gap named in 20.6, keeping I11's clamp meaningful at the cluster level.
  • Add an HTTP/2 stream-aware request accounting layer so multiplexed streams within one connection are counted individually against fingerprint-cluster rate, not undercounted as a single connection.

20.3 Deliverable

An L7 defense that detects and challenges HTTP-flood and slow-loris traffic with a proof-of-work cost asymmetry that scales with observed load, without imposing meaningful cost on legitimate clients.

20.4 Acceptance Criteria

  • Slow-loris fixture detected via connection-hold-time signal within detection-latency budget (§4), despite sub-baseline packet rate.
  • Cache-busting HTTP-flood fixture correctly clustered by fingerprint despite unique per-request query strings.
  • Legitimate-client JS-challenge solve time ≤ tens of milliseconds; PoW difficulty at baseline load imposes ≤ single-digit-millisecond legitimate-client cost (I11).

20.5 Conformance Fixtures

  • conformance/phase8/slow-loris.pcap
  • conformance/phase8/cache-busting-http-flood.pcap
  • conformance/phase8/legitimate-diverse-clients.json
  • conformance/phase8/pow-difficulty-escalation.json
  • conformance/phase8/shared-corporate-proxy-fingerprint.json

20.6 Pitfalls

  • A challenge-solving botnet (headless-browser-capable, able to execute JS) partially defeats the JS-challenge tier — motivates escalation to PoW with rising difficulty, and ultimately CAPTCHA as a deferred fallback (§1 deferral).
  • Fingerprint clustering on header order can false-positive-cluster legitimate traffic from a common corporate proxy or CDN that normalizes headers identically across many distinct real users.
  • PoW difficulty escalation tuned against aggregate load rather than per-fingerprint load punishes all legitimate clients during an attack, not just the attacking cluster — I11's clamp and per-cluster scoping both matter here.

  • Full HTTP parsing is materially more expensive per-request than L3/L4 parsing — this subsystem runs strictly on the control/slow path (I8), never the eBPF fast path.

20.8 Edge Cases

  • Legitimate clients behind a corporate proxy sharing an identical fingerprint.
  • HTTP/2 multiplexed streams within a single connection complicating per-request rate accounting.
  • A legitimate client with JavaScript disabled or a non-browser legitimate integration (e.g., a monitoring probe) that cannot solve a JS challenge by design.

20.9 Failure Analysis

A fingerprint-clustering false positive on shared-proxy legitimate traffic is contained by requiring L7 mitigation escalation (beyond a JS challenge) to combine fingerprint evidence with rate/behavioral evidence (P8), never fingerprint alone.

20.10 Operational Notes

Track challenge-issue-rate, challenge-pass-rate, and PoW-difficulty-over-time on one dashboard panel — a falling pass-rate at rising difficulty is the signal that legitimate clients are starting to be affected, the trigger for the false-positive-rollback runbook (§26).

21. Phase 9 — The Reputation and Allowlist/Blocklist System

21.1 Objectives

Implement reputation: a decaying reputation score plus allowlist/blocklist store, promoted to first-class status after early integration in Phases 7–8, satisfying I9.

21.2 Detailed Implementation Steps

  • Implement the decaying score function: score moves toward neutral over time absent new evidence (I9), with distinct decay rates for positive vs negative evidence (a single attack burst should not permanently condemn a source that later behaves legitimately, per P5's expiry principle applied to reputation).
  • Implement AllowList/BlockList as explicit override sets, checked before the decaying score (an explicit allowlist entry always wins, satisfying I2/P10 unconditionally).
  • Implement reputation-store sharding matching the flow-table's shard topology (ADR-04 consistency) to avoid cross-shard lookup cost on the near-fast path.
  • Wire reputation into every prior phase's decision point retroactively: synguard (skip challenge for allowlisted), ratelimit (bypass for allowlisted, per 19.2), l7defend (skip challenge for allowlisted, per 20.2) — this phase's real work is making that integration first-class and consistently enforced, not introducing it fresh.

21.3 Deliverable

A consistent, decaying reputation store enforced identically across every enforcement point established in Phases 3–8.

21.4 Acceptance Criteria

  • An allowlisted source is never blocked by any subsystem, verified by a cross-phase integration fixture exercising synguard, ratelimit, and l7defend against the same allowlisted source simultaneously.
  • Reputation decay reaches neutral within the documented decay window absent new evidence (numeric target set per deployment policy, verified in fixture).
  • Blocklist entries expire per policy (never permanent by default, consistent with P5).

21.6 Pitfalls

  • A reputation-store shard inconsistency (a source's score differing across shards due to a routing change mid-session) can cause the same source to be allowed on one path and blocked on another — violates I2 if not caught.
  • An attacker deliberately building positive reputation with low-rate legitimate-looking traffic before launching an attack from the same source ("reputation laundering") — a known limitation addressed only partially by decay-rate asymmetry (attacks decay reputation faster than good behavior builds it).
  • Blocklist entries added manually by an operator without an expiry (bypassing the API's default) reintroduce the permanent-block risk P5 exists to prevent.

21.7 Performance Concerns

  • Reputation lookup must stay off the true fast path (I8) but fast enough on the near-fast path that Phase 3/7/8's integrations don't regress their own latency budgets.
  • Decay computation batched per sweep interval, not per-lookup, to avoid recomputation cost dominating read-heavy access patterns.

21.8 Edge Cases

  • A source with simultaneously mixed legitimate and attack traffic (shared NAT egress) whose aggregate reputation misrepresents either population.
  • Reputation-store restart/failover losing recent decay-in-progress state.
  • An allowlist entry added for a source that later changes ownership (IP reassignment), inheriting a stale trust grant it did not earn.

21.9 Failure Analysis

Reputation-laundering (21.6) is not a system defect but a documented residual risk — mitigated operationally by weighting reputation as one signal among several (P8) and never as sole justification for bypassing an active Mitigating-state rule.

21.10 Operational Notes

Audit-log every allowlist/blocklist API call with operator identity (I6) — this is the primary forensic trail when a false-positive rollback investigation needs to determine whether a block was automated or manual.

22. Phase 10 — The Scrubbing-Center Diversion (BGP/Anycast + Clean Back-Haul)

22.1 Objectives

Implement diversion: BGP-announcement-driven anycast traffic diversion to a scrubbing center with GRE clean-traffic back-haul, satisfying I10, for attacks exceeding inline capacity.

22.2 Detailed Implementation Steps

  • Implement BgpAnnouncement construction and the announce/withdraw state machine (AnnounceState), always constructing withdrawal-capable announcements (I10 — no announcement without a paired withdrawal path).
  • Implement the diversion-activation trigger from mitigation-fsm: activates only when the Mitigating state's own capacity is assessed insufficient (escalation path named in §8's state machine failure edge).
  • Implement ScrubberTunnel/GRE backhaul setup for returning cleaned traffic to origin, including MTU accounting for GRE encapsulation overhead (ADR-13).
  • Implement convergence-time-aware policy: during the BGP-convergence window (§4, §34), inline mitigation (Phases 2–8) continues operating at the origin site — diversion supplements, does not replace, inline defense during the gap.
  • Implement withdrawal-safety logic requiring a sustained clear-traffic hold-down interval before withdrawal (preventing the I10 failure-path race named in §8's failure example).
  • Add scrubbing-center capacity-utilization telemetry feeding the traffic-engineering/shedder (last line of defense if scrubbing capacity itself risks saturation).
  • Implement a minimum-dwell-time policy on both announced and withdrawn AnnounceState values to bound BGP route-flap risk named in 22.6.
  • Add explicit GRE-overhead accounting into ScrubberTunnel.mtu at construction time (not as a runtime correction), closing the silent-fragmentation gap named in 22.6.

22.3 Deliverable

An operational diversion controller that activates on escalation, converges within the target window, and safely withdraws without reintroducing the attack.

22.4 Acceptance Criteria

  • BGP announcement/withdrawal convergence within §4's target window on a realistic peering-simulation fixture.
  • Zero premature withdrawals (I10 failure-path race) across a sustained-then-clearing attack fixture with randomized timing.
  • GRE backhaul MTU accounting verified to not silently fragment/drop clean traffic.

22.5 Conformance Fixtures

  • conformance/phase10/diversion-activation-escalation.json
  • conformance/phase10/premature-withdrawal-race.json
  • conformance/phase10/gre-mtu-accounting.pcap
  • conformance/phase10/bgp-flap-dwell-time.json

22.6 Pitfalls

  • A withdrawal issued during a brief lull that is actually a pause in an ongoing attack (not true de-escalation) — the exact I10 failure-path example named in §8, requiring the hold-down interval, not instantaneous withdrawal on first clear reading.
  • BGP route flap (repeated announce/withdraw cycling) can itself destabilize upstream routing tables — bounded by a minimum-dwell-time policy on both announced and withdrawn states.
  • GRE encapsulation overhead unaccounted for causes clean backhaul traffic to exceed path MTU, silently fragmenting or dropping — must be accounted in the MTU field of ScrubberTunnel explicitly, not assumed.

22.7 Performance Concerns

  • Diversion activation/withdrawal is inherently a control-plane, seconds-to-minutes operation — no part of this phase is on any fast or near-fast path; the constraint is convergence time, not per-packet cost.
  • Scrubbing-center capacity is the ultimate ceiling (§31) — diversion delays but does not remove the need to size scrubbing capacity against realistic attack-size distributions.

22.8 Edge Cases

  • Partial upstream BGP convergence (some peers converge faster than others) causing a mixed traffic path during the transition.
  • A scrubbing center itself approaching capacity during a record-size attack, requiring the shedder to activate above and beyond diversion.
  • A scrubbing-provider maintenance window coinciding with an active diversion, requiring failover to a secondary provider mid-mitigation.

22.9 Failure Analysis

Premature withdrawal (22.6) re-triggers the Detecting state within the hold-down window per §8's documented failure-path recovery — recovery is re-announcement, not a fresh detection cycle, minimizing the time-to-remediate a withdrawal mistake.

22.10 Operational Notes

The docs/runbooks/scrubber-diversion.md runbook (§26) must document the manual override to force-hold an announcement active past the automatic hold-down when an operator has out-of-band evidence the attack is still ongoing.

23. Phase 11 — Adaptive-Attacker Red-Team Testing, Conformance and Perf Hardening

23.1 Objectives

Harden the complete system (Phases 0–10) against an adaptive adversary that actively probes for detector blind spots, and close out the full conformance/performance gate suite (§16 harness discipline extended to the whole system).

23.2 Detailed Implementation Steps

  • Build the adaptive-attacker red-team suite: automated traffic generators that iteratively probe threshold, entropy, and sketch boundaries (per P3 and P13's premise that the attacker is assumed adversarial-aware).
  • Construct combined-vector attack fixtures (simultaneous volumetric + protocol + L7 attack, per the taxonomy in §8) to verify cross-subsystem coordination, not just per-phase isolation.
  • Run differential testing against FastNetMon and iptables/nftables baselines (§28, §5 reference implementations) to quantify detection-rate and false-positive-rate deltas.
  • Execute chaos scenarios: line-rate flood exceeding designed capacity, flow-table saturation, scrubber failover, BGP flap (§28) — verifying graceful degradation (P11) rather than catastrophic failure.
  • Run the full perf-regression gate: Mpps floor and false-positive ceiling as hard CI gates (line-rate-perf.yml, ADR-25) across every phase's fixture corpus combined.
  • Execute soak testing (72-hour sustained mixed legitimate+attack traffic) verifying no memory growth beyond the bounded ceilings in §4/§7.
  • Finalize fuzz-corpus coverage across pktparse and the L7 request parser with coverage-guided corpus minimization (ADR-24).
  • Construct a detector-seam-targeting fixture generator that specifically searches for traffic shapes straddling two detectors' boundaries simultaneously (the class of gap named in 23.6), not just each detector's individual boundary.
  • Run compound-failure chaos scenarios (e.g., BGP flap concurrent with scrubber failover, 23.8) as a distinct CI tier from single-failure chaos, since ordering-dependent bugs only surface under concurrency.

23.3 Deliverable

A system verified against an adaptive adversary, with a complete CI gate suite (attack-replay, line-rate-perf, fuzz, chaos) green and a documented false-positive/false-negative rate under combined-vector attack.

23.4 Acceptance Criteria

  • Combined-vector attack fixture: ≥ 99.9% attack-packet drop rate, ≤ §4's false-positive ceiling on co-mingled legitimate traffic.
  • Chaos scenarios recover to Clear state within documented RTO (§4) without manual intervention for at least the flow-table-saturation and BGP-flap scenarios.
  • 72-hour soak shows zero unbounded memory growth in any tracked structure (flow table, sketch, reputation store).

23.5 Conformance Fixtures

  • conformance/phase11/adaptive-threshold-probe.pcap
  • conformance/phase11/combined-vector-attack.pcap
  • conformance/phase11/chaos-scrubber-failover.json
  • conformance/phase11/soak-72h-memory-profile.json
  • conformance/phase11/compound-failure-bgp-flap-plus-failover.json

23.6 Pitfalls

  • An adaptive attacker that specifically targets the seam between two detectors (e.g., a rate low enough to avoid baseline, entropy diverse enough to avoid collapse detection, but concentrated enough to be a real heavy hitter just below the sketch's practical resolution) — the hardest class of gap, requiring the combined-vector fixture rather than any single-detector fixture to surface.
  • Chaos-induced partial failure (e.g., scrubber failover mid-diversion) interacting with I10's withdrawal logic in an untested ordering.
  • Soak-test memory growth traced to an unbounded structure introduced in a later phase's integration (e.g., an ASN-prefix mapping cache in Phase 7) rather than the phase that appears to own it.

23.7 Performance Concerns

  • Combined-vector fixtures exercise every phase's per-packet cost simultaneously — this is where cumulative per-packet budget overrun (each phase individually within budget, but summed over budget) would first surface.
  • Chaos scenarios must be run at production-representative scale, not a scaled-down test topology, or failover timing does not transfer.

23.8 Edge Cases

  • An attack that intentionally mimics the shape of a legitimate flash crowd as closely as statistically possible, testing the limit of the classification table in §8.
  • Simultaneous chaos injection (e.g., BGP flap during a live scrubber failover) — a compound-failure scenario beyond any single §25 failure class.
  • A red-team fixture that itself has a subtle bug, producing a false "detection blind spot" finding that traces back to the fixture generator rather than the system under test.

23.9 Failure Analysis

Any Phase-11 finding that traces back to a specific earlier phase's crate is filed as a regression against that phase's conformance fixture set (§12.5–§22.5), not resolved solely within Phase 11 — Phase 11 is a hardening and discovery phase, not a place where root-cause fixes permanently live.

23.10 Operational Notes

The adaptive-attacker suite is re-run on every subsequent detection-algorithm change (not just at release) — treat it as a permanent regression gate, consistent with the "attacker adapts" premise in P3.

26. Operational Readiness

Named metrics: pps/bps passed vs dropped, per verdict type (Pass/Drop/Challenge/RateLimit); false-positive-rate estimate (reputation-confirmed-legitimate traffic later found blocked); detection latency (threshold-cross to Detecting-state timestamp delta); flow-table occupancy vs ceiling; challenge issue/pass rate and PoW-difficulty-over-time; mitigation-rule activation count by LimitKey type; scrubber-utilization percentage; BGP announcement/withdrawal count and dwell time.

Tracing: OpenTelemetry spans on the control/near-fast path only (never the eBPF fast path, per I8) correlating a mitigation decision from detection trigger through rule activation to telemetry emission; span attributes include the triggering EvidenceItem IDs so a trace and a log entry can be cross-referenced during forensics.

Structured logging: every verdict logs EvidenceItems per I6, JSON-structured (ADR-20), machine-parseable for forensic replay; log volume itself is bounded by the sampling policy in ADR-18, never full-capture by default.

Dashboards: one panel combining raw-rate + entropy time series (§17.10); one panel for reputation-vs-block correlation (§21.10, FM-3 diagnosis); one panel for challenge-pass-rate vs PoW-difficulty (§20.10, FM-10 diagnosis); one panel for flow-table occupancy + eviction rate (§13.10); one panel for scrubber-utilization vs provisioned capacity (§22 escalation context).

Alerting philosophy: two alerts page immediately — attack onset (Detecting-state transition) and a false-positive-rate spike (ADR-16 trigger) — every other signal is dashboard-only, consistent with P2's framing of false positives as the primary risk metric.

SLOs: detection latency ≤ 2 s (§4, M4); false-positive rate ≤ 0.01% during active mitigation (§4, M5); RTO ≤ 3 min (§4); BGP-diversion convergence 30–180 s (§4, M11).

Incident response: attack-onset page routes to the on-call mitigation operator, who confirms the Detecting→Mitigating transition and monitors the FP-rate panel; FP-spike page routes to the same on-call with automatic rollback already in flight (ADR-16) pending confirmation, not awaiting manual trigger.

Named runbooks under docs/runbooks/:

  • attack-onset-response.md — operator checklist from first page through Mitigating-state confirmation.
  • false-positive-rollback.md — how to confirm and complete an ADR-16 automatic rollback, and how to override it if the rollback itself was wrong.
  • scrubber-diversion.md — manual force-hold override for BGP withdrawal (§22.10), diversion activation/withdrawal manual triggers.
  • capacity-exhaustion.md — FM-9 escalation path, traffic-engineering shedder manual activation.
  • adaptive-attack-escalation.md — Phase-11 red-team-suite-informed escalation path when a detection blind spot (FM-4) is suspected in production.

Backup/restore: reputation-store and mitigation-rule state snapshotted periodically to control-plane storage, restorable on node replacement without requiring re-learning from cold baseline; flow-table state is intentionally not backed up (it is fast-path-local and rebuilds from live traffic, per its crash-only design).

Deployment topology: multi-region edge nodes plus one-or-more scrubbing-center sites reachable via anycast (§1 deployment model); control-plane API and reputation-store sync run region-local with periodic cross-region reconciliation.

Canary/rollback/migration: staged rollout of any new detection threshold or rule generation to a single-region canary before global propagation (ADR-16), with automatic rollback wired to the FP-rate-spike alert; a detection-model version change (§27) always canaries before promotion, gated on the Phase-4–6 conformance fixtures re-passing.

27. Compatibility & Versioning

  • Rule/signature format versioning: MitigationRule and AttackSignature schemas are versioned; a rule bundle carries a schema version, and an edge node rejects (fails closed) a bundle newer than it understands rather than misinterpreting fields.
  • eBPF-program ABI and kernel-version compatibility: the xdp-hook program is compiled against a documented minimum kernel/libbpf version floor; CO-RE (Compile Once – Run Everywhere) relocation is used where available to reduce per-kernel-version rebuild burden, with a fallback build path for kernels lacking CO-RE support (§12.9's verifier-CI gate covers both paths).
  • Detection-model versioning: baseline/entropy/sketch parameter sets (window sizes, k, w/d) are versioned alongside the model; a detection-model version change requires re-running the Phase-4–6 conformance fixtures before promotion, per the canary gate in §26.
  • Diversion-protocol compatibility: BGP announcement community-tag conventions are documented and versioned per scrubbing-provider integration, since providers differ in expected tagging; a provider-integration change is itself versioned independently of the core diversion crate.
  • API stability: the control-plane gRPC API (ADR-19) follows SemVer; a breaking change requires a new major version with a documented migration window, published in CHANGELOG.md.
  • Migration: policy/rule migrations are always additive-first (new field with a default) before a deprecation cycle removes an old field, never a simultaneous add-and-remove.
  • Deprecation: a deprecated field/endpoint is flagged in CHANGELOG.md for at least one minor-version cycle before removal, with the removal date fixed at the time of deprecation, not left open-ended.
  • SemVer scope: applies to every crate in crates/ independently, with common-types as the most conservatively versioned crate since every other crate depends on it — a breaking change there is treated as a workspace-wide major-version event.

28. Testing & Verification Strategy

  • Unit: per-crate logic (cookie MAC construction, token-bucket refill math, entropy computation, sketch increment/query, decay-rate math).
  • Integration: cross-crate flows (SYN cookie → flow table handoff; detection → mitigation-fsm → rate limiter rule generation; reputation → every enforcement point per §21.4's cross-subsystem fixture).
  • Property: the fast path's per-packet cost is bounded regardless of packet content (I1, property-tested with randomized packet fuzz inputs bounding a cycle-count assertion); a passing legitimate flow is never dropped by a later rule (I2, property-tested by generating random rule sets against a fixed allowlisted flow); SYN state is never allocated pre-cookie-validation (I3, property-tested by asserting zero FlowState growth under randomized SYN-flood shapes); every mitigation rule expires (I5, property-tested by generating random MitigationRule constructions and asserting RuleExpiry is always populated); count-min sketch memory never grows with input cardinality (I7, property-tested across cardinalities from 10^3 to 10^7).
  • Attack-replay (named CI gate, attack-replay.yml): replaying real captured attack traffic (PCAP-class, per-phase fixtures in §12–§23 N.5) against the system and measuring drop-of-attack vs pass-of-legitimate, plus the adaptive-attacker red-team suite (Phase 11, §23) as a second named gate feeding the same pipeline.
  • Differential: against FastNetMon and iptables/nftables baselines (§5 reference implementations) — quantifying detection-rate and false-positive-rate deltas per attack fixture class (§23.2).
  • Fuzzing: pktparse and the L7 request parser (l7defend) as primary targets (ADR-24), corpus-driven, coverage-guided, run continuously via fuzz.yml.
  • Chaos: line-rate flood beyond designed capacity, flow-table saturation, scrubber failover, BGP flap (§23.2), plus compound-failure scenarios (§23.2's second addition) — verifying graceful degradation (P11) rather than catastrophic failure.
  • Load testing: sustained line-rate traffic generation matching §4's Mpps target, run against benchmarks/mpps.rs.
  • Soak: 72-hour sustained mixed legitimate+attack traffic (§23.4) verifying bounded memory across flow table, sketch, and reputation store.
  • Fault injection: forced eBPF-map failures, forced control-plane node loss, forced BGP-peer unavailability.
  • Perf-regression gating: line-rate-perf.yml enforces a Mpps floor and a false-positive-rate ceiling on every merge (ADR-25), tied to the M# targets in §30 — a merge that regresses M1/M2/M5 fails CI regardless of functional-test outcome.

29. Build & Release Engineering

  • Reproducible builds: pinned lockfile, deterministic build metadata (ADR-27), verified by a build-reproducibility CI check comparing hash-identical output across two independent build runs.
  • Artifact signing: release binaries and container images signed via cosign before publication (ADR-26).
  • SBOM: generated per release, attached as a release artifact, diffed against the prior release to surface new dependencies for audit.
  • Release channels: stable (promoted after full §28 gate suite passes) and edge (post-merge, pre-promotion, used for canary deployment per §26).
  • CI/CD topology: ci.yml (unit/integration/property) → attack-replay.yml (PCAP-gate) → line-rate-perf.yml (Mpps/FP-ceiling gate) → fuzz.yml (scheduled, not blocking merge but blocking release) → release.yml (signing, SBOM, provenance).
  • Version stamping: build embeds git commit, build timestamp, and dependency-lockfile hash into the binary for forensic traceability.
  • Provenance/attestation: SLSA-style provenance attestation generated per release artifact, recording the exact CI job and inputs that produced it.
  • Dependency auditing: cargo audit-class scanning runs on every merge and nightly against the full dependency tree, failing CI on any newly disclosed critical vulnerability.

30. Performance Engineering

31. Scalability Analysis

What stays constant: per-packet fast-path processing cost, O(1) by design (P12, I1) — this is mandatory, not merely desirable, because any per-packet cost that grows with attack size or flow cardinality directly threatens line rate; count-min sketch memory, fixed by construction (I7) regardless of flow cardinality.

What grows: flow-table memory with tracked-flow count (bounded by eviction, I4, but still O(n) in active flows up to the ceiling); reputation-store memory with tracked-source count (bounded similarly by decay-driven eviction); scrubbing-center capacity requirement with worst-case provisioned attack size — this is the ultimate limit (§34), not a per-packet cost concern.

Named bottlenecks: flow-table memory under sustained high-cardinality attack (FM-2); telemetry ingestion under high verdict-emission rate (FM-8); scrubbing-center Tbps ceiling under record-scale attacks (FM-9); BGP-convergence time as a fixed floor regardless of node count (M11, cannot be engineered away, only accepted).

Horizontal scaling: additional edge nodes scale fast-path Mpps roughly linearly (per-shard flow tables are independent, ADR-04); additional scrubbing/anycast sites scale absorbed-attack-size capacity, each site adding its own Tbps class (§31's multi-site lever, deferred federation per §1/§37).

The capacity-vs-attack-size arms race: every fixed defensive capacity number is a target the attacker can eventually exceed given enough distributed compute (the Mirai-class botnet-scale precedent, Antonakakis et al. 2017) — the practical response is layering (inline fast-path absorbs the common case; scrubbing absorbs the exceptional case) rather than any single number being permanently sufficient.

Practical Tbps ceiling and levers beyond it: a single scrubbing site's Tbps class is bounded by its own uplink and hardware provisioning; levers beyond a single site are multi-site anycast federation (deferred, §1/§37) and upstream ISP-level BCP 38 adoption reducing the spoofable amplification surface at the source (§36's rejected-but-instructive alternative architecture) — the latter lever is outside this system's control (§1 delegates it) but materially changes the ceiling if adopted upstream.

32. Mental Models & First Principles

  • MM1 — DDoS defense is an economics problem: you win by making the attack cost more than the defense costs, which is why proof-of-work and amplification-factor reduction matter more than raw absorption capacity alone (P7, §34's cost-asymmetry math).
  • MM2 — the hard problem is not dropping packets, it is telling attack from legitimate at line rate under an adversary trying to look legitimate; every defense is a classifier with a false-positive cost (P2, P3).
  • MM3 — you cannot filter what you cannot see fast enough; detection and mitigation must both run at (or near) line rate, or the slow one is the bottleneck the attacker will aim at (P1, P6, I8).
  • MM4 — no single signal is sufficient against an adaptive adversary; every real mitigation decision in this system is a combination of at least two independent signals (P8, the classification table in §8).
  • MM5 — bounded memory is not an optimization, it is a security property; an unbounded data structure fed by attacker-controlled input is itself a DoS vector (P9, I4, I7).
  • MM6 — a mitigation without an expiry is a liability, not a defense; the system must assume every rule will eventually be wrong and plan for its own reversal (P5, I5).
  • MM7 — always-on and on-demand are not competing designs but complementary layers; the choice is a latency-vs-activation-time tradeoff, not a correctness question (§1 deployment model, §33).
  • MM8 — the attacker adapts to whatever the defense publishes as its threshold; any purely static, disclosed threshold is eventually obsolete, which is why statistical and combinatorial signals outlast simple thresholds (P3, Phase 11).

Per-system notes:

  • Cloudflare (XDP/gatebot): always-on XDP is the key contrast to a traditional on-demand scrubbing center that this blueprint's ADR-11 encodes as a policy choice rather than a fixed decision — always-on taxes 100% of traffic with inline latency but has zero activation delay.
  • Akamai Prolexic: on-demand has zero baseline latency cost but pays a BGP-convergence delay (§4, §34) at the moment it matters most; a customer pays primarily for peak-attack capacity that sits mostly idle, a structurally different cost model from always-on.
  • FastNetMon: represents the detection-only end of the spectrum — a strong reference for the statistical-detection approach this blueprint adopts (§5), but it does not itself perform line-rate kernel-space filtering, relying on external enforcement (typically BGP Flowspec or upstream ACL push).
  • AWS Shield: architecturally opaque (proprietary) but publicly represents the hyperscale-cloud-integrated model, where the "edge" is the cloud provider's own network rather than a customer-operated fast path — a deployment option this project does not target since it builds a standalone platform, not a cloud-integrated service.
  • Arbor/Netscout: the classic on-demand-appliance embodiment of the same architectural family as Akamai Prolexic, historically the dominant carrier/enterprise scrubbing model before always-on cloud-edge models became common.
  • iptables/nftables: the low-end contrast named in the brief — no line-rate fast path, no statistical detection, and manual-rule-only enforcement — useful as the differential-testing floor (§28) precisely because it has none of this system's defenses, making it the baseline against which detection-rate and false-positive-rate deltas are meaningful.

This system's ADR-11 policy choice mirrors the Cloudflare-vs-Prolexic cost-structure decision at the architecture level, not merely at the deployment-topology level — implementing both rather than committing to one.

34. Back-of-Envelope Capacity Model

  1. Per-packet time budget at line rate (10 GbE, 64B min-size packets). 10 Gbps ÷ (64B + 20B interframe/preamble overhead) × 8 bits ≈ 14.88 Mpps. Time budget per packet = 1s ÷ 14.88M ≈ 67 ns/packet. At 100 GbE the same math gives ≈ 148.8 Mpps ⇒ 6.7 ns/packet — this is why XDP (kernel-native, no syscall per packet) and strictly O(1) per-packet logic (P12) are mandatory: a single cache miss (~100 ns) already exceeds the 100 GbE budget.

  2. Flow-table memory. 8,000,000 tracked flows × 64 bytes/entry (five-tuple key + counters + TCP state, packed) = 512 MB, matching the §4 ceiling exactly by construction (M7).

  3. Count-min-sketch memory and error bound. Target ε = 0.001 (0.1% of total traffic volume as the acceptable estimation slack), δ = 0.01 (99% confidence). Width w = ⌈e/ε⌉ ≈ 2,719; depth d = ⌈ln(1/δ)⌉ ≈ 5. Table size = w × d × 4 bytes (u32 counter) ≈ 2,719 × 5 × 4 ≈ 54,380 bytes ≈ 53 KB — fixed regardless of whether the tracked flow population is 10,000 or 10,000,000 distinct flows (I7).

  4. SYN-cookie capacity vs SYN-flood rate. A keyed hash (e.g., SipHash-class) computing the cookie MAC costs roughly 20–40 ns per invocation on modern hardware; at 30 ns/cookie, one core computes ≈ 33M cookies/sec — comfortably above the M6 target of 5M SYN/s/core, leaving headroom for the surrounding parse/validate logic within the same per-core budget.

  5. Amplification-factor math. Attacker upload of 1 Mbps directed at an open memcached reflector with a published amplification factor up to ~51,000× (Rossow 2014) yields attack bandwidth up to ~51 Gbps from a single attacker — this single example is why source-side BCP 38 (RFC 2827) matters disproportionately: eliminating spoofability at the source removes the attacker's ability to direct the amplified response at a victim rather than themselves, independent of any defense the victim deploys.

  6. Proof-of-work cost asymmetry. At PoW difficulty d = 20 (20 leading zero bits required), expected attacker cost ≈ 2^20 ≈ 1,048,576 hash operations per accepted request; at ~200M hashes/sec on commodity hardware, that's ≈ 5.2 ms of attacker CPU per request. Server verify cost is a single hash computation, O(1), sub-microsecond. For an attacker to sustain 1M requests/sec against this difficulty requires ≈ 5,200 CPU-seconds/sec of aggregate attacker compute — i.e., thousands of dedicated cores — while the server's verification cost for the same 1M requests/sec is negligible (M10).

  7. Scrubbing capacity needed to absorb a stated attack size. A stated 2 Tbps attack (consistent with published record-attack scale, Cloudflare/Akamai engineering write-ups) requires a scrubbing site provisioned at ≥ 2 Tbps ingress capacity with margin — motivating the §4 target of 1–5 Tbps per site and the multi-site horizontal-scaling lever in §31 for attacks exceeding any single site's provisioned ceiling.

  8. Legitimate-traffic latency budget at inline mode. The fast path's own per-packet cost (§34.1, ≤100 ns at 10 Mpps/core) is a small fraction of the p50 legitimate-traffic-latency target of 50 μs (§4) — the remaining ~49.9 μs of headroom is consumed by NIC-to-userspace ring-buffer handoff and any near-fast-path lookups (reputation, rate-limit bucket), which is why those lookups (§21.7, §19.7) must stay in the low-microsecond range, not the millisecond range, to preserve the p99 budget of 500 μs.

  9. Flow-table eviction throughput needed to survive a flow-cardinality attack. To keep occupancy below the 8M-flow ceiling (§4) against an attacker generating 1M novel five-tuples/sec sustained, the eviction path must reclaim ≥1M entries/sec — at a batched-eviction cost of roughly 20 ns/entry (cache-friendly sequential scan of an LRU list segment), that is ≈20 ms of eviction work/sec, comfortably inside a single core's budget and validating the batching design in §13.2/§13.7 over a naive per-packet eviction check.

  10. Reputation-store decay-sweep cost. For a reputation store tracking 10M distinct LimitKey entries with a decay sweep run once per minute, decaying each entry at ~5 ns/entry (a simple exponential-decay multiply) costs ≈50 ms of sweep time per minute — under 0.1% of a single core's time budget, confirming the batched-sweep design in §21.7 does not compete meaningfully with lookup-path work on the same core.

36. Alternative Architectures (Roads Not Taken)

A. Pure upstream/ISP filtering with BCP 38 everywhere.

[Attacker] --spoofed src--X  [ISP edge router: BCP38 drop]
[Attacker] --real src------->[ISP edge router: pass]------->[Internet]-->[Victim]
  • Winning regime: a world with universal BCP 38/BCP 84 ingress-filtering adoption across all transit and access networks, which would end IP-spoofing-based attacks (SYN floods with spoofed sources, most reflection/amplification) at their origin.
  • Embodying reference: no single system embodies this at scale — it is a network-operator practice (RFC 2827/RFC 3704), partially adopted (Jonker et al. 2017 documents the incomplete-adoption reality).
  • Why rejected here: undeployable as this project's architecture because it requires universal adoption across networks this project does not control (§1 boundaries — delegates BCP 38 assumptions to the network, per ADR-17's probabilistic treatment); building a mitigation platform that assumes it would leave every non-adopting network's victims undefended.

B. Cloud always-on inline model vs on-demand BGP-diversion scrubbing center.

Always-on:  [Client]-->[Inline XDP filter, every packet]-->[Origin]
On-demand:  [Client]-->[Origin] (baseline)
            [Client]-->[BGP-diverted]-->[Scrubber]--GRE-->[Origin] (under attack)
  • Winning regime: always-on wins when the protected service cannot tolerate any activation delay (financial trading infrastructure); on-demand wins when the protected service can tolerate a convergence-time gap but must not pay inline latency tax on 100% of baseline traffic (a latency-sensitive but rarely-attacked service).
  • Embodying systems: Cloudflare (always-on XDP, §33) vs Akamai Prolexic / Arbor-Netscout (on-demand, §33) — the two dominant industry models.
  • Why not chosen exclusively: this blueprint implements both behind ADR-11 as a deployment-time policy rather than picking one, because the tradeoff is customer/workload-specific, not a correctness question (MM7).

C. ML/behavioral-classification-first approach.

[Traffic]-->[Feature extraction]-->[Trained classifier model]-->[Verdict]
                                         ^
                              [Labeled training data, retrained periodically]
  • Winning regime: an environment with continuously available, high-quality labeled attack/legitimate traffic and tolerance for periodic retraining drift, where attack diversity has outpaced hand-tuned statistical signatures (ADR-06's "when rejected choice wins" column).
  • Embodying system: none of the cited reference implementations centers this approach at production scale in a documented, publicly-verifiable way at the time of this blueprint (most published ML-DDoS-detection work is academic/research-stage, distinct from the cited operational systems in §5/§33).
  • Why rejected here: training-data drift risk, interpretability loss (a false-positive investigation needs the "Detection"/"Telemetry" evidence trail in §7, which a black-box classifier complicates), and latency of retraining relative to an adversary that adapts within a single attack campaign (P3) — the statistical + sketch combination (ADR-06 locked choice) is interpretable and retrain-free by construction.

D. Proof-of-work / client-puzzle-first line making every request costly.

[Every client]-->[Mandatory PoW puzzle, all traffic]-->[Origin]
  • Winning regime: an environment where all legitimate clients are known to have surplus compute (server-to-server API traffic, not resource-constrained mobile/IoT clients) and where the operator is willing to impose baseline latency cost on 100% of legitimate traffic in exchange for near-total bot-cost-asymmetry.
  • Embodying system: client-puzzle proposals in the DDoS-defense literature (Kaufman/Perlman/Speciner-class cryptographic-puzzle designs, §5) applied as a universal front door rather than a targeted L7 challenge.
  • Why rejected here: this blueprint uses PoW only as a targeted, escalating L7 challenge (Phase 8, I11) applied to suspect fingerprint clusters, not as a mandatory universal front door — imposing it on all traffic would violate P2 (false-positive-as-outage) for every legitimate low-power client at baseline, when no attack is even occurring.
