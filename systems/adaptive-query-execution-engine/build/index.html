⬜ Phase 0 — Repo Skeleton, IR, Columnar Batches, Push Operators (Scan/Filter/Project), Single-Thread Stage Runner, EXPLAIN

Objectives

Stand up the workspace; define aqe-types IR + Arrow-backed RecordBatch; implement push-based Scan/Filter/Project; a single-threaded stage runner that cuts at Exchange; plan-versioned EXPLAIN; CLI runs scan→filter→project→exchange→count over 1M Arrow rows.

Deliverable

aqe run --plan scan_filter_proj.json --data orders.arrow executes single-threaded, prints EXPLAIN (v0) and count; cargo test green; Miri clean on scalar paths.

Acceptance
  • Filter+Project correctness vs DataFusion on 1M rows (differential, exact).
  • EXPLAIN snapshot matches golden (insta).
  • 1M-row scan→filter→project ≤ 50 ms single-thread (int cols).
  • Plan validator rejects 5 malformed plans with correct PlanError.
Fixtures
  • plans/scan_filter_proj.json — baseline. plans/empty_partitioning.json — malformed (EmptyPartitioning). plans/unresolved_col.json — malformed. golden_explain/p0_scan_filter_proj.txt. stats_traces/ empty (no reopt yet).
Pitfalls
  • Null bitmap mishandling → filter drops/keeps wrong rows. Root: ignoring Arrow validity. Debug: differential vs DataFusion on null-heavy col. Recover: route nulls through bitmap kernels.
  • Dictionary column decoded eagerly → memory blowup. Root: not passing dict through. Debug: peak RSS on dict col. Recover: keep Dictionary type end-to-end.
  • Expr eval per-row → slow. Root: scalar virtual dispatch. Debug: flamegraph in expr. Recover: batch-at-a-time slice kernels.
  • Stage cut misses a breaker → mid-pipeline materialization wrong. Root: incomplete breaker set. Debug: stage count vs expected. Recover: complete BreakerKind table.

⬜ Phase 1 — Stage DAG, Stats Collector (rows/bytes), Initial Planner, Disk Shuffle Skeleton

Objectives

Turn multi-stage plans into a scheduled StageGraph; collect exact rows/bytes per stage; implement aqe-shuffle (hash-partition to disk files + registry); seal stats at Materialized. No adaptivity yet — stats observed and logged.

Deliverable

A 3-stage plan (two scans → shuffle → join-build placeholder) runs to completion single-threaded; shuffle files on disk; sealed RuntimeStats printed; EXPLAIN shows stage DAG.

Acceptance
  • Stats rows/bytes exact vs ground truth (differential).
  • Shuffle registry complete before consumer (I12 assert passes).
  • Round-trip: shuffle files read back exactly (I11 crc match).
  • Stage DAG topo order deterministic across runs.
Fixtures
  • plans/three_stage_shuffle.json. stats_traces/three_stage.json (captured rows/bytes/partition_sizes). golden_explain/p1_stage_dag.txt. skew/ placeholder.
Pitfalls
  • Partition-size skew uncounted → later coalescing/skew-split impossible. Root: not recording partition_sizes. Debug: histogram missing. Recover: always populate per-partition bytes.
  • Shuffle FD leak → exhaust budget. Root: files not closed/coalesced. Debug: lsof count. Recover: segment coalescing + RAII handles.
  • Consumer starts before manifest complete → missing-file read. Root: race on registry. Debug: missing_shuffle_files counter. Recover: barrier on Materialized.
  • Stats sealed too early (mid-stage) → wrong counts. Root: seal on first finish, not full drain. Debug: rows < expected. Recover: seal only at stage Materialized.

⬜ Phase 2 — Vectorized Expression + Filter/Project Hardening, Predicate Pushdown into Scan

Objectives

Harden the data plane the adaptive engine will schedule: complete vectorized kernels, selection vectors, late materialization, real predicate/column pushdown into Scan (reduces bytes → better runtime stats).

Deliverable

Filter/Project run on selection vectors; Scan prunes columns + row groups; EXPLAIN shows pushed predicates. Throughput materially higher than Phase 0.

Acceptance
  • Differential correctness (incl. nulls, dict, casts) vs DuckDB + DataFusion.
  • Predicate pushdown reduces scanned bytes ≥ 30% on a selective fixture.
  • Filter+Project ≥ 500 M rows/s single-thread on int columns.
Fixtures
  • plans/pushdown_selective.json, plans/dict_filter.json, plans/cast_chain.json. golden_explain/p2_pushdown.txt. Malformed: plans/type_mismatch_cast.json (SchemaMismatch).
Pitfalls
  • Selection-vector + null interaction → counting filtered nulls wrong. Root: mask vs validity confusion. Debug: differential on null+predicate. Recover: separate validity from selection.
  • Pushdown changes semantics (predicate on computed col) → wrong pruning. Root: pushing non-pushable predicate. Debug: result diff after pushdown. Recover: pushability analysis (only base-column comparisons).
  • Dict code comparison vs literal → wrong matches when dictionaries differ across batches. Root: per-batch dictionaries. Debug: cross-batch dict mismatch. Recover: unify/translate dict codes.
  • CAST overflow silently wraps. Root: unchecked cast. Debug: boundary fixtures. Recover: checked cast → null/error per type rules.

⬜ Phase 3 — Sketches: HyperLogLog (NDV) + Count-Min (heavy hitters) + Skew Report

Objectives

Add aqe-sketch and wire it into the stats collector so each materialized stage emits NDV (HLL), heavy hitters/frequencies (CMS), and a SkewReport — the inputs to every adaptive decision.

Deliverable

RuntimeStats now includes NDV, heavy hitters, skew ratio per stage; printed in EXPLAIN's stats annotation; captured into stats_traces/.

Acceptance
  • HLL NDV within ±2% of exact on uniform 1e7-distinct fixture.
  • CMS heavy-hitter recall: top-10 hot keys identified on Zipfian fixture.
  • Skew ratio matches ground truth within tolerance on skewed fixture.
  • Sketch outputs bit-identical across runs (fixed seed) → replay-ready.
Fixtures
  • skew/uniform_1e7.arrow, skew/zipf_s1.2.arrow, skew/single_hot_key.arrow. stats_traces/sketch_uniform.json, stats_traces/sketch_zipf.json. Golden: golden_explain/p3_stats_annotated.txt.
Pitfalls
  • Per-run random hash seed → non-reproducible decisions. Root: default RNG seed. Debug: replay diff. Recover: fix seed in config (I1/I4).
  • HLL low precision on small NDV → biased small-range estimate. Root: no linear-counting fallback. Debug: NDV error on small sets. Recover: linear counting below threshold.
  • CMS collisions inflate cold keys → false heavy hitters → bad skew-split. Root: width too small / no error bound used. Debug: compare to exact freq. Recover: widen w; carry error bound; conservative threshold (principle 14).
  • Skew false positive → needless split. Root: ratio threshold too low. Debug: split that didn't help. Recover: require ratio AND absolute-size threshold.

⬜ Phase 4 — Morsel Scheduler: Work-Stealing, NUMA-Aware, Push Pipelines, Backpressure

Objectives

Replace the single-thread runner with a morsel-driven scheduler (Leis 2014): per-NUMA morsel queues, work-stealing workers, push pipelines, backpressure integrated with aqe-mem.

Deliverable

Multi-core execution; near-linear scaling on scan→filter→project→partial-agg up to core count; deterministic results (not thread order) verified by differential vs single-thread.

Acceptance
  • Scaling efficiency ≥ 0.8× linear to 8 cores (CPU-bound query).
  • Results identical to single-thread (order-independent) across 100 runs.
  • loom passes on scheduler/backpressure model.
  • No data races (Miri/loom); scheduling overhead ≤ 1% wall-time.
Fixtures
  • plans/parallel_scan_agg.json. microbench/scaling_{1,2,4,8,16}.json. Differential: single-thread vs N-thread result equality fixture.
Pitfalls
  • Morsel too small → scheduling overhead dominates (this is the tiny-task problem coalescing later fixes). Root: <100K rows. Debug: high morsel_dispatch_rate, low per-morsel work. Recover: size morsels to amortize dispatch.
  • Work-stealing thrash across NUMA → remote-memory stalls. Root: steal-first policy. Debug: NUMA miss counters. Recover: local-first, steal as last resort.
  • Backpressure deadlock (cycle of full queues) → hang. Root: bidirectional blocking. Debug: loom; blocked-worker dump. Recover: DAG is acyclic by construction; bound queues; never block holding a reservation.
  • Non-deterministic aggregation order changes float sums → differential noise. Root: float non-associativity across thread merge order. Debug: result diff. Recover: deterministic merge tree OR document tolerance for float aggs.

⬜ Phase 5 — HashJoin + HashAggregate (vectorized linear-probe), Two-Stage Partial/Final Aggregation

Objectives

Implement the breakers that produce the most important runtime stats: vectorized HashJoin (build/probe) and HashAggregate (partial→final). These materialize and emit rows/bytes/NDV/skew that drive adaptivity.

Deliverable

TPC-H Q1 (agg-heavy) and a hash-join query run multi-core; correct results; build-side and group stats emitted and visible in EXPLAIN.

Acceptance
  • TPC-H Q1 + Q3 (join) results match DuckDB exactly (SF=1, SF=10).
  • Two-stage agg reduces shuffle bytes ≥ 50% vs single-stage on high-cardinality group.
  • HashJoin throughput within ±25% of DataFusion on uniform keys.
Fixtures
  • benchmarks/tpch/q01.json, q03.json. plans/hashjoin_uniform.json, plans/two_stage_agg.json. golden_explain/p5_join_stats.txt. Malformed: plans/join_key_type_mismatch.json.
Pitfalls
  • Build side larger than memory (no spill yet) → OOM. Root: unbounded build buffer. Debug: RSS spike. Recover: deferred to Phase 6 spill; for now reservation guard + clear error.
  • Hash collisions / bad hash → long probe chains. Root: weak hash on skewed keys. Debug: probe-length histogram. Recover: strong hash; skew handled Phase 10.
  • Partial-agg state explosion on high cardinality → memory. Root: too many groups before shuffle. Debug: partial table size. Recover: spill (Phase 6) / switch to no-partial.
  • Float agg non-determinism across merge order → differential mismatch. Root: associativity. Debug: result diff. Recover: deterministic merge order or documented tolerance.

⬜ Phase 6 — Memory Manager + Spill-to-Disk for Join/Agg/Sort, Backpressure Integration, External Sort + SortMergeJoin + BroadcastJoin

Objectives

Make every breaker make progress under any memory budget (principle 6): reservation-based aqe-mem, spill for hash join/agg, external merge sort, plus SortMergeJoin and BroadcastJoin operators (needed for join-strategy switching in Phase 9/10).

Deliverable

Hash join/agg complete with build side ≫ memory (spill); external sort over data ≫ memory; SortMergeJoin + BroadcastJoin operators usable by the planner.

Acceptance
  • Hash join correct with build side = 5× budget (spill round-trip exact, I11).
  • External sort correct + stable on 10× budget input.
  • Spill amplification ≤ 1.5× (constraint §4).
  • No OOM across spill stress fixtures; backpressure engages before ceiling.
Fixtures
  • plans/spilling_hashjoin.json, plans/external_sort.json, plans/smj.json, plans/broadcast_join.json. conformance/spill/round_trip_crc.json. Golden EXPLAIN p6.
Pitfalls
  • Recursive partitioning never terminates on a single hot key (all rows one partition). Root: hash can't split identical keys. Debug: partition still oversized after split. Recover: fall back to sort-merge or block-nested for that partition; this motivates skew handling (Phase 10).
  • Spill storm (over-eager spilling) → I/O thrash, latency cliff. Root: threshold too low / no hysteresis. Debug: spill_events spike, low mem use. Recover: hysteresis + reserve headroom.
  • Reservation leak → budget shrinks over query. Root: missing RAII drop on error path. Debug: op_mem_bytes doesn't return to 0. Recover: RAII + ledger audit.
  • Broadcast of a not-actually-small side → replicate huge table OOM. Root: stale/wrong size estimate. Debug: broadcast bytes ≫ threshold. Recover: size guard at broadcast time; conservative threshold (Phase 9).
  • External-sort instability breaks SMJ correctness. Root: non-stable merge. Debug: differential. Recover: stable merge with tie-break on input order.

⬜ Phase 7 — Adaptive Controller Core: Replan Trigger, Single-Stage Re-Planner, PlanVersion, ReoptEvent Log, NO-OSCILLATION Lattice

Objectives

Build the feedback loop's brain (framework only; specific rules in Phase 8–11): on stage completion, decide whether to re-plan downstream Pending stages using sealed RuntimeStats; bump PlanVersion; record ReoptEvent; enforce determinism (I1), single-pass (I2), unstarted-only (I3).

Deliverable

End-to-end loop runs with a trivial pass-through rule: stages complete, controller inspects stats, logs (no-op) decisions, bumps version only when a rule applies. EXPLAIN diff shows v0 (with ReoptEvent framework live).

Acceptance
  • Replay harness: identical (plan, stats trace) → identical PlanVersion sequence + ReoptEvent log (I1) across 100 runs.
  • No stage re-planned more than #input-edges times (I2) — asserted by lattice; thrash fixture aborts cleanly.
  • Only Pending stages mutated (I3) — verified by fault-injection mutating a Running stage → rejected.
  • Schema/multiplicity validation rejects a deliberately-bad rewrite.
Fixtures
  • plans/reopt_framework.json. stats_traces/reopt_framework.json (drives decisions). golden_explain/p7_version_diff.txt. Thrash fixture: conformance/skew/oscillation_attempt.json (must abort via I2).
Pitfalls
  • Oscillation (re-plan A→B→A) → livelock. Root: non-monotone decision. Debug: reopt_count{stage} > edges; lattice trace. Recover: monotone lattice; single pass (I2).
  • Re-planning a started stage → torn plan. Root: race between completion and dispatch. Debug: stage-state assert. Recover: serialize controller as single writer; mutate only Pending (I3).
  • Non-deterministic decision (used wall-clock / thread order) → replay diff. Root: impure decision input. Debug: replay mismatch. Recover: pure fn of sealed stats (I1/I4).
  • Stats from wrong PlanVersion used → inconsistent decision. Root: stale stats reference. Debug: version mismatch in event. Recover: tag stats with producing version; ignore mismatches.

⬜ Phase 8 — Adaptive Rule: Coalesce Shuffle Partitions (right-size post-shuffle parallelism)

Objectives

First real adaptive rule: after a shuffle materializes, coalesce many small partitions into fewer right-sized ones (Spark AQE's flagship win) — eliminating tiny-task overhead. Enforce parallelism-only-shrinks (I8).

Deliverable

A query producing thousands of tiny partitions runs with coalesced tasks; fewer, larger tasks; lower scheduling overhead; visible in EXPLAIN (v0 N parts → v1 M parts) + ReoptEvent.

Acceptance
  • Coalescing reduces task count ≥ 5× on a tiny-partition fixture with no result change (differential).
  • End-to-end wall-time improves ≥ 20% on that fixture (scheduling overhead reclaimed).
  • Post-partition count ≤ pre (I8) always; never below parallelism floor.
Fixtures
  • plans/tiny_partitions.json (e.g., 2000 partitions, 1 MiB each). stats_traces/tiny_partitions.json. Golden: golden_explain/p8_coalesce_diff.txt. Edge: plans/already_sized.json (no coalesce).
Pitfalls
  • Over-coalescing kills parallelism → underutilized cores. Root: target too large / floor missing. Debug: low worker_busy_ratio post-coalesce. Recover: parallelism floor = ≥ cores partitions.
  • Coalescing skewed partitions together → one giant task. Root: greedy merge ignores max. Debug: post-coalesce task-size variance. Recover: don't merge across a hot partition; defer to skew-split (Phase 10).
  • Reading many shuffle files per task → FD pressure. Root: high fan-in. Debug: FD count. Recover: bound fan-in; segment coalescing.

⬜ Phase 9 — Adaptive Rule: Switch Join Strategy (shuffle-hash ↔ broadcast ↔ sort-merge)

Objectives

When a join's build side proves small at runtime, switch ShuffleHashJoin→BroadcastJoin (drop the build-side shuffle entirely); when both sides are pre-sorted, switch to SortMergeJoin. Conservative under sketch error (principle 14). Preserve output (I9).

Deliverable

A query whose build side the optimizer over-estimated runs with a broadcast join at runtime (one fewer shuffle), correct results, visible v0(ShuffleHash)→v1(Broadcast) in EXPLAIN + ReoptEvent.

Acceptance
  • On a "small-after-filter" build side, engine switches to broadcast; results match DuckDB; ≥ 30% wall-time improvement vs forced shuffle-hash.
  • Near-threshold build side → engine keeps shuffle-hash (no risky broadcast) — verified.
  • Schema/multiplicity invariant (I9) holds across all switch fixtures (differential vs non-adaptive).
Fixtures
  • plans/build_small_after_filter.json, plans/near_threshold_build.json, plans/presorted_smj.json. stats_traces/switch_join_*.json. Golden: golden_explain/p9_switch_diff.txt. Malformed: switch that breaks schema → rejected fixture.
Pitfalls
  • Broadcasting a side small in sample but large overall → OOM. Root: partial/estimated size. Debug: broadcast bytes ≫ threshold. Recover: only on materialized exact bytes; safety margin (I9, principle 14).
  • Switch changes join multiplicity (e.g., outer-join handling differs) → wrong results. Root: strategy-specific semantics bug. Debug: differential vs non-adaptive. Recover: validation hook rejects (I9).
  • Switch oscillation with skew-split (Phase 10). Root: two rules fighting. Debug: lattice trace. Recover: fixed rule order + monotone lattice (I2).
  • Dropping exchange already partially produced → orphan shuffle files. Root: switch after producer started. Debug: shuffle registry leftovers. Recover: only switch when consumer stage Pending (I3); GC orphan files.

⬜ Phase 10 — Adaptive Rules: Skew-Join Handling (split skewed partitions + replicate matching side) and Adaptive Aggregation (hash↔sort under pressure)

Objectives

Two pressure-driven rules. (a) Skew-join: detect skewed shuffle partitions (heavy hitters), split them into sub-partitions, replicate the matching side's corresponding partition → parallelize the hot key. (b) Adaptive aggregation: switch HashAggregate→SortAggregate (or disable partial agg) when the hash table spills excessively. Conserve rows (I10).

Deliverable

A join with one dominant key runs with that partition split across workers (no single hot worker); a low-reduction aggregation degrades to sort-agg under memory pressure without OOM. Both visible in EXPLAIN + ReoptEvent.

Acceptance
  • On single_hot_key fixture, skew-split reduces max-worker time ≥ 3× vs unsplit; results match DuckDB (I10 row conservation).
  • Aggregation under tight budget completes via sort-agg with no OOM; results exact.
  • Skew false-positive guard: uniform data triggers no split (verified).
Fixtures
  • skew/single_hot_key.arrow + plans/skew_join.json; plans/low_reduction_agg.json; stats_traces/skew_*.json. Golden: golden_explain/p10_skew_split.txt. Edge: skew/uniform_1e7.arrow (no split).
Pitfalls
  • Skew false positive → needless split + replication overhead. Root: ratio threshold only. Debug: split that didn't help (skew_splits up, no speedup). Recover: require ratio AND absolute size (principle 14).
  • Replication blow-up (replicate a huge matching side k×) → memory. Root: replicating large side. Debug: replicated bytes. Recover: only replicate when matching partition small; else sort-merge that partition.
  • Row loss/dup in split → wrong results. Root: sub-partition boundaries overlap/gap. Debug: count(splits) ≠ count(orig). Recover: I10 conservation assert → reject split.
  • Agg switch loses partial-state mid-flight. Root: switching a started agg. Debug: missing groups. Recover: only switch Pending final stage (I3).
  • Hash→sort switch but data unsorted → sort cost dominates. Root: switching too eagerly. Debug: sort time ≫ saved spill. Recover: switch only under genuine spill pressure (hysteresis).

⬜ Phase 11 — Dynamic Partition Pruning (DPP) + Full Integration + Plan-Versioned EXPLAIN + Operator API

Objectives

Add dynamic partition pruning: use a build-side's actual key values (collected at runtime) to prune the probe-side scan's partitions/row-groups before it runs. Finalize the public Optimizer/Executor API, full plan-versioned EXPLAIN, and end-to-end integration of all rules.

Deliverable

A star-schema query prunes the fact-table scan using dimension keys at runtime; all five adaptive rules cooperate; EXPLAIN shows the full plan-version history; stable public API.

Acceptance
  • DPP prunes ≥ 50% of fact-table partitions on a selective dimension filter (vs no DPP); results identical.
  • All-rules integration query: correct vs DuckDB; each applicable rule fires exactly once (I2); deterministic replay (I1).
  • Public API stable + documented (rustdoc); EXPLAIN diff golden matches.
Fixtures
  • plans/star_schema_dpp.json, plans/all_rules_integration.json. stats_traces/dpp_*.json. Golden: golden_explain/p11_full_diff.txt. Edge: plans/dpp_no_prune.json (non-selective → no pruning).
Pitfalls
  • DPP predicate too large (huge distinct set) → expensive to push/evaluate. Root: high-NDV build key. Debug: dynamic-filter size. Recover: switch to min/max range or Bloom filter above NDV threshold.
  • DPP false pruning (drops matching partitions) → wrong results. Root: predicate/stats mismatch. Debug: differential. Recover: only prune on sound partition stats; conservative (keep if unsure).
  • Rule interaction cycle (DPP changes stats → re-triggers an already-decided rule). Root: re-running rules. Debug: lattice trace. Recover: single pass, fixed order, monotone (I2).
  • Stale dynamic predicate from wrong PlanVersion. Root: version mismatch. Debug: event version tags. Recover: tag predicate with producing version.

⬜ Phase 12 — Deterministic Replay, Conformance Suite, Differential vs DuckDB/DataFusion, Fuzzing, Soak, Performance Gate

Objectives

Lock correctness + determinism + performance: deterministic replay harness (I1), full conformance suite (TPC-H Q1–Q22, TPC-DS subset, skew corpus), differential oracle, fuzzing of plan IR + stats traces + rules, soak + performance-regression gate. Wire metrics/tracing endpoints.

Deliverable

make conformance + make replay + make fuzz-smoke + make bench all green; metrics endpoint live; deterministic replay proven across the suite.

Acceptance
  • TPC-H Q1–Q22 results match DuckDB exactly (SF=1, SF=10).
  • 100% deterministic replay across conformance traces (I1) — identical version sequence + results.
  • Fuzz smoke (5 min/target) finds no panic/UB/oscillation; corpus retained.
  • Performance gate: within ±20% of DataFusion on TPC-H suite; no >10% regression.
  • Soak: 1 h adaptive workload — no FD/mem leak, replan budget never exceeded (I2).
Fixtures
  • conformance/plans/tpch_q{01..22}.json, tpcds_subset/*.json, skew/*. stats_traces/* for each. golden_explain/* snapshots. fuzz/corpus/*. Replay manifest cross-checks decisions.
Pitfalls
  • Replay diverges from live (non-determinism leaked in). Root: hidden clock/RNG/thread-order input. Debug: bisect decision inputs; replay diff. Recover: purge impure inputs (I1).
  • Differential float mismatch on aggregates. Root: associativity across thread merge. Debug: per-group diff. Recover: deterministic merge OR documented tolerance band.
  • Fuzz finds oscillation on adversarial stats. Root: lattice gap. Debug: minimized stats trace. Recover: tighten monotone lattice (I2).
  • Bench flakiness (noisy CI hosts). Root: shared runners. Debug: variance. Recover: pinned-core bench host, relative thresholds, multiple runs.
