318 — Adaptive Query Execution Engine from Scratch

Project Number: 318 Project Name: Adaptive Query Execution Engine from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build a single-node, multi-core Adaptive Query Execution (AQE) engine: a physical execution engine that re-optimizes the running physical plan using statistics observed during execution. Input is a resolved physical plan (operators + schemas + pre-bound expressions); output is row/column batches. The novelty is the feedback loop: stages run, emit runtime stats (row counts, byte sizes, NDV, heavy hitters, partition-size distribution, skew), and those stats gate re-optimization of downstream stages before they launch.

System boundaries (in scope):

  • Logical→physical planning baseline (Volcano/Cascades-style memo + cost model) sufficient to produce an initial plan and to re-plan a stage.
  • Physical operators: Scan, Filter, Project, HashJoin, SortMergeJoin, BroadcastJoin, HashAggregate, SortAggregate, Exchange/Shuffle, Sort, Limit.
  • Stage DAG: plan split at Exchange/materialization boundaries; stages are the unit of scheduling and the unit of re-optimization.
  • Runtime statistics: actual rows/bytes, NDV via HyperLogLog, heavy hitters via Count-Min, per-partition size histogram, skew detection.
  • Adaptive decisions: (a) coalesce shuffle partitions post-shuffle; (b) switch join strategy (shuffle-hash ↔ broadcast ↔ sort-merge); (c) skew-join split + replicate; (d) hash↔sort aggregation under memory pressure; (e) dynamic partition pruning (DPP).
  • Vectorized / morsel-driven execution over columnar RecordBatch; spill-to-disk for join/agg/sort; backpressure across exchange.
  • Observability: plan-versioned EXPLAIN, per-stage metrics, re-optimization event log, deterministic replay of plan + stats trace.

Explicit non-goals (deferred, gated PhaseDeferred):

  • SQL parser / binder / type system — input is a pre-bound physical plan. PhaseDeferred("Deferred Features Register").
  • Transactions, MVCC, durability, recovery of base tables — read-only executor. PhaseDeferred("Deferred Features Register").
  • Distributed multi-node execution beyond the exchange seam; the shuffle service is single-node disk-backed. PhaseDeferred("Phase 12").
  • Cost-based join enumeration beyond DPccp baseline; full Cascades rule set deferred. PhaseDeferred("Deferred Features Register") (cross-link #313).
  • GPU/SIMD-intrinsic kernels — portable scalar + autovectorized loops only. PhaseDeferred("Performance Engineering").
  • Streaming / continuous queries, UDF sandboxing beyond determinism flags. PhaseDeferred("Deferred Features Register").

Deployment model: a library crate (aqe-core) plus a thin aqe CLI/driver that loads a physical-plan JSON + Arrow/Parquet inputs, executes adaptively, prints plan-versioned EXPLAIN and a stats trace, and writes results to Arrow IPC. Embeds in a host DBMS as the execution layer beneath a planner.

Target users/operators/developers: query-engine engineers wiring AQE beneath an existing planner; data-infra engineers debugging skew/replan-thrash at 3 a.m.; learners who want the Spark-AQE / Photon / Presto-adaptive design built end to end.

Phase 0 deliverable (numbered crates/modules):

  1. aqe-types — RecordBatch, Schema, DataType, Buffer, plan IR (logical/physical), error enum.
  2. aqe-exec — push-based vectorized operators: Scan, Filter, Project.
  3. aqe-stage — stage cutter (split at exchange), StageGraph, stage scheduler (single-thread first).
  4. aqe-stats — runtime stats records + accumulators (rows/bytes; HLL/CMS land in Phase 3).
  5. aqe-plan — minimal physical planner: turn input IR into a StageGraph; serialize/deserialize plan.
  6. aqe-explain — plan-versioned EXPLAIN renderer (text + JSON).
  7. aqe — CLI driver: load plan + data, run a scan→filter→project→exchange→count, print EXPLAIN.

What later phases unlock: morsel scheduler + work-stealing (Phase 4); HashJoin/Agg + spill (Phase 5–6); the adaptive controller + replan trigger (Phase 7); partition coalescing (Phase 8); join-strategy switch (Phase 9); skew split + adaptive agg (Phase 10); DPP (Phase 11); replay + conformance + soak (Phase 12).

Timeline: Phase 0 = 6–14 weeks. Full plan = 5–8 months.

Recommended language: Rust (edition 2021, ≥1.78). Rationale: (a) ownership model makes operator buffer lifetimes, spill-file ownership, and exchange-channel handoff explicit and leak-free without GC pauses that would poison p99; (b) Send/Sync make the morsel scheduler's data-race freedom a compile-time property; (c) zero-cost abstractions + slices give vectorized loops the autovectorization a columnar engine needs; (d) Arrow-rs gives a battle-tested columnar buffer layer; (e) cargo fuzz, Miri, loom cover the fuzz/UB/concurrency-permutation testing AQE's adaptive control plane demands. Locked in ADR-001.

Prerequisites: relational algebra; Volcano/push execution model; columnar formats (Arrow null bitmap, offsets, dictionary); hash join vs sort-merge vs broadcast tradeoffs; sketches (HyperLogLog, Count-Min); cost-model basics; Rust borrow checker + Send/Sync; OS file I/O + mmap for spill; basic queueing/backpressure.

2. Why Build This

  • Unique systems knowledge: the control plane of execution. Most engines teach the data plane (operators, vectorization). AQE adds a closed feedback loop — observe → decide → re-plan — that is where Spark 3.x, Databricks Photon, Presto/Trino adaptive, and Snowflake get their real-world wins. Building it teaches why estimates are wrong and how to be robust to that.
  • Historical/architectural significance: the industry's admission that static cost-based optimization (System R, Volcano, Cascades) is necessary but insufficient on real skewed data. Spark AQE (2020) coalesced partitions, switched joins, and split skew at runtime; this project rebuilds that core.
  • Engineering muscles: stage scheduling; sketch-based cardinality; idempotent/deterministic re-optimization (the hard part — replanning must not oscillate); spill + backpressure; deterministic replay of a non-deterministic-looking system; plan versioning + observability.
  • Production concepts exercised: materialization boundaries, exchange/shuffle, skew handling, memory budgeting, backpressure, OOM containment, partial-stage recompute, telemetry-driven control.
  • Cross-links:
    • #52 Query Planner / #313 Query Optimizer + Cost Estimator — the planner that produces the initial plan and that Phase 7/Phase 9 re-invoke per stage.
    • #104 Vectorized OLAP Executor — the data-plane operators AQE schedules; shared RecordBatch/morsel vocabulary.
    • #206 Cost Model / #207 Columnar Vectorized Planner — the cost function fed by runtime stats in Phase 7.
  • Calibration value: after this you can debug any adaptive engine's replan log, reason about skew/coalescing/oscillation, and design feedback control that stays stable under bad statistics.

What Mastery Looks Like

  • You can split any physical plan at its true materialization boundaries and explain why each breaker ends a stage — built in Phase 0 (stage cutter) and Phase 1 (Stage DAG, I3).
  • You can design a control plane that is a pure function of sealed observations and prove it terminates — the determinism (I1) + no-oscillation (I2) discipline built in Phase 7 (controller + decision lattice).
  • You can choose a join strategy from runtime evidence and know exactly when broadcast is a trap — the error-bound-aware switch built in Phase 9 (and the conservative-rejection bias of P14).
  • You can detect and parallelize a single hot key without losing or duplicating a row — skew-split with row-conservation (I10), built in Phase 10.
  • You can size sketches to a target error and carry that error into a decision threshold — HLL/CMS engineering built in Phase 3, applied conservatively per P12/P14.
  • You can make every operator make progress under any memory budget via spill + backpressure — built in Phase 6 (memory manager, grace-hash, external sort) under P5/P6.
  • You can right-size post-shuffle parallelism and eliminate tiny-task overhead — partition coalescing (I8) built in Phase 8.
  • You can reproduce a "non-deterministic-looking" adaptive run bit-for-bit from a captured trace — the replay gate built in Phase 12 (I1), the skill that makes adaptive engines debuggable in production.

Per-box dense notes:

  • Caller / PhysicalPlan — pre-bound; expressions resolved to slots + types; no parsing. Trust boundary: malformed plan rejected by validator (§8.7) before scheduling.
  • Planner / Re-planner — produces v0 plan from static catalog; the same code re-plans a single downstream stage given merged static⊕runtime stats. Determinism: same (plan, stats) → same output (no clock/RNG in decisions). Cross-link #313.
  • Stage cutter — splits at every Exchange and at blocking operators (sort, hash-agg-final, hash-join-build, top-K). A stage is the unit of (re-)optimization; only unstarted stages may be re-planned.
  • Adaptive controller — the heart. Concurrency boundary: runs between stage completion and downstream stage launch; single-writer to the plan (serialized) → no torn plans. Enforces NO-OSCILLATION (each stage re-planned ≤ once per input edge; monotone decision lattice §7).
  • Morsel scheduler — Leis 2014 morsels (~100K-row slices), per-NUMA queues, work-stealing. Push-based; backpressure from memory manager throttles morsel dispatch.
  • Stats collector — accumulates exact rows/bytes + HLL (NDV) + Count-Min (heavy hitters) + partition-size histogram during stage execution; sealed into immutable RuntimeStats at stage completion.
  • Operator layer — push model open/push/finish; streaming operators pass batches; pipeline breakers (build, agg, sort) buffer and may spill. Shared RecordBatch vocabulary with #104.
  • Memory manager — per-operator reservation against a global budget; on pressure → spill (join/agg/sort) then backpressure; hard ceiling → OOM containment (fail the operator, not the process, when re-runnable).
  • Exchange / shuffle — hash-partition output to N shuffle files; records per-partition byte sizes (input to coalescing/skew). Backpressure to producers when consumer slow. Single-node disk shuffle; multi-node deferred.
  • Storage / spill — append-only spill segments + manifest + shuffle-file registry maps (stage, partition)→file; file loss triggers recompute of producing stage (§Failure Modes & Recovery).
  • Observability — plan-versioned EXPLAIN (every replan bumps version), per-stage metrics, ReoptEvent log; the REPLAY harness re-feeds a captured stats trace and asserts identical decisions (determinism gate, Phase 12).

6. Design Principles

  1. Estimates are wrong; measurements are truth. Static cost estimates only seed v0; every adaptive decision prefers observed RuntimeStats over catalog estimates. Tradeoff: decisions deferred until a stage materializes. Violation: trusting estimates → the exact skew/broadcast mistakes AQE exists to fix.
  2. Re-optimization is monotone and idempotent (NO OSCILLATION). Replanning a stage moves it strictly forward on a decision lattice (e.g., parallelism only coalesces, never re-splits within a query). Violation: plan thrash, livelock, non-terminating replan loop.
  3. Only unstarted stages are re-planned. A stage in flight is immutable. Violation: torn plan / data already partitioned for a strategy you abandoned.
  4. Determinism of the control plane. No wall-clock, RNG, or thread-order input to adaptive decisions; decisions are a pure function of (plan, sealed stats). Violation: non-reproducible replans → undebuggable production incidents; replay harness fails.
  5. Backpressure everywhere. Every producer→consumer edge (operator pipe, exchange) is bounded; full downstream throttles upstream. Violation: unbounded buffering → OOM that spill cannot save.
  6. Spill is a first-class path, not an error. Join/agg/sort must make progress under any memory budget by spilling. Violation: OOM kills the process instead of degrading gracefully.
  7. Materialization boundaries are the only re-opt seams. Decisions are taken at exchange/breaker edges where data is durable and counted. Violation: re-planning mid-pipeline corrupts in-flight state.
  8. Plan is versioned and explainable. Every replan bumps PlanVersion; EXPLAIN shows v0 vs final + each ReoptEvent. Violation: operators cannot tell which plan ran; postmortems impossible.
  9. Bounded resource usage. Per-operator memory reservation, FD budget, replan budget are all explicit ceilings. Violation: one skewed query starves the rest.
  10. Skew is the common case, not the exception. Heavy-hitter detection (Count-Min) + partition histograms are always on; skew-split is routine. Violation: one hot key serializes a whole stage.
  11. Push, vectorized, morsel-driven. Operators consume batches via push; the scheduler owns parallelism via morsels. Tradeoff: harder operator API than pull. Violation: per-row virtual dispatch destroys cache locality + throughput.
  12. Stats are cheap sketches, not exact scans. NDV via HLL, frequency via CMS — bounded memory, single pass. Violation: exact NDV doubles the work AQE was supposed to save.
  13. Crash-only, query-scoped. No mid-query durability; a crash restarts the query. Spill/shuffle files are scratch, GC'd on exit. Violation: recovery code complexity for a read-only engine that doesn't need it.
  14. Conservative replanning under uncertain stats. If a sketch's error bound makes a decision marginal, keep the safe plan (e.g., don't broadcast near the threshold). Violation: a CMS overcount triggers a broadcast that OOMs.
  15. Observability is not optional. Metrics, ReoptEvent log, and replay capture are emitted on the hot path by default (cheap counters). Violation: you find out about thrash from a customer, not a dashboard.

8. Domain Model

8.1 Logical algebra (input, abstract)

EBNF (logical plan, pre-bound):

LogicalPlan := Scan | Filter | Project | Join | Aggregate | Sort | Limit | Exchange
Scan        := "Scan" Table ColumnList [Predicate]
Filter      := "Filter" Expr LogicalPlan
Project     := "Project" ExprList LogicalPlan
Join        := "Join" JoinType OnExpr LogicalPlan LogicalPlan
Aggregate   := "Aggregate" GroupKeys AggExprList LogicalPlan
Sort        := "Sort" SortKeys LogicalPlan
Limit       := "Limit" N LogicalPlan
JoinType    := "Inner" | "Left" | "Right" | "Full" | "Semi" | "Anti"
Expr        := Col | Lit | Expr BinOp Expr | Fn "(" ExprList ")"   ; each Expr carries deterministic:bool

8.2 Physical algebra (what the engine runs)

PhysicalOp := Scan | Filter | Project
            | HashJoin | SortMergeJoin | BroadcastJoin
            | HashAggregate | SortAggregate
            | Exchange | Sort | Limit
Exchange   := "Exchange" Partitioning PhysicalOp     ; Partitioning = Hash(keys,n) | RoundRobin(n) | Broadcast | SinglePartition

Pipeline breakers (materialize, end a stage): HashJoin(build side), HashAggregate(final), SortMergeJoin(sort inputs), Sort, Exchange. Streaming operators: Scan, Filter, Project, BroadcastJoin(probe), HashAggregate(partial), Limit.

8.3 Stage DAG

  • Stage = maximal chain of streaming operators terminated by one breaker/exchange.
  • Edge A→B ⇔ B consumes A's materialized output (shuffle files or build hash table).
  • Stage states: Pending → Scheduled → Running → Materialized → Consumed (+ Failed, Recomputing).
  • A stage is re-optimizable iff Pending and all its input stages are Materialized (their stats sealed).

Worked example — SELECT o_custkey, SUM(o_total) FROM orders JOIN customer ON c_id=o_custkey GROUP BY o_custkey:

S0 Scan(orders)+Filter ──Exchange Hash(o_custkey)──┐
                                                    ├─► S2 HashJoin(build=cust) ─Exchange Hash(o_custkey)─► S3 HashAgg(final)
S1 Scan(customer)      ──Exchange Hash(c_id)──────┘

After S1 materializes: if customer actual bytes ≪ broadcast threshold → controller rewrites S2's join to BroadcastJoin, deletes the S1 exchange, and re-plans S2 as a streaming probe (one fewer shuffle). PlanVersion v0→v1.

8.4 Runtime statistics records

RuntimeStats { stage_id, rows: u64, bytes: u64,
               per_col: Vec<ColStats>,           // NDV(HLL), null_count, min/max if cheap
               partition_sizes: Vec<u64>,        // bytes per shuffle partition
               heavy_hitters: CountMinTopK,       // (key, est_freq) with error bound
               skew: SkewReport }                 // max/median partition ratio, hot keys
ColStats { col_id, ndv_hll: Hll, nulls: u64, min: Option<Scalar>, max: Option<Scalar> }
SkewReport { max_partition: u64, median_partition: u64, ratio: f64, hot_keys: Vec<(Scalar, u64)> }

Sealed (immutable) at stage Materialized. Sketch errors: HLL relative err ≈ 1.04/√m; CMS overestimate ≤ εN with prob 1−δ. Decisions carry these bounds (principle 14).

8.5 Re-optimization state machine (per downstream stage)

                 input stages Materialized
   Pending ───────────────────────────────► Evaluable
                                               │ run rule set (ordered, fixpoint-free, ≤1 pass)
                 no rule fires                  ▼
   Evaluable ──────────────► Scheduled (plan locked, PlanVersion++ if changed)
        │ a rule fires (Coalesce|SwitchJoin|SkewSplit|AggMode|DPP)
        └──► Rewrite(stage) ──► validate(schema,multiplicity,monotone) ──► Scheduled
   validate fails ──► keep original plan, log RejectedReopt ──► Scheduled

Rule order (deterministic): DPP → SwitchJoin → SkewSplit → CoalescePartitions → AggMode. Single pass, no fixpoint → guarantees I2.

8.6 State-transition table (join strategy under runtime stats)

ShuffleHashJoin build ≤ broadcast_thr (w/ margin) low SwitchJoin BroadcastJoin (drop build exchange)
ShuffleHashJoin build ≫ thr ratio > skew_thr SkewSplit ShuffleHashJoin + split hot partitions, replicate other side
ShuffleHashJoin both inputs pre-sorted (order property) low SwitchJoin SortMergeJoin
BroadcastJoin (planned) build grew > thr (rare; partial stats) — RejectedReopt keep ShuffleHashJoin (conservative)

8.7 Malformed / failure-path examples

  • Plan references unbound column → validator error PlanError::UnresolvedColumn (pre-schedule).
  • Exchange Hash([]) (empty keys) → PlanError::EmptyPartitioning.
  • Non-deterministic UDF in join key → reopt disabled for that subtree (I14); nondet_expr_seen emitted.
  • Stats sealed but a late write arrives → dropped + logged (I4).
  • Skew split where splits don't conserve rows → reopt rejected (I10), original plan runs.

  • Skip coalescing when partitions already well-sized or downstream needs fixed partitioning (e.g., co-located join).
  • Conservative: never coalesce below a parallelism floor (keep cores busy).

8.3 Deliverable

8.4 Acceptance Criteria

  • Coalescing reduces task count ≥ 5× on a tiny-partition fixture with no result change (differential).
  • End-to-end wall-time improves ≥ 20% on that fixture (scheduling overhead reclaimed).
  • Post-partition count ≤ pre (I8) always; never below parallelism floor.

8.5 Conformance Fixtures

  • Reading many shuffle files per task → FD pressure. Root: high fan-in. Debug: FD count. Recover: bound fan-in; segment coalescing.

8.7 Performance Concerns

Coalescing is a manifest rewrite (no data movement) → near-free decision. Larger tasks amortize dispatch but must stay cache-reasonable. Target size trades parallelism vs overhead — tunable advisory_bytes.

8.8 Edge Cases

All partitions tiny (coalesce to floor); all partitions large (no-op); single partition; one huge + many tiny (don't merge huge); partition count below floor already (no-op).

8.9 Failure Analysis

Coalescing changes results = bug (must not): differential gate (I9). Blast radius: query. Containment: coalescing only changes task grouping, not data; differential proves equivalence.

8.10 Operational Notes

Metrics: coalesced_partitions{from,to}, coalesce_task_size_p99, advisory_bytes. EXPLAIN: per-exchange partitions: 2000→200 (coalesced). Runbook note in scaling-debug.

Phase 9 — Adaptive Rule: Switch Join Strategy (shuffle-hash ↔ broadcast ↔ sort-merge)

9.1 Objectives

When a join's build side proves small at runtime, switch ShuffleHashJoin→BroadcastJoin (drop the build-side shuffle entirely); when both sides are pre-sorted, switch to SortMergeJoin. Conservative under sketch error (principle 14). Preserve output (I9).

9.2 Detailed Implementation Steps

  • aqe-adaptive/rules/switch_join.rs: on input stage materialized, compare build-side actual bytes vs broadcast_threshold (default 10 MiB) with safety margin (account HLL/size error bound).
    • build ≤ threshold·(1−margin) → rewrite downstream join to BroadcastJoin; delete the build-side Exchange; probe side streams (no shuffle).
    • both inputs carry an interesting-order property + low skew → SortMergeJoin.
    • never switch to broadcast from partial stats (only on a materialized side); never broadcast near threshold (I9, conservative).
  • Validate: output schema + multiplicity unchanged (I9); join type/semantics preserved.
  • Update StageGraph: removed exchange → fewer stages; PlanVersion++.

9.3 Deliverable

A query whose build side the optimizer over-estimated runs with a broadcast join at runtime (one fewer shuffle), correct results, visible v0(ShuffleHash)→v1(Broadcast) in EXPLAIN + ReoptEvent.

9.4 Acceptance Criteria

  • On a "small-after-filter" build side, engine switches to broadcast; results match DuckDB; ≥ 30% wall-time improvement vs forced shuffle-hash.
  • Near-threshold build side → engine keeps shuffle-hash (no risky broadcast) — verified.
  • Schema/multiplicity invariant (I9) holds across all switch fixtures (differential vs non-adaptive).

9.5 Conformance Fixtures

  • plans/build_small_after_filter.json, plans/near_threshold_build.json, plans/presorted_smj.json. stats_traces/switch_join_*.json. Golden: golden_explain/p9_switch_diff.txt. Malformed: switch that breaks schema → rejected fixture.

9.6 Pitfalls

  • Broadcasting a side small in sample but large overall → OOM. Root: partial/estimated size. Debug: broadcast bytes ≫ threshold. Recover: only on materialized exact bytes; safety margin (I9, principle 14).
  • Switch changes join multiplicity (e.g., outer-join handling differs) → wrong results. Root: strategy-specific semantics bug. Debug: differential vs non-adaptive. Recover: validation hook rejects (I9).
  • Switch oscillation with skew-split (Phase 10). Root: two rules fighting. Debug: lattice trace. Recover: fixed rule order + monotone lattice (I2).
  • Dropping exchange already partially produced → orphan shuffle files. Root: switch after producer started. Debug: shuffle registry leftovers. Recover: only switch when consumer stage Pending (I3); GC orphan files.

9.7 Performance Concerns

Broadcast saves a full shuffle (big win) but replicates build to all workers (memory × workers) — only worth it when build ≪ threshold. SMJ avoids hash build but needs sorted inputs (free only when order already present). Decision is cheap (compare bytes).

9.8 Edge Cases

Build side exactly at threshold (keep safe = shuffle); build empty (broadcast trivial); both sides small (broadcast smaller); outer join (semantics-preserving switch only); build side grew vs estimate (don't broadcast).

9.9 Failure Analysis

Wrong switch → broadcast OOM (stage abort) or wrong results (differential blocks). Containment: conservative threshold + I9 validation. Blast radius: one join stage.

9.10 Operational Notes

Metrics: join_strategy{stage,from,to}, broadcast_bytes, switch_rejected{reason}. EXPLAIN: join: ShuffleHash→Broadcast (build=8MiB < 10MiB). Runbook: docs/runbooks/skew.md cross-refs join choice.

Phase 10 — Adaptive Rules: Skew-Join Handling (split skewed partitions + replicate matching side) and Adaptive Aggregation (hash↔sort under pressure)

10.1 Objectives

Two pressure-driven rules. (a) Skew-join: detect skewed shuffle partitions (heavy hitters), split them into sub-partitions, replicate the matching side's corresponding partition → parallelize the hot key. (b) Adaptive aggregation: switch HashAggregate→SortAggregate (or disable partial agg) when the hash table spills excessively. Conserve rows (I10).

10.2 Detailed Implementation Steps

  • aqe-adaptive/rules/skew_split.rs: from producer SkewReport, a partition with size > skew_factor × median AND > absolute floor is "skewed". Split it into k sub-partitions (secondary hash / row ranges); replicate the other join input's matching partition k times (so each sub-partition has its full probe set). Union of sub-partitions = original (I10).
  • aqe-adaptive/rules/agg_mode.rs: if partial-agg hash-table spill ratio exceeds threshold (low group reduction) → drop partial agg (stream to final) OR switch final to SortAggregate (sort then streaming-group) to bound memory.
  • Validate: skew split conserves rows (count(splits)=count(orig), I10); agg switch preserves group/aggregate semantics.
  • Combine with switch-join via fixed rule order (SkewSplit after SwitchJoin, §8.5) → no oscillation (I2).

10.3 Deliverable

A join with one dominant key runs with that partition split across workers (no single hot worker); a low-reduction aggregation degrades to sort-agg under memory pressure without OOM. Both visible in EXPLAIN + ReoptEvent.

10.4 Acceptance Criteria

  • On single_hot_key fixture, skew-split reduces max-worker time ≥ 3× vs unsplit; results match DuckDB (I10 row conservation).
  • Aggregation under tight budget completes via sort-agg with no OOM; results exact.
  • Skew false-positive guard: uniform data triggers no split (verified).

10.5 Conformance Fixtures

  • skew/single_hot_key.arrow + plans/skew_join.json; plans/low_reduction_agg.json; stats_traces/skew_*.json. Golden: golden_explain/p10_skew_split.txt. Edge: skew/uniform_1e7.arrow (no split).

10.6 Pitfalls

  • Skew false positive → needless split + replication overhead. Root: ratio threshold only. Debug: split that didn't help (skew_splits up, no speedup). Recover: require ratio AND absolute size (principle 14).
  • Replication blow-up (replicate a huge matching side k×) → memory. Root: replicating large side. Debug: replicated bytes. Recover: only replicate when matching partition small; else sort-merge that partition.
  • Row loss/dup in split → wrong results. Root: sub-partition boundaries overlap/gap. Debug: count(splits) ≠ count(orig). Recover: I10 conservation assert → reject split.
  • Agg switch loses partial-state mid-flight. Root: switching a started agg. Debug: missing groups. Recover: only switch Pending final stage (I3).
  • Hash→sort switch but data unsorted → sort cost dominates. Root: switching too eagerly. Debug: sort time ≫ saved spill. Recover: switch only under genuine spill pressure (hysteresis).

10.7 Performance Concerns

Skew-split: replication cost (k× small side) vs serialization savings on the hot key — net win only for genuine skew. Sub-partition k tuned to worker count. Sort-agg trades hash-table memory for sort cost; only under pressure. CMS heavy-hitter lookup is cheap.

10.8 Edge Cases

Multiple hot keys (split each); hot key whose matching side is also large (sort-merge fallback); all keys uniform (no split); single-group agg (no benefit); agg already-sorted input (sort-agg free).

10.9 Failure Analysis

Bad split → wrong results (I10 differential blocks) or overhead (no-speedup metric). Replication OOM → stage abort. Containment: conservative thresholds + row-conservation validation. Blast radius: one join/agg stage.

10.10 Operational Notes

Metrics: skew_splits{key}, replicated_bytes, skew_max_worker_ratio_before/after, agg_mode_switch{from,to}, partial_reduction_ratio. EXPLAIN: partition 7 skew-split ×4 (hot key=...); matching side replicated ×4. Runbook: docs/runbooks/skew.md.

11.1 Objectives

11.6 Pitfalls

  • DPP predicate too large (huge distinct set) → expensive to push/evaluate. Root: high-NDV build key. Debug: dynamic-filter size. Recover: switch to min/max range or Bloom filter above NDV threshold.
  • DPP false pruning (drops matching partitions) → wrong results. Root: predicate/stats mismatch. Debug: differential. Recover: only prune on sound partition stats; conservative (keep if unsure).

DPP saves probe I/O (often the biggest table) — large win when selective. Distinct-set vs Bloom vs range trades predicate size vs pruning precision. Pruning is metadata-level (no data scan). Rule pipeline runs once per stage boundary (cheap).

11.8 Edge Cases

11.9 Failure Analysis

General recovery posture: crash-only, query-scoped — no mid-query durability; a fatal failure aborts and the query is re-run from scratch. Deterministic stages can be recomputed on shuffle-file loss without full restart.

Documented motivation (why this whole control plane exists). Leis, Gubichev, Mirchev, Boncz, Kemper, Neumann — "How Good Are Query Optimizers, Really?" (PVLDB Vol. 9 No. 3, 2015), the Join Order Benchmark study — measured cardinality-estimation error across real query optimizers and found that estimation errors grow with the number of joins and that even small per-relation errors compound multiplicatively along a join tree, routinely producing estimates off by orders of magnitude and, in turn, catastrophic plan choices (e.g. a hash/broadcast decision made on a wrong size). The paper's empirical conclusion — that good cardinality estimates matter more than the cost model or the plan-enumeration algorithm, and that estimates are systematically unreliable on real data — is the direct, published justification for runtime adaptation: this engine treats v0 cardinalities as guesses (P1) and lets sealed RuntimeStats (§8.4) override them at every materialization boundary. The "Stats unavailable/wrong" and "OOM (broadcast/replication)" failure classes above are exactly the regimes that study quantified; the conservative-rejection bias (P14) and error-bound-aware thresholds (Phase 9, Phase 10) are the engineered response. (No vendor-specific production incident is cited here because none is publicly attributable with confidence; the JOB study is the load-bearing, verifiable finding.)

Scalability Analysis

  • Bottlenecks: shuffle write/read IO (mitigated by coalescing + sequential IO); single hot key (mitigated by skew-split); controller is single-writer but runs only at stage boundaries (low frequency → not a bottleneck).
  • Scaling ceilings: single-node cores (work-stealing scales to physical cores); RAM (spill extends beyond); NVMe bandwidth (spill/shuffle ceiling).
  • Horizontal scaling: the Exchange operator is the seam; a future distributed scheduler attaches there (deferred). Stage DAG + materialization boundaries already model distributed execution.
  • Vertical scaling: morsels + coalescing right-size parallelism; NUMA-local scheduling.
  • Sharding/partitioning: hash-partitioned shuffle; coalescing tunes partition count; skew-split sub-partitions hot keys.
  • Replication pressure: broadcast/skew-replication bounded by conservative size thresholds.
  • Coordination overhead: single-writer controller serializes plan mutations — bounded because decisions are infrequent (per stage boundary) and cheap (sketch comparisons).
  • Network fanout: N/A single-node (deferred).
  • Scheduler saturation: morsel dispatch overhead ≤1%; coalescing prevents tiny-task saturation.
  • Storage growth: spill/shuffle scratch only, GC'd on query end; no persistent growth.
  • Metadata scaling: StageGraph + ReoptEvent log are O(stages); event log append-only, bounded per query.

Why this terminates (I2): each Pending stage (S3, S5, S6) is evaluated exactly once, when all its inputs are Materialized. The rule list is a single fixed-order pass per stage; the decision lattice records which decisions were applied and refuses any regression (e.g., once S5's parallelism coalesced to 48 it can never re-split to 200). No rule re-triggers another rule's already-decided stage → no cycle.

Why this is deterministic (I1): every decision input is a sealed RuntimeStats value (exact rows/bytes + fixed-seed sketches). No wall-clock, no RNG, no thread-completion-order. Replaying the captured stats_trace reproduces the identical v0→v5 sequence and identical ReoptEvent log, byte for byte.

EXPLAIN renders all six ReoptEvents inline with their triggering stats and error bounds. A non-adaptive engine would have shuffled 12M rows twice, serialized the hot key on one worker, and scattered work across 11,990 tiny tasks — the exact failure modes AQE exists to remove.

Failure-path variant (conservative rejection): suppose at t=2 the dim1 build measured 9.8 MiB (just under the 10 MiB threshold but inside the error margin). The SwitchJoin rule computes 9.8 MiB > threshold·(1−margin) = 9.0 MiB → marginal → RejectedReopt logged, ShuffleHashJoin kept (principle 14). The query is slower but never risks a broadcast OOM. This is the bias the whole system is tuned for: a correct slow plan beats a fast plan that might fall over.

Mental Models & First Principles

The compressed intuitions a principal engineer holds about an adaptive executor. Each: the insight, what it predicts, the bug class you ship without it, and where this blueprint applies it.

MM1 — Cardinality estimates compound; by the 4th join the optimizer's guess can be off by orders of magnitude. A per-relation selectivity error of, say, 4× on each of four joins multiplies to ~256× at the top — the estimate is no longer a number, it's a rumor. Predicts: the deeper the join tree, the more the v0 plan is a coin flip, and the more value there is in waiting for a materialized count. Bug without it: you trust the planner's size estimate and broadcast a "small" table that is actually huge. Applied: §6 P1, Phase 7 (replan trigger), §Failure Modes & Recovery (the Leis 2015 JOB finding).

MM2 — The only honest number is the one a stage already produced. Static catalog stats describe the table; runtime stats describe this query's data after these filters. Only the latter is causal for the next decision. Predicts: the best decisions are taken at materialization boundaries, never mid-pipeline. Bug without it: re-optimizing on an estimate (or a sample) and committing to a partitioning the real data won't honor. Applied: §6 P1/P7, §8.3 (re-optimizable iff inputs Materialized), Phase 8/9/10.

MM3 — Adaptivity without monotonicity is a livelock. If a rule can both split and un-split (or broadcast and un-broadcast) the same stage, two rules can chase each other forever. The fix is a decision lattice on which every move is one-way. Predicts: a correct adaptive engine re-plans each stage a bounded number of times — here, ≤ once per input edge. Bug without it: replan thrash, version churn, a query that never launches its next stage. Applied: §6 P2, I2, §8.5 (single fixed-order pass), Phase 7.

MM4 — A control plane that reads the wall clock is unreproducible. If any decision input is time, RNG, or thread-completion order, the same query takes different plans on different runs and no postmortem can ever reconstruct what happened. Predicts: determinism is purchased by making decisions a pure function of sealed stats. Bug without it: "it only repros in prod," replay diverges, the on-call engineer is blind. Applied: §6 P4, I1/I4, Phase 7, Phase 12 (replay gate).

MM5 — Spill is a code path, not an error path. An operator that can only succeed when its working set fits RAM is a time bomb on skewed data. Designing spill in from the start means the worst case is slow, not dead. Predicts: every breaker (join build, agg, sort) has a partition-to-disk fallback and the memory manager triggers it before the ceiling. Bug without it: one fat partition OOMs the process and kills every concurrent query. Applied: §6 P6, I6, Phase 6 (grace-hash, external sort).

MM6 — A sketch is a number with an error bar, and the error bar belongs in the decision. An HLL NDV or a Count-Min frequency is not exact; using it as if it were turns a measurement uncertainty into a wrong plan. Predicts: thresholds carry a safety margin sized to the sketch's error, and marginal calls keep the safe plan. Bug without it: a CMS overcount triggers a skew-split that doesn't help, or an HLL underestimate triggers a broadcast that OOMs. Applied: §6 P12/P14, §8.4 (error bounds), Phase 3, Phase 9.

MM7 — Parallelism has a floor and a ceiling, and both are wrong by default. Too many tiny post-shuffle partitions drown in dispatch overhead; too few starve cores. The right count is data-dependent and only knowable after the shuffle. Predicts: you right-size parallelism down after measuring partition sizes (coalescing), but never below a core-count floor. Bug without it: 11,990 tiny tasks, or 4 giant ones on a 32-core box. Applied: I8, Phase 8 (coalesce), §Scalability Analysis.

MM8 — Skew is the default, not the exception, so detect it always and split conservatively. Real join keys are Zipfian; one key often dominates. Splitting a hot partition parallelizes it, but replicating the other side has a cost, so split only on genuine skew. Predicts: heavy-hitter detection runs on every stage, but a split fires only when ratio AND absolute size cross a threshold. Bug without it: one hot key serializes a whole stage on one worker; or needless splits add overhead with no speedup. Applied: §6 P10/P14, I10, Phase 10.

MM9 — The materialization boundary is simultaneously the durability seam, the counting seam, and the only safe re-plan seam. These three coincide on purpose: data is on disk (so a switch can drop an exchange), it is fully counted (so stats are exact), and nothing downstream has started (so a rewrite tears nothing). Predicts: you cannot adapt where you cannot count, and you cannot count where you have not materialized. Bug without it: mid-pipeline re-plan corrupting in-flight partitioned state. Applied: §6 P3/P7, I3, §8.3.

MM10 — Backpressure is the only thing standing between "slow consumer" and "OOM." Every producer→consumer edge must be bounded; an unbounded queue converts a transient slowdown into an out-of-memory kill that no spill can rescue (because the buffer, not the operator state, is what grew). Predicts: full downstream throttles upstream before memory is exhausted; the DAG is acyclic so this never deadlocks. Bug without it: a saturated exchange buffers gigabytes and dies. Applied: §6 P5, I5, Phase 4 (scheduler backpressure), Phase 6 (spill-then-backpressure).

Spark SQL AQE. The direct blueprint for this blueprint's three flagship rules. Its one defining choice is to re-optimize only at shuffle-map-stage boundaries using exact map-output statistics — coalescing partitions, flipping to a broadcast join, and splitting skew. That wins precisely in its niche: large distributed shuffles where partition sizes are wildly data-dependent and a coordinator can afford a planning round-trip between stages. This engine adopts the same seam and the same three rules, but single-node and with first-class deterministic replay (which Spark AQE does not provide).

Microsoft SQL Server Adaptive Query Processing. Its defining choice is finer granularity: an adaptive join operator decides hash-vs-nested-loop at runtime once it has buffered enough rows to compare against a threshold, plus memory-grant feedback that learns a query's true memory need across repeated executions, and interleaved execution that materializes a multi-statement table-valued function's true cardinality before optimizing the rest. That wins in a transactional/analytic mixed engine running the same parameterized query many times, where cross-execution learning pays off — a regime this read-only, per-query engine deliberately does not target.

Trino / Presto. Its defining choice is to stay largely with a cost-based static plan and add dynamic filtering: a build side's join-key values become a runtime filter pushed to the probe-side scan to prune partitions/splits — conceptually the same idea as this engine's DPP (Phase 11). It wins for distributed star-schema queries over a coordinator where pruning the fact-table scan is the dominant lever; its distributed-coordinator assumptions are exactly the ones this single-node design sheds.

DuckDB. The instructive contrast: a state-of-the-art vectorized, push-based, morsel-parallel engine that performs essentially no runtime re-optimization — it commits to a cost-based plan and executes it extremely fast. It wins on the enormous class of queries where the static plan is already good and the cost of adaptation would only add latency (interactive, embedded analytics over data that fits memory). It is this engine's data-plane sibling (shared push/morsel/vectorized vocabulary) and its differential oracle (§Testing & Verification Strategy) — and the clearest evidence that adaptivity is a separable control plane bolted onto a fast data plane, not a property of the operators themselves.

Two further points of reference (static end of the spectrum). PostgreSQL is the canonical static cost-based optimizer with histograms and dynamic-programming join enumeration and no runtime adaptation — its plans can be excellent on well-estimated OLTP-shaped queries and pathological on the deep-join, badly-estimated queries the Leis 2015 JOB study targets (§Failure Modes & Recovery), which is precisely the gap this engine fills. Oracle Adaptive Plans sit between Postgres and this design: the optimizer ships a plan with built-in alternatives (e.g. nested-loop vs hash join) gated by a runtime statistics collector that picks the branch once enough rows flow — a coarser, plan-embedded form of the switch-join idea (Phase 9) that wins when you want adaptation without a materialization seam but cannot express the partition-coalescing or skew-split rules a shuffle boundary unlocks.

Synthesis. Reading down the table, the design space is organized by one axis — how late, and at what granularity, do you commit? Eddies commit per tuple (maximal adaptivity, maximal per-row cost); this engine and Spark commit per stage (exact stats, bounded cost); SQL Server/Oracle commit per operator with embedded alternatives (no seam needed, narrower rule set); Postgres/DuckDB commit at plan time (zero runtime cost, full exposure to estimation error). This engine deliberately sits at the per-stage point because the materialization seam (MM9) makes exact counting free and deterministic replay (I1) cheap — the same reasons Spark AQE chose it — while shedding Spark's distributed-coordinator weight.

A second, orthogonal axis is statistics granularity: exact runtime counts (this engine's rows/bytes/partition-sizes, and Spark's map-output sizes) versus sampled or estimated inputs (a sample-based mid-query reoptimizer, or any plan-time histogram). This engine deliberately makes its gating decisions on exact materialized counts and reserves sketches (HLL/CMS, with explicit error bounds, §8.4) only for quantities that are infeasible to count exactly cheaply — NDV and heavy-hitter frequency — and then carries those error bounds into the threshold (P14). The design rule is: measure exactly where you can, sketch where you must, and never let a sketch's uncertainty silently become a plan commitment.

Back-of-Envelope Capacity Model

The numbers an engineer computes before designing, each derived step-by-step from the System Constraints table (§4) and the per-phase defaults the spec fixes. Formula shown; assumptions stated.

C1 — Per-core row throughput. §4: ≥ 200 M rows/s aggregate across 8 cores (scan→filter→agg, int columns). per_core = 200e6 / 8 = 25 M rows/s/core. This is the budget each worker pipeline must hit on int columns; missing it by 10% trips the perf gate (§Performance Engineering).

C2 — Morsels dispatched per second per core. §4: morsel ≈ 100K rows. morsels/s/core = 25e6 / 100e3 = 250 morsels/s/core → across 8 cores = 2,000 morsels/s. The scheduler's dispatch + steal bookkeeping must cost ≪ 1 / 2000 s = 500 µs per morsel to keep overhead ≤ 1% of wall-time (§4 stage-scheduling-overhead) — this is why morsels are ~100K rows, not 1K.

C3 — Per-morsel resident bytes (cache budget). Assume a hot pipeline touches ~4 int64 columns. bytes_per_morsel = 100e3 rows × 4 cols × 8 B = 3.2 MB. That exceeds a typical 256 KB–1 MB L2, so the column slice per kernel (100K × 8 B = 800 KB) is the real residency unit — confirming §4's "≤ L2 per morsel column slice" and the column-at-a-time kernel design (Phase 2).

C4 — Memory budget vs concurrent operator reservations. §4: default budget 4 GiB. With per-operator reservations and (say) one build hash table + one agg table + sort runs live at once across 8 workers, a safe steady-state per-worker reservation ceiling is 4 GiB / 8 ≈ 512 MiB/worker before the memory manager (Phase 6) must spill. Cross-check: a single build side larger than ~512 MiB on a worker is a spill candidate — consistent with the "build side = 5× budget still completes" acceptance (Phase 6, N.4).

C5 — Spill disk footprint. §4: spill amplification ≤ 1.5×. A join whose build side is 5× the budget (5 × 4 GiB = 20 GiB logical) costs at most 20 GiB × 1.5 = 30 GiB on NVMe. Formula: spill_disk = logical_spilled_bytes × amplification. This sizes the scratch volume the container must bind (§Operational Readiness, deployment topology).

C6 — Post-shuffle partition count from advisory size. Phase 8: advisory_bytes default 64 MiB. A shuffle stage emitting S bytes coalesces to ceil(S / 64 MiB) partitions, floored at core count. Example: a 12M-row joined stage at ~64 B/row ≈ 768 MB → ceil(768 / 64) = 12 partitions (then floored to ≥ cores). Formula: parts = max(cores·k, ceil(stage_bytes / advisory_bytes)) — the rule that turned 11,990 tiny partitions into 48 in the Domain Deep Dive.

C7 — FD pressure from coalesced fan-in. §4: FD budget ≤ 256. If pre-coalesce there are P shuffle files and post-coalesce M tasks, mean fan-in = P/M files per task. With P = 2000, M = 200 → 10 files/task; a worker reading 8 tasks concurrently holds 8 × 10 = 80 FDs — under 256 with headroom. Formula: open_fds ≈ workers_reading × (P/M). Exceeding 256 forces segment coalescing (Phase 1, N.8).

C8 — Broadcast safety ceiling. Phase 9: broadcast_threshold 10 MiB, replicated across all workers. Replicated footprint = threshold × workers = 10 MiB × 8 = 80 MiB — well under the 4 GiB budget (C4), confirming broadcast is safe only below the threshold. A "10 MiB" side that is actually 1 GiB would replicate to 1 GiB × 8 = 8 GiB → OOM: the exact failure the error margin (P14, MM6) guards.

C9 — Sketch memory per stage. Phase 3: HLL precision p=14 → m = 2^14 = 16,384 registers × 1 B ≈ 16 KiB per column; Count-Min d=4 × w counters (4 B each). For 8 tracked columns: 8 × 16 KiB = 128 KiB HLL + CMS — negligible vs the 4 GiB budget (C4), confirming P12 ("stats are cheap sketches, not exact scans"). Formula: hll_bytes = 2^p × cols.

C10 — Re-optimization overhead as a fraction of query time. §4: reopt decision p95 ≤ 10 ms per stage boundary; re-plan search p95 ≤ 50 ms. A query with B stage boundaries (Domain Deep Dive had 6 decisions) costs at most B × (10 + 50) ms. For B = 6 → ≤ 360 ms of control-plane work. Against a multi-second analytic query that is < 5–10% overhead; against a 100 ms interactive query it would dominate — which is why DuckDB (§Comparative Architecture Table) skips adaptation for interactive workloads.

C11 — Shuffle write bandwidth demand. From C1, a stage producing all 200 M rows/s at ~64 B/row demands 200e6 × 64 B = 12.8 GB/s of shuffle write if everything spilled — far above a single NVMe (~2–7 GB/s). This proves shuffle must be reduced before it is written: two-stage partial aggregation (Phase 5, ≥50% byte reduction) and DPP pruning (Phase 11, ≥50% partitions) are not optimizations but necessities to keep the shuffle within NVMe bandwidth (§4 scaling assumptions).

C12 — Startup morsel-latency budget. §4: cold start ≤ 150 ms to first morsel. With C2's 500 µs/morsel dispatch cost, the first morsel's dispatch is negligible; the 150 ms is dominated by plan load + validation + thread-pool spin-up. Formula sanity: 150 ms ≫ 500 µs confirms scheduling is not the cold-start bottleneck — plan parsing/validation is, which is why the validator (Phase 0) must be linear in plan size.

Alternative Architectures (Roads Not Taken)

Four fundamentally different architectures for the same problem — runtime-robust query execution. Each: sketch, the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

A1 — Eddy: per-tuple adaptive routing (no fixed plan)

        ┌─────────┐
tuples─►│  EDDY   │◄────────── routing policy (lottery / tickets)
        └──┬───┬──┘            updated per tuple from observed
           │   │               operator selectivity + cost
        ┌──▼┐ ┌▼──┐ ┌────┐
        │op1│ │op2│ │op3 │   each tuple visits operators in a
        └──┬┘ └─┬─┘ └─┬──┘   data-dependent order; no compiled plan
           └────┴─────┘

Regime where it wins: extreme, time-varying uncertainty — selectivities that drift mid-query, streaming/sensor data, or queries so unpredictable that any fixed plan (even a re-planned one) is stale by the time it runs. Maximal adaptivity, decided per tuple. Real system: Avnur & Hellerstein's Eddies in TelegraphCQ (Required Reading paper #5). Why rejected here: per-tuple routing pays a routing decision on the hottest path (every row), destroying the cache locality and vectorization this engine's throughput target depends on (§4, §6 P11), and its continuously-changing state is hostile to the deterministic-replay guarantee (I1, MM4). Stage-boundary adaptivity captures most of the win at a fraction of the per-row cost.

What this engine borrows vs refuses: it borrows the core insight — let observed selectivity drive routing — but applies it at the stage granularity (route a whole stage's output via a re-planned exchange) rather than per tuple. It refuses the eddy's continuously-mutating routing state because that state is exactly what makes replay (I1) impossible; the deferred streaming/continuous-query feature (§Deferred Features Register) is where an eddy-like layer would re-enter, behind a determinism caveat.

A2 — Stage-boundary re-optimization (this design)

 ┌─────┐  shuffle  ┌─────┐  shuffle  ┌─────┐
 │ S0  ├──────────►│ S1  ├──────────►│ S2  │
 └─────┘  ▲sealed  └─────┘  ▲sealed  └─────┘
          │stats             │stats
          └── controller re-plans the NEXT pending stage only
              (coalesce / switch-join / skew-split / DPP / agg-mode)

Regime where it wins: batch analytic queries with materialization seams (shuffles) where exact mid-query counts are cheap to gather and a bounded planning pause between stages is acceptable. Real system: Spark SQL AQE (Required Reading paper #11; §Comparative Architecture Table). Why chosen: it is the sweet spot — exact stats, bounded adaptation, deterministic, and the seam already exists in any shuffle-based engine. This is the architecture the whole blueprint builds.

The bet, and where it loses: A2 bets that the next stage's plan is the high-leverage decision and that waiting for the current stage to materialize is affordable. It loses when there are no seams (a single giant pipeline with no breaker — then there is nothing to re-plan against, and the engine degrades to A4 for that query) or when the planning pause between stages is itself the latency budget (sub-100 ms interactive queries, C10). The mitigation for the first is to insert breakers where the cost model expects estimation risk; the second is simply out of scope — interactive latency is DuckDB's regime, not this one.

A3 — Parametric / Plan-Cache PQO (choose among precomputed plans)

 plan-time:  optimizer enumerates plans P_a, P_b, P_c
             + the parameter regions where each is optimal
             ┌───────────────────────────────────────┐
             │  region map:  σ<0.1 → P_a               │
             │               0.1≤σ<0.5 → P_b           │
             │               σ≥0.5 → P_c               │
             └───────────────────────────────────────┘
 run-time:   bind parameters → look up region → execute the cached plan
             (no search, no mid-query re-plan)

Regime where it wins: the same parameterized query shape run many times with varying bind values, where paying a heavy plan-time enumeration once and then doing an O(1) lookup per execution beats both re-planning and per-tuple routing — OLTP-ish repeated workloads. Real system: parametric query optimization / plan-region caching as in Microsoft SQL Server's plan-cache + parameter-sensitive-plan and memory-grant-feedback machinery (§Comparative Architecture Table). Why rejected here: this engine is a per-query, read-only executor that receives an already-bound physical plan (§1) and has no cross-execution history to amortize enumeration against; precomputing plan regions for queries seen once is wasted work, and the input contract gives no parameters to key on.

What this engine borrows vs refuses: it borrows nothing at runtime, but the idea of carrying multiple alternatives and choosing late is precisely what the switch-join rule (Phase 9) does — except the alternatives are generated on demand at a materialization seam from exact stats, not precomputed offline against a parameter space. If a host integration ever did see the same plan repeatedly, the captured ReoptEvent history (Phase 12) is the natural raw material for a future plan-region cache — a clean extension point, not a redesign.

A4 — Static cost-based optimization, no runtime adaptation

 catalog stats ─► [ cost-based optimizer (System R / Cascades) ] ─► plan ─► execute as-is
                    histograms, selectivity estimates, dynamic-programming
                    join enumeration; ZERO feedback from execution

Regime where it wins: queries where the static plan is reliably good — data that fits memory, low join depth, accurate histograms, and a latency budget so tight that any adaptation overhead is a net loss (interactive/embedded analytics). Real systems: PostgreSQL (static cost-based, no runtime re-opt) and DuckDB (vectorized, no runtime re-optimization; §Comparative Architecture Table). Why rejected as the whole design: the Leis 2015 JOB finding (§Failure Modes & Recovery) shows static estimates degrade badly with join depth on real data — exactly the regime this engine targets. But note this is not rejected as a component: the v0 plan is a static cost-based plan (Phase 1, cross-link #313), and the adaptive controller is a separable layer above it. The lesson (MM2) is that adaptivity is a control plane bolted onto a fast static data plane — not a replacement for it.

What this engine borrows vs refuses: it borrows the entire static optimizer — Selinger-style cost model, Cascades-style memo, dynamic-programming join enumeration (Required Reading papers #4/#14) — to produce v0 and to re-plan a single stage (Phase 7's replan.rs reuses the planner). It refuses only the assumption that v0 is final. The architectural payoff of keeping the static optimizer intact is graceful degradation: if every adaptive rule is disabled (config flag, or a non-deterministic subtree per I14), the engine reduces exactly to A4 and still produces correct results — adaptivity is strictly additive, never a correctness dependency.

Tradeoff summary (the axis these four span)

Architecture Commit time Per-row decision cost Adaptivity ceiling Determinism / replay Real embodiment
A1 Eddy Per tuple High (route every row) Maximal (handles drift mid-query) Hard — state changes continuously Eddies / TelegraphCQ
A2 Stage-boundary (this) Per stage Zero (decided off hot path) Coalesce/switch/skew/DPP/agg at seams Easy — pure fn of sealed stats (I1) Spark SQL AQE
A3 Parametric PQO Plan time (once), looked up per execution Zero (table lookup) Bounded to precomputed regions Easy — deterministic in bind values SQL Server plan-cache / PSP
A4 Static cost-based Plan time only Zero None at runtime Easy — deterministic in catalog PostgreSQL, DuckDB

The choice in one sentence. This engine picks A2 because the materialization seam (MM9) makes exact stats free, the bounded single-pass rule set (I2) makes adaptation terminate, and the sealed-stats purity (I1) makes the whole thing replayable — capturing most of A1's robustness at A4's per-row cost, which is the combination no other point on the axis offers.

Decision rule — which architecture for a new workload. A reviewer choosing among these for a different system should ask, in order:

  • Is the data bounded and materializable between operators? If no (unbounded stream, no seam) → A1 (eddy) is the only option that adapts at all.
  • Is the same query shape run many times with different parameters? If yes → A3 (parametric PQO) amortizes enumeration; per-query adaptation is wasted.
  • Are static estimates reliably good (low join depth, accurate histograms, in-memory)? If yes and latency is tight → A4 (static) wins; adaptation overhead is a net loss (cf. DuckDB, §Comparative Architecture Table).
  • Are there materialization seams (shuffles/breakers) and is exact mid-query counting affordable? If yes → A2 (this design) is the sweet spot.
  • Do you need deterministic replay for operability (I1)? A1 effectively forecloses it; A2/A3/A4 preserve it — a frequently decisive constraint in production engines.
  • Is the bottleneck a single hot key or partition-size skew? Only A2's stage-boundary rules (Phase 10) address it directly; A4 cannot, and A3 only if a skewed region was precomputed.
