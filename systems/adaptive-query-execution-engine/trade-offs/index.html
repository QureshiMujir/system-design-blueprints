Decisions (§9) · 30 ADRs

001

Language

Chosen

Rust 1.78+ (ed. 2021)

Rejected

C++, Java/Scala, Go

When the rejected choice is right

C++ wins when the target is an existing C++ engine (DuckDB/Velox) you must extend in-tree; Scala/JVM wins when the engine is Spark and reuse of its Catalyst/Tungsten stack outweighs a rewrite.

Why: Ownership for buffer/spill lifetimes; Send/Sync data-race freedom; no GC p99 tax; Arrow-rs.

002

Columnar layer

Chosen

arrow-rs (arrow-array/buffer)

Rejected

hand-rolled columnar

When the rejected choice is right

Hand-rolled wins for a closed-format engine needing a bespoke layout Arrow can't express (e.g. ClickHouse's column-per-type compression codecs) where Arrow conversion is pure overhead.

Why: Validity/offset/dict layout standard; IPC + Parquet interop.

003

Build

Chosen

Cargo workspace, multi-crate

Rejected

Bazel, custom

When the rejected choice is right

Bazel wins in a polyglot monorepo (Rust + C++ + protos) needing one hermetic build graph and remote caching across thousands of targets.

Why: Native, reproducible (Cargo.lock).

004

Async/exec model

Chosen

OS threads + work-stealing morsels (no async runtime in core)

Rejected

Tokio, rayon-only

When the rejected choice is right

Tokio wins when the executor is IO-bound (networked shuffle, remote object-store scans) where threads block on RTT and async multiplexing reclaims the stalls; rayon-only wins for a pure data-parallel batch job with no pipeline/backpressure structure.

Why: Morsel scheduler is CPU-bound; async adds overhead + nondeterminism.

005

Concurrency primitives

Chosen

crossbeam (deque, channels), parking_lot

Rejected

std-only, tokio::sync

When the rejected choice is right

std-only wins when minimizing dependency surface (audited/regulated build) matters more than the deque's last few percent; tokio::sync wins once the engine adopts an async runtime (see ADR-004's regime).

Why: Lock-free deque for work-stealing; faster mutexes.

006

Hash table

Chosen

custom vectorized linear-probe

Rejected

hashbrown directly

When the rejected choice is right

hashbrown wins for non-spilling, non-vectorized in-memory joins where SwissTable's SIMD probe already dominates and the partition-aware build hooks are unused — i.e. small builds that never spill.

Why: Control over spill partitioning + vectorized probe (Polychroniou 2015).

007

Sketches

Chosen

custom HLL + Count-Min (aqe-sketch)

Rejected

external crates

When the rejected choice is right

External crates win when you need exotic estimators (KMV/Theta sketches for set ops, t-digest for quantiles) that are non-trivial to reimplement and whose seed/error semantics you can pin externally.

Why: Determinism + exact error bounds we control.

008

Spill format

Chosen

Arrow IPC segments (append) + manifest

Rejected

bespoke binary

When the rejected choice is right

Bespoke binary wins when spill is on the critical path and IPC framing/metadata overhead per tiny segment is measurable — a hand-packed fixed-layout dump amortizes better for many small spills.

Why: Reuse Arrow reader/writer; checksummed.

009

Shuffle

Chosen

single-node disk files, hash-partitioned

Rejected

in-memory only, networked

When the rejected choice is right

In-memory shuffle wins when intermediates always fit RAM and latency dominates (interactive sub-second queries); networked shuffle wins the moment you cross the single-node ceiling (§Scalability Analysis) into distributed execution.

Why: Realistic backpressure + skew; multi-node deferred.

010

Serialization (plan IR)

Chosen

serde + JSON (canonical)

Rejected

protobuf, bincode

When the rejected choice is right

Protobuf wins for a cross-language plan IR shared with non-Rust services (a Substrait-style contract); bincode wins for a machine-only IR where diffability is irrelevant and parse speed/size dominate.

Why: Human-diffable EXPLAIN/plan; bincode for spill.

011

Memory mgmt

Chosen

reservation-based budget (aqe-mem)

Rejected

malloc-only / jemalloc tricks

When the rejected choice is right

malloc/jemalloc-only wins for an in-memory-only engine that never spills (the whole working set is guaranteed to fit), where reservation accounting is pure overhead on the hot path.

Why: Explicit per-operator accounting → spill triggers.

Logging

When the rejected choice is right

Metrics

When the rejected choice is right

014

"None" wins only for a strictly static (non-adaptive) executor with no re-optimization to replay — but that is a different system, not this one; within an adaptive engine the replay gate is mandatory.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

A1 — Eddy: per-tuple adaptive routing (no fixed plan)

        ┌─────────┐
tuples─►│  EDDY   │◄────────── routing policy (lottery / tickets)
        └──┬───┬──┘            updated per tuple from observed
           │   │               operator selectivity + cost
        ┌──▼┐ ┌▼──┐ ┌────┐
        │op1│ │op2│ │op3 │   each tuple visits operators in a
        └──┬┘ └─┬─┘ └─┬──┘   data-dependent order; no compiled plan
           └────┴─────┘

Regime where it wins: extreme, time-varying uncertainty — selectivities that drift mid-query, streaming/sensor data, or queries so unpredictable that any fixed plan (even a re-planned one) is stale by the time it runs. Maximal adaptivity, decided per tuple. Real system: Avnur & Hellerstein's Eddies in TelegraphCQ (Required Reading paper #5). Why rejected here: per-tuple routing pays a routing decision on the hottest path (every row), destroying the cache locality and vectorization this engine's throughput target depends on (§4, §6 P11), and its continuously-changing state is hostile to the deterministic-replay guarantee (I1, MM4). Stage-boundary adaptivity captures most of the win at a fraction of the per-row cost.

What this engine borrows vs refuses: it borrows the core insight — let observed selectivity drive routing — but applies it at the stage granularity (route a whole stage's output via a re-planned exchange) rather than per tuple. It refuses the eddy's continuously-mutating routing state because that state is exactly what makes replay (I1) impossible; the deferred streaming/continuous-query feature (§Deferred Features Register) is where an eddy-like layer would re-enter, behind a determinism caveat.

A2 — Stage-boundary re-optimization (this design)

 ┌─────┐  shuffle  ┌─────┐  shuffle  ┌─────┐
 │ S0  ├──────────►│ S1  ├──────────►│ S2  │
 └─────┘  ▲sealed  └─────┘  ▲sealed  └─────┘
          │stats             │stats
          └── controller re-plans the NEXT pending stage only
              (coalesce / switch-join / skew-split / DPP / agg-mode)

Regime where it wins: batch analytic queries with materialization seams (shuffles) where exact mid-query counts are cheap to gather and a bounded planning pause between stages is acceptable. Real system: Spark SQL AQE (Required Reading paper #11; §Comparative Architecture Table). Why chosen: it is the sweet spot — exact stats, bounded adaptation, deterministic, and the seam already exists in any shuffle-based engine. This is the architecture the whole blueprint builds.

The bet, and where it loses: A2 bets that the next stage's plan is the high-leverage decision and that waiting for the current stage to materialize is affordable. It loses when there are no seams (a single giant pipeline with no breaker — then there is nothing to re-plan against, and the engine degrades to A4 for that query) or when the planning pause between stages is itself the latency budget (sub-100 ms interactive queries, C10). The mitigation for the first is to insert breakers where the cost model expects estimation risk; the second is simply out of scope — interactive latency is DuckDB's regime, not this one.

A3 — Parametric / Plan-Cache PQO (choose among precomputed plans)

 plan-time:  optimizer enumerates plans P_a, P_b, P_c
             + the parameter regions where each is optimal
             ┌───────────────────────────────────────┐
             │  region map:  σ<0.1 → P_a               │
             │               0.1≤σ<0.5 → P_b           │
             │               σ≥0.5 → P_c               │
             └───────────────────────────────────────┘
 run-time:   bind parameters → look up region → execute the cached plan
             (no search, no mid-query re-plan)

Regime where it wins: the same parameterized query shape run many times with varying bind values, where paying a heavy plan-time enumeration once and then doing an O(1) lookup per execution beats both re-planning and per-tuple routing — OLTP-ish repeated workloads. Real system: parametric query optimization / plan-region caching as in Microsoft SQL Server's plan-cache + parameter-sensitive-plan and memory-grant-feedback machinery (§Comparative Architecture Table). Why rejected here: this engine is a per-query, read-only executor that receives an already-bound physical plan (§1) and has no cross-execution history to amortize enumeration against; precomputing plan regions for queries seen once is wasted work, and the input contract gives no parameters to key on.

What this engine borrows vs refuses: it borrows nothing at runtime, but the idea of carrying multiple alternatives and choosing late is precisely what the switch-join rule (Phase 9) does — except the alternatives are generated on demand at a materialization seam from exact stats, not precomputed offline against a parameter space. If a host integration ever did see the same plan repeatedly, the captured ReoptEvent history (Phase 12) is the natural raw material for a future plan-region cache — a clean extension point, not a redesign.

A4 — Static cost-based optimization, no runtime adaptation

 catalog stats ─► [ cost-based optimizer (System R / Cascades) ] ─► plan ─► execute as-is
                    histograms, selectivity estimates, dynamic-programming
                    join enumeration; ZERO feedback from execution

Regime where it wins: queries where the static plan is reliably good — data that fits memory, low join depth, accurate histograms, and a latency budget so tight that any adaptation overhead is a net loss (interactive/embedded analytics). Real systems: PostgreSQL (static cost-based, no runtime re-opt) and DuckDB (vectorized, no runtime re-optimization; §Comparative Architecture Table). Why rejected as the whole design: the Leis 2015 JOB finding (§Failure Modes & Recovery) shows static estimates degrade badly with join depth on real data — exactly the regime this engine targets. But note this is not rejected as a component: the v0 plan is a static cost-based plan (Phase 1, cross-link #313), and the adaptive controller is a separable layer above it. The lesson (MM2) is that adaptivity is a control plane bolted onto a fast static data plane — not a replacement for it.

What this engine borrows vs refuses: it borrows the entire static optimizer — Selinger-style cost model, Cascades-style memo, dynamic-programming join enumeration (Required Reading papers #4/#14) — to produce v0 and to re-plan a single stage (Phase 7's replan.rs reuses the planner). It refuses only the assumption that v0 is final. The architectural payoff of keeping the static optimizer intact is graceful degradation: if every adaptive rule is disabled (config flag, or a non-deterministic subtree per I14), the engine reduces exactly to A4 and still produces correct results — adaptivity is strictly additive, never a correctness dependency.

Tradeoff summary (the axis these four span)

Architecture Commit time Per-row decision cost Adaptivity ceiling Determinism / replay Real embodiment
A1 Eddy Per tuple High (route every row) Maximal (handles drift mid-query) Hard — state changes continuously Eddies / TelegraphCQ
A2 Stage-boundary (this) Per stage Zero (decided off hot path) Coalesce/switch/skew/DPP/agg at seams Easy — pure fn of sealed stats (I1) Spark SQL AQE
A3 Parametric PQO Plan time (once), looked up per execution Zero (table lookup) Bounded to precomputed regions Easy — deterministic in bind values SQL Server plan-cache / PSP
A4 Static cost-based Plan time only Zero None at runtime Easy — deterministic in catalog PostgreSQL, DuckDB

The choice in one sentence. This engine picks A2 because the materialization seam (MM9) makes exact stats free, the bounded single-pass rule set (I2) makes adaptation terminate, and the sealed-stats purity (I1) makes the whole thing replayable — capturing most of A1's robustness at A4's per-row cost, which is the combination no other point on the axis offers.

Decision rule — which architecture for a new workload. A reviewer choosing among these for a different system should ask, in order:

  • Is the data bounded and materializable between operators? If no (unbounded stream, no seam) → A1 (eddy) is the only option that adapts at all.
  • Is the same query shape run many times with different parameters? If yes → A3 (parametric PQO) amortizes enumeration; per-query adaptation is wasted.
  • Are static estimates reliably good (low join depth, accurate histograms, in-memory)? If yes and latency is tight → A4 (static) wins; adaptation overhead is a net loss (cf. DuckDB, §Comparative Architecture Table).
  • Are there materialization seams (shuffles/breakers) and is exact mid-query counting affordable? If yes → A2 (this design) is the sweet spot.
  • Do you need deterministic replay for operability (I1)? A1 effectively forecloses it; A2/A3/A4 preserve it — a frequently decisive constraint in production engines.
  • Is the bottleneck a single hot key or partition-size skew? Only A2's stage-boundary rules (Phase 10) address it directly; A4 cannot, and A3 only if a skewed region was precomputed.
