Decisions (§9) · 23 ADRs

ADR-01

Runtime language

Chosen

Go 1.22+

Rejected

Rust, Java/JVM, Node/TypeScript

When the rejected choice is right

Rust wins once the interceptor must run as an in-process Postgres extension needing zero-GC-pause guarantees under 100µs

Why: static binary, gRPC ecosystem, one-engineer velocity (§1)

ADR-02

Postgres capture mechanism

Chosen

Wire-protocol proxy (Mode B) default; logical-decoding plugin (Mode A) opt-in

Rejected

Trigger-based capture, WAL-shipping-only

When the rejected choice is right

Mode A wins once the operator controls the PG instance and needs < 0.5ms capture overhead

Why: Mode B needs no PG restart/superuser; Mode A is lower latency

ADR-03

Inverse-log hot tier

Chosen

PostgreSQL (runtime's own instance)

Rejected

Embedded RocksDB, Kafka

When the rejected choice is right

Kafka wins once write volume exceeds a single Postgres instance's throughput ceiling (~200k ops/sec) and cross-record queries aren't needed

Why: reuses operational familiarity; ACID commit alongside idempotency store

ADR-04

Cold-tier storage

Chosen

S3 + object-lock

Rejected

Glacier-only, tape

When the rejected choice is right

Glacier wins for > 7-year regulatory archival where hours-scale read latency is acceptable and cost dominates

Why: object-lock gives WORM tamper-evidence with immediate audit read access

ADR-05

Args/payload serialization

Chosen

Canonical JSON

Rejected

Protobuf-only, Avro

When the rejected choice is right

Protobuf wins once payload volume dominates cost and schema evolution needs strict field numbering

Why: deterministically hashable without schema-registry coordination; human-inspectable for audits

ADR-06

Runtime transport

gRPC

When the rejected choice is right

REST/JSON wins for the CLI's ad hoc debugging surface (kept as a control-plane fallback)

ADR-07

Saga-registry consensus (Phase 7)

Chosen

etcd (embedded Raft)

Rejected

When the rejected choice is right

ZooKeeper wins in shops with existing ZK operational expertise and multi-tenant ZK clusters already running

ADR-08

SQL inverse generation

Chosen

Query-parse + pre-image read (pg_query_go)

Rejected

Full-statement replay, trigger-captured deltas

When the rejected choice is right

Trigger-captured deltas win when the schema already has audit triggers and cannot tolerate a proxy hop

Why: structural precision (table/predicate/columns) without deploying triggers on customer schema

ADR-09

Concurrency model

Chosen

Goroutines + channels

Rejected

When the rejected choice is right

An actor framework wins if per-tenant supervision trees and location-transparent messaging dominate at very high per-tenant isolation counts

Why: matches Go idioms; no extra dependency

ADR-10

Backpressure

Chosen

Rejected

When the rejected choice is right

Drop-oldest wins for non-critical telemetry streams where loss is acceptable and memory pressure must be minimized above all else

Why: bounds memory under burst without silently losing operations

Rejected

Bazel hermetic builds

When the rejected choice is right

Bazel wins once the monorepo spans Go+C+TS at a scale where incremental hermetic builds save more CI time than Bazel's setup cost

ADR-22

Time source

Chosen

Monotonic clock for internal sequencing; wall-clock only for external timestamps

Rejected

Wall-clock-only sequencing

When the rejected choice is right

Wall-clock-only sequencing wins in single-node deployments with no cross-service skew risk and a need for human-readable ordering

Why: cross-service clock skew would corrupt causal order if used for sequencing

Licensing

Apache 2.0 (runtime/SDK/CLI/verbs)

BSL wins for projects needing a time-boxed anti-competitive clause during a control-plane bootstrap phase, trading OSS-community trust for it

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Event-Sourcing-First (Greenfield)

App -> Event Store (append-only) -> Projections (read models)
                                  -> Time-travel = replay events to T

Regime where it wins: greenfield systems designed from day one for full auditability and replay (e.g. a from-scratch ledger). Real system: EventStoreDB. Rejection: Rewind's value proposition is retrofitting reversibility onto an existing, running Postgres + Node system without a rewrite (§1) — event sourcing requires exactly the architectural rewrite Rewind exists to avoid.

Backup + PITR-Only (No Runtime Layer)

DB -> periodic snapshot -> WAL archive -> restore to T (whole DB, whole downtime)

Regime where it wins: single-datastore systems with no cross-service correlation requirement, where minutes-to-hours of restore downtime is acceptable. Real system: standard Postgres PITR, or Aurora Backtrack (§31) for a managed variant. Rejection: loses every correlated cross-service effect since the snapshot — the "your DB rolled back, your downstream API didn't" failure §3's diagram is built to prevent.

Centralized Two-Phase-Commit Coordinator

App -> [Prepare] -> TC -> [Commit/Abort all] -> Services (DB, API, Queue)

Regime where it wins: a closed system where every participant can implement the 2PC prepare phase (all-internal services, no third-party APIs). Real system: XA-transaction JTA deployments. Rejection: Helland (2007, §5) shows 2PC does not survive contact with third-party APIs (Stripe, Twilio) that will never implement a prepare phase — Rewind's compensating-action model (Gray 1981) is precisely the alternative Helland's paper argues for.

Manual Runbook + On-Call Culture (No Automation)

Incident -> Page on-call -> Hand-write recovery SQL/script -> Manual verify -> Close

Regime where it wins: very low-incident-rate systems where building and maintaining a reversibility runtime costs more than the expected cost of rare manual incidents. Real system: this is the de facto state of the art at most SaaS companies today. Rejection: manual runbooks fail predictably under stress — fatigue, time pressure, incomplete cross-service knowledge — exactly the failure mode motivating Rewind's existence (§2).
