Project Number: 10

Project Name: Rewind

1. Goal & Scope

Rewind is a reversible-production runtime: a Go daemon (rewindd) that intercepts every side-effecting operation a service performs — Postgres writes, Node-originated outbound API calls, queue publishes — captures a compensating inverse for each, appends it to a hash-chained inverse log, and replays inverses in reverse causal order on operator or programmatic demand (rewind tenant T --since=30m). The system exists so that a bad migration, a runaway job, or a misbehaving autonomous agent can be undone with the same routine confidence as Cmd-Z in a text editor, without hand-authoring rollback code per incident.

Phase-0 deliverable (numbered modules, §10 names them exactly):

  1. pkg/runtime — inverse-log storage, hash-chain integrity, gRPC control surface.
  2. pkg/shared — ULID generation, canonical-JSON hashing, clock abstraction.
  3. pkg/proto — the runtime.v1 gRPC service contract.
  4. cmd/rewindd — the daemon entrypoint that wires the above into a running process.

System boundaries.

  • Provides: inverse capture for Postgres DML and SDK-wrapped HTTP/queue calls; a hash-chained, tamper-evident inverse log; reverse-causal replay of inverses within a declared window; per-tenant and per-service rewind scoping.
  • Delegates: point-in-time recovery to the underlying Postgres PITR provider (§20 Phase 8 consumes it, does not reimplement it); consensus/replication primitives to etcd/Raft (ADR-07); TLS/identity to the operator's PKI or OIDC provider.
  • Does NOT provide: disaster recovery, general backup, workflow orchestration (no competing with Temporal/Camunda — Rewind composes with them, §31), arbitrary binary-protocol reverse-engineering, consensus implemented from scratch.
  • Non-goals: 100% reversibility coverage (some operations are structurally irreversible — P7 forbids pretending otherwise); zero forward-path overhead (a small, budgeted overhead is the deliberate trade, §4); a UI-first product before the runtime contract is correct.

Deployment model: self-hosted, single-binary Go daemon per environment (dev / staging / prod), one Postgres instance as the log's hot tier, S3-compatible object storage as the cold tier. A managed control plane (multi-tenant SaaS) consumes the same OSS runtime and is out of scope for this blueprint's Phase 0–9 (PhaseDeferred("§35")).

Target users/operators: platform engineers and SREs operating Postgres + Node services who need bounded-time recovery from state corruption; from Phase 9, teams operating autonomous agents that touch production.

What later phases unlock: Phase 7 unlocks correctness across many services in one rewind; Phase 8 unlocks inspecting past production state without touching it; Phase 9 unlocks reversibility as a safety property of autonomous-agent action, not just human error.

Recommended language: Go 1.22+ (ADR-01). Rationale: single statically-linked binary, mature gRPC/OpenTelemetry ecosystem, goroutine model fits the interceptor's high-fan-in I/O shape, and a one-engineer team ships faster in Go than standing up Rust's stricter compile-time guarantees for this problem shape. Rejected: Rust (superior for a zero-GC-pause in-process Postgres extension, but slower to reach Phase-1 MVP — reconsidered at ADR-01's "rejected choice wins" regime); Java/JVM (GC pause profile conflicts with the <2ms forward-path budget, §4); Node/TypeScript for the runtime itself (single-threaded event loop is the wrong shape for a CPU-bound SQL-parsing + hashing hot path — TypeScript remains the SDK language, where it fits the ecosystem it wraps).

Prerequisites (systems knowledge required): write-ahead logging and logical decoding (Postgres internals); the sagas/compensating-transaction model (§5, §8); hash-chained tamper-evidence (Merkle/blockchain-adjacent, not blockchain); Raft consensus (Phase 7); gRPC and Protocol Buffers; basic point-in-time-recovery mechanics.

Estimated timeline: Phase 0 — 2 weeks. Full system (Phase 0–9) — approximately 31 engineering-weeks (≈ 7 months) at one-to-a-few-engineer scale, per §38 Appendix B's per-phase duration column (this blueprint specifies engineering phases only, §12–§21).

Deferred features, each flagged at first mention and registered in §35: PhaseDeferred("§35") — managed multi-tenant control plane; Python/Go SDKs; cross-cloud saga convergence guarantees; customer-defined verb registration with conformance gating; BYOK/on-prem distribution.

2. Why Build This

Rewind teaches the systems knowledge that sits underneath every "oops, roll it back" Slack message: how to capture a compensating action for an arbitrary write without rearchitecting the system that made it (Gray 1981; §5); how to order those compensations correctly across causally-dependent operations (Lamport 1978; §8); how to make an inverse idempotent so a retry storm cannot double-undo (Helland 2007; §6 P4); and how to bound the blast radius of the single most dangerous command in the system — the rewind itself (§22 T2, T5).

It matters architecturally because reversibility has historically been bolted on per-incident (a hand-written rollback script, a restored snapshot that loses everything since) rather than designed in as a runtime contract. The same arc played out for idempotency (2010s, driven by Stripe's public idempotency-key contract) and observability (2020s, driven by OpenTelemetry standardizing what had been vendor-specific). Rewind treats reversibility the same way: a first-class, load-bearing property of the runtime, not an incident-response afterthought.

It builds the engineering muscles of: reasoning about causal order versus wall-clock order under concurrency; designing an interface (§11's ReversibleOperation) that forces every integrator to declare what they cannot undo, rather than silently failing; treating a single operator command as a privileged, auditable, rate-limited capability; and building conformance suites that gate correctness before a capability ships (§14.5, §5's ref-impls).

Cross-links to sibling systems: the saga coordinator (§19 Phase 7) is architecturally a narrower Temporal/Cadence — study those for workflow-compensation patterns and note where Rewind's auto-captured-inverse model diverges from their author-your-own-compensation model (§5 ref-impls, §31). The inverse log's hash-chain integrity model is the same family of technique as an audit-log system (pgaudit) but adds a replay obligation pgaudit never had (§8). The distributed saga registry (etcd/Raft) is the same coordination substrate a Kubernetes control plane depends on (§5 papers, ADR-07).

What Mastery Looks Like — after building this, the reader can:

  • Design a compensating-action model for an arbitrary datastore, not just Postgres, and correctly classify each operation's inverse strategy (compensating / tombstone / quiesce-replay / forward-only) — cemented in §14 Phase 2 and §8.
  • Reason about causal order (Lamport clocks, dependency DAGs) well enough to build a correct reverse-topological-sort replay engine — cemented in §16 Phase 4 and §19 Phase 7.
  • Build and defend a hash-chained tamper-evidence scheme without invoking "blockchain" as a buzzword, and explain exactly what attack it does and does not stop — cemented in §12 Phase 0 and §22.
  • Design an idempotency contract that survives N-times replay and defend the TTL/key-scope choices under a concrete retry-storm scenario — cemented in §15 Phase 3.
  • Bound the blast radius of a privileged, destructive command (co-sign thresholds, dry-run gating, per-agent quotas) and articulate why the command itself, not just the data it touches, is the attack surface — cemented in §17 Phase 5 and §21 Phase 9.
  • Run a Raft-replicated coordination service (etcd) as an embedded dependency and reason about its failure modes under partition — cemented in §19 Phase 7.
  • Explain, with real numbers, when this architecture is the right call and when a simpler backup/PITR-only approach dominates it — cemented in §32 and §34.

App process (untrusted from runtime POV): runs the Node SDK, which wraps outbound fetch/queue calls, registers inverses via the verb catalogue, and threads saga context. The runtime validates every SDK message as adversarial input (I8, P12).

Postgres Interceptor: two exchangeable implementations of the same contract — Mode B (wire-protocol proxy, ADR-02 default) parses DML in flight and derives inverse SQL; Mode A (logical-decoding output plugin, ADR-02 opt-in) emits compensating SQL from inside Postgres itself at lower latency but requires superuser + restart.

Rewind Runtime (rewindd, trust root): owns the inverse log, the idempotency store, and — from Phase 7 — the saga coordinator. Every authorization decision (rewind permission, co-sign requirement) is enforced here, never at the CLI.

Inverse Log: hot tier is the runtime's own Postgres instance (separate from customer DB, ADR-03); cold tier is S3 with object-lock (ADR-04). Hash-chained (I2) so tampering is detectable without a separate audit system.

Saga Coordinator (Phase 7): replicates saga/operation state across runtime instances via embedded etcd/Raft (ADR-07, Ongaro & Ousterhout 2014), computes the reverse-causal dependency graph, and fans inverses out per service with bounded parallelism.

Rewind CLI: the sole operator surface. Every command is mTLS/OIDC-authenticated and produces a signed audit record before execution (P5, P6).

Sandbox Engine (Phase 8): consumes PITR from the customer's Postgres provider plus the inverse log's forward-operation history to materialize an isolated "production at time T" environment.

Agent Safety Layer (Phase 9): wraps autonomous-agent actions in the same ReversibleOperation contract with added per-agent quotas and policy enforcement, integrating with external agent frameworks (§21).

All later sections stay consistent with this diagram; component names here (Rewind Runtime, Postgres Interceptor, Saga Coordinator, Idempotency Store, Sandbox Engine, Agent Safety Layer) are used identically in §10 and §11.

6. Design Principles

P1. Declared Inverse or No Forward. The runtime refuses to forward an operation whose inverse strategy is unregistered. Tradeoff: registration friction per new verb. Operational implication: verb-catalogue growth is the integration cost surface. Violating it: silent rewind-coverage gaps, discovered only during an incident — the worst possible time.

P2. The Inverse Log Is Sacred. Append-only, hash-chained, Tier-1 data (I2). Tradeoff: ~1.6× storage amplification (§4). Operational implication: a separate storage tier from the customer's own DB. Violating it: a poisoned log makes every subsequent rewind untrustworthy.

P3. Forward Fast, Rewind Correct. Forward budget: single-digit milliseconds (§4). Rewind budget: tens of seconds, spent on validation. Tradeoff: async-batch append on the forward path (ADR-10). Violating it: shaving rewind-path checks to hit a speed target corrupts state silently instead of loudly.

P4. Idempotency Mandatory for Inverses, Optional for Forwards. Re-applying an inverse N times must equal applying it once (I3). Tradeoff: every inverse strategy carries an idempotency key (§11). Violating it: a retry storm double-undoes an already-reverted operation.

P5. Rewind Is Auditable, Attestable, Revocable. Every rewind signs a manifest (I10); a rewind can itself be rolled forward. Tradeoff: signing overhead per rewind, not per operation. Violating it: an unaudited rewind cannot be trusted during a postmortem.

P6. Rewind Authority Is a Distinct Capability. Separately IAM-scoped from data-write access. Tradeoff: extra permission surface to administer. Violating it: write access silently implies rewind access — a privilege-escalation vector (§22 T2).

P7. Never Claim Reversibility You Don't Have. Forward-only operations are declared at registration, not discovered at rewind time. Tradeoff: visibly lower "coverage %" metrics. Violating it: an operator trusts a rewind that silently skipped an unreversible step.

P8. Causal Order Is the Only Order That Matters. Reverse-causal replay, never wall-clock replay (Lamport 1978, §5). Tradeoff: dependency-graph computation cost before every apply. Violating it: applying inverses out of causal order can produce a state that never existed forward.

P9. Dry-Run Before Apply, Always in Production. Every production rewind simulates before it executes (I5). Tradeoff: ~30s added latency (§4). Violating it: a rewind with an unbounded blast radius executes before anyone reviews it.

P10. Bounded Blast Radius, By Construction. Every verb and every agent policy declares (or inherits) a cap on rows/tenants/actions touched (I6, I12). Tradeoff: legitimate bulk operations need an explicit override flow. Violating it: one mistake cascades into an outage instead of stopping at a wall.

P11. Compatibility Is Non-Negotiable Across Majors. A Phase-N reader replays a Phase-(N-1) log without translation for ≥ 12 months (I7). Tradeoff: dual-version dispatch code lives in the runtime long after a bump. Violating it: an upgrade makes the historical log unreadable — the one thing a reversibility product cannot survive.

P12. The Runtime Trust Boundary Starts at the SDK. Every SDK-originated message is adversarial input: schema-validated, signed, rate-limited (I8). Tradeoff: per-operation signing cost. Violating it: a compromised app process injects false inverses undetected.

P13. Open the Runtime, Monetize the Coordination Plane. The single-node runtime, SDK, CLI, and verb catalogue are Apache 2.0 (ADR-23); cross-instance replication and the managed control plane are the commercial surface. Tradeoff: gives away the hardest single-node engineering for free. Violating it (blurring the line) erodes both community trust and the commercial thesis.

P14. Convergence Under Bounded Retries, Never Infinite Loops. A saga's compensation either converges within a declared retry budget or escalates to a human (FLP 1985, §5; §19 Phase 7). Tradeoff: some conflicts cannot auto-resolve. Violating it: an unbounded retry loop consumes resources forever without ever reaching a terminal state.

Debugging methodology. 8. Domain Model

Rewind's domain model has five load-bearing types (full signatures in §11): Operation, Inverse, Saga, Checkpoint, IdempotencyKey. This section gives the semantics: how a write becomes an inverse, how inverses compose into a saga, and what a checkpoint anchors.

8.1 State Machine — Saga Lifecycle

From Event To Notes
(none) sdk.saga(name, fn) called open operations begin threading sagaId
open all operations complete without error committed terminal — happy path
open an operation fails compensating coordinator begins reverse-order inverse apply (I11)
compensating all compensations applied compensated terminal — safe rollback

8.2 Worked Example — Forward Then Rewind

A checkout.complete saga performs three operations: (1) Postgres UPDATE orders SET status='paid', (2) Stripe charges.create, (3) SQS publish to shipping.notify.

Forward: the pgproxy pre-image-reads the order row (status='pending', ...) before forwarding the UPDATE; it derives inverse SQL UPDATE orders SET status='pending' WHERE id=42. The SDK wraps the Stripe call; the verb catalogue resolves stripe.charges.create to its inverse builder, producing a refunds.create inverse payload. The SQS wrapper tombstones the publish under the same sagaId. All three Operation records share sagaId=S1; operation 2's causalPredecessors includes operation 1's id (payment depends on the order being marked payable).

Rewind (rewind window --tenant=T --since=... --until=...): the coordinator builds the dependency DAG, reverse-topologically-sorts {op3, op2, op1} to {inv3, inv2, inv1}, applies the SQS tombstone, then the Stripe refund, then the Postgres UPDATE back to pending — in that order, because op1 is a precondition of op2 and must be undone last (I4).

8.3 Malformed-Input Example

An Operation record arrives from the pgproxy with verb: "pg.update.orders" but a args payload whose where-clause references a column dropped by a concurrent ALTER TABLE (schema drift, N.8 of §13). The runtime's schema validator (I8) rejects the record before append: status: "failed", no Inverse row is created, and sdk_message_rejected_total{reason=schema_drift} increments. The forward Postgres statement itself is not blocked (P3 — forward stays fast); only the doomed inverse capture is rejected, and the operation is flagged forward-only retroactively with reason schema_drift_detected so a later rewind window correctly excludes it and surfaces a partial-coverage warning.

8.4 Failure-Path Example — Interrupted Apply

A rewind window apply is 40% through a 12-inverse batch when the rewindd process is killed (SIGKILL, e.g., an OOM-killer event). On restart, the runtime replays its own write-ahead intent log (an internal use of the same hash-chain primitive, I2) for the in-flight rewind, finds inverses {1..5} marked applied, inverse 6 marked pending with no appliedAt, and inverses {7..12} untouched. Recovery: inverse 6 is re-attempted under its idempotency key (I3 — safe even if it had partially executed before the kill); 7–12 resume in their original reverse-causal order. No operator action is required unless inverse 6's idempotency-key lookup itself was lost (FM-4, §23), in which case the runtime halts and pages rather than guessing.

8.5 Consistency Semantics

Within one rewind, the runtime provides read-your-own-rewind consistency: any read issued through the Rewind CLI after a manifest is signed observes the post-rewind state. Across concurrent rewinds on disjoint tenants, there is no ordering guarantee (tenants are independently serializable, matching Postgres's per-row locking — Kleppmann 2017 ch. 7, §5). Cross-tenant rewinds (--all-tenants) are serialized cluster-wide by the saga coordinator to avoid two rewinds racing on shared reference data.

11. Core Schema & Types

All types below are signatures only (No-Code Rule, §4 of the standard): no method bodies, no control flow. Concurrency/persistence/serialization semantics are annotated per type.

11.1 Operation (pkg/runtime, storage record — Postgres row + inverse-log entry)

type Operation = {
  id: OperationId;                   // ULID, monotonic in append order; immutable
  tenantId: TenantId;
  serviceId: ServiceId;              // logical service that issued the op
  verb: VerbId;                      // catalogue entry, e.g. "pg.update.orders"
  args: SerializedArgs;               // canonical-JSON (ADR-05), schema-validated (I8)
  result?: SerializedResult;          // present iff the op completed
  causalPredecessors: OperationId[];  // dependency edges consumed by the saga coordinator
  sagaId?: SagaId;                    // present iff inside a saga
  startedAt: Timestamp;               // wall-clock, external-facing only (ADR-22)
  completedAt?: Timestamp;
  status: "pending" | "ok" | "failed" | "forward-only";
  hash: string;                       // H(args || result || prevHash) — I2
  prevHash: string;
};
// Ownership: written once by the interceptor/SDK, never mutated after `status` settles.
// Concurrency: append-only; reads are lock-free (MVCC via Postgres).
// Persistence: hot tier Postgres, cold tier S3 after 30 days (ADR-03/04).
// Compatibility: envelope carries `__rewindVersion`; N/N-1 readable (I7).

11.2 Inverse (pkg/runtime, storage record)

type Inverse = {
  id: InverseId;
  operationId: OperationId;           // back-reference, 1:1 with Operation
  strategy: "compensating" | "tombstone" | "quiesce-replay" | "forward-only";
  payload?: SerializedInversePayload;
  idempotencyKey: IdempotencyKey;      // I3
  appliedAt?: Timestamp;
  appliedBy?: ActorId;                 // operator, agent, or "auto"
  result?: "applied" | "skipped" | "conflicted" | "failed";
  hash: string;
  prevHash: string;
};
// Ownership: written by the same actor that wrote the Operation; result field mutated
//   exactly once, at apply time, guarded by the idempotency-store lookup.
// Concurrency: apply is serialized per operationId via the idempotency store (I3).
// Persistence/compatibility: identical tier and versioning rules as Operation.

11.3 Saga (pkg/saga)

type Saga = {
  id: SagaId;
  tenantId: TenantId;
  name: string;                        // e.g. "checkout.complete"
  status: "open" | "committed" | "compensating" | "compensated" | "abandoned"; // §8.1
  operations: OperationId[];           // ordered by insertion; NOT the causal order
  startedAt: Timestamp;
  closedAt?: Timestamp;
  policy: SagaPolicy;                  // retry budget, timeout, on-conflict strategy (P14)
};
// Ownership: mutated only by the saga coordinator; replicated via etcd/Raft (ADR-07)
//   from Phase 7 onward — Phase 3's skeleton keeps it single-instance.
// Concurrency: one active state-transition per Saga at a time (I11).

11.4 Checkpoint (pkg/runtime)

type Checkpoint = {
  id: CheckpointId;
  tenantId: TenantId;
  at: Timestamp;
  pgLsn: string;                       // Postgres log-sequence-number anchor
  operationCursor: OperationId;        // last operation included
  inverseCursor: InverseId;            // last inverse included
  hashAnchor: string;                  // hash-chain anchor at this checkpoint
  retentionClass: "hot" | "warm" | "cold" | "audit";
};
// Written every 60s (configurable). Purposes: dependency-graph cut points for rewinds
//   (§8.2), sandbox base images (§20 Phase 8, Chandy & Lamport 1985, §5), compliance
//   attestations (§25).

type IdempotencyKey = {

12.2 Detailed Implementation Steps

Go module + monorepo layout per §10 (cmd/rewindd, pkg/runtime, pkg/shared, pkg/proto); Buf for proto codegen (ADR-06). Implement runtime.v1 gRPC service (pkg/proto/runtime.proto, RFC: gRPC over HTTP/2, §5) with RecordOperation/RecordInverse/GetInverseSet, rejecting any message without a valid per-service signing-key signature (I8, ADR-19). A minimal CLI (rewind log show --tenant=T) round-trips a synthetic record through gRPC → Postgres → display. Daily integrity-check job walks the chain and asserts I2 holds end-to-end.

12.3 Deliverable

A running rewindd binary that accepts a signed synthetic Operation+Inverse pair over gRPC, appends both with a verified hash chain, and displays them via rewind log show.

12.4 Acceptance Criteria

Hash-chain integrity job passes on a 10,000-record synthetic corpus with zero breaks; RecordOperation p99 latency < 2ms in-DC (§4); unsigned/malformed gRPC messages rejected at 100% (fixture fx-unsigned-01, §12.5); rewind log show renders 10,000 records in < 1s.

12.6 Pitfalls

Using wall-clock timestamps for id ordering instead of ULID's embedded monotonic counter — causes ambiguous ordering under clock skew (ADR-22); detected via a skewed-clock fixture, fixed by trusting only ULID's lexicographic order for sequencing. Forgetting to fsync the hash-chain append before ack — silently violates the RPO=0 constraint (§4) on power loss; caught by a kill-9-then-verify test.

12.7 Performance Concerns

Hash computation (SHA-256) is the dominant per-record CPU cost at this stage — batched into groups of 100 before the daily integrity job to amortize syscall overhead. gRPC connection setup (mTLS handshake) is amortized via connection pooling per service, not re-negotiated per call.

12.8 Edge Cases

Two RecordOperation calls racing on the same prevHash (concurrent appenders) — resolved by a single-writer append goroutine per tenant shard (ADR-09); a record whose args fails canonical-JSON normalization (e.g. non-deterministic float serialization) is rejected at the boundary, never partially hashed.

12.9 Failure Analysis

A SIGKILL mid-append leaves at most one dangling record with no hash committed — the recovery scan on next boot finds and discards it (it was never acknowledged, so no downstream system observed it). Blast radius: zero, by construction (P3 — forward stays fast, but ack only follows a successful fsync'd append).

12.10 Operational Notes

OTel spans on every RecordOperation/RecordInverse call from day one (ADR-12); metric inverse_log_append_total{status} exported via Prometheus (ADR-13). No rollback path needed yet — Phase 0 introduces no external side effects to roll back.

13. Phase 1 — Postgres Wire-Protocol Proxy & Inverse SQL Generation

13.1 Objectives

Ship the Mode-B interceptor (ADR-02): a transparent wire-protocol proxy that sits between an application and Postgres, passes traffic through unmodified, and derives compensating SQL for every INSERT/UPDATE/DELETE it observes.

13.2 Detailed Implementation Steps

pkg/interceptor/pgproxy/proxy.go: TCP listener implementing the PostgreSQL frontend/backend protocol (RFC, §5) to decode messages without terminating TLS twice. sql_parser.go: wrap pg_query_go (§5 ref-impls, ADR-08) to classify DML and extract target table / where-clause / set-clause — the Ambassador pattern (Burns 2018, §5) applied at the wire level. inverse_gen.go: for UPDATE/DELETE, issue a synthetic pre-image SELECT over the same predicate before forwarding the original statement, matching the WAL pre-image model (Petrov 2019, ch. 3, §5); derive inverse SQL per verb (INSERT→DELETE WHERE pk=...; UPDATE→UPDATE ... SET <old values> WHERE pk=...; DELETE→INSERT <old row>). Transaction buffering: inverses from one xid commit atomically with the transaction's own outcome (I11's single-saga analogue at the SQL level). Handle prepared statements and the extended-query protocol by caching parsed inverse templates per statement name. Ship the Mode-A logical-decoding plugin (pglogical/output_plugin.c) in parallel as the ADR-02 opt-in path.

13.3 Deliverable

rewind-pgproxy binary that a psql client can connect through with zero observable behavior change, while every DML statement produces a verified inverse in the log.

13.4 Acceptance Criteria

A 50-statement TPC-C-style smoke test passes through the proxy with byte-identical result sets to a direct connection; 100% of DML statements produce an inverse that, when applied, restores the pre-image exactly (fx-tpcc-smoke-01); forward overhead p99 < 2ms in-DC (§4, M1).

Fixture Purpose Expected Output

13.6 Pitfalls

Generated/identity columns silently excluded from the pre-image SELECT — produces an inverse that "restores" a row missing a column, caught only at conformance time; fix is to always SELECT * the pre-image, never a hand-picked column list. Trigger-side-effects on the customer schema are invisible to the proxy — declare "fuzzy equivalence" (the inverse-strategy classification of §11.6, applied per-verb in §14) rather than claim exactness.

13.7 Performance Concerns

The pre-image SELECT doubles round-trips per DML statement — mitigated by pipelining it on the same connection before the original statement is forwarded, not a separate connection. SQL parsing (pg_query_go, cgo boundary) is the single largest per-statement CPU cost — profiled and batched where the extended-query protocol allows template reuse.

13.8 Edge Cases

A statement inside a transaction that later rolls back — its would-be inverse must never be committed to the log (transaction-buffered, discarded on ROLLBACK). TRUNCATE and DDL are refused by default (§14's verb catalogue policy) since no generic inverse exists. Clock skew between the proxy and the customer's Postgres does not affect correctness — sequencing uses ULID (ADR-22), not wall time.

13.9 Failure Analysis

If the pre-image SELECT fails (row deleted by a concurrent transaction between statement arrival and pre-image read), the operation is marked forward-only with reason preimage_race, and forwarded — never silently corrupted (P7). Detection: sdk_message_rejected_total{reason=preimage_race} metric spike is the operator signal.

13.10 Operational Notes

Mode toggle (rewind init --mode=proxy|logical) is a boot-time config, not runtime switchable, to avoid split-brain interceptor state. Dashboard panel tracks forward-overhead p50/p95/p99 against the §4 budget continuously; a two-release breach halts new feature work (§4's stated policy).

The fetch Proxy wrapper adds a verb-catalogue lookup (hash map, O(1)) per call — negligible versus network latency. Queue-wrapper tombstone writes are batched per-flush-interval, not per-message, to avoid amplifying SQS/BullMQ API call volume.

14.8 Edge Cases

A Stripe webhook arriving out of order relative to the SDK's own charges.create call — handled by treating the webhook as informational only; the inverse is derived from the SDK's own recorded result, never from the webhook payload. A saga that never closes (app crash mid-saga) is caught by a TTL-based saga-reaper (§15) that marks it abandoned.

14.9 Failure Analysis

If the gRPC connection to rewindd is down when forward() is called, the SDK's default policy is fail-closed (per P1: no inverse registered means no forward) with an operator-configurable fail-open override for non-critical verbs — documented per-verb in docs/verbs/<verb>.md.

14.10 Operational Notes

Every verb ships a README.md (§10) documenting forward semantics, inverse semantics, idempotency story, and known limitations — required before conformance sign-off (§26). SDK emits OTel spans per wrapped call, tagged with verb and sagaId.

15. Phase 3 — Idempotency Store & Saga Skeleton

15.1 Objectives

Implement the idempotency store (I3, I9) and a single-instance saga skeleton: sequential per-tenant sagas with automatic compensation on failure (§8.1's state machine, minus Phase 7's cross-service distribution).

15.2 Detailed Implementation Steps

pkg/idempotency/store.go: Postgres table indexed on (scope, value) (§11.5); lookup happens before every applyInverse call (I3). ttl_job.go: TTL sweep enforcing I9's boot-time invariant (ttl >= max_retry_window), validated at startup, not just at runtime. pkg/saga/saga.go: implements the §8.1 state table (open→committed|compensating; compensating→compensated|abandoned) as an explicit state machine, not implicit flags — every transition is logged and hash-chained alongside the operations it governs (P5). On saga abort, the coordinator (single-instance in this phase; distributed in §19) executes inverses for completed operations in reverse insertion order (a linear special case of the Phase 7 topological sort) and enforces I11 (the compensation set matches exactly the completed-operations set).

15.3 Deliverable

A two-step saga (charge, then email) where step 2 fails auto-compensates step 1 (the charge is refunded) without operator intervention, and the idempotency key prevents a concurrent retry from double-compensating.

15.4 Acceptance Criteria

Saga-abort-then-compensate completes in < 500ms for a 2-operation saga; idempotency-key lookup adds < 0.5ms p99 to the apply path (§4); fx-double-compensate-01 proves a duplicate compensation attempt is a no-op (I3); TTL boot-check rejects a misconfigured ttl < max_retry_window at startup with a non-zero exit code.

15.5 Conformance Fixtures

Fixture Purpose Expected Output

fx-double-compensate-01 compensation retried under load second attempt is a no-op

15.6 Pitfalls

Scoping the idempotency key too broadly (tenant-scope for a verb that needs saga-scope) causes cross-saga false-positive skips — a subtle bug only conformance testing at N≤100 concurrency surfaces (§14.5's fx-concurrent-100-01 lineage). Forgetting that abandoned is terminal (not retryable) leads to an infinite retry loop violating P14 — enforced by a hard retry-budget counter on the SagaPolicy.

15.7 Performance Concerns

Idempotency-store lookups are the single added hop on every inverse apply — indexed on (scope, value) to keep this an O(log n) B-tree lookup, not a table scan, even at millions of keys.

15.8 Edge Cases

Two sagas racing to compensate the same operation (should be structurally impossible given 1:1 operationId↔Inverse, but tested anyway via fx-concurrent-100-01's saga variant). A saga whose policy specifies zero retries — compensation failure goes straight to abandoned, by design, not a bug.

15.9 Failure Analysis

An abandoned saga is forensically visible (never deleted) with its partial-compensation state intact — a human operator resolves it manually via rewind saga show S1 and a documented runbook (docs/runbooks/abandoned-saga.md, §24).

15.10 Operational Notes

Metric saga_status_total{status} tracked continuously; an abandoned count > 0 pages on-call within the incident-response SLA (§24). Rollback/compatibility: SagaPolicy schema is versioned identically to Operation/Inverse (I7).

16. Phase 4 — Rewind CLI: Dry-Run & Apply Engine

16.1 Objectives

Ship the primary operator surface: rewind window --tenant=T --since=... --until=... producing a dry-run manifest, requiring confirmation, then applying inverses in reverse causal order (P8, P9).

16.2 Detailed Implementation Steps

rewind window command computes the candidate inverse set from the runtime (GetInverseSet, §12), then the dry-run engine simulates apply against a forked staging copy of the relevant log segment and renders a manifest (table + JSON export) — Phase 1's dry-run is "what would run, in what order, against which targets," with full DB-state simulation deferred to Phase 8's sandbox (PhaseDeferred("§20")). The apply engine, on confirmation, resolves each inverse's verb and dispatches: Postgres inverses via the proxy with a bypass header (skips re-capturing an inverse-of-an-inverse unintentionally); HTTP inverses via the SDK's applyInverse; queue inverses via tombstone publish. Reverse-causal order is computed via topological sort over the operation DAG (Lamport 1978, §5; I4), ties broken by decreasing sequence number. Post-apply invariant checks run configurable assertions (row-count deltas, FK integrity, no orphaned saga context) before the manifest is signed (I10).

16.3 Deliverable

An end-to-end rewind: manually corrupt a tenant's data, run rewind window, verify the resulting state matches the pre-corruption state exactly, with a signed manifest on disk.

16.4 Acceptance Criteria

Dry-run completes in < 30s for a 30-minute window of typical load (§4, M-table); apply completes in < 60s for the same window; post-apply invariant suite passes 100% on fx-corrupt-recover-01; a rewind attempted without a prior dry-run is rejected (I5, 0 occurrences target).

16.5 Conformance Fixtures

Fixture Purpose Expected Output
fx-corrupt-recover-01 manual corruption + rewind state matches pre-corruption byte-for-byte
fx-no-dryrun-01 apply attempted without manifest rejected (I5)
fx-topo-order-01 DAG with 3 causal levels apply order matches reverse-topological sort
fx-invariant-fail-01 post-apply FK check fails rewind flagged incomplete, operator alerted

16.6 Pitfalls

Applying inverses in insertion order instead of reverse-causal order "mostly works" on simple fixtures and only breaks under real cross-table dependencies — caught by fx-topo-order-01's explicit 3-level DAG, not by eyeballing simple cases. Treating the dry-run manifest as advisory rather than a hard gate (I5) reintroduces the exact failure mode P9 exists to prevent.

16.7 Performance Concerns

The dependency-DAG topological sort is O(V+E) in the number of operations in the window — bounded by the window size, not the whole log; large windows (> 1M operations) are explicitly out of the < 60s budget and documented as a scaling limit (§29).

16.8 Edge Cases

A rewind window that spans a schema-major-version boundary (I7) — the apply engine dispatches each inverse through its own version's decoder, never assuming uniform schema across the window. A rewind interrupted mid-apply is the subject of §8.4's worked failure-path example (crash recovery via idempotency-key re-attempt, I3).

16.9 Failure Analysis

If post-apply invariants fail, the rewind is marked incomplete (not silently "done") and surfaced with the specific failing invariant (I1–I13) for operator triage — never auto-retried without explicit confirmation, to avoid compounding a partial failure (FM-2, §23).

16.10 Operational Notes

Every rewind window invocation is logged with actor, intent, manifest hash, and outcome (P5); a red banner is shown in the CLI whenever --env=prod is set (§24's operator-mode safety carried forward unchanged from the original draft).

17. Phase 5 — Conflict Detection & Multi-Tenant Hardening

17.1 Objectives

Detect when an inverse conflicts with operations that occurred after the rewind window (concurrent writes), and harden tenant isolation and the permission model.

17.2 Detailed Implementation Steps

pkg/conflict/resolver.go: for each candidate inverse, checks whether its target rows were modified by operations outside the window (pre-image hash comparison against current state); on conflict, offers three strategies — skip (default), force (requires operator co-sign, I6), quiesce-replay (escalates to the Phase-8 PITR path, PhaseDeferred("§35") for full automation, manual in this phase). Multi-tenant scoping: every Operation/Inverse carries tenantId; rewinds are tenant-scoped by default, cross-tenant rewinds require --all-tenants plus co-sign (P6, I6). Permission model v0: Postgres roles runtime.admin / runtime.operator / runtime.read-only, CLI authenticated via mTLS (ADR-19) mapped to those roles. Audit log records actor, intent, manifest hash, outcome for every invocation (P5).

17.3 Deliverable

A test scenario with conflicting concurrent writes surfaces the conflict via rewind window --dry-run and refuses to apply without an explicit operator override.

17.4 Acceptance Criteria

100% of conflicting rows are detected in fx-conflict-detect-01 (zero false negatives); cross-tenant rewind without --all-tenants + co-sign is rejected at 100%; permission model enforces runtime.read-only cannot invoke rewind window --apply (0 successful attempts in fx-perm-readonly-01).

17.5 Conformance Fixtures

Fixture Purpose Expected Output

fx-conflict-force-01 operator issues co-signed force-override conflict overridden, logged
fx-perm-readonly-01 read-only role attempts apply rejected before any inverse runs
fx-crosstenant-01 rewind spanning 2 tenants without flag rejected

17.6 Pitfalls

Detecting conflicts via wall-clock timestamp comparison instead of the causal DAG produces false positives under clock skew — the fix is comparing against the Checkpoint's operationCursor, not timestamps (ADR-22). A permission check implemented only in the CLI (not the runtime) is bypassable by any direct gRPC caller — I6/I8 require server-side enforcement, never client-side-only.

17.7 Performance Concerns

Pre-image hash comparison for conflict detection is O(window size) — batched into a single query per affected table rather than per-row, to avoid N+1 query patterns at scale.

17.8 Edge Cases

A conflict where the "current" state is itself mid-rewind from a separate concurrent rewind — serialized cluster-wide for cross-tenant rewinds (§8.5's consistency semantics); per-tenant rewinds proceed independently since tenants are isolated by construction.

17.9 Failure Analysis

An operator who force-overrides a conflict incorrectly (the "current" state was actually correct) has a forensic trail (the co-sign record, P5) but no automatic undo of the override — this is a deliberate boundary: Rewind will not auto-recurse "rewind the rewind" without a fresh, separately-authorized invocation (§25).

17.10 Operational Notes

docs/operator-guide.md (§10) documents the conflict-resolution playbook. Metric conflict_detected_total{resolution} tracks skip/force/quiesce rates — a spike in force is itself an operational signal worth alerting on.

19. Phase 7 — Distributed Saga Coordinator

19.1 Objectives

Extend Phase 3's single-instance saga skeleton to coordinate inverses across multiple services and multiple rewindd instances, with conflict detection at scale and a provable convergence bound.

19.2 Detailed Implementation Steps

pkg/saga/registry.go: embed etcd (ADR-07) to replicate Saga/Operation state across N rewindd instances via Raft (Ongaro & Ousterhout 2014, §5) — a distributed saga registry replacing Phase 3's single-writer table. coordinator.go: build the cross-service dependency graph from causalPredecessors (§11.1), reverse-topological-sort it respecting service boundaries (P8), and fan out inverses per service with bounded parallelism (ADR-10's backpressure model extended cluster-wide). Conflict resolution extends §17's single-instance resolver: a conflict is detected when an inverse's pre-image disagrees with distributed current state; three strategies (skip / force / quiesce-replay) as before, now coordinated across instances via the registry. Convergence: with an at-most-N-retries policy per inverse (SagaPolicy, P14) and the idempotency-key contract (I3), termination is guaranteed in bounded time — the FLP result (Fischer/Lynch/Paterson 1985, §5) is exactly why this is a bounded-retry guarantee, not a consensus-reaches-agreement guarantee; Rewind never waits for unbounded consensus on a saga's outcome, only on the registry's own Raft log.

19.3 Deliverable

A 5-service synthetic topology (Postgres, Stripe-stub, inventory queue, shipping-label stub, email stub) runs a checkout.complete-style saga; killing any one service mid-saga still converges the surviving services to a correct compensated state within the retry budget.

19.4 Acceptance Criteria

Saga convergence proven under 1,000 randomized chaos scenarios (service kill, network partition, corrupted local state) with zero non-terminating sagas (fx-chaos-1000-01); idempotency store holds correct under 200,000 inverses-per-rewind load test; registry failover (kill the Raft leader) recovers coordination within 5s (etcd's default election timeout envelope).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
fx-5svc-topology-01 5-service saga, no faults all compensations apply correctly
fx-chaos-1000-01 1,000 randomized failure injections zero non-terminating sagas
fx-registry-failover-01 kill the Raft leader mid-saga new leader elected, saga resumes < 5s
fx-200k-idempotency-01 200,000 inverses in one rewind idempotency store holds, no double-apply

19.6 Pitfalls

Assuming the etcd registry's own Raft consensus is the saga's convergence guarantee conflates two different guarantees — the registry guarantees agreement on saga state; convergence of the compensation itself still depends on the bounded-retry contract (P14). Unbounded per-service retry (forgetting a service-level cap) can starve the overall saga even though the registry stays healthy — caught by fx-chaos-1000-01's service-kill variant, not by registry health checks alone.

19.7 Performance Concerns

Cross-service fan-out parallelism is bounded (ADR-10) to avoid a single rewind saturating every downstream service's connection pool simultaneously; the dependency-DAG build is O(V+E) per saga, same bound as §16's single-tenant version, now summed across services.

19.8 Edge Cases

Cross-cloud sagas (services split across AWS and GCP) are detected and surfaced but compensation across them is best-effort, not guaranteed convergent — a known, documented limitation (PhaseDeferred("§35"), production-grade cross-cloud guarantees deferred). A saga whose dependency graph contains a cycle (a modeling bug upstream, not a runtime bug) is rejected at saga-open time, never silently broken at compensation time.

19.9 Failure Analysis

A partitioned registry (etcd loses quorum) blocks new saga state transitions but does not corrupt existing state (Raft's safety property) — in-flight sagas pause, resume once quorum is restored; this is a deliberate availability-for-consistency tradeoff (Brewer 2012, §5; ADR-03's ADR-06-adjacent regime) appropriate for a coordination plane where a paused rewind is safe and a corrupted one is not.

19.10 Operational Notes

docs/adr/adr-07-etcd-registry.md documents the failover runbook; metric saga_registry_leader_changes_total alerts on election churn. Rollback: a Phase-7 rewindd instance can downgrade to Phase-3's single-instance mode by disabling the registry flag — the schema remains compatible (I7).

20. Phase 8 — Time-Travel Sandbox

20.1 Objectives

Ship "spin up production at time T": an isolated, redacted, time-boxed environment materialized from PITR plus replayed forward operations, for pre-rewind dry-run validation, debugging, and agent-training use cases.

20.2 Detailed Implementation Steps

pkg/sandbox/pitr.go: adapters for Postgres-native PITR, AWS RDS, Aurora, Crunchy — restore to the LSN nearest the requested timestamp (delegated to the provider, §1's "does NOT provide" boundary). replay.go: forward-replay engine reads the inverse log's forward-operation history from the restored LSN to the target timestamp, honoring saga boundaries and causal order (same DAG machinery as §16/§19), using a Checkpoint (§11.4) as the consistent cut point — the Chandy-Lamport distributed-snapshot model (1985, §5) applied to "what was the global state at T." External side effects (Stripe calls, etc.) are cordoned: replayed against a stub, never the real API — a replayed Stripe charge would charge a real card, which the sandbox explicitly refuses. Redaction: configurable column-level PII masking via a customer-supplied mapping, applied before the sandbox is reachable. Isolation: dedicated VPC/namespace, whitelisted egress, 24h auto-destroy.

20.3 Deliverable

rewind sandbox spin --tenant=T --at='<timestamp>' returns connection details to an isolated environment reflecting tenant T's state at that timestamp, auto-destroyed at 24h.

20.4 Acceptance Criteria

Median spin-up time < 5 minutes for a tenant under 100 GB (§4, M-table); 100% of external-side-effect verbs are stubbed, never live, in fx-sandbox-stub-01 (zero real API calls observed); redaction policy masks 100% of configured PII columns before first connection is possible.

20.5 Conformance Fixtures

Fixture Purpose Expected Output

fx-sandbox-redact-01 PII columns configured all masked pre-connection
fx-sandbox-autodestroy-01 sandbox left running 24h auto-destroyed, cost surfaced

20.6 Pitfalls

Replaying forward operations in wall-clock order instead of causal order can materialize a state that never actually existed at T (the same class of bug P8 exists to prevent, now applied to replay instead of rewind). Forgetting to cordon a newly-added verb's external side effect (a verb added after Phase 8 shipped) is caught by a conformance check that requires every verb declare its sandbox-replay behavior explicitly, defaulting to "stub" rather than "live."

20.7 Performance Concerns

PITR restore time dominates spin-up latency (§32's capacity model derives this from storage throughput); forward-replay itself is bounded by the same DAG-traversal complexity as a rewind (§16.7), typically a small fraction of total spin-up time.

20.8 Edge Cases

A sandbox spin request for a timestamp before the earliest available PITR restore point is rejected with the earliest-available timestamp surfaced, not silently rounded. Two concurrent sandbox spins for the same tenant at different timestamps are independently isolated (separate namespaces), never sharing state.

20.9 Failure Analysis

A PITR provider outage blocks new sandbox spins but does not affect any other Rewind capability (rewind, saga compensation) — sandbox is architecturally downstream-only, per §1's boundary that Rewind delegates PITR, never reimplements it.

20.10 Operational Notes

Cost-per-sandbox is surfaced in the CLI at spin time and on a dashboard; auto-destroy is enforced server-side (not client-trust-based) so a crashed CLI session cannot leave a sandbox running past 24h.

21. Phase 9 — Agent Safety Layer

21.1 Objectives

Wrap autonomous-agent actions in the ReversibleOperation contract (§11.6) with per-agent quotas, allowlists, and blast-radius caps (§11.7), plus first-class integration with external agent frameworks.

21.2 Detailed Implementation Steps

pkg/agent/envelope.go: every agent action carries agentId/actionId/parentAction/ policyRef (§11.7, I12) — the envelope is the unit the saga coordinator and idempotency store already know how to handle, so no new replay machinery is needed, only a new producer of Operation records. policy.go: enforces quotas (e.g. max 100 reversible actions/hour), allowlists (regex over verb names), blast-radius caps (max rows a single action may touch, P10), and co-sign requirements for sensitive verbs (payments tables) — all evaluated at the gRPC ingress interceptor (I8's adversarial-input boundary extended to agent-originated traffic). langgraph.go and equivalent adapters for AutoGen, the Claude Agent SDK, and the OpenAI Assistants API wrap each framework's tool/node-call boundary so every tool invocation becomes a ReversibleOperation automatically. One-button agent rewind: rewind agent A --since=last-hour resolves to the same rewind window machinery (§16), scoped by agentId instead of tenantId.

21.3 Deliverable

A reference "naughty agent" (a LangGraph agent intentionally misconfigured to over-act) is contained by its policy's blast-radius cap and quota, and rewind agent A cleanly reverts every action it took within the last hour.

21.4 Acceptance Criteria

100% of naughty-agent test scenarios are contained without a manual intervention (fx-naughty-agent-01); quota enforcement holds under 1,000 simultaneous simulated agents with zero quota bypasses; agent action wrap overhead < 50ms p99 (§4, M10); rewind agent A --since=last-hour reverts a 20-action sequence in < 10s.

21.5 Conformance Fixtures

Fixture Purpose Expected Output
fx-naughty-agent-01 agent attempts to exceed blast-radius cap action rejected before it runs
fx-agent-quota-1000-01 1,000 simulated concurrent agents zero quota bypasses
fx-agent-rewind-01 20-action agent sequence + one-button rewind full revert in < 10s

21.6 Pitfalls

Trusting an agent framework's own "this action is safe" signal instead of independently enforcing the policy at the runtime ingress reintroduces exactly the trust-boundary violation P12 forbids — the policy check must happen at rewindd, never only inside the framework adapter. A quota implemented per-process instead of per-agent-cluster-wide is bypassable by an agent spun up across multiple processes — enforced via the same distributed registry as §19.

21.7 Performance Concerns

Policy-lookup at ingress is the dominant cost of the < 50ms agent-wrap budget (§4) — cached per agentId with a short TTL to avoid a registry round-trip on every single action.

21.8 Edge Cases

A nested sub-agent action (parentAction set) inherits the parent's policy unless an explicit tighter policy is declared — never a looser one (a sub-agent cannot escalate its own privileges by declaring a laxer policyRef). An agent that races past its quota in a burst (many actions submitted concurrently) is bounded by an atomic counter at the registry, not a client-side check.

21.9 Failure Analysis

A misbehaving agent contained by its blast-radius cap produces a forensic trail (the rejected-action record) identical in shape to any other rejected operation (I1) — no special-cased agent-failure path, deliberately, so the same tooling (§16's CLI, §23's runbooks) handles both human and agent incidents.

21.10 Operational Notes

24. Operational Readiness

  • Metrics: Prometheus (client_golang, ADR-13) — every invariant (§7) and threat mitigation (§22) has a named counter; every phase's N.10 lists its own metric surface.
  • Tracing: OpenTelemetry spans (ADR-12) on every RecordOperation, RecordInverse, and rewind-apply step; span attributes include tenantId, sagaId, verb.
  • Structured logging: zerolog JSON (ADR-11); every log line carries operationId or sagaId where applicable for cross-referencing with the inverse log.
  • Dashboards: the Phase-6 Grafana template (§18.10) plus per-agent dashboards (§21.10); dashboard drift is a CI-gated check (§18.10).
  • Alerting philosophy: page on anything that violates an invariant (I1–I13) or breaches a §4 budget for two consecutive releases; do not page on expected, bounded conditions (e.g. a single skip-resolved conflict).
  • SLOs: forward-path p99 < 2ms in-DC (M1); rewind apply < 60s for a 30-minute window (M5); zero unresolved hash-chain breaks (FM-1) at any time.
  • Incident response: Sev-1 (any FM-1/FM-4/T3/T4 class event) — page within 15 min, written postmortem within 24h, blameless, filed under the relevant docs/failure-analysis/ entry.
  • Named runbooks: docs/runbooks/abandoned-saga.md (FM-3), docs/runbooks/hash-chain-break.md (FM-1), docs/runbooks/registry-partition.md (FM-6), docs/runbooks/retention-conflict.md (FM-9).
  • Backup/restore: the inverse log's own hot tier is itself backed up on the same cadence as customer data (Tier-1, P2); cold-tier S3 object-lock is the log's own disaster-recovery target.
  • Deployment topology: one rewindd instance per environment minimum; Phase 7 adds multi-instance clusters coordinated via the etcd-backed saga registry (§19).
  • Canary / rolling upgrade / rollback / migration: a new rewindd version is canaried against a synthetic-load shadow tenant before promotion; rolling upgrade requires N/N-1 schema compatibility (I7); rollback to the prior binary is always safe because the log format never regresses within the compatibility window (§25).

25. Compatibility & Versioning

  • Wire compatibility: the runtime.v1 gRPC service (§11) is additive-only within a major version — new fields, never renamed/removed ones, per standard Protocol Buffers evolution rules (§5 RFC).
  • Storage/schema evolution: every record's __rewindVersion envelope field drives version-dispatch on read (I7); a schema-major bump requires a dual-write period of at least one release before old-format writers are retired.
  • API stability: ReversibleOperation.version (§11.6) is the per-verb semver; verb-schema changes bump the verb's own major independent of the runtime's major.
  • Migration: golang-migrate (§12.2) manages hot-tier schema migrations; cold-tier S3 objects are immutable once written (object-lock, ADR-04) and are never migrated in place — a reader-side translation layer handles old formats instead.
  • Deprecation policy: a deprecated verb or field is marked in the catalogue with a removal-not-before date of at least two minor releases out; conformance suite continues testing it until removal (§14.5).
  • SemVer policy (ADR-20): MAJOR — breaking schema/wire change; MINOR — new verb, new optional field, new CLI subcommand; PATCH — bug fix, no contract change.
  • Rolling-upgrade guarantees: a cluster may run N and N-1 rewindd instances simultaneously for the duration of a rolling upgrade; the saga registry (Phase 7) tolerates mixed-version membership for the same window (I7).

26. Testing & Verification Strategy

  • Unit tests: Go testing + testify (ADR-14), ≥80% coverage on pkg/runtime, pkg/interceptor, pkg/saga, pkg/idempotency.
  • Integration tests: against real Postgres 14/15/16 and Node 20/22, per §11's Phase-1 locked floor.
  • Property-based tests: gopter (ADR-14) on the hash-chain primitive (I2) and the idempotency contract (I3) — e.g. "for all N ≥ 1, applying an inverse N times equals applying it once."
  • Differential tests: Mode A (logical-decoding) and Mode B (wire-proxy) interceptors run against the same statement corpus and must produce equivalent inverses (§13.3).
  • Fuzzing: native Go fuzzing (ADR-15) on the SQL-inverse generator; AFL++ on the C logical-decoding plugin (§5, ADR-15's rejected-choice-wins regime).
  • Chaos tests: 1,000 randomized failure injections per release against the Phase-7 saga coordinator (fx-chaos-1000-01, §19.5); kill-9 tests against the Phase-0 hash chain and the Phase-4 apply engine.
  • Deterministic replay: the conformance harness (§7's debugging methodology) reruns every fixture from a fixed seed and asserts I1–I13 after each step.
  • Soak tests: 1-hour sustained 50k-tps load (§18.5) as a release gate, not an optional nightly job.
  • Fault injection: interrupting an inverse apply at every checkpoint (the conformance protocol of §14.5) and asserting the resulting state is always committed-or-rolled-back, never half-applied.
  • Conformance suite: every verb passes forward-correctness, inverse-correctness, idempotency (N=1,2,5), and concurrency-safety (N≤100) before release (§14.5); a failing run blocks the verb's release (FM-7).
  • Performance-regression gating: every M-table target (§28) is a CI gate; two consecutive regressed release candidates halt new feature work (§4's stated policy).

29. Scalability Analysis

Stays constant: per-operation hash computation cost (O(1), §12.7); per-verb conformance-suite runtime (bounded by fixture count, §14.5); the shape of the Reversibility Contract (§11.6) regardless of scale.

Grows: inverse-log storage (linear in write volume × amplification, §32 #1); dependency-DAG size within one rewind window (O(V+E) in operations touched, §16.7, §19.7); idempotency-store size (bounded by TTL, §11.5, so effectively steady-state, not unbounded).

Named bottlenecks, in order: (1) single-instance inverse-log append throughput (~200,000 ops/sec ceiling before manual sharding, §9 ADR-03's rejected-choice-wins regime, §32 #8); (2) the pre-image SELECT's doubled round-trip on the Mode-B proxy (§13.7); (3) cross-service fan-out parallelism during a large rewind (§19.7); (4) PITR restore throughput dominating sandbox spin-up (§20.7, §32 #5).

Horizontal scaling: per-tenant sharding of the append path (§18.7) is the primary lever once bottleneck (1) is hit; Phase 7's saga registry is what makes multi-instance coordination correct rather than merely possible.

Vertical scaling: CPU-bound SQL parsing (§13.7) benefits from more cores up to the point pre-image I/O dominates (§4's CPU-assumption row); memory scaling is bounded by the idempotency LRU cache budget (§4), not by log size (the log lives on disk, not in memory).

Coordination overhead: Raft consensus (ADR-07) adds a bounded per-transition latency to saga-state changes (§19.4's < 5s failover target) but does not sit on the forward path at all (P3) — coordination overhead is paid only by the rewind/saga-abort path, never by the hot path.

Practical ceiling and levers beyond it: a single logical tenant exceeding the ~200,000 ops/sec single-instance ceiling requires either (a) manual tenant sharding across rewindd instances (available today) or (b) the deferred cross-cloud/cross-shard saga convergence work (PhaseDeferred("§35")) if that tenant's services also span multiple clouds.

30. Mental Models & First Principles

MM1 — An inverse is a proof obligation, not a convenience. Predicts: any verb without a provably-correct inverse must be declared forward-only, never shipped as an optimistic guess. Bug class without it: a rewind silently "succeeds" against a verb that never actually restored prior state. Applies in §14.2, §11.6.

MM2 — Causal order, not wall-clock order, is the only order a rewind may trust (Lamport 1978, §5). Predicts: any sequencing decision keyed on a timestamp instead of the causal DAG is a latent bug. Bug class: incorrect replay order under clock skew. Applies in §8.2, §16.2.

MM3 — A hash chain proves tampering happened; it does not prevent it. Predicts: detection-and-response framing, never "the log cannot be tampered with." Bug class: false security theater that skips building the response path (quarantine, restore). Applies in §12.2, §22 (T3/T4).

MM4 — Idempotency is a property of the operation, not the network. Predicts: an inverse must be safe under at-least-once delivery regardless of transport guarantees. Bug class: double-application under a retry storm. Applies in §15.2, §7 (I3).

MM5 — The rewind command is more dangerous than the data it touches. Predicts: privilege modeling must scope the verb (rewind-authority), not just the table. Bug class: privilege escalation via a legitimate-looking rewind. Applies in §17.2, §22 (T2).

MM6 — A saga is a state machine with an explicit abandon state, not an infinite retry loop. Predicts: any compensation path needs a bounded-retry contract wherever it composes across services. Bug class: resource-starving infinite retries. Applies in §15.2, §19.2, P14.

MM7 — A consensus protocol guarantees agreement on state, not correctness of the workflow built atop it. Predicts: conflating etcd's Raft guarantee with saga-level convergence is the exact pitfall a distributed saga coordinator must avoid. Bug class: "the registry is healthy" mistaken for "the saga converged." Applies in §19.2, §19.6.

MM8 — Reversibility coverage has an honest ceiling and is never reported as 100%. Predicts: forward-only operations are declared explicitly, never optimistically assumed reversible. Bug class: a false sense of safety that encourages riskier action because "there's an undo button." Applies in §14.2, P7.

MM9 — A checkpoint is a consistent cut, not a backup (Chandy & Lamport 1985, §5). Predicts: a checkpoint alone cannot restore state without the log segment it anchors. Bug class: assuming checkpoints are self-sufficient restore points. Applies in §11.4, §20.2.

MM10 — The forward path optimizes for speed; the rewind path optimizes for proof. Predicts: every performance tradeoff resolves by asking which path it sits on. Bug class: shaving correctness checks off the rewind path to hit a speed target. Applies in §4, P3.

Temporal makes the opposite bet on authoring: every compensation is hand-written per workflow step, trading Rewind's auto-capture convenience for deterministic-replay guarantees that hold even when a workflow's business logic is genuinely bespoke. It wins in the niche where workflows are greenfield-authored and determinism-by-construction matters more than retrofitting reversibility onto an already-running system.

Debezium treats the Postgres WAL purely as an append-only event source for propagation, with no notion of "undo" at all. It wins where the goal is one-directional (search-index sync, cache invalidation, downstream analytics) rather than reversal — and is precisely the reference implementation Rewind studies for logical-decoding consumption (§5) without adopting its no-inverse model.

Aurora Backtrack implements "rewind" natively inside the storage engine for one managed database cluster — the closest real-world sibling to Rewind's core promise. It wins when the entire reversibility need is confined to a single Aurora cluster and there is no requirement to correlate the rollback with external API calls or queue state, which is exactly the case Rewind exists to cover that Backtrack cannot.

Vitess solves an entirely different problem behind the same architectural shape as Rewind's Mode-B proxy (§13.2, ADR-02) — a transparent layer in front of a database — but optimizes for horizontal shard routing and connection pooling, never capture-and-invert. It wins whenever the operational problem is scaling one logical database across many physical shards, a concern Rewind's proxy deliberately stays out of (§1's "does NOT provide" boundary).

32. Back-of-Envelope Capacity Model

  1. Hot-tier storage growth/day = throughput × record size × amplification × seconds/day = 50,000 ops/s × 400 B × 1.6 (§4) × 86,400 s ≈ 2.76 TB/day/instance before compaction.
  2. Cold-tier monthly volume = 2.76 TB/day × 30-day hot retention ≈ 82.8 TB/month migrated to S3 before compression (chained from #1).
  3. Idempotency LRU cache capacity = 512 MiB budget (§4) ÷ ≈150 B per key+metadata ≈ 3.4M resident keys — derived directly from the §4 memory ceiling.
  4. Max concurrent proxied app connections = 65,536 hard FD ulimit (§4) ÷ 2 FDs per proxied connection ≈ 32,768 connections/instance.
  5. Sandbox spin-up budget breakdown — at an assumed 500 MB/s managed-PITR restore throughput, a 100 GB DB restores in 100,000 MB ÷ 500 MB/s = 200 s ≈ 3.3 min, leaving ≈ 1.7 min of the M6 < 5 min target for forward-replay.
  6. Agent-quota overhead budget = 100 actions/hour/agent (§21.2) × 50ms p99 wrap overhead (M7) = 5s/hour of serialized overhead per agent — negligible against the hour-long quota window.
  7. Concurrent-rewind FD headroom = 100 concurrent rewinds cluster-wide (§4) × ≈50 FDs/active rewind (per-service fan-out) = 5,000 FDs, a ≈13× headroom against the 65,536 hard ulimit.
  8. Throughput headroom before manual sharding = ≈200,000 ops/sec single-instance ceiling (ADR-03) ÷ 50,000 ops/sec baseline (§4) = 4× headroom before a tenant must be sharded across instances.
  9. Ingress bandwidth at baseline = 50,000 ops/s × 400 B/op = 20 MB/s sustained gRPC ingress/instance — well under a 1 Gbps (125 MB/s) NIC, leaving headroom for the pre-image SELECT's doubled round trips (§13.7).
  10. Phase-0 proof-of-correctness storage floor = 10,000-record synthetic corpus (§12.5) × 400 B ≈ 4 MB — confirms Phase 0's scope is correctness, not scale.

34. Alternative Architectures (Roads Not Taken)

34.1 Event-Sourcing-First (Greenfield)

App -> Event Store (append-only) -> Projections (read models)
                                  -> Time-travel = replay events to T

Regime where it wins: greenfield systems designed from day one for full auditability and replay (e.g. a from-scratch ledger). Real system: EventStoreDB. Rejection: Rewind's value proposition is retrofitting reversibility onto an existing, running Postgres + Node system without a rewrite (§1) — event sourcing requires exactly the architectural rewrite Rewind exists to avoid.

34.2 Backup + PITR-Only (No Runtime Layer)

DB -> periodic snapshot -> WAL archive -> restore to T (whole DB, whole downtime)

Regime where it wins: single-datastore systems with no cross-service correlation requirement, where minutes-to-hours of restore downtime is acceptable. Real system: standard Postgres PITR, or Aurora Backtrack (§31) for a managed variant. Rejection: loses every correlated cross-service effect since the snapshot — the "your DB rolled back, your downstream API didn't" failure §3's diagram is built to prevent.

34.3 Centralized Two-Phase-Commit Coordinator

App -> [Prepare] -> TC -> [Commit/Abort all] -> Services (DB, API, Queue)

Regime where it wins: a closed system where every participant can implement the 2PC prepare phase (all-internal services, no third-party APIs). Real system: XA-transaction JTA deployments. Rejection: Helland (2007, §5) shows 2PC does not survive contact with third-party APIs (Stripe, Twilio) that will never implement a prepare phase — Rewind's compensating-action model (Gray 1981) is precisely the alternative Helland's paper argues for.

34.4 Manual Runbook + On-Call Culture (No Automation)

Incident -> Page on-call -> Hand-write recovery SQL/script -> Manual verify -> Close

Regime where it wins: very low-incident-rate systems where building and maintaining a reversibility runtime costs more than the expected cost of rare manual incidents. Real system: this is the de facto state of the art at most SaaS companies today. Rejection: manual runbooks fail predictably under stress — fatigue, time pressure, incomplete cross-service knowledge — exactly the failure mode motivating Rewind's existence (§2).

36. Glossary

  • Agent action envelope — the AgentAction record (§11.7) wrapping an autonomous agent's operation with agentId/policyRef for retroactive enforcement.
  • Blast-radius cap — a declared ceiling on rows/records a single verb or agent action may touch (P10, I6, I12).
  • Causal predecessor — an operation whose effects are a precondition for another's correctness; drives the saga coordinator's reverse-order computation (I4).
  • Checkpoint — a consistent cross-system anchor (LSN + operation cursor + inverse cursor + hash anchor) written every 60s (§11.4); a dependency-graph cut point and sandbox base image, never a backup by itself (MM9).
  • Co-sign — the second-operator signature required before a sensitive rewind executes (I6).
  • Compensating action — a forward operation whose effect is the inverse of a previously-recorded operation (Gray 1981).
  • Conflict resolver — the component detecting when an inverse's pre-image disagrees with current state (§17.2).
  • Conformance suite — the mandatory test pack every verb must pass before release (§14.5, §26).
  • Distributed saga registry — the etcd/Raft-replicated store of saga/operation state across rewindd instances (§19.2).
  • Dry-run — a simulated rewind producing a manifest without applying it; mandatory by default for production rewinds (I5, P9).
  • Forward-only operation — an operation explicitly declared as having no inverse (P7); excluded from rewind windows, surfaced at dry-run.
  • Hash chain — the integrity scheme where every log record references the hash of its predecessor (I2); proves tampering happened, does not prevent it (MM3).
  • Idempotency key — a deterministic key guarding against double-application of an inverse (§11.5, I3).
  • Inverse — the compensating action attached to a forward operation (§11.2); one of four strategies (compensating, tombstone, quiesce-replay, forward-only).
  • Inverse log — the append-only, hash-chained record of every operation and its inverse (P2).
  • Logical decoding — Postgres's mechanism for streaming committed changes; the basis of interceptor Mode A (§5, §13.2).
  • Operation — any side effect crossing the Rewind boundary (§11.1): a Postgres write, an HTTP call, a queue publish.
  • PITR — point-in-time recovery; a delegated precondition for the Rewind sandbox (§1, §20.2), never reimplemented by Rewind.
  • Pre-image — the row state read before a Postgres UPDATE/DELETE is forwarded, used to derive the inverse SQL (§13.2).
  • Quiesce-replay — an inverse strategy that quiesces a partition, restores from PITR, and replays surviving forward operations; slow, last-resort (§17.2).
  • Retention conflict — a detected clash between a rewind and a configured retention/compliance policy (I13, FM-9).
  • Reversibility contract — the ReversibleOperation interface (§11.6) every reversible operation satisfies.
  • Reverse-topological sort — the ordering algorithm applying inverses in strict reverse causal order (§16.2, P8).
  • Rewind — the act of replaying inverses across a window of operations to revert state (§16).
  • RPW-Verified — Rewinds-per-week with verified post-rewind state restoration; the metric that only increments on a signed, invariant-passing manifest (I10).
  • Saga — a named sequence of operations sharing a saga context and an all-or-nothing inverse semantics (§11.3, §8.1).
  • Saga coordinator — the component ordering inverses across services with conflict detection and bounded-retry convergence (§19.2).
  • Sandbox — a time-boxed, redacted, isolated environment materializing production state at a past timestamp (§20).
  • Schema-version dispatch — the reader-side mechanism selecting the correct decoder for a record's __rewindVersion (I7).
  • Tombstone — an idempotent marker indicating an operation should be treated as never-having-happened by downstream consumers (§14.2).
  • ULID — a lexicographically-sortable, monotonic identifier used for Operation.id (ADR-22), avoiding wall-clock ordering ambiguity.
  • Verb — a catalogued operation (e.g. pg.update.orders, stripe.charges.create) with declared forward, inverse, and idempotency semantics (§11.6, §14).
  • Verb catalogue — the registry of all supported verbs and their inverse strategies (§11.6, moat per §2).
  • Wire-protocol proxy — the Mode-B Postgres interceptor transparently passing frontend/backend protocol traffic while deriving inverses in flight (§13.2, ADR-02).
