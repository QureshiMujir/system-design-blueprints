⬜ Phase 0 — Skeleton: unified signal model, OTLP types, in-memory oracle §12

Objectives
  • Stand up the workspace + obs-core; depend on #83/#78/#85.
  • Define the unified model: Resource/Scope/Labels, Metric/DataPoint/HistogramPoint, Span/Trace, LogRecord, Exemplar, TraceId/SpanId/ResourceHash, TenantId, OTLP types.
  • Implement identity normalization (I1/I2) and a single-tenant in-memory oracle that ingests OTLP and answers queries by brute force (the reference, principle 14).
Deliverable
  • Decode an OTLP fixture into the model, normalize identity, ingest into the oracle, and answer a metric/log/trace/pivot query; obsctl inspect prints decoded signals.
Acceptance
  • TraceId/SpanId normalize identically from hex and bytes; malformed rejected (I1).
  • ResourceHash stable under attribute reordering (I2).
  • The oracle answers a hand-checked metric/log/trace/pivot query correctly.
Fixtures
  • otlp/decode_metrics.json, otlp/decode_traces.json, otlp/decode_logs.json, correlation/oracle_pivot.json, otlp/malformed_ids.json.
Pitfalls
  • trace_id hex-vs-bytes / casing drift → the #1 correlation breaker; normalize once, test both encodings (I1).
  • Resource canonicalization must sort + dedupe deterministically (I2) — unsorted attrs → hash mismatch → broken join.
  • Float NaN/Inf in metric values — define handling now.
  • OTLP nesting (ResourceMetrics → ScopeMetrics → Metric → DataPoint) is deep — map carefully.

⬜ Phase 1 — OTLP ingestion pipeline: receivers, batching, backpressure §13

Objectives
  • Build the data-plane front door: OTLP/gRPC + OTLP/HTTP receivers, scrape, and the pipeline (batch → transform → relabel-hook → fan-out) with strict backpressure (I4) and idempotency (I15).
Deliverable
  • An obs-ingest process accepts OTLP over gRPC + HTTP and scrape, normalizes, batches, and fans out; under load it backpressures (no OOM); examples/ingest_otlp.
Acceptance
  • OTLP for all three signals decoded + validated (I7); malformed rejected, no UB.
  • Backpressure bounds queue depth under a slow consumer (I4); shed-count is observable, no OOM.
  • Duplicate batches deduped (I15); identity normalized once (I1/I2).
  • Ingest p99 (accept→enqueue) within target headroom.
Fixtures
  • otlp/grpc_roundtrip.json, otlp/http_roundtrip.json, otlp/scrape_exemplars.json, otlp/backpressure_shed.json, otlp/dedup.json.
Pitfalls
  • Unbounded queues "just to be safe" → OOM under a slow store (the classic) — bound everything (I4).
  • gRPC/HTTP2 flow control vs the internal pipeline backpressure — both must compose, not fight.
  • Protobuf decode allocating per-field → batch + arena to control allocation.
  • Validating after allocating large buffers → validate size first (I7).
  • Idempotency key choice (series/trace/log key + ts) must be stable.

⬜ Phase 2 — Metrics store (TSDB on #83) with exemplar slots §14

Objectives
  • Build the metrics pillar's backend on #83: series index, Gorilla-encoded sample chunks, head + WAL + immutable blocks, the metric query path, staleness, and — the correlation hook — exemplar slots (I3).
Deliverable
  • Ingest metric data points (with exemplars), persist + replay WAL, and answer a raw selector query over a snapshot; examples/metric_query (raw selectors); exemplars stored.
Acceptance
  • Stored + replayed samples match ingested (lossless within float encoding) vs the oracle.
  • Exemplars stored per (series, bucket) and retrievable (I3 scaffolding).
  • Staleness: a stopped series is marked stale, not carried forward (I13).
  • Block publication atomic; queries never see a torn block (I11).
  • Storage ≤ 1.5 B/sample (§4).
Fixtures
  • metrics/append_query.json, metrics/wal_replay.json, metrics/exemplar_store.json, metrics/staleness.json, metrics/block_atomicity.json.
Pitfalls
  • Gorilla encoding edge cases (first sample, value resets, NaN) — test against #83's contract.
  • Exemplar slot overflow (more exemplars than slots) → ring-buffer eviction policy (keep recent/representative).
  • WAL replay must reconstruct the exact head; a replay bug → silent data loss → checksum + oracle.
  • Staleness lookback window mis-set → phantom values or premature gaps (I13).
  • Out-of-order samples (a late sample for an old timestamp) → define (reject / accept within head window).

⬜ Phase 3 — Trace store: span ingestion + assembly + index §15

Objectives
  • Build the trace pillar's backend: span ingestion, trace assembly (group by trace_id → parent/child tree), a trace index (by trace_id, the pivot lookup) + a search index (service/operation/duration/status/tags), with the sampling hook (head now; tail P8).
Deliverable
  • Ingest spans, assemble traces, look up a trace by id, and search traces by service/operation/duration; examples/trace_search.
Acceptance
  • by_id returns the correctly assembled trace tree vs the oracle; p99 < 100 ms (§4).
  • Trace search matches the oracle for service/operation/duration/status/tag queries.
  • Out-of-order + orphan spans handled (assembled when the parent arrives, or kept as roots).
  • Block atomicity (I11).
Fixtures
  • traces/ingest_by_id.json, traces/assemble_tree.json, traces/out_of_order_spans.json, traces/orphan_span.json, traces/search.json.
Pitfalls
  • Out-of-order spans (a child arrives before its parent) → buffer/assemble lazily; don't drop.
  • Orphan spans (parent never arrives, e.g. cross-service sampling gap) → keep as a partial-trace root, don't lose.
  • Trace index must be by the normalized trace_id (I1) — drift breaks the pivot.
  • Large traces (thousands of spans) → bounded assembly; stream the tree.
  • Duplicate spans (retry) → dedup on (trace_id, span_id) (I15).

⬜ Phase 4 — Log store: label index (#78) + columnar body (#85) §16

Objectives
  • Build the logs pillar's backend: a #78 inverted index over labels (incl. trace_id as a first-class indexed label) + a #85 columnar body for the message and high-cardinality fields; the stream model; the index-then-scan log query path.
Deliverable
  • Ingest logs (indexed by labels incl. trace_id), answer a label-filtered log query, and join logs by trace_id; examples/log_query.
Acceptance
  • Label-filtered + line-filtered queries match the oracle.
  • by_trace(trace_id) returns exactly the logs of that trace (I5) vs oracle; p99 < 30 ms for the join (§4).
  • Storage ≤ 0.5× raw (compression, §4).
  • Block atomicity (I11).
Fixtures
  • logs/append_query.json, logs/label_filter.json, logs/line_filter.json, logs/by_trace_join.json, logs/compression_ratio.json.
Pitfalls
  • Indexing the body (full-text everything) → cardinality/cost explosion — index labels, scan the body (the Loki/Honeycomb lesson, ADR-6).
  • trace_id left in the body instead of indexed → the join becomes a scan → blows the 30 ms target — promote it (§8.2, I5).
  • Stream explosion: too many unique label sets → the cardinality limiter (P7) governs this too (I6).
  • Columnar encoding choice per column (dictionary for low-cardinality, raw for high) — via #85.
  • Log timestamp ordering within a stream (mostly ordered; handle late).

⬜ Phase 5 — The correlation layer: exemplars + trace↔log joins + span→metrics §17

Objectives
  • Build the unification (the platform's reason to exist): resolve exemplars (metric→trace, I3), trace↔log joins (I5), span→RED/USE metric derivation (I8), and the resource join (I2) — composing them into the pivot (§8.11). The most novel and distinctive subsystem.
Deliverable
  • The full correlation set: resolve a metric exemplar to a trace, join a trace to its logs (both directions), derive RED metrics from spans, and run a metric→trace→log pivot; examples/pivot_correlation; matches the oracle.
Acceptance
  • Exemplar resolves to the correct trace or SampledOut — never a dangling 404 (I3) vs oracle.
  • Trace↔log join returns exactly the right logs/trace (I5) vs oracle.
  • Span-derived RED metrics match a re-derivation over the same span window (I8) and match the oracle.
  • A full pivot (metric→trace→logs) returns the correct chain; correlation-lookup p99 < 30 ms (§4).
Fixtures
  • correlation/exemplar_to_trace.json, correlation/exemplar_sampled_out.json, correlation/trace_to_logs.json, correlation/log_to_trace.json, correlation/span_to_red.json, correlation/full_pivot.json.
Pitfalls
  • A dangling exemplar (the trace was dropped) → must return SampledOut, never an unexplained miss (I3) — this is the subtle correctness case the whole layer exists to get right.
  • Identity drift (un-normalized trace_id in one store) → the join silently misses → the #1 failure; assert normalization (I1) at every join.
  • Span→metric derivation non-determinism (window boundaries, ordering) → fix the window + order (I8) or RED ≠ trace reality.
  • The pivot composing stale snapshots across stores → all hops must use the same snapshot (I12).
  • USE derivation needs host/resource metrics that may not be present → degrade gracefully.

⬜ Phase 6 — Unified cross-signal query engine §18

Objectives
  • Build the one query engine (principle 2): a PromQL-subset (metrics), a LogQL-subset (logs), trace search, and — the headline — cross-signal joins (the pivot as a first-class query), all over a consistent snapshot (I11/I12), with the result cache (#59).
Deliverable
  • Answer PromQL, LogQL, trace-search, and a cross-signal pivot query over a snapshot; examples/{metric_query,log_query,trace_search,pivot_correlation}; all match the oracle.
Acceptance
  • PromQL/LogQL/trace-search results match the oracle (floats within ε); determinism per snapshot (I12).
  • The cross-signal pivot returns the correct chain (== the P5 pivot, now expressed as a query).
  • Staleness handled (I13); cache hits return identical results (snapshot-keyed).
  • Latency targets met (§4: instant < 50 ms, range < 2 s, log < 3 s, trace-id < 100 ms).
Fixtures
  • promql/*.json (selectors, rate, histogram_quantile, aggregations), logql/*.json, trace_search/*.json, correlation/query_pivot.json, query/snapshot_determinism.json, query/cache_consistency.json.
Pitfalls
  • PromQL semantics subtleties: counter rate over resets, range-vector alignment, histogram_quantile interpolation, staleness lookback (I13) — match Prometheus exactly (differential).
  • A query touching multiple stores must pin one snapshot (I12) — mixing snapshots → inconsistent cross-signal results.
  • Cache keyed without the snapshot id → stale/incorrect cached results — include it (I12).
  • Float aggregation order → fix it (sorted by series id) for determinism (I12).
  • The pivot plan must short-circuit on SampledOut/NotFound (I3), not error.

⬜ Phase 7 — Cardinality management §19

Objectives
  • Bound the platform's existential constraint (§4.1): per-tenant active-series / index-term ceilings, label limits, and relabel/drop rules at ingest — enforced before storage (I6), platform-wide (metrics + log index + span attrs).
Deliverable
  • Cardinality limits enforced across all signals; an offending label (user_id) is rejected/relabeled before storage; obsctl cardinality reports the top offenders.
Acceptance
  • Active series stay ≤ the tenant ceiling under a cardinality-bomb input (I6); the platform does not OOM.
  • An unbounded label is rejected or relabeled per policy; counted and reported.
  • The same limiter governs metrics, log streams, and span attributes (platform-wide, §8.14).
Fixtures
  • cardinality/series_ceiling.json, cardinality/label_length_limit.json, cardinality/relabel_drop.json, cardinality/relabel_hash.json, cardinality/cross_signal_bound.json.
Pitfalls
  • Counting active series accurately + cheaply (a probabilistic counter, e.g. HLL, vs exact) — pick per the accuracy/cost tradeoff.
  • Rejecting after the series is created → too late (already in the head) — check before the append (I6).
  • Relabel rules with subtle ordering (drop before rename) → define + test rule order.
  • A tenant at its ceiling silently dropping new useful series → alert the operator (card_rejected spike), don't fail silent.
  • Cross-signal: a label exploding the log index but not metrics → the limiter must see logs too.

⬜ Phase 8 — Tail-based sampling §20

Objectives
  • Decide after seeing the whole trace: buffer all spans of a trace until completion or a decision window, then keep/drop the whole trace atomically (I9), under a hard memory bound (principle 5, I4) — reconciled with exemplar references (I3).
Deliverable
  • Tail sampling that keeps all error/slow traces + a probabilistic sample of the rest, whole-trace-atomically, under a memory cap; observable keep-rate; integrates with trace-store + correlate.
Acceptance
  • A trace is kept or dropped as a whole — never partially (I9) vs the partial-trace detector.
  • Error/slow traces kept; probabilistic policy reproducible with a seed (§8.12).
  • Buffer memory stays under the cap under load; shedding to head sampling is graceful (I4).
  • An exemplar-referenced trace is not silently dropped (I3, coordinated).
Fixtures
  • sampling/whole_trace_atomic.json, sampling/keep_errors.json, sampling/keep_slow.json, sampling/probabilistic_seeded.json, sampling/buffer_shed.json, sampling/exemplar_referenced_kept.json.
Pitfalls
  • Partial traces (some spans decided before others arrive) → the classic tail-sampling bug; the decision must be atomic per trace (I9).
  • The decision window vs late spans: a span arriving after the decision → drop (or the trace was kept, append) — define precisely.
  • Buffer memory blowup from long-tail traces → the window cap + the memory cap + shedding (principle 5).
  • A dropped trace that an exemplar points at → dangling exemplar (I3) — honor the keep signal or mark sampled-out.
  • Probabilistic policy must be consistent per trace (hash trace_id, not per-span) → whole-trace consistency.

⬜ Phase 9 — Alerting: rules + multi-window multi-burn-rate SLO §21

Objectives
  • Evaluate rules (PromQL/LogQL predicates over windows) and multi-window multi-burn-rate SLO alerts (fast + slow burn against an error budget) — timely, non-flapping, correlation-linked (the firing alert carries an exemplar trace).
Deliverable
  • Rule + SLO burn-rate alerting; a fast-burn alert fires within a minute of an acute SLO violation; a slow-burn alert catches chronic drift; firing alerts carry a trace link.
Acceptance
  • Multi-window multi-burn-rate fires correctly for acute and chronic violations and does not flap on transient blips (vs a scripted SLI series).
  • Fast-window detection < 1 min (§4); rule eval within one interval.
  • A firing alert carries a representative exemplar trace (correlation link).
Fixtures
  • slo/burn_rate_fast.json, slo/burn_rate_slow.json, slo/no_flap_on_blip.json, slo/multi_window_combine.json, slo/alert_carries_exemplar.json.
Pitfalls
  • Single-window burn-rate alerts either flap (short window) or detect late (long window) → the multi-window combination is the fix — implement both halves (the common mistake is one window).
  • Burn-rate math: burn rate = (error rate) / (1 − objective); thresholds per window must be derived correctly.
  • Alert eval reading an inconsistent snapshot → pin one snapshot per eval (I12).
  • for_ debounce vs fast detection — tune; too long delays, too short flaps.
  • Resolving an alert (hysteresis) to avoid resolve/fire oscillation.

⬜ Phase 10 — Retention, downsampling, rollups + multi-tenancy §22

Objectives
  • The obs-compactor: enforce retention (TTL per signal per tenant), downsample metrics (5m/1h rollups for long-range), roll up (recording-rule precomputed series), compact blocks per signal — and finish multi-tenant isolation (structural tenant_id partition everywhere, I10) + per-tenant config.
Deliverable
  • The compactor downsamples, rolls up, and enforces retention per tenant; long-range queries hit downsampled data; tenants are structurally isolated; obs-compactor runs out-of-band.
Acceptance
  • Downsampled queries match (within bound) the equivalent raw-data aggregation vs oracle.
  • Retention drops only past-TTL blocks per tenant; storage reclaimed.
  • Cross-tenant reads structurally impossible (I10) vs the tenancy fixtures.
  • Compaction atomic; queries never see a torn merge (I11).
Fixtures
  • metrics/downsample_equiv.json, metrics/rollup_recording_rule.json, tenancy/retention_per_tenant.json, tenancy/isolation.json, tenancy/compaction_atomic.json.
Pitfalls
  • Downsampling must preserve the right aggregates (min/max/avg/count, and the bucket structure for histograms) → a naive avg loses quantile fidelity.
  • Query resolution selection (raw vs 5m vs 1h) by range — get the crossover right or queries are slow/imprecise.
  • Retention dropping data still referenced by an exemplar/trace within another signal's window → coordinate TTLs (a trace dropped at 7d but a metric exemplar at 13mo points at it → SampledOut/expired, I3).
  • Compaction racing a query → atomic publish (I11).
  • Multi-tenant block path leaks (a shared cache key without tenant) → tenant in every key (I10).

⬜ Phase 11 — C / HTTP query API §23

Objectives
  • Expose a C ABI + HTTP/JSON query API so dashboards, alerting front-ends, and C callers can run metric/log/trace/pivot queries (and push OTLP) per tenant, with full arg validation (I16) and no UB across the boundary.
Deliverable
  • libobs.so + obs.h + an HTTP query server; examples/query_from_c.c runs a metric query + a pivot; a curl/HTTP smoke test hits all endpoints.
Acceptance
  • A C/HTTP client gets results identical to the Rust facade (and the oracle).
  • Prometheus/Loki/Tempo-compatible JSON shapes (so existing tools/dashboards can query it).
  • Bad args → error code / HTTP 4xx, no compute (I16); no unwinding across FFI; tenant enforced (I10); handle lifecycle leak-free.
Fixtures
  • badargs/api_bad_range.json, badargs/api_missing_tenant.json, badargs/api_malformed_query.json, an HTTP integration test + a C integration test in CI.
Pitfalls
  • Tenant from the header must be enforced server-side (I10) — never trust a client-supplied tenant in the body.
  • Result-set size unbounded → page/limit (a query matching millions of series).
  • Panic across FFI = UB → catch_unwind.
  • JSON shape drift from Prometheus/Loki/Tempo → conform to their response schemas for tool compat.
  • Time-range parsing (RFC3339, unix, relative) — validate (I16).

⬜ Phase 12 — Performance hardening §24

Objectives
  • Close gaps to the §4 ingest-throughput and query-latency targets: pipeline/decode optimization, TSDB/log/index inner loops, correlation-lookup latency, query sharding + caching, under sustained multi-tenant load.
Deliverable
  • Ingest throughput + query/correlation latency meeting §4 under sustained multi-tenant load; ingest/query roofline curves.
Acceptance
  • Ingest ≥ the §4 spans/samples/log-lines per second per node; query p99 within §4 per signal; correlation lookup < 30 ms; no correctness regression (re-diff oracle).
  • No OOM under a cardinality/buffer stress; backpressure holds (I4).
Fixtures
  • golden/ingest_throughput.json, golden/query_latency.json, golden/correlation_latency.json, golden/cardinality_stress.json.
Pitfalls
  • Optimizing decode but leaving the limiter/normalizer on the slow path → profile the whole ingest path.
  • Cache without the snapshot id → stale results (I12) — keep it.
  • Query sharding changing float aggregation order → keep determinism (I12).
  • Tail-sampling buffer layout cache-thrashing under high in-flight count.

⬜ Phase 13 — Conformance, differential, fault-injection, benchmarks §25

Objectives
  • Lock correctness + performance: differential vs the in-memory oracle (PromQL/LogQL/trace/correlation), fault injection, determinism, and reproducible ingest/query/correlation benchmarks.
Deliverable
  • make conformance green; make fault (injection) green; make bench report.
Acceptance
  • 100% differential pass (PromQL/LogQL/trace/correlation) vs the oracle over the corpus.
  • Fault injection: every injected fault → correct validation/backpressure/recovery/isolation; WAL replay restores state.
  • Determinism stable (I12); seeded sampling reproducible; bench meets §4.
Fixtures
  • Full conformance/: otlp/, metrics/, logs/, traces/, correlation/, promql/, logql/, trace_search/, cardinality/, sampling/, slo/, tenancy/, badargs/, golden/ + a multi-tenant docker-compose harness.
Pitfalls
  • Differential float tolerance tiering (raw vs downsampled, sum order) → per-query ε.
  • Ingest is timing-nondeterministic, but stored queries are deterministic (§8.12) → ingest a fixed corpus, then assert query determinism (don't assert on live timing).
  • Fault injection must be reproducible (seeded) to debug.
  • Golden query results break on legitimate engine changes → version with the query/storage contract.
  • Correlation differential must cover the dangling/sampled-out paths (I3), not just the happy path.
