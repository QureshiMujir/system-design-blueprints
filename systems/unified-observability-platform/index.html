3.2 Box Narratives

  • ingest. The data-plane front door. Receivers speak OTLP/gRPC and OTLP/HTTP (protobuf) for push and a Prometheus-style scrape loop for pull. The pipeline batches, applies transforms (redaction/PII scrub, attribute normalization), relabels (cardinality control hook), and enforces backpressure (bounded queues; shed or block, never OOM). It normalizes Resource/trace_id/span_id once (I1/I2) and fans out each record to its per-signal writer, optionally through a bus (#58) to decouple receive from write. The unifying identity is stamped here.
  • metrics-store. The metrics pillar's backend = a TSDB (#83): a series index (label-set → series id), sample chunks (delta-of-delta timestamps + XOR float encoding), and — the correlation hook — exemplar slots attached to (series, bucket) that hold {trace_id, value, ts}. Append-mostly, time-ordered, compacted into immutable blocks.
  • trace-store. The trace pillar's backend: ingests spans (trace_id, span_id, parent_span_id, name, kind, timing, status, attributes), assembles them into traces (group by trace_id, build the parent/child tree), and maintains a span/trace index (by trace_id, by service+operation, by duration/status for search) plus the sampling decision hook (head now, tail in P8). Exemplars from metrics and trace_ids from logs both resolve here.
  • log-store. The logs pillar's backend = a label index (#78 inverted index) over the structured labels (service, level, k8s.*, and crucially trace_id) + a columnar/compressed body (#85) for the log message and high-cardinality fields. A log "stream" = a unique label set; queries filter by label index then scan the body. This is where trace_id↔log joins originate.
  • correlate. The unification — the novel subsystem. Four links: (1) exemplars — a metric point → its representative trace (resolve the exemplar's trace_id in trace-store); (2) trace_id↔log join — a trace → its logs (label-index lookup on trace_id) and vice-versa; (3) span→RED/USE metrics — derive Rate/Errors/Duration (+USE) series from the span stream (streaming aggregation, written back as metrics with exemplars at the source spans); (4) resource/label join — the shared Resource identity letting a query say "service X" and hit all three stores. Referential validity is invariant (I3/I5/I8).
  • query. The unified cross-signal query engine. Parses + executes a PromQL-subset (instant/range selectors, rate/histogram_quantile, aggregations), a log query (LogQL-subset: stream selector + line/label filters + log-range aggregations), trace search (by trace_id, service/operation/duration/status, tags), and — the headline — cross-signal joins (the "pivot": metric anomaly → exemplar trace → its logs as one plan). Results/blocks cache via #59; deterministic against a storage snapshot (I12).
  • cardinality control. Bounds active series / index terms per tenant: limits (max active series, max label-name/value length, max labels per series), relabel/drop rules (the ingest hook), and per-tenant ceilings. Rejects or aggregates offending streams before they reach storage (I6).
  • sampling. Tail-based sampling: buffer all spans of a trace until it completes (or a decision window expires), then apply a policy (keep errors, keep slow, probabilistic for the rest) — so the whole trace is kept or dropped together (I9). Head sampling (decide at root) also supported. Bounded buffer memory is the hard constraint.
  • alerting. Evaluates rules (PromQL/LogQL predicates over windows) and multi-window multi-burn-rate SLO alerts (fast-burn + slow-burn windows against an error-budget) — the standard SRE alerting that avoids both flapping and slow detection. Emits alert state with correlation links (the firing alert carries an exemplar trace).
  • retention / downsample / rollup (compactor). Background obs-compactor: enforces retention (drop blocks past TTL per tenant), downsamples metrics (5m/1h rollups for long-range queries), and rolls up (recording-rule-style precomputed series). Compaction merges blocks per signal.
  • cabi / bench / conformance. A C + HTTP query API; benches for ingest throughput and per-signal query p99 + correlation-lookup latency; conformance = an in-memory oracle (ingest the same OTLP, answer queries by brute force), PromQL/LogQL/trace-search differential tests, and fault injection.

3.3 Boundaries

  • Trust boundary: the network (OTLP receivers, scrape, the query API) and the tenant boundary. Incoming OTLP/protobuf is untrusted (size-limited, schema-validated, label-length-bounded); tenants must not see each other's data (I7/I10). The C/HTTP ABI validates all args.
  • Concurrency boundary: the ingest data plane (async receivers → bounded pipeline queues → per-signal writer tasks) is decoupled from the query plane (reads immutable published blocks). Writers and the compactor coordinate via atomic block publication; queries never see a half-written block (I11).
  • Persistence boundary: each signal store publishes immutable blocks atomically; the WAL/head is in memory + a write-ahead log; a query reads a consistent snapshot (set of published blocks + head) → query determinism (I12).
  • Correlation boundary: the shared identity (Resource hash + trace_id/span_id) is normalized once at ingest and is the only cross-store key; the correlation layer never invents links, it only resolves stamped ones (I3/I5/I8).
  • Multi-tenancy boundary: tenant_id is a mandatory partition key on every record, index, block, query, and alert; cross-tenant access is structurally impossible, not policy-gated (I10).

3.4 Data-flow walk — the correlation pivot (the platform's reason to exist)

  1. Services emit OTLP (metrics + traces + logs) tagged with the same Resource (service.name=checkout, k8s.namespace=prod) and, for traces/logs, the same trace_id. Ingest normalizes identity once (I1/I2) and fans out to the three stores.
  2. A metrics scrape records http_request_duration_seconds histogram for checkout; the SDK attached an exemplar to the le="2.5" bucket: {trace_id: T, value: 2.3s}. metrics-store stores it in the bucket's exemplar slot (I5).
  3. Span ingestion stores trace T (root + children) in trace-store; span→RED metrics derivation also writes checkout rate/error/duration series, with exemplars pointing back at representative spans (I8). Logs for T (each carrying trace_id=T) land in log-store, indexed by trace_id in the #78 label index.
  4. An operator (or an SLO alert) sees the p99 latency metric for checkout spike. They issue a range query (PromQL histogram_quantile(0.99, …)); the anomaly is in the le="2.5" bucket.
  5. Pivot 1 (metric → trace): the query engine asks correlate for the bucket's exemplar → trace_id=T → resolves the trace in trace-store (I3: the exemplar points to an existing trace). The operator now sees the concrete slow request, not just an aggregate.
  6. Pivot 2 (trace → logs): from trace T, the engine asks correlate for its logs → log-store label-index lookup on trace_id=T → returns the request's log lines (I5: the join resolves). The operator sees the error log inside the slow span.
  7. All three were joined by shared identity (Resource = checkout, trace_id = T) without any cross-store ETL — the correlation layer resolved stamped links. The query ran against a consistent snapshot (I12); the result is deterministic.
  8. QueryTrace/IngestTrace recorded ingest throughput, the correlation-lookup latency, and which blocks the query touched; cardinality control kept checkout's series bounded throughout (I6); tenant prod saw only its own data (I10).

3.5 Per-process concurrency model (tasks, queues, plane separation)

  • Receiver tasks (async, one per listener) decode OTLP/protobuf, size-check, and enqueue onto bounded pipeline queues (backpressure: block or shed, never grow unbounded — principle 5, I4).
  • Pipeline workers batch + transform + relabel, then fan-out to per-signal writer tasks (one set per store), optionally via the bus #58 so a slow store backpressures only its lane.
  • Per-signal writers append to in-memory head + WAL, and periodically cut immutable blocks published atomically (I11).
  • The tail-sampling buffer is its own bounded structure (per-trace span accumulation) with a decision timer (I9) — sized to a hard memory ceiling.
  • Query tasks read published blocks + head snapshots; the correlation resolver issues cross-store reads; the #59 cache short-circuits hot results.
  • The compactor runs out-of-band (downsample/rollup/retention), coordinating with writers only via atomic block publication — never blocking the data plane.
  • Synchronization: data-plane queues are bounded MPSC; storage publication is a single atomic pointer swap per block set; queries snapshot under a lightweight epoch — no global lock on the hot path (principle 9). The strict ingest-plane ≠ query-plane ≠ compactor separation is what keeps query p99 stable while ingest runs hot.

8. Domain Model — Signals, Identity, Correlation, Storage

8.1 The unified signal model (OpenTelemetry)

  • Every record carries a Resource (the entity emitting it: service.name, service.instance.id, k8s.namespace, host.name, …) and an InstrumentationScope (the library that produced it). The Resource attribute set, canonicalized (sorted, hashed), is the resource join key (I2).
  • Metric: a name + type (Counter/Gauge/Histogram/Summary) + a set of data points, each a {labels, timestamp, value} (or histogram buckets), optionally with exemplars.
  • Span: {trace_id, span_id, parent_span_id, name, kind, start, end, status, attributes, events, links}. A trace = all spans sharing a trace_id, assembled into a tree by parent_span_id.
  • LogRecord: {timestamp, severity, body, attributes, trace_id?, span_id?}. The optional trace_id/span_id are the log↔trace bridge (I5).
  • Exemplar: {filtered_labels, value, timestamp, trace_id, span_id} attached to a metric data point — the metric→trace bridge (I3).
  • The three signals share time and identity (Resource + trace_id); those two axes are how the platform joins them.

8.2 Identity normalization (the correlation key)

  • At ingest (I1/I2): trace_id → canonical 16 bytes, span_id → 8 bytes (parse hex or accept bytes; reject malformed); Resource attributes → sorted, deduplicated, hashed → resource_hash.
  • Every store keys on these: metrics-store series include the resource labels; trace-store indexes by trace_id; log-store's #78 index includes trace_id and the resource labels as first-class indexed labels.
  • Why first-class: the correlation-lookup p99 < 30 ms (§4) requires trace_id to be an indexed lookup, not a body scan — so trace_id is promoted to an indexed label in the log store, never left in the body.

8.3 The correlation links (the unification)

Link From → To Mechanism Invariant
Exemplar metric data point → trace exemplar slot stores trace_id; resolve in trace-store I3 (resolves or sampled-out)
Log→Trace log → trace log's trace_id (indexed) → trace-store by trace_id I5
Trace→Log trace → logs trace_id → log-store #78 index lookup I5
Span→Metric span stream → RED/USE series streaming aggregation; write series + exemplars back I8 (reproducible)

  • The correlation layer never invents a link; it only resolves identities stamped at ingest. A "pivot" composes these (metric→exemplar→trace→logs).

8.4 Per-signal storage layouts

  • Metrics (TSDB, #83): a series = a unique label set → a series_id. Samples appended to chunks (Gorilla: delta-of-delta timestamps + XOR-encoded floats, ~1.3 B/sample). A head (in-memory, recent) + a WAL + immutable blocks (compacted, time-ranged). Exemplar slots: per (series, bucket) a small ring of recent exemplars. Inverted index label→series for selectors.
  • Logs (#78 + #85): a stream = a unique label set (incl. trace_id, resource labels). The #78 inverted index maps label name=value → stream/chunk postings. The log body (message + high-cardinality attrs) stored columnar (#85), compressed; queries filter by index then scan the body columns. Chunked + blocked like metrics.
  • Traces: spans appended (append-mostly) keyed by trace_id; a trace index (trace_id → block offset) for the point lookup, plus a search index (service+operation, duration buckets, status, selected tag values) for trace search. Assembled into a tree at read time.
  • All three: in-memory head + WAL → immutable blocks (atomic publish, I11) → compacted by the compactor (downsample/rollup/retention, P10), partitioned by tenant_id (I10).

8.5 Worked exemplar (metric → trace, end to end)

scrape: http_request_duration_seconds_bucket{service="checkout",le="2.5"} 42  # {trace_id="0af7..."} 2.31 1733000000
ingest: normalize trace_id (I1) → 16 bytes; resource_hash(checkout) (I2)

8.6 Worked RED derivation (spans → metrics, I8)

  • From the span stream for service=checkout, operation=POST /order, over each 15 s window, derive: Rate = span count / window; Errors = count where status=ERROR / window; Duration = a histogram of end−start → histogram_quantile gives p50/p99.
  • Written back as metrics traces_spanmetrics_calls_total, ..._latency_bucket with the same resource labels + exemplars pointing at representative spans → the derived metric is itself correlatable back to its source spans (closing the loop). Re-deriving over the same span window yields identical series (I8).

8.7 OTLP ingest + the pipeline

  • Receivers: OTLP/gRPC (ExportTraceServiceRequest, ...Metrics..., ...Logs...) and OTLP/HTTP (protobuf body); scrape pulls OpenMetrics text. Size-limited, version-checked (I14), validated (I7).
  • Pipeline: decode → normalize identity (I1/I2) → batch (amortize per-record cost) → transform (redact/PII, attribute rename) → relabel/limit (cardinality hook, I6) → fan-out to per-signal writers (optionally via bus #58). Bounded queues at each stage (I4); idempotent on (key, ts) (I15).
  • Backpressure: a slow store fills its lane's queue → the lane backpressures its writer → the pipeline sheds (drop + count) or blocks per policy — never unbounded (principle 4).

8.8 Query model (cross-signal)

  • Metric query (PromQL-subset): selector{labels} → instant/range vector; rate(), sum by(), histogram_quantile(). Snapshot-deterministic (I12); staleness-aware (I13).
  • Log query (LogQL-subset): {stream selector} |= "filter" | label_filter → log lines or rate/count_over_time aggregations; index-then-scan.
  • Trace search: by trace_id (point lookup), or by {service, operation, minDuration, status, tag=value} → matching traces.
  • Cross-signal join (the pivot): a logical plan composing the above via the correlation links (§8.3) — e.g. pivot(metric_anomaly) → exemplar_trace → trace_logs. One query, three stores, joined by identity + time.

8.9 State machines

  • Ingest record: Received → Validated → Normalized → Batched → {Stored | Sampled-out | Sheded | Rejected}.
  • Block: Head(in-mem, WAL) → Cut → Published(immutable) → Compacted → {Retained | Expired(dropped)}.
  • Trace (tail sampling): Open(buffering spans) → {Complete | WindowExpired} → Decide(keep|drop) → {Stored | Dropped}.
  • Alert (SLO): OK → (burn-rate over window) → {Pending → Firing} → Resolved.

8.12 Determinism — what is reproducible, and what is not

  • Snapshot determinism (I12): a query over a fixed set of published blocks + head epoch yields an identical result — this is always required (the basis of differential testing vs the oracle).
  • Float aggregation: sum/rate/histogram_quantile over floats is order-sensitive; the engine fixes an evaluation order (sorted by series id) so results are stable within a snapshot and across runs; cross-implementation comparison is within a numeric bound (matches the oracle within ε).
  • Ingest non-determinism (intentional): wall-clock arrival order and tail-sampling decisions are not deterministic across live runs (they depend on timing) — but once data is stored, queries over that stored snapshot are deterministic. Conformance therefore ingests a fixed OTLP corpus (deterministic), then asserts query determinism.
  • Tail-sampling reproducibility: with a seeded probabilistic policy + a fixed corpus + fixed arrival order (replay), sampling decisions are reproducible for testing (I9); in production they are timing-dependent by design.

8.13 Multi-tenancy model (I10)

  • tenant_id is a mandatory field on every OTLP request (from an auth header / API key), every record, every series/stream/trace key, every block, every index, every query, every alert.
  • Storage is partitioned by tenant_id (separate block directories / key prefixes); a query is constructed with its tenant and can only address that tenant's partition → cross-tenant reads are structurally impossible, not policy-checked (principle 8).
  • Per-tenant: cardinality ceilings (I6), retention TTLs (P10), rate limits (ingest), query limits (max series/time-range). The control plane (quota service) that manages these limits at scale is deferred (PhaseDeferred); the enforcement is in-scope.

8.14 The cardinality control model (P7, the existential bound)

  • Limits (per tenant): max active series, max label-name length, max label-value length, max labels per series, max distinct label values per name.
  • Relabel rules (ingest hook): drop/keep/rename/hash labels before storage — the place to strip user_id from a metric (route it to traces/logs instead).
  • Enforcement: the limiter runs in the pipeline (I6); a series that would exceed the ceiling is rejected (counted card_rejected) or its offending label is dropped/aggregated per policy — before it reaches the TSDB head.
  • Cross-store: the same label cardinality drives the #78 log index and span attributes; the ceiling is platform-wide (a label exploding metrics also explodes the log index) → the limiter sees all three signals.
  • Observability: per-tenant active-series, top-cardinality label names, rejection counts → the cardinality report (obsctl cardinality) operators use to find and fix the offending instrumentation.

Design principles (§6)

  • Correlation is the product; preserve shared identity end-to-end. Resource attributes + trace_id/span_id are normalized once at ingest and are the only cross-store key. Violation: per-store identity drift (hex vs bytes, unnormalized resource) → every pivot dangles, the platform is just three silos.
  • One model, one query engine, three storage shapes. A single obs-core model + one query engine spanning PromQL/LogQL/trace-search/joins; storage differs per pillar (TSDB / index+columnar / span tree). Violation: three bolted-on engines → no cross-signal joins, the whole point lost.
  • Cardinality is bounded by construction. Active series, index terms, label lengths are limited and relabeled at ingest. Violation: one unbounded label (user_id) → OOM across all three stores; the platform falls over.
  • Backpressure everywhere on the ingest plane. Bounded queues; under pressure, shed or block, never grow. Violation: unbounded buffering on a slow store → OOM, then total ingest loss.
  • Sampling decides per-trace, atomically. Tail sampling keeps or drops all spans of a trace together; bounded buffer with shedding. Violation: partial traces (some spans kept, some dropped) → broken trace trees, dangling exemplars.
  • Storage publishes immutable blocks; queries read snapshots. Writers cut atomic immutable blocks; queries see a consistent snapshot. Violation: queries reading half-written blocks → nondeterministic/incorrect results.
  • Query determinism against a snapshot. A query over a fixed snapshot yields an identical result. Violation: time-of-day-dependent results → untestable, unreproducible incident analysis.
  • Tenant isolation is structural, not policy. tenant_id is a mandatory partition key on every path; cross-tenant reads are impossible by construction. Violation: a query reaching another tenant's data → a correctness and security incident.
  • The data plane is lock-free on the hot path; coordination is via atomic block publication. Violation: a global lock on append/query → throughput collapse, p99 blowup.
  • Derive metrics from spans deterministically and reproducibly. RED/USE series re-derive identically from the same span window. Violation: nondeterministic derivation → metric ≠ trace reality, correlation lies.
  • Observability of the observability platform. Emit ingest throughput per signal, drop/shed counts, cardinality per tenant, query latency per signal, correlation-lookup latency, sampling keep-rate. Violation: an opaque platform → can't diagnose why ingest dropped or a query is slow (and we, of all systems, must self-observe).
  • Stable OTLP + storage compatibility. OTLP versions negotiated; block/WAL formats versioned; mixed-version refused or migrated. Violation: silent format drift → unreadable old blocks, dropped ingest on upgrade.
  • Retention and downsampling are explicit and per-tenant. TTLs, rollups, downsampling are configured, enforced by the compactor, never implicit. Violation: unbounded storage growth → cost blowup, then forced data loss.
  • Correctness anchored to the in-memory oracle. The same OTLP ingested into a brute-force in-memory reference must answer every query identically (within numeric bounds for floats). Violation: no oracle → storage/correlation bugs are undebuggable.
