368 — Unified Observability Platform

Goal: Implement, from scratch in Rust, a single platform that unifies the three telemetry pillars — metrics, logs, traces (+ optional profiles/events) — under one ingestion → storage → query stack, with the defining feature being cross-signal correlation. An OTLP / OpenTelemetry receiver feeds a streaming ingestion pipeline (batching, transform, backpressure; push + scrape); three per-signal stores persist data (a metrics TSDB reusing #83, a log store = inverted index #78 + columnar body #85 with label indexing, a trace store = spans + assembly + sampling); a correlation layer stitches them together via exemplars (a metric data point → a representative trace), trace_id/span_id embedded in logs (log↔trace joins), span→RED/USE metrics derivation, and a shared resource/label identity (service, namespace) that joins all three; a unified cross-signal query engine runs PromQL-like metric queries, log queries, trace search, and joins across signals; cardinality control and tail-based sampling keep it bounded at scale; alerting (rules + multi-window multi-burn-rate SLO) and retention/downsampling/rollups + multi-tenancy round it out. Crates: obs-core / ingest / metrics-store / log-store / trace-store / correlate / sampling / query / cardinality / alerting / cabi / bench / conformance. It models the Grafana LGTM stack (Loki/Mimir/Tempo/Grafana) + Datadog + Honeycomb + Elastic + the OpenTelemetry Collector — it is not a standalone tracing system (#132), metrics system (#133), or logging system (#134); it unifies and correlates those pillars into one platform. Correctness is validated against a single-tenant in-memory reference (an oracle that ingests the same OTLP and answers queries directly) plus PromQL/LogQL/trace-search differential tests; performance against ingest-throughput and query-latency targets.

1. Goal

1.1 Engineering Definition

  • Build a from-scratch unified observability platform: OTLP receiver → ingestion pipeline → three per-signal stores → a correlation layer → a unified cross-signal query engine, with cardinality control, tail-based sampling, alerting/SLO, retention, and multi-tenancy.
  • The novelty is unification + correlation, not any one pillar: a user pivots a metric anomaly → its exemplar trace → that trace's logs, in one flow, joined by shared resource identity.
  • Data model: OpenTelemetry — Resource + Scope + signal-specific records (Metric/DataPoint, LogRecord, Span); the unifying key is the Resource attribute set + trace_id/span_id.
  • Concurrency model: a high-throughput async ingestion data plane (receivers → pipelines → per-signal writers) decoupled from a query plane that reads immutable storage snapshots.

1.2 System Boundaries

  • In scope: OTLP/gRPC + OTLP/HTTP receiver; scrape + push; pipelines (batch, transform/redact, backpressure); metrics TSDB (#83); log store (#78 label index + #85 columnar body); trace store (span assembly + index); exemplars; trace_id↔log joins; span→RED/USE derivation; resource/label join; a unified query engine (PromQL-subset, log query, trace search, cross-signal joins); cardinality control; tail-based sampling; alerting (rules + multi-window multi-burn-rate SLO); retention + downsampling + rollups; multi-tenancy; a C/HTTP query API.
  • Out of scope (non-goals): not a standalone tracing (#132), metrics (#133), or logging (#134) system — those are pillars, unified here not rebuilt; not a dashboard-UI framework (we expose a query API); not an instrumentation SDK/agent (we receive OTLP, not generate it). Gated PhaseDeferred("FINAL_BLUEPRINT §39") (the Deferred Features Register): continuous profiling pillar, RUM/frontend, eBPF auto-instrumentation, ML anomaly detection, a managed multi-tenant control plane (billing/quotas-as-a-service).
  • The pillar systems (#132/#133/#134) and the storage engines (#83/#78/#85) are dependencies / reuse, not re-implementations.

1.3 Deployment Model

  • A Rust library + a set of binaries: obs-ingest (receiver + pipeline + writers), obs-query (query engine + API), obs-compactor (downsampling/rollup/retention), and obsctl (CLI: inspect, query, replay, cardinality report). Single-binary all-in-one mode for a laptop; horizontally split for scale.
  • Storage is local/object-store-backed blocks per signal (object-store backend gated PhaseDeferred); ingest and query share storage via immutable, atomically-published blocks. Multi-tenant by a tenant_id partition key on every path.

1.4 Target Users

  • Engineers/operators who must understand how an observability backend actually correlates signals — why an exemplar links a metric to a trace, how a log finds its trace, how RED metrics fall out of spans; SREs running on-call against SLO burn-rate alerts; learners internalizing the three-pillars-plus-correlation model.
  • Downstream: instrumented services (via #132/#133/#134 SDKs) emit OTLP into this; dashboards/alerting consume its query API.

1.5 Phase 0 Deliverable — crates/modules

  1. obs-core — the unified signal model: Resource/Scope/labels, Metric/DataPoint, LogRecord, Span, Exemplar, TraceId/SpanId, OTLP types, TenantId, error types.
  2. ingest — OTLP/gRPC + OTLP/HTTP receivers, scrape, the pipeline (batch/transform/backpressure), per-signal writers.
  3. metrics-store — the TSDB (built on #83): series index, sample chunks, exemplar slots.
  4. log-store — label/tenant index (#78 inverted index) + columnar log body (#85), stream model.
  5. trace-store — span ingestion, trace assembly, span/trace index, sampling hooks.
  6. correlate — exemplars, trace_id↔log joins, span→RED/USE derivation, resource/label join — the unification.
  7. sampling — tail-based sampling (decision after seeing the whole trace) + head sampling.
  8. query — the unified cross-signal engine: PromQL-subset (metrics), log query (LogQL-subset), trace search, cross-signal joins.
  9. cardinality — active-series limits, label control/relabel, per-tenant ceilings.
  10. alerting — rule evaluation + multi-window multi-burn-rate SLO alerts.
  11. cabi / bench / conformance — C/HTTP query ABI; ingest-throughput + query-latency benches; in-memory oracle + PromQL/LogQL/trace differential + fault-injection.

1.9 Recommended Language & Rationale

  • Rust. (a) the ingestion data plane is high-throughput async I/O (millions of spans/samples/log-lines/s) where no GC jitter keeps p99 stable — Go and Java both pause; (b) ownership/Send/Sync make the multi-stage pipeline (receivers, batchers, backpressure, writers, tail-sampling buffers) memory-bound-auditable; (c) reuses #83/#78/#85 and shares the model with #132/#133/#134; (d) zero-cost columnar decode + SIMD query inner loops; (e) extern "C" + HTTP ABI for consumers.
  • Rejected: Go — the actual Grafana/Prometheus/Loki/Tempo + OTel-Collector language, great fit, but GC stop-the-world hurts the ingest p99 tail + tail-sampling memory; rejected for this build (not for the real systems). Java/JVM — the Elastic/OpenSearch lineage; mature but heavier + GC pauses. C++ — fast but no memory safety on a network data plane. Python — control-plane only; too slow for the data plane.

1.10 Prerequisites

  • TSDB (chunks, compaction, downsampling); inverted indexes + columnar storage (term dictionaries, postings, encodings); distributed tracing (spans, parent/child, sampling); metrics (counters/gauges/histograms, PromQL); structured logging; stream processing (windowing, backpressure); networking (gRPC/HTTP2, protobuf); concurrency (async I/O, bounded queues).
  • Strongly recommended prior: the three pillars #132 Tracing / #133 Metrics / #134 Logging; the backends #83 TSDB / #78 Inverted Index / #85 Column Storage; #105 Stream Processing (pipelines), #58 Pub/Sub (ingest bus), #59 Distributed Cache (query cache).

2. Why Build This

2.1 Unique Knowledge Taught

  • Cross-signal correlation from first principles. Why an exemplar (a {trace_id, value, timestamp} attached to a metric bucket) is the bridge from an aggregate to a concrete example; how a trace_id in a log line turns a flat log search into a trace-scoped join; how RED (Rate/Errors/Duration) and USE (Utilization/Saturation/Errors) metrics are derived from span streams; why a shared resource identity (service.name, k8s.namespace, …) is the join key that unifies all three.
  • Three storage shapes, one platform. Metrics → a TSDB (delta-of-delta timestamps, XOR-encoded floats, series index); logs → an inverted index over labels + a columnar/compressed body; traces → span records assembled into trees + a span index. Why each pillar demands a different physical layout and how one query engine spans them.
  • Cardinality as the existential constraint. Why a single high-cardinality label (user_id, request_id as a metric label) explodes active series and OOMs the TSDB; how limits, relabeling, and aggregation control it.
  • Tail-based sampling. Why deciding after the whole trace arrives (keep the error/slow traces) beats head sampling, and the memory/latency cost of buffering in-flight traces to decide.
  • SLO burn-rate alerting. Why multi-window multi-burn-rate alerts (fast + slow burn) catch both acute and chronic SLO violations without flapping.

2.2 Why It Matters

  • Every modern operations stack (Grafana LGTM, Datadog, Honeycomb, Elastic, the OTel Collector) is this: ingest three signals, store each natively, and — the differentiator — correlate them so an operator goes anomaly → trace → log in seconds. The correlation layer is what separates a "pile of dashboards" from an observability platform. Building it teaches how production incidents are actually diagnosed.

2.3 Engineering Muscles

  • High-throughput async network ingestion (protobuf/OTLP, batching, backpressure); multi-shape storage engineering (TSDB + inverted index + columnar, reusing #83/#78/#85); cross-signal join design (the correlation layer); query-engine design across three query languages + joins; cardinality/resource-bounding; streaming windowed aggregation (RED/USE derivation, tail sampling); SLO/alerting math; multi-tenant isolation; differential testing against an oracle.

2.4 Production Concepts Exercised

  • OTLP ingestion + pipelines; exemplars + trace↔log correlation; span-derived metrics; cardinality control; tail-based sampling; retention/downsampling/rollups; multi-window multi-burn-rate SLOs; multi-tenancy; query caching.

2.6 Calibration Value

  • You leave able to read Mimir/Loki/Tempo/Grafana, Datadog, Honeycomb, Elastic, and the OTel Collector and explain every ingestion stage, storage layout, correlation link, sampling decision, and SLO alert — and to reason about why an observability bill explodes (cardinality) and how a unified platform makes an incident debuggable in one pivot.

2.7 The correlation imperative — the defining constraint

  • #132/#133/#134 each handle one signal well; the value of this platform is the join across signals, and that join reorganizes every layer:
  • Consequence 1: a shared identity must be preserved end-to-end. Resource attributes and trace_id/span_id are normalized once at ingest (I-class invariants) so every store keys on the same identity — drift here breaks every correlation.
  • Consequence 2: correlation links must be referentially valid. An exemplar's trace_id must resolve to a stored, sampled trace; a log's trace_id must find its trace; a span-derived metric must be reproducible from its spans (I3/I5/I8).
  • Consequence 3: sampling and correlation interact. If tail sampling drops a trace, exemplars pointing at it dangle → the platform must reconcile (keep exemplar-referenced traces, or mark the link as sampled-out).
  • Consequence 4: cardinality bounds the whole platform. Correlation by resource/labels means labels are everywhere (metrics series, log index, span attributes); unbounded labels explode every store at once.
  • Consequence 5: the query engine is cross-signal, not three engines. A "pivot" is one logical query that touches metrics, traces, and logs joined by identity/time — the engine is designed around the join, not bolted on.
  • This single imperative is the sharpest contrast with the single-pillar systems and the reason this is one platform, not three.

2.8 What Mastery Looks Like

  • You can normalize a cross-signal identity that actually joins (Phase 0 + Phase 5): given hex/bytes trace_id drift and unsorted resource attributes, you produce a canonical key that makes the exemplar→trace and log→trace joins hit every time — and you can name the bug class (silent join-miss) you avoid by doing it once at ingest (I1/I2).
  • You can bound a data plane so it never OOMs (Phase 1 + Phase 8): you can size bounded MPSC queues + a tail-sampling buffer to a hard memory ceiling, choose shed-vs-block per lane, and explain why a slow store backpressures only its own lane (I4, principle 4).
  • You can build three storage shapes and know why each differs (Phase 2/3/4): a Gorilla-encoded TSDB head+WAL+blocks, an append-by-trace_id trace store with a point-lookup index, and a label-indexed (#78) + columnar-body (#85) log store — and say which physical layout each query pattern demands.
  • You can implement cross-signal correlation as resolution of stamped identity, not invented links (Phase 5): exemplar→trace (with the non-dangling SampledOut case), trace↔log, and deterministic span→RED/USE derivation — the subsystem that is the platform's reason to exist (I3/I5/I8).
  • You can reason about cardinality as the existential cost (Phase 7): you can compute active series from a label set, predict the OOM a single unbounded label causes across all three stores, and place the limiter before the head (§4.1, I6).
  • You can do tail-based sampling under a memory bound (Phase 8): buffer whole traces, decide atomically (never partial), reconcile with exemplar references, and shed to head-sampling under pressure (I9, principle 5).
  • You can derive multi-window multi-burn-rate SLO alerts that neither flap nor miss (Phase 9): you can compute burn rate from an objective and combine a fast and a slow window to catch acute and chronic violations (the SRE-workbook recipe).
  • You can guarantee query determinism against an immutable snapshot and prove it (Phase 6 + Phase 13): fixed eval order + snapshot isolation, validated by differential testing against an in-memory oracle to within a float ε (I11/I12, principle 14).

3.2 Box Narratives

  • ingest. The data-plane front door. Receivers speak OTLP/gRPC and OTLP/HTTP (protobuf) for push and a Prometheus-style scrape loop for pull. The pipeline batches, applies transforms (redaction/PII scrub, attribute normalization), relabels (cardinality control hook), and enforces backpressure (bounded queues; shed or block, never OOM). It normalizes Resource/trace_id/span_id once (I1/I2) and fans out each record to its per-signal writer, optionally through a bus (#58) to decouple receive from write. The unifying identity is stamped here.
  • metrics-store. The metrics pillar's backend = a TSDB (#83): a series index (label-set → series id), sample chunks (delta-of-delta timestamps + XOR float encoding), and — the correlation hook — exemplar slots attached to (series, bucket) that hold {trace_id, value, ts}. Append-mostly, time-ordered, compacted into immutable blocks.
  • trace-store. The trace pillar's backend: ingests spans (trace_id, span_id, parent_span_id, name, kind, timing, status, attributes), assembles them into traces (group by trace_id, build the parent/child tree), and maintains a span/trace index (by trace_id, by service+operation, by duration/status for search) plus the sampling decision hook (head now, tail in P8). Exemplars from metrics and trace_ids from logs both resolve here.
  • log-store. The logs pillar's backend = a label index (#78 inverted index) over the structured labels (service, level, k8s.*, and crucially trace_id) + a columnar/compressed body (#85) for the log message and high-cardinality fields. A log "stream" = a unique label set; queries filter by label index then scan the body. This is where trace_id↔log joins originate.
  • correlate. The unification — the novel subsystem. Four links: (1) exemplars — a metric point → its representative trace (resolve the exemplar's trace_id in trace-store); (2) trace_id↔log join — a trace → its logs (label-index lookup on trace_id) and vice-versa; (3) span→RED/USE metrics — derive Rate/Errors/Duration (+USE) series from the span stream (streaming aggregation, written back as metrics with exemplars at the source spans); (4) resource/label join — the shared Resource identity letting a query say "service X" and hit all three stores. Referential validity is invariant (I3/I5/I8).
  • query. The unified cross-signal query engine. Parses + executes a PromQL-subset (instant/range selectors, rate/histogram_quantile, aggregations), a log query (LogQL-subset: stream selector + line/label filters + log-range aggregations), trace search (by trace_id, service/operation/duration/status, tags), and — the headline — cross-signal joins (the "pivot": metric anomaly → exemplar trace → its logs as one plan). Results/blocks cache via #59; deterministic against a storage snapshot (I12).
  • cardinality control. Bounds active series / index terms per tenant: limits (max active series, max label-name/value length, max labels per series), relabel/drop rules (the ingest hook), and per-tenant ceilings. Rejects or aggregates offending streams before they reach storage (I6).
  • sampling. Tail-based sampling: buffer all spans of a trace until it completes (or a decision window expires), then apply a policy (keep errors, keep slow, probabilistic for the rest) — so the whole trace is kept or dropped together (I9). Head sampling (decide at root) also supported. Bounded buffer memory is the hard constraint.
  • alerting. Evaluates rules (PromQL/LogQL predicates over windows) and multi-window multi-burn-rate SLO alerts (fast-burn + slow-burn windows against an error-budget) — the standard SRE alerting that avoids both flapping and slow detection. Emits alert state with correlation links (the firing alert carries an exemplar trace).
  • retention / downsample / rollup (compactor). Background obs-compactor: enforces retention (drop blocks past TTL per tenant), downsamples metrics (5m/1h rollups for long-range queries), and rolls up (recording-rule-style precomputed series). Compaction merges blocks per signal.
  • cabi / bench / conformance. A C + HTTP query API; benches for ingest throughput and per-signal query p99 + correlation-lookup latency; conformance = an in-memory oracle (ingest the same OTLP, answer queries by brute force), PromQL/LogQL/trace-search differential tests, and fault injection.

3.3 Boundaries

  • Trust boundary: the network (OTLP receivers, scrape, the query API) and the tenant boundary. Incoming OTLP/protobuf is untrusted (size-limited, schema-validated, label-length-bounded); tenants must not see each other's data (I7/I10). The C/HTTP ABI validates all args.
  • Concurrency boundary: the ingest data plane (async receivers → bounded pipeline queues → per-signal writer tasks) is decoupled from the query plane (reads immutable published blocks). Writers and the compactor coordinate via atomic block publication; queries never see a half-written block (I11).
  • Persistence boundary: each signal store publishes immutable blocks atomically; the WAL/head is in memory + a write-ahead log; a query reads a consistent snapshot (set of published blocks + head) → query determinism (I12).
  • Correlation boundary: the shared identity (Resource hash + trace_id/span_id) is normalized once at ingest and is the only cross-store key; the correlation layer never invents links, it only resolves stamped ones (I3/I5/I8).
  • Multi-tenancy boundary: tenant_id is a mandatory partition key on every record, index, block, query, and alert; cross-tenant access is structurally impossible, not policy-gated (I10).

3.4 Data-flow walk — the correlation pivot (the platform's reason to exist)

  1. Services emit OTLP (metrics + traces + logs) tagged with the same Resource (service.name=checkout, k8s.namespace=prod) and, for traces/logs, the same trace_id. Ingest normalizes identity once (I1/I2) and fans out to the three stores.
  2. A metrics scrape records http_request_duration_seconds histogram for checkout; the SDK attached an exemplar to the le="2.5" bucket: {trace_id: T, value: 2.3s}. metrics-store stores it in the bucket's exemplar slot (I5).
  3. Span ingestion stores trace T (root + children) in trace-store; span→RED metrics derivation also writes checkout rate/error/duration series, with exemplars pointing back at representative spans (I8). Logs for T (each carrying trace_id=T) land in log-store, indexed by trace_id in the #78 label index.
  4. An operator (or an SLO alert) sees the p99 latency metric for checkout spike. They issue a range query (PromQL histogram_quantile(0.99, …)); the anomaly is in the le="2.5" bucket.
  5. Pivot 1 (metric → trace): the query engine asks correlate for the bucket's exemplar → trace_id=T → resolves the trace in trace-store (I3: the exemplar points to an existing trace). The operator now sees the concrete slow request, not just an aggregate.
  6. Pivot 2 (trace → logs): from trace T, the engine asks correlate for its logs → log-store label-index lookup on trace_id=T → returns the request's log lines (I5: the join resolves). The operator sees the error log inside the slow span.
  7. All three were joined by shared identity (Resource = checkout, trace_id = T) without any cross-store ETL — the correlation layer resolved stamped links. The query ran against a consistent snapshot (I12); the result is deterministic.
  8. QueryTrace/IngestTrace recorded ingest throughput, the correlation-lookup latency, and which blocks the query touched; cardinality control kept checkout's series bounded throughout (I6); tenant prod saw only its own data (I10).

3.5 Per-process concurrency model (tasks, queues, plane separation)

  • Receiver tasks (async, one per listener) decode OTLP/protobuf, size-check, and enqueue onto bounded pipeline queues (backpressure: block or shed, never grow unbounded — principle 5, I4).
  • Pipeline workers batch + transform + relabel, then fan-out to per-signal writer tasks (one set per store), optionally via the bus #58 so a slow store backpressures only its lane.
  • Per-signal writers append to in-memory head + WAL, and periodically cut immutable blocks published atomically (I11).
  • The tail-sampling buffer is its own bounded structure (per-trace span accumulation) with a decision timer (I9) — sized to a hard memory ceiling.
  • Query tasks read published blocks + head snapshots; the correlation resolver issues cross-store reads; the #59 cache short-circuits hot results.
  • The compactor runs out-of-band (downsample/rollup/retention), coordinating with writers only via atomic block publication — never blocking the data plane.
  • Synchronization: data-plane queues are bounded MPSC; storage publication is a single atomic pointer swap per block set; queries snapshot under a lightweight epoch — no global lock on the hot path (principle 9). The strict ingest-plane ≠ query-plane ≠ compactor separation is what keeps query p99 stable while ingest runs hot.

4.1 Worked cardinality cost (why it is existential)

  • Active series ≈ Π(distinct values per label) across a metric's label set. A counter http_requests_total{service, method, status} with 50 services × 5 methods × 10 statuses = 2,500 series — fine.
  • Add one unbounded label user_id (1 M users): 2,500 × 1,000,000 = 2.5 B series → the series index + head chunks blow far past the 10 M ceiling → OOM / refusal.
  • TSDB cost scales with active series, not samples: each series carries an index entry + an open chunk (~hundreds of bytes) → 10 M series ≈ several GB of head before any samples.
  • Implication: cardinality control (P7) must reject/relabel user_id-as-a-label at ingest (I6); the right place for user_id is a trace/log attribute (high-cardinality stores) or an exemplar, never a metric label — this is the single most common production failure and the platform must make it structurally hard.
  • The same label appears in the log index (#78) and span attributes → unbounded cardinality explodes all three stores; the limit is platform-wide, not per-store.

4.2 Worked tail-sampling budget (memory vs decision quality)

  • Tail sampling buffers every span of an in-flight trace until the trace completes or the decision window expires, then decides keep/drop for the whole trace (I9).
  • Buffer memory ≈ in_flight_traces × spans_per_trace × bytes_per_span. Example: 50k traces/s × 1s avg duration = 50k in-flight; × 20 spans × 200 B = 200 MB buffered — bounded and acceptable.
  • A long-tail trace (a 25 s request) holds its spans for the whole window → a few slow traces dominate buffer occupancy → the window cap (≤ 30 s) + a hard memory cap with shedding (drop-to-head-sample under pressure) keep it bounded (principle 5).
  • Decision quality vs cost: keeping all error/slow traces + 1% of the rest typically retains < 5% of spans while keeping ~100% of the interesting ones → storage drops 20×, debuggability barely changes. The policy is configurable; the buffering is the engineering hard part.
  • Interaction with exemplars (§4.3, I9): a trace referenced by a metric exemplar must not be silently dropped → the sampler honors an "exemplar-referenced" keep signal or the link is marked sampled-out.

4.3 Worked correlation-validity budget (the join must not dangle)

  • Three links, each with a referential-integrity requirement:
  • Exemplar → trace (I3): the exemplar's trace_id must resolve to a stored trace within the trace retention window. If the trace was tail-sampled out, the platform either (a) kept it because it was exemplar-referenced, or (b) returns "sampled out" — never a 404 with no explanation.
  • Log → trace / trace → log (I5): a log's trace_id must be the same normalized id as the trace's (I1) — normalization at ingest is what makes the label-index join (#78) hit. Drift in id encoding (hex vs bytes, casing) silently breaks the join → normalized once, asserted.
  • Span → metric (I8): a RED metric derived from spans must be reproducible from those spans (re-deriving over the same span window yields the same series) → the derivation is deterministic and the source spans are linkable via exemplars.
  • Latency budget: the headline correlation-lookup p99 < 30 ms means the trace-store index (by trace_id) and the log-store label index (by trace_id) must both be O(log n) point lookups, cached (#59) — never a scan. This is why trace_id is a first-class indexed label, not a body field.

6. Design Principles

  1. Correlation is the product; preserve shared identity end-to-end. Resource attributes + trace_id/span_id are normalized once at ingest and are the only cross-store key. Violation: per-store identity drift (hex vs bytes, unnormalized resource) → every pivot dangles, the platform is just three silos.
  2. One model, one query engine, three storage shapes. A single obs-core model + one query engine spanning PromQL/LogQL/trace-search/joins; storage differs per pillar (TSDB / index+columnar / span tree). Violation: three bolted-on engines → no cross-signal joins, the whole point lost.
  3. Cardinality is bounded by construction. Active series, index terms, label lengths are limited and relabeled at ingest. Violation: one unbounded label (user_id) → OOM across all three stores; the platform falls over.
  4. Backpressure everywhere on the ingest plane. Bounded queues; under pressure, shed or block, never grow. Violation: unbounded buffering on a slow store → OOM, then total ingest loss.
  5. Sampling decides per-trace, atomically. Tail sampling keeps or drops all spans of a trace together; bounded buffer with shedding. Violation: partial traces (some spans kept, some dropped) → broken trace trees, dangling exemplars.
  6. Storage publishes immutable blocks; queries read snapshots. Writers cut atomic immutable blocks; queries see a consistent snapshot. Violation: queries reading half-written blocks → nondeterministic/incorrect results.
  7. Query determinism against a snapshot. A query over a fixed snapshot yields an identical result. Violation: time-of-day-dependent results → untestable, unreproducible incident analysis.
  8. Tenant isolation is structural, not policy. tenant_id is a mandatory partition key on every path; cross-tenant reads are impossible by construction. Violation: a query reaching another tenant's data → a correctness and security incident.
  9. The data plane is lock-free on the hot path; coordination is via atomic block publication. Violation: a global lock on append/query → throughput collapse, p99 blowup.
  10. Derive metrics from spans deterministically and reproducibly. RED/USE series re-derive identically from the same span window. Violation: nondeterministic derivation → metric ≠ trace reality, correlation lies.
  11. Observability of the observability platform. Emit ingest throughput per signal, drop/shed counts, cardinality per tenant, query latency per signal, correlation-lookup latency, sampling keep-rate. Violation: an opaque platform → can't diagnose why ingest dropped or a query is slow (and we, of all systems, must self-observe).
  12. Stable OTLP + storage compatibility. OTLP versions negotiated; block/WAL formats versioned; mixed-version refused or migrated. Violation: silent format drift → unreadable old blocks, dropped ingest on upgrade.
  13. Retention and downsampling are explicit and per-tenant. TTLs, rollups, downsampling are configured, enforced by the compactor, never implicit. Violation: unbounded storage growth → cost blowup, then forced data loss.
  14. Correctness anchored to the in-memory oracle. The same OTLP ingested into a brute-force in-memory reference must answer every query identically (within numeric bounds for floats). Violation: no oracle → storage/correlation bugs are undebuggable.

8. Domain Model — Signals, Identity, Correlation, Storage

8.1 The unified signal model (OpenTelemetry)

  • Every record carries a Resource (the entity emitting it: service.name, service.instance.id, k8s.namespace, host.name, …) and an InstrumentationScope (the library that produced it). The Resource attribute set, canonicalized (sorted, hashed), is the resource join key (I2).
  • Metric: a name + type (Counter/Gauge/Histogram/Summary) + a set of data points, each a {labels, timestamp, value} (or histogram buckets), optionally with exemplars.
  • Span: {trace_id, span_id, parent_span_id, name, kind, start, end, status, attributes, events, links}. A trace = all spans sharing a trace_id, assembled into a tree by parent_span_id.
  • LogRecord: {timestamp, severity, body, attributes, trace_id?, span_id?}. The optional trace_id/span_id are the log↔trace bridge (I5).
  • Exemplar: {filtered_labels, value, timestamp, trace_id, span_id} attached to a metric data point — the metric→trace bridge (I3).
  • The three signals share time and identity (Resource + trace_id); those two axes are how the platform joins them.

8.2 Identity normalization (the correlation key)

  • At ingest (I1/I2): trace_id → canonical 16 bytes, span_id → 8 bytes (parse hex or accept bytes; reject malformed); Resource attributes → sorted, deduplicated, hashed → resource_hash.
  • Every store keys on these: metrics-store series include the resource labels; trace-store indexes by trace_id; log-store's #78 index includes trace_id and the resource labels as first-class indexed labels.
  • Why first-class: the correlation-lookup p99 < 30 ms (§4) requires trace_id to be an indexed lookup, not a body scan — so trace_id is promoted to an indexed label in the log store, never left in the body.

8.4 Per-signal storage layouts

  • Metrics (TSDB, #83): a series = a unique label set → a series_id. Samples appended to chunks (Gorilla: delta-of-delta timestamps + XOR-encoded floats, ~1.3 B/sample). A head (in-memory, recent) + a WAL + immutable blocks (compacted, time-ranged). Exemplar slots: per (series, bucket) a small ring of recent exemplars. Inverted index label→series for selectors.
  • Logs (#78 + #85): a stream = a unique label set (incl. trace_id, resource labels). The #78 inverted index maps label name=value → stream/chunk postings. The log body (message + high-cardinality attrs) stored columnar (#85), compressed; queries filter by index then scan the body columns. Chunked + blocked like metrics.
  • Traces: spans appended (append-mostly) keyed by trace_id; a trace index (trace_id → block offset) for the point lookup, plus a search index (service+operation, duration buckets, status, selected tag values) for trace search. Assembled into a tree at read time.
  • All three: in-memory head + WAL → immutable blocks (atomic publish, I11) → compacted by the compactor (downsample/rollup/retention, P10), partitioned by tenant_id (I10).

8.6 Worked RED derivation (spans → metrics, I8)

  • From the span stream for service=checkout, operation=POST /order, over each 15 s window, derive: Rate = span count / window; Errors = count where status=ERROR / window; Duration = a histogram of end−start → histogram_quantile gives p50/p99.
  • Written back as metrics traces_spanmetrics_calls_total, ..._latency_bucket with the same resource labels + exemplars pointing at representative spans → the derived metric is itself correlatable back to its source spans (closing the loop). Re-deriving over the same span window yields identical series (I8).

8.7 OTLP ingest + the pipeline

  • Receivers: OTLP/gRPC (ExportTraceServiceRequest, ...Metrics..., ...Logs...) and OTLP/HTTP (protobuf body); scrape pulls OpenMetrics text. Size-limited, version-checked (I14), validated (I7).
  • Pipeline: decode → normalize identity (I1/I2) → batch (amortize per-record cost) → transform (redact/PII, attribute rename) → relabel/limit (cardinality hook, I6) → fan-out to per-signal writers (optionally via bus #58). Bounded queues at each stage (I4); idempotent on (key, ts) (I15).
  • Backpressure: a slow store fills its lane's queue → the lane backpressures its writer → the pipeline sheds (drop + count) or blocks per policy — never unbounded (principle 4).

8.8 Query model (cross-signal)

  • Metric query (PromQL-subset): selector{labels} → instant/range vector; rate(), sum by(), histogram_quantile(). Snapshot-deterministic (I12); staleness-aware (I13).
  • Log query (LogQL-subset): {stream selector} |= "filter" | label_filter → log lines or rate/count_over_time aggregations; index-then-scan.
  • Trace search: by trace_id (point lookup), or by {service, operation, minDuration, status, tag=value} → matching traces.
  • Cross-signal join (the pivot): a logical plan composing the above via the correlation links (§8.3) — e.g. pivot(metric_anomaly) → exemplar_trace → trace_logs. One query, three stores, joined by identity + time.

8.9 State machines

  • Ingest record: Received → Validated → Normalized → Batched → {Stored | Sampled-out | Sheded | Rejected}.
  • Block: Head(in-mem, WAL) → Cut → Published(immutable) → Compacted → {Retained | Expired(dropped)}.
  • Trace (tail sampling): Open(buffering spans) → {Complete | WindowExpired} → Decide(keep|drop) → {Stored | Dropped}.
  • Alert (SLO): OK → (burn-rate over window) → {Pending → Firing} → Resolved.

8.12 Determinism — what is reproducible, and what is not

  • Snapshot determinism (I12): a query over a fixed set of published blocks + head epoch yields an identical result — this is always required (the basis of differential testing vs the oracle).
  • Float aggregation: sum/rate/histogram_quantile over floats is order-sensitive; the engine fixes an evaluation order (sorted by series id) so results are stable within a snapshot and across runs; cross-implementation comparison is within a numeric bound (matches the oracle within ε).
  • Ingest non-determinism (intentional): wall-clock arrival order and tail-sampling decisions are not deterministic across live runs (they depend on timing) — but once data is stored, queries over that stored snapshot are deterministic. Conformance therefore ingests a fixed OTLP corpus (deterministic), then asserts query determinism.
  • Tail-sampling reproducibility: with a seeded probabilistic policy + a fixed corpus + fixed arrival order (replay), sampling decisions are reproducible for testing (I9); in production they are timing-dependent by design.

8.13 Multi-tenancy model (I10)

  • tenant_id is a mandatory field on every OTLP request (from an auth header / API key), every record, every series/stream/trace key, every block, every index, every query, every alert.
  • Storage is partitioned by tenant_id (separate block directories / key prefixes); a query is constructed with its tenant and can only address that tenant's partition → cross-tenant reads are structurally impossible, not policy-checked (principle 8).
  • Per-tenant: cardinality ceilings (I6), retention TTLs (P10), rate limits (ingest), query limits (max series/time-range). The control plane (quota service) that manages these limits at scale is deferred (PhaseDeferred); the enforcement is in-scope.

8.14 The cardinality control model (P7, the existential bound)

  • Limits (per tenant): max active series, max label-name length, max label-value length, max labels per series, max distinct label values per name.
  • Relabel rules (ingest hook): drop/keep/rename/hash labels before storage — the place to strip user_id from a metric (route it to traces/logs instead).
  • Enforcement: the limiter runs in the pipeline (I6); a series that would exceed the ceiling is rejected (counted card_rejected) or its offending label is dropped/aggregated per policy — before it reaches the TSDB head.
  • Cross-store: the same label cardinality drives the #78 log index and span attributes; the ceiling is platform-wide (a label exploding metrics also explodes the log index) → the limiter sees all three signals.
  • Observability: per-tenant active-series, top-cardinality label names, rejection counts → the cardinality report (obsctl cardinality) operators use to find and fix the offending instrumentation.

20.6 Pitfalls

  • Partial traces (some spans decided before others arrive) → the classic tail-sampling bug; the decision must be atomic per trace (I9).
  • The decision window vs late spans: a span arriving after the decision → drop (or the trace was kept, append) — define precisely.
  • Buffer memory blowup from long-tail traces → the window cap + the memory cap + shedding (principle 5).
  • A dropped trace that an exemplar points at → dangling exemplar (I3) — honor the keep signal or mark sampled-out.
  • Probabilistic policy must be consistent per trace (hash trace_id, not per-span) → whole-trace consistency.

20.7 Performance Concerns

  • The buffer is on the ingest path → per-span insert must be O(1); the decision timer cheap.
  • Memory is the binding constraint (§4.2) → bytes/span × in-flight traces; cap + shed.
  • Flushing kept traces in bursts → smooth to trace-store.

20.8 Edge Cases

  • A trace that never completes (window expires → decide on partial); a single-span trace; a burst of in-flight traces exceeding the buffer (shed); a trace exactly at the slow threshold.

20.9 Failure Analysis

  • A partial-trace bug → broken trace trees downstream + dangling exemplars → the atomic-decision invariant (I9) + the partial-trace fixture + docs/failure-analysis/partial-trace.md.
  • Buffer OOM → the memory cap + shedding; never unbounded (I4).

20.10 Operational Notes

  • sample_decision, keep-rate, buffer occupancy, shed count; document the policy composition + window/memory tuning; the keep-rate is a primary cost/utility dial.

21. Phase 9 — Alerting: rules + multi-window multi-burn-rate SLO

21.1 Objectives

  • Evaluate rules (PromQL/LogQL predicates over windows) and multi-window multi-burn-rate SLO alerts (fast + slow burn against an error budget) — timely, non-flapping, correlation-linked (the firing alert carries an exemplar trace).

21.2 Detailed Implementation Steps

  • alerting::rule — a Rule { expr, for_, severity }; evaluate expr (a query) on an interval; for_ debounces (Pending → Firing).
  • alerting::eval — the evaluation loop over a snapshot (I12); reuses the query engine (P6).
  • alerting::slo_burn_rate — given an SLI query + objective (e.g. 0.999), compute the error-budget burn rate.
  • alerting::multi_window — combine a fast window (e.g. 5m/1h) and a slow window (e.g. 30m/6h); fire only when both a short and a long window burn → catches acute + chronic, avoids flapping (the SRE-workbook recipe).
  • alerting::{state,notify} — alert state machine (Ok/Pending/Firing/Resolved); a FiringAlert carries an exemplar trace_id (the correlation link, so on-call pivots straight to a trace).

21.3 Deliverable

  • Rule + SLO burn-rate alerting; a fast-burn alert fires within a minute of an acute SLO violation; a slow-burn alert catches chronic drift; firing alerts carry a trace link.

21.4 Acceptance Criteria

  • Multi-window multi-burn-rate fires correctly for acute and chronic violations and does not flap on transient blips (vs a scripted SLI series).
  • Fast-window detection < 1 min (§4); rule eval within one interval.
  • A firing alert carries a representative exemplar trace (correlation link).

21.5 Conformance Fixtures

  • slo/burn_rate_fast.json, slo/burn_rate_slow.json, slo/no_flap_on_blip.json, slo/multi_window_combine.json, slo/alert_carries_exemplar.json.

21.6 Pitfalls

  • Single-window burn-rate alerts either flap (short window) or detect late (long window) → the multi-window combination is the fix — implement both halves (the common mistake is one window).
  • Burn-rate math: burn rate = (error rate) / (1 − objective); thresholds per window must be derived correctly.
  • Alert eval reading an inconsistent snapshot → pin one snapshot per eval (I12).
  • for_ debounce vs fast detection — tune; too long delays, too short flaps.
  • Resolving an alert (hysteresis) to avoid resolve/fire oscillation.

21.7 Performance Concerns

  • Many rules × many tenants → eval is a query-engine load; schedule + cache (reuse #59).
  • SLO windows are long-range queries → use downsampled/rollup series (P10) for the slow window.

21.8 Edge Cases

  • No data (SLI undefined → don't fire spuriously); a brand-new SLO (no history for the long window); an objective of 1.0 (no budget → any error fires); simultaneous fast+slow.

21.9 Failure Analysis

  • A bad alert (flapping or missing) erodes on-call trust → the no-flap + burn-rate fixtures + scripted SLI series gate it; a missed SLO breach is the worst — the slow window is the backstop.

21.10 Operational Notes

  • Alert state + burn-rate as metrics (self-observability); the firing-alert→trace link is the on-call pivot; document the multi-window recipe + thresholds.

22. Phase 10 — Retention, downsampling, rollups + multi-tenancy

22.1 Objectives

  • The obs-compactor: enforce retention (TTL per signal per tenant), downsample metrics (5m/1h rollups for long-range), roll up (recording-rule precomputed series), compact blocks per signal — and finish multi-tenant isolation (structural tenant_id partition everywhere, I10) + per-tenant config.

22.2 Detailed Implementation Steps

  • Compaction: merge per-signal blocks (metrics chunks, log chunks, trace blocks) into larger time-ranged blocks; atomic publish (I11).
  • metrics-store downsampling: produce 5m/1h aggregated series (min/max/avg/count) for long-range queries; the query engine picks resolution by range.
  • Rollups: recording-rule-style precomputed series (e.g. per-service RED at 1m) → fast SLO slow-window queries (P9).
  • Retention: drop blocks past the per-tenant TTL (metrics/logs/traces independently); reclaim storage.
  • Multi-tenancy: confirm tenant_id partition on every block path, index, query, alert (I10); per-tenant TenantConfig (cardinality/retention/sampling/rate-limit).

22.3 Deliverable

  • The compactor downsamples, rolls up, and enforces retention per tenant; long-range queries hit downsampled data; tenants are structurally isolated; obs-compactor runs out-of-band.

22.4 Acceptance Criteria

  • Downsampled queries match (within bound) the equivalent raw-data aggregation vs oracle.
  • Retention drops only past-TTL blocks per tenant; storage reclaimed.
  • Cross-tenant reads structurally impossible (I10) vs the tenancy fixtures.
  • Compaction atomic; queries never see a torn merge (I11).

22.5 Conformance Fixtures

  • metrics/downsample_equiv.json, metrics/rollup_recording_rule.json, tenancy/retention_per_tenant.json, tenancy/isolation.json, tenancy/compaction_atomic.json.

22.6 Pitfalls

  • Downsampling must preserve the right aggregates (min/max/avg/count, and the bucket structure for histograms) → a naive avg loses quantile fidelity.
  • Query resolution selection (raw vs 5m vs 1h) by range — get the crossover right or queries are slow/imprecise.
  • Retention dropping data still referenced by an exemplar/trace within another signal's window → coordinate TTLs (a trace dropped at 7d but a metric exemplar at 13mo points at it → SampledOut/expired, I3).
  • Compaction racing a query → atomic publish (I11).
  • Multi-tenant block path leaks (a shared cache key without tenant) → tenant in every key (I10).

22.7 Performance Concerns

  • Compaction is I/O-heavy → off the data plane, throttled; merge is sequential-scan friendly.
  • Downsampled series shrink long-range query cost dramatically (the whole point).
  • Per-tenant partitioning vs many small tenants (overhead) → balance.

22.8 Edge Cases

  • A tenant with retention shorter than another signal's reference window; a brand-new tenant (no blocks); a downsample window with sparse data; a tenant being deleted (drop all partitions).

22.9 Failure Analysis

  • A downsampling bug → wrong long-range dashboards → the downsample-equivalence fixture vs oracle; a retention bug → data loss or unbounded growth → per-tenant TTL fixture + storage monitoring.
  • A tenant-isolation leak → a correctness and security incident → structural partition (I10) + docs/runbooks/tenant-isolation.md.

22.10 Operational Notes

  • Compaction/downsample/retention metrics (blocks merged, bytes reclaimed); per-tenant storage + cardinality dashboards; document retention/rollup config (live hot-reload deferred, restart shipped).

33. Scalability Analysis

  • Ingest scaling: the data plane scales horizontally by sharding tenants/series across obs-ingest nodes; per-node throughput is decode + store bound (§4). The bus (#58) decouples receive from write.
  • The cardinality ceiling: active series, not sample volume, is the binding limit (§4.1) — bounded per tenant (I6); beyond that, more nodes (more tenants/series), not bigger heads.
  • Storage scaling: immutable blocks + compaction + downsampling keep long-range cost sublinear; retention bounds total growth (P10); per-signal blocks scale independently.
  • Query scaling: sharded by time/series; the #59 cache absorbs hot panels; downsampled resolution makes long-range queries cheap. Cross-cluster federation (a global query fan-out) is the large-scale lever — deferred.
  • Correlation scaling: point lookups are O(log n) + cached; the join cost does not grow with total data, only with the indexes — the unification stays cheap at scale (the design intent).
  • Tail-sampling scaling: the buffer is bounded by in-flight traces, not total traffic (§4.2) → scales with concurrency, capped + sheddable.
  • Multi-tenant scaling: structural partitioning (I10) means tenants scale independently; many small tenants add partition overhead (balanced). The quota/control plane that manages thousands of tenants is deferred.
  • What does NOT scale here (by design): unbounded-cardinality instrumentation (rejected, I6); full-text-indexing every log body (we index labels, scan columnar bodies, ADR-6); a single giant trace (bounded assembly).

34. Mental Models & First Principles

The compressed insights an expert in observability backends holds. Each: the model, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — A telemetry signal is an identity stamped on a time series; correlation is just resolving that identity in another store. Predicts: if you normalize trace_id/resource once and index it as a first-class key, every cross-signal pivot is an O(log n) point lookup, not an ETL. Without it: you build three silos and "correlate" by scanning/parsing at query time — the join is slow, lossy, and drifts. Applied: §2.7, §8.2, §8.3, Phase 5 (§17).
  • MM2 — Cardinality, not data volume, is the binding cost of a metrics store. Predicts: a TSDB's RAM ≈ active series × (index entry + open chunk); doubling sample rate is cheap, adding one unbounded label is fatal. Without it: you let user_id become a metric label and OOM the head; you size capacity off bytes/sec and miss the real wall. Applied: §4.1, §8.14, Phase 7 (§19), I6.
  • MM3 — The right home for high-cardinality data is a high-cardinality store, not a label. Predicts: user_id/request_id belong in trace/log attributes or an exemplar, never a metric label or an indexed log term; that placement is what keeps each store bounded. Without it: the same value explodes the metrics series index and the #78 log index and span attributes at once. Applied: §4.1, §8.2 (trace_id indexed, body scanned), ADR-6/ADR-16.
  • MM4 — A tail-sampling buffer is bounded by in-flight traces, not total traffic. Predicts: buffer RAM ≈ in_flight_traces × spans/trace × bytes/span; it scales with concurrency and trace duration, capped by the decision window — a few long traces, not throughput, dominate occupancy. Without it: you size the buffer off ingest rate, a 25 s long-tail trace pins memory, and you OOM (or drop partial traces). Applied: §4.2, Phase 8 (§20), I9, principle 5.
  • MM5 — An immutable, atomically-published block is what makes a query reproducible. Predicts: if writers only ever publish whole immutable blocks and a query pins a snapshot (block set + head epoch), the same (query, snapshot) is bit-stable forever — the basis of differential testing. Without it: queries read half-written state, results flicker, and you can't diff against an oracle. Applied: §3.3 (persistence boundary), Phase 6 (§18), I11/I12.
  • MM6 — Float aggregation is order-sensitive, so determinism requires a fixed evaluation order. Predicts: sum/rate/histogram_quantile over the same series will differ by ULPs unless you sort (by series id) before reducing; cross-implementation equality is only ever "within ε". Without it: query sharding silently changes results, golden tests flake, and "the same query" disagrees with itself. Applied: §8.12, Phase 6 (§18 fixed eval order), I12.
  • MM7 — An exemplar is a pointer, and a pointer can dangle. Predicts: a metric bucket's exemplar trace_id may reference a trace that tail-sampling dropped or retention expired; the only correct outcomes are resolve or an explicit SampledOut/NotFound — never a silent miss. Without it: the pivot 404s with no explanation, on-call loses trust, and sampling/retention silently break correlation. Applied: §4.3, §8.3, Phase 5 (§17 ExemplarResult), Phase 8 (§20 keep_if_exemplar_ref), I3.
  • MM8 — Backpressure is a per-lane property; a slow store must not stall the fast ones. Predicts: with bounded MPSC queues + fan-out per signal, a slow log store backpressures only its own writer; metrics/traces keep flowing, and the system sheds-or-blocks per lane, never grows unbounded. Without it: one slow consumer fills a shared queue, head-of-line blocks every signal, and the whole data plane OOMs or stalls. Applied: §3.5, Phase 1 (§13 backpressure), I4, principle 4.
  • MM9 — A single-window burn-rate alert is forced to choose between flapping and detecting late; two windows escape the dilemma. Predicts: a short window catches acute burns but flaps on blips; a long window is stable but slow — requiring both a short and a long window to burn fires fast on real incidents and stays quiet on transients. Without it: you ship a noisy pager (short window) or miss an SLO breach for hours (long window). Applied: Phase 9 (§21 multi_window), §28 (SLOs).
  • MM10 — A derived metric must be reproducible from its source, or the correlation lies. Predicts: RED/USE series derived from spans must re-derive identically over the same span window (fixed window boundaries + order); only then does "the metric spiked" agree with "these spans were slow". Without it: the derived metric disagrees with the trace reality it points at, and the pivot misleads. Applied: §8.6, Phase 5 (§17 span_to_metrics), I8, principle 10.

36. Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived from the System Constraints table (§4). Formula then result.

  • C1 — Metrics ingest bandwidth. samples/s × bytes/sample. From §4: 2.0 M samples/s/node × 1.3 B/sample (Gorilla, §8.4) ≈ 2.6 MB/s stored metric bandwidth/node (pre-WAL-amplification). Tiny — confirms MM2: metrics cost is cardinality, not bytes.
  • C2 — Metrics head RAM from cardinality. active_series × (index_entry + open_chunk). From §4: 10 M active series × ~hundreds of B (say 700 B index+chunk, §4.1) ≈ ~7 GB head RAM/node before any samples. This is the binding capacity wall, not C1 (MM2).
  • C3 — Trace ingest bandwidth. spans/s × bytes/span. From §4: 1.0 M spans/s/node × 200 B/span ≈ 200 MB/s stored trace bandwidth/node. Two orders of magnitude over metrics — traces are the storage-heavy pillar, motivating tail sampling (§4.2).
  • C4 — Trace storage/day (post-sampling). spans/s × bytes/span × 86,400 × keep_ratio. 1.0 M × 200 B × 86,400 × 0.05 (keep 5%, §4.2) ≈ 864 GB/day/node kept. At 7-day trace retention (§4) ≈ ~6 TB/node resident — the number that forces sampling + short trace TTL.
  • C5 — Log ingest bandwidth. lines/s × bytes/line × compression. From §4: 1.5 M lines/s × ~300 B/line × 0.5 (≤0.5× raw, §4) ≈ 225 MB/s stored/node. Comparable to traces — logs + traces dominate storage; metrics are negligible (C1).
  • C6 — Tail-sampling buffer RAM. in_flight_traces × spans/trace × bytes/span. From §4.2: (50k traces/s × 1 s avg) × 20 spans × 200 B ≈ 200 MB buffered/node — bounded and within a hard cap (MM4). A 30 s decision window (§4) on a few long traces is what the cap + shedding protect against.
  • C7 — Correlation lookup budget. Target p99 < 30 ms (§4) for a pivot of ~3 hops (exemplar slot → trace_index → log trace_id index). 30 ms / 3 hops ≈ 10 ms/hop budget → each hop must be an indexed point lookup (O(log n)) + cache (#59), never a scan (§4.3, MM1).
  • C8 — WAL replay time. head_bytes / replay_throughput. With a ~7 GB metrics head (C2) + trace/log heads, and a target startup < 30 s (§4), replay must sustain ≳ 1 GB/s decode+apply — sets the WAL format's decode-speed requirement (Phase 2 §14).
  • C9 — Ingest acceptance concurrency. accept→durable p99 × throughput (Little's Law). 250 ms (§4) × 2.0 M samples/s ≈ 500k samples in flight in the metrics lane at p99 — the bounded-queue depth budget per lane (I4) must accommodate this without exceeding C2-class RAM.
  • C10 — Per-tenant share at scale. With ≤ ~1000 tenants/node-group (§4) sharing the 10 M-series ceiling (C2), the average tenant ceiling ≈ ~10k active series — but distribution is skewed, so per-tenant limits (I6) must be set individually, not by the mean (motivates §8.14's per-tenant config).
  • C11 — Query result size guard. A range query over 1k series × 6 h at 15 s resolution (§4) = 1000 × (6×3600/15) ≈ 1.44 M points materialized → motivates streaming/paging the result + the result cache (#59) so the ABI (Phase 11 §23) doesn't buffer it whole.
  • C12 — Downsampling savings. A 13-month metric range at raw 15 s vs 1 h downsample = 3600/15 = 240× fewer points for the slow SLO window (Phase 9 §21 / Phase 10 §22) — quantifies why rollups make long-range queries and slow-burn SLO eval affordable (C2/C11).

38. Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same system; each with a sketch, the regime where it wins, the real system embodying it, and why this blueprint rejected it.

Alt-A — Federated single-pillar services, correlation in the UI (the LGTM topology).

 OTLP/scrape ─┬─► Prometheus/Mimir (metrics) ─┐
              ├─► Loki (logs) ────────────────┼─► Grafana (UI joins exemplars + trace_id)
              └─► Tempo (traces) ─────────────┘
  • Wins: when each pillar must scale, version, and be operated independently, adopted incrementally, with correlation as a UI convenience. The dominant real-world deployment.
  • Real system: Grafana LGTM (Mimir + Loki + Tempo + Grafana).
  • Rejected because: this blueprint's thesis is that the pivot is a first-class, snapshot-consistent query (§3.4, MM5), not a UI stitch across three independently-snapshotted services; folding correlation into one engine (principle 2) is the teaching goal. (The independent-services regime is captured in ADR-14's "When the Rejected Choice Wins".)

Alt-B — One wide columnar event store (the Honeycomb model).

 OTLP ─► ingest ─► one columnar store of WIDE EVENTS (a span/log = a row with N high-cardinality cols)
                    query = column select/filter/group over events; "correlation" = same-row fields
  • Wins: high-cardinality exploratory debugging where you store all events un-sampled and slice by arbitrary fields; correlation is trivial because every signal is a field on one row.
  • Real system: Honeycomb (and ClickHouse-backed tracing à la SigNoz).
  • Rejected because: a single wide-row layout sacrifices the metric-range scan efficiency of a Gorilla TSDB and the cheap trace-by-id of an append store (§8.4); three native layouts serve three query patterns better, and the cardinality story differs (MM2/MM3). Regime captured in ADR-16's "When the Rejected Choice Wins".

Alt-C — Pull/scrape-centric metrics with head-only sampling, no central pipeline.

 targets /metrics ◄── scrape loop ──► TSDB         (metrics: PULL)
 SDK head-sample ─► trace store directly           (traces: decide at root, no buffer)
  • Wins: under a hard memory/latency budget (edge, embedded, single-tenant) where a central buffering pipeline + tail buffer can't fit; scrape gives target liveness for free and head sampling needs no buffer.
  • Real system: Prometheus (pull) + head sampling in OTel SDKs.
  • Rejected because: push/OTLP is the signal this platform receives (ADR-4) and tail sampling — keeping the interesting (error/slow) traces — is a core teaching objective (§4.2); pull + head-only can't preserve error traces selectively. Regimes captured in ADR-4 and ADR-13's "When the Rejected Choice Wins".

Alt-D — Object-store-native, compute/storage-separated, globally federated (the Cortex/Mimir-at-scale + Monarch shape).

 ingesters (RAM head) ─► object store (immutable blocks) ◄─ stateless queriers (fan-out, cache)
                                  ▲ compactor                 ▲ global query fan-out across regions
  • Wins: cloud-native multi-region scale where elastic, durable object storage + stateless queriers + cross-region federation matter more than local-FS latency and single-binary simplicity.
  • Real system: Grafana Mimir / Cortex (object-store blocks) and Monarch (regional, push-based, planet scale).
  • Rejected (for the Phase-0 build) because: object-store backend and cross-cluster federation are explicitly deferred (§39, ADR-26) to keep the buildable scope to local-FS blocks and a single/small split deployment; the design leaves the seam (immutable blocks, snapshots) so this is an additive path, not a rewrite. Regime captured in ADR-26's "When the Rejected Choice Wins".

40. Glossary

  • Active series — a time series currently receiving samples; the metrics-store's binding cost (cardinality).
  • Backpressure — bounded-queue + shed/block scheme that prevents the ingest plane from OOMing under a slow consumer.
  • Block — an immutable, atomically-published, time-ranged unit of per-signal storage (queries read these).
  • Burn rate — the rate at which an SLO's error budget is consumed; the basis of SLO alerting.
  • Cardinality — the number of distinct series/streams produced by a label set; the platform's existential constraint.
  • Columnar body (#85) — the log message + high-cardinality fields stored column-wise + compressed (scanned, not indexed).
  • Compactor — the background process doing compaction, downsampling, rollups, and retention.
  • Correlation — joining metrics, logs, and traces by shared identity (resource, trace_id) — the platform's defining feature.
  • Cross-signal join (pivot) — one logical query touching multiple signals joined by identity/time (metric→trace→logs).
  • Decision window — the max time tail sampling buffers a trace before deciding keep/drop.
  • Downsampling — producing lower-resolution (5m/1h) aggregated series for cheap long-range queries.
  • Exemplar — a {trace_id, span_id, value, ts} attached to a metric bucket; the metric→trace bridge.
  • Head — the in-memory, recent, append-target portion of a per-signal store (backed by a WAL).
  • Inverted index (#78) — label name=value → postings; the log/metric selector path.
  • LogQL — the log query language subset (stream selector + line/label filters + log-range aggregations).
  • Multi-window multi-burn-rate — an SLO alert combining fast and slow windows to catch acute + chronic without flapping.
  • OTLP — the OpenTelemetry Protocol; the gRPC/HTTP protobuf format the platform ingests.
  • Pillar — one of metrics, logs, traces (the three telemetry signals this platform unifies).
  • PromQL — the metric query language subset (instant/range vectors, rate, histogram_quantile, aggregations).
  • RED metrics — Rate, Errors, Duration; service metrics derivable from a span stream.
  • Relabel — ingest-time rule to drop/keep/rename/hash labels (the cardinality-control hook).
  • Resource — the OpenTelemetry entity identity (service.name, k8s., host.); the cross-signal resource join key.
  • Retention — the per-tenant per-signal TTL after which blocks are dropped.
  • Rollup — a recording-rule-style precomputed series (e.g. per-service RED at 1m).
  • Scrape — pull-based metric collection (Prometheus-style) from a target's /metrics.
  • Snapshot — a consistent set of published blocks + a head epoch a query reads (the determinism basis).
  • Span — a single timed operation in a trace; {trace_id, span_id, parent, timing, status, attrs}.
  • Staleness — marking a series with no recent sample as stale (no phantom carry-forward).
  • Stream (log) — a unique label set; the unit of log indexing/chunking.
  • Tail-based sampling — deciding keep/drop after the whole trace arrives (vs head sampling at the root).
  • Tenant — an isolated data partition (tenant_id); the multi-tenancy unit.
  • Trace — all spans sharing a trace_id, assembled into a parent/child tree.
  • Trace Context (W3C) — the traceparent/tracestate standard defining trace_id/span_id format.
  • TSDB (#83) — the time-series database backend (Gorilla chunks, head, WAL, blocks).
  • USE metrics — Utilization, Saturation, Errors; resource metrics (Brendan Gregg's method).
  • WAL — write-ahead log; durability for the in-memory head before blocks are cut.
