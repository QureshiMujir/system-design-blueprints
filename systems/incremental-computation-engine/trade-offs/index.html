Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust (edition 2021, MSRV 1.75)

Rejected

C++, OCaml, Go, Haskell

When the rejected choice is right

OCaml when the host is already an ML codebase tolerant of GC pauses — Jane Street's Incremental runs in production there; Rust would be a foreign-toolchain tax.

Why: Borrow checker proves "no stale read across revision" (P13/INV-3); Eq/Hash traits power cutoff+interning; no GC pauses competing with host.

ADR-02

Build system

Chosen

Cargo workspace, 8 crates

Rejected

Bazel, custom make

When the rejected choice is right

Bazel when the engine is one crate inside a 10^4-target polyglot monorepo needing remote-cached, hermetic cross-language builds.

Why: Native Rust tooling; per-crate test/bench/feature isolation; reproducible via Cargo.lock.

ADR-03

Dependency policy

Chosen

Minimal, audited, pinned

Rejected

"pull anything"

When the rejected choice is right

Liberal deps win in an internal app (not a published lib) where velocity beats a lean dep tree and supply-chain surface is already trusted.

Why: Embeddable lib must not bloat host dep tree; every dep justified in notes/dependencies.md; cargo-deny gate.

ADR-04

Concurrent map

Chosen

Sharded map (dashmap or hand-rolled Vec<RwLock<HashMap>>)

Rejected

single Mutex<HashMap>, lock-free trie

When the rejected choice is right

A single Mutex<HashMap> wins when the host is single-threaded (most IDEs analyze one file at a time) — sharding then only adds memory + cache-line waste.

Why: Sharding cuts contention for parallel queries on distinct keys (§4 16-core target); lock-free deferred as premature.

ADR-05

Hashing

Chosen

FxHash (internal), ahash (DoS-exposed keys)

Rejected

SipHash default

When the rejected choice is right

SipHash (std default) wins when keys are fully attacker-controlled over a network boundary and collision-DoS resistance outranks the ~2x hot-path cost.

Why: Internal keys are trusted+hot -> FxHash speed; ahash only where key bytes are adversarial.

ADR-06

Interning

Chosen

Custom append-only Interner (QueryKey -> NodeId u32)

Rejected

string-intern crate, no interning

When the rejected choice is right

No interning wins for a tiny, short-lived graph (a one-shot batch compile) where the interner's table costs more than the few hash comparisons it saves.

Why: Dense NodeId enables array-backed DDG + GC; bespoke control over recycle (INV-11).

ADR-07

Thread-local dep stack

Chosen

std::thread_local! RefCell<DependencyStack>

Rejected

passing a stack arg everywhere

When the rejected choice is right

Explicit stack-argument passing wins in a no_std/embedded target without thread-locals, or when a green-thread runtime multiplexes many logical stacks per OS thread.

Why: TLS keeps the #[query] signature clean (&Database only); per-thread isolation (no cross-contamination).

ADR-08

Parallel executor

Chosen

rayon thread pool (Phase 10)

Rejected

std threads, tokio, custom pool

When the rejected choice is right

tokio wins if queries ever block on async I/O (e.g. a query that fetches a remote artifact) — then a CPU-only rayon pool would stall its workers.

Why: Work-stealing fits independent-query fan-out; no async needed (CPU-bound, no I/O in core).

ADR-09

Async model

Chosen

None in core

Rejected

tokio/async-std throughout

When the rejected choice is right

Async wins when the engine is embedded in an async server (e.g. a language server over async stdio) and demands must yield rather than occupy a blocking thread.

Why: Engine is synchronous + CPU-bound; async adds no value and complicates borrow/Send story.

ADR-10

Cancellation

Chosen

CancellationToken (atomic flag), cooperative checks

Rejected

thread kill, OS signals

When the rejected choice is right

Hard preemption (forced abort) wins when an untrusted/runaway query body has no cooperative cancel points and a hard deadline must be enforced regardless.

Why: Cooperative cancellation at demand boundaries is deadlock-free and leak-free (§4 latency target).

ADR-11

Value storage

Chosen

Host-owned V: Clone + Eq + Hash + Send + Sync in memo

Rejected

engine-owned arena always

When the rejected choice is right

Engine-owned arena wins when values are large and highly shared (e.g. interned ASTs) so that an Arc/arena slash clone cost and bound fragmentation — the Phase-13 value-storage extension.

Why: Keep values where the host wants; arena/interning of values is an opt-in PhaseDeferred("§39").

ADR-12

Serialization (persistence)

Chosen

serde + bincode (Phase 11)

Rejected

protobuf, custom

When the rejected choice is right

protobuf wins when the persisted store must be read by a non-Rust process (cross-language tooling) where bincode's Rust-only framing is a dead end.

Why: serde is idiomatic; bincode compact+fast; format-versioned (§29). Deferred to §22.

ADR-13

Macros

Chosen

syn+quote proc-macros (#[query],#[input])

Rejected

When the rejected choice is right

macro_rules! (or hand-written impls) wins for a fixed, small query set where a proc-macro crate's compile-time cost and opacity outweigh its boilerplate savings.

Why: Query descriptors need type info; keep generated code small + documented (avoid salsa's opacity, R1).

ADR-14

38. Alternative Architectures (Roads Not Taken)

Three fundamentally different architectures for the same problem, why each is real, and why this blueprint rejected it for the Phase-0 target.

A1 — Push-based / eager stabilization (height-ordered).

   input changed
        | (push)
        v
   [recompute all dependents now, in height order]
        |
        v
   outputs always current (no per-read validation)

Regime where it wins: dense, always-observed derived state — spreadsheets, trading dashboards, reactive UIs where nearly every node is displayed every frame, so lazy validation saves nothing and eager recompute avoids per-demand overhead. Real system: Jane Street Incremental (height-based scheduler), the signals pattern in Glimmer/Solid. Why rejected here: ice's target hosts (compilers, IDEs) have sparse demand — an editor shows one file of 10^4 — so eager stabilization would recompute a huge never-observed frontier, the exact opposite of P3/MM4. Push is the dual we point at project 300.

A2 — Content-addressed / hash-of-inputs memoization (no revision clock).

   query(key) ----> H = hash(key, hashes_of_all_inputs_read)
                       |
                       v
                  lookup memo by H  --hit--> reuse
                       | miss
                       v
                  compute, store under H

Regime where it wins: coarse-grained, file-level builds and cross-machine shared caches — the hash is a portable cache key, so a build on machine A is reused on machine B with no shared revision state. Real system: Bazel/Buck (content hashing + remote cache), comemo (Typst, constraint/hash-based). Why rejected here: hashing the full transitive input set on every query is O(inputs) per lookup and loses early cutoff at intermediate nodes (a changed input changes every downstream hash even when the value is unchanged), defeating P4/MM6. Revisions + per-node changed_at give O(1) staleness checks and deep cutoff. Content-addressing is the right model for the deferred cross-process feature (§39), not the in-process core.

A3 — Collection-oriented differential dataflow (per-record diffs).

   input collection --delta {+r1,-r2}--> [map]->[join]->[reduce]
                                            |      |       |
                                       per-record (data, time, diff) flow
                                            v
                                   only affected output rows change

Regime where it wins: incremental view maintenance over large relations and iterative graph computation, where a 1-row change to a 10^9-row input must touch only matched output rows — whole-value recompute of a collection query would be catastrophic. Real system: Differential Dataflow / timely dataflow; the model behind project 366. Why rejected as the core: it solves a different problem (incremental over collections) with signed multiplicities and operator state; forcing scalar query memoization into it adds retraction/multiplicity machinery the compiler/IDE use case does not need. ice keeps whole-value granularity for Phase 0 and offers differential collections as the Phase 13 (§24) extension layered on the same revision core.
