1. Goal & Scope

Build an embeddable, deterministic incremental computation engine — a library that memoizes derived computations and recomputes, on demand, only the work transitively affected by a changed input. The engine tracks a dynamic dependency graph (DDG) discovered by execution tracing, maintains a global revision clock, and reuses prior results via the salsa-style red-green (verified_at / changed_at / durability) algorithm combined with early cutoff on value equality. Recompute cost is O(affected), never O(graph).

In precise engineering terms, the deliverable is a Rust crate set exposing:

  • a Database handle owning input cells, a memo table, and the revision clock;
  • a derived-query mechanism — pure functions Q: (Db, Key) -> Value whose reads of inputs and other queries are captured automatically;
  • demand-driven evaluation — a query computes only when its value is requested (pulled), not eagerly;
  • change propagation — set_input bumps the clock and marks dependents maybe-dirty; a later demand validates the chain bottom-up and reuses or recomputes each node;
  • early cutoff — if a recomputed input or sub-query yields a value Eq to the prior one, downstream memos are backdated and not recomputed;
  • cycle detection — query graphs must be acyclic at runtime; a cycle is a typed recoverable error, not a hang;
  • observability — every reuse/recompute decision, dependency edge, and revision transition is inspectable.

System boundaries

  • In scope: revision clock; input cells; derived/memoized queries; dependency capture; the memo cache + key interning; red-green change propagation; early cutoff; cycle detection; durability classes + backdating; DDG garbage collection + memory bounds; parallel query execution + cancellation; observability (recompute trace, reuse ratio, dependency dumps).
  • Out of scope (engine core): a language frontend, a build executor, a UI framework, a scheduler for external jobs, a network layer, a persistent on-disk store (Phase 11, deferred), collection/differential inputs (Phase 12, deferred). The engine is the substrate those systems are built on.

Explicit non-goals

  • Not a general dataflow/streaming runtime (see project 300 Dataflow Runtime). The engine is pull-based and memoized, not push-based and streaming.
  • Not a reactive UI framework or signals library (see 301 Reactive Programming Runtime); it provides the recomputation kernel such a framework would sit on.
  • Not a build tool (see 136 Bazel-like Build System); it has no process execution, sandboxing, or remote cache.
  • Not a database (see 366 Incremental Reactive Database); no transactions, durability of data, or SQL.
  • Not a parser (see 127 Tree-Sitter incremental parser); incremental parsing is a client.
  • No automatic parallelism of a single query's body; parallelism is across independent demanded queries.
  • No support for impure query functions; purity is an enforced contract (best-effort detection, §7).
  • No distributed / cross-machine memo reuse.

Deployment model

Embeddable Rust library (crates.io-shaped). Linked into a host process: a compiler, an IDE/language server, a build tool, or a UI runtime. No daemon, no server, no IPC in the core. The host owns the event loop and the threads; the engine owns the graph and the clock. A thin ice-cli exists only to drive example workloads and dump traces for debugging.

Target users

Compiler engineers (incremental type-checking, name resolution), IDE / language-server engineers (responsive on-keystroke analysis), build-tool engineers (fine-grained rebuild graphs), and UI / reactive-runtime engineers (derived-state recomputation). Operators are the host application's authors; there is no standalone operator.

Phase 0 deliverable (numbered crates / modules)

  1. ice-core — Revision, Durability, QueryKey, NodeId, Memo, Dependency, DDG storage, the red-green validation state machine (logic only, single-threaded).
  2. ice-macros — #[query] / #[input] proc-macros that generate query descriptors, key types, and dependency-capture shims.
  3. ice-runtime — the Database handle, the sharded memo cache, the execution DependencyStack, the demand-driven evaluator, change propagation, cancellation.
  4. ice-trace — tracing integration, the recompute-event log, reuse-ratio counters, dependency-graph dumps (DOT / JSON).
  5. ice-cli — example-driver binary: load a workload, run queries, mutate inputs, print reuse stats and DDG dumps.
  6. ice-conformance — the from-scratch-recompute oracle harness and fixture runner used by every phase.
  7. ice-bench — criterion benchmark suite (cold build, warm reuse, single-input edit, fan-out edit).
  8. ice-fuzz — cargo-fuzz targets (random query graphs + random edit sequences vs the oracle).

What later phases unlock

  • Phase 1 — a clock and observable input cells.
  • Phase 2 — derived queries with automatically captured dependencies.
  • Phase 3 — memoization: a second demand of an unchanged graph does zero recomputation.
  • Phase 4 — change propagation: an edit invalidates exactly the transitive dependents.
  • Phase 5 — early cutoff: an edit that does not change a value stops propagation at the firewall.
  • Phase 6 — cycles become typed errors, never hangs.
  • Phase 7 — durability classes make "constant" inputs (e.g. stdlib) almost free to validate.
  • Phase 8 — bounded memory under unbounded query-key space (LRU + reachability sweep).
  • Phase 9 — independent queries run on a thread pool with cooperative cancellation.
  • Phase 10 — production observability: reuse ratio, recompute trace, dependency dumps as first-class APIs.

Estimated timeline

  • Phase 0 (crates 1–8, single-threaded correctness + memoization + propagation): 6–14 weeks.
  • Full implementation (through Phase 10, parallel + observability + GC): 5–8 months.

Recommended language and exact rationale

Rust. Reasons, specific to this engine:

  • Ownership prevents the central hazard — handing out a &Value into the memo table while a concurrent revision overwrites it. The borrow checker makes "no observation of a stale value across a revision boundary" (§7) a type property, not a discipline.
  • Eq + Hash as traits — early cutoff and key interning need cheap, total, deterministic equality and hashing; Rust's trait system makes these first-class bounds on query value types.
  • No GC, deterministic drop — memo eviction and DDG sweeps are explicit and timed; there is no background collector competing with the host's pause budget.
  • Fearless concurrency — Send/Sync bounds let the parallel evaluator (Phase 9) share the memo table across a thread pool with the compiler proving data-race freedom. rust-analyzer's salsa proves this is the right substrate.
  • Zero-cost interning + sharded maps — FxHash/ahash and DashMap-style sharding give the contention profile a memoizer needs without a runtime.
  • Proc-macros — #[query] generates the boilerplate (key types, descriptors, capture shims) that would otherwise be hand-written and drift.

Rejected: C++ (no borrow checker → stale-reference and data-race hazards become discipline, not proof); OCaml (Jane Street's Incremental is excellent but GC pauses and weaker data-race story complicate the parallel phase); Go (GC + no generic Eq/Hash bounds at the time of writing make early cutoff and interning awkward); Haskell (laziness fights the explicit demand model and complicates strict early-cutoff equality).

Required prerequisites

  • Compilers / build systems: query-based compiler architecture, name resolution, dependency graphs, the diamond-recompute problem.
  • Data structures / algorithms: topological reasoning on dynamic graphs, hashing, interning, LRU, union-find (for cycle handling), reachability sweeps.
  • Concurrency: sharded locking, lock ordering, cancellation tokens, Send/Sync, false sharing, work stealing.
  • Memory: arena/slab allocation, cache locality, bounded caches, eviction policy design.
  • Systems hygiene: deterministic replay, property-based testing, fuzzing, differential testing against an oracle.
  • Helpful: databases (MVCC intuition for revisions-as-versions), functional programming (purity, referential transparency).

2. Why Build This

Unique systems knowledge taught

  • Incremental computation as a first-class runtime concern. Most engineers cache ad hoc (a HashMap, a lazy_static, manual invalidation). This project teaches the general solution: a self-maintaining DDG that tracks exactly what each result depends on and recomputes the minimal set. This is the kernel behind rust-analyzer, Skip, Glimmer, Adapton, Jane Street's Incremental, and modern build systems.
  • The red-green algorithm. Salsa's verified_at / changed_at / durability scheme is subtle and rarely understood in depth: how maybe-dirty differs from dirty, why backdating is necessary for early cutoff, why durability is an optimization that must never affect correctness. Implementing it from scratch internalizes it.
  • Demand-driven vs eager-dirty propagation. The tension between push (eagerly mark everything dirty on a change) and pull (lazily validate on demand) is the defining design axis of every incremental system. You implement the pull side with a push-side dirtying pass and learn precisely why pull wins for compilers/IDEs (sparse demand) and where push wins (dense, always-observed outputs).
  • Dependency capture by tracing. Recording the exact set of inputs a query read, during execution, via a thread-local read stack — and the invariant that recomputation must read exactly that set or the memo is unsound.
  • Early cutoff and the diamond problem. Why value equality, not input identity, is what stops over-recomputation; how a single firewall node prevents an exponential downstream cascade.

Historical and architectural significance

Incremental computation has a 35-year research arc: Pugh & Teitelbaum (function caching, 1989), Acar's self-adjusting computation (2005), Adapton (PLDI 2014), the incremental λ-calculus / theory of changes (Cai et al.), Build Systems à la Carte (ICFP 2018) unifying the design space, and Differential Dataflow (CIDR 2013) for the collection case. The same ideas independently re-emerged in industry as salsa (rust-analyzer), Incremental (Jane Street), Skip, and the signals pattern in front-end frameworks. Building the engine puts you at the center of that convergence: a compiler's query engine and a UI framework's signal graph are the same machine.

Engineering muscles developed

  • Designing a state machine (node states Verified / Dirty / Maybe-dirty / Computing) and proving its transitions preserve invariants.
  • Concurrency under shared mutable cache — the hardest part of any memoizer: keeping the memo table coherent while many threads read and one revision writes.
  • Allocation discipline — interning keys, arena-backing memos, bounding growth, and measuring it.
  • Differential testing — building a from-scratch-recompute oracle and proving the incremental engine always agrees with it across random edit sequences.
  • Observability design — making an inherently invisible optimization (reuse) measurable and debuggable.

Production engineering concepts exercised

Deterministic replay; bounded resource usage; backpressure (cancellation under load); cache coherence; lock-ordering discipline; semver of an embeddable API; SBOM + reproducible builds; criterion micro-benchmarks with regression gates; fuzz + property testing as the primary correctness instrument.

Calibration value

After this, "just cache it" is never again a vague instinct. You will reason about what a result depends on, when it is stale, and how little must be redone — and you will have built the machine that answers those questions automatically. It is the project that turns "incremental" from a buzzword into an implementable, testable, bounded system property. It also calibrates concurrency judgment: a shared-mutable memo table is among the most demanding concurrency problems in everyday systems work.

What Mastery Looks Like

You have mastered this domain when you can:

  • Derive the red-green algorithm from first principles — explain why verified_at/changed_at are two distinct timestamps and why backdating advances only one (Phase 5, §16; Phase 6, §17) without consulting salsa.
  • Predict the recompute set of any edit by hand — given a DDG and an input change, name exactly which nodes recompute, which backdate, and where the firewall fires (Phase 5, §16; Phase 6, §17).
  • Diagnose an incrementality bug from telemetry alone — read a reuse-ratio collapse or a stale_return_total>0 and name the broken invariant before opening the code (Phase 12, §23; §27 Failure Modes).
  • Build a sound differential oracle — construct the from-scratch reference and the property/fuzz harness that proves INV-1 across random edit sequences (Phase 2, §13; §30 Testing).
  • Design the concurrency of a shared-mutable cache — justify the shard count, the per-key compute lock, and the single-writer/snapshot split, and defend them under loom (Phase 10, §21).
  • Bound memory under an unbounded key space — design LRU + reachability eviction that is provably correctness-safe (INV-10) and stays within a pause budget (Phase 9, §20).
  • Place this engine in the design space — say precisely how it differs from Adapton, Jane Street Incremental, rustc's query system, and differential dataflow, and when each wins (§35 Comparative Architecture; §38 Alternative Architectures).

Trust boundary: the only untrusted code is the host-supplied QueryFn body (assumed pure but not provably so). Concurrency boundary: the Memo Cache, Input Cell Store, and Revision Clock are shared across threads (Phase 9); the DependencyStack is thread-local. Persistence boundary: none in core — the entire state is in-process and volatile (on-disk memos deferred, §11).

Per-box detail

Host application. Owns the event loop, threads, and lifetime. Drives the engine by two operations only: set_input(key, value) (mutation) and db.query::<Q>(key) (demand). It must treat returned values as snapshots valid only until the next mutation it issues; it must never call set_input from inside a query body (that would violate purity). The host decides when to demand — the engine never computes speculatively in Phase 0.

Database handle (ice-runtime). The single owning object. Holds the Revision Clock, Input Cell Store, Memo Cache, Key Interner, DDG, and (Phase 9) the executor. &Database is the capability passed to every query. It is Sync; mutation methods take &mut self or use interior synchronization (durability-tagged). It mediates every read so dependencies can be captured. Cloning a handle shares the same underlying state (Arc-backed storage).

Revision Clock. A monotonic Revision(u64) — the global logical clock. Every set_input that actually changes a value increments it. The clock also stores, per durability class, the last revision at which an input of that durability changed (the durability map), enabling the "if nothing of durability >= D changed since verified_at, skip re-validation" shortcut (§7). Never decreases; wraps are unreachable in practice (u64) but treated as a fatal invariant breach.

Input Cell Store. Maps each input key to (value, changed_at: Revision, durability: Durability). The leaves of the DDG. set_input compares new vs old by Eq; if equal, it is a no-op (no clock bump) — input-level early cutoff. If different, it writes the value, sets changed_at = new current revision, and updates the durability map. Reads of input cells from inside a query are intercepted to record a dependency edge on the DependencyStack.

DependencyStack (thread-local). A per-thread stack of frames, one per query currently executing on that thread. The top frame accumulates the set of (NodeId, verified-at-read-time) edges as the running query reads inputs and sub-queries. On query completion the frame's edge set becomes the memo's deps. This is dependency capture by execution tracing — the engine learns the dependency set by running the query, not by static analysis. Thread-local so parallel queries do not cross-contaminate edge recording.

Memo Cache (sharded). QueryKey -> Memo. The heart. Memo carries the cached value, verified_at (last revision we confirmed it current), changed_at (last revision its value actually changed — drives downstream cutoff), durability (min over its inputs' durabilities), and deps (the captured edge list). Sharded by key hash into N independent lock domains (DashMap-style) so parallel queries on different keys do not contend. Lookups return either a usable memo (fast path) or trigger validate-or-recompute.

Query Evaluator. Implements the red-green state machine. On demand for key k: if a memo exists and verified_at == current_rev -> reuse (green). Else run maybe-dirty validation: for each dependency, recursively demand it; if every dep's changed_at <= memo.verified_at (none changed since we last verified) -> backdate (verified_at = current_rev, value reused) — deep early cutoff. Otherwise recompute: push a DependencyStack frame, call the QueryFn, capture deps, compare new value to old by Eq; if equal, keep changed_at (cutoff), else changed_at = current_rev; set verified_at = current_rev.

#[query] user function (QueryFn). The host-supplied pure function. Receives &Database and the key; returns the value. All its reads of inputs/queries route through the Database so they are captured. It must be deterministic and side-effect-free (§6, §7). The engine cannot prove this; it provides best-effort detection (a debug-mode read-set replay check) and documents the contract loudly.

Key Interner. Maps each QueryKey to a compact NodeId(u32) so the DDG, reverse-edge index, and GC structures can use dense integer arrays instead of hashing full keys repeatedly. Interning is append-only within a process (keys are never un-interned while reachable); GC may recycle NodeIds only after a key's memo is evicted and all reverse edges are gone.

DDG (forward + reverse edges). The dynamic dependency graph. Forward edges: query -> things it read. Reverse edges: input/query -> queries that read it (the dependents index, needed to mark maybe-dirty on a change and to compute reachability for GC). Edges are versioned (each edge remembers the verified_at of the dependency when it was read) so validation can detect staleness precisely.

Maybe-dirty frontier. The set of nodes transitively reachable (via reverse edges) from a just-changed input, marked maybe-dirty (not dirty). "Maybe" because early cutoff might prove a node's value is unchanged despite an upstream change — so we cannot eagerly mark dirty. The frontier is what the validate pass walks lazily on demand.

Cycle Detector. A per-evaluation on-stack set of NodeIds currently being computed. If a demand re-enters a key already on the stack, that is a cycle -> return a typed CycleError carrying the participating keys, unwind cleanly, and never cache a partial result. Query graphs must be acyclic at runtime (§6, §7).

Garbage Collector. Bounds memo memory. Combines LRU (evict least-recently-demanded memos first) with a reachability sweep (a memo reachable only from already-evicted memos and not currently demanded is collectible). Honors a configured memory ceiling (§4). Eviction is always safe: a missing memo is simply recomputed on next demand (the oracle property — the engine is a cache, never the source of truth for derived values).

Parallel Executor (Phase 9). A thread pool that evaluates independent demanded queries concurrently. A per-key compute lock ensures two threads never recompute the same key simultaneously (the second waits on the first). A CancellationToken lets the host abandon an in-flight demand (e.g. a superseded IDE request); cancellation is cooperative — checked at demand boundaries. Cross-thread sharing of the Memo Cache and Input Cell Store is the central concurrency hazard the design controls.

ice-trace. The observability sink. Receives structured events (reuse, recompute, backdate, cutoff-fired, cycle, eviction, revision-bump), maintains counters (reuse ratio, recomputes per revision, memo count, bytes), and can dump the DDG as DOT/JSON for offline inspection. Emits tracing spans so a host can correlate engine work with its own.

6. Design Principles

Each principle is non-negotiable and referenced throughout. Format: statement; explanation; tradeoff; operational implication; how violation breaks the system.

P1 — Determinism of query functions. A query's output is a pure function of its inputs at a revision. Tradeoff: forbids reading the clock, RNG, time, or environment inside a query. Operational: enables replay, differential testing, and caching at all. Violation: a non-deterministic query returns value A then B for the same inputs; the memo lies; downstream cutoff makes wrong reuse decisions; bugs are unreproducible. Detected in debug builds by re-running and comparing (§7).

P2 — Purity / no observable side effects. Queries may not mutate inputs, perform observable I/O, or call set_input. Tradeoff: logging/metrics inside a query must be idempotent and not depended upon. Operational: lets the engine skip, reorder, parallelize, and cancel query execution freely. Violation: if a query writes a file, skipping its recompute (cutoff/reuse) silently drops the side effect; the host's world diverges from the memo.

P3 — Demand-driven (pull) recomputation. Nothing recomputes until its value is requested. Tradeoff: first demand after a change pays validation cost; no eager warm-up. Operational: sparse workloads (IDE shows one file) do near-zero work; matches compiler/IDE access patterns. Violation: eager recompute of the whole maybe-dirty frontier turns an O(affected-and-observed) workload into O(affected), wasting work on never-observed nodes — the opposite of incrementality for sparse demand.

P4 — Early cutoff by value equality. Propagation stops when a recomputed value equals the prior value (by Eq). Tradeoff: requires every memoized value to implement a correct, total, deterministic Eq; equality must be cheap or it eats the savings. Operational: the firewall that makes a format-only edit free downstream. Violation: a missing/over-broad Eq either floods downstream with needless recompute (no cutoff) or reuses across a real change (an equality lie, §7) — silent wrong results.

P5 — Minimality (recompute only transitively affected). The engine must never recompute a node not reachable from a changed input. Tradeoff: requires exact dependency capture and a precise reverse-edge index. Operational: the headline O(affected) guarantee (§4). Violation: over-recompute (perf regression, reuse ratio drops, latency spikes) or — worse — under-recompute (stale results) if a real dependency was not captured.

P6 — Explicit revision clock. A single monotonic global clock orders all state. Tradeoff: every mutation is globally serialized (a write on the clock); fine for the embedded, mostly-read workload. Operational: gives a crisp definition of "current," "verified_at," and "stale"; makes the snapshot a query sees well-defined. Violation: a non-monotonic or per-shard clock destroys the verified_at/changed_at comparisons; reuse decisions become unsound.

P7 — Dependency capture is exact and complete. The recorded dep set equals exactly the set of inputs/queries the body read. Tradeoff: every read must route through the Database (no back-door access to input storage). Operational: the basis of correct invalidation. Violation: a missed edge -> stale reuse; a phantom edge -> needless recompute. Debug builds assert the recompute read-set equals the recorded set (§7, INV-5).

P8 — Backdating preserves cutoff across depth. When validation proves a node unchanged, its verified_at advances but changed_at does not; dependents comparing against changed_at then also cut off. Tradeoff: requires the two-timestamp scheme (more memo state). Operational: makes cutoff transitive — a deep firewall works. Violation: advancing changed_at on a no-op revalidate breaks deep cutoff; every revision re-floods the graph.

P9 — Durability is an optimization, never a correctness lever. Marking an input "constant/durable" only lets validation skip work; it must never change a result. Tradeoff: mis-marking a volatile input as durable causes stale reads. Operational: makes stdlib/config inputs near-free to validate. Violation: if durability ever decides a value, a durable-but-actually-changed input yields stale results — so durability gates only the skip-validation shortcut, behind a clock check (§7).

P10 — Observability of reuse. Every reuse/recompute/backdate/cutoff/eviction decision is countable and traceable. Tradeoff: event emission has a small, sampled cost. Operational: the only way to debug "why did this recompute" and to regression-gate the reuse ratio. Violation: without it, incrementality bugs (silent over-recompute, broken cutoff) are invisible until they manifest as latency, with no signal pointing at the cause.

P11 — Bounded memo growth. Memo memory is capped; the engine evicts rather than OOMs. Tradeoff: evicted memos cost a recompute on next demand. Operational: lets the engine run indefinitely in a long-lived IDE. Violation: unbounded growth -> host OOM; or eviction of a currently-demanded memo mid-evaluation -> use-after-evict bug.

P12 — Cycles are errors, not hangs. A query graph cycle is a typed recoverable error surfaced immediately. Tradeoff: the engine must detect re-entry on the compute stack (small per-frame cost). Operational: a buggy mutually-recursive query fails fast with the participating keys, not a deadlock/stack overflow. Violation: no detection -> infinite recursion / stack overflow / deadlock under the per-key compute lock.

P13 — No observation of a stale value across a revision boundary. Once a revision is current, no demand may return a value computed against an older revision without re-validation. Tradeoff: validation on the first post-change demand. Operational: linearizable reads — the host always sees a consistent snapshot. Violation: a torn read (old value + new clock) corrupts every downstream cutoff decision and the host's view of the world.

P14 — The engine is a cache, not a source of truth (for derived values). Any memo may be dropped and reconstructed; only inputs are authoritative. Tradeoff: none for correctness; eviction always safe. Operational: GC, persistence-miss, and cold-start all reduce to "recompute on demand." Violation: if anything treats a memo as authoritative (e.g. a side effect that only happens during recompute, see P2), eviction silently changes behavior.

P15 — Single concurrent recompute per key. Two threads must never recompute the same key at once; the second joins the first. Tradeoff: a per-key compute lock + a "computing" state. Operational: prevents duplicated work and divergent memos under parallelism (Phase 9). Violation: duplicate recomputes waste CPU; if their captured dep sets differ (P1 violation) the memo table becomes inconsistent.

7. System Invariants

Each invariant: statement; why; where enforced; detection; telemetry; recovery; debugging methodology. INV-* IDs are referenced from phases and failure analysis.

INV-1 — From-scratch consistency. For any input sequence, db.query::<Q>(k) returns a value Eq to what a fresh Database built from the same inputs would return.

  • Why: the engine's entire reason to exist — incrementality must be invisible to results.
  • Where: implied by INV-2..INV-9; verified externally by the oracle harness (ice-conformance).
  • Detection: differential test — run incremental vs a from-scratch Database after every edit; assert Eq.
  • Telemetry: conformance.divergence_total (must be 0); on mismatch, dump both values + the DDG.
  • Recovery: none in prod (a divergence is a correctness bug, not a runtime condition); fail the test.
  • Debugging: shrink the edit sequence (proptest), bisect to the first diverging query, dump its captured vs recomputed dep set.

INV-2 — Revision monotonicity. current_rev only ever increases; set_input either leaves it unchanged (no-op) or increments by exactly 1.

  • Why: every staleness comparison (changed_at <= verified_at) assumes a total order.
  • Where: Revision Clock; bump() is the only writer, behind &mut self / single-writer model.
  • Detection: debug assert new > old; assert!(rev != u64::MAX) guards wrap.
  • Telemetry: engine.revision gauge; engine.revision_bumps_total counter.
  • Recovery: unreachable; a wrap or decrease is panic! (fatal — memo table is meaningless past it).
  • Debugging: log every bump with cause (which input key, which durability).

INV-3 — No stale read across a revision boundary (P13). A returned value is always validated against current_rev before it leaves the Database.

  • Why: a torn read poisons all downstream cutoff decisions.
  • Where: Query Evaluator entry — verified_at == current_rev is the only fast-path exit.
  • Detection: every memo returned carries verified_at; debug assert verified_at == current_rev at the return site.
  • Telemetry: engine.stale_return_total (must be 0).
  • Recovery: re-enter validation; if validation itself returns stale, panic (logic bug).
  • Debugging: trace the validate path; confirm each dep was demanded before the parent returned.

INV-4 — Cutoff soundness (P4/P8). changed_at advances only when the recomputed value is !Eq to the prior value; a no-op revalidate advances verified_at only.

  • Why: dependents key cutoff off changed_at; a spurious advance re-floods, a missed advance hides a real change (stale).
  • Where: the recompute tail of the Query Evaluator (the Eq compare + timestamp update).
  • Detection: debug assert: if new_value Eq old_value then changed_at unchanged; else changed_at == current_rev.
  • Telemetry: engine.cutoff_fired_total, engine.changed_at_advanced_total.
  • Recovery: none; a cutoff bug is a correctness bug (INV-1 will also fire).
  • Debugging: dump (old_value, new_value, Eq result, old/new changed_at) for the suspect key.

INV-5 — Dependency completeness & exactness (P7). A memo's deps equals exactly the set of inputs/queries read during its computation — no more, no fewer.

  • Why: the basis of correct invalidation; a missed edge -> stale reuse, a phantom edge -> waste.
  • Where: DependencyStack frame; every Database read pushes an edge to the top frame.
  • Detection: debug "read-set replay" — recompute with a recording Database and assert the read set equals stored deps.
  • Telemetry: engine.depset_mismatch_total (debug only; must be 0).
  • Recovery: none; a mismatch means a read bypassed the Database (back-door) — a bug.
  • Debugging: instrument the back-door (e.g. direct InputCellStore access) and panic in debug.

INV-6 — Maybe-dirty conservativeness. Every node whose value could have changed is in the maybe-dirty frontier after a set_input; no actually-affected node is omitted.

  • Why: if an affected node is not marked, demand takes the green fast path and returns stale (INV-3 breach).
  • Where: push dirtying pass — reverse-edge BFS from the changed input.
  • Detection: after dirtying, assert the frontier is a superset of nodes reachable via reverse edges from the changed key.
  • Telemetry: engine.maybe_dirty_marked_total per revision.
  • Recovery: none; under-marking is a correctness bug (INV-1).
  • Debugging: dump the reverse-edge closure vs the marked set after a problem edit.

INV-7 — Cycle safety (P12). A re-entrant demand of a key already on the compute stack returns CycleError; no partial/torn memo is ever cached for a cycle participant.

  • Why: prevents infinite recursion / deadlock under the per-key compute lock.
  • Where: on-stack NodeId set in the evaluator; checked at every demand entry.
  • Detection: membership test on demand; on hit, construct CycleError{ cycle: Vec<QueryKey> }.
  • Telemetry: engine.cycle_detected_total; logs the participating keys.
  • Recovery: unwind the stack, drop all in-progress frames for participants, optionally invoke registered fixpoint recovery (Phase 8).
  • Debugging: the error carries the full cycle path; render it as a DOT subgraph.

INV-8 — Single concurrent recompute per key (P15). At most one thread is in state Computing for a given key; others block on the per-key compute lock.

  • Why: duplicate recompute wastes CPU and can produce divergent memos.
  • Where: per-key lock + Computing state in the memo cell (Phase 9).
  • Detection: the state machine refuses a second -> Computing transition; debug assert single ownership.
  • Telemetry: engine.compute_lock_wait_total, engine.duplicate_compute_total (must be 0).
  • Recovery: the second thread waits then reads the freshly-written memo.
  • Debugging: record the owning thread id on the Computing cell; dump on contention spikes.

INV-9 — Determinism / no hidden inputs (P1). A query reads only Database-routed inputs; reading wall-clock, RNG, env, or process state is forbidden and flagged.

  • Why: hidden inputs make memos lie and break replay/differential testing.
  • Where: contract; best-effort detection via debug re-run comparison.
  • Detection: recompute twice at the same revision; values must be Eq. Optional #[query(nondeterministic)] opt-out flag that disables memoization entirely.
  • Telemetry: engine.nondeterminism_suspected_total.
  • Recovery: mark the query non-memoizable (always recompute) if flagged; otherwise it is a contract violation.
  • Debugging: the debug re-run diff points at the offending query; audit its body for clock/RNG.

INV-10 — Memo evictability is always safe (P14). Evicting any memo never changes a future result; a missing memo is recomputed identically.

  • Why: GC, persistence-miss, and cold-start all rely on it.
  • Where: GC (§8 phase); eviction only removes memos not currently on a compute stack.
  • Detection: differential test with GC forced after every edit vs no GC; results must match (INV-1).
  • Telemetry: engine.evicted_total, engine.evict_then_recompute_total.
  • Recovery: recompute on next demand.
  • Debugging: enable "evict-everything-each-revision" stress mode; any divergence reveals a hidden side effect (P2 breach).

INV-11 — Interning stability within a process. A given QueryKey maps to one stable NodeId for as long as any reachable structure references it; NodeIds are only recycled after full eviction.

  • Why: the DDG, reverse index, and GC use dense NodeId arrays; a remap mid-life corrupts edges.
  • Where: Key Interner; recycle only on GC with proof of zero references.
  • Detection: debug assert no live edge references a recycled NodeId.
  • Telemetry: engine.nodeid_recycled_total, engine.interned_keys.
  • Recovery: none; a bad recycle is a memory-safety-adjacent bug.
  • Debugging: tag recycled ids with a generation counter; assert generation match on edge traversal.

INV-12 — Durability never affects a value (P9). Durability only gates the skip-validation shortcut, always behind a clock check; turning durability off must not change any result, only performance.

  • Why: a durability bug that changes values is a silent correctness failure.
  • Where: the durability shortcut in the Query Evaluator (if durability_map[D] <= verified_at { skip }).
  • Detection: differential test with all durabilities forced to Low vs declared; results identical.
  • Telemetry: engine.durability_shortcut_hits_total.
  • Recovery: none; treat as correctness bug.
  • Debugging: force-Low mode reproduces; bisect to the input whose declared durability lied.

8. Domain Model

The domain is a dynamic dependency graph (DDG) of two node kinds (inputs, derived queries) connected by versioned dependency edges, evaluated against a monotonic revision clock.

Node and edge schema

Node        := Input | Derived
Input       := { key: QueryKey, value: V, changed_at: Revision, durability: Durability }
Derived     := { key: QueryKey, memo: Option<Memo> }          // None => never computed / evicted
Memo        := { value: V, verified_at: Revision, changed_at: Revision,
                 durability: Durability, deps: Vec<Dependency>, state: NodeState }
Dependency  := { node: NodeId, changed_at_when_read: Revision } // versioned reverse-checkable edge
NodeId      := u32                                              // interned, dense
QueryKey    := (QueryTypeId, KeyBytes)                          // identifies one node
Durability  := Low | Medium | High                             // High = changes rarely
NodeState   := Unverified | Verifying | Verified(Revision) | MaybeDirty | Computing
Revision    := u64                                             // monotonic, global

Forward edges live in each memo's deps; reverse edges live in a separate dependents: NodeId -> SmallVec<NodeId> index maintained alongside.

Node state transition table

From Event To Side effects
(absent) first demand Computing push DependencyStack frame
Computing QueryFn returns, value Eq old (or first run) Verified(R) verified_at=R; changed_at set (R if first run, else kept)
Computing QueryFn returns, value !Eq old Verified(R) verified_at=R; changed_at=R
Computing re-entrant demand of self (error) emit CycleError; do not cache

Worked example — A=1, B=A+1, C=B*2

Inputs/queries: input A; derived B = A + 1; derived C = B * 2. Reverse edges: A -> {B}, B -> {C}.

Cold build at R0 (set_input(A, 1) made R1; demand C):

demand C@R1 -> no memo -> Computing
  demand B@R1 -> no memo -> Computing
    read A -> value 1, A.changed_at=R1; record edge C? no: edge on B's frame: (A, changed_at=R1)
  B computes 2; verified_at=R1, changed_at=R1, deps=[A@R1]
  read B (edge on C's frame): (B, changed_at=R1)
C computes 4; verified_at=R1, changed_at=R1, deps=[B@R1]
Result: C=4. Recomputes: B,C (2). Reuses: 0.

Real edit — set_input(A, 5) (-> R2), demand C:

set_input(A,5): 5 != 1 -> bump to R2; A.value=5, A.changed_at=R2
  dirtying: reverse-closure(A) = {B, C} marked MaybeDirty
demand C@R2 -> MaybeDirty -> validate deps:
  dep B (changed_at_when_read=R1): demand B@R2 -> MaybeDirty -> validate deps:
    dep A: A.changed_at=R2 > B.verified_at(R1) -> A changed -> recompute B
    B recompute: reads A=5 -> 6; 6 != 2 -> changed_at=R2, verified_at=R2, deps=[A@R2]
  back in C: B.changed_at=R2 > C.verified_at(R1) -> recompute C
  C recompute: reads B=6 -> 12; verified_at=R2, changed_at=R2
Result: C=12. Recomputes: B,C (2 — all affected). Reuses: 0. Correct = from-scratch.

Early cutoff — set_input(A, 5) again (already 5):

set_input(A,5): 5 == 5 (Eq) -> NO-OP; clock stays R2. Input-level cutoff.
demand C@R2 -> Verified(R2) == current -> green hit. Recomputes: 0.

Deep cutoff example — make B output insensitive. Redefine B = min(A, 10). At R2, A goes 5 -> 8 (R3):

set_input(A,8) -> R3; dirty {B,C}
demand C@R3 -> MaybeDirty -> validate B:
  B MaybeDirty -> A.changed_at=R3 > B.verified_at(R2) -> recompute B
  B recompute: min(8,10)=8 ... wait prior B was min(5,10)=5; 8 != 5 -> changed_at=R3
  (cutoff would fire only if new B Eq old B)

Now A goes 8 -> 12 (R4) with B = min(A, 10):

set_input(A,12) -> R4; dirty {B,C}
demand C@R4 -> validate B:
  recompute B: min(12,10)=10; prior B (at R3) = 8; 10 != 8 -> changed (no cutoff here)

And A goes 12 -> 20 (R5):

recompute B: min(20,10)=10; prior B = 10; 10 Eq 10 -> CUTOFF: verified_at(B)=R5, changed_at(B) stays R4
back in C: B.changed_at=R4 <= C.verified_at(R4)? C last verified at R4 -> R4 <= R4 -> B did NOT change since -> backdate C: verified_at(C)=R5, no recompute.
Result: C reused. Recomputes: B only (1). C cut off by B's firewall.

A single Mutex<HashMap> wins when the host is single-threaded (most IDEs analyze one file at a time) — sharding then only adds memory + cache-line waste.
ADR-05 Hashing FxHash (internal), ahash (DoS-exposed keys) SipHash default Internal keys are trusted+hot -> FxHash speed; ahash only where key bytes are adversarial. SipHash (std default) wins when keys are fully attacker-controlled over a network boundary and collision-DoS resistance outranks the ~2x hot-path cost.
ADR-06 Interning Custom append-only Interner (QueryKey -> NodeId u32) string-intern crate, no interning Dense NodeId enables array-backed DDG + GC; bespoke control over recycle (INV-11). No interning wins for a tiny, short-lived graph (a one-shot batch compile) where the interner's table costs more than the few hash comparisons it saves.
ADR-07 Thread-local dep stack std::thread_local! RefCell<DependencyStack> passing a stack arg everywhere TLS keeps the #[query] signature clean (&Database only); per-thread isolation (no cross-contamination). Explicit stack-argument passing wins in a no_std/embedded target without thread-locals, or when a green-thread runtime multiplexes many logical stacks per OS thread.
ADR-08 Parallel executor rayon thread pool (Phase 10) std threads, tokio, custom pool Work-stealing fits independent-query fan-out; no async needed (CPU-bound, no I/O in core). tokio wins if queries ever block on async I/O (e.g. a query that fetches a remote artifact) — then a CPU-only rayon pool would stall its workers.
ADR-09 Async model None in core tokio/async-std throughout Engine is synchronous + CPU-bound; async adds no value and complicates borrow/Send story. Async wins when the engine is embedded in an async server (e.g. a language server over async stdio) and demands must yield rather than occupy a blocking thread.
ADR-10 Cancellation CancellationToken (atomic flag), cooperative checks thread kill, OS signals Cooperative cancellation at demand boundaries is deadlock-free and leak-free (§4 latency target). Hard preemption (forced abort) wins when an untrusted/runaway query body has no cooperative cancel points and a hard deadline must be enforced regardless.
ADR-11 Value storage Host-owned V: Clone + Eq + Hash + Send + Sync in memo engine-owned arena always Keep values where the host wants; arena/interning of values is an opt-in PhaseDeferred("§39"). Engine-owned arena wins when values are large and highly shared (e.g. interned ASTs) so that an Arc/arena slash clone cost and bound fragmentation — the Phase-13 value-storage extension.
ADR-12 Serialization (persistence) serde + bincode (Phase 11) protobuf, custom serde is idiomatic; bincode compact+fast; format-versioned (§29). Deferred to §22. protobuf wins when the persisted store must be read by a non-Rust process (cross-language tooling) where bincode's Rust-only framing is a dead end.
ADR-13 Macros syn+quote proc-macros (#[query],#[input]) declarative macro_rules!, manual Query descriptors need type info; keep generated code small + documented (avoid salsa's opacity, R1). macro_rules! (or hand-written impls) wins for a fixed, small query set where a proc-macro crate's compile-time cost and opacity outweigh its boilerplate savings.
ADR-14 Error model Typed enums (CycleError,OutOfMemo); thiserror anyhow, panics for control flow Cycles/OOM are recoverable -> typed; panics reserved for invariant breaches (INV-2/INV-11). anyhow wins in the ice-cli/example binaries (not the library) where ergonomic error bubbling beats exhaustive typed matching.

A built-in Prometheus client wins for a standalone service (not an embeddable lib) that scrapes its own /metrics and has no host to delegate export to.

11. Core Schema & Types

All load-bearing types as lightweight signatures. For each: ownership, mutation, concurrency, persistence, serialization, compatibility. No full bodies (CRITICAL RULE 10).

Revision (ice-core/revision.rs)

struct Revision(u64);                 // monotonic logical clock value
struct Clock { current: AtomicU64, by_durability: [AtomicU64; 3] }
impl Clock { fn current(&self)->Revision; fn bump(&self, d: Durability)->Revision; }
  • Ownership: owned by Database. Mutation: bump only (single-writer or &mut). Concurrency: AtomicU64 for lock-free reads (Phase 9). Persistence: serialized as u64 (Phase 11). Serialization: transparent u64. Compatibility: width fixed at 64-bit; never narrowed.

Durability (ice-core/durability.rs)

enum Durability { Low, Medium, High }    // ordered; High changes rarest
impl Durability { fn index(self)->usize; }
  • Ownership: Copy. Mutation: none. Concurrency: trivially Send+Sync. Persistence: u8 tag. Compatibility: variants append-only; never reordered (tags stable).

QueryKey / NodeId (ice-core/key.rs, nodeid.rs)

struct QueryTypeId(u32);                 // one per #[query]/#[input] type
struct QueryKey { ty: QueryTypeId, bytes: KeyBytes }  // identifies a node
struct NodeId { index: u32, generation: u16 }          // interned, recyclable (INV-11)
  • Ownership: QueryKey cloned into the interner; NodeId is Copy. Mutation: none post-intern. Concurrency: interner behind a lock/shard. Persistence: keys serialized by bytes; NodeIds are process-local, never persisted (remapped on load). Compatibility: QueryTypeId assignment stable within a build; persistence keys on (ty-name, bytes) not the numeric id.

Memo / Dependency / NodeState (ice-core/memo.rs)

struct Memo<V> {
  value: V, verified_at: Revision, changed_at: Revision,
  durability: Durability, deps: SmallVec<[Dependency; 4]>, state: NodeState,
}
struct Dependency { node: NodeId, changed_at_when_read: Revision }
enum NodeState { Unverified, Verifying, Verified(Revision), MaybeDirty, Computing }
  • Ownership: memo owns its value (host type V); lives in the memo cache. Mutation: replaced wholesale on recompute; verified_at/changed_at/state updated under the shard lock. Concurrency: one writer per key (INV-8); readers see a consistent memo via the shard RwLock. Persistence: value requires Serialize for Phase 11; deps persisted by stable key, not NodeId. Serialization: serde; state is reset to Unverified on load (must revalidate, INV-3). Compatibility: memo header is format-versioned; adding fields is a minor bump with defaults.

Database / DatabaseBuilder (ice-runtime/database.rs)

struct Database { /* Arc<Inner>: clock, inputs, memo_cache, interner, ddg, exec */ }
impl Database {
  fn builder() -> DatabaseBuilder;
  fn query<Q: Query>(&self, key: Q::Key) -> Q::Value;        // demand (pull)
  fn set_input<I: Input>(&mut self, key: I::Key, value: I::Value); // mutation
  fn current_revision(&self) -> Revision;
  fn snapshot(&self) -> Snapshot;                            // read-only handle (Phase 9)
  fn sweep_gc(&mut self, target_bytes: usize);               // §8 phase
}
  • Ownership: Arc-backed Inner; cloning shares state. Mutation: set_input/sweep_gc take &mut (single-writer model) or go through interior sync. Concurrency: Send+Sync; &Database is the query capability; Snapshot gives lock-free reads at a pinned revision. Persistence: save/load (Phase 11) round-trip inputs+memos. Compatibility: the public API is semver-governed (§29); additive methods are minor.

Query / Input traits (generated by ice-macros)

trait Query {
  type Key: Clone + Eq + Hash + Send + Sync;
  type Value: Clone + Eq + Send + Sync;     // Eq -> early cutoff (P4/INV-4)

Compatibility: changing a query's logic invalidates persisted memos (format/version check rejects mismatched provider hashes, §11).

DependencyStack (ice-runtime/dep_stack.rs)

thread_local! { static STACK: RefCell<DependencyStack>; }
struct DependencyStack { frames: Vec<Frame> }

12. Phase 1 — Revision Clock + Observable Input Cells

1.1 Objectives

  • Stand up Database/Inner skeleton + monotonic Revision clock (INV-2).
  • Implement InputCellStore: set_input / get_input, input-level early cutoff (Eq no-op), changed_at stamping.
  • No derived queries, no memo, no deps yet — leaves of the DDG only.
  • Establish the single-writer mutation model (&mut Database) before concurrency (Phase 9).

1.2 Detailed Implementation Steps

Applies P1/P2 (purity), P6 (explicit revision clock), INV-2 (revision monotonicity); the input-level no-op is the leaf case of P4 early cutoff.

Step File Work
Clock ice-core/revision.rs Clock{current:AtomicU64, by_durability:[AtomicU64;3]}; current(), bump(d)->Revision (single writer).
Input store ice-runtime/input_store.rs HashMap<NodeId,(V,Revision,Durability)>; set_input compares new Eq old → no-op or write+bump.
Interner stub ice-runtime/interner.rs append-only QueryKey→NodeId(u32); generation tag reserved (INV-11), recycle disabled this phase.

1.3 Deliverable

Library where the host can set_input(k,v), get_input(k), read current_revision(). Setting an Eq-equal value is a no-op (clock unchanged). ice-cli inputs workload sets/reads cells and prints the revision trajectory.

1.4 Acceptance Criteria

  • set_input with a new value → current_revision() increments by exactly 1 (INV-2).
  • set_input with an Eq-equal value → revision unchanged; RevisionBump not emitted.
  • changed_at of a cell equals the revision at which its value last actually changed.
  • 10^6 set_input of trivial scalars complete; no clock regression observed (debug assert new>old).
  • criterion single_edit cold path records a baseline for input write (~tens of ns).

1.5 Conformance Fixtures

Fixture Purpose Expected
conformance/basic/input_set_get.fixture set then get a cell returned value == last set value
conformance/basic/input_noop_cutoff.fixture set same value twice second set: no revision bump
conformance/basic/input_changed_at.fixture set,set-different changed_at advances only on real change
conformance/basic/revision_monotonic.fixture mixed set sequence revision strictly non-decreasing, +1 per real change

1.6 Pitfalls

  • Bump-on-equal: bumping the clock for an Eq-equal write breaks INV-4 downstream later (spurious change). Compare before writing.
  • Eq not total: a value with NaN-style partial equality silently misclassifies no-ops. Require total Eq, not PartialEq only.
  • Stamping changed_at from a stale clock read: read current after bump for the new stamp, not before.
  • Interner racing: even single-threaded, re-interning the same key must return the same NodeId; assert idempotence.

1.7 Performance Concerns

  • set_input hot path = hash lookup + Eq + maybe a write; keep Eq cheap (scalars/small structs). Allocation only on first insert of a key.
  • AtomicU64 clock read is a relaxed load; no contention single-threaded. Avoid SeqCst where Relaxed/Acquire suffices (revisit Phase 9).
  • Interner table reserve to amortize rehash on bulk input load.

1.8 Edge Cases

  • First set_input of a key (no prior value) → always a change, bump+stamp.
  • set_input to a value equal under Eq but distinct bit pattern (e.g. +0.0/-0.0) → no-op (matches Eq); document this.
  • Removing an input (not in scope) — inputs are append/overwrite only this phase.
  • Revision overflow → panic! (INV-2); unreachable in practice.

1.9 Failure Analysis

  • Clock regression: detection via debug assert + engine.revision gauge; blast radius = every later cutoff; recovery = none (logic bug), fail fast.
  • Lost input write: symptom = get_input returns stale; detect via fixture; cause = comparing post-write. Forensic: log (old,new,Eq,rev).

1.10 Operational Notes

  • Metrics: engine.revision (gauge), engine.revision_bumps_total, engine.input_noop_total.
  • Tracing: one span per set_input; event on real change only (avoid no-op log spam).
  • Deployment: pure library; no migration. Rollback = revert crate version.

2.6 Pitfalls

  • Frame leak on panic: if execute panics, the frame must still pop (use a guard/Drop), else the next demand records into a stale frame.
  • Recording transitive deps: the top frame must record only direct reads; sub-query reads belong to the sub-query's frame, not the parent's. (Parent records the sub-query node itself, not its inputs.)
  • Conditional dependency surprise: a branch that reads B only when A>0 records B only when taken — correct but means deps are dynamic (the DDG name). Tests must not assume static deps.
  • Re-entrancy hidden by recursion: a query demanding itself will infinite-loop here (no cycle detection until Phase 8); keep fixtures acyclic.

2.7 Performance Concerns

  • record_read is on every read; keep it a SmallVec push (inline ≤8). Avoid heap until a query exceeds 8 direct deps.
  • RefCell borrow on the TLS stack per read — cheap but non-zero; batch where the macro can.
  • Frame push/pop allocates the reads vec; reuse a pool of frames to avoid churn on deep recursion.

2.8 Edge Cases

  • Query with zero reads (pure constant) → empty deps; always re-evaluates the same value.
  • Query reading the same input twice → record once (dedup) or rely on validation idempotence; dedup to keep deps minimal.
  • Deeply nested chain (10^4) → stack depth bounded by recursion; watch native stack (Phase 8 adds explicit-stack option).
  • Panic inside execute → propagate, frame popped, no partial deps leak.

2.9 Failure Analysis

  • Missed edge (back-door read): symptom later = stale read (INV-3); detection now = read-set replay mismatch (INV-5); containment = panic in debug at the back-door; fix = route through Database.
  • Phantom edge: symptom = needless recompute later; detection = replay mismatch; cause = recording a read whose result was discarded; fix = record at point of use.

2.10 Operational Notes

  • Metrics: engine.depset_mismatch_total (debug, must be 0), engine.recompute_total.
  • Tracing: span per demand carries captured dep count; useful to spot pathological fan-in.
  • No persistence implications yet.

3.6 Pitfalls

  • Caching across a revision without validation: with no Phase-4 propagation, a memo from R1 must NOT be returned at R2 as a green hit — guard the fast path strictly on verified_at==current_rev (this is why Phase 4 is mandatory before any set_input of a query's input).

  • changed_at on first run: must be cur, not 0 — else first-ever value looks "never changed" and downstream cutoff misbehaves.

3.7 Performance Concerns

  • Green hit = one hash lookup + a Revision compare + a value.clone(). Clone cost dominates for large values → motivates arena/Arc values (PhaseDeferred("§39")).
  • RwLock read for hits; write only on insert. Single shard contends under Phase 9 — acceptable now.
  • Hashing NodeId(u32) is trivial; hashing full QueryKey only at intern time.

3.8 Edge Cases

  • Demand a query never computed → first-run compute path.
  • Two demands of the same key in one revision → first computes, second green-hits.
  • Value type that is expensive to clone → flagged; consider Arc<V> wrapper.
  • Memo present but verified_at < cur with no propagation yet → must recompute (cannot trust); this is the seam Phase 4/5 fill.

3.9 Failure Analysis

  • Stale green hit: symptom = wrong value after a change; cause = fast path not gated on current_rev; detection = INV-3 assert + oracle; recovery = none (bug). This is the most dangerous Phase-3 regression.
  • Memo bloat: symptom = memory growth; cause = caching everything with no GC (Phase 8); contained by §4 ceiling; mitigation deferred to Phase 8.

  • Tracing: GreenHit{key} events let a host see exactly which queries reused.
  • Compatibility: Memo layout is internal; persistence (Phase 11) versions it.

15. Phase 4 — Push Dirtying: MaybeDirty Frontier

4.1 Objectives

  • On set_input, mark the transitive reverse-closure of dependents MaybeDirty (INV-6), never eagerly Dirty.
  • Build the reverse-edge index (dependents: NodeId → SmallVec<NodeId>) maintained as deps are captured.
  • This is the push half of the hybrid: a cheap marking pass; recomputation stays pull (Phase 5).
  • "Maybe" because cutoff (Phase 6) may prove a marked node unchanged — so marking must not commit to recompute.

4.2 Detailed Implementation Steps

Applies INV-6 (maybe-dirty conservativeness) and the demand-driven dirtying of Adapton (P1, PLDI 2014); the maybe-not-dirty distinction is what preserves P4/P8 cutoff (R2/R3 contrast).

Step File Work
Reverse edges ice-core/ddg.rs on memo insert, for each dep.node push parent into dependents[dep.node]; on memo replace, diff old/new deps and fix the index.
Dirtying pass ice-runtime/propagate.rs set_input change → BFS/DFS over dependents from the changed NodeId; set each reachable memo state=MaybeDirty.
State guard ice-core/state_machine.rs Verified(R) → MaybeDirty transition; clears fast-path eligibility.
Idempotence ice-runtime/propagate.rs a node already MaybeDirty this revision is not re-walked (visited set).
Trace ice-trace/counters.rs engine.maybe_dirty_marked_total per revision.

4.3 Deliverable

After set_input, exactly the transitively-dependent memos are MaybeDirty; unrelated memos stay Verified. No recomputation happens during marking. ice-cli edit workload prints the marked frontier size per edit.

4.4 Acceptance Criteria

  • Marked set == reverse-edge closure of the changed input (INV-6 superset assert; equality on acyclic graphs).
  • Marking is O(affected edges), not O(graph): unrelated subgraphs untouched (counter check).
  • An input change touching a leaf with no dependents marks 0 nodes.
  • Re-mark of an already-dirty node is a no-op (visited set prevents re-walk).

4.5 Conformance Fixtures

Fixture Purpose Expected
conformance/basic/dirty_linear_chain.fixture A→B→C, edit A {B,C} marked
conformance/basic/dirty_diamond.fixture A→{B,C}→D, edit A {B,C,D} marked, each once

4.6 Pitfalls

  • Marking Dirty not MaybeDirty: committing to recompute defeats cutoff (Phase 6); a whitespace edit would then re-flood. Mark Maybe only.
  • Stale reverse edges after recompute: when a query's deps change between revisions, old reverse edges must be removed or a no-longer-dependent node gets spuriously marked (over-recompute). Diff deps on memo replace.
  • Unbounded BFS on a wide fan-out: a very-high-fan-out input (e.g. a global config) marks a huge frontier; this is correct but expensive — durability (Phase 7) is the mitigation, not skipping the mark.
  • Marking across an evicted node: a GC'd memo has no state to mark; its (future) recompute will re-derive freshness — ensure the dirtying pass tolerates absent nodes.

4.7 Performance Concerns

  • Reverse-edge index uses SmallVec inline (most nodes have few dependents); spills to heap for hubs.
  • Dirtying BFS allocates a visited bitset/SmallVec; size to the frontier, not the graph.
  • Maintaining reverse edges on every memo replace adds write cost; amortized small (diff of two short dep lists).
  • False sharing of dependents entries under Phase 9 — pad hot hub entries.

4.8 Edge Cases

  • Edit to an input read by 10^6 queries → frontier == 10^6 (correct; perf concern → durability).
  • Cyclic reverse edges (illegal graph) → visited set prevents infinite BFS even before Phase 8 cycle detection.
  • Input set to equal value → no change → no dirtying pass at all (input-level cutoff, Phase 1).
  • A node both an input dependent and itself an input — not possible; inputs have no deps.

4.9 Failure Analysis

  • Under-marking: symptom = stale read (INV-3) after edit; cause = a missing reverse edge (deps not captured / not indexed); detection = INV-6 closure assert + oracle; blast radius = every consumer of the unmarked node; recovery = none (bug).
  • Over-marking: symptom = reuse-ratio drop, latency; cause = stale reverse edges; detection = reuse-ratio regression gate; recovery = rebuild reverse index from forward deps (debug repair tool).

4.10 Operational Notes

  • Metrics: engine.maybe_dirty_marked_total, engine.dirty_frontier_size (gauge per edit), engine.reverse_edges.
  • Tracing: a span per set_input carries frontier size — the first signal of an over-broad dependency.
  • Runbook over-recompute.md: start from frontier size vs expected.

16. Phase 5 — Pull Validation: Red-Green Deep Verify

5.1 Objectives

  • Implement demand-time red-green validation: on demand of a MaybeDirty node, recursively validate deps; recompute only if a dep actually changed (INV-3, P3, P5).
  • Core comparison: dep.changed_at > node.verified_at ⇒ dep changed since last verify ⇒ recompute.
  • Backdate when all deps unchanged (verified_at=cur, value reused) — sets up deep cutoff (Phase 6).
  • This phase makes recompute cost = O(transitively-affected) (§4 headline).

5.2 Detailed Implementation Steps

Applies P5 (minimality), P3 (pull), INV-3 (no stale read), and P8 (backdating); the red-green maybe_changed_after scheme is salsa's (R1) and rustc's (R7), with cost bounds per Acar (P2).

Step File Work
State machine ice-core/state_machine.rs encode the §8 transition table: MaybeDirty + all deps unchanged → Verified(cur) (backdate); + some dep changed → Computing; + dep MaybeDirty → Verifying (recurse first).
deep_verify ice-runtime/evaluator.rs maybe_changed_after(node, since): for each dep, demand it (recurse), compare dep.changed_at to node.verified_at; short-circuit on first changed dep.
Recompute tail ice-runtime/evaluator.rs on a real change, push frame, run execute, capture fresh deps, set verified_at=cur, changed_at=cur (cutoff comparison lands in Phase 6).
Edge versioning ice-core/ddg.rs store changed_at_when_read per dep so validation can reason precisely.
Trace ice-trace/events.rs Backdate{key}, Recompute{key,reason:DepChanged(node)}.

5.3 Deliverable

A correct incremental engine for the no-cutoff case: after an edit, demanding a root recomputes exactly the affected chain and backdates the rest. Matches the from-scratch oracle on every fixture in basic/. ice-cli edit shows recompute count == affected count.

5.4 Acceptance Criteria

  • After a single-input edit, recompute_total delta == size of the transitively-affected set (no more — INV-5/P5; cutoff not yet in play so no fewer either).
  • Unchanged dependents are validated (backdated), not recomputed; validation ≤ 200 ns/node (§4).
  • Differential test vs oracle passes for all basic/ and random acyclic graphs (proptest, INV-1).
  • Re-demand after validation is a green hit (verified_at==cur).

5.5 Conformance Fixtures

Fixture Purpose Expected

5.6 Pitfalls

  • Comparing changed_at to the wrong baseline: must compare dep's changed_at against this node's verified_at (when we last saw it), not against current_rev. Using current_rev recomputes everything every revision.
  • Forgetting to recurse into MaybeDirty deps: a dep that is itself MaybeDirty must be validated first (Verifying state) before its changed_at is trusted — else you read a stale changed_at and skip a real recompute (stale read).
  • Not backdating: if you leave a validated-unchanged node MaybeDirty, every subsequent demand re-walks it — O(graph) per demand. Backdate to verified_at=cur.
  • Re-entrancy during validation: validating deps recurses through the same demand path; without Phase 8 cycle detection a malformed graph loops — keep fixtures acyclic until Phase 8.
  • Short-circuit ordering: stop at the first changed dep, but you must still validate (not skip) remaining deps the recompute will read — handled because recompute re-reads them through the stack.

5.7 Performance Concerns

  • Validation is a bottom-up DAG walk; depth-bounded recursion. Watch native stack on deep chains (Phase 8 explicit-stack option).
  • Backdating writes only verified_at/state — cheap, under the shard lock briefly.
  • Short-circuit on first changed dep avoids validating the rest only for the decision; the recompute then re-reads them (necessary). Net: each affected node validated once.
  • Memoize the maybe_changed_after result within a single demand to avoid re-validating a shared dep twice (diamond) — cache by (node, since) for the demand's duration.

5.8 Edge Cases

  • Diamond where both arms unchanged → shared dep validated once, both arms backdated.
  • Edit then edit-back-to-original across two revisions → second edit changes value back; chain recomputes (no cutoff yet); value correct.
  • Dep changed but node's recompute yields a different structure of deps → new deps captured; reverse edges updated (Phase 4 diff).
  • Demand of a never-marked node at a new revision where nothing it depends on changed → backdate (it was Verified at old rev, now validate cheaply).

5.9 Failure Analysis

  • Stale read (INV-3): symptom = value lags an edit; root cause = skipped recompute (bad changed_at comparison or un-recursed MaybeDirty dep); detection = oracle divergence + stale_return_total; blast radius = all downstream; recovery = none (bug); forensic = dump (node.verified_at, each dep.changed_at) at the suspect demand.
  • Re-flood (over-recompute): symptom = reuse ratio ≈ 0 after any edit; cause = comparing to current_rev or not backdating; detection = reuse-ratio gate; recovery = fix comparison/backdate.

5.10 Operational Notes

  • Metrics: engine.backdate_total, engine.recompute_total{reason}, engine.validate_nodes_total, engine.reuse_ratio.
  • Tracing: Recompute{reason:DepChanged(node)} names the exact dep that triggered work — the key debugging signal for "why did X recompute".
  • Runbook stale-read.md keys off stale_return_total>0.

17. Phase 6 — Early Cutoff (the Minimality Engine)

6.1 Objectives

  • Add early cutoff: after recompute, if new_value Eq old_value, keep changed_at (bump only verified_at), so dependents comparing changed_at see "unchanged" and stop (INV-4, P4/P8).
  • Combine with Phase 5 backdating to make cutoff transitive/deep: a firewall node halts an entire downstream cascade.
  • This is the headline differentiator vs naive invalidation: a format-only / value-preserving edit costs O(firewall), not O(downstream).

6.2 Detailed Implementation Steps

Applies P4 (early cutoff by value equality), P8 (backdating makes cutoff deep), and INV-4 (cutoff soundness); cutoff design follows Jane Street Incremental (R3) and salsa (R1).

Step File Work
Cutoff rule ice-core/cutoff.rs recompute tail: if new Eq old { changed_at unchanged } else { changed_at = cur }; verified_at = cur either way.
Deep cutoff ice-runtime/evaluator.rs dependents already use dep.changed_at vs verified_at; backdated unchanged value ⇒ dependent backdates too.
Eq bound ice-macros/query.rs enforce Value: Eq at the trait (compile error otherwise).
Trace ice-trace/events.rs CutoffFired{key} when new Eq old after a recompute that was triggered by a changed dep.
Counters ice-trace/counters.rs engine.cutoff_fired_total, engine.changed_at_advanced_total.

6.3 Deliverable

The full salsa-style engine: an edit that does not change a downstream value stops propagation at the firewall. The cutoff/ example (e.g. B=min(A,10), edit A above 10) recomputes B once and reuses everything below. ice-cli shows downstream recompute count == 0 past the firewall.

6.4 Acceptance Criteria

  • Whitespace/no-effect edit: 0 downstream recomputes past the firewall (§4/§5 acceptance).
  • changed_at advances iff value !Eq old (INV-4 debug assert).
  • Cutoff-soundness differential test: incremental == oracle across random edits including value-preserving ones (INV-1).
  • IDE-keystroke synthetic workload: reuse ratio ≥ 0.95 after a 1-token edit (§4 target, regression-gated).

6.6 Pitfalls

  • Advancing changed_at on cutoff: the single most damaging cutoff bug — defeats the firewall; every revision re-floods. Assert INV-4.
  • Equality lie: a Value whose Eq says "equal" for genuinely different values causes stale reuse (silent wrong results). Cannot be detected by the engine generally; caught by the oracle differential test and discouraged by documenting the Eq contract.
  • Expensive Eq: if equality costs as much as recompute, cutoff saves nothing downstream but pays full cost at the firewall. Document: cutoff is a win only when Eq ≪ recompute. Offer a structural/hash-based fast-path comparison guidance.
  • Cutoff vs side effects: a query that "looks pure but logs" loses its log on cutoff (P2) — reinforces purity.
  • Comparing against an evicted old value: if the old memo was GC'd (Phase 8), there is no old to compare — treat as changed (recompute, set changed_at=cur); correct but loses one cutoff opportunity.

6.7 Performance Concerns

  • The Eq comparison is the new hot cost at every firewall recompute; for large values prefer cheap discriminants (length, hash, version) before deep compare.
  • Cutoff reduces total work dramatically on localized edits — the whole point — but adds one Eq per recompute. Net win when downstream is large.
  • Backdate writes propagate up cheaply (timestamp-only).
  • Consider an optional content-hash in Memo to make Eq an O(1) hash compare for big values (PhaseDeferred("§39") ties in).

6.8 Edge Cases

  • Value oscillates A→B→A across three revisions: middle revision changes changed_at; third revision recompute yields original, new Eq old(of rev 2's value)? — compare against the immediately prior memo value, not the original; cutoff fires only if equal to last memo.
  • Float Eq with NaN (never equal) → cutoff never fires for NaN-bearing values (correct per Eq semantics; document).
  • Query returning a freshly-allocated but structurally-equal value (e.g. new Vec same contents) → Eq true → cutoff fires (correct; identity is irrelevant).
  • First run (no old value) → never a cutoff; changed_at=cur.

6.9 Failure Analysis

  • Silent stale via equality lie: symptom = host sees old derived value after a real change; cause = lying Eq; detection = oracle differential (INV-1/INV-4); blast radius = every consumer of the firewall; recovery = fix the type's Eq; forensic = cutoff_eq_lie_detect-style shrink.
  • Re-flood via changed_at bug: symptom = reuse ratio collapses on value-preserving edits; detection = cutoff_fired_total near 0 when expected high; recovery = fix INV-4 path.

6.10 Operational Notes

  • Metrics: engine.cutoff_fired_total, engine.changed_at_advanced_total, engine.reuse_ratio (now meaningfully high on real workloads).
  • Tracing: CutoffFired{key} is the positive signal operators look for; absence on a known no-op edit is the bug signature.
  • Compatibility: changing a Value's Eq semantics is a behavioral change (may alter cutoff) — note in CHANGELOG even though the type is host-owned.

18. Phase 7 — Durability Tiers + Validation Short-Circuit

7.1 Objectives

  • Add durability classes (Low/Medium/High) and the per-durability clock map (by_durability[3]).
  • Validation short-circuit: if nothing of durability ≥ the memo's durability changed since verified_at, skip dep validation entirely (P9/INV-12).
  • Durability is strictly an optimization — turning it off must not change any result (INV-12), only performance.
  • Target: stdlib/config inputs marked High make large dependent subgraphs near-free to validate.

7.2 Detailed Implementation Steps

Applies P9 (durability is an optimization, never a correctness lever) and INV-12 (durability never affects a value); the durability/clock-map shortcut is salsa's (R1) and the rustc query system's (R7).

Step File Work
Clock map ice-core/revision.rs by_durability[d] = last revision an input of durability d (or lower) changed; updated in bump(d).
Memo durability ice-runtime/evaluator.rs memo durability = min over deps' durabilities (a memo is only as durable as its least-durable input).
Short-circuit ice-runtime/durability_gate.rs before deep-verify: if clock.by_durability[memo.durability] <= memo.verified_at ⇒ nothing relevant changed ⇒ backdate immediately, skip dep walk.
Declared durability ice-macros/input.rs DEFAULT_DURABILITY; set_input_with_durability override.
Trace ice-trace/counters.rs engine.durability_shortcut_hits_total.

7.3 Deliverable

Validation that skips entire subgraphs rooted in durable inputs. Editing a Low-durability input does not force re-validation of High-durability-only subgraphs. ice-cli shows shortcut-hit count rising with durable workloads.

7.4 Acceptance Criteria

  • Editing a Low input → memos whose deps are all High are validated via shortcut (0 dep walks), counter increments.
  • INV-12 force-Low differential test: results identical with all durabilities forced Low vs declared (only perf differs).
  • Warm validation of a High-only subgraph after a Low edit ≤ O(roots), not O(subgraph).
  • Mis-declared durability (volatile marked High) is caught by the force-Low oracle (negative test).

7.5 Conformance Fixtures

Fixture Purpose Expected

conformance/durability/durability_lie.fixture volatile input marked High force-Low oracle diverges (negative)

7.6 Pitfalls

  • Durability deciding a value: the shortcut may only skip validation, never alter a result. If a "durable" input actually changed, the clock map must reflect it (its bump raised by_durability[Low..=its level]) so the shortcut is NOT taken. Bug here = silent stale.
  • Wrong min rule: taking max instead of min over dep durabilities marks a memo more durable than its weakest input → stale reads. It is min.
  • Clock map not covering lower tiers: a Low change must raise the relevant entries so a High memo with a Low dep does NOT shortcut. Define by_durability[d] as "last change at durability ≤ d" carefully.
  • Over-trusting host durability: hosts will mis-declare; the engine must remain correct if they do (it does, because a real change still bumps the clock) — durability only loses performance when mis-declared low, and risks staleness only if the host both mis-declares high AND the clock map omits the change (the bug to avoid).

7.7 Performance Concerns

  • Shortcut is a single Revision compare replacing a whole subgraph walk — the largest validation win for stable inputs (stdlib).
  • The by_durability array is 3 atomics; updated on every real set_input. Negligible.
  • Min-durability computation is O(deps) at recompute time — already paid.

7.8 Edge Cases

  • All inputs Low → shortcut never fires; behaves exactly like Phase 5/6.
  • A High input that genuinely changes → its bump(High) raises by_durability[High] and (by definition) the lower entries too, so all dependents re-validate.
  • New memo with no deps yet (first run) → durability defaults to the most durable (High)? No — a constant query with zero inputs is trivially reusable; assign High only if it truly reads nothing; document the zero-dep case.
  • Durability downgraded at runtime (host re-declares an input Low) → treat as a change event to be safe.

7.9 Failure Analysis

  • Stale via bad shortcut: symptom = stale read after editing a Low input that a "durable" memo actually depended on; cause = wrong min rule or clock-map gap; detection = INV-12 force-Low oracle + stale_return_total; recovery = none (bug); forensic = compare declared vs effective durability per memo.
  • Lost performance: symptom = no shortcut hits though inputs are stable; cause = everything defaulted Low; detection = durability_shortcut_hits_total ≈ 0; recovery = host declares durable inputs.

7.10 Operational Notes

  • Metrics: engine.durability_shortcut_hits_total, engine.by_durability{tier} gauges.
  • Tracing: a Backdate with reason DurabilityShortcut distinguishes shortcut backdates from full-validate backdates.
  • Compatibility: durability is advisory metadata; persistence stores declared durability (Phase 11) but always re-validates on load (INV-3), so a stale durability cannot cause a load-time stale read.

19. Phase 8 — Cycle Detection + Optional Fixpoint Recovery

8.1 Objectives

  • Detect runtime cycles in the query graph: a demand re-entering a key already Computing/on-stack ⇒ typed CycleError, never a hang/stack-overflow (INV-7, P12).
  • Clean unwind: no partial/torn memo cached for any cycle participant.
  • Optional registered fixpoint recovery: a query may declare a recovery function to iterate to a fixed point instead of erroring.
  • Replace native recursion with an explicit demand stack to bound stack depth on deep chains.

8.2 Detailed Implementation Steps

Applies P12 (cycles are errors, not hangs) and INV-7 (cycle safety); the on-stack re-entry detection mirrors salsa's cycle handling (R1), and optional fixpoint recovery follows the attribute-grammar fixpoint tradition (P9).

Step File Work
On-stack set ice-core/cycle.rs per-evaluation HashSet<NodeId> (or the Frame.on_stack flag) of keys currently computing on this thread.
Detection ice-runtime/evaluator.rs on demand entry, if node already on-stack ⇒ build CycleError{cycle:Vec<QueryKey>} from the stack slice.
Unwind ice-runtime/evaluator.rs propagate CycleError up; each frame for a participant drops without caching.
Explicit stack ice-runtime/evaluator.rs optional iterative driver (work stack) to avoid native overflow on 10^5-deep chains.
Recovery ice-core/cycle.rs Query::CYCLE_RECOVERY: Option<fn(&[QueryKey])->Value>; iterate until values stabilize (Eq fixpoint) or a max-iteration cap.
Trace ice-trace/events.rs CycleDetected{cycle}.

8.3 Deliverable

A cyclic query graph fails fast with a CycleError naming the participating keys (or converges via registered recovery), with no hang and no corrupted memo. cycle_inject fuzz target confirms no infinite loop under random cycle injection.

8.4 Acceptance Criteria

  • Direct self-cycle and indirect 2..N-node cycles → CycleError{cycle} with the correct participant list (INV-7).
  • No memo for a cycle participant is ever observable after the error (assert absence).
  • Fixpoint recovery: a declared-recovery cycle converges within the iteration cap and yields the oracle's fixpoint value, or returns CycleError if non-convergent at the cap.
  • Deep acyclic chain (10^5) evaluates without native stack overflow (explicit-stack path).
  • cycle_inject fuzz target: 0 hangs, 0 panics, every cycle ⇒ typed error.

8.5 Conformance Fixtures

Fixture Purpose Expected
conformance/cycles/self_cycle.fixture Q=f(Q) CycleError{cycle:[Q]}; nothing cached
conformance/cycles/indirect_cycle.fixture X↔Y CycleError{cycle:[X,Y]}
conformance/cycles/cycle_then_break.fixture cycle, then edit to break it after break, demand succeeds (no stale cycle state)
conformance/cycles/fixpoint_recovery.fixture recoverable monotone cycle converges to fixpoint == oracle
conformance/cycles/fixpoint_diverge.fixture non-convergent cycle CycleError at iteration cap
conformance/cycles/deep_chain_no_overflow.fixture 10^5-deep acyclic succeeds via explicit stack

8.6 Pitfalls

  • Caching a partial cycle result: writing any memo for an in-progress participant lets a later demand read a half-formed value — a correctness disaster. Drop all participant frames on unwind.
  • Detecting the cycle too late: under the Phase-9 per-key compute lock, a cycle that re-acquires its own key deadlocks instead of erroring. Detection must be the on-stack check before lock acquisition (a thread holds its own keys' "computing" markers re-entrantly).
  • Recovery non-termination: a fixpoint that never stabilizes loops forever — always bound by a max-iteration cap and fall back to CycleError.
  • Cycle through GC'd node: an evicted participant re-enters via recompute; the on-stack set is keyed by NodeId, so detection still fires regardless of memo presence.
  • Cross-thread "cycle": two threads each demanding the other's in-progress key is a deadlock, not a graph cycle. Distinguish: graph cycles are single-thread re-entry; cross-thread waits are resolved by lock ordering (Phase 10), not CycleError.

8.7 Performance Concerns

  • On-stack membership test on every demand entry: a HashSet<NodeId> or a per-Frame flag; flag-on-frame is O(1) and avoids a set. Prefer the flag.
  • Explicit work-stack adds a small per-frame heap cost vs native recursion but removes the stack-overflow ceiling — worthwhile for unbounded host graphs.
  • Fixpoint iteration multiplies recompute cost by iteration count; cap small and document.

8.8 Edge Cases

  • Zero-length "cycle" (a query that demands a key then the same key after it completes) → NOT a cycle (completed memo); only on-stack re-entry counts.
  • Cycle that appears only at certain inputs (dynamic dep) → detected exactly when the cyclic branch executes (trace-based, like all deps).
  • Recovery function itself reads queries → those reads are captured normally; recovery must also be pure.
  • Cycle detected mid-validation (not mid-compute) → same handling; validation recurses through demand.

8.9 Failure Analysis

  • Hang/overflow (detection failure): symptom = stuck thread or stack overflow; cause = missing on-stack check or check after lock; detection = cycle_inject fuzz + a watchdog on demand depth; blast radius = one host thread (or deadlock under Phase 9); recovery = none (bug) — fix detection.
  • Spurious CycleError: symptom = error on an acyclic graph; cause = NodeId reuse without generation check (INV-11) making two distinct keys collide on-stack; detection = cycle_detected_total spikes on acyclic fixtures; recovery = fix interning generation tag.

8.10 Operational Notes

  • Metrics: engine.cycle_detected_total, engine.fixpoint_iterations (histogram), engine.max_demand_depth (gauge).
  • Tracing: CycleDetected{cycle} logs the full path; runbook cycle-error.md renders it as a DOT subgraph for the host author.
  • Compatibility: CycleError is part of the public error enum (#[non_exhaustive]); recovery registration is additive API.

20. Phase 9 — Garbage Collection: LRU + Reachability Sweep

9.1 Objectives

  • Bound memo memory under an unbounded query-key space (P11): evict rather than OOM.
  • Combine LRU (least-recently-demanded first) with a reachability sweep (memo reachable only from already-evicted/undemanded memos is collectible).
  • Eviction is always correctness-safe: a missing memo is recomputed identically on next demand (INV-10/P14).
  • Honor a configured soft memory ceiling (default 2 GiB, §4); hard cap aborts with OutOfMemo.

9.2 Detailed Implementation Steps

Applies P11 (bounded memo growth) and P14/INV-10 (the engine is a cache; eviction is always safe); LRU + reachability sweep is informed by Adapton's articulation-point reasoning (R2) and standard cache-eviction practice.

Step File Work
LRU index ice-runtime/memo_cache.rs LruIndex: intrusive recency list keyed by NodeId; touched on every green hit / recompute.
Sweep ice-runtime/gc.rs sweep_gc(target_bytes): walk LRU coldest-first; evict if not on any compute stack and not a current GC root (recently demanded).
Reachability ice-core/ddg.rs optional reachable-set computation from "pinned" roots (host-registered durable queries) to protect hot subgraphs.
Byte accounting ice-runtime/memo_cache.rs per-memo size estimate (header + deps + value size hook); running total vs ceiling.
Recompute-on-miss ice-runtime/evaluator.rs demand of an evicted key = first-run compute (with RecomputeReason::EvictedMiss).
Trace ice-trace/events.rs Evicted{key,bytes}; Recompute{reason:EvictedMiss}.

9.3 Deliverable

A Database that stays under a configured memory ceiling by evicting cold memos, and recomputes them transparently on demand with identical results. ice-cli --mem-cap flag demonstrates bounded steady-state memory under a churning workload.

9.4 Acceptance Criteria

  • Under a 2 GiB cap with a workload that would otherwise use 8 GiB, steady-state stays ≤ cap (gauge check).
  • INV-10 differential test: GC forced after every edit vs no GC → identical results.
  • "Evict-everything-each-revision" stress mode → still matches oracle (reveals any hidden side effect / P2 breach).
  • Incremental sweep pause ≤ 5 ms at 10^6 memos (§4); never a stop-the-world beyond budget.
  • Never evict a memo on an active compute stack (assert).

9.5 Conformance Fixtures

Fixture Purpose Expected
conformance/gc/evict_then_recompute.fixture demand, evict, demand second demand recomputes; value identical
conformance/gc/evict_under_cap.fixture grow past cap coldest memos evicted; cap respected
conformance/gc/evict_all_stress.fixture evict-everything each revision results == oracle
conformance/gc/no_evict_on_stack.fixture GC during a deep eval on-stack memos survive
conformance/gc/evict_then_cutoff.fixture evict old value, then recompute cutoff cannot fire (no old value) → recompute, changed_at=cur

9.6 Pitfalls

  • Use-after-evict: evicting a memo currently on a compute stack (being read by an in-progress parent) corrupts the evaluation. Pin on-stack nodes; never evict them.
  • Evicting a pinned/hot root mid-cutoff opportunity: evicting an old value loses the chance to cut off on next recompute (must recompute + treat as changed). Correct but a perf loss — bias LRU to keep firewall nodes.
  • Reverse-edge dangling after evict: evicting a node must also drop its reverse edges (and update dependents' forward deps lazily, or tolerate absent on validate). A stale reverse edge causes spurious dirtying (Phase 4 pitfall).
  • Byte-accounting drift: if size estimates diverge from reality, the cap is wrong — periodically reconcile or use an allocator hook.
  • GC thrash: evicting then immediately recomputing the same hot memo wastes CPU. Keep a small protected working set (recency window) below the cap.

9.7 Performance Concerns

  • LRU touch on every hit adds a list splice; use an intrusive list / clock-approximation (second-chance) to avoid lock contention under Phase 10.
  • Sweep is incremental/amortized (bounded work per call), not stop-the-world, to honor the 5 ms budget.
  • Reachability sweep is O(reachable edges); run rarely (only when LRU alone cannot meet the cap).
  • Recompute-on-miss adds latency to the next demand of an evicted key — acceptable since evicted == cold.

9.8 Edge Cases

  • Cap set below the working-set size → constant thrash; OutOfMemo only on the hard cap, else degrade with high recompute rate (log a warning).
  • Evict a node, then its dependent is demanded → dependent re-reads, triggering recompute of the evicted node (INV-10).
  • Evict a node whose NodeId is then recycled (INV-11) → generation tag prevents an old edge from pointing at the new occupant.
  • Concurrent demand during sweep (Phase 10) → sweep skips nodes a thread has pinned; uses per-shard locks.

9.9 Failure Analysis

  • Use-after-evict crash/garbage: symptom = panic or wrong value during eval after a sweep; cause = evicting an on-stack node; detection = no_evict_on_stack fixture + assert; blast radius = the in-flight demand; recovery = none (bug); forensic = log evicted set vs active stacks.
  • OOM despite GC: symptom = host OOM; cause = working set > cap, or accounting drift; detection = memo_bytes gauge vs cap, evicted_total flatlines while bytes climb; recovery = raise cap or shrink working set; long-term = arena value storage (PhaseDeferred("§39")).
  • Stale via dangling reverse edge: symptom = spurious dirtying / over-recompute; detection = reuse-ratio regression; recovery = reverse-index rebuild tool.

9.10 Operational Notes

  • Metrics: engine.evicted_total, engine.evict_then_recompute_total, engine.memo_bytes, engine.memo_count, engine.gc_pause_seconds (histogram).
  • Tracing: Evicted{key,bytes} + Recompute{EvictedMiss} let operators see GC churn.
  • Deferred: speculative/eager pre-computation of likely-demanded queries — PhaseDeferred("§39").
  • Runbook memory-growth.md: start from memo_bytes trend and evicted_total rate.

21. Phase 10 — Concurrency: Parallel Query Execution

10.1 Objectives

  • Evaluate independent demanded queries in parallel on a rayon pool, sharing the memo cache safely.
  • Single-writer revision model: mutations (set_input) are serialized; reads/recomputes run concurrently against a pinned snapshot (Snapshot).
  • Per-key compute lock ⇒ at most one thread recomputes a given key (INV-8/P15); others join.
  • Deadlock-free ordering; cooperative cancellation (CancellationToken) at demand boundaries.

10.2 Detailed Implementation Steps

Applies P15/INV-8 (single concurrent recompute per key), P13/INV-3 (no torn read), and the single-writer revision-isolation idea from Concurrent Revisions (P8); sharding + per-key locking follows The Art of Multiprocessor Programming and salsa's Sync runtime (R1).

Step File Work
Sharding ice-runtime/memo_cache.rs shard count = next_pow2(2×cores) (ADR-04); per-shard RwLock; false-sharing pad shard headers.
Per-key lock ice-runtime/parallel.rs Computing state acts as a compute lock; a second thread on the same key waits on a condvar/parking and then reads the memo (INV-8).
Snapshot ice-runtime/database.rs snapshot() pins current_rev; reads are lock-free wrt the clock; mutations need exclusive access (single writer).
Executor ice-runtime/parallel.rs rayon join/scope for fan-out of independent demands; the host opts in via a parallel demand API.
Cancellation ice-runtime/cancel.rs CancellationToken checked between sub-query demands; cancelled demand returns early without caching a partial result.
Lock ordering ice-runtime/parallel.rs acquire shard locks in NodeId order where multiple are needed; document the global order (no clock-then-shard inversions).

10.3 Deliverable

A thread-safe Database where a host can demand many independent queries concurrently with near-linear speedup, cancel in-flight work, and never observe a torn read or a duplicated recompute. ice-bench parallel shows ≥ 0.7 linear efficiency to 16 cores.

10.4 Acceptance Criteria

  • ≥ 0.7 linear scaling efficiency to 16 cores on an independent-query workload (§4).
  • duplicate_compute_total == 0 under concurrent demand of the same key (INV-8).
  • No data races under loom/miri model checking of the cache + compute-lock paths.
  • Cancellation observed within one demand boundary (no preemption mid-execute).
  • Differential test under concurrency: results identical to single-threaded oracle (INV-1).

10.5 Conformance Fixtures

Fixture Purpose Expected
conformance/concurrency/parallel_independent.fixture many disjoint queries correct values; scaling recorded
conformance/concurrency/same_key_race.fixture N threads demand one cold key computed once (INV-8)
conformance/concurrency/cancel_inflight.fixture cancel a long demand returns promptly; no partial memo
conformance/concurrency/reader_writer.fixture reads during a set_input readers see a consistent revision (no torn read)
conformance/concurrency/loom_compute_lock.fixture loom schedules no race, single compute

10.6 Pitfalls

  • Recompute-during-mutation: allowing a set_input concurrently with recompute can yield a torn read (old value, new clock — INV-3). Enforce single-writer: mutations take exclusive access; concurrent demands operate on a pinned Snapshot.
  • Compute-lock deadlock vs cycle: a re-entrant same-thread demand under a per-key lock would deadlock — must hit the on-stack cycle check (Phase 8) before contending the lock.
  • Lock-order inversion: acquiring two shard locks in inconsistent order across threads deadlocks; enforce NodeId-ascending acquisition.
  • TLS dep stack across rayon tasks: each rayon worker has its own thread-local stack — correct, but a query body that spawns its own parallelism would split its read set across threads (forbidden; a query body is single-threaded).
  • Cancellation leaking a frame: a cancelled demand must pop its frame and release any compute lock (use guards), else the key stays Computing forever (livelock).
  • False sharing on hot counters: reuse_ratio/recompute_total atomics on one cache line throttle scaling — shard or pad counters.

10.7 Performance Concerns

  • Shard contention is the scaling ceiling; measure with parking_lot lock stats. Increase shards for high core counts.
  • Clock reads are Acquire atomic loads — cheap and concurrent. Mutations are rare and serialized.
  • Compute-lock wait should park (not spin) for long recomputes; spin briefly for short ones (adaptive).
  • Counter updates batched per demand to reduce atomic traffic.

10.8 Edge Cases

  • All threads demand the same cold key → one computes, the rest wait then green-hit (INV-8).
  • A set_input arrives while a parallel demand is mid-flight → demand finishes against its pinned snapshot; the new revision is visible only to subsequent demands.
  • Cancellation of a demand whose result another thread is waiting on → the waiter must re-drive the compute (the cancelled thread's abort must not strand the key).
  • Deeply recursive demand across many worker threads → bounded by explicit stack (Phase 8) per worker.

10.9 Failure Analysis

  • Torn read under concurrency: symptom = downstream cutoff misbehaves intermittently; cause = read during mutation; detection = loom + INV-3 assert + oracle under concurrency; blast radius = nondeterministic wrong results; recovery = none (bug); forensic = record (rev seen, value source) per read.
  • Stranded Computing key: symptom = a key never completes, waiters hang; cause = cancellation/panic leaked the compute lock; detection = compute_lock_wait_total climbs without resolution; recovery = guard-based lock release; watchdog logs the owning thread.
  • Scaling collapse: symptom = efficiency < 0.7; cause = shard contention / counter false sharing; detection = parallel bench regression; recovery = more shards / padded counters.

10.10 Operational Notes

  • Metrics: engine.compute_lock_wait_total, engine.duplicate_compute_total (0), engine.parallel_efficiency (bench), engine.cancellations_total.
  • Tracing: per-demand spans carry thread id + wait time; correlate with host spans.
  • Deployment: the parallel API is opt-in; single-threaded hosts pay no concurrency cost. Rollback = disable the parallel feature flag.

22. Phase 11 — Durable Memo Persistence Across Restarts

11.1 Objectives

  • Persist inputs + memos to disk and reload on restart, validating against current_rev so no stale value is served (INV-3).
  • Format-versioned, provider-hashed: a memo whose query logic changed (different provider hash) is rejected and recomputed.
  • Cross-process / cross-machine memo reuse is explicitly out of scope: PhaseDeferred("§39").

11.2 Detailed Implementation Steps

Applies INV-3 (revalidate on load, never serve a stale loaded value), INV-11 (NodeIds never persisted, remapped on load via key stability per Nominal Adapton, P7), and ADR-12 (serde/bincode); on-disk red-green caching follows the rustc query system (R7).

Step File Work
Serialize ice-runtime/persist.rs serde+bincode (ADR-12); persist inputs (key-bytes, value, changed_at, durability) and memos (key-bytes, value, verified_at, changed_at, durability, deps-by-key).
Provider hash ice-macros/query.rs embed a per-query content hash (of the query's identity/version) into the persisted record; mismatch ⇒ reject.

11.3 Deliverable

A Database::save(path) / load(path) round-trip: an IDE restart reloads a warm memo set, revalidates against the new revision, and avoids a full cold rebuild. Provider-changed queries are recomputed; the result equals a from-scratch build (INV-1).

11.4 Acceptance Criteria

  • Round-trip: save then load then demand → identical values to pre-save (INV-1).
  • Provider-hash mismatch (query logic changed) → that memo rejected and recomputed; no stale value (INV-3).
  • Format-version mismatch → clean PersistError, fall back to cold build (never a crash or stale read).
  • NodeIds never persisted; reload remaps from key-bytes (INV-11).
  • Load of a 10^6-memo store + revalidate is materially faster than a cold rebuild (recorded ratio).

11.5 Conformance Fixtures

Fixture Purpose Expected

conformance/persist/provider_changed.fixture bump a provider hash that memo recomputed; others reused
conformance/persist/format_mismatch.fixture load older/garbage format PersistError; cold fallback
conformance/persist/revalidate_on_load.fixture inputs changed before reload demand revalidates, no stale

11.6 Pitfalls

  • Persisting NodeIds: they are process-local and recyclable; persisting them corrupts edges on reload. Persist by stable key bytes only.
  • Trusting loaded verified_at against a new clock: the loaded clock and the live clock must be reconciled; safest is to reset state=Unverified and revalidate everything on first demand (INV-3) — never serve a loaded value without revalidation.
  • Stale provider: if query logic changed but the provider hash did not, a loaded memo is stale — the provider hash must capture the query's semantic version; CI checks hashes change when query bodies change.
  • Partial write / torn file: a crash mid-save leaves a corrupt store; write to a temp file + atomic rename; verify a checksum on load.
  • Value Serialize not required without the feature: persistence requires Value: Serialize; the persist feature must gate the bound so non-persisting hosts are unaffected.

11.7 Performance Concerns

  • bincode is compact + fast; serialization overhead dominated by value size — large values cost on save/load.
  • Reverse-edge rebuild on load is O(edges); amortized vs the cold rebuild it replaces.
  • Revalidation on first demand spreads cost across the post-restart warm-up (pull model) rather than a load-time spike.
  • Consider compression (PhaseDeferred("§39")) for large stores.

11.8 Edge Cases

  • Empty store / first run → cold build, then first save.
  • Store from a different engine version → engine_version mismatch ⇒ reject (cold fallback).
  • Input present in store but its query removed from the binary → orphan memo; ignored/garbage-collected on load.
  • Disk full on save → PersistError; in-memory state intact (save is non-destructive).
  • Clock skew across restarts → revisions are logical (per-process); the loaded clock seeds the new clock; never derived from wall time.

11.9 Failure Analysis

  • Stale read after reload: symptom = wrong value post-restart; cause = serving loaded value without revalidation or a stale provider hash; detection = roundtrip differential (INV-1) + stale_return_total; blast radius = all reloaded consumers; recovery = invalidate the store, cold rebuild; forensic = compare provider hashes.
  • Corrupt store crash: symptom = panic on load; cause = torn write / format drift; detection = checksum + format header; recovery = discard store, cold build; mitigation = atomic temp-file rename.

11.10 Operational Notes

  • Metrics: engine.persist_loaded_total, engine.persist_rejected_total, engine.persist_bytes, engine.load_revalidate_total.
  • Tracing: a load summary span; per-rejection event names the provider mismatch.
  • Deferred: cross-process / cross-machine memo reuse — PhaseDeferred("§39") (requires content-addressed keys + a shared store; out of scope).
  • Compatibility: format is format_version-gated; a bump triggers cold fallback, never a stale load (§29).

24. Phase 13 — Differential / Streaming Batched Change-Sets (Deferred Extension)

13.1 Objectives

  • Extend inputs from scalar cells to collections with incremental change-sets (insert/remove/update diffs), à la differential dataflow (P6), enabling incremental view maintenance over relations (links 366).
  • Batched mutation: apply many input deltas in one revision bump, then propagate once.
  • Marked PhaseDeferred("§39") — built on the core, not part of Phase 0.

13.2 Detailed Implementation Steps

Applies INV-1 (extended to collections) and the differential model of Differential Dataflow (P6, CIDR 2013) and the incremental λ-calculus / theory of changes (P5, OOPSLA 2014); operators are studied from timely/differential dataflow (R4).

Step File Work
Collection input ice-runtime/input_store.rs (ext) set_input_delta(key, ChangeSet); a change-set is {inserts, removes, updates} over keyed elements.
Diff value ice-core/memo.rs (ext) derived queries over collections may emit diffs, not whole values, when the host opts in.
Batched bump ice-runtime/propagate.rs (ext) accumulate deltas, single revision bump, single dirtying pass over the union of affected keys.
Incremental operators new ice-runtime/collections.rs map/filter/join/reduce that consume + produce change-sets incrementally.
Trace ice-trace/events.rs (ext) per-delta counts; change-set size histograms.

13.3 Deliverable

A deferred extension where a host maintains a derived relation incrementally: applying a small change-set to a large input collection recomputes only the affected output rows. A reactive-database-shaped example (links 366) demonstrates incremental join maintenance.

13.4 Acceptance Criteria

  • Applying a k-row change-set to an n-row collection costs O(k · affected-fanout), not O(n) (the differential target).
  • Differential test: collection-incremental result == a from-scratch recompute over the full collection (INV-1 extended).
  • Batched delta application bumps the revision once and dirties the union of affected keys.
  • Whole-value fallback (no diff) still works for hosts that do not opt into change-sets.

13.6 Pitfalls

  • Diff/whole-value coherence: a query offered both a diff and a whole value must produce the same result either way (INV-1); test both paths against the oracle.
  • Negative-count / retraction bugs: differential semantics use signed multiplicities; a missed retraction yields phantom rows. Track multiplicities carefully.
  • Batching across revisions: mixing deltas from two intended revisions into one bump can hide an intermediate state the host needed; the host controls batch boundaries explicitly.
  • Operator state growth: incremental join indices grow with input; subject to the same GC/cap (Phase 9) — collection operator state is memo state.

13.7 Performance Concerns

  • Change-set application is O(delta), not O(collection) — the whole point; index lookups dominate.
  • Join indices must be GC-aware (Phase 9) to bound memory under large collections.
  • Batching amortizes the dirtying pass across many deltas.

13.8 Edge Cases

  • Empty change-set → no bump (collection-level cutoff, analogous to scalar input cutoff).
  • Delta that nets to no change (insert then remove same row in a batch) → cutoff at the input.
  • Update modeled as remove+insert vs in-place → must be consistent with the operator semantics.
  • Very large single delta (bulk load) → degrades toward whole-value recompute; acceptable.

13.9 Failure Analysis

  • Phantom/missing rows: symptom = derived relation diverges from a full recompute; cause = retraction/multiplicity bug; detection = diff_vs_whole oracle; blast radius = the maintained view; recovery = rebuild the view from scratch.
  • Operator-state OOM: symptom = memory growth localized to join indices; detection = memo_bytes attributable to collection operators; recovery = GC/cap tuning.

13.10 Operational Notes

  • Metrics: engine.changeset_size (histogram), engine.diff_rows_recomputed_total, collection-operator memo bytes.
  • Tracing: per-batch span with delta counts.
  • Status: PhaseDeferred("§39"); not part of the Phase 0 / through-Phase-10 commitment. Cross-links 300 (push dataflow dual) and 366 (incremental reactive DB).

  • A query with a complex generic key → key-derivation must handle generics or emit a clear "implement Key manually" error.

  • A query body that does not compile → the error must surface at the user's source, not the macro internals.

  • Silent semantic drift via macro: symptom = behavior differs from hand-written impl; cause = macro encoding extra logic; detection = group_equiv differential; recovery = strip macro to pure sugar.
  • Poor diagnostics: symptom = users cannot tell why a query won't compile; cause = errors buried in generated code; detection = trybuild expected-error fixtures; recovery = improve spans.

14.10 Operational Notes

  • No runtime metrics (compile-time layer).
  • Tracing: macro-generated queries emit the same TraceEvents as hand-written ones (consistency).
  • Compatibility: the macro surface is semver-governed; additive attributes are minor; changing an attribute's meaning is breaking.
  • Status: deferred polish; correctness and observability (Phases 1–12) take precedence.

27. Failure Modes & Recovery

Taxonomy of failure classes. Each: symptoms; root causes; detection; automatic recovery; manual recovery; operator actions; forensic artifacts; long-term mitigation.

F1 — Stale read (wrong derived value). Symptoms: host sees a value inconsistent with current inputs. Root causes: missed edge (INV-5), bad changed_at comparison (INV-3), lying Eq (INV-4), durability lie (INV-12), un-revalidated persisted load (Phase 11). Detection: oracle differential (divergence_total), stale_return_total>0. Auto recovery: none — correctness bug. Manual: bisect to first diverging query; fix. Operator: if in prod, invalidate the affected store / force cold rebuild. Forensic: dump (node.verified_at, each dep.changed_at, old/new value, Eq result). Long-term: keep oracle differential in CI on every edit sequence.

F2 — Over-recompute (lost incrementality). Symptoms: reuse ratio collapses; latency spikes on edits. Root causes: changed_at advanced on a no-op (INV-4), comparing to current_rev not verified_at (Phase 5), stale reverse edges (Phase 4), no backdating, expensive/missing cutoff. Detection: reuse_ratio regression gate; cutoff_fired_total near 0 when expected. Auto recovery: none (perf bug). Manual: over-recompute.md runbook — inspect frontier size, recompute reasons. Operator: watch reuse-ratio dashboard. Forensic: Recompute{reason} event histogram. Long-term: reuse-ratio CI gate per workload.

F3 — Memory growth / OOM. Symptoms: memo_bytes climbs; host OOM or OutOfMemo. Root causes: GC not keeping up, working set > cap, byte-accounting drift, dangling reverse edges. Detection: memo_bytes vs cap gauge; evicted_total flat while bytes rise. Auto recovery: GC sweep; hard cap aborts the offending demand with OutOfMemo. Manual: raise cap / shrink working set; memory-growth.md. Operator: set cap to host budget. Forensic: per-query memo-bytes attribution. Long-term: arena/compressed values (PhaseDeferred("§39")).

F4 — Cycle (graph or deadlock). Symptoms: a demand never returns. Root causes: genuine query-graph cycle (INV-7) or cross-thread lock wait (Phase 10). Detection: on-stack check → CycleError; depth watchdog; compute_lock_wait_total climbing. Auto recovery: CycleError unwind; optional fixpoint. Manual: cycle-error.md renders the path. Operator: inspect cycle log. Forensic: cycle participant list as DOT. Long-term: cycle_inject fuzz in CI.

F5 — Concurrency hazard (torn read / duplicate compute / stranded key). Symptoms: intermittent wrong values; CPU waste; hung waiters. Root causes: read during mutation (INV-3), missing per-key lock (INV-8), leaked compute lock on cancel/panic. Detection: loom/miri; duplicate_compute_total>0; compute_lock_wait_total unbounded. Auto recovery: guard-based lock release; single-writer model. Manual: watchdog logs owning thread; restart demand. Forensic: per-Computing cell thread id. Long-term: loom model checks in CI.

F6 — Persistence corruption / mismatch. Symptoms: crash or stale on load. Root causes: torn write, format/engine drift, stale provider hash. Detection: checksum + version header; roundtrip differential. Auto recovery: reject store → cold build. Manual: delete store. Forensic: compare persisted vs current provider hashes. Long-term: atomic temp-file rename; provider-hash CI check.

F7 — Determinism breach (nondeterministic query). Symptoms: unreproducible results; replay fails. Root causes: hidden input (clock/RNG/env) in a QueryFn (INV-9). Detection: debug re-run diff; replay test. Auto recovery: none (contract). Manual: audit the flagged query; add #[query(nondeterministic)] or remove the hidden input. Forensic: the re-run value diff. Long-term: deterministic-replay test suite.

F8 — Interning corruption (NodeId reuse). Symptoms: spurious CycleError, edge mispoint. Root causes: NodeId recycled while still referenced (INV-11). Detection: generation-tag mismatch assert. Auto recovery: none (bug). Manual: disable recycle; rebuild interner. Forensic: generation log. Long-term: recycle only with proven zero references.

F9 — Broken early cutoff (re-flood or stale-via-Eq). Symptoms: either reuse ratio collapses on value-preserving edits (re-flood) or a downstream value is stale after a real change (equality lie). Root causes: changed_at advanced on a no-op recompute (INV-4 violation), or a host value type with an unsound Eq (P4). Detection: cutoff_fired_total near 0 when high is expected (re-flood); oracle divergence + divergence_total (equality lie). Auto recovery: none — correctness/perf bug. Manual: for re-flood, fix the recompute-tail timestamp logic; for the lie, fix the type's Eq. Operator: watch cutoff-fired rate vs baseline. Forensic: dump (old_value, new_value, Eq result, old/new changed_at) for the suspect key. Long-term: INV-4 debug assert + value-preserving edits in the property suite. Historical note: rustc's incremental compilation was shipped disabled by default on stable for a period (circa 2017–2018) precisely because soundness bugs in red-green tracking could produce stale/incorrect results — public motivation for ice's differential-oracle-in-CI stance (R7).

F10 — Under-marked frontier (missed dirtying). Symptoms: a demand returns a green hit and a stale value after an edit that should have affected it. Root causes: a reverse edge was never indexed (deps not captured, INV-5) or not updated on a memo replace (Phase 4 stale-reverse-edge pitfall), so the dirtying BFS skipped the node (INV-6 violation). Detection: INV-6 reverse-closure superset assert after dirtying; oracle divergence. Auto recovery: none (bug). Manual: rebuild the reverse index from forward deps (debug repair tool). Operator: stale_return_total>0 page. Forensic: dump reverse-edge closure vs marked set after the offending edit. Long-term: reverse-index-rebuild differential test; capture-completeness fuzzing.

F11 — Cancellation / panic leaks a compute lock (stranded key). Symptoms: a key never completes; threads waiting on it hang; compute_lock_wait_total climbs without resolution. Root causes: a cancelled or panicking demand left a key in Computing without releasing the per-key lock (Phase 10), violating the guard discipline. Detection: watchdog on demand duration; compute_lock_wait_total unbounded; the Computing cell's owner thread id is dead. Auto recovery: guard/Drop-based lock release on unwind; a waiter re-drives the compute if the owner aborted. Manual: restart the stranded demand; inspect the watchdog log. Operator: alert on unbounded compute_lock_wait_total. Forensic: per-Computing cell owner thread id + cancellation log. Long-term: loom schedules that inject cancellation/panic mid-compute (§30).

28. Operational Readiness

The engine is embedded; "operations" are the host application's responsibility, but the engine exposes everything an operator needs.

  • Metrics strategy. Counters/gauges (§23) exported via the metrics facade (ADR-17) behind a feature: reuse_ratio, recompute_total{reason}, green_hit_total, backdate_total, cutoff_fired_total, memo_count, memo_bytes, evicted_total, cycle_detected_total, revision, dirty_frontier_size, compute_lock_wait_total, duplicate_compute_total(0), gc_pause_seconds.
  • Tracing strategy. tracing spans per demand/recompute carry {key, reason, duration, thread, rev}; spans nest to mirror the demand tree; correlate with host spans (e.g. an IDE keystroke).
  • Structured logging. log facade; events on real changes, cutoffs, cycles, evictions, persistence load summaries — never per-green-hit (volume).
  • Dashboard design. Top row: reuse ratio (target ≥ 0.95), recomputes/revision, query p50/p95 latency. Second: memo bytes vs cap, evictions/s, GC pause. Third: cutoff-fired rate, dirty-frontier size, cycle count.
  • Alerting philosophy. Alert on symptoms the host cares about: reuse-ratio drop (incrementality lost), stale_return_total>0 (correctness — page), memo_bytes approaching cap (capacity), cycle_detected_total>0 (host bug), duplicate_compute_total>0 (concurrency bug). Avoid alerting on raw recompute counts (workload-dependent).
  • SLOs. Warm query p50 ≤ 100 ns; reuse ratio ≥ 0.95 on the IDE-keystroke workload; GC pause ≤ 5 ms at 10^6 memos; 0 stale reads; 0 duplicate computes.
  • Incident response. Four runbooks (over-recompute, stale-read, memory-growth, cycle-error), each starting from a specific metric and ending in a fix or a forensic dump (DDG DOT, recompute-reason histogram, dep-set replay).
  • Backup / restore. The persisted store (Phase 11) is the only durable artifact; it is a cache, never authoritative (P14) — backup is optional; restore is always validated (INV-3) so a bad backup cannot serve stale. "Restore testing" = the roundtrip differential fixture.
  • Deployment topology. Single in-process library; no topology. "Canary" = ship the new crate to a subset of hosts; "rolling upgrade" = host-driven; the engine's persisted format is version-gated so a downgrade reads (or rejects) cleanly.
  • Migration strategy. Memo format migrations bump format_version → old stores rejected → cold rebuild (never a stale load). Query-logic changes bump provider hashes → affected memos recomputed.

33. Scalability Analysis

  • Primary bottlenecks. (1) Shared memo-cache shard contention under parallel demand (Phase 10); (2) the single revision clock (one serialized writer for mutations); (3) value clone cost on hits for large values; (4) dirtying-frontier size for high-fan-out inputs; (5) memo memory under unbounded key space.
  • Scaling ceilings. Single process, ≤ 10^7 nodes / 5×10^7 edges (§4) before GC/persistence become mandatory; ≥ 0.7 linear efficiency to 16 cores on independent-query workloads (shard-contention-bound beyond that).
  • Horizontal scaling. Not supported in core (no cross-process memo reuse — PhaseDeferred("§39")); a host shards itself (e.g. per-file sub-databases) if needed.
  • Vertical scaling. More cores → more shards (config); more RAM → higher memo cap (fewer recomputes). Clock-write serialization caps mutation throughput regardless of cores — acceptable for the read-heavy embedded workload.
  • Sharding / partitioning. The memo cache is sharded by key hash (intra-process). Cross-process partitioning is a host concern.
  • Replication pressure. None (no replication).
  • Coordination overhead. Single-writer revision model serializes mutations; reads coordinate only via per-shard RwLock + per-key compute lock. The clock is the one global coordination point; its atomic reads are cheap, its writes (mutations) are rare.
  • Network fanout. None.
  • Scheduler saturation. rayon pool saturates on dense independent-query fan-out; cooperative cancellation keeps superseded work from monopolizing it.
  • Storage growth. Persisted store (Phase 11) grows with the live memo set; bounded by the same cap; old/rejected memos pruned on load.
  • Metadata scaling. Interner + reverse-edge index scale with node/edge count (dense NodeId arrays); GC recycles NodeIds to bound metadata under churn (INV-11).

34. Mental Models & First Principles

Compressed expert intuitions. Each: the model, what it predicts, the bug class you write without it, and where this blueprint applies it.

MM1 — A memo is a dated claim, not a value. A Memo asserts "this value was current as of verified_at, and last changed at changed_at." Predicts: you can reuse a value at a new revision without recomputing iff you can prove nothing it read changed since verified_at. Bug without it: you treat the cache as a plain HashMap<Key,Value>, return a value at the wrong revision, and corrupt every downstream cutoff (the stale-read class). Applied: §8 Domain Model; Phase 5 (§16); INV-3.

MM2 — Two clocks, not one: verified_at and changed_at. Validation answers "is it still current?" (verified_at); cutoff answers "did the value move?" (changed_at). They advance independently — backdating advances verified_at alone. Predicts: deep cutoff is possible only because a revalidated-unchanged node keeps its old changed_at. Bug without it: one timestamp → either re-flood every revision or serve stale. Applied: P8; Phase 5 (§16); Phase 6 (§17); INV-4.

MM3 — Dependencies are discovered, not declared. The dep set is whatever the body read this run, captured by tracing — so deps are dynamic and can differ run to run (a conditional read). Predicts: a branch that reads B only when A>0 records B only when taken; tests must not assume static deps. Bug without it: you hard-code an edge that a run did not take (phantom → waste) or miss one a run did take (missed → stale). Applied: Phase 2 (§13); P7; INV-5.

MM4 — Maybe-dirty is a hypothesis; demand is the experiment. Marking is cheap and conservative (push); proving is lazy and exact (pull). A node is maybe dirty until a demand validates it. Predicts: sparse demand (an IDE showing one file) does work proportional to observed-and-affected, not all-affected. Bug without it: you eagerly recompute the whole frontier (eager-dirty), wasting work on never-observed nodes. Applied: P3; Phase 4 (§15); Phase 5 (§16); INV-6.

MM5 — Cost is the distance of the change, not the size of the graph. Incremental cost is bounded by the transitively-affected-and-demanded set; the firewall (cutoff) shrinks it further. Predicts: a whitespace edit in a 10^6-node graph costs O(firewall), not O(10^6). Bug without it: you reason about absolute graph size and over-provision / mis-set caps. Applied: Acar (P2); P5; §33 Scalability; M8.

MM6 — Equality is the firewall; identity is irrelevant. Cutoff fires on Eq, so a freshly-allocated value that is structurally equal to the old one stops propagation. Predicts: returning a new Vec with identical contents cuts off; a lying Eq silently serves stale. Bug without it: you compare by pointer/identity (never cuts off) or trust a broken Eq (silent wrong results). Applied: P4; Phase 6 (§17); INV-4; T2.

MM7 — Durability gates work, never truth. A durability tier can only let validation skip a walk; a real change always bumps the clock map so the skip is not taken. Predicts: turning all durability to Low changes performance only, never a result. Bug without it: you let "this input is constant" decide a value, and a durable-but-changed input serves stale. Applied: P9; Phase 7 (§18); INV-12.

MM8 — The engine is a cache; only inputs are truth. Any memo may be dropped and recomputed identically. Predicts: eviction, persistence-miss, and cold-start all reduce to "recompute on demand"; a side effect hidden in a query body breaks this. Bug without it: you treat a recompute's side effect as load-bearing, and eviction silently changes behavior. Applied: P14; Phase 9 (§20); P2; INV-10.

MM9 — A graph cycle is single-thread re-entry; a cross-thread wait is a deadlock. They look alike (a stuck demand) but have different causes and fixes. Predicts: the on-stack check must fire before the per-key lock, or a self-cycle deadlocks instead of erroring. Bug without it: you conflate them, "fix" a cycle with lock ordering, and still hang. Applied: Phase 8 (§19); Phase 10 (§21); P12; INV-7.

MM10 — Reuse is invisible until you instrument it. An incrementality regression manifests only as latency unless every reuse/recompute/cutoff decision is counted. Predicts: a reuse-ratio gate catches a broken changed_at before users feel it. Bug without it: silent over-recompute ships and is debugged from latency graphs with no signal. Applied: P10; Phase 12 (§23); §27 Failure Modes.

36. Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from §4 System Constraints (formula shown).

  1. Memo-state RAM at the node ceiling. From §4: ≤ 200 bytes/memo overhead, 10^7 nodes. 10^7 × 200 B = 2.0 GB overhead — excluding host values. This is why the default soft cap is 2 GiB plus value bytes, and why GC (Phase 9) is mandatory at the ceiling.
  2. Reverse-edge index RAM. From §4: 5×10^7 edges; a reverse edge ≈ one NodeId (4 B) in a SmallVec, amortize ~8 B with overhead. 5×10^7 × 8 B = 0.4 GB. Plus forward deps (already in the 200 B/memo). Total graph metadata ≈ 0.4 GB on top of memo overhead.
  3. Cold-build wall-clock for a full 10^7-node graph. From §4: ≥ 10^6 trivial evals/s/core. Single-core: 10^7 / 10^6 = 10 s. At 0.7×16 = 11.2 effective cores (M11): 10 s / 11.2 ≈ 0.9 s. Cold builds of large graphs are seconds — hence persistence (Phase 11) to avoid repeating them.
  4. Warm re-validation of an unchanged 10^7 graph. From §4: ≤ 50 ns/node validated, O(roots). If re-demanding all roots forces a full validate: 10^7 × 50 ns = 0.5 s worst case; with durability shortcuts on stable subgraphs this collapses toward O(roots). Motivates Phase 7 durability.
  5. IDE keystroke budget vs reuse ratio. A 60 fps frame ≈ 16 ms. From §4: reuse ≥ 0.95 after a 1-token edit. If an edit affects 10^4 nodes but cutoff reuses 95%, recompute ≈ 500 nodes; at, say, 1 µs/node real work = 500 µs ≪ 16 ms. The reuse-ratio target is the latency budget.
  6. Green-hit throughput per core. From §4: ≤ 100 ns p50 warm hit. 1 / 100 ns = 10^7 hits/s/core. A warm IDE doing 10^4 demands/keystroke spends 10^4 × 100 ns = 1 ms — well inside frame budget.
  7. Dirtying frontier for a hub input. A global config read by N queries: marking is O(N). At 10^6 dependents and a SmallVec push ~10 ns: 10^6 × 10 ns = 10 ms just to mark — visible. This is the §4 "pathological fan-out" case and why durability (Phase 7), not marking-avoidance, is the mitigation.
  8. GC sweep work within the pause budget. From §4: ≤ 5 ms/sweep at 10^6 memos. Budget per memo: 5 ms / 10^6 = 5 ns. An LRU list splice + byte-accounting must stay ≤ 5 ns/memo amortized → intrusive list, no per-memo allocation (Phase 9).
  9. Persistence load vs cold rebuild. From §4: load+revalidate of 10^6 memos must beat a cold rebuild. Cold = 10^6 / 10^6/s = 1 s (1 core). If bincode load is ~200 MB/s and the store is ~0.4 GB: ~2 s to deserialize — so the win comes from revalidation being O(roots) (durability), not from deserialization being instant. Sets the Phase 11 acceptance ratio expectation.
  10. Shard count for 16 cores. From ADR-04: next_pow2(2 × cores) = next_pow2(32) = 32 shards. With 32 shards and uniform key hashing, the probability two of 16 threads hit the same shard on a given access ≈ 1 − Π(1 − k/32) — low enough to hold M11's ≥ 0.7 efficiency until contention on the shared clock dominates.
  11. Value-clone cost ceiling on hits. Green hit = lookup + compare + value.clone() (MM-/§4). For the 100 ns p50 budget, with ~30 ns lookup+compare, the clone must be ≤ ~70 ns → values must be small or Arc-wrapped (ADR-11; the Phase-13 arena extension). A 10 KB memcpy ≈ 1–3 µs blows the budget → such values must be shared, not cloned.
  12. FD / syscall budget. Core is syscall-free (§4) except persistence + trace export. Steady-state demand does 0 syscalls; the only FDs are the persisted-store file (1) and optional trace sink (1). Confirms the engine adds no FD pressure to the host.

38. Alternative Architectures (Roads Not Taken)

Three fundamentally different architectures for the same problem, why each is real, and why this blueprint rejected it for the Phase-0 target.

A1 — Push-based / eager stabilization (height-ordered).

   input changed
        | (push)
        v
   [recompute all dependents now, in height order]
        |
        v
   outputs always current (no per-read validation)

Regime where it wins: dense, always-observed derived state — spreadsheets, trading dashboards, reactive UIs where nearly every node is displayed every frame, so lazy validation saves nothing and eager recompute avoids per-demand overhead. Real system: Jane Street Incremental (height-based scheduler), the signals pattern in Glimmer/Solid. Why rejected here: ice's target hosts (compilers, IDEs) have sparse demand — an editor shows one file of 10^4 — so eager stabilization would recompute a huge never-observed frontier, the exact opposite of P3/MM4. Push is the dual we point at project 300.

A2 — Content-addressed / hash-of-inputs memoization (no revision clock).

   query(key) ----> H = hash(key, hashes_of_all_inputs_read)
                       |
                       v
                  lookup memo by H  --hit--> reuse
                       | miss
                       v
                  compute, store under H

Regime where it wins: coarse-grained, file-level builds and cross-machine shared caches — the hash is a portable cache key, so a build on machine A is reused on machine B with no shared revision state. Real system: Bazel/Buck (content hashing + remote cache), comemo (Typst, constraint/hash-based). Why rejected here: hashing the full transitive input set on every query is O(inputs) per lookup and loses early cutoff at intermediate nodes (a changed input changes every downstream hash even when the value is unchanged), defeating P4/MM6. Revisions + per-node changed_at give O(1) staleness checks and deep cutoff. Content-addressing is the right model for the deferred cross-process feature (§39), not the in-process core.

A3 — Collection-oriented differential dataflow (per-record diffs).

   input collection --delta {+r1,-r2}--> [map]->[join]->[reduce]
                                            |      |       |
                                       per-record (data, time, diff) flow
                                            v
                                   only affected output rows change

Regime where it wins: incremental view maintenance over large relations and iterative graph computation, where a 1-row change to a 10^9-row input must touch only matched output rows — whole-value recompute of a collection query would be catastrophic. Real system: Differential Dataflow / timely dataflow; the model behind project 366. Why rejected as the core: it solves a different problem (incremental over collections) with signed multiplicities and operator state; forcing scalar query memoization into it adds retraction/multiplicity machinery the compiler/IDE use case does not need. ice keeps whole-value granularity for Phase 0 and offers differential collections as the Phase 13 (§24) extension layered on the same revision core.

40. Glossary

  • Backdating — advancing a memo's verified_at to the current revision while leaving changed_at unchanged, after proving its value did not change; the mechanism that makes early cutoff transitive (P8/INV-4).
  • Change propagation — the process of validating/recomputing the transitively-affected portion of the DDG after an input change.
  • changed_at — the revision at which a node's value last actually changed; drives downstream cutoff decisions.
  • Cold build — full evaluation with an empty memo cache (no reuse).
  • Cutoff (early cutoff) — stopping propagation when a recomputed value equals (Eq) the prior value; the firewall against needless downstream recompute (P4).
  • CycleError — typed recoverable error returned when a demand re-enters a key already on the compute stack (INV-7).
  • DCG / DDG — Dynamic (Demanded) Computation/Dependency Graph; the runtime graph of inputs and derived queries discovered by execution tracing.
  • Demand (pull) — requesting a query's value; the only trigger for (re)computation (P3).
  • Dependency capture — recording the exact set of inputs/queries a query reads, by tracing its execution via the thread-local DependencyStack (INV-5).
  • Dependency edge — a (NodeId, changed_at_when_read) record linking a query to something it read; versioned for precise validation.
  • DependencyStack — the per-thread stack of frames accumulating read edges for the currently-executing queries.
  • Derived query — a pure function execute(db, key) -> value whose result is memoized (#[query]).
  • Durability — an advisory class (Low/Medium/High) on inputs; gates a validation short-circuit but never affects a result (P9/INV-12).
  • Early cutoff — see Cutoff.
  • Firewall — a node where cutoff fires, halting an otherwise-cascading downstream recompute.
  • Fixpoint recovery — optional iteration to a stable value for a recoverable query-graph cycle, instead of erroring (Phase 8).
  • From-scratch consistency — the property that incremental results always equal a fresh rebuild from the same inputs (INV-1); the engine's correctness contract.
  • Green hit — returning a cached value because verified_at == current_rev (no work).
  • Input cell — a leaf node holding (value, changed_at, durability); mutated by set_input (#[input]).
  • Interning — mapping a QueryKey to a dense, recyclable NodeId(u32) (INV-11).
  • MaybeDirty — the conservative state of a node transitively reachable from a changed input, pending validation (INV-6) — not committed to recompute.
  • Memo — the cached record for a derived query: {value, verified_at, changed_at, durability, deps, state}.
  • Memoization — caching a pure function's result keyed by its inputs to avoid recomputation.
  • Minimality — recomputing only the transitively-affected set, never the whole graph (P5; the O(affected) target).
  • NodeId — interned dense identifier {index:u32, generation:u16} for a node (INV-11).
  • NodeState — Unverified | Verifying | Verified(R) | MaybeDirty | Computing.
  • Oracle — the from-scratch reference Database used in differential testing (INV-1).
  • Provider hash — a per-query semantic-version hash persisted with a memo; a mismatch (changed query logic) forces recompute on load (Phase 11).
  • Pull vs push — pull = recompute on demand (this engine); push = eagerly propagate changes (the dual, project 300).
  • Reachability sweep — GC pass collecting memos reachable only from evicted/undemanded nodes (Phase 9).
  • Red-green algorithm — the salsa-style validation scheme using verified_at/changed_at/durability to decide reuse vs recompute (Phases 5–7).
  • Reuse ratio — fraction of demanded nodes served without recompute; the headline incrementality metric (target ≥ 0.95).
  • Reverse edge (dependents index) — NodeId → dependents; used to mark the MaybeDirty frontier and for GC reachability.
  • Revision — a monotonic global u64 logical clock value; orders all state (P6/INV-2).
  • Single-writer model — mutations (set_input) are serialized (exclusive); reads/recomputes run concurrently against a pinned snapshot (Phase 10).
  • Snapshot — a read-only handle pinned to a revision for lock-free concurrent reads (Phase 10).
  • Stale read — returning a value computed against an older revision without revalidation; forbidden (P13/INV-3).
  • verified_at — the revision at which a memo was last confirmed current (possibly via backdating).
