56 — In-Memory Store

Project Number: 56

Project Name: In-Memory Store

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a single-binary, single-process, from-scratch in-memory key-value data store wire-compatible with the Redis 7.x command surface on RESP2 and RESP3: the full data-type surface (strings, lists, hashes, sets, sorted sets, streams, bitmaps, HyperLogLog, geospatial), active-plus-lazy expiration, AOF/RDB/hybrid persistence, PSYNC2 leader-replica replication, and a 16,384-hash-slot cluster mode with gossip-based membership, MOVED/ASK redirection, and replica failover. Scripting ships behind an embedded Lua 5.1 interpreter (EVAL/EVALSHA); a module ABI placeholder, ACL/AUTH/TLS, command renaming, and keyspace notifications complete the Phase-0-through-11 surface. The engine is not benchmarked to beat Redis; it is built to the depth that lets an operator debug the hard cases in source: an AOF rewrite racing a write storm, a replica reconnecting with a stale replication backlog, a slot migration interleaved with a MULTI/EXEC transaction, a listpack converting to a quicklist at the wrong load-bearing moment.

Phase-0 deliverable — numbered modules:

  1. store-resp — RESP2/RESP3 parser and encoder.
  2. store-dispatcher — connection state machine, command registry, MULTI/EXEC, pub/sub, keyspace notification hooks.
  3. store-core — RedisObject, the five collection types and their dual encodings, the incremental-rehash Dict.
  4. store-server — binary entry point, config, listener, serverCron.
  5. store-persistence — AOF writer/rewriter/loader (Phase 0 ships AOF only; RDB lands Phase 5).

System boundaries.

  • Provides: RESP2/RESP3 wire service; the full documented Redis 7.x data-type/command surface except the explicitly deferred long tail (§37); AOF+RDB+hybrid persistence; leader-replica replication with PSYNC2; 16,384-slot cluster mode; ACL/AUTH/TLS; Lua 5.1 scripting; a module ABI surface (not binary-compatible with RedisModule_*, §37).
  • Delegates: eviction algorithms to the LRU/LFU cache engine (project 59, §33); active-expire sampling internals to the key-expiration engine (project 62); cluster gossip transport to the gossip-protocol crate (project 72); TLS handshake to the TLS/SSL-handshake crate (project 50); pub/sub fanout to the pub/sub-messaging crate (project 60).
  • Does NOT provide: RedisJSON/RediSearch/RedisTimeSeries-equivalent module implementations; binary RedisModule_* ABI compatibility (PhaseDeferred("Deferred Features Register")); the RESP3 client-side-caching push protocol beyond the CLIENT TRACKING skeleton (PhaseDeferred("Deferred Features Register")); cross-region conflict-free replication; on-disk-first storage (this is an in-memory store; AOF/RDB are durability, not the primary access path).

Non-goals: surpassing Redis on micro-benchmarks; implementing every long-tail debug/introspection command (OBJECT FREQ variants, CLIENT NO-EVICT, full CLUSTER SHARDS detail); shipping vector/JSON/search/time-series types (Redis 8 surface, PhaseDeferred("Deferred Features Register")).

Deployment model: one binary (store-server) per node; a cluster is N independently-deployed nodes gossiping over a dedicated bus port (client port + 10000, Redis convention); no external coordination service (no ZooKeeper/etcd dependency — cluster state is self-hosted via gossip, ADR-10).

Target users/operators: engineers who already run Redis/Valkey in production and want the ability to read and modify the source when production surprises them; systems-course learners building toward a principal-engineer command of in-memory data stores.

What later phases unlock: Phase 5 (persistence) unlocks crash recovery and the hybrid RDB+AOF default; Phase 7 (replication) unlocks read scaling and failover; Phase 8 (cluster) unlocks horizontal write scaling past one node's memory ceiling; Phase 10 (scripting) unlocks atomic multi-step server-side logic without network round-trips.

Recommended language + rationale: Rust 1.79+ (ADR-01). Ownership model closes the encoding-corruption and use-after-free bug classes at compile time (Invariant I3); a mature async runtime (tokio) supports the pinned-single-thread-per-shard model (Principle P2) natively via LocalSet. Rejected: C (antirez's own choice — manual memory management reintroduces exactly the bug classes Rust's ownership model closes, at the cost of noisier unsafe blocks confined to the listpack/skiplist internals); Go (garbage-collector pauses, even sub-millisecond in modern Go, are a tail-latency risk at the p99.9 the M-table targets, §30); C++ (no borrow checker, so the encoding-conversion race class, I3, is a code-review-only defense, not a compiler-enforced one).

Prerequisites: async Rust (tokio runtime, pinned futures, Send/Sync, !Unpin implications for a dispatcher loop); hash tables (open addressing, incremental rehash); the skiplist (Pugh 1990); the RESP wire protocol (both versions); write-ahead logging and copy-on-write snapshotting; enough TCP networking to know why TCP_NODELAY and SO_REUSEPORT matter on a request-response wire.

Estimated timeline: Phase 0 — 1 week. Full system (Phases 0–11) — 19 weeks (≈4.5 months) at one senior engineer full-time; 6 months with review/integration overhead.

Deferred features (all resolve in the Deferred Features Register, §37): PhaseDeferred("Deferred Features Register") for RedisModule_* binary ABI compatibility; RESP3 client-side-caching invalidation push protocol; vector/JSON/search/time-series data types; cross-region CRDT replication; full cross-cluster MIGRATE/DUMP/RESTORE semantics ahead of Phase 8; WAIT/WAITAOF ahead of Phase 7; cluster-bus mTLS ahead of Phase 9; 30-day continuous fuzzing ahead of the Sealed gate (§29).

2. Why Build This

  • Redis-shaped holes exist in nearly every production architecture at scale: session store, rate limiter, leaderboard, cache, broker, pub/sub fanout, coordination primitive — teams that only consume Redis cannot debug its surprises; teams that built one can.
  • Owning the wire parser, dispatcher, every dual-encoding data type, the active+lazy expiration loop, AOF/RDB/hybrid persistence, PSYNC2 replication, cluster hash slots + gossip, ACL/TLS, MULTI/EXEC/WATCH, pub/sub, and embedded Lua teaches, end to end, why every one of those subsystems is shaped the way it is — not by reading a blog post but by hitting the same design forks antirez hit between 2009 and 2024.
  • Architecturally: this is the canonical "shared-nothing shards behind a single dispatcher" design (P2) — the same shape (minus the persistence/replication machinery) as much latency-critical infra (matching engines, ad-serving caches, session routers).
  • Historically: Redis is the reason "single-threaded event loop, multi-process for scale" became a legitimate alternative to "multi-threaded with fine-grained locks" in systems design — this project reproduces that argument in code, not in the abstract.
  • Cross-links by name: the LRU/LFU cache engine (project 59) supplies eviction algorithms this store's store-eviction crate wires in (§33); the pub/sub messaging system (project 60) supplies the fanout store-dispatcher::notify calls; the key-expiration engine (project 62) supplies the active-expire sampling loop (§18); the gossip protocol (project 72) supplies cluster membership (§20); the TLS/SSL-handshake project (project 50) supplies the encrypted transport (§21); the LSM-Tree storage engine (project 68) and the WAL project (project 69) are the disk-first counterpoints referenced in the Comparative Architecture Table (§33) and Alternative Architectures (§36).
  • Calibration value: after this project, "should this subsystem be single-threaded-sharded or lock-striped" and "should this durability path be WAL-then-checkpoint or snapshot-then-tail" stop being abstract tradeoffs and become questions with a concrete, benchmarked answer from your own code.

What Mastery Looks Like

  • Wire-protocol literacy — write a RESP2/RESP3 parser from the grammar alone and explain why the parser must be incremental (Phase 1, §13).
  • Dual-encoding data-structure design — justify, with a memory/CPU tradeoff table, why every collection type ships two encodings and why the conversion is one-way (Phase 3, §15).
  • Copy-on-write snapshotting without fork() — explain why tokio is not fork-safe and design a data-structure-level COW alternative (Phase 5, §17).
  • Replication backlog sizing — derive, from a target disconnect-tolerance window and a write rate, the correct repl-backlog-size (Phase 7, §19; also §34 Capacity Model).
  • Cluster slot-map reasoning — trace a MOVED/ASK redirection sequence during a live slot migration and explain why ASKING is required for transactional correctness (Phase 8, §20).
  • Failure-mode instinct — predict, from the invariants table alone (§7), what breaks when any one of I1–I14 is violated, without running the code (Phases 6–9).
  • Security-surface literacy — design an ACL rule set that is order-sensitive-correct and explain why +@all -@dangerous differs from -@dangerous +@all (Phase 9, §21).
  • Systems-comparative fluency — place this design against Memcached, KeyDB, Dragonfly, and Aerospike on load-bearing dimensions and name exactly which one decision each made differently and why (§33).

Clients — any RESP2 or RESP3 speaker; no client-side changes required versus talking to real Redis (Principle P1).

Listener — one tokio listener task per bound (address, protocol) pair; accepts connections and hands each to a shard chosen by a fixed hash of the connection's file descriptor (round-robin at startup, sticky thereafter) so that a connection's commands always execute on the same dispatcher.

Connection — owns the per-client parse/encode buffers and all client-local state (auth, transaction, watch set, subscriptions); this is the trust boundary between an unauthenticated byte stream and an ACL-checked command.

Dispatcher — the sole mutation path into a shard's databases (I2); every command passes through lookup → arity → ACL → cluster-slot check → execute, in that order, never re-ordered.

Database — the keyspace and its cross-cutting indices (expires, watch, blocked-client, keyspace-notification matrix); one instance per SELECT-able database index, 16 per shard by default.

Persistence — reads the dispatcher's already-validated write commands; never reads the database directly outside of a snapshot handoff (P4, P8).

Replication — the same command stream persistence sees, replayed to replicas instead of a file; PSYNC2's partial-resync path is what makes short disconnects cheap (P5).

Data-type encodings — every collection type exposes exactly two encodings behind a vtable; the dispatcher never branches on encoding, only on ObjectType (P3).

Background tasks — active-expire and eviction never hold the dispatcher mutex for more than their configured budget (I2, Pitfall in §18.6).

Cluster — a slot map, not a hash ring (P6); gossip converges slot ownership across nodes without an external coordinator (ADR-10).

Three properties recur throughout this document. First, the dispatcher is single-threaded per shard; concurrency comes from sharding, not from locking (P2, ADR-05) — this is the choice antirez made in 2009 and the one this project re-makes, and it is what removes every reader-writer-lock bug class from the codebase. Second, the data path is one-way: bytes flow up from the listener into the dispatcher, mutate the database, and flow back down through the encoder; persistence and replication read the dispatcher's command stream, never the database directly. Third, every data type has exactly two encodings, and the conversion threshold is part of the type's invariant (I3); the dispatcher never reasons about encodings, it asks the type's vtable.

4. System Constraints

The defining property of this system: single-threaded-per-shard dispatch trades intra-shard parallelism for the complete absence of lock contention inside a shard (P2); throughput scales with shard count up to the physical core count, never beyond it.

6. Design Principles

  1. P1 — Wire compatibility is the contract. Every byte the engine emits is the byte real redis-cli and client libraries expect. Tradeoff: forecloses inventing a cleaner protocol. Operational implication: the conformance suite (§28) replays recorded traces and asserts byte-identical responses. Violation: any deviation silently breaks every client library in the wild, not just ours.
  2. P2 — One dispatcher per shard. Concurrency comes from sharding, never fine-grained locking. Tradeoff: no intra-shard parallelism. Operational implication: throughput scales with shard count up to core count (§4). Violation: introducing a lock inside a shard reintroduces the entire reader-writer-lock bug class this design exists to avoid.
  3. P3 — Two encodings per data type. Compact (listpack/intset) for small collections, full (hashtable/skiplist/quicklist) otherwise; conversion is one-way. Tradeoff: a key that shrinks below threshold never reverts, wasting some memory. Operational implication: OBJECT ENCODING is a supported introspection surface operators rely on. Violation: skipping compact encodings inflates per-key memory 3–8× on small-collection-heavy workloads (I3).
  4. P4 — Persistence is asynchronous; durability is configurable. AOF buffers and flushes on a cadence (always/everysec/no); RDB snapshots never block the dispatcher. Tradeoff: everysec accepts up to 1s of data loss. Operational implication: the durability knob is a documented SLA, not an implementation detail. Violation: a synchronous fsync on the dispatcher thread freezes every shard client (§17.8).
  5. P5 — The command log is the source of truth for replication. AOF and replication share one serialization path. Tradeoff: replication cannot diverge from persisted state by design. Operational implication: PSYNC2 partial resync reuses the same backlog format as AOF framing. Violation: a second, independent replication encoding doubles the surface for wire-format bugs.
  6. P6 — The cluster is a slot map, not a hash ring. 16,384 fixed slots, gossiped ownership. Tradeoff: re-sharding is coarser-grained than ring rebalancing. Operational implication: MOVED/ASK redirection is deterministic and inspectable via CLUSTER SLOTS. Violation: substituting consistent hashing breaks wire compatibility with every real Redis Cluster client (I7, I8).
  7. P7 — No silent fallbacks. A command's documented edge-case behavior is exact, never approximated. Tradeoff: more branches per command. Operational implication: the conformance suite encodes every documented distinction (e.g. LPOP nil vs empty-array). Violation: client libraries that pattern-match on exact reply shapes break silently.
  8. P8 — Determinism is the default for anything touching persistence. AOF/RDB replay is bit-deterministic given a starting point and a command log; non-deterministic commands (SRANDMEMBER, SPOP) are seeded and the seed is recorded. Tradeoff: extra bookkeeping per random command. Operational implication: replay-based debugging is possible. Violation: a replica or AOF-replay that samples independently diverges from the leader silently (I4).
  9. P9 — Eviction policy is the store's; the algorithm is delegated. The store owns the trigger (maxmemory watermark) and candidate-set construction; the LRU/LFU cache engine (project 59) owns the algorithm. Tradeoff: a crate boundary between trigger and algorithm. Operational implication: eviction policies are swappable without touching the dispatcher. Violation: inlining eviction logic into the dispatcher couples two independently-evolving concerns (ADR-12).
  10. P10 — Strings are bytes. Never validated as UTF-8, never interpreted except in the documented numeric-conversion commands. Tradeoff: no built-in encoding safety net for application bugs. Operational implication: binary-safe keys and values are a first-class guarantee. Violation: any UTF-8 validation on the write path silently corrupts binary payloads (image blobs, protobuf, etc.).
  11. P11 — Backpressure over unbounded buffering. A slow client is bounded and eventually disconnected, never allowed to grow the server's memory without limit. Tradeoff: a legitimately slow-but-valid subscriber can be dropped. Operational implication: client-output-buffer-limit is a tunable, documented SLA (ADR-22). Violation: unbounded per-connection buffers turn one slow subscriber into a cluster-wide OOM (T5, FM-6).
  12. P12 — Fail closed on ambiguity. ACL and auth decisions default-deny when a rule set is partial or conflicting. Tradeoff: a misconfigured ACL rejects more than a permissive default would. Operational implication: ACL LIST/ACL GETUSER must always show the effective, fully-resolved rule set, not just the configured deltas. Violation: default-allow on ambiguity is the root cause class of most real-world ACL privilege-escalation incidents.
  13. P13 — Observability is not optional. Every subsystem emits a trace span and a metric; a subsystem that cannot be measured cannot be operated. Tradeoff: instrumentation overhead on the hot path (bounded, see M-table §30). Operational implication: the dashboards in §26 are buildable from day one, not retrofitted. Violation: an uninstrumented subsystem is undebuggable in production by construction, not by accident.
  14. P14 — Configuration is versioned and reloadable without full data loss. CONFIG SET applies at runtime where safe (maxmemory, appendfsync); restart is required only where correctness cannot otherwise be guaranteed (cluster-enabled). Tradeoff: a two-tier config model (hot-reloadable vs restart-required) is more complex than "everything requires restart." Operational implication: CONFIG GET/CONFIG SET/CONFIG REWRITE must agree with the running process, not just the file on disk. Violation: a config surface that silently ignores a runtime CONFIG SET produces the exact "why didn't my change take effect" incident class operators hate most.

8. Domain Model / Protocol / Data Model

8.1 RESP2 Wire Grammar (EBNF)

frame        = simple-string | error | integer | bulk-string | array ;
simple-string = "+" , text , CRLF ;
error         = "-" , text , CRLF ;
integer       = ":" , [ "-" ] , digit+ , CRLF ;
bulk-string   = "$" , length , CRLF , [ length*OCTET , CRLF ] ;
array         = "*" , count , CRLF , frame* ;
length        = "-1" | digit+ ;        (* "-1" = nil bulk string *)
count         = "-1" | digit+ ;        (* "-1" = nil array *)
text          = OCTET* - (CR | LF) ;
CRLF          = %x0D.0A ;

A client request is always an array of bulk-strings (the "multi-bulk" request form); a server reply may be any frame. Applied in Phase 1 (§13.1).

8.2 RESP3 Extensions (EBNF delta)

map      = "%" , pair-count , CRLF , (frame , frame)* ;
set      = "~" , count , CRLF , frame* ;
boolean  = "#" , ("t"|"f") , CRLF ;
double   = "," , float-text , CRLF ;
bignum   = "(" , digit+ , CRLF ;
verbatim = "=" , length , CRLF , 3OCTET , ":" , (length-3)*OCTET , CRLF ;
push     = ">" , count , CRLF , frame* ;
null     = "_" , CRLF ;
streamed = "$?" , CRLF , ( ";" , chunk-len , CRLF , chunk-len*OCTET )* , ";0" , CRLF ;

A RESP2 connection parsing any of these tags is a protocol error; the connection's negotiated protocol field (set by HELLO) gates acceptance. Applied in Phase 1 (§13.2).

8.3 Worked Examples

SET foo bar EX 10, wire request (RESP2): *5\r\n$3\r\nSET\r\n$3\r\nfoo\r\n$3\r\nbar\r\n$2\r\nEX\r\n$2\r\n10\r\n → reply +OK\r\n.

ZADD leaderboard 100 alice, wire request: *4\r\n$4\r\nZADD\r\n$11\r\nleaderboard\r\n$3\r\n100\r\n$5\r\nalice\r\n → reply :1\r\n (one new member added).

HELLO 3 reply (RESP3 map form) vs the RESP2-flattened equivalent of the same logical map — this is the P1/I11 dual-mode encoding in miniature: RESP3 emits %7\r\n$6\r\nserver\r\n$5\r\nredis\r\n...; RESP2 emits the same 14 elements as *14\r\n$6\r\nserver\r\n$5\r\nredis\r\n... — one flat array, alternating key/value.

8.4 Storage Record Layouts

RedisObject header (fixed 12 bytes + pointer): kind: u8 (ObjectType) | encoding: u8 | lru_or_lfu: u32 (24-bit LRU clock or 8-bit logc + 16-bit decr-time, mode selected by maxmemory-policy) | refcount: u32 | ptr: ObjectPtr (8 bytes, tagged pointer/inline union).

Listpack (compact encoding for list/hash/set/zset): header total-bytes: u32 LE, num-elements: u16 LE (0xFFFF sentinel means "count by scan"), then a sequence of {encoding-byte, payload, backlen} entries (backlen enables O(1) reverse traversal), terminated by a single 0xFF byte.

Quicklist node (full encoding for lists ≥ threshold): a doubly-linked list of nodes, each holding one listpack of up to list-max-listpack-size entries; each node carries count: u16, sz: u32 (compressed byte size), compressed: bool (LZF compression of cold nodes, PhaseDeferred("Deferred Features Register")).

Intset (compact encoding for all-integer sets): header encoding: u32 LE (2, 4, or 8 — narrowest width that fits every member), length: u32 LE, then a sorted array of fixed-width signed integers; insertion upgrades the width in place if a new member exceeds the current one.

Skiplist node (full encoding for sorted sets, keyed by (score, member)): see §11.5 for the exact field signatures; span at each level is the exact node count skipped — the value this document's I13 protects.

8.8 Failure-Path Example

An AOF rewrite child (§17.2) crashes after writing 60% of the new file. The dispatcher continues appending to the old AOF and to the in-memory rewrite buffer throughout — the old file is never truncated until the new one is confirmed complete via a trailing checksum record. On restart, the loader (§17.4) detects the new file's missing/short checksum trailer, discards it, and loads the old AOF instead — zero data loss, one skipped rewrite (telemetry: store_aof_rewrite_failures_total increments; Pitfall cross-reference: §17.8).

13. Phase 1 — RESP2/RESP3 Codec & Command Dispatcher

13.1 Objectives

Replace Phase 0's throwaway PING handler with the real store-resp codec and store-dispatcher command registry; achieve byte-identical encode/decode against a recorded redis-cli corpus (P1); land the shard/dispatcher concurrency model (P2, ADR-05).

13.2 Detailed Implementation Steps

  • Implement the RESP2 grammar (§8.1) as an incremental parser: Ok(None) on an incomplete frame, so a pipelined client is never forced to wait for the whole buffer (ADR-04) — this is the load- bearing property distinguishing a correct parser from a naive one.
  • Implement the RESP3 extensions (§8.2): map/set/boolean/double/bignum/verbatim/push/null/streamed tags, gated by Connection::protocol (I11) — every emit path re-checks protocol, never caches it at dispatch time.
  • Implement the encoder as the dual-mode mirror of the parser: RespValue::Map flattens to an alternating array on a RESP2 connection, stays a true map on RESP3 (§8.3 worked example).
  • Implement the connection read loop: drain all complete frames from the input buffer before issuing another socket read; drain the output buffer in one write_all_buf call per iteration — this is what makes pipelining work without extra buffering logic (P2, since the dispatcher never blocks mid-batch).
  • Implement the dispatcher: a HashMap<&'static str, Arc<dyn Command>> keyed by uppercase command name; per frame — validate array-of-bulk-strings shape, look up by name, check arity (Arity), check ACL (stubbed allow-all until Phase 9, ADR placeholder), compute cluster slot if enabled (stubbed until Phase 8), execute, encode.
  • Land PING, ECHO, SELECT, COMMAND, CLIENT, HELLO, QUIT as the first real Command impls, each with its documented CommandFlags (§11.4).
  • HELLO 3 mutates Connection::protocol in place — implement and test this transition against I11 explicitly (a fixture pipelines HELLO 3 mid-stream and asserts subsequent replies switch format).

  • 100% of conformance/corpora/resp/*.bin fixtures round-trip byte-identically (≥ 40 fixtures).
  • redis-cli PING, ECHO hello, SELECT 0, COMMAND COUNT, HELLO 3, QUIT all return documented wire bytes, asserted in conformance/corpora/commands/generic/*.json.
  • Pipelined burst of 1,000 PINGs over one connection completes in ≤ 5 ms (single shard, warm).

The parser must not copy the input buffer per frame — slice into the existing BytesMut and only materialize an owned Bytes at the point a RespValue::BulkString is constructed (allocation concern, applies to M1/M3 in §30). The dispatcher's HashMap lookup is on the hot path for every command; command names are uppercased once at parse time, not per lookup.

13.8 Edge Cases

  • A single TCP read returning multiple complete frames plus one partial frame — the loop must drain the complete ones and retain the partial for the next read.
  • HELLO with an unsupported version number (e.g. HELLO 4) — must return a documented NOPROTO error, not panic.
  • Empty command name (*1\r\n$0\r\n\r\n) — arity check must reject before command lookup.

13.9 Failure Analysis

A malformed frame from one client must not affect any other client on the shard (blast radius = one connection). Detection: parser returns a typed ParseError; the dispatcher converts it to a RespValue::Error and, per the protocol spec, may close that connection — never the shard. Recovery: client reconnects; no server-side state survives a connection close at this phase.

EmbString's 44-byte threshold is chosen to share a cache line with the RedisObject header (§8.4) — going above it costs a second cache-line fetch per access, a real latency-tail contributor at the M5 target (§4/§30). 14.8 Edge Cases

  • SETRANGE extending a string past its current length must zero-pad the gap, not leave uninitialized bytes.
  • INCRBYFLOAT on a value with trailing zeros must not introduce floating-point drift across repeated calls (documented rounding behavior).
  • EXPIRE with a negative seconds argument deletes the key immediately (documented Redis behavior, not an error).
  • Clock skew: EXPIREAT with a timestamp already in the past deletes immediately; monotonic Instant internals (ADR-23) must not let a backward wall-clock step resurrect an expired key.

14.9 Failure Analysis

A SCAN cursor bug under-samples silently — no crash, no error, just missed keys — making this one of the hardest classes to detect in production. Mitigation: the property test in §14.4 runs 100 randomized rehash-interleaved iterations in CI, not just a happy-path single run. Blast radius: an under-sampling SCAN affects any admin tool relying on full iteration (backup scripts, migration tools) — a real production hazard class, not a cosmetic one.

15.6 Pitfalls

  • Checking only entry count (not per-entry byte size) for conversion ships a pathological 1KB-per-entry listpack slower than a hashtable would have been (P3, §8.5).
  • Getting the skiplist's span bookkeeping wrong breaks ZRANK/ZRANGE even while ZSCORE continues to work — the failure is invisible without the differential test in §15.4 (I13).
  • The intset's insertion is O(N) array shift — acceptable at small sizes but a latency hazard if the conversion threshold is set too high for the shift cost.
  • ZADD's flag parser is a genuine maze; conflicting flags must be rejected before any mutation is applied (a partial-apply-then-error bug corrupts state, violating P7).

15.7 Performance Concerns

Blocking commands' unblock fan-out (§15.2's blocking.rs) must not scan every connection on the shard — index by key in blocked_clients (§11.2) so an LPUSH only wakes the connections actually waiting on that key. The skiplist's random_level allocation (a Vec<SkiplistLevel> sized to the sampled level) should use a small-size-optimized allocator path since most levels sample low (geometric distribution, mean level ≈ 1.33 at p=1/4).

15.8 Edge Cases

  • LPOP key (no count) on a missing key returns nil; LPOP key 5 on a missing key returns an empty array — not nil (P7's documented-distinction principle in its own worked example).
  • SINTERCARD with a LIMIT 0 means "no limit," not "zero" — a common off-by-one-in-semantics trap.
  • ZADD on a key holding a non-zset type returns WRONGTYPE, not a silent overwrite.
  • Two connections BLPOP-blocked on the same key: unblock order must be FIFO by block time, not arbitrary hashmap iteration order.

15.9 Failure Analysis

A skiplist span corruption is silent (I13) — ZSCORE still works, only ZRANK/ZRANGE degrade, which is exactly the kind of partial failure that escapes a shallow smoke test. Detection: the differential-fixture CI gate (§15.4) is the only reliable catch; a production instance without that gate would surface this as "leaderboard ranks look wrong" support tickets weeks later. Recovery: rebuild the skiplist from the parallel hashtable (Hashtable<Bytes,f64>) — the hashtable is never subject to the same span-corruption class, so it is the recovery source of truth.

15.10 Operational Notes

OBJECT ENCODING on any of these four types is a supported, load-bearing introspection surface — operators use it to detect whether their workload's key-size distribution is drifting into a memory-costlier encoding tier before it becomes a maxmemory incident (cross-reference: Runbook docs/runbooks/memory-pressure.md).

16. Phase 4 — Streams, Geospatial, Bitmaps & HyperLogLog

16.1 Objectives

Ship the four "specialized" data types, each reusing an already-built primitive (radix tree, sorted set, or raw string) rather than inventing a fifth storage strategy.

16.2 Detailed Implementation Steps

  • Stream: an append-only log keyed by <ms>-<seq> entry IDs, encoded as a radix tree (crates/store-core/src/radix_tree.rs) of listpack-node leaves — the same structural idea as Redis's rax.c (§5 Reference Implementations), adapted to Rust's borrow rules with unsafe confined to node-link manipulation. Land XADD/XDEL/XLEN/XRANGE/XREVRANGE/XREAD/ XREADGROUP/XGROUP {CREATE|DESTROY|SETID|DELCONSUMER}/XACK/XPENDING/XCLAIM/ XAUTOCLAIM/XINFO/XTRIM/XSETID. Consumer-group state is per-stream: HashMap<GroupName, Group>, each with a last_delivered_id and a pending-entries-list (PEL) per consumer.
  • Geospatial: implemented entirely in terms of Zset (§15) with 52-bit interleaved-geohash scores — GEOADD → ZADD; GEOPOS → ZSCORE + geohash decode; GEODIST → two ZSCORE + Haversine; GEOSEARCH/GEOSEARCHSTORE → ZRANGEBYSCORE over a bounding-box of geohash ranges, then a post-filter pass (the boundary-condition Pitfall in §16.6).
  • Bitmap: a string viewed as a bit array — no new storage type. Land SETBIT/GETBIT/BITCOUNT (BYTE/BIT range modes)/BITPOS/BITOP {AND|OR|XOR|NOT}/BITFIELD (GET/SET/INCRBY/ OVERFLOW {WRAP|SAT|FAIL}). Popcount via the platform intrinsic (POPCNT on x86, vcnt_u8 on ARM).
  • HyperLogLog: probabilistic cardinality estimator (Heule, Nunkesser & Hall 2013, §5 Papers) with Sparse (run-length-encoded registers, most-zero case) and Dense (fixed 12KB array) encodings; conversion at hll-sparse-max-bytes (default 3000), one-way (P3's pattern repeats here). Land PFADD/PFCOUNT (single/multi-key/intersection-via-merge)/PFMERGE. Bias correction in the small-cardinality range and LogLog-Beta correction in the large range, constants from the cited paper.

16.3 Deliverable

crates/store-core/src/{stream,geo,bitmap,hll}.rs ship every command above; conformance/corpora/commands/{stream,geo,bitmap,hll}/* green within the tolerances of §16.5.

16.4 Acceptance Criteria

  • Stream entry-ID monotonicity: XADD <id> with id ≤ current last ID is rejected with the exact documented error text (P1, P7).
  • 100,000 random PFADD insertions produce PFCOUNT within 2% of true cardinality (the 1.04/√m standard error at m=2^14, per Heule et al.).
  • GEOSEARCH ... BYRADIUS 1 m at a boundary point returns the point (no false negative from under-fetching the bounding box).
  • BITFIELD ... OVERFLOW WRAP on i8 at the INT8_MAX + 1 boundary wraps to INT8_MIN, not an error or a truncated value.

16.5 Conformance Fixtures

Fixture Purpose Expected Output

commands/geo/geosearch_boundary.json radius boundary inclusion point included, no false negative
commands/bitmap/bitfield_overflow_wrap.json signed overflow wraparound i8 wraps at INT8_MAX+1

16.6 Pitfalls

  • XADD * field value auto-generates the next ID; an explicit ID ≤ the last one must be rejected, not silently accepted (stream monotonicity is a load-bearing consumer-group invariant, not merely a nicety).
  • Small-radius GEOSEARCH queries must over-fetch the geohash bounding box and post-filter — a tight box trims away valid boundary points (52-bit geohash precision is ≈0.6m at the equator).
  • HLL sparse-to-dense conversion is one-way; a "rebuild from elements" shortcut loses the cardinality estimate the sparse encoding was compressing.
  • BITFIELD OVERFLOW WRAP on signed integers is a classic off-by-one hiding spot — test exactly at the type-width boundary, not just "a large number."

16.7 Performance Concerns

The radix tree's node-link unsafe (§16.2) must be reviewed for the same use-after-free class Rust's ownership model otherwise prevents automatically — this is the one place in store-core where ADR-01's safety guarantee is manually re-established rather than compiler-enforced. Bitmap popcount must dispatch to the platform intrinsic at compile time, not runtime-detect per call.

16.8 Edge Cases

  • XRANGE/XREVRANGE with -/+ special IDs (open-ended range) must not be confused with a literal -1/+1 timestamp.
  • A consumer group's XCLAIM on an entry no longer in any PEL (already ack'd) must be a documented no-op, not an error.
  • BITCOUNT with start > end in BYTE mode returns 0, not an error.
  • GEODIST between a point and itself returns 0, not a floating-point near-zero epsilon issue.

16.9 Failure Analysis

A stream consumer-group's PEL that diverges from the leader on a replica (a replication-ordering bug) causes duplicate or dropped message delivery to consumers — detected via store_commands_total{cmd="xack",status} divergence between leader and replica counts in monitoring; recovery is a full resync of the affected stream's radix tree, not a partial patch (the PEL's internal consistency is not incrementally repairable).

16.10 Operational Notes

PFCOUNT's statistical nature must be documented in docs/api/command-reference.md as non-exact — an operator alerting on exact-match PFCOUNT equality across environments is a known false-alarm source; the 2% tolerance (§16.4) is the number to alert against, not zero-diff.

17. Phase 5 — AOF, RDB & Hybrid Persistence

17.1 Objectives

Ship durability: survive a restart with zero data loss under appendfsync always and ≤ 1s loss under everysec (P4, P8); ship the hybrid RDB-preamble-plus-AOF-tail default (ADR-07).

17.2 Detailed Implementation Steps

  • AOF append: every mutating command re-serializes to its RESP wire form (§8.1's encoder, run in reverse) and appends to the AOF buffer; flush cadence per appendfsync (always/everysec/ no) — everysec flushes from a background task, never blocking the dispatcher (I2, P4).
  • AOF rewrite: since tokio is not fork-safe (a naive unsafe { libc::fork() } deadlocks on the epoll reactor, cited from Silberschatz ch. 3/10, §5 Books), implement copy-on-write at the data-structure level (ADR-21) — the rewrite task acquires an Arc-shared read-only snapshot of every shard's Database; the dispatcher's writes clone the affected sub-tree on first write after the snapshot is taken. The rewrite child iterates every key, emits the minimal command sequence reconstructing it, and concatenates the parent's rewrite-buffer (writes since the snapshot) at the end. A trailing checksum record (blake3, ADR-19) marks completion; the old AOF is never truncated until the new one's checksum validates (§8.8's failure-path example is this exact scenario).
  • RDB writer: iterate every shard/database/key, emit (type_byte, key, TTL, value) tuples in the §8.4 layout, optional gzip (rdbcompression yes), trailing blake3 checksum (ADR-19).
  • RDB loader: inverse of the writer; single-threaded, runs at startup before any connection is accepted (LOADING error returned to any early client, per CommandError::Loading, §11.8).
  • Hybrid format (ADR-07, Redis 7 default): RDB preamble + AOF tail; recovery loads the preamble then replays the tail — combines RDB's load speed with AOF's low data-loss window.
  • save <seconds> <changes> rule evaluation from serverCron at 10Hz; first matching rule triggers BGSAVE.

17.3 Deliverable

A restart-durability test: write 1M keys, kill -9 the process, restart, assert every key present under appendfsync always; a rewrite-under-load test proving the post-rewrite AOF is shorter and the database is unchanged.

17.4 Acceptance Criteria

  • 1M-key kill/restart test: 100% key presence under always; ≤ 1s of the most recent writes lost under everysec (measured by comparing a pre-kill write-timestamp log to post-restart state).
  • AOF rewrite under a sustained 100K writes/sec load for 60s: rewrite completes, post-rewrite AOF is ≥ 10x smaller than pre-rewrite (synthetic high-churn workload), and post-rewrite database state is byte-identical to pre-rewrite state (I4).
  • RDB round-trip (save→load) on a 1GB dataset: byte-identical pre/post state (I5); load completes in ≤ 3s (§4).
  • appendfsync everysec under 100 KQPS for 60s: AOF growth rate tracks the write rate within 5%, and dispatcher p99 latency does not exceed the M5 target (§30) during the flush.

Fixture Purpose Expected Output

17.6 Pitfalls

  • RDB's expire-time field is little-endian milliseconds-since-epoch as u64 — byte-order mistakes here are the easy way to ship a silently-corrupt snapshot.
  • appendfsync everysec does not mean "fsync exactly every second" — it means the dispatcher never waits on the fsync; a synchronous fsync on the dispatcher thread freezes every shard client (I2 violation, cited Rosenthal-class paper: Pillai et al. OSDI 2014, §5 Papers).
  • The COW wrapper (ADR-21) must be transparent to every database read path; a missed call site reads mutated parent state mid-rewrite and corrupts the emitted snapshot.
  • The hybrid tail must be valid AOF standalone — never assume the loader saw the preamble; a corrupt preamble must not corrupt the tail's independent recoverability.

17.7 Performance Concerns

The rewrite's COW clone-on-first-write means write amplification is proportional to how much of the keyspace mutates during the rewrite window — a write-heavy rewrite costs more CPU/memory than a quiescent one; this must be measured and bounded (M6, §30). RDB's optional gzip trades CPU for disk I/O — default off for the in-memory-first use case, operator-tunable.

17.8 Edge Cases

  • A key that expires during the rewrite must be either fully present or fully absent in the rewritten AOF — never half-included (a partial-key state corrupts replay, I4).
  • Process killed mid-fsync (always mode) — the dispatcher must not have acknowledged the write to the client before the fsync completed (I12's ordering guarantee).
  • RDB load encountering an unknown future type byte (forward-compatibility case) — must fail loudly with a versioned error, never silently skip bytes.

17.9 Failure Analysis

An AOF rewrite crash mid-write (§8.8) is the canonical failure this phase defends against: the old AOF is authoritative until the new one's checksum validates, so the blast radius of a rewrite crash is exactly one skipped rewrite attempt, never data loss. Detection: store_aof_rewrite_failures_total (§23.2); forensic artifact: the truncated candidate AOF file is retained (not deleted) for postmortem inspection, per docs/runbooks/aof-rewrite-stall.md.

17.10 Operational Notes

store_aof_size_bytes, store_aof_last_rewrite_seconds, store_rdb_last_save_seconds (§23.2) are the three metrics an operator watches to catch a stalled rewrite or a save-policy misconfiguration before it becomes an incident; the runbook docs/runbooks/aof-rewrite-stall.md is the paired procedure.

18. Phase 6 — Eviction, Expiration Engine & Keyspace Notifications

18.1 Objectives

Wire the delegated eviction algorithm (project 59, P9/ADR-12) and active-expire sampling (project 62) into the dispatcher's hot path without violating I2's no-blocking guarantee; ship keyspace notification fanout (project 60).

18.2 Detailed Implementation Steps

  • Implement the maxmemory watermark check (store-eviction/src/trigger.rs) invoked at the top of every dispatcher iteration; on breach, invoke the delegated Strategy trait (P9) from crates/lru-lfu-cache (project 59) via the store-eviction/src/policy.rs adapter.
  • Wire all eight documented policies (noeviction, allkeys-lru, allkeys-lfu, volatile-lru, volatile-lfu, allkeys-random, volatile-random, volatile-ttl) — the store constructs the candidate pool (keyspace or expires-set per policy), the cache engine picks the eviction target via its own sampling algorithm (candidate-pool approximated-LRU/LFU, matching Redis's own approach).
  • Implement the active-expire cycle (store-expiration/src/active.rs, adapting project 62) driven from serverCron at 10Hz: sample 20 keys with TTLs per iteration, delete expired ones, continue sampling until the expired-rate falls below 25% or the 25ms time budget is exhausted (I2's budget-bounded requirement; I10's replica no-op requirement enforced by checking replica-read-only state before the cycle runs at all).
  • Implement keyspace notifications (store-dispatcher/src/notify.rs, adapting project 60): publish to __keyspace@<db>__:<key> (event name in body) and __keyevent@<db>__:<event> (key name in body), gated by the notify-keyspace-events config string (Ex, AKE, etc.).
  • Implement the 24-bit LRU clock (wraps ~194 days) with explicit modulo-2^24 age computation — a naive subtraction breaks at wrap (Pitfall, §18.6).

18.3 Deliverable

A database that evicts under maxmemory pressure per the configured policy, expires TTL'd keys actively without client reads, and fans out keyspace notifications to subscribers.

18.4 Acceptance Criteria

  • Filling a database to maxmemory + 1KiB under each of the 8 policies produces the exact documented eviction behavior per policy (8 fixtures, one per policy).
  • 100,000 keys with 1s TTL, polled at t=2s: ≥ 95% reaped by the active-expire cycle alone, zero client reads triggering the lazy path (I1's active leg isolated from its lazy leg).
  • A subscriber to __keyevent@0__:expired receives every expiring key's name, in expiration order, within one active-expire cycle interval (100ms at 10Hz).
  • volatile-lru on a database with zero expiring keys returns OOM, never silently falls back to allkeys-lru.

18.6 Pitfalls

  • The 24-bit LRU clock wraps every ~194 days; now - lru must be computed modulo 2^24, not as a naive signed subtraction, or eviction scoring silently inverts near the wrap boundary.
  • The active-expire cycle must yield at its 25ms budget — a cycle holding the dispatcher mutex for 250ms freezes the shard (I2 violation with a very concrete, measurable manifestation).
  • Keyspace notification publish is synchronous inside the command's execution path; a slow subscriber that fills its output buffer must be dropped under client-output-buffer-limit pubsub, per P11/ADR-22 — never let one slow subscriber block a SET.
  • volatile-lru returning OOM on an empty expires-set (not silently falling back to allkeys-lru) is easy to get backwards and easy to miss without the explicit fixture above.

18.7 Performance Concerns

The candidate-pool sampling approach (rather than a globally-precise LRU/LFU) trades eviction precision for O(1)-ish per-eviction cost — precise global LRU would require a full linked-list reordering on every access, an unacceptable per-command tax under P2. The notification fanout must not synchronously serialize the same message N times for N subscribers on the dispatcher thread — offload multi-subscriber fanout to a background task (project 60's own concern, adapted here).

18.8 Edge Cases

  • A key with both an expiring TTL and eviction eligibility — expiration takes precedence over eviction (a key already logically gone should never appear as an eviction candidate).
  • maxmemory 0 (unlimited) must disable the eviction trigger entirely, not evaluate a zero threshold that evicts everything.
  • Two concurrent evictions racing the same shard — cannot happen by construction (I2: one dispatcher, sequential command execution) but the property test still asserts it.

18.9 Failure Analysis

An active-expire cycle that exceeds its time budget under adversarial TTL density (e.g. millions of keys all set to expire at the same millisecond) degrades to a lazy-only expiration mode temporarily — detection via store_expired_keys_total{db} rate dropping while TTL'd key count grows; recovery is automatic once the cycle catches up within its next budget window, no operator action required unless the growth is sustained (escalates to a docs/runbooks/memory-pressure.md procedure).

18.10 Operational Notes

store_evictions_total{policy} and store_expired_keys_total{db} (§23.2) are the two counters that distinguish "the workload legitimately needs more memory" from "the eviction policy is misconfigured" — a dashboard panel plots both against store_memory_used_bytes / store_memory_maxmemory_bytes for the on-call engineer.

19. Phase 7 — Replication (PSYNC2, Partial Resync)

19.1 Objectives

Ship leader-replica replication: a replica connects, performs a full resync via RDB, and transitions to incremental command-stream replication with PSYNC2 partial-resync on reconnect (P5, ADR-08).

19.2 Detailed Implementation Steps

  • Implement the handshake (store-replication/src/handshake.rs): replica sends REPLCONF listening-port <port>, REPLCONF capa eof capa psync2, PSYNC <replid> <offset>; leader responds +FULLRESYNC <replid> <offset>, +CONTINUE, or +CONTINUE <newreplid>.
  • Implement ReplicationBacklog (§11.7) as a fixed-size ring buffer (default 1MiB, repl-backlog-size) with a monotonic logical offset (I6) — every mutating command appended here atomically with its AOF append (I12, same post-execute hook).
  • Implement full resync (store-replication/src/leader.rs): spawn a BGSAVE, buffer replication commands in a per-replica buffer during the transfer, stream the RDB, then ship the buffered commands, then switch to incremental streaming.
  • Implement partial resync: on reconnect, if the replica's offset is still within the backlog window (read_from in §11.7's trait), ship only the gap; if the offset predates the backlog's oldest retained offset, fall back to full resync.
  • Implement replica-read-only (default yes): the dispatcher rejects writes on a replica with CommandError::Readonly; the active-expire cycle is a structural no-op here (I10).
  • Implement REPLCONF ACK <offset> periodic acknowledgment from replica to leader; leader computes min_replica_offset for WAIT/WAITAOF (now un-deferred from §14.2's PhaseDeferred).
  • Implement the secondary replication ID mechanism (PSYNC2's key innovation over PSYNC1): on leader failover, the new leader retains the old leader's replication ID as "secondary" so existing replicas can continue streaming without a full resync (Pitfall §19.7's #1 item).

19.3 Deliverable

A leader + replica pair where the replica converges to identical state after a bulk load, survives a short disconnect via partial resync, and falls back to full resync after a disconnect longer than the backlog window.

19.4 Acceptance Criteria

  • Leader populated with 100K keys; replica started fresh; replica converges to identical state within 5s (measured via a checksum comparison, I4/I5's determinism guarantee extended across the wire).
  • Replica disconnected 10s, 1,000 writes occur during the disconnect, replica reconnects: partial resync used (no full RDB transfer — asserted via store_replication_offset continuity, not a fresh FULLRESYNC reply).
  • Replica disconnected 10 minutes (exceeds the default 1MiB backlog at any realistic write rate, per §34's derivation), writes occur, replica reconnects: falls back to full resync, and still converges to identical state.
  • WAIT 1 100 blocks until at least 1 replica acknowledges the preceding write, or returns after 100ms — both paths tested explicitly.

Fixture Purpose Expected Output

replication/partial_resync_short_gap.json 10s disconnect, in-window +CONTINUE, no RDB transfer
replication/full_resync_fallback_long_gap.json 10min disconnect, out-of-window +FULLRESYNC, converges

19.6 Pitfalls

  • Omitting the secondary replication ID means every failover forces every surviving replica to full-resync — the single highest-cost mistake in this phase (PSYNC2's entire value proposition is avoiding exactly this).
  • The backlog ring buffer's byte-offset wraparound (every size bytes) must not be confused with the logical offset's u64 wraparound (effectively never, at realistic write rates) — conflating the two ships corrupted replicated commands.
  • Replication is asynchronous by default; a write acknowledged to the client can be lost if the leader crashes before replicating — this is why WAIT exists, and why the conformance suite exercises the absence of a WAIT call as an explicitly-accepted risk, not a bug.
  • A replica must not append replicated commands to its own AOF a second time during a full resync — doing so doubles write amplification (a subtle double-count that only shows up as unexpectedly fast AOF growth on replicas).

19.7 Performance Concerns

Backlog size directly trades memory for disconnect tolerance (derived formulaically in §34); too small and short blips become expensive full resyncs (M8 target, §30). The full-resync RDB transfer competes for the same network path as normal client traffic — rate-limiting or a dedicated replication network path is an operator-tunable mitigation, not built into Phase 0.

19.8 Edge Cases

  • Two replicas reconnecting simultaneously after the same leader-side blip — each computes its own gap from the shared backlog independently; no cross-replica coordination is needed (the backlog is read-only from any replica's perspective).
  • A replica that never sends REPLCONF ACK (network issue, not disconnect) — min_replica_offset must not include it after a configurable ack-staleness timeout, or WAIT blocks forever.
  • Leader BGSAVE failing mid-full-resync (disk full) — the replica's handshake must time out and retry, not hang indefinitely.

19.9 Failure Analysis

A replica falling permanently behind (backlog perpetually insufficient for its network path) degrades to continuous full-resync cycles — each one itself competing for the network path that caused the lag, a self-reinforcing failure mode. Detection: store_replication_lag_seconds{replica_id} trending upward across repeated FULLRESYNC events (visible as a sawtooth in store_replication_offset per replica). Recovery: operator increases repl-backlog-size or investigates the network path per docs/runbooks/replica-disconnect.md.

19.10 Operational Notes

store_replication_offset and store_replication_lag_seconds{replica_id} (§23.2) are the two metrics that answer "is my replica caught up" without needing to inspect the backlog internals; the runbook docs/runbooks/replica-disconnect.md walks the on-call engineer through diagnosing a lagging replica using exactly these two signals.

20. Phase 8 — Cluster Mode (Hash Slots, Gossip, MOVED/ASK)

20.1 Objectives

Ship cluster mode: a multi-node deployment serves a client, redistributes slots live, and survives a single-node failure via replica election (P6, ADR-09).

20.2 Detailed Implementation Steps

  • Implement SlotMap (§11.6) with slots 0..16383 assigned via CLUSTER ADDSLOTS/ ADDSLOTSRANGE or the redis-cli --cluster create workflow; the slot map is the sole routing source of truth (P6, I7/I8).
  • Implement slot_for (§11.6's Cluster trait): CRC16/XMODEM (ADR-18) over the key, or over the {...} hash-tag substring if present — first {...} pair wins, not a greedy regex match (a documented Pitfall, §20.9).
  • Implement gossip (store-cluster/src/gossip_adapter.rs, adapting project 72, cited per §5): each node periodically pings N random peers over the cluster-bus port (client port + 10000); each ping/pong carries the node's view (slot ownership, health, replication offsets, config epoch); views merge, converging eventually (I7, cite Chandra & Toueg 1996 for the underlying failure-detector theory, §5 Papers).
  • Implement MOVED redirection (§11.6's RedirectKind): a node receiving a command for a slot it does not own replies -MOVED <slot> <ip:port>; the client updates its slot cache and retries.
  • Implement ASK redirection for live slot migration: source node holds the slot MIGRATING, destination holds it IMPORTING; a key still on the source is served normally, an absent one returns -ASK <slot> <ip:port>; the client must send ASKING before retrying against the destination — this is the mechanism that keeps a multi-key transaction correct mid-migration (P6, cited in §2's "What Mastery Looks Like").
  • Implement epoch-based failover election (store-cluster/src/failover.rs): on leader unreachability (no PONG for cluster-node-timeout, default 15s), replicas increment currentEpoch, broadcast FAILOVER_AUTH_REQUEST, other leaders vote; majority-vote replica promotes itself and gossips new slot ownership. Document the Raft alternative (Ongaro & Ousterhout 2014, §5 Papers) in docs/architecture/ without adopting it (Redis Cluster's own variant is locked, ADR-09).
  • Implement the full CLUSTER admin surface (§20's command list) including a cluster fix subcommand (tools/cluster-fix/) for orphan-key recovery after a crashed migration.

20.3 Deliverable

A 3-node cluster created via redis-cli --cluster create, serving 100K keys, that redistributes a subset of slots live under load and survives a single leader kill via replica promotion.

20.4 Acceptance Criteria

  • 3-node cluster, 100K keys loaded: every key reachable from any node (via direct hit or MOVED redirection), zero lookup failures.
  • Slot migration of a live-loaded slot: every client receives the correct MOVED/ASK sequence; zero keys lost; zero keys duplicated (verified via a pre/post key-count and checksum diff).
  • Leader kill: a replica promotes within cluster-node-timeout + election round-trip (≤ 20s per §4); slot ownership migrates; clients receive MOVED to the new owner.
  • CLUSTER NODES output is exactly 9 whitespace-separated fields per line, byte-identical to a recorded real-Redis-Cluster trace for the same topology (P1).

20.6 Pitfalls

  • Hash-tag extraction is a substring match for the first {...} pair, not a greedy regex — keys like user:{a}:{b} must hash on a.
  • The cluster-bus port (client port + 10000) misconfiguration causes silent gossip failure — the cluster never converges and there is no loud error, only a slowly-apparent "some nodes don't see each other" symptom.
  • A node crashing mid-migration leaves orphan keys on the source — cluster fix must recover this; a cluster without that tool has no path back to a clean slot map (I8 violation without recovery).
  • CLUSTER NODES' whitespace-sensitive 9-field format breaks every real client parser on a single extra space — this is not cosmetic, it is wire compatibility (P1).
  • The failover election can spuriously elect two leaders under an adversarial network-partition shape; cluster-require-full-coverage and cluster-allow-replica-migration bound but do not eliminate this — document the residual risk in the runbook, do not claim it is solved.

20.7 Performance Concerns

Gossip payload size grows with cluster size (each ping/pong carries a view of every known node); at very large node counts this becomes the practical ceiling on cluster size before gossip convergence time itself becomes the bottleneck (§31 Scalability Analysis addresses this concretely). Slot migration throughput (M9, §30) is bounded by the rate at which keys can be DUMPed/RESTOREd across the wire without starving normal traffic on either node.

20.8 Edge Cases

  • A client that caches a stale slot map and repeatedly hits the wrong node — must receive MOVED every time, never silently mis-serve (P7).
  • CLUSTER SETSLOT ... STABLE clearing a stuck migration state — must be idempotent (calling it twice is a no-op the second time, not an error).
  • A multi-key command whose keys hash to different slots — rejected with CROSSSLOT, never partially executed.
  • Config-epoch collision (two nodes claim the same epoch after a network partition heals) — the higher node-ID wins as a documented tiebreak (matching real Redis Cluster's rule).

20.9 Failure Analysis

A stuck slot migration (source crashes with the slot half-migrated) leaves the slot map inconsistent across gossip views — detection via CLUSTER SLOTS disagreement across nodes in the conformance/ops tooling; recovery is the cluster fix admin subcommand, which walks the orphaned keys and re-establishes a single consistent owner per slot (I8's recovery path, concretely). Blast radius: only the affected slot(s), not the whole cluster — a key design property of the 16,384-slot granularity versus a coarser partitioning scheme.

20.10 Operational Notes

store_cluster_slots_assigned and store_cluster_known_nodes (§23.2) are the two gauges that answer "is my cluster's view of itself complete and converged"; the runbook docs/runbooks/slot-migration-stuck.md pairs with the cluster fix tool for the on-call procedure.

21. Phase 9 — ACL, AUTH, TLS & Command Renaming

21.1 Objectives

Wire the security surface: ACL rule evaluation (P12's fail-closed principle), AUTH/HELLO AUTH, TLS transport (project 50), and command renaming.

21.2 Detailed Implementation Steps

  • Implement the ACL DSL (store-acl/src/rule.rs): key patterns (~prefix:*), pub/sub channel patterns (&channel:*), command/category grants (+@read, -@dangerous, +SET, -FLUSHDB), authentication method (password/no-pass/certificate), enabled flag. Evaluation is order- sensitive — rules apply left to right, so +@all -@dangerous differs from -@dangerous +@all (the latter's +@all re-enables everything, a documented trap cited in §2's "What Mastery Looks Like").
  • Implement the ACL check as the dispatcher's mandatory pre-execute gate (acl.check(user, cmd, args)) — fail-closed on any ambiguity per P12: a user with no matching rule for a command is denied, never default-allowed.
  • Implement AUTH [username] password (legacy) and HELLO 3 AUTH user pass (modern) entry points; both set Connection::auth_state (§11.3).
  • Implement TLS via the project-50 crate adapter (store-tls/src/listener.rs, ADR-11): separate tls-port, or TLS-only via port 0 tls-port 6379; mutual TLS maps a verified client certificate's CN to an ACL username.
  • Implement command renaming (rename-command FLUSHALL secret-flush or "" to disable) — the dispatcher's command-lookup table is keyed by the effective (possibly renamed) name; AOF entries always reference the canonical name regardless of the active rename (a documented Pitfall, §21.6).
  • Land the full ACL admin surface: LIST, WHOAMI, CAT, SETUSER, GETUSER, DELUSER, USERS, LOG, SAVE, LOAD.

21.3 Deliverable

A store where a restricted ACL user cannot exceed its granted key patterns/commands, TLS-enabled connections succeed with a real certificate, and command renaming/disabling is enforced at the dispatcher.

21.4 Acceptance Criteria

  • A user with +@read ~prefix:* -@write fixture: GET prefix:x succeeds, SET prefix:x v fails NOPERM, GET other:x fails NOPERM — all three asserted in one fixture.
  • redis-cli --tls --cert ... --key ... against a TLS-enabled store succeeds; a client presenting no certificate under tls-auth-clients yes is rejected.
  • rename-command FLUSHALL secret-flush: FLUSHALL returns ERR unknown command; secret-flush executes the original semantics.
  • ACL rule-order sensitivity: +@all -@dangerous and -@dangerous +@all produce different effective permission sets, both asserted explicitly (P12/§2).

21.5 Conformance Fixtures

21.6 Pitfalls

  • ACL rule order changes the effective permission set — -@dangerous +@all is a no-op on the deny, a classic misconfiguration that grants far more than intended (P12).
  • TLS handshake latency is measurable overhead — benchmark it explicitly (§21.7) rather than assume it is negligible at the M-table's latency targets.
  • Command renaming applies only to dispatcher lookup, never to AOF encoding — a misunderstanding here causes AOF-replay failures after a rename change is later reverted or altered.
  • Fail-open on ACL ambiguity (the wrong default) is the root-cause class behind most real-world ACL privilege-escalation incidents — P12 exists specifically to foreclose this class.

21.7 Performance Concerns

TLS adds a handshake-latency cost amortized over the connection's lifetime (not per-command); the benchmark suite (benchmarks/) measures this overhead separately from steady-state command latency so the M5 target is not conflated with one-time connection cost. ACL evaluation must be O(rules) per command, not O(rules × keyspace) — pattern matching against the command's keys, not a keyspace scan.

21.8 Edge Cases

  • A user disabled mid-session (ACL SETUSER x off while x has open connections) — existing connections must be rejected on their next command, not retroactively killed mid-command. execution.
  • AUTH on a connection where no password is configured (nopass) — must succeed without error, matching documented default-user behavior.
  • Renaming a command to a name that collides with an existing command — must be a startup configuration error, not a silent overwrite of the existing command.

21.9 Failure Analysis

A fail-open ACL bug (permission granted when it should be denied) is a security incident, not a correctness bug — detection requires an explicit audit log (store-acl/src/audit.rs) recording every NOPERM and every granted-but-notable command (e.g. FLUSHALL by a non-admin user), reviewed via ACL LOG. Recovery: revoke the offending rule immediately; the audit log is the forensic artifact establishing blast radius (what was actually accessed during the misconfiguration window).

21.10 Operational Notes

ACL LIST/ACL GETUSER must always reflect the effective, fully-resolved rule set, not just the configured deltas (P14) — an operator debugging "why can this user do X" must never have to mentally replay the rule-application order themselves.

22. Phase 10 — Transactions, Pub/Sub, Scripting & Modules

22.1 Objectives

Ship the four cross-cutting features a Redis-compatible server must support: MULTI/EXEC/ WATCH, pub/sub, Lua scripting, and the module ABI placeholder.

22.2 Detailed Implementation Steps

  • Implement MULTI/EXEC/WATCH/DISCARD (store-dispatcher/src/multi.rs): MULTI switches Connection::multi_state to queueing (validated-but-not-executed, per Phase 1's stub); WATCH key... registers keys in Connection::watch_set; any watched-key mutation before EXEC sets DIRTY_CAS (§11.3's ConnectionFlags), aborting EXEC with nil (I9, the optimistic- concurrency-control rule from Kleppmann ch. 9, §5 Books).
  • Implement pub/sub (store-dispatcher/src/pubsub.rs, adapting project 60): SUBSCRIBE/ UNSUBSCRIBE/PSUBSCRIBE/PUNSUBSCRIBE/PUBLISH/PUBSUB {CHANNELS|NUMSUB|NUMPAT} plus the cluster shard-pubsub variants (SPUBLISH/SSUBSCRIBE/SUNSUBSCRIBE/PUBSUB SHARDCHANNELS/ SHARDNUMSUB) — subscription state lives outside the keyspace, per-connection only.
  • Implement scripting (store-script/src/interpreter.rs, mlua against Lua 5.1, ADR-13): EVAL/EVALSHA expose KEYS[]/ARGV[]; redis.call(...) re-enters the dispatcher via a sub-dispatch path with NOSCRIPT-flagged commands rejected (recursion blocked — a naive implementation allowing recursive redis.call deadlocks the dispatcher, Pitfall §22.6). SCRIPT LOAD/EXISTS/FLUSH manage the HashMap<Sha1Hash, ScriptBody> cache. Implement redis.replicate_commands() to force script effects into the AOF/replication stream as discrete commands rather than the raw script text (avoids script-replay divergence on replicas, since Lua's PRNG and the store's PRNG are distinct sources — P8's determinism principle applied here).
  • Implement the module ABI placeholder (store-modules/src/abi.rs): extern "C"/repr(C) surface (ADR-14), one in-tree example module registering MYMODULE.HELLO; the dispatcher's command lookup falls back to the module registry when a name is not in the built-in table.

22.3 Deliverable

MULTI/SET/SET/EXEC commits atomically; a WATCH-then-concurrent-mutation aborts EXEC with nil; an EVAL script executes redis.call('SET', ...); the example module's MYMODULE.HELLO command runs end to end.

22.4 Acceptance Criteria

  • MULTI/two SETs/EXEC: both writes land atomically, visible together to a concurrent reader (never one without the other).
  • WATCH key/MULTI/SET key v/EXEC with a concurrent mutation of key between WATCH and EXEC from another connection: EXEC returns nil (I9), 1,000-trial property test, zero false negatives.
  • EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 foo bar: key foo is set to bar.
  • The example module's MYMODULE.HELLO command: registered at startup, invocable via the dispatcher's fallback lookup, returns its documented fixed reply.

Fixture Purpose Expected Output

22.6 Pitfalls

  • Transactions do not roll back partial failures — a SET/LPUSH transaction where the second command fails (wrong type) leaves the first command's effect visible; this matches Redis's own documented behavior and must not be "fixed" (P1, P7).
  • WATCH followed by EXEC without an intervening MULTI is a parse error, not a silent no-op.
  • Pub/sub delivery is best-effort; a slow subscriber is dropped, not blocked (P11/ADR-22) — this must be documented in the runbook, not discovered by an operator in production.
  • Lua's number type is double-precision float; integer-valued scripts round-tripping through tonumber() can drift — redis.replicate_commands() sidesteps script-replay divergence but does not fix script-internal float precision, a separate concern operators must be warned about.
  • Allowing recursive redis.call() invocations deadlocks the dispatcher (I2) — the recursion guard is not optional polish, it is a correctness requirement.

22.7 Performance Concerns

Pub/sub fan-out to many subscribers on one channel must not serialize the message N times on the dispatcher thread before returning control — offload multi-subscriber fanout to a background task (the same concern as §18.7, shared implementation). Script execution runs inline on the dispatcher (no async yield mid-script, since Lua state is not Send across an await point) — long-running scripts are therefore a direct latency-tail risk, flagged in SLOWLOG (§23.5).

22.8 Edge Cases

  • A script that calls redis.call() on a command the connection's ACL would otherwise deny — must still be denied inside the script (ACL applies to the sub-dispatch path too, not bypassed by scripting).
  • DISCARD without a preceding MULTI — documented error, not a silent no-op.
  • A module command name colliding with a built-in command — the built-in wins; the module command is rejected at load time with a loud error, never silently shadowed.
  • EVALSHA for a SHA not present in the script cache — documented NOSCRIPT error prompting the client to EVAL the full script instead.

22.9 Failure Analysis

A script that runs unexpectedly long (an accidental infinite loop, or an O(N²) algorithm over a large collection) blocks the entire shard for its duration (I2's tradeoff made concrete) — detection via SLOWLOG/LATENCY (§23.4–23.5) and the BUSY error surfaced to other clients attempting a write during a long script; recovery is SCRIPT KILL (read-only scripts only) or a process restart for a write-performing runaway script — this asymmetry (kill vs restart) must be documented plainly, not glossed over.

22.10 Operational Notes

store_commands_total{cmd="eval",status} alongside SLOWLOG entries for any script exceeding slowlog-log-slower-than gives the operator the same visibility into script cost as into any built-in command — scripting must not be a monitoring blind spot relative to the rest of the command surface (P13).

  • A metrics endpoint that itself blocks the dispatcher to compute a gauge (e.g. iterating the whole keyspace for store_keys_total on every scrape) violates I2 — maintain running counters incrementally, never compute them by full scan at scrape time.

23.7 Performance Concerns

Every additional instrumentation point (trace span, metric increment) on the dispatcher hot path must be accounted for in the M1–M5 latency/throughput budget (§30) — P13's "observability is not optional" principle is explicitly traded off here against the M-table's numeric targets, and the benchmark suite is the mechanism that keeps that tradeoff honest rather than aspirational.

23.8 Edge Cases

  • Scraping :9121/metrics during an active BGSAVE/AOF-rewrite — must not block or skew the scrape; metrics are updated incrementally, independent of background-task scheduling.
  • SLOWLOG RESET racing a concurrent slow command being recorded — must not lose the in-flight entry or corrupt the ring buffer.
  • A trace exporter that is unreachable (OTLP endpoint down) — must not block command execution; spans queue and drop under backpressure, never synchronously block on export (P11 applied to tracing specifically).

23.9 Failure Analysis

An observability subsystem bug (a metric that silently stops incrementing, a trace exporter that silently drops all spans) is uniquely dangerous because it degrades detectability of every other failure mode in this document — detection requires a meta-check: a synthetic canary workload run continuously, with an alert on the canary's own expected metrics going stale (a "who watches the watcher" pattern). Recovery: restart the affected background exporter/aggregator task; the dispatcher itself is never blocked by this class of failure (P13's isolation guarantee).

23.10 Operational Notes

  • Named runbooks: triage.md (general first-response), aof-rewrite-stall.md (FM-1), replica-disconnect.md (FM-3), slot-migration-stuck.md (FM-4), memory-pressure.md (FM-7, T3).
  • Backup/restore: RDB snapshots are the backup artifact; BGSAVE on a schedule (the save rule table, §17.2) plus operator-triggered snapshots before risky maintenance; restore is the RDB loader (§17.4) pointed at a chosen snapshot file.
  • Deployment topology: one binary per node; standalone (single node), leader-replica (Phase 7), or cluster (Phase 8) — the same binary, config-selected topology.
  • Canary/rolling-upgrade: a new binary version joins as a replica first (Phase 7's full-resync path validates compatibility before promotion); cluster-mode rolling upgrade replaces one node at a time, relying on gossip convergence (I7) to re-establish slot ownership after each replacement.
  • Rollback: a failed upgrade rolls back by restoring the prior binary and replaying its last compatible AOF/RDB — version compatibility rules are in §27.
  • Migration strategy: schema-free (key-value), so "migration" here means config-format migration (ADR-20) and RDB-version migration (§27), not a data schema migration in the relational sense.

27. Compatibility & Versioning

  • Wire compatibility: RESP2/RESP3 are locked, versioned protocols (P1); this engine never introduces a wire-breaking change to either without a major version bump and a documented migration note in CHANGELOG.md.
  • Storage compatibility: the RDB format version is stamped in every snapshot (§8.4); a loader encountering a newer version than it understands fails loudly (§17.8's edge case), never silently truncates.
  • Schema evolution: none in the relational sense — the data model is key-value with typed values; "evolution" is scoped to encoding changes (§8.5), which are always additive (a new compact encoding can be introduced without breaking the full encoding it complements).
  • API stability: the command surface follows Redis's own documented stability — commands are never removed within a major version; new commands are additive.
  • Deprecation policy: a deprecated command (e.g. GETSET vs SET…GET, §14.6) is retained and delegates to its replacement's code path indefinitely — never removed, per P1's wire-compat contract extending to the whole documented surface, not just the byte format.
  • SemVer policy: MAJOR.MINOR.PATCH; MAJOR bumps only on a wire or on-disk format break; MINOR adds commands/features; PATCH is bug fixes only, gated by the conformance suite (§28) showing zero regression.
  • Rolling-upgrade guarantees: any two adjacent MINOR versions can replicate with each other (a replica one MINOR version behind or ahead of its leader must still complete a successful PSYNC2 handshake) — this is the concrete guarantee that makes the canary strategy in §26 safe.

28. Testing & Verification Strategy

  • Unit tests: per-crate, covering every encoding's conversion threshold (§8.5) and every command's documented edge case (§12–§23's N.8 sections).
  • Integration tests: cross-crate scenarios — a full store-server process driven via store-client, covering persistence-then-restart (§17), replication convergence (§19), and cluster redirection (§20).
  • Property-based tests: encoding-conversion preservation (§15.4), SCAN cursor completeness under rehash (§14.4), WATCH/EXEC abort correctness (§22.4, I9) — each running ≥ 100 randomized trials in CI.
  • Differential tests: the skiplist vs BTreeMap reference (§15.4, I13); the RESP encoder vs recorded real-Redis wire traces (P1).
  • Fuzzing: cargo-fuzz/libFuzzer (ADR-24) over the RESP parser, AOF loader, RDB loader (fuzz/fuzz_targets/); gated at 30 days continuous before the Sealed milestone (M12, §30).
  • Chaos / fault injection: the deterministic simulator (tests/sim/, §7) drives randomized command sequences with injected faults (killed shards, truncated AOF, dropped gossip messages) matching every class in §25.
  • Deterministic replay: AOF/replication trace replay (tools/trace-replay/) reconstructs a production incident's exact command sequence against a test instance for root-cause analysis (P8's determinism principle, operationalized).
  • Soak testing: 24-hour continuous run under synthetic load, asserting zero unhandled exceptions and zero unbounded memory growth (M11, §30).
  • Conformance suite: the binding gate (§23.2/§28's central mechanism) — every command, every persistence path, every replication/cluster fixture, run via conformance/runner, blocking merge on any Pass→Fail regression (conformance.yml).
  • Performance-regression gating: the M-table (§30) thresholds are asserted in CI via the benchmark suite; a regression below any M-target blocks release (§29).
  • Tie-back to invariants: every invariant in §7 has at least one property test, differential test, or simulator assertion listed above — the Testing Strategy is the operational implementation of §7's debugging methodology.

29. Build & Release Engineering

  • Reproducible builds: Cargo.lock checked in; CI builds from a pinned Rust toolchain version (rust-toolchain.toml); Docker builds are multi-stage with a pinned base image digest, not a floating tag.
  • Artifact signing: release binaries are signed (cosign-style detached signature) and the signature is published alongside the binary in the GitHub release.
  • SBOM: generated per release via cargo-cyclonedx, published alongside the binary — every dependency's license and version is auditable (ties to ADR-17's license posture).
  • Release channels: stable (tagged releases only), nightly (main-branch builds, not for production).
  • CI/CD topology: .github/workflows/ (§10) — ci.yml gates every push; conformance.yml, persistence.yml, replication.yml, cluster.yml gate merge to main; security.yml runs cargo-audit/cargo-deny/fuzz-smoke on every push; release.yml runs only on a version tag. Note: Makefile's release-check target (stubbed in Phase 0, §12.2) is what release.yml invokes, tying the manual and CI-gated release paths to one source of truth.
  • Version stamping: the binary embeds its build's git SHA, build timestamp, and semver version, surfaced via INFO server (§23.2) — an operator can always identify exactly what is running.
  • Provenance/attestation: GitHub Actions' built-in artifact attestation records the workflow run that produced each release binary, closing the supply-chain gap between source and artifact.
  • Dependency auditing: cargo-deny enforces the license allowlist (Apache-2.0-compatible dependencies only, per ADR-17) and flags any advisory from the RustSec database; security.yml fails the build on any high-severity unaddressed advisory.
  • The Sealed gate: a release is only tagged Sealed (the highest release confidence tier) once M11 (24-hour soak) and M12 (30-day fuzzing) both pass (§30) — this is a release-engineering gate, not merely a testing checkbox, because it determines what release.yml is permitted to publish to the stable channel.

31. Scalability Analysis

Stays constant: per-command dispatch cost within a shard (O(1) hashtable lookup, amortized O(1) Dict access even mid-rehash, §11.2); RESP parse/encode cost per frame (O(frame size), independent of database size).

Grows, with Big-O: memory with key count (O(N) — the fundamental in-memory constraint, §4); gossip payload with node count (O(nodes known), §20.7, bounded practically before convergence time itself becomes the bottleneck, §34 item 4); AOF rewrite COW cost with write rate during the rewrite window (§17.7, proportional to keyspace churn, not keyspace size); skiplist operations O(log N) per key (Pugh 1990) — the reason sorted sets do not degrade linearly as they grow.

Named bottlenecks, in order: (1) physical core count — throughput ceiling is shard count × per-shard throughput, never beyond available cores (P2, §4); (2) network bandwidth on the replication/cluster-bus path during full resync or slot migration (§19.7, §20.7); (3) gossip convergence time at large node counts (§34 item 4); (4) single-key hot-spot contention — a single extremely hot key still serializes through one shard's one dispatcher, the one scenario ADR-05's rejected per-key lock striping alternative would address.

Horizontal scaling: cluster mode (Phase 8) — add nodes, migrate slots; bounded by gossip convergence time and migration bandwidth, not by an architectural ceiling.

Vertical scaling: add shards up to core count (ADR-06's 1–64 range) and more RAM up to the maxmemory ceiling (§4); beyond 64 cores, cluster mode (horizontal) is the only remaining lever.

Sharding/partitioning: intra-node sharding (P2) is orthogonal to inter-node partitioning (cluster hash slots, P6) — the former is a concurrency mechanism, the latter is a capacity mechanism; conflating them is a common design-review mistake (cross-reference: HQ3, §35).

Coordination overhead: zero for intra-node shards (no cross-shard coordination in the base design); gossip-based for inter-node cluster state (eventually consistent, I7) — there is no strongly-consistent coordination service in this design by choice (ADR-10), which is itself the scalability lever (no single coordinator to bottleneck) and the scalability cost (no instant convergence guarantee).

Practical ceiling and levers beyond it: a single cluster's practical ceiling is set by gossip convergence time growing with node count (§34 item 4) well before the 16,384 slot count itself becomes limiting (16,384 slots comfortably covers clusters far larger than gossip convergence would tolerate in practice). The lever beyond that ceiling is federation — multiple independent clusters behind an application-level routing layer — which is explicitly out of scope here (PhaseDeferred("Deferred Features Register")) and is the real-world path systems like this one take past a few hundred nodes.

32. Mental Models & First Principles

  1. MM1 — A shard is a single-threaded event loop; concurrency is a property of the cluster of shards, not of any one shard. Predicts the throughput ceiling is shard-count × per-shard throughput, never more. Bug class without it: reintroducing locks "for safety" inside a shard, silently re-admitting the entire reader-writer-lock class P2 exists to remove. Resolving: §3, Phase 1 (§13).
  2. MM2 — Encoding is data layout, chosen once, converted once. Predicts memory footprint given a workload's key-size distribution. Bug class without it: encoding thrash (converting back and forth) or a conversion check that misses the byte-size dimension (§15.6). Resolving: §8.5, Phase 3 (§15).
  3. MM3 — A command log is the same source of truth for durability, replication, and time-travel debugging. Predicts that AOF-replay-based root-causing works uniformly. Bug class without it: a second, independently-encoded replication path that can diverge from what AOF persists. Resolving: Phase 5 (§17), Phase 7 (§19).
  4. MM4 — A slot map is a partition function frozen at a grain coarse enough to gossip cheaply. Predicts migration granularity and gossip-payload growth with node count. Bug class without it: assuming re-partitioning is free, or that slot count should scale with node count. Resolving: Phase 8 (§20), §31.
  5. MM5 — Backpressure is a policy decision, not an emergent property. Predicts you must explicitly choose what breaks under overload (drop the slow client, never let the buffer grow unbounded). Bug class without it: FM-6's slow-consumer OOM. Resolving: P11 (§6), §18.7, §25.
  6. MM6 — Determinism is what makes distributed debugging tractable. Predicts that replaying a recorded command log reproduces a production incident exactly. Bug class without it: unseeded randomness (SPOP, SRANDMEMBER) diverging silently between a leader and its own replayed history. Resolving: P8 (§6), Phase 5 (§17), Phase 7 (§19).
  7. MM7 — Copy-on-write trades memory for time by deferring a snapshot's cost to the first mutation after it. Predicts rewrite memory cost is workload-shaped (proportional to churn during the rewrite window), not a fixed function of dataset size. Resolving: §17.2, §17.7.
  8. MM8 — A gossip protocol converges eventually, never instantly; every consumer of cluster state must tolerate a stale view. Predicts a burst of MOVED redirections immediately after any topology change, tapering as gossip converges. Bug class without it: a client or an internal subsystem that assumes CLUSTER SLOTS is always immediately authoritative. Resolving: §20.3, I7.

Redis made the single-threaded-dispatcher choice in 2009 and has only partially revisited it (I/O threads since 6.0 still funnel command execution through one thread); it wins wherever wire-protocol and ecosystem compatibility matter more than raw single-node throughput — which is most production deployments, and why this project mirrors the choice (ADR-05).

Memcached rejected almost every feature this project ships (no persistence, no replication, no rich data types) in exchange for the simplest possible slab-allocated cache; it wins wherever the workload is genuinely cache-only and operational simplicity matters more than feature breadth (§5 Reference Implementations, Nishtala et al. 2013).

KeyDB kept Redis's data model and wire protocol but forked the dispatcher to be multi-threaded with a global-lock fallback for cross-thread write conflicts; it wins on read-heavy multi-core workloads where the lock-fallback cost is rarely paid, and loses this project's consideration because that fallback re-admits the lock-contention bug class P2 was chosen to avoid (ADR-06, Alternative Architecture 1, §36).

Dragonfly rejected tokio/threads-plus-async entirely in favor of io_uring and a from-scratch Dash hash table; it wins on raw single-node throughput on Linux, at the cost of the portability and ecosystem this project's tokio choice (ADR-02) preserves (§36 Alternative 1).

Aerospike rejected "pure in-memory" itself, keeping only the index in RAM and data on flash/SSD; it wins at dataset sizes where RAM cost dominates the economics and where flash's durability characteristics obviate a separate AOF/RDB story — a fundamentally different point in the design space from this project's in-memory-first non-goal boundary (§1, §36 Alternative 2).

34. Back-of-Envelope Capacity Model

  1. Replication backlog sizing. B = W × T (backlog bytes = write-byte-rate × disconnect- tolerance seconds). At the default W ≈ 100 KB/s and T = 10s: B ≈ 1 MB — matches the default repl-backlog-size (§4, §19.4). At the M4 aggregate write target (3,000,000 ops/s × ~150 B/command ≈ 450 MB/s), tolerating even a 3s blip needs B ≈ 1.35 GB — a concrete case for operators running near M4 to override the 1 MiB default by three orders of magnitude.
  2. maxmemory headroom for COW rewrite. Worst case, 100% of keys mutate during a rewrite window, doubling live-dataset memory transiently. To avoid an OOM during rewrite: physical RAM ≥ 2 × maxmemory. At the default 4 GiB maxmemory (§4): provision ≥ 8 GiB physical RAM per node.
  3. FD budget. FDs = maxclients + shard_internal + cluster_bus_reserve = 10,000 + 64 + 4,096 = 14,160 minimum ulimit -n (§4's FD-budget row, computed exactly).
  4. Gossip payload size. Each ping/pong carries ≈100 bytes per known node. At N=100 nodes: payload ≈ 10 KB per message. At a 10-peer fanout and 1 round/sec: per-node bus bandwidth ≈ 10 × 10 KB = 100 KB/s — the number that, extrapolated to N=1,000+ nodes, drives §31's practical cluster-size ceiling well before the 16,384-slot limit itself binds.
  5. Aggregate throughput ceiling. Throughput_max = cores × M1 (per-shard GET throughput). At 64 cores (§4's max shard count) × 1,000,000 ops/s (M1) = 64,000,000 ops/s theoretical ceiling — compare to the M2 target of 5,000,000 ops/s at 16 shards, showing 12.8× headroom before the core ceiling binds.
  6. AOF growth rate and rewrite deadline. Growth = W × S (write rate × avg command size). At W = 100,000 writes/s, S = 150 B: growth ≈ 15 MB/s. Given disk capacity D and live dataset size L, the rewrite must complete within (D − L) / (W × S) seconds to avoid filling the disk — at D − L = 50 GB headroom: rewrite deadline ≈ 3,333 s (≈ 55 minutes), comfortably above the M6 rewrite-duration target under realistic dataset sizes.
  7. RDB save time. 10 GiB ÷ 500 MB/s (typical SSD sequential write) ≈ 20 s — under the M7 target of ≤ 30 s with ≈ 33% margin.
  8. Active-expire cycle capacity. At a 25 ms budget per 10 Hz cycle and ≈ 200 ns per sample-and-check operation: up to ≈ 125,000 samples possible per cycle if the budget were fully consumed on sampling alone — comfortably covers the §18.4 acceptance test's 100,000-key/1s-TTL scenario (≥ 95% reaped by t=2s, i.e. within ~20 cycles).
  9. Connection memory tax. 10,000 connections × 16 KB average buffer pair ≈ 160 MB — about 3.9% of the default 4 GiB maxmemory ceiling, a fixed tax independent of dataset size that operators must budget for separately from key-value data.
  10. Cluster-bus timeout margin. cluster-node-timeout (15s) ÷ (3000 × p99 RTT (5ms)) = 15s ÷ 15s = 1.0× — the default is calibrated exactly at the stated safety ratio (§4), meaning operators on a network with worse-than-5ms p99 RTT must raise cluster-node-timeout proportionally, not assume the default has slack.

38. Glossary

  • RESP — REdis Serialization Protocol; the wire format (RESP2 and RESP3 variants) this engine speaks (§8.1–8.2).
  • RESP2 — the original request/reply wire protocol: simple strings, errors, integers, bulk strings, arrays.
  • RESP3 — the extended protocol adding maps, sets, booleans, doubles, big numbers, verbatim strings, push messages, and streamed strings, negotiated via HELLO.
  • AOF — Append-Only File; the persistence mechanism that logs every mutating command for replay-based durability (§17.2).
  • RDB — a binary point-in-time snapshot of the dataset (§17.3).
  • Hybrid persistence — an RDB preamble followed by an AOF tail; combines RDB's load speed with AOF's low data-loss window (ADR-07).
  • PSYNC2 — the replication handshake/resync protocol supporting both full and partial resync, including the secondary-replication-ID mechanism for failover continuity (§19.2).
  • Replication backlog — a fixed-size ring buffer of recent replicated commands, enabling partial resync (§11.7, §34).
  • MOVED — the redirection reply a cluster node sends when a key's slot is owned elsewhere (§20.2).
  • ASK — the redirection reply used during live slot migration, requiring the client to send ASKING before its retry is honored on the destination node (§20.2).
  • Hash slot — one of 16,384 fixed partitions of the cluster keyspace, computed via CRC16 over the key or its {...} hash-tag (§8.4, ADR-18).
  • Gossip — the peer-to-peer protocol by which cluster nodes converge on a shared view of slot ownership and node health (§20.3).
  • Listpack — the compact, single-allocation encoding used for small lists, hashes, sets, and sorted sets (§8.4).
  • Quicklist — the full encoding for lists above the listpack threshold: a doubly-linked list of listpack nodes (§8.4).
  • Skiplist — the probabilistic ordered data structure (Pugh 1990) backing large sorted sets, paired with a hashtable for O(1) score lookup (§11.5).
  • Intset — the compact all-integer set encoding: a sorted array of fixed-width integers (§8.4).
  • Embstr — an embedded short string (≤44 bytes) stored inline with the RedisObject header, sharing its cache line (§8.4, §14.2).
  • Encoding conversion — the one-way promotion of a collection type from its compact to its full encoding once a documented threshold is crossed (§8.5, P3).
  • Incremental rehash — the Dict's technique of growing its hash table in small, bounded steps per operation rather than all at once, keeping worst-case per-op latency bounded (§11.2).
  • Active expiration — the background cycle that samples and deletes expired keys without waiting for a client read (§18.2).
  • Lazy expiration — deleting an expired key at the moment it is looked up by a command (§14.2).
  • TTL — time-to-live; the remaining lifetime of a key before automatic expiration.
  • Eviction policy — the configured strategy (noeviction, allkeys-lru, etc.) for reclaiming memory under the maxmemory watermark (§18.2, delegated per P9).
  • LRU/LFU — least-recently-used / least-frequently-used; the two families of eviction/candidate scoring this engine supports via the delegated cache-engine crate.
  • maxmemory — the configured memory ceiling that triggers eviction once exceeded (§4, §18.2).
  • WATCH/dirty CAS — the optimistic-concurrency-control mechanism aborting a queued transaction if a watched key changes before EXEC (§22.2, I9).
  • MULTI/EXEC — the transaction-queueing and atomic-commit command pair (§22.2).
  • ACL — Access Control List; the per-user rule set governing command and key-pattern permissions (§21.2).
  • AUTH — the command/handshake step establishing a connection's authenticated user.
  • mTLS — mutual TLS; both client and server present certificates, used here to map a verified client CN to an ACL username (§21.2).
  • Keyspace notification — a pub/sub event published on key mutation/expiration, gated by notify-keyspace-events (§18.2).
  • Pub/sub — the publish/subscribe messaging primitive, independent of the keyspace (§22.2).
  • Lua sandbox — the restricted Lua environment (os/io/loadfile/dofile stripped) that EVAL scripts execute within (ADR-13, T8).
  • EVAL/EVALSHA — execute a Lua script verbatim or by its cached SHA-1 (§22.2).
  • Module ABI — the extern "C" extension-point surface for loadable command modules, not binary-compatible with real Redis modules in this specification (ADR-14).
  • Cluster bus — the dedicated inter-node port (client port + 10000) carrying gossip traffic (§20.2).
  • Config epoch — a monotonically increasing per-node version number used to resolve slot- ownership conflicts during cluster convergence (§11.6, I7).
  • Slot migration — the live process of moving a hash slot's keys from one node to another, using the MIGRATING/IMPORTING state pair (§20.2).
  • Failover election — the epoch-based voting protocol by which a replica is promoted after its leader becomes unreachable (§20.2).
  • HyperLogLog (HLL) — a probabilistic cardinality estimator with bounded error, sparse/dense encodings (§16.2, Heule et al. 2013).
  • Geohash — the 52-bit interleaved-bit encoding used to represent geospatial coordinates as a sortable integer score (§16.2).
  • Bitmap — a string interpreted as a bit array for SETBIT/GETBIT/BITCOUNT/etc. (§16.2).
  • Radix tree (rax) — the prefix-tree structure backing stream storage, keyed by entry ID (§16.2).
  • Consumer group — a named, stateful reader group over a stream, tracking per-consumer pending entries (§16.2).
  • PEL (Pending Entries List) — the per-consumer-group record of delivered-but-unacknowledged stream entries (§16.2).
  • COW (Copy-on-Write) — the technique of deferring a data clone until the first mutation after a snapshot point, used for AOF-rewrite snapshotting without fork() (ADR-21, MM7).
  • fsync — the syscall that forces buffered writes to durable storage; the basis of the appendfsync durability tiers (§17.2).
  • Backpressure — the policy of bounding a slow consumer's resource cost rather than letting it grow unbounded (P11, ADR-22).
  • SLOWLOG — the ring buffer recording commands exceeding a configured latency threshold (§23.2).
  • OpenTelemetry span — a single traced unit of work in the distributed-tracing model (ADR-15, §23.2).
  • Prometheus metric — a named, labeled time series exposed at :9121/metrics for pull-based scraping (ADR-16, §23.2).
  • Dispatcher — the single-threaded command-execution loop owning one shard's databases (§11.3, P2).
  • Shard — one of N independent partitions of the keyspace and its own dispatcher, connections, and databases (§11.3).
