In one paragraph

An in-memory store keeps every key and value in RAM and answers simple commands such as GET, SET and ZADD over the network. This design is a from-scratch Rust server that speaks the same wire protocol as Redis 7.x, so existing Redis clients work unchanged (§1, P1). It adds the supporting machinery: key expiry, disk logs and snapshots, replicas, and a 16,384-slot cluster mode (§1). It is not built to beat Redis on benchmarks. It is built so an engineer who already runs Redis can read and change the source when production misbehaves (§1). Each node is one binary, and a cluster is several such nodes gossiping with no external coordinator (§1, ADR-10).

The problem, concretely

Many production systems have a Redis-shaped hole: a session store, a rate limiter, a leaderboard, a cache, a broker, a pub/sub fan-out, a coordination primitive (§2). Teams that only consume Redis cannot debug its surprises (§2). Suppose you build the obvious thing yourself, a shared in-memory map behind a socket, and then look at what the blueprint says goes wrong with each naive choice:

  • Protect the map with locks so many threads can use it. Every lock inside a shard reintroduces the reader-writer-lock bug class that the design exists to avoid (P2, ADR-05).
  • Store every small collection as a full hash table. Skipping the compact encodings inflates per-key memory 3 to 8 times on small-collection-heavy workloads (P3).
  • Make each write wait for the disk. A synchronous fsync on the dispatcher thread freezes every client of that shard (P4).
  • Let a slow reader's output queue grow. One subscriber that never drains its socket becomes a cluster-wide out-of-memory event (P11, T5, FM-6).
  • Use wall-clock time for expiry. An NTP step then expires keys early or late (FM-11, ADR-23).
  • Invent a cleaner protocol or a hash ring. Real clients expect the Redis wire format and the fixed-slot cluster scheme, so you forfeit them all (P1, P6, ADR-04).

The blueprint also names the hard cases that justify building it: an AOF rewrite racing a write storm, a replica reconnecting with a stale backlog, a slot migration interleaved with a MULTI/EXEC transaction, and a listpack converting to a quicklist at the wrong moment (§1). Its worked wire examples are SET foo bar EX 10 and ZADD leaderboard 100 alice (§8.3).

How it works, end to end

Follow one command through the boxes of §3's diagram. The diagram below is adapted from §3 and shortened to the boxes a command touches; each box is a crate or module named in the blueprint.

  1. Listener (store-server). One tokio listener task per bound address and protocol accepts the connection and hands it to a shard, so that a connection's commands always run on the same dispatcher (§3). TLS, when enabled, ends here (§3, §21).
  2. Connection (store-dispatcher, with the codec in store-resp). This box owns the input and output buffers and all client-local state: authentication, transaction, watched keys and subscriptions. It is the trust boundary between raw bytes and an ACL-checked command (§3). The parser is incremental: on a half-received frame it returns "not yet" instead of failing, so a pipelined client is never forced to wait for the whole buffer (§13.2).
  3. Dispatcher (store-dispatcher). Every command goes through lookup, arity, ACL, cluster-slot check, then execute, in that order and never reordered (§3). It is the only mutation path into a shard's databases (§3). One dispatcher serves one shard and is single-threaded (P2).
  4. Database and encodings (store-core). A Database holds a keys table and an expires table, both the project's own incremental-rehash Dict (§11.2, ADR-03). Values are RedisObjects whose encodings sit behind one vtable, so the dispatcher branches on the type, never on the encoding (P3, §3).
  5. Persistence and replication. After a write executes, one post-execute hook appends it to the AOF (if enabled) and to the replication backlog (if replicas exist), together (I12). Both read the dispatcher's command stream, never the database directly (§3, P5).
  6. Reply and background work. The encoder reads the connection's protocol on every response, so a mid-stream HELLO 3 switches reply shape correctly (I11). Active expiry and the eviction trigger never hold the dispatcher mutex longer than their configured budget (§3, I2). The cluster layer decides at step 3 whether this node owns the key's slot and redirects otherwise (§3, §20.2).

Throughput comes from running many such shards side by side, one dispatcher per core, up to 64 per node with 16 as the default (§4, ADR-06, MM1).

The core ideas

One thread per shard, no locks inside it (P2, ADR-05, MM1)

A shard is one partition of the keyspace with its own dispatcher (§38). Inside it, one thread runs commands one after another, so no two commands ever race (P2). Concurrency is a property of the set of shards, not of any one shard, so the throughput ceiling is shard count times per-shard throughput and never more (MM1, §31). The cost is stated plainly: no parallelism inside a shard, and a single very hot key still serializes through its one dispatcher (P2, §31). Sharding inside a node is a concurrency mechanism; cluster slots between nodes are a capacity mechanism, and conflating them is a named design-review mistake (§31, §35 question 3).

The one rule that protects this model is I2: the dispatcher never blocks on a syscall while holding the shard's sole mutex. The everysec flush runs from a background task (§17.2), and the expire cycle must yield at its 25 ms budget (§18.2, §18.6). The blueprint is not consistent about whether a shard has a lock at all: §4 promises "the complete absence of lock contention inside a shard" and §30 says there are no intra-shard locks, while §11.3 gives each Shard a Mutex<Dispatcher>, I2 calls it the shard's "sole mutex", and §3 has background tasks holding the dispatcher mutex up to their budget.

Two encodings per type, converted once and never back (P3, §8.5, MM2)

Small collections are stored in a compact packed layout (listpack, or intset for small all-integer sets). Past a threshold they convert to a full structure (hashtable, quicklist, skiplist), and the conversion is one-way (P3). The thresholds from the §8.5 table:

Type Compact form Converts when Full form
Hash ListpackHash entries > 128, or any value > 64 B Hashtable
List ListpackList entries > 128, or any entry > 64 B Quicklist
Set of integers Intset a non-integer member arrives, or entries > 512 ListpackSet or HashtableSet
Set of strings ListpackSet entries > 128, or any member > 64 B HashtableSet
Sorted set ListpackZset entries > 128, or any member > 64 B Skiplist + Hashtable

The check must cover both entry count and per-entry byte size. A count-only check ships a pathological 1 KB-per-entry listpack that is slower than a hashtable would have been (§15.6, P3). One-way conversion means a key that later shrinks never reverts and wastes some memory (P3). The list threshold is stated two ways: §8.5 converts when entries exceed 128, while §15.2 describes the compact form as fewer than 128 entries and §15.5 says the encoding flips at 128 entries. The count of encodings also varies: §3 says every data type has exactly two, while §3's own diagram and §15.2 give sets three (intset, listpack, hashtable) and §14.2 gives strings three (int, embstr, raw). A full sorted set keeps a skiplist for ordered operations plus a hashtable for O(1) score lookup (§38). I13 says each skiplist level's span equals the exact node count it skips; a corrupted span breaks ZRANK and ZRANGE while ZSCORE still answers correctly (I13, FM-8, §15.6).

Expiry: check on read, and sweep in the background (I1, §14.2, §18.2)

Invariant I1 says a key with a TTL is either in the expires table exactly once or already deleted. Two paths enforce it. The lazy path: lookup_key checks expires before returning any object, so SET foo bar EX 1 read at t = 1.001 s returns nil (§14.2, §14.4). The active path: a background cycle driven by serverCron at 10 Hz samples 20 keys that have TTLs, deletes the expired ones, and keeps sampling until fewer than 25% of the sample are expired or a 25 ms budget runs out (§18.2). The acceptance test needs no client reads at all: a key with a 1 s TTL must be deleted within 2 s (§14.4), and with 100,000 such keys at least 95% must be reaped by t = 2 s (§18.4).

The time budget is what keeps the cycle compatible with I2. The blueprint's own capacity estimate is that 25 ms at about 200 ns per sample-and-check allows up to about 125,000 samples per cycle (§34 item 8). Expiry uses a monotonic clock internally and wall-clock time only where a TTL is visible on the wire, such as EXPIREAT (ADR-23, FM-11). Only the leader expires keys: on a read-only replica the active cycle is a structural no-op (I10).

Durability: a command log, rewritten without fork() (§17.2, §8.8, ADR-21, MM3, MM7)

Every mutating command is re-serialized into its RESP wire form and appended to the AOF (append-only file), flushed according to appendfsync: always, everysec or no (§17.2, P4). For example, SET foo bar EX 10 has the RESP form *5\r\n$3\r\nSET\r\n$3\r\nfoo\r\n$3\r\nbar\r\n$2\r\nEX\r\n$2\r\n10\r\n (§8.3). everysec accepts up to one second of loss and flushes from a background task (P4, §17.2). An RDB is a point-in-time snapshot; the default hybrid format is an RDB preamble followed by an AOF tail (ADR-07, §17.2). The same serialization path feeds replication, so replicas cannot diverge from persisted state by design (P5, MM3).

The AOF grows forever, so it must be rewritten. Real Redis does this with fork(), but tokio's reactor is not fork-safe and a naive fork deadlocks on the epoll descriptor (ADR-21, §17.2). The design instead does copy-on-write at the data-structure level: the rewrite task takes an Arc-shared read-only snapshot of each shard's Database, the dispatcher clones an affected sub-tree only on the first write after that point, and writes made since the snapshot go into a rewrite buffer that is appended at the end (§17.2). A trailing blake3 checksum record marks the new file as complete, and the old AOF is never truncated until that checksum validates (§17.2, ADR-19).

Failure trace from §8.8: the rewrite stops after writing 60% of the new file. The dispatcher keeps appending to the old AOF and the in-memory rewrite buffer the whole time. On restart the loader sees the new file's missing or short checksum trailer, discards it, and loads the old AOF. Result: no data lost, one rewrite skipped, store_aof_rewrite_failures_total incremented (§8.8, FM-1). Because COW defers cost to the first mutation, the extra memory depends on churn during the rewrite, not on dataset size (MM7).

Replication: one log, a ring buffer, and a second replication ID (§19.2, P5, I6)

A replica connects, sends PSYNC <replid> <offset>, and the leader answers +FULLRESYNC, +CONTINUE, or +CONTINUE <newreplid> (§19.2). The leader keeps a replication backlog: a fixed-size ring buffer of recent commands (default 1 MiB, repl-backlog-size) with a logical offset that only ever increases (§19.2, I6). On reconnect, if the replica's offset is still inside the backlog window, the leader ships only the gap (partial resync). If the offset is older than the oldest retained byte, it falls back to a full resync: a BGSAVE, a stream of the RDB, then the commands buffered meanwhile (§19.2).

PSYNC2's key addition is the secondary replication ID: after a failover the new leader keeps the old leader's ID as "secondary", so existing replicas can keep streaming without a full resync (§19.2). Sizing follows B = W × T, backlog bytes equals write rate times tolerated disconnect seconds. At the default W ≈ 100 KB/s and T = 10 s that gives about 1 MB, matching the default (§34 item 1). The acceptance tests (§19.4) are the tiny trace: a replica offline for 10 s while 1,000 writes occur resumes by partial resync; one offline for 10 minutes falls back to full resync and still converges.

Cluster: 16,384 fixed slots, gossip, and two redirects (§20.2, P6, ADR-09, MM4, MM8)

A key's slot is CRC16/XMODEM of the key, or of the substring inside the first {...} hash tag if one is present (§20.2, ADR-18). The slot map says which node owns each of the 16,384 slots, and it is the sole routing source of truth (§20.2). A node that receives a command for a slot it does not own replies -MOVED <slot> <ip:port>, and the client updates its slot cache and retries (§20.2).

Moving a slot live uses a state pair, traced in §20.2:

  1. The source node marks the slot MIGRATING; the destination marks it IMPORTING.
  2. A key still on the source is served normally.
  3. A key already moved gets -ASK <slot> <ip:port> from the source.
  4. The client sends ASKING to the destination, then retries the command there.
  5. The blueprint calls ASKING the mechanism that keeps a multi-key transaction correct mid-migration (§20.2, §2).

Nodes learn each other's views by gossip over a bus port at client port + 10000, each message carrying slot ownership, health, offsets and a config epoch (§20.2, §1). Views converge eventually, never instantly, so a burst of MOVED replies right after any topology change is expected (MM8, I7). When a leader is silent for cluster-node-timeout (15 s by default), its replicas raise an epoch, ask for votes, and a majority-vote replica promotes itself (§20.2, §4).

The trade-offs — where engineers disagree

Concurrency: one dispatcher per shard (ADR-05)

Chosen: a single-threaded dispatcher per shard, which removes reader-writer-lock bug classes entirely and repeats antirez's 2009 choice (ADR-05, P2). Rejected: a global lock, or per-key lock striping. When the rejected choice is right: per-key lock striping wins when the workload is dominated by a handful of enormous keys that would otherwise serialize a whole shard (ADR-05, §31).

Snapshots: copy-on-write in the data structures (ADR-21)

Chosen: data-structure-level COW with Arc-cloned sub-trees, because tokio's reactor is not fork-safe (ADR-21, §17.2). Rejected: true fork(), or mmap plus madvise. When the rejected choice is right: true fork() wins in a non-async, single-threaded runtime with no reactor to deadlock, which is antirez's own C implementation (ADR-21).

Replication: PSYNC2 with a per-replica backlog (ADR-08)

Chosen: partial resync, which avoids a full RDB transfer on every short network blip and which the blueprint calls the highest-value replication optimization (ADR-08). Rejected: full-resync-only, or logical replication over a message bus. When the rejected choice is right: full-resync-only wins for a replica that reconnects rarely, such as a cold-standby disaster-recovery replica, where simplicity outweighs resync cost (ADR-08).

Partitioning: fixed hash slots (ADR-09)

Chosen: 16,384 fixed slots, for Redis Cluster spec compatibility and because a fixed count bounds gossip payload size and migration granularity (ADR-09, P6). Rejected: a consistent-hash ring, or range partitioning. When the rejected choice is right: consistent hashing wins when node count churns far more than key count and minimizing re-partitioning matters more than a fixed, inspectable slot map (ADR-09).

Cluster membership: gossip, not a coordinator (ADR-10)

Chosen: the project's own gossip crate (project 72), so there is no external coordination service to operate (ADR-10). Rejected: a SWIM library, or a centralized coordinator such as etcd or ZooKeeper. When the rejected choice is right: a coordinator wins when the deployment already runs etcd or ZooKeeper and wants one consistent source of cluster truth instead of eventual consistency (ADR-10, §31).

Roads not taken (§36, §37)

Multi-threaded shared-nothing shards on io_uring (§36 Alternative 1): one OS thread per shard and no tokio reactor. It wins for a Linux-only deployment that must push a single node past what a tokio-mediated epoll loop can sustain, above 10M ops/s per node; Dragonfly is the real example. It is rejected here for portability and because it forfeits the tokio ecosystem (§36, ADR-02).

Disk-tiered hybrid log (§36 Alternative 2): a hot region in RAM, a cold region on SSD. It wins when the dataset exceeds RAM but hot keys still need Redis-like latency (Microsoft Garnet). It is rejected because this project is explicitly in-memory (§36, §1).

Per-key actor model (§36 Alternative 3): one lightweight process per key. It wins for extremely hot-key-skewed workloads with complex per-key logic (the BEAM VM). It is rejected because per-key overhead far exceeds a hashtable slot and multi-key commands need awkward coordination (§36, P2).

Consistent-hash ring with virtual nodes (§36 Alternative 4): it wins when membership churns faster than slot-map gossip can re-converge, or when nodes of different capacity need uneven weights; Cassandra and Dynamo use it. It is rejected because every Redis Cluster client's MOVED/ASK handling assumes fixed slots (§36, P1, P6).

Deferred register (§37): RedisModule_* binary compatibility waits for a need to run an unmodified real module; cluster-bus mTLS waits for deployment across an untrusted network; federation of clusters waits for a deployment near the single-cluster ceiling (§37, §31).

What must never be false

  • I1: a TTL'd key has exactly one live expires entry or is deleted. Noticed by a property test (expires domain within keys domain); store_expired_keys_total.
  • I2: the dispatcher never blocks on a syscall while holding its shard's sole mutex. Noticed as a p99 outlier in store_command_latency_seconds; also code review and clippy lints.
  • I3: an object's encoding always matches its ObjectPtr variant. Enforced by the types themselves; a debug assertion and store_encoding_mismatch_total (test builds) back it up.
  • I4: AOF replay rebuilds bit-identical state, modulo recorded random seeds. Noticed by a golden-hash comparison; store_aof_replay_divergence_total.
  • I5: an RDB save then load is byte-identical. Noticed as a checksum mismatch on load; store_rdb_checksum_failures_total.
  • I6: the replication backlog offset never rewinds. Noticed by an offset-regression assertion in the replica handshake; store_replication_offset; recovery is a forced full resync.
  • I7: slot ownership is eventually recorded identically on every node that has gossiped it. Noticed by a cross-node CLUSTER NODES diff; the config-epoch gauge.
  • I8: a slot has exactly one owner per config epoch outside a MIGRATING/IMPORTING transition. Noticed by an overlap check on CLUSTER SLOTS; store_cluster_slots_assigned.
  • I9: a watched key modified before EXEC always aborts the transaction. Noticed by a conformance fixture; store_tx_aborted_total.
  • I10: the active-expire cycle never runs on a read-only replica. store_expired_keys_total{role="replica"} should always read 0.
  • I11: the connection's protocol is read on every response encode, never cached. Noticed by a fixture that sends HELLO 3 mid-pipeline.
  • I12: every mutating command reaches the AOF and the backlog atomically with its execution. Noticed through I4's replay divergence; store_aof_size_bytes and store_replication_offset advance together.
  • I13: each skiplist level's span equals the exact node count skipped. Noticed by a ZRANK differential fixture; recovery rebuilds the skiplist from the hashtable half.
  • I14: every PhaseDeferred(...) anchor resolves to a Deferred Features Register row. A document-level cross-reference check (harness check H16); no runtime telemetry.

What breaks in production

  • FM-1: an AOF rewrite stalls or crashes. Cause: disk full or a COW clone storm under heavy concurrent writes. Noticed through store_aof_rewrite_failures_total and an over-long rewrite. The old AOF stays authoritative until the new one's checksum validates, so the operator frees disk or lowers the write rate and retries BGREWRITEAOF (§8.8, I4).
  • FM-3: backlog exhaustion causes a full-resync storm. The backlog is too small for the write rate times the disconnect time (§34 item 1). Noticed as a sawtooth in store_replication_offset and repeated FULLRESYNC. There is no automatic fix because full resync is the fallback; the operator raises repl-backlog-size and investigates the network.
  • FM-4: slot-map divergence or a stuck migration. A node crashed mid-MIGRATING/IMPORTING. Noticed as CLUSTER SLOTS disagreement across nodes (an I8 violation). Recovery needs the explicit cluster fix subcommand, which walks orphaned keys.
  • FM-6: slow-consumer OOM despite backpressure. client-output-buffer-limit is set too high or disabled. Noticed as store_memory_used_bytes growth tracking one connection's buffer. The connection is dropped once past the limit (P11, ADR-22); the operator tightens the limit.
  • FM-7: active-expire starvation. Millions of keys expire at once. Noticed when store_expired_keys_total plateaus while the TTL'd key count grows. The cycle catches up over later budget windows; the operator follows docs/runbooks/memory-pressure.md.
  • FM-11: clock skew or an NTP step. Internally immune thanks to the monotonic clock (ADR-23); only the wire-visible EXPIREAT timestamp is exposed, so operators keep NTP slewing, not stepping.

Threats a reader should know (§24): T3 memory exhaustion by a giant key or write flood, answered by enforcing maxmemory on every write path and returning OOM rather than losing data silently; T5 a slow pub/sub subscriber growing a buffer, answered by client-output-buffer-limit pubsub dropping it (P11, ADR-22); T7 cluster-bus impersonation, where until bus mTLS lands (it is deferred) network isolation is the operator's job (§37); T10 tampering with AOF or RDB files at rest, detected by the blake3 checksum trailer (ADR-19, I5).

How it compares

  • Redis made the single-threaded-dispatcher choice in 2009 and has only partly revisited it, with I/O threads since 6.0 still funnelling execution through one thread. It wins where wire and ecosystem compatibility matter more than raw single-node throughput, which is why this design mirrors it (§33, ADR-05).
  • Memcached dropped persistence, replication and rich types for the simplest slab-allocated cache. That wins for a genuinely cache-only workload where operational simplicity matters more than features (§33).
  • KeyDB kept Redis's model but made the dispatcher multi-threaded with a global-lock fallback for cross-thread write conflicts. It wins on read-heavy multi-core workloads where the fallback is rarely paid; this design declines it because the fallback re-admits the lock-contention class that P2 avoids (§33, P2, §36).
  • Dragonfly replaced threads-plus-async with io_uring and a from-scratch Dash hash table. It wins on raw single-node throughput on Linux, at the cost of the portability and ecosystem that tokio preserves here (§33, ADR-02).
  • Aerospike keeps only the index in RAM and puts data on flash, so it wins when RAM cost dominates the economics and flash durability replaces a separate AOF/RDB story. That is a different point in the design space from an in-memory-first store (§33, §1).

Questions to test yourself

  1. Under what write-rate/disconnect-tolerance combination does the default 1 MiB backlog force a full resync, and how would you recompute the right size for your own workload? — Hint: §19.4 and the formula in §34 item 1.
  2. Why is "single-threaded per shard" not the same claim as "single-core"? What breaks if an implementer conflates the two? — Hint: §3, principle P2 in §6, and §31 on intra-node versus inter-node partitioning.
  3. Why is the AOF rewrite implemented as data-structure-level COW rather than fork(), and what would break if tokio's reactor were forked naively? — Hint: §17.2 and ADR-21.
  4. Why does the active-expire cycle need a per-iteration time budget rather than a per-cycle key-count budget, given both bound total work? — Hint: §18.2, the Pitfalls in §18.6, and I2.
  5. Why does the ASKING flag exist, and what transactional correctness property breaks during a live slot migration without it? — Hint: §20.2, the mastery bullet in §2, and I8.

If you only remember three things

Concurrency here comes from running many single-threaded shards, not from locks, and the dispatcher never blocks on a syscall: the disk flush runs in the background and the expiry sweep has a time budget (P2, I2, ADR-05). Persistence and replication are two readers of the same command log, and a rewrite is made safe by never discarding the old file until the new one's checksum validates (P5, §8.8, ADR-21). The cluster is a fixed slot map kept in sync by gossip that converges eventually, and the wire compatibility that forces this shape (P1, P6) is also what makes the whole project worth building.

Words used here

  • RESP: the wire format Redis clients speak; RESP2 and RESP3 are its two versions, chosen per connection by HELLO.
  • Shard: one partition of a node's keyspace with its own single-threaded dispatcher.
  • Listpack / intset: the compact packed layouts used for small collections and small integer sets.
  • Lazy / active expiration: deleting an expired key when it is read, versus a background sweep that deletes without a read.
  • AOF: the append-only log of every mutating command, replayed to rebuild state.
  • RDB: a point-in-time binary snapshot of the dataset; the hybrid format is an RDB followed by an AOF tail.
  • Replication backlog: a fixed-size ring buffer of recent commands that makes partial resync possible.
  • PSYNC2: the replication handshake that supports partial resync and keeps a secondary replication ID across failovers.
  • Hash slot: one of 16,384 fixed partitions of the cluster keyspace, picked by CRC16 of the key or its {...} tag.
  • MOVED / ASK: redirects telling a client which node owns a slot, permanently or during a live migration.
