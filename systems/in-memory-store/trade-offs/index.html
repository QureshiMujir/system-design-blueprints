Decisions (§9) · 24 ADRs

ADR-01

Core language

Chosen

Rust 1.79+

Rejected

C, Go, C++

When the rejected choice is right

C wins when the team needs byte-for-byte ABI parity with antirez's Redis to vendor real Redis modules directly

Why: Ownership model closes the encoding-corruption/use-after-free class at compile time (I3); tokio gives P2 a native LocalSet primitive

ADR-02

Async runtime

Chosen

tokio, LocalSet-pinned executors

Rejected

async-std, smol, hand-rolled epoll

When the rejected choice is right

Hand-rolled epoll/io_uring wins for a single-purpose Linux-only binary with no need for the broader async ecosystem (Dragonfly's own choice, §33)

Why: Industry-default ecosystem (rustls, hyper, tonic); LocalSet is the mainstream way to pin a !Send dispatcher to one OS thread

ADR-03

Hash table

Chosen

Project-owned incremental-rehash Dict

Rejected

dashmap, std::HashMap+RwLock

When the rejected choice is right

dashmap wins for a component off the per-command hot path (e.g. a one-off CLUSTER NODES cache)

Why: dashmap's internal sharding + RW-locks fight P2's own sharding; incremental rehash bounds worst-case per-op latency (I2)

ADR-04

Wire protocol

Chosen

RESP2 + RESP3 dual-mode per connection

Rejected

RESP3-only, custom binary protocol

When the rejected choice is right

RESP3-only wins for a greenfield deployment with one controlled client and no legacy-library constraint

Why: 90%+ of deployed clients still speak RESP2 only; a custom protocol forfeits every existing client library (P1)

ADR-05

Concurrency model

Chosen

Single-threaded dispatcher per shard

Rejected

Global lock, per-key lock striping

When the rejected choice is right

Per-key lock striping wins when workload is dominated by a handful of enormous keys that would otherwise serialize a whole shard

Why: Removes reader-writer-lock bug classes entirely (P2); antirez's own 2009 choice, validated at scale

ADR-06

Shard count

Chosen

16 default, configurable 1–64

Rejected

Fixed 1, dynamic re-sharding

When the rejected choice is right

Dynamic re-sharding wins only in a research prototype willing to run a migration protocol as complex as §20's, just to move keys between local shards

Why: Matches KeyDB's empirically-tuned default; re-sharding at runtime reintroduces the migration-consistency problem cluster mode already solves at a coarser grain

ADR-07

Default persistence

Chosen

RDB preamble + AOF tail (hybrid)

Rejected

AOF-only, RDB-only, none

When the rejected choice is right

RDB-only wins for a pure derived-data cache where losing writes since the last snapshot is acceptable

Why: Redis 7 default; combines RDB's fast load with AOF's low data-loss window

ADR-08

Replication protocol

Chosen

PSYNC2 with per-replica backlog

Rejected

Full-resync-only, logical replication over a message bus

When the rejected choice is right

Full-resync-only wins for a replica that reconnects rarely, where operational simplicity outweighs resync cost (a cold-standby DR replica)

Why: Partial resync avoids a full RDB transfer on every short network blip — the single highest-value replication optimization

ADR-09

Cluster topology

Chosen

16,384 fixed hash slots

Rejected

Consistent-hash ring, range partitioning

When the rejected choice is right

Consistent hashing wins when node count churns far more than key count and minimizing re-partitioning matters more than a fixed, inspectable slot map (§33/§36)

Why: Cluster-spec compatibility is non-negotiable (P6); fixed slot count bounds gossip payload size and migration granularity

ADR-10

Cluster gossip transport

Chosen

Project-72 Gossip-Protocol crate

Rejected

SWIM library, centralized coordinator (etcd/ZooKeeper)

When the rejected choice is right

A centralized coordinator wins when the deployment already runs etcd/ZooKeeper and wants one consistent source of cluster truth instead of eventual consistency

Why: Cross-project reuse; no external coordination-service dependency to operate (P6)

ADR-11

Transport security

Chosen

Project-50 TLS/SSL-Handshake crate (rustls-based)

Rejected

Direct rustls, openssl-sys FFI

When the rejected choice is right

openssl-sys wins when FIPS-140 certified crypto modules are a hard compliance requirement rustls does not yet satisfy

Why: Cross-project reuse; avoids an OpenSSL FFI surface in a memory-safety-first codebase

ADR-12

Eviction algorithm

Chosen

Delegate to Project-59 LRU/LFU cache engine

Rejected

Built-in eviction only

When the rejected choice is right

Built-in-only wins when the eviction algorithm needs microsecond-level dispatcher-hot-path integration a crate boundary would tax

Why: Cross-project reuse (P9); store owns trigger and candidate set, cache engine owns the algorithm

ADR-13

Scripting language

Chosen

Embedded Lua 5.1 via mlua

Rejected

Lua 5.4, a WASM sandbox

When the rejected choice is right

A WASM sandbox wins when polyglot scripting and stronger sandboxing than Lua's os/io strip-out are the priority (PhaseDeferred("Deferred Features Register"))

Why: Redis-compatible scripts are authored against Lua 5.1 semantics; Lua 5.4 changes integer semantics enough to silently break real scripts

ADR-14

Module ABI

Chosen

extern "C"/repr(C) placeholder, one example module

Rejected

Full RedisModule_* binary compatibility now, no module support

When the rejected choice is right

Full binary compatibility wins the moment the goal becomes "run RedisJSON/RediSearch unmodified" (PhaseDeferred("Deferred Features Register"))

Why: Binary compatibility with real Redis modules is a multi-month undertaking of its own; the placeholder proves the extension point without blocking Phase 0

ADR-15

Distributed tracing

Chosen

OpenTelemetry spans

Rejected

Custom span format, no tracing

When the rejected choice is right

A custom minimal span format wins in an extremely latency-sensitive embedded deployment where even OTel's per-span overhead is unacceptable

Why: Standard OTLP exporters integrate with existing operator tooling without a bespoke collector (P13)

ADR-16

Metrics

Chosen

Prometheus pull-based /metrics

Rejected

StatsD push, custom

When the rejected choice is right

StatsD push wins in an environment already standardized on push-based aggregation with very high per-key metric cardinality

Why: Pull-based fits the operator runbook (§26) without a push-target dependency

ADR-17

License

Chosen

Apache-2.0 (runtime)

Rejected

AGPL-3.0, SSPL, BSD-3-Clause

When the rejected choice is right

SSPL/AGPL wins if the explicit goal is preventing a cloud vendor from re-hosting without contributing back (Redis Inc.'s own 2024 rationale)

Why: Permissive license maximizes adoption as a learning/reference project; keeps a future hosted-control-plane license split clean

ADR-18

Cluster slot hash

Chosen

CRC16/XMODEM

Rejected

CRC32, xxHash

When the rejected choice is right

A faster hash wins only if cluster-spec compatibility is explicitly dropped (not on the table here, P1/P6)

Why: Locked by the Redis Cluster specification — any other hash breaks slot-map interop with real Redis Cluster clients

ADR-19

Persistence checksum

Chosen

blake3

Rejected

CRC64, SHA-256

When the rejected choice is right

CRC64 wins for byte-for-byte RDB-file interop with real Redis tooling inspecting the trailing checksum field

Why: Faster than CRC64 with SIMD, far stronger collision resistance for corruption detection

ADR-20

Config format

Chosen

YAML + Redis-CLI-compatible flags

Rejected

TOML, JSON

When the rejected choice is right

TOML wins for a config file meant to be hand-edited frequently, favoring strict unambiguous typing over YAML's footguns

Why: Redis operators already know the --port 6379-style flag surface; YAML is broadly familiar for structured config

ADR-21

Snapshot mechanism

Chosen

Data-structure-level COW (persistent/Arc-cloned sub-trees)

Rejected

True fork(), mmap+madvise

When the rejected choice is right

True fork() wins in a non-async, single-threaded-process runtime with no reactor to deadlock (antirez's own C implementation)

Why: tokio's reactor is not fork-safe; a naïve fork() deadlocks on the epoll fd (§17.2)

ADR-22

Backpressure policy

Chosen

Bounded per-connection output buffer, drop-slowest-subscriber

Rejected

Unbounded buffer, blocking write

When the rejected choice is right

Blocking writes win in a strictly-ordered, small-fan-out internal pipeline where losing a pub/sub message is unacceptable

Why: Bounds one slow client's memory cost; matches client-output-buffer-limit semantics operators already know (P11)

ADR-23

Time source for TTL

Chosen

Monotonic Instant internally, wall-clock at the wire boundary

Rejected

Wall-clock SystemTime throughout

When the rejected choice is right

Wall-clock throughout wins only where clock skew across nodes must be directly comparable to a client's own wall clock

Why: Monotonic clock is immune to NTP step-adjustments mid-flight; wall-clock only needed where a TTL is wire-visible (EXPIREAT)

ADR-24

Fuzzing strategy

Chosen

cargo-fuzz/libFuzzer corpus over RESP parser, AOF loader, RDB loader

Rejected

AFL++, property tests only

When the rejected choice is right

AFL++ wins when the fuzz target needs persistent-mode forking harnesses across process boundaries that libFuzzer's in-process model handles poorly

Why: libFuzzer's coverage-guided mutation integrates natively with Rust's sanitizers; property tests alone miss the byte-level malformed-input space

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Multi-threaded shared-nothing shards with io_uring dispatch.

Show the original text diagram
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ Shard thread │   │ Shard thread │   │ Shard thread │   (one OS thread per shard,
│ io_uring SQ/CQ│   │ io_uring SQ/CQ│   │ io_uring SQ/CQ│    no tokio reactor)
│ + own dict   │   │ + own dict   │   │ + own dict   │
└──────┬───────┘   └──────┬───────┘   └──────┬───────┘
       └──────────────────┴──────────────────┘
              shared-nothing, no cross-shard lock

Wins when: a Linux-only deployment needs to push single-node throughput past what a tokio-mediated epoll loop can sustain, minimizing syscall overhead at extreme rates (>10M ops/s/node). Real system: Dragonfly. Rejected here because: Linux-only portability tradeoff, and it forfeits the tokio/rustls/tonic ecosystem this project's ADR-02 explicitly preserves.

Alternative 2 — Disk-tiered hybrid log (Tsavorite/FASTER-style).

┌───────────────────────────────────────────┐
│ Hybrid log: single address space            │
│ ┌─────────────┐ ┌─────────────────────────┐│
│ │ Hot region   │ │ Cold region (on SSD/NVMe)││
│ │ (in RAM)     │ │ (append-only, compacted) ││
│ └─────────────┘ └─────────────────────────┘│
└───────────────────────────────────────────┘

Wins when: dataset size exceeds available RAM but the workload still wants a Redis-like API and latency profile for hot keys. Real system: Microsoft Garnet (Tsavorite/FASTER). Rejected here because: this project is explicitly an in-memory store (§1 non-goals) — a hybrid log changes the fundamental memory model and invalidates the pure in-memory latency guarantees in §4.

Alternative 3 — Per-key actor model.

Show the original text diagram
   client ──▶ router ──▶ [actor: key A] (mailbox, own state)
                     └──▶ [actor: key B] (mailbox, own state)
                     └──▶ [actor: key C] (mailbox, own state)
   (one lightweight process per key, message-passing, no shared dict)

Wins when: workload is extremely hot-key-skewed and per-key logic is complex enough to justify per-key scheduling isolation. Real system embodying the paradigm: the BEAM VM (Erlang/OTP), whose per-process-mailbox model is the direct ancestor of this alternative. Rejected here because: per-key process overhead (mailbox allocation, scheduling) is far higher than a hashtable slot at the throughput densities M1–M4 target, and cross-key multi-key commands (MSET, transactions) require awkward multi-actor coordination protocols that the single-dispatcher model (P2) gets for free.

Alternative 4 — Consistent-hash ring with virtual nodes, instead of 16,384 fixed slots.

        ┌── node A's vnodes ──┐
     ○──○──○──●──○──○──●──○──○──○   (ring of hash-space positions,
        └── node B's vnodes ──┘       key routed to next vnode clockwise)

Wins when: node membership churns far more frequently than the workload can tolerate slot-map gossip re-convergence, or heterogeneous node capacity requires uneven virtual-node weighting. Real system: Cassandra / Amazon Dynamo (Karger et al. 1997; Lakshman & Malik 2010; DeCandia et al. 2007). Rejected here because: Redis Cluster wire compatibility (P1/P6) requires the fixed-slot model — adopting a ring breaks every existing Redis Cluster client's MOVED/ASK redirection- handling code, which is precisely the compatibility this project exists to preserve.
