In one paragraph

A text-shaping engine takes a string and a font file and returns a list of positioned glyphs (the drawable shapes in a font), ready for a rasterizer to turn into pixels (§1). This design builds it from scratch in Rust as six crates: a property-table crate, Unicode normalization, grapheme/word/line segmentation, the bidirectional (mixed left-to-right and right-to-left) algorithm, OpenType font shaping, and a CLI (§1, ADR-02). It does not draw anything; its output goes to a separate TrueType rasterizer, project #385 (§1, P9). Terminal emulators, GUI toolkits, PDF engines and browser research are the named consumers (§1), and the stated goal is to learn the algorithms (§2, ADR-24).

The problem, concretely

Every OS, browser, terminal and PDF engine runs this pipeline, and it is invisible when correct and catastrophically visible when wrong (§2). Take the letter "é". It can be one code point (U+00E9) or two (U+0065 then U+0301) (§8.2.4, §14). The two spellings are canonically equivalent (MM2), and the blueprint lists "storage key collisions" as the result of wrong normalization (§2). Cursor movement needs grapheme-cluster boundaries, not code-point boundaries; without them one Backspace can split a ZWJ emoji sequence (MM1), and editors miscount characters (§2). Wrong bidi gives reversed display and is security-relevant, through the "Trojan Source" attack on bidi override characters (§2).

Even after the text is segmented and ordered, one character per glyph is wrong. In a font with an fi ligature, the letters f and i are replaced by a single glyph (§8.5.4). Kerning shifts the pair A, V closer together by an amount stored in the font (§8.5.5). Arabic letters change shape by position in the word (§3, ShaperArabic). Fonts are also untrusted files, so every offset in them has to be checked before it is read (P6, §3).

How it works, end to end

One string plus a font moves through four stages in a fixed order, each its own crate (§3, P3). The stages keep no state between calls (§3). This is the pipeline diagram of §3, lightly shortened:

 text (&str) + font bytes (&[u8]) + script/lang/direction hints
        |
        v
 ush-normalize : NFC/NFD/NFKC/NFKD (canonical order, Hangul, quick-check)
        |  normalized text
        v
 ush-segment   : grapheme / word / line-break boundaries -> runs
        |
        v
 ush-bidi      : process_paragraph -> BidiInfo { levels, classes, para_level }
        |         reorder_line -> visual order; mirror() per glyph
        v
 ush-shape     : Face { cmap / GDEF / GSUB / GPOS } -> nominal glyphs
        |         -> Shaper { Latin | Arabic | Indic | General }
        |         -> GSUB substitutions -> GPOS positioning
        v
 Buffer { infos: glyph_id + cluster, positions: advances + offsets }
        |
        v
 TrueType rasterizer (project #385) draws the glyphs
 ush-tables sits under all four stages and supplies the Unicode property data
  1. Property tables. ush-tables holds every per-code-point property: general category, combining class, decomposition, bidi class, the break classes and script (§3, §8.1). It is generated at build time and compiled in (§3, P8).
  2. Normalize. ush-normalize rewrites text into one canonical spelling and skips spans that a quick-check says are already normalized (§3, P4).
  3. Segment. ush-segment has a GraphemeCursor, a WordCursor and a LineBreaker, which emits Mandatory, Allowed or No per position (§3).
  4. Bidi. ush-bidi gives every character an embedding level; reorder_line turns levels into visual order, and mirror swaps paired characters such as brackets at odd levels (§3).
  5. Shape. Face<'a> in ush-shape borrows the font bytes without copying (§3). shape maps characters to glyph ids through cmap, picks a Shaper (ShaperLatin, ShaperArabic, ShaperIndic or ShaperGeneral), then runs GSUB and GPOS lookups (§3, ADR-15).
  6. Output. The Buffer holds GlyphInfo (glyph id, cluster, flags) and GlyphPosition (advances, offsets) in font units, always the same length (§3, §8.5.6). ush-cli wraps the stages as the normalize, segment, bidi and shape subcommands (§3).

The core ideas

Property tables: one lookup per code point, generated not typed (§3, §11, ADR-05, P8)

There are about 1.1 million code points and several properties each (§8.1). Instead of match arms or a hash, the design uses a two-stage trie (CodePointTrie): a small index array picks a block, and a data array holds the packed values (§11, ADR-05). In §11.1's code the lookup is index[c >> 6] * 64 + (c & 63), so blocks are 64 entries, and identical blocks are stored once (§11, Capacity Model C1). The tables are emitted by a tools/ program from the official Unicode data files, never hand-edited, and CI fails if a fresh generation differs from the committed one (P8, ADR-06). The Unicode version is pinned at 15.1 (P2, ADR-04, §4).

Normalization: decompose, order, compose (§8.2, §14, §15)

One visible character can have several spellings. Normalization picks one. The steps for NFC are: (1) decompose each character into its parts, recursively; (2) sort the combining marks by their combining class (ccc, a number that fixes the order marks must appear in); (3) recompose where a precomposed character exists (§8.2). NFD stops after step 2. NFKC and NFKD also use the looser "compatibility" decompositions, such as ﬁ into fi (§3, §15, Glossary).

Step 2 is a stable sort inside each run of marks, and a character with ccc 0 (a starter) ends the run, so marks never move across it (§8.2.2, MM3, I2). Step 3 composes a starter with a following mark only if the pair has a composite, is not on the exclusion list, and is not blocked, meaning a character in between has a ccc at least as large (§8.2.3, glossary).

A small trace from §8.2.4 and §14. Input U+00E9 decomposes to U+0065 U+0301, the single mark stays in place, and composition gives back U+00E9 (§8.2.4). Input q, U+0307 (ccc 230), U+0323 (ccc 220) ends as q, U+0323, U+0307 with nothing composed (§8.2.4). The blueprint's rows disagree on where the swap happens: the decompose row already lists U+0323 first and the ordering row says "already in order", while the last row says "Reordered vs input" (§8.2.4). Korean syllables need no table, since Hangul decomposes by arithmetic on constants such as SBase=0xAC00 and TCount=28 (§8.2.1, MM10); U+AC01 becomes U+1100 U+1161 U+11A8 (§14).

Two guards sit around this. The quick-check property says per code point "Yes, No or Maybe already normalized", and a span of only Yes values is skipped (§3, ADR-09, MM7, P4). Stream-safe text inserts a combining grapheme joiner (U+034F) after every 30 marks in a row, so a hostile run of marks cannot force quadratic sorting (T4, §4).

Segmentation as a rule machine (§8.3, §16, §17, ADR-10, ADR-11, P5)

A grapheme cluster is what a user sees as one character, and the rules that cut text into clusters are numbered GB1 to GB999 in the Unicode annex (§8.3). The code mirrors those numbers one to one, so a failing test row can be traced to a rule (P5, I4). Examples from §8.3:

Rule Effect
GB3 CR followed by LF never breaks, so "\r\n" is one cluster (§8.3, §16)
GB9 no break before an Extend mark or ZWJ, so a plus U+0301 is one cluster (§8.3, §16)
GB11 ExtPict Extend* ZWJ × ExtPict stays together, a ZWJ emoji sequence (§8.3)
GB12/13 regional-indicator flags pair up; each pair is one cluster (§8.3)

The flag rule needs memory: the machine must know whether it has seen an even or odd number of regional indicators, so a pair table alone is not enough (§8.3, ADR-10). 🇺🇸🇬🇧 is two clusters, one per pair (§8.3). Line breaking is encoded the other way, as a table indexed by the two neighbouring classes with outcomes break, no break and prohibited, after a check for mandatory breaks (§8.3, ADR-11).

Bidirectional text: assign levels, then reverse (§8.4, §18, §19, MM4, MM9)

Every character gets an embedding level, a number where even means left-to-right and odd means right-to-left (§8.4, glossary). Most of the algorithm assigns the level, and the final reorder step is small (MM4). The stages: classify each character (L, R, Arabic letter, number, neutral); take the paragraph direction from the first strong character; run the explicit-level rules with a directional status stack of (level, override, isolate) entries, capped at depth 125; then the weak, neutral and implicit rules fix the rest (§8.4.1 to §8.4.4, §4).

An isolate (LRI, RLI, FSI to PDI) scopes a run so that its contents cannot influence the neutrals around it (MM9, §8.4.3). The reorder rule L2 then reverses every maximal run at the highest level, then the next level down, until the lowest odd level (§3, §8.4.4).

The worked example of §8.4.4 is the logical text car ב→ג:

Position Char Class Final level
0 to 3 c, a, r, space L, L, L, WS 0
4 ב R 1
5 → ON 1 (neutral between two R)
6 ג R 1

Positions 4 to 6 form the highest-level run, so they are reversed; the blueprint shows the arrow mirrored at the odd level (§8.4.4). The result of reorder_line must be a permutation of the line's indices (I6). §8.4.3's own isolate example disagrees with its pseudo-code: the text says LRI pushes level 1 with an "LTR override", while the pseudo-code pushes the next even level with a Neutral override (§8.4.3).

Shaping: a font is a lookup database, and clusters link back to the text (§8.5, §21, §22, §23, MM5, MM6)

A font file is a binary container (sfnt) with a table directory (§8.5.1). cmap maps a code point to a glyph id, and a miss gives glyph 0, the .notdef (tofu) glyph, with no panic (§8.5.2, ADR-17). GSUB substitutes glyphs and GPOS positions them. Both reach their rules through a three-level chain: ScriptList to FeatureList to LookupList, where a feature is a named set of lookup indices (§8.5.3, MM5). A lookup applies to a glyph only if the glyph is in the lookup's coverage table (I9, §8.5.3).

Two examples copied from §8.5. A ligature lookup (GSUB type 4) takes the buffer [f cluster 0, i cluster 1], matches f followed by i, and leaves one glyph fi with cluster 0 (§8.5.4). A pair lookup (GPOS type 2) holds A, V with an XAdvance of -80, and applies it by adding -80 to the first glyph's x_advance (§8.5.5).

The cluster is the number that ties each output glyph back to a place in the input, used for cursor placement and hit-testing. It must never decrease along a left-to-right run (or increase along a right-to-left one), and every lookup that merges or splits glyphs must keep that true (P7, I8, MM6, §8.5.6). For a ligature, P7 says the merged glyph takes the first component's cluster, while §3 and §8.5.6 say it takes the minimum cluster (P7, §3, §8.5.6). Right-to-left buffers are reversed before GSUB and reversed back after GPOS (§3).

The trade-offs — where engineers disagree

Normalize, then segment, then bidi, then shape (ADR-07)

Chosen: that fixed order: NFC is needed before grapheme rules apply correctly, grapheme clusters define the bidi run boundaries, and bidi levels set the shaping direction; the blueprint calls it the only valid ordering per the Unicode specs (§9, P3). Rejected: segment before normalizing, bidi before segmenting, or shaping before bidi (§9). When the rejected choice is right: streaming input that arrives a character at a time and needs sub-millisecond latency per grapheme, at the cost of segment rules that must tolerate non-normalized text, which the annexes do not guarantee (§9).

Algorithmic normalization (ADR-08)

Chosen: decompose, canonical-order and compose, all four forms from one set of tables, with Hangul as arithmetic (§9). Rejected: a precomputed table from code point to its NFC string (§9). When the rejected choice is right: NFC only, severely limited ROM (under 64 KB) and a bounded repertoire, where random access beats recursive decomposition on hot paths such as key comparison (§9).

An ordered rule machine for graphemes and words (ADR-10)

Chosen: rules numbered like the annex, with state tracked per boundary (§9, P5). Rejected: a compiled pair table (property by property gives break or no break), or a regex automaton (§9). When the rejected choice is right: a pair table wins when the emoji ZWJ and flag-pair state are not needed, such as a terminal that skips emoji clusters, and speed matters most (§9).

Hand-rolled, bounds-checked font parser (ADR-13)

Chosen: a parser inside ush-shape that validates every offset and length (§9, P6). Rejected: depend on ttf-parser or allsorts (§9). When the rejected choice is right: when time to market is the constraint and the parser is not a learning exercise; ttf-parser is mature, fuzz-tested and covers CFF and variable fonts that this design defers (§9).

Glyph 0 for a cmap miss (ADR-17)

Chosen: a missing character gets glyph id 0, never a panic, with its cluster kept (§9, P13). Rejected: skip the character, or substitute U+FFFD (§9). When the rejected choice is right: substituting U+FFFD wins in a system with automatic font fallback, such as a web browser: skipping .notdef avoids visible tofu boxes and lets the layout engine detect the miss and re-shape the run with a fallback font (§9).

Roads not taken (Alternative Architectures, Deferred Features)

A monolithic C stack of ICU, FriBidi and HarfBuzz (Alt-1) wins when a browser or desktop app already links ICU and HarfBuzz; Pango and Qt do this. It is rejected here because the goal is to learn the algorithms and those libraries cannot be no_std (Alternative Architectures).

A bytecode VM for break rules, as ICU's rule-based break iterator does (Alt-2) wins when break rules must change by a data-only update. With the Unicode version pinned, generated pair tables are simpler and faster (Alternative Architectures, ADR-04).

A push-down transducer for normalization (Alt-3) wins for streaming, such as normalizing keystrokes in a chat app. The blueprint offers an incremental normalizer but keeps batch as the main API (Alternative Architectures, §15).

A GPU-resident shaper (Alt-4) wins when a GPU text renderer shapes thousands of glyphs in parallel; it needs a different programming model and gives up no_std, and the serial version is its prerequisite (Alternative Architectures).

Deferred features (§1): CFF fonts, scripts beyond Arabic and one Indic, locale line-break tailoring, variable-font axes and vertical text are marked PhaseDeferred (§1).

What must never be false

The blueprint names these INV-1 to INV-12; they are written I1 to I12 here (§7).

  • I1: normalizing twice equals normalizing once. Noticed by NormalizationTest.txt checks and a debug assert that quick_check on the output is Yes (§7).
  • I2 and I3: equal-ccc marks keep their order, and NFD of NFC of x equals NFD of x up to canonical equivalence. Noticed by equal-ccc tests, a differential test against ICU and the test-file columns (§7).
  • I4: no grapheme boundary falls between a base and its marks, inside a ZWJ emoji sequence or inside a flag pair. Noticed by a failing GraphemeBreakTest.txt row, whose error names the rule (§7).
  • I5: bidi levels never exceed 125. Noticed by a debug assert at every Level construction and by a trace! message on an ignored embedding (§7).
  • I6: reorder_line returns a permutation of the line's indices. Noticed by a debug sorted-equals check and a fuzz target on random level sequences (§7).
  • I7: every font-table read is bounds-checked. Enforced by .get() instead of [] indexing; noticed by libFuzzer on a corpus of malformed fonts (§7).
  • I8: the cluster map is monotonic and every value is inside the input. Noticed by a debug assert after each GSUB lookup and by comparison with HarfBuzz fixtures (§7).
  • I9: a lookup applies only to glyphs its coverage table matches. Noticed by tests with glyphs outside coverage and a lookup_skip trace (§7).
  • I10: without GPOS, total advance equals the sum of hmtx advances, and a ligature's advance is its own glyph's advance. Noticed by golden advance sums in Phase 13 (§7).
  • I11 and I12: unassigned and noncharacter code points are processed, never dropped; identical inputs give byte-identical output. Noticed by tests for U+FFFF and U+FDD0, and by running fixtures twice and XORing the outputs (§7).

What breaks in production

FM-1: normalization differs from NormalizationTest.txt. Causes: wrong decomposition order (for example the Hangul arithmetic), an unstable sort, a wrong exclusion set, or a missed intervening starter in the blocked check. Detection: the Phase 13 harness fails on the first divergence. Recovery: none automatic; dump the decomposed and ordered sequence, then disable composition and check NFD first (FM-1).

FM-2: bidi reorder differs from BidiTest.txt. Causes: stack push/pop confusing isolates and embeddings, wrong start/end types for an isolating run sequence, wrong weak-rule order, wrong bracket pairing, or L2 applied to the wrong range. Detection: BidiTest.txt and BidiCharacterTest.txt. Recovery: dump each character's level after each rule stage and find the first divergence (FM-2).

FM-3: GSUB/GPOS misapplied against HarfBuzz. Symptom: missing ligature, wrong form, or wrong advances. Causes include feature order, LookupFlag skipping the wrong glyphs, and reversed lookahead direction in right-to-left buffers. Detection: diff of glyph ids, clusters and advances against HarfBuzz fixtures. Recovery: a lookup-trace hook to diff lookup by lookup (FM-3).

FM-4: truncated or corrupt font. Face::new() returns Err(ParseError) with the table tag and offset; recovery is to shape with .notdef for every glyph and return both the error and the glyph-0 buffer (FM-4, §4).

FM-5: tofu from a cmap miss. Glyph id 0 appears for characters the font should cover, from a cmap off-by-one, a BMP-only font given supplementary characters, or the wrong encoding choice. Detection: a tofu-rate metric and Buffer::notdef_count() (FM-5).

FM-6: cluster map desync. Symptom: wrong cursor or hit-test after a ligature or split. Cause: a merge or split not propagating the right cluster value. Detection: Buffer::verify_clusters(). Recovery: it returns ClusterInvariantViolated and the caller falls back to character-offset equals glyph-index (FM-6).

The threats a reader should know (Threat Model):

  • T1, a malformed or hostile font, is met by checking offset + length <= font.len() before every slice, capping arrays at maxp.numGlyphs, and returning .notdef on failure (Threat Model).
  • T2, a complexity attack through contextual lookups, is met by a per-buffer cap of 16 * buffer.len() substitution steps and ShapeError::LookupOverflow (Threat Model).
  • T4, memory blowup from thousands of combining marks, is met by inserting U+034F after every 30 non-starters and capping decomposition depth at 32 (Threat Model, §4).
  • T7, look-alike characters used to spoof URLs or usernames, is out of scope: callers must apply Unicode confusable detection themselves, and normalization is not a security guarantee (Threat Model).

The numbers

These are design targets from §4 unless marked as capacity arithmetic; the blueprint says they were measured on a 2020-era x86_64 at 3 GHz, single thread, no SIMD (§4).

Quantity Target Condition (§4)
normalize NFC on already-NFC text > 100 MB/s quick-check span skip
normalize NFD, general text > 30 MB/s full decompose and order
Grapheme iteration > 50 M graphemes/s single pass
Word and line-break iteration > 40 M chars/s same pattern
process_paragraph (bidi) < 10 µs per KB linear time
shape, Latin word of about 8 characters < 2 µs cmap, liga, kern
shape, Arabic word of about 6 characters < 5 µs joining plus contextual GSUB

Latency for a 1 KB mixed paragraph, p50 / p95 / p99 (§4): normalize of NFC input under 2 / 5 / 10 µs; segment under 3 / 6 / 12 µs; process_paragraph under 5 / 10 / 20 µs; shape with a Latin font under 20 / 40 / 80 µs; the full pipeline under 30 / 60 / 120 µs.

Hard limits (§4): Unicode 15.1; bidi depth 125; stream-safe cap 30 marks per starter; GSUB/GPOS nested-lookup depth 64; static tables under 2 MB with a target near 1 MB. The capacity model gives these estimates with the blueprint's own formulas:

Decomposition tables (C2) entries x average entry size about 42 KB
Composition table (C3) composites x 12 B about 11 KB
Normalize working set (C4) at most 3 x input length (worst-case compat) O(n)

The blueprint contradicts itself on several numbers; both sides are given and not resolved:

  • Total schedule. §1 gives about 6 to 14 weeks; Appendix B says "~16 weeks", and its per-phase durations differ from §1's (Phase 0 is "1 wk" in §1 and "3 days" in Appendix B; Phases 10 and 11 are "2–3 wks" together in §1 and 2 weeks each in Appendix B) (§1, Appendix B).
  • Table size. §4 says under 2 MB (target about 1 MB); §2 and §3 say under 1 MB; C1 says about 300 KB; the Phase 1 test caps tables at 307200 bytes; Appendix B names a "64 KB budget"; ADR-05 says about 8 to 16 KB per property while C1 puts one near 162 KB. Block size also differs: §3 has a 9-bit index block, while §11.1 and C1 use 64-entry blocks (§2, §3, §4, §11, §13, ADR-05, C1, Appendix B).
  • Throughput. §4 says NFC fast path above 100 MB/s, while the Performance Engineering table headed "§4 Performance Targets" says 400 MB/s or more, and C8 cites that 400 MB/s as the §4 target. Phase 3 wants quick_check at 800 MB/s or more; Appendix B wants normalize at 200 MB/s or more and §25 says 150 MB/s or more. Graphemes: §4 says above 50 M/s, the Performance Engineering table 150 M/s, Phase 4 500 MB/s of ASCII and §25 10 M chars/s. Bidi: §4 says under 10 µs per KB, while the Performance Engineering table and §25 say 5 µs per 100 characters. Shaping is 50k glyphs/s in Appendix B and 100k in §25; C7 calls 100k a §4 target, but §4 has no glyphs/s row (§4, §15, §16, §25, Performance Engineering, C7, C8, Appendix B).
  • Recursion cap. §4 allows 64 nested lookups; P6, T1 and T2 cap depth at 8 (§4, P6, Threat Model).
  • Bidi overflow. §4 and T3 treat embeddings past depth 125 as BN; §8.4.3 ignores them and counts overflow isolates; INV-5 sets the level to the paragraph level. T3 calls the stack a fixed 125-entry array, §8.4.3 a Vec, and C5 128 entries (§4, §7, §8.4.3, Threat Model, C5).

How it compares

  • HarfBuzz is a shaper only; it delegates normalization and bidi to ICU or FriBidi. That suits browsers that already link ICU, and its cached shape plans amortize feature resolution across many calls (Comparative Architecture Table).
  • ICU4C is a broad internationalization library covering collation, number formatting and more, with a 3-level trie and an opaque data blob. That is right for Java, .NET and OS-level text where one integrated library beats composing several (Comparative Architecture Table). ADR-05 instead says HarfBuzz and ICU use the same two-stage structure as this design, and §5.3 says the CodePointTrie directly matches ICU's UCPTrie; the statements disagree (ADR-05, §5.3).
  • CoreText is tied to the macOS and iOS stack and uses the OS font cache. That is right for native Apple apps, and it cannot run on Linux or embedded targets (Comparative Architecture Table).
  • Pango with FriBidi is the GNOME/GTK stack, using HarfBuzz, FriBidi and FreeType with Fontconfig for font discovery. That fits GTK on Linux, at the cost of a long dependency chain and no embedded or WASM support (Comparative Architecture Table).

Questions to test yourself

  1. normalize(Nfc, s) returns QuickCheck::Yes on its fast path, yet a storage-key comparison fails. Is the bug in the Phase 1 QC encoding, the Phase 2 exclusion table, or a caller hashing pre-NFC input? (HQ2) — Hint: FM-1's debug steps, §15, and ADR-09.
  2. reorder_line gives the correct permutation on BidiTest.txt, but cursor positions are wrong in the layout engine. Which invariant catches this, and how can Phase 7 plus the Phase 9 cluster map produce it? (HQ3) — Hint: §19, §21, I6 and I8.
  3. A terminal moves the cursor two cells instead of one over a Latin base plus a Devanagari nukta (U+093C). Which GB rule applies, and what Phase 4 and Phase 9 output does the terminal need? (HQ9) — Hint: the rule table in §8.3, then §16 and §21.
  4. Why do the W and N rules run on isolating run sequences rather than on single level runs? Give an example from §8.4 that goes wrong without them. (HQ11) — Hint: MM9, §8.4.3, and §19.
  5. normalize(Nfd, s) is idempotent on every NormalizationTest.txt row but not on a synthesized run of 35 combining marks. Why is that expected rather than a bug? (HQ13) — Hint: T4, §4, §15.

If you only remember three things

The stages must run in the order normalize, segment, bidi, shape, and every rule is numbered like the Unicode annex so a failing test points at a rule (P3, P5, P1). A font is untrusted input, so every offset is bounds-checked and a miss gives glyph 0 instead of a panic (P6, ADR-17, I7). A cluster number ties each output glyph back to the text, and it must stay monotonic through every ligature and split (P7, I8, MM6).

Words used here

  • Code point: an integer from 0 to 0x10FFFF that names one Unicode character (§8.1, Glossary).
  • Grapheme cluster: what a user sees as one character; may be several code points (§8.1, MM1).
  • Normalization form: one of NFC, NFD, NFKC or NFKD, a chosen spelling of the same text (§3, MM2).
  • Combining class (ccc): a number per mark that fixes how marks are ordered; 0 means a starter (§8.1).
  • Blocked: a mark that cannot compose with a starter because a character in between has a combining class at least as large (§8.2.3, Glossary).
  • Stream-safe: text limited to 30 combining marks in a row, so lookahead stays bounded (§4, T4).
  • Embedding level: the bidi number per character; even is left-to-right and odd is right-to-left (§8.4).
  • GSUB / GPOS: the font tables that substitute glyphs and position them (§8.5.4, §8.5.5).
  • Coverage table: the list of glyphs a lookup applies to; others pass through (I9, §8.5.3).
  • Cluster: the number tying an output glyph back to the input text, for cursors and clicks (§8.5.6, MM6).
  • .notdef (tofu): glyph id 0, the box shown when a font has no glyph for a character (ADR-17, §8.5.2).
