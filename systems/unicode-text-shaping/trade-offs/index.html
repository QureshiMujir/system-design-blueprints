Decisions (§9) · 25 ADRs

ADR-01

Implementation language

Chosen

Rust 2021, MSRV 1.78

Rejected

C/C++, Python, Go, JS

When the rejected choice is right

C++ wins when integrating into an existing C++ rendering stack (e.g., Chromium Blink or Qt) where FFI cost and ABI mismatch outweigh safety gains; Python/JS win for offline batch text analytics where throughput is irrelevant and rapid iteration matters.

Why: Memory safety on untrusted font bytes; exhaustive enum match for bidi/break rule machines; const data for generated tables; no GC pauses

ADR-02

Workspace structure

Chosen

Six crates: ush-tables / ush-normalize / ush-segment / ush-bidi / ush-shape / ush-cli

Rejected

Monorepo single crate; separate repos

When the rejected choice is right

Single-crate wins for a research prototype or proof-of-concept where crate boundary ceremony slows iteration; separate repos win when teams own each sub-system independently and need independent semver cadences.

Why: Each crate is independently testable + publishable; minimal dep surface; no_std possible for core four

ADR-03

no_std for core crates

Chosen

ush-tables / ush-normalize / ush-segment / ush-bidi: no_std + alloc; ush-shape: no_std + alloc; ush-cli: std

Rejected

All-std; embedded-only no_std

When the rejected choice is right

All-std wins when the only deployment target is desktop/server Linux and the team wants simpler error handling (std::io, std::error::Error) throughout; the no_std constraint adds real API friction and is only worth it when WASM, kernel, or bare-metal targets are in scope.

Why: Core is usable in embedded / WASM targets; untrusted font parsing stays bounds-checked without OS; CLI needs std for file I/O

ADR-04

Unicode version

Chosen

Pinned: Unicode 15.1 (UCD 15.1.0)

Rejected

Latest-at-build; unpinned

When the rejected choice is right

Unpinned wins for a general-purpose system library that must track newly assigned scripts (e.g., a live web browser) where conformance tests are run per-release rather than per-commit and shipping stale property data is worse than transient divergence.

Why: Conformance tests (NormalizationTest, BidiTest, etc.) are version-specific; reproducible builds

ADR-05

Property table representation

Chosen

Two-stage CodePointTrie (index[] + data[], O(1) lookup, ~8–16 KB per property)

Rejected

match arms; phf perfect-hash; sorted binary-search array

When the rejected choice is right

match-arm wins when the property space is tiny (< 128 code points) and compile-time exhaustive checking matters (the compiler verifies completeness); perfect-hash wins when the set is sparse and read-only with no range queries (e.g., a keyword table in a lexer).

Why: Trie gives O(1) char lookup; compact in .rodata; no hash collisions; HarfBuzz/ICU use the same structure

ADR-06

Table generation

Chosen

tools/ binary parses UnicodeData.txt + auxiliary UCD files -> generates Rust const arrays at build time

Rejected

Vendoring unicode-normalization / unicode-bidi crates

When the rejected choice is right

Vendoring wins for a shipping product where build-time codegen is a CI maintenance burden and upstream crates are well-maintained; the tradeoff inverts when the team is not the one writing the Unicode algorithms (no-teach goal).

Why: Full control over trie packing + property subsets; no transitive dep licenses; can add custom properties

ADR-07

Pipeline order

Chosen

normalize -> segment -> bidi -> shape

Rejected

segment before normalize; bidi before segment; shape before bidi

When the rejected choice is right

An alternative partial order (segment before normalize then re-normalize) wins only in streaming contexts where text arrives character-by-character and latency per grapheme must be sub-millisecond — at the cost of requiring segment rules to tolerate non-normalized input, which the UAX specs explicitly do not guarantee.

Why: NFC required before grapheme rules apply correctly; grapheme clusters define run boundaries for bidi; bidi levels determine shaping direction; only valid ordering per Unicode specs

ADR-08

Normalization algorithm

Chosen

Decompose + canonical-order + compose (algorithmic)

Rejected

Precomputed NFC lookup table (cp -> nfc string)

When the rejected choice is right

Precomputed-lookup wins when only NFC is needed and ROM is severely constrained (< 64 KB total), and the code-point repertoire is bounded (e.g., a device handling only Latin + CJK-ext-A); the combinatorial table is large but random-access is faster than recursive decompose for hot paths like storage key comparison.

Why: Algorithmic handles all forms (NFD/NFC/NFKD/NFKC) from one set of tables; Hangul is pure arithmetic; table would be huge (full NFC pairs)

ADR-09

QuickCheck fast path

Chosen

Yes/No/Maybe per NFC_QC / NFD_QC / NFKC_QC / NFKD_QC properties; skip "Yes-only" spans

Rejected

Always run full algorithm

When the rejected choice is right

Always-full wins when the input corpus is known to be heavy with combining marks (e.g., transliterated Sanskrit, historical Greek manuscripts, RTL diacritics) where QC=Yes spans are rare and the QC scan itself becomes overhead rather than a shortcut.

Why: Majority of ASCII/Latin text is already NFC; fast path avoids decompose+recompose for >90% of common input

ADR-10

Grapheme/word rule encoding

Chosen

Ordered rule machine numbered to UAX #29 annex (GB1..GB999, WB1..WB999); state tracked per boundary

Rejected

Compiled pair table (property × property -> break|no); regex automaton

When the rejected choice is right

Compiled pair table wins for grapheme rules when ZWJ and RI stateful rules are not needed (e.g., a terminal emulator that does not need emoji ZWJ cluster support) and speed is paramount — the pair table avoids branch misprediction on the ZWJ/RI state.

Why: Ordered rules are auditable against the spec; pair table adequate for line-break (smaller rule set); ZWJ/RI state is explicit

ADR-11

Line-break encoding

Chosen

LB pair table (LbClass × LbClass -> B|N|^) + mandatory-break pre-check

Rejected

Pure ordered rules like GB

When the rejected choice is right

Pure ordered rules win if UAX #14 tailoring for specific locales (e.g., dictionary-based Thai/Khmer line breaking) is required — the pair table encodes only the default algorithm and cannot express dictionary-augmented rules without an additional state layer.

Why: LB has 50+ classes but rules reduce to a sparse pair table; pair table is faster + easier to validate against the spec's example table

ADR-12

Bidi explicit levels

Chosen

DirectionalStatusStack (max depth 125 per spec) with isolate tracking

Rejected

Flat level array with per-char FSM; recursive descent

When the rejected choice is right

Flat-array FSM wins when the implementation targets an environment with no heap (no Vec), depth ≤ 4 is contractually guaranteed (e.g., an embedded display rendering only L1–L3 bidi text), and the code-size budget prohibits a dynamic stack.

Why: Stack matches UAX #9 X-rule structure exactly; isolate entries on same stack avoid a separate isolate stack; depth cap enforced trivially

ADR-13

Font parsing

Chosen

Hand-rolled bounds-checked parser in ush-shape (offset + length validation on every table field)

Rejected

Depend on ttf-parser; depend on allsorts

When the rejected choice is right

Depending on ttf-parser wins when time-to-market is the constraint and the team is not building the parser as a learning exercise; ttf-parser is mature, fuzz-tested, and covers CFF/variable-fonts that we explicitly defer.

Why: No transitive unsafety from third-party font parsing on untrusted input; teaches the table layout; we parse exactly the tables we need

ADR-14

Glyph data model

Chosen

Buffer { infos: Vec<GlyphInfo>, positions: Vec<GlyphPosition> } with cluster invariant

Rejected

Separate arrays per field; interleaved struct-of-arrays

When the rejected choice is right

Interleaved SoA wins in SIMD-heavy shaping pipelines (e.g., a GPU-resident text renderer) where positions and infos are always processed together and cache-line packing of all fields per glyph reduces memory bandwidth; the trade-off is that the cluster map becomes opaque to SIMD operations.

Why: Matches HarfBuzz's buffer design; infos and positions parallel-indexed; cluster invariant enables cursor placement by caller

ADR-15

Shaper dispatch

Chosen

Shaper trait with ShaperLatin, ShaperArabic, ShaperIndic, ShaperGeneral; dispatched by script(c)

Rejected

Giant match in shaping loop; per-feature callbacks

When the rejected choice is right

Per-feature callbacks win in a plugin architecture (e.g., a browser where third-party ICU extensions must inject script-specific shaping without recompiling the engine); the trait object vtable cost is negligible compared to the benefit of hot-reload extensibility.

Why: Trait allows per-script collect_features / setup_masks / reorder without branching in hot path; new scripts added without touching core

ADR-16

GSUB/GPOS lookup dispatch

Chosen

Match on LookupType u16; one fn per type; subtable iteration with Coverage index

Rejected

Trait objects per lookup type; macro-generated dispatch

When the rejected choice is right

Trait-object dispatch wins when lookup implementations must be user-replaceable at runtime (e.g., a shaping engine that lets host apps override type-4 ligature application for custom cluster semantics); macro-generation wins when new lookup types are added frequently by contributors unfamiliar with the dispatch layer.

Why: Direct match is zero-cost; subtable fallback (first match wins) matches spec; Coverage index avoids per-glyph scan

ADR-17

.notdef / tofu policy

Chosen

cmap miss -> glyph_id = 0 (.notdef); no panic; cluster preserved; caller renders .notdef box

Rejected

Skip missing glyphs; substitute U+FFFD

When the rejected choice is right

Substituting U+FFFD wins for systems that render mixed-font paragraphs with automatic font fallback (e.g., a web browser's font-fallback chain): skipping .notdef avoids visible tofu boxes and lets the layout engine detect the miss and re-shape the run with a fallback font.

Why: Spec-compliant; .notdef glyph is always present in valid fonts; cluster preserves hit-testing

ADR-18

TrueType assumed; CFF deferred

Chosen

Parse glyf table only; CFF/Type2 charstring interpretation deferred to future phase

Rejected

Parse both now

When the rejected choice is right

Parsing both wins when the deployment target includes professional print workflows (Adobe Illustrator, InDesign, PDF generation) where CFF/OTF fonts are standard and TTF-only support produces visible metric differences on PostScript paths.

Why: Scope control; the vast majority of system fonts are TTF-flavored; CFF adds ~2000 lines of charstring interpreter with its own edge cases

ADR-19

#385 integration

Chosen

ush-shape emits Buffer; ush-cli pipes buffer to project #385 rasterizer via a shared type or serialized format

Rejected

Inline rasterization in ush-shape

When the rejected choice is right

Inline rasterization wins for a constrained embedded device where the IPC/serialization overhead between shaping and rasterization is prohibitive and both subsystems are maintained by the same team with no need for independent versioning.

Why: Clean separation of concerns; shaping is layout, rasterization is rendering; #385 can evolve independently

ADR-20

Differential oracle

Chosen

Tests compare against ICU4C (via C FFI or icu4x) + HarfBuzz (via hb-shape output) for normalization + shaping

Rejected

Self-consistency only

When the rejected choice is right

Self-consistency-only wins when the implementation intentionally diverges from ICU/HarfBuzz (e.g., a specialized shaper for a constructed script or a private corporate encoding) where the reference implementations are not authoritative; differential testing against them would produce false positives.

Why: Catches systematic spec misreads; HarfBuzz is the industry reference shaper; ICU is the reference normalizer

ADR-21

Conformance test suite

Chosen

UCD test files: NormalizationTest.txt, GraphemeBreakTest.txt, WordBreakTest.txt, LineBreakTest.txt, BidiTest.txt, BidiCharacterTest.txt (all at pinned Unicode 15.1)

Rejected

Handwritten unit tests only

When the rejected choice is right

Handwritten-only wins for a highly tailored engine that implements a strict subset of Unicode (e.g., ASCII + Latin-1 + Arabic only) where the UCD corpus exercises thousands of code points outside the supported range and generates false failures.

Why: Authoritative; covers thousands of tricky sequences; version-pinned for reproducibility

ADR-22

Fuzzing

Chosen

cargo-fuzz (libFuzzer) on: normalize (arbitrary &str), segment (arbitrary &str), bidi (arbitrary &str), font parser (arbitrary &[u8])

Rejected

AFL via afl.rs; no fuzzing

When the rejected choice is right

AFL wins when mutation-based coverage is needed for a target already well-covered by libFuzzer's value profiling, or when integrating with an existing security fuzzing infrastructure (OSS-Fuzz uses both; AFL++ with QEMU mode covers non-instrumented binary fonts).

Why: libFuzzer integrates with cargo natively; font parser on arbitrary bytes is highest-risk surface; normalize/segment/bidi must never panic

ADR-23

Benchmarks

Chosen

criterion crate; benches per crate (normalize: ns/char on ASCII/Latin/CJK; bidi: ns/char; shape: µs/glyph)

Rejected

Custom bench harness; no benches

When the rejected choice is right

Custom harness wins when benchmarks must share warm-up state across repeated calls (e.g., amortizing font parse cost across 10k shape calls) in a way that Criterion's per-iteration model cannot express without significant setup boilerplate.

Why: Criterion gives statistically stable results; per-char targets expose regressions early

ADR-24

Dependency policy

Chosen

Minimal: criterion (dev), cargo-fuzz (dev), no runtime dependencies in no_std crates

Rejected

Use unicode-normalization / unicode-bidi / ttf-parser as deps

When the rejected choice is right

Using upstream crates wins in a production library where correctness and maintenance velocity matter more than learning; unicode-normalization + unicode-bidi are battle-tested, actively maintained crates that receive Unicode-version updates quickly.

Why: Teaches the algorithms; no transitive unsafety; avoids license conflicts; consistent with project educational goal

ADR-25

Licensing

Chosen

MIT OR Apache-2.0 (Rust crate dual license); UCD data files covered by the Unicode License (UNICODE-3.0); note in NOTICE

Rejected

GPL; MIT only

When the rejected choice is right

GPL wins when the project is a research tool intended for academic environments where copyleft ensures all derivatives remain open; MIT-only wins when corporate legal teams prohibit Apache-2.0 (patent grant clause concerns).

Why: Dual license matches Rust ecosystem convention; Unicode License required for any bundled UCD data or generated tables derived from it

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Monolithic C Library with ICU/FriBidi/HarfBuzz linkage

+-----------------+     +-----------+     +----------+     +----------+
| ICU normalizer  | --> | FriBidi   | --> | HarfBuzz | --> | Buffer   |
| (ubidi + norm2) |     | (UAX #9)  |     | (shaping)|     | (output) |
+-----------------+     +-----------+     +----------+     +----------+
         ^                                      ^
         |                                      |
    UCD data blob                        font bytes (libfreetype)

Regime where it wins: When shipping a production browser engine or desktop application that already links ICU (for locale/collation/number formatting) and HarfBuzz (already used by GTK/Qt). The engineering investment in the component pipeline is already paid; adding ush as a competing implementation is wasteful. Pango on Linux and QTextLayout on Qt are real systems embodying this architecture.

Why this blueprint rejected it: The project's explicit goal is to learn the algorithms. Linking established libraries produces correct output but zero understanding of how it works. Additionally, no_std is incompatible with ICU/FriBidi/HarfBuzz (all require a POSIX environment), ruling out embedded/WASM targets.

Alt-2: Virtual-Machine Bytecode Interpreter (RBBI-style)

+---------------+     +-----------+     +-----------+
| Rule grammar  | --> | Bytecode  | --> | VM eval   |
| (RBBI format) |     | compiler  |     | per char  |
+---------------+     +-----------+     +-----------+
                           |
                     committed byte
                     code (icu .dat)

Regime where it wins: When break rules must be updated at runtime without recompiling the library — e.g., a deployment model where Unicode version bumps must ship as data-only patches (no binary recompile). ICU's RBBI engine embodies this: icu.dat contains compiled break-rule bytecode, and upgrading to Unicode 16.0 is a data-file swap, not a code change. This is critical for OS-level libraries (libICU on Android) updated through the OS image.

Why this blueprint rejected it: RBBI bytecode compilation is a non-trivial sub-project (lexer + parser + peephole optimizer). For the scope defined in §1 — a library with a pinned Unicode version (ADR-04) — the bytecode indirection adds complexity without benefit. Our generated pair tables (lb_table.rs) achieve the same data-driven result with simpler machinery and significantly faster interpreter throughput (table lookup vs bytecode dispatch).

Alt-3: Push-Down Transducer for Normalization

+---------------+     +-----------+     +-----------+
| Input stream  | --> | PDT rules | --> | Output    |
| char-by-char  |     | (NFD/NFC) |     | stream    |
+---------------+     +-----------+     +-----------+

Regime where it wins: For streaming normalization where output must be emitted character-by-character with minimal latency (e.g., a real-time chat application normalizing keystrokes before display). A push-down transducer can emit normalized output as soon as a starter is consumed, without buffering the entire combining-mark run. This architecture is described in the "Streaming Normalization" literature and is the basis for stream-safe text (UTN#27).

Why this blueprint rejected it: PDT normalization requires the stream-safe invariant (30-CC cap) to bound the push-down stack — otherwise correctness is not achievable for unbounded combining-mark runs. We implement stream-safe normalization as an optional IncrementalNormalizer in Phase 3, but the primary API is batch normalization (normalize(form, &str) -> String), which is simpler to test, audit, and prove correct against NormalizationTest.txt.

Alt-4: GPU-Resident Text Shaper

+-------------+     +-----------+     +-----------+     +--------+
| CPU: bidi + | --> | GPU: GSUB | --> | GPU: GPOS | --> | Pixel  |
| normalize   |     | (compute  |     | (compute  |     | output |
+-------------+     | shader)   |     | shader)   |     +--------+
                    +-----------+     +-----------+

Regime where it wins: For a GPU-resident text renderer (e.g., a game engine or a GPU-accelerated terminal emulator like WezTerm or Alacritty's proposed GPU backend) where text shaping is the performance bottleneck and thousands of glyphs must be shaped in parallel. Lookup tables (Coverage, ClassDef) map cleanly to GPU buffer reads; ligature matching can be parallelized across non-overlapping glyph runs. NVIDIA's DLSS text stack uses a variant of this approach.

Why this blueprint rejected it: The GPU shaper requires a fundamentally different programming model (WGSL/GLSL/SPIR-V), eliminates no_std compatibility, and requires the font tables to be uploaded to GPU memory as read-only buffers. The serial Rust pipeline is a prerequisite — GPU shaping requires a correct CPU reference implementation to validate correctness. Building the GPU variant is a future Phase 14+ extension, not the core scope.
