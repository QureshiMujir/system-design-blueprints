⬜ Phase 0 — Correctness Kernel & Repo Skeleton §12

Objectives

Stand up the repo skeleton (§10) and the correctness kernel: URDNA2015 canonicalisation, BLAKE3 shard fingerprinting, and a pre-signature Manifest parse/serialize round-trip. No signing yet — that is Phase 1 (§13). Establish the CI matrix.

Deliverable

lineage-py v0.0.1, installable via uv pip install -e .; CLI lineage-cli fingerprint <file> prints a BLAKE3 shard id — an operator-inspectable artefact; CI green on the full matrix.

Acceptance

Round-trip byte-identity on ≥ 500 Hypothesis-generated manifests (fixed seed); avalanche property holds over 100 randomised single-byte shard mutations (no fingerprint collision); CI wall-clock < 6 minutes; fixture manifest-minimal.json round-trips exactly.

Fixtures

fixtures/manifest-minimal.json — smallest valid pre-signature manifest | round-trip byte-identity. fixtures/manifest-malformed-missing-context.json — no @context | MUST raise SchemaError at Canonicalised (§8.2). fixtures/shard-empty.bin — zero-length shard | fingerprint defined and stable across runs.

Pitfalls

URDNA2015 blank-node labelling is non-deterministic across implementations — Lineage v1.0 manifests MUST NOT use blank nodes (documented, tested by fixture above). BLAKE3 streaming vs one-shot API produces different intermediate state if mixed — pin to the one-shot API through Phase 5. IEEE-754 double round-trip loss through naive JSON float parsing — enforce exact round-trip in the property test (ties to I9, the schema's numeric-precision rule, §11).

⬜ Phase 1 — Manifest Schema & Signing §13

Objectives

Complete the Manifest schema (§11) with signature; implement Ed25519 signing/verification (ADR-04, P5) and the full §8.2 verification state machine through SignatureChecked.

Deliverable

lineage_py.Manifest.sign() / .verify_signature() round-trip; a re-parse-and-reverify smoke script confirming an independently-loaded verifier accepts a manifest it did not build.

Acceptance

100% of 200 generated valid manifests verify; 100% of 50 tampered manifests (single-byte mutation post-signature) are rejected at SignatureChecked (I2); clock-skew fixture (issued_at = now+61s) rejected 100% of the time (I6); signing latency p95 < 5 ms on reference hardware.

Fixtures

fixtures/manifest-valid-signed.json | verifies true. fixtures/manifest-tampered-byte.json | MUST reject at SignatureChecked. fixtures/manifest-future-clock.json (issued_at=+61s) | MUST reject at SignatureChecked per I6. fixtures/manifest-unknown-algorithm.json | MUST reject (unrecognised algorithm enum value).

Pitfalls

Re-serialising a parsed manifest with a different key order before re-canonicalising silently breaks verification — always canonicalise, never re-serialise ad hoc (MM3, §34). Treating algorithm as advisory rather than signed material opens a downgrade path (T11) — it MUST be included in the canonical form prior to signing. Key files committed to the demo repo by accident — .gitignore + a pre-commit secret scanner is mandatory from this phase.

⬜ Phase 2 — Influence Tracer Core §14

Objectives

Implement the reference Influence Tracer for Llama 3 8B: the Two-Stage Retrieval Strategy (ADR-10) atop TRAK (ADR-09, Park et al. 2023, §5), sentence-level span granularity (default per §11's OutputSpan), and the reproducibility floor (I4, ε ≤ 1e-3).

Deliverable

An end-to-end prompt → completion → InfluenceVector[] pipeline over the mini-corpus; five reference traces (fact-completion, code snippet, paraphrase, refusal, hallucination-prone question) captured as fixtures.

Acceptance

Reproducibility: re-running all 5 reference traces with identical seeds reproduces top-16 scores within ε ≤ 1e-3 absolute (I4); tracer inline overhead ≤ 10% of base inference latency p95 (M3, §32); coverage_score for each reference trace within 5% of the held-out 1,000-shard brute-force estimate.

Fixtures

fixtures/trace-fact-completion.json, fixtures/trace-code-snippet.json, fixtures/trace-paraphrase.json, fixtures/trace-refusal.json, fixtures/trace-hallucination.json — each: prompt | expected top-5 shard IDs + score tolerance band.

Pitfalls

Stage-1 retrieval recall too low silently caps Stage-2 accuracy — a shard genuinely influential but outside the top-4096 cosine-similarity cohort never appears, and coverage_score will look artificially high unless validated against the held-out estimator (I3 — this is precisely why the invariant requires cross-validation, not self-report). TRAK's random-projection dimension too small trades variance for speed — under-provisioning it produces estimator_variance values that make the manifest technically valid but practically noisy (Grosse et al. 2023, §5, document this failure mode at scale).

⬜ Phase 3 — Tracer Conformance Suite §15

Objectives

Build the Tracer Conformance Suite: the mechanism that makes "Lineage v1.0 conformant" a binary, falsifiable claim (P9) rather than a marketing assertion, satisfying §7's debugging-methodology requirement (the Verification Simulator).

Deliverable

packages/tracer-conformance/ publishable as a standalone package; a conformance report (conformance-report.json) enumerating pass/fail per invariant ID.

Acceptance

100/100 reference prompts pass within documented tolerance bands; the reproducibility test (I4) passes for all 100; replay-rejection test rejects 100% of 50 synthetic replay attempts (I5); the suite completes in < 15 minutes on the reference CI runner.

Fixtures

conformance/corpora/conformance-mini/ — the published 10,000-shard corpus + embedding index. conformance/fixtures/ground-truth-100.yaml — declarative per-prompt expected top-k + score tolerance. conformance/fixtures/replay-attack-suite.json — 50 (issuer, nonce) reuse attempts.

Pitfalls

Ground-truth curated from a single brute-force run without cross-checking against a second independent implementation risks encoding a bug as "ground truth" — the suite's ground truth was cross-validated against an independent Koh–Liang-style implementation before being locked. A suite that only tests the happy path gives false confidence — malformed, replay, and revocation cases (I5, I13) are mandatory, not optional additions.

⬜ Phase 4 — Python SDK (`lineage-py`) §16

Objectives

Productionise lineage-py into a stable, documented, ≥ 85%-covered package exposing emit, parse, sign, and verify as a public API — the reference implementation every other SDK (§17) and the verifier (§18) is measured against.

Deliverable

lineage-py 1.0.0 on PyPI; API docs generated from docstrings; a migration guide for the pre-1.0 internal API used in Phases 0–3.

Acceptance

≥ 85% line coverage (pytest-cov); zero mypy strict-mode errors; PyPI install-and-import smoke test green on Linux/macOS/Windows; conformance suite (§15) green against the packaged wheel, not just the source tree.

Fixtures

fixtures/sdk-public-api-surface.json — a frozen list of public symbols; a CI check diffs against it and fails on any undocumented removal (enforces P6). fixtures/sdk-import-smoke.py — minimal import + round-trip script run against the built wheel.

Pitfalls

Exposing internal canonicalisation helpers as public API accidentally locks an implementation detail into the compatibility contract (P6) — the frozen-surface fixture (§16.5) exists precisely to catch this before 1.0.0 ships. Type-hint drift between the dataclass (§11) and the Protocol ABI (§11's LineageTracer) causes silent structural mismatches — a mypy strict CI gate prevents merge.

⬜ Phase 5 — JavaScript SDK (`lineage-js`) §17

Objectives

Ship lineage-js as a parser/verifier-only port (ADR-13) — no tracer — giving every browser/Node consumer the ability to parse, canonicalise, and verify a manifest built by lineage-py.

Deliverable

lineage-js 1.0.0 on npm; a cross-language conformance test proving every Phase-3 (§15) fixture verifies identically in Python and JS.

Acceptance

100% of the Phase-3 conformance vectors (§15.5) verify identically in both languages; bundle size ≤ 50 KB minified+gzipped (browser-budget constraint); zero runtime dependencies beyond @noble/ed25519 and jsonld.

Fixtures

fixtures/cross-lang-vector-*.json — reused from §15.5's ground truth, re-asserted here as "verifies true/false identically in both SDKs." fixtures/js-bundle-size.json — CI-checked byte budget.

Pitfalls

jsonld's JS canonicalisation implementation historically diverges from pyld's on edge-case context resolution (network-fetched vs embedded context) — Lineage v1.0 pins the context to a locally-embedded copy in both SDKs, never a live network fetch, to eliminate this divergence class entirely.

⬜ Phase 6 — Verifier Service v0 §18

Objectives

Ship a self-hostable verifier (Docker image) implementing the full §8.2 state machine end-to-end, satisfying P2 (verifiable without contacting the issuer) at the operator level.

Deliverable

A running verifier passing every Phase-3 (§15) conformance vector; a docker-compose stack (verifier + Postgres + Redis) startable in one command.

Acceptance

100% of conformance-suite vectors (§15) pass against the deployed verifier, not just the SDK in-process path; cold start ≤ 5 s to healthy (M12, §32); p95 signature-only verify < 100 ms (M1) on reference hardware with a warm connection pool.

Fixtures

fixtures/verifier-e2e-suite.json — HTTP-level replay of every §15.5 vector against the live /v1/verify endpoint. fixtures/verifier-replay-http.json — 50 replayed HTTP requests, 100% expected-rejected.

Pitfalls

Postgres connection-pool exhaustion under burst load manifests as p99 latency spikes, not errors — undetected without explicit pool-saturation metrics (§18.10). Redis replay-cache eviction tuned too aggressively silently shrinks the effective replay window below the spec's 24h (I5) — validated by a fixture that submits a nonce at T+23h59m and expects rejection on reuse.

⬜ Phase 7 — Verifier Service at Scale §19

Objectives

Take the Phase-6 (§18) single-node verifier to a multi-region, quorum-capable fleet meeting the §4 throughput ceiling (≥ 1M verifications/week at launch, ≥ 10M/week stretch).

Deliverable

A publicly reachable hosted verifier sustaining the load-test target; a published pen-test remediation log; a quorum-client reference package.

Acceptance

Sustained load test: 5,000,000 verifications/week at p95 < 200 ms (§4's combined signature+partial-dereference budget) for 72 continuous hours; cross-region failover completes within RTO ≤ 15 min (§4); zero unresolved critical/high findings from the pen-test before public launch.

Fixtures

fixtures/load-test-profile.yaml — declares the 5M/week sustained load shape (diurnal pattern, §36). fixtures/region-failover-drill.json — simulated IAD outage, expected FRA/SIN takeover within RTO. fixtures/quorum-disagreement.json — two verifiers disagreeing on one manifest, expected quorum-client verdict = unverified (fail-closed, P11).

Pitfalls

Active-active replication lag between regions creates a window where a nonce accepted in IAD has not yet propagated to FRA's replay cache — a replay inside that window is a real risk; mitigated by a conservative propagation-lag SLO monitored explicitly (§19.10), not assumed away. Load-testing against a single region and extrapolating linearly ignores cross-region replay-cache synchronisation overhead — the load test (§19.5) is run against the full multi-region topology, never a single-node proxy for it.

⬜ Phase 8 — Hover-UI Library §20

Objectives

Ship @lineage/hover-ui: a framework-agnostic client that renders per-sentence provenance, strictly consuming only the §8.2 Verified/Verified-Partial states — never rendering a provenance card from an unverified manifest (P11, I2).

Deliverable

@lineage/hover-ui 1.0.0 across all three framework wrappers; a Storybook showcase; an accessibility audit report (keyboard nav, ARIA, screen-reader smoke test).

Acceptance

Hover-to-card render p95 < 50 ms (M9, §4); zero WCAG 2.1 AA violations in the accessibility audit; 100% of fixtures render "unverified" (no card) for every non-Verified* §8.2 terminal state.

Fixtures

fixtures/hover-ui-verified.json | renders a full provenance card. fixtures/hover-ui-partial.json | renders card with "some sources restricted" indicator. fixtures/hover-ui-unverified.json | renders no card, small unverified indicator only.

Pitfalls

Caching a VerificationResult client-side past its ttl_seconds silently shows stale provenance as if freshly verified — the library re-checks staleness against ttl_seconds before rendering, never trusting a cached verdict indefinitely. Rendering a snippet when excerpt_policy changed server-side after the client cached an earlier response — the client MUST treat excerpt_policy as authoritative from the latest resolve call, not a cached one.

⬜ Phase 9 — Auto-Redact Tooling §21

Objectives

Ship lineage-redact: a CLI + library converting (output, manifest, policy) into a policy-conformant output, using only verified TrainingShardRef licence data (§11) — never an unverified or fallback span.

Deliverable

lineage-redact CLI; a RedactionReport enumerating every policy hit with the triggering shard ID and licence.

Acceptance

200 hand-curated redaction scenarios (§21.5) pass with byte-exact expected output; the paraphrase strategy's re-trace step confirms ≥ 95% of rewrites reduce the offending shard's influence score below the policy threshold on the first attempt (remaining 5% trigger a second rewrite pass, capped at 3 attempts before falling back to remove).

Fixtures

fixtures/redact-200-scenarios.yaml — declarative (output, manifest, policy) → expected redacted output + RedactionReport. fixtures/redact-fallback-span.json — a kind:"fallback" span | MUST redact conservatively (policy-unknown treated as non-compliant).

Pitfalls

The paraphrase strategy re-generating text that reintroduces the same offending influence under a different surface wording — caught only by the mandatory re-trace step (§21.2); a naive implementation that paraphrases without re-tracing silently ships non-compliant output disguised as compliant.

⬜ Phase 10 — Selective Disclosure (ZK) §22

Objectives

Implement zk_selective_disclosure (§11's ZkInfluenceProof, referenced in I12): prove a shard within a committed set influences an output above a threshold, without revealing the shard (P4, P12).

Deliverable

A reference Groth16 circuit + prover + verifier; a manifest example (examples/manifest-zk-disclosure.json) using the capability.

Acceptance

Proof generation time p95 < 2 s per span on reference hardware; proof size ≤ 200 bytes (Groth16's constant-size property); verification time p95 < 10 ms; 100% of 50 crafted false-witness attempts (proving influence for a shard not in the commitment set) rejected.

Fixtures

fixtures/zk-valid-proof.json | verifies true. fixtures/zk-false-witness.json — proof for a non-member shard | MUST reject. fixtures/zk-wrong-threshold.json — proof claiming a threshold the underlying influence doesn't meet | MUST reject.

Pitfalls

Groth16's trusted setup is circuit-specific — reusing a setup across a circuit change silently breaks soundness; the setup ceremony output is versioned and pinned per ADR-12's locked choice, with the "rejected choice wins" column (§9) naming exactly when a transparent-setup system becomes necessary. Treating "proof verifies" as "the manifest is fully verified" conflates I2 (signature) with the ZK proof's separate, narrower guarantee — the two checks are independent and both required.

⬜ Phase 11 — Training-Time Hooks §23

Objectives

Land a lineage_hooks extension in one major OSS training stack (Hugging Face Transformers Trainer, priority target) to replace post-hoc tracing (§14) with training-time shard-fingerprinted gradient capture — closing the gap Grosse et al. (2023, §5) identify between retrofit and production-grade influence tracing.

Deliverable

A merged PR in the target OSS training stack; a fidelity report; a tutorial for a downstream lab adopting the hooks.

Acceptance

Training-time vs retrofit-traced top-16 influence agreement ≥ 90% overlap by shard ID on 20 shared reference prompts; hook overhead ≤ 5% of training step wall-clock (a distinct, tighter budget than the inference-time M3, since training runs are far longer and costlier); maintainer sign-off on the merged PR (a human acceptance criterion tracked alongside the numeric ones).

Fixtures

fixtures/training-hook-fidelity-20.yaml — 20 prompts, retrofit vs training-time top-16, with expected overlap ≥ 90%. fixtures/hook-overhead-benchmark.json — training-step wall-clock with/without hooks enabled.

Pitfalls

Gradient-summary capture at every training step is far more data than a per-output tracer ever sees — naive full-gradient storage blows the training-run's disk budget; the hook stores a Kronecker-factored summary (George et al. 2018 EKFAC, §5, if_ekfac in §11's InfluenceMethod enum), not raw gradients. A maintainer-facing PR that changes core training loop control flow (rather than adding hook call-sites) will be rejected on review — the hook contract is deliberately call-site-only, never a control-flow change.

⬜ Phase 12 — Royalty Clearinghouse §24

Objectives

Close the economic loop: convert verifier-counted (never self-reported, P10) influence attributions into per-shard royalty events for a rights-holder coalition, without the core protocol mandating any specific payment mechanism (§1's non-goals).

Deliverable

A running registry + counting service; a first quarterly settlement statement for one pilot rights-holder coalition; a dispute-resolution runbook (spot-check re-tracing by a neutral third party).

Acceptance

100% of settlement amounts independently recomputable from the verifier event log by a third-party auditor script; anomaly detector flags ≥ 95% of synthetically injected influence-inflation attempts (50 synthetic cases) without flagging more than 5% of the legitimate baseline (false-positive bound).

Fixtures

fixtures/clearinghouse-settlement-recompute.json — a settlement period's raw events → expected recomputed statement. fixtures/clearinghouse-inflation-attack.json — 50 synthetic influence-inflation attempts | ≥ 95% flagged.

Pitfalls

Allowing any producer-side self-reported influence count into the settlement calculation reopens T10 (royalty-clearinghouse fraud) — the counting service reads only the verifier's own event log, never a producer-submitted summary. A settlement formula that weights raw top-1 influence equally regardless of coverage_score rewards low-fidelity sampled manifests unfairly relative to full ones — the formula weights by score × coverage_score (ties to I3), not raw score alone.

⬜ Phase 13 — Audit-Grade & Regulatory Hardening §25

Objectives

Ship the audit-grade enterprise tier and the compliance evidence required for regulated-industry deployment: single-tenant on-prem verifier, SOC 2 Type II + ISO/IEC 42001 readiness, and the conformance posture cited in regulatory engagement (§1's Phase-4-equivalent objective).

Deliverable

A SOC 2 Type II report; an ISO/IEC 42001 certification (or a dated readiness assessment if certification is still in progress); an air-gapped installer package; an audit-log export format specification.

Acceptance

SOC 2 Type II observation period ≥ 6 months with zero unremediated critical exceptions; air-gapped installer completes a from-scratch verifier deployment in ≤ 30 minutes on reference hardware with zero network egress during install; audit-log export validated against a named customer SIEM ingestion format (e.g. Splunk CIM or an OTel-compatible schema).

Fixtures

fixtures/airgap-install-checklist.yaml — step-by-step install with expected artefacts at each step, no network calls permitted. fixtures/audit-log-export-sample.json — one full day's verification events in the published export schema.

Pitfalls

An "on-prem" installer that silently phones home for a licence check violates the air-gap promise (P2's self-hostability extended to full network isolation) — licence validation is therefore an offline, cryptographically-signed token check, never a network call. Treating SOC 2 controls as a one-time checklist rather than continuously operated evidence collection fails the Type II observation period, which requires sustained operation, not a point-in-time snapshot.
