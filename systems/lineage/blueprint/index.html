12 — Lineage

Project Number: 12

Project Name: Lineage

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Lineage is a protocol-level cryptographic provenance layer for AI-generated text. For every addressable output unit a language model emits, a Lineage-conformant producer computes an InfluenceVector — a per-span, signed, quantitative attribution of which training shards, retrieval documents, system prompts, and model weights most shaped that output — and packages it into a signed LineageManifest (JSON-LD, Ed25519, URDNA2015-canonicalised) that any third party can verify without contacting the issuer. A Verifier Service dereferences manifests on demand; a Hover-UI client renders per-sentence provenance; an Auto-Redact tool strips unlicensed spans; a Royalty Clearinghouse closes the economic loop with rights-holders. The system is TLS-for-training-data: it does not certify that an output is true, only what taught the model to produce it.

Phase-0 deliverable (numbered):

  1. lineage-py package skeleton with canonicalisation (URDNA2015) and shard fingerprinting (BLAKE3) modules — no signing yet.
  2. A round-trip property-test harness (Hypothesis) proving manifest encode→decode→encode byte-identity.
  3. A CI matrix (GitHub Actions, Linux + macOS, Python 3.11/3.12).
  4. A minimal CLI (lineage-cli fingerprint <file>) as an inspectable, operator-facing artefact.

System boundaries.

  • Provides: a signed wire format for training-data influence; a normative tracer contract; a verifier API; SDKs (Python full, JS parser/verifier); UI + redaction tooling; a royalty settlement layer.
  • Delegates: pixel/audio/video provenance (C2PA's domain, §35); AI-generation detection (SynthID's domain, §35); general observability (OpenTelemetry-for-LLMs); foundation-model training itself; hosted inference.
  • Does NOT provide: proof that a generated claim is factually correct; a payment rail (settlement mechanism is pluggable, §24); retroactively-forced adoption by any lab.

Non-goals. Not a watermark. Not a content-authenticity standard for non-text media. Not a synthetic-media detector. Not a generic AI-safety platform.

Deployment model. A model-runtime library (tracer, inline or batched) + a stateless signer

  • a horizontally-scaled verifier fleet (stateful only in Postgres/Redis, §18–§19) + client libraries. No component requires multi-party coordination to deliver value to a single adopter (Design Principle P7, §6).

Target users/operators. Frontier-lab ML infrastructure teams (producers); enterprise legal/compliance and publisher integrators (consumers); a hosted-verifier operator (this project, Phase 6–7); standards-body editors (Phase 11 onward, out of blueprint scope — see Deferred Features Register, §39).

What later phases unlock. Phase 2 unlocks measurable influence; Phase 3 unlocks third-party-auditable tracer correctness; Phases 4–5 unlock integrator adoption; Phases 6–7 unlock a verifier network effect; Phase 8–9 unlock end-user-visible provenance and policy enforcement; Phase 10 unlocks privacy-preserving disclosure; Phase 11 unlocks lab-side training-time fidelity; Phase 12 unlocks rights-holder economics; Phase 13 unlocks regulated-industry deployment.

Recommended language + rationale. Python 3.12+ for the reference tracer, verifier, and redaction tooling — the influence-functions/TRAK research ecosystem (PyTorch, Faiss) is Python-native (ADR-01, §9); TypeScript 5.x for the consumer-side SDK and Hover-UI, because every manifest consumer is a web or Node application. Rejected: Rust-only (no ML ecosystem parity for the tracer; reserved instead as a Phase-6+ hot-path optimisation, ADR-01); Go-only (no mature JSON-LD/URDNA2015 or TRAK bindings).

Prerequisites. Applied cryptography (signature schemes, canonicalisation, replay defence); distributed-systems fundamentals (replication, quorum, backpressure); influence-function / gradient-based ML theory; JSON-LD and linked-data modelling; provenance-database theory (semirings, PROV).

Estimated timeline. Phase 0: 3 weeks. Full system (Phase 0 → Phase 13): ~40 months end-to-end, front-loaded (Phases 0–5 land inside 7 months; Phases 6–13 are infrastructure and standards work measured in quarters).

Deferred features (register at §39): post-quantum default signature switch PhaseDeferred("§9"); on-chain royalty settlement PhaseDeferred("§24"); token-granularity default tracing PhaseDeferred("§14"); federated on-device-only verification PhaseDeferred("§38").

2. Why Build This

Lineage teaches the full stack of a real-world cryptographic protocol: wire-format design under a no-breaking-changes constraint, canonicalisation as a precondition for signing, replay/downgrade defence, a sampling theory for an intractable full computation (influence functions at frontier scale), a verifier trust model that must not become a single point of forged truth, and a standards-adoption strategy that must work for one unilateral adopter before it works for a coalition. It matters architecturally because it sits at the same layer TLS and DNSSEC sit at — a protocol that only has value once neutral, boring, and universally implemented — and historically because every prior "trust layer" (SSL, DKIM, DID) had to solve the identical bootstrap problem this project solves in Phase 0–2: be useful to one party before it is useful to the network.

Sibling systems: it shares the signed-manifest problem with C2PA (image/video provenance, §35) and Sigstore/cosign (supply-chain provenance, §5 Reference Implementations); it shares the influence-attribution problem with TRAK/Datamodels research; it shares the lineage-graph problem with OpenLineage/Marquez and Apache Atlas (§35), though at a different unit of granularity (per-token vs per-job). Calibration value: a team that builds this can design any manifest/attestation protocol (SBOMs, provenance chains, verifiable credentials) from first principles.

What Mastery Looks Like — after building this, the reader can:

  • Design a JSON-LD wire format with a locked canonicalisation algorithm and defend the choice against a downgrade attack (Phase 0–1, §12–§13).
  • Explain why influence functions at frontier scale require a sampling theory, and derive a coverage metric for that sampling (Phase 2, §14).
  • Build a conformance suite that makes "conformant" a binary, falsifiable claim rather than a marketing word (Phase 3, §15).
  • Operate a multi-region stateful verifier fleet with replay defence and quorum trust (Phase 6–7, §18–§19).
  • Reason about zero-knowledge selective disclosure as a privacy control distinct from access-control (Phase 10, §22).
  • Design an economic settlement layer on top of a verification protocol without forcing a payment mechanism into the core spec (Phase 12, §24).

6. Design Principles

# Principle Rule Tradeoff / Operational Implication
P1 Open spec, permissive licence Spec CC-BY-4.0, code Apache-2.0; no closed-extension feature ships as Lineage Foregoes exclusive monetisation of the core protocol; monetisation moves to hosted infra (§24)
P2 Verifiability before convenience Every manifest third-party-verifiable without contacting the issuer Forbids bearer-only/opaque-token shortcuts even when they would simplify integration
P3 Influence is the floor, not marketing No InfluenceVector satisfying §8 ⇒ manifest MUST be kind:"fallback", UI MUST disclose it Some producers will ship mostly-fallback manifests early; the protocol still tells the truth
P4 Privacy co-equal with verifiability Selective disclosure (§22) and shard visibility tiers are first-class, not bolted on Adds a proof-system dependency (Groth16, ADR-12) to the critical path for private-corpus producers
P5 Cryptographic agility Signature suite versioned; algorithm is signed material (I-list) Every verifier must carry a minimum-acceptable-algorithm policy, not a single hardcoded check
P6 No retroactive breaking changes A v1.0 manifest parses under every v1.x verifier forever v2 changes require a 6-month dual-stack window (§29) — slows protocol evolution by design
P7 Lab-independent value The protocol must be useful to exactly one unilateral adopter Forbids any feature requiring a multi-lab handshake before it delivers value
P8 Standards over products When a feature can ship as spec extension or proprietary surface, the spec wins The company's moat is operational (verifier network, §2), never protocol lock-in
P9 Reproducibility Every accuracy claim ships a fixed-seed, containerised reproduction artefact Slows publication cadence; each claim has an audit trail
P10 Adversarial assumptions Every counterparty (lab, integrator, rights-holder, regulator, end user) is a potential adversary at the protocol level Every trust relationship is named explicitly in the Threat Model (§26), never implicit
P11 Fail-closed verification Ambiguous, malformed, or partially-checked manifests render as unverified, never as verified Costs UX friction (more "unverified" badges) in exchange for zero false-positive trust states
P12 Bounded disclosure Top-k cap (default 16) + per-shard rate limiting bound worst-case training-data leakage via repeated queries Limits transparency (only top-k shown) to hold a privacy invariant (I-list, T5)
P13 Deterministic canonicalisation URDNA2015 (or a declared successor) is the sole path from manifest to signable bytes Any second canonicalisation path is a protocol fork, not an optimisation

8. Domain Model

8.1 Manifest Container (JSON-LD)

A Lineage Manifest is a JSON-LD document, context https://lineage.dev/v1. Normative for v1.0 per §11's Manifest type. A producer MUST emit exactly one manifest per output unit (I1); a consumer MUST NOT treat kind as trusted until signature + replay + schema checks pass (I2, I5, I7).

8.2 Verification State Machine

State Entered From Guard On Success → On Failure →
Received (external) size ≤ 64 KB (I8) Canonicalised Rejected (oversize)
Canonicalised Received URDNA2015 succeeds (P13) SignatureChecked Rejected (malformed)
SignatureChecked Canonicalised Ed25519 valid against issuer key (I2) ReplayChecked Unverified (sig fail)
ReplayChecked SignatureChecked (issuer,nonce) unseen in window (I5) SchemaValidated Rejected (replay, T2)
SchemaValidated ReplayChecked lineage_version compatible (I11); kind valid enum (I7) Resolved Rejected (schema)
Resolved SchemaValidated Shard refs dereferenced within authZ (I12) Verified Verified-Partial (private shards withheld)

Verified and Verified-Partial are the only states a Hover-UI (§20) may render as "provenance available"; every other terminal state renders "unverified" (P11, I2).

8.3 Worked Example — Issuance

Prompt: "What is the capital of France?" → completion: "The capital of France is Paris." (single sentence span). Tracer runs Two-Stage Retrieval (§14): Stage-1 retrieves N=4096 candidate shards by embedding similarity; Stage-2 runs TRAK over the cohort. Result: top-1 shard shard_id=blake3:9f2a... (a Wikipedia "Paris" article shard), score=0.71, attribution:"training"; coverage_score=0.86 (kind:"sampled"). Manifest Builder assembles the document, URDNA2015-canonicalises it, Ed25519-signs it under did:web:lab.example.com, attaches Lineage-Manifest: header. A consumer's SDK re-canonicalises, verifies the signature, checks replay/clock/schema, resolves the shard (public visibility, no authZ needed) and renders a Hover-UI card: "86% of this sentence's influence traced; top source: Wikipedia — Paris (cc-by-sa-4.0)."

8.4 Malformed-Input Example

A manifest missing @context fails at Canonicalised (URDNA2015 requires a resolvable JSON-LD context) → SchemaError raised, lineage.manifest.count telemetry records a rejected issuance, no signature check is attempted (fail fast, P11). Contrast: a manifest with a valid @context but a corrupted nonce (wrong length) fails at SchemaValidated, not Canonicalised — the state machine (§8.2) pinpoints exactly which invariant broke.

8.5 Failure-Path Example

A manifest with a valid structure but a signature computed over a different canonical form (e.g., an issuer bug in JSON key ordering pre-canonicalisation) fails at SignatureChecked → state Unverified. Telemetry (lineage.verify.sig_result=fail) is emitted; the consumer's Hover-UI renders no provenance card and a small "unverified" indicator (I2, P11); the Auto-Redact pipeline (§21) treats an unverified span identically to a fallback span — it cannot make a licence-based redaction decision without a verified TrainingShardRef.

8.6 InfluenceVector and the Semiring View

Per Green–Karvounarakis–Tannen (2007, §5), influence contributions from multiple shards to one span compose algebraically: a span's total attribution is the (bounded, top-k-truncated) sum of per-shard scores, with attribution partitioning the mass into training | retrieval | system_prompt | model_prior categories (mirrors PROV-DM's entity/activity distinction, §5). This is a modelling lens, not new schema — the wire types are in §11.

8.7 ShardRevocation Lifecycle

Published → Revoked(reason, revoked_after) → [optionally] Superseded(new_shard_id). Per I13, a Revoked shard's past manifests keep their original signature validity; only the display and future issuance eligibility change. See Failure Modes FM-6 (§27) for the revocation-lag failure class.

11. Core Schema & Types

interface Manifest {
  "@context": "https://lineage.dev/v1";
  "@type": "LineageManifest";
  lineage_version: string;          // semver 1.x.y; immutable once issued (I11)
  issuer: string;                   // DID; owner of the signing key
  issued_at: string;                // RFC3339 UTC; validated against I6
  nonce: string;                    // 128-bit base32; unique per issuer (I5)
  ttl_seconds?: number;             // staleness window; consumer policy
  model: ModelDescriptor;
  input_context: InputContext;
  output: OutputDescriptor;
  influence: InfluenceVector[];     // one per OutputSpan; append-only at build time
  training_shards: TrainingShardRef[];
  retrieval: RetrievalRef[];
  system_prompt_fp: string;         // "sha256:" prefix; never the raw prompt (I10)
  kind: "full" | "sampled" | "fallback";  // constrains rendering (I7)
  coverage_score: number;           // 0..1, whole-manifest (I3)
  influence_method: InfluenceMethod;
  tracer_budget: TracerBudget;
  signature: SignedAttestation;     // set only after canonicalisation (P13)
  extensions?: Record<string, unknown>;   // namespaced, e.g. "lab:foo"
}
// Ownership: producer-constructed, immutable post-signature. Mutation: none after signing —
// a changed field invalidates the signature by construction. Concurrency: build is
// single-threaded per output unit. Persistence: not persisted by the verifier by default (§28).
// Serialization: JSON-LD, URDNA2015-canonicalised before signing. Compatibility: I11.
interface ModelDescriptor {
  family: string; version: string; parameter_count: number;
  weight_fingerprint: string;       // BLAKE3 of canonical weights (ADR-11)
  adapter_chain?: AdapterRef[];     // LoRA/PEFT chain, apply order
  inference_config: { temperature: number; top_p: number; seed?: number | null;
                       quantization?: string | null };
}
// Ownership: producer. Mutation: immutable. Persistence: embedded only, never stored keyed
// separately. Serialization: nested JSON-LD object. Compatibility: additive fields only (I11).
interface InputContext {
  prompt_fp: string; prompt_token_count: number; conversation_id?: string;
  retrieval_fps?: string[]; upstream_manifest?: string;  // chain to a prior manifest
}
interface OutputDescriptor {
  output_fp: string; output_token_count: number;
  span_granularity: "token" | "sentence" | "paragraph" | "document";  // PhaseDeferred("§14")
  spans: OutputSpan[];
}
interface OutputSpan { index: number; start_codepoint: number; end_codepoint: number;
                        token_start: number; token_end: number; }
interface InfluenceVector {
  span_index: number; method: InfluenceMethod; top_k: ShardInfluence[];
  coverage_score: number; estimator_variance?: number; zk_proofs?: ZkInfluenceProof[];
}
interface ShardInfluence { shard_id: ShardId; score: number; rank: number;
  attribution: "training" | "retrieval" | "system_prompt" | "model_prior"; }
type InfluenceMethod = "trak" | "datamodels" | "if_lissa" | "if_arnoldi" | "if_ekfac"
                      | "if_grad_dot" | `vendor:${string}`;
// Ownership: Tracer (§14). Mutation: none post-build. Concurrency: one InfluenceVector
// computed per span, spans computed independently (embarrassingly parallel). Persistence:
// embedded in manifest only. Compatibility: InfluenceMethod is an open enum (I11).
interface TrainingShardRef {
  shard_id: ShardId; shard_set: string; byte_range?: [number, number];
  licence: LicenceTag; rights_holder?: string; publisher?: string;
  visibility: "public" | "restricted" | "private"; resolver?: string;
  excerpt_policy: "none" | "snippet" | "full"; snippet?: string;
}
type LicenceTag = "cc-by-4.0" | "cc-by-sa-4.0" | "cc0-1.0" | "public-domain"
                 | "commercial-licensed" | "fair-use-claimed" | "unknown" | `spdx:${string}`;
// Ownership: Tracer emits, Shard Resolver (§18) dereferences. Mutation: `visibility` may
// transition via ShardRevocation (§8.7) without altering the shard_id. Persistence: registry
// row in Postgres (ADR-06), keyed by shard_id. Compatibility: I12 governs resolution authZ.
interface SignedAttestation {
  algorithm: "ed25519" | "ml-dsa-65" | "ml-dsa-87";  // signed material itself, T11
  key_id: string; canonicalisation: "urdna2015"; signature: string;
  cert_chain?: string[]; countersignatures?: SignedAttestation[];
}
interface RetrievalRef { doc_fp: string; source_url?: string; retrieval_score: number;
                          used_in_spans: number[]; licence: LicenceTag; }
interface TracerBudget { wallclock_ms: number; flops?: number; cohort_size?: number;
                          hardware_class?: string; }
// Ownership: Signer (§13). Mutation: none — a `SignedAttestation` mismatch anywhere
// invalidates I2. Concurrency: single signer key per issuer; key rotation is out-of-band
// (§26 T4 mitigation). Compatibility: `algorithm` enum growth is additive only (I11).
class LineageTracer(Protocol):
    """Model-side instrumentation producing InfluenceVectors. Signature only — see §14."""
    lineage_version: str
    def trace(self, *, model_state: ModelStateRef, input_context: InputContext,
              output_span: OutputSpan, budget: TracerBudget) -> InfluenceTrace: ...
    def fingerprint_shard(self, shard: TrainingShard) -> ShardId: ...
    def attest(self, manifest: Manifest, signing_key: Ed25519PrivateKey) -> SignedAttestation: ...
    def supports(self, capability: TracerCapability) -> bool: ...

Ownership: implemented per-runtime (Llama-3-8B reference, §14). Mutation: stateless per call. Concurrency: trace MUST be safe under concurrent invocation across spans. Persistence: none — pure function of (model_state, input_context, output_span, budget).

12. Phase 0 — Correctness Kernel & Repo Skeleton

12.1 Objectives

Stand up the repo skeleton (§10) and the correctness kernel: URDNA2015 canonicalisation, BLAKE3 shard fingerprinting, and a pre-signature Manifest parse/serialize round-trip. No signing yet — that is Phase 1 (§13). Establish the CI matrix.

12.2 Detailed Implementation Steps

Modules: packages/lineage-py/lineage_py/manifest.py (the Manifest dataclass, §11, minus signature); lineage_py/canonical.py (URDNA2015 via pyld, implementing P13 and ADR-03); lineage_py/fingerprint.py (BLAKE3 shard_id per I9 and ADR-11). Test harness: pytest + Hypothesis property tests generating random pre-signature manifests and asserting encode→decode→re-encode byte-identity. CI: GitHub Actions matrix, Linux + macOS, Python 3.11/3.12 (ADR-15).

12.3 Deliverable

lineage-py v0.0.1, installable via uv pip install -e .; CLI lineage-cli fingerprint <file> prints a BLAKE3 shard id — an operator-inspectable artefact; CI green on the full matrix.

12.4 Acceptance Criteria

Round-trip byte-identity on ≥ 500 Hypothesis-generated manifests (fixed seed); avalanche property holds over 100 randomised single-byte shard mutations (no fingerprint collision); CI wall-clock < 6 minutes; fixture manifest-minimal.json round-trips exactly.

12.5 Conformance Fixtures

fixtures/manifest-minimal.json — smallest valid pre-signature manifest | round-trip byte-identity. fixtures/manifest-malformed-missing-context.json — no @context | MUST raise SchemaError at Canonicalised (§8.2). fixtures/shard-empty.bin — zero-length shard | fingerprint defined and stable across runs.

12.6 Pitfalls

URDNA2015 blank-node labelling is non-deterministic across implementations — Lineage v1.0 manifests MUST NOT use blank nodes (documented, tested by fixture above). BLAKE3 streaming vs one-shot API produces different intermediate state if mixed — pin to the one-shot API through Phase 5. IEEE-754 double round-trip loss through naive JSON float parsing — enforce exact round-trip in the property test (ties to I9, the schema's numeric-precision rule, §11).

12.7 Performance Concerns

Canonicalisation is effectively O(n) here (no blank nodes to sort). BLAKE3 fingerprinting throughput ≥ 1 GB/s single-core (per the BLAKE3 reference benchmark, ADR-11) — never the bottleneck at the Phase-0 10,000-shard mini-corpus scale (§14).

12.8 Edge Cases

Empty manifest (all optional fields absent) must still validate against the minimal kind:"fallback" shape. Non-UTF-8 byte sequences during fingerprinting MUST raise EncodingError, never silently coerce. Duplicate shard content under two different shard_set labels MUST fingerprint identically (content-addressed, not path-addressed, I9).

12.9 Failure Analysis

A canonicalisation crash on a malformed context is caught as SchemaError, logged with the input's hash, and does not crash the process — blast radius is the single manifest under process; no shared mutable canonicalisation state exists to corrupt (I9).

12.10 Operational Notes

Structured JSON logging from Day 1 (lineage.canonical, lineage.fingerprint loggers, ADR-19). No metrics/tracing yet — deferred (PhaseDeferred("§28"), register at §39). No deployment — this phase ships a library only.

13. Phase 1 — Manifest Schema & Signing

13.1 Objectives

Complete the Manifest schema (§11) with signature; implement Ed25519 signing/verification (ADR-04, P5) and the full §8.2 verification state machine through SignatureChecked.

13.2 Detailed Implementation Steps

lineage_py/signer.py — Ed25519 signing via PyNaCl, operating strictly on the URDNA2015 canonical bytes (P13, ties to Mental Model MM3, §34); key material read from an env-scoped keyfile in Phase 1 (HSM/KMS deferred, PhaseDeferred("§25")). lineage_py/attestation.py — SignedAttestation construction (§11) including the algorithm field as signed material (I-list, defends T11 in §26). Implements I2 (no verified state without signature success) and I6 (clock-skew check, ± 60 s per §4). Publish the Phase-0 demo issuer key at did:web:lineage.dev.

13.3 Deliverable

lineage_py.Manifest.sign() / .verify_signature() round-trip; a re-parse-and-reverify smoke script confirming an independently-loaded verifier accepts a manifest it did not build.

13.4 Acceptance Criteria

100% of 200 generated valid manifests verify; 100% of 50 tampered manifests (single-byte mutation post-signature) are rejected at SignatureChecked (I2); clock-skew fixture (issued_at = now+61s) rejected 100% of the time (I6); signing latency p95 < 5 ms on reference hardware.

13.5 Conformance Fixtures

fixtures/manifest-valid-signed.json | verifies true. fixtures/manifest-tampered-byte.json | MUST reject at SignatureChecked. fixtures/manifest-future-clock.json (issued_at=+61s) | MUST reject at SignatureChecked per I6. fixtures/manifest-unknown-algorithm.json | MUST reject (unrecognised algorithm enum value).

13.6 Pitfalls

Re-serialising a parsed manifest with a different key order before re-canonicalising silently breaks verification — always canonicalise, never re-serialise ad hoc (MM3, §34). Treating algorithm as advisory rather than signed material opens a downgrade path (T11) — it MUST be included in the canonical form prior to signing. Key files committed to the demo repo by accident — .gitignore + a pre-commit secret scanner is mandatory from this phase.

13.7 Performance Concerns

Ed25519 sign/verify is sub-millisecond per operation on commodity hardware; the dominant cost at this phase is canonicalisation (§12.7), not cryptography. Batch-signing (many spans, one manifest) amortises key-load overhead — one key load per manifest, not per span.

13.8 Edge Cases

Empty training_shards array with kind:"full" — schema-invalid (an internal consistency check, not just a type check) — must reject. A manifest signed, then a field added out-of-band before transmission — MUST fail verification (any post-sign mutation breaks I2 by construction). Concurrent signs of two different output units sharing one issuer key — MUST NOT reuse a nonce (I5, generation from a CSPRNG, not a counter).

13.9 Failure Analysis

A corrupted keyfile causes signer.py to raise at load time, not at sign time — the tracer's fallback path (§14) triggers kind:"fallback" emission rather than blocking the decode loop (P11). Blast radius: one issuer's manifests until the key is repaired; other issuers unaffected (no shared key state).

13.10 Operational Notes

lineage.sign.latency_ms, lineage.verify.sig_result metrics from this phase onward. Key rotation runbook drafted (used operationally from Phase 6, §18); DID document at did:web:lineage.dev versioned in the spec repo, not hand-edited in production.

14. Phase 2 — Influence Tracer Core

14.1 Objectives

Implement the reference Influence Tracer for Llama 3 8B: the Two-Stage Retrieval Strategy (ADR-10) atop TRAK (ADR-09, Park et al. 2023, §5), sentence-level span granularity (default per §11's OutputSpan), and the reproducibility floor (I4, ε ≤ 1e-3).

14.2 Detailed Implementation Steps

lineage_py/tracer/stage1_retrieval.py — sentence-transformer embedding index over the 10,000-shard mini-corpus (OpenWebText + Wikipedia + PG-19), top-N=4096 cosine-similarity retrieval. lineage_py/tracer/stage2_trak.py — TRAK Jacobian-vector-product evaluation over the Stage-1 cohort, applying Koh & Liang's (2017, §5) influence-function formulation as adapted by TRAK. lineage_py/tracer/coverage.py — computes coverage_score per I3 against a held-out full-influence estimate on a 1,000-shard subset. Implements P3 (influence is the floor: no computed vector ⇒ kind:"fallback") and P9 (fixed-seed reproducibility script, scripts/reproduce-phase0.py).

14.3 Deliverable

An end-to-end prompt → completion → InfluenceVector[] pipeline over the mini-corpus; five reference traces (fact-completion, code snippet, paraphrase, refusal, hallucination-prone question) captured as fixtures.

14.4 Acceptance Criteria

Reproducibility: re-running all 5 reference traces with identical seeds reproduces top-16 scores within ε ≤ 1e-3 absolute (I4); tracer inline overhead ≤ 10% of base inference latency p95 (M3, §32); coverage_score for each reference trace within 5% of the held-out 1,000-shard brute-force estimate.

14.5 Conformance Fixtures

fixtures/trace-fact-completion.json, fixtures/trace-code-snippet.json, fixtures/trace-paraphrase.json, fixtures/trace-refusal.json, fixtures/trace-hallucination.json — each: prompt | expected top-5 shard IDs + score tolerance band.

14.6 Pitfalls

Stage-1 retrieval recall too low silently caps Stage-2 accuracy — a shard genuinely influential but outside the top-4096 cosine-similarity cohort never appears, and coverage_score will look artificially high unless validated against the held-out estimator (I3 — this is precisely why the invariant requires cross-validation, not self-report). TRAK's random-projection dimension too small trades variance for speed — under-provisioning it produces estimator_variance values that make the manifest technically valid but practically noisy (Grosse et al. 2023, §5, document this failure mode at scale).

14.7 Performance Concerns

Stage-1 embedding-index lookup is O(log n) with an ANN index (deferred to production scale, ADR-10's "rejected-choice-wins" column, §9) but brute-force O(n) is acceptable at the 10,000-shard Phase-0 scale. Stage-2 TRAK evaluation dominates wall-clock; batching multiple spans' Jacobian-vector products amortises the per-call overhead.

14.8 Edge Cases

A completion with zero training-corpus overlap (pure model-prior generation, e.g. arithmetic) — InfluenceVector.top_k may legitimately be near-empty with attribution:"model_prior" dominant; this is not a bug. A prompt triggering a refusal — the tracer still MUST produce a vector over the refusal text itself (refusal is also generated text). Non-deterministic GPU kernel reduction order breaking the ε ≤ 1e-3 bound — pin cuDNN determinism flags.

14.9 Failure Analysis

If Stage-2 TRAK evaluation exceeds the TracerBudget.wallclock_ms ceiling, the tracer MUST degrade to kind:"fallback" rather than block the decode loop (P11, mirrors §13.9's signer failure path) — this is the same fail-closed contract applied to the tracer instead of the signer.

14.10 Operational Notes

lineage.tracer.stage1_latency_ms, lineage.tracer.stage2_latency_ms, lineage.tracer.coverage_score metrics. GPU job runs on a self-hosted CI runner (pytest.mark.gpu); CPU-only CI paths skip tracer accuracy tests but still run schema tests.

15. Phase 3 — Tracer Conformance Suite

15.1 Objectives

Build the Tracer Conformance Suite: the mechanism that makes "Lineage v1.0 conformant" a binary, falsifiable claim (P9) rather than a marketing assertion, satisfying §7's debugging-methodology requirement (the Verification Simulator).

15.2 Detailed Implementation Steps

packages/tracer-conformance/ — 100 hand-curated reference prompts over the 10,000-shard mini-corpus with ground-truth top-k influences from offline brute-force computation; a parametrised pytest harness driving each of I1–I13 (§7) with one dedicated fixture; round-trip canonicalisation/signing tests (reusing §12–§13 fixtures); a replay-attack rejection test (automates I5); a sampling-fidelity test comparing Two-Stage Retrieval coverage_score against the held-out full-corpus estimator (ADR-10, ties to §14.6's pitfall).

15.3 Deliverable

packages/tracer-conformance/ publishable as a standalone package; a conformance report (conformance-report.json) enumerating pass/fail per invariant ID.

15.4 Acceptance Criteria

100/100 reference prompts pass within documented tolerance bands; the reproducibility test (I4) passes for all 100; replay-rejection test rejects 100% of 50 synthetic replay attempts (I5); the suite completes in < 15 minutes on the reference CI runner.

15.5 Conformance Fixtures

conformance/corpora/conformance-mini/ — the published 10,000-shard corpus + embedding index. conformance/fixtures/ground-truth-100.yaml — declarative per-prompt expected top-k + score tolerance. conformance/fixtures/replay-attack-suite.json — 50 (issuer, nonce) reuse attempts.

15.6 Pitfalls

Ground-truth curated from a single brute-force run without cross-checking against a second independent implementation risks encoding a bug as "ground truth" — the suite's ground truth was cross-validated against an independent Koh–Liang-style implementation before being locked. A suite that only tests the happy path gives false confidence — malformed, replay, and revocation cases (I5, I13) are mandatory, not optional additions.

15.7 Performance Concerns

Running the full 100-prompt suite against the reference tracer is the single most compute-expensive CI job in the repo — scheduled nightly, not per-PR, with a fast 10-prompt smoke subset gating every PR (bounds CI wall-clock, ties to ADR-15).

15.8 Edge Cases

A prompt whose ground-truth top-1 shard has since been revoked (I13) — the suite fixture freezes the corpus snapshot so revocation state does not silently change expected fixtures. Floating-point non-determinism across CPU/GPU backends — tolerance bands (not exact equality) absorb legitimate backend variance while still catching regressions.

15.9 Failure Analysis

A suite regression (any of the 100 prompts newly failing) blocks release (ADR-15's CI gate); the failure report names the specific invariant ID (§7) that broke, giving the on-call engineer a direct pointer rather than a raw diff.

15.10 Operational Notes

Suite results published publicly (lineage-conformance-corpus-v1 on Hugging Face, per the original validation plan) so third parties can independently reproduce conformance claims — this is the mechanism, not just the intention, behind P9.

16.5 Conformance Fixtures

fixtures/sdk-public-api-surface.json — a frozen list of public symbols; a CI check diffs against it and fails on any undocumented removal (enforces P6). fixtures/sdk-import-smoke.py — minimal import + round-trip script run against the built wheel.

16.6 Pitfalls

Exposing internal canonicalisation helpers as public API accidentally locks an implementation detail into the compatibility contract (P6) — the frozen-surface fixture (§16.5) exists precisely to catch this before 1.0.0 ships. Type-hint drift between the dataclass (§11) and the Protocol ABI (§11's LineageTracer) causes silent structural mismatches — a mypy strict CI gate prevents merge.

16.7 Performance Concerns

Import time — a "SDK" that imports PyTorch eagerly on every import lineage_py slows every consumer's cold start; PyTorch/TRAK imports are lazy, isolated to the tracer submodule that non-producer consumers never import.

16.8 Edge Cases

A consumer imports only lineage_py.verifier_client without ever installing the [tracer] extra (Faiss/PyTorch) — MUST work standalone (optional-dependency boundary enforced via pyproject.toml extras). A manifest built under lineage_version:1.0.0 parsed by a 1.1.0-installed SDK — MUST succeed per I11.

16.9 Failure Analysis

A PyPI release published with a broken wheel (missing compiled extension) is caught by the install-and-import smoke test (§16.5) running against the published artefact, not the local build — this distinguishes "builds locally" from "installable by a stranger."

16.10 Operational Notes

Semantic-release automation tags versions from Conventional Commits; CHANGELOG.md generated, not hand-written; deprecation warnings (Python DeprecationWarning) precede any removal by one minor version.

17. Phase 5 — JavaScript SDK (lineage-js)

17.1 Objectives

Ship lineage-js as a parser/verifier-only port (ADR-13) — no tracer — giving every browser/Node consumer the ability to parse, canonicalise, and verify a manifest built by lineage-py.

17.2 Detailed Implementation Steps

TypeScript scaffold, dual ESM/CJS build via tsup; Manifest class mirroring §16's Python API surface exactly (terminology lock — identical names for every field and method); Ed25519 via @noble/ed25519 (zero-dependency, audited, ADR-04); canonicalisation via jsonld (URDNA2015, ADR-03); replay-cache client abstraction (in-memory + a pluggable Redis-backed adapter, anticipating §18's ADR-07).

17.3 Deliverable

lineage-js 1.0.0 on npm; a cross-language conformance test proving every Phase-3 (§15) fixture verifies identically in Python and JS.

17.4 Acceptance Criteria

100% of the Phase-3 conformance vectors (§15.5) verify identically in both languages; bundle size ≤ 50 KB minified+gzipped (browser-budget constraint); zero runtime dependencies beyond @noble/ed25519 and jsonld.

17.5 Conformance Fixtures

fixtures/cross-lang-vector-*.json — reused from §15.5's ground truth, re-asserted here as "verifies true/false identically in both SDKs." fixtures/js-bundle-size.json — CI-checked byte budget.

17.6 Pitfalls

jsonld's JS canonicalisation implementation historically diverges from pyld's on edge-case context resolution (network-fetched vs embedded context) — Lineage v1.0 pins the context to a locally-embedded copy in both SDKs, never a live network fetch, to eliminate this divergence class entirely.

17.7 Performance Concerns

@noble/ed25519's pure-JS implementation is slower than native bindings — acceptable for consumer-side verify volume (a browser verifying a handful of manifests per page load), not acceptable for the hosted verifier's throughput target (§4) — hence the verifier is Python/Rust, not this SDK (ADR-08).

17.8 Edge Cases

A manifest using a vendor: extension InfluenceMethod unknown to the JS SDK — MUST parse and verify the signature/schema successfully (open enum, I11) even though the JS SDK cannot interpret the vendor-specific influence semantics; it degrades to "signature valid, semantics opaque," never a hard parse failure.

17.9 Failure Analysis

A cross-language conformance mismatch (Python says valid, JS says invalid, or vice versa) is treated as a release blocker, not a JS-side bug by default — the root cause is non-deterministic canonicalisation (§17.6's pitfall class) until proven otherwise.

17.10 Operational Notes

npm package published with provenance attestation (npm's own Sigstore-based publish provenance — a direct real-world instance of the pattern this project itself implements, Reference Implementation Sigstore/cosign, §5); CHANGELOG.md shared format with lineage-py.

18. Phase 6 — Verifier Service v0

18.1 Objectives

Ship a self-hostable verifier (Docker image) implementing the full §8.2 state machine end-to-end, satisfying P2 (verifiable without contacting the issuer) at the operator level.

18.2 Detailed Implementation Steps

apps/verifier/ — FastAPI service (ADR-08); routes POST /v1/verify, GET /v1/resolve/{shard_id}, GET /v1/issuer/{did}; Postgres backend (ADR-06) for issuer registry, shard registry, replay cache persistence; Redis-backed replay cache (ADR-07) with per-issuer LRU eviction tuned to the 24h window (I5, §4); pluggable shard-resolver backends (local filesystem, S3, HTTPS, Hugging Face) implementing I12's authZ boundary. Helm chart + docker-compose for local and cluster deploys (ADR-17).

18.3 Deliverable

A running verifier passing every Phase-3 (§15) conformance vector; a docker-compose stack (verifier + Postgres + Redis) startable in one command.

18.4 Acceptance Criteria

100% of conformance-suite vectors (§15) pass against the deployed verifier, not just the SDK in-process path; cold start ≤ 5 s to healthy (M12, §32); p95 signature-only verify < 100 ms (M1) on reference hardware with a warm connection pool.

18.5 Conformance Fixtures

fixtures/verifier-e2e-suite.json — HTTP-level replay of every §15.5 vector against the live /v1/verify endpoint. fixtures/verifier-replay-http.json — 50 replayed HTTP requests, 100% expected-rejected.

18.6 Pitfalls

Postgres connection-pool exhaustion under burst load manifests as p99 latency spikes, not errors — undetected without explicit pool-saturation metrics (§18.10). Redis replay-cache eviction tuned too aggressively silently shrinks the effective replay window below the spec's 24h (I5) — validated by a fixture that submits a nonce at T+23h59m and expects rejection on reuse.

18.7 Performance Concerns

Shard-resolver dereference (network I/O to S3/HTTPS backends) dominates the "full dereference" latency budget (M2, p95 < 500 ms, §4) — signature-only verification never touches this path, which is why the two are budgeted separately in §4.

18.8 Edge Cases

A shard resolver backend timing out mid-request — MUST return a partial VerificationResult with the unresolved shard flagged, not fail the entire verification (a signature-valid manifest with one unreachable shard is still Verified-Partial, §8.2). Concurrent requests for the same (issuer, nonce) racing the replay cache — MUST use an atomic check-and-set, not read-then-write (a TOCTOU bug here breaks I5 under concurrency).

18.9 Failure Analysis

A Redis outage degrades replay protection to fail-closed (reject all until cache is reachable) — never fail-open (which would silently disable I5); this is deliberate and documented in Failure Modes FM-4 (§27). A Postgres outage degrades shard resolution to "unresolved," never to a false "verified" (P11).

18.10 Operational Notes

lineage.verify.p50/p95/p99_ms, lineage.verifier.pool_saturation, lineage.replay.cache_hit_rate metrics from this phase onward (§28); a named runbook runbooks/verifier-redis-outage.md covers the fail-closed degradation path.

19. Phase 7 — Verifier Service at Scale

19.1 Objectives

Take the Phase-6 (§18) single-node verifier to a multi-region, quorum-capable fleet meeting the §4 throughput ceiling (≥ 1M verifications/week at launch, ≥ 10M/week stretch).

19.2 Detailed Implementation Steps

Active-active deployment across IAD + FRA + SIN (§4's cross-region RTT budget); distributed replay cache via managed Redis (Upstash) shared across regions (ADR-07, extending §18.2); token-bucket backpressure (ADR-23) returning HTTP 429 above 500 concurrent requests/instance (§4); a reference quorum-verifier client implementing P2's "never blindly trust one verifier" contract (Mental Model MM4, §34) — chains ≥ 2 verifiers and requires agreement for high-stakes consumers. Pen-test engagement (Trail of Bits or Doyensec class) before public launch.

19.3 Deliverable

A publicly reachable hosted verifier sustaining the load-test target; a published pen-test remediation log; a quorum-client reference package.

19.4 Acceptance Criteria

Sustained load test: 5,000,000 verifications/week at p95 < 200 ms (§4's combined signature+partial-dereference budget) for 72 continuous hours; cross-region failover completes within RTO ≤ 15 min (§4); zero unresolved critical/high findings from the pen-test before public launch.

19.5 Conformance Fixtures

fixtures/load-test-profile.yaml — declares the 5M/week sustained load shape (diurnal pattern, §36). fixtures/region-failover-drill.json — simulated IAD outage, expected FRA/SIN takeover within RTO. fixtures/quorum-disagreement.json — two verifiers disagreeing on one manifest, expected quorum-client verdict = unverified (fail-closed, P11).

19.6 Pitfalls

Active-active replication lag between regions creates a window where a nonce accepted in IAD has not yet propagated to FRA's replay cache — a replay inside that window is a real risk; mitigated by a conservative propagation-lag SLO monitored explicitly (§19.10), not assumed away. Load-testing against a single region and extrapolating linearly ignores cross-region replay-cache synchronisation overhead — the load test (§19.5) is run against the full multi-region topology, never a single-node proxy for it.

19.7 Performance Concerns

Redis cross-region replication adds tail latency to every replay check — budgeted explicitly inside the M1 p99 < 250 ms figure (§4, §32); a replay-cache read that would exceed the budget locally falls back to a conservative "assume possible replay, reject" posture rather than blocking indefinitely (fail-closed extension of I5).

19.8 Edge Cases

A network partition isolating one region — that region's verifier MUST NOT independently accept manifests it cannot confirm are non-replayed against the global cache; it degrades to local-only replay defence with a reduced-confidence flag surfaced in telemetry, never silent full-confidence operation. A pen-test finding requiring a schema change — routed through the ADR process (§9), never patched ad hoc in production.

19.9 Failure Analysis

A region-wide outage (FM-2, §27) triggers automatic DNS/anycast failover to the remaining regions; blast radius is bounded to elevated latency for consumers geographically close to the downed region, never a correctness failure (replay/signature guarantees hold globally by design, I5, I2).

19.10 Operational Notes

lineage.verifier.region_health, lineage.replay.propagation_lag_ms, lineage.quorum.disagreement_rate metrics; quarterly cross-region failover drills (scripted, not tabletop-only); the pen-test report is published (transparency per P2/P8).

20. Phase 8 — Hover-UI Library

20.1 Objectives

Ship @lineage/hover-ui: a framework-agnostic client that renders per-sentence provenance, strictly consuming only the §8.2 Verified/Verified-Partial states — never rendering a provenance card from an unverified manifest (P11, I2).

20.2 Detailed Implementation Steps

Core: Lit-based Web Components (framework-independent, ADR-01's TS half); thin wrappers @lineage/hover-ui-react, -vue, -svelte. Rendering policy: redaction-aware (suppresses a snippet when excerpt_policy:"none", §11's TrainingShardRef); licence-aware (badges by LicenceTag); confidence-graded (visually distinguishes low-coverage_score spans, I3). Verification path defaults to the Phase-7 (§19) hosted verifier, swappable to self-hosted or local-only signature check via one config flag (P2).

20.3 Deliverable

@lineage/hover-ui 1.0.0 across all three framework wrappers; a Storybook showcase; an accessibility audit report (keyboard nav, ARIA, screen-reader smoke test).

20.4 Acceptance Criteria

Hover-to-card render p95 < 50 ms (M9, §4); zero WCAG 2.1 AA violations in the accessibility audit; 100% of fixtures render "unverified" (no card) for every non-Verified* §8.2 terminal state.

20.5 Conformance Fixtures

fixtures/hover-ui-verified.json | renders a full provenance card. fixtures/hover-ui-partial.json | renders card with "some sources restricted" indicator. fixtures/hover-ui-unverified.json | renders no card, small unverified indicator only.

20.6 Pitfalls

Caching a VerificationResult client-side past its ttl_seconds silently shows stale provenance as if freshly verified — the library re-checks staleness against ttl_seconds before rendering, never trusting a cached verdict indefinitely. Rendering a snippet when excerpt_policy changed server-side after the client cached an earlier response — the client MUST treat excerpt_policy as authoritative from the latest resolve call, not a cached one.

20.7 Performance Concerns

DOM thrash from re-rendering the full provenance card on every mouse-move (not just hover-enter/leave) — debounced to hover-enter events only, keeping render count bounded regardless of pointer jitter.

20.8 Edge Cases

Overlapping spans (a retrieval-augmented span nested inside a training-influenced span) — the library renders the innermost span's card on hover, with an explicit "broader context" affordance rather than silently merging attributions. A manifest with zero spans (edge case of an empty completion) — renders no hover targets at all, not an empty card.

20.9 Failure Analysis

A verifier-call timeout during hover — degrades to a "checking..." transient state, then to "unverified" after a bounded timeout (never an indefinite spinner, P11-consistent UX posture).

20.10 Operational Notes

Client-side telemetry (opt-in only, per §29's privacy defaults) reports hover-card render counts, never manifest content; version-pinned against the Phase-7 verifier API contract (§29 Compatibility & Versioning).

21. Phase 9 — Auto-Redact Tooling

21.1 Objectives

Ship lineage-redact: a CLI + library converting (output, manifest, policy) into a policy-conformant output, using only verified TrainingShardRef licence data (§11) — never an unverified or fallback span.

21.2 Detailed Implementation Steps

Policy DSL (YAML): licence allowlist/denylist per LicenceTag (§11); span-rewriting strategies — mask (replace with a placeholder), paraphrase (invoke a second model, then re-trace the rewritten span to confirm the offending shard's influence is actually reduced — closing the loop rather than trusting the rewrite blindly), remove (delete and stitch). Implements P3: a fallback-kind span is treated as policy-unknown, not policy-compliant, and is redacted conservatively by default.

21.3 Deliverable

lineage-redact CLI; a RedactionReport enumerating every policy hit with the triggering shard ID and licence.

21.4 Acceptance Criteria

200 hand-curated redaction scenarios (§21.5) pass with byte-exact expected output; the paraphrase strategy's re-trace step confirms ≥ 95% of rewrites reduce the offending shard's influence score below the policy threshold on the first attempt (remaining 5% trigger a second rewrite pass, capped at 3 attempts before falling back to remove).

21.5 Conformance Fixtures

fixtures/redact-200-scenarios.yaml — declarative (output, manifest, policy) → expected redacted output + RedactionReport. fixtures/redact-fallback-span.json — a kind:"fallback" span | MUST redact conservatively (policy-unknown treated as non-compliant).

21.6 Pitfalls

The paraphrase strategy re-generating text that reintroduces the same offending influence under a different surface wording — caught only by the mandatory re-trace step (§21.2); a naive implementation that paraphrases without re-tracing silently ships non-compliant output disguised as compliant.

21.7 Performance Concerns

Re-tracing every paraphrase attempt doubles tracer load (§14) per redaction — batched against the same Two-Stage Retrieval cohort where possible to avoid re-running Stage-1 retrieval from scratch.

21.8 Edge Cases

A span whose top-k shards span both allowed and denied licences — policy evaluates per-shard, not per-span-as-a-whole; a span survives only if no top-k shard above the influence threshold is denylisted. Circular paraphrase-then-re-trace loops (rewrite re-triggers the same rule against a different shard each time) — capped at 3 attempts (§21.4), then remove.

21.9 Failure Analysis

A policy YAML parse error halts redaction for the whole batch with a clear line-numbered error — it never silently skips the malformed rule and proceeds with a partial policy (fail-closed, P11).

21.10 Operational Notes

Integration recipes for LangChain, LlamaIndex, Vercel AI SDK, Anthropic SDK, OpenAI SDK published as example configs (§10's examples/); lineage.redact.report_count and lineage.redact.strategy_used metrics.

22. Phase 10 — Selective Disclosure (ZK)

22.1 Objectives

Implement zk_selective_disclosure (§11's ZkInfluenceProof, referenced in I12): prove a shard within a committed set influences an output above a threshold, without revealing the shard (P4, P12).

22.2 Detailed Implementation Steps

Commitment set: a Merkle tree over shard fingerprints (I9's BLAKE3 IDs as leaves); proving circuit (Groth16, ADR-12) attesting "∃ shard ∈ commitment-set C : influence(shard, output) > T" without revealing which shard; integration into the Manifest Builder (§8) to emit ZkInfluenceProof alongside or instead of a plain shard_id; verification integrated into both lineage-py and lineage-js (§16–§17).

22.3 Deliverable

A reference Groth16 circuit + prover + verifier; a manifest example (examples/manifest-zk-disclosure.json) using the capability.

22.4 Acceptance Criteria

Proof generation time p95 < 2 s per span on reference hardware; proof size ≤ 200 bytes (Groth16's constant-size property); verification time p95 < 10 ms; 100% of 50 crafted false-witness attempts (proving influence for a shard not in the commitment set) rejected.

22.5 Conformance Fixtures

fixtures/zk-valid-proof.json | verifies true. fixtures/zk-false-witness.json — proof for a non-member shard | MUST reject. fixtures/zk-wrong-threshold.json — proof claiming a threshold the underlying influence doesn't meet | MUST reject.

22.6 Pitfalls

Groth16's trusted setup is circuit-specific — reusing a setup across a circuit change silently breaks soundness; the setup ceremony output is versioned and pinned per ADR-12's locked choice, with the "rejected choice wins" column (§9) naming exactly when a transparent-setup system becomes necessary. Treating "proof verifies" as "the manifest is fully verified" conflates I2 (signature) with the ZK proof's separate, narrower guarantee — the two checks are independent and both required.

22.7 Performance Concerns

Proof generation is the dominant cost (~seconds), far above the tracer's normal per-span budget (M3, §4) — zk_selective_disclosure is therefore an opt-in capability (supports() in §11's LineageTracer), never the default path, to avoid violating the inline overhead budget for producers who don't need it.

22.8 Edge Cases

A commitment set that changes between proof generation and verification (shard added/removed) — the proof references a specific Merkle root, and verification MUST reject a proof against a stale root rather than silently accepting it against the current one. A threshold set to exactly the boundary value — defined as strict inequality (>, not ≥) to avoid an off-by-epsilon ambiguity.

22.9 Failure Analysis

A circuit bug discovered post-deployment requires a new trusted-setup ceremony and a lineage_version minor bump — old proofs under the retired circuit remain verifiable against the retired verification key (mirrors I13's "history stays valid" pattern) but new issuance switches immediately.

22.10 Operational Notes

lineage.zk.proof_gen_ms, lineage.zk.verify_ms metrics; the proving-key and verifying-key artefacts are published alongside the spec (§10's spec/context/), never regenerated silently.

23. Phase 11 — Training-Time Hooks

23.1 Objectives

Land a lineage_hooks extension in one major OSS training stack (Hugging Face Transformers Trainer, priority target) to replace post-hoc tracing (§14) with training-time shard-fingerprinted gradient capture — closing the gap Grosse et al. (2023, §5) identify between retrofit and production-grade influence tracing.

23.2 Detailed Implementation Steps

Minimal LineageTrainingHook interface (signature-only, §11-style): on_batch_start(shards: List[ShardId]), on_step_end(grad_summary: GradSummary), on_checkpoint(weights_fp: str). RFC posted against the target stack's repo; reference implementation submitted as a PR with test fixtures; a fidelity test comparing training-time-traced influence against Phase-2's (§14) retrofit-traced influence on shared reference prompts, bounding the two within a documented tolerance (extends I4's reproducibility framing to a cross-method comparison).

23.3 Deliverable

A merged PR in the target OSS training stack; a fidelity report; a tutorial for a downstream lab adopting the hooks.

23.4 Acceptance Criteria

Training-time vs retrofit-traced top-16 influence agreement ≥ 90% overlap by shard ID on 20 shared reference prompts; hook overhead ≤ 5% of training step wall-clock (a distinct, tighter budget than the inference-time M3, since training runs are far longer and costlier); maintainer sign-off on the merged PR (a human acceptance criterion tracked alongside the numeric ones).

23.5 Conformance Fixtures

fixtures/training-hook-fidelity-20.yaml — 20 prompts, retrofit vs training-time top-16, with expected overlap ≥ 90%. fixtures/hook-overhead-benchmark.json — training-step wall-clock with/without hooks enabled.

23.6 Pitfalls

Gradient-summary capture at every training step is far more data than a per-output tracer ever sees — naive full-gradient storage blows the training-run's disk budget; the hook stores a Kronecker-factored summary (George et al. 2018 EKFAC, §5, if_ekfac in §11's InfluenceMethod enum), not raw gradients. A maintainer-facing PR that changes core training loop control flow (rather than adding hook call-sites) will be rejected on review — the hook contract is deliberately call-site-only, never a control-flow change.

23.7 Performance Concerns

Hook call overhead is charged against the training run's wall-clock, a budget an order of magnitude more expensive per hour than inference — the 5% ceiling (§23.4) is enforced by benchmark, not estimated.

23.8 Edge Cases

A training run using gradient checkpointing/activation recomputation — the hook's on_step_end must fire exactly once per logical step, not once per recomputation pass. A distributed-data-parallel run where shards are sharded across workers — on_batch_start receives only the local worker's shard IDs; global attribution requires an all-reduce-style aggregation documented as a Phase-11 open item, not silently assumed complete.

23.9 Failure Analysis

A hook exception during training MUST NOT crash the training run — hooks are wrapped in a try/except boundary that logs and disables the hook for the remainder of the run rather than propagating (blast-radius containment analogous to §14.9's fallback-on-budget-exceeded pattern).

23.10 Operational Notes

Fidelity reports published per adopting lab; lineage.hooks.overhead_pct, lineage.hooks.fidelity_overlap metrics collected from the reference integration, not self-reported by adopters (mirrors P10's adversarial-assumption stance).

24. Phase 12 — Royalty Clearinghouse

24.1 Objectives

Close the economic loop: convert verifier-counted (never self-reported, P10) influence attributions into per-shard royalty events for a rights-holder coalition, without the core protocol mandating any specific payment mechanism (§1's non-goals).

24.2 Detailed Implementation Steps

Registry: shard_id → rights_holder_did → licence_terms, extending §11's TrainingShardRef registry (ADR-06, Postgres); counting service: verifier-side aggregation of attested influence over a settlement period, with anomaly detection flagging statistically improbable influence-count spikes (defends T10, §26); settlement: an off-protocol periodic statement (bank or stablecoin rails per coalition preference) computed from, and independently recomputable from, the public verifier event stream (P2's verifiability extended to economic auditability).

24.3 Deliverable

A running registry + counting service; a first quarterly settlement statement for one pilot rights-holder coalition; a dispute-resolution runbook (spot-check re-tracing by a neutral third party).

24.4 Acceptance Criteria

100% of settlement amounts independently recomputable from the verifier event log by a third-party auditor script; anomaly detector flags ≥ 95% of synthetically injected influence-inflation attempts (50 synthetic cases) without flagging more than 5% of the legitimate baseline (false-positive bound).

24.5 Conformance Fixtures

fixtures/clearinghouse-settlement-recompute.json — a settlement period's raw events → expected recomputed statement. fixtures/clearinghouse-inflation-attack.json — 50 synthetic influence-inflation attempts | ≥ 95% flagged.

24.6 Pitfalls

Allowing any producer-side self-reported influence count into the settlement calculation reopens T10 (royalty-clearinghouse fraud) — the counting service reads only the verifier's own event log, never a producer-submitted summary. A settlement formula that weights raw top-1 influence equally regardless of coverage_score rewards low-fidelity sampled manifests unfairly relative to full ones — the formula weights by score × coverage_score (ties to I3), not raw score alone.

24.7 Performance Concerns

Settlement recomputation over a full quarter's verifier event log is a batch job, not a real-time path — scheduled off-peak, bounded by the event-log storage growth rate (§36).

24.8 Edge Cases

A shard revoked (§8.7, I13) mid-settlement-period — influence counted before the revoked_after timestamp remains payable; influence after does not, requiring the counting service to be revocation-timestamp-aware, not just revocation-boolean-aware. Two rights-holder coalitions both claiming the same shard_id (a licensing dispute outside the protocol's scope) — the registry rejects a second, conflicting claim rather than silently overwriting the first.

24.9 Failure Analysis

A counting-service bug producing a negative or NaN royalty amount is caught by a sanity-check gate before any statement is published — publishing is a two-phase commit (compute → validate → publish), never a single unchecked write.

24.10 Operational Notes

Quarterly settlement is a named, dated operational event with its own runbook (runbooks/clearinghouse-settlement.md); lineage.clearinghouse.settlement_amount, lineage.clearinghouse.anomaly_flags metrics reviewed by a human before publication (no fully-automated payment trigger in v1.0, PhaseDeferred("§24") for on-chain automation, §39).

25.1 Objectives

Ship the audit-grade enterprise tier and the compliance evidence required for regulated-industry deployment: single-tenant on-prem verifier, SOC 2 Type II + ISO/IEC 42001 readiness, and the conformance posture cited in regulatory engagement (§1's Phase-4-equivalent objective).

25.2 Detailed Implementation Steps

Single-tenant verifier variant with customer-managed KMS (extends §18's key-handling, closing PhaseDeferred-marked HSM/KMS deferral from §13.2); append-only audit log of every verification, exportable to a customer SIEM; on-prem installer (Helm + Terraform module + air-gapped bundle, ADR-17); controls implementation for SOC 2 Type II and ISO/IEC 42001 (AI management systems) via a managed GRC platform (Vanta/Drata class), run in parallel with feature work per P9's evidence-first posture.

25.3 Deliverable

A SOC 2 Type II report; an ISO/IEC 42001 certification (or a dated readiness assessment if certification is still in progress); an air-gapped installer package; an audit-log export format specification.

25.4 Acceptance Criteria

SOC 2 Type II observation period ≥ 6 months with zero unremediated critical exceptions; air-gapped installer completes a from-scratch verifier deployment in ≤ 30 minutes on reference hardware with zero network egress during install; audit-log export validated against a named customer SIEM ingestion format (e.g. Splunk CIM or an OTel-compatible schema).

25.5 Conformance Fixtures

fixtures/airgap-install-checklist.yaml — step-by-step install with expected artefacts at each step, no network calls permitted. fixtures/audit-log-export-sample.json — one full day's verification events in the published export schema.

25.6 Pitfalls

An "on-prem" installer that silently phones home for a licence check violates the air-gap promise (P2's self-hostability extended to full network isolation) — licence validation is therefore an offline, cryptographically-signed token check, never a network call. Treating SOC 2 controls as a one-time checklist rather than continuously operated evidence collection fails the Type II observation period, which requires sustained operation, not a point-in-time snapshot.

25.7 Performance Concerns

Audit-log append-only writes at full verifier throughput (§4's 10M/week ceiling) must not regress the verify-latency budget (M1) — the audit log is written asynchronously (fire-and-forget with a durable local buffer), never synchronously blocking the verify response path.

25.8 Edge Cases

A customer-managed KMS key rotated without coordinating with the verifier's cached key handle — the verifier MUST detect a signing/decryption failure and re-fetch rather than operate silently on a stale cached key. An air-gapped deployment needing a shard revocation update (I13) — delivered via a signed, out-of-band revocation-list file import, not a live network poll (the only exception to §18's live-poll pattern, explicitly documented here).

25.9 Failure Analysis

A failed SOC 2 control test during the observation window is logged as a formal exception with a remediation deadline — it does not silently reset the observation clock; the audit trail of exceptions-and-remediations is itself part of the evidence package.

25.10 Operational Notes

lineage.audit.log_write_latency_ms, lineage.kms.key_rotation_events metrics; a dedicated runbooks/airgap-deployment.md and runbooks/soc2-exception-handling.md; customer-facing named technical account manager engagement begins this phase (mirrors the original roadmap's enterprise-tier support model).

28. Operational Readiness

Metrics. Every phase (§12–§25) emits a scoped Prometheus-style metric under the lineage.* namespace (full list: §12.10, §13.10, §14.10, §15.10, §16.10, §17.10, §18.10, §19.10, §20.10, §21.10, §22.10, §23.10, §24.10, §25.10). Tracing. OpenTelemetry spans (ADR-18) from the verifier's POST /v1/verify down through canonicalisation, signature check, replay check, and shard resolution — matching the §8.2 state machine 1:1, so a trace span name maps directly to a verification state. Structured logging. JSON logs (ADR-19), one logger per module named identically to the metric prefix. Dashboards. One dashboard per trust domain (§3): Producer (tracer overhead, fallback rate), Transport (replay/clock rejections), Verifier (latency percentiles, region health), Consumer (Hover-UI render success rate). Alerting philosophy: alert on invariant violations (§7) and SLO burn rate (§4), never on raw error counts alone — a spike in lineage.verify.sig_result=fail is only paged if it exceeds the historical baseline by a burn-rate multiplier, since a single forged manifest is expected background noise, not an incident by itself. SLOs: 99.9% verifier availability (§4); p95 verify latency within M1/M2 (§32) measured over a rolling 28-day window. Incident response: severity levels map to trust-domain blast radius (§3) — a Producer-side incident (one issuer's keys) is Sev-2; a Verifier-fleet incident (all consumers) is Sev-1. Deployment topology: active-active multi-region (§19); canary releases at 5% traffic for 1 hour before full rollout; rolling upgrade with a dual-stack window for any schema change (§29); rollback is a single Helm revision revert (§10, ADR-17); migration scripts are additive-only until a major version boundary (I11).

29. Compatibility & Versioning

Wire compatibility. A v1.x verifier MUST accept any v1.y manifest, y ≥ x, without a mandatory-field regression (I11). Storage compatibility. Verifier registry schema migrations are additive-only within v1.x (new nullable columns only); a breaking storage change requires a version-boundary migration plan reviewed as an ADR (§9). Schema evolution. New InfluenceMethod, LicenceTag, or algorithm enum values are additive (open enums, §11); removing an enum value is a breaking change requiring v2. API stability. The verifier's POST /v1/verify response shape follows the same additive-only rule; the SDK's public surface (§16.5's frozen-surface fixture) is diffed in CI. Migration. Any breaking change (v1 → v2) ships with a six-month dual-stack window (P6): v1 and v2 verifiers run concurrently, v1 manifests remain valid throughout, and only after the window closes does v1 support sunset. Deprecation policy. A field or capability is marked deprecated one minor version before removal eligibility, with a DeprecationWarning-class signal in both SDKs (§16.6). SemVer policy. lineage_version (manifest schema) and package versions (lineage-py, lineage-js) each follow independent SemVer; a package patch release never implies a schema version bump. Rolling-upgrade guarantees. A verifier fleet may run mixed v1.x point versions during a rolling deploy; the replay cache and registry schemas are designed to tolerate this (§28's additive-only migration rule) without a hard cutover requirement.

30. Testing & Verification Strategy

Unit tests. ≥ 85% line coverage on lineage-py, lineage-js, and the verifier (§16.4). Integration tests. The Tracer Conformance Suite (§15) is the primary integration gate, exercising every invariant (§7) end-to-end rather than in isolation. Property-based testing. Hypothesis-driven manifest round-trip and fuzz-adjacent generation from Phase 0 onward (§12.2, ADR-20). Differential testing. Cross-language conformance (§17.4) — every fixture must verify identically in lineage-py and lineage-js; a divergence is a release blocker (§17.9). Fuzzing. fuzz/ targets the manifest parser directly (a documented adversarial input surface, T8) using coverage-guided fuzzing; run continuously in CI, not just pre-release. Chaos testing. Quarterly region-failover drills (§19.10) and a scripted Redis-outage injection validating the fail-closed posture (§18.9, FM-3). Deterministic replay. The Verification Simulator (§7's debugging methodology) replays the full §8.2 state machine against every conformance fixture deterministically — same input, same verdict, every run. Soak testing. 72-hour sustained load test at the Phase-7 throughput target (§19.4) before any major release. Fault injection. Synthetic replay attacks (§15.4), synthetic influence-inflation attempts (§24.4), synthetic false-witness ZK proofs (§22.4) — each a fault-injection test tied to a specific invariant or threat ID. Conformance. Binary pass/fail per the Tracer Conformance Suite (§15) — "Lineage v1.0 conformant" is never a partial claim (§15.4). Performance-regression gating. Every M-numbered target (§32) is a CI gate at its named phase; a regression blocks merge, not just release.

31. Build & Release Engineering

Reproducible builds. Pinned lockfiles across uv and pnpm (ADR-24); the Docker verifier image is built from a pinned base-image digest, not a floating tag. Artefact signing. The verifier's own Docker image and the lineage-py/lineage-js packages are signed at publish time using the Sigstore/cosign pattern (§5's Reference Implementation) — the project applies to its own release artefacts the same signed-provenance discipline it implements as a protocol. SBOM. A Software Bill of Materials generated per release (CycloneDX format) for every publishable artefact, feeding the SOC 2 evidence package (§25). Release channels. stable (SemVer-tagged), rc (spec release candidates, §5's RFC-style process), nightly (conformance suite + fuzz corpus only, never published to PyPI/npm). CI/CD topology. GitHub Actions (ADR-15): PR gate (unit + fast conformance smoke) → merge to main (full conformance suite + fuzz) → nightly (full 100-prompt suite, §15.7) → release (SBOM + signing + publish). Version stamping. Every artefact embeds its build SHA, lineage_version compatibility range, and build timestamp in a /version (verifier) or __version__ (SDK) surface. Provenance/ attestation. Build provenance follows the same in-toto/Sigstore pattern as npm's own publish provenance (§17.10) — the release pipeline is itself an instance of the manifest/attestation pattern this project specifies. Dependency auditing. Automated Dependabot/pip-audit scanning gates merge on any critical CVE in the dependency graph (ADR-24).

33. Scalability Analysis

Constant vs grows. Manifest size stays O(k) in top-k regardless of corpus size (constant, default k=16, §11); canonicalisation cost stays effectively O(n) in field count (constant per manifest). What grows: Stage-1 retrieval cost is O(corpus size) without an ANN index (ADR-10's ceiling); the shard-embedding index memory footprint (§36) grows linearly with corpus size; the replay cache grows linearly with sustained request rate × window (§36). Named bottlenecks, in order: (1) Stage-1 retrieval at frontier corpus scale (§36's 30 GB projection) — addressed by an ANN index (Faiss IVF/HNSW) rather than brute-force, the explicitly-named lever in ADR-10's rejected-choice-wins column; (2) verifier fleet size at throughput ceiling (§36) — addressed by horizontal scale-out, stateless application tier, stateful tiers (Postgres, Redis) sharded by issuer DID; (3) cross-region replay-cache propagation lag (FM-7, §27) — addressed by tighter regional read-replica placement or a relaxed consistency model with a documented, monitored risk window. Horizontal vs vertical. The verifier application tier scales horizontally (stateless FastAPI workers behind a load balancer); Postgres scales vertically first, then via read replicas, then via issuer-DID sharding at extreme scale (beyond the Phase-7 target). Coordination overhead. The only cross-instance coordination is the distributed replay cache (Redis) — bounded by the 24h window (§4), not by request volume, so coordination overhead is a function of nonce cardinality, not QPS. Practical ceiling and levers beyond it: the design as specified in §12–§25 comfortably covers the Phase-7 10M/week ceiling (§36 shows headroom at 165 req/s peak vs a 500 concurrent-request-per-instance budget); beyond that, the levers are (a) ANN-indexed Stage-1 retrieval, (b) issuer-DID-sharded Postgres, (c) a Rust-ported hot path (ADR-01's reserved option), each independently addable without a protocol-breaking change (P6).

C2PA made the decision to sign pixels/frames with an asset-centric claim/assertion model — it wins in the exact niche Lineage explicitly delegates to it (§1): single-author, single-asset media provenance where there is no "training influence" question to answer.

36. Back-of-Envelope Capacity Model

  1. Verifier average request rate = 1,000,000 verifications/week ÷ 604,800 s/week ≈ 1.65 req/s (derived from §4's launch throughput row).
  2. Verifier peak request rate = 1.65 req/s × 10 (assumed diurnal peak factor) ≈ 16.5 req/s at launch; at the 10M/week ceiling (§4): 16.5 req/s avg × 10 ≈ 165 req/s peak.
  3. Fleet size at ceiling = 165 req/s peak ÷ 100 req/s/instance (conservative sustained capacity implied by M1's p95 < 100 ms, §32, deflated for I/O and safety margin) ≈ 2 instances minimum, provisioned to 4 for the §4 RTO ≤ 15 min HA requirement.
  4. Replay-cache memory = 48 bytes/nonce-entry (16-byte nonce + 8-byte timestamp + key overhead) × 86,400 s TTL window (§4, I5) × 165 req/s peak ≈ 48 × 86,400 × 165 ≈ 685 MB — fits within the §4 2 GiB RSS ceiling with headroom for the connection pool.
  5. Manifest audit-log volume = (1,000,000 / 7) manifests/day × 4 KB (§4 typical size) ≈ 571 MB/day if every manifest were persisted (Phase 13's audit-log tier, §25, does this; Phase 6–7's default verifier does not persist manifest bodies, only verification events).
  6. Shard-embedding index memory (Phase 0 mini-corpus) = 10,000 shards × 768-dim float32 embeddings (3,072 bytes/shard) ≈ 30.7 MB — trivial; extrapolated to a hypothetical 10,000,000-shard production corpus: 10,000,000 × 3,072 bytes ≈ 30.7 GB, the number that motivates ADR-10's ANN-index lever (§33) rather than brute-force Stage-1 retrieval.
  7. Tracer GPU cost at Phase-0 scale = ≤ 10% inline overhead (§4, M3) on a reference ~50 ms/token H100 inference cost ⇒ ≤ 5 ms/token tracer overhead; for ~200 completions/day × 256 tokens: 200 × 256 × 5 ms = 256,000 ms ≈ 4.3 minutes/day of added GPU time.
  8. FD budget check = 500 concurrent requests/instance (§4) × ~3 FDs/request (client socket + Postgres conn + Redis conn) = 1,500 FDs, within the 4,096 FD/instance budget (§4) with 2.7× headroom.

38. Alternative Architectures (Roads Not Taken)

A — Blockchain-anchored manifest registry.

[Producer] --sign--> [Manifest] --anchor hash--> [L1/L2 chain] <--read-- [Consumer]

Regime where it wins: fully trustless multi-party settlement with no single operator willing to run a verifier (e.g. a royalty clearinghouse across mutually-distrusting coalitions with no neutral party). Real embodying system: Ethereum Attestation Service / OpenTimestamps. Rejected because: on-chain anchoring latency and gas cost are incompatible with the M1 <100 ms per-completion verify budget (§32); a centralised verifier plus an open spec achieves equivalent auditability for the Phase 0–7 timeline at a fraction of the operational cost.

B — Watermark-only provenance (no influence tracing).

[Model] --embed statistical signal--> [Output] --detector model--> [AI/not-AI verdict]

Regime where it wins: detection-only use cases where training-data influence is not required — content-authenticity checks, not evidentiary training lineage. Real embodying system: Google DeepMind SynthID. Rejected because: it cannot answer "which training data" — the central bet of §1/§2 — at any confidence level; it is a different, narrower claim.

C — Full-corpus exhaustive influence (no Two-Stage Retrieval sampling).

[Output span] --per-example IF over ALL N shards--> [InfluenceVector], coverage_score = 1.0

Regime where it wins: small or offline corpora where compute is not time-boxed (e.g. batch legal-discovery re-tracing over a bounded, already-collected corpus). Real embodying system: the original Koh & Liang (2017) per-example influence-function methodology at small scale. Rejected because: computationally infeasible against a frontier-scale corpus under the inline tracer overhead budget (M3, §4, §36's GPU-cost projection).

D — Federated / on-device-only verification (no hosted verifier network).

[Manifest] --local signature check only--> [Consumer], no network verifier call ever

Regime where it wins: privacy-maximalist deployments (government/defense) that cannot use any third-party service, even an open-source self-hosted one operated by someone else. Real embodying system: IPFS content-addressing with purely local resolution. Rejected because: it forfeits the verifier-network effect (§2's second moat) and pushes private-shard dereferencing entirely onto each consumer — acceptable for one deployment, but it does not generalise to the protocol's broader adoption goal (P7 is about unilateral value, not unilateral sufficiency forever).

40. Glossary

  • Attestation Registry — public registry of issuer DIDs, public keys, and key-history log.
  • ADR — Architecture Decision Record; this document's §9 table, ADR-01…ADR-24.
  • BLAKE3 — the hash function used for shard fingerprinting (I9, ADR-11).
  • Canonicalisation — the deterministic transform (URDNA2015) from a manifest to signable bytes (P13, MM3).
  • Coverage Score — real number in [0,1]; the L1-share of top-k influence mass relative to the full distribution (I3).
  • DID — Decentralised Identifier (W3C); Lineage uses did:web by default.
  • Domain Separation — cryptographic technique ensuring a hash computed for one context (e.g. one shard_set) cannot be confused with a hash from another (I9).
  • Downgrade Attack — forcing use of a deprecated or weaker cryptographic primitive (T11).
  • Ed25519 — the default v1.0 signature algorithm (ADR-04, Bernstein et al. 2012).
  • FD Budget — the file-descriptor ceiling per verifier instance (§4).
