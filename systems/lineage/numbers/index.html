36. Back-of-Envelope Capacity Model

  1. Verifier average request rate = 1,000,000 verifications/week ÷ 604,800 s/week ≈ 1.65 req/s (derived from §4's launch throughput row).
  2. Verifier peak request rate = 1.65 req/s × 10 (assumed diurnal peak factor) ≈ 16.5 req/s at launch; at the 10M/week ceiling (§4): 16.5 req/s avg × 10 ≈ 165 req/s peak.
  3. Fleet size at ceiling = 165 req/s peak ÷ 100 req/s/instance (conservative sustained capacity implied by M1's p95 < 100 ms, §32, deflated for I/O and safety margin) ≈ 2 instances minimum, provisioned to 4 for the §4 RTO ≤ 15 min HA requirement.
  4. Replay-cache memory = 48 bytes/nonce-entry (16-byte nonce + 8-byte timestamp + key overhead) × 86,400 s TTL window (§4, I5) × 165 req/s peak ≈ 48 × 86,400 × 165 ≈ 685 MB — fits within the §4 2 GiB RSS ceiling with headroom for the connection pool.
  5. Manifest audit-log volume = (1,000,000 / 7) manifests/day × 4 KB (§4 typical size) ≈ 571 MB/day if every manifest were persisted (Phase 13's audit-log tier, §25, does this; Phase 6–7's default verifier does not persist manifest bodies, only verification events).
  6. Shard-embedding index memory (Phase 0 mini-corpus) = 10,000 shards × 768-dim float32 embeddings (3,072 bytes/shard) ≈ 30.7 MB — trivial; extrapolated to a hypothetical 10,000,000-shard production corpus: 10,000,000 × 3,072 bytes ≈ 30.7 GB, the number that motivates ADR-10's ANN-index lever (§33) rather than brute-force Stage-1 retrieval.
  7. Tracer GPU cost at Phase-0 scale = ≤ 10% inline overhead (§4, M3) on a reference ~50 ms/token H100 inference cost ⇒ ≤ 5 ms/token tracer overhead; for ~200 completions/day × 256 tokens: 200 × 256 × 5 ms = 256,000 ms ≈ 4.3 minutes/day of added GPU time.
  8. FD budget check = 500 concurrent requests/instance (§4) × ~3 FDs/request (client socket + Postgres conn + Redis conn) = 1,500 FDs, within the 4,096 FD/instance budget (§4) with 2.7× headroom.
