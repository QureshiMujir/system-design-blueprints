185 — Real-Time Scheduler (RMS + EDF) from Scratch

Project Number: 185

Project Name: Real-Time Scheduler (RMS + EDF) from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. Build, from scratch, a userspace real-time task scheduler for Linux that implements both Rate Monotonic Scheduling (fixed-priority, RMS) and Earliest Deadline First (dynamic priority, EDF), with deterministic admission control, bounded-blocking synchronization via priority inheritance, multicore-aware dispatch, and a tracing/replay pipeline sufficient to prove — not assert — that deadlines are met. The system is judged on worst-case behavior first, average-case throughput second. This is a scheduling-theory-to-systems-code translation exercise: every dispatch decision must be traceable to a specific admission-time proof (utilization bound or exact response-time analysis) and every timing claim must be independently reproducible from a recorded trace.

Phase 0 deliverable — a compiling, CI-green Cargo workspace containing:

  1. rt_core — scheduler abstractions, TaskSpec/TaskRuntimeState, lifecycle state machine, timing primitive re-exports.
  2. rt_clock — monotonic clock abstraction, timerfd-backed high-resolution timers, tickless backend.
  3. rt_rms — fixed-priority RMS scheduler, Liu & Layland utilization test, exact response-time analysis.
  4. rt_edf — EDF scheduler, dynamic deadline-ordered ready queue, deadline accounting.
  5. rt_sync — mutexes, semaphores, priority inheritance, bounded-blocking analysis.
  6. rt_runtime — worker threads, dispatcher loop, CPU affinity management, migration.
  7. rt_trace — event pipeline, latency histograms, Chrome-trace export.
  8. rt_cli — workload loading, benchmark launching, trace export commands.
  9. rt_conformance — deterministic fixture suite, scheduling-correctness validation.
  10. rt_bench — stress tests, overload tests, jitter measurement (Criterion-backed).

System boundaries.

  • Provides: uniprocessor and affinity-partitioned SMP scheduling under RMS or EDF; admission control (utilization bound, exact RTA, EDF feasibility, blocking-aware admission); priority-inheritance mutex and semaphore primitives with bounded worst-case blocking; deterministic, replayable tracing; a benchmark harness free of the observer effect described in §26.
  • Delegates: physical thread creation and the OS scheduling class (SCHED_FIFO/SCHED_RR via sched_setscheduler(2)) to the Linux kernel; hardware timer interrupts to timerfd/clock_gettime; process isolation and memory protection to the OS; persistence of long-lived state to nothing — the system is designed to be stateless between runs (§25).
  • Does NOT provide: a kernel module or kernel-level scheduling class; distributed or multi-node real-time orchestration; a GUI; general-purpose async task scheduling (this is not a tokio replacement — ADR-20 explicitly excludes an async runtime); formal verification proofs; NUMA-aware placement; partitioned or global multiprocessor EDF. All five are deferred (§35).

Non-goals. Not a CFS replacement, not a cloud orchestrator, not optimized for average-case throughput, not a soft-real-time "best effort" scheduler (bounded worst case is the product; softer QoS is a side effect, not a target).

Deployment model. A single-host Linux userspace process. Two consumption modes: (a) rt_cli as a standalone workload runner/benchmark driver, or (b) rt_core/rt_rms/rt_edf/rt_runtime embedded as libraries inside a host process that owns its own worker threads pinned via sched_setaffinity(2). No network control plane in Phase 0; the trace-export socket (ADR-06) is local-host only until Phase 7.

Target operators. Systems engineers building latency-critical services who need to choose and justify RMS vs. EDF with numbers — industrial-control simulators, pre-trade risk gates, telemetry ingestion with per-message deadline SLAs. Not embedded/bare-metal engineers (RTOS migration is a Phase 1+ deferral, §35) and not application engineers wanting a generic job queue.

What later phases unlock. Phase 5 (§17) unlocks true multicore dispatch; Phase 6 (§18) unlocks priority-inheritance correctness under nested locking; Phase 7 (§19) unlocks full observability without which none of the timing claims above are trustworthy; Phase 8 (§20) unlocks benchmark-grade confidence; Phase 9 (§21) unlocks overload governance and release hardening. Beyond this blueprint, §35 registers CBS/sporadic servers, mixed-criticality scheduling, partitioned/global EDF, and NUMA-aware dispatch as the natural Phase 1+ continuation.

Recommended language: Rust. Exact rationale: ownership semantics make scheduler-state corruption a compile-time class of bug rather than a runtime one; zero-cost abstractions preserve the low-latency hot path (no forced allocation or vtable dispatch in select_next); sum-type (enum) task states make illegal lifecycle transitions unrepresentable (Principle P3); unsafe is syntactically grep-able and therefore auditable, which matters because affinity FFI and timer FFI (libc::timerfd_create, sched_setaffinity) require it; deterministic (non-GC) memory behavior makes worst-case latency reasoning tractable; the ecosystem (tracing, criterion, parking_lot) is mature for exactly the tracing/benchmarking work this project needs.

Rejected: Go — the GC introduces latency variability directly antithetical to Principle P1, and the Go runtime scheduler competes with and obscures the scheduler under test. Python — interpreter dispatch overhead dominates any latency measurement below ~100 µs and the GIL invalidates realistic multicore scheduling experiments. C++ — viable (and used by seL4's userland tooling and seL4-adjacent work) but rejected here for a larger memory-unsafety surface, weaker built-in concurrency ergonomics (no borrow checker to catch shared-mutable-state bugs in rt_sync), and a materially higher verification burden for the same confidence level.

Prerequisites. OS fundamentals; threads and synchronization; CPU scheduling theory (fixed vs. dynamic priority); cache-hierarchy basics; the Linux process/thread model; lock contention; C11/Rust memory ordering; systems programming in Rust; profiling and benchmarking; asymptotic analysis. Recommended prior projects: a thread-pool runtime, a toy kernel, an async executor, a lock-free queue, a timer-wheel implementation.

Estimated timeline. Phase 0: 1–2 weeks full-time, 2–3 weeks part-time. Full system (Phases 0–9, §12–§21): 4–6 months full-time, 8–12 months part-time, depending on verification depth (exact RTA conformance suites and priority-inheritance fuzzing dominate the variance).

2. Why Build This

2.1 What This Project Teaches

This project teaches timing correctness as a first-class systems concern, not an afterthought bolted onto a throughput-oriented scheduler. A real-time scheduler must provide provable latency bounds, schedulability mathematics, bounded-blocking guarantees under synchronization, deterministic wakeup semantics, and characterized (not merely observed) overload behavior. It forces reasoning about preemption cost, cache interference from context switches, migration penalties on multicore, starvation under fixed priority, fairness-versus-deadline tension, and synchronization correctness under deadline pressure. Most systems projects optimize the average case; this one optimizes the worst case, and that single distinction reshapes every architectural decision downstream — data structure choice (§9, ADR-12), lock discipline (ADR-08), even error-handling philosophy (Principle P12).

2.3 Calibration Value

Building this system produces durable intuition for concurrency correctness under time pressure, realistic (not textbook) latency measurement, appreciation for the constant-factor overhead a scheduler itself imposes, deep familiarity with synchronization pathologies (priority inversion, lock convoying, lost wakeups), production-grade tracing discipline, and confidence engineering timing-critical software generally. Every later project's thread coordination, contention measurement, and benchmarking methodology gets materially stronger because this project makes those skills load-bearing rather than incidental.

  • Explaining, with a worked feasibility proof, why EDF is optimal on a uniprocessor under the standard assumptions and where that optimality breaks down under blocking — mastered in Phase 4 (§16).
  • Building priority-inheritance synchronization that provably bounds blocking duration and diagnosing an inversion from a trace alone — mastered in Phase 6 (§18).
  • Engineering a tickless, drift-corrected monotonic timer subsystem and quantifying its jitter budget in microseconds, not adjectives — mastered in Phase 1 (§13).
  • Reasoning correctly about CPU affinity, migration cost, and preemption storms on a multicore dispatch layer — mastered in Phase 5 (§17).
  • Building an observability pipeline whose own overhead is bounded and measured, so that every timing claim in the document is independently reproducible — mastered in Phase 7 (§19).
  • Running benchmarks that control for observer effect, thermal throttling, and frequency scaling well enough that the resulting numbers survive scrutiny — mastered in Phase 8 (§20).
  • Designing overload governance (admission rejection, deadline-miss surfacing, criticality-aware degradation) that fails loudly instead of silently — mastered in Phase 9 (§21).

3.2 Subsystem Explanations

rt_cli (CLI / API). The sole operator-facing surface: workload ingestion, benchmark orchestration, scheduler-policy selection, trace export, metrics display, failure injection. Isolates untrusted operator input (trust boundary) from scheduler internals; every field it accepts is re-validated in rt_core::validation before crossing into the admission controller.

Workload Definition. The canonical task representation (TaskSpec): period, relative deadline, WCET, release offset, affinity mask, criticality class, and declared synchronization resources. Every downstream analysis — utilization bound, RTA, EDF feasibility — derives exclusively from these fields; TaskSpec is immutable after admission (Principle P3, Invariant I2).

Admission Controller. The primary correctness gate (Principle P8): determines schedulability before a single task runs, via RMS utilization bound, exact response-time analysis, EDF feasibility (U ≤ 1), and blocking-aware admission that folds in the maximum inherited-priority blocking term from rt_sync. Rejects here, not at runtime — late detection is operational debt.

Scheduler Frontend. Coordinates task lifecycle transitions (CREATED→READY→RUNNING→ {BLOCKED,PREEMPTED}→COMPLETED|MISSED_DEADLINE) as an explicit typed state machine (Principle P3); this layer is scheduler-policy agnostic — RMS and EDF plug into the same lifecycle.

RMS Scheduler. Fixed-priority dispatch: shortest-period-highest-priority static assignment, preemptive, with exact response-time analysis backing admission and bounded-blocking-aware priority inheritance integration. Policy boundary A — no EDF logic crosses into this module.

EDF Scheduler. Earliest-absolute-deadline dispatch with a dynamically reordered ready queue, deadline recomputation on release, and explicit overload-degradation instrumentation. Policy boundary B — demonstrates uniprocessor-optimal scheduling under Liu & Layland's ideal assumptions (§5, Papers).

Dispatch Layer. The concurrency boundary between scheduling policy and worker execution: per-core run-queue selection, CPU affinity enforcement, migration decisions, and preemption-request delivery. This is where multicore complexity concentrates (Phase 5, §17).

Worker Thread Runtime. Executes tasks while preserving deterministic accounting: runtime consumed, context-switch count, sleep duration, deadline misses, execution jitter — every field feeds rt_trace.

Synchronization Layer. Bounded-blocking primitives: mutexes and semaphores with priority-inheritance protocol, lock-ownership tracking, and deadlock diagnostics. A second concurrency boundary — this is the only place shared mutable state is permitted to block a higher-priority task, and only for a bounded duration (Principle P4, Invariant I6).

High-Resolution Clock. The hardware/OS boundary: monotonic-only timing (Principle P7), timerfd- backed deadline timers, wakeup-precision measurement, drift accounting, jitter measurement. Timer precision is the credibility floor for every other subsystem's claims.

Tracing / Telemetry. The external observability interface: scheduling-decision events, queue latency, wakeup delay, preemption frequency, missed-deadline alerts, all through a bounded ring buffer exported as Chrome-trace JSON. Without this subsystem none of the timing claims elsewhere in this document are independently verifiable (Principle P6).

6. Design Principles

  • P1 — Determinism Over Throughput. Rule: reject any average-case improvement that worsens worst-case latency · Tradeoff: lower peak throughput vs. bounded tail latency · Operational: every performance PR must report p99/p999, not mean, against §28's targets · Violated: a scheduler that benchmarks "fast" on average yet misses deadlines on the exact workload it was built for.
  • P2 — Timing Is a First-Class API. Rule: every timing assumption must be measurable and exported as a named metric · Tradeoff: instrumentation overhead vs. observability · Operational: wakeup latency, jitter, execution variance are rt_trace fields, never free-text log lines · Violated: an incident where "it felt slow" cannot be converted into a number within minutes.
  • P3 — Explicit State Machines. Rule: every task-lifecycle transition is a typed enum transition, never an implicit flag flip · Tradeoff: more boilerplate vs. unrepresentable illegal states · Operational: TaskState transitions are exhaustively matched, no catch-all arm · Violated: a task silently stuck between Running and Blocked with no recorded transition.
  • P4 — Bounded Blocking. Rule: every synchronization primitive must expose and enforce a provable worst-case blocking bound · Tradeoff: priority-inheritance bookkeeping cost vs. unbounded inversion risk · Operational: rt_sync computes the blocking term B consumed by admission control (I6) · Violated: unbounded priority inversion of the class that stalled the Mars Pathfinder rover.
  • P5 — Scheduler Policy Isolation. Rule: RMS and EDF share infrastructure (queues, dispatch, sync) but never policy logic · Tradeoff: some duplicated glue code vs. safe independent experimentation · Operational: rt_rms/rt_edf depend on rt_core/rt_runtime, never on each other · Violated: an EDF-only heuristic leaking into the RMS static priority-assignment path.
  • P6 — Traceability by Default. Rule: every scheduling decision emits a TraceEvent; invisible behavior is a defect, not a missing feature · Tradeoff: ring-buffer memory/CPU cost vs. field debuggability · Operational: rt_trace overhead is itself measured against the <5% budget (M9) · Violated: a deadline miss with no corresponding trace event explaining why.
  • P7 — Monotonic Time Only. Rule: wall-clock time is forbidden anywhere in a scheduling decision path · Tradeoff: harder correlation with external wall-clock logs vs. immunity to clock-set jumps · Operational: rt_clock::clock exposes only a CLOCK_MONOTONIC-backed Instant type · Violated: an NTP step-back making a task appear to have a negative time-to-deadline.
  • P8 — Admission Before Execution. Rule: unschedulable workloads must fail at admission, not at runtime · Tradeoff: conservative rejection of some practically-schedulable sets vs. runtime safety · Operational: rt_rms::admission/rt_edf::admission run before the first task enqueues · Violated: infeasibility discovered only after production deadline misses.
  • P9 — Minimize Unsafe Regions. Rule: unsafe is confined to affinity management, timer FFI, and low-level synchronization primitives, each in a named module · Tradeoff: ergonomic cost vs. an auditable safety surface · Operational: CI greps for unsafe outside the three allow-listed modules and fails the build · Violated: an aliasing bug in hot-path scheduler code an audit should have caught.
  • P10 — Measurement Before Optimization. Rule: no performance change lands without trace evidence, benchmark evidence, and a regression guard · Tradeoff: slower iteration vs. no unverified "obvious" wins · Operational: every PR touching rt_rms/rt_edf/rt_runtime attaches a criterion diff · Violated: a "faster" queue swap that regresses p99 dispatch latency 3× under load.
  • P11 — Reproducibility Matters. Rule: benchmark runs must be byte-for-byte replayable from a recorded workload plus seed · Tradeoff: extra fixture/version bookkeeping vs. trustworthy comparisons · Operational: rt_bench embeds the workload hash and toolchain version in every result file · Violated: a regression that cannot be reproduced two weeks later on the same hardware.
  • P12 — Fail Loudly Under Overload. Rule: deadline misses and admission rejections must be immediately surfaced via trace, metric, and non-zero exit code · Tradeoff: noisier operator experience vs. silent SLA erosion · Operational: MissedDeadline is a TraceEventKind variant with no swallow-and-continue path · Violated: a dashboard that reads green while quietly missing every third deadline.

I5 The highest-priority ready task on a core is running, except within a bounded PI window core scheduling correctness rt_runtime::dispatch preempt check rt_conformance trace cross-check priority_inversion_duration_us forced preemption + PI diagnostic dump
I6 Blocking duration under priority inheritance never exceeds the admission-computed bound B bounds worst-case latency rt_sync::pi watchdog timer fires at duration > B pi_blocking_overrun_total deadlock diagnostics + configurable panic policy
I7 A task never executes on a CPU outside its declared affinity mask isolation guarantee rt_runtime::affinity assert cpu ∈ mask on dispatch affinity_violation_total forced migration + trace event
I8 Every TraceEvent carries a strictly increasing per-CPU monotonic timestamp trace ordering correctness rt_trace::buffer replay ordering check trace_reorder_total reorder/reject at export, flag the run
I9 Timer cancellation is race-free: a cancelled timer never fires timer correctness rt_clock::timerfd conformance/timers/cancel.yaml cancelled_timer_fired_total (must stay 0) assert-fail in conformance, page the timer owner
I10 Ready-queue operations hold the scheduler lock for a bounded, measured duration bounds dispatch tail latency rt_runtime::dispatch lock-hold-time histogram lock_hold_us_p99 alarm at >2× budget, investigate contention
I11 WCET accounting never double-counts a partial execution across a preemption boundary accounting correctness rt_core runtime accumulator conformance/tasks fixture diff total_runtime cross-check recompute from trace, patch counter
I12 Deadline-miss detection latency is itself bounded to one dispatch tick overload visibility must be timely rt_runtime::worker + rt_trace trace timestamp delta check deadline_miss_detect_latency_us escalate if detection itself lags
I13 Admission control is idempotent: re-admitting the same TaskSpec set yields the same decision reproducibility (P11) rt_rms::admission / rt_edf::admission conformance replay diff admission_nondeterminism_total bisect via replay, treat as P0
I14 The trace ring buffer never silently drops events without incrementing a visible counter observability must never lie by omission (P6) rt_trace::buffer drop counter vs. trace gap trace_dropped_events_total alert, widen buffer or enable sampling

Debugging methodology: every invariant maps to exactly one runtime assertion inside a deterministic single-threaded simulator mode (rt_conformance::harness with --deterministic-sim), which replays a fixed logical clock instead of rt_clock's wall time. Each I# violation aborts the simulator immediately with the failing invariant ID in the panic message, so a conformance failure always points at exactly one row of this table rather than a stack trace through unrelated code.

8. Domain Model — Task & Scheduling Model

8.1 Task Model

Tasks are modeled as periodic or sporadic jobs. Each TaskSpec (§11) declares:

Field Meaning
period activation interval (periodic tasks) or minimum inter-arrival time (sporadic)
wcet worst-case execution time per activation
relative_deadline completion deadline, relative to release
offset initial release delay from scheduler epoch
affinity CpuMask of allowed cores
criticality scheduling-importance class, used by admission and overload governance (§21)

8.2 Task Lifecycle State Machine

   CREATED
      │
      v
   READY  <───────────────┐
      │                    │
      v                    │
   RUNNING ──preempt──> PREEMPTED
      │  \                 │
      │   \___block____>  │
      │        v            │
      │     BLOCKED         │
      │        │            │
      │        └───ready────┘
      v
  COMPLETED   (or MISSED_DEADLINE, reachable from RUNNING/READY/PREEMPTED on deadline expiry)

Every arrow is one rt_core::state transition function; there is no path that bypasses READY en route to RUNNING, and MISSED_DEADLINE is reachable from any pre-COMPLETED state, never silently absorbed (Principle P12, Invariant I3).

8.3 RMS Priority Assignment

Static priority mapping: smaller period ⇒ higher priority.

Task Period Priority
sensor 5 ms 1 (highest)
control_loop 10 ms 2
logger 100 ms 3 (lowest)

Ties (equal periods) are broken by declaration order, recorded explicitly so admission results are reproducible (Invariant I13) — never by insertion-order-of-a-hash-map, which is not stable across runs.

8.4 EDF Deadline Ordering

Dynamic priority mapping: earlier absolute deadline ⇒ higher priority. The ready queue (rt_edf::deadline_queue, a BinaryHeap keyed on absolute deadline, ADR-12) is re-ordered on every release; absolute deadline for release k is offset + k·period + relative_deadline, monotonically non-decreasing per Invariant I4.

8.5 Admission Control Equations

RMS sufficient (utilization-bound) test, Liu & Layland (1973):

U = Σ (wcet_i / period_i)  for i in 1..n
Admit if:  U <= n * (2^(1/n) - 1)

EDF necessary-and-sufficient test (implicit-deadline case), Liu & Layland (1973):

U = Σ (wcet_i / period_i)  for i in 1..n
Admit if:  U <= 1.0

Exact RTA (fixed priority, Lehoczky/Sha/Ding 1989; generalized by Audsley et al. 1993) replaces the sufficient bound when the utilization test fails but exact feasibility is still worth checking (§15); its recurrence is described, not coded, in §15.2.

tasks:
  - name: sensor
    period_ms: 5
    wcet_us: 500
    deadline_ms: 5
    criticality: high
  - name: control_loop
    period_ms: 10
    wcet_us: 1200

This three-task set is the canonical fixture referenced by conformance/rms/liu_layland.yaml and conformance/edf/ordering.yaml (§15.5, §16.5): U = 500/5000 + 1200/10000 + 5000/100000 = 0.10 + 0.12 + 0.05 = 0.27, admissible under both the RMS bound for n=3 (3·(2^(1/3)-1) ≈ 0.7798) and the EDF bound (U ≤ 1.0).

12. Phase 0 — Repository & Toolchain Bootstrap

12.1 Objectives

Stand up a compiling, CI-green, reproducible Cargo workspace and the correctness kernel it will host. Scope: workspace skeleton, pinned toolchain, lint/format enforcement, CI workflows, and the unsafe-region policy (P9) that every later phase must respect. Constraint introduced: no crate may compile with warnings (#![deny(warnings)]), and no crate outside rt_clock/rt_runtime/rt_sync may contain unsafe at all (P9).

12.2 Detailed Implementation Steps

  1. Initialize the Cargo workspace at Cargo.toml with the ten member crates listed in §10.
  2. Pin rust-toolchain.toml to a specific stable release; unpinned toolchains are the single largest source of the benchmark drift Pitfall 1 below (ADR-20).
  3. Add clippy.toml and rustfmt.toml; enable clippy::all and clippy::pedantic as CI-deny lints.
  4. Add .github/workflows/ci.yml (build+test+lint matrix), fuzz.yml, benchmark.yml, release.yml.
  5. Create the ten crate skeletons (crates/rt_core … crates/rt_bench) with empty lib.rs/main.rs per §10, each declaring its own Cargo.toml with workspace-inherited dependency versions.
  6. Configure the tracing subscriber initialization path in rt_core::lib (bring-up only; §19 wires the full pipeline) — this is the P6 traceability commitment made concrete from commit one.
  7. Add Makefile targets: build, test, lint, bench, fuzz, conformance.
  8. Add reproducible Dockerfile/docker-compose.yml dev environment (ADR-17) pinned to the same toolchain version as rust-toolchain.toml.
  9. Add the ADR template (docs/adr/template.md) and docs/threat-model.md skeleton (§22 pre-wires here).
  10. Configure cargo-nextest (ADR-13) as the workspace test runner and wire it into ci.yml.
  11. Grep-based CI check enforcing P9's unsafe-region allow-list (fails the build on violation).
  12. Configure deny.toml-equivalent dependency licensing gate feeding ADR-23.

Theory anchor: the workspace boundary itself encodes P5 (Scheduler Policy Isolation) — rt_rms and rt_edf are separate crates, not modules of one crate, specifically so a cargo build -p rt_rms can never accidentally pull in EDF-specific code.

12.3 Deliverable

A workspace that builds clean (cargo build --workspace, zero warnings), passes cargo nextest run --workspace (currently a no-op test set), passes cargo clippy --workspace -- -D warnings, and boots a tracing subscriber that prints one structured startup line per crate.

12.4 Acceptance Criteria

  • cargo build --workspace completes in ≤ 90 s on a cold cache (CI runner class: 4 vCPU / 16 GB).
  • Zero unsafe blocks outside rt_clock, rt_runtime, rt_sync (CI grep gate, exit 1 otherwise).
  • conformance/bootstrap/workspace_load.toml and conformance/bootstrap/lint_rules.txt both pass.
  • Cold-start-to-first-tracing-line ≤ 500 ms (§4 startup budget, measured in bench_cmd).

12.5 Conformance Fixtures

  • conformance/bootstrap/workspace_load.toml — asserts all ten crates resolve and compile with the pinned toolchain; malformed-Cargo.toml variant asserts a clean build failure, not a panic.
  • conformance/bootstrap/lint_rules.txt — asserts denied warnings actually fail the build (a regression test on the CI gate itself, not just the code).

12.6 Pitfalls

  1. Non-pinned toolchain causing silent benchmark drift between CI and local runs — root cause: no rust-toolchain.toml; debugging method: diff rustc --version --verbose across environments; signal: identical code, differing criterion p99 by >10%; recovery: pin and re-baseline.
  2. Feature leakage across crates via workspace-unified feature resolution — root cause: Cargo's default feature unification; debugging method: cargo tree -e features; signal: rt_rms compiling with a rt_edf-only feature enabled; recovery: split feature-gated code into separate crates, not features.
  3. Global mutable state (static mut, lazy_static singletons) sneaking into tests — root cause: test convenience; debugging method: cargo nextest run --no-capture order randomization exposing cross-test coupling; signal: tests pass alone, fail in full-suite order; recovery: inject state via constructor parameters, never globals.
  4. Non-deterministic CI environments (shared runners with noisy neighbors) polluting benchmark gates — root cause: CI runners are not isolated for timing work; debugging method: compare benchmark.yml run-to-run variance on the same commit; recovery: gate merges on correctness tests only in CI, run timing gates on dedicated hardware (§27).
  5. Hidden nightly-only dependency creeping in transitively — root cause: an unpinned transitive dep using a nightly-only feature; debugging method: cargo build on stable in a clean container; recovery: vendor or replace the dependency (ADR-03).

12.7 Performance Concerns

Build reproducibility matters more than raw build speed at this phase. Avoid excessive proc-macro usage and heavy compile-time metaprogramming in rt_core — every crate downstream recompiles when it changes, and compile-time cost compounds across ten crates. Target: incremental rebuild of a single leaf crate ≤ 8 s.

12.8 Edge Cases

  • Cross-platform timer behavior differences (this phase only stubs rt_clock; full handling is §13).
  • Differing CPU counts across CI runners vs. developer machines affecting rt_bench defaults.
  • ARM vs. x86 timing-precision differences surfacing later; captured now as a documented assumption in docs/threat-model.md rather than deferred silently.

12.9 Failure Analysis

A red CI pipeline at this phase blast-radius is zero (nothing runs in production yet), but a green pipeline hiding a lint-gate regression is the dangerous failure: detection is the conformance/bootstrap/lint_rules.txt self-test (12.5); containment is treating any CI-config change as requiring its own PR review separate from feature code; recovery is re-adding the deny-lint and re-running the self-test before merging further code.

12.10 Operational Notes

Metrics: none yet (no runtime to instrument). Tracing: rt_core::lib emits a bootstrap.startup span with fields crate_count, toolchain_version, elapsed_ms. Deployment: none (dev/CI only). Rollback: revert the workspace commit; there is no running system to migrate. Compatibility: the workspace Cargo.toml member list is the compatibility contract for CI — adding a crate requires updating ci.yml's matrix in the same PR.

13. Phase 1 — Time Infrastructure

13.1 Objectives

Build the deterministic, monotonic-only timer subsystem every later phase depends on (Principle P7). Scope: rt_clock — clock abstraction, timerfd backend, a timer-wheel prototype, drift/jitter measurement. Constraint introduced: no code anywhere in the workspace may call SystemTime::now() or CLOCK_REALTIME; this is enforced by a CI grep gate added in this phase and never relaxed.

13.2 Detailed Implementation Steps

  1. Implement the monotonic clock abstraction rt_clock::clock wrapping POSIX clock_gettime(CLOCK_MONOTONIC, ...) per POSIX.1-2017, clause 2.8.6 (§5 RFCs/Specifications).
  2. Implement rt_clock::timerfd, wrapping timerfd_create/timerfd_settime for high-resolution wakeup scheduling — the timerfd-backed monotonic-only timer source locked in by ADR-21 (rejecting CLOCK_REALTIME outright per Principle P7), with its drift-correction structure informed by RFC 5905's clock-filter algorithm (13.2 step 5 below).
  3. Implement rt_clock::wheel, a hierarchical timer-wheel prototype for O(1) amortized insertion when timer counts exceed the BinaryHeap crossover point identified in ADR-12.
  4. Implement timer cancellation as a lock-free generation-counter CAS on TimerHandle (I9): a cancelled handle's expiry callback checks its generation before firing and no-ops on mismatch.
  5. Implement drift detection: periodically cross-check CLOCK_MONOTONIC delta against a CLOCK_MONOTONIC_RAW reference, following the discipline-loop structure described in RFC 5905 (NTPv4) §11's clock-filter algorithm, adapted for local drift accounting rather than network sync.
  6. Implement jitter measurement in rt_clock::metrics: record actual-vs-scheduled wakeup delta into a histogram per Brendan Gregg's methodology (Systems Performance, 2020 — §5 Books).
  7. Implement timer batching: coalesce wakeups within a configurable epsilon window to bound wakeup-storm risk under high timer density.
  8. Add clock-calibration conformance tests validating wakeup precision against configured thresholds.

13.3 Deliverable

A standalone rt_clock crate exposing a monotonic clock, timerfd-backed deadline timers, and a metrics surface reporting wakeup latency and jitter with microsecond-level resolution, independently testable via rt_cli timers bench.

13.4 Acceptance Criteria

  • Wakeup jitter p99 ≤ 100 µs against the §4 target, measured over a 10,000-timer run.
  • Wakeup latency p50 ≤ 15 µs, p99 ≤ 50 µs (§4), measured on an otherwise-idle core.
  • conformance/timers/wakeup_precision.yaml and conformance/timers/cancel.yaml both pass with zero cancelled_timer_fired_total (I9).
  • Timer insertion cost documented and benchmarked at both the BinaryHeap and wheel backend for n ∈ {16, 512, 4096} timers.

13.5 Conformance Fixtures

  • conformance/timers/wakeup_precision.yaml — asserts wakeup jitter stays under the configured threshold across a synthetic multi-timer workload; malformed variant feeds a negative expiry.
  • conformance/timers/cancel.yaml — asserts cancelled timers never fire (I9); replay variant re-runs the exact cancellation-race schedule recorded from a prior failure to guard against regression.

13.6 Pitfalls

  1. Accidental CLOCK_REALTIME usage via a transitive dependency — root cause: a logging crate defaulting to wall time; debugging method: the CI grep gate added in 13.1; signal: a deadline computed from a value that jumps backward on NTP step; recovery: replace the dependency call site.
  2. Timer drift accumulation across a long-running process — root cause: naive next_release += period arithmetic accumulating rounding error; debugging method: drift histogram trend over a 24 h soak; signal: next_release diverging from offset + k·period; recovery: recompute from the absolute epoch each release, never accumulate.
  3. Coalesced wakeups under CPU pressure hiding a real overload — root cause: timerfd coalescing semantics under kernel tickless idle; debugging method: compare requested vs. delivered expiry timestamps in the trace; signal: jitter spike correlated with CPU frequency-scaling events; recovery: disable coalescing for Safety-criticality tasks specifically.
  4. Missed timer expirations under scheduler starvation of the timer-processing thread itself; debugging method: lock_hold_us_p99 (I10) cross-checked against timer-thread scheduling; recovery: pin the timer-processing thread to a dedicated, isolated core.
  5. Busy-spin fallback silently masking a timerfd configuration bug — root cause: a defensive busy-wait loop added "temporarily"; debugging method: CPU-utilization outlier on an otherwise-idle core; recovery: remove the fallback, fail loudly (P12) instead.

13.7 Performance Concerns

Heap-based timer insertion is O(log n); at 4096 timers this is the dominant per-wakeup cost budgeted in §32 C4. The wheel backend (13.2 step 3) trades O(1) amortized insertion for coarser expiry granularity — switch backends only past the empirically measured crossover (documented in benchmarks/), never speculatively.

13.8 Edge Cases

  • Simultaneous expirations of multiple timers on the same tick (ordering must be deterministic — I8).
  • Insertion of an already-expired timer (must fire on the next tick, not be silently dropped).
  • Long-duration timers (multi-hour) interacting with 32-bit-adjacent overflow in intermediate arithmetic.
  • Clock-source rollback anomalies on VM migration (detected via the drift monitor, 13.2 step 5).

13.9 Failure Analysis

Timer subsystem failure blast radius is total — every phase above depends on it. Detection: drift and jitter histograms breaching §4 thresholds trigger an immediate alert (timer_drift_us metric). Containment: the timer subsystem runs on its own dedicated core (13.6.4) so a timer-thread stall does not directly starve worker threads. Recovery path: rt_clock::drift exposes a manual recalibration command; postmortem guidance requires attaching the drift histogram, not just the incident timestamp.

13.10 Operational Notes

Metrics: wakeup_latency_us (histogram), timer_jitter_us (histogram), timer_drift_us (gauge), cancelled_timer_fired_total (counter, must stay 0). Tracing spans: clock.arm, clock.fire, clock.cancel. Structured-log fields: timer_id, cpu_affinity, requested_expiry, actual_expiry. Deployment: no external dependency change. Rollback: safe — no persisted state (ADR-04). Migration: none. Compatibility: TimerHandle is internal-only, not a compatibility surface (§11).

14. Phase 2 — Task Model & Runtime State

14.1 Objectives

Implement the immutable task specification and the mutable runtime-state container that the schedulers in Phases 3–4 will consume. Scope: rt_core::task, rt_core::state, rt_core::validation. Constraint introduced: TaskSpec becomes structurally immutable post-admission (I2) — this phase adds the type- level enforcement (no &mut accessor exists after the admission call consumes the builder).

14.2 Detailed Implementation Steps

  1. Define TaskSpec (§11) in rt_core/src/task.rs, constructed only via a builder that is consumed (moved) on admission — enforcing I2 at the type level, not by convention.
  2. Define TaskRuntimeState (§11) in rt_core/src/state.rs as the mutable companion, one instance per admitted task, owned by the core it is currently scheduled on.
  3. Implement the TaskState lifecycle transition function set as an exhaustive match (P3, I3); each transition function takes the current state and an event, returning Result<TaskState, illegal transition error> rather than silently clamping to a default.
  4. Implement activation counters, preemption counters, and missed-deadline counters as saturating (not wrapping) u64 increments — Pitfall 3 below explains why saturating matters.
  5. Implement deadline accounting: absolute_deadline = offset + k·period + relative_deadline, recomputed from the epoch each release per the anti-drift discipline established in Phase 1 (13.6.2) — never accumulated incrementally.
  6. Implement WCET tracking: running-max observed execution time recorded per task, cross-checked against the declared wcet field to surface WCET-underestimation as a first-class signal (feeds §21's overload governance).
  7. Implement runtime accumulation across preemption boundaries without double-counting (I11): each Running→Preempted transition snapshots elapsed time exactly once.
  8. Implement release-offset handling, including the edge case of an offset that places the first release before scheduler epoch zero (14.8).
  9. Add serde-based serialization for TaskSpec (ADR-05) so fixtures are diffable text, not opaque binary.
  10. Implement the validation pipeline (rt_core::validation) rejecting structurally invalid specs (deadline < WCET, zero period) before admission control ever sees them — a fast, cheap pre-filter ahead of the O(n²) exact-RTA path in Phase 3.

14.3 Deliverable

A rt_core crate exporting validated, immutable TaskSpec construction and a runtime-state container whose every transition is exhaustively typed, independently testable via conformance/tasks/* without needing a scheduler wired up yet.

14.4 Acceptance Criteria

  • 100% of TaskState transition functions are exhaustively matched (verified by a #[deny(non_exhaustive_omitted_patterns)]-style lint plus the state_machine.yaml fixture).
  • conformance/tasks/invalid_deadline.yaml rejects all 6 documented invalid-spec shapes with a specific AdmissionError variant, not a generic error.
  • Runtime counters (activations, preemptions, missed_deadlines) survive 10,000 synthetic transitions with zero overflow and zero double-count (I11), verified in state_machine.yaml.

14.5 Conformance Fixtures

  • conformance/tasks/invalid_deadline.yaml — asserts invalid deadlines (deadline < WCET, deadline = 0, period = 0) are rejected pre-admission with the correct AdmissionError variant.
  • conformance/tasks/state_machine.yaml — asserts illegal lifecycle transitions (e.g. Completed → Running) return an error rather than mutating state; replay variant re-plays a captured 10,000-transition trace and diffs the resulting counters byte-for-byte (P11).

14.6 Pitfalls

  1. Mutable task specs reintroduced via a #[derive(Clone)] + external mutation path — root cause: a convenience clone bypassing the builder; debugging method: grep for any &mut TaskSpec outside the builder module; recovery: make the relevant fields private with no public setter.
  2. Invalid deadline updates slipping past validation due to an incomplete rule set — root cause: validation added ad hoc rather than enumerated; debugging method: property-based testing generating adversarial TaskSpec values; recovery: encode all validation rules in one table, test exhaustively.
  3. Double-activation bugs: a task released twice for the same period tick under offset-rounding error — root cause: floating-point period arithmetic; debugging method: replay the exact tick sequence in rt_conformance::harness; recovery: use integer nanosecond arithmetic exclusively, never f64.
  4. Runtime counter overflow at extreme run durations — root cause: u64 wraparound theoretically possible past ~584 years of nanosecond accumulation, practically relevant for saturating vs. wrapping semantics choice; recovery: saturating arithmetic with an explicit "counter saturated" trace event rather than silent wraparound.
  5. Inconsistent lifecycle transitions across the RMS/EDF boundary — root cause: a scheduler-specific shortcut bypassing the shared transition function; debugging method: P5 code-review gate — no scheduler crate may call a private rt_core::state function; recovery: widen the public transition API instead of reaching around it.

14.7 Performance Concerns

TaskRuntimeState is sized to stay within one or two cache lines (target ≤ 128 B) since it is read on every dispatch decision; padding and field order matter more here than anywhere else in rt_core. Validation-pipeline cost must stay negligible relative to the Phase 3 exact-RTA cost it precedes (§32 C6) — target ≤ 200 ns per task validated.

14.8 Edge Cases

  • Zero WCET (degenerate but not invalid — treated as a valid always-instantaneous task, still admission-checked for deadline sanity).
  • relative_deadline < wcet (structurally infeasible regardless of the rest of the task set — rejected in validation, never reaches admission).
  • Enormous periods (multi-day) interacting with u64 nanosecond range — verified not to overflow.
  • Release offsets that place the first release before scheduler epoch zero — clamped to epoch zero with an explicit trace event, never silently dropped.

14.9 Failure Analysis

A validation-pipeline bug that under-rejects manifests downstream as an admission-control anomaly or, worse, a runtime deadline miss traceable to a task that should never have been admitted. Detection: rt_conformance's adversarial fixture corpus (14.6.2) run on every PR. Blast radius: bounded to the single malformed task if validation later catches it at admission (I1); unbounded if it does not. Recovery: tighten the validation rule table, add the missed case as a new fixture, never patch around it downstream in the scheduler.

14.10 Operational Notes

Metrics: task_validation_rejected_total{reason}, state_transition_rejected_total. Tracing spans: task.validate, task.transition. Structured-log fields: task_id, from_state, to_state, reason. Deployment: none. Rollback: safe, stateless. Migration: schema_version on WorkloadSpec (§11) gates any future TaskSpec field addition (§25).

15. Phase 3 — RMS Scheduler & Admission Control

15.1 Objectives

Deliver a runnable fixed-priority scheduler with both the sufficient (utilization-bound) and exact (response-time) admission tests. Scope: rt_rms::scheduler, rt_rms::admission, rt_rms::rta, rt_rms::priority. Constraint introduced: admission must run to completion (accept or a specific rejection reason) before a single task from the set is enqueued — no partial admission (P8, I1).

15.2 Detailed Implementation Steps

  1. Implement static priority assignment in rt_rms::priority: shortest-period-highest-priority, with declaration-order tie-breaking (I13) — named, not coded, per Liu & Layland (1973).
  2. Implement the ready queue as a BinaryHeap<TaskId> keyed by static priority (ADR-12), one instance per core once Phase 5 lands, single global instance until then.
  3. Implement preemption logic in rt_rms::scheduler::on_tick/select_next: a released higher-priority task immediately preempts a running lower-priority one, recorded as a TaskPreempted trace event.
  4. Implement the Liu & Layland (1973) sufficient utilization-bound test: U ≤ n·(2^(1/n) − 1) — see §8.5 — as the fast admission path.
  5. Implement exact response-time analysis (Lehoczky, Sha, Ding 1989; generalized by Audsley et al. 1993 — §5 Papers) as the fallback when the utilization bound fails but exact feasibility is still worth checking: iteratively recompute each task's worst-case response time against the interference from all higher-priority tasks until the fixed point converges or exceeds the deadline.
  6. Implement blocking-aware admission: fold the PI-bounded blocking term B (I6, computed by rt_sync once Phase 6 lands; stubbed here as a configurable constant) into the RTA recurrence.
  7. Implement dispatch hooks connecting rt_rms::scheduler to the (stubbed, single-core) dispatch layer.
  8. Implement starvation diagnostics: flag any admitted task whose measured response time trends toward its RTA-computed bound over a rolling window.
  9. Add TaskReleased/TaskStarted/TaskPreempted trace events at every relevant transition (P6).
  10. Add a schedule-visualization export (feeds rt_trace's Chrome-trace pipeline in §19).

15.3 Deliverable

A runnable rt_rms scheduler that admits or rejects a WorkloadSpec with a specific reason, and, once admitted, dispatches strictly by static priority with full preemption support — independently runnable via rt_cli run --policy rms <workload>.

15.4 Acceptance Criteria

  • conformance/rms/liu_layland.yaml validates the utilization bound against the §8.6 three-task example (U = 0.27, admissible, n=3 bound ≈ 0.7798) and at least 4 additional generated task sets spanning admitted and rejected outcomes.
  • conformance/rms/preemption.yaml validates that a released higher-priority task preempts within ≤ 25 µs (§4 dispatch p99) of release, measured across 1,000 preemption events.
  • Exact RTA converges (or correctly reports non-convergence) within ≤ 15 ms for a 512-task set (§4, §32 C6).

15.5 Conformance Fixtures

  • conformance/rms/liu_layland.yaml — validates the utilization bound decision against known-admitted and known-rejected task sets; malformed variant supplies a task set with period = 0.
  • conformance/rms/preemption.yaml — validates higher-priority takeover timing; regression variant replays a captured priority-inversion-adjacent schedule from a prior incident fixture.

15.6 Pitfalls

  1. Priority inversion under naive locking (addressed structurally only once Phase 6's PI lands; this phase's pitfall is under-estimating B and admitting a set that Phase 6 later reveals as infeasible) — debugging method: re-run admission with the real (not stubbed) blocking term once available; signal: a previously-admitted set failing re-admission (I13 flags this as unexpected).
  2. Incorrect tie-breaking on equal periods — root cause: relying on hash-map iteration order; signal: non-reproducible admission results across runs (violates I13); recovery: explicit declaration-order tie-break, tested in liu_layland.yaml.
  3. Deadline accounting skew from mixing the Phase 2 epoch-based computation with an incremental shortcut introduced for "performance"; signal: deadline_monotonicity_violation_total (I4) firing; recovery: delete the shortcut, re-derive from epoch every time.
  4. Release-jitter accumulation under sustained preemption pressure; debugging method: jitter histogram trend correlated with preemption-frequency metric; recovery: verify the timer subsystem (Phase 1) is not itself the source before blaming the scheduler.
  5. Ready-queue corruption under concurrent preemption and completion racing on the same task — root cause: missing lock scope around a two-step "remove-then-reinsert" priority update; debugging method: rt_conformance::harness --deterministic-sim with interleaving exploration; recovery: make the priority update a single atomic heap operation, never remove-then-reinsert.

15.7 Performance Concerns

Priority-queue operations dominate scheduler overhead at this phase: enqueue/dequeue are O(log n); measure enqueue latency, preemption frequency, and context-switch amplification (a single high- frequency task can force many low-priority preemptions per second). Exact RTA is O(n²) worst case per admission call (§32 C6) — cache the per-task interference set between iterations rather than recomputing from scratch each fixed-point step.

15.8 Edge Cases

  • A task set exactly at the utilization bound boundary (U == n·(2^(1/n)−1) to floating-point precision) — admission must be deterministic, not precision-dependent (use a small documented epsilon).
  • RTA non-convergence (response time still growing past the deadline) — must terminate and reject, not loop indefinitely; bounded by the sum of all deadlines as a hard iteration cap.
  • Simultaneous release of multiple equal-priority tasks at the same tick.
  • Admission of a single-task set (degenerate n=1, bound trivially 1.0).

15.9 Failure Analysis

An admission-control defect that over-admits manifests as repeated deadline misses, ready-queue growth, and cascading jitter under sustained load — exactly the failure mode Phase 8's overload fixtures are built to surface (§20). Detection: trace counters (missed_deadlines), runtime alarms on priority_inversion_duration_us (I5), and latency histograms trending toward the deadline. Containment: admission rejects further task additions once the runtime detects it is already over-committed (a Phase 9 overload-governance behavior, §21). Recovery: re-run admission with corrected WCET estimates; postmortem must attach the RTA trace, not just the miss count.

15.10 Operational Notes

Metrics: rms_admission_result{outcome}, priority_inversion_duration_us, preemption_total, rta_convergence_iterations. Tracing spans: rms.admit, rms.select_next, rms.preempt. Log fields: task_id, priority_rank, response_time_bound_us. Deployment: none beyond Phase 0/1. Rollback: safe, stateless. Compatibility: SchedulerPolicy::RateMonotonic is a frozen enum variant (§11).

16. Phase 4 — EDF Scheduler & Dynamic Admission

16.1 Objectives

Deliver the dynamic-priority counterpart to Phase 3: earliest-absolute-deadline dispatch with EDF feasibility analysis. Scope: rt_edf::scheduler, rt_edf::admission, rt_edf::deadline_queue, rt_edf::feasibility. Constraint introduced: the ready queue re-orders on every release (unlike RMS's static order), so queue-maintenance cost becomes a first-class design variable, not an afterthought.

16.2 Detailed Implementation Steps

  1. Implement absolute-deadline computation per §8.4: offset + k·period + relative_deadline, monotonically non-decreasing across releases (I4).
  2. Implement the dynamic priority queue rt_edf::deadline_queue as a BinaryHeap<TaskId> keyed by absolute deadline (ADR-12), re-heapified on every release and completion.
  3. Implement deadline updates on release, replacing the prior entry rather than inserting a duplicate (guards against a stale-priority bug class specific to dynamic reordering).
  4. Implement EDF dispatch logic (select_next): always the earliest-deadline ready task, demonstrating the uniprocessor-optimality result from Liu & Layland (1973, §5 Papers) under their stated assumptions (independent tasks, preemptive, no blocking).
  5. Implement overload diagnostics: detect and flag the "domino effect" where one deadline miss cascades into subsequent misses under EDF specifically (a documented EDF failure mode absent from bounded- priority RMS, where lower-priority tasks are protected from the domino by priority order).
  6. Implement tie-breaking semantics for equal absolute deadlines: declaration-order, mirroring 15's RMS tie-break for reproducibility (I13).
  7. Implement the EDF necessary-and-sufficient admission test U ≤ 1.0 (Liu & Layland 1973) for the implicit-deadline case.
  8. Implement EDF feasibility analysis for the sporadic (non-implicit-deadline) case using the demand- bound-function approach from Baruah, Mok, Rosier (1990, §5 Papers).
  9. Add runtime tracing for deadline-queue re-heapify events and dynamic-reprioritization cost.
  10. Add queue instrumentation: heap-depth and re-heapify-latency histograms exported to rt_trace.

16.3 Deliverable

A runnable rt_edf scheduler admitting or rejecting a WorkloadSpec via the EDF feasibility test and dispatching strictly by earliest absolute deadline, runnable via rt_cli run --policy edf <workload>, directly comparable against the Phase 3 RMS run on the same workload (feeds §31).

16.4 Acceptance Criteria

  • conformance/edf/ordering.yaml validates earliest-deadline dispatch across 1,000 releases with zero ordering violations (I4/I8).
  • conformance/edf/overload.yaml validates that an overloaded EDF set (U > 1.0) surfaces the domino effect visibly in the trace within one dispatch tick of the first miss (I12).
  • Admission via U ≤ 1.0 matches exact feasibility analysis (16.2 step 8) on 100% of a 200-case generated corpus.

16.5 Conformance Fixtures

  • conformance/edf/ordering.yaml — verifies earliest-deadline execution ordering; malformed variant supplies a task with a deadline computed to overflow Instant arithmetic.
  • conformance/edf/overload.yaml — verifies overload-degradation visibility; regression variant replays a captured domino-effect trace to confirm the diagnostic still fires identically.

16.6 Pitfalls

  1. Incorrect deadline recomputation on release, leaving a stale absolute deadline in the heap — root cause: updating the task's field but not re-heapifying; debugging method: heap-invariant assertion in rt_conformance::harness --deterministic-sim; recovery: treat deadline update and re-heapify as one atomic operation.
  2. Heap instability under high release frequency — root cause: repeated re-heapify cost growing with heap depth; debugging method: re-heapify-latency histogram (16.2 step 10); recovery: batch releases within a tick where safe, per the timer-batching precedent from Phase 1 (13.2 step 7).
  3. Priority oscillation between two near-equal-deadline tasks under jitter — root cause: sub-tick timestamp noise reordering two tasks whose deadlines differ by less than clock resolution; recovery: quantize comparison to the clock's actual resolution, not raw nanoseconds.
  4. Equal-deadline starvation of the declaration-order loser under sustained load — debugging method: per-task response-time distribution split by tie-break rank; recovery: document as expected behavior (I13-consistent), not a bug, but surface it in rms_vs_edf.md (docs/scheduler-analysis).
  5. Queue-mutation races between a completion (dequeue) and a release (insert) on the same tick — root cause: missing lock scope, same class as Pitfall 5 in §15.6; recovery: single atomic heap operation per tick per queue.

16.7 Performance Concerns

EDF requires materially more queue maintenance than RMS because every release potentially changes the dispatch order, not just adds an entry at a known priority. Measure heap re-heapify cost, migration overhead (once Phase 5 lands), and dynamic-reprioritization cost separately from raw enqueue/dequeue — they are the EDF-specific overhead RMS does not pay, and the comparative cost is exactly what §31 and the Buttazzo (2005) "Judgment Day" comparison quantify.

16.8 Edge Cases

  • A task set exactly at U == 1.0 (boundary feasibility, same epsilon-precision concern as 15.8).
  • Deadlines computed far enough in the future to approach Instant representable range.
  • A completion arriving in the same tick as the next release of the same task (must not double-insert).
  • An EDF set that is utilization-feasible but blocking-infeasible once Phase 6's PI bound is folded in — the blocking-aware admission wiring itself lands in Phase 6 (§18); formal CBS-based aperiodic servicing of this exact gap (Abeni & Buttazzo 1998, §5 Papers) is out of scope for this blueprint and registered as PhaseDeferred("§16") in §35.

16.9 Failure Analysis

EDF's domino effect (16.2 step 5) is the signature overload failure mode: one missed deadline reduces remaining capacity for all subsequent deadlines, cascading rather than staying contained the way a lower-priority RMS task's miss would. Detection: consecutive-miss-count trend per criticality class. Blast radius: unbounded without criticality-aware shedding — exactly the gap Phase 9 (§21) closes. Recovery: admission-time rejection of sets without headroom margin; runtime: shed lowest-criticality tasks first once overload is detected (§21).

16.10 Operational Notes

Metrics: edf_admission_result{outcome}, deadline_reheapify_latency_us, domino_miss_streak. Tracing spans: edf.admit, edf.select_next, edf.release. Log fields: task_id, absolute_deadline, heap_depth. Deployment: none beyond prior phases. Rollback: safe, stateless. Compatibility: SchedulerPolicy::EarliestDeadlineFirst is a frozen enum variant (§11); CBS/sporadic- server extensions are additive, tracked as deferrals (§35).

17. Phase 5 — Multicore Dispatch Runtime

17.1 Objectives

Extend the single-core schedulers from Phases 3–4 into a multicore dispatch runtime: per-core run queues, CPU affinity enforcement, migration, and preemption delivery. Scope: rt_runtime::worker, rt_runtime::dispatch, rt_runtime::affinity, rt_runtime::migration, rt_runtime::idle. Constraint introduced: no task may execute outside its declared affinity mask, ever, under any migration decision (I7) — this is the first phase where that invariant becomes exercisable rather than vacuously true.

17.2 Detailed Implementation Steps

  1. Build the worker-thread abstraction in rt_runtime::worker: one OS thread per core, created via std::thread::spawn and immediately pinned via sched_setaffinity per POSIX.1-2017 <sched.h> (§5 RFCs/Specifications), running SCHED_FIFO at a fixed OS priority above default (ADR-07 — no async runtime competes for these threads).
  2. Implement per-core run queues in rt_runtime::dispatch, one BinaryHeap per core (ADR-12), replacing Phase 3/4's single global queue; this is the concurrency boundary named in §3.
  3. Implement the dispatch loop: pop the highest-priority/earliest-deadline ready task for the local core, respecting affinity (I7), following the general per-core run-queue structure documented for kernel/sched/rt.c (§5 Reference Implementations) while explicitly not adopting its load-balancer.
  4. Implement wakeup signaling from rt_clock timer expiry into the correct core's run queue, using a futex-style wake primitive to keep the C4 (§32) wakeup-latency budget intact.
  5. Implement preemption-request delivery: a released higher-priority/earlier-deadline task on a busy core signals that core's worker to yield at the next preemption-safe point.
  6. Add context-switch tracing: every Running→Preempted and Running→Completed transition emits a TaskPreempted/TaskCompleted trace event tagged with the CpuId (P6).
  7. Implement idle-state management in rt_runtime::idle: an idle core parks (no busy-spin, per the Pitfall in 13.6.5) until the next timer expiry or cross-core wake signal.
  8. Implement migration hooks in rt_runtime::migration: a task may move cores only within its affinity mask, and only when the target core's queue has strictly lower contention — migration decisions are themselves traced (Migrated TraceEventKind, §11).
  9. Add scheduler barriers: a synchronization point used only for conformance-mode deterministic simulation (rt_conformance::harness --deterministic-sim), never on the hot path in production mode.
  10. Add runtime diagnostics: per-core utilization, queue depth, and migration-rate metrics.

17.3 Deliverable

A runnable multicore dispatch runtime supporting both RMS and EDF policies across an operator-specified core count and affinity configuration, runnable via rt_cli run --policy {rms,edf} --cores 8 <workload>, with per-core run-queue isolation verified under conformance/runtime/*.

17.4 Acceptance Criteria

  • conformance/runtime/affinity.yaml shows zero affinity_violation_total (I7) across a 10,000- dispatch synthetic run spanning 8 cores.
  • conformance/runtime/preemption.yaml shows preemption delivery within ≤ 25 µs p99 (§4) across the same run.
  • Migration rate stays below a documented budget (≤ 2% of dispatch decisions) for the reference workload at ≤ 8 cores, confirming migration is the exception, not the default path.

17.5 Conformance Fixtures

  • conformance/runtime/preemption.yaml — verifies preemption-delivery timing per core; malformed variant injects a preemption request for a TaskId not currently running anywhere.
  • conformance/runtime/affinity.yaml — verifies CPU pinning is never violated even under forced migration pressure; regression variant replays a captured cross-core race from a prior failure.

17.6 Pitfalls

  1. Lost wakeups when a timer fires between a worker checking its queue and parking — root cause: a classic check-then-park race; debugging method: rt_conformance::harness --deterministic-sim interleaving exploration around 17.2 step 7; recovery: use a wake primitive with a sequence-number guard (park only if the sequence hasn't advanced since the check).
  2. Affinity violations under migration-hook bugs — root cause: migration target selection not re-validating the mask after a concurrent affinity-mask change (rare, but declared mutable at the rt_cli layer pre-admission); recovery: re-check the mask atomically at the point of migration, not just at selection time.
  3. Migration races where a task appears briefly in two per-core queues simultaneously — root cause: a non-atomic remove-then-insert across queues; debugging method: cross-core queue-membership invariant check in --deterministic-sim; recovery: hold both queues' locks (in a fixed core-index order to avoid deadlock) for the duration of a migration.
  4. Scheduler-lock contention on the shared portions of the dispatch state under high core counts — debugging method: lock_hold_us_p99 (I10) broken out per core; recovery: shard remaining shared state (e.g., global admission registry) separately from per-core hot-path state.
  5. Preemption storms: a high-frequency task's every release forces a preemption on a core running many lower-priority tasks — debugging method: preemption-frequency metric correlated with task period; recovery: this is often a legitimate RMS consequence (P1), not a bug — but flag it in starvation diagnostics (15.2 step 8) if lower-priority tasks trend toward their own deadlines.

17.7 Performance Concerns

Critical metrics: dispatch latency, wakeup latency, migration frequency, and cache-invalidation penalties from cross-core task movement. Per-core run queues (17.2 step 2) are the primary lever for keeping the §4 per-core cache working-set budget (≤ 256 KB) intact — a shared global queue would thrash every core's cache on every dispatch decision. NUMA cross-node access penalty (§4, ≤ 120 ns assumed) is budgeted but not actively mitigated here — full NUMA-aware placement is deferred (PhaseDeferred("§17"), tracked in §35).

17.8 Edge Cases

  • A core going offline (hot-unplug or CI runner throttling) mid-run — affected tasks must migrate within their affinity mask or be flagged infeasible, never silently dropped.
  • Affinity masks that name a core index beyond the detected core count.
  • A migration decision racing a concurrent admission of a new task onto the same target core.
  • Clock skew between cores' local Instant readings (mitigated by 13's single monotonic clock source shared across cores, but re-verified here under real multicore hardware).

17.9 Failure Analysis

A dispatch-layer failure's blast radius scales with core count: a single stuck core affects only its own affinity-bound tasks (contained by I7) unless the shared admission-registry lock (17.6.4) is itself the bottleneck, in which case the blast radius is system-wide. Detection: per-core utilization and queue- depth metrics (17.2 step 10) plus lock_hold_us_p99. Containment: per-core isolation by design; manual recovery: rt_cli diagnose --core N dumps the stuck core's run-queue and lock-holder state.

17.10 Operational Notes

Metrics: dispatch_latency_us, migration_total, affinity_violation_total, core_utilization_pct. Tracing spans: dispatch.select, dispatch.preempt, dispatch.migrate. Log fields: cpu_id, task_id, from_cpu, to_cpu (migration only). Deployment: core-count and affinity configuration are operator-supplied at rt_cli invocation, not compiled in. Rollback: safe, stateless. Compatibility: CpuMask (§11) is the compatibility surface for affinity configuration.

18. Phase 6 — Synchronization & Priority Inheritance

18.1 Objectives

Deliver bounded-blocking synchronization primitives implementing the priority-inheritance protocol, and fold the resulting blocking bound back into admission control (closing the loop opened in 15.2 step 6 and 16.8's edge case). Scope: rt_sync::mutex, rt_sync::semaphore, rt_sync::pi, rt_sync::deadlock. Constraint introduced: every lock acquisition/release crosses the rt_sync API — no scheduler or runtime crate is permitted its own ad hoc locking primitive (P4, P9).

18.2 Detailed Implementation Steps

  1. Implement rt_sync::mutex: a priority-inheritance mutex per Sha, Rajkumar, Lehoczky (1990, §5 Papers) — on contention, the lock holder's effective priority is raised to the highest priority of any task blocked on it, restored on release.
  2. Implement lock-ownership tracking: every held lock records its owner TaskId and current effective- priority boost, exposed for deadlock diagnostics (18.2 step 5).
  3. Implement recursive/nested inheritance per the Stack Resource Policy structure (Baker 1991, §5 Papers): a task holding multiple nested locks propagates the highest blocked priority across the full nesting chain, not just the innermost lock.
  4. Implement rt_sync::semaphore with the same inheritance discipline as the mutex, generalized to N permits.
  5. Implement deadlock diagnostics in rt_sync::deadlock: cycle detection over the lock-ownership graph, run continuously in a background diagnostic thread (never on the hot path, per P10 — diagnostics must not themselves cost dispatch latency).
  6. Implement blocking analysis: compute, per task, the maximum blocking term B it can experience from lower-priority lock holders — this is the value 15.2 step 6 and 16.8 consume for blocking-aware admission (I6).
  7. Add timeout support on lock acquisition, with priority correctly un-inherited on timeout (Pitfall 18.6.5 below covers what happens when this is done wrong).
  8. Add tracing hooks: LockAcquired/LockReleased trace events (§11) tagged with the current effective priority, not just the base priority.
  9. Add inversion benchmarks quantifying inheritance overhead against the uncontended fast path.
  10. Wire the computed blocking bound B back into rt_rms::admission and rt_edf::admission (retroactively closing 15.2 step 6 and the 16.8 edge case within this same blueprint, not deferred).

18.3 Deliverable

A rt_sync crate providing priority-inheritance mutexes and semaphores with a provable, measured blocking bound fed into admission control end-to-end, runnable and observable via conformance/pi/* and the inversion benchmarks in rt_bench.

18.4 Acceptance Criteria

  • conformance/pi/basic_inversion.yaml shows measured blocking duration ≤ the admission-computed bound B in 100% of 1,000 synthetic inversion scenarios (I6).
  • conformance/pi/nested.yaml shows correct priority propagation across ≥ 3 levels of nested lock acquisition with zero orphaned inherited priorities (18.6.2).
  • Uncontended lock acquisition overhead ≤ 200 ns (fast-path cost budget informing §32's wakeup-latency chain, C4).

18.5 Conformance Fixtures

  • conformance/pi/basic_inversion.yaml — validates single-level priority inheritance restores the correct priority on release; malformed variant releases a lock the calling task never held.
  • conformance/pi/nested.yaml — validates chained inheritance across nested locks; regression variant replays a captured orphaned-priority incident to confirm the fix holds.

18.6 Pitfalls

  1. Priority rollback failures on release — root cause: restoring to the original base priority instead of the next-highest priority still justified by a remaining held lock; debugging method: priority-trace diff across a multi-lock release sequence; recovery: recompute effective priority from the full remaining lock-ownership set on every release, never a single stored "previous" value.
  2. Orphaned inherited priorities surviving past the releasing task's last relevant lock — same root cause as 18.6.1, called out separately because it is the most common manifestation in the nested case (18.2 step 3); signal: a task's effective priority staying elevated with zero held locks.
  3. Deadlock cycles from inconsistent lock-acquisition ordering across two tasks — root cause: no canonical lock-ordering discipline enforced; debugging method: rt_sync::deadlock's cycle detector (18.2 step 5); recovery: either enforce a documented lock-acquisition order or use a try-lock-with- backoff protocol.
  4. Recursive lock corruption when a task attempts to re-acquire a mutex it already holds without using an explicit reentrant primitive — recovery: rt_sync::mutex is deliberately non-reentrant; provide a separate, clearly-named reentrant variant rather than silently allowing self-deadlock-avoidance hacks.
  5. Timeout-cleanup races: a lock acquisition timing out at the same instant the lock becomes available — root cause: the timeout path and the wake path both racing to claim the lock; debugging method: --deterministic-sim interleaving exploration around the timeout/wake boundary; recovery: a single atomic "claim" operation that both paths contend on, with only one succeeding.

18.7 Performance Concerns

The inheritance bookkeeping (owner tracking, priority propagation) adds cost to every lock acquisition proportional to the current nesting depth — bounded in practice by the Stack Resource Policy discipline (18.2 step 3), which caps nesting depth per task by design. Deadlock-cycle detection runs on a background thread specifically to keep this cost off the P10-measured hot path. Fast-path (uncontended) acquisition must stay within the 200 ns budget (18.4) or it dominates the wakeup-latency chain in §32 C4.

18.8 Edge Cases

  • A task timing out on a lock acquisition it would have received one tick later (must still un-inherit correctly for whoever it was boosting).
  • Two tasks attempting to acquire the same two locks in opposite order (the canonical deadlock case; must be detected, not just avoided by luck in testing).
  • A lock holder completing (task lifecycle → Completed) while still holding a lock (programming error in the workload, not the scheduler; must be diagnosable, not a silent leak).
  • Semaphore permit exhaustion under a burst of simultaneous acquisitions exceeding N.

18.9 Failure Analysis

Synchronization failures manifest as runaway latency, scheduler stalls, starvation, or high-priority tasks blocked far longer than their admission-computed bound. Detection: pi_blocking_overrun_total (I6) and the deadlock-cycle detector's alert. Blast radius: bounded to the tasks sharing the specific contended resource, unless a deadlock cycle spans the scheduler's own internal locks, in which case it is system-wide. Recovery: watchdog-triggered forced-unlock diagnostics dump the full lock-ownership graph; the configurable panic policy (ADR-appropriate for a research/benchmark harness) aborts the run rather than limping forward silently (P12).

18.10 Operational Notes

Metrics: pi_blocking_overrun_total, lock_hold_us_p99, deadlock_cycles_detected_total, lock_acquire_latency_ns. Tracing spans: sync.acquire, sync.release, sync.inherit. Log fields: lock_id, owner_task_id, effective_priority, blocked_task_id. Deployment: none. Rollback: safe, stateless. Compatibility: the blocking-bound B computation is part of the admission-control contract (§11 AdmissionError::BlockingBoundExceeded) and must not silently change its units or scale.

19. Phase 7 — Tracing & Telemetry

19.1 Objectives

Build the full observability pipeline every earlier phase's trace events have been feeding into provisionally. Scope: rt_trace::event, rt_trace::buffer, rt_trace::histogram, rt_trace::export, rt_trace::chrome_trace. Constraint introduced: tracing overhead itself must be measured and stay under the §4/§28 5% budget — untraceable tracing overhead is a P6/P2 contradiction.

19.2 Detailed Implementation Steps

  1. Build the trace-event pipeline: a lock-free MPSC ring buffer (rt_trace::buffer) that every subsystem writes TraceEvents (§11) into, sized per the §32 C3 sustained-throughput calculation.
  2. Add binary event buffers using bincode (ADR-05) for the in-process wire format, chosen specifically for write-side speed since this is on the P6 hot path.
  3. Implement histogram generation in rt_trace::histogram following Brendan Gregg's log-linear bucket methodology (Systems Performance, 2020 — §5 Books) for wakeup latency, dispatch latency, and jitter.
  4. Add Chrome Trace Event JSON export (ADR-10) in rt_trace::chrome_trace, batched per the §32 C3 amplification budget (≤ 3×).
  5. Add scheduler-timeline rendering: per-core, per-task Gantt-style views derived from the exported trace, consumed by chrome://tracing or Perfetto with no custom viewer needed.
  6. Add missed-deadline alerts: a dedicated low-latency path (bypassing the batched export) that surfaces DeadlineMissed events within one dispatch tick (I12), satisfying P12's fail-loudly requirement.
  7. Add runtime dashboards: a Prometheus /metrics endpoint (ADR-11) exposing the histograms and counters accumulated across §12–§18.
  8. Add queue metrics: heap depth, re-heapify latency, migration rate — surfaced per-core.
  9. Add wakeup metrics: the full latency-chain breakdown from §32 C4, exported per-component (timerfd read, lock acquire, select_next, wake syscall) so a regression can be attributed to a specific stage.
  10. Add benchmark summaries: a structured result file (embedding the workload hash and toolchain version per P11) consumed by rt_bench and CI's benchmark.yml gate.

19.3 Deliverable

A complete observability stack: every scheduling decision from Phases 3–6 emits a trace event, every event is exportable as Chrome-trace JSON, every latency claim in this document is reproducible from a recorded trace, and tracing's own overhead is measured against the 5% budget it must respect.

19.4 Acceptance Criteria

  • Tracing overhead ≤ 5% of total runtime under the Phase 8 benchmark workload (§4, §28 M9), measured with tracing on vs. off.
  • conformance/trace/event_order.yaml shows zero out-of-order events (I8) across a 100,000-event run.
  • trace_dropped_events_total (I14) stays at 0 under the sustained 200,000 events/s load modeled in §32 C3; if the buffer would overflow, sampling engages visibly rather than dropping silently.

19.5 Conformance Fixtures

  • conformance/trace/event_order.yaml — ensures deterministic per-CPU event ordering (I8); malformed variant injects a timestamp regression to confirm it is caught, not silently accepted.
  • conformance/trace/histograms.yaml — ensures stable, reproducible histogram bucket boundaries across repeated runs of the same recorded input (P11).

19.6 Pitfalls

  1. Trace-induced latency perturbing the very system it measures (the observer effect, foreshadowing §26/§20) — root cause: synchronous export on the hot path; debugging method: A/B benchmark with tracing fully disabled; recovery: keep the ring-buffer write on the hot path lock-free and defer all formatting/export to a background thread.
  2. Buffer overflow under a trace-event burst exceeding the sized capacity (§32 C3) — root cause: underestimated sustained event rate; debugging method: trace_dropped_events_total (I14) trending up; recovery: widen the buffer or engage sampling, but always increment the visible drop counter first (never drop silently).
  3. Timestamp skew between the fast missed-deadline-alert path (19.2 step 6) and the batched export path producing two slightly different orderings of the same events; recovery: both paths read from the same monotonic clock source (Phase 1) and the same underlying event, never two independent captures.
  4. Event reordering during export batching — root cause: a parallel export worker pool reordering events across batches; recovery: partition export work by CPU, preserving per-CPU order (I8) even under parallel export.
  5. Lock contention in telemetry itself becoming a scheduler bottleneck — root cause: a naive mutex- guarded shared histogram instead of the lock-free ring buffer; debugging method: lock_hold_us_p99 attributed specifically to rt_trace call sites; recovery: per-core histogram shards, merged only at export time.

19.7 Performance Concerns

Target: tracing overhead <5% of runtime under benchmark load (§4, matching the M9 target in §28). Batching amplifies JSON export size ~3× over the raw binary event size (§32 C3) — this is intentional Chrome-trace-format overhead (ADR-10), not a bug, and is why export happens off the hot path in a dedicated background worker rather than inline.

19.8 Edge Cases

  • A trace event for a task that completed and was subsequently garbage-collected from rt_core's registry before export ran (the event itself must remain valid — trace events own their data, not a reference into the task registry).
  • Export running concurrently with a process shutdown (must flush within the §4 200 ms shutdown budget, not block indefinitely).
  • A histogram bucket boundary edge case (a latency value exactly on a bucket boundary — must be deterministic, documented rounding).
  • Clock resolution coarser than the event rate on some platforms (must degrade to coarser but still monotonic ordering, never non-monotonic).

19.9 Failure Analysis

A tracing-pipeline failure's most dangerous form is silent: an operator believing the system is observed when it is not (violating P6). Detection: the drop counter (I14) and a periodic self-check trace event that must itself appear in every export batch — its absence is the alarm. Blast radius: observability-only; scheduling correctness is unaffected by a tracing failure (tracing is deliberately off the correctness-critical path), but incident diagnosis capability is lost. Recovery: restart the export pipeline; postmortem requires the self-check event's last-seen timestamp to bound the blind spot.

19.10 Operational Notes

Metrics: trace_dropped_events_total, trace_export_latency_ms, trace_overhead_pct. Tracing spans: trace.emit, trace.export, trace.flush. Log fields: event_kind, cpu_id, batch_id. Deployment: Prometheus endpoint exposed on a local-only port by default (ADR-06). Rollback: safe, stateless. Compatibility: the Chrome-trace JSON schema (ADR-10) is versioned; consumers should not assume field stability across a major version bump (§25).

20. Phase 8 — Conformance, Benchmarking & Replay

20.1 Objectives

Build the deterministic replay harness and the benchmark suite that validate every claim made in §4/§28 under realistic, reproducible load — and control for the observer effect (19.6.1) rigorously enough that the resulting numbers survive scrutiny (P11, the authors'-review-test standard from §8 of the brief). Scope: rt_conformance::harness, rt_conformance::fixtures, rt_conformance::replay, rt_bench::overload, rt_bench::jitter, rt_bench::stress.

20.2 Detailed Implementation Steps

  1. Build the deterministic replay harness (rt_conformance::harness --deterministic-sim, referenced throughout §15–§19) using a fixed logical clock and single-threaded interleaving control, per the seL4 verification-discipline precedent (§5 Reference Implementations) adapted for conformance rather than formal proof.
  2. Add synthetic workload generators producing task sets spanning the RMS/EDF admission boundary (utilization near the bound), used across §15/§16's fixtures.
  3. Add overload scenarios (rt_bench::overload): task sets deliberately exceeding U > 1.0 to exercise 16.9's domino-effect diagnostics and 15.9's cascading-jitter detection.
  4. Add cache-stress workloads (benchmarks/cache_thrash.rs) that deliberately thrash the per-core cache working set (§4 budget) to validate the dispatch layer's cache-locality assumptions under adversarial conditions.
  5. Add mixed-criticality test scenarios combining Safety/High/Low criticality tasks (§11) to exercise the criticality-aware shedding built in Phase 9 (§21) before it exists here as a forward- looking fixture, and to validate current behavior in its absence.
  6. Add long-duration stability tests (benchmarks/migration_heavy.rs extended to a 24 h soak) to surface the timer-drift accumulation class of bug (13.6.2) that only manifests over time.
  7. Add a regression benchmark suite: every criterion benchmark records its result keyed by workload hash + toolchain version (P11), diffed automatically against the last release baseline.
  8. Add CI benchmark gates in benchmark.yml: a merge blocks if p99 latency regresses beyond a documented tolerance (5%) against the baseline, run on dedicated (non-shared) hardware (per Pitfall 12.6.4).
  9. Add percentile latency metrics (p50/p90/p99/p999) computed from the histograms built in §19, not re-measured ad hoc per benchmark.
  10. Add flamegraph automation (perf record + perf script → flamegraph, ADR-16) wired into Makefile bench-profile for investigating a benchmark regression's root cause.

20.3 Deliverable

A production-grade validation and benchmark framework: rt_conformance deterministically replays any recorded scenario byte-for-byte, and rt_bench produces p50/p99/p999 latency numbers with observer- effect controls (20.6) documented and applied, sufficient to defend every number in §4/§28/§32 under scrutiny.

20.4 Acceptance Criteria

  • conformance/benchmarks/overload.yaml and conformance/benchmarks/jitter.yaml both pass with results within 10% of the §28 targets table (M1–M10) on the reference 8-core benchmark host.
  • Deterministic replay reproduces byte-identical trace output across 10 consecutive runs of the same recorded scenario (P11, I13).
  • CI benchmark gate correctly blocks a deliberately-introduced 8% p99 regression in a canary PR (a standing regression test on the gate itself).

20.5 Conformance Fixtures

  • conformance/benchmarks/overload.yaml — measures overload behavior (domino effect, cascading jitter) against documented thresholds; malformed variant supplies a task set that should be rejected at admission, confirming the benchmark harness itself does not silently proceed past a rejection.
  • conformance/benchmarks/jitter.yaml — measures wakeup-latency variance under sustained load; regression variant replays the exact captured scenario from any prior CI-gate-triggering PR.

20.6 Pitfalls

  1. Benchmark observer effect: the act of measuring (extra tracing, extra syscalls) perturbing the measured latency — root cause identical to 19.6.1, restated here as a benchmarking-methodology concern; recovery: always report tracing-on and tracing-off numbers side by side (20.4).
  2. Thermal throttling mid-benchmark skewing later samples relative to earlier ones — debugging method: correlate p99 trend against /sys/class/thermal readings if available; recovery: discard the run, re-run after a cooldown window, document ambient conditions in the result file.
  3. CPU frequency scaling (turbo boost ramping, powersave governors) introducing non-stationarity into a single benchmark run — recovery: pin CPU governor to performance for benchmark runs specifically (documented as a benchmark-only exception, never a production recommendation).
  4. NUMA interference on multi-socket hosts producing bimodal latency distributions that a simple average/p99 hides — debugging method: split histograms by NUMA node; recovery: document per-node results separately until NUMA-aware placement (deferred, §35) exists.
  5. Non-isolated test hosts (shared CI runners, cloud VMs with noisy neighbors) invalidating absolute latency numbers even while relative regression detection still works — recovery: absolute §4/§28 numbers are validated only on dedicated hardware (per 20.2 step 8); CI gates use relative regression thresholds instead of absolute pass/fail.

20.7 Performance Concerns

The benchmark harness's own overhead must be smaller than the effect it is trying to measure — a benchmark that adds 10 µs of overhead cannot credibly validate a 15 µs wakeup-latency budget (§4). This motivates the tracing-on/tracing-off comparison (20.6.1) as a standing methodology, not a one-time check.

20.8 Edge Cases

  • A benchmark run interrupted mid-scenario (process kill, OOM) — must leave a partial-result file marked incomplete, never a silently truncated "successful" result.
  • Replay of a scenario recorded on a different core count than the replay host — must fail loudly with a specific error, not silently reinterpret the affinity masks.
  • A regression baseline missing for a newly-added benchmark — CI gate must treat "no baseline" as "record baseline, do not gate," never as "pass trivially."

20.9 Failure Analysis

A benchmarking-methodology failure (an unmeasured observer effect, an un-isolated host) manifests as numbers in this document that do not survive independent reproduction — the single worst outcome for a specification whose entire premise is measured, not asserted, correctness. Detection: the tracing-on/ tracing-off delta (20.6.1) exceeding expectations is itself the signal. Recovery: retract and re-derive any §4/§28/§32 number traced back to an unisolated or unmeasured-overhead benchmark run.

20.10 Operational Notes

Metrics: benchmark_p50_us, benchmark_p99_us, benchmark_p999_us, benchmark_regression_pct. Tracing spans: bench.run, bench.replay. Log fields: workload_hash, toolchain_version, core_count, host_class. Deployment: benchmark gate runs on dedicated hardware, separate from correctness CI (12.6.4). Rollback: safe. Compatibility: result-file schema is versioned alongside WorkloadSpec::schema_version (§11, §25).

21. Phase 9 — Overload Governance & Release Hardening

21.1 Objectives

Close the overload gaps surfaced in Phases 3–4 (15.9's cascading jitter, 16.9's domino effect) with explicit criticality-aware governance, and harden the system for a tagged release. Scope: extends rt_rms/rt_edf admission with criticality-aware shedding, extends rt_cli with an overload- governance command surface, and finalizes the release/versioning contract (§25, §27). Constraint introduced: under detected overload, degradation must be criticality-ordered and traced — an undifferentiated "drop the newest task" policy is explicitly rejected (P12).

21.2 Detailed Implementation Steps

  1. Implement overload detection: a rolling window of consecutive MissedDeadline events per criticality class, feeding the per-scheduler diagnostics in 15.2 step 8 and 16.2 step 5.
  2. Implement criticality-aware shedding: reject/suspend Low first, then Medium, never Safety except via explicit renegotiation — ordering follows Criticality's enum ordinal (§11).
  3. Implement admission-time headroom margins: reject a feasible set with zero slack above the RTA/EDF bound (Lehoczky, Sha, Ding 1989; Baruah, Mok, Rosier 1990 — §5 Papers), per P1.
  4. Add an rt_cli overload status/shed command surface exposing current state and manual override.
  5. Finalize the compatibility contract (§25): WorkloadSpec::schema_version (§11) and the Chrome-trace schema version (ADR-10) both lock for this release.
  6. Finalize release engineering (§27): signed releases (ADR-19) gated on the soak test (20.2 step 6) and the benchmark regression gate (20.2 step 8).
  7. Add release-candidate hardening fixtures: re-run conformance/ plus conformance/overload/* against the release-candidate binary, not just development builds.
  8. Document the NUMA, partitioned/global EDF, CBS/sporadic-server, mixed-criticality, and distributed- orchestration deferrals (§35) as the Phase 1+ continuation, closing this blueprint's scope (§1).
  9. Add a final security pass: re-run §22's mitigations against the release-candidate binary, including the workload-parser fuzz corpus (ADR-14) at an extended iteration count.
  10. Tag the release; publish §28's benchmark numbers and §32's capacity model as the citable baseline.

21.3 Deliverable

A release-candidate binary with criticality-aware overload governance, a locked compatibility contract, a signed release pipeline, and a full-suite conformance + soak-test + fuzz pass, runnable end-to-end via rt_cli run --policy {rms,edf} --cores N --overload-governance on <workload>.

21.4 Acceptance Criteria

  • conformance/overload/criticality_shed.yaml shows Safety-class tasks retain 100% admission-time guarantees across all 50 generated overload scenarios; Low-class tasks are shed first in 100% of cases where shedding is required.
  • conformance/overload/admission_reject.yaml shows zero-slack-margin task sets are rejected at admission in 100% of a 200-case generated corpus (21.2 step 3).
  • Release-candidate soak test (24 h) shows zero I1–I14 invariant violations and timer drift ≤ 1 µs/hour (tightening 13.4's per-run budget into a long-run one).

21.5 Conformance Fixtures

  • conformance/overload/admission_reject.yaml — verifies zero-slack-margin rejection at admission; malformed variant supplies a task set that is infeasible outright (not just zero-slack) to confirm the existing I1 rejection path still fires correctly alongside the new margin check.
  • conformance/overload/criticality_shed.yaml — verifies shedding order strictly follows the Criticality ordinal; regression variant replays a captured overload incident from Phase 3/4 benchmarking (20.6) to confirm governance now contains it.

21.6 Pitfalls

  1. Shedding the wrong task under a criticality tie (two Low-criticality tasks, which to shed first) — recovery: fall back to the same declaration-order tie-break used everywhere else (I13-consistent), never an ad hoc heuristic introduced just for this phase.
  2. Headroom-margin rejection being too conservative, rejecting task sets that would have run fine in practice — root cause: a fixed margin constant instead of one derived from measured WCET variance; debugging method: compare margin-rejected sets against their actual measured behavior in rt_bench::overload; recovery: derive the margin from the §32-documented arithmetic, not a guess.
  3. A criticality renegotiation for Safety-class tasks (21.2 step 2) being invoked silently rather than through the explicit, audited rt_cli overload command surface — recovery: Safety-class admission changes must always appear as a distinct trace event and CLI-invocation log entry, never as a side effect of another operation.
  4. A release-candidate soak test passing on a lightly-loaded benchmark host but failing on a representative host class — root cause: the same non-isolated-host pitfall as 20.6.5, now with higher stakes (a release gate, not a dev-loop benchmark); recovery: soak tests run exclusively on the dedicated hardware class from 20.2 step 8.
  5. Fuzz-corpus regressions reintroduced by a last-minute change bypassing the extended fuzz pass (21.2 step 9) — recovery: the release pipeline (§27) blocks tagging until the extended-iteration fuzz run completes clean, with no manual override path.

21.7 Performance Concerns

Overload detection and criticality-aware shedding must themselves stay off the correctness-critical dispatch hot path — the rolling-window detector (21.2 step 1) runs at trace-export cadence (§19), not per-dispatch-tick, to avoid becoming the kind of self-inflicted latency 19.6.1 warns about. Headroom- margin checking adds a fixed, small constant-factor cost to admission (already O(n²) per §32 C6) — budgeted, not re-derived, from the existing admission cost model.

21.8 Edge Cases

  • Overload detected simultaneously across multiple criticality classes (must shed strictly in ordinal order, not proportionally across classes).
  • A shed task later becoming schedulable again as load drops — must re-admit through the full admission path (I1), never silently resume from where it was shed.
  • A release-candidate soak test that itself hits the 24 h duration exactly at a daylight-saving-style host clock event — irrelevant given monotonic-only time (P7), documented here explicitly as a "why this cannot happen" note rather than a live risk.
  • A fuzz-discovered crash in the workload parser specifically at the schema-version boundary (WorkloadSpec::schema_version, §11) between two supported versions.

21.9 Failure Analysis

A governance failure — shedding the wrong class, or failing to shed at all — has a blast radius determined entirely by which criticality class is affected: a Low-class over-shed is a capacity loss; a Safety-class under-protection is the single worst failure this entire blueprint exists to prevent. Detection: criticality_shed_total{class} and the invariant-violation channel (I1–I14) already wired through every prior phase. Containment: the ordinal-ordered design (21.2 step 2) makes a Safety-class impact require multiple simultaneous defects (detection failure and ordering failure) rather than one. Recovery: postmortem requires the full trace from the overload-detection event through every shedding decision, not just the final state.

21.10 Operational Notes

Metrics: overload_detected_total{class}, criticality_shed_total{class}, admission_margin_rejected_total. Tracing spans: overload.detect, overload.shed, overload.renegotiate. Log fields: criticality_class, shed_task_id, margin_us. Deployment: --overload-governance on|off is an explicit rt_cli flag, defaulting to on for any release-tagged binary (21.2 step 6). Rollback: reverting to a prior signed release is the rollback path — there is no in-place migration of governance state since none is persisted (ADR-04). Compatibility: this phase is the last to touch the WorkloadSpec/trace schema before the version lock (21.2 step 5); no further schema changes are permitted without a major version bump (§25).

24. Operational Readiness

Runbooks. docs/runbooks/deadline_miss.md, docs/runbooks/priority_inversion.md, and docs/runbooks/timer_drift.md map directly onto FM-1, FM-6, and FM-4 respectively; each runbook opens with the exact metric/telemetry name from §23's table so an on-call operator can jump straight from an alert to the runbook without a translation step.

Dashboards. The Prometheus endpoint stood up in §19 feeds a small dashboard set: (1) per-criticality deadline-miss rate, (2) p50/p99/p999 wakeup and dispatch latency against the §28 targets table, (3) per-core utilization and migration rate, (4) admission accept/reject rate with rejection-reason breakdown. No dashboard exists that is not backed by a named metric in §19.10/§21.10 — an unnamed panel is treated as a documentation bug.

Deployment checklist. Before any release-tagged binary runs against a real workload: (1) confirm --overload-governance on (§21.10 default), (2) confirm the target host's core count and NUMA topology match the admitted workload's affinity assumptions (§4, §29), (3) confirm the dedicated benchmark baseline (§20) was captured on comparable hardware, (4) confirm docs/threat-model.md (§22) has been reviewed for the specific deployment's trust boundary.

Capacity planning. Operators size a deployment from §32's capacity model directly: task count and core count feed C1/C2/C7 for memory, C6 for admission-time budget, and C11 for the achievable jitter ceiling relative to the fastest task period in the workload. A capacity plan that does not cite a C# row is treated as a guess, not a plan (mirroring P10's discipline for performance changes).

Rollback and disaster recovery. Because the system is stateless between runs (ADR-04, I13's idempotent-admission property), rollback is simply re-deploying the prior signed release (ADR-19) — there is no data migration step. RTO is bounded by process-restart-plus-replay time (§4, ≤30 s); RPO is 0 by design, since nothing durable exists to lose.

On-call escalation. MissedDeadline events for Safety-criticality tasks (§11, §21) page immediately, no batching; Low-criticality misses roll up into the standard dashboard review cadence. This escalation asymmetry is the operational expression of the ordinal-shedding design decision in §21.2.

25. Compatibility & Versioning

Crate versioning. All ten crates (§10) follow SemVer independently but are released in lockstep for Phase 0–9 (a single workspace version tag, ADR-19) — cross-crate compatibility within one release is guaranteed by construction (the workspace-unified Cargo.lock, ADR-20), not by a separate compatibility test suite.

Workload schema. WorkloadSpec::schema_version (§11) is the compatibility gate for the on-disk workload format. A parser accepts its own version and the immediately prior one; anything older requires an explicit migration pass (there is currently no migration tool — schema changes are additive-only through Phase 9, per §21.2 step 5's version lock).

Trace schema. The Chrome Trace Event JSON schema (ADR-10) is versioned separately from the workload schema, since trace consumers (external tools like chrome://tracing/Perfetto) evolve on a different cadence than internal workload authors. TraceEventKind (§11) is append-only for the same reason TaskState is append-only (§11) — existing ordinals are load-bearing for external consumers who may have pinned to specific integer values.

Deprecation policy. No field or enum variant is removed within Phase 0–9; deprecation is a documentation-only "do not use" annotation with a stated removal target beyond this blueprint's scope (tracked alongside §35's deferrals where relevant, e.g. a future CpuMaskV2 per §11's 64-core ceiling note).

API stability. The Scheduler trait (§11) is frozen for the duration of Phase 0–9 specifically because it is the Policy-Isolation boundary (P5) — a signature change here would ripple through both rt_rms and rt_edf simultaneously, which is exactly the coupling P5 exists to prevent.

26. Testing & Verification Strategy

Unit and integration tests. cargo-nextest (ADR-13) runs per-crate unit tests plus cross-crate integration tests in crates/*/tests/, parallelized for wall-time reasons documented in ADR-13's rationale.

Conformance fixtures. Every phase (§12–§21) ships named fixtures under conformance/ (§10, §37) covering the happy path, a malformed-input variant, and — where a prior incident exists — a replay variant that pins the exact failing interleaving as a permanent regression guard (P11).

Deterministic simulation. rt_conformance::harness --deterministic-sim (introduced §12, used throughout §15–§21) replaces rt_clock's wall time with a controlled logical clock and explores interleavings deliberately, per the debugging methodology closing §7. This is the primary tool for reproducing races (lost wakeups §17.6, deadlocks §18.6, queue corruption §15.6/§16.6) that are otherwise timing-dependent and non-reproducible.

Property-based / adversarial fixtures. The validation pipeline (§14) and admission controllers (§15, §16) are exercised with generated adversarial TaskSpec corpora (§14.6.2) rather than only hand-written examples, specifically to catch the class of bug a hand-written test suite systematically misses (edge-of-boundary utilization values, extreme periods).

Fuzzing. cargo-fuzz (ADR-14) targets the workload parser and the trace-wire decoder (fuzz/fuzz_targets/, §10), run continuously in CI (fuzz.yml) and at an extended iteration count as a release gate (§21.2 step 9).

Benchmark regression. rt_bench (§20) plus the CI benchmark.yml gate gives every performance claim in §4/§28 a standing regression test, on dedicated (non-shared) hardware per the Pitfall in §12.6.4 and §20.6.5.

Soak testing. A 24 h stability run (§20.2 step 6, tightened into a release gate at §21.4) is the only test class long enough to surface slow-accumulating bugs like timer drift (§13.6.2) that unit and conformance tests structurally cannot catch.

What this blueprint does not do. Formal verification (seL4-style machine-checked proofs, §5 Reference Implementations) is explicitly out of scope and registered as a deferral (PhaseDeferred("§20"), §35) — conformance and deterministic simulation give strong confidence, not a proof. Any reviewer applying the authors'-review-test standard (would the seL4 or Tokio maintainers let this line stand) should read every claim in this document as "measured to this confidence level," never as "proven."

27. Build & Release Engineering

CI pipeline. .github/workflows/ci.yml runs build + cargo-nextest + clippy -D warnings on every PR (ADR-15); fuzz.yml runs the continuous fuzz corpus; benchmark.yml runs the regression gate on dedicated hardware (§20.2 step 8); release.yml triggers only on a signed tag (ADR-19).

Release process. A release is: (1) the full conformance/ suite green, (2) the 24 h soak test green (§21.4), (3) the extended fuzz pass clean (§21.2 step 9), (4) the benchmark regression gate green against the prior release baseline, (5) a signed, changelog-generated tag. No manual override skips any of the four gates (§21.6.5).

Reproducible builds. rust-toolchain.toml pins the exact compiler version; Cargo.lock is checked in and never .gitignored; benchmark results embed the toolchain version (P11) so a numeric claim is always attributable to a specific, reproducible build.

Packaging. rt_core/rt_rms/rt_edf/rt_sync/rt_runtime/rt_trace are published as library crates (ADR-16) for embedding; rt_cli is additionally built as a standalone release binary attached to the GitHub release artifact.

Containers. The Dockerfile/docker-compose.yml dev environment (ADR-17) pins the same toolchain version as CI, so "works in the dev container" and "works in CI" are the same claim, not two.

29. Scalability Analysis

Bottlenecks. In descending order of first-encountered severity: (1) the shared admission-registry lock (§17.6.4) once core count grows past the point where per-core run queues alone no longer eliminate contention; (2) the timer heap/wheel crossover (§13.7) under high timer density; (3) trace-buffer synchronization (§19.7) if per-core histogram sharding (§19.6.5) is skipped; (4) migration coordination (§17.6.3) under sustained cross-core load imbalance.

Vertical scaling. Lock reduction (sharding the admission registry, per-core histograms), cache locality (per-core run queues, §17.2 step 2, keeping the §4 256 KB working-set budget intact), and NUMA awareness (currently budgeted but not actively mitigated, §4, deferred PhaseDeferred("§17")) are the three levers, in the order they pay off.

Horizontal scaling. Beyond the §4/§17 32-core linear-scaling ceiling, a single global scheduler instance (even with per-core queues) hits diminishing returns from the shared admission-registry lock; partitioned EDF (statically assign each task to one core's independent scheduler instance, PhaseDeferred("§16")) or global EDF (a single logical queue spanning all cores with active migration, PhaseDeferred("§17")) are the two documented paths beyond that ceiling, deferred here specifically because their tradeoffs (partitioning loses cross-core load balancing; global EDF pays migration overhead, §32 C10) require their own admission-theory treatment this blueprint does not attempt.

What does not scale by design. A single logical admission decision (§15/§16) is inherently sequential — it must see the full task set before deciding — and is not a target for horizontal scaling; it is instead kept fast enough (§4, §32 C6) that its sequential cost stays negligible relative to run duration.

30. Mental Models & First Principles

  • MM1 — Worst-Case-First Thinking. Optimize the tail, not the mean · predicts an "obvious" average- case win can regress p99 · the bug class you write without it: a latency regression hidden behind an improved mean · applies in §28.
  • MM2 — Admission Is a Proof, Not a Guess. Schedulability is a provable property at admission time, not an empirical hope · predicts a workload that "usually works" will eventually miss under exactly the interleaving the proof rules out · bug class: silent infeasibility discovered in production · applies in §15.
  • MM3 — Blocking Is Priority Debt. Every lock acquisition is a loan of priority that must be repaid within a bound · predicts unbounded loans (no PI) cause unbounded inversion · bug class: priority- rollback bugs, orphaned inheritance · applies in §18.
  • MM4 — Time Is Not a Side Effect, It Is the API. If a timing property isn't measured and exported, it doesn't exist operationally · predicts an unmeasured latency claim will eventually be wrong · bug class: "it felt slow" incidents with no data behind them · applies in §19.
  • MM5 — Determinism Enables Debugging, Not Just Correctness. A deterministic replay turns a Heisenbug into a reproducible one · predicts nondeterministic admission (I13) will resist all ad hoc debugging · bug class: unreproducible scheduler panics · applies in §20.
  • MM6 — Cascades Beat Isolated Failures. Dynamic-priority systems propagate one miss into many; fixed- priority systems isolate misses to lower-priority tasks by construction · predicts EDF needs explicit overload governance that RMS gets almost for free · bug class: unbounded blast radius under overload · applies in §21.
  • MM7 — Every Number Must Have Arithmetic Behind It. A capacity claim without a derivation is an assertion, not an engineering fact · predicts undocumented budgets drift silently out of sync with reality · bug class: budget numbers that quietly stop matching production · applies in §32.
  • MM8 — Reject at the Gate, Not Mid-Flight. Admission control is cheaper to get right than runtime recovery · predicts any system that defers rejection to runtime pays a correctness tax later · bug class: partial admission leaving inconsistent state · applies in §15.

32. Back-of-Envelope Capacity Model

  • C1 — Task metadata memory. TaskSpec (96 B) + TaskRuntimeState (80 B) = 176 B/task × 4096 tasks = 720,896 B ≈ 0.69 MB, inside the §4 256 MB ceiling.
  • C2 — Run-queue overhead. BinaryHeap<TaskId> entry ≈ 24 B × 512 tasks/core = 12,288 B ≈ 12 KB/core, inside the §4 256 KB per-core cache budget; × 32 cores = 393,216 B ≈ 384 KB system-wide.
  • C3 — Trace buffer sustained rate. TraceEvent 40 B × 200,000 events/s × 1 s window = 8,000,000 B ≈ 7.63 MB/s raw; × the §4 3× JSON amplification = 22.9 MB/s sustained chrome-trace export rate.
  • C4 — Wakeup latency budget. timerfd expiry read 2 µs + scheduler lock acquire 3 µs + select_next 4 µs + wake syscall 6 µs = 15 µs = the §4 wakeup p50 budget exactly.
  • C5 — Dispatch latency budget. run-queue pop 2 µs + affinity-mask check 1 µs + preemption-signal delivery 5 µs = 8 µs = the §4 dispatch p50 budget exactly.
  • C6 — Admission cost at 512 tasks. 512 tasks × 512 interference iterations × 55 ns/iteration = 14,417,920 ns ≈ 14.4 ms, inside the §4 15 ms admission budget.
  • C7 — Full-deployment memory. C1 (0.69 MB) + C2 (0.384 MB) + a fixed 64 MB trace-ring allocation = 65.1 MB, inside the §4 256 MB ceiling with ≈4× headroom for fragmentation and allocator overhead.
  • C8 — FD usage. 32 timerfd handles (1/core) + 1 trace-export socket + ≤16 log/metric files = 49 FDs, inside the §4 4096 FD budget by ≈84×.
  • C9 — Availability realized. 99.9%/24 h (§4) = 86.4 s allowed downtime/day; the §4 30 s RTO permits 2 full restart cycles inside that budget before breaching the SLA.
  • C10 — NUMA penalty amortization. 120 ns/cross-node access (§4, budgeted) × 8 worst-case cross-node accesses per dispatch decision = 960 ns ≈ 6% of the §4 15 µs wakeup budget.
  • C11 — Jitter budget vs. shortest period. 100 µs p99 jitter (§4) ÷ 5 ms shortest configured period = 2% relative-jitter ceiling for the reference sensor-class workload (§8.6).
  • C12 — Startup budget. crate init 50 ms + tracing subscriber bring-up 80 ms + timerfd arm at 2 ms/core × 32 cores = 64 ms + admission preflight 15 ms (C6) = 209 ms, inside the §4 500 ms startup ceiling with ≈58% headroom.

34. Alternative Architectures (Roads Not Taken)

Alt A — Global EDF Across All Cores

        ┌───────────────────────────────┐
        │   Single global deadline queue │
        └────────────┬────────────────────┘
             ┌────────┼────────┬─────────┐
             v        v        v         v
          Core0    Core1    Core2  ...  CoreN
        (migrates the globally-earliest-deadline task to whichever core is free)

Regime where it wins: workloads with highly variable per-task WCET where static per-core partitioning (this blueprint's §17 approach) would leave some cores idle while others are overloaded. Real system embodying it: Linux SCHED_DEADLINE's default (non-partitioned) mode. Why rejected here: migration cost (§32 C10) and the cache-locality loss it causes directly contradict the per-core working-set budget in §4; §17 chose per-core queues with bounded, exceptional migration specifically to keep that budget intact, accepting some theoretical schedulable-capacity loss (§29) in exchange.

Alt B — Cooperative (Async/Poll-Based) Task Scheduling

   ┌──────────────┐     poll()      ┌──────────────┐
   │ Task future A │ ───────────▶   │ Executor loop │
   └──────────────┘                 └──────┬────────┘
   ┌──────────────┐     poll()             │
   │ Task future B │ ◀──────────────────────┘
   └──────────────┘   (task yields voluntarily; no preemption)

Regime where it wins: I/O-bound throughput workloads where thousands of lightweight tasks share a small thread pool and average-case latency, not worst-case bound, is the metric that matters. Real system embodying it: Tokio. Why rejected here: cooperative scheduling requires every task to yield promptly and voluntarily; a single misbehaving or long-running task starves everything else with no scheduler-level recourse, which is precisely the failure mode Principle P1 and Invariant I5 exist to make structurally impossible.

Alt C — Kernel-Module Real-Time Scheduling Class

   ┌───────────────────────────────────────┐
   │  Linux kernel                          │
   │   ┌─────────────────────────────────┐ │
   │   │ Custom sched_class (kernel mod)  │ │
   │   └─────────────────────────────────┘ │
   └───────────────────────────────────────┘

Regime where it wins: when userspace wakeup-latency overhead (§32 C4's 15 µs chain) itself is the bottleneck and only true kernel-level preemption points can close the gap further — the domain kernel/sched/deadline.c already occupies. Real system embodying it: the Linux kernel's own SCHED_DEADLINE class. Why rejected here: §1 explicitly scopes this blueprint to userspace (a kernel module changes the language, tooling, verification burden, and audience entirely — see ADR-01's Rust-in-userspace rationale) and a kernel-level implementation is exactly the Phase 1+ continuation PhaseDeferred("§17") (userspace/kernel co-scheduling) tracks in §35, not a Phase 0–9 goal.

36. Glossary

  • WCET — worst-case execution time; the declared per-activation upper bound a task's runtime is admitted against.
  • Jitter — variance in actual wakeup or completion time relative to the scheduled instant.
  • Deadline — the latest instant by which a task's execution must complete.
  • RMS — Rate Monotonic Scheduling; static fixed-priority assignment by shortest period.
  • EDF — Earliest Deadline First; dynamic priority assignment by nearest absolute deadline.
  • PI — Priority Inheritance; a protocol bounding blocking duration under lock contention.
  • Admission Control — the pre-execution schedulability check gating whether a task set may run.
  • Preemption — interrupting a running task's execution to run a higher-priority/earlier-deadline one.
  • Tickless — an event-driven timing model with no fixed periodic hardware tick.
  • Affinity — the set of CPUs a task is permitted to execute on.
  • Context Switch — the act of transferring CPU execution from one task to another.
  • Starvation — indefinite delay of a task's execution caused by other tasks' priority or ordering.
  • Sporadic Task — a task with irregular activation obeying only a minimum inter-arrival time.
  • Periodic Task — a task activated at a fixed, regular interval.
  • Criticality — a task's declared importance class, used to order overload-shedding decisions.
  • Utilization Bound — the Liu & Layland sufficient-schedulability threshold for RMS.
  • Response-Time Analysis (RTA) — the exact fixed-point computation of a task's worst-case response.
  • Blocking Term (B) — the maximum time a task can be blocked by lower-priority lock holders.
  • Priority Inversion — a high-priority task blocked by a lower-priority one holding a shared lock.
  • Domino Effect — cascading deadline misses under EDF once one task's deadline is missed.
  • Ready Queue — the ordered collection of tasks eligible to run, awaiting dispatch.
  • Dispatch Latency — time from a scheduling decision to the selected task actually executing.
  • Wakeup Latency — time from a timer/event expiry to the corresponding task becoming ready.
  • Deterministic Replay — re-executing a recorded scenario to produce byte-identical output.
  • Observer Effect — the perturbation a measurement/tracing mechanism introduces into what it measures.
  • Headroom Margin — reserved slack above the admission-computed feasibility bound.
  • Criticality-Aware Shedding — rejecting/suspending lower-criticality tasks first under overload.
  • Timer Wheel — a hierarchical bucket structure for amortized O(1) timer insertion at scale.
  • Drift — the accumulated divergence of a clock source from true elapsed time.
  • Monotonic Clock — a clock source guaranteed never to run backward, used for all scheduling time.
  • Trust Boundary — a point in the architecture where input crosses from untrusted to trusted context.
  • Concurrency Boundary — a point where multiple threads/cores access shared state under a lock.
  • Trace Event — a single recorded scheduling-relevant occurrence with timestamp and kind.
  • Ring Buffer — a fixed-capacity circular buffer used for lock-free event capture.
  • Chrome Trace Format — the JSON schema consumed by chrome://tracing/Perfetto viewers.
  • Stack Resource Policy — Baker's bounded-blocking protocol for nested resource acquisition.
  • Constant Bandwidth Server — Abeni & Buttazzo's aperiodic-task bandwidth-reservation mechanism.
  • Feasibility — the property that a task set can meet all deadlines under a given scheduling policy.
  • Implicit Deadline — a task whose relative deadline equals its period.
  • NUMA — Non-Uniform Memory Access; a multi-socket memory architecture with cross-node latency cost.
  • Partitioned Scheduling — statically assigning each task to exactly one core's independent scheduler.
  • Global Scheduling — scheduling from a single logical queue spanning all cores, with migration.
  • Mixed-Criticality — systems combining tasks of different assurance levels under one scheduler.
  • Fixed Priority — a scheduling discipline where task priority is assigned once, statically.
  • Dynamic Priority — a scheduling discipline where task priority changes at runtime (e.g. by deadline).
  • Lock Ownership — the recorded association between a held lock and the task currently holding it.
  • Deadlock Cycle — a circular wait among tasks each blocked on a resource another holds.
  • Soak Test — a long-duration run designed to surface slow-accumulating failure modes.
  • RPO — Recovery Point Objective; the maximum tolerable data loss window on recovery.
  • RTO — Recovery Time Objective; the maximum tolerable time to restore service after a failure.
