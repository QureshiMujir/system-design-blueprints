33. Hard Questions (Self-Examination)

  • Q1. The RMS utilization bound (§15) is sufficient but not necessary; exact RTA (§15) recovers admittable capacity at the O(n²) cost quantified in §32. At what task-set size does the §4 15 ms admission budget force falling back to the cheaper bound, and what capacity is sacrificed?
  • Q2. §18's blocking-aware admission integration retroactively tightens the sets §15/§16 would have admitted using the stubbed blocking constant. What happens to a workload already running under the stub when the real bound is wired in — does §21's re-admission discipline cover this transition?
  • Q3. §16's domino effect and §15's cascading-jitter failure mode are structurally different. Does §21's ordinal criticality shedding fully close both gaps, or only the EDF-specific one?
  • Q4. §17's per-core run queues eliminate the global-queue cache-thrash problem, but §29 identifies the shared admission-registry lock as the next bottleneck. At what core count does §32's C6 admission cost start to dominate over the per-dispatch cost §17 optimized?
  • Q5. §19's tracing pipeline is measured against a 5% overhead budget (§4, §28 M9), but §20's tracing-on/tracing-off methodology is itself a benchmark technique. How would an operator detect a regression in the observer-effect correction itself, as opposed to in the traced subsystem?
  • Q6. §11's Criticality enum ordinal directly drives §21's shedding order. If a future deferred feature (§35) needs a criticality class between two existing ones, does the append-only compatibility rule (§25) still hold, or does it force a breaking change?
  • Q7. §13's monotonic-only time and §9's ADR-21 lock out wall-clock scheduling decisions entirely. What operator-facing feature legitimately needs wall-clock correlation, and how does §19's trace pipeline provide that without violating §13's Principle P7?
  • Q8. §31 shows seL4 verifies the absence of unbounded inversion; this blueprint instead bounds it operationally (§18) and measures it (§28 M10). What would have to change in §26's testing strategy to close that gap, and is §35's registered deferral the right place to track it?
  • Q9. §32's C6 and §4's 15 ms admission budget assume a specific per-iteration cost. If the actual RTA implementation in §15 is 3× slower than assumed, does §21's headroom-margin admission still hold, or does the whole capacity model in §32 need re-derivation?
  • Q10. §16's edge cases document a blocking-infeasible-but-utilization-feasible EDF case resolved by §18. Does §15's equivalent RMS admission path have the same latent gap, and if so, why does §15 already account for it while §16 needed the explicit callout?
  • Q11. §29's horizontal-scaling discussion defers both partitioned and global EDF (§35). Given §32's C10 NUMA-penalty arithmetic, which deferred approach does the current capacity model imply will be cheaper past the §4 32-core ceiling, and why hasn't that already motivated building it?
  • Q12. §22's T8 threat and §15's normal admission path use the same RTA implementation. Does the time-budget abort in T8's mitigation change the correctness guarantee §7's I1 makes, or only its latency?
  • Q13. §24's on-call escalation asymmetry assumes the criticality classification at admission time is itself correct. What in §14's validation pipeline actually verifies an operator declared the right criticality, versus just a syntactically valid one?
  • Q14. §20's benchmark methodology explicitly controls for thermal throttling and frequency scaling. Does §21's 24 h release-candidate soak test inherit those same controls, or does a multi-hour run reintroduce the non-stationarity §20 warns about at a longer timescale?
  • Q15. §9's ADR-07 rejects an async runtime for the scheduler itself, but ADR-06 permits a local trace-export socket. Could that socket's I/O path reintroduce the cooperative-scheduling contamination §1's Principle P1 forbids, and what in §19's design specifically prevents it?
  • Q16. This section cites §15, §16, §18, and §21 repeatedly. If a future contributor changes §18's blocking-bound computation, which questions above would need re-verification, and does §26's regression-test suite actually cover that cross-section dependency?
  • Q17. §28's M7 startup budget and §32's C12 both claim 209 ms against a 500 ms ceiling. If §21's release-candidate hardening adds a mandatory extra admission preflight pass, does C12's arithmetic still hold, or does the §12 startup budget need re-deriving at release time?
  • Q18. §31 shows FreeRTOS uses no admission control at all and still ships in safety-relevant embedded contexts. Does that undermine §1's Principle-P8 argument, or does it only show admission-before-execution is necessary for this blueprint's worst-case-first goal (§2) rather than universally?
  • Q19. §23's FM-9 and §7's I13 both assume the same TaskSpec set re-admitted identically produces the same decision. Does §17's introduction of per-core queues preserve that property, or does core-assignment order become a new source of nondeterminism §14 and §15 didn't need to worry about?
  • Q20. §35 registers SMT-backed schedulability proofs against §15. Given §32's C6 already bounds RTA's cost analytically, what would an SMT solver add over the closed-form bound in §8 that isn't already captured by exact RTA — and is that gap large enough to justify un-deferring it?

30. Mental Models & First Principles

  • MM1 — Worst-Case-First Thinking. Optimize the tail, not the mean · predicts an "obvious" average- case win can regress p99 · the bug class you write without it: a latency regression hidden behind an improved mean · applies in §28.
  • MM2 — Admission Is a Proof, Not a Guess. Schedulability is a provable property at admission time, not an empirical hope · predicts a workload that "usually works" will eventually miss under exactly the interleaving the proof rules out · bug class: silent infeasibility discovered in production · applies in §15.
  • MM3 — Blocking Is Priority Debt. Every lock acquisition is a loan of priority that must be repaid within a bound · predicts unbounded loans (no PI) cause unbounded inversion · bug class: priority- rollback bugs, orphaned inheritance · applies in §18.
  • MM4 — Time Is Not a Side Effect, It Is the API. If a timing property isn't measured and exported, it doesn't exist operationally · predicts an unmeasured latency claim will eventually be wrong · bug class: "it felt slow" incidents with no data behind them · applies in §19.
  • MM5 — Determinism Enables Debugging, Not Just Correctness. A deterministic replay turns a Heisenbug into a reproducible one · predicts nondeterministic admission (I13) will resist all ad hoc debugging · bug class: unreproducible scheduler panics · applies in §20.
  • MM6 — Cascades Beat Isolated Failures. Dynamic-priority systems propagate one miss into many; fixed- priority systems isolate misses to lower-priority tasks by construction · predicts EDF needs explicit overload governance that RMS gets almost for free · bug class: unbounded blast radius under overload · applies in §21.
  • MM7 — Every Number Must Have Arithmetic Behind It. A capacity claim without a derivation is an assertion, not an engineering fact · predicts undocumented budgets drift silently out of sync with reality · bug class: budget numbers that quietly stop matching production · applies in §32.
  • MM8 — Reject at the Gate, Not Mid-Flight. Admission control is cheaper to get right than runtime recovery · predicts any system that defers rejection to runtime pays a correctness tax later · bug class: partial admission leaving inconsistent state · applies in §15.

5. Required Reading

Books

  • Real-Time Systems — Jane W. S. Liu (2000), ch. 4–8: Liu & Layland RM/EDF theory, fixed- vs. dynamic-priority scheduling, resource access control; applied in §15 and §16.
  • Scheduling: Theory, Algorithms, and Systems — Michael Pinedo (2016), ch. 1–3: scheduling taxonomy, optimization formulations, overload behavior framing; applied in §15.
  • Operating Systems: Three Easy Pieces — Remzi H. Arpaci-Dusseau & Andrea C. Arpaci-Dusseau (2018), ch. 7–10 and ch. 28–31: grounding for dispatch and sync design; applied in §17 and §18.
  • Linux Kernel Development — Robert Love (2010), ch. 4 (Process Scheduling), ch. 11 (Timers): production scheduler and timer-infrastructure design patterns; applied in §13 and §17.
  • Understanding the Linux Kernel — Daniel P. Bovet & Marco Cesati (2005), ch. 6–7: CFS and timer-wheel internals, interrupt-pipeline tradeoffs; applied in §13.
  • Systems Performance — Brendan Gregg (2020), ch. 2 and ch. 5–6: latency-analysis methodology, tracing, histogram construction, benchmarking discipline; applied in §19 and §20.
  • The Art of Multiprocessor Programming — Maurice Herlihy & Nir Shavit (2012), ch. 5 and ch. 8: lock-free structures, memory-ordering correctness; applied in §17 and §18.
  • Rust Atomics and Locks — Mara Bos (2023), ch. 4–7: atomic ordering, mutex/semaphore design, wakeup correctness; applied in §18.

Papers

  • "Scheduling Algorithms for Multiprogramming in a Hard-Real-Time Environment" — Liu & Layland, 1973, Journal of the ACM: the RM utilization bound and EDF optimality proof, driving admission control; applied in §15 and §16.
  • "Priority Inheritance Protocols: An Approach to Real-Time Synchronization" — Sha, Rajkumar, Lehoczky, 1990, IEEE Transactions on Computers: bounded-blocking priority inheritance → rt_sync mutex design; applied in §18.
  • "The Rate Monotonic Scheduling Algorithm: Exact Characterization and Average Case Behavior" — Lehoczky, Sha, Ding, 1989, RTSS: the exact response-time recurrence → rt_rms::rta; applied in §15.
  • "Rate Monotonic vs. EDF: Judgment Day" — Buttazzo, 2005, Real-Time Systems journal: practical RM-vs-EDF tradeoffs under implementation overhead, comparative framing; applied in §31.
  • "Stack-Based Scheduling of Realtime Processes" — Baker, 1991, Real-Time Systems journal: the Stack Resource Policy, bounded blocking under nested resource access; applied in §18.
  • "Applying New Scheduling Theory to Static Priority Pre-emptive Scheduling" — Audsley, Burns, Richardson, Tindell, Wellings, 1993, Software Engineering Journal: generalized exact response-time analysis; applied in §15.
  • "Preemptively Scheduling Hard-Real-Time Sporadic Tasks on One Processor" — Baruah, Mok, Rosier, 1990, RTSS: EDF feasibility analysis for sporadic task sets → rt_edf::feasibility; applied in §16.
  • "Integrating Multimedia Applications in Hard Real-Time Systems" — Abeni & Buttazzo, 1998, RTSS: the Constant Bandwidth Server, the deferred aperiodic-service design target; applied in §35.

Reference Implementations

  • torvalds/linux — study kernel/sched/rt.c, kernel/sched/deadline.c, kernel/time/: production fixed-priority and deadline-scheduler design; pitfall: do not copy CFS's load-balancer wholesale — it optimizes throughput, not bounded worst-case latency; applied in §17.
  • FreeRTOS/FreeRTOS-Kernel — study tasks.c, the timer service task, priority inheritance in queue.c: lightweight embedded-scheduler patterns; pitfall: do not copy its O(n) ready-list scan — it does not scale to §4's 512-tasks-per-core budget; applied in §14.
  • zephyrproject-rtos/zephyr — study kernel/sched.c, the SMP scheduler, k_timer: multicore-aware RTOS scheduling; pitfall: do not adopt its single global scheduler lock uncritically — it caps §29's scaling assumption; applied in §17.
  • seL4/seL4 — study the deterministic scheduler in src/kernel/thread.c and its verification discipline; pitfall: do not assume seL4's formal-verification guarantees transfer without redoing the proofs against §7's invariants; applied in §26.
  • tokio-rs/tokio — study tokio/src/runtime/scheduler, tokio/src/time/wheel.rs: cooperative wakeup mechanisms and timer-wheel driver structure; pitfall: do not adopt cooperative task scheduling — it violates Principle P1; applied in §13.

RFCs / Specifications

  • POSIX.1-2017 (IEEE Std 1003.1-2017), clause 2.8.6 — pins down CLOCK_MONOTONIC, clock_gettime, and timer_create semantics this scheduler's clock abstraction wraps; applied in §13.
  • POSIX.1-2017 (IEEE Std 1003.1-2017) <sched.h> — pins down SCHED_FIFO/SCHED_RR and the sched_setaffinity priority/affinity model the dispatch layer delegates to; applied in §17.
  • IEEE Std 1003.13-2003 (POSIX Realtime and Embedded Application Support, PSE51/52 profiles) — pins down the minimal-footprint real-time profile the eventual embedded/RTOS migration path targets; applied in §35.
  • RFC 5905 "Network Time Protocol Version 4: Protocol and Algorithms Specification" — pins down the clock-discipline and drift-accounting algorithm structure reused conceptually for drift correction; applied in §13.

Glossary (§36) · 50 terms · site-wide glossary

WCET
worst-case execution time; the declared per-activation upper bound a task's runtime is admitted against.
Jitter
variance in actual wakeup or completion time relative to the scheduled instant.
Deadline
the latest instant by which a task's execution must complete.
RMS
Rate Monotonic Scheduling; static fixed-priority assignment by shortest period.
EDF
Earliest Deadline First; dynamic priority assignment by nearest absolute deadline.
PI
Priority Inheritance; a protocol bounding blocking duration under lock contention.
Admission Control
the pre-execution schedulability check gating whether a task set may run.
Preemption
interrupting a running task's execution to run a higher-priority/earlier-deadline one.
Tickless
an event-driven timing model with no fixed periodic hardware tick.
Affinity
the set of CPUs a task is permitted to execute on.
Context Switch
the act of transferring CPU execution from one task to another.
Starvation
indefinite delay of a task's execution caused by other tasks' priority or ordering.
Sporadic Task
a task with irregular activation obeying only a minimum inter-arrival time.
Periodic Task
a task activated at a fixed, regular interval.
Criticality
a task's declared importance class, used to order overload-shedding decisions.
Utilization Bound
the Liu & Layland sufficient-schedulability threshold for RMS.
Response-Time Analysis (RTA)
the exact fixed-point computation of a task's worst-case response.
Blocking Term (B)
the maximum time a task can be blocked by lower-priority lock holders.
Priority Inversion
a high-priority task blocked by a lower-priority one holding a shared lock.
Domino Effect
cascading deadline misses under EDF once one task's deadline is missed.
Ready Queue
the ordered collection of tasks eligible to run, awaiting dispatch.
Dispatch Latency
time from a scheduling decision to the selected task actually executing.
Wakeup Latency
time from a timer/event expiry to the corresponding task becoming ready.
Deterministic Replay
re-executing a recorded scenario to produce byte-identical output.
Observer Effect
the perturbation a measurement/tracing mechanism introduces into what it measures.
Headroom Margin
reserved slack above the admission-computed feasibility bound.
Criticality-Aware Shedding
rejecting/suspending lower-criticality tasks first under overload.
Timer Wheel
a hierarchical bucket structure for amortized O(1) timer insertion at scale.
Drift
the accumulated divergence of a clock source from true elapsed time.
Monotonic Clock
a clock source guaranteed never to run backward, used for all scheduling time.
Trust Boundary
a point in the architecture where input crosses from untrusted to trusted context.
Concurrency Boundary
a point where multiple threads/cores access shared state under a lock.
Trace Event
a single recorded scheduling-relevant occurrence with timestamp and kind.
Ring Buffer
a fixed-capacity circular buffer used for lock-free event capture.
Chrome Trace Format
the JSON schema consumed by chrome://tracing/Perfetto viewers.
Stack Resource Policy
Baker's bounded-blocking protocol for nested resource acquisition.
Constant Bandwidth Server
Abeni & Buttazzo's aperiodic-task bandwidth-reservation mechanism.
Feasibility
the property that a task set can meet all deadlines under a given scheduling policy.
Implicit Deadline
a task whose relative deadline equals its period.
NUMA
Non-Uniform Memory Access; a multi-socket memory architecture with cross-node latency cost.
Partitioned Scheduling
statically assigning each task to exactly one core's independent scheduler.
Global Scheduling
scheduling from a single logical queue spanning all cores, with migration.
Mixed-Criticality
systems combining tasks of different assurance levels under one scheduler.
Fixed Priority
a scheduling discipline where task priority is assigned once, statically.
Dynamic Priority
a scheduling discipline where task priority changes at runtime (e.g. by deadline).
Lock Ownership
the recorded association between a held lock and the task currently holding it.
Deadlock Cycle
a circular wait among tasks each blocked on a resource another holds.
Soak Test
a long-duration run designed to surface slow-accumulating failure modes.
RPO
Recovery Point Objective; the maximum tolerable data loss window on recovery.
RTO
Recovery Time Objective; the maximum tolerable time to restore service after a failure.
