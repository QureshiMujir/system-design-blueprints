Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Global EDF Across All Cores

        ┌───────────────────────────────┐
        │   Single global deadline queue │
        └────────────┬────────────────────┘
             ┌────────┼────────┬─────────┐
             v        v        v         v
          Core0    Core1    Core2  ...  CoreN
        (migrates the globally-earliest-deadline task to whichever core is free)

Regime where it wins: workloads with highly variable per-task WCET where static per-core partitioning (this blueprint's §17 approach) would leave some cores idle while others are overloaded. Real system embodying it: Linux SCHED_DEADLINE's default (non-partitioned) mode. Why rejected here: migration cost (§32 C10) and the cache-locality loss it causes directly contradict the per-core working-set budget in §4; §17 chose per-core queues with bounded, exceptional migration specifically to keep that budget intact, accepting some theoretical schedulable-capacity loss (§29) in exchange.

Alt B — Cooperative (Async/Poll-Based) Task Scheduling

   ┌──────────────┐     poll()      ┌──────────────┐
   │ Task future A │ ───────────▶   │ Executor loop │
   └──────────────┘                 └──────┬────────┘
   ┌──────────────┐     poll()             │
   │ Task future B │ ◀──────────────────────┘
   └──────────────┘   (task yields voluntarily; no preemption)

Regime where it wins: I/O-bound throughput workloads where thousands of lightweight tasks share a small thread pool and average-case latency, not worst-case bound, is the metric that matters. Real system embodying it: Tokio. Why rejected here: cooperative scheduling requires every task to yield promptly and voluntarily; a single misbehaving or long-running task starves everything else with no scheduler-level recourse, which is precisely the failure mode Principle P1 and Invariant I5 exist to make structurally impossible.

Alt C — Kernel-Module Real-Time Scheduling Class

   ┌───────────────────────────────────────┐
   │  Linux kernel                          │
   │   ┌─────────────────────────────────┐ │
   │   │ Custom sched_class (kernel mod)  │ │
   │   └─────────────────────────────────┘ │
   └───────────────────────────────────────┘

Regime where it wins: when userspace wakeup-latency overhead (§32 C4's 15 µs chain) itself is the bottleneck and only true kernel-level preemption points can close the gap further — the domain kernel/sched/deadline.c already occupies. Real system embodying it: the Linux kernel's own SCHED_DEADLINE class. Why rejected here: §1 explicitly scopes this blueprint to userspace (a kernel module changes the language, tooling, verification burden, and audience entirely — see ADR-01's Rust-in-userspace rationale) and a kernel-level implementation is exactly the Phase 1+ continuation PhaseDeferred("§17") (userspace/kernel co-scheduling) tracks in §35, not a Phase 0–9 goal.
