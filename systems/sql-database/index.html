In one paragraph

A single-node relational database written from scratch in Rust as one complete vertical slice: SQL text is lexed, parsed, type-checked against a catalog, planned, optimised by cost and run by iterators that pull rows through a buffer pool, whose pages a write-ahead log protects and ARIES recovers after a crash, while multi-version concurrency control keeps each transaction's view consistent (§1). Sibling blueprints cover each layer in depth; this one is about composition, so that two promises hold end to end: a committed transaction survives any crash, and a query returns exactly what its snapshot implies (§1). Applications embed it as a library or run it as a single-process server (§1, ADR-29).

The problem, concretely

The blueprint's own failure-path example: a client sends UPDATE accounts SET balance = balance - 100 WHERE id = 1 inside a transaction, and the connection drops before it commits. The session manager's drop handler issues an implicit ROLLBACK, the transaction manager marks it aborted, and if the machine crashes later, recovery's analysis pass finds it uncommitted, so none of its changes come back (§8, I2). That is the normal path. The hard part is keeping two promises at the same time: a committed transaction's effects survive an arbitrary crash, and a query's result is exactly what its transaction's snapshot implies (§1).

The naive way to the first promise is to fsync every page write. The blueprint names the bug class that follows: it wastes throughput and still does not guarantee that the log reaches disk before the page, unless that ordering is enforced separately (§32 MM2). Getting the ordering wrong does not show up as a failed test. It shows up as silent corruption discovered only after a crash (P1).

Speed has the same shape. In the blueprint's three-table join, the right selectivity estimate predicts 10 intermediate rows; a mis-estimate predicts 100,000, and the optimiser may switch to a plan that is slow but still correct (§8, MM4). Each concern is a layer: durability is an ordering rule between the buffer pool and the log (MM1, MM2), isolation is a rule about which row version a transaction may see (I3), and plan choice is a search whose main enemy is a bad row-count estimate (MM4). The difficulty is making them correct together: the buffer pool must obey the log (I1), the vacuum must obey the snapshots (I7), and the optimiser must never change an answer (I8).

How it works, end to end

The blueprint draws the engine as a stack of boundaries, each a different kind of trust or guarantee (§3):

 Client (CLI / TCP)                                  — untrusted input
   │ wire protocol (ADR-29)
 Session manager (per-connection state, prepared statements)
 Lexer → Parser → AST                                — syntax boundary
 Catalog ◄── Semantic analyser / Binder              — type boundary
 Logical planner ◄── Statistics (histograms, NDV)
 Cost-based optimiser ──► Physical plan              — plan boundary
 Execution engine (Volcano iterators)
 Heap scan │ B+Tree scan │ Lock manager              — concurrency boundary
 Buffer pool (pin/latch, replacement policy)
 Pager (page I/O) │ Transaction manager / MVCC version store
 Heap file (slotted pages) │ Version chain + vacuum worker
 B+Tree index │ WAL writer ──► Recovery manager      — durability boundary
   │ fsync
 [ disk: heap files, index files, WAL ]

A statement arrives over the wire and is owned by a session in sqldb-proto, the point where a client socket maps to a Transaction (§1, §3). The lexer and parser in sqldb-parser turn text into an untyped Ast; malformed input must fail here, never panic — the syntax trust boundary (§3). The binder in sqldb-plan resolves every name against the catalog (sqldb-catalog), assigns types and inserts implicit casts; past this point an Ast has become a BoundExpr (§3). The logical planner, also in sqldb-plan, builds a LogicalPlan and applies rewrites such as predicate pushdown and projection pruning; the optimiser chooses a PhysicalPlan by cost within a planning-time bound, and I8 says any valid physical plan must return the same multiset of rows (§3, I8). The executor in sqldb-exec drives the operator tree through the Volcano contract — Open, Next, Close (§8, P11). Every page access passes through the buffer pool in sqldb-buffer, where a page cannot be evicted while a PinGuard is alive — a compile error, not a runtime assertion (§1, §3, P6). Below it the pager in sqldb-storage performs the actual reads, writes and fsyncs. The WAL writer in sqldb-wal appends records, and no dirty page may reach disk before its record is fsynced (§3, I1). After a crash the recovery manager in sqldb-recovery runs ARIES analysis, redo and undo (§3, §21). The transaction manager in sqldb-txn allocates transaction ids, tracks snapshots and threads each row's version chain; a transaction reads only the versions its snapshot allows (I3), and a background vacuum worker reclaims versions no live snapshot can see (§3, I7).

The core ideas

Pages with a slot directory (§8, MM5)

Pages are a fixed 8 KiB (ADR-03), with one heap file and one index file per table (ADR-10). A page has a 20-byte header — page id, LSN, a CRC32C checksum, slot count and free-space pointer — then a slot array growing upward from byte 20 and tuple data growing downward from the page end (§8). The worked insert: a page with slot_count=3 and free_space_ptr=6000 takes a 140-byte tuple by appending slot 3 at offset 20+12=32, writing the tuple at 6000−140=5860 and setting the pointer to 5860 (§8). A delete only zeroes the slot's length field and leaves free_space_ptr alone; compaction later copies tuples toward the page end, rewrites the slot offsets, and is done under the page's exclusive latch and logged as a single WAL record (§8, I1, I5). The reason for the indirection is identity versus location: a TupleId (page, slot) is stable, while the slot's offset may move, so indexes survive compaction (§32 MM5).

Write-ahead logging makes durability an ordering rule (§8, MM2)

Each log record carries an LSN, the previous LSN of the same transaction, the transaction id, a type (Update, Commit, Abort, Checkpoint or Clr), a page id and before/after images (§8, ADR-11). The rule is not "fsync everything" but "the log record must be durable before the page it describes" (I1, P2) — so only the log needs fsyncing, and commits can be batched without weakening durability (§32 MM2). Group commit fsyncs once per 2 ms window or 32 pending commits, whichever comes first (§4, ADR-13). The capacity model gives the payoff: at a 2 ms fsync, one writer tops out at 1 ÷ 0.002 = 500 commits/s, and a 32-commit batch raises the ceiling to 32 ÷ 0.002 = 16,000 commits/s (§34 items 6 and 7).

Recovery is the same log applied twice (§8, §21, MM8)

ARIES runs three passes: analysis rebuilds the dirty-page table and active-transaction table from the last checkpoint; redo replays every logged action whose page LSN is older than the record, including the work of transactions that never committed ("repeating history"); undo walks each loser's prev_lsn chain backward, writing a compensation log record (CLR) per undone action (§8). The worked trace: Update(T1,p5,lsn=100), Update(T1,p6,lsn=101), Commit(T1,lsn=102), Update(T2,p5,lsn=103), then a crash. Analysis finds T1 committed and T2 a loser; redo replays LSNs 100–103, so p5 also gets T2's uncommitted change; undo reverses LSN 103 and writes a CLR at LSN 104 pointing to T2's original prev_lsn, so a second crash during undo does not redo LSN 103 again (§8, P14).

B+Tree height is the unit of cost (§8, §34, MM7)

Internal nodes hold keys and child pointers; leaves hold keys and row ids plus a next_leaf sibling pointer, so range scans walk sideways (§8). With an 8-byte key and a 4-byte page id a node holds 8172 ÷ 12 ≈ 681 entries, and 10,000,000 keys need height 3, because log₆₈₁(10,000,000) ≈ 2.47 rounds up (§34 items 3 and 4). Once the top levels are resident in the buffer pool, the blueprint counts only the leaf read as a cold-cache cost (§34 item 4, MM7). A full leaf splits by allocating a right sibling, copying its upper half there, linking it through next_leaf and posting a separator key to the parent — recursing upward, and growing a new root if the root splits. Every step is logged before it is applied, so a crash lands on either the pre-split or the fully split tree (§8, I4, P2).

Versions, snapshots and the anomaly menu (§8, MM3, MM6)

Each row version carries (xmin, xmax, data): the transaction that created it and the one that replaced it (§8). A version is visible to a snapshot when xmin is committed and in the snapshot, and xmax is empty, uncommitted or not in the snapshot (§8, I3). The worked schedule: T1 inserts a row (xmin=10) and commits; T2 begins; T3 begins after T2, updates the row (old version xmax=30, new version xmin=30) and commits; T2 still sees the old version, while a T4 that begins after T3 commits sees only the new one (§8). Isolation levels are a menu of anomalies you accept (§32 MM6): Read Committed allows non-repeatable reads, phantoms and write skew; Repeatable Read (snapshot isolation) prevents the first two but still allows write skew — two doctors on call each read that the other is on, each goes off duty, and both commit because they wrote different rows, leaving nobody (§8). Serializable adds SSI, which detects the rw-antidependency cycle and aborts one of them (§8, ADR-16). A long-running transaction is therefore not slow; it is a storage leak, because it holds back the vacuum horizon (§32 MM3, §34 item 10).

The optimiser searches under uncertainty (§8, MM4)

Costs are comparative, not calibrated to wall-clock time (P12): a scan costs pages × an I/O unit; a hash join costs rows of each input × a hashing unit, plus a spill term past the memory budget (§8, ADR-28). The worked example joins Orders (1,000,000 rows), Customers (100,000) and Regions (10). Joining Orders and Customers first by hash join costs about 1.1 million hash operations and is estimated to yield 10 rows, so the dynamic-programming search keeps that order. Had the selectivity been mis-estimated as 1/10 instead of 1/100,000, the estimate would be 100,000 intermediate rows and the optimiser could flip to a sort-merge join that sorts needlessly — slow, but still correct (§8, P4, I8). Planning is bounded by a DP cutoff with a greedy fallback: ≤ 50 ms p99 for queries of up to 12 relations, hard cap 200 ms (§4, ADR-23, I13).

The trade-offs — where engineers disagree

Row store, not column store (ADR-02)

Chosen: a row store, because OLTP point lookups and updates dominate the scope (ADR-02). Rejected: a column store. When the rejected choice is right: analytics-heavy scans, as in DuckDB (ADR-02) — the blueprint calls this its sharpest named contrast (§36 Alternative 3).

B+Tree, not LSM-tree (ADR-07)

Chosen: a B+Tree, because read-optimised point and range queries dominate (ADR-07). Rejected: an LSM-tree, a hash index. When the rejected choice is right: write-heavy ingestion, as in RocksDB or Cassandra (ADR-07, §36 Alternative 1).

MVCC with snapshot isolation, not strict two-phase locking (ADR-16)

Chosen: MVCC snapshot isolation plus SSI-lite, so readers never block writers, matching PostgreSQL's default (ADR-16). Rejected: strict 2PL, pure optimistic concurrency control. When the rejected choice is right: strict 2PL, when serializability must be guaranteed by construction, as in classic mainframe transaction-processing systems (ADR-16, §36 Alternative 2).

In-place update with an undo chain, not append-only versions (ADR-17)

Chosen: in-place update plus an undo/version chain, bounding heap growth for update-heavy workloads, closer to InnoDB (ADR-17). Rejected: an append-only heap, delta-only versions. When the rejected choice is right: append-only, when vacuum throughput matters more than update cost, as in PostgreSQL (ADR-17). The blueprint is not consistent here: §22.2 step 1 says an update "creates a new version, does not overwrite in place" and in the same step calls this ADR-17's in-place-plus-undo-chain variant with the current version stored in place, while §33 calls PostgreSQL's append-only design the closest sibling to Phase 10 and InnoDB's in-place design ADR-17's choice.

ARIES, not shadow paging (ADR-15)

Chosen: ARIES, which matches the steal/no-force buffer policy the buffer pool needs for efficiency (ADR-15). Rejected: shadow paging (no-steal/no-force). When the rejected choice is right: simpler embedded engines avoiding a WAL entirely, as in early SQLite's rollback-journal mode (ADR-15).

Group commit, not fsync per commit (ADR-13)

Chosen: batched fsync on a timer or queue-depth trigger — 2 ms or 32 pending commits — amortising fsync latency across concurrent commits (ADR-13, §4). Rejected: fsync per commit, no fsync. When the rejected choice is right: fsync per commit, when single-transaction latency beats aggregate throughput, e.g. a single-tenant embedded app (ADR-13).

Tuple-at-a-time Volcano, not vectorised or compiled execution (ADR-25)

Chosen: the Volcano tuple-at-a-time iterator, the simplest correct composition for the row-store scope (ADR-25). Rejected: vectorised batches, compiled/JIT execution. When the rejected choice is right: vectorised execution for large analytic scans, as in DuckDB and MonetDB/X100 (ADR-25).

Roads not taken (§36)

An LSM-tree storage engine wins for write-heavy ingestion where read amplification is an acceptable price for write throughput, as in RocksDB or Cassandra. It is rejected because the target is mixed OLTP where point-lookup latency matters as much as write throughput (§36 Alternative 1).

Strict two-phase locking wins where serializability by construction is worth blocking readers, as in classic mainframe TP systems. It is kept only as the studied alternative behind the lock-compatibility matrix (§36 Alternative 2).

A vectorised or compiled column-store engine wins by an order of magnitude on analytic scans over large columns, as in DuckDB, HyPer or MonetDB/X100, and loses on the point-access latency targets in §4 (§36 Alternative 3).

An in-memory database with command logging, as in H-Store or VoltDB, wins when the whole workload fits in memory, and is rejected because the 1 TiB maximum database size and the row-count targets assume data does not fit (§36 Alternative 4, §4).

Deferred rather than rejected: window functions, recursive CTEs, foreign-key enforcement, parallel execution, distribution, overflow storage for wide rows, stored procedures and multi-tenant access control are all outside Phases 0–11 (§37).

What must never be false

  • I1 — no dirty page reaches disk before its WAL record is durable; an eviction assertion on the page LSN, counted by wal_rule_violations_total.
  • I2 — after recovery every committed transaction is present and every uncommitted one absent; a crash-injection test compares the commit log to the recovered tables.
  • I3 — a transaction reads exactly the version set its snapshot defines; an Adya-style anomaly-schedule history checker, visibility_check_failures_total.
  • I4 — the B+Tree stays balanced and every internal key bounds its subtree; a property test walks the leaves in key order after random operations.
  • I5 — a slotted page's free-space accounting equals its actual free bytes; a checksum plus free-space assertion in debug builds, page_free_space_mismatches_total.
  • I6 — every live row's version chain ends at a visible version; a chain-walk test, version_chain_length_p99.
  • I7 — vacuum never removes a version visible to any live snapshot; a read-after-vacuum regression test, oldest_snapshot_age_seconds.
  • I8 — a logical plan and every valid physical plan return identical multisets; a differential test against a naive plan and against SQLite.
  • I9 — a page's LSN never decreases; an assertion on page write, lsn_regression_events_total.
  • I10 — two transactions never both hold conflicting writes on one row without one aborting; a serialization-failure test, serialization_failures_total.
  • I11 — the catalog is never observed half-committed; a concurrent DDL/DML schedule test, catalog_read_during_ddl_total.
  • I12 — a checkpoint's dirty-page table is a superset of the pages actually dirty; a checkpoint-then-crash recovery test.
  • I13 — planning time is bounded regardless of query shape; an adversarial-query planning-time test, plan_time_p99_ms.

What breaks in production

  • FM-1 — commits hang under load. A lost wakeup in group commit (§20.6); commit_latency_p99 spikes and a stuck-thread detector fires; restart the session, or the server if systemic — in-flight uncommitted transactions roll back safely (I2).
  • FM-2 — stale or missing rows under concurrent update. A visibility-rule bug or a miscomputed vacuum horizon (I3, I7); found by the anomaly-schedule checker or a user report; no automatic recovery — halt the table's traffic and restore from the last known-good backup.
  • FM-3 — index and heap disagree. A crash mid-split not fully redone, or a stale row id after vacuum; a balanced-and-ordered check run against a production snapshot; redo fixes the crash case, otherwise rebuild the index from the heap file.
  • FM-4 — recovery never converges. Undo not logged as CLRs (P14) or a corrupt checkpoint record; a crash repeating at the same recovery step; fall back to the previous good checkpoint and replay the WAL from there.
  • FM-5 — buffer-pool thrash. The working set exceeds the pool, or a clock-sweep reference-bit bug; buffer_pool_hit_ratio falls below its SLO; enlarge the pool or shard hot tables.
  • FM-6 — one page fails its checksum on every read. A torn write or bit rot (T7); torn_page_detected_total; reconstruct from the WAL if the records are intact, otherwise restore the file from backup and replay the WAL since the backup LSN.
  • FM-8 — planning time exceeds the hard cap. An adversarial or unexpectedly large join shape; a plan_time_p99_ms alert; the DP-to-greedy fallback should already have engaged, and if it did not, that is the bug — force a naive plan for the session meanwhile.
  • FM-9 — vacuum backlog grows without bound. A long-running transaction holds back the reclaim horizon; an oldest_snapshot_age_seconds alert; this is correct behaviour per I7, and the fix is terminating the offending session.

Threats a reader should know (§24): T1 SQL injection, answered by prepared statements (Parse + Bind) that separate code from data; T2 denial of service through a deeply nested expression or a 50-relation join, answered by a recursion-depth cap and the planning cutoff; T3 a crafted database or WAL file attacking the decoders, answered by fuzzing and per-page and per-record checksums; T7 a device that acknowledges fsync without persisting, mitigated by CRC32C checksums and a full fsync on file growth, and detected as a checksum mismatch on read; T10 a transaction left open forever, answered by horizon monitoring and a version-chain length bound.

How it compares

  • SQLite gives up concurrent writers entirely, which removes a whole category of concurrency bugs this blueprint spends Phases 7, 9 and 10 on (§33). That suits its embedded, single-tenant, low-concurrency niche, at a write-throughput cost the §4 targets would not accept for multi-client OLTP (§33).
  • PostgreSQL uses append-only MVCC with a separate vacuum process, decoupling write-path latency from cleanup cost (§33). It is general-purpose OLTP, and the price it pays is the historical vacuum-under-load bloat that ADR-18 and I7 are meant to avoid (§33).
  • MySQL/InnoDB keeps versions in an undo log and updates in place — ADR-17's chosen variant — bounding heap growth for update-heavy work (§33). It targets web-scale OLTP and pays with a more complex rollback path than pure append-only (§33).
  • DuckDB runs vectorised batches over a column store and wins by an order of magnitude on analytic scans by batching tuples and using SIMD (§33). It is built for embedded, in-process OLAP and does not optimise for the point-access latencies this design targets (§33).

Questions to test yourself

  1. If the buffer pool evicts a dirty page whose WAL record has not yet been fsynced due to a bug in the I1 check, what is the exact sequence of events that turns this into undetectable corruption rather than a crash? — Hint: start from I1, the WAL phase in §20 and FM-6 in §25.
  2. Why is redo unconditional ("repeat history") while undo is conditional on transaction status, and what would break if the roles were reversed? — Hint: the ARIES sequence table in §8 and the recovery phase in §21.
  3. Given MM3 and I7, construct the exact chain of events by which a single uncommitted transaction degrades the buffer-pool hit ratio (the other leading indicator) despite never touching the buffer pool directly. — Hint: the vacuum phase in §22 and the leading indicators in §26.
  4. The write-skew example in §8 shows SI permitting an anomaly that SSI prevents — trace exactly which rw-antidependency edge SSI's cycle detection finds that first-committer-wins (I10) does not. — Hint: the doctors-on-call schedule in §8 and the SSI-lite step in §22.
  5. Why must a checkpoint's Dirty Page Table be a superset, never a subset, of the actually dirty pages at that instant (I12), and what recovery failure results from an implementation that captures a subset instead? — Hint: the analysis and redo passes in §21.

If you only remember three things

A database is a cache with an unusually strong durability promise, and the promise is an ordering rule — the log record before the page — not a count of fsyncs. Every transaction reads from a snapshot of row versions, so isolation is a menu of anomalies you accept, and an old open transaction is a storage leak, not a slow query. The optimiser may choose any plan but may never change the answer, and when plans go bad the usual culprit is a wrong row-count estimate.

Words used here

  • Slotted page — a page with a header, a slot array and tuple data growing from opposite ends.
  • Buffer pool / pin — the in-memory page cache; a pinned page cannot be evicted while in use.
  • Write-ahead logging (WAL) — the rule that a change's log record is durable before its page.
  • LSN — log sequence number, a monotonic identifier for a WAL record.
  • Group commit — batching several transactions' commit records into one fsync.
  • ARIES — the analysis/redo/undo recovery algorithm this blueprint implements.
  • CLR — compensation log record: a record describing an undo action, itself never undone.
  • Checkpoint — a recorded snapshot of dirty-page and active-transaction state that bounds recovery's replay window.
  • MVCC — keeping multiple row versions so readers and writers do not block each other.
  • Snapshot / visibility rule — the set of transactions a reader treats as committed, and the function deciding whether a version is visible to it.
  • Vacuum — the background process reclaiming versions no snapshot can see.
  • Write skew — two transactions independently making changes that together violate a constraint neither alone violated.
  • B+Tree — a balanced tree index whose leaves hold sorted keys and are linked for range scans.
  • Volcano iterator — the Open / Next / Close pull-based execution model.
  • Cardinality estimation — predicting the row count a plan node will produce.
