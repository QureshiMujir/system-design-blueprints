1. Goal & Scope

Build, from scratch in Rust, a single-node relational database engine specified as a complete vertical slice — SQL text to durable, transactionally-consistent bytes on disk and back — rather than a deep treatment of any one layer. Sibling blueprints (B-Tree-Storage, LSM-Tree-Storage, MVCC-Transaction-Manager, Query-Planner, Lock-Manager-2PL, and the Write-Ahead-Log blueprint) already specify the B+Tree, the MVCC version store, the cost-based optimizer, 2PL, and the WAL each in isolation, at a depth this document does not re-derive. This blueprint's load-bearing concern is composition: how a lexer's token stream becomes a parser's AST, how a binder's typed expression becomes a logical plan, how a logical plan's chosen physical operators pull tuples through a buffer pool that is itself synchronized against a WAL that must be durable before any page it protects reaches disk, and how a transaction's MVCC snapshot stays correct while a vacuum worker reclaims versions concurrently. The two end-to-end invariants everything else exists to serve: a committed transaction's effects survive an arbitrary crash (durability composes correctly across WAL, buffer pool, and pager), and a query's result set is exactly the result set implied by its transaction's snapshot (correctness composes correctly across binder, planner, executor, and MVCC). Every row in §7 is a decomposition of these two.

Phase-0 deliverable, as a numbered crate list:

  1. sqldb-types — Datum, SqlType, Schema, error taxonomy with SQLSTATE-style codes.
  2. sqldb-storage — Pager, Page, HeapFile, slotted-page layout.
  3. sqldb-buffer — BufferPool, Frame, PinGuard, replacement policy.
  4. sqldb-index — B+Tree (BTree, LeafNode, InternalNode).
  5. sqldb-wal — WalWriter, WalRecord, group commit.
  6. sqldb-recovery — ARIES analysis/redo/undo.
  7. sqldb-txn — Transaction, Snapshot, VersionChain, lock manager.
  8. sqldb-catalog — Catalog, TableMeta, IndexMeta.
  9. sqldb-parser — lexer, recursive-descent/Pratt parser, AST.
  10. sqldb-plan — binder, logical plan, cost-based optimizer.
  11. sqldb-exec — Volcano executor, operator library.
  12. sqldb-proto — wire protocol, session manager.
  13. sqldb-cli — embedding binary and REPL client.
  14. sqldb-harness — sqllogictest runner, crash injector, schedule-anomaly checker.

Boundaries. Provides: the full SQL DDL/DML pipeline; ACID transactions at Read Committed / Repeatable Read / Serializable(SI + SSI-lite); crash recovery; a client protocol; an embeddable library and a single-process server binary. Delegates: the exact B+Tree split/merge algorithm and its concurrency protocol to B-Tree-Storage (this blueprint specifies only the seam — the BTree trait the executor calls and the WAL records it emits); the exact MVCC version-chain GC policy to MVCC-Transaction-Manager (this blueprint specifies only the visibility rule and the vacuum-to-buffer-pool seam); the exact cost-model equations and join-enumeration search to Query-Planner (this blueprint specifies only the logical-to-physical seam and one worked example proving the seam is exercised); the exact 2PL wait-for-graph mechanics to Lock-Manager-2PL (studied here only as the alternative to MVCC, §9/§36); the exact WAL record encoding to the Write-Ahead-Log blueprint (this blueprint specifies only the durability contract the WAL must uphold for the pager and recovery manager). Does NOT provide: distribution, replication, or sharding (Phase 0 is single-node); stored procedures or a procedural extension language; column-store execution (this is a row store throughout — contrast named explicitly against DuckDB/HTAP-Engine's vectorized column store in §33/§36); LSM-tree storage (contrast named against LSM-Tree-Storage in §9/§36); full SQL:2016 conformance.

Non-goals, explicit: no query-result caching; no full-text search; no JSON path queries; no window functions in Phase 0 — PhaseDeferred("§23 Phase 11 conformance hardening"); no foreign-key enforcement beyond catalog metadata — PhaseDeferred("§23 Phase 11 conformance hardening"); no parallel query execution across cores — PhaseDeferred("§31 Scalability Analysis"); no distribution/replication — PhaseDeferred("§36 Alternative Architectures, roads-not-taken sketch 4").

SQL subset supported, precisely. DDL: CREATE TABLE, DROP TABLE, CREATE INDEX, DROP INDEX, column constraints NOT NULL, PRIMARY KEY, UNIQUE, DEFAULT. DML: SELECT, INSERT, UPDATE, DELETE, BEGIN/COMMIT/ROLLBACK, EXPLAIN. Joins: INNER JOIN, LEFT OUTER JOIN, comma-syntax cross join, ON/USING predicates. Aggregates: COUNT, SUM, AVG, MIN, MAX with GROUP BY/HAVING. Subqueries: scalar subquery, IN/NOT IN, EXISTS/NOT EXISTS, correlated subqueries decorrelated per §8. No window functions, no recursive CTEs, no stored procedures, no triggers in Phase 0.

Deployment model: embedded library (sqldb::Database::open(path)) and a single-process TCP server exposing the wire protocol from §11/§23; no separate coordinator process.

Users/operators: an application embedding the library directly (no network hop), or an operator running the server binary, applying migrations, and reading the runbooks in §26.

What later phases unlock: Phase 6 (B+Tree) unlocks index-backed access paths for the optimizer built in Phase 11; Phases 8–9 (WAL/recovery) unlock crash-safety, which Phase 10 (MVCC) depends on for version-chain durability; Phase 11 unlocks the full cost-based optimizer and the wire protocol, completing the vertical slice.

Rust and rationale: ownership and borrowing statically enforce the pin/latch discipline the buffer pool depends on — a page frame cannot be evicted while a PinGuard is live, a compile error rather than a runtime assertion; no GC pauses in the commit path where fsync latency already dominates; unsafe is isolated to the pager's raw-byte page views. Rejected: C++ (manual memory management makes the pin invariant a runtime-only property, as real InnoDB bug histories show); Go (GC pauses interact badly with WAL fsync tail latency; weaker type system for the AST/plan node hierarchy); Java (GC and JIT warm-up hurt the p99 targets in §4).

Prerequisites: relational algebra and three-valued logic (Codd 1970; Database System Concepts 7th ed. chapters 2 and 6); concurrency — locking, MVCC (Gray & Reuter; Weikum & Vossen); storage — pages, buffer pools, B-Trees (Database Internals; Comer 1979).

Timeline: Phases 0–3 (skeleton through catalog/binder), 8 weeks; Phases 4–7 (planner and executor through buffer pool), 10 weeks; Phases 8–10 (WAL through MVCC/vacuum), 12 weeks; Phase 11 (optimizer, protocol, hardening), 6 weeks. Total ≈36 weeks, single engineer.

Deferrals: PhaseDeferred("§36 Alternative Architectures") for distribution; PhaseDeferred("§23 Phase 11") for window functions and recursive CTEs; PhaseDeferred("§1 Goal & Scope") for stored procedures; PhaseDeferred("§31 Scalability Analysis") for parallel/multi-core execution.

2. Why Build This

  • Storage engineering: slotted pages, free-space accounting, tuple encoding.
  • Indexing: B+Tree splits/merges that must stay crash-safe under a concurrent workload.
  • Query compilation: lexing, recursive-descent/Pratt parsing, binding, type checking.
  • Query optimization: cost models, join enumeration, cardinality estimation, plan search.
  • Execution: Volcano iterators, spill-to-disk joins and sorts, three-valued logic.
  • Durability: write-ahead logging, group commit, ARIES-style recovery.
  • Concurrency: MVCC snapshot isolation, version chains, vacuum/GC, the 2PL alternative.
  • Protocol and operations: a wire protocol, session lifecycle, observability, runbooks.

Client: an untrusted process speaking the wire protocol; every byte it sends is treated as hostile input (§24, T1). Session manager: owns per-connection state — current transaction, prepared-statement cache, output buffer — and is the point where a client socket maps to a Transaction. Lexer: turns raw SQL text into a Token stream, attaching byte-offset positions for error reporting. Parser: a recursive-descent plus Pratt-precedence parser building a typed AST; this is the syntax trust boundary — malformed input must fail here, never panic. AST: an untyped, unbound tree exactly mirroring the grammar in §8. Catalog: the durable, MVCC-versioned source of truth for table/column/ index metadata; every other component reads it, only DDL transactions write it (I11). Semantic analyzer/binder: resolves identifiers against the catalog, assigns types, inserts implicit casts, and is the last point at which an Ast becomes a BoundExpr — this is the type boundary. Logical planner: builds a LogicalPlan tree and applies the equivalence rewrites of §8 (pushdown, pruning, decorrelation). Statistics: histograms and NDV sketches, read by the optimizer and written only by ANALYZE. Optimizer: chooses a PhysicalPlan by cost, bounded in time by P4/ADR-23 — the plan boundary, past which correctness must not depend on which plan was chosen (I8). Physical plan: a tree of physical operators annotated with the access method and join algorithm chosen for each logical node. Execution engine: drives the operator tree via the Volcano Open/Next/Close contract (§8, P11). Access methods — heap scan: a sequential cursor over a HeapFile's pages. Access methods — B+Tree scan: point/range lookups through BTree, itself specified by B-Tree-Storage. Lock manager: grants and tracks tuple/table locks for SELECT FOR UPDATE and DDL, and is the concurrency boundary where 2PL (studied alternative) would plug in instead of MVCC. Buffer pool: the single cache all page I/O passes through; pin/latch discipline is enforced by PinGuard's ownership (P6). Pager: translates PageId to file offset and performs the actual read/write/fsyncsyscalls — the persistence boundary. Heap file: the on-disk sequence of slotted pages holding a table's row versions. B+Tree index: the on-disk structure giving logarithmic point/range access, sharing the pager and buffer pool with heap files. WAL writer: appends WalRecords and is the durability boundary — no dirty page may cross the pager's write path before its WAL record is fsynced (I1). Recovery manager: replays the WAL after a crash via ARIES analysis/redo/undo (§21). Transaction manager / MVCC version store: allocates TxnIds, tracks Snapshots, and threads the version chain per row. Vacuum/GC worker: a background task reclaiming versions no live snapshot can see (I7), the only writer allowed to shrink a version chain.

6. Design Principles

P1 — Durability is defined by the WAL and nothing else. A transaction is committed exactly when its commit record is fsynced; every other layer may lose state freely. Tradeoff: every commit pays fsync latency. Operational implication: durability settings are a WAL-writer configuration, not a buffer-pool one. Violating it does not cause a bug found in testing — it causes silent corruption discovered only after a crash.

P2 — Write-ahead, always. The log record for a page mutation is durable before the page itself reaches disk. Tradeoff: extra bookkeeping (page LSN checks) on every eviction. Violating it produces torn or lost updates indistinguishable from disk corruption.

P3 — Isolation is a stated level with a named anomaly set, not a vague promise. Tradeoff: stronger levels serialize more and reduce concurrency. The test suite in §28 proves which anomalies each level prevents; silently offering a weaker level than advertised manifests as application bugs that look unrelated to the database.

P4 — The optimizer is allowed to be wrong but never allowed to be slow. Planning time is bounded (§4); a bad plan is a performance bug, a wrong plan is a correctness bug (I8). Tradeoff: bounded search sacrifices optimality for predictability past the DP cutoff (ADR-23).

P5 — A page's free-space accounting is a first-class invariant, not a cache. Tradeoff: extra bookkeeping on every insert/delete/compaction. Violating it makes the allocator either waste space or overwrite live tuples (I5).

P6 — Pin discipline is enforced by ownership, not convention. A PinGuard's lifetime statically prevents eviction of a page in use. Tradeoff: borrow-checker friction at call sites. Violating it is the classic buffer-pool corruption bug: use-after-eviction.

P7 — A transaction's snapshot is fixed at a defined point and never silently advances. Tradeoff: long transactions hold back vacuum (I7). Violating it produces non-repeatable reads inside a transaction that claims to be repeatable.

P8 — Vacuum never removes a version visible to any live snapshot. Tradeoff: bloat under long-running transactions. Violating it makes rows disappear underneath a reader — worse than the bloat it exists to prevent.

P9 — The B+Tree's structural invariant is checked, not assumed. Every internal key bounds its subtree (I4); property tests walk this after every fuzzed operation sequence. Violating it silently misroutes lookups.

P10 — Every catalog change is itself a transaction. Tradeoff: DDL takes locks like DML (I11). Violating it lets readers observe a half-created table.

P11 — The executor's iterator contract is uniform across every operator. Open/Next/ Close (Graefe 1994) composes regardless of operator kind. Tradeoff: some operators (a hash join's build side) must buffer internally to preserve pull-based semantics. Violating it breaks composability, the entire point of the Volcano model.

P12 — Cost estimates are comparative, not absolute. No cost unit is calibrated to wall-clock time. Violating this principle in practice — "fixing" the optimizer by chasing a number that was never meant to be a duration — produces plans tuned to a meaningless metric.

P13 — Group commit trades latency for throughput on purpose. Tradeoff: a lone transaction under load waits out its batch window (§4). Removing it under load collapses throughput to the single-fsync ceiling.

P14 — Recovery is deterministic and re-runnable. A second crash during recovery must converge to the same state (idempotent redo, CLR-protected undo). Tradeoff: extra CLR bookkeeping during undo. Violating it means recovery from a crash-during-recovery is unbounded in attempts.

Each invariant is exercised, not merely stated: I1/I2/I9/I12 are proven by the crash-injection harness (§28) killing the process at every fsync boundary and asserting post-recovery state; I3/I7/I10 are proven by the schedule-generator plus anomaly-checker (§28, Elle-style history validation); I4/I5 are proven by property tests that fuzz operation sequences and then walk the resulting structure; I8/I13 are proven by differential and adversarial-input tests in the optimizer harness. A violation of any invariant is treated as a correctness incident, not a flaky test — it is re-run deterministically via the crash-injector's seeded RNG before being triaged.

Three-valued logic: every comparison against NULL yields UNKNOWN. AND yields UNKNOWN unless one side is FALSE (which forces FALSE); OR yields UNKNOWN unless one side is TRUE. WHERE/HAVING/JOIN ON treat UNKNOWN as excluding the row. Aggregates skip NULL inputs (COUNT(*) counts rows including all-NULL rows; COUNT(col) skips NULL). GROUP BY treats all NULLs in a column as one group, distinct from any non-NULL value. A UNIQUE index treats every NULL as distinct from every other NULL (SQL standard Part 2), so multiple NULLs are permitted in a unique column; a PRIMARY KEY column may not contain NULL at all (enforced via an implicit NOT NULL).

Cost Model and a Worked Join-Order Example

Cost(Scan) = pages(T) × IO_page_cost. Cost(IndexScan) = height(BTree) × IO_page_cost + selectivity × rows(T) × IO_tuple_cost. Cost(NestedLoop(R,S)) = rows(R) × Cost(S). Cost(HashJoin(R,S)) = rows(R)×CPU_hash + rows(S)×CPU_hash, plus a spill term if rows(R)×row_bytes(R) exceeds the memory budget (ADR-28). Cost(SortMergeJoin(R,S)) = Cost(Sort(R)) + Cost(Sort(S)) + (rows(R)+rows(S))×CPU_merge.

Worked example, three tables: R=Orders (1,000,000 rows), S=Customers (100,000 rows), T=Regions (10 rows); predicates R.cust_id=S.cust_id (selectivity 1/100,000) and S.region_id=T.region_id (selectivity 1/10). System-R/Selinger-style DP over join pairs: (R⋈S) via HashJoin costs ≈1,000,000×CPU_hash + 100,000×CPU_hash ≈1.1M hash ops, producing an estimated 10 result rows (1,000,000 × 1/100,000); (R⋈S)⋈T then costs ≈10×CPU_hash and joins against 10 rows. The DP table retains this order over (S⋈T)⋈R because filtering by region first (10 rows) before joining 1,000,000 orders costs the same asymptotically but the enumerator prefers the plan with the smaller intermediate cardinality at each step — this is exactly the propagation Leis et al. 2015 identify: if the true selectivity of R.cust_id=S.cust_id were mis-estimated as 1/10 instead of 1/100,000, the optimizer would estimate 100,000 intermediate rows instead of 10, and could flip to a SortMergeJoin whose sort cost is paid needlessly — a cardinality-estimation error, not a search-strategy error, producing a slow but still-correct plan (P4, I8).

Offset Field Bytes Notes

Worked insert: page starts with slot_count=3, free_space_ptr=6000 (of 8192); inserting a 140-byte tuple appends slot 3 at offset 20+12=32, writes the tuple at free_space_ptr-140=5860, and sets free_space_ptr=5860. Worked delete: slot 1's tuple is marked deleted by zeroing its length field (I5 still holds — free bytes are not reclaimed until compaction, so free_space_ptr is unchanged and the accounting remains exact for "used vs. never-allocated" bytes). Worked compaction: tuples are copied toward the page end in slot order skipping deleted ones, slot offsets are rewritten to match, and free_space_ptr advances to reflect the reclaimed bytes — done under the page's exclusive latch and logged as a single WAL record so a crash mid-compaction redoes cleanly (I1, I5).

Tuple Encoding

Header: a NullBitmap of ⌈column_count/8⌉ bytes, one bit per column. Fixed-length columns follow in schema order; variable-length columns are stored as (offset:2, length:2) pairs in a trailing directory followed by the actual bytes, so a NULL variable-length column costs only its NullBitmap bit and a zero-length directory entry.

B+Tree Node Layout and Split

InternalNode: page header + [(key_1, child_1), ..., (key_n, child_{n+1})], n+1 children for n keys. LeafNode: page header + [(key_1, rid_1), ..., (key_n, rid_n)] + a next_leaf: PageId sibling pointer (Lehman & Yao 1981). Worked split: a leaf holding the maximum fanout of keys receives one more insert; the leaf allocates a new right sibling, copies the upper half of its entries into it, sets the old leaf's next_leaf to the new page, and posts (separator_key, new_page_id) into the parent — if the parent is itself full this recurses upward, and if the root splits a new root is allocated, increasing tree height by one (I4). Every step is logged before applied (P2) so a crash mid-split redoes to either the pre-split or fully-split state, never a partial one.

ARIES phases, sequence table:

Phase Input Action Output
Analysis WAL from last checkpoint rebuild Dirty Page Table and Active Transaction Table redo start LSN, loser txn list

Undo loser txn list walk prev_lsn chains backward per loser, writing a CLR per undone action all loser effects removed

Worked crash-recovery trace: WAL contains Update(T1,p5,lsn=100), Update(T1,p6,lsn=101), Commit(T1,lsn=102), Update(T2,p5,lsn=103), then the process crashes before T2 commits. Analysis finds T1 committed, T2 active (a loser). Redo replays lsn 100–103 against the pages (p5, p6 both get T1's changes; p5 additionally gets T2's uncommitted change, because redo replays everything regardless of eventual commit — this is "repeating history," Mohan et al. 1992). Undo then walks T2's chain from lsn 103 backward, reverses it, and writes a CLR at a new lsn 104 pointing to T2's original prev_lsn so a second crash during undo does not redo lsn 103 again (P14).

MVCC Version Chain and Visibility

Each row version carries (xmin, xmax, data). Visibility rule for transaction Tq with snapshot S: a version is visible iff xmin is committed and xmin ∈ S.visible_xids and (xmax is null OR xmax is not committed OR xmax ∉ S.visible_xids). Worked schedule: T1 inserts row R (xmin=10); T1 commits; T2 begins, snapshot includes xid 10; T3 begins after T2, updates R (old version xmax=30, new version xmin=30), commits. T2 still sees the pre-update version (xmax=30 is not in T2's snapshot as committed-before); a T4 beginning after T3 commits sees only the new version — this is exactly I3.

Worked write-skew example under snapshot isolation (Berenson et al. 1995): two doctors on-call, constraint "at least one doctor on call." T1 reads {Alice=on, Bob=on}, decides to set Alice=off (she is not the last one on call, since Bob is on in T1's snapshot). T2 concurrently reads the same snapshot and sets Bob=off for the same reason. Both commit under SI — first-committer-wins does not fire because they wrote disjoint rows — leaving zero doctors on call, violating the constraint neither transaction's read set overlapped the other's write set. SSI (Cahill et al. 2008) detects the rw-antidependency cycle and aborts one of the two.

Malformed-Input Examples

  • Syntax error: SELEC * FROM t → ErrorResponse("42601", "unexpected token 'SELEC'", position=0).
  • Type mismatch: WHERE id = 'abc' where id is INT4 → ErrorResponse("42804", ...).
  • Unknown column: SELECT ghost FROM t → ErrorResponse("42703", ...).
  • Unique violation: inserting a duplicate PRIMARY KEY → ErrorResponse("23505", ...).
  • Serialization failure: I10 fires → ErrorResponse("40001", ...), client should retry.
  • Deadlock: WaitsForGraph cycle → ErrorResponse("40P01", ...).
  • WAL record with a bad checksum: recovery halts that page's redo and flags it (FM-6, §25).
  • Torn write: page checksum mismatch on read → page reconstructed from WAL if possible, else surfaced as ErrorResponse("XX001", "data corruption").

Failure-Path Example

A client sends UPDATE accounts SET balance = balance - 100 WHERE id = 1 inside a transaction that never commits before the connection drops. The session manager's drop handler issues an implicit ROLLBACK; the transaction manager marks the txn aborted in the commit log; no redo of its Update records occurs on a later crash because Analysis finds it uncommitted (I2). No client-visible error is needed — this is the normal, correct path.

12. Phase 0 — Skeleton, Pager, Slotted Pages, and CI

12.1 Objectives

Stand up the workspace skeleton (crates from §1), CI gates (ADR-36), and the pager and slotted-page primitives every later phase depends on.

12.2 Detailed Implementation Steps

  1. Initialize the Cargo workspace per §10; wire clippy and cargo-deny into ci.yml (ADR-36).
  2. Implement Pager (§11): page allocation via a free-page bitmap, read_page/ write_page/fsync (P1, I1).
  3. Implement the slotted-page layout (§8 byte-layout table): PageHeader, slot array, insert/delete/compaction (P5, I5).
  4. Implement per-page CRC32C checksums on write, verified on read (ADR-32, T7).
  5. Stand up the property-testing harness (proptest) and the crash-injection scaffold in sqldb-harness, establishing the seam early even though no WAL exists yet (groundwork for P14).
  6. Stand up criterion-based benchmarking for page-level operations.

12.3 Deliverable

A standalone sqldb-storage library where a raw byte tuple can be inserted into a page, read back, deleted, and compacted, with every operation preserving I5's free-space accounting.

12.4 Acceptance Criteria

  • Property test page_free_space_invariant passes 100,000 randomized insert/delete/ compaction sequences with zero I5 violations.
  • corrupt_page_detected.rs detects 100% of 1,000 deliberately corrupted pages via CRC32C.
  • ci.yml green on stable and nightly Rust with clippy at zero warnings.

12.5 Conformance Fixtures

  • fixtures/page_insert_delete_compact.rs — insert 50 tuples, delete 20, compact, assert byte-identical slot contents to a hand-computed expected layout.
  • fixtures/page_checksum_corruption.rs — flip a random bit, assert checksum mismatch.
  • fixtures/page_overflow_reject.rs — insert a tuple larger than free space, assert a clean error, never a panic.

12.6 Pitfalls

  • Off-by-one in free_space_ptr after compaction: manifests as a later insert silently overwriting live tuple bytes; root cause is forgetting the slot array's own growth; debug via the page_free_space_invariant property test; signal is page_free_space_mismatches_total > 0; no recovery at this phase, fix and re-run.
  • Checksum computed over the checksum field itself: manifests as every page failing verification; root cause is field-ordering in the checksum computation; debug with a known-good-page unit test; signal is a 100% false-positive corruption rate.
  • Free-page bitmap desync from actual allocations: manifests as two HeapFiles claiming the same PageId; root cause is a non-atomic bitmap update; debug via an allocation-fuzz property test; recovery is rebuilding the bitmap by a full page scan.

12.7 Performance Concerns

Page-level insert must stay O(1) amortized (P5); compaction is O(slot_count) and must run only when free space is fragmented, not on every delete, or delete throughput collapses.

12.8 Edge Cases

An empty page (slot_count=0); a fully packed page (zero free space); a tuple exactly equal to remaining free space; a page whose slots are all deleted (compaction to empty).

12.9 Failure Analysis

FM-class: a torn write during a page write (fewer than 8 KiB reach disk before a crash). Detection: checksum mismatch on next read. Recovery: none until Phase 8's WAL exists — Phase 0 pages are not yet crash-safe, PhaseDeferred("§21 Phase 9") covers durable repair; this phase only guarantees detection.

12.10 Operational Notes

tools/page-dump (§10) is built in this phase to print a page's header and slot array for debugging; every later phase's runbooks depend on it.

13. Phase 1 — Heap File, Tuple Encoding, and Sequential Scan

13.1 Objectives

Compose Phase 0's pages into a HeapFile, define the tuple encoding (§8), and deliver a sequential-scan access method.

13.2 Detailed Implementation Steps

  1. Implement HeapFile (§11) as a chain of pages linked by PageId, with a per-table free-space map for fast insert placement (ADR-06).
  2. Implement tuple encoding: NullBitmap header, fixed-length fields, then the variable-length directory and bytes (§8 tuple encoding).
  3. Implement TupleId/Rid as (page_id, slot_id), the stable row identity later indexes point to (§11).
  4. Implement a SeqScan access method: an Executor (P11) that walks the heap file's pages in order, decoding each slot's tuple via TupleDesc.
  5. Implement INSERT and DELETE at the storage layer (no SQL yet — direct API calls), updating the free-space map (ADR-06) and page free-space accounting (I5).

13.3 Deliverable

A library where raw tuples can be inserted into a named heap file via a Rust API and scanned back in insertion order, byte-identical, with deletes correctly skipped.

13.4 Acceptance Criteria

  • heap_scan_roundtrip.rs: insert 1,000,000 tuples, scan back, byte-identical to input — 0 mismatches.
  • Insert throughput ≥150,000 rows/sec single-threaded on the benchmark harness (§4).
  • NullBitmap round-trips correctly for a table where every column is nullable, verified across all 2^8 bitmap patterns for an 8-column fixture.

13.5 Conformance Fixtures

  • fixtures/tuple_null_bitmap_roundtrip.rs — every combination of NULL columns for a fixed 8-column schema.
  • fixtures/heap_scan_after_delete.rs — delete every third tuple, scan, assert exact survivor set.
  • fixtures/heap_file_growth.rs — insert past a single page's capacity, assert a new page is correctly linked.

13.6 Pitfalls

  • Variable-length directory offsets computed before the fixed-length region's size is finalized: manifests as corrupted string reads; root cause is encoding order; debug via the null-bitmap-roundtrip fixture; signal is garbage Text values.
  • Free-space map going stale after a page fills via a different code path (e.g. direct index insert): manifests as repeated failed placement attempts; debug via free-space-map consistency assertions; recovery is rebuilding the map by scanning the heap file.
  • Forgetting that a deleted slot's TupleId must never be reused while any index still references it: manifests as an index pointing to an unrelated new tuple; root cause is premature slot reuse; debug via a dangling-Rid property test; this is precisely why vacuum (Phase 10) is a distinct, careful operation rather than immediate reclamation.

13.7 Performance Concerns

Sequential scan throughput is bounded by buffer-pool hit ratio (not yet built — Phase 0 pages are read directly in this phase) and by tuple-decode cost; the free-space map lookup must stay O(1) amortized to keep insert throughput at the §4 target.

13.8 Edge Cases

A table with zero rows (scan returns immediately); a table where every row is deleted (scan returns immediately after skipping every slot); a row whose variable-length field is empty string versus NULL (distinct encodings, both zero-length).

13.9 Failure Analysis

FM-class: a heap-file page-chain pointer to a PageId beyond the file's current allocation (corruption or a bug in Phase 0's allocator). Detection: scan halts with a bounds-check error rather than reading unallocated space. Recovery: none yet — Phase 9's recovery manager is the eventual repair path; this phase's contract is fail-fast, not fail-silent.

13.10 Operational Notes

tools/page-dump is extended to follow the heap-file page chain and print per-page slot occupancy, used to diagnose insert-throughput regressions later.

14.1 Objectives

Turn SQL text into a typed AST via a hand-written lexer and a recursive-descent/Pratt parser (ADR-21), covering the grammar in §8.

14.2 Detailed Implementation Steps

  1. Implement the Token/TokenKind lexer: identifiers (with quoting), string escapes, numeric literals, comments, operators — attaching byte-offset pos to every token for error reporting (§8 malformed-input examples).
  2. Implement the recursive-descent parser for statements per the EBNF in §8.
  3. Implement the Pratt/precedence-climbing expression parser matching the precedence table in §8 exactly.
  4. Build the Ast node hierarchy (§11): Select, Insert, Update, Delete, CreateTable, DropTable, CreateIndex, DropIndex, Begin, Commit, Rollback, Explain.
  5. Implement scalar, IN, and EXISTS subquery parsing (nested select_stmt per §8 grammar), deferring decorrelation to the binder (Phase 3).
  6. Fuzz the lexer and parser from day one (ADR-35) — this is a stated primary fuzz target (T3).

14.3 Deliverable

A sqldb-parser library that turns any string into either a well-formed Ast or a positioned SqlError, never a panic, for the full grammar in §8.

14.4 Acceptance Criteria

  • parser_conformance.sqllogictest: 500 hand-written SQL statements covering every grammar production parse to the expected Ast shape.
  • Fuzz target fuzz_targets/parser.rs survives 1,000,000 executions with zero panics (libFuzzer/cargo-fuzz crash count = 0).
  • Every syntax-error fixture reports the correct byte position (§8 malformed-input examples), verified exactly, not approximately.

14.5 Conformance Fixtures

  • fixtures/parser_valid_statements.sql — one example per grammar production.
  • fixtures/parser_syntax_errors.sql — 30 malformed inputs with expected (sqlstate, position) pairs.
  • fixtures/parser_precedence.sql — expressions exercising every precedence level, asserting the resulting AST's operator nesting.

14.6 Pitfalls

  • Precedence-climbing off-by-one collapsing AND/OR associativity: manifests as a OR b AND c parsing as (a OR b) AND c instead of a OR (b AND c); debug via the precedence fixture; root cause is an inverted binding-power comparison.
  • String-escape handling diverging between the lexer and the eventual Datum::Text decoder: manifests as a round-trip mismatch on any string containing a quote; debug via a lexer-unit round-trip test.
  • Recursive-descent stack overflow on deeply nested parenthesized expressions from a malicious client: manifests as a crash, not a clean error (T2); mitigation is an explicit recursion-depth counter with a bounded error, not relying on the OS stack guard.

14.7 Performance Concerns

Parsing must not dominate short-query latency (§4 point-lookup p50 is 80µs); the lexer must avoid per-token heap allocation on the hot path where feasible.

14.8 Edge Cases

An empty statement; a statement that is only whitespace/comments; a string literal containing every ASCII control character; an identifier at the maximum supported length; a deeply nested subquery at the recursion-depth boundary (T2's DoS surface, mitigated here).

14.9 Failure Analysis

FM-class: adversarial input causing unbounded parser recursion (T2, ADR context). Detection: the recursion-depth counter trips before a stack overflow. Recovery: return ErrorResponse("54001", "statement too complex"), no crash, no partial state.

14.10 Operational Notes

The fuzz corpus built in this phase (fuzz/corpus/parser/) is retained and grown across every later phase — regressions here are cheap to catch and expensive to debug once they reach the binder.

15. Phase 3 — Catalog, Binder, and Type Checking

15.1 Objectives

Bootstrap the catalog (§8 catalog schema), implement the semantic analyzer/binder that turns an Ast into a BoundExpr tree, and enforce the type system of §8.

15.2 Detailed Implementation Steps

  1. Hand-construct the four sys_* catalog tables (§8) as heap tables at first Database::open, before any SQL statement can run — the bootstrap problem (ADR-31).
  2. Implement CREATE TABLE/DROP TABLE/CREATE INDEX/DROP INDEX as ordinary transactions writing to the catalog (P10, I11).
  3. Implement the binder: resolve ident references against Catalog, producing (TableId, col_id, SqlType) triples; reject unknown tables/columns and ambiguous references (§8 malformed-input examples, SQLSTATE 42703).
  4. Implement type checking and implicit-cast insertion per the coercion table in §8; reject illegal coercions (SQLSTATE 42804).
  5. Implement three-valued-logic evaluation rules for BoundExpr (§8): NULL propagation, AND/OR/NOT truth tables.
  6. Implement subquery decorrelation for the equality-correlated case (§8 equivalence rules), producing a join BoundExpr shape the binder hands to the planner in Phase 4.

15.3 Deliverable

A sqldb-catalog + binder pipeline where any Ast from Phase 2 either becomes a fully-typed BoundExpr/DDL-effect ready for planning, or a positioned SqlError.

15.4 Acceptance Criteria

  • binder_conformance.sqllogictest: 300 statements covering every coercion-table entry and every three-valued-logic combination, matching expected typed output.
  • ddl_transactional.rs: a concurrent-schedule test proving I11 — a reader never observes a CREATE TABLE mid-flight (0 violations across 10,000 randomized schedules).
  • Every SQLSTATE in §8's malformed-input list (42601, 42804, 42703, 23505 deferred to Phase 6/10) is reachable and exactly matched by a fixture.

15.5 Conformance Fixtures

  • fixtures/binder_type_coercion.sql — one case per coercion-table row, valid and invalid.
  • fixtures/binder_three_valued_logic.sql — every NULL-involving AND/OR/NOT/ comparison combination against the truth table in §8.
  • fixtures/catalog_bootstrap.rs — fresh Database::open produces the four sys_* tables with the exact expected rows.
  • fixtures/ddl_concurrent_visibility.rs — the I11 concurrent-schedule test.

15.6 Pitfalls

  • Treating catalog metadata as a special non-transactional cache instead of ordinary MVCC-versioned rows: manifests as I11 violations under concurrent DDL; root cause is bypassing the version chain for "performance"; debug via the DDL concurrent-visibility fixture; this is the single most common shortcut that breaks P10.
  • Implicit casts inserted in the wrong direction (widening a comparison operand instead of the literal): manifests as silently wrong WHERE results, not an error; debug via the type-coercion fixture's expected-plan assertions.
  • GROUP BY NULL handling implemented as "skip NULL groups" instead of "one NULL group": manifests as missing rows in aggregate output; root cause is confusing NULL's aggregate- input semantics with its GROUP BY semantics (§8 explicitly distinguishes them).

15.7 Performance Concerns

Catalog lookups are on the hot path for every statement; Catalog must support O(1) lookup by name and must not require a full table scan of sys_tables per query — an in-memory index over the MVCC-versioned catalog snapshot is required.

15.8 Edge Cases

A column named identically to a SQL keyword (must be quotable); a table with the maximum 1,600 columns (§4); a DEFAULT expression referencing another column (rejected — defaults are constant-only in Phase 0); a UNIQUE column holding multiple NULLs (§8, permitted).

15.9 Failure Analysis

FM-class: a crash during a DDL transaction between the catalog write and its commit record. Detection: recovery's analysis phase finds the DDL txn uncommitted. Recovery: I2 applies unchanged — the partial catalog write is undone like any other transaction's effects, because DDL is P10's "just another transaction."

15.10 Operational Notes

docs/adr/ADR-31.md documents the bootstrap sequence precisely, since it is the one place in the system where code, not a transaction, constructs initial catalog rows — every future catalog-format change (§27) must account for re-running or migrating this bootstrap.

17. Phase 5 — Joins, Aggregation, and Sorting with Spill

17.1 Objectives

Extend the executor with join, aggregate, and sort operators, including disk spill for memory-bounded operation (ADR-27, ADR-28).

  1. Implement NestedLoopJoin (baseline correctness reference for I8's differential tests).
  2. Implement HashJoin with a build-side hash table; add spill-to-disk when the build side exceeds the memory budget (ADR-28, cost equations in §8).

  5. Implement external merge sort: partition into memory-sized runs, sort each in memory, multi-way merge the runs (ADR-28); used by both Sort and SortMergeJoin.
  6. Implement LEFT OUTER JOIN semantics for all three join algorithms (unmatched left rows paired with all-NULL right side).

17.3 Deliverable

TPC-H-style multi-table join-and-aggregate queries execute correctly end-to-end, including on datasets exceeding the configured memory budget (forcing spill).

17.4 Acceptance Criteria

  • join_algorithm_equivalence.rs: NestedLoopJoin, HashJoin, and SortMergeJoin return identical tuple multisets on 200 fixture queries — I8 exercised across three physical choices for the same logical join, 0 mismatches.
  • spill_correctness.rs: a join/sort forced to spill (dataset 10× the memory budget) returns results identical to an unbounded in-memory run, verified on 50 fixtures.
  • aggregate_null_semantics.sqllogictest: every NULL-involving aggregate case from §8 matches expected output exactly.

17.5 Conformance Fixtures

  • fixtures/join_three_algorithms.sql — the same 200 join queries run through all three physical operators.
  • fixtures/spill_forced_large_join.rs — a synthetic dataset sized to force spill under the §4 memory budget.
  • fixtures/aggregate_group_by_null.sql — GROUP BY over a column with NULL values, asserting one NULL group.

17.6 Pitfalls

  • Hash join build side not accounting for hash-table overhead when deciding to spill: manifests as an OOM instead of a clean spill; root cause is estimating memory by row bytes alone; debug via the spill-correctness fixture at the exact budget boundary.
  • External merge sort's final merge pass not being truly external (buffering all runs in memory "just this once"): manifests as an OOM on the largest fixture only; root cause is an off-by-one in the multi-way-merge buffer sizing; debug via a monotonically increasing dataset-size sweep.
  • LEFT OUTER JOIN implemented by post-hoc null-padding after an inner join computes matches, but failing to null-pad rows with zero matches at all: manifests as missing left rows instead of null-padded ones; debug via a fixture with a guaranteed zero-match left row.

17.7 Performance Concerns

Cost equations in §8 predict HashJoin beats NestedLoopJoin once the outer side exceeds a few thousand rows; the join-algorithm-equivalence fixture is also the performance regression gate — the DP-based optimizer in Phase 11 depends on these cost equations being accurate relative to each other, per P12.

17.8 Edge Cases

A join where one side is empty (result is empty for inner, all-null-padded for left outer); an aggregate with no GROUP BY and zero input rows (COUNT returns 0, SUM returns NULL, per SQL standard); a sort key containing NULL (sorts first or last per a stated, fixed convention — nulls-first is locked here).

17.9 Failure Analysis

FM-class: spill file left on disk after a crash mid-join. Detection: a startup sweep of the spill directory against the active-transaction table. Recovery: orphaned spill files (belonging to no active or recovering transaction) are deleted at startup — they hold no committed state, only transient intermediate results (P1 — durability is defined by the WAL, spill files are never WAL-logged).

17.10 Operational Notes

docs/runbooks/slow-plan-triage.md gains a section on diagnosing spill via tools/plan-explain's spill-event counter, ahead of the optimizer's cost-based avoidance of unnecessary spill in Phase 11.

18.1 Objectives

18.2 Detailed Implementation Steps

  1. Implement BTreeNode/LeafNode/InternalNode over Phase 0's pages (§8, §11).
  2. Implement point lookup and range scan via leaf-sibling traversal (Lehman & Yao 1981).
  3. Implement insert with split (§8 worked split example), logging the split before applying it (P2) so recovery can redo/undo a partial split.
  4. Implement delete with merge/redistribute, symmetric to split, equally logged.
  5. Implement latch-crabbing descent per ADR-08: read latches released as soon as a child is latched, write latches retained up to the split point only.
  6. Wire CREATE INDEX/DROP INDEX (Phase 3's DDL) to build/discard a BTree and update sys_indexes (I11).
  7. Implement IndexScan as an Executor (P11), giving the planner (Phase 11) a second access method to choose between.

18.3 Deliverable

Point and range queries execute via IndexScan against a CREATE INDEX-created B+Tree, concurrently correct under mixed read/write load.

18.4 Acceptance Criteria

  • btree_balanced_ordered.rs (property test): after 100,000 randomized insert/delete operations, every leaf is visited in strictly increasing key order and every internal key bounds its subtree — I4, 0 violations.
  • btree_concurrent_stress.rs: 32 threads performing random inserts/deletes/lookups for 10 minutes with zero panics, zero lost updates, and I4 holding at every checkpoint.
  • Point-lookup latency meets the §4 target (p50 80µs) on a tree of 10,000,000 keys.

18.5 Conformance Fixtures

  • fixtures/btree_split_worked_example.rs — the exact §8 worked split, asserting the new right sibling's contents and the parent's new separator key.
  • fixtures/btree_merge_underflow.rs — deletes reducing a leaf below the minimum fanout, asserting a correct merge or redistribution.
  • fixtures/btree_range_scan_sibling_chain.rs — a range scan crossing multiple leaves via next_leaf pointers.

18.6 Pitfalls

  • Releasing a parent's latch before the child's split is fully posted: manifests as a concurrent reader briefly seeing an inconsistent parent — this is exactly why latch-crabbing's ordering (child latched before parent released) matters; debug via the concurrent-stress fixture with latch-order assertions enabled.
  • Logging the split's two halves as two separate WAL records without a chain linking them: manifests as a crash between the two records leaving the tree in a state where the parent points to a not-yet-created child; root cause is not treating the split as one atomic logged unit; debug via crash-injection at every WAL-write point within a split.
  • Off-by-one in leaf minimum-fanout check triggering merge one level too early/late: manifests as excessive merge/split thrashing under a specific insert/delete pattern; debug via the merge-underflow fixture swept across boundary fanout values.

18.7 Performance Concerns

Height determines page-reads-per-lookup (§34); latch contention on the root and near-root internal nodes is the primary scalability bottleneck (§31) — this is why the top levels stay resident in the buffer pool under any reasonable hit-ratio target (§4).

18.8 Edge Cases

A tree with a single leaf (no internal nodes yet); a tree where every key is a duplicate (secondary, non-unique index); a delete that empties the tree back to a single empty leaf; an insert that triggers a cascade of splits up to and including a new root.

18.9 Failure Analysis

FM-class: a crash mid-split leaves a child page fully formed but the parent not yet updated. Detection: recovery's redo phase replays the logged split record, completing the parent update (I1/I2 apply to structural index changes exactly as to data changes). Recovery: automatic via ARIES redo (Phase 9) — no manual intervention once Phase 9 exists; until then (mid-Phase-6 development), this is a known gap tracked as FM-3 in §25.

18.10 Operational Notes

tools/page-dump gains a --btree mode to print a node's key range and child pointers; docs/runbooks/corrupt-page.md gains a B+Tree-specific triage section (broken sibling chain, mis-ordered keys) distinct from heap-page corruption.

19. Phase 7 — The Buffer Pool with a Replacement Policy and Pin Discipline

19.1 Objectives

Insert the BufferPool (§11) between every pager call made by heap files and B+Trees so far, enforcing pin/latch discipline via PinGuard's ownership (P6).

19.2 Detailed Implementation Steps

  1. Implement BufferPool: page_table: PageId → frame index, Frame with pin count and dirty bit (§11).
  2. Implement clock-sweep replacement (ADR-09): a reference bit per frame, a sweep pointer advancing on eviction pressure.
  3. Implement PinGuard<'a> as an RAII type whose Drop decrements the pin count; make Frame::evict take &mut self in a way the borrow checker rejects while any PinGuard exists (P6 — this is the load-bearing Rust-specific design choice from §1).
  4. Retrofit HeapFile and BTree to route every page access through BufferPool::fetch/ unpin instead of Pager directly (Pager becomes buffer-pool-internal only).
  5. Implement flush_page/flush_all respecting I1 — never flush a page whose LSN exceeds WalWriter::last_flushed_lsn (this ordering check is written now even though the WAL itself lands in Phase 8, as a documented PhaseDeferred("§20 Phase 8") stub that always returns "flush permitted" until the WAL exists).
  6. Add buffer-pool metrics: hit ratio, eviction rate, dirty-page count (§26).

19.3 Deliverable

Every existing heap-file and B+Tree operation from Phases 1 and 6 now runs through the buffer pool, with pin/latch violations caught at compile time, not runtime.

19.4 Acceptance Criteria

  • buffer_pool_no_evict_while_pinned.rs: a test attempting to evict a pinned page fails to compile (a compile_fail doctest) — P6 proven statically, not just tested.
  • buffer_pool_hit_ratio.rs: the TPC-C-like workload from §4 achieves ≥95% hit ratio at the configured pool size.
  • clock_sweep_fairness.rs: no single frame is starved of eviction consideration over 10,000 sweep cycles under skewed access patterns.

19.5 Conformance Fixtures

  • fixtures/pin_guard_prevents_eviction.rs — a compile_fail test asserting P6.
  • fixtures/buffer_pool_eviction_order.rs — a scripted access pattern with a known expected eviction order under clock-sweep.
  • fixtures/dirty_page_flush_ordering.rs — asserts I1's LSN check blocks a premature flush (using the Phase 7 stub ordering check).

19.6 Pitfalls

  • PinGuard implemented as a plain counter increment/decrement without tying it to a Rust lifetime: manifests as P6 becoming a runtime-only convention again, exactly the failure mode this design exists to prevent; debug via attempting (and expecting to fail) the compile-time eviction test.
  • Clock-sweep reference bit never cleared on a hit, degenerating to random eviction: manifests as a hit-ratio regression under a workload with clear hot/cold pages; debug via the hit-ratio fixture with a synthetic skewed access trace.
  • Double-fetching the same page into two different frames due to a race in page_table lookup-then-insert: manifests as two frames diverging on writes to "the same" page; root cause is a non-atomic check-then-act on the page table; debug via a concurrent fetch-stress test.

19.7 Performance Concerns

Buffer-pool hit ratio is one of the two leading operational indicators (§26); frame-latch granularity (per-frame, not global) is required to let concurrent B+Tree crabbing (ADR-08) proceed without serializing on the whole pool.

19.8 Edge Cases

A working set larger than the buffer pool (steady-state eviction pressure); a single page pinned by multiple concurrent readers simultaneously; a pool size of one frame (degenerate but must not deadlock).

19.9 Failure Analysis

FM-class: buffer-pool deadlock from two threads each holding one frame's latch and waiting on the other's (a classic latch-ordering bug, distinct from the transaction-level deadlocks of §22). Detection: a latch-wait timeout in debug builds. Recovery: fix via a documented global latch-acquisition order (e.g., always latch lower PageId first in any multi-frame operation) — the rule is stated once here and referenced by every later phase touching more than one frame at a time.

19.10 Operational Notes

buffer_pool_hit_ratio and oldest_snapshot_age_seconds (Phase 10) are named in §26 as the two leading indicators; this phase's metrics export is the first half of that pair.

20. Phase 8 — The Write-Ahead Log and Group Commit

20.1 Objectives

Implement WalWriter/WalRecord (§8, §11) and group commit (ADR-13), making I1 and I9 real enforcement points rather than the Phase 7 stub.

20.2 Detailed Implementation Steps

  1. Implement the WalRecord byte layout exactly as specified in §8 (lsn, prev_lsn, txn_id, record_type, page_id, before/after images per ADR-11).
  2. Implement WalWriter::append assigning a monotonic Lsn (I9) and buffering records until a group-commit trigger fires (§4: 2ms or 32 pending commits).
  3. Implement the WAL rule for real: BufferPool::flush_page now calls WalWriter::last_flushed_lsn and refuses to flush a page whose LSN exceeds it, forcing a WAL flush first (I1 — replacing the Phase 7 always-permit stub, per its documented PhaseDeferred).
  4. Implement Commit/Abort records and wire Transaction::commit to append a Commit record and block on its group's fsync before returning success to the client (P1).
  5. Implement fuzzing of the WAL decoder (ADR-35, T7) — a malformed or truncated record must be detected, never misinterpreted as a different record.
  6. Instrument WAL bytes/sec and fsync latency (§26).

20.3 Deliverable

Every mutation from Phases 1–6 now produces a WAL record before its page is flushable, and a transaction's commit is defined exactly as its Commit record's fsync completing.

20.4 Acceptance Criteria

  • wal_rule_enforced.rs: attempting to flush a page ahead of its WAL record is rejected in 100% of 10,000 randomized page/WAL orderings (I1).
  • group_commit_throughput.rs: commit throughput at 32-way concurrency matches the §34 batch-size/fsync-latency formula within 10%.
  • wal_decoder_fuzz: 1,000,000 fuzz executions on truncated/corrupted WAL bytes, zero panics, zero misinterpretation as a different valid record (T7).

20.5 Conformance Fixtures

  • fixtures/wal_record_roundtrip.rs — encode/decode every WalRecordType variant.
  • fixtures/group_commit_batching.rs — scripted concurrent commits asserting batch boundaries match the configured window.
  • fixtures/wal_bad_checksum.rs — a WAL record with a corrupted checksum is rejected cleanly (§8 malformed-input example).

20.6 Pitfalls

  • Assigning the LSN after buffering instead of at append time: manifests as records written out of LSN order within a batch, breaking I9; debug via the WAL-rule-enforced fixture with LSN-ordering assertions.
  • Group commit's batching trigger racing with Transaction::commit's wait, so a transaction's fsync completes but its thread is never woken: manifests as a hung commit under load; root cause is a lost-wakeup bug in the batch-completion notification; debug via a concurrency-stress test with a bounded commit-latency assertion (a stuck commit fails the test, not just runs slow).
  • Treating fdatasync as sufficient without verifying metadata (file length) is also synced when a page write extends the file: manifests as data loss for the last-appended page specifically after a crash — this is the "lying fsync" class named in T7, and the mitigation is using fsync (not fdatasync) whenever the file has grown.

20.7 Performance Concerns

Fsync is the dominant commit-path cost (§4, §30) — group commit's whole purpose is amortizing it (P13); batching too aggressively (a large window) trades latency for throughput past the point of diminishing returns, so the window is tuned, not maximized.

20.8 Edge Cases

A single transaction committing with no concurrent commits (pays the full fsync latency alone); a batch at exactly the 32-commit boundary; a commit racing a checkpoint (must not be missed by either the checkpoint's dirty-page table or the commit's own durability).

20.9 Failure Analysis

FM-class: fdatasync returning success while the underlying device lied about durability (power loss still loses the write) — an environment fault, not a software bug. Detection: none possible from software alone; mitigation is documented as an operational prerequisite (use of devices honoring FLUSH CACHE, per T7's threat-model entry) rather than a code fix. Recovery: none — this is why RPO in §4 is stated per durability setting, not as an absolute guarantee.

20.10 Operational Notes

docs/runbooks/wal-growth.md begins here, covering WAL bytes/sec monitoring and the checkpoint-triggering thresholds finalized in Phase 9.

21. Phase 9 — ARIES Recovery: Analysis, Redo, and Undo

21.1 Objectives

Implement the RecoveryManager (§8 ARIES sequence table, §11 RecoveryState), making I2 and I12 hold across an arbitrary crash.

21.2 Detailed Implementation Steps

  1. Implement fuzzy checkpointing (§8, ADR-14): periodically snapshot the Dirty Page Table and Active Transaction Table into a CheckpointRecord, flush dirty pages in the background without pausing transactions (I12).
  2. Implement the Analysis phase: scan the WAL from the last checkpoint, rebuild DPT and ATT, determine the redo start LSN and the loser-transaction set (Mohan et al. 1992).
  3. Implement the Redo phase: replay every logged action whose page LSN predates the record's LSN, "repeating history" unconditionally regardless of eventual commit status (§8 worked trace).
  4. Implement the Undo phase: walk each loser's prev_lsn chain backward, reverse its effect, and write a Compensation Log Record (CLR) for each undone action so a second crash mid-undo does not redo it again (P14).
  5. Wire RecoveryManager to run automatically on Database::open before any query is accepted.
  6. Build the crash-injection harness (sqldb-harness, ADR-34): kill the process at every fsync boundary across a scripted workload, restart, and assert I2.

21.3 Deliverable

A workload can be crash-injected at any WAL-write point and, after restart, every committed transaction's effects are present and every uncommitted transaction's effects are absent, with zero exceptions across the crash-injection suite.

21.4 Acceptance Criteria

  • crash_injection_suite.rs: 1,000 injected crash points across a mixed workload, 0 committed-transaction losses and 0 uncommitted-transaction leaks (I2) — the named crash-injection test this blueprint's §1 goal statement is written to satisfy.
  • aries_worked_trace.rs: reproduces the exact §8 worked crash-recovery trace, asserting the precise set of replayed and undone records.
  • Recovery time for a 1 GiB WAL meets the §4 target (≤30 seconds).

21.5 Conformance Fixtures

  • fixtures/crash_at_every_fsync.rs — the crash-injection suite's scripted workload.
  • fixtures/checkpoint_then_crash.rs — I12's fixture, crashing immediately after a checkpoint completes.
  • fixtures/aries_analysis_redo_undo_trace.rs — the worked trace from §8.
  • fixtures/double_crash_during_recovery.rs — a second injected crash during the undo phase itself, asserting convergence (P14).

21.6 Pitfalls

  • Undo not itself being logged (writing CLRs): manifests as a second crash during undo re-undoing an already-undone action, corrupting further; this is precisely why P14 exists and why ARIES was chosen over shadow paging (ADR-15).
  • Checkpoint's Dirty Page Table snapshot taken non-atomically with the actual dirty-page set, violating I12: manifests as a page missed by redo after a checkpoint; debug via the checkpoint-then-crash fixture.
  • Redo phase skipping a record because the "transaction eventually aborted" — violates the repeating-history principle and produces I2 violations; the fix is that redo is unconditional and undo alone is transaction-status-aware.

21.7 Performance Concerns

Recovery time is linear in WAL bytes since the last checkpoint (§31, §34); checkpoint frequency is the primary lever — too rare and recovery time grows unbounded, too frequent and checkpointing's background page-flush pressure competes with foreground I/O.

21.8 Edge Cases

A crash during the checkpoint record's own write; a crash with zero active transactions (recovery is a no-op); a crash where the WAL file itself is truncated mid-record (the last partial record is discarded, not treated as corruption); recovery encountering a record for a page that no longer exists (table was dropped — the record is skipped, not an error).

21.9 Failure Analysis

FM-class: recovery itself crashes partway through undo. Detection: the next Database::open re-runs Analysis, which finds the CLRs already written and correctly resumes undo from where it left off (P14, double_crash_during_recovery fixture). Recovery: automatic, no manual intervention — this is the defining property ARIES buys over ad hoc recovery schemes.

21.10 Operational Notes

docs/runbooks/crash-recovery.md is the primary on-call document from this phase forward; it references the crash-injection suite as the source of truth for "is recovery healthy," not manual reasoning about a specific incident.

22. Phase 10 — MVCC Snapshot Isolation, the Version Store, and Vacuum

22.1 Objectives

Implement VersionChain/Snapshot (§8, §11), the visibility rule, Read Committed and Repeatable Read isolation, first-committer-wins conflict detection, and the vacuum/GC worker (I6, I7).

22.2 Detailed Implementation Steps

  1. Implement per-row (xmin, xmax, data) version chains (§8), threaded through the existing heap-page tuple encoding from Phase 1 (an update creates a new version, does not overwrite in place — ADR-17's in-place-plus-undo-chain variant, specified precisely here as: the current version is stored in place, prior versions are chained via an undo pointer, matching InnoDB's contrast named in §33).
  2. Implement Snapshot construction: capture the active-transaction set at BEGIN/first-statement time depending on isolation level (P7).
  3. Implement the visibility rule (§8 display equation) as the single function every scan operator (SeqScan, IndexScan) consults per candidate version.
  4. Implement Read Committed (new snapshot per statement) and Repeatable Read (one snapshot per transaction) by varying only when Snapshot is constructed — both share the same visibility rule (I3).
  5. Implement first-committer-wins: on UPDATE/DELETE, check whether the target row's current xmax was set by a transaction not visible to the writer's snapshot; if so, abort with a serialization failure (I10, SQLSTATE 40001).
  6. Implement the vacuum/GC background worker: compute the oldest active snapshot's xid horizon, reclaim versions strictly older than it (I7), and update oldest_snapshot_age_seconds (§26).
  7. Implement SSI-lite for the Serializable level: track rw-antidependencies between concurrent transactions (Cahill et al. 2008) and abort one side of a detected dangerous structure (the §8 write-skew worked example is the acceptance fixture).

22.3 Deliverable

Concurrent transactions at Read Committed, Repeatable Read, and Serializable all observe exactly the anomaly set the isolation-level table in §8 states, verified by an anomaly-schedule checker, with vacuum reclaiming space without ever violating I7.

22.4 Acceptance Criteria

  • isolation_anomaly_matrix.rs: for each of the three offered levels, an Elle-style history checker confirms exactly the anomalies §8's table permits and none of the ones it prevents, across 5,000 randomized concurrent schedules per level.
  • write_skew_ssi.rs: reproduces the exact §8 doctors-on-call write-skew schedule; under Repeatable Read (SI) both commit (anomaly present, as expected); under Serializable, one aborts with SQLSTATE 40001 (anomaly prevented).
  • vacuum_never_removes_visible.rs: a long-running reader holds a snapshot while a concurrent writer creates and vacuum reclaims versions; the reader's results never change mid-transaction and never error — 0 violations across 10,000 iterations (I7).

22.5 Conformance Fixtures

  • fixtures/visibility_rule_worked_schedule.rs — the exact §8 four-transaction worked schedule.
  • fixtures/write_skew_doctors_on_call.sql — the §8 write-skew example, run at both SI and Serializable.
  • fixtures/vacuum_horizon_tracking.rs — asserts the reclaim horizon matches the oldest active snapshot's xid exactly, not approximately.
  • fixtures/first_committer_wins.rs — two concurrent updates to the same row, asserting exactly one serialization failure.

22.6 Pitfalls

  • Computing the vacuum horizon from the oldest committed transaction instead of the oldest active snapshot: manifests as I7 violations — a long-running reader's in-progress snapshot is not "committed" and must still hold back reclamation; this is the single most consequential MVCC bug class (P8).
  • Read Committed accidentally sharing one Snapshot per transaction instead of constructing a fresh one per statement: manifests as Read Committed behaving like Repeatable Read, silently offering stronger isolation than requested — which sounds harmless but breaks application code relying on RC's per-statement freshness (e.g., re-reading a counter mid-transaction).
  • SSI's rw-antidependency tracking implemented only for read-then-write conflicts and missing write-then-read: manifests as some write-skew schedules still committing both sides under "Serializable" — debug via an expanded write-skew fixture set beyond the doctors-on-call canonical case.

22.7 Performance Concerns

Version-chain length is bounded by vacuum throughput relative to write rate (§4, §34); a long-running transaction is not merely slow, it is a storage leak (MM3, §32) — vacuum backlog is monitored as a first-class metric (§26), not an afterthought.

22.8 Edge Cases

A transaction that reads a row, then the row is deleted and vacuumed, then the same transaction reads it again (must still see its original snapshot version — I3 holds even across a deletion elsewhere); a snapshot taken with zero other active transactions (horizon equals current xid); an update that targets a row already updated by the same transaction (self-conflict, not a serialization failure).

22.9 Failure Analysis

FM-class: vacuum backlog growing unbounded because a single long-running transaction never commits. Detection: oldest_snapshot_age_seconds alerting threshold (§26). Recovery: operator intervention — the runbook docs/runbooks/long-running-txn-bloat.md documents identifying and, if safe, terminating the offending session; this is explicitly a manual recovery path, not automatic (auto-killing transactions is out of scope for Phase 0).

22.10 Operational Notes

oldest_snapshot_age_seconds is confirmed here as the second of the two leading operational indicators named in §26 (alongside buffer-pool hit ratio from Phase 7); both are wired into the default dashboard built in Phase 11.

23.1 Objectives

Close the vertical slice: give the planner real cost-based choice among the physical operators built in Phases 4–6 and 10, expose the system over the wire protocol, and pass the full conformance and performance gates of §28/§30.

23.2 Detailed Implementation Steps

  1. Implement Statistics/Histogram collection via ANALYZE (ADR-24): equi-depth histograms and NDV estimates per column, stored in the catalog.

  • sqllogictest_full_suite: ≥95% pass rate against the SQLite-oracle differential corpus (the remainder are explicitly out-of-subset features, enumerated in §37).
  • optimizer_beats_naive.rs: on the TPC-H-subset benchmark (§4, §30), the cost-based plan is measurably faster than the Phase 4 naive one-mapping-per-node plan on ≥90% of queries, and never more than 2× slower on the remainder (bounding regression, not just celebrating wins).

  • conformance/sqllogictest/ — the full imported suite, gated in CI (ADR-34).

  • fixtures/protocol_extended_query.rs — a scripted Parse/Bind/Execute sequence.
  • fixtures/plan_time_20_relations.sql — the adversarial planning-time fixture.

23.6 Pitfalls

  • Trusting stale statistics after a large bulk load without re-running ANALYZE: manifests as the exact selectivity-misestimation cascade worked through in §8's join example — a slow plan, not a wrong one (P4), but a slow plan that looks like a bug report.
  • Optimizer rule application order interacting badly with the DP cutoff, so a query at exactly the cutoff relation count nondeterministically takes either path: manifests as flaky performance tests; debug via pinning the cutoff boundary as an explicit fixture rather than relying on incidental relation counts in other tests.
  • Wire-protocol framing bug only visible under TCP segmentation (a message split across two reads): manifests as a hang or a misparsed message under real network conditions but never under loopback with small payloads; debug via a fixture that forces artificial read-size chunking.

23.7 Performance Concerns

This phase is where every earlier phase's cost-model assumption (P12) is finally checked against real measured latency (§30); the DP-vs-greedy cutoff (ADR-23) is the single highest-leverage knob for the planning-time budget in §4.

23.8 Edge Cases

A query with zero rows in every table (statistics of all-zero cardinality, must not divide by zero in a selectivity formula); a client that pipelines Parse/Bind/Execute without waiting for each response; a connection that exceeds the §4 connection budget (rejected with a clean error, not an accepted-then-dropped connection, per ADR-39 backpressure).

23.9 Failure Analysis

FM-class: optimizer selects a plan that times out the planning budget on a never-before-seen query shape in production. Detection: plan_time_p99_ms alerting (§26). Recovery: the greedy fallback (ADR-23) already bounds worst-case planning time by design; if a regression still exceeds the hard cap, the runbook directs falling back to a force-naive-plan session flag as an immediate mitigation while the query shape is investigated.

23.10 Operational Notes

26. Operational Readiness

Named metrics: transactions/second; commit latency (p50/p95/p99); WAL bytes/second and fsync latency; buffer-pool hit ratio; page reads and writes per second; checkpoint duration; recovery duration; active-transaction count and oldest-snapshot age; version- chain length (p50/p99); vacuum backlog (dead-version count); lock waits and deadlocks per minute; plan time (p50/p99) and slow-query count.

Tracing spans: one span per plan operator (SeqScan, IndexScan, HashJoin, etc., named identically to the PhysicalPlan variants in §11), nested under a per-statement span, nested under a per-transaction span, enabling EXPLAIN ANALYZE-style latency attribution.

Structured logging: every log line carries txn_id, session_id, and (when applicable) lsn, via tracing (ADR-33), so a single incident's log lines are joinable across the WAL, buffer pool, and executor without manual correlation.

Dashboards: a default dashboard groups (a) the two leading indicators, (b) commit-path latency (WAL/fsync), (c) MVCC health (snapshot age, version-chain length, vacuum backlog), (d) planner health (plan time, slow-query count), (e) connection/lock health.

Alerting philosophy: alert on the two leading indicators before anything else — buffer-pool hit ratio and oldest-snapshot age predict most other failure classes before they manifest (a falling hit ratio predicts latency regressions; a rising snapshot age predicts vacuum backlog and eventual bloat-driven slowdowns) — stated plainly per this document's requirement. Every other alert is secondary and tied to a specific FM-class in §25.

SLOs: derived directly from §4 (e.g., point-lookup p99 ≤1.2ms, commit p99 ≤2ms under group commit, recovery time ≤30s per GiB of WAL since checkpoint).

Incident response: each FM-class in §25 maps to exactly one runbook under docs/runbooks/: crash-recovery.md (FM-1, FM-4), long-running-txn-bloat.md (FM-9), deadlock-storm.md (FM-7), corrupt-page.md (FM-3, FM-6), wal-growth.md (FM-10), slow-plan-triage.md (FM-8).

Backup/restore, including PITR: a physical backup copies the data directory plus the base-backup LSN; point-in-time recovery replays WAL from that LSN up to a target timestamp, reusing the exact ARIES redo machinery from Phase 9 rather than a separate code path.

Deployment topology: single-process server binary, one instance per database, no built-in clustering (§1 non-goals; distribution is PhaseDeferred).

Canary/rollback/migration: a new binary version is canaried against a copy of production traffic before a full cutover; rollback is safe only within the on-disk format compatibility window stated in §27; schema migrations run as ordinary DDL transactions (P10) and are reversible only if the reverse migration is itself supplied.

27. Compatibility & Versioning

On-disk format versioning: pages, WAL records, and the catalog each carry a format version stamped in the file header (page files) or the first WAL record (WAL segments). Upgrades are in-place for additive changes (a new optional field with a documented default) and require an explicit offline migration tool (tools/migrate) for breaking changes; a database written by version N is guaranteed readable by version N+1 (never guaranteed for N+2 without going through N+1's migration).

SQL dialect stability: the subset in §1 is stable within a major version; new grammar productions are additive only within a minor version (SemVer, ADR-37).

Wire protocol versioning: the Startup message negotiates a protocol version; unsupported versions are rejected with a clean error, never silently downgraded.

Catalog schema migration: the four sys_* tables are themselves versioned via a sys_catalog_version singleton row, checked at Database::open; a mismatch triggers the migration tool rather than silent reinterpretation.

API stability: the embedding API (sqldb::Database) follows SemVer; breaking changes require a major version bump and a CHANGELOG.md entry.

Deprecation: a deprecated grammar production or API is warned for one minor version before removal in the next major version.

28. Testing & Verification Strategy

Unit and integration: per-crate unit tests plus cross-crate integration tests exercising the seams in §1 (boundaries) directly.

Property tests, tied to invariants: a B+Tree remains balanced and ordered under random insert/delete sequences (I4, §18.4 btree_balanced_ordered); a page's free-space accounting matches reality after arbitrary operation sequences (I5, §12.4 page_free_space_invariant); a logical plan and every physical plan for it return identical tuple multisets (I8, §16.4/§17.4 equivalence tests); committed transactions survive a crash injected at every WAL-write point (I2, §21.4 crash_injection_suite); no schedule under snapshot isolation exhibits a dirty read or a non-repeatable read (I3, §22.4 isolation_anomaly_matrix).

SQL logic tests as a named CI gate: sqllogictest.yml runs the full sqllogictest-format suite against SQLite as the oracle (§23.5 conformance/sqllogictest/), gating merge.

Differential testing: the same query executes against this engine and against SQLite on a shared fixture corpus, comparing result sets exactly (§16.4, §23.4).

Crash-injection recovery testing, first-class: crash-injection.yml kills the process at every fsync boundary across scripted workloads and asserts I2 (§21.4/§21.5).

Concurrency testing: a schedule generator plus an Elle-style history checker validates isolation claims (I3, I7, I10) across randomized concurrent schedules (§22.4).

Fuzzing: the SQL parser, page decoder, and WAL decoder are the three primary targets (ADR-35, T2/T3/T7), run nightly (fuzz.yml).

Chaos, deterministic replay, soak, fault injection: chaos testing randomly delays and reorders I/O; deterministic replay re-runs a captured workload against a seeded RNG to reproduce a reported bug exactly; soak testing runs the mixed workload for 72 hours watching for buffer-pool/version-chain leaks; fault injection simulates ENOSPC, torn writes, and a lying fsync (T7) via a fault-injecting pager wrapper used only in tests.

Perf-regression gating: every §30 target (M1–M12) is checked in CI against the previous release's baseline; a regression beyond a stated threshold fails the build.

Reproducible builds: a pinned Cargo.lock (ADR-37) and a fixed toolchain version produce bit-identical release artifacts, verified by a second independent build job.

Artifact signing: release binaries are signed; signatures are published alongside the artifact and verified by tools/verify-release.

SBOM: a software bill of materials is generated per release from Cargo.lock via cargo-cyclonedx, published with the release.

Release channels: stable (SemVer-tagged), nightly (built from main, no compatibility guarantee).

CI/CD topology: ci.yml (build/clippy/unit/property) → sqllogictest.yml → crash-injection.yml → concurrency.yml → (nightly) fuzz.yml → release.yml on tag.

Dependency auditing: cargo-deny/cargo-audit run in every CI job (ADR-36, T11), blocking merge on a known-vulnerable transitive dependency.

31. Scalability Analysis

What stays constant vs. grows, with Big-O: B+Tree lookup is logarithmic in row count (§34); sequential heap scan is linear in page count; join cost is per-algorithm (nested loop is O(rows(R)×rows(S)), hash join is O(rows(R)+rows(S)) plus a spill term, sort-merge is O(n log n) per side); optimizer search is factorial in relation count without pruning, which is exactly why DP with a cutoff (ADR-23) exists — a naive exhaustive search over 12 relations already explores far more join orders than DP's bottom-up table reuse; recovery time is linear in WAL bytes since the last checkpoint (§21, §34); vacuum cost is linear in dead-version count (§22).

Named bottlenecks, in order: (1) fsync latency on the commit path (§4, §20) — the hard floor beneath which group commit cannot push single-transaction latency; (2) buffer-pool hit ratio, since a miss costs a full page I/O; (3) latch contention on the B+Tree root and near-root nodes under high write concurrency (§18.7); (4) the lock table and WaitsForGraph under contention-heavy workloads (T9); (5) vacuum backlog under long-running transactions (T10).

Vertical scaling and the buffer-pool/memory relationship: more RAM directly raises the achievable hit ratio for a given working-set size (§34); beyond the point where the whole working set fits in the buffer pool, further RAM has no effect — the ceiling is data-size- relative, not RAM-relative.

Single-writer and lock-contention limits: the pager and WAL writer are single-writer by design (ADR-10/ADR-13); this bounds write throughput below the sum of all cores' compute capacity, since every commit ultimately serializes through one WAL append point.

What would have to change for replication or sharding: the WAL would need to become shippable to replicas (a change to ADR-11/ADR-12's LSN scheme to support cross-node ordering, as CockroachCB's HLC does); the single-writer pager assumption would need to become per-shard rather than per-database; this is exactly the PhaseDeferred("§36") scope this blueprint does not undertake.

Practical ceilings and the levers beyond them: database size is practically bounded by single-pager address space and recovery-time tolerance (larger WAL-since-checkpoint means longer recovery, §34); concurrency is bounded by the lock-table size and connection budget in §4; the lever beyond both is the distributed redesign in §36, not a Phase-0 tuning knob.

32. Mental Models & First Principles

MM1 — A database is a cache with an unusually strong durability promise. The buffer pool is the cache, the WAL is the promise, and every hard bug lives where those two disagree. Predicts: any bug that "only happens after a crash" is a buffer-pool/WAL ordering bug (I1). Bug class without it: engineers chase the buffer pool for correctness bugs that are actually WAL-ordering bugs. Resolves via §12, §19, §20.

MM2 — Write-ahead logging turns durability into an ordering constraint, not a synchronization cost. The log is the only thing that must be fsynced (P1); pages can lag indefinitely as long as their WAL record precedes them. Predicts: group commit can batch freely without weakening durability, because ordering, not frequency, is what's enforced. Bug class without it: assuming every page write needs its own fsync, which both wastes throughput and still doesn't guarantee I1 unless ordering is separately enforced. Resolves via §20, §21.

MM3 — MVCC converts read-write conflicts into a garbage-collection problem. A long-running transaction is not slow, it is a storage leak (P8). Predicts: the symptom of an old transaction is not query latency, it is unbounded version-chain growth and vacuum backlog. Bug class without it: chasing query performance for a problem that is actually a GC-scheduling problem. Resolves via §22, §25 FM-9, §26.

MM4 — A query optimizer is a search under uncertainty; cardinality-estimation error, not search strategy, is what makes plans bad in practice (Leis et al. 2015). Predicts: a "broken optimizer" symptom is usually a stale-statistics symptom. Bug class without it: rewriting the cost model or the search algorithm to fix what is actually a ANALYZE staleness problem. Resolves via §8 worked join example, §23.

MM5 — The slotted page turns "where is this row" into two separate questions: identity and location. A TupleId (page, slot) is stable identity; the slot's (offset, length) is mutable location. Predicts: compaction can move bytes freely without invalidating indexes, because indexes point at slots, not byte offsets. Bug class without it: an index that breaks every time a page is compacted. Resolves via §8, §12, §18.

MM6 — Isolation levels are a menu of which anomalies you are willing to accept, not a single dial from "unsafe" to "safe." Predicts: two applications running at the same isolation level can have entirely different correctness properties depending on which specific anomaly their logic happens to be sensitive to (the write-skew example, §8). Bug class without it: treating "Serializable" as a magic word rather than checking which specific anomaly a given piece of application logic actually depends on being absent. Resolves via §8, §22.

MM7 — A B+Tree's height is the real unit of cost, and it shrinks logarithmically while data grows linearly — which is the entire reason indexes exist. Predicts: the top two or three levels of any reasonably sized B+Tree fit in cache/buffer-pool memory regardless of table size, so lookup cost is dominated by the bottom one or two levels. Bug class without it: assuming index performance degrades proportionally with table size, when it degrades logarithmically. Resolves via §18, §34.

MM8 — Recovery is not a special mode, it is the same log applied twice: once forward (redo) unconditionally, once backward (undo) selectively. Predicts: a correct recovery implementation should look almost identical to normal WAL application, not like a separate "disaster recovery" code path. Bug class without it: divergent redo/undo logic paths that each individually look correct but disagree on edge cases. Resolves via §21.

SQLite's single-writer simplicity is the decision that wins hardest here: by giving up concurrent writers entirely, it eliminates an entire category of concurrency bugs this blueprint spends Phases 7, 9, and 10 on, at the cost of write throughput this blueprint's §4 targets would consider unacceptable for a multi-client OLTP workload. PostgreSQL's append-only MVCC with a separate vacuum process is the closest architectural sibling to this blueprint's Phase 10 design, and it wins by decoupling write-path latency from cleanup cost entirely — the cost it pays is the historical vacuum-under-load bloat failure mode this blueprint's ADR-18/I7 are explicitly designed to avoid repeating. InnoDB's undo-log MVCC (in-place update plus a separate undo chain, ADR-17's chosen variant) wins by bounding heap growth for update-heavy workloads at the cost of a more complex rollback path than pure append-only. DuckDB's vectorized column-store execution wins by an order of magnitude on analytic scans by batching tuples and exploiting SIMD, at the cost of point- access performance this blueprint's OLTP-focused §4 targets require and DuckDB's design does not optimize for — this is the sharpest contrast named in §1's non-goals.

34. Back-of-Envelope Capacity Model

1. Tuples per page. Page bytes minus header (8192 − 20 = 8172) divided by (tuple bytes

  • slot bytes). For a 100-byte tuple: 8172 / (100 + 4) ≈ 78 tuples/page.

2. Pages for a table of N rows. N / 78. For N = 10,000,000: 10,000,000 / 78 ≈ 128,205 pages ≈ 1.03 GiB.

3. B+Tree fanout. Page bytes / (key bytes + pointer bytes). For an 8-byte key + 4-byte PageId: 8172 / 12 ≈ 681 entries/internal-node.

4. B+Tree height for 10,000,000 keys. log₆₈₁(10,000,000) ≈ ln(10,000,000)/ln(681) ≈ 16.1 / 6.52 ≈ 2.47 → height 3 (root + 1 internal level + leaf level, rounding up). Page reads per lookup: 3 (or fewer once the top levels are buffer-pool-resident, MM7) — the root and the single internal level total roughly 128,205/681² ≈ 0.28, i.e. under 1 page, so in steady state only the leaf read is a cold-cache cost.

5. Buffer-pool hit ratio needed for a disk-IOPS budget. If the workload issues 10,000 page requests/sec and the disk budget is 500 IOPS: hit ratio ≥ 1 − (500/10,000) = 95% — matching the §4 target exactly by construction.

6. Commit throughput without group commit. 1 / fsync_latency. At 2ms fsync latency: 1/0.002 = 500 commits/sec ceiling for a single writer with no batching.

7. Commit throughput with group commit. batch_size / fsync_latency. At the §4 batch window (32 commits or 2ms, whichever first) and the same 2ms fsync: up to 32/0.002 = 16,000 commits/sec aggregate — a 32× ceiling increase, consistent with the M6 target of ≥8× at 32-way concurrency (the lower measured multiple reflects real contention overhead the idealized formula omits).

8. WAL bytes per transaction and per day. A typical OLTP transaction touching 3 rows at ~150 bytes of before/after image each ≈ 450 bytes plus a commit record (~32 bytes) ≈ 482 bytes/txn. At the §4 target of 3,000 tpm-equivalent (≈50 txn/sec sustained): 50 × 482 ≈ 24,100 bytes/sec ≈ 2.08 GiB/day.

9. Recovery time for 1 GiB of WAL since checkpoint. WAL bytes / replay rate. At the §4 replay-rate target of ≥40 MiB/sec: 1024 MiB / 40 MiB/sec ≈ 25.6 seconds — inside the §4 30-second target.

10. Version-chain storage from a long transaction. write_rate × transaction_duration × version_bytes. At 50 writes/sec, a 1-hour transaction, and 150 bytes/version: 50 × 3600 × 150 ≈ 27 MB of otherwise-reclaimable version data held back per hour the transaction stays open — the concrete number behind MM3's "storage leak" framing.

11. Sort spill threshold. rows × row_bytes vs. memory budget. For a 10,000,000-row, 100-byte-row sort against a 256 MiB memory budget: 10,000,000 × 100 = 1 GiB of input against 256 MiB budget → spill is required, with merge passes = ⌈log_{fan-in}(1024/256)⌉; at a 16-way merge fan-in, ⌈log₁₆(4)⌉ = 1 merge pass beyond the initial sort-and-partition step.

36. Alternative Architectures (Roads Not Taken)

1. An LSM-tree storage engine instead of a B+Tree heap.

writes ──► memtable (sorted, in-memory) ──► flush ──► SSTable L0
                                                        │ compaction
                                                        ▼
                                                     SSTable L1 ... Ln
reads ──► memtable ──► bloom filter per SSTable ──► binary search per level

Winning regime: write-heavy ingestion where read amplification is an acceptable trade for write throughput. Real embodying system: RocksDB / Cassandra (and this project's own sibling, LSM-Tree-Storage). Rejected here because the target workload in §1 is a mixed OLTP workload where point-lookup latency (§4) matters as much as write throughput, and an LSM's read-side compaction/level-search cost works against that target — this contrast is named explicitly in §1's non-goals and ADR-07.

2. Strict two-phase locking instead of MVCC.

Txn ──acquire S/X lock──► Lock Manager ──► Row
Txn ──release all locks── (only at commit/abort, "two-phase")
Readers block on Exclusive holders; Writers block on any holder.

Winning regime: environments demanding serializability by construction rather than by validation, where blocking readers is acceptable. Real embodying system: classic mainframe TP systems (Gray & Reuter) and the Lock-Manager-2PL sibling blueprint. Rejected here because MVCC's readers-never-block-writers property (ADR-16) better serves the mixed read/write OLTP target and matches PostgreSQL's default; 2PL is retained only as the studied alternative in §8/§9's lock-compatibility matrix, not the default path.

3. A vectorized or compiled column-store execution engine.

Scan ──► ColumnBatch[1024 rows] ──► Filter (SIMD) ──► Project (SIMD) ──► ...
     (batches flow through the pipeline, not single tuples)

Winning regime: analytic scans over large columns, an order of magnitude faster than tuple-at-a-time execution. Real embodying systems: DuckDB, HyPer (Neumann 2011), MonetDB/X100 (Boncz et al. 2005). Rejected here because Phase 0's target workload is point-access-heavy OLTP (§1), where a row store's per-row locality wins and a column store's batch-oriented design loses on the exact latency targets in §4 — the sharpest named contrast in this whole document (§1, §33).

4. An in-memory database with command logging instead of page-level WAL.

Client cmd ──► append to command log (the operation, not the before/after page image)
           ──► apply to in-memory table
Recovery: replay every logged command from the start (or last snapshot) in order.

Winning regime: workloads that fit entirely in memory, where command logging's smaller log size and simpler recovery (replay operations, not page images) outweigh page-level WAL's generality. Real embodying systems: H-Store, VoltDB. Rejected here because §1's max database size (1 TiB) and max row-count targets assume data does not fit in memory, making page-level WAL and a disk-resident buffer pool (Phases 7–9) the load-bearing design rather than an optimization for a memory-resident special case.

38. Glossary

Relation — a table, in the relational-algebra sense. Tuple — one row. Attribute — one column. Schema — the ordered set of attributes and their types for a relation. Catalog — the durable metadata store describing every table, column, and index. Three-valued logic — the TRUE/FALSE/UNKNOWN logic NULL comparisons produce. Slotted page — a page layout with a header, a slot array, and tuple data growing from opposite ends. Page header — the fixed-size prefix of a page carrying its LSN, checksum, and slot count. Free-space pointer — the offset marking where free space ends and tuple data begins on a page. Tuple ID / Rid — a (page_id, slot_id) pair identifying a row's physical location. Heap file — the sequence of pages holding a table's rows. B+Tree — a balanced tree index whose leaves hold sorted keys and are linked for range scans. Fanout — the number of children an internal B+Tree node can have. Split — the structural operation dividing an overfull B+Tree node into two. Merge — the structural operation combining two underfull B+Tree nodes. Buffer pool — the in-memory cache of disk pages every access goes through. Frame — a buffer-pool slot holding one cached page. Pin — marking a page in-use so it cannot be evicted. Replacement policy — the algorithm choosing which unpinned page to evict. Dirty page — a page modified in the buffer pool but not yet flushed to disk. Write-ahead logging — the rule that a log record for a change is durable before the change's page. LSN — log sequence number, a monotonic identifier for a WAL record. Group commit — batching multiple transactions' commit records into one fsync. Checkpoint — a recorded snapshot of dirty-page and active-transaction state bounding recovery's replay window. ARIES — the analysis/redo/undo recovery algorithm this blueprint implements. Analysis phase — ARIES's step rebuilding recovery state from the WAL. Redo — replaying logged actions unconditionally. Undo — reversing a loser transaction's logged actions. Compensation log record (CLR) — a log record describing an undo action, itself never undone. Torn page — a page partially written before a crash. MVCC — multi-version concurrency control, keeping multiple row versions to avoid reader/writer blocking. Snapshot — the set of transactions a reader's visibility check treats as committed. Visibility rule — the function deciding whether a version is visible to a snapshot. Version chain — the linked set of a row's historical versions. Vacuum — the background process reclaiming versions no snapshot can see. Tuple bloat — excess storage from unreclaimed dead versions. Two-phase locking (2PL) — a concurrency protocol acquiring all locks before releasing any. Lock mode — shared or exclusive. Compatibility matrix — the table defining which lock modes may coexist. Deadlock — a cycle of transactions each waiting on a lock the next holds. Wait-for graph — the structure used to detect deadlock cycles. Isolation level — a named guarantee about which anomalies a transaction may observe. Dirty read — reading another transaction's uncommitted write. Non-repeatable read — a value changing between two reads in one transaction. Phantom — a new row appearing in a repeated range query. Write skew — two transactions independently making changes that together violate a constraint neither alone violated. Serialization failure — the error raised when a transaction cannot be safely committed under its isolation level. Logical plan — a tree of relational operators independent of physical implementation. Physical plan — a logical plan with concrete access methods and algorithms chosen. Volcano iterator — the Open/Next/ Close pull-based execution model. Vectorized execution — processing tuples in batches rather than one at a time. Predicate pushdown — moving a filter closer to its data source in the plan. Selectivity — the fraction of rows a predicate is expected to match. Cardinality estimation — predicting the row count a plan node will produce. Histogram — a statistics structure approximating a column's value distribution. Join order — the sequence in which a multi-way join is executed. Spill — writing intermediate operator state to disk when it exceeds a memory budget. SQLSTATE — the standardized error-code taxonomy this blueprint's SqlError follows.
