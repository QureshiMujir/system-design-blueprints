32. Mental Models & First Principles

MM1 — A database is a cache with an unusually strong durability promise. The buffer pool is the cache, the WAL is the promise, and every hard bug lives where those two disagree. Predicts: any bug that "only happens after a crash" is a buffer-pool/WAL ordering bug (I1). Bug class without it: engineers chase the buffer pool for correctness bugs that are actually WAL-ordering bugs. Resolves via §12, §19, §20.

MM2 — Write-ahead logging turns durability into an ordering constraint, not a synchronization cost. The log is the only thing that must be fsynced (P1); pages can lag indefinitely as long as their WAL record precedes them. Predicts: group commit can batch freely without weakening durability, because ordering, not frequency, is what's enforced. Bug class without it: assuming every page write needs its own fsync, which both wastes throughput and still doesn't guarantee I1 unless ordering is separately enforced. Resolves via §20, §21.

MM3 — MVCC converts read-write conflicts into a garbage-collection problem. A long-running transaction is not slow, it is a storage leak (P8). Predicts: the symptom of an old transaction is not query latency, it is unbounded version-chain growth and vacuum backlog. Bug class without it: chasing query performance for a problem that is actually a GC-scheduling problem. Resolves via §22, §25 FM-9, §26.

MM4 — A query optimizer is a search under uncertainty; cardinality-estimation error, not search strategy, is what makes plans bad in practice (Leis et al. 2015). Predicts: a "broken optimizer" symptom is usually a stale-statistics symptom. Bug class without it: rewriting the cost model or the search algorithm to fix what is actually a ANALYZE staleness problem. Resolves via §8 worked join example, §23.

MM5 — The slotted page turns "where is this row" into two separate questions: identity and location. A TupleId (page, slot) is stable identity; the slot's (offset, length) is mutable location. Predicts: compaction can move bytes freely without invalidating indexes, because indexes point at slots, not byte offsets. Bug class without it: an index that breaks every time a page is compacted. Resolves via §8, §12, §18.

MM6 — Isolation levels are a menu of which anomalies you are willing to accept, not a single dial from "unsafe" to "safe." Predicts: two applications running at the same isolation level can have entirely different correctness properties depending on which specific anomaly their logic happens to be sensitive to (the write-skew example, §8). Bug class without it: treating "Serializable" as a magic word rather than checking which specific anomaly a given piece of application logic actually depends on being absent. Resolves via §8, §22.

MM7 — A B+Tree's height is the real unit of cost, and it shrinks logarithmically while data grows linearly — which is the entire reason indexes exist. Predicts: the top two or three levels of any reasonably sized B+Tree fit in cache/buffer-pool memory regardless of table size, so lookup cost is dominated by the bottom one or two levels. Bug class without it: assuming index performance degrades proportionally with table size, when it degrades logarithmically. Resolves via §18, §34.

MM8 — Recovery is not a special mode, it is the same log applied twice: once forward (redo) unconditionally, once backward (undo) selectively. Predicts: a correct recovery implementation should look almost identical to normal WAL application, not like a separate "disaster recovery" code path. Bug class without it: divergent redo/undo logic paths that each individually look correct but disagree on edge cases. Resolves via §21.

Required reading (§5)

Books

  • Silberschatz, Korth & Sudarshan, Database System Concepts, 7th ed., chapters 10 (storage/buffer), 11 (indexing), 14 (query optimization), 17–18 (transactions/ concurrency), 19–20 (recovery). Extract: buffer-pool replacement, B+Tree structure, System-R-style cost-based optimization, recovery phases. Applied in §12, §18, §20, §21.
  • Ramakrishnan & Gehrke, Database Management Systems, 3rd ed., chapters 8–9 (storage, tree indexes), 12–13 (query evaluation/optimization), 16–18 (transactions, CC, recovery). Extract: file organization, external sorting, cost-based join ordering. Applied in §17, §23.
  • Garcia-Molina, Ullman & Widom, Database Systems: The Complete Book, chapters 13–15 (query processing), 17–18 (concurrency/recovery). Extract: relational-algebra equivalences, 2PL correctness proofs. Applied in §8, §22.
  • Hellerstein & Stonebraker, Readings in Database Systems (the Red Book), the query-optimization and transaction-processing sections. Extract: the historical System R / INGRES design tradeoffs. Applied in §33.
  • Petrov, Database Internals, Part I (storage engines, B-Trees, LSM) and Part II (WAL, checkpointing, distributed). Extract: page-layout diagrams, WAL/checkpointing mechanics. Applied in §12, §19, §20.
  • Kleppmann, Designing Data-Intensive Applications, chapters 3 (storage and retrieval) and 7 (transactions). Extract: isolation-anomaly taxonomy, storage-engine tradeoffs. Applied in §22, §8.
  • Gray & Reuter, Transaction Processing: Concepts and Techniques, the logging/recovery and locking chapters. Extract: log-sequence-number scheme, precursor recovery concepts. Applied in §21.
  • Weikum & Vossen, Transactional Information Systems, the multi-version concurrency control chapters. Extract: formal serializability arguments for MVCC. Applied in §22.

Papers

  • Selinger et al., 1979, SIGMOD, "Access Path Selection in a Relational Database Management System." Contribution: dynamic-programming join enumeration and the canonical cost model. Applied in §23 Phase 11.
  • Codd, 1970, CACM, "A Relational Model of Data for Large Shared Data Banks." Contribution: the relational algebra foundation. Applied in §8.
  • Astrahan et al., 1976, ACM TODS, System R. Contribution: end-to-end architecture precedent for a from-scratch RDBMS. Applied in §3.
  • Stonebraker & Wong, 1976, INGRES. Contribution: an alternative architecture (query modification). Applied in §33.
  • Mohan et al., 1992, ACM TODS, "ARIES." Contribution: analysis/redo/undo recovery with fine-granularity locking and CLRs. Applied in §21 Phase 9.
  • Bayer & McCreight, 1972, Acta Informatica. Contribution: the B-Tree structure. Applied in §18 Phase 6.
  • Comer, 1979, ACM Computing Surveys, "The Ubiquitous B-Tree." Contribution: a survey of B-Tree variants and their tradeoffs. Applied in §18.
  • Lehman & Yao, 1981, ACM TODS. Contribution: efficient locking for concurrent B-Tree operations (B-link trees). Applied in §18/§19.
  • Graefe, 1994, IEEE TKDE, "Volcano — An Extensible and Parallel Query Evaluation System." Contribution: the iterator execution model. Applied in §16 Phase 4.
  • Berenson et al., 1995, SIGMOD, "A Critique of ANSI SQL Isolation Levels." Contribution: precise anomaly definitions. Applied in §22 Phase 10.
  • Cahill, Röhm & Fekete, 2008, SIGMOD, "Serializable Isolation for Snapshot Databases." Contribution: the SSI algorithm. Applied in §22 Phase 10.
  • Leis et al., 2015, VLDB, "How Good Are Query Optimizers, Really?" Contribution: empirical evidence that cardinality-estimation error dominates plan quality. Applied in §23 Phase 11 and §31.

Reference Implementations

  • SQLite — src/btree.c, src/pager.c, src/vdbe.c, src/where.c. Lesson: single-writer simplicity. Pitfall: do not copy its lack of true row-level MVCC. Applied in §33, §19 Phase 7.
  • PostgreSQL — src/backend/access/nbtree/, src/backend/optimizer/, src/backend/access/transam/xlog.c. Lesson: append-only MVCC plus vacuum. Pitfall: do not copy vacuum's historical bloat-under-load failure mode without the fix. Applied in §22 Phase 10, §33.
  • DuckDB — src/execution/, src/optimizer/. Lesson: vectorized execution. Pitfall: not a fit for this project's point-lookup-heavy OLTP scope. Applied in §16, §36.
  • CMU BusTub — the teaching database's buffer-pool and B+Tree assignments. Lesson: pin/latch discipline as a minimal, readable skeleton. Pitfall: not crash-safe, do not treat as a production reference. Applied in §12 Phase 0, §19 Phase 7.
  • RisingLight — Rust-native teaching OLAP database. Lesson: idiomatic Rust planner/ executor structuring. Pitfall: minimal transaction support, do not copy its MVCC gaps. Applied in §14 Phase 2, §16 Phase 4.
  • DataFusion — datafusion/optimizer/. Lesson: a Rust-native optimizer-rule framework. Applied in §23 Phase 11, §33.

Glossary (§38) · 58 terms · site-wide glossary

Relation
a table, in the relational-algebra sense.
Tuple
one row.
Attribute
one column.
Schema
the ordered set of attributes and their types for a relation.
Catalog
the durable metadata store describing every table, column, and index.
Three-valued logic
the TRUE/FALSE/UNKNOWN logic NULL comparisons produce.
Slotted page
a page layout with a header, a slot array, and tuple data growing from opposite ends.
Page header
the fixed-size prefix of a page carrying its LSN, checksum, and slot count.
Free-space pointer
the offset marking where free space ends and tuple data begins on a page.
Tuple ID / Rid
a (page_id, slot_id) pair identifying a row's physical location.
Heap file
the sequence of pages holding a table's rows.
B+Tree
a balanced tree index whose leaves hold sorted keys and are linked for range scans.
Fanout
the number of children an internal B+Tree node can have.
Split
the structural operation dividing an overfull B+Tree node into two.
Merge
the structural operation combining two underfull B+Tree nodes.
Buffer pool
the in-memory cache of disk pages every access goes through.
Frame
a buffer-pool slot holding one cached page.
Pin
marking a page in-use so it cannot be evicted.
Replacement policy
the algorithm choosing which unpinned page to evict.
Dirty page
a page modified in the buffer pool but not yet flushed to disk.
Write-ahead logging
the rule that a log record for a change is durable before the change's page.
LSN
log sequence number, a monotonic identifier for a WAL record.
Group commit
batching multiple transactions' commit records into one fsync.
Checkpoint
a recorded snapshot of dirty-page and active-transaction state bounding recovery's replay window.
ARIES
the analysis/redo/undo recovery algorithm this blueprint implements.
Analysis phase
ARIES's step rebuilding recovery state from the WAL.
Redo
replaying logged actions unconditionally.
Undo
reversing a loser transaction's logged actions.
Compensation log record (CLR)
a log record describing an undo action, itself never undone.
Torn page
a page partially written before a crash.
MVCC
multi-version concurrency control, keeping multiple row versions to avoid reader/writer blocking.
Snapshot
the set of transactions a reader's visibility check treats as committed.
Visibility rule
the function deciding whether a version is visible to a snapshot.
Version chain
the linked set of a row's historical versions.
Vacuum
the background process reclaiming versions no snapshot can see.
Tuple bloat
excess storage from unreclaimed dead versions.
Two-phase locking (2PL)
a concurrency protocol acquiring all locks before releasing any.
Lock mode
shared or exclusive.
Compatibility matrix
the table defining which lock modes may coexist.
Deadlock
a cycle of transactions each waiting on a lock the next holds.
Wait-for graph
the structure used to detect deadlock cycles.
Isolation level
a named guarantee about which anomalies a transaction may observe.
Dirty read
reading another transaction's uncommitted write.
Non-repeatable read
a value changing between two reads in one transaction.
Phantom
a new row appearing in a repeated range query.
Write skew
two transactions independently making changes that together violate a constraint neither alone violated.
Serialization failure
the error raised when a transaction cannot be safely committed under its isolation level.
Logical plan
a tree of relational operators independent of physical implementation.
Physical plan
a logical plan with concrete access methods and algorithms chosen.
Volcano iterator
the Open/Next/ Close pull-based execution model.
Vectorized execution
processing tuples in batches rather than one at a time.
Predicate pushdown
moving a filter closer to its data source in the plan.
Selectivity
the fraction of rows a predicate is expected to match.
Cardinality estimation
predicting the row count a plan node will produce.
Histogram
a statistics structure approximating a column's value distribution.
Join order
the sequence in which a multi-way join is executed.
Spill
writing intermediate operator state to disk when it exceeds a memory budget.
SQLSTATE
the standardized error-code taxonomy this blueprint's SqlError follows. ---
