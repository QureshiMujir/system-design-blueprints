Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust (stable toolchain, edition 2021)

Rejected

C, C++, Go, Zig

When the rejected choice is right

C wins when the target team already owns a ptrace codebase in C (rr) and the priority is diff-minimal contributions to that codebase; C++ wins if the project must interoperate with an existing C++ debugger plugin ecosystem (LLDB).

Why: Memory safety without GC; zero-cost FFI to Linux syscalls; ownership model maps to tracee-state ownership (P10)

ADR-02

Build system

Chosen

Cargo workspace (Cargo.toml at root; per-crate Cargo.toml)

Rejected

Meson, CMake, Bazel

When the rejected choice is right

Bazel wins when the repo is a large polyglot monorepo requiring cross-language dependency tracking and remote build caching across dozens of teams; Meson wins for a primarily C/C++ project where Rust is a small embedded component.

Why: Native Rust ecosystem; reproducible builds via Cargo.lock; no extra toolchain

ADR-03

Workspace structure

Chosen

12 crates (dret-core … dret-cli) in crates/ subdirectory

Rejected

Single monolithic crate, flat layout

When the rejected choice is right

A single monolithic crate wins in a solo-developer prototype where incremental compile times do not matter and the priority is minimizing boilerplate; flat layout wins for projects that will never be published as separate library crates.

Why: Compile-time isolation; minimal dependency surfaces; parallel crate compilation

ADR-04

Dependency policy

Chosen

Minimal: pin exact versions; no * or open ranges; audit via cargo audit

Rejected

Liberal semver

When the rejected choice is right

Liberal semver ranges win in an application library that must compose cleanly with downstream crates that also pin shared dependencies (e.g., a public API crate used by many consumers who need flexibility on transitive versions).

Why: Reproducibility; supply-chain safety; deterministic builds

ADR-05

Trace on-disk format

Chosen

Custom binary framing: events.log + data.log + mmap.log + checkpoints/

Rejected

SQLite, RocksDB, Cap'n Proto files, FlatBuffers files

When the rejected choice is right

SQLite wins when the primary consumer is ad-hoc SQL queries over event data (e.g., a data-science team correlating traces); RocksDB wins when random-write + point-lookup semantics dominate (e.g., a streaming replay that must update intermediate state).

Why: Append-only; crash-safe (P7); no external runtime; CRC-32C per frame; forward-compatible tag fields (P8)

ADR-06

Serialization (trace frames)

Chosen

Hand-written little-endian binary (fixed-stride header + DataRef for variable payload)

Rejected

serde + bincode, postcard, protobuf, flatbuffers

When the rejected choice is right

Protobuf wins when the trace format must be consumed by tools in many languages (Go, Python, Java) without a Rust toolchain; FlatBuffers wins when zero-copy in-place reading of large message fields (e.g., 64 KB MemDelta) is the primary access pattern.

Why: Zero allocations on hot path; exact layout control for CRC; no schema compiler dependency

ADR-07

Serialization (config/metadata)

Chosen

serde + serde_json for header.json and CLI config

Rejected

TOML, YAML, custom

When the rejected choice is right

TOML wins for user-facing configuration files where comment support and multi-line string syntax matter (e.g., a CI pipeline config authors edit frequently); YAML wins in environments where the config must be generated by existing YAML tooling (Kubernetes operators, Ansible).

Why: Human-readable; standard ecosystem; config is cold path

ADR-08

Async runtime

Chosen

None (synchronous; std::thread only)

Rejected

tokio, async-std, smol

When the rejected choice is right

Tokio wins when the supervisor must simultaneously manage a large number of I/O-bound sessions (e.g., a multi-tenant replay service with hundreds of concurrent gdbserver clients); async-std wins for a lighter-weight single-binary service without Tokio's macro complexity.

Why: Supervisor is inherently synchronous (ptrace waitpid loop); async overhead adds nondeterminism risk; I6 enforces single active task

ADR-09

ptrace abstraction

Chosen

dret-ptrace safe wrapper over raw libc / nix crate bindings

Rejected

nix crate used directly everywhere, pete crate

When the rejected choice is right

The pete crate wins for a rapid prototype where minimizing boilerplate is the primary goal and the project will not need to extend ptrace semantics beyond what pete already wraps; nix direct wins in a single-crate tool that never exposes ptrace as a library API.

Why: Encapsulates PTRACE_SETOPTIONS, waitpid demux, GETREGSET/SETREGSET in one auditable module; nix used as thin FFI layer only

ADR-10

Performance counter access

Chosen

perf_event_open(2) PERF_COUNT_HW_BRANCH_INSTRUCTIONS per-task fd; overflow SIGIO

Rejected

RDPMC direct, BPF perf, Intel PT

When the rejected choice is right

Intel PT wins when instruction-level granularity is required for a replay system that must capture every control-flow transfer (not just syscalls), and the overhead budget allows 2–4× slower recording; RDPMC wins in a hypervisor context where perf_event_open is unavailable and the guest has direct PMU access.

Why: rr-proven mechanism; per-task isolation; overflow-based preemption; no ring-0 requirement

ADR-11

RCB skid correction

Chosen

Subtract skid_constant (empirically measured per CPU model at startup); validate with micro-benchmark

Rejected

No correction, post-hoc statistical correction

When the rejected choice is right

No correction wins when the replay system uses a threshold looser than 1-tick precision (e.g., a coarse-grained event-log replay where ±50-branch uncertainty is acceptable and the performance cost of single-step backward probing is prohibitive).

Why: Hardware overcounts by 1–4 branches on overflow; correction is mandatory for I2 monotonicity

ADR-12

Syscall interception mechanism

Chosen

PTRACE_SYSCALL + PTRACE_SYSEMU; seccomp-BPF SECCOMP_RET_TRACE for hot-path syscalls

Rejected

Full seccomp-BPF only, LD_PRELOAD interposition

When the rejected choice is right

Full seccomp-BPF wins when the target is a sandboxing tool (not a replay engine) where preventing execution matters more than capturing return values; LD_PRELOAD wins for user-space library interposition in environments where ptrace is disallowed (e.g., Android apps, restricted containers).

Why: PTRACE_SYSEMU for replay (no real syscall executed); seccomp for low-latency pre-entry filter

ADR-13

CPUID / RDTSC interception

Chosen

seccomp-BPF → SIGSEGV → supervisor handles; CR4.TSD via seccomp where available

Rejected

Binary rewriting, IR instrumentation, hardware PMU virtualization

When the rejected choice is right

Binary rewriting wins when the target process runs in a VM where ptrace is unavailable and the binary is owned by the recorder team (e.g., a proprietary runtime instrumented at deploy time); hardware PMU virtualization wins inside a hypervisor where the VMM can intercept CPUID at ring-0.

Why: No binary modification; works on unstripped and stripped binaries; P3 (observe, do not perturb)

ADR-14

Memory capture

Chosen

/proc/pid/mem pread/pwrite at PTRACE stops; COW page diff for checkpoints

Rejected

process_vm_readv, PTRACE_PEEKDATA word loop

When the rejected choice is right

process_vm_readv wins when the supervisor is in a container where /proc/pid/mem is blocked by a seccomp policy but cross-process vector I/O is permitted; PTRACE_PEEKDATA wins for a single-word inspection tool where bulk transfer performance is irrelevant.

Why: pread on /proc/pid/mem bulk-copies regions; fastest non-kernel path; process_vm_readv as fallback

ADR-15

Page hashing (divergence)

Chosen

xxHash3 (128-bit) per 4 KB page

Rejected

SHA-256, CRC-32, MurmurHash

When the rejected choice is right

SHA-256 wins when the hash doubles as a content-addressable storage key that must be collision-resistant against a malicious trace author (e.g., a shared replay archive where adversarial content injection is a threat model).

Why: Fastest non-cryptographic hash; 128-bit reduces collision probability to negligible; no security requirement

ADR-16

Concurrency model (supervisor)

Chosen

Single supervisor thread; waitpid(-1, WNOHANG) poll loop; one tracee thread active at a time (I6)

Rejected

Multi-threaded supervisor, async supervisor

When the rejected choice is right

A multi-threaded supervisor wins when the system records many independent single-threaded processes simultaneously (e.g., a batch fuzzing infrastructure recording hundreds of concurrent single-threaded fuzz targets), where per-process supervisor threads can run in parallel without ptrace cross-thread conflicts.

Why: Eliminates supervisor data races; ptrace semantics require tracer thread to be the same OS thread per PTRACE_ATTACH

ADR-17

Logging

Chosen

tracing crate (structured spans + events); tracing-subscriber with JSON formatter for machine-readable output

Rejected

log + env_logger, slog

When the rejected choice is right

log + env_logger wins for a single-binary CLI tool with no observability requirements where the only consumer is a human reading stderr; slog wins when the project predates tracing and migration cost outweighs the benefit.

Why: Structured key-value fields; compatible with OpenTelemetry export; log facade bridged via tracing-log

ADR-18

Metrics

Chosen

metrics crate façade; metrics-exporter-prometheus for Prometheus scraping in long-running dret record sessions

Rejected

Custom counters, statsd, no metrics

When the rejected choice is right

statsd wins in a legacy infrastructure where Prometheus is not deployed but a statsd pipeline already exists; no metrics wins for a short-lived developer tool where the session completes in seconds and aggregation overhead is not justified.

Why: Standard façade allows swapping exporter; record latency per event kind; checkpoint size histograms

ADR-19

Error handling

Chosen

thiserror for library error enums; anyhow at CLI boundary only

Rejected

std::error::Error manual impl, eyre

When the rejected choice is right

eyre wins when the project requires color-coded, contextual error reports with backtrace capture by default in a developer-facing CLI where ergonomic error display is a first-class feature; manual std::error::Error wins for a no-std embedded context.

Why: thiserror keeps library errors typed and composable; anyhow acceptable at binary entry points

ADR-20

Testing framework

Chosen

Cargo #[test] + cargo nextest; integration tests in tests/ per crate; proptest for property-based tests

Rejected

gtest via FFI, criterion-only

When the rejected choice is right

gtest via FFI wins in a polyglot codebase that already has thousands of gtest suites for C++ components and needs Rust tests to appear in the same test report infrastructure; criterion-only wins for a pure performance-characterization project with no correctness test suite.

Why: nextest parallel execution; proptest for ABI tables and serialization round-trips

ADR-21

Fuzzing

Chosen

cargo-fuzz (libFuzzer) targeting TraceReader frame parsing and SyscallRecord deserialization

Rejected

AFL++, honggfuzz, manual corpus

When the rejected choice is right

AFL++ wins when coverage-guided mutation must run across a polyglot boundary (e.g., fuzzing a C parser invoked by a Rust harness) where libFuzzer's fork-server model is insufficient; honggfuzz wins for persistent-mode fuzzing of a tight loop with sub-microsecond execution time.

Why: First-class Rust integration; sanitizer support; Phase 14 conformance corpus feeds fuzz seeds

ADR-22

Benchmarking

Chosen

criterion crate; micro-benchmarks for tick read, event write, page hash; macro-benchmark: dret record + dret replay on standard corpus programs

Rejected

ad-hoc timing, perf stat only

When the rejected choice is right

perf stat only wins for a one-time performance investigation on known bottlenecks where statistical rigor is not needed and setup time must be minimized; ad-hoc timing wins in a CI environment where the overhead of criterion's warm-up cycles would consume more wall-time than the allowable job budget.

Why: Criterion statistical analysis; CI regression detection on p50/p99 latency

ADR-23

CI/CD

Chosen

GitHub Actions; matrix: [ubuntu-22.04, ubuntu-24.04] × [stable, beta]; jobs: build, test, fuzz (short), audit, clippy

Rejected

GitLab CI, Jenkins, CircleCI

When the rejected choice is right

GitLab CI wins when the project is hosted on a self-managed GitLab instance with access to bare-metal runners that expose PMU counters (GitHub-hosted runners are VMs that often block perf_event_open); Jenkins wins in an enterprise environment with existing build infrastructure and custom hardware provisioning.

Why: Standard open-source; Linux-only (ptrace is Linux-specific); no macOS/Windows jobs

ADR-24

Linux kernel version requirement

Chosen

Minimum Linux 4.14 (perf_event_open PERF_COUNT_HW_BRANCH_INSTRUCTIONS stable; seccomp-BPF GA)

Rejected

5.x+ only, 3.x support

When the rejected choice is right

5.x+ wins when the project wants to use io_uring for async trace I/O (stable in 5.1+) or PTRACE_GET_SYSCALL_INFO (5.3+) for cleaner syscall interception without manual register decoding; 3.x support wins only for embedded Linux distributions frozen on older kernels where the tool is the only available debugger.

Why: rr targets similar floor; 4.14 is LTS and widely available in CI images

ADR-25

Packaging / distribution

Chosen

Single dret binary (all subcommands via dret-cli); cargo install from crates.io; optional Docker image on ghcr.io

Rejected

Shared libraries, split binaries

When the rejected choice is right

Shared libraries win when the project exposes dret-core and dret-replay as APIs consumed by multiple downstream tools that must avoid binary size duplication (e.g., an IDE plugin, a CI runner, and a command-line tool all linking the same replay engine).

Why: Self-contained; no runtime dependency except Linux kernel; trace portability independent of host tools

ADR-26

Trace compression

Chosen

zstd (via zstd crate) applied to data.log during dret pack; events.log left uncompressed for random-access

Rejected

lz4, brotli, gzip

When the rejected choice is right

lz4 wins when compression speed is the bottleneck (e.g., compressing during record on a CPU-constrained CI runner where zstd encoding is the limiting factor); brotli wins for a web-served trace archive where download size is more important than decompression speed.

Why: zstd best ratio/speed trade-off; events.log must remain seekable by EventId without decompression

ADR-27

Reproducibility of the build

Chosen

Cargo.lock checked in; pinned toolchain via rust-toolchain.toml; SOURCE_DATE_EPOCH set in CI

Rejected

Floating toolchain, no lockfile

When the rejected choice is right

A floating toolchain wins for a library crate published to crates.io where locking the toolchain prevents users from compiling with their own newer stable Rust; no lockfile wins for a library (not a binary) where downstream consumers determine their own lock.

Why: Reproducible binaries; bisectable; supply-chain audit

ADR-28

License

Chosen

Apache-2.0 OR MIT (dual)

Rejected

GPL, LGPL, BSL

When the rejected choice is right

GPL wins when the project's primary distribution model is OS package repositories (Debian/Fedora) where GPL is the norm and copyleft enforcement is desired; LGPL wins for a shared library where proprietary applications may link without copyleft propagation but modifications to the library must remain open.

ADR-29

gdb RSP transport

Chosen

Unix-domain socket (/tmp/dret-<pid>.sock) default; TCP (--port N) optional

Rejected

Pipe, shared memory, custom protocol

When the rejected choice is right

Pipe wins in a tight GDB integration where the debugger is always launched as a child of the replay tool and the user never needs to connect a second client; shared memory wins in a high-frequency single-step scenario where RSP packet framing overhead is measurable (e.g., stepping millions of instructions per second).

Why: gdb target remote /path and target remote :N both supported; Unix socket avoids port conflicts in CI

ADR-30

ASLR / randomization suppression

Chosen

personality(ADDR_NO_RANDOMIZE) + MAP_FIXED on replay; sysctl kernel.randomize_va_space=0 documented but not required

Rejected

Binary patching, LD_PRELOAD stub

When the rejected choice is right

sysctl kernel.randomize_va_space=0 wins in a controlled lab where all replays run on a dedicated machine and the operator prefers a single global setting over per-process personality calls; binary patching wins for a position-independent executable where MAP_FIXED cannot be applied without modifying load addresses in the ELF header.

Why: personality() is per-process; no system-wide change required; MAP_FIXED reproduces exact layout (I10)

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Hardware-Assisted Recording (Intel Processor Trace)

Tracee process
    │
    │ CPU PT hardware collects compressed
    │ branch trace at near-zero overhead
    ▼
Intel PT ring buffer (kernel-managed)
    │
    ▼
dret-pt-decoder (libipt-based):
  branch trace → instruction stream reconstruction
  → syscall positions derived from branch sequence
    │
    ▼
Trace store (instruction-grain, not syscall-grain)

Regime where it wins: Programs that are CPU-bound with very few syscalls but much intra-loop nondeterminism (e.g., a program that reads from a hardware-mapped memory region, uses inline assembly, or relies on CPU feature detection inside tight loops). Intel PT captures every branch taken, not just syscall boundaries, so it can replay arbitrary control-flow divergence without per-syscall stops.

Real system: Intel PT-based replay is prototyped in academic systems (e.g., PinPlay, and partially in rr's --chaos mode). QEMU's record/replay uses a similar instruction-grain approach via the TCG translator.

Why rejected for dret: Intel PT requires post-processing the compressed PT stream to decode branch traces, which is complex and requires libipt (C library). More importantly, PT data does not capture syscall return values — it captures which branches were taken, not what the kernel returned. A separate syscall-capture mechanism is still required, making it more complex than the ptrace approach without eliminating the need for ptrace. Additionally, PT ring buffers overflow quickly for long recordings (typical ring = 4–64 MB), requiring frequent snapshot + decode cycles that add their own complexity.

Alt-2: VM-Level Deterministic Execution (Hypervisor Record/Replay)

Physical hardware
    │
    ▼
Deterministic hypervisor (e.g., QEMU TCG, Antithesis VMM)
  - intercepts all I/O, interrupts, memory DMA
  - records all hardware nondeterminism at VM boundary
    │
    ▼
Guest OS + tracee process
  (unmodified; no ptrace; no PMU configuration)
    │
    ▼
Replay: re-execute VMM with recorded hardware events

Regime where it wins: Full-system replay of multi-machine distributed systems, kernel-mode bugs, driver interactions, and DMA-triggered nondeterminism. Antithesis uses this approach to test distributed databases and infrastructure software where the nondeterminism crosses multiple processes, kernel subsystems, and network stacks simultaneously. QEMU's built-in record/replay (enabled with -icount mode) uses the TCG translator to make execution deterministic at instruction grain.

Real system: Antithesis (commercial VMM), QEMU record/replay (-icount det,shift=N -record/-replay), ReVirt (King & Chen 2002).

Why rejected for dret: Requires either a custom hypervisor (high engineering cost; not deployable on arbitrary machines) or a software interpreter like TCG (10–100× overhead, negating the performance advantage of hardware execution). dret targets developer workstations with hardware-native execution speed; hypervisor-level recording is only feasible in controlled lab or cloud environments. Additionally, VM-level replay produces traces tied to a specific VM image, not a portable per-process trace.

Alt-3: Deterministic-Scheduler-Only (No Syscall Capture)

Tracee process (multiple threads)
    │
    ▼
Scheduler interceptor:
  - forces deterministic thread interleaving via sched_setaffinity
  - records SchedSwitch sequence
  - does NOT record syscall return values
    │
    ▼
Replay: re-execute with identical SchedSwitch sequence
  (real syscalls execute against the live kernel)

Regime where it wins: Programs whose nondeterminism is entirely due to thread interleaving (data races, lock ordering) and not due to syscall return values varying across runs. A researcher investigating a Heisenbug caused purely by a specific thread-scheduling sequence can use this approach to stabilize the interleaving without capturing any syscall data. This is the approach taken by tools like CHESS (Microsoft Research) for lock-order testing.

Real system: CHESS (Microsoft Research, Musuvathi & Qadeer 2008), partial implementations in sanitizer-mode runtimes (TSan's schedule stabilization).

Why rejected for dret: Syscall return values are a primary source of nondeterminism for I/O-bound programs (read returns different bytes, gettimeofday returns wall time, etc.). A scheduler-only approach produces replay-instability for any program that reads from files, sockets, or the clock. dret's design requirement is bit-exact replay across machines and time, which is impossible without capturing syscall return values. Scheduler-only replay is useful as a debugging aid but not as a trace-and-replay archival system.

Alt-4: Binary Instrumentation (DynamoRIO / Pin)

Tracee binary (.elf)
    │
    ▼
Dynamic binary translator (DynamoRIO / Pin):
  - recompiles basic blocks on-the-fly
  - inserts instrumentation callbacks at syscall sites,
    rdtsc instructions, CPUID, memory accesses
    │
    ▼
Instrumentation tool records:
  - syscall nr, args, ret
  - rdtsc values
  - memory writes (optional)
    │
    ▼
Trace + replay via re-instrumented execution

Regime where it wins: Cross-platform (Linux and macOS and Windows), no kernel-specific interfaces required, fine-grained control over exactly what is instrumented (e.g., only instrument memory writes to a specific address range). The iDNA/TTD approach (Bhansali 2006) is essentially this model deployed with a Windows kernel driver for performance. Pin-based record/replay tools like PinPlay (Intel) use this architecture.

Real system: PinPlay (Intel), iDNA (Microsoft, Bhansali 2006), Dr. Memory (DynamoRIO-based).

Why rejected for dret: DynamoRIO and Pin introduce nondeterminism of their own: the JIT recompiler's behavior may vary between record and replay (different code cache layout, different JIT decisions for hot paths), which is P3 violation. More critically, binary translation adds 5–50× overhead even without any instrumentation, making the combined overhead prohibitive. ptrace + perf_event_open achieves the same syscall interception at lower overhead because it is handled at the OS boundary, not by recompiling the binary. dret explicitly chooses the observe-not-perturb path (P3), which rules out binary instrumentation.
