Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does single-CPU serialization (P4, Phase 7) make futex-based atomics deterministic without recording memory barriers? What invariant guarantees this, and where would it break? (Phase 8, §7 I6, MM3)
  2. If the RCB counter has a skid of ±5 branches on a specific CPU model, what is the maximum error in delivery_ticks (Phase 9) for an async signal? How does dret handle this, and what happens if the skid exceeds the configured SKID_THRESHOLD? (Phase 4, Phase 9, §4.1)
  3. A trace records a program that calls rdtsc in a tight loop. Phase 10 injects recorded TSC values. The program uses the TSC difference to busywait 100 ns. Why might the replay tracee hang forever, and what does dret do about it? (Phase 10, §10.6 pitfalls, MM2)
  4. Explain the exact sequence of events when dret-replay calls reverse-continue and a watchpoint is on a heap address that was written by a different thread than the one currently being debugged. How many checkpoint restore + replay-forward cycles may be required? (Phase 11, Phase 13, §8.9, §8.14)
  5. A conformance corpus test fails: replay of a 4-thread program produces DivergenceReport{kind: TickMismatch} at event 50,000. List the five most likely root causes in order of probability, and for each, name the diagnostic tool and the specific trace section that would rule it out or confirm it. (Phase 12, Phase 4, Phase 7, Failure Modes & Recovery F5, F6)
  6. Why must the trace container (Phase 3) keep events.log uncompressed but may compress data.log? What would break if events.log were zstd-compressed, and what would break if data.log were not compressed at all? (Phase 3, Phase 14, ADR-26, Scalability Analysis)
  7. An operator records a program that forks 500 short-lived threads, each doing 1 syscall then exiting. The record session runs out of file descriptors. Explain exactly which fds are consumed, what the theoretical ceiling is, and how Phase 8 mitigates this. (Phase 8, §4.1 fd budget, §8.7 perf fd leak pitfall)
  8. Pernosco (Comparative Architecture Table) achieves O(1) query latency to "when was this variable last written" while dret requires O(distance) replay-forward. What architectural change would be required to make dret approach Pernosco's query latency, and what would the storage cost be? (Phase 11, Phase 13, Comparative Architecture Table, Back-of-Envelope Capacity Model)
  9. Why is P3 (observe, do not perturb) violated by injecting a trampoline into tracee .text for branch counting, and why is it NOT violated by patching the vDSO in Phase 10? What specific property distinguishes the two cases? (§P3, Phase 10, §10.6 pitfalls, Threat Model T1)
  10. The Bhansali 2006 (iDNA/TTD) approach records at instruction grain while dret records at syscall grain. For a program that does 1 M iterations of a tight CPU-bound loop with no syscalls, what does dret's trace contain? What does TTD's trace contain? Which is correct for replay and why? (Phase 2, Comparative Architecture Table, MM1)
  11. Explain why TraceFrame.data_ref == DataRef(0) for a syscall like getpid() but not for read(). Walk through the exact sequence of dret-syscall decisions that produces this difference, citing the specific invariant that would be violated if getpid() did emit a MemDelta. (Phase 2, §11.5, §8.6, I4)
  12. A developer uses dret-gdb to reverse-continue to find who wrote to address 0x7fff1000. The watchpoint fires at event 42,000. The checkpoint nearest before 42,000 is at event 40,000. The developer then issues another reverse-continue to find the previous write. Explain the full algorithmic sequence including number of replay passes and why the bisection terminates. (Phase 11, Phase 13, §8.9, §8.14)
  13. dret-sched records SchedSwitch events with (from_tid, to_tid, at_ticks). On replay, what happens if the replay tracee's RCB counter reads 999 when the recorded SchedSwitch.at_ticks == 1000? Name the exact invariant that governs this, the detection mechanism, and the recovery path. (Phase 7, §7 I6, Phase 12, MM2)
  14. Explain why mmap events are stored in mmap.log (Phase 3) rather than being recorded as normal SyscallRecord entries in events.log. What seeking operation requires mmap.log to be a separate, independently-seekable structure? (Phase 3, Phase 11, §8.4, §8.10)
  15. A user's trace contains a SIGKILL delivered to the tracee. What is in the trace at that point? What does dret replay do differently for SIGKILL vs. SIGINT? Why is there no single-step-to-delivery-tick needed for SIGKILL? (Phase 9, §8.7, §9.6, §9.8)
  16. Walk through the Back-of-Envelope Capacity Model calculation for a program with 10 M syscalls, 1 GB total memory writes, and a checkpoint interval of 100 000 events. Would the total trace exceed the ≤10× storage amplification target? Show the arithmetic. (§4.1, Back-of-Envelope Capacity Model, Scalability Analysis)
  17. A new nondeterminism source is discovered: the Linux kernel sometimes returns different errno values for EINTR vs. ERESTARTSYS for the same syscall restart. What existing dret mechanism captures this, what invariant would detect a gap, and what ADR decision would change if it could not be captured via ptrace? (Phase 2, §2.6 pitfalls, I4, ADR-12)
  18. Why does dret store raw 128-byte siginfo_t bytes rather than parsing the struct? What ABI guarantee does this rely on, and under what condition would a cross-kernel-version replay fail despite this strategy? (Phase 9, §9.7 perf concerns, Compatibility & Versioning)
  19. The Scalability Analysis shows replay throughput is bounded by PTRACE_SYSEMU round-trips. If you wanted to achieve 10× higher replay throughput (500 000 events/s), name two fundamentally different architectural changes you could make, which back-matter section predicts the tradeoffs, and which ADR would need to be revisited. Mental Models & First Principles

MM1. The tracee is a deterministic function of its inputs. A program's execution is fully determined by: (1) its initial memory image, (2) the sequence of syscall return values, (3) signal delivery order, (4) hardware instruction trap results (rdtsc/CPUID). Record exactly these four categories and replay is exact. The bug class you write without this model: attempting to record every instruction executed, which is unnecessary and impractical. Resolving §: §6 (replay engine enforces this — only syscall results + signals + trap values are injected; no instruction-level logging needed).

MM2. Retired conditional branches are the only portable, per-task logical clock. Wall time varies with frequency scaling; rdtsc varies with core migration; cycle counts vary with cache misses. Retired conditional branches (RCB) are determined purely by the program's control flow, which is itself determined by MM1's four inputs. Two recordings of the same deterministic program produce identical RCB sequences. Without this model: using wall-clock preemption, which makes SchedSwitch events non-reproducible. Resolving §: Phase 4 (PerfCounter design), P5.

MM3. Serialization is cheaper than synchronization logging. Recording the exact memory access order of N concurrent threads requires O(N²) synchronization events. Running at most one thread at a time (single logical CPU) makes all atomics and memory operations sequentially consistent by construction, requiring zero synchronization recording. The tradeoff: replay does not preserve multi-core throughput. Without this model: attempting to record all memory ordering barriers, which is the approach of Dunlap et al. 2008 at VM level and is impractical in user space. Resolving §: §P4, Phase 7 (scheduler design), Phase 8 (atomics argument).

MM4. A checkpoint is the derivative, not the integral, of state. A full memory snapshot at every event is O(RSS) per event. A dirty-page delta since the last checkpoint is O(working-set churn). Checkpoints should store only what changed. Without this model: taking full snapshots leads to O(RSS × events) storage, which is infeasible for any workload beyond a few seconds. Resolving §: Phase 5 (page-diff delta), Phase 11 (checkpoint design), Back-of-Envelope Capacity Model.

MM5. The trace is the log; replay is the query. An append-only trace with CRC-framed, EventId-indexed records behaves exactly like a write-ahead log: writes are sequential (fast), reads are random-access by EventId (fast via index), and crash leaves a replayable prefix. Without this model: designing the trace as a mutable database (random writes) eliminates crash-safety and replay-from-prefix guarantees. Resolving §: §P7, §P8, Phase 3 (trace container design).

MM6. Divergence is a recorder bug, not a replayer failure. If replay produces a state different from record, the replayer faithfully executed the injected trace — the trace simply does not match what the original program did. This means divergence always points to a gap in the recorder's coverage of nondeterminism sources. Without this model: treating divergence as a replay engine bug leads to adding workarounds in the replayer that mask real recorder gaps. Resolving §: §P6, Phase 12 (divergence detection, bisect tooling).

MM7. The observer effect is the enemy; hardware counters are the antidote. Software instrumentation (LD_PRELOAD hooks, binary rewriting, in-process timers) changes what the program executes, making the recording itself nondeterministic. Hardware PMU counters and ptrace operate outside the tracee's instruction stream. Without this model: instrumenting the tracee to count its own branches introduces new branches, invalidating the count. Resolving §: §P3, ADR-10, ADR-13, Phase 4 (perf_event_open design).

MM8. Reverse execution is forward execution from the nearest earlier checkpoint. There is no instruction-reverse hardware. "Reverse-step" means: find the last checkpoint before the target event, replay forward to (target − 1). The cost is O(distance from checkpoint), not O(distance from trace start). Without this model: attempting to un-apply syscall side effects in reverse, which is impossible for I/O syscalls. Resolving §: Phase 11 (seek algorithm), Phase 13 (reverse-step/continue design), §8.9 (checkpoint model).

MM9. The TCB size determines the attack surface. Every line of code that runs with elevated privilege or accesses the tracee's memory is part of the trusted computing base. dret-ptrace + dret-mem form the TCB; every other crate can be untrusted. Minimizing the TCB means a tracee exploit can corrupt only what crosses the TCB boundary. Without this model: growing the TCB with convenience features (e.g., parsing trace files in the supervisor) creates unnecessary attack surface. Resolving §: §P9, Threat Model (T1, T5, T9).

MM10. Forward compatibility is a write-time contract, not a read-time feature. A trace written today must be readable by a reader built next year. This is only possible if the writer commits to never changing the meaning of existing frame tags, and the reader commits to skipping unknown tags by length. Both sides of the contract must hold. Without this model: adding fields to existing frame types causes older readers to misparse subsequent fields, breaking all existing traces. Resolving §: §P8, Phase 3 (tag-skip design), Compatibility & Versioning.

Glossary · 52 terms · site-wide glossary

AddressSpace
Recorded snapshot of /proc/pid/maps: segment list (addr, len, perms, offset, dev, ino, path), mmap provenance (file-backed / anonymous / stack / vdso / vsyscall), current brk value. Must be identical at event E in record and replay (I10). Managed by dret-mem/maps.rs; updated on every mmap/munmap/mremap/brk intercept.
arch_prctl
Linux syscall (ARCH_SET_FS / ARCH_SET_GS) that sets fs_base/gs_base for TLS. Intercepted by dret-record; recorded as a SyscallRecord; replayed by dret-replay/injector to restore TLS layout.
async signal
Signal delivered by the kernel at an arbitrary execution point, unrelated to the tracee's current instruction (e.g., SIGINT, SIGALRM, SIGCHLD). Delivery tick is recorded in SignalRecord.delivery_ticks; on replay the signal is injected at that exact tick via PTRACE_SETSIGINFO (I8). Contrast: sync signal.
brk
Program break: lowest address above the heap data segment, controlled by brk(2)/sbrk(3). Tracked as part of AddressSpace. Changes intercepted and replayed deterministically; divergence in brk produces an I10 violation.
build-id
ELF .note.gnu.build-id section: a hash uniquely identifying a binary. Recorded in the trace pack (Phase 14) to verify that replay uses the same binary as was recorded; mismatch is a fatal error before replay starts.
Checkpoint
Self-consistent snapshot anchored at a precise (EventId, Ticks) boundary (I7): per-task RecordedRegs, dirty-page table (Vec<(MemRange, PageRef)>), fd table, mmap table, brk. Written to ckpt/ by checkpoint_store.rs. Enables fast seek in Phase 11; enables reverse execution in Phase 13.
COW snapshot
Copy-on-write page snapshot: pages read from /proc/pid/mem at checkpoint time. Only pages modified since the prior checkpoint are stored as MemDelta entries. Full baseline snapshot is taken at trace start.
cpuid
x86 CPUID instruction; returns CPU feature flags and topology that vary across machines. Trapped by seccomp-BPF (SECCOMP_RET_TRACE) or CR4.TSD; recorded value injected on replay to ensure portability across CPU generations (Phase 10, P3).
DataRef(u64)
Byte offset into data.log pointing to the variable-length payload for a given TraceFrame: mem_effects bytes, si_info, raw page data. Enables constant-size TraceFrame records with arbitrarily large associated data.
divergence
Any mismatch between replay and recorded state at a given EventId: register values (RegMismatch), tick count (TickMismatch), or memory-page hash (MemHashMismatch). Any divergence triggers a DivergenceReport and immediate abort (P6, I9). Treated as a recorder or replayer bug, never silently continued.
DivergenceKind
Enum: RegMismatch (specific register differs), TickMismatch (RCB count differs), MemHashMismatch (page content differs at expected address). Embedded in DivergenceReport for triage.
DivergenceReport
{ event_id: EventId, tid: TaskId, kind: DivergenceKind, expected: u64, actual: u64 }. First divergence wins; printed to stderr; replay session returns Err.
EXITKILL
PTRACE_O_EXITKILL option: if the tracer dies, all traced children are immediately killed. Ensures no tracee escapes unsupervised; mandatory for P7 and P9. Set during Phase 1 supervisor initialization.
EventId(u64)
Monotonically increasing sequence number assigned to every TraceFrame, starting at 1. Gaps indicate corruption or truncation (I1). Primary key for TraceReader::seek_by_event_id.
EventKind
Enum discriminant on TraceFrame: Syscall, Signal(async|sync), SchedSwitch, RdtscTrap, CpuidTrap, PatchVsyscall, Exec, Exit, Checkpoint. Determines which record type is stored in data.log at DataRef.
fd table
Per-process table of open file descriptors (number → kind, flags, path/pipe-id/socket-id). Captured in every Checkpoint; used during replay seek to restore file descriptor state so subsequent syscalls observe correct fds.
frame tag
A 16-bit type field in each events.log frame header enabling forward-compatible extension (P8). Unknown tags are skipped by older readers without error; new fields are appended within an existing tag's payload.
fs_base / gs_base
x86-64 segment base registers encoding thread-local storage (TLS) pointer (Linux uses fs_base). Captured in RecordedRegs at every stop; restored on context switch during replay via PTRACE_SETREGSET REGSET_NT_X86_XSTATE.
futex
Fast user-space mutex; kernel wait/wake via futex(2). Ordering of futex_wake and futex_wait across threads is non-deterministic on SMP hardware; serialized by dret-sched to one logical CPU during record, producing deterministic SchedSwitch ordering replayed exactly (Phase 8).
Heisenbug
A bug that disappears or changes behavior when observed. Avoided by P3: the recorder uses hardware RCB counters rather than software instrumentation, so the tracee runs the same instruction stream regardless of recording.
logical CPU
The single serialized execution context enforced by dret-sched. sched_setaffinity pins the tracee to one physical CPU; only one TaskId has ptrace-continue permission at any instant (I6, P4). Eliminates true concurrency nondeterminism without requiring VM-level virtualization.
MemDelta
{ range: MemRange, bytes_ref: DataRef } — the bytes a syscall wrote into tracee address space as a side effect (e.g., read(2) filling a buffer, recvmsg(2) writing data + cmsg). Replayed by pwriting the exact bytes at the exact address via /proc/pid/mem (I4).
MemRange
{ addr: u64, len: u64 } — a contiguous half-open address interval [addr, addr+len) in tracee virtual address space. Used in MemDelta, Checkpoint dirty-page list, and AddressSpace segment descriptors.
orig_rax
The original syscall number placed in rax before kernel entry, preserved in pt_regs.orig_ax. After syscall return, rax holds the return value and orig_rax holds the number. Read via PTRACE_GETREGSET at syscall-exit stop; required to correlate entry and exit stops.
overcount / skid
PMU hardware fires the overflow interrupt a small number of branches after the exact counter threshold due to instruction pipeline depth. The skid is bounded (typically 1–8 branches on modern Intel); dret-time corrects by single-stepping backward to the precise tick boundary.
page-diff delta
Between two consecutive checkpoints, only pages dirtied by the tracee change. dret-mem detects dirty pages via /proc/pid/pagemap soft-dirty bits (or userfaultfd) and records only those, keeping checkpoint size proportional to working-set churn rather than total heap size.
PageRef
Offset into ckpt/pages.bin for the raw 4096-byte page contents stored in a Checkpoint. Analogous to DataRef for data.log; avoids embedding page data inline in the checkpoint record.
perf_event_open(2)
Linux kernel interface for hardware performance counters. dret-time opens PERF_COUNT_HW_BRANCH_INSTRUCTIONS (Intel: retired conditional branches; AMD: equivalent PMU event) per tracked task. Configured with pinned=1, exclude_kernel=1, exclude_hv=1 to count only user-space branches.
PTRACE_SYSEMU
ptrace request that stops the tracee at syscall entry and does NOT execute the syscall in the kernel. Used exclusively by dret-replay to suppress all real syscall side-effects (I5). The replayer injects the recorded return value and writes recorded mem_effects into tracee memory.
RCB (retired conditional branch)
The hardware event used as the deterministic logical clock (Ticks). Conditional branches retire at the same count for a given deterministic instruction sequence regardless of wall time, CPU frequency, or cache state — making counts reproducible across replay runs on the same ISA.
RecordedRegs
Canonical x86-64 register snapshot: { rax, rbx, rcx, rdx, rsi, rdi, rbp, rsp, r8–r15, rip, rflags, orig_rax, fs_base, gs_base }. Stored in every TraceFrame. Compared verbatim at each replay event (I9); any byte difference triggers DivergenceKind::RegMismatch.
RecordSession
Top-level handle for a recording run. Owns: Tracer (dret-ptrace), TraceWriter (dret-trace), one TracedTask per thread, perf_event fds, CheckpointTrigger. Drives the supervisor stop-dispatch loop until all tasks exit.
ReplaySession
Top-level handle for a replay run. Owns: TraceReader, ptrace handles for re-executed tracee, DivergenceChecker, optional GdbServer. Drives the replay stop-dispatch loop in recorded EventId order.
RSP (gdb Remote Serial Protocol)
Wire protocol spoken by gdbserver over TCP (typically port 1234). dret-gdb implements: g/G (read/write all regs), m/M (read/write mem), c/s (continue/step), bc/bs (reverse-continue/reverse-step), Z0/z0 (breakpoint insert/remove), Z2/z2 (write watchpoint insert/remove).
SchedPoint
{ tid: TaskId, ticks: Ticks } — a deterministic preemption boundary recorded in the trace. The scheduler preempts the running task when its RCB count reaches the next SchedPoint.ticks for another task. Replayed by dret-sched to produce identical context-switch sequence.
SchedSwitch
EventKind::SchedSwitch variant. Data: { from_tid, to_tid, from_ticks, to_ticks }. Written to events.log on every context switch during record; consumed by dret-sched during replay to gate which task is allowed to proceed.
seccomp-BPF
Secure computing mode with BPF filter attached to the tracee. Used to intercept rdtsc/rdtscp/cpuid and deny dangerous syscalls with SECCOMP_RET_TRACE, delivering a ptrace-stop to the supervisor without requiring per-instruction PTRACE_SYSCALL overhead. Installed by dret-record before tracee exec.
si_code / si_info
siginfo_t fields: si_code distinguishes signal origin (SI_USER, SI_KERNEL, SI_TKILL, SEGV_MAPERR, FPE_INTDIV, …). Entire siginfo_t (128 bytes) recorded in SignalRecord.si_info; replayed via PTRACE_SETSIGINFO so the tracee's signal handler sees the exact same siginfo as during recording.
SignalRecord
{ signo: i32, si_code: i32, deterministic: bool, delivery_ticks: Ticks, si_info: [u8; 128] }. deterministic=true for sync signals (fault-induced); false for async. Stored in data.log at DataRef.
skid** — see *overcount / skid
supervisor
The tracer process running dret-record or dret-replay. The trusted computing base (P9). Observes and controls the tracee exclusively via ptrace and /proc/pid/mem. Owns all recorded state; arbitrates all nondeterminism. Must not crash after trace start (P7).
sync signal
Signal caused directly by the tracee's current instruction: SIGSEGV (invalid memory access), SIGFPE (arithmetic fault), SIGBUS (alignment / bus error), SIGTRAP (breakpoint/watchpoint). Deterministic because the same instruction sequence produces the same fault; recorded for completeness and si_info fidelity.
SyscallRecord
{ nr: u32, args: [u64; 6], ret: i64, errno: i32, mem_effects: Vec<MemDelta> }. The complete record of one syscall execution: number, all arguments, return value, errno, and every byte the kernel wrote into tracee memory as a side effect.
TaskId(u32)
Stable task identity assigned at clone(2) interception, starting at 1 for the initial thread. Invariant across record and replay; never equals the OS pid/tid which may differ between runs. Used as the primary per-task index in the trace.
Ticks(u64)
RCB count for a given TaskId at a given TraceFrame. Monotonic non-decreasing per task across the whole trace (I2). The sole addressing mechanism for positions within a task's execution. Ticks are per-task; they are not globally comparable across tasks without a SchedPoint anchor.
TracedTask
Per-thread supervisor state: { task_id: TaskId, os_tid: pid_t, ticks: Ticks, regs: RecordedRegs, stop_state: PtraceStop, perf_fd: RawFd }. Created on clone interception; destroyed on exit.
TraceFrame
The fundamental unit of the trace: { event_id: EventId, tid: TaskId, ticks: Ticks, kind: EventKind, regs: RecordedRegs, data_ref: DataRef }. Fixed-size header in events.log; variable payload in data.log at data_ref.
TraceReader
Seekable reader over a trace directory. Supports: sequential iteration by EventId, seek_by_event_id(EventId), seek_by_ticks(TaskId, Ticks). Validates CRC per frame; skips unknown tags (P8).
TraceWriter
Append-only writer over a trace directory. Assigns EventId monotonically; writes TraceFrame to events.log; appends variable payload to data.log; flushes CRC; fsync at checkpoint boundaries (P7).
TLS (thread-local storage)
Per-thread data accessed via fs_base on x86-64 Linux ABI. fs_base is captured in RecordedRegs at every stop; set via arch_prctl or PTRACE_SETREGSET on context-switch during replay to restore TLS pointer exactly.
vDSO / vsyscall
Kernel-mapped code pages providing fast user-space implementations of time-related syscalls (gettimeofday, clock_gettime, time, getcpu). Return wall-time or CPU values that are nondeterministic. dret-record patches the tracee's vDSO mappings (recorded in mmap.log as PatchVsyscall events) to trampoline through the supervisor, which injects recorded values (Phase 10).
waitpid demux
The supervisor's main event loop: calls waitpid(-1, WNOHANG | __WALL) to collect ptrace stops from any child; dispatches by (pid, stop-reason bitmask) to the correct TracedTask handler. Implemented in dret-ptrace/tracer.rs.
