Project Number: 196

Project Name: Distributed Transaction Coordinator (TrueTime-style)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

This project builds, from scratch in Python, a distributed transaction coordinator that provides externally-consistent (linearizable at the transaction level) transactions across sharded data, in the tradition of Google Spanner. The coordinator layers two-phase commit (2PC) across per-shard participants, where each participant is itself a replicated consensus group (Paxos/Raft-style); assigns global commit timestamps using a TrueTime-style bounded-clock-uncertainty API (TT.now() -> [earliest, latest], width 2*epsilon); enforces the commit-wait rule so that no transaction's effects become visible until the clock has certainly advanced past its commit timestamp; stores versioned data under multi-version concurrency control (MVCC) so that snapshot reads at a timestamp require no locks; and resolves distributed deadlocks via wound-wait and in-doubt transactions via a durable 2PC log replayed on recovery. The engineering payoff is precise: external consistency is not "eventually" anything — it is bought by waiting out a bounded, monitored clock uncertainty interval, and every other mechanism (2PC, consensus, MVCC, locking) exists to make that wait safe and durable.

Phase-0 deliverable (initial module skeleton, one module per bullet):

  1. txn_coordinator — coordinator process: begins/aborts/commits, drives 2PC across participants.
  2. participant — per-shard participant: wraps a consensus group and an MVCC store, votes in 2PC.
  3. truetime — the TT.now() interval API and the epsilon (uncertainty) bound.
  4. timestamp_oracle — timestamp assignment (start-rule) and commit-wait enforcement.
  5. mvcc_store — versioned key-value storage with timestamped snapshot reads and GC.
  6. consensus_shim — minimal in-repo Paxos/Raft-style consensus core each participant runs.
  7. lock_manager — per-participant lock table with wound-wait deadlock avoidance.
  8. twopc_log — durable prepare/commit/abort log, the source of truth on recovery.
  9. recovery_manager — in-doubt transaction detection and resolution on restart.
  10. clock_monitor — epsilon-bound violation detection and fail-safe degradation.
  11. sim_harness — deterministic multi-node simulation plus a Jepsen/Elle-style history checker.
  12. cli — operator tooling (transaction inspection, in-doubt listing, clock status).

Boundaries. Provides: transaction coordination logic — 2PC orchestration, global timestamp assignment, the commit-wait rule, cross-shard lock coordination, in-doubt recovery, and the clock-uncertainty API and its monitor. Delegates: per-shard durability and replication to a consensus module (consensus_shim, an in-repo minimal Paxos/Raft-style core built for this project, standing in for a production consensus library — a participant is a replicated group, never a single node) and data layout to an MVCC engine (mvcc_store, a versioned-dict/B-tree-style reference substrate, not a production LSM engine). Does NOT provide: a SQL parser, query planner, or optimizer; a general-purpose storage engine; a client-driver ecosystem beyond one reference Python client; general-purpose consensus or lock-manager libraries usable outside this coordinator.

Non-goals and sibling contrasts. Two-Phase + Three-Phase Commit (project 73) studies the atomic-commit protocol in isolation — message flow, blocking behavior, the 3PC non-blocking extension — with no clock and no MVCC; here 2PC is one ingredient composed with a bounded clock and MVCC to reach external consistency, not the object of study itself. Paxos and Raft-Consensus (separate projects) build general-purpose consensus cores in depth; here per-shard consensus is treated as a black-box dependency behind consensus_shim — this project's load-bearing concern is what is layered above consensus. MVCC-Transaction-Manager (separate project) builds single-node MVCC and snapshot isolation in depth; here MVCC is one ingredient inside a globally time-ordered, cross-shard system, not the object of study. Lock-Manager-2PL (separate project) builds general lock-table mechanics and full 2PL protocols; here locking is narrowly scoped to wound-wait deadlock avoidance in service of the 2PC critical section. Saga-Workflow-Coordinator (project 97) achieves eventual consistency via compensation for long-running workflows — no atomicity, no external consistency, no blocking; this project achieves atomic, externally-consistent transactions at the cost of 2PC blocking and commit-wait latency, the opposite point on the tradeoff curve. Not a SQL query engine (no parser/planner/optimizer). Not a storage engine (the MVCC store is a reference substrate, never a production LSM/B-tree engine).

Consistency level, stated precisely: external consistency per Corbett et al. 2012 — if transaction T1 commits before transaction T2 starts in real (wall-clock) time, then commit_ts(T1) < commit_ts(T2), and every client observes commits in commit-timestamp order (equivalent to linearizability applied to the transaction-commit event). This is strictly stronger than plain serializability, which orders transactions consistently but not with respect to real time.

Deployment model: N stateless-w.r.t.-outcome coordinator processes (each owns a durable 2PC log for the transactions it drives), M participant shards each backed by a k-node consensus group (k=3 or 5, running consensus_shim), and a time daemon per host exposing TT.now(). Because this is a from-scratch Python project without real GPS/atomic-clock hardware, epsilon is a configured, monitored, and fault-injectable parameter rather than a physically sourced one — clock_monitor treats an epsilon violation as a correctness-threatening event regardless of source.

Users/operators: distributed-systems engineers studying Spanner-style coordination end to end; operators running the coordinator/participant cluster and its runbooks; the sim_harness Jepsen/Elle-style checker is the primary way the external-consistency claim is demonstrated absent real hardware clocks.

What later phases unlock: Phase 0-3 unlock a working single-shard transactional store with 2PL+MVCC and snapshot reads. Phase 4-6 unlock cross-shard atomic, externally-consistent commits (2PC over consensus, commit-wait). Phase 7-9 unlock production-grade fault tolerance — coordinator crash recovery, wound-wait deadlock handling, lock-free snapshot reads at a timestamp. Phase 10-11 unlock the clock-fail-safe and the verification harness that proves external consistency under fault injection.

Python and rationale: Python is chosen because the protocol logic — 2PC state machines, commit-wait arithmetic, MVCC visibility rules, wound-wait ordering — is the pedagogical point, not memory-layout optimization; dataclasses, asyncio, and clear control flow make every state machine auditable; time.monotonic() plus asyncio primitives are sufficient to simulate bounded TrueTime intervals and per-shard actors without systems-language ceremony. Rejected languages: Rust — its memory-safety and throughput advantages are wasted when the deliverable is a correctness reference, not a production database, and its ceremony slows iteration on protocol-level bugs. Go — GC pauses confound the very latency experiments (epsilon sensitivity, commit-wait tuning) this project exists to teach, and its type system is a weaker fit for the state-machine-heavy domain model. Java — JVM warmup and GC pauses again confound commit-wait pedagogy, and record/message ceremony is heavier than dataclasses for this domain.

Prerequisites: distributed systems fundamentals (CAP, FLP impossibility), Lamport clocks and causality (Lamport 1978), Paxos/Raft consensus, ACID transaction theory (isolation levels, MVCC, Bernstein-Hadzilacos-Goodman), two-phase commit and its blocking failure mode, basic queueing and tail-latency reasoning.

Timeline: Phase 0-3 (single-shard foundation) approximately 6 weeks; Phase 4-6 (cross-shard 2PC, consensus layering, commit-wait) approximately 8 weeks; Phase 7-9 (recovery, deadlock, snapshot reads) approximately 6 weeks; Phase 10-11 (clock fail-safe, verification harness) approximately 4 weeks; total approximately 24 weeks at reference pace.

Deferrals: PhaseDeferred("§31 Scalability Analysis") for geo-partitioned locality-aware routing across regions; PhaseDeferred("§36 Alternative Architectures (Roads Not Taken)") for a hybrid-logical-clock (HLC) fallback mode usable without any bounded-uncertainty source; PhaseDeferred("§24 Threat Model") for Byzantine-fault-tolerant participant voting; PhaseDeferred("§36 Alternative Architectures (Roads Not Taken)") for deterministic Calvin-style transaction pre-ordering as a 2PC alternative; PhaseDeferred("§30 Performance Engineering") for adaptive contention-aware lock scheduling; PhaseDeferred("§1 Goal & Scope") for a SQL query layer, permanently out of scope per the non-goals above.

2. Why Build This

Keyword bullets — the gaps this project closes:

  • uncertainty intervals and why a scalar timestamp is not enough,
  • the commit-wait rule as a hardware-clock guarantee converted into a database guarantee,
  • external consistency versus plain serializability, precisely distinguished,
  • timestamp-allocation races and monotonicity under coordinator failover,
  • two-phase commit's blocking failure mode and why it needs consensus underneath it,
  • 2PC-over-Paxos layering — atomicity from 2PC, durability and fault tolerance from consensus,
  • MVCC snapshot reads as the lock-free majority of read traffic,
  • wound-wait deadlock avoidance under wide-area lock hold times,
  • in-doubt transaction recovery after a coordinator crash mid-2PC,
  • clock-epsilon monitoring as a correctness-critical (not merely operational) alarm,
  • Jepsen/Elle-style history checking as the only way to falsify a linearizability claim,
  • the structural separation of read-only and read-write transaction types as a misuse-resistance decision, not a naming convenience,
  • counterexample minimization as the difference between a checker that finds bugs and a checker that finds debuggable bugs,
  • why single-shard throughput dominates cross-shard throughput by an order of magnitude, and what that implies for application schema design.

What Mastery Looks Like

  • Explaining why latest - earliest <= 2*epsilon and commit-wait together guarantee external consistency, and reproducing the worked proof (Phase 6).
  • Implementing 2PC so that every participant's prepare and commit vote is itself a durably-replicated consensus write, not a local disk write (Phase 5).
  • Building an MVCC store where a snapshot read at timestamp t requires zero locks and zero coordinator round-trips (Phase 9).
  • Diagnosing and resolving an in-doubt transaction after a coordinator crash between prepare and commit, purely from the durable 2PC log (Phase 7).
  • Detecting and breaking a distributed deadlock with wound-wait without a stop-the-world detector (Phase 8).
  • Building a clock-epsilon monitor that pages immediately on a bound violation because it threatens correctness, not availability (Phase 10).
  • Running a Jepsen/Elle-style checker that can falsify external consistency under injected clock skew and partition, and reading its counterexample traces (Phase 11).

Client / Driver: begins transactions, issues reads/writes, calls commit; retries under coordinator failover without turning an ambiguous outcome into a silent abort.

Transaction Coordinator: owns the transaction state machine (Pending -> Prepared -> Committed/Aborted, plus In-Doubt), drives 2PC across participant shards, consults the Timestamp Oracle for commit timestamps, and enforces commit-wait before releasing locks or acknowledging the client.

Participant shards: each is a replicated consensus group (Paxos/Raft-style) fronting an MVCC store; a participant never single-point-fails because its prepare and commit votes are themselves consensus writes, replicated before being acted on.

MVCC storage per shard: keeps a version chain per key tagged with commit timestamps; snapshot reads at timestamp t return the newest version with commit_ts <= t with no locking.

TrueTime/HLC clock service: exposes TT.now() -> [earliest, latest] with bounded width 2*epsilon; the coordinator uses it for the start rule (pick s >= TT.now().latest) and the commit-wait rule (wait until TT.now().earliest > s).

Lock manager: per-participant lock table implementing wound-wait; locks are held from acquisition through the end of commit-wait, never released early.

Timestamp oracle: the coordinator-side component that assigns provisional and final commit timestamps from TrueTime intervals and enforces monotonicity across coordinator epochs.

2PC log: the coordinator's durable, append-only record of every prepare vote and commit/abort decision; the sole source of truth for recovery.

Recovery manager: on coordinator or participant restart, scans the 2PC log (coordinator side) or consensus log (participant side) to resolve in-doubt transactions to the logged decision, never to a locally-guessed one.

6. Design Principles

  • P1 — External consistency is bought with commit-wait: the coordinator waits out the clock-uncertainty interval before releasing locks, so any transaction starting later gets a strictly larger timestamp — the wait IS the guarantee (Corbett et al. 2012).
  • P2 — Atomic commit across shards is 2PC, but each participant is itself replicated by consensus, so a participant never single-point-fails — 2PC supplies atomicity, consensus supplies durability (Gray & Lamport 2006).
  • P3 — Reads at a timestamp need no locks because MVCC keeps the version that was current then — snapshot reads are lock-free and dominate read traffic.
  • P4 — A timestamp interval, not a scalar, is the honest representation of "now" in a distributed system with bounded clock error; treating it as a scalar is where bugs hide.
  • P5 — Locks are held through the full commit-wait, never released early — releasing early is the single most common way to silently break external consistency.
  • P6 — The 2PC log is the only source of truth on recovery; a recovering coordinator resolves in-doubt transactions to the log, never to a freshly re-derived guess.
  • P7 — Every participant vote and commit decision is durable before it is acted upon — "durable" means replicated by consensus, not merely fsynced to one disk.
  • P8 — Wound-wait deadlock avoidance is preferred over detection because detection round-trips add latency to the already latency-sensitive commit path.
  • P9 — Clock-uncertainty violations are treated as correctness incidents, not availability incidents — the response is to halt commits, not to degrade gracefully.
  • P10 — Monotonicity of commit timestamps must survive coordinator failover; a new coordinator epoch must never assign a timestamp less than or equal to one already assigned.
  • P11 — The commit path (2PC + commit-wait) and the read path (MVCC snapshot read) are architected as separate concerns with separate latency budgets — conflating them inflates read latency for no correctness benefit.
  • P12 — Determinism in the verification harness (sim_harness) is non-negotiable — every injected fault must be replayable byte-for-byte to debug a counterexample.
  • P13 — Backpressure beats unbounded queuing everywhere a WAN round-trip is involved — an unbounded prepare-vote queue turns a slow participant into a coordinator memory leak.
  • P14 — Protocol messages are versioned from the start; a coordinator and a participant must be able to disagree on version and fail closed, not silently misinterpret a field.
  • P15 — A read-only fast path and a write-heavy commit path are architecturally distinct concerns from the first line of code, not an optimization bolted on later — conflating them anywhere makes every subsequent phase's latency reasoning unreliable.
  • P16 — Every fault-injection scenario must be seeded and replayable; an unreproducible counterexample is worse than no counterexample, because it erodes confidence in the checker itself.
  • P17 — A metric that cannot distinguish "slow because of contention" from "slow because of clock uncertainty" from "slow because of network" is not yet a useful metric — telemetry granularity is a first-class design decision, not an afterthought.
  • P18 — Recovery logic is exercised as often as the fault-injection harness runs, never left as a code path that only executes during a real production incident for the first time.

8. Domain Model

TrueTime API

TT.now() -> TTInterval(earliest, latest), with the guarantee latest - earliest <= 2*epsilon for a configured bound epsilon. Two derived rules:

  • Start rule: a transaction's candidate commit timestamp s is chosen such that s >= TT.now().latest at the moment of choosing.
  • Commit-wait rule: the coordinator must wait until TT.now().earliest > s before releasing locks or exposing the commit to readers.

Worked external-consistency example: transaction T1 finishes (releases locks) at absolute real time t_end(T1). Because of commit-wait, TT.now().earliest > s1 held at t_end(T1), so s1 < TT.now().earliest at every real time >= t_end(T1). Transaction T2, starting at real time t_start(T2) >= t_end(T1), picks s2 >= TT.now().latest >= TT.now().earliest > s1. Hence s2 > s1, establishing I1 directly from the two rules — the proof requires no assumption beyond the bounded-interval guarantee.

Hybrid Logical Clock (HLC) comparison: HLC ((physical, logical) pairs, as CockroachDB uses) provides causality tracking without special clock hardware, but has no bounded-uncertainty guarantee — external consistency under HLC alone requires either a conservatively large fixed uncertainty window or accepting occasional read restarts when a transaction observes a timestamp from "the future" of its own clock. TrueTime's advantage is a bounded and monitored epsilon; HLC's advantage is zero special hardware. See §36 for this tradeoff as an alternative architecture.

2PC Protocol (sequence table)

Step Coordinator Participant
1 send PREPARE(txn, writes) to all participants receive PREPARE
2 — validate locks, durably log intent via consensus write, reply VOTE(commit|abort)
3 collect votes; if all COMMIT, assign commit_ts —
4 append COMMIT decision to 2PC log (durable) —
5 send COMMIT(txn, commit_ts) to all participants receive COMMIT, apply via consensus write, ack
6 commit-wait until TT.now().earliest > commit_ts —
7 release locks, ack client release locks

Worked cross-shard commit: transaction touches shards A and B. Coordinator sends PREPARE to A and B in parallel; both log the prepare via their own consensus group and vote COMMIT; coordinator picks commit_ts = TT.now().latest at decision time, durably logs COMMIT, fans out COMMIT to A and B, then commit-waits before releasing locks and acking the client.

Worked coordinator-failure recovery: coordinator crashes after step 4 (COMMIT durably logged) but before step 5 completes at participant B. A new coordinator (or the same one restarting) replays the 2PC log, finds a logged COMMIT decision for the transaction, and re-drives step 5 to B — B was already committed at A, so this preserves I2 and I6 without asking A or B to re-vote.

MVCC Model

Concept Representation Rule
Version (key, commit_ts, value) immutable once written
Snapshot read at t scan version chain for max(commit_ts) <= t never blocks on locks
Write intent provisional version tagged PENDING invisible to readers until COMMIT applied
GC remove versions older than the oldest active snapshot timestamp never remove a version a live snapshot may still need

Worked snapshot read: a read-only transaction picks read_ts = TT.now().latest (no commit-wait needed — it writes nothing), and for each key returns the newest version with commit_ts <= read_ts, ignoring PENDING intents entirely.

Isolation level achieved: external consistency plus one-copy serializability, which sits at the strict-serializable point of the Berenson/Adya hierarchy — strictly above snapshot isolation (which permits write skew) and above plain serializability (which does not order w.r.t. real time).

Lock model: exclusive locks for writes, shared for reads-that-must-block (rare, given snapshot reads); wound-wait assigns each transaction a start-timestamp-derived priority — an older transaction wounds (aborts) a younger one holding a conflicting lock rather than waiting, which is deadlock-free by construction (no cycle can form when all edges point from younger to older).

Transaction Lifecycle State Machine

   BEGIN
     |
     v
  PENDING --prepare fails/any NO vote--> ABORTED
     |
     | all PREPARE votes COMMIT
     v
  PREPARED --coordinator crash before decision--> IN_DOUBT --replay resolves--> COMMITTED|ABORTED
     |
     | commit_ts assigned, decision logged
     v
  COMMITTED --commit-wait--> (locks released, visible)

Failure edges: PENDING -> ABORTED on any participant timeout or NO vote; PREPARED -> IN_DOUBT on coordinator crash before the decision is durably logged (resolved on recovery per I6, never left standing); COMMITTED is terminal and irreversible (I13); ABORTED is terminal.

Malformed / Hard Examples

  • Coordinator crash between prepare and commit, leaving participants in-doubt — resolved per I6 via 2PC log replay (§ Phase 7).
  • A clock-uncertainty spike inflating commit-wait — clock_monitor extends the wait per I5 rather than truncating it, at a latency cost (§ Phase 10).
  • A wound-wait cycle attempt — broken within one detection interval per I10 (§ Phase 8).
  • A snapshot read racing a commit — the read observes the pre-commit version because the intent is PENDING until the consensus-replicated COMMIT lands (§ Phase 9).
  • A participant's consensus group losing quorum mid-2PC — the coordinator's PREPARE or COMMIT RPC times out; the transaction remains PREPARED/IN_DOUBT until quorum is restored, never guessed at (§ Phase 7-8).
  • A clock that violates its epsilon bound — the single correctness-critical failure; clock_monitor trips the fail-safe and halts new commits cluster-wide until the bound is re-established (§ Phase 10, I11).

Failure-path example: participant B's consensus group loses its leader mid-PREPARE. The coordinator's RPC to B times out; the transaction stays PREPARED at A (locks held) and un-decided at B. The coordinator retries PREPARE to B on a bounded backoff; if B's group re-elects within the transaction's max-duration budget, PREPARE proceeds normally; if not, the coordinator aborts and sends ABORT to A, releasing A's locks — no commit_ts is ever assigned for an outcome that did not reach all-COMMIT votes.

12.6 Pitfalls

  • Off-by-one on commit_ts <= read_ts vs < — silently breaks I4 in one direction.
  • GC racing an in-flight read holding an older read_ts reference — must snapshot the retention floor before sweeping.
  • Treating tombstones as ordinary deletions instead of versioned markers, losing point-in-time visibility of prior values.
  • Non-deterministic dict iteration order leaking into version-chain scan order, breaking reproducibility (P12) before it even matters.
  • Skipping the baseline benchmark in step 20 and later having no reference point to attribute Phase 4-6 latency growth to coordination overhead versus storage overhead (§34).

12.7 Performance Concerns

  • Version-chain scan is O(chain depth); unbounded growth without GC degrades read latency (§4 target: chain depth <= 50).
  • Naive full-chain scan per read; a real target (§30) is an index by commit_ts descending to short-circuit early.
  • GC sweep cost itself must be bounded and off the read/write hot path, or it becomes a self-inflicted tail-latency source before any real workload exists.

12.8 Edge Cases

  • Read at a timestamp older than the oldest retained version (post-GC) — must raise StaleSnapshotReadError, not return wrong data.
  • Write with a commit_ts older than an existing version's commit_ts for the same key — must be rejected (writes are monotonic per key in this phase; cross-shard reordering issues arrive in later phases).
  • Empty version chain read — must return "not found," not raise.
  • A GC sweep running concurrently with a burst of writes to the same key — the sweep must observe a consistent snapshot of the chain, not a torn read of it.

12.9 Failure Analysis

A GC bug that removes a version still needed by a live read manifests as StaleSnapshotReadError spikes in the property-test suite; the recovery action in this phase is purely developmental (fix and re-run), since no production traffic exists yet — but the detection method (retention-floor audit) is the same one carried into Phase 9's operational monitoring.

A reproducible-build check failure at this phase is treated as a release-blocking finding even though nothing ships yet, because the whole point of establishing it in Phase 0 (per P12 and ADR-26) is to make its violation impossible to reintroduce silently in any later phase.

12.10 Operational Notes

Even at this early phase, wire the reproducible-build check and lint gate into CI exactly as they will run for the rest of the project (ADR-24, ADR-26) — retrofitting reproducibility later is far more expensive than establishing it now.

The Phase 0 baseline benchmark figure belongs on the same dashboard axis as every later phase's latency metrics (§26, §30) from day one, so that a reviewer can see the incremental cost each subsequent phase adds rather than only the final cumulative number.

  • A snapshot read whose deadline_ns has already passed at call time — must reject immediately rather than attempt the read.

13.9 Failure Analysis

If the placeholder counter ever regresses (e.g., process restart resetting it), snapshot reads could silently see a different visibility ordering than writers intended; this phase adds an assertion that the counter is monotonic across restarts within a test harness restart-simulation, foreshadowing I8's full treatment in Phase 6.

Because this phase's timestamp source is explicitly a placeholder, any correctness finding here is scoped to the transaction-level wrapper logic, not the timestamp source itself — the debugging methodology is to first confirm whether a failure reproduces against the Phase 0 MvccStore directly before investigating the new wrapper.

13.10 Operational Notes

Expose snapshot_read_latency_ms as a histogram from this phase onward; it is one of the two headline read-path metrics reused unchanged through §26.

The Phase 1 baseline is the first point at which read-path and write-path latency can be compared side by side, even before the write path has any coordination overhead — establish that comparison view in the dashboard now so its shape is familiar before Phase 4-6 change it substantially.

14. Phase 2 — TrueTime/HLC Clock API and Epsilon

14.1 Objectives

Replace the Phase 1 placeholder counter with a real TrueTimeInterval-returning TT.now() (simulated bounded uncertainty, per ADR-02 and ADR-17), implement Epsilon configuration, and implement the comparison Hlc clock (ADR-36 fallback groundwork).

14.2 Detailed Implementation Steps

  1. Implement TrueTimeInterval(earliest, latest) as a frozen dataclass.
  2. Implement a simulated clock daemon publishing intervals with configurable, injectable epsilon (ADR-17).
  3. Enforce latest - earliest <= 2*epsilon as an assertion in the simulated daemon itself.
  4. Implement TT.now() client API consulted by timestamp_oracle and (later) clock_monitor.
  5. Implement Hlc (physical, logical) as a separate, parallel clock for later comparison (§36).
  6. Implement clock-skew injection hooks for sim_harness (drift forward, drift backward, epsilon spike).
  7. Implement ClockMonitor skeleton: continuously samples TT.now() width (full I11 enforcement lands Phase 10).
  8. Add telemetry: epsilon_current_ms, epsilon_bound_violations (I11).
  9. Add property tests: the simulated daemon never emits an interval wider than 2*epsilon under normal operation.
  10. Add fault-injection tests: when epsilon is artificially widened, the monitor's sample reflects it within one sampling interval.
  11. Update TimestampOracle.assign_start_ts() to the real start rule: s >= TT.now().latest (P4, §8).
  12. Document the TrueTime-vs-HLC tradeoff (§8, §36) in docs/adr/ADR-02.md.
  13. Add tools/cli.py clock-status showing current interval and epsilon.
  14. Wire epsilon as a cluster-wide config value validated at startup.
  15. Implement an Epsilon change-audit log so any runtime reconfiguration of the bound is itself a traceable, timestamped event (groundwork for the Phase 10 fail-safe's forensic trail).
  16. Add a differential fixture comparing Hlc ordering against TrueTimeInterval ordering on the same synthetic event stream, feeding §33's later comparative table directly.
  17. Add docs/performance/phase2-baseline.md recording TT.now() call overhead in isolation, before it becomes load-bearing on the Phase 6 commit-wait hot path.

14.3 Deliverable

A simulated TrueTime clock service exposing TT.now() -> TrueTimeInterval, a configurable and monitored epsilon, a parallel Hlc implementation for later comparison, the real start rule wired into TimestampOracle, and a recorded baseline for TT.now() call overhead ahead of its Phase 6 criticality.

14.4 Acceptance Criteria

  • 100,000 sampled intervals from the simulated daemon never exceed width 2*epsilon under normal (non-injected) operation.
  • Injected epsilon spikes are visible in epsilon_current_ms within one sampling interval.
  • assign_start_ts() always returns s >= TT.now().latest at call time (spot-checked in property tests).
  • TT.now() call overhead stays sub-millisecond in the recorded baseline.
  • Every runtime epsilon reconfiguration appears in the change-audit log with a timestamp and prior/new value.

14.5 Conformance Fixtures

  • conformance/phase2/epsilon_bound_normal.json — normal-operation interval-width sampling.
  • conformance/phase2/epsilon_spike_injection.json — injected widening, monitor visibility check.
  • conformance/phase2/hlc_vs_truetime_ordering.json — comparison fixture used again in §36/§33.
  • conformance/phase2/epsilon_reconfiguration_audit.json — verifies the change-audit log captures a runtime bound change.

14.6 Pitfalls

  • Simulated daemon accidentally emitting a zero-width interval, masking bugs that only manifest under real uncertainty (Corbett et al. 2012's guarantee is <=, not =).
  • Sampling the clock monitor too infrequently to catch a transient epsilon spike (§4: monitor must sample at least as often as the daemon publishes, sub-1ms).
  • Confusing Hlc causality tracking with TrueTimeInterval bounded uncertainty — they answer different questions and must not be interchanged in timestamp_oracle.
  • Omitting the change-audit log for epsilon reconfiguration, leaving no forensic trail if a bound change later correlates with an I11 violation.

14.7 Performance Concerns

  • TT.now() call overhead on the commit-wait hot path (Phase 6) must stay sub-millisecond; benchmark it here before it is load-bearing.
  • The Hlc comparison path must not be computed on every TT.now() call in later phases — it is a comparison/fallback tool, not a dual-write hot-path cost (ADR-02).

14.8 Edge Cases

  • Epsilon reconfigured mid-run — must not retroactively invalidate already-in-flight commit-wait calculations from before the change.
  • Clock daemon process restart — must not emit a narrower-than-honest interval immediately after restart (a false sense of tightened uncertainty).
  • Two concurrent epsilon reconfiguration requests racing — the audit log must record a single consistent final value, not an interleaved partial write.

14.9 Failure Analysis

An interval wider than 2*epsilon from the simulated daemon itself is a test-harness bug, not a production concern yet — but the assertion added in this phase is the direct ancestor of I11's Phase 10 fail-safe, and the failure-handling posture (assert loudly, never silently clamp) is set here.

14.10 Operational Notes

epsilon_current_ms and epsilon_bound_violations are introduced in this phase and never renamed again — they are the two metrics that Phase 10 wires to a page-immediately alert (§26).

The epsilon change-audit log introduced here becomes, in production terms, the first place an operator checks when investigating any correctness incident that might trace back to a clock reconfiguration.

15. Phase 3 — Single-Shard Transactions with 2PL + MVCC

15.1 Objectives

Implement full single-shard read/write transactions combining LockManager (two-phase locking, still without wound-wait — that arrives Phase 8) with MvccStore, producing a complete single-shard ACID transaction with no cross-shard coordination yet.

15.2 Detailed Implementation Steps

  1. Implement Lock, LockMode, and a per-shard LockManager with acquire/release and a FIFO waiter queue.
  2. Implement two-phase locking discipline: all locks acquired before any release (growing/shrinking phases).
  3. Implement Transaction FSM states PENDING -> COMMITTED/ABORTED for the single-shard case (PREPARED/IN_DOUBT arrive with 2PC in Phase 4).
  4. Wire write operations to acquire an exclusive lock, buffer the write as a PENDING intent, and only materialize it in MvccStore at commit.
  5. Wire read operations inside a read-write transaction to acquire a shared lock and read via MvccStore.read at the transaction's start_ts.
  6. Implement commit: assign commit_ts via TimestampOracle, materialize all buffered writes, release all locks.
  7. Implement abort: discard buffered writes, release all locks, no MvccStore mutation.
  8. Add deadlock timeout (crude, pre-wound-wait) so Phase 3 does not hang indefinitely on a cycle.
  9. Add property tests: two-phase locking discipline is never violated (no lock acquired after any release in the same transaction).
  10. Add property tests: committed writes are never visible before commit_ts (still I4, now under concurrent writers).
  11. Add contention benchmarks: single-shard throughput under increasing writer concurrency.
  12. Add tools/cli.py txn-inspect <txn_id> showing FSM state and held locks.
  13. Implement ReadSet/WriteSet freezing on entry to commit (§11), so a transaction's declared footprint cannot silently grow after lock acquisition begins.
  14. Add a lock-table sharding scheme (per-key hash bucket) so lock-table contention itself does not become a single-mutex bottleneck ahead of the Phase 8 wound-wait work.
  15. Add docs/performance/phase3-baseline.md recording single-shard throughput and lock-wait queue depth at increasing concurrency, extending the Phase 0-2 baseline series.

15.3 Deliverable

A complete single-shard transactional engine: begin, read, write, commit, abort, with two-phase locking and MVCC-backed materialization, usable end-to-end without any other shard or coordinator involved, with a recorded contention baseline ahead of Phase 8's wound-wait replacement.

15.4 Acceptance Criteria

  • No transaction violates two-phase locking discipline under 10,000 randomized concurrent-transaction schedules.
  • Committed writes are invisible to any reader with read_ts < commit_ts (I4 under concurrency).
  • Crude timeout-based deadlock breaking prevents indefinite hangs in the benchmark harness (full wound-wait replaces this in Phase 8).
  • ReadSet/WriteSet freezing is enforced: an attempted write after commit has begun is rejected, not silently accepted.
  • Lock-table sharding shows near-linear throughput scaling with bucket count in the recorded baseline.

15.5 Conformance Fixtures

  • conformance/phase3/two_phase_locking_violation.json — must never occur; negative fixture.
  • conformance/phase3/write_skew_check.json — documents current isolation level before wound-wait/full concurrency control lands.
  • conformance/phase3/commit_abort_basic.json — commit and abort scenarios named per the harness requirement.
  • conformance/phase3/frozen_write_set_rejection.json — a post-freeze write attempt is rejected.

15.6 Pitfalls

  • Materializing a write to MvccStore before all locks for the transaction are confirmed held, breaking two-phase locking retroactively.
  • Releasing a lock on abort before all buffered writes are discarded, allowing a reader to observe a half-aborted state.
  • Crude timeout-based deadlock breaking picking the wrong victim (arbitrary, not age-based) — acceptable only because Phase 8 replaces this mechanism entirely.
  • Sharding the lock table by a poorly-chosen hash function that clusters hot keys into one bucket, defeating the point of sharding it at all.

15.7 Performance Concerns

  • Lock-table contention under high single-shard write concurrency; benchmark lock-wait queue depth against the §4 target (100,000 entries max).
  • Buffering writes in memory until commit bounds transaction size — enforce the §4 max commit payload (16 MB) here.
  • Per-bucket lock-table sharding trades a small fixed routing overhead for reduced global contention; measure the crossover point where sharding stops paying for itself at low concurrency.

15.8 Edge Cases

  • A transaction that only reads and never writes — should not acquire exclusive locks at all (this becomes the read-only fast path fully realized in Phase 9).
  • A transaction exceeding the max duration budget (§4: 30 s) — must be forcibly aborted with locks released.
  • Two transactions racing to acquire the same exclusive lock — exactly one proceeds, the other queues in FIFO order.
  • A transaction whose write set spans multiple lock-table shard buckets — must acquire all bucket locks in a globally consistent order to avoid a local cross-bucket deadlock even before Phase 8's cross-transaction wound-wait applies.

15.9 Failure Analysis

A process crash mid-commit (after some writes materialized, before others) is out of scope for correctness in this single-node phase — it becomes correctness-critical in Phase 4 once a durable log exists; here, the acceptance bar is that the benchmark harness never induces a real crash, and the crude timeout mechanism's known limitations are documented, not fixed.

A lock-table sharding bug that acquires cross-bucket locks in inconsistent order is treated with the same severity as the two-phase-locking violation it is a special case of, since both manifest identically to a caller as an unexplained hang.

15.10 Operational Notes

lock_wait_queue_depth and lock_hold_duration_ms are introduced here and reused unchanged through §26; they are the earliest signals of the contention behavior that wound-wait (Phase 8) exists to bound.

The Phase 3 baseline is the last opportunity to measure pure single-shard, no-coordination throughput before Phase 4 introduces cross-shard overhead — keep it as the permanent reference point in the M9 (§30) target discussion.

16. Phase 4 — The 2PC Protocol Across Shards

16.1 Objectives

Extend Phase 3's single-shard transaction to multiple shards using two-phase commit (P2, ADR-03), introducing the Coordinator, Participant split, PrepareRequest/Vote/CommitDecision types, and the PREPARED/IN_DOUBT states — still without consensus underneath participants (that lands Phase 5) and without commit-wait (Phase 6).

16.2 Detailed Implementation Steps

  1. Split the Phase 3 monolith into a Coordinator process and per-shard Participant processes communicating over gRPC (ADR-14).
  2. Implement PrepareRequest and fan out PREPARE to all participants touched by a transaction's write_set.
  3. Implement participant-side prepare handling: acquire locks (Phase 3 lock manager), durably log the intent locally (I9), reply Vote.
  4. Implement coordinator-side vote collection: all COMMIT -> proceed; any ABORT or timeout -> abort all.
  5. Implement CommitDecision construction and the TwoPcLog append (I12) before any COMMIT RPC is sent (I2).
  6. Implement fan-out of COMMIT (or ABORT) to all participants; participants materialize writes and release locks.
  7. Implement the PREPARED transaction state, entered once all votes are COMMIT and before the decision is logged.
  8. Add bounded-queue backpressure (P13, ADR-27) on the PREPARE fan-out path.
  9. Add property tests: I2 (atomicity) holds under randomized single-participant-failure injection.
  10. Add a worked cross-shard commit fixture matching the §8 sequence table exactly.
  11. Add contention/latency benchmarks: cross-shard commit latency vs. participant count (§4, §34).
  12. Add tools/cli.py txn-inspect support for cross-shard transactions (per-participant vote state).
  13. Document the 2PC message-flow diagram in docs/adr/ADR-03.md, cross-referencing project 73's isolated treatment (§1 non-goals).
  14. Implement per-participant vote-collection timeouts distinct from the overall transaction max-duration budget (§4), so a single slow participant can be retried or aborted without immediately sacrificing the whole transaction's time budget.
  15. Add a Participant registry keyed by ShardId so the coordinator can resolve which participants a given write_set touches deterministically (ADR-13 groundwork).
  16. Add docs/performance/phase4-baseline.md recording cross-shard commit latency as a function of participant count, the first direct input to §34's fan-out model.

16.3 Deliverable

A working cross-shard 2PC engine: a coordinator driving PREPARE/COMMIT/ABORT across N participants with a durable coordinator-side 2PC log, achieving atomicity (I2) under single-participant failure, without yet surviving a coordinator crash (Phase 7) or clock-based external consistency (Phase 6), with a recorded fan-out latency curve.

16.4 Acceptance Criteria

  • I2 holds (all-or-nothing) under fault injection killing exactly one participant mid-PREPARE, across 5,000 randomized runs.
  • Cross-shard commit latency p95 (excluding commit-wait, added Phase 6) meets the 2PC-round-trip component of the §4 budget.
  • The 2PC log contains exactly one CommitDecision or abort record per transaction, checksummed (I12).
  • The recorded fan-out latency curve shows the expected tail-amplification shape (bounded by the slowest of N participants), confirmed against 2, 4, 8, and 16 participants.

16.5 Conformance Fixtures

  • conformance/phase4/two_shard_commit_success.json — the canonical worked cross-shard commit from §8.
  • conformance/phase4/participant_abort_vote.json — one NO vote aborts all.
  • conformance/phase4/participant_timeout_during_prepare.json — timeout treated as an implicit ABORT vote.
  • conformance/phase4/sixteen_participant_fanout.json — the maximum §4 fan-out ceiling exercised directly.

16.6 Pitfalls

  • Sending COMMIT to any participant before the CommitDecision is durably logged coordinator-side, breaking I2 on a coordinator crash mid-fan-out (fully addressed in Phase 7, but the ordering discipline must start here).
  • Treating a PREPARE timeout as "still pending" indefinitely instead of a bounded-retry-then-abort, violating the max transaction duration budget (§4).
  • Materializing writes at a participant before receiving the actual COMMIT RPC, based only on having voted COMMIT itself.
  • Conflating the per-participant vote-collection timeout with the overall transaction deadline, causing a single slow participant to silently consume the whole transaction's remaining time budget.

16.7 Performance Concerns

  • PREPARE fan-out latency is bounded by the slowest participant (tail amplification) — this is the direct ancestor of the §34 cross-shard-vs-single-shard cost-ratio model.
  • Bounded queues (ADR-27) must not themselves become a throughput ceiling under normal (non-degraded) load; size them against the §4 fan-out ceiling (16 participants).

16.8 Edge Cases

  • A transaction touching only one shard — must not incur the full 2PC round-trip (optimization deferred, but correctness must not regress: a single-participant 2PC is still a degenerate-but-valid 2PC run in this phase).
  • Duplicate PREPARE delivery (retried RPC) — must be idempotent at the participant (keyed by txn_id).
  • All participants vote COMMIT but the coordinator itself crashes before logging the decision — explicitly out of scope for correctness until Phase 7; document the current gap here.
  • A participant registry lookup for a ShardId that does not exist (misconfiguration) — must fail the transaction cleanly at PREPARE time, not silently skip that shard's writes.

16.9 Failure Analysis

Because Phase 7 has not yet added crash recovery, a coordinator crash between vote collection and log-write in this phase is a known, documented gap — an acceptable, explicitly deferred failure mode for this phase's acceptance bar, closed in the very next phase.

16.10 Operational Notes

Introduce twopc_commit_latency_ms (excluding commit-wait) and twopc_abort_rate here; both are reused unchanged through §26 and later split by cause (participant abort vs. timeout) in Phase 7's telemetry additions.

The fan-out latency curve recorded in this phase becomes the baseline that §31's scalability analysis and §34's capacity model both cite directly — keep the raw benchmark data, not just the summary figure, for later re-derivation.

17. Phase 5 — Layering 2PC Prepare/Commit Over Per-Shard Consensus

17.1 Objectives

Replace each participant's local-only prepare/commit logging (Phase 4) with a real replicated ConsensusGroup (consensus_shim), so that a participant's vote and commit application are themselves consensus-replicated writes (P2, ADR-04, ADR-05, Gray & Lamport 2006) — a participant survives node loss without losing a 2PC vote.

17.2 Detailed Implementation Steps

  1. Implement consensus_shim: a minimal Paxos/Raft-style single-value-per-slot replicated log (Lamport 2001, Ongaro & Ousterhout 2014).
  2. Implement leader election, log replication, and a majority-quorum commit rule within consensus_shim.
  3. Route participant prepare-vote logging through a consensus-replicated write, not a local file (I3, I9).
  4. Route participant commit-application through a second consensus-replicated write.
  5. Implement participant-side read of "what did we vote / did we apply commit" from the consensus log on restart (groundwork for Phase 7's in-doubt handling at the participant side).
  6. Implement quorum-loss detection: a participant whose consensus group cannot reach majority must not vote or apply (I3 enforced structurally).
  7. Add fault injection: kill a minority of a participant's consensus-group nodes mid-2PC; verify the participant still votes/commits correctly via the surviving majority.
  8. Add fault injection: kill a majority (quorum loss); verify the coordinator's PREPARE/COMMIT RPC blocks/times out rather than silently succeeding.
  9. Add property tests: no participant ever applies a commit that was not majority-replicated (I3).
  10. Add consensus-round latency benchmarks (§4 target: 6 ms p99) feeding into §34's capacity model.
  11. Document the 2PC-over-consensus composition explicitly as Paxos Commit (Gray & Lamport 2006) in docs/adr/ADR-05.md.
  12. Implement a ConsensusGroup health-check surface (member liveness, current leader, log-index lag) consumed by both the coordinator (for routing) and tools/cli.py (for operator inspection).
  13. Add fault injection: a full network partition isolating one consensus-group node from the rest, distinct from a hard kill, to exercise partition-specific behavior (message loss vs. process death) ahead of Phase 11's combined chaos scenarios.
  14. Add docs/performance/phase5-baseline.md recording the added consensus-round latency layered on top of the Phase 4 fan-out baseline.

17.3 Deliverable

Every participant is now a replicated consensus group of 3 or 5 nodes; every prepare vote and commit application is a majority-replicated write before it is acted on or reported to the coordinator, closing the single-node-loss gap left open in Phase 4, with a health-check surface and a recorded latency delta over the Phase 4 baseline.

17.4 Acceptance Criteria

  • I3 holds under minority-node-kill fault injection across 5,000 runs: no vote or commit is ever lost.
  • Quorum loss (majority killed) causes the coordinator's RPC to time out, never to silently succeed or silently corrupt state.
  • Consensus-round p99 latency meets the §4 target under nominal load.
  • The health-check surface correctly reports current leader and log-index lag under both nominal operation and injected partition.
  • Partition-based fault injection (message loss, not process death) produces the same I3-preserving outcome as the hard-kill fault injection.

17.5 Conformance Fixtures

  • conformance/phase5/minority_node_kill_during_prepare.json — vote survives.
  • conformance/phase5/majority_quorum_loss.json — coordinator times out cleanly.
  • conformance/phase5/leader_reelection_mid_commit.json — commit application survives a leadership change within the group.
  • conformance/phase5/network_partition_vs_hard_kill.json — confirms equivalent I3-preserving behavior under both fault types.

17.6 Pitfalls

  • Allowing a participant to vote COMMIT based on a leader-local write that has not yet reached majority replication — silently reintroduces the Phase 4 gap.
  • Failing to fence a deposed consensus-group leader, allowing a stale leader to double-apply a commit after a new leader was already elected.
  • Conflating consensus-log compatibility (§27) with 2PC-log compatibility — they are versioned independently (ADR-05 note) and must not share a schema.
  • Treating a network partition as equivalent to a hard kill in the fault-injection harness, missing partition-specific bugs like a stale leader that can still receive but not send.

17.7 Performance Concerns

  • Every 2PC round now costs at least one consensus round per participant per phase (prepare, commit) — this doubling is the direct input to §34's cross-shard latency model; do not let a naive implementation add a third round accidentally.
  • The health-check surface's polling frequency must not itself add meaningful load to the consensus group it is monitoring.

17.8 Edge Cases

  • A consensus-group leader election happening concurrently with an in-flight PREPARE — the PREPARE must be retried against the new leader, not lost.
  • A participant that was partitioned away during PREPARE and rejoins after COMMIT was already applied elsewhere in its group — must catch up via consensus log replay, not via the 2PC RPC.
  • A minority partition that can still see the coordinator but not its own group's leader — must not be able to independently ack anything on the coordinator's behalf.

17.9 Failure Analysis

A participant reporting a vote that later turns out not to have reached majority replication (a bug, not an expected fault) is the single most dangerous regression this phase guards against — the property test in step 9 exists specifically to catch it before Phase 7 builds recovery logic on top of the assumption that I3 always holds.

A health-check surface reporting stale leader information after an election is a distinct, lower-severity bug class from an actual I3 violation, and the debugging methodology treats the two very differently: the former is an observability defect, the latter is release-blocking.

17.10 Operational Notes

Expose consensus_round_latency_ms and quorum_loss_events per shard from this phase forward; quorum_loss_events becomes one of the named alert conditions in §26 (quorum-loss runbook).

The health-check surface introduced here is what the quorum-loss runbook (§26) instructs an operator to consult first, before any log inspection.

18. Phase 6 — The Commit-Wait Rule and External Consistency

18.1 Objectives

Implement the commit-wait rule (P1, I1, I5) using the real TT.now() from Phase 2, closing the loop that makes external consistency actually hold — this is the load-bearing phase of the entire project.

18.2 Detailed Implementation Steps

  1. Implement TimestampOracle.commit_wait(commit_ts): block until TT.now().earliest > commit_ts (§8 commit-wait rule).
  2. Insert commit-wait into the coordinator's commit path strictly after the CommitDecision is logged and strictly before locks are released or the client is acked (I7, P5).
  3. Ensure commit-wait duration is computed fresh from TT.now() on each poll, never assumed from a static 2*epsilon constant (I5: must cover the actual interval, which may be wider under a transient epsilon spike).
  4. Implement epoch fencing in TimestampOracle so that a new coordinator epoch cannot assign a commit_ts less than or equal to any timestamp assigned by a prior epoch (I8, P10).
  5. Add the worked external-consistency proof from §8 as an executable property test: T1 finishes before T2 starts in simulated real time implies commit_ts(T1) < commit_ts(T2).
  6. Add fault injection: widen epsilon mid-commit-wait; verify the wait extends rather than truncates (I5).
  7. Add fault injection: two non-overlapping transactions racing under tight simulated real-time gaps; verify ordering never inverts.
  8. Add telemetry: commit_wait_ms histogram, separated from twopc_commit_latency_ms (Phase 4) so the two latency components are independently visible (§30 methodology).
  9. Add a coordinator-epoch-failover fixture proving I8 holds across a simulated coordinator restart with a new epoch.
  10. Update sim_harness to begin recording full commit-wait timing traces for later Elle-style analysis (Phase 11 groundwork).
  11. Implement a bounded max-wait alarm: if commit-wait exceeds a generous multiple of the configured epsilon, surface a warning distinct from the Phase 10 fail-safe (which trips on the clock bound itself, not on wait duration).
  12. Add a dedicated docs/adr/ADR-08.md write-up of the commit-wait implementation choice (explicit polling vs. static sleep) with the worked proof from §8 reproduced as its rationale.
  13. Add docs/performance/phase6-baseline.md recording end-to-end commit latency (2PC round-trip plus commit-wait) at several configured epsilon values, directly instantiating the §34 commit-wait-duration formula.

18.3 Deliverable

A coordinator that never releases locks or exposes a commit before waiting out the full, dynamically-measured clock-uncertainty interval, with monotonic cross-epoch timestamp assignment — external consistency now holds end-to-end for the fault-free path, with a recorded latency curve across multiple epsilon configurations validating the §34 model empirically.

18.4 Acceptance Criteria

  • Zero external-consistency violations (I1) across 20,000 randomized non-overlapping-transaction pairs in sim_harness.
  • Commit-wait duration always >= 2*epsilon at the time of the wait, and always extends (never truncates) under injected epsilon widening (I5).
  • Zero timestamp regressions across 1,000 simulated coordinator-epoch failovers (I8).
  • The recorded latency curve across epsilon values matches the §34 2*epsilon formula within measurement noise.
  • The bounded max-wait alarm fires distinctly from (and before) the Phase 10 fail-safe in a fixture where the wait is merely slow, not the clock actually out of bound.

18.5 Conformance Fixtures

  • conformance/phase6/external_consistency_nonoverlapping.json — the canonical worked proof as an executable fixture.
  • conformance/phase6/commit_wait_epsilon_spike.json — wait extension under injected spike.
  • conformance/phase6/epoch_failover_monotonicity.json — I8 across simulated failover.
  • conformance/phase6/commit_wait_duration_formula.json — validates measured wait duration against the 2*epsilon formula at several configured bounds.

18.6 Pitfalls

  • Computing commit-wait duration once at commit-decision time and sleeping a fixed interval, instead of polling TT.now() — silently breaks I5 under any epsilon spike during the wait.
  • Releasing locks optimistically "because the wait should be over by now" without an actual final TT.now() check (P5, I7).
  • Forgetting epoch fencing entirely and allowing a freshly-restarted coordinator to reuse a low-numbered timestamp range, breaking I8 without any epsilon involvement at all.
  • Confusing the bounded max-wait alarm (an operational hint that something is slow) with the Phase 10 fail-safe (a correctness-critical halt) — they must remain distinct severities in telemetry and alerting.

18.7 Performance Concerns

  • Commit-wait is now the latency floor of every write transaction (§4, §34) — any implementation inefficiency here (e.g., busy-polling TT.now() at too high a frequency) adds CPU cost without shortening the wait, since the wait's duration is fixed by epsilon, not by polling rate.
  • Choose a polling interval for the commit-wait loop that balances responsiveness (detecting earliest > commit_ts promptly) against CPU overhead at high transaction concurrency.

18.8 Edge Cases

  • TT.now().earliest never crosses commit_ts because the clock daemon itself is stalled — must eventually surface as a clock_monitor alert (Phase 10) rather than an indefinite silent hang; this phase adds a bounded max-wait alarm as a stopgap.
  • A read-only transaction (Phase 1/9) must never be subjected to commit-wait — verify the read-only fast path remains untouched by this phase's changes (P11).
  • A transaction whose commit_ts was assigned just before an epoch failover — the new epoch's fencing must not retroactively invalidate a commit-wait already legitimately in progress under the old epoch.

18.9 Failure Analysis

If the external-consistency property test ever produces a counterexample, the debugging methodology from §7 applies directly: replay the recorded sim_harness seed, inspect the two transactions' TT.now() samples and commit-wait traces, and check first whether epoch fencing (I8) or the wait-extension rule (I5) was the actual point of failure — the two are the only two ways this guarantee can break given the Phase 4-5 foundation already holds.

A discrepancy between the measured latency curve and the §34 formula beyond expected measurement noise is itself a finding worth investigating before proceeding to Phase 7, since it may indicate the polling implementation is adding unaccounted-for overhead to every single write transaction going forward.

18.10 Operational Notes

commit_wait_ms becomes, from this phase forward, the headline write-latency metric surfaced in every dashboard (§26); operators must be able to distinguish "slow because of contention" (Phase 3/8 telemetry) from "slow because epsilon is wide" (this phase's telemetry) at a glance.

The recorded epsilon-vs-latency curve from this phase is the single most useful artifact for justifying a future clock-hardware investment (§31's commit-wait-vs-clock-tightness tradeoff) — keep it current as the implementation evolves.

19. Phase 7 — Coordinator Failure and In-Doubt Recovery

19.1 Objectives

Implement RecoveryManager and the IN_DOUBT state fully (I6), so that a coordinator crash at any point in the 2PC sequence (§8) is resolved deterministically from the durable TwoPcLog on restart, never left blocking locks indefinitely.

19.2 Detailed Implementation Steps

  1. Implement the IN_DOUBT transition: any PREPARED transaction whose owning coordinator has not logged a decision within a bounded window is marked IN_DOUBT by a fresh coordinator instance on restart.
  2. Implement RecoveryManager.scan(): replay the TwoPcLog from the last checkpoint, reconstructing the state of every transaction that was PREPARED or COMMITTED at crash time.
  3. Implement resolution: for a transaction with a logged CommitDecision, re-drive COMMIT to any participant that has not yet acknowledged it (I6); for one with no logged decision, drive ABORT to all participants.
  4. Implement participant-side idempotent handling of a re-driven COMMIT/ABORT (already covered structurally by Phase 4's idempotency requirement, now exercised under real crash-restart).
  5. Implement a 2PC log checkpoint mechanism so replay does not have to scan an unbounded log on every restart.
  6. Add fault injection: crash the coordinator at each of the seven §8 sequence-table steps in turn; verify recovery reaches the correct terminal state every time.
  7. Add the "coordinator crash between prepare and commit" worked example from §8 as an executable fixture.
  8. Add telemetry: in_doubt_transaction_count, in_doubt_resolution_time_ms (§4 target: < 10 s).
  9. Add a bound on how long a transaction may remain IN_DOUBT before an operator alert fires (feeds §26's named runbook).
  10. Add property tests: I2 and I6 both hold across all seven crash-point injections, combined with the Phase 5 consensus-loss injections.
  11. Add tools/cli.py in-doubt-list and tools/cli.py in-doubt-resolve --force (manual override, audited).
  12. Implement a recovery-time benchmark harness that varies checkpoint distance and affected-transaction count independently, directly instantiating the §34 in-doubt-recovery-time formula.
  13. Add a RecoveryCheckpoint integrity check (§11) so a corrupted checkpoint is detected and rejected in favor of the next-older valid checkpoint, rather than silently used.
  14. Document the full in-doubt-transaction-resolution runbook (§26) alongside this phase's implementation, not deferred to the operational-readiness write-up later.

19.3 Deliverable

A coordinator that can crash at any point in the 2PC sequence and, on restart, deterministically resolve every affected transaction to the correct terminal state within the §4 recovery-time budget, using only the durable 2PC log — no transaction is ever left blocking locks forever — with a recovery-time benchmark validating the §34 formula and a checkpoint-integrity safeguard.

19.4 Acceptance Criteria

  • 100% of transactions reach a terminal state (COMMITTED or ABORTED) within 10 s of coordinator restart, across all seven crash-point injections x 1,000 runs each (§4, I6).
  • Zero cases of a transaction resolved to an outcome inconsistent with its logged CommitDecision (I2, I6).
  • in_doubt_transaction_count returns to zero after every recovery run in the fixture suite.
  • The recovery-time benchmark's measured values fall within the range predicted by the §34 formula across at least three checkpoint-distance configurations.
  • A corrupted checkpoint is detected and recovery falls back to the next-older valid checkpoint without operator intervention.

19.5 Conformance Fixtures

  • conformance/phase7/crash_after_prepare_before_decision.json — resolves to ABORT (no decision logged).
  • conformance/phase7/crash_after_decision_before_fanout.json — the canonical §8 worked recovery example; resolves to COMMIT, re-drives fan-out.
  • conformance/phase7/crash_during_commit_wait.json — decision already logged; recovery must still enforce commit-wait before considering the transaction externally visible, not skip it.
  • conformance/phase7/corrupted_checkpoint_fallback.json — recovery falls back to the next-older valid checkpoint.

19.6 Pitfalls

  • Resolving an IN_DOUBT transaction by re-asking participants to vote again instead of consulting the log — risks a different outcome than what a participant may have already partially applied (ADR-12).
  • Forgetting that a crash during commit-wait (decision already logged, wait incomplete) must resume the wait on recovery, not skip straight to "committed and visible" (I5 still applies during recovery).
  • Unbounded 2PC log growth without checkpointing, making recovery-time scale with cluster history instead of recent activity, violating the §4 recovery-time budget over the cluster's lifetime.
  • Trusting a checkpoint's contents without an integrity check, risking a recovery built on corrupted state that then propagates incorrect decisions to participants.

19.7 Performance Concerns

  • Recovery-time scales with the distance since the last checkpoint; checkpoint frequency is a direct lever on the §4 10-second target and must be benchmarked, not assumed.
  • Checkpoint-writing itself must not stall the coordinator's ability to keep logging new prepare/commit decisions during the checkpoint operation.

19.8 Edge Cases

  • Multiple transactions IN_DOUBT simultaneously after a coordinator crash affecting many concurrent transactions — recovery must resolve all of them, not just the first found.
  • A participant that was also down during the coordinator crash and recovery, rejoining later — must independently catch up via its own consensus log (Phase 5) and correctly apply a re-driven COMMIT/ABORT it missed.
  • --force manual resolution invoked by an operator on a transaction that is, in fact, resolvable automatically — must refuse or warn loudly, since bypassing the log is a correctness hazard (I6).
  • Every available checkpoint being corrupted (a cascading failure) — recovery must fall all the way back to a full-log replay from genesis rather than proceeding on any unverified state.

19.9 Failure Analysis

An IN_DOUBT transaction that fails to resolve within the alert threshold is escalated per the in-doubt-transaction-resolution runbook (§26): the forensic first step is always "does the 2PC log have a decision for this txn_id," because every other recovery action is downstream of that single fact per I6.

A recovery-time benchmark that diverges meaningfully from the §34 formula's prediction is investigated before Phase 8 begins, since an unexplained gap here usually indicates an inefficiency in the checkpoint-scan implementation that would otherwise silently erode the §4 recovery-time budget as the cluster's log history grows.

19.10 Operational Notes

This phase's telemetry (in_doubt_transaction_count, in_doubt_resolution_time_ms) and its CLI tooling (in-doubt-list) are exactly what operators use in production; document the manual-override audit trail requirement here, since it is the only place in the system where an operator can override a logged decision, and it must never be silent.

The checkpoint-integrity safeguard introduced here is the direct ancestor of the FM-9 (§25) disk-capacity failure mode's mitigation — a corrupted or missing checkpoint should never be a silent single point of recovery failure.

20. Phase 8 — Wound-Wait Deadlock Handling

20.1 Objectives

Replace Phase 3's crude timeout-based deadlock breaking with proper wound-wait (P8, I10, ADR-10), assigning transaction priority from start_ts so that no detection round-trip is ever needed on the commit-critical path.

20.2 Detailed Implementation Steps

  1. Implement WoundWait.compare(older, younger) using start_ts as the priority key (lower start_ts = older = higher priority).
  2. Modify LockManager.acquire(): on conflict, if the requester is older than the holder, wound (abort) the holder and proceed; if younger, wait.
  3. Implement wound signaling: an aborted-by-wound transaction receives an explicit abort reason distinct from a voluntary abort.
  4. Implement cascading-wound handling: a transaction wounded while itself holding locks must release them immediately, potentially unblocking further waiters.
  5. Prove-by-construction that no cycle can form (I10): every wait edge points from a younger to an older transaction, so a cycle would require a transaction older than itself.
  6. Add property tests generating randomized lock-acquisition graphs and asserting no deadlock ever persists beyond one wound-wait pass.
  7. Add fault injection: a wounded transaction that was mid-2PC-prepare at a different participant — verify the wound propagates and the transaction aborts cleanly cluster-wide, not just at the local lock table.
  8. Add telemetry: deadlock_cycles_detected (should trend toward the number of wound events, since none should ever mature into a real cycle), wound_events_total, lock_wait_queue_depth (carried from Phase 3).
  9. Remove the Phase 3 crude timeout mechanism entirely, replacing it with wound-wait as the sole deadlock-avoidance path.
  10. Add a starvation check: verify the oldest transaction in a contended benchmark always eventually completes (wound-wait's fairness property).
  11. Implement a deterministic tiebreak (txn_id lexical order) in WoundWait.compare() for the structurally-impossible-but-defensively-handled case of identical start_ts.
  12. Add a cross-shard wound-propagation protocol: a wound decided at one participant's lock table must notify the owning coordinator, which then drives a cluster-wide ABORT exactly as any other abort trigger would (reusing the Phase 4 abort fan-out, not a bespoke path).
  13. Add docs/performance/phase8-baseline.md recording abort rate and lock-wait queue depth under contention, compared directly against the Phase 3 crude-timeout baseline to quantify wound-wait's improvement.

20.3 Deliverable

A per-participant lock manager using wound-wait exclusively for deadlock avoidance, with no detection round-trip on the commit path, integrated with the Phase 4-7 cross-shard 2PC flow so a wound at one participant correctly aborts the transaction everywhere, with a benchmark quantifying the improvement over Phase 3's crude mechanism.

20.4 Acceptance Criteria

  • Zero surviving deadlock cycles across 20,000 randomized concurrent-transaction lock-acquisition graphs (I10).
  • The oldest transaction in every contended benchmark run eventually commits (no starvation).
  • A wound at any single participant results in a full cross-shard ABORT within one 2PC round, not a partial abort.
  • The deterministic tiebreak resolves an identical-start_ts fixture without mutual wounding or a stall.
  • The Phase 8 benchmark shows lower abort latency and lower lock-wait queue depth under contention than the Phase 3 crude-timeout baseline.

20.5 Conformance Fixtures

  • conformance/phase8/deadlock_cycle_two_txn.json — the canonical named deadlock scenario referenced by the harness requirement.
  • conformance/phase8/wound_cascade.json — a wounded transaction itself holding locks that unblock further waiters.
  • conformance/phase8/cross_shard_wound_propagation.json — a wound at one participant aborting the transaction cluster-wide.
  • conformance/phase8/identical_start_ts_tiebreak.json — the deterministic tiebreak fixture.

20.6 Pitfalls

  • Comparing transactions by wall-clock arrival order instead of start_ts, which can disagree under clock skew and silently reintroduce cycles.
  • Wounding a transaction that is already in PREPARED state (post-vote) without correctly transitioning it through ABORT at every participant, violating I2.
  • Forgetting cascading release: a wounded transaction that does not immediately release its own locks can itself deadlock a third transaction.
  • Building a bespoke cross-shard wound-propagation path instead of reusing the Phase 4 abort fan-out, doubling the number of places I2 must be independently verified.

20.7 Performance Concerns

  • Wound-wait avoids detection latency but pays an abort-and-retry cost for the wounded transaction; benchmark abort rate under high contention against the §4 assumptions to confirm the tradeoff (P8) holds in practice, not just in theory.
  • A high wound rate under pathological hot-key contention is a workload-shape problem, not a wound-wait implementation defect — the benchmark must distinguish the two before concluding the mechanism itself needs tuning.

20.8 Edge Cases

  • Two transactions with identical start_ts (should be structurally impossible given monotonic assignment, I8, but the comparator must have a deterministic tiebreak, e.g., txn_id, to avoid mutual wounding).
  • A transaction wounded so many times it never makes progress (should not happen under correct age-based wounding, but add a fixture proving the oldest-transaction-always-wins property directly).
  • A wound decided at a participant whose coordinator connection is itself temporarily unreachable — the wound decision must be retried until it reaches the coordinator, never silently dropped.

20.9 Failure Analysis

A surviving deadlock cycle found by the property tests indicates a comparator bug (most likely a tiebreak or clock-skew issue in step one above); the debugging methodology is to replay the exact sim_harness seed and inspect the wait-graph edges' start_ts ordering directly.

20.10 Operational Notes

deadlock_cycles_detected should be zero in steady-state production; a nonzero value is itself an operational signal that the wound-wait invariant (I10) has regressed and belongs in the same alert tier as other correctness invariants (§26).

The Phase 3-vs-Phase 8 abort-latency comparison belongs in the project's own before/after performance record (§30) as concrete evidence that wound-wait's theoretical advantage (P8) materializes in the actual implementation, not just in the design rationale.

21. Phase 9 — Read-Only Snapshot Transactions at a Timestamp

21.1 Objectives

Fully realize the read-only fast path (P3, P11, ADR-11) as a first-class transaction type distinct from read-write transactions, guaranteeing zero lock acquisition and zero coordinator round-trip for the common case, building on Phase 1's groundwork with the real TrueTime clock from Phase 2 and the cross-shard MVCC stores from Phase 4-5.

21.2 Detailed Implementation Steps

  1. Implement SnapshotRead(read_ts, keys) as a client-callable API distinct from Transaction.commit().
  2. Implement read_ts assignment: read_ts = TT.now().latest at the client or a nearby coordinator, with no commit-wait ever applied (read-only, P11).
  3. Implement multi-shard snapshot reads: fan out SnapshotRead to each relevant participant's MvccStore directly, no lock manager involvement.
  4. Implement participant-side snapshot-read serving with no coordination with in-flight 2PC transactions beyond MVCC visibility (I4) — an in-flight PREPARED write's intent must remain invisible until its COMMIT is actually applied.
  5. Add a "stale read" mode: an explicitly older read_ts for bounded-staleness reads, still lock-free.
  6. Add property tests: a snapshot read racing a concurrent commit never observes a partially-applied cross-shard transaction (either all its writes are visible or none are, at any given read_ts).
  7. Add throughput benchmarks: snapshot-read throughput must scale independently of concurrent write load (§31).
  8. Add telemetry: snapshot_read_latency_ms (carried from Phase 1), snapshot_read_throughput.
  9. Add the "snapshot read racing a commit" worked example from §8 as an executable fixture.
  10. Document why snapshot reads need no locks (P3) directly in docs/adr/ADR-11.md with a reference to the MVCC visibility rule (I4).
  11. Implement a bounded-wait mechanism for a lagging participant's applied consensus index catching up to a requested read_ts, distinct from and much shorter than the Phase 6 commit-wait, since a read-only request must never pay a write-path-scale delay.
  12. Add a differential benchmark directly comparing snapshot-read latency against read-write single-shard transaction latency (Phase 3) at matched key-access patterns, quantifying the P3 lock-free advantage numerically rather than only asserting it.
  13. Add docs/performance/phase9-baseline.md recording snapshot-read throughput under zero, moderate, and peak concurrent write load, the direct empirical input to M14 (§30) and the §31 independence claim.

21.3 Deliverable

A read-only snapshot-read API usable across shards, requiring no lock acquisition and no participation in 2PC, scaling independently of write throughput, with a documented and tested guarantee that it never observes a partially-committed cross-shard transaction, and a benchmark quantifying the lock-free read-path advantage against the Phase 3 read-write baseline.

21.4 Acceptance Criteria

  • Zero lock-manager calls observed during any snapshot read across the full cross-shard fixture suite.
  • Zero instances of a snapshot read observing a partial cross-shard commit (some but not all participants' writes visible) across 10,000 racing-commit fixture runs.
  • Snapshot-read throughput in the benchmark harness does not degrade as concurrent write load increases (§31 independence claim), confirmed at zero, moderate, and peak write load.
  • The lagging-participant bounded wait resolves within a small fixed budget, independent of any in-progress commit-wait elsewhere in the cluster.

21.5 Conformance Fixtures

  • conformance/phase9/snapshot_read_races_commit.json — the canonical §8 worked example.
  • conformance/phase9/cross_shard_snapshot_all_or_nothing.json — verifies atomic visibility across shards at one read_ts.
  • conformance/phase9/bounded_staleness_read.json — the stale-read mode.
  • conformance/phase9/lagging_participant_bounded_wait.json — a snapshot read against a participant still catching up on its consensus log.

21.6 Pitfalls

  • Reading a cross-shard transaction's writes at different shards using slightly different effective timestamps, producing an inconsistent partial view — this is precisely what I4 (extended to the cross-shard case) forbids.
  • Accidentally routing a snapshot read through any part of the lock manager "just to be safe," reintroducing coordination cost the whole phase exists to avoid (P3, P11).
  • Treating "read-only" as a client-declared hint rather than a structurally enforced property — a transaction that later attempts a write after being routed as read-only must be rejected, not silently upgraded.
  • Implementing the lagging-participant wait with the same polling loop shape as commit-wait, accidentally coupling read-path latency to write-path clock semantics it has nothing to do with.

21.7 Performance Concerns

  • Cross-shard snapshot-read fan-out latency is bounded by the slowest participant, same tail-amplification shape as 2PC fan-out (Phase 4) but without the round-trip cost of locking or voting — quantify the difference in §34.
  • The lagging-participant bounded wait must be tuned short enough that a genuinely stuck participant surfaces as a distinct failure (quorum loss, FM-3) rather than masquerading as ordinary read latency.

21.8 Edge Cases

  • A snapshot read at a read_ts for which some participant has already GC'd the needed version (§4 retention window) — must raise StaleSnapshotReadError cleanly (carried from Phase 0), not return wrong data.
  • A snapshot read issued for a read_ts in the future relative to a lagging participant's applied consensus index — must wait briefly for the participant to catch up, bounded, rather than returning stale data silently.
  • A snapshot read against a participant that never catches up within the bounded wait — must surface a distinct, named error rather than blocking indefinitely or silently returning stale data.

21.9 Failure Analysis

A partial cross-shard visibility bug (I4 violation at the multi-shard level) is treated with the same severity as a single-shard I4 violation (§7); the debugging methodology adds one step specific to this phase: compare the applied consensus log index at each participant at the moment of the read to rule out a lagging-replica read as the root cause before suspecting the MVCC visibility logic itself.

21.10 Operational Notes

snapshot_read_throughput growing independently of twopc_commit_latency_ms and commit_wait_ms is the operational signal that P11's separation of concerns is holding in production; dashboard them side by side (§26).

The Phase 3-vs-Phase 9 latency comparison is one of the most persuasive artifacts in the whole project for explaining P3 to a newcomer: the same key-access pattern, an order of magnitude apart in latency, purely from removing coordination.

22. Phase 10 — The Clock-Epsilon Monitor and the Fail-Safe on Epsilon Violation

22.1 Objectives

Fully implement ClockMonitor and its fail-safe (I11, ADR-18): continuous epsilon-bound sampling that halts new commits cluster-wide the instant the bound is violated, since a silent epsilon violation is the single failure mode that breaks external consistency without any other visible symptom.

22.2 Detailed Implementation Steps

  1. Implement continuous sampling of TT.now() interval width at a frequency exceeding the clock daemon's publish rate (Phase 2 groundwork).
  2. Implement the fail-safe trip condition: interval width exceeds a configured multiple of epsilon (§4: 3x) for more than one sampling interval.
  3. Implement the halt action: reject new PREPARE and new commit-timestamp assignment cluster-wide while tripped; in-flight commit-waits already using a correct (pre-violation) interval are allowed to complete safely, never abandoned mid-wait.
  4. Implement automatic recovery: once sampled interval width returns within bound for a configured stability window, resume accepting new commits.
  5. Implement manual override for operators to force a resume (audited, per the in-doubt override pattern from Phase 7).
  6. Add fault injection: inject an epsilon violation of varying severity and duration; verify the halt trips within one sampling interval and resumes correctly after recovery.
  7. Add fault injection: inject a violation during an in-flight commit-wait; verify the wait itself still correctly extends per I5 rather than being aborted mid-wait.
  8. Add telemetry: epsilon_bound_violations (carried from Phase 2, now load-bearing), commits_halted_total, fail_safe_active (gauge).
  9. Wire epsilon_bound_violations to a page-immediately alert per §26 (this is the one alert in the whole system tagged correctness-critical, not merely availability-critical).
  10. Add the "clock that violates its epsilon bound" worked example from §8 as an executable fixture.
  11. Document the clock-epsilon-violation runbook fully in docs/runbooks/clock-epsilon-violation.md.
  12. Implement a distinct halt path for new read-write transaction begins (not only new PREPARE/commit), so a flood of doomed transactions cannot pile up against an already-tripped fail-safe.
  13. Implement a "near-miss" telemetry path: a transient epsilon widening that self-resolves before crossing the trip threshold is still recorded, feeding long-run trend analysis distinct from actual trips.
  14. Add docs/performance/phase10-baseline.md recording fail-safe trip-and-resume latency across severity levels, confirming the detection-within-one-sampling-interval acceptance bar with real numbers, not just a pass/fail assertion.

22.3 Deliverable

A continuously-running clock monitor that detects an epsilon-bound violation within one sampling interval, halts new commit activity and new transaction begins cluster-wide before external consistency can be silently broken, safely completes any commit-wait already in flight, resumes automatically once the bound is re-established, and records near-miss telemetry for trend analysis.

22.4 Acceptance Criteria

  • 100% of injected epsilon violations trip the fail-safe within one sampling interval, across severity levels from 1.5x to 10x the configured bound.
  • Zero external-consistency violations occur during or immediately after any injected violation-and-recovery cycle (I1, I11 combined check).
  • In-flight commit-waits during an injected violation always complete correctly (I5), never abandoned.
  • New transaction begins are rejected (not merely queued) while the fail-safe is tripped, verified by a fixture that floods begins during an active trip.
  • Near-miss telemetry correctly distinguishes a self-resolving transient widening from an actual trip across a dedicated fixture set.

22.5 Conformance Fixtures

  • conformance/phase10/epsilon_violation_clean_trip.json — the canonical §8 worked example.
  • conformance/phase10/violation_during_inflight_commit_wait.json — wait extension under active violation.
  • conformance/phase10/violation_recovery_resume.json — automatic resume after stability window.
  • conformance/phase10/transaction_begin_flood_during_halt.json — begins rejected cleanly during an active trip.
  • conformance/phase10/near_miss_transient_widening.json — telemetry recorded without a trip.

22.6 Pitfalls

  • Sampling too infrequently, letting a transient-but-real violation slip through undetected — this defeats the entire purpose of the phase and must be caught by the fault-injection suite, not assumed correct from code inspection.
  • Halting new commits but forgetting to also halt new read-write transaction begins, allowing a flood of doomed transactions to pile up against the halt.
  • Treating the fail-safe as "just another availability degradation" in dashboards, rather than surfacing it distinctly as the single correctness-critical alert it is (P9, ADR-18).
  • Conflating near-miss telemetry with actual trip telemetry in the same counter, obscuring the trend signal §26 depends on for early-warning purposes.

22.7 Performance Concerns

  • The monitor's sampling frequency itself must not become a throughput bottleneck (it runs off the hot commit path, but shares the clock daemon's resources) — benchmark sampling overhead against the daemon's own publish rate.
  • The new-transaction-begin halt path must add negligible overhead in the common case (fail-safe not tripped), since it now sits on every transaction's entry point, not only the commit path.

22.8 Edge Cases

  • An epsilon violation that self-resolves within a single sampling interval (a genuine transient blip, not a sustained fault) — must still be counted in epsilon_bound_violations telemetry even if it does not trip the halt, since trend analysis (§26) depends on seeing near-misses.
  • An operator-forced resume issued while the underlying violation is, in fact, still active — must re-trip immediately on the next sample, never trust the override blindly.
  • A violation occurring at the exact moment a coordinator is also failing over (Phase 7) — the two mechanisms must not deadlock each other; the fail-safe halt must not block the recovery scan itself.

22.9 Failure Analysis

Any correctness violation (I1) that correlates in time with an epsilon-bound violation is escalated per the clock-epsilon-violation runbook (§26) as the top-priority forensic hypothesis, ahead of any 2PC or consensus-layer explanation, precisely because this is the one failure mode with no other structural safeguard.

A fail-safe that trips correctly but fails to also halt new transaction begins is treated as a partial-fix regression, not a pass, since the doomed-transaction pileup it permits is itself an availability hazard layered on top of the correctness one.

22.10 Operational Notes

epsilon_bound_violations transitioning from zero is the single highest-priority page in the entire operational surface (§26); the runbook must be rehearsed, not merely written, since the correct response (verify halt engaged, do not manually force resume without confirming bound restoration) is counterintuitive to an on-call engineer trained on availability incidents.

The near-miss telemetry stream introduced here gives operators an early warning system distinct from the page-immediately alert — a rising near-miss rate with zero actual trips is a legitimate reason to schedule proactive clock-infrastructure investigation before a real trip ever occurs.

23.1 Objectives

Build the sim_harness into a full Jepsen/Elle-style history checker (Herlihy & Wing 1990) capable of falsifying external consistency and linearizability under combined clock-skew and partition fault injection, and run a final chaos-and-performance hardening pass across every invariant and metric established in Phase 0-10.

23.2 Detailed Implementation Steps

  1. Implement a history recorder capturing every transaction's invocation/response with real-time bounds, across all coordinators and participants.
  2. Implement an Elle-style cycle-detection checker over the recorded history, checking for external-consistency violations (I1) and general serializability anomalies (write skew, phantom reads) as a cross-check against the isolation-level claim (§8).
  3. Implement combined fault injection: partition a participant's consensus group while simultaneously injecting a clock-epsilon spike, exercising Phase 5, 7, 8, and 10 mechanisms together.
  4. Implement deterministic seed-based replay for every fault-injection run (P12), so any checker-found counterexample reproduces byte-for-byte.
  5. Implement a differential-testing mode comparing observed transaction outcomes against a reference serializability oracle for small, exhaustively-enumerable workloads.

  8. Add performance-regression gating: benchmark every §4 metric before and after this phase's changes; fail CI on regression beyond a configured threshold.

  10. Produce the final harness comment block (§ end of document) summarizing H1-H20 pass status.

  12. Implement a long-run regression corpus: every counterexample the checker ever finds, once fixed, is permanently added to the corpus replayed on every future CI run, so no correctness bug this project finds is ever silently reintroduced.
  13. Add docs/performance/phase11-baseline.md consolidating every prior phase's baseline into one end-to-end view, the final artifact answering "what does each phase cost" for the whole project.

A deterministic, seed-replayable Jepsen/Elle-style verification harness that runs combined chaos scenarios across every subsystem, checks the recorded history for external-consistency and serializability violations, gates CI on both correctness and performance regression, automatically minimizes any counterexample it finds, permanently regression-tests every historical finding, and produces the evidence trail this blueprint's own harness section reports against.

  • Zero external-consistency or serializability-anomaly findings by the Elle-style checker across a soak run combining all four chaos scenario types, for a minimum of 100,000 recorded transaction histories.
  • The linearizability CI job runs on every push and blocks merge on any finding (ADR-24).

  • Any counterexample injected synthetically into the harness for testing the checker itself is minimized to a schedule no larger than necessary to still reproduce it.

23.5 Conformance Fixtures

  • conformance/phase11/combined_partition_and_clock_spike.json — the flagship combined-fault scenario.

23.6 Pitfalls

  • Building a checker that only checks per-invariant (I1, I2, ...) assertions already covered by earlier phases, rather than a true history-based Elle-style analysis capable of finding anomalies no single invariant check anticipated.

  • Letting the regression corpus grow without bound on CI wall-clock time, eventually making every push too slow to be useful — budget corpus replay time explicitly and prioritize combined-fault cases over single-fault ones if trimming is ever needed.

23.7 Performance Concerns

  • The history recorder itself must not perturb the timing behavior it is measuring (observer effect) — benchmark recorder overhead and keep it below a documented threshold relative to baseline commit latency.
  • Counterexample minimization itself must terminate in bounded time even for a large fault-injection schedule, or it becomes a second source of CI slowness alongside the corpus itself.

23.8 Edge Cases

  • A counterexample found only under a very specific combined-fault timing window (a true "one in a million" race) — the deterministic replay (step 4) must still reproduce it exactly from the recorded seed, however rare.
  • A performance-regression gate false-positive caused by CI infrastructure noise rather than a real regression — document the re-run policy so genuine regressions are never dismissed as noise by habit.
  • A minimization pass that shrinks a schedule so far it no longer reproduces the original violation (an over-aggressive shrink) — the minimizer must verify reproduction at every shrink step, never assume it.

23.9 Failure Analysis

Any Elle-style checker finding is treated as a release-blocking correctness bug regardless of how rare the triggering condition was; the forensic process is: replay the seed, isolate which of I1-I13 was actually violated, and trace it to the specific phase (4-10) whose mechanism failed, using this document's phase arc as the diagnostic map.

A regression-corpus entry that stops reproducing after an unrelated refactor is itself worth investigating rather than silently removing — it may mean the refactor accidentally fixed a second bug, or it may mean the fixture itself became stale relative to a protocol version change (§27).

23.10 Operational Notes

The linearizability CI job's pass/fail history is itself an operational artifact worth dashboarding (§26) — a project that starts seeing intermittent checker failures under increased load is seeing an early warning of a production external-consistency risk before it ever reaches a real cluster.

The consolidated end-to-end baseline document produced in this phase is the single artifact most worth handing to a newcomer alongside this blueprint — it turns every abstract latency claim in §4 and §34 into a number someone actually measured.

26. Operational Readiness

Named metrics: twopc_commit_latency_ms and commit_wait_ms (the two write-path latency components, kept separate per P11), epsilon_current_ms and epsilon_bound_violations (clock health, the sole correctness-critical alert tier), in_doubt_transaction_count and in_doubt_resolution_time_ms, twopc_abort_rate, deadlock_cycles_detected and wound_events_total, snapshot_read_latency_ms and snapshot_read_throughput, consensus_round_latency_ms and quorum_loss_events, external_consistency_violations (must be zero; sourced from the Phase 11 Elle-style checker in CI and, if ever wired to production, from live history sampling).

Tracing: every RPC (client-to-coordinator, coordinator-to-participant, coordinator-to-clock-daemon) propagates txn_id, coordinator_epoch, and shard_id as span attributes (ADR-20), so a single cross-shard commit's full 2PC-plus-commit-wait timeline is reconstructable from traces alone.

Structured logging: JSON logs (ADR-19) keyed by txn_id, node_id, trace_id, coordinator_epoch, emitted at every FSM transition (§8) and every invariant check (§7).

Dashboards: a write-path dashboard splitting twopc_commit_latency_ms from commit_wait_ms; a clock-health dashboard for epsilon_current_ms trended against its configured bound; a contention dashboard for lock_wait_queue_depth, wound_events_total, deadlock_cycles_detected; a recovery dashboard for in_doubt_transaction_count and resolution time; a read-path dashboard for snapshot_read_latency_ms/throughput shown independently of write load, demonstrating P11's separation in production data.

Alerting philosophy: an epsilon_bound_violations transition from zero is page-immediately, correctness-critical, and outranks every availability alert in the system (P9, ADR-18) — it threatens I1 directly. in_doubt_transaction_count exceeding the §4 10-second resolution budget is page-immediately, availability-and-correctness-adjacent. quorum_loss_events and elevated twopc_abort_rate are ticket-and-investigate, not page-immediately, unless sustained beyond a configured window.

SLOs: 99.99% availability for cross-shard commits; zero external-consistency violations (a correctness SLO, not a percentile); p99 cross-shard commit latency within the §4 budget; in-doubt resolution within 10 s of coordinator restart in 99% of restarts.

Incident response: the on-call rotation carries five named runbooks under docs/runbooks/: clock-epsilon-violation.md (Phase 10's fail-safe response, top priority), in-doubt-transaction-resolution.md (Phase 7's audited manual-override procedure), coordinator-failover.md (epoch transition and RTO verification), deadlock-storm.md (FM-10 response), quorum-loss.md (FM-3 response).

Backup/restore: 2PC log and consensus-group snapshots are backed up on the checkpoint cadence (Phase 7); restore replays from the last checkpoint plus subsequent log segments, and restore correctness is verified by running the Phase 11 Elle-style checker against the restored cluster's replayed history before returning it to production traffic.

Deployment topology: coordinators and participant consensus-group nodes deployed across failure domains such that no single domain loss removes a coordinator's ability to reach quorum at any participant it depends on; canary deployments roll a single coordinator instance first, observing external_consistency_violations and epsilon_bound_violations before wider rollout; rollback reverts to the last known-good coordinator binary while preserving the 2PC log format (§27) so in-flight transactions survive the rollback; migrations follow the compatibility rules in §27.

27. Compatibility & Versioning

2PC-log format versioning: every TwoPcLog entry carries a schema-version tag (ADR-15); a coordinator refusing to interpret an unknown version fails closed rather than guessing, and log-format upgrades are additive-field-only within a major version.

MVCC storage format: Version records are tagged with a storage-format version independent of the 2PC-log version; mvcc_store supports reading N-1 storage-format versions during a rolling upgrade window.

Coordinator-participant protocol: versioned via Protocol Buffers field numbering (ADR-16) with strict append-only field addition; a ProtocolVersionMismatchError (§11) is raised rather than silently ignoring an unrecognized field, and the coordinator-participant handshake negotiates the highest mutually-supported version at connection time.

Clock-API contract: TT.now()'s guarantee (latest - earliest <= 2*epsilon) is a stable contract independent of the underlying clock-source implementation (simulated today, potentially real GPS/PTP later per ADR-17's rejected-choice-wins column); any change to this contract itself is a major-version, migration-gated event given how much of the system depends on it (P1, I1, I5).

Consensus-log compatibility: consensus_shim's log format is versioned independently of both the 2PC log and the MVCC storage format (established explicitly in Phase 5) — the three must never share a schema, since they evolve on different cadences tied to different subsystems.

API stability: the client-facing Transaction and SnapshotRead APIs follow SemVer; MAJOR bumps accompany any change to the external-consistency contract itself, MINOR bumps for additive capability (e.g., new isolation-level options), PATCH for bugfixes with no contract change.

Migration and deprecation: a deprecated protocol version is supported for at least one MAJOR release cycle after its successor ships, with ProtocolVersionMismatchError telemetry tracked to confirm zero remaining traffic before removal.

28. Testing & Verification Strategy

Unit tests cover every FSM transition (§8), every LockManager/WoundWait comparator branch, and every MvccStore visibility rule in isolation, tied to I4, I10, I13.

Integration tests exercise full cross-shard commits (Phase 4-6), coordinator crash-and-recover cycles (Phase 7), and combined chaos scenarios (Phase 11), tied to I2, I3, I6.

Property-based tests (Hypothesis, ADR-22), each tied to a specific invariant and phase fixture set: external consistency — if T1 finishes before T2 begins in real time, commit_ts(T1) < commit_ts(T2) (I1, tied to Phase 6 fixtures external_consistency_nonoverlapping.json); atomicity — all-or-nothing across participants under injected failures (I2, tied to Phase 4 and Phase 7 fixtures); snapshot-visibility — a snapshot read at t sees exactly commits with commit_ts <= t (I4, tied to Phase 0, 1, 9 fixtures); commit-wait coverage — the wait always covers the full epsilon interval even under injected spikes (I5, tied to Phase 6 and Phase 10 fixtures); in-doubt resolution — always resolves to the logged decision (I6, tied to Phase 7 fixtures).

The Jepsen/Elle-style history checker (Phase 11, Herlihy & Wing 1990) is the named CI gate (linearizability.yml, ADR-24) for linearizability and external consistency under clock skew and partition — these are exactly the guarantees only fault injection can falsify, since no single unit or property test can observe the full cross-process, cross-time-window interaction that a real counterexample requires.

Differential testing compares transaction-outcome semantics against CockroachDB's and TiKV's documented transaction behavior on a shared, small, exhaustively-checkable workload (§33), flagging any divergence in isolation-level guarantees as a design-review item, not an automatic failure (since some divergence is an intentional design choice per §9's ADRs).

Fuzzing (Atheris, ADR-23) targets the RPC decoders (PrepareRequest, CommitDecision deserialization) and the 2PC-log decoder, tied to T8.

Chaos testing (Phase 11) injects: coordinator crash between prepare and commit (I6), clock-epsilon spikes and violations (I11), participant consensus-group partition (I3), and injected deadlocks (I10) — individually in Phase 7-10 and combined in Phase 11.

Deterministic replay (P12) is a first-class capability of sim_harness from Phase 2 onward, mandatory for every fault-injection run, and the sole mechanism for reproducing any Elle-style checker counterexample.

Soak testing (Phase 11) runs sustained randomized fault injection over extended wall-clock duration, watching for invariant drift not visible in short runs (e.g., a slow in_doubt_transaction_count leak).

Performance-regression gating (§30) benchmarks every §4 metric on every CI run and fails on regression beyond a configured threshold, tied to the Phase 11 CI wiring.

31. Scalability Analysis

What stays constant regardless of scale: commit-wait duration, floored at 2*epsilon (P1) — no amount of horizontal scaling shortens it, which is precisely why tighter clock synchronization (a smaller epsilon, per ADR-17's real-hardware regime) is the only lever on this component; the lock-free nature of snapshot reads, which scale with participant count and read-path resources rather than with commit-path contention.

What grows with scale, and its shape: 2PC fan-out latency grows with participant-count-per-transaction (O(k) RPC round-trips for k participants, tail-dominated by the slowest one, per Phase 4's tail-amplification finding); cross-shard-transaction cost relative to single-shard is a fixed multiplicative penalty (an extra full 2PC-over-consensus round-trip per participant beyond the first, per Phase 5) that single-shard transactions never pay — this is why single-shard transaction throughput (M9: 50,000 tx/s) so vastly exceeds cross-shard throughput (M8: 5,000 tx/s), and why application design that minimizes cross-shard transactions dominates overall cluster throughput far more than any coordinator-side optimization can.

Named bottlenecks: the clock daemon's publish rate and clock_monitor's sampling rate (Phase 2, 10) if either falls behind the commit-wait hot path's demand; per-participant consensus-group leader throughput (Phase 5) under extreme single-shard write concentration; the 2PC log's fsync rate at the coordinator (Phase 4, 7) under very high transaction-begin rates; lock-table contention on a small number of hot keys (Phase 3, 8), which wound-wait bounds but does not eliminate.

The commit-wait-vs-clock-tightness tradeoff: halving epsilon (via tighter clock synchronization, ADR-17) halves the commit-wait floor directly and thus raises the achievable write-path throughput ceiling for any workload where locks are held through the wait (I7) — this is the single highest-leverage infrastructure investment available to a real deployment of this design, strictly above adding coordinator or participant hardware.

Horizontal scaling: by sharding data across more participants (more, smaller consensus groups), which raises aggregate single-shard throughput roughly linearly (M9's regime) while leaving cross-shard throughput (M8) governed by the fixed per-transaction fan-out cost regardless of total shard count — this is why single-shard-transaction-dominant workloads scale far better than cross-shard-heavy ones, and why schema/sharding design that keeps related data co-located in one shard is the dominant scalability lever available to an application built on this coordinator.

Practical ceilings and levers beyond them: participant count per transaction (§4: 16 max) is a practical ceiling because fan-out tail latency grows with it; geo-distribution across regions raises consensus-round latency (Phase 5) and thus both 2PC round-trip time and effective epsilon (wider clock uncertainty over longer distances) — the lever beyond this ceiling is deferred geo-partitioned locality-aware routing, PhaseDeferred("§31 Scalability Analysis"), which keeps most transactions single-region and single-shard rather than attempting to optimize the worst case.

The clock-monitor's own sampling interval (§4: <= 1ms) is a small but nonzero scalability input: as cluster size grows, more independent TT.now() samples must be reconciled by clock_monitor without the monitor itself becoming a bottleneck (T11, I15) — this is a secondary but real scaling concern distinct from the primary commit-wait and 2PC fan-out costs above, and one that a real deployment's clock-infrastructure investment (ADR-17) must budget for alongside epsilon tightening itself.

32. Mental Models & First Principles

  • MM1 — Spanner's insight is that if you can bound clock uncertainty, you can buy external consistency by simply waiting it out: commit-wait converts a hardware (or simulated) clock guarantee into a database correctness guarantee (Corbett et al. 2012).
  • MM2 — 2PC gives atomicity but is a blocking protocol with a single-point coordinator, so you make the participants and the coordinator's decision themselves fault-tolerant with consensus — 2PC over Paxos is the standard composition (Gray & Lamport 2006).
  • MM3 — Reads are the easy 90%: MVCC snapshot reads at a timestamp need no coordination at all, so the entire hard engineering effort concentrates in the write commit path.
  • MM4 — A timestamp interval, not a scalar, is the honest unit of "now" in any system with bounded clock error; every bug class in this project traces back to someone treating an interval as if it collapsed to a point too early.
  • MM5 — Locks and clocks are the same kind of resource: both are held/consulted for the minimum correct duration and never released or trusted early, because "early" is exactly where external consistency breaks silently.
  • MM6 — A durable log is a memory, and recovery is nothing but re-reading that memory correctly; every recovery bug in this project is, at root, a case of trusting some other source over the log.
  • MM7 — Wound-wait turns deadlock avoidance into a total order (by transaction age) rather than a search problem (cycle detection) — the entire cost is paid at the moment of conflict, never a background scan.
  • MM8 — The commit path is inherently more expensive than the read path not because of implementation quality but because of the physics of the guarantee being made — a write must be ordered against every future observer, a read only against the past.
  • MM9 — Determinism in verification (seeded, replayable fault injection) is what turns "it worked in testing" into an actual falsifiable claim about external consistency, rather than an unfalsifiable one.

34. Back-of-Envelope Capacity Model

Commit-wait latency floor: wait_duration = 2 * epsilon. At epsilon = 1ms: wait_duration = 2ms. At epsilon = 7ms (a looser, more conservative bound): wait_duration = 14ms. This is a per-commit fixed cost, additive to every write transaction's latency regardless of contention.

Throughput impact of held locks during commit-wait: if a transaction holds its locks for lock_hold_time = txn_execution_time + wait_duration, and a given key sees one contending writer at a time, the maximum commit throughput against that key is 1 / lock_hold_time. At txn_execution_time = 3ms and epsilon = 4ms (wait_duration = 8ms): lock_hold_time = 11ms, giving a per-key max throughput of 1000/11 ≈ 91 commits/sec against a single hot key — explaining why hot-key contention, not aggregate cluster capacity, is usually the binding constraint (§31).

2PC round-trip latency: prepare_RTT + commit_RTT + (2 * consensus_round_latency per participant). At prepare_RTT = 5ms, commit_RTT = 5ms, consensus_round_latency = 6ms (§4/M6), and 2 participants: 5 + 5 + (2 * 6 * 2) = 34ms before commit-wait; adding wait_duration = 8ms gives 42ms, consistent with the §4/M2 cross-shard p95 budget of 45ms leaving a small margin for scheduling overhead.

Cross-shard-vs-single-shard commit cost ratio: single-shard skips the cross-participant PREPARE/COMMIT fan-out entirely, paying only one consensus round-trip pair (2 * 6ms = 12ms) plus commit-wait (8ms) = 20ms vs. the two-participant cross-shard figure of 42ms above — roughly a 2.1x cost ratio for two participants, growing further with participant count per the O(k) fan-out shape (§31).

MVCC version storage: at a write rate of 10,000 writes/sec, average value size 200 bytes, and a GC-retention window of 60s (§4/M10): 10,000 * 200 * 60 = 120,000,000 bytes ≈ 114 MB of live version data retained per shard at steady state before GC reclaims it.

Lock-hold time and max lock throughput (restated generally): lock_hold_time = txn_duration + wait_duration; max_throughput_per_key = 1 / lock_hold_time. This is the formula instantiated numerically above and is the single most important capacity-planning equation for write-heavy, hot-key workloads on this design.

In-doubt recovery time: dominated by (log_size_since_checkpoint / replay_throughput) + (affected_txn_count * per_txn_redrive_RTT). At a checkpoint interval keeping log_size_since_checkpoint to roughly 10MB, a replay throughput of 300MB/s (borrowing the WAL-replay figure as a reasonable proxy), and 50 affected transactions each needing a 10ms re-drive RTT: (10/300)*1000 + 50*10 = 33ms + 500ms ≈ 533ms, comfortably inside the §4/M7 10-second budget with wide margin for larger logs or more affected transactions.

Snapshot-read throughput (unbounded by coordination): bounded only by per-shard read-path resources (CPU for version-chain scan, I/O for cold data), not by commit-path contention — at a benchmark figure of 0.5ms CPU-bound scan cost per read, a single shard's snapshot-read capacity is roughly 2,000 reads/sec/core, scaling linearly with added read-serving cores, in stark contrast to the hot-key-bound write throughput above.

Fail-safe trip-to-halt latency: bounded by sampling_interval + halt_propagation_time. At a sampling_interval of 1ms (§4) and a halt_propagation_time of 2ms (a local flag flip plus in-flight-request draining), total detection-to-halt latency is approximately 3ms — small relative to the 8ms commit-wait floor at the default epsilon = 4ms, meaning the fail-safe does not itself become the dominant source of halted-window duration.

Cross-region consensus-round latency floor: bounded below by the one-way network propagation delay between the furthest two group members, roughly distance_km / 200,000 km/s for fiber (a standard back-of-envelope figure) doubled for a round trip; at 2,000 km separation this floors the consensus round at roughly 20ms, directly inflating the §34 2PC round-trip figure for any geo-distributed deployment and motivating the deferred locality-aware routing (§31, §37).

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Deterministic Transaction Ordering (Calvin)

   Client --> Sequencer (global order, batched epochs)
                    |
                    v
         +---------------------+
         | Deterministic        |
         | Scheduler (per node) |
         +----------+-----------+
                    |
       (no 2PC, no per-txn voting)
                    v
         +---------------------+
         |  Deterministic       |
         |  Execution Engine    |
         +---------------------+

Winning regime: extremely high write throughput with read/write sets knowable in advance (e.g., known-schema OLTP with simple predicates). Real embodying system: Calvin (Thomson et al. 2012), and its lineage in FaunaDB. Rejected here because: this project's pedagogical goal is precisely the TrueTime/commit-wait/2PC-over-consensus composition (§1) — pre-ordering sidesteps the exact mechanisms (clock uncertainty, 2PC voting) this blueprint exists to teach, and requiring full read/write sets up front is a poor fit for interactive, ad hoc transactions.

Alternative 2 — HLC Without Atomic Clocks

   Node A: HLC (phys, logical) --\
   Node B: HLC (phys, logical) ---> max() on message receipt --> causal order
   Node C: HLC (phys, logical) --/
                    |
      external consistency via larger, conservative
      uncertainty window + occasional read-restart

Winning regime: deployments with no access to dedicated clock hardware (GPS/atomic clocks) that still want external consistency, accepting a wider uncertainty window and occasional client-visible read restarts. Real embodying system: CockroachDB. Rejected as the primary mechanism here (though implemented as a comparison point in hlc.py, Phase 2) because the project's explicit goal is to reproduce Spanner's bounded-and-monitored-epsilon mechanism (§1); HLC's unbounded worst case would weaken the very commit-wait guarantee this blueprint is built to demonstrate precisely. PhaseDeferred("§36 Alternative Architectures (Roads Not Taken)") as a selectable fallback clock mode.

Alternative 3 — Optimistic Concurrency with a Central Timestamp Oracle

   Clients --> Central Timestamp Oracle (TSO) --> monotonic ts
                        |
        +---------------+---------------+
        v                               v
   Node A (OCC, primary-lock)      Node B (OCC, primary-lock)

Winning regime: workloads where a single, simple, centrally-ordered timestamp service is acceptable and write conflict rates are low enough that optimistic validation rarely aborts. Real embodying system: TiKV/TiDB (Percolator lineage, Peng & Dabek 2010). Rejected here because a central oracle is a single logical bottleneck and reintroduces exactly the kind of centralization this project's bounded-clock, decentralized-timestamp-assignment design (ADR-09) is built to avoid.

Alternative 4 — Single-Shard-Only Design (No Cross-Shard Transactions)

   Client --> Shard Router --> exactly one shard's
                                Coordinator+Participant
                                (local 2PL + MVCC only)
              (cross-shard transactions rejected at the API)

Winning regime: applications that can be fully partitioned by a single sharding key with no cross-partition transactional need — the common case for many multi-tenant SaaS systems. Rejected as this project's primary design because the entire pedagogical point (§1) is the cross-shard 2PC-over-consensus-plus-commit-wait composition; a single-shard-only system would still need everything through Phase 3 but would skip Phase 4-7 and 11's most load-bearing content entirely.

38. Glossary

Term Definition
Distributed transaction a transaction whose reads/writes span more than one shard/node
Atomic commit the property that a transaction's effects are applied at every participant or none
Two-phase commit (2PC) prepare-then-commit protocol achieving atomic commit across participants
Three-phase commit (3PC) Skeen's non-blocking extension of 2PC adding a pre-commit phase
Paxos Commit Gray & Lamport's composition of 2PC with Paxos-replicated votes
Prepare the 2PC phase in which a participant durably logs intent and votes
In-doubt a transaction state where a participant has voted but not learned the final decision
Coordinator the process driving 2PC and owning the durable decision log
Participant a shard-owning process that votes and applies a transaction's local effects
Consensus agreement among replicas on a single value or log entry despite failures
Paxos Lamport's foundational consensus protocol
Raft Ongaro & Ousterhout's understandable consensus protocol
Replication maintaining multiple copies of state for fault tolerance
External consistency if T1 commits before T2 starts in real time, T1's timestamp precedes T2's
Linearizability the correctness condition that operations appear to take effect atomically at some point between invocation and response
Serializability transactions appear to execute in some sequential order, without regard to real time
Strict serializability serializability plus real-time ordering, equivalent to external consistency at the transaction level
Snapshot isolation an isolation level where a transaction sees a consistent snapshot but may permit write skew
MVCC multi-version concurrency control: keeping multiple timestamped versions per key
Version one immutable, timestamped value of a key
Version chain the ordered sequence of versions for one key
Snapshot read a read at a fixed timestamp returning the version current as of that time
TrueTime Spanner's bounded-clock-uncertainty API, TT.now() -> [earliest, latest]
Clock uncertainty the width of the interval within which the true time is known to lie
Epsilon half the width of the TrueTime uncertainty interval
Commit-wait waiting until the clock has certainly passed a transaction's commit timestamp before releasing its effects
Hybrid logical clock (HLC) a clock combining physical time and a logical counter for causality tracking without special hardware
Timestamp oracle the component assigning transaction timestamps
Wound-wait a deadlock-avoidance scheme where an older transaction aborts (wounds) a younger conflicting one
Wait-die a deadlock-avoidance scheme where an older transaction waits and a younger one dies (aborts)
Deadlock a cycle of transactions each waiting on a lock held by the next
Lock an exclusivity token on a key held by a transaction
Two-phase locking (2PL) acquiring all locks before releasing any, within one transaction
Quorum a majority subset of a replica group sufficient to make progress
Deterministic transactions transactions executed in a globally pre-agreed order, avoiding 2PC
Calvin Thomson et al.'s deterministic-ordering distributed transaction system
Percolator Google's OCC-over-Bigtable incremental transaction system, central-timestamp-oracle style
Epoch a coordinator's leadership generation number, used for fencing
Fencing token a monotonically increasing token preventing a stale leader/epoch from acting
Consensus group the set of replicas replicating one shard's log
Leader election the process by which a consensus group selects its current leader
Log replication copying log entries from a leader to followers under consensus
2PC log the coordinator's durable, append-only prepare/commit/abort decision record
Tombstone a versioned marker recording a delete, distinct from absence
Garbage collection (GC) reclaiming old MVCC versions no longer needed by any live snapshot
Read-only transaction a transaction with an empty write set, servable via snapshot read alone
Read-write transaction a transaction that acquires locks and participates in 2PC
Fail-safe a deliberate halt of new activity triggered by detection of a correctness-threatening condition
Shard a partition of data owned by one participant/consensus group
Fan-out the number of participants a coordinator must contact for one transaction
Tail latency latency at high percentiles (p95/p99), often dominated by the slowest component
Backpressure bounding queues/concurrency to prevent unbounded resource growth under load
Idempotency the property that repeating an operation has the same effect as doing it once
Checkpoint a compacted snapshot of log state used to bound recovery-time scan length
Forensic replay deterministic re-execution of a recorded fault-injection run for debugging
Jepsen Kingsbury's distributed-systems testing methodology and tool family for fault-injection verification
Elle a history-checker methodology for detecting transactional-isolation and consistency anomalies
History checker a tool that analyzes a recorded operation history for correctness violations
Write skew an anomaly where two transactions each read overlapping data and write disjoint data, violating a joint constraint
Phantom read an anomaly where a transaction's predicate query sees a different result set on repetition due to a concurrent insert/delete
