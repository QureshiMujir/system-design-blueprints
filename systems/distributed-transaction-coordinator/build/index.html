⬜ Phase 0 — Repository Skeleton, Single-Shard MVCC Store, CI §12

Objectives

Establish the repository per §10, a working single-shard mvcc_store with immutable versions, and a CI pipeline that runs lint, unit tests, and a reproducible-build check. No coordination, no clock, no locking yet — this phase proves the storage substrate MVCC visibility rule in isolation before anything is layered on top of it.

Deliverable

A single, in-process MvccStore module with immutable versioned writes, timestamp-bounded reads, tombstones, and a naive GC sweep, fully covered by property tests, running green in CI with a reproducible build check, and a recorded baseline read/write latency figure that every later phase's overhead is measured relative to.

Acceptance
  • MvccStore.read never returns a version with commit_ts > read_ts (I4) across 10,000 Hypothesis-generated cases.
  • GC never removes a version needed by an outstanding read timestamp in the test harness.
  • CI is green: lint, unit, property tests, reproducible-build hash check.
  • mvcc-inspect CLI command renders a key's full version chain.
  • The baseline bench-smoke figure is recorded in docs/performance/phase0-baseline.md for later comparison.
  • SBOM generation runs successfully on every CI push from this phase forward.
Fixtures
  • conformance/phase0/mvcc_basic_write_read.json — write then read at increasing timestamps.
  • conformance/phase0/mvcc_tombstone_visibility.json — delete then read before/after tombstone commit_ts.
  • conformance/phase0/mvcc_gc_retention.json — GC must not remove a version a live read still needs.
  • conformance/phase0/mvcc_monotonic_write_rejection.json — a write with a commit_ts older than the key's current head is rejected cleanly.
  • conformance/phase0/mvcc_empty_chain_read.json — read of a never-written key returns "not found," not an error.
Pitfalls
  • Off-by-one on commit_ts <= read_ts vs < — silently breaks I4 in one direction.
  • GC racing an in-flight read holding an older read_ts reference — must snapshot the retention floor before sweeping.
  • Treating tombstones as ordinary deletions instead of versioned markers, losing point-in-time visibility of prior values.
  • Non-deterministic dict iteration order leaking into version-chain scan order, breaking reproducibility (P12) before it even matters.
  • Skipping the baseline benchmark in step 20 and later having no reference point to attribute Phase 4-6 latency growth to coordination overhead versus storage overhead (§34).

⬜ Phase 1 — Timestamp Assignment and Snapshot Reads §13

Objectives

Introduce Timestamp and TimestampOracle as first-class concepts (still without a real clock — a monotonic counter stands in), and implement read-only SnapshotRead against the Phase 0 MvccStore, establishing the read path that Phase 9 will later harden with a true TrueTime source.

Deliverable

A read-only transaction API returning MVCC snapshot reads at an assigned timestamp, with no locking and no coordination overhead, plus a placeholder timestamp source ready to be replaced by TrueTime in Phase 2, and a recorded read-path latency baseline at multiple concurrency levels.

Acceptance
  • Snapshot-read p99 latency < 5 ms in the local benchmark harness (§4).
  • Zero lock acquisitions observed during any snapshot read (verified by a lock-manager stub asserting no calls).
  • I4 holds under 10,000 randomized write/read interleavings.
  • All Phase 0 conformance fixtures pass unchanged when replayed through the new transaction-level API.
  • The recorded baseline shows snapshot-read latency remaining flat as concurrent read volume increases (an early signal for §31's independence claim).
Fixtures
  • conformance/phase1/snapshot_multi_key.json — multi-key read at one timestamp.
  • conformance/phase1/snapshot_read_only_no_lock.json — asserts zero lock-manager calls.
  • conformance/phase1/snapshot_read_regression.json — regression corpus from Phase 0 fixtures replayed through the new API.
  • conformance/phase1/snapshot_read_deadline_bound.json — a snapshot read exceeding its deadline_ns is aborted cleanly.
Pitfalls
  • Accidentally routing a read-only transaction through the future 2PC path once it exists, adding needless latency (violates P11).
  • Assigning read_ts from a counter that is not yet monotonic across process restarts (temporary risk, resolved for real in Phase 2).
  • Multi-key reads at slightly different timestamps due to a per-key now() call instead of one read_ts for the whole request.
  • Treating the placeholder counter's monotonicity as permanently sufficient instead of a known stopgap explicitly retired in Phase 2.

⬜ Phase 2 — TrueTime/HLC Clock API and Epsilon §14

Objectives

Replace the Phase 1 placeholder counter with a real TrueTimeInterval-returning TT.now() (simulated bounded uncertainty, per ADR-02 and ADR-17), implement Epsilon configuration, and implement the comparison Hlc clock (ADR-36 fallback groundwork).

Deliverable

A simulated TrueTime clock service exposing TT.now() -> TrueTimeInterval, a configurable and monitored epsilon, a parallel Hlc implementation for later comparison, the real start rule wired into TimestampOracle, and a recorded baseline for TT.now() call overhead ahead of its Phase 6 criticality.

Acceptance
  • 100,000 sampled intervals from the simulated daemon never exceed width 2*epsilon under normal (non-injected) operation.
  • Injected epsilon spikes are visible in epsilon_current_ms within one sampling interval.
  • assign_start_ts() always returns s >= TT.now().latest at call time (spot-checked in property tests).
  • TT.now() call overhead stays sub-millisecond in the recorded baseline.
  • Every runtime epsilon reconfiguration appears in the change-audit log with a timestamp and prior/new value.
Fixtures
  • conformance/phase2/epsilon_bound_normal.json — normal-operation interval-width sampling.
  • conformance/phase2/epsilon_spike_injection.json — injected widening, monitor visibility check.
  • conformance/phase2/hlc_vs_truetime_ordering.json — comparison fixture used again in §36/§33.
  • conformance/phase2/epsilon_reconfiguration_audit.json — verifies the change-audit log captures a runtime bound change.
Pitfalls
  • Simulated daemon accidentally emitting a zero-width interval, masking bugs that only manifest under real uncertainty (Corbett et al. 2012's guarantee is <=, not =).
  • Sampling the clock monitor too infrequently to catch a transient epsilon spike (§4: monitor must sample at least as often as the daemon publishes, sub-1ms).
  • Confusing Hlc causality tracking with TrueTimeInterval bounded uncertainty — they answer different questions and must not be interchanged in timestamp_oracle.
  • Omitting the change-audit log for epsilon reconfiguration, leaving no forensic trail if a bound change later correlates with an I11 violation.

⬜ Phase 3 — Single-Shard Transactions with 2PL + MVCC §15

Objectives

Implement full single-shard read/write transactions combining LockManager (two-phase locking, still without wound-wait — that arrives Phase 8) with MvccStore, producing a complete single-shard ACID transaction with no cross-shard coordination yet.

Deliverable

A complete single-shard transactional engine: begin, read, write, commit, abort, with two-phase locking and MVCC-backed materialization, usable end-to-end without any other shard or coordinator involved, with a recorded contention baseline ahead of Phase 8's wound-wait replacement.

Acceptance
  • No transaction violates two-phase locking discipline under 10,000 randomized concurrent-transaction schedules.
  • Committed writes are invisible to any reader with read_ts < commit_ts (I4 under concurrency).
  • Crude timeout-based deadlock breaking prevents indefinite hangs in the benchmark harness (full wound-wait replaces this in Phase 8).
  • ReadSet/WriteSet freezing is enforced: an attempted write after commit has begun is rejected, not silently accepted.
  • Lock-table sharding shows near-linear throughput scaling with bucket count in the recorded baseline.
Fixtures
  • conformance/phase3/two_phase_locking_violation.json — must never occur; negative fixture.
  • conformance/phase3/write_skew_check.json — documents current isolation level before wound-wait/full concurrency control lands.
  • conformance/phase3/commit_abort_basic.json — commit and abort scenarios named per the harness requirement.
  • conformance/phase3/frozen_write_set_rejection.json — a post-freeze write attempt is rejected.
Pitfalls
  • Materializing a write to MvccStore before all locks for the transaction are confirmed held, breaking two-phase locking retroactively.
  • Releasing a lock on abort before all buffered writes are discarded, allowing a reader to observe a half-aborted state.
  • Crude timeout-based deadlock breaking picking the wrong victim (arbitrary, not age-based) — acceptable only because Phase 8 replaces this mechanism entirely.
  • Sharding the lock table by a poorly-chosen hash function that clusters hot keys into one bucket, defeating the point of sharding it at all.

⬜ Phase 4 — The 2PC Protocol Across Shards §16

Objectives

Extend Phase 3's single-shard transaction to multiple shards using two-phase commit (P2, ADR-03), introducing the Coordinator, Participant split, PrepareRequest/Vote/CommitDecision types, and the PREPARED/IN_DOUBT states — still without consensus underneath participants (that lands Phase 5) and without commit-wait (Phase 6).

Deliverable

A working cross-shard 2PC engine: a coordinator driving PREPARE/COMMIT/ABORT across N participants with a durable coordinator-side 2PC log, achieving atomicity (I2) under single-participant failure, without yet surviving a coordinator crash (Phase 7) or clock-based external consistency (Phase 6), with a recorded fan-out latency curve.

Acceptance
  • I2 holds (all-or-nothing) under fault injection killing exactly one participant mid-PREPARE, across 5,000 randomized runs.
  • Cross-shard commit latency p95 (excluding commit-wait, added Phase 6) meets the 2PC-round-trip component of the §4 budget.
  • The 2PC log contains exactly one CommitDecision or abort record per transaction, checksummed (I12).
  • The recorded fan-out latency curve shows the expected tail-amplification shape (bounded by the slowest of N participants), confirmed against 2, 4, 8, and 16 participants.
Fixtures
  • conformance/phase4/two_shard_commit_success.json — the canonical worked cross-shard commit from §8.
  • conformance/phase4/participant_abort_vote.json — one NO vote aborts all.
  • conformance/phase4/participant_timeout_during_prepare.json — timeout treated as an implicit ABORT vote.
  • conformance/phase4/sixteen_participant_fanout.json — the maximum §4 fan-out ceiling exercised directly.
Pitfalls
  • Sending COMMIT to any participant before the CommitDecision is durably logged coordinator-side, breaking I2 on a coordinator crash mid-fan-out (fully addressed in Phase 7, but the ordering discipline must start here).
  • Treating a PREPARE timeout as "still pending" indefinitely instead of a bounded-retry-then-abort, violating the max transaction duration budget (§4).
  • Materializing writes at a participant before receiving the actual COMMIT RPC, based only on having voted COMMIT itself.
  • Conflating the per-participant vote-collection timeout with the overall transaction deadline, causing a single slow participant to silently consume the whole transaction's remaining time budget.

⬜ Phase 5 — Layering 2PC Prepare/Commit Over Per-Shard Consensus §17

Objectives

Replace each participant's local-only prepare/commit logging (Phase 4) with a real replicated ConsensusGroup (consensus_shim), so that a participant's vote and commit application are themselves consensus-replicated writes (P2, ADR-04, ADR-05, Gray & Lamport 2006) — a participant survives node loss without losing a 2PC vote.

Deliverable

Every participant is now a replicated consensus group of 3 or 5 nodes; every prepare vote and commit application is a majority-replicated write before it is acted on or reported to the coordinator, closing the single-node-loss gap left open in Phase 4, with a health-check surface and a recorded latency delta over the Phase 4 baseline.

Acceptance
  • I3 holds under minority-node-kill fault injection across 5,000 runs: no vote or commit is ever lost.
  • Quorum loss (majority killed) causes the coordinator's RPC to time out, never to silently succeed or silently corrupt state.
  • Consensus-round p99 latency meets the §4 target under nominal load.
  • The health-check surface correctly reports current leader and log-index lag under both nominal operation and injected partition.
  • Partition-based fault injection (message loss, not process death) produces the same I3-preserving outcome as the hard-kill fault injection.
Fixtures
  • conformance/phase5/minority_node_kill_during_prepare.json — vote survives.
  • conformance/phase5/majority_quorum_loss.json — coordinator times out cleanly.
  • conformance/phase5/leader_reelection_mid_commit.json — commit application survives a leadership change within the group.
  • conformance/phase5/network_partition_vs_hard_kill.json — confirms equivalent I3-preserving behavior under both fault types.
Pitfalls
  • Allowing a participant to vote COMMIT based on a leader-local write that has not yet reached majority replication — silently reintroduces the Phase 4 gap.
  • Failing to fence a deposed consensus-group leader, allowing a stale leader to double-apply a commit after a new leader was already elected.
  • Conflating consensus-log compatibility (§27) with 2PC-log compatibility — they are versioned independently (ADR-05 note) and must not share a schema.
  • Treating a network partition as equivalent to a hard kill in the fault-injection harness, missing partition-specific bugs like a stale leader that can still receive but not send.

⬜ Phase 6 — The Commit-Wait Rule and External Consistency §18

Objectives

Implement the commit-wait rule (P1, I1, I5) using the real TT.now() from Phase 2, closing the loop that makes external consistency actually hold — this is the load-bearing phase of the entire project.

Deliverable

A coordinator that never releases locks or exposes a commit before waiting out the full, dynamically-measured clock-uncertainty interval, with monotonic cross-epoch timestamp assignment — external consistency now holds end-to-end for the fault-free path, with a recorded latency curve across multiple epsilon configurations validating the §34 model empirically.

Acceptance
  • Zero external-consistency violations (I1) across 20,000 randomized non-overlapping-transaction pairs in sim_harness.
  • Commit-wait duration always >= 2*epsilon at the time of the wait, and always extends (never truncates) under injected epsilon widening (I5).
  • Zero timestamp regressions across 1,000 simulated coordinator-epoch failovers (I8).
  • The recorded latency curve across epsilon values matches the §34 2*epsilon formula within measurement noise.
  • The bounded max-wait alarm fires distinctly from (and before) the Phase 10 fail-safe in a fixture where the wait is merely slow, not the clock actually out of bound.
Fixtures
  • conformance/phase6/external_consistency_nonoverlapping.json — the canonical worked proof as an executable fixture.
  • conformance/phase6/commit_wait_epsilon_spike.json — wait extension under injected spike.
  • conformance/phase6/epoch_failover_monotonicity.json — I8 across simulated failover.
  • conformance/phase6/commit_wait_duration_formula.json — validates measured wait duration against the 2*epsilon formula at several configured bounds.
Pitfalls
  • Computing commit-wait duration once at commit-decision time and sleeping a fixed interval, instead of polling TT.now() — silently breaks I5 under any epsilon spike during the wait.
  • Releasing locks optimistically "because the wait should be over by now" without an actual final TT.now() check (P5, I7).
  • Forgetting epoch fencing entirely and allowing a freshly-restarted coordinator to reuse a low-numbered timestamp range, breaking I8 without any epsilon involvement at all.
  • Confusing the bounded max-wait alarm (an operational hint that something is slow) with the Phase 10 fail-safe (a correctness-critical halt) — they must remain distinct severities in telemetry and alerting.

⬜ Phase 7 — Coordinator Failure and In-Doubt Recovery §19

Objectives

Implement RecoveryManager and the IN_DOUBT state fully (I6), so that a coordinator crash at any point in the 2PC sequence (§8) is resolved deterministically from the durable TwoPcLog on restart, never left blocking locks indefinitely.

Deliverable

A coordinator that can crash at any point in the 2PC sequence and, on restart, deterministically resolve every affected transaction to the correct terminal state within the §4 recovery-time budget, using only the durable 2PC log — no transaction is ever left blocking locks forever — with a recovery-time benchmark validating the §34 formula and a checkpoint-integrity safeguard.

Acceptance
  • 100% of transactions reach a terminal state (COMMITTED or ABORTED) within 10 s of coordinator restart, across all seven crash-point injections x 1,000 runs each (§4, I6).
  • Zero cases of a transaction resolved to an outcome inconsistent with its logged CommitDecision (I2, I6).
  • in_doubt_transaction_count returns to zero after every recovery run in the fixture suite.
  • The recovery-time benchmark's measured values fall within the range predicted by the §34 formula across at least three checkpoint-distance configurations.
  • A corrupted checkpoint is detected and recovery falls back to the next-older valid checkpoint without operator intervention.
Fixtures
  • conformance/phase7/crash_after_prepare_before_decision.json — resolves to ABORT (no decision logged).
  • conformance/phase7/crash_after_decision_before_fanout.json — the canonical §8 worked recovery example; resolves to COMMIT, re-drives fan-out.
  • conformance/phase7/crash_during_commit_wait.json — decision already logged; recovery must still enforce commit-wait before considering the transaction externally visible, not skip it.
  • conformance/phase7/corrupted_checkpoint_fallback.json — recovery falls back to the next-older valid checkpoint.
Pitfalls
  • Resolving an IN_DOUBT transaction by re-asking participants to vote again instead of consulting the log — risks a different outcome than what a participant may have already partially applied (ADR-12).
  • Forgetting that a crash during commit-wait (decision already logged, wait incomplete) must resume the wait on recovery, not skip straight to "committed and visible" (I5 still applies during recovery).
  • Unbounded 2PC log growth without checkpointing, making recovery-time scale with cluster history instead of recent activity, violating the §4 recovery-time budget over the cluster's lifetime.
  • Trusting a checkpoint's contents without an integrity check, risking a recovery built on corrupted state that then propagates incorrect decisions to participants.

⬜ Phase 8 — Wound-Wait Deadlock Handling §20

Objectives

Replace Phase 3's crude timeout-based deadlock breaking with proper wound-wait (P8, I10, ADR-10), assigning transaction priority from start_ts so that no detection round-trip is ever needed on the commit-critical path.

Deliverable

A per-participant lock manager using wound-wait exclusively for deadlock avoidance, with no detection round-trip on the commit path, integrated with the Phase 4-7 cross-shard 2PC flow so a wound at one participant correctly aborts the transaction everywhere, with a benchmark quantifying the improvement over Phase 3's crude mechanism.

Acceptance
  • Zero surviving deadlock cycles across 20,000 randomized concurrent-transaction lock-acquisition graphs (I10).
  • The oldest transaction in every contended benchmark run eventually commits (no starvation).
  • A wound at any single participant results in a full cross-shard ABORT within one 2PC round, not a partial abort.
  • The deterministic tiebreak resolves an identical-start_ts fixture without mutual wounding or a stall.
  • The Phase 8 benchmark shows lower abort latency and lower lock-wait queue depth under contention than the Phase 3 crude-timeout baseline.
Fixtures
  • conformance/phase8/deadlock_cycle_two_txn.json — the canonical named deadlock scenario referenced by the harness requirement.
  • conformance/phase8/wound_cascade.json — a wounded transaction itself holding locks that unblock further waiters.
  • conformance/phase8/cross_shard_wound_propagation.json — a wound at one participant aborting the transaction cluster-wide.
  • conformance/phase8/identical_start_ts_tiebreak.json — the deterministic tiebreak fixture.
Pitfalls
  • Comparing transactions by wall-clock arrival order instead of start_ts, which can disagree under clock skew and silently reintroduce cycles.
  • Wounding a transaction that is already in PREPARED state (post-vote) without correctly transitioning it through ABORT at every participant, violating I2.
  • Forgetting cascading release: a wounded transaction that does not immediately release its own locks can itself deadlock a third transaction.
  • Building a bespoke cross-shard wound-propagation path instead of reusing the Phase 4 abort fan-out, doubling the number of places I2 must be independently verified.

⬜ Phase 9 — Read-Only Snapshot Transactions at a Timestamp §21

Objectives

Fully realize the read-only fast path (P3, P11, ADR-11) as a first-class transaction type distinct from read-write transactions, guaranteeing zero lock acquisition and zero coordinator round-trip for the common case, building on Phase 1's groundwork with the real TrueTime clock from Phase 2 and the cross-shard MVCC stores from Phase 4-5.

Deliverable

A read-only snapshot-read API usable across shards, requiring no lock acquisition and no participation in 2PC, scaling independently of write throughput, with a documented and tested guarantee that it never observes a partially-committed cross-shard transaction, and a benchmark quantifying the lock-free read-path advantage against the Phase 3 read-write baseline.

Acceptance
  • Zero lock-manager calls observed during any snapshot read across the full cross-shard fixture suite.
  • Zero instances of a snapshot read observing a partial cross-shard commit (some but not all participants' writes visible) across 10,000 racing-commit fixture runs.
  • Snapshot-read throughput in the benchmark harness does not degrade as concurrent write load increases (§31 independence claim), confirmed at zero, moderate, and peak write load.
  • The lagging-participant bounded wait resolves within a small fixed budget, independent of any in-progress commit-wait elsewhere in the cluster.
Fixtures
  • conformance/phase9/snapshot_read_races_commit.json — the canonical §8 worked example.
  • conformance/phase9/cross_shard_snapshot_all_or_nothing.json — verifies atomic visibility across shards at one read_ts.
  • conformance/phase9/bounded_staleness_read.json — the stale-read mode.
  • conformance/phase9/lagging_participant_bounded_wait.json — a snapshot read against a participant still catching up on its consensus log.
Pitfalls
  • Reading a cross-shard transaction's writes at different shards using slightly different effective timestamps, producing an inconsistent partial view — this is precisely what I4 (extended to the cross-shard case) forbids.
  • Accidentally routing a snapshot read through any part of the lock manager "just to be safe," reintroducing coordination cost the whole phase exists to avoid (P3, P11).
  • Treating "read-only" as a client-declared hint rather than a structurally enforced property — a transaction that later attempts a write after being routed as read-only must be rejected, not silently upgraded.
  • Implementing the lagging-participant wait with the same polling loop shape as commit-wait, accidentally coupling read-path latency to write-path clock semantics it has nothing to do with.

⬜ Phase 10 — The Clock-Epsilon Monitor and the Fail-Safe on Epsilon Violation §22

Objectives

Fully implement ClockMonitor and its fail-safe (I11, ADR-18): continuous epsilon-bound sampling that halts new commits cluster-wide the instant the bound is violated, since a silent epsilon violation is the single failure mode that breaks external consistency without any other visible symptom.

Deliverable

A continuously-running clock monitor that detects an epsilon-bound violation within one sampling interval, halts new commit activity and new transaction begins cluster-wide before external consistency can be silently broken, safely completes any commit-wait already in flight, resumes automatically once the bound is re-established, and records near-miss telemetry for trend analysis.

Acceptance
  • 100% of injected epsilon violations trip the fail-safe within one sampling interval, across severity levels from 1.5x to 10x the configured bound.
  • Zero external-consistency violations occur during or immediately after any injected violation-and-recovery cycle (I1, I11 combined check).
  • In-flight commit-waits during an injected violation always complete correctly (I5), never abandoned.
  • New transaction begins are rejected (not merely queued) while the fail-safe is tripped, verified by a fixture that floods begins during an active trip.
  • Near-miss telemetry correctly distinguishes a self-resolving transient widening from an actual trip across a dedicated fixture set.
Fixtures
  • conformance/phase10/epsilon_violation_clean_trip.json — the canonical §8 worked example.
  • conformance/phase10/violation_during_inflight_commit_wait.json — wait extension under active violation.
  • conformance/phase10/violation_recovery_resume.json — automatic resume after stability window.
  • conformance/phase10/transaction_begin_flood_during_halt.json — begins rejected cleanly during an active trip.
  • conformance/phase10/near_miss_transient_widening.json — telemetry recorded without a trip.
Pitfalls
  • Sampling too infrequently, letting a transient-but-real violation slip through undetected — this defeats the entire purpose of the phase and must be caught by the fault-injection suite, not assumed correct from code inspection.
  • Halting new commits but forgetting to also halt new read-write transaction begins, allowing a flood of doomed transactions to pile up against the halt.
  • Treating the fail-safe as "just another availability degradation" in dashboards, rather than surfacing it distinctly as the single correctness-critical alert it is (P9, ADR-18).
  • Conflating near-miss telemetry with actual trip telemetry in the same counter, obscuring the trend signal §26 depends on for early-warning purposes.

⬜ Phase 11 — Jepsen/Elle-Style Verification Harness, Chaos, and Performance Hardening §23

Objectives

Build the sim_harness into a full Jepsen/Elle-style history checker (Herlihy & Wing 1990) capable of falsifying external consistency and linearizability under combined clock-skew and partition fault injection, and run a final chaos-and-performance hardening pass across every invariant and metric established in Phase 0-10.

Deliverable

A deterministic, seed-replayable Jepsen/Elle-style verification harness that runs combined chaos scenarios across every subsystem, checks the recorded history for external-consistency and serializability violations, gates CI on both correctness and performance regression, automatically minimizes any counterexample it finds, permanently regression-tests every historical finding, and produces the evidence trail this blueprint's own harness section reports against.

Acceptance
  • Zero external-consistency or serializability-anomaly findings by the Elle-style checker across a soak run combining all four chaos scenario types, for a minimum of 100,000 recorded transaction histories.
  • The linearizability CI job runs on every push and blocks merge on any finding (ADR-24).
  • No §4 or §30 metric regresses beyond its configured CI threshold.
  • Any counterexample injected synthetically into the harness for testing the checker itself is minimized to a schedule no larger than necessary to still reproduce it.
  • The consolidated end-to-end baseline document accounts for the full commit-latency budget as the sum of each phase's measured contribution, reconciling with the §34 capacity model.
Fixtures
  • conformance/phase11/combined_partition_and_clock_spike.json — the flagship combined-fault scenario.
  • conformance/phase11/elle_checker_regression_corpus.json — replayed counterexamples from every prior phase's fault-injection fixtures, re-checked under the full Elle-style analysis.
  • conformance/phase11/deterministic_replay_bitexact.json — proves seed-based replay reproduces an identical history.
  • conformance/phase11/counterexample_minimization.json — a synthetically-injected violation is shrunk to a minimal reproducing schedule.
Pitfalls
  • Building a checker that only checks per-invariant (I1, I2, ...) assertions already covered by earlier phases, rather than a true history-based Elle-style analysis capable of finding anomalies no single invariant check anticipated.
  • Non-determinism leaking into the harness itself (unseeded randomness anywhere in the fault-injection or scheduling code), silently breaking P12 and making every counterexample unreproducible.
  • Running chaos scenarios in isolation only, missing the combined-fault interactions (e.g., partition plus clock spike) that are the actual point of this phase per the arc description.
  • Letting the regression corpus grow without bound on CI wall-clock time, eventually making every push too slow to be useful — budget corpus replay time explicitly and prioritize combined-fault cases over single-fault ones if trimming is ever needed.
