32. Mental Models & First Principles

  • MM1 — Spanner's insight is that if you can bound clock uncertainty, you can buy external consistency by simply waiting it out: commit-wait converts a hardware (or simulated) clock guarantee into a database correctness guarantee (Corbett et al. 2012).
  • MM2 — 2PC gives atomicity but is a blocking protocol with a single-point coordinator, so you make the participants and the coordinator's decision themselves fault-tolerant with consensus — 2PC over Paxos is the standard composition (Gray & Lamport 2006).
  • MM3 — Reads are the easy 90%: MVCC snapshot reads at a timestamp need no coordination at all, so the entire hard engineering effort concentrates in the write commit path.
  • MM4 — A timestamp interval, not a scalar, is the honest unit of "now" in any system with bounded clock error; every bug class in this project traces back to someone treating an interval as if it collapsed to a point too early.
  • MM5 — Locks and clocks are the same kind of resource: both are held/consulted for the minimum correct duration and never released or trusted early, because "early" is exactly where external consistency breaks silently.
  • MM6 — A durable log is a memory, and recovery is nothing but re-reading that memory correctly; every recovery bug in this project is, at root, a case of trusting some other source over the log.
  • MM7 — Wound-wait turns deadlock avoidance into a total order (by transaction age) rather than a search problem (cycle detection) — the entire cost is paid at the moment of conflict, never a background scan.
  • MM8 — The commit path is inherently more expensive than the read path not because of implementation quality but because of the physics of the guarantee being made — a write must be ordered against every future observer, a read only against the past.
  • MM9 — Determinism in verification (seeded, replayable fault injection) is what turns "it worked in testing" into an actual falsifiable claim about external consistency, rather than an unfalsifiable one.

5. Required Reading

Books

  • Bernstein, Hadzilacos & Goodman, Concurrency Control and Recovery in Database Systems — ch. 3 (serializability theory), ch. 4 (locking, 2PL), ch. 7 (distributed transactions, 2PC) — applied in §8, §12-§17.
  • Kleppmann, Designing Data-Intensive Applications — ch. 7 (transactions), ch. 8 (distributed systems trouble, clocks), ch. 9 (consistency and consensus) — applied in §6, §8, Phase 6.
  • Gray & Reuter, Transaction Processing: Concepts and Techniques — 2PC and recovery chapters — applied in §12, Phase 4-5, Phase 7.
  • Petrov, Database Internals — MVCC, WAL, and concurrency-control chapters — applied in Phase 1, Phase 3.
  • Ongaro, Consensus: Bridging Theory and Practice (Raft dissertation) — leader election, log replication, membership — applied in Phase 5 (consensus_shim).
  • Weikum & Vossen, Transactional Information Systems — multi-level and distributed transaction chapters — applied in §8, Phase 7-8.

Papers

  • Corbett et al. 2012, "Spanner: Google's Globally-Distributed Database" (OSDI) — THE foundational paper: TrueTime, commit-wait, external consistency — applied in §8, Phase 2, Phase 6.
  • Bacon et al. 2017, "Spanner: Becoming a SQL System" (SIGMOD) — evolution and lessons — applied in §33.
  • Lamport 1978, "Time, Clocks, and the Ordering of Events in a Distributed System" (CACM) — causality baseline for TrueTime/HLC contrast — applied in §8, Phase 2.
  • Lamport 2001, "Paxos Made Simple" (and 1998 "The Part-Time Parliament") — consensus core — applied in Phase 5.
  • Ongaro & Ousterhout 2014, "In Search of an Understandable Consensus Algorithm" (Raft, USENIX ATC) — applied in Phase 5.
  • Gray & Lamport 2006, "Consensus on Transaction Commit" (ACM TODS) — Paxos Commit, directly on-point for 2PC-over-consensus — applied in §9 ADR-05, Phase 5.
  • Skeen 1981, three-phase commit — the non-blocking alternative, contrasted in §9 ADR-04 — applied in Phase 4.
  • Herlihy & Wing 1990, "Linearizability: A Correctness Condition for Concurrent Objects" (ACM TOPLAS) — the formal target of §28's checker — applied in Phase 11.
  • Thomson et al. 2012, "Calvin: Fast Distributed Transactions for Partitioned Database Systems" (SIGMOD) — deterministic ordering alternative — applied in §36.
  • Peng & Dabek 2010, "Large-scale Incremental Processing Using Distributed Transactions and Notifications" (OSDI, Percolator) — OCC-with-central-oracle alternative — applied in §36.
  • Bailis et al. 2013, "Highly Available Transactions" (VLDB) — the availability/consistency tradeoff frame — applied in §31.
  • Adya 1999 (weak-isolation thesis) and Berenson et al. 1995 (ANSI SQL isolation critique) — isolation-hierarchy placement — applied in §8.
  • Bailis et al. 2013 "Highly Available Transactions" is cited a second time here specifically for its availability-vs-consistency framing of the commit-wait tradeoff — applied in §31, §36.
  • Kingsbury's Jepsen analyses (ongoing series, jepsen.io) — the methodology and prior findings against real distributed databases that motivate this project's own Phase 11 history checker — applied in §23, §28.

Reference Implementations

  • CockroachDB, pkg/kv/kvserver/ and pkg/storage/ — HLC hybrid-logical-clock, transaction record, intent resolution; lesson: external consistency is achievable without atomic clocks at the cost of a larger uncertainty window; pitfall: read restarts under uncertainty must be visible to the client contract — applied in §33, §36.
  • TiKV, src/storage/txn/ — Percolator-style OCC over a central timestamp oracle; lesson: a central oracle simplifies ordering but becomes a throughput ceiling; pitfall: primary-lock cleanup races — applied in §33, §36.
  • YugabyteDB — hybrid-time implementation layered on a Raft-replicated document store; lesson: HLC composes with Raft cleanly; pitfall: clock-skew bounds must be operator-visible — applied in §33.
  • FoundationDB, fdbserver/ — a strictly-serializable transaction system with a separate resolver tier; lesson: separating conflict resolution from storage aids testability; pitfall: resolver becomes a single logical bottleneck at extreme scale — applied in §33, §31.
  • Google Spanner (as described in Corbett et al. 2012 and Bacon et al. 2017) — the canonical TrueTime + commit-wait system; lesson: commit-wait is a deliberate, bounded, monitored wait, not a hack; pitfall: requires dedicated clock hardware and a monitored fail-safe — applied throughout, especially §8, Phase 2, Phase 10.
  • etcd's Raft implementation — a widely-deployed, well-documented Raft core; lesson: a clean separation between the consensus core and its storage/network integration aids testability, directly informing consensus_shim's own layering; pitfall: membership-change edge cases are easy to under-test — applied in Phase 5, §36.

RFCs / Specifications

  • gRPC/Protocol Buffers specification — the normative transport and wire-format reference for coordinator-participant RPC — applied in §9 ADR-16, §10.
  • NTP (RFC 5905) and PTP (IEEE 1588, referenced descriptively) — the clock-synchronization baselines that bound achievable epsilon — applied in §9 ADR-18, Phase 2.
  • The Spanner and Gray & Lamport papers above serve as the normative protocol specifications for TrueTime and Paxos Commit respectively, in the absence of a dedicated RFC — applied in §8, Phase 5-6.

Glossary (§38) · 60 terms · site-wide glossary

Distributed transaction
a transaction whose reads/writes span more than one shard/node
Atomic commit
the property that a transaction's effects are applied at every participant or none
Two-phase commit (2PC)
prepare-then-commit protocol achieving atomic commit across participants
Three-phase commit (3PC)
Skeen's non-blocking extension of 2PC adding a pre-commit phase
Paxos Commit
Gray & Lamport's composition of 2PC with Paxos-replicated votes
Prepare
the 2PC phase in which a participant durably logs intent and votes
In-doubt
a transaction state where a participant has voted but not learned the final decision
Coordinator
the process driving 2PC and owning the durable decision log
Participant
a shard-owning process that votes and applies a transaction's local effects
Consensus
agreement among replicas on a single value or log entry despite failures
Paxos
Lamport's foundational consensus protocol
Raft
Ongaro & Ousterhout's understandable consensus protocol
Replication
maintaining multiple copies of state for fault tolerance
External consistency
if T1 commits before T2 starts in real time, T1's timestamp precedes T2's
Linearizability
the correctness condition that operations appear to take effect atomically at some point between invocation and response
Serializability
transactions appear to execute in some sequential order, without regard to real time
Strict serializability
serializability plus real-time ordering, equivalent to external consistency at the transaction level
Snapshot isolation
an isolation level where a transaction sees a consistent snapshot but may permit write skew
MVCC
multi-version concurrency control: keeping multiple timestamped versions per key
Version
one immutable, timestamped value of a key
Version chain
the ordered sequence of versions for one key
Snapshot read
a read at a fixed timestamp returning the version current as of that time
TrueTime
Spanner's bounded-clock-uncertainty API, TT.now() -> [earliest, latest]
Clock uncertainty
the width of the interval within which the true time is known to lie
Epsilon
half the width of the TrueTime uncertainty interval
Commit-wait
waiting until the clock has certainly passed a transaction's commit timestamp before releasing its effects
Hybrid logical clock (HLC)
a clock combining physical time and a logical counter for causality tracking without special hardware
Timestamp oracle
the component assigning transaction timestamps
Wound-wait
a deadlock-avoidance scheme where an older transaction aborts (wounds) a younger conflicting one
Wait-die
a deadlock-avoidance scheme where an older transaction waits and a younger one dies (aborts)
Deadlock
a cycle of transactions each waiting on a lock held by the next
Lock
an exclusivity token on a key held by a transaction
Two-phase locking (2PL)
acquiring all locks before releasing any, within one transaction
Quorum
a majority subset of a replica group sufficient to make progress
Deterministic transactions
transactions executed in a globally pre-agreed order, avoiding 2PC
Calvin
Thomson et al.'s deterministic-ordering distributed transaction system
Percolator
Google's OCC-over-Bigtable incremental transaction system, central-timestamp-oracle style
Epoch
a coordinator's leadership generation number, used for fencing
Fencing token
a monotonically increasing token preventing a stale leader/epoch from acting
Consensus group
the set of replicas replicating one shard's log
Leader election
the process by which a consensus group selects its current leader
Log replication
copying log entries from a leader to followers under consensus
2PC log
the coordinator's durable, append-only prepare/commit/abort decision record
Tombstone
a versioned marker recording a delete, distinct from absence
Garbage collection (GC)
reclaiming old MVCC versions no longer needed by any live snapshot
Read-only transaction
a transaction with an empty write set, servable via snapshot read alone
Read-write transaction
a transaction that acquires locks and participates in 2PC
Fail-safe
a deliberate halt of new activity triggered by detection of a correctness-threatening condition
Shard
a partition of data owned by one participant/consensus group
Fan-out
the number of participants a coordinator must contact for one transaction
Tail latency
latency at high percentiles (p95/p99), often dominated by the slowest component
Backpressure
bounding queues/concurrency to prevent unbounded resource growth under load
Idempotency
the property that repeating an operation has the same effect as doing it once
Checkpoint
a compacted snapshot of log state used to bound recovery-time scan length
Forensic replay
deterministic re-execution of a recorded fault-injection run for debugging
Jepsen
Kingsbury's distributed-systems testing methodology and tool family for fault-injection verification
Elle
a history-checker methodology for detecting transactional-isolation and consistency anomalies
History checker
a tool that analyzes a recorded operation history for correctness violations
Write skew
an anomaly where two transactions each read overlapping data and write disjoint data, violating a joint constraint
Phantom read
an anomaly where a transaction's predicate query sees a different result set on repetition due to a concurrent insert/delete
