Decisions (§9) · 32 ADRs

ADR-01

Implementation language

Chosen

Python 3.12+

Rejected

Rust, Go, Java

When the rejected choice is right

a production Spanner-class system serving real traffic, where Rust's throughput and memory safety pay for their ceremony

Why: protocol clarity over throughput; dataclasses and asyncio suit the state-machine-heavy domain

ADR-02

Clock mechanism

Chosen

TrueTime-style bounded-uncertainty interval (simulated)

Rejected

HLC, plain logical clocks, central timestamp oracle

When the rejected choice is right

a deployment with no dedicated clock hardware and no tolerance for commit-wait latency — HLC wins there (see §36)

Why: matches the Spanner load-bearing mechanism this project is built to teach

ADR-03

Atomic-commit protocol

Chosen

Two-phase commit (2PC)

Rejected

Three-phase commit (3PC), Paxos Commit as sole protocol

When the rejected choice is right

a deployment intolerant of any coordinator-crash blocking window — 3PC wins there despite its own quorum-failure edge cases

Why: matches project 73's baseline while this project adds consensus underneath rather than a non-blocking 3PC extension

ADR-04

Per-shard replication

Chosen

Paxos/Raft-style consensus (consensus_shim, in-repo minimal)

Rejected

no replication (single node per shard)

When the rejected choice is right

a purely local, single-machine prototype with no availability requirement

Why: a participant must survive node loss without losing a 2PC vote

ADR-05

2PC/consensus layering

Chosen

2PC prepare and commit are themselves consensus-replicated writes (Paxos Commit style, Gray & Lamport 2006)

Rejected

2PC votes logged locally only

When the rejected choice is right

a deployment where participant hosts are individually fault-tolerant hardware (e.g., mirrored enterprise storage) making software replication redundant

Why: prevents a single node's local-disk 2PC vote from being lost on crash

ADR-06

Concurrency control

Chosen

MVCC + wound-wait 2PL

Rejected

pure OCC, deterministic (Calvin-style) ordering

When the rejected choice is right

a workload with fully known read/write sets up front and very high write contention — Calvin-style determinism wins there (see §36)

Why: snapshot reads must be lock-free while writes still need conflict serialization

ADR-07

Isolation level target

Chosen

external consistency (strict serializability)

Rejected

snapshot isolation, plain serializability

When the rejected choice is right

an analytics-heavy workload tolerant of write skew, where snapshot isolation's lower coordination cost wins

Why: matches the Spanner guarantee this project is built to reproduce

ADR-08

Commit-wait implementation

Chosen

explicit wait loop polling TT.now() until earliest > s

Rejected

no wait (assume clocks perfect)

When the rejected choice is right

A single-region deployment with a tightly-synchronized shared clock (ε≈0) where the wait rounds to zero anyway, or a system that only promises snapshot isolation, not external consistency — where omitting the wait breaks I1 unconditionally; it wins in no real regime

Why: the wait is the entire correctness mechanism (P1)

ADR-09

Timestamp-assignment strategy

Chosen

coordinator-local assignment from TT interval, epoch-fenced

Rejected

central timestamp-oracle service (Percolator-style)

When the rejected choice is right

an OCC design already built around a central oracle for conflict detection — TiKV/Percolator's regime (see §36)

Why: avoids a single bottleneck service for every transaction

ADR-10

Deadlock handling

Chosen

wound-wait

Rejected

wait-die, cycle detection

When the rejected choice is right

a workload with very short lock hold times and low contention, where lightweight detection's simplicity wins

Why: wound-wait avoids a detection round-trip on the latency-critical commit path

ADR-11

Snapshot-read design

Chosen

MVCC version-chain scan at a read timestamp, lock-free

Rejected

locking reads, read-through to leader only

When the rejected choice is right

a workload requiring read-your-writes without any timestamp bookkeeping, where always-read-leader is simpler

Why: matches P3 and keeps reads off the write critical path

ADR-12

In-doubt resolution

Chosen

durable 2PC log replay on coordinator recovery

Rejected

participant-side voting re-run

When the rejected choice is right

a stateless-coordinator design with no durable log at all, acceptable only if participants can safely re-negotiate (rare)

Why: the log is authoritative and re-voting risks a different outcome than what was already partially applied

ADR-13

Participant-group membership

Chosen

Rejected

When the rejected choice is right

a long-lived production cluster requiring live shard rebalancing without downtime

Why: reconfiguring mid-transaction adds a correctness hazard this project does not need to solve first

ADR-18

Epsilon-bound monitoring / fail-safe

Chosen

continuous clock_monitor sampling, halt-new-commits on violation

Rejected

When the rejected choice is right

A read-only replica or an analytics-only deployment that never issues externally-consistent writes, where a stale ε only degrades read freshness rather than breaking a correctness invariant, so best-effort logging suffices

Why: a silent epsilon violation breaks external consistency invisibly — the single correctness-critical failure mode

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1 — Deterministic Transaction Ordering (Calvin)

   Client --> Sequencer (global order, batched epochs)
                    |
                    v
         +---------------------+
         | Deterministic        |
         | Scheduler (per node) |
         +----------+-----------+
                    |
       (no 2PC, no per-txn voting)
                    v
         +---------------------+
         |  Deterministic       |
         |  Execution Engine    |
         +---------------------+

Winning regime: extremely high write throughput with read/write sets knowable in advance (e.g., known-schema OLTP with simple predicates). Real embodying system: Calvin (Thomson et al. 2012), and its lineage in FaunaDB. Rejected here because: this project's pedagogical goal is precisely the TrueTime/commit-wait/2PC-over-consensus composition (§1) — pre-ordering sidesteps the exact mechanisms (clock uncertainty, 2PC voting) this blueprint exists to teach, and requiring full read/write sets up front is a poor fit for interactive, ad hoc transactions.

Alternative 2 — HLC Without Atomic Clocks

   Node A: HLC (phys, logical) --\
   Node B: HLC (phys, logical) ---> max() on message receipt --> causal order
   Node C: HLC (phys, logical) --/
                    |
      external consistency via larger, conservative
      uncertainty window + occasional read-restart

Winning regime: deployments with no access to dedicated clock hardware (GPS/atomic clocks) that still want external consistency, accepting a wider uncertainty window and occasional client-visible read restarts. Real embodying system: CockroachDB. Rejected as the primary mechanism here (though implemented as a comparison point in hlc.py, Phase 2) because the project's explicit goal is to reproduce Spanner's bounded-and-monitored-epsilon mechanism (§1); HLC's unbounded worst case would weaken the very commit-wait guarantee this blueprint is built to demonstrate precisely. PhaseDeferred("§36 Alternative Architectures (Roads Not Taken)") as a selectable fallback clock mode.

Alternative 3 — Optimistic Concurrency with a Central Timestamp Oracle

   Clients --> Central Timestamp Oracle (TSO) --> monotonic ts
                        |
        +---------------+---------------+
        v                               v
   Node A (OCC, primary-lock)      Node B (OCC, primary-lock)

Winning regime: workloads where a single, simple, centrally-ordered timestamp service is acceptable and write conflict rates are low enough that optimistic validation rarely aborts. Real embodying system: TiKV/TiDB (Percolator lineage, Peng & Dabek 2010). Rejected here because a central oracle is a single logical bottleneck and reintroduces exactly the kind of centralization this project's bounded-clock, decentralized-timestamp-assignment design (ADR-09) is built to avoid.

Alternative 4 — Single-Shard-Only Design (No Cross-Shard Transactions)

   Client --> Shard Router --> exactly one shard's
                                Coordinator+Participant
                                (local 2PL + MVCC only)
              (cross-shard transactions rejected at the API)

Winning regime: applications that can be fully partitioned by a single sharding key with no cross-partition transactional need — the common case for many multi-tenant SaaS systems. Rejected as this project's primary design because the entire pedagogical point (§1) is the cross-shard 2PC-over-consensus-plus-commit-wait composition; a single-shard-only system would still need everything through Phase 3 but would skip Phase 4-7 and 11's most load-bearing content entirely.
