Project Number: 96

Project Name: Distributed Lock Service

1. Goal & Scope

coord is a Chubby/ZooKeeper/etcd-lock-class distributed coordination service: a hierarchical namespace of znodes (persistent, ephemeral, sequential) with one-shot watches, session-leased liveness (Connecting → Connected → Jeopardy → Expired), per-znode ACLs, and a Raft-replicated state machine giving linearizable writes and sequential-consistency reads with an explicit sync() read-linearization primitive. Every successful lock grant returns a monotonic 64-bit fencing token so a protected resource can reject a stale holder's writes after a GC pause, a network partition, or a clock-skew event (Kleppmann 2016).

Phase-0 deliverable (numbered modules — crate names are normative, reused identically everywhere in this document):

  1. coord-core — no_std + alloc state machine: namespace tree, Stat, Session, Watch, AclEntry, Zxid, Mutation::apply.
  2. coord-net — bespoke length-prefixed wire protocol; single-node connection loop.
  3. coord-storage — the Wal/Snapshot trait surface (Phase 5 fills the implementation).
  4. coord-sdk — minimal client: connect, create, get_data, set_data, delete.
  5. coord-cli — coordctl binary wrapping the SDK for operator use.

System boundaries:

  • Provides: linearizable hierarchical namespace; session leases; ephemeral/sequential znodes; one-shot watches; per-znode ACLs; monotonic fencing tokens; lock/leader-election/group-membership/barrier recipes; Raft replication; snapshot+WAL durability.
  • Delegates: TLS record-layer detail to rustls; replica-set discovery to the deployment's service-discovery layer; the protected resource's fencing-token check to the resource owner — by design, not oversight (§8.4 explains why this cannot be pulled inside the service).
  • Does NOT provide: Byzantine-fault tolerance (PhaseDeferred("§1")); cross-region geo-replication (PhaseDeferred("§1")); persistent (non-one-shot) watches (PhaseDeferred("§1")); observer (non-voting) replicas (PhaseDeferred("§1")); multi-tenant subtree quotas beyond the per-session caps in §4 (PhaseDeferred("§1")); a gRPC wire protocol (PhaseDeferred("§1")); ACL templates/inheritance (PhaseDeferred("§1")); a BoundedStaleness read mode (PhaseDeferred("§1")).

Non-goals: general key-value-store semantics (no range scans, no streaming/append, no offset-based access — §8.1 makes writes whole-value); a from-scratch ZAB re-implementation (Raft substitutes; Junqueira-Reed-Serafini 2011, section 2, shows the operational guarantees are equivalent — §35 discusses the tradeoff); a general-purpose pub/sub bus (watches are one-shot, not a durable message queue).

Deployment model: 3- or 5-node clusters, one OS process per replica, rack-local or single-availability-zone (the RTT budget in §4 assumes this); clients are a separate fleet connecting over TCP+TLS 1.3, discovered via a static list or DNS SRV records.

Target users/operators: platform/infrastructure teams operationalizing leader election, distributed mutual exclusion, or configuration distribution for services such as an HDFS NameNode HA pair, a pre-KRaft Kafka controller, an HBase master, or any custom service that must answer "who is the leader" correctly under partition.

What later phases unlock: Phase 4 (§16, Raft) unlocks multi-node durability and linearizable writes; Phase 6 (§18, SDK) unlocks the recipe layer; Phases 7–8 (§19–§20) unlock lock/leader/membership/barrier; Phase 9 (§21) unlocks multi-tenant ACL isolation; Phase 10 (§22) unlocks the throughput/latency targets tabulated in §29.

Recommended language: Rust 1.78+ (edition 2021). Rationale: the borrow checker eliminates the use-after-free and data-race classes that have caused real ZooKeeper/etcd client-library CVEs in C-based dependencies; coord-core's no_std + alloc discipline makes the state machine deterministically testable under cargo miri; tikv/raft-rs and openraft are the operational benchmark for Raft-in-Rust maturity (ADR-03, §9). Rejected: Go — its GC pauses are exactly the failure class the fencing-token mechanism (§8.4) exists to survive; building the fencing-token teacher in a garbage-collected language undercuts the pedagogy. C++ — memory-safety risk concentrates precisely in the wire-decode and WAL-replay paths, the two surfaces the fuzz corpus (§27) exercises hardest. Java — the ZooKeeper/Chubby-successor ecosystem already owns this niche in Java; reimplementing it there teaches nothing new.

Prerequisites: the FLP impossibility result (Fischer-Lynch-Paterson 1985); the Paxos/Raft consensus family; the distinction between linearizability and sequential consistency (Herlihy-Wing 1990, Lamport 1979); the failure-detector hierarchy (Chandra-Toueg 1996); and why STW GC pauses and kernel-level NIC stalls motivate fencing tokens (Kleppmann 2016). A reader must be able to explain, unaided, why a ZooKeeper watch is one-shot and why the namespace is a tree, not a key-value store (Hunt et al. 2010, section 4.1).

Estimated timeline: Phase 0 in 1 week (repo skeleton + single-node namespace smoke test); the full system (Phases 0–10) in 6–9 months of dedicated engineering time; the Sealed gate (30-day soak + 30-day fuzz canary + Jepsen-class harness, §27) adds a mandatory 30 calendar days after Phase 10 code-complete.

Every deferred feature is flagged inline with PhaseDeferred("§1"); the Deferred Features Register (§36) lists each with its anchor and un-defer trigger.

2. Why Build This

  • A coordination service answers three questions every distributed system needs and, absent one, reinvents badly: who is the leader, is this node alive, and did my lock get revoked while I was paused. Chubby (Burrows 2006) was Google's first production answer; ZooKeeper (Hunt et al. 2010) was Yahoo!'s open-source successor and became the Hadoop ecosystem's default; etcd (Raft-backed) is Kubernetes's coordination substrate.
  • Concrete cross-links by name: HDFS NameNode HA uses ZooKeeper for active/standby election; HBase uses it for region-server membership and master election; pre-KRaft Kafka used it for controller election and topic metadata; Mesos uses it for master election; Kubernetes uses etcd — conceptually the same primitive family, Raft-replicated.
  • The folklore alternative — SET NX EX in Redis — fails in ways that only surface in production: a GC pause exceeding the lease, a partition quarantining the lease-check from the protected resource, a clock-skew event making two nodes believe they hold the lock simultaneously. Kleppmann's 2016 essay is the definitive teardown; the fix (fencing tokens) is this project's central lesson (§8.4, §19).
  • Engineering muscles built: hierarchical tree state machines with O(log n) traversal (§13); session-liveness state machines distinct from transport liveness (§14); one-shot watch delivery ordering (§15); Raft leader election, log replication, and commit-then-apply (§16); snapshot+WAL durability with per-record CRC (§17); ACL evaluation without inheritance (§21); recipe composition (lock/leader/membership/barrier, §19–§20) built entirely from four primitives.
  • Calibration value: after Phase 10 (§22) you can explain exactly why a partition is harmless to the majority side and read-only-degraded on the minority side; exactly why writes traverse Raft and reads optionally do not; exactly why a watch is fired-and-forgotten; exactly which invariant (§7) a given production incident violated.
  • The deliverable is deliberately small enough to finish: no ZAB (Raft substitutes — §35 gives the tradeoff), no BFT (§36 deferred), no cross-region replication (§36 deferred), no multi-tenant quotas beyond per-session caps (§36 deferred).

What Mastery Looks Like

  • Can explain, without notes, why ephemeral-node deletion on session expiry must be atomic with the ExpireSession log entry, and what state corruption results if it is not. Cemented in Phase 2 (§14).
  • Can trace the exact Raft log-entry sequence a Lock::acquire() call produces under contention, including the predecessor-watch optimization that defeats the thundering herd. Cemented in Phase 7 (§19).
  • Can reproduce the Kleppmann 2016 scenario verbatim and explain why the coordination service alone cannot stop a paused lock-holder from writing to the resource, and why the resource-side fencing check is the only closure. Cemented in Phase 7 (§19) and the Threat Model (§23).
  • Can distinguish sequential consistency from linearizability operationally, not just definitionally, and name exactly which read mode a given client-visible bug required. Cemented in Phase 4 (§16) and Phase 6 (§18).
  • Can reconstruct, from the WAL and snapshot formats alone (§8.6), the exact replay procedure a crashed replica executes on restart, including CRC-mismatch truncation behavior. Cemented in Phase 5 (§17).
  • Can redesign the replication core around ZAB instead of Raft and name the two properties that would need re-proving. Cemented by the Alternative Architectures discussion (§35).
  • Can operate the service — read the dashboards, diagnose a stuck election, execute the leader-failover runbook — without escalating. Cemented in Operational Readiness (§25).

Application layer — external services that consume coord as a dependency; out of this project's scope but the reason it exists. Client SDK — owns connection pooling, session reconnection, idempotent retry via request-id de-duplication, watch re-arming, and the four composed recipes; the only layer application code touches. Session layer — the truth-source for liveness (§7 I6); tracks heartbeats and the four-state session machine; every ephemeral znode and every watch is indexed by session. ACL layer — evaluates the per-znode ACL list against the connection-resolved principal on every single request (§7 I7); never caches. Hierarchical namespace + watch subsystem — the in-memory state machine Raft replicates; a radix-indexed tree of znodes plus the one-shot watch registry, both opaque to Raft (§7 I3, I4). Raft replication — the sole path to linearizable writes; commit-then-apply ordering (§7 I9) is the cornerstone invariant; reads optionally bypass it for throughput. Storage layer — WAL plus periodic snapshot give crash recovery; every record is CRC-checked (§7 I10) because fsync alone does not guarantee bit-level integrity (Pillai et al. 2014). 6. Design Principles

  1. Linearizable writes are the contract. Every mutating operation (create, delete, set_data, set_acl) goes through Raft and is applied in commit order. Tradeoff: every write pays at least one round-trip to a majority. Operational implication: write latency has a floor equal to the slowest-of-majority RTT. Violation: two concurrent writers observe different orderings — the conformance suite's linearizability checker (§27) catches this before it reaches production.
  2. Sequential-consistency reads with explicit sync() for linearizability. A follower-local get_data is sequentially consistent (Lamport 1979) but may be stale; sync() promotes it. Tradeoff: default reads are fast but can return stale data. Operational implication: any client logic that needs freshness must call sync() explicitly — a documented, not implicit, cost. Violation: omitting sync() before a leader-only write check reintroduces split-brain (§6 P12).
  3. Sessions are the truth-source for liveness, not TCP connections. A session is a server-side lease independent of any one TCP socket. Tradeoff: a client can appear "gone" for up to the full session timeout before ephemerals are released. Operational implication: short timeouts release resources faster but risk false expiry under transient GC pauses. Violation: treating disconnect as instant failure causes premature ephemeral deletion and false leader-election churn.
  4. Ephemeral nodes tie state to sessions. An ephemeral znode's ephemeral_owner field binds it to exactly one session; ExpireSession atomically removes every znode that session owned. Tradeoff: no independent per-znode TTL — lifetime is entirely session-derived. Operational implication: there is no garbage collector to tune; the deletion is part of the linearizable log. Violation: a non-atomic cleanup leaves dangling protected-resource ownership no replay can reconstruct (§7 I2).
  5. Fencing tokens are non-negotiable. Every successful lock acquire returns a monotonic 64-bit fencing token; the protected resource MUST check it. Tradeoff: requires the resource owner to add one comparison — a small but mandatory integration cost. Operational implication: a RawLock API without a token is never shipped. Violation: skipping the check reproduces the exact Kleppmann 2016 GC-pause outage (§8.4, §19).
  6. The hierarchical namespace is not a filesystem. Znodes carry whole-value data (≤ 1 MiB, ADR-06) and metadata; no streaming, append, or offset access. Tradeoff: large or growing payloads must be chunked by the application. Operational implication: get_data/set_data are O(payload size), never O(1) partial updates. Violation: an application that treats a znode as a log or a stream will hit ZnodeTooLarge and lose data if it doesn't chunk (§7 I11).
  7. Watches are one-shot. A watch fires exactly once, then must be re-armed. Tradeoff: clients must implement fire-and-refetch loops correctly (§15.6 pitfall). Operational implication: server-side watch memory is bounded by design, not by luck. Violation: a naive while true: watch; wait loop has a race window that silently drops updates.
  8. ACLs are per-znode, evaluated on every operation, never inherited. Tradeoff: no POSIX-style inheritance convenience; every znode's ACL is explicit. Operational implication: set_acl takes effect immediately with no cache-invalidation lag. Violation: client-side ACL caching produces stale grants after set_acl commits (§7 I7).
  9. Reconfiguration is part of the protocol, not bolted on. Adding or removing a replica goes through the same Raft log using joint consensus (Ongaro thesis, section 6). Tradeoff: reconfiguration is slower than a naive single-step add. Operational implication: there is no "manual" config change that bypasses Raft. Violation: the single-server-addition shortcut has a known partition-induced disagreement bug (Howard et al. 2015) — this design forbids it (§24 FM-3).
  10. Storage durability is snapshot + WAL, with per-record CRC32C. Tradeoff: every WAL append pays a CRC computation and an fsync. Operational implication: corrupted records are detected and the WAL truncated, never silently skipped. Violation: skipping the CRC check lets a single bit-flip propagate into a state-machine divergence no later Raft check can catch (§7 I10).
  11. The 1 MiB max-znode-size cap is load-bearing, enforced three times. Tradeoff: legitimately large payloads must be split by the application, adding client-side complexity. Operational implication: the cap is checked at the API boundary, the Raft-proposal boundary, and the snapshot-chunk boundary — deliberately redundant. Violation: single-point enforcement lets a bug in one layer let an oversized entry reach Raft batching or snapshot streaming and OOM a replica (§7 I11).
  12. sync() is specifically a read-linearization barrier, not a general fence. Tradeoff: it cannot be used as a generic distributed barrier (that's the dedicated Barrier recipe, §20.3). Operational implication: documentation must distinguish the two explicitly. Violation: confusing them produces code that assumes ordering guarantees sync() does not provide.
  13. Conformance is the contract. The Jepsen-style harness (§27) gates the Sealed milestone: linearizability on writes, sequential consistency on follower reads, lock correctness under partition, watch-delivery guarantees under reconnect. Tradeoff: a 30-day soak and a 30-day fuzz canary add real calendar time before Sealed. Operational implication: a conformance regression is a hard merge block, not a warning. Violation: shipping without it is exactly how the ZooKeeper/etcd Jepsen reports (Kingsbury 2013+) found real production bugs.
  14. Deterministic serialization everywhere in the replicated state. Every serializable type uses BTreeMap, never HashMap. Tradeoff: marginally slower map operations than a hash table. Operational implication: any two replicas that applied the same log produce byte-identical snapshots — a cheap correctness check. Violation: one HashMap in a serializable type makes cross-replica snapshot comparison useless and can mask real divergence (§7 I8, §24 FM-6).

8. Domain Model, Protocol & Data Model

8.1 Znode data model

A znode carries a canonical path (/services/db/leader, leading /, no trailing /, no .., no double-/), a byte-vector data (≤ 1 MiB, P6), a Stat record, an ACL list, and a children index. Stat fields: czxid (creation zxid), mzxid (last-modification zxid — the fencing-token source, P5), pzxid (last modification of the children list), ctime/mtime (advisory wall-clock, not load-bearing), version (data version, bumped on set_data), cversion (children version, bumped on child add/remove), aversion (ACL version, bumped on set_acl), ephemeral_owner (Some(session_id) or None for persistent), data_length, num_children. Operations are whole-value: get_data returns the entire payload, set_data replaces it (P6) — there is no partial-write or append primitive.

8.3 Watch protocol

Four kinds, each armed as a side effect of a successful read: NodeCreated (via exists(path, watch) when absent), NodeDeleted (via get_data/exists(path, watch) when present), NodeDataChanged (via get_data(path, watch)), NodeChildrenChanged (via get_children(path, watch), fires only on direct child add/remove, not grandchild change). Delivery-ordering guarantee (I4): a watch fires on the client's outbound channel before any later response on that same session can reflect the post-event state. A watch is one-shot (I3, P7): registered, fired once, removed; the client must re-arm inside the same call that observes the new state to avoid the classic re-arm race (§15.6).

8.4 Fencing-token protocol — the Kleppmann scenario, worked example

  1. Client A acquires the lock on /locks/db-primary; fencing token = mzxid = 0x0000000100000005.
  2. Client A enters a GC pause exceeding the session timeout.
  3. The leader commits ExpireSession(A); A's ephemeral lock child is deleted atomically (I2).
  4. Client B acquires the lock; fencing token = mzxid = 0x0000000100000007 (strictly greater, I5).
  5. Client A's GC pause ends; unaware its session expired, A writes to the protected resource presenting token 0x...05.
  6. The resource compares 0x...05 against its stored high-watermark 0x...07, rejects the write.

The point: coord cannot prevent step 5 — A has no way to know locally that its session expired. The resource-side check in step 6 is the only closure (P5); a Lock API that returns no token cannot close this hole, which is why one is never shipped (§19.2).

8.5 Wire protocol framing

Request  frame:  | 4B length (LE) | 1B opcode | payload (bincode) |
Response frame:  | 4B length (LE) | 1B status | payload (bincode) |
Reconnect frame:  session_id(8B) | password(16B) | last_seen_zxid(8B)
                  | watch_count(2B) | watches[]: (path_len(2B), path,
                  last_seen_zxid(8B), kind_mask(1B))

Opcodes: 0x01 Create, 0x02 Delete, 0x03 SetData, 0x04 GetData, 0x05 GetChildren, 0x06 Exists, 0x07 SetAcl, 0x08 Sync, 0x09 Heartbeat, 0x0A Connect, 0x0B Reconnect. Status codes mirror the coord-core::error::Error enum (§11.7): 0x00 Ok, 0x01 NoNode, 0x02 NodeExists, 0x03 BadVersion, 0x04 NotEmpty, 0x05 NoAuth, 0x06 SessionExpired, 0x07 ZnodeTooLarge, 0x08 NotLeader, 0x09 LimitExceeded.

8.6 WAL and snapshot record layout

WAL record:      | 4B length (LE) | 4B CRC32C(payload) | bincode(LogEntry) |
LogEntry:        term(8B) | index(8B) | Mutation (§11.6)

Snapshot file:    | 16B magic "COORD-SNAP-V1\0\0\0" | 8B snapshot_index
                  | 8B snapshot_term | 8B namespace_len
                  | namespace bytes, chunked 1 MiB each, per-chunk CRC32C
                  | 8B sessions_len | session-set bytes, chunked, per-chunk CRC32C
                  | 4B file-level CRC32C of all preceding bytes

LogEntry carries the Mutation enum (§11.6) that the state machine applies deterministically (I8). Chunked per-record and per-chunk CRC32C let recovery skip and log a single corrupted unit instead of discarding the whole file.

8.7 Malformed-input example

A client sends a Create request whose declared 4B length field is 40 bytes but only 12 bytes follow before the connection closes. coord-net::frame reads the length prefix, attempts to read 40 bytes, hits EOF at byte 12, and returns FrameError::Truncated without touching the namespace or Raft — the connection is dropped, no Mutation is proposed, and the fuzz target wire_decode (§27) exercises exactly this class continuously. A second malformed case: a Create payload that bincode-decodes structurally but names a path containing .. — Path::parse (§11.2) rejects it at construction with Error::InvalidPath before it ever reaches Namespace::create, so no zxid is allocated for a request that was never going to succeed (§13.4 pitfall).

8.8 Failure-path example

A client issues set_data("/config/x", ...) to the current leader; the leader appends the entry, begins replicating, then crashes before a majority acknowledges. The client's request times out; its SDK (§18) retries the identical request_id against the new leader (elected per §16.5). Two sub-cases: (a) the crashed leader's entry never reached a majority — it is truncated from the log during the new leader's term, the retry proposes fresh, and the write lands exactly once; (b) the crashed leader's entry did reach a majority before the crash — it is already committed, the new leader has it in its log, and the retry is recognized as a duplicate via the pending_requests de-duplication map (§16.3) and returns the original response without re-applying. Both sub-cases preserve I1 and I9; neither double-applies nor silently drops the write.

Ownership: Namespace owns every Znode. Mutation: only via Mutation::apply (§11.6), never directly. Persistence: serialized into snapshots (§8.6) via BTreeMap-only fields (I8). Concurrency: single-writer (the apply loop, §16.2); readers see a consistent point-in-time view guarded by the state machine's single-threaded apply discipline.

12. Phase 0 — Repository Skeleton & Correctness Kernel

12.1 Objectives

Stand up the workspace, governance files, and CI so every later phase lands cleanly; implement the smallest possible correctness kernel — a single-node, in-memory Namespace (P6, no Raft, no sessions, no watches, no ACL) reachable over the bespoke wire protocol — and prove it round-trips data. This phase introduces no consensus and no durability; it exists purely to make Phases 1–10 land on solid scaffolding.

12.2 Detailed Implementation Steps

Land the full tree from §10 in one commit. Populate Cargo.toml as a workspace with all eight crates (coord-core, coord-raft, coord-storage, coord-net, coord-sdk, coord-cli, coord-fuzz, coord-jepsen), each an empty-but-compiling crate except coord-core and coord-net, which get real code. Implement Path::parse (§11.2, ADR-11) enforcing canonical-path rules at construction, not at use time — this is the first place a future regression would silently reappear if skipped. Implement Namespace::{new, create, delete, set_data, get_data, get_children, exists} (§11.4) against a BTreeMap<String, Znode> with no ephemeral/sequential/watch/ACL logic yet — those are Phases 1–3, 9. Implement coord-net::frame (§8.5) and a single-connection-at-a-time coord-net::server loop wired to four opcodes (Create, GetData, SetData, opcode Delete). Land Makefile targets bootstrap, build, test, lint, conformance, jepsen, tla, fuzz, soak. Land deny.toml with the ADR-18 licence allowlist.

12.3 Deliverable

A cloned repo where make bootstrap && make build && make test all exit 0, plus tests/hello_znode.rs: connect over the wire protocol, create("/hello", b"world"), get_data("/hello"), assert the bytes round-trip exactly.

12.4 Acceptance Criteria

make test passes with ≥ 1 passing test (hello_znode); cargo clippy --workspace -- -D warnings exits 0; cargo fmt --check exits 0; repository tree matches §10 exactly (verified by scripts/bootstrap.sh --verify-tree); ADR-01, ADR-02, ADR-11, ADR-18 files exist under docs/adr/.

12.5 Conformance Fixtures

conformance/corpora/zk_protocol/create_get_roundtrip.json — create then get, expect byte-identical payload. conformance/corpora/zk_protocol/malformed_length_prefix.json — truncated frame (§8.7), expect FrameError::Truncated and no state mutation. conformance/corpora/zk_protocol/invalid_path_dotdot.json — path containing .., expect Error::InvalidPath at parse time, zero zxid allocated.

12.6 Pitfalls

Skipping canonical-path validation at Path::parse and instead validating "wherever it's convenient" reintroduces the exact bug class ADR-11 exists to prevent — every later phase assumes an already-valid Path. Building the Phase-0 API surface narrower than the eventual Phase-4 surface (e.g., omitting expected_version parameters "because there's no concurrency yet") forces an API break exactly when Raft lands; the signatures in §11.4 are final from day one. Treating coord-net::server's single-connection assumption as permanent instead of a deliberate Phase-0 simplification risks baking single-connection assumptions into the wire codec.

12.7 Performance Concerns

None load-bearing yet — Phase 0 has no throughput target. The one forward-looking concern: Namespace's BTreeMap<String, Znode> keyed by full canonical path (not path components, ADR-11) is chosen now because switching key schemes later requires a storage-format migration (§26); prove the O(k log n) get_children prefix-scan works before Phase 1 adds volume.

12.8 Edge Cases

Empty path (""), root-only operations (create("/", ...) must fail — root always exists), zero-length data payload (must succeed, distinct from NoNode), duplicate create on an existing path (NodeExists), get_data on a nonexistent path (NoNode), a path exactly at the 64-component hard cap (§4) and one component past it.

12.9 Failure Analysis

At this phase the only "failure" is a process crash — there is no durability yet, so a crash loses all state by design (Phase 5 fixes this). Blast radius: total, but bounded to a single dev/test process; no operator-facing recovery procedure exists until Phase 5. This is documented explicitly in BUILD_PLAN.md so nobody mistakes Phase-0 output for anything but scaffolding.

12.10 Operational Notes

No metrics or tracing yet beyond tracing::info! on connection accept/close — full observability lands in Phase 4+ (§25). make bootstrap is idempotent and safe to re-run. No rollback/migration concerns exist yet; the wire protocol's opcode table (§8.5) is versioned from this phase forward so later additions are additive, not breaking.

13. Phase 1 — Hierarchical Namespace

13.1 Objectives

Complete the namespace's operation semantics (P6): version-checked mutation, sequential-node numbering, and the invariant "every non-root znode has an existing parent" — all still single-node, still no Raft, still no watches/sessions/ACL. This phase is where the O(log n) traversal claim (§4) becomes real and measured.

13.2 Detailed Implementation Steps

Extend Namespace::create (§11.4, ADR-11) to fail on missing parent (NoNode), existing path (NodeExists), or oversized data (ZnodeTooLarge, I11); on success allocate next_zxid, set czxid = mzxid = pzxid = zxid, insert, and bump the parent's cversion/pzxid. Extend delete to check expected_version (BadVersion on mismatch) and refuse non-empty znodes (NotEmpty) — no recursive delete at this layer (P6; recursive delete is an SDK-level composition, §18). Extend set_data with the same version-check discipline. Implement sequential-node naming: a 10-digit zero-padded suffix equal to the parent's cversion + 1 at creation time (this becomes Raft-commit-ordered once Phase 4 lands, P1). Write a differential test harness comparing every operation against a HashMap<String, Vec<u8>> reference oracle.

13.3 Deliverable

Namespace passes the differential oracle test across 100K randomized operation sequences; benchmarks/runner reports p50/p99 for get_data and create at 10K resident znodes.

13.4 Acceptance Criteria

10K-znode benchmark: get_data p99 ≤ 10 µs, create p99 ≤ 50 µs, single host (fixture benchmarks/results/phase1-namespace.json). Property test namespace_invariant_parent_exists runs ≥ 100,000 random create/delete/set_data sequences with zero invariant violations. Differential oracle test: zero divergences across 100K sequences.

13.5 Conformance Fixtures

conformance/corpora/zk_protocol/sequential_naming.json — two concurrent sequential creates under one parent, expect strictly increasing suffixes. conformance/corpora/zk_protocol/version_mismatch.json — set_data with a stale expected_version, expect BadVersion and zero state change. conformance/corpora/zk_protocol/delete_nonempty.json — delete a znode with children, expect NotEmpty.

13.6 Pitfalls

Recursive delete is intentionally absent from Namespace (P6) — ZooKeeper has the same restriction; exposing it here would make a single Raft entry non-atomic at the wrong granularity (the SDK composes it as a top-down or bottom-up traversal, §18). The radix-trie key is the full path, never path components (ADR-11): a component-keyed trie makes get_children O(n) over the whole tree instead of O(k log n) prefix-scan. Do not allocate a Zxid for read operations — the zxid is the write linearization point (I9); a read must never advance it.

13.7 Performance Concerns

get_children's prefix-range scan over the path-keyed BTreeMap is the namespace's one non-trivial complexity claim; verify it stays O(k log n) as resident znode count grows past 10K by re-running the benchmark at 100K in Phase 5's snapshot-scale test. Sequential-node creation under high concurrency contends on the parent's cversion — Phase 4 batches this (§16.2, §22.2).

13.8 Edge Cases

Two sequential creates racing for the same next suffix (resolved by Raft commit order once Phase 4 lands — Phase 1's single-node test uses a mutex to simulate); delete racing a concurrent set_data on the same path (version check resolves it); a create whose parent was deleted in the same batch (must fail NoNode, never silently succeed); maximum path depth (64, §4) exactly at and one past the boundary.

13.9 Failure Analysis

A namespace invariant violation (e.g., an orphaned non-root znode) is caught by the differential oracle and the property test before merge; in production this would surface as I2/I8-adjacent snapshot divergence (§24 FM-6) — Phase 1 has no replication yet, so the only detection is pre-merge testing.

13.10 Operational Notes

benchmarks/results/phase1-namespace.json is committed and diffed on every PR touching namespace.rs (regression gate, §29). No metrics/tracing beyond Phase 0's connection-level logging; per-operation tracing spans are added in Phase 4 alongside Raft (§16.10).

14. Phase 2 — Sessions & Ephemeral Znodes

14.1 Objectives

Implement the session lease protocol (P3), the four-state machine (§8.2), and ephemeral-znode lifecycle bound to session expiry (P4, I2) — still single-node (Raft integration is Phase 4; this phase simulates commit via a local mutex to keep the state-machine logic testable in isolation).

14.2 Detailed Implementation Steps

Implement Session/SessionState (§11.5) and the NewSession/HeartbeatSession/ExpireSession Mutation variants (§11.6). Wire the Connect opcode (§8.5): client sends proposed_timeout_ms and last_seen_zxid; server negotiates a timeout in [5s, 120s] (ADR-05) and returns session_id + a 16-byte password. Implement the heartbeat cadence: client sends Heartbeat at timeout/3; server transitions Connected → Jeopardy after missing timeout/3 * 2, and would propose ExpireSession after the full timeout (P3, I6). Implement the Raft-propagated-clock technique ahead of schedule (§8.2, ADR-05 note): every applied entry carries a proposed_at timestamp; session expiry is evaluated relative to max(local_clock, proposed_at), not wall time, so Phase 4's real multi-replica clock story slots in without a rewrite. Implement atomic ephemeral cleanup: ExpireSession(id) walks Session.ephemeral_znodes and removes every one in the same apply() call (I2, P4) — never a background sweep (P4 violation class, §24 FM-2).

14.3 Deliverable

A running single-node server where a client connects, creates an ephemeral znode, disconnects, and — after timeout elapses in the simulated-commit harness — the ephemeral znode is gone and the session reports Expired.

14.4 Acceptance Criteria

Integration test session_expiry_removes_ephemeral: connect, create ephemeral /x, force-close the socket, assert /x still exists at t = timeout/2, assert /x is gone and session state is Expired at t = timeout + 1s. TLA+ check tla/Session.tla passes with zero invariant violations across ≥ 10,000 explored states. Property test: 10,000 random heartbeat/disconnect/reconnect schedules preserve I2 and I6.

14.5 Conformance Fixtures

conformance/corpora/session_expiry/ephemeral_atomic_delete.json — session expiry with 50 owned ephemerals, expect all 50 gone in the same applied entry. conformance/corpora/session_expiry/jeopardy_recovery.json — heartbeat arrives during Jeopardy, expect transition back to Connected, no ephemeral loss. conformance/corpora/session_expiry/stale_reconnect.json — reconnect with last_seen_zxid greater than the server's committed zxid, expect rejection (the client knows more than a stale replica would).

14.6 Pitfalls

Reusing a SessionId after expiration lets a delayed packet from the dead session authenticate against a fresh one — the high 32 bits MUST carry a per-leader nonce (§11.1). A heartbeat arriving at a different owner_replica than the session's current home means the client is reconnecting, not just heartbeating — this is a ReownSession case, not a protocol error, and Phase 4 (§16) is where cross-replica reconnection becomes real. Treating the wall clock, not the Raft-propagated clock, as the expiry source lets a fast leader expire sessions faster than followers can apply the log (§8.2).

14.7 Performance Concerns

Session-registry lookups are O(1) (hash-indexed by SessionId in the running implementation, distinct from the BTreeMap-only rule which applies to serializable state — §11.5 note). The heartbeat cadence (timeout/3) sets a floor on server-side wakeup frequency: at 10,000 sessions and a 30s timeout, that's ~333 wakeups/sec minimum, which must not become a scheduler bottleneck (validated in Phase 10, §22).

14.8 Edge Cases

Session timeout negotiated outside [5s, 120s] (clamped, not rejected — §4). Two heartbeats racing at the exact timeout/3*2 boundary. A session that reconnects one tick before Expired fires. A client that never sends Connect and instead sends Heartbeat cold (rejected, Error::NoAuth equivalent — no session exists yet).

14.9 Failure Analysis

A non-atomic ephemeral cleanup bug (violating I2) manifests as a "ghost lock" — a resource believing itself protected by a session that no longer exists. Detection: the session_expiry conformance bucket and the TLA+ model both assert this cannot happen; in production, ephemeral_delete_count telemetry diverging from expected counts is the signal (§7 I2 row). Recovery: none needed if the invariant holds; if violated, the fix is a code rollback plus a manual namespace audit against the WAL.

14.10 Operational Notes

New metrics: session_state{state} gauge (I6), ephemeral_delete_count counter (I2). New structured-log fields: session_id, state_transition. No rollback/migration concerns — session semantics are additive from here forward (§26).

15. Phase 3 — Watches

15.1 Objectives

Implement the one-shot watch subsystem (P7, I3) across all four kinds (§8.3), the delivery-ordering guarantee (I4), and the reconnect-synthesis hazard (§8.3) that is the single most common client-library bug class in this whole domain.

15.2 Detailed Implementation Steps

Implement Watch/WatchKind registration (§11.5) as a side effect of get_data, get_children, and exists when called with watch: true; index by (path, kind) for O(1) fan-out lookup on mutation. On every applied Mutation that touches a path, compute the matching watch kind(s) and fire: remove the Watch from the registry (I3) and enqueue a WatchEvent on the owning session's outbound channel — the same channel that carries ordinary responses, which is what makes I4's ordering guarantee free (§3, session layer paragraph). Implement the reconnect frame (§8.5): on Reconnect, the server receives (path, last_seen_zxid, kind_mask) per watch the client still cares about; for any path whose current mzxid > last_seen_zxid, synthesize and fire the appropriate WatchEvent immediately, before resuming normal traffic. Enforce the per-session watch cap (ADR-16, I13) at registration time.

15.3 Deliverable

All four watch kinds (NodeCreated, NodeDeleted, NodeDataChanged, NodeChildrenChanged) covered by integration tests against conformance/corpora/watch_delivery/; tla/Watch.tla model-checked.

15.4 Acceptance Criteria

tla/Watch.tla passes with zero violations across ≥ 10,000 explored states, checking: every committed mutation produces exactly the correct watch firings; no registration fires twice; the reconnect-synthesis set is identical to what the client would have received had it stayed connected. Benchmark benchmarks/results/phase3-watch.json: 1,000,000 registered watches across 10,000 sessions sustain ≥ 10,000 fires/sec (M6-adjacent; the full M6 latency target is validated in Phase 10, §22).

15.5 Conformance Fixtures

conformance/corpora/watch_delivery/one_shot.json — register, fire once, assert removed from registry. conformance/corpora/watch_delivery/delivery_order.json — client A's set_data must not be observably preceded, on client B's channel, by a later same-path response arriving before B's watch fires. conformance/corpora/watch_delivery/reconnect_synthetic.json — client disconnects, three mutations happen on watched paths, client reconnects with pre-disconnect last_seen_zxid, expect exactly three synthesized events, in commit order.

15.6 Pitfalls

The naive client loop while true: get(path, watch=true); wait_for_event has a race: between a watch firing and the next get, a second mutation can occur and be silently missed. The correct pattern (documented in the SDK, §18) is fire-and-refetch in one call, comparing the returned Stat.version against the previously observed value to detect a missed intermediate mutation. Cross-session watch leakage (session A's watch delivered to session B) is a security bug, not a performance one — the registry's (session, path, kind) keying must be enforced, and conformance/corpora/watch_delivery includes an isolation check. Watches on / (root) are operationally common (config-watcher recipes, §20.2) but a 1,000-key root produces a 1,000-fold thundering herd on every top-level change — document the cost, do not silently optimize it away here (the predecessor-watch pattern, §19, is the domain-specific fix for the lock recipe only).

15.7 Performance Concerns

Watch fan-out on a hot path (e.g., every session watching /config) is O(watchers) per mutation — bounded by the per-session cap (ADR-16) times the number of sessions, not unbounded. The reconnect-synthesis scan is O(watches-in-reconnect-frame), paid once per reconnect, not per mutation — keep it that way; do not make every mutation scan every session's watch list.

15.8 Edge Cases

A watch registered then immediately invalidated by a concurrent delete of the watched path's parent (must still fire the correct kind, not silently drop). A reconnect frame naming a path that no longer exists (synthesize NodeDeleted if it existed at last_seen_zxid). A session hitting the watch cap mid-batch (the batch's remaining registrations fail LimitExceeded, already-registered ones stand). Two watches on the same (session, path, kind) tuple registered twice (idempotent — second registration is a no-op, not an error).

15.9 Failure Analysis

A missed watch (I4 violation) is invisible to the server — the bug lives entirely in "did the client's channel actually deliver it before the client's next read." Detection is client-side: the conformance suite's delivery_order bucket instruments both sides of the channel and asserts ordering; production detection relies on the client SDK's own assertions plus application-level staleness symptoms (e.g., a config watcher that silently stops updating — §24 FM-7).

15.10 Operational Notes

New metrics: watch_fire_total, watch_registered_total, per-session watch_count gauge (I13). New structured-log fields: watch_kind, watch_path (hashed if paths carry sensitive data — an operator config knob). No migration concerns: watches are never persisted (ADR-12), so a rolling upgrade simply drops in-flight watches, which clients recover via reconnect-synthesis — a deliberate design property, not a gap.

16. Phase 4 — Raft Replication

16.1 Objectives

Implement coord-raft (Ongaro-Ousterhout 2014, section 5; ADR-03): leader election with pre-vote, log replication, commit-then-apply ordering (I9), and the majority-quorum split-brain guarantee (I12, P9). This phase turns the single-node kernel from Phases 0–3 into a real 3-/5-node cluster.

16.2 Detailed Implementation Steps

Implement RaftNode<S: StateMachine> (§11.8) with Role::{Follower, Candidate, Leader}, current_term, voted_for, commit_index, last_applied, and leader-only next_index/match_index maps. Implement AppendEntries (leader→follower log replication + heartbeat) and RequestVote with the Raft paper's section 5.4 safety constraint (grant a vote only if the candidate's log is at least as up-to-date). Implement the pre-vote phase (Ongaro thesis, section 9.6, P9 corollary) from day one — a node that lost connectivity must not disrupt the cluster on reconnect by incrementing its term unilaterally. Implement advance_apply: applies committed-but-unapplied entries to the StateMachine strictly in log order (I9), routing each response back to the caller via a pending_requests map keyed by request_id (the SDK's idempotency mechanism, §18.3, P1 anchor). Implement joint-consensus membership changes (Ongaro thesis, section 6, P9) — no single-step "add one replica" shortcut (Howard et al. 2015 documents its bug class, §24 FM-3). Wire Mutation::Sync (§11.6, ADR-14, I14) as a real logged no-op that only advances the session's synced-through zxid on apply.

16.3 Deliverable

A 3-node cluster that elects a leader, replicates writes, and survives kill -9 on any single node; a 5-node cluster that survives two concurrent kills. Differential test against tikv/raft-rs (§5 Reference Implementations) over 10,000 random scenarios.

16.4 Acceptance Criteria

tla/Raft.tla (vendored Ongaro spec) passes with zero violations. Differential test: 10,000 random Raft scenarios produce identical state-machine sequences between coord-raft and tikv/raft-rs (fixture conformance/corpora/raft_replay/differential-10k.json). Leader election completes within the randomized [150ms, 300ms] timeout window in ≥ 99.9% of 1,000 forced-election trials. raft.partition conformance bucket: majority side commits within 2× election timeout of a partition; minority side commits zero entries for the partition's duration.

16.5 Conformance Fixtures

conformance/corpora/raft_replay/log_truncation.json — a follower with divergent uncommitted entries must truncate and catch up, never past its committed index. conformance/corpora/raft_replay/prevote_disruption.json — a disconnected-then-reconnected node without pre-vote disrupts the cluster; with pre-vote, it does not. conformance/corpora/raft_replay/joint_consensus_add.json — adding a replica mid-term via joint consensus, expect no window where two disjoint quorums can both commit.

16.6 Pitfalls

Log truncation during follower catch-up must never truncate past the committed index (the Raft paper's section 5.3 guarantees this is unnecessary, but the implementation defends anyway — cheap insurance, §24 FM-3). Snapshot install and running log replication are mutually exclusive on a single follower — never interleave; the leader sends InstallSnapshot only once a follower's needed log range has been compacted away (§17). Omitting pre-vote lets a partitioned-then-reconnected node's stale, incrementing term disrupt a healthy leader (Ongaro thesis, section 9.6) — implement it from day one, not as a hardening afterthought. The single-server-addition membership shortcut has a known partition-induced disagreement bug (Howard et al. 2015); joint consensus is the only implementation path.

16.7 Performance Concerns

The leader's AppendEntries fan-out to N−1 followers is the primary bandwidth cost (quantified in §33 #8); batching multiple client writes into one Raft entry (Phase 10, §22.2) amortizes the per-entry overhead. advance_apply's strict single-threaded ordering (I9) is a deliberate serialization point — do not parallelize apply across entries, ever; parallelizing reads (Phase 4's Sequential mode, §6 P2) is the correct lever instead.

16.8 Edge Cases

A candidate whose log is behind the cluster majority (denied votes, correctly). A term number wrapping near u64::MAX (out of practical scope at realistic election rates — documented, not defended against). A follower that receives AppendEntries for a term lower than its own (rejected, tells the stale leader to step down). A Mutation::Sync proposed by a node that loses leadership mid-flight (the client's retry against the new leader re-issues it; idempotent by nature since Sync has no side effect beyond the synced-through marker).

16.9 Failure Analysis

A pre-vote omission bug manifests as repeated, disruptive elections under flaky network conditions — detection via raft_term divergence telemetry across replicas (§7 I12 row) and the prevote_disruption conformance case. A joint-consensus violation (two disjoint quorums both committing) is the worst failure class this phase can produce; detection is the raft.partition bucket plus the TLA+ model; recovery requires manual log forensics and is documented in docs/runbooks/split-brain-postmortem.md (§24 FM-3).

16.10 Operational Notes

New metrics: raft_term (gauge, per replica), raft_commit_index, raft_apply_index (I9 row), raft_role (gauge: 0=Follower/1=Candidate/2=Leader). New tracing spans: one per AppendEntries round-trip, tagged with term and leader_id. Rolling upgrade: joint consensus (§16.2) is the only supported path for adding/removing replicas during a live upgrade; a direct membership-file edit is unsupported and unsafe (§24 FM-3).

17. Phase 5 — Snapshots and WAL

17.1 Objectives

Implement coord-storage (§11.9): the append-only WAL with per-record CRC32C (I10, ADR-08), the chunked snapshot format (§8.6), compaction (ADR-07), and crash recovery — the durability boundary the whole system depends on.

17.2 Detailed Implementation Steps

Implement Wal::append (fsync-after-write, per §8.6's record layout) and Wal::read_from/truncate_after. Implement SnapshotWriter/SnapshotReader per the chunked format (§8.6): namespace bytes and session-set bytes each split into 1 MiB chunks with independent CRC32C, plus a file-level CRC32C. Implement compaction (ADR-07): triggered at 100K applied entries or 1 GB WAL size, proposed as a CompactionMarker { snapshot_index } Raft entry so every replica independently snapshots at the same logical point — never a leader-computed snapshot streamed to followers (§13.3 rationale: byte-identical snapshots require independent, deterministic serialization, I8). Implement recovery: load the latest valid snapshot, set last_applied = commit_index = snapshot_index, replay the WAL from snapshot_index + 1 verifying each record's CRC32C, truncating and requesting InstallSnapshot/AppendEntries catch-up on the first mismatch (I10, never skip a bad record silently).

17.3 Deliverable

coord-storage recovers correctly across four induced scenarios: clean shutdown, mid-WAL-record crash, snapshot-during-write crash, single-bit WAL flip.

17.4 Acceptance Criteria

Property test: random write workload + random crash injection; post-recovery namespace state matches an oracle computed by re-applying the same operations to a fresh in-memory Namespace, across ≥ 10,000 trials, zero divergences. Benchmark: WAL append latency p99 ≤ 5 ms on NVMe SSD (fixture benchmarks/results/phase5-wal.json). Snapshot restore, 100K-znode namespace, ≤ 5 s (M8, fixture benchmarks/results/phase5-restore.json).

17.5 Conformance Fixtures

conformance/corpora/raft_replay/wal_crc_mismatch.json — a single flipped bit in one WAL record, expect truncation at that record and successful catch-up from a peer. conformance/corpora/raft_replay/power_loss_simulation.json — simulated fsync-lies (data reported durable but not flushed), expect the CRC layer catches the resulting corruption on the next read, per Pillai et al. 2014. conformance/corpora/raft_replay/snapshot_chunk_corruption.json — one corrupted 1 MiB chunk, expect that chunk logged and skipped, not a whole-file failure.

17.6 Pitfalls

Some consumer SSDs acknowledge fsync before the FTL has actually flushed — the power_loss_simulation fixture exercises this; production deployments must use fsync-and-write-barrier-respecting filesystems (XFS, ext4 data=ordered) (§5 Pillai et al. 2014). A snapshot taken mid-mutation is inconsistent — because the apply loop is single-threaded (I9), snapshotting is automatically point-in-time-consistent as long as it runs on that same thread (a stop-the-world snapshot, not copy-on-write — the PhaseDeferred("§1") consistent-prefix-streaming snapshot is a Phase-11+ optimization). Unbounded WAL growth from a missed compaction trigger is an operational failure mode documented explicitly (§24 FM-8) — one production ZooKeeper-class deployment is known to have run 18 months without compaction and accumulated a 600 GB WAL.

17.7 Performance Concerns

WAL append is on the write-latency critical path (bounds M1 via §33 #5's bandwidth derivation) — batching writes (Phase 10, §22.2) amortizes the per-record fsync cost. Snapshot restore time (M8) is dominated by deserialization CPU, not disk I/O, at realistic namespace sizes (§33 #7 shows ~90x I/O headroom) — profile deserialization first if M8 regresses.

17.8 Edge Cases

A crash exactly between snapshot-write-complete and WAL-truncation (recovery must prefer the snapshot and safely re-verify the still-present WAL prefix). A WAL file that is zero bytes (fresh cluster, not corruption — must not trigger the CRC-mismatch recovery path). A snapshot whose file-level CRC32C is valid but whose declared namespace_byte_length doesn't match the actual chunk count (reject the whole snapshot, fall back one snapshot generation if available, else full InstallSnapshot from a peer).

17.9 Failure Analysis

WAL corruption (I10 violation) is caught before it reaches the state machine — worst case is a replica falling behind and catching up via InstallSnapshot, never applying corrupted bytes. A compaction that never fires (operator misconfiguration) degrades recovery time linearly with WAL size until disk exhaustion — detection via a wal_size_bytes alert threshold (§25); recovery is a manual compaction trigger plus a runbook (docs/runbooks/snapshot-corruption.md).

17.10 Operational Notes

New metrics: wal_crc_mismatch_total (I10), wal_size_bytes, snapshot_age_seconds, snapshot_restore_duration_seconds. Backup/restore: an offline tools/snapshot-inspect binary dumps a snapshot's namespace tree for operator inspection without starting a full replica (§10). Rolling upgrade: the WAL/snapshot binary format carries a version field (§26); a replica refuses to load a snapshot from a newer, incompatible format version rather than silently misparsing it.

18. Phase 6 — Client SDK

18.1 Objectives

Implement coord-sdk::Client (§11.10): connection management across a replica set, transparent session reconnection with watch re-arming, and request-id-based idempotent retries (P1 anchor) — the layer every application actually touches.

18.2 Detailed Implementation Steps

Implement Client::connect (§11.10): handshake a session against any replica in the configured list, negotiate a timeout (ADR-05), store the 16-byte session password. Implement transparent reconnection: on TCP disconnect, round-robin or randomly pick a different replica, present (session_id, password, last_seen_zxid, armed_watches) via the Reconnect frame (§8.5); on SessionExpired, fire a terminal callback and require the application to construct a new Client (P3 — a session, once Expired, has no reconnection path). Implement request-id de-duplication (P1 anchor, §16.2's pending_requests map on the server side): every write carries a UUID-v4 request_id; retries reuse it; reads carry none (naturally idempotent). Implement the client-visible session mirror Connecting → Connected → Jeopardy → Expired (§8.2) with a Jeopardy callback hook applications use to pause lock-dependent writes (§19.5). Implement watch re-arming as part of reconnection (§15.2): the SDK tracks every currently-armed watch's (path, last_seen_zxid, kind) and includes them in every Reconnect frame.

18.3 Deliverable

The SDK passes a chaos-test suite: random TCP drops, random reconnect-to-a-different-replica, random leader failover mid-write, with the application observing consistent state throughout.

18.4 Acceptance Criteria

Integration test: 100 concurrent Clients each executing 1,000 (create, set_data, delete) cycles under injected random disconnects, zero errors, final state matches a reference computed without fault injection. Chaos suite (conformance/corpora/session_expiry + raft_replay combined workload) passes 1,000 consecutive runs with zero request lost or double-applied (fixture conformance/corpora/session_expiry/sdk_chaos_1k.json).

18.5 Conformance Fixtures

conformance/corpora/session_expiry/reconnect_watch_rearm.json — disconnect with 3 armed watches, 2 mutations occur, reconnect, expect exactly 2 synthesized events and both watches still armed for future fires. conformance/corpora/raft_replay/retry_dedup_across_leader_change.json — a write's leader crashes after replicating to a majority but before acking the client; the client retries against the new leader; expect the write applied exactly once, response identical both times.

18.6 Pitfalls

A naive SDK that retries create without a request_id will, on a network-failure-after-success, see NodeExists on retry and surface a confusing error to the application — request_id de-duplication (server-side pending_requests, §16.2) closes this. Watch callbacks invoked synchronously on the network-reader thread will stall the entire SDK if a callback blocks — document that callbacks must be non-blocking or must post to a queue. Multiple Client instances sharing one session_id is impossible by construction (sessions are server-allocated), but a misconfigured application that copies rather than Arc-shares a Client ends up with two threads racing one connection — document Client: Send but not safely Clone-shared.

18.7 Performance Concerns

Connection-pool sizing: one TCP connection per Client, pipelined (Phase 10, §22.1) rather than one-connection-per-request. Reconnect storms (many clients reconnecting simultaneously after a leader failover) must not overwhelm the new leader — the SDK backs off with jitter, bounded by the M5 5-second failover target.

18.8 Edge Cases

A reconnect racing the exact moment a watched path is deleted (the synthesis logic must still fire NodeDeleted, not silently drop it because "the path is gone now"). A request_id collision across two genuinely different requests (probability-zero at UUID-v4 scale, documented not defended). A client that reconnects to the same replica it was already connected to (must be a correct no-op path, not a special case that diverges from the cross-replica path).

18.9 Failure Analysis

An SDK that loses track of last_seen_zxid across a reconnect can present a stale value to the server's freshness check, causing spurious SessionExpired responses — detection via elevated SessionExpired-on-reconnect rate telemetry (§25); recovery is a client-library fix, not a server-side one. A blocking watch callback causing SDK-wide stalls surfaces as client-side request-latency spikes uncorrelated with server metrics — the differential signal operators use to distinguish "server is slow" from "a client callback is blocking."

18.10 Operational Notes

New client-side metrics (exposed via the SDK's own tracing integration): sdk_reconnect_total, sdk_request_retry_total, sdk_watch_rearm_total. No server-side operational change. Compatibility: the SDK's public surface (Client, ClientOptions, Lock, FencingToken, §11.10) is the API-stability boundary tracked in §26 — a breaking SDK change requires a major-version bump.

19. Phase 7 — Lock Recipe & Fencing Tokens

19.1 Objectives

Implement the canonical sequential-ephemeral lock recipe (Hunt et al., section 5.2, P5) with the predecessor-watch thundering-herd defeater, and prove the fencing-token contract (§8.4) end to end under a Jepsen-class linearizability check.

19.2 Detailed Implementation Steps

Implement Lock::acquire (§11.10): create a sequential ephemeral child /locks/<resource>/holder-<seq> (P4, P1 anchor — the create is itself a linearizable Raft write); list /locks/<resource>'s children; if the caller's child has the lowest sequence number, the lock is held — return FencingToken(stat.mzxid) (ADR-13, I5). Otherwise, find the immediate predecessor by sorted sequence number and register a NodeDeleted watch on it (P7, §15.2) — never watch the lock root directly (§15.6 pitfall, the thundering-herd class this recipe exists to defeat, quantified in §33 #10). On the predecessor's watch firing, re-list and re-check. Implement Lock::release: delete the caller's child; clear the cached token. Implement Lock::is_definitely_held(): returns false whenever the session is not Connected (P3 corollary) — a defense-in-depth signal, not the safety mechanism (the token check at the resource is, I5).

19.3 Deliverable

The lock recipe passes a Jepsen-class linearizability run: 5 clients contending for one lock under leader-kill faults, every grant strictly greater fencing token than the previous, no two clients ever simultaneously believe they hold the lock per the resource's reconstructed accept-log.

19.4 Acceptance Criteria

tla/Lock.tla passes with zero violations, checking mutual exclusion and bounded waiting. Jepsen bucket lock.linearizable (§27): 1,000 acquire/release cycles across 5 contending clients with injected leader kills, zero fencing-token monotonicity violations (I5). Benchmark: lock acquisition p99 ≤ 10 ms under 100 concurrent contenders (M3), ≤ 2 ms steady state at 1 contender (M4) — fixture benchmarks/results/phase7-lock.json.

19.5 Conformance Fixtures

conformance/corpora/recipe_lock/predecessor_watch_thundering_herd.json — 1,000 waiters, one release, expect exactly one watch fire (not 1,000) — the direct, numeric proof of §33 #10's derivation. conformance/corpora/recipe_lock/kleppmann_gc_pause.json — replays the §8.4 worked example verbatim: client A pauses past session expiry, client B acquires with a higher token, A's late write is rejected by a simulated resource checking the token. conformance/corpora/recipe_lock/no_double_grant.json — concurrent acquire attempts under partition, expect no two clients simultaneously "held" per the resource's global timeline.

19.6 Pitfalls

Treating the lock as held while the session is in Jeopardy is unsafe — it might be, it might not; is_definitely_held() returns false there and applications must consult it, though the fencing-token check at the resource (I5) is the actual safety net regardless (P5). No lock-service implementation can fix a resource that ignores fencing tokens — the SDK refuses to name the acquire method lock(); it is named acquire, returns a token, and forces the caller to confront it (P5, §8.4). Re-entrant acquire() calls on the same Lock handle return the cached token without creating a second child — document and test this explicitly to avoid orphaned lock children accumulating under /locks/<resource>.

19.7 Performance Concerns

The predecessor-watch pattern turns an O(N) thundering herd (watching the lock root) into an O(1) notification per release (§33 #10) — this is the recipe's entire performance argument and must never regress to root-watching in a future refactor. Lock-acquire latency under contention (M3) is bounded by the chain of sequential watch-fire round-trips a waiter passes through before reaching the front — worst case is O(queue depth) round-trips, though in practice each waiter only watches its immediate predecessor, so the notification cost stays O(1) per release even though a deeply queued waiter's total wait time is proportional to its position.

19.8 Edge Cases

Two clients racing to create sequential children at the exact same Raft-commit instant (Raft's total order resolves this deterministically — whichever entry commits first gets the lower sequence number, P1). A predecessor that is deleted between the listing and the watch-registration call (the exists(predecessor, watch) call itself detects this — if the predecessor is already gone, the caller re-lists immediately rather than waiting on a watch that will never fire). A lock-holder that crashes without calling release() (the ephemeral child is cleaned up via session expiry, I2 — no explicit release is required for correctness, only for prompt handoff).

19.9 Failure Analysis

A fencing-token monotonicity violation (I5) is the single worst possible outcome of this recipe and is a hard Sealed-gate blocker (§7 I5 row) — detection is the Jepsen lock.linearizable bucket; there is no "recovery" from a violation in production beyond a full incident review, because it means a resource may have accepted two conflicting writes. A thundering-herd regression (predecessor pattern silently reverted to root-watching) manifests as a lock-release latency spike proportional to waiter count — detection via watch_fire_total spiking on /locks/<resource> itself rather than on individual predecessor paths.

19.10 Operational Notes

New metrics: fencing_token_high_watermark (I5), lock_acquire_duration_seconds histogram, lock_queue_depth gauge per resource. Documentation requirement: every SDK doc page for the lock recipe cites the exact Hunt et al., section 5.2, / Kleppmann 2016 section it implements (§5 traceability). No migration concerns — the lock recipe is a pure client-side composition of already-stable primitives (create/get_children/exists/delete), so it can evolve independently of the wire protocol version.

20. Phase 8 — Leader Election, Group Membership, Distributed Barrier

20.1 Objectives

Compose the three remaining standard recipes from the same primitives as the lock (§19): leader election (P5 corollary — "the lock holder is the leader"), group membership, and a distributed barrier — proving that recipes are pure client-side compositions, not new server primitives (§27 Final Notes analogue, §1).

20.2 Detailed Implementation Steps

Implement leader election as the lock recipe applied to /election/<group>/leader-<seq> (P5's fencing-token discipline applies unchanged), plus a LeaderCallbacks trait (on_become_leader(token), on_lose_leadership(), §11.10 pattern) — on_lose_leadership fires defensively whenever the session enters Jeopardy (I6, §14.4), not only on confirmed loss, so callers stop issuing leader-only writes before they can be proven wrong. Implement group membership: members create an ephemeral child /groups/<name>/member-<id> carrying metadata as data; membership is get_children("/groups/<name>"); change notifications use a NodeChildrenChanged watch on the parent — document explicitly that a member's data change does not fire the parent's watch, only add/remove does (§15.1 kind semantics). Implement the distributed barrier: each participant creates an ephemeral /barrier/<name>/p-<seq>, calls get_children(watch=true), proceeds once the count reaches N, and the completion-barrier dual (create on completion, wait for count = N, then all proceed).

20.3 Deliverable

All three recipes have integration tests against a 3-node Docker-Compose cluster; the leader-election recipe passes a 7-candidate chaos test with random leader kills.

20.4 Acceptance Criteria

Leader-election chaos test: 7 candidates, leader killed repeatedly, next election completes in ≤ 5 s each time (M5, fixture benchmarks/results/phase8-election.json). tla/Barrier.tla passes with zero violations for N ∈ {2, 5, 10}. Group-membership integration test: 50 members join/leave in randomized order, get_children count matches expected membership at every watched checkpoint.

20.5 Conformance Fixtures

conformance/corpora/recipe_lock/leader_failover_chaos.json (shared corpus with §19, tagged for the election use-case) — kill the current leader-election holder repeatedly, expect each subsequent election within the M5 bound. conformance/corpora/watch_delivery/membership_child_vs_data_change.json — a member's data-only update, expect the parent's NodeChildrenChanged watch does NOT fire; a member add/remove, expect it does. conformance/corpora/watch_delivery/barrier_all_arrive.json — N participants arriving in random order, expect every participant's proceed-gate to fire only once the Nth arrives.

20.6 Pitfalls

A leader that believes it's still leader after a partition heals asymmetrically must call sync() before any leader-only write (P2, P12) — omitting this reintroduces exactly the split-brain scenario the whole Raft layer exists to prevent. Group-membership watchers can go stale if a NodeChildrenChanged fire is missed due to a network drop landing on the wrong replica — the SDK's reconnect logic (§18.2) re-fires synthetic events, but application code must not assume "no watch fired" means "no change happened" across a reconnect boundary. A barrier participant that crashes before reaching the barrier has its ephemeral child auto-removed on session expiry (I2) — the remaining participants will see the count drop, which the barrier recipe surfaces but does not resolve; "what to do about a lost participant" is an application-level decision.

20.7 Performance Concerns

Leader-election failover time (M5) is bounded by Raft election timeout ([150ms, 300ms], §16) plus one lock-acquire round-trip (§19.7) — the two costs are additive, not overlapping, because the new leader must first be elected before any client's acquire can even be proposed. Group-membership watches on a single parent scale linearly with member count for fan-out cost (§15.7) — a 10,000-member group watched by 10,000 separate clients is the worst case and is bounded only by the per-session watch cap (ADR-16) on the watcher side, not the member side.

20.8 Edge Cases

A leader-election candidate that never sees on_become_leader because it lost its predecessor-watch race and then crashed before re-listing (its ephemeral child vanishes on expiry, I2, and the next-in-line's watch fires normally — no stuck state). A barrier where N is larger than the number of participants that will ever arrive (defined as an application misconfiguration, not a service concern — the service has no timeout on barrier waits by design; a stuck barrier is the application's responsibility to bound, e.g., via Client::sync health checks). A group-membership metadata payload exceeding 1 MiB (rejected at creation with ZnodeTooLarge, I11, same as any znode).

20.9 Failure Analysis

A stuck leader election (no candidate ever reaches sequence-zero) indicates either a Raft-layer problem (no leader can be elected — this phase's failure is actually a Phase-4 failure surfacing here) or an application bug holding a lock-adjacent child open without releasing — detection via lock_queue_depth (§19.10) staying non-zero longer than the M5 bound. A membership watch storm (many members joining/leaving rapidly) is bounded by the per-session ephemeral cap (ADR-17) on the member side and the watch cap (ADR-16) on the watcher side; no additional containment is needed at this layer.

20.10 Operational Notes

New metrics: leader_election_duration_seconds histogram (M5), group_membership_count gauge per group, barrier_participants_current gauge per barrier. Runbook: docs/runbooks/leader-failover.md documents the exact operator steps to verify a failover completed within SLA and to manually force a leadership handoff for planned maintenance (via graceful release() rather than a kill).

21. Phase 9 — ACLs & Authentication

21.1 Objectives

Implement per-znode ACL evaluation (P8, I7) across the four ZooKeeper-compatible schemes (world, auth, digest, ip) and connection-level authentication (mTLS default, SASL optional, ADR-10).

21.2 Detailed Implementation Steps

Implement AclEntry/Perms (§11.6) and check_acl(acl, principal, required): iterate the target znode's ACL list, grant iff some entry's scheme matches the principal and its Perms include the required bit. Map operations to required permissions: create (parent) → CREATE; delete/target → DELETE; get_data/get_children/exists → READ; set_data → WRITE; set_acl → ADMIN. Implement scheme matching: world:anyone matches unconditionally; auth matches any authenticated principal; digest compares a SHA-256 digest of user:password (accept legacy SHA-1 for compatibility only); ip matches a CIDR block against the connection's source address. Implement connection-level principal resolution at handshake: mTLS (client cert SAN/CN), SASL DIGEST-MD5 (username), SASL GSSAPI/Kerberos (service/host@REALM) — the resolved principal attaches to every request on that connection; ACL evaluation runs fresh per request (I7), never cached client- or server-side.

21.3 Deliverable

ACL evaluation passes 1,000 scheme/permission/operation permutations; mTLS and SASL DIGEST-MD5 paths exercised end to end against a 3-node cluster.

21.4 Acceptance Criteria

conformance/corpora bucket acl.eval: 1,000/1,000 permutations grant/deny correctly (fixture conformance/corpora/watch_delivery/../acl_eval_matrix.json, conceptually its own corpus directory acl_matrix/). Fuzz target acl_scheme_decode runs 24 h with zero panics (§27). Default ACL on create with no explicit list is world:anyone:ALL, verified by a dedicated fixture matching ZooKeeper's own 15-year-old default.

21.5 Conformance Fixtures

conformance/corpora/acl_matrix/scheme_permutation_1000.json — the full 1,000-case (scheme × id × perms × op) matrix. conformance/corpora/acl_matrix/cidr_overlap.json — overlapping ip:10.0.0.0/8:READ and ip:10.0.1.0/24:WRITE on one znode, expect the union of grants (all matching entries evaluated, not most-specific-wins). conformance/corpora/acl_matrix/set_acl_immediate_effect.json — set_acl followed immediately by an operation that the new ACL should deny, expect denial with no caching lag.

21.6 Pitfalls

Client-side ACL result caching produces stale grants the instant a set_acl commits — the SDK does not cache, and the server evaluates per-request (I7); this must never regress for a "performance win." The auth scheme is a wide-open pass for any authenticated principal — operationally this means "any client that can complete a TLS handshake," which is fine only if the deployment trusts every such client; the deployment guide must say so explicitly, not leave it implicit. CIDR overlaps evaluate as a union of all matching entries, not "most specific wins" — some operators expect POSIX-style most-specific semantics and are surprised; document this loudly.

21.7 Performance Concerns

ACL evaluation is O(ACL-list-length) per request — in practice bounded (lists are typically 1–5 entries); no caching layer exists to amortize this because caching directly violates I7. mTLS handshake cost is paid once per connection, not per request — connection reuse (§18.7) is what keeps this off the request-latency critical path.

21.8 Edge Cases

An ACL list that is empty (denies everything except ADMIN-holders who can set_acl to fix it — never silently defaults to allow-all). A digest scheme entry with a malformed hash (rejected at set_acl time, not deferred to evaluation time). A principal presenting both an mTLS certificate and a SASL token on the same connection (mTLS wins; documented precedence, not an error). A CIDR entry with an invalid prefix length (rejected at set_acl time by the fuzz-hardened acl_scheme_decode path).

21.9 Failure Analysis

An ACL-evaluation bug that over-grants is a security incident, not merely a correctness bug — detection via the acl.eval conformance bucket pre-merge and via anomalous acl_deny_total drops in production (an unexpected drop to near-zero on a znode that should see regular denials is itself a signal). An under-grant bug (false denial) surfaces as application-visible NoAuth errors and is caught faster in practice because it breaks functionality immediately rather than silently.

21.10 Operational Notes

New metrics: acl_deny_total (I7), acl_eval_duration_seconds histogram, auth_scheme{scheme} counter (mTLS vs SASL usage). Security note cross-reference: §23 T2 (session hijacking) and T7 (Byzantine clients) both assume ACLs are correctly evaluated per this phase; a regression here weakens both mitigations simultaneously.

22. Phase 10 — Performance Hardening

22.1 Objectives

Meet every quantified target in §4/§29 (M1–M9) through pipelining, write-batching, and the read-mode fast path — the phase that turns a functionally-correct cluster into an operationally-viable one.

22.2 Detailed Implementation Steps

Implement request pipelining: a single client connection may have many requests in flight; the server processes them in submission order, bounded by the Raft proposal rate. Implement write-batching: Mutation::Batch(Vec<Mutation>) lets the leader coalesce proposals arriving within a tunable window (default 5 ms or 256 mutations, whichever first, ADR-07 adjacent) into one Raft entry, applied atomically on commit — the batch window trades latency for throughput and must be adaptive (shrink under low queue depth) to avoid penalizing low-volume workloads (§16.7). Implement the read-mode fast path: Sequential reads bypass Raft entirely, hitting the local state machine directly (P2); Linearizable reads call sync() first (ADR-14, I14). Implement the SDK-side "read-your-own-writes" guard: the client tracks the highest committed zxid it has observed and refuses a Sequential read from a replica whose last_applied is behind that watermark, retrying against a more caught-up replica instead.

22.3 Deliverable

A 5-node cluster sustaining ≥ 50,000 writes/sec (M1) and ≥ 200,000 reads/sec (M2) simultaneously under the conformance suite's mixed workload generator.

22.4 Acceptance Criteria

M1: ≥ 50,000 writes/sec, 1 KiB payload, 5-node cluster. M2: ≥ 200,000 reads/sec, follower-local. M3: lock acquire p99 ≤ 10 ms at 100 contenders. M5: leader failover ≤ 5 s end-to-end. All four gated in CI via benchmarks/results/phase10-full.json against the §29 targets table; a regression beyond 10% of any target fails the PR.

22.5 Conformance Fixtures

conformance/corpora/raft_replay/batch_window_adaptive.json — queue depth drops to zero mid-run, expect the batch window shrinks within one window-cycle, verified via commit-latency histogram shape. conformance/corpora/session_expiry/read_your_own_write.json — write then immediate Sequential read on a replica intentionally lagged, expect the SDK retries against a caught-up replica rather than returning stale data silently.

22.6 Pitfalls

A batch window fixed too long (e.g., 50 ms) quintuples write latency for low-volume workloads that don't need the throughput gain — the adaptive shrink-under-low-queue-depth behavior is mandatory, not an optimization. Sequential reads that ignore the read-your-own-writes guard produce a client that writes then immediately reads its own stale value from a lagging follower — the SDK must track and enforce the watermark itself; this is not a server-side fix. Pipelining across a reconnect must preserve response-sequence semantics: in-flight requests retry with their original request_ids and the new leader's pending_requests map de-duplicates (§18.2) — a client must observe the same response sequence it would have seen without the reconnect.

22.7 Performance Concerns

This entire phase is the performance-concerns phase; the specific levers are: batch window size (adaptive), pipeline depth (bounded by the per-connection in-flight limit), read-mode selection (Sequential default, Linearizable opt-in), and follower count (more followers increase AppendEntries fan-out bandwidth, §33 #8, without increasing write throughput — only read-scaling benefits from more replicas, and only up to the point observer replicas would help, PhaseDeferred("§1")).

22.8 Edge Cases

A workload with 100% linearizable reads (every read calls sync()) collapses toward write-path throughput limits — document this explicitly as an anti-pattern the SDK's docs warn against. A batch that straddles a leader-crash boundary (partially replicated) is handled by Phase 4's log-truncation/re-proposal logic (§16.6), not by anything new here. Pipeline depth exceeding the leader's pending_requests map capacity (bounded, configurable) causes backpressure — the client must handle NotLeader/backpressure signals gracefully rather than treating them as hard errors.

22.9 Failure Analysis

A throughput regression below M1/M2 is caught by the CI performance gate before merge (§29); in production, sustained throughput below target surfaces via the same metrics and pages on-call per the SLO in §25. A batch-window misconfiguration (stuck at a large fixed value) manifests as elevated p50 write latency with normal p99 — a distinctive signature distinguishing it from an actual overload (which elevates both).

22.10 Operational Notes

New metrics: raft_batch_size histogram, raft_batch_window_ms gauge (adaptive value), read_mode{mode} counter (Sequential vs Linearizable split), pipeline_depth gauge per connection. This is also the phase where the full §29 performance-regression CI gate goes live; every subsequent PR touching the hot path runs the benchmark suite automatically.

23. Threat Model

23.1 Trust boundaries

Four boundaries, matching §3's diagram: (1) Client boundary — clients are untrusted; may be malicious, buggy, or partitioned; ACLs (§21) and session-password randomness defend. (3) Network boundary — partitions, drops, reorderings, duplicates are all expected; Raft (§16) handles them. (4) Disk boundary — bit-rot is detected via per-record CRC32C (I10); whole-file loss is recovered from a healthy replica.

25. Operational Readiness

Metrics are Prometheus-style, scraped per replica: session (session_state{state}), watch (watch_fire_total, session_watch_count), Raft (raft_term, raft_commit_index, raft_apply_index, raft_role), storage (wal_crc_mismatch_total, wal_size_bytes, snapshot_age_seconds), lock (fencing_token_high_watermark, lock_acquire_duration_seconds), ACL (acl_deny_total). Tracing: one span per client request tagged with session_id, request_id, op; one span per AppendEntries round-trip tagged with term, leader_id (§16.10). Structured logging: JSON lines, one event per state transition (session, Raft role, watch fire), tracing-crate-backed, shipped to the deployment's log aggregator.

Dashboards: cluster-health (leader identity, term, commit-lag per replica), session-health (state distribution, expiry rate), lock-recipe-health (queue depth per resource, acquire-latency percentiles), storage-health (WAL size, snapshot age, CRC-mismatch rate). Alerting philosophy: page on any Sealed-gate-class invariant violation (I1, I5, I8, I9, I12) immediately; warn on approaching a §4 constraint (e.g., session count approaching the FD-derived ceiling, §33 #1); info-log everything else.

SLOs: 99.95% availability (§4), M5 leader-failover ≤ 5 s, M6 watch-delivery p99 ≤ 20 ms — each tied to a Performance Engineering target (§29) and gated in CI.

Incident response: named runbooks under docs/runbooks/ — leader-failover.md (verify SLA, force planned handoff), jepsen-failure-triage.md (reproduce a nightly Jepsen failure locally), split-brain-postmortem.md (FM-3 response), snapshot-corruption.md (FM-11/I10 response). Backup/restore: tools/snapshot-inspect dumps a snapshot for offline audit without starting a replica (§17.10); restore is "start a fresh replica, let InstallSnapshot populate it from a healthy peer" — there is no separate backup-file restore path, by design (the replica set is the backup).

Deployment topology: 3- or 5-replica StatefulSet (ops/k8s/statefulset.yaml), one replica per node/AZ where possible. Canary/rolling-upgrade: joint-consensus membership changes (§16.2, P9) are the only supported replica-replacement mechanism during a live upgrade; roll one replica at a time, verify raft_term stability before proceeding to the next. Rollback: a downgrade is supported only within the same WAL/snapshot format version (§26); cross-version rollback requires a snapshot taken before the upgrade. Migration: schema-evolution of Mutation variants is additive-only during a rolling upgrade window (§26) so mixed-version replicas can still agree on log contents.

Capacity planning: an operator sizing a new cluster starts from §33's derivations, not from guesswork — the FD-derived session ceiling (§33 #1), the WAL-bandwidth floor (§33 #5), and the leader-egress bandwidth requirement (§33 #8) are the three numbers that must be checked against the target hardware profile before a cluster is provisioned; a deployment that skips this step is the single most common root cause of a cluster that "works in staging, falls over in production." On-call escalation: a page on any Sealed-gate-class invariant violation (I1, I5, I8, I9, I12) escalates immediately to the on-call engineer with the corresponding runbook (docs/runbooks/split-brain-postmortem.md for I12, docs/runbooks/snapshot-corruption.md for I8/I10) linked directly from the alert; a warn-level alert on an approaching §4 constraint escalates only if it persists past one full session-timeout window (§4 ADR-05), avoiding alert fatigue from transient spikes.

26. Compatibility & Versioning

  • Wire protocol: the opcode table (§8.5) is versioned; new opcodes are additive, existing ones are not renumbered or repurposed — an opcode change is a major-version event (SemVer-style).
  • Storage format: the WAL/snapshot binary layout (§8.6) carries an explicit version field; a replica refuses to load an incompatible newer version rather than misparsing it (§17.10).
  • Schema evolution: Mutation (§11.6) variants are additive during any rolling-upgrade window; removing or reinterpreting a variant requires draining all replicas to the new version first.
  • API stability: the SDK surface (Client, Lock, FencingToken, §11.10) follows SemVer; a breaking change to any of these types is a major-version bump.
  • Deprecation policy: a deprecated opcode, Mutation variant, or SDK method is marked in CHANGELOG.md and kept functional for at least one minor-version cycle before removal.
  • Rolling-upgrade guarantees: mixed-version clusters are supported only across one minor version at a time (N and N+1, not N and N+2); joint consensus (§16.2, P9) is the sole mechanism for adding a differently-versioned replica.
  • Client-SDK compatibility window: an SDK at version N can talk to a server cluster at version N or N+1 but is not guaranteed against N+2 — the SDK's Connect handshake (§8.5) exchanges a protocol_version field and fails fast with a clear error rather than silently misbehaving against an out-of-window server.

29. Performance Engineering

Benchmarking methodology: benchmarks/runner (§10) drives fixed workload generators against a live cluster and records p50/p95/p99 into benchmarks/results/*.json, diffed on every PR touching a hot path (§22.10). 30. Scalability Analysis

What stays constant: per-request ACL-evaluation cost (O(ACL-list length), §21.7), watch-registration cost (O(1) via (path, kind) indexing, §15.7), fencing-token derivation cost (O(1), reuses mzxid, ADR-13). What grows: namespace size (O(n) memory, O(log n) per-operation traversal, §13.7), session count (O(n) memory, bounded by the FD budget derivation, §33 #1), watch count (O(n) memory per session up to the ADR-16 cap, §15.7), Raft replication bandwidth (O(followers), §33 #8). Named bottlenecks in order: (1) leader AppendEntries fan-out bandwidth at high follower count; (2) WAL fsync latency at high write rate (§33 #5); (3) per-session watch-fan-out at hot, widely-watched paths like /config or / (§15.6); (4) snapshot-restore deserialization CPU at very large namespaces (§33 #7). Horizontal scaling: read throughput scales by adding non-leader replicas up to the point observer replicas (PhaseDeferred("§1")) would be needed to avoid inflating the write quorum; write throughput does not scale horizontally at all — it is bounded by majority-commit latency, which worsens with more replicas, not improves (an odd asymmetry every operator sizing a cluster must internalize, MM6, §31). Sharding/partitioning: out of scope — a single namespace tree is the unit of consistency; splitting the namespace across multiple independent coord clusters (per top-level path prefix) is an application-level sharding strategy, not a service feature. Coordination overhead: every write pays one majority round-trip regardless of cluster size (3 or 5 nodes cost the same per-write latency, only the failure-tolerance differs). The practical ceiling: write throughput saturates when the WAL fsync rate or the AppendEntries fan-out bandwidth (whichever binds first, §33) is reached; the lever beyond it is write-batching (§22.2), which trades latency for throughput up to the batch window's own diminishing returns.

31. Mental Models & First Principles

  • MM1 — A session is a lease, not a connection. Insight: liveness is a server-granted lease independent of any one socket. Predicts: TCP flaps need not be catastrophic. Bug class without it: treating disconnect as instant failure, causing thundering reconnect storms and premature ephemeral loss. Resolving §14.
  • MM2 — A watch is an edge-triggered interrupt, not a level-triggered poll. Insight: it fires once, on the transition, then goes silent. Predicts: you must re-arm after every fire or you go blind to further changes. Bug class without it: the classic re-arm race where a fetch-after-fire misses an intervening mutation. Resolving §15.
  • MM3 — The log is the database; the state machine is a derived view. Insight: any replica can rebuild identical state from the log alone. Predicts: two replicas that applied the same log entries are byte-identical. Bug class without it: non-deterministic serialization (a stray HashMap) silently breaking replica agreement. Resolving §16, §8.
  • MM4 — A fencing token doesn't stop the pauper from writing; it stops the write from being believed. Insight: the lock service's responsibility ends at token issuance; the resource's begins there. Predicts: no coordination-service-side fix can ever close the Kleppmann gap alone. Bug class without it: shipping a Lock API that never exposes a token, silently reproducing the Redlock failure class. Resolving §19.
  • MM5 — Sequential consistency is free; linearizability is what you pay sync() for. Insight: the default read mode trades freshness for throughput deliberately. Predicts: read-your-own-write bugs on a lagging follower are expected, not anomalous, absent sync(). Bug class without it: assuming every read reflects the latest write. Resolving §16, §18.
  • MM6 — A quorum is a majority, not a supermajority, and that asymmetry is what makes one side of a partition survivable. Insight: a 3-node cluster tolerates exactly 1 failure, a 5-node exactly 2 — and more replicas make writes slower, not faster. Predicts: naively adding replicas "for more throughput" backfires on the write path. Bug class without it: sizing a cluster by guesswork instead of doing the majority arithmetic. Resolving §4, §30.
  • MM7 — Atomicity of ephemeral cleanup is a state-machine property, not a garbage-collector property. Insight: there is no async reaper thread, and there must never be one. Predicts: cleanup is instantaneous-and-total at the exact commit of ExpireSession, never partial. Bug class without it: a background sweep that races the state machine and leaves orphaned ephemerals. Resolving §14.
  • MM8 — CRC catches corruption; consensus catches disagreement — different failure classes need different defenses. Insight: fsync alone is not durability against bit-rot. Predicts: a successful fsync can still return corrupted bytes on read. Bug class without it: assuming disk-level acknowledgment implies data integrity. Resolving §17.
  • MM9 — More replicas make reads scale and writes slower, in the same breath. Insight: majority-commit latency grows with replica count even as read fan-out capacity grows with it too — the two curves point in opposite directions from the same knob. Predicts: "just add more nodes" is never a free throughput lever for the write path. Bug class without it: operators who size a cluster for read scaling and are then surprised by degraded write tail latency. Resolving §30, §33.

33. Back-of-Envelope Capacity Model

  1. Max sessions/replica = FD budget ÷ FDs-per-session = 65,536 ÷ 10 ≈ 6,500 sessions/replica (§4 FD-budget row).
  2. Cluster session capacity (5 replicas) = 6,500 × 5 ≈ 32,500 concurrent sessions, ignoring leader-only overhead.
  3. Worst-case watch memory/session = 10,000 watches × ~100 B/watch struct ≈ 1 MB/session; at 6,500 sessions/replica that's 6.5 GB/replica worst case — this is why the §4 CPU/memory ceiling (8 GiB RSS) assumes typical, not worst-case, watch load; an operator must monitor session_watch_count against this derived ceiling.
  4. Namespace memory at 100K znodes = 100,000 × (≈1 KiB avg data + ≈200 B Stat/ACL overhead) ≈ 120 MB — well within the 8 GiB budget, confirming most of the memory budget is watch/session state, not znode data.
  5. WAL write bandwidth at M1 = 50,000 writes/sec × (1,024 B payload + 8 B header) ≈ 51.6 MB/sec sustained — the minimum disk-throughput spec any deployment must exceed with headroom (an NVMe SSD's ≈2 GB/sec sequential write gives ≈40x headroom).
  6. Snapshot size at 100K znodes ≈ 100 MB namespace + ~10 MB session set ≈ 110 MB, chunked at 1 MiB ≈ 110 chunks.
  7. Snapshot-restore I/O floor for M8 = 110 MB ÷ 5 s = 22 MB/sec required — ~90x below typical NVMe sequential read (~2 GB/sec), so M8's real bottleneck is deserialization CPU, not I/O (§17.7).
  8. Leader replication egress at M1, 5-node cluster = 50,000 writes/sec × 1,032 B × 4 followers ≈ 206 MB/sec aggregate leader egress — decisively requires ≥ 1 Gbps NIC, 10 GbE recommended for headroom.
  9. FD-derived session ceiling vs. the stated §4 constraint: the FD-derived 6,500 sessions/replica (#1) is below the officially quantified "10,000 max concurrent connections" row in §4 — a documented discrepancy resolved operationally by raising the ulimit to 100,000 in docs/runbooks/ (§25), not by changing the derivation.
  10. Thundering-herd factor, predecessor-watch vs. naive root-watch = at N = 1,000 waiters and M4's 2 ms per-watch round trip: naive (watch the root) = 1,000 × 2 ms = 2,000 ms (2 s) of serialized notification per release; predecessor pattern = 1 × 2 ms = 2 ms per release — a 1,000x factor derived directly from the recipe choice (§19.7).
  11. Write-batching amortization at the M1 target = at 256 mutations/batch (§22.2 default) and 50,000 writes/sec, the leader proposes ≈ 50,000 ÷ 256 ≈ 195 Raft entries/sec, not 50,000 — the batch window converts a 50,000/sec fsync requirement into a ≈195/sec one, explaining why §33 #5's 51.6 MB/sec bandwidth figure is payload-bound, not fsync-call-count-bound.
  12. Total cluster storage footprint at steady state = WAL retained since last compaction (≤ 1 GB, ADR-07) + latest snapshot (≈110 MB, #6) + one prior generation kept for rollback safety (≈110 MB) ≈ 1.22 GB/replica — small enough that storage is never the binding constraint at this design's target scale (§4), reinforcing that fsync latency and network bandwidth (#5, #8), not disk capacity, are the real ceilings.

35. Alternative Architectures (Roads Not Taken)

A1 — ZAB replication (as ZooKeeper itself), instead of Raft.

Show the original text diagram
   Leader ──FIFO broadcast──► Follower, Follower, Follower
     (primary-backup atomic broadcast; two-phase: propose, commit)

Regime where it wins: extending an already-deployed ZooKeeper ensemble where wire-level protocol compatibility with existing tooling matters more than implementation clarity. Real embodying system: Apache ZooKeeper itself. Why rejected: Ongaro-Ousterhout 2014's whole thesis is that Raft is more teachable with equivalent guarantees (Junqueira et al. 2011, section 2) — for a from-scratch build whose purpose is teaching consensus correctly, that pedagogical edge outweighs ensemble compatibility (ADR-03).

A2 — Gossip-based eventually-consistent advisory locking, no strong consensus.

Show the original text diagram
   [Node]──gossip──[Node]──gossip──[Node]   (SWIM-style mesh,
      \_______________gossip_______________/    no total order)

Regime where it wins: massive scale where locks are advisory hints (e.g., cache-invalidation coordination) and partition-tolerance is valued over strict mutual exclusion. Real embodying system: HashiCorp Serf's gossip membership layer (which Consul itself layers strong consensus atop for anything requiring real locking). Why rejected: no linearizable fencing-token issuance is possible without a total order — this defeats the entire Kleppmann lesson (§8.4) that is this project's central teaching goal.

A3 — Single-node service backed by externally-replicated block storage (no consensus implemented at all).

Show the original text diagram
   [Single active node] ──sync replicate──► [Replicated block device]
          (failover = remount + process restart on a standby)

Regime where it wins: when the durability substrate is already synchronously replicated by the infrastructure (e.g., a cloud provider's zonal-replicated disk) and the team wants to avoid implementing consensus entirely. Real embodying system: legacy warm-standby HA-Postgres patterns built on DRBD-replicated block devices. Why rejected: failover time is bounded by disk-remount-plus-process-restart (seconds to tens of seconds, worse than M5's 5 s target), there is no read-scaling, and there is no majority-quorum split-brain protection — a fundamentally more fragile design under network partition than Raft (I12).

A4 — Paxos with an aggressive client-side caching proxy layer (Chubby's own approach).

Show the original text diagram
   [Client]──cache hit (local)──► answer, no round-trip
   [Client]──cache miss────────► [Paxos master] (invalidation on write)

Regime where it wins: extremely read-heavy workloads across huge fleets where round-tripping every read to the coordination service would overwhelm it (Chubby's own motivation, Burrows 2006, section 2.4). Real embodying system: Chubby itself. Why rejected: Paxos's implementation subtlety — multiple papers exist just to clarify it (Lamport 1998 vs. 2001) — makes it a worse pedagogical target than Raft (the same ADR-03 rationale as A1); the caching-proxy layer itself is a legitimate future addition, deferred to §36 as a stretch goal rather than rejected outright.

37. Glossary

  • ACL (Access Control List) — the per-znode list of (scheme, id, perms) entries evaluated on every request (§21).
  • AppendEntries — the Raft RPC a leader uses to replicate log entries and send heartbeats (§16).
  • Apply index — the log index up to which the state machine has applied committed entries (last_applied, §11.8).
  • Barrier recipe — the SDK composition where N participants all wait for each other at a checkpoint (§20.3).
  • BFT (Byzantine Fault Tolerance) — tolerance of arbitrarily malicious replicas, out of scope for v1 (§23, §36).
  • Bincode — the binary serialization format used for Mutation/LogEntry encoding (§8.6).
  • BoundedStaleness — a deferred read mode trading a bounded staleness window for read scaling (§36).
  • Candidate — the Raft role a node takes while soliciting votes (§11.8).
  • Chubby — Google's original coordination service (Burrows 2006), the historical ancestor of this design (§2, §32).
  • Commit index — the highest log index known to be replicated to a majority (§11.8, I9).
  • Compaction — the process of taking a snapshot and truncating the WAL prefix it supersedes (§17.3, ADR-07).
  • Consul — HashiCorp's Raft-based service-mesh/coordination system, a comparative system in §32.
  • CRC32C — the Castagnoli CRC variant used for per-record and per-chunk integrity checks (§8.6, I10).
  • Digest scheme — the ACL scheme matching a SHA-256 (or legacy SHA-1) hash of user:password (§21.2).
  • Ephemeral znode — a znode bound to a session's lifetime, deleted atomically on ExpireSession (§8.1, I2).
  • etcd — the Raft-backed coordination service underlying Kubernetes, a comparative system in §32.
  • Failure detector — an abstraction (Chandra-Toueg 1996) approximated here by session timeouts (§14, §5).
  • Fencing token — the monotonic 64-bit value returned on lock acquire, checked by the protected resource (§8.4, I5).
  • FLP impossibility — the Fischer-Lynch-Paterson 1985 result that consensus is impossible in a fully asynchronous system with even one faulty process (§1, §5).
  • Follower — the Raft role that replicates a leader's log and does not propose entries itself (§11.8).
  • Group membership recipe — the SDK composition tracking a set of live members via ephemeral children (§20.2).
  • Ip scheme — the ACL scheme matching a CIDR block against the connection's source address (§21.2).
  • Jeopardy — the session state between missed heartbeats and full expiry, where the client may still resume (§8.2, MM1).
  • Joint consensus — Raft's two-phase membership-change protocol preventing disjoint-quorum disagreement (§16.2, P9).
  • Kleppmann scenario — the canonical GC-pause-then-stale-write failure fencing tokens exist to defeat (§8.4).
  • Knossos — the Jepsen project's linearizability checker, the model for coord-jepsen::checker (§5, §27).
  • Leader — the Raft role that proposes entries and drives replication (§11.8).
  • Leader election recipe — the lock recipe applied to an /election/<group> path (§20.1).
  • Linearizability — the correctness condition (Herlihy-Wing 1990) that all writes appear in one real-time-consistent total order (§6 P1, §7 I1).
  • Lock recipe — the sequential-ephemeral-child composition providing mutual exclusion (§19).
  • mzxid — the Stat field recording the zxid of a znode's last modification; the fencing-token source (§8.1, ADR-13).
  • Namespace — the in-memory hierarchical tree of znodes that is the replicated state machine (§11.4).
  • Observer replica — a deferred non-voting replica that scales reads without inflating the write quorum (§36).
  • pzxid — the Stat field recording the zxid of the last modification to a znode's children list (§8.1).
  • Path — a canonical znode identifier: leading /, no trailing /, no .., no // (§11.2).
  • Persistent watch — a deferred watch variant that survives more than one fire (§36).
  • Predecessor-watch pattern — watching the immediate predecessor sequential child instead of the lock root, defeating the thundering herd (§19.2, P7).
  • Pre-vote — the Raft hardening that prevents a reconnected, term-incrementing node from disrupting a stable cluster (§16.2, §16.6).
  • Principal — the authenticated identity attached to a connection, resolved via mTLS or SASL (§21.2).
  • Quorum — a majority of replicas; the unit of commit safety in Raft (§7 I12, MM6).
  • Raft — the consensus algorithm (Ongaro-Ousterhout 2014) this design uses for replication (§16, ADR-03).
  • Read mode — Sequential (follower-local) or Linearizable (sync()-gated); the throughput/freshness tradeoff (§6 P2, ADR-15).
  • Request ID — the client-generated UUID-v4 used for idempotent write retries (§11.6, §18.3).
  • Scheme — the ACL matching mechanism: world, auth, digest, or ip (§21.2).
  • Sequential znode — a znode whose name is suffixed with a monotonic, zero-padded counter at creation (§8.1, §13.2).
  • Sequential consistency — the weaker correctness condition (Lamport 1979) satisfied by follower-local reads (§6 P2, §7).
  • Session — the server-side lease that is the truth-source for a client's liveness (§8.2, §11.5, MM1).
  • Split-brain — the failure mode of two leaders committing conflicting entries; prevented by majority quorum (§7 I12, T1).
  • Stat — the metadata record attached to every znode (czxid, mzxid, version fields, etc., §8.1, §11.3).
  • sync() — the read-linearization primitive: a no-op write that must commit before a subsequent read is guaranteed fresh (§8.2, ADR-14, I14).
  • Thundering herd — the failure mode of many waiters all being notified by one event; defeated in the lock recipe by the predecessor-watch pattern (§19.2, T3).
  • Watch — a one-shot subscription firing on the next matching mutation to a path (§8.3, I3, I4).
  • WatchKind — one of NodeCreated, NodeDeleted, NodeDataChanged, NodeChildrenChanged (§11.5).
  • WAL (Write-Ahead Log) — the append-only, CRC-checked durability log between snapshots (§8.6, I10).
  • world:anyone — the default, unrestricted ACL scheme entry (§21.2, §21.4).
  • ZAB (ZooKeeper Atomic Broadcast) — ZooKeeper's own replication protocol, the rejected alternative to Raft (ADR-03, §35 A1).
  • ZooKeeper — Apache's open-source coordination service (Hunt et al. 2010), the primary wire-contract ancestor of this design (§2, §32).
  • Znode — a node in the hierarchical namespace: path, data, Stat, ACL, children (§8.1, §11.3).
  • Zxid — the cluster-wide monotonic transaction identifier, (epoch << 32) | counter (§11.1).
