  1. Why does a 3-node cluster's minority partition remain read-available (Sequential mode) but write-unavailable, and what would change if minority writes were allowed? (§16, §4)

  5. Why must sync() be a real Raft-committed no-op rather than "wait until local apply catches the leader's last known commit index"? (§16, §7 I14)

  12. Why can't ACL evaluation be cached client-side, and which invariant would a cache violate? (§21, §7 I7)

  15. Derive the per-replica session capacity from the FD budget, and explain why the officially quantified 10,000-connection constraint in §4 needs an operational correction. (§4, §33)
  16. Why is cross-replica snapshot byte-identity a correctness requirement, given that Raft only replicates the log, not the periodic snapshot, by default? (§17, §7 I8)
  17. Trace a client-visible symptom of FM-3 (log divergence after a bad membership change) back to the specific joint-consensus step that was skipped. (§24, §16)
  18. Why does the blueprint reject BFT replication for v1 but treat it as a first candidate for the deferred register rather than an outright non-goal? (§1, §36)

31. Mental Models & First Principles

  • MM1 — A session is a lease, not a connection. Insight: liveness is a server-granted lease independent of any one socket. Predicts: TCP flaps need not be catastrophic. Bug class without it: treating disconnect as instant failure, causing thundering reconnect storms and premature ephemeral loss. Resolving §14.
  • MM2 — A watch is an edge-triggered interrupt, not a level-triggered poll. Insight: it fires once, on the transition, then goes silent. Predicts: you must re-arm after every fire or you go blind to further changes. Bug class without it: the classic re-arm race where a fetch-after-fire misses an intervening mutation. Resolving §15.
  • MM3 — The log is the database; the state machine is a derived view. Insight: any replica can rebuild identical state from the log alone. Predicts: two replicas that applied the same log entries are byte-identical. Bug class without it: non-deterministic serialization (a stray HashMap) silently breaking replica agreement. Resolving §16, §8.
  • MM4 — A fencing token doesn't stop the pauper from writing; it stops the write from being believed. Insight: the lock service's responsibility ends at token issuance; the resource's begins there. Predicts: no coordination-service-side fix can ever close the Kleppmann gap alone. Bug class without it: shipping a Lock API that never exposes a token, silently reproducing the Redlock failure class. Resolving §19.
  • MM5 — Sequential consistency is free; linearizability is what you pay sync() for. Insight: the default read mode trades freshness for throughput deliberately. Predicts: read-your-own-write bugs on a lagging follower are expected, not anomalous, absent sync(). Bug class without it: assuming every read reflects the latest write. Resolving §16, §18.
  • MM6 — A quorum is a majority, not a supermajority, and that asymmetry is what makes one side of a partition survivable. Insight: a 3-node cluster tolerates exactly 1 failure, a 5-node exactly 2 — and more replicas make writes slower, not faster. Predicts: naively adding replicas "for more throughput" backfires on the write path. Bug class without it: sizing a cluster by guesswork instead of doing the majority arithmetic. Resolving §4, §30.
  • MM7 — Atomicity of ephemeral cleanup is a state-machine property, not a garbage-collector property. Insight: there is no async reaper thread, and there must never be one. Predicts: cleanup is instantaneous-and-total at the exact commit of ExpireSession, never partial. Bug class without it: a background sweep that races the state machine and leaves orphaned ephemerals. Resolving §14.
  • MM8 — CRC catches corruption; consensus catches disagreement — different failure classes need different defenses. Insight: fsync alone is not durability against bit-rot. Predicts: a successful fsync can still return corrupted bytes on read. Bug class without it: assuming disk-level acknowledgment implies data integrity. Resolving §17.
  • MM9 — More replicas make reads scale and writes slower, in the same breath. Insight: majority-commit latency grows with replica count even as read fan-out capacity grows with it too — the two curves point in opposite directions from the same knob. Predicts: "just add more nodes" is never a free throughput lever for the write path. Bug class without it: operators who size a cluster for read scaling and are then surprised by degraded write tail latency. Resolving §30, §33.

5. Required Reading

Books

  • Kleppmann, M. — Designing Data-Intensive Applications (O'Reilly, 2017). Ch. 8 (Distributed Systems Trouble), Ch. 9 (Consistency and Consensus). Extract: linearizability vs. eventual consistency, consensus algorithms, the fencing-token pattern. Applied in §8, §19.
  • Cachin, C., Guerraoui, R., Rodrigues, L. — Introduction to Reliable and Secure Distributed Programming, 2nd ed. (Springer, 2011). Ch. 2 (failure detectors), Ch. 5 (consensus). Extract: the formal failure-detector hierarchy underlying session timeouts. Applied in §7, §14.
  • Tanenbaum, A. S., Van Steen, M. — Distributed Systems: Principles and Paradigms, 3rd ed. (2017). Ch. 6 (Coordination), Ch. 8 (Fault Tolerance). Extract: logical clocks, election algorithms, the vocabulary this blueprint assumes. Applied in §7, §15.
  • Ghosh, S. — Distributed Systems: An Algorithmic Approach, 2nd ed. (CRC Press, 2014). Ch. 5 (mutual exclusion algorithms), Ch. 12 (agreement protocols). Extract: classical mutual-exclusion algorithms that motivate why a coordination service beats ad hoc locking. Applied in §19.
  • Birman, K. — Guide to Reliable Distributed Systems (Springer, 2012). Ch. 22 (group communication), Ch. 24 (consensus). Extract: view-change patterns ancestral to both ZAB and Raft. Applied in §14, §16.
  • Burns, B. — Designing Distributed Systems (O'Reilly, 2018). Ch. 2 (leader election pattern). Extract: the operational packaging of leader election as a reusable pattern. Applied in §20.

Reference Implementations

  • Apache ZooKeeper (github.com/apache/zookeeper) — study ServerCnxn, FinalRequestProcessor, the session tracker. Lesson: watch/session integration end to end. Pitfall: do not copy the single-threaded SyncRequestProcessor group-commit batching verbatim without understanding why it exists (it is the throughput lever, §22). Applied in §14, §15.
  • etcd (github.com/etcd-io/etcd) — study raft/, mvcc/, lease/. Lesson: lease-based liveness at scale. Pitfall: etcd's linearizable-by-default read path trades throughput this design explicitly declines (§18). Applied in §16, §18.
  • tikv/raft-rs (github.com/tikv/raft-rs) — study raft/src/raft.rs, raft/src/raw_node.rs. Lesson: a readable, production-grade Rust Raft core. Pitfall: its Ready() API couples I/O scheduling to the caller more tightly than a teaching implementation needs. Applied in §16, §9 ADR-04.
  • openraft (github.com/datafuselabs/openraft) — study openraft/src/core/. Lesson: async-native Raft in Rust. Pitfall: heavier abstraction than warranted for a from-scratch teaching build. Applied in §16, §9 ADR-04.
  • Jepsen / Knossos (github.com/jepsen-io/jepsen, github.com/jepsen-io/knossos) — study the linearizability checker and the ZooKeeper/etcd nemesis suites. Lesson: how to build a fault-injecting conformance harness. Pitfall: brute-force linearizability checking is exponential in concurrency — bound history size (§33). Applied in §27, §33.

RFCs / Specifications

  • RFC 8446 — TLS 1.3. The mTLS transport-security layer. Applied in §21, §9 ADR-10.
  • RFC 4422 — SASL. The alternative auth mechanism. Applied in §21, §9 ADR-10.
  • RFC 4120 — Kerberos V5. The GSSAPI mechanism SASL wraps. Applied in §21.

Glossary (§37) · 59 terms · site-wide glossary

ACL (Access Control List)
the per-znode list of (scheme, id, perms) entries evaluated on every request (§21).
AppendEntries
the Raft RPC a leader uses to replicate log entries and send heartbeats (§16).
Apply index
the log index up to which the state machine has applied committed entries (last_applied, §11.8).
Barrier recipe
the SDK composition where N participants all wait for each other at a checkpoint (§20.3).
BFT (Byzantine Fault Tolerance)
tolerance of arbitrarily malicious replicas, out of scope for v1 (§23, §36).
Bincode
the binary serialization format used for Mutation/LogEntry encoding (§8.6).
BoundedStaleness
a deferred read mode trading a bounded staleness window for read scaling (§36).
Candidate
the Raft role a node takes while soliciting votes (§11.8).
Chubby
Google's original coordination service (Burrows 2006), the historical ancestor of this design (§2, §32).
Commit index
the highest log index known to be replicated to a majority (§11.8, I9).
Compaction
the process of taking a snapshot and truncating the WAL prefix it supersedes (§17.3, ADR-07).
Consul
HashiCorp's Raft-based service-mesh/coordination system, a comparative system in §32.
CRC32C
the Castagnoli CRC variant used for per-record and per-chunk integrity checks (§8.6, I10).
Digest scheme
the ACL scheme matching a SHA-256 (or legacy SHA-1) hash of user:password (§21.2).
Ephemeral znode
a znode bound to a session's lifetime, deleted atomically on ExpireSession (§8.1, I2).
etcd
the Raft-backed coordination service underlying Kubernetes, a comparative system in §32.
Failure detector
an abstraction (Chandra-Toueg 1996) approximated here by session timeouts (§14, §5).
Fencing token
the monotonic 64-bit value returned on lock acquire, checked by the protected resource (§8.4, I5).
FLP impossibility
the Fischer-Lynch-Paterson 1985 result that consensus is impossible in a fully asynchronous system with even one faulty process (§1, §5).
Follower
the Raft role that replicates a leader's log and does not propose entries itself (§11.8).
Group membership recipe
the SDK composition tracking a set of live members via ephemeral children (§20.2).
Ip scheme
the ACL scheme matching a CIDR block against the connection's source address (§21.2).
Jeopardy
the session state between missed heartbeats and full expiry, where the client may still resume (§8.2, MM1).
Joint consensus
Raft's two-phase membership-change protocol preventing disjoint-quorum disagreement (§16.2, P9).
Kleppmann scenario
the canonical GC-pause-then-stale-write failure fencing tokens exist to defeat (§8.4).
Knossos
the Jepsen project's linearizability checker, the model for coord-jepsen::checker (§5, §27).
Leader
the Raft role that proposes entries and drives replication (§11.8).
Leader election recipe
the lock recipe applied to an /election/<group> path (§20.1).
Linearizability
the correctness condition (Herlihy-Wing 1990) that all writes appear in one real-time-consistent total order (§6 P1, §7 I1).
Lock recipe
the sequential-ephemeral-child composition providing mutual exclusion (§19).
mzxid
the Stat field recording the zxid of a znode's last modification; the fencing-token source (§8.1, ADR-13).
Namespace
the in-memory hierarchical tree of znodes that is the replicated state machine (§11.4).
Observer replica
a deferred non-voting replica that scales reads without inflating the write quorum (§36).
pzxid
the Stat field recording the zxid of the last modification to a znode's children list (§8.1).
Path
a canonical znode identifier: leading /, no trailing /, no .., no // (§11.2).
Persistent watch
a deferred watch variant that survives more than one fire (§36).
Predecessor-watch pattern
watching the immediate predecessor sequential child instead of the lock root, defeating the thundering herd (§19.2, P7).
Pre-vote
the Raft hardening that prevents a reconnected, term-incrementing node from disrupting a stable cluster (§16.2, §16.6).
Principal
the authenticated identity attached to a connection, resolved via mTLS or SASL (§21.2).
Quorum
a majority of replicas; the unit of commit safety in Raft (§7 I12, MM6).
Raft
the consensus algorithm (Ongaro-Ousterhout 2014) this design uses for replication (§16, ADR-03).
Read mode
Sequential (follower-local) or Linearizable (sync()-gated); the throughput/freshness tradeoff (§6 P2, ADR-15).
Request ID
the client-generated UUID-v4 used for idempotent write retries (§11.6, §18.3).
Scheme
the ACL matching mechanism: world, auth, digest, or ip (§21.2).
Sequential znode
a znode whose name is suffixed with a monotonic, zero-padded counter at creation (§8.1, §13.2).
Sequential consistency
the weaker correctness condition (Lamport 1979) satisfied by follower-local reads (§6 P2, §7).
Session
the server-side lease that is the truth-source for a client's liveness (§8.2, §11.5, MM1).
Split-brain
the failure mode of two leaders committing conflicting entries; prevented by majority quorum (§7 I12, T1).
Stat
the metadata record attached to every znode (czxid, mzxid, version fields, etc., §8.1, §11.3).
sync()
the read-linearization primitive: a no-op write that must commit before a subsequent read is guaranteed fresh (§8.2, ADR-14, I14).
Thundering herd
the failure mode of many waiters all being notified by one event; defeated in the lock recipe by the predecessor-watch pattern (§19.2, T3).
Watch
a one-shot subscription firing on the next matching mutation to a path (§8.3, I3, I4).
WatchKind
one of NodeCreated, NodeDeleted, NodeDataChanged, NodeChildrenChanged (§11.5).
WAL (Write-Ahead Log)
the append-only, CRC-checked durability log between snapshots (§8.6, I10).
world:anyone
the default, unrestricted ACL scheme entry (§21.2, §21.4).
ZAB (ZooKeeper Atomic Broadcast)
ZooKeeper's own replication protocol, the rejected alternative to Raft (ADR-03, §35 A1).
ZooKeeper
Apache's open-source coordination service (Hunt et al. 2010), the primary wire-contract ancestor of this design (§2, §32).
Znode
a node in the hierarchical namespace: path, data, Stat, ACL, children (§8.1, §11.3).
Zxid
the cluster-wide monotonic transaction identifier, (epoch << 32) | counter (§11.1).
