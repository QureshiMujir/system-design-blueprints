In one paragraph

A distributed lock service lets many machines agree on who holds a lock, who the leader is, and which processes are still alive, even when machines pause, crash or lose their network (§2). This design, coord, is a Rust coordination service in the Chubby/ZooKeeper/etcd family. It keeps a tree of small data nodes (znodes), copies every change to a majority of 3 or 5 replicas with the Raft consensus protocol, and hands every lock holder a fencing token, a number that only grows, so the protected resource can reject a stale holder (§1). Platform teams run it as a 3- or 5-node cluster (§1). Its defining target: every write is linearizable and every token is monotonic (§4).

The problem, concretely

A common shortcut is a lock built from Redis SET NX EX, a key that sets itself only if absent and expires on a timer (§2). It fails in ways that appear only in production: a garbage-collection pause longer than the lease, a partition that cuts the lease check off from the protected resource, or a clock-skew event that makes two nodes both believe they hold the lock (§2).

The blueprint's own walk-through of the failure (§8.4): client A takes the lock and then enters a pause longer than its session timeout. The service expires A's session and deletes A's lock node. Client B takes the lock. A wakes up, does not know it lost the lock, and writes to the protected resource. Nothing inside the lock service can prevent that last step, because A has no way to know locally that its session expired (§8.4). So the design has to answer three questions at once: who is the leader, is this node alive, and did my lock get revoked while I was paused (§2). It answers the last with a fencing token checked by the resource itself, the only closure (§8.4, P5, MM4).

How it works, end to end

The blueprint stacks seven boxes (§3). Lightly condensed:

Follow one Lock::acquire (a create of a sequential ephemeral znode, §19.2) down the stack:

  1. Client SDK (coord-sdk). Every write carries a UUID-v4 request_id, and retries reuse it (§18.2). The SDK is the only layer application code touches (§3).
  2. Wire layer (coord-net, module coord-net::frame). The request is a frame: 4-byte little-endian length, 1-byte opcode (0x01 Create), bincode payload (§8.5). A truncated or malformed frame is dropped before it reaches the namespace or Raft (§8.7).
  3. Session layer (coord-core::session). The session is the truth-source for liveness, not the TCP socket (I6, P3). Every ephemeral znode and every watch is indexed by session (§3).
  4. ACL layer (request dispatch in coord-net). The ACL is evaluated on every request and never cached (I7). create needs the CREATE permission on the parent (§21.2).
  5. Raft (coord-raft). The leader appends the write as a log entry, replicates it with AppendEntries, and only after a majority acknowledges does advance_apply apply it, strictly in log order (I9, §16.2). The WAL record is a length, a CRC32C, and the bincode LogEntry (§8.6).
  6. Namespace (coord-core). Mutation::apply changes the tree deterministically; the response goes back to the caller through the pending_requests map keyed by request_id (§16.2, I8).
  7. Watch subsystem. A mutation that touches a watched path removes the watch and queues a WatchEvent on the owning session's outbound channel, the same channel as ordinary responses, which is what makes the ordering guarantee free (§15.2, I4).

Reads take a shorter road: a default read is answered by a follower (Sequential); a read that must be fresh first calls sync(), a real logged Raft entry (§3, P2, ADR-14). Cluster shape (§3):

The core ideas

A session is a lease, not a connection (§8.2, P3, I6, MM1)

A session is a server-side lease that outlives any one TCP socket. It has four states, and Expired is terminal (§8.2):

From To Trigger (§8.2, §14.2)
Connecting Connected first heartbeat after NewSession commits
Connected Jeopardy no heartbeat for timeout/3 * 2
Jeopardy Connected any heartbeat before the full timeout
Jeopardy Expired leader commits Mutation::ExpireSession (no heartbeat for timeout)

The client sends Heartbeat every timeout/3; the default timeout is 30 s, negotiated within [5 s, 120 s] (§14.2, §4, ADR-05). Jeopardy is the state Chubby pioneered: the client may still resume, but application code is warned that its lock might already be gone (§8.2). The blueprint's test trace (§14.4): connect, create ephemeral /x, force-close the socket; at t = timeout/2 /x still exists, at t = timeout + 1s it is gone and the state is Expired. Expiry is judged against a Raft-propagated clock (max(local_clock, proposed_at)), never wall time (§14.2).

Ephemeral znodes die atomically with their session (§14.2, I2, P4, MM7)

An ephemeral znode has an ephemeral_owner that binds it to exactly one session (§8.1, P4). ExpireSession(id) walks that session's list and removes every owned znode inside the same apply() call, never in a background sweep (§14.2, I2). The blueprint's fixture: a session with 50 owned ephemerals must have all 50 gone in the same applied entry (§14.5). If it were not atomic, you would get a "ghost lock", a resource that believes it is protected by a session that no longer exists (§14.9).

Writes go through Raft; reads choose their price (§6 P1/P2, I1, I9, I14, ADR-14)

Every mutation is a Raft log entry, applied only after it is committed (I9). Raft here also covers pre-vote (a reconnecting node may not bump its term and disrupt the cluster) and joint-consensus membership changes, never a single-step "add one replica" (§16.2, P9). A write that survives a leader crash, from the blueprint's own failure-path trace (§8.8):

  1. The leader appends set_data, starts replicating, and crashes before a majority acknowledges.
  2. The SDK retries the same request_id against the newly elected leader.
  3. Either the old entry never reached a majority (it is truncated, the retry proposes fresh, the write lands once), or it did (it is already committed, the retry is matched in pending_requests and returns the original response without re-applying).

For reads, a follower-local get_data is sequentially consistent but may be stale; sync() promotes it to linearizable (P2, MM5). sync() is a real committed no-op, because a local shortcut would reintroduce split-brain (I14, ADR-14).

Fencing tokens: the resource, not the service, closes the hole (§8.4, I5, ADR-13, P5, MM4)

The token is the mzxid (zxid of last modification) of the lock znode, and Raft's commit order makes it monotonic (ADR-13, I5). The blueprint's six-step trace (§8.4):

Step Event Token involved
1 A acquires /locks/db-primary 0x0000000100000005
2-3 A pauses past the timeout; leader commits ExpireSession(A); A's lock child is deleted (I2) none
4 B acquires the lock 0x0000000100000007, strictly greater (I5)
5 A wakes and writes, presenting its old token 0x...05
6 The resource compares against its stored high-watermark and rejects 0x...07

Lock::is_definitely_held() returns false whenever the session is not Connected. The blueprint calls it a defense-in-depth signal, not the safety mechanism; the token check at the resource is (§19.2, I5). The SDK method is named acquire, not lock(), and returns a token (§19.6, P5).

The lock recipe and the predecessor watch (§19.2, §33 item 10, T3)

The lock is built only from four primitives (create, get_children, exists, delete, §19.10):

  1. Create a sequential ephemeral child /locks/<resource>/holder-<seq> (§19.2). The suffix is 10 digits, zero-padded, from the parent's cversion + 1 (§13.2).
  2. List the children. If yours has the lowest sequence number, you hold the lock and get FencingToken(stat.mzxid) (§19.2).
  3. Otherwise register a NodeDeleted watch on your immediate predecessor only, and re-list when it fires (§19.2). If the predecessor vanished before the watch was registered, re-list at once (§19.8).

Never watch the lock root: that is the thundering herd (T3). The blueprint's arithmetic (§33 item 10): with N = 1,000 waiters and M4's 2 ms per-watch round trip, a root watch costs 1,000 × 2 ms = 2,000 ms of serialized notification per release, the predecessor pattern 1 × 2 ms, a 1,000x factor. Its fixture expects exactly one watch fire, not 1,000 (§19.5).

One-shot watches (§8.3, I3, I4, P7, MM2)

A watch is a subscription that fires once and is then removed; the blueprint calls it an edge-triggered interrupt, not a level-triggered poll (MM2). Four kinds, each armed as a side effect of a read: NodeCreated, NodeDeleted, NodeDataChanged, NodeChildrenChanged (children changes only, direct children only, §8.3). The client must re-arm inside the same call that observes the new state, or an update slips through the gap (§8.3, P7). On reconnect the client sends each watch with its last_seen_zxid, and the server fires a synthetic event for any path whose mzxid is newer (§8.5, §15.2). Watches are in memory only and not replicated (ADR-12).

The trade-offs — where engineers disagree

Replication protocol: Raft (ADR-03)

Chosen: Raft, because Ongaro-Ousterhout 2014 is the most teachable consensus paper and Junqueira et al. 2011, section 2, shows ZAB-equivalent guarantees (ADR-03, §35 A1). Rejected: ZAB, Paxos. When the rejected choice is right: ZAB, when you are extending an existing ZooKeeper deployment and want wire-level compatibility with its ensemble protocol (ADR-03).

Raft crate: write a minimal one (ADR-04)

Chosen: vendor a minimal coord-raft, since the project teaches Raft rather than consuming it (ADR-04). Rejected: depend on tikv/raft-rs or openraft. When the rejected choice is right: once the team has proven the vendored core correct and wants battle-tested edge-case handling instead of continued pedagogy (ADR-04).

Fencing token source: the mzxid (ADR-13)

Chosen: the lock znode's mzxid, already monotonic cluster-wide in Raft commit order, which avoids a parallel counter (ADR-13). Rejected: an independent atomic counter. When the rejected choice is right: when tokens must survive a full namespace wipe-and-rebuild while zxids reset (ADR-13).

What sync() means: a real Raft entry (ADR-14)

Chosen: a no-op Raft proposal that returns on commit; it must traverse real consensus or split-brain returns (ADR-14, I14). Rejected: wait for a local apply-index. When the rejected choice is right: advisory, non-safety-critical "roughly fresh" reads that explicitly forgo the linearizable guarantee (ADR-14).

Where watches live: in memory only (ADR-12)

Chosen: not replicated; the client re-arms on reconnect, because replicating watches is expensive and the client already knows what it watched (ADR-12). Rejected: replicate watch state via Raft. When the rejected choice is right: if server-initiated migration without client cooperation becomes a hard requirement (ADR-12).

Session timeout: 30 s default, bounded 5 to 120 s (ADR-05)

Chosen: 30 s, client-negotiated within [5 s, 120 s], matching ZooKeeper's observed sweet spot between fast ephemeral release and GC-pause tolerance (ADR-05). Rejected: fixed 10 s, fixed 60 s. When the rejected choice is right: fixed 10 s, in a tightly controlled internal cluster with no GC pauses and a hard SLA on ephemeral release latency (ADR-05).

WAL durability: fsync on commit plus a checksum (ADR-08)

Chosen: append-only, fsync-on-commit, CRC32C per record, because fsync alone does not catch controller-level corruption (ADR-08, MM8). Rejected: fsync-on-batch, no CRC. When the rejected choice is right: fsync-on-batch, when write latency dominates over corruption risk and the deployment trusts enterprise storage with end-to-end ECC (ADR-08).

Znode size: 1 MiB, checked three times (ADR-06)

Chosen: 1 MiB, enforced at the API, the Raft proposal and the snapshot chunk (ADR-06, I11, P11). Rejected: 4 MiB, unbounded. When the rejected choice is right: 4 MiB, for larger config blobs where the operator explicitly raises --max-znode-bytes and accepts the batching cost (ADR-06).

Roads not taken (§35, §36)

ZAB replication (§35 A1) wins when extending a deployed ZooKeeper ensemble where wire compatibility matters more than clarity. It was rejected as the teaching target (ADR-03).

Gossip-based advisory locking with no consensus (§35 A2) wins at massive scale where locks are hints, such as cache-invalidation coordination. It was rejected because no fencing token can be issued without a total order, which defeats the central lesson (§8.4).

A single node over externally replicated block storage (§35 A3) wins when the infrastructure already replicates the disk synchronously and the team wants no consensus code. It was rejected: failover is bounded by remount and restart, with no read scaling and no majority-quorum split-brain protection (§35 A3, I12).

Paxos with a client-side caching proxy, Chubby's own approach (§35 A4) wins for extremely read-heavy workloads across huge fleets. It was rejected as a teaching target; the caching proxy itself is deferred, not rejected (§35 A4, §36).

The deferred register (§36) holds 11 items, each with an un-defer trigger: for example BFT when a cross-organization deployment needs untrusted-replica tolerance, observer replicas when read throughput stays above twice M2 for 30+ days, and gRPC when 3 or more language SDKs are needed at once.

What must never be false

Each line gives the invariant and how the system notices a violation (§7).

  • I1 all writes are observed in one total order. Caught by the Jepsen linearizability checker; watch raft_commit_index and raft_apply_index.
  • I2 session expiry deletes all owned ephemerals atomically with ExpireSession. Caught by the namespace_ops property fixture; ephemeral_delete_count.
  • I3 a watch registration fires at most once. watch.one_shot bucket; watch_fire_total.
  • I4 a fired watch precedes any later response that shows the post-event state, on one session. watch.delivery_order bucket; channel-depth gauge.
  • I5 every grant's token exceeds every prior token for that resource. lock.linearizable Jepsen bucket; fencing_token_high_watermark.
  • I6 a session is alive if and only if its state is not Expired, independent of TCP. session.state_machine bucket; session_state{state} gauge.
  • I7 ACLs are evaluated per request and never cached. acl.eval 1000-permutation bucket; acl_deny_total.
  • I8 identical state serializes identically on every replica. Cross-replica snapshot-hash diff test; snapshot_hash_mismatch_total must stay 0.
  • I9 no mutation is visible before its entry commits. raft.replay bucket; the commit_index − last_applied lag gauge.
  • I10 every WAL record's CRC32C is checked before apply. wal.crash_recovery bucket; wal_crc_mismatch_total.
  • I11 no znode payload exceeds 1 MiB. Fuzz target namespace_ops; znode_too_large_total.
  • I12 no two leaders commit conflicting entries in one term. raft.partition bucket; divergence of per-replica raft_term.
  • I13 at most 10,000 watches and 10,000 ephemerals per session. session_caps conformance case; session_watch_count and session_ephemeral_count gauges.
  • I14 sync() always performs a real Raft commit. raft.replay bucket plus a manual review checklist; sync_latency_seconds histogram.

What breaks in production

  • FM-1: an ephemeral znode survives a client crash. Root cause: the session has not yet expired, which is expected behavior until t = timeout (§24). Detection: ephemeral_delete_count stays flat past the expected expiry. Recovery: none needed; an operator may force ExpireSession early if the client is confirmed dead (§24).
  • FM-2: partial ephemeral cleanup. Some but not all owned znodes disappear because ExpireSession was applied non-atomically, an I2 violation and an implementation bug (§24). The namespace_ops property test catches it before merge; in production the sign is an orphaned ephemeral with no live session. Recovery: roll back the release and audit the namespace against the WAL (§24).
  • FM-3: split-brain or log divergence. Root cause: a single-server membership-change shortcut that bypassed joint consensus (§24, P9). Detection: the raft.partition bucket and raft_term divergence. Recovery: full incident review, docs/runbooks/split-brain-postmortem.md, possibly manual log truncation on a minority replica (§24).
  • FM-5: a fencing token is not monotonic. Root cause: an ADR-13 derivation bug or a zxid-allocation race (§24). Detection: the lock.linearizable Jepsen bucket. There is no auto recovery; the blueprint treats it as a correctness emergency and a Sealed-gate blocker (§24, §19.9).
  • FM-6: replica snapshots differ byte for byte. A HashMap crept into a serializable type, an I8 violation. Detection: the cross-replica snapshot-hash diff. Recovery: a code fix and a forced re-snapshot on all replicas (§24, P14).
  • FM-7: a config watcher silently stops updating. A watch fire was missed on reconnect. It shows as application-level staleness and, before merge, in the watch.reconnect_synthetic bucket. The SDK attempts a synthetic re-fire; a client restart forces a fresh Connect that re-arms all watches (§24).
  • FM-9: leader election never converges. Pre-vote was omitted or misimplemented, so nodes keep starting disruptive elections (§24, §16.6). Detection: raft_term incrementing rapidly with no stable leader. Recovery: restart the disruptive node and verify the pre-vote logic (§24).
  • FM-12: a replica cannot rejoin after a long isolation. Its log fell too far behind for AppendEntries. Detection: an InstallSnapshot request spike on the rejoining replica. Recovery: InstallSnapshot sends a fresh snapshot automatically; re-provision if disk space is short (§24).

Threats a reader should know (§23.2):

  • T2 session hijacking with a stolen session password. Answered by a 16-byte password plus mTLS-bound connections; revoke the session with ExpireSession and rotate certs.
  • T3 thundering herd on lock release. Answered by the predecessor-watch pattern (§19.2).
  • T4 a watch storm from a buggy or malicious client. Answered by the 10,000-per-session cap (ADR-16, I13); the proposal is rejected with LimitExceeded. T5 is the same with ephemerals (ADR-17).
  • T6 a Byzantine replica. Out of scope for v1; ACLs only limit the blast radius at the client layer, and BFT is the deferred un-defer path (§23.2, §36).
  • T7 clock skew causing false session expiry. Answered by the Raft-propagated clock and a 10 s max-skew SLO (§23.2, §4).

How it compares

  • Chubby caches aggressively on the client with lease invalidation (§32, Burrows 2006 section 2.4), so reads bypass the master. That wins in read-heavy, huge fleets; coord declines it in v1 as a separate piece of engineering and defers it (§32, §36).
  • ZooKeeper uses ZAB instead of Raft and has no native fencing token, so client libraries derive zxid-based tokens by hand (§32). It fits when extending an existing ensemble where wire compatibility matters; coord chose Raft for teachability (ADR-03).
  • etcd reads linearizably by default (--consistency=l) and exposes its lease revision as a usable fencing token (§32). That suits teams that would rather pay latency than reason about read modes; coord makes the choice explicit (P2).
  • Consul bakes service discovery and health checking into the coordination layer and uses a session LockIndex as a fencing token (§32). It wins when one system should do both discovery and locking; coord stays a narrower primitive so it stays teachable (§32, §1).

If you only remember three things

A lock service cannot stop a paused holder from writing, so every grant carries a monotonic fencing token that the protected resource must check (§8.4, I5, MM4). Liveness belongs to a leased session and ephemeral cleanup is one atomic log entry, never a sweeper (I6, I2, MM1, MM7). Writes pay a majority round trip through Raft while reads choose between fast-but-possibly-stale and sync()-fresh, and that cost shows up explicitly (P1, P2, MM5).

Words used here

  • Znode: a node in the tree, holding whole-value data (up to 1 MiB), metadata (Stat), an ACL and children.
  • Ephemeral znode: a znode that lives only as long as its owning session.
  • Sequential znode: a znode whose name gets a monotonic, zero-padded counter suffix at creation.
  • Session: a server-side lease that decides whether a client counts as alive, independent of its socket.
  • Jeopardy: the session state between missed heartbeats and full expiry, where the client may still resume.
  • Watch: a one-shot subscription that fires on the next matching change to a path, then is removed.
  • Fencing token: the monotonic 64-bit number returned with a lock grant, checked by the protected resource.
  • mzxid: the transaction id of a znode's last modification; the source of the fencing token.
  • Linearizability: all writes appear in one total order consistent with real time.
  • Sequential consistency: the weaker guarantee followers give for local reads, which may be stale.
  • sync(): a committed no-op write that makes the next read fresh.
  • Pre-vote: a Raft step that stops a reconnecting node from disrupting a stable cluster.
  • Joint consensus: Raft's two-phase membership change that prevents two disjoint majorities.
  • WAL (write-ahead log): the append-only, CRC-checked log between snapshots.
  • Thundering herd: many waiters woken by one event; the predecessor watch avoids it.
