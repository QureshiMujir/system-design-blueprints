33. Back-of-Envelope Capacity Model

  1. Max sessions/replica = FD budget ÷ FDs-per-session = 65,536 ÷ 10 ≈ 6,500 sessions/replica (§4 FD-budget row).
  2. Cluster session capacity (5 replicas) = 6,500 × 5 ≈ 32,500 concurrent sessions, ignoring leader-only overhead.
  3. Worst-case watch memory/session = 10,000 watches × ~100 B/watch struct ≈ 1 MB/session; at 6,500 sessions/replica that's 6.5 GB/replica worst case — this is why the §4 CPU/memory ceiling (8 GiB RSS) assumes typical, not worst-case, watch load; an operator must monitor session_watch_count against this derived ceiling.
  4. Namespace memory at 100K znodes = 100,000 × (≈1 KiB avg data + ≈200 B Stat/ACL overhead) ≈ 120 MB — well within the 8 GiB budget, confirming most of the memory budget is watch/session state, not znode data.
  5. WAL write bandwidth at M1 = 50,000 writes/sec × (1,024 B payload + 8 B header) ≈ 51.6 MB/sec sustained — the minimum disk-throughput spec any deployment must exceed with headroom (an NVMe SSD's ≈2 GB/sec sequential write gives ≈40x headroom).
  6. Snapshot size at 100K znodes ≈ 100 MB namespace + ~10 MB session set ≈ 110 MB, chunked at 1 MiB ≈ 110 chunks.
  7. Snapshot-restore I/O floor for M8 = 110 MB ÷ 5 s = 22 MB/sec required — ~90x below typical NVMe sequential read (~2 GB/sec), so M8's real bottleneck is deserialization CPU, not I/O (§17.7).
  8. Leader replication egress at M1, 5-node cluster = 50,000 writes/sec × 1,032 B × 4 followers ≈ 206 MB/sec aggregate leader egress — decisively requires ≥ 1 Gbps NIC, 10 GbE recommended for headroom.
  9. FD-derived session ceiling vs. the stated §4 constraint: the FD-derived 6,500 sessions/replica (#1) is below the officially quantified "10,000 max concurrent connections" row in §4 — a documented discrepancy resolved operationally by raising the ulimit to 100,000 in docs/runbooks/ (§25), not by changing the derivation.
  10. Thundering-herd factor, predecessor-watch vs. naive root-watch = at N = 1,000 waiters and M4's 2 ms per-watch round trip: naive (watch the root) = 1,000 × 2 ms = 2,000 ms (2 s) of serialized notification per release; predecessor pattern = 1 × 2 ms = 2 ms per release — a 1,000x factor derived directly from the recipe choice (§19.7).
  11. Write-batching amortization at the M1 target = at 256 mutations/batch (§22.2 default) and 50,000 writes/sec, the leader proposes ≈ 50,000 ÷ 256 ≈ 195 Raft entries/sec, not 50,000 — the batch window converts a 50,000/sec fsync requirement into a ≈195/sec one, explaining why §33 #5's 51.6 MB/sec bandwidth figure is payload-bound, not fsync-call-count-bound.
  12. Total cluster storage footprint at steady state = WAL retained since last compaction (≤ 1 GB, ADR-07) + latest snapshot (≈110 MB, #6) + one prior generation kept for rollback safety (≈110 MB) ≈ 1.22 GB/replica — small enough that storage is never the binding constraint at this design's target scale (§4), reinforcing that fsync latency and network bandwidth (#5, #8), not disk capacity, are the real ceilings.
