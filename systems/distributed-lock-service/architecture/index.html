Leader-follower topology (3- or 5-node typical):

Application layer — external services that consume coord as a dependency; out of this project's scope but the reason it exists. Client SDK — owns connection pooling, session reconnection, idempotent retry via request-id de-duplication, watch re-arming, and the four composed recipes; the only layer application code touches. Session layer — the truth-source for liveness (§7 I6); tracks heartbeats and the four-state session machine; every ephemeral znode and every watch is indexed by session. ACL layer — evaluates the per-znode ACL list against the connection-resolved principal on every single request (§7 I7); never caches. Hierarchical namespace + watch subsystem — the in-memory state machine Raft replicates; a radix-indexed tree of znodes plus the one-shot watch registry, both opaque to Raft (§7 I3, I4). Raft replication — the sole path to linearizable writes; commit-then-apply ordering (§7 I9) is the cornerstone invariant; reads optionally bypass it for throughput. Storage layer — WAL plus periodic snapshot give crash recovery; every record is CRC-checked (§7 I10) because fsync alone does not guarantee bit-level integrity (Pillai et al. 2014). All later sections stay consistent with this diagram; a box referenced elsewhere always resolves to one of these seven.

8. Domain Model, Protocol & Data Model

8.1 Znode data model

A znode carries a canonical path (/services/db/leader, leading /, no trailing /, no .., no double-/), a byte-vector data (≤ 1 MiB, P6), a Stat record, an ACL list, and a children index. Stat fields: czxid (creation zxid), mzxid (last-modification zxid — the fencing-token source, P5), pzxid (last modification of the children list), ctime/mtime (advisory wall-clock, not load-bearing), version (data version, bumped on set_data), cversion (children version, bumped on child add/remove), aversion (ACL version, bumped on set_acl), ephemeral_owner (Some(session_id) or None for persistent), data_length, num_children. Operations are whole-value: get_data returns the entire payload, set_data replaces it (P6) — there is no partial-write or append primitive.

Transition table: Connecting → Connected on first heartbeat after NewSession commits. Connected → Jeopardy on missing a heartbeat for timeout/3 * 2. Jeopardy → Connected on any subsequent heartbeat before full timeout elapses. Jeopardy → Expired on the leader committing Mutation::ExpireSession, which is terminal — no transition leaves Expired; the client must construct a new session. Jeopardy exists because Chubby pioneered it (Burrows 2006, section 2.6); between TCP loss and the leader giving up, the client may still resume, but application code must be warned the lock it holds might already be gone (P3, the on_lose_leadership hook in §20.1).

8.3 Watch protocol

Four kinds, each armed as a side effect of a successful read: NodeCreated (via exists(path, watch) when absent), NodeDeleted (via get_data/exists(path, watch) when present), NodeDataChanged (via get_data(path, watch)), NodeChildrenChanged (via get_children(path, watch), fires only on direct child add/remove, not grandchild change). Delivery-ordering guarantee (I4): a watch fires on the client's outbound channel before any later response on that same session can reflect the post-event state. A watch is one-shot (I3, P7): registered, fired once, removed; the client must re-arm inside the same call that observes the new state to avoid the classic re-arm race (§15.6).

8.4 Fencing-token protocol — the Kleppmann scenario, worked example

  1. Client A acquires the lock on /locks/db-primary; fencing token = mzxid = 0x0000000100000005.
  2. Client A enters a GC pause exceeding the session timeout.
  3. The leader commits ExpireSession(A); A's ephemeral lock child is deleted atomically (I2).
  4. Client B acquires the lock; fencing token = mzxid = 0x0000000100000007 (strictly greater, I5).
  5. Client A's GC pause ends; unaware its session expired, A writes to the protected resource presenting token 0x...05.
  6. The resource compares 0x...05 against its stored high-watermark 0x...07, rejects the write.

The point: coord cannot prevent step 5 — A has no way to know locally that its session expired. The resource-side check in step 6 is the only closure (P5); a Lock API that returns no token cannot close this hole, which is why one is never shipped (§19.2).

8.5 Wire protocol framing

Request  frame:  | 4B length (LE) | 1B opcode | payload (bincode) |
Response frame:  | 4B length (LE) | 1B status | payload (bincode) |
Reconnect frame:  session_id(8B) | password(16B) | last_seen_zxid(8B)
                  | watch_count(2B) | watches[]: (path_len(2B), path,
                  last_seen_zxid(8B), kind_mask(1B))

Opcodes: 0x01 Create, 0x02 Delete, 0x03 SetData, 0x04 GetData, 0x05 GetChildren, 0x06 Exists, 0x07 SetAcl, 0x08 Sync, 0x09 Heartbeat, 0x0A Connect, 0x0B Reconnect. Status codes mirror the coord-core::error::Error enum (§11.7): 0x00 Ok, 0x01 NoNode, 0x02 NodeExists, 0x03 BadVersion, 0x04 NotEmpty, 0x05 NoAuth, 0x06 SessionExpired, 0x07 ZnodeTooLarge, 0x08 NotLeader, 0x09 LimitExceeded.

8.6 WAL and snapshot record layout

WAL record:      | 4B length (LE) | 4B CRC32C(payload) | bincode(LogEntry) |
LogEntry:        term(8B) | index(8B) | Mutation (§11.6)

Snapshot file:    | 16B magic "COORD-SNAP-V1\0\0\0" | 8B snapshot_index
                  | 8B snapshot_term | 8B namespace_len
                  | namespace bytes, chunked 1 MiB each, per-chunk CRC32C
                  | 8B sessions_len | session-set bytes, chunked, per-chunk CRC32C
                  | 4B file-level CRC32C of all preceding bytes

LogEntry carries the Mutation enum (§11.6) that the state machine applies deterministically (I8). Chunked per-record and per-chunk CRC32C let recovery skip and log a single corrupted unit instead of discarding the whole file.

8.7 Malformed-input example

A client sends a Create request whose declared 4B length field is 40 bytes but only 12 bytes follow before the connection closes. coord-net::frame reads the length prefix, attempts to read 40 bytes, hits EOF at byte 12, and returns FrameError::Truncated without touching the namespace or Raft — the connection is dropped, no Mutation is proposed, and the fuzz target wire_decode (§27) exercises exactly this class continuously. A second malformed case: a Create payload that bincode-decodes structurally but names a path containing .. — Path::parse (§11.2) rejects it at construction with Error::InvalidPath before it ever reaches Namespace::create, so no zxid is allocated for a request that was never going to succeed (§13.4 pitfall).

8.8 Failure-path example

A client issues set_data("/config/x", ...) to the current leader; the leader appends the entry, begins replicating, then crashes before a majority acknowledges. The client's request times out; its SDK (§18) retries the identical request_id against the new leader (elected per §16.5). Two sub-cases: (a) the crashed leader's entry never reached a majority — it is truncated from the log during the new leader's term, the retry proposes fresh, and the write lands exactly once; (b) the crashed leader's entry did reach a majority before the crash — it is already committed, the new leader has it in its log, and the retry is recognized as a duplicate via the pending_requests de-duplication map (§16.3) and returns the original response without re-applying. Both sub-cases preserve I1 and I9; neither double-applies nor silently drops the write.

Design principles (§6)

  • Linearizable writes are the contract. Every mutating operation (create, delete, set_data, set_acl) goes through Raft and is applied in commit order. Tradeoff: every write pays at least one round-trip to a majority. Operational implication: write latency has a floor equal to the slowest-of-majority RTT. Violation: two concurrent writers observe different orderings — the conformance suite's linearizability checker (§27) catches this before it reaches production.
  • Sequential-consistency reads with explicit sync() for linearizability. A follower-local get_data is sequentially consistent (Lamport 1979) but may be stale; sync() promotes it. Tradeoff: default reads are fast but can return stale data. Operational implication: any client logic that needs freshness must call sync() explicitly — a documented, not implicit, cost. Violation: omitting sync() before a leader-only write check reintroduces split-brain (§6 P12).
  • Sessions are the truth-source for liveness, not TCP connections. A session is a server-side lease independent of any one TCP socket. Tradeoff: a client can appear "gone" for up to the full session timeout before ephemerals are released. Operational implication: short timeouts release resources faster but risk false expiry under transient GC pauses. Violation: treating disconnect as instant failure causes premature ephemeral deletion and false leader-election churn.
  • Ephemeral nodes tie state to sessions. An ephemeral znode's ephemeral_owner field binds it to exactly one session; ExpireSession atomically removes every znode that session owned. Tradeoff: no independent per-znode TTL — lifetime is entirely session-derived. Operational implication: there is no garbage collector to tune; the deletion is part of the linearizable log. Violation: a non-atomic cleanup leaves dangling protected-resource ownership no replay can reconstruct (§7 I2).
  • Fencing tokens are non-negotiable. Every successful lock acquire returns a monotonic 64-bit fencing token; the protected resource MUST check it. Tradeoff: requires the resource owner to add one comparison — a small but mandatory integration cost. Operational implication: a RawLock API without a token is never shipped. Violation: skipping the check reproduces the exact Kleppmann 2016 GC-pause outage (§8.4, §19).
  • The hierarchical namespace is not a filesystem. Znodes carry whole-value data (≤ 1 MiB, ADR-06) and metadata; no streaming, append, or offset access. Tradeoff: large or growing payloads must be chunked by the application. Operational implication: get_data/set_data are O(payload size), never O(1) partial updates. Violation: an application that treats a znode as a log or a stream will hit ZnodeTooLarge and lose data if it doesn't chunk (§7 I11).
  • Watches are one-shot. A watch fires exactly once, then must be re-armed. Tradeoff: clients must implement fire-and-refetch loops correctly (§15.6 pitfall). Operational implication: server-side watch memory is bounded by design, not by luck. Violation: a naive while true: watch; wait loop has a race window that silently drops updates.
  • ACLs are per-znode, evaluated on every operation, never inherited. Tradeoff: no POSIX-style inheritance convenience; every znode's ACL is explicit. Operational implication: set_acl takes effect immediately with no cache-invalidation lag. Violation: client-side ACL caching produces stale grants after set_acl commits (§7 I7).
  • Reconfiguration is part of the protocol, not bolted on. Adding or removing a replica goes through the same Raft log using joint consensus (Ongaro thesis, section 6). Tradeoff: reconfiguration is slower than a naive single-step add. Operational implication: there is no "manual" config change that bypasses Raft. Violation: the single-server-addition shortcut has a known partition-induced disagreement bug (Howard et al. 2015) — this design forbids it (§24 FM-3).
  • Storage durability is snapshot + WAL, with per-record CRC32C. Tradeoff: every WAL append pays a CRC computation and an fsync. Operational implication: corrupted records are detected and the WAL truncated, never silently skipped. Violation: skipping the CRC check lets a single bit-flip propagate into a state-machine divergence no later Raft check can catch (§7 I10).
  • The 1 MiB max-znode-size cap is load-bearing, enforced three times. Tradeoff: legitimately large payloads must be split by the application, adding client-side complexity. Operational implication: the cap is checked at the API boundary, the Raft-proposal boundary, and the snapshot-chunk boundary — deliberately redundant. Violation: single-point enforcement lets a bug in one layer let an oversized entry reach Raft batching or snapshot streaming and OOM a replica (§7 I11).
  • sync() is specifically a read-linearization barrier, not a general fence. Tradeoff: it cannot be used as a generic distributed barrier (that's the dedicated Barrier recipe, §20.3). Operational implication: documentation must distinguish the two explicitly. Violation: confusing them produces code that assumes ordering guarantees sync() does not provide.
  • Conformance is the contract. The Jepsen-style harness (§27) gates the Sealed milestone: linearizability on writes, sequential consistency on follower reads, lock correctness under partition, watch-delivery guarantees under reconnect. Tradeoff: a 30-day soak and a 30-day fuzz canary add real calendar time before Sealed. Operational implication: a conformance regression is a hard merge block, not a warning. Violation: shipping without it is exactly how the ZooKeeper/etcd Jepsen reports (Kingsbury 2013+) found real production bugs.
  • Deterministic serialization everywhere in the replicated state. Every serializable type uses BTreeMap, never HashMap. Tradeoff: marginally slower map operations than a hash table. Operational implication: any two replicas that applied the same log produce byte-identical snapshots — a cheap correctness check. Violation: one HashMap in a serializable type makes cross-replica snapshot comparison useless and can mask real divergence (§7 I8, §24 FM-6).
