1. Goal & Scope

Oneiros ("Oneiros — The Dream Engine") is a real-time, multi-modal generative-media streaming system that composes a continuous, unrepeatable audiovisual narrative for exactly one viewer per session, drawn from a persistent per-user world model, dispatched under a hard per-scene latency/cost budget, and gated by a hard safety envelope for sleep and child-directed contexts. The system has five load-bearing subsystems: the Composer (LLM-driven scene planner and world-coherence engine), the Modality Adapter Bus (pluggable renderers — text, image, music, video, voice — behind one interface), the Persistent World Store (PWS, per-user encrypted durable state), the Streaming Runtime (a latency-budgeted scene scheduler that keeps generation ahead of playback), and the GPU Orchestration Pool (multi-provider inference routing under a cost ceiling). A Safety Classifier Ensemble gates every adapter output before delivery. The wedge domain is sleep/bedtime narrative (insomniacs, meditators, parents); the engineering problem — soft-real-time multi-modal scheduling over heterogeneous, cost-variable, latency-variable generative providers, with persistent stateful coherence and a non-bypassable safety gate — is general.

Phase-0 deliverable (numbered):

  1. packages/schema — Core Schema & Types (World, Character, Scene, Asset, Stream, Seed) at schema v1.0.0 (§11).
  2. packages/composer — deterministic Composer stub: scene planning from world + vibe via fixture-driven responses, no live LLM call yet (§12).
  3. packages/adapter-core — ModalityAdapter interface, capability registry, conformance-harness skeleton (§12, §15).
  4. packages/pws — Persistent World Store client against a local Postgres fixture database (§12, §13).
  5. services/scheduler-svc — single-scene scheduler (no cross-scene parallelism yet) plus a deterministic simulator with one assertion per invariant in §7 (§12).
  6. tools/conformance-runner — CLI driving the adapter conformance suite (§26).

System boundaries. Provides: scene planning, world persistence, modality dispatch under budget, safety gating, edge caching, cost telemetry, cancellation. Delegates: the generative inference itself (LLM completion, diffusion image synthesis, music/video generation) to external frontier HTTP APIs or self-hosted GPU pools via the Adapter Bus — Oneiros trains no foundation model. Does not provide: viewer-facing editing tools, synchronous multi-viewer co-streaming, general creative tooling, chat-with-character dialogue, server-side recording for re-broadcast.

Non-goals. A recommendation/retrieval system; a social network; a general text-to-video authoring tool; a native mobile client (deferred, see Deferred Features Register).

Deployment model. Multi-region stateless Edge/API tier; a regional Postgres primary with read replicas for the Persistent World Store; S3-compatible object storage for large prose/asset blobs; a CDN edge cache; a GPU Orchestration Pool routing across frontier HTTP APIs and self-hosted GPU pools.

Target users/operators. Viewers: consumer sleep/meditation/bedtime-story personas, one per session. Operators: the engineering team running the Edge/API tier, the GPU Orchestration Pool, and the weekly safety-classification review.

What later phases unlock. Video modality and continuous long-form streaming (§21); higher-fidelity mood conditioning via biometric input (deferred, see Deferred Features Register); licensed style packs, seed-sharing, and a creator tier (all deferred, see Deferred Features Register).

Language: TypeScript 5.x end-to-end for the control plane (web app, Composer, Scheduler, PWS client, adapter wrappers); Python 3.12 confined to self-hosted-model adapter processes. Rationale: a single control-plane language minimizes schema drift across four services that all consume packages/schema directly (ADR-01); Python is required only where an adapter wraps a PyTorch inference server, and that is a process boundary, not a shared address space, so the heterogeneity costs nothing at the contract layer. Rejected: full-stack Python — weak static-type guarantees across a 40+-type shared schema are the dominant source of contract drift in comparable systems (ADR-01); full-stack Rust — the adapter layer is I/O-bound HTTP orchestration, not CPU-bound, and the 2026 frontier-provider SDK ecosystem is TypeScript/Python-first (ADR-01); Go — no first-party SDKs for the frontier providers used at Phase 1, and 2026-era Go generics were materially worse than TypeScript for a large shared schema (ADR-01).

Prerequisites. Soft-real-time deadline-aware scheduling; LLM tool-use / function-calling patterns; streaming protocols (WebSocket, HLS); envelope-encryption key management; content-safety classification pipelines; multi-provider cost-aware routing.

Estimated timeline. Phase 0: 3 weeks. Phases 0–9 (full system to the Phase 9 exit criteria, §21.4): ≈ 14 months.

Deferred features (full detail in Deferred Features Register): native mobile client PhaseDeferred("§1"); biometric-conditioned pacing beyond a wearable HR band PhaseDeferred("§21"); licensed style packs PhaseDeferred("§3"); seed-sharing PhaseDeferred("§3"); creator tier PhaseDeferred("§3").

2. Why Build This

Unique systems knowledge. Building Oneiros forces mastery of four things that rarely appear together: (a) soft-real-time scheduling over generative-inference calls whose latency and cost are provider-controlled, not self-controlled; (b) maintaining long-lived narrative/state coherence against a stochastic LLM planner; (c) a non-bypassable safety-classification gate on machine-generated multi-modal output; (d) multi-provider cost arbitrage where the "backend" is itself a fleet of black-box foundation models with independent pricing curves.

Why it matters architecturally. Generative-media pipelines are becoming the 2020s successor to the 2010s streaming-video problem (Netflix, YouTube): instead of scheduling bytes from a fixed library, the scheduler dispatches inference calls whose output does not exist until requested. Scheduling and caching techniques from adaptive-bitrate streaming transfer directly, but the correctness surface is larger: content is generated, not retrieved, so safety and provenance become architectural, not editorial, concerns.

Engineering muscles built. Deadline-aware multi-modal dispatch; event-sourced persistent state under a single-writer invariant; classifier-in-the-critical-path pipeline design; multi-provider circuit-breaking and cost-aware routing — each transfers directly to any soft-real-time, trust-boundary-crossing, or multi-backend-arbitrage system elsewhere in this portfolio.

Calibration value. Oneiros calibrates judgment on: when to trust a stochastic component (the Composer) inside an otherwise deterministic system; how to bound an unbounded cost surface (GPU inference) with hard invariants rather than after-the-fact billing alerts; how to design a safety gate that fails closed under adversarial and organic failure alike.

What Mastery Looks Like

  • Deadline-aware multi-modal scheduling: design a scheduler that keeps ≥1 scene ahead of playback under heterogeneous adapter latency, proven in Phase 5 (§17).
  • Persistent narrative coherence: maintain character/world identity across an unbounded scene count without schema-breaking drift, proven in Phase 1–2 (§13–§14).
  • Non-bypassable safety gating: build a classifier-in-the-critical-path pipeline with measurable false-negative/false-positive rates, proven in Phase 6 (§18).
  • Multi-provider cost arbitrage: route inference across providers to hit a ¢/stream-hour ceiling with graceful degradation on provider failure, proven in Phase 7 (§19).
  • Cache-driven cost amortization: design an edge cache that measurably lowers ¢/SH on session resume, proven in Phase 8 (§20).
  • Cancellation-correct billing: guarantee that skipped/cancelled generative work reclaims GPU cost within a bounded window, proven in Phase 5 and Phase 7 (§17, §19).
  • Continuous long-form generation: stitch discrete generative calls into a seamless multi-minute stream, proven in Phase 9 (§21).

Viewer Browser (untrusted): submits vibe input, plays the emitted scene stream, never talks to model providers or another user's world directly.

Edge/API Tier (trusted): owns authentication, session lifecycle, and every cross-user isolation check (I12). Hosts the Composer and Streaming Runtime.

Composer: the sole writer to the Persistent World Store (P1); plans N scenes ahead from world state + vibe; single-threaded per session (I1).

Persistent World Store: per-user encrypted durable state — Worlds, Characters, Threads, Vibe history — schema-versioned and forward-migrating only (P8, I9).

Scene Scheduler / Streaming Runtime: dispatches modality-adapter calls in parallel for the next scene while the current scene plays; enforces the buffer-ahead invariant (I7) and the latency budget (§4).

Modality Adapter Bus: pluggable adapters — text, image, music (Phase 3–4), video (Phase 9); voice deferred (Deferred Features Register) — behind one interface (§11); each independently swappable (P2) and independently health-checked.

Safety Classifier Ensemble: gates every adapter output before it reaches the cache or the viewer (P4, I3); applies the strictest tone envelope in sleep mode (I4).

GPU Orchestration Pool: routes each adapter call across frontier APIs and self-hosted pools to hold ¢/SH inside the phase ceiling (P9, §4); reclaims cost on cancellation (I11).

CDN / Edge Asset Cache: caches classified assets for resume and repeat-hit amortization (§20).

Style Pack Engine / Seed-Sharing / Creator Studio (deferred, dotted boxes not drawn above — see Deferred Features Register): planned consumers of the same Adapter Bus and PWS once licensed and social features are in scope.

6. Design Principles

  1. P1 — Single-writer worlds. The Composer is the sole writer to a world's persistent state, serialized per-session by the session orchestrator. Tradeoff: no concurrent multi-agent editing of one world. Operational: write contention shows up as scheduler queue depth, never DB lock contention. Violating it: two Composer instances writing the same world causes character-identity collapse (I2).
  2. P2 — Adapters are swappable, not bespoke. Every modality adapter implements one bounded interface (§11); provider swap is a deploy, not a migration. Tradeoff: the interface caps how much provider-specific capability can be exposed. Violating it: a provider price hike becomes existential (R-class risk).
  3. P3 — One viewer, one stream. No shared mutable state across sessions; no synchronous co-viewing. Tradeoff: no live shared streams. Operational: horizontal scaling is embarrassingly parallel per session. Violating it: cross-session state leakage is a privacy incident (T3).
  4. P4 — Classify the output, not the plan. Safety classification runs on every adapter output before delivery, never on the Composer's internal plan alone. Tradeoff: added latency inside the scene budget. Violating it: an unclassified plan can still emit unsafe adapter output.
  5. P5 — Defense in depth for sleep mode. The sleep-mode tone envelope is enforced at three independent layers: Composer planning constraint, adapter routing constraint, output classifier. Tradeoff: triple-checked cost. Violating it (single-layer enforcement): one layer's bug becomes a production safety incident with no backstop.
  6. P6 — Always one scene ahead. The scheduler keeps ≥1 fully rendered scene ahead of playback (I7). Tradeoff: wasted GPU spend on unplayed scenes if the viewer exits early, bounded by cancellation (P10). Violating it: visible stutter breaks the immersion contract.
  7. P7 — No anonymous assets. Every generated asset carries provenance (prompt hash, seed, model version). Tradeoff: extra columns per asset row. Violating it: cannot answer "what did we show this viewer" after the fact.
  8. P8 — Forward-only schema evolution. Schema changes are additive; no breaking change to a persisted world. Tradeoff: schema accretion over years, mitigated by dual-version support (I9). Violating it: a viewer's multi-year world becomes unreadable.
  9. P9 — Cost is a gated metric. ¢/Stream-Hour is checked in CI like a test, not reviewed after the invoice arrives. Tradeoff: slower feature velocity near a ceiling. Violating it: silent cost creep triggers phase kill-criteria (§34-adjacent risk).
  10. P10 — Cancellation reclaims cost. Cancelling an in-flight adapter call must reclaim ≥95% of its GPU cost within 2 s (I11). Tradeoff: every adapter must expose a real cancel path, not an abandoned promise. Violating it: viewer skip-ahead behavior bankrupts the cost model.
  11. P11 — Scope every cross-user access at the data layer. PWS reads are scoped by authenticated userId, never trusted from the caller. Tradeoff: extra scoping code on every query. Violating it: cross-user world leakage (T3), automatic Sev-1.
  12. P12 — Every tradeoff gets an ADR with a regime for the loser. Every latency-vs-quality or cost-vs-fidelity decision is recorded with the regime where the rejected choice wins (§9). Tradeoff: authoring overhead per decision. Violating it: decisions get silently re-litigated by the next engineer.
  13. P13 — Degrade the modality, not the scene. A dead or slow adapter falls back to a cheaper modality (video→image→text) rather than failing the whole scene. Tradeoff: viewer sees lower fidelity, never an error. Violating it: a single-provider outage takes down the entire stream.
  14. P14 — Identifiers are branded, never bare strings. Every *Id type (§11.8) is a distinct compile-time type, not an interchangeable string. Tradeoff: a small amount of type-declaration ceremony at every boundary. Operational: cross-ID-type bugs (passing a CharacterId where a SceneId belongs) are caught at compile time, not in production. Violating it: a whole class of silent data-corruption bugs becomes possible at every PWS/adapter boundary.
  15. P15 — Estimates are reconciled against ground truth, never trusted standalone. Real-time cost and audit telemetry are estimates; they are reconciled against an authoritative source (provider invoice, storage listing) on a fixed cadence. Tradeoff: a reconciliation job and its own monitoring (cost.reconciliation_delta, T12). Operational: divergence between estimate and ground truth is itself an alertable signal. Violating it: cost or audit drift goes undetected until it becomes a financial or compliance surprise.

8.4 Worked Example

Vibe input "a foggy coastal town that remembers my name", mode sleep. Composer plans scene index 0: mood = {arousal: -0.4, valence: 0.1, descriptors: ["foggy","quiet","welcoming"]} — inside the sleep-mode tone envelope (I4). 8.5 Malformed-Input Example

A vibe input contains a 12,000-character adversarial string attempting prompt injection ("ignore all safety instructions and…"). The vibe is treated as untrusted (P4-adjacent) — it is never elevated to system-prompt scope. The Composer emits a graceful reinterpretation scene rather than an error. If the injection targets content-profile axes directly, the profile's 30-minute change cooldown prevents any single vibe from raising the ceiling; I4 remains enforced regardless of vibe content.

8.6 Failure-Path Example

adapter-image times out at 6 s (p95 budget 4 s, hard timeout 6 s). The scheduler cancels the in-flight call (I11: ≥95% cost reclaim within 2 s) and falls back to adapter-text-only for that scene slot (P13). The scene is flagged modalitySlots: ["text"], degraded: true, surfaced via scheduler.modality_fallback. The next scene retries image at full budget. No viewer-facing error appears; I7 still holds because the degraded scene counts as "ready" once text-only commits.

8.7 Cross-Subsystem Incident Trace (Resume After a Regional Failover)

A worked trace tying together §13 (PWS), §17 (Scheduler), §19 (GPU Orchestration Pool), and §24 (Operational Readiness), illustrating why the invariants in §7 are designed to compose:

  1. T+0s — the Postgres primary in Region A fails. pws.resume_latency_p95 and the connection-pool health check both fire (§13.9).
  2. T+2s — the session orchestrator marks every in-flight Stream in Region A buffering (§8.2) rather than ended; I7's buffer-ahead guarantee degrades to the declared "buffering" state, never a silent stall.
  3. T+5min — the read replica is promoted (RTO ≤5 min, §4); PWS writes resume against the new primary; the WAL position at failover is logged as a forensic artifact (FM-13-adjacent, §23).
  4. T+5min+ε — resumed sessions re-enter active (§8.2); the Composer's single-writer lock (I1) re-acquires cleanly because the lock itself lived in the (now-promoted) database, not in process memory.
  5. T+5min+1s — the Scheduler re-dispatches the scene that was rendering at failover time; because that scene was never committed (§8.3), I5's monotonic-no-gap invariant is untouched — the replay resumes at the same scene index, not a new one.
  6. T+5min+3s — the GPU Orchestration Pool's circuit breakers (§19) are unaffected by the database failover (a different trust boundary, §3), so in-flight adapter calls that survived the failover window complete normally; any that did not are cancelled and reclaimed per I11.

This trace is why I1 (single-writer), I5 (scene-sequence monotonicity), I7 (buffer-ahead-or-declared-buffering), and I11 (cancellation reclaim) are independent invariants rather than one combined "session health" check: each one fails, is detected, and recovers on its own timeline, and the sim-harness (§12, §26) asserts each independently for exactly this reason.

8.8 Worked Example — Video Session Cold Start (Phase 9)

A second worked example, chosen because video's cost/latency profile (§4, §32 item 12) makes cold start qualitatively different from the Phase 1 text+image+music case in §8.4:

  1. Viewer opens a world with licensedStylePackId unset (no style pack, out of scope per the Deferred Features Register) and submits vibe "a rain-soaked cyberpunk alley, something is following me", mode free.
  2. Composer plans scene index 0 with mood = {arousal: 0.3, valence: -0.2, descriptors: ["tense","neon-lit","rain"]} — outside any sleep-mode rail since mode !== "sleep" (I4 does not apply here).
  3. Scheduler dispatches adapter-video with no prior clip to stitch from (§21.8 edge case): the stitching layer falls back to a static establishing image (P13, video→image degradation) for this first scene only.
  4. adapter-video renders the first real clip against the establishing image as its sole conditioning input (no PersistentCharacter.appearance.seed yet, since no character has appeared); latency lands at the p95 budget of 30 s (§4, M5).
  5. From scene index 1 onward, the stitching layer conditions each clip on the previous clip's last frame plus any now-established character seeds, and the streaming runtime's 30 s pre-warm buffer (§21.2) is fully established, hiding all subsequent cold-start-class latency from the viewer.

This example is why Phase 9's Acceptance Criteria (§21.4) are measured over a 30-minute cohort rather than a single scene: the first-scene cold start is expected and budgeted for, while the cost/continuity story is only meaningful once the buffer has stabilized.

  • Clock skew between sim-harness host and Postgres — mitigated by ADR-23 (monotonic clock for deadline arithmetic; wall-clock only for stored timestamps).

Containment: the fixture DB is a disposable Docker volume, reset between CI runs. Recovery: make reset-fixtures. Operator visibility: CI log shows the exact scene index at crash time.

Containment: the harness treats a fixture-parse failure as a hard CI failure, never a skipped test. Recovery: regenerate fixtures from the current schema via scripts/regen-fixtures.ts. Forensic artifact: the schema diff correlated with the first failing fixture.

13.7 Performance Concerns

  • Read-replica lag (RPO ≤ 30 s, §4) can serve a stale World to a just-resumed session; mitigated by routing the first read after a resume gap > 5 min to the primary.
  • Envelope-decrypt cost on every World read adds a fixed per-call overhead; mitigate by caching the decrypted data-key for the session lifetime (§13.6) rather than re-invoking the KMS on every scene commit.

13.8 Edge Cases

  • A world at exactly the snapshot boundary (scene 50 itself).
  • A resume request arriving mid-snapshot-write — must block, not race.
  • A schema-major-version bump landing while 10,000 worlds are mid-session — canary on 1% of worlds first.
  • A KMS outage during resume — fail closed, no plaintext fallback (I10).
  • A user deletes their account mid-session (soft-delete grace period) — the active Stream must be allowed to end gracefully rather than having its PWS access revoked mid-scene, with the soft-delete timer starting only after Stream.endedAt is set.

13.9 Failure Analysis

  • Postgres primary failure mid-session. Detection: connection-pool health check. Containment: promote the read replica within RTO ≤ 5 min (§4). Recovery: in-flight sessions at failover are marked buffering (§8.2) and resume against the new primary. Forensic artifact: WAL position at failover, logged for postmortem.
  • KMS master-key compromise (suspected or confirmed). Detection: anomalous decrypt-volume alert or external disclosure. Containment: immediate key rotation, all active sessions using the compromised key forced to re-authenticate. Recovery: per-user data keys are re-wrapped under the new master key in a background job (I10 unaffected — data keys themselves were never exposed). Forensic artifact: KMS access log for the suspected compromise window.

13.10 Operational Notes

  • Dashboards track pws.resume_latency_p95, pws.snapshot_overhead_ratio, kms.plaintext_key_egress (must stay 0). Schema migrations are additive-only (P8), so a service rollback never requires a schema rollback — only a code rollback.

14. Phase 2 — Composer & Scene Planning Engine

14.1 Objectives

  • Replace the Phase-0 rule-based Composer stub with a live LLM-backed planner; establish world coherence and character continuity over an extended scene run.

14.2 Detailed Implementation Steps

  • packages/composer wraps a frontier LLM completion API behind the Composer interface (§11.5); the transformer backbone rationale follows Vaswani et al. (2017), applied here to justify a single-model planner over an ensemble.
  • System prompt is hardened per Ouyang et al. (2022) RLHF-alignment findings: vibe input is never elevated to system-prompt scope (P4-adjacent, mitigates prompt injection, §8.5).
  • planScenes produces N=3 scenes ahead per call, referencing existing CharacterIds from World.characters to enforce continuity (I2); pacing follows Murch's "rule of six" (Murch 2001) — no more than one major tonal shift per 6 scenes in sleep mode.
  • ingestSceneCompletion writes WorldDeltas back through the single-writer path established in Phase 1 (P1, I1).
  • The Composer's LLM provider version is pinned explicitly in configuration (never tracked as "latest"), anticipating the model-upgrade failure mode documented in §14.9.

14.3 Deliverable

A 50-scene fixture run in which the same three characters (by CharacterId) appear, are referenced consistently by name/archetype, and the world's cosmology prose remains internally consistent.

14.4 Acceptance Criteria

  • Character-continuity check: 0 identity-field mismatches (I2) across a 50-scene fixture run, verified against fixtures/character-continuity-50.json.
  • Composer planning latency p95 ≤ 1.5 s/scene (§4), measured over 500 planning calls.
  • Prompt-injection corpus (fixtures/injection-corpus-200.json, 200 adversarial vibes): 0 vibes elevate to system-prompt scope.

14.5 Conformance Fixtures

  • fixtures/character-continuity-50.json — 50-scene run, 3 characters. Expected: 0 identity drift.
  • fixtures/injection-corpus-200.json — 200 adversarial vibe strings. Expected: 0 system-prompt elevations, 0 tone-envelope breaches.
  • fixtures/empty-world-bootstrap.json — a brand-new world with no prior state. Expected: Composer synthesizes cosmology + 3 starting characters + 1 location.
  • fixtures/model-version-pin-regression.json — a fixture re-run against a newer (unpinned) provider model version. Expected: character-continuity and pacing scores must not regress relative to the pinned baseline (§14.9).

14.6 Pitfalls

  • Character drift via prose paraphrase — the LLM renames a character mid-run without a logged world-drift event, silently violating I2; debug via the identity-diff validator (§7); recovery: revert to the last snapshot and re-plan with an explicit continuity reminder injected into the prompt.
  • Over-long context causing latency blowout — as vibeHistory and memories grow, planning latency creeps past the 1.5 s p95 budget; signal: composer.planning_latency_p95 trending upward; recovery: summarize memories into condensed records past a length threshold (full hierarchical-memory design deferred, see Deferred Features Register).
  • Prompt injection via nested vibe fields (e.g. a vibe that itself quotes a fake "system:" line) bypassing the naive untrusted-input filter; recovery: strip role-like tokens from vibe text before injection, verified by the 200-item corpus.
  • Pacing rule applied mechanically rather than semantically — a literal "one shift per 6 scenes" counter (Murch's rule, §5) fires a tonal shift even when the narrative calls for stability; recovery: treat the rule-of-six as a ceiling on shift frequency, not a scheduled event, per Murch's original framing (2001, ch. 1).

14.7 Performance Concerns

  • LLM round-trip is the dominant term in planning latency; mitigate with response streaming where the provider supports it, and by planning N=3 scenes per call rather than N=1 to amortize the fixed per-call overhead.
  • vibeHistory/memories context growth (§11.6) increases prompt token count linearly with session age; monitored as a leading indicator for the hierarchical-memory work tracked in the Deferred Features Register (§35).

14.8 Edge Cases

  • A vibe requesting a scene that would exceed the sleep-mode tone envelope — Composer must silently redirect, never surface the rail to the viewer (I4).
  • A world with 0 threads (brand new) — planScenes must not reference a non-existent ThreadId.
  • LLM provider returns a malformed (non-JSON) plan — Composer retries once with a stricter schema-constrained prompt, then falls back to the Phase-0 rule-based stub for that single scene.
  • Two vibes submitted in rapid succession (double-click) — the second is queued behind the in-flight planScenes call, never interleaved (I1).
  • A vibe in a language the LLM provider handles poorly — Composer degrades to a best-effort plan rather than rejecting the session outright, flagged degraded: true for observability (§14.10).

14.9 Failure Analysis

  • LLM provider outage mid-session. Detection: health() check on the Composer's provider client fails. Containment: session enters buffering (§8.2), not ended. Recovery: fail over to a secondary frontier provider (locked in Phase 7, §19); until then, Phase 2 falls back to the Phase-0 rule-based stub for continuity. Forensic artifact: the last successfully committed ScenePlan, logged for replay.
  • A model version upgrade from the LLM provider silently changes output style/tone distribution. Detection: mood-fidelity and pacing regressions in the conformance suite (§26) even though no Oneiros code changed. Containment: pin the provider's model version explicitly rather than tracking "latest." Recovery: re-run the character-continuity and injection-corpus fixtures (§14.5) against the new version before opting in. Forensic artifact: side-by-side scene-plan diff, old vs. new model version.

14.10 Operational Notes

  • Metrics: composer.planning_latency_p50/p95/p99, composer.identity_drift_flagged, composer.injection_elevation_attempts (must stay 0). System-prompt changes require an ADR (P12) and are never auto-merged.
  • The LLM provider's model-version pin is recorded in /version (§27 version stamping) alongside the service's own semver, so an incident review can immediately see whether a model bump correlates with a regression.

15.6 Pitfalls

  • Seed reuse producing near-duplicate, not consistent, images — over-reliance on a fixed seed collapses visual variety; recovery: seed pins identity features only, style/pose still varies per scene.
  • Health-check false positives — an adapter reporting healthy while its underlying provider is rate-limited; signal: adapter.render_error_rate diverges from adapter.health_report; recovery: fold real error rate into the routing decision, not just the health poll.
  • Cancellation race — a cancel arriving after the adapter has already committed to billing (provider-side) the full call; recovery: track a "point of no return" per provider and stop issuing cancels past it (documented per-provider in docs/adr).
  • Reference-image staleness — a character's pinned reference asset (§11.1 appearance.referenceAssetIds) is evicted from the edge cache (§20) before Phase 8 ships, forcing a costly regeneration on every scene; recovery: pinned reference assets are exempt from LRU eviction regardless of cache pressure (a distinct retention class from ordinary scene assets).

15.7 Performance Concerns

  • Image-adapter cold start (first call after idle) adds ~1.5 s; mitigate with preWarm() hints issued by the scheduler one scene ahead (P6-adjacent, full scheduler logic in Phase 5).
  • Reference-image conditioning (§15.2) adds an extra payload to every character-bearing request; keep pinned reference assets small (downsampled conditioning copies, not the full-resolution delivered asset) to avoid inflating per-call latency.

15.8 Edge Cases

  • A character with no referenceAssetIds yet (first appearance) — adapter must synthesize a fresh reference and persist it as the new pin.
  • An image request during a provider-side content-policy rejection (provider itself blocks the prompt) — treated as a render() failure, triggers P13 modality fallback, not a crash.
  • A capability-registry entry for an adapter version that has since been deprecated — registry must reject routing to it, not silently degrade.
  • Two characters sharing visually similar appearance.descriptionProse (e.g. twins) — the consistency classifier (§15.4) must be evaluated per-CharacterId, never by prose similarity alone, to avoid conflating distinct characters.

15.9 Failure Analysis

  • Frontier image API returns HTTP 503 across a sustained window. Detection: adapter.health_report transitions unhealthy after 3 consecutive failures. Containment: routing shifts to the self-hosted fallback (ADR-14). Recovery: automatic re-routing back to primary once health recovers for 3 consecutive polls. Forensic artifact: the provider-response log for the 503 window.
  • The self-hosted fallback tier itself runs out of GPU capacity while the primary is also down (compound failure). Detection: both adapter.health_report unhealthy and self-hosted queue depth maxed. Containment: degrade to text-only for affected scenes (P13) rather than blocking the stream. Recovery: capacity-add on the self-hosted pool or wait out the primary's outage. Forensic artifact: correlated health/queue-depth timeline across both tiers.

15.10 Operational Notes

  • Metrics: adapter.render_latency_p50/p95/p99 per adapter id, adapter.cost_per_unit_measured, adapter.leaked_gpu_minutes. Adapter prompt-engineering changes require human review regardless of CI status (safety-adjacent).
  • Reference-image assets are tagged as a distinct retention class (§15.6) in services/audit-svc's inventory, so the Phase 8 cache-eviction policy can special-case them without a schema change.

16.1 Objectives

16.3 Deliverable

A 30-minute sleep-mode session runs a continuous, seamless ambient bed with mood shifting per scene, with zero audible loop seams on internal dogfood review.

16.4 Acceptance Criteria

  • Music adapter latency p95 ≤ 6 s/30 s loop (§4), measured over 500 calls.
  • Mood-fidelity classifier ≥ 0.75 accuracy across all 4 quadrants, fixtures/mood-quadrant-corpus.json.
  • Sleep-mode routing: 0 non-approved adapter versions selected across 1,000 sleep-mode scene dispatches (I4).

16.5 Conformance Fixtures

  • fixtures/mood-quadrant-corpus.json — 200 prompts across 4 quadrants. Expected: ≥ 0.75 classifier accuracy per quadrant.
  • fixtures/sleep-routing-1000.json — 1,000 sleep-mode scene dispatches. Expected: 0 non-approved routes.
  • fixtures/loop-seam-detection.json — synthetic crossfade boundary samples. Expected: 0 detectable amplitude discontinuities > −40 dB.
  • fixtures/gpu-pool-contention.json — simultaneous image and music demand on a shared pool partition. Expected: p95 latency for both stays within budget once dedicated partitioning (§16.6) is active.

16.6 Pitfalls

  • Tempo/key mapping saturating at extremes — very high arousal values clamp to the same output as moderate-high, losing fidelity; recovery: recalibrate the mapping table against the classifier's confidence curve, not a linear assumption.
  • GPU pool contention between image and music self-hosted models sharing a pool — manifests as both adapters' p95 latency degrading together; signal: gpu_pool.utilization correlated across adapter ids; recovery: dedicated pool partition per modality (locked in Phase 7, ADR-adjacent).
  • Sleep-mode routing bypass via a stale capability-registry cache — a just-deprecated non-approved adapter version still served from cache; recovery: registry cache TTL ≤ 30 s, matching the health-poll interval.
  • Crossfade window miscalibrated against real loop length — a loop rendered slightly short of 30s causes the crossfade engine to overlap into silence; recovery: the adapter reports its realizedDurationMs (§11.7 AdapterResponse) and the player crossfade window is computed from that measured value, never the requested value.

16.7 Performance Concerns

  • Self-hosted MusicGen inference is GPU-memory-bound; batch multiple scene requests per GPU tick where mood parameters are similar, bounded by the scene latency budget.
  • Crossfade computation runs client-side (§16.2); keep it off the main render thread on lower-end devices to avoid frame drops in the player UI during a mood transition.

16.8 Edge Cases

  • A mood request at the exact quadrant boundary (arousal = 0, valence = 0) — mapping table must have an explicit neutral-zone entry, not divide-by-zero on quadrant lookup.
  • Sleep mode enabled mid-session (viewer toggles it) — in-flight non-approved adapter calls must be cancelled and re-dispatched to approved adapters (I11 + I4 interaction).
  • Crossfade with a track shorter than the crossfade window (rare truncated-generation output) — player must pad with silence, not glitch.
  • A viewer's device audio output has no capability to play the delivered sample rate — the player negotiates a supported format at connect time, never assumes a single fixed output format.

16.9 Failure Analysis

  • Self-hosted GPU pool for adapter-music runs out of capacity during a demand spike. Detection: request queue depth exceeds a threshold. Containment: fall back to a pre-rendered ambient loop library (a bounded, pre-classified fallback set) rather than blocking the scene. Recovery: autoscale the pool (Phase 7 territory) or degrade to fewer music-conditioned scenes per session. Forensic artifact: queue-depth time series around the incident window.
  • The pre-rendered fallback library itself becomes stale or repetitive under sustained load. Detection: rising complaint rate / falling session length correlated with fallback-library usage rate. Containment: none automatic — this is a quality, not a correctness, degradation. Recovery: expand the fallback library's variety during the next content refresh cycle. Forensic artifact: fallback-usage rate correlated with session-length metrics.

16.10 Operational Notes

  • Metrics: adapter.mood_fidelity_score, gpu_pool.utilization (music partition), sleepmode.non_approved_route_attempts (must stay 0). Music-model version bumps go through the same conformance gate as any adapter (§26).
  • The player's crossfade window is computed from AdapterResponse.realizedLatencyMs/duration (§11.7), not the requested duration, closing the loop-seam pitfall (§16.6) at the data-contract level rather than in player-side heuristics.

17. Phase 5 — Streaming Runtime & Scene Scheduler

17.1 Objectives

  • Build the real Scene Scheduler / Streaming Runtime: parallel adapter dispatch, buffer-ahead guarantee (I7), WebSocket streaming protocol.

17.2 Detailed Implementation Steps

  • services/scheduler-svc implements SceneScheduler (§11.5): dispatches all of a scene's adapter calls in parallel while the prior scene plays (P6); watermark/windowing model per Akidau, Chernyak, Lax (2018) chs. 2–3 governs the buffer-ahead accounting.
  • WebSocket protocol events: scene-start, asset-ready (one per modality slot), scene-end, world-delta — versioned envelope, additive-only (P8-adjacent for the wire contract).
  • Bounded per-session dispatch queue, depth 3 (ADR-24); reject new plans when full rather than buffering unboundedly.
  • Deadline arithmetic uses the monotonic clock (ADR-23); a scene's deadline is derived from the current playback position, not wall-clock time, per Lamport's ordering discipline (Lamport 1978, I5).
  • Rolling-deploy drain logic hands off in-flight sessions to a peer instance rather than terminating them, keeping shutdown within the 15 s budget (§4) even under a full scheduler-fleet rollout.

17.3 Deliverable

A player session shows zero visible scene-to-scene gaps across a 30-minute run under nominal adapter latency; TTFF ≤ 8 s.

17.4 Acceptance Criteria

  • TTFF p95 ≤ 8 s (§4), measured over 200 session starts.
  • Buffer-depth gauge (I7) never reports "empty + not-buffering" — 0 silent-stall events across a 1,000-session load test.
  • Scene-to-scene visible gap: 0 s median across the same load test (fixtures/gapless-30min.json).

17.5 Conformance Fixtures

  • fixtures/gapless-30min.json — 30-minute session under nominal latency. Expected: 0 visible gaps.
  • fixtures/queue-overflow.json — a burst of vibe changes exceeding dispatch-queue depth 3. Expected: excess plans rejected, not buffered (ADR-24), viewer sees a graceful "still composing" state, not an error.
  • fixtures/deadline-clock-skew.json — a simulated wall-clock jump (NTP correction) mid-session. Expected: scheduling unaffected (monotonic clock, ADR-23).
  • fixtures/rolling-deploy-drain.json — a scheduler instance draining mid-session during a simulated rollout. Expected: session hand-off completes within the 15 s shutdown budget (§4), no dropped scene.

17.6 Pitfalls

  • Buffer accounting drift — the buffer-depth gauge undercounts a scene still rendering, showing false "empty" alerts; root cause: gauge updated on dispatch, not on commit; recovery: gauge increments only at committed state (§8.3).
  • Thundering-herd dispatch — all modality adapters for a scene fire simultaneously, causing a shared-dependency (e.g. KMS, §13) latency spike; recovery: stagger non-latency-critical calls (e.g. audit-log writes) outside the critical dispatch path.
  • WebSocket envelope version skew between an old cached player bundle and a newer server envelope; recovery: envelope carries a version field, older players ignore unknown fields (additive-only wire contract, P8-adjacent).
  • Monotonic-clock/wall-clock confusion at the deadline boundary — a scheduler component logs a deadline in wall-clock time for a human-readable dashboard, then accidentally compares it against a monotonic timestamp; recovery: the two clock domains are distinct types at compile time (never both plain number), enforced by the same branding discipline as §11.8.

17.7 Performance Concerns

  • Parallel dispatch fan-out (up to 4 adapters/scene) multiplies connection-pool pressure; size the adapter-bus HTTP connection pool to maxConcurrency × modalitySlots and monitor against the FD budget (§4, 8,192/instance).
  • The bounded dispatch queue (depth 3, ADR-24) trades a small amount of head-of-line latency for a hard ceiling on memory growth under a vibe-change burst; profiling confirms queue-wait time stays a minor contributor to TTFF (M1) relative to adapter render time.

17.8 Edge Cases

  • Viewer skips ahead past a scene still rendering — triggers cancellation (I11) and immediate re-dispatch for the target scene.
  • All adapters for a scene fail simultaneously (correlated provider outage) — scheduler must surface buffering, not silently repeat the last scene.
  • A scene's modalitySlots array is empty after all-adapter fallback exhaustion — scheduler emits a text-only placeholder rather than an empty scene.
  • A viewer reconnects (network blip) mid-scene — the scheduler replays already-committed StreamEvents from the current scene rather than re-dispatching adapter calls, since I5 guarantees the scene index hasn't moved.

17.9 Failure Analysis

  • Scheduler process crash mid-dispatch. Detection: process-supervisor health check. Containment: in-flight adapter calls are provider-side orphaned but bounded by their own timeout; on restart the scheduler resumes from the last committed scene index (I5), never replaying a committed scene. Recovery: session resumes in buffering state. Forensic artifact: the dispatch queue snapshot at crash time, logged via services/audit-svc.
  • A rolling deploy drains a scheduler instance while it holds several in-flight sessions. Detection: drain-timeout counter approaching the 15 s shutdown budget (§4). Containment: sessions not yet drained are handed off to another instance via the shared dispatch-queue state (not held hostage by the terminating process). Recovery: none needed if drain completes in budget; otherwise the session enters buffering and resumes elsewhere. Forensic artifact: drain-duration histogram per deploy.

17.10 Operational Notes

  • Metrics: scheduler.buffer_depth, scheduler.ttff_p95, scheduler.modality_fallback_count, scheduler.queue_rejections. Rolling deploys drain in-flight sessions gracefully (§4 shutdown/drain ≤ 15 s) rather than dropping connections.
  • Drain-duration histograms (§17.9) feed directly into the canary-analysis SLI set (§24), so a deploy that regresses drain time is caught by the automated canary halt before it reaches full rollout.

18. Phase 6 — Safety Classifier Ensemble & Audit Pipeline

18.1 Objectives

  • Build the non-bypassable Safety Classifier Ensemble (P4, I3) and the per-scene audit-log pipeline; certify the sleep-mode dual-classifier path (I4, P5).

18.2 Detailed Implementation Steps

  • packages/safety-classifier: dual-classifier ensemble — a general classifier plus a sleep-mode-specific classifier (ADR-16) — following the holistic undesired-content-detection approach of Markov et al. (2023).
  • Every adapter output routes through the ensemble before cache promotion or delivery (P4); a block decision triggers Composer replan (§8.3 blocked state), never a raw viewer-facing error.
  • services/audit-svc persists {prompts, adapter outputs, classifier decisions, adapter versions} per scene, retained 90 days, then aggregated (privacy default).
  • Adversarial corpus runner (tools/conformance-runner) executes a 1,000-prompt general corpus plus a 200-prompt sleep-mode subset before every release (§26).
  • The classifier ensemble's underlying model version is pinned per environment (staging vs. production), the same discipline as the Composer's LLM pin (§14.2), so a classifier-provider model bump is an explicit, conformance-gated event rather than a silent drift.

18.3 Deliverable

A release-gating CI job runs the full adversarial corpus and reports 0 sleep-mode false negatives; every committed scene has a complete audit record.

18.4 Acceptance Criteria

  • Sleep-mode adversarial corpus (200 prompts): 0 unsafe emissions reach committed state (§4 zero-tolerance gate).
  • General adversarial corpus (1,000 prompts): false-negative rate < 0.1% (fewer than 1 miss per 1,000).
  • Audit completeness: 100% of committed scenes have a non-null safetyAudit record (I8-adjacent for safety metadata).

18.5 Conformance Fixtures

  • fixtures/sleepmode-adversarial-200.json — 200 adversarial sleep-mode prompts. Expected: 0 pass-through.
  • fixtures/general-adversarial-1000.json — 1,000 general adversarial prompts. Expected: < 0.1% false negatives.
  • fixtures/audit-completeness-scan.json — a 10,000-scene sample. Expected: 100% non-null safetyAudit.
  • fixtures/classifier-model-pin-regression.json — the sleep-mode corpus (§18.4) re-run against an unpinned classifier model version. Expected: no score regression relative to the pinned baseline (§18.9).

18.6 Pitfalls

  • Classifier false positives collapsing immersion — an overly strict general classifier blocks benign scenes; recovery: a soft-warn tier (§11.2 safetyAudit.decision) nudges the Composer to replan mid-scene rather than hard-blocking, with weekly false-positive review.
  • Ensemble disagreement handled inconsistently — general classifier passes, sleep classifier blocks (or vice versa) with no defined precedence; recovery: sleep-mode classifier decision is authoritative whenever Stream.mode === "sleep" (explicit precedence rule, I4).
  • Audit-log write failure silently dropping records — a scene commits even though its audit write failed; recovery: audit write is part of the same transaction as the scene commit (I8-adjacent atomicity), a failed audit write blocks the commit.
  • Adversarial-corpus staleness — the 200-prompt sleep-mode corpus stops reflecting current adversarial technique because it was written once and never revisited; recovery: the corpus is versioned and appended to after every T9 evasion disclosure (§22), never treated as a frozen artifact.

18.7 Performance Concerns

  • The dual-classifier call adds latency inside the scene budget (§4); mitigate by running both classifiers in parallel (not sequential) and treating the ensemble as a single latency-budgeted hop.
  • Audit-log writes are transactionally atomic with the scene commit (§18.6, I8-adjacent) and therefore sit on the critical path; keep the services/audit-svc write itself sub-10ms (a local, indexed insert) so this required atomicity never becomes the dominant term in scene-commit latency.

18.8 Edge Cases

  • A scene with zero adapter outputs (all fell back to a placeholder) — still requires a safetyAudit record, classifying the placeholder itself.
  • Classifier service itself unavailable — scheduler must fail closed (block delivery, not pass through unclassified, I3), never fail open.
  • A borderline soft-warn scene repeated 3+ times in a row — escalate to a full block and flag for manual review rather than looping indefinitely.
  • A classifier model version bump changes score calibration such that historically pass-rated content would now soft-warn — the change is conformance-gated (§26) against the existing adversarial corpus before rollout, not discovered live in production.

18.9 Failure Analysis

  • Safety classifier service outage. Detection: health() failure on the classifier client. Containment: I3 forces the scheduler to halt delivery (fail closed) rather than deliver unclassified content — sessions enter buffering. Recovery: fail over to a secondary classifier deployment (a distinct provider/region) if configured; otherwise the stream halts until the classifier recovers. Forensic artifact: the outage window and every scene that entered buffering during it.
  • The sleep-mode-specific classifier degrades in accuracy after a silent upstream model change (if the classifier itself depends on a third-party model API). Detection: a scheduled re-run of the 200-prompt sleep-mode corpus (§18.4) shows a regression outside the release cycle. Containment: pin the classifier's underlying model version explicitly, mirroring the Composer's model-pinning discipline (§14.9). Recovery: roll back to the last known-good classifier model version. Forensic artifact: corpus-score time series independent of Oneiros's own deploys.

18.10 Operational Notes

  • Metrics: safety.unclassified_delivery (must be 0), safety.false_positive_rate, safety.block_rate by mode. Weekly internal safety review of flagged scenes; pen-test of classifier evasions before each major release from this phase onward.
  • The classifier's pinned model version is recorded alongside the Composer's (§14.10 pattern), giving incident review a single place to check both stochastic-component pins at once.

19. Phase 7 — GPU Orchestration Pool & Cost Telemetry

19.1 Objectives

  • Build multi-provider GPU/inference routing to hold ¢/SH inside the phase ceiling (P9, §4); wire cost telemetry as a CI-gated metric.

19.2 Detailed Implementation Steps

  • services/gpu-orchestrator-svc: routes each adapter call across a primary and secondary provider per modality; hedged-request routing for the image adapter's p99 tail follows Dean & Barroso (2013), "The Tail at Scale."
  • Circuit breaker + bulkhead per provider (Nygard 2018 ch. 5, ADR-11-adjacent): an unhealthy provider is isolated, not retried in a tight loop.
  • tools/cost-dashboard: computes ¢/SH per session and per cohort, rolling 24 h window, enforcing I13 (breach beyond ceiling × 1.2 opens an incident).
  • Every PR touching an adapter or the orchestrator reports a ¢/SH delta on a 100-session benchmark, gated in CI (P9).
  • The cost-reconciliation job (I14, P15) ships in the same phase as the dashboard itself, rather than being deferred as a follow-up — an estimate without a reconciliation path is exactly the gap T12 targets.

19.3 Deliverable

A cost dashboard shows real-time ¢/SH per phase cohort; a synthetic provider-outage drill demonstrates automatic failover with no session interruption beyond one buffering cycle.

19.4 Acceptance Criteria

  • ¢/SH at p50 ≤ Phase 1 ceiling of $0.40 (§4) across a 500-session benchmark.
  • Provider failover drill: session resumes within 1 buffering cycle (≤ 2 s per I7 recovery target) after a simulated primary-provider outage.
  • CI cost-regression gate: 0 merged PRs with an unreviewed ¢/SH regression > 10%.

19.5 Conformance Fixtures

  • fixtures/cost-benchmark-500.json — 500-session cohort. Expected: p50 ¢/SH ≤ $0.40.
  • fixtures/provider-outage-drill.json — simulated primary-provider 503 storm. Expected: failover within 1 buffering cycle.
  • fixtures/hedged-request-tail.json — synthetic p99 latency injection. Expected: hedged request reduces realized p99 by ≥ 30% vs. unhedged baseline.
  • fixtures/reconciliation-heartbeat-gap.json — the cost-reconciliation job (I14) is paused mid-run. Expected: cost.reconciliation_delta heartbeat-gap alert fires within one missed cycle, distinct from a divergence alert.

19.6 Pitfalls

  • Hedging doubling cost silently — a naive hedge-always policy sends two billed calls per request; recovery: hedge only past a declared p95 threshold, and cancel the loser (I11) the instant the winner returns.
  • Circuit breaker flapping — a provider oscillating between healthy/unhealthy causes routing thrash; recovery: require 3 consecutive good/bad polls before flipping state (matches the adapter health-poll cadence from Phase 3).
  • Cost-dashboard double-counting cancelled calls that were partially billed before cancellation landed; recovery: reconcile provider invoices against adapter.leaked_gpu_minutes weekly, not just trust the real-time estimate.
  • Provider-diversity illusion — primary and secondary providers for a modality turn out to share a common upstream dependency (e.g. the same underlying GPU cloud), so "failover" doesn't actually diversify risk; recovery: provider-diversity ADRs (§9) must document the actual infrastructure dependency chain, not just the API vendor name, per the FM-9-adjacent correlated-outage lesson (§19.9).

19.7 Performance Concerns

  • Multi-provider routing adds a decision hop before dispatch; keep the routing decision itself sub-millisecond (in-memory capability + health lookup, no synchronous network call) so it never threatens the scene latency budget (§4).
  • Reconciliation against provider invoices (§19.6) is inherently batch/delayed (invoices post hours or days later); the real-time cost dashboard is therefore an estimate, and its accuracy is itself monitored (cost.reconciliation_delta, T12) rather than assumed exact.

19.8 Edge Cases

  • Both primary and secondary providers for a modality unhealthy simultaneously — falls back further to the self-hosted tier (image: ADR-14) or to modality degradation (P13).
  • A provider changes its pricing mid-billing-cycle — cost dashboard must detect the ¢/unit drift and re-run the ceiling check, not use a stale cached price.
  • A hedge request wins by a margin so small that cancelling the loser races the provider's own completion — accept the rare double-bill as within I11's 95% (not 100%) reclaim target.
  • A provider's declared costPerUnit (§11.4) is stale relative to its actual current pricing — the cost dashboard's reconciliation job (§19.6) is the source of truth for ceiling checks, never the capability-registry's cached value alone.

19.9 Failure Analysis

  • Cascading provider failure across primary + secondary for a modality simultaneously (correlated outage, e.g. a shared upstream dependency). Detection: both circuit breakers open within the same window. Containment: modality degrades per P13 rather than the whole stream halting. Recovery: self-hosted fallback tier absorbs load until at least one frontier provider recovers. Forensic artifact: correlated-outage timeline across both providers, informing future provider-diversity ADRs.
  • The cost-reconciliation job (I14) itself fails silently, masking a real cost regression. Detection: cost.reconciliation_delta stops updating (a missing-heartbeat alert, distinct from a divergence alert). Containment: treat a stale reconciliation job as equivalent to an unknown cost state — escalate as if ceiling status were unverified. Recovery: restart the reconciliation job, backfill the missed window from provider invoice history. Forensic artifact: reconciliation-job heartbeat gap.

19.10 Operational Notes

  • Metrics: cost.sh_p50/p95, cost.sh_ceiling_breach, provider.circuit_state, provider.hedge_win_rate. Cost alerts fire at ceiling × 1.2 (§4); a sustained breach freezes non-safety feature work (I13).
  • The reconciliation job's own heartbeat (I14, §19.9) is itself dashboarded, so "the cost dashboard looks fine" is never mistaken for "the cost dashboard is currently trustworthy."

20. Phase 8 — CDN / Edge Asset Cache & Session Resume

20.1 Objectives

  • Build the CDN/Edge Asset Cache to amortize cost on session resume and repeat asset hits; hit the ≥ 35% edge-cache-hit-rate target (§4).

20.2 Detailed Implementation Steps

  • Classified assets (post-Phase-6 gate) are promoted to the edge cache keyed by ModalityAsset.edgeCacheKey; cache promotion is blocked for any asset with a null provenance field (I8).
  • Resume flow: a returning session's cosmology-establishing assets (world intro imagery, recurring character portraits) are served from cache rather than regenerated, directly lowering ¢/SH (§32 capacity model).
  • Cache eviction policy: LRU bounded by a per-user storage quota, with evictedAt written back to the ModalityAsset record (§11.2) rather than a silent delete.
  • Cache-hit/-miss telemetry feeds the cost dashboard (Phase 7) as a direct ¢/SH lever.
  • Cache keys are namespaced by userId from the very first line of cache-layer code (P11/I12 extended, §22 T11), never retrofitted after a scope-check failure is found.

20.3 Deliverable

A viewer resuming a world after 48 hours sees the world's establishing imagery load from edge cache with measurably lower latency and zero regeneration cost for those assets.

20.4 Acceptance Criteria

  • Edge-cache hit rate ≥ 35% on resume sessions (§4), measured over a 1,000-session resume cohort.
  • Cache-served asset latency p95 ≤ 200 ms (vs. ≥ 4 s regenerated), measured on the same cohort.
  • 0 cache promotions of assets with null provenance (I8 enforcement at the cache-promotion boundary).

20.5 Conformance Fixtures

  • fixtures/resume-cache-hit-1000.json — 1,000 resume sessions. Expected: ≥ 35% hit rate.
  • fixtures/cache-promotion-provenance-check.json — assets with deliberately null provenance fields. Expected: 100% rejected at promotion.
  • fixtures/lru-eviction-quota.json — a user exceeding their storage quota. Expected: oldest assets evicted, evictedAt recorded, no silent deletes.
  • fixtures/checksum-corruption-scale.json — a synthetic batch of assets with deliberately corrupted checksums. Expected: cache-promotion pause triggers once the failure rate crosses threshold (§20.9), reads fall back to origin.

20.6 Pitfalls

  • Cache key collision across users — a naive cache key derived only from promptHash could theoretically collide across two users' near-identical prompts; recovery: edgeCacheKey is namespaced by userId (P11/I12 extended to the cache layer).
  • Stale cache serving a pre-migration asset shape — a schema-major-version bump changes asset metadata shape but cached blobs are unaffected (blobs are opaque); recovery: only the metadata row is versioned, cache stores immutable blobs so this is a non-issue by construction — document it as a deliberate non-pitfall to prevent needless "fixes."
  • Eviction racing an in-flight resume read — an asset evicted the instant a resume flow tries to serve it from cache; recovery: read-through fallback regenerates on a cache miss rather than erroring.
  • Quota accounting drift between the cache and the storage bill — the per-user LRU quota (§20.2) is tracked in the cache metadata but the actual object-storage bill diverges due to a delayed-delete queue; recovery: quota accounting reconciles against a nightly storage-provider listing, not just the cache's own bookkeeping.

20.7 Performance Concerns

  • Cache-hit path must stay off the Composer/PWS critical path entirely — a CDN edge lookup, not an origin round trip — to keep resume TTFF inside the same ≤ 8 s budget as cold start (§4).
  • LRU eviction bookkeeping (§20.2) runs as a background job, never synchronously on the request path that triggered the quota breach, so a resume request is never held up waiting for an eviction sweep to complete.

20.8 Edge Cases

  • A user's entire cache evicted due to quota pressure right before a resume — falls back to full regeneration, degrading gracefully to cold-start TTFF rather than failing.
  • Two devices resuming the same world simultaneously (viewer opens the app on phone and laptop) — single-writer discipline (P1) still applies; the second session waits behind the orchestrator lock, cache serves both read paths concurrently.
  • A cached asset whose underlying model version has since been deprecated — still servable (immutable blob), but not eligible for re-promotion if regenerated fresh under the deprecated model.
  • A viewer resumes from a region other than the one that generated their cached assets (travel) — the CDN serves from the nearest edge regardless of origin region, so cache-hit rate is unaffected by viewer geography.

20.9 Failure Analysis

  • CDN provider regional outage. Detection: edge-lookup error rate spike. Containment: fall back to origin (S3-compatible object storage) directly, at higher latency but no correctness loss. Recovery: DNS/routing shifts back to CDN once the region recovers. Forensic artifact: the outage window and the realized ¢/SH delta during origin-fallback (cache-amortization temporarily lost).
  • A cache-integrity checksum mismatch is detected at scale (many assets, not one) suggesting a systemic bug rather than a one-off corruption. Detection: cache.checksum_failure_rate crosses a threshold rather than an isolated event. Containment: pause new cache promotions (§20.2) until root-caused, serving reads from origin in the interim. Recovery: identify and roll back the offending write path, re-promote from clean origin copies. Forensic artifact: checksum-failure rate correlated with recent cache-layer deploys.

20.10 Operational Notes

  • Metrics: cache.hit_rate, cache.eviction_count, cache.served_latency_p95. Cache-key namespacing is verified by the same scope-check fuzz suite as PWS reads (I12, shared test harness).
  • cache-region-outage.md (§24) documents the origin-fallback path (§20.9) so an on-call engineer can confirm the fallback is active without first having to derive it from first principles under incident pressure.

21. Phase 9 — Video Adapter & Long-Form Streaming

21.1 Objectives

  • Ship adapter-video; build the clip-stitching layer for near-continuous long-form video; hit the Phase 9 ¢/SH ceiling of $2.50 (§4).

21.2 Detailed Implementation Steps

  • adapter-video: frontier video-provider integration behind the standard ModalityAdapter interface (§11.4–11.5); latency budget ≤ 30 s/30 s clip (§4); sleep mode defaults video off (image-only sleep experience remains default, per the original product locked rail).
  • Stitching layer: the last frame of clip i conditions clip i+1, plus shared PersistentCharacter.appearance.seed reuse (§11.1), to hide clip boundaries from the viewer — extends the Phase-3 image character-consistency technique (§15.2) to the temporal dimension.
  • Pre-warming: the streaming runtime (Phase 5) issues preWarm() for the next clip while the current clip plays, maintaining a 30 s buffer ahead (I7 extended to video-scale buffering).
  • Provider routing (Phase 7 infrastructure) selects cheaper providers for low-arousal clips, premium providers for high-arousal clips, per the cost/quality tradeoff locked in ADR-14.
  • Video-adapter cancellation uses a tightened 1 s deadline distinct from the general 2 s (I11) budget, reflecting the higher per-call cost analyzed in §32 item 12 — a deliberate per-modality override of an otherwise system-wide default.

21.3 Deliverable

A 30-minute continuous 720p video session runs with no visible seams between clips and ¢/SH ≤ $2.50 measured over a benchmark cohort.

21.4 Acceptance Criteria

  • ¢/SH ≤ $2.50 at p50 (§4) over a 200-session 720p benchmark — this is the Phase 9 (and full-system) exit criterion.
  • Visual-continuity classifier (extended from Phase 3, §15.4): returning characters recognizable in ≥ 70% of clips across a 100-clip test corpus.
  • Video-adapter cancellation cleanliness: ≥ 95% GPU-cost reclaim within 2 s across 1,000 cancellations (I11, extended to video's higher-cost calls).

21.5 Conformance Fixtures

  • fixtures/continuous-video-30min.json — a 30-minute synthetic stream. Expected: 0 visible clip-boundary seams (frame-difference classifier below threshold at every splice point).
  • fixtures/video-character-consistency-100.json — 100 clips, one returning character. Expected: ≥ 70% recognized match.
  • fixtures/video-cost-benchmark-200.json — 200-session cohort. Expected: p50 ¢/SH ≤ $2.50.
  • fixtures/stitch-regression-fleetwide.json — a simulated fleet-wide stitching-layer model bump. Expected: release-gate blocks promotion if video.stitch_seam_score regresses on the conformance corpus (§21.9).

21.6 Pitfalls

  • Stitching artifacts at high-motion boundaries — the last-frame-conditioning technique degrades when clip i ends mid-motion; recovery: the Composer plans clip boundaries at low-motion narrative beats (an N.2 scheduling hint, not a video-adapter fix).
  • Cancellation cost asymmetry — video generation is far more expensive per call than image/music, so a missed cancellation is proportionally costlier; recovery: video-specific cancellation deadline is tighter (1 s, not the general 2 s) and monitored as its own SLI.
  • Provider cost-routing oscillation — routing flips between cheap/premium providers scene-to-scene in a way that itself becomes visually inconsistent; recovery: routing decision is sticky per-world for a rolling window, not re-decided every scene.
  • Stitching-conditioning frame fetched from the wrong cache tier — the last-frame extraction accidentally reads from origin object storage instead of the CDN edge cache (§20), adding hundreds of milliseconds to every clip boundary; recovery: the stitching layer's frame-fetch path is a dedicated, monitored call (video.stitch_frame_fetch_latency), never a fallthrough of the generic asset-read path.

21.7 Performance Concerns

  • Video is the first modality where GPU memory bandwidth for the stitching-conditioning step (loading the prior clip's last frame) becomes a measurable latency term; keep the last-frame extraction on the CDN edge cache path (Phase 8) rather than re-fetching from origin.
  • The 30s pre-warm buffer (§21.2) is the single largest per-session memory/bandwidth cost increase over Phase 1–8; monitor scheduler.buffer_depth (I7) specifically for video sessions, since a video-scale buffer is far more expensive to over-provision than a text/image-scale one.

21.8 Edge Cases

  • A clip generation that fails entirely (not just late) with no prior successful clip to stitch from (session's first video clip) — falls back to a static establishing image (P13, video→image degradation) for that scene.
  • A viewer skipping ahead mid-clip — cancels the clip (I11, tightened 1 s deadline) and the stitching layer treats the last fully delivered frame as the new conditioning anchor, not the cancelled clip's partial output.
  • Two consecutive clips both routed to the same now-unhealthy provider due to sticky routing (§21.6) — sticky routing has a hard override: 2 consecutive failures break stickiness immediately.
  • A viewer enables "soft video" in sleep mode (§4-adjacent product rail) — the video adapter must additionally pass the sleep-mode classifier tier (I4, ADR-16), not just the general classifier, exactly as image/music already do.

21.9 Failure Analysis

  • Frontier video provider price shock (sudden ¢/unit increase) breaching the $2.50 ceiling. Detection: cost.sh_ceiling_breach (I13) fires on the video cohort specifically. Containment: provider routing (Phase 7) shifts weight toward the cheaper provider immediately; if no provider is under ceiling, the system degrades to Phase-2-era clip-only (non-continuous) video per the locked kill/pivot posture. Recovery: ceiling restored once a provider's pricing or the stitching layer's cache-hit rate improves. Forensic artifact: the pricing-change timestamp cross-referenced with the ¢/SH time series.
  • A stitching-layer regression causes visible seams across an entire cohort simultaneously (not an isolated clip). Detection: video.stitch_seam_score degrades in the fleet-wide telemetry, not just the pre-release conformance suite. Containment: roll back the video-adapter version fleet-wide (§27 rollback mechanism) rather than patching forward under pressure. Recovery: re-run the full stitching-continuity conformance suite (§21.5) against the rollback candidate before re-attempting the release. Forensic artifact: seam-score time series bracketing the regressing deploy.

21.10 Operational Notes

  • Metrics: video.stitch_seam_score, video.cost_per_clip, video.cancel_reclaim_rate. Video-model version bumps require the full conformance suite (§26) plus the stitching-continuity classifier before release, given the higher per-call cost of a regression.
  • This phase closes out the Phase 0–9 build: Appendix B's exit criteria (§38) for Phase 9 double as the full-system exit criteria referenced throughout §1's estimated timeline.

25. Compatibility & Versioning

  • Wire compatibility: the WebSocket envelope (scene-start/asset-ready/scene-end/world-delta, §17.2) is additive-only; unknown fields are ignored by older player bundles, never rejected.
  • Storage compatibility: every persisted record carries schemaVersion (§11); the migration runner (§13) is forward-only; a downgrade is explicitly unsupported (locked decision, matches the original product's schema-versioning intent).
  • Schema-evolution policy: additive fields only within a minor version; a breaking change requires a major-version bump plus a 12-month dual-major-version read-support window (I9).
  • API stability: the ModalityAdapter, Composer, and SceneScheduler interfaces (§11.4–11.5) are versioned as a whole (ADR-25); adding an optional method is non-breaking, changing an existing signature requires a major bump and a deprecation cycle.
  • Migration policy: every schema-major-version bump ships with an automated forward-migration script tested against a synthetic corpus before any production world is migrated (§13.4).
  • Deprecation policy: a deprecated adapter version remains servable for cached (already-generated) assets indefinitely (§20.6) but is removed from new-generation routing after its declared sunset date, published in CHANGELOG.md.
  • SemVer policy (semver.org, §5 RFCs/Specs): packages/schema and the Adapter contract follow strict semver; patch = bugfix, minor = additive field/method, major = breaking change.
  • Rolling-upgrade guarantees: a mixed-version fleet (old and new Edge/API instances serving simultaneously during a rollout) is always safe because the wire envelope and schema are additive-only within a version window (P8) — no service needs to assume fleet-wide version uniformity.
  • Compatibility-surface table:

29. Scalability Analysis

  • Constant regardless of load: per-scene latency budget (§4) — the architecture's entire point is that scene latency does not degrade with fleet size, only with provider-side load; per-session memory footprint (≤256 MB, §4) is bounded by hierarchical-memory summarization design intent (full implementation deferred, Deferred Features Register).
  • Grows with load, and its Big-O: Edge/API instance count — O(sessions) horizontally, embarrassingly parallel (P3: one viewer, one stream, no shared mutable state); GPU Orchestration Pool capacity — O(concurrent adapter calls), the true bottleneck (see below); PWS write volume — O(scenes committed), bounded per-world by I1's single-writer serialization, but aggregate write throughput scales horizontally across worlds (no cross-world coordination).
  • Named bottlenecks, in order: (1) GPU Orchestration Pool capacity / frontier-provider rate limits — the dominant ceiling, addressed by multi-provider routing (§19) and self-hosted fallback tiers (ADR-14, ADR-15); (2) Postgres primary write throughput for PWS — addressed by read-replica offload for reads and by the fact that writes are naturally sharded per-world with no cross-world transaction; (3) Safety Classifier Ensemble throughput — addressed by horizontal replication of stateless classifier instances, since classification has no cross-request state.
  • Horizontal vs. vertical scaling: the Edge/API tier and adapter processes scale horizontally by design (P3); the PWS Postgres primary scales vertically up to a ceiling, after which per-world sharding (partitioning Worlds across multiple primaries by worldId hash) is the lever — not yet required at the Phase 9 scale target (§4 constraints), tracked as a Phase-9+-adjacent concern.
  • Sharding/partitioning: not required within this blueprint's scope (single Postgres primary + replicas suffices at ≤5,000 concurrent sessions/region, §4); the natural shard key, if needed later, is worldId (no cross-world queries exist, so sharding introduces no coordination overhead).
  • Coordination overhead: the only cross-component coordination is the per-world single-writer lock (I1) — strictly local to one world, never global — so coordination overhead does not grow with fleet size, only with (rare) same-world concurrent-access attempts (§13.6). Formally, coordination cost is O(1) per world regardless of total fleet size: the lock is acquired and released independent of how many other worlds exist, so the aggregate lock-acquisition rate scales linearly with the total scene-commit rate, never superlinearly — the architecture never requires a global consensus round for an ordinary scene commit.
  • Bottleneck-to-lever mapping:
Bottleneck Current Ceiling Primary Lever Secondary Lever
GPU Orchestration Pool / provider rate limits ≈ 900,000 calls/hr/region (§32 item 5) Multi-provider routing + self-hosted fallback (ADR-14, ADR-15) Deepen edge-cache hit rate (§20)
Postgres primary write throughput Not yet reached at 5,000 sessions/region (§4) Read-replica offload for reads Per-world sharding by worldId hash (deferred, §35)
Safety Classifier Ensemble throughput Not yet reached — stateless, horizontally replicated Add classifier replicas Batch classification across scenes sharing a provider response window
Edge/API instance FD budget ≈ 1,638 sessions/instance (§32 item 4) Add instances Reduce per-session FD footprint via connection-pool reuse
  • Practical ceiling and the levers beyond it: the practical ceiling is set by aggregate frontier-provider inference capacity, not by Oneiros's own code. Levers beyond it: deepen the self-hosted GPU fallback tier (shifts the ceiling from "provider-limited" to "capital-limited," a strictly better failure mode); expand edge-cache hit rate (§20) to reduce the number of fresh inference calls needed per stream-hour; and, structurally, the persistent-world model itself amortizes cost over a user's lifetime (§32) rather than requiring fresh generation every session.
  • Vertical scaling of the Composer itself: a single session's Composer call is bounded by prompt-token count, which grows with vibeHistory/memories (§11.6); this is a per-session vertical concern, not a fleet-scaling one — the mitigation (hierarchical memory, Deferred Features Register) reduces the vertical ceiling per session rather than adding horizontal capacity, and is tracked independently of the fleet-scaling levers above.
  • What does not scale by adding money: provider rate limits are frequently contractual/quota-based, not purely capacity-based — doubling spend does not always double available throughput on a single frontier provider. This is precisely why multi-provider routing (§19) is a scalability lever, not just a cost lever: it adds independent quota pools, which a single larger contract with one provider cannot.
  • Read-path vs. write-path scaling asymmetry: PWS read traffic (world/character lookups during active sessions) is an order of magnitude higher than write traffic (one write per scene commit, §11.2) and scales independently via read replicas; conflating the two when capacity-planning would over-provision the write path and under-provision the read path.

30. Mental Models & First Principles

  1. MM1 — A scene is a state machine; the scheduler is its clock. Predicts that buffer-ahead invariants generalize from any clock-driven system. Bug class without it: treating scene dispatch as fire-and-forget rather than deadline-driven, producing visible stutter. Applied in §17.
  2. MM2 — The Composer is a single-writer log, not a database. Predicts that append-only world deltas compose safely, and that concurrent writers are a category error, not a race to optimize away. Bug class without it: attempting multi-writer world edits, causing identity collapse. Applied in §13, §14, I1/I2.
  3. MM3 — Safety classification is a trust boundary, not a feature. Predicts it must sit on the output path of every adapter, never bypassable by a fast-path optimization. Bug class without it: an optimization that skips classification "just this once," producing FM-4. Applied in §18.
  4. MM4 — Cost is a scheduling input, not a billing afterthought. Predicts routing decisions must weigh ¢/unit at dispatch time, not just measure it after the fact. Bug class without it: unbounded cost growth invisible until the invoice arrives. Applied in §19, I13.
  5. MM5 — Cancellation is a contract, not a courtesy. Predicts every adapter must treat cancel() as a first-class API symmetric with render(). Bug class without it: skip-ahead behavior silently bankrupting the cost model. Applied in §17, §19, I11.
  6. MM6 — A persistent world is an event-sourced log with periodic snapshots, not a mutable row. Predicts replay-from-log always recovers correctness; snapshots are an optimization, not a source of truth. Bug class without it: trusting a stale or corrupted snapshot as ground truth after a crash. Applied in §13.
  7. MM7 — Provider heterogeneity is data, not an exception. Predicts the capability registry (latency/cost/health) must be queried at every dispatch, not hardcoded per adapter. Bug class without it: brittle single-provider assumptions that break the moment one provider changes pricing. Applied in §15, §19.
  8. MM8 — Degradation must be modality-local, not session-global. Predicts a failing video adapter should never take down text/image/music in the same scene. Bug class without it: cascading failure from what should be an isolated fault. Applied in §21, P13.
  9. MM9 — An estimate without a reconciliation path is a liability, not a metric. Predicts that any real-time telemetry derived from external billing (cost) or external classification (safety) needs a scheduled ground-truth check. Bug class without it: silent drift between believed and actual state, discovered only when it becomes a financial or compliance surprise. Applied in §19, §22 (T12), I14, P15.
  10. MM10 — A branded identifier is cheaper than the bug it prevents. Predicts that compile-time type distinctions between superficially identical strings (WorldId vs. SceneId) pay for themselves the first time a refactor would otherwise silently swap them. Bug class without it: cross-entity confusion bugs that only surface as data corruption in production, never a compiler error. Applied in §11.8, P14.

Netflix made a fundamentally different bet: the finite-library-plus-recommendation model wins whenever content reuse across millions of viewers amortizes production cost — Oneiros's per-viewer-unique generation is the opposite bet, viable only because inference cost (not production cost) is the marginal unit.

Temporal made the opposite determinism bet: it assumes workflow steps are deterministic and replayable, which lets it recover any execution from history. Oneiros cannot make that assumption (LLM sampling is stochastic), so it recovers via delta-replay against committed state rather than full re-execution — the niche where Temporal's model wins is exactly where every step is deterministic (business workflows, payment orchestration).

Kafka decouples producers and consumers via a durable, replayable log — the right call when many independent consumers need the same event stream at their own pace. Oneiros's scene-completion events have exactly one consumer (the Composer, ingesting its own completions), so a full log-compaction/multi-consumer-group model would be pure overhead; Oneiros borrows only the segment/retention idea (§5 Reference Implementations), not the full system.

LiveKit wins where bidirectional, low-latency, multi-party live media is the point — real conversation, real co-presence. Oneiros is deliberately one-way and asynchronous-tolerant (a few seconds of buffer-ahead is a feature, not a defect, per I7), so WebRTC's low-latency machinery would be solving a problem Oneiros doesn't have, at the cost of the NAT-traversal and SFU-scaling complexity LiveKit must carry.

AI Dungeon is the closest narrative-persistence neighbor and is cited directly in §5 Reference Implementations: it proved that a single LLM loop can sustain a persistent story world, but it never formalized a multi-modal scheduling layer, a non-bypassable safety classifier, or a cost-bounded adapter contract — exactly the three subsystems (§15, §18, §19) Oneiros adds on top of the same core insight. AI Dungeon's architecture wins where text-only narrative is the entire product and multi-modal cost/latency budgeting is unnecessary overhead (Alternative Architecture 4, §34).

32. Back-of-Envelope Capacity Model

  1. Image bandwidth/session/hour = 60 scenes/hr (avg 60 s/scene, §8.4) × 300 KB/image ≈ 18 MB/hour/session (pre-cache).
  2. Region image egress at max concurrency = 18 MB × 5,000 sessions (§4 max concurrency) = 90,000 MB/hr; at ≥35% cache-hit rate (§4), origin-served fraction = 65% → ≈ 58.5 GB/hr origin egress/region.
  3. Aggregate Composer-context RAM/region = 256 MB ceiling/session (§4) × 5,000 concurrent sessions = 1.28 TB upper-bound resident memory before hierarchical-memory summarization (deferred) reduces it.
  4. Minimum Edge/API instances/region for FD headroom = 8,192 FDs/instance (§4) ÷ ~5 FDs/session (1 WebSocket + ~4 adapter connections) ≈ 1,638 sessions/instance; 5,000 sessions ÷ 1,638 ≈ 4 instances minimum (FD-bound, before CPU/latency sizing).
  5. Adapter calls/hour/region = 3 adapters/scene (text, image, music, Phase 1) × 60 scenes/hr × 5,000 sessions = 900,000 calls/hour/region.
  6. Region-wide cost ceiling exposure = $0.40/SH ceiling (§4, Phase 1) × 5,000 concurrent sessions = $2,000/hr theoretical peak, i.e. ≈ $48,000/day — the number I13's rolling-window gate exists to keep in check.
  7. PWS Scene-metadata storage/world/year = 1,095 scenes/year (3/day × 365) × ~2 KB/Scene row × 1.4 amplification (§4) ≈ 3.1 MB/year/world; at 5,000 WAD retained a full year ≈ 15.5 GB/year region-wide (excludes asset blobs, held separately in object storage).
  8. Cache-driven cost reduction = resume-session fraction (~60%, tracking the ≥40% persistent-world-recall target) × cache-hit rate (≥35%, §4) ≈ 21% of all scene-asset generations avoided, a direct ¢/SH reduction versus a no-cache baseline — the number the Phase 8 cache-hit target is chasing.
  9. Global concurrent-session ceiling (3 regions) = 5,000/region (§4) × 3 regions = 15,000 global concurrent sessions before a 4th region is required.
  10. Cancellation-path throughput requirement = 900,000 calls/hr (item 5) × ~5% viewer skip-ahead rate ≈ 45,000 cancellations/hour/region, each requiring ≥95% cost-reclaim within 2 s (I11) — sizes the cancellation subsystem independent of the render subsystem.
  11. Safety Classifier Ensemble call volume = 900,000 adapter calls/hr (item 5) × 1 classification per output ≈ 900,000 classifications/hour/region, each with an added-latency budget of ≤300 ms p95 (M9, §28) — sizes the classifier replica count needed to stay off the scene-latency critical path.
  12. Phase-9 video cost crossover point = at ¢/SH ceiling $2.50 (§4) and self-hosted GPU-hour cost of roughly $2–4/GPU-hour (2026-era spot pricing), a self-hosted video clip becomes cost-competitive with a frontier-API clip once per-session GPU utilization exceeds ≈60% (i.e., the GPU is busy more than 36 minutes of every stream-hour) — the threshold ADR-14's "when self-hosted wins" column is keyed to.

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Fully Offline Batch Pre-Generation

[Batch Generator] --> [Object Store] --> [CDN] --> [Player]
        (no live Composer loop; episodes rendered overnight)

Regime where it wins: GPU cost per live call far exceeds what a subscription can bear, or latency tolerance is measured in hours. Real system embodying it: personalized-trailer batch-rendering pipelines used by large streaming services for promotional assets. Rejected because: it kills the "never told before, right now" real-time promise and reintroduces a library-like ceiling on variety — the opposite of the product's differentiation.

Alternative 2 — Fully Client-Side Generation

[Viewer Device: local Composer + local Adapters] --> local playback
        (no server round trip at all)

Regime where it wins: extreme privacy requirements, zero marginal server-side cost at scale, offline usage. Real system embodying it: emerging on-device LLM/diffusion apps using WebGPU/ONNX Runtime Web. Rejected because: Phase-1-era consumer hardware cannot run a frontier-quality multi-modal stack inside the latency budget (§4), and it forfeits the multi-provider cost-arbitrage moat (§19).

Alternative 3 — Peer-to-Peer / Federated World-Hosting

[Peer A] <--> [Peer B] <--> [Peer C]   (mesh; each hosts partial world shards)

Regime where it wins: censorship-resistant distribution, community-run infrastructure. Real system embodying it: BitTorrent-style content distribution / federated systems (ActivityPub). Rejected because: the non-bypassable safety-classification invariant (I3, P4) requires a trusted, centrally auditable gate — a federated model cannot guarantee that untrusted peers apply it.

Alternative 4 — Single-Modality-First, No Real-Time Scheduler

[Viewer] <-> [Chat Loop] -> text now; image/audio fetched async, later
        (no buffer-ahead scheduling, no scene-level modality fan-out)

Regime where it wins: a much simpler engineering bar when narrative text alone is the product. Real system embodying it: AI Dungeon's original architecture (§5 Reference Implementations). Rejected because: it forfeits the multi-modal ambient/visual sleep-aid experience that defines the product's differentiation and the sleep wedge's core value proposition.

36. Glossary

  • Adapter — modality-specific renderer implementing ModalityAdapter (§11.4–11.5).
  • Arousal — Mood axis, −1 (calming) to +1 (intense); capped at 0 in sleep mode (I4).
  • Buffer-ahead — the invariant (I7) that ≥1 scene is fully rendered ahead of playback.
  • Bulkhead — resource-isolation pattern preventing one failure from exhausting shared capacity (§19).
  • ¢/SH — cost per stream-hour, the defining cost metric (§4, I13).
  • Cache promotion — moving a classified asset into the CDN edge cache (§20).
  • Cancellation — explicit reclaim of an in-flight adapter call's cost (I11).
  • Capability registry — in-memory index of adapter capabilities by modality (§11.4, §15).
  • Circuit breaker — a provider-health pattern isolating a failing dependency (§19).
  • Classifier Ensemble — the dual (general + sleep-mode) safety-classification pipeline (§18).
  • Composer — the LLM-driven scene planner and sole PWS writer (§11.5, P1).
  • Conformance suite — the per-adapter release gate covering latency, cost, mood-fidelity, safety, cancellation (§15, §26).
  • Content profile — per-user policy bounding Composer planning and classifier admission.
  • Cosmology — Composer-authored world-physics/history prose (§11.1).
  • Edge Asset Cache — CDN-level cache of classified assets (§20).
  • Envelope encryption — a per-user data key wrapped by a KMS master key (I10, RFC 7516).
  • GPU Orchestration Pool — multi-provider inference-routing subsystem (§19).
  • Hedged request — a redundant request issued to cut tail latency, cancelled on first response (§19).
  • Modality — a sensory channel: text, image, music, video, voice (voice deferred).
  • Modality Adapter Bus — the collection of pluggable adapters behind one interface (§3, §11.4–11.5).
  • Modality fallback — degrading a scene to a cheaper modality rather than failing it (P13).
  • Mood — the (arousal, valence, descriptors, biometrics?) tuple conditioning adapter output (§11.4).
  • PWS — Persistent World Store, per-user encrypted durable state (§13).
  • Provenance — per-asset record of prompt hash, seed, model version (I8).
  • Scene — the atomic streaming unit, 30–90 s (§8.3, §11.2).
  • Scene Scheduler — dispatches adapter calls under budget, enforces I7 (§17).
  • Schema version — the semver tag on every persisted record, non-decreasing (I6).
  • Seed — 256-char re-hydration payload for a world (type defined §11.3, feature deferred).
  • Session orchestrator — enforces the per-world write lock (I1) and cross-user scoping (I12).
  • Sim-harness — the deterministic invariant simulator gating Composer/Scheduler/PWS changes (§12, §26).
  • Sleep mode — a Stream mode with the strictest tone envelope (I4, P5).
  • Snapshot — a periodic (every 50 scenes) durable checkpoint of world state (§13).
  • Stitching layer — the Phase 9 technique hiding video clip boundaries via last-frame + seed conditioning (§21).
  • Stream — a viewer session, a sequence of scenes (§11.3).
  • Streaming Runtime — the latency-budgeted scene-scheduling subsystem (§3, §17).
  • Tone envelope — the per-world arousal/valence hard rails (§11.1).
  • TTFF — time-to-first-frame, prompt submit to first scene byte (§4, M1).
  • Valence — Mood axis, −1 (dark) to +1 (joyful); floored at −0.2 in sleep mode (I4).
  • Vibe — viewer-supplied text/voice input biasing scene planning (§11.2).
  • Watermark — the streaming-systems accounting concept underlying buffer-ahead tracking (§17).
  • World — a persistent per-user context: cosmology, characters, threads, locations (§11.1).
  • World delta — an incremental change to world state emitted after a scene (§11.5).
  • WorldId — the stable ULID identifying a World forever (§11.1).
  • Branded type — a compile-time-only type wrapper (e.g. WorldId vs. plain string) preventing cross-identifier confusion with zero runtime cost (§11.8).
  • Canary analysis — automated comparison of key SLIs between a 1%-traffic canary and the stable cohort before a full rollout (§24).
  • Error budget — the allowed cumulative SLO-violation time within a measurement window (e.g. 3.6 h/month at 99.5% availability, §24).
  • RTO — Recovery Time Objective, the maximum acceptable time to restore service after a failure (§4, §13.9).
  • RPO — Recovery Point Objective, the maximum acceptable data loss window measured in time (§4, §13).
  • SBOM — Software Bill of Materials, the enumerated dependency manifest generated per release (§27).
  • Reconciliation — the batch process comparing real-time cost/audit estimates against an authoritative source (provider invoice, storage listing) after the fact (§19, T12).
  • Sticky routing — a provider-routing policy that holds a choice stable across a rolling window rather than re-deciding per call, with a hard override on repeated failure (§21.6).
  • Deferred feature — a capability intentionally out of scope for Phases 0–9, tracked with an anchor, building phase, and un-defer trigger (§35).
  • Hierarchical memory — a deferred Composer design (short/medium/long-term layers) for bounding context growth in multi-year worlds (§35).
