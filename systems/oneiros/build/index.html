⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives
  • Stand up the monorepo skeleton, the packages/schema types (§11), a fixture-driven Composer stub, and a deterministic invariant simulator.
  • Establish the single-writer discipline (P1) and scene-ordering discipline (I5) before any real LLM or adapter exists.
Deliverable

pnpm sim-harness run fixtures/basic-world.json produces a 50-scene run with zero invariant failures; packages/schema compiles clean under tsc --strict.

Acceptance
  • Sim-harness: 0 assertion failures across 10 seeded runs of 50 scenes each (500 scenes total).
  • packages/schema: 100% of §11 types round-trip JSON serialize/deserialize with zero field loss.
  • CI green on pnpm build && pnpm test, coverage ≥ 75% on packages/schema and packages/composer.
Fixtures
  • fixtures/basic-world.json — 3-character, 1-location starter world. Expected: 50 scenes committed, index 0..49, no gaps.
  • fixtures/malformed-schema-version.json — a record with schemaVersion: "0.9.0" (below current). Expected: PWS write rejected, schema.version_regression incremented.
  • fixtures/duplicate-writer.json — two Composer stub instances racing on the same worldId. Expected: second writer rejected, composer.write_lock_conflicts incremented.
  • fixtures/branded-id-misuse.json — a hand-crafted call passing a CharacterId where a SceneId is expected. Expected: tsc --strict compile failure, never a runtime error (P14).
Pitfalls
  • Silent schema drift between packages/schema and the Postgres migrations — passes unit tests but fails the sim-harness run; root cause: migrations hand-authored instead of generated from the TS types; signal: schema.compat_test_failures; recovery: generate migrations from the schema, never author both by hand.
  • Sim-harness false confidence — a harness exercising only the happy path never trips I2/I11; root cause: fixtures lack adversarial cases; signal: 0 failures forever; recovery: mandate ≥1 fixture per invariant.
  • Postgres unique-constraint race on (worldId, index) under two concurrent stub writers — surfaces as an unhandled 40001 serialization-failure rejection; recovery: catch and retry with the CAS pattern later locked in ADR-06.
  • Branded-type erosion at the PWS boundary — a hand-written SQL query returns a bare string that TypeScript happily assigns to a WorldId parameter without the compiler catching the type confusion; recovery: all PWS reads pass through a single typed mapper function (never raw query results) so branding (§11.8) is enforced at exactly one seam.

⬜ Phase 1 — Persistent World Store & Core Schema §13

Objectives
  • Harden the Phase-0 PWS stub into a real service: per-user envelope encryption, snapshotting, forward-only migrations. Lock schema v1.0.0.
Deliverable

A CLI test client creates a world, disconnects, and resumes it 48 hours later with identical character state via resumeWorld.

Acceptance
  • Resume-after-48h test passes on 100 synthetic worlds, zero character-field drift.
  • Snapshot storage overhead measured ≤ 1.4× logical size on a 500-scene world.
  • Encryption round-trip verified on 1,000 world creations, zero plaintext-key-egress events (I10).
  • Migration test suite passes at 100% on a 1,000-world synthetic corpus (scaled precursor to the 100,000-world Phase-9-era corpus).
Fixtures
  • fixtures/resume-after-gap.json — a world paused 48h. Expected: identical character snapshot on resume.
  • fixtures/mid-migration-write.json — a write arriving during a schema-major-version rollout. Expected: queued, not dropped.
  • fixtures/kms-key-rotation.json — a key rotation mid-session. Expected: zero plaintext egress, session uninterrupted.
  • fixtures/snapshot-storage-amplification.json — a 500-scene world measured for storage overhead. Expected: amplification ≤ 1.4× logical size (§4).
Pitfalls
  • Snapshot-pointer off-by-one — snapshot taken at scene 50 but referenced after scene 53, causing a 3-scene replay gap on resume. Signal: scene.sequence_gap after resume. Recovery: replay from the event log, not the snapshot, whenever a gap is detected.
  • KMS latency spikes blocking the resume path. Debug via the pws.resume trace span. Recovery: cache the data-key for the session lifetime; only re-fetch on rotation.
  • Read-replica staleness silently serving a stale World on resume. Signal: character field mismatch vs. the last committed scene. Recovery: route the first post-gap read to the primary (§13.7).
  • Migration canary skipped under deadline pressure — a schema-major-version bump goes straight to the full corpus to save time; recovery: the 1%-canary step (§13.9-adjacent, §24 canary analysis) is a hard CI gate, not an optional step an engineer can bypass under a deadline.

⬜ Phase 2 — Composer & Scene Planning Engine §14

Objectives
  • Replace the Phase-0 rule-based Composer stub with a live LLM-backed planner; establish world coherence and character continuity over an extended scene run.
Deliverable

A 50-scene fixture run in which the same three characters (by CharacterId) appear, are referenced consistently by name/archetype, and the world's cosmology prose remains internally consistent.

Acceptance
  • Character-continuity check: 0 identity-field mismatches (I2) across a 50-scene fixture run, verified against fixtures/character-continuity-50.json.
  • Composer planning latency p95 ≤ 1.5 s/scene (§4), measured over 500 planning calls.
  • Prompt-injection corpus (fixtures/injection-corpus-200.json, 200 adversarial vibes): 0 vibes elevate to system-prompt scope.
Fixtures
  • fixtures/character-continuity-50.json — 50-scene run, 3 characters. Expected: 0 identity drift.
  • fixtures/injection-corpus-200.json — 200 adversarial vibe strings. Expected: 0 system-prompt elevations, 0 tone-envelope breaches.
  • fixtures/empty-world-bootstrap.json — a brand-new world with no prior state. Expected: Composer synthesizes cosmology + 3 starting characters + 1 location.
  • fixtures/model-version-pin-regression.json — a fixture re-run against a newer (unpinned) provider model version. Expected: character-continuity and pacing scores must not regress relative to the pinned baseline (§14.9).
Pitfalls
  • Character drift via prose paraphrase — the LLM renames a character mid-run without a logged world-drift event, silently violating I2; debug via the identity-diff validator (§7); recovery: revert to the last snapshot and re-plan with an explicit continuity reminder injected into the prompt.
  • Over-long context causing latency blowout — as vibeHistory and memories grow, planning latency creeps past the 1.5 s p95 budget; signal: composer.planning_latency_p95 trending upward; recovery: summarize memories into condensed records past a length threshold (full hierarchical-memory design deferred, see Deferred Features Register).
  • Prompt injection via nested vibe fields (e.g. a vibe that itself quotes a fake "system:" line) bypassing the naive untrusted-input filter; recovery: strip role-like tokens from vibe text before injection, verified by the 200-item corpus.
  • Pacing rule applied mechanically rather than semantically — a literal "one shift per 6 scenes" counter (Murch's rule, §5) fires a tonal shift even when the narrative calls for stability; recovery: treat the rule-of-six as a ceiling on shift frequency, not a scheduled event, per Murch's original framing (2001, ch. 1).

⬜ Phase 3 — Modality Adapter Contract, Text & Image Adapters §15

Objectives
  • Implement the ModalityAdapter interface (§11.4–11.5) for real; ship adapter-text and adapter-image; stand up the capability registry and conformance suite.
Deliverable

A 30-minute session streams text + one consistent image per scene; a returning character's image is recognizably the same across scenes.

Acceptance
  • Image adapter latency p95 ≤ 4 s/1024×1024 image (§4), measured over 1,000 calls.
  • Character-consistency classifier score ≥ 0.70 across a 100-clip test corpus (visual-continuity check).
  • Conformance suite: 0 failures across latency, cost (±10% of declared costPerUnit), and cancellation-cleanliness (0 leaked GPU-minutes over 1,000 cancellations, I11) checks.
Fixtures
  • fixtures/adapter-latency-load.json — 1,000 synthetic image requests. Expected: p95 ≤ 4 s.
  • fixtures/character-consistency-100.json — 100 clips of one returning character. Expected: ≥ 70% classifier-recognized match.
  • fixtures/cancel-storm-1000.json — 1,000 rapid-fire cancellations. Expected: 0 leaked GPU-minutes (I11).
  • fixtures/compound-fallback-outage.json — primary provider down and self-hosted fallback saturated simultaneously. Expected: graceful text-only degradation (P13), no crash.
Pitfalls
  • Seed reuse producing near-duplicate, not consistent, images — over-reliance on a fixed seed collapses visual variety; recovery: seed pins identity features only, style/pose still varies per scene.
  • Health-check false positives — an adapter reporting healthy while its underlying provider is rate-limited; signal: adapter.render_error_rate diverges from adapter.health_report; recovery: fold real error rate into the routing decision, not just the health poll.
  • Cancellation race — a cancel arriving after the adapter has already committed to billing (provider-side) the full call; recovery: track a "point of no return" per provider and stop issuing cancels past it (documented per-provider in docs/adr).
  • Reference-image staleness — a character's pinned reference asset (§11.1 appearance.referenceAssetIds) is evicted from the edge cache (§20) before Phase 8 ships, forcing a costly regeneration on every scene; recovery: pinned reference assets are exempt from LRU eviction regardless of cache pressure (a distinct retention class from ordinary scene assets).

⬜ Phase 4 — Music Adapter & Mood Conditioning §16

Objectives
  • Ship adapter-music; formalize Mood-conditioning fidelity across all adapters registered so far (text, image, music).
Deliverable

A 30-minute sleep-mode session runs a continuous, seamless ambient bed with mood shifting per scene, with zero audible loop seams on internal dogfood review.

Acceptance
  • Music adapter latency p95 ≤ 6 s/30 s loop (§4), measured over 500 calls.
  • Mood-fidelity classifier ≥ 0.75 accuracy across all 4 quadrants, fixtures/mood-quadrant-corpus.json.
  • Sleep-mode routing: 0 non-approved adapter versions selected across 1,000 sleep-mode scene dispatches (I4).
Fixtures
  • fixtures/mood-quadrant-corpus.json — 200 prompts across 4 quadrants. Expected: ≥ 0.75 classifier accuracy per quadrant.
  • fixtures/sleep-routing-1000.json — 1,000 sleep-mode scene dispatches. Expected: 0 non-approved routes.
  • fixtures/loop-seam-detection.json — synthetic crossfade boundary samples. Expected: 0 detectable amplitude discontinuities > −40 dB.
  • fixtures/gpu-pool-contention.json — simultaneous image and music demand on a shared pool partition. Expected: p95 latency for both stays within budget once dedicated partitioning (§16.6) is active.
Pitfalls
  • Tempo/key mapping saturating at extremes — very high arousal values clamp to the same output as moderate-high, losing fidelity; recovery: recalibrate the mapping table against the classifier's confidence curve, not a linear assumption.
  • GPU pool contention between image and music self-hosted models sharing a pool — manifests as both adapters' p95 latency degrading together; signal: gpu_pool.utilization correlated across adapter ids; recovery: dedicated pool partition per modality (locked in Phase 7, ADR-adjacent).
  • Sleep-mode routing bypass via a stale capability-registry cache — a just-deprecated non-approved adapter version still served from cache; recovery: registry cache TTL ≤ 30 s, matching the health-poll interval.
  • Crossfade window miscalibrated against real loop length — a loop rendered slightly short of 30s causes the crossfade engine to overlap into silence; recovery: the adapter reports its realizedDurationMs (§11.7 AdapterResponse) and the player crossfade window is computed from that measured value, never the requested value.

⬜ Phase 5 — Streaming Runtime & Scene Scheduler §17

Objectives
  • Build the real Scene Scheduler / Streaming Runtime: parallel adapter dispatch, buffer-ahead guarantee (I7), WebSocket streaming protocol.
Deliverable

A player session shows zero visible scene-to-scene gaps across a 30-minute run under nominal adapter latency; TTFF ≤ 8 s.

Acceptance
  • TTFF p95 ≤ 8 s (§4), measured over 200 session starts.
  • Buffer-depth gauge (I7) never reports "empty + not-buffering" — 0 silent-stall events across a 1,000-session load test.
  • Scene-to-scene visible gap: 0 s median across the same load test (fixtures/gapless-30min.json).
Fixtures
  • fixtures/gapless-30min.json — 30-minute session under nominal latency. Expected: 0 visible gaps.
  • fixtures/queue-overflow.json — a burst of vibe changes exceeding dispatch-queue depth 3. Expected: excess plans rejected, not buffered (ADR-24), viewer sees a graceful "still composing" state, not an error.
  • fixtures/deadline-clock-skew.json — a simulated wall-clock jump (NTP correction) mid-session. Expected: scheduling unaffected (monotonic clock, ADR-23).
  • fixtures/rolling-deploy-drain.json — a scheduler instance draining mid-session during a simulated rollout. Expected: session hand-off completes within the 15 s shutdown budget (§4), no dropped scene.
Pitfalls
  • Buffer accounting drift — the buffer-depth gauge undercounts a scene still rendering, showing false "empty" alerts; root cause: gauge updated on dispatch, not on commit; recovery: gauge increments only at committed state (§8.3).
  • Thundering-herd dispatch — all modality adapters for a scene fire simultaneously, causing a shared-dependency (e.g. KMS, §13) latency spike; recovery: stagger non-latency-critical calls (e.g. audit-log writes) outside the critical dispatch path.
  • WebSocket envelope version skew between an old cached player bundle and a newer server envelope; recovery: envelope carries a version field, older players ignore unknown fields (additive-only wire contract, P8-adjacent).
  • Monotonic-clock/wall-clock confusion at the deadline boundary — a scheduler component logs a deadline in wall-clock time for a human-readable dashboard, then accidentally compares it against a monotonic timestamp; recovery: the two clock domains are distinct types at compile time (never both plain number), enforced by the same branding discipline as §11.8.

⬜ Phase 6 — Safety Classifier Ensemble & Audit Pipeline §18

Objectives
  • Build the non-bypassable Safety Classifier Ensemble (P4, I3) and the per-scene audit-log pipeline; certify the sleep-mode dual-classifier path (I4, P5).
Deliverable

A release-gating CI job runs the full adversarial corpus and reports 0 sleep-mode false negatives; every committed scene has a complete audit record.

Acceptance
  • Sleep-mode adversarial corpus (200 prompts): 0 unsafe emissions reach committed state (§4 zero-tolerance gate).
  • General adversarial corpus (1,000 prompts): false-negative rate < 0.1% (fewer than 1 miss per 1,000).
  • Audit completeness: 100% of committed scenes have a non-null safetyAudit record (I8-adjacent for safety metadata).
Fixtures
  • fixtures/sleepmode-adversarial-200.json — 200 adversarial sleep-mode prompts. Expected: 0 pass-through.
  • fixtures/general-adversarial-1000.json — 1,000 general adversarial prompts. Expected: < 0.1% false negatives.
  • fixtures/audit-completeness-scan.json — a 10,000-scene sample. Expected: 100% non-null safetyAudit.
  • fixtures/classifier-model-pin-regression.json — the sleep-mode corpus (§18.4) re-run against an unpinned classifier model version. Expected: no score regression relative to the pinned baseline (§18.9).
Pitfalls
  • Classifier false positives collapsing immersion — an overly strict general classifier blocks benign scenes; recovery: a soft-warn tier (§11.2 safetyAudit.decision) nudges the Composer to replan mid-scene rather than hard-blocking, with weekly false-positive review.
  • Ensemble disagreement handled inconsistently — general classifier passes, sleep classifier blocks (or vice versa) with no defined precedence; recovery: sleep-mode classifier decision is authoritative whenever Stream.mode === "sleep" (explicit precedence rule, I4).
  • Audit-log write failure silently dropping records — a scene commits even though its audit write failed; recovery: audit write is part of the same transaction as the scene commit (I8-adjacent atomicity), a failed audit write blocks the commit.
  • Adversarial-corpus staleness — the 200-prompt sleep-mode corpus stops reflecting current adversarial technique because it was written once and never revisited; recovery: the corpus is versioned and appended to after every T9 evasion disclosure (§22), never treated as a frozen artifact.

⬜ Phase 7 — GPU Orchestration Pool & Cost Telemetry §19

Objectives
  • Build multi-provider GPU/inference routing to hold ¢/SH inside the phase ceiling (P9, §4); wire cost telemetry as a CI-gated metric.
Deliverable

A cost dashboard shows real-time ¢/SH per phase cohort; a synthetic provider-outage drill demonstrates automatic failover with no session interruption beyond one buffering cycle.

Acceptance
  • ¢/SH at p50 ≤ Phase 1 ceiling of $0.40 (§4) across a 500-session benchmark.
  • Provider failover drill: session resumes within 1 buffering cycle (≤ 2 s per I7 recovery target) after a simulated primary-provider outage.
  • CI cost-regression gate: 0 merged PRs with an unreviewed ¢/SH regression > 10%.
Fixtures
  • fixtures/cost-benchmark-500.json — 500-session cohort. Expected: p50 ¢/SH ≤ $0.40.
  • fixtures/provider-outage-drill.json — simulated primary-provider 503 storm. Expected: failover within 1 buffering cycle.
  • fixtures/hedged-request-tail.json — synthetic p99 latency injection. Expected: hedged request reduces realized p99 by ≥ 30% vs. unhedged baseline.
  • fixtures/reconciliation-heartbeat-gap.json — the cost-reconciliation job (I14) is paused mid-run. Expected: cost.reconciliation_delta heartbeat-gap alert fires within one missed cycle, distinct from a divergence alert.
Pitfalls
  • Hedging doubling cost silently — a naive hedge-always policy sends two billed calls per request; recovery: hedge only past a declared p95 threshold, and cancel the loser (I11) the instant the winner returns.
  • Circuit breaker flapping — a provider oscillating between healthy/unhealthy causes routing thrash; recovery: require 3 consecutive good/bad polls before flipping state (matches the adapter health-poll cadence from Phase 3).
  • Cost-dashboard double-counting cancelled calls that were partially billed before cancellation landed; recovery: reconcile provider invoices against adapter.leaked_gpu_minutes weekly, not just trust the real-time estimate.
  • Provider-diversity illusion — primary and secondary providers for a modality turn out to share a common upstream dependency (e.g. the same underlying GPU cloud), so "failover" doesn't actually diversify risk; recovery: provider-diversity ADRs (§9) must document the actual infrastructure dependency chain, not just the API vendor name, per the FM-9-adjacent correlated-outage lesson (§19.9).

⬜ Phase 8 — CDN / Edge Asset Cache & Session Resume §20

Objectives
  • Build the CDN/Edge Asset Cache to amortize cost on session resume and repeat asset hits; hit the ≥ 35% edge-cache-hit-rate target (§4).
Deliverable

A viewer resuming a world after 48 hours sees the world's establishing imagery load from edge cache with measurably lower latency and zero regeneration cost for those assets.

Acceptance
  • Edge-cache hit rate ≥ 35% on resume sessions (§4), measured over a 1,000-session resume cohort.
  • Cache-served asset latency p95 ≤ 200 ms (vs. ≥ 4 s regenerated), measured on the same cohort.
  • 0 cache promotions of assets with null provenance (I8 enforcement at the cache-promotion boundary).
Fixtures
  • fixtures/resume-cache-hit-1000.json — 1,000 resume sessions. Expected: ≥ 35% hit rate.
  • fixtures/cache-promotion-provenance-check.json — assets with deliberately null provenance fields. Expected: 100% rejected at promotion.
  • fixtures/lru-eviction-quota.json — a user exceeding their storage quota. Expected: oldest assets evicted, evictedAt recorded, no silent deletes.
  • fixtures/checksum-corruption-scale.json — a synthetic batch of assets with deliberately corrupted checksums. Expected: cache-promotion pause triggers once the failure rate crosses threshold (§20.9), reads fall back to origin.
Pitfalls
  • Cache key collision across users — a naive cache key derived only from promptHash could theoretically collide across two users' near-identical prompts; recovery: edgeCacheKey is namespaced by userId (P11/I12 extended to the cache layer).
  • Stale cache serving a pre-migration asset shape — a schema-major-version bump changes asset metadata shape but cached blobs are unaffected (blobs are opaque); recovery: only the metadata row is versioned, cache stores immutable blobs so this is a non-issue by construction — document it as a deliberate non-pitfall to prevent needless "fixes."
  • Eviction racing an in-flight resume read — an asset evicted the instant a resume flow tries to serve it from cache; recovery: read-through fallback regenerates on a cache miss rather than erroring.
  • Quota accounting drift between the cache and the storage bill — the per-user LRU quota (§20.2) is tracked in the cache metadata but the actual object-storage bill diverges due to a delayed-delete queue; recovery: quota accounting reconciles against a nightly storage-provider listing, not just the cache's own bookkeeping.

⬜ Phase 9 — Video Adapter & Long-Form Streaming §21

Objectives
  • Ship adapter-video; build the clip-stitching layer for near-continuous long-form video; hit the Phase 9 ¢/SH ceiling of $2.50 (§4).
Deliverable

A 30-minute continuous 720p video session runs with no visible seams between clips and ¢/SH ≤ $2.50 measured over a benchmark cohort.

Acceptance
  • ¢/SH ≤ $2.50 at p50 (§4) over a 200-session 720p benchmark — this is the Phase 9 (and full-system) exit criterion.
  • Visual-continuity classifier (extended from Phase 3, §15.4): returning characters recognizable in ≥ 70% of clips across a 100-clip test corpus.
  • Video-adapter cancellation cleanliness: ≥ 95% GPU-cost reclaim within 2 s across 1,000 cancellations (I11, extended to video's higher-cost calls).
Fixtures
  • fixtures/continuous-video-30min.json — a 30-minute synthetic stream. Expected: 0 visible clip-boundary seams (frame-difference classifier below threshold at every splice point).
  • fixtures/video-character-consistency-100.json — 100 clips, one returning character. Expected: ≥ 70% recognized match.
  • fixtures/video-cost-benchmark-200.json — 200-session cohort. Expected: p50 ¢/SH ≤ $2.50.
  • fixtures/stitch-regression-fleetwide.json — a simulated fleet-wide stitching-layer model bump. Expected: release-gate blocks promotion if video.stitch_seam_score regresses on the conformance corpus (§21.9).
Pitfalls
  • Stitching artifacts at high-motion boundaries — the last-frame-conditioning technique degrades when clip i ends mid-motion; recovery: the Composer plans clip boundaries at low-motion narrative beats (an N.2 scheduling hint, not a video-adapter fix).
  • Cancellation cost asymmetry — video generation is far more expensive per call than image/music, so a missed cancellation is proportionally costlier; recovery: video-specific cancellation deadline is tighter (1 s, not the general 2 s) and monitored as its own SLI.
  • Provider cost-routing oscillation — routing flips between cheap/premium providers scene-to-scene in a way that itself becomes visually inconsistent; recovery: routing decision is sticky per-world for a rolling window, not re-decided every scene.
  • Stitching-conditioning frame fetched from the wrong cache tier — the last-frame extraction accidentally reads from origin object storage instead of the CDN edge cache (§20), adding hundreds of milliseconds to every clip boundary; recovery: the stitching layer's frame-fetch path is a dedicated, monitored call (video.stitch_frame_fetch_latency), never a fallthrough of the generic asset-read path.
