1. Goal & Scope

Engineering definition. Build, from scratch, a columnar vectorized execution planner and runtime: a system that lowers declarative relational queries (a bound SQL AST) through relational algebra, cost-based optimization, and physical pipeline construction, into a vectorized execution graph that runs over Arrow-inspired columnar batches with deterministic operator semantics, bounded memory behavior under a hard quota, spill-to-disk overflow when that quota is exceeded, and observability-first instrumentation (metrics, tracing, deterministic replay) sufficient to debug a production regression from an operator trace alone, without attaching a debugger. The unit of work at every layer is a VectorBatch (§11), not a tuple; every operator, every kernel, and every scheduler decision is expressed in terms of batches, selection masks, and validity bitmaps.

This is not a SQL front-end and not a toy iterator engine. It is the execution core that sits beneath a query surface: parser → binder → logical plan → optimizer → physical plan → vectorized runtime → observability. Each of those seven layers is a real subsystem with its own invariants, failure modes, and test surface, built in the phase order fixed by §12–§21.

System boundary — provides:

  • logical query representation and relational algebra transformation (§14),
  • rule-based and cost-based optimizer infrastructure with histogram-driven cardinality estimation (§15),
  • physical planning: pipeline construction, batch-size planning, pipeline-breaker placement (§16),
  • a columnar memory engine: flat/dictionary/constant/sequence vectors, validity bitmaps, slab arenas, spill-aware allocation (§17),
  • an expression compiler lowering scalar expressions to SIMD vector kernels with branchless null propagation (§18),
  • vectorized hash-join and hash-aggregation engines with spill-to-disk under memory pressure, runtime filter propagation, and skew handling (§19),
  • a cooperative work-stealing scheduler with NUMA-aware affinity hints and backpressure propagation across every queue and exchange edge (§20),
  • a disk-backed spill engine, deterministic replay trace persistence, and a metrics/tracing observability layer wired into every subsystem from Phase 0 onward (§21),
  • local (single-process, multi-core) parallel exchange operators, architected so partition routing generalizes to a distributed transport later (§16, §21, deferred item in §35).

System boundary — delegates (assumed present, not built here):

  • an external SQL surface / connector layer (JDBC/ODBC, wire protocol) — this system consumes a bound AST, not client connections,
  • durable base-table storage — the storage-abstraction crate (§10) defines the scan trait; a real storage engine (Parquet files, an existing columnar store) implements it,
  • a catalog service beyond the in-process catalog crate's snapshot-consistent metadata store (§7, I10).

System boundary — does NOT provide:

  • distributed consensus or a distributed transaction coordinator,
  • a transactional MVCC storage engine or durable WAL,
  • full ANSI SQL:2016 conformance (a conformance subset is defined in §26, not the full standard),
  • multi-tenant security/authn/authz,
  • cloud-native autoscaling control planes,
  • row-oriented OLTP storage,
  • a production JDBC/ODBC connector.

Explicit non-goals: a full distributed warehouse; a transactional database kernel; a durable WAL-based storage layer; a hand-written parser-generator framework (the parser is a hand-rolled recursive-descent parser, not a generator); an adaptive ML-based optimizer; GPU-native vector kernels before the system is CPU-vectorization-complete (deferred, §35); distributed fault-tolerant shuffle recovery; fully asynchronous storage engines.

Deployment model: single-node first. NUMA-aware multi-core execution on one host, local SSD-backed spill storage, optionally containerized (Linux-first, cgroup-aware memory accounting). The exchange abstraction (§16, §21) is deliberately partition-addressed rather than thread-addressed so a later phase can swap the in-process transport for a networked one without touching operator code — that swap is explicitly deferred (§35) and out of scope for this blueprint's ten phases.

Target operators: infrastructure engineers running the runtime in production; benchmarking engineers gating releases on the Performance Engineering targets (§28); SREs evaluating crash-free duration and replay fidelity (§24); incident responders reconstructing an execution from replay traces (§21, §23) during a postmortem.

Primary developers / users: systems and database-kernel engineers, compiler/runtime engineers, query-optimization researchers, storage-engine developers building the storage-abstraction trait implementation, performance engineers doing flamegraph-driven tuning (§28).

What later phases unlock (beyond this blueprint's 10 phases): distributed exchange transport, adaptive mid-query re-optimization, JIT-compiled vector kernels, Arrow/Parquet-native zero-copy scans, GPU vector execution, and vectorized window operators — all formally registered as deferred in §35, anchored to the phase each would extend: PhaseDeferred("§16") for distributed exchange transport (generalizing the in-process partition router built there); PhaseDeferred("§16") for Arrow/Parquet-native zero-copy scan (extending the VectorScan operator built there); PhaseDeferred("§15") for adaptive mid-query re-optimization (extending the cost model built there); PhaseDeferred("§18") for JIT-compiled vector kernels (extending the static kernel-fusion built there); PhaseDeferred("§18") for GPU vector execution offload (an alternate backend for the same kernel-dispatch boundary); PhaseDeferred("§19") for a vectorized window-function engine (extending the aggregation engine built there).

Recommended implementation language: Rust. Rationale, weighed against the rejected alternatives:

  • vs. C++ — Rust wins on ownership-checked memory safety under concurrency (no use-after-free in the scheduler's work-stealing deques, §20) without giving up manual allocation control (vector-memory slab arenas, §17) or SIMD access (std::simd). C++ wins when a team already has a decade of hand-tuned SIMD kernels and cannot afford a rewrite — not the case here (see ADR-01, regime column).
  • vs. Go — Go's GC introduces pause behavior incompatible with the p99 scheduler-stall budget (§4); Go's lack of a real SIMD story rules it out for expression-engine (§18).
  • vs. Java — JVM GC pause and object-header overhead per ColumnVector are incompatible with the columnar memory ceilings in §4; JIT warm-up conflicts with the <500 ms warm-startup target.
  • vs. C — no ownership model, so vector-memory lifetime bugs (I11, dangling selection masks) become undetectable at compile time; manual memory-safety auditing does not scale to 30 crates.

Prerequisites: relational algebra; database internals; vectorized execution models; cost-based optimization; memory allocator behavior; CPU cache hierarchies; NUMA behavior; concurrency primitives and lock-free structures; storage engine fundamentals; SIMD execution; branch prediction; OS virtual memory; async/cooperative scheduling; compiler IR design; serialization formats; tracing/metrics systems; deterministic replay systems; performance profiling and flamegraph analysis; benchmarking methodology.

2. Why Build This

Modern analytical databases are execution engines built around vectorized columnar batch processing, not tuple-at-a-time Volcano iterators. Building this planner forces the internalization of why that inflection happened: modern CPUs are constrained less by raw arithmetic throughput than by branch misprediction, cache-miss penalties, memory bandwidth, TLB pressure, and pipeline stalls. A tuple-at-a-time next() call defeats every one of those; a vectorized execute(batch) call amortizes the per-call overhead across thousands of rows and lets the compiler and CPU exploit SIMD.

This project teaches, in dependency order: relational query transformation (§14); optimizer architecture and cost-based join ordering (§15); vector execution semantics — selection masks, null propagation, batch contracts (§16–§18); CPU-aware operator design (§18–§19); memory locality engineering (§17); runtime scheduling and backpressure (§20); spill-aware execution under memory pressure (§21); exchange/shuffle semantics and pipeline-breaking behavior (§16); cardinality propagation and its failure modes (§15); instrumentation-driven debugging via deterministic replay (§21, §23).

Production engineering concepts exercised: bounded queues and backpressure propagation (§20); pipeline scheduling under NUMA constraints (§20); spill recovery (§21); allocator tuning (mimalloc, ADR chosen in §17); execution telemetry as an API contract (P11); tail-latency stabilization (§28); deterministic replay (§21); structured failure analysis (§23); operator instrumentation (§12.10–§21.10); runtime feature gating for staged rollout (§25).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: all planner and runtime behavior is reproducible given identical inputs and statistics; any randomized algorithm uses a fixed seed. · Tradeoff: reduced optimizer exploration entropy vs. ad-hoc randomized search. · Operational: replay fidelity (I9) depends on this holding everywhere. · Violated: replay divergence, optimizer plan instability, non-debuggable production regressions.
  • P2 — Backpressure Everywhere. Rule: every queue, exchange edge, and pipeline boundary propagates pressure upstream instead of buffering unboundedly. · Tradeoff: added latency at the producer under load vs. unbounded memory growth. · Operational: queue-depth telemetry is mandatory on every edge (§20). · Violated: unbounded memory growth, spill storms, scheduler collapse.
  • P3 — Bounded Resource Ownership. Rule: every allocation carries ownership metadata and lifetime tracking; nothing is allocated without a designated owner that frees it. · Tradeoff: extra bookkeeping per allocation vs. raw malloc/free simplicity. · Operational: vector-memory pool audits detect orphaned allocations (§17.9). · Violated: memory leaks, orphan vectors, spill deadlocks.
  • P4 — Observability Before Optimization. Rule: no subsystem ships without metrics and tracing hooks, even before it is performance-tuned. · Tradeoff: instrumentation overhead on the hot path vs. debuggability. · Operational: every phase's N.10 subsection names the metrics added. · Violated: opaque failures, impossible tail-latency debugging.
  • P5 — Immutable Logical Plans. Rule: a logical plan becomes immutable the instant it is submitted to the optimizer; rewrites produce new plan nodes, never mutate in place. · Tradeoff: more allocation churn during rewrite passes vs. free concurrent read access. · Operational: plan nodes are Arc-shared read-only after submission. · Violated: nondeterministic optimizer state corruption, unreplayable rewrite order.
  • P6 — Explicit Pipeline Breakers. Rule: every materialization boundary (sort, hash-build, full aggregation) is an explicit physical-plan node, never an implicit buffering side effect. · Tradeoff: more visible plan complexity vs. hidden memory amplification. · Operational: pipeline breakers are enumerable from the execution graph (§16.2). · Violated: hidden memory amplification, replay instability.
  • P7 — Replayability First. Rule: every execution trace reconstructs the full sequence of runtime state transitions, not just final results. · Tradeoff: replay-log write volume vs. forensic completeness. · Operational: ReplayEvent sequence numbers are strictly increasing (I9). · Violated: irrecoverable production debugging gaps.
  • P8 — Columnar Memory Canonicalization. Rule: all vectors obey one of four stable layouts (flat/dictionary/constant/sequence, §11) with fixed binary semantics across versions. · Tradeoff: less layout flexibility vs. operator interoperability. · Operational: operators cannot assume a layout beyond the ColumnVector contract. · Violated: operator incompatibility, SIMD alignment faults.
  • P9 — Spill as First-Class Behavior. Rule: spill code paths are engineered and tested to the same bar as the in-memory path, never a fallback afterthought. · Tradeoff: implementation cost of a second execution path per operator vs. graceful degradation under memory pressure. · Operational: fixtures/spill/ conformance suite runs on every release (§26). · Violated: catastrophic degradation under memory pressure, spill-path bugs discovered only in production.
  • P10 — Fail Closed. Rule: any invariant violation aborts the query rather than returning a possibly-corrupt result. · Tradeoff: reduced availability for a single query vs. zero silent corruption. · Operational: invariant checks are compiled into every operator boundary in debug and fixture builds. · Violated: silent result corruption — the single failure budget item in §4 set to zero.
  • P11 — Metrics Are APIs. Rule: telemetry schemas are versioned and compatibility-checked like any other public interface. · Tradeoff: metrics-schema migration overhead vs. safe consumer evolution. · Operational: metrics additions follow the same semver discipline as operator contracts (§25). · Violated: silent dashboard breakage on upgrade, undetected metric renames.
  • P12 — Isolation of Optimization Phases. Rule: logical rewrites (§14) and physical rewrites (§16) never share a rule engine or intermix passes. · Tradeoff: some rule duplication across layers vs. clean separation of algebra-preserving vs. execution-shape rewrites. · Operational: optimizer never imports physical-plan types. · Violated: correctness rules silently becoming execution-shape rules, unreplayable rewrite ordering.
  • P13 — Explicit Null Semantics. Rule: null propagation through every kernel is written into the kernel signature, never inferred implicitly from a sentinel value. · Tradeoff: an extra validity-bitmap parameter on every kernel vs. implicit sentinel encoding. · Operational: I3 (null-bitmap consistency) is checked at every batch boundary. · Violated: silent null-handling bugs that differ per kernel, non-portable sentinel collisions.
  • P14 — Stable Operator Contracts. Rule: an operator's batch-in/batch-out contract is backward compatible across minor versions once shipped. · Tradeoff: contract rigidity vs. easy iteration. · Operational: contract changes are MAJOR-version events (§25). · Violated: silent operator incompatibility after an upgrade, undebuggable cross-version pipeline failures.

11. Core Schema & Types

struct QueryPlan
    logical_root: LogicalNodeId
    physical_root: PhysicalNodeId
    execution_graph: ExecutionGraphId

Ownership: owned by runtime for the query's lifetime, immutable after physical planning (P5). Mutation: none post-construction. Concurrency: Arc-shared, read-only across worker threads. Persistence: replay-serializable via replay::trace (I9). Serialization: protobuf, field-reserved per ADR-05. Compatibility: MAJOR-version bump if execution_graph topology semantics change (§25).

struct VectorBatch
    batch_id: BatchId
    cardinality: u32
    columns: Vec<ColumnVector>
    selection_mask: SelectionMask
    null_masks: Vec<ValidityBitmap>

Ownership: allocated and freed by vector-memory pools (P3); an operator borrows a batch for the duration of execute(). Mutation: payload buffers are mutable in place for in-pipeline operators; batch_id and cardinality are immutable metadata (I1). Concurrency: single-writer per batch — never shared across threads while Running (I5). Persistence: spillable via spill-engine segment encoding (I4). Serialization: Arrow-compatible buffer layout (RFC: Arrow Columnar Format). Compatibility: layout is one of four fixed kinds (P8); adding a fifth is a MINOR-compatible additive change if existing kinds are untouched.

enum ColumnVector
    Flat(FlatVector)
    Dictionary(DictionaryVector)
    Constant(ConstantVector)
    Sequence(SequenceVector)

Ownership: owned by the enclosing VectorBatch. Mutation: Flat payload mutable in place; Dictionary/Constant/Sequence are conceptually immutable views. Concurrency: same rules as VectorBatch. Persistence: each variant has a dedicated spill encoding (§21). Serialization: stable discriminant tag per RFC (Arrow Columnar Format). Compatibility: stable binary semantics — variant order is append-only (P8, I8).

struct ExecutionTask
    task_id: TaskId
    pipeline_id: PipelineId
    state: AtomicTaskState

Ownership: owned by scheduler from Created to a terminal state. Mutation: state transitions via compare-and-swap only (I5, I12). Concurrency: lock-free, one owning queue at a time (I5). Persistence: transient — no direct persistence, but every transition emits a ReplayEvent. Serialization: not wire-serialized; observable only via telemetry. Compatibility: AtomicTaskState transition table is append-only across versions.

struct SpillSegment
    segment_id: SegmentId
    checksum: u64
    row_count: u64

Ownership: owned by spill-engine for the segment's on-disk lifetime. Mutation: immutable once written and checksummed (I4). Concurrency: single-writer, multi-reader during recovery. Persistence: durable for the temp lifecycle, cleaned up per §21.6. Serialization: binary segmented format mirroring the columnar buffer layout of ADR-04 (Vector Layout), formalized here as the spill wire format. Compatibility: forward-compatible header versioning (§25).

trait RuntimeMetric
    fn emit(&self, sink: &mut MetricsSink);
    fn snapshot(&self) -> MetricSnapshot;

Ownership: implemented by every subsystem's metric types; no shared mutable state beyond the sink. Mutation: emit is append-only to the sink. Concurrency: sink is internally synchronized (lock-free counters, ADR chosen for telemetry). Persistence: snapshots are what replay embeds. Serialization: Prometheus exposition format (ADR-11). Compatibility: versioned per P11.

trait Operator
    fn initialize(&mut self, ctx: &OperatorContext) -> Result<(), OperatorError>;
    fn execute(&mut self, batch: &mut VectorBatch) -> Result<(), OperatorError>;
    fn finalize(&mut self) -> Result<(), OperatorError>;

Ownership: one instance per pipeline stage, owned by vector-engine. Mutation: internal operator state is mutable across calls; batch contract is immutable at the trait boundary (P14). Lifecycle guarantee: initialize exactly once, execute zero-or-more times, finalize exactly once, even on the cancellation path (I12). Concurrency: an operator instance is single-threaded; parallelism comes from multiple instances across partitions. Persistence: none directly; spill-capable operators delegate to spill-engine. Serialization: n/a. Compatibility: contract changes are MAJOR (P14, §25).

struct ExchangePacket
    partition_id: u32
    sequence_no: u64
    payload: VectorBatch

Ownership: owned by exchange from send to receive acknowledgment. Mutation: immutable in transit. Concurrency: sequence_no is monotonic per partition (I7 depends on deterministic partition routing, not sequencing, but both are enforced together). Persistence: not persisted unless the exchange edge is also a pipeline breaker with spill. Serialization: protobuf (ADR-05). Compatibility: semver-versioned wire format (§25).

struct ReplayEvent
    event_id: u64
    timestamp_ns: u64
    event_type: ReplayEventType

Ownership: owned by replay for the append-only log's lifetime. Mutation: append-only, never mutated post-write (I9). Concurrency: single-writer per query, multiplexed across queries by event_id namespace. Persistence: durable, chunked-zstd compressed on rotation. Serialization: append-only custom binary format (ADR-05's "custom binary vector frames" lineage). Compatibility: ReplayEventType is an append-only enum across MINOR versions.

struct SchedulerQueue
    runnable: LockFreeDeque<TaskId>

Ownership: one per worker thread, owned by scheduler. Mutation: push/pop via lock-free deque operations only (Mara Bos, Rust Atomics and Locks, §5). Concurrency: work-stealing — other workers may pop from the tail (I5 still holds: exactly one queue owns a task at a time). Persistence: none — purely in-memory scheduling state. Serialization: n/a. Compatibility: internal type, no external compatibility contract.

struct CatalogSnapshot
    snapshot_id: u64
    tables: Vec<TableMetadata>
    issued_at_ns: u64

Ownership: owned by catalog, immutable once issued (I10). Mutation: none — a new mutation produces a new snapshot_id. Concurrency: Arc-shared across concurrent binds. Persistence: not durably persisted itself; derived from the durable catalog store. Serialization: internal only. Compatibility: TableMetadata additions are additive/MINOR.

struct CostEstimate
    cpu_cost: f64
    io_cost: f64
    memory_cost_bytes: u64
    spill_risk: SpillRiskClass

Ownership: owned by cost-model, attached to each candidate plan in the optimizer memo. Mutation: recomputed, never mutated in place, on every rewrite (P5). Concurrency: read-only once attached to a memo entry. Persistence: included in explain-plan snapshots (§21.2). Serialization: JSON (explain format, §21.2). Compatibility: additive fields are MINOR; removing a field is MAJOR.

Add scheduler telemetry (queue depth, steal count, task-latency histograms). Implement backpressure propagation (P2): a Blocked transition on any exchange or queue edge above its credit limit (ADR-21) stalls the producer pipeline rather than buffering unboundedly. Add NUMA affinity hints consumed from §16's physical-plan annotations — worker threads pinned per socket, work-stealing preferring same-socket victims first (Leis et al. 2014's morsel-driven NUMA locality, §5). Implement queue- saturation alerts when queue depth approaches the 256-runnable-task budget (§4).

20.3 Deliverable

A parallel vector runtime: runtime orchestrates scheduler + vector-engine operators across 64 execution threads (§4), exercised end-to-end by fixtures/scheduler/ and the TPC-H-inspired benchmark suite (§28).

20.4 Acceptance Criteria

  • bounded queue growth: no queue exceeds the 256-task depth budget (§4) under fixtures/scheduler/saturation.fixture without triggering backpressure first,
  • p99 scheduler stall <25 ms (§4 target, unchanged) measured over a 10-minute sustained-load run,
  • cancellation completes within 2 s for 100% of 1,000 injected-cancellation runs of fixtures/scheduler/cancellation.fixture,
  • zero double-enqueue events (I5) and zero duplicate-terminal-transition events (I12) over a 72h soak (§4).

20.6 Pitfalls

  1. Queue starvation when work-stealing always prefers the same victim queue — manifestation: one worker thread idles while another's queue backs up; root cause: steal-victim selection not randomized/rotated; debug via per-queue depth telemetry over time; signal: fairness-variance metric exceeding a documented ceiling; recovery: rotate victim selection.
  2. Deadlock cycles between two pipelines each waiting on the other's exchange backpressure release — root cause: a physical plan with a genuine circular data dependency, which §16's DAG validator should have rejected; signal: stalled-task detector (no state transition for N seconds); recovery: forced cancellation of the deadlocked query, and a regression fixture added to §16.
  3. False sharing between two AtomicTaskState fields placed on the same cache line — manifestation: throughput regression under high concurrency invisible in single-threaded profiling; root cause: struct layout not cache-line-padded; signal: perf c2c (cache-to-cache) report; recovery: pad ExecutionTask to a cache-line boundary.

20.7 Performance Concerns

Lock contention is designed out via lock-free deques (Bos, §5), but false sharing remains a risk (above); queue occupancy telemetry itself must not become a contention point (use per-worker counters, aggregate on read, not on write); NUMA cross-socket steals cost a measurable latency penalty, hence the same-socket preference.

20.8 Edge Cases

Cancellation arriving during a spill operation (§21) — must not corrupt the in-progress spill segment, must wait for a checksum-safe boundary; exchange stalls when a downstream pipeline is permanently blocked (must eventually escalate to cancellation, not hang indefinitely); a task migrating between NUMA-node queues under steal (affinity hint is a preference, not a hard constraint — correctness must not depend on it).

20.9 Failure Analysis

Scheduler traces reconstruct every runnable-queue transition from the replay log (P7), letting a deadlock or starvation incident be replayed exactly rather than reasoned about from a live-system snapshot. Blast radius for a stalled task is contained to its own pipeline until the stall-detector escalates; other pipelines continue under their own backpressure budgets (P2).

20.10 Operational Notes

21. Phase 9 — Spill Engine, Replay & Observability

21.1 Objectives

Implement the resilient disk-backed spill subsystem and the observability layer (metrics, tracing, deterministic replay) that every earlier phase has been emitting into since Phase 0. Constraints: zero silent-corruption budget (§4), 100% replay fidelity (§4), spill checksum integrity (I4).

21.2 Detailed Implementation Steps

Implement spill writers in spill-engine/src/writer.rs: segmented spill files (binary segmented format, ADR lineage from §9's ADR-04 predecessor) with per-segment checksums in spill-engine/src/checksum.rs (I4). Add spill-recovery metadata — a manifest mapping SegmentId -> (checksum, row_count, partition_id) cached within the 128 MB spill-metadata budget (§4). Implement temp-file cleanup lifecycle (delete-on-finalize, orphan-sweep on startup) and disk-pressure alerts when available spill-storage headroom drops below a documented floor. Implement spill throttling — a rate limiter preventing fsync storms from a burst of concurrent spill triggers across queries sharing the same disk (P2 applied to disk IO, not just memory). Implement structured tracing in tracing/ (OpenTelemetry, ADR-10) and the metrics registry in telemetry/src/metrics.rs (Prometheus, ADR-11), both wired retroactively into every crate's instrumentation points added since §12. Add replay-event persistence in replay/src/trace.rs: append-only binary log (I9), chunked-zstd-compressed on rotation. Implement explain-plan snapshots and flamegraph-export tooling (scripts/profile.sh, §12). Implement query-execution replay: planner replay <trace> reconstructs the full state-transition sequence for a completed or crashed query.

21.3 Deliverable

Disk-backed overflow runtime plus replayable diagnostics: spill-engine survives injected corruption and disk-full conditions; planner replay reconstructs a crashed query's execution state with byte-identical fidelity against the original run.

21.6 Pitfalls

  1. Temp-file leaks when a query is cancelled mid-spill and the cleanup lifecycle isn't invoked on the cancellation path — manifestation: FD budget (1024 spill FDs, §4) creeping toward exhaustion over a long-running host; root cause: cleanup hooked to Finished only, not Failed/cancelled; signal: FD-count telemetry trend; recovery: hook cleanup to every terminal state (I12-consistent).
  2. Checksum drift between the writer's checksum algorithm version and the reader's, across a rolling upgrade — root cause: no checksum-algorithm version tag in the segment header; signal: false-positive corruption alerts immediately after a deploy; recovery: version-tag the checksum algorithm, per §25's compatibility rules.
  3. Telemetry overload from per-row tracing spans instead of per-batch — manifestation: tracing overhead dominates the operator's own execution cost; root cause: span granularity mismatched to batch-oriented execution; signal: perf showing tracing-library frames dominating the profile; recovery: span per batch, not per row, matching the vectorized execution model throughout.

21.7 Performance Concerns

fsync storms under concurrent spill triggers (mitigated by the throttling rate limiter above); IO amplification from segment metadata overhead relative to payload size (bounded by the <1.5x spill- amplification target, §4); tracing-span cardinality explosion if span attributes include high-cardinality fields like raw row values (avoid — attribute only IDs and counts).

21.8 Edge Cases

Partial writes from a process kill mid-segment-flush (must be detectable as a truncated segment, distinct from a corrupted-but-complete one, via a segment-length field checked before checksum); disk-full conditions (must fail closed — abort the query, per P10 — rather than write a truncated segment silently); replay during spill recovery (a replay reconstruction that itself needs to read spilled data must not deadlock against a live recovery holding the same segment lock); clock skew between timestamp_ns fields across a host-migration scenario (replay ordering relies on event_id monotonicity, I9, never on wall-clock comparison, per ADR-20).

21.9 Failure Analysis

Spill forensics reconstruct exact segment timelines from the manifest plus the replay log, letting an operator determine which segment was being written at the moment of a crash without guessing. Trace gaps are surfaced through the integrity scanner run as part of the 72h soak (§4) and as a release gate (§27). Blast radius for a corrupted segment is contained to its own partition — I4's per-segment (not per-file) checksum granularity means one bad segment does not invalidate its siblings.

Metrics: spill_bytes_written_total, spill_corruption_total, replay_gap_total, replay_fidelity_ratio. Tracing spans: spill_engine.write, spill_engine.recover, replay.replay. Structured-log fields: segment_id, partition_id, event, matching the source system's spill_start-style structured event convention. 25. Compatibility & Versioning

Wire compatibility: ExchangePacket (§11) is semver-versioned; a MAJOR bump is required for any field removal or reinterpretation. Storage compatibility: spill segment headers (§21) are forward-compatible — an older reader can skip unknown-but-reserved header fields per the protobuf field-reservation rules (RFC: proto3 Language Guide, §5). Schema evolution: field reservation is enforced by a CI lint that rejects a field-number reuse. API stability: operator contracts (P14) are versioned identically to the crate's own semver — a contract-breaking change is a MAJOR release regardless of how small the code diff is.

Migration guarantees: replay ships schema translators for the two most recent MAJOR versions, letting an operator replay an old trace against a current build. Deprecation policy: a minimum of two MINOR versions between deprecation notice and removal. Semantic versioning: MAJOR for operator- contract or wire-format breaks; MINOR for additive features (new ColumnVector variant, new metric); PATCH for bug fixes with no contract change. Rolling upgrades: mixed-version replay compatibility is required for one MAJOR version boundary — I7's deterministic partition hashing must produce identical assignments on both sides of a rolling upgrade, or the upgrade is blocked.

29. Scalability Analysis

Primary bottlenecks: memory bandwidth (aggregation/projection kernels, §18), hash-table locality (join/aggregation probe, §19), spill IO (§21), scheduler contention (mitigated but not eliminated by work-stealing, §20). Horizontal scaling: the exchange abstraction (§16) is partition-addressed, not thread-addressed, specifically so it can grow into the deferred distributed transport (PhaseDeferred("§16"), registered in §35) without an operator-level rewrite. Vertical scaling: NUMA-aware scheduling (§20) becomes required, not optional, beyond 2 sockets — the affinity-hint mechanism degrades gracefully but its benefit is unmeasured beyond the dual-socket target in §4.

Sharding: partitioned exchanges, deterministic partition hashing (I7) is the sharding key guarantee that must hold across a future distributed deployment. Replication pressure: a future distributed shuffle amplifies network IO in proportion to partition fanout — out of scope for this blueprint's 10 phases but bounded by the same exchange abstraction. Scheduler saturation: queue telemetry (§20.10) is the leading indicator before the 256-task budget (§4) is breached. Metadata scaling: optimizer memo growth is bounded by the timeout guard (§15.6), not by an explicit memo-size ceiling — this is a deliberate choice reviewed in §33 (Hard Questions). Storage growth: spill manifests are segmented (§21) specifically so manifest size scales with active spill volume, not with total historical spill activity.

30. Mental Models & First Principles

  • MM1 — Batches, not tuples. Compressed insight: every abstraction boundary in this system is drawn at the batch level, never the row level. What it predicts: any design that reasons per-row will regress throughput by an order of magnitude the moment it's on the hot path. Bug class without it: accidental per-row branching inside a kernel that looks vectorized but isn't; applies in §18.
  • MM2 — Backpressure is a signal, not a failure. Compressed insight: a Blocked state (§8) is the system working correctly, not an error. What it predicts: a system without backpressure doesn't avoid the problem, it just converts it into an OOM later. Bug class without it: unbounded buffering that looks fine in testing and collapses in production; applies in §20.
  • MM3 — Determinism is a debugging multiplier, not a purity requirement. Compressed insight: P1's cost (reduced optimizer entropy) buys back orders of magnitude of debugging time via replay. What it predicts: any nondeterminism introduced "just for this one optimization" will eventually cost more in incident time than it saved in plan quality. Bug class without it: replay divergence incidents with no reproducible root cause; applies in §15 and §21.
  • MM4 — Spill is a phase transition, not an error path. Compressed insight: an operator that treats spill as exceptional will under-invest in its correctness (P9). What it predicts: the first production incident under memory pressure will be in the spill path specifically, because it's the least-tested path. Bug class without it: spill code that "mostly works" and fails only under real skew; applies in §19 and §21.
  • MM5 — Cardinality errors compound multiplicatively across joins. Compressed insight: a 2x cardinality misestimate on each of four joined tables becomes a 16x error in join-order costing. What it predicts: cost-based join reordering is only as good as its worst histogram, not its average one. Bug class without it: chronically bad join orders blamed on "the optimizer" when the root cause is stale statistics; applies in §15.
  • MM6 — A queue's depth is a proxy for a rate mismatch, not a capacity problem. Compressed insight: increasing queue depth treats the symptom; the fix is matching producer/consumer rates via backpressure or added parallelism. What it predicts: raising the 256-task budget (§4) without addressing the underlying rate mismatch just delays the same collapse. Bug class without it: "fixing" saturation alerts by loosening the alert threshold; applies in §20.
  • MM7 — NUMA locality is a probability, not a guarantee. Compressed insight: affinity hints (§20) bias scheduling but work-stealing can and will cross sockets under load imbalance. What it predicts: correctness must never depend on same-socket execution; only latency does. Bug class without it: a "correctness" bug that's actually a NUMA-crossing performance regression misdiagnosed as a race; applies in §20 and §29.
  • MM8 — Every invariant needs exactly one enforcement point, not a defensive check everywhere. Compressed insight: I1–I12 (§7) are each enforced at one designated boundary; scattering the same check across many call sites hides which one is authoritative. What it predicts: a codebase with redundant invariant checks in ten places will eventually have one of them silently drift out of sync with the real rule. Bug class without it: an invariant that's "checked" everywhere but actually enforced nowhere consistently; applies in §7 and §12.

32. Back-of-Envelope Capacity Model

  • C1 — Vector pool sizing. 1024 concurrent vectors (§4) × ~500 KB average batch payload (2048 rows × ~8 columns × ~32 B/value average) = 512 MB, matching the §4 vector-batch allocator pool ceiling exactly.
  • C2 — Per-query hard limit headroom. 4 GB hard limit (§4) ÷ 512 MB vector pool = 8x headroom for hash-table build-side growth before a query must spill.
  • C3 — Default execution memory across concurrent queries. 8 GB default execution memory (§4) ÷ 2 GB per-query soft limit = 4 concurrently-resident queries at the soft limit before pool pressure telemetry (§17.10) should start trending upward.
  • C4 — Spill metadata cache capacity. 128 MB spill-metadata cache (§4) ÷ 64 B/SpillSegment index entry (§11: segment_id 8 B + checksum 8 B + row_count 8 B + index overhead ~40 B) = ~2M addressable segments before the cache itself needs eviction.
  • C5 — Replay buffer duration. 256 MB replay buffer (§4) ÷ (64 B/ReplayEvent × ~50k events/sec at peak scheduler throughput) = ~80 seconds of buffered replay before a forced flush to disk is required.
  • C6 — FD budget partition. 1024 spill FDs + 128 telemetry FDs + 256 replay FDs (§4) = 1408 FDs, inside a typical Linux default ulimit -n of 1024–65536 depending on distribution, hence the deployment assumption (§1) that the operator raises the soft FD limit in production.
  • C7 — Scan throughput vs. hard limit drain time. 4 GB hard limit (§4) ÷ 2–5 GB/s scan throughput floor (§4) = 0.8–2 s to fully scan a hard-limit-sized working set, well inside the <2 s cancellation-latency target (§4) — a cancelled scan-bound query drains before the cancellation deadline even in the worst case.
  • C8 — Hash join throughput vs. p95 operator latency. At 50M rows/sec hash-join throughput (§4) and a 2048-row batch size (§16), one batch takes 2048 ÷ 50,000,000 = ~41 µs of pure join work, two orders of magnitude under the <10 ms p95 operator-latency budget (§4), leaving headroom for scheduler dispatch and cache-miss variance.
  • C9 — Runnable-task queue drain time. 256 runnable tasks (§4) ÷ 64 execution threads (§4) = 4 tasks queued per thread at full occupancy — inside the work-stealing deque's expected steal latency, supporting the <25 ms p99 scheduler-stall target (§4).
  • C10 — Spill amplification bound in absolute bytes. At the <1.5x spill-amplification target (§4) against a 4 GB hard-limit query, worst-case spilled bytes on disk = 4 GB × 1.5 = 6 GB per query, times the FD-budget-implied concurrency of a few queries at once, sizing the local SSD spill volume in the tens-of-GB range for a single host.

34. Alternative Architectures (Roads Not Taken)

Alt A — Tuple-at-a-Time Iterator Model

   +--------+     next()      +--------+     next()      +--------+
   |  Scan  | <--------------- | Filter | <--------------- |  Join  |
   +--------+  one row at a  +--------+  one row at a   +--------+
                 a time                     a time

Regime where it wins: OLTP-style point-lookup workloads where a query touches a handful of rows and the per-call dispatch overhead this blueprint's vectorized model amortizes away never materializes in the first place. Real system that embodies it: PostgreSQL's executor (classic Volcano-style ExecProcNode iterator, Graefe 1994's model applied directly, §5). Why this blueprint rejects it: §2's core motivation — modern analytical workloads are throughput-bound on branch misprediction and cache misses, both of which the per-row next() call maximizes rather than minimizes; §4's throughput targets (100M+ rows/sec aggregation) are unreachable in a pure iterator model.

Alt B — Fully JIT-Compiled Query Codegen

   query plan --[LLVM IR codegen]--> specialized machine code --[execute]--> result
   (no generic operator dispatch; every predicate/expression inlined)

Regime where it wins: repeated execution of the same query shape at very high row counts, where codegen's compile-time cost amortizes across enough executions that per-row inlining beats vectorized dispatch overhead entirely (Neumann 2011, §5). Real system that embodies it: HyPer (Kemper & Neumann 2011, §5) and its descendants. Why this blueprint rejects it: Kersten et al. 2018's crossover analysis (§5) shows vectorization matches or beats codegen for ad-hoc, not-yet-warm queries — the dominant case for this blueprint's target operators (§1); codegen also conflicts with the <2 s cold-startup target (§4) by adding JIT compilation latency on the cold path. JIT vector kernels remain a registered deferred feature (§35) for a future phase once query repetition patterns justify the tradeoff.

Alt C — Distributed-First Shuffle Architecture

   Coordinator
     |  stage assignment
     v
   Worker 1 <--shuffle--> Worker 2 <--shuffle--> Worker N
   (every join/aggregate potentially crosses the network)

Regime where it wins: federated, multi-petabyte, multi-source analytical workloads where no single host can hold the working set, and network shuffle cost is unavoidable regardless of engine design. Real system that embodies it: Presto/Trino (§31, distributed-native from inception). Why this blueprint rejects it: §1's deployment model is explicitly single-node first — building distributed coordination before the single-node vectorized kernel is correct and fast would mean debugging two hard problems (vectorized execution correctness and distributed coordination) simultaneously, violating the phase-by-phase, each-phase-runnable discipline of §12–§21. The exchange abstraction (§16) is deliberately partition-addressed so this architecture remains reachable later (PhaseDeferred("§16"), §35) without a rewrite.

36. Glossary

  • Vector Batch — fixed-capacity columnar execution unit (VectorBatch, §11) carrying a cardinality, column vectors, a selection mask, and null masks.
  • Pipeline Breaker — a physical operator requiring full materialization before its consumer can proceed (P6).
  • Selection Vector — an explicit active-row index list distinct from the validity bitmap, enabling late materialization (§18).
  • Selection Mask — the active-row bitmap carried on a VectorBatch (I11).
  • Exchange — the partition-movement operator between pipelines (§16, §20).
  • Replay Trace — the deterministic, append-only execution log (replay/, I9).
  • Cardinality — estimated or actual row count of a relation or batch.
  • Spill — disk-backed overflow path for operators exceeding their memory budget (§21).
  • SIMD — Single Instruction Multiple Data; vectorized CPU execution (§18).
  • Probe Side — the join-input relation used for hash-table lookups (§19).
  • Build Side — the join-input relation used to construct the hash table (§19).
  • Memo — the optimizer's candidate-plan equivalence-class structure (§15).
  • Predicate Pushdown — moving a filter as close to the scan as algebraically valid (§14).
  • Late Materialization — deferring column value fetch until after filtering, operating on selection vectors instead (§18).
  • Null Bitmap — per-column validity mask (I3).
  • Runtime Filter — a build-side-derived filter (typically a Bloom filter) pushed to the probe- side scan (§19).
  • Operator Fusion — combining adjacent expression kernels into one execution pass (§18).
  • NUMA — Non-Uniform Memory Access; multi-socket memory locality behavior (§20).
  • Tail Latency — the worst-case (p95/p99) response delay, as distinct from the median (§28).
  • Materialization — persisting an intermediate result rather than streaming it.
  • Work Stealing — a scheduler load-balancing algorithm where idle workers pop tasks from another worker's queue (§20).
  • Robin-Hood Hashing — an open-addressing hash-table scheme minimizing probe-length variance (§19).
  • Morsel — a small, cache-sized unit of work used for NUMA-aware scheduling (Leis et al. 2014, §5, §20).
  • Dictionary Vector — a ColumnVector variant encoding values as indices into a shared dictionary (§11, §17).
  • Constant Vector — a ColumnVector variant representing one broadcast value with zero-copy (§11).
  • Sequence Vector — a ColumnVector variant representing an arithmetic progression with no materialized buffer (§11).
  • Batch Contract — the invariant set (I1, I3, I11) every operator's input/output batch must satisfy (P14).
  • Backpressure — upstream propagation of downstream pressure to avoid unbounded buffering (P2).
  • Fail Closed — aborting on invariant violation rather than risking corrupt output (P10).
  • Snapshot Consistency — planning against an immutable, versioned catalog view (I10).
  • Radix Partitioning — splitting a hash join's build/probe input by hash-bit prefix to bound per-partition memory (§19).
  • Checksum Segment — a spill-file unit individually validated for corruption (I4).
  • Cooperative Cancellation — task cancellation honored at explicit yield points (batch boundaries) rather than via preemptive interruption (§20).
  • Affinity Hint — a scheduling preference tying a task to a NUMA node without a hard guarantee (MM7, §20).
