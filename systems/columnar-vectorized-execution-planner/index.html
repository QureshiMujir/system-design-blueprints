parser (§13) — deterministic tokenizer + recursive-descent grammar; arena-backed AST with stable source spans; the only subsystem that touches untrusted external text, hence the trust boundary drawn above it. binder (§13) — symbol resolution, catalog binding against an immutable snapshot (I10), type coercion; failures are deterministic and span-stable for replay. logical-plan (§14) — bound trees become an immutable relational algebra graph; this is the optimizer's only input contract. optimizer/cardinality/cost-model (§15) — memo-based rule and cost rewrites; statistics propagation; determinism is mandatory here because plan instability cascades into every downstream phase. physical-plan/execution-graph (§16) — logical operators become a schedulable pipeline DAG with explicit pipeline breakers and exchange partition metadata; this is where concurrency boundaries are first drawn. vector-engine + expression-engine (§16–§19) — the vectorized operator implementations and their SIMD kernels; operators obey the batch invariants in §7. scheduler/runtime + exchange (§20) — cooperative work-stealing scheduling with NUMA affinity; exchange is both a concurrency boundary and a fault-isolation boundary. vector-memory (§17) — owns all vector buffers, slab arenas, and validity bitmaps; the only subsystem permitted to allocate/free VectorBatch payload. spill-engine (§21) — the persistence boundary: the only place execution state crosses to disk, under checksum (I4). telemetry/tracing/metrics/replay (§21) — the protocol boundary to the outside world (OTEL collector, Prometheus scrape target, replay files consumed by cli replay). benchmark/conformance/fuzz (§26, §28) — the external validation loop gating every release.

8. Domain Model — Relational Algebra & Vectorized Execution Contract

Relational algebra model (logical operator chain, §14):

Scan -> Filter -> Projection -> Join -> Aggregate -> Sort -> Limit

Core execution abstraction (physical, §16):

Pipeline -> Operators -> Vector Batches -> Column Vectors -> Buffers

VectorBatch fields (see §11 for the full type signature):

Field Meaning
batch_id Runtime-unique batch identifier
cardinality Row count
columns Ordered list of ColumnVector
selection_mask Active-row bitmap (bounded by I11)
null_masks Per-column validity bitmaps (bounded by I3)

Execution state machine (ExecutionTask.state, §11):

State Meaning
Created Allocated, not yet scheduled
Ready Runnable, in a scheduler queue (I5)
Running Actively scheduled on a worker thread
Blocked Waiting on backpressure or an exchange edge (P2)
Spilling Disk overflow in progress (§21)
Finished Completed normally
Failed Aborted (P10 fail-closed path)

Join state transitions (join-engine, §19):

BuildPending -> BuildComplete -> ProbeRunning -> SpillRequired -> Recovery -> Finished

Malformed input example (parser, §13):

SELECT SUM(a FROM table

Expected behavior: deterministic parser span error at the unclosed-paren token, stable diagnostic message, no binder or runtime invocation (fail-closed at the earliest layer, P10).

Failure-path example (join engine, §19 and §21):

HashJoin -> memory pressure -> spill threshold exceeded
         -> partition spill -> replay marker persisted -> execution resumes

Sequence diagram (client to result, spanning §13–§21):

Client -> Parser -> Binder -> Optimizer -> Physical Planner
       -> Scheduler -> Runtime -> Operator Pipelines -> Result Sink

Consistency semantics: snapshot-consistent planning against an immutable catalog (I10); deterministic execution ordering unless explicitly marked unordered (I2); batch-stable operator semantics (I1, I11). Memory model: ownership-based (P3); immutable vector metadata post-allocation; mutable payload regions within the owning operator's lifetime; atomic scheduler-owned state transitions (I5, I12).
