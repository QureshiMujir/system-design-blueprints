⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up all 30 crates from §1's Phase-0 deliverable list with compiling stubs, wire CI/fuzz/ benchmark/conformance workflows, and build the minimal correctness kernel every later phase depends on: ID types (BatchId, TaskId, SegmentId, PartitionId), the Operator and RuntimeMetric trait signatures (§11), and a first invariant-checking harness. Constraints introduced: immutable crate dependency graph (P12 — optimizer may not depend on runtime); every crate ships with a metrics stub before any logic (P4); reproducible builds from commit one (ADR-19).

Deliverable

cargo build --workspace succeeds across all 30 crates; cli binary runs planner --version and prints a git-SHA + build-timestamp version string (ADR version-stamping); CI is green on an empty diff.

Acceptance
  • all 30 crates in §10 compile with zero warnings under -D warnings,
  • cargo deny check reports zero dependency-direction violations (P12),
  • CI pipeline (Lint -> Unit Tests -> Fuzz -> Conformance -> Benchmark -> Release Packaging, §27) completes in <10 minutes on an empty diff,
  • conformance/ simulator boots and loads zero fixtures without panicking (fixture count = 0 is valid at this phase).
Fixtures
Fixture Purpose
fixtures/skeleton/empty_workspace verifies every crate compiles standalone
fixtures/skeleton/dep_direction fails the build if optimizer imports runtime
fixtures/skeleton/version_stamp verifies planner --version output format
Pitfalls
  1. Circular crate dependencies introduced accidentally through a shared "utils" grab-bag crate — root-cause: no dependency-direction lint yet; debug via cargo tree -d; signal: cargo deny failure; recovery: split the grab-bag into direction-respecting crates.
  2. ID newtypes leaking a Copy+arithmetic implementation that lets a BatchId be added to a TaskId — root-cause: deriving Deref too eagerly; signal: type confusion in review; recovery: remove Deref, keep newtypes opaque.
  3. CI caching Cargo.lock across a dependency bump silently, breaking ADR-19's reproducibility guarantee — signal: cargo-audit diff not matching Cargo.lock diff; recovery: pin CI cache key to Cargo.lock hash.

⬜ Phase 1 — Parser, Binder & Canonical AST §13

Objectives

Build deterministic parsing and semantic binding producing immutable, arena-backed canonical AST structures with source-span fidelity and replay-stable diagnostics. Constraints introduced: immutable AST ownership post-parse (P5 lineage applied one layer earlier); deterministic parse trees (P1); arena-backed allocations to avoid fragmentation under batch benchmark execution; normalized identifier casing; catalog binding against an immutable snapshot (I10).

Deliverable

Runnable parser CLI: planner parse query.sql emits AST, semantic tree, and diagnostics as JSON.

Acceptance
  • 100,000 malformed inputs fuzzed via fuzz/src/parser_target.rs without a crash or hang,
  • AST hashes are byte-identical across three repeated parses of the same input (determinism, P1),
  • parser p95 latency <5 ms on fixtures/parser/select_basic.sql-class inputs,
  • zero binder ambiguity false-negatives on fixtures/parser/duplicate_alias.sql.
Fixtures
Fixture Purpose
fixtures/parser/select_basic.sql baseline successful parse
fixtures/parser/malformed_join.sql syntax failure, span-stable diagnostic
fixtures/parser/duplicate_alias.sql binder ambiguity failure
fixtures/parser/nested_agg.sql semantic validation of nested aggregates
fixtures/parser/unicode_identifier.sql identifier normalization regression
Pitfalls
  1. Ambiguous alias shadowing across nested subqueries — manifestation: binder picks the wrong symbol; root cause: scope stack popped one level too early; debug via scope-trace dump; signal: duplicate_alias.sql regression; recovery: fix scope lifetime, add regression fixture.
  2. Arena lifetime leaks when a diagnostic holds a reference past the arena's drop — manifestation: use-after-free caught by Rust's borrow checker at compile time, but only if lifetimes are annotated correctly; root cause: diagnostic struct borrowing instead of owning span text; signal: compile error, not runtime; recovery: own the span text in diagnostics.
  3. Recursive-descent stack overflow on deeply nested expressions — root cause: no recursion-depth guard; signal: SIGSEGV under fuzz/src/parser_target.rs; recovery: add an explicit depth counter and a bounded-depth parser error.
  4. Unicode identifier normalization drift between parse and re-parse — root cause: NFC normalization applied inconsistently; signal: AST hash mismatch on unicode_identifier.sql; recovery: normalize at tokenization, once, before AST construction.

⬜ Phase 2 — Logical Planning & Relational Algebra §14

Objectives

Transform bound semantic trees into canonical, immutable relational algebra graphs that form the optimizer's sole input contract (P5). Constraints: immutable operator graph, stable node identities, replay-safe transformation ordering (P1, P7).

Deliverable

planner explain --logical query.sql renders an explainable, validated relational algebra graph as JSON and GraphViz.

Acceptance
  • logical plans are deterministic — identical bound input yields byte-identical serialized plan,
  • the acyclicity validator rejects 100% of synthetically cyclic plan graphs in fixtures/logical/cyclic_plan.fixture,
  • projection pruning removes ≥1 unused column on fixtures/logical/nested_projection.sql without changing result cardinality,
  • rewrite traces reconstruct the exact rule-application order on replay (P7).
Fixtures
Fixture Purpose
fixtures/logical/filter_pushdown.sql predicate decomposition correctness
fixtures/logical/nested_projection.sql projection-pruning correctness
fixtures/logical/invalid_grouping.sql malformed GROUP BY rejected at validation
fixtures/logical/cyclic_plan.fixture synthetic DAG-acyclicity regression
Pitfalls
  1. Cyclic plan graphs introduced by a buggy rewrite that reuses a node ID — root cause: node-ID reuse across rewrite passes; debug via the acyclicity validator's cycle trace; signal: validator abort; recovery: allocate fresh LogicalNodeIds per rewrite (P5).
  2. Duplicate projection aliases surviving normalization — root cause: alias map not deduplicated before projection-pruning; signal: invalid_grouping.sql regression; recovery: dedupe at bind time (§13), not at logical-plan time.
  3. Predicate mutation bugs where a pushdown rewrite mutates the original predicate node in place, violating P5 — signal: rewrite-trace divergence on replay; recovery: enforce copy-on-rewrite via a lint that forbids &mut on already-submitted plan nodes.

⬜ Phase 3 — Optimizer & Cost Model §15

Objectives

Build deterministic rule-based and cost-based optimizer infrastructure: a memo structure, histogram statistics, cardinality estimation, and CPU/IO/memory/spill-risk plan costing. Constraints: bounded optimization time (§4 does not set this explicitly but §28's M-series does); optimizer determinism mandatory for plan replay stability (P1).

Deliverable

planner explain --costed query.sql produces a costed candidate plan with CPU/IO/memory/spill-risk breakdown per candidate.

Acceptance
  • optimizer produces byte-identical costed plans across three repeated runs on fixtures/optimizer/star_schema.sql (determinism, P1),
  • optimization wall-clock time <200 ms on a 12-table join per the timeout guard,
  • histogram staleness beyond a 20% cardinality-drift threshold triggers a stale_histogram_total telemetry emission (see M-series target in §28),
  • join reordering on fixtures/optimizer/skewed_join.sql avoids the worst-case plan (validated against a known-good reference plan checked into the fixture).
Fixtures
Fixture Purpose
fixtures/optimizer/star_schema.sql join-reordering determinism baseline
fixtures/optimizer/skewed_join.sql cost-model behavior under skew
fixtures/optimizer/high_selectivity.sql pushdown-driven cardinality collapse
fixtures/optimizer/memo_explosion.fixture timeout-guard regression
Pitfalls
  1. Memo explosion on wide joins (>10 tables) — manifestation: optimization time grows combinatorially; root cause: no join-order search-space pruning; debug via memo-size counter; signal: timeout-guard trips; recovery: fall back to a greedy heuristic order (documented degradation, not a crash).
  2. Unstable join ordering across runs with tied costs — root cause: no deterministic tie-break; signal: star_schema.sql determinism check fails; recovery: tie-break by LogicalNodeId ordering (P1).
  3. Statistics drift — a histogram built at bind time no longer reflects the table at execution time; root cause: I10's snapshot consistency guarantees plan-time consistency, not execution-time freshness; signal: stale_histogram_total telemetry; recovery: re-cost on significant drift (deferred adaptive re-optimization, see PhaseDeferred("§15")).

⬜ Phase 4 — Physical Planning & Pipeline Construction §16

Objectives

Convert optimized logical plans into executable vectorized pipelines: physical operators, pipeline breakers, exchange partition metadata, batch-size planning, scheduler affinity hints. Constraints: valid execution DAGs, deterministic pipeline IDs (P1), explicit pipeline breakers (P6).

Deliverable

planner explain --physical query.sql renders an executable, validated physical execution graph (pipeline DAG) as JSON and GraphViz, with no scheduler execution yet.

Acceptance
  • 100% of fixtures/physical/ plans produce a DAG with zero cycles (validated by execution-graph's walker),
  • pipeline IDs are deterministic — identical physical plan yields identical pipeline-ID assignment across three runs,
  • default batch size is 2,048 rows and is overridable per operator within the 512 MB vector-pool budget (§4),
  • every pipeline breaker in the DAG corresponds to an explicit node type (no implicit materialization, P6).

Fixture Purpose

fixtures/physical/parallel_join.sql exchange partition metadata correctness
fixtures/physical/zero_row_pipeline.fixture degenerate empty-input pipeline
Pitfalls
  1. Hidden materialization introduced by an operator buffering internally without a physical Materialize node — manifestation: memory growth invisible to execution-graph; root cause: an operator implementation violating P6; signal: memory-profile mismatch against the declared DAG; recovery: require every operator's internal buffering to register a synthetic Materialize node.
  2. Cyclic pipeline edges from a buggy exchange-partition assignment that routes a partition back to its own producer — root cause: partition-hash collision with the producer's own ID; signal: execution-graph walker abort; recovery: reserve partition-ID space disjoint from producer-pipeline-ID space.

⬜ Phase 5 — Columnar Memory Engine §17

Objectives

Implement the stable vector-memory subsystem with bounded allocation semantics: the four ColumnVector layouts (§11), validity bitmaps, slab-arena pools, and spill-aware allocation. Constraints: zero leaks (P3), bounded fragmentation, cache-line-aligned buffers for SIMD (P8).

Deliverable

A reusable vector-allocator runtime: vector-memory exposes alloc_batch(schema, capacity) / free_batch(batch) with pool-backed reuse, exercised by a standalone allocator benchmark in benchmark/.

Acceptance
  • zero leaked allocations over a 1-hour soak of fixtures/memory/vector_reuse.fixture (validated by the allocation-tracing walker),
  • fragmentation ratio stays <10% of pool size under the soak (P3),
  • validity-bitmap length exactly equals cardinality on 100% of constructed batches (I3),
  • pool occupancy telemetry updates within one allocation cycle (no stale-read window >1 batch).
Fixtures
Fixture Purpose
fixtures/memory/null_bitmap.fixture validity-bitmap/cardinality consistency (I3)
fixtures/memory/vector_reuse.fixture pool reuse and leak-freedom soak
fixtures/memory/oversized_vector.fixture allocation beyond pool slab-class ceiling
Pitfalls
  1. Bitmap corruption from an off-by-one in the bit-index-to-byte-offset math — manifestation: a valid row read as null or vice versa; root cause: byte/bit index confusion at a batch boundary resize; debug via null_bitmap.fixture byte-diff; signal: I3 assertion trip; recovery: fix the offset math, add a boundary-value regression case.
  2. Allocator fragmentation from mismatched slab-class rounding — manifestation: fragmentation ratio creeps above the 10% acceptance ceiling over the soak; root cause: too many distinct capacity requests missing the nearest slab class; debug via fragmentation-ratio telemetry over time; recovery: widen slab-class granularity or round capacity requests up more aggressively.

⬜ Phase 6 — Expression Engine & SIMD Kernels §18

Objectives

Build the vectorized expression-execution engine: expression lowering to SIMD kernels, selection vectors, branchless null propagation. Constraints: SIMD alignment (from §17), explicit null semantics at every kernel boundary (P13), type stability post-lowering (I8).

Deliverable

A vectorized expression runtime: expression-engine::compile(expr) -> KernelChain, exercised by a standalone kernel-correctness fixture suite and a Criterion microbenchmark.

Acceptance
  • SIMD kernel outputs match a scalar reference implementation bit-for-bit on fixtures/expression/arithmetic_nulls.fixture (100% agreement, zero tolerance per I8),
  • null propagation through a 5-deep expression fusion chain matches SQL null semantics on fixtures/expression/boolean_masks.fixture,
  • AVX2 kernel throughput ≥250M values/sec on a synthetic arithmetic benchmark (contributing to the filter-throughput target in §4),
  • zero SIMD alignment faults over 1M fuzzed expression trees.
Fixtures
Fixture Purpose
fixtures/expression/arithmetic_nulls.fixture null-propagation correctness vs. scalar reference
fixtures/expression/boolean_masks.fixture selection-vector/validity-bitmap interaction
fixtures/expression/nan_propagation.fixture floating-point NaN handling regression
Pitfalls
  1. SIMD alignment faults from a buffer starting off a 64-byte boundary — root cause: a slab-class rounding bug from §17 propagating into a kernel that assumes alignment; signal: SIGBUS/SIGILL under fuzzing; recovery: assert alignment at kernel entry in debug builds, fix the allocator.
  2. Selection-mask corruption from a fused kernel chain that updates the mask out of order relative to the value buffers — root cause: fusion reordering violating I11; signal: boolean_masks.fixture mismatch; recovery: fix fusion ordering to update mask and values atomically per fused step.
  3. Silent overflow in fused arithmetic chains — root cause: intermediate results not widened before the final narrowing cast; signal: differential-testing mismatch against the scalar reference; recovery: widen intermediates per SQL numeric promotion rules, checked in fixtures/expression/arithmetic_nulls.fixture.

⬜ Phase 7 — Join & Aggregation Engines §19

Objectives

Implement vectorized hash joins and hash aggregation with spill-to-disk under memory pressure, runtime filter propagation, and skew handling. Constraints: correctness under skew, spill recovery success (P9), dictionary-aware execution reusing §17's dictionary vectors.

Deliverable

Parallel joins and aggregations: join-engine/aggregation-engine operators pass the full fixtures/join/ and fixtures/aggregation/ suites including spill-triggered paths.

Acceptance
  • correctness under skew: fixtures/join/skewed_hash.fixture produces row-count-identical results to a non-skewed reference partitioning at 10x skew factor,
  • spill recovery success rate ≥99% over 1,000 injected-spill runs of fixtures/join/spill_join.fixture (feeding the recovery-success-rate target in §4),
  • hash-join throughput ≥50M rows/sec on an unskewed synthetic benchmark (§4 target, unchanged),
  • runtime filter reduces probe-side scanned rows by a measurable amount on fixtures/join/parallel_join.sql-class fixtures (non-zero pruning, not just "present").
Fixtures
Fixture Purpose
fixtures/join/skewed_hash.fixture correctness and rebalancing under partition skew
fixtures/join/spill_join.fixture build-side spill and recovery correctness
fixtures/aggregation/spill_agg.fixture partial-aggregate spill/merge correctness
fixtures/join/all_null_join.fixture join-key null semantics (no false matches)
Pitfalls
  1. Hash-table blowup under extreme skew — manifestation: one partition's build side exceeds the hard memory limit before the skew monitor reacts; root cause: monitor sampling interval too coarse; debug via per-partition occupancy telemetry; signal: I6 quota-breach trip; recovery: tighten the sampling interval, add fixtures/join/skewed_hash.fixture at a higher skew factor.
  2. Spill recursion — a spilled partition, on reload, is still too large to build in memory and must spill again; root cause: radix-partition fanout too coarse for the actual skew; signal: repeated Spilling state transitions on the same partition (§8 state machine); recovery: increase partition fanout adaptively on a detected re-spill.
  3. Probe-chain depth blowup in the robin-hood table under a bad hash-seed choice — root cause: non-uniform hash distribution for a skewed key domain; signal: probe-chain-depth telemetry exceeding a documented ceiling; recovery: reseed and rebuild, logged as a rebuild event.

⬜ Phase 8 — Runtime Scheduler & Parallel Execution §20

Objectives

Build the deterministic vector-execution scheduler: work-stealing queues, task lifecycle, cooperative cancellation, NUMA affinity. Constraints: bounded queue growth (P2), stable scheduling fairness, task-ownership safety (I5), cancellation idempotency (I12).

Deliverable

A parallel vector runtime: runtime orchestrates scheduler + vector-engine operators across 64 execution threads (§4), exercised end-to-end by fixtures/scheduler/ and the TPC-H-inspired benchmark suite (§28).

Acceptance
  • bounded queue growth: no queue exceeds the 256-task depth budget (§4) under fixtures/scheduler/saturation.fixture without triggering backpressure first,
  • p99 scheduler stall <25 ms (§4 target, unchanged) measured over a 10-minute sustained-load run,
  • cancellation completes within 2 s for 100% of 1,000 injected-cancellation runs of fixtures/scheduler/cancellation.fixture,
  • zero double-enqueue events (I5) and zero duplicate-terminal-transition events (I12) over a 72h soak (§4).
Fixtures
Fixture Purpose
fixtures/scheduler/cancellation.fixture cooperative-cancellation latency and idempotency
fixtures/scheduler/saturation.fixture queue-depth backpressure trigger correctness
fixtures/scheduler/numa_affinity.fixture same-socket steal preference regression
Pitfalls
  1. Queue starvation when work-stealing always prefers the same victim queue — manifestation: one worker thread idles while another's queue backs up; root cause: steal-victim selection not randomized/rotated; debug via per-queue depth telemetry over time; signal: fairness-variance metric exceeding a documented ceiling; recovery: rotate victim selection.
  2. Deadlock cycles between two pipelines each waiting on the other's exchange backpressure release — root cause: a physical plan with a genuine circular data dependency, which §16's DAG validator should have rejected; signal: stalled-task detector (no state transition for N seconds); recovery: forced cancellation of the deadlocked query, and a regression fixture added to §16.
  3. False sharing between two AtomicTaskState fields placed on the same cache line — manifestation: throughput regression under high concurrency invisible in single-threaded profiling; root cause: struct layout not cache-line-padded; signal: perf c2c (cache-to-cache) report; recovery: pad ExecutionTask to a cache-line boundary.

⬜ Phase 9 — Spill Engine, Replay & Observability §21

Objectives

Implement the resilient disk-backed spill subsystem and the observability layer (metrics, tracing, deterministic replay) that every earlier phase has been emitting into since Phase 0. Constraints: zero silent-corruption budget (§4), 100% replay fidelity (§4), spill checksum integrity (I4).

Deliverable

Disk-backed overflow runtime plus replayable diagnostics: spill-engine survives injected corruption and disk-full conditions; planner replay reconstructs a crashed query's execution state with byte-identical fidelity against the original run.

Acceptance
  • spill replay recovery succeeds on 100% of fixtures/spill/spill_resume.fixture runs after a simulated process kill mid-spill,
  • corruption detection catches 100% of bit-flip-injected segments in fixtures/spill/corrupt_spill.fixture (I4, zero silent-corruption tolerance),
  • replay fidelity is 100% across fixtures/replay/replay_stability.fixture (§4 target, unchanged; any divergence blocks release per I9),
  • trace-gap integrity scanner reports zero gaps over a 72h soak (§4).
Fixtures
Fixture Purpose
fixtures/spill/corrupt_spill.fixture checksum-detection of injected bit-flip corruption
fixtures/spill/spill_resume.fixture crash-mid-spill recovery correctness
fixtures/replay/replay_stability.fixture deterministic replay hash-match regression
fixtures/replay/trace_gap.fixture replay sequence-number gap detection (I9)
Pitfalls
  1. Temp-file leaks when a query is cancelled mid-spill and the cleanup lifecycle isn't invoked on the cancellation path — manifestation: FD budget (1024 spill FDs, §4) creeping toward exhaustion over a long-running host; root cause: cleanup hooked to Finished only, not Failed/cancelled; signal: FD-count telemetry trend; recovery: hook cleanup to every terminal state (I12-consistent).
  2. Checksum drift between the writer's checksum algorithm version and the reader's, across a rolling upgrade — root cause: no checksum-algorithm version tag in the segment header; signal: false-positive corruption alerts immediately after a deploy; recovery: version-tag the checksum algorithm, per §25's compatibility rules.
  3. Telemetry overload from per-row tracing spans instead of per-batch — manifestation: tracing overhead dominates the operator's own execution cost; root cause: span granularity mismatched to batch-oriented execution; signal: perf showing tracing-library frames dominating the profile; recovery: span per batch, not per row, matching the vectorized execution model throughout.
