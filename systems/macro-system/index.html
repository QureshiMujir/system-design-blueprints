Lexer — converts raw bytes to a TokenStream; every token's scope set starts empty (no hygiene decision made yet); Unicode identifiers follow UAX #31. Parser — builds the AST; a MacroInvocation node is first-class and holds its unexpanded TokenStream verbatim so the expander can re-tokenize with fresh scope marks. Pattern matcher — consumes a macro arm's PatternTree against an invocation's TokenStream, producing metavariable bindings or a diagnosable failure (§15). Template substitute — walks a TemplateTree, replacing metavariable references with their bound fragments and expanding ellipsis repetitions (§16). Set-of-scopes mark + fixpoint driver — the hygiene core: allocates use-site/intro scopes, marks tokens, and iterates until no invocations remain or a cap trips (§17–18). Procedural macro sandbox — a wasmtime engine invoked in place of the pattern-matching machinery when a macro is MacroKind::Procedural; the sandbox's output re-enters the same fixpoint loop (§21). Modules — tracks each macro's immutable definition-site scope across import/re-export so re-exporting never rewrites lexical context (§22). Resolver — the only pass that inspects scope sets; converts every identifier use to a resolved binding or a diagnostic (§19). Downstream — type checker and codegen consume resolved AST only; they never see a ScopeSet (I8, §7). Diagnostics — a cross-cutting overlay: every box above can emit a Diagnostic carrying both invocation and definition spans (§20).

Three properties hold system-wide and are referenced throughout: the scope set is carried on every token from lexer to resolver, and no pass loses it (I3, §7); the expander is purely syntactic and never consults the resolver, so expansion order can never depend on semantic information (I8); the resolver is the only scope-set consumer downstream of the expander, so a type checker written once against resolved AST never needs to understand hygiene at all (MM6, §32).

8. Domain Model

8.1 Grammar

MacroDef      ::= "macro" Ident "{" MacroArm+ "}" | "macro" Ident "=" "proc" Path ";"
MacroArm      ::= Pattern "=>" Template ";"
Pattern       ::= PatternTok*
PatternTok    ::= Token | MetaVar | Repeat
MetaVar       ::= "$" Ident ":" FragKind
FragKind      ::= "ident" | "expr" | "pat" | "ty" | "path" | "tt"
                | "block" | "stmt" | "literal"
Repeat        ::= "$" "(" PatternTok+ ")" Sep? Quant
Quant         ::= "*" | "+" | "?"
Sep           ::= Token                      (* excludes Quant tokens *)
Template      ::= TemplateTok*
TemplateTok   ::= Token | MetaVarRef | TRepeat
TRepeat       ::= "$" "(" TemplateTok+ ")" Sep? Quant
MacroInvoc    ::= Path "!" "(" TokenTree* ")"

8.2 Pattern/template matching

The matcher (§15) consumes a PatternTree against an invocation's TokenStream, producing either Bindings: Vec<(MetaVarName, FragmentValue)> or a diagnosable failure. Repetition matches accumulate a list per ellipsis-bound metavariable; zero matches yields an empty list, never an error (I10 guards the follow-set ambiguity this raises with $x:expr followed directly by +).

8.3 Set-of-scopes hygiene algorithm — state table

Step Input Action Output
1 AST node = MacroInvocation allocate fresh use-site scope U caller tokens marked +U
2 macro definition tokens allocate fresh intro scope I definition tokens marked +I
3 marked invocation tokens vs PatternTree pattern match (§15) bindings, each fragment carrying its own +U-bearing scope set
4 bindings + TemplateTree substitute (§16): template tokens get +I; metavar-bound tokens keep their caller scope set expanded TokenStream
5 expanded TokenStream re-parse into AST fragment fragment scoped {…,I} for def tokens, {…,U} for spliced caller tokens
6 AST fragment check for residual MacroInvocation nodes none: fixpoint reached (§18); some: repeat from step 1, one level deeper (bounded by I4)

8.4 Worked example — swap!

Definition: macro swap { ($a:expr, $b:expr) => { let tmp = $a; $a = $b; $b = tmp; } }, defined in lexical scope {S_def}. Invocation: swap!(tmp, x) at call site scope {S0}.

Token (origin) Scope set after expansion
let (definition) {S_def, I7}
tmp (definition's own, the let-bound one) {S_def, I7}
tmp (from $a, caller's) {S0, U7}
x (from $b, caller's) {S0, U7}

Resolver (§19) sees two distinct tmp identities: tmp@{S_def,I7} (the macro's own let binding) and tmp@{S0,U7} (the caller's variable, substituted via $a). Because neither scope set is a subset of the other in the general case (S_def ≠ S0), the two never collide — hygiene holds by construction, matching I1/I3.

8.5 Malformed-input example

swap!(tmp) — arity mismatch, missing the $b:expr argument. The matcher's arity/ follow-set check (I10) finds no arm matches; a diagnostic is emitted naming the expected fragment ($b:expr) and the invocation span — handled by Phase 8 (§20).

8.6 Failure-path example

macro loopy { () => { loopy!() } } invoked as loopy!(). Each expansion step produces another loopy!() invocation; the invocation count never strictly decreases. The iteration cap (1,024, §4) trips; the fixpoint driver (§18) emits a cycle-detection diagnostic naming the full invocation chain (I4, T4, FM-2, §24/§25).

Design principles (§6)

  • P1 — Scope-Set Hygiene by Construction. Identifier identity is (surface name, scope set), never a renamed symbol. Trade-off: every substitution step must carry scope-set bookkeeping. Operational implication: diagnostics show real user-written names. Violating it: silently regresses to alpha-renaming's diagnostic opacity.
  • P2 — One Transformer Contract, Two Macro Kinds. Pattern macros and procedural macros both implement MacroTransformer (§11), but pattern macros run inside the expander's algebra while procedural macros run in the sandbox. Trade-off: two code paths to maintain. Operational implication: a bug class is isolated to one kind at a time. Violating it: a unified "just call arbitrary code" model loses hygiene-by-default for the common case (§36 AA3).
  • P3 — Expansion Is a Pure Function of (AST, Scope State). No ambient global mutable state. Trade-off: scope-ID allocation must thread explicitly. Operational implication: expansion is trivially parallelizable across independent compilation units (§31). Violating it: reintroduces cross-file nondeterminism (T5).
  • P4 — Fixpoint Expansion, Bounded. Iterate outer-to-inner until no invocations remain or the iteration/depth caps trip (§4). Trade-off: legitimately deep macros need a documented escape (raise the cap). Operational implication: compile time is provably bounded. Violating it: an unbounded loop is a compiler-hang DoS (T4).
  • P5 — The Resolver Is the Sole Scope-Set Consumer. Type checker and codegen never see a ScopeSet (I8). Trade-off: the resolver must fully commit to resolved names before handing off. Operational implication: downstream passes are hygiene-agnostic and reusable. Violating it: couples every future front-end pass to macro internals (MM6).
  • P6 — Diagnostics Carry Definition Site + Invocation Site + Expansion Trace. Every macro error is walkable end to end (I9). Trade-off: diagnostic objects are larger. Operational implication: multi-level macro-in-macro failures stay debuggable. Violating it: users get "error in generated code" with no way back to their own call site (FM-8).
  • P7 — Procedural Macros Are Sandboxed and Deterministic by Default. No ambient I/O; escape hatches are explicit opt-ins (§21). Trade-off: sandbox overhead per invocation. Operational implication: builds are reproducible and supply-chain-safe. Violating it: a compromised macro crate gets arbitrary host access at compile time (T8).
  • P8 — Definition-Site Scope Travels With Re-Exports. A macro's lexical context is a property of the macro, not of wherever it is imported (I6). Trade-off: modules (§22) must store and never mutate this field. Operational implication: re-exported macros keep resolving their own helpers correctly. Violating it: reproduces FM-7.
  • P9 — Source-Order Determinism. Scope IDs and expansion order are a function of source position, never thread/allocation order (I2). Trade-off: forecloses some lock-free allocator designs. Operational implication: byte-identical builds across machines. Violating it: reproduces FM-4.
  • P10 — Fail Closed on Ambiguous Resolution. Two equally specific candidate bindings is a compile error, never a silent pick (I5). Trade-off: some programs the author "meant" one way are rejected. Operational implication: no silently-wrong resolution ships. Violating it: reproduces FM-5's false confidence.
  • P11 — Grammar and Hygiene Are Orthogonal Concerns. The pattern/fragment grammar (what syntax matches) is decided independently of the scope algebra (what identifiers mean). Trade-off: two subsystems to specify (§15 vs §17) instead of one. Operational implication: either can evolve without destabilizing the other. Violating it is the C preprocessor's original sin — mixing the two makes hygiene impossible to retrofit (§36 AA4).
  • P12 — Conformance Before Performance. Every optimization (memoization, store pooling, caching) must not change any bucket's expected output; the differential oracle gates every merge (I12). Trade-off: some fast paths are deferred until proven safe. Operational implication: performance work never silently regresses correctness. Violating it repeats the Communion.md-class failure of shipping unverified claims.
  • P13 — Every Escape Hatch Is Explicit and Audited. Sandbox capability grants (clock, random, network) are opt-in per macro and appear in a build manifest (I11). Trade-off: macro authors needing a capability must declare it visibly. Operational implication: an audit can enumerate every non-default-safe macro in a build. Violating it silently reproduces T2/T8's blast radius.
  • P14 — Macros Are First-Class, Namespaced Items. A macro is importable, exportable, and shadowable exactly like a function or type, never a second-class textual construct. Trade-off: the module system (§22) must model macros as items. Operational implication: libraries can ship macros safely. Violating it reproduces the C preprocessor's flat, unscoped #define namespace.
