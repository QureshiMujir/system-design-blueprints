146 — Macro System with Hygiene

Project Number: 146

Project Name: Macro System with Hygiene

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade hygienic macro system for a Rust-like systems language: a lexer that attaches scope sets to tokens, a macro_rules!-style pattern-and-template macro definition language, a sandboxed procedural-macro runtime, a set-of-scopes hygienic expander (Flatt 2016, applied §17) that iterates to fixpoint under bounded recursion, a resolver that is the sole consumer of scope sets, a diagnostics layer that renders every macro-expansion error with both invocation and definition spans, and a modules layer that lets macros be imported/re-exported without losing their definition-site scope. The one non-negotiable property: an identifier introduced by a macro is never confusable, under any nesting or import path, with a same-surface-name identifier introduced by the macro's caller (I1, §7).

Phase-0 deliverable — numbered crates (Cargo workspace, §10):

  1. ms-tokens — token + scope-set core type.
  2. ms-ast — macro-aware AST (items, expressions, MacroInvocation nodes).
  3. ms-lexer — UAX #31 identifier lexing, scope-set attachment.
  4. ms-parser — recursive-descent parser producing the AST.
  5. ms-diagnostics — structured diagnostic type (spans only in Phase 0; rendering §20).
  6. conformance/cli — fixture-runner skeleton (buckets populate from Phase 1 onward).

System boundaries:

  • Provides: macro definition surface (pattern + procedural), hygienic expansion to fixpoint, name resolution over scope sets, diagnostics, module-scoped import/export of macros.
  • Delegates: type checking, code generation, linking — all consume the resolved AST this system emits; none of it lives here (sibling project 42 — Type Checker, project 76 — Linker/Loader).
  • Does NOT provide: a general-purpose language front end (no full type system, no borrow checker — project 145); no incremental recompilation cache beyond the expansion cache of ADR-13 (full incrementality is project 242 — Incremental Compiler); no IDE protocol server (project 139 — LSP Server integrates against this system's diagnostics and resolver contracts, not the reverse).

Non-goals: reader macros / arbitrary read-table syntax extension (Common Lisp model, §36 AA3's rejection rationale); runtime (non-compile-time) macro evaluation; macro systems for dynamically-typed scripting where hygiene is optional.

Deployment model: a linkable Rust library (ms-* crates) plus a CLI (ms-cli) invoked by a host compiler's build pipeline as a compile-time pass; the procedural-macro sandbox runs as an in-process wasmtime engine, not a separate service.

Target users/operators: language-implementation engineers embedding this crate family into a larger compiler; macro authors consuming the pattern language and procedural-macro SDK; build-infrastructure operators running the differential/fuzz CI fleet (§26).

Later phases unlock: sandboxed procedural macros (§21), cross-module macro sharing (§22), a Racket-differential correctness oracle and continuous fuzz canary (§23).

Language: Rust 1.78+ MSRV (ADR-01, §9). Rejected: OCaml (native GADT-like ASTs, but a weaker wasm-sandbox embedding story than wasmtime's Rust-native API); C++ (no memory-safety guarantee for a component whose entire value proposition is hygiene-by-construction — a use-after-free in the expander is worse than a hygiene bug); Haskell (strong pattern matching, but the target host ecosystem is Rust macro_rules!/proc-macro compatible, and subprocess + wasmtime bindings are easiest to drive from Rust).

Prerequisites: lexing/parsing systems knowledge, one hygienic-macro paper (Kohlbecker 1986, §5), set/graph algebra comfort, WebAssembly sandboxing basics.

Estimated timeline: Phase 0 — 2 weeks. Full system (Phases 0–11) — 7 months.

Deferred features (register in §37): PhaseDeferred("§15") syntax-class pattern definitions; PhaseDeferred("§21") inline procedural macros; PhaseDeferred("§20") macro debugger; PhaseDeferred("§27") LSP hover-expansion; PhaseDeferred("§26") distributed build-cache network layer.

2. Why Build This

A macro system is the canonical metaprogramming facility whose textbook description is half a page and whose production implementation is decades of refinement. Kohlbecker's algorithm (1986) is twelve pages; Clinger-Rees (1991) syntactic closures, ten; Flatt's set-of-scopes (2016), twenty. Production reality is keeping identifier capture impossible under arbitrary macro nesting while not breaking the obvious cases: a macro that introduces a let binding the caller also names; a macro that splices a caller expression into a position where the caller's local bindings must remain visible; a macro expanding into another macro; a macro consuming a token stream produced by yet another macro. swap!(a, b) expanding to { let tmp = a; a = b; b = tmp; }, invoked as swap!(tmp, x), must not let the macro's internal tmp collide with the caller's tmp (§8 worked example). Every architectural decision here is downstream of that one problem.

Historically, three architectures compete: text-substitution (C preprocessor — unsound, §36 AA4), AST-rewriting templates (Java annotation processors — sound, limited), full procedural macros (Lisp defmacro — sound, unbounded, hygiene-by-author-discipline, §36 AA3). Systems that shipped set-of-scopes hygiene (Racket, Rust since 2017) get the structural guarantee that a macro-introduced identifier is distinct from any caller identifier with the same surface name — load-bearing for module systems, error reporting, IDE tooling, refactoring, and edition migrations (project 139 — LSP Server depends on stable macro-expansion diagnostics; project 145 — Borrow Checker depends on resolved, not raw, AST; project 241 — Trait Resolution Engine assumes expansion is complete and hygienic before it runs).

This project owns the full pipeline: lexer (scope-set-bearing tokens), pattern-matching macro language (match-like patterns, ellipsis quantifiers, template expansion), procedural macro runtime (sandboxed AST → AST, deterministic-execution constraint), expander (set-of-scopes hygiene, mark generation, fixpoint), resolver (scope-set-aware name lookup), diagnostics (invocation + definition span), modules (import/re-export without scope drift), and the conformance/differential/fuzz suite proving every invariant.

The bar is Racket's: a macro system deployable under a million-line program with a thousand third-party libraries, with no fear of a hygiene violation, a confusing diagnostic on triple-nested expansion, or a compile-time regression that visibly slows builds.

What Mastery Looks Like — after building this, the reader can:

  • Explain why identifier identity must be (name, scope-set) rather than a renamed symbol, and reproduce Flatt's 2016 argument for why this beats Kohlbecker 1986 and Clinger-Rees 1991 — cemented in §17 (Phase 5).
  • Implement a fixpoint expansion driver with a provable termination bound (iteration cap × depth cap) instead of an ad hoc timeout — cemented in §18 (Phase 6).
  • Design a pattern-matching macro language with fragment kinds and follow-set disambiguation that rejects ambiguous grammars at definition time, not at first invocation — cemented in §15 (Phase 3).
  • Build a capability-sandboxed procedural-macro runtime where determinism is a first-class contract, not an afterthought — cemented in §21 (Phase 9).
  • Keep a resolver as the sole consumer of scope-set information, preserving phase separation between syntactic expansion and semantic name resolution — cemented in §19 (Phase 7).
  • Produce diagnostics that remain debuggable through five levels of macro-in-macro expansion — cemented in §20 (Phase 8).
  • Build and interpret a differential-oracle test harness (against Racket) and understand exactly what it does and does not prove about correctness — cemented in §23 (Phase 11), MM7 (§32).

Lexer — converts raw bytes to a TokenStream; every token's scope set starts empty (no hygiene decision made yet); Unicode identifiers follow UAX #31. Parser — builds the AST; a MacroInvocation node is first-class and holds its unexpanded TokenStream verbatim so the expander can re-tokenize with fresh scope marks. Pattern matcher — consumes a macro arm's PatternTree against an invocation's TokenStream, producing metavariable bindings or a diagnosable failure (§15). Template substitute — walks a TemplateTree, replacing metavariable references with their bound fragments and expanding ellipsis repetitions (§16). Set-of-scopes mark + fixpoint driver — the hygiene core: allocates use-site/intro scopes, marks tokens, and iterates until no invocations remain or a cap trips (§17–18). Procedural macro sandbox — a wasmtime engine invoked in place of the pattern-matching machinery when a macro is MacroKind::Procedural; the sandbox's output re-enters the same fixpoint loop (§21). Modules — tracks each macro's immutable definition-site scope across import/re-export so re-exporting never rewrites lexical context (§22). Resolver — the only pass that inspects scope sets; converts every identifier use to a resolved binding or a diagnostic (§19). Downstream — type checker and codegen consume resolved AST only; they never see a ScopeSet (I8, §7). Diagnostics — a cross-cutting overlay: every box above can emit a Diagnostic carrying both invocation and definition spans (§20).

Three properties hold system-wide and are referenced throughout: the scope set is carried on every token from lexer to resolver, and no pass loses it (I3, §7); the expander is purely syntactic and never consults the resolver, so expansion order can never depend on semantic information (I8); the resolver is the only scope-set consumer downstream of the expander, so a type checker written once against resolved AST never needs to understand hygiene at all (MM6, §32).

6. Design Principles

  1. P1 — Scope-Set Hygiene by Construction. Identifier identity is (surface name, scope set), never a renamed symbol. Trade-off: every substitution step must carry scope-set bookkeeping. Operational implication: diagnostics show real user-written names. Violating it: silently regresses to alpha-renaming's diagnostic opacity.
  2. P2 — One Transformer Contract, Two Macro Kinds. Pattern macros and procedural macros both implement MacroTransformer (§11), but pattern macros run inside the expander's algebra while procedural macros run in the sandbox. Trade-off: two code paths to maintain. Operational implication: a bug class is isolated to one kind at a time. Violating it: a unified "just call arbitrary code" model loses hygiene-by-default for the common case (§36 AA3).
  3. P3 — Expansion Is a Pure Function of (AST, Scope State). No ambient global mutable state. Trade-off: scope-ID allocation must thread explicitly. Operational implication: expansion is trivially parallelizable across independent compilation units (§31). Violating it: reintroduces cross-file nondeterminism (T5).
  4. P4 — Fixpoint Expansion, Bounded. Iterate outer-to-inner until no invocations remain or the iteration/depth caps trip (§4). Trade-off: legitimately deep macros need a documented escape (raise the cap). Operational implication: compile time is provably bounded. Violating it: an unbounded loop is a compiler-hang DoS (T4).
  5. P5 — The Resolver Is the Sole Scope-Set Consumer. Type checker and codegen never see a ScopeSet (I8). Trade-off: the resolver must fully commit to resolved names before handing off. Operational implication: downstream passes are hygiene-agnostic and reusable. Violating it: couples every future front-end pass to macro internals (MM6).
  6. P6 — Diagnostics Carry Definition Site + Invocation Site + Expansion Trace. Every macro error is walkable end to end (I9). Trade-off: diagnostic objects are larger. Operational implication: multi-level macro-in-macro failures stay debuggable. Violating it: users get "error in generated code" with no way back to their own call site (FM-8).
  7. P7 — Procedural Macros Are Sandboxed and Deterministic by Default. No ambient I/O; escape hatches are explicit opt-ins (§21). Trade-off: sandbox overhead per invocation. Operational implication: builds are reproducible and supply-chain-safe. Violating it: a compromised macro crate gets arbitrary host access at compile time (T8).
  8. P8 — Definition-Site Scope Travels With Re-Exports. A macro's lexical context is a property of the macro, not of wherever it is imported (I6). Trade-off: modules (§22) must store and never mutate this field. Operational implication: re-exported macros keep resolving their own helpers correctly. Violating it: reproduces FM-7.
  9. P9 — Source-Order Determinism. Scope IDs and expansion order are a function of source position, never thread/allocation order (I2). Trade-off: forecloses some lock-free allocator designs. Operational implication: byte-identical builds across machines. Violating it: reproduces FM-4.
  10. P10 — Fail Closed on Ambiguous Resolution. Two equally specific candidate bindings is a compile error, never a silent pick (I5). Trade-off: some programs the author "meant" one way are rejected. Operational implication: no silently-wrong resolution ships. Violating it: reproduces FM-5's false confidence.
  11. P11 — Grammar and Hygiene Are Orthogonal Concerns. The pattern/fragment grammar (what syntax matches) is decided independently of the scope algebra (what identifiers mean). Trade-off: two subsystems to specify (§15 vs §17) instead of one. Operational implication: either can evolve without destabilizing the other. Violating it is the C preprocessor's original sin — mixing the two makes hygiene impossible to retrofit (§36 AA4).
  12. P12 — Conformance Before Performance. Every optimization (memoization, store pooling, caching) must not change any bucket's expected output; the differential oracle gates every merge (I12). Trade-off: some fast paths are deferred until proven safe. Operational implication: performance work never silently regresses correctness. Violating it repeats the Communion.md-class failure of shipping unverified claims.
  13. P13 — Every Escape Hatch Is Explicit and Audited. Sandbox capability grants (clock, random, network) are opt-in per macro and appear in a build manifest (I11). Trade-off: macro authors needing a capability must declare it visibly. Operational implication: an audit can enumerate every non-default-safe macro in a build. Violating it silently reproduces T2/T8's blast radius.
  14. P14 — Macros Are First-Class, Namespaced Items. A macro is importable, exportable, and shadowable exactly like a function or type, never a second-class textual construct. Trade-off: the module system (§22) must model macros as items. Operational implication: libraries can ship macros safely. Violating it reproduces the C preprocessor's flat, unscoped #define namespace.

8. Domain Model

8.1 Grammar

MacroDef      ::= "macro" Ident "{" MacroArm+ "}" | "macro" Ident "=" "proc" Path ";"
MacroArm      ::= Pattern "=>" Template ";"
Pattern       ::= PatternTok*
PatternTok    ::= Token | MetaVar | Repeat
MetaVar       ::= "$" Ident ":" FragKind
FragKind      ::= "ident" | "expr" | "pat" | "ty" | "path" | "tt"
                | "block" | "stmt" | "literal"
Repeat        ::= "$" "(" PatternTok+ ")" Sep? Quant
Quant         ::= "*" | "+" | "?"
Sep           ::= Token                      (* excludes Quant tokens *)
Template      ::= TemplateTok*
TemplateTok   ::= Token | MetaVarRef | TRepeat
TRepeat       ::= "$" "(" TemplateTok+ ")" Sep? Quant
MacroInvoc    ::= Path "!" "(" TokenTree* ")"

8.2 Pattern/template matching

The matcher (§15) consumes a PatternTree against an invocation's TokenStream, producing either Bindings: Vec<(MetaVarName, FragmentValue)> or a diagnosable failure. Repetition matches accumulate a list per ellipsis-bound metavariable; zero matches yields an empty list, never an error (I10 guards the follow-set ambiguity this raises with $x:expr followed directly by +).

8.3 Set-of-scopes hygiene algorithm — state table

Step Input Action Output
1 AST node = MacroInvocation allocate fresh use-site scope U caller tokens marked +U
2 macro definition tokens allocate fresh intro scope I definition tokens marked +I
3 marked invocation tokens vs PatternTree pattern match (§15) bindings, each fragment carrying its own +U-bearing scope set
4 bindings + TemplateTree substitute (§16): template tokens get +I; metavar-bound tokens keep their caller scope set expanded TokenStream
5 expanded TokenStream re-parse into AST fragment fragment scoped {…,I} for def tokens, {…,U} for spliced caller tokens
6 AST fragment check for residual MacroInvocation nodes none: fixpoint reached (§18); some: repeat from step 1, one level deeper (bounded by I4)

8.4 Worked example — swap!

Definition: macro swap { ($a:expr, $b:expr) => { let tmp = $a; $a = $b; $b = tmp; } }, defined in lexical scope {S_def}. Invocation: swap!(tmp, x) at call site scope {S0}.

Token (origin) Scope set after expansion
let (definition) {S_def, I7}
tmp (definition's own, the let-bound one) {S_def, I7}
tmp (from $a, caller's) {S0, U7}
x (from $b, caller's) {S0, U7}

Resolver (§19) sees two distinct tmp identities: tmp@{S_def,I7} (the macro's own let binding) and tmp@{S0,U7} (the caller's variable, substituted via $a). Because neither scope set is a subset of the other in the general case (S_def ≠ S0), the two never collide — hygiene holds by construction, matching I1/I3.

8.5 Malformed-input example

swap!(tmp) — arity mismatch, missing the $b:expr argument. The matcher's arity/ follow-set check (I10) finds no arm matches; a diagnostic is emitted naming the expected fragment ($b:expr) and the invocation span — handled by Phase 8 (§20).

8.6 Failure-path example

macro loopy { () => { loopy!() } } invoked as loopy!(). Each expansion step produces another loopy!() invocation; the invocation count never strictly decreases. The iteration cap (1,024, §4) trips; the fixpoint driver (§18) emits a cycle-detection diagnostic naming the full invocation chain (I4, T4, FM-2, §24/§25).

impl ScopeSet {
    pub fn empty() -> Self;

    pub fn flip(&self, s: ScopeId) -> Self;
    pub fn is_subset_of(&self, other: &ScopeSet) -> bool; // resolver subset check (I5)

Ownership: Token owned by AST nodes, cloned on substitution (cheap: SmolStr + BTreeSet<u64>). Mutation: ScopeSet is immutable/functional (add/remove/flip return new values) — enforces I3. Concurrency: Send + Sync, safe to share across parallel compilation units (P3). Persistence: not persisted directly; the expansion cache (ADR-13) stores a content hash of the resolved AST, not raw tokens. Serialization: bincode-derivable for the sandbox boundary (ADR-14). Compatibility: ScopeId is an opaque u64; never serialized across compiler versions (§27).

15. Phase 3 — Pattern Language and Matcher

15.1 Objectives

  • Implement ms-patterns: PatternTree, the 9 fragment kinds (ADR-06), repetition (Quantifier), and the matcher producing Bindings or a diagnosable failure.

15.2 Detailed Implementation Steps

  • Fragment kinds ident/expr/pat/ty/path/tt/block/stmt/literal each own a dedicated sub-parser invoked by the matcher (Blandy et al. Ch. 20, §5, applied here).
  • Follow-set checking at macro-definition time (I10): for every metavar immediately followed by a literal token, verify the fragment kind's grammar cannot itself consume that token — reject ambiguous arms before any invocation (P11, I10).
  • Repetition matcher recurses on the inner PatternTree, accumulating one FragmentValue per iteration into a list; Quantifier::ZeroOrMore matching zero times yields an empty list (never an error) — a named pitfall class from B1 (Dybvig, §5).
  • Matcher failure produces a diagnosable "closest arm" record for the suggestion engine (feeds §20's best-effort matching, ADR-11).

15.3 Deliverable

ms-patterns matches every fixture in conformance/buckets/patterns/, including the swap!/or!/for! example macros' pattern arms.

15.4 Acceptance Criteria

Match a 1,000-token pattern against a 10,000-token input: p50 ≤ 5 ms (M4, §30); ≥ 25 fixtures green in patterns/, one per fragment kind plus 3 repetition-quantifier cases.

15.5 Conformance Fixtures

conflicting_arm.rs | $x:expr directly followed by + | rejected at definition time (I10) naming the ambiguous arm. empty_repeat.rs | $($x:ident),* matching zero idents | empty binding list, template emits nothing. fragment_kind_matrix.rs | one invocation per of the 9 kinds | each binds correctly.

15.6 Pitfalls

  • :expr vs :tt interchangeable in simple cases but differ on parser precedence — $x:expr + 1 parses x greedily; $x:tt + 1 does not (ADR-06).
  • A repetition separator token that itself matches a quantifier token (*/+/?) is rejected at definition time, not silently misparsed.

15.7 Performance Concerns

Backtracking in the fragment sub-parsers is memoized per (position, fragment-kind) pair to avoid quadratic re-parsing on deeply repeated patterns — the named bottleneck of §31 item 1.

15.8 Edge Cases

A pattern with zero metavariables (a fixed-shape macro); a repetition nested inside another repetition ($($($x:ident),*);*); a tt fragment matching a whole delimited group atomically.

15.9 Failure Analysis

A bug in follow-set resolution accepts a pattern that should be rejected, surfacing only when an ambiguous invocation later silently picks the wrong arm — mitigated by I10's static check plus the conflicting_arm.rs regression fixture guarding the exact historical bug shape.

15.10 Operational Notes

patterns.follow_set_rejections_total metric tracks how often macro authors hit the ambiguity guard, informing whether PhaseDeferred("§15") syntax-classes (Culpepper & Felleisen, §5) should be un-deferred (§37 trigger).

  • Implement ms-patterns' template half: substitute Bindings into a TemplateTree, producing a flat TokenStream — deliberately without scope marking yet, to isolate substitution correctness from hygiene correctness (P11: two orthogonal concerns, proven independently before composing them in Phase 5).

16.2 Detailed Implementation Steps

  • Walk TemplateTree; MetaVarRef substitutes the bound FragmentValue's token sequence verbatim; TRepeat iterates in lock-step across every ellipsis-bound metavar referenced inside it (rejecting mismatched repetition lengths as a definition-time error, an application of I10's discipline to templates).
  • This phase's expander is intentionally the unhygienic baseline (equivalent to Kohlbecker-era text substitution, P1's rejected starting point, §5 Kohlbecker 1986) — Phase 5 replaces it with scope marking; keeping the two phases separate lets the conformance suite prove "substitution is correct" and "hygiene is correct" as independent claims.
  • conformance/buckets/hygiene/ gains its first (expected-failing) fixtures here: the swap!(tmp, x) self-collision case, captured as a known-broken baseline to be fixed by Phase 5, not silently passing.

16.3 Deliverable

The unhygienic baseline expander correctly substitutes every fixture's tokens (substitution-only correctness), while swap_self_collision.rs is a documented, expected-red fixture proving the baseline's capture bug exists before it is fixed.

16.4 Acceptance Criteria

100% of patterns/ template-substitution fixtures green; swap_self_collision.rs explicitly asserted RED (capture reproduced) as a regression guard that Phase 5 must flip to GREEN — a red-to-green transition is itself part of Phase 5's N.4.

16.5 Conformance Fixtures

swap_self_collision.rs | swap!(tmp, x) under unhygienic substitution | asserted RED: tmp and x end up bound to the same slot. repeat_length_mismatch.rs | two ellipsis-bound metavars of different lengths in one TRepeat | definition-time rejection.

16.6 Pitfalls

  • Confusing "substitution is correct" with "expansion is hygienic" — a common Kohlbecker- era conflation (B2 Graham, §5) this phase's explicit red fixture exists to prevent.
  • Forgetting to carry Span provenance through substitution breaks Phase 8's diagnostic spans two phases later.

16.7 Performance Concerns

Template substitution is O(template size × repetition count); no scope-set overhead yet (deferred to Phase 5) isolates this phase's own perf baseline for later comparison.

16.8 Edge Cases

A template that references a metavar never bound by the pattern (definition-time error); an empty template (macro that expands to nothing, valid for e.g. conditional-compilation- style macros).

16.9 Failure Analysis

A substitution bug here is indistinguishable from a hygiene bug unless the two are tested separately — this phase's entire purpose is making that distinction possible for Phase 9's diagnostics and Phase 11's differential oracle.

16.10 Operational Notes

The red swap_self_collision.rs fixture is tagged expected-failure in the bucket runner so CI does not block on it, but Phase 5's exit criteria requires it flip to green.

17. Phase 5 — Set-of-Scopes Hygienic Expander

17.1 Objectives

  • Replace Phase 4's unhygienic baseline with Flatt's set-of-scopes algorithm (P1, ADR-02): allocate use-site and intro scopes per invocation, mark tokens, and flip swap_self_collision.rs from red to green.

17.2 Detailed Implementation Steps

  • Per invocation: allocate fresh use-site scope U (§8.3 step 1); allocate fresh intro scope I for the macro's definition tokens (step 2); mark caller tokens +U, definition tokens +I (I3: scopes only added/flipped, never dropped, during this step).
  • Template substitution (Phase 4's logic, reused) now runs on marked tokens: a MetaVarRef's substituted tokens keep the caller's own scope set (their +U); template- literal tokens keep the definition's +I (§8.3 step 4, Flatt 2016 §5).
  • Re-parse the expanded TokenStream into an AST fragment (§8.3 step 5); if it contains residual MacroInvocation nodes, hand off to the fixpoint driver (§18) rather than recursing inline here (P3: expansion stays a pure function, no ambient recursion state).
  • ScopeSet::flip (§11) is used, not add, when a definition-site scope must be toggled for a re-entrant macro invoking itself with a different argument list — this is the one place flip differs operationally from add (Adams 2015, §5, applied here).

17.3 Deliverable

swap_self_collision.rs (Phase 4's red fixture) is green; conformance/buckets/hygiene/ covers ≥ 15 canonical patterns (swap!, or!, for!, an anaphoric-macro deliberate- capture case documented as intentional per B2/Graham, §5).

17.4 Acceptance Criteria

Expand 1,000 macro invocations at depth ≤ 5: p50 ≤ 200 ms (M5, §30); zero scope-loss assertions triggered (I3) across the full hygiene/ bucket; swap_self_collision.rs green.

17.5 Conformance Fixtures

swap_hygiene.rs | swap!(tmp, x) | resolves to two distinct tmp bindings (§8.4). anaphoric_deliberate.rs | a macro intentionally capturing it | documented exception, asserted intentional via an explicit opt-out annotation, not a silent bug. nested_macro_ hygiene.rs | macro-in-macro, 3 levels | each level's intro scope stays distinct.

17.6 Pitfalls

  • The "definition site" of a macro is its lexical context at definition, not at import — macros imported from another module retain the original module's definition site (previews §22; a bug here surfaces only once Phase 10 lands, so a dedicated Phase 5 unit test locks def_site immutability early).
  • Splicing a $x:expr metavar into a non-expression template position is rejected by the re-parse step (§8.3 step 5), with the diagnostic (stubbed until §20) pointing at both spans.

17.7 Performance Concerns

Scope-set add/flip cost is O(log k) for k scopes on a token (§4's depth cap of 64 bounds k); measured against M5's 200 ms budget for 1,000 invocations.

17.8 Edge Cases

Two macros invoked at the same call site sharing the use-site scope but requiring distinct intro scopes (m1!(); m2!(); must not collide, per §17.6's definition-site discussion); a macro invoking itself recursively with flip semantics (Adams 2015).

17.9 Failure Analysis

A scope-set bug that drops a scope during substitution breaks hygiene silently until the differential oracle (§23) or a scope-set post-expansion assertion (I3's enforcement point) catches it; blast radius is every macro invocation downstream in the same compilation unit.

17.10 Operational Notes

tracing span expand_invocation records {use_site, intro_scope, depth} per call, feeding the expansion-trace viewer (tools/, §37 deferred debugger).

18. Phase 6 — Fixpoint Driver, Recursion Limits, Termination

18.1 Objectives

  • Implement FixpointDriver (§11): iterate Phase 5's per-invocation expansion outer-to- inner until no MacroInvocation nodes remain, enforcing the iteration cap (1,024) and depth cap (64) from §4 (I4, P4).

18.2 Detailed Implementation Steps

  • Outer loop walks the AST for MacroInvocation nodes in source order (P9: deterministic traversal, not HashMap iteration order — ADR-08); each found invocation increments its own depth field and the driver's global iterations counter.
  • Cap check: iterations > 1024 or any invocation.depth > 64 emits a cycle-detection Diagnostic naming the full invocation chain (stub spans; full rendering §20) and halts the unit's expansion (T4, FM-2, I4).
  • Termination argument (MM4, §32): each successful expansion step strictly reduces the count of not-yet-expanded invocations by at least the one just expanded, though it may introduce new ones — the cap exists precisely because that reduction is not itself provable for arbitrary macros, only assumed for well-formed ones (Queinnec Ch. 12, §5).
  • Two-run determinism harness (--assert-determinism): run the same unit twice, byte-diff the resulting TokenStream (I2/I14, ADR-08) — this phase is where P9's promise becomes mechanically checked, not just designed-in.

18.3 Deliverable

ms-expander (fixpoint half) processes loopy!() (§8.6's failure-path example) and every legitimate nested-macro fixture in hygiene/ to a stable, capped result.

18.4 Acceptance Criteria

loopy_self_recursive.rs fixture trips the iteration cap and emits a diagnostic naming the cycle within 1,024 iterations, never hanging; two-run byte-diff is 0 bytes across the entire hygiene/ + patterns/ buckets (M10, §30); depth-64 fixture (nested_64_deep.rs) accepted, nested_65_deep.rs rejected with a depth-cap diagnostic.

18.5 Conformance Fixtures

loopy_self_recursive.rs | macro loopy { () => { loopy!() } } | cap-exceeded diagnostic naming the chain. nested_64_deep.rs | 64 levels of legitimate nesting | accepted. nested_65_deep.rs | 65 levels | depth-cap diagnostic.

18.6 Pitfalls

  • Iteration cap too low rejects legitimate deeply-recursive macros (e.g. a Church-numeral- style encoding expanding to 200 invocations of itself) — 1,024 is chosen with headroom documented in ADR-07's rationale, and the cap is a tunable, not hard-coded.
  • Determinism regressions often hide in incidental HashMap/HashSet iteration inside the driver's bookkeeping — every internal collection here is BTreeMap/Vec, audited specifically for this phase.

18.7 Performance Concerns

Worst-case wall-clock bound: iteration cap × per-iteration cost ≈ 1,024 × 200 µs ≈ 205 ms (§34 item 4) — consistent with M5/M9's budgets; this bound is what makes P4's "provably bounded compile time" claim concrete rather than aspirational.

18.8 Edge Cases

A macro that expands to exactly the cap boundary (1,024th iteration resolves cleanly); concurrent expansion of independent compilation units sharing no state (P3) must produce identical per-unit results regardless of scheduling.

18.9 Failure Analysis

A non-terminating macro without the cap would hang the compiler indefinitely (T4); with the cap, blast radius is contained to the one offending compilation unit, and the diagnostic's invocation chain lets the author locate the missing base case immediately.

18.10 Operational Notes

expander.cap_exceeded_total and build.determinism_check_failed_total metrics (§7) feed the hygiene-regression and a new nontermination-spike runbook (§26).

19. Phase 7 — Resolver

19.1 Objectives

  • Implement ms-resolver: the sole consumer of ScopeSet information (I8, P5); converts every identifier use in the expanded AST into a resolved Binding or a diagnostic.

19.2 Detailed Implementation Steps

  • Candidate collection: for each identifier use, gather every Binding sharing its surface name (§8.3's identity model, I1).
  • Subset filter: retain only bindings whose scopes is a subset of the use's scopes (ScopeSet::is_subset_of, §11) — the use must be "in scope" for the binding (Herman & Wand 2008, §5, formal grounding for this step).
  • Most-specific selection: among remaining candidates, pick the one with the largest scope set; if two candidates tie in size, or none remain, emit an ambiguous/unresolved diagnostic (I5, P10) — never a silent pick.
  • The resolver never imports ms-expander's internals beyond ScopeSet itself — enforced by the I8 static lint (a cargo-deny rule banning ms-resolver → ms-expander beyond the shared ms-tokens crate).

19.3 Deliverable

ms-resolver resolves every identifier in the hygiene/ and resolver/ buckets to exactly the binding the fixture's expected-output annotation names.

19.4 Acceptance Criteria

Resolve 10,000 identifiers: p50 ≤ 100 ms (M6, §30); zero I5 violations (no silent ambiguous pick) across ≥ 20 resolver/ fixtures; swap_hygiene.rs resolves its two tmp identities to two distinct DefIds.

19.5 Conformance Fixtures

ambiguous_binding.rs | two candidates with incomparable, equally-specific scope sets | ambiguity diagnostic, no pick. macro_vs_user_tmp.rs | a macro-introduced tmp and a user tmp in the same lexical region | resolves to the user's binding (its scope set lacks the macro's intro scope, so it is strictly less specific in the caller's context and wins per shadowing rules) — see §8.4.

19.6 Pitfalls

  • A subset-check bug that treats disjoint scope sets as comparable silently resolves wrong (FM-5) — guarded by ambiguous_binding.rs and a property test over random scope-set pairs (ADR-19).
  • Forgetting I8's boundary and letting a convenience helper reach into ms-expander reintroduces the exact coupling P5 exists to prevent.

19.7 Performance Concerns

Candidate collection is O(bindings sharing a name); for pathological programs with thousands of same-named macro-introduced bindings, an index keyed by surface name bounds this to O(1) average lookup before the O(k) subset-filter over the k same-named candidates.

19.8 Edge Cases

Zero candidates (genuinely unresolved identifier — user typo); exactly one candidate whose scope set is not a subset (still unresolved, must not fall back to "pick anyway"); a binding introduced by a macro that itself was never invoked (dead code, still must not appear as a candidate).

19.9 Failure Analysis

A resolver bug either produces a false "unresolved" (blocks valid programs, high visibility, fast bug reports) or a false silent-correct-looking resolution (low visibility, caught only by I12's differential oracle) — the second is far more dangerous and is why I5 is enforced as fail-closed rather than best-effort.

19.10 Operational Notes

resolver.ambiguous_total and resolver.identity_mismatch_total metrics (§7) surface on the same dashboard as expander metrics for correlated triage during a hygiene-regression incident (§26).

20. Phase 8 — Diagnostics Through Expansion

20.1 Objectives

  • Implement ms-diagnostics: render every macro-expansion error with invocation span, definition span, and a full expansion trace (I9, P6); implement the suggestion engine's re-expansion check (I13).

20.2 Detailed Implementation Steps

  • Diagnostic (§11) is built incrementally as expansion recurses: each fixpoint iteration (§18) that touches a MacroInvocation pushes its span onto trace; a terminal failure (parse error, cap exceeded, ambiguous resolution) sets primary and definition_site.
  • Renderer strips internal ScopeIds from user-facing text (P1, T7) — shows surface name and span only; an internal --debug-scopes flag opts back in for maintainers.
  • Suggestion engine: for a pattern-match failure, find the closest arm by edit-distance over expected vs actual fragment kinds (ADR-11); every suggestion is re-expanded and re-parsed before being surfaced (I13) — a suggestion that fails re-expansion is suppressed, not shown broken (a named Culpepper & Felleisen "fortifying" discipline, §5).
  • For procedural macros (interface stub here, implemented §21), the macro's own panic message is surfaced verbatim alongside the sandboxed invocation's span.

20.3 Deliverable

Every fixture in conformance/buckets/diagnostics/ renders a snapshot-tested message containing both spans and, where applicable, a re-expansion-checked suggestion.

20.4 Acceptance Criteria

100% of ≥ 18 diagnostics/ snapshot fixtures match byte-for-byte; zero internal ScopeIds appear in any rendered message (grep-checked in CI); every surfaced suggestion passes its re-expansion check (I13) — 0 "bad suggestion" escapes in the bucket.

20.5 Conformance Fixtures

nested_failure_trace.rs | a 3-level macro-in-macro pattern-match failure | trace lists all 3 invocation spans plus the definition span of the failing arm. suppressed_bad_ suggestion.rs | a suggestion that would not re-parse | suppressed, fixture asserts no suggestion field present rather than a broken one.

20.6 Pitfalls

  • A "no pattern matched" diagnostic that names only the innermost arm (not the closest) confuses users — the edit-distance closest-arm heuristic (ADR-11) exists specifically to avoid this.
  • Diagnostics built before the trace is complete can freeze a stale (too-shallow) trace — the builder appends spans lazily, finalized only at the terminal failure point.

20.7 Performance Concerns

Diagnostic construction is off the hot path (only built on failure); the renderer's ScopeId-stripping pass is O(message length), negligible next to expansion cost.

20.8 Edge Cases

A failure inside a procedural macro invoked from inside a pattern macro (mixed-kind trace); a suggestion whose re-expansion succeeds but produces a different diagnosable error (still suppressed — only a suggestion that fully resolves is surfaced).

20.9 Failure Analysis

A diagnostic that misattributes invocation vs definition span (FM-8) is caught by nested_failure_trace.rs's exact span-ordering assertion; blast radius is user confusion, not a correctness bug, but it is treated with equal severity because debuggability is a first-class invariant (I9).

20.10 Operational Notes

diagnostics.bad_suggestion_suppressed_total (§7, I13) tracked as a leading indicator for PhaseDeferred("§20")'s macro-debugger un-defer trigger (§37).

21. Phase 9 — Procedural Macros and the Sandbox

21.1 Objectives

  • Implement ms-procmacro: a wasmtime-backed sandbox executing MacroKind::Procedural transformers under the MacroTransformer contract (P2), with capability defaults all- false (I11, P7, P13).

21.2 Detailed Implementation Steps

  • Compile the procedural macro to a .wasm module ahead of time; the host invokes expand(input_ptr, input_len) -> output_ptr/len after serializing the TokenStream via bincode (ADR-14) across the boundary — a scheme informed by dtolnay/syn + proc-macro2's TokenStream boundary shape (§5, applied here).
  • AllowedCaps (§11) is read from the macro's manifest at load time; the sandbox denies filesystem, process-spawn, network, clock, and random by default (I11) — an author must explicitly opt in per capability, and the opt-in is recorded in the build manifest for audit (P13, ADR-24).
  • Store pooling: each invocation prefers a warmed, reset wasmtime::Store from a bounded pool (§4's 256-instance ceiling, ADR-28's backpressure) rather than cold-initializing per call; a reset-and-verify step (asserting zero residual linear memory) runs before reuse (T12).
  • Timeout: wasmtime fuel metering plus a wall-clock deadline (default 5,000 ms, §4) terminates a runaway invocation; the trap is caught at the host boundary, isolated to that one invocation (I7's hermeticity — the trap must not corrupt the pool).

21.3 Deliverable

ms-procmacro runs the examples/ derive-like macro and a format-string macro through the sandbox, producing deterministic output across 10 repeated invocations with identical input.

21.4 Acceptance Criteria

Warm invocation p50 ≤ 200 µs, cold ≤ 5 ms (M7/M8, §30); hermeticity property test (I7) passes 1,000 randomized trials with zero output variance; procmacro/ bucket ≥ 12 fixtures green including a timeout fixture that trips at exactly the configured deadline.

21.5 Conformance Fixtures

derive_debug_like.rs | a derive-style procedural macro | deterministic expanded output across repeated runs. infinite_loop_macro.rs | a macro with a deliberate infinite loop | killed at the 5,000 ms default timeout, diagnostic names the macro. capability_denied.rs | a macro attempting file I/O without a manifest grant | SandboxError::CapabilityDenied.

21.6 Pitfalls

  • Wasmtime initialization overhead is significant per cold call — store pooling amortizes it, but a pool that does not fully reset state between invocations reintroduces a cross-macro information leak (T12) — the reset-and-verify step is the mitigation.
  • A procedural macro timing out from an infinite loop needs both the fuel/timeout kill and a localized diagnostic (P6) — a bare kill with no diagnostic just silently hangs the perceived build from the user's point of view.

21.7 Performance Concerns

Per-invocation cost dominated by (de)serialization at low token counts, by wasm execution at high token counts; store-pool contention becomes the named bottleneck under high parallel-build concurrency (§31 item 2), bounded by the FD budget (§4).

21.8 Edge Cases

A macro invocation whose serialized TokenStream exceeds a size ceiling (rejected before sandbox entry, not after); a macro that legitimately needs wall-clock time (opts into clock: true explicitly, audited per P13); concurrent invocations racing for the same pooled store slot.

21.9 Failure Analysis

A sandbox escape (in theory, via a wasmtime CVE) is tracked as T2; detection relies on wasmtime security-advisory monitoring plus cargo-audit in CI (ADR-24); recovery is pinning/patching wasmtime and revoking the affected macro's publish token.

21.10 Operational Notes

sandbox.timeout_total, sandbox.capability_denied_total, sandbox.store_reset_ failures_total metrics (§7) feed the sandbox-timeout-spike runbook (§26); the capability-audit log is retained for supply-chain review (T8).

22. Phase 10 — Modules, Imports, and Re-Exports

22.1 Objectives

  • Implement ms-modules: macros as first-class namespaced items (P14) importable and re-exportable across module boundaries without mutating MacroDef.def_site (I6, P8).

22.2 Detailed Implementation Steps

  • ModuleGraph (§11) tracks every MacroDef keyed by MacroDefId; an Import record stores the importing path alongside a copy of the original def_site, never a rewritten one (Tobin-Hochstadt et al. 2011 "Languages as Libraries", §5, applied here: macros as libraries requires this exact non-mutation guarantee).
  • Re-export (pub use a::foo as bar) creates a second Import pointing at the same MacroDefId; both resolve helper identifiers through the original module's scope chain, never the re-exporting module's (Flatt et al. 2012 "Macros That Work Together", §5, applied here for partial-expansion-safe re-export semantics).
  • Topological ordering pass over the module import graph precedes parallel expansion (§31): cross-crate macro invocation resolution requires the imported crate's macros already registered in the ModuleGraph before expansion of the importing crate begins.

22.3 Deliverable

ms-modules correctly expands a macro defined in module a, re-exported through module b, and invoked from module c, resolving a's internal helper identifiers throughout.

22.4 Acceptance Criteria

modules/ bucket ≥ 10 fixtures green, including a 2-hop re-export chain (reexport_chain_a_b_c.rs); zero I6 violations (def_site immutability assertion) across the bucket; topological ordering pass on a 50-crate synthetic graph completes in < 50 ms.

22.5 Conformance Fixtures

reexport_chain_a_b_c.rs | macro defined in a, re-exported via b, invoked in c | resolves a's internal helper correctly. reexport_helper_missing.rs | a deliberately broken re-export that rewrites def_site | unresolved-name diagnostic (regression guard for FM-7).

22.6 Pitfalls

  • Re-exporting a macro must preserve its definition site; a re-export that "moves" the definition site breaks hygiene for any internal helper the macro calls (FM-7, T6) — the reexport_helper_missing.rs fixture pins this exact historical bug shape.
  • A cyclic import graph (crate a imports a macro from b, which imports one from a) must be rejected by the topological pass with a clear cycle diagnostic, not an infinite registration loop.

22.7 Performance Concerns

Topological ordering is O(crates + import edges), not O(invocations) — cheap even at large scale (§31); the dominant cost stays proportional to module count, not macro-call volume.

22.8 Edge Cases

Diamond import (module d imports the same macro from both b and c, both re-exporting from a) must resolve to one MacroDefId, not a duplicate/ambiguous one; a macro re-exported under a different name (as bar) must still report its original name in diagnostics' definition-site rendering.

22.9 Failure Analysis

A bug in import resolution makes a macro invisible to its importer (silent, high- visibility failure: "macro not found" instead of a subtle miscompile) — detection is immediate at the call site; a bug that instead corrupts def_site is silent and low- visibility until an internal-helper resolution fails downstream (FM-7's blast radius).

22.10 Operational Notes

resolver.unresolved_after_reexport_total (§7) is the leading indicator for this phase's health; docs/runbooks/ gains a re-export-drift entry cross-linked from differential- drift.md (§26).

23. Phase 11 — Differential Conformance, Fuzzing, Soak Canary

23.1 Objectives

  • Stand up the Racket-differential oracle (I12, ADR-10) and the 4-target fuzz suite (ADR-20), and gate releases on a 30-day continuous canary (ADR-12).

23.2 Detailed Implementation Steps

  • Differential harness: for each of ~500 curated corpus fixtures (written in a subset that lowers to both this system's surface and Racket's, per B6/Butterick, §5), run this expander and Racket's syntax-parse-based expander, then assert the resolved-AST shape matches modulo documented surface-syntax differences (I12); Dockerfile/docker-compose (ADR-23) pins the Racket version to avoid CI drift (FM-11).
  • Fuzz targets (ms-fuzz, ADR-20): (1) parser — random source → no panic; (2) expander — random macro definitions + invocations → converges or cleanly rejects within caps (I4); (3) procmacro — random TokenStream → sandbox host never crashes (FM-9); (4) differential — random macros → this expander and Racket agree (I12).
  • 30-day canary: a scheduled CI workflow (distinct from the per-PR 5-minute fuzz budget) runs all 4 targets continuously against a rolling 24h failure window (ADR-12); a failure blocks the release channel until root-caused (T10).
  • Capacity basis for "0 panics" being meaningful, not lucky: at ~2,000 exec/sec × 86,400 s/day × 30 days ≈ 5.18 billion executions (§34 item 8) — this is the statistical argument the canary's pass/fail actually rests on.

23.3 Deliverable

differential-racket/ bucket green on the full corpus; all 4 fuzz targets run 5 minutes per PR with 0 panics; the 30-day canary workflow is live and gating the release channel.

23.4 Acceptance Criteria

Differential corpus (~500 fixtures) runs in < 10 minutes (§34 item 6); divergence rate < 1%, and every divergence documented as an intentional surface-syntax difference (M9, §30); 30-day canary: 0 unexpected panics per rolling 24h window (M12); per-PR fuzz budget: 0 panics in 5 minutes per target (ADR-20).

23.5 Conformance Fixtures

differential_corpus/ (~500 files) | curated macro patterns lowering to both surfaces | resolved-AST parity. fuzz/corpus/regression_*.rs | minimized crash inputs from prior fuzz finds | must not reproduce the original crash.

23.6 Pitfalls

  • Racket and this system's surface syntax differ; the corpus is deliberately written in a lowest-common-denominator subset — expanding the corpus to cover new fragment kinds requires hand-verifying the Racket-side equivalent lowers correctly first.
  • A CI-only Racket version drift produces flaky, not failing, differential results (FM-11) — pinned via the Dockerfile, not the contributor's local Racket install (ADR-23).

23.7 Performance Concerns

Differential runtime is dominated by Racket process startup (~1.2 s/fixture including process spawn, §34 item 6) — batching fixtures into a single long-lived Racket process (rather than one process per fixture) is the primary lever if the 10-minute ceiling is threatened by corpus growth.

23.8 Edge Cases

A fuzz-found input that is valid but pathologically slow (not a panic, a perf cliff) is triaged separately from a crash — tracked as a perf-regression ticket, not a correctness bug; a differential divergence that turns out to be a Racket quirk (not this system's bug) is documented and excluded, never silently "fixed" by matching the quirk.

23.9 Failure Analysis

A fuzz-found hygiene violation reaching a release (T10) is the single most severe class this phase exists to prevent; detection is the 30-day canary blocking the release channel; recovery is holding the release, root-causing via an ADR, and adding the minimized input as a permanent corpus seed (FM-9's forensic path).

23.10 Operational Notes

fuzz.canary_failures_total and differential.divergence_total (§7) are the two headline metrics on the release-readiness dashboard (§26); the canary's rolling-window design means a single flaky failure does not itself block a release — only a reproducible one does.

27. Compatibility & Versioning

  • Wire (sandbox boundary): the bincode TokenStream ABI (ADR-14) is versioned independently of the compiler's own SemVer; a negotiation step at sandbox load time selects the highest ABI version both host and compiled macro support.
  • Storage: the expansion cache (ADR-13) is keyed by (content hash, compiler version); any compiler-version mismatch invalidates the cache entry rather than risking a stale hit.
  • Schema evolution: fragment kinds (ADR-06) are additive-only across minor versions — removing or redefining a kind's grammar is a major-version change.
  • API stability: public crate APIs (ms-tokens, ms-ast, ms-patterns) follow SemVer (ADR-25); ScopeId/ScopeSet internal representation is never part of the public stability contract (only the algebra in §11 is).
  • Migration: when a fragment kind's follow-set rules tighten (a previously-accepted ambiguous pattern becomes rejected, I10), a cargo fix-style lint ships one minor version ahead of the tightening, flagging affected macro definitions.
  • Deprecation policy: a deprecated fragment-kind behavior warns for 2 minor versions before removal.
  • Rolling-upgrade guarantees: a compiler upgrade must still expand macros compiled against the previous minor version's TokenStream ABI; both N and N-1 ABI versions are supported concurrently during the deprecation window (ties to §26's canary/rollback guarantee).

28. Testing & Verification Strategy

  • Unit: scope-set algebra (add/remove/flip/is_subset_of, §11), pattern matcher fragment-kind sub-parsers (§15).
  • Integration: per-crate conformance buckets (§10) exercised end-to-end through conformance/cli.
  • Property-based: proptest (ADR-19) over scope-set algebra identities (I3's foundation, §13.2) and over random scope-set pairs for the resolver's subset-check (guards FM-5).
  • Differential: the Racket oracle (I12, §23) — necessary, not sufficient, per MM7 (§32).
  • Fuzzing: 4 targets (parser, expander, procmacro, differential, ADR-20) run 5 minutes per PR and continuously for 30 days pre-release (ADR-12).
  • Chaos: kill a sandbox mid-invocation (simulated wasmtime trap) and assert a clean diagnostic, not a host crash (T2/FM-9's defense-in-depth check).
  • Deterministic replay: two-run byte-diff on every CI run (I2/I14, M10).
  • Soak: the 30-day canary (§23.2).
  • Fault injection: deliberately corrupt a pooled sandbox store's reset step and assert the reset-and-verify guard (§21.2) catches it before reuse (T12).
  • Conformance: the 9 buckets of §10, each tied to the invariant(s) and phase(s) it proves.
  • Performance-regression gating: every M-table target (§30) gates CI merge; a regression beyond its threshold fails the build, never silently degrades (P12).

Every fixture in every bucket traces back to at least one invariant (§7) or ADR (§9); the mapping is maintained in conformance/cli's fixture metadata, not left implicit.

31. Scalability Analysis

What stays constant: per-token scope-set operation cost, O(log k) for k scopes on a token, bounded by the depth cap (k ≤ 64, §4). What grows: token count and invocation count with program size. Expansion cost is O(n · d) where n = invocation count and d = average expansion depth (bounded by the 1,024/64 caps, §4, I4).

Named bottlenecks, in order: (1) pattern-matching backtracking on ambiguous follow sets (§15.7) — mitigated by memoization, not eliminated; (2) sandbox cold-start under parallel builds (§21.7) — mitigated by store pooling within the FD-budget ceiling; (3) resolver candidate-set collection when many macro-introduced bindings share a surface name (§19.7) — mitigated by a name-keyed index.

Horizontal scaling: compilation units are independent (P3 — expansion is a pure function of its own unit), so sharding across files/crates for parallel expansion is safe without coordination beyond the Phase 10 topological ordering pass. Vertical scaling: more cores help sandbox-pool parallelism up to the FD-budget ceiling (256 instances, §4); beyond that, additional cores go idle waiting on the bounded queue (ADR-28). Sharding/ partitioning: compile units partition by crate; cross-crate macro invocation always resolves through the resolver's module graph (§22), never by direct file access. Coordination overhead: the import-graph topological pass is O(crates + edges), not O( invocations) — cheap relative to expansion itself (§22.7).

Practical ceiling: the FD budget (4,096, §4) caps concurrent sandbox instances at 256; beyond that, ADR-28's bounded queue applies backpressure rather than growing unbounded. Levers beyond the ceiling: raise the FD ulimit; shard across multiple build-farm workers; disable procedural macros for a batch with --no-procmacro when only pattern-macro throughput matters.

32. Mental Models & First Principles

  • MM1 — An identifier's identity is (name, scope-set), not name alone. Predicts two lexically identical tokens can refer to different bindings. Bug class without it: naive text-substitution capture. Applies §8 (Domain Model), §17 (Phase 5).
  • MM2 — Hygiene is a construction property of expansion, not a post-hoc check. Predicts you cannot bolt hygiene onto an expander after the fact — it must thread through every substitution step. Bug class without it: teams that try to "add hygiene later" end up rewriting the expander from scratch. Applies §17, ADR-02 (§9).
  • MM3 — A macro system has (at least) two phases: pattern/definition-time and expansion-time, and confusing them is the C-preprocessor's original sin. Predicts any design sharing one evaluation context between "the macro body" and "the expanded code" reintroduces capture. Bug class: token-paste bugs. Applies §8, §15 (Phase 3).
  • MM4 — Expansion is a fixpoint computation, and every fixpoint needs a convergence argument. Predicts that without an explicit termination bound (I4), some legal- looking macro will hang the compiler. Bug class: unbounded recursive-macro DoS. Applies §18 (Phase 6), I4 (§7).
  • MM5 — A sandbox boundary is only as strong as its narrowest capability leak. Predicts one ambient capability (clock, env var) left enabled defeats the entire sandbox's determinism guarantee. Bug class: "deterministic except on Tuesdays" bugs. Applies §21 (Phase 9), T2/T8 (§24).
  • MM6 — The resolver, not the expander, owns meaning. Predicts that keeping scope sets out of the type checker/codegen keeps phase separation clean and lets multiple front ends share one resolver contract. Bug class: a type checker accidentally depending on macro-internal scope IDs. Applies §19 (Phase 7), I8 (§7).
  • MM7 — A differential oracle only proves what its corpus covers. Predicts passing 100% of a differential suite is necessary, not sufficient, for hygiene correctness. Bug class: false confidence from a narrow corpus. Applies §23 (Phase 11).
  • MM8 — Determinism is a build property, not a runtime property. Predicts a system can pass every test yet be non-reproducible across machines if any nondeterministic source (hash-iteration order, wall clock) leaks in. Bug class: works-in-CI, fails-in- release builds. Applies §18 (Phase 6), P9/I2 (§6/§7).

Racket's expander is the direct ancestor of this design's hygiene mechanism; the one decision it makes differently is running entirely trusted, unsandboxed compile-time code, which wins in its niche (a single-user REPL-driven language workbench where the "supply chain" is the user's own files). Scheme's syntax-case systems (Chez, Guile) made the opposite bet from Flatt — explicit renaming via wraps — which wins when an implementation must stay byte-compatible with decades of existing syntax-case macro libraries. Rust's actual production mechanism (SyntaxContext marks, not pure sets-of-scopes) wins when a compiler's resolver is already deeply coupled to the whole language's name resolution and retrofitting a fully separate scope-set model would be a multi-year rewrite — rustc chose incremental compatibility over architectural purity. Common Lisp's unhygienic defmacro wins when the language's entire value proposition is unrestricted code-as-data metaprogramming and the community has fifty years of gensym discipline baked into its macro-authoring culture — automated hygiene would change idioms (like deliberately capturing it in anaphoric macros, B2/Graham §5) that the community treats as a feature, not a bug.

34. Back-of-Envelope Capacity Model

  1. Max sandbox instances = FD budget ÷ FDs-per-store = 4,096 ÷ 16 = 256 — matches §4's concurrency ceiling exactly.
  2. Max sustained warm procedural-macro rate = 1 ÷ M7(p50) = 1 ÷ 200 µs = 5,000 invocations/sec/core; × 16 reference cores (§4) = 80,000/sec ceiling before the sandbox itself becomes the bottleneck.
  3. Expansion bookkeeping memory per macro-heavy unit ≈ tokens/invocation (empirically ~40) × invocations (iteration-cap-bounded, 1,024) × bytes/token (Token + ScopeSet overhead ≈ 64 B) = 40 × 1,024 × 64 ≈ 2.6 MB — negligible against the 2 GiB ceiling (§4), implying the ceiling is dominated by AST size, not expansion bookkeeping (HQ15, §35).
  4. Worst-case fixpoint wall-clock = iteration cap × per-iteration cost. Per-iteration cost ≈ M5(p50) ÷ 1,000-invocation batch = 200 ms ÷ 1,000 = 200 µs/invocation; 1,024 × 200 µs ≈ 205 ms worst-case bound per unit before the cap trips — consistent with the M5/M9 budgets (§30).
  5. 100,000-line corpus token estimate ≈ 12 tokens/line (Rust-like density) × 100,000 = 1.2 M tokens; at lexer throughput 200,000 tokens/sec (§4) → 6 s lex time, leaving ~9 s of the 15 s M9 p50 budget for parse + expand + resolve.
  6. Differential-Racket corpus runtime ≈ corpus size (~500 fixtures) × avg per-fixture time (~1.2 s incl. Racket process startup) ≈ 600 s ≈ 10 minutes — the exact ceiling asserted in §23.4/M9's Phase-11 gate.
  7. FD headroom check = 256 stores × 16 FDs = 4,096 = exactly the §4 ulimit ceiling, leaving zero headroom for the host process's own FDs; production configs reserve 512 FDs for the host, so the effective sandbox ceiling becomes (4,096 − 512) ÷ 16 = 224 (operationally tighter than the nominal 256, per §21/ADR-28).
  8. 30-day fuzz canary statistical basis ≈ 2,000 exec/sec (typical cargo-fuzz throughput for a mid-size grammar) × 86,400 s/day × 30 days ≈ 5.18 billion executions — the basis for treating "0 panics" as meaningful evidence rather than coincidence (T10, M12, §23.2).

36. Alternative Architectures (Roads Not Taken)

AA1 — Alpha-renaming hygiene (Kohlbecker 1986).

invocation --> [rename every macro-introduced identifier to a fresh gensym] --> output

Regime where it wins: minimal teaching interpreters where diagnostic quality is irrelevant and implementation simplicity dominates. Real system: early Scheme macro expanders, most textbook implementations (B1/Dybvig, §5). Why rejected here: surface names are lost from diagnostics and tooling at exactly the scale (§2) this project targets — a tmp_42 in an error message fails the "debuggable through 5 levels of nesting" bar of §2's mastery goals.

AA2 — Explicit-renaming / syntax-case (Dybvig, Hieb, Bruggeman 1992/1993).

tokens --> [wrap with rename/mark pairs] --> [compose wraps on nested expansion] --> output

Regime where it wins: an implementation needing exact syntax-case/syntax-rules compatibility for direct Scheme interop. Real system: Chez Scheme, Guile's psyntax (R3/R4, §5). Why rejected here: wrap composition is subtle and expensive to get right without the decades of production hardening Chez/Guile already have; set-of-scopes is the simpler, current-SOTA replacement Racket itself moved to.

AA3 — Unrestricted procedural-only macros (Common Lisp defmacro model).

invocation --> [arbitrary compile-time function, code as data] --> output (author-hygienic)

Regime where it wins: a Lisp-family language whose core value is code-as-data and full compile-time computation, where hygiene is the macro author's manual responsibility (gensym discipline, B2/B3 §5). Real system: Common Lisp (SBCL, CCL) (R6, §5). Why rejected here: loses hygiene-by-construction (P1) and pushes the correctness burden onto every macro author instead of the platform — exactly the failure mode this project's ADR- 02 is designed to eliminate.

AA4 — Text-substitution / preprocessor macros (C/C++ model).

source text --> [token-paste, no parsing yet] --> re-lex --> parse

Regime where it wins: extremely simple, language-agnostic conditional-compilation needs (feature flags, header guards) where macros never introduce bindings and hygiene is irrelevant. Real system: the C/C++ preprocessor (cpp). Why rejected here: cannot express binding-introducing macros safely at all — the entire hygiene problem this project solves does not exist for cpp because cpp lacks the expressive power to cause it, and therefore also lacks the power to solve real metaprogramming needs like swap! (§8.4).

38. Glossary

  • Alpha-renaming — the pre-1991 hygiene algorithm; rename every macro-introduced identifier to a fresh name (§36 AA1).
  • AllowedCaps — the sandbox capability manifest struct; all fields default false (§11, I11).
  • Ambiguous resolution — two or more equally-specific candidate bindings for one identifier use; a compile error, never a silent pick (I5, P10).
  • Bincode — the binary serialization format used across the sandbox TokenStream boundary (ADR-14).
  • Binding — a (name, scopes, kind, id) record the resolver matches identifier uses against (§11).
  • Capability manifest — the per-macro declaration of which sandbox capabilities (clock, network, random, …) it requires (P13, ADR-24).
  • Def-site (definition site) — the lexical position where a macro is defined; immutable across import/re-export (I6, P8).
  • Depth cap — the ceiling (64, §4) on macro-invocation nesting depth (I4).
  • Differential oracle — Racket's expander used as the correctness truth source (I12, ADR-10).
  • Ellipsis quantifier — the */+/? repetition operator in a pattern or template (§8.1 EBNF).
  • Expansion — replacing a MacroInvocation with its matched/substituted template (§16-17).
  • Fixpoint driver — the component iterating expansion until no invocations remain or a cap trips (§18, §11).
  • Fragment kind — a classifier for what a metavariable matches (expr, ident, pat, …, ADR-06).
  • Fresh scope — a ScopeId not previously allocated in the current compilation unit (I2).
  • Hermeticity — the property that identical (macro, input, seed) yields identical output across processes/machines (I7).
  • Hygiene — the property that macro-introduced identifiers never collide with caller identifiers of the same surface name (I1).
  • Identity (identifier) — the pair (surface name, scope set); two tokens are the same identifier iff both match (I1, MM1).
  • Intro scope — the scope attached to tokens from the macro's own definition during one expansion step (§8.3).
  • Invocation site — the source position where a macro is called.
  • Iteration cap — the ceiling (1,024, §4) on total fixpoint iterations per unit (I4).
  • MacroArm — one pattern => template rule inside a pattern macro's definition (§11).
  • MacroDef — the AST item representing a macro's definition, pattern or procedural (§11).
  • MacroInvocation — the AST node representing a macro call site, holding its unexpanded TokenStream (§11).
  • MacroTransformer — the shared trait pattern and procedural macros both implement (P2, §11).
  • Metavariable (metavar) — a pattern variable bound to part of the invocation's input ($x:expr).
  • Most-specific binding — among subset-matching candidates, the one with the largest scope set; the resolver's selection rule (§19.2).
  • Pattern macro — a macro defined by patterns and templates (declarative, §15-16).
  • Procedural macro — a macro defined by a sandboxed function mapping TokenStream to TokenStream (§21).
  • Re-export — exposing a macro defined in one module through another module's namespace, preserving def-site (§22, I6).
  • Resolver — the pass mapping identifier uses to bindings; the sole scope-set consumer (§19, I8).
  • Sandbox — the wasmtime-backed restricted execution environment for procedural macros (§21).
  • Scope set — the set of ScopeIds attached to a token, used for identity (§11).
  • Set-of-scopes — Flatt's 2016 hygiene algorithm; this project's locked choice (ADR-02).
  • Store pool — the bounded, reused set of wasmtime::Store instances behind the sandbox (§21.2, ADR-28).
  • Subset check — the resolver's test that a binding's scope set is a subset of a use's scope set (§19.2).
  • TokenStream — the input/output type of procedural macros and the raw payload of a MacroInvocation (§11).
  • Template — the right-hand side of a macro arm; substituted with bindings on match (§16).
