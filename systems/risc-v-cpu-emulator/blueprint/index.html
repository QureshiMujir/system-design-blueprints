Status: specification — locked

1. Goal & Scope

Engineering definition. A RISC-V CPU emulator is a virtual-platform runtime that decodes and executes RV64GC machine code with architecturally faithful semantics — general-purpose register file, privileged CSR file, Sv39 paged virtual memory, CLINT/PLIC interrupt delivery, and a minimal MMIO device set — sufficient to run user-mode ELF binaries and boot an unmodified Linux kernel to a shell, while guaranteeing deterministic, replayable, snapshot-restartable execution suitable for differential correctness validation against Spike and QEMU. It is a specification-grade software model of hardware, not a cycle-accurate simulator and not a JIT-first fast path in Phase 0.

Phase 0 deliverable — crates (workspace members, one crate = one deliverable):

  1. rvemu-isa — opcode/CSR metadata tables, encoding constants, immediate-field layouts.
  2. rvemu-decode — RV64GC + Zicsr/Zifencei instruction decoder, compressed (RVC) expansion.
  3. rvemu-core — hart state, register file, CSR engine, trap engine, execution/retirement loop.
  4. rvemu-memory — guest physical RAM, page allocator, dirty-page tracking, snapshot integration.
  5. rvemu-mmu — Sv39 page-table walker, TLB, PMP, translation-fault generation.
  6. rvemu-bus — address decode, MMIO dispatch, DMA arbitration, device registration.
  7. rvemu-devices — UART (16550-like), CLINT, PLIC, VirtIO-blk/net MMIO models.
  8. rvemu-loader — ELF64 parser, segment mapper, ABI/stack/argv/envp setup.
  9. rvemu-runtime — hart scheduler, timer wheel, trap router, replay coordinator, shutdown.
  10. rvemu-trace — structured logging, tracing spans, replay-event serialization, metrics.
  11. rvemu-cli — operator entry point: run/replay/snapshot/bench subcommands, config resolution.
  12. rvemu-gdb — GDB remote serial protocol server, breakpoints/watchpoints/single-step.
  13. rvemu-testkit — fixture harness, differential-execution driver, golden-trace comparator.
  14. rvemu-fuzz — cargo-fuzz targets for decoder, ELF loader, MMIO handlers.
  15. rvemu-bench — criterion benchmark suite (MIPS, TLB hit ratio, boot time, replay overhead).
  16. rvemu-conformance — riscv-tests / riscv-arch-test vector runner and report generator.

System boundaries — provides / delegates / does NOT provide.

Provides: RV64GC user- and supervisor-mode execution: Sv39 translation; CLINT/PLIC/UART/VirtIO device emulation; ELF loading; SBI shim sufficient for OpenSBI-free direct kernel boot; deterministic replay; snapshot/restore; GDB remote debugging; differential and fuzz test harnesses.

Delegates: kernel and root-filesystem images to upstream distributions (BusyBox/Alpine/Debian riscv64); machine-mode firmware semantics beyond the minimal SBI surface to a future OpenSBI integration; cryptographic key management for signed artifacts to the release pipeline (§27).

Does NOT provide: cycle-accurate timing, out-of-order/superscalar modeling, GPU emulation, FPGA bitstream generation, hardware-description-language output, full UEFI/ACPI firmware, PCIe bus enumeration, RISC-V vector-extension (RVV) execution in Phase 0, hardware power-management modeling, speculative-execution side-channel fidelity.

Non-goals (explicit, not merely deferred): binary-compatible replacement for real silicon; security research platform for microarchitectural side channels; a general-purpose x86/ARM emulator; a hypervisor product.

Deployment model. Standalone CLI binary (rvemu) on Linux x86_64/ARM64 hosts; embeddable library crate for CI harnesses; containerized execution (Docker/Podman-compatible image); a headless replay farm for regression triage. No GUI in Phase 0; no cloud-hosted control plane.

Target operators: emulator developers (ISA correctness, performance); OS/kernel developers (bring-up, low-level debugging via rvemu-gdb); security researchers (replay + tracing); systems students (modular reference implementation); CI operators (deterministic integration gating).

What later phases unlock: Phase 5 (§17) — supervisor mode and page-table isolation, prerequisite for any multi-process guest workload; Phase 6 (§18) — interrupt-driven device IO, prerequisite for timers and console; Phase 7 (§19) — Linux boot to shell, the system's headline milestone; Phase 8 (§20) — deterministic replay and snapshot, prerequisite for forensic debugging and CI bisection; Phase 9 (§21) — GDB attach and structured observability, prerequisite for kernel-level debugging.

Recommended language: Rust 1.80+. Rationale: memory safety without a GC pause on the hot decode path; sum-type (enum) modeling maps directly onto ISA instruction variants and CSR trap causes; ownership rules make the single-owner-per-state invariant (P3) mechanically checkable; mature fuzzing (cargo-fuzz/libFuzzer) and benchmarking (criterion) ecosystem; deterministic panic/abort semantics simplify crash-only recovery (P2); adequate FFI story for future QEMU/Spike differential linkage. Rejected: C++ — larger undefined-behavior surface makes replay determinism harder to guarantee under UB-triggering guest input; Go — GC pauses violate the p99 interrupt-injection budget (§4); Zig — ecosystem/tooling maturity (fuzzing, async, crates for postcard/zstd/blake3) insufficient in 2026; C — manual memory management raises the audited-unsafe surface (P11) beyond what a single-team project can review.

Required prerequisites: computer architecture and pipelining; virtual memory theory; operating systems (trap/interrupt handling, scheduling); ELF/ABI internals; RISC-V or comparable assembly; concurrency and lock-free queues; Linux internals; parsing and binary-format handling; debugging methodology and profiling; cryptographic hashing (for snapshot integrity); deterministic-systems design (WAL ordering, replay).

Estimated timeline. Phase 0 (§12, repository + decode skeleton): 6–14 weeks. Full blueprint (Phase 0 through Phase 9, §12–§21, Linux boot + replay + GDB + operational tooling): 8–14 months for a small team (2–4 engineers) working part-time-equivalent; a single engineer full-time tracks the upper end of that range.

2. Why Build This

Systems knowledge developed. ISA interpretation and instruction-set semantics; CPU privilege-mode transitions; trap and exception handling; memory-consistency reasoning at the single-hart level; binary decoding and bitfield extraction; virtual-memory translation (Sv39); deterministic runtime scheduling; state-machine architecture for a trap engine; emulator-grade observability; record/replay systems; fault containment; performance engineering under a hard MIPS budget.

Historical importance. RISC-V is the most consequential open ISA of the last decade — an open encoding with no royalty gate has let academic, embedded, and now datacenter-class silicon share one toolchain. Building a compliant emulator forces direct engagement with: instruction-encoding design trade-offs (fixed 32-bit + optional 16-bit compressed forms); the privileged-architecture split (M/S/U modes, delegable traps); device interaction over MMIO; the expectations a real OS kernel places on firmware (SBI) and platform (DTB); ABI compatibility (ELF64, RVABI); and the hardware/software boundary that every hypervisor and JIT ultimately has to model correctly.

Engineering muscles exercised. Low-level debugging without a debugger (until Phase 9, §21); binary compatibility across toolchain versions; deterministic execution under concurrency; interface design for a 16-crate workspace; stateful protocol handling (GDB remote serial protocol, VirtIO); concurrency reasoning for the scheduler/timer/trap interaction; resource budgeting (§4); failure recovery (crash-only, P2); reproducibility (bit-identical replay, I1/I2); performance tuning against a fixed interpreter-dispatch budget.

Production engineering concepts exercised. Backpressure (P4); structured logging and span-based tracing (P7); telemetry pipelines feeding external metrics; crash-only recovery (P2); snapshotting and restore; rolling upgrades under schema versioning (ADR-06/ADR-19); deterministic replay as a debugging artifact; fuzz-driven development (cargo-fuzz on decode/loader/MMIO); differential validation against Spike/QEMU; CI reproducibility (pinned toolchain, hash-stable artifacts).

Related systems domains. Compilers — instruction decoding mirrors frontend tokenization and IR lowering (§13 decode tables ≈ lexer tables). Kernels — trap handling and hart scheduling are the same state machine a kernel's own interrupt controller implements, just modeled from the outside. Databases — the replay WAL (§20) and snapshot mechanism mirror write-ahead-log storage engines almost exactly (Petrov, Database Internals, applied in §20). Hypervisors — M/S/U privilege transitions are a software model of what KVM/Xen do in hardware-assisted mode. Distributed systems — deterministic replay and monotonic event ordering share the same invariants as a replicated state machine's log (Raft/Paxos lineage) even though this system runs on one host.

Calibration value. Completing this project materially upgrades: runtime design; low-level debugging; performance analysis under a numeric budget; correctness validation methodology; interface stability practice; operational maturity. The competence transfers directly to kernels, VMMs, database storage engines, language runtimes, and networking stacks — anywhere a state machine must be both fast and provably deterministic.

What Mastery Looks Like

  • Can explain why x0 hard-wiring and PC-misalignment trapping are decode-time, not execute-time, concerns, and can point to the exact fixture that would catch a regression — Phase 1 (§13).
  • Can trace a page fault from TLB miss through page-table walk to trap-vector dispatch without consulting the spec, and can name which invariant (I7) it would violate if skipped — Phase 5 (§17).
  • Can design a wire format for a replay event that is both forward-compatible and byte-stable enough for a blake3 snapshot hash to be meaningful — Phase 8 (§20).
  • Can reason about why a single global lock-ordering hierarchy (I5) is required the moment CLINT timers and PLIC interrupts share a hart, and can name the deadlock it prevents — Phase 6 (§18).
  • Can differentiate a decoder bug from an interpreter bug from an MMU bug purely from a Spike differential trace, without re-running under a debugger — Phase 2 (§14), Phase 5 (§17).
  • Can justify, with a concrete regime, why crash-only recovery (P2) beats partial-rollback recovery for a hart in an undefined CSR state — Phase 0 (§12), Phase 9 (§21).
  • Can size a replay buffer and a snapshot cadence from a measured WAL write-amplification number rather than a guess — Phase 8 (§20), §32.
  • Can explain, to a kernel developer attaching via GDB, exactly which subsystem owns breakpoint re-entry and why watchpoints cannot be implemented as plain memory-access traps — Phase 9 (§21).

rvemu-cli — sole operator boundary; parses config/argv (least-trusted input alongside guest binaries), wires topology, drives replay/snapshot/bench subcommands. No ISA semantics live here; it stays stateless apart from resolved configuration, so it can be re-invoked idempotently in CI.

rvemu-runtime — the concurrency boundary. Owns hart scheduling, CLINT-driven timer dispatch, trap routing, cooperative cancellation, and replay orchestration; defines the global lock-ordering hierarchy (I5) that every other subsystem must respect when it needs cross-hart or cross-device state.

rvemu-core (with rvemu-decode/rvemu-isa) — the execution kernel. Owns register file, CSR file, privilege-mode state, trap generation, decode dispatch, and monotonic retirement accounting (I1). This is the only subsystem allowed to mutate architectural state directly.

rvemu-mmu — owns every guest-visible address-translation invariant: Sv39 walk, TLB, PMP checks, translation-fault generation. A translation crossing this boundary without a validated PTE is a correctness bug, not a performance one (I7).

rvemu-devices — virtual peripherals (UART/CLINT/PLIC/VirtIO). Devices talk to each other and to RAM only through rvemu-bus; direct device-to-device or device-to-RAM coupling is the isolation invariant (I10) this subsystem exists to enforce.

rvemu-trace — the persistence boundary. Every subsystem's structured logs, spans, metrics, and replay events flow through here before they leave the process; nothing bypasses it for telemetry (P7).

rvemu-bus — the protocol boundary between the CPU-side subsystems and memory/devices: address decode, MMIO dispatch, DMA arbitration, device registration. Prevents any subsystem from addressing physical memory except through a validated region lookup.

rvemu-memory — the trust boundary around guest RAM: allocation, dirty-page tracking for snapshotting, and access instrumentation. Guest-controlled addresses are validated here before any host-memory touch.

rvemu-loader — the external-IO boundary for guest images: ELF64 parsing, segment mapping, ABI/stack construction. It is the last place untrusted binary input is validated before it becomes executable guest state.

rvemu-gdb and the rvemu-testkit/rvemu-fuzz/rvemu-bench/rvemu-conformance cluster are external interfaces: a GDB remote-serial-protocol socket into the trap router, and a family of harnesses driving the runtime from outside without becoming part of its concurrency boundary.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every observable execution path must be byte-for-byte replayable from its WAL. Tradeoff: forbids any wall-clock or thread-scheduler-order dependence in guest-visible state. Operational: replay traces become the authoritative forensic artifact for every incident. Violated: differential testing against Spike becomes statistically noisy and bug reports stop reproducing.
  • P2 — Crash-Only Recovery. Rule: a faulted subsystem restarts from its last valid snapshot rather than attempting partial-mutation rollback. Tradeoff: loses in-flight work since the last checkpoint. Operational: recovery code path is identical to cold-start code path, halving the tested surface. Violated: ad hoc rollback logic accumulates untested corners and silently corrupts state (I6).
  • P3 — Explicit Ownership. Rule: every piece of runtime state has exactly one owning subsystem. Tradeoff: cross-subsystem reads require an explicit handle, never a shared mutable reference. Operational: makes I5's lock-ordering hierarchy mechanically auditable. Violated: race conditions and stale references appear the moment two subsystems believe they own the same CSR or page.
  • P4 — Backpressure Everywhere. Rule: no queue (trace, replay, MMIO) may grow unbounded. Tradeoff: producers must block or drop under sustained overload instead of buffering forever. Operational: bounds tail latency and memory footprint under fault-injection load (§26). Violated: telemetry queue growth silently exhausts the §4 memory budget until the process OOMs.
  • P5 — Replayability First. Rule: every state mutation is captured before it is applied. Tradeoff: adds a serialization step to the hot retirement path. Operational: enables bisection of a Linux-boot regression to the exact divergent instruction. Violated: a replay gap turns every hard bug into an unreproducible one.
  • P6 — Stable Wire Compatibility. Rule: replay-event and snapshot schemas carry an explicit version field and only grow by additive fields. Tradeoff: dead fields must be retained, not deleted, across a major version. Operational: lets a CI replay farm mix binaries built days apart. Violated: an old snapshot silently misparses under a newer binary and corrupts hart state on restore.
  • P7 — Observability By Default. Rule: every subsystem emits metrics, spans, and structured logs through rvemu-trace — no ad hoc eprintln!. Tradeoff: instrumentation overhead is paid on every hot path, not opt-in. Operational: a boot failure is diagnosable from the trace bundle alone. Violated: postmortems degrade into printf-driven guesswork under time pressure.
  • P8 — Bounded Resource Usage. Rule: every buffer, queue, and cache declares an explicit upper bound in §4. Tradeoff: some workloads see early backpressure rather than graceful degradation. Operational: makes capacity planning (§32) arithmetic rather than empirical guesswork. Violated: an unbounded TLB or trace buffer becomes the failure mode under a malicious or pathological guest.
  • P9 — Fail Closed. Rule: malformed guest or host state terminates hart execution rather than attempting a best-effort continuation. Tradeoff: a single corrupted CSR halts a hart that might otherwise have limped along. Operational: prevents corrupted state from propagating into a snapshot. Violated: undefined-behavior propagation makes every downstream trace suspect.
  • P10 — Compatibility Before Optimization. Rule: interpreter correctness (Phase 2, §14) is locked and conformance-gated before any JIT work begins. Tradeoff: leaves MIPS on the table for months. Operational: gives every later optimization a trustworthy correctness oracle to diff against. Violated: a fast-but-wrong emulator produces confidently incorrect kernel-boot traces.
  • P11 — Minimal Unsafe Rust. Rule: every unsafe block carries a documented invariant comment and fuzz coverage before merge. Tradeoff: slows down low-level memory-model code that would be one line in C. Operational: keeps the audited-unsafe surface small enough for one reviewer to hold in their head. Violated: an unreviewed unsafe block becomes the emulator's own memory-safety bug, defeating the entire rationale for choosing Rust (§1).
  • P12 — Isolation Between Devices. Rule: devices communicate only through rvemu-bus, never directly with each other or with rvemu-memory. Tradeoff: every device interaction pays a routing indirection. Operational: lets a single device be fuzzed or reset without modeling its neighbors. Violated: a UART-to-PLIC direct coupling becomes an unauditable, untestable side channel (I10).
  • P13 — Single Source of Truth. Rule: decoded ISA metadata is generated from one authoritative opcode table in rvemu-isa, never hand-duplicated per instruction handler. Tradeoff: adds a codegen step to the build (§27). Operational: an encoding fix in one place fixes decode, disassembly, and conformance reporting simultaneously. Violated: decode-table drift (a documented Phase 1 pitfall, §13.6) reintroduces the exact bug class code generation exists to prevent.
  • P14 — Structured Errors Only. Rule: no subsystem propagates a bare String as an error type; all faults are typed enums with a stable discriminant. Tradeoff: more boilerplate per error site. Operational: lets rvemu-trace attach machine-parseable fault codes to every span. Violated: stringly-typed errors make automated incident triage in the replay farm impossible.
  • P15 — Operational Transparency. Rule: every fatal failure emits a crash snapshot, an execution trace, and a telemetry bundle before the process exits. Tradeoff: fatal-path code must stay allocation-safe enough to run during an unwind. Operational: converts every crash into a self-contained bug report. Violated: a bare panic with no artifact turns a reproducible crash into an unreproducible one the moment the terminal scrolls.

7. System Invariants

# Invariant Why Enforced At Detection Telemetry Recovery
I1 Instruction retirement counters are strictly monotonic per hart. Retirement count is the replay-alignment key (P5). rvemu-core execution loop, post-retire increment. Runtime assertion + replay-divergence comparator. hart.retired_total counter. Terminate hart, dump state (FM-4).
I2 CSR side effects apply in a fixed, deterministic sub-order within one instruction. Non-deterministic CSR order breaks bit-identical replay (P1). rvemu-core CSR-commit stage. Differential trace vs. Spike (§26). csr.mutation_order_violation counter. Fail-closed hart termination (P9).
I3 A replay WAL record commits before its device-visible side effect becomes observable. Otherwise a crash between the two leaves an unreplayable gap (P5). rvemu-trace WAL writer, ahead of rvemu-bus dispatch. Sequence-gap check on WAL read. wal.commit_lag_ns histogram. Replay rollback to last committed sequence (FM-5).
I4 Trap-context mutation (cause/tval/epc/mode) is all-or-nothing. Partial trap state is unrecoverable and unreplayable (P9). rvemu-core trap-entry routine. Post-trap invariant assertion. trap.partial_commit counter (should be 0). Terminate hart.
I5 Global lock order is runtime → scheduler → hart → device → trace; no subsystem acquires out of order. Prevents deadlock the moment CLINT and PLIC share a hart (P3). Compile-time lock-type wrappers + runtime debug-assert. Deadlock watchdog timeout (FM-6). lock.order_violation counter. Process abort with lock-order dump.
I6 A snapshot only captures globally quiesced state (all harts paused, no in-flight MMIO). Otherwise restore resumes mid-transaction (P2). rvemu-runtime snapshot controller quiesce barrier. Snapshot checksum + quiesce-flag assertion. snapshot.quiesce_wait_ms histogram. Reject snapshot, retry quiesce.
I7 An invalid PTE never produces a host-memory access. The MMU is the sole guest-visible translation authority (§3). rvemu-mmu page-table walker, pre-access validation. Fault-injection fixture fixtures/mmu/invalid_pte.bin. mmu.invalid_pte_blocked counter. Raise page fault, enter trap handler.
I8 TLB invalidation (sfence.vma) semantics are globally consistent across all harts sharing an ASID. Stale TLB entries cause silent wrong-answer execution, not a crash. rvemu-mmu TLB shootdown path. Differential trace vs. Spike on sfence.vma fixtures. tlb.shootdown_latency_ns histogram. Full TLB flush + re-walk.
I9 Trace-event timestamps are monotonic per hart. Non-monotonic spans break causal ordering in postmortem analysis (P7). rvemu-trace span emitter. Ingest-time monotonicity check. trace.non_monotonic_span counter. Drop and re-timestamp at ingest.
I10 A device mutates only memory regions it is registered to own via rvemu-bus. Direct cross-device coupling is unauditable (P12). rvemu-bus MMIO dispatch, region-ownership check. Bus-violation assertion. bus.unauthorized_write counter. Reject write, raise access fault.
I11 Register x0 always reads as zero regardless of any write. Hard-wired by the ISA; silent violation corrupts every downstream computation. rvemu-core register-write path (write-to-x0 is a no-op). Conformance fixture fixtures/core/x0_write.bin. core.x0_write_attempt counter. N/A — enforced structurally, no recovery needed.
I12 A misaligned instruction fetch always traps; it never silently proceeds. Guest ABI assumes IALIGN=32 (or 16 with C); silent tolerance masks real bugs. rvemu-core fetch stage, pre-decode alignment check. Conformance fixture fixtures/core/pc_misalign.bin. core.misaligned_fetch_trap counter. Raise instruction-address-misaligned exception.

Debugging methodology: the runtime is built as a deterministic simulator with one runtime assertion per invariant — each row above compiles to exactly one debug_assert!-class check plus one production-mode counter, so a violation is caught in CI (debug build, panics) and surfaced in production (release build, counter + telemetry) without divergent code paths between the two.

8. Domain Model — Hart, Trap & Replay Protocol

Hart State Model (owned exclusively by rvemu-core, per P3):

HartState
  regs               : [u64; 32]        (x0 hardwired zero, I11)
  pc                 : u64
  csr                : CsrFile
  privilege          : PrivilegeMode    (U | S | M)
  pending_interrupts : InterruptBitmap
  trap_state         : TrapState
  mmu_ctx            : MmuContext
  retired            : u64               (monotonic, I1)

Privilege modes:

Mode Encoding Description
U 0b00 User — unprivileged application execution.
S 0b01 Supervisor — kernel-mode execution under Sv39 translation.
M 0b11 Machine — highest privilege, owns SBI shim and boot ROM.

Trap flow (synchronous exception or asynchronous interrupt, both funnel through the same path, enforcing I4):

Instruction Execute
    |
    +--> exception or pending interrupt taken?
            |
            +--> save {cause, tval, epc, previous_mode}   (I4: atomic)
            +--> apply delegation (medeleg/sedeleg)
            +--> update CSRs (deterministic sub-order, I2)
            +--> switch privilege mode
            +--> jump to trap vector (mtvec/stvec)

Sv39 translation walk (three-level, enforced by rvemu-mmu, I7/I8):

VA[38:0] --VPN[2]--> PTE (level 2) --VPN[1]--> PTE (level 1) --VPN[0]--> PTE (level 0) --> PA

ReplayEvent

  sequence_id       : u64            (WAL ordering key, I3)
  hart_id           : u8
  instruction_pc    : u64
  opcode            : u32

  memory_deltas     : Vec<MemDelta>
  csr_deltas        : Vec<CsrDelta>
  interrupt_state   : InterruptBitmap
  timestamp_ns      : u64            (monotonic per hart, I9)

MmioRequest
  address     : u64
  width       : AccessWidth  (Byte | Half | Word | Double)
  operation   : MmioOp       (Read | Write)

parse ELF64 header
  -> validate machine=EM_RISCV, class=ELFCLASS64
  -> map PT_LOAD segments (permission-checked, I7-adjacent MMU setup)
  -> initialize user stack (argv/envp per RVABI)
  -> set entry PC
  -> hand off to rvemu-core execution loop

TLB miss
  -> walk page table
  -> invalid leaf PTE encountered
  -> raise page fault (synchronous exception)
  -> enter trap handler (per trap-flow diagram above)
  -> emit fault telemetry (mmu.invalid_pte_blocked, I7)

11. Core Schema & Types

Every load-bearing type below is a signature only (no method bodies), annotated for ownership, mutation, concurrency, persistence, serialization, and compatibility — the six axes every type in this system must resolve before it is allowed to cross a subsystem boundary (§3).

struct HartState
  regs               : [u64; 32]
  pc                 : u64
  csr                : CsrFile
  privilege          : PrivilegeMode
  pending_interrupts : InterruptBitmap
  trap_state         : TrapState
  mmu_ctx            : MmuContext
  retired            : u64

Ownership: rvemu-core, exactly one instance per hart (P3, I1). Mutation: exclusive in-process, no aliased mutable references. Concurrency: not shared across harts; cross-hart inspection only via immutable clone. Persistence: snapshot-serializable, part of SnapshotHeader payload. Serialization: postcard (ADR-05). Compatibility: additive-only fields under schema_version (P6).

struct CsrFile
  machine_csrs    : SparseMap<CsrAddr, u64>
  supervisor_csrs : SparseMap<CsrAddr, u64>
  timer_csrs      : SparseMap<CsrAddr, u64>

Ownership: rvemu-core, embedded in HartState. Mutation: through the CSR-commit stage only, in the fixed sub-order enforced by I2. Concurrency: single-owner, no shared access. Persistence: included in every snapshot. Serialization: postcard. Compatibility: unknown CSR addresses at deserialize time are preserved verbatim, never dropped (forward compatibility, P6).

struct TrapState
  cause          : TrapCause
  tval           : u64
  epc            : u64
  previous_mode  : PrivilegeMode

Ownership: rvemu-core. Mutation: all-or-nothing per I4; no partial-field writes escape the trap-entry routine. Concurrency: single-owner. Persistence: snapshot-included. Serialization: postcard. Compatibility: TrapCause is a closed enum versioned alongside the ISA decode table (P13).

struct MmuContext
  satp        : u64
  tlb         : TlbTable
  pmp_entries : [PmpEntry; 16]

Ownership: rvemu-mmu, referenced (not owned) by HartState. Mutation: TLB entries mutated only via the shootdown path (I8). Concurrency: single-owner per hart; cross-hart ASID invalidation coordinated through rvemu-runtime's lock order (I5). Persistence: TLB is not snapshotted (rebuilt on restore); satp/PMP are. Serialization: postcard for the persisted subset. Compatibility: PMP entry count is fixed at 16 for the life of the major schema version.

enum PrivilegeMode { U, S, M }

Ownership: rvemu-core. Mutation: only via the trap-flow state machine (§8). Concurrency: copy type, no aliasing concerns. Persistence: snapshot-included. Serialization: postcard, one byte. Compatibility: closed set — RISC-V defines no fifth mode; safe to never version.

struct ReplayEvent
  schema_version  : u16
  sequence_id     : u64
  hart_id         : u8
  instruction_pc  : u64
  opcode          : u32
  register_deltas : Vec<RegDelta>
  memory_deltas   : Vec<MemDelta>
  csr_deltas      : Vec<CsrDelta>
  interrupt_state : InterruptBitmap
  timestamp_ns    : u64

Ownership: rvemu-trace, produced by rvemu-core/rvemu-mmu/rvemu-devices at the point of mutation. Mutation: immutable once constructed (append-only WAL, I3). Concurrency: single-writer per hart, funnel merge at the trace pipeline. Persistence: the WAL itself. Serialization: postcard + zstd (ADR-05/06). Compatibility: additive-only fields; schema_version gates parser behavior (P6).

struct MemoryRegion
  base        : u64
  size        : u64
  permissions : AccessPerm
  backing     : BackingKind

Ownership: rvemu-memory, registered with rvemu-bus at boot. Mutation: immutable after registration; region table changes require a bus-registry transaction. Concurrency: read-shared, single-writer at registration time. Persistence: region table is part of the snapshot header. Serialization: postcard. Compatibility: BackingKind is a closed enum (RAM | MMIO | Reserved).

trait MmioDevice
  fn read(addr: u64, width: AccessWidth) -> Result<u64, BusFault>;
  fn write(addr: u64, width: AccessWidth, value: u64) -> Result<(), BusFault>;
  fn reset() -> Result<(), BusFault>;

Ownership: implemented once per device crate module (uart.rs, clint.rs, plic.rs, virtio_blk.rs), owned by rvemu-devices. Mutation: only through this trait, never direct field access (P12). Concurrency: single-owner per device instance; cross-device interaction forbidden by I10. Persistence: device-internal state opts into snapshotting via a companion Snapshot impl. Serialization: device-defined, postcard-compatible. Compatibility: adding a method is a breaking change to this trait — versioned as MmioDeviceV2 if ever required.

struct TranslationResult
  physical_addr : u64
  access_perm   : AccessPerm
  cacheable     : bool

Ownership: rvemu-mmu, returned by value, never stored. Mutation: immutable (value type). Concurrency: no shared state. Persistence: not persisted — recomputed on every access. Serialization: not serialized. Compatibility: internal type, no wire contract.

struct SchedulerHandle
  hart_wakeups     : BoundedChannel<HartId>
  timer_deadlines  : TimerWheel
  cancel_token     : CancelToken

Ownership: rvemu-runtime. Mutation: through channel send/recv only (P4 backpressure). Concurrency: multi-producer (devices raise wakeups), single-consumer (scheduler loop) — respects lock order I5. Persistence: not persisted; rebuilt from HartState + pending-interrupt bitmaps on restore. Serialization: not serialized. Compatibility: internal runtime type.

struct SnapshotHeader
  magic           : [u8; 4]
  schema_version  : u16
  hart_count      : u8
  content_hash    : [u8; 32]

Ownership: rvemu-trace (snapshot writer). Mutation: write-once per snapshot file. Concurrency: produced under the global quiesce barrier (I6). Persistence: this is the persistence contract. Serialization: postcard, fixed-layout header followed by the variable body. Compatibility: magic + schema_version are validated before any body byte is trusted (P6, P9).

struct DecodedInstruction
  opcode_class : OpcodeClass
  rd, rs1, rs2 : RegIndex
  imm          : i64
  mnemonic     : &'static str

Ownership: rvemu-decode, produced per fetch, consumed by rvemu-core. Mutation: immutable once decoded. Concurrency: value type, no shared state. Persistence: not persisted directly; contributes to ReplayEvent.opcode. Serialization: not independently serialized. Compatibility: OpcodeClass is generated from the single authoritative opcode table (P13); adding an extension adds enum variants, never renumbers existing ones.

13. Phase 1 — ISA Definitions and Decode Engine

13.1 Objectives

  • Implement the canonical RV64GC opcode/CSR metadata tables (rvemu-isa) as the single source of truth (P13).
  • Build the decode engine (rvemu-decode) covering RV64I/M/A/F/D + Zicsr/Zifencei + compressed (RVC).
  • Guarantee deterministic instruction parsing: identical bytes always decode to an identical DecodedInstruction (§11).

13.2 Detailed Implementation Steps

  • Define the opcode metadata schema in opcode_table.rs: one row per instruction, generated per P13, following rv8's data-table-driven strategy rather than Spike's switch-based dispatch (§5 Reference Implementations).
  • Generate decode tables at build time from the authoritative schema; wire csr_table.rs from the RISC-V Privileged Architecture Specification sec. 3–4 (§5).
  • Implement instruction-format extraction in bitfield.rs: R/I/S/B/U/J formats plus the compressed formats (CR/CI/CSS/CIW/CL/CS/CA/CB/CJ) in compressed.rs.
  • Implement illegal-instruction detection as a first-class decode outcome, enforcing I12's alignment check upstream of decode.
  • Add the decode fuzzing target decode_target.rs (cargo-fuzz, ADR-15) seeded from the riscv-tests corpus.
  • Add a decode-only benchmark validating the > 200 MIPS decode-throughput budget (§4) independent of the interpreter.
  • Instrument decode with malformed-opcode telemetry keyed by opcode class (sinks wired fully once §20 lands).

13.3 Deliverable

A standalone rvemu-decode crate turning a u32/u16 fetch word into a DecodedInstruction (§11) for the full RV64GC + compressed encoding space, with zero heap allocation on the decode path.

13.4 Acceptance Criteria

  • Passes all official RISC-V decode vectors from riscv-tests (100% of the RV64GC subset, ~1,200 vectors).
  • Zero panics across 24 CPU-hours of decode_target.rs fuzzing.
  • Decode throughput > 200 MIPS on the criterion decode benchmark (§4).
  • Illegal-instruction detection: 100% on the decode_illegal.bin corpus, zero false accepts.

13.5 Conformance Fixtures

  • fixtures/decode/rv64i_base.bin — canonical RV64I vectors; expected: exact DecodedInstruction match.
  • fixtures/decode/compressed_rvc.bin — RVC vectors; expected: correct expansion to base-format equivalent.
  • fixtures/decode/malformed_opcode.bin — deliberately invalid encodings; expected: IllegalInstruction outcome, never a panic.
  • fixtures/decode/replay_decode_trace.bin — regression case pinning a previously fixed sign-extension bug.

13.6 Pitfalls

  • Bitfield sign errors. Manifestation: wrong result on negative immediates. Root cause: incorrect sign extension in immediate assembly. Debugging method: differential-compare against Spike's insns/ reference. Signal: rv64i_base fixture mismatch on B/S-type instructions. Recovery: fix the extension mask, re-run the full vector suite.
  • Decode-table drift. Manifestation: two opcode entries silently disagree after a manual edit. Root cause: hand-duplicated opcode row bypassing the P13 single-source generator. Debugging method: diff the generated table against a schema checksum. Signal: codegen checksum mismatch in CI. Recovery: regenerate from schema; forbid direct edits to generated files.
  • Compressed-instruction ambiguity. Manifestation: one RVC opcode maps to two different base instructions depending on an ignored field. Root cause: incomplete CR/CI disambiguation. Debugging method: cross-check against the Unprivileged ISA sec. 16 compressed table. Signal: compressed_rvc fixture divergence. Recovery: add the missing discriminant field.

13.7 Performance Concerns

  • Branch misprediction on opcode-class dispatch: keep the primary dispatch table cache-line-aligned and sized to fit L1 for the hot RV64I subset.
  • Table locality: co-locate opcode metadata and the CSR address map to avoid cross-cache-line lookups.
  • Allocation-free decode path is mandatory — any allocation inside decoder.rs breaks the 200 MIPS budget at realistic instruction mixes.

13.8 Edge Cases

  • An all-zero 32-bit word must decode as illegal, not as a valid-looking encoding.
  • Partially valid compressed instructions crossing a page boundary — decode must not assume 4-byte alignment; fetch-side handling belongs to §15/§17.
  • Reserved/unallocated opcode-space encodings map to IllegalInstruction, distinct from Unimplemented.

13.9 Failure Analysis

A malformed-decode path emits opcode bytes, PC, hart ID, and a decode-stage trace ID sufficient to reconstruct the fault without re-running the guest. Blast radius is contained to the single fetch: a decode failure raises IllegalInstruction, entering the standard trap flow (§8) rather than corrupting any architectural state.

13.10 Operational Notes

Metrics: decode.failures_total, decode.instruction_category_histogram, decode.compressed_ratio. Tracing spans: decode.fetch_decode (sampled 1:1000 in production, P4). Structured-log fields: opcode_hex, pc, hart_id, decode_outcome. Deployment: decode tables compile into the binary — a table fix ships as a new binary, no runtime migration path exists. PhaseDeferred("§13") marks RV64V vector-extension decode as out of scope for this phase, registered in §35.

14. Phase 2 — Core Interpreter Runtime

14.1 Objectives

  • Execute the full RV64I/M/A/F/D instruction set through rvemu-core's execution loop.
  • Implement register-file, arithmetic, branch, and memory-op semantics with retirement accounting (I1).
  • Implement synchronous trap propagation for illegal instructions and misaligned access (I12).

14.2 Detailed Implementation Steps

  • Build the execution loop in execute.rs: fetch (via rvemu-decode) → dispatch → commit, as a data-driven table keyed by OpcodeClass (P13), deliberately avoiding QEMU's TCG code generation per Bellard (2005) — interpreter-first per P10.
  • Implement arithmetic/branch/memory-op handlers in hart.rs; enforce x0 hardwiring (I11) at the single register-write chokepoint.
  • Implement CSR read/write semantics in csr.rs with the deterministic sub-order commit stage required by I2.
  • Implement trap generation in trap.rs, funneling every synchronous exception through the atomic trap-entry routine (I4).
  • Add retirement counters in retire.rs, strictly monotonic per I1, feeding the future ReplayEvent.sequence_id (§11) once §20 lands.
  • Add execution-tracing hooks and instruction-histogram telemetry, wired to real sinks once rvemu-trace exists.
  • Add deterministic scheduling hooks: the loop yields at a fixed retirement-count granularity, the seam rvemu-runtime's scheduler (§18) later drives.

14.3 Deliverable

A runnable single-hart interpreter executing RV64I/M/A/F/D user-mode binaries end to end, with retirement counters and a differential-testing hook against Spike.

14.4 Acceptance Criteria

  • Passes 100% of the rv64ui-*/rv64um-* riscv-tests suites.
  • Zero divergence against Spike across a 10-million-instruction differential run (rvemu-testkit).
  • Interpreter throughput within the 25–80 MIPS budget (§4) on the criterion interpreter benchmark.
  • No undefined architectural-state transition across the full riscv-tests corpus.

14.5 Conformance Fixtures

  • fixtures/core/rv64ui_add.bin — base arithmetic; expected: bit-identical register file vs. Spike.
  • fixtures/core/rv64ui_branch.bin — branch/jump semantics; expected: correct PC sequence.
  • fixtures/core/rv64ui_loadstore.bin — memory ops; expected: correct byte/half/word/double semantics.
  • fixtures/core/x0_write.bin — I11 regression case; expected: x0 reads zero after any write.
  • fixtures/core/pc_misalign.bin — I12 regression case; expected: InstructionAddressMisaligned trap.

14.6 Pitfalls

  • x0 mutation. Manifestation: silently corrupted downstream computation. Root cause: a handler writes regs[0] directly instead of through the write chokepoint. Debugging method: x0_write.bin plus a runtime assertion on every register write. Signal: assertion fires in debug build. Recovery: route all writes through one function (I11).
  • PC misalignment tolerated. Manifestation: the guest continues from a misaligned address instead of trapping. Root cause: missing alignment check before fetch dispatch. Debugging method: pc_misalign.bin. Signal: conformance fixture failure. Recovery: enforce I12 at the fetch chokepoint.
  • Overflow-semantics mismatch. Manifestation: differential divergence from Spike on signed overflow. Root cause: two's-complement wraparound at the wrong operand width. Debugging method: differential trace isolates the exact instruction. Signal: rvemu-testkit divergence report. Recovery: fix the operand-width mask, re-run rv64um-*.

14.7 Performance Concerns

  • Dispatch overhead dominates at the 25 MIPS floor: keep the dispatch table a flat jump table, not a comparison chain.
  • Indirect-branch mispredict penalty from the dispatch table — keep it small enough to stay resident in L1 BTB for the hot RV64I subset.
  • Register aliasing: avoid host-side reference aliasing between rs1/rs2/rd that forces redundant reloads.

14.8 Edge Cases

  • Signed-overflow arithmetic (ADDW/SUBW 32-bit sign extension into 64-bit registers).
  • Misaligned load/store where the host tolerates unaligned access but guest semantics require a trap.
  • Infinite-loop guest programs: the scheduling yield point must still fire, bounded by a max-retirement watchdog fixture.
  • Division-by-zero and signed-division overflow: RISC-V defines non-trapping results (all-ones / most-negative), not a trap — a common porting mistake.

14.9 Failure Analysis

Execution divergence dumps full architectural state (registers, CSRs, PC, privilege mode) and compares the retirement-indexed trace against Spike's reference trace to isolate the first diverging instruction. Blast radius: confined to the diverging hart; other harts (once §17/§18 introduce them) are unaffected because state is single-owned per hart (P3).

14.10 Operational Notes

Metrics: core.ipc_estimate, core.retired_total, core.branch_frequency, core.trap_rate. Tracing spans: core.execute_instruction (sampled). Structured-log fields: pc, opcode_class, retired, privilege_mode. Deployment: interpreter correctness is gated by rvemu-conformance before merge; rollback is a binary revert — no persistent state exists yet to migrate. PhaseDeferred("§14") marks a binary-translation JIT backend as out of scope for this phase (P10: correctness before optimization), registered in §35.

15. Phase 3 — Memory Subsystem and Bus

15.1 Objectives

  • Build the guest physical RAM model (rvemu-memory) with page-granular allocation and dirty tracking.
  • Implement MMIO routing and address-space isolation via rvemu-bus (I10).
  • Enforce region-ownership validation ahead of any host-memory touch.

15.2 Detailed Implementation Steps

  • Implement the page allocator (page_alloc.rs) over an mmap-backed guest-RAM region (ADR-04), sized per the §4 per-1-GB-guest metadata budget.
  • Add dirty-page tracking in dirty_tracking.rs via mprotect-based write protection, feeding the future snapshot dirty-bitmap (§20), bounded at the §4 memory ceiling.
  • Implement aligned-access helpers (ram.rs) enforcing width-correct access with permission validation ahead of every touch.
  • Implement the bus registry (address_decoder.rs, mmio_router.rs): every MemoryRegion (§11) is registered once at boot with no runtime re-registration, enforcing P12 at the routing layer.
  • Add DMA abstraction (dma.rs) as a bus-arbitrated path, not a direct device-to-RAM shortcut, so future VirtIO work (§18) cannot bypass I10.
  • Implement memory-access tracing and allocation-pressure metrics (sinks wired once rvemu-trace lands, §20).
  • Implement access-fault propagation: an out-of-range or permission-violating access raises a bus fault through the same trap-flow chokepoint as a decode-time illegal instruction (§13), keeping fault handling single-sourced.

15.3 Deliverable

A working guest-RAM subsystem plus MMIO routing layer: any guest physical address resolves deterministically to a RAM range or a registered device, with no unmapped gaps silently returning zero.

15.4 Acceptance Criteria

  • Address-decode correctness across 100% of registered regions in mmio_overlap.json's topology.
  • Zero overlapping regions accepted at registration time (hard rejection, not a runtime check).
  • Faults generated deterministically: 100% reproducibility across repeated ram_alignment.bin runs.
  • Dirty-bitmap growth stays within the §4-adjacent ceiling under the stress fixture.

15.5 Conformance Fixtures

  • fixtures/memory/ram_alignment.bin — width-correct access matrix; expected: correct trap on misalignment where required.
  • fixtures/memory/mmio_overlap.json — deliberately overlapping topology; expected: registration-time rejection.
  • fixtures/memory/dirty_bitmap_stress.bin — sustained write pattern; regression case for unbounded dirty-tracking growth.
  • fixtures/memory/out_of_range_access.bin — access beyond the mapped range; expected: deterministic bus fault.

15.6 Pitfalls

  • Region overlap. Manifestation: undefined device-routing behavior. Root cause: registration-time validation gap. Debugging method: dump the region table, check pairwise interval overlap. Signal: mmio_overlap.json failure. Recovery: reject overlapping registration at boot (I10).
  • Unbounded dirty tracking. Manifestation: snapshot serialization time grows unboundedly. Root cause: the dirty bitmap is never compacted between snapshot cycles. Debugging method: dirty_bitmap_stress.bin plus allocation-pressure trend. Signal: memory.dirty_page_growth exceeding budget. Recovery: compact the bitmap on every successful snapshot commit (P8).
  • Torn partial write. Manifestation: a multi-byte MMIO write straddling a boundary hits the wrong device for its tail bytes. Root cause: router splitting logic assumes width-aligned regions. Debugging method: boundary-crossing write fixture. Signal: differential mismatch. Recovery: reject boundary-crossing accesses as a bus fault (P9).

15.7 Performance Concerns

  • TLB locality (once §17 lands) depends on RAM contiguity per page — the allocator must not fragment guest-physical pages relative to host-virtual pages.
  • memcpy overhead on large segment loads (§16) — batch by page, not per byte.
  • Cache alignment: keep the region-lookup table cache-line-aligned since it is as hot as the decode dispatch table (§13.7).

15.8 Edge Cases

  • Partial writes at a region boundary — rejected, never silently split.
  • Device-region overlap discovered only under a custom configuration — must fail at registration, not first access.
  • Zero-sized region registration — rejected, distinct from a zero-sized ELF segment (§16.8).
  • Out-of-range access from guest integer overflow — resolves to a deterministic bus fault, never a host out-of-bounds read.

15.9 Failure Analysis

A bus violation emits the faulting address, access type, and the mapped-region table snapshot at fault time. Blast radius is contained to the faulting access — the bus rejects the operation before it reaches rvemu-memory or any MmioDevice, so no host or guest state is touched (P9).

15.10 Operational Notes

Metrics: memory.dirty_page_growth, bus.mmio_dispatch_rate, memory.allocation_pressure. Tracing spans: bus.route_access (sampled). Structured-log fields: address, access_type, region_id. Deployment: the region table is boot-time-fixed per configuration; changing the device map requires a process restart, not a hot migration.

17. Phase 5 — Privileged Architecture and MMU

17.1 Objectives

  • Implement Sv39 virtual-memory translation (rvemu-mmu) and supervisor-mode execution.
  • Add full CSR privilege-check semantics and trap delegation (medeleg/sedeleg).
  • Support the U/S/M privilege-mode transitions defined in §8's domain model.

17.2 Detailed Implementation Steps

  • Implement the three-level page-table walker (sv39.rs) per the RISC-V Privileged Architecture Specification sec. 10 (§5), enforcing I7 at every leaf-PTE validation point.
  • Add the TLB (tlb.rs) with per-ASID entries and a shootdown path for sfence.vma, enforcing I8's global-consistency requirement across the hart topology.
  • Implement PMP enforcement (pmp.rs): 16 configurable region-check entries validated ahead of every physical access, layered beneath the Sv39 walk per the privileged spec's PMP-before-translation ordering.
  • Add CSR privilege checks in csr.rs (extended from §14): an S-mode access to an M-mode-only CSR raises IllegalInstruction, not a silent no-op.
  • Implement trap delegation: medeleg/sedeleg bit checks determine M-mode vs. delegated S-mode handling, extending the §8 trap-flow diagram with a delegation-check step.
  • Implement satp handling (Bare/Sv39 mode switch) and page-fault semantics (instruction/load/store variants) as distinct TrapCause variants.
  • Add translation tracing and TLB-hit/miss metrics; add PMP-violation telemetry distinct from translation-fault telemetry.

17.3 Deliverable

Supervisor-mode execution: a guest kernel stub enables Sv39, takes a page fault, and resumes correctly under the interpreter — the prerequisite for any multi-process guest workload and for Phase 7's boot.

17.4 Acceptance Criteria

  • Passes 100% of the rv64si-*/rv64mi-* privileged riscv-tests vectors.
  • Deterministic page-fault behavior: identical cause/tval/epc across 100 repeated page_fault.bin runs.
  • Correct TLB invalidation: zero stale-translation hits across satp_switch.bin's mode-switch sequence.
  • p95 translation latency under the 250 ns §4 budget on the sv39_walk.bin benchmark.

17.5 Conformance Fixtures

  • fixtures/mmu/sv39_walk.bin — canonical three-level walk; expected: correct PA + permission bits.
  • fixtures/mmu/page_fault.bin — invalid leaf PTE; expected: deterministic page-fault trap (I7).
  • fixtures/mmu/satp_switch.bin — Bare→Sv39 transition; expected: correct TLB flush on switch.
  • fixtures/mmu/invalid_pte.bin — malformed PTE bit patterns; expected: rejection before any host-memory touch (I7).
  • fixtures/mmu/pmp_violation.bin — access outside a configured PMP region; expected: distinct PMP-fault telemetry.

17.6 Pitfalls

  • TLB staleness. Manifestation: silent wrong-answer execution after a page-table update without an sfence.vma. Root cause: a gap in the TLB-invalidation path. Debugging method: differential trace against Spike immediately after a satp/PTE update. Signal: satp_switch.bin divergence with no fault raised — the dangerous case. Recovery: audit every page-table-touching path for a required shootdown per I8.
  • Incorrect privilege checks. Manifestation: an S-mode guest reads/writes an M-mode-only CSR without trapping. Root cause: the privilege-check table missing an entry for a newly added CSR. Debugging method: cross-reference the CSR map against the privileged spec's access-mode column. Signal: rv64mi-* fixture failure. Recovery: regenerate the check table from the same single-source schema as csr_table.rs (P13).
  • PMP-before-translation ordering bug. Manifestation: an access that should be blocked by PMP proceeds to a successful walk. Root cause: pmp.rs invoked after, not before, the walk. Debugging method: pmp_violation.bin with a valid mapping but a violating PMP entry. Signal: fixture expects a PMP fault but observes success. Recovery: reorder per the spec's mandated sequence.

17.7 Performance Concerns

  • Page-walk overhead on TLB miss dominates MMU cost — the 250 ns p95 budget assumes > 95% warm hit ratio on typical kernel workloads; below that, Linux boot time (§19) is at risk.
  • TLB hit ratio depends on ASID-tagged entries surviving context switches — an untagged, flush-on-switch TLB would violate the budget under any multi-process workload.
  • Cache pollution: keep the TLB table separate from the decode dispatch table (§13.7) in cache layout — both hot, for different instruction phases.

17.8 Edge Cases

  • Recursive/self-referential page tables — the walker must bound depth at exactly 3 levels, never loop.
  • Invalid leaf entries with reserved bits set — rejected per I7, not masked and accepted.
  • Huge-page leaf entries at level 1/2 — must short-circuit correctly rather than always descending to level 0.
  • Simultaneous PMP/Sv39 permission conflict — PMP denial wins per the ordering in §17.6.

17.9 Failure Analysis

An MMU divergence dumps the full page-table walk trace and compares it against Spike's walk to isolate whether the divergence is in the walker, the TLB layer, or the PMP check. Blast radius: confined to the faulting hart's translation state; I7 guarantees no host-memory access before validation, so a walker bug produces a wrong fault decision, never a host memory-safety violation.

17.10 Operational Notes

Metrics: mmu.tlb_hit_rate, mmu.fault_frequency, mmu.walk_latency_ns, mmu.pmp_violation_total. Tracing spans: mmu.translate (sampled), mmu.tlb_shootdown. Structured-log fields: va, pa, satp, fault_cause. Deployment/compatibility: SMP beyond 4 harts is PhaseDeferred("§17") — ASID scoping and cross-hart shootdown coordination are designed for 4 harts; registered in §35.

  • Correct privilege-mode delivery: 100% of nested_irq.bin cases deliver to the correct mode per delegation state (§17.2).
  • Zero lost interrupts across a 1-million-injection stress run.

18.5 Conformance Fixtures

  • fixtures/devices/timer_irq.bin — CLINT timer-compare sequence; expected: interrupt fires exactly at mtimecmp crossing.
  • fixtures/devices/uart_echo.bin — UART TX/RX loopback; expected: byte-identical echo, no drops.
  • fixtures/devices/nested_irq.bin — interrupt arriving mid-trap-handler; expected: correct nesting per delegation rules.
  • fixtures/devices/malformed_plic_claim.bin — out-of-range PLIC claim ID; expected: typed rejection, no panic.

18.6 Pitfalls

  • Lost interrupts. Manifestation: a pending interrupt never delivered. Root cause: incorrect pending-bit clear ordering racing a new assertion in the same retirement window. Debugging method: replay-trace diff isolating the exact retirement index. Signal: timer_irq.bin stress-fixture failure. Recovery: serialize pending-bit mutation through I2's commit-order discipline.
  • Timer drift. Manifestation: replay divergence around timer-interrupt-adjacent instructions. Root cause: mtime derived from host wall clock instead of the virtual clock (violating ADR-21). Debugging method: check whether mtime reads correlate with retirement count or Instant::now(). Signal: non-reproducible timer_irq.bin runs. Recovery: route all time reads through the virtual clock (P1).
  • PLIC claim/complete mismatch. Manifestation: an interrupt source appears permanently masked after one claim. Root cause: the complete-side pending-bit re-arm is missing. Debugging method: fixture-driven claim/complete trace. Signal: nested_irq.bin regression on repeated interrupts. Recovery: fix the re-arm step in the claim/complete state machine.

18.7 Performance Concerns

  • IRQ dispatch latency must stay well under the p99 20 µs budget; avoid extra lock acquisition beyond the I5-mandated order on the delivery hot path.
  • Lock contention between the CLINT timer-wheel thread and the single-threaded hart loop is the primary concurrency risk this phase introduces — bounded by I5's fixed order.
  • Device-latency variance under a UART flood must not regress interpreter MIPS (§4) — device polling must be bounded, not busy-loop.

18.8 Edge Cases

  • Nested traps: an interrupt arriving inside a trap handler before mret/sret — delivery must respect current delegation/privilege state, never double-enter.
  • Interrupt storms (pathological or fuzz-injected) must be absorbed without violating the trace-queue backpressure bound (§4, P4), degrading gracefully rather than OOMing.
  • Simultaneous CLINT/PLIC interrupts in one retirement window — priority resolution must match the privileged-spec-mandated precedence.
  • Device reset mid-transaction at snapshot-restore time — must leave a valid, spec-defined reset state.

18.9 Failure Analysis

IRQ diagnostics collect the pending/enabled bitmask at fault time, PLIC priority/claim state, and the full delivery trace. Blast radius: confined to interrupt-delivery correctness — a lost or misdelivered interrupt does not corrupt architectural state directly (I4 holds), but produces a replay-visible divergence, which is itself the detection mechanism.

18.10 Operational Notes

Metrics: irq.rate, irq.dropped_total, device.latency_ns, plic.claim_complete_mismatch_total. Tracing spans: runtime.deliver_interrupt, devices.uart_io. Structured-log fields: irq_source, hart_id, delivery_mode. Deployment: device configuration is part of the boot-time region table (§15.2), versioned alongside the snapshot schema (P6) so a restored snapshot always matches its originating device topology.

  • fixtures/boot/dtb_mismatch.bin — inconsistent DTB vs. region table; expected: boot-time rejection.

19.6 Pitfalls

  • DTB mismatch. Manifestation: kernel panic during early boot, before console is live. Root cause: the constructed DTB disagrees with the actual region table — e.g. a stale UART base address. Debugging method: the early-boot ring buffer captures the pre-panic sequence without console output. Signal: dtb_mismatch.bin, or an unexpected panic offset in linux_boot.trace. Recovery: generate the DTB directly from the region table, never from a hand-maintained template.
  • SBI incompatibility. Manifestation: kernel timer init hangs or panics. Root cause: the minimal SBI shim is missing a call the target kernel build expects. Debugging method: trace every SBI ecall and argument state; compare against the kernel's probe sequence. Signal: boot hangs immediately after the SBI probe, before CLINT ticks appear. Recovery: extend the SBI shim's supported-extension bitmap.
  • VirtIO virtqueue misalignment. Manifestation: root-filesystem reads intermittently corrupted. Root cause: descriptor-ring alignment not matching the VirtIO sec. 2.6 layout requirement. Debugging method: dump ring state at the point of a corrupted read. Signal: small reads succeed, multi-descriptor reads fail. Recovery: fix ring alignment/wrap-around arithmetic per spec.

19.7 Performance Concerns

  • Kernel decompression adds fixed startup latency counted against the 15 s §4 boot budget — favor an uncompressed Image for the conformance fixture.
  • Disk IO batching: VirtIO-blk requests should coalesce at the virtqueue level to avoid per-sector MMIO round-trip overhead that would violate the boot budget under the interpreter's MIPS floor (§14.7).
  • The early-boot ring buffer must be fixed-size and pre-allocated (P8) since it runs before the full rvemu-trace pipeline (§18.2) is guaranteed live.

19.8 Edge Cases

  • Malformed initramfs (truncated cpio archive) — must fail with a typed boot error, not hang waiting for a root filesystem that will never mount.
  • Kernel command-line exceeding a configured maximum length — rejected at boot-ROM construction time.
  • Unsupported kernel configuration (a device this emulator does not model) — must produce a diagnosable panic trace, not a silent hang (P15).
  • Boot-time race between DTB construction and lazy device registration — DTB generated only after all §18 devices complete registration.

19.9 Failure Analysis

Boot failures collect the full console/early-boot-ring log, a device-state snapshot at the failure point, and the DTB actually presented to the kernel. Blast radius: a boot failure halts the single hart attempting to boot; it does not corrupt any already-committed snapshot or replay artifact, since I3's WAL-ordering guarantee holds regardless of boot outcome.

19.10 Operational Notes

Metrics: boot.duration_seconds, boot.syscall_frequency (post-shell), boot.io_throughput_bytes_sec. Tracing spans: runtime.boot_sequence, devices.virtio_blk_request. Structured-log fields: boot_stage, dtb_hash, sbi_call_id. PhaseDeferred("§19") marks full UEFI/ACPI firmware boot as out of scope for this phase, registered in §35.

20. Phase 8 — Deterministic Replay and Snapshotting

20.1 Objectives

  • Implement the replay WAL and snapshot subsystem (rvemu-trace) to full production strength.

20.2 Detailed Implementation Steps

  • Implement the replay WAL writer (replay_wal.rs): every ReplayEvent (§11) commits before its device-visible side effect becomes observable, enforcing I3 as a hard barrier at the rvemu-bus dispatch boundary.
  • Implement the event serializer using postcard + zstd (ADR-05/ADR-06), with schema_version-gated forward compatibility (P6) — the WAL-checkpoint-recovery model follows Petrov's Database Internals ch. 3–4 (§5).
  • Implement checkpoint/dirty-page snapshotting (snapshot_writer module): captures globally quiesced state (I6) under the rvemu-runtime quiesce barrier introduced conceptually in §12.
  • Implement the replay validator and divergence detector: compares live retirement-indexed state against recorded deltas at every commit, giving the < 1-instruction detection latency from §4.
  • Add the replay CLI subcommands (commands.rs) for record/replay/snapshot-restore operator workflows.
  • Add the compression pipeline and replay-overhead metrics; benchmark WAL write-amplification (replay_overhead.rs) to validate the 512 MB replay-buffer budget (§4), feeding §32's arithmetic.
  • Implement blake3 snapshot content-hashing (ADR-07) into SnapshotHeader (§11), validated on every restore before any body byte is trusted (P9).

20.3 Deliverable

A fully replayable execution environment: any recorded run replays to bit-identical architectural state, and any quiesced snapshot restores and resumes within the §4 RTO budgets.

20.4 Acceptance Criteria

  • Bit-identical replay: zero divergence across 1,000 replay runs of replay_boot.trace (§19's boot sequence).
  • Snapshot restore functional: snapshot_restore.bin restores and resumes within the 30 s §4 RTO budget.
  • Divergence detection: 100% of injected single-instruction perturbations detected within 1 instruction.
  • WAL write-amplification measured and documented within the 512 MB budget under a full boot-length run.

20.5 Conformance Fixtures

  • fixtures/replay/replay_boot.trace — full boot-sequence WAL; expected: bit-identical replay across 1,000 runs.
  • fixtures/replay/snapshot_restore.bin — a mid-boot quiesced snapshot; expected: successful restore.
  • fixtures/replay/partial_wal_corruption.bin — a truncated WAL segment; expected: typed corruption error, rollback to last valid sequence (I3).
  • fixtures/replay/interrupted_snapshot_write.bin — a snapshot write interrupted mid-serialization; expected: rejected on next restore attempt via checksum mismatch, never silently accepted.

20.6 Pitfalls

  • Non-deterministic timers. Manifestation: replay drift around CLINT-driven interrupts. Root cause: a residual host-wall-clock read outside §18.6's virtual-clock discipline. Debugging method: grep for Instant/SystemTime usage outside timer_wheel.rs. Signal: divergence localized to timer-adjacent retirement indices. Recovery: eliminate the wall-clock read, re-validate ADR-21.
  • Missing device events. Manifestation: silent divergence with no error raised — the most dangerous failure mode here. Root cause: a device mutates state without emitting a ReplayEvent. Debugging method: audit every MmioDevice::write call site against WAL-emission coverage. Signal: replay produces a plausible but subtly wrong final state. Recovery: enforce WAL emission at the rvemu-bus dispatch chokepoint (§15.2), not per-device self-reporting.
  • Interrupted snapshot write. Manifestation: a snapshot file that looks complete but is truncated. Root cause: process crash mid-serialization before the content-hash footer is written. Debugging method: check SnapshotHeader.content_hash (§11) validity before trusting any body byte. Signal: interrupted_snapshot_write.bin; checksum mismatch on restore. Recovery: atomic-rename into place only after the hash is verified.

20.7 Performance Concerns

  • WAL write amplification: batching multiple small deltas into fewer, larger writes reduces syscall overhead without violating I3's per-commit ordering.
  • Compression CPU cost (zstd, ADR-06) competes with interpreter throughput on the same host CPU — bound to a background pool respecting I5's lock order, never inline on the hart-execution critical path.
  • Snapshot pause time (§4's 250 ms budget) is dominated by the quiesce-barrier wait, not serialization itself at 4 harts.

20.8 Edge Cases

  • Partial WAL corruption mid-file — roll back to the last valid sequence boundary (I3), never skip and continue past a corrupted record.
  • Interrupted snapshot write handled per §20.6; cross-host live-migration snapshotting's un-defer trigger is registered in §35.
  • Replay of a trace recorded under a different schema_version — upgrade additively (P6) or reject explicitly, never silently misparse.
  • Concurrent snapshot request during an in-flight replay validation — serialized through I6's quiesce barrier, never interleaved.

20.9 Failure Analysis

Replay-mismatch diagnostics produce parallel retirement-count, memory-delta, and CSR-delta diffs, each isolating which subsystem's WAL emission first diverged from live state. Blast radius: a replay mismatch is a detection event, not a corruption event — I3's ordering guarantee means the WAL remains trustworthy even when live state has diverged, so recovery is always possible from the last checkpoint.

20.10 Operational Notes

Metrics: wal.write_amplification_ratio, snapshot.restore_latency_ms, replay.divergence_total. Tracing spans: trace.commit_wal_record, trace.snapshot_quiesce. Structured-log fields: sequence_id, schema_version, content_hash. Retention: snapshots retained 14 days; replay traces zstd-compressed at rest. PhaseDeferred("§20") marks cross-host live snapshot migration out of scope, registered in §35.

21.6 Pitfalls

  • Breakpoint re-entry. Manifestation: an infinite trap loop from a breakpoint set on the trap-vector entry instruction. Root cause: the breakpoint-hit trap and the original trap share the dispatch chokepoint without a re-entry guard. Debugging method: trace the retirement sequence around the loop for a repeating PC with no forward progress. Signal: gdb_breakpoint.trace hangs instead of completing. Recovery: add a one-shot re-entry guard keyed on PC + breakpoint ID.
  • Trace amplification. Manifestation: disk exhaustion once full observability (§21.2) turns every placeholder span real. Root cause: sampling rate (P4) not re-tuned after this phase. Debugging method: check trace.commit_wal_record volume against §4's FD/storage budgets. Signal: disk-usage alert on the trace filesystem. Recovery: apply P4's sampling policy uniformly, not just to the highest-volume span.
  • Concurrent debugger-attach race. Manifestation: two GDB sessions both believe they hold the single debug lock. Root cause: the accept loop is missing single-session enforcement. Debugging method: concurrent_attach.trace. Signal: the second session's packets interleave with the first's. Recovery: enforce single-session ownership at the socket-accept chokepoint.

21.7 Performance Concerns

  • Telemetry overhead: fully wired spans risk regressing the §4 MIPS budget if sampling isn't enforced uniformly — re-validate the interpreter benchmark after this phase.
  • Span allocation cost: keep span-context objects on the stack/arena, not heap-allocated per instruction, preserving §13.7's allocation-free-decode discipline.
  • Single-step mode abandons the batched-dispatch performance path (§14.7) for the session's duration — acceptable with a human in the loop, not a throughput-sensitive batch run.

21.8 Edge Cases

  • Stale breakpoints after a snapshot restore (§20) — re-validated against restored HartState, since the address may no longer map to executable memory.
  • A watchpoint on a region a later restore un-maps — cleared or reported invalid, never silently retained pointing at nothing.
  • Debugger disconnect mid-single-step — the runtime resumes normal scheduling cleanly, never wedged.
  • A breakpoint set on an RVC instruction's second byte — resolves to the correct instruction-start address, never traps mid-instruction.

21.9 Failure Analysis

Debugger-facing failures collect the full RSP protocol transcript, the trap history around the failure point, and the underlying TCP socket trace. Blast radius: confined to the debugging session — a GDB-side protocol bug cannot corrupt architectural state, since every register/memory mutation the protocol requests routes through the same single-owner chokepoints (P3) as any other write path.

25. Compatibility & Versioning

Wire compatibility. Replay-event and snapshot schemas (§11) carry an explicit schema_version and grow only by additive fields (P6). A parser encountering an unknown field preserves it verbatim rather than dropping it, preserving forward compatibility across a minor version boundary.

Storage compatibility. Every snapshot file opens with a SnapshotHeader (§11): magic bytes, schema version, hart count, content hash. All four are validated before any body byte is trusted (P9); a version mismatch fails closed with a typed error naming the expected vs. actual version, never a best-effort partial parse.

SemVer policy. Major: any incompatible snapshot/replay schema change (requires a migration tool or an explicit "no migration path" release note). Minor: additive features — new CSR support, new device model, new metric — with no schema break. Patch: correctness fixes only, no observable behavior change outside the fixed bug itself.

ISA-extension compatibility. New RISC-V extensions are added by extending the single-source opcode table (rvemu-isa, P13) and regenerating decode tables; this is a minor-version-compatible change as long as no existing opcode encoding changes meaning.

Migration path. A major-version snapshot migration is a distinct, explicitly-scoped tool (out of Phase 0-9 scope, related to but distinct from the cross-host live-migration deferral registered in §35) — within a major version, restore is guaranteed to work across any two builds sharing that version.

Deprecation policy. A deprecated metric, span name, or CLI flag is retained for one full major version cycle with a structured-log warning before removal, giving operators one upgrade cycle of notice.

26. Testing & Verification Strategy

Unit testing. Mandatory per-module coverage for rvemu-decode (decoder.rs, bitfield.rs, compressed.rs), rvemu-mmu (sv39.rs, tlb.rs, pmp.rs), and rvemu-core's CSR semantics (csr.rs) — the three subsystems where a silent logic bug is hardest to detect any other way.

Differential testing. Every interpreter and MMU change is validated against Spike (riscv-isa-sim, §5, ADR-24) as the authoritative oracle; QEMU serves as a secondary cross-check for device-model and boot-path behavior specifically (§19), since Spike does not model a full device tree. rvemu-testkit's differential.rs drives both comparisons from one fixture format.

Fuzzing. cargo-fuzz targets (ADR-15) cover the decoder (decode_target.rs, §13), the ELF loader (loader_target.rs, §16), and MMIO handlers (mmio_target.rs, §15/§18) — the three surfaces that parse untrusted or adversarial input directly. Corpus seeded from riscv-tests and real-world ELF binaries.

Conformance testing. rvemu-conformance runs the full riscv-tests and riscv-arch-test vector suites (vector_runner.rs) and produces a pass/fail report (report.rs) gating every merge to main; this is the CI-speed cost derived in §32's C8.

Chaos testing. rvemu-testkit's interrupt-injection primitive (§18.2) drives fault-injection scenarios: interrupt storms, partial writes, timer-drift simulation, and mid-serialization snapshot interruption — exercising the exact failure modes catalogued in §23.

Regression testing. Every fixed bug ships with a pinned fixture (e.g. decode_replay_decode_trace, §13.5) added to the permanent conformance corpus, ensuring the differential/fuzz surface only grows.

27. Build & Release Engineering

Reproducible builds. Pinned toolchain (rust-toolchain.toml), a vendored Cargo.lock under cargo-deny policy (ADR-03), fixed SOURCE_DATE_EPOCH, and deterministic archive packing together produce a byte-identical release artifact across independent CI runs (§12.4's acceptance gate).

Artifact signing. Release binaries are signed via cosign with an accompanying SHA256 manifest (ADR-20); scripts/release_sign.sh is the only code path permitted to produce a signed artifact, keeping the signing key's usage auditable to one script.

CI/CD topology. Seven gated stages, each a hard gate for the next: (1) lint — rustfmt + clippy deny(warnings); (2) unit tests — per-crate; (3) fuzz smoke — a short cargo-fuzz run per target, not the full corpus; (4) integration — tests/integration/, tests/replay/; (5) conformance — full riscv-tests via rvemu-conformance; (6) benchmark — criterion suite against the §4/§28 targets, regression-gated; (7) release signing — only on a tagged commit that passed stages 1-6.

Packaging. Cargo crates plus a single static binary artifact (ADR-17) is the Phase 0-9 packaging target; distro packaging (deb/rpm) is out of scope until post-Phase-9 operator demand justifies it.

Containerization. A multi-stage Docker build (ADR-18) produces a minimal runtime image; the build stage and runtime stage are split so the shipped image excludes the full Rust toolchain.

Versioned release cadence. Tagged releases follow the §25 SemVer policy; every tag triggers the full seven-stage pipeline, with stage 7 (release signing) as the only stage gated on tag creation rather than every commit.

28. Performance Engineering

Benchmarking methodology. rvemu-bench (criterion, ADR-14) measures interpreter MIPS (interpreter_bench.rs), TLB hit ratio and translation latency (mmu_bench.rs), boot time (boot_time.rs), and replay overhead (replay_overhead.rs) — one benchmark file per §4 budget category that has a corresponding runtime cost, keeping the mapping from budget to benchmark one-to-one.

Profiling. perf and flamegraph (Gregg, Systems Performance, §5) for CPU-bound interpreter hotspots; tokio-console for the bounded async paths (CLI/telemetry, ADR-09) where scheduling latency rather than raw CPU is the concern.

Lock analysis. Mutex wait time and scheduler-contention tracking, focused on the I5 lock-order boundaries — any measured contention at the hart → device or device → trace boundary is a signal that P4's backpressure tuning or I5's ordering needs revisiting, not that a faster lock primitive would fix the underlying issue.

Cache-locality discipline. The decode dispatch table (§13.7), the TLB (§17.7), and the region-lookup table (§15.7) are each independently kept cache-line-aligned and sized to fit host L1 for their hot subset — profiled and re-validated whenever a new opcode or device is added, since table growth is the most common regression vector for all three.

29. Scalability Analysis

Bottlenecks. Interpreter dispatch overhead (§14.7) is the single-hart throughput ceiling; page-walk latency on TLB miss (§17.7) is the dominant per-access cost once supervisor mode is live; tracing overhead (§21.7) is the risk introduced last, once every placeholder span becomes real.

Horizontal scaling. The CI replay farm shards conformance and differential workloads across many independent single-process instances — replay determinism (P1) is exactly what makes this safe: two shards replaying the same trace must produce identical results, so sharding by fixture rather than by guest state is trivially correct.

Vertical scaling. Single-hart interpreter throughput benefits from larger host L1/L2 cache (feeding §13.7/§14.7/§17.7's locality assumptions) and higher single-thread IPC host CPUs; it does not benefit from more host cores until SMP beyond 4 harts (PhaseDeferred("§17")) is un-deferred.

Scaling ceiling within Phase 0-9 scope. With the hart count fixed at 4 (§4) and execution single-threaded per hart, this system's scaling story for the specification period is entirely vertical (faster single-thread execution) plus horizontal-at-the-farm-level (more independent replay shards) — never horizontal-within-one-guest, which is exactly what the SMP deferral defers.

30. Mental Models & First Principles

  • MM1 — Determinism Is A Constraint, Not A Feature. Insight: treating replay as bolted on after the fact always fails; it must gate every design decision from day one. Predicts: any subsystem added without a WAL-emission review eventually causes a silent divergence (FM-1). Bug class avoided: unreproducible guest-execution bugs. Applies in §20.
  • MM2 — The MMU Is A Trust Boundary, Not A Cache. Insight: TLB/page-table logic exists to make an untrusted guest's addresses safe, not merely fast. Predicts: any optimization skipping PTE validation for a perceived-safe fast path reintroduces I7 violations. Bug class avoided: guest-triggered host-memory corruption. Applies in §17.
  • MM3 — Interpret Before You Compile. Insight: a provably correct interpreter is a JIT's only usable oracle. Predicts: building a JIT before the interpreter's conformance suite is green produces a fast emulator with no way to tell if it is also wrong. Bug class avoided: confidently-incorrect execution. Applies in §14.
  • MM4 — Every Queue Is A Liability Until Bounded. Insight: an unbounded queue is a deferred OOM, not a performance optimization. Predicts: any new telemetry/replay/MMIO queue added without an explicit bound (P8) becomes the next incident's root cause. Bug class avoided: memory-exhaustion crashes under load. Applies in §20.
  • MM5 — A Trap Is A State Machine, Not An Exception. Insight: modeling a trap as a language-level try/catch loses the atomicity (I4) and delegation semantics real hardware guarantees. Predicts: trap-handling code written as "try execute, catch fault" eventually leaks partial state. Bug class avoided: partially-committed trap context. Applies in §17.
  • MM6 — Observability Debt Compounds Silently. Insight: a placeholder span left unwired doesn't fail loudly — it just makes the next postmortem impossible. Predicts: any phase deferring "wire it up later" (§13/§14/§18) needs a single phase (§21) that closes every gap, or some gap is permanently forgotten. Bug class avoided: undiagnosable production incidents. Applies in §21.
  • MM7 — Single Ownership Beats Careful Locking. Insight: explicit ownership (P3) eliminates entire classes of races that "just add a mutex" only papers over. Predicts: any cross-subsystem shared-mutable-reference proposal is a P3 violation waiting to become an FM-3 deadlock. Bug class avoided: cross-subsystem races and lock-order deadlocks. Applies in §18.
  • MM8 — A Golden Reference Beats A Spec Reading. Insight: the RISC-V spec has ambiguous corners; Spike's actual behavior is the community's de facto tie-breaker. Predicts: any semantic disagreement between this emulator's spec reading and Spike's behavior should resolve in Spike's favor until proven otherwise. Bug class avoided: spec-literal but ecosystem-incompatible behavior. Applies in §14.

32. Back-of-Envelope Capacity Model

  • C1 — Per-hart state size. 32 GPRs × 8 B = 256 B + CSR sparse map (≈200 entries × 16 B) = 3.2 KB + TLB (64 entries × 24 B) = 1.5 KB + PMP (16 × 16 B) = 256 B + trap/misc ≈ 1 KB → total ≈ 6.2 KB, well inside the §4 256 KB per-hart ceiling with ~40x headroom for a richer CSR footprint.
  • C2 — Guest-RAM metadata overhead (1 GB guest). Dirty bitmap 1 GB / 4 KiB page / 8 bits = 32 KB + Sv39 page-table shadow ≈ 2 MB + worst-case dirty-snapshot staging (10% of guest) = 100 MB → 32 KB + 2 MB + 100 MB ≈ 102 MB, inside the §4 200 MB ceiling.
  • C3 — Replay-buffer fill time. ReplayEvent ≈ 23 B header + 18 B register deltas + 17 B memory delta + 8.5 B CSR delta + 4 B interrupt state + 8 B timestamp = 80 B per event, and 80 B × 80 M events/s (§4 MIPS ceiling) = 6.4 GB/s raw, so the 512 MB §4 replay-buffer ceiling fills in 512 MB / 6.4 GB/s ≈ 80 ms without a flush — why zstd compression (ADR-06) and a sub-100 ms flush cadence are load-bearing, not optional.
  • C4 — Boot-trace storage (uncompressed). 300 M instructions (§4 Linux-boot-time derivation) × 80 B/event = 24 GB raw, and at a 4:1 zstd ratio (ADR-06) 24 GB / 4 = 6 GB compressed per full boot trace — why fixtures/replay/replay_boot.trace (§19/§20) is captured once as a golden fixture rather than regenerated per CI run.
  • C5 — FD-budget accounting. 16 trace outputs + 32 snapshot files + 64 device backing files = 112, leaving 256 − 112 = 144 FDs of headroom for GDB/CLI sockets and ephemeral fixture handles under the §4 256-FD ceiling.
  • C6 — Lock-order audit surface. 5 hierarchy levels (I5) × 4 harts × 6 device-class instances (UART/CLINT/PLIC/VirtIO-blk + 2 reserved) = 120 distinct acquisition contexts to audit per subsystem change — small enough for the single-reviewer discipline P3/P11 assume.
  • C7 — Snapshot restore time budget. Header deserialize (negligible) + blake3 hash over up to 100 MB dirty-staging body (C2) at ≈1 GB/s = 100 ms + quiesce release (negligible) ≈ 100 ms total, well inside the 30 s §4 RTO, leaving > 290x margin for a slower storage backend.
  • C8 — Conformance-suite CI cost. ≈1,200 decode vectors (§13.4) + ≈400 privileged vectors (§17.4) = 1,600 vectors, and 1,600 × ≈5 ms average (decode + execute + Spike differential) = 8 s total conformance run time, cheap enough to gate every PR rather than running nightly only.
  • C9 — Availability-budget alert threshold. 99.5% crash-free target (§4) over a 1,000-run nightly CI farm allows at most 1,000 × 0.5% = 5 crashing runs before the SLO is breached, setting the alert threshold at 6 in the replay-farm dashboard (§24).
  • C10 — Dispatch-latency headroom. 1 / 80 MIPS = 12.5 ns theoretical minimum dispatch interval, and the §4 35 ns p50 budget / 12.5 ns = 2.8x that floor — the headroom the decode-table cache-locality work (§13.7) is meant to preserve as instruction mixes shift toward CSR-heavy kernel code.

33. Hard Questions (Self-Examination)

  • Q1. Why does the lock-order hierarchy (I5, §7) place trace last rather than first, given that §21's observability-by-default principle (§6) demands every subsystem emit telemetry — wouldn't acquiring the trace lock earliest minimize the risk of losing a telemetry event during a crash?
  • Q2. §17's TLB shootdown and §20's snapshot quiesce barrier both need every hart to reach a synchronization point — why are they implemented as two separate barriers instead of one shared quiesce primitive?
  • Q3. §14's interpreter-first principle delays JIT work past Phase 2, yet §19's Linux-boot budget (§4, 15 s) assumes the same MIPS ceiling the interpreter alone must hit — what happens to §19's acceptance criterion if the interpreter lands at the low end of the 25–80 MIPS range?
  • Q4. §20's replay WAL guarantees a commit before device-visible mutation, but §18's CLINT/PLIC devices are the first real telemetry producers — how does the WAL-commit-ordering guarantee interact with a device subsystem that predates the WAL's own completion in the phase order?
  • Q5. §22's threat model (T4) treats WAL tampering as an external-attacker threat, while §23's failure modes (FM-2, FM-5) treat WAL corruption as an accidental-fault scenario — does the blake3 hash actually distinguish these two cases, or only detect "some" corruption without attribution?
  • Q6. §17's staleness pitfall documents TLB staleness as "the dangerous case" because no fault is raised — given §7's debugging methodology (one assertion per invariant), why doesn't I8 have a direct runtime assertion the way I11/I12 do?
  • Q7. §9's ADR-10 locks single-threaded deterministic hart execution for the whole build, but §35's SMP deferral is anchored at §17 (the MMU phase) rather than §18 (the interrupt/device phase) — which phase's design actually gates SMP readiness?
  • Q8. §28's M10 (TLB hit ratio > 95%) and §32's C10 both assume a "typical kernel workload" — what happens to both numbers under the pathological interrupt storm §18 describes, and which section would first show the regression?
  • Q9. §26's differential-testing strategy compares against both Spike and QEMU, but §31 notes QEMU is not itself deterministic — how can a non-deterministic reference validate the determinism-critical invariants (§7) this project cares about most?
  • Q10. §16's ELF loader rejects ET_DYN as a permanent non-goal, while §19's Linux boot loads a kernel Image that is not a standard ELF at all — do these facts imply rvemu-loader has two structurally different code paths, and should §10's layout reflect that split?
  • Q11. §30's MM3 argues an interpreter must be provably correct before a JIT is attempted, but §14's acceptance criteria only require zero divergence over a 10-million-instruction differential run — is that enough evidence before §14's PhaseDeferred("§14") JIT work could safely begin?
  • Q12. §35 lists cross-host live snapshot migration anchored at §20, but §20's own invariant (I6) is defined only for a single host's harts — what new invariant would migration require that I6 does not already provide?
  • Q13. §24 names "replay mismatch" as a critical alert, while §32's C9 derives the alert threshold from a 99.5% availability budget tolerating 5 failing runs per 1,000 — if a single mismatch is critical-severity per §24, why does C9's threshold tolerate any failures at all?
  • Q14. §21's GDB single-step mode explicitly abandons the batched-dispatch performance path (§14.7) — does attaching a debugger change which of §4's latency budgets still apply, or are they suspended for the session's duration?
  • Q15. §6's P11 requires fuzz coverage for every unsafe block, while §26's fuzzing targets are scoped to decoder/loader/MMIO — does the mmap-backed guest-RAM allocator (§15, ADR-04), which is necessarily unsafe, have a fuzz target, or does it fall through a gap between §6 and §26?
  • Q16. §31 notes gem5 optimizes for cycle-level timing fidelity, which §1 explicitly excludes as a non-goal — if a user's actual need turns out to be microarchitectural analysis, does any phase between §12 and §21 produce data that could be repurposed?
  • Q17. §9's ADR-09 locks tokio for CLI/telemetry paths only, while §18's lock-contention pitfall names the CLINT timer-wheel thread as that phase's primary concurrency risk — is the timer-wheel thread in tokio's scope or a plain OS thread, and does §18 actually resolve that ambiguity?
  • Q18. §7's invariants cover retirement, CSR, WAL, trap, lock-order, snapshot, MMU, TLB, trace, device, x0, and PC-alignment — what invariant would govern the GDB single-step mode's interaction with I1's monotonic retirement counter, and does §21 or §7 currently own that gap?

34. Alternative Architectures (Roads Not Taken)

Alt A — Dynamic Binary Translation (JIT) First

Guest Code Block --translate--> Host-Native Block --cache--> Execute Natively
        ^                                                        |
        +-------------------- cache hit, skip translate ---------+

Regime where it wins: long-running, throughput-dominated workloads where JIT warm-up cost amortizes (full-distro boot plus sustained application benchmarking). Real system: QEMU's TCG. Why this blueprint rejects it for Phase 0–9: P10 and MM3 (§30) require a correctness oracle before a harder-to-audit translation cache is trusted, and the §1 timeline does not afford building both a correctness kernel and a JIT simultaneously without risking neither being solid; PhaseDeferred("§14") keeps the door open.

Alt B — Full-System Cycle-Accurate Timing Model

Fetch -> Decode -> Issue -> [Reorder Buffer] -> Execute (multi-cycle) -> Retire (in-order)
                                    |
                            Cache/Branch-Predictor Timing Models

Regime where it wins: microarchitectural research — branch-predictor studies, cache-hierarchy tuning. Real system: gem5. Why rejected: an explicit non-goal (§1); timing fidelity trades away the MIPS throughput budget (§4) this project needs for CI-speed conformance runs (§26, C8).

Alt C — Multi-Threaded Free-Running Harts

Hart0 Thread ---\
Hart1 Thread ----+--> shared MMIO bus (locked) --> devices
Hart2 Thread ----+
Hart3 Thread ---/
   (no global instruction-order barrier)

Regime where it wins: real hardware-speed SMP workloads where wall-clock throughput matters more than bit-identical replay. Real system: QEMU's multi-threaded TCG (MTTCG). Why rejected: violates P1 and I1–I9's replay-determinism guarantees; this project's headline differentiator (§2) is deterministic replay, not raw SMP throughput.

Alt D — Snapshot-Free Restart-From-ELF Recovery

Crash --> reload ELF/kernel image --> replay full input log from t=0 --> resume

Regime where it wins: short-lived, deterministic-from-cold-start workloads such as a pure userspace fuzz target with no accumulated kernel state. Real system: rr's default checkpoint-free recording mode (§5). Why rejected: replay-from-zero cost grows linearly with run length; at §19's 15 s Linux boot time this already exceeds the §4 30 s snapshot-restore RTO once a workload runs past a few minutes — §20 exists specifically to bound recovery time independent of run length.

36. Glossary

  • Hart — a RISC-V hardware thread; this project's unit of single-owned execution state (§11).
  • CSR — control and status register; privileged state accessed via dedicated instructions.
  • MMIO — memory-mapped IO; device registers exposed as addressable memory ranges.
  • TLB — translation lookaside buffer; caches Sv39 virtual-to-physical translations.
  • WAL — write-ahead log; the replay-event commit log underlying I3.
  • Replay divergence — a mismatch between recorded and replayed execution; the primary detection signal for FM-1.
  • Trap — a synchronous exception or delegated interrupt transition through the trap-flow state machine (§8).
  • SBI — supervisor binary interface; the minimal machine-mode service surface implemented in §19.
  • PLIC — platform-level interrupt controller; priority/claim/complete arbitration (§18).
  • CLINT — core-local interruptor; timer-compare and software-interrupt registers (§18).
  • Sv39 — the RISC-V three-level paged virtual-memory mode implemented in §17.
  • Retirement — the point an instruction's effects are committed; the basis of I1's monotonic counter.
  • Dirty page — a guest memory page modified since the last snapshot, tracked for incremental serialization (§15).
  • PMP — physical memory protection; region-based access control enforced beneath Sv39 (§17).
  • Snapshot — a serialized, globally quiesced copy of runtime state (I6), validated by SnapshotHeader (§11).
  • Differential testing — comparing this emulator's output against a reference implementation (Spike/QEMU) to detect divergence (§26).
  • Replay trace — the ordered ReplayEvent stream produced by the WAL (§20).
  • Watchpoint — a memory-access-triggered debugger breakpoint, distinct from an instruction-address breakpoint (§21.2).
  • Breakpoint — an instruction-address execution stop set via the GDB remote serial protocol (§21).
  • DTB — device tree blob; the hardware-description structure handed to the booting kernel (§19).
  • RSP — GDB Remote Serial Protocol; the packet-based wire protocol rvemu-gdb implements.
  • ASID — address-space identifier; scopes TLB entries per address space to avoid full flush on switch (§17).
  • PTE — page-table entry; the Sv39 walker's per-level leaf/branch record.
  • VirtIO — the paravirtualized device interface standard used for the emulated block device (§19).
  • Virtqueue — the VirtIO descriptor-ring transport structure for device request/response pairs.
  • Quiesce — bringing all harts to a synchronization point before a snapshot or migration operation (I6).
  • Backpressure — bounded-queue flow control preventing unbounded memory growth under load (P4).
  • Crash-only recovery — restarting from the last valid checkpoint rather than attempting partial rollback (P2).
  • Fail closed — terminating rather than continuing on malformed or ambiguous state (P9).
  • Single-owner — the rule that exactly one subsystem may mutate a given piece of state (P3).
  • ABI — application binary interface; the RVABI calling and stack-layout convention (§16).
  • ELF — Executable and Linkable Format; the guest binary format parsed by rvemu-loader.
  • ISA — instruction set architecture; the RV64GC encoding and semantics this project emulates.
  • RVC — the RISC-V compressed (16-bit) instruction-encoding extension.
  • IALIGN — the instruction-alignment requirement (32 or 16 bits with RVC) enforced by I12.
  • Trap delegation — medeleg/sedeleg-controlled routing of a trap to M-mode or S-mode (§17).
  • satp — the supervisor address-translation-and-protection CSR selecting Bare or Sv39 mode.
  • Privilege mode — one of U/S/M, the RISC-V execution-privilege level (§8).
  • x0 hardwiring — the ISA rule that register x0 always reads zero regardless of writes (I11).
  • Blast radius — the scope of state a given failure can corrupt before containment (§23).
  • Postmortem — the forensic analysis following an incident, driven by the trace/telemetry bundle (P15).
  • SBOM — software bill of materials; the dependency-provenance artifact from §12.2.
  • Reproducible build — a build producing a byte-identical artifact across independent runs (§27).
  • Content hash — the blake3 digest validating snapshot integrity before restore (ADR-07).
