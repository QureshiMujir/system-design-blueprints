Decisions (§9) · 24 ADRs

ADR-01

Language

Chosen

Rust 1.80+

Rejected

C++, Zig, C

When the rejected choice is right

C++ wins when embedding directly inside an existing giant C++ host (e.g. wrapping QEMU's TCG) outweighs the safety cost.

Why: Memory safety plus ownership rules make the single-owner invariant (P3) mechanically checkable.

ADR-02

Build System

Chosen

Cargo workspace

Rejected

Bazel, plain Make

When the rejected choice is right

Bazel wins once the build must span large non-Rust artifacts (vendored kernel + rootfs) under one hermetic graph.

Why: Native Rust tooling, simplest contributor onboarding for a 16-crate workspace.

ADR-03

Dependency Policy

Chosen

cargo-deny + vendored Cargo.lock

Rejected

Unpinned floating dependencies

When the rejected choice is right

Floating deps win for a disposable prototype where reproducibility has no value.

Why: Reproducible builds are required by ADR-16's release signing.

ADR-04

Guest RAM Storage

Chosen

Anonymous mmap-backed region

Rejected

malloc'd heap buffer

When the rejected choice is right

A malloc'd buffer wins for guest RAM under ~16 MB, where mmap's page-granularity overhead dominates.

Why: Enables page-granular dirty tracking via mprotect and cheap snapshot forking.

ADR-05

Serialization

Chosen

postcard

Rejected

protobuf, JSON

When the rejected choice is right

protobuf wins when the wire format must be shared with a non-Rust, cross-language consumer.

Why: Deterministic, compact binary encoding required for byte-stable replay hashing (P6).

ADR-06

Replay Compression

Chosen

zstd

Rejected

gzip, lz4

When the rejected choice is right

lz4 wins when CPU budget is tighter than storage budget, e.g. constrained CI runners.

Why: Best throughput/ratio tradeoff at the 512 MB replay-buffer scale (§4).

ADR-07

Snapshot Hashing

Chosen

Rejected

When the rejected choice is right

sha256 wins when FIPS-mode compliance is mandated by the deployment environment.

Why: ~10x throughput at comparable collision resistance for large snapshot files.

Debug-Protocol Networking

Async Runtime

ADR-10

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Dynamic Binary Translation (JIT) First

Guest Code Block --translate--> Host-Native Block --cache--> Execute Natively
        ^                                                        |
        +-------------------- cache hit, skip translate ---------+

Regime where it wins: long-running, throughput-dominated workloads where JIT warm-up cost amortizes (full-distro boot plus sustained application benchmarking). Real system: QEMU's TCG. Why this blueprint rejects it for Phase 0–9: P10 and MM3 (§30) require a correctness oracle before a harder-to-audit translation cache is trusted, and the §1 timeline does not afford building both a correctness kernel and a JIT simultaneously without risking neither being solid; PhaseDeferred("§14") keeps the door open.

Alt B — Full-System Cycle-Accurate Timing Model

Fetch -> Decode -> Issue -> [Reorder Buffer] -> Execute (multi-cycle) -> Retire (in-order)
                                    |
                            Cache/Branch-Predictor Timing Models

Regime where it wins: microarchitectural research — branch-predictor studies, cache-hierarchy tuning. Real system: gem5. Why rejected: an explicit non-goal (§1); timing fidelity trades away the MIPS throughput budget (§4) this project needs for CI-speed conformance runs (§26, C8).

Alt C — Multi-Threaded Free-Running Harts

Hart0 Thread ---\
Hart1 Thread ----+--> shared MMIO bus (locked) --> devices
Hart2 Thread ----+
Hart3 Thread ---/
   (no global instruction-order barrier)

Regime where it wins: real hardware-speed SMP workloads where wall-clock throughput matters more than bit-identical replay. Real system: QEMU's multi-threaded TCG (MTTCG). Why rejected: violates P1 and I1–I9's replay-determinism guarantees; this project's headline differentiator (§2) is deterministic replay, not raw SMP throughput.

Alt D — Snapshot-Free Restart-From-ELF Recovery

Crash --> reload ELF/kernel image --> replay full input log from t=0 --> resume

Regime where it wins: short-lived, deterministic-from-cold-start workloads such as a pure userspace fuzz target with no accumulated kernel state. Real system: rr's default checkpoint-free recording mode (§5). Why rejected: replay-from-zero cost grows linearly with run length; at §19's 15 s Linux boot time this already exceeds the §4 30 s snapshot-restore RTO once a workload runs past a few minutes — §20 exists specifically to bound recovery time independent of run length.
