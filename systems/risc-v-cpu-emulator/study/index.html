33. Hard Questions (Self-Examination)

  • Q1. Why does the lock-order hierarchy (I5, §7) place trace last rather than first, given that §21's observability-by-default principle (§6) demands every subsystem emit telemetry — wouldn't acquiring the trace lock earliest minimize the risk of losing a telemetry event during a crash?
  • Q2. §17's TLB shootdown and §20's snapshot quiesce barrier both need every hart to reach a synchronization point — why are they implemented as two separate barriers instead of one shared quiesce primitive?
  • Q3. §14's interpreter-first principle delays JIT work past Phase 2, yet §19's Linux-boot budget (§4, 15 s) assumes the same MIPS ceiling the interpreter alone must hit — what happens to §19's acceptance criterion if the interpreter lands at the low end of the 25–80 MIPS range?
  • Q4. §20's replay WAL guarantees a commit before device-visible mutation, but §18's CLINT/PLIC devices are the first real telemetry producers — how does the WAL-commit-ordering guarantee interact with a device subsystem that predates the WAL's own completion in the phase order?
  • Q5. §22's threat model (T4) treats WAL tampering as an external-attacker threat, while §23's failure modes (FM-2, FM-5) treat WAL corruption as an accidental-fault scenario — does the blake3 hash actually distinguish these two cases, or only detect "some" corruption without attribution?
  • Q6. §17's staleness pitfall documents TLB staleness as "the dangerous case" because no fault is raised — given §7's debugging methodology (one assertion per invariant), why doesn't I8 have a direct runtime assertion the way I11/I12 do?
  • Q7. §9's ADR-10 locks single-threaded deterministic hart execution for the whole build, but §35's SMP deferral is anchored at §17 (the MMU phase) rather than §18 (the interrupt/device phase) — which phase's design actually gates SMP readiness?
  • Q8. §28's M10 (TLB hit ratio > 95%) and §32's C10 both assume a "typical kernel workload" — what happens to both numbers under the pathological interrupt storm §18 describes, and which section would first show the regression?
  • Q9. §26's differential-testing strategy compares against both Spike and QEMU, but §31 notes QEMU is not itself deterministic — how can a non-deterministic reference validate the determinism-critical invariants (§7) this project cares about most?
  • Q10. §16's ELF loader rejects ET_DYN as a permanent non-goal, while §19's Linux boot loads a kernel Image that is not a standard ELF at all — do these facts imply rvemu-loader has two structurally different code paths, and should §10's layout reflect that split?
  • Q11. §30's MM3 argues an interpreter must be provably correct before a JIT is attempted, but §14's acceptance criteria only require zero divergence over a 10-million-instruction differential run — is that enough evidence before §14's PhaseDeferred("§14") JIT work could safely begin?
  • Q12. §35 lists cross-host live snapshot migration anchored at §20, but §20's own invariant (I6) is defined only for a single host's harts — what new invariant would migration require that I6 does not already provide?
  • Q13. §24 names "replay mismatch" as a critical alert, while §32's C9 derives the alert threshold from a 99.5% availability budget tolerating 5 failing runs per 1,000 — if a single mismatch is critical-severity per §24, why does C9's threshold tolerate any failures at all?
  • Q14. §21's GDB single-step mode explicitly abandons the batched-dispatch performance path (§14.7) — does attaching a debugger change which of §4's latency budgets still apply, or are they suspended for the session's duration?
  • Q15. §6's P11 requires fuzz coverage for every unsafe block, while §26's fuzzing targets are scoped to decoder/loader/MMIO — does the mmap-backed guest-RAM allocator (§15, ADR-04), which is necessarily unsafe, have a fuzz target, or does it fall through a gap between §6 and §26?
  • Q16. §31 notes gem5 optimizes for cycle-level timing fidelity, which §1 explicitly excludes as a non-goal — if a user's actual need turns out to be microarchitectural analysis, does any phase between §12 and §21 produce data that could be repurposed?
  • Q17. §9's ADR-09 locks tokio for CLI/telemetry paths only, while §18's lock-contention pitfall names the CLINT timer-wheel thread as that phase's primary concurrency risk — is the timer-wheel thread in tokio's scope or a plain OS thread, and does §18 actually resolve that ambiguity?
  • Q18. §7's invariants cover retirement, CSR, WAL, trap, lock-order, snapshot, MMU, TLB, trace, device, x0, and PC-alignment — what invariant would govern the GDB single-step mode's interaction with I1's monotonic retirement counter, and does §21 or §7 currently own that gap?

30. Mental Models & First Principles

  • MM1 — Determinism Is A Constraint, Not A Feature. Insight: treating replay as bolted on after the fact always fails; it must gate every design decision from day one. Predicts: any subsystem added without a WAL-emission review eventually causes a silent divergence (FM-1). Bug class avoided: unreproducible guest-execution bugs. Applies in §20.
  • MM2 — The MMU Is A Trust Boundary, Not A Cache. Insight: TLB/page-table logic exists to make an untrusted guest's addresses safe, not merely fast. Predicts: any optimization skipping PTE validation for a perceived-safe fast path reintroduces I7 violations. Bug class avoided: guest-triggered host-memory corruption. Applies in §17.
  • MM3 — Interpret Before You Compile. Insight: a provably correct interpreter is a JIT's only usable oracle. Predicts: building a JIT before the interpreter's conformance suite is green produces a fast emulator with no way to tell if it is also wrong. Bug class avoided: confidently-incorrect execution. Applies in §14.
  • MM4 — Every Queue Is A Liability Until Bounded. Insight: an unbounded queue is a deferred OOM, not a performance optimization. Predicts: any new telemetry/replay/MMIO queue added without an explicit bound (P8) becomes the next incident's root cause. Bug class avoided: memory-exhaustion crashes under load. Applies in §20.
  • MM5 — A Trap Is A State Machine, Not An Exception. Insight: modeling a trap as a language-level try/catch loses the atomicity (I4) and delegation semantics real hardware guarantees. Predicts: trap-handling code written as "try execute, catch fault" eventually leaks partial state. Bug class avoided: partially-committed trap context. Applies in §17.
  • MM6 — Observability Debt Compounds Silently. Insight: a placeholder span left unwired doesn't fail loudly — it just makes the next postmortem impossible. Predicts: any phase deferring "wire it up later" (§13/§14/§18) needs a single phase (§21) that closes every gap, or some gap is permanently forgotten. Bug class avoided: undiagnosable production incidents. Applies in §21.
  • MM7 — Single Ownership Beats Careful Locking. Insight: explicit ownership (P3) eliminates entire classes of races that "just add a mutex" only papers over. Predicts: any cross-subsystem shared-mutable-reference proposal is a P3 violation waiting to become an FM-3 deadlock. Bug class avoided: cross-subsystem races and lock-order deadlocks. Applies in §18.
  • MM8 — A Golden Reference Beats A Spec Reading. Insight: the RISC-V spec has ambiguous corners; Spike's actual behavior is the community's de facto tie-breaker. Predicts: any semantic disagreement between this emulator's spec reading and Spike's behavior should resolve in Spike's favor until proven otherwise. Bug class avoided: spec-literal but ecosystem-incompatible behavior. Applies in §14.

5. Required Reading

Books

  • Computer Organization and Design RISC-V Edition — Patterson & Hennessy (2017), ch. 2, 4, 5: instruction encoding, pipelined control flow, memory-hierarchy behavior; applied in §13 and §14.
  • Computer Architecture: A Quantitative Approach — Hennessy & Patterson (2019), ch. 2–3: pipeline hazards and branch behavior informing the dispatch-loop cost model; applied in §14 and §28.
  • Operating Systems: Three Easy Pieces — Remzi H. Arpaci-Dusseau & Andrea C. Arpaci-Dusseau (2018), ch. on virtual memory and CPU scheduling: paging structures, scheduler fairness concepts; applied in §17 and §12.
  • Systems Performance: Enterprise and the Cloud, 2nd ed. — Brendan Gregg (2020), ch. 5–6, 13: profiling methodology, flamegraphs, syscall/latency analysis; applied in §28.
  • Database Internals — Alex Petrov (2019), ch. 3–4, 8: WAL semantics, checkpointing, recovery design directly informing the replay/snapshot subsystem; applied in §20.
  • Linux Kernel Development, 3rd ed. — Robert Love (2010), ch. 7, 15: interrupt handling and timer subsystem design used as the model for CLINT/PLIC delivery semantics; applied in §18.
  • The Design and Implementation of the FreeBSD Operating System, 2nd ed. — McKusick, Neville-Neil & Watson (2014), ch. 4: trap-frame construction and VM-fault handling as a cross-check for §17's trap-atomicity design; applied in §17.

Papers

  • "QEMU, a Fast and Portable Dynamic Translator" — Fabrice Bellard, 2005, USENIX ATC (FREENIX Track): emulator subsystem structure and translation-block caching → informs why Phase 0 stays interpreter-first before any JIT is attempted; applied in §14.
  • "Engineering Record And Replay For Deployability" — O'Callahan, Paleino, Zhang & Sturgill, 2017, USENIX ATC: low-overhead deterministic record/replay design (rr) → directly informs the WAL event granularity chosen in §20; applied in §20.
  • "An Infrastructure for Adaptive Dynamic Optimization" — Bruening, Garnett & Amarasinghe, 2003, CGO: DynamoRIO's instrumentation model → informs the span/trace instrumentation hook points chosen for rvemu-trace; applied in §21.
  • "kvm: the Linux Virtual Machine Monitor" — Kivity, Kamay, Laor, Lublin & Liguori, 2007, Ottawa Linux Symposium: hardware-assisted privilege-transition model used as the conceptual cross-check for M/S/U mode switching; applied in §17.
  • "Instruction Sets Should Be Free: The Case For RISC-V" — Asanović & Patterson, 2014, UCB/EECS Technical Report: rationale for the open, modular encoding this project decodes; applied in §13.
  • "Simics: A Full System Simulation Platform" — Magnusson et al., 2002, IEEE Computer: full-system simulator architecture (checkpointing, deterministic time model) → cross-checked against §20's snapshot design; applied in §20.
  • "The gem5 Simulator" — Binkert et al., 2011, ACM SIGARCH Computer Architecture News: modular simulator component decomposition → informs the crate-boundary split in §10; applied in §10.
  • "Bochs: A Portable PC Emulator for Unix/X" — Kevin Lawton, 1996, Linux Journal: early full-system emulator debugging-facility design → cross-checked against rvemu-gdb scope; applied in §21.

Reference Implementations

  • qemu/qemu — study target/riscv/, softmmu/, hw/riscv/virt.c: mature RV64GC decode + Sv39 + device model reference; pitfall: do not copy the macro-heavy TCG dispatch — it optimizes for JIT throughput this project defers past Phase 0; applied in §13 and §14.
  • riscv-software-src/riscv-isa-sim (Spike) — study riscv/processor.cc, riscv/mmu.cc, riscv/insns/: the ISA-correctness golden reference used for §26 differential testing; pitfall: its per-instruction dispatch is a giant switch, not a data-driven table — do not copy that structure into rvemu-decode; applied in §14 and §26.
  • rv8-io/rv8 — study src/emu/emu-cpu.h: data-table-driven decode strategy, a closer structural model for rvemu-decode than Spike or QEMU; applied in §13.
  • bellard/tinyemu (TinyEMU) — study riscv_cpu.c, virtio.c: the minimal-Linux-boot reference implementation, useful as the smallest working cross-check for §19's boot path; applied in §19.
  • yeurch/bochs (Bochs) — study bochs/cpu/, bochs/gdbstub.cc: mature GDB-stub integration pattern used as the structural reference for rvemu-gdb; pitfall: its debugger hooks are woven directly into the CPU loop — keep them isolated behind the trap router instead; applied in §21.

RFCs / Specifications

  • RISC-V Unprivileged ISA Specification, v20191213, sec. 2, sec. 16, sec. 26 — canonical RV64I/M/A/F/D/C encoding, immediate layouts, compressed-instruction expansion rules; applied in §13.
  • RISC-V Privileged Architecture Specification, v20211203, sec. 3–4, sec. 10 — CSR address map, trap delegation (medeleg/sedeleg), Sv39 PTE bit layout; applied in §17.
  • ELF64 System V ABI Specification, sec. 5 — program-header/segment layout consumed by rvemu-loader; applied in §16.
  • DWARF Debugging Information Format, Version 5, sec. 6.2 — line-table structure rvemu-gdb resolves symbols against; applied in §21.
  • VirtIO Specification v1.2 (OASIS), sec. 2.6, sec. 5.2 — MMIO transport and virtqueue layout for the VirtIO-blk device model; applied in §19.
  • GDB Remote Serial Protocol (GDB User Manual, "Remote Protocol" chapter) — packet framing, qSupported negotiation, breakpoint/watchpoint packet semantics; applied in §21.
  • POSIX.1-2017 (IEEE Std 1003.1-2017), Signal Concepts — signal-delivery semantics bounding the scope of rvemu-loader's minimal syscall stubs; applied in §16.

Glossary (§36) · 44 terms · site-wide glossary

Hart
a RISC-V hardware thread; this project's unit of single-owned execution state (§11).
CSR
control and status register; privileged state accessed via dedicated instructions.
MMIO
memory-mapped IO; device registers exposed as addressable memory ranges.
TLB
translation lookaside buffer; caches Sv39 virtual-to-physical translations.
WAL
write-ahead log; the replay-event commit log underlying I3.
Replay divergence
a mismatch between recorded and replayed execution; the primary detection signal for FM-1.
Trap
a synchronous exception or delegated interrupt transition through the trap-flow state machine (§8).
SBI
supervisor binary interface; the minimal machine-mode service surface implemented in §19.
PLIC
platform-level interrupt controller; priority/claim/complete arbitration (§18).
CLINT
core-local interruptor; timer-compare and software-interrupt registers (§18).
Sv39
the RISC-V three-level paged virtual-memory mode implemented in §17.
Retirement
the point an instruction's effects are committed; the basis of I1's monotonic counter.
Dirty page
a guest memory page modified since the last snapshot, tracked for incremental serialization (§15).
PMP
physical memory protection; region-based access control enforced beneath Sv39 (§17).
Snapshot
a serialized, globally quiesced copy of runtime state (I6), validated by SnapshotHeader (§11).
Differential testing
comparing this emulator's output against a reference implementation (Spike/QEMU) to detect divergence (§26).
Replay trace
the ordered ReplayEvent stream produced by the WAL (§20).
Watchpoint
a memory-access-triggered debugger breakpoint, distinct from an instruction-address breakpoint (§21.2).
Breakpoint
an instruction-address execution stop set via the GDB remote serial protocol (§21).
DTB
device tree blob; the hardware-description structure handed to the booting kernel (§19).
RSP
GDB Remote Serial Protocol; the packet-based wire protocol rvemu-gdb implements.
ASID
address-space identifier; scopes TLB entries per address space to avoid full flush on switch (§17).
PTE
page-table entry; the Sv39 walker's per-level leaf/branch record.
VirtIO
the paravirtualized device interface standard used for the emulated block device (§19).
Virtqueue
the VirtIO descriptor-ring transport structure for device request/response pairs.
Quiesce
bringing all harts to a synchronization point before a snapshot or migration operation (I6).
Backpressure
bounded-queue flow control preventing unbounded memory growth under load (P4).
Crash-only recovery
restarting from the last valid checkpoint rather than attempting partial rollback (P2).
Fail closed
terminating rather than continuing on malformed or ambiguous state (P9).
Single-owner
the rule that exactly one subsystem may mutate a given piece of state (P3).
ABI
application binary interface; the RVABI calling and stack-layout convention (§16).
ELF
Executable and Linkable Format; the guest binary format parsed by rvemu-loader.
ISA
instruction set architecture; the RV64GC encoding and semantics this project emulates.
RVC
the RISC-V compressed (16-bit) instruction-encoding extension.
IALIGN
the instruction-alignment requirement (32 or 16 bits with RVC) enforced by I12.
Trap delegation
medeleg/sedeleg-controlled routing of a trap to M-mode or S-mode (§17).
satp
the supervisor address-translation-and-protection CSR selecting Bare or Sv39 mode.
Privilege mode
one of U/S/M, the RISC-V execution-privilege level (§8).
x0 hardwiring
the ISA rule that register x0 always reads zero regardless of writes (I11).
Blast radius
the scope of state a given failure can corrupt before containment (§23).
Postmortem
the forensic analysis following an incident, driven by the trace/telemetry bundle (P15).
SBOM
software bill of materials; the dependency-provenance artifact from §12.2.
Reproducible build
a build producing a byte-identical artifact across independent runs (§27).
Content hash
the blake3 digest validating snapshot integrity before restore (ADR-07).
