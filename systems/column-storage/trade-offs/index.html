Decisions (§9) · 23 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+ stable

Rejected

C++; Zig

When the rejected choice is right

C++ if you must link an existing C++ analytics codebase (Velox/DuckDB) and reuse its kernels directly

Why: Borrow checker pays for itself across page-cache/prefetch; arrow-rs/parquet mature; stable SIMD intrinsics

ADR-02

In-memory format

Chosen

Apache Arrow

Rejected

Bespoke columnar layout

When the rejected choice is right

Bespoke if you need a layout Arrow cannot express (e.g. PAX hybrid) and own every consumer

Why: De-facto standard; every interop point speaks Arrow; bespoke is a 4-month detour

ADR-03

On-disk format (read+write)

Chosen

Apache Parquet

Rejected

ORC write; custom format

When the rejected choice is right

ORC if your ecosystem is Hive/Spark-on-ORC and Parquet interop is not required

Why: The format users have on disk; Iceberg/Delta sit atop it

ADR-04

ORC support

Chosen

Read-only

Rejected

ORC read+write; no ORC

When the rejected choice is right

ORC write if you are a producer in an ORC-only lake

Why: Reading is the cost we pay; writing is a larger commitment not earning its keep at rank 85

ADR-05

Vector size

Chosen

4096 rows (default, tunable)

Rejected

1024; 8192; row-at-a-time

When the rejected choice is right

1024 if L1-resident kernels dominate and per-batch overhead is negligible

Why: X100/Photon support 1024–8192; 4096 balances L2 residence and dispatch amortisation

ADR-06

Selection-vector representation

Chosen

Dense bitmap < 1/8 selectivity, Roaring above

Rejected

Always dense; always Roaring; sorted index vector

When the rejected choice is right

Always-dense if selectivity is always low and Roaring's metadata overhead dominates

Why: Dense is cheap when sparse; Roaring is smaller and faster at high density

ADR-07

Per-page Bloom filters

Chosen

Written for dict-encoded high-card cols (cardinality > 1024)

Rejected

Always; never; column-chunk only

When the rejected choice is right

Column-chunk-only if pages are tiny and per-page Bloom overhead exceeds the prune benefit

Why: Per-page Bloom earns its bytes only on high-card equality predicates

ADR-08

Statistics granularity

Chosen

Footer (row group) + column index (page), mandatory

Rejected

Footer only; none

When the rejected choice is right

Footer-only if pages are not independently addressable (legacy v1 files)

Why: Page-level stats are the fast pushdown path; footer alone forces whole-page reads

ADR-09

Distinct-count sketch

Chosen

HyperLogLog p=14

Rejected

Exact distinct; KMV; p=12/p=16

When the rejected choice is right

Exact distinct if cardinalities are tiny and memory is free (small dimension tables)

Why: 12 KB/chunk, 0.81% error to 2^32; consumed from rank 72

ADR-10

Planner histogram

Chosen

Equi-height, 256 buckets (rank 54)

Rejected

Equi-width; sketch-based; none

When the rejected choice is right

Equi-width if the domain is uniform and bucket-boundary cost matters

Why: Equi-height is robust to skew; the planner owns it, the engine writes it

ADR-11

Compression policy

Chosen

zstd raw / lz4 short / snappy dict / none bit-packed

Rejected

Single codec everywhere; gzip

When the rejected choice is right

Single-codec (snappy) if decode latency must be uniform and ratio is secondary

Why: Encoder-aware per-page wins ratio and decode latency simultaneously

Eager if every column is always projected and selectivity is ~100%

Alternative Architectures (Roads Not Taken)

A1 — Row-at-a-time Volcano iterator engine.

Scan.next() -> row -> Filter.next() -> row -> Project.next() -> row -> ...

Wins when: the data is tiny, queries are point lookups, and per-row overhead is irrelevant (OLTP-flavoured). Embodied by: classic Volcano (PostgreSQL executor heritage). Rejected because: it boxes values, defeats SIMD, and collapses analytical throughput an order of magnitude (P3, MM1).

A2 — Whole-column eager materialisation (MonetDB BAT model).

Filter(col) -> full materialised col -> Project(col) -> full materialised col -> ...

Wins when: memory is abundant, selectivity is ~100%, and operator composition simplicity matters more than bandwidth. Embodied by: MonetDB's BAT algebra. Rejected because: eager materialisation burns memory and cache; late materialisation via selection vectors is the bandwidth-optimal default (P6, ADR-12, MM4).

A3 — Bespoke in-memory format with a translation layer at the Arrow boundary.

Disk -> bespoke columnar -> [translate] -> Arrow only at the API edge

Wins when: you need a layout Arrow cannot express (e.g. a PAX hybrid for mixed point/scan workloads) and own every consumer. Embodied by: ClickHouse's MergeTree blocks. Rejected because: it forces a copy at every interop point and is a four-month detour with no payoff for an interop-first engine (P1, ADR-02, PF14).

A4 — JIT/codegen execution (compile each query to native code).

PhysicalPlan -> LLVM IR -> native fn -> run over batches

Wins when: queries are long-running and codegen latency amortises, or expression trees are deep. Embodied by: DuckDB's late codegen, Photon's generated kernels, Hyper. Rejected (for Phase 0) because: interpretation over vectorised kernels reaches the throughput target without query-time compile latency; codegen is a Stretch goal once the interpreted path is correct (MM9, Stretch).
