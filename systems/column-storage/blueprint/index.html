85 — Column-Oriented Storage Engine

Project Number: 85

Project Name: Column-Oriented Storage Engine

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

A column-oriented storage engine in Rust that reads and writes Apache Parquet on disk, holds data as Apache Arrow record batches in memory, evaluates analytical queries through a vectorised expression engine with SIMD-driven filter / project / aggregate kernels, pushes predicates down to the Parquet page level using zone maps and Bloom filters, exposes an Arrow IPC stream and an Arrow Flight gRPC surface for distributed scan, and matches the upstream Arrow and Parquet reference implementations under a conformance suite. The engine is the analytical read path and the bulk-write path; transactions, secondary update paths, and a SQL frontend are out of scope.

1. Goal & Scope

Goal. Build the smallest column-oriented storage engine that still teaches the full analytical-execution surface: an Arrow-native in-memory layer, a Parquet read/write codec with statistics and Bloom-filter pages, a vectorised SIMD expression engine, four-level predicate pushdown, an Arrow IPC and Arrow Flight surface, and a conformance suite that verifies parity against the upstream Arrow and Parquet reference implementations.

In scope.

  • In-memory layout: Arrow record batches with validity buffers, offset buffers, and dictionary / RLE / FOR / delta / zigzag-varint encodings.
  • On-disk format: a Parquet writer and reader with row-group and page statistics, dictionary pages, and Bloom-filter pages. Arrow IPC stream and file (read + write). ORC (read-only).
  • Page-level compression: zstd, lz4, snappy, chosen per page by the encoder.
  • Vectorised expression evaluation: filter, project, hash aggregate, sort, top-k, with SIMD kernels on x86_64 (AVX2, AVX-512) and aarch64 (NEON).
  • Index: zone maps per row group, Bloom filters per column, an inverted index for high-cardinality strings.
  • Statistics: column min / max / null count / distinct count via HyperLogLog, equi-height histograms (consumed from portfolio dependencies).
  • Streaming surfaces: Arrow IPC stream, Arrow IPC file, Arrow Flight gRPC, append-only streaming ingest with delta-CDC.

Out of scope (and why). Transactions (the engine is read-optimised; the streaming path is best-effort, not ACID — Phase 11). A SQL parser or cost-based planner (the engine consumes a physical-plan IR; the planner is portfolio rank 54). Distributed joins, shuffles, and multi-node aggregation (Arrow Flight scatter-gather is the only distributed primitive — ADR-18). ORC writing (ADR-04).

Estimated time. 5–7 months for the full plan; 5–7 weeks for a Phase-0 drop that ingests Parquet, holds the data as Arrow batches, evaluates a filter / project / sum query end to end through the vectorised path, and emits a conformance report against the upstream reference vectors.

Recommended language. Rust 1.78+ (stable). The crate uses unsafe only at the SIMD boundary and at the Arrow-buffer aliasing boundary; both surfaces are covered by Miri runs and a sanitised CI lane (ADR-01).

Prerequisites. Working knowledge of relational analytics ("I have written a TPC-H query and know why a hash join beats a nested loop on lineitem"), intermediate Rust (lifetimes, traits, unsafe, Pin, async), the Arrow columnar format (record batches, validity buffers, offset buffers, dictionary encoding), the Parquet file format (row groups, column chunks, pages, dictionary pages, statistics), the SIMD model on x86_64 (AVX2, AVX-512, masked loads, gathers) and aarch64 (NEON), and the basics of cost-based query planning.

2. Why Build This

Analytical query engines are a mature corner of the database literature, and the engineering tradition is dense: MonetDB and X100 introduced the modern vectorised execution model in 2005; Vectorwise and Hyper carried the model into commercial systems; Apache Parquet and Apache Arrow standardised the on-disk and in-memory representations; DuckDB demonstrated that an embeddable engine can match the throughput of clustered systems for single-node analytics; Velox and Photon pushed the kernel-engineering frontier to what a CPU and a modern memory hierarchy can sustain. Every team that runs analytical workloads at scale eventually meets one of these systems and is bitten at least once by something that lives below the SQL layer: a Parquet file that decodes more slowly than expected because dictionary pages are missing, a hash aggregate that spills because the cardinality estimator under-counted, a predicate that is not pushed down because the column type lost its statistics, or a scan that does not vectorise because the iterator boxed every value into a Box<dyn Any>.

This project is the smallest engine that still teaches the full surface. You own the in-memory layout, the on-disk format, the page-level compression, the vectorised expression evaluator with SIMD kernels, the index, the planner statistics, the streaming surfaces, and the streaming ingest path. At the end of the plan you understand exactly why DuckDB does what it does, why Velox is a kernel library and not a database, why Photon's row-format-to-columnar-format transition exists at the Spark boundary, and which lines of your code execute when a scan touches a Parquet page.

The deliverable is small enough to actually finish. You do not implement transactions, you do not implement a SQL parser or planner, and you do not target every analytical workload. You target TPC-H and the Arrow / Parquet reference corpora, and you target two formats end-to-end: Parquet (read and write) and Arrow IPC (read and write). ORC is read-only. That tight focus is the only reason the timeline is 5–7 months rather than 5–7 years.

The engine exists in a portfolio whose other projects supply primitives this engine consumes. The Bloom-Filter and Count-Min sketch library (rank 72) supplies the Bloom filter and the HyperLogLog (ADR-14, §11, Phase 8). The Search Engine (rank 80) supplies the inverted index for high-cardinality string columns (ADR-15, Phase 8). The Query Planner (rank 54) supplies the equi-height histogram (ADR-16, Phase 8). The dependency direction is unilateral: this engine consumes, never vendors.

What Mastery Looks Like.

  • You can predict, before running it, how many bytes a pushdown filter against an indexed column will read — and the conformance bucket confirms it within 1% (Phase 4, Phase 8).
  • You can write a SIMD aggregate kernel whose AVX-512, AVX2, NEON, and scalar lanes produce bit-identical output, including float summation (Phase 5).
  • You can decode a Parquet file zero-copy where the layout permits and explain exactly which encodings force a streaming decode (Phase 2, Phase 4).
  • You can trace a TPC-H Q6 query from the physical-plan IR through four-level pushdown to the kernel dispatch and back (Phase 7, Appendix B.1).
  • You can reason about why the page cache budget and the operator memory budget are independent, and design an engine that does not OOM under concurrent scans (Phase 1, §4).
  • You can build a hash aggregate that radix-partitions, spills, and merges with bounded memory (Phase 5).
  • You can defend every locked ADR against its rejected alternative and name the regime where the rejected choice would win (§9).

Frontends. The externally visible boundary: the embedded API (the Engine handle and the physical-plan IR), the colstore CLI driver, and the Arrow Flight gRPC server. All three are thin drivers over the execution engine; none holds query state of its own.

Execution Engine. The operator tree. Each operator is a Scan (produces batches), a Sink (consumes batches), or a Pipeline (both). The engine wires operators by configuration and pushes Arrow record batches through them. Late materialisation (selection vectors) and predicate pushdown are the load-bearing disciplines here.

Statistics & Stats Sketches. Produced on the write path: min / max / null count, HyperLogLog distinct count, equi-height histograms. Consumed by the planner (external) and by the pushdown layer. Never recomputed on the read path unless the file declares them missing.

Index. Zone maps (per row group), Bloom filters (per column chunk and per page), inverted index (per opt-in string column). The codec consults the index during pushdown; the index never reaches into the codec.

Compute Kernels. The SIMD hot path. One trait-bound kernel per operation; runtime dispatch to scalar / AVX2 / AVX-512 / NEON from a single registry. Operators never branch on SIMD level.

In-Memory Layer. Arrow record batches are the unit of work; Arrow buffers are the unit of ownership. Decode produces Arrow buffers directly. Slicing and projection are zero-copy.

Parquet Codec. Writer and reader interoperable with parquet-mr and parquet-cpp. Zero-copy decode where the layout permits; streaming decode otherwise. ORC reader is read-only and structurally parallel.

Storage Layer. The ObjectStore abstraction (local, s3, gcs, azure), the two-tier page cache, the prefetch queue, and the I/O scheduler that merges adjacent small reads.

Three architectural properties recur throughout. First, the data path is one-way: bytes flow up from storage through the codec into Arrow buffers; pushdown predicates flow down from the engine through the codec into the page reader. Second, the kernel layer is backend-agnostic: the engine never branches on SIMD level at the call site. Third, every cross-cut (statistics, indexes, compression, allocator) is owned by the layer that produces it and exposed by trait-bound calls everywhere else; you never reach across layers.

6. Design Principles

Twelve principles. Each: the rule, the tradeoff it accepts, and how violating it breaks the system. They are enforced at the type level where possible and by code review where not.

P1 — Arrow is the in-memory format, not a translation layer. Rule: the engine never holds a non-Arrow representation of column data in steady state; translations happen only at the codec and SIMD-kernel boundaries. Tradeoff: you inherit Arrow's quirks (offset-exclusive ends, LSB-first validity) rather than designing a cleaner layout. Violation: a bespoke in-memory format forces a copy at every interop point and a four-month detour with no payoff (PF14, ADR-02).

P2 — Zero-copy from page to kernel where the layout permits. Rule: an uncompressed dictionary or RLE page decodes directly into an Arrow dictionary / run-end array without copying indices. Tradeoff: the reader carries two code paths (zero-copy and streaming decode) for the same column chunk. Violation: eager copy of every page burns memory bandwidth — the dominant cost in a scan — and forfeits the engine's throughput target (§4).

P3 — Vectorisation is a scheduling discipline, not an optimisation. Rule: every operator processes a batch in a single dispatch; per-row iterators are forbidden inside the engine. Tradeoff: operators must handle partial final batches and carry batch-sized scratch. Violation: a row-at-a-time iterator boxes values, defeats SIMD, and collapses throughput by an order of magnitude (PF24, Phase 6).

P4 — SIMD is a backend, not a bytecode. Rule: one trait-bound kernel per operation; runtime dispatch lives in exactly one place (the registry); operators never see the level. Tradeoff: four implementations per kernel to maintain and cross-check. Violation: dispatch decisions scattered across call sites make cross-lane parity untestable and let a lane diverge silently (PF25).

P5 — Predicate pushdown is the first optimisation, not the last. Rule: filters push below row groups, then pages, then into the decode for dictionary columns. Tradeoff: the writer must always produce the statistics the reader relies on, even when the workload may not use them. Violation: reading Parquet as an opaque blob defeats the column index, the offset index, and the Bloom pages — the entire point of the format (PF19).

P6 — Late materialisation is the default. Rule: filters produce selection vectors; only ProjectOp materialises, and only the columns and rows the selection permits. Tradeoff: the engine carries selection-vector machinery (dense + Roaring) everywhere. Violation: eager materialisation of intermediate tables burns memory and cache and turns a scan into a copy festival (PF32, ADR-12).

P7 — Compression is per-page and encoder-aware. Rule: the writer chooses the codec per page from the encoding it picked (zstd raw, lz4 short, snappy dictionary, none for bit-packed); the reader honours the page header and never assumes a default. Tradeoff: a more complex writer policy and a header-driven reader branch. Violation: a reader that assumes a default codec silently corrupts on a file written by another implementation (PF10).

P8 — Statistics are produced on the write path, not the read path. Rule: min / max / null / distinct (HLL) are computed at write time; the reader trusts what the file claims and recomputes only if declared missing. Tradeoff: write-path cost and the risk of trusting a lying file (mitigated by the column-index hash). Violation: recomputing on the read path turns every scan into a full scan and defeats pushdown (P5, PF36).

P9 — The engine is single-node first, distributed second. Rule: Phase 0 ships embedded + CLI; Arrow Flight scatter-gather is the only distributed primitive. Tradeoff: no distributed joins or shuffles, ever, within this project. Violation: building distributed execution inside the engine doubles the surface and never finishes (ADR-18, Stretch).

P10 — Determinism is the default. Rule: same files + same query → same output bytes; float aggregations use a locked summation order (pairwise) reproducible across runs and SIMD lanes. Tradeoff: the locked order forfeits a small amount of SIMD throughput. Violation: lane-dependent float sums make the conformance suite non-reproducible and break user trust (PF20).

P11 — Bounded memory under concurrency. Rule: the page cache budget and the operator memory budget are separate, each independently bounded; the hash aggregate spills rather than grows. Tradeoff: spill paths and bounded-buffer back-pressure add code. Violation: conflating the two budgets is the classic OOM under high-concurrency scans (PF4, §4).

P12 — Dependencies are consumed unilaterally, never vendored. Rule: the Bloom filter (rank 72), inverted index (rank 80), and histogram (rank 54) are external crate dependencies; the engine consumes published types and defers behind PhaseDeferred when the dependency is not yet built. Tradeoff: a build-order coupling across the portfolio. Violation: vendoring a copy forks the primitive and drifts from the upstream the conformance suite assumes (PF37).

8. Domain Model / Data Model

The engine's domain is the columnar table: a schema (ordered, named, typed, nullable fields) over a sequence of record batches, persisted as one or more Parquet files (or Arrow IPC streams), each file partitioned into row groups, each row group holding one column chunk per column, each column chunk a sequence of pages.

8.1 The layered data model

Table  ─┬─ Schema (Vec<Field>)
        └─ Files ─┬─ Parquet File ─┬─ Footer (FileMetaData, column/offset index)
                  │                └─ RowGroup* ─ ColumnChunk* ─ Page* (dict | data | bloom | index)
                  └─ Arrow IPC ─ Schema msg ─ RecordBatch msg*
In memory: RecordBatch ─ ArrayRef* ─ (Buffer values, Option<Validity>, Offsets?)

8.2 Worked example — one column chunk, end to end

Column l_shipdate (Date32, non-null), one row group of 1,048,576 rows. The writer sorts nothing but observes the column is low-cardinality (≈ 2,500 distinct dates over the data window), so it dictionary-encodes: a dictionary page lists the 2,500 distinct i32 day-counts once; data pages hold RLE/bit-packed indices (12 bits each). Per-page statistics record min/max day-count; the column chunk records min/max/null-count and an HLL distinct estimate (≈ 2,500). A Bloom filter is not written (cardinality < the 1024-equality-pushdown heuristic is false here, but dictionary + zone map already prune efficiently; ADR-07). On read, a predicate l_shipdate BETWEEN '1994-01-01' AND '1994-12-31' is checked against the column-chunk zone map (intersects → keep), then each page's min/max (prune pages outside the window), then the surviving pages decode zero-copy into an Arrow DictionaryArray<Int32, Int32> and the filter kernel runs against the dictionary indices.

8.4 Malformed-input and failure-path catalogue

  • Footer magic wrong (PAR1 missing at head or tail) → InvalidParquet("bad magic"); never attempt to parse the Thrift.
  • Footer length exceeds file size → OutOfRange; refuse to seek.
  • Dictionary index ≥ dictionary length → InvalidEncoding; do not index out of bounds (I10).
  • Validity bitmap length disagrees with value count → InvalidArrow; reject the array (I13).
  • Delta-binary-packed header claims more values than the page holds → InvalidEncoding; bounded read, no infinite loop (Threat Model, T3).
  • Page codec = Snappy but body is zstd-framed → decompress fails → InvalidParquet (I6).
  • Flight schema contradicts table schema → SchemaMismatch before any data is accepted (I10, Phase 9).

12.7 Performance Concerns

Cold cargo build --workspace across the ~19 crates in §10 is the baseline CI cost before any kernel exists; budget it now, because every later phase adds compile units, never fewer. sccache (ADR-21) amortises rebuild cost across CI runners and maintainer machines; the Nix flake pins the toolchain so cache hits are not invalidated by an unrelated environment drift. Keep lib.rs module declarations free of heavy proc-macro derives at this stage — front-loading them here would tax every later crate's incremental build before any kernel work justifies it.

12.8 Edge Cases

  • An empty conformance corpus must report Empty, never Pass — a runner that treats "no fixtures found" as success is the bug Phase 13's PF47 exists to catch, seeded here.
  • A workspace member with a circular path dependency fails cargo check with a cycle error — CI must surface it, not hang.
  • The minimum-toolchain CI lane must fail loudly (not silently downgrade) if a later phase accidentally uses a post-MSRV language feature.
  • A CI runner without the nix binary available falls back to plain cargo rather than hard-failing the whole lane (documented degradation, not a silent success).

12.9 Failure Analysis

A red CI lane at this phase has zero blast radius beyond blocking merges — no runtime code exists yet, so no System Invariant (§7) can be violated. Detection is the CI status check itself; containment is "do not merge"; recovery is fixing the Cargo.toml/Makefile/workflow file and re-running. The one forensic artifact worth keeping is the CI log of the first red run after a governance-doc change, since regressions here are almost always a copy-paste error in a workflow YAML rather than a logic bug.

13.6 Pitfalls

  • PF4 — Treating the page cache as the whole memory budget: it is only the I/O-amortisation layer, independent of the operator budget (P11, MM6).
  • PF5 — Holding a sync lock across an .await — deadlock (I11).
  • PF6 — Forgetting the etag on head — S3 strong-consistency detection depends on it.

13.7 Performance Concerns

get_range amortisation is the whole point of the I/O scheduler (step 5): a scan issuing one range read per page instead of one merged read per column chunk pays a syscall/RTT tax per page, dominating wall-clock at the 1 MiB page size (§4). The hot/cold tier split trades a small amount of double-bookkeeping (two LRU maps, two atomics) for keeping decoded pages (expensive to reproduce) separate from compressed bytes (cheap to hold more of) — sizing the ratio wrong either wastes decode CPU (cold tier too big) or wastes RAM on rarely-reused decoded pages (hot tier too big). Prefetch depth (4, §4) trades read-ahead I/O against wasted bandwidth if the scan is later pruned by pushdown (Phase 9) — over-eager prefetch fights zone-map pruning.

13.8 Edge Cases

  • get_range requesting bytes past end-of-file returns typed OutOfRange, never a panic or a silently truncated read (I10).
  • A prefetch hint issued for a page later pruned by pushdown (Phase 9, not yet built at this phase) must be cancellable without leaking the in-flight future.
  • Cache eviction racing a concurrent get for the same key must not return a torn/partial Arc<DecodedPage> — the LRU's own locking is the sole arbiter.
  • A remote-backend feature flag enabled without credentials configured fails at ObjectStore construction with a typed error, not a panic on first get.
  • Clock skew between the local host and an eventually-consistent remote store can make head's last_modified stale — the cache key never trusts wall-clock freshness alone, only the etag.

13.9 Failure Analysis

A page-cache-capacity misconfiguration (e.g., hot tier sized larger than the process RSS budget) manifests as OOM under concurrent scans, detected via RSS approaching the §4 ceiling before page_cache_hit_total/miss_total show anything unusual — the operator runbook (docs/runbook/oom.md) is the first stop. A scheduler bug that fails to merge adjacent reads is detected by io_reads_merged_total staying flat under a sequential-scan benchmark; containment is per-request (no cross-scan blast radius); recovery is redeploying with the scheduler's coalescing threshold logged for postmortem. A stuck .await while holding a parking_lot lock (I11 violation slipping past the clippy lane) deadlocks the holder's Tokio task; detection is a watchdog timeout on get_range, forensic artifact is the task dump at timeout.

13.10 Operational Notes

Spans wrap every get_range; metrics: page_cache_hit_total, page_cache_miss_total, prefetch_issued_total, io_reads_merged_total, lock_held_across_await_total (I11, must be 0). No migration surface at this phase (no persisted state format); a remote-backend credential rotation is an operator action outside the engine's compatibility surface (documented in docs/runbook/triage.md).

14. Phase 3 — Encoding and Compression

The bridge between bytes on disk and Arrow buffers in memory. Read alongside the Parquet specification; the encodings here implement what Parquet writes.

14.1 Objectives

Implement the seven encodings (Plain, Dictionary, RLE/bit-packed-hybrid, Frame-of-Reference, Delta-binary-packed, Zigzag-varint, Bit-packing) and the four codecs (zstd, lz4, snappy, none), each round-tripping bit-for-bit. Constraint introduced: every encoder/decoder pair must satisfy I5 before it is wired into the Phase 5 Parquet writer/reader.

14.2 Detailed Implementation Steps

Applies P2 (zero-copy where layout permits), P7 (encoder-aware compression), I5 (round-trip), and I6 (reader honours header codec). Bit-packing and zigzag draw on Hacker's Delight (§5); the RLE/bit-packed hybrid is the Parquet variant.

  1. Plain: fixed-width little-endian; trivially zero-copy when uncompressed (P2).
  2. Dictionary: dictionary page lists distinct values once; data pages hold indices; decode produces an Arrow DictionaryArray directly when indices are RLE-bit-packed and the dictionary is small.
  3. RLE/hybrid: leading varint (len << 1) | flag chooses RLE-run vs. bit-packed-group; the decoder reads the varint before branching.
  4. Frame-of-Reference: store each value as a delta from the per-page reference (min); a logical encoding the engine recognises for kernel fast paths (Phase 6).
  5. Delta-binary-packed: header (block size, mini-block size, total values, first value) then mini-blocks of bit-packed second-order deltas; bound the value count to the page (T3, T4).
  6. Zigzag-varint: map signed→unsigned, varint-pack LSB-first 7-bit groups with continuation bits.
  7. Bit-packing: pack n values of b bits each; LSB-first (Parquet) default, MSB-first available for legacy ORC.
  8. Compression: zstd (raw), lz4 (short < 64 KB), snappy (dictionary page), none (bit-packed); selected per page by the writer (P7), honoured exactly by the reader (I6) — never a fixed default (PF10).

14.6 Pitfalls

  • PF7 — Off-by-one in the RLE/bit-packed-run decoder — most bugs trace to misreading the leading varint.
  • PF8 — Mixing LSB-first and MSB-first bit-packing (Parquet vs. legacy ORC) — the decoder must be told which.
  • PF9 — Assuming the dictionary fits in memory — the writer falls back to plain when it exceeds the threshold; the reader handles both in one chunk.
  • PF10 — Assuming a fixed default compression codec instead of reading the page header — a reader that assumes a default silently corrupts on a file written by another implementation honoring per-page codec choice (P7, I6).

14.7 Performance Concerns

Dictionary encoding trades a dictionary-page read (once per column chunk) for narrower per-value indices (bit-width sized to cardinality) — a net win only below the 1 MiB dictionary threshold (ADR-07 territory); above it the writer falls back to plain, which the reader must handle without a branch penalty on the hot path. Zstd at level 3 (Appendix C default) balances ratio against decode latency (§4 p50/p95/p99 targets); a higher level trades write-time CPU for a smaller file, which only pays off when the file is read many more times than it is written. Frame-of-reference and delta-binary-packed both trade encode-time computation (finding the reference/deltas) for smaller on-disk footprint and, critically, for kernels that can operate on the delta representation directly without fully materialising the original values (Phase 6 fast paths).

14.8 Edge Cases

  • A delta-binary-packed header claiming more values than the page byte length permits is bounded to the page and rejected, never read past the page boundary (T3, T4, I10).
  • A dictionary page with zero entries (empty domain) is valid and decodes to an empty DictionaryArray, not an error.
  • Bit-packing at a 0-bit width (single-valued column) still round-trips — the constant is carried as a run-length in the RLE/hybrid path rather than a zero-width pack.
  • A codec mismatch between what the header declares and what the byte stream actually contains (e.g., Snappy header, zstd-framed body) fails decompression cleanly (I6, F2).
  • Zigzag-varint decode of the maximum-magnitude negative integer (i64::MIN) must not overflow during the signed→unsigned remap.

14.9 Failure Analysis

encoding_roundtrip_fail_total > 0 on any dtype is a sealed-tier blocker (I5) — CI blocks merge immediately; the forensic artifact is the specific proptest-shrunk failing input, replayed as a new named fixture under corpora/encoding/. A codec mismatch in production (F2) is detected at decompress time and surfaces as typed InvalidParquet, containing the blast radius to the single column chunk being read; recovery is rejecting the file, never attempting a best-effort partial decode. A dictionary-fallback bug (writer claims dictionary encoding but exceeds the threshold without falling back) is caught by the proptest sweep before it reaches production, since the sweep includes high-cardinality inputs designed to trigger the fallback path.

14.10 Operational Notes

Blast radius of a slice-identity bug is every zero-copy consumer downstream (Phase 7 selection vectors, Phase 8 operators) — contained by the arrays_equal conformance bucket catching any divergence from arrow-rs before merge. A RecordBatch::try_new that fails to reject a shape mismatch (I13) propagates a corrupt batch arbitrarily far downstream before a kernel finally panics on an out-of-bounds index — the fix is always at construction, never at the point of eventual failure.

16.7 Performance Concerns

Row-group size (128 MiB, zone-map granularity) and page size (1 MiB, column-index + prefetch granularity) are independently tunable: a smaller page size sharpens pushdown (finer-grained min/max) at the cost of more page headers and more decompressor invocations; a smaller row-group size sharpens zone-map pruning at the cost of more per-row-group metadata in the footer. Zero-copy decode (P2) applies when a dictionary or RLE page is uncompressed or the codec produces an aligned buffer directly — the streaming-decode fallback path exists for every other case and is measurably slower (extra copy), so the writer's encoding choice has a direct read-side throughput consequence (BE1–BE6). Time-to-first-row (§4, M6) is dominated by footer parse + first-row-group zone-map check, not by decompression — keep the footer parse allocation-free where possible.

16.8 Edge Cases

  • A footer whose declared length exceeds the file size is rejected before any seek is attempted (OutOfRange, §8.4).
  • A dictionary index at or beyond the dictionary's length is rejected as InvalidEncoding, never indexed (I10, T2).
  • A column chunk with bloom_filter_offset present but the referenced bytes malformed skips the Bloom check and falls back to fetching the page (I9's conservative direction — never a hard failure), logged via stats_corruption_total.
  • Row groups spanning a page-header size boundary that would require re-reading a partially-buffered page are handled by the I/O scheduler's range logic (Phase 2), not by the Parquet reader re-implementing buffering.
  • A v1 Parquet file with no column index at all (legacy writer) falls back to row-group-only pruning (footer stats), a slower but still-correct pushdown path (ADR-08's footer-only regime).

16.9 Failure Analysis

decode_panic_total > 0 on any input, valid or malformed, is a sealed-tier blocker (I10, M12) — the fuzz harness runs continuously (M7 target: 30 days) and any panic pages on-call immediately; blast radius is contained to the single file/column-chunk being decoded since the reader never holds cross-file state. stats_corruption_total rising (I12) signals a file whose declared statistics do not match its data — detected via the column-index hash check, recovery is a full recompute on that column chunk with a warning, not a crash. A codec mismatch (F2) between page header and body is detected at decompress time and rejects the file with InvalidParquet, never attempting a partial decode that could silently return wrong rows.

17.6 Pitfalls

  • PF20 — Float summation order differing between lanes — lock the pairwise tree (I8, P10).
  • PF21 — Mask register width — AVX-512 has 8-bit masks for i64 lanes; preserve the lane count.
  • PF22 — Misaligned loads — buffers are 64-byte aligned but slices are not; use unaligned loads on the prefix/suffix.
  • PF23 — Branchful inner loops — compute both branches and select with a mask (IF-conversion).
  • PF24 — A row-at-a-time iterator inside a kernel or operator boxes values and defeats SIMD — collapses throughput by an order of magnitude (P3).
  • PF25 — Scattering SIMD-level dispatch decisions across call sites instead of the single registry — makes cross-lane parity untestable and lets a lane diverge silently (P4, I7).

17.7 Performance Concerns

Vector size 4096 (ADR-05) is chosen to keep a batch column resident in L2 across the kernel's full pass while amortising the per-call dispatch overhead (BE12: ≈2,173 dispatches per row group per column at Q6 scale) — smaller vectors (1024) favor L1 residence at the cost of more dispatches; larger (8192) reduce dispatch count but risk L2 eviction on wide row groups. AVX-512's mask registers avoid the movemask round-trip AVX2 needs, the source of its ≈2× per-lane advantage on comparison-heavy kernels (Scalability Analysis). The radix hash aggregate's 256-way partitioning trades a hash-and-scatter pass for cache-resident per-partition tables (BE10); too few partitions and a hot partition thrashes cache, too many and per-partition overhead dominates for low-cardinality group-bys.

17.8 Edge Cases

  • A batch shorter than the vector size (the final, partial batch of a scan) must still dispatch through the same kernel path, not a separate scalar-only tail loop that could diverge from the vectorised lanes (I7).
  • NaN and signed-zero handling in float comparison kernels must match the scalar reference exactly, including NaN != NaN and -0.0 == 0.0.
  • Integer overflow in sum_i64 on adversarial input (all i64::MAX) must saturate or error per the declared dtype semantics, never silently wrap (T4 territory).
  • A hash aggregate group-by key set that hashes to a single radix partition (adversarial or pathological key distribution) must still bound memory via the spill path, not OOM.
  • AVX-512 unavailable at runtime (older CPU) falls back to AVX2 or scalar via KernelLevel::detect() — every kernel must have a correct fallback, not just the fast path.

17.9 Failure Analysis

kernel_lane_divergence_total > 0 (I7) is a sealed-tier blocker: CI fails immediately, the lane is disabled pending a fix, and the engine falls back to the next-slower verified lane rather than shipping a silently wrong fast path. float_sum_order_violation_total > 0 (I8) indicates the pairwise tree was not honoured on some lane — detected by the golden fixture, blast radius is every aggregate query until fixed, recovery is relocking the summation order and re-verifying every lane. A hash-aggregate spill bug (partition merge producing a different result than the non-spilled path) is caught by the partition-spill conformance fixture before it reaches TPC-H Q1 golden comparison; in production it would silently return wrong aggregate values, the worst class of failure this engine can produce.

17.10 Operational Notes

Metrics: kernel_dispatch_total{op,dtype,level}, kernel_lane_divergence_total (I7, must be 0), float_sum_order_violation_total (I8, must be 0), hash_aggregate_spill_total; spans wrap each aggregate build/merge. docs/kernel-reference.md documents which lane services which CPU, used when triaging an unexpected throughput regression after a deployment to new hardware.

18. Phase 7 — Expression Evaluator

Sits between the operators and the kernels: compiles a small expression IR into a sequence of kernel calls, applies them to a batch, and produces a result batch or a selection vector.

18.1 Objectives

Implement the Expr IR, the tree-walking compiler with an inline cache, and the executor that produces selection vectors for filters and materialises only at project (late materialisation). Constraint introduced: the IR never inserts implicit casts (the planner above must) — the compiler errors rather than silently coercing types.

18.2 Detailed Implementation Steps

Applies P3 (vectorised), P6 (late materialisation), I8 (locked float order in aggregates). The operator/iterator distinction is Graefe (§5); the vector algebra below the operator is Voodoo (§5).

    Column(Arc<str>), Literal(Scalar),
    BinaryOp { op: BinaryOp, lhs: Box<Expr>, rhs: Box<Expr> },

    Cast { expr: Box<Expr>, target: DataType },

  2. Compile by tree walk: each node compiles to either a value-producing kernel (Array) or a mask-producing kernel (SelectionVector). Keep a small inline cache so repeated compilation of the same expression in a long scan is amortised.
  3. Inline the dispatch decision at compile time: BinaryOp::Eq on an i32 column compiles to a direct registry.filter_eq_i32 call, not a virtual call (P4).
  4. The executor produces a selection vector per filter; only ProjectOp materialises surviving rows (P6, ADR-12).
  5. Implement three-valued Kleene logic for AND/OR/NOT over nullable booleans.

18.6 Pitfalls

  • PF26 — Three-valued logic: null AND false = false, null AND true = null, null OR true = true, null OR false = null — SQL semantics depend on it.
  • PF27 — Implicit casts — the IR does not insert them; the compiler errors on type mismatch.
  • PF28 — Integer overflow — pick the wider type or error; never silently wrap.

18.7 Performance Concerns

The inline compile cache exists because a long scan re-evaluates the same expression tree once per batch; recompiling it from the Expr IR every batch would dominate wall-clock at the 4096-row vector size (thousands of batches per row group, BE12). Compiling BinaryOp::Eq to a direct kernel-registry function pointer rather than a virtual dispatch through the Expr tree avoids an indirect call per vector, keeping the expression layer's overhead below the kernel's own cost. Selection-vector propagation (P6) means the executor's cost scales with selectivity for everything after the first filter, not with the full column width — the late-materialisation fixture's buffer count is the direct measure of this.

18.8 Edge Cases

  • A Like/Regex predicate against a column containing invalid UTF-8 bytes (should not occur given Arrow's Utf8 invariants, but a corrupt decode upstream could produce it) must fail typed, not panic mid-pattern-match.
  • InList against an empty list is a valid expression that always evaluates to an all-false selection vector, not an error.
  • A Cast from a wider to a narrower integer type that would overflow errors at evaluation time rather than silently truncating (mirrors PF28).
  • Three-valued logic combined with a SelectionVector::Full (no filter yet applied) treats "no mask" as "all true," never as "all null."
  • An expression tree deep enough to risk stack overflow during tree-walk compilation (pathological nested BinaryOp) is bounded by a maximum-depth check at compile time, erroring rather than overflowing the stack.

18.9 Failure Analysis

A compiler bug that silently inserts an implicit cast (violating the "IR never casts" contract) is caught by the type-mismatch conformance fixture before merge; in production it would silently change query semantics, the worst class of expression-layer bug. A Kleene-logic bug (three-valued truth table wrong for one operator) is caught by the truth-sweep fixture; blast radius is every query with a nullable boolean predicate, common enough that this fixture runs on every CI build, not just nightly. A late-materialisation regression (an operator eagerly materialising when it should propagate a selection vector) is detected by the buffer-count fixture regressing upward — the fix is always at the operator boundary (Phase 8), never inside the kernel.

18.10 Operational Notes

Metrics: expr_compile_cache_hit_total, expr_compile_cache_miss_total, selection_vector_materialise_total; spans wrap each batch evaluation. The compile-cache hit ratio is the operator-facing signal that a workload's expressions are being amortised correctly — a persistently low hit ratio under a repetitive workload indicates a cache-key bug (e.g., hashing the Expr tree by pointer instead of by structural equality).

19. Phase 8 — Operators and the Engine

The thinnest viable layer above the kernels. The engine wires operators into a tree and pushes batches through.

19.1 Objectives

Implement the operators (TableScan, Filter, Project, Aggregate, Sort, TopK, Write) and the engine that executes a physical-plan IR and returns a stream of batches. Constraint introduced: only ProjectOp materialises (P6) — every other operator propagates selection vectors or passes batches through unmodified.

19.2 Detailed Implementation Steps

Applies P5 (pushdown), P6 (late materialisation), P9 (single-node first), P10/I8 (deterministic float order). The operator model is Graefe (§5); the radix aggregate is DuckDB (§5).

pub enum Operator {
    Scan { table: Arc<Table>, projection: Option<Vec<Arc<str>>>, filter: Option<Expr> },

  2. FilterOp: apply an ExprExecutor (Phase 7) per batch, returning (batch, mask); fuse into TableScan when the filter is pushable.
  3. ProjectOp: apply expressions per batch; the only materialising operator (P6, ADR-12).
  4. AggregateOp: hash aggregate (Phase 6) over group-by + aggregate expressions; emit at end-of-input.
  5. SortOp: in-memory sort Phase-0; spilling external sort deferred (Deferred Features Register).
  6. TopKOp: heap-based, no full sort.
  7. WriteOp: a sink writing Parquet via the Phase-5 writer.
  8. Engine: wire operators by configuration; query accepts a PhysicalPlan, returns a Stream<RecordBatch> in row-major file order.

19.6 Pitfalls

  • PF29 — Operator interleaving — None means end-of-data; returning a batch after None breaks downstream (state-machine bug).
  • PF30 — The aggregate operator emits at end-of-input — all others emit per-batch; the driver must respect the exception.
  • PF31 — Float aggregation order locked across SIMD lane widths (I8, PF20 restated for the operator layer).
  • PF32 — Eager materialisation of intermediate tables between FilterOp and ProjectOp burns memory bandwidth and cache, turning a scan into a copy festival — only ProjectOp materialises (P6, ADR-12).

19.7 Performance Concerns

Fusing a pushable filter into TableScan (step 2) avoids one extra batch pass — critical at the throughput targets in §4, since every unnecessary pass over a batch costs memory bandwidth (MM2). The aggregate operator's end-of-input emission (vs. per-batch for every other operator) means its memory footprint grows with group cardinality until the spill path (Phase 6) engages — the engine must never buffer the whole input in the operator layer waiting for aggregate emission, only the partition tables. TopK's heap-based approach avoids the full-sort cost (O(n log k) vs O(n log n)) whenever k is small relative to row count, the common case for "top N" queries.

19.8 Edge Cases

  • An empty input table (zero row groups) produces a None immediately, not a batch with zero rows followed by None — the two are semantically different for aggregate initial-value handling.
  • AggregateOp with an empty group-by list (a single global aggregate) emits exactly one output row, even over zero input rows (e.g., count() = 0, sum() = NULL).
  • TopK with k larger than the total row count returns all rows sorted, not an error.
  • SortOp on a column containing NULL places nulls consistently first-or-last per a documented convention, never per whatever the underlying sort algorithm happens to do.
  • WriteOp receiving a batch whose schema does not match the target table's declared schema fails before any bytes are written (mirrors SchemaMismatch, I13).

19.9 Failure Analysis

An operator violating the None-terminates-the-stream contract (PF29) manifests as a downstream operator processing a phantom batch — detected by the operator-after-None conformance fixture, contained because the engine's RecordBatchStream wrapper asserts the invariant at the type level in debug builds. A pushdown-bytes regression (the engine reading more bytes than predicted) is detected by the pushdown-bytes fixture drifting outside the 1% band — root-caused by walking back through the four pushdown levels (§8.3) to find which level failed to prune. A WriteOp schema mismatch slipping through would corrupt the target table's Parquet footer statistics — prevented by the pre-write schema check, never caught after the fact.

19.10 Operational Notes

Spans wrap each operator's batch loop; metrics: operator_batches_total{op}, scan_rowgroups_pruned_total, scan_bytes_read_total, aggregate_emit_total. 20. Phase 9 — Index and Statistics

The index and statistics layer sits beside the engine. The index is what the codec consults during pushdown; the statistics are what the planner consumes.

20.1 Objectives

Implement zone maps, Bloom filters (consumed from rank 72), the inverted index (consumed from rank 80), the statistics (min/max/null/HLL), the histogram (consumed from rank 54), and the four-level pushdown. Constraint introduced: a Bloom "yes" is never treated as definitive (I9) — every pushdown level that can only say "maybe" must fall through to a value-level verification.

20.2 Detailed Implementation Steps

Applies P5 (pushdown), P8 (write-path stats), P12 (consume not vendor), I9 (Bloom yes is probabilistic), ADR-09/10/14/15/16. HLL p=14 from the rank-72 primitive; equi-height histograms from rank 54.

20.6 Pitfalls

  • PF33 — Interpreting a Bloom "no" too strongly is fine; treating "yes" as definitive is the bug — always verify values (I9).
  • PF34 — HLL state is per-column-chunk, not per-page (per-page is too coarse and too expensive).
  • PF35 — The inverted index is opt-in; the default is none.
  • PF36 — Recomputing statistics on the read path instead of trusting write-path stats turns every scan into a full scan and defeats pushdown (P8, I12).
  • PF37 — Vendoring a copy of the Bloom filter / inverted index / histogram primitive instead of consuming the published crate forks the primitive and drifts from the upstream the conformance suite assumes (P12).

20.7 Performance Concerns

The four pushdown levels are ordered cheapest-to-most-expensive: zone map (footer-resident, no I/O) → column index (footer-resident, no I/O) → Bloom filter (one page fetch, probabilistic) → inverted index (one or more posting-list lookups) → kernel filter (requires the page body). BE6 derives the ≈94 ms time-to-first-row from a 7%-selective filter surviving only to level 2/3 before most pages are pruned — a bug that lets pages reach level 5 unnecessarily inflates bytes-read proportionally (BE1, BE6). HLL at p=14 costs 12 KB/chunk (BE8) — a higher precision buys a lower standard error at a linear memory cost per chunk, not worth it past the point where the histogram (not the distinct count) drives planner decisions.

20.8 Edge Cases

  • A column chunk with no Bloom filter written (ADR-07's cardinality heuristic decided against it) must still correctly fall through to zone-map/column-index-only pruning, not error.
  • A predicate that is not an equality (e.g., a range) never consults the Bloom filter at all — Bloom only answers membership queries.
  • An inverted-index posting list referencing a row offset beyond the column chunk's row count (corrupt index) is rejected as InvalidParquet, never used to seek out of bounds.
  • HLL merge across row groups (for a whole-file distinct estimate) uses the sketch's own merge operation, never naive summation, or the estimate is wrong by construction.
  • A histogram sidecar file missing or stale for a table whose Parquet file has been rewritten falls back to footer-only statistics for planning, never blocks the scan.

20.9 Failure Analysis

A Bloom-filter parsing bug that produces spurious "no" answers would silently under-return rows (a correctness bug, not just a performance one) — contained by the conformance bucket comparing pushdown-pruned output against a full-scan baseline on every fixture, so any level's over-pruning is caught before merge. bloom_false_positive_total rising in production is expected (Bloom is probabilistic) and not itself a bug; what would be a bug is bloom_false_positive_total correlating with wrong query results, which the value-verification step (I9) is specifically designed to prevent. A stale rank-72/80/54 dependency version drifting from what the conformance suite assumes (PF37's failure mode) is caught by pinning exact versions in the workspace Cargo.toml (Phase 1) and re-running the index bucket on every dependency bump.

20.10 Operational Notes

Un-defer trigger for the rank-72/80/54 dependencies is each portfolio project reaching Done (Deferred Features Register) — until then this phase's index/stats surfaces run in a reduced mode with those specific indexes absent, degrading pushdown precision but never correctness.

    pub async fn append(&mut self, batch: RecordBatch) -> Result<(), Error>;
    pub async fn upsert(&mut self, batch: RecordBatch, key: &[Arc<str>]) -> Result<(), Error>;
    pub async fn delete(&mut self, batch: RecordBatch, key: &[Arc<str>]) -> Result<(), Error>;
    pub async fn flush(&mut self) -> Result<FlushReport, Error>;
}
  1. Buffer incoming batches; flush to a new Parquet file (Phase 5 writer) when any threshold (rows/bytes/seconds) is crossed.
  2. upsert/delete require a key; without a key, an update is delete-then-insert.
  3. CDC: Full emits every change as a (op, key, before, after) record into a separate Arrow IPC stream (Phase 5); Compact coalesces multiple updates to the same key within the flush window into one tuple (before = original, after = final).
  4. CDC ordering is flush-time, not event-time; consumers needing event-time order carry their own sequence number.

22.3 Deliverable

colstore-stream (ingest, cdc, writer) compiled; a runnable examples/streaming-ingest.rs demonstrating an append/upsert/delete sequence flushed to Parquet with a consumable CDC stream.

22.4 Acceptance Criteria

The sink writes Parquet at the configured cadence (rows/bytes/seconds threshold, whichever crosses first); the CDC stream is consumable as Arrow IPC; an (insert, update, delete) sequence produces the expected final table state exactly matching corpora/stream/append.json; bounded-memory ingest is verified (buffer never exceeds flush_bytes before a flush is triggered).

22.6 Pitfalls

  • PF41 — The flush window is not a transaction — concurrent readers may see a partially-flushed state (best-effort, F10).
  • PF42 — CDC ordering is flush-time, not event-time.
  • PF43 — Update without a key is delete-then-insert; upsert requires a key.

22.7 Performance Concerns

The flush thresholds (1M rows / 256 MiB / 60 s, Appendix C) trade ingest latency (how fresh a written file is) against write amplification and small-file proliferation (too-frequent flushes produce many small Parquet files, hurting later scan throughput per BE1–BE2's page/row-group math). Compact CDC mode trades a coalescing pass (extra CPU per flush window) for a smaller CDC stream — worth it whenever the same key updates multiple times per window, a common pattern for high-churn dimension tables. Buffering incoming batches in Arrow form (not re-encoding until flush) avoids a double-encode cost, deferring the Phase 3 encoding work to exactly once per flush.

22.8 Edge Cases

  • A flush triggered by the flush_seconds timer with zero buffered rows is a no-op, not an empty Parquet file write.
  • delete for a key never seen by this sink (no matching row in the target table or buffer) is a no-op, not an error — the key may have been deleted by a prior flush already visible on disk.
  • A CDC Compact window where a key is inserted then deleted before any flush produces zero CDC records for that key (net effect is nothing), not an insert-then-delete pair.
  • Process crash mid-buffer (before a flush) loses the buffered-but-unflushed rows — this is the documented RPO (≤ flush window, §4), not a bug to fix in this phase.
  • A batch appended with a schema different from the target table's schema is rejected before buffering, not silently coerced.

22.9 Failure Analysis

A partial-flush visible to a concurrent reader (F10) is expected behavior at this phase's contract (best-effort ingest, P9) — detection is a reader observing a row count that briefly does not match either the pre- or post-flush state; this is documented, not paged on, and the lakehouse phase (Phase 12) is the eventual fix via snapshot isolation. A CDC compaction bug (failing to coalesce correctly) is caught by the cdc-compact.json fixture before it reaches a downstream CDC consumer, where it would otherwise cause duplicate or missing change events — a correctness class of bug for any consumer building a materialised view off the CDC stream. Buffer-bytes exceeding flush_bytes without triggering a flush (a threshold-check bug) is caught by the bounded-memory ingest test; in production it would degrade toward the same OOM class as Phase 2's cache/operator conflation (PF4), so it is monitored via the same ingest_buffer_bytes metric family.

22.10 Operational Notes

Metrics: ingest_rows_buffered, ingest_flush_total, cdc_records_emitted_total, ingest_buffer_bytes; spans wrap each flush. RPO for the streaming path is bounded by the flush window (default 60 s, §4) — an operator sizing the ingest SLA reads this metric family directly rather than assuming durability guarantees the engine does not provide.

23.6 Pitfalls

  • PF44 — Snapshot isolation is non-trivial atop a flat-file table; lean on the table-format metadata.
  • PF45 — Manifest/transaction-log writing is the larger commitment (deferred write path).
  • PF46 — Treating a stretch-goal read path as production-ready — the write path (snapshots/manifests) remains deferred and the read path alone does not guarantee cross-engine consistency semantics.

23.7 Performance Concerns

Following the Iceberg manifest list to the manifests is an extra round of metadata I/O before any data page is touched — for a table with many small snapshots this metadata-read cost can rival the eventual scan cost, so the reader caches resolved manifests per snapshot id rather than re-walking the list per query. Delta's _delta_log/ reconstruction similarly costs O(log entries since last checkpoint) — a table without periodic checkpointing degrades linearly with log length, a cost this phase inherits rather than controls.

23.8 Edge Cases

  • A Delta table with no checkpoint yet (very early in its log) must reconstruct from the full log, not assume a checkpoint exists.
  • An Iceberg manifest list referencing a manifest file that has since been garbage-collected by a retention policy fails typed, not with a generic I/O error the operator cannot triage.
  • A snapshot id requested that predates the table-format's retention window is a distinct error from "snapshot never existed."
  • Concurrent Iceberg/Delta writers external to this engine advancing the table between this reader's manifest-list read and its data read is read-then-stale, not a torn read — the reader's snapshot id pins a consistent view throughout.

23.9 Failure Analysis

A read that silently falls back to the latest snapshot when the requested one is stale/missing would violate the caller's expectation of a pinned view — prevented by returning a typed error instead (the stale-snapshot fixture verifies this); blast radius of getting this wrong is every time-travel-style query silently reading the wrong data. Since the write path is deferred, no lakehouse-specific write failure mode exists yet at this phase — the only failure surface is read-path metadata resolution, contained entirely within colstore-iceberg and never touching the core engine's invariants (§7).

23.10 Operational Notes

Metrics: lakehouse_snapshot_opens_total, lakehouse_manifests_read_total; spans wrap snapshot resolution. This phase's crate ships off-by-default (Appendix D); an operator enabling it should expect read-only lakehouse interop and confirm the write path's PhaseDeferred status in the Deferred Features Register before depending on write-through behavior.

24. Phase 13 — Conformance Suite

The contract between the engine and the upstream Arrow / Parquet ecosystem; the gate every release passes.

24.1 Objectives

Implement the conformance runner and buckets, emit a conformance.report.json, and wire it into CI as a merge gate. Constraint introduced: a bucket may never report Pass without at least one fixture backing it — the runner itself is guarded against this class of bug.

24.2 Detailed Implementation Steps

Formalises the Required Reading (§5) interface clauses into runnable buckets, operationalising I5 (round-trip), I7 (lane parity), and I10 (no panic on input) as CI-gated verdicts rather than one-off assertions. arrow-rs, parquet-mr, parquet-cpp are the references (§5).

The runner is wired into CI as a merge gate; Phase-0 buckets (arrow, parquet, ipc, tpch:q6, kernel, encoding) report Pass; Phase-1+ buckets report Deferred with a resolving blueprint_ref; a Pass bucket without a backing fixture is flagged by the pass-without-fixture probe, never silently accepted.

24.6 Pitfalls

  • PF47 — Treating Deferred as Fail — they are distinct; CI must distinguish.
  • PF48 — Forgetting to update the corpus when the format changes — corpora are versioned alongside the engine in separate commits.
  • PF49 — A handler swallowing an error and returning Pass is a sealed-tier blocker.

24.7 Performance Concerns

The conformance run itself is a CI-time cost, not a runtime cost — but a slow conformance suite (e.g., re-downloading reference corpora on every run instead of caching them) directly taxes merge velocity. Keeping corpora small and targeted (lineitem-sf001, not full-scale TPC-H) is a deliberate choice to keep the suite fast enough to run on every PR rather than nightly-only, which is what makes it viable as a hard merge gate rather than an advisory one.

24.8 Edge Cases

  • A bucket whose manifest lists zero fixtures reports Empty, never Pass — this is the Phase 1 seed state and must remain distinguishable from a bucket that has fixtures and passed them all.
  • A fixture handler that throws mid-comparison (e.g., a panic inside arrays_equal) is caught by the runner and reported as Fail with the panic message as the reason, never silently swallowed into Pass (PF49).
  • A blueprint_ref on a Deferred bucket that does not resolve to a real heading is itself a conformance-runner defect, caught the same way this blueprint's own cross-reference check catches dangling references.
  • Two fixtures in the same bucket disagreeing on expected output for the same input (a corpus authoring bug) is caught by a manifest-consistency check before the runner even executes them.

24.9 Failure Analysis

A Pass-without-fixture bug (the runner reporting success despite having nothing to verify) is the single worst class of defect this suite can contain, because it would let every other phase's regressions through silently — caught by the pass-without-fixture probe on every CI run, never deferred to a periodic audit. A swallowed-error bug (PF49) is structurally identical in effect and caught by the swallowed-error probe. A stale corpus (PF48, the format changed but the fixture did not) manifests as a Fail on an otherwise-correct implementation — distinguished from a real regression by checking the corpus's own version stamp against the engine version in the report.

24.10 Operational Notes

The report itself is the telemetry: one verdict per bucket plus an overall verdict, posted as a CI status check; conformance_buckets_pass_total / _fail_total / _deferred_total. The release gate (make release-check, Build & Release Engineering) refuses to tag a release while any Phase-0 bucket is Fail, and treats a Deferred Phase-0 bucket (one that should have graduated to Pass by release time) as a release-blocking regression too.

Scalability Analysis

  • Single-core throughput scales with kernel quality: scalar → AVX2 (≈4×) → AVX-512 (≈2× over AVX2 on i32) closes the 200 MB/s → 1 GB/s gap (M1). The bottleneck above AVX-512 is memory bandwidth, not compute (P2: zero-copy keeps bandwidth the bottleneck, not copies).
  • Multi-core scales by per-page Rayon parallelism (ADR-17): row groups and pages are independent units; a scan fans out across the Rayon pool while Tokio drives I/O. The two pools never share threads, avoiding the classic starvation.
  • Memory is bounded per scan (256 MiB, M10) and per cache tier independently (P11); the hash aggregate spills rather than growing, so cardinality does not bound by RAM (Phase 6 spill).
  • Concurrency scales to 64 concurrent scans (§4) before the memory ceiling × scan count exceeds a typical node; beyond that, scatter across nodes via Arrow Flight (P9).
  • Distributed scaling is scatter-gather only (ADR-18): a coordinator splits a scan across nodes by row group and merges; joins/shuffles are explicitly out of scope and belong to a separate project.
  • Data volume scales with row-group count: pushdown prunes whole row groups before any I/O on the body (P5), so query latency tracks the matching data, not the total.

Mental Models & First Principles

MM1 — Arrow buffers are the unit of ownership; record batches are the unit of work. Predicts: every API either takes/returns a batch or operates on a buffer pointer — there is no third granularity. Bug class without it: mixing row-at-a-time and batch-at-a-time code, which boxes values and defeats SIMD. Applied: P1, P3, Phase 4, Phase 6.

MM2 — Memory bandwidth, not instruction count, is the scan bottleneck. Predicts: the win from AVX-512 is bounded by how few bytes you touch, so zero-copy decode and pushdown matter more than clever kernels. Bug class: optimising the kernel while eagerly copying every page. Applied: P2, P5, Scalability Analysis, Phase 5/6.

MM3 — A Parquet file is a structured access path, not a blob. Predicts: the column index, offset index, and Bloom pages let you read the matching data, not the whole file; bytes-read is predictable. Bug class: whole-file scans when the index would have pruned 90% of it. Applied: P5, Phase 5, Phase 9, PF19.

MM4 — Late materialisation turns a query into selection-vector propagation. Predicts: only ProjectOp touches column bytes; filters move bitmaps. Bug class: materialising intermediate tables and burning cache. Applied: P6, Phase 7, Phase 8.

MM5 — Determinism is a property you design in, not test in. Predicts: lock the float summation order once (pairwise) and every lane agrees; you never chase a lane-dependent diff. Bug class: AVX2 and AVX-512 producing different sums on the same input. Applied: P10, I7, I8, Phase 6.

MM6 — The page cache budget and the operator budget are different budgets. Predicts: you can size the cache for I/O amortisation and the operators for working set independently, and neither starves the other. Bug class: OOM under concurrency from conflating them. Applied: P11, Phase 2, §4, PF4.

MM7 — A Bloom "no" is information; a Bloom "yes" is not. Predicts: you prune on "no" and always verify on "yes" — the index never short-circuits a correctness check. Bug class: skipping a page because the Bloom said "yes". Applied: I9, Phase 9, PF33.

MM8 — Statistics are a write-path artefact you trust on read. Predicts: the read path never scans to estimate; it trusts the file (with a hash check) and only recomputes when the file declares stats absent. Bug class: every scan degenerating into a full scan. Applied: P8, I12, Phase 5, Phase 9.

MM9 — Dispatch in one place; the call site is blind to the backend. Predicts: adding a GPU backend is a registry change, not an operator change. Bug class: SIMD-level branches scattered across call sites, making parity untestable. Applied: P4, Phase 6, Stretch (GPU).

MM10 — The smallest engine that teaches the full surface is the right scope. Predicts: dropping transactions, SQL, and distributed joins is what makes the 5–7 month timeline real. Bug class: scope creep into a database. Applied: §1, §2, P9, ADR-23.

Back-of-Envelope Capacity Model

Derived step-by-step from the §4 System Constraints table.

BE1 — Pages per 256 MiB Parquet file. page_size = 1 MiB ⇒ 256 MiB / 1 MiB = 256 pages per file (per column chunk it is fewer; per file across columns ≈ 256).

BE2 — Row groups per file. row_group = 128 MiB ⇒ 256 MiB / 128 MiB = 2 row groups per 256 MiB file.

BE3 — Rows per row group (lineitem, ~150 B/row uncompressed, 10:1 compressed → 15 B/row on disk). 128 MiB / 15 B ≈ 8.9 M rows per row group on disk.

BE4 — Scan time, Phase-0 (200 MB/s). 256 MiB / 200 MB/s ≈ 1.34 s to read the file body cold; Phase-1 at 1 GB/s ⇒ 0.26 s (M1).

BE5 — Page-decode budget per file. 256 pages × p50 1.5 ms = 0.38 s decode at p50; at p99 12 ms the tail page costs 12 ms — so decode overlaps I/O via prefetch (depth 4).

BE6 — Pushdown win. If a filter matches 7% of pages (Appendix B.1), bytes read ≈ 0.07 × 256 MiB = 17.9 MiB ⇒ scan time ≈ 17.9 MiB / 200 MB/s ≈ 94 ms, under the §4 time-to-first-row 100 ms target.

BE7 — Page cache residence. 256 MiB cache / 1 MiB page = 256 hot pages if all hot, or more cold compressed pages (≈ 2,560 at 10:1) — the cache holds roughly one full file hot or ten files cold.

BE8 — HLL state per file. p=14 ⇒ 2^14 registers × 6 bits ≈ 12 KB/chunk × (columns); for 16 columns × 2 row groups = ≈ 384 KB of HLL state per file (ADR-09).

BE9 — Concurrent scan memory. 64 scans × 256 MiB ceiling = 16 GiB worst case ⇒ a 64-scan node needs ≥ 16 GiB just for operators (the §4 concurrency × M10 ceiling); this is why 64 is the cap.

BE10 — Hash aggregate partitions. 256 radix partitions; spill at 16 MiB/partition ⇒ in-memory aggregate holds up to 256 × 16 MiB = 4 GiB before everything spills — within the per-scan budget only for low cardinality, hence the spill path (Phase 6).

BE11 — FD budget headroom. ≤ 1024 FDs; 64 Flight streams + object-store handles (pooled) leaves ≈ 900 FDs for open files — comfortable for a 2-row-group-per-file layout.

BE12 — Vector dispatch count for a Q6 scan. 8.9 M rows/row group ÷ 4096 vector = ≈ 2,173 kernel dispatches per row group per column — amortising dispatch cost across the batch (ADR-05).

Alternative Architectures (Roads Not Taken)

A1 — Row-at-a-time Volcano iterator engine.

Scan.next() -> row -> Filter.next() -> row -> Project.next() -> row -> ...

Wins when: the data is tiny, queries are point lookups, and per-row overhead is irrelevant (OLTP-flavoured). Embodied by: classic Volcano (PostgreSQL executor heritage). Rejected because: it boxes values, defeats SIMD, and collapses analytical throughput an order of magnitude (P3, MM1).

A2 — Whole-column eager materialisation (MonetDB BAT model).

Filter(col) -> full materialised col -> Project(col) -> full materialised col -> ...

Wins when: memory is abundant, selectivity is ~100%, and operator composition simplicity matters more than bandwidth. Embodied by: MonetDB's BAT algebra. Rejected because: eager materialisation burns memory and cache; late materialisation via selection vectors is the bandwidth-optimal default (P6, ADR-12, MM4).

A3 — Bespoke in-memory format with a translation layer at the Arrow boundary.

Disk -> bespoke columnar -> [translate] -> Arrow only at the API edge

Wins when: you need a layout Arrow cannot express (e.g. a PAX hybrid for mixed point/scan workloads) and own every consumer. Embodied by: ClickHouse's MergeTree blocks. Rejected because: it forces a copy at every interop point and is a four-month detour with no payoff for an interop-first engine (P1, ADR-02, PF14).

A4 — JIT/codegen execution (compile each query to native code).

PhysicalPlan -> LLVM IR -> native fn -> run over batches

Wins when: queries are long-running and codegen latency amortises, or expression trees are deep. Embodied by: DuckDB's late codegen, Photon's generated kernels, Hyper. Rejected (for Phase 0) because: interpretation over vectorised kernels reaches the throughput target without query-time compile latency; codegen is a Stretch goal once the interpreted path is correct (MM9, Stretch).

Glossary

  • Arrow: the Apache Arrow columnar format; the in-memory layout used end to end.
  • Parquet: the Apache Parquet file format; the on-disk layout read and written.
  • ORC: the Apache ORC file format; read-only here.
  • Record batch: a contiguous slice of rows across a fixed schema, materialised as a vector of arrays.
  • Row group: a horizontal partition of a Parquet file, default ~128 MiB.
  • Column chunk: the bytes of a single column within a single row group.
  • Page: a sub-unit of a column chunk (~1 MiB); the granularity of compression and the column index.
  • Dictionary page: the first page of a dictionary-encoded column chunk, holding the distinct values.
  • Bloom filter page: an optional page holding a Bloom filter over the column chunk's values.
  • Zone map: per-row-group min / max / null-count statistics in the Parquet footer.
  • Column index: per-page min / max statistics; the fast pushdown path.
  • Offset index: per-page byte offsets; the prefetch and seek path.
  • Selection vector: a bitmap (dense or Roaring) over row indices that survive a filter.
  • Late materialisation: producing selection vectors before materialising columns.
  • Vector size: rows processed per kernel call; default 4096.
  • Pushdown: pushing predicates below the operator boundary into scan, page index, and Bloom filter.
  • Zero-copy decode: producing an Arrow array directly over page bytes without copying.
  • HyperLogLog (HLL): a probabilistic distinct-count sketch; here p=14.
  • Equi-height histogram: a partition of the value domain into equal-row-count buckets.
  • Frame-of-reference (FOR): encode values as deltas from a per-page reference.
  • Delta-binary-packed: Parquet's second-order delta encoding for monotone keys.
  • Zigzag-varint: signed→unsigned mapping then LSB-first 7-bit varint packing.
  • Bit-packing: packing n values of b bits into a contiguous buffer; LSB-first in Parquet.
  • RLE/hybrid: Parquet's run-length / bit-packed hybrid for booleans and dictionary indices.
  • Radix-partitioned hash aggregate: partition rows by hash bits, aggregate per partition, spill, merge.
  • Spill: writing a partition to disk (Arrow IPC) when it exceeds a memory threshold.
  • Three-valued logic (Kleene): AND/OR/NOT semantics over nullable booleans.
  • Selectivity: the fraction of rows surviving a filter.
  • Arrow IPC: the Arrow stream/file serialisation; the spill and Flight wire format.
  • Arrow Flight: the Arrow gRPC surface for streaming record batches.
  • DoGet / DoPut / GetFlightInfo: the Flight RPCs the engine implements.
  • Iceberg: a table-format metadata layer over Parquet providing snapshots and schema evolution.
  • Delta Lake: an alternative table-format metadata layer over Parquet.
  • CDC: change-data-capture; a stream of (op, key, before, after) records.
  • Physical-plan IR: the operator-tree input the engine executes (no SQL).
  • Kernel registry: the single place runtime SIMD dispatch is decided.
  • Kernel level: scalar / AVX2 / AVX-512 / NEON, detected at startup.
  • Zone-map prune: skipping a row group whose min/max cannot match the predicate.
  • Page-index prune: skipping a page whose min/max cannot match.
  • Conformance bucket: a named group of fixtures verified against a reference implementation.
  • Verdict: a bucket's outcome: Pass / Fail / Deferred / Empty.
  • PhaseDeferred: the typed error marking a legibly-deferred surface.
  • TPC-H: the canonical analytical benchmark; targets Q1, Q3, Q6, Q12.
  • Scatter-gather scan: the only distributed primitive — split a scan across nodes and merge.

Appendix B.1 — Worked example: Q6-shaped query, end to end

The query: SELECT l_orderkey, sum(l_quantity) FROM lineitem WHERE l_shipdate BETWEEN '1994-01-01' AND '1994-12-31' AND l_discount BETWEEN 0.05 AND 0.07 AND l_quantity < 24 GROUP BY l_orderkey. The engine receives it as a PhysicalPlan (an Aggregate over a Filter over a Scan with projection [l_orderkey, l_quantity, l_shipdate, l_discount] and the conjunctive filter). Execution: (1) the Scan reads the footer and column index; (2) zone maps prune row groups whose l_shipdate range misses; (3) the column index prunes pages whose l_shipdate/l_discount/l_quantity ranges miss; (4) surviving pages are fetched (prefetch), decompressed, decoded — l_shipdate decodes zero-copy as a dictionary array; (5) the Scan emits batches over the projected columns; (6) the Filter runs the AVX2 lt_f64 / between_date32 kernels and produces a selection vector; (7) the Aggregate hashes l_orderkey, radix-partitions into 256, updates per-partition sum(l_quantity); (8) at end-of-input the partitions merge and a single result batch emits. Four-level pushdown is visible at steps 2 (zone map), 3 (column index), 4 (dictionary-aware decode), 6 (kernel filter). The corpus conformance/corpora/engine/tpch-q-walked.json carries the expected bytes-read per step; the Phase-0 baseline reads ≈ 7% of the lineitem column bytes (Capacity #6) and produces the expected aggregate output.
