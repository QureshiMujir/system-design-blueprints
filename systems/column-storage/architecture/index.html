Frontends. The externally visible boundary: the embedded API (the Engine handle and the physical-plan IR), the colstore CLI driver, and the Arrow Flight gRPC server. All three are thin drivers over the execution engine; none holds query state of its own.

Execution Engine. The operator tree. Each operator is a Scan (produces batches), a Sink (consumes batches), or a Pipeline (both). The engine wires operators by configuration and pushes Arrow record batches through them. Late materialisation (selection vectors) and predicate pushdown are the load-bearing disciplines here.

Statistics & Stats Sketches. Produced on the write path: min / max / null count, HyperLogLog distinct count, equi-height histograms. Consumed by the planner (external) and by the pushdown layer. Never recomputed on the read path unless the file declares them missing.

Index. Zone maps (per row group), Bloom filters (per column chunk and per page), inverted index (per opt-in string column). The codec consults the index during pushdown; the index never reaches into the codec.

Compute Kernels. The SIMD hot path. One trait-bound kernel per operation; runtime dispatch to scalar / AVX2 / AVX-512 / NEON from a single registry. Operators never branch on SIMD level.

In-Memory Layer. Arrow record batches are the unit of work; Arrow buffers are the unit of ownership. Decode produces Arrow buffers directly. Slicing and projection are zero-copy.

Parquet Codec. Writer and reader interoperable with parquet-mr and parquet-cpp. Zero-copy decode where the layout permits; streaming decode otherwise. ORC reader is read-only and structurally parallel.

Storage Layer. The ObjectStore abstraction (local, s3, gcs, azure), the two-tier page cache, the prefetch queue, and the I/O scheduler that merges adjacent small reads.

Three architectural properties recur throughout. First, the data path is one-way: bytes flow up from storage through the codec into Arrow buffers; pushdown predicates flow down from the engine through the codec into the page reader. Second, the kernel layer is backend-agnostic: the engine never branches on SIMD level at the call site. Third, every cross-cut (statistics, indexes, compression, allocator) is owned by the layer that produces it and exposed by trait-bound calls everywhere else; you never reach across layers.

8. Domain Model / Data Model

The engine's domain is the columnar table: a schema (ordered, named, typed, nullable fields) over a sequence of record batches, persisted as one or more Parquet files (or Arrow IPC streams), each file partitioned into row groups, each row group holding one column chunk per column, each column chunk a sequence of pages.

8.1 The layered data model

Table  ─┬─ Schema (Vec<Field>)
        └─ Files ─┬─ Parquet File ─┬─ Footer (FileMetaData, column/offset index)
                  │                └─ RowGroup* ─ ColumnChunk* ─ Page* (dict | data | bloom | index)
                  └─ Arrow IPC ─ Schema msg ─ RecordBatch msg*
In memory: RecordBatch ─ ArrayRef* ─ (Buffer values, Option<Validity>, Offsets?)

8.2 Worked example — one column chunk, end to end

Column l_shipdate (Date32, non-null), one row group of 1,048,576 rows. The writer sorts nothing but observes the column is low-cardinality (≈ 2,500 distinct dates over the data window), so it dictionary-encodes: a dictionary page lists the 2,500 distinct i32 day-counts once; data pages hold RLE/bit-packed indices (12 bits each). Per-page statistics record min/max day-count; the column chunk records min/max/null-count and an HLL distinct estimate (≈ 2,500). A Bloom filter is not written (cardinality < the 1024-equality-pushdown heuristic is false here, but dictionary + zone map already prune efficiently; ADR-07). On read, a predicate l_shipdate BETWEEN '1994-01-01' AND '1994-12-31' is checked against the column-chunk zone map (intersects → keep), then each page's min/max (prune pages outside the window), then the surviving pages decode zero-copy into an Arrow DictionaryArray<Int32, Int32> and the filter kernel runs against the dictionary indices.

8.4 Malformed-input and failure-path catalogue

  • Footer magic wrong (PAR1 missing at head or tail) → InvalidParquet("bad magic"); never attempt to parse the Thrift.
  • Footer length exceeds file size → OutOfRange; refuse to seek.
  • Dictionary index ≥ dictionary length → InvalidEncoding; do not index out of bounds (I10).
  • Validity bitmap length disagrees with value count → InvalidArrow; reject the array (I13).
  • Delta-binary-packed header claims more values than the page holds → InvalidEncoding; bounded read, no infinite loop (Threat Model, T3).
  • Page codec = Snappy but body is zstd-framed → decompress fails → InvalidParquet (I6).
  • Flight schema contradicts table schema → SchemaMismatch before any data is accepted (I10, Phase 9).
