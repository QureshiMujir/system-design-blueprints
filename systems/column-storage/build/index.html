⬜ Phase 1 — Repository Skeleton and Governance §12

Objectives

Land the production scaffold: the crate workspace, the build/CI machinery, the governance docs, and the conformance harness wired against an empty corpus. Constraint introduced: every later phase adds code only inside an existing crate boundary from §10 — no phase may invent a new top-level crate.

Deliverable

The complete §10 tree compiled (empty crates), a green five-lane CI run, and a conformance.report.json whose every bucket verdict is Empty — inspectable via cat conformance.report.json | jq '.buckets[].verdict'.

Acceptance

make build, make typecheck, make lint each return exit 0 on placeholder code; all five .github/workflows/*.yml lanes are green on a clean checkout; the harness emits Empty for every bucket (zero Pass, zero Fail); exactly one ADR file exists per §9 row (23 files); BUILD_PLAN.md carries the Phase-0 seed row (Appendix E).

⬜ Phase 2 — Storage Layer §13

Objectives

Provide the ObjectStore abstraction, the two-tier scan-aware page cache, the prefetch queue, and the I/O scheduler that merges adjacent small reads. Constraint introduced: the page-cache budget (§4, 256 MiB default) is tracked and enforced independently of any later operator budget (P11) — this phase must not let the two merge even implicitly.

Deliverable

colstore-storage compiled with the local backend live, remote backends feature-gated behind PhaseDeferred, and a runnable microbenchmark (benchmarks/scan_speed) that exercises cache hit/miss and prefetch against a local corpus.

Acceptance

The local store round-trips put/get/delete exactly per corpora/storage/local-rw.json; the deterministic cache-load test in corpora/storage/page-cache.json reproduces the expected hit/miss sequence bit-for-bit; two concurrent readers do not interfere (parallel-readers test, zero data races under Miri/loom-style stress); the I/O scheduler's merged-range count matches the merge-reads fixture; lock_held_across_await_total is 0 across a full CI run (I11).

Fixtures
Fixture Purpose Expected
corpora/storage/local-rw.json put/get/delete sequence results match expected
corpora/storage/page-cache.json access sequence under fixed capacity hit/miss outcomes match
parallel-readers test concurrency safety two readers do not interfere
merge-reads test scheduler coalescing merged-range count matches
malformed-range fixture get_range past EOF typed OutOfRange, no panic
Pitfalls
  • PF4 — Treating the page cache as the whole memory budget: it is only the I/O-amortisation layer, independent of the operator budget (P11, MM6).
  • PF5 — Holding a sync lock across an .await — deadlock (I11).
  • PF6 — Forgetting the etag on head — S3 strong-consistency detection depends on it.

⬜ Phase 3 — Encoding and Compression §14

Objectives

Implement the seven encodings (Plain, Dictionary, RLE/bit-packed-hybrid, Frame-of-Reference, Delta-binary-packed, Zigzag-varint, Bit-packing) and the four codecs (zstd, lz4, snappy, none), each round-tripping bit-for-bit. Constraint introduced: every encoder/decoder pair must satisfy I5 before it is wired into the Phase 5 Parquet writer/reader.

Deliverable

colstore-encoding and colstore-compression compiled with all seven encodings and four codecs wired to a codec registry; a runnable cargo test -p colstore-encoding exercising the proptest sweep.

Acceptance

All seven encodings implement PageEncoder/PageDecoder; round-trip holds bit-for-bit on every primitive and variable-length dtype (I5, zero failures over ≥10,000 proptest cases); the codec registry rejects unknown variants as InvalidParquet; the compression ratio on the lineitem fixture meets the §4 10:1 target (M4).

Fixtures
Fixture Purpose Expected
corpora/encoding/plain-{i32,i64}.json round-trip per dtype decode(encode(x))==x
corpora/encoding/dict-string.json dictionary string column known dict + indices
corpora/encoding/rle-boolean.json RLE boolean known runs
corpora/encoding/delta-i64.json delta-binary-packed known sequence
proptest sweep random integer streams × all encodings round-trip holds, ≥10,000 cases
malformed-delta-header fixture oversized claimed value count typed InvalidEncoding, no allocation blowup
Pitfalls
  • PF7 — Off-by-one in the RLE/bit-packed-run decoder — most bugs trace to misreading the leading varint.
  • PF8 — Mixing LSB-first and MSB-first bit-packing (Parquet vs. legacy ORC) — the decoder must be told which.
  • PF9 — Assuming the dictionary fits in memory — the writer falls back to plain when it exceeds the threshold; the reader handles both in one chunk.
  • PF10 — Assuming a fixed default compression codec instead of reading the page header — a reader that assumes a default silently corrupts on a file written by another implementation honoring per-page codec choice (P7, I6).

⬜ Phase 4 — In-Memory Layer (Arrow) §15

Objectives

Implement the buffer types, every Arrow array type, RecordBatch, builder APIs, zero-copy slicing/projection, and the canonical arrays_equal. Constraint introduced: from this phase on, the engine holds no non-Arrow representation of column data in steady state (P1) — every later phase's data structures are built from these types, never a parallel format.

Deliverable

colstore-buffer and colstore-array compiled with every array type, builder APIs, zero-copy slice/project, and arrays_equal; a Miri-clean test run over the buffer surface.

Acceptance

Every array type implements Array; slicing is zero-copy (pointer identity preserved pre/post-slice, I3); RecordBatch::try_new rejects mismatched column lengths/types (I13); conformance vectors are bit-identical to arrow-rs across ≥1,000 generated batches (the arrow bucket); buffer_alloc_misaligned_total is 0 across the full test run (I1).

Fixtures
Fixture Purpose Expected
corpora/arrow/primitive-i32.json 16 int32 records array with known buffer SHA
corpora/arrow/string.json variable-length strings exact bytes
corpora/arrow/dictionary-string.json dict string column known dict + keys
corpora/arrow/struct.json nested struct, 2 nullable children exact structure
slice-identity test zero-copy slice underlying ptr unchanged (I3)
malformed-validity fixture bitmap length disagrees with value count typed InvalidArrow (I13)
Pitfalls
  • PF11 — Forgetting the slice offset — "validity says null but values says 42" is a sliced bitmap ignoring the offset.
  • PF12 — 64-byte alignment — Rust's default allocator does not provide it; AlignedBytes enforces it (I1).
  • PF13 — Variable-length offsets are end-exclusive with len+1 entries (I4).
  • PF14 — Building a bespoke in-memory format instead of adopting Arrow natively — forces a copy at every interop point and is a multi-month detour with no payoff (P1, ADR-02).

⬜ Phase 5 — Parquet Codec §16

Objectives

Implement a Parquet writer that emits readable files with statistics, dictionary pages, and Bloom-filter pages, and a reader that decodes the corpora with four-level pushdown and zero-copy where the layout permits. Constraint introduced: every byte the reader accepts is untrusted (I10) — no code path may panic on malformed Thrift, encodings, or page bytes.

Deliverable

colstore-parquet (writer + reader), colstore-orc (read-only reader), and colstore-ipc (stream + file) all compiled; a round-trip of the lineitem-sf001 corpus through the engine's own Parquet writer then reader, byte-identical to a round-trip through parquet-mr/parquet-cpp; docs/parquet-format.md published.

Acceptance

Round-trip correctness against parquet-mr and parquet-cpp holds both directions (the parquet conformance bucket, zero mismatches); pushdown bytes-read is within 1% of the corpus expectation (M5); every primitive and variable-length dtype plus DictionaryArray<i32, StringArray> is handled; the negative fuzz corpus produces decode_panic_total == 0 (I10, M12); the ipc bucket passes both directions.

Fixtures
Fixture Purpose Expected
corpora/parquet/lineitem-sf001.parquet TPC-H subset round-trip bit-identical to parquet-mr/-cpp
corpora/parquet/dictstring.parquet dict string column known dictionary

corpora/parquet/pushdown-eq.json filter on int64 col bytes-read within 1%

Pitfalls
  • PF15 — Mis-parsing the magic — files start and end with PAR1; the footer length is the 4 bytes before the trailing magic (§8.4).
  • PF16 — Conflating row-group size (zone-map granularity) and page size (column-index + prefetch granularity) — they are independent.
  • PF17 — Forgetting to flush page-level stats into the column index — leaves the index empty and forces whole-page reads (P8).
  • PF18 — Encrypted footers — deferred (see Deferred Features Register).
  • PF19 — Treating a Parquet file as an opaque blob instead of consulting the column index / offset index / Bloom pages before fetching page bytes — defeats the entire point of the format (P5, MM3).

⬜ Phase 6 — Vectorised Compute Kernels §17

Objectives

Implement the filter, compare, arithmetic, reduce, aggregate, and hash kernels, each with scalar / AVX2 / AVX-512 / NEON lanes producing identical output, plus the radix-partitioned hash aggregate. Constraint introduced: every kernel dispatch happens through exactly one registry (P4) — no operator or expression node may branch on SIMD level directly.

Deliverable

colstore-kernel compiled with the registry, four lane modules, six kernel families, and the radix hash aggregate; a runnable benchmarks/ kernel suite reporting per-kernel, per-lane throughput.

Acceptance

Every kernel has scalar + AVX2 + AVX-512 (where supported) + NEON (where supported) lanes; the cross-lane parity fuzz (kernels.yml) is green with kernel_lane_divergence_total == 0 (I7, M11); the hash aggregate passes TPC-H Q1 bit-for-bit modulo the locked float order (I8); the float-sum golden fixture reproduces bit-for-bit across every lane.

Fixtures
Fixture Purpose Expected
corpora/kernel/filter-eq-i32.json 4096 int32 + needle known dense bitmap
corpora/kernel/sum-f64-pairwise.json 16384 f64 bit-for-bit pairwise sum (I8)
corpora/kernel/aggregate-q1.json TPC-H Q1 input expected groups
cross-lane fuzz (kernels.yml) scalar vs AVX2/AVX-512/NEON identical output (I7)
partition-spill fixture partition > 16 MiB spill-then-merge reproduces the non-spilled result
Pitfalls
  • PF20 — Float summation order differing between lanes — lock the pairwise tree (I8, P10).
  • PF21 — Mask register width — AVX-512 has 8-bit masks for i64 lanes; preserve the lane count.
  • PF22 — Misaligned loads — buffers are 64-byte aligned but slices are not; use unaligned loads on the prefix/suffix.
  • PF23 — Branchful inner loops — compute both branches and select with a mask (IF-conversion).
  • PF24 — A row-at-a-time iterator inside a kernel or operator boxes values and defeats SIMD — collapses throughput by an order of magnitude (P3).
  • PF25 — Scattering SIMD-level dispatch decisions across call sites instead of the single registry — makes cross-lane parity untestable and lets a lane diverge silently (P4, I7).

⬜ Phase 7 — Expression Evaluator §18

Objectives

Implement the Expr IR, the tree-walking compiler with an inline cache, and the executor that produces selection vectors for filters and materialises only at project (late materialisation). Constraint introduced: the IR never inserts implicit casts (the planner above must) — the compiler errors rather than silently coercing types.

Deliverable

colstore-expr compiled with the IR, compiler, inline cache, executor, and selection-vector integration; a runnable 1000-vector proptest comparing the executor to a scalar reference loop.

Acceptance

The compiler accepts the IR and produces an executor; the executor matches a scalar reference exactly on a 1000-vector proptest (zero mismatches); late materialisation is verified — only the columns and rows a three-filter chain's selection permits are ever materialised, confirmed by the buffer-count fixture; three-valued Kleene logic matches the truth-table fixture exactly.

Fixture Purpose Expected

1000-vector proptest vs. scalar reference loop identical results

Pitfalls
  • PF26 — Three-valued logic: null AND false = false, null AND true = null, null OR true = true, null OR false = null — SQL semantics depend on it.
  • PF27 — Implicit casts — the IR does not insert them; the compiler errors on type mismatch.
  • PF28 — Integer overflow — pick the wider type or error; never silently wrap.

⬜ Phase 8 — Operators and the Engine §19

Objectives

Implement the operators (TableScan, Filter, Project, Aggregate, Sort, TopK, Write) and the engine that executes a physical-plan IR and returns a stream of batches. Constraint introduced: only ProjectOp materialises (P6) — every other operator propagates selection vectors or passes batches through unmodified.

Deliverable

colstore-engine compiled with all seven operators, the engine driver, and the embedded-API surface; a runnable end-to-end execution of TPC-H Q1/Q3/Q6/Q12 against the lineitem-sf001 corpus.

Acceptance

The engine executes TPC-H Q1/Q3/Q6/Q12 end-to-end against the corpus with output rows matching the golden fixtures exactly; pushdown reads only the permitted row groups/pages/bytes (within 1% of prediction, M5); the aggregate passes Q1 bit-for-bit modulo the locked float order (I8); TPC-H Q6 meets the §4 wall-clock target (M2).

Fixtures
Fixture Purpose Expected
corpora/engine/tpch-q1.json Q1 over lineitem-sf001 expected output rows
corpora/engine/tpch-q6.json Q6 expected output rows
corpora/engine/pushdown-bytes.json indexed-column query bytes-read count matches
Appendix B.1 walked query end-to-end pushdown ≈7% of column bytes read
operator-after-None fixture state-machine violation rejected before it reaches the driver
Pitfalls
  • PF29 — Operator interleaving — None means end-of-data; returning a batch after None breaks downstream (state-machine bug).
  • PF30 — The aggregate operator emits at end-of-input — all others emit per-batch; the driver must respect the exception.
  • PF31 — Float aggregation order locked across SIMD lane widths (I8, PF20 restated for the operator layer).
  • PF32 — Eager materialisation of intermediate tables between FilterOp and ProjectOp burns memory bandwidth and cache, turning a scan into a copy festival — only ProjectOp materialises (P6, ADR-12).

⬜ Phase 9 — Index and Statistics §20

Objectives

Implement zone maps, Bloom filters (consumed from rank 72), the inverted index (consumed from rank 80), the statistics (min/max/null/HLL), the histogram (consumed from rank 54), and the four-level pushdown. Constraint introduced: a Bloom "yes" is never treated as definitive (I9) — every pushdown level that can only say "maybe" must fall through to a value-level verification.

Deliverable

colstore-index (zone map, bloom, inverted, pushdown) and colstore-stats (min_max, null_count, hll, histogram) compiled; a runnable four-level pushdown demonstration against lineitem-sf001 with docs/pushdown-design.md published.

Acceptance

Four-level pushdown is correct on lineitem-sf001 for a high-cardinality equality predicate; bytes-read is within 1% of the index prediction (M5); the HLL distinct estimate is within the documented standard error (0.81% at p=14, ADR-09); the rank-72/80/54 dependencies are consumed as external crates (or deferred behind PhaseDeferred if not yet built, P12).

Fixtures
Fixture Purpose Expected
corpora/index/zonemap-prune.json row-group prune known surviving set
corpora/index/bloom-prune.json Bloom prune known surviving set
corpora/index/inverted-substring.json substring search resolved without column body
corpora/stats/hll-distinct.json distinct estimate within HLL standard error
bloom-false-positive fixture Bloom says "yes", value absent page fetched and value-verified, not trusted
Pitfalls
  • PF33 — Interpreting a Bloom "no" too strongly is fine; treating "yes" as definitive is the bug — always verify values (I9).
  • PF34 — HLL state is per-column-chunk, not per-page (per-page is too coarse and too expensive).
  • PF35 — The inverted index is opt-in; the default is none.
  • PF36 — Recomputing statistics on the read path instead of trusting write-path stats turns every scan into a full scan and defeats pushdown (P8, I12).
  • PF37 — Vendoring a copy of the Bloom filter / inverted index / histogram primitive instead of consuming the published crate forks the primitive and drifts from the upstream the conformance suite assumes (P12).

Deliverable

colstore-cli and colstore-flight (server + client + proto) compiled; a runnable examples/arrow-flight-server.rs readable by a second-process client.

Acceptance

The CLI runs the TPC-H scan-heavy queries end-to-end (M2); the Flight server passes the round-trip test (corpora/flight/roundtrip.json, batch bit-identical); a second-process client reads a stream; concurrent-stream capping is verified under load (flight_streams_rejected_total rises past 64 concurrent, none silently dropped).

⬜ Phase 11 — Streaming Ingest and Delta-CDC §22

Objectives

Implement the IngestSink (append/upsert/delete/flush) with configurable flush cadence and an optional delta-CDC side stream. Constraint introduced: the flush window is best-effort, not transactional (P9) — this phase never claims snapshot isolation.

Deliverable

colstore-stream (ingest, cdc, writer) compiled; a runnable examples/streaming-ingest.rs demonstrating an append/upsert/delete sequence flushed to Parquet with a consumable CDC stream.

Acceptance

The sink writes Parquet at the configured cadence (rows/bytes/seconds threshold, whichever crosses first); the CDC stream is consumable as Arrow IPC; an (insert, update, delete) sequence produces the expected final table state exactly matching corpora/stream/append.json; bounded-memory ingest is verified (buffer never exceeds flush_bytes before a flush is triggered).

Fixtures
Fixture Purpose Expected

corpora/stream/cdc-compact.json upsert sequence expected coalesced CDC stream

Pitfalls
  • PF41 — The flush window is not a transaction — concurrent readers may see a partially-flushed state (best-effort, F10).
  • PF42 — CDC ordering is flush-time, not event-time.
  • PF43 — Update without a key is delete-then-insert; upsert requires a key.

⬜ Phase 12 — Iceberg / Delta Lake Integration (stretch) §23

Objectives

Read Iceberg and Delta tables into the engine's Table abstraction keyed by snapshot/version; write through the IngestSink to a new snapshot/version. Constraint introduced: the write path (manifests/transaction-log entries) stays behind PhaseDeferred for this stretch phase — only the read path is a Phase-0 deliverable.

Deliverable

colstore-iceberg (iceberg + delta read paths) compiled behind feature flags, off by default; a read round-trip against a Spark-produced fixture of each format.

Acceptance

A Spark-produced Iceberg table and a Delta table both read identically to the engine (row-for-row, schema-for-schema); the write path remains behind PhaseDeferred and is registered in the Deferred Features Register; enabling the feature flag before the underlying table-format crate is available fails at construction, not at first query.

Pitfalls

⬜ Phase 13 — Conformance Suite §24

Objectives

Implement the conformance runner and buckets, emit a conformance.report.json, and wire it into CI as a merge gate. Constraint introduced: a bucket may never report Pass without at least one fixture backing it — the runner itself is guarded against this class of bug.

Deliverable

colstore-conformance (runner + buckets + report), report_schema.json, and the corpora directories all compiled and wired into conformance.yml; a runnable conformance.report.json produced on every CI run.

Acceptance

The runner is wired into CI as a merge gate; Phase-0 buckets (arrow, parquet, ipc, tpch:q6, kernel, encoding) report Pass; Phase-1+ buckets report Deferred with a resolving blueprint_ref; a Pass bucket without a backing fixture is flagged by the pass-without-fixture probe, never silently accepted.

Fixtures
Fixture Purpose Expected

Pitfalls
  • PF47 — Treating Deferred as Fail — they are distinct; CI must distinguish.
  • PF48 — Forgetting to update the corpus when the format changes — corpora are versioned alongside the engine in separate commits.
