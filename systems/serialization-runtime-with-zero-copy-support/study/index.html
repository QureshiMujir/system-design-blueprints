Hard Questions (Self-Examination)

Q1. If a caller caches a Reader<'a, T> across the buffer's lifetime, Rust's borrow checker prevents the bug. But what happens with raw FFI callers that bypass lifetime tracking — which invariants in §7 prevent use-after-free? Answer synthesizes: §7.2 Validation Trust Boundary (the validated buffer must outlive all readers — contract enforced by caller, not runtime) + §6.8 Safe Abstractions Over Unsafe Internals (I5: no Reader is created without a valid validated message reference; FFI callers must honor the equivalent of 'a lifetime explicitly). The buffer-outlives-reader contract is an FFI caller responsibility, not a runtime enforcement. The spec must document this explicitly.

Q2. The canonical encoding mode (P5, §8.15 Canonical Encoding) guarantees byte-identical output for logically-equal messages. But what does "logically equal" mean for a union type where the active arm has different padding in different schema versions? Answer synthesizes: §6.4 Append-Only Schema Evolution (reserved holes preserve layout) + §8.11 Schema Evolution Worked Example (canonical form is defined per writer schema — two messages encoded under different schema versions may be logically equal under the application model but not byte-identical under canonical encoding). The canonical guarantee is per-schema-version, not cross-version.

Q3. The amplification defense (§6.5) caps traversal at MAX_TRAVERSAL_WORDS. But far pointers (§8.2) can form a chain — can a chain of N far pointers all within the word budget still cause O(N) heap allocations? Answer synthesizes: §8.2 Wire Format far-pointer spec (far pointer resolution follows one indirection — double-far pointer follows exactly two hops, not a chain) + §6.5 Bounded Resource Usage (each hop visits exactly 2 words — the landing pad; total work = 2 × number_of_far_ptrs ≤ MAX_TRAVERSAL_WORDS). Far pointers cannot chain beyond double-far; there is no "chain of N far pointers." The spec must document this explicitly to prevent implementation confusion.

Q4. The schema hash (ADR-08) uses xxHash3, which is non-cryptographic. A malicious schema server could send a crafted schema with the same hash as a legitimate one. What defense exists, and when is SHA-256 required? Answer synthesizes: ADR-08 (xxHash3 for non-crypto use; SHA-256 for security boundaries) + §7.2 Validation Trust Boundary (schema hash is a compatibility identifier, not a capability token; the trust model assumes the schema registry is trusted infrastructure). If the registry is untrusted (public internet, adversarial tenants), the schema hash becomes a security boundary and SHA-256 is required. ADR-08 explicitly calls this out as the "When the Rejected Choice Wins" case.

Q5. ListReader::get(idx) is bounds-checked against count (Phase 5). But the validation pass already confirmed list bounds. Is this a double-check, and does it violate the zero-copy / no-redundant-work design principle? Answer synthesizes: §7.2 Validation Trust Boundary (validation establishes that all element offsets are in-bounds; post-validation accessor reads are total) + §6.2 Zero-Copy by Default (accessor bounds check against count is an index-out-of-range guard, not a buffer-bounds guard). The validation pass proves buffer bounds; the accessor's count check proves index validity — two different invariants. The count check is O(1) and not redundant; it is the right layer for index-out-of-range errors.

Q6. The layout computer (Phase 2) packs fields by alignment descending to minimize padding. But the canonical encoding pass (Phase 9) writes fields in FieldId ascending order. Can these two orders conflict in a way that produces non-deterministic padding? Answer synthesizes: Phase 2 (layout assigns byte offsets independently of write order) + Phase 9 (canonical encoding writes data to pre-determined offsets, not recomputing them). Layout is a pure function of schema; offsets are fixed before encoding begins. Write order does not affect padding because padding bytes are zeroed regardless of when they are written. The two orders operate on different abstractions: layout on offsets, canonical encoding on write sequence.

Q7. The ser-evolve compat checker (Phase 7) verifies backward/forward compat between two schema versions. What is the O() complexity of the check and what is the failure mode if a schema has 10,000 fields? Answer synthesizes: Phase 7 (compat check is O(F) for field count per type, O(T×F) total for T types) + §4.1 System Constraints (field count per schema bounded by FieldId u16 range = 65,535 max; practical limit lower). For a schema with 10,000 fields, compat check is ~10,000 comparisons — sub-millisecond. Cache schema pairs by (hash_a, hash_b) to avoid recomputing on repeated calls.

Q8. Far pointers enable messages to span multiple segments (§8.2). In a multi-segment message, can the validation pass visit the same segment more than once? What prevents a cycle? Answer synthesizes: Phase 5 (validation tracks visited words via BitSet; any word re-visited → BadPointer) + §6.5 (MAX_SEGMENTS = 512 caps segment count). A segment can legitimately be referenced by multiple pointers, but each word within it can only be the target of one pointer (enforced by the visited-words BitSet). Cycles are detected when a far-pointer landing pad points back to an already-visited word.

Q9. The Builder pool (Phase 10) caps at MAX_POOL_SIZE (default 64) builders. What happens under burst traffic where 200 concurrent goroutines/tasks request builders simultaneously? Answer synthesizes: Phase 10 (pool miss path: acquire() creates a new Builder when pool is empty — not a blocking call) + §4.1 (encode latency target 1 µs/KB). A pool miss allocates a new Builder on the fly. The pool is an optimization (reduces allocation per message in steady state), not a semaphore. Under burst load, extra builders are allocated and discarded after use (not returned to full pool). Latency impact: single allocation of arena slab — sub-microsecond.

Q10. The codegen path (Phase 6) emits Rust source code. If the generated code contains a bug in an offset constant, that bug is invisible at compile time. What is the verification strategy? Answer synthesizes: Phase 6 (generated accessors are derived from Layout constants, which are tested in layout_golden.rs) + Phase 13 (differential harness verifies generated Reader against reflective Reader for the same schema). The golden test catches layout divergence at codegen time; the differential benchmark catches runtime divergence. No offset constant in generated code is hand-written — all derived from Layout via emit_accessor(field.offset, field.ty).

Q11. Text fields (WireType::Text, Phase 8) are validated as UTF-8 during the validation pass. The accessor then uses from_utf8_unchecked. What happens if a future version of the validation pass skips the UTF-8 check as an "optimization"? Answer synthesizes: §7.2 Validation Trust Boundary (I5: from_utf8_unchecked is only safe under the post-validation guarantee that UTF-8 check was performed) + ADR-17 (unsafe policy: every unsafe block must carry a SAFETY comment naming the invariant it relies on). The SAFETY: comment on from_utf8_unchecked must cite I8 (UTF-8 validated in validation pass). Any future optimization removing the UTF-8 check must break the SAFETY: contract visibly, causing a mandatory audit.

Q12. The schema IDL supports union types. A union's active arm is identified by a u16 discriminant in the data section (Phase 8). What prevents a writer from encoding discriminant 5 but writing the data of arm 3? Answer synthesizes: Phase 6 (codegen emits typed set_arm_X() methods on UnionBuilder that both set the discriminant and write the arm's data in one atomic operation) + Phase 7 (evolution: new arms appended; old discriminants never reused). The Builder API makes mismatched discriminant/data physically impossible through the typed API. The validation pass does not separately validate discriminant-data consistency (it is a structural, not semantic, check) — the correctness guarantee is in the codegen layer.

Q13. ser-telemetry uses tracing spans for distributed pipeline correlation (Phase 12). What happens to span context when a message crosses a process boundary (encode in process A, decode in process B)? Answer synthesizes: Phase 12 (span context is injected via TelemetryContext; not embedded in the wire format) + §6.15 Explicit Message Framing, No Magic Bytes (wire format carries only schema hash and data — no tracing metadata). Span context propagation across processes is out of scope for this runtime; it is an application-layer concern (e.g., inject trace ID into a dedicated metadata field in the application schema). The runtime does not inject or extract distributed tracing context from wire messages.

Q14. The differential benchmark (Phase 13) compares this runtime against bincode on round-trip correctness. If bincode round-trips correctly but this runtime returns a different value for a float64 field containing NaN, which is "correct"? Answer synthesizes: Phase 13 (differential asserts field equality via PartialEq) + §4.1 System Constraints + ADR-04 (little-endian fixed). IEEE 754 NaN is not equal to itself under PartialEq. The differential harness must use bits() == bits() for float comparisons, not ==. This is a correctness trap in the differential test design, not a bug in the serialization format. The format passes through float64 bits verbatim (fixed-width LE).

Q15. The Deferred Features Register includes mmap-backed zero-copy read (DF7). What invariants from the current design must remain stable to un-defer this feature without a breaking change? Answer synthesizes: §7.2 Validation Trust Boundary (I5: post-validation safety) + Phase 5 (validation pass must accept a &[u8] slice view, regardless of backing store — mmap or heap) + §8.2 Wire Format (relative pointers → position-independent format). The format is already mmap-compatible: relative pointers, fixed layout, no absolute addresses. Un-deferring requires only providing an mmap-backed &[u8] to validate() — no format change needed. The invariant that must remain stable: validation input is a contiguous &[u8] slice (I5 pre-condition).

Q16. If two engineers independently write the same struct in two different .szs files with the same TypeId, what happens at schema registry time and at decode time? Answer synthesizes: Phase 1 (validate.rs rejects duplicate TypeId within one schema) + Phase 12 (schema registry maps SchemaHash → Schema; two different schema files with the same TypeId but different structures have different SchemaHash values). There is no collision at registry time — they are distinct schemas. At decode time, if a message encoded under schema A is decoded with schema B (same TypeId but different layout), ser-evolve compat check returns IncompatibleSchema. The defense is: SchemaHash is a commit to the full schema structure, not just the TypeId.

Q17. The packed scalar list (ADR-30, Phase 8) requires a decode pass into a temporary allocation. This breaks the zero-allocation guarantee on the accessor path. Is this a design inconsistency? Answer synthesizes: ADR-30 (packed mode is opt-in; explicitly noted as incompatible with zero-copy) + §6.2 Zero-Copy by Default (zero-copy is the default; packed lists are a documented exception accessible only through an explicitly different API surface). The design is consistent: the default path is zero-copy and zero-allocation; the packed API is a separate opt-in for bandwidth-constrained scenarios with explicit allocation semantics. The API surface enforces the distinction — there is no ambiguity at call sites.

Q18. What is the minimum-correct implementation of this runtime — the smallest subset of crates that can encode and decode a single fixed-schema struct without evolution, codegen, or telemetry? Answer synthesizes: Phase 0 (ser-core skeleton), Phase 3 (ser-layout), Phase 4 (ser-encode), Phase 5 (ser-decode). The minimum-correct implementation is: ser-core (types + wire format) + ser-schema (parse) + ser-layout (offset assignment) + ser-encode (Builder + Arena) + ser-decode (validate + Reader). Six crates. No ser-codegen (use reflective Reader), no ser-evolve (single schema version), no ser-telemetry (no metrics), no ser-tool, no ser-bench, no ser-cli. This is the "phase 0–5 bootstrap" and is the target deliverable for the first milestone gate.

Mental Models & First Principles

MM-1 — Wire format is a typed memory map, not a serialized object. The buffer IS the struct; there is no intermediate representation. Field access is an arithmetic offset read into shared memory. Predicts: any "parse" step is a performance regression; zero-copy decode is the target state. Without this model, engineers add unnecessary deserialization steps. Applied in: Phase 0 (skeleton), Phase 5 (decode), §6.2 Zero-Copy by Default.

MM-2 — Validation is a firewall, not a guard rail. The validation pass separates trusted space (post-validation buffer) from untrusted space (raw wire bytes). After the firewall, no further checking is needed; before it, no cast is safe. Predicts: all security vulnerabilities arise from bypassing or weakening the firewall, not from post-validation accessor bugs. Without this model, engineers add redundant checks in hot-path accessors (slowing them) or skip validation for "performance" (creating vulnerabilities). Applied in: Phase 5, Phase 11, §6.5 Bounded Resource Usage, §7.2 Validation Trust Boundary.

MM-3 — Schema is immutable identity, not mutable configuration. A schema is a content-addressed artifact: its SchemaHash is a commitment to its exact structure. Changing a schema produces a new schema with a new hash. Evolution rules define how reader schemas and writer schemas relate — not how a single schema mutates. Predicts: all compat bugs arise from treating schema change as in-place mutation. Without this model, engineers overwrite schema versions and lose the ability to validate in-flight messages. Applied in: Phase 1, Phase 7, §6.4 Append-Only Schema Evolution.

MM-4 — Layout is a pure function of schema, not of platform. Given the same schema bytes, compute_layout produces byte-identical Layout on every CPU architecture and OS. This means layout is testable, deterministic, and cacheable. Predicts: any layout divergence is a bug in the layout computer, not a platform difference to work around. Without this model, engineers introduce platform-conditioned offsets, breaking cross-platform wire compatibility. Applied in: Phase 2, §7.3 Layout Determinism, I2.

MM-5 — Amplification is a force multiplier for attackers. A 128-byte message that claims a list of 2^32 elements causes O(2^32) work during validation. The severity of amplification scales with the ratio of message bytes to claimed work, not with message size. Predicts: any counter field (count, depth, segment count) that isn't bounds-checked against message size is an amplification vector. Without this model, engineers add count fields without validating that count × element_size ≤ buffer size. Applied in: Phase 5, Phase 11, §6.5, ADR-17, P11 (Cap'n Proto advisory).

MM-6 — Schema evolution is append-only because deletion is physically impossible. Removing a field from a schema does not remove its bytes from existing wire messages. Those bytes exist on disk, in flight, in archives. "Removing" a field must instead declare it reserved — preserving the byte range and offset so surviving fields are not displaced. Predicts: any "remove field" operation without a reserved hole will silently corrupt existing messages read by old code. Without this model, engineers delete field entries and shift offsets. Applied in: Phase 7, Phase 8, §6.4, ADR-07, P10.

MM-7 — Arena allocation is amortization, not optimization. The arena allocator does not make individual allocations faster; it amortizes the overhead of many allocations across a single bump operation. The win is not per-allocation latency but total allocation count. Predicts: arena reuse (reset without free) compounds the win — steady-state operation reaches near-zero allocation cost. Without this model, engineers profile per-alloc speed rather than total allocation count per message. Applied in: Phase 4 (encode), Phase 10 (performance), §8.9 Arena Segment Growth Policy.

MM-8 — Pointer encoding is relative, not absolute. All struct and list pointers encode a word offset relative to the pointer slot's own position, not an absolute address into the segment. This means a serialized message is position-independent: it can be placed at any address in memory, copied to any segment, or memory-mapped from any file offset. Predicts: any absolute-address pointer in the wire format breaks mmap-backed zero-copy. Without this model, engineers use absolute offsets and tie the format to a fixed load address. Applied in: Phase 3 (Wire Format), Phase 4 (encode), §8.2 Wire Format.

Glossary · 51 terms · site-wide glossary

Zero-copy read
Decode = validate-then-view; field access performs NO heap allocation and NO byte copy. Explicit deep-copy/canonicalize is opt-in only.
Validation trust boundary
The single validation pass where ALL bounds, alignment, pointer-target, count, and recursion-depth checks occur. Post-validation accessor reads are total — cannot OOB or misalign. Unvalidated buffers are never accessed.
Reader<'a, T>
Zero-copy borrowed view over &'a [u8]; holds buf + base: Offset; accessors cast into the buffer using 'a lifetime; no allocation, no parse.
Builder<'a, T>
Arena-backed write handle for type T; allocates into an owned Arena; emits a Message on finish.
Schema
{ types: Vec<TypeDef>, root: TypeId, schema_hash: SchemaHash } — complete type graph for one logical namespace.
SchemaHash
u64 fingerprint computed deterministically from type ids, field ids, field types, and layout; used for compat checking and wire tagging.
TypeDef
One type in the schema: `{ id, name, kind: Struct
Field
{ id: FieldId, name, ty: WireType, offset: Offset, default: DefaultVal, since_version: u32 } — immutable once published.
TypeId
u32 globally unique identifier for a type within a schema; stable across schema versions.
FieldId
u16 stable identifier for a field within its type; used for evolution/compat matching; never reused.
Offset
u32 byte-offset within a segment's data array; always a multiple of the field's alignment requirement.
SegmentId
u32 index into Message::segments; segment 0 is the root segment.
WireType
Enum of representable wire kinds: Void, Bool, I8–I64, U8–U64, F32, F64, Enum, Struct, List, Union, Text, Bytes, Pointer.
Word
8-byte unit; all offsets and size fields in the wire format are expressed in words.
Layout
{ data_words: u16, ptr_words: u16, align: u8 } — struct footprint in the data section and pointer section. Layout is a pure function of schema.
Data section
First data_words * 8 bytes of a struct's allocation; holds scalar fields packed by offset.
Pointer section
Immediately follows the data section; ptr_words * 8 bytes holding Pointer values pointing to variable-length or nested objects.
Struct pointer
Pointer::Struct { offset, data_words, ptr_words } — relative word offset from pointer slot to target struct; carries inline layout for validation.
List pointer
Pointer::List { offset, elem, count } — points to a sequence of count elements of wire type elem.
Far pointer
Pointer::Far { seg, offset } — crosses segment boundaries; resolver must dereference into segment seg at word offset. Amplification-safe: max-segments limit applies.
Segment
{ id: SegmentId, bytes: Vec<u8> } — contiguous allocation arena; a Message has 1..N segments.
Arena
Bump allocator backing a Builder session; grows by adding new segments; never frees mid-build.
Message framing
4-byte segment count + per-segment 4-byte size prefix, little-endian; enables prefixing over any byte stream.
Packed encoding
Optional compression of wire bytes: runs of zero bytes replaced with tag byte + nonzero bytes; packing is a post-encode filter, not a format change.
Little-endian
All scalar wire values stored in little-endian byte order; fixed for all platforms; accessors on big-endian hosts perform byte-swap on read.
IDL / .szs
Interface Description Language source file (extension .szs); parsed by ser-schema; defines structs, enums, unions, lists, and field defaults.
Layout determinism
Identical schema → byte-identical layout on every platform; layout is a pure function of TypeDef; no runtime variation.
Canonical encoding
Encoding mode yielding byte-identical output for logically-equal messages: fixed field order, zeroed padding, no dead space; enables hashing and deduplication.
Validation pass
Single sequential scan of all message bytes performed by ser-decode before any field access; checks bounds, alignment, pointer targets, depth, and segment count.
Amplification attack
Crafted message exploiting far-pointer chains or list counts to cause superlinear work; mitigated by total-bytes cap, max-segment count, and recursion-depth limit.
Recursion depth limit
Hard cap (default 64) on pointer-following depth during validation; prevents stack overflow on adversarial pointer cycles.
Schema evolution
Rules governing backward/forward compat across schema versions: append-only field ids, optional fields default to zero/null, union arms append-only, removed fields become reserved holes.
Reserved hole
Byte range left in a struct's data section after a field is logically removed; ensures offsets of surviving fields are not disturbed.
Forward compatibility
Old reader can consume message written by new writer; unrecognized fields are silently ignored; unknown union arms present as Unknown variant.
Backward compatibility
New reader can consume message written by old writer; absent fields read their schema-declared defaults.
since_version
u32 on each Field; the schema version at which the field was added; readers with older schema treat the field as absent.
DefaultVal
Per-field encoded default used when an absent or zeroed field is accessed; stored in schema, not in the wire message.
Accessor
Generated or reflective method on Reader<'a, T> that returns a field value or a nested Reader; always borrows from the message buffer.
Offset table / vtable
Optional indirection table (FlatBuffers-style) mapping field ids to offsets; used in union/evolving structs where layout cannot be fully static.
Union tag / discriminant
A u16 stored in the data section identifying the active arm of a Union type.
Text
Wire type for UTF-8 strings: pointer-section entry pointing to a byte list prefixed with length; NUL-terminated for C interop.
Bytes
Wire type for opaque byte blobs; like Text but no NUL termination, no UTF-8 requirement.
Packed scalar list
List whose elements are primitive scalars stored contiguously without per-element pointers; stride = element size.
Varint
Variable-length integer encoding (used in protobuf contrast); NOT used in this format — all scalars are fixed-width for zero-copy alignment.
Endianness
Byte order of multi-byte scalars on the wire; this runtime fixes little-endian; accessors on BE hosts emit to_le/from_le intrinsics.
Reflective fallback
Dynamic field access via Schema + TypeDef at runtime without generated code; used by ser-tool and for schema-less consumers.
ser-telemetry tap
Hook points in encode/validate/decode paths that emit tracing spans and metrics counters without altering correctness.
Differential benchmark
Benchmark in ser-bench that compares this runtime against capnproto-rust, flatbuffers, and rkyv on identical payloads; regression gate.
Schema registry
Service/store in ser-tool mapping SchemaHash → Schema; enables wire-diff and reflective decode of archived messages.
SerError
enum { SchemaInvalid, OutOfBounds, Misaligned, BadPointer, DepthExceeded, Truncated, IncompatibleSchema } — exhaustive error taxonomy; all public APIs return Result<_, SerError>.
MSRV
Minimum Supported Rust Version = 1.78; governs which stable features are permitted; enforced by rust-version field in workspace Cargo.toml.
