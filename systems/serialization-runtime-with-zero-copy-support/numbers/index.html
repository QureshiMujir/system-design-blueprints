4.2 Memory Model Constraints

  • Arena allocator: segments are Vec<u8> grown by doubling; max segment size bounded before alloc to prevent OOM amplification.
  • Reader<'a, T> holds &'a [u8] borrow; message buffer must outlive all Readers — enforced by Rust lifetime system, not runtime check.
  • Stack depth during validation: O(nesting depth) stack frames; max 64 levels → ≤ 64 recursive calls; no unbounded recursion.
  • Canonical encoding zeroes all padding bytes: no information leakage via uninitialized memory in wire bytes.

4.4 Scaling Assumptions

  • Horizontal: library; scales with caller's thread/process count; no shared state between messages.
  • Vertical: arena per-message; larger messages use more heap; no global allocator pressure beyond individual message lifetime.
  • Schema cardinality: ≤ 4096 types practical; schema registry lookup O(1) by SchemaHash (hash map).
  • Schema evolution frequency: checker runs in CI; not on hot path; O(|fields| × |versions|) complexity.
  • Telemetry overhead: ≤ 2% throughput degradation when telemetry feature enabled; zero overhead when disabled.
  • Fuzz corpus: target 10 000+ seeds; validation pass must handle all without panic (only Err(SerError::*)).

Back-of-Envelope Capacity Model

All derivations start from the System Constraints table (§4.1). Notation: 1 GiB = 2^30 bytes; 1 MiB = 2^20 bytes; 1 word = 8 bytes.

1. Encode throughput ceiling (single-thread arena path)

System constraint: target encode throughput = 1 GiB/s.

  • Arena bump allocator: 1 pointer increment + 1 zeroing pass per word written.
  • Memory bandwidth requirement: 1 GiB/s output means 1 GiB/s of memset-equivalent work on the arena slab.
  • Modern cores: ~40–80 GiB/s L1/L2 bandwidth, ~25 GiB/s L3 bandwidth.
  • At 1 GiB/s, encode is comfortably within L3 bandwidth for small messages (< 256 KB fit in LLC).
  • Multi-segment overhead: each segment boundary triggers 1 far-pointer write (8 bytes) + segment header update; at typical segment size 4 KB = 512 words, overhead = 1/512 = 0.2% — negligible.
  • Result: 1 GiB/s encode is achievable on a single core against L3 cache. Sustained throughput across many cores: limited by DRAM bandwidth (~50 GiB/s dual-channel) → up to ~50 concurrent encoding cores before memory is the bottleneck.

2. Decode (validate-then-view) throughput ceiling

Validation pass: visits every word in the message once (O(N) pointer traversal).

  • 1 GiB/s decode target.
  • Traversal cost = 1 cache-line load per 8-word block = 1 load per 64 bytes.
  • At 1 GiB/s, decode reads ~15.6 million 64-byte cache lines per second.
  • L3 hit rate for messages < 8 MB: high (most messages fit in LLC of 8–32 MB).
  • L3 latency: ~10 ns; 15.6 M × 10 ns = 156 ms/s of pure latency → throughput ceiling ~6.4 GiB/s at L3 latency (sequentially reads are pipelined by hardware prefetch).
  • Result: validation at 1 GiB/s is memory-bandwidth limited, not latency limited. Hardware prefetch makes sequential scan near L3-bandwidth optimal (~30–60 GiB/s theoretical; practical 6–10 GiB/s after pointer chasing).

3. Amplification attack budget

Constraint: MAX_MESSAGE_BYTES = 512 MiB (I10).

  • Worst-case amplification: list pointer claiming 2^29 elements of 1 word each = 2^29 × 8 = 4 GiB → rejected immediately (> MAX_MESSAGE_BYTES).
  • With MAX_MESSAGE_BYTES check: any list count × element_size > 512 MiB → rejected in O(1) before traversal.
  • Remaining amplification: nested struct traversal; MAX_NESTING_DEPTH = 64 (I6); MAX_TRAVERSAL_WORDS bounds total words visited.
  • MAX_TRAVERSAL_WORDS = MAX_MESSAGE_BYTES / 8 = 64 Mi words = 67,108,864 words.
  • Traversal budget per validation: 64 Mi word visits × 1 ns per visit = 67 ms. This is the worst-case validation latency for a 512 MiB message.
  • Result: amplification is bounded. A 128-byte message cannot cause more than 128/8 = 16 word visits (bounds check rejects count > buffer size). The ratio of work to message bytes is O(1).

4. Schema parse cost per service startup

Typical schema: 100 types × 20 fields average = 2000 fields.

  • IDL token rate: ~10 MB/s parse (conservative; serial PEG parser).
  • Typical .szs file: 2000 fields × ~50 bytes per field declaration = ~100 KB.
  • Parse time: 100 KB / 10 MB/s = 10 ms.
  • Hash computation: SipHash-1-3 over ~10 KB canonical bytes: < 0.1 ms.
  • Result: schema parse is a one-time 10–15 ms startup cost. Not on hot path. Safe to run synchronously during service initialization.

5. Schema registry memory footprint

10,000 distinct schema versions deployed across an organization (large org estimate).

  • Per schema: ~2000 fields × 64 bytes per Field struct = ~128 KB per schema (in-memory).
  • 10K schemas: 10K × 128 KB = 1.28 GB. This is too large for a per-service in-memory cache.
  • Practical model: cache most-recently-used 100 schemas; 100 × 128 KB = 12.8 MB → well within per-service budget.
  • SchemaHash→Schema map overhead: 10K entries × 32 bytes (hash + pointer) = 320 KB for the index.
  • Result: per-service cache of 100 schemas costs ~13 MB. Full in-process registry for large orgs requires demand-loading from persistent store.

6. Fuzzing corpus size vs bug discovery rate

Empirical (libFuzzer behavior): coverage-guided fuzzing plateau for a 2 KLOC validation function is typically reached at ~100K unique corpus entries.

  • Corpus entry: average 256 bytes (message-like structure with valid/invalid pointer patterns).
  • Total corpus size: 100K × 256 bytes = ~25 MB.
  • Daily CI fuzz run: 30 minutes × 10^6 executions/min (modern libFuzzer rate) = 1.8 × 10^9 executions/day.
  • At 30-minute CI runs, the fuzz target explores ~54 million paths/day.
  • Result: 30-minute daily fuzz runs are meaningful for input coverage. 25 MB corpus is acceptable for commit to repository. Continuous fuzzing (separate from CI) recommended for security-critical targets.
