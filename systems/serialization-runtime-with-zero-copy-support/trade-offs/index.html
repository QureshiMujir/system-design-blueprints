Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust (edition 2021, MSRV 1.78)

Rejected

C++ (buffer safety), Go (GC + layout limits), Java (GC + layout limits), Zig (ecosystem immaturity)

When the rejected choice is right

C++: when integrating with an existing C++ codebase where FFI overhead outweighs safety benefits and the team has deep ASAN-enforced C++ discipline; Go: when throughput targets are relaxed (< 100 MB/s) and schema-first is less critical than rapid iteration

Why: Zero-copy demands lifetime-checked borrows, no GC, precise layout control; safe unsafe encapsulation

ADR-02

Build system

Chosen

Cargo (workspace)

Rejected

Bazel, Buck2, CMake

When the rejected choice is right

Bazel/Buck2: when the project is part of a large monorepo with multiple languages (C++, Java, Python) where Cargo does not integrate and build hermeticity across languages is required

Why: Cargo is idiomatic; workspace unifies all 12 crates; reproducible with Cargo.lock; no cross-lang compilation needed

ADR-03

Dependency policy

Chosen

Minimal; no default-features; pin exact versions in Cargo.lock

Rejected

Broad dependency tree

When the rejected choice is right

Broad dependency tree: in a rapid-prototyping context where developer velocity matters more than security auditability and the artifact is not exposed to untrusted network input

Why: Zero-copy runtime is security-sensitive; each dep is an attack surface; audit via cargo-deny

ADR-04

Wire endianness

Chosen

Little-endian fixed

Rejected

Big-endian, network byte order, native endian

When the rejected choice is right

Big-endian / network byte order: when interoperating with legacy mainframe (z/OS, SPARC) systems or network protocols (XDR, SunRPC) where the peer controls the wire format and re-negotiation is not possible

Why: x86/ARM are LE; WASM is LE; fixed endian avoids per-platform branches; mirrors Cap'n Proto

ADR-05

Word size

Chosen

8 bytes (64-bit word)

Rejected

4-byte word (FlatBuffers), 16-byte, variable

When the rejected choice is right

4-byte word: in embedded or 32-bit microcontroller targets (Cortex-M) where 8-byte alignment wastes RAM and pointer arithmetic is 32-bit; FlatBuffers' 4-byte word is correct for that regime

Why: Natural 64-bit alignment; pointer encoding fits comfortably; matches Cap'n Proto

ADR-06

Integer encoding

Chosen

Fixed-width LE (no varint in default mode)

Rejected

Varint (protobuf), zigzag, LEB128

When the rejected choice is right

Varint/LEB128: when message payloads consist primarily of small integers (< 128) and wire size dominates over decode latency — e.g., mobile battery-constrained environments where bandwidth cost exceeds compute cost

Why: Zero-copy requires fixed offsets; varint requires parsing pass; packed varint mode is opt-in

ADR-07

Schema IDL format

Chosen

Custom .szs (ser-schema)

Rejected

JSON Schema, Protobuf .proto, Thrift, Avro IDL, Cap'n Proto .capnp

When the rejected choice is right

Protobuf .proto: when sharing schemas across an organization that already uses the Protobuf ecosystem and toolchain investment amortizes across dozens of services; Thrift: in polyglot environments (Python/Java/C++) with mature Thrift generator infrastructure

Why: Full control over extension points; evolution rules embedded; no dependency on external IDL compilers

ADR-08

Schema hashing

Chosen

xxHash3 (SchemaHash u64)

Rejected

SHA-256, SHA-1, MD5, FNV

When the rejected choice is right

SHA-256: when SchemaHash is used as a security boundary (schema as capability token, tamper-evident registry) rather than merely a compatibility identifier — cryptographic strength required for adversarial schema forgery

Why: xxHash3: collision-resistant for non-crypto use; extremely fast; 64-bit sufficient for schema registry

ADR-09

Async runtime

Chosen

None in core crates; tokio optional in ser-runtime

Rejected

async-std, smol, embassy

When the rejected choice is right

embassy/no-std async: on bare-metal microcontrollers without an OS where synchronous blocking APIs are impossible and embassy's single-executor async is the only viable concurrency model

Why: Core encode/decode is synchronous CPU work; async is transport concern (out of scope); tokio integration opt-in

ADR-10

Memory allocator

Chosen

System allocator (Builder/Arena); jemalloc optional

Rejected

mimalloc, tcmalloc, bump-only

When the rejected choice is right

mimalloc: in high-frequency trading or game-server workloads where thousands of short-lived messages per millisecond stress the default allocator's thread-local caches; mimalloc's segment-based design reduces fragmentation dramatically

Why: Arena allocator for encode is internal; system alloc default; jemalloc feature flag for bench/prod

ADR-11

Concurrency model

Chosen

No shared mutable state in core; Reader<'a,T> is Send+Sync

Rejected

Lock-based global state, Rc

When the rejected choice is right

Lock-based global state: when a single-threaded event loop (Node.js-style) owns all encode/decode and the simplicity of a global mutable context outweighs the overhead of per-message arena allocation

Why: Rust type system enforces: Reader is read-only borrow → trivially Sync; Builder is owned → Send

ADR-12

Logging

Chosen

Rejected

log crate, slog, env_logger

When the rejected choice is right

log crate: in no_std embedded targets where tracing's allocations are unacceptable and only a simple key=value log line over UART is feasible

Why: tracing supports async context; structured fields; compatible with OpenTelemetry; de-facto Rust ecosystem

ADR-30

Packed integer mode

Chosen

Opt-in pack() API producing varint-compressed scalars

Rejected

Always-packed (breaks zero-copy), always-fixed

When the rejected choice is right

Always-packed: in pure network transmission contexts (mobile APIs, IoT telemetry) where wire byte count is the dominant cost and the decode latency budget is relaxed — prost/protobuf wins here

Why: Zero-copy incompatible with varints; packed mode produces compact bytes but requires decode pass; separate API surface

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Interpreted/Reflective-Only (No Arena, No Codegen)

+--------+     parse IDL      +--------+     interpret      +--------+
| .szs   | -----------------> | Schema | ----------------> | Reader |
| source |                    | (heap) |     at runtime     | (dyn)  |
+--------+                    +--------+                    +--------+
         all field accesses: schema lookup + offset compute per call

Architecture: keep schema in memory as a runtime graph; each field access looks up the schema graph to find the offset, then performs a bounds check and cast. No code generation. No arena allocator — use system heap per-struct.

Regime where it wins: dynamic scripting environments (Python plugins, REPL tools, schema-less consumers) where the schema is not known at compile time and type-safety is irrelevant. Also correct for prototyping where schema churn is high.

Real system that embodies it: ser-tool's reflective reader (the reflective fallback path already in this design); also rkyv's Archived without codegen; also Protocol Buffers' DynamicMessage API.

Why rejected as primary design: field access cost is O(schema_lookup) + O(offset_compute) per access rather than O(1) compiled constant. For a 10-field struct accessed 10 million times per second, schema lookup dominates. The codegen path reduces this to a single integer addition.

Alt-2 — Vtable-Per-Object (FlatBuffers-style)

+--------+   allocate vtable  +-------+  vtable pointer   +--------+
| Builder| -----------------> |Vtable | <---------------- | Object |
|        |   (per-object,     | [off] |                   | header |
|        |    heap or arena)  +-------+                   +--------+
         each field access: deref vtable[virtual_id] -> offset -> data

Architecture: every encoded object carries a vtable pointer. The vtable maps virtual field IDs to byte offsets. Fields absent in a given message have vtable entry 0. Layout is computed at encode time, not schema time.

Regime where it wins: highly optional field presence (sparse messages where most fields are absent most of the time); backward compat without any layout pre-declaration; mobile/game clients where schema version churn is high and vtable overhead (8–16 bytes per object) is acceptable.

Real system that embodies it: FlatBuffers (table objects carry vtable offset in the first word; vtable is builder-allocated per distinct field set).

Why rejected: vtable adds one memory indirection per field read. For a cache-line-resident struct of 8 fields, the vtable dereference is a separate cache-line load, doubling memory traffic. The schema-first layout model of this design makes vtables unnecessary: all offsets are known at compile/schema-parse time.

Alt-3 — Copy-on-Decode (Protobuf/Serde-style)

+--------+   full parse pass  +--------+   field access    +--------+
| wire   | -----------------> |  Heap  | ----------------> | owned  |
| bytes  |   (alloc per       | object |   (direct field   | struct |
|        |    field/string)   |        |    in heap struct) |        |
+--------+                    +--------+                    +--------+
         decode = parse + alloc + copy; no validation separate from parse

Architecture: decode is a single-pass operation that simultaneously parses the wire format and builds an owned in-memory struct. Each field is individually allocated (strings as String, bytes as Vec<u8>, nested structs as Box<Nested>). Field access after decode is O(1) struct field access — no wire-format involvement.

Regime where it wins: when messages are frequently processed (many fields accessed repeatedly after decode), when fields are mutated after decode, or when the application model requires owned data with arbitrary lifetimes (across .await points, across thread boundaries, stored in data structures). Protocol Buffers, serde + bincode, Avro with code-generated structs.

Why rejected: zero-copy is the stated design goal. Copy-on-decode is structurally incompatible: no amount of optimization reduces copy-on-decode to zero allocation. The target use case (decode and inspect a message once, then route or discard the buffer) is served by zero-copy with zero allocation; copy-on-decode adds O(message_size) allocation and copy overhead.

Alt-4 — Fixed-Stride, No-Pointer (SBE-style)

+--------+   template lookup  +-------+  stride offset    +--------+
| header | -----------------> | SBE   | <---------------- | field  |
| tempId |                    |Template|  (no pointer,    | access |
|        |                    | (XML) |   no validation)  |        |
+--------+                    +-------+                   +--------+
         decode = template[templateId] -> stride arithmetic; no validation needed

Architecture: the wire format carries a templateId that identifies a fixed message template. All fields are at compile-time-fixed byte offsets from the message start. No pointer types, no variable-length fields in the base template (variable-length fields appended as a "group" with a block length header). No validation pass needed because there are no pointers to validate.

Regime where it wins: ultra-low-latency fixed-schema financial messaging (FIX/FASTs); decode latency in nanoseconds; schema contractually frozen between counterparties; no schema evolution required between releases. SBE is deployed on trading floors where single-digit-nanosecond decode paths are critical.

Real system that embodies it: SBE (Simple Binary Encoding), used in the FIX trading community and the London Metal Exchange.

Why rejected: no pointer types means no variable-length strings, no nested structs, no recursive types. The target use case requires rich type support (Text, Bytes, nested structs, List<T>) and schema evolution. SBE's fixed-stride model is correct only when the message structure is known to both parties at link time and never changes.
