In one paragraph

SWIM is a way for a group of machines to keep an eventually consistent list of which members are alive, with no central coordinator and no all-to-all heartbeating (§1). Each node checks one other node per time period, so a node's detection load stays the same no matter how big the cluster gets (§4, §19). News about joins, suspicions and deaths then spreads by rumor, riding on the checks that are already happening (§3, §6 P2, P6). The blueprint builds it as a Go library plus a runnable agent, swimd, and an inspector, swimctl (§1, ADR-24). Each application process embeds one node, and the application receives join, fail, update and leave events (§1, §3).

The problem, concretely

A naive cluster has every node send a heartbeat to every other node each period. That costs N(N−1) messages per period across the cluster, about 10^6 per second at N=1000 with a 1 s period (§22 item 3). Failure detection also gets worse as the cluster grows: to avoid wrongly declaring slow nodes dead you lengthen the miss timeout, and that makes real failures take longer to notice (§19 D.1).

A central registry avoids that load, but it becomes a coordinator that every node depends on. It blocks when the network splits, and its write rate becomes the ceiling for how fast membership can change (§24 road B, P9, P11).

SWIM splits the job in two. Detection is a cheap poll of one target per period (P1). Spreading the result is epidemic gossip (P2, MM1). The price is that the view is only eventually consistent: nodes may briefly disagree, and consumers must tolerate that (P9, §1 boundaries). Anything needing agreement, such as leader election, belongs to consensus (§1, MM8).

How it works, end to end

Follow one node's view of one probe through the boxes of §3's diagram:

 application ◀── events: join / fail / update / leave ── node / API  (Members, Join, Leave)
                                                            │
                         membership list (state, shuffled ring, suspicion timers, merge rules)
        ┌──────────────┬────────────────┬───────────────────┐
   failure detector  suspicion      dissemination        anti-entropy
   ping/ack+ping-req  Alive→Suspect   piggyback buffer    TCP push-pull
   (k relays)         →Dead, refute   λ·log N, freshest   periodic + join
        └──────── lifeguard (LHM, adaptive timeouts, buddy, NACK) ────────┘
                         codec (compact encode + piggyback packing, ≤ MTU)
                  UDP transport (probes, bounded)      TCP transport (full-state sync)
  1. node / API (node, cli) is all the application sees: Join(seeds), Leave(), Members() and event callbacks (§1, §3).
  2. Membership list (core) holds, per node, {address, state, incarnation, meta}, plus the shuffled probe ring, live suspicion timers and the conflict-resolution rules. Every mutation goes through one merge function under the list lock (§3, §8.1, I13).
  3. Failure detector (failuredetector) takes the next member from the ring each period and pings it. An ack ends the probe (§3, §8.4).
  4. Indirect probing (indirect): with no ack, the node asks k random relays to probe the target (ping-req). A relay that cannot reach the target answers nack (§8.4).
  5. Suspicion (suspicion): if nothing answers, the target becomes Suspect, not Dead. A timer runs and the suspicion is gossiped (§8.4, §8.5, P4).
  6. Dissemination (dissemination) packs state changes into the spare bytes of every ping, ack and ping-req, resending each about λ·log(N+1) times and then retiring it (§3, I7).
  7. Anti-entropy (antientropy) periodically, and on join, exchanges the whole list over TCP with a random peer, to catch what lossy UDP gossip missed (§3, P7).
  8. Lifeguard (lifeguard) lets a node that suspects its own health slow its timers rather than blame peers (§3, I11).
  9. Codec and transport (codec, transport) keep every UDP datagram under the MTU, about 1400 B (§3, I6, §4).

No wall-clock time enters the protocol. Ordering of liveness claims uses per-node counters, and timers use a monotonic clock (P3, ADR-28).

The core ideas

The probe round: poll one, escalate through k relays (§8.4, I8)

Each period T′ (about 1 s, §4) a node does the following:

Step What happens Outcome
1 Take the next member from the shuffled ring, send ping wait up to a sub-period timeout (§4)
2 ack arrives target stays Alive; the period is done
3 No ack: send ping-req to k=3 random relays (not the target) each relay pings the target
4 Any ack arrives, directly or forwarded by a relay target stays Alive
5 No ack from the target or any relay before the period ends mark target Suspect, start a timer, gossip it

The ring is a shuffled permutation, so every member is probed once per cycle before any repeat (I8, ADR-08). Reshuffle happens when the ring wraps (§7 I8). Load per node is 1 ping and 1 ack in a normal period, and up to k extra ping-req exchanges only after a direct miss (§22 items 1–2). Per-node load never contains N.

Incarnations and precedence: who wins when two claims disagree (§8.3, MM2)

An incarnation is a number per node that only that node may raise (I1, ADR-07). A claim about node M carries the incarnation it was made at. Comparing an incoming claim with the local entry:

Incoming It overrides the local entry when
Alive(i) i is greater than the local incarnation j
Suspect(i) local is Alive and i ≥ j, or local is Suspect and i > j
Dead(i) i ≥ j and local is not already Dead
Leave(i) i ≥ j

In words: a higher incarnation always wins. At equal incarnation, Suspect beats Alive, and Dead beats both (§8.3). A node that hears itself called Suspect or Dead sets its own incarnation past the rumor and broadcasts Alive (refutation, P5). Because only the node itself can mint a higher number, a false death heals itself while a real crash cannot be refuted (MM2, §19 D.4). The blueprint calls this function the single highest-blast-radius component, and Phase 0 must test every cell (§23 item 14, §8.3, I2). One cell is stated two ways: §8.3, the §8.5 diagram and §19 D.4 clear a Suspect only with a strictly higher Alive (i > j), while the §8.5 transition table and the Phase 4 steps clear it with i′ ≥ the suspect incarnation.

Suspicion: a window before a verdict (§8.5, §8.6, P4, MM3)

A failed probe moves a node to Suspect, never straight to Dead. A node enters Dead only through a suspicion timeout with no refutation, or an explicit Leave or Confirm (I3). The timeout is suspicion_mult · log(N+1) · T′ (§4); at mult=4 and N=1000 the blueprint computes about 40 s (§22 item 9).

The blueprint's own trace (§8.6): five nodes A–E. A is unlucky; its direct ping and its ping-req via B and D to a healthy C are all lost. A marks C Suspect at incarnation 7 and gossips it. B, D and E also mark C Suspect(7). C hears the rumor, sets its incarnation to 8 and broadcasts Alive(8). Since 8 > 7, everyone clears the suspicion. Had C really crashed, no Alive(8) would appear, the timers would fire, and C would become Dead everywhere (§8.6, I4).

Stacked accuracy gates: why false positives get rare (MM4, §19 D.3)

With packet loss p, a direct-only detector falsely suspects a live node with probability about p. With k relays, the target is suspected only if the direct probe and all k relay probes are lost, about p^(k+1). At p=0.1 and k=3 the blueprint gives 10⁻⁴ instead of 10⁻¹ (§19 D.3). The suspicion window is a second gate, because a falsely suspected node has time to refute (M4, M5 in §18). Lifeguard adds a third. A node whose own probes keep failing, probably because it is overloaded, raises a local health multiplier (LHM) and stretches its own timers rather than blaming peers (I11, P10). LHM must rise only on signals about the node's own health, not because a peer failed to answer (§19 pitfall 10).

Infection-style dissemination (§3, §22 items 5–7, I7, MM1)

Updates ride in the spare space of existing messages, freshest first, and each update is retransmitted at most λ·log(N+1) times, then retired (I7, ADR-10, ADR-11). The packing budget is floor((MTU − header) / update_size). With about 1400 B, a 60 B header and 50 B per update the blueprint gets about 26 updates per datagram (§22 item 5). At N=1000 and λ=3 that is about 30 sends per update before retirement (§22 item 7). Like a rumor, news reaches everyone in O(log N) periods, about 10 at N=1000 by log2(N) × T′ (§22 item 6, M6). If churn exceeds the per-datagram budget, the overflow waits for later messages and convergence stretches (§22 guardrails).

Anti-entropy and the partition heal (§8.7, §19 D.6, MM5, MM7, I10)

Every ~30 s (A, §4) a node exchanges its full list with a random peer over TCP (push-pull). Merging identical lists changes nothing (I10), so the exchange is safe to repeat.

The blueprint's partition trace (§19 D.6) has six nodes, {A,B,C} and {D,E,F}, all at incarnation 1. A link cut makes each side suspect and then declare the other side Dead(1). Nothing crashed, and each side reports the nodes it can reach. When the link heals, A syncs with D and D sees itself listed as Dead(1). D sets its incarnation to 2 and broadcasts Alive(2); 2 > 1, so A, B and C accept it. The other five nodes do the same. After O(log N) periods plus one anti-entropy round, all six are Alive again. A node that had truly crashed mints nothing and stays Dead (§19 D.6, I4, I5).

The trade-offs — where engineers disagree

Version number: per-node incarnation (ADR-07)

Chosen: a per-node u64 incarnation, so liveness needs no synchronized clock (P3). Rejected: wall-clock timestamps. When the rejected choice is right: when nodes share a tightly disciplined clock (PTP or GPS, sub-millisecond skew) and operators want human-readable cross-cluster event ordering for forensics, the Cassandra-style assumption (§9).

Probe transport: one UDP socket (ADR-04)

Chosen: UDP on a single socket, for constant load and no per-connection overhead. Rejected: a TCP connection per probe. When the rejected choice is right: on networks that block or throttle UDP (many corporate firewalls, some inter-region cloud links), where a pooled TCP probe is the only path that survives (§9). The capacity model also ties the choice to file descriptors: about 2 steady-state versus an O(N) budget for a connection per peer (§22 item 11).

Target selection: a shuffled ring (ADR-08)

Chosen: a shuffled permutation, giving bounded time to be probed (I8). Rejected: random selection with replacement. When the rejected choice is right: under heavy continuous churn, where keeping a stable permutation costs more than it saves because joins and leaves keep invalidating the ring (§9).

Dissemination: piggyback on probes (ADR-10)

Chosen: piggyback updates on probe traffic plus a small gossip tick, for bounded bandwidth (P6). Rejected: a standalone flood per update. When the rejected choice is right: in a small cluster (N up to about 10) where one critical event, such as a leader's death, must reach everyone in a single period and O(N) flood bandwidth is trivial (§9).

Suspicion timing: scaled with log N, plus Lifeguard (ADR-12)

Chosen: a timeout proportional to log(N)·T′ plus Lifeguard, so accuracy scales with cluster size (P4, P10). Rejected: a fixed timeout. When the rejected choice is right: in a homogeneous, fixed-size, uniform-latency cluster, where the log(N) term is constant and Lifeguard's adaptivity adds tuning surface without benefit (§9). A constant window is what produces false positives at scale (MM3, §22 guardrails).

Datagram authentication: keyring HMAC, optional AEAD (ADR-14)

Chosen: a keyring HMAC on datagrams with optional authenticated encryption, avoiding per-connection TLS. Rejected: no authentication, or TLS only. When the rejected choice is right: TLS-only wins when SWIM runs exclusively over TCP inside an existing mTLS mesh (Istio sidecars) that already authenticates every connection. "None" wins on a fully isolated trusted network segment (§9).

Roads not taken (§24)

All-to-all heartbeating (road A): wins when N is tiny and fixed (about 10–20, one rack), where O(N²) is negligible and "no gossip, no suspicion" is the simplest thing that works. It is rejected because its load grows as O(N²) and its accuracy degrades with size (§24, §19).

A consensus store such as etcd or ZooKeeper (road B): wins when every node must see one agreed membership set at a quorum-defined instant, for example for quorum reconfiguration. It is rejected as the base because it adds a coordinator, blocks under partition and caps churn at the store's write rate. The blueprint's stated answer is to use both: SWIM beneath, consensus for the few decisions needing agreement (§24, MM8).

Tiered LAN and WAN gossip (road C): wins across high-latency, lossy multi-datacenter links, where one fast tier mistakes latency for failure. It is deferred rather than rejected, and is built in Phase 11 (§24, §25).

φ-accrual detectors (road D): win where link latencies are heterogeneous and drift, since a single static timeout is wrong everywhere at once. SWIM keeps the coarse, refutable Suspect state and gets adaptivity from the node-local LHM instead (§24, I11).

What must never be false

  • I1: a node's incarnation never decreases and only it advances it. Noticed by a local regress check (incarnation, self_refutes_total).
  • I2: an incoming update is applied only if it wins conflict resolution. Noticed by a precedence-rule audit (updates_applied/rejected).
  • I3: a node becomes Dead only via suspicion timeout or explicit Leave/Confirm, never one failed probe. A direct-to-dead detector watches it (suspect_to_dead_total).
  • I4: every crashed member is eventually marked Dead by every non-faulty member. Checked in partition and loss simulation (undetected_dead, a test metric).
  • I5: a correctly running node is eventually Alive in every non-faulty view. A false-positive monitor watches it (false_positive_total).
  • I6: no UDP datagram exceeds the MTU. A packing-time size guard (oversize_dropped_total).
  • I7: each update is retransmitted at most λ·log(N+1) times. A per-update count cap (gossip_retransmits).
  • I8: probe order is a permutation. A ring-coverage audit (probe_ring_position).
  • I9: a suspicion timer fires exactly once and is cancelled on refute or leave. A timer-leak detector (suspicion_timers_active).
  • I10: reconciling identical states is a no-op. A sync-diff-is-empty check (antientropy_changes).
  • I11: a node that suspects its own health dilates its own timers, not peers' states. Seen by comparing LHM against the miss rate (local_health_multiplier).
  • I12: a graceful Leave removes a node with no Suspect cycle. A leave-vs-suspect path check.
  • I13: all membership mutations go through the conflict-resolution function under the list lock. A concurrent-mutation race test (merge_lock_contention).
  • I14: randomness is reproducible under a fixed seed. Replay equality; the seed is a recorded value (seed).
  • I15: full per-node lists stay LAN-local; only DC and gateway state crosses the WAN. A cross-DC byte audit (wan_bytes, wan_members).
  • I16: user events are Lamport-ordered and delivered at most once per node. A dedup-window check (events_deduped_total, lamport_time).
  • I17: per-node meta never exceeds its byte bound. An oversize-meta guard (meta_oversize_rejected_total).
  • I18: a rotated-out auth key is never accepted past its keyring TTL. A key-age check on decode (expired_key_rejected_total).

What breaks in production

The blueprint's failure modes are named classes in a table with no numeric IDs, so they are cited by class name (§13).

  • False positive. A live node is marked Dead and then comes back. The root causes are transient loss, a short suspicion window or an overloaded node. Detection is the I5 monitor and refute events. Recovery is automatic through indirect probes and self-refutation. By hand, raise the suspicion multiplier, k or Lifeguard (§13, I5).
  • Missed detection. A crashed node stays Alive in some views, because gossip was lost and nothing swept it up. It shows in the I4 simulation and in anti-entropy change counts. The anti-entropy sweep recovers it, and the operator checks gossip and MTU settings (§13, I4).
  • Partition. Each side sees the other as all Dead. Partition metrics and asymmetry show it. Once the network heals, anti-entropy plus incarnations repair the views automatically; the operator's part is healing the network (§13, §19 D.6).
  • Flapping. A node oscillates between Alive and Suspect on borderline reachability or overload. Suspect/refute churn shows it, and Lifeguard's LHM damps it. By hand, tune timeouts or fix the node (§13).
  • MTU fragmentation. Gossip is silently lost because a datagram exceeded the MTU. There is no error, only slow convergence, so the oversize counter (I6) is the tell. The system truncates piggyback automatically; the operator lowers the MTU setting (§13, MM6).
  • Timer leak. Suspicion timers grow because a refute did not cancel them, and a refuted node later dies wrongly. The active-timer gauge shows it. The fix is the cancel path (§13, I9, §19 pitfall 5).
  • Slow convergence. Updates take long to spread because of high loss, λ too low or an idle cluster. The convergence metric shows it. The gossip tick and anti-entropy help, and the operator can raise λ or the gossip rate (§13).
  • Metadata bloat. Anti-entropy bandwidth climbs because the application writes oversized meta. antientropy_bytes and meta_oversize_rejected_total show it. Writes are rejected at the codec boundary (§13, I17).

The §13 table also lists cross-cluster merge, auth flood, memory growth and WAN gateway loss. The blueprint cites the Lifeguard paper's account of healthy nodes marked failed in production Serf and Consul deployments because the detecting node was starved of CPU. That is why LHM exists (§13, I11). It cites no single named outage (§13).

Threats worth knowing (§12): T1 a forged Suspect or Dead about a victim, answered by HMAC auth, with incarnation refutation limiting any lie that gets through. T4 gossip amplification by injecting fake updates, answered by the retransmit cap (I7) and a bounded drop-oldest buffer (ADR-29). T5 a decompression bomb or huge list in a TCP sync, answered by size caps. T13 a Byzantine relay lying about a ping-req outcome, diluted by k>1 and bounded by refutation (P5, I1). Even an authenticated false dead is refuted by the victim's higher incarnation (§12, MM10).

The numbers

Symbols (§22): N = cluster size, T′ = period (1 s), k = 3 relays, λ ≈ 3 (also ADR-11; §4 gives λ ≈ 3–4), MTU ≈ 1400 B, R ≈ 40 B per member record, A = 30 s anti-entropy interval. §4 values are design targets, and §22 rows are arithmetic from them.

Quantity Formula N=100 N=1000 N=10000
Per-node message rate, steady 2 / T′ (§22 item 1) 2/s 2/s 2/s
Per-node rate, every period needs indirect probes (worst case) (2 + 2k) / T′ (§22 item 2) 8/s 8/s 8/s
Cluster-wide message rate N × 2 / T′ 200/s 2000/s 20000/s
All-to-all equivalent N(N−1) / T′ ~9900/s ~10^6/s ~10^8/s
Per-node list memory N × 40 B ~4 KB ~40 KB ~400 KB
Convergence latency log2(N) × T′ ~7 s ~10 s ~13 s
Retransmits per update λ · log2(N+1) ~21 ~30 ~40
Anti-entropy bytes per node 2 × N × 40 B / A ~0.27 KB/s ~2.7 KB/s ~27 KB/s

All rows are from the §22 scaling summary, except the worst-case indirect row, which is §22 item 2. The worst-case row is the blueprint's value at its pathological bound of f→1. At a healthy f≈0.02 the same item states about 2.16 messages/s, from its formula 2 + f × 2k with k=3 (§22 item 2).

Other §4 targets, each a design target:

  • Detection time, expected: T′·(1/(1−e^-1)) for the first failed probe, plus the suspicion window (§4).
  • False-positive rate: at most 1% under at most 10% packet loss, with k=3 and Lifeguard on (§4, gate M3).
  • UDP datagram at most the path MTU, about 1400 B (§4, M10); CPU under 1% of one core per node; validated to about 1k nodes in simulation; join gives a usable view in a few periods (§4, M9).
  • File descriptors: about 2 at steady state, independent of N (§22 item 11).
  • Bandwidth: about 400 B/s per node plus about 2.7 KB/s anti-entropy at N=1000, so the ceiling is memory and convergence, not the wire (§22 items 8 and 12).

Two places where the blueprint's numbers need care, stated without resolving them. First, §22 calls the SWIM-versus-all-to-all gap 500× at N=1000, while §19 D.7 calls it three orders of magnitude, comparing about 1000 probes with about 1,000,000 heartbeats. Second, §19 D.2 says the expected time to first probe of a failed node is bounded and size-independent (M2), while §22 item 10 computes about (N+1)/2 · T′, roughly 500 s at N=1000, to be targeted, and treats the size-independent figure as detection once targeted.

How it compares

  • HashiCorp memberlist, Serf and Consul chose almost nothing differently, since memberlist is the reference this design is tested against (ADR-26, §21). Its distinguishing move is packaging: encryption, compression, labels and a Serf event layer in one agent. That is right for a turnkey cluster agent such as Consul.
  • Apache Cassandra chose a φ-accrual detector, which turns heartbeat inter-arrival times into a continuous suspicion level, over a binary Suspect-then-Dead (§21). That fits links with drifting, heterogeneous latency where one static timeout is wrong everywhere. SWIM's version is coarser but cheaper to reason about and refute (§21, §24).
  • Akka Cluster chose a φ-accrual reachability check over gossip and a leader that applies state changes once the view converges (§21). That suits a JVM application cluster where actors are already the concurrency model. The cost is a leader and convergence dependency that SWIM avoids, and the blueprint declines to import it (§21, ADR-15).
  • Redis Cluster chose to require a majority of masters to agree before a failure verdict sticks (PFAIL to FAIL) (§21). That is right where a false eviction triggers slot failover and is expensive. SWIM accepts one node's verdict because its consumers tolerate transient disagreement (§21, P9).
  • Netflix Eureka chose client-driven lease renewal to a central registry, with a self-preservation mode that stops evicting during mass lease loss (§21). That fits a client/server registry where renewing a lease rides on a call clients already make. It gives up eviction accuracy under real mass failure and needs a registry tier that SWIM's peer-to-peer design avoids (§21, P11).

Building it — the phase plan

Build the simulator-friendly pieces first: Phases 0 and 1 give the correctness kernel and a Transport interface with a simulated backend, so Phases 2–7 can be tested without real sockets (Appendix B build order). Build card: blueprints/build-cards/SWIM Membership Protocol.md.

Phase What exists afterwards The proof (acceptance criterion)
0 core types, merge function, shuffled ring every precedence-table cell (§8.3) has a passing test
1 UDP and TCP transport, codec, simulated transport no datagram exceeds the MTU, and leftover piggyback is deferred rather than fragmented (I6)
2 Direct ping/ack failure detector per-node load is constant per period regardless of N, measured in simulation
3 Indirect probing via k relays with selective loss on the direct path only, the target is not suspected
4 Suspicion and refutation a node reaches Dead only via timeout or Leave, never one failed probe (I3)
5 Piggyback dissemination in simulation, an update converges to all N nodes within O(log N) periods
6 TCP push-pull anti-entropy with all gossip for an update dropped, it still converges within one anti-entropy interval
7 Join, graceful leave, Lifeguard a graceful Leave never triggers a Suspect state on peers (I12)
8 Auth, compression, cluster labels a datagram with a bad or missing HMAC is dropped
9 Metrics, deterministic simulator a scenario replays bit-identically under a fixed seed (I14)
10 Conformance, interop, scale runs per-node load is constant across N=100/500/1000
11 WAN / multi-DC gossip tiers a transient WAN partition does not mark a remote DC's nodes Dead
12 Serf-style events and queries a broadcast event reaches all live nodes and, with no loss, is delivered exactly once per node

Appendix B gives per-phase durations and says phases 0–10 take about 11–12 weeks. §1 says Phase 0 (detection, suspicion, dissemination, anti-entropy, Lifeguard) takes 8–11 weeks. The blueprint does not reconcile these (§1, Appendix B).

Questions to test yourself

  1. Why does the suspicion timeout scale with log N rather than being constant, and what failure appears in large clusters if you make it constant? — Hint: §4, §8.5 and MM3 in §20; compare §22 item 9 with the guardrail on refutation time.
  2. On partition heal, what single piece of state distinguishes a node that was merely partitioned from one that actually crashed, and why can only that node produce it? — Hint: §19 D.6, §8.7, MM2 and MM7.
  3. Explain the precise precedence among Alive/Suspect/Dead at equal incarnation, and construct a two-update sequence that flaps a healthy node if you get one cell wrong. — Hint: the §8.3 table and the Phase 0 pitfalls.
  4. Derive the cluster-wide message rate at N=1000 for SWIM vs all-to-all heartbeat, and state the asymptotic gap as a function of N. — Hint: §22 item 3 and §19 D.7; note the two figures the blueprint gives.
  5. Why is anti-entropy necessary if epidemic gossip already reaches all nodes with high probability — and what observable metric tells an operator that gossip is silently under-delivering? — Hint: P7, MM5, Phase 6 and the anti-entropy metrics in §14.

If you only remember three things

SWIM splits failure detection (one probe per node per period, so load is flat in N) from dissemination (rumor spread in O(log N) periods) (MM1, P1, P2). A failed probe produces only a Suspect, and only the node itself can overturn that with a higher incarnation, so false deaths heal and real crashes do not, with no clocks involved (MM2, MM3, P4, P5). The view is eventually consistent by contract, so anything needing agreement belongs to a consensus layer that SWIM merely feeds (MM8, P9).

Words used here

  • Protocol period (T′): the interval at which a node probes one target (§26).
  • Ping / ack: a direct liveness probe and its reply (§26).
  • Ping-req: a request to a relay to probe a target on one's behalf (§26).
  • Suspect: the provisional "maybe dead" state before Dead (§26).
  • Incarnation: a per-node counter that only that node advances (§26).
  • Refutation: a node overriding a false suspicion by raising its incarnation and broadcasting Alive (§26).
  • Piggyback: carrying updates on probe and ack messages instead of separate floods (§26).
  • Infection-style / epidemic: gossip where each informed node infects others (§26).
  • λ (lambda): the retransmit multiplier; updates are sent about λ·log N times (§26).
  • Anti-entropy / push-pull: periodic full-state exchange over TCP that backstops lossy gossip (§26).
  • Lifeguard / LHM: accuracy extensions, including a self-distrust factor that stretches a node's own timers (§26).
  • Convergence: all nodes reaching a consistent view after a change (§26).
  • False positive: a live node wrongly declared dead (§26).
  • MTU: the size limit datagrams must stay under to avoid fragmentation (§26).
  • AP vs CP: available under partition (SWIM) versus consistent under partition (consensus) (§26).
