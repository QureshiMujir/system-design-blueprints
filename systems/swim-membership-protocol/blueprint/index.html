304 — SWIM Membership Protocol

Project Number: 304

Project Name: SWIM Membership Protocol

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Build the SWIM protocol from scratch — Scalable Weakly-consistent Infection-style process group Membership — a decentralized failure detector and membership service in which every node maintains an eventually-consistent view of the live set, detects failures in (near) constant time per node, and disseminates updates epidemically.

The system answers, at every node, two questions cheaply and at scale: who is in the group? and who just failed or joined? — without a central coordinator, without all-to-all heartbeating, and with a per-node message load that does not grow with cluster size.

In scope (Phase 0 deliverable):

  1. core — Member, NodeState (Alive/Suspect/Dead/Left), Incarnation, MembershipList.
  2. transport — UDP (probes, size-bounded) + TCP (full-state sync) abstraction.
  3. codec — compact wire encoding of messages + piggybacked updates.
  4. failuredetector — direct ping/ack on a fixed protocol period; round-robin probe-target selection.
  5. indirect — ping-req via k relays (the SWIM completeness mechanism).
  6. dissemination — infection-style piggyback buffer (λ·log N retransmits, freshest-first).
  7. suspicion — Alive→Suspect→Dead state machine with incarnation-number refutation.
  8. membership — join (via seeds), graceful leave, conflict-resolution rules.
  9. antientropy — periodic TCP push-pull full-state reconciliation.
  10. lifeguard — local health multiplier, adaptive timeouts, buddy system, NACK.
  11. node + cli — embeddable library + a runnable agent (swimd) and inspector (swimctl).

System boundaries. Provides: membership view + failure events (join/leave/fail/update) to an application via callbacks. Delegates: what to do with membership (leader election #198, sharding #98, service discovery #40) to consumers; payload replication to the app. Does NOT provide: strong consistency, total ordering, consensus (use Raft #37 for that), or message delivery guarantees beyond best-effort gossip.

Non-goals (Phase 0): Byzantine fault tolerance (crash/omission model only), cryptographic group membership policy, multi-datacenter WAN gossip tuning (single-LAN assumptions first), payload/event-bus delivery (Serf-style user events) beyond a thin hook, IPv6-only optimizations, NAT traversal.

Deployment model. A library (libswim) linked into each application process + an optional standalone agent. Each node runs one SWIM instance; nodes form a single group via a seed list. Linux/macOS, x86-64/aarch64. Tens to thousands of nodes per group (Phase 0 validated to ~1k in simulation).

Target users. Engineers learning epidemic protocols + failure detection; builders of clustered systems (databases, caches #59, schedulers #200, service meshes #164) needing membership; operators wanting a dependency-free cluster substrate.

What later phases unlock. WAN/multi-DC gossip (separate slow/fast gossip tiers), Serf-style user events + query flooding, encryption keyring rotation, IPv6 + NAT, larger-scale tuning (10k+), metrics-driven adaptive fanout, integration adapters (DNS #40, leader election #198).

Deferred features (each anchored to the phase that builds it — see the Deferred Features Register):

  • WAN multi-DC dual-gossip tiers — PhaseDeferred("Phase 11").
  • Encryption keyring rotation (live re-key) — PhaseDeferred("Deferred Features Register").
  • Serf-style user events + queries — PhaseDeferred("Phase 12").
  • NAT traversal / IPv6-only paths — PhaseDeferred("Deferred Features Register").

Estimated timeline. Phase 0 (failure detector + suspicion + dissemination + anti-entropy + Lifeguard): 8–11 weeks. Hardened + WAN + events: 4–6 months.

Recommended language: Go. Rationale: SWIM's reference implementations (Hashicorp memberlist, serf) are Go, so the design maps 1:1 and reading them is direct; the goroutine + channel model fits the "one goroutine per protocol period, one per probe, a few background loops" structure cleanly; net gives first-class UDP + TCP with the precise control SWIM needs (one UDP socket, bounded datagrams, separate TCP for sync); GC pauses are irrelevant at SWIM's message rates (a handful of small datagrams per second per node). Rejected: Rust (excellent and viable, but the async-runtime + buffer-ownership ceremony slows iteration on a protocol whose hot path is tiny and not CPU-bound; the portfolio's networking projects that need raw throughput chose Rust, but SWIM's bottleneck is latency/topology, not CPU); C (no memory safety for a network-facing daemon parsing untrusted datagrams); Python (GIL + overhead poor for many concurrent timers, though fine for a teaching prototype).

Prerequisites. UDP vs TCP semantics + datagram size limits (MTU/fragmentation); failure-detector theory (completeness vs accuracy); epidemic/gossip dissemination math (O(log N) spread); logical version numbers (incarnation, not wall-clock); basic probability (false-positive analysis); the crash/partition failure model.

2. Why Build This

  • Failure detection done right. Naive clusters all-to-all heartbeat: O(N²) messages, and detection time/accuracy degrade with size. SWIM decouples failure detection (constant load per node) from dissemination (epidemic, O(log N) latency), achieving scalability that heartbeating cannot. Implementing it teaches why this separation is the canonical answer.
  • Epidemic algorithms. Infection-style dissemination — piggybacking updates on probes, retransmitting λ·log N times, freshest-first — is the same family as anti-entropy replication (#99), gossip (#72), and CRDT propagation (#55). SWIM is the cleanest place to internalize it.
  • The incarnation-number idea. Resolving "is node X alive or dead?" without synchronized clocks, using a per-node monotonically increasing incarnation that only X can advance (to refute a false suspicion), is a small, deep, reusable mechanism — a single-writer logical clock for self-state.
  • Suspicion as accuracy tuning. The Suspect state is a tunable knob trading detection latency for false-positive rate; Lifeguard's local-health multiplier makes it adaptive. This is failure-detector engineering you feel in production.
  • Weak consistency that is actually useful. SWIM gives no strong guarantees, yet underpins real clusters. Building it calibrates your sense of when eventual consistency suffices and when you must reach for consensus.
  • Cross-links. Membership feeds leader election (#198), sharding/partition routing (#98), service discovery (#40), distributed caches (#59), schedulers (#200/#302), and gossip-based stores (#36). Contrast with Raft (#37) — SWIM is the AP membership layer beneath CP coordination. Dissemination ↔ #72 gossip, #99 anti-entropy.
  • Calibration. After SWIM, "failure detector," "gossip," and "eventual membership" stop being buzzwords. You can reason about detection time, false-positive rate, convergence latency, and message load as quantities you tune — the core competency behind every large distributed system's liveness layer.

What Mastery Looks Like

  • Design a constant-load failure detector and prove it. You can architect detection that is O(1) per node and demonstrate a flat per-node load curve as N grows — built in Phase 2 (direct ping/ack on the protocol period) and certified in Phase 10 (scale runs at N=100/500/1000).
  • Engineer accuracy as a multiplicative stack of gates. You can reason about and tune the indirect-probe gate (p^(k+1)), the suspicion-timeout gate (∝ log N · T′), and the Lifeguard self-distrust gate as independent, composable knobs — built in Phase 3 (indirect probing), Phase 4 (suspicion), and Phase 7 (Lifeguard LHM).
  • Wield a single-writer logical clock. You can use a per-node incarnation to resolve liveness without synchronized clocks, partition-resilient — and explain why it is strictly simpler than a Lamport/vector clock for self-state — built in Phase 0 (conflict resolution) and Phase 4 (refutation).
  • Implement epidemic dissemination at the theoretical optimum. You can build infection-style gossip that converges in O(log N) rounds with a λ·log N retransmit bound, and justify each constant against branching-process math — built in Phase 5 (dissemination).
  • Build a guaranteed-convergence backstop over best-effort gossip. You can design idempotent anti-entropy push-pull that turns "high-probability" infection into "eventual certainty," and explain the bandwidth tradeoff — built in Phase 6 (anti-entropy).
  • Operate the AP membership layer beneath a CP spine. You can articulate exactly when eventual membership suffices and when to escalate to consensus, and trace a partition-and-heal to prove no permanent error — built in Phase 4 and the partition scenario in Phase 9 (simulator).
  • Make a distributed protocol deterministically debuggable. You can build a logical-clock network simulator that replays any loss/latency/partition scenario bit-identically and expresses every invariant as an assertion — built in Phase 9 (simulation harness).
  • Harden an untrusted-datagram protocol. You can authenticate per-datagram gossip with a rotatable keyring, bound resource exhaustion, and reason about how incarnation refutation structurally limits the blast radius of even authenticated lies — built in Phase 8 (wire hardening).

Per-box.

  • node / API — the embeddable surface: Join(seeds), Leave(), Members(), and event callbacks (member joined/failed/updated/left). The only thing the application sees.
  • membership list — the authoritative local view: per-node {address, state, incarnation, metadata}, the shuffled probe ring (round-robin target order), live suspicion timers, and the conflict-resolution rules that decide which incoming update wins. Single source of truth at this node (no global truth exists by design).
  • failure detector — every protocol period T′, picks the next member from the shuffled ring and pings it; on ack within the timeout, done; on timeout, escalates to indirect probing via k randomly-chosen relays (ping-req). Direct + indirect probing is the SWIM failure detector.
  • suspicion subprotocol — when probing fails (directly and indirectly), the target is marked Suspect (not immediately Dead); a suspicion timer runs; if the target (or anyone) refutes via a higher incarnation Alive, suspicion is cleared; on timeout, it becomes Dead. This is the accuracy/latency knob.
  • dissemination — membership changes (alive/suspect/dead/join/leave) are not flooded as standalone messages; they ride piggybacked on the ping/ack/ping-req traffic. The buffer retransmits each update ~λ·log N times, freshest updates first, then retires it. Infection-style spread reaches the whole cluster in O(log N) periods.
  • anti-entropy — periodically (and on join) a node opens a TCP connection to a random peer and exchanges its entire membership state (push-pull), reconciling by incarnation. This backstops the lossy UDP gossip — any update that failed to infect via piggyback is eventually swept in.
  • lifeguard — the Hashicorp accuracy extensions: a local health multiplier (a node that suspects its own probes are failing dilates its timers, trusting itself less), adaptive probe interval/timeout, a buddy system (route suspicions through the suspected node's near-neighbors first to give it a fast chance to refute), and NACKs to distinguish "target dead" from "I'm unhealthy."
  • codec — compact binary encoding of messages plus the piggyback packing that fits as many updates as possible into each bounded UDP datagram (without fragmentation).
  • UDP transport — one socket; carries pings, acks, ping-reqs, and all piggybacked gossip; datagrams kept under the MTU to avoid fragmentation.
  • TCP transport — reliable, ordered; used only for full-state push-pull (anti-entropy + large join syncs) where the payload exceeds a datagram.

Boundaries. Trust: all datagrams are untrusted (auth via keyring, Phase 8). Concurrency: a probe-period goroutine, per-ping/ping-req goroutines, suspicion timers, an anti-entropy loop, and a receive loop — synchronized through the membership list's lock + a piggyback queue. Persistence: none required (membership is reconstructed on join); optional snapshot for fast restart. Protocol: SWIM messages over UDP; push-pull over TCP.

The defining property: per-node load is constant in N (a node probes one target per period regardless of cluster size). Detection load does not grow; only state memory (O(N)) and convergence latency (O(log N)) do.

6. Design Principles

  1. Constant per-node load, independent of N. A node probes exactly one target per period and relays a bounded number of indirect pings; detection cost never grows with cluster size. Tradeoff: detection of a specific node is probabilistic per period. Violation: per-node heartbeating every peer reintroduces O(N²) and defeats the entire point.
  2. Separate detection from dissemination. Failure detection is the ping/ack mechanism; spreading the news is epidemic piggybacking. They have independent tunables (period vs fanout). Violation: coupling them (flood on every detection) creates message storms.
  3. No synchronized clocks; logical incarnations only. "Alive vs dead" is resolved by per-node monotonic incarnation numbers, advanced only by the node itself (to refute). Tradeoff: no wall-clock ordering of events. Violation: timestamp-based liveness breaks under skew/partition — exactly when you need it.
  4. Suspect before declaring dead. A failed probe yields Suspect, not Dead; a timeout (or refutation) resolves it. Tradeoff: detection latency increases by the suspicion timeout. Violation: immediate Dead on one missed probe makes transient packet loss evict healthy nodes (false positives storm).
  5. Self-refutation is authoritative. Only node X can declare X alive at a higher incarnation; a node that hears itself suspected/declared-dead immediately bumps its incarnation and broadcasts Alive. Violation: letting others "resurrect" a node creates flapping and ambiguity.
  6. Piggyback, don't flood. Updates ride on existing probe traffic; standalone gossip messages are the exception (memberlist adds a small gossip tick, but the principle holds). Tradeoff: dissemination latency bounded by probe rate. Violation: a message per update per node is O(N) bandwidth per change.
  7. Anti-entropy backstops gossip. Periodic full-state TCP sync guarantees convergence even when piggyback updates are lost. Tradeoff: O(N)-sized periodic syncs. Violation: relying on lossy UDP gossip alone leaves permanent divergence after message loss.
  8. Bounded, fragmentation-free datagrams. Pack piggyback updates only up to the safe MTU; never rely on IP fragmentation (fragments amplify loss). Violation: oversized datagrams fragment, and one lost fragment drops the whole probe.
  9. Eventual consistency is the contract — nothing stronger. The membership view converges; it is never claimed globally consistent at an instant. Tradeoff: consumers must tolerate transient disagreement. Violation: building strong-consistency assumptions (e.g. "all nodes agree X is dead now") on top of SWIM is a category error — use consensus.
  10. Accuracy is tunable and adaptive (Lifeguard). False-positive rate is a function of suspicion timeout + local health; a node that detects its own unhealthiness backs off rather than blaming others. Violation: static timeouts make a slow/overloaded node a false-positive generator.
  11. Symmetric, coordinator-free. Every node runs identical logic; there is no master. Tradeoff: no single point to query for "the" view. Violation: a coordinator reintroduces a SPOF and a scaling bottleneck.
  12. Determinism where it aids debugging. Randomness (target selection, relays) is seedable; the shuffled probe ring is a reproducible permutation. Violation: unseeded randomness makes failures unreproducible in test/simulation.
  13. Graceful leave is a first-class event. A departing node broadcasts Leave (a Dead-with-intent at its current incarnation) so peers remove it without a suspicion cycle. Violation: treating intentional shutdown as failure wastes a full detection+suspicion latency and pollutes false-positive metrics.
  14. Observability of liveness. Every state transition (alive/suspect/dead/leave/refute) emits an event + metric; convergence and false positives are measurable. Violation: an undebuggable membership layer turns every cluster incident into guesswork.

8.2 Messages (UDP unless noted)

Type Fields Purpose
ping seqno, source, target, [piggyback] direct liveness probe
ack seqno, source, [piggyback] probe reply
ping-req seqno, source, target, [piggyback] ask a relay to probe target
nack seqno, source relay reachable but target not (Lifeguard)

Every UDP message carries a piggyback section: as many alive/suspect/dead updates as fit under the MTU (I6), freshest-first.

8.3 Conflict-resolution / precedence rules (the heart of correctness)

When an update U{node M, inc i, state S} arrives, compare to local entry L{inc j, state T}:

Incoming S Overrides local when If M == self
Alive(i) i > j (any T), OR refutes a Suspect(j) with i > j (n/a — handled below)
Suspect(i) T==Alive ∧ i ≥ j, OR T==Suspect ∧ i > j refute: self.inc = max(self.inc, i)+1; broadcast Alive(self, self.inc)
Dead(i) i ≥ j ∧ T≠Dead refute if still running: self.inc = i+1; broadcast Alive; else accept + Leave
Leave(i) i ≥ j accept (own shutdown)

Rules in prose: a higher incarnation always wins; at equal incarnation, Suspect beats Alive (caution), Dead beats both; a node hearing itself Suspect/Dead refutes by advancing its own incarnation past the rumor (P5/I1). Dead is terminal for a given incarnation — only a strictly higher incarnation Alive (which a dead node cannot produce) could revive it, so dead stays dead.

8.4 Protocol period (failure detector) — sequence

Step Guard / condition Action
P1 start of every period T′ M = ring.next() — round-robin target selection (I8)
P2 — send ping(seq, →M) [+piggyback]
P3 — wait up to t_direct for ack
P4 ack received within t_direct M stays Alive; apply piggyback; period done
P5 no ack within t_direct (direct probe failed) pick k relays R1..Rk (random, ≠M); send ping-req(seq, target=M) to each Ri [+piggyback]
P6 relay Ri reaches M Ri pings M; on M's ack, Ri forwards the ack to the requester
P7 relay Ri cannot reach M Ri sends nack to the requester (Lifeguard hook)
P8 — wait the remainder of the period for any forwarded ack
P9 any ack received (direct or via a relay) M Alive; period done
P10 no ack from M or any of the k relays before the period ends mark M Suspect (incarnation = current); start suspicion timer; gossip Suspect(M)

        probe fails (direct+indirect)            suspicion timeout

8.6 Worked example — false positive healed

N=5 nodes {A,B,C,D,E}. C is healthy but a transient burst drops A→C and relays' pings.
t0  A probes C: ping times out; ping-req via B,D also time out (unlucky loss)
t1  A marks C Suspect(inc=7); gossips Suspect(C,7) piggybacked
t2  B,D,E receive Suspect(C,7): C was Alive(7) → they mark C Suspect(7), start timers
t3  C (alive!) receives Suspect(C,7) via gossip → REFUTE: C sets inc=8, broadcasts Alive(C,8)
t4  Alive(C,8) infects cluster: 8>7 ⇒ everyone clears Suspect, C Alive(8). False positive healed.
    (Had C truly crashed, no refutation arrives; suspicion timers fire ⇒ C Dead everywhere — I4.)

8.7 Malformed / failure-path examples

  • Datagram larger than MTU → codec refuses to pack beyond MTU (I6); excess piggyback deferred to next message.
  • alive for an unknown node → treated as a join (new member, that incarnation).
  • suspect about self → immediate refute (I1/P5).
  • dead with incarnation < local self incarnation → ignored (stale).
  • Two nodes with the same name, different addr → name is the identity key; addr change with higher incarnation updates the addr (rejoin); conflicting same-incarnation → keep existing, log.
  • Partition: each side suspects then declares the other Dead; on heal, anti-entropy + incarnations reconcile (the side that kept running has advanced incarnations and refutes its own deaths).

0.1 Objectives

Lay down the module, the membership state (Member, MembershipList, ring), and the conflict-resolution function (§8.3) — the correctness kernel — with no networking yet.

0.2 Detailed Implementation Steps

0.3 Deliverable

A membership list that correctly resolves any sequence of alive/suspect/dead/leave updates to the same converged state regardless of order (modulo precedence) — verified in-memory.

0.4 Acceptance Criteria

  • Every precedence-table cell (§8.3) has a passing test.
  • Applying a set of updates in any permutation yields the same final state (order-independence property).
  • Self-suspect/self-dead triggers RefuteSelf with a strictly higher incarnation (I1/P5).
  • Ring visits every member once before repeating (I8 coverage test).

0.5 Conformance Fixtures

resolve/alive-beats-lower-inc, resolve/suspect-beats-alive-equal-inc, resolve/dead-terminal, resolve/self-refute, resolve/order-independence, ring/full-coverage.

0.6 Pitfalls

  • Wrong precedence at equal incarnation (Suspect must beat Alive; Dead beats both) → flapping or missed deaths. Table-drive + exhaustively test.
  • Letting a peer advance our own incarnation → I1 breach, identity chaos. Only RefuteSelf advances selfInc.
  • Ring with replacement → some node never probed for long → unbounded detection time. Use a permutation (I8).
  • Mutating the list without the lock → torn view. All mutations through Merge under the lock (I13).

0.7 Performance Concerns

Merge is O(1) per update (map lookup + comparison). Ring reshuffle is O(N) once per full cycle — negligible. The list lock is held briefly; readers use RLock. No hot loop here.

0.8 Edge Cases

Update about an unknown node (= join); update about self (refute path); equal incarnation same state (no-op); Dead then later Alive same incarnation (rejected — Dead terminal); empty cluster (self only).

0.9 Failure Analysis

A resolve bug corrupts every node's view → cluster-wide disagreement. Blast radius: total (this is the correctness kernel). Containment: exhaustive precedence tests + order-independence property + the simulator (Phase 21). Forensics: log every rejected/applied merge with both incarnations.

0.10 Operational Notes

Metrics from day one: members_total{state}, updates_applied_total, updates_rejected_total, self_refutes_total, incarnation. swimctl members dumps the list. The resolve function's correctness is the foundation every later phase assumes.

  • Codec fuzz survives 5 min (no panic/UB on malformed datagrams).
  • Simulated transport is byte-identical to real for the same inputs.

1.5 Conformance Fixtures

codec/roundtrip-all-types, codec/piggyback-mtu-budget, codec/leftover-deferred, codec/malformed-reject, transport/sim-equiv-real.

1.6 Pitfalls

  • Relying on IP fragmentation → one lost fragment drops the whole probe + its piggyback. Stay under MTU (P8/I6).
  • Unbounded piggyback packing → oversize datagram. Budget by remaining bytes.
  • Codec panic on malformed input → remote DoS (a crafted datagram crashes the daemon). Total decode + fuzz.
  • Endianness / version drift in the wire format → interop breakage. Fix byte order + version the format.

1.7 Performance Concerns

Encoding is per-message and tiny; pool buffers to avoid per-datagram allocation. UDP recv is the only hot path — read into a reused buffer. TCP push-pull is rare (anti-entropy) — correctness over speed.

1.8 Edge Cases

Zero-update piggyback (bare ping); maximum-size single update exceeding MTU alone (must still fit one — bound metadata size); truncated datagram; TCP connection reset mid-sync; dual-stack addresses.

1.9 Failure Analysis

A codec bug either drops messages (silent slowdown of dissemination) or crashes on malformed input (DoS). Detection: fuzz + round-trip + the simulator's loss accounting. Containment: total decode never panics; oversize guard prevents fragmentation. Forensics: log decode errors with the raw bytes (rate-limited).

1.10 Operational Notes

Metrics: udp_sent/recv_total, udp_bytes, decode_errors_total, oversize_dropped_total, piggyback_packed_avg. --mtu N. The simulated transport is the workhorse for every later phase's tests.

Phase 2 — Failure Detector: Direct Ping/Ack + Protocol Period

2.1 Objectives

The core failure-detector loop: every period T′, probe one round-robin target; on ack it's alive, on timeout escalate (Phase 3). Constant per-node load (P1).

2.2 Detailed Implementation Steps

  • failuredetector: a period ticker; each tick calls NextProbeTarget (I8), sends ping(seq), registers a pending-ack with a sub-period timeout.
  • Receive loop: on ping, reply ack (+ piggyback); on ack, resolve the pending probe; apply piggyback to the list.
  • Sequence numbers to match acks to pings; expire stale pending probes.
  • Wire the period to a monotonic clock (P3/ADR-28); seedable target order (I14).

2.3 Deliverable

A node probes peers once per period and marks a non-responding peer as a candidate for suspicion (full suspicion in Phase 4); ack traffic is one ping + one ack per period.

2.4 Acceptance Criteria

  • Per-node UDP load is constant per period regardless of N (measured in sim: 1 ping + 1 ack, plus piggyback) (P1).
  • Every member is probed once per ring cycle (I8).
  • A crashed node (sim: stops acking) is detected as non-responsive within ~1 period of being targeted.
  • Period uses monotonic time; no wall-clock dependence (P3).

2.5 Conformance Fixtures

fd/constant-load, fd/ring-coverage, fd/detect-nonresponsive, fd/ack-matching, fd/monotonic-period.

2.6 Pitfalls

  • Probing all peers per period → O(N) load, defeats SWIM. Exactly one target/period (P1).
  • Ack/seq mismatch → false timeouts. Match acks to pings by seq; expire correctly.
  • Wall-clock period → skew/NTP-step breaks timing. Monotonic clock (P3/ADR-28).
  • Blocking the period loop on a slow probe → cascading delays. Probe asynchronously; the period ticks independently.

2.7 Performance Concerns

The period loop + receive loop are the steady-state hot paths but at trivial rates (a few datagrams/s). Pending-probe map is small (bounded by in-flight probes). No CPU concern; latency/timing correctness is what matters.

2.8 Edge Cases

Cluster of 1 (self only — no probing); target leaves mid-probe; duplicate acks (idempotent); ack arriving after timeout (late — ignore or clear if still pending); clock jump (monotonic immune).

2.9 Failure Analysis

A detector that probes too rarely is slow to detect; too aggressively loads the net. Detection: probe_period, load metrics. Containment: one-target-per-period is structural. Note: this phase only flags non-response; declaring Dead is gated behind suspicion (Phase 4) so a detector bug cannot directly evict nodes.

2.10 Operational Notes

Metrics: probes_sent_total, acks_received_total, probe_timeouts_total, probe_period_seconds, pending_probes. --period-ms, --seed. The constant-load metric is the headline scalability evidence.

Phase 3 — Indirect Probing (ping-req via k Relays)

3.1 Objectives

The SWIM completeness mechanism: when a direct probe times out, ask k relays to probe the target, distinguishing "target dead" from "the direct path is lossy." Reduces false positives without per-node load growth.

3.2 Detailed Implementation Steps

  • On direct-probe timeout, pick k random members (≠ target, ≠ self) and send ping-req(target) (+ piggyback) to each.
  • A relay receiving ping-req pings the target on the requester's behalf; on the target's ack, the relay forwards an ack to the requester.
  • Requester waits the remainder of the period for any forwarded ack; any ack ⇒ target Alive.
  • Lifeguard hook: a relay that itself cannot reach the target sends a nack (Phase 7 uses nack counts).
  • k and the timing budget are configurable (ADR-09).

3.3 Deliverable

A target reachable via some path stays Alive even if the direct probe was lost; only a target unreachable directly and via all k relays proceeds to suspicion.

3.4 Acceptance Criteria

  • Sim with selective loss on the direct A→C path (but B→C, D→C fine): C is not suspected (indirect ack saves it).
  • Sim with C truly crashed: direct + all indirect probes fail ⇒ C suspected.
  • Per-node load still bounded: + up to k ping-reqs only on the (rarer) direct-timeout path.
  • Differential vs memberlist on the same loss scenario (same suspicion outcome).

3.5 Conformance Fixtures

indirect/lossy-direct-path-saved, indirect/true-crash-suspected, indirect/k-relays-load, indirect/relay-forwards-ack, indirect/vs-memberlist.

3.6 Pitfalls

  • k too small → false positives under loss; too large → load spikes on timeout. Tune (default 3).
  • Relay pings target with relay's own identity confusion → ack routed wrong. Carry the original requester; relay forwards.
  • Not bounding indirect within the period → detection latency drifts. Budget direct + indirect within T′.
  • Choosing the suspected/self as a relay → wasted probe. Exclude target + self.

3.7 Performance Concerns

Indirect probing only triggers on direct timeout (the uncommon case under a healthy net), so steady-state load is unchanged (P1). k forwarded pings + acks are the burst; bounded by k. Relay work is one extra ping — negligible.

3.8 Edge Cases

Fewer than k available relays (use what exists); all relays also can't reach target (→ suspect); relay itself down (no forward — counts as no ack); target acks directly and via relay (dedupe); ping-req for a target that left.

3.9 Failure Analysis

Without indirect probing, transient loss = false positives = healthy nodes evicted (then re-refuted) = churn. With it, only genuinely unreachable nodes advance. Detection: false_positive_total should be near-zero under modeled loss with indirect on. Containment: indirect is the accuracy gate before suspicion. Recovery: increase k / suspicion timeout.

3.10 Operational Notes

Metrics: ping_req_sent_total, ping_req_acks_total, indirect_saves_total (target saved by a relay), nacks_received_total. --indirect-k N. indirect_saves quantifies the accuracy benefit.

Phase 4 — Suspicion Subprotocol + Incarnation Refutation

4.1 Objectives

Turn detection into safe state changes: Alive→Suspect on probe failure, Suspect→Dead on timeout, and self-refutation via incarnation numbers (§8.5, P4/P5).

4.2 Detailed Implementation Steps

  • suspicion: on direct+indirect failure, mark target Suspect at its current incarnation; start a suspicion timer (Timeout(N) ∝ suspicion_mult·log(N+1)·T′); gossip suspect.
  • On hearing alive(node, inc') with inc' ≥ suspect inc → cancel timer (I9), mark Alive, gossip.
  • On suspicion timeout (no refute) → mark Dead, gossip dead/confirm, schedule removal after the update has disseminated.
  • Self-refutation: on hearing self Suspect or Dead, RefuteSelf (bump selfInc strictly above the rumor) and broadcast alive(self, selfInc) (I1/P5).
  • Timer management via a timer wheel or per-suspicion timers (I9 — fire once, cancel on resolve).

4.3 Deliverable

The full failure-decision pipeline: transient loss → Suspect → refuted back to Alive; genuine crash → Suspect → Dead everywhere; a falsely-suspected live node refutes itself within a period.

4.4 Acceptance Criteria

  • I3: a node reaches Dead only via timeout or explicit Leave/Confirm, never one failed probe.
  • I4 (sim): a crashed node is marked Dead by every live node within bounded periods.
  • I5 (sim): a transiently-lossy live node is never permanently Dead (self-refute heals it).
  • I9: suspicion timers fire once and are cancelled on refute/leave (no timer leaks).

4.5 Conformance Fixtures

suspect/transient-then-refute, suspect/crash-to-dead, suspect/self-refute-fast, suspect/timeout-scales-logn, suspect/timer-no-leak, suspect/no-direct-to-dead.

4.6 Pitfalls

  • Suspicion timeout too short → false positives under load (a busy node can't refute in time). Scale with log N + Lifeguard (Phase 7).
  • Not cancelling the timer on refute → a refuted node later wrongly declared Dead (I9 breach). Cancel atomically with the state change.
  • Refuting with an equal (not higher) incarnation → the rumor isn't overridden (precedence: Alive needs inc > Suspect's). Bump strictly above.
  • Removing a Dead node before the update disseminates → peers re-learn it as Alive (resurrection). Retire after dissemination window.

4.7 Performance Concerns

Suspicion timers scale with the number of currently-suspected nodes (small in a healthy cluster). A timer wheel keeps O(1) insert/cancel. Self-refutation is a single broadcast — cheap. Dissemination of suspect/dead piggybacks on normal traffic (Phase 5).

4.8 Edge Cases

A node suspected by multiple peers simultaneously (one local Suspect entry; highest incarnation wins); refute racing the timeout (refute must win if it arrives first — lock); suspect about a node that already Left (ignore); incarnation wraparound (u64 — effectively never); a node suspected, refutes, immediately suspected again (flapping — Lifeguard dampens).

4.9 Failure Analysis

This is where false positives (evicting healthy nodes) and missed detections (never marking crashed nodes Dead) both live. Detection: I4/I5 simulator assertions; false_positive_total, suspect_to_dead_total. Containment: suspicion gate (no direct-to-dead) + self-refutation. Recovery: tune suspicion_mult; Lifeguard (Phase 7) makes it adaptive. Forensics: per-node state-transition log with incarnations.

4.10 Operational Notes

Metrics: nodes_suspected_total, suspect_to_dead_total, suspect_refuted_total, self_refutes_total, suspicion_timeout_seconds, suspicion_timers_active. --suspicion-mult N. The suspect→dead vs refuted ratio is the primary accuracy dashboard.

Phase 5 — Infection-Style Dissemination (Piggyback Gossip)

5.1 Objectives

Spread membership updates epidemically by piggybacking them on probe traffic, retransmitting each λ·log N times freshest-first, achieving O(log N) convergence with bounded bandwidth (P6/I7).

5.2 Detailed Implementation Steps

  • dissemination: a gossip buffer holding pending updates with a per-update retransmit counter.
  • On any outgoing UDP message (ping/ack/ping-req), Pack(remainingBytes) selects freshest-first updates that fit (I6), incrementing their counters.
  • Retire an update after λ·log(N+1) transmissions (I7).
  • A small periodic "gossip" tick (memberlist-style) sends gossip to a few random members to bound latency even when probe traffic is sparse.
  • Newer updates preempt older ones in packing (recency ordering) so fresh news spreads fastest.
  • Apply received piggyback through Merge (Phase 0 resolve).

5.3 Deliverable

A single membership change (join/suspect/dead/leave) reaches the whole cluster in O(log N) periods without any standalone flood; bandwidth per change is bounded.

5.4 Acceptance Criteria

  • Sim: an update converges to all N nodes within O(log N) periods (measured curve).
  • I7: no update transmitted more than λ·log(N+1) times.
  • Bandwidth per change is bounded and independent of how the change occurred.
  • Freshest-first ordering verified (a newer update overtakes an older queued one).

5.5 Conformance Fixtures

gossip/converge-logn, gossip/retransmit-cap, gossip/freshest-first, gossip/piggyback-only, gossip/bandwidth-bounded.

5.6 Pitfalls

  • Unbounded retransmission → bandwidth blowup + stale news lingering. Cap at λ·log N (I7).
  • FIFO instead of freshest-first → fresh critical news (a death) stuck behind stale updates. Order by recency.
  • Dissemination only on probe traffic → slow convergence in idle clusters. Add the periodic gossip tick.
  • Re-queuing an update on every reception → never retires, infinite gossip. Count transmissions, not receptions.

5.7 Performance Concerns

Packing is O(buffer) per message — keep the buffer bounded (drop oldest beyond capacity, ADR-29). The λ·log N count means total transmissions per update ≈ N·λ·log N across the cluster — bounded and the theoretical epidemic optimum. Recency ordering needs a priority structure (heap or sorted insert) — small N of pending updates.

5.8 Edge Cases

Buffer overflow under churn (drop oldest, rely on anti-entropy backstop); an update about a node that since changed state (newer update supersedes — resolve handles); very small clusters (log N ≈ 0 → minimum retransmit floor); duplicate updates merged in the buffer.

5.9 Failure Analysis

Lost gossip = divergence; without anti-entropy (Phase 6) some nodes never learn a change. Detection: sim convergence assertions; gossip_convergence_periods. Containment: λ·log N gives high-probability full infection; anti-entropy guarantees it. Recovery: anti-entropy sweep. Forensics: per-update transmission count + reach.

5.10 Operational Notes

Metrics: gossip_queue_depth, gossip_retransmits_total, gossip_updates_retired_total, gossip_convergence_periods (sim), piggyback_bytes_avg. --lambda N, --gossip-interval-ms. Convergence-periods is the dissemination health signal.

Phase 6 — Anti-Entropy (TCP Push-Pull Full-State Sync)

6.1 Objectives

Backstop lossy gossip with periodic full-state reconciliation: a node opens TCP to a random peer, both exchange entire membership lists, and reconcile by incarnation — guaranteeing eventual convergence (P7/I10).

6.2 Detailed Implementation Steps

  • antientropy: a periodic loop (interval ~30 s, ADR) picks a random member, dials TCP, sends its full list (push), receives the peer's (pull), and merges both ways via Merge (I10 — idempotent).
  • Also run push-pull on join (Phase 7) to bootstrap a complete view fast.
  • Handle large lists by streaming over TCP (no datagram limit here).
  • Reconciliation is symmetric: both nodes end with the merge of both states.

6.3 Deliverable

Any update lost by gossip is swept in within one anti-entropy interval; two nodes that diverged (e.g. across a brief partition) reconverge on the next sync.

6.4 Acceptance Criteria

  • Sim: drop all gossip for an update; it still converges within one anti-entropy interval (I4 via backstop).
  • I10: syncing two identical states changes nothing (idempotent).
  • Diverged states (post-partition) reconcile to the incarnation-wise newest per node.
  • Push-pull handles an N=1000 list over TCP without datagram limits.

6.5 Conformance Fixtures

antientropy/sweeps-lost-update, antientropy/idempotent, antientropy/post-partition-reconcile, antientropy/large-list-tcp, antientropy/on-join-bootstrap.

6.6 Pitfalls

  • Anti-entropy too frequent → O(N) TCP syncs dominate; too rare → slow convergence backstop. Tune interval.
  • Non-idempotent merge → sync oscillation. Merge must be a pure function of incarnations (I10).
  • Syncing only push (not pull) → one-directional, the peer doesn't learn our updates. Always bidirectional.
  • Blocking the protocol on a slow TCP sync → period jitter. Run anti-entropy in its own goroutine.

6.7 Performance Concerns

Each sync is O(N) bytes over TCP — the most bandwidth-heavy operation; keep the interval generous and the encoding compact. With one sync per interval per node, aggregate is O(N) syncs/interval cluster-wide — acceptable as a backstop. Compression (Phase 8) helps large lists.

6.8 Edge Cases

Peer unreachable (skip, try next interval); concurrent sync from both directions (idempotent merge — safe); list changes mid-sync (next sync reconciles); a node Left during sync (Dead/Left wins); empty peer list (no-op).

6.9 Failure Analysis

Without anti-entropy, packet loss leaves permanent divergence (gossip is best-effort). With it, convergence is guaranteed (I4). Detection: antientropy_changes_total (non-zero means gossip missed something — a loss signal). Containment: the periodic sweep bounds divergence duration. Forensics: diff applied per sync.

6.10 Operational Notes

Metrics: antientropy_syncs_total, antientropy_changes_total, antientropy_bytes, antientropy_duration_seconds. --antientropy-interval-s. A rising antientropy_changes indicates gossip is under-delivering (loss/MTU issues).

Phase 7 — Membership Lifecycle: Join, Leave, Lifeguard

7.1 Objectives

Complete the lifecycle: join via seed nodes (bootstrap a view), graceful Leave (no suspicion cycle), and the Lifeguard accuracy extensions (local health multiplier, adaptive timeouts, buddy system).

7.2 Detailed Implementation Steps

  • Join: contact seed addresses; push-pull (TCP) with each reachable seed to obtain a full view; announce self via alive(self, inc=1) gossip; emit NotifyJoin callbacks.
  • Leave: broadcast leave(self, current inc); wait briefly for dissemination; peers mark Left and remove without suspicion (I12/P13).
  • Lifeguard local health multiplier (LHM): track missed acks to self (peers failing to ack our pings, or our ping-reqs returning nacks); raise LHM when our own probing seems unhealthy, dilating our probe interval + suspicion timeout (trust ourselves less, blame peers slower) (I11/P10); lower LHM on clean acks; clamp to [0, max].
  • Adaptive timeouts: probe + suspicion timeouts scaled by LHM.
  • Buddy system: when suspecting a node, send the Suspect first to the suspected node's near-neighbors (so it hears + refutes fastest).
  • NACK integration: nacks from relays raise LHM (the relay reached us but not the target — or signals our unhealth).

7.3 Deliverable

A node joins an existing cluster and gets a full view within a few periods; a node leaving disappears cleanly without a suspicion cycle; an overloaded node stops generating false positives (LHM dilates its judgments).

7.4 Acceptance Criteria

  • Join: a new node has a near-complete view within a few periods (push-pull + gossip).
  • I12: a graceful Leave never triggers a Suspect state on peers.
  • I11: a node with high missed-ack-to-self raises LHM and dilates timers (measured); LHM clamped.
  • Sim: under one-sided overload, the overloaded node's false-positive generation drops vs Lifeguard-off.

7.5 Conformance Fixtures

join/seed-bootstrap, join/view-complete-fast, leave/no-suspect-cycle, lifeguard/lhm-raises-on-misses, lifeguard/adaptive-timeout, lifeguard/buddy-fast-refute, lifeguard/fewer-false-positives.

7.6 Pitfalls

  • Join without push-pull → slow, partial initial view. Always TCP-sync with seeds on join.
  • Leave that relies on detection → wasted detection+suspicion latency + a false-positive-looking event. Explicit Leave broadcast (P13).
  • LHM unclamped → runaway dilation (a node stops detecting anything). Clamp [0,max].
  • LHM raised by peer failures (not self) → blames the wrong side. Raise only on signals about our own health (missed acks to us, nacks).
  • Buddy list stale → suspicions routed to dead neighbors. Refresh from the live set.

7.7 Performance Concerns

Join push-pull is O(N) once per join — fine. LHM is O(1) state. Buddy selection is O(small k). Adaptive timeouts add no overhead, just scale existing timers. The whole phase is logic, not throughput.

7.8 Edge Cases

Join with all seeds unreachable (retry/backoff, report error); two nodes joining simultaneously (both gossip alive; resolve handles); leave message lost (falls back to normal detection — Leave is an optimization); LHM at max (effectively very cautious — log it); rejoin after leave (new incarnation, treated as fresh).

7.9 Failure Analysis

A bad LHM makes a node either over-cautious (misses real deaths) or ineffective (LHM stuck low under genuine local trouble → false positives). Detection: local_health_multiplier vs probe_timeouts correlation; the Lifeguard-on-vs-off false-positive comparison. Containment: clamp + the suspicion gate. Recovery: tune LHM bounds. Forensics: LHM time-series alongside ack-miss rate.

7.10 Operational Notes

Metrics: joins_total, graceful_leaves_total, local_health_multiplier, lhm_changes_total, buddy_refutes_total, nacks_to_self_total. swimctl join <seed>, swimctl leave. LHM is the key Lifeguard observability surface.

Phase 8 — Wire Hardening: Security, Compression, Labels

8.1 Objectives

Make the protocol safe on a real network: authenticated (and optionally encrypted) datagrams via a keyring, compression for large syncs, and message labels to prevent cross-cluster contamination.

8.2 Detailed Implementation Steps

  • security (ADR-14): HMAC over each datagram with a shared key (keyring of accepted keys for rotation); reject unauthenticated/forged messages (Threat T1 — spoofed Suspect/Dead); optional AEAD (e.g. AES-GCM) for confidentiality.
  • Keyring: multiple valid keys to allow rolling re-key (live rotation PhaseDeferred("Deferred Features Register") for the seamless variant; static multi-key Phase 0).
  • Compression for TCP push-pull (large lists) and optionally large piggyback.
  • Cluster label: a tag in every message; drop messages whose label doesn't match (prevents two clusters on a shared network from merging — Threat T6).
  • Replay resistance: the incarnation precedence rules (P5/I1) already bound replay damage — even an authenticated stale dead is refuted by the victim's higher incarnation; add a nonce/sequence guard for auth where needed (Threat T7).

8.3 Deliverable

A cluster that ignores forged/foreign/unauthenticated datagrams and resists trivial spoofing; large syncs are compressed; two clusters on one LAN stay separate.

8.4 Acceptance Criteria

  • A datagram with a bad/missing HMAC is dropped (auth test).
  • Encrypted mode round-trips; plaintext rejected when encryption required.
  • A foreign-label message is dropped (no cross-cluster merge).
  • Compression reduces large push-pull size measurably with no semantic change.

8.5 Conformance Fixtures

security/hmac-reject-forged, security/aead-roundtrip, security/keyring-multi-key, security/label-mismatch-drop, security/compression-roundtrip, security/replay-bounded.

8.6 Pitfalls

  • No datagram auth → any host can declare any node Dead (spoofed suspicion/dead). HMAC every message (Threat T1).
  • Single key, no ring → re-keying requires full cluster downtime. Keyring with multiple valid keys.
  • Compressing then forgetting to bound decompressed size → decompression bomb DoS. Cap decompressed bytes.
  • No cluster label → a stray node from cluster B poisons cluster A's membership. Label + drop mismatches.

8.7 Performance Concerns

HMAC per datagram is cheap (small messages). AEAD adds modest CPU — still negligible at SWIM rates. Compression helps only large payloads (push-pull); skip it for tiny datagrams (overhead > savings). Keyring lookup is O(keys) on auth failure — keep the ring small.

8.8 Edge Cases

Key rotation window (old + new keys both valid); a node with the wrong key (its messages dropped — appears silent → suspected → dead, correctly); oversized compressed payload; label change mid-cluster (treat as a new cluster); HMAC over which bytes (cover the whole datagram incl. piggyback).

8.9 Failure Analysis

Without auth, the protocol is trivially abusable (spoof a dead for the leader → cluster disruption). Detection: auth_failures_total, foreign_label_dropped_total. Containment: drop-on-auth-fail + incarnation rules (even an authenticated false dead is refuted by the victim). Recovery: rotate keys; isolate the bad actor. Forensics: log auth failures with source addr (rate-limited).

8.10 Operational Notes

Metrics: auth_failures_total, foreign_label_dropped_total, encrypted_messages_total, compression_ratio. --keyring file, --label name, --encrypt. Auth-failure spikes indicate misconfiguration or attack.

Phase 9 — Observability, Convergence Measurement, Simulation Harness

9.1 Objectives

Make liveness fully observable and the protocol testable at scale: metrics + events for every transition, a convergence/detection measurement harness, and the deterministic network simulator that all earlier phases lean on.

9.2 Detailed Implementation Steps

  • observability: Prometheus metrics (all the per-phase counters), structured slog events, and the Delegate callbacks (NotifyJoin/Leave/Update) for the application.
  • sim/network.go: an in-memory Transport with controllable per-link loss, latency distributions, and partition sets; deterministic under a seed (I14).
  • Convergence/detection measurement: instrument the sim to record, per scenario, the periods-to-converge and detection time distributions.
  • sim/scenarios: join-storm (many nodes join at once), partition-heal, false-positive-under-loss, mass-failure (k nodes crash), rolling-restart.
  • swimctl inspector: dump members, force a leave, show LHM + suspicion timers.

9.3 Deliverable

Dashboards + a simulator that reproduces any membership scenario deterministically and measures convergence/detection/false-positive quantitatively.

9.4 Acceptance Criteria

  • Every state transition emits a metric + event (coverage audit).
  • Sim reproduces a scenario bit-identically under a fixed seed (I14).
  • Measured convergence is O(log N) and detection time is size-independent (matches the SWIM analysis) on the scenario suite.
  • False-positive rate under modeled loss (sim/false-positive-rate fixture, §4) stays ≤1% at 10% packet loss with indirect probing + Lifeguard on, versus an order-of-magnitude higher rate with both off (M3).

9.5 Conformance Fixtures

sim/deterministic-replay, sim/convergence-logn-curve, sim/detection-size-independent, sim/false-positive-rate, sim/partition-heal, sim/mass-failure.

9.6 Pitfalls

  • Non-deterministic sim → unreproducible test failures. Seed all randomness (I14).
  • High-cardinality metrics (per-peer labels) → Prometheus blowup. Aggregate; per-state counts, not per-node.
  • Measuring convergence with wall-clock → flaky. Measure in protocol periods (logical).
  • Simulator that diverges from real transport behavior → green sim, broken prod. Keep the sim a faithful Transport (Phase 1 equivalence test).

9.7 Performance Concerns

The simulator must scale to ~1k nodes in-process — use lightweight goroutines/event-loop and a logical clock (don't real-time-sleep periods; tick logically). Metrics scrape is cheap. Event callbacks must not block the protocol (deliver async).

9.8 Edge Cases

Simulating N=1 (degenerate); a partition that never heals (each side stable, the other Dead — correct); extreme loss (>50% — convergence degrades gracefully, measured); simultaneous mass join + mass fail.

9.9 Failure Analysis

This phase is the failure-analysis capability for the whole project: it is how I4/I5/I7 and the SWIM analytical claims are validated. A gap here means later regressions go unnoticed. Validate that every invariant (§7) has a simulator assertion.

9.10 Operational Notes

Metrics: the full set from prior phases, plus convergence_periods, detection_time_periods, false_positive_rate (sim). Dashboards: cluster size + state breakdown, suspicion activity, gossip health, anti-entropy changes, LHM distribution. The simulator + conformance report is the "Done" gate.

10.1 Objectives

10.3 Deliverable

make sim + make conformance green; documented convergence/detection/load curves matching the SWIM analysis; interop demonstrated on core messages.

10.4 Acceptance Criteria

Phase 11 — WAN / Multi-Datacenter Gossip Tiers

11.1 Objectives

Extend single-LAN SWIM to spanning datacenters: a fast LAN tier per DC plus a slow WAN tier connecting DCs, with latency-aware timing and probe selection. Fulfils the WAN multi-DC deferral (this phase; see the Deferred Features Register).

11.2 Detailed Implementation Steps

  • Dual pools (Serf model): each node is in a LAN pool (all nodes in its DC, fast gossip, T′≈1 s) and, for designated nodes, a WAN pool (one+ members per DC gossiping across DCs with relaxed timing — longer period, more relays, larger suspicion timeout).
  • Cross-DC membership (I15): the WAN tier disseminates only DC-level / gateway membership; full per-node lists stay LAN-local to bound WAN bandwidth.
  • Network coordinates (Vivaldi): maintain a coordinate per node estimating RTT; bias probe-target selection and timeouts by predicted latency so a slow link isn't mistaken for a failure.
  • Relaxed accuracy on WAN (P4): higher suspicion multiplier + more indirect relays across DCs (loss/latency is higher); the suspect-before-dead gate is widened so transient WAN loss never evicts a whole DC before refutation can cross.
  • Tier-aware Lifeguard (I11): the local health multiplier is tuned separately per tier.

11.3 Deliverable

A cluster spanning ≥2 DCs where intra-DC failure detection stays fast and accurate while cross-DC membership converges over the slower, lossier WAN without false-positive DC evictions.

11.4 Acceptance Criteria

  • Intra-DC detection/convergence unchanged from single-LAN targets (M1/M2/M6 hold per DC).
  • A transient WAN partition does not falsely mark a remote DC's nodes Dead (heals on reconnect via WAN anti-entropy).
  • WAN bandwidth bounded (only gateway/DC-level state crosses, not full per-node lists).
  • Vivaldi coordinates reduce cross-DC false positives vs latency-blind timing (sim comparison).

11.5 Conformance Fixtures

wan/two-dc-converge, wan/transient-partition-no-evict, wan/bandwidth-bounded, wan/vivaldi-fewer-fp, wan/relaxed-suspicion.

11.6 Pitfalls

  • Using LAN timing on WAN links → high-latency links look like failures → DC-wide false positives. Relaxed per-tier timing.
  • Gossiping full per-node lists across DCs → WAN bandwidth blowup. Cross only DC/gateway-level state.
  • One WAN member per DC (SPOF) → losing it isolates the DC at the WAN tier. ≥2 WAN members per DC.
  • Vivaldi coordinate drift → bad latency estimates → wrong timeouts. Clamp + periodically re-anchor coordinates.

11.7 Performance Concerns

WAN tier runs at a slower period — lower message rate, but each message may be lossier; more retransmits (λ) compensate. Network coordinates add O(1) per-probe math. Keeping full lists LAN-local is the key bandwidth lever; WAN carries O(#DCs), not O(N).

11.8 Edge Cases

A DC with a single node (it is its own gateway); asymmetric WAN loss (one direction worse); a DC rejoining after a long partition (WAN anti-entropy full sync); clock-free still holds (incarnations, not timestamps, across DCs); coordinate cold-start.

11.9 Failure Analysis

A WAN-timing bug evicts entire datacenters on transient cross-DC loss — a large blast radius. Detection: per-DC reachability metrics; wan_false_evictions. Containment: relaxed WAN suspicion + ≥2 gateways/DC + incarnation refutation across the WAN tier. Recovery: WAN anti-entropy reconciles on reconnect. Forensics: per-tier transition logs.

11.10 Operational Notes

Metrics: wan_members, wan_period_seconds, wan_partition_events, vivaldi_rtt_error, per-tier suspicion/refute counts. --wan-members, --wan-period-ms, --wan-suspicion-mult. Runbook dc-partition.md. Document the LAN-fast / WAN-slow two-tier model prominently — it is the most common operator confusion.

Phase 12 — Serf-Style User Events and Queries

12.1 Objectives

Layer an application event bus on the membership substrate: best-effort broadcast user events and request/response queries over the same gossip, ordered + deduped by a Lamport clock. Fulfils the Serf-style events deferral (this phase; see the Deferred Features Register).

12.2 Detailed Implementation Steps

  • Lamport clock: a cluster-wide logical clock; each event/query stamped with a Lamport time for ordering + dedup (distinct from per-node incarnations, which are for liveness).
  • User events: app calls Broadcast(name, payload); the event piggybacks on gossip with a Lamport time + TTL; nodes dedup via an event buffer (recent Lamport times) and deliver once to the app; coalesce same-name events where configured.
  • Queries: Query(name, payload, timeout) floods a query (Lamport-stamped) across the cluster; each node optionally responds; responses are gossiped/uni-cast back to the originator, which collects until timeout or response-threshold.
  • Dedup + retransmit: same λ·log N infection-style spread (I7) with a per-message dedup window; bound payload size (MTU, I6).
  • Delivery semantics: at-least-once-ish, best-effort (no guarantee under heavy loss) — explicitly weak, matching the membership layer's contract (P9).

12.3 Deliverable

Applications can broadcast events and run cluster-wide queries over the existing gossip — no new transport — with ordering, dedup, and bounded fanout.

12.4 Acceptance Criteria

  • A broadcast event reaches all live nodes (O(log N) periods) and is delivered exactly once per node (dedup) under no-loss; best-effort under loss.
  • Queries collect responses from live nodes within the timeout; late responses dropped.
  • Lamport ordering is monotonic; out-of-order/duplicate events filtered.
  • Event/query payloads never exceed MTU (I6); fanout bounded (I7).

12.5 Conformance Fixtures

events/broadcast-reaches-all, events/dedup-once, events/lamport-order, query/collect-responses, query/timeout-drops-late, events/payload-mtu-bound.

12.6 Pitfalls

  • Confusing Lamport time (events) with incarnation (liveness) → ordering/refutation bugs. Keep the two clocks separate and distinctly purposed.
  • No dedup window → an event delivered many times as it re-infects. Track recent Lamport times per name.
  • Unbounded event payloads → fragmentation (I6 breach). Cap payload; large blobs go out-of-band (app's job).
  • Treating events as reliable → app assumes delivery that loss can break. Document best-effort (P9).

12.7 Performance Concerns

Events share the gossip budget with membership updates — prioritize membership (liveness) over user events in packing under pressure. Query floods are O(N) responses to the originator — bound response size + use a response threshold to stop early. Event buffer is bounded (recent window).

12.8 Edge Cases

Event broadcast during a partition (only the local side hears it; other side gets it on heal if within TTL — else lost); a query with zero responders; duplicate query ids; Lamport clock skew across a rejoining node (clock advances to max-seen); coalescing dropping a meaningful distinct event (config carefully).

12.9 Failure Analysis

User events competing with membership gossip can starve liveness updates if not prioritized — a subtle availability risk (membership is the priority). Detection: membership convergence regressions when events are heavy; event_gossip_share. Containment: membership-first packing; bounded event buffer. Recovery: throttle events. Forensics: Lamport-time event log.

12.10 Operational Notes

Metrics: user_events_total, events_delivered_total, events_deduped_total, queries_total, query_responses_total, lamport_time. swimctl event <name> <payload>, swimctl query <name>. Document that events are best-effort and share the membership gossip budget.

19. Scalability Analysis

  • The headline property: per-node detection load is constant in N — one probe target per period — so adding nodes does not increase any single node's failure-detection traffic. This is what heartbeating (O(N) per node, O(N²) cluster) cannot do, and it is the entire reason SWIM exists.
  • What does grow: state memory is O(N) per node (one entry per member); convergence latency is O(log N) periods (epidemic spread); anti-entropy sync size is O(N) bytes (periodic).
  • Dissemination scaling: infection-style spread reaches all N in O(log N) rounds with λ·log N retransmits/update — the epidemic optimum; bandwidth per change is bounded.
  • Bottleneck #1 anti-entropy: O(N)-sized TCP syncs are the heaviest op; interval-tuned + compressed; aggregate O(N) syncs/interval cluster-wide.
  • Bottleneck #2 membership memory: O(N) entries; at 10k+ nodes, metadata size + list memory dominate — bound metadata, consider sub-grouping (WAN tiers — Phase 11).
  • Bottleneck #3 convergence under loss: high loss degrades the epidemic; anti-entropy guarantees eventual convergence but the latency grows — measured + documented.
  • Horizontal scaling: linear in nodes (symmetric, coordinator-free, P11); no central bottleneck.
  • WAN scaling (deferred): a single fast-gossip tier doesn't suit high-latency WAN links; dual-tier gossip (fast LAN, slow WAN) is the Phase 11 extension.
  • Practical ceiling (Phase 0): validated to ~1k in simulation; beyond that, sub-grouping + WAN tiers + metadata discipline are the levers.

Domain Deep Dive — Why SWIM Scales Where Heartbeating Fails

The reason SWIM matters is best seen by contrast. Walk through the alternatives and the math.

D.1 The all-to-all heartbeat baseline

Every node sends a heartbeat to every other node every period: O(N) messages sent per node, O(N²) per cluster per period. At N=1000 that's a million messages/period. Worse, to detect a failure you wait for a heartbeat-miss timeout; to keep false positives low you lengthen the timeout, which lengthens detection. Accuracy and load both degrade with size. This does not scale, full stop.

D.2 SWIM's decoupling

SWIM splits the problem:

  • Detection is a random probe, not a broadcast. Each node probes one target per period (+ k indirect only on failure). Load is O(1) per node per period, independent of N (M1). The probability any given node is checked in a period is ~1/N, but over a full ring cycle (N periods) every node is probed exactly once (I8) — so expected time-to-first-probe of a failed node is bounded and size-independent (M2).
  • Dissemination is epidemic, not a broadcast. One node learns of a death and infects others by piggybacking; each infected node infects more. Like a rumor, it reaches all N in O(log N) rounds (M6) with each update sent ~λ·log N times (M7, I7) — bounded bandwidth.

The two have independent knobs: probe period (detection latency) and gossip fanout/λ (dissemination latency). Neither involves O(N) per-node work.

D.3 The accuracy mechanism in numbers

A single missed probe under p% packet loss would, in a direct-only detector, falsely suspect a node with probability ~p per probe. Indirect probing through k relays drops that to ~p^(k+1) (the target is only suspected if the direct probe and all k relay probes are lost) — at p=0.1, k=3 that's 10⁻⁴ instead of 10⁻¹ (M3). The Suspect state adds a second gate: even a falsely-suspected node has a full suspicion-timeout window (∝ log N · T′, M5) to refute via its incarnation (M4). Lifeguard's LHM adds a third: a node whose own probes are failing (it's overloaded, not its peers) dilates its own timers rather than blaming others (I11). Three independent multiplicative accuracy gates — that is how SWIM keeps false positives low without sacrificing detection speed.

D.4 Incarnations: liveness without clocks

The deep trick is resolving "alive or dead?" with no synchronized clock. Each node owns a monotonic incarnation it alone advances (I1). A suspect/dead rumor carries the incarnation it was observed at; the only way to overturn it is an alive at a strictly higher incarnation — which only the node itself can mint (P5). So a false death is self-healing (the victim refutes) and a true death is permanent (a crashed node mints nothing). No timestamps, no clock sync, partition-resilient. Compare Lamport/vector clocks (#95): incarnations are a single-writer logical clock for one node's self-state — simpler and exactly sufficient.

D.5 Where the bodies are buried

Every nasty SWIM bug is one of: (1) a conflict-resolution precedence error (§8.3) — wrong winner → flapping or zombies; (2) MTU/fragmentation silently dropping gossip (I6) — slow convergence with no obvious cause; (3) suspicion timer not cancelled on refute (I9) — a refuted node later wrongly dies; (4) per-node load secretly growing with N (a "probe all suspects" shortcut) — defeats the entire premise. The deterministic simulator (Phase 9) exists precisely to catch these — each maps to an invariant assertion. Internalize this deep dive and you can reason about any gossip-based liveness layer.

D.6 The canonical scenario — partition and heal

Nothing tests a membership protocol like a network partition. Trace one with 6 nodes {A,B,C} | {D,E,F} split by a link cut:

t0   healthy: all 6 Alive, everyone's incarnation = 1
t1   PARTITION: {A,B,C} cannot reach {D,E,F}
t2   A probes D: direct ping lost; ping-req via B,C also can't reach D ⇒ A marks D Suspect(1)
       (symmetrically D's side suspects A,B,C)
t3   gossip within {A,B,C}: B,C also mark D,E,F Suspect(1)
t4   suspicion timers (∝ log N · T′) expire with no refutation possible across the cut
       ⇒ {A,B,C} mark {D,E,F} Dead(1); {D,E,F} mark {A,B,C} Dead(1)
       Each side now has a coherent 3-node view. NO node crashed — this is correct AP behavior:
       under partition, each side reports the reachable set. (Consensus would block; SWIM does not — P9.)
t5   HEAL: link restored. Anti-entropy: A dials D (TCP push-pull).
       A's list says D=Dead(1); D's list says D=Alive(1) locally — but D is the authority on D.
t6   Reconcile: D sees itself Dead(1) in A's pushed state ⇒ D REFUTES: D.inc=2, broadcasts Alive(D,2).
       2 > 1 ⇒ A,B,C accept Alive(D,2). Symmetrically E,F refute; A,B,C refute on the other side.
t7   Within O(log N) periods + one anti-entropy round, all 6 converge back to Alive (incarnations now 2).

The crucial insight: the partition produced no permanent error because (a) each side stayed internally consistent and available (no blocking, P9), and (b) on heal, every falsely-dead node refuted itself with a higher incarnation (P5/I1) and anti-entropy guaranteed the refutations propagated (P7/I10). This is precisely invariant I5 (eventual accuracy) realized. Had a node truly crashed during the partition, it mints no higher incarnation, so it stays Dead (I4). The incarnation number is what distinguishes "was partitioned" from "actually died" — without it, you could not tell them apart on heal.

D.7 The load math — why "constant per node" is literal

Let cluster size be N, protocol period T′. Per node, per period:

  • 1 ping sent to one target + 1 ack received (or sent, as a target) ⇒ ~2 messages, independent of N.
  • On the fraction f of periods where the direct probe fails (f is small under a healthy net), +k ping-reqs + their acks ⇒ +O(k) messages, k constant (=3).
  • Piggyback rides on those same messages — zero extra datagrams; it only fills bytes already in flight (bounded by MTU, I6).
  • Anti-entropy: 1 TCP sync per anti-entropy interval (≫ T′), O(N) bytes but amortized over many periods ⇒ negligible per-period.

So steady-state per-node message rate ≈ (2 + f·O(k)) / T′ — a constant, not a function of N (M1). Cluster-wide it is O(N) messages/period (each node sends ~1 probe), versus all-to-all heartbeating's O(N²). At N=1000: SWIM ≈ 1000 probes/period; heartbeating ≈ 1,000,000. That three-orders-of-magnitude gap at 1k nodes (and growing with N) is the whole reason the protocol exists — and why the §10 scale test asserts a flat per-node load curve as the headline result.

D.8 Tuning the three knobs

SWIM's behavior is governed by three operator-facing parameters; understanding their tradeoffs is the difference between a stable cluster and a flapping one.

  • Protocol period T′ (detection latency vs load). Shorter T′ → faster detection but more probes/sec/node. Detection time of a specific failure ≈ proportional to T′. Typical 1 s. Halving it doubles steady-state traffic for a 2× faster detection — rarely worth it past ~1 s on a LAN. It does not change the shape of scaling (still constant per node); it scales the constant.
  • Suspicion multiplier (accuracy vs detection latency). Suspicion timeout ≈ mult · log(N+1) · T′. Higher mult → fewer false positives (more time to refute) but slower confirmation of true deaths. The log(N+1) factor matters: in a bigger cluster, a refutation needs more periods to propagate, so the window must grow with N or large clusters false-positive. This is the knob you raise when you see false-positive storms under load.
  • Fanout: λ (retransmits) and k (indirect relays). λ governs dissemination — higher λ → faster, more reliable convergence but more bytes per update; λ≈3–4 gives high-probability full infection. k governs accuracy — higher k → fewer false positives under loss (probability ≈ p^(k+1)) but a bigger burst on each direct-probe failure; k=3 is the sweet spot. Crucially, both are multipliers on bounded operations, so raising them does not break the constant-per-node-load property — it scales the constant, never the exponent in N.

The interaction to internalize: detection latency is set by T′ + suspicion timeout; accuracy is set by k + suspicion timeout + Lifeguard; convergence latency is set by λ + T′ + anti-entropy interval. They are largely independent dials, which is exactly why SWIM is tunable in production where a monolithic heartbeat-timeout is not. Lifeguard's LHM makes the suspicion knob adaptive per node, so a single overloaded machine self-corrects instead of forcing you to detune the whole cluster.

Consolidated Pitfalls (Top 10, cross-phase)

  1. Conflict-resolution precedence error — wrong winner between Alive/Suspect/Dead at equal incarnation → flapping or zombie members. Example: letting Alive(i) beat Suspect(i). Guard: §8.3 table, exhaustively tested (I2).
  2. Per-node load secretly O(N) — a "probe all suspects" or "heartbeat everyone" shortcut defeats SWIM's entire premise. Example: pinging every member each period. Guard: one target/period (P1, M1, I8).
  3. Datagram exceeds MTU — fragmentation, one lost fragment drops the probe + its piggyback → silent slow convergence. Example: packing too many updates. Guard: MTU-bounded packing (I6, M10).
  4. Direct-to-Dead on one failed probe — transient loss evicts healthy nodes (false-positive storm). Example: skipping the Suspect state. Guard: suspicion gate (P4, I3).
  5. Suspicion timer not cancelled on refute — a refuted node later wrongly declared Dead. Example: timer fires after Alive arrived. Guard: cancel atomically with state change (I9).
  6. Letting a peer advance our own incarnation — identity/liveness chaos. Example: accepting Alive(self, higher-inc) from another node. Guard: only RefuteSelf advances selfInc (P5, I1).
  7. Removing a Dead node before the update disseminates — peers re-learn it as Alive (resurrection). Example: instant delete on timeout. Guard: retire after the dissemination window.
  8. No anti-entropy backstop — UDP gossip loss leaves permanent divergence. Example: relying on piggyback alone. Guard: periodic TCP push-pull (P7, I10, M8).
  9. Unauthenticated datagrams — anyone can spoof a dead about any node. Example: no HMAC. Guard: keyring auth (§8, T1) — and incarnation refutation bounds even authenticated lies.
  10. LHM raised by peer failures instead of self — blames the wrong side, either over-cautious or ineffective. Example: raising LHM when a peer doesn't ack (could be the peer's fault). Guard: raise only on signals about our own health (I11, P10).

20. Mental Models & First Principles

The compressed intuitions an expert holds about SWIM. Each is one load-bearing sentence, what it predicts, the bug class you write without it, and where this blueprint applies it.

MM1 — Detection is a poll of one; dissemination is a rumor that infects.

  • Insight: SWIM is two independent loops bolted together — a round-robin poll (one target per period) and an epidemic spread (each informed node infects others).
  • Predicts: per-node load is flat in N (the poll is O(1)) while news still reaches everyone in O(log N) (the rumor branches).
  • Bug without it: you conflate the two and "flood on detection," resurrecting O(N) per-change bandwidth.
  • Applied: §3 (the two-loop architecture), Phase 2 (the poll), Phase 5 (the rumor).

MM2 — The incarnation is a single-writer logical clock for self-state.

  • Insight: only node X advances X's incarnation, and a claim about X is overturnable only by a strictly higher incarnation X mints.
  • Predicts: a false death self-heals (the victim refutes) and a true death is permanent (a crashed node mints nothing) — with no synchronized clock.
  • Bug without it: you reach for wall-clock timestamps and your liveness logic breaks precisely under the skew/partition you needed it to survive.
  • Applied: §8.3 (precedence rules), §8.5 (refutation), Phase 0, Phase 4.

MM3 — Suspicion is a probability gate, not a state.

  • Insight: marking a node Suspect buys a window (∝ log N · T′) in which a false accusation can be refuted before it becomes a Dead verdict.
  • Predicts: lengthening the window trades detection latency for a lower false-positive rate, monotonically.
  • Bug without it: you go Alive→Dead on one missed probe and a transient packet-loss burst evicts a third of a healthy cluster.
  • Applied: §8.5 (the FSM), Phase 4, and the window duration derived in §22 (#9).

MM4 — Accuracy is a product of independent gates, so it improves multiplicatively.

  • Insight: false-positive probability ≈ p (direct only) → p^(k+1) (indirect) → × the refutation-window survival → × Lifeguard self-distrust.
  • Predicts: three cheap, composable knobs drive false positives down by orders of magnitude without slowing true-death detection.
  • Bug without it: you over-tune one knob (a huge suspicion timeout) and make true-death detection unusably slow.
  • Applied: Phase 3 (k), Phase 4 (window), Phase 7 (LHM); the p^(k+1) math is worked in the Domain Deep Dive (D.3) and §22 (#2).

MM5 — Anti-entropy converts "probably" into "eventually certain."

  • Insight: epidemic gossip gives high-probability full infection; a periodic full-state push-pull (idempotent) closes the residual-loss gap.
  • Predicts: even if every piggybacked copy of an update is lost, the update still converges within one anti-entropy interval.
  • Bug without it: a run of bad luck on a critical dead leaves permanent divergence and you never find out why.
  • Applied: §6 (P7), Phase 6, I10.

MM6 — The MTU is a hard wall; fragmentation is silent death.

  • Insight: a datagram over the path MTU fragments, and losing one fragment loses the whole probe plus all its piggyback.
  • Predicts: packing "just a few more updates" past the MTU degrades convergence with no error message and no obvious cause.
  • Bug without it: you debug "mysterious slow gossip" for days before finding the oversize datagrams.
  • Applied: §6 (P8), Phase 1, I6, and the FD-budget number in §22.

MM7 — A partition is indistinguishable from mass death until you ask the incarnation.

  • Insight: during a split each side correctly reports its reachable set as the cluster; on heal, only the nodes that were alive can mint a higher incarnation to refute their false death.
  • Predicts: partition-and-heal produces zero permanent error, and the incarnation is the single bit that tells "was partitioned" from "actually died."
  • Bug without it: on heal you either resurrect genuinely-dead nodes or permanently kill survivors.
  • Applied: §8.7, the partition trace in the Domain Deep Dive (D.6), Phase 9, I4/I5.

MM8 — SWIM is the AP membrane; consensus is the CP spine.

  • Insight: SWIM never blocks and never agrees; it tells each node who is reachable, cheaply, at scale.
  • Predicts: you must layer consensus (Raft #37) on top for any decision needing agreement (quorum reconfig, leadership) — SWIM feeds it liveness but cannot replace it.
  • Bug without it: you build strong-consistency assumptions ("everyone agrees X is dead now") on an eventually-consistent substrate — a category error.
  • Applied: §6 (P9), §1 (boundaries), the comparison in §21 and the consensus road in §24.

MM9 — The simulator is the protocol's microscope; logical time is its lens.

  • Insight: a failure detector is defined by behavior under loss/latency/partition — conditions a real network won't reproduce on demand — so you test in a deterministic in-memory network ticked in logical periods, not wall-clock.
  • Predicts: every invariant becomes a reproducible assertion and convergence is measured in periods, not flaky milliseconds.
  • Bug without it: you ship green unit tests and a cluster that flaps in production under conditions you never exercised.
  • Applied: §9 (ADR-22), Phase 9, I14, and every phase's N.5 fixtures.

MM10 — Even authenticated lies are bounded by the protocol's own logic.

  • Insight: auth (HMAC) stops forged messages, but the deeper defense is that a false dead — authenticated or not — is automatically refuted by the victim's higher incarnation.
  • Predicts: the blast radius of a membership lie is one refutation round, not a cluster-wide eviction.
  • Bug without it: you treat auth as the only line of defense and panic when you realize an insider key could declare anyone dead.
  • Applied: §8 (Phase 8), the Threat Model (T1/T7), P5/I1.

How the models chain. These ten are not a list — they compose into one line of reasoning. MM1 splits the problem into a cheap poll and an epidemic spread, which is what makes the load flat (§22 #1). MM3 and MM4 then layer accuracy gates onto the poll so the cheap detection is also correct, and MM2 supplies the single mechanism — the incarnation — that makes those gates refutable without a clock. MM5 backstops the epidemic so "probably converged" becomes "eventually certain," while MM6 guards the one physical constraint (the MTU) that can silently break the spread. MM7 shows the incarnation paying off again at the hardest case (partition heal), and MM8 places the whole thing in the broader stack: SWIM is the AP liveness membrane, never the CP agreement spine. MM9 is the meta-model — the simulator is how you prove the other nine hold under conditions you can't reproduce on a real network — and MM10 is the security closure: the same incarnation refutation that heals false positives also bounds the blast radius of malicious lies. Hold all ten and you can predict SWIM's behavior under any load, loss, partition, or attack from first principles, which is the entire point of building it.

Reading the table. The first three columns are the same protocol family — SWIM and memberlist are nearly identical (memberlist is the reference), and the difference from Cassandra/Akka is concentrated in the failure-verdict and consistency rows: SWIM/memberlist use a discrete, refutable Suspect→Dead with eventual/weak (AP) views, while Akka adds a leader to coordinate convergence and Redis adds a quorum gate before a FAIL verdict commits. Everything else (O(1) per-node load, clock-freedom, gossip dissemination) is shared — which is the point: these four are all variations on "poll cheaply, gossip the result, resolve conflicts with a logical version," and they diverge precisely at how strong a verdict is and who must agree to it. Eureka is the outlier in the dissemination row: it has no peer-to-peer gossip at all — liveness flows client→registry, not node→node — trading SWIM's coordinator-freedom (P11) for a simpler client integration.

HashiCorp memberlist/Serf/Consul. The one decision made differently: nothing fundamental — it is production SWIM+Lifeguard, and is this blueprint's ground-truth reference (ADR-26). Its distinguishing move is packaging: it bundles encryption, compression, labels, and a Serf event/query layer on top. That integration wins in the niche this blueprint defers — a turnkey, batteries-included cluster agent (Consul) where operators want service discovery, KV, and events out of one binary, not a protocol kernel to build on.

Apache Cassandra. The one decision made differently: a φ-accrual detector instead of binary Suspect→Dead. Rather than a hard timeout, each node computes a continuous suspicion level φ from the statistical distribution of recent heartbeat inter-arrival times, and the application picks a φ threshold. That wins in the niche where links have heterogeneous, drifting latency and a single static timeout is wrong everywhere at once: φ adapts the implicit timeout per-link to observed conditions. SWIM's discrete Suspect state is coarser but cheaper to reason about and refute (see §24's φ-accrual road).

Akka Cluster. The one decision made differently: membership runs over an actor runtime with a designated leader that coordinates convergence (state transitions like Up/Down are applied when the gossip view converges and the leader acts). That wins in the niche of a single JVM-based application cluster where actors are already the concurrency model and slightly stronger, leader-mediated membership semantics simplify the app — at the cost of a convergence/leader dependency SWIM deliberately avoids (P11 coordinator-free). This blueprint rejects importing Akka's leader-convergence (ADR-15).

Redis Cluster. The one decision made differently: a node moving from PFAIL (probably failed) to FAIL requires agreement from a majority of master nodes via the cluster bus before the verdict sticks. That injects a quorum gate — a CP-flavored step — into an otherwise gossip-based membership, which wins in the niche where a false eviction is catastrophic (it triggers slot failover and data-placement changes) so the system pays a coordination round to avoid acting on one node's lonely suspicion. SWIM accepts a lone node's verdict (gated only by suspicion + refutation) because its consumers tolerate transient disagreement (P9).

Netflix Eureka. The one decision made differently: membership is client-driven lease renewal, not peer probing — instances push a periodic heartbeat to a central registry to renew a lease, the registry evicts on lease expiry, and a self-preservation mode stops evicting when too many leases expire at once (treating that as a likely network problem, not mass death, deliberately favoring stale-but-present data over aggressive eviction). That wins in the niche of a centralized client/server service registry (clients already call a directory server to discover peers, so piggybacking liveness renewal onto that same call is free) — at the cost of the registry tier itself, a component SWIM's peer-to-peer design avoids entirely (P11), and of eviction accuracy under real mass failure, which self-preservation deliberately trades away for eviction-storm safety.

22. Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints table (§4). Symbols: N = cluster size; T′ = protocol period (1 s, §4); k = indirect relays (3, §4); λ = retransmit multiplier (≈3, §4); MTU = safe datagram (≈1400 B, §4); R = per-member record (~40 B incl. name/addr/inc/state/meta headroom, from "tens of bytes/node", §4); A = anti-entropy interval (30 s, §4). Worked at N=1000 unless noted.

Method: every number below is a closed-form function of those §4 symbols, so the model re-derives for any deployment by substitution — halve T′ and the message-rate numbers double while the convergence/suspicion numbers halve; raise R (fatter metadata) and only the memory/anti-entropy rows move; change N and watch which rows are flat (load), linear (memory, bandwidth), or logarithmic (latency). The point of computing these before writing code is to discover which resource hits its ceiling first (here: per-node memory at ~10^4 nodes, never the wire), so the design effort goes where the scaling actually binds.

  1. Steady-state per-node message rate. Formula: msgs/period = 1 ping + 1 ack = 2; rate = 2 / T′. With T′=1 s → 2 msgs/s per node, independent of N (the M1 constant-load claim, §4/Phase 2). This is the headline: it does not contain N.

  2. Per-node rate including indirect, worst plausible loss. Formula: + k pingreqs + k acks = 2k only on the fraction f of periods with a direct miss. Upper-bound f→1 (pathological): (2 + 2k)/T′ = (2 + 6)/1 = 8 msgs/s; at a healthy f≈0.02: ≈ 2.16 msgs/s. Bounded by k, still independent of N.

  3. Cluster-wide message rate. Formula: N × per-node rate = N × 2 / T′. At N=1000 → 2000 msgs/s cluster-wide. Contrast all-to-all heartbeat N(N−1)/T′ ≈ 10^6 msgs/s — a 500× gap at N=1000, widening linearly with N (motivates §19 and the D.7 load math).

  4. Membership-list memory per node. Formula: N × R. At N=1000, R=40 B → 1000 × 40 = 40 KB/node; at N=10000 → 400 KB/node. O(N) per node — the memory that does grow (§19 bottleneck #2). Drives the "bound metadata" discipline.

  5. Piggyback updates per datagram. Formula: floor((MTU − header) / update_size). With ~1400 B MTU, ~60 B fixed message header, ~50 B per packed update → floor((1400−60)/50) = ~26 updates per datagram (I6 budget). This is why a single probe can carry a large slice of current churn for free.

  6. Convergence latency (periods). Formula (epidemic, branching-process): ≈ log_b(N) rounds × T′, with effective base b > 1 from fanout. At N=1000, log2(1000) ≈ ~10 periods ≈ 10 s to full infection (M6, §4/Phase 5). At N=10^6, log2 ≈ 20 periods — still tiny; this is the O(log N) that makes SWIM scale.

  7. Retransmits per update (dissemination ceiling). Formula: λ · log(N+1) (I7). At N=1000, λ=3 → 3 × log2(1001) ≈ 3 × 10 = ~30 transmissions per update before retirement. Cluster-wide cost per change ≈ N × λ · log N / N per node — bounded, the epidemic optimum (§19).

  8. Anti-entropy bandwidth per node. Formula: (N × R) / A bytes/s (one full-list push-pull per interval). At N=1000 → 40 KB / 30 s ≈ ~1.3 KB/s per node (×2 for push+pull ≈ 2.7 KB/s). The heaviest per-byte op (§19 bottleneck #1) yet trivial in absolute terms — why the interval can stay generous.

  9. Suspicion-window duration. Formula: suspicion_mult · log(N+1) · T′ (§4). At mult=4, N=1000 → 4 × 10 × 1 s = ~40 s worst-case before a non-refuting Suspect becomes Dead. This sets the true-death detection-time tail and why the window must grow with N (or large clusters false-positive, MM3).

  10. Expected time-to-first-probe of a failed node. Formula: full ring cycle = N × T′, expected hit ≈ N·T′ / 2 if random, but the shuffled-ring permutation (I8) bounds it to ≤ N · T′ and expected ≈ (N+1)/2 · T′. At N=1000 → expected ~500 s to be targeted, but detection of a failure somewhere is per-period; the relevant SLO is detection-once-targeted (M2), size-independent at ~1–2 periods.

  11. File-descriptor / socket budget. Formula: SWIM uses 1 UDP socket (all probes/gossip) + transient TCP for anti-entropy/join. FD count = 1 + (concurrent TCP syncs). With one anti-entropy sync at a time → ~2 FDs steady-state, independent of N — a deliberate consequence of ADR-04 (single UDP socket) vs a connection-per-peer design that would be O(N) FDs.

  12. Bandwidth headroom check. Formula: steady-state bytes/s ≈ (2 msgs/s) × (avg datagram ~ 200 B with piggyback) = ~400 B/s ≈ 3.2 kbit/s per node, plus ~2.7 KB/s anti-entropy. Against the 1 GbE assumption (§4) this is ~6 orders of magnitude of headroom — confirming SWIM is latency/topology-bound, not bandwidth-bound (§18), and that the scaling ceiling is memory (#4) and convergence (#6), never the wire.

Derived sanity bounds (operational guardrails). These fall straight out of the model and are the thresholds an operator watches:

  • Metadata budget: each byte of per-node meta costs N × A^{-1} × 2 bytes/s of anti-entropy bandwidth cluster-wide; at N=10^4 that is ~0.67 KB/s per byte-of-meta per node — so keep meta in the tens of bytes, not kilobytes (#4, #8).
  • Anti-entropy interval floor: set A so that N × R / A stays a small fraction of link bandwidth; at N=10^4, R=40 B, a 30 s interval is ~27 KB/s — fine, but dropping A to 1 s would be ~800 KB/s, the first row to threaten the wire (#8).
  • Piggyback adequacy: if average churn-events-per-period exceeds the ~26-update datagram budget (#5), the overflow defers to later messages and convergence stretches — a signal to raise the gossip-tick rate or lambda, not the MTU (#5, #7).
  • Suspicion-window vs convergence: the window (#9, ~mult·log N·T′) must exceed the refutation propagation time (~convergence, #6) or a busy node can't refute in time — this is why both scale with log N together, and why a constant window false-positives at scale (MM3).
  • Memory ceiling first: at ~10^4 nodes the per-node list (~400 KB, #4) and the O(N) anti-entropy are what bind before message rate or wire ever do — so the scaling levers are metadata discipline and sub-grouping (WAN tiers, Phase 11), exactly as §19 concludes.

24. Alternative Architectures (Roads Not Taken)

Fundamentally different architectures for the same problem — who-is-alive at scale — each with the regime it wins, the real system embodying it, and why this blueprint rejected it.

A. All-to-all heartbeating (O(N²)).

   every node ──heartbeat──▶ every other node, every period
        A ⇄ B ⇄ C ⇄ D ⇄ E ... (full mesh, N(N−1) messages/period)
   miss-timeout ⇒ declare dead (no suspicion, no gossip)

Wins when: N is tiny and fixed (≤ ~10–20, single rack) where O(N²) is negligible and the simplicity of "no gossip, no suspicion, just timeouts" beats any protocol machinery. Real system: early Cassandra and many first-generation clusters heartbeated all-to-all before adopting gossip. Rejected because: load grows O(N²) cluster-wide and detection accuracy degrades with size (longer timeouts to suppress false positives) — the exact failure §19 and the D.7 load math quantify; it violates P1 (constant per-node load) at the first design step. The trade vs this design: you buy immediate per-pair detection (no convergence wait — everyone heartbeats everyone) and dead-simple code, but you pay it back at O(N²) and lose all the accuracy/dissemination machinery; the crossover is roughly where N×heartbeat-rate saturates a link — empirically a few tens of nodes (see §22 #3, where SWIM is already 500× cheaper at N=1000).

B. Centralized membership via a consensus store.

   nodes ──register / lease-renew──▶ ┌──────────────┐
                                     │  etcd / ZK    │  (Raft/ZAB quorum)
   nodes ◀──watch: who is alive──── └──────────────┘
   coordinator holds THE authoritative member set; lease expiry ⇒ dead

Wins when: you need a single agreed membership set with strong consistency — every node must see the identical list at a quorum-defined instant (quorum reconfiguration, exact slot ownership). Real system: Kubernetes node membership via etcd; ZooKeeper-based membership in many Hadoop-era systems. Rejected because: it reintroduces a coordinator (a SPOF + scaling bottleneck), blocks under partition (CP — unavailable exactly when nodes are flapping), and makes the lease store's throughput the cluster's membership-churn ceiling — violating P9 (eventual consistency is the contract) and P11 (coordinator-free). SWIM is the AP membrane beneath such a store, not a replacement (MM8, §20). The trade vs this design: you buy a single authoritative answer to "who is in the group right now" (no transient disagreement, no split-brain ambiguity) but you pay availability under partition and a hard scaling ceiling at the store's write throughput; the right architecture for most large systems is both — SWIM for cheap, partition-tolerant liveness feeding a small consensus group for the few decisions that genuinely need agreement (§1 boundaries, the D.9 decision rule).

C. Hierarchical / tiered gossip.

   ┌─ DC-1 LAN pool ─┐        ┌─ DC-2 LAN pool ─┐
   │ A B C (fast T′) │        │ D E F (fast T′) │
   └───────┬─────────┘        └────────┬────────┘
        gateway G1 ⇄══ slow WAN pool ══⇄ gateway G2
   full per-node state stays LAN-local; only DC/gateway state crosses WAN

Wins when: the cluster spans high-latency, lossy links (multi-datacenter, WAN) where one uniform fast-gossip tier would mistake latency for failure and blow WAN bandwidth on full-list sync. Real system: HashiCorp Serf's LAN/WAN dual pools (and Consul's federation). Rejected for Phase 0 only — adopted later: this is not rejected outright; it is deferred to Phase 11 because single-LAN is the right first scope (§1 non-goals), and importing WAN tiering before the single-tier core is correct would conflate two hard problems. It is the chosen extension, anchored in the Deferred Features Register and built in Phase 11. The trade vs this design: the tiered model buys WAN-bounded bandwidth (O(#DCs) crossing the WAN, not O(N), per I15) and per-tier timing that won't evict a slow DC, but it adds a gateway role (a partial SPOF mitigated by ≥2 gateways/DC) and the operational complexity of two gossip schedules — which is exactly why it is staged after the single-tier core proves correct, not before.

D. φ-accrual adaptive failure detectors.

   per monitored node: record heartbeat inter-arrival times
   φ(now) = −log10( P(next arrival later than now-since-last) )
   φ rises smoothly as silence grows; app picks a φ threshold ⇒ suspected
   (a continuous suspicion *level*, not a binary Suspect state)

Wins when: link latencies are heterogeneous and drift over time, so a single static timeout is simultaneously too tight on fast links and too loose on slow ones — φ adapts the implicit timeout per link to the observed distribution. Real system: Apache Cassandra and Akka Cluster both use φ-accrual detectors. Rejected because: φ-accrual replaces SWIM's discrete, easily-refuted Suspect state with a continuous statistical estimate that is harder to reason about, harder to make consistent across nodes (each node's φ is local), and does not by itself provide the dissemination or incarnation-refutation machinery SWIM needs — it is a detector, not a membership protocol. SWIM keeps the coarse Suspect state (cheaper, refutable via incarnation, MM3) and gets adaptivity instead from Lifeguard's LHM (Phase 7, I11), which adapts to the local node's health rather than per-link statistics. The φ-accrual approach informs the adaptive-timeout discussion (§5, the Hayashibara paper) without being adopted as the core. The trade vs this design: φ-accrual buys per-link adaptivity (a noisy link self-tunes its own timeout without operator intervention) but loses the clean refutation story — there is no single "Suspect" bit a victim can overturn with one higher-incarnation message, so a falsely-suspected node cannot self-heal as crisply; SWIM deliberately keeps the coarser-but-refutable verdict and pushes adaptivity into LHM, which is node-local rather than link-local and so composes with incarnation refutation instead of competing with it.

Why these four and not more. These are the genuinely different architectures — they differ in the load-bearing axis (mesh vs gossip; coordinator vs coordinator-free; flat vs tiered; discrete vs continuous verdict), not in parameters. Everything else in the space (different fanout, different timeout formulas, different codecs) is a tuning of one of these, not a fifth architecture. The decision rule that selects among them is the same one in the Domain Deep Dive (D.9): pick by whether you need agreement (→ B), WAN reach (→ C), per-link adaptivity (→ D), or just cheap scalable liveness with refutable verdicts (→ this design); reach for A only when N is small enough that none of it matters.

The matrix makes the rejection rationale concrete: no single column dominates, so the choice is a requirements decision, not a quality ranking. SWIM wins the intersection most cluster substrates actually need — constant load + partition-availability + refutable verdicts — and concedes only the "single agreed view" cell, which is precisely the cell you delegate to consensus (B) when you need it (MM8, §20). A is chosen only when simplicity at tiny N outweighs everything; C and D are reached for when WAN reach or per-link adaptivity is the dominating requirement.

What you must be able to redesign. The v2 bar is that, having read this blueprint, you can mutate this design into any of the four roads and state exactly what you'd trade. Concretely:

  • Into A (all-to-all): delete the dissemination buffer (Phase 5), the suspicion FSM (Phase 4), and the ring (I8); have each node ping every peer each period and declare Dead on timeout. You gain immediate per-pair detection and lose constant load (back to O(N²)) and all accuracy gates — viable only at tiny fixed N.
  • Into B (consensus store): replace the membership list and gossip with reads/writes against an external Raft/ZAB store holding the authoritative set; nodes renew leases instead of being probed. You gain a single agreed view and lose partition-availability (P9) and coordinator-freedom (P11).
  • Into C (tiered gossip): this is the sanctioned mutation — split the single gossip schedule into LAN and WAN pools, keep full lists LAN-local (I15), relax WAN timing (P4); it is already staged as Phase 11. You gain WAN-bounded bandwidth and per-tier timing and pay a gateway role + two schedules.
  • Into D (φ-accrual): replace the binary Suspect→Dead (§8.5) with a per-link φ estimate from heartbeat inter-arrival times and an app-chosen threshold; keep incarnations for identity but lose the crisp single-bit refutation. You gain per-link adaptivity and lose the clean self-heal story (MM3).

Being able to perform these four mutations on paper — and predict the resulting load, accuracy, and availability — is the operational definition of mastering this design space.

26. Glossary

  • SWIM — Scalable Weakly-consistent Infection-style Process group Membership.
  • Membership view — a node's local map of who is in the group and their state.
  • Failure detector — the mechanism that decides a member is unreachable.
  • Completeness — every faulty member is eventually detected by every correct one; also called strong completeness (I4).
  • Accuracy — correct members are not falsely declared faulty; also called eventual accuracy — no correct member is permanently suspected (I5).
  • Protocol period (T′) — the interval at which a node probes one target.
  • Ping / ack — direct liveness probe and reply.
  • Ping-req — a request to a relay to probe a target on one's behalf (indirect).
  • Relay (k) — the helper nodes used for indirect probing.
  • NACK — a relay's signal that it reached the requester but not the target (Lifeguard).
  • Suspect — provisional "maybe dead" state before declaring Dead.
  • Suspicion timeout — the window for refutation before Suspect→Dead; the full mechanism (Alive→Suspect→Dead with incarnation refutation) is the suspicion subprotocol, and the Dead verdict is gossiped as dead/confirm.
  • Incarnation — a per-node monotonic logical version; only the node advances its own.
  • Refutation — a node overriding a false suspicion by bumping its incarnation + broadcasting Alive.
  • Dissemination — spreading membership updates through the cluster.
  • Infection-style / epidemic — gossip where each informed node infects others.
  • Piggyback — carrying membership updates on probe/ack messages, plus a small periodic gossip tick that bounds latency in idle clusters (no separate flood).
  • λ (lambda) — the retransmit-count multiplier; updates sent ~λ·log N times.
  • Anti-entropy — periodic full-state reconciliation backstopping lossy gossip.
  • Push-pull — bidirectional full-state exchange (TCP) for anti-entropy/join; idempotent — reconciling identical states is a no-op (I10).
  • Convergence — all nodes reaching a consistent view after a change, measured in convergence periods (one per T′).
  • False positive — a live node wrongly declared dead.
  • Lifeguard — Hashicorp's accuracy extensions (LHM, adaptive timeouts, buddy, NACK).
  • Local Health Multiplier (LHM) — a self-distrust factor dilating a node's own timers.
  • Buddy system — routing a suspicion to the suspected node's neighbors first for fast refute.
  • Seed node — a known address used to bootstrap a join.
  • Graceful leave — an intentional departure broadcast to skip the suspicion cycle.
  • Cluster label — a tag preventing two clusters on one network from merging.
  • Keyring — the set of valid auth/encryption keys (enables rotation).
  • MTU — maximum transmission unit; datagrams must stay under it (no fragmentation).
  • Eventual consistency — the view converges over time, not instantaneously.
  • Weak consistency — SWIM's guarantee: convergent, not globally synchronized.
  • Coordinator-free — no master; every node runs identical, symmetric logic.
  • Timer wheel — an O(1) data structure for many suspicion timers.
  • LAN pool / WAN pool — fast intra-DC gossip tier / slow cross-DC gossip tier (multi-DC).
  • Gateway node — a node participating in the WAN pool on its DC's behalf.
  • Network coordinates (Vivaldi) — per-node coordinates estimating pairwise RTT for latency-aware timing.
  • Dual-tier gossip — separate fast (LAN) and slow (WAN) gossip schedules.
  • Lamport clock — a cluster-wide logical clock ordering user events (distinct from per-node incarnation).
  • User event — an application-level message broadcast over the gossip substrate (best-effort).
  • Query — a cluster-wide request that collects responses within a timeout.
  • TTL — time-to-live bounding how long an event keeps being gossiped.
  • Dedup window — recent-Lamport-time buffer preventing duplicate event delivery.
  • AP (vs CP) — available-under-partition (SWIM) vs consistent-under-partition (consensus).
  • Probe — one target's liveness check in a period: a direct ping to the round-robin-selected target (a shuffled permutation, not random-with-replacement), escalating on the sub-period ack-timeout to an indirect ping-req through k relays.
  • Fanout — the number of peers an update is sent to before retirement (governed by λ).
  • Branching process — the epidemic model explaining O(log N) infection spread.
  • Delegate / callback — the application hook receiving join/leave/update events.
  • Metadata — opaque, size-bounded per-node application data carried in membership.
  • Split-brain — two partition halves each operating as the full cluster (resolved on heal via incarnations).
  • Churn — the rate of joins/leaves/failures the cluster must absorb.
  • Soak test — a long-running test asserting no leaks/regressions under sustained churn.
  • Differential test — comparing this implementation's outcomes to a reference (memberlist).
  • Snapshot — an optional persisted membership view for fast restart (re-validated via anti-entropy).
  • HMAC — keyed hash authenticating each datagram (§8).
  • AEAD — authenticated encryption with associated data (optional confidentiality).
  • Keyring rotation — swapping auth/encryption keys with multiple valid keys live.
  • Asymmetric connectivity — A reaches B but B cannot reach A (a detection hazard).
  • Backpressure — bounding the gossip buffer + dropping oldest under churn (ADR-29).

Build Order & Completion-Bar Guidance

SWIM encodes three load-bearing ideas beyond its short protocol period: decouple detection from dissemination (constant load + epidemic spread, Phase 2/Phase 5), suspect before declaring dead (a tunable accuracy gate, Phase 4), and logical incarnations instead of clocks (clock-free, partition-resilient self-state, Phase 0/Phase 4). Get any one wrong and the cluster either flaps healthy nodes out or never notices dead ones.

The single highest-leverage artifact is the deterministic network simulator (Phase 9): failure detectors are defined by behavior under loss, latency, and partition — conditions a real network will not reproduce on demand. Build the simulator early (it shares the Transport interface from Phase 1), express every invariant (§7) as a simulator assertion, and measure convergence/detection/load in logical periods, never wall-clock, so results are reproducible (I14).

Recommended build order. Build Phase 0 (the conflict-resolution kernel) and Phase 1 (the Transport abstraction with its simulated backend) first — this lets Phases 2–7 be developed and tested entirely in the deterministic simulator with controllable loss and partitions, with no flaky real sockets and no wall-clock timers. The protocol's correctness lives in the precedence rules (§8.3) and the suspicion/refutation interplay (§8.5), both pure logic best exercised in simulation. Only after the simulator proves I1–I10 should a real UDP socket be bound. This is why the Repository Layout places sim/ adjacent to transport/ and why every phase's N.4 references simulator scenarios; inverting this order trades protocol-correctness debugging for socket-timing debugging.
