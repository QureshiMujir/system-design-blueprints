scheduler-api. Terminates TLS at trust boundary A, authenticates tenants, enforces per-tenant rate limits, normalizes requests into SchedulerRequest (§11), and opens the distributed trace root. Never makes a placement decision — ADR-19 forbids it from holding scheduling logic.

admission-controller. Validates model availability, quota budgets (quota-engine), SLA eligibility, token ceilings, and payload legality before any scheduling work is spent — the fast-fail boundary that keeps queue-manager from ever seeing malformed load.

queue-manager. Owns every priority, delayed, and fairness queue plus batch-assembly windows (§4: 1–15ms configurable). Converts admitted requests into schedulable execution groups; enforces I3 (Queue Capacity Bound).

scheduler-core. Computes placement using cluster state, runtime pressure, KV-cache locality, topology, and SLA constraints; coordinates preemption and failover; the only writer of PlacementDecision records into the WAL (persistence boundary).

metadata-store. Authoritative state behind a Raft quorum (ADR-04): node inventory, leases, runtime health, placement state, queue metadata, quotas, replay logs, cluster topology. CAS updates enforce I1.

placement-engine. Executes scoring functions, GPU-fit analysis, anti-affinity checks, memory pressure estimation, and topology-aware heuristics; a pure function of RuntimeDescriptor snapshots — no side effects, which is what makes it replay-deterministic.

replay-framework. Deterministic reconstruction of scheduling decisions from the placement WAL, used for debugging, regression analysis, incident reconstruction, and the conformance suite.

runtime-agent mesh. Node-local, partially-trusted (trust boundary B) processes exposing runtime inventory, model residency, GPU telemetry, health, queue pressure, and failure signals over a gRPC stream (concurrency boundary: single-writer heartbeat updates, lock-free snapshot reads, §11).

model runtime. Executes inference (vLLM, TensorRT-LLM). Treated as a partially trusted execution provider — the scheduler never assumes runtime-reported state is correct without corroborating telemetry (§22, T3).

KV cache layer. Maintains prompt/token cache-affinity metadata read by placement-engine's scoring pipeline; critical for minimizing token recomputation under prefix reuse.

streaming aggregator. Merges token streams, applies cancellation semantics, tracks stream deadlines, emits transport-safe partial responses; enforces I4 (Token Stream Monotonicity) at the queue boundary just before the client.

tracing-pipeline / metrics-exporter. The decoupled telemetry stack: ingests metrics, traces, audit logs, scheduler decisions, replay records, queue state, GPU utilization — architected so a telemetry outage degrades observability, never scheduling correctness (P5, §6).

8. Domain Model — Request Lifecycle & Scheduling Protocol

Core request lifecycle.

Client Request -> Gateway Validation -> Admission Control -> Queue Placement
  -> Batch Assembly -> Scheduler Decision -> Runtime Allocation -> Token Streaming
  -> Completion Persistence

Scheduler state machine.

State Meaning Valid Next States
RECEIVED request accepted at scheduler-api QUEUED, REJECTED
QUEUED awaiting placement in queue-manager SCHEDULED, CANCELLED
SCHEDULED runtime assigned, lease held RUNNING, FAILED
RUNNING execution active on runtime STREAMING, FAILED, COMPLETED
STREAMING token emission in progress COMPLETED, FAILED
COMPLETED terminal success none
FAILED terminal failure RETRY_PENDING
CANCELLED client-terminated none
REJECTED admission-controller fast-fail none
RETRY_PENDING queued for bounded retry QUEUED, CANCELLED

Transitions outside this table are rejected at the state-machine boundary in scheduler-core and counted under invalid_state_transition_total — this is I6's enforcement point in practice.

PlacementRecord fields (append-only WAL row, replay-reconstructable per I8):

PlacementRecord fields:
  request_id: RequestId;
  tenant_id: TenantId;
  model_id: ModelId;
  runtime_id: RuntimeId;
  gpu_set: GpuSet;
  kv_cache_affinity: CacheAffinityKey;
  batch_group: BatchGroupId;
  priority: PriorityClass;
  placement_epoch: Epoch;
  replay_sequence: ReplaySeq;
  created_at: TimestampNs;

Failure example — malformed runtime heartbeat. Symptoms: heartbeat_epoch regression, runtime reports negative queue depth, GPU inventory mismatch against last known-good snapshot. Expected handling: reject the heartbeat at node-heartbeat-service, mark the runtime degraded (not evicted immediately — avoids flap amplification, §16.6), emit security telemetry (T3, §22), and quarantine the runtime after a configurable consecutive-rejection threshold.

Sequence diagram — happy path.

Client -> scheduler-api: inference request
scheduler-api -> admission-controller: normalized request
admission-controller -> queue-manager: enqueue
queue-manager -> scheduler-core: placement request
scheduler-core -> runtime-agent: lease proposal
runtime-agent -> scheduler-core: lease accepted
scheduler-core -> model runtime: dispatch execution
model runtime -> streaming aggregator: token stream
streaming aggregator -> Client: streamed tokens

This protocol is the single canonical source for every later reference to "the request lifecycle" — §15, §17, and §26 all cite these exact state names and transitions.
