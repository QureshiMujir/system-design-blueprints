1. Goal & Scope

Engineering definition. A model serving scheduler is a distributed control plane that converts inference requests into GPU-bound execution assignments under hard latency, fairness, and durability budgets. It sits between stateless inference gateways and node-local execution runtimes and owns admission control, queue management, GPU-aware placement, batching coordination, KV-cache affinity, preemption, autoscaling coordination, and telemetry aggregation. It is a scheduler, not a runtime: it never executes a tensor kernel, never generates a CUDA graph, and never converts model weights.

Phase 0 deliverable — crates/services shipped by the end of §12:

  1. scheduler-core — placement/lease/preemption/fairness kernel.
  2. scheduler-api — gRPC/HTTP gateway surface, auth, rate limiting.
  3. placement-engine — scoring, topology, anti-affinity, fragmentation estimation.
  4. quota-engine — tenant budgets, token accounting.
  5. queue-manager — priority/fairness queues, batch assembly windows.
  6. runtime-agent — node-local GPU inventory and health agent.
  7. node-heartbeat-service — heartbeat collection and freshness scanning.
  8. metadata-store — Raft-replicated authoritative state.
  9. admission-controller — quota/SLA/legality fast-fail validation.
  10. tracing-pipeline — distributed trace propagation and sampling.
  11. metrics-exporter — Prometheus exposition, cardinality control.
  12. replay-framework — deterministic scheduling reconstruction.
  13. benchmark-harness — Criterion-based placement/queue/WAL benchmarks.
  14. conformance-suite — protocol and replay fixtures.
  15. operator-cli — lease inspection, replay extraction, drain control.

System boundaries.

Provides: admission control · queue management · GPU allocation · replica placement · batching coordination · KV-cache affinity scoring · fairness enforcement · SLA-aware routing · preemption · speculative-execution placement coordination · failure recovery · runtime telemetry aggregation · deterministic replay.

Delegates: tensor execution and CUDA graph capture (to the model runtime, e.g. vLLM/TensorRT-LLM) · tokenization (to the runtime/tokenizer library) · model weight storage and conversion (to model registries) · TLS termination detail and edge rate-limit policy authoring (to the gateway operator, though the gateway is in-tree) · container orchestration primitives (to Kubernetes/containerd when present).

Does NOT provide: tensor kernels · CUDA graph generation · model training · compiler graph optimization · tokenizer implementations · model weight conversion · a deep-learning framework of any kind.

Non-goals. Training-workload scheduling; multi-cluster active-active inference in Phase 0–9 (see §35); a general-purpose batch scheduler (Slurm/YARN already solve that; §31 explains why this blueprint does not re-solve it); a bin-packing solver for arbitrary Kubernetes workloads.

Deployment model. Stateless control-plane services (scheduler-api, admission-controller) behind a horizontally scalable gateway tier; a stateful scheduler quorum (scheduler-core + metadata-store, Raft-replicated, ADR-04); node-local runtime-agent processes, one per GPU host; a decoupled telemetry stack (tracing-pipeline, metrics-exporter) that never blocks the scheduling hot path. Runs on Kubernetes (optional) or bare metal; both are first-class per §4's deployment assumptions.

Target operators. Platform engineers · inference infrastructure teams · GPU cluster operators · AI infrastructure researchers · SRE teams · performance engineering teams. All are assumed comfortable with distributed systems failure modes but not necessarily with GPU memory hierarchies — §5's GPU Systems Architecture reading closes that gap.

What later phases unlock. Phase 3 placement (§15) unlocks topology-aware tensor-parallel placement. Phase 6 autoscaling (§18) unlocks spot/preemptible GPU orchestration. Phase 7 replay (§19) unlocks ML-driven placement prediction once enough replay corpus exists. Phase 8 fairness/preemption (§20) unlocks a programmable scheduling DSL. Multi-cluster federation and elastic KV-cache migration remain deferred past Phase 9 (§35).

Recommended implementation language: Rust 1.82+. Rationale: deterministic ownership semantics make lease/lifetime bugs compile-time errors instead of production incidents (directly enforces I1, §7); memory safety under concurrency pressure removes an entire CVE class from a system that parses untrusted runtime heartbeats (§22); predictable async runtime behavior (Tokio, ADR-02) avoids GC-pause tail latency that would blow the p99 budget in §4; the ecosystem (tonic, prost, tracing, OpenTelemetry) is the strongest available for exactly this domain; lock-free primitives (crossbeam, arc-swap) are needed for the lock-free snapshot reads in §11; the binary integrates with Linux systems tooling (cgroup v2, io_uring) with zero FFI ceremony. Rejected: Go — GC pauses interact badly with the sub-3ms p50 placement budget (§4) and its generics-poor era-appropriate ecosystem made the WAL/Raft layer (§13) harder to keep branch-free; still the right call for a simpler control plane with a looser latency budget. Rejected: C++ — no ownership model to enforce I1 at compile time; would require an equivalent of Rust's borrow checker built by hand via code review, which does not scale past the team size this project assumes.

Prerequisites. Operating-systems internals · Linux scheduling · NUMA architecture · TCP/IP · QUIC · gRPC · distributed systems · consensus algorithms (Raft) · GPU execution fundamentals · CUDA memory hierarchy · async runtimes · tracing systems · databases · replication systems · performance engineering · concurrency debugging · observability engineering.

Estimated timeline. Phase 0 MVP: 10 weeks. Production-capable scheduler (Phases 0–7): 6–9 months. Multi-cluster-hardened implementation (Phases 0–9 plus the operational maturity in §24–§29): 12–18 months.

2. Why Build This

A model serving scheduler sits at the densest intersection of distributed-systems engineering and performance-critical infrastructure available to a systems engineer today. Modern inference platforms fail less often from tensor-math bugs than from placement instability, queue collapse, GPU fragmentation, runaway tail latency, KV-cache invalidation storms, or overload amplification — failure classes that look identical to a classic distributed-database or packet-scheduler incident, just with a GPU instead of a disk as the scarce resource.

Lineage. Large-scale schedulers evolved from Borg (Google, EuroSys 2015) and Omega (Google, EuroSys 2013) through Kubernetes, Ray, Mesos, Slurm, and YARN, plus the parallel line of distributed query schedulers and packet schedulers. Inference scheduling inherits all of that lineage's hard problems and adds domain-specific pressure: GPU memory fragmentation, KV-cache locality, prompt-length variance, token-rate instability, dynamic-batching tradeoffs, tight latency-vs-throughput coupling, and burst-heavy request distributions that a training-job scheduler never sees.

Engineering disciplines exercised. Queueing theory · systems observability · lock-free coordination · replicated state management · scheduling algorithms · congestion control · tail-latency mitigation · adaptive batching · capacity planning.

Related systems projects. Distributed databases · stream processors · cluster orchestrators · kernel schedulers · RPC frameworks · consensus systems · storage engines · network load balancers · tracing infrastructures — a working model serving scheduler transfers directly to all eight.

Calibration value. Completing this project forces engineering maturity in reasoning about partial failure, designing measurable systems, handling contention explicitly, enforcing deterministic invariants, and building debuggable distributed infrastructure. Every optimization in this system must stay explainable under production failure conditions — that constraint, held for ten phases, is what raises capability permanently rather than temporarily.

What Mastery Looks Like

  • Replicated consensus and WAL-durable state design that survives node loss without acknowledged-write loss — built in Phase 1 (§13).
  • GPU-aware placement scoring that reasons about fragmentation, topology, and KV-cache affinity as first-class scoring inputs, not afterthought heuristics — built in Phase 3 (§15).
  • Backpressure-safe token streaming that preserves ordering under cancellation and runtime disconnect — built in Phase 5 (§17).
  • Autoscaling control-loop design that avoids oscillation under bursty, non-stationary load — built in Phase 6 (§18).
  • Deterministic replay as a debugging methodology: reconstructing a scheduling decision byte-for-byte from persisted inputs — built in Phase 7 (§19).
  • Multi-tenant fairness and preemption under real contention, including starvation detection and cooperative cache-aware preemption — built in Phase 8 (§20).
  • Production release engineering: reproducible builds, SBOM/provenance, canary rollout, and conformance gating before a build reaches a GPU cluster — built in Phase 9 (§21).
  • Incident forensics from telemetry alone: reconstructing a cluster-wide failure from traces, replay logs, and metrics without reproducing it live — exercised across §19, §23, and §24.

scheduler-api. Terminates TLS at trust boundary A, authenticates tenants, enforces per-tenant rate limits, normalizes requests into SchedulerRequest (§11), and opens the distributed trace root. Never makes a placement decision — ADR-19 forbids it from holding scheduling logic.

admission-controller. Validates model availability, quota budgets (quota-engine), SLA eligibility, token ceilings, and payload legality before any scheduling work is spent — the fast-fail boundary that keeps queue-manager from ever seeing malformed load.

queue-manager. Owns every priority, delayed, and fairness queue plus batch-assembly windows (§4: 1–15ms configurable). Converts admitted requests into schedulable execution groups; enforces I3 (Queue Capacity Bound).

scheduler-core. Computes placement using cluster state, runtime pressure, KV-cache locality, topology, and SLA constraints; coordinates preemption and failover; the only writer of PlacementDecision records into the WAL (persistence boundary).

metadata-store. Authoritative state behind a Raft quorum (ADR-04): node inventory, leases, runtime health, placement state, queue metadata, quotas, replay logs, cluster topology. CAS updates enforce I1.

placement-engine. Executes scoring functions, GPU-fit analysis, anti-affinity checks, memory pressure estimation, and topology-aware heuristics; a pure function of RuntimeDescriptor snapshots — no side effects, which is what makes it replay-deterministic.

replay-framework. Deterministic reconstruction of scheduling decisions from the placement WAL, used for debugging, regression analysis, incident reconstruction, and the conformance suite.

runtime-agent mesh. Node-local, partially-trusted (trust boundary B) processes exposing runtime inventory, model residency, GPU telemetry, health, queue pressure, and failure signals over a gRPC stream (concurrency boundary: single-writer heartbeat updates, lock-free snapshot reads, §11).

model runtime. Executes inference (vLLM, TensorRT-LLM). Treated as a partially trusted execution provider — the scheduler never assumes runtime-reported state is correct without corroborating telemetry (§22, T3).

KV cache layer. Maintains prompt/token cache-affinity metadata read by placement-engine's scoring pipeline; critical for minimizing token recomputation under prefix reuse.

streaming aggregator. Merges token streams, applies cancellation semantics, tracks stream deadlines, emits transport-safe partial responses; enforces I4 (Token Stream Monotonicity) at the queue boundary just before the client.

tracing-pipeline / metrics-exporter. The decoupled telemetry stack: ingests metrics, traces, audit logs, scheduler decisions, replay records, queue state, GPU utilization — architected so a telemetry outage degrades observability, never scheduling correctness (P5, §6).

6. Design Principles

  • P1 — Determinism Over Throughput. Rule: every scheduling decision must be replayable from persisted inputs alone. · Tradeoff: forgoes some throughput headroom that nondeterministic scoring shortcuts would buy. · Operational: replay checksum mismatch (I8) pages the on-call within one incident cycle. · Violated: nondeterministic scheduling produces latency spikes no one can reproduce or debug (§19.9).
  • P2 — Backpressure Everywhere. Rule: every queue, stream, and transport exposes bounded capacity. · Tradeoff: bounded queues reject work under burst instead of absorbing it silently. · Operational: queue-depth and stream-buffer saturation counters feed admission shedding (§14). · Violated: unbounded queues produce catastrophic tail latency and eventual OOM (I3).
  • P3 — Crash-Only Components. Rule: every process assumes abrupt termination as a normal event, not an exception. · Tradeoff: forgoes graceful-shutdown optimizations in favor of recovery-path correctness. · Operational: crash-recovery replay (§13.2) is exercised in CI on every build, not just incidents. · Violated: processes that need clean shutdown to stay correct corrupt state on the next outage.
  • P4 — Replayability First. Rule: every placement decision emits replay metadata before it is considered committed. · Tradeoff: adds WAL-append latency to the hot path (budgeted in §4). · Operational: replay-framework consumes this metadata continuously, not just on demand. · Violated: undebuggable incidents accumulate because there is nothing to replay (§19.6).
  • P5 — Observability By Default. Rule: no subsystem ships without metrics, traces, structured logs, and queue visibility. · Tradeoff: instrumentation overhead is a permanent tax on every hot path. · Operational: tracing-pipeline and metrics-exporter run as decoupled services so telemetry failure cannot block scheduling. · Violated: an outage with no signal — the single most expensive failure mode in production inference (§24).
  • P6 — Explicit Resource Ownership. Rule: GPU allocations, queue leases, and execution tokens have exactly one authoritative owner at any instant. · Tradeoff: ownership transfer requires an explicit fencing protocol instead of implicit reassignment. · Operational: lease fencing (I11) is checked on every runtime dispatch. · Violated: double allocation — two requests believe they own the same GPU slot (I1).
  • P7 — Latency Isolation. Rule: interactive workloads must not collapse due to bulk inference sharing the same cluster. · Tradeoff: requires separate fairness windows and SLA classes instead of a single global queue. · Operational: per-tenant SLA-class dashboards (§14.10) surface isolation failures directly. · Violated: a bulk batch job starves a latency-sensitive tenant with no isolation boundary to blame.
  • P8 — Bounded Memory Usage. Rule: the scheduler rejects work before memory exhaustion occurs, never after. · Tradeoff: admission shedding under legitimate burst traffic looks like unavailability to the caller. · Operational: queue memory accounting (§14.2) feeds admission control directly. · Violated: OOM kill takes down the scheduler process mid-decision, corrupting in-flight state.
  • P9 — Stable Wire Compatibility. Rule: protocol evolution must support rolling upgrades across at least one major version. · Tradeoff: forbids field removal or type changes that would be simpler than append-only evolution. · Operational: protobuf schema compatibility is a CI gate (§25). · Violated: a rolling upgrade partitions the cluster into two incompatible wire dialects mid-rollout.
  • P10 — Monotonic State Transitions. Rule: placement state machines move forward only, or roll back through explicit compensating transitions — never silently. · Tradeoff: every rollback path must be designed and tested, doubling the state-machine surface. · Operational: the scheduler-epoch counter (I6) makes forward-only progress auditable. · Violated: a state machine "goes backward" invisibly and a stale decision is re-applied over a newer one.
  • P11 — Failure Containment. Rule: node-local corruption must not propagate cluster-wide. · Tradeoff: containment boundaries (quarantine, circuit breakers) add latency to the failure-detection path. · Operational: node quarantine (§16.10) isolates a bad runtime before it corrupts placement decisions. · Violated: one corrupted runtime descriptor cascades into cluster-wide placement oscillation (§15.9).
  • P12 — Instrumentation Before Optimization. Rule: no optimization ships without a measurable baseline. · Tradeoff: slows down performance work in exchange for provable, not assumed, wins. · Operational: every §28 performance target cites the benchmark-harness fixture that measures it. · Violated: a "performance fix" regresses p99 latency because no one measured the baseline first.

I8 Replay Determinism — replaying a WAL segment reproduces identical placement decisions debuggability (P1, P4) replay-framework checksum comparison replay checksum mismatch replay_divergence_total replay isolation; forensic bundle export

I11 Runtime Lease Fencing — a superseded lease token can never be honored by a runtime prevents stale-owner writes (P6) runtime-agent fencing-token check fenced lease presented by runtime stale_lease_rejected_total drop dispatch; re-lease
I12 Metadata Quorum Write Ordering — linearizable reads never observe a write before quorum commit correctness of every downstream read metadata-store Raft read-index protocol stale-read detector in conformance-suite linearizable_read_violation_total invalidate read cache; re-issue read-index

Debugging methodology: every invariant above has exactly one assertion in the deterministic simulator (§26) that can fail independently of the others — no invariant is checked implicitly as a side effect of checking a different one. The simulator drives scheduler-core, queue-manager, and metadata-store against recorded and synthetic replay corpora (§19) and asserts I1–I12 after every simulated tick; a failing assertion identifies the violated invariant by ID directly in the CI log, never by inference from a downstream symptom.

11. Core Schema & Types

SchedulerRequest — immutable after admission (P4); shared via Arc references; persisted in the placement WAL; wire form is Protobuf (ADR-05), evolved append-only (P9).

SchedulerRequest fields:
  request_id: RequestId;
  tenant_id: TenantId;
  model_id: ModelId;
  priority: PriorityClass;
  prompt_tokens: u32;
  max_output_tokens: u32;
  latency_sla_ms: u32;
  affinity_hints: Vec<AffinityHint>;
  enqueue_timestamp_ns: u64;

Ownership: constructed once at admission-controller, never mutated downstream (compile-time enforced by lacking &mut accessors). Mutation: none post-construction. Concurrency: safe for concurrent read via Arc<SchedulerRequest> clone, zero lock cost. Persistence: appended to WAL before admission ack (I2). Serialization: Protobuf, field numbers frozen at ADR-05 lock. Compatibility: new fields must be optional with a documented default (P9).

RuntimeDescriptor — node-local snapshot; lock-free reads, single-writer heartbeat updates.

RuntimeDescriptor fields:
  runtime_id: RuntimeId;
  node_id: NodeId;
  gpu_inventory: GpuInventory;
  resident_models: Vec<ModelId>;
  queue_depth: u32;
  kv_cache_pressure: f32;
  heartbeat_epoch: Epoch;
  health_state: HealthState;

Ownership: owned by node-heartbeat-service; runtime-agent proposes, node-heartbeat-service commits. Mutation: single-writer per runtime_id (I11 enforces exclusivity). Concurrency: arc-swap snapshot — readers never block a writer (ADR-02 ecosystem choice). Persistence: latest snapshot only; history lives in the placement WAL via referencing PlacementDecision, not here. Serialization: Protobuf over the gRPC heartbeat stream (ADR-19). Compatibility: health_state enum additions must be non-breaking (§25).

PlacementDecision — the WAL row scheduler-core commits; the unit replay-framework replays.

PlacementDecision fields:
  decision_id: DecisionId;
  request_id: RequestId;
  runtime_id: RuntimeId;
  selected_gpus: GpuSet;
  score_breakdown: ScoreBreakdown;
  lease_expiry: TimestampNs;
  scheduler_epoch: Epoch;

Ownership: single writer (scheduler-core, holding the placement lease, I1). Mutation: none — append-only, corrections are new rows referencing the superseded decision_id. Concurrency: WAL append is serialized behind the epoch counter (I6). Persistence: durable before ack (I2), replayable (I8). Serialization: Protobuf; score_breakdown carries explainability metadata (§15.2). Compatibility: append-only field growth only, per P9.

QueueShard — one fairness/backpressure unit inside queue-manager (ADR-20 sharding).

QueueShard fields:
  shard_id: ShardId;
  tenant_heap: BinaryHeap<QueuedRequest>;
  fairness_window: FairnessWindow;
  backpressure_state: BackpressureState;

Ownership: one QueueShard per tenant-hash partition; owned exclusively by its shard worker task. Mutation: enqueue/dequeue only through the shard's single-threaded event loop — no external mutation. Concurrency: cross-shard communication is message-passing only (P6). Persistence: shard state checkpointed to metadata-store on a bounded interval for crash recovery (P3). Serialization: internal only, never crosses the wire directly — external views go through SchedulerRequest/PlacementRecord. Compatibility: shard count changes require a documented rebalance protocol (§18).

SchedulerError — the error taxonomy every public API surfaces; no anyhow-style opaque errors cross a crate boundary (P5 — every failure must be classifiable by an operator).

SchedulerError variants:
  QuotaExceeded;
  RuntimeUnavailable;
  PlacementConflict;
  InvalidRequest;
  LeaseExpired;
  QueueSaturated;
  MetadataUnavailable;

Ownership: value type, cloned freely. Mutation: immutable once constructed. Concurrency: Send + Sync, safe across the Tokio task boundary. Persistence: logged (structured JSON, ADR-15) but never itself persisted to the WAL — it is a control-flow signal, not scheduler state. Serialization: mapped to a gRPC status code plus a structured detail field for the client. Compatibility: variants are additive only; a client encountering an unknown variant must fail safe to a generic Internal mapping (P9).

PriorityClass, AffinityHint, GpuSet, CacheAffinityKey, Epoch, ReplaySeq are newtype wrappers over u8/u32/u64/Vec<GpuId> respectively — declared once in scheduler-core/src/ lib.rs, re-exported, never redefined in a downstream crate (terminology lock, §5 of this contract).

12.6 Pitfalls

  1. Hidden nondeterministic timestamps in log lines defeat config-checksum reproducibility — root cause: SystemTime::now() called during config normalization; debug via diffing two checksum runs; signal: checksum mismatch with no config change; recovery: inject a fixed clock during checksum computation.
  2. Dependency version drift between CI and a developer laptop — root cause: unpinned transitive range in Cargo.toml; debug via Cargo.lock diff; signal: "works on CI, fails locally"; recovery: cargo update -p <crate> --precise.
  3. Environment-variable precedence ambiguity — root cause: undocumented override order; debug via the config-checksum trace which logs the winning source per field; recovery: enforce the CLI > env > file

    default order from step 6 in code, not convention.

  4. Protobuf backward incompatibility introduced silently — root cause: a field renumbered instead of appended; debug via buf breaking in CI; recovery: revert, re-add as a new field number (P9).

12.7 Performance Concerns

  • Avoid startup allocation spikes from eager protobuf descriptor registration — lazy-init descriptors.
  • Preallocate tracing-subscriber ring buffers sized to expected span volume, not grown on demand.
  • Avoid synchronous log flushing on the hot path — logging must never block a Tokio worker thread.

12.8 Edge Cases

  • Corrupted configuration file (truncated TOML) — must fail closed with a specific InvalidRequest.
  • Invalid or expired TLS certificate at gateway startup — process refuses to bind, not silently plaintext.
  • Clock skew during startup — startup timestamp uses monotonic clock for internal sequencing (ADR-23), wall clock only for the human-readable log field.
  • Partial protobuf code generation (build interrupted) — the build step is atomic (temp dir + rename).

12.9 Failure Analysis

Build-reproducibility failures typically originate from transitive dependency drift, not from source changes. Operators compare Cargo.lock hashes and SBOM manifests (ADR-18) across the failing and last good build; a mismatch localizes the drift to a specific crate. Blast radius is zero at runtime — this class of failure blocks CI, never production, because ADR-26 pinning prevents an unreproducible build from ever being signed (ADR-17).

12.10 Operational Notes

  • All services emit at startup: build SHA, git tree hash, config checksum, startup timestamp, deployment region — startup_info structured-log event, one line, machine-parseable.
  • Tracing span: scheduler.startup — root span for every process's first tick.
  • Metric: startup_duration_seconds (histogram).
  • Migration/compatibility: none yet — Phase 0 introduces no persisted state to migrate.

  8. Add write fencing — CAS-based lease acquisition (Omega, Schwarzkopf et al. 2013, EuroSys) preventing the double-allocation failure I1 exists to catch.
  9. Implement linearizable reads via Raft's read-index protocol (I12).
  10. Create scheduler-epoch transitions — monotonic-only (I6), rejected on regression.
  11. Add crash-recovery replay — reconstructs in-memory state from the last snapshot plus WAL tail (P3).

  13. Add corruption checksums per WAL segment (CRC32C), checked on every read.
  14. Add a replica-divergence detector comparing checksums across the quorum.
  15. Implement snapshot-transfer throttling — bounds transfer bandwidth to avoid starving live traffic.

A three-to-five-node (§4 replication factor) metadata-store quorum that survives one-node failure with zero acknowledged-write loss, durable WAL, snapshot-based recovery, and deterministic replay of any committed segment.

13.4 Acceptance Criteria

  • Quorum survives one-node failure with write availability restored within the < 15ms metadata quorum write-latency budget (§4) once re-formed.
  • Replay of fixtures/wal/wal_partial_write.bin restores a consistent state with zero silently dropped writes.
  • No acknowledged write loss across 10,000 injected crash-recovery cycles in the deterministic simulator.
  • Snapshot transfer completes for a 25,000-model metadata set within the < 120s startup-recovery budget (§4).

13.5 Conformance Fixtures

  • fixtures/raft/raft_split_brain.bin — dual-leader scenario; expects fencing-token rejection of the stale leader.
  • fixtures/wal/wal_partial_write.bin — truncated append; expects checksum-detected rollback.
  • fixtures/lease/lease_recovery_case.json — lease table state after a crash mid-lease-acquisition.

13.6 Pitfalls

  1. fsync batching starvation — small writes queue behind a fsync barrier under load; debug via WAL append-latency histogram tail; signal: p99 append latency exceeds the 25ms fsync-durability budget (§4); recovery: group-commit batching with a bounded wait window.
  2. Stale leader acceptance after a network partition heals — root cause: missing fencing-token check on AppendEntries; debug via raft_split_brain.bin; recovery: reject any RPC bearing a lower term.
  3. Snapshot corruption during transfer — root cause: unbounded transfer interrupted mid-stream; debug via checksum mismatch on receive; recovery: resumable chunked transfer with per-chunk checksums.
  4. Replay divergence between two replicas — root cause: nondeterministic iteration order over a HashMap during snapshot serialization; debug via replay_divergence_total (I8); recovery: use a deterministically ordered (BTreeMap-backed) snapshot encoder.

13.7 Performance Concerns

  • WAL syscall amplification — batch fsync calls (ADR-08 binary format keeps records fixed-width where possible to make batching predictable).
  • Compaction pause times — run compaction on a background thread, never blocking the Raft apply loop.
  • Allocator fragmentation from variable-length log entries — pool-allocate fixed-size WAL record slabs.

13.8 Edge Cases

  • Partial snapshot transfer interrupted by node crash — resumable from last acknowledged chunk.
  • Monotonic clock violations across nodes with skewed hardware clocks — Raft terms use logical counters, never wall-clock time (ADR-23).
  • Leader-churn storms under flapping network conditions — randomized election-timeout jitter bounds storm duration.

13.9 Failure Analysis

Replication lag increases queue-placement staleness — a scheduler reading a stale RuntimeDescriptor snapshot can propose a placement the current leader must then reject. Detection relies on replication-age histograms and lease-conflict metrics (I1 telemetry). Blast radius is contained to the affected shard (ADR-20 sharding) — a lagging replica never corrupts another shard's state. Containment: reject writes from any node below the quorum-health threshold. Manual recovery: quorum restore from the last verified snapshot per docs/runbooks/quorum-loss.md.

13.10 Operational Notes

  • Metrics: raft_replication_lag_ms, wal_append_latency_ms, lease_conflict_total, quorum_health.
  • Tracing spans: metadata.append_entries, metadata.snapshot_transfer, metadata.replay.
  • Structured-log fields: term, leader_id, commit_index, snapshot_index.
  • Rollback: a bad metadata-store release is rolled back by redeploying the prior binary against the existing WAL — the binary format is versioned (§25) so no data migration is required for a patch rollback.

14.6 Pitfalls

  1. Priority inversion — a low-priority request holds a shard lock a high-priority request needs; debug via lock-hold-time histograms; signal: high-priority p99 latency spikes despite low queue depth; recovery: priority-inheritance-free design — shards never hold cross-tenant locks (P6).
  2. Queue amplification — a retry storm re-enqueues faster than it drains; debug via enqueue-rate vs drain-rate divergence; recovery: exponential backoff on RETRY_PENDING re-enqueue.
  3. Stale cancellations — a cancellation arrives after the request already left the queue for placement; debug via cancellation-vs-state-machine-state cross-check; recovery: cancellation is idempotent and checked at every state-machine transition, not just at the queue.
  4. Timer-wheel scaling collapse under high delayed-queue cardinality; debug via timer-tick latency; recovery: hierarchical timer wheel instead of a flat one.

14.7 Performance Concerns

  • Heap contention across concurrent enqueue/dequeue on a hot shard — batched dequeue reduces per-op lock acquisition.
  • Queue serialization overhead for persistence checkpoints — checkpoint on a bounded interval, not every mutation.
  • Timer-wheel scaling for delayed/retry queues at high cardinality (see Pitfall 4).

14.8 Edge Cases

  • Simultaneous multi-tenant spikes hitting the same shard — fairness window degrades gracefully, never deadlocks.
  • Queue replay after crash mid-batch-assembly — the batch-assembly window itself is not persisted state; it is reconstructed from queued requests, not replayed as a unit.
  • Invalid token estimates from a malformed prompt — clamp to a configured ceiling rather than reject outright, unless the ceiling is itself exceeded (§4 token ceilings).

14.9 Failure Analysis

Admission collapse typically manifests as scheduler idle periods despite rising queue depth — the signature of a deadlocked fairness window or a quota leak (a tenant's budget never replenishing). Root cause is isolated by inspecting fairness_deviation_ratio (I10) alongside quota_underflow_total (I9); a leak shows quota permanently near zero with no corresponding usage. Manual recovery is a quota adjustment; automatic recovery is admission shedding once queue-depth alarms fire (§23, FM-4).

14.10 Operational Notes

  • Dashboards expose: queue age, queue depth per tenant, admission-rejection reasons (by SchedulerError variant), SLA misses.
  • Metrics: queue_depth{tenant}, fairness_deviation_ratio, admission_reject_total{reason}.
  • Tracing spans: admission.validate, queue.enqueue, queue.dequeue.
  • Migration: quota-schema changes are additive-only (P9); a quota-engine rollback must tolerate reading a newer schema version written by a not-yet-rolled-back peer.

15.4 Acceptance Criteria

  • p99 placement latency < 20ms under a 5,000-node, 40,000-GPU synthetic cluster (§4).
  • Placement replay is bit-for-bit deterministic across 1,000 replayed WAL segments (I8).
  • Zero double-allocation events (I1/I7) across a 72-hour soak run (§26 soak testing).

15.5 Conformance Fixtures

  • fixtures/placement/gpu_fragmentation_case.json — fragmented inventory; expects a fit despite no single node having full free capacity via multi-GPU split scoring.
  • fixtures/placement/stale_heartbeat_case.json — inventory snapshot older than TTL; expects exclusion from candidate scoring, not a stale placement.
  • fixtures/placement/topology_preference_case.json — NUMA-local candidate present; expects it to outscore an equally-free but NUMA-remote candidate.

15.6 Pitfalls

  1. Stale inventory snapshots used for scoring — root cause: snapshot read racing a heartbeat update; debug via snapshot-age vs. decision-time delta; signal: placement onto a runtime that was already full; recovery: re-validate GPU-fit at lease-acceptance time, not just at scoring time.
  2. Placement oscillation — repeated migration of the same workload between two near-equally-scored runtimes; debug via migration-rate telemetry; recovery: runtime cooldowns (step 14) plus a score-hysteresis margin before triggering a migration.
  3. Cache-affinity overfitting — KV-cache scoring dominates so heavily that load imbalance across GPUs grows unchecked; debug via GPU-utilization variance across the fleet; recovery: cap the affinity score's weight relative to the fragmentation/topology terms.
  4. Unfair GPU monopolization by one tenant exploiting affinity stickiness; debug via per-tenant GPU-hour share vs. quota; recovery: fairness scoring (step 13) caps affinity stickiness per tenant.

15.7 Performance Concerns

  • Placement heap allocations per scoring pass — pool-allocate scoring-candidate buffers, reused across requests.
  • Cache misses during scoring over a large RuntimeDescriptor table — structure-of-arrays layout for the hot scoring fields (GPU free memory, queue depth) to keep the scan cache-resident.
  • Excessive lock acquisition — arc-swap snapshot reads (ADR-02) avoid a lock per scoring pass entirely.

15.8 Edge Cases

  • Runtime disappears mid-placement (heartbeat lapses between candidate selection and lease proposal) — lease-acceptance re-validation (Pitfall 1 recovery) catches this.
  • Partial GPU availability (some GPUs on a node are quarantined, others healthy) — GpuSet scoring operates at the individual-GPU granularity, not node granularity.
  • Stale cache metadata after a runtime restart clears its KV cache — affinity score decays to zero on detected restart (via heartbeat_epoch reset, §11).

15.9 Failure Analysis

Scheduler thrashing appears as excessive placement migrations with no corresponding cluster-capacity change. Detection depends on migration-rate telemetry and runtime-churn metrics; root cause is almost always insufficient hysteresis margin (Pitfall 2) or a scoring-weight misconfiguration causing two runtimes to alternate as the top-scored candidate. Containment: runtime cooldowns bound the blast radius to the oscillating workload, not the cluster. Postmortem guidance: replay the affected placement sequence (§19) and diff score breakdowns across consecutive decisions.

15.10 Operational Notes

  • Operators require placement heatmaps and topology-aware cluster visualization (fed by score_breakdown, §11).
  • Metrics: placement_latency_ms (p50/p99), migration_rate, gpu_overlap_detected_total (I7).
  • Tracing spans: placement.score, placement.lease_negotiate, placement.commit.
  • Compatibility: ScoreBreakdown field additions are additive-only; operator-cli must render an unknown field generically rather than fail (P9).

Containment: quarantine (soft) before eviction (hard).

18.5 Conformance Fixtures

  • fixtures/autoscale/scale_flap_case.json — borderline pressure score oscillating near threshold; expects hysteresis (step 6) to suppress flapping.
  • fixtures/autoscale/warm_pool_recovery.json — warm pool exhausted under burst; expects cold-start provisioning bounded by the 2-minute budget.
  • fixtures/autoscale/quota_scale_conflict.json — two reservation budgets exceed headroom; expects quota-respecting arbitration.

18.6 Pitfalls

  1. Oscillating scale loops — root cause: symmetric thresholds with no hysteresis gap; signal: alternating scale-up/down within one cooldown window; recovery: asymmetric hysteresis (step 6).
  2. Cold-start amplification — root cause: warm-pool floor below the measured p99 startup latency; recovery: raise the floor to cover p99, not the median (step 9).
  3. Delayed metrics causing scale overshoot — root cause: a stale queue-depth sample in the predictive window; recovery: gate decisions on metric freshness (mirrors §15.6 Pitfall 1).
  4. Quota-blind forecast causing runaway scale-up — root cause: the predictive window ignores I9; recovery: quota-aware scaling (step 19) caps the forecast at remaining budget.

18.7 Performance Concerns

  • Decision frequency trades oscillation risk against missed burst windows, tuned against cooldown (step 4).
  • Autoscaling replay traces (step 11) batch with placement WAL writes to avoid a second fsync path.
  • The predictive window (step 2) must stay cheap enough to run every tick without competing with placement-engine's scoring pass for CPU.

18.8 Edge Cases

  • Autoscaler partitioned from scheduler-core — fails closed (no decisions) rather than acting on stale cluster-pressure data.
  • Cloud-API provisioning failures (Kubernetes-present only) — rollback (step 14) retries an alternate target with backoff.
  • Delayed node registration after a successful provision call stays "in-flight" in the audit trail until the registration TTL expires.

18.9 Failure Analysis

Scale failures typically show as sustained queue saturation despite an apparent successful scale event — provisioning startup lag or a registration deadlock. Detection cross-references node_startup_latency _seconds against the audit trail's decision timestamp; a large gap localizes the fault to provisioning. Containment: failed-scale rollback (step 14) prevents a stuck attempt from blocking healthier targets. Blast radius is bounded to the affected pool.

  • Metrics: cluster_pressure_score, warm_pool_depth, scale_decision_total{direction}, node_startup_latency_seconds.
  • Tracing spans: autoscale.decide, autoscale.provision, autoscale.drain_before_terminate.

  • Operators require scaling-event audit logs and predictive-capacity dashboards, surfaced through operator-cli (§21).

19.4 Acceptance Criteria

  • Replay reproduces 100% of PlacementDecision rows bit-for-bit across 1,000 WAL segments (I8), zero checksum divergence.

  • fixtures/replay/replay_regression_case.bin — a known-good WAL segment; expects byte-identical replay across binary versions.
  • fixtures/tracing/trace_sampling_case.json — mixed error/success traces; expects tail-based sampling to retain 100% of error traces regardless of the head-sampling rate.
  • fixtures/tracing/corrupted_trace_case.json — a span with a missing parent; expects orphan-span handling, not a dropped trace.

19.6 Pitfalls

  1. Cardinality explosion — root cause: a metric labeled by request_id/stream_id; recovery: allowlist enforcement (step 7) rejects new high-cardinality registrations.
  2. Replay drift between original and reconstructed decisions — root cause: reintroduced nondeterminism (e.g. unordered-map iteration, §13.6 Pitfall 4); recovery: audit every scoring path, re-apply deterministic ordering.
  3. Telemetry overhead on the hot path — root cause: synchronous span export during scoring; recovery: asynchronous, batched export (P5).
  4. Sampling bias hiding rare failures — root cause: pure head-based sampling drops low-frequency error traces; recovery: dual head/tail sampling (step 6).

19.7 Performance Concerns

  • Trace serialization at 5,000-node × per-request span volume — batched async export off the hot path.
  • Storage amplification from full-fidelity retention — tiered retention (step 18) bounds growth.
  • Ingestion saturation at high cardinality — allowlists (step 7) primary control, downsampling (step 8) secondary.

19.8 Edge Cases

  • Missing trace parents from a crashed span-emitter — best-effort causality reconstruction, not discard.
  • Replay schema mismatch after a PlacementDecision field addition — renders an unknown-but-additive field generically (P9).
  • WAL truncation mid-replay halts at the last valid checksum boundary, reporting a partial result.

19.9 Failure Analysis

A replay mismatch signals either an upstream invariant violation or reintroduced nondeterminism (Pitfall 2) — never a replay-framework bug in isolation. Operators compare replay checksums and scheduler epochs (I6) to localize which subsystem's write drifted. Replay-performance snapshots (step 20) run continuously against a standing corpus, so a determinism regression surfaces in CI before a production incident. Blast radius: replay-only, unless the same nondeterminism also affected the original decision (then it is an I1/I7 incident).

19.10 Operational Notes

  • Mandatory dashboards: queue saturation, scheduler-decision latency, GPU utilization, placement churn, replay divergence rate.
  • Metrics: trace_sample_rate, cardinality_reject_total, replay_divergence_total (I8), incident_bundle_export_duration_ms.
  • Tracing spans: replay.extract, replay.checksum_validate, replay.differential_compare.
  • Migration: trace/replay-bundle schema changes are additive-only (P9).

20. Phase 8 — Fairness, Preemption & Speculative Execution

20.1 Objectives

  • Finalize the preemption pipeline coordinated between placement-engine (§15.2 step 10) and scheduler-core/src/preemption.rs, enforcing I1/I7 on every preemption.
  • Complete cross-tenant fairness enforcement (I10) under sustained contention, including starvation detection.
  • Implement cooperative, cache-aware preemption minimizing KV-cache invalidation cost.
  • Finalize speculative-execution placement coordination for dry-run candidates evaluated ahead of commit.

20.2 Detailed Implementation Steps

  1. Implement the preemption decision function per Borg's priority/preemption model (Verma et al., 2015, §5); every preemption is a compensating transition (P10), never a silent overwrite.
  2. Add preemption-candidate selection scoring priority-inversion risk and KV-cache invalidation cost, preferring the lowest-affinity-loss target (§15.2 step 6).
  3. Implement cooperative preemption signaling — a bounded grace-period drain before forced termination, mirroring node-drain semantics (§16.2 step 16).
  4. Add fairness-window enforcement finalization closing the loop between admission-time tagging (§14.2 step 17) and placement-time fairness scoring (§15.2 step 13).
  5. Implement starvation detection — a tenant below the I10 threshold for N consecutive windows triggers forced-preemption escalation.
  6. Add speculative-placement finalization — a dry-run (§15.2 step 8) commits only after the preemption pipeline confirms the target GPU set is actually reclaimable.
  7. Implement preemption fencing — a preempted lease's token (I11) is revoked before the reclaimed set is offered, closing the I1/I7 double-allocation window.
  8. Add preemption cost accounting recording the KV-cache-affinity loss, feeding the cache-affinity- overfitting guard (§15.6 Pitfall 3) with measured, not estimated, cost.
  9. Implement priority-band-ordered preemption — a request cannot preempt a strictly higher-priority lease (§5), preventing inversion at the preemption boundary itself.
  10. Add preemption replay logging extending I8 to the preemption path, not only initial placement.
  11. Implement Ray-style speculative dry-run coordination (Moritz et al., 2018, §5) for candidates that may be discarded without a committed side effect.
  12. Add preemption-storm damping — a per-window preemption cap prevents one escalation cascading.
  13. Implement per-priority-class grace periods — interactive classes get a shorter forced-termination grace period than bulk classes (P7).
  14. Add fairness-deviation alerting — a 5% (§14.4) breach triggers automatic re-weighting before forced preemption escalates.
  15. Implement preemption-target diversity, avoiding repeated preemption of one tenant across windows — a second-order fairness property beyond I10.
  16. Add speculative-evaluation budget limits bounding dry-run count per request, protecting the p99 placement budget (§4, §15.7).
  17. Implement preemption-outcome verification — confirms the preempted lease released its GPU set (via a follow-up RuntimeDescriptor refresh) before marking the preemption complete.
  18. Add a cross-tenant preemption audit trail logging the triggering signal and preempted tenant.
  19. Implement preemption-aware autoscaling feedback — sustained preemption rate feeds cluster-pressure scoring (§18.2 step 7) as a corroborating undercapacity signal.
  20. Add preemption simulation mode replaying historical contention against the finalized pipeline (§7) before a policy-parameter change ships.

20.3 Deliverable

A finalized preemption and fairness pipeline enforcing bounded starvation, cache-aware cost minimization, and speculative-placement coordination, fully replay-instrumented.

20.4 Acceptance Criteria

  • Fairness deviation stays under 5% (I10, §14.4) across a 72-hour multi-tenant soak (§26).
  • Zero priority-inversion preemptions across 10,000 simulated contention scenarios.
  • Zero I1/I7 violations across 1,000 concurrent speculative-placement-then-preempt sequences.
  • Starvation escalation resolves within 2 fairness windows on fixtures/fairness/starvation_escalation _case.json.

20.5 Conformance Fixtures

  • fixtures/fairness/starvation_escalation_case.json — one tenant below threshold for 3 consecutive windows; expects forced-preemption escalation, not indefinite re-weighting alone.
  • fixtures/preemption/preemption_fencing_race.json — speculative placement and fencing interleaved; expects the reclaimed GPU set never double-offers.
  • fixtures/preemption/priority_inversion_case.json — a low-priority request attempts to preempt a higher-priority lease; expects rejection at the ordering boundary (step 9).

20.6 Pitfalls

  1. Preemption storms from one starvation escalation — root cause: no per-window cap; recovery: preemption-storm damping (step 12).
  2. Speculative/preemption race producing a transient double-allocation — root cause: a candidate is offered before release is verified; recovery: fencing (step 7) plus outcome verification (step 17).
  3. Cache-affinity cost blindness — root cause: candidate selection ignores invalidation cost; recovery: weight selection by cache-affinity loss (step 8), not priority alone.
  4. Grace-period abuse — a preempted runtime never confirms release; recovery: forced termination after grace-period expiry, escalated to node quarantine if repeated (§16.2 step 10).

20.7 Performance Concerns

  • Preemption-candidate scoring is a second pass bounded to the sampled candidate subset (§15.2 step 11).
  • Speculative-evaluation budget (step 16) trades exploration depth against p99 placement headroom (§4).
  • Fairness-deviation computation is incremental on enqueue/dequeue, never a full recompute per check.

20.8 Edge Cases

  • Two tenants simultaneously eligible for escalation on one shard — resolved by target diversity (step
    1. to avoid compounding cost.
  • A preempted lease's runtime crashes mid-drain, before confirming release — treated as an orphan lease (I5), reclaimed by the standard TTL scanner.
  • Speculative placement evaluated against a runtime that quarantines mid-evaluation — the dry-run result is discarded, never promoted (step 6 guard).

20.9 Failure Analysis

Fairness collapse under sustained contention shows as a rising fairness_deviation_ratio (I10) that preemption escalation is not resolving — usually preemption-target concentration on a tenant that cannot release capacity fast enough (Pitfall 4) or a damping cap set too conservatively. Detection cross- references preemption-outcome-verification latency against the escalation timeline. Containment: the storm cap bounds blast radius to one fairness window's churn; manual recovery is a temporary cap relaxation plus a quota review.

20.10 Operational Notes

  • Metrics: preemption_total{reason}, fairness_deviation_ratio (I10), preemption_cache_cost_total, starvation_escalation_total.
  • Tracing spans: preemption.select_candidate, preemption.fence, preemption.verify_release.
  • Structured-log fields: preempted_lease_id, preempting_request_id, cache_affinity_loss_estimate.
  • Compatibility: preemption-reason enum additions are additive-only (P9).

24. Operational Readiness

Metrics strategy. RED metrics (rate/errors/duration) for every API surface (scheduler-api, admission-controller); USE metrics (utilization/saturation/errors) for every runtime and queue resource; queue-depth histograms per tenant; scheduler-decision-latency histograms with p50/p99 split (§4). Metric label cardinality is allowlist-controlled (§19.2 step 7) as a release-blocking gate, not an afterthought.

Tracing strategy. One trace root per inference request, opened at scheduler-api (§3); scheduler- decision spans (§19.2 step 3) nested under it; runtime-execution spans joined via the lease-negotiation handshake. Dual head/tail sampling (§19.2 step 6) guarantees error-trace retention independent of the head-sampling rate.

Alerting philosophy. Symptom-based alerts first (client-visible latency/error-rate breach); saturation alerts second (queue depth, GPU utilization, FD budget approaching the §4 ceiling); predictive alerts third (autoscaling-forecast divergence, replication-lag trend). This ordering prevents alert fatigue from saturation signals that have not yet produced a symptom.

SLOs. Placement latency (p50 < 3ms, p99 < 20ms, §4); request success rate ≥ 99.95% (§4 availability target); queue-wait duration within the configured fairness window (I10); replay correctness — zero unexplained checksum divergence (I8) per rolling 30-day window.

Backup strategy. Periodic metadata-store snapshots (§13.2 step 3) at a bounded interval; WAL archival to durable object storage; replay-archive retention matching the 30-day replay-reconstruction window (§4); SBOM/signed-artifact retention matching the 24-month WAL-compatibility window (§25).

Rolling upgrade strategy. Wire-compatible protobuf evolution (P9, ADR-05) is the hard precondition; canary scheduler-core partitions (§21.2 step 7) run the candidate build against a traffic subset; staged runtime-agent rollout (§21.2 step 8) never restarts the fleet simultaneously. A rollback at any stage redeploys the prior signed binary against the existing WAL with no data migration (§21.10).

On-call runbook set. docs/runbooks/quorum-loss.md (FM-1, FM-3) and docs/runbooks/node- quarantine.md (FM-2, FM-7) are dry-run against the deterministic simulator (§7) as part of the Phase 9 conformance gate (§21.2 step 13) — a runbook that cannot be exercised in simulation is treated as unverified, not merely undocumented.

25. Compatibility & Versioning

  • Wire compatibility. Protobuf fields are append-only (P9, ADR-05); field renumbering or removal is a CI-blocking buf breaking failure (§12.6 Pitfall 4). A client encountering an unknown field or enum variant falls back to a documented default rather than failing closed, except for SchedulerError variants, which map to a generic Internal status (§11) to avoid masking a real failure as a no-op.
  • Storage schema versioning. metadata-store WAL records and RocksDB-backed queue-shard checkpoints (ADR-09) carry an explicit schema-version field; a reader must support the current version and the immediately prior one, matching the rolling-upgrade window.
  • Rolling upgrade support. One major version at a time — the cluster tolerates a mixed-version scheduler-core quorum during a canary rollout (§21.2 step 7) but never a two-major-version gap.
  • WAL backward compatibility. WAL readers remain compatible for 24 months (§21.10), bounding how long a rollback can reach without a migration step; this window also bounds SBOM/signed-artifact retention (§24).
  • API versioning. scheduler-api's gRPC surface is semantically versioned; a breaking change ships behind a new service version, never as an in-place mutation of an existing RPC's contract.
  • Deprecation policy. A deprecated protobuf field is removable no earlier than 24 months after the deprecation release (§21.2 step 17), enforced by the same buf breaking CI check used for renumbering.
  • Cross-crate terminology lock. SchedulerRequest, RuntimeDescriptor, PlacementDecision, QueueShard, and SchedulerError (§11) are defined once in scheduler-core/src/lib.rs and re- exported; no downstream crate redefines or shadows a type name, preventing the exact drift class this contract's cross-reference convention exists to catch.
  • Health-state and preemption-reason enums. Both are additive-only (P9); operator-cli's rendering of an unrecognized variant is generic, never a parse failure (§15.10, §20.10).

26. Testing & Verification Strategy

Unit testing. Queue invariants (I3, I10) in queue-manager; lease ownership (I1, I11) in scheduler-core/src/lease.rs; placement scoring functions in placement-engine/src/scoring.rs tested against fixed RuntimeDescriptor fixtures for reproducibility.

Integration testing. Multi-node scheduling across a three-to-five-node metadata-store quorum (§4 replication factor); replay correctness against conformance-suite's placement-replay fixtures; runtime- failure injection via the local docker-compose.yml cluster (§12.2 step 15).

Property testing. Queue ordering (FIFO-within-priority-class); monotonic stream offsets (I4); deterministic replay (I8) — properties checked via randomized fixture generation feeding the same deterministic simulator used for invariant assertions (§7).

Deterministic simulator. The single source of truth for invariant verification: drives scheduler-core, queue-manager, and metadata-store against recorded and synthetic replay corpora (§19), asserting I1–I12 independently after every simulated tick (§7's debugging-methodology paragraph). Every Pitfalls entry across Phases 0–9 that names a fixture is exercised here before it is exercised in CI integration tests.

Chaos testing. Runtime crashes mid-execution (§16.8); metadata-store network partitions (§13.8); delayed or storming heartbeats (§16.6 Pitfall 1) — injected via the fault-injection harness stood up in Phase 0 (§12.2 step 20).

Fuzzing. fuzz/wal_parser.rs against malformed/truncated WAL segments (ADR-13, §12.6 Pitfall 4); fuzz/protobuf_decode.rs against malformed SchedulerRequest payloads (T5); fuzz/queue_replay.rs against corrupted queue-replay fixtures.

Soak testing. 72-hour sustained inference traffic at the §4 GPU-utilization target (> 72%); the acceptance criterion for zero double-allocation events (§15.4) and bounded fairness deviation (§20.4) both cite this soak explicitly.

Conformance gating. conformance-suite (queue ordering, placement replay, heartbeat, WAL, streaming fixtures) must pass at 100% before any release promotion (§21.2 step 10) — the hard boundary between "tested" and "releasable."

27. Build & Release Engineering

  • Reproducible Cargo.lock builds — two clean-host builds of one commit produce an identical lock-file hash and SBOM digest (§12.4), extended to the full release pipeline in Phase 9 (§21.4).
  • cosign artifact signing (ADR-17) and syft SBOM generation (ADR-18) on every release artifact, gated into release.yml (§12.2 step 11).
  • Release channels dev/canary/stable (§21.2 step 2), promotion gated by conformance-suite pass rate and release-health scoring (§21.2 step 18).
  • Automated changelog generation from conventional-commit history (§21.2 step 3), feeding CHANGELOG.md.
  • Provenance attestation alongside the SBOM (§21.2 step 4) — an operator verifies both before deploying to a GPU cluster.
  • Container-image scanning (Trivy, ADR-16) as a release-gate check distinct from the merge-time check (§21.2 step 5), catching a base-image regression introduced between merge and release.
  • Release-time differential replay validation (§19.2 step 16, §21.2 step 6) — a determinism regression blocks canary-to-stable promotion, not just a CI warning.
  • Canary-partition rollout (§21.2 step 7) and staged, drain-before-upgrade runtime-agent rollout (§21.2 step 8) — no simultaneous fleet-wide restart at either tier.
  • Automatic rollback (§21.2 step 9) on a release-health-score breach, within the 5-minute acceptance target (§21.4).
  • Nix-pinned toolchain (flake.lock, ADR-26) ensures the CI build host and an operator's verification host produce byte-identical artifacts.

28. Performance Engineering

Methodology. Every optimization ships with a benchmark-harness (Criterion, ADR-14) fixture measuring the baseline before and after (P12) — a performance change with no measured baseline does not ship. Profiling uses flamegraphs for CPU hotspots, allocator profiling for the placement-scoring pool allocations (§15.7), lock-contention analysis for queue-shard hot paths (§14.7), and syscall tracing for WAL fsync batching (§13.7). Benchmarking strategy. Synthetic queue bursts up to the 250k req/s regional target (§4); realistic prompt-length distributions drawn from the replay corpus (§19); heterogeneous-GPU-cluster fixtures covering both dual-socket NUMA topologies named in §4's deployment assumptions.

29. Scalability Analysis

Primary bottlenecks. Scheduler-core coordination overhead as candidate-runtime count grows toward the 5,000-node ceiling (§4, §32 C4); metadata-store Raft replication fan-out, which bounds quorum write latency (§4) before it bounds node count; queue-shard imbalance under skewed tenant-hash distribution (ADR-20's rejection-regime column names this explicitly); telemetry cardinality growth at 5,000-node × per-request span volume (§19.7).

Horizontal scaling. Tenant-hash scheduler sharding (ADR-20) — each shard's queue-manager and fairness windows scale independently; runtime partitioning across NUMA-local pools; federated telemetry ingestion (tracing-pipeline, metrics-exporter) decoupled from the scheduling hot path (P5) so a telemetry-tier scale-out never touches scheduler-core.

Vertical scaling. Scheduler-core instances scale to the 64-vCPU host class (§4); larger queue- metadata memory windows trade RAM for deeper fairness-window history; increased replay caches (Phase 7, §19) trade RAM for faster incident-bundle assembly at the cost of the 32GB scheduler memory ceiling (§4).

Scaling ceilings. Metadata quorum write-fan-out pressure is the first ceiling reached, ahead of raw node count — §32 C4 derives the 5,000-node limit from this, not from placement-engine CPU. Trace- ingestion bandwidth is the second ceiling, mitigated by cardinality allowlists and tiered retention (§19.7) before it is mitigated by adding ingestion capacity. Placement fan-out (candidate-sampling depth, §15.2 step 11) is the third — Sparrow-style sampling (Ousterhout et al., 2013, §5) holds the p50 budget by deliberately not scanning the full inventory as node count grows.

Non-linear failure regime. Past the 5,000-node ceiling, Raft quorum write latency grows faster than linearly in node count because per-append fan-out competes with follower catch-up bandwidth; this is why ADR-20's tenant-hash sharding, not a larger single quorum, is the scale-out path recommended past this point (§34 Alt B covers the alternative of a larger single quorum and why it was rejected).

30. Mental Models & First Principles

  • MM1 — Tail Latency Is a Fan-Out Property. The compressed insight: a scheduler's p99 is dominated by fan-out amplification (Dean & Barroso, 2013, §5), not by any single slow component · predicts that adding redundant candidate scoring paths can raise p99 even while lowering p50 · the bug class without it: chasing p50 wins that regress p99 · applies in §28.
  • MM2 — Backpressure Is Structural, Not Optional. The insight: every unbounded queue is a future OOM with a deferred timestamp (P2) · predicts that a system passing load tests will still fail under a sustained burst if any single queue lacks a ceiling · bug class without it: silent memory growth that looks fine until it isn't · applies in §14.
  • MM3 — Determinism Buys Debuggability, Not Correctness. The insight: replay (I8) proves what happened, it does not prove what should have happened (P1, P4) · predicts that a replay-clean incident can still be a policy bug, not a determinism bug · bug class without it: chasing a "replay bug" that is actually a scoring-weight misconfiguration · applies in §19.
  • MM4 — Fencing Tokens Convert Time Into a Total Order. The insight: a fencing token (I11) turns "who had the lease last" into a comparison, not a race · predicts that any lease-like resource without a monotonic token will eventually double-grant under partition · bug class without it: split-brain double execution (I1/I7) · applies in §13.
  • MM5 — Hysteresis Is the Generic Cure for Oscillation. The insight: any control loop comparing a noisy signal against a single threshold will oscillate near that threshold (§15.6 Pitfall 2, §18.6 Pitfall 1) · predicts that autoscaling, placement, and preemption will all independently need the same fix · bug class without it: three separately "discovered" flapping bugs that are one bug · applies in §15, §18, and §20.
  • MM6 — Priority Without Fairness Windows Is Not Isolation. The insight: a priority field alone does not prevent starvation (I10) — it only orders contention, it does not bound it (P7) · predicts that a purely priority-ordered queue eventually starves a low-priority-but-paying tenant under sustained high- priority load · bug class without it: an SLA violation with a technically-correct priority ordering · applies in §14 and §20.
  • MM7 — Cache Locality Is a Scoring Input, Not a Cache-Layer Concern. The insight: KV-cache affinity (Kwon et al., 2023, §5) belongs in the placement decision itself, not in a post-hoc cache-warming pass · predicts that bolting affinity on after placement produces the exact fragmentation §15 was built to avoid · bug class without it: GPU-utilization variance despite "correct" placement scores · applies in §15.
  • MM8 — Crash-Only Design Removes a Whole Recovery-Path Class. The insight: a component that assumes abrupt termination as normal (P3) never needs a separate "graceful shutdown correctness" code path · predicts that a system with two distinct shutdown paths (graceful and crash) will eventually diverge and the untested one will be wrong · bug class without it: a clean-shutdown-only bug that only appears during an actual outage · applies in §12.

32. Back-of-Envelope Capacity Model

  • C1 — Placement p50 budget. 0.3ms queue-manager dequeue + 1.5ms placement-engine scoring over ≤200 sampled candidates (Sparrow-style, §15.2 step 11) + 1ms amortized WAL-append fsync = 2.8ms, inside the §4 3ms p50 ceiling.
  • C2 — Queue enqueue throughput. 50M tok/min regional target ÷ ~200 avg tokens/req = 250,000 req/min ÷ 60 = 4,167 req/s sustained average; provisioned to the 250k req/s §4 burst ceiling for a ~60x burst headroom over sustained average.
  • C3 — GPU utilization target derivation. 100% theoretical − 18% fragmentation loss (Robin-Hood-style multi-GPU split overhead, §15.6 Pitfall 1's mitigation) − 10% preemption/drain overhead (§20) = 72% sustained target, matching §4.
  • C4 — Max cluster nodes. 15ms Raft quorum write-latency budget (§4) ÷ 0.003ms marginal fan-out cost per follower at intra-region RTT (0.2–2ms, §4) = 5,000 nodes before replication lag exceeds the budget, matching §4's ceiling.
  • C5 — Max active models / lease-table budget. 25,000 models × 1.2KB average PlacementDecision + lease-table row footprint = 30MB, well inside the 32GB scheduler memory ceiling (§4), leaving headroom for queue-shard state (C8 below).
  • C6 — Startup recovery window. 25,000-model snapshot load at ~250 models/s deserialization rate (RocksDB-backed, ADR-09) ≈ 100s + WAL-tail replay ≈ 15s = 115s, inside the §4 120s ceiling.
  • C7 — Error budget. 0.05% of a 30.44-day month = 0.05% × 30.44 × 24 × 60 = 21.6 minutes/month, matching §4 exactly.
  • C8 — Concurrent-stream memory footprint. 2,000,000 max streams (§4) × ~4KB per-stream buffer (§17.2 step 5) = 8GB, within the 32GB scheduler memory ceiling (§4) alongside C5's 30MB lease-table footprint.
  • C9 — Runtime-agent memory ceiling check. 512MB budget (§4) ÷ 8 GPUs/node average (§4) = 64MB per GPU inventory record's amortized share, comfortably inside NVML-class probe overhead.
  • C10 — Max FDs vs. concurrent streams. 2,000,000 FD budget (§4) ÷ 2,000,000 max concurrent streams (§4) = 1.0 FD per stream, exactly matching the 1-FD-per-stream design assumption with zero multiplexing slack — gRPC connection multiplexing (ADR-19) is required, not optional, to avoid exhausting the FD ceiling under the max-stream scenario.

33. Hard Questions (Self-Examination)

  • Q1. Why does §4's p50/p99 gap (3ms vs. 20ms, a 6.7x ratio) not indicate a tail-latency bug, given §28's fan-out reasoning (§4, §28)?

  • Q3. §18's autoscaling hysteresis (§18.2 step 6) and §15's runtime cooldowns (§15.2 step 14) are the same fix applied twice — why weren't they unified into one shared primitive, and what would unifying them cost the independent-failure property invariants rely on (§15, §18, §7)?
  • Q4. §20's preemption-outcome verification (§20.2 step 17) depends on a follow-up RuntimeDescriptor refresh — what happens to preemption correctness if that refresh itself reads a stale snapshot, the exact failure §15.6 Pitfall 1 already names (§15, §20)?
  • Q5. §9's ADR-04 locks Raft for "operational familiarity," but §29 shows quorum write fan-out is the first scaling ceiling hit — did the ADR under-weight the scaling cost of that choice relative to Omega- style optimistic concurrency (§9, §29, §34)?
  • Q6. §17's streaming aggregator lives inside the stateless scheduler-api tier, but §3's diagram draws it as a separate box after the model runtime — is the repository layout (§10) actually consistent with the architectural diagram, and if not, which one is wrong (§3, §10, §17)?
  • Q7. §14's admission-controller fast-path explicitly avoids scheduling work before acceptance — but §18's predictive autoscaling forecast reads queue_depth{tenant} (I3), a post-admission signal — does this create a subtle timing dependency where admission and autoscaling disagree on load during a burst (§14, §18)?
  • Q8. §32's C2 shows 250k req/s is a ~60x burst multiple over sustained average — does §4's queue- shard-level memory accounting (P8) actually bound worst-case memory at that burst multiple, or only at sustained average (§4, §32, §14)?
  • Q9. §19's replay-differential testing (§19.2 step 16) catches determinism regressions between binary versions — but what catches a determinism regression introduced within one version, before any second version exists to diff against (§19, §26)?
  • Q10. §22's T3 (falsified runtime telemetry) is mitigated by corroborating signals, but §16's degraded-node scoring penalty (§15.2 step 15) still trusts the runtime's self-reported health as one of those signals — is the corroboration actually independent, or partially circular (§22, §15, §16)?
  • Q11. §20's preemption-storm damping (§20.2 step 12) bounds concurrent preemptions per window — does this interact with §18's scale-up trigger (§18.2 step 7, which treats preemption rate as an undercapacity signal) to produce a delayed scale-up exactly when preemption pressure is capped rather than resolved (§20, §18)?
  • Q12. §25's 24-month WAL-compatibility window and §24's matching SBOM-retention window are both derived from the same number — if a future ADR shortens WAL compatibility, does §24's backup strategy silently become inconsistent unless someone remembers to check it (§24, §25)?
  • Q13. §31 compares this system favorably against Kubernetes on placement latency — but Kubernetes serves a broader workload diversity; does §4's constraint table implicitly assume a workload homogeneity Kubernetes does not get to assume, making the comparison less fair than it reads (§4, §31)?
  • Q14. §13's snapshot-transfer throttling (§13.2 step 15) bounds bandwidth to avoid starving live traffic — but §12.4's startup-recovery acceptance criterion (§12.4) requires a 120s bound on loading a 25,000-model snapshot — do these two constraints admit a feasible throttle setting simultaneously, or only under favorable network assumptions (§13, §12, §4)?
  • Q15. §30's MM5 claims hysteresis is a generic oscillation cure applied independently in §15, §18, and §20 — if a future engineer unifies them into one shared crate primitive, does every phase's Pitfalls section referencing its own hysteresis mechanism need updating, and would the harness (§16 of the standard) even catch a stale reference (§30, §15, §18, §20)?
  • Q16. §21's canary-partition rollout (§21.2 step 7) evaluates release health per-shard — but §20's fairness windows are also per-shard (ADR-20) — could a canary shard's fairness deviation be misattributed to the release candidate when it is actually ordinary cross-tenant contention (§21, §20)?

Alt A — Centralized Monolithic Scheduler

|         Single Scheduler Process         |
|  admission + queue + placement + lease   |
|  + metadata (in-process, no Raft)        |
+--------------------+---------------------+
                     | direct dispatch
          +----------v----------+
          |   Runtime Agent Mesh  |
          +-----------------------+

Regime where it wins: a single-region, single-tenant cluster under ~500 nodes where operational simplicity outweighs the availability cost of a single point of failure. The real system that embodies this: early single-controller Slurm deployments (slurmctld without HA failover configured, §5 Reference Implementations). Rejected here because §4's 99.95% availability target and 5,000-node ceiling both require surviving a single-node loss without an acknowledged-write-loss window (I2) — a monolith cannot satisfy this without becoming, in effect, a poorly-tested reimplementation of Raft.

Alt B — Single Larger Raft Quorum Instead of Tenant-Hash Sharding

+------------------------------------------+
|      One Raft Quorum, All Tenants          |
|      (no ADR-20 sharding)                  |
+------------------+--------------------------+
                   | linearizable reads/writes
        +----------v-----------+
        |  All Scheduler Shards |
        +-----------------------+

Regime where it wins: a cluster small enough (well under the §32 C4-derived 5,000-node ceiling) that quorum write-fan-out never becomes the bottleneck, and where cross-tenant global ordering has real value (e.g., strict global fairness auditing). The real system that embodies this: etcd deployed as a single cluster-wide store without application-level sharding (§5 Reference Implementations, etcd-io/etcd). Rejected here because §29's scalability analysis shows quorum fan-out is the first ceiling hit at scale — tenant-hash sharding (ADR-20) trades a small amount of cross-shard ordering guarantee for headroom against exactly this ceiling.

Alt C — Fully Decentralized Peer-to-Peer Placement (No Central Scheduler)

+--------+   gossip    +--------+   gossip    +--------+
| Node A |<----------->| Node B |<----------->| Node C |
+--------+             +--------+             +--------+
   ^ each node self-selects placements via local view

Regime where it wins: extremely large, latency-insensitive batch clusters where no single component needs a global view and eventual consistency in placement decisions is acceptable — closer to how some peer-to-peer distributed hash tables place data. No mainstream inference scheduler embodies this in production today; the closest real-world analogue is gossip-based service discovery layers (e.g., Serf/Consul's gossip protocol) used for membership, not placement. Rejected here because I1 (lease uniqueness) and I7 (GPU exclusivity) require a linearizable arbitration point under contention — a purely gossip-based system can only achieve this with a secondary consensus layer, which collapses back to Alt B's tradeoffs while adding gossip-convergence latency on top.

Alt D — Kubernetes-Native Scheduler Extension (No Standalone Control Plane)

+---------------------------------------------+

|   +-------------------------------------+     |
|   |  Custom Scheduler Extender/Plugin    |     |
|   +-------------------------------------+     |
+---------------------------------------------+

Regime where it wins: organizations fully committed to Kubernetes as the only orchestration surface, where reusing kube-scheduler's reconciliation loop and RBAC model outweighs the latency cost of API-server round trips on every scoring decision. 36. Glossary

  • Admission Shedding — intentional rejection of incoming work under overload, before scheduling work is spent (P8).
  • Anti-Affinity — a placement constraint preventing co-location of conflicting tenants or workloads.
  • Backpressure — bounded-capacity signaling that propagates upstream pressure instead of buffering unboundedly (P2).
  • Batch-Assembly Window — the 1–15ms configurable interval during which same-SLA-class requests are grouped for execution (§4).
  • Cache Affinity — scoring preference for a runtime holding a reusable KV-cache prefix for a request.
  • Canary Partition — a subset of scheduler-core shards running a release candidate ahead of full promotion (§21).
  • CAS (Compare-And-Swap) — an atomic conditional update used for lease acquisition and quota decrement.
  • Cluster-Pressure Score — an aggregate autoscaling input combining queue depth, GPU utilization, and fragmentation (§18).
  • Cooldown Period — a bounded window after a scaling or placement decision during which the same decision cannot repeat, bounding oscillation.
  • Crash-Only Component — a process designed to treat abrupt termination as a normal event, not an exception (P3).
  • Deterministic Simulator — the CI harness asserting I1–I12 independently after every simulated tick (§7).
  • Drain State — a runtime health state accepting no new work while finishing active work.
