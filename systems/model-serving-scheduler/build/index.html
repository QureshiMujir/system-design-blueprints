⬜ Phase 0 — Repository Bootstrap & Deterministic Foundations §12

Objectives
  • Establish a reproducible repository foundation across all fifteen Phase 0 crates (§1).
  • Implement deterministic configuration loading with a checksum-verifiable snapshot.
  • Create the structured-logging and tracing baseline every later phase depends on (P5).
  • Freeze the initial protobuf contract set (scheduler-api/proto/scheduler.proto).
  • Stand up CI (ADR-12) and the reproducible build strategy (ADR-26).
  • Define the scheduler-epoch primitive (I6) and the structured error taxonomy (§11).
Deliverable

Workspace builds clean on a fresh host with zero clippy warnings; CI green end to end; protobuf generation is byte-reproducible across two independent hosts; a running (empty) scheduler-api process emits build SHA, config checksum, and a startup trace span visible in the local Jaeger/OTel collector.

Acceptance
  • Reproducible build: two clean-host builds of the same commit produce identical Cargo.lock hash and an identical SBOM digest.
  • Zero clippy warnings across all fifteen crates.
  • CI wall-clock runtime under 15 minutes (§4-adjacent operational budget, not a hot-path number).
  • Configuration checksum reproducible byte-for-byte given identical env + file inputs.
  • fixtures/config/config_valid.toml loads with zero errors; fixtures/config/config_invalid_queue .toml is rejected with SchedulerError::InvalidRequest-class diagnostics.
Fixtures
  • fixtures/config/config_valid.toml — canonical valid configuration, one per deployment topology.
  • fixtures/config/config_invalid_queue.toml — malformed queue-depth field, expects rejection.
  • fixtures/boot/scheduler_boot_trace.json — expected startup span tree for regression comparison.
  • fixtures/replay/replay_seed_fixture.bin — deterministic RNG seed corpus consumed from Phase 7.
Pitfalls
  1. Hidden nondeterministic timestamps in log lines defeat config-checksum reproducibility — root cause: SystemTime::now() called during config normalization; debug via diffing two checksum runs; signal: checksum mismatch with no config change; recovery: inject a fixed clock during checksum computation.
  2. Dependency version drift between CI and a developer laptop — root cause: unpinned transitive range in Cargo.toml; debug via Cargo.lock diff; signal: "works on CI, fails locally"; recovery: cargo update -p <crate> --precise.
  3. Environment-variable precedence ambiguity — root cause: undocumented override order; debug via the config-checksum trace which logs the winning source per field; recovery: enforce the CLI > env > file

    default order from step 6 in code, not convention.

  4. Protobuf backward incompatibility introduced silently — root cause: a field renumbered instead of appended; debug via buf breaking in CI; recovery: revert, re-add as a new field number (P9).

⬜ Phase 1 — Metadata Store & Raft Replication §13

Objectives
  • Implement the authoritative metadata plane (metadata-store) behind a Raft quorum (ADR-04).
  • Support replicated scheduler state: node inventory, leases, placement state, quotas, topology.
  • Provide runtime lease semantics enforcing I1 (Placement Lease Uniqueness).
  • Persist WAL entries durably before acknowledgement, enforcing I2.
Deliverable

A three-to-five-node (§4 replication factor) metadata-store quorum that survives one-node failure with zero acknowledged-write loss, durable WAL, snapshot-based recovery, and deterministic replay of any committed segment.

Acceptance
  • Quorum survives one-node failure with write availability restored within the < 15ms metadata quorum write-latency budget (§4) once re-formed.
  • Replay of fixtures/wal/wal_partial_write.bin restores a consistent state with zero silently dropped writes.
  • No acknowledged write loss across 10,000 injected crash-recovery cycles in the deterministic simulator.
  • Snapshot transfer completes for a 25,000-model metadata set within the < 120s startup-recovery budget (§4).
Fixtures
  • fixtures/raft/raft_split_brain.bin — dual-leader scenario; expects fencing-token rejection of the stale leader.
  • fixtures/wal/wal_partial_write.bin — truncated append; expects checksum-detected rollback.
  • fixtures/lease/lease_recovery_case.json — lease table state after a crash mid-lease-acquisition.
Pitfalls
  1. fsync batching starvation — small writes queue behind a fsync barrier under load; debug via WAL append-latency histogram tail; signal: p99 append latency exceeds the 25ms fsync-durability budget (§4); recovery: group-commit batching with a bounded wait window.
  2. Stale leader acceptance after a network partition heals — root cause: missing fencing-token check on AppendEntries; debug via raft_split_brain.bin; recovery: reject any RPC bearing a lower term.
  3. Snapshot corruption during transfer — root cause: unbounded transfer interrupted mid-stream; debug via checksum mismatch on receive; recovery: resumable chunked transfer with per-chunk checksums.
  4. Replay divergence between two replicas — root cause: nondeterministic iteration order over a HashMap during snapshot serialization; debug via replay_divergence_total (I8); recovery: use a deterministically ordered (BTreeMap-backed) snapshot encoder.

⬜ Phase 2 — Queue Manager & Admission Control §14

Objectives
  • Implement bounded, tenant-isolated queueing (queue-manager) enforcing I3 (Queue Capacity Bound).
  • Add SLA priority classes and weighted fairness windows enforcing I10.
  • Implement admission-controller quota, SLA, and legality fast-fail validation.
  • Provide replayable queue transitions consumable by replay-framework (Phase 7, §19).
Deliverable

Persistent, bounded, tenant-isolated queues with SLA-class fairness, replayable queue transitions, and an admission fast-path that rejects malformed or over-quota work before any placement work is spent.

Acceptance
  • No queue growth beyond the configured per-shard limit under a sustained 250k req/s burst (§4).
  • Fairness deviation across tenants stays under 5% of configured window share (I10 threshold).
  • Cancellation propagation reaches the queue within 50ms of client disconnect.
  • fixtures/tenancy/tenant_starvation_case.json shows zero starvation events after the fix, versus a documented starvation event before it.
Fixtures
  • fixtures/tenancy/tenant_starvation_case.json — one tenant saturates a shard; expects fairness re-weighting within one fairness window.
  • fixtures/admission/overload_shed_case.json — burst beyond queue capacity; expects graceful shedding, not crash.
  • fixtures/admission/malformed_request.pb — a SchedulerRequest with a negative prompt_tokens; expects SchedulerError::InvalidRequest.
Pitfalls
  1. Priority inversion — a low-priority request holds a shard lock a high-priority request needs; debug via lock-hold-time histograms; signal: high-priority p99 latency spikes despite low queue depth; recovery: priority-inheritance-free design — shards never hold cross-tenant locks (P6).
  2. Queue amplification — a retry storm re-enqueues faster than it drains; debug via enqueue-rate vs drain-rate divergence; recovery: exponential backoff on RETRY_PENDING re-enqueue.
  3. Stale cancellations — a cancellation arrives after the request already left the queue for placement; debug via cancellation-vs-state-machine-state cross-check; recovery: cancellation is idempotent and checked at every state-machine transition, not just at the queue.
  4. Timer-wheel scaling collapse under high delayed-queue cardinality; debug via timer-tick latency; recovery: hierarchical timer wheel instead of a flat one.

⬜ Phase 3 — Placement Engine & GPU-Aware Scheduling §15

Objectives
  • Implement GPU-aware scheduling in placement-engine with topology, anti-affinity, and fragmentation scoring.
  • Support KV-cache locality as a first-class scoring input, not a post-hoc heuristic.
  • Implement preemption and speculative-placement evaluation feeding scheduler-core.
  • Hold the p99 < 20ms placement-latency budget (§4) under 5,000-node cluster scale.
Deliverable

A functioning placement engine producing topology- and cache-aware GPU assignments, coordinating runtime-lease negotiation, with every decision explainable and replay-deterministic.

Acceptance
  • p99 placement latency < 20ms under a 5,000-node, 40,000-GPU synthetic cluster (§4).
  • Placement replay is bit-for-bit deterministic across 1,000 replayed WAL segments (I8).
  • Zero double-allocation events (I1/I7) across a 72-hour soak run (§26 soak testing).
Fixtures
  • fixtures/placement/gpu_fragmentation_case.json — fragmented inventory; expects a fit despite no single node having full free capacity via multi-GPU split scoring.
  • fixtures/placement/stale_heartbeat_case.json — inventory snapshot older than TTL; expects exclusion from candidate scoring, not a stale placement.
  • fixtures/placement/topology_preference_case.json — NUMA-local candidate present; expects it to outscore an equally-free but NUMA-remote candidate.
Pitfalls
  1. Stale inventory snapshots used for scoring — root cause: snapshot read racing a heartbeat update; debug via snapshot-age vs. decision-time delta; signal: placement onto a runtime that was already full; recovery: re-validate GPU-fit at lease-acceptance time, not just at scoring time.
  2. Placement oscillation — repeated migration of the same workload between two near-equally-scored runtimes; debug via migration-rate telemetry; recovery: runtime cooldowns (step 14) plus a score-hysteresis margin before triggering a migration.
  3. Cache-affinity overfitting — KV-cache scoring dominates so heavily that load imbalance across GPUs grows unchecked; debug via GPU-utilization variance across the fleet; recovery: cap the affinity score's weight relative to the fragmentation/topology terms.
  4. Unfair GPU monopolization by one tenant exploiting affinity stickiness; debug via per-tenant GPU-hour share vs. quota; recovery: fairness scoring (step 13) caps affinity stickiness per tenant.

⬜ Phase 4 — Runtime Agents & Health Propagation §16

Objectives
  • Implement node-local runtime-agent processes exposing GPU inventory, health, and queue pressure.
  • Propagate heartbeats at the §4 1s interval with < 5s failure detection.
  • Support runtime draining for planned maintenance without dropping in-flight work.
  • Distinguish heartbeat absence from confirmed runtime failure (§16.9).
Deliverable

Production-capable runtime agents propagating heartbeats and health at the §4 1s interval, with orphan leases reclaimed automatically and node drain completing without dropping in-flight work.

Acceptance
  • Node failure detected within 5 seconds of the fifth missed heartbeat (§4 derivation).
  • Orphan leases reclaimed within one node-heartbeat-service TTL scan cycle.
  • Runtime drain completes for a node with 200 active streams within the 60s graceful-shutdown budget.
Fixtures
  • fixtures/heartbeat/missing_heartbeat.pb — five consecutive missed heartbeats; expects quarantine, not immediate eviction.
  • fixtures/heartbeat/corrupt_gpu_inventory.json — malformed GPU inventory payload; expects rejection and a degraded mark per §8's failure example.
  • fixtures/lease/lease_orphan_case.json — a lease with no owning request; expects reclamation within one TTL scan.
Pitfalls
  1. Heartbeat storms — all nodes send heartbeats on the same tick boundary, saturating node-heartbeat-service; debug via ingest-latency spike aligned to a fixed period; recovery: jittered send offsets (step 11).
  2. Node-flap amplification — a runtime oscillating between Healthy and Degraded triggers repeated placement migrations; debug via health-state transition rate per node; recovery: quarantine after a consecutive-failure threshold, not a single miss (§8).
  3. Stale runtime descriptors served to placement-engine after a heartbeat gap — debug via snapshot-age check; recovery: exclude any snapshot older than TTL from candidate scoring (§15.6 Pitfall 1).
  4. Telemetry overload from per-node metric explosion at 5,000-node scale — debug via metrics-exporter cardinality dashboards; recovery: cardinality controls (§19.2 step 7).

⬜ Phase 5 — Streaming Execution Pipeline §17

Objectives
  • Implement token streaming with deterministic ordering, enforcing I4 (Token Stream Monotonicity).
  • Support client-cancellation propagation within a 100ms budget derived from the admission p99 (§4).
  • Provide backpressure across the client-facing stream boundary, per P2.
  • Isolate stream failure from placement correctness — a stream fault never re-triggers a placement.
Deliverable

Stable, cancellation-safe token streaming with enforced ordering, adaptive flushing, and forensic replay capture, running entirely in the stateless gateway tier.

Acceptance
  • Zero token reordering across 100,000 synthetic multi-chunk streams in conformance-suite.
  • Cancellation reaches the owning lease within 100ms of client disconnect, p99.
  • fixtures/streaming/duplicate_token_case.json detects corruption with zero false negatives over 10 runs.
  • Idle-stream eviction reclaims a leaked buffer within one eviction cycle (30s default).
Fixtures
  • fixtures/streaming/out_of_order_stream.json — non-monotonic chunk delivery; expects reordering to restore I4 before client delivery.
  • fixtures/streaming/duplicate_token_case.json — a runtime double-emits a chunk; expects dedup via the integrity checksum (step 18).
  • fixtures/streaming/runtime_disconnect_trace.bin — mid-stream disconnect; expects failover or a clean SchedulerError::RuntimeUnavailable termination.
Pitfalls
  1. Stalled client sockets holding a buffer indefinitely — root cause: no read-progress timeout; signal: buffer occupancy climbing with no drain; recovery: idle-stream eviction (step 6).
  2. Stream-buffer leaks under cancellation races — root cause: cancellation arrives after a flush is already scheduled; recovery: cancellation checked at every flush boundary (mirrors §14.6 Pitfall 3).
  3. Head-of-line blocking across multiplexed streams — root cause: one slow stream's flow-control window starves siblings; recovery: independent per-stream flow-control windows (RFC 9113 §5).
  4. Duplicate emission after disconnect-recovery failover — root cause: the original runtime's late chunk arrives post-failover; recovery: fencing-token check (I11) rejects it.

⬜ Phase 6 — Autoscaling & Elastic Capacity §18

Objectives
  • Implement reactive, queue-aware autoscaling in scheduler-core/src/autoscale.rs without oscillation, building on the cooldown pattern from §15.6 Pitfall 2.
  • Support warm-pool capacity bounding cold-start latency against the rebalance budget (§4, < 2 min).
  • Provide tenant- and cost-aware scaling consistent with quota-engine budgets (I9).
  • Emit every scaling decision as a replayable record, consistent with P4.
Deliverable

A reactive, replay-instrumented autoscaling subsystem scaling capacity within the rebalance-convergence budget without oscillation, respecting tenant reservations and quota.

Acceptance
  • Zero flap events (more than one direction reversal within one cooldown window) across fixtures/autoscale/scale_flap_case.json replayed 1,000 times.
  • fixtures/autoscale/warm_pool_recovery.json restores target capacity within the 2-minute budget (§4).
  • 100% of scale decisions replay bit-for-bit (I8 extended to capacity decisions).
  • fixtures/autoscale/quota_scale_conflict.json resolves deterministically — the tenant floor wins.
Fixtures
  • fixtures/autoscale/scale_flap_case.json — borderline pressure score oscillating near threshold; expects hysteresis (step 6) to suppress flapping.
  • fixtures/autoscale/warm_pool_recovery.json — warm pool exhausted under burst; expects cold-start provisioning bounded by the 2-minute budget.
  • fixtures/autoscale/quota_scale_conflict.json — two reservation budgets exceed headroom; expects quota-respecting arbitration.
Pitfalls
  1. Oscillating scale loops — root cause: symmetric thresholds with no hysteresis gap; signal: alternating scale-up/down within one cooldown window; recovery: asymmetric hysteresis (step 6).
  2. Cold-start amplification — root cause: warm-pool floor below the measured p99 startup latency; recovery: raise the floor to cover p99, not the median (step 9).
  3. Delayed metrics causing scale overshoot — root cause: a stale queue-depth sample in the predictive window; recovery: gate decisions on metric freshness (mirrors §15.6 Pitfall 1).
  4. Quota-blind forecast causing runaway scale-up — root cause: the predictive window ignores I9; recovery: quota-aware scaling (step 19) caps the forecast at remaining budget.

⬜ Phase 7 — Observability & Deterministic Replay §19

Objectives
  • Complete the observability stack: tracing-pipeline, metrics-exporter, replay-framework as decoupled services (P5).
  • Implement deterministic replay reproducing any PlacementDecision bit-for-bit from WAL inputs (I8).
  • Enable forensic incident reconstruction without live reproduction.
  • Bound telemetry cardinality against the metrics-ingestion-saturation failure class.
Deliverable

End-to-end tracing across every crate boundary, replay-capable forensic debugging reproducing any placement decision bit-for-bit, and operational dashboards covering the mandatory view set (§19.10).

Acceptance
  • Replay reproduces 100% of PlacementDecision rows bit-for-bit across 1,000 WAL segments (I8), zero checksum divergence.
  • Traces available for ≥ 99.9% of requests over a 24-hour sustained-load window.
  • Incident bundles exportable within 30 seconds for any request_id inside the 30-day window (§4).
  • fixtures/replay/replay_regression_case.bin replays identically across two consecutive release builds.
Fixtures
  • fixtures/replay/replay_regression_case.bin — a known-good WAL segment; expects byte-identical replay across binary versions.
  • fixtures/tracing/trace_sampling_case.json — mixed error/success traces; expects tail-based sampling to retain 100% of error traces regardless of the head-sampling rate.
  • fixtures/tracing/corrupted_trace_case.json — a span with a missing parent; expects orphan-span handling, not a dropped trace.
Pitfalls
  1. Cardinality explosion — root cause: a metric labeled by request_id/stream_id; recovery: allowlist enforcement (step 7) rejects new high-cardinality registrations.
  2. Replay drift between original and reconstructed decisions — root cause: reintroduced nondeterminism (e.g. unordered-map iteration, §13.6 Pitfall 4); recovery: audit every scoring path, re-apply deterministic ordering.
  3. Telemetry overhead on the hot path — root cause: synchronous span export during scoring; recovery: asynchronous, batched export (P5).
  4. Sampling bias hiding rare failures — root cause: pure head-based sampling drops low-frequency error traces; recovery: dual head/tail sampling (step 6).

⬜ Phase 8 — Fairness, Preemption & Speculative Execution §20

Objectives
  • Finalize the preemption pipeline coordinated between placement-engine (§15.2 step 10) and scheduler-core/src/preemption.rs, enforcing I1/I7 on every preemption.
  • Complete cross-tenant fairness enforcement (I10) under sustained contention, including starvation detection.
  • Implement cooperative, cache-aware preemption minimizing KV-cache invalidation cost.
  • Finalize speculative-execution placement coordination for dry-run candidates evaluated ahead of commit.
Deliverable

A finalized preemption and fairness pipeline enforcing bounded starvation, cache-aware cost minimization, and speculative-placement coordination, fully replay-instrumented.

Acceptance
  • Fairness deviation stays under 5% (I10, §14.4) across a 72-hour multi-tenant soak (§26).
  • Zero priority-inversion preemptions across 10,000 simulated contention scenarios.
  • Zero I1/I7 violations across 1,000 concurrent speculative-placement-then-preempt sequences.
  • Starvation escalation resolves within 2 fairness windows on fixtures/fairness/starvation_escalation _case.json.
Fixtures
  • fixtures/fairness/starvation_escalation_case.json — one tenant below threshold for 3 consecutive windows; expects forced-preemption escalation, not indefinite re-weighting alone.
  • fixtures/preemption/preemption_fencing_race.json — speculative placement and fencing interleaved; expects the reclaimed GPU set never double-offers.
  • fixtures/preemption/priority_inversion_case.json — a low-priority request attempts to preempt a higher-priority lease; expects rejection at the ordering boundary (step 9).
Pitfalls
  1. Preemption storms from one starvation escalation — root cause: no per-window cap; recovery: preemption-storm damping (step 12).
  2. Speculative/preemption race producing a transient double-allocation — root cause: a candidate is offered before release is verified; recovery: fencing (step 7) plus outcome verification (step 17).
  3. Cache-affinity cost blindness — root cause: candidate selection ignores invalidation cost; recovery: weight selection by cache-affinity loss (step 8), not priority alone.
  4. Grace-period abuse — a preempted runtime never confirms release; recovery: forced termination after grace-period expiry, escalated to node quarantine if repeated (§16.2 step 10).

⬜ Phase 9 — Release Engineering, Conformance Gating & Operator Tooling §21

Objectives
  • Finalize operator-cli (§1 Phase 0 deliverable 15) covering lease inspection, replay extraction, and drain control against a production cluster.
  • Implement the release pipeline: reproducible builds, SBOM/provenance, signing, canary rollout, and conformance gating before a build reaches a GPU cluster.
  • Close remaining PhaseDeferred gaps due for un-deferral per §35's trigger conditions.
  • Establish the rollback contract every prior phase's compatibility notes assumed.
Deliverable

A production release pipeline — reproducible, signed, provenance-attested builds promoted through dev/canary/stable behind a hard conformance gate — plus a finalized operator-cli covering every operator-facing surface introduced across Phases 0–8.

Acceptance
  • 100% conformance-suite pass rate required before any promotion; zero exceptions.
  • Canary rollout automatically reverts within 5 minutes of a release-health-score breach.
  • Two independent hosts produce byte-identical signed artifacts and SBOM digests for one commit, extending the Phase 0 reproducibility criterion (§12.4) to the full pipeline.
  • operator-cli's explainability view renders a complete causality chain for any decision_id inside the 30-day window (§4) in under 5 seconds.
Fixtures
  • fixtures/release/canary_rollback_case.json — a canary regressing p99 latency past the health threshold; expects automatic rollback within 5 minutes.
  • fixtures/release/reproducibility_check.json — two build hosts; expects identical Cargo.lock hash, SBOM digest, and cosign signature subject.
  • fixtures/operator/decision_explain_case.json — a decision_id spanning placement, preemption, and a scale decision; expects operator-cli to render the full causality chain.
Pitfalls
  1. Conformance-gate bypass under release pressure — root cause: a manual "just this once" promotion; recovery: the gate has no manual override path (ADR-12).
  2. Canary partition too small to detect a regression before full rollout; recovery: scale the canary shard count to the traffic volume needed for the target detection confidence.
  3. Signing-key compromise invalidating trust in prior releases; recovery: key rotation (step 15) plus re-signing within the retention window.
  4. Rollback loop from a flapping release-health score; recovery: apply the same hysteresis pattern used for autoscaling (§18.6 Pitfall 1) to promotion decisions.
