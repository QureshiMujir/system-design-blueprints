Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Centralized Monolithic Scheduler

+-----------------------------------------+
|         Single Scheduler Process         |
|  admission + queue + placement + lease   |
|  + metadata (in-process, no Raft)        |
+--------------------+---------------------+
                     | direct dispatch
          +----------v----------+
          |   Runtime Agent Mesh  |
          +-----------------------+

Regime where it wins: a single-region, single-tenant cluster under ~500 nodes where operational simplicity outweighs the availability cost of a single point of failure. The real system that embodies this: early single-controller Slurm deployments (slurmctld without HA failover configured, §5 Reference Implementations). Rejected here because §4's 99.95% availability target and 5,000-node ceiling both require surviving a single-node loss without an acknowledged-write-loss window (I2) — a monolith cannot satisfy this without becoming, in effect, a poorly-tested reimplementation of Raft.

Alt B — Single Larger Raft Quorum Instead of Tenant-Hash Sharding

+------------------------------------------+
|      One Raft Quorum, All Tenants          |
|      (no ADR-20 sharding)                  |
+------------------+--------------------------+
                   | linearizable reads/writes
        +----------v-----------+
        |  All Scheduler Shards |
        +-----------------------+

Regime where it wins: a cluster small enough (well under the §32 C4-derived 5,000-node ceiling) that quorum write-fan-out never becomes the bottleneck, and where cross-tenant global ordering has real value (e.g., strict global fairness auditing). The real system that embodies this: etcd deployed as a single cluster-wide store without application-level sharding (§5 Reference Implementations, etcd-io/etcd). Rejected here because §29's scalability analysis shows quorum fan-out is the first ceiling hit at scale — tenant-hash sharding (ADR-20) trades a small amount of cross-shard ordering guarantee for headroom against exactly this ceiling.

Alt C — Fully Decentralized Peer-to-Peer Placement (No Central Scheduler)

+--------+   gossip    +--------+   gossip    +--------+
| Node A |<----------->| Node B |<----------->| Node C |
+--------+             +--------+             +--------+
   ^ each node self-selects placements via local view

Regime where it wins: extremely large, latency-insensitive batch clusters where no single component needs a global view and eventual consistency in placement decisions is acceptable — closer to how some peer-to-peer distributed hash tables place data. No mainstream inference scheduler embodies this in production today; the closest real-world analogue is gossip-based service discovery layers (e.g., Serf/Consul's gossip protocol) used for membership, not placement. Rejected here because I1 (lease uniqueness) and I7 (GPU exclusivity) require a linearizable arbitration point under contention — a purely gossip-based system can only achieve this with a secondary consensus layer, which collapses back to Alt B's tradeoffs while adding gossip-convergence latency on top.

Alt D — Kubernetes-Native Scheduler Extension (No Standalone Control Plane)

+---------------------------------------------+
|              Kubernetes API Server            |
|   +-------------------------------------+     |
|   |  Custom Scheduler Extender/Plugin    |     |
|   +-------------------------------------+     |
+---------------------------------------------+

Regime where it wins: organizations fully committed to Kubernetes as the only orchestration surface, where reusing kube-scheduler's reconciliation loop and RBAC model outweighs the latency cost of API-server round trips on every scoring decision. The real system that embodies this: the Kubernetes Scheduling Framework's extender/plugin model (§5 Papers, SIG Scheduling design docs) as used by several GPU- scheduling extensions in the Kubernetes ecosystem. Rejected here as the sole architecture because the API-server round-trip cost is incompatible with the §4 p50 < 3ms budget — this blueprint instead treats Kubernetes as an optional deployment substrate (§4 deployment assumptions) rather than the scheduling authority itself.
