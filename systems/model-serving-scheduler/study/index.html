33. Hard Questions (Self-Examination)

  • Q1. Why does §4's p50/p99 gap (3ms vs. 20ms, a 6.7x ratio) not indicate a tail-latency bug, given §28's fan-out reasoning (§4, §28)?
  • Q2. If placement-engine's candidate sampling (§15.2 step 11) never scans the full inventory, how does §15's zero-double-allocation acceptance criterion (§15.4) hold under adversarial worst-case fragmentation, and what does §32's C4 assume that could break this (§15, §32)?
  • Q3. §18's autoscaling hysteresis (§18.2 step 6) and §15's runtime cooldowns (§15.2 step 14) are the same fix applied twice — why weren't they unified into one shared primitive, and what would unifying them cost the independent-failure property invariants rely on (§15, §18, §7)?
  • Q4. §20's preemption-outcome verification (§20.2 step 17) depends on a follow-up RuntimeDescriptor refresh — what happens to preemption correctness if that refresh itself reads a stale snapshot, the exact failure §15.6 Pitfall 1 already names (§15, §20)?
  • Q5. §9's ADR-04 locks Raft for "operational familiarity," but §29 shows quorum write fan-out is the first scaling ceiling hit — did the ADR under-weight the scaling cost of that choice relative to Omega- style optimistic concurrency (§9, §29, §34)?
  • Q6. §17's streaming aggregator lives inside the stateless scheduler-api tier, but §3's diagram draws it as a separate box after the model runtime — is the repository layout (§10) actually consistent with the architectural diagram, and if not, which one is wrong (§3, §10, §17)?
  • Q7. §14's admission-controller fast-path explicitly avoids scheduling work before acceptance — but §18's predictive autoscaling forecast reads queue_depth{tenant} (I3), a post-admission signal — does this create a subtle timing dependency where admission and autoscaling disagree on load during a burst (§14, §18)?
  • Q8. §32's C2 shows 250k req/s is a ~60x burst multiple over sustained average — does §4's queue- shard-level memory accounting (P8) actually bound worst-case memory at that burst multiple, or only at sustained average (§4, §32, §14)?
  • Q9. §19's replay-differential testing (§19.2 step 16) catches determinism regressions between binary versions — but what catches a determinism regression introduced within one version, before any second version exists to diff against (§19, §26)?
  • Q10. §22's T3 (falsified runtime telemetry) is mitigated by corroborating signals, but §16's degraded-node scoring penalty (§15.2 step 15) still trusts the runtime's self-reported health as one of those signals — is the corroboration actually independent, or partially circular (§22, §15, §16)?
  • Q11. §20's preemption-storm damping (§20.2 step 12) bounds concurrent preemptions per window — does this interact with §18's scale-up trigger (§18.2 step 7, which treats preemption rate as an undercapacity signal) to produce a delayed scale-up exactly when preemption pressure is capped rather than resolved (§20, §18)?
  • Q12. §25's 24-month WAL-compatibility window and §24's matching SBOM-retention window are both derived from the same number — if a future ADR shortens WAL compatibility, does §24's backup strategy silently become inconsistent unless someone remembers to check it (§24, §25)?
  • Q13. §31 compares this system favorably against Kubernetes on placement latency — but Kubernetes serves a broader workload diversity; does §4's constraint table implicitly assume a workload homogeneity Kubernetes does not get to assume, making the comparison less fair than it reads (§4, §31)?
  • Q14. §13's snapshot-transfer throttling (§13.2 step 15) bounds bandwidth to avoid starving live traffic — but §12.4's startup-recovery acceptance criterion (§12.4) requires a 120s bound on loading a 25,000-model snapshot — do these two constraints admit a feasible throttle setting simultaneously, or only under favorable network assumptions (§13, §12, §4)?
  • Q15. §30's MM5 claims hysteresis is a generic oscillation cure applied independently in §15, §18, and §20 — if a future engineer unifies them into one shared crate primitive, does every phase's Pitfalls section referencing its own hysteresis mechanism need updating, and would the harness (§16 of the standard) even catch a stale reference (§30, §15, §18, §20)?
  • Q16. §21's canary-partition rollout (§21.2 step 7) evaluates release health per-shard — but §20's fairness windows are also per-shard (ADR-20) — could a canary shard's fairness deviation be misattributed to the release candidate when it is actually ordinary cross-tenant contention (§21, §20)?
  • Q17. §35 registers four deferred features anchored to §13, §15, §16, and §17 — why were exactly these four phases chosen as anchors rather than, say, §20 (fairness) or §21 (release), given that some deferred features plausibly extend those phases too (§35, §20, §21)?
  • Q18. §28's M10 target (zero replay-throughput regression release-over-release) is enforced at Phase 9's gate (§21) — but §19's replay-performance snapshots (§19.2 step 20) run continuously — is the Phase 9 gate catching anything the continuous snapshot didn't already catch earlier, or is it a redundant second gate (§28, §19, §21)?
  • Q19. §7's debugging methodology asserts one invariant per simulator check "independently of the others" — but I1 (lease uniqueness) and I7 (GPU-set exclusivity) are checked by inspecting overlapping telemetry (lease_conflict_total, gpu_overlap_detected_total) — are these really independent detections, or could a single root cause trip both and make the "independent" claim misleading (§7, §11)?
  • Q20. §32's C10 shows exactly 1.0 FD per max-concurrent-stream with zero multiplexing slack — if gRPC multiplexing (ADR-19) is mandatory to avoid FD exhaustion at the stated ceiling, why does §4 list the FD budget as if it were an independent constraint rather than a derived consequence of the multiplexing decision (§32, §4, §9)?

30. Mental Models & First Principles

  • MM1 — Tail Latency Is a Fan-Out Property. The compressed insight: a scheduler's p99 is dominated by fan-out amplification (Dean & Barroso, 2013, §5), not by any single slow component · predicts that adding redundant candidate scoring paths can raise p99 even while lowering p50 · the bug class without it: chasing p50 wins that regress p99 · applies in §28.
  • MM2 — Backpressure Is Structural, Not Optional. The insight: every unbounded queue is a future OOM with a deferred timestamp (P2) · predicts that a system passing load tests will still fail under a sustained burst if any single queue lacks a ceiling · bug class without it: silent memory growth that looks fine until it isn't · applies in §14.
  • MM3 — Determinism Buys Debuggability, Not Correctness. The insight: replay (I8) proves what happened, it does not prove what should have happened (P1, P4) · predicts that a replay-clean incident can still be a policy bug, not a determinism bug · bug class without it: chasing a "replay bug" that is actually a scoring-weight misconfiguration · applies in §19.
  • MM4 — Fencing Tokens Convert Time Into a Total Order. The insight: a fencing token (I11) turns "who had the lease last" into a comparison, not a race · predicts that any lease-like resource without a monotonic token will eventually double-grant under partition · bug class without it: split-brain double execution (I1/I7) · applies in §13.
  • MM5 — Hysteresis Is the Generic Cure for Oscillation. The insight: any control loop comparing a noisy signal against a single threshold will oscillate near that threshold (§15.6 Pitfall 2, §18.6 Pitfall 1) · predicts that autoscaling, placement, and preemption will all independently need the same fix · bug class without it: three separately "discovered" flapping bugs that are one bug · applies in §15, §18, and §20.
  • MM6 — Priority Without Fairness Windows Is Not Isolation. The insight: a priority field alone does not prevent starvation (I10) — it only orders contention, it does not bound it (P7) · predicts that a purely priority-ordered queue eventually starves a low-priority-but-paying tenant under sustained high- priority load · bug class without it: an SLA violation with a technically-correct priority ordering · applies in §14 and §20.
  • MM7 — Cache Locality Is a Scoring Input, Not a Cache-Layer Concern. The insight: KV-cache affinity (Kwon et al., 2023, §5) belongs in the placement decision itself, not in a post-hoc cache-warming pass · predicts that bolting affinity on after placement produces the exact fragmentation §15 was built to avoid · bug class without it: GPU-utilization variance despite "correct" placement scores · applies in §15.
  • MM8 — Crash-Only Design Removes a Whole Recovery-Path Class. The insight: a component that assumes abrupt termination as normal (P3) never needs a separate "graceful shutdown correctness" code path · predicts that a system with two distinct shutdown paths (graceful and crash) will eventually diverge and the untested one will be wrong · bug class without it: a clean-shutdown-only bug that only appears during an actual outage · applies in §12.

5. Required Reading

Books

  • Designing Data-Intensive Applications — Martin Kleppmann (2017), ch. 5–9: replication, consistency models, stream processing, coordination; applied in §13 and §17.
  • Systems Performance: Enterprise and the Cloud — Brendan Gregg (2020), ch. CPU/memory/networking: production bottleneck analysis methodology; applied in §28.
  • Database Internals — Alex Petrov (2019), ch. on WAL and storage engines: deterministic persistence and compaction design; applied in §13.
  • Distributed Systems — Maarten van Steen & Andrew Tanenbaum (3rd ed.), ch. on replication and coordination: quorum reasoning applied directly to metadata-store; applied in §13.
  • Linux Kernel Development — Robert Love (3rd ed.), scheduler and memory-management chapters: informs NUMA-aware placement heuristics; applied in §15.
  • Kubernetes in Action — Marko Lukša (2nd ed.), scheduling and reconciliation sections: the reconciliation-loop pattern reused by the autoscaler; applied in §18.
  • GPU Systems Architecture — memory hierarchy and topology chapters (course-level reference, NVIDIA architecture whitepapers): drives GPU-fit scoring and fragmentation estimation; applied in §15.
  • Site Reliability Engineering — Google SRE Book (Beyer, Jones, Petoff, Murphy, 2016), alerting and operational-readiness chapters: SLO and error-budget methodology; applied in §24.

Papers

  • "Large-scale cluster management at Google with Borg" — Verma et al., 2015, EuroSys: allocs, priority/preemption, and quota design → directly informs scheduler-core's preemption pipeline; applied in §15 and §20.
  • "Omega: flexible, scalable schedulers for large compute clusters" — Schwarzkopf et al., 2013, EuroSys: optimistic concurrency for parallel scheduling decisions → informs the CAS-based lease model; applied in §13.
  • "Sparrow: distributed, low latency scheduling" — Ousterhout et al., 2013, SOSP: batch sampling for sub-millisecond scheduling decisions → informs placement-engine's candidate-sampling fast path; applied in §15.
  • "Quincy: fair scheduling for distributed computing clusters" — Isard et al., 2009, SOSP: min-cost flow fairness formulation → informs the fairness-window scoring model; applied in §14 and §20.
  • "Ray: A Distributed Framework for Emerging AI Applications" — Moritz et al., 2018, OSDI: actor scheduling and dynamic task graphs → informs speculative-execution coordination; applied in §20.
  • "Scheduling Framework" — Kubernetes SIG Scheduling design docs: plugin-pipeline extension points → informs placement-engine's scoring-pipeline structure; applied in §15.
  • "Efficient Memory Management for Large Language Model Serving with PagedAttention" — Kwon et al., 2023, SOSP (vLLM): paged KV-cache allocation → informs KV-cache affinity scoring; applied in §15.
  • "Orca: A Distributed Serving System for Transformer-Based Generative Models" — Yu et al., 2022, OSDI: iteration-level scheduling and selective batching → informs batch-assembly window design; applied in §14.
  • "The Tail at Scale" — Dean & Barroso, 2013, CACM: tail-latency amplification in fan-out systems → informs the p50/p99 latency separation in §4; applied in §28.
  • "Dapper, a Large-Scale Distributed Systems Tracing Infrastructure" — Sigelman et al., 2010, Google technical report: trace-sampling and span-propagation design → informs tracing-pipeline; applied in §19.

Glossary (§36) · 47 terms · site-wide glossary

Admission Shedding
intentional rejection of incoming work under overload, before scheduling work is spent (P8).
Anti-Affinity
a placement constraint preventing co-location of conflicting tenants or workloads.
Backpressure
bounded-capacity signaling that propagates upstream pressure instead of buffering unboundedly (P2).
Batch-Assembly Window
the 1–15ms configurable interval during which same-SLA-class requests are grouped for execution (§4).
Cache Affinity
scoring preference for a runtime holding a reusable KV-cache prefix for a request.
Canary Partition
a subset of scheduler-core shards running a release candidate ahead of full promotion (§21).
CAS (Compare-And-Swap)
an atomic conditional update used for lease acquisition and quota decrement.
Cluster-Pressure Score
an aggregate autoscaling input combining queue depth, GPU utilization, and fragmentation (§18).
Cooldown Period
a bounded window after a scaling or placement decision during which the same decision cannot repeat, bounding oscillation.
Crash-Only Component
a process designed to treat abrupt termination as a normal event, not an exception (P3).
Deterministic Simulator
the CI harness asserting I1–I12 independently after every simulated tick (§7).
Drain State
a runtime health state accepting no new work while finishing active work.
Fairness Window
a bounded interval over which per-tenant resource share is measured against a configured target (I10).
Fencing Token
a monotonically comparable token preventing a superseded lease holder from being honored (I11).
Fragmentation Estimator
a scoring component measuring GPU-memory fragmentation across candidate nodes.
Head-of-Line Blocking
a slow stream or request stalling siblings sharing the same transport channel.
Health State
one of Healthy, Degraded, Quarantined, Draining, Offline for a runtime.
Heartbeat Jitter
randomized send-offset control preventing synchronized heartbeat storms.
Hysteresis
an asymmetric threshold gap preventing oscillation in a control loop (MM5).
Incident Bundle
an exported forensic artifact combining a WAL segment, trace IDs, and metric snapshots.
KV-Cache Pressure
a runtime-reported signal of cache occupancy feeding affinity and health scoring.
Lease
a temporary, fenced ownership contract over a runtime GPU slot (I1, I11).
Linearizable Read
a read guaranteed to observe every write committed before it began (I12).
Node Quarantine
automatic isolation of a runtime after a consecutive-failure threshold, short of eviction.
Orphan Lease
a lease whose owning request no longer exists, reclaimed by TTL scan (I5).
Placement Decision
the WAL row committing a scheduling outcome, replay-reconstructable (I8).
Placement Epoch
the monotonic generation counter backing forward-only scheduler progress (I6).
Preemption
forced reclamation of an active lease to serve a higher-priority request (§20).
Priority Class
a tenant- or request-level tag determining scheduling and preemption ordering.
Provenance Attestation
a signed record of how and where a release artifact was built (§21).
Quorum
the majority subset of metadata-store replicas required to commit a write (ADR-04).
Read-Index Protocol
the Raft mechanism enabling linearizable reads without a full log append.
Release Health Score
an aggregate canary-promotion signal combining error rate, latency, and replay-differential results (§21).
Replay Determinism
the guarantee that replaying a WAL segment reproduces identical decisions (I8).
Runtime Descriptor
a node-local snapshot of GPU inventory, health, and queue pressure (§11).
Scheduler Epoch
see Placement Epoch.
Score Breakdown
per-component explainability metadata attached to a placement decision.
Sparrow Sampling
batch-sampling a candidate subset instead of the full inventory for sub-millisecond scoring decisions (§5).
Speculative Placement
a dry-run scoring evaluation not yet committed to a lease.
Starvation Escalation
a forced-preemption trigger following sustained fairness-window breach.
Stream Offset
the monotonic per-stream token sequence counter enforcing I4.
Tail Latency
the worst-case latency percentile (typically p99) of a distribution.
Tenant-Hash Sharding
partitioning scheduler shards by a stable hash of tenant identity (ADR-20).
Token Bucket
a rate-limiting primitive bounding admission or backpressure throughput.
Warm Pool
pre-registered, not-yet-leased runtime capacity reducing cold-start latency (§18).
Watchdog
a runtime-local self-health check independent of the scheduler's external view (§16).
Write Fencing
CAS-based lease acquisition preventing double-allocation (§13, I1).
