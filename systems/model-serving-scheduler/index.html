In one paragraph

A model serving scheduler is the control plane that decides which GPU runs each inference request (§1). It sits between stateless gateways and the node-local runtimes that execute the model, and it owns admission, queueing, placement, batching, preemption and autoscaling coordination, but it never runs a tensor kernel (§1). It exists because inference platforms fail from placement instability, queue collapse, GPU fragmentation and runaway tail latency more than from tensor-math bugs (§2). The design is a Rust system of fifteen crates and services whose authoritative state lives in a Raft-replicated store (§1, ADR-01, ADR-04). Platform engineers, GPU cluster operators and SRE teams run it (§1).

The problem, concretely

The simplest design is one scheduler process that holds admission, queues, placement, leases and metadata in memory (§34 Alt A). The blueprint names how that breaks as load and cluster size grow:

  • Two requests think they own the same GPU slot. The result is double allocation, and sharing a GPU set across tenants corrupts tensor memory (P6, I1, I7).
  • A queue with no ceiling. Every unbounded queue is a future out-of-memory kill with a deferred timestamp (MM2, P2). The blueprint's own arithmetic: sustained load averages 4,167 req/s, but the system is provisioned to take bursts of 250k req/s, about 60 times that (§32 C2).
  • Priority with no fairness. A queue ordered only by priority starves a low-priority but paying tenant under sustained high-priority load, and a bulk batch job can starve an interactive tenant (MM6, P7).
  • Silence treated as death. If a missing heartbeat alone evicts a node, a network blip reassigns work that is still running, and the result is double execution (§16.9).
  • One process, one failure. A monolith cannot survive losing its node without a window where an acknowledged write is lost (§34 Alt A, I2), against a 99.95% availability target that leaves 21.6 minutes of error budget a month (§4, §32 C7).
  • Decisions nobody can reproduce. Nondeterministic scheduling gives latency spikes no one can replay or debug (P1).

How it works, end to end

Follow one request through §3's diagram. Most boxes are crates or services from §1; the model runtime, KV cache layer and streaming aggregator are not on §1's list (§1, §3).

 Client -> scheduler-api -> admission-controller -> queue-manager -> scheduler-core
            (TLS, auth)     (quota/SLA/legality)    (fair queues)      (placement + lease)
 scheduler-core <-> placement-engine (scoring, pure function of snapshots)
 scheduler-core -> metadata-store (Raft quorum) + placement WAL -> replay-framework
 scheduler-core -> runtime-agent mesh (lease proposal / accept) -> model runtime (vLLM, TensorRT-LLM)
 model runtime -> streaming aggregator (ordering, cancellation) -> Client
 side channel: tracing-pipeline, metrics-exporter (never block scheduling)
  1. Gateway. scheduler-api terminates TLS at trust boundary A, authenticates the tenant, rate-limits, and normalizes the call into a SchedulerRequest (§3). §11 instead says that request is constructed once at admission-controller and never mutated afterwards (§11). It makes no placement decision (§3).
  2. Admission. admission-controller checks quota (quota-engine), SLA eligibility, token ceilings and payload legality before any scheduling work is spent. A failure is REJECTED (§3, §8).
  3. Queue. queue-manager holds the priority and fairness queues and the 1–15 ms batch-assembly window, and enforces I3 (§3, §4).
  4. Decision. scheduler-core asks placement-engine for a score and is the only writer of PlacementDecision rows into the WAL (§3, §11). State sits in metadata-store behind a Raft quorum (§3, ADR-04).
  5. Lease and dispatch. scheduler-core proposes a lease to the node's runtime-agent, which is partially trusted (trust boundary B), then dispatches to the model runtime (§3, §8). Heartbeats come in through node-heartbeat-service (§1, §16).
  6. Streaming. Tokens return through the streaming aggregator, which enforces I4 and applies cancellation (§3). The diagram draws it as its own box, but §17.2 step 1 puts it inside the stateless gateway tier, as scheduler-api/src/streaming.rs (§3, §17.2 step 1, §33 item 6).
  7. Replay and telemetry. replay-framework rebuilds decisions from the WAL, and the telemetry stack is decoupled so an outage degrades observability, never correctness (§3, P5).

The request moves through ten states (§8). RECEIVED goes to QUEUED or REJECTED. QUEUED goes to SCHEDULED or CANCELLED. SCHEDULED goes to RUNNING or FAILED. RUNNING goes to STREAMING, FAILED or COMPLETED, and STREAMING to COMPLETED or FAILED. FAILED goes to RETRY_PENDING, which goes back to QUEUED or to CANCELLED. COMPLETED, CANCELLED and REJECTED have no next state; §8 also calls FAILED "terminal failure" while listing RETRY_PENDING as its next state (§8). Any other transition is rejected and counted in invalid_state_transition_total. §8 calls this "I6's enforcement point", although I6 is the epoch-monotonicity invariant (§8, §7).

Stateless services are scheduler-api and admission-controller. The stateful part is the scheduler-core plus metadata-store quorum, and one runtime-agent runs per GPU host (§1).

The core ideas

Leases and fencing tokens: one owner per GPU slot (§13, I1, I11, MM4)

A lease is a temporary ownership contract over a runtime's GPU slot (§36). It is a row RuntimeLease { runtime_id, fencing_token, expiry } in the Raft-replicated metadata-store (§13.2 step 5), although ADR-09 names embedded RocksDB as the queue and lease persistence store (ADR-09). It is taken by compare-and-swap (CAS): the update applies only if the row is still what the caller last saw, so two schedulers cannot both win (§13.2 step 8, I1). The fencing token is a monotonic value the runtime checks on every dispatch, so a superseded token is refused (I11, P6, §16.2 step 8). Fencing turns "who held it last" into a comparison, not a race (MM4).

  1. scheduler-core proposes a lease and runtime-agent accepts; only then does dispatch go out (§8).
  2. If preemption reclaims the slot, the old token is revoked before the freed GPU set is offered to anyone else (§20.2 step 7).
  3. If the old holder still sends work, the runtime rejects it and counts stale_lease_rejected_total (I11).

The same idea guards the leader: after a partition heals, any RPC bearing a lower term is rejected (§13.6 pitfall 2, T6). The epoch counter (I6) never decreases (§13.2 step 10). A lease whose owning request is gone is an orphan lease, reclaimed by a TTL scan (I5, §16.2 step 17).

Placement: score a sample, not the whole fleet (§15, MM7)

Placement is a pure function of read-only RuntimeDescriptor snapshots with no side effects, which is what makes it replayable (§3). The snapshots are read without locks (§15.2 step 1). The pipeline in placement-engine/src/scoring.rs follows the Kubernetes Scheduling Framework's plugin shape (§15.2 step 3). Its terms are GPU-memory accounting that feeds fragmentation estimates (steps 2 and 11), NUMA topology (steps 4–5), KV-cache affinity (step 6), anti-affinity (step 7), a fairness cross-check (step 13) and a penalty for unhealthy runtimes (step 15). KV-cache affinity means preferring a runtime that already holds a reusable prompt prefix. It goes into the score itself, not into a cache-warming pass afterwards (MM7). To stay inside the p50 budget the engine scores at most 200 sampled candidates instead of up to 5,000 nodes (Sparrow sampling, §15.2 step 11, §32 C1):

Stage of the p50 budget Time
queue-manager dequeue 0.3 ms
scoring over at most 200 sampled candidates 1.5 ms
WAL append fsync, amortized 1 ms
Total 2.8 ms, inside the 3 ms ceiling (§32 C1, §4)

Two guards matter. A snapshot can be stale, so GPU fit is re-validated when the runtime accepts the lease, not only when scoring (§15.6 pitfall 1). Affinity can dominate and unbalance the fleet, so its weight is capped against the fragmentation and topology terms (§15.6 pitfall 3).

Queues, admission and fairness windows (§14, I3, I10, MM6)

Admission runs three cheap checks (quota, SLA eligibility, payload legality), each a single CAS or lookup (§14.2 step 13). Admitted work lands in one QueueShard per tenant-hash partition, owned by a single-threaded task (§14.2 step 1, §11). Each shard has a depth ceiling (I3) and a fairness window, the interval over which a tenant's share is measured against its target (I10, §36). Priority orders contention but does not bound it, so priority alone is not isolation (MM6). A deviation over 5% of the window share triggers re-weighting before forced preemption (§14.4, §20.2 step 14). When a shard nears its memory ceiling it sheds, rejecting new work before out-of-memory (admission shedding, P8, §14.2 step 15). The conformance fixture tenant_starvation_case.json has one tenant saturate a shard and expects re-weighting within one fairness window (§14.5).

Heartbeats and quarantine before eviction (§16, I5, P10)

Every runtime-agent sends a heartbeat each second, at a randomized offset so nodes do not all fire on the same tick (§4, §16.2 step 11). A runtime's health moves forward through Healthy -> Degraded -> Quarantined -> Draining -> Offline, with explicit compensating moves back (§16.2 step 5, P10). Silence is not proof of death: "no heartbeat received" may be the network, while "confirmed dead" needs watchdog silence plus process exit (§16.9).

  1. A malformed heartbeat is rejected and the runtime is marked degraded, not evicted (§8).
  2. After a configurable run of consecutive rejections, the runtime is quarantined (§16.2 step 10).
  3. A node past its heartbeat TTL becomes unschedulable and its leases are revoked (I5).

The conformance fixture with five consecutive missed heartbeats expects quarantine, not eviction (§16.5).

Cooldown and hysteresis: stopping control loops from flapping (§15, §18, §20, MM5)

A control loop that compares a noisy signal to one threshold oscillates near it (MM5). Hysteresis is an asymmetric threshold gap that prevents oscillation (§36). A cooldown is a window after a decision during which it cannot repeat (§36). The blueprint applies the same fix in three places. In placement, a recently preempted runtime is deprioritized for a bounded window and a score margin is required before migrating, so a workload stops bouncing between two near-equal runtimes (§15.2 step 14, §15.6 pitfall 2, FM-6). In autoscaling, scale-up and scale-down thresholds differ and a cooldown follows each decision (§18.2 steps 4 and 6, FM-8). In preemption, a per-window cap damps cascades (§20.2 step 12, FM-9). A "flap" is defined as more than one direction reversal within one cooldown window, and the fixture must show zero across 1,000 replays (§18.4).

Deterministic replay: reconstruct a decision from its inputs (§19, I8, P1, P4)

Every placement emits a PlacementDecision row, append-only and durable before the acknowledgement, and it carries a ScoreBreakdown (§11, I2, P4). Because placement is a pure function of snapshots (§3), replay-framework can re-run a WAL segment in a sandbox and compare its checksum with the commit-time checksum, failing loudly on divergence (§19.2 steps 2, 9 and 12, I8). A second check replays one segment under two binary versions to catch a determinism break before release (§19.2 step 16). One real cause is iterating a HashMap while serializing a snapshot, fixed by an ordered encoder (§13.6 pitfall 4). Replay proves what happened, not what should have happened, so a replay-clean incident can still be a policy bug (MM3).

The trade-offs — where engineers disagree

Language: Rust for the control plane (ADR-01)

Chosen: Rust, because the ownership model enforces I1 and I11 at compile time and there is no garbage-collector pause inside the p50 budget (§9, §1). Rejected: Go and C++ (§9). §1 adds that Go's GC pauses interact badly with the sub-3 ms p50 and that C++ has no ownership model to enforce I1. When the rejected choice is right: Go wins for a control plane with a latency budget above 50 ms and a small team unwilling to learn borrow-checking (§9).

Metadata replication: Raft over Paxos (ADR-04)

Chosen: Raft, for operational familiarity and a single reference implementation (etcd) to study (§9). Rejected: multi-Paxos (§9). When the rejected choice is right: when leaderless writes under network partition matter more than operational simplicity (§9). The blueprint itself asks whether this under-weighted a cost, since quorum write fan-out is the first scaling ceiling (§33 item 5, §29).

Sharding: tenant-hash partitioning (ADR-20)

Chosen: hash the tenant to a shard, so a tenant's requests keep landing together and keep KV-cache locality (§9). It also ties into the scale-out path past the node ceiling (§29). Rejected: random partitioning (§9). When the rejected choice is right: when tenant volume is so skewed that hash sharding creates hot shards (§9). §29 names queue-shard imbalance as a bottleneck and T10 a hash-collision risk.

Backpressure: bounded channels plus a token bucket (ADR-24)

Chosen: bounded channels and token-bucket admission, because P2 requires every queue, stream and transport to be bounded (§9). The price is that a legitimate burst is rejected, not absorbed (P2). Rejected: unbounded mpsc channels (§9). When the rejected choice is right: a fixed, small, trusted internal fan-out that no outside actor can overload (§9).

Log format: binary append-only WAL (ADR-08)

Chosen: a binary append-only WAL for throughput, avoiding SQLite's page-cache and B-tree overhead (§9), against a WAL amplification target under 1.8x (§4). Rejected: SQLite WAL (§9). When the rejected choice is right: when ad hoc SQL queries over the log outweigh raw append throughput (§9).

Runtime dispatch: gRPC bidirectional streams (ADR-19)

Chosen: long-lived bidirectional streams, because polling adds tens of milliseconds the p99 budget cannot absorb (§9). Heartbeats ride the same transport (§16.2 step 2). Rejected: HTTP long-poll (§9). When the rejected choice is right: when runtime agents sit behind a proxy that cannot terminate long-lived streams (§9). §3 also credits ADR-19 with keeping scheduling logic out of scheduler-api, but the ADR-19 row is about dispatch (§3, §9).

Roads not taken (§34, §35)

Centralized monolith (§34 Alt A) wins for a single-region, single-tenant cluster under about 500 nodes where simplicity outweighs a single point of failure; early slurmctld without HA is the example. It loses here because 99.95% availability needs surviving a node loss without losing an acknowledged write (I2, §4).

One bigger Raft quorum, no sharding (§34 Alt B) wins on a cluster well under the 5,000-node ceiling where cross-tenant global ordering has value, as with a single etcd cluster. It loses because quorum fan-out is the first ceiling reached (§29, ADR-20).

Peer-to-peer gossip placement (§34 Alt C) wins for huge, latency-insensitive batch clusters that tolerate eventual consistency. It loses because I1 and I7 need a linearizable arbiter, and adding one collapses back to Alt B plus gossip latency.

A Kubernetes scheduler extension as the whole system (§34 Alt D) wins for organizations committed to Kubernetes as the only orchestration surface, where reusing its scheduler and RBAC beats API-server round trips. It loses because that round trip breaks the 3 ms p50 budget (§4), so Kubernetes is only an optional substrate here.

Deferred features (§35) each wait for a trigger: cross-region active-active inference, when inter-region RTT falls below 20 ms; ML-driven placement, once the replay corpus holds at least 90 days of labeled outcomes; MIG-style GPU partitioning, when a GPU generation ships a stable driver API; and RDMA-native routing, when the fabric standardizes on RDMA NICs (§35).

What must never be false

  • I1: only one scheduler lease owns a runtime slot. Noticed by duplicate lease IDs and runtime conflict telemetry; lease_conflict_total.
  • I2: mutations are durable before they are acknowledged. Noticed by sequence gaps and replay checksum mismatch; wal_append_latency_ms.
  • I3: queues never exceed their configured limits. Noticed by a depth threshold breach; queue_depth{tenant}.
  • I4: streamed token offsets only increase. Noticed by the aggregator's offset check; stream_offset_regression_total.
  • I5: a node with no heartbeat inside the TTL is unschedulable. Noticed by the TTL scanner; heartbeat_age_seconds.
  • I6: the scheduler epoch never decreases. Noticed by a regression check on write; epoch_regression_total.
  • I7: a GPU set belongs to at most one placement. Noticed by overlapping gpu_set on active leases; gpu_overlap_detected_total.
  • I8: replaying a WAL segment gives identical decisions. Noticed by replay checksum comparison; replay_divergence_total.
  • I9: a tenant's token budget never goes negative. Noticed by a negative-balance write attempt; quota_underflow_total.
  • I10: no tenant exceeds its window share. Noticed by deviation above 5% (§14.4); fairness_deviation_ratio.
  • I11: a superseded lease token is never honored. Noticed when a runtime is shown a fenced lease; stale_lease_rejected_total.
  • I12: a linearizable read never sees a write before quorum commit. Noticed by the stale-read detector in conformance-suite; linearizable_read_violation_total.

A deterministic simulator asserts all twelve independently after every simulated tick, so a failure names the broken invariant directly (§7, §26).

What breaks in production

FM-1, leader loss. Placement stalls cluster-wide and raft_replication_lag_ms spikes. Causes are a leader crash, a partition or host exhaustion. Followers detect it by heartbeat timeout and elect a new leader automatically. If the quorum is lost, restore from the last verified snapshot (§23, §13.2 step 1).

FM-2, runtime node crash. Leases are orphaned and queue depth rises. Causes are hardware faults, OOM kills or crashes. Missed heartbeats past the 5 s budget detect it, orphan-lease reclamation (I5) and placement retry recover automatically, and the affected PlacementDecision sequence can be replayed (§23, §4).

FM-3, WAL corruption. Replay checksums mismatch and the snapshot load fails. Causes are disk faults, a partial write during a crash or bit rot. A CRC32C mismatch on read detects it, a healthy replica replays automatically, and the manual path is a snapshot restore (§23, T7).

FM-4, queue saturation. The admission-reject rate climbs and depth pins at the shard ceiling. The cause is a sustained burst beyond capacity or a quota leak. Queue-depth alarms (I3) detect it, admission shedding is the automatic response, and operators adjust quotas or add capacity (§23, P8).

FM-5, replay divergence. A replayed decision differs from the original. The cause is reintroduced nondeterminism. The replay-checksum mismatch (I8) detects it, and the divergent segment is isolated from further replay while engineers diff the scoring path (§23).

FM-6, placement oscillation. migration_rate rises with no capacity change. The cause is insufficient hysteresis margin or misconfigured scoring weights. Migration-rate telemetry detects it, runtime cooldowns contain it, and the fix is a retune plus replaying the sequence to diff score breakdowns (§23, §15.9).

FM-9, preemption storm. preemption_total spikes from one triggering tenant. The cause is no per-window preemption cap, or a starvation-escalation cascade. Damping contains it, and operators relax the cap and review quotas (§23, §20.2 step 12).

FM-11, cross-tenant starvation. One tenant's p99 wait persistently exceeds the fairness window. Causes are priority inversion or affinity stickiness monopolizing GPUs. A sustained fairness_deviation_ratio breach detects it, forced-preemption escalation responds, and operators review that tenant's quota and priority class (§23, §20.2 step 5).

Threats worth knowing (§22):

  • T3, a runtime lying about its GPU inventory or health to win placement, is met by cross-checking against watchdog and heartbeat before trusting a self-report; the response is degraded, then quarantine (heartbeat_rejected_total).
  • T6, a stale leader accepting writes after a partition heals, is met by rejecting any RPC with a lower term (stale_write_rejected_total).
  • T10, one tenant starving another through shared-shard placement, is met by tenant-hash sharding and the fairness window (fairness_deviation_ratio).
  • T11, a fully compromised runtime dispatching unauthorized work, is met by lease fencing, which limits dispatch to a runtime holding a current token (stale_lease_rejected_total).
  • T1, an oversized request exhausting queue memory, is rejected at admission before queue-manager sees it (admission_reject_total{reason}).

Places where the blueprint disagrees with itself, stated unresolved:

  • How many numbers. §4 says "These 27 numbers are load-bearing", but its table has 30 rows (§4).
  • What 250k req/s is. §4's rationale column derives it from 50M tok/min divided by about 200 tokens per request. §32 C2 computes 250,000 req/min, that is 4,167 req/s sustained, and treats 250k req/s as the provisioned burst ceiling (§4, §32 C2).
  • Failure detection. §4 budgets under 5 s, derived from 5 missed heartbeats at a 1 s interval. §16.4's criterion starts the 5 s clock at the fifth missed heartbeat (§4, §16.4).
  • "Verbatim" targets. §28 says every M-row's target is the §4 constraint verbatim, but M9 (cancellation under 100 ms), M10, M11 (CI under 15 min) and M12 (rollback under 5 min) match no §4 row, and §12.4 calls the CI budget "§4-adjacent" (§28, §4, §12.4).
  • The error budget. §4 and §32 C7 both state 21.6 minutes, but C7's own formula, 0.05% x 30.44 x 24 x 60, does not evaluate to 21.6 (§4, §32 C7).

How it compares

  • Borg / Kubernetes chose a general reconciliation loop with a seconds-scale scheduling target. It fits mixed batch, service and stateful workloads where sub-10 ms placement is not the goal, and this design borrows its plugin pipeline but not its O(n) scoring fallback (§31).
  • Ray Serve chose Python actor scheduling with an eventually consistent control store. That is right for research and rapid iteration where control-plane latency is not the bottleneck (§31).
  • Slurm chose batch-oriented fairshare with a decay curve and a non-replicated slurmctld by default. That is right for HPC jobs that run for hours, where queueing overhead is negligible (§31).
  • NVIDIA Triton Inference Server chose per-node serving with no cluster-wide placement. That is right when an orchestration layer, here the scheduler, owns placement and Triton owns execution (§31).

Questions to test yourself

  1. Why does §4's p50/p99 gap (3ms vs. 20ms, a 6.7x ratio) not indicate a tail-latency bug, given §28's fan-out reasoning (§4, §28)? — Hint: start from the p99 derivation in §4, then MM1.
  2. If placement-engine's candidate sampling (§15.2 step 11) never scans the full inventory, how does §15's zero-double-allocation acceptance criterion (§15.4) hold under adversarial worst-case fragmentation, and what does §32's C4 assume that could break this (§15, §32)? — Hint: §15.6 pitfall 1's recovery, then §32 C4.
  3. §32's C2 shows 250k req/s is a ~60x burst multiple over sustained average — does §4's queue- shard-level memory accounting (P8) actually bound worst-case memory at that burst multiple, or only at sustained average (§4, §32, §14)? — Hint: §14.2 step 20 and P8.
  4. §19's replay-differential testing (§19.2 step 16) catches determinism regressions between binary versions — but what catches a determinism regression introduced within one version, before any second version exists to diff against (§19, §26)? — Hint: §26's deterministic-simulator paragraph and I8.
  5. §22's T3 (falsified runtime telemetry) is mitigated by corroborating signals, but §16's degraded-node scoring penalty (§15.2 step 15) still trusts the runtime's self-reported health as one of those signals — is the corroboration actually independent, or partially circular (§22, §15, §16)? — Hint: T3's mitigation column and §16.2 step 7.

If you only remember three things

Exactly one owner holds each GPU slot, proven by a fencing token the runtime checks on every dispatch (I1, I11, MM4). Every queue, stream and wait is bounded, and a silent node is quarantined before it is evicted (P2, I3, §16.9). Scheduling is a pure function written to a durable log before it is acknowledged, so any decision can be replayed and explained (P1, P4, I2, I8).

Words used here

  • Lease: a temporary, fenced ownership contract over a runtime's GPU slot (§36, I1).
  • Fencing token: a comparable number that stops a superseded lease holder from being honored (§36, I11).
  • CAS (compare-and-swap): an atomic conditional update, used for leases and quota decrements (§36).
  • Quorum: the majority of metadata-store replicas needed to commit a write (§36, ADR-04).
  • Orphan lease: a lease whose request no longer exists, reclaimed by a TTL scan (§36, I5).
  • Cache affinity: scoring preference for a runtime holding a reusable KV-cache prefix (§36).
  • Sparrow sampling: scoring a sampled subset of candidates instead of the whole inventory (§36).
  • Fairness window: the interval over which a tenant's share is measured against its target (§36, I10).
  • Admission shedding: deliberately rejecting work under overload before scheduling effort is spent (§36, P8).
  • Backpressure: bounded capacity that pushes pressure upstream instead of buffering forever (§36, P2).
  • Hysteresis: an asymmetric threshold gap that prevents oscillation in a control loop (§36, MM5).
  • Cooldown period: a window after a decision during which it cannot repeat (§36).
  • Node quarantine: isolating a runtime after consecutive failures, short of eviction (§36, §16.2 step 10).
  • Replay determinism: replaying a WAL segment reproduces identical decisions (§36, I8).
