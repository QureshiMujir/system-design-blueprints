⬜ Phase 0 — Repository Skeleton & Correctness Kernel Scaffolding §12

Objectives

Stand up the Cargo workspace, CI matrix, and the minimal nf-core types so every later phase has a compiling target. Establish the correctness kernel: Packet, FiveTuple, Verdict, and the nf-verifier invariant harness (I1–I14 stubs), per P13 (telemetry- first) and P9 (bounded/O(1) access). No packet-processing logic yet — this phase is plumbing plus the type system.

Deliverable

Workspace builds clean on both CI architectures; nf-verifier reports "14/14 invariants vacuously satisfied"; docs/adr/ holds 28 files matching §9.

Acceptance

cargo build --all-targets --all-features exits 0 on x86_64 and aarch64. Cold build time < 120 s (M14, §32). nf-verifier --dry-run reports exactly 14 invariant stubs, 0 failures. Fixture conformance/fixtures/phase0_empty_ruleset.json round-trips through nf-control load/dump byte-identically.

Fixtures
Fixture Purpose Expected Output
phase0_empty_ruleset.json empty ruleset load/dump round-trip byte-identical dump
phase0_workspace_build.sh CI smoke build exit 0, both arches
phase0_invariant_stub.trace nf-verifier vacuous-pass trace 14/14 PASS
Pitfalls

Feature-flag combinatorics (ADR-26) can explode CI matrix time if every combination is tested — test only the shipped combinations (all-off, all-on, Phase-0 default). MSRV drift: a contributor's local toolchain silently newer than the pinned 1.78 masks a real MSRV break; CI must pin explicitly.

⬜ Phase 1 — Packet Path & Five-Hook Pipeline §13

Objectives

Implement the five-hook PacketPath (§3) per P1, and the Verdict semantics (§8.2) that enforce the routing-decision boundary (I2).

Deliverable

nf-core::PacketPath::process (§11 signature) dispatches a synthetic packet through all five hooks in the fixture harness; an accept-all INPUT rule passes 100% of a 10,000- packet synthetic trace.

Acceptance

Fixture phase1_trivial_accept.pcap (10,000 packets): 100% Accept, 0 drops, 0 panics. Empty-hook dispatch latency < 100 ns p50 (M1). I2/I8 assertions: 0 violations across 1,000,000 fuzzed dispatch orderings.

Fixtures
Fixture Purpose Expected Output
phase1_trivial_accept.pcap baseline accept-all correctness 100% Accept
phase1_local_vs_forward.json routing-decision boundary (I2) exactly one of INPUT/FORWARD fires
phase1_malformed_hook_order.trace replayed out-of-order hook injection rejected at dispatch, logged
Pitfalls

A rule with no terminal action must fall through as Continue (next hook), not an implicit Accept — a common nftables-migration bug. BSD pf's hook positions differ from Linux's five-hook model (Hansteen, Ch. 4); this design is Linux-compatible only, documented rather than papered over.

⬜ Phase 2 — Packet Classifier & Rule Match Engine §14

Objectives

Implement the typed Match/Rule engine (§11) and the decision-tree compiler that replaces linear scan above 50 rules (P9), plus the IPset accelerator (§8.5).

Deliverable

nf-classifier::RuleSet evaluates both linear and decision-tree modes; a bucket verifies decision-tree output matches linear-scan output on the same input for every generated rule set.

Acceptance

10,000 randomly generated rules verified against the linear-scan oracle: 100% verdict agreement. Decision-tree lookup < 200 ns p99 at R=10,000 (M2). IPset lookup O(1) confirmed via constant-time benchmark across set sizes 10–1,000,000.

Fixtures
Fixture Purpose Expected Output
classifier_random_10k.rules tree-vs-linear differential 100% agreement
classifier_ipset_accel.json IPset O(1) lookup constant lookup time across set size
classifier_any_match.pcap wildcard "any" rule correctness matches every packet
Pitfalls

An "any" rule must match unconditionally — a classifier whose default is "no match" for an absent field silently loses this case. IPset acceleration only pays off above a threshold set size; below it, linear CIDR scan is cache-friendlier (measure, don't assume).

⬜ Phase 3 — Conntrack Core & TCP State Machine §15

Objectives

Implement the 5-tuple+zone hash table (I1, I9) with SipHash-keyed buckets (ADR-12, Aumasson & Bernstein applied here) and the TCP state machine of §8.3 (I4).

Deliverable

nf-conntrack inserts, looks up (either direction), and transitions TCP state for a synthetic three-way-handshake-plus-teardown trace with 0 invariant violations.

Acceptance

State-machine fuzz target: 0 invalid-transition escapes across 10,000,000 generated packet sequences (I4). Lookup latency < 100 ns p50 / < 300 ns p99 (M1). Fixture-verified transitions for every row of §8.3, including the RFC 793 section 3.4 simultaneous-open case.

Fixtures
Fixture Purpose Expected Output
conntrack_syn_sent_to_established.pcap happy-path handshake correct state sequence
conntrack_simultaneous_open.pcap section 3.4 of RFC 793 case resolves to Established
conntrack_rst_any_state.pcap RST regardless of sequence immediate Close
conntrack_out_of_window_retransmit.pcap 32 KB tolerance window accepted, not dropped
Pitfalls

Out-of-window tolerance must be bounded (32 KB), not unbounded — an unbounded tolerance reopens the evasion class ADR-20/§18 exists to close for fragments and would do the same here for sequence numbers. SACK/timestamp options extend tracked state per direction; skipping their parsing misclassifies legitimate reordered segments as invalid.

⬜ Phase 4 — UDP/ICMP Conntrack & Timeout Management §16

Objectives

Extend nf-conntrack to UDP (unreplied/established timeouts, ADR-07) and ICMP (echo tracking plus error-message correlation, RFC 5508).

Deliverable

UDP and ICMP flows are tracked in the same nf-conntrack table (P2, I1) as TCP; ICMP error correlation resolves to the originating flow in the differential fixture.

Acceptance

ICMP error correlation: 100% correct inner-tuple lookup across 500 generated error cases. UDP established-timeout transition verified within ±1 s of the configured 180 s value.

Fixtures
Fixture Purpose Expected Output
icmp_error_inner_tuple.pcap inner-header correlation (RFC 5508) correct parent-flow match
udp_established_transition.json bidirectional-traffic timeout bump 30 s → 180 s at correct trigger
udp_reverse_without_forward.pcap reverse-first UDP packet classified New, not Established
Pitfalls

ICMP error inner headers can be truncated below the full original header — extraction must bound-check before reading (P5), per §8.7. A UDP packet in the reverse direction with no prior forward packet is a New flow, not part of an established one — treating it as established would violate P2/I1.

⬜ Phase 5 — NAT Engine: SNAT/DNAT/Masquerade & Port Allocation §17

Objectives

Implement NatPool/PortAllocator (§11): random-with-retry default port allocation (ADR-14, RFC 6056), full-cone default mapping/filtering (ADR-15, RFC 4787 REQ-1/REQ-8), and masquerade.

Deliverable

nf-nat performs SNAT, DNAT, and masquerade with atomic port allocation (I6); a 1,000,000-concurrent-allocation stress fixture shows 0 collisions.

Acceptance

Port allocation collision rate: 0 across the 1,000,000-allocation stress fixture (I6). NAT rewrite latency < 200 ns p50 / < 500 ns p99 (M3). PBA configuration test: 1,000- port blocks yield 64 subscribers per public IPv4 address (chained from §36 item 9).

Fixtures
Fixture Purpose Expected Output
nat_snat_basic.pcap outbound SNAT round trip correct rewrite both directions
nat_dnat_basic.pcap inbound DNAT round trip correct rewrite both directions
nat_masquerade_dhcp_change.json egress IP change mid-session masquerade re-resolves
nat_port_block_alloc.json PBA fairness 1,000 ports/subscriber, no cross-subscriber collision
Pitfalls

Port-collision retry storms under pool near-exhaustion must be bounded (ADR-14's max_retries), not retried indefinitely. A DNAT rule that rewrites to an internal host whose reply the firewall re-DNATs again creates a loop unless direction is respected (I3-adjacent: DNAT applies only in the original direction, never on the reply).

⬜ Phase 6 — Hairpinning & Fragment Handling §18

Objectives

Support hairpin traffic (internal → own public IP → internal) and implement scrub- first fragment reassembly (ADR-20) ahead of classification.

Deliverable

Hairpin round-trip fixture passes end-to-end with two NAT rewrites; fragmentation- evasion fixtures are detected and normalized rather than passed through.

Acceptance

Fragmentation-evasion fixtures (tiny-fragment, overlapping-fragment): 100% detected/ normalized, 0 evasions. Hairpin round-trip fixture: verified NAT applied exactly twice, correct final delivery.

Fixtures
Fixture Purpose Expected Output
frag_tiny_fragment_attack.pcap evasion via undersized fragments normalized/dropped, not evaded
frag_overlap_attack.pcap evasion via overlapping fragments normalized per first-fragment-wins policy
hairpin_internal_to_public.pcap internal→own-public→internal double NAT rewrite, correct delivery
Pitfalls

Hairpinning requires NAT in both directions on the same packet — a single-rewrite implementation silently fails this case (a common "why can't I reach my own public IP from inside" support ticket). Fragment-reassembly buffers can grow unbounded under a fragmentation-flood attack if not capped per-flow (P8).

⬜ Phase 7 — Rule DSL, Bytecode VM & Atomic Reload §19

Objectives

Implement the nftables-inspired typed DSL (§8.5, ADR-04), its bytecode compiler, and atomic ruleset reload (I10, P11).

Deliverable

nf-rules parses, compiles, and atomically reloads a ruleset; a 10,000-line reference nftables-style config round-trips through parse→compile→re-emit.

Acceptance

10,000-line config parses in < 1 s (M9). Concurrent-reload stress fixture: 0 partial- ruleset observations across 100,000 concurrent-packet/reload interleavings (I10). Ruleset reload latency < 10 ms p50 / < 50 ms p99 (M15).

Fixtures
Fixture Purpose Expected Output
rules_nftables_roundtrip.conf reference-syntax round trip byte-stable re-emit
rules_variable_substitution.conf $variable expansion correct substitution, no leaks across chains
rules_concurrent_reload.trace reload under live traffic 0 partial-generation reads (I10)
Pitfalls

Variable-substitution ordering can silently shadow an earlier definition — resolve in strict declaration order, error on redefinition. Chain-priority ties are a configuration error, not a silently-resolved ambiguity (fail closed per P5's spirit applied to configuration, not just packets).

⬜ Phase 8 — Conntrack Expectations & Application-Layer Gateways §20

Objectives

Implement ExpectationTable (§11, I7) and the FTP (active + passive) and SIP Helper implementations (ADR-16, P7).

Deliverable

FTP active/passive and SIP INVITE flows traverse NAT correctly via ALG rewriting; a per-parent expectation cap enforces P8 under a flood fixture.

Acceptance

FTP active-mode conformance bucket: 100% agreement against the reference nftables FTP helper (ADR-11 differential). Per-parent expectation cap = 16 enforced: 0 unbounded- growth escapes across the expectation-flood fixture.

Fixtures
Fixture Purpose Expected Output
algs_ftp_active.pcap PORT-command rewrite + expectation server-initiated data connection admitted
algs_ftp_passive.pcap PASV-response handling correct client-side connect, no rewrite needed
algs_sip_invite_rewrite.pcap SDP c=/m= rewrite RTP flows admitted via expectation
algs_expectation_flood.pcap per-parent flood capped at 16, excess rejected
Pitfalls

An expectation orphaned when its parent connection is torn down must be cascaded away, not left lingering (I7-adjacent hygiene). SIP messages can carry both a request and a response in adjacent segments; the Helper must disambiguate which is which before rewriting.

⬜ Phase 9 — DDoS Mitigation: SYN Proxy & Rate Limiting §21

Objectives

Implement the SYN-proxy cookie (I11, ADR-18, Schuba et al. 1997 applied here) and a per-source token-bucket rate limiter, directly addressing the state-table-exhaustion defense named in I5.

Deliverable

nf-ddos::synproxy defers conntrack admission until cookie verification; a synthetic SYN-flood fixture shows bounded conntrack growth throughout the attack.

Acceptance

Cookie-forgery fuzz target: 0 forged-cookie acceptances across 10,000,000 attempts (I11). SYN-proxy rate ≥ 2,000,000 SYN/s p50, ≥ 500,000 SYN/s p99 under sustained load (M7).

Fixtures
Fixture Purpose Expected Output
ddos_syn_flood_synthetic.pcap sustained flood, conntrack stays bounded 0 table-full events during flood
ddos_cookie_forgery_fuzz.corpus forged-cookie attempts 0 acceptances (I11)
ddos_rate_limit_per_source.json per-source token bucket correct throttling above configured rate
Pitfalls

The MSS encoded in the cookie must match what the real backend would negotiate — a mismatch (e.g., cookie MSS 1500 vs. backend PMTU-derived MSS 1460) degrades post- handshake performance without breaking correctness. Cookie time-buckets typically span 1 minute; a bucket window over 2 minutes wide reopens replay risk.

⬜ Phase 10 — Deep Packet Inspection Module §22

Objectives

Implement opt-in per-rule DPI (ADR-17): Aho-Corasick multi-pattern signature matching and TLS ClientHello SNI extraction.

Deliverable

nf-dpi identifies the listed protocols and extracts SNI from both single-segment and fragmented ClientHellos.

Acceptance

Fragmented-ClientHello fixture: 100% correct SNI extraction across a 2-segment split. DPI overhead < 5 µs per 1500 B packet (M4).

Fixtures
Fixture Purpose Expected Output
dpi_http_signature.pcap HTTP method-line signature correctly identified as HTTP
dpi_tls_sni_fragmented.pcap ClientHello split across 2 segments correct SNI extracted
dpi_unknown_protocol.pcap no matching signature classified unknown, policy default applies
Pitfalls

A fragmented ClientHello requires buffering — a stateless per-packet DPI implementation cannot see the SNI. HTTPS payload beyond the ClientHello is opaque by design; DPI cannot claim visibility it structurally does not have.

⬜ Phase 11 — IPv6 Transition: NAT64, DS-Lite, MAP-T/E §23

Objectives

Implement stateful NAT64 (RFC 6146), DS-Lite (RFC 6333), MAP-T (RFC 7599), and MAP-E (RFC 7597) as first-class transition technologies (ADR-10).

Deliverable

Four crates (nf-nat64, nf-dslite, nf-mapt, nf-mape) each translate/tunnel according to their RFC; NAT64 reuses the §17 NAT engine rather than reimplementing port allocation.

Acceptance

NAT64 well-known-prefix translation: 100% correct across 1,000 synthetic IPv6-to-IPv4 flows. MAP-T PSID port-derivation fixture: 0 port collisions across the configured PSID range.

Fixtures
Fixture Purpose Expected Output
nat64_wkp_translation.pcap 64:ff9b::/96 translation correct IPv4 destination extraction
dslite_aftr_tunnel.pcap IPv4-in-IPv6 tunnel to AFTR correct decapsulation + NAT
mapt_psid_derivation.json stateless port-set derivation 0 collisions across PSID range
mape_encapsulation.pcap IPv4-in-IPv6 encapsulation (vs. MAP-T translation) correct encapsulated frame
Pitfalls

NAT64's prefix may be the well-known 64:ff9b::/96 or a network-specific prefix (NSP) — confusing the two misroutes translated traffic. MAP parameter misconfiguration (overlapping PSID ranges) creates cross-subscriber port collisions identical in shape to a §17 PBA misconfiguration.

⬜ Phase 12 — eBPF/XDP Fastpath §24

Objectives

Compile a verified-equivalent rule subset to XDP (I13, ADR-09) targeting the M10 100 Gbps stretch throughput, per Dobrescu et al.'s RouteBricks parallelism argument and Kohler et al.'s Click node-graph lineage (both applied here).

Deliverable

nf-xdp loads a compiled program that agrees with the default path on every packet in the XDP-eligible subset; ineligible rules are reported, not silently dropped from enforcement.

Acceptance

Differential fixture: 100% verdict agreement between XDP and default path across the eligible subset (I13). XDP throughput ≥ 80 Gbps p99 (M10).

Fixtures
Fixture Purpose Expected Output
xdp_vs_netfilter_differential.pcap cross-path verdict agreement 100% agreement (I13)
xdp_verifier_rejection.rules intentionally verifier-ineligible rules clean fallback, no partial enforcement
xdp_fallback_ineligible_rule.json mixed eligible/ineligible ruleset eligible rules on XDP, rest on default path
Pitfalls

The eBPF verifier rejects unbounded loops and most dynamic-dispatch helpers — some rules are structurally ineligible and must fall back cleanly, not be silently dropped from enforcement. A rule reload that changes a rule's XDP-eligibility mid-flight must not leave a window where it's enforced nowhere.

⬜ Phase 13 — Control Plane, Conformance, Fuzzing & Soak Canary §25

Objectives

Wire nf-control/nf-cli (nfctl), complete the conformance suite, add cargo-fuzz targets, and run the 24-hour fuzz canary plus 30-day soak (ADR-23, ADR-24).

Deliverable

nfctl operates a running instance end-to-end (load, dump, reload); the full conformance suite and both fuzz/soak jobs are wired into CI/CD (§31).

Acceptance

24 h fuzz canary: 0 panics, 0 undefined-behavior reports (M13). Differential-vs- nftables conformance: 100% agreement on the curated corpus (M12). 30-day soak: 0 memory growth beyond ±5% of steady-state baseline.

Fixtures
Fixture Purpose Expected Output
soak_30day_synthetic_traffic.plan sustained realistic mixed traffic ±5% steady-state memory
fuzz_corpus_seed.tar seed inputs for all fuzz targets non-crashing baseline corpus
differential_nftables_corpus.rules curated ruleset corpus 100% cross-implementation agreement (M12)
Pitfalls

A fuzz corpus goes stale as new rule features ship — it must be refreshed alongside each feature phase, not left frozen at Phase-0 vintage. A soak-canary environment that drifts from production sysctls (conntrack timeouts, table size) produces misleading results.
