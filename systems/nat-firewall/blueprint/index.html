1. Goal & Scope

158 — NAT / Firewall is a stateful packet-classification, connection-tracking, and network-address-translation dataplane: a five-hook packet path (PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING, per the netfilter tradition) in front of a connection tracker that is the single source of truth for flow state, a NAT engine that rewrites tuples independently of policy, an ordered-rule/set/longest-prefix match engine, and protocol-aware extensions (ALGs, DPI, IPv6 transition, DDoS mitigation) layered on top without touching the correctness kernel. The system exists to answer, for every packet, in bounded time and with a fully reconstructable audit trail: which flow does this belong to, what is its state, what does policy say, and what (if anything) must be rewritten before it leaves.

Phase-0 deliverable (numbered, matches §10 Repository Layout and §11 Core Schema & Types):

  1. nf-core — Packet, FiveTuple, Direction, Verdict, PacketPath (five-hook dispatch, no policy yet).
  2. nf-classifier — linear-scan Match/Rule evaluation, IPv4 only.
  3. nf-conntrack — 5-tuple hash table, TCP/UDP/ICMP tracking per RFC 5382 / RFC 4787 / RFC 5508.
  4. nf-nat — SNAT, DNAT, masquerade; random-with-retry port allocation (RFC 6056).
  5. nf-rules — minimal DSL parser (table/chain/rule; accept/drop/snat/dnat actions).
  6. nf-control — control socket: ruleset load, conntrack dump.
  7. nf-verifier — invariant-checking deterministic simulator (I1–I14 stubs).
  8. conformance/ shell — classifier/, conntrack/, nat/ buckets.

System boundaries. Provides: packet classification, stateful tracking, NAT (SNAT/DNAT/masquerade/CGN), rule/ACL evaluation, opt-in DPI, pluggable ALGs, DDoS mitigation (SYN proxy, rate limiting), IPv6 transition (NAT64/DS-Lite/MAP-T/E). Delegates: routing-table computation, ARP/NDP resolution, and NIC DMA to the host OS (or a DPDK PMD in the XDP-adjacent deployment) — this system consumes a routing decision, it does not compute one. Does NOT provide: a BGP speaker or general router (see sibling project BGP-Router, #157 for policy alignment at an AS edge), a VPN tunnel implementation (see VPN-WireGuard, #156 — WireGuard UDP/51820 traffic must simply be permitted through, not terminated here), or a general signature-based IDS/IPS engine (the DPI module identifies protocols/SNI, it is not a Suricata-class payload-inspection system).

Non-goals. Replacing netfilter/nftables/pf in existing production estates; Common Criteria certification (the architecture does not preclude it later — see the Deferred Features Register); non-IP L3 protocols (IPX, AppleTalk).

Deployment model. Single-box inline gateway/bump-in-the-wire (default, netfilter hook-integrated); containerized control-plane with kernel/eBPF dataplane split (cross-ref the Comparative Architecture Table, §35, vs Cilium); carrier-grade multi- tenant edge with Port Block Allocation (§17, Phase 5) for CGN operators.

Target users/operators. Network engineers running edge/gateway firewalls; ISP CGN operators; platform teams building Kubernetes-adjacent NAT/firewall dataplanes; security engineers auditing rule sets and conntrack behavior.

What later phases unlock. DPI-based semantic policy (§22, Phase 10); IPv6 transition for IPv4-exhausted deployments (§23, Phase 11); an XDP fastpath for 100 Gbps line rate (§24, Phase 12); CGN-scale port sharing (§17, Phase 5).

Recommended language: Rust 1.78+ (MSRV, ADR-01). Rationale: the ownership model eliminates use-after-free and double-free as a class in exactly the parsing/rewriting code paths (packet headers, ALG payloads) where C-family firewalls have paid a recurring CVE tax (CVE-2022-1972, CVE-2022-32250, CVE-2021-22555 — all §26 Threat Model entries); zero-cost abstractions preserve C-like hot-path performance; the crate ecosystem (cargo-fuzz, criterion, tracing) matches the Testing & Verification Strategy (§30) directly. Rejected languages: C — the netfilter/pf reference implementations' own CVE history is the counter-argument to using it again; C++ — RAII narrows but does not close the manual-lifetime footgun class, and the larger language surface increases reviewer burden in security-critical code; Go — GC pauses are incompatible with the sub-microsecond packet-path budget in §4, and avoiding them requires an unsafe-adjacent subset that forfeits Go's main ergonomic advantage anyway.

Prerequisites. TCP three-way handshake and RFC 793 state diagram; NAT terminology (section 2 of RFC 2663: traditional NAT, basic NAT, NAPT); basic Rust ownership and Arc/atomic concurrency; Linux networking internals (netfilter hooks, sk_buff); hash tables and lock-free/CAS-based data structures.

Estimated timeline. Phase 0: 2 weeks. Full system (Phase 0 through Phase 13, §12–§25): ~47 weeks (~11 months) — see Appendix B for the per-phase breakdown.

Deferred features (full register in the Deferred Features Register, §39): SCTP-aware NAT PhaseDeferred("§17"); a full TCP-splice SYN-proxy mode PhaseDeferred("§21"); a TLA+ formal model of the conntrack state machine PhaseDeferred("§15"); VPP/DPDK full kernel-bypass integration PhaseDeferred("§24"); hardware NIC ASIC offload PhaseDeferred("§33"); H.323/IRC-DCC/PPTP ALG helpers beyond the FTP+SIP baseline PhaseDeferred("§20"); conntrackd-style multi-box state sync for asymmetric routing PhaseDeferred("§27"); GENEVE/VXLAN decapsulation-aware classification PhaseDeferred("§14"); eBPF-resident DPI PhaseDeferred("§22"); a centralized SDN control-plane push model PhaseDeferred("§38").

2. Why Build This

A stateful firewall + NAT is the canonical lesson in getting a state machine right under adversarial and asymmetric conditions, not in packet filtering per se — "drop packets that don't match policy" is three lines of pseudocode; "the load-balanced reply path injects RSTs with sequence numbers that look out-of-window because the LB rewrote them, and 100,000 other flows are being tracked concurrently on a 4-core box at line rate" is the actual production problem, and every decision in this document is downstream of it. The unique systems knowledge here spans four disciplines that rarely appear together: real-time state-machine correctness (the TCP/UDP/ICMP conntrack machine, §8.3), classification-algorithm design (decision-tree compilation, §14 Phase 2), distributed/adversarial reasoning (SYN floods, off-path port-prediction, ALG payload injection — §21 Phase 9, §26 Threat Model), and protocol archaeology (why FTP active mode, SIP, and NAT64 each need a different rewriting strategy, §20 and §23).

It matters architecturally because the systems that got it right — netfilter's five-hook separation, pf's scrub-then-match normalization, nftables' bytecode VM, VPP's node-graph pipeline, eBPF/XDP's kernel-bypass fastpath — share one structural guarantee: classification, state lookup, and rewriting are three separate concerns, never conflated into one function. That guarantee is what makes DDoS mitigation, DPI, ALGs, and IPv6 transition addable later without destabilizing the correctness kernel, and it is precisely the guarantee this blueprint's Design Principles (§6) exist to enforce, and its System Invariants (§7) exist to keep enforced under concurrency. Building this teaches the same muscles as BGP-Router (#157) (policy evaluation independent of the forwarding decision) and VPN-WireGuard (#156) (a different answer to "where does the trust boundary live in the packet path").

What Mastery Looks Like:

  • Trace any packet through PREROUTING → routing decision → {INPUT|FORWARD} → OUTPUT → POSTROUTING and name, at each hop, which invariant (§7) would catch a violation — gained in §13 (Phase 1).
  • Explain, with the state table in hand, why a load-balancer-injected RST is not an off-path attack and how PAWS/timestamp tracking disambiguates it — gained in §15 (Phase 3).
  • Compute the port-collision probability of random-vs-sequential allocation and justify RFC 6056 with numbers, not adjectives — gained in §17 (Phase 5).
  • Explain why an ALG must create a bounded Expectation rather than a general firewall-rule injection, with CVE-2002-0985 as the counter-example — gained in §20 (Phase 8).
  • Derive the SYN-proxy cookie's forgery probability and its MSS-negotiation failure mode — gained in §21 (Phase 9).
  • Justify, with RFC 4787's mapping/filtering matrix, why full-cone is the residential default and address/port-restricted is the enterprise opt-in — gained in §8.4 and §17 (Phase 5).
  • Compute, from §4's constraints alone, the memory and throughput ceiling of a single box and name the next lever past it — gained in §36 (Back-of-Envelope Capacity Model) and §33 (Scalability Analysis).
  • Redesign the dataplane as a pure eBPF/XDP or a centralized-SDN-control architecture and state exactly what each trades away — gained in §38 (Alternative Architectures).

Four properties hold everywhere downstream. PREROUTING/POSTROUTING bracket the routing decision because DNAT must run before the destination decides the egress interface, and SNAT must run after the egress interface is known (P1, P3). One conntrack table, one lookup, both directions — a flow's original and reply 5-tuples both hash into the same table (I1), so a single lookup resolves either direction (P2). NAT is orthogonal to policy — DNAT/SNAT rewrite tuples at PRE/POSTROUTING; accept/ drop decisions are made at INPUT/FORWARD/OUTPUT; neither hook performs the other's job (P3, ADR-02). The control plane is decoupled from the data plane — nf-rules and nf-control mutate a RuleSet snapshot; the packet path only ever reads an immutable, atomically-swapped generation of it (I10, P11).

Per box: NIC RX hands a frame to either the XDP hook (§24, opt-in fastpath, verified- equivalent rule subset, I13) or the default in-process path. PREROUTING applies DNAT and performs the first conntrack lookup/creation. Routing decision is delegated to the host OS per §1; this box only consumes "local" vs "forward." INPUT/FORWARD apply policy (RuleSet evaluation, §14). OUTPUT applies policy to locally-originated traffic. POSTROUTING applies SNAT/masquerade using the egress interface now known. nf-conntrack is drawn once, at the center, because every hook above consults it — it is not a per-hook cache, it is the single state authority (P2, I1).

6. Design Principles

  • P1. Five-Hook Separation. Rule: classification, NAT, and policy attach only at PREROUTING/INPUT/FORWARD/OUTPUT/POSTROUTING, never inline in the parser. Tradeoff: less flexible than one monolithic hook. Operational implication: operators reason about DNAT-vs-SNAT placement without reading source. Violated: merging hooks reintroduces "which stage rewrote this packet" as an undebuggable question.
  • P2. Conntrack Is the Single Source of Truth. Rule: no hook keeps parallel per- connection state; all of it lives in nf-conntrack. Tradeoff: every hook pays one lookup. Operational implication: one table to inspect, one table to size (§4). Violated: two hooks disagreeing about a flow's state is a split-brain bug class.
  • P3. NAT Is Orthogonal to Policy. Rule: DNAT/SNAT rewrite tuples; ACL evaluation decides accept/drop; neither hook does the other's job. Tradeoff: a NAT'd packet must still separately pass policy. Operational implication: operators can express "NAT this, but still filter it" without a special case. Violated: a NAT rule that also filters silently bypasses the policy audit trail.
  • P4. Ordered-List Determinism. Rule: identical (packet, ruleset) ⇒ identical verdict, on any core, any time. Tradeoff: no per-core rule-evaluation shortcuts that could diverge. Operational implication: nft-style trace output is trustworthy. Violated: nondeterminism turns every incident into "reproduce if you can" (I8).
  • P5. Fail Closed on Ambiguity. Rule: a packet the parser cannot fully classify (malformed header, unknown protocol, truncated inner header) is dropped, never passed. Tradeoff: a parser bug drops legitimate traffic rather than admitting it. Operational implication: "silently permissive" is not a failure mode this system has. Violated: fail-open on ambiguity is exactly the ALG-injection and evasion class in T4/T3.
  • P6. Endpoint-Independent Mapping Is the Configurable Default. Rule: the default NAT mapping/filtering is full-cone (RFC 4787 REQ-1/REQ-8); address/port-restricted is opt-in. Tradeoff: full-cone is more permissive. Operational implication: STUN/P2P works out of the box (§8.4). Violated: silently defaulting to restricted breaks residential P2P compatibility without a visible policy change.
  • P7. ALGs Are Least-Privilege. Rule: a Helper may only create a bounded Expectation (§11); it can never inject an arbitrary firewall rule. Tradeoff: some protocol features an ALG can't express are simply unsupported. Operational implication: an ALG CVE (e.g., CVE-2002-0985) is contained to a wrong/missing expectation, not a policy bypass. Violated: unbounded ALG rule-injection is the historical FTP-ALG vulnerability class.
  • P8. Bounded Resource Consumption Everywhere. Rule: conntrack table, expectation table, and per-parent expectation count (§20) all have hard ceilings with an eviction/ backpressure policy. Tradeoff: a legitimate burst past the ceiling is throttled, not admitted. Operational implication: capacity planning is a table lookup (§4), not a guess. Violated: unbounded growth under load is the SYN-flood and expectation-flood attack surface (T1, T12).
  • P9. Sub-Linear Load-Bearing Lookups. Rule: every hot-path table access is O(1) or O(log R) amortized; no unbounded linear scan on the packet path. Tradeoff: the decision-tree compiler (§14) adds ruleset-load-time cost to buy per-packet speed. Operational implication: rule-count growth degrades gracefully (§33). Violated: an O(R) rule scan at 100,000 rules blows the latency budget in §4.
  • P10. Fastpath/Default-Path Verdict Parity. Rule: the XDP dataplane (§24) and the default in-process dataplane must agree bit-for-bit on Accept/Drop for every rule in the subset both support (I13). Tradeoff: not every rule is XDP-eligible. Operational implication: enabling XDP never silently changes policy outcomes. Violated: a verdict mismatch is a P1 defect (I13), because it means two dataplanes enforce two policies.
  • P11. Atomic Configuration Change. Rule: a ruleset reload is all-or-nothing; no packet is ever evaluated against a half-applied ruleset (I10). Tradeoff: a reload either fully lands or fully rolls back — no partial-apply recovery path exists. Operational implication: nfctl reload is safe to run under live traffic. Violated: partial application under concurrent packet processing is exactly nftables' historical non-atomic-reload class.
  • P12. Cryptographic State Must Not Be Forgeable From Observation. Rule: SYN cookies and the conntrack hash key use a keyed PRF (SipHash), not a public deterministic hash. Tradeoff: a keyed hash costs more cycles than an unkeyed one (ADR-12). Operational implication: an attacker who can observe traffic cannot predict hash-bucket collisions or forge a cookie. Violated: an unkeyed hash is a chosen-key collision DoS vector (T8).
  • P13. Telemetry Is a First-Class Output. Rule: every invariant (§7) emits a counter on violation; the debugging methodology is "read the dashboard, then the trace." Tradeoff: every hot-path check that can fail must carry an atomic counter increment. Operational implication: Operational Readiness (§28) is built directly on invariant telemetry, not bolted on. Violated: a silent invariant violation is undebuggable by definition.
  • P14. Protocol Extensions Live Behind a Stable Trait. Rule: every ALG, transition technology, and DPI signature module is a separate crate implementing a fixed trait (Helper, §11); the core packet path never special-cases a protocol by name. Tradeoff: a trait boundary costs one indirection per protocol dispatch. Operational implication: shipping a new ALG never touches nf-core/nf-conntrack. Violated: special-casing "if protocol == FTP" in the core path is exactly the coupling this principle exists to prevent.

8. Domain Model

8.1 Packet & Flow Representation

Every packet entering the pipeline is parsed once into offsets (L2/L3/L4/L5) over a mutable buffer — no copy, no re-parse per hook. The 5-tuple (src_ip, dst_ip, src_port, dst_port, proto) plus a zone (I9) is the flow identity used by every subsystem; FiveTuple::reverse() (signature, §11) produces the reply-direction key used by the single-table, both-directions lookup (P2). Fields and their semantics are formalized in §11 (Core Schema & Types) — this section only fixes vocabulary.

8.2 Five-Hook Packet Path (Sequencing)

Sequencing is fixed (§3): PREROUTING → routing decision → {INPUT|FORWARD} → OUTPUT → POSTROUTING. A Verdict returned by any hook is one of Continue (fall through to the next hook — the correct behavior for a rule with no terminal action), Accept, Drop, Reject, Stolen (handed to a queue/userspace consumer), or Queue(id). Only Continue ever proceeds to the next hook; every other verdict terminates the pass.

8.3 Connection-Tracking State Machine (TCP)

State Trigger Next State Notes
(none) SYN seen, admitted SynSent new ConntrackEntry, ConntrackState::New
SynSent SYN-ACK seen (reply dir) SynReceived per section 3.4 of RFC 793
SynSent simultaneous SYN (both dirs) SynReceived simultaneous-open case, RFC 793
SynReceived ACK seen Established ConntrackState::Established
Established FIN seen (either dir) FinWait (sender) / CloseWait (receiver) half-close begins
FinWait FIN-ACK seen TimeWait 30 s default timeout
CloseWait LAST-ACK seen Close GC'd promptly
any RST seen Close regardless of sequence number, per I4
any timeout exceeded, no traffic reclaimed GC path, §15 (Phase 3)

Out-of-window tolerance: packets within 32 KB behind the expected sequence are accepted as retransmits, not rejected — a strict RFC-793 window check would drop legitimate retransmissions arriving after the window slid. SACK and timestamp (PAWS) options extend the tracked state per direction; ignoring them misclassifies legitimate reordered/ retransmitted segments as invalid (I4).

8.4 NAT Mapping & Filtering Model (RFC 4787)

Mapping \ Filtering Endpoint-Independent Address-Restricted Address+Port-Restricted
Endpoint-Independent Full-cone (P6 default) Restricted-cone Port-restricted-cone
Address-Dependent (uncommon) Address-restricted, symmetric-ish —
Address+Port-Dependent — — Symmetric NAT (ADR-15 opt-in)

Endpoint-independent mapping: NAT(int_addr, int_port, dst1) == NAT(int_addr, int_port, dst2) — the same internal 5-tuple always yields the same external mapping regardless of destination, which is what makes STUN-style P2P discovery work (Ford, Srisuresh, Kegel 2005). Endpoint-independent filtering (full-cone) then additionally admits reply traffic from any external source once the mapping exists, subject to policy.

8.5 Rule/ACL Match Engine Grammar

ruleset   = { table } ;
table     = "table" family ident "{" { chain } "}" ;
chain     = "chain" ident "{" hookdecl { rule } "}" ;
hookdecl  = "type" chaintype "hook" hookname "priority" int ";" ;
rule      = { match } action ";" ;
match     = field relop value | "ip" "saddr" cidr | "ct" "state" statelist ;
action    = "accept" | "drop" | "reject" | "snat" natargs | "dnat" natargs
          | "masquerade" | "jump" ident | "goto" ident | "return" ;

Evaluation is ordered, first-match-wins within a chain (P4, I8); Set { name, key } matches are O(1) via an IPset hash accelerator instead of an O(N) CIDR scan (P9); CIDR matches use longest-prefix selection when multiple set entries could match the same address.

8.6 Worked Example — Outbound TCP Round Trip Through SNAT/DNAT

Internal host 10.0.0.5:51000 opens TCP to 93.184.216.34:443. At POSTROUTING, SNAT rewrites the source to 203.0.113.9:54321 (I6 allocates the port); nf-conntrack records the pair (10.0.0.5:51000→93.184.216.34:443, 93.184.216.34:443→ 203.0.113.9:54321) (I1). The reply's destination 203.0.113.9:54321 is looked up in the reply direction, resolving to the same entry; POSTROUTING reverses the rewrite back to 10.0.0.5:51000. State progresses SynSent → SynReceived → Established (§8.3) on the SYN/SYN-ACK/ACK sequence, entirely on this one entry.

8.7 Malformed-Input Example

A crafted TCP segment sets SYN, FIN, and RST simultaneously — a combination no legitimate stack produces. Per P5 (fail closed) and I4 (no transition-table edge exists for this event), the packet is classified ConntrackState::Invalid and dropped; default policy never evaluates it as a new-flow candidate. An ICMP error whose embedded inner IP+L4 header is truncated below 8 bytes fails inner-tuple extraction (§16, Phase 4) and is dropped rather than guessed at.

8.8 Failure-Path Example — Conntrack Exhaustion Mid-Handshake

The table is at its §4 ceiling (I5) when a new SYN arrives. Admission is refused for a plain new-flow entry; if SYN-proxy (§21, Phase 9, I11) is enabled, the SYN is answered with a cookie SYN-ACK without allocating conntrack state yet, deferring the table insert until the client's ACK proves cookie validity — converting a would-be table-full drop into a cost-shifted, forgery-resistant admission decision.

A rule with no terminal action must fall through as Continue (next hook), not an implicit Accept — a common nftables-migration bug. BSD pf's hook positions differ from Linux's five-hook model (Hansteen, Ch. 4); this design is Linux-compatible only, documented rather than papered over.

13.7 Performance Concerns

Empty-hook evaluation must stay allocation-free; pre-size RuleSet vectors at ruleset- load time, not per-packet. The is-local branch is computed once per packet, not once per hook (P9).

13.8 Edge Cases

A packet destined to a local interface's broadcast/multicast address must resolve is-local unambiguously. Zero-length or truncated L2 frames are rejected before hook dispatch (P5), never passed with garbage offsets. A re-injected Queue verdict must not re-run PREROUTING a second time.

13.9 Failure Analysis

A hook that panics must not take down the pipeline for concurrent packets on other cores — dispatch is wrapped in a catch boundary converting a panic to Drop plus an invariant-violation telemetry event. A dispatch-order regression violating I2 is a P1 defect: it can cross-deliver a forwarded packet to the local stack.

13.10 Operational Notes

Metrics: hook_dispatch_ns histogram per hook name, is_local_decision_total{result}. No operator-facing config yet — this phase ships in nf-core only, not wired to nf-control.

14. Phase 2 — Packet Classifier & Rule Match Engine

14.1 Objectives

Implement the typed Match/Rule engine (§11) and the decision-tree compiler that replaces linear scan above 50 rules (P9), plus the IPset accelerator (§8.5).

14.2 Detailed Implementation Steps

Implement Rule::matches/Match::test (§11 signatures) as a pure predicate evaluation, no branching side effects. For R > 50 rules, compile to a decision tree following Gupta & McKeown's HiCuts and Singh et al.'s HyperCuts (both applied here) — cut on the most discriminating field first. Set { name, key } matches resolve via a pre-built IPset hash (O(1)) instead of a per-CIDR linear scan, per P9 and Srinivasan et al.'s grid-of-tries lineage.

14.3 Deliverable

nf-classifier::RuleSet evaluates both linear and decision-tree modes; a bucket verifies decision-tree output matches linear-scan output on the same input for every generated rule set.

14.4 Acceptance Criteria

10,000 randomly generated rules verified against the linear-scan oracle: 100% verdict agreement. Decision-tree lookup < 200 ns p99 at R=10,000 (M2). IPset lookup O(1) confirmed via constant-time benchmark across set sizes 10–1,000,000.

14.5 Conformance Fixtures

Fixture Purpose Expected Output
classifier_random_10k.rules tree-vs-linear differential 100% agreement
classifier_ipset_accel.json IPset O(1) lookup constant lookup time across set size
classifier_any_match.pcap wildcard "any" rule correctness matches every packet

14.6 Pitfalls

An "any" rule must match unconditionally — a classifier whose default is "no match" for an absent field silently loses this case. IPset acceleration only pays off above a threshold set size; below it, linear CIDR scan is cache-friendlier (measure, don't assume).

14.7 Performance Concerns

Decision-tree node layout should be cache-line-aligned for the hot discriminating fields (Gregg's cache-locality methodology, applied here). SIMD-based multi-field matching (comparing 4 packet headers against 4 rule masks in parallel) is a documented Phase-13-adjacent optimization, not required for correctness.

14.8 Edge Cases

Overlapping CIDR ranges in the same set must resolve by longest-prefix, per §8.5. A proto wildcard (proto=0 sentinel) must not accidentally match a real proto-0 (HOPOPT) packet. A port range of exactly 0..0 must never silently match all ports.

14.9 Failure Analysis

A misordered rule set (deny placed after a broader allow when the operator intended the reverse) is a policy-authoring bug the engine does not — and per P4 must not silently — correct; nft-style trace output (I8) is the debugging tool, not automatic reordering.

14.10 Operational Notes

Metrics: rule_eval_ns histogram, decision_tree_depth_gauge. Deployment note: the linear-vs-tree threshold (R=50) is a compile-time constant surfaced in BUILD_PLAN.md, not yet operator-tunable in Phase 2 (tunability arrives with nf-rules, §19).

15. Phase 3 — Conntrack Core & TCP State Machine

15.1 Objectives

Implement the 5-tuple+zone hash table (I1, I9) with SipHash-keyed buckets (ADR-12, Aumasson & Bernstein applied here) and the TCP state machine of §8.3 (I4).

15.2 Detailed Implementation Steps

Implement Bucket/Slot (§11) with per-bucket spinlocks and atomic CAS state transitions, per ADR-13. Key every ConntrackEntry by FiveTuple + zone (ADR-05, I9). Implement the TCP transition table exactly as enumerated in §8.3, sourced from section 3.4 of RFC 793 and RFC 5382's NAT-specific extensions; reject any event with no listed edge as Invalid (I4). Reuse the RFC 5382-required out-of-window tolerance and PAWS/timestamp tracking described in §8.3.

15.3 Deliverable

nf-conntrack inserts, looks up (either direction), and transitions TCP state for a synthetic three-way-handshake-plus-teardown trace with 0 invariant violations.

15.4 Acceptance Criteria

State-machine fuzz target: 0 invalid-transition escapes across 10,000,000 generated packet sequences (I4). Lookup latency < 100 ns p50 / < 300 ns p99 (M1). Fixture-verified transitions for every row of §8.3, including the RFC 793 section 3.4 simultaneous-open case.

15.5 Conformance Fixtures

Fixture Purpose Expected Output
conntrack_syn_sent_to_established.pcap happy-path handshake correct state sequence
conntrack_simultaneous_open.pcap section 3.4 of RFC 793 case resolves to Established
conntrack_rst_any_state.pcap RST regardless of sequence immediate Close

15.6 Pitfalls

Out-of-window tolerance must be bounded (32 KB), not unbounded — an unbounded tolerance reopens the evasion class ADR-20/§18 exists to close for fragments and would do the same here for sequence numbers. SACK/timestamp options extend tracked state per direction; skipping their parsing misclassifies legitimate reordered segments as invalid.

15.7 Performance Concerns

Hot fields (key, state, last_seen) are laid out in one 64-byte cache line; cold fields (helper, zone metadata) in a second line accessed only on a confirmed hit (Gregg's cache-locality methodology). 15.8 Edge Cases

A SYN-ACK with no prior SYN is out-of-state and invalid (I4). TCP Fast Open (data in the SYN) must be handled as SYN-with-payload without breaking the SynSent → SynReceived → Established sequence. Concurrent inserts for the same new flow on two cores must resolve to one entry, not two (I1) — recheck-under-lock plus CAS on the bucket head.

15.9 Failure Analysis

A bug in the transition table that accepts an invalid edge is the single highest- severity defect class this phase can produce, because I4 is the load-bearing safety property for everything downstream (NAT, policy) that trusts ConntrackState. Detection is the exhaustive-transition fuzz target; recovery is classify-Invalid-and-drop, never silently-accept.

15.10 Operational Notes

Metrics: tcp_invalid_transition_total, conntrack_count gauge (vs. the §4 ceiling). Rolling upgrade note: the on-disk/wire dump format for conntrack entries is versioned independently of the in-memory layout (§29).

16.4 Acceptance Criteria

17. Phase 5 — NAT Engine: SNAT/DNAT/Masquerade & Port Allocation

17.1 Objectives

Implement NatPool/PortAllocator (§11): random-with-retry default port allocation (ADR-14, RFC 6056), full-cone default mapping/filtering (ADR-15, RFC 4787 REQ-1/REQ-8), and masquerade.

17.2 Detailed Implementation Steps

SNAT at POSTROUTING rewrites source IP+port and records the mapping in ConntrackEntry (I3, I6); DNAT at PREROUTING does the equivalent for destination. Masquerade is SNAT to the egress interface's current address, re-resolved on interface- address change. Port allocation is random-with-retry per RFC 6056's recommendation (applied here), bounded retries (ADR-14); Port Block Allocation (CGN) assigns contiguous port ranges per subscriber to reduce conntrack pressure and produce fair sharing (§36 item 9). SCTP chunk-level rewriting is out of scope this phase — PhaseDeferred("§17"), registered in §39.

17.3 Deliverable

nf-nat performs SNAT, DNAT, and masquerade with atomic port allocation (I6); a 1,000,000-concurrent-allocation stress fixture shows 0 collisions.

17.4 Acceptance Criteria

Port allocation collision rate: 0 across the 1,000,000-allocation stress fixture (I6). NAT rewrite latency < 200 ns p50 / < 500 ns p99 (M3). PBA configuration test: 1,000- port blocks yield 64 subscribers per public IPv4 address (chained from §36 item 9).

17.5 Conformance Fixtures

Fixture Purpose Expected Output

nat_dnat_basic.pcap inbound DNAT round trip correct rewrite both directions
nat_masquerade_dhcp_change.json egress IP change mid-session masquerade re-resolves

17.6 Pitfalls

Port-collision retry storms under pool near-exhaustion must be bounded (ADR-14's max_retries), not retried indefinitely. A DNAT rule that rewrites to an internal host whose reply the firewall re-DNATs again creates a loop unless direction is respected (I3-adjacent: DNAT applies only in the original direction, never on the reply).

17.7 Performance Concerns

Checksum updates use the incremental method (per RFC 1624's additive approach) instead of full recomputation — a few additions versus reparsing the whole header, directly supporting the M3 latency target.

17.8 Edge Cases

NAT pool exhaustion (no free ports) must drop with nat_pool_exhausted_total telemetry, not silently retry forever. Port preservation (keep the internal port when unique in the pool) helps protocols that embed the source port; falls back to allocation on collision.

17.9 Failure Analysis

NAT pool exhaustion is detected via the admission check before allocation ever begins (I6); recovery is drop-plus-telemetry-plus-operator-runbook (cross-ref §28 Operational Readiness, NAT-pool-exhaustion runbook).

17.10 Operational Notes

Metrics: nat_port_alloc_total{strategy}, nat_pool_exhausted_total. Deployment note: PBA block size is operator-configurable per subscriber group, default 1,000 (§36 item 9).

18. Phase 6 — Hairpinning & Fragment Handling

18.1 Objectives

Support hairpin traffic (internal → own public IP → internal) and implement scrub- first fragment reassembly (ADR-20) ahead of classification.

18.2 Detailed Implementation Steps

Hairpin: an internal host addressing the NAT's own public IP is SNAT'd on the way out and DNAT'd on the way back to the real internal destination — both rewrites on the same packet, exercising I3 and I6 twice per packet. Fragment handling: reassemble before classification (scrub-first, per Handley, Paxson, Kreibich 2001, applied here, and Hansteen's pf scrub chapter) rather than matching per-fragment, closing the tiny- fragment/overlapping-fragment evasion class (ADR-20). Reassembly buffers are bounded per flow (P8).

18.3 Deliverable

Hairpin round-trip fixture passes end-to-end with two NAT rewrites; fragmentation- evasion fixtures are detected and normalized rather than passed through.

18.4 Acceptance Criteria

Fragmentation-evasion fixtures (tiny-fragment, overlapping-fragment): 100% detected/ normalized, 0 evasions. Hairpin round-trip fixture: verified NAT applied exactly twice, correct final delivery.

18.5 Conformance Fixtures

Fixture Purpose Expected Output
frag_tiny_fragment_attack.pcap evasion via undersized fragments normalized/dropped, not evaded
frag_overlap_attack.pcap evasion via overlapping fragments normalized per first-fragment-wins policy
hairpin_internal_to_public.pcap internal→own-public→internal double NAT rewrite, correct delivery

18.6 Pitfalls

Hairpinning requires NAT in both directions on the same packet — a single-rewrite implementation silently fails this case (a common "why can't I reach my own public IP from inside" support ticket). Fragment-reassembly buffers can grow unbounded under a fragmentation-flood attack if not capped per-flow (P8).

18.7 Performance Concerns

Reassembly buffer is capped at N fragments per flow; packets beyond the cap are rejected rather than buffered indefinitely, keeping worst-case memory bounded and consistent with §4's memory ceiling.

18.8 Edge Cases

Fragment reordering (later fragments arriving first) must still reassemble correctly within the buffer window. Fragment reassembly timeout must reclaim the buffer if the tail fragment never arrives. IPv6 fragmentation extension headers require separate parsing from IPv4's in-header fragmentation.

18.9 Failure Analysis

Reassembly buffer exhaustion (attack-driven) triggers drop-new-fragmented-flows with frag_buffer_exhausted_total telemetry rather than evicting in-progress legitimate reassembly.

18.10 Operational Notes

Metrics: frag_reassembly_ns, hairpin_rewrite_total. Operational note: hairpin support is on by default; disabling it is a documented, explicit opt-out (not a hidden default) since its absence is a common support escalation.

21. Phase 9 — DDoS Mitigation: SYN Proxy & Rate Limiting

21.1 Objectives

Implement the SYN-proxy cookie (I11, ADR-18, Schuba et al. 1997 applied here) and a per-source token-bucket rate limiter, directly addressing the state-table-exhaustion defense named in I5.

21.2 Detailed Implementation Steps

On an incoming SYN, respond with a SYN-ACK whose sequence number is a cookie encoding (tuple, MSS index, time bucket, secret), keyed with the same SipHash construction as ADR-12 (reused here for I11); no conntrack entry is created until the client's ACK proves cookie validity (§8.8's failure-path example is this exact mechanism). A per- source token-bucket rate limiter bounds new-flow admission independent of the cookie path, per P8.

21.3 Deliverable

nf-ddos::synproxy defers conntrack admission until cookie verification; a synthetic SYN-flood fixture shows bounded conntrack growth throughout the attack.

21.4 Acceptance Criteria

Cookie-forgery fuzz target: 0 forged-cookie acceptances across 10,000,000 attempts (I11). SYN-proxy rate ≥ 2,000,000 SYN/s p50, ≥ 500,000 SYN/s p99 under sustained load (M7).

21.5 Conformance Fixtures

Fixture Purpose Expected Output
ddos_syn_flood_synthetic.pcap sustained flood, conntrack stays bounded 0 table-full events during flood

21.6 Pitfalls

The MSS encoded in the cookie must match what the real backend would negotiate — a mismatch (e.g., cookie MSS 1500 vs. backend PMTU-derived MSS 1460) degrades post- handshake performance without breaking correctness. 21.8 Edge Cases

21.10 Operational Notes

23. Phase 11 — IPv6 Transition: NAT64, DS-Lite, MAP-T/E

23.4 Acceptance Criteria

23.6 Pitfalls

nf-xdp compiles only the subset of RuleSet bytecode the eBPF verifier accepts (bounded loops, no dynamic helpers beyond the verifier's allow-list) — ineligible rules fall back to the default path entirely, never partially. Conntrack lookups from XDP use kernel eBPF maps sized consistently with the §4 ceiling. Differential testing (ADR-11's methodology, applied here against the default path instead of nftables) asserts I13 on every build.

24.3 Deliverable

nf-xdp loads a compiled program that agrees with the default path on every packet in the XDP-eligible subset; ineligible rules are reported, not silently dropped from enforcement.

24.4 Acceptance Criteria

Differential fixture: 100% verdict agreement between XDP and default path across the eligible subset (I13). XDP throughput ≥ 80 Gbps p99 (M10).

24.6 Pitfalls

The eBPF verifier rejects unbounded loops and most dynamic-dispatch helpers — some rules are structurally ineligible and must fall back cleanly, not be silently dropped from enforcement. A rule reload that changes a rule's XDP-eligibility mid-flight must not leave a window where it's enforced nowhere.

24.7 Performance Concerns

XDP runs ~100 ns/packet versus ~1,000 ns on the default netfilter-integrated path (chained in §36 item 10) because it runs before sk_buff allocation — the entire rationale for the fastpath's existence.

24.8 Edge Cases

A partial eBPF program load failure (verifier rejects mid-update) must not leave a half-loaded program active. A rule that becomes ineligible after a reload must transition its flows to the default path without a gap in enforcement.

24.9 Failure Analysis

An eBPF program load failure falls the entire affected flow set back to the default path with an alert — this is the documented degradation path, not a silent capability loss. Any I13 verdict-mismatch report is a P1 defect, since it means two dataplanes are enforcing two different policies simultaneously.

24.10 Operational Notes

Metrics: xdp_verdict_mismatch_total (must stay 0 in production), xdp_program_load_ failed_total. Deployment note: XDP is opt-in per interface, defaulting off (ADR-09).

28. Operational Readiness

Metrics: every counter/gauge named in §7 (invariant telemetry) and each phase's N.10 is exported via the Prometheus text-exposition endpoint on nf-control (ADR-31 — folded here as the operational consequence of that decision). Tracing: tracing- crate spans (ADR-30) correlate a log line to a conntrack zone/flow ID end to end. Structured logging: JSON subscriber output, one event per invariant violation, ALG rewrite failure, and reload outcome. Dashboards: one per subsystem (classifier, conntrack, NAT, DDoS, DPI, transition), each keyed to the metrics above. Alerting philosophy: alert on invariant-violation counters (§7) crossing zero, on M-series targets (§32) breaching their gate, and on the FM-class detection signals (§27) — never on raw traffic-volume alone, which is too noisy to page on.

SLOs: 99.95% inline uptime (§4); p99 added latency within the default-path or XDP- path targets of §4 depending on which is active; 0 unresolved I1–I14 violations in any rolling 24 h window.

Incident response: an I8 (nondeterminism) or I13 (fastpath/default-path mismatch) violation is a P1 page — both mean two code paths are enforcing two different policies. An FM-1/FM-2 (table/pool exhaustion) is a P2 unless sustained past the SLO window.

Named runbooks (one file per entry under docs/runbooks/, cross-referenced from §27): Conntrack Table Full (FM-1) — raise nf_conntrack_max-equivalent ceiling, tune established-timeout, enable SYN proxy. NAT Pool Exhaustion (FM-2) — add public IPs, enable PBA, cap per-host connections. ALG Misbehavior (FM-3) — disable the specific ALG, fall back to plain NAT. Rule Denies Legitimate Traffic (FM-4) — use nfctl trace to find the offending rule, reorder. DDoS Attack (FM-5) — enable/tune SYN proxy, apply temporary source blocklist. Asymmetric Routing (FM-7) — apply policy- based routing for symmetry, or accept the deferred conntrackd-style sync (§39).

Backup/restore: the ruleset source (DSL) is the backed-up artifact, not the compiled bytecode or the conntrack table — conntrack state is deliberately not persisted across restart (§4 storage-amplification row), so restore means "reload the last-known-good ruleset," not "restore flow state."

Deployment topology: single-box inline default; containerized control-plane with kernel/eBPF dataplane split for the Kubernetes-adjacent topology (cross-ref §35 vs. Cilium). Canary/rolling-upgrade/rollback: a new binary version is canaried on a fraction of ECMP-hashed traffic before full rollout (§33); rollback is a binary downgrade plus ruleset reload, safe because of I10's atomicity; migration between wire- protocol versions follows §29.

29. Compatibility & Versioning

Wire compatibility: the nf-control binary protocol (ADR-21) is versioned independently of the in-memory RuleSet/ConntrackEntry layouts (§11); a MINOR wire- version bump is additive-only (new optional fields), a MAJOR bump may break decode and requires a documented migration. Storage: conntrack has no persistent storage by design (§4); ruleset DSL source is the only durable artifact, versioned via git plus CHANGELOG.md. Schema evolution: Match/Action/ProtoState/AllocationStrategy enum variants are additive-only within a MAJOR version (§11's per-type compatibility notes); removing a variant is a MAJOR-version event. API stability: the nfctl CLI's JSON output is stable within a MAJOR version; the underlying binary wire format may change MINOR-to-MINOR as long as nfctl itself is upgraded in lockstep with nf-control. Migration: a MAJOR wire-version upgrade requires a documented dual- read window (old and new control-plane binaries both accepted) sized to the slowest operator's upgrade cadence. Deprecation policy: a feature flagged for removal carries one full MAJOR-version deprecation window with a tracing-emitted warning on every use. SemVer policy: MAJOR = breaking wire/schema change; MINOR = additive feature (new ALG, new transition tech, per ADR-26 feature flags); PATCH = bug fix, no interface change. Rolling-upgrade guarantees: because conntrack state is not persisted (§4), a rolling upgrade of the dataplane process necessarily resets in-flight connections unless a future state-sync mechanism (§39, conntrackd-style) is un- deferred — this is a documented, current-state limitation, not a hidden one.

30. Testing & Verification Strategy

Unit: per-crate, focused on pure functions (Match::test, FiveTuple::reverse, checksum-update arithmetic). Integration: cross-crate flows (a packet through the full five-hook path with NAT and conntrack live). Property: Match/Action combinators tested against algebraic properties (e.g., idempotent SNAT-then-reverse- SNAT). Differential: against nftables (ADR-11) on the curated corpus (M12) — the primary conformance oracle. Fuzzing: cargo-fuzz/libFuzzer targets on every parser (packet, DSL, ALG payloads), nightly 24 h canary (ADR-24, §25). Chaos: concurrent- reload-under-load stress (I10), conntrack-race stress (I1/I14), simulated NIC-driver packet reordering. Deterministic replay: nf-verifier replays a recorded trace and asserts I1–I14 after every packet (§7's debugging methodology) — this is also how a production incident is reproduced offline. Soak: 30-day synthetic-traffic canary (§25) watching for memory growth and invariant drift. Fault injection: simulated partial eBPF-load failure (§24 N.9), simulated ALG-parser malformed input (§20 N.8), simulated NAT-pool exhaustion (§17 N.9). Conformance: the bucket suite under conformance/buckets/ (§10), one bucket per subsystem, gated per-PR. Performance- regression gating: every M-series target (§32) is asserted in CI via nf-bench (criterion); a regression beyond a target's threshold blocks merge. 33. Scalability Analysis

Constant regardless of scale: per-packet classifier/conntrack/NAT costs (O(1)/ O(log R), P9) — these do not grow with connection count, only with rule count (log R). Grows with scale: conntrack memory (linear in active-flow count, §36 item 1), hash- bucket count (sized to keep collision chains short, §36 item 2), NAT-pool contention (grows with subscriber count per public IP, mitigated by PBA, §17). Named bottlenecks, in order: (1) conntrack table occupancy (I5, the defining property of §4) is the first ceiling reached; (2) rule-evaluation cost at very high R (mitigated to O(log R) by the decision tree, §14, but the tree-compile cost itself grows with R); (3) per-bucket lock contention under an extreme single-bucket hot spot (ADR-13's documented lever: shard to sub-locks). Horizontal scaling: ECMP-hashed traffic across multiple boxes, each with an independent conntrack table — correct only for symmetric routing (FM-7); asymmetric routing requires the deferred conntrackd-style sync (§39). Vertical scaling: baseline is single-NUMA-node, ≤32 cores (§4); beyond that, ADR-13's rejected-alternative regime (full RCU) becomes the right call, not per-bucket spinlocks. Sharding/partitioning: the conntrack table can be sharded by 5-tuple hash across NUMA nodes as a documented future lever, not implemented in Phase 0–13. Coordination overhead: horizontal scaling's coordination cost is exactly the conntrackd-sync problem (§39) — the practical ceiling of a single box is the conntrack-table/PPS product in §36; the practical ceiling of a fleet is that coordination overhead. Levers beyond the ceiling: XDP fastpath (§24) for PPS; PBA (§17) for NAT-pool pressure; deferred hardware NIC offload (§39) once single-box PPS is fully exhausted.

34. Mental Models & First Principles

  • MM1. "The conntrack table is the constitution; every hook is a branch of government that must consult it before acting." Predicts: any hook that maintains parallel state will eventually disagree with another hook. Bug class without it: split-brain flow state. Applies in §7 (I1, I2) and §3.
  • MM2. "A Verdict is a monad with one absorbing element per terminal state." Predicts: Continue is the only non-terminal value; everything else short-circuits the remaining hooks. Bug class without it: a rule author assumes an implicit Accept on fallthrough. Applies in §8.2 and §13.
  • MM3. "NAT is a pure function of (tuple, pool-state) at the moment of first packet; every subsequent packet just replays the recorded mapping." Predicts: the interesting bugs are all in first-packet allocation, not steady-state rewriting. Bug class without it: debugging effort misdirected at the rewrite path instead of the allocator. Applies in §8.6 and §17.
  • MM4. "A state machine's safety property is exactly its transition table's completeness — an unlisted edge is a security bug, not a missing feature." Predicts: any input triggering an unlisted transition is either a bug or an attack. Bug class without it: silently permissive fallback on unrecognized packet sequences. Applies in §7 (I4) and §15.
  • MM5. "An ALG's privilege boundary is the shape of the data structure it can create, not a runtime check." Predicts: bounding an ALG to Expectation-creation only (not general rule injection) closes an entire vulnerability class by construction. Bug class without it: CVE-2002-0985-style arbitrary firewall-rule injection. Applies in §6 (P7) and §20.
  • MM6. "A cookie is a stateless credential; verifying it must cost less than storing the state it stands in for." Predicts: SYN-proxy viability depends on cookie-verify cost staying far below conntrack-insert cost. Bug class without it: a "DDoS mitigation" that itself becomes the resource-exhaustion target. Applies in §21 and §36 (item 6).
  • MM7. "Every fastpath is a claim of equivalence, and an unverified claim of equivalence is a policy bug waiting to happen." Predicts: any dataplane acceleration (XDP, hardware offload) needs a differential test against the reference path, not just a throughput benchmark. Bug class without it: silent policy divergence between fast and slow paths. Applies in §7 (I13) and §24.
  • MM8. "Capacity planning is arithmetic on §4's numbers, not a separate art." Predicts: every operational ceiling (memory, PPS, subscriber count) is derivable from the System Constraints table without new assumptions. Bug class without it: under-provisioning discovered in production instead of in the capacity model. Applies in §4 and §36.

Linux netfilter/nftables made the opposite bytecode-VM tradeoff earliest — generic opcode dispatch for maximal rule expressiveness — winning wherever operator-authored rule flexibility matters more than raw per-packet dispatch cost (the everyday Linux gateway/router case). OpenBSD pf made scrub-first normalization the load-bearing default a decade before it was common elsewhere, winning in a security-first, single- implementation environment where fragmentation-evasion resistance outweighs the extra reassembly-buffer memory. Cilium made the eBPF map the state store from day one, winning in Kubernetes-native environments where service-mesh-scale churn (thousands of pod IPs appearing/disappearing) outpaces what a traditional conntrack table's provisioning model assumes. VPP made full kernel bypass and vectorized (batched) node dispatch the baseline, winning at the 100 Gbps+ dedicated-appliance end where even XDP's per-packet overhead is too much and the kernel's routing/ARP integration this design delegates to (§1) is deliberately discarded instead.

36. Back-of-Envelope Capacity Model

  1. Conntrack entry memory: 10,000,000 entries × 240 B/entry (§11 layout + alignment) = 2.4 GB (chained from §4's entry ceiling).
  2. Hash-bucket memory: buckets sized 8× peak load to keep collision chains short = 80,000,000 buckets × 16 B (pointer + spinlock) = 1.28 GB.
  3. Total conntrack subsystem memory: 2.4 GB + 1.28 GB ≈ 3.7 GB — comfortably under a typical 16–64 GB firewall appliance (§4).
  4. Baseline throughput → packets/sec: 10 Gbps ÷ (1500 B × 8 bits) = 833,333 pps (§4's baseline row).
  5. Per-packet CPU budget at 10 Gbps, one core: 1 ÷ 833,333 pps = 1.2 µs/packet; measured path cost (classifier 100 ns + conntrack 100 ns + NAT 200 ns + rule-eval 100 ns ≈ 500 ns) leaves ~2.4× headroom.
  6. SYN-proxy worst-case CPU: M7's 2,000,000 SYN/s × ~50 ns cookie-verify cost = 100 ms CPU/sec ≈ 10% of one core — sustainable during a flood.
  7. Control-plane FD headroom: 65,536 FDs ÷ 1 FD per management session ≈ 65,536 concurrent CLI/API sessions — over-provisioned; the real ceiling is the control- plane thread pool, not FDs.
  8. Rule-set bytecode footprint: 100,000 rules × ~64 B compiled bytecode/rule ≈ 6.4 MB — fits inside a modern server's 8–32 MB L3 cache, explaining the < 100 ns rule-eval target (M2).
  9. CGN port math: one public IPv4 has 64,512 usable ports (65,535 − 1,023); a 1,000-port PBA block yields 64 subscribers per public IP at the default block size (§17.4).
  10. XDP fan-out at minimum frame size: 100 Gbps ÷ (64 B × 8 bits) = 195,312,500 pps worst case, i.e. a 5.1 ns/packet budget — explaining why XDP (§24), not the default path (~1 µs/packet), is required to reach the M10 stretch target.

38. Alternative Architectures (Roads Not Taken)

Alternative 1 — Full kernel-bypass, DPDK/VPP-first.

NIC ──DMA──▶ [ DPDK PMD ] ──▶ [ VPP-style node graph: classify─NAT─policy ] ──▶ NIC
              (no kernel network stack touched at all)

Regime where it wins: dedicated appliances targeting sustained 100 Gbps+ with no need for kernel routing/ARP integration. Real system: VPP/DPDK-based vRouters and appliances. Rejected here because Phase 0–11 need incremental adoption on existing Linux estates (§1 deployment model) and kernel-integration for routing/ARP (§1 boundaries) — XDP is added as a stretch (§24) precisely to get some of this benefit without discarding the kernel integration baseline.

Alternative 2 — eBPF/XDP-only, no default path.

NIC ──▶ [ XDP program: classify + conntrack (eBPF maps) + NAT ] ──▶ NIC
         (netfilter/default path removed entirely)

Regime where it wins: cloud-native L4 NAT/load-balancing at very high PPS with limited L7 richness required (Kubernetes service dataplanes). Real system: Cilium, Katran. Rejected here because DPI (§22) and full ALG payload rewriting (§20) exceed current eBPF-verifier expressiveness — I13's fastpath/default-path parity requirement exists precisely because this alternative cannot yet cover the full rule surface.

Alternative 3 — Centralized SDN control plane, dumb dataplane.

[ Central controller: computes per-flow decision ]
        │ pushes decision, per new flow
        ▼
[ Dataplane switch: applies pushed decision, no local policy engine ]

Regime where it wins: large multi-tenant data centers where centralized visibility and consistent policy across thousands of hosts outweighs per-box autonomy and latency. Real system: OpenFlow/ONOS-style SDN firewalls, cloud VPC Security-Group control planes. Rejected here because a per-new-flow controller round-trip breaks this design's p99 added-latency budget (§4) for a single inline box — this system's policy evaluation must stay local (P3, P4).

Alternative 4 — Formally-verified separation-kernel firewall.

[ seL4-style microkernel ]
   ├─ isolated component: packet classifier (proven)
   ├─ isolated component: NAT engine (proven)
   └─ isolated component: conntrack (proven)
   (inter-component channels formally verified, not just tested)

Regime where it wins: certification-driven government/defense deployments where a mathematical isolation proof outweighs development velocity. Real system: seL4-based and Muen separation-kernel firewalls. Rejected here because a full formal model of the whole system (ADR-23's rejected alternative) is disproportionate to the 47-week, 14- phase timeline (§1) and this project's iteration-speed goal — differential/property/ fuzz testing (§30) is the chosen tradeoff instead.

40. Glossary

  • 5-tuple: (src_ip, dst_ip, src_port, dst_port, proto), the flow-identity key.
  • ALG: Application-Layer Gateway; rewrites embedded addresses in application payloads.
  • BPF/eBPF: (extended) Berkeley Packet Filter; in-kernel verified bytecode execution.
  • CGN: Carrier-Grade NAT; many subscribers share one public IPv4 address.
  • Conntrack: the connection-tracking subsystem; the single source of truth for flow state (P2).
  • CT zone: an isolation context for overlapping address spaces (I9).
  • DDoS: Distributed Denial of Service.
  • DNAT: Destination NAT; rewrites destination address/port, applied at PREROUTING.
  • DPI: Deep Packet Inspection; opt-in application-protocol identification (§22).
  • DS-Lite: Dual-Stack Lite; IPv4-in-IPv6 tunneling to an AFTR (RFC 6333).
  • Endpoint-independent mapping: same NAT mapping regardless of destination (RFC 4787).
  • Endpoint-dependent mapping: a distinct NAT mapping per destination (symmetric NAT).
  • Expectation: a bounded, single-fire pending conntrack entry created by an ALG (I7).
  • Five-hook model: PREROUTING/INPUT/FORWARD/OUTPUT/POSTROUTING (P1).
  • Full-cone NAT: endpoint-independent mapping + endpoint-independent filtering.
  • Hairpinning: internal → own public IP → internal traffic flow (§18).
  • Helper: the trait behind every ALG/DPI/transition extension (P14, §11).
  • IPset: a hash-accelerated set of addresses/ranges for O(1) match (§14).
  • MAP-E: Mapping of Address and Port with Encapsulation (RFC 7597).
  • MAP-T: Mapping of Address and Port with Translation (RFC 7599).
  • Masquerade: SNAT to the current egress-interface address, re-resolved on change.
  • MSS clamping: rewriting the TCP MSS option to fit through a tunnel.
  • NAT: Network Address Translation.
  • NAT-T: NAT Traversal for IPsec (RFC 3948; ESP wrapped in UDP 4500).
  • NAT64: stateful IPv6-to-IPv4 translation (RFC 6146).
  • netfilter: the Linux kernel hook framework this design's default path integrates with.
  • nftables: the modern netfilter userspace/bytecode-VM tooling; the conformance oracle (ADR-11).
  • PAT: Port Address Translation, a synonym overlapping with NAPT/NAT.
  • PBA: Port Block Allocation; contiguous per-subscriber port ranges for CGN (§17).
  • Path MTU (PMTU): the smallest MTU along a path; discovered via ICMP (RFC 8201).
  • pf: the OpenBSD packet filter; source of the scrub-first design lesson (ADR-20).
  • Port-restricted NAT: filtering that additionally requires matching the prior destination port.
  • RFC 4787 / 5382 / 5508: NAT behavioral-requirements RFCs for UDP/TCP/ICMP respectively.
  • RST: TCP reset segment; terminates a connection regardless of sequence state (I4).
  • SACK: TCP Selective Acknowledgment option.
  • SipHash: the keyed pseudorandom function used for the conntrack hash and SYN cookies (P12).
  • Slot: the internal hash-bucket linked-list node owning one ConntrackEntry (§11).
  • SNAT: Source NAT; rewrites source address/port, applied at POSTROUTING.
  • STUN: Session Traversal Utilities for NAT (RFC 5389); NAT-mapping discovery.
  • SYN cookie / SYN proxy: cryptographic-cookie-based SYN-flood defense (I11, §21).
  • Symmetric NAT: address+port-dependent mapping and filtering (ADR-15 opt-in).
  • TCP Fast Open: an extension allowing data in the initial SYN.
  • TLS SNI: the Server Name Indication field in a TLS ClientHello, extractable by DPI.
  • Verdict: the terminal (or Continue) value returned by a hook pass (§8.2).
  • XDP: eXpress Data Path; the pre-sk_buff kernel fastpath hook (§24).
  • Zone: see CT zone.
