Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust (stable channel, min 1.78)

Rejected

C++, Go, Java, Python

When the rejected choice is right

Go wins when team velocity > raw throughput, operator graph is small, and GC pauses < 5 ms are acceptable; Java wins for large existing JVM ecosystems with mature IVM libraries (e.g., Noria-JVM or Flink-based solutions)

Why: Memory safety without GC; zero-cost abstractions; ownership model maps onto Capability/Trace lifetime semantics; Arc<RwLock<T>> and trait objects align with operator abstractions

ADR-02

Build system

Chosen

Cargo workspace; one workspace root, one Cargo.toml per crate

Rejected

Bazel, Buck, CMake

When the rejected choice is right

Bazel wins when the project spans multiple languages (Rust + C++ SIMD kernels + Python bindings) and hermetic reproducibility across polyglot toolchains is required

Why: Cargo is the standard Rust build tool; workspace unifies the 13 crates; no cross-language build needed

ADR-03

Dependency policy

Chosen

Minimal pinned deps in Cargo.lock; no transitive dep may be left un-audited via cargo deny; cargo deny check in CI

Rejected

Vendoring everything, no external deps

When the rejected choice is right

Full vendoring wins in air-gapped environments (regulated finance, defense) where internet access is absent and supply-chain auditability requires a complete offline dep tree

Why: Balances reproducibility with ecosystem leverage; cargo deny enforces license and advisory constraints

ADR-04

Crate structure

Chosen

13 domain crates as listed in the spine + integration test crate ird-tests

Rejected

Single crate, feature-flags

When the rejected choice is right

Single-crate wins for a proof-of-concept or research prototype where build time and compile-unit overhead matter more than layering discipline; feature-flags suffice when the operator set is small and stable

Why: Enforces dependency layering (ird-core has zero upward deps); enables fine-grained compilation and testing

ADR-05

Logical timestamp type

Chosen

u64 epoch for Phase 1–8; (u64,u64) product time Phase 9+

Rejected

Wall-clock SystemTime, UUID, vector clock

When the rejected choice is right

Vector clocks win when causality across distributed, truly concurrent input streams must be captured without a global coordinator assigning sequence numbers; SystemTime wins for time-series views where human-readable timestamps are the domain primary key

Why: Product timestamps support nested scopes (outer = transaction, inner = sub-step); lattice laws easily verified on integer pairs

ADR-06

Diff type

Chosen

Diff(i64) newtype

Rejected

i32, f64, arbitrary ring element

When the rejected choice is right

f64 (or a semiring over reals) wins in probabilistic / approximate query processing (e.g., count sketches, weighted aggregates) where fractional multiplicities are semantically meaningful

Why: 64-bit signed integer handles all practical multiplicities; newtype prevents accidental arithmetic; upgrade path to generic ring deferred to Phase 14

ADR-07

Batch storage format (in-memory)

Chosen

Sorted Vec<(Key, Val, Timestamp, Diff)> inside Batch; spine stored as Vec<Arc<Batch>>

Rejected

B-tree, skip list, hashmap

When the rejected choice is right

B-tree wins when the workload is predominantly random point updates (high insert/lookup ratio) and sorted scans are rare; a hash map wins for pure point-lookup-only arrangements with no range queries

Why: Sort enables binary search and cursor merge; Arc sharing avoids copy on join; simple to reason about compaction

ADR-08

Batch merge strategy

Chosen

Logarithmic merging (powers-of-two size classes)

Rejected

LSMT-style compaction, fixed-size tiers

When the rejected choice is right

LSMT-style tiered compaction wins at very high write rates (>10 M rows/s) where write amplification must be minimized and occasional large compaction pauses are acceptable

Why: O(log N) batches; O(N log N) amortized merge cost; bounded lookup depth; mirrors differential-dataflow reference implementation

ADR-10

Arrangement persistence (checkpoints)

Chosen

Periodic snapshot of Batch files (sorted binary) + frontier metadata

Rejected

Full re-index from WAL only, RocksDB

When the rejected choice is right

RocksDB wins when arrangement sizes exceed available RAM (>100 GB) and require LSM-backed on-disk arrangement access with block cache; also wins when WAL and arrangement storage must be unified under one transactional store

Why: Bounds recovery time (I10); WAL tail replay is short; avoids RocksDB dependency and its GC complexity

ADR-11

Serialization (wire protocol / IPC)

Chosen

postcard (no-std compatible, compact binary) for internal messages; serde derive macros

Rejected

protobuf, capnproto, JSON, bincode

When the rejected choice is right

Protobuf wins when interoperability with non-Rust clients (Python, Java, Go) is required and schema evolution (field addition, deprecation) must be language-agnostic; Cap'n Proto wins when zero-copy deserialization is critical on the hot path

Why: postcard + serde covers both in-memory and network serialization with minimal boilerplate; postcard's format is stable and size-efficient

ADR-12

Async / concurrency model

Chosen

tokio async runtime for ird-server network I/O; single-threaded cooperative scheduler for dataflow operators (Phase 5); Arc<RwLock<T>> for shared Arrangements

Rejected

rayon, crossbeam only, actor model

When the rejected choice is right

Rayon wins when the operator graph is embarrassingly parallel per key range and lock-free work-stealing across cores is more important than deterministic scheduling; actor model wins when each operator must be independently fail-stoppable with message-based isolation

Why: tokio for I/O concurrency; deterministic single-threaded scheduler avoids non-determinism in operator execution (P8); multi-threaded dataflow deferred post-Phase 14

ADR-13

Channel implementation

Chosen

tokio::sync::mpsc bounded channels between operators

Rejected

crossbeam channel, flume, std channel

When the rejected choice is right

crossbeam::channel wins in a fully synchronous, thread-per-operator model where async overhead is undesirable and select!-based fan-in is required across many channels simultaneously

Why: Integrates with tokio scheduler; bounded capacity enforces back-pressure; async-aware blocking

ADR-14

SQL parsing

Chosen

sqlparser-rs crate (Apache-2.0)

Rejected

nom hand-rolled parser, pest grammar, ANTLR

When the rejected choice is right

A hand-rolled nom parser wins when the supported SQL is so constrained (3–5 constructs) that a dependency is heavier than the grammar itself, or when parse error messages must be richly customized for a domain-specific UX

Why: sqlparser-rs handles the supported SQL subset with correct AST; avoids maintaining a grammar; well-tested; dialect-configurable

ADR-15

Logging

Chosen

tracing crate with structured spans; tracing-subscriber with JSON formatter in production

Rejected

log crate, slog, env_logger

When the rejected choice is right

The log crate wins in embedded or resource-constrained deployments where tracing's span overhead and subscriber allocation are measurable on the hot path and only severity-filtered text output is needed

Why: Structured spans capture operator identity, frontier values, batch sizes; integrates with OpenTelemetry; aligns with P10 observability

ADR-16

Metrics

Rejected

When the rejected choice is right

StatsD wins when the deployment already aggregates push-based metrics and pull-based Prometheus scrape intervals (15 s) are too coarse for real-time latency alerting requiring sub-second event emission

Why: Prometheus scrape endpoint; exposes per-operator frontier lag, arrangement byte size, update throughput (P10); facade allows swapping exporter

ADR-17

Jaeger SDK direct wins when the full deployment uses Jaeger exclusively and the OTLP abstraction layer's overhead is measurable in high-frequency span emission scenarios (>100 K spans/s)

When the rejected choice is right

Fuzz testing

Rejected

When the rejected choice is right

ADR-20

Differential correctness oracle

Chosen

Dedicated test harness in ird-tests: random delta sequences → compare peek(t) vs. batch-recompute on same inputs; validates I1

Rejected

Manual golden-file tests only

When the rejected choice is right

Manual golden-file tests win when the oracle's batch recompute is itself non-trivial (e.g., requires an external database to evaluate the SQL ground truth) and automated generation cannot reliably produce the reference output

Why: Automated oracle catches retraction bugs, join edge cases, compaction errors; runs in CI on each push

Benchmarking

Chosen

ADR-23

Error handling

Chosen

Rejected

When the rejected choice is right

Custom enums by hand win when the error taxonomy is small (< 5 variants), the crate has zero tolerance for proc-macro compile-time cost, and the error types must be no_std compatible for embedded targets

.deb/.rpm packaging, Homebrew

ADR-25

Container support

Chosen

Dockerfile using rust:1.78-alpine builder + scratch final image; WAL and checkpoint directories as mounted volumes

Rejected

When the rejected choice is right

No container wins for bare-metal high-performance deployments where container overhead (namespaces, cgroups, image layering) adds measurable latency jitter on NUMA systems running the dataflow scheduler at high frequency

Why: Minimal image size; volume mounts decouple data from container lifecycle; aligns with P9 (WAL as source of truth)

Alternative Architectures (Roads Not Taken)

Alt-A — Periodic full recomputation (batch refresh).

inputs --> [ store ] --(every T seconds)--> recompute whole view from scratch --> publish

Wins when: views are small, freshness tolerance is minutes, and engineering simplicity dominates (nightly BI rollups). Embodied by: classic materialized-view REFRESH in PostgreSQL/Oracle. Rejected because: the core requirement is sub-5 ms p95 incremental latency (§4.1); full recompute is O(view) per refresh and cannot meet it.

Alt-B — Trigger-based incremental view maintenance in an RDBMS.

base table --row trigger--> hand-written delta SQL --> update summary table

Wins when: you live inside an existing RDBMS, the views are few and simple, and you want no new infrastructure. Embodied by: hand-rolled IVM with triggers, some commercial IVM extensions. Rejected because: triggers do not compose across joins/aggregates correctly under concurrency, and they lack a progress/frontier model (MM3); correctness becomes per-view bespoke rather than provable (MM4).

Alt-C — Partial materialization with upqueries (Noria model).

reads --miss--> upquery recomputes cold state --> fill cache --> evict under pressure

Wins when: the hot working set is far smaller than the full view universe and reads dominate (web app read caches). Embodied by: Noria. Rejected (deferred) because: upquery latency is unpredictable (cold reads pay recompute) and complicates the incremental==batch oracle; ird chooses full arrangements for predictable latency, deferring eviction (Deferred Features Register).

Alt-D — Distributed timely dataflow across a cluster.

inputs --partition--> worker[0..N] each runs operator graph; exchange edges shuffle by key

Wins when: a single machine cannot hold the arrangements or sustain the throughput (multi-TB state, >1 M updates/s). Embodied by: Naiad, Materialize cloud. Rejected because: distribution adds network exchange, fault-tolerant coordination, and rack-aware placement (all deferred); the blueprint targets a single embeddable process where the dataflow loop stays single-threaded (MM7).
