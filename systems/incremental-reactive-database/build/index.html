⬜ Phase 1 — core types: Diff, Timestamp, Update, Collection

Objectives
  • Define Diff(i64), Timestamp, Update<D>, Collection<D>, Row, Key, Val in ird-core.
  • Timestamp satisfies a join-semilattice: join, meet, less_equal; partial order; antichain-compatible.
  • Collection<D> is a typed stream of Update<D> triples; no I/O, no allocation policy.
  • All types are Clone + Debug + PartialEq; Diff and Timestamp also Copy + Ord (Timestamp: partial order only).
  • Property tests cover diff arithmetic and timestamp lattice laws.
  • Zero external I/O, zero persistence; this crate is a dependency leaf.
Deliverable
  • ird-core compiles with cargo build.
  • All lattice-law and diff-arithmetic property tests pass (cargo test -p ird-core).
  • Types importable by all other crates via use ird_core::{Diff, Timestamp, Update, Collection, Row, Key, Val}.

Pitfalls
  • Timestamp total-order confusion: using Ord instead of less_equal causes join/meet to silently use lexicographic order for product times; use the trait method exclusively.
  • Diff silent truncation: wrapping arithmetic on Diff produces incorrect multiplicities; use checked_add or saturating_add with explicit policy.
  • Row equality via Vec<Value>: float Value variants break PartialEq; disallow floats or use a bit-exact repr.
  • Arc<str> clone cost: cloning Row in hot paths is cheap but not free; measure before adding Cow.
  • Lattice commutativity assumption: ProductTime join is commutative, but custom timestamp impls may not be; test both orderings.

⬜ Phase 2 — differential collections + consolidation

Objectives
  • Implement ird-collection: accumulate Update<D> triples; consolidate to canonical form.

  • Implement as_of(t: &T) -> Multiset<D>: sum diffs over all times <= t per record.

  • as_of returns the correct multiset at any logical time.
  • ird-collection usable as a dependency in Phase 3 operators.

Pitfalls
  • Sort instability on equal keys: if two updates have same (data,time) and different diffs, sort order affects summing correctness only if the scan is buggy; use stable grouping, not sort order, for summation.
  • as_of with partial order: naively using <= on total-ordered proxy will miss concurrent updates on a product lattice; must use time.less_equal(t) not time <= t.
  • HashMap non-determinism in as_of: HashMap iteration order is randomized; multiset equality must compare by key set, not iteration order.
  • Zero-diff entry leak: consolidation must drop entries where summed diff == 0; leaving them causes phantom records in join lookups (Phase 8).
  • D: Ord requirement for sort: not all data types have a natural Ord; encode Row with a stable byte encoding for sort key.
  • Consolidation of already-consolidated data: must be a no-op; inserting duplicate (data,time) pairs violates canonical form if not re-consolidated.

⬜ Phase 3 — stateless operators

Objectives
  • Implement stateless operators in ird-operator: map, filter, flat_map, concat, negate.
  • Each operator is a pure per-update function: consumes Update<D>, emits zero or more Update<E>.
  • Preserve time and diff unchanged (map/filter/flat_map transform only data).
  • negate flips diff sign; concat is union (append two collections).
  • Establish commutativity with consolidation: op(consolidate(c)) ≡ consolidate(op(c)).
  • No operator holds state; no references to frontier, arrangements, or persistence.
Deliverable
  • ird-operator compiles; all operator unit tests pass.
  • apply_batch applies any stateless operator to a DiffCollection.
  • Commutativity with consolidation verified by property tests.
  • concat + negate implement multiset union/difference, usable by Phase 5 dataflow.

Pitfalls
  • flat_map diff propagation: all emitted outputs from one input update must carry the same diff; emitting with diff=1 always is wrong under retractions — the input diff must be forwarded.
  • map non-injectivity: if two distinct inputs map to the same output, consolidation merges their diffs; this is correct behavior but confuses developers expecting bijective maps.
  • filter on consolidated input: filtering after consolidation is safe; filtering before may pass zero-diff entries that are then consolidated away — acceptable but wasteful.
  • negate of zero: Diff(0).neg() = Diff(0); no panic, but the entry is still useless; consolidation drops it.
  • Closure captures: MapOp with closures capturing mutable state violates the stateless invariant; F must be Fn not FnMut.
  • concat order-sensitivity: concat(a,b) and concat(b,a) are multiset-equal after consolidation but not byte-equal before; tests must consolidate before comparing.

⬜ Phase 8 — Incremental Join

Objectives
  • Implement JoinOp in ird-operator using the delta-join algorithm over two Arrangements from ird-arrange.
  • Symmetric delta handling: a new batch on the left side probes the right arrangement as-of that time; new batch on right probes left as-of that time.
  • Correctness under concurrent updates and retractions on both sides (I5).
  • This is the central IVM operator: join output at time t must equal the full equijoin of both input multisets as-of t.
