1. Goal

1.1 What Is Built

An incremental reactive database engine that keeps SQL-style materialized views correct under continuous change using differential dataflow. Relations are multisets of (row, logical-time, diff) update triples where diff is a signed multiplicity. View definitions compile to a dataflow of differential operators (map/filter/join/reduce/distinct) that consume input deltas and emit output deltas. Shared time-versioned arrangements hold keyed operator state. Progress frontiers signal when an output is complete for a logical time so a peek returns a result identical to recomputing the view from scratch over the same inputs.

1.3 Explicit Non-Goals

  • No distributed multi-node operation (single-process; partitioned execution deferred).
  • No OLTP row-level locking or MVCC.
  • No full SQL (CTEs, window functions, lateral joins deferred; see PhaseDeferred("Deferred Features Register")).
  • No PostgreSQL wire protocol compatibility (deferred; see PhaseDeferred("Deferred Features Register")).
  • No horizontal scaling / rack-aware placement (deferred; see PhaseDeferred("Deferred Features Register")).
  • No cost-based query optimizer (rule-based lowering only).
  • No user-defined functions with side effects.

1.10 Language Rationale — Rust (locked)

This is differential dataflow territory (Timely/Differential Dataflow are themselves Rust): an operator graph processing typed multiset deltas (data, time, diff) over shared time-versioned indexes (arrangements), where memory discipline and zero-copy delta movement decide whether large views stay maintainable. Rust gives trait-based operator composition, arena/columnar arrangement storage, exhaustive enums for the operator/diff taxonomy, and no GC on the per-delta hot path. The collection layer, operators, arrangements, progress tracking, plan compiler, view manager, and server are all Rust.

2.2 Historical and Architectural Significance

  • McSherry et al. (CIDR 2013) introduced differential dataflow as the first general IVM framework handling arbitrary iterative computation with retractions.
  • Naiad (SOSP 2013) established the progress/frontier model; almost all modern streaming systems (Flink, Kafka Streams, Materialize) descended from this model.
  • Materialize (the commercial product) is differential dataflow applied to SQL; building this system reproduces its core architecture.
  • The DBSP paper (VLDB 2023) reformalized differential dataflow as a circuit algebra (Z-sets, linear operators, fixpoint); this codebase implements the same ideas in operational Rust.
  • IVM is the foundational technique behind CDC pipelines, reactive dashboards, live query caches, and incremental build systems — all share the same signed-multiplicity delta model.

2.4 Production Engineering Concepts Exercised

  • Observability: per-operator frontier lag, arrangement byte size, output-behind-input delta — all measurable (P10).
  • Backpressure: dataflow channel capacity bounds; scheduler stalls when downstream is full.
  • Determinism under replay: identical outputs regardless of scheduling or batching (I9, I10).
  • Graceful degradation: arrangement compaction as memory pressure relief; admission control at server layer.
  • Conformance testing: Phase 14 oracle compares incremental output to from-scratch recompute — the gold-standard correctness test pattern for any IVM system.

After completing this project, a builder holds the following verifiable competencies:

  • Differential dataflow semantics (Phase 1–2): can derive the incremental form of any relational operator from first principles using signed-multiplicity algebra, and explain why diff subsumes insert/delete/update without special cases.
  • Progress and capability discipline (Phase 4–5): can design a correct progress protocol from scratch — including Capability RAII, antichain maintenance, and ProgressMsg batching — and diagnose a frontier stall from telemetry alone.
  • Arrangement and compaction design (Phase 6): can specify a time-versioned indexed store including its cursor API, logarithmic merge policy, and the since-frontier compaction invariant (I7); can prove compaction soundness by construction.
  • Stateful operator correctness under retractions (Phase 7–8): can write delta-join and reduce implementations that emit correct retractions when input decreases, and can oracle-test them using the batch-recompute equivalence principle (I1, I5, I6).
  • Incremental query compilation (Phase 9): can translate a relational plan to a differential operator graph, identify shared sub-expressions for arrangement reuse, and explain the SQL constructs that are not incrementally maintainable and why.
  • WAL-based crash recovery (Phase 12): can design a WAL framing format with CRC, a checkpoint protocol, and a replay procedure that guarantees I10 recovery equivalence; can inject and diagnose crash scenarios at any point in the write path.
  • Operational mastery of an IVM system (Phase 13–14): can read the full metrics surface (frontier lag, arrangement size, oracle divergence counter), follow a runbook to diagnose a production I1 violation, and redesign a view's plan to reduce arrangement memory under a constraint.

3.2 Subsystem Descriptions

ird-plan (SQL subset → differential plan). Accepts a CREATE VIEW SQL string; parses it into a relational AST; validates schema and type correctness; lowers each relational operator to a differential operator node (selection → filter, projection → map, equijoin → join, group-by/aggregate → reduce, distinct → distinct, union → concat); emits an Plan operator tree. Inputs: SQL text + schema catalog. Outputs: Plan (operator tree). No I/O, no state.

ird-input (base relation input handles). Owns one InputHandle per base relation. Accepts (Update, Timestamp) triples from the application or server layer; batches them by time; writes each batch to the WAL before forwarding into the dataflow; calls advance_to(t) to emit a ProgressMsg closing time t on that relation's output edge. Inputs: application delta stream. Outputs: Update batches + ProgressMsg into dataflow channels. Persistence boundary: WAL write happens here before dataflow entry.

ird-dataflow (operator graph + scheduling). Builds the physical operator graph from a Plan. Each Plan node becomes an Operator instance; edges become typed channels carrying (Update batch, ProgressMsg) pairs. A work-stealing or round-robin scheduler drives operators when input is available. Propagates ProgressMsg downstream when an operator's output frontier advances. Deterministic under any scheduling order (I9). Inputs: Plan, InputHandle connections. Outputs: operator instances + channel topology + scheduling loop.

ird-operator (stateless and stateful operators). Stateless: map, filter, flat_map, concat, negate — pure per-Update transforms, no operator state, commute with consolidation. Stateful: distinct, count, reduce, threshold — maintain a keyed Arrangement of input (and output for reduce) accumulated over time; on each input batch compute the delta between old and new output multiset and emit only that delta. Join (Phase 8) is a two-input stateful operator using two arrangements. Inputs: Update batches + frontier from upstream. Outputs: Update batches + frontier downstream.

ird-arrange (arrangements / traces). A Trace is an indexed, time-versioned multiset: a sequence of immutable, merge-sorted Batch objects keyed by Key, each entry (Val, Time, Diff). Supports as_of(t) cursor scans (sum diffs over times <= t) and key-range lookups. Shared across operators via Arc (one arrangement, many readers). Compaction merges batches below the since-frontier: any two times indistinguishable at or after the frontier are merged, bounding arrangement size (P7, I7). Inputs: Update batches from operators. Outputs: immutable Batch objects; cursor API for readers.

ird-time (frontiers + capabilities + progress protocol). Frontier is an antichain of Timestamp values: a compact lower bound on times an operator may still produce. Capability tokens grant the right to emit at times >= a given Timestamp; dropping a capability advances the frontier. ProgressMsg carries frontier updates along dataflow edges. An operator knows a time t is complete when its input frontier has advanced strictly past t on all input edges (I3, I5). Inputs: capability lifecycle events from operators. Outputs: ProgressMsg to downstream edges; frontier queries from operators and ird-query.

ird-view (materialized view manager). Registers ViewDef objects (name, SQL, plan, output arrangement). Builds the dataflow subgraph for each view. Maintains the output Arrangement as the output frontier advances. Multiple views may share upstream arrangements (P6, Phase 13 CSE). Exposes snapshot(view, t) returning the consolidated multiset at frontier-complete time t. Inputs: ViewDef registrations + dataflow output deltas. Outputs: maintained Arrangement; snapshot access API.

ird-storage (WAL + trace durability + recovery). WAL: append-only log of input Update triples (source of truth, I10, P9). Periodic checkpoints serialize arrangement Batch objects to disk. Recovery: load latest checkpoint, identify the consistent frontier, replay WAL tail from that frontier forward through the dataflow graph to reconstruct all arrangements. Recovery time is bounded by checkpoint interval. Inputs: Update triples from ird-input; Batch objects from ird-arrange. Outputs: WAL files + checkpoint files; recovery stream of Update triples.

ird-query (peek + changefeed). peek(view, t) blocks until the output frontier of view has advanced past t, then returns the consolidated multiset as_of(t) from the output arrangement — identical to a from-scratch batch recompute (I1, I4). changefeed(view) subscribes to consolidated output Update batches as the frontier advances: monotonic, gap-free, de-duplicated. Snapshot-to-changefeed boundary: a client may take a snapshot at t and then subscribe to all changes after t without missing updates. Inputs: output arrangement + frontier from ird-view. Outputs: PeekResult or Changefeed stream.

ird-server (define / insert / delete / peek / subscribe). TCP server exposing commands: DEFINE VIEW, INSERT INTO relation, DELETE FROM relation, PEEK view AT time, SUBSCRIBE view. Routes deltas to ird-input, view definitions to ird-plan + ird-view, reads to ird-query. Shares arrangements across overlapping views (CSE, Phase 13). Enforces admission + flow control. Exposes metrics: per-operator frontier lag, arrangement byte size, output-behind-input delta. Inputs: client TCP connections. Outputs: responses to peek/subscribe; metrics endpoint.

ird-cli (command-line driver). Thin binary over ird-server's client interface: define | insert | delete | peek | subscribe | explain subcommands. explain prints the operator plan for a view. Used for smoke tests and interactive development. Inputs: CLI args. Outputs: formatted table results or delta streams.

6. Design Principles

P1 — Incremental correctness equals batch

Statement. For every registered view and every frontier-complete logical time t, peek(view, t) returns the identical multiset that a from-scratch batch evaluation of the view's SQL over the inputs at times ≤ t would return. No approximation, no staleness tolerance, no "eventually correct."

Tradeoffs.

  • Operators cannot take shortcuts that lose precision; every retraction must propagate fully before output is final at t.
  • Correctness testing (Phase 14) is feasible: a batch oracle is always computable, so conformance is checkable via randomized differential testing.
  • Higher per-update work than approximate streaming systems, justified by the precision guarantee.

Operational implication. peek must block until the output Frontier has advanced past t (I3), guaranteeing I1. Peeking a time t before the output Frontier reaches it is an error, not a stale read.

Violation consequence. If a delta-join omits a retraction path, the maintained multiset accumulates ghost rows; peek diverges from batch. Detected by I1 conformance tests; silent in production without the oracle.

P2 — Process deltas, not data

Statement. Operators consume and emit Update<D> triples (data, time, diff). An operator's computational work is proportional to the size of the input delta batch, not to the total size of the relation.

Tradeoffs.

  • Arrangement (indexed state) is necessary for stateful operators (join, reduce) to answer "what does the other side look like at this time?" — arrangement memory is the cost of buying delta-proportional compute.
  • A large initial load is an extreme delta; cold-start cost is O(data). Only subsequent changes are cheap.

Operational implication. Arrange phase-5 scheduling so that full-snapshot computes at startup are throttled; thereafter monitor arrangement size (P10) to confirm bounded memory (P7).

Violation consequence. A reduce operator that re-scans all input rows on every arriving delta is correct (P1) but violates P2; throughput degrades linearly with relation size. Detectable via Phase 14 throughput benchmarks.

P3 — Retraction is first-class

Statement. A deletion is an Update with diff = Diff(-1). Every operator — map, filter, join, reduce, distinct — must be correct under negative diffs, not just under insertions. Multiplicities may go to zero or negative transiently before consolidation.

Tradeoffs.

  • Join delta-rules require two symmetric cases (delta on left × arrangement on right, and delta on right × arrangement on left), each producing output diffs with the same sign as the input diff. Extra code paths vs. insert-only operators.
  • Consolidation eliminates zero-multiplicity rows (I2); operators may produce transient negative multiplicities as long as the final consolidated output is non-negative for any valid multiset.

Operational implication. Every operator unit test (Phase 3, 7, 8) must include retraction sequences: insert a row then delete it; the output must reflect absence, not a ghost.

Violation consequence. An aggregate that only handles diff > 0 will accumulate excess counts on deletion, breaking I6 and I1. Detected by the fuzz test in Phase 14 (random insert/delete sequences).

P4 — Consistency via logical time

Statement. Outputs are defined at logical Timestamp values forming a partial order. A peek at time t reflects exactly the inputs with time ≤ t. No read ever sees a partial application of an update batch that spans multiple timestamps.

Tradeoffs.

  • Timestamps must be attached to every Update at ingestion; out-of-order or unlabeled updates are not permitted.
  • Wall-clock time is separate; the system does not guarantee that logical time t corresponds to any real-time bound without an external SLA.

Operational implication. InputHandle::advance_to(t) is the commitment that no future input will carry a time < t; callers must respect this contract. Violating it breaks I3 (monotone progress) and causes incorrect output.

Violation consequence. Inserting an update at time t - 1 after advancing to t silently corrupts the view: the Frontier has already passed t - 1, so the late update may be dropped or misplaced, producing an answer inconsistent with the actual input history.

P5 — Progress is explicit

Statement. Frontiers (antichains of Timestamp) flow along dataflow edges as ProgressMsg. An operator knows a time t is complete for an input edge when the edge's Frontier has advanced past t. No operator guesses; no wall-clock timeouts substitute for frontier advancement.

Tradeoffs.

  • Progress messages add protocol overhead on every edge; must be batched (see ird-time).
  • A stalled input (no new updates, no advance_to) stalls dependent operators; callers must advance even when sending no data.

Operational implication. Expose per-edge frontier lag as a metric (P10). Alert on frontiers that have not advanced for a configurable interval — this diagnoses stalled inputs, not system bugs.

Violation consequence. An operator that finalizes output at a time before the input Frontier has advanced past it will emit output for a time that may still receive updates, violating I4 and I1. Detected by correctness tests that advance inputs in steps and verify partial-time outputs.

P6 — Shared arrangements

Statement. A Trace / Arrangement is built once and shared (via Arc) across all operators and views that access the same key-indexed collection. Common sub-expressions in overlapping view definitions reuse the same arrangement rather than maintaining separate copies.

Tradeoffs.

  • Shared arrangements require a coordination mechanism for compaction: the since-Frontier of a shared Trace can only advance to the minimum over all readers' horizons. A slow reader blocks compaction, causing memory growth.
  • View creation at runtime must scan the existing arrangement graph for reuse opportunities (Phase 13 CSE).

Operational implication. Track per-arrangement reader count and since-Frontier. Alert when a reader's horizon lags significantly behind the global frontier — the lagging reader is blocking compaction (P7).

Violation consequence. Duplicate arrangements for the same collection multiply memory consumption proportionally to the number of views; defeating P7 bounded-memory property. Detectable via Phase 14 memory benchmarks.

P7 — Bounded memory via compaction

Statement. A Trace is periodically compacted below its since-Frontier: update triples at times no longer distinguishable (because all readers are past them) are consolidated and merged into fewer Batches. A long-running view does not accumulate unbounded history.

Tradeoffs.

  • Compaction is a background merge operation; it must not block foreground delta processing. Run compaction in a separate task; use copy-on-write Batch semantics.
  • Compaction correctness (I7): the answer at any time ≥ since-Frontier must be identical before and after compaction.

Operational implication. Expose arrangement size in bytes and number of Batches as metrics. Tune compaction thresholds (max Batch count, max uncommitted bytes) to keep memory bounded at a configurable cap.

Violation consequence. Without compaction, Trace memory grows proportionally to the total number of updates ever received — unbounded for a long-running database. Detected by Phase 14 memory benchmark run over many epochs.

P8 — Determinism

Statement. The maintained output multiset is a deterministic function of the input Update set and their Timestamp values. Different scheduling orders, batch sizes, or thread interleavings produce identical consolidated outputs.

Tradeoffs.

  • Operators must not use non-deterministic internal state (e.g., hash-map iteration order that affects output ordering must be neutralized by consolidation).
  • Determinism enables reproducible debugging: replaying the WAL always reproduces the same state (P9, I10).

Operational implication. Phase 14 fuzzing runs the same input sequence with different batch boundaries and scheduling permutations and asserts identical outputs. Any divergence is a determinism bug, not a concurrency race.

Violation consequence. A reduce operator that accumulates floats in arrival order produces different results under different scheduling; this breaks I9 and makes the WAL replay (I10) non-reproducible.

P9 — The input log is the source of truth

Statement. Base-relation deltas are appended to the WAL (ird-storage) at the time they are accepted. Arrangements and materialized view outputs are derived state, fully rebuildable by replaying the WAL from a checkpoint. No arrangement is the authoritative record of a fact.

Tradeoffs.

  • WAL replay time is bounded by checkpoint frequency; without checkpoints, full replay from the beginning is O(total history). Checkpoint strategy (Phase 12) is mandatory.
  • WAL must be crash-consistent: a partial write must not appear as a committed update. Use a framed record with a CRC and a commit marker.

Operational implication. Recovery procedure (Phase 12): load latest checkpoint → replay WAL tail → verify Frontier matches expected recovery time. Any divergence between replay result and checkpoint signals WAL or checkpoint corruption.

Violation consequence. If arrangement state is treated as authoritative and the WAL is not written, a crash loses updates permanently; recovery is impossible. Detected only at crash time — testing requires crash injection in Phase 12.

P10 — Observability by default

Statement. Every operator emits per-frontier advancement events, every Arrangement emits current size-in-bytes and Batch count, and every view emits output lag (current-time minus output-Frontier). These are structural, always-on metrics — not opt-in instrumentation.

Tradeoffs.

  • Metric emission adds per-operator overhead; use counters and gauges (not histograms) for the hot path; export via a background thread.
  • Metrics must not perturb the determinism guarantee (P8); they are side-channel outputs, never used in computation.

Operational implication. ird-server exposes a /metrics endpoint (OpenTelemetry Metrics format). Alerting rules: output-lag > threshold → input stall; arrangement-size > cap → compaction not keeping up.

Violation consequence. Without lag metrics, a stalled input Frontier is indistinguishable from a slow but live system; operators silently accumulate unprocessed updates. Operational impact: SLA breaches detected only by user-facing queries returning stale results.

P11 — Backpressure absorbs load, never unbounded buffering

Statement. Every producer/consumer edge in the system — dataflow channel (Phase 5), server admission path (Phase 13 AdmissionGate), changefeed subscriber queue (Phase 11/13) — is bounded. When a downstream consumer falls behind, the correct response is to signal the upstream producer to slow down, never to grow a queue without limit.

Tradeoffs.

  • Bounded channels convert a memory-growth failure mode into a latency/throughput failure mode (producers stall); this is deliberate — OOM is a harder failure to recover from than backpressure-induced latency.
  • Requires every producer path to handle a Backpressure / try_acquire failure explicitly; cannot assume send always succeeds.

Operational implication. channel_depth{edge_id} (Phase 5), AdmissionGate byte ceiling (Phase 13), and changefeed_buffer_bytes (Phase 13 T7) are the three load-bearing backpressure gauges; alert before any of them saturates, not after.

Violation consequence. A single slow changefeed subscriber or downstream operator that is allowed to buffer unbounded output turns a local slowdown into a global OOM (T7); detected only when the process is killed, not before. Phase 5's backpressure.rs test and Phase 13's test_admission_gate are the conformance checks.

P12 — The query surface is closed by construction

Statement. The supported SQL subset (§1.2, §9.1) is fixed and rule-based: every relational operator it admits has a known, statically-derivable differential operator (Phase 9 lowering table) with a provably correct delta rule (P3 DBSP δ-transform). No user-defined function with side effects, no cost-based optimizer choosing between semantically-different plans, no operator without a maintained incremental form is ever accepted.

Tradeoffs.

  • Rules out large classes of real-world SQL (window functions, recursive CTEs, arbitrary UDFs) that lack a known incremental maintenance strategy — explicit non-goals (§1.3), not oversights.
  • In exchange, every accepted query has a machine-checkable correctness argument (I1 oracle) and a bounded lowering algorithm (ADR-01 rule-based, not cost-based).

Operational implication. ird-plan's validate.rs rejects, at plan time, any construct outside the closed surface (PlanError::Unsupported*); the rejection is a design guarantee, not a missing feature to silently degrade.

Violation consequence. Accepting an operator without a known delta rule (e.g. an ad hoc window function) would either require unbounded state to maintain incrementally or silently fall back to full recompute, breaking P2 and P7 without warning. Rejected at Phase 9 validation instead of discovered in production.

8. Domain Model

8.1 Update Triple — The Atomic Unit

Every change in the system is an Update<D>:

Field Type Invariant
data D (Row / (Key,Val)) immutable after creation
time Timestamp must be >= capability held by sender
diff Diff(i64) nonzero before consolidation

Semantics: the collection at time t = { d : Σ_{s≤t} diff(d,s) > 0 } with multiplicity equal to that sum. Diff conservation (I8): sum of all diffs for (data, times ≤ t) equals the net multiplicity at t.

Worked example — insert then delete:

Update { data: Row[1,"Alice",30], time: T1, diff: +1 }   // insert
Update { data: Row[1,"Alice",30], time: T3, diff: -1 }   // retract

At T2: multiplicity = 1. At T4: multiplicity = 0. Consolidation at T4 yields no entry (zero diff dropped per I2).

Malformed example:

Update { data: Row[1,"Alice",30], time: T1, diff: 0 }    // INVALID — zero diff; must be rejected at ingestion

8.2 Timestamp and Lattice

Timestamp is a partially ordered type forming a lattice:

Operation Signature Contract
join(a,b) (T,T)->T least upper bound; a ≤ join(a,b)
meet(a,b) (T,T)->T greatest lower bound
less_equal(a,b) (T,T)->bool antisymmetric, transitive, reflexive

For Phase 1–8, Timestamp is a single u64 epoch (total order). From Phase 9 onward, product timestamps (u64, u64) support multi-level time (outer = transaction epoch, inner = operator sub-step).

Lattice laws (tested via property tests in Phase 1):

  • join(a,a) == a (idempotent)
  • join(a,b) == join(b,a) (commutative)
  • join(a, join(b,c)) == join(join(a,b), c) (associative)
  • a ≤ b ↔ join(a,b) == b

8.3 Frontier / Antichain State Machine

States:       OPEN ──advance──> ADVANCED ──advance──> ... ──close──> CLOSED
Invariant:    frontier is always an antichain (no element ≤ another)
              frontier may only advance (I3 — monotone progress)
Event Precondition Postcondition Error
advance_to(t) t > all elements currently in frontier new frontier contains t FrontierRegressionError if t ≤ any current element
join(other_frontier) both valid antichains element-wise join; remove dominated none
close() any state frontier = {} (empty = "all times complete") none

An empty frontier means no future updates will arrive — all times complete.

Edge case — concurrent capability drops: when two capabilities at times T1, T2 are held and T1 is dropped first, the frontier becomes {T2}. If T2 is then dropped, frontier becomes {}. Any intermediate peek at T1 ≤ T2 must wait until frontier passes T1 before returning.

8.4 Collection Semantics

A Collection<D> is a stream of Update<D> triples. It is NOT a snapshot; it is a delta stream. The multiset at time t is computed by accumulation:

multiset(C, t) = { (d, n) | n = Σ_{(d,s,δ) ∈ C, s ≤ t} δ,  n ≠ 0 }

Consolidation: consolidate(batch) groups by (data, time), sums diffs, removes zero entries. Idempotent. Result satisfies I2.

Multiset equality: two collections A, B are equal at time t iff multiset(A,t) == multiset(B,t).

8.5 Operator State Machine and Execution Semantics

Each Operator advances through a fixed cycle:

IDLE ──input_available──> RUNNABLE ──scheduled──> RUNNING ──emit_output──> IDLE
                                                     │
                                                     └──frontier_advance──> FRONTIER_SENT
Operator kind Input state required Output produced Frontier held
Stateless (map, filter, flat_map, negate, concat) none per-update transform passthrough
Threshold / distinct keyed Arrangement of input output delta when net diff crosses 0/1 boundary delayed until input frontier advances
Count / reduce keyed Arrangement of input + output per-key retract-old / emit-new delta delayed

Frontier propagation rule: output frontier ≤ min of all held input frontiers. An operator may not emit an update at time t without holding a capability at t.

8.6 Arrangement / Trace Layout

A Trace is the indexed, time-versioned state structure. Its storage layout:

  • Trace
    • ├── since_frontier: Frontier // times below which diffs have been merged
    • ├── upper_frontier: Frontier // upper bound on times present
    • └── batches: Vec<Batch>
  • Batch
    • ├── lower: Frontier
    • ├── upper: Frontier
    • ├── keys: sorted Vec<Key>
    • └── data: sorted Vec<(Key, Val, Timestamp, Diff)>
  • // sort order: (Key ASC, Val ASC, Timestamp ASC)

Cursor semantics: a cursor into a Trace yields (Val, Timestamp, Diff) tuples for a given Key, in (Timestamp ASC, Val ASC) order. Valid only while no compaction advances since_frontier past the cursor's time.

Compaction: merge all Batches whose upper ≤ new since frontier; consolidate diffs at merged times; drop zero entries. I7 guarantees query answers are unchanged at or after the new since frontier.

Shared-reference model: Arc<Mutex<Trace>> or epoch-based reader/writer. Multiple operators hold read handles; one writer (the arrangement operator) holds exclusive write access per epoch.

Batch merge rule (logarithmic merging): maintain O(log N) batches; merge two batches of equal size into one; ensures O(log N) lookup and O(N log N) amortized insert.

8.7 Delta-Join Execution Semantics (Incremental Join)

Given two arrangements A (key -> (val_a, time, diff)) and B (key -> (val_b, time, diff)), and an incoming delta ΔA at time t:

for each update (key, val_a, t, d_a) in ΔA:
    for each (val_b, s, d_b) in B.lookup(key) where s ≤ t:
        emit Update { data: join_fn(val_a, val_b), time: join(t,s), diff: d_a * d_b }

Symmetric for ΔB. The full join output equals A×B + ΔA×B + A×ΔB + ΔA×ΔB; the incremental form processes only the delta terms.

Correctness under retractions (I5): if d_a = -1 (retraction), the emitted products have negative diff, correctly retracting previous join outputs. No special case needed — diff algebra handles it.

Edge case — concurrent deltas on both sides at same time T: both ΔA and ΔB arrive at T. Processing ΔA against B (without ΔB) and ΔB against A (without ΔA) is correct because the ΔA×ΔB cross-term is counted when processing ΔA against the arrangement that already includes ΔB (if flushed first), or is emitted as a separate delta. The arrangement must be locked to a consistent snapshot per operator invocation.

Malformed path — missing retraction: upstream emits +1 at T1 but never emits -1 before re-inserting +1 at T3 → net multiplicity = 2; downstream join doubles output. Detected by I1 oracle (batch recompute yields multiplicity 1). Input handles must enforce: update = retract-old then assert-new.

8.8 Reduce / Distinct Correctness Model

reduce maintains per-key state:

input_arrangement:  Key -> multiset of Val at each time
output_arrangement: Key -> aggregate(Val) at each time

On input delta (key, val, t, d):

  1. Apply delta to input_arrangement[key].
  2. Compute new_output = aggregate_fn(input_arrangement[key].as_of(t)).
  3. Fetch old_output = output_arrangement[key].as_of(t).
  4. If new_output ≠ old_output: emit retraction (key, old_output, t, -1) + assertion (key, new_output, t, +1).

Edge case — aggregate goes to zero: COUNT(*) drops to 0. Must emit retraction of the 0-count row (if present) and suppress emitting a new 0-count row (SQL semantics: groups with count=0 disappear). Tracked by I6.

Distinct semantics: output multiplicity is always 0 or 1; positive input multiset → output +1; zero input multiset → output 0. Threshold at 1 over input arrangement.

8.11 WAL and Storage Layout

WAL record:
  [ magic: u32 | seq: u64 | timestamp: Timestamp | key_len: u16 | key: [u8] |
    val_len: u16 | val: [u8] | diff: i64 | crc32: u32 ]
  // fixed-width header (28 bytes) + variable key + val

Checkpoint record:
  [ magic: u32 | frontier: Frontier (serialized antichain) |
    arrangement_snapshot_ref: u64 (offset in trace file) | crc32: u32 ]

Recovery protocol:

  1. Load latest valid checkpoint; restore arrangements from trace file.
  2. Scan WAL from checkpoint's seq forward; replay each Update triple into dataflow.
  3. Advance frontier to checkpoint's frontier; re-run operators until output frontier catches up.
  4. Signal recovery complete; accept new input.

Edge case — partial WAL record at tail: truncated write detected by CRC mismatch; discard tail and replay only up to last valid record. This may lose the last batch of updates — acceptable if clients use at-least-once delivery with sequence numbers.

8.12 Changefeed and Peek Semantics

Peek (point-in-time read):

peek(view: ViewDef, at: Timestamp) -> PeekResult
  precondition: output_frontier.less_than_equal(at)   // time is complete
  returns: consolidated multiset of view output at `at`
  blocks: until output_frontier advances past `at`

Changefeed (streaming delta):

changefeed(view: ViewDef, since: Frontier) -> Stream<Update<Row>>
  emits: consolidated output Updates as output frontier advances
  guarantees: monotonic, gap-free, no duplicate times
  ordering: frontier-bounded (all updates at time T emitted before frontier advances past T)

Snapshot+changefeed boundary: a client may peek at T0 then open a changefeed from T0 — the union of snapshot + changefeed deltas is a consistent, complete history.

Malformed path — peek before frontier: if output_frontier has not yet passed at, the peek MUST block (not return stale data). Returning early violates I4. Timeout must return PeekError::NotYetAvailable, never a partial result.

Back-pressure: each operator channel has a bounded capacity; the scheduler parks a sender when the channel is full, preventing unbounded memory accumulation.

8.14 Scheduling Semantics

Operator scheduling is cooperative and deterministic (P8):

while work_available:
    for each operator O in topological_order:
        if O.has_pending_input() or O.frontier_changed():
            O.run_once()    // process one batch; may emit to output channels
            propagate_frontiers(O)
  • Topological order: operators are sorted by dataflow topology; sources first, sinks last.
  • Determinism: given the same set of input updates, the same outputs are produced regardless of batch sizes or interleaving, because diffs commute under addition and consolidation is idempotent.
  • No preemption: run_once completes atomically per operator invocation; no shared mutable state between concurrent run_once calls on different operators (single-threaded scheduler for Phase 5; async-capable in Phase 13).

Phase 1 — core types: Diff, Timestamp, Update, Collection

1.1 Objectives

  • Define Diff(i64), Timestamp, Update<D>, Collection<D>, Row, Key, Val in ird-core.
  • Timestamp satisfies a join-semilattice: join, meet, less_equal; partial order; antichain-compatible.
  • Collection<D> is a typed stream of Update<D> triples; no I/O, no allocation policy.
  • All types are Clone + Debug + PartialEq; Diff and Timestamp also Copy + Ord (Timestamp: partial order only).
  • Property tests cover diff arithmetic and timestamp lattice laws.
  • Zero external I/O, zero persistence; this crate is a dependency leaf.

1.2 Detailed Implementation Steps

  • ird-core/src/diff.rs: Diff(i64) newtype [P1 Sec. 2 signed-multiplicity model; ADR-06]; impl Add, Sub, Neg, Zero; const ZERO, ONE, NEG_ONE.
  • ird-core/src/timestamp.rs: Timestamp trait [P2 Sec. 3 pointstamp/lattice; B9 partial-order clocks; ADR-05] with join(&self, &Self) -> Self, meet(&self, &Self) -> Self, less_equal(&self, &Self) -> bool; provide ProductTime<A,B> (coordinate-wise) and u64 (total order) as canonical impls.
  • ird-core/src/update.rs: Update<D> { data: D, time: T, diff: Diff } [P1 Sec. 2 Update triple definition] where T: Timestamp; derives Clone, Debug, PartialEq.
  • ird-core/src/collection.rs: Collection<D> = Vec<Update<D>> at this phase [P3 Sec. 2 Z-set formalism] (batch-oriented); exposes push, extend, iterator impl.
  • ird-core/src/row.rs: Row(Vec<Value>), Key(Vec<Value>), Val(Vec<Value>); Value enum: Int(i64), Str(Arc<str>), Bool(bool), Null; Row::split_at(n) -> (Key, Val).
  • ird-core/src/lib.rs: re-exports; feature flags for serde [ADR-11 serialization policy].
  • Property tests in ird-core/tests/lattice_laws.rs using proptest [B8 Ch. 23 (order-theoretic subtyping/lattice parallel)]: commutativity, associativity, idempotency of join/meet; less_equal reflexive/transitive/antisymmetric; join is least upper bound.
  • Property tests in ird-core/tests/diff_arith.rs [P1 Sec. 2 diff algebra]: additive inverse, associativity, diff sign round-trip.

1.6 Pitfalls

  • Timestamp total-order confusion: using Ord instead of less_equal causes join/meet to silently use lexicographic order for product times; use the trait method exclusively.
  • Diff silent truncation: wrapping arithmetic on Diff produces incorrect multiplicities; use checked_add or saturating_add with explicit policy.
  • Row equality via Vec<Value>: float Value variants break PartialEq; disallow floats or use a bit-exact repr.
  • Arc<str> clone cost: cloning Row in hot paths is cheap but not free; measure before adding Cow.
  • Lattice commutativity assumption: ProductTime join is commutative, but custom timestamp impls may not be; test both orderings.

1.7 Performance Concerns

  • Row(Vec<Value>) heap-allocates; in Phase 6 consider small-vec or arena allocation.
  • Diff(i64) is zero-cost wrapper; ensure no boxing via dyn Diff patterns.
  • Arc<str> string interning: contention-free clone but fragmented allocation; profile in Phase 8.
  • Collection<D> as Vec is cache-friendly for batch iteration; avoid linked-list alternatives.

1.8 Edge Cases

  • Diff(i64::MIN) negation overflows; document as UB or add checked negation.
  • Empty Row (zero columns): valid; split_at(0) returns (Key([]), Val(row)).
  • ProductTime with mismatched inner types: caught by type system at compile time.
  • Update<D> with diff == 0: legal to construct but consolidation will drop it; do not panic on insert.
  • less_equal(a, a) must return true (reflexivity); failure breaks frontier logic in Phase 4.

Phase 2 — differential collections + consolidation

2.1 Objectives

  • Implement ird-collection: accumulate Update<D> triples; consolidate to canonical form.
  • Consolidation: group by (data, time), sum diffs, discard zero-multiplicity entries.
  • Define multiset-equality: two Collection<D> are equal iff their consolidated forms are identical.
  • Implement as_of(t: &T) -> Multiset<D>: sum diffs over all times <= t per record.
  • Establish the foundational delta semantics all operators rely on.

2.2 Detailed Implementation Steps

  • ird-collection/src/collection.rs: DiffCollection<D, T> wrapping Vec<Update<D,T>> [P1 Sec. 2 collection as multiset stream]; methods: push, extend, consolidate(&mut self), is_consolidated(&self) -> bool, as_of(&self, t: &T) -> HashMap<D, Diff>.
  • consolidate algorithm [P1 Sec. 3 consolidation; P3 Z-set normalization; I2 invariant]: sort by (data, time) using a lexicographic key (requires D: Ord + Hash, T: Timestamp + Ord); then linear scan summing diffs; retain only non-zero entries; in-place to avoid extra allocation.
  • as_of algorithm [P5 Sec. 3 counting algorithm; I8 diff conservation]: iterate all updates, keep those with time.less_equal(t), accumulate HashMap<D, Diff>, drop zero entries.
  • ird-collection/src/multiset.rs: Multiset<D> = BTreeMap<D, Diff>; union, difference, contains_key, iteration [B2 Sec. IV multiset view maintenance].
  • ird-collection/src/ops.rs: collection_union (append + consolidate), collection_negate (flip all diffs), collection_difference (union with negated right) [P1 Sec. 2 operator algebra].
  • Tests in ird-collection/tests/consolidate.rs [I2 invariant; ADR-18 proptest]: idempotency, commutativity of union before consolidation, zero-sum drops.
  • Tests in ird-collection/tests/as_of.rs: monotone: as_of(t1) is a subset of as_of(t2) when t1 <= t2; empty at time before first update.
  • Property tests: consolidate(consolidate(c)) == consolidate(c); union(a,b).as_of(t) == union(a.as_of(t), b.as_of(t)) [P3 Sec. 3 linearity of δ-transform].

2.6 Pitfalls

  • Sort instability on equal keys: if two updates have same (data,time) and different diffs, sort order affects summing correctness only if the scan is buggy; use stable grouping, not sort order, for summation.
  • as_of with partial order: naively using <= on total-ordered proxy will miss concurrent updates on a product lattice; must use time.less_equal(t) not time <= t.
  • HashMap non-determinism in as_of: HashMap iteration order is randomized; multiset equality must compare by key set, not iteration order.
  • Zero-diff entry leak: consolidation must drop entries where summed diff == 0; leaving them causes phantom records in join lookups (Phase 8).
  • D: Ord requirement for sort: not all data types have a natural Ord; encode Row with a stable byte encoding for sort key.
  • Consolidation of already-consolidated data: must be a no-op; inserting duplicate (data,time) pairs violates canonical form if not re-consolidated.

2.7 Performance Concerns

  • consolidate sort is O(n log n); for large batches use radix sort on encoded keys.
  • HashMap in as_of is O(n) but with high constant; for small collections, Vec-linear scan beats hash.
  • Avoid cloning D during sort: sort indices, then rearrange in-place.
  • BTreeMap in Multiset is cache-unfriendly for large sets; consider Vec + sort for read-once paths.
  • Repeated consolidation of small incremental appends is quadratic if naively re-sorting from scratch; Phase 6 batch merging solves this.

2.8 Edge Cases

  • Collection with a single Update with diff == 0: consolidate produces empty collection.
  • as_of at a time before all updates: returns empty multiset (correct: no inputs).
  • as_of at max timestamp: should include all updates.
  • Negative net multiplicity (more deletes than inserts): valid; represents over-retraction; operators must handle Diff < 0 output from as_of.
  • Very large multiplicities: Diff(i64) can represent up to ~9.2e18; summing many small diffs to i64 max is an edge case — checked arithmetic required.

ird-operator/src/stateful.rs — four operator structs [P1 Sec. 4 stateful operators; R1 operators/reduce.rs, threshold.rs]:

Operator Input Arrangement key Output Arrangement key Core logic
DistinctOp Key -> ((), Time, Diff) Key -> ((), Time, Diff) output diff = sign(new_input_count) - sign(old_input_count)
ThresholdOp<F> Key -> ((), Time, Diff) Key -> ((), Time, Diff) predicate F: Fn(i64)->bool; output = 1 where predicate holds, 0 otherwise; emit delta

ReduceOp<F> Key -> (Val, Time, Diff) Key -> (Out, Time, Diff) user-supplied F: Fn(&[(Val,i64)]) -> Out; call on updated input multiset; diff old output out, diff new output in

Algorithm (shared across all four):

  1. Receive input Batch of Update<(Key, Val)> at some Timestamp.
  2. For each key k in the batch: look up input_arr[k] as-of the batch time (cursor scan), accumulate net multiplicity per (Val, Time), apply pending batch delta, consolidate.
  3. Compute old_output = output_arr[k] as-of the same time.
  4. Compute new_output by applying the operator function to the updated input multiset.
  5. Emit Update { data: new_output, time, diff: +1 } and Update { data: old_output, time, diff: -1 } if they differ; skip if equal.
  6. Insert the output delta into output_arr.
  7. Advance both arrangements' since-frontier when the input frontier advances (Phase 6 compaction API).

Frontier handling: hold a Capability per arrangement; drop it only when no times at or before it can still arrive; trigger output finalization only after frontier covers the time.

ird-operator/src/join.rs — JoinOp<L,R,O> [P1 Sec. 5 Δ(A⋈B) = ΔA⋈B + A⋈ΔB derivation; R1 operators/join.rs]:

JoinOp {
  left_arrangement:  Arc<Trace<Key, LVal, Timestamp, Diff>>,
  right_arrangement: Arc<Trace<Key, RVal, Timestamp, Diff>>,
  output_fn: fn(&Key, &LVal, &RVal) -> O,
}

Delta-join algorithm: for each new input Batch on the left channel at time t, for each (key, lval, t_delta, diff_l) in the batch: open a cursor on right_arrangement restricted to times <= t_delta (the arrangement's as-of view); for each matching (key, rval, diff_r) in the right cursor at key, emit Update { data: output_fn(key, lval, rval), time: t_delta.join(t_right), diff: diff_l * diff_r }. Symmetric for right-side batches probing the left arrangement. Time join: t_delta.join(t_other) is the lattice join of both times; ensures output time is at or after both input times. Arrangement probe API (ird-arrange): Trace::cursor_as_of(key: &Key, t: Timestamp) -> Cursor<RVal, Diff> — iterates over (RVal, net_diff) pairs whose time is <= t after compaction; used for left-probes-right and right-probes-left. Batching: accumulate all output Updates from a single input batch before emitting; consolidate before forwarding downstream. Frontier propagation: JoinOp output frontier = meet of left input frontier and right input frontier (cannot advance output past either input). Module layout: ird-operator/src/join.rs — JoinOp, delta-join algorithm; ird-operator/src/join_tests.rs — unit + property tests; ird-arrange/src/cursor.rs — cursor_as_of API (consumed by JoinOp). Shared arrangement access: left and right Arc<Trace> may be shared with other operators; cursor API is read-only, no lock required during scan; write lock only during batch merge. 8.7 Performance Concerns

Explain generation: allocates string per node; only called in non-critical path (query submission, not execution). Schema lookup: column resolution looks up schema per column ref; cache schema in a HashMap<String, Column> per Scan node.

9.8 Edge Cases

  • Empty SELECT list: reject with PlanError::EmptyProjection. Self-join: same table name appears twice; de-duplicate by aliasing before join lowering. GROUP BY with no aggregates: treated as DISTINCT; lower to DistinctOp.
  • LIMIT: recorded in the Plan but differential operators do not support it natively; emit PlanWarning::LimitIgnored (not incrementally maintainable). ORDER BY: likewise recorded, emit PlanWarning::OrderByIgnored; applied only at peek time.
  • Very deeply nested sub-selects (> 10 levels): enforce a recursion depth limit; return PlanError::MaxDepthExceeded. SQL keywords in identifiers require quoting; unquoted reserved words are a parse error.
  • Multi-column equijoin: lower to a map that concatenates join columns into a composite Key, then JoinOp, then a map to extract.

ird-query (src/lib.rs) [I1 peek = batch oracle; I4 frontier-complete read; RFC-5 changefeed offset analogy]:

Symbol Shape Contract
PeekRequest { view: ViewName, as_of: Timestamp } as_of must be frontier-complete
PeekResult Vec<(Row, Diff)> consolidated, zero-diff rows absent satisfies I2
peek(req: PeekRequest, view_mgr: &ViewManager) -> Result<PeekResult> reads output Trace, iterates batches with time <= as_of, consolidates blocks until frontier >= as_of; timeout returns Err(NotYetComplete)

peek algorithm:

  1. Wait until output_arrangement.frontier() >= as_of (antichain comparison, I3).
  2. Open cursor on output_trace; scan all (row, time, diff) where time <= as_of.
  3. Accumulate into HashMap<Row, i64>; filter entries with sum == 0.
  4. Return sorted Vec<(Row, Diff)>.

changefeed pipeline:

  • ViewManager maintains a Vec<ChangefeedSender> per view; on each scheduler tick that advances output frontier, consolidate deltas since last emitted frontier, send ChangefeedBatch.
  • Consolidation: group by (row, time) within the batch window, sum diffs, drop zeros.
  • Ordering: batches ordered by frontier; within a batch, ordering by row key (deterministic, I9).
  • De-duplication: changefeed sender tracks last_emitted_frontier; only emits if new frontier strictly dominates last.

snapshot+changefeed boundary:

 snapshot at T: all rows with net diff > 0 as of time T
 changefeed from T: all updates at times strictly > T
 union: complete history, no gap (time > T not in snapshot), no overlap (time = T not in changefeed)
  • Client protocol: first call peek(view, T), then subscribe(view, T+1).

Checkpoint design (ird-storage/src/checkpoint.rs):
    Symbol Shape Contract
    CheckpointWriter serializes each Trace (batch sequence) to a named file per arrangement write_trace(trace_id, &Trace) -> CheckpointOffset

1. Scan checkpoint directory; find manifest with largest frontier.
2. For each trace_id in manifest: load Trace from checkpoint file.
3. Open WAL at manifest.wal_offset; replay records until EOF or Seal.
4. For each UpdateBatch record: send to corresponding InputHandle (bypasses network).
5. For each FrontierAdvance: call advance_to on InputHandle.
6. After replay: flush all InputHandles; wait for output frontier to reach recovered frontier.
7. Assert I10: peek all views at recovered frontier; compare against manifest's saved multiset hashes.

13.7 Performance Concerns

  • CSE hash lookup: per-plan-node on every CREATE VIEW; negligible vs. ingestion; cache hash in PlanNode.
  • Arrangement ref-count: Arc<dyn Trace> clone per view; no contention on read path.
  • Metrics collection: avoid lock per update; use atomic counters; aggregate at scrape time.

13.8 Edge Cases

  • DefineViewReq referencing unknown base relation — return Err(UnknownRelation) before plan compilation.

Phase 14 — hardening + incremental==batch conformance + perf + packing

14.1 Objectives

  • Implement the differential correctness oracle: peek(view, t) == batch_recompute(view, inputs_at_t) for all views and times (I1). Randomized delta+retraction fuzzer: generate arbitrary insert/delete/update sequences; verify oracle after each step.
  • Confirm join correctness under deletions (I5), reduce/distinct correctness under retractions (I6), and arrangement compaction soundness (I7).
  • Throughput benchmark: updates/second sustained; memory benchmark: arrangement bytes vs input size. WAL + trace pack: compact WAL segments and trace checkpoint files for long-running deployments.

14.2 Detailed Implementation Steps

<!-- Theory anchors: P1 Sec. 5 incremental==batch guarantee (I1); ADR-20 differential correctness oracle; ADR-21 criterion benchmarking; P5 counting algorithm correctness under retractions; R1 differential-dataflow test patterns -->

Correctness oracle (ird-oracle test harness inside ird-core/tests/) [P1 Sec. 5 I1 guarantee; ADR-20 oracle design; P5 counting algorithm]: BatchEngine — pure in-memory SQL evaluation over HashMap<RelName, Vec<Row>>, no differential machinery; apply_updates(state, updates) mutates BatchEngine state by applying Update triples (diff +1 = insert, -1 = delete, magnitudes > 1 = multiplicity); batch_query(state, view_sql) evaluates view SQL against current state, returns BTreeMap<Row, i64> (row -> net multiplicity); incremental_peek(engine, view_name, t) calls ird-query::peek, consolidates to same BTreeMap format; oracle_check(batch_result, incremental_result) is an equality assertion — on failure emits diff of mismatched rows, frontier at which failure occurred, input sequence hash. Randomized fuzzer (tests/fuzz_oracle.rs):

loop N_ROUNDS:
  pick random base relation updates (insert/delete, random rows, random timestamps)
  apply to BatchEngine state
  push same Updates via ird-input
  advance_to(t); flush
  wait for frontier to advance past t
  oracle_check(batch_query(t), incremental_peek(t))
  optionally: retract previously inserted rows (negative diff)
  optionally: advance compaction frontier; re-check oracle still holds
  • Seed-reproducible via --seed N; CI runs fixed seeds, nightly runs randomized. Property: oracle_check never fails across 10,000 rounds with joins, reduces, distinct, and retractions. Join correctness under deletions: fixture inserts rows into R and S, joins on key, verifies, deletes subset of R, verifies delta correct (I5); assert no phantom rows after deletion, no missing rows after re-insertion. Test test_join_retraction_roundtrip — insert A, join, delete A, re-insert A; final state equals initial join. Reduce/distinct under retractions: fixture inserts rows, reduces (COUNT, SUM), retracts half, verifies aggregate equals batch result (I6). Distinct: insert duplicates, verify output multiplicity 1, retract all but one copy (still 1), retract last (0). Compaction soundness (I7): advance since frontier past time t, call compact(since), peek at times >= since, compare to batch. Negative test: peek at time < since returns Err(TimeTooOld), not wrong data. Throughput benchmark (benches/throughput.rs): bench_insert_throughput — sustained insert rate, single view (project + filter), target reports ops/s not a fixed pass threshold; bench_join_throughput — two-relation equijoin, measures delta-join rate; bench_reduce_throughput — group-by COUNT on high-cardinality key; bench_arrangement_memory — measures arrangement_bytes as function of unique key count, expect O(keys · avg_val_size); uses criterion, emits JSON for CI trend tracking. WAL + trace pack (ird-storage additions): wal_pack(segments: &[WalSegment], before: Frontier) -> PackedWal — merges WAL segments with timestamps < before, consolidates updates per (row, time), outputs one compacted segment; trace_pack(trace: &mut dyn Trace, pack_frontier: Frontier) — merges all Batches below pack_frontier into one Batch, rewrites to storage, updates since-frontier; PackedWal validation replays packed WAL and original WAL segments and compares resulting arrangement states, must be identical (I10 variant); pack_schedule configurable — trigger pack when WAL segments > N or total WAL bytes > threshold.

14.7 Performance Concerns

  • Oracle in CI: BatchEngine recompute is O(input_size); limit fuzz round input size to 10K rows to bound CI time; nightly can run larger.
  • Criterion warm-up: ensure JIT / page-fault effects are excluded; use criterion::Criterion::warm_up_time(Duration::from_secs(5)).
  • WAL pack I/O: read all segments, consolidate in memory, write one; for large WALs, stream via merge-sort on (row, time) to avoid OOM.
  • Trace pack allocation: merging N Batches allocates one large Batch; pre-size with sum of all input record counts; avoid Vec realloc.
  • Fuzz loop overhead: oracle_check BTreeMap diff is O(n log n); use sorted Vec comparison to reduce constant factor.
  • Arrangement memory baseline: ensure bench records arrangement_bytes metric at end; enables memory regression detection.
  • Join benchmark input skew: test both uniform-key and skewed-key distributions; skewed joins expose hash-bucket contention in arrangement lookup.

14.8 Edge Cases

  • Zero-diff updates in fuzz input: generator may emit Diff(0); ird-collection must drop these before processing; BatchEngine same.
  • Peek at Timestamp::MIN: valid time; view over empty input; oracle returns empty multiset; incremental must also return empty.
  • Retract row never inserted: Diff(-1) for unknown row; net multiplicity goes negative; both BatchEngine and ird-collection must tolerate; output negative multiplicity is well-defined (IVM counting algorithm).
  • WAL pack with empty segments: wal_pack([]) returns empty pack; no file written; no panic.
  • Trace pack at since == since_frontier: idempotent; second pack call is a no-op.
  • Concurrent peek + trace_pack: peek holds a read cursor; pack must not invalidate live cursors; use epoch/snapshot cursor protocol.
  • Overflow in SUM aggregate: i64 SUM overflow; define behavior (saturate or error); oracle uses same rule.
  • Fuzz seed exhaustion: after u64::MAX steps, wrap; seeds are independent; no shared state between rounds.

Tracing Strategy

  • Use tracing crate spans throughout; structured fields, not string interpolation.
  • Span hierarchy: server.request → plan.compile → dataflow.build → operator.process_batch → arrange.merge.
  • Span fields: operator_id, operator_type, view, batch_update_count, frontier_before, frontier_after, duration_us.
  • ird-plan emits one root span per compilation: plan_node_count, estimated_join_factor, sql_hash (not full SQL text — privacy).
  • ird-storage spans: wal_write (bytes, fsync latency), batch_checkpoint (batch count, bytes), recovery_replay (record count, duration).

Alerting Philosophy

  • Alert on symptoms (frontier lag, peek latency, correctness counters), not just causes.
  • P0 (page immediately, escalate within 5 min): ivm_divergence_detected > 0, wal_write_error_total > 0, compaction_soundness_error > 0, process OOM kill.
  • P1 (page within 15 min): output_frontier_age_ms > 120 000 sustained for 2 min, frontier_stuck_total > 0 sustained for 1 min, arrangement_bytes > 90% limit.
  • P2 (create ticket, no page): peek_latency_p99_ms > 500 sustained for 5 min, changefeed_buffer_bytes > 100 MB, wal_corrupt_records_total > 0, trace_since_lag_ms > 60 000.
  • Suppress duplicate alerts: fire once per 5 min per (alert_name, view, operator_id); auto-resolve when metric clears for 2 min.
  • Alert routing: P0/P1 → on-call engineer; P2 → team ticket queue.

Incident Response Protocol

  1. Alert fires: acknowledge within 5 min (P0) / 15 min (P1); check ivm_divergence_detected and frontier_stuck_total first.
  2. Triage: pull output_frontier_age_ms, arrangement_bytes, WAL error counters; check recent deploy (was this a MINOR upgrade?).
  3. Divergence path: mark affected views suspect via admin API; halt peek responses to those views; export arrangement snapshot, WAL tail, span traces; follow RB-001.
  4. Frontier stall path: dump capability registry via admin API; identify holding operator; advance or restart; follow RB-002.
  5. WAL path: halt input ingestion; check disk; follow RB-004; assess data loss window; inform clients.
  6. Resolution: verify SLOs restored; write post-mortem within 48 h; extract minimal test reproducer; add to fuzz corpus.

Backup and Trace Management Strategy

  • WAL segments: rolled at 64 MB (configurable); offloaded to S3-compatible object storage after sealing; 7-day local retention, 30-day remote retention.
  • Arrangement checkpoints: taken every checkpoint_interval_updates (default 1 M updates) or checkpoint_interval_ms (default 5 min), whichever comes first; stored as Batch files + WAL offset marker in checkpoint manifest (JSON); retain 3 checkpoint generations.
  • Restore procedure: (1) download latest checkpoint bundle from object storage; (2) verify SHA-256 of each Batch file; (3) replay WAL from checkpoint.wal_offset to desired recovery time; (4) verify arrangement integrity; (5) open server.
  • Point-in-time recovery (PITR): supported to any WAL-covered time within retention window by specifying --recover-to-time <timestamp> at startup.
  • Compaction and GC: WAL segments may be pruned only after (a) a checkpoint covering their entire range exists and is verified and (b) all active views' since-frontiers have advanced past the segment's time range. Never prune ahead of the oldest active checkpoint.
  • Backup validation: weekly automated restore drill to a staging instance; verify output_frontier_age_ms and oracle conformance after restore.

Compatibility & Versioning

Versioning Policy

  • Semantic versioning MAJOR.MINOR.PATCH applied per published crate.
  • MAJOR: any breaking change to wire format, storage format, public trait signatures in ird-core / ird-collection / ird-operator / ird-arrange / ird-time, or removal of a SQL construct from ird-plan.
  • MINOR: backward-compatible additions — new operator variant, new SQL construct, new metric, new admin API endpoint, new ViewDef field (optional), new Plan node type that old planners reject with a clear error.
  • PATCH: bug fixes, performance changes, documentation; no API, format, or behavioral change visible to callers.
  • ird-core is the version anchor for the crate graph; all other workspace crates declare ird-core = "=MAJOR.MINOR" (exact minor).
  • Crates with public APIs (ird-core, ird-collection, ird-operator, ird-arrange, ird-time, ird-plan, ird-server) are published; internal crates (ird-dataflow, ird-input, ird-view, ird-query, ird-storage) are workspace-only and semver-exempt for external consumers.

Storage Format Compatibility

  • WAL record schema: fixed frame [version: u8 | flags: u8 | payload_len: u32 | payload: [u8] | crc32c: u32]. Version byte allows format evolution; old reader returns WalFormatError::UnknownVersion on mismatch.
  • Batch file header: [magic: b"IRDB" | format_version: u16 | key_schema_hash: u32 | block_count: u32 | ... data blocks ... | sha256: [u8; 32]]. key_schema_hash detects Row schema mismatch (column count / types) at load time.
  • Checkpoint manifest: JSON (human-readable, diffable); checkpoint_format_version field; wal_offset is a WAL byte offset (stable across MINOR); batch_paths are relative to checkpoint_dir.
  • Forward compatibility (old binary reads new-format data): only within MINOR increments; new fields in manifest are ignored; new WAL record flags bits are masked by old reader if version byte unchanged.
  • Backward compatibility (new binary reads old-format data): guaranteed within a MAJOR; new binary reads all MINOR-earlier WAL and Batch formats.
  • Cross-MAJOR: not guaranteed; always migrate via ird-migrate tool; never silently accept unknown MAJOR version.

Differential (Reference Oracle) Tests — I1 Enforcement

The cardinal conformance suite: after any sequence of input updates, peek(view, t) must equal a batch recompute of the query over inputs with time <= t.

oracle_loop:
  for each step:
    apply random delta batch (Insert|Delete|Update) to:
      (a) incremental view via ird-input → ird-dataflow
      (b) in-memory reference table (simple HashMap multiset)
    advance_to(t); flush; wait for frontier >= t
    assert peek(view, t) == reference.compute_view(query, t)
  • Scope: every operator type; every relational operator in ird-plan.
  • Phases: Phase 14 drives this harness after every operator addition.
  • Tolerance: zero divergence; any diff logged with full update trace for replay.

Mental Models & First Principles

The compressed insights an expert in incremental view maintenance and differential dataflow holds. Each predicts a bug class. Every cited § resolves to a real heading.

MM1. A change is a value with a sign and a time, not an event. An Update is (data, time, diff) where diff ∈ ℤ; a delete is diff = −1, an update is −1 of the old plus +1 of the new. Predicts: operators are linear functions over a commutative group, so order of arrival is irrelevant. Bug without it: modelling deletes as side-effecting mutations breaks commutativity and makes replay non-idempotent. Applied: §8 (Update/Collection), Phase 1, I1.

MM2. Consolidation is the garbage collector of the difference world. Multiple (d, t, +1)/(d, t, −1) pairs at the same (data, time) cancel to zero and must be dropped. Predicts: memory stays proportional to the net multiset, not the gross update count. Bug without it: unbounded arrangement growth as canceling diffs accumulate. Applied: Phase 2 (consolidation), §4.1 (arrangement ≤ 1.1× after compaction), P7.

MM3. A Frontier is an antichain of times, and progress is its forward movement. The frontier is the set of minimal times that may still arrive; once it passes t, all data at t is final. Predicts: exactly when an output at t is safe to emit (peek fast path, §4.1). Bug without it: emitting results before the frontier closes → retractions visible to clients, or hanging peeks. Applied: §8.3 (Frontier state machine), Phase 4, P5, I-progress invariants.

MM4. Incremental == batch is the only correctness oracle that matters. For any input, feeding it incrementally must produce the exact multiset that re-running the whole computation from scratch would. Predicts: the differential testing strategy (Phase 14 fuzz, 10 M sequences). Bug without it: subtle operator bugs that only manifest after specific retraction interleavings ship undetected. Applied: Phase 14 (incremental==batch conformance), §4.1 (correctness budget), I1.

MM5. An Arrangement is an index shared by readers across logical time. A Trace keeps all versions of a keyed collection; many operators read the same arrangement concurrently without copying. Predicts: join memory is paid once per arrangement, not per consumer. Bug without it: re-indexing the same collection in every join → multiplicative memory blowup. Applied: §8 (Arrangement/Trace), Phase 6, P6, ADR-08.

MM6. Compaction is forgetting the past you can prove no one will ask about. Times below the since frontier can be coalesced to a single representative time. Predicts: the ≤ 1.1× steady-state memory (§4.1) and why advancing since too far breaks historical peeks. Bug without it: compacting below a live capability → wrong answers for in-flight queries. Applied: Phase 6 (logarithmic batch merge), I7, B6.

MM7. The dataflow loop is single-threaded on purpose; parallelism is across partitions. One operator graph runs on one worker; scale-out is by partitioning keys across workers, not by locking shared operator state. Predicts: zero hot-path contention and the work-stealing model (§4.1). Bug without it: sharing mutable operator state across threads → races and nondeterministic frontiers. Applied: Phase 5 (dataflow scheduling), §4.1 (concurrency model).

MM8. The WAL is the source of truth; arrangements are a derived cache. Committed input deltas are durable before ack; all in-memory state is reconstructable by replay. Predicts: I10 recovery equivalence and the ≤ 1.5× WAL amplification (§4.1). Bug without it: checkpointing arrangements without a replayable input log → unrecoverable corruption after a torn write. Applied: Phase 12 (WAL + recovery), P9, I10.

MM9. A join is two arrangements meeting at matching keys, delta-driven from both sides. Each side's new delta probes the other side's arrangement at the appropriate time. Predicts: the 100 K delta-pairs/sec budget and why both inputs must be arranged. Bug without it: re-scanning a full relation per delta → O(n) per update instead of O(matches). Applied: Phase 8 (incremental join), §4.1 (join throughput), Comparative Architecture (CA-1).

MM10. Logical time is a lattice, not a number line. Timestamps support a partial order with meet/join; concurrent times are incomparable, not "equal." Predicts: correct handling of nested scopes/iteration and multi-input operators. Bug without it: forcing a total order collapses concurrent updates and corrupts frontier math. Applied: §8.2 (partial-order timestamps), Phase 4, P4, B9 (Lamport).

Differential Dataflow is the library that originated ℤ-weighted difference traces and timely progress; it wins as an embeddable, maximally general dataflow engine for Rust programs that need custom operators and no SQL. ird narrows it to a server with SQL, WAL durability, and changefeeds — trading generality for an operable product (CA-4, CA-6).

Materialize wraps differential dataflow in full PostgreSQL-wire SQL with a cloud-native persist layer; it wins for teams that want "Postgres but the views are always fresh" at cloud scale. ird rejects distributed sharding and full SQL (both deferred — see Deferred Features Register) to stay a single-process, embeddable engine with a tractable surface.

Noria (CA-2) chose partial materialization — it materializes hot paths and issues upqueries to recompute cold state on demand, evicting under memory pressure; it wins when the working set is far smaller than the full view universe (read-heavy web caches). ird chose full arrangements for predictable latency and simpler correctness, accepting higher memory (§4.1: ≤ 3× before compaction), and defers partial-state eviction.

Apache Flink (CA-4) recovers via Chandy-Lamport checkpoint barriers across a distributed operator graph and tracks event time with watermarks; it wins for large distributed stream processing with event-time windows. ird uses a WAL + checkpoint on a single process because its correctness oracle is incremental==batch (MM4), not at-least/exactly-once message delivery.

Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived from §4.1. Assume an Update triple ≈ 32 B on the wire/log (data key + time + diff + framing).

  • C1 — Input ingest bandwidth. 500 K updates/s × 32 B = 16 MB/s sustained per view (§4.1 throughput). A single NVMe and one core absorb this; CPU consolidation, not I/O, is the limit.
  • C2 — WAL write bandwidth. 16 MB/s × 1.5 (amplification, §4.1) = 24 MB/s to the WAL; with group-commit fsync this is well inside NVMe write budgets and bounds the p99 20 ms latency during fsync.
  • C3 — Arrangement memory, pre-compaction. A 16 GB raw arrangement (§4.1 tested ceiling) × 3 (all time versions before compaction) = up to 48 GB transient; compaction must keep pace or the box OOMs — motivates logarithmic merge (MM6, Phase 6).
  • C4 — Arrangement memory, steady state. 16 GB × 1.1 = 17.6 GB after compaction (§4.1); the 0.1 overhead is the index/antichain bookkeeping.
  • C5 — Checkpoint size & recovery I/O. Checkpoint = 1.2 × 17.6 GB ≈ 21 GB; to recover a 10 GB arrangement in < 60 s (§4.1) requires ≥ 170 MB/s restore throughput — feasible on NVMe, not on spinning disk.
  • C6 — File-descriptor budget. 128 base + 2 × 1000 changefeeds + 4 × WAL/checkpoint files ≈ 2 150 FDs at max subscribers (§4.1); requires ulimit -n ≥ 4096.
  • C7 — Join cost. At 100 K delta-pairs/s (§4.1) and ~10 matches/probe average, each side's arrangement is probed 100 K × 10 = 1 M lookups/s; the L2-resident cursor (≤ 256 KB working set, §4.1) keeps this cache-friendly.
  • C8 — Changefeed fan-out. 1 000 subscribers × notification ≤ 2 ms after frontier advance (§4.1): a single waker sweep over 1 000 wakers must complete inside the 2 ms budget ⇒ ≤ 2 µs/waker — argues for batched wake, not per-subscriber syscalls.
  • C9 — Multi-view memory. 100 active views (§4.1), even at a modest 256 MB arrangement each, = 25.6 GB resident; large arrangements force fewer concurrent views or eviction (deferred partial state).
  • C10 — Reduce throughput vs input. Reduce sustains 200 K key-deltas/s (§4.1); against 500 K input updates/s, a reduce-heavy plan is the bottleneck at 0.4× the ingest rate — plan accordingly.
  • C11 — Recovery replay tail. WAL decode ≈ 100 K rows/s (§4.1 glossary): a 1 M-row WAL tail replays in ≈ 10 s, matching the stated recovery target.
  • C12 — Frontier antichain size. For a single-input linear chain the frontier is a single time (antichain size 1); for an n-way join it is bounded by the product of input frontiers — kept small (≤ a few elements) by advancing inputs in lock-step (MM3, MM10).

Alternative Architectures (Roads Not Taken)

Alt-A — Periodic full recomputation (batch refresh).

inputs --> [ store ] --(every T seconds)--> recompute whole view from scratch --> publish

Wins when: views are small, freshness tolerance is minutes, and engineering simplicity dominates (nightly BI rollups). Embodied by: classic materialized-view REFRESH in PostgreSQL/Oracle. Rejected because: the core requirement is sub-5 ms p95 incremental latency (§4.1); full recompute is O(view) per refresh and cannot meet it.

Alt-B — Trigger-based incremental view maintenance in an RDBMS.

base table --row trigger--> hand-written delta SQL --> update summary table

Wins when: you live inside an existing RDBMS, the views are few and simple, and you want no new infrastructure. Embodied by: hand-rolled IVM with triggers, some commercial IVM extensions. Rejected because: triggers do not compose across joins/aggregates correctly under concurrency, and they lack a progress/frontier model (MM3); correctness becomes per-view bespoke rather than provable (MM4).

Alt-C — Partial materialization with upqueries (Noria model).

reads --miss--> upquery recomputes cold state --> fill cache --> evict under pressure

Wins when: the hot working set is far smaller than the full view universe and reads dominate (web app read caches). Embodied by: Noria. Rejected (deferred) because: upquery latency is unpredictable (cold reads pay recompute) and complicates the incremental==batch oracle; ird chooses full arrangements for predictable latency, deferring eviction (Deferred Features Register).

Alt-D — Distributed timely dataflow across a cluster.

inputs --partition--> worker[0..N] each runs operator graph; exchange edges shuffle by key

Wins when: a single machine cannot hold the arrangements or sustain the throughput (multi-TB state, >1 M updates/s). Embodied by: Naiad, Materialize cloud. Rejected because: distribution adds network exchange, fault-tolerant coordination, and rack-aware placement (all deferred); the blueprint targets a single embeddable process where the dataflow loop stays single-threaded (MM7).

Glossary

Alphabetical. Each term is implementation-relevant and operationally precise.

Term Definition
Antichain A set of timestamps such that no element is less-than-or-equal to any other; a Frontier is an antichain; the minimal description of a progress lower bound.
Arrangement Indexed, time-versioned shared state built from Batches; keyed by Key, holding (Val, Timestamp, Diff) sorted by key then time; shared read-only across operators (P6).
Batch An immutable, compacted, time-sorted run of (Key, Val, Timestamp, Diff) records covering a contiguous key range; the unit of arrangement storage and merge.
Capability A token granting an operator the right to emit updates at times ≥ some Timestamp; dropping all capabilities at a time advances the downstream frontier (P5).
Changefeed A subscription emitting consolidated output Updates as the output frontier advances; monotonic, gap-free; the streaming interface to a maintained view (ird-query).
Collection A multiset over D evolving in logical time; represented as a stream of Update<D> triples; the central abstraction of ird-collection.
Common sub-expression (CSE) Two views sharing an intermediate operator's Arrangement rather than each computing it separately; implemented in ird-server to bound memory (P6).
Compaction Merging Batches in a Trace below the since-frontier; times that can no longer be distinguished are collapsed, bounding trace size (I7, P7).
Consolidation Group updates by (data, time), sum their Diffs, drop records where net Diff = 0; produces canonical multiset representation (I2).
Delta-join The incremental join algorithm: for a new delta on one side, look up matching keys in the other side's Arrangement as-of the delta's time, emit product deltas; symmetric on both sides (Phase 8, I5).
Diff Diff(i64) — the signed multiplicity of a record in a Collection; +1 = insert, -1 = retraction; multiplicities sum under consolidation (I8).
Differential dataflow A computation model where operators consume and emit Collections of Update triples; work is proportional to input change, not total data size (P2); see McSherry et al., CIDR 2013.
Distinct A stateful unary operator that outputs each record with multiplicity 1 whenever its input multiset is non-empty; correct under retractions (I6, Phase 7).
Frontier An antichain of Timestamps representing the lower bound on future times an edge or operator may still produce; never moves backward (I3).
IVM (Incremental View Maintenance) Maintaining a materialized view's output current by processing only the changes (deltas) to the base relations rather than recomputing the view from scratch.
InputHandle The driver for a base relation: exposes send(Update), advance_to(Timestamp), flush; advances the base time frontier after a batch is flushed (ird-input).
Join (delta-join) See delta-join. The central stateful binary operator; correctness across concurrent updates and retractions is I5.
Lattice A partial order with join (least upper bound) and meet (greatest lower bound) operations on Timestamps; required for Frontier antichain arithmetic.
Logical time A Timestamp drawn from a partially ordered set (lattice); not wall-clock; used to version updates and determine frontier completeness (P4).
Materialized view A named query result stored as a maintained Arrangement; kept correct under input changes by incremental operators; exposed via peek and changefeed (ird-view).
Multiset A set permitting duplicate elements; membership tracked by net Diff; the semantic domain for all Collections.
Negate A stateless unary operator that flips the sign of every Diff; used to implement set difference as concat(A, negate(B)) (Phase 3).
Operator A trait: consumes input Update batches and a Frontier, emits output Update batches and advances its output Frontier; stateless (map, filter) or stateful (arrange, reduce, join).
Peek A point-in-time consistent read: returns the consolidated multiset of a view at a frontier-complete time t; equivalent to a from-scratch batch recompute (I1, I4, Phase 11).
Plan An operator tree (Map, Filter, Join, Reduce, Distinct, Union, Negate) compiled from a SQL-subset view definition by ird-plan; the intermediate representation between SQL and ird-dataflow.
Progress protocol The mechanism by which Capability tokens and ProgressMsg frontier updates propagate through the dataflow graph, allowing downstream operators to know when a time is complete (P5, ird-time).
Reduce A stateful keyed operator: per-key fold producing output deltas as input deltas arrive; maintains input and output Arrangements; must emit correct retractions when input decreases (I6, Phase 7).
Retraction An update with Diff = -1 (or negative); represents deletion or correction; every operator — including join and reduce — must process retractions correctly (P3).
Since-frontier The lower bound on the compacted portion of a Trace; times below the since-frontier have been merged and are no longer distinguishable; queries at or after are unaffected (I7).
Threshold A stateful unary operator that passes records only when their net input multiplicity meets a threshold; generalisation of distinct; correct under decrements.
Timely dataflow A dataflow execution model with explicit timestamps and progress tracking via capabilities and frontiers; provides the coordination mechanism for differential dataflow; see Murray et al., SOSP 2013.
Timestamp A member of the logical time lattice; defines the version of an Update; partially ordered; used to compute frontiers and as-of lookups in Arrangements.
Trace Synonym for Arrangement in the implementation; an Arrangement's underlying indexed, compactable, time-sorted store of Batches (ird-arrange).
Update Update<D> = (data: D, time: Timestamp, diff: Diff); the atomic unit of change in the system; all operators consume and emit sequences of Updates.
ViewDef { name, sql, plan, output_arrangement }; the registered specification of a materialized view in ird-view; the basis for building a dataflow subgraph and maintaining output state.
WAL (Write-Ahead Log) Append-only log of input Update triples, written before arrangements are updated; the source of truth (P9); used in recovery to replay deltas from a checkpoint to a consistent frontier (I10).
Z-set The DBSP formalism for a signed multiset (map D → ℤ); isomorphic to a Collection consolidated at a single time; the algebraic object differential operators act on (see Budiu et al., VLDB 2023).
