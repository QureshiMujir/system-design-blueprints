Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If early-Z is defeated by a discard shader (§17), how much of the Phase 9 roofline classification for that draw call is actually attributable to the resulting late-Z bandwidth doubling versus the shader's own arithmetic cost? (§17, §21)
  2. Does the Hi-Z mip-chain's conservativeness invariant (I8) still hold if two draw calls in the same pass write overlapping depth ranges out of submission order? (§7, §17)
  3. When a tiny-triangle quad-overshading storm (§8.12) coincides with a heavily divergent fragment shader (§14), do the two waste terms compound multiplicatively or does one dominate — and does the model currently report that interaction correctly? (§18, §34)
  4. Is the TBDR bandwidth-savings formula (~2V, §8.8) still accurate when the binning pass itself has to spill because a tile's primitive list exceeds the modeled tile-buffer SRAM capacity? (§22, §4)
  5. How does the differential-fidelity gate (Phase 11) distinguish a genuine model bug from a case where Mesa and SwiftShader themselves disagree at the sub-pixel level? (§23.8, §28)
  6. Does the occupancy model's min() of three limiters (§8.3) correctly capture a scenario where the scheduler limit itself depends on the current divergence rate, or are these treated as independent when they are not? (§14, §21)
  7. If a scene is exactly at the roofline ridge point (§8.10), is the model's bandwidth-bound/compute-bound classification stable under small measurement noise, or does it flicker? (§21.8, §30)
  8. Does the texture-cache-locality argument (§8.6) still hold for anisotropic filtering, which samples across a footprint rather than a single texel neighborhood? (§19.8, §8.5)
  9. What happens to I6's single-flush-per-tile guarantee if a render pass is aborted mid-frame (a chaos scenario, §23) — does the model correctly avoid a partial, silently-wrong flush? (§22, §25 FM-7)
  10. Is the sim-to-wall-clock ratio (M1, §30) roughly constant across scene types, or does it vary enough between bandwidth-bound and compute-bound scenes that a single target number is misleading? (§30, §31)
  11. Given that Larrabee's software-rasterization bet failed on power/performance (§33), what specifically in this project's fixed-function/programmable split (P2) would have to change for a hypothetical "software-only" mode to be architecturally honest rather than just a toy? (§33, §36)
  12. Does the model's abstract-ISA representation (ADR-19) risk understating divergence cost relative to a real compiler's control-flow optimizations (e.g., branch predication)? (§14, §9)
  13. If VRAM bandwidth is upgraded in the configuration (a scaling lever, §31) without also scaling texture-cache size, does the roofline classification shift in a way that is still internally consistent with §8.6's locality argument? (§31, §19)
  14. How does the model account for the geometry-binning latency of TBDR (§22.6) in a scene with exactly one draw call per frame, where there is no pipelined overlap to hide that latency behind? (§22, §30)
  15. Is the exactly-once-coverage property (I1) still well-defined at a T-junction (three or more triangles meeting at a non-manifold vertex), or does the fill rule's guarantee implicitly assume a strictly manifold, 2-triangles-per-edge mesh? (§16, §7)

32. Mental Models & First Principles

  • MM1 — a GPU hides latency with parallelism instead of avoiding it: thousands of warps in flight so that while one waits on memory another computes, which is why occupancy and bandwidth, not clock, decide performance (Lindholm et al., NVIDIA Tesla).
  • MM2 — almost everything expensive about a fragment is memory, not math: texture fetches and framebuffer traffic dominate, so the whole hardware pipeline exists to feed the ALUs, not to add more of them (§8.10, §34).
  • MM3 — TBDR trades on-chip SRAM for VRAM bandwidth by binning geometry per tile and resolving once — mobile GPUs made that trade because bandwidth is power, and power is the mobile constraint (PowerVR/Mali whitepapers, P8).
  • MM4 — the top-left fill rule is not an arbitrary tie-break, it is the mechanism that makes "watertight mesh in, watertight coverage out" a provable property rather than a hope (Pineda 1988, I1).
  • MM5 — fixed-function hardware exists precisely where every draw call needs the same operation done the same way — rasterization, depth test, and blend are not "simpler" than shading, they are simply universal (P2).
  • MM6 — a quad is the smallest unit that can answer "how fast is texture coordinate changing here," and that single design choice (2x2 grouping) is why mip-mapping and helper-lane waste are the same coin's two faces (Williams 1983, P3).
  • MM7 — divergence is a throughput tax, not a correctness hazard: the SIMT model pays for a data-dependent branch in wasted lane-cycles, never in a wrong answer (I5, P9).
  • MM8 — a performance model is only as trustworthy as its last differential test against a real implementation; self-consistency is necessary but never sufficient (P12, Phase 11).
  • MM9 — sort-middle (binning) is a real point on a real taxonomy, not a TBDR-specific trick — the same idea recurs anywhere geometry must be bucketed before the expensive per-pixel work begins (Molnar et al. 1994, P13).
  • MM10 — the roofline model turns "is this fast" into "is this bandwidth-bound or compute-bound," which is a more useful question because it tells you which lever to pull (§8.10, §34).

Reference Implementations

  • Mesa src/gallium/drivers/llvmpipe — a CPU software GPU driver with a real rasterizer core. Lesson: how a documented pipeline stage order maps to real code. Pitfall: it optimizes for wall-clock speed, not architectural transparency — do not copy its fused stages verbatim. Applied in Phase 11.
  • Mesa src/gallium/drivers/softpipe — the reference (non-optimized) Gallium driver. Lesson: the clearest mapping from Gallium's stage abstraction to the fixed-function/programmable split. Applied in Phase 0 and Phase 11.
  • SwiftShader src/Pipeline/ and src/Device/ — a production CPU Vulkan implementation. Lesson: how quad-based fragment shading and derivatives are implemented for real. Pitfall: SwiftShader targets correctness+speed, not per-stage telemetry — the model must add its own instrumentation. Applied in Phase 6 and Phase 11.
  • MIAOW (open-source AMD-Southern-Islands-derived GPU RTL, teaching-oriented) and Nyuzi (Jeff Bush's GPGPU). Lesson: a from-scratch open GPU ISA/warp design at a level below what this project models. Pitfall: RTL-level detail is out of scope (fidelity level, §1) — use for cross-checking the warp/SIMT model only. Applied in Phase 2.
  • The Vulkan/OpenGL Conformance Test Suite (CTS) — rasterization-rule conformance tests. Lesson: the normative fill-rule and coverage test vectors. Applied in Phase 4 and Phase 11.
  • RenderDoc — a real GPU frame-capture and pipeline-state inspector. Lesson: the per-stage pipeline-trace UX this project's graster-viz imitates. Applied in Phase 0 and §26.

RFCs / Specifications

Glossary (§38) · 50 terms · site-wide glossary

Rasterization
Converting a geometric primitive into a set of covered pixels/samples.
Triangle setup
Computing a triangle's edge functions and bounding box before coverage evaluation.
Edge function
A linear function of screen position used to test which side of a triangle edge a point lies on (Pineda 1988).
Top-left fill rule
The tie-break rule ensuring a shared edge between two triangles is rasterized by exactly one of them.
Coverage
The set of samples/pixels a primitive is determined to overlap.
Hierarchical-Z (Hi-Z)
A mip-chain of conservative depth bounds used to reject occluded screen tiles before shading.
Early-Z
A depth test performed before fragment shading, valid only when the shader cannot change depth/discard.
Late-Z
The fallback depth test performed after fragment shading when early-Z is defeated.
Depth test
Comparing a fragment's depth against the stored depth buffer value to determine visibility.
Stencil
An auxiliary per-pixel value used for masking and multi-pass effects.
Fragment
A candidate pixel-sample produced by rasterization, prior to and during shading.
Quad
A 2x2 group of fragments shaded together so screen-space derivatives are defined.
Screen-space derivative
The rate of change of an interpolated value across screen space, used for mip selection.
Mip LOD
The mipmap level of detail selected based on screen-space derivative magnitude.
SIMT
Single-Instruction-Multiple-Thread: the GPU execution model where many threads (lanes) execute one instruction stream in lockstep, masked individually.
Warp
A group of lanes (commonly 32) executing in lockstep under SIMT (NVIDIA terminology).
Wavefront
AMD's term for the SIMT execution group, commonly 64 lanes.
Lane
One scalar thread within a warp/wavefront.
Execution mask
The per-lane active/inactive bitmask used to implement divergent control flow.
Divergence
When lanes within a warp take different control-flow paths, requiring serialized execution of each path.
Reconvergence
The point where divergent lanes resume executing together after all paths complete.
Occupancy
The number of warps resident and schedulable on an SM/CU, bounded by register/shared-memory/scheduler limits.
Register file
The on-chip storage holding each thread's registers.
SM/CU
Streaming Multiprocessor (NVIDIA) / Compute Unit (AMD): the GPU's core execution block hosting multiple warps.
Latency hiding
Covering memory-access latency by switching to another resident warp instead of stalling.
Texture unit
The fixed-function hardware that resolves texture addresses, fetches, and filters texels.
Texel
A single texture element (the texture-space analog of a pixel).
Morton order (Z-order/swizzle)
A bit-interleaved addressing scheme that maps 2D coordinates to a locality-preserving 1D address.
Texture cache
The cache hierarchy (commonly L1 per-SM, shared L2) serving texture fetches.
ROP
Raster Operations (pipe): the fixed-function unit performing depth/stencil test, blend, and framebuffer writeback.
Output merger
Direct3D's term for the ROP stage.
Blend
Combining a new fragment's color with the existing framebuffer color per a configured equation.
MSAA
Multisample Anti-Aliasing: sampling coverage/depth at multiple sub-pixel positions, shading once, resolving to one color.
Sample
One sub-pixel coverage/depth/color slot within a multisampled pixel.
Resolve
Filtering a multisampled pixel's per-sample values down to a single displayable value.
Overdraw
The number of times a given pixel is shaded/written within a frame due to overlapping geometry.
Fill rate
The rate (pixels/clock or pixels/second) at which the ROP can process fragments.
IMR
Immediate-Mode Rendering: rasterizing and resolving each primitive directly against the framebuffer as it arrives.
TBDR
Tile-Based Deferred Rendering: binning all geometry per screen tile before shading and resolving once.
Tile buffer
The on-chip SRAM accumulating a tile's color/depth across a TBDR render pass before flush.
Binning
The TBDR pass that assigns primitives to the screen tiles they overlap.
Sort-first/middle/last
Molnar et al.'s taxonomy for where a parallel-rendering architecture binds geometry to screen regions.
Memory bandwidth
The rate at which data can move between a processor and memory (register file/cache/VRAM).
Roofline model
A performance model bounding achievable throughput by the lesser of peak compute and peak-bandwidth-times-arithmetic-intensity.
Arithmetic intensity
The ratio of floating-point operations to bytes moved, used to classify a workload as bandwidth- or compute-bound.
Command processor
The fixed-function front end that decodes and issues draw calls to the execution units.
Draw call
A single unit of rendering work submitted by the application (a mesh plus pipeline state).
Cycle-approximate
A simulation fidelity level matching published architecture timing constants without gate-level accuracy.
Differential testing
Validating a model's output by comparing it against an independent reference implementation on the same input.
Helper lane
A lane in a partially-covered quad that executes the shader for derivative purposes but discards its output.
