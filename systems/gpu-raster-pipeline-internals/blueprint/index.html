191 — GPU Raster Pipeline Internals

Project Number: 191

Project Name: GPU Raster Pipeline Internals

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

GPU Raster Pipeline Internals (191) builds a cycle-approximate model and simulator of a modern GPU's hardware rasterization pipeline, written in Rust. It is not a renderer that draws pixels for its own sake — it is a teaching/analysis instrument: a simulation library that ingests a stream of draw calls, drives each one through modeled pipeline stages (command processor, vertex fetch, the programmable vertex stage running as warps/wavefronts under SIMT, primitive assembly and clipping, the fixed-function rasterizer with triangle setup and edge-function coverage and hierarchical-Z, early-Z, the programmable fragment stage running in warps with 2x2-quad derivatives, the texture units and their cache hierarchy, and the ROP/output-merger doing depth/stencil test, blend, and MSAA resolve), and reports the same class of numbers a GPU architect reasons about day to day: fill rate, fragments/cycle, warp occupancy, texture-cache hit rate, warp-divergence rate, overdraw factor, and memory-bandwidth utilization. Its acceptance criterion is fidelity to documented GPU behavior (the Vulkan/OpenGL rasterization rules, the pipeline-stage order in the Real-Time Rendering GPU-architecture chapter, and the empirical claims in Fabian Giesen's "A trip through the Graphics Pipeline 2011" series) — not a rendered image.

Phase-0 Deliverable — Crate List

  1. graster-core — shared pipeline-stage traits, cycle/event scheduling primitives, error taxonomy.
  2. graster-math — homogeneous-coordinate math, barycentrics, fixed-point edge arithmetic.
  3. graster-cmdproc — command processor / draw-call front end, draw-call decode and validation.
  4. graster-isa — abstract shader ISA representation (not a real compiler; a modeled instruction stream).
  5. graster-simt — the SIMT/warp execution engine, execution masks, divergence and reconvergence.
  6. graster-geom — vertex fetch, the vertex shader stage, primitive assembly, clipping.
  7. graster-raster — triangle setup, edge-function rasterization, the top-left fill rule, hierarchical-Z.
  8. graster-frag — the fragment shader stage, quad grouping, screen-space derivatives.
  9. graster-tex — texture units, address/swizzle (Morton order), the texture cache model.
  10. graster-rop — the ROP/output-merger: depth/stencil test, blend equations, MSAA resolve.
  11. graster-mem — the memory-hierarchy model: register file, L1/L2, VRAM, bandwidth accounting.
  12. graster-tbdr — the tile buffer and TBDR binning/resolve mode.
  13. graster-occupancy — the occupancy model (register-limited / shared-mem-limited / scheduler-limited).
  14. graster-trace — the draw-call/trace file format, deterministic replay.
  15. graster-stats — PipelineStats telemetry aggregation and per-stage counters.
  16. graster-viz — the RenderDoc-like per-stage pipeline-trace visualizer.
  17. graster-cli — the driver binary: loads a trace, runs the simulation, emits stats.
  18. graster-conformance — differential tests against Mesa llvmpipe/SwiftShader/Vulkan CTS rasterization rules.
  19. graster-fuzz — fuzz harnesses for the draw-call/trace parser and the geometry path.
  20. graster-bench — throughput and roofline-validation benchmarks.
  21. graster-docs — architecture notes, ADRs, runbooks.

Boundaries

Provides: a stage-accurate behavioral and performance model of the fixed-function and programmable GPU raster pipeline, from draw-call issue to shaded, resolved pixels in a modeled framebuffer; a numeric performance model (fill rate, occupancy, bandwidth) validated against published architecture behavior; a trace-driven, replayable simulation with per-stage telemetry.

Delegates to a host application: actual on-screen display/presentation, windowing/swapchain integration, real GPU driver/API plumbing (Vulkan/OpenGL/Metal), and real shader compilation — the fragment/vertex "shaders" here are abstract ISA traces (graster-isa), not compiled GLSL/HLSL/SPIR-V.

Does NOT provide: a real GPU driver, a shader compiler, gate-level or RTL hardware simulation, a ray tracer, or a general 3D renderer meant to produce pretty images.

Non-Goals

This is explicitly not Software-Rasterizer / 3D Renderer (project 169, already REAL-GOD). 169 is a CPU software rasterizer whose job is to draw images — its acceptance criterion is a correct picture. 191 is a model of GPU hardware's raster pipeline and its performance characteristics — a teaching/analysis simulator whose acceptance criterion is fidelity to documented GPU behavior (Vulkan/OpenGL rasterization rules, the Giesen pipeline series, the NVIDIA Tesla SIMT paper), not a pretty image. 191 is also not Ray-Tracer (170), which traces rays as its visibility algorithm, and not CUDA-Kernel-Fusion (248), which fuses general compute kernels rather than modeling the fixed-function graphics pipeline. 191 does not implement a real driver, a real shader compiler, or hardware ray tracing, and it does not target gate-level or SPICE-level circuit fidelity.

Fidelity Level

Cycle-approximate: stage latencies, occupancy, and bandwidth are modeled with published, order-of-magnitude-correct constants (warp width, ROP throughput, VRAM GB/s) and event-driven stage timing, not cycle-accurate RTL replay. Architecturally faithful: the stage order, the SIMT/warp execution model, the quad/derivative rule, the fill rule, and the TBDR/IMR distinction all follow documented GPU architecture (Real-Time Rendering, the Giesen series, the NVIDIA Tesla paper, the PowerVR/Mali TBDR whitepapers) exactly. Not gate-level: no transistor, pipeline-latch, or clock-domain-crossing modeling.

Reference Architecture

Primary reference: a modern desktop immediate-mode-rendering (IMR) GPU as documented in the Real-Time Rendering GPU-architecture chapter and Lindholm et al.'s NVIDIA Tesla SIMT/warp architecture — warp width 32, SM/CU-based occupancy, ROP-driven output merging, VRAM-bandwidth-dominated. Contrasted throughout with a tile-based-deferred (TBDR) mode modeled after the Imagination PowerVR and ARM Mali architecture documentation — wavefront width may differ (commonly 32 or 64, configurable in the model), on-chip tile buffer, bin-then-resolve.

Deployment Model

A simulation library (graster-core plus the stage crates) linked by a trace/draw-call driver (graster-cli, which loads a graster-trace file and steps the modeled pipeline) and a stats visualizer (graster-viz, a RenderDoc-like per-stage inspector reading graster-stats output). No network service, no persistent server — an offline analysis tool.

Users / Operators

Primary users: graphics and GPU-architecture engineers validating a performance intuition before touching real hardware or a real driver; computer-architecture students and teaching assistants building coursework around the SIMT/warp model, the fill rule, or the TBDR/IMR tradeoff; performance engineers prototyping a roofline argument. Operators: CI maintainers running the differential-fidelity gate against Mesa/SwiftShader/CTS; benchmark maintainers tracking the sim's own throughput.

What Later Phases Unlock

Warp-divergence-aware occupancy reporting (Phase 2) unlocks realistic fragment-stage throughput modeling (Phase 6). The texture-cache model (Phase 7) unlocks a real bandwidth accounting for the roofline model (Phase 9). The TBDR mode (Phase 10) unlocks the central IMR-vs-TBDR bandwidth-savings comparison that anchors the project's teaching value. Phase 11's differential validation against Mesa llvmpipe/SwiftShader/Vulkan CTS is the gate that converts "plausible model" into "fidelity-checked model."

Rust — Rationale and Rejected Languages

Rust is chosen for: memory safety in a long-lived simulation core that must run for hours during a fuzz/soak campaign without heap corruption masking a fidelity bug; explicit ownership, which keeps the memory-hierarchy model's register-file/cache/VRAM ownership unambiguous (no aliased mutable state pretending to be a cache line); zero-cost abstractions suited to the warp/lane SIMD-shaped ExecMask code; strong enum modeling for the many small pipeline-stage state machines (tile states, warp states); a mature proptest/fuzzing ecosystem needed for the fill-rule and coverage invariants (I1, I2).

Rejected: C++ — unsafe aliasing makes the memory-hierarchy ownership model harder to keep sound at this scale; Zig — ecosystem immaturity for the differential-testing tooling needed against Mesa/CTS; Python — acceptable for prototyping the stats visualizer but rejected as the simulation-core language, too slow for the warp-level inner loop; C — no type-level modeling for the stage-typed pipeline, error-prone for the ADR-02 (fidelity model) invariants.

Prerequisites

Linear algebra (homogeneous coordinates, barycentric interpolation, perspective-correct division); computer architecture (cache hierarchies, pipelining, SIMD, latency hiding, occupancy); the graphics pipeline (the fixed-function/programmable split, rasterization rules, the Vulkan/OpenGL stage order).

Timeline

Phase 0: 3 weeks. Full 12-phase implementation (Phases 0-11): 10-14 months. Production hardening (differential-fidelity gate, fuzzing, soak): additional 2-3 months.

2. Why Build This

  • teaches the SIMT/warp execution model and why occupancy, not clock speed, sets throughput (NVIDIA Tesla, Lindholm et al.)
  • teaches the fixed-function/programmable split and why rasterization, depth test, and blend are still hardware
  • teaches the edge-function rasterization algorithm (Pineda 1988) and the top-left fill rule that guarantees exactly-once coverage
  • teaches hierarchical-Z and early-Z as bandwidth-saving optimizations, and when they degrade to late-Z
  • teaches the quad/derivative model — why fragments run in 2x2 groups and what that costs at triangle edges
  • teaches the texture-cache locality argument and Morton/swizzle addressing (Morton 1966)
  • teaches the ROP/output-merger ordering rules (depth-test-then-blend) and MSAA resolve semantics
  • teaches the IMR-vs-TBDR tradeoff (bandwidth vs on-chip SRAM, geometry-binning latency) as documented by the PowerVR/Mali architecture whitepapers
  • teaches the roofline/bandwidth model that dominates real GPU performance reasoning
  • teaches the sort-first/middle/last taxonomy for parallel rendering (Molnar et al. 1994)
  • gives an engineer who has only ever called a graphics API a mental model of what happens underneath it
  • builds the discipline of validating a performance model against a real reference (Mesa llvmpipe, SwiftShader, the Vulkan CTS) instead of trusting intuition

What Mastery Looks Like

  • can explain, from the model's own event trace, why a scene with many tiny triangles tanks fragment-shader efficiency via quad overshading (Phase 6)
  • can compute occupancy by hand from register/shared-memory limits and have the simulator agree (Phase 2, Phase 9)
  • can predict, before running the sim, whether a scene is bandwidth-bound or compute-bound using the roofline equation (Phase 9)
  • can explain why a given draw call defeats early-Z (a discard or depth-writing fragment shader) and see the fallback to late-Z in the trace (Phase 5)
  • can quantify the VRAM-bandwidth savings TBDR achieves over IMR for a specific scene and overdraw factor (Phase 10)
  • can point to the exact edge-function evaluation and top-left tie-break that gives a shared edge between two triangles coverage exactly once (Phase 4)
  • can read a per-stage pipeline trace (the model's RenderDoc-like artifact) and localize a performance regression to one stage (Phase 11)
  • can defend, citing the differential-fidelity CI gate, that the model's numbers are not just plausible but validated against Mesa/SwiftShader/CTS behavior (Phase 11)

Command Processor / Draw-Call Front End: decodes each draw call, validates pipeline state, and issues geometry work to the modeled SMs/CUs; fixed-function, models the ADR-19 draw-call front end.

Vertex Fetch + Vertex Shader Stage: fetches vertex attributes and runs the abstract-ISA vertex program across warps under SIMT (I5); programmable, on-chip register-file resident (§11 SimtCore).

Primitive Assembly + Clipping: assembles shaded vertices into primitives, clips against the view frustum; fixed-function, feeds the rasterizer only well-formed primitives.

Rasterizer (Triangle Setup, Edge Evaluation, Coverage, Hi-Z): computes edge functions (Pineda 1988), applies the top-left fill rule (I1), and uses hierarchical-Z to reject fully-occluded tiles before fragment generation; fixed-function.

Early-Z: tests fragment depth before shading when the fragment shader cannot change depth/discard (I3); fixed-function, bandwidth-saving.

Fragment Shader Stage: runs the abstract-ISA fragment program across warps grouped into 2x2 quads so screen-space derivatives are defined (I2); programmable, on-chip register-file + L1 resident.

Texture Units + Texture Cache: resolve texture addresses through Morton/swizzle order, sample through the modeled cache hierarchy, and filter; on-chip L1 texture cache backed by L2/VRAM.

ROP / Output-Merger: performs the depth/stencil test, then blend, then MSAA resolve in that fixed order (I4); fixed-function, the final arbiter of framebuffer writes.

Memory Hierarchy: register file and L1/L2 caches on-chip, VRAM off-chip; the dominant performance limiter per the roofline model (§8, §34).

Tile Buffer (TBDR mode): an on-chip SRAM buffer accumulating a screen tile's fragments across the whole draw before one VRAM flush, trading on-chip capacity for VRAM bandwidth (I6, §22).

6. Design Principles

  • P1 — the GPU is a throughput machine, not a latency machine: it hides memory latency with massive warp parallelism, so occupancy and bandwidth, not clock speed, set performance (NVIDIA Tesla, Lindholm et al.). Applied via Occupancy (§11) and Phase 9.
  • P2 — the pipeline is mostly fixed-function with programmable islands: rasterization, depth test, and blend are hardware because they are identical for every draw call, and modeling that split faithfully is the point (I3, I4). Applied in §3 and Phase 4/5/8.
  • P3 — fragments execute in 2x2 quads so screen-space derivatives (for mip selection) are free, but that means helper lanes and quad-granularity waste at triangle edges, which the model must expose, not hide (I2). Applied in Phase 6.
  • P4 — acceptance is fidelity to documented GPU behavior (the Vulkan/OpenGL rasterization rules, the Giesen articles), not a rendered image (§1 non-goals). Applied throughout, gated in Phase 11.
  • P5 — the top-left fill rule exists so a shared triangle edge is rasterized by exactly one of the two adjoining triangles — never both, never neither (I1, Pineda 1988). Applied in Phase 4.
  • P6 — early-Z is an optimization, not a guarantee: it only applies when the fragment shader cannot change depth or discard, and the model must fall back to late-Z faithfully when it cannot (I3). Applied in Phase 5.
  • P7 — hierarchical-Z trades a coarse conservative test for a bandwidth win: a tile fully behind known-nearer geometry is rejected before any fragment work, and the model must track the Hi-Z mip chain explicitly. Applied in Phase 5.
  • P8 — TBDR trades on-chip SRAM for VRAM bandwidth: binning geometry per tile and resolving once eliminates repeated off-chip read-modify-write traffic, at the cost of a full-scene geometry pass before any pixel is shaded (PowerVR/Mali whitepapers). Applied in Phase 10.
  • P9 — warp divergence is not a correctness hazard, it is a throughput hazard: both sides of a divergent branch execute under a mask, and the model must never lose a lane's result while faithfully reporting the wasted cycles (I5). Applied in Phase 2.
  • P10 — memory bandwidth dominates GPU performance more often than ALU throughput: the roofline model is the load-bearing analytical tool, and every stage's telemetry must feed it (Hennessy & Patterson). Applied in Phase 9 and §34.
  • P11 — the model is cycle-approximate, not cycle-accurate: constants are drawn from published architecture documentation, and the model must never claim gate-level precision it does not have (§1 fidelity level). Applied via ADR-02.
  • P12 — differential testing against a real implementation (Mesa llvmpipe, SwiftShader) and against the Vulkan CTS is the only trustworthy fidelity gate — self-consistency is not evidence of correctness. Applied in Phase 11 and §28.
  • P13 — sort classification (sort-first/middle/last, Molnar et al. 1994) is the right vocabulary for describing where a design binds geometry to screen tiles, and TBDR is a sort-middle architecture in this taxonomy. Applied in §8 and Phase 10.
  • P14 — every stage emits telemetry by default: a model whose internals are opaque cannot teach anything (§26). Applied via PipelineStats (§11).

I1 The rasterizer applies the top-left fill rule so a shared triangle edge is covered exactly once — no double-shading, no cracks. I8 Hierarchical-Z only rejects a tile when the Hi-Z value is conservative (never optimistic) relative to true depth. 8.2 The SIMT/Warp Execution Model

Named steps: (1) group N scalar threads (lanes) into one warp, N = warp width (32 or 64, ADR-05); (2) issue one instruction per cycle to all lanes in lockstep; (3) on a data-dependent branch, compute a per-lane predicate and push an ExecMask; (4) execute the taken side with the mask applied, inactive lanes idle; (5) execute the not-taken side symmetrically; (6) reconverge at the immediate post-dominator, popping the mask; (7) when a warp stalls on memory, the scheduler switches to another resident warp (latency hiding, P1).

Worked divergence example: a warp of 32 lanes executes if (fragment.depth < threshold) { A } else { B }. Suppose 20 lanes take branch A and 12 take branch B. The warp executes A with a 20-active/12-masked pass, then B with a 12-active/20-masked pass — 2 total passes instead of 1, so this warp's effective throughput for this instruction is halved relative to a non-divergent warp, active-lane fraction = 20/32 then 12/32, average 0.5. This is the quantity divergence_rate (I5) tracks.

8.3 Occupancy Equation

occupancy_warps = min(register_file_size / (registers_per_thread * warp_width), shared_mem_size / shared_mem_per_block, scheduler_max_warps)

Worked calculation: register file = 65536 32-bit registers/SM, registers_per_thread = 64, warp_width = 32 → register-limited warps = 65536 / (64*32) = 32. Shared memory = 96 KB/SM, shared_mem_per_block = 8 KB → shared-mem-limited warps-worth-of-blocks = 12 blocks, at 4 warps/block = 48 warps. Scheduler max = 64 warps/SM. occupancy_warps = min(32, 48, 64) = 32 — register-limited (I9 binds at the register ceiling here).

8.4 Triangle Setup and Edge-Function Rasterization (Pineda)

Named steps: (1) compute three edge functions E_i(x,y) = (x - x_i)*(y_j - y_i) - (y - y_i)*(x_j - x_i) for each triangle edge; (2) a point is inside iff all three edge functions share the reference sign (or zero, subject to the fill rule); (3) apply the top-left fill rule (I1): an edge is "top" if horizontal and above the triangle, "left" if it goes downward — points exactly on a top or left edge are inside, points on a bottom or right edge are not, so shared edges between adjacent triangles are covered by exactly one; (4) compute the bounding box of the triangle and iterate candidate pixels/quads within it; (5) accumulate coverage into a sample mask (for MSAA, one bit per sample position); (6) consult hierarchical-Z: if the tile's conservative far-Z bound is nearer than the triangle's nearest depth in the tile, reject the whole tile before generating fragments (I8, Greene/Kass/Miller 1993); (7) emit surviving fragments grouped into 2x2 quads (I2).

8.5 The Quad and Screen-Space-Derivative Model

mip_lod = log2(max(|d(u)/d(x)|, |d(u)/d(y)|, |d(v)/d(x)|, |d(v)/d(y)|) * texture_size)

Named steps: (1) shade a 2x2 quad together even if only one lane's fragment is covered (I2); (2) uncovered lanes become "helper lanes" — they execute the fragment shader for derivative purposes but their output is discarded; (3) compute du/dx, du/dy, dv/dx, dv/dy by finite difference across the quad; (4) feed the maximum derivative magnitude into the mip-LOD equation above (Williams 1983); (5) select or trilinearly blend between mip levels for the texture fetch.

8.6 The Texture-Unit Model

Named steps: (1) resolve (u, v) plus mip level to a texel address; (2) remap the address into Morton/Z-order swizzle for 2D cache locality (Morton 1966); (3) probe the L1 texture cache; (4) on miss, fetch from L2, then VRAM, populating the cache along the way; (5) apply the configured filter (nearest/bilinear/trilinear/anisotropic) across the fetched texels. The texture-cache-locality argument: because nearby screen-space fragments (within a quad, within a warp) tend to sample nearby texels, Morton-order swizzling turns a 2D access pattern into a cache-friendly 1D one, raising the L1 hit rate far above a naive row-major layout for the same working set.

8.8 IMR vs TBDR — Contrasted Sequence

IMR: (1) rasterize triangle, (2) shade fragments, (3) ROP reads current framebuffer pixel from VRAM, (4) ROP writes result back to VRAM — repeated per triangle touching that pixel (overdraw amplifies VRAM traffic).

TBDR: (1) bin all geometry for the frame/pass into per-tile primitive lists (a full geometry pass before any pixel shading — P8), (2) for each tile, rasterize and shade using the on-chip tile buffer (SRAM) for all read-modify-write traffic, (3) resolve the tile once to VRAM (I6).

Bandwidth-saving math for TBDR (see also §34): for a tile of P pixels with overdraw factor V, IMR VRAM traffic ≈ P * V * bytes_per_pixel * 2 (one read + one write per overdraw layer); TBDR VRAM traffic ≈ P * bytes_per_pixel (one write, no read, regardless of V) — savings factor ≈ 2V.

8.10 The Roofline / Bandwidth Model

achievable_throughput = min(peak_compute_flops, peak_bandwidth_GBps * arithmetic_intensity), where arithmetic_intensity = flops / byte. When a draw's arithmetic intensity is below the ridge point (peak_compute_flops / peak_bandwidth_GBps), the draw is bandwidth-bound and adding ALUs does not help (P10) — this is the central diagnostic §9/§30/§34 return to.

8.11 Worked Example — One Triangle to Shaded MSAA Pixels

A single opaque, screen-facing triangle covering a 32x32-pixel region, 4x MSAA, 16 B/pixel-sample framebuffer format: vertex fetch loads 3 vertices (fixed-function, negligible bandwidth); the vertex shader stage runs in one warp-pass (3 lanes active of 32, heavy waste — a case for instanced/batched vertex work in later phases); primitive assembly/clipping pass with no clipping needed; triangle setup computes 3 edge functions; rasterization walks the 32x32 bounding box, evaluates coverage per quad, and Hi-Z is not conclusive (triangle fully visible, no early tile reject); early-Z passes for all covered fragments (opaque, depth-writing, no discard, I3 does not defeat); the fragment stage shades 256 quads (1024 lanes) fully active, no helper-lane waste (interior triangle, no partial quads at this scale); texture unit performs one filtered fetch per fragment, mostly L1 hits due to Morton locality; ROP performs depth-test-then-blend (blend disabled, opaque) then MSAA resolves 4 samples/pixel to 1 final value (I7). Bandwidth accounting: VRAM write ≈ 1024 pixels * 16 B (post-resolve) = 16 KB; if this were IMR under 3x overdraw the VRAM read+write would triple; TBDR reduces the on-chip resolve to a single VRAM write regardless of overdraw (§8.8).

8.12 Malformed / Hard Examples

  • A degenerate (zero-area) triangle: all three edge function coefficients collapse, setup must detect and skip it rather than divide by zero.
  • A divergent warp tanking throughput: a fragment shader with a data-dependent loop where lane trip-counts vary 1-64x, active-lane fraction collapses toward 1/warp_width in the worst case (I5).
  • A texture-cache-thrashing access pattern: a shader sampling with a stride equal to the cache's associativity-induced conflict stride, driving L1 hit rate toward zero despite spatial locality existing in principle.
  • An early-Z defeat by a discard/depth-write shader: forces late-Z, doubling ROP-adjacent bandwidth relative to the early-Z path (I3).
  • Overdraw: a scene with back-to-front unsorted transparent geometry, V >> 1, directly inflating the IMR bandwidth term in §8.8/§34.
  • A tiny-triangle quad-overshading storm: sub-pixel triangles from aggressive tessellation or distant geometry, where each covered fragment still costs a full 2x2 quad, driving helper-lane fraction toward 3/4 (P3).

8.13 Failure-Path Example

A malformed draw call references a texture handle that was never bound: (1) the command processor's validation step (graster-cmdproc) detects the missing binding at decode time; (2) the draw call is rejected before entering the pipeline (fail-fast, no partial simulation state); (3) a structured PipelineStats validation-failure event is emitted, tagged with the draw-call ID and the invariant class (analogous to I10's bounds discipline); (4) graster-trace still records the rejected draw call for replay so the operator can reproduce the failure; (5) the CLI surfaces a diagnostic naming the missing binding.

  5. Reproduce the §8.3 worked occupancy calculation (32 warps, register-limited) as a fixture and assert the calculator agrees exactly.
  6. Build a roofline-validation benchmark comparing the model's predicted achievable throughput against Hennessy & Patterson's documented roofline methodology on a synthetic sweep of arithmetic intensities.
  7. Cross-reference Owens et al.'s "GPU Computing" and Lindholm et al.'s NVIDIA Tesla paper for the occupancy-vs-throughput relationship's documented shape.

21.3 Deliverable

An occupancy calculator and roofline model consuming every prior stage's telemetry, classifying each draw call as bandwidth-bound or compute-bound and reporting achievable throughput.

21.4 Acceptance Criteria

  • The §8.3 worked example reproduces exactly: occupancy_warps = min(32, 48, 64) = 32, register-limited (I9).
  • Roofline-predicted achievable throughput matches the synthetic-sweep reference within 5% across the arithmetic-intensity range tested.
  • Zero occupancy_ceiling_violation_count across all conformance fixtures (I9, structurally enforced by construction).

21.6 Pitfalls

  • Computing occupancy from only one limiter (e.g., registers only) and silently ignoring shared-memory or scheduler limits, violating I9's min() semantics.
  • Classifying a draw call's roofline regime using peak (not achieved) bandwidth, overstating how compute-bound a scene actually is.
  • Treating the simulator's own event-processing cost as if it were the modeled GPU's cycle cost (conflating §30's two different performance questions).

21.7 Performance Concerns

  • This phase is the synthesis point for every prior phase's telemetry — a bug in any upstream counter (vertex-fetch bandwidth, texture bandwidth, ROP bandwidth) silently corrupts the roofline classification here.
  • The roofline-sweep benchmark itself must run fast enough to be a routine CI check, not a special occasion (§29 CI/CD topology).

21.8 Edge Cases

  • A draw call with zero texture fetches (arithmetic intensity undefined by the naive formula, requires a guarded divide).
  • A scene exactly at the roofline ridge point (bandwidth-bound and compute-bound simultaneously, boundary classification).
  • An occupancy calculation where all three limiters tie exactly.

21.9 Failure Analysis

An occupancy or roofline miscalculation does not crash anything — it produces confidently wrong performance guidance, which is the single most damaging failure mode for a teaching/analysis tool (named as T5 in §24); the worked-example and synthetic-sweep fixtures are the primary defenses, and both are release-blocking.

21.10 Operational Notes

Occupancy and roofline classification become the headline metrics on the §26 dashboard; the "fidelity-divergence triage" runbook starts every investigation by checking this phase's classification against the raw per-stage bandwidth counters from Phases 1-8.

22. Phase 10 — Tile-Based Deferred Rendering (TBDR) vs IMR

22.1 Objectives

Implement the TBDR mode (graster-tbdr): geometry binning per tile, the on-chip TileBuffer, and single-flush resolve (I6, P8), and validate pixel-identical output against the existing IMR path.

22.2 Detailed Implementation Steps

  1. Implement the binning pass: assign each primitive to every screen tile it overlaps, per §8.8 step 1 (sort-middle, Molnar et al. 1994, P13).
  2. Implement TileBuffer's on-chip accumulation of color/depth across all primitives binned to a tile before any VRAM write (§8.8 step 2).
  3. Implement the single-flush-per-tile-per-pass discipline (I6), rejecting any code path that would flush twice.
  4. Reuse the Phase 4-8 rasterizer/fragment/ROP stages unmodified against the tile buffer instead of direct VRAM, proving stage reuse across IMR/TBDR modes.
  5. Implement the differential harness comparing final resolved pixels between IMR mode and TBDR mode for the same scene (I12).
  6. Implement the bandwidth-accounting comparison per §8.8's savings formula (~2V factor) and §34's derivation.
  7. Cross-reference the Imagination PowerVR and ARM Mali TBDR whitepapers (§5) for the binning-then-resolve sequence's documented shape.

22.3 Deliverable

A working TBDR mode producing pixel-identical output to IMR mode for the same scene, with a measured VRAM-bandwidth savings factor.

22.4 Acceptance Criteria

  • Zero pixel mismatches between IMR and TBDR final output across the full conformance fixture set (I12, structurally gated).
  • Measured bandwidth savings factor matches the ~2V prediction (§8.8) within 10% across overdraw factors V in {1, 2, 4, 8}.
  • Zero double-flush events across all fixtures (I6).

Fixture Purpose

22.6 Pitfalls

  • Binning a triangle to a tile it only marginally touches (bounding-box-only binning) without a precise overlap test, wasting tile-buffer capacity.
  • Flushing a tile early (before all binned primitives are processed), producing a partial and therefore wrong TBDR result — this would also silently violate I12.
  • Assuming TBDR always wins: for very low overdraw (V≈1) and expensive binning, the geometry-pass latency cost can dominate — the model must report this, not hide it (§36).

22.7 Performance Concerns

  • The binning pass is a full geometry pre-pass — its latency cost is TBDR's structural tradeoff against IMR's zero-pre-pass-latency design (P8), and must be visible in the model's timing, not just its bandwidth counters.
  • Tile-buffer SRAM capacity is finite in the model (per §4 tile-size constants); a scene with excessive per-tile primitive density can force early or thrashing flushes, which the model should flag rather than silently absorb.

22.8 Edge Cases

  • A primitive spanning the entire framebuffer (binned to every tile).
  • Zero-overdraw (V=1) scene, where TBDR's bandwidth advantage should shrink toward the formula's lower bound.
  • A tile with zero primitives binned (empty-tile flush should be a no-op, not a wasted VRAM write).

22.9 Failure Analysis

Any IMR/TBDR pixel mismatch (I12) is the highest-severity fidelity bug this phase can produce, since I12 is the project's central pedagogical claim ("same pixels, different bandwidth") — a mismatch is treated identically to a release-blocking correctness bug, not a performance nuance.

22.10 Operational Notes

The "TBDR-vs-IMR analysis" runbook (§26) walks an operator through running overdraw_sweep_v1_v8.trace and reading the resulting bandwidth-savings chart directly off graster-viz.

27. Compatibility & Versioning

Trace/draw-call format: graster-trace carries an explicit version field (ADR-20); minor versions are additive and backward-readable, major versions may break compatibility and require a migration tool.

Modeled-architecture profile versioning: IMR and TBDR configuration profiles (warp width, tile size, cache sizes) are versioned independently of the trace format, so a profile update does not invalidate existing trace fixtures.

Stats-schema stability: PipelineStats's per-stage counter schema is additive-only within a major version; removing or renaming a counter is a breaking change requiring a major version bump.

Shader-ISA interface: graster-isa's abstract instruction set is versioned separately (ADR-19); new instructions may be added without breaking existing programs, but semantic changes to an existing instruction require a major bump.

API stability: the graster-core stage traits follow SemVer; a breaking trait-signature change requires a major version.

Migration: a graster-trace migration tool ships alongside any major version bump, converting old-format traces forward.

Deprecation: deprecated counters/instructions are marked for one minor-version cycle before removal, logged at load time.

SemVer: the whole workspace follows SemVer at the workspace level; individual crates may version independently for internal refactors that do not change the public trace/stats/ISA contracts.

28. Testing & Verification Strategy

Unit: edge-function arithmetic, occupancy-limiter formulas, blend-equation math, Morton-swizzle address computation.

Integration: full draw-call-to-pixel runs across the Phase 0-10 stage chain for each conformance fixture.

Property-based (tied to named invariants and Phase 4-8/10 fixtures):

  • the rasterizer covers a watertight mesh's pixels exactly once — no cracks/double-shade under the top-left rule (I1, watertight_quad.trace).
  • perspective-correct interpolation matches the analytic value (Phase 1/3 fixtures).
  • occupancy equals the min of the three limiters (I9, occupancy_worked_example.trace).
  • MSAA resolve of N identical samples equals the single-sample value (I7, msaa_identical_samples.trace).
  • TBDR and IMR produce identical final pixels, differing only in bandwidth (I12, imr_tbdr_parity.trace).

Differential/fidelity testing against Mesa llvmpipe/SwiftShader pixel output and against the Vulkan CTS rasterization rules — the primary named CI gate (ADR-21, P12, Phase 11): the model must match documented GPU behavior, not merely be internally consistent.

Fuzzing: the draw-call/trace parser and the geometry path (clipping, primitive assembly), per T2 and Phase 11.

Chaos: mid-frame trace truncation, out-of-order tile-flush injection, malformed ISA program injection (Phase 11).

Deterministic replay: every fixture run is replay-hash-checked (I11) as a standing regression guard, not just a Phase-0 one-off.

Soak: 24-hour mixed-workload replay watching for replay-hash drift or resource growth (Phase 11, FM-8/FM-9).

Fault injection: malformed bindings (Phase 0), degenerate geometry (Phase 3), cache-thrashing access patterns (Phase 7), early-Z defeat conditions (Phase 5).

Perf-regression gating: the simulator's own throughput (sim-to-wall-clock ratio, §4/§30) is gated in CI so future phases cannot silently regress simulation speed.

30. Performance Engineering

Methodology: two distinct performance questions are kept separate throughout — (a) the simulator's own speed (event-driven vs. stage-pipelined modeling, per-fragment simulation cost, the sim's own memory-access pattern, parallelizing the simulation across draw calls or tiles, the sim's own tail latency) and (b) the modeled subject's performance (the roofline/bandwidth analysis of the simulated GPU, §8.10/§34). Event-driven modeling is chosen over full stage-pipelined cycle replay to keep simulation cost roughly proportional to work performed rather than to wall-clock cycles elapsed (ADR-02). Per-fragment simulation cost is the dominant driver of the sim's own runtime for high-overdraw scenes, motivating the perf-regression gate below.

31. Scalability Analysis

Stays constant: the per-stage algorithmic structure (edge-function evaluation, quad grouping, ROP ordering) regardless of scene size.

Grows with scene complexity: fragment work grows with covered-pixel count times overdraw factor, not with triangle count directly (§8.11) — a scene with few large overlapping triangles can cost more than one with many small non-overlapping ones. The memory-bandwidth wall (§8.10, §34) is the real limit the model exposes as scenes grow, well before ALU throughput saturates for typical scenes. Occupancy imposes a hard ceiling (I9) independent of scene size, capping how much latency-hiding parallelism any single scene can exploit. The simulator's own cost scales roughly linearly with total fragment-quad count plus texture-fetch count, per Phase 6/7's event-driven design (ADR-02).

Named bottlenecks: VRAM bandwidth (dominant, §4/§34), occupancy ceiling (register/shared-mem/scheduler limits, I9), texture-cache capacity under poor locality (§8.6/§19), TBDR binning-pass latency for very low-overdraw scenes (§22.6).

Bandwidth-vs-compute crossover: the roofline ridge point (§8.10) — scenes below it are bandwidth-bound and immune to added ALU throughput; scenes above it are compute-bound and immune to added bandwidth.

Modeling larger scenes/GPUs: larger register files, larger tile-buffer SRAM, and higher VRAM bandwidth are all configuration knobs (ADR-13, ADR-14, ADR-15), not architectural rewrites — the model is designed to be re-parameterized rather than re-architected for a different reference GPU class.

Practical scene-complexity ceiling: bounded by the simulator's own event-processing throughput (M1) rather than by any modeled hardware limit; beyond roughly 15M simulated primitives per frame, sim wall-clock time becomes impractical for interactive use, and the levers beyond that ceiling are parallelizing the simulation across tiles/draw calls or accepting a coarser (less event-granular) approximation mode.

32. Mental Models & First Principles

  • MM1 — a GPU hides latency with parallelism instead of avoiding it: thousands of warps in flight so that while one waits on memory another computes, which is why occupancy and bandwidth, not clock, decide performance (Lindholm et al., NVIDIA Tesla).
  • MM2 — almost everything expensive about a fragment is memory, not math: texture fetches and framebuffer traffic dominate, so the whole hardware pipeline exists to feed the ALUs, not to add more of them (§8.10, §34).
  • MM3 — TBDR trades on-chip SRAM for VRAM bandwidth by binning geometry per tile and resolving once — mobile GPUs made that trade because bandwidth is power, and power is the mobile constraint (PowerVR/Mali whitepapers, P8).
  • MM4 — the top-left fill rule is not an arbitrary tie-break, it is the mechanism that makes "watertight mesh in, watertight coverage out" a provable property rather than a hope (Pineda 1988, I1).
  • MM5 — fixed-function hardware exists precisely where every draw call needs the same operation done the same way — rasterization, depth test, and blend are not "simpler" than shading, they are simply universal (P2).
  • MM6 — a quad is the smallest unit that can answer "how fast is texture coordinate changing here," and that single design choice (2x2 grouping) is why mip-mapping and helper-lane waste are the same coin's two faces (Williams 1983, P3).
  • MM7 — divergence is a throughput tax, not a correctness hazard: the SIMT model pays for a data-dependent branch in wasted lane-cycles, never in a wrong answer (I5, P9).
  • MM8 — a performance model is only as trustworthy as its last differential test against a real implementation; self-consistency is necessary but never sufficient (P12, Phase 11).
  • MM9 — sort-middle (binning) is a real point on a real taxonomy, not a TBDR-specific trick — the same idea recurs anywhere geometry must be bucketed before the expensive per-pixel work begins (Molnar et al. 1994, P13).
  • MM10 — the roofline model turns "is this fast" into "is this bandwidth-bound or compute-bound," which is a more useful question because it tells you which lever to pull (§8.10, §34).

Desktop IMR is this project's primary reference architecture (§1): it rasterizes and resolves directly against VRAM per draw call, so overdraw directly multiplies bandwidth (§8.8) — the behavior Phase 8's ROP model and Phase 9's roofline model are built to expose. Mobile TBDR is the central architectural foil (§1, ADR-03): by binning geometry per tile and resolving once, it eliminates the repeated VRAM read-modify-write that IMR pays for, at the cost of a full geometry pre-pass — exactly the tradeoff Phase 10 measures. Mesa llvmpipe is the reference CPU implementation this project validates fill-rule and coverage fidelity against (Phase 11, ADR-21) — it proves the documented rasterization rules can be implemented purely in software, which is also this project's implementation substrate, even though its optimization goals (wall-clock speed) differ from this project's goals (architectural transparency). SwiftShader is the second independent reference for the same differential-fidelity gate, chosen specifically because it is a production-grade, specification-conformant Vulkan implementation rather than a research driver. Larrabee is cited as the instructive failure: betting that general x86 cores could do fixed-function rasterization's job in software at competitive power/performance did not pan out against dedicated fixed-function silicon (Seiler et al. 2008) — which is itself evidence for P2's claim that the fixed-function/programmable split is not an accident of history but a real efficiency argument, and is why this project models that split explicitly rather than treating the whole pipeline as programmable.

34. Back-of-Envelope Capacity Model

Fill rate and 4K frame time. fill_rate = rop_count * clock_ghz * 1e9 pixels/second. For 64 ROPs at 1.5 GHz: fill_rate = 64 * 1.5e9 = 9.6e10 pixels/second. A 4K frame (3840x2160 = 8,294,400 pixels) at overdraw factor 3: frame_time = (8,294,400 * 3) / 9.6e10 = 2.59e-4 seconds ≈ 0.26 ms of pure fill time (excludes shading/texture cost, isolating the ROP term per §8.7).

Memory bandwidth needed per frame vs. VRAM budget. bandwidth_needed = pixels * overdraw * bytes_per_pixel_touched * frames_per_second. For the same 4K frame, overdraw 3, 16 bytes/pixel-touched (IMR read+write of a typical color+depth combo), 60 FPS: bandwidth_needed = 8,294,400 * 3 * 16 * 60 = 2.39e10 bytes/second ≈ 23.9 GB/s. Against a modeled VRAM budget of 700 GB/s, this frame is nowhere near the roofline ridge for bandwidth alone at this overdraw — but at overdraw 30 (heavy transparency), bandwidth_needed ≈ 239 GB/s, materially closer to the ceiling, showing the roofline crossover directly (§8.10).

Occupancy from registers. warps = register_file_size / (registers_per_thread * warp_width), capped by the scheduler. For a 65,536-register file, 64 registers/thread, warp width 32: warps = 65536 / (64*32) = 32, capped at the scheduler's 64-warp ceiling — register-limited at 32 (reproduces §8.3's worked example exactly).

Texture bandwidth. texture_bandwidth = texels_fetched * bytes_per_texel / hit_rate_adjustment, where hit_rate_adjustment discounts fetches served from cache. For 1e8 texel fetches/frame at 4 bytes/texel and an 80% L1 hit rate (only the 20% miss fraction reaches VRAM): vram_texture_bandwidth = 1e8 * 4 * 0.20 = 8e7 bytes/frame ≈ 80 MB/frame, or 4.8 GB/s at 60 FPS.

Quad-overshading waste for tiny triangles. helper_lane_fraction = wasted_quad_lanes / total_quad_lanes. A 1-pixel triangle inside an otherwise-empty 2x2 quad wastes 3 of 4 lanes: helper_lane_fraction = 3/4 = 0.75 — the worst-case value used as the Phase 6 acceptance target (§18.4, §8.12).

TBDR bandwidth saving. From §8.8: IMR_traffic ≈ P * V * bytes_per_pixel * 2, TBDR_traffic ≈ P * bytes_per_pixel, so savings_factor ≈ 2V. At overdraw V=4: savings_factor ≈ 8x less VRAM traffic for TBDR versus IMR on the same tile.

Warp-divergence throughput loss. throughput_fraction = active_lanes / warp_width. Reproducing §8.2's worked example: pass 1 at 20/32 = 0.625, pass 2 at 12/32 = 0.375, average active-lane fraction across the two passes = 0.5 — half of peak achievable warp throughput for that divergent instruction.

35. Hard Questions (Self-Examination)

  1. If early-Z is defeated by a discard shader (§17), how much of the Phase 9 roofline classification for that draw call is actually attributable to the resulting late-Z bandwidth doubling versus the shader's own arithmetic cost? (§17, §21)
  2. Does the Hi-Z mip-chain's conservativeness invariant (I8) still hold if two draw calls in the same pass write overlapping depth ranges out of submission order? (§7, §17)
  3. When a tiny-triangle quad-overshading storm (§8.12) coincides with a heavily divergent fragment shader (§14), do the two waste terms compound multiplicatively or does one dominate — and does the model currently report that interaction correctly? (§18, §34)
  4. Is the TBDR bandwidth-savings formula (~2V, §8.8) still accurate when the binning pass itself has to spill because a tile's primitive list exceeds the modeled tile-buffer SRAM capacity? (§22, §4)
  5. How does the differential-fidelity gate (Phase 11) distinguish a genuine model bug from a case where Mesa and SwiftShader themselves disagree at the sub-pixel level? (§23.8, §28)
  6. Does the occupancy model's min() of three limiters (§8.3) correctly capture a scenario where the scheduler limit itself depends on the current divergence rate, or are these treated as independent when they are not? (§14, §21)
  7. If a scene is exactly at the roofline ridge point (§8.10), is the model's bandwidth-bound/compute-bound classification stable under small measurement noise, or does it flicker? (§21.8, §30)
  8. Does the texture-cache-locality argument (§8.6) still hold for anisotropic filtering, which samples across a footprint rather than a single texel neighborhood? (§19.8, §8.5)
  9. What happens to I6's single-flush-per-tile guarantee if a render pass is aborted mid-frame (a chaos scenario, §23) — does the model correctly avoid a partial, silently-wrong flush? (§22, §25 FM-7)
  10. Is the sim-to-wall-clock ratio (M1, §30) roughly constant across scene types, or does it vary enough between bandwidth-bound and compute-bound scenes that a single target number is misleading? (§30, §31)
  11. Given that Larrabee's software-rasterization bet failed on power/performance (§33), what specifically in this project's fixed-function/programmable split (P2) would have to change for a hypothetical "software-only" mode to be architecturally honest rather than just a toy? (§33, §36)
  12. Does the model's abstract-ISA representation (ADR-19) risk understating divergence cost relative to a real compiler's control-flow optimizations (e.g., branch predication)? (§14, §9)
  13. If VRAM bandwidth is upgraded in the configuration (a scaling lever, §31) without also scaling texture-cache size, does the roofline classification shift in a way that is still internally consistent with §8.6's locality argument? (§31, §19)
  14. How does the model account for the geometry-binning latency of TBDR (§22.6) in a scene with exactly one draw call per frame, where there is no pipelined overlap to hide that latency behind? (§22, §30)
  15. Is the exactly-once-coverage property (I1) still well-defined at a T-junction (three or more triangles meeting at a non-manifold vertex), or does the fill rule's guarantee implicitly assume a strictly manifold, 2-triangles-per-edge mesh? (§16, §7)

36. Alternative Architectures (Roads Not Taken)

Immediate-mode rendering (IMR) vs. tile-based deferred (TBDR) — the central fork.

   IMR                                TBDR
  +----------+                        +----------+
  | rasterize|--\                     | bin all  |
  | + shade  |   \                    | geometry |
  +----------+    v                   +----------+
  | ROP r/m/w|--> VRAM (per triangle)      |
  +----------+                              v
        (repeats per overlapping tri)  +----------+
                                        | tile SRAM|
                                        | shade+ROP|
                                        +----------+
                                              |
                                              v (once)
                                            VRAM

Winning regime: IMR wins on desktop, where VRAM bandwidth is abundant and geometry-binning latency is unwelcome; TBDR wins on mobile, where bandwidth is the power-constrained resource. Real embodying systems: NVIDIA/AMD desktop GPUs (IMR); Imagination PowerVR and ARM Mali (TBDR). Rejected as the sole model here because the project's teaching value is precisely the contrast (§1, ADR-03) — modeling only one would erase the comparison that makes the bandwidth argument concrete.

A CPU software rasterizer (the sibling-169 approach).

  +-------------------------------------------+
  | CPU thread pool: fetch -> transform ->     |
  | rasterize -> shade -> blend -> framebuffer |
  +-------------------------------------------+

Winning regime: maximum flexibility, no fixed-function silicon required, ideal when the goal is producing a correct image rather than modeling hardware behavior. Real embodying system: Mesa llvmpipe. Rejected as the primary model here because 191's job is to model the hardware pipeline's stages and performance characteristics (§1 non-goals) — a pure CPU software rasterizer (which is what 169 already is) has no fixed-function/programmable split to model and no warp/SIMT execution model to expose.

Larrabee: many-core x86 with software rasterization.

  +----------------------------------------+
  | many x86 cores, wide SIMD each          |
  | rasterization + shading, all in software|
  | on general-purpose cores                |
  +----------------------------------------+

Winning regime: maximal programmability of every pipeline stage, useful when the fixed-function/programmable boundary itself needs to move. Real embodying system: Larrabee (Seiler et al. 2008) — commercially unshipped as a discrete GPU, its architecture concepts survived into Xeon Phi. Rejected as the primary model here because it collapses exactly the fixed-function/programmable distinction (P2) that this project exists to make legible, and because it is a documented instructive failure on power/performance grounds (§33).

Ray tracing as an alternative visibility model (the sibling-170 approach).

  +---------------------------------------------+
  | per-pixel ray generation -> BVH traversal -> |
  | intersection -> shading                      |
  +---------------------------------------------+

Winning regime: view-independent effects (reflections, global illumination) where rasterization's screen-space locality assumption breaks down. Real embodying system: modern RTX/RDNA ray-tracing cores, and sibling project Ray-Tracer (170). Rejected as the primary model here because 191's entire scope is the rasterization visibility algorithm and its hardware pipeline — ray tracing is a different visibility algorithm entirely, explicitly out of scope per §1 non-goals.

38. Glossary

Term Definition
Rasterization Converting a geometric primitive into a set of covered pixels/samples.
Triangle setup Computing a triangle's edge functions and bounding box before coverage evaluation.
Edge function A linear function of screen position used to test which side of a triangle edge a point lies on (Pineda 1988).
Top-left fill rule The tie-break rule ensuring a shared edge between two triangles is rasterized by exactly one of them.
Coverage The set of samples/pixels a primitive is determined to overlap.
Hierarchical-Z (Hi-Z) A mip-chain of conservative depth bounds used to reject occluded screen tiles before shading.
Early-Z A depth test performed before fragment shading, valid only when the shader cannot change depth/discard.
Late-Z The fallback depth test performed after fragment shading when early-Z is defeated.
Depth test Comparing a fragment's depth against the stored depth buffer value to determine visibility.
Stencil An auxiliary per-pixel value used for masking and multi-pass effects.
Fragment A candidate pixel-sample produced by rasterization, prior to and during shading.
Quad A 2x2 group of fragments shaded together so screen-space derivatives are defined.
Screen-space derivative The rate of change of an interpolated value across screen space, used for mip selection.
Mip LOD The mipmap level of detail selected based on screen-space derivative magnitude.
SIMT Single-Instruction-Multiple-Thread: the GPU execution model where many threads (lanes) execute one instruction stream in lockstep, masked individually.
Warp A group of lanes (commonly 32) executing in lockstep under SIMT (NVIDIA terminology).
Wavefront AMD's term for the SIMT execution group, commonly 64 lanes.
Lane One scalar thread within a warp/wavefront.
Execution mask The per-lane active/inactive bitmask used to implement divergent control flow.
Divergence When lanes within a warp take different control-flow paths, requiring serialized execution of each path.
Reconvergence The point where divergent lanes resume executing together after all paths complete.
Occupancy The number of warps resident and schedulable on an SM/CU, bounded by register/shared-memory/scheduler limits.
Register file The on-chip storage holding each thread's registers.
SM/CU Streaming Multiprocessor (NVIDIA) / Compute Unit (AMD): the GPU's core execution block hosting multiple warps.
Latency hiding Covering memory-access latency by switching to another resident warp instead of stalling.
Texture unit The fixed-function hardware that resolves texture addresses, fetches, and filters texels.
Texel A single texture element (the texture-space analog of a pixel).
Morton order (Z-order/swizzle) A bit-interleaved addressing scheme that maps 2D coordinates to a locality-preserving 1D address.
Texture cache The cache hierarchy (commonly L1 per-SM, shared L2) serving texture fetches.
ROP Raster Operations (pipe): the fixed-function unit performing depth/stencil test, blend, and framebuffer writeback.
Output merger Direct3D's term for the ROP stage.
Blend Combining a new fragment's color with the existing framebuffer color per a configured equation.
MSAA Multisample Anti-Aliasing: sampling coverage/depth at multiple sub-pixel positions, shading once, resolving to one color.
Sample One sub-pixel coverage/depth/color slot within a multisampled pixel.
Resolve Filtering a multisampled pixel's per-sample values down to a single displayable value.
Overdraw The number of times a given pixel is shaded/written within a frame due to overlapping geometry.
Fill rate The rate (pixels/clock or pixels/second) at which the ROP can process fragments.
IMR Immediate-Mode Rendering: rasterizing and resolving each primitive directly against the framebuffer as it arrives.
TBDR Tile-Based Deferred Rendering: binning all geometry per screen tile before shading and resolving once.
Tile buffer The on-chip SRAM accumulating a tile's color/depth across a TBDR render pass before flush.
Binning The TBDR pass that assigns primitives to the screen tiles they overlap.
Sort-first/middle/last Molnar et al.'s taxonomy for where a parallel-rendering architecture binds geometry to screen regions.
Memory bandwidth The rate at which data can move between a processor and memory (register file/cache/VRAM).
Roofline model A performance model bounding achievable throughput by the lesser of peak compute and peak-bandwidth-times-arithmetic-intensity.
Arithmetic intensity The ratio of floating-point operations to bytes moved, used to classify a workload as bandwidth- or compute-bound.
Command processor The fixed-function front end that decodes and issues draw calls to the execution units.
Draw call A single unit of rendering work submitted by the application (a mesh plus pipeline state).
Cycle-approximate A simulation fidelity level matching published architecture timing constants without gate-level accuracy.
Differential testing Validating a model's output by comparing it against an independent reference implementation on the same input.
Helper lane A lane in a partially-covered quad that executes the shader for derivative purposes but discards its output.
