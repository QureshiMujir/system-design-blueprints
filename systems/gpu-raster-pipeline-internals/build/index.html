⬜ Phase 0 — Skeleton, Draw-Call Front End, Framebuffer Model, and CI §12

Objectives

Establish the crate workspace skeleton (§1 Phase-0 deliverable list), a working command processor/draw-call front end, a minimal framebuffer model (no shading yet), and a CI pipeline that will host the fidelity-gate job added in Phase 11 (ADR-27).

Deliverable

A runnable graster-cli binary that loads a graster-trace file, decodes and validates each draw call through the command processor, and reports "N draws processed, M rejected" with no shading performed.

Acceptance
  • 100% of the malformed_binding.trace fixture's draw calls rejected at validation (0 false-accepts).
  • CI green on Linux x86_64 for three consecutive commits.
  • Deterministic replay hash (I11) identical across 10 successive runs of basic_drawcall.trace.
Fixtures
Fixture Purpose
basic_drawcall.trace single well-formed draw call, front-end smoke test
malformed_binding.trace draw call referencing an unbound resource, validation-rejection test
empty_scene.trace zero draw calls, boundary condition for the CLI's summary report
Pitfalls
  • Hidden nondeterminism from HashMap iteration order leaking into PipelineStats serialization.
  • Unbounded draw-call queue growth if the validation step is slower than ingestion.
  • Deferring CI fidelity-gate scaffolding until Phase 11, making that phase's integration a big-bang change.
  • Skipping the version field in graster-trace "for now," creating a migration debt for §27.

⬜ Phase 1 — Vertex Fetch and the Vertex Stage §13

Objectives

Implement vertex fetch and the programmable vertex shader stage running the abstract ISA (ADR-19) across a single warp (full SIMT/warp scheduling arrives in Phase 2).

Deliverable

A pipeline that fetches vertices and produces clip-space output through the abstract-ISA vertex shader for single-triangle and small-mesh traces.

Acceptance
  • Clip-space output matches a hand-computed reference to floating-point tolerance 1e-5 for the single_triangle.trace fixture.
  • Vertex-fetch bandwidth counter matches vertex_count * attrib_bytes exactly (fixed-function accounting, no cache modeled yet at this phase).
Fixtures
Fixture Purpose
single_triangle.trace reference transform validation
high_attrib_count.trace vertex-fetch bandwidth stress with wide vertex layouts
degenerate_vertex.trace NaN/Inf attribute regression guard
Pitfalls
  • NaN propagation from a malformed vertex attribute silently poisoning downstream stages (guarded by the degenerate_vertex.trace fixture).
  • Treating the single-warp vertex stage's throughput as representative before Phase 2's full SIMT model lands.
  • Misordering the perspective divide relative to clipping (clipping is Phase 3's responsibility — vertex stage must output pre-divide clip-space only).

⬜ Phase 2 — The SIMT/Warp Execution Model and Divergence §14

Objectives

Implement the full SIMT/warp execution engine (graster-simt): multi-warp residency, ExecMask divergence/reconvergence, and latency-hiding warp switching (P1, I5, Lindholm et al.'s NVIDIA Tesla model).

Deliverable

A multi-warp SIMT execution engine that correctly handles nested divergence and reports per-warp divergence telemetry.

Acceptance
  • The divergent_warp_32_20_12.trace fixture reproduces the §8.2 worked example exactly: active-lane fraction 20/32 then 12/32, average 0.5.
  • Zero lanes lose their computed result across 10,000 randomized divergent-branch property-test iterations (I5).
  • Warp switching on a modeled memory stall measurably improves aggregate throughput versus a no-switching baseline in the bench suite.
Fixtures
Fixture Purpose
divergent_warp_32_20_12.trace reproduces the §8.2 worked divergence example
nested_divergence.trace two levels of nested branching, mask-stack correctness
fully_convergent.trace regression guard: no divergence overhead when all lanes agree
memory_stall_switch.trace validates latency-hiding warp switching improves throughput
Pitfalls
  • Popping the ExecMask stack at the wrong point, causing early reconvergence and lost divergent-path results (violates I5).
  • Modeling divergence cost as purely additive when real warps can sometimes execute both paths with partial overlap — the model documents this as a simplification (ADR-02).
  • Forgetting to account for a fully-masked-off warp (all lanes predicated false) still consuming a scheduler slot.

⬜ Phase 3 — Primitive Assembly and Clipping §15

Objectives

Assemble shaded vertices into primitives and implement view-frustum clipping, producing well-formed triangles for the Phase 4 rasterizer (§8.1 pipeline stage table).

Deliverable

A primitive-assembly-and-clipping stage that turns vertex-stage output into a stream of valid, non-degenerate, correctly-wound triangles.

Acceptance
  • Zero degenerate triangles reach graster-raster in any conformance fixture (validated by a post-stage assertion).
  • Near-plane clipping matches the OpenGL specification's reference clip-space test vectors exactly.
  • Backface-culled triangle count matches a hand-computed reference for the culling_reference.trace fixture.
Fixtures
Fixture Purpose
near_plane_clip.trace triangle straddling the near plane, clip correctness
fully_outside_frustum.trace triangle entirely outside, full-cull regression
zero_area_triangle.trace degenerate-triangle discard guard (§8.12)
culling_reference.trace backface-cull count validation
Pitfalls
  • Clipping after the perspective divide instead of before, producing incorrect interpolation across the near plane.
  • Floating-point precision drift at grazing near-plane intersections producing inconsistent winding.
  • Failing to re-triangulate a clipped polygon correctly when a triangle intersects more than one clip plane.

⬜ Phase 4 — The Hardware Rasterizer (Triangle Setup, Edge Functions, Fill Rule) §16

Objectives

Implement triangle setup and edge-function rasterization (Pineda 1988) with the top-left fill rule (I1), producing deterministic per-pixel/per-sample coverage.

Deliverable

A deterministic, fixed-point edge-function rasterizer producing correct top-left-rule coverage for arbitrary triangles.

Acceptance
  • 100% agreement with the Vulkan CTS rasterization-rule reference coverage for the imported CTS fixture subset.
  • Zero double-shaded or uncovered pixels across the watertight_quad.trace property test (I1), over 10,000 randomized triangle-pair configurations.
  • Bitwise-identical coverage output across 3 independent runs (fixed-point determinism, I11).
Fixtures
Fixture Purpose
watertight_quad.trace shared-edge exactly-once-coverage property test (I1)
subpixel_triangle.trace sub-pixel-area triangle coverage boundary case
cts_rasterization_subset.trace imported Vulkan CTS rasterization-rule vectors
axis_aligned_triangle.trace degenerate top/left classification regression
Pitfalls
  • Using floating-point edge evaluation without a consistent fixed-point convention, breaking I11's determinism guarantee.
  • Misclassifying a horizontal edge's top/bottom orientation relative to winding, inverting the fill rule (violates I1).
  • Off-by-one bounding-box iteration missing boundary pixels at exact edge coincidence.

⬜ Phase 5 — Hierarchical-Z and Early-Z §17

Objectives

Implement the hierarchical-Z conservative occlusion test (Greene, Kass & Miller 1993) and the early-Z depth test with its documented defeat conditions (I3, I8).

Deliverable

A Hi-Z-accelerated rasterizer front end plus a correctly-gated early-Z/late-Z depth-test stage.

Acceptance
  • Zero false Hi-Z rejects (I8) across 10,000 randomized occluded/unoccluded tile-pair property-test iterations.
  • 100% of discard/depth-write-shader draw calls correctly routed to late-Z, verified against the early_z_defeat_* fixtures (I3).
  • Measured bandwidth savings from Hi-Z tile rejection on the heavy_occlusion.trace fixture matches the analytically predicted savings within 5%.
Fixtures
Fixture Purpose
heavy_occlusion.trace Hi-Z bandwidth-savings validation
early_z_defeat_discard.trace discard-shader early-Z defeat routing
early_z_defeat_depthwrite.trace depth-write-shader early-Z defeat routing
hiz_boundary_tile.trace a tile straddling occluded/unoccluded, false-reject guard
Pitfalls
  • Letting a Hi-Z mip go stale after a depth write, producing a false (optimistic) reject — the single worst fidelity bug this stage can produce (violates I8).
  • Applying early-Z unconditionally without checking the shader-capability flag, silently breaking discard/depth-write semantics (violates I3).
  • Conflating "no depth write" with "no side effects" — a discard-only shader also defeats early-Z per the Vulkan spec.

⬜ Phase 6 — The Fragment Stage with Quads and Derivatives §18

Objectives

Run the fragment shader stage across warps grouped into 2x2 quads (I2), computing screen-space derivatives for mip selection (§8.5, Williams 1983).

Deliverable

A quad-based fragment shader stage producing shaded fragments and correct screen-space derivatives, feeding the Phase 7 texture units.

Acceptance
  • Mip-LOD selection matches the §8.5 equation to within 0.1 mip levels for the known_gradient.trace fixture.
  • Helper-lane fraction for the tiny_triangle_storm.trace fixture matches the analytically predicted 3/4 worst case within 5% (§8.12, §34).
  • Fragments/cycle throughput on a fully-covered large-triangle fixture matches the modeled ALU-throughput ceiling within 10%.
Fixtures
Fixture Purpose
large_interior_triangle.trace low-helper-lane-waste baseline
tiny_triangle_storm.trace quad-overshading worst-case validation (§8.12)
known_gradient.trace derivative/mip-LOD equation validation
divergent_fragment_shader.trace ties Phase 2's divergence model into fragment-stage throughput
Pitfalls
  • Computing derivatives from a partial (helper-lane-less) quad, producing undefined or incorrect mip selection (violates I2).
  • Letting a helper lane's discarded output leak into PipelineStats shaded-fragment counts, inflating apparent throughput.
  • Ignoring the interaction between Phase 2's divergence model and quad occupancy — a divergent fragment shader wastes lanes twice over (once for divergence, once for helper-lane quad padding).

⬜ Phase 7 — The Texture Units and Cache Hierarchy §19

Objectives

Implement texture address resolution with Morton/swizzle ordering (Morton 1966) and the L1/L2/VRAM texture-cache hierarchy, establishing the texture-cache-locality argument (§8.6).

Deliverable

A texture-unit model with Morton-order addressing and a working L1/L2/VRAM cache hierarchy, reporting hit rates and bandwidth.

Acceptance
  • Morton-order addressing improves L1 hit rate over the row-major ablation by a measured, reported margin (not merely nonzero) for the locality_reference.trace fixture.
  • The cache_thrash.trace fixture drives L1 hit rate below 10%, matching the analytically predicted conflict-stride behavior (§8.12).
  • Texture-fetch bandwidth accounting matches texels_fetched * bytes_per_texel * (1 - hit_rate_adjustment) within 2% (§34 formula).
Fixtures
Fixture Purpose
locality_reference.trace Morton-vs-row-major hit-rate ablation
cache_thrash.trace conflict-stride worst-case regression (§8.12)
mip_chain_sweep.trace filter/mip-level correctness across the full mip chain
cold_cache_startup.trace first-fetch miss-rate boundary condition
Pitfalls
  • Implementing Morton swizzle only for square power-of-two textures, silently mishandling non-power-of-two or non-square textures.
  • Double-counting bandwidth when an L2 hit still triggers a spurious "VRAM fetch" event in telemetry.
  • Ignoring associativity in the L1 model, understating real conflict-miss behavior and overstating hit rate.

⬜ Phase 8 — The ROP (Depth/Stencil, Blend, MSAA Resolve) §20

Objectives

Implement the ROP/output-merger's fixed depth-test-then-blend ordering (I4) and MSAA sample-mask accumulation and resolve (I7), completing §8.7's decision table.

Deliverable

A complete ROP stage performing ordered depth/stencil test, blend, and MSAA resolve, writing to the IMR-mode framebuffer.

Acceptance
  • Zero rop_order_violation_count across all conformance fixtures (I4, structurally enforced).
  • MSAA resolve of N identical samples equals the single-sample value exactly, verified as a property test over N in {2, 4, 8} (I7).
  • Blend-equation output matches a hand-computed reference for the alpha_blend_stack.trace fixture to floating-point tolerance 1e-6.
Fixtures
Fixture Purpose
alpha_blend_stack.trace multi-layer blend-equation validation
stencil_wrap.trace stencil-op wraparound boundary case
msaa_identical_samples.trace N-identical-samples resolve property test (I7)
depth_fail_stencil.trace depth-fail stencil-op path validation
Pitfalls
  • Applying blend before the depth test in a code-path shortcut, violating I4's normative ordering.
  • Using a non-box resolve filter without exposing it in configuration, silently breaking the I7 identical-samples property.
  • Overdraw bandwidth accounting that forgets the read half of read-modify-write for IMR, understating §8.8's bandwidth term.

⬜ Phase 9 — The Occupancy and Memory-Bandwidth Performance Model §21

Objectives

Implement the full occupancy model (§8.3 equation, I9) and the roofline/bandwidth model (§8.10) that ties every prior stage's telemetry into the project's central performance-analysis deliverable.

Deliverable

An occupancy calculator and roofline model consuming every prior stage's telemetry, classifying each draw call as bandwidth-bound or compute-bound and reporting achievable throughput.

Acceptance
  • The §8.3 worked example reproduces exactly: occupancy_warps = min(32, 48, 64) = 32, register-limited (I9).
  • Roofline-predicted achievable throughput matches the synthetic-sweep reference within 5% across the arithmetic-intensity range tested.
  • Zero occupancy_ceiling_violation_count across all conformance fixtures (I9, structurally enforced by construction).
Fixtures
Fixture Purpose
occupancy_worked_example.trace reproduces §8.3's hand-computed occupancy exactly
register_limited_shader.trace high-register-pressure occupancy ceiling test
shared_mem_limited_shader.trace high-shared-memory occupancy ceiling test
roofline_sweep.trace synthetic arithmetic-intensity sweep for roofline validation
Pitfalls
  • Computing occupancy from only one limiter (e.g., registers only) and silently ignoring shared-memory or scheduler limits, violating I9's min() semantics.
  • Classifying a draw call's roofline regime using peak (not achieved) bandwidth, overstating how compute-bound a scene actually is.
  • Treating the simulator's own event-processing cost as if it were the modeled GPU's cycle cost (conflating §30's two different performance questions).

⬜ Phase 10 — Tile-Based Deferred Rendering (TBDR) vs IMR §22

Objectives

Implement the TBDR mode (graster-tbdr): geometry binning per tile, the on-chip TileBuffer, and single-flush resolve (I6, P8), and validate pixel-identical output against the existing IMR path.

Deliverable

A working TBDR mode producing pixel-identical output to IMR mode for the same scene, with a measured VRAM-bandwidth savings factor.

Acceptance
  • Zero pixel mismatches between IMR and TBDR final output across the full conformance fixture set (I12, structurally gated).
  • Measured bandwidth savings factor matches the ~2V prediction (§8.8) within 10% across overdraw factors V in {1, 2, 4, 8}.
  • Zero double-flush events across all fixtures (I6).
Fixtures
Fixture Purpose
imr_tbdr_parity.trace pixel-identical-output differential test (I12)
overdraw_sweep_v1_v8.trace bandwidth-savings-factor validation across overdraw levels
tile_boundary_triangle.trace a triangle spanning multiple tiles, binning correctness
single_flush_guard.trace double-flush regression guard (I6)
Pitfalls
  • Binning a triangle to a tile it only marginally touches (bounding-box-only binning) without a precise overlap test, wasting tile-buffer capacity.
  • Flushing a tile early (before all binned primitives are processed), producing a partial and therefore wrong TBDR result — this would also silently violate I12.
  • Assuming TBDR always wins: for very low overdraw (V≈1) and expensive binning, the geometry-pass latency cost can dominate — the model must report this, not hide it (§36).

⬜ Phase 11 — Validation, Performance-Model Benchmark, and Hardening §23

Objectives

Gate the entire model's fidelity with differential testing against Mesa llvmpipe/SwiftShader pixel output and the Vulkan CTS rasterization rules (P12, ADR-21), validate the roofline model against a reference, and harden the system (fuzzing, soak, chaos).

Deliverable

A CI-gated differential-fidelity harness, a validated roofline benchmark, and a hardened build passing fuzzing, soak, and chaos testing.

Acceptance
  • 100% pixel agreement with Mesa llvmpipe/SwiftShader on the shared differential-fixture corpus, and 100% agreement with the imported Vulkan CTS rasterization-rule vectors.
  • Roofline-validation benchmark agrees with the reference roofline curve within 5% across the tested arithmetic-intensity sweep.
  • Zero crashes and zero replay-hash drift (I11) across the 24-hour soak run.
  • Zero new crashes found by graster-fuzz across a 1M-iteration corpus on the trace parser and geometry path.
Fixtures
Fixture Purpose
mesa_swiftshader_diff_corpus.trace full differential-fidelity fixture corpus
cts_rasterization_full.trace complete imported Vulkan CTS rasterization subset
soak_mixed_workload.trace 24-hour soak-test corpus
chaos_truncated_trace.trace mid-frame truncation recovery test
sim_throughput_regression.trace perf-regression gate baseline
Pitfalls
  • Treating a passing differential test on a small fixture set as sufficient evidence of general fidelity — the corpus must span the malformed/hard examples from §8.12, not just clean geometry.
  • Letting the fidelity-gate CI job become slow enough that engineers routinely skip it locally, eroding P12's discipline.
  • Fuzzing only the trace parser and neglecting the geometry path, missing clipping/degenerate-triangle-induced crashes.
