In one paragraph

Anti-Entropy Read Repair is a Rust library embedded in a replicated key-value store. It makes the copies of each key agree again after a crash, a network split, clock skew, or a write that missed a replica (§1). It is not a store: the host supplies sorted-range iteration, replica RPC and cluster membership (§1). It runs three repair mechanisms side by side: background comparison of hash summaries, buffered writes for a replica that is down, and fixes made while serving reads (P2). On top sit a pluggable rule for picking a winner among conflicting values and a fast path for small differences (§1). Storage engineers building Dynamo/Cassandra-style stores embed it, and SREs run it through the ae CLI (§1).

The problem, concretely

Take a store that keeps several copies of every key and accepts a write once W of the N copies have it (§4, §15.1). One copy goes dark for 6 hours. The reachable copies keep taking writes, so the absent copy falls behind (§23.3). The coordinator buffers writes meant for it, up to the queue caps. When it returns, those buffered writes must be replayed, and a full comparison must catch anything the buffer dropped or never captured: cold keys nobody wrote during the outage that drifted anyway, for example through a sibling resolved on another replica (§23.3).

The naive fix is the one §2 names, if a != b { sync(a, b) } (§2). MM1 calls unconditionally shipping full range payloads "to be safe" the O(N) design this subsystem exists to avoid; the blueprint ships a 32-byte summary and descends only where summaries disagree (MM1, §3). A second naive fix is to repair only on reads. It fails on "cold" ranges that are never read and never hinted at, which drift indefinitely (§24 FM-1, §34 question 1). A third is to buffer every missed write for the downed replica. Without a bound that is a disk problem: a target down 24 hours at 1,000 writes per second and about 1 KB per hint accumulates about 86.4 GB (§33 item 3). So the blueprint requires all three mechanisms, because dropping any one creates a distinct persistent-divergence class (P2, §3, §24).

How it works, end to end

Follow one write and one read through the boxes of §3. The diagram is drawn from §3, boxes folded, coloured by role:

  1. Coordinator (ae-repair::coordinator) handles every client request. On a write it needs W real acknowledgments; a replica that times out or is marked down gets a hint recorded instead (§3, §15.2). A hint never substitutes for one of the W acknowledgments, and if the hint cannot be durably stored the write must not be reported as successful (§15.8).
  2. Hint queue (ae-hints) stores hints in RocksDB, one column family per target replica, bounded in bytes and in age (§3, §15.2, ADR-09, ADR-10). When gossip sees the downed replica's heartbeat resume, ReplayDriver (ae-hints/src/replay.rs) replays its hints at a rate limit and deletes each one only after the replica acknowledges it (§15.2).
  3. Read path. ReadCoordinator::get collects R responses. If they are equal it returns directly. In synchronous-non-blocking mode, if they differ it calls Resolver::resolve, returns the winner, and spawns the write-back in the background (§16.2). A read at R = 1 never repairs, because one response cannot be compared with itself (§16.4). In asynchronous mode, a sampled fraction of reads (10% by default) is repaired by a background task (§17.2, ADR-11). The mode is a per-request or per-keyspace policy value (§16.10).
  4. Background reconciliation. GossipScheduler in ae-gossip picks a (peer, range) pair every cycle (1 s intra-DC by default) (§14.2, ADR-06). It sends a FingerprintExchange carrying the Merkle root; if roots differ, ae-merkle::diff::locate_divergence walks down with SubtreeQuery/SubtreeReply until it reaches the divergent leaves (§8.1, §8.3, §13.2).
  5. Fix-up. The two sides fetch the divergent leaf entries, Resolver::resolve picks the outcome and the write-back applies it (§13.2, §8.3).
  6. Fast path. For small, bounded differences ae-iblt ships a compact table instead, and falls back to the Merkle walk if it cannot decode (§3, §19.2, ADR-15).

All replica traffic goes over ae-net as length-prefixed CBOR on Tokio TCP (§3, §8.1). Every repair trigger, located divergent leaf and resolver decision emits an event into the Disagreement Event Log, which operators and the adaptive scheduler consume (§3, I11).

Each repair attempt is a small state machine (§8.2). The transition list reads Queued → InFlight → Applying → Done; InFlight or Applying go to Failed on an RPC error or resolver panic, and Failed → Retrying up to max_retries (default 3, backoff 1 s / 2 s / 4 s). Past that the task becomes Abandoned and is re-queued at Background priority on the next gossip cycle rather than dropped (§8.2, P2). The §8.2 diagram instead draws InFlight → Retrying on timeout/error and a Queued → Abandoned arrow, neither of which the list has.

The core ideas

Merkle descent: compare summaries, not data (§13, I1, I2, P3, MM1)

A Merkle tree is a tree of hashes: leaves hash the keys in a slice of the range, and each parent hashes its children. Two replicas first compare only the root, 32 bytes. If equal, they stop (MM1, §13.8). If not, they compare children and recurse only into the subtrees that differ.

  • Leaves are bucketed by the key's 16-bit prefix (65,536 leaves at the default depth), using BLAKE3 with distinct prefixes for leaf and internal-node hashes (§13.2, ADR-04, ADR-07).
  • The leaf hash covers (key, ts, value_hash), so two replicas with the same value but different HLCs are detected as divergent (§13.8).
  • The combine step is order-independent, so the same data gives bit-identical roots whatever order storage iterates (I1).
  • Cost for d divergent keys of N total is O(d log N) fingerprints plus O(d) payload (P3). The acceptance bound is bytes_exchanged ≤ 2 × d × log2(leaf_count) × 40 (§13.4).

The blueprint's own trace (§8.3): replica A holds key1 → "old" at Hlc{100, 0, node 1}, replica B holds "new" at Hlc{100, 1, node 1}. The gossip cycle sends A's root to B; roots differ; SubtreeQuery/SubtreeReply descend to the single divergent leaf; both sides fetch it; LwwResolver::resolve returns "new" because logical 1 beats 0; the write-back updates A; the roots for that range now match (§8.3).

The gossip scheduler: who repairs what, and how fast (§14, P4, P13, I10, I13)

There is no central scheduler. Each node decides locally, every cycle, which peer and which range to reconcile (P4, §14.2). Choice is random but weighted by last_reconciled, because purely random choice starves some ranges (§14.6). Three safeguards:

  • Partition-aware scope: only pairs where both endpoints currently own the range are scheduled (§14.2, T12).
  • Token bucket (a counter that refills at a fixed rate): caps repair bandwidth at 25 MB/s per (peer, range), with a 50 KB credit needed before an exchange starts. It must be per pair, never global, or a fast pair starves a slow one (§14.2, §14.6, I10).
  • Adaptive throttling: when the 5-minute request rate exceeds 1.5 times baseline, halve the cycle frequency and the cap, restoring on cooldown, with a floor of one exchange per minute per node so nothing starves (§14.2, P11). Concurrent range repairs are capped at 4 per node (ADR-08, I13).

Why gossip converges quickly: a rumor reaches all N nodes in O(log N) rounds (MM3). The blueprint's worked case is N = 1000: about 10 rounds, so about 10 s at a 1 Hz cycle (§33 item 7, ADR-06).

Hinted handoff: a bounded memo for a down replica (§15, I4, I5, P5)

Hinted handoff means the coordinator stores a write meant for an unreachable replica and replays it later; accepting the write at W real acks is called a sloppy quorum (§15.1, §37). The queue is bounded three ways:

  1. Bytes: a cap per target (default 1 GiB) inside a 4 GiB total, enforced by oldest-first eviction and a drop counter, so it is never silent (§15.2, I4, ADR-09).
  2. Age: hints older than the TTL (24 h default) are never replayed (§15.2, I5, ADR-10).
  3. Replay speed: rate-limited so a recovering replica is not swamped (§15.2, §15.6).

A three-step trace: the target goes down, so hints accumulate in its column family; the target's heartbeat returns, so ReplayDriver replays and deletes only after acknowledgment; any hints that were dropped are covered later by active anti-entropy (§15.2, I4, T2). Replay is at-least-once: a crash mid-replay re-sends, and the receiver deduplicates by HLC (§15.2). The blueprint states the default replay rate limit as 1,000 hints per second (§15.2) yet requires at least 10K hints per second "under the default rate limiter" (§15.4).

Read repair: fix what clients actually touch (§16, §17, P6, ADR-11)

Read repair compares replica answers during a read and writes the winner back. Two modes exist.

  • Synchronous-non-blocking (§16.2, §16.4): resolve, return to the client at once, tokio::spawn the write-back. Target added latency at p99 is at most 0.5 ms (M7). §16.2 says a same-value, different-HLC pair is not divergence for read repair, while §13.8 requires the Merkle leaf hash to flag exactly that pair as divergent.
  • Asynchronous probabilistic (§17.2): after collecting R responses, a Bernoulli draw at the sample rate (10% default) decides whether to spawn repair. The queue is a bounded channel (10K pending by default); when full, work is dropped and counted, never buffered without limit (§17.2, MM7).

The blueprint names both as "the default". §16.1 and §16.2 call synchronous-non-blocking the default, and the §37 glossary calls it the "adopted default". P6 and ADR-11 call asynchronous sampling at 10% the default, with synchronous opt-in per request (P6), and §17.1 calls the asynchronous mode "the production default read-repair mode".

The write-back is idempotent: the replica's storage layer rejects a write-back whose timestamp is not strictly greater than the stored one (§16.2). Example from the blueprint: at 100,000 reads per second and a 10% rate, that is 10,000 background resolver-plus-write-back invocations per second (§33 item 9).

Conflict resolution: picking a winner safely (§18, I3, I6, P7, P8, P9, MM8)

When two replicas hold different values for one key, a Resolver reduces them to one outcome (§18). The hybrid logical clock (HLC) gives a total order: (physical, logical, node_id) compared left to right, always (I3, P7). Plain wall-clock LWW is rejected because skew then decides the winner (P7, ADR-12). Four resolvers share one trait (§18.2, §3):

  • LwwResolver: highest HLC wins, and a winning tombstone is returned as Tombstone, not Single.
  • SiblingsResolver: keeps mutually concurrent versions, deduplicated with dotted version vectors so a replayed write is not mistaken for a second writer (MM4). Opt-in only (P8).
  • CrdtResolver<C>: wraps a type from blueprint #55; merge is that type's own merge (P9).
  • with_custom_resolver: wraps an application closure; the contract is documented, not compiler-checked (§18.2).

The contract every resolver must meet is CAI: commutative, associative, idempotent (I6, MM8). A custom resolver without it will eventually produce a permanently diverging sibling set under the right write pattern (MM8). All replicas serving one range must also run the same resolver; a policy-hash mismatch makes a write be refused (I9).

IBLT: ship a small table instead of a tree walk (§19, I8, P10, MM5)

An Invertible Bloom Lookup Table (IBLT) is a fixed-size table of cells that can be subtracted from another replica's table, leaving a table that holds only the difference between the two sets (§19.2). Each element is hashed into 3 cells, which XOR-accumulate an id and a check hash and bump a count (§19.2).

  1. Both sides build a table sized from d_expected, the expected number of differing elements: cell_count = (d_expected × 1.5).next_power_of_two(), ADR-14's c ≈ 1.5 (§19.2, ADR-14).
  2. One table is subtracted from the other (Iblt::sub), giving a table for the symmetric difference (§19.2).
  3. Peel-back decoding repeatedly finds a "pure" cell (count.abs() == 1 and the check hash confirms a single element), records it, and subtracts it from all three of its cells (§19.2).
  4. If cells remain non-zero with no pure cell, the decode returns Err(Exhausted), never a partial answer (I8), and the coordinator falls back to the Merkle walk (§19.2, ADR-15).

The blueprint's bandwidth figures, as written: §33 item 6 gives cell_count = 1500 at d_expected = 1000, c = 1.5, and 1500 × 24 B = 36,000 B ≈ 36 KB, "versus #5's ~125 KB Merkle cost at a comparable divergence count", quantifying P10's CPU-for-bandwidth trade; item 5 is 2 × 100 × 16 × 40 B = 128,000 B ≈ 125 KB for d = 100 (§33 items 5 and 6). §19.4 gives ~36 KB (1500 cells × 24 bytes) for d_expected = 1000 and an actual diff of 500, "versus ~115 KB for the equivalent Merkle exchange" (§19.4). §19.6 warns that the power-of-two rounding in §19.2 can nearly double the provisioned cell count. A mis-sized d_expected costs performance, not correctness (§19.9).

The trade-offs — where engineers disagree

Hint queue cap (ADR-09)

Chosen: 4 GiB total default (§9), enforced by bytes with oldest-first eviction (§15.2). Rejected: 512 MiB, or unbounded (§9). When the rejected choice is right: 512 MiB wins on memory-constrained edge deployments where active anti-entropy is cheap to lean on more heavily (§9). The unbounded option is what §33 item 3 warns against: about 86.4 GB for one bad day on one target.

Read-repair sampling rate (ADR-11)

Chosen: 10% asynchronous, matching Cassandra's default (§9, P6). Rejected: 1% and 100% (§9). When the rejected choice is right: 100% wins only as a short-lived, operator-triggered manual repair window; the standing production default stays 10% (§9, §17.6). A 100% rate is synchronous-blocking in disguise once the background queue saturates (§17.6).

Timestamp source for last-writer-wins (ADR-12)

Chosen: a hybrid logical clock from blueprint #95 (§9). Rejected: plain wall-clock, or pure vector clocks (§9). When the rejected choice is right: pure vector clocks win when the application wants explicit sibling exposure instead of a forced total order (§9). Plain wall-clock LWW lets clock skew pick the winner instead of causality (P7).

Sibling exposure (ADR-13)

Chosen: opt-in per keyspace via SiblingsResolver (§9, P8). Rejected: always-on, Riak-style global allow_mult (§9). When the rejected choice is right: a store whose whole API contract is "you always resolve conflicts yourself", the pure Riak deployment model (§9).

IBLT sizing (ADR-14)

Chosen: c × d_expected cells with c ≈ 1.5 (§9). Rejected: c = 1.0 and c = 3.0 (§9). When the rejected choice is right: c = 3.0 wins when decode-failure probability must be near zero and bandwidth is not the binding constraint (§9).

IBLT failure handling (ADR-15)

Chosen: fall back to Merkle on Exhausted, accepting O(d log N) cost (§9). Rejected: no fallback, a hard failure (§9). When the rejected choice is right: only where d_expected is provably an upper bound, for example a bounded write rate plus a bounded outage window (§9). MM5 predicts that an IBLT deployment without a correctness-preserving fallback will eventually fail silently at high divergence (MM5).

Roads not taken

Pure-CRDT convergence (§35.1): replicas merge CRDT state and nothing else. It wins when the whole data model is CRDT-expressible and full-state gossip is cheap relative to divergence rate. It is rejected because most KV workloads (arbitrary blobs) do not fit a CRDT shape, which is why CRDTs are opt-in (P9).

Consensus replication (§35.2): a Raft leader makes divergence impossible by construction. It wins under strict consistency with moderate write throughput. It is rejected because it sacrifices the availability under partition that eventual consistency exists to provide (§35.2, P1).

Differential-dataflow streaming (§35.3): event-driven incremental diffing instead of polled gossip. It wins at very large N, where polling overhead is itself the dominant cost (§30). It is rejected as operationally heavy for an embedded library, deferred as ADR-21 (§35.3).

Chain replication (§35.4): writes pass head to tail, so there is no divergence to repair. It wins for workloads that tolerate primary-side write serialization. It is rejected because a mid-chain failure blocks writes until reconfiguration, trading away availability under partition (§35.4).

What must never be false

  • I1: Merkle roots over the same (key, ts, value_hash) multiset are bit-identical in any order. Noticed by conformance/merkle.build_determinism; metric ae_merkle_root_compute_seconds (§7).
  • I2: recursive comparison finds every divergent leaf and no other. Noticed by conformance/merkle.diff_localisation; metric ae_repair_bytes_exchanged_total (§7).
  • I3: HLC comparison is (physical, logical, node_id) lexicographic, always. Noticed by a permutation-invariance property test; metric ae_conflict_resolution_outcomes (§7).
  • I4: hint-queue bytes per target never exceed the cap. Noticed by conformance/hint.cap_enforcement; metrics ae_hint_queue_bytes and ae_hint_drops_total (§7).
  • I5: expired hints are never replayed. Noticed by conformance/hint.ttl_drop; metric ae_hint_drops_total{reason="ttl"} (§7).
  • I6: Resolver::resolve is commutative, associative and idempotent. Not compiler-checked; noticed by conformance/resolver.lww, .siblings, .crdt before merge (§7).
  • I7: HLC state is persisted before every tick() and replayed at startup. Noticed by a startup replay assertion; telemetry is delegated to blueprint #95 (§7).
  • I8: IBLT decode returns the exact difference or Err(Exhausted), never a partial answer. Noticed by conformance/iblt.decode_correctness; metric ae_iblt_decode_outcomes (§7).
  • I9: the active Resolver is uniform across replicas serving a range. Noticed by comparing policy hashes over gossip; metric ae_repair_ranges_total{outcome="policy_mismatch"} (§7).
  • I10: token-bucket spend never exceeds the cap by more than 5% over any 60 s window. Noticed by conformance/gossip.token_bucket; metric ae_repair_bytes_exchanged_total rate (§7).
  • I11: every reconciliation event emits exactly one telemetry event. Noticed by conformance/metrics.exposition; a missing emission is a code-review defect (§7).
  • I12: repair priority (Background < Normal < High) is respected by queue ordering. Noticed by a priority-inversion property test; metric ae_repair_duration_seconds{mode} (§7).
  • I13: repair concurrency never exceeds repair_concurrency_limit (4 by default). Noticed by a concurrency-limiter unit test and soak assertion; metric ae_repair_ranges_total (§7).

What breaks in production

  • FM-1: cold ranges drift. Symptom: ranges nobody reads or hints about diverge indefinitely. Root cause: active anti-entropy disabled or misconfigured, leaning on read repair alone (violates P2). Detection: ae_repair_ranges_total{mode="active"} flatlines while divergence rises elsewhere. Recovery: none automatic, it is a configuration defect; re-enable the scheduler and check ae repair status (§24).
  • FM-2: hint queue at its cap. Symptom: queue bytes near cap, drop counter rising. Root cause: the target has been down longer than the cap absorbs, or the cap is too low for the write rate. Detection: ae_hint_queue_bytes trend and ae_hint_drops_total{reason="cap"}. Recovery: oldest-first drop bounds the damage; the hint-queue-overflow runbook says to confirm reachability, then ae hints replay or ae hints drop and rely on active anti-entropy (§24, §15.9).
  • FM-3: request-time inconsistency persists despite convergence elsewhere. Root cause: hinted handoff without read repair enabled (violates P2). Detection: an elevated denominator-vs-numerator mismatch for ae_read_repair_fires_total in monitoring dashboards. Recovery: none automatic; enable synchronous or asynchronous read repair per keyspace (§24).
  • FM-5: repair makes an incident worse. Root cause: an unthrottled or under-throttled scheduler (violates P13); the cited precedent is Datastax's 2015 postmortem. Detection: ae_repair_bytes_exchanged_total rate above the cap. Recovery: the token bucket (I10) bounds it structurally; ae repair stop --range <id> halts a runaway range (§24, §14.9).
  • FM-6: LWW winner looks causally wrong after a restart. Root cause: the HLC logical counter was reset without persistence (violates I7). Detection: startup HLC-replay assertion failure. Recovery: check that blueprint #95's persistence path is wired and replay the on-disk HLC (§24).

Threats a reader should know (§23): T2 unbounded hint accumulation for a permanently-down target, answered by byte cap, TTL and FIFO drop (I4, I5); T3 resolver-policy mismatch across replicas, answered by policy-hash comparison and refusing the write (I9); T5 repair traffic amplifying an incident, answered by the token bucket and adaptive throttle (P13, I10); T6 a silent-wrong IBLT decode from a hash collision, answered by a BLAKE3-keyed check hash with false positive rate below 2⁻³⁰ and the Merkle fallback (T6, §19.6, ADR-15); T9 a malformed SubtreeQuery with an out-of-range node_index, answered by a RangeGenerationMismatch check before any index is used (§8.4). Replica equivocation (a lying replica, T1) is out of scope by design (ADR-22).

How it compares

  • Cassandra made incremental repair and non-blocking read repair its two departures from the original Dynamo design, after years of production pain (§32). This design adopts both from day one (§32, §16.4), and it adds an IBLT fast path where Cassandra is Merkle-only (§32).
  • DynamoDB shipped sloppy quorum, hinted handoff and Merkle anti-entropy together from its first paper (§32). This design imitates that choice explicitly (P2), differing in leaving the storage engine to the host (§32).
  • Riak made siblings (allow_mult) the default, pushing merge complexity onto every application (§32). This design reverses that, making siblings opt-in (P8, ADR-13), which is fine for Riak's niche of apps that always want to resolve conflicts themselves (ADR-13).
  • ScyllaDB made shard-per-core concurrency (Seastar) its central performance lever (§32). This design is async Rust on Tokio with a no_std core, and takes from it the discipline of bounding the Rayon pool to physical cores (§32, §22.6).

Questions to test yourself

  1. Why does read repair alone, without active anti-entropy, leave "cold" ranges permanently diverged — and what metric would reveal this in production before an operator notices via a complaint? — Hint: §14, and FM-1 in §24.
  2. Why is the hint queue capped at bytes rather than at hint count, and what regime would make a count-based cap wrong instead? — Hint: ADR-09 in §9 and §33 item 3.
  3. Why does synchronous-blocking read repair explode p99 latency, and what does the synchronous-non-blocking design trade away to fix it? — Hint: §16.2, §16.4 and P6.
  4. Why must the token bucket be per-(peer, range) rather than global, and what specific failure does a global bucket permit? — Hint: §14.2, §14.6 and P13.
  5. Why is repair concurrency bounded per node (ADR-08) independently of the token bucket's bandwidth bound, and what happens if only one of the two bounds exists? — Hint: ADR-08 in §9, §14.2 and §4.

If you only remember three things

Three mechanisms are required because each covers a gap the others leave: read repair for keys being touched, hinted handoff for a replica that is briefly down, and gossip-driven Merkle comparison for everything nobody is reading (P2, §3). The hint queue and the async-repair queue drop with telemetry instead of growing, and a per-pair token bucket caps repair bandwidth, because repair traffic can itself worsen the incident it is fixing (P5, P13, MM7). Fingerprints go first and payloads second, and the IBLT fast path always falls back to Merkle, so a mis-tuned d_expected costs performance rather than correctness (§3, ADR-15, I8, §19.9).

Words used here

  • Anti-entropy: protocols that detect and repair replica divergence after the fact (§37).
  • Active anti-entropy: the background, gossip-scheduled, Merkle-driven repair of ranges nobody is reading (§37, §14).
  • Merkle tree: a tree of hashes that lets two replicas find differing ranges by comparing summaries first (§37, §13).
  • Hinted handoff: buffering a write for an unreachable replica and replaying it later (§37).
  • Sloppy quorum: accepting a write once W replicas acknowledge, hinting the rest (§37).
  • Read repair: detecting and fixing divergence on the keys a client is actually reading (§37).
