1. Goal & Scope

Anti-Entropy Read Repair specifies the reconciliation subsystem an eventually-consistent replicated key-value store needs to make replicas converge, within a bounded time budget, after any transient fault — replica crash, network partition, clock skew, or a coordinator that could not reach every replica at write time. It combines three complementary mechanisms (Merkle-tree active anti-entropy, gossip-scheduled peer reconciliation, hinted handoff for transient unavailability, and read-time repair — synchronous and probabilistic) with a pluggable conflict-resolution layer (LWW/HLC, Riak-style siblings, CRDT merge, application-defined hook) and an Invertible Bloom Lookup Table (IBLT) fast path for small-divergence set reconciliation. The system is a library, not a store: it is embedded into an existing partitioned KV engine and assumes that engine supplies sorted-range iteration, replica RPC, and cluster membership.

Phase-0 deliverable — numbered modules:

  1. ae-core — no_std domain types: KeyRange, VersionedValue, Hlc, RangeFingerprint, Hint, RepairTask, the Resolver and AntiEntropyEngine traits.
  2. ae-merkle — Merkle tree skeleton (MerkleTree::build hashing leaves only; recursive diff ships Phase 1).
  3. ae-repair — coordinator skeleton wiring two in-process Replica handles via direct calls (no network).
  4. ae-resolver — LwwResolver skeleton (highest-HLC wins).
  5. Cargo workspace, CI skeleton (ci.yml), Makefile, docker-compose.yml simulator harness.
  6. examples/two_replica_repair.rs — deterministic-seed smoke test proving one repair round converges two diverged replicas.

System boundaries.

  • Provides: Merkle-tree anti-entropy, gossip-driven scheduling, hinted handoff, synchronous + asynchronous read repair, a pluggable conflict-resolution interface, an IBLT fast path for bounded-difference set reconciliation, an operator CLI + Prometheus metrics, and a Jepsen-style fault-injection harness.
  • Delegates: the storage engine itself (assumes sorted-range iteration and a durable put/get/scan API — not built here); the HLC implementation (Project #95, referenced throughout as "blueprint #95"); the CRDT type library (Project #55, "blueprint #55"); ring/partition membership and topology (assumed supplied by the host store).
  • Does NOT provide: Byzantine-fault-tolerant repair with signed Merkle proofs (Project #94); linearizable/transactional consistency (Paxos/Raft — Projects #91, #92); a general CRDT library; cryptographically signed multi-tenant policy distribution (deferred, Deferred Features Register, §36).

Non-goals: strong/linearizable consistency, cross-key transactions, Byzantine tolerance, building a storage engine, building a partitioner.

Deployment model: embedded library linked into a replicated KV store's process; one instance per replica node; gossip transport over TCP by default (QUIC deferred, ADR-20, §20); hint queue is a RocksDB column family colocated with the replica's data directory.

Target users/operators: distributed-storage engineers building or operating a Dynamo/Cassandra-lineage store; SREs operating the ae CLI and consuming the Prometheus exposition (§21.2).

What later phases unlock: Phase 7 (§19) unlocks bandwidth-efficient reconciliation on constrained links; Phase 8 (§20) unlocks true multi-DC deployment; Phases 9–10 (§21–§22) unlock production operability and the performance headroom the M-series targets (§29, Performance Engineering) require.

Recommended language: Rust 1.78+ (edition 2021). Rationale: memory safety without a GC pause (the read-repair path has a sub-millisecond latency budget, §4); a no_std core lets storage engines with custom allocators embed ae-core/ae-merkle/ae-iblt; the Tokio async ecosystem is load-bearing for the gossip scheduler and hint replay; cargo fuzz + Miri give the IBLT decoder and BLAKE3 Merkle hasher a verification story no comparable C library has out of the box. Rejected languages: Go — GC pauses conflict with the p99 read-repair budget (M7, §29); C++ — memory-safety CVE history in comparable systems (memcached, redis-cluster); Java/JVM — GC pause and cold-start cost unsuitable for an embedded library; Zig — no equivalent to Tokio's select!/bounded mpsc as of the decision date (2026).

Prerequisites: replication/quorum/gossip fundamentals; hash trees (Merkle, Patricia); the eventual-consistency literature (Vogels 2009, Bailis-Ghodsi 2013, Burckhardt 2014); coding-theory basics (Bloom filters, BCH codes) for IBLT; the Rust async runtime.

Estimated timeline: Phase 0 in 1 week; the full system (Phases 0–10, §12–§22) in 5–7 months, gated by the conformance suite (§27) and a 30-day soak (§36 row soak-30d).

Deferred features (flagged here, registered in §36):

  • PhaseDeferred("§23") — Byzantine-tolerant repair via signed Merkle proofs; replicas are assumed honest-but-down (§23.1); true BFT is Project #94's surface.
  • PhaseDeferred("§20") — QUIC transport for cross-DC repair (ADR-20); TCP carries Phases 0–9.
  • PhaseDeferred("§21") — cryptographically signed policy registry; the Phase 9 registry (§21.1) is unsigned and operator-trusted until this lands.
  • PhaseDeferred("§35") — differential-dataflow (Naiad-style) streaming convergence as a wholesale alternative to polled gossip; rejected in §35.3, revisited as a scaling lever.

2. Why Build This

Eventual consistency is the most-deployed consistency model in the industry: DynamoDB, Cassandra, Riak (while it lived), Voldemort, ScyllaDB, every CDN content-propagation layer, every CRDT-backed collaborative editor, and every geo-replicated cache ships a reconciliation subsystem to make "eventually" actually arrive. The founding literature is excellent — Demers et al. PODC 1987 invented epidemic algorithms; Dynamo SOSP 2007 productionised anti-entropy and hinted handoff; Bailis-Ghodsi 2013 surveyed the space; Burckhardt 2014 formalised it — but the production policy layer (hint-queue TTL before spill, gossip cadence, the IBLT-to-Merkle fallback threshold, repair-induced load- amplification bounds) is folklore scattered across Datastax and Riak engineering blogs and nodetool repair source comments. This blueprint is the single document that walks an engineer from "I understand the Dynamo paper" to "I can build a Cassandra-grade repair subsystem."

The reconciliation problem is also mathematically rich, and that theory pays rent directly in the design. Minsky-Trachtenberg-Zippel 2003 (P10, §6) proved that two sets differing by d elements reconcile with O(d) communication — independent of set size — via a characteristic-polynomial exchange; that result underlies IBLT-style protocols generally (Eppstein et al. 2011, the direct ancestor of §19's set-reconciliation engine). Any engineer who has written if a != b { sync(a, b) } and wondered whether there is a provably-better way should own this stack once.

This project is deliberately the smallest stack that still teaches the full surface: the Merkle subsystem (incremental build, hash-chain root, recursive subtree comparison, the O(d log N) bandwidth proof — §13); the gossip scheduler (peer selection, partition-aware scope, token-bucket throttling — §14); the hinted-handoff queue (persistent, bounded, TTL'd, telemetered on drop — §15); the read-repair pipeline (synchronous quorum-disagreement write-back and asynchronous fire-and-forget — §16, §17); the conflict resolver (LWW+HLC, siblings, the CRDT escape hatch, the application hook — §18); and the set-reconciliation engine (IBLT construction, peel-back decode, fallback-to-Merkle — §19). Cross-links: the HLC timestamp source is blueprint #95's surface; the CRDT merge types are blueprint #55's; the BFT variant is blueprint #94's — this project is deliberately the hub that plugs into all three without reimplementing any of them.

By the end of Phase 10 (§22) a reader understands why Cassandra's read_repair_chance defaults to 0.1 and not 1.0 (P6, §16.4), why Riak's hinted handoff spills to disk at 256 MB and not 4 GB (contrast with ADR-09's 4 GiB default, §9), why Dynamo bounds the hint queue and TTLs it and gossips an explicit drop signal (I4, §7), and exactly which module executes when a replica returns from a 6-hour partition (§23.3 walks the trace).

The deliverable is intentionally bounded. It does not implement Byzantine-tolerant anti-entropy (§23, Project #94's surface), a strongly-consistent linearizable store (Projects #91/#92), or a general CRDT library (Project #55) — it depends on all three via narrow interfaces. That tight focus is the only reason the timeline is months, not years.

What Mastery Looks Like — after building this, the reader can:

  • Derive the bandwidth cost of any Merkle-vs-IBLT reconciliation strategy from first principles and pick the right one for a given divergence regime (Phase 1, §13; Phase 7, §19).
  • Explain, without notes, why three separate repair mechanisms are required and what persistent-divergence class each one alone leaves unaddressed (Phase 0–5, §12–§17; P2, §6).
  • Design a bounded, telemetered hinted-handoff queue that never grows unboundedly and degrades observably (Phase 3, §15; I4, §7).
  • Choose and justify a conflict-resolution policy (LWW/HLC vs. siblings vs. CRDT) against an application's actual write-concurrency profile (Phase 6, §18).
  • Reason about repair-induced load amplification and design the token-bucket + adaptive throttling that prevents it (Phase 2, §14; P13, §6).
  • Run and interpret a Jepsen-style fault-injection suite and know which convergence property it is actually testing (Phase 10, §22; §27).
  • Redesign the whole reconciliation stack around a different primitive (Alternative Architectures, §35) and state precisely what that trade costs.

Four properties recur throughout this document. First, repair is three separate mechanisms, not one (P2, §6): read repair fixes divergence on the keys clients are actually touching; hinted handoff buffers writes for a transiently-down replica; active anti-entropy (Merkle gossip) reconciles ranges nobody is reading or hinting about. Dropping any one creates a distinct persistent-divergence class (§24, Failure Modes). Second, the conflict resolver is pluggable, not baked-in (I9, §7): LWW+HLC is the default; siblings and CRDT merge are consumers of the same Resolver trait (§11.7), not special cases. Third, the network protocol is fingerprint-first, payload-second (§13.2): a Merkle root is 32 bytes; fingerprints are gossiped every cycle and only leaf payloads are shipped once divergence is localized — the Back-of-Envelope Capacity Model (§33) quantifies this. Fourth, the Disagreement Event Log is the system's observability surface: every repair trigger, every located divergent leaf, every resolver decision emits a telemetry event (I11, §7) that both operators and the adaptive scheduler (§14.4) consume.

6. Design Principles

  1. P1 — Eventual consistency is contractually correct only if the repair protocols converge. Rule: "eventual" without a bounded-convergence proof is a marketing word. Tradeoff: proving convergence requires the property-test infrastructure of §27, which is nontrivial engineering effort up front. Operational implication: every release gates on the convergence property suite, not just unit tests. Violating it: the system silently accumulates divergence with no detection.
  2. P2 — Three reconciliation mechanisms, not one. Rule: read repair, hinted handoff, and active anti-entropy are complementary and all three must be present (§3). Tradeoff: more surface area to build and operate than a single mechanism. Operational implication: dashboards must track all three independently (§25). Violating it: skipping any one creates a distinct persistent-divergence class (§24, FM-1..FM-3).
  3. P3 — Merkle trees are the bandwidth-optimal full-range primitive at moderate divergence. Rule: for d divergent keys of N total, Merkle costs O(d log N) fingerprints plus O(d) payload. Tradeoff: IBLT beats Merkle when d is small (sub-thousand) and loses when d is large or unbounded (§19.3). Operational implication: the fallback threshold (ADR-14) must be tuned per workload. Violating it: using IBLT unconditionally causes decode failures under high divergence with no recovery path.
  4. P4 — Gossip-driven scheduling beats centralized scheduling for fault tolerance. Rule: each node decides locally which peer to reconcile with this cycle (§14.1). Tradeoff: harder to reason about global repair progress than a central scheduler. Operational implication: convergence proofs rely on Karp-Schenker-Shenker (§6 Papers) not on operator intervention. Violating it: a central scheduler is a single point of failure and a single point of policy.
  5. P5 — Hinted handoff is bounded, never unbounded. Rule: hints spill to disk, then drop with telemetry past a hard cap (ADR-09, ADR-10). Tradeoff: dropped hints rely on active anti-entropy to converge, delaying full correction. Operational implication: the drop counter (ae_hint_drops_total) must alert. Violating it: an unbounded queue for a permanently-down replica exhausts disk (I4, §7).
  6. P6 — Synchronous read repair adds latency; default off for high-throughput paths. Rule: the added cost is one replica round-trip plus a write-back (§16.4). Tradeoff: asynchronous (probabilistic) repair converges slower per-key but never blocks the read path. Operational implication: the default is asynchronous at a 10% sample rate (ADR-11); synchronous is opt-in per request. Violating it: p99 latency explodes on any workload with frequent divergence.
  7. P7 — Conflict resolution requires a total order; LWW+HLC is the pragmatic default. Rule: plain wall-clock LWW lets clock skew pick the winner instead of causality (§18.1). Tradeoff: HLC requires a monotone, persisted clock (blueprint #95). Operational implication: HLC state must survive process restart (I7, §7). Violating it: a slow-clock node loses every conflict regardless of causal order.
  8. P8 — Siblings are correct but unfriendly; expose as opt-in. Rule: applications that need custom merge can request the sibling list (§18.2). Tradeoff: default callers never see siblings and get LWW; opt-in callers own the merge complexity. Operational implication: sibling-count histograms (ae_sibling_count) must be monitored per keyspace. Violating it: forcing siblings on all callers pushes merge complexity onto applications that do not need it.
  9. P9 — CRDTs eliminate conflict resolution at the cost of API constraints. Rule: blueprint #55's CRDT types plug into the Resolver trait (§11.7). Tradeoff: only CRDT-expressible state benefits; arbitrary application state falls back to LWW/siblings. Operational implication: adopting CRDTs is a per-keyspace migration, not a global default. Violating it: forcing CRDTs everywhere constrains the data model unnecessarily.
  10. P10 — Set reconciliation via IBLT trades CPU for bandwidth. Rule: constructing and decoding an IBLT costs more CPU than a Merkle build, but wire cost is O(d) not O(d log N) (Minsky-Trachtenberg-Zippel 2003; Eppstein et al. 2011). Tradeoff: bandwidth-constrained links (cross-DC, mobile) prefer IBLT; CPU-constrained nodes prefer Merkle. Operational implication: the d_expected cell-count parameter is per-range tunable (§19.3). Violating it: fixed cell budgets either waste bandwidth or fail to decode.
  11. P11 — Repair is never "finished." Rule: there is no terminal "repaired" state; the gossip scheduler runs forever (§14). Tradeoff: metrics must track rate of reconciliation, not a binary done/not-done. Operational implication: operator runbooks must never promise "repair complete," only "converged as of gossip round N." Violating it: an operator who believes repair "finishes" will miss ongoing cold-range drift.
  12. P12 — Conformance is the contract. Rule: the conformance suite (§27) gates every release; property tests for convergence, Merkle correctness, hint durability, resolver determinism, and IBLT decoding are merge gates, plus a 30-day Jepsen-style soak. Tradeoff: slower release cadence than "ship and monitor." Operational implication: a red conformance bucket blocks release regardless of urgency. Violating it: undetected regressions ship to production reconciliation logic — the worst possible place for a silent bug.
  13. P13 — Repair-induced load amplification is a footgun. Rule: a scheduler that accelerates repair under high divergence can cause the very partition it was meant to heal (Datastax's 2015 incident, cited in §24 FM-5). Tradeoff: the token bucket (ADR-06 successor at §14.3) caps throughput even when divergence is severe, extending wall-clock convergence time. Operational implication: the 25 MB/s per-(peer,range) default (§4) is non-negotiable without an explicit override. Violating it: repair traffic amplifies the incident it is trying to fix.
  14. P14 — Observability is built-in, not bolted-on. Rule: every reconciliation event (repair start, divergent-leaf located, hint dropped, sibling created, conflict resolved) emits a Prometheus metric and a structured log line (§21.2). Tradeoff: instrumentation overhead on the hot path (bounded, measured in §29). Operational implication: the operator runbooks (§21.3) exist from Phase 9, not "written after production breaks." Violating it: an operator debugging a stuck repair at 3 a.m. with no telemetry.

8. Domain Model / Protocol / Data Model

8.1 Wire protocol (ae-net)

Messages are length-prefixed CBOR (RFC 8949) over Tokio TCP (ADR-16); QUIC is deferred (ADR-20, §20). Every message begins with a 4-byte big-endian length prefix, then the CBOR payload. Three message families:

FingerprintExchange   { range_id: RangeId, root_hash: Hash256, depth: u8,
                         leaf_count: u32, generation: u64 }
SubtreeQuery          { range_id: RangeId, node_index: u32 }
SubtreeReply          { range_id: RangeId, node_index: u32, hash: Hash256 }
IbltExchange          { range_id: RangeId, cell_count: u32, hash_count: u8,
                         seed: u64, cells: Vec<CellWire> }
HintReplayBatch       { batch_id: u64, hints: Vec<HintWire> }
HintReplayAck         { batch_id: u64, delivered: u32, failed: u32 }

Field types reuse ae-core's canonical types (RangeId, Hash256, Hint → HintWire); no protocol-local type shadows a core type under a different name (the terminology-lock discipline this document holds throughout).

8.2 Repair-task state machine

Show the original text diagram
        submit                accept                complete
Queued ────────► InFlight ───────────► Applying ───────────► Done
  │                  │  timeout/error         │  resolver error
  │                  ▼                        ▼
  │              Retrying ◄───────────── Failed
  │                  │  retries exhausted
  │                  ▼
  └───────────► Abandoned (telemetry: ae_repair_ranges_total{outcome="abandoned"})

Transitions: Queued → InFlight on scheduler dispatch (respecting I12/I13); InFlight → Applying on successful fingerprint/IBLT exchange; Applying → Done on successful resolver + write-back; InFlight/Applying → Failed on RPC error or resolver panic; Failed → Retrying up to max_retries (default 3, exponential backoff 1s/2s/4s); Retrying → Abandoned past max_retries, logged and re-queued at Background priority on the next gossip cycle rather than dropped outright (active anti-entropy is the backstop, P2).

8.3 Worked example — convergence trace

Replica A holds key1 → ("old", Hlc{physical:100, logical:0, node:1}). Replica B holds key1 → ("new", Hlc{physical:100, logical:1, node:1}). Gossip cycle fires: A sends FingerprintExchange{root_hash: R_a} to B; roots differ; recursive SubtreeQuery/ SubtreeReply descends to the single divergent leaf containing key1; both sides fetch the leaf's entries; LwwResolver::resolve([("old", ts=100.0.1), ("new", ts=100.1.1)]) returns Single(("new", ts=100.1.1)) (I3's lexicographic order: logical 1 > 0); the write-back applies ("new", ...) to A. Both replicas' Merkle roots for that range now match (I1).

8.4 Malformed-input example

A SubtreeQuery arrives with node_index exceeding the local tree's 2^depth - 1 bound (e.g. the peer's tree has a stale, pre-split depth). The receiver rejects with a RangeGenerationMismatch error (checked against the generation field of the last exchanged FingerprintExchange, §8.1) rather than indexing out of bounds; the gossip scheduler treats this as Failed → Retrying, and on repeated mismatch escalates to a full-range re-fingerprint (bypassing the stale cached tree).

8.5 Failure-path example

Mid-IbltExchange, the peer disconnects (TCP RST). The in-flight repair task transitions InFlight → Failed (detection: RPC future resolves to Err(Error::PeerUnreachable)); ae_repair_ranges_total{outcome="peer_unreachable"} increments; the task retries with backoff; if the peer remains unreachable past 3 retries the range moves to Abandoned and is re-queued at Background priority — active anti-entropy will pick it up again next cycle rather than starve it indefinitely (P11).

11. Core Schema & Types

All load-bearing types, as signatures only (no method bodies; per the standard's No-Code Rule). Ownership/mutation/concurrency/persistence/serialization notes follow each type.

11.1 KeyRange, RangeId — crates/ae-core/src/range.rs

type Key = bytes::Bytes;
type Value = bytes::Bytes;

struct KeyRange { start: Key /* inclusive */, end: Key /* exclusive */ }
struct RangeId(u64);   // stable across membership changes

impl KeyRange { fn contains(&self, key: &[u8]) -> bool; }

Ownership: Key/Value are ref-counted (Bytes), cheaply cloned. Mutation: immutable once constructed. Concurrency: Send + Sync. Persistence: not persisted directly; ranges are derived from partitioner state. Serialization: CBOR via ae-net::protocol.

struct Hlc { physical: u64 /* ms since epoch */, logical: u32, node_id: u32 }

Ordering: Hlc is Ord on (physical, logical, node_id) lexicographically (I3). Ownership: owned by blueprint #95's clock service; ae-core only consumes tick() / update_with(remote). Concurrency: Hlc is Copy. Persistence: blueprint #95 persists pre-tick (I7). Serialization: CBOR.

11.3 RangeFingerprint — crates/ae-core/src/fingerprint.rs

type Hash256 = [u8; 32];
struct RangeFingerprint { range_id: RangeId, root_hash: Hash256, depth: u8,
                           leaf_count: u32, generation: u64 }

The unit gossiped every cycle (§8.1). generation guards stale-tree comparisons across topology changes (§8.4). Serialization: CBOR, 48 bytes wire-size (§33).

struct MerkleTree { leaves: Vec<Hash256>, internal: Vec<Hash256>, depth: u8 }

impl MerkleTree {
    fn build<I: Iterator<Item = LeafEntry>>(depth: u8, entries: I) -> Self;
    fn root(&self) -> Hash256;
    fn children_of(&self, node: usize) -> (usize, usize);
    fn node_at(&self, node: usize) -> Hash256;
    fn is_leaf_index(&self, node: usize) -> bool;
}

Ownership: one MerkleTree per (RangeId, generation), owned by the replica's repair subsystem. 13. Phase 1 — Merkle Tree Subsystem

13.1 Objectives

Ship the full Merkle-tree anti-entropy primitive: incremental build over a sorted keyspace range, hash-chain root, and recursive subtree comparison that localizes divergence in O(d log N) fingerprint exchanges for d divergent leaves of N total (P3). This is the bandwidth-optimal full-range reconciliation primitive the rest of the stack falls back to (ADR-15).

13.2 Detailed Implementation Steps

  • ae-merkle/src/builder.rs: build_from_sorted hashes leaves with domain-separated BLAKE3 (b"AE-MERKLE-LEAF\0" prefix) then hashes pairs upward (b"AE-MERKLE-NODE\0" prefix) — the distinct-prefix discipline is non-negotiable (§13.6 pitfall); implements ADR-04 and applies P3's bandwidth-optimality claim.
  • Leaf bucketing by the key's 16-bit prefix (ADR-07 default, 2^16 leaves); the combine step is XOR-order-independent so the same range on two replicas produces bit-identical roots regardless of storage-iteration order (I1).
  • ae-merkle/src/diff.rs: locate_divergence — frontier-based recursive descent (SubtreeQuery/SubtreeReply, §8.1) starting at the root; on hash mismatch, descend to children; on leaf mismatch, record divergence. Implements I2 and the AntiEntropyEngine trait's compare method (§11.8).
  • Leaf-level payload fetch-and-apply: once divergent leaves are located, fetch the peer's entries for the leaf's key range, run Resolver::resolve (§11.7) against local + peer entries, apply the merged result — the first real use of the Resolver trait outside a unit test.
  • EMPTY_LEAF_HASH constant: BLAKE3(b"AE-MERKLE-EMPTY\0"), never [0u8; 32] (§13.6).
  • Bandwidth-invariant instrumentation: count bytes exchanged per comparison round, exposed for the conformance bucket merkle.bandwidth_invariant.

13.3 Deliverable

ae-merkle crate with build_from_sorted, locate_divergence, and leaf-repair fully implemented and property-tested; examples/two_replica_repair.rs extended to exercise the recursive-descent path instead of Phase 0's direct-diff stub.

13.4 Acceptance Criteria

  • MerkleTree::build produces bit-identical roots for 1000 random pairs of iterators containing the same multiset in different orders (I1, merkle.build_determinism).
  • locate_divergence identifies all and only divergent leaves on 1000 random (sorted-keyspace, perturbation) pairs — zero false positives, zero false negatives (I2).
  • Bandwidth invariant bytes_exchanged ≤ 2 × d × log2(leaf_count) × 40 holds for divergence rates up to 10% (merkle.bandwidth_invariant, ties to M2).
  • Merkle root computation for a 1 M-key range completes in ≤ 100 ms on an 8-core SIMD host (M1; full SIMD path lands in Phase 10, §22, but the scalar baseline is measured here).

13.5 Conformance Fixtures

Fixture Purpose Expected Output

13.6 Pitfalls

  • Domain separation. Identical BLAKE3 prefixes for leaf and internal hashing let a bug (or adversarial input) construct a leaf whose hash collides with an internal-node hash; distinct prefixes are non-negotiable.
  • EMPTY_LEAF_HASH as zeros. Using [0u8; 32] for an empty leaf lets a crafted entry whose leaf_hash happens to be zero masquerade as empty; use the domain-separated constant instead.
  • Iteration-order sensitivity on first build. blake3_combine is associative- commutative only over the multiset of entries, not the iterator's traversal order — a storage engine that iterates differently across replicas on the very first build is still safe (I1 holds regardless), but tests must cover it explicitly (merkle_order_invariance, §12.5) or the invariant is unverified, not just untested.

13.7 Performance Concerns

Tree memory: ≈ 4.0 MiB per range at depth 16 (§4). Build is O(N) in entries and O(2^depth) in tree size; the flat Vec<Hash256> layout (not nested structs) is cache-friendly and enables the Phase-10 SIMD batch-hash path (§22.1). Comparison RPC overhead is ~40 bytes fixed per SubtreeQuery/SubtreeReply pair on top of the 32-byte hash — dominates total bytes at low divergence rates (§33).

13.8 Edge Cases

  • A range with zero entries: all leaves equal EMPTY_LEAF_HASH; roots match trivially; locate_divergence returns empty without a network round-trip (root-hash short-circuit).
  • A single-key range at the maximum tree depth: leaf bucketing degenerates to one occupied leaf out of 2^16; correctness holds but is a build-time/memory waste (§13.6-adjacent — ADR-07 recommends adjusting depth per range size).
  • Two replicas with the same keys but different HLCs (no value difference): the leaf hash must incorporate the full (key, ts, value_hash) triple so this is detected as divergence, not silently missed (feeds §14's resolver call, not a false convergence).

13.9 Failure Analysis

A regression in locate_divergence that under-reports divergent leaves is a silent correctness failure — the range appears converged when it is not. Detection: merkle.diff_localisation's differential test against a full linear scan baseline catches this pre-merge; in production, the Jepsen-style jepsen.partition_heal bucket (§27) would also surface it as a convergence-time SLO violation. Blast radius: unbounded (affects every range using the buggy code path). Containment: the conformance gate (P12) blocks release. Recovery: none needed in production if caught pre-merge; if it escapes, a full-range IBLT-or-Merkle re-scan (§19.4) is the remediation.

13.10 Operational Notes

Metric: ae_merkle_root_compute_seconds histogram, labeled by range_id (§21.2). Tracing: each locate_divergence call is a span with child spans per SubtreeQuery. Deployment: no schema/wire changes at this phase beyond what §8.1 already defines. Rollback: Phase 1 is additive over Phase 0's stub; reverting drops back to direct in-process diff with no data loss (Merkle trees are derived, not source-of-truth state).

14. Phase 2 — Active Anti-Entropy Scheduler

14.1 Objectives

Ship the gossip-driven scheduler that decides, every cycle, which peer to reconcile which range with — without a central coordinator (P4). Introduces partition-aware repair scope and token-bucket throttling to prevent repair-induced load amplification (P13).

14.2 Detailed Implementation Steps

  • ae-gossip/src/scheduler.rs: GossipScheduler — per-node loop on cycle_period (1 Hz default, ADR-06), selecting a (peer, range) pair via last_reconciled-weighted random selection (avoids the "same pair reconciles every second" starvation failure, §14.6). Applies Karp-Schenker-Shenker's push-pull-push convergence result (§5 Papers) to justify the cycle period.
  • ae-gossip/src/partition.rs: partition-aware scope filter — consults the membership view; only schedules (peer, range) pairs where both endpoints currently own the range (rejects stale-topology exchanges, I13-adjacent).
  • ae-gossip/src/token_bucket.rs: TokenBucket capping bandwidth at 25 MB/s per (peer, range) (§4; ADR successor of the original Cassandra compaction_throughput analog); EXPECTED_BYTES = 50 KB credit required before an exchange starts; enforces I10.
  • Repair-while-load adaptive policy: when 5-minute request-rate moving average exceeds 1.5× baseline, halve cycle frequency and token-bucket cap; restore on cooldown; floor at 1 exchange/minute/node so no range starves indefinitely (P11).
  • Wire the scheduler to ae-merkle::diff::locate_divergence (§13) via the AntiEntropyEngine trait (§11.8), now over ae-net's real TCP transport instead of Phase 0's direct calls.

Blast radius: the peer(s) targeted by the runaway exchange, and potentially cascading if their application traffic degrades.

15.1 Objectives

Ship the persistent, bounded hinted-handoff queue: coordinator-side hint generation on write-time replica unavailability (Dynamo sec. 4.6's sloppy quorum, P5), RocksDB-backed durable storage, rate-limited replay on replica recovery, and a non-silent drop policy.

16. Phase 4 — Synchronous Read Repair

16.1 Objectives

Ship request-time divergence detection and repair: a read at consistency level R collects R replica responses; on disagreement, resolve and write back. Establishes the synchronous-non-blocking default (P6) that later phases' asynchronous path (§17) builds on.

16.2 Detailed Implementation Steps

  • ae-repair/src/coordinator.rs: ReadCoordinator::get — fan out to replicas_for(key), collect r_count = level.required_for_read(replicas.len()) responses; if all equal, return directly (I6's idempotence means repeated equal reads never trigger spurious resolver calls).
  • ae-repair/src/quorum.rs: ConsistencyLevel::required_for_read enforcing W + R > N quorum-overlap semantics (Kleppmann 2017 ch. 5, §5 Required Reading).
  • Divergence detection: byte-for-byte VersionedValue comparison; a same-value, different-HLC pair is not divergence (HLC's logical component drifts harmlessly) — only a (value, ts) mismatch triggers repair (§8.3's worked example is this exact case).
  • ae-repair/src/sync_repair.rs: on divergence, call Resolver::resolve (§11.7, applying I6's CAI contract) then write back at W = 1 — durable-somewhere is sufficient because gossip (§14) and active anti-entropy propagate from there.
  • The blocking-vs-non-blocking ADR (§16.4 below): default to synchronous-non-blocking — resolve and return to the client immediately, tokio::spawn the write-back. Applies P6 and cites CASSANDRA-13289 as the real-world precedent for this default.
  • Write-back idempotence: the replica's storage layer rejects a write-back whose ts is not strictly greater than the currently-stored ts (HLC monotonicity check happens at the storage layer, not the coordinator — I3).

  • Write-back HLC-monotonicity check rejects 100% of stale write-backs in a fuzzed out-of-order-arrival test.

Allocation: responses.clone() before the spawn is a bounded, small-R allocation; not a hot-path concern at typical R ≤ 5.

16.8 Edge Cases

  • All R responses agree but one carries a tombstone: tombstone equality must be compared like any other VersionedValue (no special-casing that could mask a real divergence).
  • Coordinator crash between read-return and write-back spawn: the repair is lost for this read, but the next read on the same key re-detects and re-repairs (P11) — never treated as a correctness gap requiring special recovery.
  • Two concurrent reads on the same key both detect divergence and both write back: the storage-layer HLC-monotonicity check (§16.2) makes the second write-back a no-op, not a double-apply.

16.9 Failure Analysis

A resolver panic mid-resolve (e.g., malformed VersionedValue from a corrupted replica) propagates as a read-path error to the client — detection: error-rate metrics on ae_read_repair_fires_total; blast radius: the single request; containment: the resolver contract (I6) is property-tested pre-merge specifically to make this unreachable in correct code; recovery: none needed at the read layer — active anti-entropy (§14) will still converge the underlying range independent of any single read's outcome.

16.10 Operational Notes

Metrics: ae_read_repair_fires_total{mode="sync"}, ae_conflict_resolution_outcomes{kind} (§21.2). Tracing: the write-back span is detached from the client-request span (since it is tokio::spawned) but tagged with the originating request ID for correlation. Deployment: ReadRepairPolicy::Synchronous vs. AsynchronousProbabilistic is a per-request or per-keyspace policy-registry value (§21.1), hot-reloadable.

17. Phase 5 — Asynchronous (Probabilistic) Read Repair

17.1 Objectives

Ship the production default read-repair mode: fire-and-forget probabilistic repair at a configurable sampling rate (10% default, ADR-11), bounded by a backpressured queue so a high-divergence workload degrades observably rather than blocking reads (P6).

17.2 Detailed Implementation Steps

  • ae-repair/src/policy.rs: ReadRepairPolicy::AsynchronousProbabilistic { rate } — per-read Bernoulli draw against rate after the R-response collection (§16.2); on success, spawn resolver + write-back to the background; on failure, return the already-collected responses' resolved value with no repair work (client path is unaffected either way).
  • ae-repair/src/async_repair.rs: AsyncRepairQueue — bounded tokio::sync::mpsc channel (10K pending default, §4); try_submit is non-blocking: on a full queue, the work is dropped with an AtomicU64 counter increment and an ASYNC_REPAIR_DROPS metric, never queued unboundedly (mirrors I4's hint-queue bounding philosophy applied to a different subsystem).
  • Sampling-rate fidelity: use a per-coordinator SmallRng reseeded on a long interval (not rand::random()'s thread-local RNG) to keep the sampling draw cheap on the hot path (§17.6).
  • Backpressure semantics: a drop here is not catastrophic (P11 — active anti-entropy is the backstop) but is an operational signal that divergence is outpacing repair capacity.

17.3 Deliverable

ae-repair's AsyncRepairQueue and probabilistic sampling path fully wired; conformance bucket read_repair.async_sampling passing at the default 10% rate.

17.4 Acceptance Criteria

  • Sampling fidelity: a 10% sample rate over 100K reads fires repair within 10% ± 1% of target (read_repair.async_sampling).
  • Backpressure: under a synthetic 100K rps "every read diverges" workload, the queue drops at exactly the 10K-pending cap rate, the drop counter is accurate, and no panic/deadlock occurs (M8's throughput floor: ≥ 10K tasks/sec sustained before drop).
  • A 100% configured sample rate is documented and tested to degrade to synchronous-blocking-equivalent behavior once the queue saturates (§17.6) — the test asserts this is visible via metrics, not hidden.

17.5 Conformance Fixtures

Fixture Purpose Expected Output
read_repair.async_sampling (100K reads, 10%) Sampling fidelity Fire rate within ± 1% of target
async_repair_backpressure (100K rps synthetic) M8 Drops at cap rate, no panic
async_repair_100pct_saturation (regression) Saturation behavior Visible drop-rate spike, no silent stall

17.6 Pitfalls

  • rand::random()'s thread-local RNG allocation is non-zero-cost on a hot path; a per-coordinator SmallRng with periodic reseed avoids it.
  • A 100% sample rate is synchronous-blocking in disguise once the background queue saturates — recommend 1–10% for standing production configuration; reserve 100% for short, operator-triggered repair windows (ADR-11's rejected-alternative note).
  • Dropped-work telemetry must be a distinct counter from resolver-error telemetry — conflating "we chose not to repair this" with "repair failed" hides a real signal from operators.

17.7 Performance Concerns

try_submit's mpsc::Sender::try_send is O(1) and non-blocking by construction — the client-facing read path never waits on queue state. The SmallRng sampling draw is a few nanoseconds; negligible against the ≤ 0.5 ms read-repair latency budget inherited from §16's M7 (asynchronous mode adds effectively zero synchronous cost by design).

17.8 Edge Cases

  • Sample-rate reconfiguration mid-flight (policy-registry hot reload, §21.1): in-flight reads use the rate captured at read-start; no read observes a rate change mid-request.
  • Queue full at the exact moment of a rate-limit boundary: try_submit's failure path must be race-free — verified by the async_repair_backpressure fixture's concurrent producer stress variant.
  • A resolver that itself blocks (a misbehaving application-defined hook, §18.4): the background task blocks, consuming one queue slot indefinitely; documented as a contract violation (§18.4) with no runtime guard beyond the queue's fixed capacity bounding the blast radius.

17.9 Failure Analysis

Unbounded async-repair queue growth (a Phase-3-style bug reintroduced here) would exhaust memory; prevented structurally by the bounded mpsc channel (I4's bounding philosophy extended). Detection: ae_read_repair_async_drops_total rate; if it never increments under sustained high divergence, that itself is suspicious (should investigate whether the channel bound was accidentally raised or removed). Recovery: none needed — dropped repairs are recovered by active anti-entropy on the next gossip cycle (P2, P11).

17.10 Operational Notes

Metrics: ae_read_repair_fires_total{mode="async"}, ae_read_repair_async_drops_total (§21.2). A sustained non-zero drop rate is the operational signal to either raise the queue capacity, lower the sample rate, or investigate the underlying divergence source — documented in the (Phase 9) operator runbooks (§21.3).

18. Phase 6 — Conflict Resolution

18.1 Objectives

Ship the pluggable Resolver family: LWW+HLC (default), Riak-style siblings, CRDT integration (via blueprint #55), and the application-defined hook — all implementing the CAI contract (I6) that the entire convergence proof depends on (P7, P8, P9).

18.2 Detailed Implementation Steps

  • ae-resolver/src/lww.rs: LwwResolver — highest-Hlc wins (I3's lexicographic order, applying P7); a tombstone-winning resolution returns ResolveOutcome::Tombstone, not Single, so callers can distinguish delete-wins from value-wins.
  • ae-resolver/src/siblings.rs: SiblingsResolver — causal dedupe via Dotted Version Vectors (Preguiça et al. 2010, §5 Required Reading) solving the anonymous-client-update problem plain vector clocks cannot; returns Siblings(Vec<VersionedValue>) when the causal set has more than one mutually-concurrent member (applies P8).
  • ae-resolver/src/crdt.rs: CrdtResolver<C: Crdt> — wraps any blueprint #55 CRDT type (Counter, LwwMap, OrSet, Mvr, Sequence); merge is the CRDT's own merge operation; resolved timestamp is the max HLC observed (conservative, preserves I3's ordering downstream) (applies P9).
  • ae-resolver/src/custom.rs: with_custom_resolver — wraps an application-supplied closure satisfying the CAI contract (I6) as a Box<dyn Resolver>; the library documents but does not compiler-check the contract (§18.6).
  • Policy-registry integration (§21.1): the active resolver per-keyspace is a gossip- distributed policy value; I9 (uniform resolver across replicas serving a range) enforced by refusing to apply a write under a mismatched policy hash.

18.3 Deliverable

ae-resolver crate with all four Resolver implementations passing their respective property suites; examples/crdt_resolver.rs demonstrating blueprint #55 integration via CrdtResolver<C>.

18.4 Acceptance Criteria

  • LWW determinism: 10K random Vec<VersionedValue> inputs; resolve(permutation) is independent of permutation order (I6, resolver.lww).
  • Siblings causal dedupe: 1000 DVV scenarios match the Preguiça 2010 reference algorithm's output exactly (resolver.siblings).
  • CRDT merge: counter, OR-set, and LWW-map merges agree with blueprint #55's reference implementation on 1000 randomized merge sequences (resolver.crdt).
  • Resolver policy-mismatch detection: 100% of injected cross-replica policy-hash mismatches are caught and the write refused, in a 500-case fuzzed test.

18.5 Conformance Fixtures

Fixture Purpose Expected Output

18.6 Pitfalls

  • Plain wall-clock LWW (never shipped here, but a common mistake elsewhere) lets clock skew pick the winner instead of causality (P7) — the only LWW exposed is HLC-based.
  • A non-idempotent custom resolver is the classic bug: deduping by reference equality after deserialization produces fresh references every time, so the "merge" grows the value unboundedly — documented in the operator runbook (§21.3) as a caller responsibility, not a library guarantee.
  • Hand-rolled DVV implementations are subtle; Riak hit an off-by-one in this exact area (RIAK-1245) — property-test against the Preguiça 2010 reference rather than trusting a from-scratch implementation.

18.7 Performance Concerns

LwwResolver::resolve is O(R) comparisons — negligible. SiblingsResolver's causal dedupe is O(R^2) in the worst case (pairwise concurrency checks) — acceptable at typical R ≤ 5 but documented as a scaling concern if R grows (§30). CrdtResolver::resolve's cost is delegated entirely to the wrapped CRDT's merge — an allocating merge on every read at a sibling-bearing key is a per-read cost concern flagged in §18.8.

18.8 Edge Cases

  • A CRDT merge that allocates (Vec::clone, HashSet::from_iter) on every read inflates per-read cost when integrated carelessly; blueprint #55 is designed to be allocation-free in its merge path, but the integration point here must not add its own copy.
  • Sibling resolution "by length" (picking the longest sibling) is not commutative- associative-idempotent and is explicitly rejected — never implemented as a shortcut.
  • A resolver invoked with a zero-length values slice (should be unreachable given read-repair only fires at R ≥ 2, §16.6) is documented as a precondition violation, not silently handled — a debug-assertion catches it in development builds.

18.9 Failure Analysis

A non-idempotent custom resolver in production causes unbounded sibling-list growth (FM-7, §24; "sibling explosion") — detection: ae_sibling_count histogram trending upward; auto recovery: none (application-level contract violation); manual recovery: the sibling-explosion runbook (§21.3) recommends switching the affected keyspace to a CRDT resolver or a single-writer-per-key model.

18.10 Operational Notes

Metrics: ae_conflict_resolution_outcomes{kind}, ae_sibling_count histogram (§21.2). Runbook: docs/runbooks/sibling-explosion.md. Deployment: resolver selection is a per-keyspace policy-registry value (ae policy set --key /keyspace/x/resolver --value crdt:or-set, §21.1), hot-reloadable but gossip-propagated (so a brief window of cross-replica policy disagreement is possible and is what I9's mismatch-refusal guards against).

19. Phase 7 — Set Reconciliation via IBLT

19.1 Objectives

Ship the Invertible Bloom Lookup Table fast path: O(d) bandwidth set reconciliation for bounded symmetric-difference sizes, with a correctness-preserving fallback to Merkle (§13) when the difference exceeds the provisioned cell budget (P10, ADR-14, ADR-15).

19.2 Detailed Implementation Steps

  • ae-iblt/src/params.rs: cell-count formula cell_count = (d_expected × 1.5).next_power_of_two() (ADR-14's c ≈ 1.5 over-provisioning factor, Eppstein et al. 2011 §4).
  • ae-iblt/src/construct.rs: Iblt::add — hash each (element_id, check_hash) pair to 3 cells (the 3-hash variant), XOR-accumulate id_xor/hash_xor, increment count; the check-hash is BLAKE3-keyed with the IBLT's own seed (not a plain hash) to bound the false-positive rate below 2⁻³⁰ (§19.5, applies ADR-17's constant-time-comparison discipline for the equality check).
  • ae-iblt/src/decode.rs: peel-back decoder — repeatedly find a "pure" cell (count.abs() == 1 and the check-hash confirms a single element), record it, subtract it from all three cells it hashes to; terminate successfully when every cell is zero; return Err(DecodeError::Exhausted) if no pure cell remains and cells are non-zero (I8's never-silently-wrong guarantee).
  • Iblt::sub — element-wise XOR/count-subtract producing an IBLT over the symmetric difference of the two input sets, without either side revealing its full set (Minsky- Trachtenberg-Zippel 2003's O(d)-communication result, §5 Required Reading, realized here via the IBLT construction rather than the polynomial-interpolation variant).
  • Fallback wiring (ae-repair::coordinator::reconcile_range_via_iblt_or_merkle): on Exhausted, increment IBLT_DECODE_FAILS and invoke ae-merkle::diff::locate_divergence (§13) instead — applies ADR-15's non-negotiable fallback.

19.3 Deliverable

ae-iblt crate with construction, subtraction, and peel-back decoding fully implemented and property-tested; examples/iblt_decode_demo.rs demonstrating a successful decode and a deliberately-over-budget fallback-to-Merkle case.

19.4 Acceptance Criteria

  • IBLT correctness: 10K random (A, B) set pairs with |A △ B| ≤ 0.8 × d_expected decode successfully and produce the exact symmetric difference (iblt.decode_correctness).
  • Fallback behavior: when |A △ B| > d_expected, decode fails gracefully (Err(Exhausted)) and the Merkle fallback recovers full correctness in bounded time (iblt.fall_back).
  • False-positive rate (a non-pure cell misidentified as pure due to hash collision) < 2⁻³⁰ over 100K decode runs near the provisioning budget (iblt.false_positive_rate).
  • Bandwidth: for d_expected = 1000 and actual diff = 500, IBLT exchange costs ~36 KB (1500 cells × 24 bytes/cell) versus ~115 KB for the equivalent Merkle exchange.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
iblt.decode_correctness (10K pairs) I8 Exact symmetric difference recovered
iblt.fall_back (1000 over-budget cases) ADR-15 Exhausted → Merkle recovers state
iblt.false_positive_rate (100K near-budget runs) Check-hash soundness Rate < 2⁻³⁰
iblt_cell_count_power_of_two (regression) Cell-count rounding Actual size logged, no silent doubling surprise

19.6 Pitfalls

  • Cell-count next_power_of_two rounding is convenient for indexing but can nearly double the provisioned cell count — the actual size must be logged/exposed in metrics, not silently absorbed.
  • The "no pure cell exists but the IBLT is non-empty" case is a correctness failure if undetected — the post-decode all-cells-zero check (I8) is non-negotiable; skipping it returns a partial, silently-wrong difference.
  • IBLT decoding is probabilistic: very rarely, a hash collision in hash_xor makes a non-pure cell look pure. The BLAKE3-keyed check-hash (not a plain hash) is the guard; Eppstein et al. 2011 sec. 4.2 gives the false-positive analysis this blueprint's 2⁻³⁰ target is derived from.

19.7 Performance Concerns

IBLT construction/decoding costs more CPU than a Merkle build for the same key count, but wire cost is O(d) not O(d log N) (P10) — the tradeoff is explicit and per-range tunable via d_expected. Decode is O(cells) per peel-back iteration in the scalar path; the Phase-10 SIMD variant (§22.4) reduces this to O(cells/8) for large IBLTs. Bandwidth- constrained links (cross-DC, §20) prefer IBLT; CPU-constrained nodes prefer Merkle (§13).

19.8 Edge Cases

  • d_actual = 0 (sets already identical): decode terminates immediately with empty difference sets — no peel-back iterations needed, and the fixed IBLT payload is still exchanged (a small fixed cost even at zero divergence, unlike Merkle's root-hash short-circuit at §13.8).
  • d_actual exactly at the d_expected boundary: decode success probability is not 100% at the boundary by design (the 1.5× over-provisioning gives headroom, ADR-14) — the fallback path (ADR-15) is the correctness backstop for this exact regime, not an edge case to special-case away.
  • Two IBLTs built with different seed values: sub still produces a mathematically valid symmetric-difference IBLT (the seed only affects the check-hash, not the XOR algebra) but the check-hash validation during decode requires using a consistent seed convention — the wire protocol (§8.1) carries the seed explicitly to avoid this class of bug entirely.

19.9 Failure Analysis

An operator-configured d_expected that is chronically too low for the workload causes a rising IBLT_DECODE_FAILS rate — detection: ae_iblt_decode_outcomes{outcome="exhausted"} trend; auto recovery: the Merkle fallback (ADR-15) keeps correctness intact automatically; manual recovery: raise d_expected via ae policy set (§21.1), which grows the cell count proportionally on the next IBLT build. Blast radius of a mis-tuned d_expected: pure performance (more Merkle fallback traffic), never correctness (I8 guarantees this).

19.10 Operational Notes

Metrics: ae_iblt_decode_outcomes{outcome} (§21.2). An alert on a rising exhausted-outcome rate is the signal to re-tune d_expected per range, documented as part of the stuck-repair runbook's diagnostic checklist (§21.3). Deployment: d_expected is per-range, policy-registry-configurable, defaulting to 1000 (§4).

20. Phase 8 — Multi-DC / WAN Anti-Entropy

20.1 Objectives

Extend the gossip scheduler (§14) and Merkle exchange (§13) to cross-DC links: distinct bandwidth caps, a slower gossip cadence, and leaf-batching to reduce round count on high-RTT, low-bandwidth links. PhaseDeferred("§20") marks QUIC transport (ADR-20) as out of scope for this phase; TCP carries it.

20.2 Detailed Implementation Steps

  • ae-gossip/src/scheduler.rs: CrossDcScheduler wraps GossipScheduler with a dc_bandwidth_cap: HashMap<DcId, f64> and cross_dc_cycle: Duration (60 s default, §4) — distinct from the 1 Hz intra-DC cycle (ADR-06).
  • Membership must carry DC labels (a prerequisite noted as a pitfall, §20.6); the scheduler's partition-aware filter (§14.2) is extended to also distinguish intra- vs. inter-DC peer pairs for cap selection.
  • Batched-leaf Merkle hashing: an additional tree level groups k = 16 consecutive leaves into one exchanged hash; on batch-hash disagreement, descend into the batch to find the differing leaf(ves) — optimizes for WAN's "cheap round-trip, expensive byte" cost profile, the mirror image of intra-DC's assumption (applies P3 to a different regime).
  • Cross-DC Merkle comparison reuses the identical SubtreeQuery/SubtreeReply protocol (§8.1) over the same transport, just at the slower cadence and lower cap.

20.3 Deliverable

CrossDcScheduler in ae-gossip, exercised by a 2-DC simulator topology with configurable cross-DC RTT; docs/architecture/gossip-scheduler.md updated with the WAN variant.

20.4 Acceptance Criteria

  • A 2-DC simulator with 100 ms cross-DC RTT converges a 1 M-key range with 1% divergence in under 5 minutes using the cross-DC scheduler (M10).
  • Batched-leaf hashing reduces cross-DC bandwidth by ≥ 60% for the same divergence rate on the 1 M-key range, measured against the unbatched baseline.
  • The cross-DC bandwidth cap (1 MB/s default) is respected within 5% over a 60 s window, identically to I10's intra-DC guarantee but at the WAN cap value.

20.5 Conformance Fixtures

Fixture Purpose Expected Output
wan.convergence_2dc (100 ms RTT, 1% divergence) M10 Converged within 5 minutes
wan.batched_leaf_bandwidth Batching efficiency ≥ 60% bandwidth reduction vs. unbatched
wan.cap_enforcement Cross-DC I10 analog ≤ 5% deviation from 1 MB/s cap

20.6 Pitfalls

  • A cross-DC repair that consumes 100% of the link's bandwidth starves application traffic — the cap is non-negotiable, identically to P13's intra-DC rationale.
  • DC-aware membership is a prerequisite, not an add-on: without DC labels from Phase 0 onward, the scheduler cannot distinguish intra- from inter-DC peers and bandwidth-aware scheduling is impossible to retrofit cleanly.
  • Applying the intra-DC 1 Hz cycle unmodified to a WAN link wastes bandwidth on fingerprint exchange alone (48 bytes × 1000 ranges × 1 Hz adds up over many DC pairs) — the 60 s cross-DC default exists specifically to avoid this.

20.7 Performance Concerns

Batched-leaf hashing trades a small amount of localisation precision (a batch of 16 leaves must be fully re-compared on disagreement) for a large reduction in round count — the right trade when RTT dominates cost (WAN) rather than bytes (intra-DC, where unbatched per-leaf comparison is preferred, §13). The batch factor k = 16 is tunable per link.

20.8 Edge Cases

  • A DC pair with asymmetric bandwidth (one direction fast, one slow): the token bucket is per-(peer, range) directional in principle but the current design caps aggregate exchange bytes symmetrically — documented as a known simplification, not a silent gap (revisit if asymmetric-link deployments become common, §30).
  • A node whose DC label is missing or malformed at startup: the scheduler must refuse to schedule any cross-DC exchange involving that node rather than guessing a default DC — fail-safe, not fail-open.
  • Cross-DC link flapping (brief connectivity loss every few minutes): the 60 s cycle's relative infrequency means a flapping link may cause a full cycle's exchange to fail and retry next cycle rather than thrashing — an intentional damping effect of the slower cadence.

20.9 Failure Analysis

A misconfigured cross-DC cap that is too aggressive (set too high) reintroduces P13's load-amplification risk across the more expensive/scarcer WAN link — detection: link saturation alerts (outside this system's scope, but ae_repair_bytes_exchanged_total correlated with known link capacity is the internal signal); recovery: lower the cap via the policy registry (§21.1), hot-reloadable without restart.

20.10 Operational Notes

Metrics: existing ae_repair_* metrics gain a DC-pair dimension via labels where the membership table supplies it. The partition-heal runbook (§21.3) is extended with a cross-DC variant noting the longer expected convergence window (M10's 5-minute bound vs. intra-DC's 30 s).

22. Phase 10 — Performance Hardening

22.1 Objectives

Close the gap between "correct" (Phases 0–9) and "meets the M1–M12 targets" (§29): SIMD-accelerated Merkle hashing, parallel range repair, batched hint replay, and SIMD IBLT decoding. This is the last phase before the conformance suite (§27) and 30-day soak gate this system for release.

22.2 Detailed Implementation Steps

  • Vectorised Merkle hashing: BLAKE3's built-in SIMD via Hasher::update_rayon, parallelising leaf-level hashing across cores (dominant cost at depth 16, §13.7); the Rayon pool is bounded to num_cpus::get_physical() (not logical/hyper-threaded cores) to avoid contending with the application's own threads (§22.6).
  • Parallel range repair: the scheduler's repair_concurrency_limit = 4 (ADR-08) permits up to 4 ranges repairing concurrently; bandwidth-bounded independently by the per- (peer, range) token bucket (§14.2, I10) and CPU-bounded independently by the Rayon pool — the two bounds do not interact.
  • Batched hint replay: HintBatch of up to 1000 hints per RPC, applied transactionally (all-or-nothing) at the receiving replica so a mid-batch crash never produces partial state — ~10× replay throughput over Phase 3's per-hint RPC baseline, at the cost of higher per-batch worst-case latency.
  • SIMD IBLT decoding: AVX2 __m256i-based scan of 8 cells at once for the "find a pure cell" peel-back step, reducing per-iteration cost from O(cells) to O(cells/8) for large IBLTs (d_expected > 10000); runtime-dispatches to the scalar path (§19.2) on hosts without AVX2 — both paths run in the conformance suite (§22.5).

22.3 Deliverable

Benchmark results in benchmarks/results/ meeting all of M1, M4, M6, and the parallel- repair throughput target below; both SIMD and scalar IBLT decode paths passing conformance.

22.4 Acceptance Criteria

  • Merkle root computation: < 100 ms for 1 M keys on an 8-core SIMD-capable host (M1, now measured with the full vectorised path rather than Phase 1's scalar baseline).
  • Hint replay: > 50K hints/sec sustained over a 1 M-hint replay on SSD (M4, with batching).
  • IBLT decode: 10K-element symmetric difference decodes in < 100 ms on a single core; < 20 ms with SIMD (M6).
  • Parallel-range repair: 4 concurrent range repairs sustain 60 MB/s aggregate without exceeding any single per-(peer, range) bucket's cap.

22.6 Pitfalls

  • Rayon's thread pool defaults to one thread per logical core; on a hyper-threaded host this contends with application threads — bound the pool to num_cpus::get_physical() explicitly.
  • Batched hint replay introduces an in-flight-but-unacknowledged window; on coordinator crash the same batch can be retried, and the receiving replica must dedupe by HLC (I3) — this is the storage layer's responsibility, tested under crash injection here.
  • SIMD IBLT decoding requires AVX2; the scalar fallback must be exercised in CI on a non-AVX2 runner (or an explicitly-disabled-feature build), not just assumed correct by symmetry with the SIMD path.

22.7 Performance Concerns

This entire phase is the performance-concerns phase — see §29 (Performance Engineering) for the full benchmarking methodology, allocation/lock/cache analysis, and the complete M1–M12 targets table this phase is gated against.

22.8 Edge Cases

  • A host with AVX2 but a CPU-throttling BIOS setting that disables it at runtime: the dispatch must detect actual runtime support (via is_x86_feature_detected!), not just compile-time target features, or it will crash on unsupported instructions.
  • Rayon pool contention when num_cpus::get_physical() == 1 (single-core host, e.g., a small container): the parallel Merkle hash path must degrade to effectively-sequential execution correctly, not deadlock on an empty thread pool.
  • A hint batch that is exactly at the 1000-hint boundary: batch-size-off-by-one is a classic bug class; a dedicated boundary-value fixture (999/1000/1001 hints) is included in the conformance corpus.

22.9 Failure Analysis

A Rayon pool misconfiguration (unbounded logical-core usage) starves application request- handling threads on the same host — detection: application-level p99 latency regression correlated with a Merkle-build event; recovery: the num_cpus::get_physical() bound (§22.6) is the structural fix, not a runtime toggle — a regression here requires a code fix and redeploy, caught by the perf.merkle_simd benchmark's regression gate (§29) before it reaches production.

22.10 Operational Notes

Benchmark results are archived per-commit under benchmarks/results/ (§10) and gated in CI (bench.yml, §26/§28) — a regression beyond a configured tolerance fails the build (Performance Engineering, §29). No new metrics beyond §21.2's table; this phase makes existing metrics hit their targets rather than introducing new observability surface.

23. Threat Model

23.1 Trust boundaries

  1. Caller boundary. The host application supplies keys, values, and consistency-level annotations; this library trusts it not to corrupt the storage engine underneath and does not audit on-disk bytes itself.
  2. Replica boundary. Replicas are honest-but-down: they may crash, partition, or restart with stale state, but they do not lie. Byzantine (lying) replicas are out of scope (PhaseDeferred("§23"), Project #94's surface, ADR-22).
  3. Network boundary. The network may delay, reorder, or drop packets arbitrarily but is assumed not to modify them undetected — integrity is delegated to the transport (TLS optional intra-DC, expected cross-DC).
  4. Operator boundary. Operators are trusted; the CLI's UID-based RBAC (§21.1) prevents accidental cross-tenant action, not a malicious operator. Audit logging is the mitigation for that residual risk.

23.3 Worked incident trace — 6-hour partition recovery

A replica partitions for 6 hours. During the partition: the coordinator hints every write targeting it (T2's mitigation path, §15) up to the 4 GiB/1 GiB caps; active anti-entropy (§14) continues gossiping fingerprints among the reachable replicas, so they stay converged with each other. On heal: gossip detects the recovered heartbeat; ReplayDriver (§15.2) drains hints for that target at the rate-limited throughput (M4); simultaneously, the gossip scheduler's next cycles run full Merkle comparisons against the recovered replica to catch anything the hint queue dropped or never captured (cold keys nobody wrote during the partition but that drifted via, e.g., a resolved sibling on another replica). Convergence completes within the RTO bound (§4: ≤ 30 s intra-DC per jepsen.partition_heal, §27) once both mechanisms finish their pass — this is precisely the "three mechanisms, not one" property (P2) demonstrated end-to-end.

23.4 Deferred security surfaces

PhaseDeferred("§23") — Byzantine-tolerant repair via signed Merkle proofs (T1); out of scope, Project #94. PhaseDeferred("§21") — cryptographically signed policy registry (T3's deeper mitigation); required before multi-tenant deployment across a trust boundary.

25. Operational Readiness

Metrics. The full Prometheus exposition is defined once, in §21.2, and referenced by name from every phase's N.10 — there is no second metrics list to drift out of sync with it.

Tracing. Every AntiEntropyEngine call (§11.8) and every ReadCoordinator::get invocation (§16.2) is a tracing span; child spans cover SubtreeQuery/SubtreeReply round-trips (§8.1) and resolver invocations, so a slow repair round or a slow read can be attributed to a specific sub-step rather than a single opaque duration.

Structured logging. Every telemetry-emitting event (I11) pairs its metric increment with a structured log line carrying the relevant IDs (range_id, target node, batch_id) — never a bare counter increment with no correlatable context.

Dashboards. One dashboard per subsystem (Merkle, gossip, hints, read-repair, resolver, IBLT), each keyed to the metrics table in §21.2; a cluster-overview dashboard aggregates ae_repair_ranges_total and ae_hint_drops_total across all nodes.

Alerting philosophy. Alert on rates and trends, not point-in-time values: a rising ae_hint_drops_total slope, a rising ae_iblt_decode_outcomes{outcome="exhausted"} slope, a ae_sibling_count histogram whose p99 crosses a threshold. Point-in-time thresholds alone (P14) produce alert fatigue on a system whose steady state is "constantly repairing something, slowly" (P11).

SLOs. Intra-DC partition-heal convergence ≤ 30 s (RTO, §4); cross-DC convergence ≤ 5 min for the M10 scenario; synchronous-non-blocking read-repair latency add ≤ 0.5 ms p99 (M7). SLO breaches feed the stuck-repair and partition-heal runbooks.

Incident response. The four runbooks (§21.3) are the first response artifact for any paging alert tied to the metrics above; each names the specific commands and metrics to check, never "contact on-call" as a terminal step (§21.6).

Named runbooks. docs/runbooks/stuck-repair.md, hint-queue-overflow.md, sibling-explosion.md, partition-heal.md (§10, §21.3).

Backup/restore. The Merkle tree is derived state (rebuildable from the storage engine's own data, §11.4) and is never backed up directly. The hint queue is transient state (§26) and is also excluded from backup scope — a lost hint queue converges via active anti-entropy instead of data loss.

Deployment topology. One ae instance embedded per replica process; the RocksDB hint CF colocated with the replica's own data directory so hint durability and data durability share the same failure domain (a lost data directory loses both consistently, rather than a hint queue surviving a data loss it should not survive).

Canary / rolling-upgrade / rollback. New phases are additive over prior ones (each phase's §N.3 Deliverable is independently runnable); a rolling upgrade can run mixed Phase-N and Phase-(N+1) binaries during rollout because the wire protocol (§8.1) is versioned via the generation field and the ADR-16 CBOR schema is additive-only (§26). Rollback is symmetric: reverting a phase's binary drops back to the prior phase's capability set with no forced data migration, because all phase-specific state (Merkle trees, IBLTs) is derived/ephemeral.

26. Compatibility & Versioning

Wire compatibility. ae-net's CBOR messages (§8.1) are additive-only: new optional fields may be added; existing fields are never removed or repurposed within a major version. The generation field on RangeFingerprint (§11.3) is the mechanism that lets two differently-versioned replicas detect and safely reject a stale/incompatible comparison (§8.4) rather than silently misinterpreting bytes.

Storage compatibility. The hint queue (RocksDB, §11.10) is transient — it is safe to drop entirely across a major-version upgrade (no migration required); Merkle trees are derived and rebuilt on demand, never migrated. The only durable, migration-relevant state this library owns is the policy registry (§21.1), which uses a versioned schema with a schema_version field mirrored from the conformance report format (§19.2's precedent).

API stability. The Resolver and AntiEntropyEngine traits (§11.7, §11.8) are the public extension points; both are Send + Sync + 'static and additive-only across minor versions (new methods are added with default implementations, never breaking existing implementors).

Migration. A major-version upgrade that changes the Merkle leaf-hash domain-separation scheme (§13.2) forces a one-time full-range rebuild on all replicas — documented as an explicit, operator-triggered migration step (ae repair start --mode manual across every range), never an implicit background migration that could race with normal repair traffic.

Deprecation policy. A deprecated ADR-locked choice (e.g., an old IBLT cell-count formula) is supported for one full major version after its replacement ships, with a deprecated flag surfaced in ae policy get output, then removed.

SemVer policy. MAJOR.MINOR.PATCH. MAJOR: wire or storage schema break. MINOR: new optional wire field, new CLI subcommand, new metric. PATCH: bug fixes with no schema or API change.

Rolling-upgrade guarantees. Because the wire protocol is additive-only and the generation field detects true incompatibilities, a cluster may run N and N+1 binaries simultaneously during a rolling upgrade for the duration of that upgrade window, with active anti-entropy (§14) and read repair (§16, §17) continuing to function correctly against both versions throughout.

27. Testing & Verification Strategy

Unit tests. Per-crate, colocated with source (#[cfg(test)]); cover pure-function contracts (Hlc ordering, I3; KeyRange::contains; cell-count formulas).

Integration tests. examples/*.rs (§10) double as executable integration tests, exercised via cargo test --examples and again via CI (ci.yml).

Property tests. The backbone of correctness verification, one property per invariant (§7's debugging methodology): merkle.build_determinism (I1), merkle.diff_localisation (I2), hint.cap_enforcement (I4), hint.ttl_drop (I5), resolver.lww/siblings/crdt (I6), iblt.decode_correctness/false_positive_rate (I8), gossip.token_bucket (I10) — implemented with proptest or hand-rolled randomized-input harnesses seeded deterministically (§12.6's discipline extended cluster-wide).

Differential testing. merkle.diff_localisation and iblt.decode_correctness are differential tests against a brute-force linear-scan baseline — the property under test is "the fast path agrees with the obviously-correct slow path," not just "the fast path does not crash."

Fuzzing. ae-fuzz crate (§10): merkle_diff.rs, iblt_decode.rs, hint_replay.rs, resolver_lww.rs — cargo fuzz targets run nightly (fuzz.yml) with a corpus seeded from the conformance fixtures (§12.5, §13.5, §15.5, §18.5, §19.5); any crash or Miri-flagged undefined behavior in the IBLT decoder or BLAKE3 hasher (both partially unsafe for SIMD, §1) blocks release.

Chaos / fault injection. The Jepsen-style buckets (jepsen.partition_heal, jepsen.replica_restart, jepsen.sibling_explosion, §27.1 below) run against the simulator/ deterministic world with injected partitions, restarts, and adversarial write patterns — modeled directly on Kingsbury's Jepsen methodology (§5 Required Reading).

Deterministic replay. Every simulator scenario is seed-driven (SeedableRng, §12.2); a failing CI run's exact scenario is reproducible locally via the same seed — no "couldn't reproduce the flaky failure" class of bug is tolerated in this test suite.

Soak testing. A 24-hour continuous-churn canary (M11) runs on every release candidate; a 30-day continuous-churn soak (M12, PhaseDeferred("§27") as the un-defer trigger for the Sealed milestone, §36) gates the long-lived-stability claim beyond what a 24-hour run can show (memory growth, fd leaks, slow-accumulating queue drift).

Fault injection matrix. Partition (symmetric, asymmetric, flapping), process crash (SIGKILL at 1000 random points, §15.4), disk-full, clock skew, membership churn — each combined with the three repair mechanisms independently disabled/enabled to verify P2's "all three required" claim empirically, not just by assertion.

28. Build & Release Engineering

Reproducible builds. rust-toolchain.toml pins the exact compiler version (ADR-01); Cargo.lock is committed and verified unchanged in CI (cargo verify-project plus a lock- file-diff check) so a given commit always produces a bit-identical dependency graph.

Artifact signing. Release binaries are signed (cosign or an equivalent detached- signature scheme) and the signature published alongside the artifact in release.yml.

SBOM. A Software Bill of Materials is generated per release (cargo-cyclonedx or equivalent) and archived alongside the binary, enumerating every dependency and its license (cross-checked against deny.toml's allowlist, ADR-18).

Release channels. stable (tagged releases, soak-gated per M12), nightly (built from main, conformance-gated but not soak-gated) — mirroring the Rust project's own channel convention, familiar to the target audience (§1).

CI/CD topology. ci.yml (build + unit) → conformance.yml (P12's gate) → jepsen.yml + fuzz.yml + bench.yml (parallel, all required) → security.yml (cargo-audit, cargo-deny, MSRV check) → release.yml (tag-triggered, only after all upstream jobs are green).

Version stamping. Every binary embeds its git SHA, build timestamp, and schema_version (§26) via vergen or equivalent, surfaced by ae --version and in the conformance report's stack_version field (§19.2).

Provenance/attestation. Release artifacts carry SLSA-style provenance metadata (build system identity, source commit, build parameters) sufficient for a consumer to verify the binary was built by the documented CI pipeline from the documented source, not hand-assembled.

Dependency auditing. cargo audit runs in security.yml on every PR and nightly on main; a new advisory affecting a dependency in deny.toml's tracked set blocks merge until triaged (patched, replaced, or explicitly allowlisted with a documented justification).

29. Performance Engineering

Benchmarking methodology. criterion-based benches (ae-bench, §10) run in CI (bench.yml) with statistical regression detection (a run whose mean exceeds the historical mean by more than a configured tolerance, e.g., 10%, fails the gate) — not a single-sample "looks fine" check.

Profiling methodology. perf/flamegraph for CPU hotspots (Merkle build, IBLT decode); heaptrack/valgrind --tool=massif for allocation profiling on the hint-queue and resolver paths; tokio-console for async task scheduling visibility on the gossip scheduler and replay driver.

Allocation analysis. The Merkle tree's flat Vec<Hash256> layout (§13.7) and the IBLT's fixed-size Vec<Cell> (§19.7) are both single-allocation-per-structure by design — profiled to confirm no per-hash or per-cell heap churn during build/decode.

Lock contention analysis. The HintLog's RocksDB-internal locking (§11.10) and the gossip scheduler's RwLock<Membership> (§14.2) are the two lock-bearing hot paths; tokio-console's task-blocking view is the primary diagnostic for contention regressions.

Cache locality. The flat Merkle tree layout is deliberately cache-friendly (level-order Vec, §13.7); the IBLT's cell array is similarly contiguous, enabling the SIMD scan (§22.2's __m256i 8-cells-at-once path).

Syscall overhead. RocksDB WAL fsync cadence (§15.2's tuning) and Tokio's TCP read/write syscalls are the two syscall-heavy paths; batched hint replay (§22.2) amortizes syscall count per hint from O(1 per hint) to O(1 per 1000 hints).

Tail-latency analysis. p99/p999 tracked separately from mean for the read-repair path (M7) specifically because the synchronous-non-blocking design (§16.2) exists to bound tail latency, not just average latency — a mean-only view would hide exactly the regression this design guards against.

30. Scalability Analysis

What stays constant. Per-range Merkle tree memory (≈ 4.0 MiB at depth 16, §4) regardless of key count within the range (fixed leaf count); per-(peer, range) token-bucket bookkeeping (O(1) state per pair, §14.2).

What grows, and the Big-O. Number of ranges grows with total keyspace size (linear); gossip scheduling candidate set grows O(peers × ranges) per cycle (§14.7); hint-queue column-family count grows O(cluster size) (one CF per distinct target, §11.10, bounded by the FD budget, §4); sibling-list length grows unboundedly without a convergent resolver (the failure mode this system is designed to prevent, FM-7).

Named bottlenecks, in order. (1) Gossip scheduler candidate evaluation at very large N (peers × ranges) — the motivating case for the deferred dataflow-streaming alternative (§35.3, ADR-21). (2) RocksDB column-family count at very large cluster size — mitigated by capping total CFs and consolidating rarely-hinted targets (a Phase-1+ refinement, not yet built). (3) Cross-DC bandwidth at many-DC topologies — each DC pair needs its own bandwidth-cap bookkeeping, O(DC²) in the worst fully-connected-mesh case (§20).

Horizontal scaling. Adding replica nodes increases both N (the divergence-detection surface, more pairwise gossip) and the aggregate repair-bandwidth budget (more (peer, range) token buckets) — the system scales horizontally by design (P4's decentralization argument) but the gossip candidate-evaluation cost (bottleneck 1 above) is the practical ceiling before a scheduling redesign is needed.

Vertical scaling. More cores directly speeds Merkle build/IBLT decode (§22's SIMD + Rayon parallelism) and more memory permits larger d_expected IBLT provisioning without falling back to Merkle as often (P10) — vertical scaling helps the CPU-bound paths more than the network-bound ones.

Sharding/partitioning. This library does not own partitioning (delegated to the host store, §1) but assumes range boundaries are relatively stable; a partitioner that re-shards frequently invalidates Merkle trees frequently (forcing rebuilds, §13.1) and is the sharding-frequency assumption the generation field (§11.3) is designed to detect and handle safely, not silently corrupt.

Coordination overhead. Zero centralized coordination by design (P4) — the only coordination primitive is the policy registry's gossip-propagated eventual consistency (§21.1, itself using this project's own machinery, "eating its own dog food").

Practical ceiling and levers beyond it. At very large N (thousands of nodes, hundreds of thousands of ranges), gossip candidate-evaluation cost and RocksDB CF count become the binding constraints (bottlenecks 1–2 above); the levers are: (a) hierarchical gossip (gossip within a rack/AZ first, then across, reducing the effective N per cycle); (b) the deferred differential-dataflow streaming convergence model (§35.3, ADR-21), which trades polling overhead for continuous incremental computation; (c) consolidating low-volume hint targets into shared CFs once the per-target volume drops below a threshold. None of these are built in Phases 0–10; all are named explicitly rather than silently assumed away.

31. Mental Models & First Principles

  1. MM1 — A Merkle tree is a bandwidth-compression scheme for equality checking. The insight: you never need to ship the data to know whether two ranges match; you ship a 32-byte summary and only descend where summaries disagree. It predicts that fingerprint exchange cost is independent of range size and depends only on divergence (§13.4's O(d log N) bound). The bug class you write without it: unconditionally shipping full range payloads to "be safe," which is the O(N) design this entire subsystem exists to avoid. Resolving §: §13.
  2. MM2 — Repair is a rate, not a state. There is no "fully repaired" signal (P11); the only meaningful question is "what is the reconciliation rate right now, relative to the divergence rate?" It predicts that any dashboard or runbook promising "repair complete" is wrong by construction. The bug class without it: operators who wait for a terminal state that never arrives, or alerts that fire on "repair still running" as if that were itself an anomaly. Resolving §: §14, §30.
  3. MM3 — Gossip convergence time is logarithmic in cluster size, not linear. From Karp-Schenker-Shenker (§5): a rumor started at one node reaches all N nodes in O(log N) push-pull-push rounds. It predicts that a 1 Hz cycle stays adequate as cluster size grows into the low thousands without a cycle-period redesign. The bug class without it: assuming gossip "doesn't scale" and over-engineering a centralized scheduler (P4) that is itself a single point of failure. Resolving §: §14.1, §9 ADR-06.
  4. MM4 — A vector clock without per-writer dots can't tell two independent writers from one replayed write. The Dotted Version Vector insight (Preguiça et al. 2010, §5): annotating each version with a per-replica dot disambiguates "anonymous concurrent update" from "the same update replicated twice." It predicts that a naive vector-clock sibling implementation produces phantom conflicts under replay. The bug class without it: sibling lists that grow even when no real concurrent write occurred. Resolving §: §18.2.
  5. MM5 — IBLT trades a probabilistic guarantee for a communication-complexity win. From Minsky-Trachtenberg-Zippel and Eppstein et al. (§5): O(d) communication is only achievable by accepting a decode-failure probability that grows as the actual difference approaches the provisioned budget. It predicts that any IBLT deployment without a correctness-preserving fallback will eventually — not might, will — fail silently at high divergence. The bug class without it: shipping IBLT alone, no Merkle fallback, and treating a rare decode failure as "it'll never happen in practice." Resolving §: §19, §9 ADR-15.
  6. MM6 — A delete is a write, and forgetting that creates unbounded state growth. A tombstone (§11.2) participates in Merkle hashing and gossip exactly like a live value; it predicts that a system that special-cases deletes as "just remove the bytes" breaks convergence (a delete on one replica must still be reconcilable against a live value on another). The bug class without it: an ever-growing keyspace from ungarbage-collected tombstones (§24, adjacent to FM-10's memory-bloat class). Resolving §: §13.6, §24.
  7. MM7 — Backpressure is a design decision, not an accident. Every bounded queue in this system (hint queue, §15; async-repair queue, §17) drops with telemetry rather than growing — this predicts that "just increase the buffer size" is never the fix for a drop-rate alert; the fix is either reducing the input rate or increasing the drain rate. The bug class without it: an unbounded queue that defers an out-of-memory crash instead of surfacing an operational signal early. Resolving §: §15, §17.
  8. MM8 — A resolver is only safe if it is a CAI (commutative, associative, idempotent) function — which is exactly the algebraic structure a CRDT merge has. This predicts that any custom resolver hook (§18.4) that is not CAI will eventually produce a permanently-diverging sibling set under the right write pattern, not just an occasionally-wrong answer. The bug class without it: a "reasonable-looking" custom merge (e.g., pick-the-longest-value) that silently breaks convergence under replay or reordering. Resolving §: §11.7, §18.

33. Back-of-Envelope Capacity Model

  1. Merkle tree memory per range (depth 16, ADR-07): (2^16 − 1 + 2^16) × 32 B = 131,071 × 32 B = 4,194,272 B ≈ 4.0 MiB (§4).
  2. Total Merkle memory per node at a typical 256 ranges/node (vnode-style token-ring granularity): 256 × 4.0 MiB ≈ 1.0 GiB — the memory-planning number an operator needs before provisioning node RAM (chained from #1).
  3. Worst-case hint accumulation for a target down T = 24 h at write rate W = 1000 writes/s, average hint size H ≈ 1 KB: T × 3600 × W × H = 24 × 3600 × 1000 × 1 KB ≈ 86.4 GB — this is why ADR-09's 4 GiB cap exists: uncapped, a single bad day exceeds most nodes' disk budget by 20×.
  4. Gossip fingerprint bandwidth per peer pair per cycle at 256 ranges, 48 B/fingerprint (§11.3), 1 Hz (ADR-06): 256 × 48 B/s ≈ 12.3 KB/s — negligible against the 25 MB/s intra-DC cap (§4), confirming fingerprint exchange is "nearly free" as claimed in §3.
  5. Merkle subtree-comparison bandwidth for d = 100 divergent leaves at depth 16 (log2(65536) = 16, using M2's formula, §13.4): 2 × 100 × 16 × 40 B = 128,000 B ≈ 125 KB per reconciliation round — chained directly from the System Constraints' bandwidth-amplification-per-divergent-key assumption (§4).
  6. IBLT exchange bandwidth at d_expected = 1000, c = 1.5 (ADR-14): cell_count = 1500, 24 B/cell (8 B id_xor + 8 B hash_xor + 4 B count, rounded for wire alignment): 1500 × 24 B = 36,000 B ≈ 36 KB — versus #5's ~125 KB Merkle cost at a comparable divergence count, quantifying P10's CPU-for-bandwidth trade.
  7. Gossip rounds to full dissemination at cluster size N = 1000 (Karp-Schenker- Shenker, §5): O(log2 N) ≈ log2(1000) ≈ 10 rounds; at the 1 Hz cycle (ADR-06) that is ≈ 10 s to disseminate a rumor cluster-wide — the exact derivation ADR-06's rationale cites.
  8. FD budget for hint-queue column families at cluster size 1000 (one CF per distinct target, §11.10), assuming RocksDB opens ≈ 10 files per moderately-sized CF: 1000 × 10 = 10,000 FDs — comfortably under a raised Linux ulimit -n of 65,536 but the number an operator must explicitly raise the default (1024) to accommodate (§4's FD-budget row).
  9. Read-repair background-work overhead at the ADR-11 default 10% async sampling rate, read QPS = 100,000/s: 0.10 × 100,000 = 10,000 background resolver+write-back invocations/sec — the number that sizes the async-repair queue's required drain rate relative to its 10K-pending capacity (§4), showing the default queue size is sized to exactly one second of buffering at this reference load, not an arbitrary constant.
  10. Cross-DC convergence bound for a 1 M-key range, 1% divergence (d = 10,000), 100 ms RTT, 1 MB/s cap (§20): dominant cost is the leaf-payload transfer for 10,000 divergent keys at an assumed ~200 B average entry size: 10,000 × 200 B = 2 MB; at 1 MB/s that is 2 s of pure transfer, leaving the remainder of the M10 5-minute budget (§29) as headroom for RTT-bound round-trip overhead across the batched-leaf descent (§20.2).

35. Alternative Architectures (Roads Not Taken)

35.1 Pure-CRDT convergence (no Merkle/IBLT at all)

Show the original text diagram
Replica A ──merge(CRDT)──► Replica B ──merge(CRDT)──► Replica C
     ▲                                                     │
     └─────────────────── gossip full CRDT state ──────────┘

Regime where it wins: applications whose entire data model is CRDT-expressible (counters, sets, sequences) and where full-state gossip bandwidth is cheap relative to divergence rate. Real embodying system: Riak with allow_mult effectively always true, or a pure Automerge-backed document store. Rejected because: forces every application data model into a CRDT shape; most production KV workloads (arbitrary blobs) do not fit, which is exactly why this design makes CRDTs opt-in (P9) rather than foundational.

35.2 Consensus-based replication (no anti-entropy needed)

Show the original text diagram
Client ──► Raft Leader ──replicate(log)──► Follower, Follower
                (linearizable; no divergence possible by construction)

Regime where it wins: strict-consistency requirements, moderate write throughput, and a willingness to pay coordination latency and reduced partition-availability. Real embodying system: CockroachDB, etcd (both Raft-based). Rejected because: it sacrifices the availability-under-partition property that eventual consistency exists to provide (P1's entire premise); this is explicitly Projects #91/#92's surface, not this one's.

35.3 Differential-dataflow streaming convergence (no polled gossip)

Show the original text diagram
Change stream ──► [incremental dataflow operator: continuously-updated diff] ──► Repair
   (continuous, event-driven — no fixed-cycle poll)

Regime where it wins: very large N where gossip-cycle polling overhead itself becomes the dominant cost (§30's bottleneck 1) rather than the actual divergence-detection work. Real embodying system: Naiad / Differential Dataflow, and Materialize's incremental view-maintenance engine built on the same model. Rejected because: significant operational-complexity increase and immature fit for a per-node embedded library at this project's current scale target; deferred as ADR-21 rather than abandoned — it is the named lever beyond the polled-gossip ceiling (§30).

35.4 Chain replication (no quorum, no divergence by construction)

Show the original text diagram
Write ──► Head ──► Mid ──► Tail ──► Ack           Read ──► Tail
   (strict order; a chain failure blocks writes until reconfigured)

Regime where it wins: workloads that tolerate primary-side write serialization and want zero read-repair complexity by eliminating divergence structurally. Real embodying system: van Renesse & Schneider's original Chain Replication design, used in systems like FAWN-KV. Rejected because: a mid-chain node failure blocks writes until the chain reconfigures, trading the availability-under-partition guarantee this project prioritizes (P1) for strict ordering — the opposite trade from this project's mission.

37. Glossary

  • Active anti-entropy — the gossip-scheduled, Merkle-driven background reconciliation mechanism that repairs ranges nobody is reading or hinting about (§14).
  • Anti-entropy — the general class of protocols that detect and repair replica divergence, as opposed to preventing it (Demers et al. 1987).
  • Asynchronous (probabilistic) read repair — repair triggered on a sampled fraction of reads, fired-and-forgotten to a background task (§17).
  • Backpressure — the deliberate rejection or dropping of new work, with telemetry, once a bounded queue is full, rather than letting the queue grow unboundedly (§15, §17).
  • Bounded staleness — a quantified upper bound on how out-of-date a read may be, expressible as P(staleness > t) (Bailis et al. 2012 PBS, §33).
  • CAI contract — commutative, associative, idempotent: the algebraic property every Resolver implementation must satisfy for convergence to be provable (I6, §11.7).
  • Cell — a fixed-size slot in an IBLT holding XOR-accumulated element IDs and a check hash plus a signed count (§11.9).
  • Check hash — a BLAKE3-keyed hash stored per IBLT cell, used to verify a cell is "pure" during peel-back decoding without a false positive (§19.2).
  • Column family (CF) — a RocksDB namespace-within-a-database; used one-per-target- replica in the hint queue for efficient bounded eviction and replay (§11.10).
  • Conflict resolution — the process of reducing multiple divergent VersionedValues for one key down to a single resolved outcome (§18).
  • Conformance suite — the deterministic property-test/fixture runner that gates every merge and release (§27.1).
  • Consistency level — the (N, W, R) quorum configuration a read or write is executed under (§16.2).
  • Divergent leaf — a Merkle-tree leaf whose hash differs between two replicas being compared, localizing the set of keys that actually need reconciliation (§13.2).
  • Dotted Version Vector (DVV) — a vector-clock variant that disambiguates anonymous concurrent updates from replayed ones via per-replica dots (Preguiça et al. 2010, §18.2).
  • Domain separation — using distinct hash-function prefixes for structurally different purposes (e.g., leaf vs. internal-node hashing) to prevent cross-context collisions (§13.6).
  • Eventual consistency — a consistency model guaranteeing that, absent new writes, all replicas converge to the same state in bounded time (Vogels 2009).
  • Fingerprint — a compact summary (Merkle root + metadata) exchanged in place of full range payloads (§11.3).
  • Fingerprint-first, payload-second — this system's core bandwidth strategy: exchange cheap summaries aggressively, ship expensive payloads only once divergence is localized (§3).
  • Generation — a monotonically increasing counter on a RangeFingerprint guarding against comparing fingerprints across incompatible range/topology states (§11.3, §8.4).
  • Gossip — a peer-to-peer, decentralized information-dissemination protocol with logarithmic convergence time in cluster size (Demers et al. 1987, Karp et al. 2000).
  • Hinted handoff — buffering a write intended for a temporarily-unreachable replica at the coordinator, for later replay ("sloppy quorum," Dynamo sec. 4.6, §15).
  • Hint — a single buffered (target, key, versioned_value) write awaiting replay (§11.5).
  • Hybrid Logical Clock (HLC) — a clock combining a physical-time component with a logical counter, giving a total order that respects causality when observable (Kulkarni et al. 2014, §18.1).
  • Idempotent write-back — a repair write that is a safe no-op if the target already holds an equal-or-newer value, enforced via HLC comparison at the storage layer (§16.2).
  • Invertible Bloom Lookup Table (IBLT) — a probabilistic data structure supporting exact recovery of a bounded symmetric set difference via peel-back decoding (Eppstein et al. 2011, §19).
  • Last-Writer-Wins (LWW) — a conflict-resolution policy that always picks the value with the highest timestamp (§18.1).
  • Load amplification (repair-induced) — a failure mode where repair traffic itself worsens the condition (e.g., a partial outage) it was meant to fix (P13, §24 FM-5).
  • Merkle tree — a hash tree enabling O(log N)-depth equality verification of a data set via recursive hash comparison (Merkle 1987, §13).
  • Peel-back decoding — the IBLT decode algorithm that iteratively removes "pure" cells until the structure is empty or exhausted (§19.2).
  • Policy registry — the gossip-distributed, per-keyspace configuration store for resolver choice, d_expected, and cap/TTL overrides (§21.1).
  • Quorum — the minimum number of replicas (W for writes, R for reads) that must respond for an operation to be considered successful, out of N total (§16.2).
  • RangeId — a stable identifier for a (range, replica-set) pair that survives membership/topology changes even as the underlying key boundaries shift (§11.1).
  • Read repair — request-time detection and correction of replica divergence on the keys a client is actually reading (§16, §17).
  • Resolver — the pluggable trait implementing conflict resolution; implementors include LWW, Siblings, CRDT, and application-defined hooks (§11.7).
  • Sloppy quorum — accepting a write as successful once W replicas (not necessarily the "natural" N owners) acknowledge it, buffering the rest as hints (Dynamo sec. 4.6, §15.1).
  • Sibling — one of several mutually-concurrent VersionedValues returned to the caller when the resolver cannot or should not pick a single winner (§18.2).
  • Symmetric difference — the set of elements present in exactly one of two sets being reconciled (A △ B), the quantity IBLT and Merkle diff both aim to recover (§19).
  • Synchronous read repair — read-time repair whose write-back either blocks the client response (rejected default) or completes in the background before or after the resolved value is returned (adopted default, §16).
  • Token bucket — a rate-limiting structure that caps repair bandwidth per (peer, range) pair, replenished at a fixed rate (§14.2, I10).
  • Tombstone — a VersionedValue marking a deletion, retained and garbage-collected on a TTL rather than removed immediately, so deletes participate correctly in convergence (§11.2, §13.6).
  • VersionedValue — the canonical (value, timestamp, tombstone-flag) triple every stored entry carries (§11.2).
  • Write-back — the repair-driven write that applies a resolved value to a replica found to be missing or behind it (§16.2).
