Project Number: 124

Project Name: HTML/CSS Layout Engine

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a standalone, embeddable HTML/CSS layout engine — the layout half of a browser rendering engine — that turns an HTML byte stream plus a set of CSS stylesheets into a positioned, paintable box tree at a target viewport, and keeps that box tree correct under incremental DOM and style mutation. The engine owns everything between "bytes arrive" and "a display list is ready for a rasteriser": HTML5 parsing, DOM construction, CSSOM construction, selector matching, the cascade (origin/importance/layer/specificity/source-order), computed-style resolution, box generation (the box tree, distinct from the DOM), the block and inline formatting contexts, flexbox, grid, tables, multi-column, absolute/fixed/sticky positioning, paint (stacking contexts, paint order, display-list emission), hit testing, and dirty-bit-driven incremental relayout. It does not own script execution, networking, or rasterisation.

Phase-0 deliverable (in-scope modules, crates/):

  1. kosmos — public facade crate and embedder API (C ABI optional).
  2. kosmos-url — WHATWG URL parser.
  3. kosmos-html — HTML5 tokenizer + tree-construction state machines.
  4. kosmos-dom — DOM node graph, Range, MutationObserver.
  5. kosmos-css-syntax — css-syntax-3 tokenizer and grammar-level parser.
  6. kosmos-selectors — selectors-4 parser and bloom-filter-accelerated matcher.
  7. kosmos-values — values-and-units-4 per-property parsers.
  8. kosmos-style — stylist, rule tree, cascade, computed values, invalidation.
  9. kosmos-box — box-tree generation, anonymous boxes, pseudo-elements.
  10. kosmos-layout — BFC, IFC, flex, grid, table, multi-column, positioned layout.
  11. kosmos-paint — stacking-context tree, paint order, display-list emission.
  12. kosmos-text — line-breaking, bidi, shaping glue (HarfBuzz, ICU4X).

System boundaries. Provides: parsing → style → layout → paint (display list) → hit-testing. Delegates: script execution (project rank 126, consumed via kosmos-bindings), networking (the embedder's BlobFetcher), rasterisation (the embedder's GPU/CPU backend; a softbuffer demo backend ships for smoke tests only), font-file I/O (the embedder's FontProvider). Does NOT provide: a JavaScript engine, a network stack, GPU rasterisation, accessibility-tree emission (PhaseDeferred("§37")), print pagination beyond multi-column (PhaseDeferred("§37")).

Non-goals. Full quirks-mode HTML4 fidelity; XML/XHTML strict-mode parsing; MathML and SVG layout (PhaseDeferred("§37")); a general-purpose GPU compositor.

Deployment model. A dylib/rlib embedded inside a host process (desktop app, kiosk shell, in-game UI, documentation reader, headless screenshot service). One Engine value per host surface; multiple engines coexist in one process (P9).

Target users/operators. Application engineers embedding a layout surface without a full browser; the operator is whoever ships the host binary and owns its crash/perf telemetry.

What later phases unlock. Phase 4 unlocks correct cascade/inheritance; Phase 5–8 unlock the full box-and-layout surface (BFC/IFC/flex/grid/tables); Phase 9–10 unlock paint, hit-testing, and sub-millisecond incremental reflow; Phase 11 unlocks WPT-gated conformance and hardening.

Language: Rust (2024 edition, 2021 floor). Rationale: memory safety on a billion-allocation-per-session surface with zero garbage collector pause budget (§4); the borrow checker eliminates aliasing bugs in the rule tree's Arc-based interning and use-after-free in layout-cursor passes — the exact bug class that has consumed engineer-years in Blink/WebKit's C++ layout code (ADR-01). Rejected: C++ (the incumbent choice in every shipping browser; rejected because the memory-safety bug class it invites is precisely what this project exists to avoid), Go (GC pauses violate the 16 ms frame budget, §4), Swift (no production-grade cross-platform layout precedent; ARC overhead on the box-tree's fine-grained node graph is unproven at this scale).

Prerequisites. Working knowledge of: finite state machines, arena/generational-index memory management, the CSS cascade model, Unicode text segmentation (UAX #9/#14/#29), and at least one production compiler or interpreter's incremental-recomputation strategy.

Estimated timeline. Phase 0: 1 week (repo skeleton + correctness kernel: parse → cascade → display:block/inline layout → softbuffer paint of <body><p>hi</p>). Full system (Phase 0–11): 7–8 months at one senior engineer full-time, per the per-phase weeks in §12–§23.

Every deferred feature is flagged PhaseDeferred("§N.s") inline and re-listed, anchor-resolved, in the Deferred Features Register (§37).

2. Why Build This

A layout engine is the canonical example of a specification hostile to a clean implementation. Float clearance interacts with line boxes; line boxes interact with the strut and half-leading rules of font metrics; the strut interacts with the writing-mode axis; the writing-mode axis flips block-flow direction and changes what min-height means; min-height triggers a re-layout that may discover a new orthogonal-flow container, which changes the available size of every nested flex item upstream. None of this is obvious from the specifications; all of it is load-bearing for the web as it exists; production engines carry a million-plus lines of layout code that no one person understands end to end (Grosskurth & Godfrey's browser architecture survey documents this exact accretion pattern across Mozilla and WebKit).

It teaches, uniquely: (1) the DOM/box-tree split and why conflating them is the single most common homegrown-engine bug (P1); (2) the two-pass intrinsic-then-layout sizing model that every constraint-based UI toolkit (Flutter, Yoga, egui) borrows from CSS; (3) incremental recomputation under a dirty-bit lattice — the same shape as a build system's dependency graph or a reactive-UI diffing engine; (4) text layout's Unicode substrate (bidi, line-breaking, shaping) which recurs in every text-rendering system, terminal emulator, and typesetting engine. Architecturally it sits beside: a database query planner (the cascade is a total-order tie-break resolver, structurally identical to a plan-ranking comparator), a build system (invalidation sets mirror dependency-graph dirtying), and a game engine's scene graph (the box tree's formatting contexts are sub-routines dispatched by tag, exactly like a game engine's component-system dispatch, ADR-03). Calibration value: an engineer who ships Phase 6 (BFC+IFC) can read Blink's LayoutNG or Servo's layout_2020 source cold and know exactly what problem each file solves.

Teams that reach for an embedded WebView (Electron, CEF, Tauri) for a fixed layout surface routinely discover a 300 MB resident-set cost per surface during a perf audit, when their actual surface needed ~10% of what Blink ships (§4, §34). This project is the smallest engine that still carries the full surface a real browser carries, sized to actually finish (§1 timeline) and to run inside a 20 MB binary.

What Mastery Looks Like (5–8 competencies, each tied to the phase that builds it):

  • Transcribe a W3C algorithm (flex resolution, track sizing) into working code without "simplifying" it — Phase 6 (§18), Phase 7 (§19).
  • Explain why the box tree cannot be the DOM tree, with a concrete anonymous-box counter-example — Phase 4 (§16).
  • Diagnose a missed style invalidation from a bug report alone, using the rule-hash/invalidation trace — Phase 3 (§15), Phase 10 (§22).
  • Reason about margin collapsing, BFC boundaries, and stacking-context formation from first principles, not memorized tables — Phase 5 (§17).
  • Read a WPT reftest failure and localize it to tokenizer, cascade, or layout — Phase 11 (§23).
  • Derive a performance budget (§4, §34) from first principles rather than copy a number.

Embedder API. The only surface a host process touches; a value type, not a singleton (P9). Document & DOM. Owns node identity and mutation semantics; the arena is per-document so multiple documents never share liveness. Stylesheet pipeline. Speaks only the specified-value vocabulary; never touches layout types. Script bridge. A parallel consumer of DOM/CSSOM, not a layer the layout pipeline depends on — this engine ships with no JS engine (ADR-21) and the bridge is a pure export surface. Style resolution. The single largest CPU consumer on steady-state pages (§4); the rule tree and invalidation set are its two load-bearing structures (ADR-08, I4). Box generation. The DOM/box-tree split (P1, ADR-02) is enforced here and nowhere downstream ever walks the DOM again. Layout engines. Each formatting context is a sub-routine keyed by an enum tag (P2, ADR-03), not a subclass. Paint & hit-test. Consumes only the box tree's computed geometry; emits a flat DisplayList (P10) that a hit-test walk traverses back-to-front (P11). Rasterise. Genuinely out of scope; the softbuffer backend exists only to make Phase-0's smoke test observable end to end.

6. Design Principles

P1 — The box tree is the layout artefact; the DOM is the input. No layout algorithm ever walks the DOM. Tradeoff: a second tree to keep in sync. Operational implication: box-tree regeneration is itself an invalidation class (I1). Violate it and anonymous-box logic leaks into DOM code, the single most common homegrown-engine bug.

P2 — Formatting contexts are sub-routines, not subclasses. A LayoutBox carries a FormattingContext enum tag; layout dispatches by tag, never by virtual method on a class hierarchy. Tradeoff: static dispatch loses runtime polymorphism's easy extensibility. Violating it reproduces Blink's legacy LayoutObject maintenance burden (ADR-03).

P3 — Computed style is the boundary between style and layout. Cascade produces specified values; layout only ever reads computed values via ComputedStyle accessors. Tradeoff: an extra resolution pass per property. Violating it collapses the type-level guarantee that made Stylo's integration safe (Servo's own postmortem).

P4 — Style sharing is opt-in and predicate-verified. The 12-item sharing predicate (§15.6) gates every cache hit; a failure on any item disqualifies the share. Tradeoff: a false negative (missed sharing) is cheap; a false positive would be a correctness bug, so the predicate is conservative (I13).

P5 — The cascade order is normative and total. Origin×importance, layer, specificity, source order — a stable sort guarantees a deterministic winner for every property on every element. Violating stability breaks cross-run determinism (§28 conformance gate).

P6 — Invalidation is computed at insertion time, not at mutation time. The per-rule invalidation set is built once when a stylesheet lands; mutation hooks only consult it (I4, ADR-08). Tradeoff: O(rules) work up front for O(1) amortized mutation cost.

P7 — Layout is reentrancy-safe by construction. A LayoutPhase enum blocks any layout-flushing call from a non-Idle phase (I11). Tradeoff: scripts that assume synchronous flush-anywhere semantics (common on the legacy web) must be adapted at the binding layer.

P8 — Incremental invalidation is the default; full re-layout is a test-only escape hatch. Engine::force_full_layout() exists only behind a test-mode flag. Violating this — defaulting to full re-style — is a 30×+ slowdown on steady-state pages (measured by Servo's own stylo integration notes).

P9 — No global state. Engine is a value constructed via EngineConfig::build(); no static, no thread_local! registry. Tradeoff: the embedder must thread an Engine handle explicitly; the payoff is N independent engines per process with no shared-mutable-state bugs.

P10 — The painter targets a display list, not a canvas. kosmos-paint emits typed PaintCommands; rasterisation is a separate, swappable consumer. Tradeoff: an extra serialization step versus painting directly; the payoff is a Send + Sync list a GPU backend can consume in parallel.

P11 — Hit testing walks the display list, not the box tree. Appendix-E paint order is the only correct hit-test order; the box tree's shape does not encode it. Violating this — hit testing the box tree directly — silently mis-orders overlapping stacking contexts.

P12 — Fonts are owned by the embedder. FontProvider is a trait; the engine never touches a filesystem path. Tradeoff: every embedder must wire a font backend; the payoff is zero filesystem trust boundary inside the engine (§24 threat model).

P13 — Conformance is web-platform-tests, not invention. Every shipped layout algorithm lands with a WPT subset pinned in conformance/wpt/ (§10). "Green" is defined as a pass-rate commitment (§23.1), never an internally-invented test suite alone.

P14 — Errors at parse and cascade are non-fatal. A malformed rule is dropped and logged to the parse-error sink; the document keeps loading (matches the web platform's liberal-input stance, the one place this engine adopts it).

P15 — No surprises in API shape. Every public type is #[non_exhaustive]; every panic path is documented and exists only on a contract violation (reentrancy, missing config); errors are typed, never Box<dyn Error>.

8.6 Worked Example

Input: <div style="display:flex; justify-content:space-between"><span>A</span><span>B</span></div> at viewport 300×100 with UA stylesheet only.

  1. Parse → DOM: one div with two span children (§13).
  2. Cascade → computed: div.display=flex, justify-content=space-between; each span inherits display:inline collapsed to atomic-inline participation inside the flex item's own IFC.
  3. Box generation → LayoutBox{fc:Flex} with two LayoutBox{fc:Inline} children, each wrapping one atomic-inline text run (§16.1).
  4. Flex layout (§18.2): base size of each item = its IFC's max-content width (e.g. 8px, 8px); free space = 300 − 16 = 284px; justify-content:space-between places item 1 at x=0, item 2 at x=292.
  5. Paint (§21): two Glyph commands inside two PushStackingContext-free boxes (no stacking context is established; display:flex alone does not create one).

8.7 Malformed-Input Example

Input: <div style="width: 1e308em; display: flerx">text (unterminated tag, invalid display, overflowing length).

  • Tokenizer (§13.1): EOF-in-tag-name triggers the HTML5 "parse error, reconsume" rule; a synthetic end tag is inserted per §13.2.6's tree-construction error recovery.
  • Values parser (§14.5): 1e308em saturates to the typed value's safe maximum (P14); recorded as a ParseDiagnostic with byte span and the css-values-4 section it violates.
  • display: flerx is an unrecognized keyword; the whole declaration is dropped to the next semicolon (css-syntax-3 recovery, §14.2); display falls back to its initial value (inline).
  • Document continues to load and lay out; zero panics (§24 threat model, adversarial-property-values row).

8.8 Failure-Path Example

Scenario: a script calls Element.getBoundingClientRect() from inside a ResizeObserver callback that itself fires during an active Layout phase (a real Blink/WebKit pathology, §19.6/pitfalls carried from the original analysis).

  1. Binding entry point checks Engine.phase (I11); phase is Layout, not Idle.
  2. LayoutPhaseError::ReentrantFlush is raised, typed, to the script bridge (§22.3).
  3. tracing emits reentrancy.blocked with the call site and the current dirty-box id.
  4. The observer's mutation is queued to the next microtask checkpoint rather than dropped — no data loss, bounded latency (< 1 frame).
  5. Operator visibility: the runbook docs/runbook/layout-thrash.md (§10) names this exact trace signature as the first diagnostic step.

13. Phase 1 — URL, DOM & HTML5 Parser

13.1 Objectives

Land the plumbing every later phase depends on: the WHATWG URL parser, the DOM node graph (§8.1, §11), and the full HTML5 tokenizer + tree-construction state machines (P1: the DOM is the input, never the layout artefact).

13.2 Detailed Implementation Steps

kosmos-url: implement the WHATWG URL state machine — tokeniser → state machine → parsed URL (scheme, host, path, query, fragment, port) + canonical serialisation. kosmos-dom: arena-owned Node tagged union (§8.1, §11) in a per-document bumpalo arena (ADR-24); MutationObserver per the DOM Living Standard, batched per microtask (P6 precondition). kosmos-html: every tokenizer state in the HTML Living Standard's tokenizer state-machine table as a named per-state dispatch function (never literal control-flow code in this document, per the governing no-code rule); every insertion mode in the tree-construction state-machine table (initial → after-after-frameset, 21 modes); the adoption-agency algorithm transcribed verbatim (its cross-engine bug history is the reason WPT fixtures, not code review, are the safety net — §13.6); <template> content as a real DocumentFragment, not collapsed.

13.3 Deliverable

A parser that turns arbitrary (including malformed, §8.7) HTML bytes into a DOM tree matching the WHATWG reference parser's tree shape, plus a BlobFetcher/FontProvider trait pair with Phase-0 stub implementations (FileSystemBlobFetcher, DataUrlBlobFetcher, fontdue-backed FontProvider).

13.4 Acceptance Criteria

HTML tokenizer passes ≥ 99% of web-platform-tests/html/syntax/parsing/ tokenisation subset; tree construction passes ≥ 95% of the tree-construction subset (both gated in wpt.yml, I12). URL parser passes 100% of web-platform-tests/url/ (§4 constraint: zero tolerance on a well-specified small grammar). Font smoke test ("render the letter A") diffs zero against a reference glyph raster.

13.5 Conformance Fixtures

conformance/wpt/html/syntax/parsing/* — WPT tokenizer/tree-construction subset. conformance/ parser_corpus/adoption-agency.html — purpose: exercises the adoption-agency algorithm's historically buggiest path; expected: WHATWG reference tree. conformance/parser_corpus/ template-nested.html — purpose: <template> content-fragment nesting; expected: fragment subtree isolated from the main document tree.

13.6 Pitfalls

The adoption-agency algorithm (P1, §8) has an infamous cross-engine bug history — WPT fixtures are the only safety net, do not "clean up" the transcription. <script> execution gating is out of scope here (ADR-21); mark <script> nodes "needs execution" for the Phase-10 bridge and do not block parsing on it. The WHATWG URL parser is not RFC 3986 — mixing the two grammars is the single most common URL-parser bug; WPT catches it (ADR-13).

13.7 Performance Concerns

Tokenizer throughput target 50 MB/s single-core (M1, §30) — achieved via a table-driven state machine, not a regex cascade. Arena allocation (ADR-24) amortizes per-node allocation cost; do not allocate per-attribute Strings — intern via InternedStr (§11).

13.8 Edge Cases

EOF mid-tag-name (reconsume rule, §8.7 malformed-input example). Deeply nested formatting elements overflowing the active-formatting-elements list (bounded per spec, not unbounded growth). Non-UTF-8 byte streams (encoding-sniffing fallback, P14). A <template> inside <select> (a real cross-browser divergence historically; WPT fixture pinned).

13.9 Failure Analysis

A tokenizer state-transition bug manifests as a diverging tree shape versus the WHATWG reference — detected by WPT diff (I12), not by manual review. Blast radius is contained to the affected document only (P9: no global state to corrupt). Recovery: the parse-error sink (§11) surfaces every dropped/recovered token for postmortem.

13.10 Operational Notes

tracing span html.tokenize and html.tree_construct with per-document token counts. The parse-error sink is queryable via Engine::recent_parse_errors() (§11) for embedder-side diagnostics; bounded ring buffer, no unbounded growth (§24 threat model, adversarial-HTML row).

14.2 Detailed Implementation Steps

kosmos-css-syntax: tokenizer emits ident/function/at-keyword/hash/string/bad-string/url/ bad-url/delim/number/percentage/dimension/whitespace/cdo/cdc/:/;/,/[]/()/{ }/EOF per css-syntax-3 verbatim (ADR-04); parser turns the token stream into declaration/rule/at-rule lists with the recovery rule "drop to next semicolon or block boundary" (P14). At-rules in scope: @media @supports @import @namespace @charset @font-face @keyframes @layer @scope @page @property; @container deferred (PhaseDeferred("§37")). kosmos-selectors: full selectors-4 grammar (type/universal/attribute/class/id/pseudo-class/pseudo-element/combinator incl. :is() :where() :not() :has() :nth-child() :nth-of-type() :lang() :dir()); specificity computed at parse time, capped at [u16;3] per §16 (I-lattice saturation, ADR-05). kosmos-values: per-property parsers generated from properties.toml (name, initial, inherited, computed-value form, animation type, syntax grammar); generic parsers for <length> <percentage> <length-percentage> <angle> <time> <frequency> <resolution> <integer> <number> <string> <custom-ident> <color> <image> <position> <url> <gradient> <calc()> <min()> <max()> <clamp()>.

14.3 Deliverable

A Stylesheet value (§8.2) for any input CSS byte stream, with every dropped/malformed construct recorded as a ParseDiagnostic (§11, P14) and zero panics on adversarial input (§24).

14.4 Acceptance Criteria

css-syntax-3 tokenizer+parser pass ≥ 99% of conformance/wpt/css/css-syntax (I12). Selectors-4 parser passes ≥ 95% of conformance/wpt/css/selectors parsing fixtures. Values parsers pass ≥ 90% of the WPT values fixtures. Every Phase-2 property has a properties.toml entry, a parser, and a named fixture (H9-style named-fixture requirement carried into every N.4 in this document).

14.5 Conformance Fixtures

conformance/wpt/css/css-syntax/* — tokenizer/parser subset. conformance/wpt/selectors/ parsing/* — selector grammar subset. conformance/parser_corpus/import-ordering.css — purpose: @import applies at source position, not fetch-resolution order (css-cascade-5); expected: cascade order matches source order regardless of fetch latency. conformance/parser_corpus/ has-backwards.css — purpose: :has() backwards-walking matcher; expected: matches per the selectors-4 grammar. conformance/parser_corpus/specificity-overflow.css — purpose: 300-argument :is() list; expected: specificity saturates at 65,535 per component, no overflow panic.

14.6 Pitfalls

@import ordering: cascade-5 applies import rules at their parsed position, not the position their fetch resolves — a fetcher returning futures out of order must not reorder the cascade (P6 precondition). :has() breaks the bloom-filter fast path (ADR-05) — mark :has() rules "slow" and route through the ancestor-invalidation path (§15.7), not the standard descendant path.

14.7 Performance Concerns

Selector-parsing depth is capped (default 1024, §24 adversarial-selectors row) to bound worst-case stack depth. The values parser uses saturating arithmetic (P14) so a 1e308em never triggers UB or a panic (§8.7 malformed-input example).

14.8 Edge Cases

:not(a, b, c) specificity is the maximum of any argument, not the sum (css-selectors-4 is normative — a common implementer mistake). Custom properties (--*) tokenize to a raw token stream and defer resolution to Phase 3's computed-value pass (§8.3). Unicode-range tokens inside @font-face follow the "starts a unicode-range" predicate transcribed verbatim.

14.9 Failure Analysis

A malformed @media condition that the parser cannot recognize drops the whole rule (P14); the telemetry counter css.rule_dropped increments and the affected selector never enters the stylist's buckets — detectable via conformance.report.json's parse-error summary.

14.10 Operational Notes

tracing span css.tokenize / css.parse / selectors.parse. Parse-error sink entries carry the exact drafts.csswg.org section violated (§11 ParseDiagnostic.spec_ref), enabling a one-hop link from a bug report to the normative text.

15. Phase 3 — Style Resolution: Stylist, Cascade, Invalidation

15.1 Objectives

Implement the four load-bearing style-pipeline structures in build order — stylist, rule tree, cascade, invalidation set — matching Servo's stylo reference shape (§8.3, P3–P6, ADR-07/08). This phase dominates steady-state CPU cost by roughly 3× over layout (§4) and is the single largest phase in the plan.

15.2 Detailed Implementation Steps

Stylist (P5, ADR-05): bucket rules by rightmost compound selector (id, class, local-name, attribute-presence, namespace, catch-all); id bucket consulted first (at-most-one-match property). Maintain a 4-hash-function, 4096-bit ancestor bloom filter per descending matcher (< 0.5% false-positive on a 10k-rule sheet, Häkkinen 2008). Author/user/UA rules in three sharded stylist instances. Rule tree (I5): interned (parent, rule) node table; walking it yields cascade-ordered matching rules; doubles as the style-sharing key. Cascade (P5): stable sort over (origin×importance, layer order, specificity, source position); per-property table lookup resolves the winning declaration or falls back to initial/inherited. Computed values (P3, I2/I3): per-property specified → computed transform table (computed_table.toml); calc() reduces fully when resolvable, else defers to used-value time; var() cycle detection via depth-first walk, visited set, depth bound 32 (ADR-08 precondition: invalidation sets must be correct before this pass runs safely). Sharing (P4, I13, §8.3): 12-item predicate (§15.6 below) gates every cache hit. Invalidation (P6, ADR-08, I4): computed at stylesheet-insertion time — per-rule feature dependency set (attribute/class/id/state); mutation hooks consult it via hash lookup, never a full-tree walk.

15.3 Deliverable

A Stylist+RuleTree+cascade pipeline producing ComputedStyle values that match Servo's style crate output bit-for-bit on a shared 10k-rule corpus, with an invalidation-set implementation that dirties only the affected subtree on mutation.

15.4 Acceptance Criteria

Cascade output matches the Servo reference corpus bit-for-bit (0 diffs) on 500 canonical (html, stylesheet) pairs. Style sharing reduces resolved-style count ≥ 90% on a 1,000-row table fixture (M2 precondition, §30). Invalidation traces match the Servo reference dirty-set to ≥ 99% overlap on conformance/invalidation_traces/* (I4). Style-resolve throughput ≥ 1,000,000 elements/sec on a 1k-rule sheet (§4 row, M2).

15.5 Conformance Fixtures

conformance/ref_tests/cascade-determinism.json — purpose: (html, stylesheet, expected-per- element-computed-style) triples generated by Servo stylo; expected: 0-diff match. conformance/ invalidation_traces/*.json — purpose: (mutation, expected-dirty-set) pairs; expected: ≥ 99% overlap. conformance/wpt/selectors/* — selector-matching semantic subset (distinct from §14's parsing subset).

15.6 Pitfalls

The 12-item style-sharing predicate — same parent, shadow root, id, class (canonicalised), lang, dir, stylist-dependent attributes, state pseudo-class bits, style attribute, :nth- child/:nth-of-type index (Phase-0 disables sharing when these appear in any bucket), no active animation/transition, same parent computed display — a failure on any one item disqualifies the share (P4); this predicate is adopted verbatim from Servo because it is the only published predicate validated against a multi-engine determinism corpus. !important reversal follows cascade-4/5 (UA-important > user-important > author-important > author-normal > user-normal > UA-normal), not the cascade-2 misreading. unset resolves to inherit for inherited properties and initial otherwise — do not collapse the two keywords. revert-layer rolls back to the previous layer's value, not to initial (cascade-5 is normative).

15.7 Performance Concerns

:has() invalidation walks upward (ancestor-invalidation set, distinct from the standard descendant path, §14.6) — measurably slower; the runbook docs/runbook/slow-style-resolve.md documents the perf signature. Custom-property cascade participates in the same ordering tuple but resolution defers to computed-value time — do not fold it into the standard per-property fast path (a common perf regression source).

15.8 Edge Cases

Specificity overflow on a 300-argument :is() list saturates at 65,535 per component (§14.8). Animation- and transition-origin styles cascade after all six standard origins — do not fold them into author-important. Custom-property cycles (var(--a) chaining back to --a) are detected and fall back to the initial value, never an infinite loop (depth bound 32).

15.9 Failure Analysis

A missed invalidation manifests as a stale visual artifact with no crash — the hardest class of bug to attribute. Detection: property-test the invalidation engine against a full-re-style oracle in CI (I4); any divergence fails the build. Forensic artifact: the invalidation-trace corpus (§15.5) plus tracing span stylist.invalidate with the triggering mutation's feature diff.

15.10 Operational Notes

tracing spans stylist.match, stylist.cascade, stylist.invalidate, sharing.hit/ sharing.miss counters. No schema migration concerns (style state is not persisted, ADR-22); a stylesheet hot-reload (runtime <style> insertion/removal) is a first-class, tested path (§15.2).

16. Phase 4 — Box Generation

16.1 Objectives

Generate the box tree (§8.4, P1, ADR-02) from the DOM plus computed styles — the artefact every downstream layout phase consumes. No layout algorithm in this phase; box generation only.

16.2 Detailed Implementation Steps

Walk the DOM; for each element consult ComputedStyle::display() (P3) to pick its principal box: none → no box; contents → no box, children re-parent to the nearest ancestor box (P1); block/inline-block/inline/flex/grid/table/list-item/flow-root → a principal LayoutBox tagged with the matching FormattingContext (§11). Replaced elements (<img> <video> <canvas> <iframe> <object> <embed> <svg> <input> <select> <textarea>) get a Replaced box carrying intrinsic dimensions. Anonymous-box rules (CSS 2.1's anonymous-block-box rule): an inline sibling of a block gets wrapped in an anonymous block; a table-cell outside a table-row synthesizes anonymous row/table boxes; a list-item synthesizes an anonymous ::marker box. Pseudo-elements: ::before/::after generate content boxes from the content property; ::first-line/::first-letter record pseudo-styles on the parent box for the IFC (Phase 5) to consult; ::placeholder/::selection/ ::backdrop are rendering-only. run-in implemented per spec (CR-but-not-fully-shipped, flagged in the conformance report). Positioned boxes (absolute/fixed) and floats generate principal boxes whose layout participation is deferred to Phase 8/5 respectively; order (flex/grid) affects layout order only, never box-tree order.

16.3 Deliverable

A box-tree generator producing a LayoutBox forest (§11) from any (DOM, ComputedStyle) pair, matching a checked-in corpus of DOM+style → box-tree snapshots.

16.4 Acceptance Criteria

Anonymous-box generation passes the WPT anonymous-table-boxes subset (≥ 95%). ::before/ ::after generation passes the WPT content-property subset (≥ 95%). Box-tree snapshot corpus (50 fixtures) diffs zero against checked-in expected trees.

16.5 Conformance Fixtures

conformance/wpt/css/css-tables/anonymous-boxes/*. conformance/wpt/css/css-content/*. conformance/parser_corpus/box-tree-snapshots/*.json — purpose: DOM+style → box-tree fixture pairs; expected: exact tree-shape match including anonymous boxes.

16.6 Pitfalls

display: contents combined with ::before/::after is a corner case the spec only recently clarified — cite the exact spec section in code comments (per P15's no-surprises rule). The first-letter pseudo-element selects across nested inlines; implement to spec, not to intuition.

16.7 Performance Concerns

Box generation runs once per style-invalidated subtree, not once per document (P6/P8) — a needs_box_regenerate dirty bit (I6, §11) scopes the walk. Anonymous-box synthesis allocates from the per-document arena (ADR-24), never the global allocator.

16.8 Edge Cases

Nested display: contents collapsing multiple levels. A run-in box adjacent to a block versus adjacent to another inline (two different synthesis paths per spec). A replaced element with no intrinsic dimensions and no aspect-ratio (falls back to the CSS2.1 default replaced-element size, 300×150).

16.9 Failure Analysis

A box-generation bug manifests as a missing or duplicated anonymous box, caught by the snapshot corpus (§16.5) diffing to non-zero. Blast radius is scoped to the dirty subtree (I6); a full-tree regression only occurs if the needs_box_regenerate bit itself is mis-set (a P6 invalidation bug, not a box-generation bug — cross-reference §15.9).

16.10 Operational Notes

tracing span box.generate with per-subtree box counts. The box tree is inspectable via a debug dump (Engine::debug_box_tree(doc), test-only) for runbook use during triage.

17. Phase 5 — Block & Inline Formatting Contexts

17.1 Objectives

Implement the two oldest, most load-bearing formatting contexts (§8.5): the block formatting context (BFC, per CSS 2.1's block-layout model) and the inline formatting context (IFC, per CSS 2.1's inline-layout model plus css-text-3 and css-writing-modes-4), including margin collapsing, floats, line-breaking, bidi, and shaping.

17.2 Detailed Implementation Steps

BFC: rooted at any BFC-establishing condition (flow-root, floats, abspos containing block, overflow≠visible, table-cell, inline-block, table caption, flex/grid item, multicol); top-to-bottom stacking per writing-modes-4 block axis; margin collapsing per CSS 2.1's collapsing rule (I7) — adjacent in-flow vertical margins collapse to max(both≥0), sum(mixed sign), or −max(|both|<0); float positioning per CSS 2.1's float algorithm (outer edge at line edge if it fits, else cursor advances) with the exclusion shape consumed by subsequent layout; clearance per CSS 2.1's clearance rule grows the cleared element's margin until satisfied. IFC: line boxes accumulate inline boxes/atomic inlines/text runs left-to-right (or RTL) until full or forced-break; strut + half-leading per CSS 2.1's inline-box model; vertical-align (baseline sub super top bottom text-top text-bottom middle <length> <percentage>) anchors to a named reference baseline per CSS 2.1's vertical-align algorithm; white-space collapsing per css-text-3's white-space processing rules; line-breaking via ICU4X's UAX #14 (ADR-12) — soft breaks at word boundaries, forced breaks at <br>/white-space:pre newlines; bidi reorder via UAX #9 (I8, ADR-12) — classify Bidi_Class, compute paragraph embedding level, resolve isolating runs, apply X/W/N/I-rules, reverse same-level runs; shaping via HarfBuzz (ADR-11) on the bidi-reordered, cluster-respecting run; justification per css-text-3's justification algorithm. Atomic inlines (inline-block/inline-table/replaced) are single rectangles with an intrinsic baseline to the IFC. ::first-line/::first-letter re-shape/carve the first line/letter fragment (§16.2 pseudo-styles consulted here).

17.3 Deliverable

A BFC+IFC layout pass producing correct Fragment geometry (§11) for any block/inline subtree, including margin collapsing, floats, bidi paragraphs, and shaped text runs.

17.4 Acceptance Criteria

BFC passes the WPT CSS 2.1 block-layout subset (≥ 95%, §23.1). IFC passes WPT css-text-3 + css-writing-modes-4 subsets (≥ 90%). Reference-image diff against Firefox on 50 hand-curated typographic pages < 1% pixel-diff (ADR-19). Block-layout throughput ≥ 100,000 boxes/sec (M4, §4).

17.5 Conformance Fixtures

conformance/wpt/css/css21/block-layout/*. conformance/wpt/css/css-text/*, conformance/wpt/css/css-writing-modes/*. conformance/ref_tests/margin-collapsing/* — 50 fixtures dedicated to §17.2's collapsing rules (the single largest cross-browser divergence source on legacy pages). conformance/ref_tests/bidi-ucd/* — Unicode UCD bidi-test fixtures run through the shaper+line-breaker+reorderer (I8).

17.6 Pitfalls

Margin collapsing has corner cases the spec wording alone does not make obvious (an empty block's adjacent top/bottom margins collapsing together, then re-collapsing with the surrounding margins if non-zero) — WPT fixtures are the only safety net. vertical-align: baseline on an empty inline picks up the strut, not content — a near-universal first surprise. The bidi algorithm runs on paragraphs, not lines — applying it per-line is a common, wrong shortcut. Line-break opportunities are between characters, not glyphs — UAX #14 runs before shaping, not after. text-indent applies to the first line only (CSS 2.1 is normative).

17.7 Performance Concerns

The IFC's line cache survives across re-layouts when the paragraph's content is unchanged (P8); invalidating it wholesale on every re-layout defeats the incrementality contract this project is built around (ADR-23). Shaping throughput target ≥ 10,000,000 chars/sec on the book-paragraph corpus (§4), achieved by delegating entirely to HarfBuzz's SIMD paths (§30.5) rather than a custom shaper.

17.8 Edge Cases

white-space: pre-line collapses spaces but preserves newlines (per-character algorithm, not per-line). A line-height: 0 strut produces a well-defined but visually degenerate line box. Hanging punctuation (CSS Text 4) is out of scope (PhaseDeferred("§37")). A float that does not fit any line advances the layout cursor per CSS 2.1's exact float-placement algorithm, not a heuristic.

17.9 Failure Analysis

A margin-collapsing bug manifests as visible extra/missing vertical whitespace, caught by the 50-fixture collapsing corpus (§17.5) or the reference-image diff (< 1% threshold, else CI fails). A bidi bug manifests as visually reordered text; caught by the UCD bidi-test corpus. Both classes are structural-correctness bugs, not crashes — the only detection path is corpus-based diffing, never manual QA (P13).

17.10 Operational Notes

tracing spans layout.bfc, layout.ifc, text.shape, text.bidi_reorder. The runbook docs/runbook/layout-thrash.md (§10) documents the BFC/IFC re-layout trace signature used in §8.8's failure-path example.

18. Phase 6 — Flexbox

18.1 Objectives

Implement CSS Flexible Box Layout Level 1's flex-layout algorithm (ADR-06 precondition: layers must already resolve display:flex correctly) exactly as specified — no "intuitive" shortcuts (a documented cross-engine implementer failure mode: treating the resolution algorithm as obvious from its name instead of transcribing its numbered steps, §18.6).

18.2 Detailed Implementation Steps

Nine-stage algorithm (I9 termination guarantee): (1) collect flex items in order-property order; (2) determine each item's flex-base size per the spec's base-size resolution rules (from flex-basis:content, <length>, the item's main-size property, or intrinsic main size); (3) clamp to hypothetical main size via min/max; (4) determine the container's main-axis available size; (5) collect items into flex lines (nowrap = one line; wrap = fill until hypothetical-main-size sum exceeds available size); (6) resolve flexible lengths per the spec's flex-resolution algorithm — free space, frozen items, flex factors, a loop that converges by freezing items at their min/max bound each iteration (I9: strictly monotonically decreasing unfrozen-item count guarantees termination); (7) determine cross-size via per-item layout (recursing into the item's own formatting context); (8) align on cross axis (align-items/align-self), justify on main axis (justify-content), resolve gap; (9) align lines via align-content. Replaced items with intrinsic aspect ratios (or the aspect-ratio property) contribute their intrinsic main size; the algorithm must call per-item layout to learn cross size given a hypothesised main size. Container intrinsic sizes: run the algorithm with infinite available main size (max-content) and per-item min-main-size (min-content).

18.3 Deliverable

A flex-layout pass producing correct main/cross-axis geometry for any display:flex/inline-flex subtree, terminating in bounded iterations (I9) on every input including adversarial ones (§24).

18.4 Acceptance Criteria

Flexbox passes ≥ 90% of conformance/wpt/css/css-flexbox (§23.1). Reference-image diff against Firefox on a Twitter-style timeline, a Material-design app shell, and a YouTube-style grid < 1% pixel-diff. Flex-layout throughput ≥ 100,000 boxes/sec (M5, §4/§30).

18.5 Conformance Fixtures

conformance/wpt/css/css-flexbox/*. conformance/ref_tests/flex-timeline.png, flex-app-shell.png, flex-grid.png — named reference-image fixtures (§18.4). conformance/ parser_corpus/flex-freeze-adversarial.html — purpose: an input engineered to stress the §18.2 stage-6 freeze loop; expected: bounded iteration count, no hang (I9).

18.6 Pitfalls

The flex-resolution loop must terminate — items freeze on hitting min/max bounds; implementing the freezing rule imprecisely spins the loop (I9 exists exactly to name this failure mode). align-content with a single line is a documented no-op per spec — do not "fix" it. min-width:auto on a flex item is not zero; it resolves to the item's content size on the main axis (a frequent implementer mistake per the flexbox spec's own non-normative notes).

18.7 Performance Concerns

Stage 6's convergence loop is the algorithm's only unbounded-looking step; I9's freeze-accounting turns it into a bounded, monotonically-terminating loop — instrument tracing counter flex.iterations (§7 I9 row) to catch any regression that reintroduces unbounded looping.

18.8 Edge Cases

flex-basis: content combined with an intrinsic-aspect-ratio replaced item (two resolution paths that must agree). A flex container with zero free space and all items at their minimum (no further shrinking possible — algorithm must not underflow). order reordering items across flex lines without reordering the box tree (§16.2).

18.9 Failure Analysis

A freeze-accounting bug manifests as either an infinite loop (caught by the CI iteration-bound assertion, I9) or incorrect sizing (caught by WPT/reference-image diff). Blast radius: scoped to the flex subtree; a hang in one document's flex resolution does not affect other Engine instances (P9).

18.10 Operational Notes

tracing span layout.flex with per-line item counts and freeze-iteration counts. No migration/compatibility concerns beyond the standard WPT-gated regression policy (§27).

19. Phase 7 — Grid

19.1 Objectives

Implement CSS Grid Layout Level 2 — the hardest single algorithm in CSS (§29 pitfall carried forward) — without shortcuts; schedule the longest single-phase budget in the plan (4 weeks, §12 timeline note) for exactly this reason.

19.2 Detailed Implementation Steps

The grid spec's track-sizing algorithm, four phases: (1) initialise track base sizes and growth limits from grid-template-columns/-rows including repeat(), minmax(), fit-content(); (2) resolve intrinsic track sizes from item content contributions, span-restricted per track; (3) maximise tracks up to their growth limit; (4) expand flexible (fr) tracks to consume remaining space. The grid spec's auto-placement algorithm: place un-positioned items (no grid-area/grid-row/grid-column) per grid-auto-flow (row column row-dense column-dense). Alignment: justify-content align-content justify-items align-items justify-self align-self per box-alignment-3. Subgrid (per the grid spec's subgrid chapter): inherit parent-grid tracks; alignment interacts with the parent's resolved tracks, not the subgrid's own. Container intrinsic sizes: run track-sizing with infinite container size (max-content) and min-content-contribution mode (min-content) — mirroring Phase 6's approach (§18.2 last step) for a structurally analogous two-pass sizing problem (P1/domain-model consistency, §8.5).

19.3 Deliverable

A grid-layout pass resolving the full track grid and per-cell fragment geometry for any display:grid/inline-grid subtree, including repeat(), minmax(), fit-content(), and subgrid.

19.4 Acceptance Criteria

Grid passes ≥ 80% of conformance/wpt/css/css-grid at Phase-0 ship, ≥ 95% by the Phase-2 hardening gate (§23.1 bucket table). Reference-image diff on a holy-grail layout, a dashboard with sparkline cells, and a calendar view < 1% pixel-diff.

19.5 Conformance Fixtures

conformance/wpt/css/css-grid/*. conformance/ref_tests/grid-holy-grail.png, grid-dashboard.png, grid-calendar.png. conformance/parser_corpus/grid-template-areas- invalid.html — purpose: a non-rectangular grid-template-areas value; expected: parse error (exact per-cell rectangle validation), not a silent layout fallback.

19.6 Pitfalls

The track-sizing algorithm has multiple "do not double-count a span's contribution" rules that are easy to miss transcribing — WPT fixtures are the only safety net (mirrors §17.6/§18.6's corpus-first philosophy). grid-template-areas rectangle validation is exact — an off-by-one is a parse error, not a layout error (a common conflation). Subgrid's track inheritance interacts with the parent's alignment properties; cite the exact spec section in code comments.

19.7 Performance Concerns

Grid layout throughput target ≥ 50,000 boxes/sec (M6, §4/§30) — lower than flex/block because track-sizing's four phases are inherently more expensive per item; Meyerovich & Bodik (WWW 2010) identify constraint-solving parallelism opportunities across independent tracks — a Phase-2 stretch (§30.4), not a Phase-7 requirement.

19.8 Edge Cases

A grid item spanning more tracks than exist (grid-column: span 999) — implicit tracks are generated per grid-auto-columns/-rows, bounded by a configurable max (§24 adversarial-layout- shapes row). subgrid nested two levels deep. fit-content() combined with a flexible (fr) sibling track in the same axis.

19.9 Failure Analysis

A track-sizing bug manifests as incorrect cell dimensions, caught by WPT diff or the reference- image gate; because track-sizing is the "largest single algorithm in CSS," a regression here has historically been the hardest bucket to keep green (§23.1's Phase-0/Phase-2 two-tier commitment reflects this directly, not an arbitrary discount).

19.10 Operational Notes

tracing span layout.grid with per-phase (initialise/resolve/maximise/expand) timing breakdown, enabling the runbook to distinguish "slow track-sizing" from "slow auto-placement" as distinct pathologies.

20. Phase 8 — Tables, Multi-Column & Positioning

20.1 Objectives

Implement CSS 2.1's table-layout chapter, CSS Multi-column Level 1, and the three positioning schemes (absolute fixed sticky) — the last of the "classic" formatting contexts before paint (§8.5).

20.2 Detailed Implementation Steps

Tables (CSS 2.1's table chapter): table/row-group/row/column-group/column/cell/caption box types; anonymous-table-box generation per CSS 2.1's anonymous-table-object rule (a row outside a table synthesizes an anonymous table, mirroring §16.2's anonymous-block rule and the same P1/ ADR-02 box-tree-vs-DOM discipline); auto-layout (CSS 2.1's automatic-table-layout algorithm, two-pass: minimum then preferred content widths per column) and fixed-layout (CSS 2.1's fixed-table-layout algorithm, single-pass from the first row); row-span/col-span per CSS 2.1's table cell-span rules. Multi-column (CSS Multicol 1): column-count column-width column-gap column-rule column-span break-inside; the fragmentation engine is shared with the deferred print/paginated module (PhaseDeferred("§37")). Absolute (position:absolute): box removed from flow; containing block = nearest positioned ancestor's padding box (or the initial containing block); static position = the position the box would occupy in normal flow, consulted when top/left/right/bottom are auto; the absolute-layout pass runs after in-flow layout since absolute boxes do not size their containing block unless it is shrink-to-fit. Fixed: identical to absolute except the containing block is always the initial containing block. Sticky (position:sticky): hybrid — flows normally until the containing block scrolls past a threshold, then offsets to stay within the scrollport; requires a scrollport reference and a per-frame layout fixup (layout computes the offset, paint applies it, §21).

20.3 Deliverable

A tables+multicol+positioning layout pass producing correct fragment geometry, including auto-layout's two-pass column-width resolution and sticky's per-frame offset recomputation.

20.4 Acceptance Criteria

Tables pass the WPT css-tables subset (≥ 85%, §23.1). Multi-column passes WPT css-multicol (≥ 85%). Positioning passes WPT css-position (≥ 90%). Auto-layout table two-pass resolution matches the reference-image corpus to < 1% pixel-diff on a 200-row financial-table fixture.

20.5 Conformance Fixtures

conformance/wpt/css/css-tables/*, css-multicol/*, css-position/*. conformance/ref_tests/ table-financial-200row.png — named fixture for auto-layout worst-case perf+correctness. conformance/parser_corpus/sticky-no-scrollport.html — purpose: sticky outside any scrollport must behave identically to position:relative (spec-normative edge case).

20.6 Pitfalls

Auto-layout tables are slow on worst-case input (two full passes over every cell) — document the perf characteristic and recommend table-layout:fixed as the opt-out (a real-world guidance every production engine ships). Sticky requires scrollport tracking — an engine that does not track scroll position must short-circuit sticky to always-static, not silently misbehave. The static position of an absolute box is computed in its hypothetical containing block, not the actual one — WPT fixtures catch this exact bug class.

20.7 Performance Concerns

Auto-layout's two-pass column-width resolution is O(rows×cols) per pass; the 200-row fixture (§20.5) is the explicit worst-case perf gate, not merely a correctness fixture. Sticky's per-frame offset fixup must not trigger a full re-layout (P8) — it is a paint-time offset application, not a layout-invalidating change (cross-reference §21's paint-time sticky application).

20.8 Edge Cases

A table with more colspan-expanded cells than declared columns (implicit column growth, bounded per §24's adversarial-layout-shapes row). Nested multicol inside a table cell. A position:fixed element inside a transform-ed ancestor (per spec, the transformed ancestor becomes the containing block instead of the viewport — a widely-missed spec detail).

20.9 Failure Analysis

An auto-layout bug manifests as incorrect column widths, caught by WPT/reference-image diff. A sticky bug manifests as an element failing to stick or sticking at the wrong offset, caught by a dedicated scroll-simulation fixture. Both are structural-correctness bugs with no panic signature — detection is corpus-driven, consistent with every prior layout phase's failure-detection philosophy (§17.9, §18.9, §19.9).

20.10 Operational Notes

tracing span layout.table, layout.multicol, layout.positioned with per-pass timing for the auto-layout two-pass algorithm specifically (enabling the runbook to attribute a slow-style- resolve-adjacent complaint to table layout rather than the cascade).

21. Phase 9 — Paint & Hit Testing

21.1 Objectives

Emit a DisplayList (§11, P10) from the box tree's computed geometry and implement the back-to-front hit-test walk (P11) — the last stage before an embedder's rasteriser takes over.

21.2 Detailed Implementation Steps

Stacking contexts: established by the root element, position:fixed/sticky, position:absolute/relative with z-index≠auto, opacity<1, transform≠none, filter, mask, mix-blend-mode≠normal, isolation:isolate, will-change naming a stacking-context property, contain:paint. They form a tree, walked recursively. Paint order (CSS 2.1 Appendix E, transcribed exactly, I10): per stacking context — (1) background (border-radius-clipped per background-clip); (2) borders; (3) negative-z-index child stacking contexts, ascending; (4) in-flow non-inline non-positioned descendants; (5) non-positioned floats; (6) in-flow inline-level descendants incl. atomic inlines/text; (7) z-index-zero child stacking contexts, tree order; (8) z-index-zero positioned descendants, tree order; (9) positive-z-index child stacking contexts, ascending. Display-list commands (§11): SolidRect Border BoxShadow Glyph Image Gradient Stop PushClip PopClip PushStackingContext PopStackingContext Transform Filter Mask; the list is Send + Sync (P10) so a GPU-backed rasteriser can parallelise consumption. Compositing hints: advisory LayerHint on stacking contexts likely promoted to compositor layers (animating transform/opacity, will-change, position:fixed) — the embedder decides whether to honour them. Hit testing (P11): backward walk over the display list (paint order is back-to-front; hit order is front-to-back); rectangles are the default hit shape, clip-path/border-radius produce non-rectangular shapes; pointer-events:none short-circuits the box while still hit-testing descendants.

21.3 Deliverable

A paint pass emitting a correctly-ordered DisplayList for any box tree, a softbuffer rasteriser consuming it to a PNG (ADR-10, Phase-0 demo path extended), and a hit-test walk resolving (x,y) to a NodeId.

21.4 Acceptance Criteria

Paint passes WPT css-paint and css-shapes subsets (≥ 95%, §23.1). Hit testing passes WPT pointer-events and css-clip-path subsets. Reference-image diff on the §17/§18/§19 corpora < 1% pixel-diff. Display-list emission throughput ≥ 1,000,000 commands/sec (M8, §4/§30).

21.5 Conformance Fixtures

conformance/wpt/css/css-paint/*, css-shapes/*, pointer-events/*, css-clip-path/*. conformance/ref_tests/stacking-negative-zindex.png — purpose: negative-z-index paint-order regression fixture (§21.6 pitfall). conformance/ref_tests/blend-mode-isolated.png — purpose: mix-blend-mode requiring an isolated group.

21.6 Pitfalls

Negative-z-index children paint behind in-flow non-positioned children but in front of the parent's own backgrounds (Appendix E is precise; a common off-by-one in stage ordering). transform:none does not establish a stacking context — only a non-identity transform does (WPT catches this). will-change establishes a stacking context for any property that would itself establish one if actively animating. mix-blend-mode requires an isolated group; non-isolated descendants composite individually and produce the wrong visual result.

21.7 Performance Concerns

Paint is fully parallel below the stacking-context root (§30.4) — display-list emission per stacking context has no cross-context dependency, unlike layout's sequential-per-formatting- context constraint. The hit-test backward walk is O(display-list length) worst case; a spatial index (quad-tree over stacking-context bounds) is a documented Phase-2 stretch, not required at Phase-0 throughput targets.

21.8 Edge Cases

A stacking context with opacity<1 and descendants that themselves establish stacking contexts (nested isolation). pointer-events:none on a stacking-context root with pointer-events:auto descendants (descendants remain hit-testable per spec). A clip-path shape entirely outside the viewport (zero-size hit region, not a panic).

21.9 Failure Analysis

A paint-order bug manifests as visually incorrect layering, caught only by reference-image diff (no crash signature) — consistent with every layout phase's corpus-first detection philosophy. A hit-test bug manifests as clicks resolving to the wrong element, caught by the pointer-events WPT subset and a dedicated click-simulation harness.

21.10 Operational Notes

tracing span paint.emit, hit_test.walk. The runbook docs/runbook/paint-jank.md documents the display-list-size-vs-frame-time correlation used to triage a jank complaint.

22. Phase 10 — Script Bridge & Incremental Invalidation

22.1 Objectives

Expose the typed CSSOM/DOM surface a script host consumes (this engine ships no JS interpreter, ADR-21) and wire incremental invalidation end to end — the design's single load-bearing decision (ADR-23) — from dirty-bit marking through subtree-scoped re-layout.

22.2 Detailed Implementation Steps

CSSOM (kosmos-bindings::cssom): CSSStyleDeclaration CSSStyleSheet CSSRule CSSMediaRule CSSSupportsRule CSSLayerBlockRule CSSContainerRule as a typed surface the bridge translates to whichever script host's binding shape (V8/JerryScript/QuickJS/project-126). DOM surface (kosmos-bindings::dom): Node Element Document Range MutationObserver ShadowRoot IntersectionObserver ResizeObserver; the reentrancy guard (P7, I11) is enforced at every binding entry point via the LayoutPhase enum (Idle Style Box Layout Paint). Layout-flushing call sites: getBoundingClientRect getClientRects offsetWidth/Height/Top/Left getComputedStyle scrollTop scrollHeight scrollY — each registered in a table documenting whether it flushes style, box, or layout (§8.8's failure-path example exercises exactly this table). Observers: IntersectionObserver batched per animation frame; ResizeObserver supporting border-box content-box device-pixel-content-box. Incremental invalidation: per-box dirty bits (needs_style needs_box_regenerate needs_layout needs_paint, §11, I6) set by the upstream stage, consulted by the downstream; dirty bits propagate to the nearest formatting-context root (a dirty inline marks its containing block's IFC dirty). Style invalidation consults the Phase-3 invalidation set (I4); box invalidation triggers on display/content/position changes; layout invalidation on any layout-affecting property; paint invalidation on paint-only properties (color background-color box-shadow-color opacity) without re-layout. Re-layout strategies: full (test-only, force_full_layout, P8), subtree (default, from the nearest FC root), repaint-only (display-list re-emit with no re-layout).

22.3 Deliverable

A script-bridge surface passing WPT's CSSOM/observer subsets, plus an incremental-invalidation pipeline whose dirty-set matches a Servo reference trace on canonical mutation sequences.

22.4 Acceptance Criteria

CSSOM passes WPT cssom subset (≥ 90%, §23.1). IntersectionObserver/ResizeObserver pass their WPT subsets (≥ 95% each). The reentrancy guard catches a getBoundingClientRect call during an active Layout phase and raises LayoutPhaseError (I11) — verified by a dedicated unit test, 0 silent successes tolerated. Invalidation trace matches the Servo reference dirty-set to ≥ 99% overlap (§15.4 restated at the integration level). A "type one character into an input" benchmark completes in < 1 ms on the page-of-the-day corpus (M9, §4). A "scroll a sticky header" benchmark completes in < 100 µs.

22.5 Conformance Fixtures

conformance/wpt/cssom/*, intersection-observer/*, resize-observer/*. conformance/ invalidation_traces/keystroke.json, sticky-scroll.json — the two named performance-gating fixtures from N.4. conformance/parser_corpus/reentrant-raf-resize.html — purpose: reproduces §8.8's ResizeObserver-during-Layout failure path; expected: LayoutPhaseError, no panic, no silent flush.

22.6 Pitfalls

Layout-flushing inside a requestAnimationFrame callback is the most common reentrancy pathology in production browsers — document it explicitly in the runbook (§8.8, §21.10 cross-reference). IntersectionObserver thresholds must be interpreted as a sorted list — sort at construction time, not per-notification (a real perf regression source if done lazily).

22.7 Performance Concerns

The invalidation set's correctness is the entire incrementality story (P6, ADR-08, I4); a missed invalidation produces silent visual staleness (§15.9) while an over-broad invalidation produces a perf regression that only a benchmark (§22.4's two named benchmarks) will catch — both directions are gated in CI (perf.yml, §10), not left to manual review.

22.8 Edge Cases

A ResizeObserver callback that itself resizes its own observed element (a documented re-entrant-loop hazard the spec bounds via a "the browser MAY skip additional notifications" escape hatch — implement the bound, don't loop forever). A MutationObserver batch spanning a stylesheet insertion and a class-attribute change in the same microtask (both invalidation paths must compose without double-counting).

22.9 Failure Analysis

A reentrancy-guard bug (I11) manifests as either a spurious LayoutPhaseError on a legitimate call (usability regression, caught by the WPT CSSOM subset) or a silent reentrant flush (a correctness/crash-adjacent bug, caught by the dedicated reentrancy fixture, §22.5). Both paths are covered because a false-positive is at least as harmful operationally as a false-negative.

22.10 Operational Notes

tracing span bindings.flush, reentrancy.blocked (I11 telemetry), invalidation.dirty_mark. No rolling-upgrade concerns (in-process library, not a networked service, §27).

23.6 Pitfalls

Animation interpolation for non-numeric values (e.g. display) uses discrete steps — not every property is animatable, and treating all properties as continuously interpolable is a common implementer error. 23.9 Failure Analysis

27. Compatibility & Versioning

Wire compatibility: not applicable — the engine has no network wire protocol (ADR-22). Storage compatibility: not applicable — no persisted state. API stability: every public type is #[non_exhaustive] (P15) and every public method is documented; a SemVer-major bump is required to remove or change the signature of any type/method enumerated in §11. Schema evolution: the properties.toml/computed_table.toml property tables (§14.2, §15.2) are additive-only within a minor version — a new CSS property is a minor bump, a changed computed-value form for an existing property is a major bump. Deprecation policy: a deprecated public API is marked #[deprecated] for one minor version before removal in the next major version. 30.1 Allocator Discipline

The per-document arena (bumpalo, ADR-24) resets between layout passes; no per-pass Vec::new() sits on the hot path — pre-allocated scratch buffers are owned by the per-pass state. ComputedStyle is the largest per-element allocation; style sharing (M3) reduces the allocation count ≥ 90% on typical pages. The box tree's intrinsic-size cache (§11) is per-formatting-context; a cache hit short-circuits the layout sub-routine entirely.

30.2 Branch Prediction

The hot path (BFC stacking, IFC line accumulation, §17) is structured so the common case (no float, no abspos, no orthogonal flow) is the fall-through branch. Mispredict rate is measured on the news-article corpus (§21.5-adjacent reference-image corpus) and tracked per commit via criterion (ADR-15).

30.3 Cache Locality

The box tree is laid out depth-first in memory so a layout-pass walk reads contiguous cache lines; sibling boxes are co-located. ComputedStyle (§11) is under 256 bytes (§4 constraint); common properties sit in the first 64-byte cache line.

30.4 Parallelism

Style resolution is embarrassingly parallel below the rule-tree root (§15.2) — each subtree's matched-rule list computes independently; Phase-0 ships single-threaded, a Phase-2 stretch adds a Rayon-based parallel matcher with identical observable output (Meyerovich & Bodik WWW 2010, §5). Layout is sequential per formatting context — sibling contexts could parallelize but the dependency graph (sticky positioning depends on parent scroll offset, §20.2) constrains it; deferred (PhaseDeferred("§37")). Paint is fully parallel below the stacking-context root (§21.7) since display-list emission has no cross-context dependency.

30.5 SIMD Opportunities

Text shaping is the largest SIMD target; HarfBuzz carries AVX2/NEON paths (ADR-11) — consumed through HarfBuzz, never reimplemented (§17.7). The css-syntax-3 tokenizer's ASCII-identifier inner loop is SIMD-friendly (a memchr-style scanner, Phase-1 stretch). The selectors bloom filter (§15.1) is a small, low-priority SIMD candidate — one cache-line probe is already fast; deferred (PhaseDeferred("§37")).

30.6 Tracing & Profiling

Every phase emits per-phase tracing spans (§26): parse-time, style-resolve-time, box-generate- time, layout-time, paint-time. Per-element style-resolve time is sampled at a configurable rate (default 1-in-1024). The runbooks (§26, §10) name the diagnostic span sequence for each common pathology.

30.7 Memory Profile

Heap snapshots at five canonical points (post-parse, post-style, post-box-generate, post-layout, post-paint) on the canonical corpus, checked into audits/heap-snapshots/ (§10); a snapshot diff is a CI artifact, not a merge-blocking gate. dhat allocation profiling runs on the bench harness and produces an allocation-count diff per commit (FM-7 detection path).

31. Scalability Analysis

What stays constant vs. grows: per-document memory grows O(elements) (M11/M12); style-resolve time is O(elements × average-matched-rules) before sharing, reduced to near-O(elements) after sharing (M3, §15.6); incremental reflow is O(dirty subtree size), not O(document size) — the entire point of ADR-08/ADR-23. Named bottlenecks, in order: (1) the cascade's per-property table walk on a cache miss (mitigated by the rule tree's interning, §15.2); (2) grid track-sizing's four-phase cost (M6 is deliberately lower than M4/M5 for exactly this reason, §19.7); (3) the :has() ancestor-invalidation path (§15.7), which is intentionally excluded from the standard descendant-invalidation fast path. Horizontal scaling: N independent Engine instances across N host surfaces in one process (P9) — there is no shared mutable state to coordinate, so horizontal scaling is embarrassingly parallel at the process level. Vertical scaling: within one document, style resolution parallelizes below the rule-tree root (§30.4) and paint parallelizes below the stacking-context root (§21.7); layout itself remains sequential per formatting context due to cross-context dependencies (e.g. sticky positioning depending on parent scroll offset). Sharding/ partitioning: not applicable at the document level (a DOM tree is not partitioned); at the process level, "sharding" is simply "one engine per surface" (P9). Coordination overhead: zero cross-engine coordination by design (P9) — this is the deliberate trade against a shared-cache architecture that would need cross-engine invalidation coordination. Practical ceiling: bounded by single-document memory (M12: 200 MB at 100k elements) and single-core style-resolve throughput (M2); the lever beyond it is the Phase-2-stretch Rayon-based parallel matcher (§30.4) which amortizes style resolution across cores within one document.

32. Mental Models & First Principles

MM1 — "The box tree is a compiled artefact of the DOM, not a view of it." Predicts: any bug where a script mutation "should" instantly reflect in layout without a regeneration step is a misunderstanding, not a bug. Bug class without it: engineers reach for direct DOM-to-pixel shortcuts and reinvent anonymous-box logic ad hoc. Resolves in §16 (P1, ADR-02).

MM2 — "Computed style is a pure function boundary." Predicts: given the same (DOM subtree, matching rules), the computed style is always the same — a property the sharing cache (P4) depends on for soundness. Bug class without it: a "style leaks layout state" bug where computed values differ across otherwise-identical elements for no cascadable reason. Resolves in §15 (P3, I2, I13).

MM3 — "Invalidation is a graph-coloring problem solved once, not re-solved per mutation." Predicts: the cost of a mutation is O(1) hash lookup, never O(rules). Bug class without it: full re-style on every keystroke, a 30×+ regression (P8). Resolves in §15 (P6, ADR-08, I4).

MM4 — "A formatting context is a pluggable strategy, not an inheritance layer." Predicts: adding a new layout mode (e.g. subgrid) should touch one dispatch arm, not a class hierarchy. Bug class without it: the Blink LayoutObject maintenance burden this project explicitly avoids (ADR-03). Resolves in §16, §19 (P2).

MM5 — "Text layout is Unicode substrate wearing a CSS costume." Predicts: bidi and line-breaking bugs are almost always UAX #9/#14 conformance bugs, not CSS bugs. Bug class without it: engineers "fix" a bidi bug in the CSS layer instead of the Unicode layer, papering over the real defect. Resolves in §17 (I8, ADR-12).

MM6 — "The display list is the only thing paint order can be reasoned about in." Predicts: any hit-testing or stacking bug must be diagnosed against the display list, never the box tree. Bug class without it: hit-testing implemented against the box tree silently mis-orders overlapping stacking contexts. Resolves in §21 (P11, I10).

MM7 — "Reentrancy is a phase, not a lock." Predicts: the right primitive for "is it safe to flush layout right now" is a small state machine (LayoutPhase), not a mutex — because the question is about logical phase, not thread contention (P9: one writer thread already). Bug class without it: deadlock-prone lock-based reentrancy guards, or silent reentrant corruption if no guard exists at all. Resolves in §22 (P7, I11).

MM8 — "Every asserted performance number must be an amortized cost, not a peak cost." Predicts: a target like M9 (< 1 ms incremental reflow) is only meaningful because it is the steady-state cost after invalidation-set construction (a one-time O(rules) cost, §15.2) — quoting it without that context invites an apples-to-oranges comparison against a full-relayout engine. Resolves in §34 (Back-of-Envelope Capacity Model), §30 (M-table).

34. Back-of-Envelope Capacity Model

  1. Style-resolve time for 100k elements = elements ÷ throughput = 100,000 ÷ 1,000,000/sec (M2, §4/§30) = 100 ms for a full-document resolve (never paid in steady state, P8 — only at first paint or force_full_layout).
  2. First-paint style-resolve budget check — 100 ms (step 1) vs. no hard first-paint SLO in §4; acceptable because Phase-0's target document (100k elements, §4) is a ceiling, not a typical case — a typical 5k-element page resolves in 5,000 ÷ 1,000,000 = 5 ms.
  3. Incremental reflow cost floor = dirty-subtree size ÷ block-layout throughput; for a single-paragraph edit (≈ 50 boxes) ÷ 100,000 boxes/sec (M4) = 0.5 ms, comfortably under the M9 p50 < 1 ms target — the arithmetic that makes M9 plausible rather than asserted.
  4. Resident memory for 100k elements = elements × ComputedStyle size (M12 constraint) = 100,000 × 256 B (§4 ComputedStyle row) = 25.6 MB for styles alone; the remaining budget to the 200 MB ceiling (M12) covers the DOM arena, box tree, fragments, and display list.
  5. Style-sharing memory saving = un-shared cost × (1 − share rate) = 25.6 MB × (1 − 0.90) (M3, ≥ 90% reduction) = 2.56 MB actual ComputedStyle residency on a highly homogeneous (table-like) 100k-element document — a 10× reduction directly attributable to P4/§15.6.
  6. Font-shaping cost for a 2,000-word article ≈ 12,000 characters ÷ 10,000,000 chars/sec (M7) = 1.2 ms — negligible against the 16.6 ms frame budget (§4), confirming shaping is not the steady-state bottleneck for prose-heavy pages.
  7. Display-list size for a 100k-element document ≈ 100,000 boxes × ~2 PaintCommands/box (background + content, typical) = 200,000 commands ÷ 1,000,000 commands/sec (M8) = 0.2 ms emission time — confirms paint is not the dominant cost relative to style-resolve (step 1/2).
  8. Fan-out × rate for observer notifications — a 60 Hz IntersectionObserver on 1,000 observed elements batches per animation frame (§22.2): 1,000 elements ÷ 16.6 ms frame = ** ≈ 60,000 element-checks/sec**, well inside a single core's branch-predictable comparison budget.
  9. Grid track-sizing cost for a 12×12 dashboard grid ≈ 144 cells ÷ 50,000 boxes/sec (M6) = 2.9 µs — confirms grid's lower per-box throughput (vs. M4/M5) is still negligible at realistic dashboard scale; the M6 discount only matters at pathological track counts (§19.8).
  10. 30-day fuzz canary throughput — assuming ≈ 1,000 execs/sec per fuzz target (typical cargo-fuzz throughput) × 7 targets (§10) × 30 days × 86,400 s = ≈ 18.1 billion total fuzz executions before a release branch cuts (§23.2), the empirical basis for the "clean canary" release gate's confidence level.

Every number above chains from the §4 constraint table; none is asserted independent of it (§15.C gate item 13 / H13).

36. Alternative Architectures (Roads Not Taken)

A1 — Single-tree retained-mode render-object model (Flutter-style).

Element tree == RenderObject tree == "box tree"
(one node type carries DOM identity, style, AND layout geometry)

Regime where it wins: a closed, first-party UI framework with no untrusted external DOM/CSS input and no legacy-web-compatibility requirement (exactly Flutter's regime). Real system: Flutter's RenderObject/Element/Widget three-tree model collapses much of what this project keeps structurally separate (P1) because Flutter controls both ends of the pipe. Rejected here because this engine must ingest arbitrary, adversarial, legacy-web-shaped HTML/CSS (§24) where anonymous boxes and pseudo-elements have no DOM-node analogue to attach to — Flutter's collapse is only safe because it never has to represent an anonymous box in the first place.

A2 — Immediate-mode layout (Dear ImGui-style), no persistent box tree.

loop { input -> layout(now) -> paint(now) }  // no cross-frame retained state

Regime where it wins: a UI that fully re-lays-out every frame anyway (a game HUD at a fixed, small element count) where retained-state bookkeeping costs more than a full recompute. Real system: Dear ImGui itself. Rejected here because the incrementality contract (ADR-23) is the project's central bet — a 100k-element document (§4) cannot afford a full relayout every frame (§34 item 1 shows this costs 100 ms, 6× the entire frame budget), so retained, dirty-bit-scoped state (I6) is not optional at this scale.

A3 — GPU-first constraint solver for all formatting contexts (Cassowary/Auto-Layout-style).

[constraints: item.left + item.width <= container.width, ...] -> LP solver -> positions

Regime where it wins: a UI toolkit whose layout rules are genuinely linear/constraint-based end to end (Apple's Auto Layout is the canonical example) with no CSS-specific special-casing (float clearance, BFC/IFC interleaving, table auto-layout's two-pass rule) to encode. Real system: Apple AutoLayout / Cassowary-based toolkits. Rejected here because CSS's formatting contexts are not uniformly linear-constraint-shaped — flexbox's freeze-loop (§18.2) and grid's four-phase track sizing (§19.2) are closer to specialized fixed-point iterations than a general LP, and forcing them into one solver would either violate spec-exactness (P13) or require a solver expressive enough to lose the performance this project's M-table (§30) demands.

A4 — Fully GPU-resident scene graph with no CPU display list (WebRender's most aggressive mode).

CPU: box tree -> GPU: primitive batches (built and diffed entirely on GPU-visible buffers)

Regime where it wins: a compositor-first browser where every frame is expected to hit a GPU path unconditionally (modern Firefox's WebRender in its steady-state configuration). Rejected as this project's default: the display list (P10, ADR-09) is deliberately CPU-resident and backend-agnostic so a headless/CPU-only embedder (a CI screenshot tool, T8-adjacent) is a first-class target, not a degraded fallback — ADR-10's softbuffer demo backend depends on exactly this choice. An embedder that only ever targets GPU surfaces could adopt A4 as a swappable consumer of the same DisplayList type without changing this document's architecture.

38. Glossary

  • Anonymous box. A box generated by box generation (§16) with no corresponding DOM element — e.g. an anonymous block wrapping a run of inlines inside a block container.
  • Atomic inline. An inline-level box treated as a single rectangle by the IFC: inline-block, inline-table, or a replaced element.
  • Bidirectional algorithm (bidi). UAX #9; translates a logical character sequence to a visual order given the paragraph's embedding level (§17, I8).
  • Block formatting context (BFC). A region of layout in which block-level boxes stack vertically and float positioning is computed (§17.2, I7).
  • Bloom filter. A probabilistic ancestor-feature cache short-circuiting descendant-selector matching (§15.1, ADR-05).
  • Box tree. The layout-internal tree of LayoutBox values, structurally distinct from the DOM tree (§8.4, P1, ADR-02).
  • Cascade. The algorithm resolving a property to its specified value from matching declarations, per a total order (§15, P5).
  • ComputedStyle. The immutable, #[non_exhaustive] value produced after cascade + computed- value transform; the boundary between style and layout (§11, P3, I2).
  • Dirty bits. Per-box flags (needs_style needs_box_regenerate needs_layout needs_paint) forming a monotonic lattice within a frame (§11, I6).
  • Display list. A flat, typed, Send + Sync list of paint commands; the deliverable of the paint pass (§21, P10).
  • Engine. The value-typed root object of the public API; Send, not Sync (§11, P9, I11).
  • Flex formatting context. The region of layout implementing CSS Flexbox Level 1 (§18).
  • FormattingContext. The enum tag selecting a LayoutBox's layout sub-routine (§8.4, P2, ADR-03).
  • Fragment. The positioned, sized output of a layout pass for one box (§8.4, §11).
  • Grid formatting context. The region of layout implementing CSS Grid Layout Level 2 (§19).
  • Inline formatting context (IFC). The region of layout in which inline-level boxes lay out into line boxes (§17.2).
  • Initial value. A property's value in the absence of any matching declaration (§15.3).
  • Intrinsic size cache. Per-formatting-context cache of min-/max-content sizes, shared in shape between flexbox and grid's two-pass sizing (§35 Q15, §11).
  • Invalidation set. The set of selectors whose match status depends on a given feature; consulted on mutation (§15.7, P6, I4).
  • LayoutBox. The box-tree node type: id, style, formatting context, fragments, intrinsic cache, dirty bits (§11).
  • LayoutPhase. The reentrancy-guard enum (Idle Style Box Layout Paint) enforcing P7/I11.
  • Line box. A horizontal slice of an IFC; the unit of line-breaking (§17.2).
  • Margin collapsing. CSS 2.1's rule merging adjacent in-flow block margins within a BFC (§17.2, I7).
  • PaintCommand. A tagged union of typed paint operations forming the display list (§11, §21).
  • Painting. The pass emitting a display list from the box tree's computed geometry (§21, P10).
  • Pseudo-element. A box generated by ::before/::after/::marker/::first-line/ ::first-letter (§16.2).
  • Reentrancy guard. The LayoutPhase-based mechanism blocking layout-flushing calls from a non-Idle phase (§22, P7, I11).
  • Replaced element. An element whose rendering delegates to an external resource — image, video, canvas, iframe (§16.2).
  • Rule tree. The interned tree of (rule, source) pairs; the canonical representation of an element's matching-rule list and the style-sharing key (§15.2, I5).
  • Sibling style sharing. A cache reusing a ComputedStyle across siblings gated by a 12-item predicate (§15.6, P4, I13).
  • Stacking context. A self-contained painting region with its own z-index ordering (§21.2).
  • Static position. The position an absolutely positioned box would occupy in normal flow, consulted when its offset properties are auto (§20.2).
  • Sticky positioning. A hybrid positioning scheme flowing normally until a scroll threshold, then offsetting to remain within the scrollport (§20.2).
  • Stylist. The per-document index of stylesheets and their rules, bucketed for fast matching (§15.1, ADR-05).
  • Track-sizing algorithm. CSS Grid's four-phase column/row-size resolution (§19.2).
  • WPT. Web Platform Tests, the cross-browser conformance corpus (§5, P13, ADR-13).
