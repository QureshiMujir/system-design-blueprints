36. Alternative Architectures (Roads Not Taken)

A1 — Single-tree retained-mode render-object model (Flutter-style).

Element tree == RenderObject tree == "box tree"
(one node type carries DOM identity, style, AND layout geometry)

Regime where it wins: a closed, first-party UI framework with no untrusted external DOM/CSS input and no legacy-web-compatibility requirement (exactly Flutter's regime). Real system: Flutter's RenderObject/Element/Widget three-tree model collapses much of what this project keeps structurally separate (P1) because Flutter controls both ends of the pipe. Rejected here because this engine must ingest arbitrary, adversarial, legacy-web-shaped HTML/CSS (§24) where anonymous boxes and pseudo-elements have no DOM-node analogue to attach to — Flutter's collapse is only safe because it never has to represent an anonymous box in the first place.

A2 — Immediate-mode layout (Dear ImGui-style), no persistent box tree.

loop { input -> layout(now) -> paint(now) }  // no cross-frame retained state

Regime where it wins: a UI that fully re-lays-out every frame anyway (a game HUD at a fixed, small element count) where retained-state bookkeeping costs more than a full recompute. Real system: Dear ImGui itself. Rejected here because the incrementality contract (ADR-23) is the project's central bet — a 100k-element document (§4) cannot afford a full relayout every frame (§34 item 1 shows this costs 100 ms, 6× the entire frame budget), so retained, dirty-bit-scoped state (I6) is not optional at this scale.

A3 — GPU-first constraint solver for all formatting contexts (Cassowary/Auto-Layout-style).

[constraints: item.left + item.width <= container.width, ...] -> LP solver -> positions

Regime where it wins: a UI toolkit whose layout rules are genuinely linear/constraint-based end to end (Apple's Auto Layout is the canonical example) with no CSS-specific special-casing (float clearance, BFC/IFC interleaving, table auto-layout's two-pass rule) to encode. Real system: Apple AutoLayout / Cassowary-based toolkits. Rejected here because CSS's formatting contexts are not uniformly linear-constraint-shaped — flexbox's freeze-loop (§18.2) and grid's four-phase track sizing (§19.2) are closer to specialized fixed-point iterations than a general LP, and forcing them into one solver would either violate spec-exactness (P13) or require a solver expressive enough to lose the performance this project's M-table (§30) demands.

A4 — Fully GPU-resident scene graph with no CPU display list (WebRender's most aggressive mode).

CPU: box tree -> GPU: primitive batches (built and diffed entirely on GPU-visible buffers)

Regime where it wins: a compositor-first browser where every frame is expected to hit a GPU path unconditionally (modern Firefox's WebRender in its steady-state configuration). Rejected as this project's default: the display list (P10, ADR-09) is deliberately CPU-resident and backend-agnostic so a headless/CPU-only embedder (a CI screenshot tool, T8-adjacent) is a first-class target, not a degraded fallback — ADR-10's softbuffer demo backend depends on exactly this choice. An embedder that only ever targets GPU surfaces could adopt A4 as a swappable consumer of the same DisplayList type without changing this document's architecture.
