Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust (edition 2021, MSRV 1.74)

Rejected

C, C++, Go, Python, Zig

When the rejected choice is right

C++ wins when the team must share one codebase with existing SDSL-lite/divsufsort C++ callers and cannot introduce a second toolchain

Why: C++-class bit control; bounded untrusted-index decode (no UB); safe unsafe islands for hot loops

ADR-02

Core/std split

Chosen

no_std core primitives (bits, codecs, SA-IS over int alphabet, rank) + std loader/CLI behind feature="std"

Rejected

monolithic std-only

When the rejected choice is right

Monolithic std-only wins for a short-lived internal CLI that never targets WASM/embedded and the split's upkeep isn't justified

Why: query-only core embeddable in WASM; filesystem/mmap isolated

ADR-03

Primary SA construction

Chosen

SA-IS O(n) (PR2)

Rejected

DC3/skew; prefix-doubling; qsufsort; divsufsort

When the rejected choice is right

DC3 wins when the port target is a data-parallel/GPU pipeline whose difference-cover recursion parallelizes more directly than SA-IS's sequential induced-sort passes

Why: linear time; modest constants; the de-facto standard; DC3 kept as cross-check (ADR-19)

ADR-04

SA index width

Chosen

u32 default (texts ≤ 4 GiB), u64 behind feature="wide"

Rejected

always u64; usize

When the rejected choice is right

Always-u64 wins when texts routinely exceed 4 GiB (pan-genome collections, web-scale corpora), making the width-selection branch not worth its complexity

Why: halve SA memory on the common case; width chosen by n (I16)

ADR-05

Sentinel

Chosen

unique 0x00, defined smallest, appended once

Rejected

no sentinel + primary index; 0xFF largest

When the rejected choice is right

The primary-index-without-sentinel scheme (as bzip2 uses) wins when no byte value can be reserved — e.g. indexing arbitrary binary blobs where 0x00 is legitimate data

Why: invertible BWT without primary-index hack; distinct prefix-free suffixes (I3)

ADR-06

LCP algorithm

Chosen

Kasai O(n) (+ PLCP variant)

Rejected

O(n log n) from SA; Φ-algorithm only

When the rejected choice is right

The Φ-algorithm (PLCP-only) wins when only the text-order LCP is ever needed and the SA-order array is disposable, saving one array's memory

Why: linear; the h−1 invariant; PLCP for cache locality (PR4)

ADR-07

RMQ / LCE

Chosen

sparse table default, Fischer–Heun O(n) behind feature="rmq-compact"

Rejected

segment tree; ±1-RMQ Cartesian only

When the rejected choice is right

Fischer–Heun always wins on space-constrained builds (embedded/WASM query-only) where the O(n log n)-word sparse table would dominate memory

Why: simple O(1) query; compact variant when SA memory is tight

ADR-08

Occ representation

Chosen

wavelet tree (general σ) + direct Occ table for σ ≤ 64

Rejected

per-symbol bitvector always; sampled counter only

When the rejected choice is right

A pure wavelet tree (no small-σ fast path) wins when σ is large and variable at runtime (e.g. a general Unicode codepoint alphabet) and two Occ code paths aren't worth the small-alphabet constant-factor win

Why: O(log σ) general path; O(1) small-σ path; build picks per σ

ADR-09

Wavelet shape

Chosen

balanced default, Huffman-shaped behind feature="wt-huff"

Rejected

always Huffman; wavelet matrix only

When the rejected choice is right

Huffman-shaped wins whenever the corpus's symbol distribution is skewed and known in advance (natural-language text, GC-skewed DNA) and the codebook-serialization cost is amortized over many queries

Why: predictable depth; Huffman reaches n·H_0 when entropy matters

ADR-10

Bitvector representation

Chosen

plain (popcount rank) default, RRR behind feature="rrr"

Rejected

always RRR; SD-vector only

When the rejected choice is right

RRR-always wins when the deployment target is space-constrained above all else (mobile/embedded read-only corpus index) and the ~3× rank slowdown is acceptable

Why: plain is fastest; RRR (n·H_0) when space-bound; SD for very sparse marks

ADR-11

Rank structure

Chosen

two-level (512-bit superblock + 64-bit block) + popcount

Rejected

single-level; interleaved only

When the rejected choice is right

Single-level (block-only) rank wins on tiny bitvectors (a few KB) where the superblock's fixed overhead isn't amortized

Why: ≤ 0.25 n-bit overhead; O(1); cache-friendly (DP5)

ADR-12

Select structure

Chosen

sampled positions (every 4096th 1) + scan

Rejected

Clark's o(n) select; dense only

When the rejected choice is right

Clark's o(n) select wins when select is itself on the hot path at high frequency (e.g. select-heavy wavelet-matrix decoding) and its complexity pays for itself

Why: ≤ 0.20 n bits; simple; adequate for FM-index access patterns

ADR-13

SA sampling for locate

Chosen

text-position sampling, rate s (default 32)

Rejected

row sampling; no sampling (full SA)

When the rejected choice is right

Row sampling wins when queries are locate-dominated with few but very frequent patterns, giving more uniform per-row walk cost

Why: predictable locate latency; marked-bitvector + packed values (DP9, I11)

ADR-14

Repetitive-text index

Chosen

r-index / RLBWT, auto-selected when r/n < 0.3

Rejected

always FM-index; always r-index

When the rejected choice is right

Always-FM-index wins when build-time BWT-run counting is undesirable — e.g. a streaming/incremental builder that cannot afford a second corpus pass

Why: O(r) space on repetitive corpora; FM-index elsewhere (I15)

ADR-15

Suffix automaton role

Chosen

oracle + distinct/LRS, not the primary count path

Rejected

SAM as primary index; suffix tree

When the rejected choice is right

SAM-as-primary wins in an online/streaming setting where the corpus grows incrementally and a full sort-based rebuild per update is unacceptable

Why: independent cross-check (I14); compact-ish; online build (PR10)

ADR-16

Error model

Chosen

Rejected

When the rejected choice is right

anyhow/dynamic errors win in an internal CLI or research prototype where call sites never match on a specific variant and velocity matters more than exhaustive handling

Why: exhaustive matching; bounded decode; no panic on untrusted index (DP7)

ADR-17

Arithmetic

Chosen

Rejected

When the rejected choice is right

Wrapping arithmetic wins in an already-fuzzed, perf-critical inner loop where the width was separately proven safe (post ADR-04 gate) and debug_assert overhead is measurable in profiles

Why: overflow is a typed build error, never silent wrap (I16)

Why: bounds-validatable; zero-copy load; stable across machines (I17)

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

AA1 — Pointer-based suffix tree (McCreight / Ukkonen)

        root
       / | \ \
      a  b  n $
     /|      |
    n a      a
    ...     (internal nodes carry suffix links;
             each edge is a (start,end) substring pointer
             into T, not a copied string)

Regime where it wins: interactive/online construction where new suffixes must be inserted one at a time with O(1) amortized work per character (Ukkonen), and where the ~20n-byte pointer overhead is acceptable because n is small (single genes, not whole genomes). Real embodying system: classic genome-alignment tools built directly on suffix trees (e.g. early REPuter/MUMmer1-generation tools before SA-based successors). Why rejected here: the ~20n-byte pointer/node overhead is 5-10× the plain SA's 4n–8n bytes at the n scales this blueprint targets (§4), and SA+LCP+RMQ (§8.5) already emulates every suffix-tree query this project needs at a fraction of the memory.

AA2 — Suffix automaton (CDAWG/SAM) as the primary index

  extend(c): last -> new state (len=len[last]+1)
  walk suffix links from last, redirect/clone as needed
  (state graph grows by <=2 states per symbol, online)

Regime where it wins: streaming/incremental corpora where the index must grow one symbol at a time without a full resort, and where the workload is dominated by LZ-factorization / dictionary-compression parsing (the suffix automaton and its compact form, the CDAWG, are the standard substrate for optimal LZ77 parsing). Real embodying system: online LZ-factorization research parsers built on suffix automata / CDAWGs. Why rejected here: this blueprint's corpus is static (build-once, DP3), so SA-IS's superior space (4n bytes vs the SAM's ≤2n-1 states each carrying a transition map) and the FM-index's compressibility make the sort-based path strictly better for the batch, queried-many-times workload this project targets; the SAM is retained only as a cross-check oracle (ADR-15).

AA3 — k-mer hash-table seed index (BLAST-style)

  hash_table[k-mer] -> list of text positions
  (fixed k, e.g. k=11; no full-text sort at all)

Regime where it wins: approximate / seed-and-extend search where exact full-text membership is not the primitive needed — only "does this k-mer appear, and roughly where" — trading exactness and worst-case guarantees for much cheaper construction and no global sort. Real embodying system: BLAST's k-mer seed-and-extend index. Why rejected here: this project's contract is exact substring count/locate/extract (§1), which a fixed-k hash table cannot answer for patterns shorter or longer than k, or with any position guarantee beyond the seed; approximate/seed-based search is explicitly out of scope and deferred (Deferred Features Register).

AA4 — External-memory / disk-backed construction (pSAscan-style)

  text (on disk, > RAM) -> disk-backed radix/induced-sort
  passes with bounded RAM buffers -> SA (on disk)

Regime where it wins: corpora that exceed available RAM (whole-genome pan-genome collections, web-scale text) where in-RAM SA-IS simply cannot run regardless of time budget. Real embodying system: pSAscan / eSAIS external-memory suffix-array construction algorithms (Kärkkäinen, Kempa, Puglisi and related work, referenced in B4). Why rejected here: Phase 0's engineering budget (§1, 6-12 weeks) targets the in-RAM regime that covers the stated n ≤ 2^32 ceiling (§4); external-memory construction is a materially larger engineering project (disk-aware buffer management, multi-pass merge) that is explicitly deferred (Deferred Features Register) rather than attempted as a half-measure.
