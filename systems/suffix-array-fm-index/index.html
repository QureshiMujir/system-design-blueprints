In one paragraph

A substring index answers "where does this pattern occur in this large, unchanging text?" without scanning the text. This design is a Rust library plus a small command-line tool (sufx). It builds the index once, offline, and then answers count, locate and extract queries from a read-only structure (§1). It sorts every suffix of the text (a suffix array), then stores the text in a rearranged form that can be searched while compressed (an FM-index), with a variant for highly repetitive text (an r-index) (§1, §3). The design target is under 2 µs per count for patterns of up to 64 symbols over a byte alphabet (§4). Search-infrastructure and bioinformatics engineers are the intended users (§1).

The problem, concretely

Take the blueprint's own example: the text banana and the pattern ana (§8.6, §8.8). The blueprint's point is that building an index removes the "search = scan" habit, and that the alternative looks simple ("sort the suffixes and binary-search") but is really a construction, succinct-data-structure, information-theory and adversarial-decode problem (§2). Four pressures follow.

First, sorting the suffixes makes search easy. All suffixes starting with ana sit next to each other in sorted order, so the answer is one contiguous range of the sorted list (§8.2). For banana$ the list of start positions is [6, 5, 3, 1, 0, 4, 2], and ana occupies rows 2 and 3, which hold positions 3 and 1 (§8.3.3, §8.8).

Second, that list is large. A plain suffix array costs 4n bytes with 32-bit indices (§4). At the design's maximum text length that is about 17.18 GB, against 4.29 GB for the text itself (Capacity Model items 1 and 2). Storing the full array defeats compression (§8.9).

Third, building it naively is slow and, worse, easy to get subtly wrong. The comparison-sort builder is kept only as a test oracle, and a bucket-pointer bug in the fast builder can return wrong positions while small tests still pass (§3, DP1, FC1). The blueprint states the oracle's cost as O(n log²n) in §3, DP1 and ADR-19 but as O(n² log n) worst case in the §8.3 table, and does not reconcile them.

Fourth, the index file is loaded from disk, and a truncated or hostile file can make a decoder read past the end of a buffer. The blueprint names this the dominant risk class and picks Rust partly for it (§1, ADR-01, T1). The design's answers map onto these pressures: search by range (§8.2), budget space in bits (DP5), check every construction against an independent oracle (DP1), and bounds-check every load (DP7).

How it works, end to end

The blueprint has an offline build pipeline and an online, read-only query pipeline (§3). A condensed copy of its diagram:

 TEXT SOURCE T  (sentinel $ = 0x00 appended; n = |T|+1)
   -> SA CONSTRUCTION (SA-IS, O(n))        <-> NAIVE SA ORACLE (test-only differential check)
   -> SA[0..n) feeds three branches:
        LCP (Kasai, PLCP, RMQ)  -> LRS / LCS / distinct substrings
        BWT (L[i] = T[SA[i]-1]) -> SUCCINCT LAYER (rank/select, WAVELET TREE, RRR) -> FM-INDEX
        SUFFIX AUTOMATON (DAWG) -> SAM queries (count, distinct, longest substring)
   FM-INDEX (C[], Occ(c,i), backward search -> interval [sp, ep))
        + sampled SA/ISA   -> LOCATE / EXTRACT
        + runs of the BWT  -> r-INDEX / RLBWT
 QUERY API: count | locate | extract | lrs | lcs | distinct   (serialized, mmap, shared Arc)
  1. Text source. The input text is immutable. One unique, smallest symbol $ (byte 0x00) is appended so that every suffix is distinct, and the alphabet can be remapped to a dense range (§3, §8.1, DP2, DP11).
  2. Suffix array construction (sufx-sa, module sais). It builds the sorted list of suffix positions in linear time and checks that the result is a permutation (§3, ADR-03, I1). The comparison-sort builder naive sits beside it, never shipped, as the oracle (§3, DP1).
  3. LCP branch (lcp, rmq). The array of "how many leading characters two neighbouring suffixes share" (LCP) plus a range-minimum structure imitates a suffix tree without its pointers, and answers longest-repeated-substring and distinct-substring queries (§3, §8.5, MM8).
  4. BWT branch (sufx-bwt). The Burrows–Wheeler transform (BWT) is the text rearranged in suffix-array order; it and the primary index are the only structures the self-index needs from the suffix array (§3, §8.7).
  5. Succinct layer (sufx-succinct). Bit vectors that answer "how many 1s before position i" in constant time with small overhead (rank/select), a wavelet tree that extends rank to larger alphabets, and an entropy-compressed bit vector (RRR) (§3, §8.11–§8.13).
  6. FM-index (sufx-fm, search). It narrows an interval of suffix-array rows one pattern symbol at a time, so count falls out as the interval width. It stores no plaintext (§3, §8.8).
  7. Sampling (sample, locate, extract). Only every s-th suffix-array value is kept; locate and extract walk back to a kept value (§3, §8.9, §8.10).
  8. Suffix automaton (sufx-sam). An independent structure that accepts exactly the substrings of the text, used as a second method for count, distinct substrings and LRS (§3, §8.15, DP12).
  9. r-index (sufx-rindex). For repetitive text it stores only the runs of the BWT; the build chooses it automatically when runs are few relative to length (§3, §8.14, ADR-14).
  10. Query API and file. The serialized index is versioned, length-prefixed and checked on load, then shared read-only as Arc<Index> across threads with no locks (§3, ADR-18, ADR-29, I18).

A query such as count("ana") touches box 6 and the succinct layer only: two rank queries per pattern symbol (§8.8). The CLI (sufx-cli) offers build, query, lrs, lcs, distinct, inspect and verify (§1, ADR-24).

The core ideas

Sorted suffixes turn substring search into a range (§8.2, §8.4, §8.6)

The suffix at position i is the text from i to the end. List the start positions in the order of the suffixes they point to. For banana$ (with $ smallest) the list is SA = [6,5,3,1,0,4,2]:

row SA[row] suffix LCP[row]
0 6 $ 0
1 5 a$ 0
2 3 ana$ 1
3 1 anana$ 3
4 0 banana$ 0
5 4 na$ 0
6 2 nana$ 2

LCP[row] is how many leading characters a suffix shares with the one above it (§8.4). Kasai's method computes it in one pass by carrying the running match length h forward and lowering it by at most one per step (h ← max(h−1, 0)), which bounds the total work at O(n) (§8.4). Two queries read off these arrays. The longest repeated substring is the one at the largest LCP value: 3, which is ana at positions 1 and 3. The distinct-substring count is Σ(n − SA[i]) − Σ LCP[i], which is 28 − 6 = 22 including substrings that contain $, and 15 without (§8.6).

SA-IS: sorting all suffixes in linear time (§8.3, ADR-03, MM2)

The method is induced sorting. Label each position S (its suffix is smaller than the next one) or L (larger), scanning right to left; equal neighbours inherit the next label (§8.3.1). For banana$ the labels are L S L S L L S. A position is LMS (leftmost-S) when it is S and the one before it is L, giving {1, 3, 6} here (§8.3.3). Then three passes: place the LMS suffixes at the ends of their symbol's slot range, sweep left to right inducing the L suffixes into slot fronts, sweep right to left inducing the S suffixes into slot ends (§8.3.2). The LMS stretches get names; if names repeat, the method recurses on the string of names. LMS positions are never adjacent, so each level has at most half the size, T(n) = T(≤ n/2) + O(n) = O(n) (§8.3.2). For banana$ the 7-position problem reduces to 3 LMS names before the final pass (§8.3.3).

The BWT and the LF-mapping: a rearranged text that is still the text (§8.7, MM3)

Write BWT[i] = T[(SA[i] − 1) mod n]: the character just before each sorted suffix. Let F be the first character of each sorted suffix, C[c] the number of symbols smaller than c, and Occ(c,i) the count of c in BWT[0..i). Then LF(i) = C[BWT[i]] + Occ(BWT[i], i) points to the row where the same text character appears as a first character (§8.7). For banana$, with C[$]=0, C[a]=1, C[b]=4, C[n]=5:

row BWT F LF
0 a $ 1
1 n a 5
2 n a 6
3 b a 4
4 $ b 0
5 a n 2
6 a n 3

LF is a bijection (I4). Following it from row 0 visits 0→1→5→2→6→3→4; the F symbols met along the way spell banana$ backwards, which is how the transform is inverted (§8.7, I5).

Backward search: the FM-index's whole trick (§8.8, DP8, MM5)

Process the pattern right to left, keeping a half-open interval [sp, ep) of suffix-array rows that start with the part of the pattern processed so far. Start with [0, n). For each symbol c, set sp ← C[c] + Occ(c, sp) and ep ← C[c] + Occ(c, ep), both computed from the old values. If sp ≥ ep the pattern is absent (§8.8, §8.16). For count("ana") on banana$:

step symbol new interval
start [0, 7)
1 a [1, 4)
2 n [5, 7)
3 a [2, 4)

count = ep − sp = 2 (§8.8). Each step is two rank queries, so the cost is O(m · t_rank) for a pattern of length m (§8.8, §4). Confusing an inclusive with an exclusive ep is failure class FC5, and the half-open interval is invariant I7 (§19, §7, DP8).

Locate and extract from samples (§8.9, §8.10, DP9)

The full suffix array is as large as the thing the FM-index is trying to avoid. So keep SA[i] only where SA[i] mod s == 0 (default s = 32), marked in a bit vector next to a packed array of the kept values (§8.9, ADR-13). To locate the occurrence at row i: if the row is unmarked, step i ← LF(i), count one step, and repeat; at a marked row the answer is sample + steps. That costs at most s steps per occurrence (§8.9, §4). With the full array, locate("ana") on banana$ is just SA[2]=3 and SA[3]=1 (§8.8); the sampled walk must return the same set (I11). extract(i,j) does the reverse: find the nearest sampled text position at or after j (kept as an inverse-array sample), then step LF backward emitting characters, for cost O((j − i + s) · t_rank) (§8.10). Raising s saves space and lengthens every locate; the knob is explicit in the index header (DP9).

Rank, wavelet trees, RRR and runs: where the space goes (§8.11–§8.14, MM4, MM6)

Everything above leans on rank: rank1(i) is the number of 1s in B[0..i). The design stores an absolute count every 512 bits and a relative count every 64 bits, then finishes with a hardware popcount on the partial word: rank1(i) = superblock[i/512] + block[i/64] + popcount(word[i/64] & ((1<<(i mod 64)) − 1)), about 0.25n bits of overhead (§8.11). A wavelet tree splits the alphabet in half at each node and stores a bit vector per node, each child recursing on its half, so Occ over a bigger alphabet costs O(log σ) steps of rank (§8.12). RRR cuts each block into a (class, offset) pair, where class is the number of 1s and offset names which pattern with that many 1s it is, trading a few table lookups per rank for space on compressible text (§8.13). When the BWT has far fewer runs of equal symbols than characters (r ≪ n), the r-index keeps run heads and lengths, suffix-array samples at run boundaries and a "toehold", for O(r) space (§8.14). The suffix automaton is independent of the suffix-array path and is not part of this chain (§3, §8.15).

The trade-offs — where engineers disagree

Construction algorithm: SA-IS (ADR-03)

Chosen: SA-IS, linear time with modest constants and the de-facto standard, with DC3 kept as a cross-check (§9, ADR-19). Rejected: DC3/skew, prefix doubling, qsufsort, divsufsort. When the rejected choice is right: DC3, when the port target is a data-parallel or GPU pipeline whose difference-cover recursion parallelizes more directly than SA-IS's sequential induced-sort passes (§9).

The end-of-text marker: a unique smallest 0x00 (ADR-05)

Chosen: append one unique 0x00, smallest, so the BWT inverts without a "primary index" workaround (§9, I3). Rejected: no sentinel plus a primary index, or 0xFF as largest. When the rejected choice is right: the primary-index scheme (as bzip2 uses), when no byte value can be reserved, such as indexing arbitrary binary data in which 0x00 is legitimate (§9).

Counting symbols in the BWT: wavelet tree plus a small-alphabet table (ADR-08)

Chosen: a wavelet tree for general alphabets and a direct Occ table for small ones; the build picks per alphabet size (§9, §8.12). Rejected: one bit vector per symbol always, or sampled counters only. When the rejected choice is right: a pure wavelet tree, when the alphabet is large and varies at runtime (a Unicode code-point alphabet) and two code paths are not worth the small-alphabet speedup (§9). The small-alphabet bound is stated as 64 in ADR-08 and as 256 in §8.12.

Bit vector representation: plain by default, RRR on request (ADR-10)

Chosen: plain popcount rank, fastest, with RRR behind a feature when space-bound (§9, §8.13). Rejected: always RRR, or the SD-vector only. When the rejected choice is right: RRR always, when the target is space-constrained above all else (a mobile or embedded read-only corpus index) and the roughly 3× rank slowdown is acceptable (§9, M9).

Repetitive text: switch to the r-index automatically (ADR-14)

Chosen: build the r-index when r/n < 0.3, otherwise the sampled-array FM-index (§9, §8.14). Rejected: always the FM-index, or always the r-index. When the rejected choice is right: always-FM-index, when counting BWT runs at build time is unwelcome, for example a streaming builder that cannot afford a second pass over the corpus (§9).

The suffix automaton's job: a checker, not the main path (ADR-15)

Chosen: use it as an oracle and for distinct/LRS, not for primary count (§9, I14). Rejected: SAM as the primary index, or a suffix tree. When the rejected choice is right: SAM as primary, in an online or streaming setting where the corpus grows incrementally and a full sort-based rebuild per update is unacceptable (§9).

Language: Rust (ADR-01)

Chosen: Rust, for C++-class bit control and bounded decoding of untrusted indexes (§9, §1). Rejected: C, C++, Go, Python, Zig. When the rejected choice is right: C++, when the team must share one codebase with existing SDSL-lite or divsufsort callers and cannot add a second toolchain (§9).

Roads not taken (§1, Alternative Architectures, Deferred Features Register)

Pointer-based suffix tree (AA1): wins for online construction where suffixes arrive one at a time and n is small (single genes). It is rejected because its roughly 20n-byte overhead is 5–10× the plain array at the targeted scales, and array + LCP + RMQ already answer the queries needed (§8.5).

Suffix automaton as primary index (AA2): wins for streaming corpora and dictionary-compression parsing. It is rejected because the corpus here is static and the sort-based path is smaller and compressible; the automaton stays as an oracle (ADR-15).

k-mer hash seed index, BLAST-style (AA3): wins for approximate seed-and-extend search. It is rejected because the contract is exact count, locate and extract, which a fixed-k table cannot answer for other pattern lengths (§1).

External-memory construction (AA4): wins when the corpus exceeds RAM, where in-memory SA-IS cannot run. It is rejected as a larger project than this budget covers, and deferred along with approximate search, dynamic updates, multi-document listing, GPU rank, circular/2D structures and the constant-workspace builder, each with a trigger in the register (Deferred Features Register).

What must never be false

Each line gives the rule, how the system notices, and the telemetry name (all from §7).

  • I1: every text position appears exactly once in the suffix array. O(n) sweep; inv_violation{id=I1}.
  • I2: suffixes are in strictly increasing order. Differential vs naive; inv_violation{id=I2}.
  • I3: the sentinel is unique, 0x00, smallest. Scan for 0x00, assert SA[0] == n−1; sentinel_reject.
  • I4: LF hits every row exactly once. O(n) coverage check; inv_violation{id=I4}.
  • I5: inverting the BWT returns the text. Round trip at build; bwt_roundtrip_fail.
  • I6: LCP values are right and LCP[0] = 0. Naive cross-check on samples; inv_violation{id=I6}.
  • I7: the search interval stays half-open, sp ≤ ep ≤ n. Assertion each step; interval_underflow.
  • I8: rank1(i) is exactly the count of 1s before i. Brute force on random i; inv_violation{id=I8}.
  • I9: rank and select are consistent inverses. Property test; inv_violation{id=I9}.
  • I10: C[] is correct and non-decreasing. Recompute from BWT symbol counts; c_table_mismatch.
  • I11: locate returns exactly the naive position set. Differential vs naive; locate_mismatch.
  • I12: extract(i,j) equals T[i..j]. Differential vs the source text; extract_mismatch.
  • I13: automaton has ≤ 2n−1 states, ≤ 3n−4 transitions. Assert after build; sam_size_violation.
  • I14: both distinct-substring counts agree. Compare on every conformance text; distinct_mismatch.
  • I15: r-index run count is the BWT's true run count, lengths sum to n. Recompute; run_count_mismatch.
  • I16: arithmetic is width-checked, no u32 overflow. Overflow tests near 2^32; width_overflow.
  • I17: save then load gives the same structure. Round-trip test per structure; serde_roundtrip_fail.
  • I18: the index is immutable and Send + Sync. Compile-time assertion; no telemetry.

What breaks in production

The blueprint names these failure classes FC1–FC13 (Failure Modes & Recovery), not FM-n.

  • FC1: construction defect. Symptom: count and locate are wrong on a large corpus but right on small tests. Cause: a bucket-pointer bug in the induced sort. Detection: the I1 permutation sweep and differential runs against the naive builder and DC3. Recovery: the build is rejected when invariant-checks is on; sufx verify --stage sa (Failure Modes & Recovery, DP1, ADR-19).
  • FC3: rank/select corruption. Symptom: plausible but wrong counts. Cause: a superblock or block indexing bug. Detection: the brute-force rank fixture (I8) and count differentials. Recovery: rebuild the rank index in O(n) (Failure Modes & Recovery).
  • FC5: off-by-one in backward search. Symptom: counts are off by exactly one. Cause: mixing up inclusive and exclusive ep. Detection: count-versus-naive differential (I7). Recovery: no automatic one; sufx inspect --search prints the interval trace (Failure Modes & Recovery).
  • FC6: locate sampling bug. Symptom: positions off by a constant, missing, or an endless walk. Cause: marking or step arithmetic. Detection: locate-versus-naive (I11) and a walk-step cap of s+1 (T8). Recovery: manual, via sufx inspect --samples and rebuilding samples (Failure Modes & Recovery, §20).
  • FC9: RRR decode bug. Symptom: wrong answers only with --compress rrr. Cause: an error in a binomial or offset table. Detection: RRR-versus-plain parity and count differential. Recovery: fall back to --compress none and rebuild (Failure Modes & Recovery).
  • FC10: r-index toehold bug. Symptom: wrong or missing positions only on repetitive text. Cause: the toehold bootstrap or run-boundary samples. Detection: r-index versus naive and versus FM-index. Recovery: force --index fm while debugging (Failure Modes & Recovery, §8.14).
  • FC11: malformed index on load. Symptom: a typed IndexError, not a crash. Cause: truncation or tampering on disk. Detection: bounds checks on load and a fuzz target index_load. Recovery: reject the load and report the field or version (Failure Modes & Recovery, DP7).
  • FC13: space-budget regression. Symptom: overhead exceeds the o(n) or O(r) budget. Cause: constant drift in rank, select or RRR. Detection: space_breakdown against a budget fixture. Recovery: profile the structure and revert the change (Failure Modes & Recovery, DP5).

Threats a reader should know (Threat Model): T1, an index that declares more rows than the buffer holds, answered by checking every length against the buffer first and returning IndexError::Truncated (DP7). T4, out-of-memory from a pattern that occurs everywhere or a huge extract range, answered by allocating exactly the output size and range-checking (DP13). T5, a "decode bomb" of crafted offsets that forces huge loops in RRR or wavelet decoding, answered by bounding decode by structure size and fuzzing rrr and wavelet. T8, a non-terminating LF walk from a marking bug, answered by step caps and an assertion. T9, supply-chain compromise of a crate or the test corpus, answered by cargo deny/audit, pinned checksums and a pinned lockfile.

The capacity rows are arithmetic from stated inputs. Items 5 and 7 rest on assumed ratios (H_k ≈ 2, r/n = 0.01) that the blueprint calls "representative" (Capacity Model items 5 and 7). Item 11 is explicitly "not a hard derivation" (Capacity Model item 11).

How it compares

  • SDSL-lite chose to be a general C++ toolbox of succinct building blocks rather than one opinionated engine. That is fine for a research team assembling many self-index variants quickly who can accept header-only template compile costs (Comparative Architecture Table, R3).
  • BWA / Bowtie2 specialize the FM-index to a fixed 2-bit DNA alphabet and an aligner workload. That is fine when the alphabet is small and known and the real query is approximate seed-and-extend matching, not exact substring indexing (Comparative Architecture Table, R4, R5).
  • bzip2 uses the BWT only for compression and adds no rank, select or search layer. That is fine when the goal is storage reduction with sequential decompression and no queries at all (Comparative Architecture Table, R9).
  • Apache Lucene indexes words and documents with ranked retrieval, not every position. That is fine when queries are word or phrase searches with relevance ranking (Comparative Architecture Table, §2).

Questions to test yourself

  1. Why must the sentinel be both unique and the strictly-smallest symbol, and what specifically breaks in LF-mapping invertibility if either property is dropped? (§8.1, DP2, I3) — Hint: §8.1 and §8.7, then ADR-05's note on the alternative.
  2. What would go wrong with backward-search correctness if Occ used BWT[0..=i] (inclusive) instead of BWT[0..i) (exclusive) semantics, and where is this locked down in the phase plan? (§8.8, §19 Pitfalls) — Hint: §8.8 and §8.16 on pre-update values; DP8 and FC5.
  3. Contrast the space/time tradeoff of the SA sample rate s with the RRR block size t: both trade space for time, but along which different axes? (§8.9, §8.13, DP9) — Hint: §8.9 (what grows with s) against §8.13 (what the block size changes); §4 for s.
  4. Why can't the plain sampled-SA locate scheme be reused unmodified for the r-index's locate, and what does the toehold mechanism replace? (§8.9, §8.14, §23) — Hint: §8.14 on where the first known SA value comes from, set against §8.9's walk.
  5. Using the Back-of-Envelope Capacity Model, explain why a 4.29 GB genomic corpus is a reasonable single-machine target for the plain FM-index, but would strongly favor the r-index if it were a pan-genome collection instead. If you only remember three things

Sorting all suffixes turns "find this pattern" into "find this range", and the BWT with backward search does that range search from a rearranged copy of the text that need not be stored in plain form (MM1, MM3, MM5). Space is a spectrum, and the design lets you choose the point (plain, RRR, r-index, sample rate s) that matches how compressible or repetitive the corpus is (MM6, DP9). Because a subtly wrong index still returns plausible answers, every structure is checked against an independent second method, and the index file is treated as untrusted input (MM7, DP1, DP7).

Words used here

  • Suffix array (SA): the list of start positions of all suffixes, in sorted order of the suffixes.
  • Sentinel $: a unique, smallest end marker appended once so every suffix is distinct.
  • LCP array: for each row, how many leading characters it shares with the previous row.
  • SA-IS: the linear-time suffix sorting method that classifies suffixes S or L and induces order.
  • BWT: the character before each sorted suffix; a rearrangement of the text that can be undone.
  • LF-mapping: the rule sending a BWT row to the row of the same text character in the first column.
  • FM-index: BWT plus counting tables, searchable without the text.
  • Backward search: narrowing a row interval [sp, ep) one pattern symbol at a time, right to left.
  • Occ(c,i): how many times symbol c appears in the BWT before position i.
  • Rank / select: count the 1s before a position, and find the position of the j-th 1.
  • Wavelet tree: a binary tree over the alphabet that gives rank for any symbol in O(log σ).
  • RRR: a bit vector compressed by block class and offset, still answering rank quickly.
  • Sample rate s: how sparsely suffix-array values are kept; larger means smaller index, slower locate.
  • r-index: an index sized by the number of BWT runs r, for highly repetitive text.
  • Suffix automaton: the smallest machine accepting exactly the text's substrings; the cross-check here.
