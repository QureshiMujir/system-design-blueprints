55 — CRDT System

Project Number: 55

Project Name: CRDT System

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade library of Conflict-Free Replicated Data Types in Rust, with state-based and delta-state semantics at the center, an op-based bridge for streaming workloads, causality tracked by vector clocks, dotted version vectors, Lamport timestamps and hybrid logical clocks, anti-entropy via Merkle-tree diff, gossip-based dissemination over a pluggable transport, persistence on an append-only log plus snapshots, and bindings for the browser (WASM) and Python (PyO3).

The library implements the full canonical CRDT zoo — G-Counter, PN-Counter, G-Set, 2P-Set, OR-Set, LWW-Register, MV-Register, RGA / WOOT / Logoot for sequences, a Yjs / Y.Map-shaped tree CRDT, and an Automerge-shaped JSON CRDT — and ships them with property-based tests for commutativity, associativity, and idempotence, plus Jepsen-style chaos tests for partition behaviour.

In scope. The algebraic primitives (no_std-friendly); the causality module; the canonical CRDT set; delta-state encoding; in-memory + libp2p transport; Merkle anti-entropy and gossip dissemination (reusing workspace projects); WAL+snapshot persistence (reusing the WAL project); WASM and PyO3 bindings; a conformance harness; a Jepsen-style chaos suite.

Out of scope (deferred — see Deferred Features Register). Yjs / Automerge wire-byte compatibility; rich-text spans; a C ABI; a hosted sync control plane; encrypted CRDTs; differential-dataflow bridges; columnar change encoding. The library mirrors Yjs/Automerge document shape only; it does not promise wire-compatibility.

Estimated effort. 4–6 months for the full plan; 4–6 weeks for a Phase-0 drop shipping the causality primitives, counter and set CRDTs, an RGA sequence, the delta-state codec, an in-memory replication harness, and the conformance suite.

Language. Rust 1.78+ for the core, wasm-bindgen for the browser binding, pyo3 for the Python binding. The algebraic core is no_std-friendly; std is used at the transport, persistence, and gossip boundaries.

Prerequisites. Distributed-systems vocabulary (consistency, causality, partition tolerance, eventual consistency, strong eventual consistency); Rust at the level of knowing why Pin exists and when to reach for Arc<RwLock<T>> vs Arc<Mutex<T>>; the algebra of join-semilattices (commutative, associative, idempotent merge); enough concurrency theory to know what a vector clock is and why it is not a Lamport timestamp.

2. Why Build This

Every collaborative product on the modern internet is, secretly, a CRDT product. Figma's multi-user canvas is a tree CRDT with custom conflict semantics on layer ordering. Linear's offline-first issue tracker is an OR-Set of issues with an LWW-Register on each field. Notion's blocks are a Yjs-shaped tree with presence on top. Replicache and PowerSync are general-purpose sync engines whose internal model is an op-based CRDT plus a server-side authority for conflict resolution. The CRDT toolkit is the set of primitives the entire industry leans on — and almost nobody has built one end to end. The few that have (Yjs, Automerge, Riak's data types, AntidoteDB, Bayou) are the only places where the tradeoffs between state, op, and delta encodings are legible at the source level.

This project teaches the full CRDT surface by implementing it from the algebraic primitives upward. You start with vector clocks because nothing else makes sense without them. You then implement the simplest CRDTs — G-Counter, PN-Counter, G-Set, 2P-Set — because their algebra is small enough to prove the merge laws on paper and transcribe the proof into property-based tests. Once you trust the primitives, you move to the harder shapes: OR-Set with observed-remove semantics, LWW-Register with its surprising edge cases when clocks go backwards, MV-Register where the merge keeps both values, and finally the sequence CRDTs (RGA, WOOT, Logoot) where the design space is wide and the right choice depends on the workload. By the time you implement the JSON and tree CRDTs, you have built every piece you need to compose them.

The deliverable is tightly bounded. We implement the canonical set that covers the canonical workloads (collaborative text, shared whiteboard, offline-first sync, distributed counters), not every CRDT in the literature. We ship libp2p as the default transport with WebSocket and gRPC as documented alternatives behind one trait. We ship vector clocks and dotted version vectors as the workhorses, with Lamport and HLC for the cases where they fit better. The result is small enough to read in an afternoon, complete enough to back a production sync engine, and rigorous enough that the merge laws are checked by proptest on every push.

You build this so that when a collaborative product ships and the conflict resolution starts producing surprises in production, you know which page of which paper to open and which line of which CRDT to fix.

What Mastery Looks Like

  • You can prove the three merge laws (commutativity, associativity, idempotence) on paper for any CRDT in the library and transcribe the proof into a proptest! strategy. — Phase 2, Phase 3.
  • You can explain why causality is a CRDT input, not a CRDT field, and swap a vector clock for a dotted version vector without touching a single primitive. — Phase 1, P3.
  • You can read a delta off the wire, identify the version byte, and predict exactly which MergeError a malformed body produces. — Phase 7, §8.
  • You can choose between RGA, WOOT, and Logoot for a given workload from first principles (insert burstiness, document lifetime, adversarial-position risk). — Phase 5.
  • You can run anti-entropy and gossip side by side and articulate why one catches up while the other keeps the steady state close. — Phase 8, Phase 9.
  • You can name the exact precondition (causal stability) under which a tombstone may be GC'd and the resurrection bug that appears if you GC early. — Phase 3, §7 I4.
  • You can identify, from a divergence incident, whether the bug is in the algebra, the codec, the transport, or the storage layer — because the architecture keeps them separable. — §3, Failure Modes.

Application layer. Three consumer kinds — native Rust crates, browser WASM modules, and Python server processes — all reach the same Crdt trait surface. They never see merge internals.

Document layer (Phase 6). A Document is a keyed map from string to CRDT. It owns the causality clock, exposes snapshot and encode/decode, and is the only object that allocates dots. This is the composition boundary.

CRDT primitives (Phases 2–6). Every CRDT implements one trait (Crdt, §11) exposing merge, delta_since, apply_delta, encode_state, decode_state. The trait is the contract every other layer talks to.

Causality primitives (Phase 1). A standalone module. A CRDT does not embed a clock; it accepts one and is told which dot it operates under. This separation lets us swap causality schemes without touching the primitives.

Sync layer (Phases 8–9). Anti-entropy (Merkle diff) catches replicas up; gossip keeps the steady state close. Both are pure transports for delta encodings; neither knows what CRDT a delta belongs to.

Transport (Phase 8). A Transport trait with four backends. The CRDTs do not know which transport runs.

Persistence (Phase 10). WAL + snapshot. A CRDT does not know whether it is merged from disk, a peer, or a delta on the wire. The merge law is the merge law.

Bindings (Phase 11). Thin wrappers. The Rust core is the single source of truth; bindings re-implement no merge logic.

Three load-bearing properties recur throughout: (1) the algebra is the contract; (2) causality is a separate module from the CRDTs; (3) sync and storage layer on top, never below.

6. Design Principles

Twelve principles every CRDT, encoding, and API surface has been negotiated against. Each: the rule, the tradeoff, and how violating it breaks the system.

  • P1 — Strong eventual consistency is the contract. Every CRDT satisfies SEC: replicas that observed the same updates converge regardless of order, duplication, delay. Tradeoff: no global total order; the application must accept multi-value outcomes for some types. Violation: if any merge is not commutative-associative-idempotent, replicas silently diverge and no amount of re-sync converges them.
  • P2 — State-based and delta-state are first-class; op-based is a bridge. Center of mass is state-based merge; delta-state is the wire encoding; op streams are lifted into delta sequences. Tradeoff: we do not invest in the at-most-once delivery story op-based CRDTs need. Violation: mixing op-based delivery into the core forces exactly-once semantics onto the transport, which it cannot guarantee.
  • P3 — Causality is a CRDT input, not a CRDT field. The document owns the clock and tells the CRDT which dot a mutation uses. Tradeoff: one extra parameter on every mutating call. Violation: embedding a clock per CRDT makes swapping causality schemes a rewrite and couples merge to clock representation.
  • P4 — Tombstones are observable until they are stable. OR-Set, 2P-Set, and sequence CRDTs carry tombstones; GC happens only after causal stability across all known replicas. Tradeoff: memory grows until stability. Violation: GC before stability resurrects deleted elements when a lagging peer delivers its add.
  • P5 — The wire format is versioned and validated. Every encoded state/delta carries a version byte; the decoder rejects unknown versions. Tradeoff: a forced version bump on every schema change. Violation: an un-versioned decoder mis-parses a newer payload and corrupts state silently.
  • P6 — No silent fallbacks on conflict. A CRDT that cannot merge (corrupt wire, unknown dot, schema mismatch) returns Err(MergeError::*). Tradeoff: callers must handle errors. Violation: silently choosing one side or zeroing the conflict produces data loss invisible to the application.
  • P7 — The transport is pluggable. In-memory (tests), libp2p (default), WebSocket/gRPC behind the trait. Tradeoff: a trait indirection on every send. Violation: a CRDT that knows its transport cannot be tested in-memory and cannot be redeployed across networks.
  • P8 — Persistence is WAL + snapshot, reused not reinvented. Write deltas to the workspace WAL (rank 69); flush snapshots periodically; recover by replaying the log onto a snapshot. Tradeoff: a cross-project dependency. Violation: a bespoke storage format duplicates the WAL's durability bugs and divergent fsync discipline.
  • P9 — Bindings are thin. WASM and PyO3 expose the same trait surface with idiomatic host types; no re-implemented merge. Tradeoff: host code crosses the FFI boundary for every op. Violation: a binding that re-implements merge introduces a second, divergent algebra.
  • P10 — Determinism in tests, controlled randomness in chaos. Merge laws checked with proptest and a fixed seed; chaos uses a recorded seed. Tradeoff: chaos failures need the seed to reproduce. Violation: un-seeded randomness yields flaky, irreproducible failures that erode trust in the suite.
  • P11 — The algebra is no_std-friendly. Causality and primitives avoid std where possible. Tradeoff: some ergonomic types (e.g. HashMap) become BTreeMap. Violation: pulling std into the algebra blocks embedded and WASM-minimal deployments.
  • P12 — Identifiers are stable for a replica's lifetime. ReplicaId is generated once and persisted in the snapshot. Tradeoff: a replica that loses its id must rejoin as a new participant. Violation: reusing or rotating a ReplicaId breaks dot uniqueness and the vector-clock algebra, producing convergence failures.

These are enforced at the type level where possible, by code review where not.

8. Domain Model / Protocol / Data Model

The domain object is the delta: a self-describing, versioned, schema-tagged byte payload that carries a join-semilattice element. Everything on the wire and in the WAL is a delta.

8.1 Wire layout (delta envelope)

byte 0      : version   (u8)   — currently 1; decoder rejects unknown (I7)
byte 1      : kind       (u8)   — 0=GCounter 1=PNCounter 2=GSet 3=2PSet
                                  4=ORSet 5=LWW 6=MV 7=RGA 8=WOOT 9=Logoot
                                  10=JsonMap 11=JsonArray 12=Document
bytes 2..6  : body_len   (u32 LE)
bytes 6..   : body              — zstd(level 3) over bincode(payload)

8.2 Worked example — OR-Set "add then concurrent remove + re-add"

Replicas A (id 1) and B (id 2). Start empty.

  1. A: add("x") → dot (1,1). State A: {x: {(1,1)}}.
  2. A → B sync. Both: {x:{(1,1)}}.
  3. Concurrently: A remove("x") (removes observed dot (1,1)); B add("x") → dot (2,1).
  4. A state: {}. B state: {x:{(1,1),(2,1)}}.
  5. Merge A into B: B already has (1,1); A's remove only tombstoned the observed (1,1). The concurrent (2,1) survives. Result: {x:{(2,1)}} — add wins, "x" is present.

This is the observed-remove rule (I4, P4): remove acts only on dots the remover had observed.

8.3 State-transition table (OR-Set element lifecycle)

Current Event Next Notes
absent add (dot d) live {d} fresh dot allocated
live {d…} add (dot d′) live {d…,d′} union of dots
live {d…} remove absent (tombstone the observed dots) only observed dots removed
absent (tombstoned) concurrent add d′ live {d′} re-add survives — d′ unobserved by remover
live {d…} gc(stable) where all d ∈ stable live (dots compacted) I4 precondition

8.4 Malformed-input handling

Input Decoder result
empty buffer MergeError::BadWire("empty")

kind not matching expected CRDT MergeError::SchemaMismatch{expected,actual}
body_len exceeds buffer MergeError::BadWire("truncated")

8.5 Failure path

On any decode error the delta is not applied; the receiver returns the typed error up the stack (I8), increments wire.decode.error{kind}, and the sync layer either retries (transient/truncated) or asks the sender to downgrade (version/schema). State is never partially mutated: decode fully precedes apply.

8.6 Worked example — vector-clock causality and the concurrency verdict

Two replicas A (id 1) and B (id 2), each performing two local updates and one cross-merge.

Step Actor Action VC(A) VC(B) partial_cmp(A,B)
0 — start {} {} Equal
1 A tick {1:1} {} Greater
2 A tick {1:2} {} Greater
3 B tick {1:2} {2:1} None (concurrent)
4 A→B B merges A {1:2} {1:2,2:1} Less
5 B tick {1:2} {1:2,2:2} Less

The verdict at step 3 is the load-bearing one: A and B have each made progress the other has not seen, so the clocks are concurrent and partial_cmp returns None (I9). Any code that .unwrap()s here mis-reads concurrency as an ordering and silently drops a write — the exact bug MM2 predicts. After the merge at step 4, B's clock dominates A's, so Less is well-defined again.

8.7 Decision table — which set CRDT for which requirement

Requirement G-Set 2P-Set OR-Set Choice
add only, never remove ✓ ✓ ✓ G-Set (smallest)
remove, never re-add — ✓ ✓ 2P-Set (no dot overhead)
remove then re-add the same value — ✗ ✓ OR-Set
concurrent add/remove must favour add — ✗ ✓ OR-Set
bounded memory without GC ✓ ✗ (tombstones) ✗ (dots) G-Set, else GC at stability

Picking 2P-Set where re-adds are required is the single most common production set-CRDT bug; it surfaces exactly when a user re-adds something they previously deleted and the operation silently no-ops (Phase 3 pitfall, MM4).

8.8 Worked example — JSON document concurrent edit

Document root is a JsonMap. Replicas A and B both edit /profile.

  1. Initial (both synced): { "profile": { "name": "Ada", "tz": "UTC" } }.
  2. Concurrently: A sets /profile/name = "Ada L." (HLC t=10@A); B sets /profile/tz = "PST" (HLC t=11@B).
  3. The two writes touch different keys of the same JsonMap, so they merge cleanly: { "profile": { "name": "Ada L.", "tz": "PST" } }.
  4. Now suppose both instead write /profile/tz: A→"EST" (t=12@A), B→"PST" (t=12@B). Same key, equal HLC. The LWW tiebreak (timestamp, replica) (I10) breaks the tie by replica id: B (id 2) > A (id 1), so "PST" wins on every replica deterministically.

This is why same-path conflicts need a total order on writes (I10) while different-path edits need none (they commute by construction, I14).

11.2 The CRDT trait

/// Contract every CRDT implements. The merge law (I1–I3) is verified per impl
/// by the proptest harness. `State` is implicit (Self); `Delta` is the
/// delta-state representation; both round-trip through encode/decode.
pub trait Crdt: Sized + Clone + Eq {
    type Delta: Clone;
    type Error: std::error::Error;

    fn merge(&mut self, other: &Self);
    fn apply_delta(&mut self, delta: &Self::Delta) -> Result<(), Self::Error>;
    fn delta_since(&self, since: &VersionVector) -> Self::Delta;
    fn encode_state(&self) -> Vec<u8>;
    fn decode_state(bytes: &[u8]) -> Result<Self, Self::Error>;
    fn encode_delta(delta: &Self::Delta) -> Vec<u8>;
    fn decode_delta(bytes: &[u8]) -> Result<Self::Delta, Self::Error>;
    /// GC history that is causally stable (observed by every replica in `stable`) — I4.
    fn gc(&mut self, stable: &VersionVector);
}

13. Phase 1 — Causality Primitives

13.1 Objectives

Implement the causality module: vector clock, version vector, dotted version vector, Lamport timestamp, HLC, and the causal-stability marker. Every later CRDT depends on these (P3). Constraint introduced: causality types must be no_std-friendly (P11) — BTreeMap, not HashMap.

13.2 Detailed Implementation Steps

Theory: vector clocks (Lamport 1978, §5 #10); DVVs (Almeida 2014, §5 #9); HLC (Kulkarni 2014, §5 #11). Enforces I5 (dot uniqueness), I6 (1-indexed ticks), I9 (None iff concurrent). Applies P3, P11, P12. Types per §11.3: VectorClock, VersionVector, DottedVersionVector, LamportTimestamp, HybridLogicalClock, is_stable; HlcError::SkewExceeded when skew exceeds MAX_SKEW_US.

  1. VectorClock: tick increments per-replica counter and returns it (1-indexed, I6); merge is per-key max; partial_cmp walks both maps tracking self_lt/other_lt and returns Equal/Less/Greater/None (I9).
  2. VersionVector: same internal map; observe(dot) raises the per-replica tick if greater; contains(dot) compares; diff(since) yields every dot above the since watermark per replica.
  3. DottedVersionVector: observe inserts the dot then compact repeatedly pulls every dot contiguous with base[replica]+1 into the base until none remain — order-independent by construction (ADR-03).
  4. LamportTimestamp: local := max(local, incoming) + 1 on observe (§5 #10).
  5. HybridLogicalClock: tick advances physical or bumps logical; observe takes max(self.phys, remote.phys, now), returns SkewExceeded if the bound is exceeded, else updates per Kulkarni (§5 #11).
  6. is_stable(dot, peers): true iff every peer VV contains(dot) — precondition for GC (I4, Phase 3).

HLC update rule (Kulkarni 2014), precisely. On a local event with wall-clock reading now: pt = max(physical, now); if pt == physical then logical += 1 else { physical = pt; logical = 0 }. On observing a remote HLC r with wall-clock now: pt = max(physical, r.physical, now); the new logical is 0 if pt strictly exceeds both old physicals, max(logical, r.logical) + 1 if pt equals both, logical + 1 if pt equals only the local physical, r.logical + 1 if pt equals only the remote physical. If pt − now > MAX_SKEW_US, return SkewExceeded (Threat #10). The logical component preserves causal correctness when two events share a physical-microsecond bucket; the physical component keeps the timestamp human-readable and roughly monotone — why HLC is the LWW default (Phase 4, P3) over a pure Lamport timestamp.

13.6 Pitfalls

  • Off-by-one in tick (first tick is Tick(1), I6).
  • Calling .unwrap() on partial_cmp of concurrent clocks (I9, MM2).
  • Keying a clock by anything but a stable ReplicaId (P12).

13.7 Performance Concerns

VectorClock/VersionVector are BTreeMap<ReplicaId,u64> — tick, merge, partial_cmp all cost O(N replicas); for the common N ≤ 100 case this is sub-microsecond, but a client-server topology with thousands of ephemeral client replicas inflates every clock comparison — the motivation for DVV (ADR-03), which bounds cost by concurrent dot count, not total ever-seen replicas. HybridLogicalClock::tick costs one clock_gettime syscall (~20–40 ns) per event; this is irreducible per-event cost since batching ticks would violate I6's strict per-event ordering.

13.8 Edge Cases

  • Two replicas tick with an identical wall-clock reading — HLC's logical component disambiguates, no lost update.
  • A ReplicaId reused after a replica restarts with no persisted identity (P12 violation) — dot uniqueness (I5) breaks silently until caught by conformance.
  • Clock skew exceeding MAX_SKEW_US mid-session — observe returns SkewExceeded; the write is rejected, not silently accepted (Threat #10).
  • VersionVector::diff(since) against a since watermark from a never-before-seen replica — treated as watermark Tick(0), yields the full history for that replica.
  • DVV compact racing a concurrent observe on the same struct — impossible by construction: the API requires &mut self, so the type system forbids concurrent mutation.

13.9 Failure Analysis

A miscomparison in partial_cmp (e.g. an .unwrap() on a None) is the highest-blast-radius bug class in the library: every merge law built on causality (I1–I3) and every downstream CRDT inherits it silently. Detection is a proptest concurrency-property failure with a minimal shrunk counterexample (Testing & Verification Strategy). Containment: the causality module boundary (§3) means a bad clock corrupts a merge decision, never CRDT storage directly — the algebra stays inspectable. Recovery is a code fix plus a full conformance re-run; replicas that already diverged from this bug need a forced anti-entropy re-sync (Phase 8) post-fix, since no persisted state is itself corrupted, only past merge outcomes.

13.10 Operational Notes

14.6 Pitfalls

  • Storing decrements in one G-Counter (breaks the join-semilattice — merge is no longer a valid join once subtraction enters the per-key max).
  • Returning i64::MAX for an empty PN-Counter (must be 0 — an unsigned-underflow-adjacent bug).
  • Merging p but forgetting n (asymmetric merge breaks I1/I2 for the composite type).

14.7 Performance Concerns

GCounter::merge is O(N replicas) per-key max over two BTreeMaps — at M1's target (≥5 Mops/s single replica, no I/O) this bounds N: a 4-replica merge touches ≤4 keys → ≤200 ns budget per merged key (Back-of-Envelope Capacity Model #4). value() sums the whole map — O(N) — called on every read; cache it if reads dominate writes (not done in Phase 2; deferred optimisation if profiling shows it matters).

14.8 Edge Cases

  • Merging a GCounter with a PnCounter of the same logical counter — rejected via SchemaMismatch (I14) at the Document composition boundary (Phase 6), not silently coerced.
  • A replica double-applies its own historical delta (should be a no-op, I3) — verified by the double-apply proptest case.
  • Integer overflow on u64 count after 2⁶⁴ increments from one replica — theoretically unreachable at any realistic write rate (M1's 5 Mops/s would take ~117,000 years), documented rather than defended against.
  • A delta for a replica never before observed — merged in as a fresh key, no special-casing needed (per-key max on an absent key is the incoming value).

14.9 Failure Analysis

A broken GCounter::merge (e.g. sum instead of max) fails silently until the property harness catches it, because a single-replica or non-adversarial ordering can still look correct — this is precisely why the CAI property suite (not just example-based tests) gates this phase (Testing & Verification Strategy). Blast radius if it ships: every counter-shaped feature (distributed like-counters, Phase 12) double-counts under replay. Detection is the proptest counterexample or a conformance byte-mismatch; recovery is a code fix — no persisted state needs repair since counters have no tombstones to reconcile.

15. Phase 3 — Set CRDTs (G-Set, 2P-Set, OR-Set)

15.1 Objectives

Implement the three canonical set CRDTs, introducing tombstones (2P-Set) and observed-remove dots (OR-Set) as the first types with delete semantics. Constraint introduced: GC (compaction) is gated on causal stability (I4) from this phase forward.

15.2 Detailed Implementation Steps

Theory: Shapiro 2011 (§5 #7); Riak DT (§5 #20) for the production OR-Set. Verifies I4 (stability before GC) and the add-wins-on-concurrency rule (§8.2). Applies P4. Types (§11):

pub struct GSet<T: Ord> { /* BTreeSet<T> */ }     // add; merge = union; no remove
pub struct TwoPSet<T: Ord> { /* add: GSet<T>, tomb: GSet<T> */ }
                                                  // contains = add ∧ ¬tomb; removes permanent
#[derive(Clone, Eq, PartialEq, Debug, Default)]
pub struct OrSet<T: Ord + Clone> { /* elements: BTreeMap<T, BTreeSet<Dot>>, clock: VectorClock */ }
impl<T: Ord + Clone> OrSet<T> {
    pub fn add(&mut self, replica: ReplicaId, value: T) -> Dot;  // fresh dot
    pub fn remove(&mut self, value: &T);                         // remove observed dots only
    pub fn contains(&self, value: &T) -> bool;
}
  1. G-Set: add inserts; merge is union; no remove.
  2. 2P-Set: two G-Sets; contains = add.contains ∧ ¬tomb.contains; remove is permanent (re-add is a no-op) — ship the canonical variant (§8.7 decision table).
  3. OR-Set: add allocates a fresh dot via the clock (Phase 1, P3) and inserts (value,{dot}); remove deletes the currently-observed dots for the value; merge is element-wise union of dot sets minus dots tombstoned by either side (carry the observed-but-dead dot set alongside state per the paper). gc(stable) compacts dot sets once all dots are in stable (I4).

The OR-Set merge, precisely. The naive "union the dot sets" is wrong: it would resurrect removed elements. The correct merge needs each replica's causal context — the version vector of everything it has observed. For each element, the merged live dot set is (dotsₐ ∪ dots_b) minus any dot that is in the other replica's causal context but absent from its dot set (meaning the other replica observed and then removed it). Concretely: if B's context covers dot d but B's dot set for the element does not contain d, then B removed d, so d is dropped from the merge even though A still lists it. This is the mechanism that makes "concurrent add wins" fall out automatically (§8.2, MM4): a concurrent add carries a dot outside the remover's context, so it is never dropped. Shipping the causal context alongside the dot sets is the cost OR-Set pays over 2P-Set (ADR-02), and it is why OR-Set deltas (Phase 7) include the relevant context slice, not just the changed dots.

15.3 Deliverable

15.4 Acceptance Criteria

15.6 Pitfalls

  • Using 2P-Set where re-adds are needed (§8.7 decision table; the single most common production set-CRDT bug, MM4).
  • Dot reuse across replicas (I5).
  • GC before causal stability → resurrected elements (I4, P4, FM-2).

15.7 Performance Concerns

OR-Set merge is O(E · dots) where E = live elements and dots = concurrent writers per element (Scalability Analysis) — dominated by per-element BTreeSet<Dot> union/difference, not by hashing or allocation, since dot sets stay small in non-adversarial workloads. Memory before GC can reach 8× live-state size (§4) because every add/remove pair leaves a dot until stability; this is the direct cost of P4 (tombstones observable until stable) and is why gc(stable) throughput matters as much as merge throughput at scale.

15.8 Edge Cases

  • Concurrent add and remove of the same value from different replicas — resolves to add-wins (§8.2 worked example) by construction, not by a special case.
  • A replica's causal context claims to have observed a dot it never actually added (malformed/adversarial peer) — MergeError::UnknownReplica or a dot-uniqueness conformance failure surfaces it (I5).
  • 2P-Set attempted re-add after remove — silently absorbed as a no-op by design (not a bug; §8.7 documents this as the reason to choose OR-Set instead when re-adds matter).
  • gc(stable) called with a stable vector that omits a live replica — under-approximates stability, which is safe (merely defers GC) rather than unsafe (never resurrects); the failure direction is deliberately conservative.

15.9 Failure Analysis

Early GC (violating I4) is the phase's signature failure: a lagging peer later delivers an add whose dot predates the GC boundary, and the receiving replica cannot distinguish "concurrent add that should survive" from "already-GC'd history" — the element silently reappears (FM-2). Detection is the chaos partition+GC scenario (§15.5) or, in production, an unexpected crdt.tombstone.count drop followed by an element re-appearing without a corresponding add in the application's own audit log. Recovery is re-merging from every replica that still holds the pre-GC dot set and reinstating the stability precondition before the next GC cycle; blast radius is contained to elements GC'd in that window, not the whole set, because dot-level state is otherwise independent per element.

15.10 Operational Notes

16. Phase 4 — Register CRDTs (LWW-Register, MV-Register)

16.1 Objectives

Implement single-value registers differentiated by conflict-resolution rule: last-writer-wins (a total order) vs multi-value (preserves concurrency). Constraint introduced: LWW requires a total-order tiebreak (I10) — the first CRDT in the library to need one.

16.2 Detailed Implementation Steps

Theory: Shapiro 2011 (§5 #7); HLC tiebreak from Kulkarni 2014 (§5 #11). Verifies I10 (total-order tiebreak). Applies P3. Types (§11):

#[derive(Clone, Eq, PartialEq, Debug)]
pub struct LwwRegister<V: Clone + Eq> { /* value: V, timestamp: HybridLogicalClock, writer: ReplicaId */ }
impl<V: Clone + Eq> LwwRegister<V> {
    pub fn set(&mut self, replica: ReplicaId, v: V, ts: HybridLogicalClock);  // (ts, replica) tiebreak
    pub fn value(&self) -> &V;
}
#[derive(Clone, Eq, PartialEq, Debug, Default)]
pub struct MvRegister<V: Clone + Eq + Ord> { /* values: BTreeMap<Dot, V>, clock: VectorClock */ }
impl<V: Clone + Eq + Ord> MvRegister<V> {
    pub fn set(&mut self, replica: ReplicaId, v: V);  // drop dominated dots, insert fresh
    pub fn value(&self) -> Vec<&V>;                   // all concurrent values
}
  1. LWW: set overwrites iff ts > self.timestamp, or on tie iff replica > writer (I10). Merge applies the same comparison. Timestamp is HLC (Phase 1) by default; Lamport opt-in.
  2. MV: set allocates a fresh dot (Phase 1, P3), removes any dot dominated by the current vector clock, inserts (dot, v); value returns every surviving value. Merge unions surviving dots and drops dominated ones.

16.6 Pitfalls

  • Wall-clock timestamps for LWW (clocks go backwards — use HLC, MM2).
  • Ignoring the replica tiebreaker on equal timestamps (breaks I10 → merge is no longer associative).
  • Returning a single value from MV-Register (it is multi-value by design; collapsing early loses information the application needed).

16.7 Performance Concerns

LWW set/merge is O(1) — one timestamp comparison. MV set is O(current dot count) to find dominated dots; under heavy concurrent-write contention on one key, the live dot set can grow before the next sequential write collapses it — bounded in practice by application-level write patterns, not by the algebra (no tombstones here, unlike OR-Set). HLC's clock_gettime cost (Phase 1, §13.7) recurs on every LWW set.

16.8 Edge Cases

  • Two writes with identical HLC timestamp from different replicas — resolved by the (ts, replica) total order (I10), never by "last write applied locally."
  • An MV-Register with an empty value set (never written) — value() returns an empty Vec, not a panic or a default value.
  • A set call using a Lamport timestamp when the register was previously written with HLC — LwwRegister is generic over one timestamp kind per instance; mixing is a compile-time type error, not a runtime concern.
  • Merge of two MV-Registers where one dot dominates another under the vector clock's dominates_dot — the dominated value is dropped even if its wall-clock timestamp is numerically higher (causal dominance outranks timestamp, since MV does not use timestamps at all).

16.9 Failure Analysis

Ignoring the replica tiebreak on an LWW timestamp tie (§16.6) breaks associativity silently: merge(merge(A,B),C) can pick a different winner than merge(A,merge(B,C)) depending on ordering, and the bug surfaces only under 3+ replica chaos testing, not 2-replica unit tests — a manifestation of MM1 (a broken merge law is invisible until reordering is exercised). Detection is the associativity proptest with ≥3 replicas; blast radius is any application field using LWW (Phase 6 JSON same-path writes) silently diverging. Recovery is fixing the comparator and forcing a full anti-entropy re-sync across affected replicas, since the divergence is in which value wins, not in unrecoverable data loss (both values existed transiently).

16.10 Operational Notes

17. Phase 5 — Sequence CRDTs (RGA, WOOT, Logoot)

17.1 Objectives

Implement three sequence CRDTs (RGA default, WOOT oracle, Logoot opt-in) so the user picks per workload and the conformance harness cross-checks convergence across all three. Constraint introduced: concurrent-insert ordering must be total and deterministic (extends I5's dot uniqueness into a full ordering).

17.2 Detailed Implementation Steps

Theory: RGA (Roh 2011, §5 #12, ADR-04); WOOT (Oster 2006, §5 #13); Logoot (Weiss 2009, §5 #14). Yjs (§5 #18) as the RGA reference oracle. Applies P4 (tombstones), I4. Types (§11):

#[derive(Clone, Eq, PartialEq, Debug)]
pub struct RgaNode { pub id: Dot, pub parent: Option<Dot>, pub value: char, pub tombstone: bool }
#[derive(Clone, Eq, PartialEq, Debug, Default)]
pub struct Rga { /* nodes: BTreeMap<Dot,RgaNode>, children: BTreeMap<Option<Dot>,BTreeSet<Dot>>, clock: VectorClock */ }
impl Rga {
    pub fn insert_after(&mut self, replica: ReplicaId, parent: Option<Dot>, c: char) -> Dot;
    pub fn delete(&mut self, id: Dot);     // sets tombstone
    pub fn to_string(&self) -> String;     // topological walk, concurrent siblings by (replica,tick)
}
// WOOT: each char has left/right neighbour ids; insert intersects neighbour sets.
// Logoot: position ids are dense rationals (paths in a virtual tree); insert allocates between neighbours.
  1. RGA: insert_after allocates a dot, records the node under its parent in children; delete tombstones; to_string walks from the root, ordering concurrent siblings by (replica,tick) descending (I5), skipping tombstones.
  2. WOOT: place each insert by intersecting the left/right neighbour visibility sets; correct but potentially quadratic — shipped as a reference oracle, not the default.
  3. Logoot: allocate a dense rational identifier strictly between the left and right neighbours' ids; expose a rebase operation (heavy, coordinated) to re-encode when identifier length crosses a threshold.
  4. All three implement Crdt (§11.2); gc(stable) prunes tombstones at causal stability (I4, P4).

Why concurrent siblings sort by (replica, tick). When two replicas insert after the same parent without seeing each other, their inserts are concurrent. RGA must pick a deterministic order so every replica renders the same string. Ordering by (replica, tick) descending gives a total order on dots (I5 guarantees uniqueness) that every replica computes identically — this is the sequence-CRDT analogue of the LWW tiebreak (I10). Get the comparator wrong or non-total and the same edit history renders differently on two replicas: a convergence bug that property tests catch only if the corpus includes concurrent same-parent inserts (§17.5).

RGA vs WOOT vs Logoot — the actual tradeoff.

Property RGA WOOT Logoot
insert cost O(1) amortised O(neighbours) — up to O(n) O(log n) id allocation
id size one dot (16 B) left+right neighbour ids grows with same-position contention
worst case tombstone bloat quadratic on adversarial input unbounded id growth
best fit bursty inserts, default reference cross-check very long-lived, sparse edits

RGA is the default (ADR-04) because its insert is cheap and its failure mode (tombstone bloat) is bounded by GC at stability, which we already need for OR-Set. WOOT ships only as an oracle. Logoot's unbounded id growth under adversarial same-position inserts (FM-5) is why it is opt-in, not default.

17.4 Acceptance Criteria

All three converge to the identical string for every delivery permutation tested; RGA matches the Yjs oracle byte-for-byte (to_string); M5 (100k-char RGA diff < 100 ms) met; sequence.rga/.woot/.logoot conformance buckets Pass; M-seq (Appendix B) met.

17.6 Pitfalls

  • Tombstone bloat in long-lived RGA (GC at stability is the only mitigation, FM-4).
  • Adversarial same-position inserts in Logoot (unbounded id growth → rebase/rate-limit, FM-5, Threat #4).
  • WOOT's quadratic worst case (ship as reference; expose the asymptotic in crdt-bench, never as the default per ADR-04).

17.7 Performance Concerns

RGA to_string is O(L) including tombstones (Scalability Analysis) — an un-GC'd long-lived document degrades render latency even at small live length, so GC is load-bearing for performance, not just memory (§17.6, FM-4). Logoot id comparison cost grows with identifier length under contention (dense-rational encoding), directly trading off against RGA's fixed 16-byte dot — the reason Logoot is reserved for sparse, long-lived documents (§17.2 tradeoff table) rather than bursty ones. WOOT's neighbour-intersection insert is O(neighbours) and can degrade to O(n) under pathological same-position bursts — acceptable only because it never runs in the production default path.

17.8 Edge Cases

  • Two replicas insert after the same parent concurrently — resolved deterministically by (replica,tick) descending (§17.2), never left ambiguous.
  • Delete of a node that was never observed locally (received via a delta before the corresponding insert) — the delta apply order must tolerate an out-of-order delete-before-insert by buffering or rejecting with a typed error; the conformance permutation corpus (§17.5) exercises exactly this ordering.
  • Logoot identifier exhaustion under sustained adversarial same-position inserts — triggers rebase (§17.2); absent rebase, comparisons still work but identifiers grow unboundedly (FM-5).
  • RGA to_string called mid-merge in a concurrent-access context — forbidden by the single-writer-per-document model (P3); the type system's &mut self requirement on merge prevents this at compile time.

17.9 Failure Analysis

An incorrect concurrent-sibling comparator (e.g. non-total or ordering by wall-clock instead of (replica,tick)) produces silent divergence: two replicas hold logically-equal RGA node sets but render different strings, and single-replica or two-replica testing without concurrent same-parent inserts will not catch it (§17.2). Detection is the permutation-corpus conformance check or the Yjs oracle comparison; blast radius is any sequence-backed feature (collaborative text, Phase 12 editor) rendering inconsistently across clients — a user-visible bug, not a crash. Recovery is fixing the comparator and forcing every replica to recompute to_string from the (unaffected) underlying node set — no data is lost, since divergence here is a rendering bug, not a state-corruption bug.

17.10 Operational Notes

Blast radius is confined to the affected subtree (I14's isolation guarantee: a CRDT never mutates another's state except via the join), so a bug in array-merge cannot corrupt map-merge elsewhere in the same document. 19. Phase 7 — Delta-State Encoding

19.1 Objectives

Ship the delta-state wire encoding — a state-based CRDT shipped at delta granularity — as the library default. Constraint introduced: every wire payload from this phase forward is a versioned, schema-tagged envelope (P5) that the decoder must reject-or-accept typed, never silently mis-parse (P6).

19.2 Detailed Implementation Steps

Theory: Almeida 2018 (§5 #8, ADR-02); Akka Distributed Data (§5 #22) for delta gossip in production. Verifies I7, I8, I11. Applies P5, P6, ADR-17. Types (§11):

pub const WIRE_VERSION: u8 = 1;
pub fn encode_delta<C: Crdt>(d: &C::Delta) -> Vec<u8>;        // envelope per §8.1
pub fn decode_delta<C: Crdt>(bytes: &[u8]) -> Result<C::Delta, MergeError>;
fn kind_for<C: Crdt>() -> u8;
  1. encode_delta: write [WIRE_VERSION, kind_for::<C>()], append u32 LE body length, append zstd(level 3, bincode(delta)).
  2. decode_delta: reject empty (BadWire), wrong version (UnknownVersion, I7), wrong kind (SchemaMismatch), truncated body (BadWire); zstd-decode then bincode-decode, mapping each failure to a typed MergeError (I8). Decode fully precedes apply (§8.5).
  3. A Delta is itself a join-semilattice element: merging two deltas yields a delta (the property that makes delta gossip correct, I11).

Delta-interval semantics. delta_since(vv) returns every change not covered by the caller's version vector vv — a delta interval in the Almeida 2018 sense. The receiver applies it with apply_delta, which must produce exactly the state merge would produce had the full state been shipped (the delta/state agreement law). Two consequences: (a) delta intervals can be merged together into a single larger interval before shipping (delta-grouping), which is how gossip batches a burst of edits into one frame; (b) a lost delta interval is self-healing — anti-entropy (Phase 8) will later detect the gap via the Merkle diff and re-ship it, because the underlying state is still a join-semilattice element. This is why the library never needs per-delta acknowledgement.

Why compression sits inside the envelope, not around it. The version and kind bytes are outside the zstd frame so a receiver can route and reject (UnknownVersion/SchemaMismatch) without paying decompression cost on a payload it will discard — important under the fanout-amplification threat (Threat #9).

19.3 Deliverable

delta/codec.rs; docs/delta-encoding.md; the delta_fuzz.rs fuzz target that every later phase's wire path reuses.

19.4 Acceptance Criteria

19.7 Performance Concerns

The p99 ≤ 100 µs apply-delta budget (M11, §4) decomposes as ~30 µs zstd decode (tail) + ~10 µs bincode deserialize + ~1 µs envelope validation + ~5 µs–plus join, per the Performance Engineering latency-budget breakdown — decompression, not the join itself, dominates the tail, which is why zstd level 3 (not a higher ratio level) is locked (ADR-17). 19.8 Edge Cases

  • A delta whose declared body_len exceeds the actual buffer — BadWire("truncated"), never a buffer over-read (§8.4).
  • A zstd frame that decompresses to a bomb (declared small, expands huge) — bounded by a maximum decompressed-size check before allocation (implementation detail of decode_delta, prevents a decompression-bomb DoS).
  • A delta for a kind byte not yet assigned (future CRDT type from a newer library version) — SchemaMismatch or UnknownVersion depending on which byte disagrees, never a panic on an unrecognized discriminant.
  • Concurrent encode_delta calls on the same CRDT from two threads — forbidden by the single-writer-per-document model (P3); the API takes &self for encode (safe to call read-only) but &mut self for merge/apply.

19.9 Failure Analysis

A codec bug that accepts a subtly-malformed payload (e.g. truncated body silently zero-padded instead of rejected) violates I8 and can corrupt CRDT state without any error surfacing — the highest-severity failure class this phase guards against, which is why delta_fuzz.rs runs continuously (nightly, escalating to the 30-day canary at M10) rather than only as a pre-merge check. Detection is a fuzz crash/panic or a conformance byte-mismatch; blast radius is bounded to the receiving replica's copy of that one CRDT (I14 isolation) but can propagate via gossip before anti-entropy catches the divergence (FM-3) — so a codec regression is treated as sev-1, not sev-3.

20. Phase 8 — Anti-Entropy via Merkle-Tree Diff & Transport

20.1 Objectives

Implement periodic catch-up sync via Merkle-tree diff over the op log, plus the pluggable Transport trait with in-memory and libp2p backends. Constraint introduced: the Merkle tree must span the entire log (I12) — a partial tree is a silent-divergence bug, not an optimization shortcut.

20.2 Detailed Implementation Steps

Theory: reuses the Merkle-Tree project (rank 71, ADR-07); transport from ADR-09. Verifies I12 (full-tree spanning). Applies P7. Types (§11.5):

pub struct AntiEntropy<T: Transport> { /* log: OpLog, merkle: MerkleTree<u64>, transport: T */ }
impl<T: Transport> AntiEntropy<T> {
    pub async fn diff_with(&mut self, peer: PeerId) -> Result<usize, AntiEntropyError>; // bytes shipped
}
// Transport trait per §11.5. Backends: memory, libp2p, websocket, grpc.
  1. Each replica maintains a Merkle tree over its op log indexed by (replica_id, tick) lexically; leaves are encoded deltas, internal nodes are xxh3 hashes (ADR-16).
  2. diff_with: compare root hashes; if equal, done; else recurse into differing internal nodes, request children, identify differing leaves, ship them. Cost O(log N + diff).
  3. Use the Merkle-Tree project's incremental update API so per-op tree update is O(log N) (I12 requires the tree span the whole log).
  4. Transport: in-memory backend for tests; libp2p default (ADR-09); WebSocket/gRPC behind the trait. Truncated transport → Err(Truncated); sender retries.

Protocol walkthrough (one anti-entropy round). Replica A initiates with peer B: A requests B's root hash — if equal, the logs are identical and the round ends in one round-trip shipping 0 bytes. Otherwise A requests B's two child hashes, compares to its own, and descends only into the differing subtree(s) — pruning identical subtrees entirely, which is what makes the cost O(log N + diff) rather than O(N). At the leaf level A has identified the exact differing (replica_id, tick) ranges and ships those deltas (bidirectionally). B applies via apply_delta (idempotent, I11), updates its incremental tree, and the next round-trip confirms convergence.

Indexing choice. The lexical (replica_id, tick) ordering clusters a fresh replica's deltas in one subtree, so a new replica's diff localises to O(log N) comparisons rather than scattering — the single biggest determinant of anti-entropy efficiency under churn (Phase 9 interplay).

20.3 Deliverable

crdt-sync/merkle.rs, anti_entropy.rs; crdt-transport/* (memory/libp2p/websocket/grpc backends); the anti-entropy conformance corpus.

20.4 Acceptance Criteria

Two divergent replicas (1000-delta disjoint logs) converge in one round shipping only the differing leaves (byte count ≈ diff size, not full-log size); robust to transport truncation (retries succeed); sync.anti_entropy conformance bucket Pass; M7 (1k-delta divergence anti-entropy round < 200 ms p95) met; M-ae (Appendix B) met.

20.6 Pitfalls

  • Recomputing the whole Merkle tree per op (use the incremental path; O(N) recompute would erase the O(log N) diff advantage).
  • Diffing when one side is at null root (empty → ship everything, not an error).
  • Partial Merkle tree → silent divergence (I12, FM-1).

20.7 Performance Concerns

Anti-entropy cost is O(log L + diff) where L = op-log length (Scalability Analysis) — an identical million-leaf subtree costs one hash comparison, so the dominant cost is genuinely differing data, not log size. Capacity model #7 derives: L=1M → tree depth ≈20 → ≤20 round-trips to localise one differing leaf; at ~5 ms RTT that is ≤100 ms, comfortably inside the M7 200 ms p95 budget with headroom for the actual leaf transfer.

20.8 Edge Cases

  • Both replicas' root hashes equal but their logs actually differ (xxh3 hash collision) — mitigated by the 64-bit hash space (10M-leaf collision-safety fixture, §20.5); a false "converged" verdict here would be a silent-divergence bug (I12), so xxh3 is chosen for speed with the collision probability at this leaf count kept negligible, not for cryptographic tamper-evidence (ADR-16 explicitly trades this off against SHA-256/blake3).
  • A peer's Merkle tree is only partially built (crash mid-rebuild) — diff_with against it produces a false convergence unless the tree-build completion is tracked and gates participation (operational discipline, not an algebra guarantee).
  • Diffing against a peer with zero overlap in replica ids (freshly joined, disjoint history) — degenerates to "ship everything," handled by the empty-tree-diff fixture, not a special code path.
  • Network partition mid-round — the round aborts cleanly (no partial apply, §8.5); the next scheduled round retries from scratch.

20.9 Failure Analysis

A partial or incorrectly-rebuilt Merkle tree (violating I12) causes the root-hash comparison to under-report differences, so two replicas can believe they are converged while actually diverged — FM-1's signature failure, detected only when a different mechanism (a conformance regression, or an application-level state mismatch) surfaces the gap, because anti-entropy itself reports success. Recovery is rebuilding the Merkle tree from the full op log and re-running the round (§20.6); the SLO table pages if a root-hash mismatch persists beyond 3 anti-entropy rounds, treating "still diverging after multiple rounds" as the detection signal for a tree-integrity bug rather than ordinary transient network loss.

20.10 Operational Notes

sync.merkle.leaf_count, sync.ae.bytes_shipped, sync.ae.rounds, transport bytes_sent/recv (SLO: root-hash mismatch converges within 3 rounds or pages, per the Operational Readiness SLO table). Rolling upgrades rely on the Transport trait being version-negotiated independently of the CRDT wire version (Compatibility & Versioning).

21. Phase 9 — Gossip-Based Dissemination

21.1 Objectives

Implement push-pull gossip to keep the steady state close to up-to-date, with selectable topologies and backpressure. Constraint introduced: gossip must degrade gracefully under load (backpressure, not unbounded queueing) and under churn (co-designed with anti-entropy, not a replacement for it).

21.2 Detailed Implementation Steps

Theory: reuses the Gossip-Protocol project (rank 72, ADR-08); push-pull from ADR-22; epidemic theory (§5 #5). Applies P7, P10. Types (§11.5):

pub struct Gossip<T: Transport, P: Topology> { /* transport, topology, log, interval, fanout */ }
impl<T: Transport, P: Topology> Gossip<T, P> {
    pub async fn run(&mut self) -> !;   // periodic push-pull to a random fanout
}
// Topology trait per §11.5. Impls: FullMesh, HubAndSpoke, Hierarchical.
  1. Default push-pull: each round selects a fanout of peers; push fresh deltas, pull missed ones; combination yields log-N convergence (ADR-22).
  2. Topologies: FullMesh (small clusters only), HubAndSpoke (leaves talk to hubs), Hierarchical (regions gossip internally then across the tree).
  3. A periodic background round runs anti-entropy (Phase 8) with a random peer; interval tunable (default 5 s).
  4. Backpressure: per-peer in-flight-bytes cap; exceeding it triggers jittered back-off (P10, deterministic seed for the jitter in tests).

Round anatomy. Each gossip tick: (a) the topology selects a fanout of peers (default ≈ ⌈log₂N⌉ random peers, the epidemic sweet spot — §5 #5); (b) push the deltas accumulated since that peer was last contacted (per-peer VersionVector watermark, Phase 1); (c) pull by sending our own watermark so the peer pushes back what we lack. Push alone leaks to late joiners (FM-6, MM6); pull alone is latency-bound; push-pull (ADR-22) gives the log-N convergence M8 requires.

Convergence intuition. A single new delta reaches all N replicas in ≈ log₂N rounds because each informed replica infects ≈ fanout new ones per round, doubling the informed set. The "+2" slack in M8 absorbs the tail where the last uninformed replicas are hit by chance. Under 30% churn, departed peers drop from the fanout set and rejoiners catch up via the next anti-entropy round — gossip handles the steady-state gradient, anti-entropy handles the discontinuities churn introduces (MM6).

Topology selection guidance. FullMesh is correct only when N ≤ ~16. HubAndSpoke concentrates fanout at hubs — good for thin clients, but a dead hub is a partition. Hierarchical bounds cross-region traffic, the choice past ~10⁴ nodes (Scalability Analysis).

crdt-sync/gossip.rs, topology.rs; the gossip conformance corpus covering (peers, churn, delta-rate) triples.

21.4 Acceptance Criteria

100 replicas converge within M8 (≤ ⌈log₂100⌉+2 = 9 rounds); still converges under 30% churn; backpressure bounds memory (no OOM under a sustained delta flood); sync.gossip conformance bucket Pass; M-gossip (Appendix B) met.

21.6 Pitfalls

  • Push-only gossip leaks to late joiners (push-pull is the default, ADR-22, FM-6).
  • Unbounded fanout (fanout 50 on 50 peers == full mesh; default ≈ log₂N).
  • Assuming a complete topology (a dead hub is a partition; expose a "hub healthy" predicate, application owns failover).

21.7 Performance Concerns

Bandwidth per round is bounded by fanout × average delta size × frequency; Capacity model #6 derives round counts (N=100→9, N=10⁴→16, N=10⁶→22) and, at the default 5 s interval, a 10⁴-node cluster fully converges in ≈80 s worst case. Per-peer in-flight-byte caps (Phase 9 backpressure) bound memory under a flood but trade off round latency — a tighter cap means more back-off cycles before catch-up, a direct latency/memory tension operators tune via the cap value.

21.8 Edge Cases

  • A peer disappears mid-round (churn) — the round for that peer times out and is simply skipped; no retry storm (bounded by the transport's own timeout, not gossip-level retry logic).
  • Fanout selection picks the same peer twice in adjacent rounds by chance — harmless (push-pull is idempotent per delta, I11), just a wasted round-trip.
  • A HubAndSpoke topology's hub goes down — leaves cannot gossip until failover; this is a structural limitation of the topology choice (§21.2 guidance), not a bug, and is why FullMesh/Hierarchical exist as alternatives.
  • Backpressure engages exactly at the in-flight cap boundary — the jittered back-off (P10 seeded) must not synchronize across peers into a thundering-herd retry pattern; jitter is the mitigation.

21.9 Failure Analysis

Push-only misconfiguration (violating ADR-22) causes late joiners to never catch up via gossip alone — FM-6's failure mode — detected operationally by a joining replica's delta count staying flat past several gossip intervals while peers' counts grow. Recovery is switching to push-pull (the default) or, in the interim, forcing an anti-entropy round against a known-current peer; blast radius is confined to newly-joined or long-disconnected replicas, not the steady-state cluster, because push-pull-connected peers are unaffected. A sustained backpressure trip (FM-11) degrades to anti-entropy-only catch-up rather than failing outright — the system trades freshness for stability under load.

21.10 Operational Notes

sync.gossip.rounds, sync.gossip.fanout, sync.gossip.inflight_bytes gauge (SLO: warn at 80% cap), sync.gossip.churn gauge. Rolling upgrades are safe because gossip payloads are the same versioned delta envelope as anti-entropy (§8.1) — no separate gossip-specific wire format to version.

22. Phase 10 — Persistence (WAL + Snapshot, integrating rank 69)

22.1 Objectives

Persist deltas durably and recover byte-identically, integrating the WAL project (rank 69) for the log and a per-CRDT snapshot story. Constraint introduced: recovery must be byte-identical to pre-crash state (I13) — the strongest correctness bar in the library outside the merge laws themselves.

22.2 Detailed Implementation Steps

Theory: reuses the WAL project (rank 69, ADR-10); MVCC snapshot from ADR-21. Verifies I13 (byte-identical recovery). Applies P8. Types (§11.5):

pub struct Storage { /* wal: Wal, snapshot_dir: PathBuf, snapshot_every: u64, deltas_since_snapshot: u64 */ }
impl Storage {
    pub fn append<C: Crdt>(&mut self, delta: &C::Delta) -> Result<(), StorageError>;
    fn snapshot<C: Crdt>(&mut self) -> Result<(), StorageError>;   // atomic via rename
    pub fn recover<C: Crdt>(&mut self) -> Result<C, StorageError>;
}
// Storage trait per §11.5. fsync discipline: fsync_every_write | fsync_every_n | no_fsync (tests).
  1. Write path: every mutation encodes a delta and appends to the WAL; durability follows the configured fsync discipline (RPO from §4).
  2. Snapshot: every N deltas (default 10k) write the encoded state to snapshots/<seq>.snap, atomic via rename; use an MVCC frozen view so appends continue during snapshot (ADR-21).
  3. Recovery: find the most recent snapshot, decode it, replay the WAL from that sequence forward (I13).
  4. Compaction: old snapshots + covered WAL prefix become deletable once a newer snapshot is durable — automatic compaction deferred (Deferred Features Register); Phase 10 ships manual compaction only.

Recovery protocol, step by step (I13). Scan snapshots/ for the highest sequence number s whose file passes its checksum (none found → start empty, s=0). Decode the snapshot (Document::decode_state); a decode failure falls back to the previous snapshot and a longer WAL replay (FM-8). Open the WAL, seek to the first record with sequence > s. For each subsequent record: verify its per-record checksum (corruption → typed error, never skipped, FM-7/Threat #7), decode the delta, apply_delta it — because apply is idempotent (I11) and associative (I2), replaying a record the snapshot already incorporated is harmless, so the snapshot boundary need only be a lower bound. The resulting state is byte-identical (I13), verified by storage.recovery.

Snapshot atomicity. The writer serialises to a temp file, fsyncs it, then renames over the target — atomic on POSIX, so a crash mid-write leaves either the old or the new snapshot intact, never torn. The WAL prefix a snapshot covers is truncated only after the snapshot's fsync returns (ADR-21).

crdt-storage/* modules (log.rs wraps the WAL project, snapshot.rs, recovery.rs); the storage-recovery conformance corpus; the crash-during-snapshot chaos scenario.

22.4 Acceptance Criteria

1M-delta workload recovers byte-identically to pre-crash state (I13); snapshot writes are crash-atomic (chaos/scenarios/crash_during_snapshot.rs always recovers to a valid prior state, never a torn one); corrupted WAL records surface as a typed error, never a silent skip; startup recovery completes in < 3 s (M12, §4); storage.recovery conformance bucket Pass; M-storage (Appendix B) met.

22.6 Pitfalls

  • Snapshotting under load without MVCC blocks appends (ADR-21).
  • Truncating the WAL before the snapshot is durable (sync snapshot first, then truncate — never the reverse).
  • Recovering from a corrupted WAL silently (propagate, never skip — relies on the WAL's per-record checksum, Threat #7).

22.7 Performance Concerns

Capacity model #8/#9 derive the operational tradeoffs: with fsync_every_write, RPO=0 but each append costs an fsync (~100 µs–1 ms on NVMe) → ≤10k appends/s; fsync_every_n (n=100) raises throughput ~100× at an RPO of ≤100 deltas. Recovery cost is O(snapshot decode + tail replay) — at the default 10k-delta snapshot interval and M11's ~5 µs p50 apply rate, tail replay alone is ~50 ms, well inside the 3 s startup budget (M12), leaving headroom for snapshot decode of large documents.

22.8 Edge Cases

  • Process crash between WAL append and snapshot trigger — recovery replays the un-snapshotted tail; correctness holds because apply is idempotent/associative (I2/I11), not because the crash point was anticipated.
  • A snapshot file present but the WAL prefix it should supersede was already truncated, then the snapshot itself fails its checksum — recovery must fall back to the previous snapshot, which requires retaining at least two snapshot generations (an operational policy, not an algebraic requirement) until the newest is proven durable.
  • Disk full mid-snapshot-write — the temp file write fails before rename, so the old snapshot remains authoritative; StorageError surfaces to the operator rather than a partial rename.
  • Recovering onto a machine with a different ReplicaId file than the one that crashed (P12 violation risk) — recovery must restore the persisted ReplicaId from the snapshot, never regenerate one, or dot uniqueness (I5) breaks on rejoin.

22.9 Failure Analysis

A recovery bug that silently skips a corrupted WAL record (rather than propagating the typed error) is the single most severe failure this phase guards against: it produces a plausible but wrong recovered state with no error signal, violating I13 invisibly (FM-8's worst case). Detection relies entirely on the WAL's own per-record checksum (owned by the rank-69 project, reused not reimplemented per P8) — if that checksum is disabled or bypassed, this phase has no independent detection. Blast radius is the single recovering replica; containment is that a byte-mismatch is always eventually caught by the next anti-entropy round against a healthy peer (§20), which is why recovery correctness and anti-entropy are treated as complementary safety nets, not redundant ones.

22.10 Operational Notes

storage.append.count, storage.snapshot.duration, storage.recover.bytes (SLO: 0 mismatch, page on any — FM-8), storage.fsync.count. Disaster recovery: a node restored from snapshot+WAL rejoins via one anti-entropy round (Operational Readiness); there is no separate "rebuild from peers" path, since recovery and sync share apply_delta.

  • Allocating in the WASM hot path (batch operations across the boundary; every crossing has fixed marshalling cost).
  • Holding the GIL across a long merge (use Python::allow_threads, else other Python threads stall).
  • Re-implementing merge in a binding (forbidden, P9 — the single-source-of-truth violation this phase exists to prevent).

23.7 Performance Concerns

Every FFI boundary crossing (WASM linear-memory copy, PyO3 PyObject conversion) has fixed marshalling cost independent of payload size for small values but linear for large ones (e.g. a large JsonArray serialized to a JS array) — the mitigation is batching operations across the boundary (§23.6) rather than one call per CRDT operation. binding.boundary.bytes (§23.10) makes this cost visible per call so a chatty integration is diagnosable from metrics alone.

23.8 Edge Cases

  • A JS caller passes a Symbol or BigInt beyond f64 precision — rejected at the boundary with a JS exception, never silently truncated (type-mapping discipline, §23.2).
  • A Python caller holds a reference to a Document across a fork() — PyO3/Rust ownership does not have Python's expectations around fork-safety; document the restriction rather than attempt to support it (unsupported, not silently broken).
  • WASM binding invoked from a Web Worker concurrently with the main thread on the same Document — forbidden by the single-writer model (P3); the application must not share one Document handle across workers without its own synchronization.
  • A Python merge call from a thread that does not hold the GIL when the binding expects it (misuse of allow_threads) — PyO3's type system prevents this at compile time for the binding authors; the constraint does not reach the Python caller.

23.9 Failure Analysis

A binding that re-implements even a small piece of merge logic (e.g. "just for JS ergonomics") is the highest-risk regression this phase can introduce, because it creates a second, divergent algebra (P9's violation clause) that the byte-identity conformance corpus (§23.5) is specifically designed to catch — a corpus failure here means the binding computed a different result than the core, not a marshalling bug. Detection is exactly that corpus; blast radius is every consumer of that binding (all browser or Python users), which is why binding round-trip conformance gates release the same way core conformance does (Testing & Verification Strategy), not as an optional check.

  • Coupling examples to internal types (public API only — an example that reaches into crdt_core::internal cannot validate what a real consumer experiences).

24.7 Performance Concerns

The soak harness (M9) must distinguish genuine memory growth (a leak) from expected steady-state growth (tombstone accumulation pre-GC, §7 I4) — the harness asserts mem.rss growth rate flattens once GC cycles engage, not that it stays at zero from t=0. Chaos scenarios run nightly rather than per-PR (Build & Release Engineering CI gate ordering) because transient-cluster spin-up cost does not fit a PR latency budget.

24.8 Edge Cases

  • A partition that heals asymmetrically (one side receives the other's deltas before the reverse direction) — convergence must still hold (I1, commutativity) regardless of heal-direction ordering.
  • A crash during active gossip and active anti-entropy simultaneously — recovery (Phase 10) and re-sync (Phase 8/9) must compose without a special-cased "recovering while gossiping" state, since both operate through the same apply_delta primitive.
  • The CodeMirror editor stretch example invoked before Phase 11 bindings ship — returns PhaseDeferred, and the conformance report's outcome stays Pass as long as every non-deferred bucket passes (Testing & Verification Strategy).
  • Soak test process itself crashes at hour 20 of 24 — the harness must resume from its own checkpoint or the run is invalidated, not silently reported as a partial pass.

24.9 Failure Analysis

A chaos scenario that fails to converge after a simulated partition heal indicates one of I1–I4 or I12–I13 is violated under adversarial conditions that unit/property tests at smaller scale did not exercise — the highest-value bug class this phase catches precisely because it composes every prior phase's guarantees under simultaneous stress. Detection is the scenario's own convergence assertion; blast radius is scoped to the scenario's simulated cluster (no production impact, since this runs in CI); recovery is bisecting which invariant broke (the recorded seed, P10, makes any chaos failure exactly reproducible) and routing the fix to the owning phase (e.g. an I4 violation routes to Phase 3's GC logic, not to the chaos harness itself).

Threat Model

Trust boundaries

  1. Network. Untrusted: any peer. Authenticated: peers whose libp2p identity is in the cluster allowlist.
  2. WAL. WAL bytes come from disk; treat as untrusted; the WAL project's per-record checksum is the mitigation.
  3. Binding. WASM/PyO3 own conversion; bad arguments raise host-language exceptions and do not corrupt the engine.

Threats

  1. Malformed delta on the wire. Mitigation: versioned envelope, schema-tagged kind, length-prefixed body, zstd validity check, bincode parse via serde_bytes. Fuzz target delta_fuzz.rs (§8.4, I7/I8).
  2. Adversarial peer shipping invalid dots. Mitigation: dots signed by the peer's libp2p identity; unknown replicas rejected with MergeError::UnknownReplica (I5).
  3. Tombstone-bloat DoS. A peer creating/removing many entries to bloat the document. Mitigation: per-replica transport rate limits; docs/threat-model.md.
  4. Logoot identifier explosion. Repeated same-position inserts. Mitigation: rebase past a length threshold (§17.6).
  5. Replay attack. A peer re-ships a merged delta. Mitigation: merge is idempotent (I3); replay is a no-op.
  6. Forked history. A peer ships state from a forked branch. Mitigation: causal stability; the application sees both branches as concurrent and resolves via the merge law.
  7. WAL tampering at rest. Mitigation: per-record checksum; corruption surfaces as a typed error (I8, I13), never silently skipped.
  8. Schema-downgrade attack. A peer claims an old version to coax a lossy decode. Mitigation: the decoder rejects unknown versions (I7) and never downgrades silently; the sender downgrades only on explicit SchemaMismatch.
  9. Resource exhaustion via fanout amplification. A peer requesting huge leaf sets in anti-entropy. Mitigation: per-peer in-flight-bytes cap and back-off (Phase 9).
  10. Clock-skew abuse on HLC. A peer advertising a far-future physical clock to win LWW. Mitigation: observe returns SkewExceeded past MAX_SKEW_US (Phase 1) and the write is rejected.
  11. Identity spoofing of ReplicaId. Mitigation: bind ReplicaId to the libp2p identity at the allowlist boundary (deferred enforcement, Register).

The threat model's organising principle: the algebra is the last line of defence. Deployment and rolling upgrade

  • Rolling upgrade. Because every node decodes down and encodes to the version floor (Compatibility & Versioning), a cluster upgrades node-by-node with no downtime: an upgraded node still encodes at the old wire version until every peer advertises the new one. The compose stack (§12) and crdtctl health give the operator a per-node version readout to confirm the floor has lifted before relying on new-version features.
  • Capacity planning. Provision sockets from the gossip fanout (≈ log₂N per node) plus client connections, against the 256-FD budget (§4). Provision memory at the pre-GC OR-Set ceiling (8× live, §4) plus the largest snapshot, not the steady-state figure, so a GC stall does not OOM the node.
  • Backpressure as a load shedder. Under a delta flood, the per-peer in-flight cap (Phase 9) degrades gracefully: gossip rounds back off and the node falls back to anti-entropy catch-up (FM-11) rather than queueing unboundedly. Operators should alert on sustained cap-hits, not single spikes.
  • Disaster recovery. A node restored from a snapshot + WAL is byte-identical to its pre-crash self (I13) and rejoins via one anti-entropy round; there is no separate "rebuild from peers" path because recovery and sync share the same delta-apply primitive.

Compatibility & Versioning

  • Wire version. A single u8 version byte gates every payload (I7, §8.1). Every schema change is an ADR + version bump (P5). The decoder rejects unknown versions, never downgrades silently.
  • Kind byte. A stable u8 per CRDT kind (§8.1); new kinds append, never renumber.
  • SemVer. The crate follows SemVer; a wire-version bump is a major version. Bindings track the core version.
  • Shape compatibility. Yjs/Automerge shape parity is supported; wire-byte compatibility is deferred (Register, ADR-05/06).
  • Cross-project APIs. Merkle-Tree (71), Gossip-Protocol (72), WAL (69): a breaking upstream change is captured in an ADR and the conformance suite re-runs before the bump lands.
  • Conformance corpora are versioned with the library; a corpus change that alters expected bytes is a wire-version event.

Cross-version interoperation rule

A node MUST be able to decode every wire version from its own version down to the oldest still in the field, and SHOULD encode the lowest version any current peer advertises. Version negotiation happens at the transport handshake: each peer advertises a max_wire_version; the sender encodes at min of the two. A node that receives a version above its max returns UnknownVersion (I7) and the sender downgrades — never the reverse, so an old node can never be tricked into mis-parsing a new frame (Threat #8). This is the same discipline gossip relies on for rolling upgrades: a cluster can run mixed versions during a deploy because every node decodes down and encodes to the floor.

Schema-change checklist (every wire-version bump)

  1. Write the ADR documenting the change and the rejected alternatives.
  2. Bump WIRE_VERSION and add the new arm to the decoder (keep the old arm).
  3. Add a conformance corpus entry pinning the new bytes; keep the old corpus for backward decode.
  4. Add a dual-version interop test to bindings.* and delta.codec.
  5. Bump the crate major version (SemVer).

Benchmark methodology. All targets are measured on the §4 reference hardware with criterion (crdt-bench/), warm caches, and a fixed RNG seed (P10). Latency budget decomposition (apply one delta, M11). The p99 ≤ 100 µs budget breaks down as: zstd frame decode (~30 µs at the tail for a small payload) + bincode deserialize (~10 µs) + envelope validation (~1 µs, §8.4) + the actual join (~5 µs p50, longer for large OR-Set dot sets). The hot merge path avoids per-element heap allocation by merging into the existing BTreeMap in place; deltas are decoded into a reused scratch buffer where the binding boundary allows it (Phase 11 pitfall on WASM allocation). Scalability Analysis

Complexity table (per operation, N = ever-seen replicas, L = op-log length, E = live elements).

Operation Time Space Dominant cost

DVV observe (amortised) O(1) O(N + concurrent dots) compaction pulls contiguous dots

  • Replica count. Vector-clock state grows linearly in the number of ever-seen replicas; DVVs (ADR-03) bound the client-server fan-in case where clients vastly outnumber servers. Past ~10⁴ replicas, prefer DVVs and hub-and-spoke topology.
  • Document size. RGA/Logoot state grows with insert count, not live length, until GC. A 100k-char document with heavy edit history can hold millions of tombstones; GC at causal stability is the bound (I4, FM-4). The RGA to_string cost is O(L) including tombstones, so an un-GC'd document degrades render latency even though live length is small — a second reason GC is not optional in long-lived deployments.
  • Throughput. The algebraic core is single-writer per document (P3); horizontal scale comes from sharding documents across processes, not from intra-document parallelism. A 16-core node hosting independent documents scales linearly until it saturates the FD budget (§4) or the gossip fanout sockets.
  • Gossip. Convergence is O(log N) rounds (M8); bandwidth per round is bounded by the in-flight cap. A 10⁴-node cluster converges in ~16 rounds.
  • Anti-entropy. O(log N + diff) per pair; the cost is dominated by diff (differing leaves), which is the actual divergence, not the log size.
  • Storage. WAL append is O(1) amortised; snapshot is O(state) every N deltas; recovery is O(snapshot + tail). The snapshot interval trades recovery time (RTO) against steady-state write amplification.

Mental Models & First Principles

  • MM1 — A CRDT is a join-semilattice; merge is the join. Predicts: any merge that is not commutative/associative/idempotent will diverge under reordering. Bug class without it: "works in tests, diverges in production under reordering." Applied: Phase 2, §7 I1–I3.
  • MM2 — Causality is a partial order, not a clock reading. Predicts: two events with no happens-before are concurrent, and concurrency is a first-class outcome, not an error. Bug class: forcing a total order (e.g. wall-clock LWW) silently drops one of two concurrent writes. Applied: Phase 1, Phase 4, §7 I9.
  • MM3 — A delete is the addition of a tombstone, not a subtraction. Predicts: you cannot truly remove information from a CRDT until everyone agrees it is safe (causal stability). Bug class: early GC resurrects deletes. Applied: Phase 3, §7 I4, FM-2.
  • MM4 — Observed-remove means "remove what I saw." Predicts: a concurrent add the remover never saw must survive (add wins). Bug class: 2P-Set semantics where re-adds silently fail. Applied: Phase 3, §8.2.
  • MM5 — Delta-state is "ship the join increment," and a delta is itself a CRDT. Predicts: merging deltas is associative, so gossip can re-ship freely. Bug class: treating a delta as a non-idempotent op breaks under duplication. Applied: Phase 7, §7 I11.
  • MM6 — Anti-entropy answers "what differs," gossip answers "spread what's new." Predicts: a system needs both — gossip for freshness, anti-entropy for completeness after churn. Bug class: push-only gossip leaks to late joiners. Applied: Phase 8, Phase 9, FM-6.
  • MM7 — The wire is hostile; decode is a parser, not a cast. Predicts: every byte sequence must map to either a value or a typed error, never a panic. Bug class: silent corruption from an unchecked cast. Applied: Phase 7, §8.4, §7 I7/I8.
  • MM8 — Recovery is a pure replay of an immutable log onto a checkpoint. Predicts: if append-order is preserved and merge is associative, recovery is deterministic and byte-identical. Bug class: mutating state in place during recovery yields non-reproducible state. Applied: Phase 10, §7 I13.
  • MM9 — Identifiers are forever; never reuse a ReplicaId. Predicts: dot uniqueness depends on stable ids; rotation corrupts the algebra. Bug class: convergence failures after a node restarts with a fresh-but-colliding id. Applied: §6 P12, §7 I5/I12.

Back-of-Envelope Capacity Model

All inputs are taken from the §4 System Constraints table; formulas shown.

  1. G-Counter dot size. A (ReplicaId u64, count u64) pair = 16 B raw. With 4 replicas → 64 B state.
  2. Delta budget (M6). Delta ≤ 5% of state → for a 4-replica chat doc whose state is ~64 B per counter, a delta ≤ ~3.2 B per counter pre-compression; the ~24 B/delta sanity figure (Phase 7) reflects envelope + zstd framing overhead on small payloads.
  3. OR-Set memory before GC. Memory ≤ 8× live (§4). For 100k live elements at ~32 B each (value + one dot) → live ≈ 3.2 MB; pre-GC ceiling ≈ 25.6 MB. M3 says a 100k-element 4-replica merge runs < 1 s, so merge bandwidth ≥ 3.2 MB / 1 s = 3.2 MB/s minimum (well under memory bandwidth; the cost is map operations, not copying).
  4. Merge op budget (M1). ≥ 5 Mops/s on one core → ≤ 200 ns per merged key. A 4-replica G-Counter merge touches ≤ 4 keys → ≤ 800 ns per full merge → ≥ 1.25 M full-merges/s.
  5. Apply-delta latency budget (§4/M11). p99 ≤ 100 µs. A single-key delta decode (zstd frame + bincode) must fit in that; subtract ~5 µs p50 apply → decode budget ≈ 95 µs at the p99 tail.
  6. Gossip rounds (M8). rounds ≈ ⌈log₂N⌉ + 2. N=100 → 9; N=10⁴ → 16; N=10⁶ → 22. At a 5 s default interval, a 10⁴-node cluster fully converges in ≈ 80 s worst case.
  7. Anti-entropy tree depth. A log of L deltas in a binary Merkle tree has depth ⌈log₂L⌉. L=1M → depth 20 → ≤ 20 round-trips to localise a single differing leaf; M7 (< 200 ms) at ~5 ms RTT allows ≈ 40 round-trips, comfortably within budget.
  8. Snapshot interval vs RTO. Default snapshot every 10k deltas; RTO < 5 s (FM-7). If recovery replays ≤ 10k deltas at the M11 apply rate (p50 5 µs) → 10k × 5 µs = 50 ms replay, plus snapshot decode; the 10k interval is conservative against the 5 s RTO.
  9. WAL write rate vs RPO. With fsync_every_write, RPO=0 but each append costs an fsync (~100 µs–1 ms on NVMe) → ≤ 10k appends/s. With fsync_every_n (n=100), throughput rises ~100× at an RPO of ≤ 100 deltas.
  10. FD budget headroom. ≤ 256 sockets (§4). At log₂N fanout, a 10⁴-node cluster needs ≈ 14 concurrent peer sockets per round — two orders of magnitude under the cap.

Alternative Architectures (Roads Not Taken)

A. Operation-based CRDTs over a reliable causal-broadcast layer

[client op] → [causal broadcast / exactly-once log] → [apply op at each replica]

Wins when the transport already provides exactly-once, causally-ordered delivery (e.g. a single Kafka partition or a TCP-ordered server fan-out) and op payloads are far smaller than state. Embodied by Yjs (op/struct-based with a reliable provider). Rejected because it pushes exactly-once delivery onto the transport (P2), which our pluggable, churn-tolerant transport (P7) cannot guarantee; state/delta-state merge is idempotent under duplication and reordering, which the wire here is not.

B. Server-authority / operational-transform with a central resolver

[clients] → [authoritative server resolves order] → [broadcast canonical log]

Wins when you need stronger-than-SEC guarantees (a single linear history, server-enforced invariants) and can tolerate a central point — the classic Google-Docs-style OT server. Embodied by Replicache/PowerSync-style server-authority sync. Rejected as the default because it forfeits offline-first peer-to-peer convergence; it is retained only as a deferred "server authority" mode (Register) for workloads where SEC is too weak.

C. Database-embedded CRDTs on a Dynamo-style ring

[client] → [hash ring vnode] → [state-based CRDT stored + replicated by the ring]

Wins when the storage engine already owns replication, hinted hand-off, and read-repair, so CRDTs are "just another column type." Embodied by Riak DT. Rejected because it couples the CRDT algebra to one storage engine's replication, violating the "sync and storage layer on top, never below" property (§3) and the pluggable-transport/persistence principles (P7, P8).

D. Columnar change-log document store

[edits] → [append to columnar change log] → [materialise document on read]

Wins when you must store and ship the full edit history compactly (audit trails, time-travel, cold storage) and can pay a heavier read-time materialisation. Embodied by Automerge's columnar encoding. Rejected as the Phase-0 default to keep the codec simple (ADR-17) and the in-memory model direct; columnar encoding is captured as a deferred feature (Register).

Glossary

  • CRDT. Conflict-Free Replicated Data Type; a type whose merge is commutative, associative, idempotent, guaranteeing SEC.
  • CvRDT. Convergent (state-based) Replicated Data Type.
  • CmRDT. Commutative (operation-based) Replicated Data Type.
  • Delta-state CRDT. A state-based CRDT shipped at delta granularity (Almeida 2018).
  • Strong Eventual Consistency (SEC). Replicas that observed the same updates converge; no conflicts at convergence.
  • Eventual consistency. Replicas converge eventually, without SEC's no-conflict guarantee.
  • Join-semilattice. A partial order with a least upper bound (join) for every pair; the algebraic structure of a CRDT.
  • Join / merge. The least-upper-bound operation; the CRDT's merge.
  • Commutativity / Associativity / Idempotence. The three merge laws (I1–I3).
  • Vector clock. A per-replica counter; the canonical causality primitive.
  • Version vector. Algebraically a vector clock; semantically "which dots have I observed."
  • Dotted version vector (DVV). A version vector plus dots concurrent with the base (Almeida 2014).
  • Lamport timestamp. A (replica, counter) pair under local := max(local, incoming)+1; total order, partial causality.
  • Hybrid logical clock (HLC). A (physical, logical, replica) triple with bounded skew (Kulkarni 2014).
  • Dot. A unique (replica, tick) identifier for one update event.
  • Tick. A monotonic per-replica counter; 1-indexed (Tick(0) = never observed).
  • ReplicaId. A stable, lifetime-unique replica identifier.
  • Tombstone. A record of a deleted element retained for causal correctness.
  • Causal stability. A dot observed by every known replica; precondition for GC.
  • Concurrency. Two events with no happens-before relation.
  • Happens-before. Lamport's partial-order causality relation.
  • Anti-entropy. Periodic catch-up sync; implemented via Merkle-tree diff.
  • Gossip. Randomised epidemic dissemination; push, pull, or push-pull.
  • Push-pull. Gossip that both sends fresh deltas and requests missed ones.
  • Merkle tree. A hash tree over the op log enabling O(log N) diff.
  • Op log. The append-only sequence of deltas a replica has applied.
  • G-Counter. Grow-only counter; per-replica map under per-key max.
  • PN-Counter. Increment/decrement counter; two G-Counters.
  • G-Set. Grow-only set; union merge.
  • 2P-Set. Two-phase set; add-set plus permanent tombstone-set.
  • OR-Set. Observed-Remove Set; remove acts only on observed dots.
  • LWW-Register. Last-Writer-Wins Register; (timestamp, replica) tiebreak.
  • MV-Register. Multi-Value Register; preserves all concurrent writes.
  • RGA. Replicated Growable Array; default sequence CRDT (Roh 2011).
  • WOOT. Without Operational Transform; reference sequence CRDT (Oster 2006).
  • Logoot. Dense-rational position-identifier sequence CRDT (Weiss 2009).
  • Treedoc. A tree-structured sequence CRDT (Preguiça 2009).
  • YATA. Yjs's list CRDT algorithm.
  • Snapshot. A point-in-time encoded state checkpoint.
  • WAL. Write-Ahead Log; the durable append-only delta log (rank 69).
  • RTO / RPO. Recovery Time / Point Objective.
  • fsync discipline. The policy governing when WAL writes are flushed.
  • MVCC snapshot. A snapshot taken from a frozen view while appends continue.
  • Topology. The peer-connection structure (mesh / hub-and-spoke / hierarchy).
  • Fanout. The number of peers contacted per gossip round.
  • Backpressure. Bounding in-flight bytes to prevent overload.
  • Wire version. The u8 byte gating payload schema (P5).
  • Kind byte. The u8 identifying which CRDT a payload encodes.
  • Schema mismatch. A decode failure when the kind byte disagrees with the expected CRDT.
  • PhaseDeferred. The typed error / anchor marking a deferred surface.
  • Conformance suite. The byte-identity test harness gating Done/Sealed.
  • Property test. A randomized law-checking test (proptest).
  • Chaos test. A fault-injection (partition/churn/crash) test (Jepsen-style).
  • SEC theorem. Shapiro 2011's result that CRDTs converge under SEC.
  • libp2p. The default transport providing discovery, NAT traversal, authenticated channels.
