Back-of-Envelope Capacity Model

All inputs are taken from the §4 System Constraints table; formulas shown.

  1. G-Counter dot size. A (ReplicaId u64, count u64) pair = 16 B raw. With 4 replicas → 64 B state.
  2. Delta budget (M6). Delta ≤ 5% of state → for a 4-replica chat doc whose state is ~64 B per counter, a delta ≤ ~3.2 B per counter pre-compression; the ~24 B/delta sanity figure (Phase 7) reflects envelope + zstd framing overhead on small payloads.
  3. OR-Set memory before GC. Memory ≤ 8× live (§4). For 100k live elements at ~32 B each (value + one dot) → live ≈ 3.2 MB; pre-GC ceiling ≈ 25.6 MB. M3 says a 100k-element 4-replica merge runs < 1 s, so merge bandwidth ≥ 3.2 MB / 1 s = 3.2 MB/s minimum (well under memory bandwidth; the cost is map operations, not copying).
  4. Merge op budget (M1). ≥ 5 Mops/s on one core → ≤ 200 ns per merged key. A 4-replica G-Counter merge touches ≤ 4 keys → ≤ 800 ns per full merge → ≥ 1.25 M full-merges/s.
  5. Apply-delta latency budget (§4/M11). p99 ≤ 100 µs. A single-key delta decode (zstd frame + bincode) must fit in that; subtract ~5 µs p50 apply → decode budget ≈ 95 µs at the p99 tail.
  6. Gossip rounds (M8). rounds ≈ ⌈log₂N⌉ + 2. N=100 → 9; N=10⁴ → 16; N=10⁶ → 22. At a 5 s default interval, a 10⁴-node cluster fully converges in ≈ 80 s worst case.
  7. Anti-entropy tree depth. A log of L deltas in a binary Merkle tree has depth ⌈log₂L⌉. L=1M → depth 20 → ≤ 20 round-trips to localise a single differing leaf; M7 (< 200 ms) at ~5 ms RTT allows ≈ 40 round-trips, comfortably within budget.
  8. Snapshot interval vs RTO. Default snapshot every 10k deltas; RTO < 5 s (FM-7). If recovery replays ≤ 10k deltas at the M11 apply rate (p50 5 µs) → 10k × 5 µs = 50 ms replay, plus snapshot decode; the 10k interval is conservative against the 5 s RTO.
  9. WAL write rate vs RPO. With fsync_every_write, RPO=0 but each append costs an fsync (~100 µs–1 ms on NVMe) → ≤ 10k appends/s. With fsync_every_n (n=100), throughput rises ~100× at an RPO of ≤ 100 deltas.
  10. FD budget headroom. ≤ 256 sockets (§4). At log₂N fanout, a 10⁴-node cluster needs ≈ 14 concurrent peer sockets per round — two orders of magnitude under the cap.
