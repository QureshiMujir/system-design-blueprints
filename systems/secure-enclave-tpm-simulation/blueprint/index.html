226 — Secure Enclave / TPM Simulation from Scratch

Project Number: 226

Project Name: Secure Enclave / TPM Simulation from Scratch

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering Definition

Build, from scratch, a software-emulated Trusted Platform Module (TPM 2.0-shaped command processor) and Secure Enclave runtime with deterministic execution semantics, cryptographically verifiable persistence, isolated execution contexts, measured-boot simulation, remote attestation, sealed storage, monotonic anti-replay counters, and policy-gated command authorization. The system is a layered trust-computing platform, not a toy emulator: it reproduces the architectural, concurrency, persistence, observability, and failure semantics of enclave-backed trusted execution systems (TPM 2.0 implementations, SGX/SEV runtime stacks, Nitro Enclaves) without touching real hardware roots of trust.

Phase 0 Deliverable — Crates and Services

Phase 0 (§12) produces a compiling, CI-green Cargo workspace with fifteen crates/services, each a placeholder-to-functional skeleton wired into the observability and fixture harness before any later phase adds behavior:

  1. tpm-core — shared primitives: context, handles, state machine (§11, §12).
  2. tpm-crypto — cryptographic execution engine (§14).
  3. tpm-command-engine — binary protocol, frame decode, dispatch (§13).
  4. tpm-persistence — WAL, snapshot, integrity trees (§16).
  5. tpm-pcr — PCR banks and measured-boot extension (§15).
  6. tpm-policy — composable authorization evaluator (§17).
  7. enclave-runtime — isolation scheduler, quotas, cancellation (§18).
  8. attestation-service — quotes, verifier, trust anchors (§19).
  9. eventlog-engine — append-only event records feeding replay (§12, §16).
  10. replay-engine — deterministic recorder and re-execution (§20).
  11. telemetry-stack — metrics, tracing, structured logs (§12, §24).
  12. conformance-harness — fixture loader, differential runner (§12, §26).
  13. fault-injection-framework — disk faults, scheduler stalls, corruption injectors (§21, §26).
  14. cli-shell — operator CLI (tpmsim) for inspection and replay tooling (§20).
  15. grpc-control-plane — gRPC/Unix-socket transport gateway (§13).

System Boundaries

Provides:

  • a TPM-inspired command engine (create-key, quote, extend-pcr, nv-write, policy commands),
  • a software enclave runtime with cooperative scheduling and memory quotas,
  • encrypted crash-safe persistence with WAL + snapshot + integrity-tree verification,
  • remote attestation primitives (quote generation, verifier API, trust-anchor chains),
  • deterministic replay of every externally visible mutation,
  • a conformance-fixture and fault-injection framework for regression and chaos testing.

Delegates (relies on, does not reimplement):

  • transport-layer security (TLS termination delegated to rustls at the gRPC boundary),
  • OS-level process isolation (delegated to the host kernel; the enclave boundary is a software abstraction, not a hardware ring transition),
  • underlying disk durability (delegated to fsync/fdatasync semantics of the host filesystem).

Does NOT provide:

  • actual hardware TPM chip access or TPM passthrough,
  • Intel SGX, AMD SEV, or ARM TrustZone integration,
  • physical side-channel resistance or speculative-execution mitigation,
  • a kernel-mode hypervisor,
  • hardware DMA isolation or certified FIPS 140-3 validation.

Non-Goals

Not a certified security module. Not a drop-in TPM 2.0 replacement for firmware attestation. Not a general-purpose confidential-computing hypervisor. Not optimized for embedded/low-memory targets.

Deployment Model

Primary: Linux x86_64 and ARM64, containerized CI execution, Kubernetes integration testing, bare-metal deterministic benchmarking. Secondary: macOS development builds, Windows WSL validation. Runtime topology: user-space daemon (tpmsimd) + isolated worker pool (crypto + enclave workers) + encrypted persistence volume + optional gRPC control plane (grpc-control-plane), fronted by a Unix domain socket for local low-latency clients and gRPC/TCP for remote verifiers.

Target Operators

Infrastructure security engineers, platform SRE teams, attestation-infrastructure maintainers, distributed-systems researchers running conformance suites against real TPM stacks (swtpm, tpm2-tss) for differential validation.

What Later Phases Unlock

Phase 1 (§13) unlocks a fuzzable wire protocol. Phase 2 (§14) unlocks real cryptographic sealing and quote signing. Phase 3 (§15) unlocks measured-boot lineage. Phase 4 (§16) unlocks crash-safe persistence — nothing before it survives a kill -9. Phase 5 (§17) unlocks authorization; Phase 6 (§18) unlocks multi-tenant isolation; Phase 7 (§19) unlocks remote trust verification; Phase 8 (§20) unlocks forensic replay; Phase 9 (§21) unlocks production hardening and soak-validated release.

Recommended Language and Rationale

Rust, chosen for: deterministic ownership semantics that make "singular ownership of key material" (§6 P3) a compiler-enforced invariant rather than a convention; memory safety without GC pauses (GC pause jitter would corrupt p99 latency budgets in §4); Send/Sync bounds that make the enclave-isolation boundary (§18) statically checkable; zero-copy bytes/prost serialization for the wire protocol (§13); a mature RustCrypto/ring ecosystem (§14); cargo-fuzz and loom/cargo-careful for concurrency and parser fuzzing (§26); and Nix + locked Cargo.lock for reproducible builds (§27).

Rejected: Go — GC pauses and weaker ownership tracking make secure key-material zeroization (ADR-01) unenforceable at compile time; acceptable only for interoperability clients, not the trust kernel. C++ — manual memory management raises use-after-free risk directly inside the security boundary this system exists to model; acceptable only where FFI to a hardware SDK is unavoidable, which this project has none of. Python — no compile-time memory-safety or concurrency guarantees; retained only as secondary tooling for fixture generation (§26).

Prerequisites

Operating-system internals, process isolation, virtual memory, concurrency control and lock-free programming, applied cryptography (AEAD, HKDF, RSA/ECC), TPM 2.0 architecture, enclave systems (SGX/SEV/TrustZone at a conceptual level), asynchronous runtimes (tokio), storage-engine internals and write-ahead logging, binary protocol design, deterministic-replay systems, observability engineering, incident-response workflow.

Estimated Timeline

Phase 0: 10 weeks minimum, 14 weeks realistic. Full implementation (Phases 0–9): 8–14 months. Production hardening beyond Phase 9: additional 4–6 months (extended soak, external audit, compatibility-matrix validation against swtpm/tpm2-tss).

2. Why Build This

Historical and Systems Importance

Trusted-computing primitives underpin secure boot, measured boot, hardware attestation, confidential computing, secure credential storage, cloud workload isolation, encrypted-VM infrastructure, and root-of-trust architectures. Modern distributed infrastructure increasingly depends on enclave-backed trust verification (confidential VMs, remote-attested service meshes). Understanding enclave systems requires simultaneously reasoning about cryptographic identity, persistence semantics, concurrency isolation, scheduler correctness, deterministic replay, trust chains, policy engines, and fault recovery — a rare combination that most single-domain systems projects never force together.

Systems Knowledge Developed

Cryptographic protocol engineering; systems concurrency design; deterministic state-machine engineering; secure persistence architecture (WAL + integrity trees); isolation-runtime design; attestation-protocol reasoning; replay-based debugging; observability-first runtime engineering; crash-consistency engineering (Pillai et al., applied in §16); policy-evaluation correctness under fail-closed semantics.

Engineering Muscles Exercised

Bounded resource management under adversarial input; state-machine design with byte-identical replay; binary protocol evolution across wire versions; crash-safe persistence under SIGKILL at arbitrary instruction boundaries; secure key-lifecycle handling (creation → lineage → zeroization); asynchronous scheduler correctness under starvation and cancellation races; cryptographic API design that fails closed; operational telemetry design; recovery engineering.

Related and Comparable Systems

Strongly related domains: kernels, hypervisors, secure-boot chains, distributed-consensus systems, cryptographic HSM systems, storage engines with WAL, capability systems, database WAL engines, deterministic runtimes, secure microkernels. Comparable architectural systems (real, named, used throughout §31): TPM 2.0 reference implementations (swtpm, tpm2-tss), Intel SGX runtime stacks, AWS Nitro Enclaves, AMD SEV firmware stacks, Keylime attestation, SoftHSM, HashiCorp Vault seal systems.

Calibration Value

An engineer who independently builds this system can design secure state machines, reason about cryptographic isolation boundaries, debug distributed trust failures from replay traces, implement replay-safe crash-consistent persistence, and build operationally safe security infrastructure — skills that generalize to consensus systems, storage engines, and any system where "correct" and "observable under failure" must hold simultaneously.

What Mastery Looks Like

  • Can explain why PCR extension (§15) must be one-way and ordered, and derive the collision- resistance argument from the hash-chain construction — competency gained in Phase 3 (§15).
  • Can design a WAL + snapshot recovery path that survives SIGKILL at any commit boundary and prove it with fixtures, not assertions — Phase 4 (§16).
  • Can build a policy evaluator that fails closed on ambiguity and is byte-identical on replay — Phase 5 (§17).
  • Can reason about cooperative-scheduler starvation and quota enforcement under adversarial task submission — Phase 6 (§18).
  • Can construct and verify a remote-attestation quote chain, including anti-replay nonce windows — Phase 7 (§19).
  • Can build a deterministic replay engine that detects divergence from a single execution-hash mismatch — Phase 8 (§20).
  • Can take a security-sensitive system through soak testing, compatibility-matrix validation, and a production release gate — Phase 9 (§21).

Subsystem Descriptions

CLI / SDK Clients — untrusted callers. Never touch persistence or crypto internals directly. Every command is versioned and sequence-numbered; SDKs must preserve replay determinism through canonical (deterministic-field-order) serialization.

Transport / RPC Gateway (grpc-control-plane) — terminates transport sessions, validates framing, enforces per-session quotas, normalizes requests into internal command envelopes. This is the primary trust boundary between untrusted callers and trusted runtime components (marked TRUST BOUNDARY in the diagram).

Command Validation Layer (tpm-command-engine) — replay prevention, policy pre-check, authorization checking, command sequencing, session validation, bounded resource enforcement. Rejects malformed or ambiguous requests before any state mutation reaches the trust kernel.

TPM Command Engine — the canonical TPM-inspired command state machine. Commands are deterministic; side-effect ordering is serialized through explicit transaction boundaries in tpm-persistence.

PCR Manager (tpm-pcr) — PCR banks, extension semantics, reset semantics, hashing invariants, replay-safe measurement ordering.

Policy Evaluator (tpm-policy) — composable authorization: PCR predicates, locality constraints, command lineage, session assertions, evaluated fail-closed.

Key Hierarchy Manager (tpm-crypto) — endorsement keys, storage root keys, sealing keys, transient handles, hierarchy ownership, lifecycle transitions.

Secure Persistence Layer (tpm-persistence) — encrypted crash-safe persistence: append-only WAL, integrity-verification trees, monotonic sequence guarantees, replay validation. Marks the persistence boundary: nothing below this line is visible to a client without going through integrity verification.

Crypto Execution Engine (tpm-crypto) — all cryptographic operations, isolated worker pool, deterministic audit instrumentation.

Enclave Runtime Scheduler (enclave-runtime) — software-defined isolation contexts, cooperative scheduling, memory quotas, execution accounting, cancellation. Marks the concurrency boundary: task state for one enclave context is never visible to another.

Event Log / Replay (eventlog-engine, replay-engine) — deterministic execution records for replay-based debugging and conformance validation. The system's only queue that is explicitly unbounded-in-retention (bounded by disk, not by count) because forensic replay depends on it.

Telemetry Stack (telemetry-stack) — metrics, traces, structured logs, crash dumps, replay snapshots, queue-depth statistics, latency histograms. An external interface consumed by Prometheus/OTel collectors outside the trust boundary.

Attestation / Verification (attestation-service) — signed attestation evidence, trust-chain validation, PCR-lineage verification, quote API. The system's other external interface: remote verifiers call in over gRPC and receive only signed, replayable evidence — never raw state.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every state transition must be replayable byte- identically. Tradeoff: forbids convenience APIs that read wall-clock time or OS entropy directly inside the trust kernel. Operational: replay-hash mismatch is a page-able signal, not a warning. Violated: attestation histories become unverifiable and postmortems cannot reconstruct the failing sequence.
  • P2 — Crash-Only Semantics. Rule: assume abrupt termination at any instruction boundary (SIGKILL, kernel panic, power loss). Tradeoff: every mutation must be WAL-durable before it is observable, costing one fsync on the critical path. Operational: recovery path is the only startup path, never a special case. Violated: partially committed hierarchy state corrupts trust roots silently.
  • P3 — Explicit Ownership. Rule: security-sensitive resources (key material, monotonic counters, policy sessions) have exactly one owner at a time; shared mutable ownership is forbidden. Tradeoff: forces explicit handle-transfer protocols instead of shared references. Operational: ownership violations are compile-time errors in Rust, not runtime checks. Violated: a cloned key handle makes zeroization unenforceable and use-after-revoke possible.
  • P4 — Replayability First. Rule: every externally visible mutation emits a replay artifact before it is acknowledged to the caller. Tradeoff: adds one serialization + append per mutation. Operational: replay IDs are mandatory fields on every log line and trace span. Violated: forensic analysis and conformance debugging lose their evidentiary trail.
  • P5 — Bounded Resource Usage. Rule: no unbounded queues, allocations, or session growth anywhere in the runtime. Tradeoff: callers see explicit backpressure/rejection instead of unbounded buffering. Operational: every queue exports a depth metric with an alert threshold. Violated: a slow consumer becomes an unbounded-memory denial-of-service vector.
  • P6 — Stable Wire Compatibility. Rule: protocol evolution preserves backward-compatible decoding across minor versions. Tradeoff: new fields must be additive and optional, never reordering existing ones. Operational: a compatibility-matrix CI job decodes N-1 minor-version fixtures on every change. Violated: a rolling upgrade partitions the cluster on wire mismatch.
  • P7 — Observability by Default. Rule: every critical subsystem exports metrics, traces, queue depths, latency histograms, and replay identifiers without an opt-in flag. Tradeoff: baseline telemetry overhead is paid even in the common case. Operational: dashboards exist before a feature ships, not after an incident. Violated: an operator cannot distinguish "slow" from "stuck" during an incident.
  • P8 — Isolation Before Optimization. Rule: enclave isolation invariants outrank throughput. Tradeoff: cooperative scheduling accepts some context-switch overhead rather than sharing state across enclave contexts for speed. Operational: no fast path may bypass the quota accountant. Violated: one enclave context can starve or read residual state from another.
  • P9 — Immutable Audit Trails. Rule: event records are append-only; mutation is forbidden outside explicit snapshot compaction. Tradeoff: storage grows monotonically between compactions. Operational: compaction is a scheduled, observable job, never an implicit side effect of a read. Violated: a tampered event log invalidates every attestation history built on top of it.
  • P10 — Fail Closed. Rule: authorization uncertainty (ambiguous policy, unreachable session state, malformed assertion) results in rejection, never in a best-effort allow. Tradeoff: false rejections under transient ambiguity are acceptable; false allows are not. Operational: every fail-closed rejection increments a denial counter with a reason label. Violated: a policy- evaluation panic that defaults to "allow" turns the authorization layer into a no-op.
  • P11 — Integrity Before Availability. Rule: corrupted persistence causes subsystem quarantine, not degraded-but-running service. Tradeoff: a corrupted node stops serving even if the corruption is localized. Operational: quarantine state is externally visible (QUARANTINED in §8) and pages an operator. Violated: a subsystem silently serves partially corrupted trust state to a remote verifier.
  • P12 — Explicit Versioning. Rule: every persisted object carries a schema version, checksum, and compatibility metadata. Tradeoff: adds ~12 bytes of framing overhead per persisted record. Operational: a version mismatch during recovery is a structured, logged event, not a silent reinterpretation. Violated: a schema-drifted snapshot is misparsed as a different, structurally compatible-looking record.

Debugging methodology: every invariant above has exactly one assertion site in the deterministic simulator (conformance-harness, §12/§26) — no invariant is checked implicitly by "it didn't crash." Core Entities

struct TPMContext

  monotonic_counters: BTreeMap<CounterId, u64>,

Represents the global mutable trust state, owned exclusively by the command-execution actor in tpm-core (P3). Never cloned; snapshots serialize a point-in-time view, they do not alias it.

struct EnclaveContext
  enclave_id: EnclaveId,
  scheduler_state: SchedulerState,
  memory_quota: QuotaBytes,
  execution_lineage: ExecutionLineage,
  attestation_state: AttestationState,

Represents isolated execution state for one enclave (I9). One EnclaveContext per scheduled tenant; never shared across contexts.

PolicySession — composable authorization evaluation state (§17); EventRecord — append-only immutable mutation record (§16, I7).

TPM Command Envelope (wire layout)

struct CommandEnvelope
  version: u16,
  sequence_number: u64,
  command_code: CommandCode,
  authorization_area: AuthArea,
  payload: Bytes,
  checksum: [u8; 32],

version gates decode compatibility (P6, P12). sequence_number is the replay-ordering key (I1, I4). checksum is CRC32C for framing integrity, separate from any cryptographic MAC inside payload.

Command Lifecycle

Client -> Gateway -> Validation -> Policy Evaluation
       -> Command Execution -> Persistence Commit
       -> Event Emission -> Response Serialization

Every arrow is a synchronous handoff within one command's causal chain; no stage may reorder past another for the same sequence_number (I1, I4).

PCR Extension Flow

new_pcr = HASH(old_pcr || digest) — append-only lineage, replay-deterministic, collision- resistant lineage tracking (I2). HASH is the PCR bank's configured algorithm (SHA-256 or SHA-384 bank, §15); banks never mix algorithms mid-lineage.

State Machine

State Meaning Exit Conditions
INIT bootstrap, integrity verification running integrity verification complete → READY
READY accepting commands shutdown signal → INIT (next boot); corruption → QUARANTINED
RECOVERY WAL replay in progress replay success → READY; replay divergence → QUARANTINED
DEGRADED partial subsystem failure, reduced command set operator recovery → READY
QUARANTINED corruption detected manual intervention only; no automatic exit

Failure Path Example — Malformed Command

  1. framing validation fails at the Command Validation Layer;
  2. event logged (EventRecord, immutable, I7);
  3. replay artifact generated (P4);
  4. metrics incremented (protocol_frame_rejected_total);
  5. connection quota adjusted (repeated malformed frames tighten the session's quota);
  6. response rejected with a structured error code, never a partial response.

11. Core Schema & Types

struct TPMHandle
  handle_id: u64,
  handle_type: HandleType,
  generation: u32,
  owner_session: SessionId,

Ownership: single owner session (P3); unique per generation, never cloned. Mutation: generation increments on reissue, immutable otherwise. Concurrency: read under the tpm-core handle-table lock, writes serialized through the command executor. Persistence: not directly persisted; derived from EventRecord replay on recovery. Serialization: not wire-visible; internal only. Compatibility: generation field added in v1, never removed (P6).

struct PCRBank
  algorithm: HashAlgorithm,
  registers: Vec<PCRValue>,
  epoch: u64,

Ownership: owned by TPMContext, one bank per configured algorithm. Mutation: append-only extension (I2); reset requires explicit locality authorization. Concurrency: extends serialize through the PCR-manager actor, no cross-bank locking needed. Persistence: snapshotted whole; WAL records individual extends. Serialization: PersistenceFrame-wrapped on disk, protobuf on the attestation wire path. Compatibility: algorithm is fixed at bank-creation time, never migrated in place — a new algorithm means a new bank.

struct EventRecord
  event_id: u128,
  sequence: u64,
  timestamp: u64,
  command: CommandCode,
  payload_hash: [u8; 32],
  replay_hash: [u8; 32],

Ownership: owned by eventlog-engine, append-only (I7, P9). Mutation: none after commit. Concurrency: appended under a single-writer sequence lock; read concurrently by replay consumers. Persistence: the durability unit of the event log; every record is fsync-ordered before ack. Serialization: fixed-width binary append-log format (ADR-05). Compatibility: version lives in the enclosing PersistenceFrame, not duplicated per record.

struct EnclaveTask
  task_id: TaskId,
  enclave_id: EnclaveId,
  quota: QuotaBytes,
  scheduling_class: SchedulingClass,
  cancellation_token: CancellationToken,

Ownership: owned by exactly one enclave-runtime scheduler queue at a time (I9). Mutation: quota decremented by the accountant, never by the task itself. Concurrency: cancellation_token is the only field safely shared (atomic flag) across the owning task and the canceller. Persistence: transient, never persisted — tasks are re-derived from EnclaveContext on restart. Serialization: none; process-local only. Compatibility: not wire-visible.

struct PersistenceFrame
  version: u16,
  sequence: u64,
  checksum: u32,
  payload_size: u32,
  payload: Bytes,

Ownership: owned by the persistence writer for the duration of one append; ownership transfers to the WAL segment on fsync ack. Mutation: immutable once written (I7 analog for the storage layer). Concurrency: writes serialized per-segment; reads are lock-free once a segment is sealed. Persistence: the on-disk envelope for every WAL entry and snapshot chunk (P12). Serialization: custom fixed-header binary format, checksum is CRC32C over payload. Compatibility: version gates decode path; unknown versions quarantine the segment rather than best-effort parse.

enum PolicyExpression
  PCRMatch(PCRPredicate),
  SignedAssertion(AssertionRef),
  Locality(LocalityBound),
  CounterThreshold(CounterId, u64),
  CompositeAnd(Vec<PolicyExpression>),
  CompositeOr(Vec<PolicyExpression>),

Ownership: owned by the PolicySession that parsed it; immutable after parse. Mutation: none — re-parsing produces a new tree rather than mutating in place. Concurrency: shared read-only across concurrent evaluations of the same session (I4 requires this to be safe). Persistence: persisted as parsed bytes, re-parsed (not re-evaluated) on replay to preserve I4. Serialization: protobuf oneof on the wire, matching the enum shape 1:1. Compatibility: new variants are additive; an unknown variant on decode is a hard reject, never a silent no-op.

struct CommandEnvelope
  version: u16,
  sequence_number: u64,
  command_code: CommandCode,
  authorization_area: AuthArea,
  payload: Bytes,
  checksum: [u8; 32],

Ownership: owned by the gateway until dispatch, then transferred to the command executor. Mutation: immutable after checksum validation. Concurrency: one envelope, one dispatch — no sharing. Persistence: the payload survives into EventRecord.payload_hash; the envelope itself is not persisted verbatim. Serialization: the wire format (§8); protobuf-framed with a CBOR fallback decoder for interoperability testing. Compatibility: version field is the sole compatibility gate (P6, ADR-05).

struct AttestationReport
  report_id: u128,
  pcr_snapshot: Vec<PCRValue>,
  nonce: [u8; 32],
  signature: Signature,
  trust_anchor_id: TrustAnchorId,

Ownership: owned by attestation-service for the duration of quote assembly, then handed to the caller as an immutable value. Mutation: none after signing. Concurrency: signing serialized per key, report assembly parallel across requests. Persistence: not persisted long-term; reconstructible from EventRecord + PCR lineage for audit. Serialization: protobuf on the verifier wire path. Compatibility: trust_anchor_id allows rotating anchors without breaking historical report verification.

struct NvSlot
  index: NvIndex,
  attributes: NvAttributes,
  data: Bytes,
  write_counter: u64,

Ownership: owned by TPMContext.nv_indexes; one slot per index. Mutation: writes bump write_counter monotonically (I3). Concurrency: per-slot write lock, cross-slot reads unlocked. Persistence: snapshotted with the rest of TPMContext; WAL-logged per write. Serialization: PersistenceFrame-wrapped. Compatibility: attributes bitflags are additive only.

struct ReplayTrace
  trace_id: u128,
  origin_sequence_range: (u64, u64),
  scheduler_ordering: Vec<TaskId>,
  execution_hash: [u8; 32],

Ownership: owned by replay-engine for the trace's retention window (bounded by the §4 replay- buffer ceiling before disk rotation). Mutation: append-only during recording, immutable once sealed. Concurrency: one recorder per process; readers (replay CLI) access sealed traces only. Persistence: written to the replay-artifact directory, never to the primary WAL. Serialization: binary append-log, mirrors EventRecord framing. Compatibility: execution_hash algorithm is pinned per trace format version; mixed-version comparison is rejected, not coerced.

Blast radius is build-time only — nothing here touches persisted trust state, so containment is "block merge," not "quarantine node." Deferred: cross-architecture (ARM64 vs x86_64) bit-identical reproducibility is PhaseDeferred("§12") pending a Nix cross-compilation toolchain — tracked in §35.

13. Phase 1 — Binary Protocol & Command Engine

13.1 Objectives

Implement the canonical command-envelope wire format, frame decoding, replay-safe sequencing, authorization routing, and deterministic dispatch in tpm-command-engine. Introduces the constraint that no malformed input may mutate state (P10, fail closed) before validation completes.

13.2 Detailed Implementation Steps

  • Implement tpm-command-engine::frame — a bounds-checked frame decoder for CommandEnvelope (§11), rejecting any length-prefix overrun before allocating the payload buffer. Anchor: Andriesse (2018) binary-parsing hardening, applied per §5.
  • Implement checksum validation (CRC32C over payload) as a mandatory pre-dispatch gate.
  • Implement replay-safe sequencing: monotonically increasing sequence_number per session, gap detection feeding I1-adjacent replay guarantees.
  • Define the command registry (CommandCode enum) and a dispatch table mapping code → handler, built at compile time (no runtime registration) to keep dispatch deterministic (P1).
  • Define transient-handle lifecycle hooks (tpm-core::handle), wiring I6 (handle revocation on expiration/eviction) into the dispatch path.
  • Add bounded request queues in grpc-control-plane per P5; queue depth caps at the §4 concurrency budget (10k sessions).
  • Implement malformed-frame quarantine: reject-and-log rather than best-effort reinterpretation.
  • Add protocol metrics (protocol_frame_rejected_total, protocol_dispatch_latency_seconds).
  • Implement the protocol fuzzing harness (fuzz/frame_decoder.rs) targeting the frame decoder under cargo-fuzz (ADR-13).
  • Implement backpressure semantics: explicit RESOURCE_EXHAUSTED rejection when a queue is full, never silent buffering (P5, ADR-21).

A runnable command engine that receives commands over the gRPC/Unix-socket gateway, validates framing, and dispatches to stub handlers — end to end, with zero unhandled panics under fuzzing.

13.4 Acceptance Criteria

  • Malformed frames are rejected deterministically: 100% of fuzz/frame_decoder.rs corpus crashes fixed, zero crashes after 4 CPU-hours of fuzzing.
  • Replay traces are byte-identical across 3 repeated executions of fixtures/protocol/replay- sequence-gap-003.
  • p99 dispatch latency for a valid frame < 1 ms measured via benchmarks/, well inside the §4 command-latency budget once policy/persistence stages are added later.

13.5 Conformance Fixtures

  • fixtures/protocol/frame-valid-001 — well-formed envelope, expects successful dispatch to a stub handler.
  • fixtures/protocol/frame-invalid-checksum-002 — corrupted checksum byte, expects deterministic rejection with CHECKSUM_MISMATCH.
  • fixtures/protocol/replay-sequence-gap-003 — a gap in sequence_number, expects rejection and a protocol_sequence_gap_total increment, never a silent skip.
  • fixtures/protocol/truncated-frame-004 — length prefix exceeds actual payload, expects rejection before allocation (regression fixture for a buffer-overrun-shaped bug class).

13.6 Pitfalls

  • Endian inconsistencies between the length prefix and payload — manifests as intermittent decode failures only on cross-architecture fixtures; root cause is mixing native-endian and wire-endian reads; debug via a fixed-endian round-trip fixture; recovery is standardizing on little-endian on the wire regardless of host.
  • Unchecked length prefixes — manifests as an allocation spike or OOM under a crafted frame; root cause is trusting the prefix before bounds-checking against the connection's quota; signal is a memory-usage metric spike correlated with one session; recovery is a hard length ceiling checked before allocation.
  • Handle-reuse races — manifests as a handler operating on a handle whose generation just rolled over; root cause is missing the generation check from I6; debug via replay trace diffing; recovery is enforcing generation-match at dispatch, not just at creation.

13.7 Performance Concerns

Parser branch prediction suffers on mixed valid/invalid frame mixes — keep the hot decode path branch-light by validating length and checksum before switching on command_code. Allocator churn from per-frame buffer allocation — pool buffers sized to the p99 payload size observed in benchmarks. Queue contention under 10k concurrent sessions — shard the bounded queue by session-id hash to avoid a single mutex becoming the bottleneck.

13.8 Edge Cases

Truncated frames (fixture 13.5-004); duplicated sequence numbers from a retrying client; replayed session tokens from a reconnecting client after a network partition; zero-length payloads on commands that require a body; a command_code valid in a newer protocol version than the decoder supports (must reject per P6, not guess).

13.9 Failure Analysis

Parser corruption risks process-wide desynchronization if a malformed frame is partially consumed before rejection. Mitigation: frame quarantine happens atomically — either the whole frame is consumed and rejected, or none of it is, verified by the truncated-frame-004 fixture. Blast radius is bounded to the offending session (the queue shard, per §13.7); other sessions are unaffected. TPM command passthrough to physical hardware and a QUIC-native attestation transport are both PhaseDeferred("§13"), tracked in §35 — neither changes this phase's decode-and-dispatch contract. Detection is immediate via protocol_frame_rejected_total; forensics rely on the replay artifact generated at rejection time (P4).

13.10 Operational Notes

Export: protocol_frame_rejected_total{reason}, protocol_parse_latency_seconds histogram, protocol_queue_depth gauge per shard. Tracing span: protocol.dispatch. Structured-log fields: session_id, sequence_number, command_code. Deployment: this phase ships behind a feature flag until Phase 4's persistence layer lands, since dispatch currently has nowhere durable to commit to.

14. Phase 2 — Cryptographic Execution Engine

14.1 Objectives

Implement isolated cryptographic execution workers and key-lifecycle primitives in tpm-crypto: AEAD, RSA hierarchy, ECC quote signing, HKDF, deterministic RNG, and secure zeroization. Introduces the constraint that key material has exactly one owner at all times (P3) and every crypto operation is auditable (P7).

14.2 Detailed Implementation Steps

  • Integrate AES-GCM via RustCrypto/ring (§1, §5); wire AES-NI detection with a documented software fallback (§12.8 edge case carried forward).
  • Implement the RSA key hierarchy (endorsement key → storage root key → child keys) enforcing I5 (child keys never outlive parent lineage) at creation time, not just at revoke time.
  • Implement ECC quote signing (P-256/P-384) for attestation-service consumption in §19; pin padding/format per RFC 8017 where RSA signing is configured (applied in §5).
  • Add HKDF derivation (RFC 5869) for sealing-key derivation from the storage root key.
  • Implement the deterministic RNG harness: a NIST SP 800-90A-shaped CTR_DRBG seeded from a recorded seed for replay (P1 — RNG output must be replayable, never live entropy inside the trust kernel).
  • Implement secure zeroization on key drop (zeroize crate), verified by a fixture that scans process memory after drop for the plaintext key pattern.
  • Implement the key-slot allocator: bounded slot table per P5, explicit SLOTS_EXHAUSTED rejection rather than unbounded growth.
  • Add key-lineage tracking (parent → child edges) feeding I5's cascade-revoke path.
  • Add a crypto worker pool (128 workers per §4) with NUMA-aware pinning (ADR-08 concurrency model).
  • Add crypto-operation telemetry: operation ID, latency, audit lineage per operation (P7).

14.3 Deliverable

An operational crypto subsystem: key creation, signing, sealing, and quote generation, callable from tpm-command-engine handlers, with all 128 workers passing NIST test vectors.

14.4 Acceptance Criteria

  • 100% of applicable NIST CAVP test vectors pass for AES-GCM, RSA, ECC, and HKDF.
  • Zero memory leaks under valgrind/miri across a 10,000-operation key-lifecycle fuzz run.
  • Replay determinism preserved: fixtures/crypto/hkdf-003 produces byte-identical derived keys across 5 replays.
  • p99 AES-GCM seal latency < 200 µs single-op, feeding the §4 command-latency budget.

14.5 Conformance Fixtures

  • fixtures/crypto/aes-gcm-001 — NIST vector encrypt/decrypt round trip, exact ciphertext match.
  • fixtures/crypto/ecc-sign-002 — deterministic ECDSA (RFC 6979-shaped) sign/verify round trip.
  • fixtures/crypto/hkdf-003 — RFC 5869 test-vector derivation, exact output-key match.
  • fixtures/crypto/nonce-reuse-004 — forces a nonce collision under fault injection, expects a hard reject, never silent reuse (regression fixture for a known AES-GCM catastrophic-failure class).
  • fixtures/crypto/zeroize-005 — post-drop memory scan finds no residual key bytes.

14.6 Pitfalls

  • Accidental key cloning via a Clone-derived struct — manifests as two live copies of secret material surviving one drop; root cause is deriving Clone on a type holding key bytes; debug via a compile-time lint (clippy::derive_partial_eq_without_eq-style custom lint); recovery is banning Clone on key-bearing types at the type-system level (P3).
  • Nonce reuse under concurrent access to the same key — manifests as AES-GCM confidentiality failure (fixture 14.5-004); root cause is a counter shared without atomic increment; debug via the nonce-reuse fixture; recovery is an atomic per-key nonce counter, never caller-supplied.
  • Entropy starvation on the deterministic RNG harness under high concurrency — manifests as workers blocking on reseed; root cause is a single shared DRBG instance; recovery is per-worker DRBG instances reseeded from a session-level seed tree.

14.7 Performance Concerns

AES batching across multiple small payloads reduces per-call overhead — batch at the worker-pool dispatch layer, not inside tpm-crypto's public API. CPU cache locality for RSA/ECC big-integer operations — pin workers to NUMA nodes matching the persistence layer's node to avoid cross-node memory traffic. Worker oversubscription past 64 physical cores degrades throughput — cap the pool at the §4 target of 128 workers regardless of core count above that.

14.8 Edge Cases

RNG exhaustion under a sustained key-generation burst; oversized payloads exceeding the AEAD single-call limit (must chunk, not silently truncate); invalid signatures presented for verification (must reject with a specific error, not panic); a key-slot request when the allocator is exhausted (P5 — explicit rejection).

14.9 Failure Analysis

A cryptographic-operation mismatch (wrong ciphertext, failed verify) indicates one of: replay divergence upstream, persistence corruption in a stored key, or serialization drift between wire and internal representation. Detection is immediate (operation fails its own self-check). Blast radius is contained to the requesting session's keys, not the whole hierarchy, unless the affected key is a parent — in which case I5's cascade-revoke widens the blast radius intentionally. An SGX/SEV hardware-backed key-sealing compatibility layer is PhaseDeferred("§14"), tracked in §35.

14.10 Operational Notes

Every cryptographic operation emits: operation_id, crypto_op_latency_seconds{algorithm}, crypto_audit_lineage (parent-key-id chain). Tracing span: crypto.execute. Rollback: a key- hierarchy corruption triggers P11 quarantine, not a partial-hierarchy rollback — trust state is all-or-nothing per hierarchy root.

15. Phase 3 — PCR & Measured-Boot Engine

15.1 Objectives

Implement measured-boot semantics: PCR banks, extend/reset, locality rules, and event-measurement records in tpm-pcr. Introduces I2 (ordered extension only) as an enforced, not advisory, constraint from the first commit.

15.2 Detailed Implementation Steps

  • Implement PCRBank (§11) with per-algorithm registers and an epoch counter incremented on reset.
  • Implement extend semantics: new_pcr = HASH(old_pcr || digest) (§8), serialized through a single per-bank extend lock to make concurrent extends deterministic-ordered rather than racily interleaved — anchor I2.
  • Implement locality rules: reset requires explicit locality authorization, checked against the requesting context's locality field before any register mutation.
  • Add event-measurement records feeding eventlog-engine (§12), giving every extend a corresponding immutable EventRecord (I7).
  • Implement replay validation: re-running the recorded extend sequence must reproduce the exact final PCR value (I8 applied at the PCR-bank granularity).
  • Add snapshot serialization for PCRBank via PersistenceFrame (§11).
  • Implement integrity checks: on load, verify the bank's checksum before trusting any register value; anchor Matetic et al. (2017) ROTE rollback-protection reasoning, applied per §5, for why a stale-but-checksum-valid snapshot is still a rollback risk without the monotonic counter tie-in from I3.

15.3 Deliverable

A measured-state engine supporting PCR extend, reset, and quote linkage — extend calls from tpm-command-engine now durably affect PCR state and are visible to attestation-service stubs.

15.4 Acceptance Criteria

  • Replay hashes stable across 10 repeated replays of fixtures/pcr/extend-sequence-001.
  • Event-log ordering preserved: extend records appear in eventlog-engine in the exact order submitted, verified against sequence_number.
  • PCR lineage deterministic under 3 concurrent extend attempts (§15.8), resolved to one well-defined winner order, never an undefined interleaving.
  • Extend throughput ≥ 50,000/sec single-bank, matching the §4 target.

15.5 Conformance Fixtures

  • fixtures/pcr/extend-sequence-001 — 1,000 sequential extends, expects a specific final digest.
  • fixtures/pcr/reset-locality-002 — reset attempted without required locality, expects rejection.
  • fixtures/pcr/concurrent-extend-003 — 3 concurrent extend requests on one bank, expects one deterministic serialized order and a matching replay hash.
  • fixtures/pcr/corrupted-bank-004 — checksum-corrupted snapshot on load, expects quarantine, not a best-effort partial load.

15.6 Pitfalls

  • Hash-ordering bugs from extending with digest || old_pcr instead of old_pcr || digest — manifests as a PCR value that matches no known-good reference measurement; root cause is operand order; debug by comparing against a reference swtpm extend of the same digest sequence; recovery is fixing operand order and re-deriving all downstream quotes.
  • Locality bypass via a reset path that doesn't check the locality field — manifests as an unauthorized reset succeeding; root cause is a second reset code path added later that skips the §15.2 check; recovery is centralizing all reset entry points through one authorization gate.
  • Inconsistent replay ordering under concurrent extends without the per-bank lock — manifests as replay hash mismatch (I8 violation) despite each individual extend being individually valid; recovery is the single per-bank extend lock from §15.2, never per-register locking.

15.7 Performance Concerns

Hashing throughput is the binding constraint for the 50k/sec extend target — use SHA-NI where available (§4 CPU assumptions), falling back to a software implementation with a telemetry flag. Event-serialization amplification: one EventRecord per extend adds a fixed overhead — batch event-log fsyncs (§16) rather than per-extend fsyncs to stay under the WAL fsync p99 budget.

15.8 Edge Cases

Simultaneous extend attempts on the same bank from different sessions (fixture 15.5-003); corrupted event logs discovered mid-replay (must halt replay and quarantine, not skip the bad record); a reset request during an in-flight extend (must serialize, not interleave); an extend digest of the wrong width for the bank's algorithm (reject, don't zero-pad).

15.9 Failure Analysis

PCR divergence invalidates attestation trust immediately — any quote issued against a divergent PCR value is a false attestation. Detection is the replay-hash check (I8) plus the integrity- tree checksum on load. Containment: quarantine the affected bank, not the whole TPMContext — other banks and NV indexes remain servable in DEGRADED state (§8). Postmortem guidance: always diff the full extend sequence against the replay trace before assuming hardware-equivalent behavior, since this is a software simulation with no hardware root to cross-check against.

15.10 Operational Notes

Export: pcr_extend_rate, pcr_mutation_total{bank}, quote_linkage_count. Tracing span: pcr.extend. Structured-log fields: bank_algorithm, epoch, sequence_number. Migration: adding a new bank algorithm is additive (ADR-05-style versioning) and never mutates an existing bank's algorithm field in place.

16. Phase 4 — Secure Persistence Layer (WAL & Snapshots)

16.1 Objectives

Implement encrypted crash-safe persistence in tpm-persistence: WAL append protocol, snapshot compaction, integrity trees, and recovery replay. This is the phase that makes P2 (crash-only semantics) real rather than aspirational — everything durable from Phases 1–3 now survives SIGKILL.

16.2 Detailed Implementation Steps

  • Implement the WAL append protocol: PersistenceFrame-wrapped records (§11), group-commit batched fsync bounded by the §4 32 MB in-memory buffer ceiling. Anchor: Ongaro & Ousterhout (2014) deterministic log-replication ordering, applied per §5.
  • Implement snapshot compaction: periodic whole-state snapshot with atomic rename-based publication (I11 — snapshot writes are atomic).
  • Add checksum validation (CRC32C per frame) and an integrity tree (Merkle-style, per-segment root) giving O(log n) tamper localization instead of O(n) full-segment rehash on suspected corruption.
  • Implement recovery replay: on startup, load the latest valid snapshot, then replay WAL entries with sequence_number greater than the snapshot's watermark (I1).
  • Implement corruption quarantine: any checksum or integrity-tree mismatch during replay halts recovery and transitions to QUARANTINED (§8), never a best-effort skip-and-continue.
  • Add fsync batching: group commits within a bounded window (tunable, default derived from the §4 25 ms WAL fsync p99 budget) to trade a small latency tax for throughput.
  • Implement persistence metrics: WAL lag, snapshot age, compaction duration (P7).

16.3 Deliverable

A crash-safe persistence engine: tpm-command-engine handlers now durably commit through WAL before acknowledgment, and a killed-and-restarted daemon recovers to the exact pre-crash state.

16.4 Acceptance Criteria

  • Survives 500 SIGKILL-during-commit trials (fixtures/wal/crash-mid-commit-001) with zero corrupted recoveries.
  • Replay recovery is deterministic: same WAL + snapshot always recovers to the same state hash.
  • Corruption is detected reliably: 100% of fixtures/wal/checksum-corruption-002 injections are caught before any corrupted data is served.
  • Integrity-replay validation completes in < 15 s for a 10 GB state, matching §4.
  • Persistence commit throughput ≥ 20,000/sec, matching §4; WAL fsync p99 < 25 ms.

16.5 Conformance Fixtures

  • fixtures/wal/crash-mid-commit-001 — SIGKILL injected at a randomized point mid-commit across 500 trials, expects clean recovery every time.
  • fixtures/wal/checksum-corruption-002 — a single flipped byte in a WAL segment, expects detection and quarantine, not a silently corrupted state.
  • fixtures/wal/partial-segment-003 — a WAL segment truncated mid-write (simulating disk-full), expects recovery to the last complete record, not a parse error that halts recovery entirely.
  • fixtures/wal/snapshot-race-004 — a snapshot compaction racing an in-flight commit, expects I1 (no snapshot references unapplied WAL) to hold.

16.6 Pitfalls

  • Torn writes on power loss (partial sector write) — manifests as a checksum mismatch on the last WAL record after an unclean shutdown; root cause is a write spanning a sector boundary without a write barrier; debug via the partial-segment-003 fixture; recovery is treating the last incomplete record as absent, not as corrupt-the-whole-segment.
  • fsync ordering bugs where the snapshot rename happens before the underlying data fsync completes — manifests as a snapshot that looks committed but loses data on crash; root cause is missing an explicit fsync-then-rename barrier; recovery is enforcing fsync(data) → fsync(dir) → rename order per I11.
  • Snapshot race conditions between the compactor and the live commit path — manifests as snapshot-race-004's failure mode; root cause is compaction reading a watermark that the commit path then moves past mid-compaction; recovery is a compaction-time write-lease that blocks new commits from advancing the watermark until compaction publishes.

16.7 Performance Concerns

Write amplification from per-frame checksums and integrity-tree updates — budget this against the 20k commits/sec target; batch integrity-tree updates per fsync group, not per frame. Compaction stalls: a naive stop-the-world compaction violates P8 (isolation before optimization applies to availability too) — compaction must run incrementally, never blocking the command path for more than one fsync-group duration. Cache invalidation: snapshot load on recovery should stream rather than materialize the whole 10 GB state before validating, to keep the §4 15 s recovery budget.

16.8 Edge Cases

Disk-full mid-WAL-append (must reject the commit, not corrupt the segment); a WAL segment with a version newer than the running binary understands (P6 — reject, don't guess); a snapshot and WAL from different schema versions after a partial upgrade; clock skew between the snapshot timestamp and the WAL segment timestamps (must not be used for ordering — only sequence_number is authoritative, per P1).

16.9 Failure Analysis

Corruption containment must prevent trust-state leakage: a quarantined node must not serve any command that touches the corrupted region, even read-only ones, since a corrupted PCR or key hierarchy cannot be trusted to be internally consistent. Detection is the integrity-tree check on every load. Blast radius: quarantine is scoped to the smallest containing integrity-tree subtree when possible (§16.2), falling back to whole-TPMContext quarantine if the corruption is in shared metadata. Recovery path is always operator-confirmed rollback to the last known-good snapshot, never automatic silent rollback (P11).

16.10 Operational Notes

Export: wal_lag_seconds, snapshot_age_seconds, compaction_duration_seconds, persistence_commit_latency_seconds. Tracing span: persistence.commit. Structured-log fields: segment_id, watermark_sequence. Deployment: persistence volume must be a dedicated, separately monitored mount (§24) — co-locating it with the OS root volume risks disk-full false correlation with unrelated OS activity.

17. Phase 5 — Policy Evaluation Engine

17.1 Objectives

Implement composable authorization evaluation in tpm-policy: expression parsing, composite policies, signed assertions, and replay-safe evaluation. Introduces P10 (fail closed) as an enforced gate on every command from this phase forward.

17.2 Detailed Implementation Steps

  • Implement the expression parser for PolicyExpression (§11) — bounds-checked, rejecting cyclic or unbounded-depth trees before evaluation (P5).
  • Implement composite policies (CompositeAnd/CompositeOr) with short-circuit evaluation defined to be replay-identical regardless of evaluation order chosen at runtime — anchor I4.
  • Implement signed assertions (SignedAssertion) verified against tpm-crypto's ECC/RSA verification path (§14), never against a locally cached "trusted" flag.
  • Add replay-safe evaluation: policy evaluation reads only from the TPMContext snapshot visible at the command's sequence_number, never from live mutable state that could change mid- evaluation.
  • Implement a policy cache keyed by (policy_hash, context_epoch), invalidated on any PCR epoch change (§15) to prevent stale-epoch cache poisoning.
  • Add authorization telemetry: denial counters labeled by rejection reason (P7, P10).

17.3 Deliverable

A deterministic policy evaluator wired into tpm-command-engine's dispatch path (§13): every command now passes through policy evaluation before execution, with composite PCR + locality + counter-threshold policies fully evaluable.

17.4 Acceptance Criteria

  • Replay deterministic: fixtures/policy/composite-and-001 produces identical allow/deny across 10 replays.
  • Malformed policies rejected: fixtures/policy/cyclic-policy-003 rejected at parse time, never reaching evaluation.
  • Evaluation latency p99 < 500 µs single-policy, keeping policy evaluation off the critical path of the §4 10 ms p95 command-latency budget.

17.5 Conformance Fixtures

  • fixtures/policy/composite-and-001 — a 3-term CompositeAnd (PCR match + locality + counter threshold), expects deterministic allow.
  • fixtures/policy/pcr-match-002 — a PCR-predicate policy evaluated against a stale epoch, expects cache invalidation and re-evaluation, not a stale allow.
  • fixtures/policy/cyclic-policy-003 — a self-referential composite policy, expects parse-time rejection.
  • fixtures/policy/stale-lineage-004 — an assertion referencing a revoked key lineage, expects fail-closed rejection.

17.6 Pitfalls

  • Policy-cache poisoning from caching across a PCR epoch boundary — manifests as a stale allow after a PCR reset that should have invalidated the policy's PCR predicate; root cause is a cache key missing the epoch; debug via pcr-match-002; recovery is epoch-scoped cache keys.
  • Short-circuit inconsistency where CompositeAnd/CompositeOr evaluate operands in a different order on replay than on original execution — manifests as I4 violation only under composite policies with side-effect-free-but-order-sensitive sub-evaluations (e.g., a counter-threshold check that reads a counter mid-mutation); recovery is defining a canonical left-to-right evaluation order and enforcing it identically on replay.
  • Fail-open defaults from an unhandled PolicyExpression variant — manifests as a new variant added in a later change silently matching "true" in an exhaustive-looking match that has a catch-all arm; recovery is banning catch-all arms on PolicyExpression matches via lint (P10).

17.7 Performance Concerns

Branch-heavy evaluation for deep composite trees — flatten common 2–3 term policies into a specialized fast path rather than always walking the general tree interpreter. Expression allocation churn from re-parsing on cache miss — pool parsed-expression allocations keyed by policy_hash since the same policy text recurs across many sessions.

17.8 Edge Cases

Cyclic policies (fixture 17.5-003); stale lineage references to a revoked key (fixture 17.5-004); a policy referencing an NV index that doesn't exist; a counter-threshold policy where the threshold counter itself is concurrently being written (must read a consistent snapshot, per §17.2); an empty CompositeAnd (vacuously true — must be an explicit design decision, documented, not accidental).

17.9 Failure Analysis

Policy ambiguity must fail closed (P10) — an evaluator panic, timeout, or unresolvable reference all map to a hard deny, never a default allow. Detection is immediate (the evaluator itself observes the ambiguity). Blast radius is the single command being authorized; it does not propagate to other sessions. Operator visibility: denial-reason counters spike distinctly from "expected" denials (wrong PCR value) versus "ambiguous" denials (parse/reference errors), enabling postmortem triage without reading raw policy text.

17.10 Operational Notes

Export: policy_denial_total{reason}, policy_eval_latency_seconds, policy_cache_hit_ratio. Tracing span: policy.evaluate. Structured-log fields: policy_hash, context_epoch, session_id. Compatibility: new PolicyExpression variants are additive only (§11); a policy using an unknown variant on decode is a hard reject, matching P6.

18. Phase 6 — Enclave Runtime Scheduler

18.1 Objectives

Implement the isolated execution scheduler in enclave-runtime: enclave contexts, quota accounting, cooperative scheduling, cancellation, and bounded mailboxes. Introduces I9 (memory isolation between contexts) and I12 (quota never negative) as compiler- and runtime-checked invariants.

18.2 Detailed Implementation Steps

  • Implement EnclaveContext (§11) and its scheduler-visible EnclaveTask (§11), one task table per context, never a shared global task table across contexts (P8, anchor: Costan & Devadas 2016 SGX isolation model, Costan/Lebedev/Devadas 2016 Sanctum, applied per §5).
  • Add quota accounting: an atomic per-context debit/credit accountant enforcing I12 at every mutation site, not just at task-admission time.
  • Implement cooperative scheduling: a work-stealing-free, per-context run queue with explicit yield points, avoiding preemption races (ADR-08).
  • Implement cancellation semantics via CancellationToken (§11) — cooperative check-and-yield, not forced thread termination, to keep persistence commits (§16) from being interrupted mid-write.
  • Implement bounded mailboxes per context (P5) — a full mailbox rejects new messages rather than growing unboundedly.
  • Add isolation guards: boundary-crossing canary checks (§7 I9) verifying no context's memory region is reachable from another's task closure.
  • Implement scheduler tracing: every context switch emits a span (P7).

18.3 Deliverable

A runnable multi-tenant enclave runtime: up to 512 concurrent enclave contexts (§4), each isolated, quota-enforced, and cancellable, hosting the crypto and PCR operations from Phases 2–3 as scheduled tasks rather than direct calls.

18.4 Acceptance Criteria

  • Quotas enforced: fixtures/scheduler/quota-enforcement-001 — a context exceeding its 64 MB default quota (§4) is denied further allocation, never OOM-killed silently.
  • Starvation prevented: fixtures/scheduler/starvation-002 — under 512 contexts submitting work continuously, the lowest-priority context still makes forward progress within a bounded number of scheduler ticks.
  • Replay deterministic: scheduler ordering recorded and replayed produces the identical task interleaving, feeding I8 via replay-engine (§20).
  • Context-switch throughput ≥ 250,000/sec across 512 contexts, matching §4.

18.5 Conformance Fixtures

  • fixtures/scheduler/quota-enforcement-001 — a context allocating past its quota, expects rejection at the exact byte over the limit, not a fuzzy threshold.
  • fixtures/scheduler/starvation-002 — 512 contexts under sustained load, expects bounded max wait-time per context.
  • fixtures/scheduler/cancellation-race-003 — cancellation issued mid-yield-point, expects clean teardown, no partial-state leak into a subsequent task reusing the same slot.
  • fixtures/scheduler/nested-cancellation-004 — a cancelled context that itself owns sub-tasks, expects cascading cancellation, not orphaned sub-tasks.

18.6 Pitfalls

  • Deadlocks from a context awaiting its own quota release inside a callback holding the quota lock — manifests as a hung context that never times out; root cause is re-entrant locking around the accountant; debug via tokio-console task-dump; recovery is making the accountant lock-free (atomic compare-and-swap) rather than mutex-guarded.
  • Runaway allocations from a task that yields but never releases its partial allocation — manifests as quota exhaustion despite low apparent activity; root cause is missing a yield-point cleanup hook; recovery is RAII-style quota guards tied to task lifetime, not manual release calls.
  • Cancellation races where a cancelled task's in-flight persistence commit (§16) is torn — manifests as a WAL entry with no corresponding task outcome; root cause is cancelling without waiting for the commit's fsync ack; recovery is making cancellation cooperative-only at yield points that exclude in-flight commits (§18.2).

18.7 Performance Concerns

Context-switch overhead is the binding constraint for the 250k/sec target (§4) — keep per-switch work to queue-pointer manipulation only, no allocation on the switch path. Queue contention across 512 per-context queues under a shared worker pool — shard workers by context-id hash to avoid a global scheduler lock.

18.8 Edge Cases

Nested cancellation (fixture 18.5-004); quota exhaustion exactly at the boundary byte (fixture 18.5-001); a context requesting more concurrent tasks than its mailbox bound allows; two contexts racing to acquire the last available worker slot in the pool; a context that never yields (must be detected by a watchdog and forcibly quarantined, not allowed to monopolize a worker indefinitely).

18.9 Failure Analysis

Scheduler corruption can invalidate enclave isolation itself — a bug here is categorically worse than a bug in any single subsystem, since it breaks the guarantee every other subsystem assumes. Detection: isolation-guard canary failures (I9) and quota-underflow assertions (I12). Blast radius: terminate only the offending context; per P8, isolation invariants outrank keeping a misbehaving context alive. Postmortem guidance: scheduler bugs are diagnosed from the replay trace first (§20), never from live-process inspection, since live inspection risks disturbing timing- sensitive reproduction. Enclave live migration, enclave snapshot replication, and a WebAssembly enclave runtime target are all PhaseDeferred("§18"), tracked in §35 — none is required for single-node isolation correctness.

18.10 Operational Notes

Export: scheduler_runnable_queue_depth, scheduler_task_latency_seconds, scheduler_preemption_total, enclave_memory_usage_bytes{enclave_id}. Tracing span: scheduler.context_switch. Structured-log fields: enclave_id, task_id, scheduling_class. Rollback: a scheduler code rollback requires draining all 512 contexts to a safe yield point first — never a hard restart mid-task.

19.1 Objectives

Implement quote generation and the verifier stack in attestation-service: attestation reports, verifier API, certificate chains, nonce validation, and anti-replay windows. Introduces I10 (single-use nonces) as the anti-replay backbone for remote trust establishment.

  • fixtures/attestation/malformed-quote-bundle-004 — a truncated certificate chain, expects rejection before signature verification is even attempted (fail fast on structural malformation).

19.6 Pitfalls

  • Nonce reuse from a client retry that resubmits the same nonce after a timeout — manifests as a legitimate retry being indistinguishable from a replay attack at the nonce layer alone; root cause is conflating "nonce reuse" with "attack" without a client-visible retry protocol; recovery is requiring clients to request a fresh nonce per attempt, enforced by the verifier rejecting reused nonces unconditionally (the client, not the server, absorbs the retry cost).
  • Clock-drift assumptions in the anti-replay window — manifests as legitimate requests rejected across a multi-region deployment with clock skew; root cause is using wall-clock deltas instead of the injected logical sequence from ADR-20; recovery is windowing on sequence number primarily, wall-clock as a secondary sanity bound only.

19.7 Performance Concerns

Signature-verification cost dominates verifier-side latency for RSA-signed reports — prefer ECC signing (§14) for the default hierarchy configuration to keep quote-generation p99 under the §4 75 ms budget; RSA remains available for interoperability fixtures against RSA-only reference verifiers.

19.8 Edge Cases

Expired trust roots (fixture 19.5-003); malformed quote bundles (fixture 19.5-004); a verifier request during an in-flight trust-anchor rotation (must resolve against whichever anchor was valid at report-signing time, not report-verification time); a quote request for a PCR bank that has been quarantined (§15.9) — must fail the request, not attest to a value known to be untrustworthy.

19.9 Failure Analysis

Attestation failures degrade trust establishment for the requesting verifier only — this system's own trust state is not compromised by a failed outbound attestation, only by a compromised inbound signing key (which is a §14/I5 concern, not an attestation-service concern). Detection: verifier-failure metrics distinguish "expected reject" (bad nonce, expired anchor) from "unexpected reject" (internal error), the latter paging an operator. Blast radius for a signing-key compromise is bounded by trust-anchor rotation (§19.2) — historical reports remain verifiable against the anchor active at signing time even after rotation. Distributed attestation federation across multiple verifier clusters is PhaseDeferred("§19"), tracked in §35.

19.10 Operational Notes

Track: attestation_quote_issuance_rate, attestation_verifier_failure_total{reason}, attestation_nonce_reuse_total (I10 telemetry). Tracing span: attestation.quote. Structured-log fields: report_id, trust_anchor_id, nonce_window_state. Deployment: verifier API is the second external interface (§3) and gets its own rate limit, independent of the command- engine gateway's quota.

20. Phase 8 — Replay & Deterministic Debugging

20.1 Objectives

Implement the replay engine and forensic tooling in replay-engine: scheduler-ordering recording, deterministic re-execution, divergence detection, and CLI tooling. This phase makes I8 (replay hash equality) mechanically checkable across the whole system rather than per-subsystem.

20.2 Detailed Implementation Steps

  • Implement ReplayTrace (§11) recording: scheduler ordering (§18) + command sequence (§13) + cryptographic operation IDs (§14), sealed on trace rotation.
  • Persist replay traces to the replay-artifact directory (§10 conformance/replay/), bounded by the §4 128 MB replay-buffer ceiling before forced rotation to disk.
  • Implement deterministic re-execution: replay a sealed trace against a fresh TPMContext initialized from the same starting snapshot, recomputing execution_hash end to end.
  • Add divergence detectors: a hash mismatch at any checkpoint (per-phase boundaries: post-dispatch, post-crypto, post-persistence-commit) localizes divergence to a specific subsystem instead of only reporting a whole-execution mismatch — anchor: Savage et al. (1997) Eraser's lockset- localization philosophy applied to hash checkpoints instead of memory accesses, per §5.
  • Add replay CLI tooling in cli-shell (tpmsim replay <trace-id>), exposing per-checkpoint divergence output for operator triage.

20.3 Deliverable

A replay-debuggable runtime: any production incident can be replayed offline from its ReplayTrace, reproducing the exact scheduler interleaving and cryptographic operation sequence that led to the observed state.

20.4 Acceptance Criteria

  • Replay hash equality: fixtures/replay/divergence-001 — a known-good trace replays to the identical execution_hash across 20 repeated replays.
  • Deterministic scheduler reproduction: the exact task-interleaving order from the original execution is reproduced, not merely an equivalent-outcome interleaving.
  • Divergence localization: an injected single-bit corruption in a mid-trace checkpoint is localized to the correct subsystem boundary in fixtures/replay/crash-recovery-002.

20.5 Conformance Fixtures

  • fixtures/replay/divergence-001 — a clean trace, expects zero divergence across 20 replays.
  • fixtures/replay/crash-recovery-002 — a trace spanning a SIGKILL-and-recover boundary (§16), expects the recovered portion to replay identically to the pre-crash portion's continuation.
  • fixtures/replay/hidden-entropy-003 — a trace containing an accidental live-clock read, expects the divergence detector to flag the exact checkpoint, not a generic "mismatch" error.
  • fixtures/replay/partial-artifact-004 — a trace truncated by an unclean shutdown mid-write, expects graceful partial-replay-with-warning, not a hard crash of the replay tool itself.

20.6 Pitfalls

  • Hidden entropy sources (a stray SystemTime::now() call inside a supposedly deterministic path) — manifests as intermittent, unreproducible divergence; root cause is bypassing the injected logical clock (ADR-20); debug via the hidden-entropy-003 fixture and a lint banning direct SystemTime/Instant reads inside trust-kernel crates; recovery is routing all time reads through the injected clock abstraction.
  • Clock-based divergence from using wall-clock deltas for any decision inside the trust kernel — same root cause as above, different manifestation (a timeout fires differently on replay than on original execution); recovery is identical.

20.7 Performance Concerns

Replay-storage overhead: every checkpoint hash adds bytes to the trace; budget checkpoint density against the §4 128 MB replay-buffer ceiling — checkpoint at phase boundaries (§20.2), not per- operation, to keep overhead sublinear in operation count.

20.8 Edge Cases

Partial replay artifacts from an unclean shutdown mid-trace-write (fixture 20.5-004); a trace recorded under an older binary version being replayed against a newer one (P6 — must reject incompatible trace versions, not attempt a lossy replay); a trace referencing a snapshot that has since been compacted away (must fail with a clear "snapshot unavailable" error, not silently replay against the wrong starting state).

20.9 Failure Analysis

Replay divergence indicates an invariant violation somewhere upstream — it is a symptom, not a root cause, and the localization from §20.2's checkpoints is what turns "replay diverged" into an actionable postmortem lead. Detection is the checkpoint-hash comparison itself. Blast radius is purely diagnostic — replay runs against a copy of state, never against the live TPMContext, so a replay divergence never itself corrupts production state. Postmortem guidance: always start triage at the earliest diverging checkpoint, not the final execution_hash mismatch, since later checkpoints inherit the corruption.

20.10 Operational Notes

Replay IDs (trace_id) are included in all critical logs from Phase 1 onward (retroactively wired in this phase's telemetry pass). Export: replay_divergence_total{checkpoint}, replay_storage_bytes. Tracing span: replay.reexecute. Deployment: the replay CLI runs offline against exported traces, never against the live daemon's in-memory state, keeping forensic replay from ever becoming an availability risk to production.

21. Phase 9 — Operational Hardening & Release

21.1 Objectives

Finalize production readiness: chaos testing, soak testing, compatibility-matrix validation, rolling-upgrade validation, backup/restore verification, SLO dashboards, and incident runbooks. This phase's scope is entirely operational — no new subsystem behavior is introduced, only validation and hardening of Phases 0–8.

21.2 Detailed Implementation Steps

  • Implement chaos testing in fault-injection-framework (§1): disk faults, scheduler stalls, corruption events injected against the full system, not unit-level mocks — anchor P11 (integrity before availability) as the property under test.
  • Implement soak testing: a 30-day continuous-load run tracking WAL lag, replay-divergence count, and memory growth for slow leaks invisible in short runs.
  • Implement compatibility-matrix validation: decode fixtures from the previous two minor versions against the current binary (P6, ADR-05), run as a scheduled CI matrix job.
  • Implement rolling-upgrade validation: a mixed-version cluster (N and N+1) processing live traffic without a wire-compatibility break, validated against docs/compatibility.md.
  • Implement backup/restore verification: a full snapshot + WAL export/import cycle against a fresh instance, validated bit-for-bit against the source instance's state hash.
  • Stand up SLO dashboards (§24) covering every §4 budget: latency, WAL lag, replay divergence, queue saturation, availability.
  • Write incident runbooks (docs/runbooks/) for each Failure Mode in §23, one runbook per class.

21.3 Deliverable

A production-ready release candidate: soak-validated, chaos-tested, compatibility-matrix-passing, with SLO dashboards live and runbooks published for every registered failure class.

21.4 Acceptance Criteria

  • 30-day soak run stable: zero unrecoverable corruption events, memory growth < 5% over the full window after excluding expected cache warm-up.
  • No unrecoverable corruption across 200 chaos-injection trials (fixtures/ops/backup-restore-002 family).
  • All §4 SLO targets met in the soak environment, cross-checked against §28's target table.
  • Rolling upgrade validated across 3 consecutive minor versions with zero client-visible errors.

21.5 Conformance Fixtures

  • fixtures/ops/rolling-upgrade-001 — a mixed N/N+1 cluster processing 10,000 commands, expects zero decode failures.
  • fixtures/ops/backup-restore-002 — full export/import cycle, expects bit-identical state hash.
  • fixtures/ops/chaos-disk-fault-003 — randomized disk-fault injection during sustained load, expects either clean commit or clean rejection, never silent corruption.
  • fixtures/ops/soak-memory-004 — a scaled-down 24-hour soak fixture used as a CI gate before the full 30-day run, expects bounded memory growth.

21.6 Pitfalls

  • Telemetry overload from soak-run metric cardinality (per-session labels accumulating over 30 days) — manifests as the telemetry pipeline itself becoming the bottleneck; root cause is unbounded label cardinality (violates P5 applied to observability, not just to queues); recovery is capping per-session labels and aggregating to per-shard cardinality for long-running metrics.
  • Upgrade schema drift where a rolling upgrade's N+1 node writes a snapshot field the N node's decoder doesn't recognize — manifests as decode failures during the rollback path of a bad upgrade; root cause is an additive field that wasn't actually optional at decode time; recovery is a compatibility-matrix CI gate (§21.2) that must pass before any release tag.

21.7 Performance Concerns

Observability amplification: soak-scale telemetry volume must not itself violate the §4 memory ceilings — cap histogram bucket counts and trace-sampling rates for the 30-day run specifically, distinct from the steady-state production sampling rate.

21.8 Edge Cases

Partial cluster upgrades where only some nodes complete the rolling upgrade before a rollback decision (must remain wire-compatible in both directions, per P6); a chaos-injection trial that coincides with a real (non-injected) fault (must be distinguishable in telemetry via the injection- source label); a backup taken mid-compaction (§16) must restore correctly regardless of compaction phase.

21.9 Failure Analysis

Operational regressions found in soak or chaos testing are tracked through replay-linked incidents (§20) — every soak-run anomaly must be reproducible from its trace_id, or the anomaly is treated as a test-infrastructure bug, not a system bug, until proven otherwise. Detection is the SLO dashboard threshold breach. Blast radius for a soak-environment finding is zero for production (soak runs in an isolated environment) but the finding blocks the release gate until resolved.

21.10 Operational Notes

Mandatory dashboards (§24): latency (§4 p50/p95/p99), persistence (WAL lag, snapshot age), replay divergence rate, queue saturation per subsystem. Runbooks published for FM-1 through the full §23 failure-mode table, each linked from its corresponding dashboard alert. Release: this phase's completion is the gate for the first v1.0.0 tag (ADR-18 signed release).

24. Operational Readiness

Metrics Strategy

Mandatory metrics, all exported via Prometheus exposition (ADR-11): command latency histograms (§4 p50/p95/p99), WAL lag, replay-divergence count, queue occupancy per subsystem, enclave memory usage per context, attestation failure rate, key-lineage orphan count. Every metric name used in this document (protocol_frame_rejected_total, wal_lag_seconds, scheduler_runnable_queue_depth, etc.) is registered once in telemetry-stack::metrics and referenced by name everywhere else — no ad-hoc metric names introduced downstream of Phase 0 (§12).

Tracing Strategy

Every request carries request_id, replay_id, session_id, and — once inside the scheduler — enclave_id, propagated via OpenTelemetry context (ADR-10) from the gateway through to persistence commit and event emission. Span names follow <subsystem>.<operation> (e.g. persistence.commit, scheduler.context_switch) as fixed in each phase's N.10 Operational Notes.

Logging Strategy

Structured JSON logs only, one event per log line, no multi-line stack-trace dumps in the primary stream (crash dumps go to a separate artifact path). Every log line includes trace_id (P4).

Alerting Philosophy

Alert on invariant violations (any I<n>-labeled counter incrementing), replay divergence, corruption detection, queue saturation approaching the §4 bound, and quote-failure spikes. Alerts are scoped to the smallest containing subsystem (§16.9 blast-radius principle) to avoid operator alert fatigue from a single root cause paging five dashboards simultaneously.

Deployment Topology

Recommended: a 3-node verifier cluster (matching the 99.95% availability target in §4, derived as an N=3 quorum-tolerant topology per Dynamo-style reasoning, DeCandia et al. 2007, applied per §5), a dedicated persistence volume separate from the OS root volume (§16.10), and an isolated telemetry backend so a telemetry-pipeline incident cannot mask a trust-kernel incident.

25. Compatibility & Versioning

Wire Compatibility

Minor versions maintain backward-compatible decoding (P6, ADR-05). New CommandEnvelope fields and new PolicyExpression variants are additive only; a decoder encountering an unknown variant hard-rejects rather than guessing (§11, §17.6).

Storage Compatibility

Snapshots support forward migration and rollback validation. PersistenceFrame.version (§11) gates the decode path; a version mismatch during recovery quarantines the segment rather than best-effort reinterpreting it (§16.8).

Semantic Versioning

MAJOR: incompatible persistence or wire changes (requires the §21 compatibility-matrix gate to be explicitly bypassed with an operator-signed migration plan). MINOR: additive APIs, new PolicyExpression variants, new metrics. PATCH: bugfixes only, no schema or wire changes.

26. Testing & Verification Strategy

Unit Testing

Mandatory for parsers (§13), policy evaluation (§17), and persistence ordering (§16) — the three subsystems where a subtle bug directly threatens an invariant (I1, I4, I7).

Integration Testing

Attestation workflows (§19), replay recovery (§20), crash recovery (§16) — each exercised end to end through conformance-harness against real fixtures, never mocked subsystem boundaries.

Differential Testing

Compare local replay against live execution (replay-engine, §20) on every CI run for a sampled fixture set; also compare quote-verification output against an independent verifier implementation in conformance-harness to catch verifier-side and issuer-side bugs that would otherwise cancel out in a self-consistent-but-wrong pair.

Fuzzing

Targets: parsers (fuzz/frame_decoder.rs), protocol envelopes, policy evaluators (fuzz/policy_parser.rs), persistence decoders (fuzz/snapshot_decoder.rs) — all under cargo-fuzz (ADR-13), run continuously in .github/workflows/fuzz.yml with a minimum 4 CPU-hour gate before merge to any of these four crates.

Chaos Testing

Inject disk faults, scheduler stalls, and corruption events (fault-injection-framework, §21) against the full running system, validating P11 (integrity before availability) holds under every injected fault class in §23.

Reproducible Builds

All releases generated from Nix-pinned environments (ADR-19); Cargo.lock byte-identical across builders is a Phase 0 acceptance gate (§12.4) that remains enforced on every release build.

Artifact Signing

Artifacts signed with offline release keys (ADR-18) — the signing key itself is never present on a CI runner, only on an air-gapped signing host, matching the trust-boundary philosophy this project otherwise applies to its own key hierarchy (§14).

SBOM Generation

CycloneDX SBOM (sbom.cdx.json) emitted for every release via scripts/gen_sbom.sh (§12.2), covering every crate and third-party dependency, cross-checked by cargo-deny (ADR-03, ADR-17).

CI/CD Stages

  1. lint (clippy, rustfmt --check);
  2. unit tests;
  3. integration tests (§26);
  4. fuzz smoke tests (short-duration subset of the full §26 fuzz gate);
  5. replay validation (differential vs. live execution, §20, §26);
  6. packaging (static musl binaries, ADR-15);

Each stage is a hard gate — no stage runs in parallel with an earlier failing stage, since a packaging step running against unvalidated replay output would defeat the purpose of stage 5.

29. Scalability Analysis

Horizontal Scaling

The verifier layer (attestation-service fronted by grpc-control-plane) is horizontally scalable — stateless per request beyond the trust-anchor chain, which is read-only at request time. The persistence layer (tpm-persistence) remains single-writer by design (ADR-06): scaling writes horizontally would require a consensus layer (§34 Alt C), rejected for this project's latency budget.

Vertical Scaling

Crypto workers (tpm-crypto) scale with core count up to the §4 128-worker ceiling; beyond that, oversubscription degrades throughput (§14.7). Enclave contexts scale with available RAM up to the §4 2 GB RSS ceiling ÷ 64 MB per-context quota ≈ 32 theoretical contexts at full quota simultaneously (§32 C3), though the 512-context target assumes most contexts run well under full quota.

Bottlenecks

fsync latency (bounds persistence commit throughput, §16.7); quote-signing throughput (bounds attestation issuance rate, §19.7); scheduler queue contention under 512 contexts (§18.7). All three are explicitly budgeted in §4 and re-verified in §28 — none is a surprise discovered post-launch.

30. Mental Models & First Principles

  • MM1 — Crash-Only Design. Treat every shutdown as if it were a crash; predicts that any special-cased graceful-shutdown path eventually gets skipped in production. Bug class without it: a well-tested graceful path masking a rotten crash-recovery path. Applies in §16.
  • MM2 — Replay Is the Debugger. If an execution can't be replayed byte-identically, it can't be debugged deterministically; predicts that any hidden entropy source becomes an unreproducible bug report. Bug class without it: "works on my machine" nondeterminism. Applies in §20.
  • MM3 — Fail Closed Beats Fail Safe. Ambiguity in a security decision must resolve to denial; predicts that a catch-all match arm on an authorization enum eventually fails open. Bug class without it: silent authorization bypass. Applies in §17.
  • MM4 — Isolation Is a Boundary, Not a Feature. Isolation must be enforced at every mutation site, not asserted once at creation; predicts that a "trusted internal" API bypassing the quota accountant becomes the isolation hole. Bug class without it: cross-context state leakage. Applies in §18.
  • MM5 — Numbers Must Chain. A constraint not derived from another number is a guess; predicts that budgets set independently across §4/§28/§32 drift and silently invalidate each other. Bug class without it: a capacity model that "passes" while contradicting the latency budget it's built from. Applies in §32.
  • MM6 — The Log Is the Truth, the Cache Is a Lie. Any cached or derived state must be reconstructible from the WAL/event log alone; predicts that a cache key missing an epoch will eventually serve a stale decision. Bug class without it: cache-poisoning-shaped authorization bugs. Applies in §17.
  • MM7 — One Assertion Per Invariant. An invariant without an executable check is a comment, not a guarantee; predicts that invariants added without a fixture erode silently as surrounding code changes. Bug class without it: invariant drift hidden behind a clean-looking test suite. Applies in §7.
  • MM8 — Attestation Proves the Past, Not the Present. A quote is only as fresh as its nonce window; predicts that a long-lived quote eventually gets replayed against a since-changed trust state. Bug class without it: stale attestation accepted as current. Applies in §19.

  • HashiCorp Vault (seal system) — chose human-held Shamir key shares over hardware or remote attestation for its trust root; wins in operational contexts where the trust root must be recoverable by a quorum of humans rather than tied to a piece of hardware or a remote verifier.

32. Back-of-Envelope Capacity Model

  • C1 — WAL Steady-State Write Rate. 20,000 commits/sec × 512 B/frame average = 10.24 MB/sec sustained WAL write, comfortably inside typical NVMe sustained-write bandwidth.
  • C2 — WAL Buffer Fill Time At Steady Load. 32 MB buffer ÷ 10.24 MB/sec = 3.1 s to fill at steady-state throughput — the 25 ms fsync p99 budget flushes the buffer roughly 125× more often than a fill-driven flush would, confirming the fsync interval, not the buffer size, drives flush cadence.
  • C3 — Enclave Memory Envelope. 512 contexts × 64 MB quota = 32.77 GB theoretical peak, 16.4× over the 2 GB §4 RSS ceiling — proves the per-context quota is a cap enforced by the accountant (I12), never a sum guarantee; at most ~6% of contexts can run at full quota simultaneously.
  • C4 — Quote Signing Throughput Floor. 5,000 quotes/sec target ÷ ~10,000 ECC-P256 signs/sec per core = 0.5 cores dedicated to signing at peak, leaving the remaining 75 ms p99 budget headroom for certificate-chain assembly and serialization.
  • C5 — FD Budget Allocation. 8,192 client-session FDs + 2,048 telemetry FDs + (512 contexts × 4 avg WAL/snapshot FDs = 2,048) = 12,288 FDs, inside the 32,768 hard ceiling with 62.5% headroom for connection churn.
  • C6 — Replay Buffer Drain Time. 128 MB replay buffer ÷ (20,000 commits/sec × 256 B/record = 5.12 MB/sec) = 25 s max retention before forced rotation to disk at steady peak commit load.
  • C7 — Integrity Replay Scan Rate Required. 10 GB ÷ 15 s target = 667 MB/sec minimum scan-and-verify throughput, achievable via SHA-NI-accelerated per-segment checksums on the §4 4-core minimum host.
  • C8 — Crypto Worker Utilization at Peak HMAC Load. 100,000 HMAC ops/sec ÷ 128 workers = 781 ops/sec/worker, three orders of magnitude under a single core's ~1M HMAC-SHA256/sec capability.
  • C9 — Session Table Memory. 10,000 sessions × 2 KB/session state = 20 MB, negligible against the 256 MB baseline RSS budget.

33. Hard Questions (Self-Examination)

  • Q1. If §16's WAL group-commit batches to hit the 20k/sec throughput target (§4, §28 M7), and §17's policy cache invalidates on every PCR epoch change (§15), does a burst of PCR extends under load create a policy-cache thrash that itself becomes the bottleneck the WAL batching was meant to avoid?
  • Q2. §18's cooperative scheduler assumes tasks yield voluntarily at defined points; §14's crypto workers run CPU-bound RSA operations. What happens to §18's starvation-prevention guarantee (I12, fixture 18.5-002) if a crypto worker's yield point is starved by the scheduler's own accounting overhead?
  • Q3. §19's nonce window is bounded (I10, §4 P5) and §20's replay engine must reproduce the exact scheduler interleaving. If a replayed trace regenerates a nonce request outside the original window's retention, does replay fidelity (I8) conflict with the bounded-nonce-window design?
  • Q4. §21's rolling-upgrade validation assumes wire compatibility (P6, §25) holds across exactly one minor version step. Does the §16 persistence-layer version field (§11 PersistenceFrame) make the same guarantee across a two-minor-version skip, or does §25's compatibility matrix silently stop covering that case?
  • Q5. §22's T3 (persistence tampering) and §16's I11 (snapshot atomicity) both assume the attacker cannot write to the persistence volume directly. What is the actual blast radius (§23 FM-1) if that assumption is wrong and the attacker can write, given §14's key material is also persisted through the same layer?
  • Q6. §32's C3 shows only ~6% of enclave contexts can run at full 64 MB quota simultaneously under the 2 GB ceiling (§4). Does §18's quota accountant (I12) actually enforce this system-wide ceiling, or only the per-context 64 MB cap — and if only the latter, what stops 100% of contexts from hitting full quota at once and violating §4's RSS budget?
  • Q7. §17's fail-closed principle (P10) and §19's fail-closed attestation-nonce rejection both reject on ambiguity. Under §21's chaos testing (fault-injection-framework), does a fault that makes both subsystems ambiguous simultaneously produce a compounding availability failure that §4's 99.95% availability budget didn't account for?
  • Q8. §15's PCR extend lock is per-bank (§15.6); §16's WAL commit is serialized per-segment. If a single command extends a PCR and commits to the WAL in the same transaction (§8 command lifecycle), which lock is acquired first, and does the ordering choice create a deadlock risk with §18's scheduler cancellation path?
  • Q9. §20's divergence detector localizes to phase-boundary checkpoints (post-dispatch, post-crypto, post-persistence). Does a divergence introduced by §17's policy cache (I4) — which sits between dispatch and crypto — actually get caught by either checkpoint, or does it fall in a gap between them?
  • Q10. §27's reproducible-build gate (§12.4) verifies Cargo.lock hash identity. Does that guarantee extend to §14's cryptographic test-vector fixtures, which depend on the exact ring/ RustCrypto version pinned — and if a security patch bumps that pin, does §27's gate or §14's acceptance criteria catch the resulting behavior change first?
  • Q11. §29 states the persistence layer is single-writer by design (ADR-06). §24's recommended 3-node verifier cluster is stateless for attestation but not for the trust-anchor chain (§19). If trust-anchor rotation (§19.2) requires a write, does that silently reintroduce a second writer path that ADR-06 was meant to foreclose?
  • Q12. §7's I5 (key lineage) and §23's FM-11 (key orphaning) both assume hierarchy revocation walks the full lineage before completing. Does §18's cancellation semantics (cooperative, yield-point-based) allow a revoke operation to be cancelled mid-walk, leaving a partial cascade that neither I5 nor FM-11's detection path was designed to catch?
  • Q13. §33 itself and §32's capacity model both derive from §4's numbers. If a future phase changes the enclave quota from 64 MB to, say, 32 MB, which of §28's M1–M11 targets are silently invalidated because the arithmetic in §32 no longer applies, and would §26's testing strategy actually catch that drift before release?
  • Q14. §21's soak test tracks memory growth over 30 days (§21.4). §32's C9 shows session-table memory is negligible. If the actual leak during a 30-day soak turns out to be in §20's replay-trace retention (§4 128 MB ceiling, §32 C6) rather than sessions, does the soak test's dashboard (§24) actually distinguish the two, or does it only report aggregate RSS?
  • Q15. §31 notes AWS Nitro Enclaves have no enclave-local persistence, while this project's entire sealed-storage model (§16) depends on it. Does §34's rejection of the "ephemeral enclave" alternative architecture actually address why sealed storage matters for this project's threat model (§22 T3, T10), or only that it was rejected?
  • Q16. §9's ADR-08 locks cooperative scheduling over OS-thread-per-context for resource-bound reasons. §18's I9 (memory isolation) is enforced by software canaries, not hardware. Under §22's T7 (task-flooding resource exhaustion), does a successful flood attack against the scheduler also degrade the canary-check cadence enough to create a second, isolation-breach failure mode (FM-7) as a side effect of the first?
  • Q17. §5 cites Matetic et al.'s ROTE for rollback protection, applied in §15/§16. §7's I3 (monotonic counters never decrement) is the mechanism actually implementing that protection. Does §16's snapshot-rollback recovery path (§16.9, used for WAL corruption) ever legitimately need to roll a monotonic counter backward, and if so, does that create a direct conflict with I3 that the blueprint has not resolved?
  • Q18. §28's M9 (cold startup < 3 s) and §16's M10 (integrity replay < 15 s per 10 GB) are both Phase 0/Phase 4 gates. For a daemon restarting with a 10 GB state, which target actually governs observed startup time, and does §24's alerting philosophy distinguish a "slow but within-M10" restart from a genuinely stuck one?

34. Alternative Architectures (Roads Not Taken)

Alt A — Hardware-Backed Enclave Instead of Software Simulation

+--------------------+       +---------------------------+
| CLI / SDK Clients  | ----> | Hardware Enclave (SGX/SEV)|
+--------------------+       | page-table isolation      |
                             | CPU-attested measurement  |
                             +---------------------------+

Wins in: production confidential computing where the isolation guarantee must survive a fully compromised host OS/hypervisor. Real system: Intel SGX (via Gramine) / AWS Nitro Enclaves. Rejected here because §1 explicitly scopes this project as a software simulation for portability across dev machines without SGX/SEV hardware and to keep the trust-boundary reasoning teachable without a hardware dependency (§2) — the entire point is reproducing the semantics in software, per §1's non-goals.

Alt B — OS-Process-Per-Enclave Instead of Cooperative Scheduling

+------------------+     fork/seccomp    +------------------+
| Scheduler        | ------------------> | Sandboxed Process |
| (dispatch only)  |                     | (1 per enclave)   |
+------------------+     <-- IPC -->     +------------------+

Wins in: workloads needing true CPU-level fault isolation (a crashing enclave cannot corrupt another's memory even via a scheduler bug). Real system: seccomp-sandboxed worker-process models (e.g. Chromium's process-per-site-instance architecture). Rejected here because 512 concurrent OS processes cannot hit the §4 250,000 context-switches/sec target (§28 M8) — process-level context switches cost orders of magnitude more than the in-process cooperative switches ADR-08 requires.

Alt C — Consensus-Replicated Persistence Instead of Single-Writer WAL

+--------+     Raft log replication     +--------+
| Node A | <---------------------------> | Node B |
+--------+                               +--------+
     \                                       /
      \--------------- Node C --------------/
      (majority-write quorum before commit ack)

Wins in: deployments needing horizontal write scaling and multi-region durability beyond a single persistence volume's failure domain. Real system: TiKV / etcd (Raft-based replicated log). Rejected here because §29 fixes persistence as single-writer by design (ADR-06) — a Raft round trip adds one-to-several RTTs to every commit, which would blow the §4 40 ms p99 command-latency budget for this project's intra-datacenter deployment model (§1); §35 tracks distributed attestation federation, the one place multi-node coordination is deferred rather than rejected outright.

36. Glossary

  • PCR — Platform Configuration Register; append-only measurement register extended via a hash chain.
  • Quote — a signed attestation statement binding a PCR snapshot and a nonce.
  • WAL — write-ahead log; the durability unit committed before any state mutation is acknowledged.
  • NV Index — a persistent TPM storage slot (NvSlot, §11) addressed independently of hierarchy.
  • Replay Hash — the deterministic digest of an execution, compared across original and replayed runs (I8).
  • Locality — an execution privilege domain gating PCR reset authorization.
  • Sealing — encrypting data such that decryption requires a specific trust-state predicate.
  • Attestation — cryptographic trust verification of a remote system's measured state.
  • Hierarchy — a TPM ownership domain rooted at an endorsement or storage root key.
  • Monotonic Counter — a non-decreasing durable counter (I3) underpinning anti-replay.
  • Trust Anchor — a root or intermediate verification key/certificate for attestation reports.
  • Snapshot — a durable, atomic point-in-time state checkpoint (I11).
  • Integrity Tree — a tamper-evident hash structure enabling sub-linear corruption localization.
  • Replay Divergence — a mismatch between original and replayed execution hashes (I8 violation).
  • Quarantine — the isolation state entered after corruption or integrity-tree failure (P11).
  • TPMContext — the global mutable trust-state struct (§11).
  • EnclaveContext — isolated per-tenant execution state (§11).
  • PolicySession — composable authorization evaluation state (§17).
  • EventRecord — an append-only immutable mutation record (I7, §11).
  • CommandEnvelope — the wire-level command frame (§11).
  • PersistenceFrame — the on-disk framing envelope for WAL/snapshot records (§11).
  • DRBG — Deterministic Random Bit Generator; the replayable RNG construction (NIST SP 800-90A).
  • HKDF — HMAC-based Key Derivation Function (RFC 5869), used for sealing-key derivation.
  • AEAD — Authenticated Encryption with Associated Data; the AES-GCM sealing primitive.
  • Fail Closed — the principle that authorization ambiguity resolves to denial (P10).
  • Backpressure — explicit rejection of new work when a bounded queue is full (P5).
  • Cooperative Scheduling — a scheduling model where tasks yield voluntarily at defined points.
  • Cancellation Token — the cooperative-cancellation signal checked at scheduler yield points.
  • Quota Accounting — the per-context resource ledger enforcing I12.
  • Group Commit — batching multiple WAL appends into one fsync to amortize durability cost.
  • Compaction — periodic snapshot rewriting that reclaims WAL space (P9 exception path).
  • Replay Trace — the sealed artifact recording scheduler ordering and execution hash (§11).
  • Nonce Window — the bounded single-use validity window for attestation nonces (I10).
  • Trust Boundary — the point (gateway) where untrusted input becomes validated internal state.
  • Persistence Boundary — the point below which state is only visible after integrity verification.
  • Concurrency Boundary — the point at which one enclave context's state becomes invisible to another (I9).
  • Handle Generation — the version counter on a TPMHandle preventing stale-handle reuse (I6).
  • Session Token — the credential binding a policy session to one command-sequence lineage (I13).
  • Fixture — a named, checked-in test input/expected-output pair under fixtures/ or conformance/.
  • Soak Test — a long-duration (30-day) continuous-load run detecting slow leaks (§21).
  • Chaos Testing — randomized fault injection against the running system (§21, §26).
  • SBOM — Software Bill of Materials; CycloneDX manifest of every dependency (§27).
  • Reproducible Build — a build producing a byte-identical artifact across independent builders (§12.4, ADR-19).
  • Verifier — a remote party that validates an AttestationReport against a trust anchor (§19).
  • Divergence Detector — the per-checkpoint hash-comparison mechanism in replay-engine (§20).
