In one paragraph

This is a design for a software-emulated Trusted Platform Module (a chip that guards keys and boot measurements) plus a secure-enclave runtime, with no real hardware root of trust underneath (§1). It exists so engineers can study and test measured boot, remote attestation, sealed storage and policy-gated commands, including their crash and replay behaviour, without special hardware (§1, §2). Infrastructure security engineers, platform SRE teams and attestation-infrastructure maintainers run it as a user-space daemon (tpmsimd) behind a Unix socket or gRPC (§1). It is explicitly not a certified security module (§1).

The problem, concretely

The blueprint says the goal is "a layered trust-computing platform, not a toy emulator" (§1). A toy emulator that only answers TPM-shaped commands in memory fails in ways the design names one by one.

  • Its state dies with the process: "nothing before" the persistence phase "survives a kill -9" (§1). The real design must assume termination at any instruction boundary and make every mutation durable in a write-ahead log before it is observable (P2).
  • A torn write at power loss leaves a half-written last record. The design treats that record as absent, not as a reason to throw the whole segment away (§16.6).
  • A stale snapshot can pass its checksum and still be a rollback. The blueprint ties this to a monotonic counter (I3) and cites the ROTE rollback-protection paper for the reasoning (§15.2).
  • A quote replayed to a verifier looks valid unless nonces are single-use inside a window (I10, §19.2). A client retry after a timeout is indistinguishable from a replay at the nonce layer, so the client must ask for a fresh nonce each attempt (§19.6).
  • A stray wall-clock read inside the trust kernel causes "intermittent, unreproducible divergence" between an original run and its replay (§20.6, P1).

The blueprint answers these with durability, anti-rollback, anti-replay and determinism behind a boundary that rejects bad input before any state changes (§3, P10).

How it works, end to end

The blueprint's lifecycle for one command is: Client, Gateway, Validation, Policy Evaluation, Command Execution, Persistence Commit, Event Emission, Response Serialization, and no stage may reorder past another for the same sequence_number (§8). The diagram is adapted from §3 (condensed), with its three boundaries:

 CLI / SDK clients (untrusted)
   -> [grpc-control-plane]      gRPC | Unix socket
      === TRUST BOUNDARY ===
   -> [tpm-command-engine]      validation (auth, sequencing, replay guards, quota), then dispatch
   -> [tpm-pcr] [tpm-policy] [tpm-crypto]     PCR banks | policy evaluator | key hierarchy
      === PERSISTENCE BOUNDARY ===
   -> [tpm-persistence]         WAL | snapshots | integrity trees | encrypted blobs
   -> [tpm-crypto]              crypto worker pool (AES-GCM, RSA, ECC, HMAC, HKDF, RNG)
      === CONCURRENCY BOUNDARY ===
   -> [enclave-runtime]         isolation | task queues | quotas
   -> [eventlog-engine, replay-engine]   [telemetry-stack]
   -> [attestation-service]     quotes | verifier | trust chains
  1. grpc-control-plane ends transport sessions, validates framing, enforces per-session quotas and turns requests into internal envelopes. It is the main trust boundary (§3).
  2. tpm-command-engine decodes the CommandEnvelope with a bounds-checked decoder, checks the checksum and sequence number, then dispatches through a table built at compile time (§13.2). Anything malformed is rejected before any state mutation (§3, §13.1).
  3. tpm-policy evaluates the authorization expression fail-closed before execution (§17.3, P10).
  4. tpm-pcr and tpm-crypto do the work: PCR extension (§15) and key lifecycle, signing and sealing (§14). Phase 6 runs both as scheduled tasks inside enclave-runtime, not as direct calls (§18.3).
  5. tpm-persistence commits through the WAL before acknowledgment (§16.3). Below this line, nothing is visible to a client without integrity verification (§3).
  6. eventlog-engine appends immutable EventRecords (I7); every PCR extend gets one (§15.2), and every externally visible mutation emits a replay artifact before it is acknowledged (P4).
  7. attestation-service hands remote verifiers only signed, replayable evidence, never raw state (§3). telemetry-stack exports metrics, traces and logs to collectors outside the trust boundary (§3).
  8. conformance-harness is the single-threaded, clock-injected fixture runner that every later phase must pass through (§12.2, §12.1), and fault-injection-framework and cli-shell (tpmsim) supply chaos testing and replay tooling (§21.2, §20.2).

The core ideas

PCR extension: a hash chain you can only append to (§8, §15)

A PCR (Platform Configuration Register) holds one running measurement of what has booted. You cannot set it; you can only extend it: new_pcr = HASH(old_pcr || digest) (§8). HASH is the bank's configured algorithm (SHA-256 or SHA-384) and a bank never mixes algorithms mid-lineage (§8). The blueprint expects a builder to explain why extension must be one-way and ordered, and to derive the collision-resistance argument from this hash-chain construction (§2, I2).

Rules around it:

  • A single per-bank extend lock makes concurrent extends land in one deterministic order. Fixture concurrent-extend-003 throws 3 concurrent extends at one bank and expects one serialized order plus a matching replay hash (§15.2, §15.5).
  • Reset needs explicit locality authorization, checked before any register changes (§15.2). Every reset path must go through one gate (§15.6).
  • The operand order matters: digest || old_pcr instead of old_pcr || digest yields a value that matches no reference measurement (§15.6). A wrong-width digest is rejected, not zero-padded (§15.8).
  • A bank is "snapshotted whole" and the WAL records each extend (§11). Replaying the recorded extends must reproduce the exact final value, tested with 1,000 sequential extends in extend-sequence-001 (§15.2, §15.5).

Crash-only persistence, and the one-way door to quarantine (§16, §8)

Plain words: write down what you are about to do (a write-ahead log, WAL) before doing it, and take occasional full copies (snapshots) so recovery does not replay everything. The WAL record frame carries a version, a sequence number, a CRC32C checksum, a payload size and the payload (§11). A Merkle-style integrity tree with one root per segment localizes tampering in O(log n) instead of rehashing the segment (§16.2).

Recovery is the only startup path (P2). The steps (§16.2):

  1. Load the latest valid snapshot (§16.2).
  2. Replay WAL entries whose sequence_number is greater than the snapshot's watermark, so no snapshot references unapplied WAL entries (I1, §16.2).
  3. Any checksum or integrity-tree mismatch halts recovery and enters QUARANTINED; there is no skip-and-continue (§16.2, P11).

One case conflicts: §16.2 quarantines on any checksum mismatch, but §16.6 treats a torn last WAL record (which shows up as a checksum mismatch) as absent, and partial-segment-003 expects recovery to the last complete record (§16.2, §16.6, §16.5). The blueprint does not reconcile the two.

A snapshot is published atomically with the order fsync(data), then fsync(dir), then rename (I11, §16.6). Group commit batches several appends into one fsync, bounded by the 32 MB buffer (§4, §16.2). Only sequence_number orders records; timestamps never do (§16.8, P1). The five states:

State Meaning (§8) Exit (§8)
INIT integrity verification running verification complete, then READY
READY accepting commands corruption, then QUARANTINED
RECOVERY WAL replay in progress success, then READY; divergence, then QUARANTINED
DEGRADED partial failure, reduced command set operator recovery, then READY
QUARANTINED corruption detected manual intervention only

A quarantined node serves no command that touches the corrupted region, even a read (§16.9). Quarantine is scoped to the smallest containing integrity-tree subtree when possible (§16.9). The acceptance test is 500 SIGKILL-during-commit trials with zero corrupted recoveries (§16.4).

Determinism and replay: the log is the debugger (§20, §13, §14, §17)

Goal: re-run a recorded execution and get the same execution hash (I8). Everything that could differ between a run and its replay is therefore pulled inside the record:

  • time comes from an injected logical clock, never a direct wall-clock read (ADR-20, §20.6);
  • randomness comes from a CTR_DRBG-shaped generator seeded from a recorded seed, never live entropy inside the trust kernel (§14.2, P1);
  • command dispatch is a table built at compile time with no runtime registration (§13.2);
  • policy evaluation reads only the context snapshot visible at the command's sequence_number (§17.2).

A ReplayTrace records scheduler ordering, command sequence and cryptographic operation IDs, and is sealed on rotation (§20.2). Replay re-executes against a fresh TPMContext built from the same starting snapshot, recomputing execution_hash (§20.2). Checkpoint hashes after dispatch, after crypto and after the persistence commit localize a divergence to a subsystem, and triage starts at the earliest diverging checkpoint because later ones inherit the corruption (§20.2, §20.9). Replay runs on a copy of state, never the live TPMContext (§20.9). Fixture hidden-entropy-003 plants a live-clock read and expects the detector to flag the exact checkpoint (§20.5).

Fail-closed policy evaluation (§17)

A policy is a small expression tree: PCRMatch, SignedAssertion, Locality, CounterThreshold, CompositeAnd, CompositeOr (§11). Three rules make it safe:

  • Ambiguity means deny. An evaluator panic, timeout or unresolvable reference is a hard deny, never a default allow (§17.9, P10). A lint bans catch-all match arms on PolicyExpression, since a new variant would otherwise silently match true (§17.6).
  • Composites evaluate in one canonical left-to-right order, identical on replay (§17.6, I4).
  • A policy cache keyed by (policy_hash, context_epoch) is invalidated on any PCR epoch change (§17.2). Fixture pcr-match-002 evaluates against a stale epoch and expects re-evaluation, not a stale allow (§17.5).

Fixture composite-and-001 is a 3-term CompositeAnd (PCR match, locality, counter threshold) that must give the same allow on 10 replays (§17.5, §17.4). Cyclic or unbounded-depth trees are rejected at parse time (§17.2, cyclic-policy-003, §17.5). An empty CompositeAnd is vacuously true, which the blueprint says must be an explicit documented decision (§17.8).

Software isolation: quotas, yield points, no shared task tables (§18)

Each EnclaveContext is isolated execution state for one tenant and never shared (§8, I9). Four mechanisms enforce it in software:

  • One task table per context, never a global one (§18.2, P8).
  • An atomic per-context quota accountant debits and credits at every mutation site, not only at admission (§18.2, I12). A context over its 64 MB default is rejected "at the exact byte", never silently OOM-killed (§18.5, §18.4, §4).
  • Cooperative scheduling: tasks yield at explicit points, so there are no preemption races (§18.2, ADR-08). Cancellation is a CancellationToken checked at yield points, and never lands inside an in-flight persistence commit (§18.2, §18.6).
  • Boundary-crossing canary checks, and a watchdog that quarantines a context that never yields (§18.2, §18.8). Bounded mailboxes reject new messages instead of growing (§18.2, P5).

Attestation: signed evidence with single-use nonces (§19)

A quote is a signed statement binding a PCR snapshot and a nonce (§36). An AttestationReport is PCR snapshot, nonce, signature and a trust-anchor reference (§19.2). The verifier returns a structured result, never a bare boolean (§19.2). The anti-replay design has two layers:

  • Nonces are single-use inside a window, held in a bounded LRU (I10, §19.2, P5).
  • A request outside the accepted sequence/time window is rejected even if its nonce is new; the window is keyed on the injected sequence first and wall-clock only as a sanity bound (§19.2, §19.6).

Trust anchors are chained records with validity windows, so rotation works without a single hardcoded root (§19.2). A report is checked against the anchor valid at signing time, not at verification time (§19.8). The blueprint's mental model is that a quote proves the past, not the present, and is only as fresh as its nonce window (MM8).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust, because ownership guarantees make explicit ownership of key material compiler-enforced (ADR-01, P3, §1). Rejected: Go and C++ (ADR-01); §1 also rejects Python, keeping it only for fixture-generation tooling (§1). When the rejected choice is right: Go, for interoperability CLI clients needing fast iteration outside the trust kernel (ADR-01, §1).

Serialization: protobuf with a CBOR fallback (ADR-05)

Chosen: Prost (protobuf) plus a CBOR fallback, because replay equality needs binary determinism (ADR-05, P1, I4). Rejected: JSON. When the rejected choice is right: human-debuggable, low-throughput admin endpoints where compactness does not matter (ADR-05).

Persistence engine: a custom WAL and block store (ADR-06)

Chosen: custom WAL plus block store, because the 20k commits/sec target exceeds SQLite's single-writer throughput (ADR-06, §4). Rejected: SQLite. When the rejected choice is right: embedded single-writer deployments under about 100 commits/sec (ADR-06).

Concurrency model: cooperative scheduling with quotas (ADR-08)

Chosen: cooperative scheduling with explicit quotas, for bounded resource control without 512 OS threads (ADR-08, P5, P8). Rejected: one OS thread per context. §34 Alt B adds that 512 OS processes cannot reach the 250,000 switches/sec target. When the rejected choice is right: when true CPU-level fault isolation, not just software isolation, is required (ADR-08, §34).

Time source: an injected logical clock (ADR-20)

Chosen: an injected logical clock inside the trust kernel, because determinism forbids non-replayable time (ADR-20, P1). Rejected: direct wall-clock reads. When the rejected choice is right: in the CLI/SDK layer outside the trust boundary, where real timestamps are user-facing (ADR-20).

Backpressure: bounded mailbox plus explicit reject (ADR-21)

Chosen: a bounded mailbox that rejects when full (RESOURCE_EXHAUSTED), per the bounded-resource principle (ADR-21, P5, §13.2). Rejected: unbounded buffering. When the rejected choice is right: briefly during a controlled load test to find the true saturation point, never in production (ADR-21).

Roads not taken

Hardware-backed enclave (§34 Alt A). Wins in production confidential computing where isolation must survive a fully compromised host OS or hypervisor (SGX via Gramine, Nitro). Rejected because §1 scopes this as a software simulation that needs no SGX/SEV hardware and keeps the trust-boundary reasoning teachable (§34, §2).

Process per enclave (§34 Alt B). Wins when a crashing enclave must not corrupt another's memory even via a scheduler bug (§34). Rejected on context-switch cost (ADR-08, §28 M8).

Raft-replicated persistence (§34 Alt C). Wins for horizontal write scaling and multi-region durability beyond one volume (§34, TiKV/etcd). Rejected because a Raft round trip adds one or more RTTs to every commit and would break the 40 ms p99 budget; §29 fixes persistence as single-writer (§34, §29, ADR-06).

Deferred register (§35). Eight items wait on named triggers, for example QUIC-native attestation transport (when gRPC-over-QUIC is stable), SGX/SEV key-sealing interop (when a customer needs a real sealing key), and distributed attestation federation (when more than one verifier cluster must share trust-anchor state) (§35).

What must never be false

  • I1: no snapshot references unapplied WAL entries. Noticed by a sequence-mismatch scanner on snapshot load (persistence_snapshot_sequence_gap) (§7).
  • I2: PCRs change only by ordered extension. A lineage-continuity check on every extend (pcr_extend_out_of_order_total) (§7).
  • I3: monotonic counters never decrement. A monotonicity assertion on every write (counter_regression_detected_total) (§7).
  • I4: policy evaluation is byte-identical on replay. A replay differential test (policy_replay_divergence_total) (§7).
  • I5: child keys never outlive their parent lineage. A lineage walk on revoke (key_orphan_detected_total) (§7).
  • I6: transient handles are revoked after expiry or eviction. A handle-generation mismatch check (handle_stale_use_total) (§7).
  • I7: committed events are immutable. A write-once storage assertion (eventlog_mutation_attempt_total) (§7).
  • I8: replay hash equals the original execution hash. A hash comparison at replay completion (replay_hash_mismatch_total) (§7).
  • I9: one enclave context's memory is never visible to another. Boundary-crossing canary checks (enclave_isolation_violation_total) (§7).
  • I10: attestation nonces are single-use within their window. A nonce-reuse lookup on each quote request (attestation_nonce_reuse_total) (§7).
  • I11: snapshot writes are atomic. A rename fence plus checksum on load (snapshot_partial_write_total) (§7).
  • I12: quota accounting never goes negative. An assertion on every debit and credit (quota_accounting_underflow_total) (§7).
  • I13: a policy session token authorizes exactly one command-sequence lineage. A lineage-tag mismatch check (policy_session_lineage_mismatch_total) (§7).

Each invariant has exactly one assertion site in the single-threaded, clock-injected simulator, and a new invariant must ship with its assertion and fixture in the same change (§7, MM7).

What breaks in production

  • FM-1, WAL corruption. Symptom: checksum mismatch on segment load. Cause: torn write, bit rot or a buggy compaction. Detection: the integrity-tree scan on startup. Recovery: the blueprint disagrees with itself. §23's row puts "rollback to last verified snapshot" where the automatic recovery belongs and "none automatic — requires operator confirmation" where the manual recovery belongs; §16.9 says recovery is always an operator-confirmed rollback, never an automatic silent one (FM-1, §16.9, P11).
  • FM-2, replay divergence. Symptom: execution_hash mismatch at a checkpoint. Cause: a hidden entropy source or an upstream invariant violation. Detection: checkpoint-hash comparison. Recovery: quarantine the node and root-cause from the earliest diverging checkpoint (FM-2, §20.9).
  • FM-3, scheduler deadlock. Symptom: watchdog timeout and stalled context switches. Cause: a re-entrant lock around the quota accountant. Detection: a per-context watchdog timer. Recovery: restart the affected worker shard, and a lock-free accountant is the fix (FM-3, §18.6).
  • FM-5, policy evaluation panic. Symptom: evaluator crash and a denial spike. Cause: an unhandled PolicyExpression variant or a cyclic policy that escaped parse-time checks. Detection: a panic hook. Recovery: fail closed automatically, then patch and replay affected sessions (FM-5, P10).
  • FM-7, enclave isolation breach. Symptom: a canary-check failure. Cause: a scheduler bug that bypasses the quota accountant. Detection: the isolation-guard canary (I9). Recovery: terminate the offending context automatically, then audit the scheduler (FM-7, §18.9).
  • FM-9, snapshot compaction stall. Symptom: compaction exceeds its budget and the WAL grows unbounded. Cause: a stop-the-world compaction path. Detection: a compaction_duration_seconds threshold. Recovery: nothing automatic; an operator restarts compaction in incremental mode (FM-9, §16.7).
  • FM-11, key hierarchy orphaning. Symptom: an orphan-key alarm and a cascading revoke storm. Cause: a parent revoked without a full lineage walk. Detection: the lineage-walk assertion (I5). Recovery: cascade-revoke is automatic, then audit commands that used an orphaned key (FM-11).

Threats a reader should know (§22):

  • T3: tampering with the WAL or snapshots at rest, answered by per-frame checksums and the integrity tree, with the node quarantined on mismatch (T3, §16.2).
  • T4: a forged replay trace, answered by re-deriving execution_hash on load and never trusting the stored hash (T4, §20).
  • T5: a replayed valid quote, answered by the single-use nonce window (T5, I10).
  • T8: sequence-number replay of an old valid command, answered by monotonic sequencing and gap detection (T8, §13.5).
  • T10: key material leaking from memory after a crash dump, answered by zeroization on drop and no Clone on key types, with a post-drop memory-scan fixture (T10, P3, §14.5).

How it compares

  • swtpm chose full software fidelity to the TPM 2.0 command set with no hardware isolation. That suits CI and test environments needing a real command surface, the niche tpm-command-engine inherits (§31).
  • Intel SGX / Gramine chose CPU-enforced hardware isolation. That suits production confidential computing that must survive a compromised host OS, a guarantee this project excludes (§31, §1).
  • AWS Nitro Enclaves chose hypervisor isolation with no enclave-local persistence. That suits cloud workloads that can treat the enclave as ephemeral, at the cost of the sealed-storage model this project centres on (§31, §16).
  • Keylime chose to be a verifier only, with no TPM simulation. That suits fleets that already have real TPM hardware and need a scalable verifier, the complement of this project (§31).
  • HashiCorp Vault (seal) chose human-held Shamir key shares as its trust root. That suits contexts where a quorum of people, not hardware or a remote verifier, must be able to recover the root (§31).

Per §31's table, none of the five offers deterministic replay.

Questions to test yourself

  1. If §16's WAL group-commit batches to hit the 20k/sec throughput target (§4, §28 M7), and §17's policy cache invalidates on every PCR epoch change (§15), does a burst of PCR extends under load create a policy-cache thrash that itself becomes the bottleneck the WAL batching was meant to avoid? — Hint: §16.2 (group commit), §17.2 (cache key) and §15.2 (epoch).
  2. §19's nonce window is bounded (I10, §4 P5) and §20's replay engine must reproduce the exact scheduler interleaving. If a replayed trace regenerates a nonce request outside the original window's retention, does replay fidelity (I8) conflict with the bounded-nonce-window design? — Hint: §19.2, §19.6 and §20.2 show the two sides of the tension.
  3. §15's PCR extend lock is per-bank (§15.6); §16's WAL commit is serialized per-segment. If a single command extends a PCR and commits to the WAL in the same transaction (§8 command lifecycle), which lock is acquired first, and does the ordering choice create a deadlock risk with §18's scheduler cancellation path? — Hint: §15.2 (per-bank lock), §16.6 (commit path) and §18.6 (cancellation).
  4. §20's divergence detector localizes to phase-boundary checkpoints (post-dispatch, post-crypto, post-persistence). Does a divergence introduced by §17's policy cache (I4) — which sits between dispatch and crypto — actually get caught by either checkpoint, or does it fall in a gap between them? — Hint: §20.2 lists the checkpoints; §17.2 shows where the policy cache is read.
  5. §5 cites Matetic et al.'s ROTE for rollback protection, applied in §15/§16. §7's I3 (monotonic counters never decrement) is the mechanism actually implementing that protection. Does §16's snapshot-rollback recovery path (§16.9, used for WAL corruption) ever legitimately need to roll a monotonic counter backward, and if so, does that create a direct conflict with I3 that the blueprint has not resolved? — Hint: §15.2 and §16.9, with I3 in §7; the blueprint poses this without resolving it.

If you only remember three things

Everything durable is written to a log before it is visible, and recovery from that log is the only way the system starts, which is why a SIGKILL at any point is survivable (P2, §16.2). Everything that could differ on a re-run is injected or recorded, so an execution hash can catch any divergence and point at the first bad checkpoint (P1, I8, §20.2). When anything is ambiguous, the answer is deny or quarantine rather than best effort (P10, P11, §17.9, §16.2).

Words used here

  • TPM: Trusted Platform Module; a chip, here emulated, holding keys and measurement registers (§1).
  • PCR: a register extended only by hashing the old value with a new digest (§36, §8).
  • Measured boot: recording hashes of what has started into PCRs, so later quotes can prove it (§15).
  • Quote: a signed statement binding a PCR snapshot and a nonce (§36).
  • Nonce: a value that may be used once inside its validity window (I10, §36).
  • WAL: write-ahead log; the record committed before any state change is acknowledged (§36).
  • Snapshot: a durable, atomic point-in-time copy of state (I11, §36).
  • Integrity tree: a tamper-evident hash tree that locates corruption in sub-linear time (§36).
  • Quarantine: the stop-serving state entered after corruption or integrity failure (§36, §8).
  • Fail closed: ambiguity in an authorization decision resolves to denial (P10, §36).
  • Replay hash: the digest of an execution, compared between original and replayed runs (I8, §36).
  • Enclave context: isolated per-tenant execution state with its own quota (§8, I9).
  • Cooperative scheduling: tasks yield voluntarily at defined points (§36, ADR-08).
  • Trust anchor: a root or intermediate key that attestation reports are verified against (§36).
  • Sealing: encrypting so that decryption needs a specific trust-state predicate (§36).
