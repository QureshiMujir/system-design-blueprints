33. Hard Questions (Self-Examination)

  • Q1. If §16's WAL group-commit batches to hit the 20k/sec throughput target (§4, §28 M7), and §17's policy cache invalidates on every PCR epoch change (§15), does a burst of PCR extends under load create a policy-cache thrash that itself becomes the bottleneck the WAL batching was meant to avoid?
  • Q2. §18's cooperative scheduler assumes tasks yield voluntarily at defined points; §14's crypto workers run CPU-bound RSA operations. What happens to §18's starvation-prevention guarantee (I12, fixture 18.5-002) if a crypto worker's yield point is starved by the scheduler's own accounting overhead?
  • Q3. §19's nonce window is bounded (I10, §4 P5) and §20's replay engine must reproduce the exact scheduler interleaving. If a replayed trace regenerates a nonce request outside the original window's retention, does replay fidelity (I8) conflict with the bounded-nonce-window design?
  • Q4. §21's rolling-upgrade validation assumes wire compatibility (P6, §25) holds across exactly one minor version step. Does the §16 persistence-layer version field (§11 PersistenceFrame) make the same guarantee across a two-minor-version skip, or does §25's compatibility matrix silently stop covering that case?
  • Q5. §22's T3 (persistence tampering) and §16's I11 (snapshot atomicity) both assume the attacker cannot write to the persistence volume directly. What is the actual blast radius (§23 FM-1) if that assumption is wrong and the attacker can write, given §14's key material is also persisted through the same layer?
  • Q6. §32's C3 shows only ~6% of enclave contexts can run at full 64 MB quota simultaneously under the 2 GB ceiling (§4). Does §18's quota accountant (I12) actually enforce this system-wide ceiling, or only the per-context 64 MB cap — and if only the latter, what stops 100% of contexts from hitting full quota at once and violating §4's RSS budget?
  • Q7. §17's fail-closed principle (P10) and §19's fail-closed attestation-nonce rejection both reject on ambiguity. Under §21's chaos testing (fault-injection-framework), does a fault that makes both subsystems ambiguous simultaneously produce a compounding availability failure that §4's 99.95% availability budget didn't account for?
  • Q8. §15's PCR extend lock is per-bank (§15.6); §16's WAL commit is serialized per-segment. If a single command extends a PCR and commits to the WAL in the same transaction (§8 command lifecycle), which lock is acquired first, and does the ordering choice create a deadlock risk with §18's scheduler cancellation path?
  • Q9. §20's divergence detector localizes to phase-boundary checkpoints (post-dispatch, post-crypto, post-persistence). Does a divergence introduced by §17's policy cache (I4) — which sits between dispatch and crypto — actually get caught by either checkpoint, or does it fall in a gap between them?
  • Q10. §27's reproducible-build gate (§12.4) verifies Cargo.lock hash identity. Does that guarantee extend to §14's cryptographic test-vector fixtures, which depend on the exact ring/ RustCrypto version pinned — and if a security patch bumps that pin, does §27's gate or §14's acceptance criteria catch the resulting behavior change first?
  • Q11. §29 states the persistence layer is single-writer by design (ADR-06). §24's recommended 3-node verifier cluster is stateless for attestation but not for the trust-anchor chain (§19). If trust-anchor rotation (§19.2) requires a write, does that silently reintroduce a second writer path that ADR-06 was meant to foreclose?
  • Q12. §7's I5 (key lineage) and §23's FM-11 (key orphaning) both assume hierarchy revocation walks the full lineage before completing. Does §18's cancellation semantics (cooperative, yield-point-based) allow a revoke operation to be cancelled mid-walk, leaving a partial cascade that neither I5 nor FM-11's detection path was designed to catch?
  • Q13. §33 itself and §32's capacity model both derive from §4's numbers. If a future phase changes the enclave quota from 64 MB to, say, 32 MB, which of §28's M1–M11 targets are silently invalidated because the arithmetic in §32 no longer applies, and would §26's testing strategy actually catch that drift before release?
  • Q14. §21's soak test tracks memory growth over 30 days (§21.4). §32's C9 shows session-table memory is negligible. If the actual leak during a 30-day soak turns out to be in §20's replay-trace retention (§4 128 MB ceiling, §32 C6) rather than sessions, does the soak test's dashboard (§24) actually distinguish the two, or does it only report aggregate RSS?
  • Q15. §31 notes AWS Nitro Enclaves have no enclave-local persistence, while this project's entire sealed-storage model (§16) depends on it. Does §34's rejection of the "ephemeral enclave" alternative architecture actually address why sealed storage matters for this project's threat model (§22 T3, T10), or only that it was rejected?
  • Q16. §9's ADR-08 locks cooperative scheduling over OS-thread-per-context for resource-bound reasons. §18's I9 (memory isolation) is enforced by software canaries, not hardware. Under §22's T7 (task-flooding resource exhaustion), does a successful flood attack against the scheduler also degrade the canary-check cadence enough to create a second, isolation-breach failure mode (FM-7) as a side effect of the first?
  • Q17. §5 cites Matetic et al.'s ROTE for rollback protection, applied in §15/§16. §7's I3 (monotonic counters never decrement) is the mechanism actually implementing that protection. Does §16's snapshot-rollback recovery path (§16.9, used for WAL corruption) ever legitimately need to roll a monotonic counter backward, and if so, does that create a direct conflict with I3 that the blueprint has not resolved?
  • Q18. §28's M9 (cold startup < 3 s) and §16's M10 (integrity replay < 15 s per 10 GB) are both Phase 0/Phase 4 gates. For a daemon restarting with a 10 GB state, which target actually governs observed startup time, and does §24's alerting philosophy distinguish a "slow but within-M10" restart from a genuinely stuck one?

30. Mental Models & First Principles

  • MM1 — Crash-Only Design. Treat every shutdown as if it were a crash; predicts that any special-cased graceful-shutdown path eventually gets skipped in production. Bug class without it: a well-tested graceful path masking a rotten crash-recovery path. Applies in §16.
  • MM2 — Replay Is the Debugger. If an execution can't be replayed byte-identically, it can't be debugged deterministically; predicts that any hidden entropy source becomes an unreproducible bug report. Bug class without it: "works on my machine" nondeterminism. Applies in §20.
  • MM3 — Fail Closed Beats Fail Safe. Ambiguity in a security decision must resolve to denial; predicts that a catch-all match arm on an authorization enum eventually fails open. Bug class without it: silent authorization bypass. Applies in §17.
  • MM4 — Isolation Is a Boundary, Not a Feature. Isolation must be enforced at every mutation site, not asserted once at creation; predicts that a "trusted internal" API bypassing the quota accountant becomes the isolation hole. Bug class without it: cross-context state leakage. Applies in §18.
  • MM5 — Numbers Must Chain. A constraint not derived from another number is a guess; predicts that budgets set independently across §4/§28/§32 drift and silently invalidate each other. Bug class without it: a capacity model that "passes" while contradicting the latency budget it's built from. Applies in §32.
  • MM6 — The Log Is the Truth, the Cache Is a Lie. Any cached or derived state must be reconstructible from the WAL/event log alone; predicts that a cache key missing an epoch will eventually serve a stale decision. Bug class without it: cache-poisoning-shaped authorization bugs. Applies in §17.
  • MM7 — One Assertion Per Invariant. An invariant without an executable check is a comment, not a guarantee; predicts that invariants added without a fixture erode silently as surrounding code changes. Bug class without it: invariant drift hidden behind a clean-looking test suite. Applies in §7.
  • MM8 — Attestation Proves the Past, Not the Present. A quote is only as fresh as its nonce window; predicts that a long-lived quote eventually gets replayed against a since-changed trust state. Bug class without it: stale attestation accepted as current. Applies in §19.

5. Required Reading

Books

  • Designing Data-Intensive Applications — Martin Kleppmann (2017), ch. 3–5, 11: WAL, replication, and stream-processing correctness models; applied in §16 and §20.
  • Database Internals, Vol. 1 — Alex Petrov (2019), ch. 3–7: storage-engine WAL and crash-recovery patterns transplanted onto the sealed-storage layer; applied in §16.
  • Rust Atomics and Locks — Mara Bos (2023), all chapters: lock-free primitives and memory ordering for the enclave scheduler's cancellation and quota accounting; applied in §18.
  • The Linux Programming Interface — Michael Kerrisk (2010), memory/process/signal chapters: SIGKILL-survivable persistence and process isolation semantics; applied in §12 and §16.
  • Operating Systems: Three Easy Pieces — Remzi H. Arpaci-Dusseau, Andrea C. Arpaci-Dusseau (2018, free online edition), virtual memory and concurrency chapters: scheduler correctness under contention; applied in §18.
  • Practical Binary Analysis — Dennis Andriesse (2018), ch. 2–4: parser hardening and bounds-checked binary decoding for the wire protocol; applied in §13.
  • Security Engineering, 3rd ed. — Ross Anderson (2020), ch. on trusted computing and API security: threat-model structure and fail-closed API design; applied in §22 and §17.
  • Systems Performance, 2nd ed. — Brendan Gregg (2020), CPU/cache/scheduler chapters: profiling methodology and tail-latency diagnosis; applied in §28.

Papers

  • "Intel SGX Explained" — Costan, Devadas, 2016, IACR ePrint 2016/086: enclave memory- isolation model and sealing-key derivation → informs the software isolation contract in enclave-runtime; applied in §18.
  • "Sanctum: Minimal Hardware Extensions for Strong Software Isolation" — Costan, Lebedev, Devadas, 2016, USENIX Security: page-table-based isolation reasoning without a black-box CPU root of trust → validates simulating enclave isolation entirely in software; applied in §18.
  • "ROTE: Rollback Protection for Trusted Execution" — Matetic et al., 2017, USENIX Security: anti-rollback protocol for TEEs without trusted hardware counters → directly informs the monotonic-counter design; applied in §15 and §16.
  • "In Search of an Understandable Consensus Algorithm (Extended Version)" — Ongaro, Ousterhout, 2014, USENIX ATC: deterministic log replication and leader-driven commit ordering → the WAL commit-coordinator model; applied in §16.
  • "Dynamo: Amazon's Highly Available Key-value Store" — DeCandia et al., 2007, SOSP: failure-recovery and quorum reasoning under partial failure → informs verifier-cluster recovery; applied in §24.
  • "The Tail at Scale" — Dean, Barroso, 2013, CACM: tail-latency amplification under fan-out → the p99 budgeting methodology in §4 and §28; applied in §28.
  • "Eraser: A Dynamic Data Race Detector for Multithreaded Programs" — Savage, Burrows, Nelson, Sobalvarro, Anderson, 1997, SOSP: lockset-based race detection → the concurrency-fixture strategy for enclave-runtime; applied in §18 and §26.
  • "All File Systems Are Not Created Equal: On the Role of Semantics in Crash Consistency" — Pillai, Chidambaram, Alagappan, Al-Kiswany, Arpaci-Dusseau, Arpaci-Dusseau, 2014, OSDI: crash- consistency vulnerability classes in real WAL implementations → the torn-write pitfalls in §16; applied in §16.

Reference Implementations

  • stefanberger/libtpms — study src/tpm2/ command processor: TPM 2.0 command-dispatch structure and NVRAM persistence (the reference-implementation core that stefanberger/swtpm links as a library); pitfall: do not copy its synchronous, single-call-at-a-time command dispatch, it caps throughput far below §4's 20k commits/sec target; applied in §13.
  • tpm2-software/tpm2-tss — study src/tss2-mu/ marshaling layers: ABI discipline for TPM command/response marshaling; pitfall: do not copy its C ABI directly, prefer prost-typed envelopes; applied in §13 and §11.
  • opendnssec/SoftHSM2 — study src/lib/data_mgr/: PKCS#11 key-storage isolation and object handle lifecycle; pitfall: its flat-file object store is not crash-safe under SIGKILL, do not copy the storage layer; applied in §14 and §16.
  • keylime/keylime — study keylime/tpm/: attestation-verifier architecture and quote- validation workflow; pitfall: its Python verifier trusts client-reported nonces too loosely, do not copy the nonce-validation path; applied in §19.
  • gramineproject/gramine — study libos/: enclave-runtime isolation semantics and syscall shimming; pitfall: its LibOS surface is far larger than this project needs, do not import the full syscall shim; applied in §18.
  • aws/aws-nitro-enclaves-sdk-c — study source/attestation.c: COSE-signed attestation-document structure and operational patterns for remote verification; pitfall: Nitro's attestation model assumes a hypervisor-issued document, this project must issue its own trust anchor; applied in §19.

RFCs / Specifications

  • TPM 2.0 Library Specification, Part 1 — Architecture — TCG: hierarchy, PCR, and NV-index semantics that this project's command engine is shaped after; applied in §8 and §15.
  • RFC 8446 — TLS 1.3 — pins the transport-security handshake terminated at the gateway before commands reach the trust boundary; applied in §13.
  • RFC 5869 — HKDF — pins the key-derivation construction used for sealing-key derivation; applied in §14.
  • RFC 8017 — PKCS #1 v2.2 — pins RSA signature padding for quote signing where RSA hierarchies are configured; applied in §14 and §19.
  • NIST SP 800-90A Rev. 1 — pins the deterministic-RNG construction (CTR_DRBG/Hash_DRBG) used for the deterministic RNG harness; applied in §14.
  • NIST SP 800-108 — pins the KDF-in-counter-mode construction used alongside HKDF for hierarchy-key derivation; applied in §14.
  • RFC 8949 — CBOR — pins the canonical-encoding fallback format for replay-artifact interoperability with non-Rust tooling; applied in §20.

Glossary (§36) · 45 terms · site-wide glossary

PCR
Platform Configuration Register; append-only measurement register extended via a hash chain.
Quote
a signed attestation statement binding a PCR snapshot and a nonce.
WAL
write-ahead log; the durability unit committed before any state mutation is acknowledged.
NV Index
a persistent TPM storage slot (NvSlot, §11) addressed independently of hierarchy.
Replay Hash
the deterministic digest of an execution, compared across original and replayed runs (I8).
Locality
an execution privilege domain gating PCR reset authorization.
Sealing
encrypting data such that decryption requires a specific trust-state predicate.
Attestation
cryptographic trust verification of a remote system's measured state.
Hierarchy
a TPM ownership domain rooted at an endorsement or storage root key.
Monotonic Counter
a non-decreasing durable counter (I3) underpinning anti-replay.
Trust Anchor
a root or intermediate verification key/certificate for attestation reports.
Snapshot
a durable, atomic point-in-time state checkpoint (I11).
Integrity Tree
a tamper-evident hash structure enabling sub-linear corruption localization.
Replay Divergence
a mismatch between original and replayed execution hashes (I8 violation).
Quarantine
the isolation state entered after corruption or integrity-tree failure (P11).
TPMContext
the global mutable trust-state struct (§11).
EnclaveContext
isolated per-tenant execution state (§11).
PolicySession
composable authorization evaluation state (§17).
EventRecord
an append-only immutable mutation record (I7, §11).
CommandEnvelope
the wire-level command frame (§11).
PersistenceFrame
the on-disk framing envelope for WAL/snapshot records (§11).
DRBG
Deterministic Random Bit Generator; the replayable RNG construction (NIST SP 800-90A).
HKDF
HMAC-based Key Derivation Function (RFC 5869), used for sealing-key derivation.
AEAD
Authenticated Encryption with Associated Data; the AES-GCM sealing primitive.
Fail Closed
the principle that authorization ambiguity resolves to denial (P10).
Backpressure
explicit rejection of new work when a bounded queue is full (P5).
Cooperative Scheduling
a scheduling model where tasks yield voluntarily at defined points.
Cancellation Token
the cooperative-cancellation signal checked at scheduler yield points.
Quota Accounting
the per-context resource ledger enforcing I12.
Group Commit
batching multiple WAL appends into one fsync to amortize durability cost.
Compaction
periodic snapshot rewriting that reclaims WAL space (P9 exception path).
Replay Trace
the sealed artifact recording scheduler ordering and execution hash (§11).
Nonce Window
the bounded single-use validity window for attestation nonces (I10).
Trust Boundary
the point (gateway) where untrusted input becomes validated internal state.
Persistence Boundary
the point below which state is only visible after integrity verification.
Concurrency Boundary
the point at which one enclave context's state becomes invisible to another (I9).
Handle Generation
the version counter on a TPMHandle preventing stale-handle reuse (I6).
Session Token
the credential binding a policy session to one command-sequence lineage (I13).
Fixture
a named, checked-in test input/expected-output pair under fixtures/ or conformance/.
Soak Test
a long-duration (30-day) continuous-load run detecting slow leaks (§21).
Chaos Testing
randomized fault injection against the running system (§21, §26).
SBOM
Software Bill of Materials; CycloneDX manifest of every dependency (§27).
Reproducible Build
a build producing a byte-identical artifact across independent builders (§12.4, ADR-19).
Verifier
a remote party that validates an AttestationReport against a trust anchor (§19).
Divergence Detector
the per-checkpoint hash-comparison mechanism in replay-engine (§20).
