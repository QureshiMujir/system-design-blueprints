⬜ Phase 0 — Repository, Build Foundations & Correctness Kernel §12

Objectives

Stand up the Cargo workspace, reproducible toolchain, CI topology, dependency policy, and baseline observability scaffolding, and land the correctness kernel: tpm-core's context/handle/state- machine skeleton and the conformance-harness fixture runner that every later phase depends on. Scope excludes any real cryptography or protocol decoding — those arrive in Phase 1 (§13) and Phase 2 (§14). This phase introduces the constraint that nothing later may bypass the fixture harness to validate behavior.

Deliverable

A compiling, lint-clean, reproducible-hash Cargo workspace with all fifteen crates from §1 present as skeletons, green CI on GitHub Actions, an operational metrics registry, and a fixture runner capable of loading and replaying a fixture file end to end (with a no-op command).

Acceptance
  • All 15 crates compile with zero warnings under -D warnings in CI.
  • Cargo.lock hash is byte-identical across 2 independent CI runners for 3 consecutive builds.
  • SBOM (sbom.cdx.json) generated successfully on every CI run.
  • fixtures/build/reproducible-build-001 passes: identical output hash across builders.
  • fixtures/logging/span-propagation-001 passes: a synthetic 3-hop span propagates a shared trace_id end to end.
Fixtures
  • fixtures/build/reproducible-build-001 — two clean builds, identical sha256 of the release binary; regression if either builder drifts.
  • fixtures/logging/span-propagation-001 — synthetic request through gateway → executor → persistence stub; expects one continuous trace_id.
  • fixtures/build/malformed-lockfile-002 — corrupted Cargo.lock; expects a hard build failure with a specific diagnostic, not a silent re-resolve.
Pitfalls
  • Hidden dependency drift from unpinned transitive versions — manifests as CI passing on one runner and failing on another; root cause is a floating semver range slipping past cargo-deny; debug via cargo tree --duplicates; signal is a lockfile diff nobody authored; recovery is re-pinning and adding a cargo-deny ban rule.
  • Non-deterministic build timestamps embedded via env!("CARGO_PKG_VERSION")-adjacent macros — breaks the reproducible-build fixture; root cause is a build script reading wall-clock time; fix by injecting a fixed SOURCE_DATE_EPOCH.
  • CI cache poisoning from a stale target/ cache surviving a toolchain bump — manifests as mysterious link errors; detect via cache-key including toolchain hash; recover by cache eviction.

⬜ Phase 1 — Binary Protocol & Command Engine §13

Objectives

Implement the canonical command-envelope wire format, frame decoding, replay-safe sequencing, authorization routing, and deterministic dispatch in tpm-command-engine. Introduces the constraint that no malformed input may mutate state (P10, fail closed) before validation completes.

Deliverable

A runnable command engine that receives commands over the gRPC/Unix-socket gateway, validates framing, and dispatches to stub handlers — end to end, with zero unhandled panics under fuzzing.

Acceptance
  • Malformed frames are rejected deterministically: 100% of fuzz/frame_decoder.rs corpus crashes fixed, zero crashes after 4 CPU-hours of fuzzing.
  • Replay traces are byte-identical across 3 repeated executions of fixtures/protocol/replay- sequence-gap-003.
  • p99 dispatch latency for a valid frame < 1 ms measured via benchmarks/, well inside the §4 command-latency budget once policy/persistence stages are added later.
Fixtures
  • fixtures/protocol/frame-valid-001 — well-formed envelope, expects successful dispatch to a stub handler.
  • fixtures/protocol/frame-invalid-checksum-002 — corrupted checksum byte, expects deterministic rejection with CHECKSUM_MISMATCH.
  • fixtures/protocol/replay-sequence-gap-003 — a gap in sequence_number, expects rejection and a protocol_sequence_gap_total increment, never a silent skip.
  • fixtures/protocol/truncated-frame-004 — length prefix exceeds actual payload, expects rejection before allocation (regression fixture for a buffer-overrun-shaped bug class).
Pitfalls
  • Endian inconsistencies between the length prefix and payload — manifests as intermittent decode failures only on cross-architecture fixtures; root cause is mixing native-endian and wire-endian reads; debug via a fixed-endian round-trip fixture; recovery is standardizing on little-endian on the wire regardless of host.
  • Unchecked length prefixes — manifests as an allocation spike or OOM under a crafted frame; root cause is trusting the prefix before bounds-checking against the connection's quota; signal is a memory-usage metric spike correlated with one session; recovery is a hard length ceiling checked before allocation.
  • Handle-reuse races — manifests as a handler operating on a handle whose generation just rolled over; root cause is missing the generation check from I6; debug via replay trace diffing; recovery is enforcing generation-match at dispatch, not just at creation.

⬜ Phase 2 — Cryptographic Execution Engine §14

Objectives

Implement isolated cryptographic execution workers and key-lifecycle primitives in tpm-crypto: AEAD, RSA hierarchy, ECC quote signing, HKDF, deterministic RNG, and secure zeroization. Introduces the constraint that key material has exactly one owner at all times (P3) and every crypto operation is auditable (P7).

Deliverable

An operational crypto subsystem: key creation, signing, sealing, and quote generation, callable from tpm-command-engine handlers, with all 128 workers passing NIST test vectors.

Acceptance
  • 100% of applicable NIST CAVP test vectors pass for AES-GCM, RSA, ECC, and HKDF.
  • Zero memory leaks under valgrind/miri across a 10,000-operation key-lifecycle fuzz run.
  • Replay determinism preserved: fixtures/crypto/hkdf-003 produces byte-identical derived keys across 5 replays.
  • p99 AES-GCM seal latency < 200 µs single-op, feeding the §4 command-latency budget.
Fixtures
  • fixtures/crypto/aes-gcm-001 — NIST vector encrypt/decrypt round trip, exact ciphertext match.
  • fixtures/crypto/ecc-sign-002 — deterministic ECDSA (RFC 6979-shaped) sign/verify round trip.
  • fixtures/crypto/hkdf-003 — RFC 5869 test-vector derivation, exact output-key match.
  • fixtures/crypto/nonce-reuse-004 — forces a nonce collision under fault injection, expects a hard reject, never silent reuse (regression fixture for a known AES-GCM catastrophic-failure class).
  • fixtures/crypto/zeroize-005 — post-drop memory scan finds no residual key bytes.
Pitfalls
  • Accidental key cloning via a Clone-derived struct — manifests as two live copies of secret material surviving one drop; root cause is deriving Clone on a type holding key bytes; debug via a compile-time lint (clippy::derive_partial_eq_without_eq-style custom lint); recovery is banning Clone on key-bearing types at the type-system level (P3).
  • Nonce reuse under concurrent access to the same key — manifests as AES-GCM confidentiality failure (fixture 14.5-004); root cause is a counter shared without atomic increment; debug via the nonce-reuse fixture; recovery is an atomic per-key nonce counter, never caller-supplied.
  • Entropy starvation on the deterministic RNG harness under high concurrency — manifests as workers blocking on reseed; root cause is a single shared DRBG instance; recovery is per-worker DRBG instances reseeded from a session-level seed tree.

⬜ Phase 3 — PCR & Measured-Boot Engine §15

Objectives

Implement measured-boot semantics: PCR banks, extend/reset, locality rules, and event-measurement records in tpm-pcr. Introduces I2 (ordered extension only) as an enforced, not advisory, constraint from the first commit.

Deliverable

A measured-state engine supporting PCR extend, reset, and quote linkage — extend calls from tpm-command-engine now durably affect PCR state and are visible to attestation-service stubs.

Acceptance
  • Replay hashes stable across 10 repeated replays of fixtures/pcr/extend-sequence-001.
  • Event-log ordering preserved: extend records appear in eventlog-engine in the exact order submitted, verified against sequence_number.
  • PCR lineage deterministic under 3 concurrent extend attempts (§15.8), resolved to one well-defined winner order, never an undefined interleaving.
  • Extend throughput ≥ 50,000/sec single-bank, matching the §4 target.
Fixtures
  • fixtures/pcr/extend-sequence-001 — 1,000 sequential extends, expects a specific final digest.
  • fixtures/pcr/reset-locality-002 — reset attempted without required locality, expects rejection.
  • fixtures/pcr/concurrent-extend-003 — 3 concurrent extend requests on one bank, expects one deterministic serialized order and a matching replay hash.
  • fixtures/pcr/corrupted-bank-004 — checksum-corrupted snapshot on load, expects quarantine, not a best-effort partial load.
Pitfalls
  • Hash-ordering bugs from extending with digest || old_pcr instead of old_pcr || digest — manifests as a PCR value that matches no known-good reference measurement; root cause is operand order; debug by comparing against a reference swtpm extend of the same digest sequence; recovery is fixing operand order and re-deriving all downstream quotes.
  • Locality bypass via a reset path that doesn't check the locality field — manifests as an unauthorized reset succeeding; root cause is a second reset code path added later that skips the §15.2 check; recovery is centralizing all reset entry points through one authorization gate.
  • Inconsistent replay ordering under concurrent extends without the per-bank lock — manifests as replay hash mismatch (I8 violation) despite each individual extend being individually valid; recovery is the single per-bank extend lock from §15.2, never per-register locking.

⬜ Phase 4 — Secure Persistence Layer (WAL & Snapshots) §16

Objectives

Implement encrypted crash-safe persistence in tpm-persistence: WAL append protocol, snapshot compaction, integrity trees, and recovery replay. This is the phase that makes P2 (crash-only semantics) real rather than aspirational — everything durable from Phases 1–3 now survives SIGKILL.

Deliverable

A crash-safe persistence engine: tpm-command-engine handlers now durably commit through WAL before acknowledgment, and a killed-and-restarted daemon recovers to the exact pre-crash state.

Acceptance
  • Survives 500 SIGKILL-during-commit trials (fixtures/wal/crash-mid-commit-001) with zero corrupted recoveries.
  • Replay recovery is deterministic: same WAL + snapshot always recovers to the same state hash.
  • Corruption is detected reliably: 100% of fixtures/wal/checksum-corruption-002 injections are caught before any corrupted data is served.
  • Integrity-replay validation completes in < 15 s for a 10 GB state, matching §4.
  • Persistence commit throughput ≥ 20,000/sec, matching §4; WAL fsync p99 < 25 ms.
Fixtures
  • fixtures/wal/crash-mid-commit-001 — SIGKILL injected at a randomized point mid-commit across 500 trials, expects clean recovery every time.
  • fixtures/wal/checksum-corruption-002 — a single flipped byte in a WAL segment, expects detection and quarantine, not a silently corrupted state.
  • fixtures/wal/partial-segment-003 — a WAL segment truncated mid-write (simulating disk-full), expects recovery to the last complete record, not a parse error that halts recovery entirely.
  • fixtures/wal/snapshot-race-004 — a snapshot compaction racing an in-flight commit, expects I1 (no snapshot references unapplied WAL) to hold.
Pitfalls
  • Torn writes on power loss (partial sector write) — manifests as a checksum mismatch on the last WAL record after an unclean shutdown; root cause is a write spanning a sector boundary without a write barrier; debug via the partial-segment-003 fixture; recovery is treating the last incomplete record as absent, not as corrupt-the-whole-segment.
  • fsync ordering bugs where the snapshot rename happens before the underlying data fsync completes — manifests as a snapshot that looks committed but loses data on crash; root cause is missing an explicit fsync-then-rename barrier; recovery is enforcing fsync(data) → fsync(dir) → rename order per I11.
  • Snapshot race conditions between the compactor and the live commit path — manifests as snapshot-race-004's failure mode; root cause is compaction reading a watermark that the commit path then moves past mid-compaction; recovery is a compaction-time write-lease that blocks new commits from advancing the watermark until compaction publishes.

⬜ Phase 5 — Policy Evaluation Engine §17

Objectives

Implement composable authorization evaluation in tpm-policy: expression parsing, composite policies, signed assertions, and replay-safe evaluation. Introduces P10 (fail closed) as an enforced gate on every command from this phase forward.

Deliverable

A deterministic policy evaluator wired into tpm-command-engine's dispatch path (§13): every command now passes through policy evaluation before execution, with composite PCR + locality + counter-threshold policies fully evaluable.

Acceptance
  • Replay deterministic: fixtures/policy/composite-and-001 produces identical allow/deny across 10 replays.
  • Malformed policies rejected: fixtures/policy/cyclic-policy-003 rejected at parse time, never reaching evaluation.
  • Evaluation latency p99 < 500 µs single-policy, keeping policy evaluation off the critical path of the §4 10 ms p95 command-latency budget.
Fixtures
  • fixtures/policy/composite-and-001 — a 3-term CompositeAnd (PCR match + locality + counter threshold), expects deterministic allow.
  • fixtures/policy/pcr-match-002 — a PCR-predicate policy evaluated against a stale epoch, expects cache invalidation and re-evaluation, not a stale allow.
  • fixtures/policy/cyclic-policy-003 — a self-referential composite policy, expects parse-time rejection.
  • fixtures/policy/stale-lineage-004 — an assertion referencing a revoked key lineage, expects fail-closed rejection.
Pitfalls
  • Policy-cache poisoning from caching across a PCR epoch boundary — manifests as a stale allow after a PCR reset that should have invalidated the policy's PCR predicate; root cause is a cache key missing the epoch; debug via pcr-match-002; recovery is epoch-scoped cache keys.
  • Short-circuit inconsistency where CompositeAnd/CompositeOr evaluate operands in a different order on replay than on original execution — manifests as I4 violation only under composite policies with side-effect-free-but-order-sensitive sub-evaluations (e.g., a counter-threshold check that reads a counter mid-mutation); recovery is defining a canonical left-to-right evaluation order and enforcing it identically on replay.
  • Fail-open defaults from an unhandled PolicyExpression variant — manifests as a new variant added in a later change silently matching "true" in an exhaustive-looking match that has a catch-all arm; recovery is banning catch-all arms on PolicyExpression matches via lint (P10).

⬜ Phase 6 — Enclave Runtime Scheduler §18

Objectives

Implement the isolated execution scheduler in enclave-runtime: enclave contexts, quota accounting, cooperative scheduling, cancellation, and bounded mailboxes. Introduces I9 (memory isolation between contexts) and I12 (quota never negative) as compiler- and runtime-checked invariants.

Deliverable

A runnable multi-tenant enclave runtime: up to 512 concurrent enclave contexts (§4), each isolated, quota-enforced, and cancellable, hosting the crypto and PCR operations from Phases 2–3 as scheduled tasks rather than direct calls.

Acceptance
  • Quotas enforced: fixtures/scheduler/quota-enforcement-001 — a context exceeding its 64 MB default quota (§4) is denied further allocation, never OOM-killed silently.
  • Starvation prevented: fixtures/scheduler/starvation-002 — under 512 contexts submitting work continuously, the lowest-priority context still makes forward progress within a bounded number of scheduler ticks.
  • Replay deterministic: scheduler ordering recorded and replayed produces the identical task interleaving, feeding I8 via replay-engine (§20).
  • Context-switch throughput ≥ 250,000/sec across 512 contexts, matching §4.
Fixtures
  • fixtures/scheduler/quota-enforcement-001 — a context allocating past its quota, expects rejection at the exact byte over the limit, not a fuzzy threshold.
  • fixtures/scheduler/starvation-002 — 512 contexts under sustained load, expects bounded max wait-time per context.
  • fixtures/scheduler/cancellation-race-003 — cancellation issued mid-yield-point, expects clean teardown, no partial-state leak into a subsequent task reusing the same slot.
  • fixtures/scheduler/nested-cancellation-004 — a cancelled context that itself owns sub-tasks, expects cascading cancellation, not orphaned sub-tasks.
Pitfalls
  • Deadlocks from a context awaiting its own quota release inside a callback holding the quota lock — manifests as a hung context that never times out; root cause is re-entrant locking around the accountant; debug via tokio-console task-dump; recovery is making the accountant lock-free (atomic compare-and-swap) rather than mutex-guarded.
  • Runaway allocations from a task that yields but never releases its partial allocation — manifests as quota exhaustion despite low apparent activity; root cause is missing a yield-point cleanup hook; recovery is RAII-style quota guards tied to task lifetime, not manual release calls.
  • Cancellation races where a cancelled task's in-flight persistence commit (§16) is torn — manifests as a WAL entry with no corresponding task outcome; root cause is cancelling without waiting for the commit's fsync ack; recovery is making cancellation cooperative-only at yield points that exclude in-flight commits (§18.2).

⬜ Phase 7 — Attestation Services §19

Objectives

Implement quote generation and the verifier stack in attestation-service: attestation reports, verifier API, certificate chains, nonce validation, and anti-replay windows. Introduces I10 (single-use nonces) as the anti-replay backbone for remote trust establishment.

Deliverable

A remote attestation service: a verifier can request a quote over gRPC, receive a signed AttestationReport, and independently verify it against a known trust anchor — interoperable with the fixture-driven differential harness against keylime-shaped verification logic.

Acceptance
  • Quote verification interoperable: fixtures/attestation/quote-valid-001 verifies successfully against an independent verifier implementation in conformance-harness.
  • Replay attacks rejected: fixtures/attestation/replay-attack-002 — a reused nonce is rejected 100% of the time across 1,000 trials.
  • Quote generation p99 < 75 ms, matching §4.
  • Trust-anchor rotation completes with zero verification downtime for reports signed under the prior anchor still within its validity window.
Fixtures
  • fixtures/attestation/quote-valid-001 — a well-formed quote request/response round trip.
  • fixtures/attestation/replay-attack-002 — a captured valid quote replayed with the same nonce, expects rejection via I10.
  • fixtures/attestation/expired-trust-root-003 — a report signed under an anchor past its validity window, expects rejection, not a grace-period allow.
  • fixtures/attestation/malformed-quote-bundle-004 — a truncated certificate chain, expects rejection before signature verification is even attempted (fail fast on structural malformation).
Pitfalls
  • Nonce reuse from a client retry that resubmits the same nonce after a timeout — manifests as a legitimate retry being indistinguishable from a replay attack at the nonce layer alone; root cause is conflating "nonce reuse" with "attack" without a client-visible retry protocol; recovery is requiring clients to request a fresh nonce per attempt, enforced by the verifier rejecting reused nonces unconditionally (the client, not the server, absorbs the retry cost).
  • Clock-drift assumptions in the anti-replay window — manifests as legitimate requests rejected across a multi-region deployment with clock skew; root cause is using wall-clock deltas instead of the injected logical sequence from ADR-20; recovery is windowing on sequence number primarily, wall-clock as a secondary sanity bound only.

⬜ Phase 8 — Replay & Deterministic Debugging §20

Objectives

Implement the replay engine and forensic tooling in replay-engine: scheduler-ordering recording, deterministic re-execution, divergence detection, and CLI tooling. This phase makes I8 (replay hash equality) mechanically checkable across the whole system rather than per-subsystem.

Deliverable

A replay-debuggable runtime: any production incident can be replayed offline from its ReplayTrace, reproducing the exact scheduler interleaving and cryptographic operation sequence that led to the observed state.

Acceptance
  • Replay hash equality: fixtures/replay/divergence-001 — a known-good trace replays to the identical execution_hash across 20 repeated replays.
  • Deterministic scheduler reproduction: the exact task-interleaving order from the original execution is reproduced, not merely an equivalent-outcome interleaving.
  • Divergence localization: an injected single-bit corruption in a mid-trace checkpoint is localized to the correct subsystem boundary in fixtures/replay/crash-recovery-002.
Fixtures
  • fixtures/replay/divergence-001 — a clean trace, expects zero divergence across 20 replays.
  • fixtures/replay/crash-recovery-002 — a trace spanning a SIGKILL-and-recover boundary (§16), expects the recovered portion to replay identically to the pre-crash portion's continuation.
  • fixtures/replay/hidden-entropy-003 — a trace containing an accidental live-clock read, expects the divergence detector to flag the exact checkpoint, not a generic "mismatch" error.
  • fixtures/replay/partial-artifact-004 — a trace truncated by an unclean shutdown mid-write, expects graceful partial-replay-with-warning, not a hard crash of the replay tool itself.
Pitfalls
  • Hidden entropy sources (a stray SystemTime::now() call inside a supposedly deterministic path) — manifests as intermittent, unreproducible divergence; root cause is bypassing the injected logical clock (ADR-20); debug via the hidden-entropy-003 fixture and a lint banning direct SystemTime/Instant reads inside trust-kernel crates; recovery is routing all time reads through the injected clock abstraction.
  • Clock-based divergence from using wall-clock deltas for any decision inside the trust kernel — same root cause as above, different manifestation (a timeout fires differently on replay than on original execution); recovery is identical.

⬜ Phase 9 — Operational Hardening & Release §21

Objectives

Finalize production readiness: chaos testing, soak testing, compatibility-matrix validation, rolling-upgrade validation, backup/restore verification, SLO dashboards, and incident runbooks. This phase's scope is entirely operational — no new subsystem behavior is introduced, only validation and hardening of Phases 0–8.

Deliverable

A production-ready release candidate: soak-validated, chaos-tested, compatibility-matrix-passing, with SLO dashboards live and runbooks published for every registered failure class.

Acceptance
  • 30-day soak run stable: zero unrecoverable corruption events, memory growth < 5% over the full window after excluding expected cache warm-up.
  • No unrecoverable corruption across 200 chaos-injection trials (fixtures/ops/backup-restore-002 family).
  • All §4 SLO targets met in the soak environment, cross-checked against §28's target table.
  • Rolling upgrade validated across 3 consecutive minor versions with zero client-visible errors.
Fixtures
  • fixtures/ops/rolling-upgrade-001 — a mixed N/N+1 cluster processing 10,000 commands, expects zero decode failures.
  • fixtures/ops/backup-restore-002 — full export/import cycle, expects bit-identical state hash.
  • fixtures/ops/chaos-disk-fault-003 — randomized disk-fault injection during sustained load, expects either clean commit or clean rejection, never silent corruption.
  • fixtures/ops/soak-memory-004 — a scaled-down 24-hour soak fixture used as a CI gate before the full 30-day run, expects bounded memory growth.
Pitfalls
  • Telemetry overload from soak-run metric cardinality (per-session labels accumulating over 30 days) — manifests as the telemetry pipeline itself becoming the bottleneck; root cause is unbounded label cardinality (violates P5 applied to observability, not just to queues); recovery is capping per-session labels and aggregating to per-shard cardinality for long-running metrics.
  • Upgrade schema drift where a rolling upgrade's N+1 node writes a snapshot field the N node's decoder doesn't recognize — manifests as decode failures during the rollback path of a bad upgrade; root cause is an additive field that wasn't actually optional at decode time; recovery is a compatibility-matrix CI gate (§21.2) that must pass before any release tag.
