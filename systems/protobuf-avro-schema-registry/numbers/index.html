32. Back-of-Envelope Capacity Model

  • C1 — Registry RSS. Schema cache 10,000 × 2 KB = 20 MB + SQLite pool 16 × 2 MB = 32 MB + HTTP buffers 512 × 64 KB = 32 MB → 84 MB total, inside the 512 MB §4 ceiling.
  • C2 — Proto encode CPU budget. 150 ns (§4, M1) × 5,000 req/s peak = 0.75 ms CPU/s ≈ 0.075% of one core.
  • C3 — FD budget. 16 SQLite conns + 512 max-concurrency keep-alives + 32 misc = 560, inside the 1,024 §4 FD ceiling.
  • C4 — Storage amplification. 1 schema avg 2 KB raw × 1.3 amplification (§4) = 2.6 KB on disk per stored version.
  • C5 — WAL checkpoint exposure. RPO 5 min (§4) ÷ avg write rate 10 writes/min = 50 writes at risk inside one checkpoint gap.
  • C6 — Fuzz corpus growth. 20,000 exec/s (M11) × 8 h nightly run = 576,000,000 execs/night; corpus dedup keeps unique retained inputs under 50,000.
  • C7 — Transitive compat-check cost. 50 versions × 0.5 ms per pairwise check = 25 ms (half of M8's 1 ms p99 margin, matching M9's target exactly).
  • C8 — Registration throughput ceiling. p99 POST 10 ms (§4/M6) → 100 req/s per connection × 16 conns = 1,600 req/s before queueing begins.
  • C9 — Cache hit savings. Cached GET p99 2 ms vs. uncached SQLite read ≈ 8 ms (M12 analog) = 4× latency reduction from the fingerprint LRU.
  • C10 — Availability-to-incident budget. 99.9% monthly (§4) = 43.8 min downtime budget ÷ 15 min average incident MTTR (RTO, §4) = 2.9 allowed incidents/month before SLA breach.
  • C11 — Startup budget breakdown. 300 ms (§4) = SQLite open+migration-check 120 ms + tokio init 40 ms + axum router build 30 ms + tracing init 20 ms = 210 ms, leaving a 90 ms margin.
  • C12 — Max-concurrency memory. 512 concurrency (§4) × 64 KB per-request buffer = 32 MB, already counted inside C1's HTTP-buffer line.
