178 — Protobuf / Avro Serializer + Schema Registry from Scratch

Project Number: 178

Project Name: Protobuf / Avro Serializer + Schema Registry from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. Build, from first principles and without wrapping prost, protobuf, or apache-avro, a Rust workspace that (a) parses and compiles Protocol Buffers proto3 IDL and Apache Avro JSON schemas into a single unified schema intermediate representation, (b) implements protobuf and Avro binary wire codecs that interoperate byte-for-byte with protoc/prost and Java Avro, (c) implements a compatibility-checking engine matching Confluent's BACKWARD / FORWARD / FULL / *_TRANSITIVE semantics, and (d) serves a Confluent-Schema-Registry-API-compatible HTTP registry backed by pluggable storage. The system is a reusable serialization and schema-governance foundation, not an application.

Phase 0 deliverable — numbered crates/services:

  1. serdes-common — shared error types, byte-buffer helpers, ID newtypes.
  2. serdes-proto-parse — proto3 lexer, recursive-descent parser, AST, descriptor builder.
  3. serdes-proto-codec — protobuf wire encoder/decoder, unknown-field retention, packed repeated.
  4. serdes-avro-schema — Avro JSON schema parser, namespace resolver, canonicalizer, fingerprints.
  5. serdes-avro-codec — Avro binary encoder/decoder, reader/writer resolution, union dispatch.
  6. serdes-schema — unified schema IR (SchemaKind), evolution metadata, fingerprint algorithm.
  7. serdes-compat — compatibility checker: backward, forward, full, transitive.
  8. serdes-registry — Confluent-compatible REST API (axum), subject/version lifecycle.
  9. serdes-store — storage trait; SQLite (WAL) and in-memory backends.
  10. serdes-cli — compile / encode / decode / validate / serve commands (clap).
  11. fixtures/ — protobuf, Avro, and registry-API fixture corpora.
  12. benchmarks/ — Criterion throughput/latency harness.
  13. fuzz/ — cargo-fuzz targets for parsers, decoders, and the registry API surface.

System boundaries.

  • Provides: proto3 + Avro parsing/compilation, binary codecs, compatibility checking, a schema registry HTTP API, a CLI, conformance and fuzz infrastructure.
  • Delegates: TLS termination and load balancing to the deployment's reverse proxy/ingress; container orchestration to Kubernetes or equivalent; multi-tenant authentication to a future gateway (PhaseDeferred, see Deferred Features Register).
  • Does not provide: gRPC transport, code generation for non-Rust languages, distributed consensus/replication, a UI, or Kafka producer/consumer client libraries — the registry is consumed by such clients, it does not embed them.

Non-goals: proto2 extension groups, dynamic reflection over arbitrary FFI, a general-purpose JSON-schema engine, multi-region active-active writes in Phase 0–9.

Deployment model: single stateless serdes-registry binary per replica, N replicas behind a load balancer, one shared SQLite file on a durable volume (single-writer) or one in-memory instance for tests/CI. Clients (Kafka producers, gRPC services, CDC connectors) call the REST API or embed serdes-proto-codec / serdes-avro-codec directly as libraries.

Target operators: platform/infrastructure teams running a Kafka or event-bus deployment who need schema governance without a JVM dependency; embedded/edge teams needing a no_std-friendly codec without a registry at all.

What later phases unlock: Phase 3–4 unlock Avro interoperability; Phase 5 unlocks safe schema evolution; Phase 6–7 unlock a running registry service; Phase 8 unlocks operator/CI ergonomics; Phase 9 unlocks certified interoperability claims via differential fuzzing against protoc and Java Avro.

Recommended language: Rust 1.78+. Rationale: ownership-tracked buffer lifetimes make zero-copy decoding (P4) statically checkable rather than convention-based; the enum/pattern-match model maps directly onto SchemaKind's closed sum type (§11) with exhaustiveness checked at compile time; #![forbid(unsafe_code)] is enforceable workspace-wide without losing wire-level performance, which the no-panic invariant (I8) depends on; the fuzzing ecosystem (cargo-fuzz, libFuzzer) is first-class. Rejected: Go — GC pauses and interface-based dynamic dispatch complicate the sub-microsecond encode budget (§4) and its type system cannot express SchemaKind as a closed, exhaustively-matched sum type; C++ — memory safety of a network-facing parser (handling untrusted .proto/.avsc input, §22) is a correctness liability without a borrow checker, and the fuzzing/tooling ergonomics are weaker than Rust's for this domain.

Prerequisites: Rust ownership and lifetimes; binary/varint encoding; UTF-8; recursive-descent parser construction; HTTP semantics; async runtimes (tokio); Kafka and protobuf fundamentals; schema-evolution theory (backward/forward compatibility).

Estimated timeline: Phase 0 MVP (workspace + correctness kernel, §12) — 2 weeks. Full production stack (Phases 0–9, a running registry with conformance and fuzzing) — 5–6 months at one senior engineer full-time. Distributed registry clustering (deferred) — +2 months. Multi- language codegen (deferred) — +2 months.

What Mastery Looks Like

  • Can implement Avro's Parsing Canonical Form and prove two syntactically different schemas fingerprint identically — gained in §15.

  • Can design a SQLite-backed storage trait that supports both an embedded single-writer backend and a future distributed backend without changing the registry's HTTP layer — gained in §18.

2. Why Build This

Every RPC request, Kafka event, CDC record, stream-processing payload, cache snapshot, ML feature vector, database replication log, and telemetry event on a distributed system crosses a serialization boundary. Most engineers consume protobuf/avro as opaque black boxes and cannot: explain protobuf wire tags; implement zigzag encoding; preserve unknown fields on re-serialization; perform Avro reader/writer schema resolution; enforce BACKWARD/FORWARD/FULL compatibility; build a schema registry; canonicalize a schema; compute a deterministic fingerprint; or design a schema- governance REST API. This project builds all of it: parser construction, binary protocol design, schema-evolution theory, compatibility semantics, high-performance encoding, registry architecture, distributed-metadata-adjacent storage design, conformance testing, and protocol fuzzing.

Portfolio connectivity. This project is a dependency of, or a direct unlock for, several other projects in the portfolio: a Kafka clone needs its wire serialization; a gRPC framework needs its protobuf codec; a CDC engine needs its schema-evolution semantics; a stream processor needs its runtime decoding; an OLAP engine needs columnar-friendly ingestion of decoded records; a feature store needs versioned schemas; an API gateway needs JSON/protobuf transcoding; a service mesh needs xDS-style protobuf config parsing.

Calibration value. Completing it demonstrates systems-level protocol literacy, compiler front-end competence, storage-interface design, wire-level debugging ability, production schema- governance understanding, binary performance engineering, and interoperability discipline. After it, network-protocol implementations, compiler front ends, and Kafka/gRPC internals debugging all become materially easier — the parser (§13), the codec (§14/§16), and the registry (§19) are the three hardest sub-problems most engineers never build once, let alone twice.

Box notes. Clients are the trust boundary: all .proto/.avsc and registry-API input is adversarial (§22). serdes-proto-parse / serdes-avro-schema lower untrusted syntax into typed ASTs with bounded recursion (I2, I14). serdes-schema is the single normalization point — every compatibility and codec decision reads the IR, never the source ASTs directly (P1, P2). The codec layer is the only place wire bytes exist; it is intentionally the smallest, most performance- critical, most fuzzed component (§14, §16, §21). serdes-compat is pure — it takes two IR values and a mode, returns a report, and never touches storage or the network (P5). serdes-registry is the only network-facing, async, multi-tenant-adjacent component (concurrency boundary: tokio) and the only component with an authentication surface (currently deferred, §35). serdes-store is the persistence boundary: everything above it operates on SchemaKind values in memory; everything below it is bytes on disk, gated by a trait so SQLite can be swapped for a future distributed backend (P8) without touching the registry HTTP layer.

6. Design Principles

  • P1 — Schema-First Architecture. Rule: every encode/decode call resolves through a registered SchemaKind (§11); no schemaless path exists. Tradeoff: rejects ad-hoc dynamic JSON passthrough for unknown payloads. Operational: schema fingerprint is logged on every codec invocation (see §19.10). Violated: silent type confusion at decode time corrupts downstream columnar ingestion with no error signal.
  • P2 — Unified Intermediate Representation. Rule: both the proto AST (§13) and the Avro AST (§15) lower into SchemaKind before any compatibility or codec logic runs. Tradeoff: an extra lowering pass (~microseconds) per schema compile. Operational: IR fingerprint logged per lowering. Violated: the compatibility engine (§17) forks into two divergent rule sets, doubling the test surface and guaranteeing drift.
  • P3 — Deterministic Encoding. Rule: encoding the same SchemaKind value twice, on any host, produces byte-identical output. Tradeoff: forbids nondeterministic map/field ordering shortcuts. Operational: encode output is snapshot-tested (insta, ADR-25). Violated: fingerprints (I5) stop being reproducible and CI snapshot diffs become permanently noisy.
  • P4 — Zero-Copy Hot Paths. Rule: decoders borrow &[u8] slices from the input buffer instead of allocating new String/Vec<u8> on the fast path. Tradeoff: decoded values carry input- buffer lifetimes, complicating ownership at call sites. Operational: allocation count asserted in codec benchmarks (§28). Violated: decode latency (M2/M4, §28) regresses under load from heap churn.
  • P5 — Explicit Evolution Semantics. Rule: every compatibility failure returns a structured report naming the violating field; no silent coercion. Tradeoff: producers must handle explicit 409 responses instead of "best effort" writes. Operational: rejection reasons are counted per category (compat_reject_reason_total, §19.10). Violated: a producer ships a breaking schema that consumers discover only in production.
  • P6 — No Panic Boundaries. Rule: no parser or decoder path may panic on attacker-controlled bytes (I8); all failures are Result<_, E>. Tradeoff: every fallible step needs explicit error variants instead of unwrap(). Operational: decoder_panics_total must read zero in production; any nonzero value pages on-call. Violated: a single malformed message crashes the registry process, taking down every subject's availability.
  • P7 — Protocol Correctness Over Convenience. Rule: the protobuf and Avro specs dominate any implementation shortcut that would break interop. Tradeoff: some ergonomic Rust idioms (e.g. serde's automatic field-name matching) are rejected in favor of spec-exact field-number/order semantics. Operational: differential fuzzing against protoc/Java Avro (§21) gates releases. Violated: the codec silently diverges from protoc on an edge case, breaking cross-language interop invisibly until a partner team hits it.
  • P8 — Pluggable Storage. Rule: serdes-registry never imports rusqlite directly; it depends only on the SchemaStore trait (§11). Tradeoff: every storage operation must be expressible as an async trait method, ruling out backend-specific shortcuts. Operational: both SQLite and in-memory backends run the identical integration-test suite (§18.5). Violated: swapping storage backends (P8's whole purpose, see §34's rejected Raft alternative) requires rewriting the HTTP layer instead of one crate.
  • P9 — Canonicalization Determinism. Rule: canonicalizing an Avro schema is a pure function — same input schema, same canonical bytes, every time (I5). Tradeoff: canonicalization must avoid any hash-map iteration order dependency. Operational: a differential fixture asserts N syntactically distinct but semantically equal schemas fingerprint identically (§15.5). Violated: the registry treats two copies of the same schema as different subjects, doubling storage and breaking dedup.
  • P10 — Interoperability First. Rule: every codec claim is proven against a real external implementation (protoc, Java Avro), never against this project's own round-trip alone. Tradeoff: Phase 9 (§21) must vendor or shell out to reference tooling in CI. Operational: diff_protoc and cross-Avro fixtures run on every merge. Violated: two mutually-consistent bugs in encoder and decoder cancel out locally but break every external consumer.
  • P11 — Observability by Default. Rule: every phase ships tracing spans, structured-log fields, and Prometheus metrics before the phase is marked deliverable (§12.10 onward). Tradeoff: instrumentation code is written before the feature it measures is fully proven out. Operational: serve command refuses to start without a metrics endpoint bound (§20.4). Violated: a production incident (§23) has no signal to triage against, and MTTR blows past the RTO budget.
  • P12 — Phase Isolation. Rule: deferred functionality (§35) must not leak into any Phase 0–9 API surface — no half-finished trait methods for gRPC or multi-tenant auth. Tradeoff: some APIs look intentionally narrower than the eventual system. Operational: a grep-based CI check scans for todo!()/unimplemented!() in shipped phase code. Violated: a deferred feature's partial implementation ships silently broken, and a consumer depends on it before it is finished.
  • P13 — Backpressure Before Buffering. Rule: the registry sheds load via a bounded concurrency limiter (ADR-21) before ever growing an unbounded queue. Tradeoff: clients see 503 under sustained overload instead of increasing latency. Operational: http_requests_rejected_total tracked alongside p99 latency (§28). Violated: an unbounded internal queue grows until the process OOMs, failing every in-flight request instead of shedding the newest ones.
  • P14 — Fixture-Driven Regression. Rule: every bug found by fuzzing or in production becomes a named, checked-in conformance fixture (§21.5) before the fix merges. Tradeoff: bug-fix PRs are larger and slower to land. Operational: CI fails if a fuzz crash directory has no matching fixture reference in the PR diff. Violated: the same bug class recurs after a refactor because nothing pinned the original failure.

Debugging methodology. Every invariant above has exactly one assertion site and one fixture that would fail if the assertion were removed — enforced by a deterministic, seedable simulator (serdes-common::sim) that replays recorded byte streams and schema mutations against the codec, compatibility, and store layers with no wall-clock or OS-scheduler nondeterminism. 8. Domain Model — Protobuf and Avro Wire-Format Semantics

Protobuf wire tags. Every field is encoded as one leading varint: (field_number << 3) | wire_type (I1). Wire types: 0 Varint (int32/int64/uint32/uint64/sint32/sint64/bool/enum), 1 64-bit (fixed64/sfixed64/double), 2 Length-delimited (string/bytes/embedded message/packed repeated), 5 32-bit (fixed32/sfixed32/float). There is no wire type 3/4 in proto3 (groups, proto2-only, deferred — see §35).

Varint encoding. Little-endian base-128 with a continuation bit: each byte holds 7 payload bits in the low bits and a high bit set on every byte except the last. Bounded by I2 to ≤ 10 bytes (covers a full u64).

ZigZag encoding. Maps signed integers onto the unsigned varint space so small-magnitude negatives stay short: encoded = (n << 1) ^ (n >> 63) for 64-bit sint64. Used only for sint32/sint64; plain int32/int64 varint-encode negatives as full-width two's-complement (long encoding), which is why ZigZag exists as a distinct wire convention.

Avro binary encoding. Schema-directed, no field tags: fields are read/written strictly in schema declaration order (I4). A record with fields id: long, name: string encodes as <long><string> with zero framing bytes between them — the reader schema alone determines field boundaries, which is why reader/writer resolution (§16) exists as a distinct engine from the codec itself.

Schema Registry API model. POST /subjects/{subject}/versions with body {"schema": "..."} returns {"id": <SchemaId>}. Compatibility modes: NONE (no checks), BACKWARD (new schema can read data written with the old schema), FORWARD (old schema can read data written with the new schema), FULL (both directions), and the *_TRANSITIVE variants of each, which check against every historical version of the subject, not just the immediately preceding one (I7).

13.1 Objectives

13.2 Detailed Implementation Steps

  1. serdes-proto-parse::token — define enum Token (Ident, IntLiteral, StringLiteral, punctuation, keywords) with Span (byte-offset range) attached to every variant.

  3. serdes-proto-parse::parser — recursive-descent parser over the token stream: package, import, message, enum, service, oneof, field-option, repeated-field, and map-field grammar productions; anchors to Nystrom's recursive-descent architecture (§5) and to P7 (spec-exact grammar, no shortcuts).
  4. serdes-proto-parse::ast — typed AST nodes (MessageDecl, FieldDecl, EnumDecl, ServiceDecl) mirroring the grammar, each carrying its Span for diagnostics.
  5. serdes-proto-parse::descriptor — lowers AST into ProtoDescriptor (§11): resolves field types (scalar vs. message-reference), assigns default field ordering, validates field-number uniqueness within a message (a precursor to I1's tag-space invariant).
  6. serdes-proto-parse::import_resolver — resolves import "path.proto" statements against a sandboxed root directory; maintains a visited-set to reject cycles (I14) and rejects path traversal (../) per the threat model's T4.
  7. serdes-proto-parse::diagnostics — structured parse errors carrying Span + human message; never a bare panic! (I8) — every parser function returns Result<_, ParseError>.
  8. Add parser error recovery: on a malformed field declaration, skip to the next ; or } and continue collecting diagnostics instead of aborting on the first error (P6-adjacent UX, not an invariant, but required for the invalid_field.proto fixture to report all errors at once).

  • Recursive imports (a.proto imports b.proto imports a.proto) — manifestation: parser hang or stack overflow; root cause: no visited-set in import_resolver; debugging: add cycle-path logging before the fix, reproduce with imports.proto's cyclic variant; signal: CI timeout; recovery: I14's visited-set check, reject with the cycle path in the diagnostic.
  • Span corruption after error recovery — manifestation: a diagnostic points at the wrong source line after a skip-to-; recovery; root cause: recovery logic advances the token cursor without updating the span baseline; debugging: differential test comparing span offsets against a known-good parse; signal: confusing error messages in invalid_field.proto's CI output; recovery: recompute span from the resumed token, not the pre-error token.
  • Keyword-vs-identifier ambiguity (message used as a field name in some grammars) — root cause: proto3 reserves fewer keywords than expected; debugging: differential test against protoc's accepted grammar; signal: a valid .proto file used by a real service rejected; recovery: match protoc's exact reserved-word list (P10, P7).
  • Malformed UTF-8 in string literals or comments — manifestation: lexer panics or produces garbled tokens; root cause: byte-slicing without UTF-8 boundary checks; debugging: fuzz the lexer (§21.2) with arbitrary byte sequences; signal: cargo-fuzz crash bucket; recovery: validate UTF-8 boundaries before slicing, return ParseError::InvalidUtf8.

13.7 Performance Concerns

Token allocation churn: each Token should avoid owning a String where a Span into the source buffer suffices (P4 applied to the parse phase, not just codec). Parser recursion depth interacts with stack size — bound it explicitly (13.6) rather than relying on the OS default stack to fail safely. Diagnostic collection in a Vec is fine at parse-time scale (schemas are KBs, not GBs) — no streaming parser is needed here, unlike the codec's decode path.

13.8 Edge Cases

Empty .proto files (zero messages) must parse successfully to an empty ProtoDescriptor, not error. Duplicate field numbers within one message must be rejected at descriptor-construction time, not silently overwrite. Reserved keywords used incorrectly (e.g. reserved ranges overlapping active field numbers) must be diagnosed, not ignored. Deeply nested oneof-inside- oneof constructs (not legal proto3, but worth testing the parser's rejection path) must produce a diagnostic, not a panic.

13.9 Failure Analysis

A parser bug either (a) rejects valid .proto input — detected by the basic.proto/nested.proto regression fixtures failing, blast radius limited to whichever schema triggers it, contained by CI gating merges — or (b) accepts invalid input silently, which is more dangerous: it can produce a descriptor with duplicate field numbers that later corrupts wire encoding (§14). Detection for (b) leans on differential fuzzing against protoc (§21, P10) rather than unit tests alone, since unit tests only encode cases the author already thought of. Recovery: patch plus a new fixture per P14.

13.10 Operational Notes

Metrics: proto_parse_errors_total{kind}, proto_parse_duration_seconds (histogram). Tracing span: proto.parse with fields file_path, message_count, error_count. Structured-log fields: subject_hint (best-effort, populated once the CLI/registry callers exist in §19/§20). Deployment: this crate is a library, not a service — no independent deployment. Rollback: n/a. Migration: n/a. Compatibility implications: none yet — descriptor-level compatibility is §17's concern, applied only after §14/§16 give it something to check against.

14. Phase 2 — Protobuf Binary Codec

14.1 Objectives

Implement the protobuf wire codec: varint/zigzag primitives, wire-tag encode/decode, packed repeated fields, and unknown-field retention, interoperating byte-for-byte with protoc/prost (P10). Constraint introduced: encode/decode must hit the §4 latency budgets (< 150 ns / < 250 ns p50 for a 64 B message) with zero heap allocation on the hot path (P4). Dynamic reflection over descriptors and protobuf-JSON mapping are PhaseDeferred("§14") (see §35).

14.2 Detailed Implementation Steps

  1. serdes-proto-codec::varint — encode/decode functions for unsigned base-128 varints, bounded to 10 bytes max per I2; anchors to Petrov's Database Internals varint chapter (§5).
  2. serdes-proto-codec::zigzag — sint32/sint64 transforms per §8's ZigZag formula.
  3. serdes-proto-codec::wire — WireTag encode ((field_number << 3) | wire_type, I1) and decode with overflow checking on field_number.
  4. serdes-proto-codec::encoder — implements ProtoEncoder (§11) over SchemaKind; field dispatch by declared type; deterministic field-order emission (P3).
  5. serdes-proto-codec::decoder — implements ProtoDecoder (§11) with a decode state machine over ByteCursor (P4, zero-copy borrow of the input buffer).
  6. serdes-proto-codec::packed — packed-repeated encoding for scalar-typed repeated fields (length-delimited run of varints/fixed-width values, not one tag per element).
  7. serdes-proto-codec::unknown_fields — UnknownFieldSet (§11) captures any tag not present in the active schema as raw bytes, re-emitted verbatim on re-encode (I3).
  8. String/bytes handling: length-delimited payloads validated as UTF-8 for string fields (not bytes), rejecting invalid sequences per I8's no-panic-on-bad-input guarantee.
  9. Add a decode state machine covering malformed-length-prefix and truncated-payload paths, returning DecodeError::Truncated/DecodeError::LengthOverflow rather than panicking (I2).
  10. Cross-validate encode/decode output against protoc --encode/--decode in CI (P10, ADR reference: protocolbuffers/protobuf, §5) using the fixtures in 14.5.

14.3 Deliverable

serdes-proto-codec encodes and decodes any RecordSchema-shaped message to/from bytes that protoc's reference C++ implementation accepts and round-trips identically; unknown fields survive a decode→re-encode cycle byte-for-byte.

14.4 Acceptance Criteria

  • Encode p50 latency < 150 ns and decode p50 < 250 ns for a 64 B message with 5 scalar fields, measured by the Criterion bench in benchmarks/codec_bench.rs (M1/M2, §28).
  • malformed.bin (§14.5) decode returns Err(DecodeError::Truncated), never panics, in 100/100 fuzz replay runs.
  • unknown.bin roundtrips with zero byte drift, asserted by a byte-equality check, not just a structural equality check.
  • Zero heap allocations recorded by the allocation-counting test harness during decode of int32.bin (P4).

14.5 Conformance Fixtures

Fixture Assertion
fixtures/proto/int32.bin varint round-trip correctness for int32/int64/uint32/uint64
fixtures/proto/packed.bin packed-repeated scalar fields encode/decode correctly
fixtures/proto/malformed.bin truncated varint returns a decode error, never panics
fixtures/proto/unknown.bin unknown fields retained byte-exact across a roundtrip

14.6 Pitfalls

  • Truncated varints at end-of-buffer — manifestation: decoder reads past the buffer end; root cause: missing bounds check before the continuation-bit test; debugging: fuzz with truncated inputs (§21); signal: cargo-fuzz OOB-read crash; recovery: I2's 10-byte + bounds-checked loop.
  • Integer overflow on a maliciously long varint sequence — manifestation: silently wrapping u64 arithmetic instead of erroring; root cause: shift-accumulate loop without an overflow guard on byte 10; debugging: fixed fuzz corpus entry with 11 continuation bytes; signal: incorrect decoded value instead of an error; recovery: explicit checked_shl/overflow check.
  • Recursion bombs via deeply nested embedded messages — manifestation: stack overflow on decode; root cause: no depth limit on length-delimited sub-message recursion; debugging: fuzz with deeply nested packed.bin-style payloads; signal: crash, not a graceful error; recovery: shared recursion-depth counter with the parser's I14 limit (128 levels).
  • Duplicate fields for a non-repeated scalar — manifestation: ambiguity over which value wins; root cause: protobuf spec says "last one wins" but that's easy to implement backwards; debugging: differential fixture against protoc's documented last-wins semantics; signal: decoded value mismatches protoc's output; recovery: always overwrite on duplicate, never merge.

14.7 Performance Concerns

Branch misprediction in the field-dispatch match on wire type — mitigated by ordering match arms by observed frequency (varint and length-delimited dominate real traffic) rather than declaration order. Buffer reallocation during encode — pre-size the output Vec<u8> using a cheap upper-bound size estimate before encoding, avoiding repeated Vec growth. Small-write amplification — batch field writes into a local stack buffer before a single extend_from_slice call rather than many small push calls, reducing bounds-check overhead per byte.

14.8 Edge Cases

Empty repeated fields must encode as zero bytes, not an empty length-delimited marker. Max u64 values (0xFFFFFFFFFFFFFFFF) must round-trip exactly through the 10-byte varint boundary. Malformed UTF-8 in a string field must be rejected at decode with DecodeError::InvalidUtf8, never lossily replaced. Zero-length messages (all fields absent, all defaults) must encode as zero bytes total, per proto3's default-value-omission rule.

14.9 Failure Analysis

A codec bug is the highest-blast-radius failure class in the whole system: every consumer of every schema is affected simultaneously, and corruption can be silent (wrong bytes, no error) rather than loud (a decode error). Detection leans on three layers: unit fixtures (14.5), differential testing against protoc (P10), and continuous fuzzing (§21) — because unit tests alone have already been shown (Heartbleed-class bugs across the industry) to miss boundary conditions in binary parsers. Containment: the codec has no ambient state, so a bad decode cannot corrupt other decodes, only the one malformed input. Recovery: patch, add a fixture (P14), re-run the full differential suite before merge, never just the new fixture.

14.10 Operational Notes

Metrics: codec_encode_errors_total, codec_decode_truncated_total, codec_decode_overflow_total, unknown_field_bytes_retained (I1–I3's telemetry columns, §7). Tracing: no per-message span (too high-frequency — would itself become a performance concern per §4's latency budget); instead, sampled span proto.codec.decode.slow fires only when decode exceeds 10× the p50 budget. Structured-log fields: none per-message (volume); aggregate error counters only. Deployment: n/a, library crate. Migration: a codec change that alters byte layout for any type is a breaking wire change and must go through §25's compatibility/versioning process, not a normal release.

15. Phase 3 — Avro Schema Parser & Canonicalization

15.1 Objectives

Parse Avro JSON schemas (.avsc) into SchemaKind (§11) via an AST, resolve namespaces, support recursive named-type references, and compute Parsing-Canonical-Form fingerprints (I5). Constraint introduced: canonicalization must be a pure, order-independent function of schema content (P9) — this phase is the trust root every dedup and compatibility decision in §17/§18 depends on.

15.2 Detailed Implementation Steps

  1. serdes-avro-schema::json_parser — parses .avsc JSON text per RFC 8259 (§5) using serde_json (ADR-05) into an untyped serde_json::Value, then a typed AvroAst.
  2. serdes-avro-schema::namespace — resolves each named type's fully-qualified name (namespace.name), building a registry of named types visible for Reference(String) resolution (§11); detects and rejects namespace collisions.
  3. serdes-avro-schema::canonical — implements Avro's Parsing Canonical Form: strips docs/aliases, normalizes field order preservation (order matters for Avro, unlike JSON object key order), fully qualifies all type names; anchors to apache/avro's Schema.java canonicalization algorithm (§5) and to P9.
  4. serdes-avro-schema::fingerprint — computes SchemaFingerprint (§11) as a hash (e.g. CRC-64- AVRO per the Avro spec) over the canonical-form bytes; pure function, I5.
  5. serdes-avro-schema::aliases — resolves field- and type-level aliases used by reader/writer resolution (§16) to match renamed fields across schema versions.
  6. Support recursive named-type references (a record referencing itself via a named union branch) using the namespace registry's visited-set, mirroring I14's cycle-safety pattern from the proto parser but permitting legitimate self-reference (unlike proto's import cycles, Avro recursive types are valid and required for e.g. linked-list-shaped schemas).
  7. Support Avro unions (["null", "string"]-style) as SchemaKind::Union, validating that no union contains two branches of the same unnamed type (an Avro spec ambiguity rule).
  8. Validate field defaults against their declared type at parse time (a "default": "x" on an int field is a compile-time schema error, not a runtime surprise).
  9. Build canonical-form snapshot tests (insta) proving two syntactically different but semantically equal schemas produce byte-identical canonical output (P9's fixture).
  10. Validate Reference(String) targets resolve to a type actually present in the namespace registry, rejecting dangling references before this schema is ever fingerprinted.

15.3 Deliverable

serdes-avro-schema compiles an .avsc JSON string into a SchemaKind value with a computed SchemaFingerprint, exposed as parse(src: &str) -> Result<SchemaKind, AvroSchemaError>.

15.4 Acceptance Criteria

  • user.avsc (§15.5) parses into a SchemaKind::Record with exactly its 2 declared fields, in ≤ 300 µs.
  • Two reordered-but-semantically-identical copies of user.avsc (differing only in JSON key order within each field object) produce identical SchemaFingerprint values — the direct P9 fixture.
  • recursive.avsc parses successfully (no stack overflow, no false-positive cycle rejection).
  • invalid_union.avsc (duplicate unnamed-type union branch) is rejected with a specific AvroSchemaError::AmbiguousUnion variant, not a generic parse failure.

15.5 Conformance Fixtures

Fixture Assertion
fixtures/avro/user.avsc parses a valid two-field record
fixtures/avro/recursive.avsc self-referential record type parses without infinite recursion
fixtures/avro/invalid_union.avsc ambiguous union (duplicate branch type) is rejected

15.6 Pitfalls

  • Namespace collisions between two same-named types in different files — manifestation: the second type silently shadows the first; root cause: namespace registry keyed by short name instead of fully-qualified name; debugging: differential fixture with two user.avsc variants under different namespaces; signal: wrong type resolved at reference time; recovery: key the registry by fully-qualified name always.
  • Recursive-type infinite loop during canonicalization — manifestation: canonicalizer hangs on recursive.avsc; root cause: canonical-form serialization walks the type graph without a visited-set; debugging: add a recursion-depth counter and reproduce with a minimal self- referential fixture; signal: CI timeout; recovery: canonicalize named types once, referencing by name thereafter, not by full inline expansion.
  • Invalid defaults accepted silently — manifestation: a "default": "x" on an int field parses without error, then fails confusingly at decode time; root cause: default validation deferred to the codec instead of the schema parser; debugging: add a fixture pairing every primitive type with a mismatched default; signal: a decode-time error that should have been a compile-time one; recovery: validate defaults against declared type during parse (15.2 step 8).
  • Ambiguous unions — manifestation: two branches of the same underlying type in one union; root cause: Avro spec forbids this but many hand-written schemas violate it unknowingly; debugging: invalid_union.avsc fixture; signal: AvroSchemaError::AmbiguousUnion; recovery: reject at parse, never attempt best-effort disambiguation.

15.7 Performance Concerns

JSON parsing allocation pressure (serde_json::Value's tree-of-Box shape) is acceptable since schemas are KB-scale, parsed rarely at registration time, not per-message. Canonicalization copies happen once per distinct schema and are cached with the fingerprint (I5) — never recomputed by §17's compatibility checks, which read the cached canonical bytes directly.

15.8 Edge Cases

Empty unions ([]) are invalid per spec and must be rejected, not silently treated as null. Duplicate aliases across two fields must be rejected (ambiguous rename target during §16 resolution). Invalid namespace strings (leading digit, embedded whitespace) must be rejected at parse time, not deferred to a confusing failure during registry storage (§18).

15.9 Failure Analysis

A canonicalization bug is uniquely dangerous because it is invisible until compared — two schemas that should fingerprint identically but don't will silently double-register in the store (§18), and two schemas that shouldn't match but do will falsely trigger dedup. Detection: the P9 equivalence-class fixture (15.4) run on every change to canonical.rs. Blast radius: every subject using an affected schema shape. Containment: fingerprint mismatches surface immediately as unexpected new SchemaIds in the registry's version history, visible to operators via fingerprint_collisions_total (I5's telemetry). Recovery: fix canonicalization, then a one-time backfill re-fingerprints existing stored schemas (migration, see 15.10).

15.10 Operational Notes

Metrics: avro_parse_errors_total{kind}, fingerprint_collisions_total, canonicalization_duration_seconds. Tracing span: avro.schema.parse with fields namespace, type_count. Structured-log fields: schema_fingerprint on every successful parse, for correlation with later registry events. Deployment: library crate, no independent deployment. Migration: a canonicalization algorithm change requires a re-fingerprint backfill job against serdes-store — tracked as a Phase 6 (§18) operational runbook entry, never a silent behavior change. Compatibility implications: none directly — this phase produces the inputs §17 checks, but does not itself check compatibility.

16. Phase 4 — Avro Binary Codec

16.1 Objectives

Implement the Avro binary codec: schema-directed positional encoding, block-encoded arrays/maps, union dispatch, and reader/writer schema resolution (type promotion, default injection, unknown- field skipping), interoperating with Java Avro (P10). Constraint introduced: decode must resolve a writer schema against a possibly-different reader schema without any registry lookup mid-decode — resolution is a pure function of the two schemas (I12).

16.2 Detailed Implementation Steps

  1. serdes-avro-codec::encoder — implements ProtoEncoder-shaped trait for Avro: encodes primitives (zigzag varint for int/long, IEEE-754 for float/double, length-prefixed for string/bytes) in strict declaration order (I4).
  2. serdes-avro-codec::block — block encoding for array/map: a sequence of (item-count, items) blocks terminated by a zero-length block, per the Avro spec's array/map framing (distinct from protobuf's packed-repeated framing in §14).
  3. serdes-avro-codec::union — union branch dispatch: writer encodes a zigzag-varint branch index followed by the branch's value; anchors to apache-avro's decode.rs reference (§5), adapted away from its dynamic Value dispatch per that entry's stated pitfall.
  4. serdes-avro-codec::decoder — implements the decode side, borrowing from the input buffer where the branch type permits (P4); returns DecodedMessage-equivalent typed values.
  5. serdes-avro-codec::resolution — reader/writer schema resolution: matches fields by name (with alias fallback from §15.2), applies numeric type promotion (int→long→float→ double, the one promotion chain the spec allows), injects reader-side defaults for fields absent from the writer schema, and skips writer fields absent from the reader schema.
  6. Implement default injection: when the reader schema declares a field the writer schema lacks, inject the reader's declared default rather than erroring (unless no default exists, which is I12's guarded case).
  7. Implement writer-field skipping: an unrecognized (from the reader's perspective) writer field must still be parsed (to know its byte length) and discarded, never merely byte-skipped blindly, because variable-length types require full decoding to find their end.
  8. Validate union branch selection against the schema at compile time (reject a schema whose union branches can't be unambiguously encoded), separate from the ambiguous-union rejection already done in §15.
  9. Add block-encoding edge-case handling: negative block counts signal a "count then size" framing variant in the Avro spec (used for skippable unknown blocks) — support decoding it even though this codec never emits it.
  10. Cross-check against Java Avro's reference implementation in CI using evolution.bin and the other fixtures in 16.5 (P10, apache/avro reference, §5).

16.3 Deliverable

serdes-avro-codec encodes/decodes any SchemaKind value to/from Avro binary bytes that interoperate with Java Avro, including cross-version reader/writer resolution.

16.4 Acceptance Criteria

  • Encode p50 < 400 ns, decode p50 < 450 ns for a typical 5-field record (M3/M4, §28).
  • evolution.bin (§16.5) decodes correctly under three different reader schemas (older, same, newer than the writer), each producing the resolution-correct value set.
  • A reader schema requiring a field the writer lacks, with no default declared, returns Err(SchemaResolutionError::MissingDefault) — the I12 fixture — in 100% of 50 fuzz-generated variants.
  • arrays.bin round-trips block-encoded arrays of 0, 1, and 10,000 elements with byte-exact re-encoding.

16.5 Conformance Fixtures

Fixture Assertion
fixtures/avro/primitives.bin primitive-type encode/decode correctness for all 9 PrimitiveType variants
fixtures/avro/arrays.bin block encoding correctness across empty, small, and large arrays
fixtures/avro/evolution.bin reader/writer resolution across three schema-version pairs

16.6 Pitfalls

  • Union dispatch ambiguity at decode — manifestation: decoder picks the wrong branch for a value that could structurally fit two branches; root cause: the encoder didn't preserve which branch was chosen distinctly enough; debugging: differential fuzz against Java Avro (§21); signal: FM-10 (§23); recovery: always trust the explicit branch-index prefix, never re-infer from shape.
  • Incorrect default injection — manifestation: a missing field gets the wrong default (e.g. 0 instead of the schema's declared default); root cause: default lookup falls back to a type's zero-value instead of Field.default (§11); debugging: evolution.bin fixture with a non-zero default; signal: silently wrong data downstream; recovery: always read Field.default.
  • Schema-mismatch handling that silently truncates — manifestation: extra writer fields are dropped without validating they parse to a complete, well-formed value first; root cause: attempting a byte-skip instead of a full decode-then-discard; debugging: fuzz with variable- length extra fields (nested records, strings); signal: decode desyncs on the next field after the skipped one; recovery: 16.2 step 7's decode-then-discard, never skip by estimated length.

16.7 Performance Concerns

Union branch scans — dispatch by branch index directly (O(1)) rather than scanning branches by type match (O(n)); the wire format already encodes the index, so re-deriving it from value shape is both slower and the root cause of 16.6's ambiguity pitfall. Recursion overhead for nested records is bound by the depth limit shared with the parser (I14-adjacent); Avro's tag-free framing makes a recursive record cheaper per level (no per-field tag byte) but riskier to bound.

16.8 Edge Cases

Empty arrays/maps must encode as a single zero-length terminating block, not an absent block. Deeply nested unions (["null", ["null", "string"]]-shaped illegal nesting, or legally nested records-within-unions) must be exercised by a dedicated fixture. Invalid promotions (e.g. double→int, not in the allowed promotion chain) must be rejected during resolution, returning SchemaResolutionError::InvalidPromotion, not a silently truncating cast.

16.9 Failure Analysis

Reader/writer resolution bugs are the Avro-specific analog of §14.9's codec risk, but with a distinct failure shape: because there's no wire tag to cross-check against, a resolution bug can produce a plausible but wrong decoded value rather than an outright decode error, making it the hardest class of bug in this system to detect via monitoring alone. Detection leans almost entirely on differential testing against Java Avro (P10) plus the fixture corpus in 16.5, since production telemetry cannot distinguish "correctly resolved" from "wrongly but plausibly resolved" without a ground truth. Containment: resolution is stateless and schema-pair-scoped, so a bug affects only messages decoded under that specific (writer, reader) schema pair. Recovery: patch resolution.rs, add the specific (writer, reader) pair as a permanent fixture (P14).

16.10 Operational Notes

Metrics: avro_encode_order_violations_total, avro_resolution_missing_default_total, avro_union_branches_rejected_total. Tracing span: avro.codec.decode, sampled at the same slow-path rate as §14.10's proto equivalent. Structured-log fields: writer_fingerprint, reader_fingerprint on any resolution event, correlating which schema pairs are actually exercised in production. Deployment: library crate. Migration: PhaseDeferred("§16") — Avro logical types and Avro object container files (OCF) are deferred; see the Deferred Features Register. Compatibility implications: this resolution engine makes §17's abstract rules real — a "PASS" that this engine can't actually resolve at decode time would be a contract violation.

17. Phase 5 — Compatibility Engine

17.1 Objectives

Implement serdes-compat: a pure function from (old: &SchemaKind, new: &SchemaKind, mode: CompatibilityMode) -> CompatibilityResult (§11's CompatibilityChecker trait) matching Confluent's BACKWARD/FORWARD/FULL/*_TRANSITIVE semantics exactly (P10, confluentinc/schema- registry reference, §5). Constraint introduced: the engine touches no storage and no network — it is testable in complete isolation from §18/§19 (P5).

17.2 Detailed Implementation Steps

  1. serdes-compat::backward — a new schema is BACKWARD-compatible with an old one if data written with the old schema can be read with the new one: added fields must have a default or be optional; removed fields must have had a default in the old schema; anchors to Kleppmann's Schema Evolution comparison (§5) and I7.
  2. serdes-compat::forward — the symmetric check: old schema can read data written with the new one; removed fields need a default in the new schema, added fields don't break the old reader as long as it ignores unknowns (I3's retention guarantee makes this provable, not assumed).
  3. serdes-compat::full — both directions must hold; implemented by calling backward and forward and requiring both Ok, not by writing a third independent rule set (avoids drift, P2).
  4. serdes-compat::transitive — for *_TRANSITIVE modes, checks the new schema against every stored version of the subject, not just the latest (I7); short-circuits on the first failing pair but records all violations for reporting (P5).
  5. Enum widening rule: adding a new Avro/proto enum symbol is BACKWARD-safe; removing one is always treated as breaking (undecidable historical-usage otherwise) — a deliberately conservative, locked design choice, not a bug.
  6. Field-removal checks: a field can be removed only if it carried a default in the schema version it's being removed relative to (§11's Field.default).
  7. Alias resolution: a field rename (old name aliased by the new schema, §15.2 step 5) is treated as the same field, not a remove+add pair — the one place this engine reads metadata beyond raw structure.
  8. Type-promotion compatibility: the numeric promotion chain the Avro codec resolves at decode time (§16.2 step 5) must be recognized as compatible here too, per §5's terminology-lock rule.
  9. serdes-compat::report — structured CompatibilityResult with one CompatibilityViolation per failing field, never a single opaque boolean (P5).
  10. Build the transitive-check graph traversal as an explicit visited-set walk over stored versions (I7), not naive O(n²) pairwise re-checking beyond what's needed for the short-circuit.

17.3 Deliverable

A CompatibilityChecker implementation callable as a library function and, once §19 exists, via POST /compatibility/subjects/{subject}/versions/{version}.

17.4 Acceptance Criteria

  • backward.json (§17.5): a schema adding an optional field passes BACKWARD in < 1 ms p99 (M8, §28).
  • breaking.json: a schema removing a required field with no default is rejected under all four base modes, with a CompatibilityViolation naming the exact field path.
  • aliases.json: a field renamed via alias is treated as compatible, not reported as a remove+add.
  • Transitive check across 50 synthetic historical versions completes in < 25 ms p99 (M9, §28).

17.5 Conformance Fixtures

Fixture Assertion
fixtures/compat/backward.json additive, defaulted change passes BACKWARD
fixtures/compat/breaking.json required-field removal without a default is rejected
fixtures/compat/aliases.json alias-based rename resolves as the same field, not a break

17.6 Pitfalls

  • Incorrect transitive traversal — manifestation: a *_TRANSITIVE check passes when it should fail against an older-than-latest version; root cause: the traversal only compared against the immediately preceding version; debugging: a 3-version fixture where versions 1 and 3 conflict but 2 and 3 don't; signal: a consumer on version 1 breaks despite a "compatible" registration; recovery: I7's full visited-set walk over every stored version, not just the latest.
  • Enum narrowing accepted by mistake — manifestation: removing an enum symbol passes BACKWARD; root cause: enum checks reused the field-removal default-check path, which doesn't apply to symbols; debugging: a dedicated enum-narrowing fixture; signal: a consumer reading old data encounters a symbol its (over-narrowed) schema doesn't know; recovery: treat all enum-symbol removal as breaking, unconditionally (17.2 step 5).
  • Default-coercion bugs — manifestation: a numeric default like 0 is treated as "no default" by a truthy-check bug; root cause: Option<LiteralValue> unwrapped with a falsy-value shortcut instead of an is_some() check; debugging: a fixture with an explicit zero default; signal: false-positive breaking-change rejection; recovery: always check Option presence, never the contained value's truthiness.

17.7 Performance Concerns

Recursive graph traversal cost scales with subject history length — bounded in practice by the §4 storage-amplification budget limiting how many versions accumulate before archival, but the transitive check itself is O(versions × fields) per registration, which is why M9's 25 ms budget assumes 50 versions, not unbounded history. Large schema histories are mitigated by caching each pairwise comparison's canonical-form inputs (already fingerprinted, §15) rather than re- canonicalizing per check.

17.8 Edge Cases

Cyclic schema references (a record referencing itself through a chain of aliases) must not cause the transitive traversal to loop — reuses the namespace registry's cycle-safety pattern (§15.6). Duplicate aliases pointing at two different current fields must be rejected as ambiguous before compatibility checking ever runs (caught upstream in §15, not re-validated here). Union widening (adding a branch) is BACKWARD-safe only if the new branch isn't required for older data to decode — validated against the resolution engine's actual behavior (§16), not assumed structurally.

17.9 Failure Analysis

A false "compatible" verdict is the dangerous failure mode: it lets a breaking schema into production, surfacing later as a consumer decode error (§16.9) with no compatibility-engine signal pointing back at root cause. Detection: golden fixtures (17.5) covering every rule in 17.2; a false "incompatible" verdict is lower-risk (blocks a valid change) and surfaces as a support complaint instead. Containment: the engine is pure and stateless, so a bug reproduces deterministically from the two schemas alone. Recovery: patch, add the schema pair as a fixture (P14), re-run the full 17.5 suite.

17.10 Operational Notes

Metrics: compat_transitive_checks_total, compat_reject_reason_total{reason}. Tracing span: compat.check with fields subject, mode, version_count. Structured-log fields: old_fingerprint, new_fingerprint, compatible. Deployment: library crate, invoked synchronously from §19's registration handler. Migration: tightening a rule (e.g. enum-narrowing) is versioned per §25 — it can retroactively fail a previously-accepted schema pair on re-check. Compatibility implications: this phase is the compatibility implication for every other phase.

18. Phase 6 — Registry Storage Layer

18.1 Objectives

Implement serdes-store: the SchemaStore trait (§11) with a SQLite (WAL-mode) backend and an in-memory backend, both passing an identical integration-test suite (P8). Constraint introduced: every registration is one atomic transaction (I9); SchemaId allocation is strictly monotonic (I6) even under concurrent writers.

18.2 Detailed Implementation Steps

  1. serdes-store::lib — define the SchemaStore trait boundary (§11) as the only interface serdes-registry (§19) is allowed to depend on (P8).
  2. serdes-store::sqlite — WAL-mode rusqlite connection pool (ADR-04); schema table keyed by (subject, version) with a unique index on SchemaFingerprint for dedup (I5) and a monotonic INTEGER PRIMARY KEY for SchemaId (I6).
  3. serdes-store::txn — wraps insert + index-update in one transaction (I9); anchors to Petrov's Database Internals storage-structures chapter (§5) for the WAL/checkpoint model.
  4. Add optimistic locking on version increment: a CHECK constraint plus a retry-on-conflict loop guards against two concurrent registrations both trying to claim "next version" for the same subject.
  5. Add the schema-fingerprint index used by §15's dedup path: a lookup by fingerprint must return the existing SchemaId instead of inserting a duplicate row.
  6. Add the subject/version index enabling list_versions/list_subjects (§11) without a full table scan — anchors to Chang et al.'s Bigtable sorted-storage model (§5).
  7. serdes-store::migrations — a versioned migration system with a checksum recorded per applied migration, checked on boot (I9-adjacent: refuses to serve on migration-checksum mismatch).
  8. serdes-store::memory — an in-memory SchemaStore implementation backed by a RwLock<HashMap> used by tests and by ephemeral CI environments; must allocate SchemaIds with the same monotonic guarantee (I6) as the SQLite backend.
  9. Add integration tests that run the same test suite against both backends via a generic fn run_store_suite<S: SchemaStore>(store: S) helper, directly enforcing P8.

18.3 Deliverable

A SchemaStore implementation (SQLite or in-memory) that durably persists registered schemas with monotonic IDs, atomic writes, and consistent reads, swappable behind the trait with zero changes to any caller.

18.4 Acceptance Criteria

  • sqlite_insert.rs (§18.5): 1,000 sequential registrations produce 1,000 strictly increasing SchemaIds with zero gaps.
  • sqlite_txn.rs: a simulated kill -9 mid-write (via the deterministic simulator, §7) followed by restart shows either the full write committed or none of it — never a partial row.
  • memory_store.rs: the in-memory backend passes the identical suite as the SQLite backend, asserted by running both through run_store_suite.
  • SQLite insert transaction commit p99 < 8 ms (M12, §28).

18.6 Pitfalls

  • Race conditions on concurrent version-increment — manifestation: two clients registering to the same subject simultaneously both get "version 3"; root cause: read-then-write without a transaction wrapping both; debugging: a concurrency stress test with 50 parallel registrations; signal: duplicate version numbers in list_versions; recovery: 18.2 step 4's optimistic-lock retry loop.
  • Duplicate SchemaIds across a crash/restart boundary — manifestation: the sequence counter resets; root cause: using an in-memory counter instead of the SQLite INTEGER PRIMARY KEY auto-increment as the source of truth; debugging: restart-and-register replay test; signal: I6's gap-scan actually finds a duplicate, not a gap — a distinct failure mode worth its own check; recovery: never maintain the counter outside the durable table.
  • Migration drift between a manually-patched database and the checked-in migration history — manifestation: boot fails with a checksum mismatch; root cause: an operator ran a manual ALTER TABLE outside the migration system; debugging: migrations.rs's version log (§18.10); signal: FM-8 (§23); recovery: an operator-run migration-repair script, never a silent skip.

18.7 Performance Concerns

DB write-lock contention under WAL mode is the dominant bottleneck (§29) — a single writer connection serializes all registrations, which is why §4's 512-concurrency budget applies to reads (served from the fingerprint LRU or read-only connections) far more than writes. Large subject-list scans are avoided by the subject index (18.2 step 6) rather than a SELECT DISTINCT over the full schema table.

18.8 Edge Cases

A corrupted database file (detected via SQLite's PRAGMA integrity_check on boot) must refuse to serve rather than silently operating on partial data. Partial writes from a killed process must be fully rolled back by WAL replay (18.4). Duplicate registration of byte-identical schema content to the same subject must return the existing SchemaId, not create a new version (I5's dedup guarantee applied at the storage layer).

18.9 Failure Analysis

Storage-layer bugs risk data loss or data corruption, the two failure classes this system can least tolerate, because a registry with corrupted history poisons every future compatibility check (§17) against a bad baseline. Detection: PRAGMA integrity_check on every boot plus the kill-mid-write simulator test (18.4). Blast radius: contained to the affected subject's version history unless the corruption is file-level, in which case it's the whole registry — the reason RTO/RPO budgets exist in §4. Containment: WAL mode means a crash loses at most the RPO window (5 min) of unfulfilled writes, never committed ones. Recovery: restore from the nightly backup (RTO ≤ 15 min) and replay WAL, per the runbook in docs/runbooks/incident-response.md.

18.10 Operational Notes

Metrics: store_txn_rollback_total, schema_id_gap_detected_total, store_lock_timeout_total. Tracing span: store.insert_schema with fields subject, fingerprint. Structured-log fields: schema_id, version on every successful insert. Deployment: SQLite file on a durable volume, mounted read-write into exactly one active serdes-registry process (single-writer, ADR-04). Rollback: restore prior SQLite file from backup. Migration: migrations.rs version log is the audit trail; PhaseDeferred("§18") — distributed registry clustering and Raft replication are deferred until write throughput exceeds the single-node ceiling (C8, §32); see the Deferred Features Register.

19. Phase 7 — Schema Registry HTTP API

19.1 Objectives

Implement serdes-registry: an axum-based (ADR-06) Confluent-compatible REST API over SchemaStore (§18) and CompatibilityChecker (§17) — subject/version lifecycle, compatibility- mode config with inheritance (I13), health checks, and observability (P11). Constraint introduced: no handler blocks the tokio reactor for more than 1 ms without an .await (I10); the registry sheds load via a bounded concurrency limiter before ever buffering unboundedly (P13).

19.2 Detailed Implementation Steps

  1. serdes-registry::routes — axum router wiring POST /subjects/{subject}/versions, GET /subjects/{subject}/versions/{version}, GET /schemas/ids/{id}, GET /subjects, PUT /config/{subject}, POST /compatibility/subjects/{subject}/versions/{version}.
  2. serdes-registry::subjects — subject lifecycle: registration, listing, soft-delete (Confluent-compatible semantics: a deleted subject's versions are recoverable, not purged).
  3. serdes-registry::versions — version listing and lookup, calling SchemaStore::list_versions (§18) and CompatibilityChecker::check (§17) in sequence on every POST.
  4. serdes-registry::config — compatibility-mode config storage with subject→global inheritance (I13): a subject with no explicit override reads the global default at request time, not at config-write time (so a global-default change retroactively affects un-overridden subjects, by design).
  5. serdes-registry::http — request/response JSON (de)serialization matching Confluent's exact field names and status codes (RFC 7231 §6, §5) — 409 for a compatibility rejection, 422 for a malformed schema, 404 for an unknown subject/version.
  6. serdes-registry::middleware — tracing middleware (span per request, ADR-09/10), the tower::limit::ConcurrencyLimit layer (ADR-21, P13), and a request-size limit against the oversized-payload threat (T1, §22).
  7. serdes-registry::metrics — Prometheus exporter (ADR-11) exposing http_requests_total, http_request_duration_seconds, and every counter named in each phase's Operational Notes.
  8. Add GET /health asserting an open SQLite connection and a non-lagging metrics exporter — the same endpoint Phase 0's docker_boot.rs fixture exercises (§12.5), now with real checks.
  9. Add graceful shutdown: on SIGTERM, drain in-flight requests up to the §4 5 s grace budget, then flush the SQLite WAL checkpoint before exit.
  10. Add OpenAPI generation (docs/api/openapi.yaml) from the route definitions, and structured 409 error bodies carrying the CompatibilityViolation list (§17.2 step 9) verbatim.

19.3 Deliverable

A running serdes-registry HTTP server implementing the Confluent Schema Registry REST contract, backed by either storage backend, observable via Prometheus and OTLP tracing.

19.4 Acceptance Criteria

  • register.http (§19.5): a valid schema registration returns 200 with a SchemaId in < 10 ms p99 (M6, §28).
  • compat.http: a breaking-change registration returns 409 with a violation list naming the exact field, never a bare boolean.
  • list_subjects.http: subject enumeration returns all registered subjects, including soft- deleted ones only when a ?deleted=true query parameter is present (Confluent parity).
  • Load test at 512 concurrent in-flight requests (§4) shows zero unbounded-queue memory growth and a clean 503 shed rate once the concurrency limit is hit.

19.6 Pitfalls

  • Incorrect HTTP status-code semantics — manifestation: a compatibility rejection returns 400 instead of 409, breaking Confluent-client retry logic keyed on status code; root cause: a generic error-mapping layer collapsing distinct error kinds; debugging: differential fixture against Confluent's documented codes; signal: a client retries a request that will never succeed; recovery: map each SerdesError variant to its exact Confluent-parity status, 1:1.
  • Non-idempotent retries on POST /subjects/.../versions — manifestation: a client retry after a timeout creates two versions for one logical registration; root cause: fingerprint-dedup (I5) only covers byte-identical schemas, not a client-side reformat before retry; debugging: fixture simulating a slow-then-retried request; signal: unexpected duplicate versions; recovery: document dedup's exact scope; a real idempotency-key design is out of scope for Phase 0–9.
  • Malformed JSON handling that panics instead of returning 422 — manifestation: a crafted request body crashes the handler; root cause: serde_json deserialization error not mapped to a Result path before axum's extractor runs; debugging: fuzz the registration endpoint body (§21.2's registry_api.rs target); signal: I8 violation, decoder_panics_total nonzero; recovery: explicit extractor error handling, never .unwrap() on request-body parsing.

19.7 Performance Concerns

DB contention under write-heavy load is the registry's dominant tail-latency source (§18.7) — mitigated at the HTTP layer by the concurrency limiter (P13) shedding load before it queues against an already-contended SQLite writer. Serialization overhead for large schemas (multi-KB .avsc payloads) is bounded by the request-size limit (19.2 step 6), avoiding a full-body buffer.

19.8 Edge Cases

Duplicate concurrent writes to the same subject must resolve deterministically via 18.6's optimistic-lock retry, visible at the HTTP layer as one 200 and one either-200-with-same-ID- or-retried-success, never a lost write. Invalid schema IDs in GET /schemas/ids/{id} return 404, not a 500. Requests against a soft-deleted subject return 404 unless ?deleted=true is present, matching Confluent's exact recoverability semantics.

19.9 Failure Analysis

The registry HTTP layer is the system's only network-facing, multi-tenant-adjacent attack surface (§22) and its only classically availability-critical component (a codec bug affects correctness; a registry outage stops every producer from registering or validating at all). Detection: http_requests_rejected_total and p99 latency dashboards (§28) plus health-check failures. Blast radius: all subjects, all clients, for the outage's duration. Containment: the concurrency limiter (P13) and request-size cap bound worst-case per-request resource use. Recovery: restart via the process supervisor, or the §18.9 storage path if SQLite-file-level; runbook in docs/runbooks/incident-response.md.

19.10 Operational Notes

Metrics: http_requests_total{method,path,status}, http_request_duration_seconds, http_requests_rejected_total, compat_reject_reason_total, config_override_total. Tracing span: http.request per inbound request, child spans compat.check and store.insert_schema nested beneath it (P11). Structured-log fields: request_id, subject, schema_fingerprint, status. Deployment: stateless binary behind a load balancer, N replicas sharing one SQLite file (single-writer, ADR-04) or a future distributed backend. Rollback: standard blue/green replica swap, no schema migration needed for a code-only rollback. Migration: config-schema changes (new compatibility modes) follow §25. PhaseDeferred("§19") — gRPC integration, Kafka serializer/ deserializer plugins, multi-tenant auth, and the ACL engine are deferred; see §35.

20. Phase 8 — CLI & Tooling

20.1 Objectives

Implement serdes-cli (clap, ADR-04's CLI counterpart is ADR referenced elsewhere; CLI itself locked by the clap ADR): compile, encode, decode, validate, and serve subcommands wrapping the library crates for operator and developer ergonomics. Constraint introduced: the CLI must never corrupt binary stdout with diagnostic text (T9-adjacent), and every subcommand exits with a distinct, documented exit code.

20.2 Detailed Implementation Steps

  1. serdes-cli::compile — wraps serdes-proto-parse/serdes-avro-schema (§13/§15); prints diagnostics to stderr, exits nonzero on any parse error, matching P6's no-panic guarantee at the process-exit level (a panic would produce an unhelpful backtrace instead of a diagnostic).
  2. serdes-cli::encode / decode — wrap the codecs (§14/§16); binary output goes to stdout only when explicitly requested (--out -), otherwise to a named file, avoiding the T9 stdin/stdout binary-corruption pitfall from mixing log lines with binary bytes on the same stream.
  3. serdes-cli::validate — wraps serdes-compat (§17) for offline compatibility checks against two local schema files, without needing a running registry.
  4. serdes-cli::serve — starts serdes-registry (§19) in-process; wires init_tracing() from Phase 0 (§12.2 step 10) before binding the HTTP listener.
  5. Add JSON output mode (--format json) for every subcommand, making the CLI scriptable in CI pipelines without regex-scraping human-readable output.
  6. Add shell completions (bash/zsh/fish) generated from the clap command definitions.
  7. Add colored diagnostics (respecting NO_COLOR/non-TTY detection) reusing the same ParseError/AvroSchemaError types from §13/§15 rather than a separate CLI-only error format.
  8. Add interactive --help text for every subcommand generated from clap's derive macros, kept in sync with behavior automatically rather than hand-written and drifting.
  9. Wire distinct exit codes: 0 success, 1 parse/validation error, 2 I/O error, 3 incompatible-schema (validate subcommand only) — documented in README.md and asserted by the snapshot fixtures in 20.5.

20.3 Deliverable

A single serdes-cli binary exposing compile/encode/decode/validate/serve, usable both interactively and in CI pipelines via JSON output mode and documented exit codes.

20.4 Acceptance Criteria

  • serdes-cli serve refuses to start without a bound metrics endpoint (P11), exiting with code 2 and a diagnostic naming the missing --metrics-addr flag.
  • compile.snap (§20.5): compiling basic.proto produces byte-identical JSON-mode output across three consecutive runs (P3's determinism, exercised at the CLI boundary).
  • CLI cold-start latency < 300 ms (M10, §28), measured from process exec to first stdout byte for serdes-cli --version.
  • encode.snap: encoding a fixture through the CLI produces output byte-identical to calling the library function directly — the CLI adds zero encoding-affecting behavior.

20.6 Pitfalls

  • Inconsistent exit codes across subcommands — manifestation: a CI pipeline's error handling works for compile but not validate; root cause: exit codes chosen ad hoc per subcommand instead of from the shared table (20.2 step 9); debugging: a snapshot test asserting every subcommand's exit code for its error fixture; signal: CI scripts silently treat a real failure as success; recovery: centralize exit-code mapping in one function, tested once.

  • Binary/stdout corruption — manifestation: decode --out - output is unreadable because a log line was interleaved into stdout; root cause: tracing's default subscriber writes to stdout instead of stderr; debugging: encode.snap's byte-equality check catches this immediately; signal: downstream pipe (serdes-cli decode --out - | some-consumer) fails to parse; recovery: configure the tracing subscriber to stderr always, reserving stdout for command output only.

20.7 Performance Concerns

Startup latency (M10, §28) is dominated by tokio runtime initialization even for subcommands that don't need async (compile/encode/decode are synchronous) — mitigated by only initializing the async runtime lazily, inside serve, not at the top of main() unconditionally. Large-file handling for compile/encode streams from disk rather than reading the whole file into memory where the codec's zero-copy design (P4) permits.

20.8 Edge Cases

Stdin streaming (serdes-cli decode --in -) must handle a slow or chunked stdin without buffering unboundedly (P13's backpressure principle applied to a CLI context, not just the registry). Invalid UTF-8 in command-line arguments (e.g. a malformed filename) must be handled by clap's OsString argument type, not force an early UTF-8 panic. Broken pipes (downstream consumer exits early) must be handled as a normal SIGPIPE/EPIPE exit, not an unhandled panic (I8 applies at the CLI boundary too).

20.9 Failure Analysis

CLI bugs are lower-blast-radius than registry or codec bugs (single invocation, single operator) but disproportionately erode trust if they corrupt output silently, since the CLI is often used to generate fixtures that other phases then trust as ground truth (P14's fixture-driven-regression principle depends on the CLI not lying). Detection: encode.snap's direct-library-comparison fixture is the load-bearing check here — it would catch any CLI-introduced divergence immediately. Blast radius: whichever pipeline invoked the buggy subcommand. Recovery: patch, add a fixture, treat any output-corrupting bug as P1-severity even though it doesn't affect a running service.

20.10 Operational Notes

Metrics: none server-side (a CLI invocation, not a long-running process) except when running serve, which reuses §19.10's metrics wholesale. Tracing: cli.invoke span with fields subcommand, exit_code, written to stderr only per 20.6. Structured-log fields: same as tracing fields, JSON-formatted when --format json is set. Deployment: distributed as a cargo-dist prebuilt binary per target (ADR-15). Rollback: pin the previous binary version; CLI has no persistent state to migrate. Compatibility implications: PhaseDeferred("§20") — schema diff visualizer, TypeScript codegen, and Java codegen subcommands are deferred; see §35.

21. Phase 9 — Conformance, Fuzzing & Interop

21.1 Objectives

Prove the interoperability claims every prior phase made (P10) with automated differential testing against protoc and Java Avro, and harden every parser/decoder against adversarial input via continuous fuzzing (P6, I8). This phase has no new library code of its own — it is entirely verification infrastructure over Phases 1–7.

21.2 Detailed Implementation Steps

  1. fuzz/fuzz_targets/proto_parser.rs — cargo-fuzz (ADR-13) target feeding arbitrary bytes into serdes-proto-parse::compile, asserting no panic (I8) regardless of input.
  2. fuzz/fuzz_targets/proto_decoder.rs — fuzzes serdes-proto-codec::decoder against arbitrary bytes interpreted as wire-format messages, the primary defense against T2/T7 (§22).
  3. fuzz/fuzz_targets/avro_decoder.rs — fuzzes serdes-avro-codec::decoder paired with randomly mutated schemas, catching resolution ambiguities (16.9) that unit fixtures alone would miss.
  4. fuzz/fuzz_targets/registry_api.rs — fuzzes the HTTP request-body extractors (19.6's malformed-JSON pitfall) end-to-end through axum's routing layer.
  5. Add protoc differential validation: every fixtures/proto/*.bin fixture is also decoded by protoc --decode in CI and diffed field-by-field against this project's decoder output (P10, protocolbuffers/protobuf reference, §5).
  6. Add Java Avro differential validation: fixtures/avro/*.bin fixtures are cross-checked against a Java Avro decode via a small JVM harness invoked from CI (apache/avro reference, §5).
  7. Add a mutation corpus: seed the fuzzers with every fixture from §13.5/§14.5/§15.5/§16.5, then let cargo-fuzz's coverage-guided mutation explore from those seeds rather than starting from nothing.
  8. Add randomized schema generation: a proptest-style generator producing structurally valid but randomly shaped proto/Avro schemas, used to fuzz the compatibility engine (§17) with schema pairs rather than just single malformed messages.
  9. Add snapshot tests (insta, ADR-25) over the differential-testing harness's own output, so a regression in the harness itself (not just the code under test) is caught.
  10. Add a nightly CI job running the fuzz targets for a fixed corpus-growth budget (C6, §32), triaging any new crash into a permanent fixture (P14) before the next release.

21.3 Deliverable

A CI-integrated conformance and fuzzing suite proving byte-exact interoperability with protoc and Java Avro, plus a continuously-run fuzz corpus with zero known crashes at release time.

21.4 Acceptance Criteria

  • diff_protoc (§21.5): 100% field-by-field agreement across all fixtures/proto/*.bin fixtures, zero tolerated mismatches.
  • fuzz_varint: 20,000+ executions/sec sustained (M11, §28) with zero crashes over an 8-hour nightly run.
  • random_schema: 10,000 randomly generated compatible schema-evolution pairs all agree between the compatibility engine's verdict and the codec's actual resolution behavior (closing the 16.9/17.9 gap between abstract rule and operational reality).
  • Every crash found by fuzzing in the last 90 days has a corresponding checked-in fixture (P14), verified by a CI script that greps fuzz/artifacts/ history against the fixture manifest.

21.6 Pitfalls

  • Nondeterministic snapshots — manifestation: insta snapshot fixtures flake in CI but pass locally; root cause: HashMap iteration order leaking into snapshot output somewhere upstream of this phase (a P3 violation surfacing here first); debugging: run the snapshot 100× locally with varying RUSTFLAGS hash-seed settings; signal: intermittent CI red with no code change; recovery: trace back to the non-canonical serialization and fix at the source (usually §15's canonicalizer), not by relaxing the snapshot check.
  • Flaky fuzz minimization — manifestation: cargo-fuzz's crash minimizer produces a different minimal repro on each run; root cause: the target itself has nondeterministic behavior (e.g. reading wall-clock time); debugging: re-run minimization with a fixed seed; signal: the same underlying bug files as two different "distinct" fixtures; recovery: eliminate all nondeterminism from fuzz targets, per ADR-20's monotonic-clock discipline.
  • Platform-dependent ordering — manifestation: diff_protoc passes on Linux CI but fails on a contributor's macOS machine; root cause: a HashMap-ordering or float-formatting difference across platforms; debugging: reproduce with the exact same rustc/OS pairing as the failure; signal: "works in CI, fails locally" bug reports; recovery: pin canonical serialization to not depend on platform-specific float formatting or hash-map iteration.

21.7 Performance Concerns

Fuzz execution speed (M11, §28) directly determines corpus coverage per nightly run (C6, §32) — mitigated by keeping fuzz targets allocation-light (reusing P4's zero-copy decode path directly, not a fuzz-only wrapper that adds overhead) so the fuzzer's own instrumentation dominates, not the code under test. Corpus growth is bounded by deduplication (cargo-fuzz's built-in corpus minimization) rather than an unbounded artifact directory.

21.8 Edge Cases

"Billion laughs"-style schema expansion (a schema whose canonical form is exponentially larger than its source text, via nested self-referential aliases) must be rejected by the same recursion/size bounds as §15's cycle-safety, not newly re-invented here. Recursive nesting bombs targeting the codec (§14.6/§16.8) are exercised specifically by the fuzz corpus, not just the hand-written fixtures, since fuzzing finds depth/width combinations a human wouldn't think to write. Oversized payloads (multi-GB crafted messages) are rejected by the request-size limit (19.2 step 6) before ever reaching the decoder, verified by a fuzz target specifically targeting the size-limit boundary itself.

21.9 Failure Analysis

This phase's entire purpose is catching failure classes the other phases' hand-written fixtures miss — its own failure mode is therefore silence: a fuzz target that never finds anything wrong might mean the code is correct, or might mean the target has a coverage gap. Detection: track fuzz-target code coverage (via cargo-fuzz coverage) as a leading indicator, not just crash count. Blast radius: a fuzz-found bug that reaches production before this phase catches it has whatever blast radius its own phase's failure-analysis section already describes (14.9/16.9/17.9/ 19.9). Recovery: any fuzz crash becomes a P14 fixture before the triggering code merges to the default branch, never deferred to "someday."

21.10 Operational Notes

Metrics: fuzz_execs_per_second, fuzz_crashes_total, diff_protoc_mismatches_total (should read zero). Tracing: none (offline CI infrastructure, not a running service). Structured-log fields: fuzz-run summary logged as one structured line per nightly job (corpus_size, new_coverage_edges, crash_count). Deployment: runs entirely in CI (.github/workflows/fuzz.yml, benchmarks.yml); no production deployment. Migration: n/a. Compatibility implications: a diff_protoc/Java-Avro mismatch discovered here that requires a codec behavior change follows the same wire-compatibility process as any other codec change (§25) — interop fixes are still breaking changes if they alter byte output for previously "working" inputs.

24. Operational Readiness

Launch checklist. SQLite file on a durable, backed-up volume with WAL mode enabled; Prometheus scrape target configured; OTLP collector endpoint reachable; deny.toml advisory scan green; health check (§19.2 step 8) verified against a cold-started container; runbook (docs/runbooks/incident-response.md) reviewed by on-call.

On-call signals. Page on: decoder_panics_total > 0 (I8 violation, P0), health-check failing for > 30 s, store_txn_rollback_total rate spike, p99 latency exceeding 2× the §4 budget for 5 consecutive minutes. Ticket (non-page) on: compat_reject_reason_total rate change (may indicate a producer rollout issue, not a registry bug), fingerprint_collisions_total > 0 (investigate before it becomes a dedup problem).

Capacity review cadence. Monthly review of C1–C12 (§32) against actual production RSS, subject count, and SQLite file size, updating §4's budgets if the deployment has genuinely grown past the original assumptions rather than silently drifting out of budget.

Runbooks. docs/runbooks/incident-response.md covers: registry unresponsive (restart via supervisor, check SQLite lock state), suspected data corruption (run PRAGMA integrity_check, follow FM-1's recovery path), and fuzz-found crash triage (FM-7's path, converting the crash into a P14 fixture before the next deploy).

Backup and restore drill. RTO/RPO (§4) are validated quarterly by actually restoring a backup into a scratch environment and replaying WAL, not merely assumed from the backup schedule.

25. Compatibility & Versioning

Wire compatibility. Any change to serdes-proto-codec/serdes-avro-codec byte layout is a breaking wire change (P3, P10) and requires: (a) a new fixture proving the old behavior no longer holds, (b) a major version bump per SemVer (ADR-18), (c) a migration note in CHANGELOG.md.

Schema compatibility. Governed entirely by serdes-compat (§17); a rule change (e.g. tightening enum-narrowing) is versioned independently of the crate's SemVer, since it changes registry behavior, not library behavior — tracked via a compat_ruleset_version field returned in the registry's /config response so clients can detect a ruleset change.

API compatibility. The registry's REST contract (§19) follows Confluent's own versioning precedent: additive fields are non-breaking; removing or renaming a response field is breaking and requires a new API version path segment (/v2/subjects/...), not an in-place change.

Storage compatibility. serdes-store's migrations.rs (§18) is the sole mechanism for schema- table changes; a migration must be backward-compatible with the immediately preceding binary version to support zero-downtime rolling deploys — the new binary must be able to read data written by the old one for the duration of a rollout.

Deprecation policy. A deprecated API field or CLI flag is documented in CHANGELOG.md, retained for at least one minor version cycle (ADR-18), and removed only in a major version with an explicit migration note.

26. Testing & Verification Strategy

Layered strategy. Unit tests per module (codec primitives, parser productions, compat rules) → integration tests per crate (the run_store_suite generic harness, §18.2 step 9) → conformance fixtures per phase (§12.5–§21.5) → differential tests against protoc/Java Avro (§21) → continuous fuzzing (§21) → the deterministic simulator (§7) for invariant-violation reproduction.

Snapshot testing. insta (ADR-25) covers AST/descriptor output (§13), canonical-form output (§15), and CLI JSON-mode output (§20) — anywhere a structural comparison is more maintainable than a hand-written assertion, subject to P3's determinism requirement holding first.

Property-based testing. proptest-style random schema generation (§21.2 step 8) exercises the compatibility engine (§17) with structurally valid but unpredictable schema-evolution pairs, catching combinations no fixture author would think to write by hand.

Regression discipline. Every fuzz crash and every production incident becomes a permanent, named fixture before the fix merges (P14) — enforced by a CI script checking the PR diff against fuzz/artifacts/ history.

Coverage targets. Line coverage is tracked but not gated (a vanity metric on its own); branch coverage of error paths specifically (every Result::Err arm) is gated at 100% for serdes-proto-codec and serdes-avro-codec, the two crates where I8's no-panic guarantee is most load-bearing.

27. Build & Release Engineering

Build. cargo build --workspace via Cargo (ADR-02) with sccache in CI; cargo-deny (ADR-17) gates every dependency addition; rust-toolchain.toml pins the compiler version workspace-wide, eliminating the toolchain-drift pitfall from §12.6.

CI pipeline. .github/workflows/ci.yml (ADR-14) runs build, cargo-nextest (ADR-12), and clippy/fmt checks on every PR; fuzz.yml and benchmarks.yml run nightly, non-blocking for merge but blocking for release (a release cannot ship with an open fuzz crash or a performance regression past the §28 targets).

Packaging. cargo-dist (ADR-15) produces prebuilt binaries per target platform; the serdes-registry container image is built multi-stage onto a distroless base (ADR-16), minimizing attack surface (§22) by excluding a shell and package manager from the runtime image.

Release process. SemVer + conventional commits + cargo-release (ADR-18): a release is cut from a green main, tagged, and the changelog is generated from commit history, not hand-written after the fact.

Reproducibility. Cargo.lock is checked in and never .gitignored (ADR-19); CI verifies a release build is bit-identical across two independent build machines before publishing, catching any accidental non-determinism in the build process itself (distinct from P3's runtime-encoding determinism, but built on the same philosophy).

Rollback. A bad release is rolled back by redeploying the previous container tag; because storage migrations (§18/§25) are designed backward-compatible for one version, a rollback never requires a storage rollback in the common case.

29. Scalability Analysis

Bottlenecks. SQLite write-lock serialization (§18.7) is the hard ceiling on registration throughput; compatibility-graph traversal (§17.7) scales with subject history length; schema canonicalization (§15.7) scales with schema size, not message volume; recursive decoding (§14.7/§16.7) scales with nesting depth, bounded by I14's shared depth cap.

Horizontal scaling. serdes-registry replicas are stateless (P8) — any replica can serve any request given a shared storage backend. Read-heavy load scales linearly with replica count via each replica's own fingerprint LRU cache (§4); write throughput does not scale with replica count under the single-writer SQLite backend (ADR-04) and requires the deferred distributed backend (PhaseDeferred("§18")) to scale writes horizontally.

Vertical scaling. Registry memory is dominated by the schema cache, decode buffers, and parser allocations (C1, §32) — vertical scaling (more RAM per replica) primarily buys a larger fingerprint cache, not more write throughput, since the SQLite writer is CPU/IO-bound on WAL fsync, not memory-bound.

Scaling assumption reused from §4. The 512-MB RSS and 512-concurrency budgets assume a single- region, single-writer deployment; a multi-region or multi-writer deployment (either alternative in §34) requires re-deriving §4's numbers from scratch, not scaling them linearly.

30. Mental Models & First Principles

  • MM1 — Wire bytes are a contract, not an implementation detail. Compressed insight: every byte layout choice is a promise to every future consumer, forever, once the first message ships. Predicts: why P3 (determinism) and P10 (interop-first) are non-negotiable. Bug class avoided: "quick fix" encoding changes that silently break every existing consumer. Applies in §14/§16.
  • MM2 — Schema evolution is a partial order, not a timeline. Compressed insight: two schema versions can each be individually compatible with the latest without being compatible with each other. Predicts: why *_TRANSITIVE modes (I7) must check all pairs, not just chronological neighbors. Bug class avoided: a transitive-compatibility engine that only walks a linked list of "previous version." Applies in §17.
  • MM3 — Absence of an error is not proof of correctness. Compressed insight: a decoder that never panics on malformed input might be silently producing wrong values instead of failing loudly. Predicts: why differential testing (P10) is required alongside fuzzing (I8), not instead of it. Bug class avoided: shipping a "robust" decoder that's robustly wrong. Applies in §21.
  • MM4 — Canonicalization is the only place equivalence can be decided. Compressed insight: without a single normalized form, "are these two schemas the same" has no stable answer. Predicts: why P9 gates I5 — a fingerprint computed before canonicalization is fully deterministic is worthless. Bug class avoided: dedup logic that works by accident on today's test inputs. Applies in §15.
  • MM5 — Backpressure must be applied before the point of no return. Compressed insight: once a request is queued, the resource commitment (memory, a DB connection) is already made; shedding after that point wastes the resource anyway. Predicts: why P13 rejects at the concurrency-limiter layer, not inside the handler after work has started. Bug class avoided: an "overload protection" layer that itself becomes the OOM source. Applies in §19.
  • MM6 — A trait boundary is a promise about what varies, not just an abstraction. Compressed insight: SchemaStore (§11) exists specifically to make the storage backend swappable — if any caller ever imports rusqlite directly, the boundary has already failed. Predicts: why P8 is enforced by an integration-test suite run against every implementation, not by convention. Bug class avoided: a "pluggable" architecture that's pluggable in name only. Applies in §18.
  • MM7 — Monotonicity is easier to prove than to patch on afterward. Compressed insight: I6's SchemaId monotonicity is trivial if the counter is the database's own primary key, and a significant redesign if bolted on after the fact with a separate counter. Predicts: why 18.6's "duplicate ID after crash" pitfall exists specifically for designs that separate the counter from the durable write. Applies in §18.
  • MM8 — Fixtures encode institutional memory; fuzzers discover it. Compressed insight: a fuzz corpus without fixture promotion (P14) forgets every bug the moment CI clears the crash directory. Predicts: why 21.4's acceptance criteria explicitly check "every 90-day-old crash has a fixture," not just "current fuzz run is clean." Applies in §21.

32. Back-of-Envelope Capacity Model

  • C1 — Registry RSS. Schema cache 10,000 × 2 KB = 20 MB + SQLite pool 16 × 2 MB = 32 MB + HTTP buffers 512 × 64 KB = 32 MB → 84 MB total, inside the 512 MB §4 ceiling.
  • C2 — Proto encode CPU budget. 150 ns (§4, M1) × 5,000 req/s peak = 0.75 ms CPU/s ≈ 0.075% of one core.
  • C3 — FD budget. 16 SQLite conns + 512 max-concurrency keep-alives + 32 misc = 560, inside the 1,024 §4 FD ceiling.
  • C4 — Storage amplification. 1 schema avg 2 KB raw × 1.3 amplification (§4) = 2.6 KB on disk per stored version.
  • C5 — WAL checkpoint exposure. RPO 5 min (§4) ÷ avg write rate 10 writes/min = 50 writes at risk inside one checkpoint gap.
  • C6 — Fuzz corpus growth. 20,000 exec/s (M11) × 8 h nightly run = 576,000,000 execs/night; corpus dedup keeps unique retained inputs under 50,000.
  • C7 — Transitive compat-check cost. 50 versions × 0.5 ms per pairwise check = 25 ms (half of M8's 1 ms p99 margin, matching M9's target exactly).
  • C8 — Registration throughput ceiling. p99 POST 10 ms (§4/M6) → 100 req/s per connection × 16 conns = 1,600 req/s before queueing begins.
  • C9 — Cache hit savings. Cached GET p99 2 ms vs. uncached SQLite read ≈ 8 ms (M12 analog) = 4× latency reduction from the fingerprint LRU.
  • C10 — Availability-to-incident budget. 99.9% monthly (§4) = 43.8 min downtime budget ÷ 15 min average incident MTTR (RTO, §4) = 2.9 allowed incidents/month before SLA breach.
  • C11 — Startup budget breakdown. 300 ms (§4) = SQLite open+migration-check 120 ms + tokio init 40 ms + axum router build 30 ms + tracing init 20 ms = 210 ms, leaving a 90 ms margin.
  • C12 — Max-concurrency memory. 512 concurrency (§4) × 64 KB per-request buffer = 32 MB, already counted inside C1's HTTP-buffer line.

34. Alternative Architectures (Roads Not Taken)

Alt A — Schemaless Self-Describing Envelopes

┌───────────────────────────────┐
│ Message                       │
│ [type-tag][len][value] ...    │  each field carries its own type inline
│ no external schema needed     │
└───────────────────────────────┘

Regime where it wins: zero schema-registry operational burden, trusted internal-only consumers, rapid prototyping where governance is a later concern. Real system that embodies it: MongoDB's BSON wire protocol. Rejected here because it forfeits deterministic fingerprinting (I5) and the compact wire size (§4's latency/size budgets) that a fixed, externally-agreed schema provides — and it offers no mechanism at all for the compatibility governance this project's Phase 5 (§17) exists to provide.

Alt B — Schema-in-Payload Container Files

┌──────────────┬───────────────────────────────┐
│ OCF Header   │ Data Blocks                   │
│ (schema JSON,│ [block: count|codec|records]  │
│  sync marker)│  repeated...                  │
└──────────────┴───────────────────────────────┘

Regime where it wins: batch/offline pipelines where producer and consumer are decoupled in time by months, and self-description matters more than per-message overhead. Real system that embodies it: Apache Avro's own Object Container File format (and, in spirit, Cap'n Proto's framed messages). Rejected as this project's primary path because it duplicates schema bytes across millions of small streaming messages, violating §4's storage-amplification budget, when this project's primary consumer is a low-latency streaming path, not batch files — deferred as Avro OCF support, PhaseDeferred("§16"), not abandoned.

Alt C — Raft-Replicated Distributed Registry

┌────────┐   Raft log replication   ┌────────┐
│ Node A │◄─────────────────────────►│ Node B │
│(leader)│                           │(follower)│
└───┬────┘                           └────────┘
    │            ┌────────┐
    └───────────►│ Node C │
                 │(follower)│
                 └────────┘

Regime where it wins: 5+ concurrent writer replicas needing linearizable multi-region writes. Real system that embodies it: etcd (and CockroachDB's metadata layer, built on the same Raft model). Rejected for Phases 0–9 because it triples operational complexity (consensus, leader election, snapshotting) against a single-writer workload profile — §4's availability/RTO numbers assume single-node SQLite — deferred as distributed registry clustering and Raft replication, PhaseDeferred("§18"), pending write-throughput growth past C8's ceiling (§32).

36. Glossary

  • Varint — variable-length base-128 integer encoding used by both the protobuf tag and Avro int/long wire representations.
  • ZigZag — signed-to-unsigned integer mapping used for sint32/sint64 so small negatives stay short.
  • Wire Type — the 3-bit protobuf field category (Varint, 64-bit, Length-delimited, 32-bit).
  • Wire Tag — (field_number << 3) | wire_type, the leading varint of every protobuf field.
  • Schema Evolution — the practice of changing a schema over time while preserving readability of historical data.
  • Compatibility — the ability of a schema to read data written under a different schema version.
  • Subject — a registry namespace under which schema versions are registered sequentially.
  • Fingerprint — a deterministic hash of a schema's canonical form, used for identity and dedup.
  • Schema IR — the unified SchemaKind intermediate representation both proto and Avro compile into.
  • Packed Field — protobuf's compact repeated-scalar encoding (one length-delimited run, not one tag per element).
  • Union — an Avro field that may hold a value of one of several declared types.
  • Canonical Form — the normalized, alias-stripped, fully-qualified representation of a schema.
  • Reader Schema — the schema a consumer uses to decode data.
  • Writer Schema — the schema a producer used to encode data.
  • Descriptor — the lowered, typed representation of a compiled .proto file.
  • OCF — Avro Object Container File, a self-describing batch file format (deferred, §35).
  • SchemaId — the registry-assigned monotonic integer identifying a specific registered schema.
  • BACKWARD — a compatibility mode: the new schema can read data written with the old schema.
  • FORWARD — a compatibility mode: the old schema can read data written with the new schema.
  • FULL — a compatibility mode requiring both BACKWARD and FORWARD to hold.
  • TRANSITIVE — a compatibility-mode suffix requiring the check to hold against every stored historical version, not just the immediately preceding one.
  • Namespace — an Avro naming scope qualifying a type's fully-qualified name.
  • Alias — an alternate name for a field or type, used to match renamed fields during resolution or compatibility checks.
  • Default Value — a schema-declared fallback value used when a field is absent from encoded data.
  • Field Number — the protobuf-assigned integer identifying a field on the wire.
  • Recursive Descent Parser — a parser architecture with one function per grammar production, calling itself for nested constructs.
  • Lexer — the scanner that converts source text into a token stream.
  • Token — a classified, span-tagged lexical unit produced by the lexer.
  • AST — Abstract Syntax Tree, the parser's typed output before descriptor lowering.
  • Span — a byte-offset range into source text, attached to tokens and AST nodes for diagnostics.
  • WAL — Write-Ahead Log, SQLite's durability mechanism used by serdes-store.
  • Optimistic Locking — a concurrency-control pattern that detects conflicting writes at commit time rather than locking pessimistically up front.
  • Concurrency Limiter — a middleware layer bounding the number of in-flight requests.
  • Backpressure — rejecting or slowing new work before an internal queue grows unboundedly.
  • Load Shedding — deliberately rejecting excess requests to protect overall system health.
  • Differential Testing — comparing this project's output against a trusted reference implementation's output for the same input.
  • Corpus — the set of inputs a fuzzer has discovered to be interesting, used to seed further mutation.
  • Crash Minimization — reducing a fuzz-found crashing input to its smallest reproducing form.
  • Type Promotion — Avro's allowed numeric widening chain (int→long→float→double) during reader/writer resolution.
  • Branch Dispatch — selecting which union branch a value belongs to, based on its encoded index.
  • Block Encoding — Avro's array/map framing: a sequence of (count, items) blocks terminated by a zero-length block.
  • Length-Delimited — a wire value prefixed by its byte length, used for strings, bytes, and embedded messages.
  • Monotonic ID — an identifier guaranteed to strictly increase, never repeat or go backward.
  • Soft Delete — marking a subject deleted while retaining its version history for recovery.
  • Idempotency — the property that repeating an operation has the same effect as performing it once.
  • p99 — the 99th-percentile latency, the value below which 99% of measured requests complete.
  • RTO — Recovery Time Objective, the maximum acceptable time to restore service after a failure.
  • RPO — Recovery Point Objective, the maximum acceptable data-loss window measured in time.
