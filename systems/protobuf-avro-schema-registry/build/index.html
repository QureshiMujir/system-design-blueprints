⬜ Phase 0 — Workspace Bootstrap & Correctness Kernel §12

Objectives

Stand up a buildable Cargo workspace with all ten crates (§10) as empty-but-compiling skeletons, lock toolchain and lint policy, and land the correctness primitives every later phase depends on: serdes-common's error taxonomy, byte-buffer helpers, and ID newtypes (SchemaId, SchemaFingerprint, §11). No parsing or codec logic ships here — this phase is the substrate. Constraints introduced: #![forbid(unsafe_code)] workspace-wide (P6); every crate compiles under --no-default-features to keep no_std embedding viable later; CI must be green before any Phase 1 work lands.

Deliverable

cargo build --workspace and cargo test --workspace both succeed with zero warnings under clippy -D warnings; docker compose up boots an empty serdes-registry binary that answers GET /health with 200 OK; CI is green on a fresh clone.

Acceptance
  • cargo build --workspace completes in ≤ 90 s cold (CI cache miss) per §4's CI budget.
  • All 10 crates listed in §10 exist and compile; cargo tree shows zero cyclic dependencies.
  • docker_boot.rs integration test (§12.5) asserts GET /health returns 200 within 300 ms of container start, matching the §4 cold-start budget.
  • tracing_init.rs asserts at least one structured span is emitted on startup.
Fixtures
Fixture Purpose
fixtures/registry/ci_smoke.json asserts workspace-level health-check contract before any real endpoint exists
fixtures/registry/docker_boot.json asserts container boots and /health responds within budget
Pitfalls
  • Cyclic crate dependencies (e.g. serdes-registry accidentally depending on serdes-cli) — manifestation: cargo build fails with a dependency-cycle error; root cause: a convenience re-export placed in the wrong crate; debugging: cargo tree -d; signal: CI build-stage failure before any test runs; recovery: move the shared type down into serdes-common.
  • Feature-flag leakage across the workspace — manifestation: a crate silently pulls in tokio's full feature set via another crate's default features, bloating binaries; debugging: cargo tree -f "{p} {f}"; signal: binary-size regression in CI; recovery: pin explicit feature lists per dependency.
  • Toolchain drift between contributors — manifestation: "works on my machine" clippy failures; root cause: no rust-toolchain.toml; debugging: compare rustc --version across CI and local; signal: CI green, local red or vice versa; recovery: pin the toolchain file, checked in.
  • Flaky Docker-boot integration test — manifestation: intermittent docker_boot.rs timeout; root cause: container health-check polled before the binary finished linking tracing subscribers; debugging: add a startup span timestamp; signal: nondeterministic CI failures; recovery: poll /health with backoff instead of a fixed sleep.

⬜ Phase 1 — Proto Lexer, Parser & Descriptor Model §13

Objectives

Compile proto3 .proto source text into a validated AST and lower it into ProtoDescriptor (§11). Scope: lexing, recursive-descent parsing (Crafting Interpreters, §5), import resolution, and descriptor construction — no wire encoding yet (that is §14). Constraint introduced: parser must never recurse unboundedly on attacker-controlled input (I14) and must never panic (I8/P6). proto2 extension-group syntax is explicitly out of grammar scope, PhaseDeferred("§13") (see §35).

Deliverable

serdes-proto-parse compiles a .proto source string into a ProtoDescriptor value, exposed as a library function compile(src: &str, importer: &dyn Importer) -> Result<ProtoDescriptor, Vec<ParseError>>, and is callable from serdes-cli compile (stubbed CLI wiring only; full CLI is §20).

Acceptance
  • basic.proto (§13.5) parses into a ProtoDescriptor with exactly the fields declared, field numbers preserved, in ≤ 500 µs for a 50-field message.
  • invalid_field.proto produces ≥ 1 diagnostic per malformed declaration, not just the first.
  • Parser recursion depth is bounded at 128 nested message levels (I14); exceeding it returns ParseError::RecursionLimit, never a stack overflow.
  • imports.proto's import graph resolves to the correct transitive closure, verified against a hand-checked expected file list.
Fixtures
Fixture Assertion
fixtures/proto/basic.proto parses a single message with scalar fields
fixtures/proto/nested.proto nested message types resolve correctly
fixtures/proto/imports.proto import graph resolves to the correct transitive closure
fixtures/proto/invalid_field.proto produces diagnostics for duplicate field numbers
Pitfalls
  • Recursive imports (a.proto imports b.proto imports a.proto) — manifestation: parser hang or stack overflow; root cause: no visited-set in import_resolver; debugging: add cycle-path logging before the fix, reproduce with imports.proto's cyclic variant; signal: CI timeout; recovery: I14's visited-set check, reject with the cycle path in the diagnostic.
  • Span corruption after error recovery — manifestation: a diagnostic points at the wrong source line after a skip-to-; recovery; root cause: recovery logic advances the token cursor without updating the span baseline; debugging: differential test comparing span offsets against a known-good parse; signal: confusing error messages in invalid_field.proto's CI output; recovery: recompute span from the resumed token, not the pre-error token.
  • Keyword-vs-identifier ambiguity (message used as a field name in some grammars) — root cause: proto3 reserves fewer keywords than expected; debugging: differential test against protoc's accepted grammar; signal: a valid .proto file used by a real service rejected; recovery: match protoc's exact reserved-word list (P10, P7).
  • Malformed UTF-8 in string literals or comments — manifestation: lexer panics or produces garbled tokens; root cause: byte-slicing without UTF-8 boundary checks; debugging: fuzz the lexer (§21.2) with arbitrary byte sequences; signal: cargo-fuzz crash bucket; recovery: validate UTF-8 boundaries before slicing, return ParseError::InvalidUtf8.

⬜ Phase 2 — Protobuf Binary Codec §14

Objectives

Implement the protobuf wire codec: varint/zigzag primitives, wire-tag encode/decode, packed repeated fields, and unknown-field retention, interoperating byte-for-byte with protoc/prost (P10). Constraint introduced: encode/decode must hit the §4 latency budgets (< 150 ns / < 250 ns p50 for a 64 B message) with zero heap allocation on the hot path (P4). Dynamic reflection over descriptors and protobuf-JSON mapping are PhaseDeferred("§14") (see §35).

Deliverable

serdes-proto-codec encodes and decodes any RecordSchema-shaped message to/from bytes that protoc's reference C++ implementation accepts and round-trips identically; unknown fields survive a decode→re-encode cycle byte-for-byte.

Acceptance
  • Encode p50 latency < 150 ns and decode p50 < 250 ns for a 64 B message with 5 scalar fields, measured by the Criterion bench in benchmarks/codec_bench.rs (M1/M2, §28).
  • malformed.bin (§14.5) decode returns Err(DecodeError::Truncated), never panics, in 100/100 fuzz replay runs.
  • unknown.bin roundtrips with zero byte drift, asserted by a byte-equality check, not just a structural equality check.
  • Zero heap allocations recorded by the allocation-counting test harness during decode of int32.bin (P4).
Fixtures
Fixture Assertion
fixtures/proto/int32.bin varint round-trip correctness for int32/int64/uint32/uint64
fixtures/proto/packed.bin packed-repeated scalar fields encode/decode correctly
fixtures/proto/malformed.bin truncated varint returns a decode error, never panics
fixtures/proto/unknown.bin unknown fields retained byte-exact across a roundtrip
Pitfalls
  • Truncated varints at end-of-buffer — manifestation: decoder reads past the buffer end; root cause: missing bounds check before the continuation-bit test; debugging: fuzz with truncated inputs (§21); signal: cargo-fuzz OOB-read crash; recovery: I2's 10-byte + bounds-checked loop.
  • Integer overflow on a maliciously long varint sequence — manifestation: silently wrapping u64 arithmetic instead of erroring; root cause: shift-accumulate loop without an overflow guard on byte 10; debugging: fixed fuzz corpus entry with 11 continuation bytes; signal: incorrect decoded value instead of an error; recovery: explicit checked_shl/overflow check.
  • Recursion bombs via deeply nested embedded messages — manifestation: stack overflow on decode; root cause: no depth limit on length-delimited sub-message recursion; debugging: fuzz with deeply nested packed.bin-style payloads; signal: crash, not a graceful error; recovery: shared recursion-depth counter with the parser's I14 limit (128 levels).
  • Duplicate fields for a non-repeated scalar — manifestation: ambiguity over which value wins; root cause: protobuf spec says "last one wins" but that's easy to implement backwards; debugging: differential fixture against protoc's documented last-wins semantics; signal: decoded value mismatches protoc's output; recovery: always overwrite on duplicate, never merge.

⬜ Phase 3 — Avro Schema Parser & Canonicalization §15

Objectives

Parse Avro JSON schemas (.avsc) into SchemaKind (§11) via an AST, resolve namespaces, support recursive named-type references, and compute Parsing-Canonical-Form fingerprints (I5). Constraint introduced: canonicalization must be a pure, order-independent function of schema content (P9) — this phase is the trust root every dedup and compatibility decision in §17/§18 depends on.

Deliverable

serdes-avro-schema compiles an .avsc JSON string into a SchemaKind value with a computed SchemaFingerprint, exposed as parse(src: &str) -> Result<SchemaKind, AvroSchemaError>.

Acceptance
  • user.avsc (§15.5) parses into a SchemaKind::Record with exactly its 2 declared fields, in ≤ 300 µs.
  • Two reordered-but-semantically-identical copies of user.avsc (differing only in JSON key order within each field object) produce identical SchemaFingerprint values — the direct P9 fixture.
  • recursive.avsc parses successfully (no stack overflow, no false-positive cycle rejection).
  • invalid_union.avsc (duplicate unnamed-type union branch) is rejected with a specific AvroSchemaError::AmbiguousUnion variant, not a generic parse failure.
Fixtures
Fixture Assertion
fixtures/avro/user.avsc parses a valid two-field record
fixtures/avro/recursive.avsc self-referential record type parses without infinite recursion
fixtures/avro/invalid_union.avsc ambiguous union (duplicate branch type) is rejected
Pitfalls
  • Namespace collisions between two same-named types in different files — manifestation: the second type silently shadows the first; root cause: namespace registry keyed by short name instead of fully-qualified name; debugging: differential fixture with two user.avsc variants under different namespaces; signal: wrong type resolved at reference time; recovery: key the registry by fully-qualified name always.
  • Recursive-type infinite loop during canonicalization — manifestation: canonicalizer hangs on recursive.avsc; root cause: canonical-form serialization walks the type graph without a visited-set; debugging: add a recursion-depth counter and reproduce with a minimal self- referential fixture; signal: CI timeout; recovery: canonicalize named types once, referencing by name thereafter, not by full inline expansion.
  • Invalid defaults accepted silently — manifestation: a "default": "x" on an int field parses without error, then fails confusingly at decode time; root cause: default validation deferred to the codec instead of the schema parser; debugging: add a fixture pairing every primitive type with a mismatched default; signal: a decode-time error that should have been a compile-time one; recovery: validate defaults against declared type during parse (15.2 step 8).
  • Ambiguous unions — manifestation: two branches of the same underlying type in one union; root cause: Avro spec forbids this but many hand-written schemas violate it unknowingly; debugging: invalid_union.avsc fixture; signal: AvroSchemaError::AmbiguousUnion; recovery: reject at parse, never attempt best-effort disambiguation.

⬜ Phase 4 — Avro Binary Codec §16

Objectives

Implement the Avro binary codec: schema-directed positional encoding, block-encoded arrays/maps, union dispatch, and reader/writer schema resolution (type promotion, default injection, unknown- field skipping), interoperating with Java Avro (P10). Constraint introduced: decode must resolve a writer schema against a possibly-different reader schema without any registry lookup mid-decode — resolution is a pure function of the two schemas (I12).

Deliverable

serdes-avro-codec encodes/decodes any SchemaKind value to/from Avro binary bytes that interoperate with Java Avro, including cross-version reader/writer resolution.

Acceptance
  • Encode p50 < 400 ns, decode p50 < 450 ns for a typical 5-field record (M3/M4, §28).
  • evolution.bin (§16.5) decodes correctly under three different reader schemas (older, same, newer than the writer), each producing the resolution-correct value set.
  • A reader schema requiring a field the writer lacks, with no default declared, returns Err(SchemaResolutionError::MissingDefault) — the I12 fixture — in 100% of 50 fuzz-generated variants.
  • arrays.bin round-trips block-encoded arrays of 0, 1, and 10,000 elements with byte-exact re-encoding.
Fixtures
Fixture Assertion
fixtures/avro/primitives.bin primitive-type encode/decode correctness for all 9 PrimitiveType variants
fixtures/avro/arrays.bin block encoding correctness across empty, small, and large arrays
fixtures/avro/evolution.bin reader/writer resolution across three schema-version pairs
Pitfalls
  • Union dispatch ambiguity at decode — manifestation: decoder picks the wrong branch for a value that could structurally fit two branches; root cause: the encoder didn't preserve which branch was chosen distinctly enough; debugging: differential fuzz against Java Avro (§21); signal: FM-10 (§23); recovery: always trust the explicit branch-index prefix, never re-infer from shape.
  • Incorrect default injection — manifestation: a missing field gets the wrong default (e.g. 0 instead of the schema's declared default); root cause: default lookup falls back to a type's zero-value instead of Field.default (§11); debugging: evolution.bin fixture with a non-zero default; signal: silently wrong data downstream; recovery: always read Field.default.
  • Schema-mismatch handling that silently truncates — manifestation: extra writer fields are dropped without validating they parse to a complete, well-formed value first; root cause: attempting a byte-skip instead of a full decode-then-discard; debugging: fuzz with variable- length extra fields (nested records, strings); signal: decode desyncs on the next field after the skipped one; recovery: 16.2 step 7's decode-then-discard, never skip by estimated length.

⬜ Phase 5 — Compatibility Engine §17

Objectives

Implement serdes-compat: a pure function from (old: &SchemaKind, new: &SchemaKind, mode: CompatibilityMode) -> CompatibilityResult (§11's CompatibilityChecker trait) matching Confluent's BACKWARD/FORWARD/FULL/*_TRANSITIVE semantics exactly (P10, confluentinc/schema- registry reference, §5). Constraint introduced: the engine touches no storage and no network — it is testable in complete isolation from §18/§19 (P5).

Deliverable

A CompatibilityChecker implementation callable as a library function and, once §19 exists, via POST /compatibility/subjects/{subject}/versions/{version}.

Acceptance
  • backward.json (§17.5): a schema adding an optional field passes BACKWARD in < 1 ms p99 (M8, §28).
  • breaking.json: a schema removing a required field with no default is rejected under all four base modes, with a CompatibilityViolation naming the exact field path.
  • aliases.json: a field renamed via alias is treated as compatible, not reported as a remove+add.
  • Transitive check across 50 synthetic historical versions completes in < 25 ms p99 (M9, §28).
Fixtures
Fixture Assertion
fixtures/compat/backward.json additive, defaulted change passes BACKWARD
fixtures/compat/breaking.json required-field removal without a default is rejected
fixtures/compat/aliases.json alias-based rename resolves as the same field, not a break
Pitfalls
  • Incorrect transitive traversal — manifestation: a *_TRANSITIVE check passes when it should fail against an older-than-latest version; root cause: the traversal only compared against the immediately preceding version; debugging: a 3-version fixture where versions 1 and 3 conflict but 2 and 3 don't; signal: a consumer on version 1 breaks despite a "compatible" registration; recovery: I7's full visited-set walk over every stored version, not just the latest.
  • Enum narrowing accepted by mistake — manifestation: removing an enum symbol passes BACKWARD; root cause: enum checks reused the field-removal default-check path, which doesn't apply to symbols; debugging: a dedicated enum-narrowing fixture; signal: a consumer reading old data encounters a symbol its (over-narrowed) schema doesn't know; recovery: treat all enum-symbol removal as breaking, unconditionally (17.2 step 5).
  • Default-coercion bugs — manifestation: a numeric default like 0 is treated as "no default" by a truthy-check bug; root cause: Option<LiteralValue> unwrapped with a falsy-value shortcut instead of an is_some() check; debugging: a fixture with an explicit zero default; signal: false-positive breaking-change rejection; recovery: always check Option presence, never the contained value's truthiness.

⬜ Phase 6 — Registry Storage Layer §18

Objectives

Implement serdes-store: the SchemaStore trait (§11) with a SQLite (WAL-mode) backend and an in-memory backend, both passing an identical integration-test suite (P8). Constraint introduced: every registration is one atomic transaction (I9); SchemaId allocation is strictly monotonic (I6) even under concurrent writers.

Deliverable

A SchemaStore implementation (SQLite or in-memory) that durably persists registered schemas with monotonic IDs, atomic writes, and consistent reads, swappable behind the trait with zero changes to any caller.

Acceptance
  • sqlite_insert.rs (§18.5): 1,000 sequential registrations produce 1,000 strictly increasing SchemaIds with zero gaps.
  • sqlite_txn.rs: a simulated kill -9 mid-write (via the deterministic simulator, §7) followed by restart shows either the full write committed or none of it — never a partial row.
  • memory_store.rs: the in-memory backend passes the identical suite as the SQLite backend, asserted by running both through run_store_suite.
  • SQLite insert transaction commit p99 < 8 ms (M12, §28).
Fixtures
Fixture Assertion
fixtures/registry/sqlite_insert.json sequential registrations yield gap-free monotonic IDs
fixtures/registry/sqlite_txn.json mid-write kill leaves no partial row after WAL replay
fixtures/registry/memory_store.json in-memory backend matches SQLite backend's ID semantics
Pitfalls
  • Race conditions on concurrent version-increment — manifestation: two clients registering to the same subject simultaneously both get "version 3"; root cause: read-then-write without a transaction wrapping both; debugging: a concurrency stress test with 50 parallel registrations; signal: duplicate version numbers in list_versions; recovery: 18.2 step 4's optimistic-lock retry loop.
  • Duplicate SchemaIds across a crash/restart boundary — manifestation: the sequence counter resets; root cause: using an in-memory counter instead of the SQLite INTEGER PRIMARY KEY auto-increment as the source of truth; debugging: restart-and-register replay test; signal: I6's gap-scan actually finds a duplicate, not a gap — a distinct failure mode worth its own check; recovery: never maintain the counter outside the durable table.
  • Migration drift between a manually-patched database and the checked-in migration history — manifestation: boot fails with a checksum mismatch; root cause: an operator ran a manual ALTER TABLE outside the migration system; debugging: migrations.rs's version log (§18.10); signal: FM-8 (§23); recovery: an operator-run migration-repair script, never a silent skip.

⬜ Phase 7 — Schema Registry HTTP API §19

Objectives

Implement serdes-registry: an axum-based (ADR-06) Confluent-compatible REST API over SchemaStore (§18) and CompatibilityChecker (§17) — subject/version lifecycle, compatibility- mode config with inheritance (I13), health checks, and observability (P11). Constraint introduced: no handler blocks the tokio reactor for more than 1 ms without an .await (I10); the registry sheds load via a bounded concurrency limiter before ever buffering unboundedly (P13).

Deliverable

A running serdes-registry HTTP server implementing the Confluent Schema Registry REST contract, backed by either storage backend, observable via Prometheus and OTLP tracing.

Acceptance
  • register.http (§19.5): a valid schema registration returns 200 with a SchemaId in < 10 ms p99 (M6, §28).
  • compat.http: a breaking-change registration returns 409 with a violation list naming the exact field, never a bare boolean.
  • list_subjects.http: subject enumeration returns all registered subjects, including soft- deleted ones only when a ?deleted=true query parameter is present (Confluent parity).
  • Load test at 512 concurrent in-flight requests (§4) shows zero unbounded-queue memory growth and a clean 503 shed rate once the concurrency limit is hit.
Fixtures
Fixture Assertion
fixtures/registry/register.json valid registration returns 200 and a monotonic SchemaId
fixtures/registry/compat.json breaking-change registration returns 409 with a violation list
fixtures/registry/list_subjects.json subject enumeration matches the store's actual contents
Pitfalls
  • Incorrect HTTP status-code semantics — manifestation: a compatibility rejection returns 400 instead of 409, breaking Confluent-client retry logic keyed on status code; root cause: a generic error-mapping layer collapsing distinct error kinds; debugging: differential fixture against Confluent's documented codes; signal: a client retries a request that will never succeed; recovery: map each SerdesError variant to its exact Confluent-parity status, 1:1.
  • Non-idempotent retries on POST /subjects/.../versions — manifestation: a client retry after a timeout creates two versions for one logical registration; root cause: fingerprint-dedup (I5) only covers byte-identical schemas, not a client-side reformat before retry; debugging: fixture simulating a slow-then-retried request; signal: unexpected duplicate versions; recovery: document dedup's exact scope; a real idempotency-key design is out of scope for Phase 0–9.
  • Malformed JSON handling that panics instead of returning 422 — manifestation: a crafted request body crashes the handler; root cause: serde_json deserialization error not mapped to a Result path before axum's extractor runs; debugging: fuzz the registration endpoint body (§21.2's registry_api.rs target); signal: I8 violation, decoder_panics_total nonzero; recovery: explicit extractor error handling, never .unwrap() on request-body parsing.

⬜ Phase 8 — CLI & Tooling §20

Objectives

Implement serdes-cli (clap, ADR-04's CLI counterpart is ADR referenced elsewhere; CLI itself locked by the clap ADR): compile, encode, decode, validate, and serve subcommands wrapping the library crates for operator and developer ergonomics. Constraint introduced: the CLI must never corrupt binary stdout with diagnostic text (T9-adjacent), and every subcommand exits with a distinct, documented exit code.

Deliverable

A single serdes-cli binary exposing compile/encode/decode/validate/serve, usable both interactively and in CI pipelines via JSON output mode and documented exit codes.

Acceptance
  • serdes-cli serve refuses to start without a bound metrics endpoint (P11), exiting with code 2 and a diagnostic naming the missing --metrics-addr flag.
  • compile.snap (§20.5): compiling basic.proto produces byte-identical JSON-mode output across three consecutive runs (P3's determinism, exercised at the CLI boundary).
  • CLI cold-start latency < 300 ms (M10, §28), measured from process exec to first stdout byte for serdes-cli --version.
  • encode.snap: encoding a fixture through the CLI produces output byte-identical to calling the library function directly — the CLI adds zero encoding-affecting behavior.
Fixtures
Fixture Assertion
fixtures/cli/compile.snap compile subcommand's JSON output is stable across runs
fixtures/cli/encode.snap CLI-produced binary output matches direct library output
fixtures/cli/compat.snap validate subcommand's compatibility verdict matches the library
Pitfalls
  • Inconsistent exit codes across subcommands — manifestation: a CI pipeline's error handling works for compile but not validate; root cause: exit codes chosen ad hoc per subcommand instead of from the shared table (20.2 step 9); debugging: a snapshot test asserting every subcommand's exit code for its error fixture; signal: CI scripts silently treat a real failure as success; recovery: centralize exit-code mapping in one function, tested once.
  • Shell escaping issues with file paths containing spaces or globs — manifestation: serdes-cli compile *.proto behaves differently than expected on paths with spaces; root cause: relying on shell globbing instead of clap's explicit multi-value argument parsing; debugging: a fixture with a space-containing filename; signal: "file not found" on a file that exists; recovery: use clap's Vec<PathBuf> argument type, never string-split a shell-provided glob result manually.
  • Binary/stdout corruption — manifestation: decode --out - output is unreadable because a log line was interleaved into stdout; root cause: tracing's default subscriber writes to stdout instead of stderr; debugging: encode.snap's byte-equality check catches this immediately; signal: downstream pipe (serdes-cli decode --out - | some-consumer) fails to parse; recovery: configure the tracing subscriber to stderr always, reserving stdout for command output only.

⬜ Phase 9 — Conformance, Fuzzing & Interop §21

Objectives

Prove the interoperability claims every prior phase made (P10) with automated differential testing against protoc and Java Avro, and harden every parser/decoder against adversarial input via continuous fuzzing (P6, I8). This phase has no new library code of its own — it is entirely verification infrastructure over Phases 1–7.

Deliverable

A CI-integrated conformance and fuzzing suite proving byte-exact interoperability with protoc and Java Avro, plus a continuously-run fuzz corpus with zero known crashes at release time.

Acceptance
  • diff_protoc (§21.5): 100% field-by-field agreement across all fixtures/proto/*.bin fixtures, zero tolerated mismatches.
  • fuzz_varint: 20,000+ executions/sec sustained (M11, §28) with zero crashes over an 8-hour nightly run.
  • random_schema: 10,000 randomly generated compatible schema-evolution pairs all agree between the compatibility engine's verdict and the codec's actual resolution behavior (closing the 16.9/17.9 gap between abstract rule and operational reality).
  • Every crash found by fuzzing in the last 90 days has a corresponding checked-in fixture (P14), verified by a CI script that greps fuzz/artifacts/ history against the fixture manifest.
Fixtures
Fixture Assertion
fixtures/fuzz/fuzz_varint decoder safety under arbitrary byte input, zero crashes
fixtures/fuzz/random_schema compatibility-engine stability across generated schema pairs
fixtures/fuzz/diff_protoc exact field-level equivalence with protoc's decode output
Pitfalls
  • Nondeterministic snapshots — manifestation: insta snapshot fixtures flake in CI but pass locally; root cause: HashMap iteration order leaking into snapshot output somewhere upstream of this phase (a P3 violation surfacing here first); debugging: run the snapshot 100× locally with varying RUSTFLAGS hash-seed settings; signal: intermittent CI red with no code change; recovery: trace back to the non-canonical serialization and fix at the source (usually §15's canonicalizer), not by relaxing the snapshot check.
  • Flaky fuzz minimization — manifestation: cargo-fuzz's crash minimizer produces a different minimal repro on each run; root cause: the target itself has nondeterministic behavior (e.g. reading wall-clock time); debugging: re-run minimization with a fixed seed; signal: the same underlying bug files as two different "distinct" fixtures; recovery: eliminate all nondeterminism from fuzz targets, per ADR-20's monotonic-clock discipline.
  • Platform-dependent ordering — manifestation: diff_protoc passes on Linux CI but fails on a contributor's macOS machine; root cause: a HashMap-ordering or float-formatting difference across platforms; debugging: reproduce with the exact same rustc/OS pairing as the failure; signal: "works in CI, fails locally" bug reports; recovery: pin canonical serialization to not depend on platform-specific float formatting or hash-map iteration.
