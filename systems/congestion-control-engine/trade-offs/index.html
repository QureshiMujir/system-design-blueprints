Decisions (§9) · 32 ADRs

ADR-001

Implementation language

Chosen

Rust (edition 2021, MSRV pinned)

Rejected

C, C++, Go, Zig

When the rejected choice is right

C wins when the target is in-tree Linux tcp_congestion_ops (the kernel is C; a Rust module still crosses the C ABI of Phase 12 — for a kernel-only deliverable, native C removes the FFI shim entirely).

Why: no-GC determinism, trait→vtable fit, repr(C) FFI, fixed-point safety, mature fuzz/bench tooling (§1.10)

ADR-002

Control-math representation

Chosen

Integer + fixed-point (u64 µs/bytes/bps, Q16.16 gains)

Rejected

f64/f32

When the rejected choice is right

f64 wins when reproducibility is not a requirement and you want the smoothest CUBIC/BBR curves with least implementation effort (a single-host research prototype that runs on one machine and does not cross-check traces across architectures).

Why: float nondeterminism (FMA/libm) forbidden; INV-1; INV-7

ADR-003

Module dispatch

Chosen

&mut dyn CongestionControl trait object

Rejected

enum-of-algos, generics-only

When the rejected choice is right

enum-of-algos wins when the algorithm set is closed and fixed at compile time and hot-swap/external modules are not needed — the compiler then devirtualizes and inlines, shaving the per-ACK indirect call.

Why: dynamic per-conn swap (INV-10); mirrors tcp_congestion_ops; enum loses external modules

ADR-004

FFI ABI

Chosen

#[repr(C)] vtable struct of extern "C" fn ptrs

Rejected

bindgen of Rust trait, message-passing

When the rejected choice is right

message-passing wins when the transport lives in a different process/address space (a userspace TCP stack over a socket/shared-ring) where a shared function-pointer table is unsafe and a serialized signal/decision channel is the right boundary.

Why: parity with kernel vtable; non-Rust transports register modules

ADR-005

Build system

Chosen

Cargo workspace (multi-crate)

Rejected

Bazel, Make-only

When the rejected choice is right

Bazel wins when ccx is one crate inside a large polyglot monorepo with remote caching and hermetic cross-language builds already standardized on Bazel.

Why: native Rust tooling; reproducible; Make wraps cargo for CI

ADR-006

Dependency policy

Chosen

Minimal; #![forbid(unsafe_code)] in core/algos; cargo-deny gate

Rejected

liberal deps

When the rejected choice is right

liberal deps win for a throwaway evaluation harness where development speed dominates and the supply-chain/audit surface is irrelevant (no shipped artifact).

Why: small attack surface; supply-chain control; determinism

ADR-007

PRNG

Chosen

Pcg64 (rand_pcg) seeded explicitly, single instance per run

Rejected

OS RNG, thread_rng, Mersenne

When the rejected choice is right

OS RNG wins if the loss/reorder model must resist an adversary predicting the sequence (a security study of CC under crafted loss) — there, unpredictability beats reproducibility.

Why: reproducible (INV-1); fast; not crypto (no crypto need)

ADR-008

Time source

Chosen

injected Clock trait (now_us()->u64); sim virtual clock

Rejected

Instant::now() calls inline

When the rejected choice is right

inline Instant::now() wins in a live, non-simulated embedding where wall-clock pacing matters and there is no replay/determinism requirement — clock injection is then needless indirection.

Why: determinism + replay (P15)

ADR-009

Sim architecture

Chosen

discrete-event, binary-heap event queue, fixed µs tick

Rejected

time-stepped fluid sim, real sockets

When the rejected choice is right

real sockets win for end-to-end validation against a live kernel stack (an interop/qualification test) where fidelity to actual NIC/OS behavior beats determinism and speed. Fluid sim wins for very-large-scale (10⁶+ flow) macroscopic fairness studies where per-packet detail is unaffordable.

Why: accuracy + determinism + speed (≥5M ev/s)

ADR-010

Event ordering tiebreak

Chosen

(time_us, monotonic seq, kind) total order

Rejected

insertion-order only

When the rejected choice is right

insertion-order wins when the event source already guarantees no two events share a timestamp (a coarse-grained sim with unique-time events), where the extra (seq,kind) key is dead weight.

Why: stable order under simultaneous events (INV-13)

ADR-011

Queue disciplines

Chosen

DropTail, RED, CoDel, FQ-CoDel as Qdisc trait

Rejected

DropTail only

When the rejected choice is right

DropTail-only wins when the study target is loss-based AIMD on classic tail-drop routers (reproducing a 1990s-Internet or shallow-buffer datacenter result) and AQM would change the very phenomenon under test.

Why: AQM needed for bufferbloat/RTT-fairness studies (§Phase 9)

ADR-012

Sent-history structure

Chosen

Rejected

When the rejected choice is right

a hashmap/scoreboard wins when per-packet random-access lookup by sequence is required (a full SACK-based loss detector that must locate arbitrary holes), which a ring cannot do in O(1).

Why: O(1) push/evict; bounded memory (constraint §4)

ADR-015

ADR-016

Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build congestion control for the same goal. Each: sketch, winning regime, the real system embodying it, why this blueprint rejected it.

A1 — Explicit router feedback (rate stamped by the network). The router computes each flow's fair rate and writes it into the packet; the sender obeys.

  sender ──data──▶ [router: compute fair-share, stamp rate field] ──▶ receiver
     ▲                                                                   │
     └──────────── feedback carries explicit per-flow rate ─────────────┘
  • Wins: datacenters or single-administrator fabrics where every router cooperates and can be upgraded — convergence is near-instant and fairness is exact, with no buffer-filling search.
  • Real system: XCP (Katabi et al., SIGCOMM 2002) and RCP embody explicit per-flow rate feedback; DCTCP (RFC 8257) is a deployed partial form (1-bit ECN feedback rather than a full rate).
  • Rejected because: it requires changing every router on the path — impossible on the public Internet and outside this engine's scope (the engine consumes abstract signals and assumes commodity routers; only the ECN-fraction slice, DCTCP, is in scope via §8.6).

A2 — Centralized / scheduled bandwidth allocation (no per-flow control loop). A controller with a global view assigns bandwidth to flows; endpoints do not run an independent AIMD loop.

   ┌─────────── central controller (global topology + demand) ───────────┐
   │ allocates rate per flow, pushes schedules                            │
   └───────┬───────────────┬───────────────┬───────────────┬─────────────┘
        flow A           flow B           flow C          flow D   (obey, no probing)
  • Wins: a private WAN whose operator controls all endpoints and switches and wants near-100% utilization with engineered fairness — global optimization beats distributed probing.
  • Real system: Google's B4 SDN WAN (Jain et al., SIGCOMM 2013) centrally schedules inter-DC bandwidth; endpoint CC becomes secondary.
  • Rejected because: it presumes a global controller and administrative control of the whole network — the antithesis of an end-to-end, per-connection pluggable engine. ccx deliberately models the endpoint control loop; centralized allocation is a different system class.

A3 — Monolithic, single-algorithm sender (no vtable, algorithm compiled in). One congestion controller is hard-coded into the sender; switching it means recompiling, and the mechanism/policy split is collapsed.

   ┌──────────────── sender (one fixed algorithm) ────────────────┐
   │  cwnd accounting + growth law + pacing all interwoven inline  │
   └──────────────────────────────────────────────────────────────┘
  • Wins: an embedded/appliance sender that ships exactly one algorithm forever, where the indirect call per ACK and the API surface are pure overhead and inlining the whole controller is fastest.
  • Real system: most early/textbook TCP stacks (e.g. classic BSD TCP) embedded Reno directly before Linux introduced tcp_congestion_ops (the pluggable framework B4/R1 study).
  • Rejected because: the entire point of this project is the pluggable host that mounts five paradigms behind one stable vtable and hot-swaps them (§1.1, design principle 3, Phase 1). A monolith forecloses comparison, hot-swap, and external modules — the deliverable itself.
