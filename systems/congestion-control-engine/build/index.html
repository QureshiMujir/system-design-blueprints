Define the stable vtable, per-connection state, the module registry, and the invariant-preserving hot-swap. This is the architectural keystone (P3, the vtable contract).

Deliverable

⬜ Phase 3 — Estimators: SRTT/RTTVAR, min-RTT Filter, Delivery-Rate §15

Objectives

Implement the three estimators that all algorithms read: RFC 6298 RTT/RTO, windowed min-RTT (RTprop), and the Cheng/Cardwell delivery-rate RateSample. Pure, deterministic, allocation-free.

Deliverable

Given a signal stream, estimators produce SRTT/RTTVAR/RTO, min-RTT, and per-ACK RateSample deterministically. Unit + property tested.

Acceptance
  • RFC 6298 vectors reproduced exactly (fixed-point) within ±1 µs of integer reference.
  • min-RTT never exceeds any in-window sample (INV-6 property test).
  • Delivery-rate matches a hand-computed reference for a known send/ack schedule (±0.1%).
  • Estimator update ≤ 60 ns (criterion); ring memory ≤ 64 KiB at 1024-pkt cwnd.
Fixtures
  • rfc6298_rtt_vectors.txt: sample sequence → expected SRTT/RTTVAR/RTO.
  • minrtt_window.json: timed samples → expected min + expiry flags.
  • rate_sample_schedule.json: send/ack timeline (incl. app-limited gap, reordering) → expected RateSample series.
Pitfalls
Manifestation Root cause Debug Signal Recovery

⬜ Phase 4 — Pacer (Token Bucket, Send-Quantum, Burst Budget) §16

Objectives

Implement pacing so the sender shapes output to pacing_rate rather than bursting to cwnd (P6, backpressure). Provide SendDecision (send_bytes, next_send_us) consumed by transport/sim.

Deliverable

A flow paced at rate R emits sends spaced ≈ MSS/R apart, bounded by cwnd; burst budget bounds micro-bursts. Deterministic given tick. Unit + property tested.

Acceptance
  • Over any interval T, bytes sent ≤ rate·T + burst_cap (INV-12 property test).
  • Inter-packet spacing within ±1 tick of MSS/rate at steady state.
  • Pacer respects cwnd cap (never inflight > cwnd).
  • poll ≤ 40 ns (criterion).
Fixtures
  • pacer_spacing.json: rate + cwnd + tick schedule → expected send times.
  • pacer_burst.json: idle then resume → expected burst ≤ cap.
  • pacer_cwnd_cap.json: tokens available but cwnd full → expect hold.
Pitfalls
Manifestation Root cause Debug Signal Recovery
Standing queue despite pacing burst_cap too large queue + pacer trace pacer_overshoot_total shrink burst_cap
Pacing starvation (never sends) next_send_us miscomputed / rate=0 pacer trace pacer_idle_total floor rate; recompute next time
Token accrual overflow long idle × high rate overflow counter overflow_saturated_total cap tokens at burst_cap
Spacing jitter integer division truncation spacing fixture — distribute remainder across sends

⬜ Phase 7 — BBR v1 Module (BtlBw & RTprop Model) §19

Objectives

Implement model-based control: estimate BtlBw (max-filtered delivery rate) and RTprop (min-RTT), drive pacing_rate and cwnd by gain, cycle through STARTUP/DRAIN/PROBE_BW/PROBE_RTT. This is the hardest module and the strongest test of the estimator + pacer subsystems.

Deliverable

BBR ramps in STARTUP, drains the queue, settles into PROBE_BW gain cycling, periodically enters PROBE_RTT, and tracks bandwidth/RTT changes. Golden trace committed.

Acceptance
  • STARTUP→DRAIN→PROBE_BW→PROBE_RTT transitions occur at correct triggers (state-trace fixture).
  • Achieved throughput ≈ BtlBw (within 5%) at steady state; queue stays low (≤ ~1.5·BDP inflight).
  • Responsiveness: on a mid-run 2× bandwidth increase, BBR converges to new rate within ~3 round-trips (responsiveness metric, §Phase 10).
  • Golden trace byte-identical across runs/arches.
  • PROBE_RTT lowers inflight to ~4 pkts and refreshes RTprop.
Fixtures
  • bbr_state_machine.toml + expected state-transition trace (with triggers).
  • bbr_probebw.trace (golden cwnd/pacing/state).
  • bbr_bw_change.json: bandwidth step → expected convergence rounds.
  • bbr_app_limited.json: app-limited interval → expect BtlBw not reduced.
  • bbr_probe_rtt.json: 10 s without min-RTT update → expect PROBE_RTT entry.
