Perf-target IDs M1–M10 are the row anchors cited by §Performance Engineering, §Back-of-Envelope Capacity Model, Phase 13, and the Hard Questions below; every M# used elsewhere in this document resolves to exactly one of the ten rows above.

CPU/cache: hot path fits in L1 (CcState ≤ 1 KiB); estimator ring access is sequential. NUMA: single-threaded per connection; sim sharding (Phase 13) pins flows to cores. Availability/RTO/failure budgets are simulation-domain (no live service); "recovery" = deterministic replay (RTO = re-run from seed).

Performance Engineering

  • Benchmarking strategy: criterion micro-benches (per-ACK per algo, estimator, pacer, heap ops) + macro benches (full scenario wall-time, events/sec). Baselines committed (bench_baselines.json); regressions gate CI.
  • Profiling methodology: cargo flamegraph on the sim hot loop and a synthetic per-ACK driver; perf stat for IPC, cache-miss, branch-mispredict on the per-ACK path; perf c2c for false-sharing if sharding (Phase 13).
  • Flamegraph workflow: capture before/after each optimization; store in docs/performance/; the per-ACK flamegraph should show only intake+estimator+module+clamp (no allocation, no syscalls).
  • Tracing methodology: the per-event trace doubles as a perf timeline (event counts/sec); tracing spans bracket sim phases.
  • Allocator analysis: counting allocator in tests asserts 0 allocations on the per-ACK and per-event hot paths (INV-11); modules/connections allocate only at construction.
  • Lock analysis: none on the per-connection path (single-thread per conn, ADR-015/016); sim sharding uses no shared mutable state (independent runs).
  • Cache analysis: CcState hot fields packed in the first cache line; estimator ring is contiguous (sequential access); Event ≤ 24 B to fit many per cache line in the heap.
  • Syscall analysis: zero syscalls on hot paths (no I/O); CLI does file I/O only at start/end.
  • Throughput targets: per-ACK ≤ 200 ns median (M1); sim ≥ 5 M ev/s (M3); §4.
  • Tail-latency analysis: per-ACK p99 ≤ 1 µs (M1); rare spikes from CUBIC cbrt (loss-only) and BBR PROBE_RTT bookkeeping — both off the common path; documented.
  • Memory profiling: per-conn ≤ 1 KiB (M4) + bounded ring ≤ 64 KiB (M5); 10⁴ flows ≤ 8 GiB (M10); verified under soak.

Back-of-Envelope Capacity Model

Numbers an expert computes from §4 (System Constraints) before designing. Each is derived; the §4 input is named.

  • C1 — cwnd ceiling at the BDP (the operating point). Input: §4 RTT model (1 µs–10 s) and a representative WAN link. For 100 Mb/s × 50 ms RTT: BDP = 100e6 b/s × 0.050 s ÷ 8 = 625,000 B ≈ 417 × 1500-B MSS. This is the cwnd a full-throughput flow must reach — and the per-conn sent-history ring must index that many packets.
  • C2 — sent-history ring size. Input: §4 "Sent-history ring ≤ 64 KiB at cwnd ≤ 1024 pkts" (M5). 1024 entries × sizeof(PacketMeta); with PacketMeta ≈ 40 B (5×u64-ish per §11.4) → 1024 × 40 = 40 KiB < 64 KiB ✓. Confirms the M5 ceiling holds for the C1 cwnd (417 pkts) with headroom.
  • C3 — per-connection memory and the 10⁴-flow run. Input: §4 "≤ 1 KiB CcState+module" (M4) and "≥ 10⁴ flows in 8 GiB" (M10). 10⁴ × (1 KiB CcState + 64 KiB ring) = 10⁴ × 65 KiB ≈ 650 MiB. Well under 8 GiB → the ceiling is the ring, not CcState; trimming the ring (C1: 417-pkt cwnd needs ~16 KiB) lands ~170 MiB.
  • C4 — embedded engine at 10⁶ connections. Input: §4 per-conn ceilings (M4) + §Scalability Analysis "10⁶ connections". 10⁶ × 1 KiB CcState ≈ 1 GiB of CC state (excluding rings, which a real transport may bound smaller). Matches the §Scalability Analysis claim; the ring, not cwnd state, dominates if kept at 64 KiB (10⁶ × 64 KiB = 64 GiB — so a high-conn transport must shrink the ring).
  • C5 — per-ACK CPU budget vs ACK rate. Input: §4 "per-ACK ≤ 200 ns" (M1). One core at 1 s ÷ 200 ns = 5×10⁶ ACK-events/s. At ~1 ACK per 2 packets (delayed ACK) and 1500-B packets, that services 5e6 × 2 × 1500 × 8 ≈ 120 Gb/s of aggregate ACK-clocked traffic per core before the CC hook itself is the bottleneck.
  • C6 — simulator wall-time for a scenario. Input: §4 "≥ 5 M events/sec" (M3). A 60 s-sim-time, 2-flow, 100 Mb/s dumbbell at ~1500-B packets generates ≈ (100e6/8/1500) × 60 × 2 flows × ~4 events/pkt (send/arrive/dequeue/ack) ≈ 4×10⁶ events. At 5 M ev/s → ≈ 0.8 s wall-time. CI can run hundreds of such scenarios per minute.
  • C7 — standing queue delay from buffer size. Input: §4 link model + a tail-drop buffer sized at 1×BDP. queue_delay = buffer_bytes ÷ link_rate. For a 625,000 B buffer (= 1 BDP, C1) at 100 Mb/s: 625,000 × 8 ÷ 100e6 = 50 ms of added delay when full — doubling the 50 ms RTT. This is the bufferbloat MM6/MM1 predicts and what CoDel (§4 target ≤ 5 ms, M9) caps.
  • C8 — CoDel target vs BDP. Input: §4 "CoDel sojourn ≤ 5 ms" (M9). 5 ms at 100 Mb/s = 5e-3 × 100e6 ÷ 8 = 62,500 B ≈ 42 MSS of standing queue — i.e. CoDel holds the queue to ~10% of the C1 BDP, the quantitative meaning of "controlled delay".
  • C9 — Reno throughput from loss (Mathis et al.). Input: §4 loss model + C1 path. Mathis approximation throughput ≈ MSS/RTT × √(3/2) / √p. At MSS=1500 B, RTT=50 ms, loss p = 10⁻⁴: (1500×8/0.050) × 1.22 / 0.01 = 240,000 × 122 ≈ 29 Mb/s — i.e. Reno cannot fill the 100 Mb/s C1 pipe at that loss rate, the exact long-fat-network problem CUBIC/BBR exist to solve.
  • C10 — RTO floor vs RTT. Input: §4 "RTO bounded [200 ms, 60 s]" and the 50 ms RTT. The 200 ms floor is 4× the path RTT — a spurious-timeout guard; a flow with 50 ms RTT waits ≥ 200 ms before an RTO, so RACK-TLP (P15) time-based detection is what actually drives fast loss recovery, not the RTO.
  • C11 — determinism trace volume. Input: §4 per-event + C6 event count. A 4×10⁶-event run emitting one ~40-B trace line per cwnd-relevant event (a fraction of events, say ~10⁶ ACKs) → 10⁶ × 40 B ≈ 40 MB per golden run. Confirms §Scalability's "sample trace lines for very long runs" guidance — full traces are fine for short golden scenarios, not hour-long soaks.
