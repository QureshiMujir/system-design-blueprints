1. Goal

1.1 What is being built

A pluggable congestion-control engine (ccx): a reusable host/framework that mounts multiple congestion-control (CC) algorithms behind one stable vtable (CongestionControl trait, mirroring Linux tcp_congestion_ops) plus a deterministic discrete-event network simulator (ccx-sim) used to drive, compare, and conformance-test those algorithms without real networks. The deliverable is the host + shared sender machinery + testbed, not any one algorithm.

  • Engine core (ccx-core): trait + module registry + per-connection state object (CcState), algorithm hot-swap, shared sender core (cwnd vs pacing, packet conservation, bytes-in-flight, app-limited detection, send-quantum/TSO abstraction), delivery-rate estimator (Cheng/Cardwell rate-sample), RTT estimators (SRTT/RTTVAR per RFC 6298, windowed min-RTT filter), loss/ECN signal plumbing.
  • Algorithm modules (ccx-algos): NewReno (RFC 5681/6582), CUBIC (RFC 9438), BBR v1 (Cardwell), Vegas (delay-based), DCTCP (ECN-fraction). Each behind the trait; each ships a state-machine diagram + control equations + golden cwnd trace.
  • Pacer (ccx-pace): token-bucket pacer, pacing_rate = gain × BtlBw, inter-packet spacing, burst budget, cwnd-cap interaction.
  • Simulator (ccx-sim): discrete-event engine, bottleneck link (bandwidth, propagation delay), queue disciplines (DropTail, RED, CoDel, FQ-CoDel), configurable loss/reorder, dumbbell topology, deterministic seeded PRNG → bit-reproducible runs.
  • Metrics/eval (ccx-metrics): throughput, goodput, queue occupancy/bufferbloat, p50/p95/p99 RTT, loss rate, Jain fairness, convergence time, TCP-friendliness/coexistence, RTT-fairness, responsiveness.

1.2 System boundaries

  • In scope: the CC abstraction; shared sender-side accounting; estimators (RTT, delivery rate, min-RTT); the five reference modules; the pacer; the simulator + queue disciplines + topologies; the metrics harness; conformance fixtures (golden traces); fuzz harness for ACK/SACK/ECN inputs.
  • Out of scope (non-goals): a full TCP/IP stack, real sockets, NIC drivers, kernel integration, congestion signalling on the wire, retransmission buffer management, a QUIC/TLS implementation, packet payload handling. The engine consumes abstract signals (ack/sack/ecn/loss/rtt-sample/time) and emits abstract decisions (cwnd, pacing_rate, send/no-send). Transport plumbing is mocked by ccx-sim and the test harness.

1.4 Intended deployment model

  • Primary: a library crate linked into a transport (TCP-like or QUIC-like) sender, plus a simulation binary (ccx-sim) and a CLI (ccx) for batch experiments and conformance runs. No daemon, no network listener.
  • Secondary: a cdylib exposing a C ABI vtable so non-Rust transports can register modules (FFI parity with tcp_congestion_ops).
  • The simulator is the canonical environment that produces all verifiable artifacts (golden traces, fairness reports) in CI; no hardware or cloud required.

1.5 Target users / operators / developers

  • Algorithm authors: implement the trait, get a registry slot, run against the simulator, diff golden traces.
  • Transport integrators: link ccx-core, feed signals, read decisions; swap algorithms per-connection without recompiling.
  • Researchers/operators: run dumbbell/heterogeneous-RTT scenarios, compare fairness/throughput/queue, regression-gate changes.

1.10 Recommended language & exact rationale

Rust. Rationale, point by point:

  • No GC / deterministic latency: per-ACK hook runs on the data path; a GC pause would corrupt control-loop timing and the latency budget (§4). Rust gives manual control without GC jitter.
  • Reproducible math: control loops must be bit-reproducible across runs/platforms. Rust lets us forbid floating-point in the hot path and use fixed-point/integer math (Q16.16, u64 micro-units) with defined overflow semantics (checked_*/saturating_*); float nondeterminism (FMA, rounding, transcendental libm drift) is banned in the control core.
  • vtable fit: trait objects (&dyn CongestionControl) map 1:1 onto a tcp_congestion_ops-style function-pointer table; #[repr(C)] + extern "C" give a clean FFI vtable for non-Rust transports.
  • Zero-cost abstraction: per-connection CcState can be a plain struct with no hidden allocation; registry uses static dispatch internally and dynamic dispatch only at the module boundary.
  • Safety on adversarial input: ACK/SACK/ECN parsing faces malicious feedback (ACK-division, optimistic ACK); Rust's bounds-checking + #[forbid(unsafe_code)] in ccx-core/ccx-algos (unsafe confined to ccx-ffi) shrinks the memory-corruption surface.
  • Tooling: cargo, criterion, cargo-fuzz/libFuzzer, proptest, miri, cargo-deny cover bench/fuzz/property/UB/supply-chain needs.
  • Rejected: C (no borrow checker, manual lifetime hazards on per-conn state); C++ (template/UB complexity, ABI churn); Go (GC pauses on the data path, float-only math, weaker determinism story); Zig (immature fuzz/property tooling). See ADR-001.

2. Why Build This

2.1 Unique systems knowledge taught

  • The separation between a congestion-control policy (algorithm) and the sender mechanism (cwnd accounting, pacing, packet conservation, delivery-rate estimation) — the exact separation Linux encodes in tcp_congestion_ops and that most engineers never see cleanly.
  • How a single vtable must be expressive enough for loss-based (Reno/CUBIC), delay-based (Vegas), rate/model-based (BBR), and ECN-based (DCTCP) algorithms simultaneously — API design under genuine semantic tension.
  • Delivery-rate estimation (Cheng/Cardwell rate-sample): how delivered/interval_us/is_app_limited are tracked per-packet to recover bandwidth without explicit signalling.
  • Deterministic simulation of a stochastic system: making a network model bit-reproducible (fixed tick, seeded PRNG, total event ordering) so algorithm changes are diffable.
  • Fairness and coexistence as first-class, measurable properties (Jain index, CUBIC-vs-BBR coexistence, RTT-fairness).

2.2 Historical / architectural significance

  • AIMD (Jacobson 1988) saved the early Internet from congestion collapse; CUBIC is the Linux/Android default; BBR (2016) reframed CC as model-based (estimate BtlBw & RTprop) rather than loss-reactive. Building all behind one interface forces understanding of why the interface looks the way it does.
  • The tcp_congestion_ops vtable is one of the cleanest plugin architectures in any kernel; reproducing it teaches plugin-API design, ABI stability, and hot-swap.

2.3 Engineering muscles developed

  • API/vtable design under multi-paradigm pressure; ABI stability; FFI.
  • Numerical determinism and fixed-point math discipline.
  • Discrete-event simulator construction and validation.
  • Property-based + differential + fuzz testing of stateful algorithms.
  • Performance engineering of a per-ACK hot path (ns budget).

2.4 Production engineering concepts exercised

  • Backpressure (pacing as flow shaping), bounded resource usage (per-conn memory ceiling), observability (per-event trace), crash-only/replay (deterministic re-run from a seed+input log), compatibility (stable vtable across module versions).

2.6 Calibration value

Permanently raises capability in: plugin/vtable architecture, numerical determinism, transport internals, and simulation-driven verification — a combination that transfers directly to kernel networking, QUIC stacks, and any control-loop system (rate limiters, schedulers, autoscalers).

What Mastery Looks Like

  • Design a multi-paradigm plugin ABI under tension — after Phase 1 you can author a single vtable (CongestionControl) that expresses loss-based, delay-based, rate/model-based, and ECN-based control without leaking any one paradigm's assumptions into the contract, and version it additively (P3, ADR-003/004).
  • Make a stochastic system bit-reproducible — after Phase 9 you can take a queue/loss/topology model with seeded randomness and total-order it (fixed tick, single Pcg64, (time,seq,kind) ordering) so an algorithm change is diffable against a golden trace across architectures (INV-1, INV-13).
  • Forbid floating point from a control loop and prove it — after Phase 0 you can carry SRTT/RTTVAR, CUBIC's (t−K)³, and BBR gains in integer/Q16.16 math with checked/saturating semantics and an integer cbrt, and gate the ban with cross-arch hash equality (ADR-002, INV-7).
  • Recover bandwidth without explicit signalling — after Phase 3 you can implement the Cheng/Cardwell delivery-rate estimator (delivered/interval_us/is_app_limited) and a windowed min-RTT filter, and explain exactly when is_app_limited must suppress a BtlBw update (P9 §5.2, INV-5/6).
  • Reason about fairness and coexistence as measured properties — after Phase 10 you can quantify Jain fairness, RTT-fairness, convergence time, and CUBIC-vs-BBR coexistence over a steady-state window, and know why BBRv1 can starve loss-based flows on deep buffers (P13, §19.9).
  • Build a per-ACK hot path inside a nanosecond budget — after Phase 13 you can hold on_ack ≤ 200 ns median with zero hot-path allocation, cache-line-pack CcState, and gate regressions in CI (§4, INV-11).
  • Harden an untrusted feedback channel — after Phase 11 you can defend Signal Intake against optimistic-ACK, ACK-division, SACK flood, and RTT/ECN lies with byte-counted growth and bounded structures, proving 0 panics/overflow under fuzz (§Threat Model, INV-8/9).

3.2 One paragraph per box

  • Signal Intake: the only untrusted entry. Normalizes raw feedback (ACK ranges, SACK blocks, ECN CE counts, RTT samples, time) into typed AckEvent/SackEvent/EcnEvent/LossEvent/RttSample. Enforces monotonic time, rejects ACKs beyond SND.NXT, caps SACK block counts, detects ACK-division/optimistic-ACK (§Threat Model). Trust boundary: everything downstream assumes validated input.
  • Shared Sender Core: owns mechanism, not policy — cwnd (bytes), bytes_in_flight, packet conservation, app-limited detection, send-quantum/TSO abstraction, and the delivered/delivered_time bookkeeping feeding the rate estimator. Calls the active module's hooks; never embeds algorithm-specific logic.
  • Estimators: SRTT/RTTVAR (RFC 6298), windowed min-RTT filter (BBR RTprop), and the RateSample delivery-rate estimator (Cheng/Cardwell: delivered, interval_us, is_app_limited). Pure functions of validated input + prior state; deterministic.
  • Module Registry: name → constructor map; constructs per-connection module state; supports hot-swap (replace active module mid-connection while preserving CcState invariants). Equivalent to tcp_register_congestion_control.
  • Algorithm Module: one active dyn CongestionControl per connection. Implements on_ack/on_loss/on_ecn/cwnd_event/pacing_rate/ssthresh/on_rtt_update/undo. Pure policy; reads estimators + CcState, writes cwnd/ssthresh/pacing intent.
  • Pacer: token-bucket; pacing_rate = gain × BtlBw (or cwnd/SRTT fallback); produces inter-packet spacing and a burst budget; capped by cwnd. Decides send/hold. Deterministic given tick + state.
  • ccx-sim Event Queue: fixed-tick discrete-event core; total ordering of simultaneous events by (time, seq, kind); single seeded PRNG (Pcg64) for loss/reorder. Reproducibility guarantee lives here.
  • Bottleneck Link: one link with bandwidth (bytes/tick) and one-way propagation delay; serialization + propagation modeled as scheduled events.
  • Queue Discipline: DropTail | RED | CoDel | FQ-CoDel; decides enqueue/drop/mark and dequeue order; emits drops (loss) and CE marks (ECN) back into Signal Intake via feedback.
  • ccx-metrics: consumes the event stream; computes throughput/goodput, queue occupancy, RTT p50/p95/p99, loss rate, Jain fairness, convergence time, coexistence; emits the run report.
  • Run report + golden trace: the verifiable artifacts. The cwnd/ssthresh trace is byte-comparable to a committed golden file; the JSON report feeds regression gates.

6. Design Principles

  1. Mechanism/policy separation is sacred. Shared Sender Core owns cwnd accounting, bytes-in-flight, pacing math, rate estimation; the Module owns only policy (how to change cwnd/ssthresh/gain). Tradeoff: more indirection per ACK. Operational: a buggy module cannot corrupt accounting invariants. Violation: if a module mutates bytes_in_flight directly, packet conservation (INV-3) breaks and fairness measurements become meaningless.

  2. Determinism over convenience. Same (seed, scenario, build) ⇒ byte-identical trace. No floats in the control core, no wall-clock, no hashmap iteration order, no thread races in a single connection. Tradeoff: fixed-point math is fiddlier. Operational: every bug is reproducible from a seed; CI diffs traces. Violation: float FMA drift makes a CUBIC trace differ across CPUs → conformance is impossible.

  3. The vtable is the contract. CongestionControl hooks, their argument types, and call ordering are a stable ABI; modules and transports depend on it. Tradeoff: hard to evolve. Operational: versioned via CC_ABI_VERSION; additive-only within a major. Violation: reordering on_ack vs on_rtt_update silently changes every algorithm's behavior.

  4. Signals in, decisions out — nothing else crosses the boundary. Modules never do I/O, never read the clock directly (they get now), never allocate on the hot path. Tradeoff: richer context must be passed explicitly. Operational: modules are trivially unit-testable and fuzzable. Violation: a module reading the real clock breaks determinism (P2).

  5. Bounded resource usage. Per-conn memory ≤ 1 KiB + bounded sent-history ring; no unbounded SACK scoreboard growth. Tradeoff: ring eviction logic. Operational: 10⁴ flows fit in 8 GiB. Violation: unbounded scoreboard → OOM under SACK-reordering attack.

  6. Backpressure via pacing, not bursting. Sender shapes output to pacing_rate; cwnd is a cap, not a license to burst. Tradeoff: pacing adds a timer per send. Operational: avoids standing queues / bufferbloat. Violation: cwnd-only sends create line-rate bursts that overflow shallow queues (loss, RTT spikes).

  7. Observability by default. Every cwnd change, state transition, loss/ECN event, and rate sample is traceable (event log) without code changes. Tradeoff: trace volume. Operational: golden traces are the conformance medium; incidents are post-hoc replayable. Violation: silent cwnd changes can't be conformance-tested.

  8. Replayability first. A run is fully described by (scenario.toml, seed, build hash). Inputs (ack/sack/ecn streams) can be captured and replayed against a module in isolation. Tradeoff: must log inputs. Operational: a field bug from a real transport replays offline. Violation: nondeterministic inputs ⇒ unreproducible bugs.

  9. Stable, additive ABI. New hooks default to no-op; new fields appended; never reorder/repurpose. Tradeoff: deprecated fields linger. Operational: old modules keep working across minor versions. Violation: breaking the FFI vtable silently UB-crashes C transports.

  10. Integer/fixed-point everywhere in control math. Bytes in u64, time in u64 µs, rates in bytes/sec u64, gains in Q16.16; all multiply/divide via checked/saturating helpers with documented rounding. Tradeoff: precision/rounding care. Operational: no overflow, no NaN, no platform drift. Violation: cwnd * gain overflow wraps cwnd to near-zero → stall.

  11. Fail safe, not silent. Invalid signals (ACK beyond SND.NXT, time going backward) are rejected and counted; the connection degrades to conservative behavior (e.g., treat as no-ack) rather than trusting bad input. Tradeoff: dropped legitimate edge inputs. Operational: ack-division/optimistic-ack attacks bounded. Violation: trusting optimistic ACKs inflates cwnd → congestion collapse / DoS.

  12. One active algorithm per connection; hot-swap is explicit and invariant-preserving. Swap copies/clamps shared state, resets module-private state, never violates cwnd ≥ min, bytes_in_flight ≤ cwnd-window semantics. Tradeoff: swap is a defined operation, not free. Operational: A/B algorithms on live flows. Violation: swapping mid-recovery without resetting recovery state double-reduces cwnd.

  13. Conformance is golden-trace, not assertion-only. Each algorithm's behavior is pinned by a committed cwnd/state trace over a canonical scenario; any drift fails CI. Tradeoff: traces must be regenerated intentionally on real changes. Operational: prevents accidental behavior regressions. Violation: refactors silently change CUBIC's curve.

  14. Simulator realism is explicit and documented. Link/queue/loss models are simplifications with stated assumptions (fluid vs packet, no jitter unless configured). Tradeoff: not a packet-accurate ns-3 clone. Operational: results interpreted with documented caveats. Violation: over-claiming "real-world" fairness from an idealized model.

  15. Time is injected, monotonic, and µs-quantized. No component reads Instant::now() except the (testable) clock source; sim drives a virtual clock. Tradeoff: clock threading through APIs. Operational: determinism + replay. Violation: hidden time reads ⇒ nondeterminism + clock-skew bugs.

8.4 RTT estimation (RFC 6298 + min-RTT filter)

on first sample:   SRTT = R ; RTTVAR = R/2
subsequent:        RTTVAR = (1-β)·RTTVAR + β·|SRTT - R|        β=1/4
                   SRTT   = (1-α)·SRTT   + α·R                 α=1/8
                   RTO    = SRTT + max(G, K·RTTVAR)            K=4, G=clock granularity
Karn:              ignore R from retransmitted segments (RttSample.is_retrans ⇒ drop)
min-RTT (RTprop):  windowed min over last W (default 10 s); refresh forces sample (BBR PROBE_RTT)

All α,β,K applied in fixed-point (α=1/8 ⇒ shift; β=1/4 ⇒ shift). RTO bounded [200 ms, 60 s] (config).

8.5 Loss-signal model (shared with loss-recovery layer)

Engine consumes LossEvent from a loss detector (dupack-threshold / SACK / RACK-TLP time-based / RTO). It does not implement RFC 8985 itself (that is the transport/224's job) but defines the contract: kind ∈ {FastRetx, RackTlp, Rto}, lost_bytes, monotonic now_us. Modules react via on_loss. DSACK / spurious detection arrives as an undo signal triggering CongestionControl::undo.

8.6 ECN / AccECN model

ECT(0)/ECT(1)/CE codepoints (RFC 3168); CE feedback as a counter (ce_count) per EcnEvent. DCTCP semantics (RFC 8311) use the fraction of CE-marked bytes. AccECN full negotiation (separate ECT0/ECT1/CE counters, ACE field) is PhaseDeferred("FINAL_BLUEPRINT §8.6"); Phase 8 implements the classic single-CE-counter path sufficient for DCTCP.

8.7 Delivery-rate estimator (Cheng/Cardwell rate-sample)

Per sent packet store PacketMeta { delivered_at_send:u64, delivered_time_us:u64, is_app_limited:bool, size:u64, sent_us:u64 } in a bounded ring. On ACK:

rs.delivered      = C.delivered - pkt.delivered_at_send         -- bytes delivered in the interval
rs.interval_us    = max( C.now_us - pkt.delivered_time_us ,     -- ack-rate interval
                         pkt.sent_us_of_latest - pkt.sent_us )  -- send-rate interval; take max
rs.is_app_limited = pkt.is_app_limited
delivery_rate_bps = rs.delivered * 1e6 / rs.interval_us         -- fixed-point µs

is_app_limited set when the app had < cwnd bytes to send and inflight < cwnd (don't let idle gaps depress BtlBw). BtlBw = windowed-max of delivery_rate over ~10 RTTs (BBR).

8.8 Control equations per algorithm

NewReno (RFC 5681/6582):

slow start:   cwnd += SMSS per ACK (or += acked, ABC)              until cwnd ≥ ssthresh
cong-avoid:   cwnd += SMSS·SMSS/cwnd per ACK   (≈ +1 SMSS / RTT)
loss(FR):     ssthresh = max(FlightSize/2, 2·SMSS); cwnd = ssthresh (+3 SMSS infl. during recovery)
RTO:          ssthresh = max(FlightSize/2, 2·SMSS); cwnd = 1·SMSS; → slow start

CUBIC (RFC 9438):

W_cubic(t) = C·(t − K)^3 + W_max          C = 0.4 (fixed-point), t = time since last reduction
K          = cbrt( W_max·(1−β_cubic)/C )  β_cubic = 0.7
on loss:    W_max = cwnd; cwnd = cwnd·β_cubic ; recompute K
TCP-friendly region: W_est = W_max·β + 3·(1−β)/(1+β)·(t/RTT); cwnd = max(W_cubic, W_est)
fast convergence:  if W_max < W_last_max → W_max·=(1+β)/2 (yield to new flows)

Cube root via integer Newton iteration (no libm); C and β_cubic in Q16.16.

BBR v1 (Cardwell):

model:      BtlBw = max filter(delivery_rate, 10 RTT); RTprop = min filter(rtt, 10 s)
BDP         = BtlBw · RTprop
pacing_rate = pacing_gain · BtlBw ; cwnd = cwnd_gain · BDP (cwnd_gain=2)
STARTUP:    pacing_gain = cwnd_gain = 2/ln2 ≈ 2.885 ; exit when BtlBw plateaus (3 rounds <25% growth)
DRAIN:      pacing_gain = 1/2.885 ; drain queue until inflight ≤ BDP
PROBE_BW:   8-phase gain cycle [5/4, 3/4, 1,1,1,1,1,1] ; one RTT each
PROBE_RTT:  every 10 s if min-RTT not updated: cwnd = 4 pkts for max(200 ms,1 RTT) to re-measure RTprop

Vegas (delay-based):

expected = cwnd / BaseRTT        (BaseRTT = min RTT)
actual   = cwnd / RTT            (current sample)
diff     = (expected − actual)·BaseRTT     -- in packets
if diff < α:  cwnd += 1   (per RTT)
if diff > β:  cwnd −= 1
else:        cwnd unchanged          α=2, β=4 packets

DCTCP (ECN-fraction):

F        = fraction of CE-marked bytes this window
α        = (1−g)·α + g·F            g = 1/16
on marks: cwnd = cwnd·(1 − α/2)     -- proportional, gentler than Reno halving
no marks: behave like Reno cong-avoid

11.1 The vtable: CongestionControl

/// Stable per-connection congestion-control policy vtable (mirrors tcp_congestion_ops).
/// One active impl per CcState. All hooks: no alloc, no block, no wall-clock (INV-11).
pub trait CongestionControl {
    fn name(&self) -> &'static str;                 // registry key, e.g. "cubic"
    fn init(&mut self, st: &mut CcState);           // set IW, ssthresh=∞, private state
    fn on_ack(&mut self, st: &mut CcState, rs: &RateSample, now_us: u64); // primary growth hook
    fn on_rtt_update(&mut self, st: &mut CcState, srtt_us: u64, min_rtt_us: u64); // optional
    fn on_loss(&mut self, st: &mut CcState, ev: &LossEvent);              // FastRetx/Rto/RackTlp
    fn on_ecn(&mut self, st: &mut CcState, ce_count: u64, acked: u64);    // ECN/AccECN response
    fn cwnd_event(&mut self, st: &mut CcState, ev: CwndEvent);            // init/idle/tx-start/loss-recovery
    fn ssthresh(&mut self, st: &CcState) -> u64;    // value to set on loss (mechanism reads it)
    fn pacing_rate(&self, st: &CcState) -> u64;     // bytes/sec; default cwnd*MSS/SRTT
    fn undo(&mut self, st: &mut CcState);           // spurious-loss: restore snapshot
    fn min_cwnd(&self) -> u64;                       // floor (INV-4); default provided = 2 * SMSS
}
pub enum CwndEvent { Init, TxStart, Idle, LossRecoveryEnter, LossRecoveryExit, PrrUpdate }

Ownership: module owns its private state inline; CcState is borrowed &mut per call (no aliasing). Mutation: only via these hooks. Concurrency: !Sync; one thread per conn. Persistence: none (in-memory). Compatibility: additive-only; new hooks get default impls; CC_ABI_VERSION bumped on any signature change.

12.6 Pitfalls

Manifestation Root cause Debug Signal Recovery

12.7 Performance Concerns

Fixed-point mul/div compile to a few integer ops; cbrt is the only loop — cache result of K in CUBIC (Phase 6) so per-ACK cost stays ≤ 200 ns. No allocation in ccx-time.

12.8 Edge Cases

Div-by-zero (interval/RTT = 0 → caller clamps to 1 µs); Q16_16 of value > 65535 (saturate + flag); negative results impossible (unsigned domain; "diff" handled as signed delta in algos).

12.9 Failure Analysis

A float sneaking into control math breaks INV-1 silently and only surfaces as a cross-arch conformance failure. Containment: the grep gate + cross-arch determinism job catch it at PR time. Forensic artifact: differing trace line + arch pair.

12.10 Operational Notes

build_hash (git SHA + toolchain) is stamped into every trace/report header so any artifact is traceable to a build. Toolchain pin is the single most important reproducibility control.

20. Phase 8 — Vegas (Delay-Based) + DCTCP (ECN-Fraction) Modules

20.1 Objectives

Add a delay-based algorithm (Vegas) and an ECN-based algorithm (DCTCP) to prove the vtable spans all four CC paradigms (loss/cubic/rate/delay/ECN). Exercises on_rtt_update and on_ecn hooks fully.

20.2 Detailed Implementation Steps

  • ccx-algos/vegas.rs per §8.8 (delay-based expected-vs-actual control per P6): track BaseRTT = min RTT; per RTT compute diff = (cwnd/BaseRTT − cwnd/RTT)·BaseRTT (in packets, fixed-point); α=2, β=4; adjust cwnd ±1 per RTT within [α,β] band; slow-start exits to CA when diff > γ (γ=1). Uses on_rtt_update for RTT, on_ack for cwnd timing.
  • ccx-algos/dctcp.rs per §8.8 (ECN-fraction proportional response per P10/RFC 8257): maintain α (EWMA of CE fraction, g=1/16); on_ecn(ce_count, acked) updates F = ce_count/acked per window, α = (1−g)α + g·F; on marked window cwnd ·= (1 − α/2) (fixed-point); unmarked windows behave Reno-like (CA). Requires ECN feedback path (§8.6, classic single-CE-counter; clamp per INV-8/§8.10).
  • Both register; goldens vegas_delay.trace (on a buffered link) and dctcp_ecn.trace (on ecn_dctcp.toml with RED/CoDel marking).
  • AccECN full negotiation remains PhaseDeferred("FINAL_BLUEPRINT §8.6"); DCTCP uses classic ECN counter.

21. Phase 9 — Deterministic Discrete-Event Simulator, Queue Disciplines, Topologies

21.1 Objectives

  • ccx-sim/event.rs + scheduler.rs: BinaryHeap<Reverse<Event>>; events ordered by (time_us, seq, kind) (INV-13); seq is a monotonic tiebreaker; single Pcg64 seeded from scenario (ADR-007). Virtual clock = now_us from the next event.
  • ccx-sim/link.rs: BottleneckLink { bandwidth_bps, prop_delay_us }; model serialization (pkt_size·1e6/bandwidth µs) + propagation as scheduled Arrive events; one in-flight serialization at a time.

  • ccx-sim/loss.rs: independent (Bernoulli) and burst (Gilbert-Elliott) loss; reorder via delayed Arrive; all draws from the single seeded PRNG (INV-1).
  • ccx-sim/topology.rs + flow.rs: dumbbell (N senders → shared bottleneck → N receivers); per-flow RTT via differing prop delays (heterogeneous RTT); wire each flow's engine Connection to send/ack events; ECN marking from qdisc → EcnEvent.

25.7 Performance Concerns

Per-ACK: target a handful of integer ops + ≤ 1 divide; ensure CcState+module-private ≤ 1 cache line set; branch-predict the valid-ACK path. Sim: heap ops dominate → small Event, arena packets, batched metrics; consider shard-per-core for throughput of independent runs (not within a run — determinism). Tail latency (p99 per-ACK) driven by rare cbrt (CUBIC loss) and PROBE_RTT bookkeeping (BBR) — both off the common path.

25.8 Edge Cases

Benchmarks on a noisy CI runner (use criterion's outlier filtering; gate on median); aarch64 weaker single-core (separate threshold or relative gate); musl vs glibc behavior diffs (musl is the release target); very long runs (event seq u64 won't wrap in practice; guarded); 10⁴ flows stressing the heap (memory + ev/s edge).

25.9 Failure Analysis

A perf regression that ships degrades every embedding transport's data path; a determinism regression silently invalidates conformance. Detection: criterion + cross-arch determinism gates block the PR. Blast radius: all consumers (perf) / all goldens (determinism). Containment: gates are mandatory CI. Postmortem: flamegraph diff (perf) or first-diverging-event bisect (determinism), documented in docs/performance/ and docs/failure-analysis/nondeterminism.md.

Compatibility & Versioning

  • Wire compatibility: N/A — the engine has no wire format (it consumes/produces abstract signals/decisions). The signal/decision types (§11.3) are the analog; #[non_exhaustive] allows additive growth.
  • ABI compatibility (the real contract): CongestionControl (Rust) and CcxOps (C, §12) are versioned by CC_ABI_VERSION. Additive-only within a major: new hooks get default/no-op impls; new struct fields appended; never reorder/repurpose/remove. Breaking change ⇒ major bump + AbiMismatch rejection of old modules.
  • Storage compatibility: N/A (no persistence) — except golden traces and RunReport.json, whose formats are versioned (report_version, trace header) and forward-additive.
  • Schema evolution: scenario.toml schema is versioned; unknown keys warn (forward-compat); new keys get defaults (backward-compat).
  • API stability: public Rust API follows semver; #[deprecated] for one minor before removal in a major. Hot-swap semantics (INV-10/15) are stable.
  • Migration guarantees: a golden-trace change is a reviewed, documented migration; never silent. CHANGELOG.md flags every ABI/behavior change.
  • Deprecation policy: deprecate → warn (≥1 minor) → remove (major). Deferred features (AccECN, BBRv2, kernel binding) become additive when implemented.
  • Semantic versioning: MAJOR.MINOR.PATCH; MAJOR = ABI/behavior break; MINOR = additive (new algo/hook/metric); PATCH = bugfix (must not change goldens unless flagged).
  • Rolling-upgrade guarantees: an embedding transport can upgrade libccx within a major without recompiling C modules (ABI additive); modules built for an older minor keep working.

Scalability Analysis

  • Bottlenecks: (sim) the event heap (O(log n) per event) and metrics aggregation; (engine) per-ACK divide and dynamic dispatch.
  • Scaling ceilings: single-thread sim ≈ 5–20 M ev/s; ~10⁴ flows per run within 8 GiB (heap + per-conn state). Beyond that → shard into independent runs.
  • Horizontal scaling: independent scenarios/seeds run on separate cores/machines (embarrassingly parallel); results aggregated offline. Determinism preserved (each run self-contained).
  • Vertical scaling: bigger machine → more flows per run (memory-bound) and faster single-run wall time (CPU-bound on the heap).
  • Sharding / partitioning: shard runs (not a single run — within-run parallelism would break INV-1). Optionally partition flows across sub-simulators only if they don't share a bottleneck (independent → still deterministic per shard).
  • Replication pressure: N/A (no replication; no persistence).
  • Coordination overhead: zero within a run (single thread); zero across runs (independent).
  • Network fanout: N/A (simulated); dumbbell fanout is the modeled topology — O(N) flows on one bottleneck.
  • Scheduler saturation: the event loop saturates one core; more cores = more concurrent independent runs, not a faster single run.
  • Storage growth: traces/reports grow with run length × flows; mitigate by sampling trace lines for very long runs (golden scenarios kept short).
  • Metadata scaling: per-conn CcState (≤ 1 KiB) × flows is the memory driver; registry is O(#algorithms) (tiny). Sent-history ring bounded per conn.
  • Embedded-engine scaling: in a real transport, the engine scales with #connections; per-conn cost (memory ≤ 1 KiB, per-ACK ≤ 200 ns) is the relevant ceiling — e.g., 10⁶ connections ⇒ ≤ ~1 GiB CC state + ≤ 200 ns × ACK-rate CPU.

Mental Models & First Principles

The compressed intuitions an expert holds about congestion control. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — CC is a control loop estimating the bottleneck's bandwidth-delay product. The "right" amount of in-flight data is BDP = BtlBw × RTprop; everything else (cwnd growth laws, pacing) is a search strategy for that operating point. Predicts: hold inflight ≈ BDP and you get full throughput with an empty queue; exceed it and you only add queueing delay, not goodput. Bug without it: treating cwnd as "go faster" rather than "fill the pipe", producing standing queues that look like throughput wins but are bufferbloat. Applied: §8.7 (BtlBw·RTprop), Phase 7 (BBR), §Back-of-Envelope Capacity Model.
  • MM2 — Loss and delay are proxies for the same hidden state (queue occupancy), measured at different points on the curve. Loss fires when the buffer overflows (late, coarse); delay rises as the queue fills (early, noisy); ECN is an explicit early signal. Predicts: a delay-based algo (Vegas) yields to a loss-based one (Reno) because Reno keeps pushing until the buffer is full, past where Vegas already backed off. Bug without it: expecting Vegas and Reno to share a link fairly. Applied: §8.8 (Vegas vs NewReno), Phase 8 (§20.9 coexistence), §Comparative Architecture.
  • MM3 — The sender mechanism and the control policy are different machines. cwnd accounting, packet conservation, and rate estimation are mechanism (always correct); how to move cwnd is policy (algorithm-specific). Predicts: a buggy algorithm can produce bad throughput but must never corrupt bytes_in_flight. Bug without it: a module that mutates inflight directly, making every fairness number meaningless. Applied: design principle 1 (§6), §11.1/§11.2, Phase 2.
  • MM4 — Determinism is a property you engineer, not one you get. A network is stochastic, but a model of one is reproducible iff every nondeterminism source (float rounding, hashmap order, multiple RNGs, usize width) is removed. Predicts: a single hidden f64 makes a CUBIC trace differ across CPUs — invisible until a cross-arch diff. Bug without it: "works on my machine" conformance that silently drifts. Applied: INV-1/INV-13, ADR-002/007/010, Phase 0 & Phase 9.
  • MM5 — A windowed min/max filter is the right tool for a quantity that drifts but whose extreme is the truth. RTprop is the minimum RTT (queueing only adds delay); BtlBw is the maximum delivery rate (everything else under-measures). Both need a bounded window so they re-learn after a route/bandwidth change. Predicts: forget to expire the window and min-RTT sticks high after a path shortens, starving cwnd. Bug without it: a min-RTT that never refreshes (no PROBE_RTT). Applied: INV-6, §8.4/§8.7, Phase 3 & Phase 7.
  • MM6 — cwnd is a cap; pacing is the smoother. cwnd bounds how much is outstanding; pacing controls how fast it leaves. A full cwnd released as a line-rate burst overflows a shallow queue even when the average rate is fine. Predicts: cwnd-only senders cause loss and RTT spikes on shallow buffers that a paced sender at the same cwnd avoids. Bug without it: bursting to cwnd and blaming the queue. Applied: design principle 6 (§6), §8.8 (BBR pacing_rate), Phase 4.
  • MM7 — Untrusted feedback can drive the loop; therefore the loop's inputs are an attack surface. ACKs, SACKs, and ECN counts come from the peer; an optimistic-ACK inflates cwnd, ACK-division speeds growth, a tiny RTT lie collapses the RTO. Predicts: byte-counted growth (not per-ACK increments) neutralizes ACK-division; rejecting acks beyond SND.NXT neutralizes optimistic-ACK. Bug without it: a trusting intake that a malicious peer turns into a congestion-collapse/DoS vector. Applied: INV-8/INV-9, §Threat Model (T1–T8), Phase 11.
  • MM8 — Fairness is only meaningful over a steady-state window, and only between like signals. Jain's index on a transient (warm-up, a flow mid-join) lies; comparing a delay-based and a loss-based flow measures the paradigm gap, not unfairness. Predicts: a fairness number computed including warm-up "flaps"; RTT-bias means equal-cwnd flows at different RTTs get unequal throughput. Bug without it: declaring an algorithm unfair from a measurement window that includes convergence. Applied: §22.2 (steady-state window), P13, Phase 10.
  • MM9 — Overflow is a control bug, not just a safety bug. cwnd × gain wrapping a u64 doesn't crash — it silently sets cwnd near zero and stalls the flow. Predicts: unchecked fixed-point multiply on a high-BDP path stalls exactly when throughput should be highest. Bug without it: a "random" stall that only appears at large windows. Applied: INV-7, ADR-002, Phase 0 & Phase 6 (CUBIC (t−K)³).
  • MM10 — Hot-swap is a state-migration problem, not a pointer swap. Replacing a connection's algorithm mid-flight must clamp shared state into the new module's valid range and reset recovery flags, or the new module double-reduces cwnd. Predicts: swapping during Recovery without resetting flags halves cwnd twice. Bug without it: an A/B test that corrupts the flow it was meant to measure. Applied: INV-10/INV-15, design principle 12 (§6), Phase 1.

  • TCP NewReno (RFC 5681) made the AIMD choice: react to loss with a multiplicative cut and probe with additive increase. It wins where the bottleneck buffer is shallow and loss is a timely congestion signal, and it is the irreplaceable TCP-friendliness baseline every other algorithm is judged against (our Phase 5 golden). Its niche today is correctness reference, not deployment.
  • CUBIC (RFC 9438) changed one thing: make window growth a function of absolute time since the last loss, not RTTs, so throughput is RTT-independent on long-fat networks. That wins on high-BDP WAN paths where Reno's RTT bias starves long-RTT flows — which is why it is the Linux/Android default. It still fills the buffer (loss-based), so it can cause bufferbloat without AQM.
  • BBR v1 (Cardwell et al., ACM Queue 2016; Google) rejected loss as the primary signal entirely, modeling the path as BtlBw × RTprop and pacing to it. It wins on lossy high-BDP paths (e.g. WAN, wireless) where loss is not congestion — Google's published YouTube/B4 deployment (2016–2017) showed throughput gains on such paths. Its documented cost is RTT-unfairness and aggression against loss-based flows on deep buffers (our §19.9), which BBRv2 (deferred §19.10) addresses with inflight_hi/lo.
  • TCP Vegas (Brakmo & Peterson 1995) made the delay-based choice: infer the queue from RTT inflation and back off before loss. It wins when every flow is Vegas (low latency, no induced loss), but loses catastrophically sharing a buffer with loss-based flows, which keep pushing past where Vegas yields (MM2). Its niche is homogeneous/controlled environments.
  • DCTCP (Alizadeh et al., SIGCOMM 2010; RFC 8257) used ECN not as a binary signal but as a proportional one — reduce cwnd by a fraction tracking the mark rate α. It wins in a single-administrator datacenter fabric with ECN-marking switches, holding sub-millisecond queues; it requires that controlled environment (ECN-capable AQM, no AccECN needed) and is not a general-Internet algorithm.

Back-of-Envelope Capacity Model

Numbers an expert computes from §4 (System Constraints) before designing. Each is derived; the §4 input is named.

  • C1 — cwnd ceiling at the BDP (the operating point). Input: §4 RTT model (1 µs–10 s) and a representative WAN link.   • C2 — sent-history ring size. Input: §4 "Sent-history ring ≤ 64 KiB at cwnd ≤ 1024 pkts" (M5). 1024 entries × sizeof(PacketMeta); with PacketMeta ≈ 40 B (5×u64-ish per §11.4) → 1024 × 40 = 40 KiB < 64 KiB ✓. Confirms the M5 ceiling holds for the C1 cwnd (417 pkts) with headroom.
  • C3 — per-connection memory and the 10⁴-flow run. Input: §4 "≤ 1 KiB CcState+module" (M4) and "≥ 10⁴ flows in 8 GiB" (M10). 10⁴ × (1 KiB CcState + 64 KiB ring) = 10⁴ × 65 KiB ≈ 650 MiB. Matches the §Scalability Analysis claim; the ring, not cwnd state, dominates if kept at 64 KiB (10⁶ × 64 KiB = 64 GiB — so a high-conn transport must shrink the ring).
  • C5 — per-ACK CPU budget vs ACK rate. Input: §4 "per-ACK ≤ 200 ns" (M1). One core at 1 s ÷ 200 ns = 5×10⁶ ACK-events/s. At ~1 ACK per 2 packets (delayed ACK) and 1500-B packets, that services 5e6 × 2 × 1500 × 8 ≈ 120 Gb/s of aggregate ACK-clocked traffic per core before the CC hook itself is the bottleneck.
  • C6 — simulator wall-time for a scenario. Input: §4 "≥ 5 M events/sec" (M3). A 60 s-sim-time, 2-flow, 100 Mb/s dumbbell at ~1500-B packets generates ≈ (100e6/8/1500) × 60 × 2 flows × ~4 events/pkt (send/arrive/dequeue/ack) ≈ 4×10⁶ events. At 5 M ev/s → ≈ 0.8 s wall-time. CI can run hundreds of such scenarios per minute.
  • C7 — standing queue delay from buffer size. Input: §4 link model + a tail-drop buffer sized at 1×BDP. queue_delay = buffer_bytes ÷ link_rate. For a 625,000 B buffer (= 1 BDP, C1) at 100 Mb/s: 625,000 × 8 ÷ 100e6 = 50 ms of added delay when full — doubling the 50 ms RTT. This is the bufferbloat MM6/MM1 predicts and what CoDel (§4 target ≤ 5 ms, M9) caps.
  • C8 — CoDel target vs BDP. Input: §4 "CoDel sojourn ≤ 5 ms" (M9). 5 ms at 100 Mb/s = 5e-3 × 100e6 ÷ 8 = 62,500 B ≈ 42 MSS of standing queue — i.e. CoDel holds the queue to ~10% of the C1 BDP, the quantitative meaning of "controlled delay".
  • C9 — Reno throughput from loss (Mathis et al.). Input: §4 loss model + C1 path. Mathis approximation throughput ≈ MSS/RTT × √(3/2) / √p. At MSS=1500 B, RTT=50 ms, loss p = 10⁻⁴: (1500×8/0.050) × 1.22 / 0.01 = 240,000 × 122 ≈ 29 Mb/s — i.e. Reno cannot fill the 100 Mb/s C1 pipe at that loss rate, the exact long-fat-network problem CUBIC/BBR exist to solve.
  • C10 — RTO floor vs RTT. Input: §4 "RTO bounded [200 ms, 60 s]" and the 50 ms RTT. The 200 ms floor is 4× the path RTT — a spurious-timeout guard; a flow with 50 ms RTT waits ≥ 200 ms before an RTO, so RACK-TLP (P15) time-based detection is what actually drives fast loss recovery, not the RTO.
  • C11 — determinism trace volume. Input: §4 per-event + C6 event count. A 4×10⁶-event run emitting one ~40-B trace line per cwnd-relevant event (a fraction of events, say ~10⁶ ACKs) → 10⁶ × 40 B ≈ 40 MB per golden run. Confirms §Scalability's "sample trace lines for very long runs" guidance — full traces are fine for short golden scenarios, not hour-long soaks.

Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build congestion control for the same goal. Each: sketch, winning regime, the real system embodying it, why this blueprint rejected it.

A1 — Explicit router feedback (rate stamped by the network). The router computes each flow's fair rate and writes it into the packet; the sender obeys.

  sender ──data──▶ [router: compute fair-share, stamp rate field] ──▶ receiver
     ▲                                                                   │
     └──────────── feedback carries explicit per-flow rate ─────────────┘
  • Wins: datacenters or single-administrator fabrics where every router cooperates and can be upgraded — convergence is near-instant and fairness is exact, with no buffer-filling search.
  • Real system: XCP (Katabi et al., SIGCOMM 2002) and RCP embody explicit per-flow rate feedback; DCTCP (RFC 8257) is a deployed partial form (1-bit ECN feedback rather than a full rate).
  • Rejected because: it requires changing every router on the path — impossible on the public Internet and outside this engine's scope (the engine consumes abstract signals and assumes commodity routers; only the ECN-fraction slice, DCTCP, is in scope via §8.6).

A2 — Centralized / scheduled bandwidth allocation (no per-flow control loop). A controller with a global view assigns bandwidth to flows; endpoints do not run an independent AIMD loop.

   ┌─────────── central controller (global topology + demand) ───────────┐
   │ allocates rate per flow, pushes schedules                            │
   └───────┬───────────────┬───────────────┬───────────────┬─────────────┘
        flow A           flow B           flow C          flow D   (obey, no probing)
  • Wins: a private WAN whose operator controls all endpoints and switches and wants near-100% utilization with engineered fairness — global optimization beats distributed probing.
  • Real system: Google's B4 SDN WAN (Jain et al., SIGCOMM 2013) centrally schedules inter-DC bandwidth; endpoint CC becomes secondary.
  • Rejected because: it presumes a global controller and administrative control of the whole network — the antithesis of an end-to-end, per-connection pluggable engine. ccx deliberately models the endpoint control loop; centralized allocation is a different system class.

A3 — Monolithic, single-algorithm sender (no vtable, algorithm compiled in). One congestion controller is hard-coded into the sender; switching it means recompiling, and the mechanism/policy split is collapsed.

   ┌──────────────── sender (one fixed algorithm) ────────────────┐
   │  cwnd accounting + growth law + pacing all interwoven inline  │
   └──────────────────────────────────────────────────────────────┘
  • Wins: an embedded/appliance sender that ships exactly one algorithm forever, where the indirect call per ACK and the API surface are pure overhead and inlining the whole controller is fastest.
  • Real system: most early/textbook TCP stacks (e.g. classic BSD TCP) embedded Reno directly before Linux introduced tcp_congestion_ops (the pluggable framework B4/R1 study).
  • Rejected because: the entire point of this project is the pluggable host that mounts five paradigms behind one stable vtable and hot-swaps them (§1.1, design principle 3, Phase 1). A monolith forecloses comparison, hot-swap, and external modules — the deliverable itself.
