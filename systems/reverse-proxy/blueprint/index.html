Project Number: 82

Project Name: Reverse Proxy

1. Goal & Scope

Build a Layer-7 (application-layer) reverse proxy / HTTP load balancer: a single event-driven process that terminates downstream client connections (HTTP/1.1, HTTP/2, HTTP/3, WebSocket, SSE), applies routing, rewriting, caching, authentication, and WAF policy to each request, selects a healthy upstream via a pluggable load-balancing algorithm, and forwards the request over a pooled upstream connection (HTTP/1.1 keep-alive or HTTP/2 multiplexed), returning the response byte-faithfully to the client. The system is request-aware end-to-end — every stage inspects or mutates the request/response; blind byte-forwarding with only a connection-selection algorithm is a Layer-4 load balancer, a strictly smaller system (contrast in §33 Comparative Architecture Table).

In-scope Phase-0 deliverable (numbered modules/crates):

  1. revp-core — shared types, config schema, error taxonomy, metrics registry.
  2. revp-proto-h1 — HTTP/1.1 wire codec (request/response framing, chunked transfer-encoding, trailers).
  3. revp-router — host/path/method matcher, longest-prefix radix tree.
  4. revp-upstream — connection pool, round-robin selection, active health check.
  5. revp-observe — structured JSON access log, RED counters.
  6. revp-control — SIGHUP-triggered hot reload of the route table.
  7. revp-bin — the revp binary; wires the above into a Tokio multi-threaded runtime.

System boundaries:

  • Provides — connection termination and framing for five protocol surfaces; routing; request/response transformation; RFC 9111 caching; TLS termination, SNI routing, and ACME; authentication (Basic, JWT, OAuth introspection, mTLS); a WAF rule engine; sandboxed edge programs (Wasm, Lua); load balancing (round-robin, least-connections, power-of-two-choices, consistent hashing); active and passive health checking; hot configuration reload; an mTLS-only control plane.
  • Delegates — DNS resolution (hickory-dns); cryptographic primitives (rustls / aws-lc-rs); bounded-cost regex compilation (the Regex-Engine reference design, cited not re-specified); token-bucket rate limiting (the Rate-Limiter reference design); Wasm sandbox semantics (the Sandbox-Execution reference design).
  • Does NOT provide — service-mesh sidecar injection; a Kubernetes CRD control plane; a UI or dashboard; log storage or analytics (ships structured logs, does not retain them); origin server logic; DNS hosting; certificate-authority operation (ACME client only, never a CA).

Non-goals: not a forward proxy (no CONNECT-tunnel-everywhere default posture); not a monetized API gateway (no billing, no developer portal); not a CDN edge (no anycast, no global PoP orchestration — deferred, §37).

Deployment model: single static binary per node; stateless except the in-process cache and connection pools; horizontally scaled behind DNS or an L4 balancer; configuration distributed via file, HTTP pull, or xDS (deferred, §37).

Target users/operators: platform/SRE teams operating the ingress tier of a multi-service backend; on-call engineers triaging routing, cache, or TLS incidents; security engineers tuning WAF rules.

What later phases unlock: §17–§18 (TLS + ACME) unlock public HTTPS without a manual certificate pipeline; §19–§20 (auth + WAF) unlock authenticated, defended multi-tenant ingress; §21 (edge programs) unlocks per-tenant logic without redeploying the binary; §22 (HTTP/2/3, gRPC, WebSocket, SSE) unlocks protocol parity with NGINX/Envoy; §23 (hot reload + control plane) unlocks zero-downtime operations.

Recommended language: Rust, edition 2024, on the Tokio multi-threaded runtime. Rationale: no stop-the-world GC pause competes with the request-forwarding hot path, and a GC pause directly inflates the p99 added-latency metric that defines this system (§4); the borrow checker statically forecloses the use-after-free and data-race classes that dominate the historical CVE record of C-based proxies (NGINX, HAProxy, Apache httpd); a mature async HTTP/TLS/QUIC ecosystem (hyper, rustls, quinn) already exists, so the project builds a proxy, not a runtime. Rejected — Go: a moving, stop-the-world-capable GC runs on the same path serving 100K rps/core (§4), and GC pause tail directly inflates p99; C: memory safety is the dominant historical bug class in this exact domain, and hand-rolled epoll/kqueue reimplements what Tokio already hardened; C++: RAII narrows but does not statically foreclose the same memory-safety class Rust forecloses at compile time.

Prerequisites: HTTP semantics per RFC 9110/9111/9112 (§5); TLS 1.2/1.3 handshake mechanics, SNI, ALPN, session resumption; Rust async fundamentals (futures, Pin, the Send + 'static bound, structured cancellation via tokio::select!); ability to read a packet capture.

Estimated timeline: Phase 0 in 4 weeks; the full 12-phase system in 8–9 months (per-phase durations in Appendix B).

Deferred features (flagged here; resolved with anchor, phase, and un-defer trigger in §37 Deferred Features Register): xDS control-plane adapter PhaseDeferred("§37"); Encrypted Client Hello (ECH) PhaseDeferred("§37"); hedged requests PhaseDeferred("§37"); request mirroring PhaseDeferred("§37"); gRPC-Web translation PhaseDeferred("§37"); kernel TLS (kTLS) offload PhaseDeferred("§37"); multi-tenant control-plane RBAC PhaseDeferred("§37").

2. Why Build This

A reverse proxy is the one component every request touches in a multi-service backend, and it teaches request-lifecycle engineering more densely than almost any other systems project because it must get parsing, concurrency, TLS, caching, and failure handling correct simultaneously, on the hot path, at low latency.

  • Teaches event-driven I/O at scale — one thread serving tens of thousands of concurrent connections through Tokio's epoll/kqueue reactor, not a thread-per-connection model.
  • Teaches protocol correctness under adversarial input — HTTP/1.1 request smuggling, HTTP/2 HPACK bombs, and slowloris are not academic; they are the CVE classes every production proxy has shipped and patched.
  • Teaches the full HTTP caching model (RFC 9111) as a state machine, not a folk heuristic — Vary, validators, freshness, and stale-while-revalidate interact non-trivially.
  • Teaches load-balancing theory as engineering — round-robin, least-connections, power-of-two-choices, and consistent hashing each have a provable regime where they win and lose (§33).
  • Teaches defense-in-depth under a sandboxing budget — edge programs must be resource-bounded by the runtime, not by the program's cooperation, the same problem as any multi-tenant plugin system.
  • Teaches zero-downtime operations — hot-reloading a live configuration without dropping an in-flight request is a distributed-systems problem (generation-tagged state, reference counting, graceful drain) disguised as a single-process feature.

Historically this is the component NGINX (2004), HAProxy (2001), Envoy (2016), and Pingora (2024, Cloudflare) were each built to own rather than rent — the economics of routing billions of requests/day through a vendor's black box versus a team's own code are why every hyperscaler eventually writes one. Cross-links: a Load-Balancer design is a strict subset of this one (request awareness removed, connection selection only); an API-Gateway design is a strict superset (this proxy plus billing, a developer portal, and API-key lifecycle). Building this system first is the correct calibration point for either.

What Mastery Looks Like:

  • Explain, byte-for-byte, why the HTTP/1.1 codec (§12) must reject ambiguous Transfer-Encoding/Content-Length pairs, and reproduce the CL.TE/TE.CL smuggling attack from first principles.
  • Derive — not recite — why power-of-two-choices (§14) beats round-robin under heterogeneous backend latency, citing Mitzenmacher (§5).
  • Trace a cached response through every RFC 9111 clause that permitted or forbade its storage and reuse (§16).
  • Explain the TLS 1.3 handshake and SNI-based certificate selection well enough to debug a stapled-OCSP failure blind, from a packet capture (§17).
  • Reason about the blast radius of a compromised edge program and why fuel, epoch interruption, and host-function allow-listing (§21) bound it to a single request.
  • Design a hot-reload protocol that provably never drops an in-flight request (§23), and explain why a naive "swap the global" implementation fails under concurrency.
  • Justify, with a derived number, why the proxy's added p99 latency budget (§4, §34) forecloses certain implementation choices (synchronous DNS, blocking mutexes on the hot path) outright.

A — Downstream Clients. Untrusted, trust boundary #1. Five protocol surfaces multiplex at the TLS/ALPN layer; the proxy never assumes a well-behaved client.

B — Listener. One shard per core via SO_REUSEPORT (ADR-17) to avoid a single accept-queue bottleneck at the 100K-rps/core target (§4). Performs the TLS handshake and demultiplexes by ALPN into the h1/h2/h3 codec chosen for the connection.

C — Request Pipeline. The concurrency boundary is one Tokio task per connection; stages exchange no mutable state except the read-only Arc<Config> snapshot captured at accept time (invariant I1, §7). This is what makes hot reload (H) safe without per-request locking.

D — Cache. Persistence boundary #2: an in-memory LRU backed optionally by a disk tier. The only stage besides logging that writes state surviving a single request.

E — Upstream Selection. Applies the configured load-balancing policy over the health-filtered endpoint set (§8), then checks out a connection from that endpoint's pool.

F — Origin Services. Trust boundary #2; mTLS to the upstream is optional per pool (ADR-05, ADR-13).

G — Response Path. Mirrors C in reverse; the cache store decision happens here, distinct from D's lookup — a response is evaluated for cacheability only after the full response head is available.

H — Control Plane. The only external interface besides the client-facing listener; mTLS-only (P9, §6) or a Unix domain socket. Owns the generation-tagged atomic Config swap that Phase 11 (§23) makes zero-downtime.

I — Observability. An async channel decouples request-path latency from exporter I/O; OTLP export is best-effort and drops silently under exporter unavailability (P10, §6) rather than blocking the request path.

J — Edge Runtime. Invoked synchronously from stage C under a hard wall-clock, memory, and instruction budget (P6, §6). The only place tenant-supplied logic executes; sandboxed per the Sandbox-Execution reference design (§5).

6. Design Principles

  1. P1 — Connections survive config reloads. A configuration change drops zero in-flight requests; the old generation stays alive for every request that started under it. Tradeoff: bounded memory held per stale generation (I1). Violate it and every config push becomes a mini-outage.
  2. P2 — Routing is deterministic and explainable. Given a request and a configuration, the route match is a pure function; an admin-only x-route-id header names the matched route. Violate it and on-call cannot explain "why did this request go there."
  3. P3 — The cache is RFC 9111 with extensions, never RFC-9111-inspired. Extensions (surrogate keys, Cache-Tag) never override an RFC "do not cache." Violate it and the cache becomes an unbounded liability (stale/incorrect responses).
  4. P4 — TLS is terminated, not snooped. Passthrough routes never decrypt; terminating routes zeroize keys on drop and never log or forward key material. Violate it and a single log line becomes a key-compromise incident.
  5. P5 — The WAF blocks before it opens an upstream connection. A blocked request never reaches an upstream, partially or fully. Violate it and the WAF becomes advisory rather than a boundary.
  6. P6 — Edge programs are sandboxed, time-bounded, memory-bounded. Default budget: 1 ms wall-clock, 2 MiB memory, a fixed host-function allow-list. The runtime enforces the budget; the program's cooperation is never assumed. Violate it and one tenant's bug is every tenant's outage.
  7. P7 — Upstream connections are pooled and never trusted blindly. A connection is health-checked before reuse; one that returns 5xx or a frame-parse error is ejected, never recycled. Violate it and errors compound across requests sharing the poisoned connection.
  8. P8 — One configuration source, multiple formats. YAML/TOML/JSON/Caddyfile-style all parse to one internal Config; no per-format code path exists past parsing. Violate it and every feature must be implemented N times.
  9. P9 — The control plane is mTLS-only. No plaintext admin endpoint exists, ever, even on localhost. Violate it and local-privilege escalation becomes remote-privilege escalation.
  10. P10 — Observability is the default, not the opt-in. Every request emits an access-log line and bumps RED counters; OTLP export drops silently if the collector is absent rather than blocking. Violate it and incidents become undebuggable, and violate the "never block" half and an observability outage becomes a request-path outage.
  11. P11 — Backpressure is explicit, never infinite queuing. Every queue (accept backlog, pool checkout, edge-program dispatch) has a bounded depth and a documented rejection policy. Violate it and a slow downstream turns into unbounded memory growth.
  12. P12 — Time is a single injectable source. All timeouts, cache freshness math, and health-check scheduling read from one Clock abstraction, mockable in tests. Violate it and tests become flaky and untestable against clock skew.
  13. P13 — Every error variant maps to exactly one client-visible status code. RevpError variants are exhaustive and each names its HTTP status (§11 RevpError). Violate it and clients see inconsistent status codes for the same underlying failure.
  14. P14 — Hop-by-hop headers never cross the proxy boundary unmodified. Connection, Keep-Alive, TE, Trailers, Transfer-Encoding, Upgrade, Proxy-Authenticate, Proxy-Authorization are stripped per section 7.6.1 of RFC 9110, with an explicit allow-list exception for Upgrade on WebSocket routes. Violate it and protocol-layer state leaks across a boundary that must not see it.

These IDs (P1…P14) are referenced throughout the phase plan and back matter.

8. Domain Model

Connection Lifecycle State Machine

Request Lifecycle State Machine

Received → Parsed → Routed → Authenticated → WafEvaluated → EdgeEvaluated → CacheChecked → UpstreamSelected → UpstreamForwarded → ResponseReceived → Transformed → CacheStored → Sent → Logged

Each arrow is a pipeline stage from §3 box C/D/E/G. A stage may short-circuit directly to Transformed/Sent (WAF block at WafEvaluated, cache hit at CacheChecked, edge-program generated response at EdgeEvaluated) — the state machine is a DAG with Sent reachable from five different upstream states, never a strict linear pipeline once short-circuits are drawn. Logged is unconditional (I14) regardless of which path reached Sent.

Load-Balancing Algorithms

Policy Selection Rule Complexity Regime Where It Wins
RoundRobin next endpoint in fixed cyclic order O(1) homogeneous backend latency, uniform request cost
LeastConn endpoint with fewest in-flight requests O(log n) with a heap heterogeneous request duration, connection-oriented backends
PowerOfTwoChoices (default) sample 2 endpoints at random, pick the less-loaded O(1) large N, avoids the herding failure mode of pure least-conn under synchronized probes (Mitzenmacher, §5)
ConsistentHash hash(key) → ring position → nearest endpoint clockwise O(log n) session affinity / cache-locality-sensitive backends; bounded remapping on membership change (Karger et al., §5)
Random uniform random endpoint O(1) stateless baseline for differential testing against the others

Worked Example — Full Request Trace

GET /api/users/42 HTTP/1.1, Host: api.example.com, Authorization: Bearer <jwt>. Trace: (1) Parsed — h1 codec yields a Request with method=GET, uri.path=/api/users/42; (2) Routed — router matches Matcher{host: Exact("api.example.com"), path: Prefix("/api/")} at priority 100, binds RouteId(7), emits x-route-id: 7; (3) Authenticated — JWT verified against cached JWKS, Principal::Jwt{sub: "u_42", ...}; (4) WafEvaluated — 0 rule matches, Pass; (5) EdgeEvaluated — no edge program configured on this route, no-op; (6) CacheChecked — cache key (GET, /api/users/42, vary=[]) misses; (7) UpstreamSelected — P2C samples endpoints 3 and 7, picks endpoint 3 (fewer in-flight); (8) UpstreamForwarded — request sent over a pooled h1 keep-alive connection; (9) ResponseReceived — 200, Cache-Control: max-age=60; (10) Transformed — response-scope transforms (none configured) no-op; (11) CacheStored — entry stored, fresh_until = now + 60s; (12) Sent; (13) Logged — one JSON access-log line with route_id=7, upstream=3, cache_status=Miss, status=200, duration_us=<n>.

Malformed-Input Example

POST /upload HTTP/1.1 with both Content-Length: 100 and Transfer-Encoding: chunked present (the CL.TE smuggling shape, section 6.3 of RFC 9112). Per I4/P14 and the h1 codec contract (§12 (0.2)): the codec rejects the request at Parsed with 400 Bad Request, closes the connection (never attempts to guess which header wins), and increments smuggling_attempt_rejected_total. The request never reaches Routed. Conformance bucket h1/smuggling fixes this as a regression case (§12 (0.5)).

Failure-Path Example

Upstream connection reset mid-response, after headers were flushed to the client but before the body completed. The proxy cannot recall sent bytes; it cannot retry (retrying would duplicate a partially delivered response — P7's method-aware retry policy, §14 (2.2), only retries before any byte reaches the client). Recovery: the h1/h2 codec terminates the downstream stream with an incomplete-body signal (chunked: no terminating 0\r\n\r\n; content-length: fewer bytes than declared, which well-behaved clients detect as a truncated response), increments upstream_reset_midresponse_total, ejects the upstream connection from the pool (I3), and emits a Logged entry with outcome=upstream_reset_midresponse for postmortem correlation (§25 FM-3).

All types below are signatures only (no method bodies), per the No-Code Rule. Ownership, concurrency, and persistence semantics are annotated after each.

Request / Response / Body

pub struct Request {
    pub id: RequestId, pub received_at: Instant, pub client_addr: SocketAddr,
    pub tls: Option<TlsContext>, pub method: Method, pub uri: Uri, pub version: Version,
    pub headers: HeaderMap, pub body: Body, pub route: Option<RouteId>,

    pub status: StatusCode, pub headers: HeaderMap, pub body: Body,

}
pub enum Body { Empty, Bytes(Bytes), Stream(BoxStream<'static, Result<Bytes, BodyError>>) }

Ownership: Request/Response are owned exclusively by the pipeline task processing them (§3 box C), never shared. Mutation: in-place, stage by stage. Concurrency: none — single-task ownership; no Arc/lock. Persistence: none — pure in-memory, request-lifetime only. Serialization: never serialized as a whole; wire (de)serialization happens only at codec boundaries (§12, §22). Compatibility: internal type, not wire-visible; free to evolve without a version tag.

Ownership: Route is owned by Config (§11 Config), reachable read-only from any pipeline task via Arc<Config>. 12. Phase 0 — Repo Skeleton & Correctness Kernel

0.1 Objectives

Stand up the Cargo workspace (§10) and land the smallest system that is a real reverse proxy: an HTTP/1.1 listener, a fixed route, a health-checked upstream pool, an access log, and a hot-reload path. This phase establishes the concurrency model (one Tokio task per connection, §3 box C) and the correctness kernel — invariants I1, I2, I3, I4, I14 must all hold by the end of this phase, not be deferred to a later one.

0.2 Detailed Implementation Steps

  • Scaffold the workspace per §10; land revp-core's Request/Response/Body (§11) and the RevpError taxonomy (§11, P13).
  • Listener (revp-bin + a listener module): per-core SO_REUSEPORT shard (ADR-17), bounded accept backlog (P11), graceful drain on SIGTERM honoring the 30 s default (ADR-20, I2).
  • HTTP/1.1 codec (revp-proto-h1): request-line → headers → body read-side state machine (§8 Connection Lifecycle); reject ambiguous Content-Length/Transfer-Encoding combinations per section 6.3 of RFC 9112 (I4, P14) — this is the CL.TE/TE.CL defense traced in §8's Malformed-Input Example.
  • Upstream pool (revp-upstream): fixed-size pool per static endpoint, HTTP/1.1 keep-alive reuse, active health check via a periodic GET against the actual route path (not a synthetic liveness-only endpoint) — precursor to the full state machine in §14 (I10).
  • One hardcoded Route (host + path-prefix → pool), no transforms (§11 Route).
  • Access log (revp-observe): one structured JSON line per request, unconditionally (I14, P10).
  • Hot reload: SIGHUP triggers ConfigSource::load (§11) and an atomic Arc<Config> swap (I1) — the prototype of the full generation-tagged swap built out in §23.
  • Per-connection idle/read timeout via a hashed timing wheel (Varghese & Lauck, §5) — O(1) amortized instead of a per-connection sleep task.

0.3 Deliverable

revp binary proxying HTTP/1.1 between a downstream client and a static two-endpoint upstream pool; examples/minimal-h1.yaml runs end-to-end against a mock upstream.

0.4 Acceptance Criteria

Conformance bucket h1/basic at 100% Pass against NGINX-1.27-captured golden fixtures; p99 added latency < 2 ms at 25,000 rps/core (the Phase-0 floor — §4's 100,000 rps/core target is reached at §22); zero dropped connections across 100 consecutive SIGHUP reloads under 5,000 rps background load.

0.5 Conformance Fixtures

h1/basic/keep-alive-reuse.toml — one TCP connection serves 10 sequential requests, expect a single upstream connection reused; h1/smuggling/cl-te-conflict.toml — expect 400 and immediate connection close; h1/basic/chunked-trailers.toml — expect trailers preserved end-to-end; reload/sighup-zero-drop.toml — expect 0 dropped requests across a reload at 10,000 rps.

0.6 Pitfalls

Mis-parsing the 0\r\n\r\n chunked end-marker truncates responses silently; Connection: close must be honored independently on the downstream and upstream sides (a downstream close does not imply the upstream connection should close, and vice versa); a 200 from a synthetic liveness path is not proof the service can serve the routes actually configured — the active health check must probe a real route path.

0.7 Performance Concerns

The accept loop allocates nothing beyond the unavoidable socket and task; header parsing zero-copy-slices into the read buffer rather than allocating a String per header; the timing wheel keeps idle-timeout bookkeeping O(1) amortized rather than one sleep() future per connection, which would not scale to the 500,000-connection ceiling (§4).

0.8 Edge Cases

A client that sends a request line then stalls forever (the slowloris shape, bounded here by the 30 s read timeout, hardened further at §20/§24 T-rows); a pipelined client sending two requests in one TCP segment; an upstream that accepts the TCP connection then closes it without writing a byte.

0.9 Failure Analysis

An upstream reset before any response byte reaches the client is retried once, and only for idempotent methods (P7); a reset after headers were flushed downstream is never retried (§8 Failure-Path Example) and surfaces as a truncated response logged with outcome=upstream_reset_midresponse, feeding FM-3 (§25).

0.10 Operational Notes

Metrics exported from process start: connections_active, requests_total, access_log_emitted_total (I14). SIGHUP is the only reload trigger in this phase (the mTLS control-plane API arrives at §23). Rollback is "redeploy the previous binary" — no migration concerns exist yet because Config has no persisted state.

13. Phase 1 — Routing Matrix

1.1 Objectives

Replace Phase 0's single hardcoded route with a compiled, priority-ordered routing matrix: host/path/method/header/JWT-claim/query matching, longest-prefix-wins path semantics, and an admin-only debug header naming the matched route (P2).

1.2 Detailed Implementation Steps

  • Compile Matcher (§11) into an evaluator with short-circuit AND across sub-matchers.
  • Path matching: exact, prefix (via a radix tree for longest-prefix-wins in O(path length), not O(routes)), regex (bounded per I9 — timeout + instruction budget, the Regex-Engine reference design).
  • Host matching: exact, suffix wildcard (*.example.com), regex; canonicalize to SNI when present, falling back to :authority (HTTP/2) then Host (RFC 3986 canonical form, §5).
  • Header matching: presence, exact value, regex value, case-insensitive name (P14-adjacent hygiene — comparison is case-insensitive, wire case is preserved).
  • Method matching as a bitset over the 9 standard methods plus an extension slot.
  • Route priority + tie-break by configuration source-line order; emit x-route-id (P2) on admin-scoped requests only.
  • Path normalization policy: RFC 3986 normalize-then-match, applied before matching, not after (§8 cross-reference to the malformed-input handling philosophy).

1.3 Deliverable

A compiled routing table serving all matcher dimensions against the Phase-0 listener; x-route-id observable via the admin API stub.

1.4 Acceptance Criteria

Routing table compiles 10,000 routes in < 100 ms; route lookup is O(log n) worst case, O(1) amortized for prefix/exact paths via the radix tree; conformance bucket routing/all at 100% Pass against Envoy-v1.32-captured fixtures; a 5,000-route / 1,000,000-synthetic-request fuzz run completes with zero panics.

1.5 Conformance Fixtures

routing/host-wildcard-suffix.toml; routing/path-longest-prefix-wins.toml; routing/regex-timeout-rejected.toml — expects a pathological regex route to time out and fall through priority rather than hang the worker; routing/host-sni-vs-authority-precedence.toml.

1.6 Pitfalls

Unbounded regex routes are a denial-of-service surface — cap at 1,000 regex routes by default and reject configurations that exceed it (I9); /foo/../bar, /foo//bar, and /foo%2Fbar each need an explicit normalization policy or routes silently diverge from operator intent; the Host header, the TLS SNI, and the HTTP/2 :authority pseudo-header can disagree — canonicalize explicitly rather than picking whichever the codec happens to expose first.

1.7 Performance Concerns

Radix-tree lookup keeps path matching off the O(routes) linear-scan path that a naive Vec<Route> walk would incur at 10,000 routes; regex routes are evaluated last (lowest priority in the evaluation order, not the routing priority) so cheap matchers reject most candidates before the expensive path is reached.

1.8 Edge Cases

Two routes at equal priority with overlapping matchers (resolved by source-line order, P2 requires this be explainable, not silent); a route whose regex compiles but is pathological (catastrophic backtracking) — caught by I9's instruction budget, not just wall-clock; an empty path ("") request-target on a non-OPTIONS method.

1.9 Failure Analysis

A regex route that exceeds its instruction budget mid-match is treated as a non-match (I9) and routing continues to the next priority — it never propagates as a request-level error, keeping a single bad regex from taking down the routing stage for other routes.

1.10 Operational Notes

x-route-id and x-route-priority are admin-only debug headers, stripped for non-admin-scoped requests; routes_compiled_total and regex_timeout_total (I9 telemetry) are exported; reloading the route table is a Config swap (§23), never an in-place mutation of the compiled radix tree.

14. Phase 2 — Upstream Pool & Load Balancing

2.1 Objectives

Build the full upstream layer: endpoint resolution, a lock-free connection pool with HTTP/1.1 keep-alive and HTTP/2 multiplexing, the five load-balancing policies (§8), active and passive health checking (§8 state machine), a circuit breaker, and a method-aware retry policy (P7).

2.2 Detailed Implementation Steps

  • Endpoint resolver: static list, DNS A/AAAA via hickory-dns (ADR-21), SRV, Kubernetes service discovery; DNS refresh interval min(TTL, 30s).
  • Connection pool: per-endpoint sub-pool, lock-free checkout fast path (Bos, §5, ch. 9) with work-stealing across per-thread sub-pools on a miss.
  • Load-balancing policies (§8 table): RoundRobin, LeastConn, PowerOfTwoChoices (default, Mitzenmacher §5), ConsistentHash (Karger et al. §5), Random.
  • Active health check: periodic HTTP probe with configurable expected status/body; success streak ≥ 2 admits Healthy (§8 state machine).
  • Passive health check: consecutive-5xx or connection-error streak ejects (I10); exponential backoff on re-probe.
  • Circuit breaker per endpoint, tripped by the same passive signal, half-open probing on cooldown.
  • Retry policy (P7): idempotent methods retry on any pre-byte upstream failure; non-idempotent methods retry only when the failure occurred strictly before any request byte was written upstream.

2.3 Deliverable

revp-upstream sustaining multi-endpoint pools with live health-check state transitions observable via the admin status endpoint stub.

2.4 Acceptance Criteria

Pool sustains 50,000 in-flight requests across 100 upstream endpoints with no connection thrash (checkout p99 < 20 µs); P2C selection beats round-robin on tail latency by ≥ 30% in the benchmarks/routed_1k.rs harness under a synthetic heterogeneous-latency backend mix; conformance bucket upstream/all at 100% Pass.

2.5 Conformance Fixtures

upstream/ejection-and-reprobe.toml; upstream/p2c-tail-latency.toml; upstream/retry-idempotent-only.toml — expects a POST never retried after a partial write; upstream/dns-ttl-respected.toml.

2.6 Pitfalls

Connection-pool contention is the primary bug source — a single global mutex around checkout collapses throughput at the 50,000-in-flight target; DNS refreshed too aggressively burns resolver QPS, too lazily routes to dead endpoints (min(TTL, 30s) is the balance point); retries that ignore request-body replay for non-idempotent methods leak side effects (double-charge class bugs).

2.7 Performance Concerns

Checkout must stay lock-free on the fast path (ADR referenced via Bos, §5) — a per-thread sub-pool with work-stealing on miss avoids a single contended structure; health-check probes are scheduled off the request path entirely (a separate Tokio task per endpoint), never inline with request forwarding.

2.8 Edge Cases

An endpoint that flaps between Healthy and Suspect faster than the probation window — the probation success-streak counter must reset on any failure, not decay; a DNS resolution that returns zero records (all endpoints vanish) — the pool must reject new requests with NoHealthyUpstream (§11 RevpError) rather than serve stale cached endpoints past a bounded staleness window; a circuit breaker and passive health check disagreeing about an endpoint's state in the same tick (resolved by giving passive ejection precedence — a breaker trip without an ejection is a bug).

2.9 Failure Analysis

Total endpoint loss (NoHealthyUpstream) surfaces as 503 to the client (P13) and increments a paging-eligible alert threshold (§26); a poisoned connection returned to the pool despite I3 is a correctness bug caught by the conformance harness's invariant-mode assertion (§7), never a runtime possibility once shipped.

2.10 Operational Notes

Per-endpoint gauges: upstream_healthy, upstream_ejected (I10 telemetry), upstream_inflight; pool-wide checkout_latency_us histogram; the admin /admin/upstreams endpoint (built out in §23) surfaces live state for on-call triage without requiring log access.

15. Phase 3 — Request/Response Transformation

3.1 Objectives

Implement the Transform chain (§11): header set/remove/rename, path rewrite, bounded body rewrite, redirects, request/response injection — applied per-scope, in configured order, bidirectionally around the upstream call.

3.2 Detailed Implementation Steps

  • Header transforms: set/remove/rename/append, scoped to Request or Response (P14 governs which headers may never be user-rewritten — hop-by-hop headers are stripped before the transform chain ever sees them, not after).
  • Path rewrite: strip-prefix, add-prefix, regex-replace (bounded per I9).
  • Body rewrite: regex-replace within a max_bytes cap (default 1 MiB); requests/responses beyond the cap bypass rewrite and emit x-rewrite-skipped (admin-only).
  • Redirect transform: 301/302/307/308 with a templated Location.
  • Request/response injection: header injection from configurable sources (client IP, SNI, JWT claim via §19's Principal); response fragment injection at <head>/</body> boundaries for SSR use cases.
  • Hop-by-hop stripping (P14, I4): Connection, Keep-Alive, Proxy-Authenticate, Proxy-Authorization, TE, Trailers, Transfer-Encoding, Upgrade per section 7.6.1 of RFC 9110, with an explicit Upgrade allow-list exception for WebSocket routes (built out fully at §22).

3.3 Deliverable

A configurable transform chain executing around the Phase-2 upstream call, exercised by examples/edge-rewrite.yaml.

3.4 Acceptance Criteria

Transform chain executes in < 10 µs for a typical 5-rule chain (measured in benchmarks/routed_1k.rs); conformance bucket transform/all at 100% Pass; body rewrites correctly bypass and flag (x-rewrite-skipped) any payload exceeding the 1 MiB default cap.

3.5 Conformance Fixtures

transform/header-rewrite-roundtrip.toml; transform/hop-by-hop-stripped.toml; transform/body-rewrite-cap-exceeded.toml; transform/redirect-templated-location.toml.

3.6 Pitfalls

A body rewrite that must simultaneously stream, buffer, and stay within a byte bound is the primary bug source — each rule must declare which mode it runs in and document the consequence of exceeding the cap; header capitalization is preserved on the wire even though comparison is case-insensitive (some legacy clients break on case changes the proxy did not intend to make).

3.7 Performance Concerns

Header transforms operate on HeaderMap in place, never reallocating the full map per rule; body rewrites that would require buffering an otherwise-streamed body are the single largest latency and memory risk in this phase and are capped accordingly (§4 memory ceilings).

3.8 Edge Cases

A PathRewrite producing an empty path; a ResponseInject fragment injected into a response with no <head>/</body> tag present (no-op, logged, never a hard error); a redirect Location template referencing a route variable that is absent on this request.

3.9 Failure Analysis

A malformed rewrite rule (e.g., an invalid regex capture-group reference) is caught at config load (§23 (11.8)), never at request time — a request never observes a TransformError that could have been caught statically; a runtime TransformError (e.g., body cap exceeded) always degrades to bypass-with-flag, never to a dropped request.

3.10 Operational Notes

x-rewrite-skipped and x-route-id are the two admin-debug headers introduced so far; transform_chain_duration_us histogram feeds the §30 M7 performance gate; rollback of a bad transform rule is a Config reload (§23), applied instantly to new connections and, per I1, never to in-flight ones.

16. Phase 4 — RFC 9111 Caching Layer

4.1 Objectives

Implement the cache as a literal reading of RFC 9111 (P3): key construction, cacheability decision, freshness lifetime, validator-based revalidation, stale-while-revalidate/stale-if-error, surrogate-key invalidation, and a two-tier store (in-memory LRU + optional disk tier).

4.2 Detailed Implementation Steps

  • Cache key (§11 CacheKey): method + URL + Vary-relevant headers + optional surrogate key; hashed with xxhash-3 (ADR-13); full key retained for collision detection.
  • Cacheability decision: status code, method, Cache-Control, Authorization presence, response body presence — an Authorization-bearing response is never shared-cached unless Cache-Control: public is explicit (RFC 9111, applied here directly).
  • Freshness lifetime: max-age, s-maxage, Expires, and the section 4.2.2 of RFC 9111 heuristic (10% of time since Last-Modified, capped — default cap 1 h, RFC ceiling 24 h).
  • Validation: ETag/Last-Modified; conditional revalidation via If-None-Match / If-Modified-Since.
  • stale-while-revalidate and stale-if-error per their respective Cache-Control extensions.
  • Surrogate keys (Cache-Tag header) and the invalidation API (POST /admin/cache/purge, built out fully in §23).
  • Two-tier store: in-memory LRU bounded by RSS budget (§4), disk tier bounded by file count and bytes; I12 strips Set-Cookie on store unless explicitly opted in.
  • Vary cardinality cap: 32 vary-tuples per resource by default, LRU-evicts the 33rd (I5 telemetry: cache_vary_cardinality).

4.3 Deliverable

revp-cache serving as CacheStore (§11) behind the Phase-3 pipeline; examples/ cache-with-surrogates.yaml demonstrating tag-based invalidation end to end.

4.4 Acceptance Criteria

Cache passes the httpwg/9111-cache-tests suite at 100%; surrogate-key invalidation propagates across the in-process cache in < 100 ms; cache lookup p99 < 50 µs (§30 M11); conformance bucket cache/all at 100% Pass.

4.5 Conformance Fixtures

cache/vary-accept-encoding.toml (§10 example scenario); cache/set-cookie-stripped.toml; cache/stale-while-revalidate.toml; cache/surrogate-key-purge-propagation.toml.

4.6 Pitfalls

Vary cardinality explosion (I5) if not capped; caching an Authorization-bearing response without an explicit public directive leaks one user's data to another; heuristic freshness without an explicit cap surprises operators who expected a no-cache-adjacent default.

4.7 Performance Concerns

Cache-key hashing is on the request hot path for every request, cache hit or miss — xxhash-3 (ADR-13) is chosen specifically because SHA-256 would add measurable latency at the 100,000 rps/core target (§4); the LRU eviction structure must not lock the whole cache on a single insert.

4.8 Edge Cases

A response whose Vary header changes between two stores of the "same" resource (cache key namespace must include the vary-tuple, not just the URL); a revalidation request racing a concurrent purge (the purge must win — a stale entry must never be re-validated back into the cache after its tag was explicitly invalidated); a disk-tier write that fails mid-write (partial file) must never be served — checksum or size-verify on read.

4.9 Failure Analysis

A disk-tier corruption (partial write, checksum mismatch) degrades that single entry to Miss and evicts it — it never crashes the process nor serves corrupted bytes; a surrogate-key purge that fails to reach every shard in a multi-process deployment is a documented eventual-consistency window (bounded by the 100 ms target, alertable if exceeded, §26).

4.10 Operational Notes

cache_status (§11 CacheStatus) is logged on every request (I14); POST /admin/cache/purge (§23) is the only invalidation entry point; the disk tier's on-disk format is versioned (§27) so a binary upgrade can detect and safely discard an incompatible tier rather than misread it.

17. Phase 5 — TLS Termination & SNI Routing

5.1 Objectives

Terminate TLS 1.3 (and optional 1.2 fallback) with SNI-based certificate selection, ALPN negotiation across h1/h2/h3, OCSP stapling, optional mTLS to both client and upstream, and key-material hygiene (P4, I6).

5.2 Detailed Implementation Steps

  • rustls integration with the aws-lc-rs crypto provider (ADR-05).
  • CertResolver (§11): SNI → Arc<CertifiedKey>, exact + wildcard matching; the ACME implementation (§18) wraps this resolver rather than replacing it.
  • ALPN negotiation: announce h2, http/1.1 (h3 announced separately over QUIC, §22); honor client preference order.
  • OCSP stapling: prefetch on cert load, refresh in the background before the staple's 7-day staleness bound.
  • mTLS to upstream: present a client cert configurable per upstream pool (ADR-05); mTLS from client: SAN/subject-DN/fingerprint verification feeding Principal::Mtls (§19).
  • Session-ticket rotation hourly per process; I6 zeroization on drop and on shutdown, enforced via a Zeroize implementation, never a manual memset.
  • TLS-passthrough mode for routes that must not decrypt (P4) — the listener demuxes by SNI alone and forwards the raw TCP stream.

5.3 Deliverable

TLS-terminating listener serving SNI-routed certs over the Phase-0–4 pipeline; examples/tls-acme.yaml scaffold (cert provisioning itself lands in §18).

5.4 Acceptance Criteria

10,000 distinct SNI mappings load in < 5 s and resolve in < 10 µs each; TLS handshake p99 < 5 ms resumed / < 50 ms fresh (§4, §30 M8/M9); conformance bucket tls/all at 100% Pass including the 1.2-fallback path (opt-in, default 1.3-only).

5.5 Conformance Fixtures

tls/sni-wildcard-resolution.toml; tls/ocsp-staple-fresh.toml; tls/passthrough-no-decrypt.toml — asserts the proxy process never holds a decrypted byte for a passthrough route; tls/mtls-upstream-chain-validated.toml.

5.6 Pitfalls

Session-ticket key reuse across processes silently breaks forward secrecy — each process generates and rotates its own key unless an explicit cluster-wide KMS integration is configured; a failed OCSP fetch must not block cert loading (the cert loads unstapled and an alert fires, §26); SNI is plaintext on the wire absent ECH (deferred, §37).

5.7 Performance Concerns

SNI resolution is a hash-map lookup, not a linear cert scan, to hit the 10 µs target at 10,000 mappings; the TLS handshake itself (not resolution) dominates the p99 budget (§4) — session resumption is the primary lever, which is why its p99 target is 10x tighter than a fresh handshake.

5.8 Edge Cases

A ClientHello with no SNI at all (route to a configured default cert or reject, per policy); an OCSP responder that is unreachable at renewal time (serve the last-known-good staple until its 7-day bound, then serve unstapled with an alert rather than fail the handshake); a mid-handshake client disconnect (clean up the partially-constructed ServerConnection without leaking).

5.9 Failure Analysis

A handshake failure (bad cert, unsupported cipher, client abort) closes the connection at TlsHandshake (§8 Connection Lifecycle) and increments tls_handshake_failed_total tagged by failure reason — it never reaches the request pipeline, so no route-level error handling applies.

5.10 Operational Notes

tls_handshake_duration_us (resumed vs. fresh, tagged) feeds §30 M8/M9; cert inventory is introspectable via CertResolver::list() (§11) through the admin API (§23); rotating a cert is a Config reload — new connections see the new cert immediately, connections mid-handshake complete under whichever cert they started with.

18. Phase 6 — ACME Automatic Certificate Provisioning

6.1 Objectives

Automate certificate issuance and renewal against an ACME v2 directory (Let's Encrypt), so operators never run a manual cert pipeline; wraps the CertResolver from §17 rather than replacing it.

6.2 Detailed Implementation Steps

  • ACME v2 client (revp-acme): directory discovery, account creation, order, authorize, finalize, certificate download (RFC 8555, §5).
  • HTTP-01 challenge handler on the existing listener (Caddy-precedent, §5 reference implementation).
  • DNS-01 challenge handler with provider plugins (e.g. Route 53, Cloudflare DNS).
  • Renewal scheduler: renew at 1/3 remaining lifetime by default, configurable.
  • Cert storage: filesystem by default; KMS/Vault as pluggable backends.
  • Account-key persistence and rotation policy, scoped to a single designated orchestrator node per deployment (I13).

6.3 Deliverable

revp obtains and auto-renews a cert against the Pebble test ACME server with zero manual steps after initial account creation.

6.4 Acceptance Criteria

Fresh install obtains a Let's Encrypt staging cert in < 30 s (§30 M10); renewal under 5,000 rps background load drops zero requests; conformance bucket acme/all at 100% Pass against Pebble.

6.5 Conformance Fixtures

acme/http01-challenge-roundtrip.toml; acme/dns01-provider-route53.toml; acme/renewal-zero-drop.toml; acme/rate-limit-batching.toml.

6.6 Pitfalls

Let's Encrypt production enforces a hard 50 certs/registered-domain/week limit — batch SAN-bundled certs or the deployment silently stalls issuance; account-key compromise is catastrophic and total, which is why I13 confines it to one orchestrator node; clustered ACME without leader election races on challenge state (documented as a single-node-ACME default, multi-node as an explicit opt-in in docs/acme.md).

6.7 Performance Concerns

ACME orchestration runs entirely off the request path — a slow ACME directory or a rate-limited order must never block an in-flight request's TLS handshake, which continues to use the last-known-good cert until renewal succeeds.

6.8 Edge Cases

A renewal that fails repeatedly as the cert approaches expiry (alert escalates in urgency as the remaining lifetime shrinks, §26); a challenge response race between two nodes in a misconfigured multi-node ACME setup; an ACME directory that changes its terms-of-service requirement mid-renewal (surfaced as a hard error, never silently retried past a bounded attempt count).

6.9 Failure Analysis

An expired, unrenewed cert is a P0 incident — the renewal scheduler pages before expiry (at the 1/3-remaining mark, then escalates at 7 days, 1 day) rather than waiting for a hard failure; Boulder's (Let's Encrypt production ACME server, §5) rate-limit responses are parsed and surfaced verbatim in the renewal log for triage.

6.10 Operational Notes

Runbook docs/runbook/cert-renewal-failed.md; metric acme_cert_expiry_seconds (gauge, per SNI) is the primary dashboard signal; the account key's node designation is a deployment-topology decision documented in docs/acme.md, not a runtime-configurable one.

19. Phase 7 — Authentication & Authorization

7.1 Objectives

Implement the four authentication schemes (Basic, JWT, OAuth introspection, mTLS) producing a Principal (§11) the router and downstream stages can act on, with auth chains (any-of/all-of/ none) and per-route failure responses.

7.2 Detailed Implementation Steps

  • Basic auth: Authorization: Basic parse, htpasswd-compatible store, bcrypt verify.
  • JWT auth: JWKS fetch + cache + rotate; signature verify (RS256, ES256, EdDSA); claim extraction feeding Matcher.jwt_claims (§13); alg: none rejected unconditionally.
  • OAuth introspection (RFC 7662): bearer token forwarded to the introspection endpoint, response cached by token hash.
  • mTLS client-cert auth: consumes the chain already validated at §17 — never re-validates it (P7-adjacent cost discipline).
  • Auth chains: any-of (first success), all-of (all required), none (anonymous allowed) — composable per route.
  • Failure responses configurable per route (status, body, headers).

7.3 Deliverable

revp-auth producing Principal values consumed by the router (§13 jwt_claims matcher) and the access log; examples/jwt-routing.yaml.

7.4 Acceptance Criteria

JWKS rotation completes in < 100 ms with zero failed verifications during the swap (overlap window covers both old and new keys); conformance bucket auth/all at 100% Pass.

7.5 Conformance Fixtures

auth/jwt-alg-none-rejected.toml; auth/jwks-rotation-overlap.toml; auth/oauth-introspection-cache-ttl.toml; auth/mtls-principal-from-chain.toml.

7.6 Pitfalls

Fetching JWKS on every request is the primary bug source — cache respecting the JWKS endpoint's own Cache-Control: max-age (default 1 h if absent) is mandatory; a revocation event must propagate through the introspection cache invalidation path or a revoked token stays accepted until its cached TTL expires.

7.7 Performance Concerns

JWT signature verification is on the request hot path for every JWT-authenticated request — verifying against a cached, pre-parsed JWKS avoids a network round-trip per request; OAuth introspection caching by token hash bounds the introspection endpoint's QPS to the cache-miss rate, not the request rate.

7.8 Edge Cases

A JWT that verifies but whose exp has just passed mid-request (reject, do not race clock skew — apply a small configurable leeway, default 0); a JWKS endpoint that returns a key set with zero overlap with the previous set (immediate hard rotation, no overlap window possible — logged as a notable event, not a silent success); an mTLS chain that was valid at handshake but whose leaf cert's CRL entry appears mid-connection (not re-checked per-request, connection-lifetime cached by design, P7-cost tradeoff documented).

7.9 Failure Analysis

An auth failure returns the route's configured failure response (P13-consistent status mapping via RevpError::Auth); a JWKS fetch failure during rotation retains the last-known-good key set rather than failing every request — an unreachable JWKS endpoint degrades to "can't rotate" not "can't authenticate."

7.10 Operational Notes

Principal is logged in redacted form only (sub and kid, never the raw token or claims blob, §24 threat model); jwks_rotation_total and auth_failure_total (tagged by scheme) are the primary dashboards; auth-scheme configuration changes are a Config reload, taking effect for new connections only (I1).

20. Phase 8 — Web Application Firewall & Rate Limiting

8.1 Objectives

Implement a WAF rule engine (OWASP CRS v4.x subset, ADR-10) with anomaly scoring, detect/block modes, and integrate token-bucket rate limiting (ADR-11) per IP/JWT-subject/API-key — enforced strictly before any upstream connection opens (P5, I11).

8.2 Detailed Implementation Steps

  • OWASP CRS subset: SQL-injection, XSS, RFI, LFI, RCE rule families (§5 CRS reference).
  • Rule engine: regex-based matchers (Regex-Engine reference design) over URL, headers, cookies, and body (body inspection off by default, capped at 64 KiB when enabled).
  • Anomaly scoring: each rule match contributes a score; a configurable threshold triggers block.
  • Modes: detect (log only, the recommended initial mode), block (reject before upstream, I11), challenge (stubbed here, built out at §37's deferred JS-challenge item).
  • Rate limiting integration: token bucket per route, keyed by IP, JWT sub, or API key (Rate-Limiter reference design, §5-adjacent).
  • IP reputation: GeoIP lookup, ASN block list, opt-in upstream feeds.
  • Custom rules via DSL, compiled with the same regex timeout/instruction budget as §13 (I9).

8.3 Deliverable

revp-waf evaluated as a mandatory pre-upstream pipeline stage (§3 box C); examples/ waf-mode.yaml demonstrating detect-then-block promotion.

8.4 Acceptance Criteria

WAF processes a 1 KB request through 200 rules in < 50 µs (§30 M12); false-positive rate against a captured production-traffic sample < 0.1% at the default score threshold; conformance bucket waf/all at 100% Pass including the CRS test corpus.

8.5 Conformance Fixtures

waf/sqli-crs-corpus.toml; waf/xss-crs-corpus.toml; waf/ordering-before-upstream.toml (I11); waf/regex-timeout-bounded.toml.

8.6 Pitfalls

Regex denial-of-service is the primary bug source — every WAF regex is compiled with the same timeout/instruction budget as routing (I9); enabling body inspection without a byte cap buffers unbounded request bodies; false positives in production require rule tuning, which is why detect-only is the shipped default and block requires explicit opt-in.

8.7 Performance Concerns

200-rule evaluation at 1 KB must stay under 50 µs — rules are ordered cheapest-first (presence checks before regex evaluation) and short-circuit on the first block-triggering match in block mode (detect mode evaluates all rules to log full anomaly context).

8.8 Edge Cases

A request whose body inspection is enabled but whose body exceeds the 64 KiB cap (evaluated against the truncated prefix only, flagged x-waf-body-truncated admin-only); a custom DSL rule whose regex is itself pathological (caught by the shared I9 budget, not a WAF-specific exception); a rule matching in both detect and block mode simultaneously configured on overlapping routes (block wins — P5 is never advisory).

8.9 Failure Analysis

A WAF block is logged with the triggering rule ID and anomaly score (§25 FM-adjacent forensic requirement); a WAF engine internal error (never a rule match, a bug in the engine itself) fails open or closed per an explicit configuration flag, defaulting to fail-closed (reject) because P5's ordering guarantee is a security boundary, not a convenience.

8.10 Operational Notes

waf_block_total, waf_detect_total (tagged by rule ID), and waf_false_positive_reported_total (fed by an operator feedback loop) are the primary dashboards; runbook docs/runbook/waf-false-positive.md documents the tuning checklist before enabling block mode on a new route.

21. Phase 9 — Edge Programs: Wasm + Lua Sandboxing

9.1 Objectives

Let tenants run small request/response-transforming programs (Wasm or Lua) inside the pipeline under a hard, runtime-enforced resource budget (P6) — never relying on the program's cooperation.

9.2 Detailed Implementation Steps

  • Wasm runtime: wasmtime (ADR-06) with fuel-based instruction metering, epoch-based wall-clock interruption, and a fixed memory limit per Store.
  • Wasm host functions: a small, explicit allow-list (read/set request or response header, read a body chunk, log, increment a metric) — no syscall passthrough, following the proxy-wasm ABI for Envoy filter compatibility (§5 Envoy reference).
  • Wasm Component Model / WASI Preview 2 bindings for the host ABI, so filters compiled from Rust, TinyGo, or AssemblyScript all run unmodified.
  • Lua runtime: mlua + LuaJIT (ADR-07), sandboxed via an empty _G populated only with whitelisted functions — no debug library, no string.format format-string surface.
  • Resource budgets (P6 defaults): 1 ms wall-clock, 2 MiB memory, 10M instructions.
  • Lifecycle: compile on config load, instantiate per request, dispose on response — no state persists across requests unless explicitly backed by an external store the program calls into.

9.3 Deliverable

revp-edge-wasm and revp-edge-lua invoked as an optional pipeline stage (§3 box J); examples/edge-rewrite.yaml running a Rust-compiled Wasm filter.

9.4 Acceptance Criteria

Wasm filter overhead < 100 µs for a no-op program (§30 M13); Lua filter overhead < 50 µs (§30 M14 — note: table cites both under the M-series, §30); conformance bucket edge/all at 100% Pass including Rust-, TinyGo-, and AssemblyScript-compiled Wasm filters.

9.5 Conformance Fixtures

edge/wasm-fuel-exhaustion-reject.toml; edge/lua-sandbox-escape-blocked.toml; edge/proxy-wasm-abi-compat.toml; edge/host-function-allowlist-enforced.toml.

9.6 Pitfalls

Fuel exhaustion mid-request is the primary bug source — the action on exhaustion is configurable (pass-through, reject, terminate; default reject, P6); Lua sandbox escape via string.format or debug-library access is closed by removing both from the sandboxed _G; a Wasm module that calls a host function per byte of body data is pathological — a streaming on_request_body_chunk ABI amortizes the call cost.

9.7 Performance Concerns

Instantiating a fresh Wasm Store per request must stay cheap relative to the 100 µs budget — module compilation happens once at config load, only instantiation happens per request; the fuel counter and epoch deadline are checked by the runtime itself, adding negligible per-call overhead compared to a manual timeout wrapper.

9.8 Edge Cases

A Wasm module that traps (e.g., unreachable instruction) mid-execution (treated as EdgeError, never a process-level panic — wasmtime traps are caught at the host boundary); a Lua script that recurses until the instruction budget is hit (same exhaustion path as fuel, unified telemetry); two edge programs configured on the same route in sequence, the first modifying a header the second's matcher depends on (order is configuration-defined and must be explicit, never implied).

9.9 Failure Analysis

An edge-program budget violation (I7) never crashes the worker thread — the sandbox boundary (fuel/epoch/memory limits, wasmtime's own isolation) contains the fault to the single request; a proxy-wasm ABI mismatch (an Envoy filter compiled against an incompatible ABI version) is rejected at module-load time with a clear error, never at request time.

9.10 Operational Notes

edge_budget_exceeded_total (I7 telemetry, tagged by runtime and reason: fuel/epoch/memory); edge_invocation_duration_us histogram feeds §30 M13/M14; a misbehaving edge program is disabled per-route via Config reload without redeploying the binary — the core operational value proposition of this phase.

22. Phase 10 — HTTP/2, gRPC, HTTP/3, WebSocket, SSE

10.1 Objectives

Reach full downstream/upstream protocol parity: HTTP/2 with HPACK, gRPC framing and trailers, HTTP/3 over QUIC with QPACK, WebSocket proxying, and Server-Sent Events streaming — hitting the 100,000 rps/core defining target (§4) on HTTP/1.1 and HTTP/2.

10.2 Detailed Implementation Steps

  • HTTP/2 (ADR-03, hyper's h2 implementation): ALPN announces h2 first; HPACK dynamic-table sizing (default 4 KiB, configurable per peer); the codec closes the connection on any HPACK error rather than attempting recovery (an HPACK desync corrupts every subsequent header on the connection).
  • Stream-concurrency limits per connection — a single client opening 1,000 streams must not starve others (P11 backpressure principle applied to multiplexed streams).
  • gRPC (revp-proto-grpc): trailers handling, status-code mapping, deadline propagation via grpc-timeout; unary, server-streaming, client-streaming, and bidirectional all proxy correctly.
  • HTTP/3 (revp-proto-h3, ADR-04): quinn + h3 over a UDP listener; ALPN announces h3, falling back to h2/http1.1; Alt-Svc advertisement; 0-RTT restricted to idempotent methods only (config validator rejects 0-RTT on POST/PATCH/DELETE).
  • WebSocket (revp-proto-ws): 101 Switching Protocols negotiation, frame proxying, close handshake; on h2, :protocol = websocket per RFC 8441 extended CONNECT.
  • SSE (revp-proto-sse): text/event-stream triggers stream mode; the cache layer (§16) bypasses SSE responses entirely; the listener flushes on every event boundary, never buffers.

10.3 Deliverable

Full protocol parity across the listener (box B) and upstream layer (box E); conformance buckets h2, h3, grpc, ws, sse all wired into the harness.

10.4 Acceptance Criteria

HTTP/1.1 and HTTP/2 sustain 100,000 rps/core on the no-op route (§4, §30 M1/M2); HTTP/3 sustains 75,000 rps/core (the documented QUIC-overhead gap, §30 M3); WebSocket proxying holds 100,000 concurrent connections/node (§30 M15); SSE holds 50,000 concurrent connections/node with a 15 s heartbeat (§30 M16); conformance buckets h2/all, h3/all, grpc/all, ws/all, sse/all all at 100% Pass.

10.5 Conformance Fixtures

h2/hpack-error-closes-connection.toml; h3/0rtt-rejected-on-post.toml; grpc/bidi-streaming-interop.toml; ws/close-handshake-on-upstream-disconnect.toml; sse/no-buffering-flush-per-event.toml.

10.6 Pitfalls

HPACK dynamic-table desync between peers corrupts every subsequent header decode on the connection — the only correct recovery is closing the connection, never attempting to resync; gRPC trailer handling differs from generic HTTP/2 trailers in frame-ordering and status-mapping subtlety, tested against the gRPC interop suite (§5); stream-multiplexing fairness requires an explicit per-connection stream-count limit or one client starves the rest; 0-RTT replay on non-idempotent methods is a correctness and security bug, foreclosed at config-validation time, not request time.

10.7 Performance Concerns

The 100,000 rps/core target is reached here, not before — HTTP/2 stream state must not allocate per-frame; QUIC/h3's per-packet crypto overhead is the documented reason its throughput target is 25% lower than h2's; SSE and WebSocket connections must not participate in the cache-lookup hot path at all (bypassed entirely, not merely marked non-cacheable, to avoid wasted key-construction work).

10.8 Edge Cases

A WebSocket connection whose upstream closes without a close frame (the proxy must inject one downstream rather than leave the client hanging — traced in §8's Domain Model); an SSE stream whose client disconnects without a clean TCP close (detected via write failure, not a read timeout, since SSE is server-to-client only); an HTTP/2 client that never sends a SETTINGS ack (bounded by a settings-ack timeout, connection closed past it).

10.9 Failure Analysis

An HPACK or QPACK decode error is unrecoverable by design — connection closed, hpack_error_total incremented, no partial-recovery attempt (attempting one has historically been the source of smuggling-adjacent bugs in other proxies); a gRPC deadline exceeded maps to the gRPC status DEADLINE_EXCEEDED, not a generic HTTP timeout status, preserving the client's error-handling contract.

10.10 Operational Notes

Per-protocol RED metrics (h2_stream_duration_us, h3_handshake_duration_us, ws_connections_active, sse_connections_active); Alt-Svc header is emitted only once h3 has passed its own conformance bucket in a given deployment, avoiding advertising an unready protocol.

23. Phase 11 — Hot Reload, Control Plane & Conformance Harness

11.1 Objectives

Deliver zero-downtime configuration reload (P1, I1) via a real mTLS-only control-plane API (P9, I8), and close the loop with a conformance harness that diffs behavior against NGINX, Envoy, and Caddy on the full scenario corpus.

11.2 Detailed Implementation Steps

  • SIGHUP and POST /admin/config both trigger a config reload; validation runs in a dry-run mode returning the result without applying, distinguishing hard errors (parse/schema) from soft errors (JWKS/DNS reachability) with explicit severities.
  • Control-plane API (revp-control): Unix domain socket by default, mTLS TCP optional (I8); endpoints POST /admin/config, POST /admin/cache/purge (§16), GET /admin/status, GET /admin/routes/:id, GET /admin/upstreams (§14), POST /admin/drain.
  • Atomic swap: the old Config generation stays alive, reference-counted, for the duration of every request that started under it (I1); new connections observe the new generation immediately; a held generation older than 10 minutes is force-evicted with a warning (bounds the memory leak class where a request never finishes).
  • Reload latency target < 100 ms p99 on a 10,000-route configuration.
  • Conformance harness (conformance/runner): capture golden fixtures from NGINX 1.27, Envoy v1.32, and Caddy v2.8 against the full scenario corpus (§10); diff byte-for-byte where possible, semantically otherwise; categorize differences as bug / spec / policy, documenting every policy difference in docs/conformance/policy-differences.md.

11.3 Deliverable

Full revp binary with a live mTLS control plane and a conformance report showing 100% Pass against the scenario corpus, differences against reference proxies categorized and signed off.

11.4 Acceptance Criteria

10,000 reloads in sequence with no memory leak (heaptrack-verified, RSS delta < 1% across the run); cache-purge propagation < 100 ms (§16); reload p99 < 100 ms at 10,000 routes (§30 M17); every conformance category at 100% Pass; zero plaintext control-plane bind possible (I8, enforced at startup).

11.5 Conformance Fixtures

reload/10k-reloads-no-leak.toml; control-plane/plaintext-bind-rejected.toml; conformance/nginx-diff-categorized.toml; conformance/envoy-diff-categorized.toml.

11.6 Pitfalls

Old-Config-generation retention leaks if a request never finishes — the 10-minute force-eviction bound (with a warning) is the safety net, not the primary defense (the primary defense is bounded request timeouts, §4); validation that depends on external state (JWKS reachability, upstream DNS) must be distinguished from parse/schema errors or operators cannot tell "config is wrong" from "network is flaky right now"; NGINX and Envoy disagree on real edge cases (chunked whitespace, percent-encoded / in paths, ambiguous Vary) — each disagreement is resolved by an explicit ADR, never left silently inconsistent.

11.7 Performance Concerns

The atomic swap itself must be O(1) (a pointer swap under an ArcSwap-style structure), never O(routes) — the 100 ms reload target at 10,000 routes is dominated by config compilation (radix-tree build, regex compilation, JWKS prefetch), not by the swap.

11.8 Edge Cases

A reload that fails validation after several routes' JWKS have already been prefetched (the partial prefetch is discarded, the old generation stays active — reload is all-or-nothing, never partially applied); a conformance scenario where the "reference" proxies disagree with each other, not just with revp (resolved by an explicit ADR choosing a side, documented in docs/conformance/policy-differences.md, never silently deferred).

11.9 Failure Analysis

A reload that fails validation is a no-op from the client's perspective — the old generation keeps serving traffic and the failure is surfaced only to the operator via the API's response and a config_reload_failed_total counter; a control-plane process that crashes mid-reload leaves the last-successfully-applied generation active on restart (the swap is atomic, so there is no partially-applied state to recover from).

11.10 Operational Notes

config_reload_duration_us, config_generations_held (should track near zero outside brief overlap windows — a sustained non-zero value pages, §26); the conformance report (conformance.report.json, §10) is published on every release and gates the release pipeline (§29) at 100% Pass for P0/P1 scenarios.

26. Operational Readiness

Metrics: RED (rate/errors/duration) per route, per upstream endpoint, per protocol (§22 (10.10)); invariant-adjacent gauges (config_generations_held, upstream_ejected) surfaced on the primary dashboard. Tracing: OTLP spans per pipeline stage (router, auth, WAF, edge, cache, upstream), sampled head-based at 1% by default plus tail-based 100% for any request ending in 5xx. Structured logging: one JSON access-log line per request (I14), one structured error log per RevpError::Internal. Dashboards: per-route latency/error-rate, per-upstream health-state timeline, cache hit-rate, WAF block-rate, edge-program budget-exhaustion rate, TLS handshake success-rate. Alerting philosophy: page only on symptoms with a documented runbook (below), never on a raw metric threshold without an accompanying "what to do" — a FM-class table row is the minimum bar for a new page-worthy alert. SLOs: 99.95% monthly availability (§4); p99 added latency under 1 ms as an internal SLO gating releases (§29), not a customer-facing SLA. Incident response: severity levels mirror the FM classes' auto-recovery presence — FM rows with "none" under Auto Recovery are Sev-1 by default. Named runbooks: docs/runbook/triage.md, reload-failed.md, cert-renewal-failed.md, upstream-unhealthy.md, waf-false-positive.md (§10 tree). Backup/restore: the proxy holds no authoritative state — the cache is a hit-rate optimization (§31), so "restore" means "reload configuration from its source of truth," never a data restore. Deployment topology: N stateless nodes behind DNS or an L4 balancer, one designated ACME-orchestrator node (I13). Canary/rolling-upgrade: canary a new binary version on a small node subset, promote on green conformance + SLO signal over a soak window; rollback is redeploying the previous binary version, safe because Config compatibility is versioned (§27).

27. Compatibility & Versioning

Wire compatibility: HTTP/1.1, HTTP/2, HTTP/3, WebSocket, SSE, and gRPC framing follow their respective RFCs verbatim (§5) — the proxy never introduces a wire-incompatible extension on the client-facing side. Storage compatibility: the disk cache-tier record format carries a version byte (§11 CacheEntry persistence annotation); a binary upgrade that changes the format bumps the byte and discards an incompatible tier rather than misreading it (never a silent corruption). Schema evolution: Config's ConfigVersion field (§11) gates which fields are required vs. optional; a new optional field defaults to a no-op (matcher/policy) so older configs stay valid under a newer binary (§11 Route annotation). API stability: the control-plane API (§23) is versioned by URL prefix (/admin/v1/...); a breaking change ships as /admin/v2/... alongside the old prefix for one deprecation window. Migration: config-format migrations ship a documented revp validate --migrate CLI path (ADR-19's single-binary CLI surface) rather than a separate tool. Deprecation policy: a deprecated config key or API path emits a structured warning for two minor releases before removal, tracked in CHANGELOG.md. SemVer policy: the crate workspace (§10) follows SemVer; a wire-format or storage-format change is a major bump regardless of code diff size. Rolling-upgrade guarantees: two adjacent minor versions never disagree on wire framing or Config schema interpretation, so a mixed-version fleet during a rolling upgrade behaves identically from the client's perspective.

28. Testing & Verification Strategy

Unit tests: per-crate (§10), covering codec edge cases, matcher logic, and transform rules in isolation. Integration tests: conformance/ scenarios (§10) drive the full binary end-to-end. Property tests: the routing matcher and cache freshness-lifetime computation are property-tested against randomly generated route sets and Cache-Control header combinations, asserting the invariants of §7 hold for all generated inputs. Differential testing: the conformance harness's NGINX/Envoy/Caddy diff mode (§23 (11.2)) is differential testing at the system level. Fuzzing: fuzz/fuzz_targets/ (§10) — h1_codec, h2_codec, header_parse, chunked_decode, path_match, waf_eval, cache_key, tls_record — run continuously in CI (fuzz.yml, §10) and on a schedule against an accumulating corpus. Chaos/fault injection: soak.yml (§10) injects upstream resets, DNS failures, and JWKS unavailability during a sustained load run, verifying FM-1/FM-3/FM-5 recovery paths (§25) actually fire. Deterministic replay: the invariant-mode simulator (§7 debugging methodology) replays captured production traffic offline before every release. Soak testing: 10,000 sequential reloads (§23 (11.4)) and a 24-hour sustained-load run with heaptrack RSS tracking. Conformance: the full scenario corpus (§10) at 100% Pass for P0/P1 categories gates every release; P2 gates the Phase-11 milestone (Appendix B). Performance- regression gating: every M# row in §30 is checked in CI against the previous release's recorded value, failing the build on regression beyond a 10% tolerance band. Every fixture referenced in a phase's N.5 (§12–§23) is a named file under conformance/scenarios/, tying this strategy directly back to the phase plan and to the System Invariants (§7).

30. Performance Engineering

Benchmarking methodology: benchmarks/ (§10) uses Criterion-style statistical benchmarking for micro-targets (transform chain, cache lookup) and a dedicated load-generation harness (h1_no_op.rs etc.) for throughput/latency targets, run on the reference hardware (§4: c7g.4xlarge ARM / c7i.4xlarge x86-64). Profiling methodology: perf + flamegraphs for CPU, heaptrack for allocation, tokio-console for task-scheduling/lock-contention visibility — applying Ousterhout's "measure one level deeper" (§5) discipline: a CPU% number alone never closes a performance investigation. Allocation analysis: the hot path (parse → route → forward) is benchmarked for zero-allocation-per-request under steady state, verified via heaptrack diffing against a baseline. Lock-contention analysis: tokio-console flags any await point blocked on a contended mutex; the connection-pool checkout path (§14) is the primary structure held to a lock-free bar. Cache-locality/syscall analysis: batching is applied to host-function calls in the edge runtime (§21 (9.7)) and to socket writes (writev-style vectored I/O) to amortize syscall overhead. Tail-latency analysis: every M# target below is a p99 or p50, never an average — an average hides exactly the tail this system is built to bound (§4's defining property).

31. Scalability Analysis

What stays constant as load grows: per-request added latency (§4's defining property) — the lock-free checkout path (§14) and the radix-tree router (§13) are both designed for O(1)/O(log n) behavior independent of fleet size. What grows: connection count (bounded by FD budget, §4), cache working-set size (bounded by the RSS/disk ceilings, §4), and control-plane reload compilation time (O(routes), the dominant term in M17). Named bottlenecks in order: (1) the per-core accept queue at very high connect-rate bursts (mitigated by SO_REUSEPORT sharding, ADR-17); (2) the upstream connection pool at high fan-out to few endpoints (mitigated by P2C's better tail behavior than round-robin, §5 Mitzenmacher); (3) config-compilation time at very large route counts (mitigated by keeping the reload path off the request path entirely, §23); (4) the regex-route budget cap (I9) as a deliberate ceiling, not an incidental one. Horizontal scaling: add nodes behind DNS/L4 balancing — the design's statelessness (§26) makes this the primary lever. Vertical scaling: add cores, each running its own SO_REUSEPORT shard — near-linear to the point the shared upstream connection pool's cross-core coordination (still lock-free, §14) becomes visible in profiling. Sharding/partitioning: the cache is not sharded across nodes by default (each node's cache is independent, hit-rate optimization only, §26) — cross-node cache coherence is explicitly out of scope (a CDN-tier concern, §1 non-goals). Coordination overhead: the only cross-node coordination in the base design is DNS-based service discovery refresh (§14) and the single-node ACME orchestrator designation (I13) — both bounded, neither in the request path. Practical ceiling: a single node's ceiling is the FD budget (§4, ~500K connections) or the 100,000 rps/core throughput target times core count, whichever binds first for a given traffic shape. Levers beyond the ceiling: horizontal scale-out (primary), the deferred xDS/multi-tenant control plane for centralized fleet-wide routing decisions (§37), and kernel TLS offload (§37, deferred) to push handshake cost off userspace CPU entirely.

32. Mental Models & First Principles

  • MM1 — A connection is a state machine, not a byte pipe. Predicts: every protocol bug is a missed or malformed state transition. Without it: ad-hoc flag-based logic that cannot express valid transition ordering, the root shape of the smuggling and desync bug classes. Applied in §8, §12.
  • MM2 — Config is a value, not a place. A Config generation is immutable once compiled; reload produces a new value, never mutates the old one in place. Predicts: hot reload is safe exactly when no code holds a mutable reference across generations. Without it: reload races and dropped in-flight requests. Applied in §11, §23, §7 I1.
  • MM3 — The pool owns trust, not the connection. A pooled connection is guilty (untrusted) until health-checked; trust is a property the pool asserts, not one the connection carries. Predicts: errors compound only until the poisoned connection is excised, never further. Without it: error amplification across otherwise-healthy traffic sharing a bad connection. Applied in §14, §7 I3, §6 P7.
  • MM4 — Cache correctness is a freshness proof, not a TTL guess. Every serve decision must cite the RFC 9111 clause that permitted it. Predicts a cache that never "mostly" follows the spec. Without it: silent staleness or over-caching of security-sensitive responses. Applied in §16, §6 P3.
  • MM5 — A sandbox is a budget, not a promise. Safety holds even against adversarial code because the runtime enforces limits unconditionally, never because the program cooperates. Predicts a bounded blast radius regardless of program intent. Without it: the standard multi-tenant-plugin failure mode — trusting "well-behaved" code. Applied in §21, §6 P6, §7 I7.
  • MM6 — Backpressure is a design decision, not an accident. Every queue has a bounded depth and an explicit rejection policy. Predicts unbounded queues always eventually become an outage. Without it: OOM under a slow-downstream/fast-upstream (or reverse) mismatch. Applied in §6 P11, §14.
  • MM7 — Every constraints-table number is a promise the architecture keeps, derived, not asserted. Predicts a system whose §4 numbers cannot be traced to a design choice is unreviewable by definition. Without it: an architecture that "feels fast" with no basis for its SLO. Applied in §4, §34.
  • MM8 — Two truths about time: wall-clock for humans, monotonic for correctness. Predicts that an NTP jump or leap second must never perturb a timeout comparison or freshness calculation. Without it: reload/health-check flapping correlated with clock adjustments rather than real signal. Applied in §6 P12, §12.

NGINX made the opposite extensibility bet: compiled C modules chosen at build time, not a sandboxed runtime plugin. It wins where the configuration is close to static, raw per-connection throughput matters more than dynamic per-tenant logic, and the operator base's decades of NGINX familiarity outweighs the benefit of a from-scratch design.

Envoy made xDS the foundation, not an adapter — every config decision flows from a control plane by default. It wins in large, multi-team service-mesh deployments (Istio-adjacent) where centralized policy and per-node config drift being itself the threat model outweigh the cost of requiring a control plane to exist at all — the opposite of this design's non-goals (§1).

HAProxy treats L4 and L7 balancing as one configuration surface with historically simpler (if less request-aware) processing. It wins where connections-per-second and pure TCP-level balancing dominate the traffic shape, and where the full L7 feature set (WAF, edge programs, RFC 9111 caching) this blueprint provides is unnecessary overhead.

Pingora is the closest architectural sibling — same language, same async runtime family, built at Cloudflare's operating scale. It wins where Rust's safety guarantees matter and native filter code is acceptable, but it does not ship a general-purpose sandboxed multi-tenant scripting layer as a first-class primitive the way this design's Wasm/Lua edge runtime (§21) does — the niche this design closes over Pingora's is exactly the "many mutually-untrusted tenants" case (§24 T6).

34. Back-of-Envelope Capacity Model

  1. Peak node throughput = 16 vCPU × 100,000 rps/core (§4) = 1,600,000 rps/node (no-op route ceiling).
  2. FD headroom = 500,000 conns × 2 FDs/conn (downstream + upstream, §4) = 1,000,000 FDs against the 1,048,576 ulimit (§4) → ~4.8% margin, tight enough to justify the FD-budget row existing as its own constraint rather than an afterthought.
  3. Memory floor at the connection ceiling = 500,000 conns × 16 KiB/idle conn (§4, §30 M- adjacent) = 8 GiB, exactly matching §4's process RSS soft ceiling — meaning cache RSS (§4, up to 2 GiB) must be budgeted as a separate pool, not drawn from the same ceiling, once a node approaches its connection limit.
  4. TLS handshake supply vs. demand = 8,000 handshakes/s/core (§4) × 16 cores = 128,000 handshakes/s/node supply. At 1,600,000 rps with an assumed 1% cold-handshake rate, demand = 16,000 handshakes/s → 8× headroom against supply.
  5. Cache disk-tier addressable objects = 50 GiB disk tier (§4) ÷ 20 KiB assumed average object size = ~2.5M objects/node.
  6. Bandwidth at peak = 1,600,000 rps × 8 KiB assumed average response size = 12.8 GB/s ≈ ~102 Gbps/node — this exceeds a typical 25/50 Gbps NIC, deriving (not asserting) that throughput at this response size is NIC-bound before CPU-bound, directly feeding the bottleneck ordering in §31.
  7. Edge-program CPU fan-out = at 1,600,000 rps with edge programs on 10% of routes and a 100 µs budget each (§30 M13) = 160,000 invocations/s × 100 µs = 16 core-seconds/s demanded ≈ 16 cores fully dedicated — showing the 100 µs default budget is conservative, not generous: at that coverage it would saturate an entire reference node's CPU.
  8. WebSocket memory cross-check = 100,000 concurrent WS/node (§4, §30 M15) × 16 KiB/conn = 1.6 GiB, well under the 8 GiB RSS budget → confirms WebSocket capacity is FD-bound, not memory-bound.
  9. Reload compile-time budget = 100 ms p99 (§30 M17) ÷ 10,000 routes = 10 µs/route amortized compilation budget — a concrete per-route cost ceiling for anyone adding a new matcher type in a future phase.
  10. Regex-route evaluation cost bound = the 1,000-regex-route cap (§13) does not multiply per request — routing evaluates in priority order and stops at the first match, so a request's worst case is bounded by I9's per-match instruction budget times the number of higher-priority routes actually evaluated before a match, never the full 1,000.

Every number above chains from the §4 constraints table with its formula shown, per the god-level bar's requirement that no capacity number stand asserted alone.

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Thread-per-connection, blocking I/O.

  conn 1 ──► [ OS thread, blocking read()/write() ]
  conn 2 ──► [ OS thread, blocking read()/write() ]
  conn N ──► [ OS thread, blocking read()/write() ]

Regime where it wins: low concurrency (< 1,000 conns/node) or workloads where per-request CPU dominates I/O wait, and where async-runtime complexity is not worth paying for. Real system: Apache httpd's prefork/worker MPM. Why rejected: does not scale to the 500,000-connection ceiling (§4) — a thread per connection at that scale exhausts kernel scheduler capacity and per-thread stack memory far before the event-driven model's limits are reached.

Alternative 2 — Kernel-space/eBPF (XDP) accelerated pre-filter.

  NIC ──► [ eBPF/XDP: drop/allow/simple-route in-kernel ] ──► userspace L7 proxy (only survivors)

Regime where it wins: extreme throughput floors (millions of rps) where even a userspace event-loop is the bottleneck, e.g. DDoS-scrubbing edges. Real system: Cloudflare's XDP-based L4 mitigation layer, deployed in front of (not instead of) a Pingora-style L7 proxy. Why rejected: eBPF/XDP cannot run arbitrary WAF regex evaluation, Wasm sandboxing, or the RFC 9111 cache state machine — it is a complementary L4 pre-filter, never a substitute for this system's L7 request-awareness (§1 scope).

Alternative 3 — Fully declarative, control-plane-driven (xDS-native).

  Control plane (Istio-style) ──stream(xDS)──► Data plane (no local config file)

Regime where it wins: large multi-team service-mesh deployments where centralized policy must be the single source of truth and per-node config drift is itself the threat model. Real system: Envoy inside Istio. Why rejected: couples every deployment to running a control plane (§1 non-goals explicitly exclude this); this blueprint keeps xDS a Phase-11+ adapter (§9 ADR-15) so the common single-team, single-config-file case never pays that coupling cost.

Alternative 4 — Pure Layer-4 (TCP/UDP) passthrough, SNI-only routing.

  client ──TCP──► [ SNI sniff, no HTTP parse ] ──TCP──► origin (TLS terminates at origin)

Regime where it wins: extreme low-latency requirements where even microsecond-scale request parsing is unacceptable (e.g. HFT gateways), or where TLS must terminate only at the origin for compliance. Real system: LVS/IPVS, or HAProxy in mode tcp. Why rejected: forecloses every feature this system exists to provide — path/header/JWT routing, RFC 9111 caching, the WAF, transformation — this is the Load-Balancer document's domain (§1, §33), a different system by definition, not a rejected parameter of this one.

38. Glossary

  • ALPN — Application-Layer Protocol Negotiation; TLS extension selecting h1/h2/h3 during the handshake (§17).
  • SNI — Server Name Indication; the plaintext hostname sent in ClientHello, used for cert selection (§17).
  • HPACK — HTTP/2's header-compression format with a stateful dynamic table (§22).
  • QPACK — HTTP/3's header-compression format, decoupled from stream ordering (§22).
  • Backpressure — an explicit, bounded rejection policy applied when a queue would otherwise grow without limit (§6 P11).
  • Circuit breaker — a per-endpoint state machine that stops sending traffic to a failing endpoint before every request against it times out individually (§14).
  • Consistent hashing — a hashing scheme where membership changes remap only a bounded fraction of keys (§14, §5 Karger et al.).
  • Content-Length — the HTTP header declaring a fixed request/response body length in bytes.
  • Chunked transfer-encoding — an HTTP/1.1 body-framing mode using length-prefixed chunks terminated by a zero-length chunk (§12).
  • Cache stampede — a burst of simultaneous origin requests caused by many clients missing the cache for the same resource at once (§25 FM-2).
  • Cold handshake — a full TLS handshake with no resumed session, the more expensive of the two handshake paths (§4, §30 M9).
  • Session resumption — reusing a previously negotiated TLS session's keys via a ticket or ID to skip the full handshake (§17).
  • OCSP stapling — the server attaching a signed certificate-revocation-status response to the handshake instead of the client querying the CA directly (§17).
  • mTLS — mutual TLS; both peers present and verify certificates (§17, §19).
  • JWKS — JSON Web Key Set; the published set of public keys used to verify JWT signatures (§19).
  • Anomaly scoring — a WAF technique where each matched rule contributes to a cumulative score that trips a block threshold, rather than any single match blocking alone (§20).
  • CRS — the OWASP Core Rule Set, a portable WAF rule baseline (§5, §20).
  • Fuel (Wasm) — wasmtime's instruction-metering mechanism used to bound a guest program's CPU consumption (§21).
  • Epoch interruption — wasmtime's mechanism for bounding a guest program's wall-clock execution time independent of fuel (§21).
  • Wasm Component Model — a WebAssembly extension standardizing cross-language component interfaces (WIT), used for the edge-program host ABI (§21).
  • WASI — the WebAssembly System Interface, a standardized set of host capabilities for Wasm guests (§21).
  • LuaJIT — a just-in-time compiling implementation of Lua, embedded via mlua (§21).
  • Token bucket — a rate-limiting algorithm allowing bursts up to a bucket capacity while enforcing a steady-state refill rate (§20, §9 ADR-11).
  • P2C — power-of-two-choices; sample two candidates, pick the less-loaded (§14, §5 Mitzenmacher).
  • Round robin — cyclic, fixed-order endpoint selection (§14).
  • Least connections — selecting the endpoint with the fewest in-flight requests (§14).
  • Active health check — a proxy-initiated periodic probe against an upstream endpoint (§14).
  • Passive health check — inferring endpoint health from the outcome of real proxied requests (§14).
  • Ejection — removing an endpoint from selection eligibility after a health-check failure threshold (§7 I10, §8).
  • Probation — a capped-traffic re-admission state between Ejected and Healthy (§8).
  • Hop-by-hop header — a header meaningful only for one transport hop, never forwarded across a proxy boundary (§6 P14, section 7.6.1 of RFC 9110).
  • Vary header — an HTTP response header naming request headers a cache must also key on (§16).
  • Surrogate key — an out-of-band cache tag enabling bulk invalidation across many cached entries at once (§16).
  • Stale-while-revalidate — serving a stale cached response while a background request refreshes it (§16).
  • RTO — Recovery Time Objective; the target maximum time to restore service after a failure (§4).
  • SLO — Service Level Objective; an internal target a system is held to (§26).
  • Trailers — headers sent after a chunked or HTTP/2 body, rather than before it (§12, §22).
  • Extended CONNECT — the RFC 8441 mechanism bootstrapping WebSocket over HTTP/2 (§22).
  • 0-RTT — TLS 1.3's zero-round-trip early-data mode, replay-vulnerable and restricted to idempotent methods here (§22, §24 T12).
  • Slowloris — an attack sending data slowly enough to hold a connection open without triggering a byte-level timeout (§24 T2).
  • Request smuggling — exploiting disagreement between two HTTP parsers over where one request ends and the next begins (§8, §24 T1).
  • ReDoS — Regular-expression Denial of Service via catastrophic backtracking (§24 T10).
  • SBOM — Software Bill of Materials; a manifest of a build's dependency graph (§29).
  • Reproducible build — a build process guaranteed to produce bit-identical artifacts from the same source (§29).
  • Generation (Config) — one immutable, atomically-swapped version of the compiled Config (§7 I1, §11, §23).
  • Graceful drain — completing in-flight requests before closing a connection during shutdown or reload, rather than aborting them (§6 P1, §12).
  • Radix tree — a compressed prefix tree used here for longest-prefix-wins path routing in sub-linear time (§13).
  • Timing wheel — an O(1)-amortized data structure for scheduling large numbers of timeouts (§5 Varghese & Lauck, §12).
