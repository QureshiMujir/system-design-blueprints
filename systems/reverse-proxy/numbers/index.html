34. Back-of-Envelope Capacity Model

  1. Peak node throughput = 16 vCPU × 100,000 rps/core (§4) = 1,600,000 rps/node (no-op route ceiling).
  2. FD headroom = 500,000 conns × 2 FDs/conn (downstream + upstream, §4) = 1,000,000 FDs against the 1,048,576 ulimit (§4) → ~4.8% margin, tight enough to justify the FD-budget row existing as its own constraint rather than an afterthought.
  3. Memory floor at the connection ceiling = 500,000 conns × 16 KiB/idle conn (§4, §30 M- adjacent) = 8 GiB, exactly matching §4's process RSS soft ceiling — meaning cache RSS (§4, up to 2 GiB) must be budgeted as a separate pool, not drawn from the same ceiling, once a node approaches its connection limit.
  4. TLS handshake supply vs. demand = 8,000 handshakes/s/core (§4) × 16 cores = 128,000 handshakes/s/node supply. At 1,600,000 rps with an assumed 1% cold-handshake rate, demand = 16,000 handshakes/s → 8× headroom against supply.
  5. Cache disk-tier addressable objects = 50 GiB disk tier (§4) ÷ 20 KiB assumed average object size = ~2.5M objects/node.
  6. Bandwidth at peak = 1,600,000 rps × 8 KiB assumed average response size = 12.8 GB/s ≈ ~102 Gbps/node — this exceeds a typical 25/50 Gbps NIC, deriving (not asserting) that throughput at this response size is NIC-bound before CPU-bound, directly feeding the bottleneck ordering in §31.
  7. Edge-program CPU fan-out = at 1,600,000 rps with edge programs on 10% of routes and a 100 µs budget each (§30 M13) = 160,000 invocations/s × 100 µs = 16 core-seconds/s demanded ≈ 16 cores fully dedicated — showing the 100 µs default budget is conservative, not generous: at that coverage it would saturate an entire reference node's CPU.
  8. WebSocket memory cross-check = 100,000 concurrent WS/node (§4, §30 M15) × 16 KiB/conn = 1.6 GiB, well under the 8 GiB RSS budget → confirms WebSocket capacity is FD-bound, not memory-bound.
  9. Reload compile-time budget = 100 ms p99 (§30 M17) ÷ 10,000 routes = 10 µs/route amortized compilation budget — a concrete per-route cost ceiling for anyone adding a new matcher type in a future phase.
  10. Regex-route evaluation cost bound = the 1,000-regex-route cap (§13) does not multiply per request — routing evaluates in priority order and stops at the first match, so a request's worst case is bounded by I9's per-match instruction budget times the number of higher-priority routes actually evaluated before a match, never the full 1,000.

Every number above chains from the §4 constraints table with its formula shown, per the god-level bar's requirement that no capacity number stand asserted alone.
