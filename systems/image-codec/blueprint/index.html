173 — Image Codec (JPEG + PNG)

Project Number: 173

Project Name: Image Codec (JPEG + PNG)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

A from-scratch image codec library in Python implementing two independent pixel pipelines against their published specifications rather than by porting existing C codecs: a lossy pipeline (baseline and progressive JPEG per ITU-T T.81 / ISO 10918-1) and a lossless pipeline (PNG per the W3C/ISO PNG specification, second edition, and RFC 2083). Both pipelines share a bit-level I/O layer, an ImageBuffer pixel model, a decoder-hardening/validation layer that treats every input byte as adversarial, and a quality/ratio measurement harness (PSNR, SSIM, bits-per-pixel). The system reads compressed bytes, produces validated pixels, and reverses the process on encode; malformed input is rejected without unbounded allocation or unbounded decode time.

Phase-0 deliverable — the following packages exist, import cleanly, and pass a smoke test (P1, I2):

  1. imgcodec.bitio — BitReader / BitWriter, MSB-first and LSB-first bit orders.
  2. imgcodec.buffer — ImageBuffer, ColorType, BitDepth, PixelFormat.
  3. imgcodec.limits — DecodeLimits, allocation/time-bound enforcement.
  4. imgcodec.errors — the CodecError taxonomy.
  5. imgcodec.cli — a skeleton CLI (imgcodec identify <file>) wired to CI.

Provides: baseline + progressive JPEG decode/encode; full-color-type, full-bit-depth PNG decode/encode with Adam7 interlacing; a shared bit-reader/writer; a decoder-hardening layer with quantified allocation and time bounds; a conformance/fuzzing harness; a PSNR/SSIM/bpp measurement CLI. Delegates: no automatic repair of corrupt files beyond the documented recovery rules (§25); no GPU acceleration (PhaseDeferred("§31")); no color-managed rendering pipeline beyond gAMA/sRGB/iCCP pass-through. Does NOT provide: JPEG 2000, WebP, AVIF, HEIF, or any wavelet/transform-coding codec beyond DCT (§36 covers why); a general ICC-profile transform engine; video or animation (APNG) support; GPU/SIMD-intrinsic kernels.

Non-goals: not a JPEG 2000 implementation; not WebP/AVIF/HEIF; not a color-management engine — ICC profiles are parsed, validated, and passed through, never applied.

Deployment model: (a) a library (import imgcodec) for embedding; (b) a CLI (imgcodec encode|decode|identify|measure) for batch/scripting; (c) a conformance harness (conformance/run.py) run in CI and by hand against the specification's own test vectors and a differential corpus. Users/operators: application engineers embedding image I/O; security engineers auditing decoder hardening; the CI system running the fuzz/conformance/perf gates. Later phases unlock: Phase 4 unlocks full-corpus PNG round-tripping; Phase 8 unlocks a usable baseline JPEG codec; Phase 10 unlocks safety against untrusted input; Phase 11 unlocks quantitative quality comparison against reference codecs.

Language: Python 3.11+. Rationale: the domain payoff is understanding the DCT, entropy coding, and filter mathematics precisely — Python's readability keeps the spec-to-code mapping legible, and its standard library (array, struct, an optional zlib binding) covers byte-level plumbing without a build system (ADR-01). Numeric-core strategy: NumPy ndarray operations vectorize the block-parallel, embarrassingly-parallel stages — color transform, DCT/IDCT via matrix multiply, quantization, chroma resampling, scanline-filter application post-decode — across a whole image at once; the inherently sequential, bit-at-a-time stages (Huffman/LZ77 bitstream state machines) stay pure Python behind an interface that an accelerated backend can later replace without touching call sites (PhaseDeferred("§31")). Rejected languages: Rust — strong memory safety, but its type-system ceremony obscures the algorithm on a first build (ADR-01); C/C++ — matches reference-implementation performance but forfeits the memory safety this build is partly meant to study, reintroducing the exact CVE class (ADR-01); Go — weak numeric/array ecosystem and no operator overloading, awkward for matrix-shaped DCT code (ADR-01).

Prerequisites: linear algebra (DCT matrix factorization, separability); information theory (entropy, Kraft inequality, Huffman optimality); entropy coding (canonical Huffman construction, LZ77 dictionary coding); discrete-time signal processing (frequency-domain intuition for quantization); elementary probability/statistics (PSNR/SSIM as error-distribution measures).

Timeline: Phase 0 — 1 week. Full system (Phases 0–11) — 5–6 months at sustained part-time pace: PNG pipeline (Phases 0–4) ~6 weeks, JPEG pipeline (Phases 5–9) ~10 weeks, hardening + metrics (Phases 10–11) ~4 weeks.

Deferrals: PhaseDeferred("§31") — GPU/SIMD acceleration of the DCT and Huffman inner loops; PhaseDeferred("§36") — a JPEG 2000/wavelet alternate pipeline; PhaseDeferred("§27") — a byte-identical-across-versions encoder-output guarantee; PhaseDeferred("§37") — an arithmetic-coding entropy backend for JPEG.

2. Why Build This

  • DCT-based perceptual coding — the foundational lossy-compression idea, echoed by MPEG/H.26x intra-frame coding and the block-transform ancestry of HEIC/AVIF.
  • Canonical Huffman + LZ77 — the two-idea backbone of DEFLATE, gzip, and zlib; understanding it here transfers directly to any DEFLATE-adjacent format.
  • Decoder hardening — the single largest CVE-driving lesson in the C-codec ecosystem (MS04-028, the 2015 libpng CVEs, BLASTPASS); building the validation layer from first principles internalizes "parse, don't trust."
  • Bit-level state machines — MSB-first vs. LSB-first bit orders, canonical code assignment, byte-stuffing — transferable to any binary-protocol work.
  • Chunk/container parsing discipline — PNG's CRC-guarded chunk model and JPEG's marker-segment model are two working instances of the same container pattern used elsewhere in the portfolio.
  • Quantitative quality measurement — PSNR/SSIM turn "looks fine" into a number, the discipline any lossy-system regression gate needs.
  • Direct utility — texture/asset loading for Game-Engine-Core (#172) and the software rasterizer (#169) depends on correct image decode.

What Mastery Looks Like

  • Derive the 2-D DCT's separability into row/column 1-D passes and explain why it collapses the multiply count, from Phase 6.
  • Explain why a canonical Huffman code needs only code lengths, not the tree itself, to reconstruct bit-identically, from Phase 7.
  • Explain why PNG's Paeth filter looks at three neighbors yet stays a linear predictor followed by modular subtraction, from Phase 3.
  • Show, with a computed byte count, that 4:2:0 chroma subsampling is a data-rate decision made before entropy coding, from Phase 5.
  • Enumerate the decompression-bomb attack surface in DEFLATE and state the exact allocation-time defense used here, from Phase 10.
  • Defend PSNR's blind spot on structural artifacts using a measured SSIM-vs-PSNR disagreement case, from Phase 11.
  • Trace a truncated file through the decoder state machine to the exact byte offset where recovery diverges from a crash, from Phase 10.
  • Contrast Huffman's unencumbered history against arithmetic coding's patent history and state why that mattered operationally in the 1990s, from Phase 7.

Format Sniffer — reads the first 8 bytes; dispatches to PNG or JPEG parser on an exact signature/marker match; anything else is CodecError.InvalidSignature before any further read. PNG Container Parser — walks <len><type><data><crc> chunks; validates CRC-32 (I4) before returning chunk data to any consumer; enforces IHDR-first / IEND-last ordering. JPEG Container Parser — walks marker segments (SOI, APPn, DQT, DHT, SOF0/SOF2, SOS, EOI); handles byte-stuffing (0xFF 0x00) inside entropy data; validates marker length fields against remaining bytes. DecodeLimits gate — the buffer boundary: computes width × height × channels × bytes_per_sample with checked (overflow-safe) arithmetic and rejects before any pixel buffer is allocated (P1, I2, T2). Shared BitReader/BitWriter — two instances, MSB-first (JPEG) and LSB-first (DEFLATE/PNG); never interchanged (P10); both refuse to read past the declared buffer end (I3). DEFLATE Inflate — RFC 1951 LZ77 + Huffman decoder with a 32 KiB sliding window; enforces the decompression-bomb bound (I11, T3) during streaming, not after. Huffman Entropy Decoder (JPEG) — decodes DC/AC symbols via canonical codes; rejects over-subscribed tables (I5); resets DC predictors on restart markers (I8). Scanline Unfilter — applies the inverse of one of five PNG filter types per row; requires the previous row to already be materialized (I10) before Up/Average/Paeth math runs. Dequantize + Zigzag + IDCT — reverses zigzag order, multiplies by the quantization table, runs the separable inverse DCT (P4, P11). Adam7 Deinterlace — reassembles the seven interlace passes into the final scanline grid; validates per-pass geometry sums to the declared image size (I9). Chroma Upsample + YCbCr→RGB — reconstructs full-resolution chroma planes, applies the fixed-point color-space transform, clamps to the pixel format's range. ImageBuffer — the one pixel representation both pipelines converge on; the trust boundary is crossed outward here — everything downstream trusts this buffer. PNG Encoder — selects a per-scanline filter heuristically, re-filters, and re-DEFLATEs into IDAT chunks with recomputed CRC-32. JPEG Encoder — forward color transform, chroma subsample, forward DCT, quality-scaled quantization, zigzag, RLE, Huffman encode, marker assembly. Quality Metrics Harness — computes PSNR, SSIM, and bits-per-pixel between a reference and a codec-round-tripped ImageBuffer (§11, §28). CLI — imgcodec entry points wiring the above into scriptable commands; the operator-facing surface (§26).

6. Design Principles

P1 — Hostile input first. Every input is hostile until validated; the decoder allocates only after dimensions and color type are checked against declared bounds. Tradeoff: an extra validation pass before any useful work. Operational implication: header parsing is always the very first stage, never interleaved with allocation. Violating it: an attacker-controlled length field drives an allocation before it is range-checked, enabling T2/T3.

P2 — Bit-exact lossless. A lossless pipeline must be bit-exact on round-trip, and the test suite proves it, because "looks the same" is not a lossless claim. Tradeoff: no filter/compression shortcut may introduce even 1-bit drift. Operational implication: PNG round-trip tests compare raw bytes, never a perceptual metric. Violating it: silent precision loss in a color-type conversion masquerading as lossless.

P3 — Spec conformance outranks reference-implementation agreement. Conformance against the specification's own test vectors outranks agreement with any single reference implementation. Tradeoff: occasionally disagreeing with libjpeg-turbo on an edge case the spec leaves implementation-defined. Operational implication: the conformance suite (§28) runs spec vectors and differential tests, and a spec-vector failure blocks release even if differential tests pass. Violating it: silently copying a reference decoder's spec deviation forward.

P4 — Exploit separability. Factor 2-D transforms into row/column 1-D passes wherever the math allows (the DCT). Tradeoff: two passes over the data instead of one dense matrix multiply, but far fewer total multiplies. Operational implication: dct.py never implements the naive O(N⁴)-per-block form in the hot path. Violating it: an O(N⁴) DCT implementation that technically works but blows the throughput target (M-table, §30).

P5 — Canonical codes over explicit trees. A canonical Huffman code's wire format is a code-length array; the canonical assignment rule reconstructs identical codes deterministically. Tradeoff: encoder must sort by (length, symbol) before assigning codes. Operational implication: HuffmanSpec never serializes a tree — only lengths and a value order. Violating it: ambiguous code assignment that decodes differently across implementations.

P6 — Stream where the algorithm allows. Process one scanline / one MCU at a time to bound memory to O(row) or O(block), not O(image). Tradeoff: less opportunity for whole-image optimization (e.g., global filter search). Operational implication: the PNG unfilter and JPEG MCU loop hold at most two rows / one MCU of state. Violating it: an O(image) buffer that defeats the memory ceiling in §4.

P7 — Perceptual loss is chosen, not incidental. The quantization table is the perceptual model; every rounding decision in JPEG traces back to that table. Tradeoff: quality is a single scalar knob mapped through a fixed table shape (ADR-05). Operational implication: quality-to-scale mapping (§8) is the one place perceptual tuning lives. Violating it: ad hoc per-coefficient rounding rules that aren't derivable from the table.

P8 — Fail closed. An ambiguous or partially invalid structure (an over-subscribed Huffman table, an oversized chunk) is rejected, never guessed at. Tradeoff: some malformed-but-benign files that lenient decoders accept are rejected here. Operational implication: strict_crc/strict_eof default true (ADR-19). Violating it: a lenient guess that happens to work on the fuzz corpus but not on a crafted exploit (T5).

P9 — Bounded decode time regardless of outcome. An accept path and a reject path both terminate within the declared time/allocation budget. Tradeoff: some legitimate very-large images require the caller to explicitly raise DecodeLimits. Operational implication: the decompression-bomb check runs during streaming inflate, not after full decompression (I11). Violating it: unbounded inflate loop before the size check fires (T3).

P10 — One bit order per format. JPEG is MSB-first; DEFLATE is LSB-first; the two BitReader instances are never interchangeable. Tradeoff: two separate bit-reader code paths instead of one generic one. Operational implication: BitReader(order=...) is a required constructor argument, never a default. Violating it: a shared "clever" bit reader that silently misdecodes one format under refactor pressure.

P11 — Numeric precision is a stated contract. IDCT precision (32-bit fixed-point, ADR-04) is chosen once and documented; it is not silently promoted to float in one code path and int in another. Tradeoff: fixed-point requires explicit scale-factor bookkeeping. Operational implication: Block8x8 carries an explicit dtype/scale annotation. Violating it: mixed float/int paths producing different rounding on encode vs. decode (I1's cousin for JPEG's own regression tests).

P12 — Every quantitative claim is measured. PSNR/SSIM/bpp numbers in this document and in the shipped harness come from the same measurement code (imgcodec.metrics). Tradeoff: the harness must ship as a first-class module, not a one-off script. Operational implication: §4's numeric targets are gated in CI by the same code that produced them (§30). Violating it: a hand-waved "looks about right" quality claim.

P13 — Metadata is inert. EXIF/ICC data is parsed and validated but never executed or interpreted as anything but data. Tradeoff: no automatic color-profile application, only pass-through (§1 non-goals). Operational implication: the EXIF parser never invokes an external interpreter (contrast with the ImageMagick/Ghostscript incident class, §24). Violating it: treating a TIFF-shaped EXIF blob as trusted structured input beyond its own bounds.

P14 — The entropy table bounds the quantizer. Quantized coefficients must fit the categories the Huffman tables can represent; this constrains the encoder before it constrains the decoder. Tradeoff: extreme low-quality encodes must clamp rather than saturate silently. Operational implication: the encoder's quantization step clamps to the category range the standard Huffman tables define (§8). Violating it: an encoder emitting a coefficient magnitude the standard tables cannot categorize, producing an undecodable file.

8. Domain Model

8.1 Color transform (JPEG, JFIF convention)

Forward (RGB → YCbCr):

Y  =  0.299   R + 0.587   G + 0.114   B
Cb = -0.168736 R - 0.331264 G + 0.5     B + 128
Cr =  0.5     R - 0.418688 G - 0.081312 B + 128

Inverse (YCbCr → RGB):

R = Y                       + 1.402   (Cr - 128)
G = Y - 0.344136 (Cb - 128) - 0.714136 (Cr - 128)
B = Y + 1.772   (Cb - 128)

Fixed-point form (ADR-04): each coefficient scaled by 2^10 and rounded to an integer; multiply, sum, then arithmetic-shift right 10, matching the precision policy in P11.

8.2 Forward/inverse DCT-II, 8×8

Forward:

F(u,v) = (1/4) C(u) C(v) Σx Σy f(x,y) cos((2x+1)uπ/16) cos((2y+1)vπ/16)
C(0) = 1/√2 ;  C(k>0) = 1

Inverse:

f(x,y) = (1/4) Σu Σv C(u) C(v) F(u,v) cos((2x+1)uπ/16) cos((2y+1)vπ/16)

Separability (P4): the 2-D sum factors into an 8-point 1-D DCT applied to each row, then an 8-point 1-D DCT applied to each resulting column — 16 one-dimensional transforms per block instead of one 2-D convolution.

8.3 Quantization / dequantization and quality mapping

Fq(u,v)  = round( F(u,v) / Q(u,v) )                     [encode]
F'(u,v)  = Fq(u,v) × Q(u,v)                              [decode]
scale    = quality < 50 ? floor(5000/quality) : 200 - 2×quality
Q(u,v)   = clamp( floor((Qbase(u,v)×scale + 50)/100), 1, 255 )

quality=50 → scale=100 → Q=Qbase; quality=100 → scale=0 → Q≈1 (near-lossless); quality=1 → scale=4900 → Q saturates at 255. Monotonicity (I14) follows directly from scale being monotonic non-increasing in quality.

8.5 DC differential coding

DIFF = DC_i − DC_{i−1} (per component, reset to 0 at SOI and at every restart marker per I8). Encoded as (category, sign-magnitude bits) where category = number of bits needed to represent |DIFF| (0 for DIFF=0).

8.6 Run-length / end-of-block AC symbol structure

Each AC Huffman symbol byte = (RUNLENGTH << 4) | SIZE. RUNLENGTH = zero-run length before the next nonzero (0–15); SIZE = category of the following nonzero's magnitude. Reserved symbols: 0x00 = EOB (all remaining AC coefficients zero); 0xF0 = ZRL (16 zeros, no value, run continues).

8.7 Huffman canonical code construction

Given code-length counts L[1..16] and a value order list: assign codes in increasing length, increasing value order, each length's first code = (previous length's first code + previous length's count) << 1. No two symbols of the same length ever share a numeric code; the code-length array alone reconstructs the table (P5).

8.8 LZ77 match/literal model and DEFLATE block types

Literal: one byte, 0–255. Match: (length, distance), length ∈ [3,258], distance ∈ [1,32768]. BTYPE: 00 stored (raw, byte-aligned), 01 fixed Huffman (RFC 1951 section 3.2.6 fixed tables), 10 dynamic Huffman (tables transmitted per-block), 11 reserved/error.

8.9 PNG per-scanline filter equations (byte-wise, mod 256)

Type Encode (Filt) Decode (Recon)
0 None Filt(x) = Orig(x) Recon(x) = Filt(x)
1 Sub Filt(x) = Orig(x) − Orig(x−bpp) Recon(x) = Filt(x) + Recon(x−bpp)
2 Up Filt(x) = Orig(x) − Prior(x) Recon(x) = Filt(x) + Prior(x)
3 Average Filt(x) = Orig(x) − floor((Orig(x−bpp)+Prior(x))/2) Recon(x) = Filt(x) + floor((Recon(x−bpp)+Prior(x))/2)
4 Paeth Filt(x) = Orig(x) − Paeth(Orig(x−bpp),Prior(x),Prior(x−bpp)) Recon(x) = Filt(x) + Paeth(Recon(x−bpp),Prior(x),Prior(x−bpp))

Paeth(a,b,c): p = a+b−c; pick whichever of a, b, c minimizes |p−a|,|p−b|,|p−c| (ties broken a, then b, then c). bpp = bytes per complete pixel (≥1); out-of-range neighbors (row/column < 0) are treated as 0 (I10).

8.11 CRC-32 (PNG, Ethernet/RFC-1952 polynomial)

Polynomial 0xEDB88320 (reversed representation of 0x04C11DB7), initial value 0xFFFFFFFF, final XOR 0xFFFFFFFF, computed over chunk type + data.

8.12 PSNR and SSIM

MSE  = (1/N) Σ (ref_i − test_i)^2
PSNR = 10 log10( MAXval^2 / MSE )                (MAXval = 255 for 8-bit)
SSIM(x,y) = [(2μxμy+C1)(2σxy+C2)] / [(μx²+μy²+C1)(σx²+σy²+C2)]

evaluated per local window and averaged (Wang et al. 2004); C1=(0.01×255)^2, C2=(0.03×255)^2 for 8-bit images.

8.17 Worked numeric example — one 8×8 luma block, quality 50

Input pixels (row 0, illustrative 8 values, level-shifted by −128): [52,55,61,66,70,61,64,73]−128 = [-76,-73,-67,-62,-58,-67,-64,-55]. Row 1-D DCT (per §8.2) on this row yields a DC-heavy coefficient vector with F(0)≈−509 (scaled) and rapidly decaying AC terms; after all 8 rows then 8 columns (§8.2 separability), the block's F(0,0) (DC) dominates and high-frequency F(u,v) for u+v≥10 are near zero for a smooth patch. Quantizing at quality 50 (Q=Qbase, §8.3) rounds most F(u,v) with u+v≥6 to 0. Zigzag reorders (§8.4) so the surviving nonzeros cluster early; RLE/Huffman (§8.6–8.7) encodes them in roughly 40–60 bits versus 512 bits raw (8×8×8). Reconstruction error after IDCT + level-shift-back is bounded by the discarded high-frequency energy — for a smooth 8×8 patch this is typically < 2 gray levels RMS, consistent with the §4 bit-exactness tolerance.

8.19 Failure-path example

A JPEG truncated mid-MCU 3 of 40 in the only scan: ScanEntropy hits ReadMagnitude with fewer bits than the category demands → UnexpectedEof is raised → the top-level decode call catches it, returns an ImageBuffer populated through MCU 2 with truncated=True and a CodecError.UnexpectedEof attached as partial_error, per I7; no exception escapes to the caller unless strict_eof=True (ADR-19), in which case the call raises instead of returning a partial buffer.

  • Mixing bit orders in one shared BitReader across formats: garbage from byte 0; root cause a "clever" shared reader; debug via a type-level BitOrder mismatch assertion; recovery: separate instantiation per format (P10).

12.9 Failure Analysis

14. Phase 2 — DEFLATE Decode Then Encode

14.1 Objectives

Implement RFC 1951 DEFLATE — inflate first (own implementation, the conformance path, ADR-11), then deflate — plus the zlib-binding fast path.

14.2 Detailed Implementation Steps

  • Decode block header (BFINAL, BTYPE) via the shared BitReader in LSB-first order (P10), per §8.8.
  • Stored blocks: byte-align, read 2-byte LEN + 2-byte one's-complement of LEN, validate before copying raw bytes.
  • Fixed Huffman: hardcode RFC 1951 section 3.2.6's fixed literal/length and distance tables via HuffmanSpec (§8.7, P5).
  • Dynamic Huffman: decode the 19-symbol code-length alphabet, then the literal/length and distance tables per RFC 1951 section 3.2.7; reject over-subscribed tables at construction (I5).
  • Implement the 32 KiB sliding window; back-references read from the window, including the length > distance overlap case (defined behavior, not an error).
  • Wire the streaming decompressed-byte counter against DecodeLimits.bomb_ratio_multiple × declared_size (I11, T3, P9), checked every output chunk, not after full inflate.
  • Implement the zlib wrapper (RFC 1950): 2-byte header validation, Adler-32 trailer check.
  • Implement the zlib-binding fast path (ADR-11) behind the same inflate()/deflate() interface, selected by a backend= parameter defaulting to "zlib".
  • Own encoder (deflate.py): LZ77 greedy matcher (min match 3, max 258, max distance 32768) + dynamic Huffman table construction mirroring §8.7's canonical assignment.

14.3 Deliverable

inflate(deflate(data)) == data for the full conformance/fixtures/deflate/ corpus, both backends; a hand-crafted stream exercising all three block types decodes correctly.

14.4 Acceptance Criteria

  • 100% round-trip byte-identity over a 200-file corpus spanning 0 bytes to 10 MiB, both backends (own, zlib).
  • Own-backend inflate throughput ≥ 1 MP/s-equivalent (§4); zlib-backend ≥ 15 MP/s-equivalent (§4).
  • bomb_10kb_to_2gb.bin aborts within max_decode_seconds (2.0 s) and raises AllocationTooLarge, 100% of 20 runs.

14.5 Conformance Fixtures

  • conformance/fixtures/deflate/stored_block.bin — single stored block; expected: byte-identical round trip.
  • conformance/fixtures/deflate/fixed_huffman.bin — single fixed-Huffman block; expected: byte-identical round trip.
  • conformance/fixtures/deflate/dynamic_huffman.bin — multi-block dynamic-Huffman; expected: byte-identical round trip.
  • conformance/fixtures/deflate/bomb_10kb_to_2gb.bin — crafted high-ratio stream; expected: AllocationTooLarge before full expansion.
  • conformance/fixtures/deflate/truncated_mid_block.bin — cut mid-Huffman-code; expected: CodecError.UnexpectedEof.

14.6 Pitfalls

  • Conflating LSB-first bit reads with byte-level multi-bit fields (stored-block LEN is byte-order-normal): silently wrong LEN; recovery: separate "bit-level LSB" reads from "byte-level" reads explicitly.
  • Over-subscribed dynamic Huffman table accepted by a lenient decoder: garbage output instead of a clean reject; recovery: I5's construction-time Kraft-inequality check.
  • Back-reference distance exceeding bytes produced so far: reads uninitialized window memory; recovery: reject if distance > total_output_so_far.
  • Length > distance overlap mishandled as an error instead of the defined repeat behavior: spurious rejects on legal streams; recovery: implement "read what you just wrote" explicitly.
  • Adler-32 (zlib wrapper) vs. CRC-32 (PNG chunks) confusion: validating the wrong checksum; recovery: keep the two checksum implementations in separate modules.

14.7 Performance Concerns

The own-backend Huffman decode dominates cost; batch multi-bit lookups via fast_lookup (§11), reusing Phase 7's fast-table pattern once available. Sliding-window back-reference copies: bulk bytearray slice-assignment, not a byte-at-a-time Python loop, for the non-overlapping case.

14.8 Edge Cases

Empty DEFLATE stream (BFINAL=1, BTYPE=00, LEN=0); a dynamic-Huffman block needing the full 19-symbol code-length alphabet; back-to-back stored blocks with no intervening compressed block; a final block ending mid-byte (trailing bits ignored).

14.9 Failure Analysis

If I11's streaming counter is checked only per-block instead of per-output-chunk, a single crafted block can exhaust memory before the check fires; mitigated by checking at the smallest safe granularity (every window write), not per block (ties T3).

14.10 Operational Notes

Metrics deflate.bomb_limit_hit and deflate.backend_used{own|zlib} feed §26; runbook docs/runbooks/fuzz-crash-reproduction.md covers replaying a fuzz-discovered DEFLATE crash deterministically (§28).

15. Phase 3 — PNG Filters and Lossless Round-Trip

15.1 Objectives

Integrate Phase 2's inflate into the PNG pipeline; implement all five scanline filters' inverse (decode) and forward (encode) forms; reach the first true lossless round trip (I1, P2).

15.2 Detailed Implementation Steps

  • Concatenate all IDAT payloads (Phase 1) into one buffer before inflate — PNG's zlib stream spans chunk boundaries arbitrarily (P8: never assume one IDAT = one filter row).
  • Implement ScanlineFilter decode per §8.9's five equations; maintain exactly two row buffers (current, prior), swapping after each row (P6, I10) — never allocate a full-image buffer for the unfilter step.
  • Compute bpp (bytes-per-complete-pixel) from PixelFormat; for sub-byte bit depths (1/2/4), bpp=1 per the PNG filter definition (filters operate on whole bytes even for sub-byte pixels — flagged early to avoid a Phase-4 confusion).
  • Encoder direction: apply each of the 5 filters (§8.9 Filt equations) to a candidate scanline, pick one via ADR-10's MSAD heuristic, write filter byte + filtered row.
  • Wire the IDAT writer: filtered rows → own-or-zlib deflate (ADR-11) → chunked into IDAT payloads (8 KiB default chunk size) → CRC computed and appended (I4 applies symmetrically to the encoder).
  • First end-to-end round-trip test: encode → decode → byte-compare pixels (I1).

15.3 Deliverable

A grayscale and an RGB PNG (no palette, no interlace yet) round-trip byte-identically through encode→decode.

15.4 Acceptance Criteria

  • 100% byte-identical round trip over conformance/fixtures/png/roundtrip_*.png (20 files, mixed dimensions including 1×1, 1×N, N×1, odd widths).
  • Filter-selection heuristic reduces post-DEFLATE size by ≥15% vs. always-filter-0 on the natural-photograph corpus.
  • Zero row-order violations (I10) across the fixture corpus, asserted in CI.

15.5 Conformance Fixtures

  • conformance/fixtures/png/roundtrip_1x1.png, roundtrip_1xN.png, roundtrip_Nx1.png — degenerate-dimension round trips; expected: byte-identical.
  • conformance/fixtures/png/filter_byte_invalid.png — filter byte value 5 (illegal); expected: CodecError.Malformed("filter_type").
  • conformance/fixtures/png/all_five_filters.png — each scanline uses a different filter type; expected: correct unfilter per row.

15.6 Pitfalls

  • Assuming the "left neighbor" is always 1 byte back: for RGBA8 it's 4 bytes (bpp=4), for 16-bit RGBA it's 8; wrong bpp scrambles color channels while dimensions look correct; debug via a single-pixel-wide test image; recovery: compute bpp from PixelFormat, never hardcode 1.
  • Forgetting the filter-type byte in scanline byte length (1 + ceil(width×bpp_bits/8)): desyncs every row after the first; recovery: a 2-row test image where desync is immediately visible.
  • Treating Average's division as signed instead of floor on a non-negative sum before mod-256 subtraction: recovery: compute in the unsigned/masked domain per the PNG specification's wording.
  • Reading the filtered prior row instead of the reconstructed prior row for Up/Average/Paeth: cascading corruption after row 1; recovery: I10 enforces reconstructed-row use.

15.7 Performance Concerns

Two-row buffer swap avoids O(image) memory (P6), but a per-byte Paeth predictor in pure Python is slow; vectorize with NumPy across a whole row (abs/argmin over the three candidates) rather than a Python loop per byte. Filter selection tries all 5 candidates per row; ADR-10's MSAD heuristic is O(1) per candidate given a vectorized absolute-sum, keeping encode throughput within the M-table targets (§30).

15.8 Edge Cases

A 1-pixel-wide image (every "left neighbor" is the zero-fill case); a 1-row image (every "prior row" is the zero-fill case); bit-depth-1 grayscale with a non-byte-aligned row (7 leftover bits) — filters still operate byte-wise; sub-byte unpacking happens after unfilter (Phase 4).

15.9 Failure Analysis

A single wrong bpp value corrupts every pixel subtly (colors shift, dimensions stay correct) — the most dangerous bug class in this phase because it can pass a cursory visual check; contained by I1's byte-exact (not "looks right") acceptance criterion.

15.10 Operational Notes

Metric png.filter.heuristic_savings_pct tracks ADR-10's assumption in production; a regression here feeds the quality-regression-bisect runbook (§26).

  • conformance/fixtures/color/known_triples.json — 20 hand-computed RGB→YCbCr pairs; expected: exact fixed-point match.
  • conformance/fixtures/color/gradient_10000px.png — synthetic RGB gradient; expected: round-trip RMS ≤1 gray level.
  • conformance/fixtures/color/edge_step.png — a hard chroma edge; expected: bilinear upsample reduces ringing vs. nearest, quantified by the second-derivative metric.

17.6 Pitfalls

  • Off-by-one chroma upsampling at odd image dimensions: a 4:2:0 image with odd width/height has a chroma plane whose dimensions are ceil(width/2), not floor; using floor silently drops the last column/row of chroma data; debug via an odd-dimension fixture; recovery: always ceil chroma-plane dimensions on encode, and replicate the last sample on decode upsample.
  • Using the wrong color-transform matrix (BT.601 vs. BT.709 vs. JFIF's specific rounding constants) inconsistently between encode and decode: manifests as a color-cast round-trip error; recovery: lock to the JFIF constants in §8.1 everywhere, document the choice in ADR-06's rationale.
  • Nearest-neighbor upsampling used silently where bilinear was assumed: manifests as blocky chroma edges the caller didn't expect; recovery: make the upsample strategy an explicit, logged parameter, never a silent default drift.
  • Clamping applied after the fixed-point shift instead of before: manifests as wraparound artifacts near pure black/white; recovery: clamp post-shift, pre-cast-to-uint8, exactly per §8.1's inverse formula order.

17.7 Performance Concerns

Whole-plane NumPy operations make this phase cheap relative to DCT/entropy coding (§30's profiling shows color transform + subsampling under 10% of total JPEG decode time); the main risk is accidentally falling back to a per-pixel Python loop during a "quick fix," which would dominate cost.

17.8 Edge Cases

A 1×1 image (no subsampling possible, chroma plane is 1×1); an odd-width, even-height image (and the reverse); a grayscale JPEG (1 component, no chroma planes at all — color transform is skipped entirely, not degenerate-cased through it).

17.9 Failure Analysis

A chroma-upsampling off-by-one at odd dimensions is a boundary bug that the majority of natural (even-dimensioned, screen-resolution) test images never exercise — it survives casual testing and only surfaces on odd-dimensioned real-world crops; contained by making odd-dimension fixtures a permanent, non-optional part of conformance/fixtures/color/ (§28).

17.10 Operational Notes

Metric jpeg.color.chroma_dim_odd_path_hit tracks how often the odd-dimension code path actually executes in production traffic, guarding against silent bit-rot in a rarely-hit branch.

18. Phase 6 — DCT and Quantization

18.1 Objectives

Implement the forward and inverse 8×8 DCT (§8.2), separable into row/column 1-D passes (P4), plus quantization/dequantization and the quality-to-scale mapping (§8.3, ADR-05).

18.2 Detailed Implementation Steps

  • Implement a slow, direct O(N⁴)-per-block (well, O(N²) per 1-D pass × 2 passes = the naive separable form) float64 reference IDCT/DCT as the correctness oracle (ADR-02, ADR-03) — this is the ground truth every fast path is checked against.
  • Implement the AAN fast IDCT (Arai, Agui & Nakajima 1988; ADR-02) as the production path: butterfly-structured, ~11 multiplies per 8 samples, vectorized across all blocks of an image simultaneously via NumPy's batched matrix multiply (treat the image's blocks as a stacked 3-D array, one matmul per pass).
  • Implement 32-bit fixed-point precision (ADR-04, P11) for the production IDCT path; document the exact scale factor and rounding point (post-IDCT, pre-level-shift-back).
  • Implement QuantTable/QualityScale/ZigzagTable (§11) and the quality→scale formula (§8.3); build the standard base tables (values sourced from the JPEG standard's example luminance/chrominance tables, ITU-T T.81).
  • Implement the encoder's clamp-to-category-range step (I6, P14): a quantized coefficient magnitude that would overflow the largest Huffman category is clamped, counted, and logged, never silently wrapped.
  • Cross-check: for every block in a differential corpus, assert |reference_IDCT(q) - fast_IDCT(q)| ≤ tolerance (feeds §28's property tests).

18.3 Deliverable

A forward-DCT→quantize→dequantize→inverse-DCT round trip on a synthetic 8×8 block matches the worked example in §8.17 within the stated reconstruction-error bound; the fast and reference IDCT agree within tolerance across a 10,000-block corpus.

18.4 Acceptance Criteria

  • Fast IDCT vs. reference IDCT: max per-sample deviation ≤ 2, RMS ≤ 0.5, over 10,000 randomized quantized blocks (I6's neighbor: precision, not just range).
  • Quality-to-scale monotonicity (I14) holds for all 100 integer quality values, 0 violations.
  • DCT/IDCT round trip (forward then inverse, no quantization) recovers the original block within ≤1 gray level RMS over the same 10,000-block corpus (isolates transform error from quantization error).

18.5 Conformance Fixtures

  • conformance/fixtures/dct/worked_example_block.json — the §8.17 worked 8×8 block, expected coefficients and reconstruction error at quality 50.
  • conformance/fixtures/dct/random_blocks_10000.npy — randomized synthetic blocks; expected: fast/reference IDCT agreement within tolerance.
  • conformance/fixtures/dct/quality_monotonicity.json — all 100 quality values' derived Q tables; expected: monotonic non-increasing scale.
  • conformance/fixtures/dct/coefficient_overflow.json — a crafted coefficient exceeding category range at quality 1; expected: clamped + jpeg.encode.coefficient_clamped counter increments (I6).

18.6 Pitfalls

  • Integer overflow in the IDCT's intermediate precision: a 32-bit accumulator can still overflow if intermediate products aren't bounded (e.g., chaining fixed-point multiplies without intermediate rescale); debug via the coefficient-overflow fixture at extreme quantization; recovery: rescale after each butterfly stage per the AAN paper's documented bit-growth analysis.
  • Color banding from quantization-table rounding: visible at low quality on smooth gradients; root cause: round() vs. floor() inconsistency between encode and the standard's definition; debug via the edge_step-style gradient fixture reused from Phase 5; recovery: lock to round-half-to-even or the standard's exact rounding rule, applied identically encode-side and in any reference comparison.
  • Mixing float64 reference results into the production fixed-point path "just to double check": silently changes production precision; recovery: keep the reference path fully isolated (a separate function, never imported into the hot path).
  • Forgetting the level shift (−128 before DCT, +128 after IDCT): manifests as a globally too-bright or too-dark reconstruction; recovery: unit test a mid-gray (128) flat block, which should DCT to a single nonzero DC and IDCT back to exactly 128.

18.7 Performance Concerns

Naive O(N⁴)-equivalent DCT costs roughly 1,024 multiplies/block (§34); AAN's separable factorization costs roughly 176/block — a ~5.8× reduction that is the dominant lever for meeting the M-table's DCT-stage throughput sub-target (§30). Batch all blocks of an image into one NumPy call per DCT pass rather than looping per-block in Python.

18.8 Edge Cases

An all-zero block (DC=0, all AC=0 — must round-trip to exactly the level-shift constant); a block with only a DC component (a flat-color region); a block with maximum-magnitude alternating values (worst-case high-frequency energy, stresses fixed-point headroom); quality=100 (near-unity quantizer, minimal rounding) and quality=1 (maximum rounding, stresses I6's clamp path).

18.9 Failure Analysis

An unbounded intermediate in the fixed-point IDCT is the highest-severity bug class here: it can silently wrap in a way that produces a plausible-looking but wrong pixel value rather than crashing, evading casual review; contained by the property test comparing fast vs. reference IDCT on every CI run (§28), not just a handful of hand-picked cases.

18.10 Operational Notes

Metrics jpeg.encode.coefficient_clamped and jpeg.dct.reference_deviation_max (sampled in non-production/debug builds only, to avoid the reference path's cost in production) feed the quality-regression-bisect runbook (§26).

19. Phase 7 — Zigzag, Run-Length, and Huffman Entropy Coding

19.1 Objectives

Implement zigzag reordering (§8.4), DC differential coding (§8.5), the AC run-length/EOB symbol structure (§8.6), and canonical Huffman construction (§8.7, P5) for JPEG's MSB-first entropy stream.

19.2 Detailed Implementation Steps

  • Implement ZigzagTable (§11) as a precomputed constant lookup (forward and inverse), shared read-only across all blocks (P6-adjacent: no per-block recomputation).
  • Implement DC differential encode/decode (§8.5): predictor per component, reset at SOI and every restart marker (I8); category = bit-length of |DIFF|.
  • Implement AC run-length/EOB encode/decode (§8.6): the RunLengthSymbol structure, reserved symbols 0x00 (EOB) and 0xF0 (ZRL) handled as special cases before the general run/category path (a documented pitfall class, §12.4 of the salvaged original).
  • Implement canonical Huffman construction (§8.7) shared with Phase 2's HuffmanSpec/HuffmanTable, parameterized by BitOrder.MSB_FIRST for JPEG (P10) and by table_class (DC/AC) and component class (luma/chroma) — the four standard tables (DC-luma, AC-luma, DC-chroma, AC-chroma) are distinct and never interchanged.
  • Implement the fast_lookup (256-entry first-byte accelerator, §11) for decode-side speed, falling back to the full lookup dict for codes longer than 8 bits.
  • Implement JPEG byte-stuffing inside entropy data (0xFF followed by 0x00 means a literal 0xFF; any other byte following 0xFF is a marker, ending the current scan segment).

19.3 Deliverable

A known small JPEG's entropy-coded data decodes to the correct zigzag-ordered coefficient blocks, matching a hand-verified expected sequence; the encoder reproduces the same bitstream (modulo standard-vs-optimal table choice) for the same input.

19.4 Acceptance Criteria

  • 100% correct decode of conformance/fixtures/jpeg/known_block_sequence.bin against a hand-verified expected coefficient sequence.
  • Canonical Huffman round trip (encode table → decode table → identical code assignment) for all four standard tables, 0 mismatches.
  • Fast-table decode throughput ≥ 3× the full-dict-lookup fallback path, measured on a 10 MB entropy-data corpus (feeds the JPEG decode M-target, §30).

19.5 Conformance Fixtures

  • conformance/fixtures/jpeg/known_block_sequence.bin — a small hand-verified entropy segment; expected: exact coefficient sequence.
  • conformance/fixtures/jpeg/oversubscribed_huffman.bin — a Huffman table with lengths summing past capacity; expected: CodecError.Malformed("huffman_table") (I5).
  • conformance/fixtures/jpeg/dc_predictor_reset.bin — entropy data spanning two restart intervals; expected: DC predictor resets to 0 at each RST marker for all components (I8).
  • conformance/fixtures/jpeg/zrl_run_overflow.bin — a crafted run exceeding 63 total AC positions via repeated ZRL; expected: CodecError.Malformed("zigzag_overflow").

19.6 Pitfalls

  • An over-subscribed Huffman table accepted by a lenient decoder: the classic silent-corruption bug in this phase; debug via the oversubscribed_huffman.bin fixture; recovery: I5's Kraft-inequality check at table-build time, shared with Phase 2's DEFLATE tables.
  • Missing DC predictor reset on restart, or resetting only the current component instead of all components (I8): manifests as DC drift/banding a few restart intervals in; debug via dc_predictor_reset.bin; recovery: zero the full predictor vector, not a single scalar.
  • Special-casing 0x00/0xF0 after, rather than before, the general run/category decode: manifests as EOB/ZRL misinterpreted as a run=0/run=15 category-0 symbol, corrupting the rest of the block; recovery: check the two reserved byte values first, unconditionally.
  • Confusing JPEG's MSB-first bit order with DEFLATE's LSB-first when reusing the shared HuffmanTable/BitReader types: recovery: P10's separate-instance rule, enforced by a constructor-level BitOrder requirement (no default).

19.7 Performance Concerns

The fast 256-entry first-byte lookup table is the single highest-leverage optimization in the JPEG decode path (§13 of the salvaged original correctly flagged this); building it incorrectly (e.g., not handling codes shorter than 8 bits that have multiple matching first-byte patterns) both breaks correctness and forfeits the speedup — verify it against the full-dict path on every table construction in debug builds.

19.8 Edge Cases

A block that is entirely EOB (all AC coefficients zero, DC nonzero); a block using ZRL runs to reach exactly position 63 with no residual EOB; a DC category of 0 (DIFF=0, zero magnitude bits); the maximum DC category (11) requiring an 11-bit magnitude read.

19.9 Failure Analysis

An over-subscribed table that a lenient decoder accepts anyway (the historical failure class this phase's I5 check specifically targets) can decode to plausible-looking but arbitrary coefficient data — a data-integrity failure, not a crash, making it the highest-severity un-detected-if-unguarded case in this phase; contained by making the Kraft-inequality check unconditional and covered by a permanent fuzz corpus entry (§24, §28).

19.10 Operational Notes

Metrics huffman.table_rejected, jpeg.restart.reset_count, and jpeg.entropy.fast_table_hit_rate feed §26; the last one is a performance-regression canary — a sudden drop indicates a fast-table construction bug even before correctness tests catch it.

20. Phase 8 — The Full Baseline JPEG Encoder and Decoder

20.1 Objectives

Assemble Phases 5–7 into a complete baseline (SOF0) JPEG decoder and encoder: marker parsing (§8.13), JFIF/EXIF containers, DQT/DHT/SOF/SOS handling, the full decode state machine (§8.15), and a quality-parameterized encoder.

20.2 Detailed Implementation Steps

  • Implement JpegMarker/JfifHeader/ExifSegment (§11); marker-segment reader validates each segment's length against remaining bytes before reading its payload (P1, I2), matching the JFIF and EXIF specifications' documented layouts.
  • Implement the decode state machine (§8.15) exactly: StartOfImage → HeaderScan → FrameReady → ScanEntropy → Done, with the failure edges at each transition raising the matching CodecError.
  • Wire DQT (Phase 6's QuantTable), DHT (Phase 7's HuffmanTable), SOF0 (frame header: dimensions, ComponentInfo-equivalent ScanComponent sampling factors), SOS (per-scan component-to-table binding) — SOS validates every referenced table ID was already defined (I12).
  • Implement the MCU (Minimum Coded Unit) loop: for 4:2:0, 4 Y + 1 Cb + 1 Cr blocks per MCU; for 4:2:2, 2 Y + 1 Cb + 1 Cr; for 4:4:4, 1 Y + 1 Cb + 1 Cr — MCU geometry derived from SubsampleFactor (Phase 5), not hardcoded per subsampling mode.
  • Implement APP1/EXIF orientation parsing (P13, ADR-15): parsed and exposed on ImageBuffer's metadata, applied to pixels only when the caller explicitly requests it — never silently.
  • Implement the encoder direction end-to-end: RGB→YCbCr (Phase 5) → subsample → forward DCT (Phase 6) → quantize at the requested quality (Phase 6) → zigzag → DC-diff/AC-RLE (Phase 7) → Huffman encode (standard tables by default) → marker assembly (SOI, APP0/JFIF, DQT, DHT, SOF0, SOS, entropy data, EOI).

20.3 Deliverable

A real-world baseline JPEG decodes to an ImageBuffer visually and numerically consistent with a reference decoder; the encoder produces a valid, standard-conformant baseline JPEG at a requested quality that a reference decoder (Pillow/libjpeg-turbo) also decodes correctly.

20.4 Acceptance Criteria

  • Decode: PSNR ≥ 34 dB and SSIM ≥ 0.94 (§4) when comparing this decoder's output to libjpeg-turbo's decode of the same file, over conformance/fixtures/jpeg/photo_corpus/ (30 images).
  • Encode: at quality 75, file size within 5% of libjpeg-turbo's output size on the same corpus, and this decoder's round-trip decode of its own encoded output meets the same PSNR/SSIM bar.
  • Decode throughput ≥ 9 MP/s single-core (§4, M-table §30); encode throughput ≥ 6 MP/s single-core.
  • Zero crashes over the photo_corpus × {4:4:4, 4:2:2, 4:2:0} × {quality 1, 50, 75, 100} matrix (120 combinations).

20.5 Conformance Fixtures

  • conformance/fixtures/jpeg/photo_corpus/*.jpg — 30 natural photographs; expected: PSNR/SSIM thresholds above vs. libjpeg-turbo.
  • conformance/fixtures/jpeg/grayscale_1component.jpg — single-component (no chroma) baseline JPEG; expected: color-transform stage skipped entirely, correct decode.
  • conformance/fixtures/jpeg/exif_orientation_6.jpg — EXIF orientation tag 6 (90° rotation); expected: orientation exposed in metadata, pixels unrotated unless requested.
  • conformance/fixtures/jpeg/progressive_rejected.jpg — a SOF2 (progressive) file fed to a baseline-only build config; expected: CodecError.UnsupportedFeature("progressive") (superseded once Phase 9 lands).

20.6 Pitfalls

  • EXIF orientation silently ignored: many real-world phone-camera JPEGs are stored "sideways" relative to the orientation tag; a decoder that reads pixels without checking or exposing the tag produces a plausible-looking but rotated image the caller didn't ask for; recovery: expose orientation on ImageBuffer.metadata always, apply only on explicit request (ADR-15, P13).
  • The Adobe APP14 marker gotcha: an Adobe-produced JPEG's color-transform interpretation depends on APP14's transform field; assuming YCbCr unconditionally for 3-component frames misreads a small but real subset of files; recovery: check APP14 when present, default YCbCr when absent (Phase 5).
  • Mixing up the four standard Huffman tables (DC-luma, AC-luma, DC-chroma, AC-chroma): produces garbage decode that "almost" works (looks like static); recovery: bind table selection strictly by (component_class, table_class), verified in known_block_sequence.bin (Phase 7).
  • MCU geometry hardcoded for 4:2:0 only, breaking on 4:2:2/4:4:4 inputs: recovery: derive MCU block layout from SubsampleFactor generically, tested against all three factors in the acceptance matrix.

20.7 Performance Concerns

The MCU loop is the outer loop of the entire JPEG decode; per §30's profiling budget, Huffman decode (~30%) and IDCT (~40%) dominate — both already optimized in Phases 6–7; this phase's own cost is marker parsing (cheap, one-time) and MCU-to-plane scatter (vectorize the scatter with NumPy fancy indexing rather than a per-pixel Python loop).

20.8 Edge Cases

A JPEG with only 1 component (grayscale, no SOS chroma references at all); a JPEG with 4 components (CMYK, non-standard for baseline but seen in the wild — explicitly UnsupportedFeature rather than mis-decoded); a JPEG with multiple DQT/DHT segments defining the same table ID (last-write-wins per the spec, tested explicitly); a JPEG whose SOF0 dimensions don't evenly divide by the MCU size (partial MCUs at the right/bottom edge, requiring edge-block padding/cropping).

20.9 Failure Analysis

A misbound Huffman table (wrong table_class/component_class pairing) produces a full-image decode that superficially "looks like a JPEG artifact" rather than an obvious crash — the single hardest-to-catch bug class in this phase because it can be mistaken for expected lossy-compression noise; contained by the PSNR/SSIM acceptance gate (§20.4), which catches it numerically even when it might pass a casual visual check.

20.10 Operational Notes

Metrics jpeg.decode.psnr_vs_reference, jpeg.decode.ssim_vs_reference, and jpeg.exif.orientation_present feed §26's quality-distribution dashboard; the EXIF-orientation metric specifically tracks how often the un-rotated-by-default policy (ADR-15) is actually relevant in production traffic.

21. Phase 9 — Progressive JPEG and Restart Markers

21.1 Objectives

Extend the baseline decoder/encoder (Phase 8) to progressive JPEG (SOF2): spectral selection and successive approximation scans; implement restart-marker emission on encode (decode support already required by I8 since Phase 7).

21.2 Detailed Implementation Steps

  • Implement SOF2 frame-header parsing distinct from SOF0 (§8.13); progressive frames declare component sampling factors identically to baseline but the entropy data arrives across multiple SOS scans instead of one.
  • Implement spectral selection: each progressive scan covers a contiguous coefficient-index range (Ss–Se in the SOS header) rather than the full 64; the decoder accumulates coefficients across scans into a shared per-block coefficient buffer, only running IDCT after the last scan touching a block.
  • Implement successive approximation: each scan may refine only the higher-order bits of a coefficient first, then lower-order bits in a later scan (Ah/Al fields); implement the DC first-scan/refinement-scan distinction and the AC first-scan/refinement-scan distinction (including the AC refinement's own small run-length variant) per ITU-T T.81's progressive-mode annex.
  • Implement restart-marker emission on encode (ADR-09): when restart_interval is set, insert RSTn markers every N MCUs and reset DC predictors (I8) symmetrically with decode.
  • Implement partial-scan buffering: a progressive file's coefficient buffer for the whole image must be held in memory across scans (documented tradeoff vs. Phase 8's streaming baseline decode, ADR-16) — this is the one place whole-buffer decode is unavoidable given the format.

21.3 Deliverable

A real-world progressive JPEG (multiple SOS scans, spectral selection and successive approximation both present) decodes to the same pixel output as libjpeg-turbo's decode within the §4 tolerance; an encoder-produced progressive JPEG with restart markers round-trips through both this decoder and a reference decoder.

21.4 Acceptance Criteria

  • Progressive decode matches baseline-equivalent PSNR/SSIM thresholds (§20.4) on a 10-file progressive corpus.
  • Restart-marker round trip: DC drift (banding) absent across 5 restart-interval settings (1, 4, 16, 64 MCUs, and "none"), verified by I8's reset-count metric matching the expected reset count exactly.
  • Zero crashes over a progressive-scan-structure fuzz corpus of 500 crafted files (pathological Ss/Se/Ah/Al combinations), feeding forward into Phase 10's fuller campaign.

21.5 Conformance Fixtures

  • conformance/fixtures/jpeg/progressive_corpus/*.jpg — 10 real-world progressive JPEGs; expected: PSNR/SSIM thresholds match baseline-equivalent bar.
  • conformance/fixtures/jpeg/restart_interval_16.jpg — encoded with restart_interval=16; expected: exact reset-count match, no banding.
  • conformance/fixtures/jpeg/progressive_bad_spectral_range.jpg — a crafted scan with Ss > Se; expected: CodecError.Malformed("spectral_selection").
  • conformance/fixtures/jpeg/progressive_resource_exhaustion.jpg — a pathological scan count (thousands of tiny scans); expected: rejected under DecodeLimits, not an unbounded-time decode (ties T-class resource exhaustion, §24).

21.6 Pitfalls

  • Running IDCT after every scan instead of only the last scan touching a block: manifests as visibly wrong intermediate images treated as final (a correctness bug, not just an efficiency one, if the caller reads the buffer mid-decode); recovery: track a per-block "scans remaining" count derived from the frame's declared scan structure.
  • Successive-approximation bit-position bookkeeping errors (Ah/Al off by one): manifests as a subtly wrong final image (each refinement scan shifts by the wrong bit position); recovery: unit test against the worked spectral-selection/successive-approximation example in ITU-T T.81's informative annex.
  • Restart markers not resetting AC end-of-band run state (progressive AC scans carry their own inter-block run state distinct from DC's per-component predictor): recovery: reset both DC predictors and the AC run-state accumulator at every RST (extends I8).
  • Unbounded scan count from a malicious/pathological file: each SOS is cheap individually but thousands of them can still exhaust decode time; recovery: cap total scan count via DecodeLimits (feeds T12's resource-exhaustion mitigation).

21.7 Performance Concerns

Progressive decode's whole-buffer coefficient accumulation (ADR-16's documented exception) costs more memory than baseline's streaming MCU loop — bounded by the same DecodeLimits.max_buffer_size, but the multiplier in §4's memory-ceiling row is measured against progressive files specifically, not just baseline ones.

21.8 Edge Cases

A progressive file with exactly one scan covering the full spectral range (degenerates to baseline-equivalent, but through the progressive code path — must still work); a scan touching only the DC coefficient; a scan with Ah=0 (first scan) immediately followed by a scan with Ah>0 for the same component and spectral range (refinement); an AC scan whose end-of-band run spans multiple MCUs.

21.9 Failure Analysis

A resource-exhaustion attack via a pathological progressive scan structure (thousands of near-empty scans, each individually well-formed) is the highest-severity new attack surface this phase introduces (T12); contained by capping total scan count and total cumulative scan-header bytes via DecodeLimits, independent of any single scan's own validity.

21.10 Operational Notes

Metric jpeg.progressive.scan_count and jpeg.progressive.buffer_bytes feed §26's allocation-high-water-mark dashboard; a sustained rise in scan_count distribution is an early indicator of either a new legitimate encoder pattern or an attack pattern, disambiguated by cross-referencing rejection-reason counts.

22. Phase 10 — Decoder Hardening, Limits, and the Fuzzing Campaign

22.1 Objectives

Make every prior phase's decoder safe against adversarial input as a first-class deliverable: enforce DecodeLimits everywhere, close every gap the invariants (§7) describe, and stand up the Atheris fuzzing campaign (ADR-24).

22.2 Detailed Implementation Steps

  • Audit every allocation site in both pipelines against I2/P1: confirm each is preceded by a DecodeLimits.check() call using only already-validated header fields, with checked (overflow-safe) arithmetic for width × height × channels × bytes_per_sample.
  • Audit every BitReader call site against I3: confirm no path can read past limit even under a crafted truncation at an arbitrary byte offset (feeds §28's fault-injection strategy: truncate at every offset).
  • Audit the decompression-bomb defense (I11) end-to-end: confirm the streaming counter fires during inflate, not after, for both the own-DEFLATE and zlib-binding backends.
  • Implement Atheris harnesses under fuzz/: one per untrusted-input entry point (fuzz_png_decode.py, fuzz_jpeg_decode.py, fuzz_deflate_inflate.py, fuzz_exif_parse.py), each wrapping the corresponding decode entry point and asserting "no unhandled exception, no CodecError subclass escaping as a raw traceback."
  • Wire the CI fuzz stage (ADR-25): a time-boxed (30-minute PR-gated, 8-hour nightly) Atheris run per harness; any crash blocks merge and is auto-minimized (Atheris's built-in corpus minimization) and attached to the PR.
  • Implement the CLI's output-path handling hardening: reject path-traversal sequences (../, absolute paths outside a configured output directory) in imgcodec encode/decode --output (T9).
  • Implement the EXIF GPS-retention policy (ADR-15, T10): GPS tags are parsed, flagged (gps_present), and stripped by default on re-encode unless the caller explicitly opts to retain metadata.

22.3 Deliverable

Both decoders survive a 1,000,000-iteration Atheris campaign per harness with zero crashes and zero timeouts beyond the declared max_decode_seconds; the CLI rejects a path-traversal probe corpus.

22.4 Acceptance Criteria

  • Zero crashes, zero hangs beyond max_decode_seconds (2.0 s), over 1,000,000 Atheris iterations per harness (4 harnesses, §22.2).
  • 100% of conformance/fixtures/*/malformed_* and */bomb_* fixtures across all prior phases rejected with the correct CodecError variant (regression-locking every prior phase's hardening claim in one gate).
  • Fault-injection: truncation at every byte offset of a 50-file representative corpus produces either a clean error or a truncated=True partial result, 0 unhandled exceptions (ties I7, §28).
  • Path-traversal probe corpus (20 crafted --output paths) 100% rejected.

22.5 Conformance Fixtures

  • fuzz/corpus/png_seed/*, fuzz/corpus/jpeg_seed/* — seed corpora derived from every prior phase's conformance fixtures, used as Atheris's starting corpus.
  • conformance/fixtures/hardening/truncate_matrix/ — every representative file truncated at every byte offset (generated, not hand-authored); expected: clean error or partial result, per I7.
  • conformance/fixtures/hardening/path_traversal_probes.json — 20 crafted output-path strings (../../etc/passwd, absolute paths, symlink-adjacent names); expected: CodecError.Malformed("output_path").
  • conformance/fixtures/hardening/exif_gps_present.jpg — EXIF with GPS tags; expected: gps_present=True, stripped on default re-encode.

22.6 Pitfalls

  • A fuzz harness that catches too broadly (e.g., a bare except Exception: pass inside the harness itself) silently hides real crashes; recovery: the harness re-raises anything that isn't a documented CodecError subclass, so Atheris sees the real crash.
  • Timeout-as-hang vs. timeout-as-slow-but-correct ambiguity: a very large but legitimate image can look like a hang under a naive timer; recovery: the max_decode_seconds bound is checked against the declared image size's expected decode time (scaled from the M-table), not a flat constant, avoiding false-positive "hangs" on large legitimate inputs while still catching true bombs.
  • Path-traversal checks applied only to the literal string, missing symlink-based traversal: recovery: resolve the real path (os.path.realpath) and check it remains within the configured output directory, not just a string-prefix check.
  • Stripping EXIF metadata by default breaking a caller that genuinely wanted round-trip metadata preservation: recovery: make retention an explicit, documented opt-in (ADR-15) rather than a silent behavior change mid-project.

22.7 Performance Concerns

The fault-injection truncation matrix (every byte offset × representative corpus) is expensive to run fully on every PR; the CI fuzz stage runs a time-boxed subset per PR and the full matrix nightly (ADR-25), keeping PR latency bounded while still exercising the full matrix regularly.

22.8 Edge Cases

A file that is valid up to the very last byte, then truncated by exactly 1 byte (the hardest truncation case to detect cleanly, since almost everything has already been read); a decompression bomb crafted to just barely exceed bomb_ratio_multiple (boundary-value testing of I11); an output path that is valid but points at a FIFO/device file rather than a regular file (rejected, not blocked-indefinitely-on-read).

22.9 Failure Analysis

A hardening gap discovered by the fuzzer post-release is the scenario this phase exists to prevent pre-release; the nightly 8-hour campaign plus the PR-gated 30-minute subset (ADR-25) together define the detection window; any crash found nightly is triaged same-day per the malformed-input-triage.md runbook (§26) and becomes a new permanent regression fixture before the fix ships.

22.10 Operational Notes

Metrics fuzz.crash_count, fuzz.corpus_size, hardening.truncate_matrix_pass_rate feed §26's dashboards; the fuzz-crash-reproduction runbook (docs/runbooks/fuzz-crash-reproduction.md) documents replaying a minimized Atheris crash deterministically from its saved input bytes.

23. Phase 11 — Quality-Metrics Harness, Conformance Suite, and Perf Hardening

23.1 Objectives

Ship the PSNR/SSIM/bpp measurement harness (imgcodec.metrics) as a first-class module (P12), assemble the full conformance suite (spec vectors + differential + regression), and close out performance work against the M-table (§30).

23.2 Detailed Implementation Steps

  • Implement QualityReport (§11) computation: PSNR and SSIM (§8.12, Wang et al. 2004) between a reference ImageBuffer and a codec-round-tripped one; bits-per-pixel from compressed-size ÷ pixel count.
  • Implement the imgcodec measure CLI command: given two images (or one image and a quality setting to re-encode at), print a QualityReport.
  • Assemble conformance/run.py: runs every phase's fixture corpus, the specification's own test vectors (PNG test-suite-derived fixtures, JPEG conformance images), the differential corpus (libjpeg-turbo/libpng/Pillow comparison), and the invariant-per-file assertions from §7's debugging methodology, in one command.
  • Implement performance-regression gating (ADR-25, §30): benchmarks/ suite runs the M-table's throughput/latency targets on every release candidate; a regression beyond a stated tolerance (5% throughput drop) blocks release.
  • Implement the SSIM-vs-PSNR disagreement case study fixture (§2's "What Mastery Looks Like" bullet): a synthetic image where a structural artifact (a shifted edge) produces high PSNR but low SSIM, demonstrating the metrics' different sensitivities concretely, not just by assertion.
  • Finalize the CLI's full command surface (encode, decode, identify, measure) and its help text/error-reporting UX.

23.3 Deliverable

conformance/run.py executes the full suite (spec vectors, differential, fuzz-regression fixtures, invariant assertions) in one command with a pass/fail summary; imgcodec measure a.png b.png prints a QualityReport; the M-table's throughput targets are gated in CI.

23.4 Acceptance Criteria

  • conformance/run.py reports 100% pass on the full fixture corpus (all prior phases' fixtures combined, ≥ 400 files) with 0 skipped-without-reason entries.
  • Differential test: decoded pixels within the §4 tolerance (≤2 gray-level RMS for JPEG, bit-exact for PNG) against libjpeg-turbo/libpng/Pillow on a shared 50-image corpus, and this decoder rejects every file the reference decoders also reject (matching rejection sets, not just acceptance sets).
  • M-table (§30) throughput/latency targets met on the benchmark corpus, gated in CI with a 5% regression tolerance.
  • SSIM-vs-PSNR disagreement fixture demonstrates ≥10 dB PSNR "looks fine" while SSIM drops below 0.85, concretely proving the metrics' differing sensitivity.

23.5 Conformance Fixtures

  • conformance/fixtures/spec_vectors/ — the specification's own JPEG/PNG conformance test images, used verbatim (not resynthesized).
  • conformance/fixtures/differential/* — 50-image shared corpus with recorded libjpeg-turbo/libpng/Pillow reference outputs.
  • conformance/fixtures/metrics/ssim_psnr_disagreement.png — the shifted-edge synthetic case; expected: PSNR ≥ 34 dB, SSIM < 0.85.
  • conformance/fixtures/regression/* — every bug found and fixed in Phases 0–10, permanently retained with a numeric tolerance and a link to its originating FM-#/T#.

23.6 Pitfalls

  • A quality-harness bug (e.g., an off-by-one in the SSIM windowing) silently produces plausible-but-wrong numbers that then get trusted as ground truth for every other acceptance criterion in this document; recovery: validate the harness itself against Wang et al. 2004's published reference SSIM values on a known test pair before trusting any downstream number (P12).
  • Conformance suite "passing" because a fixture was silently skipped (e.g., a missing test-vector file treated as a soft skip instead of a hard failure); recovery: conformance/run.py treats a missing fixture as a failure, never a skip, unless explicitly marked xfail with a tracked reason.
  • Perf-regression gate flaky due to CI-runner noise (shared-tenancy variance): recovery: run each benchmark 5× and gate on the median, not a single sample, per §30's methodology.
  • Differential testing against a reference decoder's own known bugs (treating a reference-decoder quirk as ground truth): recovery: P3's conformance-outranks-reference-agreement principle — spec-vector failures always outrank differential disagreement.

23.7 Performance Concerns

The full conformance suite (≥400 files, differential comparisons against three reference decoders) is the most expensive CI stage; run it after the faster unit/property stages (ADR-25) so a cheap failure surfaces before the expensive one runs.

23.8 Edge Cases

A reference decoder (libjpeg-turbo/libpng) itself rejecting a spec-vector file this decoder accepts (or vice versa) — resolved by P3, not automatically "our bug"; a benchmark corpus image that happens to be degenerate (1×1) skewing throughput-per-megapixel math — excluded from throughput averages, retained for correctness-only fixtures.

23.9 Failure Analysis

A silently-wrong quality-metrics harness is the single highest-blast-radius bug possible at this phase, because every earlier phase's PSNR/SSIM acceptance criterion depends on it being correct; contained by validating the harness against Wang et al. 2004's published reference values before this phase's own deliverable is considered done (self-referential but necessary — the harness must be tested by something other than itself, namely the paper's own worked numbers).

23.10 Operational Notes

Metrics metrics.psnr_distribution, metrics.ssim_distribution, and conformance.pass_rate feed §26's dashboards; the quality-regression-bisect runbook (docs/runbooks/quality-regression-bisect.md) documents using conformance/fixtures/regression/* to bisect a quality drop to the responsible commit.

Named metrics (exported via a pluggable sink, ADR-22): png.decode.throughput_mp_s, jpeg.decode.throughput_mp_s, decode.rejected.{reason} (rate by reason, keyed to every CodecError variant), decode.allocation_high_water_mark_bytes, fuzz.crash_count, metrics.psnr_distribution, metrics.ssim_distribution, conformance.pass_rate.

Dashboards: (1) rejection-rate-by-reason over time, (2) decode-throughput distribution by format, (3) allocation-high-water-mark distribution, (4) PSNR/SSIM distribution for encode-path traffic, (5) fuzz-crash-count trend (should trend to zero and stay there).

Alerting philosophy: alert on rate-of-change in rejection reasons (a sudden spike in one CodecError variant suggests either an upstream format change or an attack probe), not on absolute rejection count (legitimate malformed-input rejection is expected background noise). SLOs: 99.9% of well-formed inputs (spec-vector + differential corpus) decode within the §4 latency p99; 100% of malformed-input fixtures rejected with the documented CodecError; 0 fuzz crashes outstanding at release time.

Incident response: a discovered decoder crash in production is treated as a security incident (T-class) until proven otherwise; the on-call engineer follows docs/runbooks/malformed-input-triage.md first.

Backup/restore: the library holds no persistent state of its own; "backup" is the versioned conformance/fuzz-corpus data in the repository itself, restored by git clone.

Deployment topology: embedded library within a caller's process (no standalone service); the CLI is a single-process, single-image-at-a-time invocation (ADR-29). Canary/rollback: a new release is canaried by running the full conformance/run.py suite plus the perf-regression gate before promotion; rollback is a version pin (§27, §29). Migration: no data migration applies (stateless library); API-compatibility migration is covered in §27.

27. Compatibility & Versioning

Bitstream conformance is the primary compatibility contract: any PNG this codec produces must decode correctly in libpng/Pillow/browsers, and vice versa; any JPEG this codec produces must decode correctly in libjpeg-turbo/browsers, and vice versa. This is tested continuously by §28's differential suite, not asserted once.

Encoder-output stability across versions: byte-identical output across releases is not promised (PhaseDeferred("§27")) — filter-selection heuristics (ADR-10) or Huffman table construction may improve, changing bytes while preserving the pixel-fidelity contract (I1 for PNG, the PSNR/SSIM bar for JPEG). A version bump that changes encoder output is a documented CHANGELOG entry, never a silent behavior change.

API stability: the public surface (imgcodec.decode, imgcodec.encode, ImageBuffer, CodecError, DecodeLimits, QualityReport) follows SemVer (ADR-27); a breaking signature change requires a major version bump.

Metadata handling policy across versions: EXIF/ICC pass-through behavior (ADR-15) is part of the API contract — a version that changes the default (e.g., start stripping GPS by default where it previously didn't) is a documented, changelog-flagged, minor-version-minimum change given its user-visible privacy implication (T10).

Decoder strictness changes as breaking changes: tightening strict_crc/strict_eof defaults (ADR-19), or any change that causes previously-accepted files to be rejected, is a major-version change per SemVer, since it can break a caller's existing corpus.

Migration/deprecation: deprecated API surfaces emit a DeprecationWarning for one minor-version cycle before removal at the next major version.

Rolling-upgrade guarantees: since this is an embedded library (not a service), "rolling upgrade" means a caller can depend on two adjacent major versions' ImageBuffer shape being convertible via a documented adapter for one release cycle, easing multi-service migrations that embed this library independently.

28. Testing & Verification Strategy

Unit: per-function correctness for every imgcodec.* module (pytest, ADR-23); every I# has at least one direct unit test asserting it.

Property (Hypothesis): "PNG encode→decode is bit-exact for every color type and bit depth" (I1); "the IDCT is the exact inverse of the DCT within the stated numeric tolerance" (Phase 6's precision acceptance criteria); "every canonical Huffman table round-trips" (P5, Phase 2/7); "the decoder never allocates more than the declared bound for any input" (I2), generated via Hypothesis strategies that produce arbitrary (including pathological) header field combinations.

Differential: against libjpeg-turbo, libpng, and Pillow on the shared conformance/fixtures/differential/ corpus — decoded pixels compared within the §4 tolerance, and rejection sets compared (this decoder must reject what the reference decoders reject, and vice versa, per P3/FM-6/FM-7).

Fuzzing (first-class phase deliverable, Phase 10): Atheris harnesses per untrusted-input entry point, 1,000,000-iteration PR-gated campaign plus an 8-hour nightly campaign, zero-crash gate blocking merge/release (ADR-24).

Chaos: randomized truncation/bit-flip injection at the CI conformance stage (not just Phase 10's dedicated matrix) to catch regressions in hardening introduced by unrelated feature work.

Deterministic replay: every fuzz-discovered crash is saved as a minimized input byte sequence under fuzz/crashes/, replayed deterministically by fuzz-crash-reproduction.md — no reliance on the original random seed.

Soak: a multi-hour continuous encode/decode loop over the full conformance corpus, checking for memory growth (a leak would violate the memory-ceiling constraint in §4 even without any single request exceeding it).

Fault injection: truncation at every byte offset of a representative corpus (Phase 10's truncate matrix), verifying I7 (clean error or partial result, never an unhandled exception) at every offset.

Conformance vectors: the specification's own JPEG/PNG test images, run verbatim, never resynthesized — the ultimate arbiter per P3.

Perf-regression gating: the M-table (§30) benchmarks run on every release candidate; a >5% regression on any M# blocks release (ADR-25).

Each of the above ties back to specific invariants (I1–I14) and to the phase-local fixtures named in each phase's N.5.

30. Performance Engineering

Profiling/benchmark methodology: (1) cache locality of block traversal — profile whether the MCU/block loop's memory access pattern is row-major-contiguous or scattered (NumPy strided views should keep it contiguous); (2) allocation profiling — count and size of every allocation per decode, checked against the §4 memory-ceiling multiple; (3) the DCT's multiply count — measured directly (not estimated) via an instrumented reference build, compared against the naive/AAN theoretical counts (§34); (4) bit-reader branch behavior — measure branch-misprediction-adjacent Python-level overhead (function-call count per decoded bit/symbol) as the proxy metric, since CPython lacks direct branch-predictor visibility; (5) vectorization opportunity — profile the ratio of NumPy-vectorized time to pure-Python time per pipeline stage, flagging any stage whose pure-Python fraction grows over time as a regression risk; (6) tail latency — p99 specifically tracked per §4, since Python's GC pauses are a plausible tail-latency contributor distinct from mean-case cost.

31. Scalability Analysis

What stays constant: per-block/per-MCU/per-scanline processing cost (the DCT's ~176-multiply constant per 8×8 block under AAN, ADR-02; the Paeth predictor's fixed 3-neighbor lookup per byte). What grows: total decode/encode time is linear in pixel count for both pipelines — O(width×height) — with the DCT's per-block constant (Phase 6) and DEFLATE's window-dependent match search (bounded by the 32 KiB window, Phase 2) as the two per-unit multipliers.

Named bottlenecks, in order: (1) JPEG Huffman entropy decode (~30% of decode time, Phase 7); (2) IDCT (~40%, Phase 6); (3) DEFLATE's LZ77 match search on encode (5–10× slower than decode, Phase 2); (4) color transform/chroma resample (<10%, Phase 5) — cheap because NumPy-vectorized whole-plane operations.

Parallelism: across independent JPEG blocks (embarrassingly parallel — no inter-block dependency once DC predictors are resolved sequentially per component), across restart intervals (fully independent, by design — ADR-09's whole rationale), and across PNG scanlines within a single filter type only up to the point the filter's own dependency allows — Up/Average/Paeth are inherently sequential row-to-row (I10 prevents parallelizing across the row-dependency boundary), so PNG's row-level parallelism is limited to independent Adam7 passes (7-way) and to the DEFLATE decompression pipeline stage running concurrently with the next file's parsing (pipeline parallelism across files, not within one row sequence).

Memory scaling: O(width×height×bytes_per_pixel) for the final ImageBuffer, plus a bounded constant multiple for working buffers (§4's ≤6× ceiling) — independent of compression ratio, since decompressed size is what's bounded, not compressed size.

Practical ceiling: single-core Python throughput (M1–M5) is the practical ceiling for this build; the lever beyond it is PhaseDeferred("§31")'s GPU/SIMD acceleration path, or horizontal scaling at the caller's level (multiple processes, one image each, since ADR-29 keeps the library single-image-synchronous by design) rather than intra-library concurrency.

32. Mental Models & First Principles

MM1 — The quantization table is the perceptual model. Lossy compression is not about discarding data but about choosing which errors the eye forgives. Predicts: encoder quality tuning is table design, not per-pixel special-casing. Bug class without it: ad hoc rounding rules that can't be justified against any perceptual model, breaking P14's clamp contract. Resolving: §8.3, P7.

MM2 — Every decoder is a parser for adversarial input; bounds checking is the feature, decoding is the side effect. Predicts: validation code should be as prominent in review as decode logic, not bolted on afterward. Bug class without it: hardening treated as a Phase-10 afterthought rather than woven through every earlier phase's acceptance criteria. Resolving: §7, §24.

MM3 — A canonical Huffman code is an agreement on tie-breaking; the tree itself is disposable, only the length shape matters. Predicts: any two independent implementations building from the same lengths + value order produce bit-identical codes. Bug class without it: serializing/comparing trees instead of length arrays, or a non-deterministic tie-break producing cross-implementation-incompatible codes. Resolving: §8.7, P5.

MM4 — Separable transforms turn intractable per-axis work into tractable per-axis work. The 2-D DCT's row/column split is the general pattern: any transform claimed to be "2-D" should be checked for separability before writing the naive form. Bug class without it: an O(N⁴)-equivalent DCT that is "correct" but blows the throughput target. Resolving: §8.2, P4.

MM5 — A filter is a bet that neighbors predict you well; DEFLATE is the payoff collector. PNG's two-stage design (predict, then general-purpose compress) means filter quality only matters insofar as it helps the downstream compressor — not as a standalone metric. Predicts: a filter heuristic should ultimately be judged by post-DEFLATE size, not its own proxy metric alone. Bug class without it: over-trusting the MSAD heuristic (ADR-10) in a regime where it diverges from actual compressed size. Resolving: §8.9, ADR-10.

MM6 — Precision is a stated contract, not a property of the hardware. Fixed-point vs. float is a decision, documented once, not an accident of which code path happened to be written first. Predicts: every numeric path names its scale explicitly. Bug class without it: silent precision drift between an encoder's fixed-point path and a decoder's (accidentally) float path. Resolving: P11, §8.3, ADR-04.

MM7 — A header field is trustworthy only as an upper bound on validation, never directly as an allocation size. Predicts: allocation always follows a two-step validate-then-allocate sequence, with the validated bound (not the raw field) driving the allocation call. Bug class without it: T1/T2's overflow-driven heap-overflow class. Resolving: I2, §24.

MM8 — Quality metrics disagree with each other on purpose. PSNR measures energy, SSIM measures structure; an encoder tuned to only one will eventually look wrong on the other's blind spot. Predicts: any change that improves PSNR should be sanity-checked against SSIM before being called an improvement. Bug class without it: "improving" PSNR while making banding or structural artifacts measurably worse. Resolving: §8.12, §23.6.

libjpeg-turbo: the SIMD-accelerated intrinsic-DCT path is exactly what this design defers (PhaseDeferred("§31")) — it wins wherever raw single-core throughput dominates, e.g. a server-side thumbnail pipeline processing millions of images/day.

mozjpeg: trellis quantization (choosing coefficients jointly rather than rounding independently) buys several percent smaller files at equal perceptual quality — it wins whenever encode time is cheap relative to storage/bandwidth cost at scale (a CDN's one-time re-encode pass), which is why ADR-05 notes it as the perceptual-tuning alternative this build didn't adopt.

libpng + zlib: the reference embodiment of this design's own PNG half; wins wherever C-level throughput and decades of production hardening matter more than an auditable from-scratch implementation — most production software should simply use it, which is why ADR-11 offers it as this design's own default performance-path backend rather than reinventing it for production use.

stb_image: single-header, zero-dependency simplicity wins wherever integration friction (no build system, no package manager) matters more than validation completeness or performance — a game-jam prototype or an embedded tool with no room for a full codec.

Pillow: the Python-facing C-core codec boundary (src/libImaging/) is the direct precedent for this design's own Python-API/optimizable-core split (ADR-01) — it wins wherever a Python application wants broad format coverage today without building anything from scratch, which is exactly why §1 calls it out as the "adopt unless you have a specific reason" alternative to this whole project.

Guetzli: an extreme point on the quality/ratio-vs-encode-time curve — its perceptual-model-guided quantization search wins for one-time, offline, quality-critical encodes (e.g. a publisher's hero images) where encode time is irrelevant and file size matters enormously.

34. Back-of-Envelope Capacity Model

  1. Raw vs. compressed size, 1920×1080 RGB24. Raw = 1920×1080×3 = 6,220,800 bytes (≈ 6.22 MB). At the JPEG q75 target ratio (10:1–15:1, §4), compressed ≈ 6,220,800 ÷ 12 (midpoint) ≈ 518,400 bytes. Bits per pixel = (518,400 × 8) ÷ (1920×1080) ≈ 2.0 bpp, versus 24 bpp raw.

  2. Block count and DCT multiply count, 1920×1080, 4:2:0. Luma blocks = ceil(1920/8) × ceil(1080/8) = 240 × 135 = 32,400. Chroma planes (each halved both axes) = ceil(960/8) × ceil(540/8) = 120 × 68 = 8,160 per plane × 2 planes = 16,320. Total blocks ≈ 48,720. Naive separable DCT: 1024 mults/block × 48,720 ≈ 49.9M multiplies. AAN (M10): 176 mults/block × 48,720 ≈ 8.57M multiplies — a 5.8× reduction, matching M10 exactly.

  3. Decoder memory, 1920×1080 RGBA8. Decoded buffer = 1920×1080×4 = 8,294,400 bytes (≈8.3 MB). JPEG working set adds ≈3 YCbCr planes (≈0.75×buffer, accounting for 4:2:0 chroma) + a float64 DCT staging copy (≈2×buffer) + a dequantized-coefficient array (≈1×buffer) ≈ 8.3 MB × (1 + 0.75 + 2 + 1) = 8.3 MB × 4.75 ≈ 39.4 MB, i.e. ≈4.75× the decoded buffer — within the §4/M8 6× ceiling with headroom.

  4. Decompression-bomb ratio and the resulting hard limit. DEFLATE's back-reference model (length ≤258, distance ≥1) can in principle repeat a pattern to compression ratios exceeding 1000:1. For the 8,294,400-byte declared image above, I11's bomb_ratio_multiple=4 caps allowed decompressed bytes at 4 × 8,294,400 ≈ 33.2 MB regardless of input compactness — the mechanism enforcing §4's ≤3× declared-size allocation bound (set below the 4× inflate-check ceiling so the allocator's own cap fires first).

  5. Chroma-subsampling data saving, 4:2:0 vs. 4:4:4. 4:4:4 chroma bytes, 1920×1080 = 2 planes × 1920×1080 = 4,147,200. 4:2:0 chroma bytes = 2 planes × (960×540) = 1,036,800. Fraction = 1,036,800 ÷ 4,147,200 = 0.25 exactly — matching §17.4's acceptance criterion precisely.

  6. PSNR from a measured MSE at quality 75. Assume a corpus-measured MSE ≈ 8.0 (gray-level² units): PSNR = 10 log10(255² ÷ 8.0) = 10 log10(65,025 ÷ 8.0) = 10 log10(8,128.1) ≈ 10 × 3.910 = 39.1 dB — comfortably above the §4 34 dB floor, showing the floor has real headroom for a worse-than-typical corpus image.

  7. Adam7 per-pass pixel counts summing to the total, 16×16 image. Pass 1: 2×2=4. Pass 2: 2×2=4. Pass 3: 4×2=8. Pass 4: 4×4=16. Pass 5: 8×4=32. Pass 6: 8×8=64. Pass 7: 16×8=128. Sum = 4+4+8+16+32+64+128 = 256 = 16×16 exactly, verifying I9 arithmetically.

  8. Startup table-construction cost. 4 standard Huffman tables × ≤256 symbols ≈ 1,024 canonical-code assignments, plus building each table's 256-entry fast_lookup ≈ 1,024 more operations ≈ 2,048 total operations at import. Even at a pessimistic 25,000 ops/ms Python rate, this is <1 ms — well inside the <50 ms M12/§4 startup budget, leaving the remainder for module import and NumPy initialization.

35. Hard Questions (Self-Examination)

  1. Why does the decoder validate dimensions before allocating anything, and what attack does skipping that step enable? (§7 I2, §24 T1/T2)
  2. Why is DEFLATE's decompression-bomb check performed during streaming rather than after full inflate, and what would change if it ran after? (§14.2, §24 T3)
  3. Why must JPEG's bit reader be MSB-first while DEFLATE's is LSB-first, and what breaks if one shared reader instance serves both? (P10, §11 BitReader)
  4. Why does a canonical Huffman code transmit only code lengths rather than the tree itself, and how does canonical assignment guarantee two independent decoders agree? (§8.7, P5)
  5. Why is 4:2:0 chroma subsampling applied before entropy coding rather than as an entropy-coding trick, and what data-rate argument justifies the ordering? (§17, §34 item 5)
  6. Why does this design keep a float64 reference IDCT alongside the fixed-point production IDCT rather than trusting the fixed-point path alone? (§18, P11)
  7. Why does PNG's Paeth filter require three neighbors rather than one, yet remain a linear predictor despite its nonlinear selection rule? (§8.9, MM5)
  8. Why does Adam7 interlacing need an explicit sum-of-passes invariant rather than trusting the geometry formula alone? (I9, §34 item 7)
  9. Why does this design reject an over-subscribed Huffman table instead of attempting a best-effort decode, and what historical incident class motivates that? (I5, §24 T5/the libwebp-BLASTPASS reference)
  10. Why is EXIF orientation exposed as metadata but never silently applied to pixels? (ADR-15, §24 T10)
  11. Why does progressive JPEG require whole-buffer coefficient accumulation when baseline JPEG streams MCU-by-MCU? (§21, ADR-16)
  12. Why does a JPEG restart marker reset predictors for all components simultaneously rather than per-component as each is encountered? (I8, §25 FM-5)
  13. Why does this design prefer the specification's own conformance vectors over agreement with libjpeg-turbo when the two disagree? (P3, §25 FM-6/FM-7)
  14. Why is PSNR alone insufficient to gate JPEG quality, and what does the SSIM-vs-PSNR disagreement fixture concretely demonstrate? (§23.6, MM8)
  15. Why does the quantization table function as "the perceptual model" instead of perceptual tuning happening elsewhere in the pipeline? (§8.3, MM1)
  16. Why does this design choose NumPy vectorization for DCT/color/filter stages but keep Huffman/LZ77 bitstream state machines in pure Python? (§1 numeric-core strategy, §30)
  17. Why is the malicious-input allocation bound set as a multiple of the declared size rather than a flat constant, and what would a flat constant break? (§4, §34 item 4)
  18. Why does mozjpeg's trellis quantization not appear as this design's default quantization strategy despite its measurable size advantage? (ADR-05, §33)
  19. Why is arithmetic coding rejected as JPEG's entropy coder here despite its measurable ratio advantage over Huffman? (ADR-07, §36)
  20. Why does this design defer GPU/SIMD acceleration rather than build it from the start, and what does that deferral cost against the M-table targets? (§1 PhaseDeferred, §30, §37)

36. Alternative Architectures (Roads Not Taken)

A1 — Wavelet-based codec (JPEG 2000's approach).

Image → DWT (multi-resolution wavelet) → EBCOT bit-plane coding
      → embedded quality-scalable bitstream → arbitrary-ratio truncation

Regime where it wins: applications needing progressive quality/resolution scalability from one encoded stream (e.g. medical imaging, archival masters) and freedom from block-boundary artifacts. Real embodying system: JPEG 2000 (ISO/IEC 15444), covered comparatively via Taubman & Marcellin. Rejected here: the wavelet transform and EBCOT's bit-plane coding are a substantially different mathematical and implementation surface from the DCT+Huffman pair this blueprint teaches; JPEG 2000 also never achieved JPEG's ubiquity, so the interoperability payoff is lower for the stated goal (§1).

A2 — Arithmetic/range coder replacing Huffman.

Coefficients → adaptive probability model → arithmetic/range coder
             → few-percent-smaller output, no per-symbol integer bit-length constraint

Regime where it wins: a closed ecosystem where a few percent better ratio matters more than universal baseline-decoder compatibility (JPEG's own historically underused arithmetic-coding mode). Real embodying system: JPEG's Annex-defined arithmetic-coding mode (rarely deployed) and, more broadly, the entropy stage used in later transform codecs. Rejected here: ADR-07 — Huffman is unencumbered today and mandatory-baseline-compatible; historically, arithmetic coding's patent status (through the 1990s–2000s) blocked broad adoption, a lesson worth teaching but not worth building as the default here.

A3 — Block-based video-derived intra codec (WebP/AVIF/HEIF's approach).

Image → larger variable-size prediction blocks → intra spatial prediction
      → residual transform (varies by codec) → modern entropy coder (e.g. boolean/CABAC-like)

Regime where it wins: modern web delivery where both encoder and decoder are recent and file-size-per-quality matters more than decades of universal deployment. Real embodying systems: WebP (VP8 intra), AVIF (AV1 intra), HEIF/HEIC (HEVC intra). Rejected here: these formats derive their transform/prediction/entropy stack from video codecs, a materially different (and larger) design surface than "DCT + Huffman" or "filter + DEFLATE" — explicitly out of scope per §1's non-goals.

A4 — Learned/neural codec.

Image → CNN/transformer encoder → learned latent → learned entropy model
      → learned decoder → reconstructed image (rate-distortion trained end-to-end)

Regime where it wins: research settings optimizing rate-distortion beyond hand-designed transforms, where training-time and inference-hardware cost are acceptable trade-offs. Real embodying systems: published learned-image-compression autoencoder-plus-entropy-model architectures (an active research area). Rejected here: no training pipeline, no learned-model inference runtime, and no fixed bitstream specification to teach against — fundamentally incompatible with this blueprint's from-the-published-spec, deterministic-bitstream design goal (§1).

38. Glossary

  • Lossy — a compression scheme (JPEG) that discards information irrecoverably in exchange for a smaller file, guided by a perceptual model (§8.3).
  • Lossless — a compression scheme (PNG) whose decode reproduces the original pixel data exactly (I1, P2).
  • YCbCr — a color space separating luma (Y) from two chroma components (Cb, Cr); JPEG's working color space (§8.1).
  • Chroma subsampling — reducing chroma-plane resolution relative to luma, exploiting the eye's lower spatial acuity for color (§17).
  • 4:2:0 — a chroma-subsampling factor halving both horizontal and vertical chroma resolution (ADR-06).
  • DCT-II — the specific discrete cosine transform variant used by JPEG, mapping spatial pixel blocks to frequency-domain coefficients (§8.2).
  • Basis function — one of the fixed cosine waveforms the DCT projects a block onto; each coefficient is the block's weight on one basis function.
  • Quantization table — the per-frequency divisor array that discards perceptually-unimportant coefficient precision (§8.3, MM1).
  • Quality factor — the 1–100 scalar an encoder exposes, mapped through the quantization-table scaling formula (§8.3).
  • Zigzag order — the diagonal traversal ordering of an 8×8 coefficient block that clusters low frequencies first (§8.4).
  • DC coefficient — a block's [0,0] coefficient, representing its average value (§8.5).
  • AC coefficient — any non-DC coefficient, representing higher-frequency content (§8.6).
  • Run-length — the count of consecutive zero coefficients preceding the next nonzero AC value (§8.6).
  • End-of-block (EOB) — the reserved AC symbol signaling all remaining coefficients in a block are zero (§8.6).
  • Huffman code — a variable-length, prefix-free entropy code assigning shorter codes to more frequent symbols (Huffman 1952).
  • Canonical code — a Huffman code reconstructible from code lengths alone via a fixed assignment rule (§8.7, P5).
  • Over-subscribed table — an invalid Huffman code-length set violating the Kraft inequality; must be rejected, not decoded (I5).
  • Restart marker — a JPEG marker resetting DC prediction state, enabling error resync and parallel decode (§8.13, I8).
  • Progressive scan — a JPEG scan covering a coefficient subset (spectral selection) or bit-plane subset (successive approximation) rather than a full block in one pass (§21).
  • Spectral selection — the progressive-JPEG technique of encoding a coefficient-index range per scan (§21.2).
  • Successive approximation — the progressive-JPEG technique of encoding a coefficient's bits from most- to least-significant across scans (§21.2).
  • JFIF — the JPEG File Interchange Format, defining APP0 and the default color-space/density convention (§5, §20).
  • EXIF — the metadata format embedded in APP1, including camera orientation and (optionally) GPS data (§5, ADR-15).
  • DEFLATE — the LZ77 + Huffman compression algorithm defined by RFC 1951, underlying PNG's IDAT stream (§8.8).
  • LZ77 — the dictionary-coding scheme replacing repeated byte sequences with (length, distance) back-references (Ziv & Lempel 1977).
  • Sliding window — DEFLATE's 32 KiB bounded history buffer that back-references may point into (§8.8).
  • Match/literal — DEFLATE's two token kinds: a literal byte, or a length/distance back-reference match (§8.8).
  • PNG filter type — one of five per-scanline byte-transform strategies (None/Sub/Up/Average/Paeth) applied before DEFLATE (§8.9).
  • Paeth predictor — PNG's three-neighbor linear predictor with a nonlinear closest-neighbor selection rule (§8.9, MM5).
  • Adam7 interlace — PNG's seven-pass progressive-scan geometry for incremental image display (§8.10).
  • CRC-32 — the 32-bit cyclic redundancy check validating every PNG chunk's integrity (§8.11, I4).
  • Critical vs. ancillary chunk — PNG's case-bit convention distinguishing chunks a decoder must understand (critical, uppercase first letter) from ones it may skip (ancillary, lowercase) (§8.14).
  • Decompression bomb — a small compressed input engineered to expand to an enormous decompressed size, an allocation-DOS attack (T3, I11).
  • PSNR — Peak Signal-to-Noise Ratio, a logarithmic energy-error quality metric (§8.12).
  • SSIM — Structural Similarity Index, a perceptual quality metric sensitive to structural (not just energy) error (Wang et al. 2004, §8.12).
  • Bits per pixel (bpp) — compressed size in bits divided by pixel count, the standard density metric for comparing compression ratios (§8.12).
  • Blocking artefact — visible 8×8 block-boundary discontinuities from independent per-block DCT quantization at low quality.
  • Banding — visible discrete steps in what should be a smooth gradient, from quantization-table rounding (FM-8).
  • MCU (Minimum Coded Unit) — the smallest independently-decodable group of blocks in a JPEG scan, sized by the components' sampling factors (§20.2).
  • IDCT — the Inverse Discrete Cosine Transform, mapping frequency-domain coefficients back to spatial pixels (§8.2).
  • zlib — the RFC 1950 wrapper format around a raw DEFLATE stream, adding a header and Adler-32 trailer (§14.2).
  • Adler-32 — the checksum zlib uses for stream integrity, distinct from PNG's CRC-32 (§14.6).
  • Fixed-point — a numeric representation using an implicit scale factor over integers instead of floating-point, chosen here for deterministic rounding (ADR-04, P11).
  • Level shift — JPEG's −128/+128 pixel-value rebiasing around zero before/after the DCT/IDCT (§18.6).
  • Trust boundary — the point in the pipeline where previously-untrusted bytes become a validated, trusted ImageBuffer (§3).
  • Canonical assignment — the deterministic rule mapping a sorted code-length list to explicit Huffman codes (§8.7).
  • Baseline JPEG — the universally-supported JPEG variant (SOF0), sequential single-pass entropy coding (§20).
  • Sample precision — the bit depth of a single color-channel sample (8-bit for baseline JPEG; 1–16-bit for PNG) (§4).
