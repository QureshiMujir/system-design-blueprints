Decisions (§9) · 30 ADRs

ADR-01

Language + numeric core

Chosen

Python 3.11+ with NumPy for vectorized block math

Rejected

Rust; C/C++; Go

When the rejected choice is right

Rust/C/C++ win when the deliverable is a production embedded decoder needing memory-safety-by-construction or maximum throughput (e.g., a browser image pipeline)

Why: readability keeps spec-to-code mapping legible; NumPy vectorizes the parallel stages

ADR-02

DCT algorithm

Chosen

Separable 1-D passes, AAN fast factorization for the hot path, naive O(N⁴) kept as a reference oracle

Rejected

Loeffler 11-multiply factorization as the primary path; naive as primary

When the rejected choice is right

Loeffler wins when targeting a fixed-point-only hardware backend where its multiply/add balance is preferred (e.g., a DSP core)

Why: AAN is well-published, matches Pennebaker & Mitchell's treatment, and NumPy vectorizes its butterfly stages cleanly

ADR-03

DCT numeric domain

Chosen

Integer/fixed-point IDCT (32-bit) as the shipped path; float64 kept as the correctness oracle

Rejected

Pure float64 IDCT in production

When the rejected choice is right

Float64 wins for a research/quality-ceiling build where cross-platform bit-identical output is not required

Why: fixed-point matches how real baseline decoders behave and keeps rounding deterministic across platforms

ADR-04

Fixed-point precision policy

Chosen

32-bit accumulator, 10-bit fractional scale for color transform, category-scaled ints for DCT coefficients

Rejected

16-bit fixed point

When the rejected choice is right

16-bit wins on memory-constrained embedded targets where the extra precision is not perceptible

Why: 32-bit avoids visible banding at low quality (FM-8) while staying vectorizable

ADR-05

Quantization-table source + quality mapping

Chosen

Annex-K-style standard base tables, scaled by the quality→scale formula (§8.3)

Rejected

Fully custom per-encoder tables; Watson/DCTune perceptual tables

When the rejected choice is right

Watson/DCTune-style tables win when targeting perceptual-quality-per-byte beyond baseline interoperability (mozjpeg/Guetzli territory, §33)

Why: matches the vast majority of interoperable encoders and is directly testable against conformance vectors

ADR-06

Chroma-subsampling default

Chosen

4:2:0

Rejected

4:4:4; 4:2:2

When the rejected choice is right

4:4:4 wins for text/line-art or when chroma fidelity matters more than size (e.g., screenshots with colored text)

Why: best size/quality tradeoff for natural photographs, matches the majority of web JPEGs

ADR-07

Entropy coder

Chosen

Huffman (canonical, per §8.7)

Rejected

Arithmetic/range coding (Rissanen & Langdon 1979; Witten/Neal/Cleary 1987)

When the rejected choice is right

arithmetic coding wins when a few percent better ratio matters more than universal baseline decoder compatibility (JPEG's own arithmetic mode, or a closed ecosystem)

Why: Huffman is unencumbered today and matches the baseline-JPEG mandatory mode; historically arithmetic coding's patent status blocked adoption through the 1990s–2000s

ADR-08

Progressive-mode support

Chosen

Implemented (Phase 9) as a second decode/encode path sharing the entropy/DCT core

Rejected

Baseline-only

When the rejected choice is right

baseline-only wins for a size-constrained embedded decoder that only ever receives baseline-encoded assets

Why: progressive JPEG is common on the web and exercises spectral-selection/successive-approximation, a distinct-enough state machine to be worth building

ADR-09

Restart-marker policy

Chosen

Supported on decode always; emitted on encode only when restart_interval is explicitly set

Rejected

Never emit on encode

When the rejected choice is right

never-emit wins when file size is the only concern and the target images are always small enough that resync value is negligible

Why: restart markers enable parallel decode and error-resync, valuable for large images, but add ~0.1–0.3% overhead

ADR-10

PNG filter-selection heuristic

Chosen

Minimum-sum-of-absolute-values (MSAD) heuristic per scanline

Rejected

Brute-force try-all-5-then-DEFLATE-each (optimal)

When the rejected choice is right

brute-force wins when encode time is unconstrained and maximum compression ratio matters more (e.g., archival re-encoding)

Why: MSAD is O(1) per filter vs. O(DEFLATE) per filter; a good proxy for post-DEFLATE size

ADR-11

DEFLATE implementation strategy

Chosen

Own RFC 1951 implementation is the canonical/conformance path; CPython's zlib binding is the default performance path

Rejected

Own implementation only; zlib binding only

When the rejected choice is right

own-implementation-only wins in an environment where linking a C extension is disallowed (e.g., a security sandbox with no native code)

Why: own implementation proves spec understanding and is the conformance oracle; zlib binding meets the throughput targets in §4 pure Python cannot reach

ADR-12

Compression-level policy

Chosen

Default DEFLATE level 6 equivalent (own encoder mirrors zlib's level/lazy-match tradeoff)

Rejected

Always level 9

When the rejected choice is right

level 9 wins for one-time archival encodes where encode time is free

Why: level 6 is the standard size/speed knee; level 9 buys ~1% smaller output for 5–10× encode time

ADR-13

Color-type/bit-depth coverage

Chosen

All PNG color types (0,2,3,4,6) × all bit depths (1,2,4,8,16)

Rejected

8-bit RGB/RGBA only

When the rejected choice is right

8-bit-only wins for a narrow embedded target that only ever produces 8-bit RGBA screenshots

Why: full coverage is required to claim spec conformance (§28) and to pass the PNG test-suite-derived fixtures

ADR-14

ADR-15

Metadata handling

Chosen

ADR-16

ADR-17

Chosen

36. Alternative Architectures (Roads Not Taken)

A1 — Wavelet-based codec (JPEG 2000's approach).

Image → DWT (multi-resolution wavelet) → EBCOT bit-plane coding
      → embedded quality-scalable bitstream → arbitrary-ratio truncation

Regime where it wins: applications needing progressive quality/resolution scalability from one encoded stream (e.g. medical imaging, archival masters) and freedom from block-boundary artifacts. Real embodying system: JPEG 2000 (ISO/IEC 15444), covered comparatively via Taubman & Marcellin. Rejected here: the wavelet transform and EBCOT's bit-plane coding are a substantially different mathematical and implementation surface from the DCT+Huffman pair this blueprint teaches; JPEG 2000 also never achieved JPEG's ubiquity, so the interoperability payoff is lower for the stated goal (§1).

A2 — Arithmetic/range coder replacing Huffman.

Coefficients → adaptive probability model → arithmetic/range coder
             → few-percent-smaller output, no per-symbol integer bit-length constraint

Regime where it wins: a closed ecosystem where a few percent better ratio matters more than universal baseline-decoder compatibility (JPEG's own historically underused arithmetic-coding mode). Real embodying system: JPEG's Annex-defined arithmetic-coding mode (rarely deployed) and, more broadly, the entropy stage used in later transform codecs. Rejected here: ADR-07 — Huffman is unencumbered today and mandatory-baseline-compatible; historically, arithmetic coding's patent status (through the 1990s–2000s) blocked broad adoption, a lesson worth teaching but not worth building as the default here.

A3 — Block-based video-derived intra codec (WebP/AVIF/HEIF's approach).

Image → larger variable-size prediction blocks → intra spatial prediction
      → residual transform (varies by codec) → modern entropy coder (e.g. boolean/CABAC-like)

Regime where it wins: modern web delivery where both encoder and decoder are recent and file-size-per-quality matters more than decades of universal deployment. Real embodying systems: WebP (VP8 intra), AVIF (AV1 intra), HEIF/HEIC (HEVC intra). Rejected here: these formats derive their transform/prediction/entropy stack from video codecs, a materially different (and larger) design surface than "DCT + Huffman" or "filter + DEFLATE" — explicitly out of scope per §1's non-goals.

A4 — Learned/neural codec.

Image → CNN/transformer encoder → learned latent → learned entropy model
      → learned decoder → reconstructed image (rate-distortion trained end-to-end)

Regime where it wins: research settings optimizing rate-distortion beyond hand-designed transforms, where training-time and inference-hardware cost are acceptable trade-offs. Real embodying systems: published learned-image-compression autoencoder-plus-entropy-model architectures (an active research area). Rejected here: no training pipeline, no learned-model inference runtime, and no fixed bitstream specification to teach against — fundamentally incompatible with this blueprint's from-the-published-spec, deterministic-bitstream design goal (§1).
