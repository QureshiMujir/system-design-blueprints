Project Name: Terminal Emulator

1. Goal & Scope

Build a production-grade terminal emulator in Rust: a byte-stream-driven virtual terminal that owns the PTY master, the VT/ANSI escape-sequence parser, the cell grid with scrollback, cursor and mode state, an input encoder, and two renderer backends (CPU/software, GPU/wgpu), validated against vttest/esctest and hardened against escape-sequence injection. The system decouples byte parsing (a pure state machine) from semantic effect (a typed grid mutator) from presentation (a dumb consumer of dirty cells) — the architectural guarantee every long-lived emulator (xterm, Alacritty, kitty, WezTerm) converged on independently.

Phase-0 deliverable (numbered modules, one crate each, Cargo workspace):

  1. tem-core — shared types: Cell, Cursor, Color, Attrs, ParserState.
  2. tem-pty — PTY master/slave abstraction (Unix openpty/forkpty, Windows ConPTY).
  3. tem-parser — Paul Williams DEC state-machine parser.
  4. tem-performer — CSI/OSC/DCS dispatch onto the grid.
  5. tem-grid — main/alt screen, scrollback ring buffer, dirty tracking.
  6. tem-conformance — CLI fixture runner.

System boundaries:

  • Provides: PTY lifecycle, escape-sequence parsing, grid state, scrollback, cursor/mode state, dirty-region tracking, an input encoder (keyboard/mouse → bytes), two renderer backends, image protocols, ligature shaping, BiDi reordering, a conformance/fuzz harness.
  • Delegates: window creation and event pump (host application via winit/GTK/AppKit), font discovery and rasterization primitives (FreeType/HarfBuzz), process supervision beyond the direct child (shell) — a multiplexer (tmux-equivalent) is out of scope.
  • Does NOT provide: a shell, a multiplexer, a configuration UI, a package manager for terminfo entries, session persistence across process restart (deferred).

Non-goals: reimplementing a shell; a GUI settings app; full ISO-2022 multi-byte designation beyond G0–G3 SCS; VT52 compatibility mode.

Deployment model: a single long-running process per terminal window/tab; the renderer runs on the host's event loop thread; the PTY read loop runs on a dedicated thread or async task feeding the parser.

Target users/operators: engineers building terminal emulators, TUI framework authors validating against a reference implementation, security teams auditing escape-sequence handling.

Later phases unlock: sixel/kitty/iTerm2 inline images and OSC 8/52 (§23), ligature shaping and BiDi (§22), GPU rendering with damage tracking (§20), a 30-day fuzz canary (§24).

Recommended language: Rust (1.78+ MSRV) — memory safety without GC pauses in the render hot path, a mature FFI story for FreeType/HarfBuzz, cargo-fuzz/libFuzzer integration, and the vte/termwiz prior art to validate architecture against (ADR-01). Rejected: C (memory-unsafe parser is the historical CVE class — CVE-2003-0063-class bugs are use-after-free/overflow in exactly this parsing code); Go (GC pause spikes violate the ≤2 ms p99 GPU frame budget, §4); C++ (viable — kitty and xterm are C/C++ — but no equivalent to Rust's borrow checker for the grid/renderer aliasing discipline central to this design; the guarantee ADR-02 gives for free would need to be hand-rolled and audited).

Prerequisites: POSIX terminal I/O (termios, pty(7)), Unicode segmentation (UAX #11/#29), state-machine design, GPU texture-atlas rendering.

Estimated timeline: Phase 0 — 1 week (repo skeleton). Full system (Phases 0–12) — 6 months to a conformant, fuzzed, GPU-accelerated emulator.

Deferred features (see Deferred Features Register for the full table): IME preedit composition PhaseDeferred("§21"); native AppKit renderer PhaseDeferred("§20"); session serialization / crash-restore PhaseDeferred("§15"); built-in multiplexer PhaseDeferred("§18"); Wayland zero-copy fast path PhaseDeferred("§20"); animated sixel/kitty frames PhaseDeferred("§23"); Lua scripting layer PhaseDeferred("§21"); accessibility API (AT-SPI/NSAccessibility/UIA) PhaseDeferred("§19").

2. Why Build This

A terminal emulator is a live, running compilation target for forty years of de-facto protocol: ECMA-48 defines the control functions in eighty pages, DEC's VT100/VT220 manuals define the reference behaviour in hundreds more, and every terminfo entry ever shipped encodes an assumption about which subset of that protocol a xterm-256color TERM value actually implements. Building one from scratch — not gluing together xterm.js or libvte — is the fastest way to internalize: (1) why parsing a byte-oriented protocol that reflects into a live 2D data structure demands a state machine, not a grammar; (2) why "renders text" is a rendering-engine problem indistinguishable from a 2D graphics library once ligatures, BiDi, and inline images are in scope; (3) why security in a terminal is a parsing-robustness problem first (malformed OSC/DCS is the dominant historical CVE class) and a policy problem second (OSC 52 clipboard exfiltration).

It matters architecturally because the terminal is the load-bearing interface between every shell, every TUI (vim, htop, tmux, zellij), and the human at the keyboard; a single dropped escape sequence corrupts a user's mental model of their own screen. It matters historically because the design that won — Paul Williams' state machine, adopted verbatim by xterm, Alacritty's vte, kitty, and WezTerm's termwiz — is a textbook case of a hard problem solved once, correctly, and never revisited; understanding why it won over ad-hoc regex/line-based parsers (still used by lower-rigor implementations like pyte) is a transferable lesson in protocol-parser design generally (compare: HTTP/1.1 header parsing, a JSON SAX tokenizer).

Engineering muscles this builds: state-machine design under adversarial input; strict separation of parsing from side effects (directly reusable in any streaming-protocol codebase — SMTP, IRC, a custom binary RPC framing layer); dirty-region-tracked rendering (reusable in any high-frequency-repaint UI: a log viewer, a spreadsheet, a game HUD); Unicode segmentation and bidirectional text handling; and threat-modeling a parser whose input is, by construction, attacker-influenced (any program run inside the terminal can emit arbitrary bytes to it).

Cross-links to sibling systems in this portfolio: the DEC parser's fixed transition-table dispatch is the same technique as a lexer/tokenizer project; the scrollback ring buffer is the same data structure as a log-tailing system's in-memory ring; the GPU atlas renderer shares its bin-packing and dirty-tracking discipline with any custom 2D rendering engine; the PTY layer's openpty/ConPTY split is the same cross-platform process-supervision problem a container runtime's process-attach feature solves.

Calibration value: after this project, "how would you parse an adversarial byte stream that reflects into shared mutable state at 60 Hz" stops being a hypothetical interview question and becomes a system built and fuzzed for 30 days straight.

  • Explain why alternate-screen mode is two backing stores, not a flag, and what breaks if it isn't — cemented by §15 (Phase 3 — Grid & Screen Model).

  • Distinguish a false-dirty from a false-clean bug and say which one is tolerable — cemented by §20 (Phase 8 — GPU Renderer & Damage Tracking).
  • Design a keyboard-encoding scheme that disambiguates Ctrl-Tab from Ctrl-I without breaking legacy shells — cemented by §21 (Phase 9 — Input Encoder & Window Integration).
  • Explain why OSC 52 clipboard reads are the highest-value terminal CVE surface and how a policy gate closes it — cemented by §23 (Phase 11 — Image Protocols, Hyperlinks & Clipboard) and the Threat Model.
  • Run a differential fuzzer against a reference emulator and diagnose a divergence from first principles — cemented by §24 (Phase 12 — Conformance, Fuzzing & Release Gate).

Host application / window system: owns the OS window, the event pump, and pixel presentation; forwards raw input events and resize notifications; never touches parser or grid state directly (trust boundary 1 — the host is a caller of the Terminal API, not a participant in its invariants).

Input encoder: the only producer of bytes flowing into the PTY; stateless per event (mode stack lookups only); concurrency boundary — runs on whichever thread receives host input events, never the parser thread.

PTY master/shell process: the trust boundary between the emulator and arbitrary attacker-controlled output (any program the user runs can emit any byte sequence); the protocol boundary is exactly the byte stream ECMA-48/xterm define.

Parser: pure function of (state, byte) → (state, action); no grid access; the concurrency boundary is a single-threaded state machine (I1) fed by one PTY-read loop.

Performer: the sole grid mutator (I7); the only component permitted to hold &mut Grid.

Grid: the persistence boundary within the process — the queue/channel boundary between performer (producer) and renderer (consumer) is the dirty bitmap, never the grid itself (the renderer holds a read-only view).

Renderer: a pure consumer of grid state; never re-parses input; never mutates the grid (I6). Two interchangeable backends behind one trait — the swap point is a build/config flag, not a runtime code path duplicated per feature.

Four properties hold system-wide and are referenced throughout: (1) the data path is one-way at the parsing level — bytes flow PTY → parser → performer → grid → renderer; input flows encoder → PTY; there is no back-edge (performer response bytes, e.g. DA1, use a separate typed response channel, not the parser); (2) the parser is pure — all semantic state lives in the performer; (3) the grid is swappable, not flagged — alternate-screen mode swaps two backing stores (ADR-03); (4) the renderer never re-parses — it consumes typed Cell values only. The conformance suite (§29) enforces all four.

6. Design Principles

  1. P1 — Williams' state machine, verbatim. Rule: the parser is the published Paul Williams state machine exactly, no shortcuts. Tradeoff: forecloses a simpler recursive-descent parser that would be easier to read but wrong on overlapping byte classes (ESC vs CSI vs 8-bit C1). Operational implication: any parser change is an ADR, never a patch. Violating it breaks: every shell that assumes xterm-identical parsing (i.e., all of them).
  2. P2 — VT102 baseline plus xterm extensions. Rule: implement the VT102 surface every shell expects, plus the xterm extensions production tooling relies on (mouse, alt screen, bracketed paste, OSC 52/8, SGR). Tradeoff: excludes VT52 and most DEC private modes past the common subset. Operational implication: undocumented extensions are Deferred with a register anchor. Violating it breaks: tmux, vim, htop.
  3. P3 — The grid is typed; renderers are pure consumers. Rule: no path from renderer back into the grid; no re-parsing by the renderer. Tradeoff: a renderer cannot "helpfully" reinterpret raw bytes for a missing feature — it must wait for a performer change. Operational implication: renderer bugs never corrupt grid state (bounds the blast radius, FM-6). Violating it breaks I6.
  4. P4 — Dirty-region rendering by default. Rule: false-positive dirty cells are tolerated (cost: an unnecessary repaint); false-negative dirty cells are forbidden (cost: display corruption). Tradeoff: extra bookkeeping (a per-row bitmap) on every mutation. Operational implication: the conformance suite asserts the dirty set is a superset of the true changed set (I3). Violating it breaks 60 Hz rendering (M4).
  5. P5 — Two backing stores: main and alternate screen. Rule: the alternate-screen flag is a swap pointer (ActiveScreen), never a conditional inside grid operations. Tradeoff: roughly 2× grid memory. Operational implication: alt-screen restore is structurally byte-perfect, not "rebuilt from a flag." Violating it breaks vim/less exit behaviour (I4, ADR-03).
  6. P6 — Scrollback belongs to the main screen; it is a ring buffer. Rule: alternate screen has no scrollback; the main screen's scrollback is a fixed-capacity ring. Tradeoff: index arithmetic on every read. Operational implication: amortised O(1) insert regardless of history length (I5, ADR-04). Violating it breaks memory bounds under long-running sessions.
  7. P7 — UTF-8 is the default character set. Rule: ISO 2022 SCS designations are supported for legacy compatibility but never the default. Tradeoff: legacy-charset code paths are maintained but rarely exercised. Operational implication: new shells work out of the box; legacy ones opt in via SCS. Violating it breaks modern CJK/emoji rendering by default.
  8. P8 — Cell width follows UAX #11 with ambiguous-narrow default. Rule: match the consensus of xterm/Alacritty/kitty/WezTerm; hosts may opt into ambiguous-wide via config. Tradeoff: a few legacy East-Asian-locale applications misalign. Operational implication: one config knob, not a runtime auto-detect heuristic. Violating it breaks column alignment for the majority default case.
  9. P9 — The kitty keyboard protocol is supported; legacy CSI is the fallback. Rule: both encodings coexist behind a mode-stack. Tradeoff: three keyboard encodings to maintain (legacy, modifyOtherKeys, kitty). Operational implication: TUI apps that push the kitty protocol get lossless key events; others get legacy behaviour unchanged. Violating it breaks Ctrl-Tab vs Ctrl-I disambiguation (ADR-09).
  10. P10 — All response sequences flow through a typed channel, never a direct PTY write. Rule: DA1/DA2/DSR/DECRQSS responses are emitted via ResponseChannel, never inline from the performer. Tradeoff: one more indirection layer. Operational implication: responses are unit-testable without a live PTY (I14). Violating it makes response correctness untestable in isolation.
  11. P11 — Every escape sequence has a resource budget. Rule: a malformed sequence that would consume unbounded memory or CPU is capped (max_params, max_osc_bytes, max_dcs_bytes) — the ReDoS-in-practice pattern (Davis et al. 2018) applied to escape parsing. Tradeoff: a handful of legitimate large sixel DCS bodies must fit the cap or be chunked. Operational implication: the historical OSC/DCS-overflow CVE class is structurally closed (I2, ADR-11). Violating it reopens that CVE class.
  12. P12 — Clipboard reads via OSC 52 are policy-gated; writes are not. Rule: OSC 52 writes are allowed by default; reads require explicit per-window user consent. Tradeoff: a few legacy "read clipboard via escape sequence" workflows break by default. Operational implication: the dominant terminal clipboard-exfiltration CVE class (T3) is closed at the policy layer, not just the parser layer. Violating it reopens T3.
  13. P13 — The parser is single-writer, single-state; concurrency lives above it. Rule: one Parser instance per session, driven by exactly one PTY-read loop; no shared mutable parser state across threads. Tradeoff: cannot parallelize parsing of one stream (not needed — throughput target M2 is met single-threaded). Operational implication: no lock is ever taken inside the parser hot path. Violating it introduces data races on ParserState (I1).
  14. P14 — Fonts and shaping are FFI boundaries, never reimplemented. Rule: FreeType rasterizes, HarfBuzz shapes; the emulator owns none of that logic. Tradeoff: two C library dependencies with their own thread-safety rules (FreeType is not thread-safe). Operational implication: font bugs are upstream bugs, filed against FreeType/HarfBuzz, not this codebase. Violating it (reimplementing shaping) reinvents a multi-year effort poorly.

8. Domain Model

8.1 Escape-sequence grammar (EBNF)

Escape sequences are not context-free (final-byte meaning depends on parser state), but the byte-level shape is expressible as EBNF; the dispatch is the state machine below (§8.2), not this grammar alone.

sequence        ::= c0-seq | esc-seq
c0-seq          ::= %x00-1F                          ; single control byte, "execute"
esc-seq         ::= ESC ( final-1b | csi-seq | osc-seq | dcs-seq | intermediate esc-seq )
csi-seq         ::= "[" params? intermediates? final-csi
osc-seq         ::= "]" osc-body ( BEL | ST )
dcs-seq         ::= "P" params? intermediates? final-dcs dcs-body ST
params          ::= param ( ";" param )*
param           ::= subparam ( ":" subparam )*
subparam        ::= 1*DIGIT
intermediates   ::= 1*2( %x20-2F )
final-csi       ::= %x40-7E
final-dcs       ::= %x40-7E
final-1b        ::= %x30-7E
osc-body        ::= *( %x20-7E )                      ; capped at max_osc_bytes (ADR-11)
dcs-body        ::= *OCTET                            ; capped at max_dcs_bytes (ADR-11)
ST              ::= ESC "\"
BEL             ::= %x07
ESC             ::= %x1B

8.2 Parser state-transition table (Paul Williams DEC state machine)

13 states, byte-class-driven, fixed transitions (excerpted; the full 256×13 table is generated at build time from this specification, not hand-maintained):

State On 0x00–0x17,0x19,0x1C–0x1F (C0) On 0x1B (ESC) On printable (0x20–0x7F) On [ (after ESC) On final byte
Ground execute, stay → Escape print, stay — —
Escape execute, stay → Escape (re-enter) → EscapeIntermediate or dispatch → CsiEntry esc_dispatch, → Ground
CsiEntry execute, stay → Escape (abort) digit → CsiParam; ;/: → CsiParam — csi_dispatch, → Ground
CsiParam execute, stay → Escape (abort) digit/;/: → stay; intermediate → CsiIntermediate — csi_dispatch, → Ground
CsiIntermediate execute, stay → Escape (abort) intermediate → stay — csi_dispatch, → Ground
CsiIgnore execute, stay → Escape (abort) consume, stay — ignore, → Ground
OscString ignore except BEL ST sequence → dispatch osc_put, stay (capped, I2) — BEL → osc_dispatch, → Ground
DcsEntry/Param/Intermediate ignore → Escape (abort) collect params/intermediates — → DcsPassthrough on final
DcsPassthrough dcs_put, stay (capped, I2) ST → dcs_unhook, → Ground dcs_put, stay — —
DcsIgnore ignore → Escape (abort) consume, stay — ST → Ground
SosPmApcString ignore ST → Ground consume (diagnostic-only), stay — —

Eleven dispatchable actions cover every observable side effect: print, execute, csi_dispatch, esc_dispatch, osc_start/osc_put/osc_end, dcs_hook/dcs_put/ dcs_unhook, ignore.

8.3 Worked example — ESC [ 1 ; 31 m H i ESC [ 0 m

Step Byte(s) State before Action State after Grid effect
1 1B Ground (transition only) Escape none
2 5B (‘[’) Escape (transition only) CsiEntry none
3 31 (‘1’) CsiEntry param digit CsiParam none
4 3B (‘;’) CsiParam param separator CsiParam none
5 33 31 (‘31’) CsiParam param digits CsiParam none
6 6D (‘m’) CsiParam csi_dispatch(params=[1,31], final='m') → SGR handler (§16) Ground cursor's `attrs
7 48 (‘H’) Ground print('H') Ground cell at cursor gets Cell{glyph:'H', fg:Indexed(1), attrs:BOLD,…}; cursor advances
8 69 (‘i’) Ground print('i') Ground same as step 7 for 'i'
9 1B 5B 30 6D Ground→…→CsiParam csi_dispatch(params=[0], final='m') → SGR reset Ground cursor attrs/fg/bg reset to default

Result: two bold red cells H, i at the pre-sequence cursor position, cursor advanced two columns, attributes reset for subsequent prints — exactly the grid state vttest chapter 3 asserts for this class of fixture.

8.4 Malformed-input example — unterminated OSC

Input: ESC ] 0 ; followed by 10,000 bytes of printable ASCII with no BEL/ST. Behaviour: the parser enters OscString, accumulates via osc_put until max_osc_bytes = 4096 (ADR-11) is reached, then stops accumulating but stays in OscString (does not re-enter Ground early — doing so would misinterpret the remaining attacker bytes as commands). On eventual BEL/ST (or PTY EOF), osc_dispatch fires with a truncated: true flag; the performer applies the window-title semantics to the first 4096 bytes only and increments parser.truncations_total (I2, telemetry). No allocation exceeds the cap; no hang.

8.5 Failure-path example — differential divergence on truecolor SGR

Scenario: the Phase 12 differential fuzzer (§24) feeds ESC [ 38:2::255:0:0 m (the modern colon-delimited truecolor syntax, no color-space id) to this emulator and to a reference xterm. Divergence: xterm (older builds) treats the missing color-space subparameter as a parse error and ignores the whole SGR; this emulator's parser accepts the empty subparameter per the modern spec and sets Color::TrueColor{255,0,0}. Root-cause path: the differential harness flags a grid-state mismatch at the affected cell, dumps both grids via Grid::dump_screen(), and the on-call engineer consults ADR-06's rationale column to confirm the divergence is a known, accepted one (modern-syntax support) rather than a bug — the fixture is then added to conformance/buckets/csi/sgr/ with an expected_divergence: true marker so future fuzz runs do not re-flag it (see N.9 of §16 for the phase-level version of this procedure).

13. Phase 1 — PTY Layer

13.1 Objectives

Deliver the smallest possible abstraction exposing a bidirectional byte stream connected to a child shell process, cross-platform (ADR-12), satisfying I11 (no fd leak) and feeding the Phase 2 parser.

13.2 Detailed Implementation Steps

Unix: openpty (or posix_openpt+grantpt+unlockpt) then fork+setsid+dup2 of the slave onto the child's stdio. Windows: CreatePseudoConsole + UpdateProcThreadAttribute + CreateProcess (per the ConPTY reading, §5). Both hide behind the Pty trait (§11, ADR-12). Lifecycle: spawn — PtyBuilder::spawn() returns (Box<dyn Pty>, ChildHandle); read — non-blocking, fd registered with epoll/kqueue/IOCP on the event loop (P13: one PTY-read loop per session, feeding the single-writer parser, I1); write — blocking on the master fd, backpressure is the kernel pipe buffer, 64 KB default (ADR-23, §4 FD budget); resize — ioctl(fd, TIOCSWINSZ) / ResizePseudoConsole, sends SIGWINCH; kill — SIGHUP to the child group (Unix) / close the pseudoconsole handle (Windows).

13.3 Deliverable

tem-pty compiles on Linux/macOS/Windows; exposes spawn(builder) -> (Box<dyn Pty>, ChildHandle) plus the Pty trait; hello-pty example opens a PTY, runs echo hello, prints the received bytes.

13.4 Acceptance Criteria

Read throughput ≥ 1 GB/s from the kernel pipe buffer on Linux (§4); the "spawn 10,000 PTYs in a loop" soak test (I11) completes with zero fd leak (lsof count returns to baseline ±0); hello-pty output matches hello\n byte-for-byte.

13.5 Conformance Fixtures

Fixture Purpose Expected Output

pty_resize_sigwinch Resize the PTY Child observes new size via getwinsize

13.6 Pitfalls

Forgetting setsid after fork on Linux leaves the child sharing the parent's controlling terminal — Ctrl-C then routes to the parent, not the shell. On macOS, openpty's master fd does not propagate ECHO — the slave's termios needs explicit tcsetattr initialisation (the pty-process crate has the canonical sequence, §5). ConPTY's undocumented "no FILE_FLAG_OVERLAPPED" rule — an overlapped handle silently drops bytes on Windows. A child that exits faster than the event loop registers its PID races SIGCHLD delivery — register the PID before fork, never after.

13.7 Performance Concerns

Write throughput is bounded by the 64 KB kernel pipe buffer (ADR-23); a large paste fills it and backpressures the writer until the child reads — this is intentional (P11-adjacent budget discipline, no internal queue masking it).

13.8 Edge Cases

A resize landing mid-read must not corrupt in-flight parse state — the event loop serialises resize and read on one mutex (see §20 N.8 for the renderer-side race). A child that never reads its stdin (a hung shell) backpressures forever — the host UI surfaces a "process not responding" state after the FM-1 watchdog window.

13.9 Failure Analysis

A leaked PTY master fd is a persistent fd exhaustion risk under long-running multi-tab usage (§4 FD budget: 340-session ceiling assumes zero leaks). Detection: Pty::open_fds_gauge telemetry (I11) trending upward without matching session closes. Recovery: the Drop impl on PtyHandle closes both ends unconditionally; the soak test is the structural regression guard.

13.10 Operational Notes

RUST_LOG=tem_pty=trace logs every fd creation, dup, and ioctl (ADR-16). The hello-pty example is the canonical "is the PTY layer functional?" smoke test for a new platform port.

14. Phase 2 — DEC Parser (Escape-Sequence State Machine)

14.1 Objectives

Implement the Paul Williams DEC state machine (§8.1–8.2, P1) exactly — the load-bearing correctness kernel every downstream phase depends on. Establish I1 (no unbounded loop) and I2 (no unbounded allocation) as enforced, tested invariants, not aspirations.

14.2 Detailed Implementation Steps

Parser (§11) holds ParserState plus accumulator buffers; advance(byte) drives one transition per the §8.2 table, dispatching one of the eleven actions to a Performer via ADR-02's verbatim-implementation decision. Limits per ADR-11/I2: max_params = 16 (xterm allows 30; capped lower to bound worst-case CSI dispatch cost), max_intermediates = 2 (ECMA-48), max_osc_bytes = 4096, max_dcs_bytes = 65536 (sixel is the only legitimate large DCS, §23). The transition table itself is generated at build time (tools/gen-transitions) from the §8.2 specification, not hand-maintained, to keep the implementation and this document's state table from drifting (P1).

14.3 Deliverable

tem-parser — a single-file state machine with a generated transition table; Performer is the consumer trait (§11); a property test fuzzes the parser with random byte streams.

14.4 Acceptance Criteria

Throughput ≥ 100 MB/s single-core for pass-through streams (M1); the property fuzz test runs 10⁹ random byte sequences with zero panics, zero allocations past the ADR-11 caps, zero hangs (I1, I2); every vttest parser-level fixture (chapters 1–3) produces the expected action sequence.

14.5 Conformance Fixtures

Fixture Purpose Expected Output
parser_sgr_trace.yaml The §8.3 worked example Action sequence matches §8.3 table exactly
parser_osc_truncation.yaml The §8.4 malformed-OSC case truncated: true, parser.truncations_total += 1

14.6 Pitfalls

C1 controls arrive as raw bytes in 8-bit-clean mode and as two-byte ESC equivalents otherwise — both paths must produce identical actions. CSI 0x3A (:) is the modern SGR sub-parameter delimiter but an illegal-byte-restart in older xterm — ECMA-48's modern interpretation is followed (ADR-06 style precedent). A printf with an embedded ESC at byte 500,000 must not buffer the first 500,000 bytes — the parser streams byte-by-byte, never buffers ahead. Bell (0x07) and ST (ESC \) both terminate OSC — both are conformance-tested.

14.7 Performance Concerns

Throughput target (M1/M2) is memory-bandwidth-limited for pass-through streams; CSI-heavy streams (e.g. htop's redraw storm) are slower due to per-sequence dispatch overhead — the transition table lookup is O(1) but the csi_dispatch match in the performer (§15–§18) dominates wall time under heavy CSI load.

14.8 Edge Cases

A CSI sequence with more than max_params parameters is truncated and dispatched with ignore: true rather than dropped silently (I2). A DCS body that never sees ST (process exits mid-sequence) is flushed via unhook on PTY EOF, not left dangling. Nested/re-entrant ESC bytes inside an OSC string abort the OSC and restart from Escape (§8.2 table, "abort" transitions).

14.9 Failure Analysis

A transition-table bug allowing a state to loop without consuming a byte is the single worst possible parser bug (denial of service on the render thread). Detection: the property fuzz test asserts strict byte-cursor monotonic advance (I1) every iteration; CI fails the build on any violation, not just a nightly report. Blast radius if it escaped to production: the render loop stalls indefinitely (FM-1). Recovery: the watchdog (§4 availability budget: 100 ms) resets the parser to Ground and logs the last N bytes for offline replay via tem-conformance replay.

14.10 Operational Notes

RUST_LOG=tem_parser=trace logs every state transition (ADR-16); Parser::dump_state() prints the current state and accumulator contents for live debugging. The differential fuzz target (fuzz/fuzz_targets/differential.rs, §24) runs continuously in the 30-day canary against this exact parser build.

19. Phase 7 — Software Renderer (CPU)

19.1 Objectives

Deliver a FreeType-based renderer drawing into a CPU framebuffer — the fallback for GPU-less hosts and the reference for headless/CI testing (P3, P4).

19.2 Detailed Implementation Steps

Pipeline: (1) receive the grid's dirty bitmap (I3); (2) for each dirty row, iterate cells and draw each into the framebuffer; (3) glyph cache keyed by (font, size, codepoint, attrs), LRU-evicted at a fixed memory cap; (4) present the framebuffer (Vec<u8> RGBA8) to the host. Font handling: primary font from config, fallback fonts for missing glyphs (CJK/emoji/math); font metrics fix the cell size. Rendering: integer-aligned cell positions (no subpixel positioning, P4); subpixel AA follows host preference; bold uses the bold font variant or synthesises via double-strike; italic uses the italic variant or synthesises via skew.

19.3 Deliverable

tem-render-cpu compiles against freetype-rs; the headless-bench example renders a 132×60 grid at 60 Hz for 10 s and reports achieved frame rate.

19.4 Acceptance Criteria

A 10%-dirty-cell repaint: 2 ms p50, 5 ms p99 (M3). A full repaint: 20 ms p50, 50 ms p99 (M3). Headless output is pixel-identical to a curated reference-PNG set (conformance/buckets/render/).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
render_reference_pngs/ Curated grid states rendered offscreen Pixel-identical to reference PNGs
render_10pct_dirty.bench Partial repaint timing ≤ 2 ms p50 / 5 ms p99 (M3)
render_full_repaint.bench Full repaint timing ≤ 20 ms p50 / 50 ms p99 (M3)

19.6 Pitfalls

FreeType is not thread-safe (P14) — the renderer holds the FT library on a single thread and serialises glyph rasterisation. Glyph-cache eviction must consider the dirty bitmap — an evicted-then-immediately-redrawn glyph is a 1000× slowdown on the next frame. Subpixel-positioning bugs produce visible edge fringing — the renderer asserts integer-aligned cell positions at every draw call.

19.7 Performance Concerns

The glyph cache is the dominant performance lever — a cache miss costs a full FreeType rasterisation (~10–50 µs) vs. a cache hit's memcpy (~100 ns); the LRU cap is sized to the working-set glyph count of a typical 132×60 session (a few hundred distinct (font,size,codepoint,attrs) tuples).

19.8 Edge Cases

A font file lacking emoji glyphs renders empty cells unless the fallback-font chain is exercised — the bucket includes a font with deliberately missing emoji coverage to force the fallback path. A glyph cache at capacity during a burst of novel codepoints (e.g. a large non-ASCII paste) evicts aggressively — verified not to thrash by measuring eviction rate under the "50 MB pasted JSON blob" scenario (§1-adjacent motivating case).

19.9 Failure Analysis

A cache-eviction bug that drops a glyph still referenced by the dirty bitmap renders a blank cell for one frame — low severity, self-heals on the next full repaint, but is still a conformance-bucket regression (render_reference_pngs/). Detection: pixel-diff against the reference set. Recovery: none needed at runtime (self-healing); fix upstream in the eviction policy.

19.10 Operational Notes

headless-bench doubles as the CI performance-regression gate (Performance Engineering) — a regression beyond M3's p99 budget fails the conformance.yml workflow, not just a nightly report.

20. Phase 8 — GPU Renderer & Damage Tracking

20.1 Objectives

Deliver a wgpu-based atlas renderer meeting the ≤2 ms p99 full-repaint budget (§4, M4) and formalise damage tracking (I3) as a first-class renderer contract, not an implementation detail of the CPU backend alone.

20.2 Detailed Implementation Steps

A 4096×4096 RGBA8 atlas texture holds pre-rasterised glyphs (ADR-07); the vertex shader emits one quad per cell, the fragment shader samples the atlas. Atlas management: a missing glyph is rasterised on-demand via FreeType (shared discipline with §19, P14) and uploaded to the next free slot via a skyline/shelf bin-packer; eviction is LRU at the row granularity, batched at frame end (never mid-frame, N.6); multiple atlases back a working set exceeding 4096×4096. Damage tracking: the renderer consumes Grid's dirty bitmap (I3) and only re-emits quads for dirty cells; 2026 synchronized-output mode (§18) defers presentation until ESU to avoid multi-step-redraw flicker (P4).

20.3 Deliverable

tem-render-gpu compiles on Linux (Vulkan+GL), macOS (Metal), Windows (DX12+Vulkan); headless-bench reports GPU frame times against the M4 budget.

20.4 Acceptance Criteria

Full repaint of 132×60 < 1 ms on a 4080-class GPU, < 4 ms on integrated Intel UHD (M4); output identical to the CPU renderer within a configurable per-pixel dithering tolerance (cross-backend conformance).

20.5 Conformance Fixtures

Fixture Purpose Expected Output

atlas_overflow.yaml Working set > one 4096² atlas Second atlas allocated, no visible glitch
sync_output_2026.yaml BSU/ESU bracketed update No intermediate frame presented

20.6 Pitfalls

wgpu's Wayland surface configuration is finicky — the host must pass the surface; the renderer cannot create it (P3 boundary: renderer never owns window resources). An atlas eviction mid-frame is a bug — eviction is batched strictly at frame end. Subpixel-rendered glyphs need one atlas entry per pixel offset — the cache key includes the offset, or glyphs alias incorrectly.

20.7 Performance Concerns

Per-pixel cost is one texture sample plus a background blend — the atlas-miss rasterisation cost (shared with §19) is the only unbounded-looking cost, bounded in practice by the working-set size of a typical session (a few hundred glyphs).

20.8 Edge Cases

A resize that races with a PTY read (shared race class with §13 N.8) must not present a partially-resized atlas — the event loop's single mutex covers both the grid and the renderer's frame-begin. An atlas overflow during heavy emoji use (large working set of rare glyphs) is the eviction policy's stress case — verified not to glitch by a dedicated fixture (§20.5).

20.9 Failure Analysis

An atlas-eviction race (a glyph evicted while its quad is still queued for this frame) produces a visible one-frame glitch (wrong glyph or blank quad) — the load-bearing fix is the "batch eviction at frame end" rule (N.6); detection is the parity fixture (§20.5) run under fuzzed eviction pressure; recovery is self-healing on the next frame (the glitch does not persist, but the fixture treats even a single occurrence as FAIL).

20.10 Operational Notes

GPU frame times are exported via the metrics crate (ADR-17) as renderer.gpu_frame_time_ns, gated in CI against M4 the same way §19's CPU path is gated against M3 (Performance Engineering).

Encode keyboard/mouse/paste events into the correct byte sequences per the active protocol (P9, ADR-09) and define the host-integration contract (window creation, resize, clipboard, focus) that later phases assume.

21.2 Detailed Implementation Steps

tem-input::encode(key, mods, mode_stack) -> SmallVec<u8>: legacy CSI (ESC[1;5A for Ctrl-Up, the back-compat default); modifyOtherKeys=2 (CSI 27;5;105~ disambiguates Ctrl-I from Tab); kitty keyboard protocol (CSI <codepoint>;<mods>:<event> u, enabled via CSI > N u, P9). Modes are pushed/popped via CSI > Pm u/CSI < Pm u, maintained as a stack per session (topmost wins, N.6). Mouse: X10/X11 (CSI M Cb Cx Cy, capped at column 223), SGR (CSI < Cb;Cx;Cy [Mm], no cap), urxvt, pixel-precision. Bracketed paste: host clipboard events wrap in ESC[200~/ESC[201~ when mode 2004 is on; large pastes chunk at 4 KB and yield to the event loop between chunks (prevents UI freeze on the "50 MB pasted JSON blob" scenario, §1). Window integration: the host owns the window/event pump; the emulator exposes a Terminal struct consuming host-provided input events and producing a renderer-ready framebuffer (CPU) or drawing into a host surface (GPU, §20); the host is responsible for keyboard/mouse capture, resize, clipboard provider, and presentation.

21.3 Deliverable

tem-input exposes encode/encode_mouse; examples/kitty-keyboard-demo.rs and examples/winit-terminal.rs demonstrate both keyboard modes and full window integration across winit-on-X11/Wayland/macOS/Windows plus a headless test host.

21.4 Acceptance Criteria

Encoding cost < 100 ns per event (M8); every encoding/modifier/key-class combination has a fixture in conformance/buckets/keyboard/; window-to-PTY latency (keypress to display) < 16 ms p99 (§4-adjacent frame budget); a helix session runs 60 minutes on each supported platform without a visible glitch (manual + nightly canary loop).

21.5 Conformance Fixtures

Fixture Purpose Expected Output

mouse_encoding_matrix.yaml X10/X11/SGR/urxvt/pixel Byte-exact match; SGR uncapped past column 223

21.6 Pitfalls

Mode-stack ordering: the topmost mode wins; pushing a new mode never retroactively affects in-flight key events (N.2). Function-key encoding varies by terminfo entry — the emulator emits xterm-standard sequences and lets terminfo translate, never special-cases a specific shell. A paste containing raw ESC bytes is delivered verbatim inside the bracket markers — filtering is the application's responsibility, not the terminal's (Threat Model T8). A resize racing a PTY read (shared with §13/§20) corrupts the grid if unserialised — one event-loop mutex covers all three.

21.7 Performance Concerns

Encoding is allocation-free on the hot path (SmallVec avoids heap allocation for the common ≤16-byte sequence case); the mode-stack lookup is O(1) (a fixed-depth stack, not a hashmap).

21.8 Edge Cases

A 250-column terminal under legacy X10/X11 mouse encoding silently miscodes coordinates past column 223 (protocol limitation, not a bug) — the encoder logs a warning and recommends SGR mode when the grid exceeds 223 columns. A bracketed paste that spans a mode toggle (bracketed paste disabled mid-paste by the application) completes the in-flight paste under the mode active at paste-start, never mid-switches.

21.9 Failure Analysis

A modifyOtherKeys-encoding bug that makes Ctrl-Tab indistinguishable from Ctrl-I breaks any TUI relying on the distinction — user-visible as "my keybinding doesn't work." Detection: the keyboard-encoding-matrix bucket (§21.5). A host that never calls Terminal::tick() stalls the parser entirely — the Terminal trait's documented contract makes this an integration bug, not a terminal-emulator bug; detection is a "minimum tick rate" assertion in the winit example.

21.10 Operational Notes

examples/winit-terminal.rs is the canonical integration reference for a new host platform; the nightly 60-minute helix soak (§21.5) is the operational regression gate for window-integration correctness across all five supported hosts.

22. Phase 10 — Ligatures (HarfBuzz) & BiDi (UAX #9)

22.1 Objectives

Add font-shaping-driven ligatures (P14) and UAX #9 bidirectional reordering for RTL scripts, both render-time passes over the otherwise-unmodified logical grid.

22.2 Detailed Implementation Steps

Ligatures: the renderer collects a run — a contiguous sequence of cells with identical font/size/attrs — and passes it to HarfBuzz (P14, §5 Required Reading) for shaping; the output glyph IDs/positions replace per-codepoint rendering; a cell whose glyph crosses a boundary suppresses the neighbour's independent draw. Off by default; per-glyph blacklist supported (e.g. excluding == ligatures some users find confusing). BiDi: the grid stores cells in logical (as-written) order always; at render time, UAX #9 (paper, §5) produces a visual order per line; a (logical_col → visual_col) cache per line lets cursor placement and selection (§18) translate between the two; embedded LTR runs inside RTL text use the spec's directional-run analysis; BiDi is strictly per-line — lines never interact.

22.3 Deliverable

tem-shape wraps HarfBuzz; tem-bidi implements or wraps UAX #9; conformance/buckets/ligatures/ covers Fira Code, JetBrains Mono, Cascadia Code; conformance/buckets/bidi/ runs the full UAX #9 test corpus.

22.4 Acceptance Criteria

Every entry in the UAX #9 corpus passes; visual diff against reference PNGs matches for all three ligature test fonts; shaping cost ≈ 10 µs per run (cached per (font, attrs, codepoint sequence)); per-line BiDi cost ≤ 100 ns ASCII fast path, ≤ 10 µs mixed RTL/LTR line.

22.5 Conformance Fixtures

Fixture Purpose Expected Output
ligature_fira_code.png Reference-diff for Fira Code arrows Pixel match within AA tolerance
ligature_attr_boundary.yaml Ligature spanning an attribute change Shaping run splits at the boundary
uax9_bidi_corpus.yaml Full UAX #9 test corpus Every case's visual order matches the annex
bidi_cursor_rtl.yaml Cursor placement mid-RTL-run Visually correct column via the mapping cache

22.6 Pitfalls

HarfBuzz is a C library — the FFI boundary must handle UTF-8 input and report shaping errors, never panic across the boundary (P14). A ligature spanning an attribute boundary (one cell bold, the next not) must be split — the shaper runs per-attribute-run, never across one. Cursor placement on a ligature is editor-dependent; the emulator places the cursor on the logical cell, not the visual glyph — consistent with the BiDi logical/visual split (§22.2). The UAX #9 corpus's tricky cases (mirroring, weak types, neutral characters) are exactly where naive implementations diverge from the annex.

22.7 Performance Concerns

Shaping is cached per (font, attrs, codepoint sequence) — the cache hit rate for a typical coding session (mostly-repeated ligature patterns like ->, =>, ==) is high; the ASCII-only BiDi fast path (100 ns) dominates for the common case, since most terminal sessions are LTR-only.

22.8 Edge Cases

A ligature test font with no ligature table for a given sequence falls back to per-codepoint rendering, never a blank cell. An RTL line containing an embedded URL (LTR run inside RTL text) is handled by UAX #9's directional-run analysis, verified by a dedicated corpus case.

22.9 Failure Analysis

A run-detection bug that crosses an attribute boundary produces visibly incorrect shaped output (e.g. a ligature rendered across a color change) — caught by the ligature_attr_boundary fixture pre-release; no runtime self-check exists since shaping is deterministic given the same run. A mirroring bug in the BiDi pass produces backwards-pointing brackets in RTL text — caught by the UAX #9 corpus; both are release-blocking conformance failures, not runtime-recoverable.

22.10 Operational Notes

Ligature and BiDi passes are both feature-flagged independently (config, not compile-time) so an operator can disable either without a rebuild if a font or script triggers a regression in production.

23. Phase 11 — Image Protocols, Hyperlinks & Clipboard

23.1 Objectives

Implement the three inline-image protocols (sixel, kitty graphics, iTerm2), OSC 8 hyperlinks, and policy-gated OSC 52 clipboard (P12, ADR-10) — the phase with the largest security surface in the system (Threat Model T1–T3, T7, T9, T11).

23.2 Detailed Implementation Steps

Images: sixel (DCS sequence, six-vertical-pixel runs, DEC technical manual, §5) — chained color introducers parsed greedily; kitty graphics (APC, base64 image data, chunked via a c= parameter the performer accumulates across multiple APC sequences into a pending-chunks buffer); iTerm2 (OSC 1337, a File=... sub-format). All three decode into an ImageTable (§11 Grid) keyed by protocol-derived id; a Placement anchors an image at (row, col, width, height); the renderer draws images beneath cells, alpha-composited where cells overlay. Hyperlinks: OSC 8 ; params ; URI assigns a HyperlinkId (I13), copied onto every subsequently printed cell until an empty-URI OSC 8 clears it; the renderer underlines linked cells; click handling resolves (row, col) → URI via the host's "open" callback. Clipboard: OSC 52 ; c ; base64 write passes decoded bytes to the host provider if policy allows (write allowed by default, P12); OSC 52 ; c ; ? read is policy-gated, default deny, explicit per-window consent required (ADR-10, I12).

23.3 Deliverable

tem-images (three protocols), tem-performer/src/osc.rs (OSC 8/52 dispatch), tem-clipboard (policy + host integration); buckets images/, hyperlinks/, clipboard/.

23.4 Acceptance Criteria

The curated PNG set decodes and matches reference grid+image state exactly; a 1024×1024 PNG decodes and uploads in ≤ 50 ms (M9); hyperlink dispatch < 100 ns; OSC 52 base64 decode of a 1 MB clipboard ≤ 5 ms; OSC 52 read policy tested in all three configurations (deny, allow, prompt) with zero unauthorized reads (I12).

23.5 Conformance Fixtures

Fixture Purpose Expected Output
images_curated_set.yaml Sixel/kitty/iTerm2 decode Grid + image state matches reference
kitty_chunked_upload.yaml Multi-APC chunked image Reassembled correctly across chunks
hyperlink_roundtrip.yaml Emit → render → click Correct URI delivered to host callback
osc52_policy_matrix.yaml Deny/allow/prompt × read/write Zero reads bypass policy (I12)

23.6 Pitfalls

An OSC 8 with a malformed URI is logged, not rendered as a clickable link — the emulator never validates or normalises the URI itself. An OSC 52 read with no policy gate is the historical hostile-shell-prompt clipboard-exfiltration vector (T3) — the default-deny policy is load-bearing, not a nice-to-have. A sixel image with an extreme aspect ratio risks an allocation-size attack — dimensions are capped at 8192×8192 (Threat Model T11). The kitty protocol's chunked upload requires state across multiple APC sequences — a missing chunk (connection interrupted mid-image) must time out and discard the pending buffer, never accumulate unbounded.

23.7 Performance Concerns

Image decode (PNG/JPEG) is the most expensive single operation in the system (M9's 50 ms budget dwarfs every other per-event cost in this document) — it runs off the parser's hot path, in a dedicated decode task, so a large image never stalls byte parsing (P13 boundary).

23.8 Edge Cases

A malformed image payload (truncated PNG, corrupt sixel stream) fails decode in isolation — it must not corrupt parser state or leave the DCS/APC accumulator in a bad state for the next sequence (I2-adjacent). A clipboard write larger than the host's clipboard-size limit is truncated with a logged warning, never silently dropped without signal.

23.9 Failure Analysis

A malformed image protocol that allocates unbounded memory is a CVE-class bug (T1/T2 analogue for images) — mitigated by the 64 MB per-image size budget (Threat Model); detection is the fuzz target covering image decode paths (§24); blast radius if it escaped is a single-session OOM, not cross-session, since images are scoped to one ImageTable. A clipboard-policy bypass (a code path that reads without checking policy) is the single worst-case security bug in this phase — the conformance bucket (osc52_policy_matrix) is fuzzed specifically to catch a bypass, and any policy check added later must route through the one tem-clipboard gate, never a duplicate check site.

23.10 Operational Notes

Clipboard-policy decisions are logged (who requested, what was decided, which window) via tracing (ADR-16) at info level for read-attempts and debug for writes — the audit trail is the primary operational tool for diagnosing a disputed "did my clipboard get read" incident.

24. Phase 12 — Conformance, Fuzzing & Release Gate

24.1 Objectives

Assemble every prior phase's conformance bucket into one CI-gated suite, run the fuzz targets to zero findings, and stand up the 30-day continuous canary — the phase that converts "we believe it's correct" into "we can prove it's correct" (Testing & Verification Strategy).

24.2 Detailed Implementation Steps

tem-conformance is the CLI runner over every bucket from §10 (parser/, csi/, osc/, dcs/, modes/, charset/, width/, grapheme/, alt_screen/, scroll/, mouse/, keyboard/, paste/, hyperlinks/, clipboard/, images/, ligatures/, bidi/, ime/ [Deferred], responses/, differential/); a bucket is Pass (every fixture green), Deferred (carries a Deferred Features Register anchor), or Fail (release blocker). Five fuzz targets (fuzz/fuzz_targets/): parser_bytes (random bytes → parser, I1/I2), performer_actions (random actions → performer, grid invariants hold), grid_invariants (random mutations → I3 superset check), input_encode (random KeyEvents → well-formed output), differential (this emulator vs. xterm/Alacritty headless, §8.5's divergence-triage procedure generalised). CI (fuzz.yml) runs each target 5 minutes per PR; an external 30-day canary runs continuously and is published quarterly (Operational Readiness).

24.3 Deliverable

tem-conformance CLI producing a JSON report; every bucket at Pass on every CI matrix entry; the 30-day canary report artifact.

24.4 Acceptance Criteria

All 21 buckets green; every fuzz target runs its 5-minute CI budget with zero findings; the full conformance suite completes in < 10 minutes on a 16-core runner (M12-adjacent, vttest chapters 1–11 specifically ≤ 60 s p50 / 90 s p99); the 30-day canary completes with zero unexpected findings (only pre-registered expected_divergence entries, §8.5).

Fixture Purpose Expected Output

24.6 Pitfalls

Differential testing against xterm requires xterm in headless-PTY mode — the CI image bakes it in as a pinned version (reproducibility, ADR-21). A fuzz target that consumes unbounded memory crashes the harness itself rather than reporting a finding — every target caps PTY buffer size and iteration count independent of the ADR-11 in-process caps, as defense in depth. A new feature landing without an accompanying fixture is untested by construction — the PR template (CONTRIBUTING.md) requires a fixture path for any behaviour change.

24.7 Performance Concerns

The full suite's 10-minute CI budget is dominated by the differential bucket (spawning a reference emulator per fixture) — parallelised across the CI matrix's available cores to stay under budget; the 30-day canary runs on dedicated infrastructure outside the PR-gating path entirely, so it never blocks a merge.

24.8 Edge Cases

A fixture that passes locally but fails in CI due to a font-rendering difference (§19) between the developer's machine and the CI image is resolved by pinning the CI image's font set exactly (reproducibility, same discipline as ADR-21). A fuzz-found divergence that is neither a bug nor a known-accepted divergence (§8.5) blocks the PR until triaged — there is no silent "probably fine, ignore it" path.

24.9 Failure Analysis

A regression that passes all 21 buckets but fails the 30-day canary (a divergence only reachable after hours of accumulated state, e.g. a scrollback-ring wraparound bug) is the hardest class to catch pre-release — detection relies entirely on the canary's continuous operation; blast radius is bounded to the specific accumulated-state bug class; recovery is adding a targeted long-running fixture to the standard suite once found, so the next regression is caught in the 10-minute path instead of the 30-day one.

24.10 Operational Notes

The quarterly canary report (marketing/transparency-reports/<period>.md-equivalent, here docs/performance/canary-<period>.md) is the operational artifact an on-call engineer consults first when a user reports "the terminal glitched after running for days" — it is cross-referenced against FM-1 through FM-10 (Failure Modes & Recovery) by symptom.

27. Operational Readiness

Metrics: exported via the metrics crate (ADR-17) to a Prometheus-compatible endpoint in headless/bench mode; per-session gauges (pty.open_fds_gauge, scrollback.stats) and counters (parser.truncations_total, clipboard.read_denied_total, and every *_total/*_ns metric named in §25/§26). Tracing: structured spans (ADR-16) per session, tagged with session id, phase, and invariant id where relevant; JSON output in production, pretty-printed in development. Structured logging: every log line carries a session id so a multi-tab host's logs can be filtered per terminal instance. Dashboards: one per phase-cluster — Parser Health (I1/I2 counters), Render Performance (M3/M4 timings), Security Posture (T1–T12 detection counters). Alerting philosophy: alert on rate-of-change for *_total security counters (a sudden spike in clipboard.read_denied_total may indicate an active exploitation attempt against many sessions at once), not on absolute thresholds for normal-operation counters. SLOs: 99.9% of frames within the M3/M4 p99 budget; zero P0 (FM-1, FM-3 fd-leak-class) incidents per quarter. Incident response: FM-table rows map directly to runbooks (docs/runbooks/{stuck-parser,render-flicker,pty-leak}.md). Named runbooks: stuck-parser.md (FM-1), render-flicker.md(FM-6/FM-11), pty-leak.md (FM-3). Backup/restore: N/A — sessions hold no persistent state in v1 (session serialization is deferred). Deployment topology: single binary per host platform, no server component. Canary/rolling-upgrade: the 30-day differential canary (§24) is the pre-release gate; there is no rolling-upgrade concept for a desktop-installed binary — new versions are a fresh install/update (Compatibility & Versioning covers the wire/behavioural guarantees across versions).

28. Compatibility & Versioning

Wire compatibility: the escape-sequence surface (ECMA-48 + the documented xterm/kitty extensions) is the "wire format"; this emulator commits to interpreting every documented sequence identically across minor versions — a behavioural change to an already-shipped sequence is a major-version change and an ADR. Storage compatibility: N/A in v1 (no persistent format); session serialization (Deferred Features Register) will introduce a versioned on-disk format when built. API stability: tem-core, tem-parser, and tem-grid's public traits (Performer, Pty) are SemVer-governed — adding a Performer method is a breaking (major) change; adding an enum variant to NamedKey is additive (minor) per §11. Schema evolution: the conformance-fixture YAML schema (ADR-15) is versioned; a fixture-format change ships a migration script in scripts/. Deprecation policy: a deprecated escape sequence handler stays functional for at least one major version with a tracing warning before removal. SemVer policy: the crate version follows the wire/API compatibility rules above, not calendar versioning. Rolling-upgrade guarantees: N/A (single-process desktop application, no fleet-rollout concept) — the closest analogue is that a mid-session binary replacement (e.g. package manager auto-update) must not corrupt an in-flight PTY session, guaranteed by the OS process model (the old binary's process keeps running until the user restarts it).

29. Testing & Verification Strategy

Unit: per-crate cargo test covering pure functions (width lookup, SGR parameter mapping, encoder output) — fast, no PTY required. Integration: hello-pty-style examples exercising real PTY + parser + performer + grid end to end. Property (proptest): random byte streams into the parser (I1/I2), random action sequences into the performer, random KeyEvents into the encoder — each tied to a specific invariant (§7). Differential: this emulator vs. xterm/Alacritty headless on the same byte stream, asserting grid-state equality modulo documented divergences (§8.5, FM-10). Fuzzing: cargo-fuzz/libFuzzer targets (§24.2), 5-minute CI budget per PR, unbounded budget in the 30-day canary. Chaos: deliberately racing resize against PTY read/write (T10) under a stress-test harness. Deterministic replay: tem-conformance replay re-runs a recorded byte-and-action trace and checks every invariant in §7 after each action — the single debugging tool referenced by name in six different phase sections (§12.10, §14.10, §15.10, §16.10, §18.10). Soak: the 10,000-PTY-spawn loop (I11), the 1,000,000-line scrollback push (I5), the 60-minute helix window-integration run (§21.5), the 30-day canary (§24). Fault injection: forced OOM on the glyph-atlas allocator to verify the eviction path degrades gracefully rather than panicking. Conformance: the 21-bucket suite (§24) is the release gate; fixtures are traceable to a specific phase's N.5. Performance- regression gating: every M-table row (§31) is asserted in CI via cargo bench (tem-bench); a regression beyond the documented p99 fails conformance.yml, not just a nightly report.

30. Build & Release Engineering

Reproducible builds: Cargo.lock committed (ADR-21); release builds use cargo vendor to pin the exact dependency source tree, avoiding any registry-availability drift between build and audit. Artifact signing: release binaries are signed (cosign or platform-native codesigning: Apple notarization on macOS, Authenticode on Windows) before publication via cargo-dist (ADR-20). SBOM: a CycloneDX SBOM is generated per release, enumerating every dependency and its license (cross-checked against ADR-14's vetted-crates policy). Release channels: stable (tagged releases only), nightly (main-branch builds, used by the 30-day canary infrastructure). CI/CD topology: GitHub Actions matrix (ADR-19) gates every PR on ci.yml + conformance.yml; release.yml runs only on a tag push and depends on both prior workflows passing (§12.9). Version stamping: the binary embeds its exact git commit hash and build timestamp, queryable via a --version flag, for incident forensics (cross-referenced in FM-table root-cause analysis). Provenance/attestation: build-provenance metadata (SLSA-style) is attached to each release artifact, recording the exact CI job and commit that produced it. Dependency auditing: cargo audit runs on every PR (security-advisory database check) and cargo vet runs on every dependency bump (ADR-14) — both are release-blocking, not advisory-only.

31. Performance Engineering

Methodology: tem-bench (criterion-based) benchmarks every M-row below on pinned reference hardware (16-core x86_64, AMD Ryzen 9 7950X-class; 32 GB DDR5; NVMe SSD; Linux 6.6; an RTX-4070-class GPU for the GPU rows) so numbers are reproducible via make bench and comparable release to release. Allocation analysis: dhat/heaptrack profiles confirm the parser and grid mutation paths perform zero heap allocation in the steady state (allocation happens only at glyph-cache miss and scrollback-line-push, both already budgeted). Lock contention: the single event-loop mutex (shared by resize/read serialization, §13/§15/§20 N.8) is profiled under the "resize storm" stress test to confirm it never becomes a bottleneck at the M5 scroll-latency budget. Cache locality: Screen::cells is a row-major Vec<Vec<Cell>> chosen for scroll-friendly row swaps over a single flat buffer's marginally better cache locality (a documented, accepted tradeoff). Syscall analysis: PTY read/write syscall counts are tracked per session to catch a regression that turns a batched write into a per-byte write storm. Tail-latency analysis: every M-row below reports p50 and the CI-gated p99, since a terminal's felt-responsiveness is a tail-latency property, not an average-case one.

32. Scalability Analysis

What stays constant: per-byte parse cost (O(1) transition-table lookup, §8.2); per-cell render cost given a warm glyph cache (O(1) texture sample). What grows: scrollback memory grows linearly with configured max_lines (bounded by design, P6) — not with wall-clock session duration beyond that cap; glyph-atlas memory grows with the distinct-glyph working set (bounded by eviction, §20). Named bottlenecks, in order: (1) single-core parse throughput (M1/M2) — the parser is intentionally single-threaded (P13); scaling beyond one core requires either parallel sessions (each with its own parser, already the model) or a redesign that shards a single stream, which is not attempted here because no observed workload saturates M2; (2) glyph-atlas texture size (4096×4096 per atlas, §20) — scaling beyond the working set of common fonts requires multiple atlases (already supported) or atlas eviction tuning; (3) FD budget (§4: 340-session ceiling) — the practical ceiling on how many terminal sessions one host process can multiplex. Horizontal scaling: N/A within one process — the natural unit is "one more OS process per additional terminal window," which the OS scheduler already load-balances across cores; there is no shared state to shard or replicate across windows (§1 scaling assumption). Vertical scaling: more cores let more independent sessions run in parallel (each pinned to its own core-affinity-free thread) but do not speed up any single session's parse throughput past M1/M2, since P13 forbids parallelizing one stream. Coordination overhead: zero cross-session coordination exists by design (§1); a multiplexer (tmux-equivalent) that needed cross-session coordination is explicitly out of scope and deferred. Practical ceiling: ~340 concurrent sessions per host process (FD-budget-derived, Back-of-Envelope Capacity Model) before the 1024-fd ulimit default is exhausted; the lever beyond that ceiling is raising the process's ulimit -n, not a code change.

33. Mental Models & First Principles

  1. MM1 — A terminal is a compiler for a byte stream into a 2D data structure. The parser is the front end (lexer+parser fused, §8.2), the performer is the code generator, the grid is the object code. Predicts: any "just regex the escape codes" design will hit the same overlapping-grammar wall a hand-rolled tokenizer hits on a real language. Bug class avoided: ambiguous-sequence misparses (ESC vs CSI vs 8-bit C1, §14.6). Applied in §8, §14.
  2. MM2 — State belongs to exactly one owner; everyone else is a read-only view. The performer owns grid state (I7); the renderer is a view (I6); the parser owns none. Predicts: any bug where "two things can both write X" traces back to a violation of this rule. Bug class avoided: torn writes, renderer-induced corruption. Applied in §7 (I6, I7), §15.
  3. MM3 — Dirty tracking trades a small constant cost per mutation for a large win at render time. Every mutation marks its cell(s) dirty (O(1) amortised); render only visits the dirty set. Predicts: a system without this either over-renders (wasted cycles) or under-renders (visible corruption) — there is no free third option. Bug class avoided: full-repaint-every-frame performance cliffs at scale. Applied in §7 (I3), §19, §20.
  4. MM4 — A resource budget converts an unbounded-input DoS into a bounded-degradation event. Every parser accumulator has a cap (ADR-11); exceeding it truncates, never crashes or hangs. Predicts: any "attacker controls the input, no cap exists" design is a live DoS/CVE waiting for a fuzzer to find it. Bug class avoided: the entire historical OSC/DCS-overflow CVE lineage. Applied in §8.4, §14, Threat Model T1/T2.
  5. MM5 — Two backing stores beat one store plus a flag whenever "restore" must be exact. A flag-conditioned code path accumulates subtle asymmetries between the "normal" and "flagged" cases over time; two independent stores cannot leak into each other by construction. Predicts: any single-store-plus-flag design will eventually corrupt the non-active state. Bug class avoided: alt-screen restore bugs (P5). Applied in §7 (I4), §15.
  6. MM6 — Logical order and visual order are different coordinate systems; conflating them breaks the moment either RTL or reflow enters the picture. The grid stores logical order always; BiDi and (eventually) reflow are view-time transforms with an explicit mapping cache. Predicts: any renderer that "just draws cells left to right" is only correct for LTR-only content. Bug class avoided: RTL cursor-placement and selection bugs. Applied in §22.
  7. MM7 — A protocol's "final byte determines meaning" design (CSI's dispatch-on-final- byte) trades ambiguity during accumulation for certainty at completion. Predicts: any premature interpretation of an in-progress CSI sequence (before the final byte arrives) is necessarily wrong for some parameter count. Bug class avoided: partial- sequence misdispatch. Applied in §8.2, §14.
  8. MM8 — Security in a byte-stream parser is a robustness property, not a policy property, until the very last mile (the clipboard). Parsing-robustness (bounded accumulators, no panics) closes most terminal CVEs structurally; only the OSC 52 clipboard-read case additionally needs a policy decision, because it crosses a trust boundary (arbitrary program output → the user's system clipboard). Predicts: a threat model that only reasons about "policy" and ignores parser robustness will miss T1/T2/ T9/T11/T12. Applied in §25.

35. Back-of-Envelope Capacity Model

  1. Scrollback memory ceiling = max_lines × cols × sizeof(Cell) = 10,000 × 132 × 32 B ≈ 42 MB (chained from §4's 128 MB steady-state ceiling — leaves ~86 MB for the glyph atlas and grid working set).
  2. Glyph atlas memory (one atlas) = 4096 × 4096 × 4 bytes (RGBA8) = 64 MB — a second atlas (worst case, heavy emoji/CJK working set) brings the renderer's own ceiling to 128 MB, which is why the §4 steady-state target assumes a single-atlas common case.
  3. Steady-state echo throughput at 60 Hz = cols × rows × refresh_hz = 132 × 60 × 60 = 475,200 cells/s; at ~1.2 bytes/cell average (mixed ASCII + occasional SGR) ≈ 570 KB/s required — three orders of magnitude below the M2 200 MB/s target, demonstrating the parser's throughput headroom for typing/echo workloads.
  4. PTY write-buffer drain = pipe_buffer_size ÷ paste_chunk_size = 64 KB ÷ 4 KB = 16 writes to drain one full kernel pipe buffer during a large paste (§21.2's chunking rationale, derived, not asserted).
  5. FD-budget session ceiling = ulimit_default ÷ fds_per_session = 1024 ÷ 3 ≈ 341 sessions (rounds to the §4/§32 "≤ 340" ceiling) before a host process exhausts its default file-descriptor budget.
  6. 30-day canary fuzzed-byte volume = seconds_per_day × days × sustained_rate = 86,400 × 30 × 10 MB/s ≈ 25.9 TB total bytes fuzzed through the differential target over one canary run — the scale needed to surface an accumulated-state bug like FM-10.
  7. GPU frame headroom = frame_budget − M4_p99 = 16.67 ms (60 Hz) − 2 ms = 14.67 ms left for host compositing/vsync/OS overhead per frame, derived directly from §4's frame-latency row.
  8. Conformance-suite wall time = bucket_count × avg_fixtures_per_bucket × avg_fixture_time = 21 × ~50 × 5 ms ≈ 5.25 s of pure fixture execution — the remainder of the M12 60 s budget is process-spawn overhead per differential fixture (reference-emulator startup dominates, not the fixture logic itself).
  9. Glyph cache working-set size (typical coding session) = distinct_fonts × distinct_sizes × distinct_attrs_combos × ~200 common codepoints ≈ 1 × 1 × 8 × 200 = 1,600 cache entries — small enough that even a conservative LRU cap (e.g. 8,192 entries) never thrashes under normal use (chained into §19.7's cache-sizing rationale).
  10. Max supported grid memory = 500 rows × 500 cols × 32 B ≈ 8 MB for the largest single-screen grid this system accepts (§4's 500×500 hard cap) — small relative to the scrollback ceiling, confirming grid size was never the memory driver.

37. Alternative Architectures (Roads Not Taken)

Alt-1 — Regex/line-based parser (no state machine).

byte stream ──▶ [line buffer] ──▶ [regex match against known sequences] ──▶ grid

Regime where it wins: a scripting-language terminal emulator whose users value readability of the parser source over correctness under malformed/adversarial input (quick prototyping, teaching tools). Real embodying system: pyte (the Python terminal emulator library). Rejected here because line-buffering cannot handle a control byte arriving mid-sequence without unbounded lookahead, and regex matching against overlapping sequence shapes (ESC vs CSI vs 8-bit C1) is provably ambiguous in exactly the cases §8.2's state machine resolves cleanly (MM1, MM7).

Alt-2 — Single grid with an alternate-screen flag.

┌─────────────┐   if (alt_flag) { apply-with-offset() }  else { apply-direct() }
│  One Grid   │◀──────────────────────────────────────────────────────────────
└─────────────┘

Regime where it wins: a minimal embedded serial-console emulator where alternate-screen mode is rarely or never exercised and memory is scarce enough that a second backing store is unaffordable. Real embodying system: many minimal embedded console emulators (e.g. BusyBox's microcom) that skip alt-screen entirely rather than implement it half-heartedly. Rejected here because the flag approach's restore-on-exit path is a well-documented bug class (MM5) the moment alt-screen is a first-class, frequently-used feature (vim, less, tmux — the majority of real-world terminal usage).

Alt-3 — Immediate-mode full repaint (no damage tracking).

every frame: for row in 0..rows { for col in 0..cols { draw(cell) } }   // no dirty check

Regime where it wins: a small, fixed, low-resolution grid (e.g. an IoT device's 16×2 character display, or an early low-bandwidth SSH client with a tiny window) where the total cell count is small enough that full repaint costs less than dirty-bitmap bookkeeping. Real embodying system: many early serial-terminal emulators and simple SSH-client "terminal views" that redraw the whole visible buffer per update. Rejected here because a 500×500-cell grid (§4's max) at 60 Hz makes full repaint the dominant cost (MM3), directly violating the M3/M4 latency budgets.

Alt-4 — A structured buffer API instead of a byte-stream escape protocol.

App ──▶ WriteCellAPI(row,col,attrs,glyph) ──▶ Console buffer (no parser needed at all)

Regime where it wins: a fully vendor-controlled, single-ecosystem stack where every program targeting the console is recompiled against the same API and cross-shell/Unix compatibility is not a goal. Real embodying system: the pre-ConPTY Windows Console API (direct WriteConsoleOutput buffer manipulation), which Microsoft itself moved away from via ConPTY specifically to gain Unix-shell compatibility (§5 Required Reading, ConPTY docs). Rejected here because this project's entire value proposition (§1, §2) is interoperating with the forty-year installed base of shells and TUIs that emit ECMA-48/xterm byte sequences — a structured API forecloses exactly that compatibility.

39. Glossary

  • Action — one of the eleven side effects the parser emits to the Performer (§8.2).
  • Alternate screen — the second backing store activated by CSI ?1049h, restored on ?1049l; carries no scrollback (P5, P6, I4).
  • APC — Application Program Command; an ECMA-48 sequence whose body is application-defined; used by the kitty graphics protocol (§23).
  • Atlas (glyph atlas) — a large GPU texture holding pre-rasterised glyphs, consumed by the GPU renderer (§20, ADR-07).
  • Bracketed paste — a mode wrapping pasted text in ESC[200~/ESC[201~ so an application can distinguish paste from typed input (§21, Threat Model T8).
  • C0 — the lower 32 ASCII control bytes (0x00–0x1F).
  • C1 — a parallel set of single-byte control codes (0x80–0x9F), rarely seen as raw bytes in modern 8-bit-clean-disabled practice (§14.6).
  • Cell — the typed value at a (row, col) grid position (§11).
  • ConPTY — Microsoft's pseudoconsole API on Windows 10+ (§13, ADR-12).
  • CSI — Control Sequence Introducer, the ESC [ prefix to the most common escape sequences (§8.1).
  • Damage tracking — the general term for dirty-region tracking that lets a renderer skip unchanged cells (I3, §19, §20).
  • DA1/DA2/DA3 — Device Attributes responses; the terminal identifies itself to the application (P10, §11).
  • DCS — Device Control String, the ESC P prefix to sequences whose body is consumed verbatim until ST (§8.1, §23 for sixel).
  • DEC — Digital Equipment Corporation, whose VT100/VT102/VT220 terminals standardised the modern terminal protocol (§5).
  • DECCKM — DEC Cursor Keys Mode; toggles whether cursor keys emit CSI A or SS3 A.
  • DECRQSS — DEC Request Status String; asks the terminal to report its state (Threat Model T5).
  • DECSLRM — DEC Set Left and Right Margins (§15.2).
  • DECSTBM — DEC Set Top and Bottom Margins (§15.2, §15.6).
  • Dirty bitmap — the per-row (or per-cell) tracking structure recording which cells changed since the last render (I3).
  • DSR — Device Status Report, a status query (Threat Model T5).
  • ECMA-48 — the standard documenting ANSI/ISO control functions underlying escape codes (§5).
  • ESC — the byte 0x1B, the prefix to most multi-byte sequences (§8.1).
  • G0/G1/G2/G3 — the four character-set slots designated via ISO 2022 SCS (§17.2).
  • Grapheme cluster — a UAX #29 user-perceived character, possibly multiple codepoints (I9, §17.2).
  • Grid — the two-screen, dirty-tracked data structure holding all visible and scrolled-back cell state (§11, §15).
  • Hyperlink — an OSC 8-attached URI associated with a range of cells via a HyperlinkId (I13, §23).
  • Kitty keyboard protocol — a modern, lossless keyboard encoding originated by the kitty terminal project (ADR-09, §21).
  • Ligature — a multi-codepoint glyph produced by OpenType shaping, e.g. == rendering as one glyph (§22).
  • modifyOtherKeys — an xterm keyboard-encoding extension disambiguating Ctrl-letter from the C0 control byte (§21.2).
  • OSC — Operating System Command, the ESC ] prefix to sequences terminated by BEL or ST (§8.1, §23).
  • Parser state machine — the Paul Williams DEC state machine implemented verbatim by tem-parser (P1, §8.2, §14).
  • Pending wrap — the cursor flag marking "at the right margin, the next print will wrap" (§11 Cursor, §15.6).
  • Performer — the trait/component consuming parser actions and mutating the grid (I7, §11).
  • PTY — Pseudo-TTY, a kernel-mediated pair of file descriptors mimicking a serial terminal (§13).
  • Ring buffer — the fixed-capacity FIFO structure backing scrollback (ADR-04, §18).
  • Scroll region — the row (and optionally column) range within which scroll operations apply (ScrollRegion, §11, §15).
  • Scrollback — lines that have scrolled off the top of the main screen, held in the ring buffer (P6, §18).
  • SGR — Select Graphic Rendition, the CSI Pm m sequence setting cell attributes (§16).
  • Sixel — a DEC bitmap image format encoding six vertical pixels per byte (§23).
  • SOS — Start of String, a rarely used ECMA-48 sequence (§8.2 SosPmApcString).
  • ST — String Terminator, ESC \ (§8.1).
  • Surrogate pair — a pair of UTF-16 code units jointly encoding one codepoint outside the BMP (relevant to host-side text APIs, not this system's internal UTF-8 model).
  • Synchronized output — DEC private mode 2026, buffering renderer updates between BSU/ESU to avoid multi-step-redraw flicker (§18.2, §20.2).
  • UAX #9 — the Unicode annex defining the Bidirectional Algorithm (§22).
  • UAX #11 — the Unicode annex defining East Asian Width (§17).
  • UAX #29 — the Unicode annex defining grapheme-cluster boundaries (§17).
