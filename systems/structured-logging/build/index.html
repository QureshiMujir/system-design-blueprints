⬜ Phase 0 — Skeleton & Correctness Kernel §12

Objectives

Stand up the repository skeleton (§10) and the smallest correctness kernel: a Logger that constructs, emits through an InMemoryExporter, and asserts the record round-trips unchanged. No sinks, no network, no buffer yet — the goal is a compiling workspace with the type spine (§11) in place.

Deliverable

A compiling workspace; meridian-cli log --level info "hello" emits one record captured by InMemoryExporter; make bootstrap && make test passes clean.

Acceptance
  • cargo test -p meridian-model passes with zero failures.
  • InMemoryExporter captures exactly 1 record for 1 logger.info("hello") call — named fixture conformance/corpora/json-lines/smoke.jsonl.
  • cargo-deny check and cargo-audit report zero advisories.
Fixtures
Fixture Purpose Expected Output
smoke.jsonl one-record round trip 1 captured LogRecord, fields match input exactly
severity_range.rs (unit) severity_number bounds rejects values outside 1..=24
Pitfalls
  • Shipping the macro system (Phase 2) before the data model is stable — resist; the schema (P1) must lock first or every downstream phase re-churns.
  • cargo-deny failing on an unpinned license — pin before first commit.
  • Treating InMemoryExporter as a toy — it is the permanent Phase-0/testing sink referenced by every later conformance fixture.

⬜ Phase 1 — Structured Event Model & Type System §13

Objectives

Complete meridian-model to the full OTel Logs Data Model shape (§8, §11) and implement JSON Lines serialization (ADR-03) with full round-trip fidelity, including every JSON edge case.

Deliverable

meridian-format::json_lines::{serialize, deserialize} round-trips every fixture in conformance/corpora/json-lines/ with zero data loss.

Acceptance
  • 100% pass rate on conformance/corpora/json-lines/ (≥ 20 fixtures including NaN, deeply-nested KvList, embedded newlines).
  • Serialization throughput ≥ 5,000,000 simple records/s/core (single-field body) — benchmark bench_serialise.rs.
  • schema_version present on 100% of serialized output (I13).
Fixtures
Fixture Purpose Expected Output
nan_double.jsonl NaN/Infinity float body serializes to JSON null, deserializes back to NaN sentinel
embedded_newline.jsonl multi-line stack-trace body one JSON line; \n escaped, not literal
deep_kvlist.jsonl 10-level nested KvList round-trips without truncation
malformed_utf8.jsonl invalid UTF-8 byte sequence quarantined (I14), not panicked
Pitfalls
  • A Value::Bytes field naively UTF-8-decoded corrupts binary payloads — base64-encode per §16's documented conversion.
  • Attribute insertion order matters for human debugging (dev mode) but must canonicalize in production to keep serialized output diff-stable (P13).
  • NaN handling is a common oversight — the fixture corpus (nan_double.jsonl) is the oracle, not ad hoc review.

⬜ Phase 2 — Non-Blocking Producer Front-End §14

Objectives

Build the allocation-bounded, panic-free producer hot path: the log! macro, the lock-free MPSC ring (I4), severity/attribute filters, and samplers — the safety boundary of the whole system (P2).

Deliverable

log!(level: Info, "user logged in", user: 42) executes end-to-end through the ring into InMemoryExporter; criterion benchmarks for both the disabled and enabled paths are wired into CI (perf.yml).

Acceptance
  • Disabled-call path: < 10 ns p99 (I1; benchmark bench_log_macro.rs::disabled).
  • Enabled-call path, 4 attributes: < 200 ns p99 (benchmark bench_log_macro.rs::enabled_4attr).
  • Zero heap allocations on the disabled path, verified via a counting allocator harness (tests/alloc_count.rs).
  • Fuzz target log_call_fuzz runs 10,000 panicking-format-arg inputs with zero producer panics (I2).
Fixtures
Fixture Purpose Expected Output
disabled_path.rs (bench) allocation-free disabled check 0 allocations recorded
panicking_format_arg.rs Display impl panics mid-format error record emitted, no propagated panic (I2)
ring_overflow.rs ring full under sustained load drop counter increments (I4), no block
smallvec_spill.rs > 16 attributes spills to heap correctly, still round-trips
Pitfalls
  • #[track_caller] captures the macro's own span unless combined with #[inline(never)] at the call site — document the workaround.
  • A format!()-built String body defeats allocation-boundedness — the lazy-format variant (log_lazy!) must defer formatting until ship time.
  • The SmallVec inline cap (16) is a tuned constant, not arbitrary — exceeding it under normal load is itself a signal worth alerting on (P8).

⬜ Phase 3 — Contextual Correlation (Trace/Span Propagation) §15

Objectives

Implement in-process context propagation (trace_id/span_id/request_id) and cross-process propagation via the shared W3C TraceContext (ADR-23), completing the injection stub left in Phase 2 (I11).

Deliverable

A trace_id set via Context::current().with("trace_id", ...) around an async block is auto-injected into every log! call inside that scope, including across an .await point.

Acceptance
  • 100% of log records emitted within an active trace scope carry the correct trace_id/span_id — fixture conformance/corpora/pipeline/trace_scope.rs.
  • Cross-process round-trip: an HTTP request carrying a W3C traceparent header produces a log record on the receiving service with the identical trace_id — fixture trace_http_roundtrip.rs.
  • Context propagation overhead: < 5 ns per log call (single task-local load).
Fixtures
Fixture Purpose Expected Output
trace_scope.rs nested async scopes inner scope's trace_id wins, restores on exit
trace_http_roundtrip.rs W3C header inject/extract identical trace_id both sides
thread_migration.rs task migrates OS threads async-local survives; thread-local would not
reserved_field_overwrite.rs transform rule targets trace_id rejected at pipeline construction (I11)
Pitfalls
  • A coroutine migrating across OS threads loses thread-local context — only the async-local survives; document this explicitly since it is a frequent source of "trace_id randomly missing" bugs.
  • A child logger created via with_attrs() snapshots the parent's context at creation time; later context mutations on the parent do not retroactively apply to the child.
  • Baggage propagation without a size cap allows unbounded HTTP header growth — cap baggage at a fixed byte budget.

⬜ Phase 4 — Wire Formats & Schema (JSON, OTel Logs, ECS) §16

Objectives

Complete the format surface beyond JSON Lines: OTLP Protobuf (ADR-04, ADR-14), Elastic Common Schema mapping, logfmt, and RFC 5424 syslog — all round-trip-tested against the canonical LogRecord.

Deliverable

All four formats (OTLP, ECS-JSON, syslog, logfmt) round-trip through conformance/corpora/ with zero field loss for every fixture, gated by conformance.yml.

Acceptance
  • 100% pass rate across otel-logs-data-model/, otlp-protocol/, syslog-5424/ corpora (≥ 15 fixtures each).
  • OTLP Protobuf serialization: ≥ 3,000,000 records/s/core (benchmark bench_serialise.rs::otlp).
  • Syslog structured-data escaping matches the RFC 5424 grammar for all 12 corpus fixtures, including the nested-quote edge case.
Fixtures
Fixture Purpose Expected Output
otlp_severity_mapping.rs OTel severity_number ↔ syslog severity correct bidirectional mapping
syslog_structured_data_escape.rs nested quotes in SD-PARAM correctly escaped/unescaped
ecs_field_mapping.rs LogRecord → ECS dotted paths exact ECS field names (§5)
logfmt_quoted_value.rs value containing a space double-quoted, \" escaped
Pitfalls
  • Syslog's structured-data escaping rules are subtle (], ", \ inside SD-PARAM values) — the fixture corpus is the oracle, not manual review, per Reference Implementations #2's Fluent Bit lesson on legacy-format fragility (§5).
  • OTLP's severity range (1–24) does not map 1:1 onto syslog's 8 severities — document the lossy direction explicitly (syslog → OTel is lossy; OTel → syslog picks the nearest bucket).
  • ECS field names use dots as path separators, which collide with JSON's flat-key convention if not handled via nested objects.

⬜ Phase 5 — Sinks & Multi-Sink Fan-Out §17

Objectives

Implement the sink trait (§11 LogExporter) and its concrete implementations: stdout/stderr, file with rotation+compression, syslog (UDP/TCP/TLS), OTLP (gRPC/HTTP) — establishing per-sink independent failure handling (P7, I6) ahead of the full retry/DLQ machinery in Phase 9.

Deliverable

Each of the 6 sink implementations ships a sustained 1,000 records/s stream in the local dev-compose topology (docker-compose.yml); killing one sink's backend (e.g. stopping the OTLP receiver) leaves the other 5 sinks unaffected.

Acceptance
  • JSON Lines path throughput: ≥ 100,000 records/s/core aggregate across sinks (§4 constraint table).
  • File rotation: zero record loss or duplication across 100 rotation cycles in the chaos fixture file_rotation_race.rs.
  • Sink isolation: stopping the OTLP receiver for 60 s produces zero measurable latency increase on the stdout/file sinks (I6; fixture sink_isolation_chaos.rs).
Fixtures
Fixture Purpose Expected Output
file_rotation_race.rs write during rotation boundary 0 lost/duplicated/split records
syslog_octet_counting.rs RFC 6587 TCP framing correct byte-count prefix, reassembly
otlp_grpc_backpressure.rs receiver returns RESOURCE_EXHAUSTED exporter backs off, does not crash
sink_isolation_chaos.rs one sink's backend killed other sinks' latency unaffected (I6)
Pitfalls
  • File rotation without advisory locking races with a second process writing the same path — document the lock discipline explicitly.
  • syslog UDP's ~1500-byte datagram ceiling silently truncates long records — document and counter it (feeds T2 in §24).
  • Re-establishing a TLS handshake on every OTLP batch is the canonical perf bug — the exporter must hold a persistent connection (contract, not an optimization).
  • Background compression of a rotated file leaves a brief window where the file is present but uncompressed — operator tooling must tolerate both states.

⬜ Phase 6 — Durable Disk Buffer & Crash Recovery §18

Objectives

Implement the WAL-backed durable buffer (ADR-06) that sits between the producer ring and the shipper, making at-least-once delivery (P4, I3) survive a producer-process crash without unbounded producer blocking.

Deliverable

A producer sustaining 1,000,000 records/s through ring → WAL → shipper, with a mid-run kill -9 on the producer process followed by restart replaying all WAL-acknowledged records with zero loss.

Acceptance
  • Sustained throughput: ≥ 1,000,000 records/s through the buffer (§4; benchmark bench_buffer_write.rs).
  • Crash recovery: zero record loss across 50 randomized kill-and-restart trials (fixture crash_recovery_fuzz.rs), duplicates permitted per I3/P4.
  • WAL segment rotation: zero corrupted segments across 200 rotation-under-load trials (fixture wal_rotation_race.rs, I10).
  • Disk usage tracks shipper lag within 10% of the theoretical unshipped-bytes calculation.
Fixtures
Fixture Purpose Expected Output
crash_recovery_fuzz.rs random kill during ring→WAL→ship 0 loss, duplicates allowed (I3)
wal_rotation_race.rs rotation under concurrent write load 0 corrupted/half-rotated segments (I10)
manifest_inconsistent.rs manifest missing/corrupt on restart recovered by scanning WAL directly
backpressure_modes.rs all 4 modes under sustained overload correct per-mode drop/block behavior
Pitfalls
  • fsync_each guarantees durability at a steep throughput cost — document the throughput/durability trade explicitly per record (ADR-06's rationale).
  • A shipper that lags far behind the producer keeps WAL segments alive, slowly filling disk — the docs/runbooks/buffer-full.md runbook must give the exact diagnostic query.
  • block back-pressure mode with a permanently-dead sink blocks the application indefinitely — restrict block mode's use to audit-log producers with a stable, monitored sink (P3 layered admission control; document the operational guardrail).
  • A half-written manifest after a crash mid-update must never be trusted blindly — always cross-check against a WAL directory scan (I10's atomicity guarantee is what makes this cross-check cheap).

⬜ Phase 7 — Aggregator Ingest §19

Objectives

Stand up meridian-aggregator as an independently-deployable binary (ADR-07: the policy engine lives here, not in producers) with concurrent multi-source ingest: OTLP, syslog, TCP JSON Lines, file-tail, Kafka, stdin.

Deliverable

The aggregator ingests OTLP, syslog, JSON Lines/TCP, and file-tail sources concurrently in the local dev-compose topology, each source independently rate-limited.

Acceptance
  • Aggregate ingest throughput: ≥ 100,000 records/s/core across sources combined (§4 constraint; benchmark bench_aggregator_ingest.rs).
  • File-tail correctly resumes from checkpoint across 100 simulated rotation events with zero duplicate or lost lines beyond Kafka's documented at-least-once semantics.
  • meridian_malformed_records_total{source} increments on every fixture in conformance/corpora/syslog-5424/malformed/ with zero ingest-loop crashes (I14).
Fixtures
Fixture Purpose Expected Output
file_tail_rotation.rs file rotated mid-tail resumes correctly via inode+checkpoint
kafka_rebalance.rs consumer group rebalances mid-batch partitions released/reacquired cleanly
syslog_malformed_batch.rs truncated/malformed datagrams quarantined per-record (I14), stream continues
inotify_watch_exhaustion.rs > 8192 watched files documented degradation, not a crash
Pitfalls
  • inotify's per-process watch-limit default (8192) is exhausted by a workload tailing many files — document the fs.inotify.max_user_watches operator knob explicitly (this is a real, common production surprise, not a hypothetical).
  • A Kafka rebalance mid-processing needs explicit partition-release handling or records can be double-processed beyond the documented at-least-once bound.
  • File-tail's inode-tracking must handle the "size shrunk without inode change" case (truncate-in-place logging), distinct from true rotation.

⬜ Phase 8 — Transform, Enrich & PII Redaction §20

Objectives

Implement the aggregator's policy stages: filter, enrich, transform, sample, and — the security-critical stage — redaction (P5, I5), fixed in pipeline order ahead of routing (§8).

Deliverable

A pipeline with filter+enrich+transform+redact+sample+route runs end-to-end against the conformance/corpora/redaction/ corpus with zero PII leakage and zero false-positive redactions on the corpus's benign-lookalike fixtures.

Acceptance
  • Pipeline throughput (pre-redaction stages): ≥ 100,000 records/s/core (§4; bench_pipeline.rs).
  • Redaction throughput: ≥ 50,000 records/s/core (§4; bench_redact.rs).
  • 100% of PII fixtures in conformance/corpora/redaction/pii/ redacted; 0% false-positive rate on conformance/corpora/redaction/benign_lookalikes/ (Luhn-gated credit-card fixtures included).
  • Pipeline-order conformance test asserts Redact always precedes Route (I5) across every configured pipeline topology.
Fixtures
Fixture Purpose Expected Output
pii_credit_card.rs Luhn-valid card number in body redacted [REDACTED:cc]
benign_16digit.rs Luhn-invalid 16-digit transaction ID not redacted (false-positive guard)
nested_stack_trace_pii.rs PII inside a multi-line stack trace redacted without breaking line delimiter
redaction_order.rs pipeline misconfigured with Route before Redact pipeline construction rejected (I5)
Pitfalls
  • A regex matching benign data silently corrupts logs — the fixture corpus, not manual regex review, is the oracle (per §5's Cox paper, correctness of regex behavior is provable, not eyeballed).
  • Redaction inside a multi-line body must not break the JSON Lines line-delimiter contract — the escape pass runs after redaction, never before.
  • A hash-based redaction (join-correlation use case) with a leaked salt enables dictionary-based un-hashing — the salt is per-tenant and treated as a secret (feeds T7, §24).
  • Rule ordering matters: a redaction rule re-matching a previous rule's [REDACTED:...] marker text is a documented ordering pitfall — later rules must skip already-redacted spans.

⬜ Phase 9 — Batching, Compression & Per-Sink Retry/DLQ §21

Objectives

Complete the export path: batching + compression to each sink, and independent per-sink retry with dead-letter-queue fallback (P6, P7, I6, I8, I12), making delivery reliable without cross-sink coupling.

Deliverable

A pipeline with a deliberately-unreachable OTLP sink continues delivering to stdout/file sinks at full throughput while OTLP batches accumulate in meridian_dlq/otlp/; the replay tool successfully redelivers 100% of DLQ'd batches once the sink recovers.

Acceptance
  • Batch delivery: zero partial/corrupted records across 10,000 batches under injected network failure (fixture batch_partial_fuzz.rs, I8).
  • DLQ replay: 100% of DLQ'd batches redeliver byte-for-byte identical to their original form (fixture dlq_replay_fidelity.rs, I12).
  • Sink isolation under failure: stopping one sink's backend produces 0% throughput degradation on the remaining sinks (I6; extends the Phase 5 chaos fixture with retry/DLQ engaged).
  • Compression ratio: ZSTD cold-storage batches achieve ≥ 4:1 on the reference corpus.
Fixtures
Fixture Purpose Expected Output
batch_partial_fuzz.rs network failure mid-batch-send 0 records split/corrupted (I8)
dlq_replay_fidelity.rs replay after extended outage byte-identical redelivery (I12)
retry_backoff_isolation.rs one sink backing off others unaffected (I6, I7)
compression_ratio_cold.rs ZSTD on cold-storage corpus ≥ 4:1 ratio
Pitfalls
  • Retry backoff state shared across sinks (instead of per-sink) reintroduces the coupling I6 exists to prevent — a common refactoring mistake to guard against explicitly.
  • A DLQ with no size cap can itself fill disk during an extended outage — cap DLQ size per sink and alert before the cap is reached (feeds FM entries in §25).
  • Replaying a DLQ out of original order breaks any downstream consumer relying on approximate time ordering — the replay tool preserves original batch order.

⬜ Phase 10 — Query Store & API §22

Objectives

Build the read side: a column-oriented store with per-attribute inverted indexes (ADR-09) and a field-predicate query API, matching the filter-by-attribute + scan-time-range access pattern (§5, Kleppmann ch. 3).

Deliverable

GET /api/v1/query?query=severity:ERROR service:checkout&start=...&end=... returns matching records streamed in time order within the p99 target; the token-index full-text search answers body:contains("timeout") correctly (suffix-array substring search remains PhaseDeferred("§22.3"), registered in §37).

Acceptance
  • Store write throughput: ≥ 100,000 records/s/node (§4; bench_store_write.rs).
  • Indexed query latency: p99 < 1 s for a single-hour, single-service, single-attribute-filter query (§4; bench_query.rs::indexed).
  • Full-text (token-index) query latency: p99 < 5 s (§4; bench_query.rs::fulltext).
  • Every query lacking a time:[...] predicate is rejected with a 400, never executed unbounded (fixture query_missing_time_range.rs).
Fixtures
Fixture Purpose Expected Output
query_missing_time_range.rs query with no time predicate 400 rejection, not full scan
chunk_compaction_hot_warm.rs hourly compaction warm chunk matches hot chunk's records exactly
inverted_index_lookup.rs attribute-filter query correct record set via postings
tail_slow_client.rs WebSocket tail with slow consumer drop-oldest at 1,000-record buffer cap, not OOM
Pitfalls
  • Sparse attribute columns produce many near-empty Arrow columns — per-column overhead compounds at scale; document the practical column-count ceiling.
  • Building the full suffix-array full-text index eagerly is expensive — correctly deferred to PhaseDeferred("§22.3"), not silently skipped.
  • A tenant query hitting cold (object-store) tier with no local cache is second-scale — document this trade rather than let it surprise an operator expecting hot-tier latency everywhere.

⬜ Phase 11 — Multi-Tenancy, Cardinality & Conformance/Perf/Soak §23

Objectives

Close the system with tenant isolation (ADR-11), the cardinality hard cap (ADR-12, I9), and the full conformance/performance/soak gate that certifies the whole pipeline production-ready.

Deliverable

Ten conformance buckets (otel-logs-data-model, otlp-protocol, json-lines, syslog-5424, logfmt, pipeline, redaction, query, cardinality, multi-tenant) each at 100% pass rate; a 30-day soak completes with zero crashes and zero invariant violations (I1–I14 all clean per the simulator's per-tick assertions).

Acceptance
  • Cardinality cap enforcement: 100% of fixtures in conformance/corpora/cardinality/ show the attribute dropped, record retained (I9).
  • Tenant isolation: tenant A sustaining 200,000 records/s produces 0% measurable latency increase on tenant B's queries (fixture tenant_noisy_neighbor.rs).
  • 30-day soak: zero crashes, zero meridian_producer_panics_total increments (I2), sustained 50,000 records/s (§4).
  • All ten conformance buckets: 100% pass rate, gated in conformance.yml.
Fixtures
Fixture Purpose Expected Output
cardinality_cap_enforced.rs attribute exceeds 100K distinct values attribute dropped, record ships (I9)
tenant_noisy_neighbor.rs tenant A floods ingest tenant B unaffected (ADR-11)
forged_tenant_header.rs spoofed X-Meridian-Tenant in prod mode rejected; auth-token required
soak_30day.rs sustained load, ASan+TSan 0 crashes, 0 invariant violations
Pitfalls
  • A cardinality cap set too low silently drops legitimate high-cardinality user data (e.g. per-request UUIDs used as an attribute) — the runbook (docs/runbooks/tenant-isolation.md) documents the diagnostic for distinguishing "attacker cardinality bomb" from "legitimately high-cardinality field."
  • Trusting bench numbers over the soak — the soak catches slow leaks (memory, FD, disk) that microbenchmarks structurally cannot see (§28's rationale).
  • A forgeable tenant header in any environment reachable by untrusted clients is a security defect, not a convenience feature — auth-token derivation is mandatory outside dev (T7, §24).
