Project Number: 134

Project Name: Structured Logging Pipeline

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Definition. A structured logging pipeline: an in-process, allocation-bounded producer front-end (library) that emits typed log events (level, timestamp, message body, key/value fields, trace/span correlation) through a lock-free ring buffer into a non-blocking pipeline — ingest → parse/enrich → transform/redact → buffer → sink — with explicit backpressure, at-least-once delivery, batching + compression to sinks, disk-buffering for crash-durability, schema conformance (JSON Lines, OpenTelemetry Logs Data Model, Elastic Common Schema), PII redaction, and multi-sink fan-out with per-sink retry/DLQ.

Phase-0 deliverable (numbered modules/crates):

  1. meridian-model — the typed event schema (LogRecord, Severity, Value, Resource, Scope).
  2. meridian-sdk — the producer front-end: macro, lock-free ring buffer, level filter, clock.
  3. meridian-format — JSON Lines serializer/deserializer (round-trip, malformed-input handling).
  4. meridian-sink — StdoutSink + InMemorySink (the two Phase-0 sinks).
  5. meridian-cli — a log/dump smoke-test binary.

System boundaries.

  • Provides: typed event capture, non-blocking producer, durable pipeline delivery, schema conformance, redaction, multi-sink fan-out with independent retry/DLQ.
  • Delegates: long-term cold storage and full-text search execution to an external store (Elasticsearch/OpenSearch/Loki equivalent) — §22 Query Store & API provides only the reference columnar implementation, not a claim to replace a mature search engine at scale.
  • Does NOT provide: distributed tracing span collection (that is a sibling system, referenced but not rebuilt here); metrics aggregation (same); a general-purpose stream-processing DSL beyond the fixed pipeline stages in §8.

Non-goals. Not a general ETL engine; not a time-series metrics store; not a log-based event-sourcing message bus (Kafka is used underneath one ingest source, never re-implemented).

Deployment model. The producer SDK links into the instrumented process (in-process, no sidecar required). The aggregator is a separate binary (meridian-aggregator), deployable as a per-host daemon or a per-cluster fan-in service, mirroring the Vector/Fluent Bit topology choice.

Target users/operators. Backend service teams (producer SDK integrators); platform/observability teams (aggregator operators, redaction-policy owners, retention/quota administrators).

What later phases unlock. Phase 0 unlocks a working typed-log smoke test. Phases 1–5 unlock a production-ready in-process SDK with durable delivery to real sinks. Phases 6–9 unlock the standalone aggregator with policy enforcement and reliable multi-sink fan-out. Phases 10–11 unlock queryability and multi-tenant safety at scale.

Recommended language + rationale. Rust. The producer's hot path executes inside the caller's request handler; a GC pause or allocator handshake there is a production incident (see M1, §30). Rust's ownership model gives allocation-bounded, panic-free hot-path code without a runtime GC. Rejected: Go (GC pause risk on the hot path, though smaller than Java's — still non-zero, see ADR-01's rejected alternatives); Java/JVM (GC pause + JIT warm-up unacceptable for an embedded library); C (memory safety risk in a library every service links, given the redaction/parsing attack surface in §24).

Prerequisites (systems knowledge required): lock-free ring buffers (SPSC/MPSC), write-ahead logging and crash recovery, backpressure and admission control, wire-format versioning, columnar storage and inverted indexes, regular-expression complexity (ReDoS), distributed-tracing context propagation.

Estimated timeline. Phase 0: 1 week. Full system (Phases 0–11): 24–27 weeks (~6 months).

Deferred features, each flagged and anchored (register in §37):

  • Suffix-array full-text index — PhaseDeferred("§22.3") — full substring search over log bodies.
  • SIMD JSON-escape fast path — PhaseDeferred("§30") — 5× serialization speedup on long bodies.
  • LogQL-compatible query front-end — PhaseDeferred("§22.3") — Loki-compatible query surface.
  • OSS-Fuzz continuous fuzzing onboarding — PhaseDeferred("§28") — beyond in-repo cargo-fuzz.

2. Why Build This

  • Unique systems knowledge: the interaction of a hot-path allocation budget with a durable, at-least-once delivery guarantee — most logging libraries pick one (fast producer, no durability) or the other (durable shipper, blocking producer); this system forces both simultaneously.
  • Why it matters architecturally: structured logging pipelines are the load-bearing observability primitive under every incident response; a pipeline that drops silently or blocks the request path during an outage turns an observability tool into an outage amplifier.
  • Historically: the evolution from printf-style logs → line-oriented text logs → structured JSON → OpenTelemetry's unified logs/traces/metrics data model tracks the industry's growing need to query, correlate, and automate over log data rather than grep it.
  • Engineering muscles built: lock-free concurrent data structures, write-ahead-log durability, backpressure/admission-control design, wire-format schema evolution, regex-DoS defense, columnar storage with inverted indexes.
  • Cross-links to sibling systems (by name): shares the W3C TraceContext propagator with the Distributed-Tracing project; shares the lock-free MPMC ring with the Lock-Free-Structures project; shares the async I/O runtime with the Async-Runtime project; shares the linear-time regex engine (ReDoS-safe) with the Regex-Engine project for the redaction pass.
  • Calibration value: this is the smallest system that still forces the producer-vs-durability tension, the redaction-vs-performance tension (§16.8, Luhn-validated PII scanning), and the cardinality-vs-storage tension (I9) that every real observability pipeline must resolve.

What Mastery Looks Like (5–8 bullets, each tied to a named phase):

  1. Explain why the disabled-log-call path must be sub-10-nanosecond and how the macro achieves it — Phase 2 (§14).
  2. Design a crash-safe WAL with bounded duplicate exposure and prove the recovery invariant — Phase 6 (§18).
  3. Defend a specific backpressure policy (drop-oldest vs block vs shed-to-disk) for a named workload (audit log vs high-volume debug log) — Phase 6 (§18) and Phase 9 (§21).
  4. Explain why redaction defaults to the aggregator, not the producer, and when that default is wrong — Phase 8 (§20).
  5. Derive the cardinality cap needed to keep a query-store node's memory under budget — Phase 11 (§23) and the Back-of-Envelope Capacity Model (§34).
  6. Explain why a column-oriented store with per-attribute inverted indexes beats a row store for this query pattern — Phase 10 (§22).
  7. Trace a single log record from log!() call through WAL, aggregator pipeline, redaction, and into a sink's DLQ on failure, naming every invariant it exercises — Phase 9 (§21).

Producer Front-End box. The safety boundary: a log call may never panic, block, or allocate on the disabled path (I1, I2). It is the concurrency boundary — the ring buffer is the only structure multiple producer threads/tasks touch concurrently.

Local Disk Buffer / WAL box. The persistence boundary and the crash-durability boundary: the only state that survives a producer-process crash. Acknowledgement to the caller (in block back-pressure mode) happens only after the configured fsync policy commits (I3).

Aggregator box. The policy engine and the trust boundary: raw producer-shipped records are untrusted here — this is where redaction (I5), sampling, rate-limiting, and routing are enforced, because the aggregator is centrally deployable and independently upgradable (ADR-07).

Sinks + DLQ box. The external-interface boundary and the failure-isolation boundary: one sink's outage never blocks another (I6); a sink's undeliverable batch lands in its own DLQ, replayable byte-for-byte (I12).

Query Store / API box. The read-side persistence and protocol boundary: columnar storage tuned for the filter-by-attribute + scan-time-range query pattern (ADR-09), exposed over the Query API's field-predicate protocol (§22).

Crate prefix meridian-* is normative; used identically in §10 and Appendix A.

6. Design Principles

  • P1 — Typed event is the atom. Every emitted record has a schema: level, timestamp, body, attributes, resource, scope. A bare string is never the unit of record. Violate it → downstream consumers regex-parse free text, reintroducing the exact fragility structured logging exists to remove.
  • P2 — The producer never blocks the caller on I/O. Worst case under load is a counted, observable drop; never a panic, never an unbounded pause. Violate it → the logger becomes an outage amplifier during the exact incident it should be illuminating.
  • P3 — Backpressure is explicit and layered. Ring buffer → disk buffer → sink, each with its own admission policy (I4, I9, I6). Violate it → a single congested layer silently propagates pressure to the application thread.
  • P4 — At-least-once, never silent loss. An acknowledged record survives a producer crash; duplicates are permitted, silent loss is not (I3). Violate it → the pipeline can no longer be trusted for audit/compliance use cases.
  • P5 — Redaction defaults to the aggregator; producer-side is opt-in fail-safe. Violate it by redacting only at the producer → a misconfigured producer ships PII with nothing downstream to catch it; by redacting only at the aggregator → PII crosses the process boundary in transit (mitigated by transport TLS, ADR-05).
  • P6 — A batch boundary is never a correctness boundary. Batching/compression amortize I/O; a partially-delivered batch does not corrupt or duplicate a whole record (I8). Violate it → a single slow sink can corrupt every other record in its batch.
  • P7 — Sinks fail independently. One sink's outage never blocks or drops for any other sink (I6). Violate it → a single misconfigured TLS cert takes down stdout logging too.
  • P8 — Filter/sample as early (cheaply) as possible. The producer drops what it can prove unwanted before the aggregator spends CPU on it. Violate it → the aggregator pays redaction/parse cost for records nobody will ever read.
  • P9 — Clocks are explicit and abstracted (a Clock trait). Tests use a fixed clock; production uses monotonic-plus-wall. Violate it → tests become flaky/non-deterministic and timestamp bugs hide until DST or leap-second events.
  • P10 — Cardinality is bounded by design, not by hope. Every indexed dimension has a hard, enforced cap (I9). Violate it → a single high-cardinality attribute OOMs a query-store node (the Elasticsearch mapping-explosion failure mode).
  • P11 — Every module is independently testable via conformance fixtures. Not integration-only. Violate it → a regression in one format (e.g. syslog) is caught only by an end-to-end test months later.
  • P12 — No global mutable state. A Logger/Pipeline is a value; multiple instances coexist (P12 in §11's Logger type). Violate it → tests interfere with each other via shared statics and library embedding becomes unsafe.
  • P13 — Wire formats are versioned and round-trip-tested. Schema evolution never silently drops a field (I13). Violate it → a producer upgrade silently breaks every downstream consumer.
  • P14 — The pipeline observes itself. It emits its own health telemetry (meridian_records_dropped_total etc.) so a broken logger is itself detectable, not a silent single point of blindness. Violate it → the observability system's own failure is the one failure nobody is watching for.

Debugging methodology. A deterministic simulator (conformance/runner.rs) drives a fixed seed of synthetic records (normal, malformed, oversize, duplicate, out-of-order) through the full pipeline in a single-threaded, fixed-clock harness; one assertion per invariant (I1–I14) runs after each simulated tick, so a regression in any invariant fails a single, localized test rather than an end-to-end flake.

8. Domain Model

Structured event schema (full signatures in §11): a LogRecord carries timestamp_unix_nano, observed_timestamp_unix_nano, severity_number (1–24 per the OpenTelemetry Logs Data Model, mapped 1:1 from Severity), severity_text, body: Value, attributes: Vec<(String, Value)>, resource, scope, optional trace_id/span_id/trace_flags, dropped_attributes_count, and schema_version (I13). Value is the OTel-shaped tagged union: Bool | Int | Double | String | Bytes | Array | KvList.

Pipeline stage sequence (the fixed order every record passes through; ADR-07, I5):

ingest → parse → enrich → transform → sample/rate-limit → redact → route → batch+compress → sink(N)
   │        │        │         │             │              │        │          │            │
 (§19)    (§19)    (§20)     (§20)          (§20)          (§20)    (§20)      (§21)        (§17)

Redaction is fixed between sample/rate-limit and route (I5) — a record is never routed to an external sink before redaction runs.

State table — pipeline stage effect on record shape:

Stage Input Output May Drop Record? May Drop Attribute?

Worked example. Producer emits log!(Info, "user logged in", user_id: 42, source: "google") inside an HTTP handler with an active trace context (trace_id=abcd..., span_id=1234...). The macro (§14) builds a LogRecord on the stack, injects trace_id/span_id from the current Context (§15), pushes onto the ring buffer. The batch processor drains, WAL-appends (fsync per policy, §18), and the shipper ships to the aggregator via OTLP. The aggregator's enrich stage adds cluster=prod-us-east-1; redact finds no PII; route sends it to both the stdout sink and the store sink; both sinks batch+compress independently. The query API later answers trace_id:abcd... by joining the store's trace_id column.

Malformed-input example. A syslog UDP datagram truncated mid-STRUCTURED-DATA field (exceeding the 1500-byte datagram ceiling, §17.9) fails RFC 5424 parse. Per I14, the ingest stage tags it quarantine_reason=syslog_parse_error, writes the raw bytes to the quarantine sink (never the main pipeline), increments meridian_malformed_records_total{source=syslog}, and continues consuming the next datagram — the malformed record never reaches parse/enrich/redact.

Failure-path example. The OTLP/gRPC sink's endpoint is unreachable for 40 minutes during a network partition. Per I6, the stdout and file sinks continue delivering unaffected. The OTLP sink's per-sink retry (§21) exhausts its backoff budget (5 attempts, exponential, cap 30 s) and writes the batch to meridian_dlq/otlp/. meridian_dlq_depth{sink=otlp} climbs and pages the on-call operator per the shipper-stuck runbook (§26). When the network recovers, the operator (or the DLQ auto-drain, Phase 9) replays the DLQ byte-for-byte (I12) in original order.

14. Phase 2 — Non-Blocking Producer Front-End

14.1 Objectives

Build the allocation-bounded, panic-free producer hot path: the log! macro, the lock-free MPSC ring (I4), severity/attribute filters, and samplers — the safety boundary of the whole system (P2).

14.2 Detailed Implementation Steps

Implement the Vyukov-style bounded MPSC ring (ring.rs) per Vyukov's bounded-queue design (§5, Reference Implementations #1's queue pattern) — cache-line-padded head/tail indices. Implement the log! macro (macros.rs): (1) atomic is_enabled check (I1); (2) if enabled, stack-allocate the LogRecord via a SmallVec-backed attribute list (inline cap 16, P2); (3) inject contextual fields via Context::current() (stub until Phase 3 lands the real propagator, I11); (4) push onto the ring. Wrap format-argument evaluation in catch_unwind (I2) so a panicking Display impl degrades to an error record instead of crashing the caller. Implement SeverityFilter/AttributeFilter (P8: filter as early as possible) and RatioSampler/RateLimitSampler.

14.3 Deliverable

log!(level: Info, "user logged in", user: 42) executes end-to-end through the ring into InMemoryExporter; criterion benchmarks for both the disabled and enabled paths are wired into CI (perf.yml).

14.4 Acceptance Criteria

  • Disabled-call path: < 10 ns p99 (I1; benchmark bench_log_macro.rs::disabled).
  • Enabled-call path, 4 attributes: < 200 ns p99 (benchmark bench_log_macro.rs::enabled_4attr).
  • Zero heap allocations on the disabled path, verified via a counting allocator harness (tests/alloc_count.rs).
  • Fuzz target log_call_fuzz runs 10,000 panicking-format-arg inputs with zero producer panics (I2).

14.5 Conformance Fixtures

Fixture Purpose Expected Output

14.6 Pitfalls

  • #[track_caller] captures the macro's own span unless combined with #[inline(never)] at the call site — document the workaround.
  • A format!()-built String body defeats allocation-boundedness — the lazy-format variant (log_lazy!) must defer formatting until ship time.
  • The SmallVec inline cap (16) is a tuned constant, not arbitrary — exceeding it under normal load is itself a signal worth alerting on (P8).

14.7 Performance Concerns

Cache-line padding on the ring's head/tail indices (Mogul & Ramakrishnan's livelock paper, §5, informs the admission-control reasoning) prevents false sharing between producer and drain threads. The is_enabled check is a single atomic load, not a lock (I1). Format-argument evaluation is the dominant cost on the enabled path when it allocates — the lazy variant exists precisely to defer this.

14.8 Edge Cases

  • A producer thread panicking inside its own log call (not the format arg, but application logic around it) is out of scope — I2 only covers panics originating from the logging call itself.
  • Ring full + samplers active simultaneously: sampling drops are counted separately from ring-overflow drops (distinct metrics, P14).
  • A record with zero attributes must still round-trip through the ring without a null-pointer or zero-length special case.

14.9 Failure Analysis

A ring-buffer bug (torn read/write) is the highest-severity Phase-2 failure — it can corrupt an unrelated record. Detection: miri (ADR-21) catches undefined behavior in CI; the fuzz target exercises concurrent push/drain interleavings. Containment: the ring is the sole shared-mutable structure in the producer (§3 concurrency boundary) — a bug here cannot spread beyond one process. Recovery: revert; the allocation-count and miri gates block merge.

14.10 Operational Notes

New metrics: meridian_records_dropped_total{reason=ring_full|sampled|rate_limited}, meridian_bench_disabled_ns (CI-gated, I1). No deployment change; still in-process.

  • A coroutine migrating across OS threads loses thread-local context — only the async-local survives; document this explicitly since it is a frequent source of "trace_id randomly missing" bugs.
  • A child logger created via with_attrs() snapshots the parent's context at creation time; later context mutations on the parent do not retroactively apply to the child.
  • Baggage propagation without a size cap allows unbounded HTTP header growth — cap baggage at a fixed byte budget.

15.7 Performance Concerns

Task-local/thread-local reads are single-load operations (~2 ns) — negligible against the < 200 ns enabled-path budget (§4, M-table row for producer latency). Baggage injection is bounded by its size cap to avoid unbounded per-call cost.

15.8 Edge Cases

  • No active context (a background job with no trace scope): fields are simply absent, not zero-valued placeholders.
  • A malformed traceparent header (wrong version, bad hex): extraction fails closed — no trace_id injected, not a corrupted one.
  • Baggage exceeding its size cap: oldest entries evicted, counted.

15.9 Failure Analysis

A propagation bug silently breaks trace/log correlation — the failure is invisible until an incident needs the join. Detection: the trace_http_roundtrip.rs fixture running in CI on every change to meridian-ctx. Containment: correlation failure never affects delivery (I3/I4 independent of I11). Recovery: none needed at runtime — this is a correctness bug caught pre-release, not a live incident class.

15.10 Operational Notes

No new metrics beyond meridian_context_missing_total (records emitted with no active trace scope, for operator visibility into instrumentation coverage). Runbook docs/runbooks/tenant-isolation.md is unaffected here; correlation runbooks land with the query layer (Phase 10).

  • File rotation without advisory locking races with a second process writing the same path — document the lock discipline explicitly.

Recovery: automatic reconnect with backoff; manual intervention only if the backend is permanently gone (see docs/runbooks/shipper-stuck.md, §26).

Rollback: a sink misconfiguration is hot-reloadable without producer restart (config watch, feeds §27).

18. Phase 6 — Durable Disk Buffer & Crash Recovery

18.1 Objectives

Implement the WAL-backed durable buffer (ADR-06) that sits between the producer ring and the shipper, making at-least-once delivery (P4, I3) survive a producer-process crash without unbounded producer blocking.

18.2 Detailed Implementation Steps

Implement the in-memory bounded ring (meridian-buffer::ring, the Vyukov-style structure reused from Phase 2's design, ADR-13). Implement the WAL writer (wal/writer.rs): a background task drains the ring in batches and appends to the current 64 MiB segment (§4 constraint), applying the configured fsync policy (fsync_each | fsync_batch default 100 ms | fsync_none) — this is the mechanism that satisfies I3 without violating P2 (the producer's synchronous path never fsyncs). Implement segment rotation (checkpoint.rs) as an atomic operation (I10): open new segment, fsync-close old, update the manifest in one atomic rename. Implement the shipper's WAL reader (wal/reader.rs) which resumes from the manifest's last_shipped_offset on restart, replaying since the last checkpoint (I3). Implement the four back-pressure modes (drop_oldest default, drop_newest, block, shed_to_disk) per P3's layered admission-control design, informed by Mogul & Ramakrishnan's livelock-avoidance reasoning (§5).

18.3 Deliverable

A producer sustaining 1,000,000 records/s through ring → WAL → shipper, with a mid-run kill -9 on the producer process followed by restart replaying all WAL-acknowledged records with zero loss.

18.4 Acceptance Criteria

  • Sustained throughput: ≥ 1,000,000 records/s through the buffer (§4; benchmark bench_buffer_write.rs).
  • Crash recovery: zero record loss across 50 randomized kill-and-restart trials (fixture crash_recovery_fuzz.rs), duplicates permitted per I3/P4.
  • WAL segment rotation: zero corrupted segments across 200 rotation-under-load trials (fixture wal_rotation_race.rs, I10).
  • Disk usage tracks shipper lag within 10% of the theoretical unshipped-bytes calculation.

18.5 Conformance Fixtures

Fixture Purpose Expected Output
crash_recovery_fuzz.rs random kill during ring→WAL→ship 0 loss, duplicates allowed (I3)
wal_rotation_race.rs rotation under concurrent write load 0 corrupted/half-rotated segments (I10)
manifest_inconsistent.rs manifest missing/corrupt on restart recovered by scanning WAL directly
backpressure_modes.rs all 4 modes under sustained overload correct per-mode drop/block behavior

18.6 Pitfalls

  • fsync_each guarantees durability at a steep throughput cost — document the throughput/durability trade explicitly per record (ADR-06's rationale).
  • A shipper that lags far behind the producer keeps WAL segments alive, slowly filling disk — the docs/runbooks/buffer-full.md runbook must give the exact diagnostic query.
  • block back-pressure mode with a permanently-dead sink blocks the application indefinitely — restrict block mode's use to audit-log producers with a stable, monitored sink (P3 layered admission control; document the operational guardrail).
  • A half-written manifest after a crash mid-update must never be trusted blindly — always cross-check against a WAL directory scan (I10's atomicity guarantee is what makes this cross-check cheap).

18.7 Performance Concerns

The two-stage design (ring → WAL → shipper) decouples producer-observed latency from network latency — the producer's "acknowledged" return happens after the WAL fsync, not after network delivery (Kreps's "the log" framing, §5, applies directly: the WAL is the durability spine, the network ship is a downstream consumer of it). fsync_batch (default, 100 ms) is the throughput/durability median; tune via the constraint table (§4) per workload.

18.8 Edge Cases

  • Disk fills while the WAL is mid-append: the write fails, triggering the configured back-pressure mode (not a silent truncation of the segment).
  • A crash during segment rotation exactly between "new segment opened" and "manifest updated": recovery scans for orphan segments and reconciles (I10).
  • A shipper crash (not the producer) mid-batch: the batch is re-read from the last committed last_shipped_offset, producing bounded duplicates (P4), never gaps.

18.9 Failure Analysis

The WAL is the single most safety-critical component in the system — a bug here breaks P4/I3 system-wide. Detection: the crash-recovery fuzz harness runs on every change to meridian-buffer (CI-gated). Blast radius: contained to one producer's buffer (no cross-producer WAL sharing). Containment: the manifest's atomic-rename discipline (I10) bounds inconsistency to "scan and reconcile," never silent corruption. Recovery: automatic on restart (WAL replay); the runbook documents the manual disk-pressure escalation path.

18.10 Operational Notes

Metrics: meridian_wal_replay_records (on restart), meridian_wal_segment_count, meridian_wal_disk_bytes, meridian_records_dropped_total{reason=backpressure_mode}. Deployment: buffer directory is a persistent volume in containerized deployments (Dockerfile documents the mount point). Migration: a WAL format version bump (I13) requires draining the old-format WAL before upgrade — documented in §27.

  • Redaction throughput: ≥ 50,000 records/s/core (§4; bench_redact.rs).

  • A regex matching benign data silently corrupts logs — the fixture corpus, not manual regex review, is the oracle (per §5's Cox paper, correctness of regex behavior is provable, not eyeballed).

21. Phase 9 — Batching, Compression & Per-Sink Retry/DLQ

21.1 Objectives

Complete the export path: batching + compression to each sink, and independent per-sink retry with dead-letter-queue fallback (P6, P7, I6, I8, I12), making delivery reliable without cross-sink coupling.

21.2 Detailed Implementation Steps

Implement the batch writer (exporter/store.rs and per-sink exporters) enforcing I8 (a batch flush is atomic per record — no record is split across a batch boundary) via a length-prefixed framing within each batch. Apply Snappy compression cross-process (ADR-15) and ZSTD for cold-storage-bound batches (ADR-16). Implement per-sink retry (exporter/dlq.rs): exponential backoff (base 100 ms, cap 30 s, 5 attempts default) per P7's sink-independence principle — each sink's retry state is isolated, so a stalled OTLP sink's backoff timer never throttles the stdout sink. On retry exhaustion, write the whole batch to that sink's DLQ (I12: byte-for-byte replayable), tagged with sink_id, first-failure timestamp, and attempt count (§11 DlqEntry). Implement the DLQ replay tool (meridian-cli dlq replay --sink=...).

21.3 Deliverable

A pipeline with a deliberately-unreachable OTLP sink continues delivering to stdout/file sinks at full throughput while OTLP batches accumulate in meridian_dlq/otlp/; the replay tool successfully redelivers 100% of DLQ'd batches once the sink recovers.

21.4 Acceptance Criteria

  • Batch delivery: zero partial/corrupted records across 10,000 batches under injected network failure (fixture batch_partial_fuzz.rs, I8).
  • DLQ replay: 100% of DLQ'd batches redeliver byte-for-byte identical to their original form (fixture dlq_replay_fidelity.rs, I12).
  • Sink isolation under failure: stopping one sink's backend produces 0% throughput degradation on the remaining sinks (I6; extends the Phase 5 chaos fixture with retry/DLQ engaged).
  • Compression ratio: ZSTD cold-storage batches achieve ≥ 4:1 on the reference corpus.

21.5 Conformance Fixtures

Fixture Purpose Expected Output
batch_partial_fuzz.rs network failure mid-batch-send 0 records split/corrupted (I8)
dlq_replay_fidelity.rs replay after extended outage byte-identical redelivery (I12)
retry_backoff_isolation.rs one sink backing off others unaffected (I6, I7)
compression_ratio_cold.rs ZSTD on cold-storage corpus ≥ 4:1 ratio

21.6 Pitfalls

  • Retry backoff state shared across sinks (instead of per-sink) reintroduces the coupling I6 exists to prevent — a common refactoring mistake to guard against explicitly.
  • A DLQ with no size cap can itself fill disk during an extended outage — cap DLQ size per sink and alert before the cap is reached (feeds FM entries in §25).
  • Replaying a DLQ out of original order breaks any downstream consumer relying on approximate time ordering — the replay tool preserves original batch order.

21.7 Performance Concerns

Batching amortizes per-record I/O and compression overhead; the batch-size/batch-timeout dial (shared shape with the buffer's watermark-driven flush, Phase 6) trades latency for throughput. Snappy's low CPU cost suits the network-hop compression role; ZSTD's better ratio suits the write-once, read-rarely cold storage role — two different compression algorithms for two different access patterns, not one one-size-fits-all choice.

21.8 Edge Cases

  • A batch that is retried and then the sink recovers mid-retry: the in-flight retry must not race with a fresh delivery of the same batch (idempotency key per batch, consumed at the sink where supported).
  • DLQ replay racing with new live traffic to the same sink: replay is rate-limited so it does not starve live delivery.
  • A sink that partially acknowledges a batch (some records accepted, some rejected): treated as a full batch failure for retry purposes — no partial-batch bookkeeping (keeps I8 simple).

21.9 Failure Analysis

An extended sink outage is the expected, designed-for failure mode here — not an incident by itself; the incident trigger is DLQ depth crossing an alert threshold (approaching disk-cap). Detection: meridian_dlq_depth{sink} gauge. Containment: per-sink isolation (I6) bounds the blast radius to that one sink. Recovery: automatic reconnect + DLQ auto-drain (background task attempts periodic redelivery) or operator-triggered replay via the CLI tool.

21.10 Operational Notes

Metrics: meridian_dlq_depth{sink}, meridian_batch_export_latency_seconds{sink}, meridian_batch_compression_ratio{sink}. Runbook: docs/runbooks/shipper-stuck.md documents the DLQ depth escalation procedure. Rollback: a sink's retry/backoff parameters are hot-reloadable.

GET /api/v1/query?query=severity:ERROR service:checkout&start=...&end=... returns matching records streamed in time order within the p99 target; the token-index full-text search answers body:contains("timeout") correctly (suffix-array substring search remains PhaseDeferred("§22.3"), registered in §37).

22.4 Acceptance Criteria

  • Store write throughput: ≥ 100,000 records/s/node (§4; bench_store_write.rs).
  • Indexed query latency: p99 < 1 s for a single-hour, single-service, single-attribute-filter query (§4; bench_query.rs::indexed).
  • Full-text (token-index) query latency: p99 < 5 s (§4; bench_query.rs::fulltext).
  • Every query lacking a time:[...] predicate is rejected with a 400, never executed unbounded (fixture query_missing_time_range.rs).

22.6 Pitfalls

  • Sparse attribute columns produce many near-empty Arrow columns — per-column overhead compounds at scale; document the practical column-count ceiling.
  • Building the full suffix-array full-text index eagerly is expensive — correctly deferred to PhaseDeferred("§22.3"), not silently skipped.
  • A tenant query hitting cold (object-store) tier with no local cache is second-scale — document this trade rather than let it surprise an operator expecting hot-tier latency everywhere.

22.7 Performance Concerns

Query execution parallelizes across hot/warm/cold tiers, merging by timestamp; the hot tier's in-memory residency is what makes the p99 < 1 s target achievable — a query hitting only cold tier is explicitly out of that latency budget (documented, not silently violated).

22.8 Edge Cases

  • A tail query (/api/v1/tail) whose client stalls: server-side buffer caps at 1,000 records (tail_buffer_size default), then drop_oldest, per Edge Case handling shared with I4's ring-overflow policy shape.
  • An aggregation query with unbounded-cardinality group_by: result-size cap enforced, not an unbounded response.
  • A regex predicate (body:regex(...)) without anchors is effectively unbounded cost — the linear-time regex engine (ADR-25) bounds worst-case cost per byte scanned, but the operator-facing runbook still documents the latency implication.

22.9 Failure Analysis

A query-store bug (e.g. an index corruption) risks returning incomplete or wrong results silently — the worst failure mode for an incident-response tool. Detection: chunk_compaction_hot_warm.rs's exact-match assertion across the hot→warm transition, run on every storage-layer change. Containment: per-tenant storage isolation (ADR-11) bounds a corruption to one tenant's chunks. Recovery: chunks are append-only/immutable once sealed — recovery is re-derivation from the WAL-backed upstream data, not in-place repair.

22.10 Operational Notes

Metrics: meridian_store_write_latency_seconds, meridian_query_latency_seconds{tier}, meridian_chunk_compaction_duration_seconds. Runbook: docs/runbooks/slow-query.md. Deployment: the store's object-store backend (S3/GCS/Azure/local FS) is operator-configured per §10's object_store/ trait implementations.

23. Phase 11 — Multi-Tenancy, Cardinality & Conformance/Perf/Soak

23.1 Objectives

Close the system with tenant isolation (ADR-11), the cardinality hard cap (ADR-12, I9), and the full conformance/performance/soak gate that certifies the whole pipeline production-ready.

23.2 Detailed Implementation Steps

Implement meridian-tenant (tenant scoping via X-Meridian-Tenant header in dev, auth-token-derived in production — a forgeable header is explicitly a dev-only trust model, T7 in §24) and per-tenant quotas (ingest rate, storage size, retention days, query rate/concurrency). Implement meridian-cardinality's per-tenant per-attribute cap (default 100,000 distinct values, §4): exceeding the cap drops the new attribute value, never the record (I9) — enforced at the ingest cardinality gate, the same architectural position as the Elasticsearch mapping-explosion failure this design defends against (Reference Implementations #5, §5). Wire the full conformance suite (conformance/runner.rs's deterministic simulator, §7) plus the perf budget gate (§30's M-table) plus a 30-day soak at 50,000 records/s sustained with ASan+TSan enabled on the test suite (ADR-21).

23.3 Deliverable

Ten conformance buckets (otel-logs-data-model, otlp-protocol, json-lines, syslog-5424, logfmt, pipeline, redaction, query, cardinality, multi-tenant) each at 100% pass rate; a 30-day soak completes with zero crashes and zero invariant violations (I1–I14 all clean per the simulator's per-tick assertions).

23.4 Acceptance Criteria

  • Cardinality cap enforcement: 100% of fixtures in conformance/corpora/cardinality/ show the attribute dropped, record retained (I9).
  • Tenant isolation: tenant A sustaining 200,000 records/s produces 0% measurable latency increase on tenant B's queries (fixture tenant_noisy_neighbor.rs).
  • 30-day soak: zero crashes, zero meridian_producer_panics_total increments (I2), sustained 50,000 records/s (§4).
  • All ten conformance buckets: 100% pass rate, gated in conformance.yml.

23.6 Pitfalls

  • A cardinality cap set too low silently drops legitimate high-cardinality user data (e.g. per-request UUIDs used as an attribute) — the runbook (docs/runbooks/tenant-isolation.md) documents the diagnostic for distinguishing "attacker cardinality bomb" from "legitimately high-cardinality field."
  • Trusting bench numbers over the soak — the soak catches slow leaks (memory, FD, disk) that microbenchmarks structurally cannot see (§28's rationale).
  • A forgeable tenant header in any environment reachable by untrusted clients is a security defect, not a convenience feature — auth-token derivation is mandatory outside dev (T7, §24).

23.7 Performance Concerns

The cardinality gate's cost is a hash-set lookup per attribute value per tenant — bounded and cheap relative to redaction's regex cost (§20), so it is placed early in ingest (P8: cheap checks first).

23.8 Edge Cases

  • A tenant's quota exactly at the cardinality cap boundary (100,000th distinct value): the boundary behavior (accept vs reject the exact-Nth value) is specified as inclusive-accept, exclusive-reject beyond, tested explicitly.
  • Multi-tenant query concurrency cap reached: excess queries queue with a bounded wait, then reject with a 429, never unbounded queueing.
  • A soak-discovered slow FD leak in one ingest source: isolated by the per-source task boundary (§19), identifiable via per-source FD-count telemetry.

23.9 Failure Analysis

A cardinality-cap or tenant-isolation failure is a shared-fate risk (one tenant/attribute affecting others) — the single most important production risk this phase closes. Detection: tenant_noisy_ neighbor.rs and the cardinality corpus, both CI-gated. Containment: ADR-11's three-layer scoping (storage+query+ingest) bounds a failure to the misbehaving tenant. Recovery: automatic (cap enforcement is stateless per-attribute); the runbook covers raising a specific tenant's cap after human review.

23.10 Operational Notes

Metrics: meridian_cardinality_dropped_attrs_total{tenant}, meridian_tenant_quota_rejections_total{tenant}, soak-run dashboards tracking memory/FD/disk trend lines over the 30-day window. This is the last phase; Appendix B (§40) summarizes all twelve phases' exit criteria together.

26. Operational Readiness

Metrics. All meridian_* counters/gauges/histograms listed per-phase (§12.10–§23.10) are exported via the self-instrumentation path (P14, ADR-20) in Prometheus-exposition-compatible format.

Tracing. The aggregator and producer both participate in the shared W3C TraceContext (ADR-23) — pipeline-stage spans (ingest, pipeline.redact, export.sink) let an operator trace one record's processing latency breakdown end-to-end.

Structured logging (self-hosted). The system's own operational logs are themselves meridian records (dogfooding, §5 Cross-Rank-equivalent internal consistency) — a broken pipeline is visible via the same query API used for application logs, unless the failure is total (in which case stdout is the fallback sink, always configured, per P7).

Dashboards. Per-sink health (meridian_sink_healthy), per-tenant ingest/query rate, DLQ depth by sink, WAL disk usage, cardinality-drop rate by tenant, redaction throughput vs pipeline throughput.

Alerting philosophy. Alert on rate-of-change and threshold-breach for counters that represent designed degradation (drops, DLQ growth) rather than treating every non-zero drop counter as page-worthy — the drop counters exist precisely so that degradation is observable, not so that it is always an incident.

SLOs. Ingest-accept availability 99.9% (§4); indexed-query p99 < 1 s; redaction-corpus pass rate 100% (a redaction regression blocks release, is not merely alerted on in production).

Incident response. Named runbooks: dropped-logs.md, buffer-full.md, shipper-stuck.md, redaction-failed.md, slow-query.md, tenant-isolation.md (§10) — each maps to a specific FM-# or T-# entry above.

Backup/restore. WAL segments and sealed store chunks are the durable artifacts; object-store cold tier is the backup target for chunks (retention-policy-governed, §22); the WAL itself is not long-term-backed-up (it is a transient durability bridge, not an archive, per ADR-06's rationale).

Deployment topology. Producer SDK: in-process, no separate deployment. Aggregator: per-host sidecar or per-cluster fan-in (operator choice, §19.10). Store: horizontally sharded by (tenant, time).

Canary / rolling-upgrade / rollback / migration. A new aggregator version canaries against a fraction of ingest traffic before fleet-wide rollout; rollback is a version-pin revert (stateless aggregator, no schema migration needed for a rollback since WAL/store formats are versioned, I13); schema-version bumps require the version-aware deserializer deployed fleet-wide before the new version is enabled (§27).

27. Compatibility & Versioning

Wire compatibility. Every persisted/shipped record carries schema_version (I13); a consumer encountering an unrecognized version degrades explicitly (reject-and-quarantine) rather than mis-parsing — never a silent field-drop.

Storage compatibility. Store chunk format is versioned per Arrow schema evolution rules (add-only column changes are backward-compatible; column removal/type-change requires a new chunk generation with a migration/compaction pass, §22).

API stability. The Query API's HTTP surface (/api/v1/*) follows SemVer at the path-prefix level (/api/v2/ for a breaking change); the field-predicate query language (§22) is additive-only within a major version.

Migration. A WAL-format version bump requires draining the old-format WAL (replaying it fully) before the new-format writer activates on that producer instance (§18.10).

Deprecation policy. A deprecated field/format/API version is supported for a minimum of 2 minor releases before removal, announced in CHANGELOG.md.

SemVer policy. meridian-* crates follow SemVer; a breaking change to any public trait (LogExporter, LogProcessor, §11) is a major-version bump across the whole workspace (single version number, per the terminology-lock discipline applied consistently across §10, §11, and Appendix A).

Rolling-upgrade guarantees. Old and new aggregator versions can run concurrently against the same WAL directory and DLQ during a rolling upgrade because the manifest format (I10) and DLQ entry format (I12) are both versioned and additive-only within a major version.

28. Testing & Verification Strategy

Unit tests. Per-crate, exercising individual type/function contracts (§11 signatures).

Integration tests. Cross-crate pipeline flows (conformance/runner.rs's simulator, §7).

Property tests (proptest, ADR-18). Serialization round-trip properties (§13), pipeline-stage order invariants (I5, I11), ring-buffer concurrent-access properties (I1, I4).

Differential tests. Syslog/OTLP/ECS field-mapping compared against reference-implementation output (Vector, Fluent Bit, §5) on shared fixture inputs, to catch silent semantic drift.

Fuzzing (cargo-fuzz, ADR-18). Five targets (§10): json_lines_parse, syslog_parse, otlp_decode, query_parse, redact_regex — each seeded from the conformance corpora and run continuously in CI (fuzz.yml); OSS-Fuzz onboarding is PhaseDeferred("§28").

Chaos testing. Sink-kill isolation fixtures (§17.5, §21.5), network-partition DLQ fixtures (§21), tenant-noisy-neighbor fixtures (§23.5).

Deterministic replay. The conformance simulator (§7) runs with a fixed seed and fixed clock (P9), making every invariant-violation reproducible bit-for-bit across re-runs.

Soak testing. 30-day sustained-load run (§23) with ASan+TSan enabled, tracking memory/FD/disk trend lines — the gate microbenchmarks cannot substitute for (§28's core rationale, echoed from §23.6).

Fault injection. Simulated disk-full, network-partition, and process-kill conditions injected at each of the WAL, sink-export, and ingest boundaries (§18, §21, §19 respectively).

Conformance gating. Ten buckets (§23.3) at 100% pass rate, tied directly to each phase's N.5 fixtures and the fourteen invariants (I1–I14) — a conformance regression identifies exactly which invariant it violates, never a vague "test failed."

Performance-regression gating. Every M-table row (§30) is enforced in perf.yml; a merge that regresses a benchmark below its threshold is blocked, not merely flagged.

31. Scalability Analysis

Stays constant. Producer per-call latency (M1/M2) is independent of fleet size — it is a local, in-process cost. Per-sink isolation (I6) means adding sinks does not degrade existing sinks' latency.

Grows (with Big-O). Aggregator ingest CPU: O(n) in records/s. Query-store memory: O(n) in distinct-attribute-value count before the cardinality cap (I9) makes it O(cap) per tenant per attribute — this is precisely why the cap exists (§34's capacity model derives the concrete number). Query latency for a full-text scan: O(chunks-in-range) without the deferred suffix-array index (PhaseDeferred("§22.3")).

Named bottlenecks in order: (1) redaction CPU (regex-dominated, M8's 50K/s/core ceiling is the tightest per-core throughput number in the whole pipeline); (2) WAL fsync latency under fsync_each; (3) cold-tier query latency (object-store round-trip); (4) inverted-index build cost at compaction time.

Horizontal scaling. Aggregator instances scale horizontally behind a load-balanced ingest front (stateless per-instance beyond its own WAL/DLQ); store nodes shard by (tenant, time).

Vertical scaling. Redaction throughput benefits most from vertical scaling (more cores directly parallelize the per-record regex cost, §20.7) up to the point cross-core cache contention dominates.

Sharding/partitioning. Store chunks partition by (service, hour, tenant) (§22.2); Kafka ingest partitions by the topic's own partitioning key, consumed via consumer groups (§19.2).

Coordination overhead. Kafka consumer-group rebalancing (FM-9) is the only cross-instance coordination cost in the ingest path; the aggregator's pipeline stages are otherwise per-instance, coordination-free.

Practical ceiling and levers beyond it. The practical per-aggregator-instance ceiling is bounded by M8 (redaction, 50K records/s/core) — beyond that, the lever is horizontal aggregator scale-out, not further per-instance tuning, since the regex cost is already linear-time-bounded (ADR-25) and cannot be meaningfully reduced further without SIMD acceleration (PhaseDeferred-eligible stretch, not core).

32. Mental Models & First Principles

  • MM1 — A log record is a schema, not a string. Predicts: any system that treats logs as opaque text eventually builds a fragile regex parser downstream to recover structure it threw away at write time. Bug class without it: silent parsing breakage on every log-format change. Applied in §8, §11.
  • MM2 — The WAL is the source of truth; the network ship is a downstream consumer of it (Kreps, §5). Predicts: durability must be measured at the WAL fsync, never at "we called the network send." Bug class without it: conflating "sent" with "durable," losing records the operator believed were safe. Applied in §18.
  • MM3 — Backpressure must be explicit at every layer or it becomes implicit blocking somewhere. Predicts: a system with no explicit admission policy at each boundary eventually blocks the application thread when any downstream layer slows. Bug class without it: mystery request-latency spikes traced back to an unbounded internal queue. Applied in §14, §18.
  • MM4 — Redaction is a trust-boundary control, not a formatting step. Predicts: redaction's position in the pipeline order is a security decision, not a stylistic one. Bug class without it: a PII leak from a pipeline misconfigured to route before it redacts. Applied in §8, §20.
  • MM5 — Cardinality is the OOM you don't see coming. Predicts: any indexed dimension without a hard cap eventually exhausts query-store memory as real-world entropy (UUIDs, timestamps-as-labels) finds its way into it. Bug class without it: a slow, unexplained memory-growth incident weeks after a seemingly unrelated schema change. Applied in §23, §34.
  • MM6 — A ring buffer's overflow policy is a business decision, not an implementation detail. Predicts: an audit-log workload and a debug-log workload need different overflow semantics (block vs drop) and a single hard-coded policy is wrong for one of them. Bug class without it: a compliance-critical log silently drops under exactly the load spike an audit needs it most. Applied in §18.6, §21.
  • MM7 — Sinks are bulkheads (Nygard, §5). Predicts: shared retry/backoff state across sinks reintroduces the coupling isolation exists to prevent. Bug class without it: one dead sink's backoff timer throttling every healthy sink. Applied in §17, §21.
  • MM8 — A regex is a program; its complexity class is a security property, not an implementation detail (Cox, §5). Predicts: any backtracking regex exposed to attacker-influenced input is a latent CPU-exhaustion vulnerability, regardless of how carefully rules are authored. Bug class without it: a crafted log body or redaction rule causing pipeline-wide CPU exhaustion. Applied in §20, §24 (T4).

Chose to index only labels, explicitly rejecting full-text/attribute indexing to keep per-stream storage cost near-flat regardless of cardinality — wins for cost-optimized long-retention deployments where full-text query is rare; this design indexes arbitrary attributes and instead bounds cost via the cardinality cap (I9), accepting more indexing cost for richer query expressiveness.

OpenTelemetry Collector. Chose a fully general, config-driven pipeline graph (arbitrary receiver→processor→exporter topologies) — wins when the deployment must unify logs, metrics, and traces in one configurable agent; this design fixes the stage order (§8) specifically for logs, trading topology flexibility for the ability to make pipeline-order invariants (I5, I11) enforceable at construction time rather than only at configuration-review time.

34. Back-of-Envelope Capacity Model

  1. Producer ring memory = capacity (8,192) × avg record size (~300 B) ≈ 2.4 MB; well inside the 20 MB steady-state budget (§4) once SmallVec/thread-local buffer overhead (~a few MB) is added.
  2. WAL growth rate (unshipped) = ingest rate (100,000 rec/s) × avg serialized size (~300 B) = 30 MB/s ≈ 2.6 TB/day if never drained — the number that makes WAL-size-cap alerting (T8, FM-3) non-optional.
  3. WAL segment rotation frequency at peak = segment size (64 MiB) ÷ growth rate (30 MB/s) ≈ every 2.1 s at sustained 100K rec/s on one producer.
  4. Aggregator instance capacity = per-core ingest throughput (100,000 rec/s/core, M6) × core count (8) = 800,000 rec/s per instance before horizontal scale-out is required.
  5. Cardinality index memory per tenant per attribute = cap (100,000 values, I9) × postings-entry size (~50 B) ≈ 5 MB; with ~20 commonly-indexed attributes per tenant ≈ 100 MB baseline index memory per tenant.
  6. Hot-tier write volume per hour = ingest rate (100,000 rec/s) × 3,600 s × avg size (300 B) ≈ 108 GB/hour — the number that sizes the hot-tier memory budget referenced in §22.6/FM-10.
  7. Tail-query buffer ceiling = max concurrent tail connections (10,000, §4) × per-connection buffer (1,000 records) × avg size (300 B) ≈ 3 GB worst-case tail-buffering memory.
  8. Redaction-vs-pipeline core ratio = pipeline throughput (100,000 rec/s/core, M7) ÷ redaction throughput (50,000 rec/s/core, M8) = 2× — redaction needs twice the cores of the rest of the pipeline to keep pace, the arithmetic behind the §31 bottleneck ranking.
  9. DLQ accumulation during a 40-minute sink outage (§8's worked failure-path) at a per-sink share of 10,000 rec/s × 300 B ≈ 7.2 GB accumulated in that sink's DLQ before recovery — sizes the DLQ disk budget referenced in FM-3.
  10. Cold-tier storage after compression = hot-tier volume (108 GB/hour, #6) ÷ ZSTD ratio (≥ 4:1, M12) ≈ ≤ 27 GB/hour equivalent in cold storage at the same logical volume.

36. Alternative Architectures (Roads Not Taken)

Alt-1 — Sidecar-only shipper, no in-process SDK.

App (any language) → stdout/file → sidecar tails file → parses → ships

Regime it wins: legacy or polyglot fleets where embedding a Rust library per-language is infeasible. Real system: classic Filebeat/Fluentd deployments tailing application stdout. Why rejected: loses typed events at the source — trace/span injection (§15) and redaction (§20) cannot happen before the record is serialized to a flat text line, forcing a parse-then-reparse round trip and reintroducing the exact text-log fragility (MM1) this system exists to remove.

Alt-2 — Fully synchronous logging (no ring buffer, direct write).

log!() → write() syscall directly → caller blocks until sink accepts

Regime it wins: low-volume batch jobs where blocking briefly on I/O is genuinely acceptable. Real system: classic synchronous handlers in early logging libraries (e.g. unbuffered Python logging handlers). Why rejected: directly violates P2 — blocks the caller under sink slowness, unacceptable for any request-path code, which is this system's primary target (§4).

Alt-3 — Exactly-once delivery via two-phase commit between producer and store.

Producer  <—— 2PC coordinator ——>  Store
   (prepare / commit / abort across both)

Regime it wins: financial-ledger-style systems where a duplicate record is worse than added coordination latency. Real system: transactional-outbox patterns (e.g. Debezium's database-outbox approach). Why rejected: 2PC's coordinator-blocking cost is incompatible with P2's non-blocking hot path; at-least-once delivery (I3) plus idempotent/dedup-capable consumers is chosen instead, accepting bounded duplicates over any coordination blocking.

Alt-4 — Schema-on-read: raw blob storage, parse at query time.

Raw bytes → object-store blob (no ingest-time structuring) → parsed on each query

Regime it wins: extremely high ingest volume where write-time structuring cost is prohibitive. Real system: raw CloudWatch Logs export to S3, queried via Athena. Why rejected: pushes parsing cost to every query instead of once at ingest, and — critically — removes the ingest-time enforcement point for redaction (I5) and cardinality capping (I9), since neither can run before data has already landed in an external-facing store.

38. Glossary

  • Aggregator. The independently-deployed service that ingests, filters, enriches, transforms, redacts, and routes log records.
  • Attribute. A typed key/value field on a LogRecord.
  • Backpressure. An explicit admission-control signal propagated when a downstream layer cannot keep pace with an upstream producer.
  • Baggage. Cross-cutting key/value context propagated alongside trace/span IDs.
  • Batch. A group of records flushed to a sink together; atomic per record (I8), not as a whole unit.
  • Body. The free-form message payload of a LogRecord.
  • Cardinality. The count of distinct values observed for a given attribute.
  • Cardinality cap. The per-tenant per-attribute hard limit (I9) beyond which new values are dropped.
  • Checkpoint manifest. The on-disk record of WAL segment state and last-shipped offset (I10).
  • Chunk. A columnar storage unit scoped to (service, hour, tenant).
  • Compaction. The process of merging/promoting chunks between storage tiers (hot→warm→cold).
  • Conformance corpus. A named set of fixtures used to gate correctness for a specific format or stage.
  • Context. The in-process carrier of trace_id/span_id/baggage/custom fields (§15).
  • Contextual field. A field auto-injected into a record from the active Context.
  • Dead-letter queue (DLQ). The per-sink store for batches that exhausted retry (I12).
  • Deferred feature. A scoped-out capability tracked in the Deferred Features Register (§37).
  • ECS. Elastic Common Schema — a field-naming convention for log/event data.
  • Enrich. The pipeline stage that adds static-config fields to a record.
  • Exporter. The component implementing LogExporter that ships records to one sink.
  • Fan-out. Delivery of one record to multiple sinks via routing.
  • File-tail. An ingest source that follows an existing log file's growth via inode tracking.
  • Filter. A pipeline stage that drops records matching (or not matching) a predicate.
  • Fsync policy. The WAL durability dial: fsync_each, fsync_batch, or fsync_none.
  • Ingest. The aggregator stage that decodes an external wire format into a LogRecord.
  • Instrumentation scope. The name/version of the logger that produced a record.
  • Invariant. A system property (I1–I14) that must hold at all times, independent of configuration.
  • Inverted index. A per-attribute index mapping value → matching record set.
  • JSON Lines. The line-delimited JSON wire format (one record per line).
  • Level (Severity). The record's importance classification (Trace…Fatal, mapped to 1–24).
  • LogRecord. The canonical typed event structure (§11).
  • logfmt. The flat key=value wire format.
  • Luhn validation. The checksum algorithm used to reduce false-positive credit-card redaction.
  • Observed timestamp. The time a record was received by the ingest stage, distinct from its originating timestamp.
  • OTLP. OpenTelemetry Protocol — the canonical structured wire format.
  • Pipeline. The fixed-order sequence of aggregator stages (§8).
  • Processor. The producer-side component (LogProcessor) managing record lifecycle before export.
  • Producer. The in-process SDK component that constructs and emits records.
  • Quarantine. The isolated destination for malformed input records (I14).
  • Query API. The HTTP surface for searching and aggregating stored records.
  • Redaction. Replacement of sensitive field/body content with a placeholder or hash.
  • Resource. Attributes describing the producing service (e.g. service.name).
  • Retention. The per-tenant policy governing how long chunks remain queryable.
  • Ring buffer. The lock-free bounded structure between the producer macro and the WAL writer.
  • Route. The pipeline stage that assigns a redacted record to one or more sink targets.
  • Sampler. The component deciding whether a record is kept (ratio- or rate-based).
  • Schema version. The explicit version tag on every persisted/shipped record (I13).
  • Severity. See Level.
  • Sink. An output endpoint implementing LogExporter.
  • Structured logging. Logging where every emitted event is a typed record, not free text.
  • Syslog. The RFC 5424 legacy ingest/emit protocol.
  • Tail query. A streaming (WebSocket) query that pushes matching records as they arrive.
  • Tenant. The multi-tenancy isolation boundary spanning storage, query, and ingest.
  • Token index. The whitespace/punctuation-tokenized full-text index (word-boundary search).
  • Trace context. The W3C-standard carrier of trace_id/span_id across process boundaries.
  • Value. The OTel-shaped typed attribute/body union (Bool/Int/Double/String/Bytes/Array/KvList).
  • WAL. Write-Ahead Log — the on-disk durability mechanism between the ring buffer and the shipper.
  • Watermark. The high-water-mark trigger that causes the shipper to drain the buffer aggressively.
