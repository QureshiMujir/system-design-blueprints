⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the §10 repository layout, CI hygiene chain (ADR-16), and a hand-crafted "hello parser" correctness kernel: a trivial grammar (S -> "hello"), a hand-built ParseTable (§8.1), and a GLR runtime that can execute it end to end. This phase introduces no generator code — the table is authored by hand to de-risk the runtime before the generator exists.

Deliverable

A repository at CI-green scaffold bar; make test runs and passes one test that parses "hello" end to end and asserts the resulting tree's root kind() == "S".

Acceptance

make test exits 0 with exactly 1 passing test named hello_parser_smoke; make lint (clippy --deny warnings) exits 0; make conformance emits conformance.report.json with exactly one Pass bucket (hello-smoke); CI wall time for the full workflow < 3 minutes on the reference runner.

Fixtures

conformance/corpora/parse-trees/hello.txt — input "hello", expected tree (S "hello"). conformance/corpora/parse-trees/hello_malformed.txt — input "goodbye", expected an ERROR root node (I7 exercised even in Phase 0's minimal recovery stub).

Pitfalls
  • Building the generator first before the runtime — the smaller, higher-confidence deliverable is a runtime against a hand-built table (P2, §6).
  • cargo-deny failing on day one over license metadata — pin LICENSE-APACHE/ LICENSE-MIT and Cargo.toml license fields before first CI run.
  • Skipping the tracing wiring "for now" — every later phase's diagnostics (§25) depend on the span convention established here.

⬜ Phase 1 — Grammar DSL & IR §13

Objectives

Implement the grammar DSL parser and the canonical grammar IR lowering (§8.1) in parsekit-grammar. Compile the four reference grammars (JSON, JavaScript-subset, Rust-subset, Python-subset) to validated IR. No LR table generation yet (Phase 2).

Deliverable

parsekit-grammar compiles the four reference grammars' .js DSL sources (crates/parsekit-grammars/{json,javascript-subset,rust-subset,python-subset}/ grammar.js) to a snapshot-tested IR with zero validation errors.

Acceptance

All four reference grammars compile to IR in < 200ms each (single-threaded, reference host, §4); the IR snapshot tests (insta-style) are byte-identical across two consecutive runs (I2, determinism); the validator rejects 12 seeded malformed grammar fixtures (§13.5) with typed, span-located errors — zero false negatives.

Fixtures

grammar-dsl/json.js → valid IR, 6 rules. grammar-dsl/left_recursion_no_prec.js → Err(UnresolvedLeftRecursion). grammar-dsl/dangling_rule_ref.js → Err (UnresolvedRuleName). grammar-dsl/external_no_scanner.js → Err (MissingExternalScanner). grammar-dsl/ambiguous_field.js → validator warning (non-fatal), snapshot-tested.

Pitfalls
  • Allowing arbitrary JS constructs to leak through the whitelist parser — the DSL parser must reject, not silently ignore, unrecognized JS syntax.
  • Treating prec on a non-binary alternation as valid — the validator must flag this common grammar-author mistake (rule N.2, ADR-21 longest-match discipline depends on correctly-scoped precedence).
  • alias applied to a bare terminal literal — legal but rarely intentional; documented, not rejected.

⬜ Phase 2 — LR(1) Table Generator §14

Objectives

Build the canonical LR(1) automaton from the grammar IR, detect shift/reduce and reduce/reduce conflicts, resolve what prec/prec.left/prec.right can resolve, and compact the table via the Pager merge (P7, ADR-07).

Deliverable

The four reference grammars produce ParseTable binaries; JSON's table is conflict-free and < 50 KB; the Rust-subset table's residual conflicts are covered entirely by bounded GLR forks (no unresolved-conflict compile warning above the I4 soft cap).

Acceptance

JSON table size < 50 KB (M8); table generation for the Rust-subset grammar completes in < 2 s on the reference host; the Pager merge reduces state count by ≥ 60% versus canonical LR(1) on the Rust-subset grammar (measured and asserted in pager_merge_reduction_test); regenerating from the same IR twice produces byte-identical tables (I2).

Fixtures

lr-tables/json.grammar → table, zero conflicts. lr-tables/dangling_else.grammar (the classic shift/reduce ambiguity fixture) → resolved via prec, zero residual forks. lr-tables/genuinely_ambiguous.grammar → residual GLR fork, snapshot-tested fork count. lr-tables/pathological_state_blowup.grammar → generator error StateCountExceeded (malformed/adversarial-input regression case).

Pitfalls
  • Skipping the Pager merge "to ship faster" — canonical LR(1) tables for real grammars are 5–10× larger (§14.4), directly blowing the WASM budget (§4).
  • Forking on every shift/reduce conflict instead of resolving with prec — correct but slow (P1's tradeoff clause); the generator's compile-time fork-count warning exists precisely to catch grammar authors doing this by accident.
  • The Pager compatibility test producing a phantom reduce-reduce conflict on a subtle lookahead-set interaction — the pairwise compatibility test (§8) is the documented safety net; any merge failing it is left unmerged, never forced.

⬜ Phase 3 — Lexer DFA Generation & External Scanners §15

Objectives

For each LR state, generate a DFA over the terminals shiftable in that state (P6, §6); implement the external-scanner hook (ADR-19) for context-sensitive tokens.

Deliverable

The JSON grammar's lexer tokenizes a 50 MB JSON corpus with zero misclassified tokens; a hand-written external scanner for Python-style indentation tokens (INDENT/DEDENT) passes its round-trip serialization property test.

Acceptance

Lexer throughput ≥ 200 MB/s on the JSON corpus (reference host, single core); the external-scanner round-trip property test (proptest, ADR-13) passes 10,000 random scanner-state sequences with zero serialization mismatches; token disambiguation matches upstream tree-sitter byte-for-byte on the queries/token-disambiguation conformance bucket (100% match required, no tolerance).

Fixtures

lr-tables/lexer/json_50mb.txt → zero misclassified tokens. lexer/type_param_vs_lt.rs — the Vec<T> vs a < b disambiguation fixture exercising §15.6's LR-state-aware lexing. lexer/python_indent.py — external-scanner INDENT/DEDENT round-trip fixture. lexer/heredoc.rb-style fixture for a second external-scanner shape (context-sensitive delimiter matching).

Pitfalls
  • Treating the lexer as a standalone stage decoupled from LR state — reintroduces the < ambiguity bug class this design exists to avoid (P6).
  • An external scanner that consumes input but emits no token — the runtime's "no progress" detector (§15.7 in the original draft, now enforced via a per-scan token-emission assertion) must bail rather than hang.
  • Two external scanners recognizing an overlapping prefix with no declared preference — a grammar-authoring error the validator (Phase 1) should have caught; the runtime treats it as a nondeterminism bug (I2 violation) if it reaches this phase undetected.

⬜ Phase 4 — GLR Runtime Engine §16

Objectives

Implement the graph-structured stack (GSS, I3) and the per-token GLR step: push (shift), pop (reduce), fork (conflict), merge (convergence) — Tomita's algorithm (§5) executed against the Phase-2/3 generated tables.

Deliverable

The JSON parser produces trees byte-identical to upstream tree-sitter on a 50 MB corpus; the Rust-subset parser passes the parse-trees/rust-subset conformance bucket at ≥ 99%.

Acceptance

Cross-engine determinism corpus (§27) passes ≥ 95% overall, 100% on the JSON bucket (M1, §29); cold-parse throughput ≥ 25 MB/s on the Rust-subset grammar (M4, §4); live branch count never exceeds 64 without a logged glr.fork_cap_warning event (I4) across the full conformance corpus.

Fixtures

parse-trees/json_50mb.txt → byte-identical to upstream. parse-trees/ ambiguous_dangling_else.rs-style fixture → deterministic tie-break, snapshot-tested. parse-trees/deep_fork_no_merge.grammar+input — a deliberately pathological fixture exercising the I4 soft-cap warning path. parse-trees/malformed_utf8.bin — replay fixture ensuring non-UTF8 byte sequences never panic the lexer/GLR boundary.

Pitfalls
  • Getting the GSS merge step wrong — the single hardest correctness surface in this system; the conformance corpus (§27) is the only reliable safety net, not code review alone.
  • Merging branches with different prec.dynamic accumulations — this silently discards the ambiguity-resolution signal (P12 violation); merge must compare accumulated dynamic precedence before coalescing.
  • Long fork sequences with no merges — a performance pathology (§16.7); the generator's compile-time warning (§14.10) is the first line of defense, the I4 runtime cap the second.
  • External scanners mutating state visible outside their own scan call — breaks the GLR contract that branches are independently replayable (ADR-19's determinism requirement).

⬜ Phase 5 — Red/Green Syntax Tree §17

Objectives

Implement the green tree (interned, value-typed, arena-allocated) and the red tree (lazy, positioned, parent-aware projection) per §8.2 and ADR-04; implement TreeCursor (P3, §6).

Deliverable

A 1 MB source file produces a green tree with < 5 MB total allocation (M6, §4); two trees from adjacent non-overlapping edits share ≥ 95% of green-tree storage (measured via arena byte-accounting in bench_incremental.rs).

Acceptance

Green-tree memory ≤ 5 bytes per source byte on the four reference-grammar corpora (M6); intern-table hit rate ≥ 70% on the Rust-subset 1 MB corpus (tree.intern_hit_rate telemetry, I5); red-node first-visit latency ≤ O(depth) verified via a depth- parameterized benchmark asserting linear (not superlinear) scaling.

Fixtures

incremental/green_tree_sharing_1mb.rs — asserts ≥ 95% storage sharing across one localized edit. incremental/intern_hit_rate_rust_subset.rs — asserts the 70% hit-rate floor. parse-trees/field_accessor_roundtrip.json — every field()-declared child in the JSON grammar resolves correctly via child_by_field_name.

Pitfalls
  • Forgetting to intern structurally identical subtrees — direct memory-bound violation (M6); caught by the intern-hit-rate CI gate (§17.4).
  • A red node holding an Rc/Arc-cycle to its parent — creates a leak; the parent link is a borrowed reference bound by 'tree, never a strong-counted cycle (I6).
  • Omitting the kind_id from the intern hash function — two structurally identical trees of different kinds would collide, corrupting the green tree (a correctness bug, not just a performance one).
  • Assuming red-tree materialization is free — the first visit to a deeply nested node is O(depth); this is a documented, not hidden, cost (§17.4's benchmark makes it visible).

⬜ Phase 6 — Incremental Re-parse §18

Objectives

Implement InputEdit application and the incremental cursor (§8.3) that reuses unchanged green subtrees and re-parses only the affected span (P4, Wagner & Graham §5).

Deliverable

A single-byte edit in a 1 MB file produces a new tree via subtree reuse, byte-identical to a full non-incremental re-parse of the final source (I2's determinism extended to the incremental path).

Acceptance

Single-byte edit, 1 MB file: p50 < 300 µs, p99 < 1 ms (M2, §4); whole-line edit, 100 KB file: p99 < 100 µs (M3); incremental output byte-identical to non-incremental parse on 100% of the conformance/corpora/incremental corpus (zero tolerance — this is the one bucket with no percentage discount, since any divergence is a correctness bug, not a grammar-ambiguity artifact).

Fixtures

incremental/single_byte_edit_1mb.rs — the M2 latency-gated fixture. incremental/ whole_line_edit_100kb.json — the M3 fixture. incremental/edit_crosses_delimiter.rs — an edit that inserts a {, forcing cascading re-parse beyond the immediate edit range (§18.7 pitfall). incremental/edit_at_eof.py — no resync point exists; must re-parse cleanly from edit to new EOF. incremental/resync_window_exceeded.rs — a synthetic 200-token-deep structural edit exceeding the 128-token window, asserting a clean bail rather than a hang or panic.

Pitfalls
  • Tuning the resync window as a universal constant — it is grammar-dependent; the 144-line detail section documents the heuristic, and per-grammar override is exposed via Language's metadata (docs/architecture/incremental.md).
  • Assuming every edit has a resync point — edits at EOF have none; the cursor must cleanly re-parse edit-to-EOF rather than looping searching for a match that cannot exist (§18.8 edge case).
  • Ignoring external-scanner state at the reuse boundary — I11's serialize/deserialize round-trip is the reuse predicate's fourth (unwritten in Wagner & Graham, added by ADR-19) condition: a subtree spanning an external-scanner boundary is only reusable if the scanner state round-trips identically.
  • An edit that inserts a structural delimiter ({) cascading re-parse far beyond the edit itself — a real, not hypothetical, perf characteristic; documented rather than "fixed" (there is no fix — it is a correct consequence of the grammar's structure).

⬜ Phase 7 — Error Recovery §19

Objectives

Implement single-token insertion/deletion recovery, N-token skip, and error-node synthesis (§8.4, §8.5, ADR-08, Burke & Fisher 1987, §5) so Parser::parse never fails to return a tree (I7, P5).

Deliverable

A file with one syntax error per 10 lines produces a tree with correct structure outside the error regions; the recovery-quality benchmark (a fixed, hand-scored corpus of broken files) scores ≥ 0.80 on its 0–1 scale.

Acceptance

Recovery-quality benchmark score ≥ 0.80 (M7, named fixture conformance/corpora/ recovery/scored_corpus/); insertion recovery attempted within a bounded trial count (≤ the number of valid-shift terminals in the current state, typically < 20, keeping recovery latency bounded); zero panics across the recovery fuzz target (fuzz_targets/recovery.rs) after a 24-hour local fuzz run (pre-Phase-10's 30-day canary, §22.4).

Fixtures

recovery/missing_rhs_expr.rs — the let x = ; fixture from §8.4, asserting a MISSING identifier node at the correct offset. recovery/unterminated_string.py — the §8.5 failure-path fixture, asserting a single ERROR node spans exactly the unterminated region plus the bail window. recovery/one_error_per_10_lines.rs — the M7 scored-corpus fixture. recovery/cascading_brace_mismatch.rs — nested delimiter mismatch exercising N-token skip escalation.

Pitfalls
  • Recovering too eagerly — producing a tree that diverges from the author's intent; the recovery window (§4) is the explicit throttle against this (documented tradeoff, not tuned away).
  • Inserting MISSING tokens without a zero-byte range — breaks editor highlighting, which assumes every node has a valid (if empty) range (I13).
  • Assuming a unique best recovery exists — an ambiguous grammar can yield multiple equally-good recoveries; the deterministic first-found tie-break (P12) is chosen over an arbitrary or random pick.
  • Treating insertion and deletion as independent of the resync/bail escalation chain — they are one algorithm with four escalating tiers (§19.2), not four separate strategies tried in isolation per error site.

⬜ Phase 8 — Query Engine §20

Objectives

Implement the S-expression query DSL parser, NFA-based pattern compiler with capture slots, streaming QueryCursor, and the standard predicate set (P8, ADR-09).

Deliverable

The Rust-subset highlight query matches upstream tree-sitter-rust's highlight-query match set on the standard corpus; QueryCursor throughput ≥ 50 MB/s on the highlight corpus.

Acceptance

Query-match throughput ≥ 50 MB/s (M9, §4-adjacent target, reference host); highlight- query parity with upstream ≥ 95% match rate (M-table row, §29); a malformed query pattern returns a typed QueryError (never a panic) across 5,000 proptest-generated malformed patterns.

Fixtures

queries/rust_highlight.scm — the upstream-parity fixture (§20.4). queries/ capture_slot_overlap.scm — nested captures at the same byte range, asserting most-specific-wins resolution (shared with §21.7's highlight-driver logic). queries/predicate_eq_match.scm — #eq?/#match? composite fixture. queries/malformed_pattern_fuzz_corpus/ — the proptest seed corpus for §20.4's malformed-pattern property test.

Pitfalls
  • Evaluating predicates during the tree walk instead of at match-emit — couples predicate cost to walk depth unnecessarily; ADR-09's NFA-sharing design assumes predicates are a post-filter.
  • A #match? predicate whose regex risks catastrophic backtracking (a ReDoS-shaped pattern) — mitigated by compiling query predicate regexes through a linear-time engine (not the runtime's own lexer-NFA machinery, ADR-22's boundary: query predicates are the only place a regex engine is consulted at runtime).
  • Quantifiers combined with negation producing a pattern that never matches — a grammar-author usability issue, not a system bug, but documented in docs/ architecture/query.md per the tree-sitter query reference (§5 RFCs).

⬜ Phase 9 — Front-Ends: Highlight, Fold, Symbols, Indent, Injection §21

Objectives

Build the query-driven front-ends: highlight (token classes), fold (collapsible ranges), symbols (outline), indent, and language injection (embedded-language grafting), each a query plus a small driver (P8's design carried to its consumers).

Deliverable

Highlight, fold, symbol, and indent queries for the four reference grammars are checked in under parsekit-grammars/*/queries/; CSS-in-<style>-tag injection works end to end against an HTML-subset host grammar.

Acceptance

Highlight/fold/symbol/injection conformance buckets each ≥ 95% parity with upstream tree-sitter's equivalent query outputs (M10, §29); the highlight driver's incremental update path re-renders only the edited span's token-class stream, verified by an assertion counting re-emitted tuples versus total tuples on a localized edit (< 5% of the file's tuples re-emitted for a single-line edit in a 10,000-line file).

Fixtures

highlight/rust_subset_vs_upstream.rs — the parity fixture (§21.4). fold/nested_ blocks.json — fold-range correctness on nested structures. symbols/outline_ duplicate_names.py — two declarations sharing a name, asserting the outline disambiguates by byte range, not name alone. injection/css_in_style_tag.html — the end-to-end injection fixture (§21.3).

Pitfalls
  • Emitting overlapping highlight captures without a most-specific-wins rule — produces visibly wrong (usually parent-class) highlighting; the active-capture stack (§21.2) is the fix, not a special case per grammar.
  • Injection across nested injections (e.g., HTML > CSS > a CSS @media construct resembling further nesting) — requires careful resynchronization at the injection boundary; documented in docs/architecture/injection.md, not silently approximated.
  • Treating theme/color mapping as in-scope — it is explicitly out of scope (§1 system boundaries); the engine emits token classes only.
  • An indent query producing conflicting indent/outdent signals at the same line — a grammar-authoring bug; the driver surfaces a diagnostic rather than silently picking one signal.

⬜ Phase 10 — Editor Integration & Production Hardening §22

Objectives

Ship the C ABI (ADR-10), WASM packaging (ADR-11), editor demos, and the full performance/fuzzing/conformance hardening pass gating a first release.

Deliverable

A binary-compatible (documented subset) C header versus tree-sitter's; a WASM bundle < 200 KB compressed for the four reference grammars; the Neovim plugin highlights Rust source interactively; the VS Code extension highlights Markdown with embedded fenced code blocks via injection (§21).

Acceptance

30-day fuzz canary: zero crashes, zero miri-detected UB across all fuzz targets (M-table row, §29); WASM bundle < 200 KB compressed (M11, §4); C ABI conformance test (binary layout comparison against a pinned tree-sitter header version) passes on the documented function subset (§22.2) with zero layout mismatches; cross-engine conformance ≥ 95% aggregate across all buckets (§27), 100% on the JSON bucket.

Fixtures

fuzz_targets/c_abi_roundtrip.rs — round-trips a parse through the C ABI and back, asserting tree equality with the pure-Rust path. upstream-treesitter/aggregate_ report.json — the full cross-engine conformance report, checked into CI artifacts per run. wasm/bundle_size_check.rs — asserts the compressed bundle stays under the 200 KB budget, failing CI on regression.

Pitfalls
  • Letting a Rust panic unwind across the extern "C" boundary — undefined behavior in the C host; every C ABI entry point wraps its body in std::panic::catch_unwind (documented in docs/architecture/overview.md's FFI-safety section).
  • WASM bundle-size creep from an innocuous new dependency — every Cargo.toml change to parsekit-runtime or its transitive deps is reviewed against the WASM budget before merge (a standing PR-template checklist item, not a one-time check).
  • Treating the 30-day fuzz canary as optional because "the unit tests pass" — the canary exists precisely because unit tests cannot enumerate the input space; release is gated on the canary's completion, not bypassed under schedule pressure.
  • Assuming WASM's single-threaded constraint is automatically enforced — it is documented but not compiler-enforced; the JS glue layer's own re-entrancy guard (a simple in-flight flag) is the actual enforcement mechanism.
