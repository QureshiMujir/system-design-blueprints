Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does the generator/runtime split (ADR-05) matter for the WASM bundle-size budget (M11)? (§9 ADR-05, §22.7)
  2. Why is the Pager merge (§14.4) necessary even though canonical LR(1) is strictly more precise than LALR? (§9 ADR-07, §14.8)
  3. Under what grammar conditions does GLR's fork-and-merge stay sub-cubic, and what observable signal tells you it has stopped being sub-cubic on a real grammar? (§16.7, §7 I4, §24 FM-7)
  4. Why can the incremental cursor and the error-recovery engine share the same resync mechanism, and what would break if they were implemented independently? (§18.2, §19.2, MM5 §31)
  5. Why does conflating the green and red tree layers reintroduce a historically documented bug class rather than just "losing an optimization"? (§9 ADR-04, §24 FM-4, §5 Reference Implementations)
  6. What is the precise reuse predicate for a subtree during incremental re-parse, and which of its three (really four, with I11) conditions is most often the one a naive implementation forgets? (§8.2, §18.2, §7 I11)
  7. Why is the resync window (128 tokens) a per-grammar tunable rather than a system constant, and what happens when it is set too small versus too large? (§4, §18.6)
  8. Trace what happens when a shift/reduce conflict and an ambiguous prec.dynamic tie occur in the same parse — which mechanism resolves first, and why does the order matter for determinism (I2)? (§16.2, §16.9's original detail folded into §16.2, §7 I2)
  9. Why does the external-scanner trait require a serialize/deserialize round-trip rather than just re-running the scanner from scratch on every incremental boundary? (§7 I11, §15.2, §18.6)
  10. Why is a regex engine explicitly excluded from the lexer but explicitly included (bounded) in the query predicate layer — what property differs between the two use sites? (§9 ADR-22, §20.6, §23 T11)
  11. What concretely would go wrong if error recovery's insertion trial-parse were unbounded (tried every possible multi-token insertion) instead of single-token? (§9 ADR-08, §19.7, §33 item 9)
  12. Why does the C ABI need its own panic-boundary discipline (catch_unwind) when the pure-Rust API already guarantees I7 (no panics on malformed input)? (§22.2, §22.6, §23 T7, MM8 §31)
  13. Compare this system's red/green split to rust-analyzer's rowan and to IntelliJ's PSI — what does each give up relative to the other two? (§32, §5 Reference Implementations)
  14. Why is the 30-day fuzz canary gated on releases rather than every CI push, and what does the capacity model say about why that is the economically correct choice? (§28, §33 item 12)
  15. Under what condition does GLR lose to PEG despite PEG's rejected-alternative status in ADR-02 — i.e., where in the design space does the rejected choice actually win? (§9 ADR-02's sixth column, §35)
  16. Why does query-match evaluation defer predicates to match-emit time instead of evaluating them during the tree walk, and what would the cost model look like if it didn't? (§20.6, §20.7, MM6 §31)
  17. What is the exact chain of evidence that would convince a skeptical reviewer this system's incremental output is byte-identical to a full re-parse, and which conformance bucket carries zero tolerance for divergence? (§18.4, §27.1, §7 I2)
  18. Why does the Deferred Features Register anchor streaming parse to the Scalability Analysis rather than to a specific phase? (§30, §36)
  19. Explain why the intern table's hash function choice (FxHash, non-cryptographic) is safe here but would be unsafe in a security-sensitive hashing context — what threat model difference justifies it? (§17.7, §23)
  20. Why is "the tree always exists" (I7) necessary infrastructure for every other front-end (highlight, fold, symbols) rather than a Phase-7-only concern? (§7 I7, §21.1, §19.1)

31. Mental Models & First Principles

  1. MM1 — A parser is a table interpreter, not a program. The generator does the thinking (LR(1) construction, Pager merge); the runtime just walks a table (§16.2). Predicts: correctness bugs live overwhelmingly in the generator (§14), not the runtime loop. Bug class without it: engineers debug the wrong crate when a parse is wrong. Applied in §14, §16.
  2. MM2 — The GSS is a lattice of "what if," not a tree of guesses. Every live branch is a legitimate parse-in-progress, not speculative backtracking (Tomita, §5). Predicts: merge is not an optimization bolted onto backtracking — it is what makes GLR sub-exponential in practice. Bug class without it: engineers "optimize" by deleting merges, reintroducing exponential blowup. Applied in §16.2, §16.7.
  3. MM3 — Green is what the tree IS; red is where the tree IS. Identity (structural sharing) and position (byte offsets, parent pointers) are orthogonal concerns that must never share one representation (ADR-04). Predicts: any "simplification" that stores a byte offset inside a green node is a regression. Bug class without it: FM-4's Roslyn-era conflation. Applied in §17.
  4. MM4 — Incrementality is a reuse predicate, not a diff algorithm. The system never computes a text diff; it asks, per subtree, "is this still valid here" (§18.2). Predicts: incremental correctness reduces to proving the predicate sound, not to diff-algorithm cleverness. Bug class without it: engineers reach for a generic tree-diff library, missing the LR-state-validity check the predicate needs. Applied in §18.
  5. MM5 — Error recovery is resync, and resync is the same operation whether triggered by an edit or a syntax error. Both ask "where can the parser legitimately resume." Predicts: the incremental cursor and the recovery engine can share machinery (§19.2). Bug class without it: two independently-maintained resync implementations drift and disagree. Applied in §18, §19.
  6. MM6 — A query is a second, smaller grammar over the tree, not a string search. The NFA-with-captures design (§20.2) treats structural matching as a first-class parsing problem, not text scanning. Predicts: query performance scales with tree shape, not source length. Bug class without it: implementing queries as a tree-walk-plus-regex hybrid, losing the shared-NFA amortization. Applied in §20.
  7. MM7 — Determinism is a compounding asset, not a nicety. Every downstream gate (conformance, fuzzing, replay) assumes I2; a single nondeterministic tie-break silently invalidates all of them at once. Predicts: any "random" tie-break request ("just pick one") is actually a request to break the entire testing strategy. Bug class without it: flaky CI blamed on "test infrastructure" when the real cause is a nondeterministic parse. Applied in §7 (I2), §27.
  8. MM8 — The C ABI is a second language boundary with its own correctness contract, not a mechanical export of the Rust API. Ownership, panics, and lifetimes do not cross extern "C" for free (§22.2). Predicts: every new public Rust API needs an explicit FFI-safety review, not an automatic re-export. Bug class without it: T7/FM-9's ABI-corruption and layout-mismatch failure modes. Applied in §22.

5. Required Reading

Books

  • Aho, Sethi, Ullman, Lam. Compilers: Principles, Techniques, and Tools, 2nd ed. Ch. 4 (parsing, LR item sets) and Ch. 5 (translation schemes). Applied in §14 (LR(1) item-set construction) and §11 (ParseTable schema).
  • Grune & Jacobs. Parsing Techniques: A Practical Guide, 2nd ed. Ch. 9 (GLR parsing) and Ch. 10 (error recovery). Applied in §16 (GSS design) and §19 (recovery algorithm).
  • Appel. Modern Compiler Implementation in ML (or the C/Java editions). Ch. 3 (LR parsing implementation detail). Applied in §14.6 (table compaction).
  • Fowler, Beck, et al. Refactoring, 2nd ed. (Ch. 2, on tooling that must tolerate broken intermediate states). Applied in §19 (error recovery — a tree must exist for refactoring tools mid-edit).
  • Hopcroft, Motwani, Ullman. Introduction to Automata Theory, Languages, and Computation. Ch. 2–3 (NFA/DFA subset construction). Applied in §15 (lexer DFA generation) and §20 (query-pattern NFA compilation).
  • Cardelli & Wegner (survey chapters in any PL-theory text covering type/grammar soundness). Applied in §8 (grammar-IR validation soundness).

Papers

  • Tomita, 1985/1986. "Efficient Parsing for Natural Language: A Fast Algorithm for Practical Systems." The GLR algorithm and the graph-structured stack. Applied in §16 (Phase 4, GSS push/pop/fork/merge).
  • Wagner & Graham, 1998. "Efficient and Flexible Incremental Parsing." ACM TOPLAS 20(5). The incremental-reparse cursor and subtree-reuse predicate. Applied in §18 (Phase 6, incremental re-parse).
  • Ghezzi & Mandrioli, 1979. "Incremental Parsing." ACM TOPLAS 1(1). Earlier incremental-parsing formalization; the reuse-predicate soundness argument. Applied in §18.3.
  • DeRemer, 1969. "Practical Translators for LR(k) Languages" (PhD thesis, MIT). The LALR construction and its size/power trade-off against canonical LR(1). Applied in §14.1 and ADR-02 (§9).
  • Pager, 1977. "A Practical General Method for Constructing LR(k) Parsers." The Pager-merge compaction algorithm. Applied in §14.4 (Pager merge in detail) and ADR-07.
  • Aho & Ullman, 1972 (foundational LR theory, in "The Theory of Parsing, Translation, and Compiling"). Background for shift/reduce and reduce/reduce conflict formalism. Applied in §14.3.
  • Ford, 2004. "Parsing Expression Grammars: A Recognition-Based Syntactic Foundation." The PEG design; the rejected-alternative rationale. Applied in ADR-02 (§9) and §35 (Alternative Architectures, Roads Not Taken).
  • Earley, 1970. "An Efficient Context-Free Parsing Algorithm." CACM 13(2). The Earley algorithm; the rejected-alternative rationale for constant-factor performance. Applied in ADR-02 and §35.
  • Burke & Fisher, 1987. "A Practical Method for LR and LL Syntactic Error Diagnosis and Recovery." ACM TOPLAS 9(2). The classical single-token insertion/deletion recovery algorithm. Applied in §19 (Phase 7, error recovery).
  • Chase, 1987. "An Improvement to Bottom-up Tree Pattern Matching." Tree-pattern matching background for the query-NFA design. Applied in §20.7 (pattern compilation).

Reference Implementations

  • tree-sitter — github.com/tree-sitter/tree-sitter. Study cli/src/generate/ (the LR(1)/GLR table generator) and lib/src/{parser.c, tree.c, subtree.c, query.c} (the runtime, tree, and query engine). The reference this system's every phase is measured against for cross-engine conformance. Applied in §14, §15, §16 (Phases 2-4, table generation and GLR runtime). Pitfall: its C runtime's manual reference counting is exactly what Rust's ownership model replaces — do not port the refcounting pattern verbatim; port the algorithm, not the memory-management idiom.
  • rust-analyzer, crates/rowan/ — github.com/rust-lang/rust-analyzer. The red/ green tree split this system's §17 (Phase 5) is built from. Applied in §17 (Phase 5). Pitfall: rowan's green tree is untyped (kind IDs only); this system's tree keeps the same discipline — resist the temptation to add typed AST wrappers into the runtime crate itself.
  • Lezer (CodeMirror 6's parser) — github.com/lezer-parser/lezer. A second, independent GLR-adjacent engineering pass on the same problem (incremental, tree- sitter-inspired, browser-first). Applied in §32 (Comparative Architecture) and §35. Pitfall: Lezer's grammar DSL differs from tree-sitter's; do not conflate the two surfaces when reading its source for GLR-table lessons.
  • IntelliJ Platform PSI (intellij-community on GitHub, platform/core-api/src/ com/intellij/psi/) — a red/green-tree-adjacent design (PSI over a lexer-based AST) used at IDE scale. Applied in §32 (Comparative Architecture). Pitfall: PSI's incremental reparse is coarser-grained (block-level) than this system's byte-range reuse; do not assume PSI's granularity is a ceiling.
  • Roslyn (dotnet/roslyn on GitHub, src/Compilers/CSharp/Portable/Syntax/ Internal/) — the original public red/green split (Eric Lippert's design). Applied in §17 (Phase 5) and ADR-04 (§9). Pitfall: Roslyn's red nodes are heavier (carry diagnostics inline); this system keeps diagnostics out of the tree (I7, §7) to keep the red projection cheap to materialize lazily.

RFCs / Specifications

  • tree-sitter grammar DSL reference (tree-sitter.github.io/tree-sitter/creating- parsers). The grammar surface this system's DSL is contractually compatible with (ADR-03, §9). Applied in §13 (Phase 1, grammar DSL).
  • tree-sitter query syntax reference (tree-sitter.github.io/tree-sitter/using- parsers#pattern-matching-with-queries). Applied in §20 (Phase 8, query engine).

Glossary (§37) · 42 terms · site-wide glossary

ADR
Architectural Decision Record; a locked, justified design choice (§9).
Bail (recovery/resync)
The final escalation tier: give up finding a resync point and treat the remainder as a single ERROR node (§19.2).
bumpalo
The Rust arena-allocation crate used for per-parse allocation (ADR-23).
Capture slot
A named binding (@name) recorded during query matching (§20.2).
Closure (LR item sets)
The set of LR items reachable from a kernel item via epsilon-style expansion (§14.2).
Conflict (shift/reduce, reduce/reduce)
A state where the LR table cannot determine a single action; resolved by prec or forked to GLR (§14.2).
CST
Concrete syntax tree; this system's tree retains every token, unlike an AST (§8.2).
DFA
Deterministic finite automaton; the lexer's per-LR-state structure (§15.1).
External scanner
A user-supplied function recognizing context-sensitive tokens the LR-state-aware DFA cannot express alone (§11, ADR-19).
Field
A named child reference declared via field("name", rule) in the grammar DSL (§8.1).
Fork (GLR)
Splitting a parse into parallel branches at an unresolved conflict (§16.2).
Generation counter
A per-Tree counter incremented on edit(), used to detect stale QueryCursor use (I10, §7).
GLR
Generalized LR; the fork-and-merge parsing algorithm (Tomita, §5).
Grammar DSL
The JavaScript-like declarative grammar-authoring surface (§8.1).
Grammar IR
The canonicalized, validated internal representation the DSL lowers to (§8.1, §13.2).
Green tree
The structurally-shared, value-typed, immutable syntax-tree layer (§8.2, §17.2).
GSS
Graph-structured stack; the GLR runtime's core data structure (§16.2).
InputEdit
A byte-range edit descriptor applied to a Tree (§11).
Injection
Embedding a child-language parse inside a parent tree via a query capture pair (§21.2).
Intern (hash-cons)
Deduplicating structurally identical green subtrees to a single allocation (I5, §7).
LALR
Look-Ahead LR; a merged-lookahead approximation of canonical LR(1) (§5, DeRemer 1969).
Lookahead set
The set of terminals that may follow a given LR item (§14.1).
LR(1)
Left-to-right, rightmost-derivation parsing with 1-token lookahead (§14.1).
MISSING node
A synthetic, zero-byte-range node inserted by recovery to stand in for an absent required token (§8.4, §19.2).
NFA
Non-deterministic finite automaton; the query pattern-compilation target (§20.2) and the token-regex intermediate form (§15.2).
Node
A positioned, read-only view into a Tree (§11).
Pager merge
The 1977 LR(1) state-compaction algorithm reducing table size toward LALR while preserving LR(1) precision (§14.4, ADR-07).
Parse-table binary
The versioned, serialized cross-cut artifact between the generator and the runtime (§8.1, I12).
PEG
Parsing expression grammar; a rejected alternative algorithm (§35 Alt-1).
prec/prec.left/prec.right/prec.dynamic
Grammar-DSL precedence annotations resolving shift/reduce and reduce/reduce conflicts (§8.1, §14.3).
Predicate (query)
A post-match filter such as #eq?/#match? (§20.2).
QueryCursor
The stateful, streaming, restartable query-match iterator (§11).
Recovery window
The token budget (default 8) bounding insertion/deletion recovery attempts before escalating (§4, §19.1).
Red tree
The lazily-materialized, positioned, parent-aware projection of the green tree (§8.2, §17.2).
Resync window
The token budget (default 128) bounding incremental-reparse resynchronization before bailing to a full reparse (§4, §18.6).
Reuse predicate
The three-(really four-)condition test determining whether a green subtree can be reused across an edit without re-parsing (§8.2, §18.2).
Soft cap (fork)
The live-branch-count ceiling (64) that warns rather than hard-stops (I4, §7).
Subset construction
The classical NFA-to-DFA conversion algorithm used per LR state (§15.2, Hopcroft/Motwani/Ullman).
Table compaction
Encoding the LR action/goto tables as row-compressed sparse matrices (§14.2, §8.1).
Token disambiguation
Longest-match-then-precedence resolution when multiple terminals match at one input position (ADR-21, §15.2).
TreeCursor
The stateful O(1)-movement tree walker (§11, §17.2).
Wire compatibility
The parse-table binary's cross-version compatibility contract (I12, §26).
