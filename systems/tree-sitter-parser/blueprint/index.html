127 — Tree-Sitter-style Incremental Parser

Project Number: 127

Project Name: Tree-Sitter-style Incremental Parser

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade incremental parsing toolkit in the tree-sitter tradition: a parser generator that compiles a declarative grammar into an LR(1)/GLR parse-table binary, a GLR runtime that executes that table against source bytes using a graph-structured stack (GSS) to fork on ambiguity and merge on convergence, a red/green concrete syntax tree (CST) with byte/point ranges and structural sharing, an incremental re-parse path that reuses unchanged subtrees given an InputEdit and reparses only the affected span in amortized near-constant time, an error-recovery layer (single-token insertion/deletion, N-token skip, ERROR/MISSING node synthesis) so a tree always exists even for malformed source, an external-scanner hook for context-sensitive lexing (indentation, heredocs, raw strings), a tree-query engine (S-expression patterns compiled to an NFA with capture slots and predicates) driving highlighting/folding/symbol extraction/language injection, and a stable C ABI plus WASM package for editor hosts.

Phase-0 deliverable (see §12, Phase 0), numbered modules/crates:

  1. parsekit — public Rust facade (Parser, Tree, Node, TreeCursor).
  2. parsekit-grammar — grammar DSL parser + canonical grammar IR.
  3. parsekit-generator — LR(1) item-set construction, Pager-merge table compaction, GLR fork-instruction emission, parse-table binary encoder.
  4. parsekit-runtime — GLR engine (GSS), mode-switching lexer, red/green tree builder.
  5. parsekit-grammars — vendored reference grammars (JSON at Phase 0; JS/Rust/Python subsets from Phase 1 onward).
  6. parsekit-cli — parsekit compile / parsekit parse developer entry points.

System boundaries. Provides: grammar compilation, GLR parsing, incremental re-parse, error recovery, tree queries, a stable C ABI, WASM packaging. Delegates: text storage / rope management (the embedder owns the source buffer; §8 documents the byte-range contract), syntax highlighting theme mapping (the toolkit emits token classes, not colors), LSP transport (examples/lsp-shim is a demo, not a shipped server). Does not provide: a general-purpose regex engine for the lexer (token regexes compile to NFAs at generation time, §10 ADR-22), semantic analysis / type checking, a package manager for grammars (PhaseDeferred("§36")), streaming parse for files above 1 GB (PhaseDeferred("§36")).

Non-goals. Not a compiler front end (no code generation, no semantic passes beyond what a query can express); not a general string-processing library; not a drop-in binary replacement for libtree-sitter (ABI-compatible subset only, §22 Phase 10).

Deployment model. A linkable Rust library (cdylib/rlib) embedded in editors, CLIs, and CI tools; a cdylib C ABI for non-Rust hosts (Neovim, Emacs); a wasm32 build for browser/VS Code hosts. No network service, no daemon — parsing is in-process and synchronous per call.

Target users/operators. Editor and IDE integrators (Neovim, VS Code, Helix maintainers), static-analysis and code-search platform engineers, language-tooling authors who need a grammar compiled once and executed millions of times per day.

Language + rationale. Rust (2021 edition floor; ADR-01, §9). Rationale: the runtime is parse-table-driven and safety-critical on untrusted input (a malformed source file must never corrupt memory); Rust gives memory safety without a GC pause budget, and the runtime crate can be built no_std-able for WASM/embedded hosts. Rejected: C (the reference implementation's own use-after-free CVE history is the concrete counter- example), C++ (equivalent risk, worse dependency-hygiene story for a cdylib), Go (GC pauses interact badly with a keystroke-latency budget of low single-digit milliseconds), Zig (immature crates.io-equivalent ecosystem for the fuzzing/property- testing tooling this project depends on).

Prerequisites. LR parsing theory (shift-reduce, item sets, conflicts), formal language theory (CFGs, ambiguity), amortized-analysis reasoning, arena/interning allocation patterns, DFA/NFA construction, and enough production-editor experience to know what "fast enough to not drop a keystroke" means operationally.

Timeline. Phase 0 (repo skeleton + hand-table "hello parser" correctness kernel): 1 week. Full system (Phases 0–10, §12–§22): 21–25 weeks (~5–6 months) at one senior engineer, per the milestone table in Appendix B.

Deferred features, each flagged with its Deferred Features Register anchor (§36): full non-reference grammars (Go, TypeScript, C++, SQL) PhaseDeferred("§36"); streaming parse for files >1 GB PhaseDeferred("§36"); multi-threaded per-file parallel parse PhaseDeferred("§36"); incremental (subtree-scoped) query re-evaluation PhaseDeferred("§36"); OSS-Fuzz continuous integration PhaseDeferred("§22"); grammar live-reload for grammar authors PhaseDeferred("§36"); a parsekit-grammars package registry PhaseDeferred("§36"); WASM component-model packaging PhaseDeferred("§36"); stack graphs for cross-file name resolution PhaseDeferred("§36").

2. Why Build This

  • Teaches the full LR/GLR theory stack in one system: item-set construction, shift/reduce and reduce/reduce conflict resolution, the Pager compaction algorithm, and Tomita's graph-structured stack — the four ideas that separate "a parser" from "an editor-grade parser."
  • Teaches the red/green tree split, the same architecture Roslyn and rust-analyzer's rowan independently converged on, and the concrete bug class (structural-sharing loss, parent-pointer cycles) that appears when it is conflated.
  • Teaches incremental algorithms under a hard latency budget — not "make it faster" but "prove the amortized bound and gate it in CI," the discipline every low-latency editor subsystem needs (LSP servers, live type checkers, hot-reload build systems).
  • Teaches error-recovery engineering, a discipline almost absent from academic compiler courses but load-bearing for every tool that must be useful on the 40% of keystrokes where the file is momentarily invalid.
  • Cross-links by name: shares its GSS/table-compaction lineage with any LALR-based build-system parser; shares its red/green tree lineage with any IDE/refactoring engine project in this portfolio; shares its query-NFA-with-captures design with any structural code-search project; shares its C-ABI/WASM packaging concerns with any editor-plugin or sandboxed-runtime project in the portfolio.
  • Calibration value: this is one of the few systems where "correct" and "fast enough to not drop a keystroke" are both hard, both measurable, and both gated — a rare combination that calibrates an engineer's sense of what "production-grade" costs.

What Mastery Looks Like (after building this, the engineer can, unaided):

  1. Derive an LR(1) item-set automaton for a small grammar by hand and explain why the Pager merge shrinks it toward LALR size — demonstrated in Phase 2 (§14).
  2. Trace a GLR fork-and-merge sequence for an ambiguous input and explain why the branch count stays bounded on real grammars — demonstrated in Phase 4 (§16).
  3. Explain, with a byte-offset diagram, why conflating red and green tree layers reintroduces the Roslyn-era bug class — demonstrated in Phase 5 (§17).
  4. Prove the O(edit size + resync window) bound for incremental re-parse and name the exact predicate that makes a subtree reusable — demonstrated in Phase 6 (§18).
  5. Design an error-recovery policy that trades recovery quality against worst-case latency and justify the trade with a number — demonstrated in Phase 7 (§19).
  6. Compile an S-expression query to an NFA with capture slots and explain the streaming-cursor restart contract — demonstrated in Phase 8 (§20).
  7. Explain exactly which cross-engine conformance signal would catch a silent GLR regression before it reaches an editor's keystroke path — demonstrated in Phase 10 (§22).

Embedder box. The only two calls an editor makes on the hot path: parse (cold or warm with old_tree) and Tree::edit to pre-adjust offsets before a re-parse; every other API is read-only against an immutable Tree.

Grammar pipeline box. Runs once per grammar, offline, never on the hot path. Its sole output is the parse-table binary (§11 ParseTable); the runtime never sees the DSL or the IR. This is ADR-05's cross-cut: generator and runtime share zero code.

Runtime parser box. The lexer is not a standalone stage — it runs per active LR state (§16.7), because a byte sequence can lex to different tokens depending on parser state (the < example, §16.7). The GLR engine's GSS is the box's core data structure (I3, §7). The incremental cursor and error recovery both operate inside this box, on the same GSS, because a resync after a re-parse or a recovery is structurally the same operation: find a state to resume normal shifting from.

Syntax tree box. Trust boundary for the "no code" separation of concerns: the green tree owns structural sharing (I5, §7); the red tree owns position. This is the box P5 (§6) and ADR-04 (§9) protect — conflating the two layers is the single most-cited architectural regression in this class of system (Roslyn's early years, cited in §24 Failure Modes & Recovery, FM-4).

Query engine box. Consumes only the red tree's read-only surface (Node, TreeCursor); it never mutates a tree. Concurrency boundary: a QueryCursor is !Send across a tree edit — using one after Tree::edit is a documented panic (I11, §7), not undefined behavior.

Front-ends and editor-integration boxes. Pure consumers of the query engine; they carry no parsing logic of their own. The C ABI is the only place unsafe Rust appears outside the arena allocator (§29); it is reviewed and fuzzed as its own surface (fuzz target c_abi_roundtrip, §22.5).

All later sections stay consistent with this diagram; a component not shown here does not exist in this system (per I14, §7, "no undocumented subsystem").

6. Design Principles

  1. P1 — GLR is the parsing algorithm. LR(1) with GLR fork-on-conflict; PEG, Packrat, Earley, and Pratt-only are rejected (ADR-02, §9). Tradeoff: GLR's worst-case branch count is exponential in theory; operationally bounded by the soft fork cap (§4) and the Pager merge (P7). Violating this (e.g., silently falling back to backtracking) reintroduces PEG's unbounded-worst-case failure mode.
  2. P2 — The grammar pipeline is offline; the runtime is table-only. The generator and runtime crates share zero code (ADR-05, §9). Tradeoff: a grammar change always requires recompilation, never hot-patching. Violating this (embedding DSL evaluation in the runtime) reopens the runtime's attack surface to arbitrary grammar code.
  3. P3 — Syntax trees are red/green. Green: value-typed, structurally shared, immutable (I5, §7). Red: positioned, parent-aware, lazily materialized. Tradeoff: two allocation regimes to reason about instead of one. Violating this (a single positioned, shared tree) reopens the Roslyn-era architectural bug (FM-4, §24).
  4. P4 — Incremental re-parse is the contract, not an optimization. The public API is parse(text, old_tree); the non-incremental path exists only for cold starts. Tradeoff: every phase after Phase 5 must preserve the reuse predicate (§18.3), which constrains implementation choices elsewhere (e.g., error recovery must serialize external-scanner state, §15.3). Violating this turns every keystroke into a full re-parse — the exact failure this system exists to prevent.
  5. P5 — Error recovery always produces a tree. No parse path returns Err for malformed source (I7, §7); it returns a tree with ERROR/MISSING nodes. Tradeoff: downstream consumers (queries, highlighters) must explicitly tolerate synthetic nodes. Violating this (bailing to Option::None) breaks every front-end that must keep functioning on a mid-edit file.
  6. P6 — Lexing is a function of parser state, not a standalone stage. A DFA is generated per LR state (§15.1); token disambiguation is LR-state-aware. Tradeoff: more DFA tables to generate and cache; solves context-sensitive lexical ambiguity (< as operator vs. type-parameter opener, §15.6) without a separate parser pass.
  7. P7 — LR(1) tables are Pager-compacted before serialization. ADR-07 (§9). Tradeoff: an extra generation-time pass (§14.4); without it, real-world grammar tables are 5–10× larger, which blows the WASM bundle-size budget (§4).
  8. P8 — Queries are an S-expression DSL compiled to an NFA with capture slots. Surface-compatible with tree-sitter's query language (ADR-03, §9). Tradeoff: no general-purpose scripting inside a query; violating this (allowing embedded arbitrary code) reopens an injection attack surface in editor plugins that load community-authored queries.
  9. P9 — No global mutable state. Parser, Language, Tree are values (I9, §7). Tradeoff: every call site must thread state explicitly; the payoff is that multiple parsers/languages coexist safely in one process with no synchronization.
  10. P10 — The C ABI is a stable, versioned, binary-compatible subset of tree-sitter's. ADR-10 (§9). Tradeoff: the ABI surface is frozen once published (§26); an embedder depending on today's tree-sitter can port with a header swap.
  11. P11 — WASM is a first-class packaging target, not an afterthought. ADR-11 (§9). Tradeoff: every dependency added to parsekit-runtime is scrutinized for its wasm32 footprint (§4 WASM bundle-size row); pulls in wee_alloc instead of the system allocator.
  12. P12 — Determinism is the default. A given (grammar, input) pair produces a byte-identical tree across builds and hosts (I2, §7). Tradeoff: ambiguity resolution (prec.dynamic) must be deterministic tie-breaking, never "first thread to finish."
  13. P13 — The runtime is allocation-tight on the hot path. Per-token GLR steps are allocation-free in steady state; tree-node construction is the only per-node allocation, from a bumpalo arena (ADR-23, §9). Tradeoff: arena lifetime management adds a class of "dangling across Tree::edit" bugs that the API's ownership model must close off (I6, §7).
  14. P14 — Every public panic path is documented and exists only on contract violation. No Box<dyn Error> in public signatures (§11); errors are typed enums. Tradeoff: more enum variants to maintain; the payoff is that an embedder can match exhaustively and never unwrap() a surprise.

8. Domain Model

8.1 Grammar IR and parse-table schema

The grammar DSL (a JS-like declarative surface: seq, choice, repeat, repeat1, optional, prec/prec.left/prec.right/prec.dynamic, token, token.immediate, alias, field, named externals) lowers to a canonical IR: optional(a) becomes choice([a, ε]); repeat(a) becomes a fresh non-terminal R -> a R | ε; repeat1(a) becomes R -> a R | a. The IR is the only representation the generator (§14) consumes.

ParseTable {
  magic: u32,                     // I12: version-checked on load
  version: u16,
  grammar_name: str,
  states: [LrState],              // indexed by state id
  action: SparseMatrix<Action>,   // [state][terminal] -> Action
  goto: SparseMatrix<StateId>,    // [state][nonterminal] -> StateId
  lexer_dfas: [LexerDfa],         // one per state (§15.1)
  field_names: [str],             // interned field-name table
  node_kinds: [str],               // interned kind table
  externals: [ExternalDecl],
}

Action = Shift(StateId)
       | Reduce(RuleId, arity: u16, kind: NodeKindId)
       | Fork([Action])           // GLR fork instruction (§16.3)
       | Accept
       | Error

8.2 Concrete syntax tree schema (subtree reuse)

GreenNode {
  kind: NodeKindId,
  byte_length: u32,
  child_count: u16,
  named_child_count: u16,
  field_bits: BitSet,            // which children are field-bearing
  children: [Interned<GreenNode>],
}

RedNode<'tree> {
  green: &'tree GreenNode,
  parent: Option<&'tree RedNode<'tree>>,
  byte_offset: u32,
  parent_child_index: u16,
}

A green subtree is reusable across an edit iff (Wagner & Graham, §5): (a) its byte range lies wholly outside the edited range, (b) its kind is a valid instance of the non-terminal expected at the incremental cursor's current LR state, and (c) the token immediately following the subtree is a valid shift in that state. Failing any predicate forces re-parse of that subtree (§18.3).

8.3 Incremental edit worked example

Source let x = 1 + 2; parses to a tree rooted at let_decl with children [ "let", identifier("x"), "=", binary_expr(1, "+", 2), ";" ]. Applying InputEdit{ start_byte: 12, old_end_byte: 13, new_end_byte: 13 } (replacing 2 with 3) — the incremental cursor walks the old tree: let_decl's range overlaps the edit, so it descends; identifier("x") and "=" are wholly before the edit and are reused verbatim (zero re-parse cost); binary_expr's range overlaps, so it descends into it; 1 and "+" are before the edit and reused; the literal 2 is inside the edit and is re-lexed to 3; the reduce that built binary_expr re-fires with the new leaf; ";" is after the edit and is byte-shifted (offset += 0, since old/new end bytes are equal) and reused without re-lexing. Total re-parse work: one leaf re-lex plus one reduce — O(1) independent of source size, matching the M2 gate (§4).

8.4 Malformed-input example

Source let x = ; (missing right-hand-side expression). The LR state after = expects a expression non-terminal's first-set token; ; is not in that set. Recovery (§19.1) attempts single-token insertion: inserting a synthetic identifier (a plausible first-set token) lets the parser shift past it and successfully reduce let_decl; the inserted node is marked MISSING with a zero-byte range at offset 8. The resulting tree has structurally valid shape (let_decl with a MISSING identifier child) even though the source is invalid — satisfying I7 (§7) and giving the highlighter and outline view a tree to render around the error.

8.5 Failure-path example

Source containing an unterminated string literal followed by 40 more lines of otherwise valid code. The lexer's DFA for the string-literal token never reaches an accept state before EOF; insertion/deletion recovery (§19.1–19.2) cannot resolve a lexical (not grammatical) failure, so the N-token skip (§19.6 step 3) consumes tokens until a resynchronizing token (a statement terminator or a token that starts a new top-level declaration) is found; if none is found within the 16-token bail window (§4), the remainder of the file becomes a single ERROR node. The highlighter (§21.1) still renders the 40 lines as an opaque ERROR span rather than crashing or losing the whole buffer's highlighting — the concrete cost of P5 (§6) paid off.

11. Core Schema & Types

All types below are signatures only (no bodies), living in crates/parsekit/src/ per §10. Ownership/mutation/concurrency/persistence/serialization annotations follow each.

  • Parser — opaque value type. fn new() -> Self; fn set_language(&mut self, lang: &Language); fn parse(&mut self, text: &[u8], old_tree: Option<&Tree>) -> Tree; fn set_timeout(&mut self, d: Duration). Owns no shared state; !Sync, Send; not persisted; no serialization surface.
  • Language — opaque, Clone (cheap, Arc-backed), Send + Sync. fn load(bytes: &[u8]) -> Result<Self, LanguageError>. Immutable after load (I1, §7); the table bytes are the serialization format (versioned, I12).
  • Tree — immutable value, Clone (cheap, structural sharing via green-tree interning). fn root_node(&self) -> Node<'_>; fn edit(&self, edit: &InputEdit) -> Tree; fn language(&self) -> Language. Carries a generation counter (I10).
  • Node<'tree> — borrowed, positioned view, lifetime-bound to its Tree (I6). fn kind(&self) -> &'static str; fn kind_id(&self) -> u16; fn child_count(&self) -> usize; fn child(&self, i: usize) -> Option<Node<'tree>>; fn child_by_field_name(&self, name: &str) -> Option<Node<'tree>>; fn start_byte(&self) -> u32; fn end_byte(&self) -> u32; fn start_point(&self) -> Point; fn parent(&self) -> Option<Node<'tree>>; fn next_sibling(&self) -> Option<Node<'tree>>; fn is_error(&self) -> bool; fn is_missing(&self) -> bool; fn text<'s>(&self, source: &'s [u8]) -> &'s [u8].
  • TreeCursor<'tree> — stateful walker, owns a stack of (Node<'tree>, usize). fn goto_first_child(&mut self) -> bool; fn goto_next_sibling(&mut self) -> bool; fn goto_parent(&mut self) -> bool; fn current_node(&self) -> Node<'tree>; fn current_field_name(&self) -> Option<&'static str>.
  • InputEdit — plain data, Copy. Fields: start_byte: u32, old_end_byte: u32, new_end_byte: u32, start_point: Point, old_end_point: Point, new_end_point: Point. Constructor validates I8 (monotonic, non-overlapping).
  • Point — Copy, Eq, Ord. Fields: row: u32, column: u32.
  • Query — opaque, immutable after construction. fn new(lang: &Language, pattern: &str) -> Result<Self, QueryError>. Carries the compiled pattern NFA (§20.2).
  • QueryCursor<'q, 'tree> — stateful, generation-checked against its Tree (I10). fn matches(&mut self, query: &'q Query, node: Node<'tree>, source: &[u8]) -> impl Iterator<Item = QueryMatch<'tree>>; fn set_byte_range(&mut self, range: Range<u32>).
  • QueryMatch<'tree> — data. Fields: pattern_index: u16, captures: Vec<QueryCapture <'tree>>.
  • QueryCapture<'tree> — data. Fields: node: Node<'tree>, capture_index: u16.
  • LanguageError — typed enum: InvalidTableVersion { found: u16, expected: u16 }, InvalidLanguage, IncompatibleAbi. #[non_exhaustive]; no Box<dyn Error> (P14).

13. Phase 1 — Grammar DSL & IR

13.1 Objectives

Implement the grammar DSL parser and the canonical grammar IR lowering (§8.1) in parsekit-grammar. Compile the four reference grammars (JSON, JavaScript-subset, Rust-subset, Python-subset) to validated IR. No LR table generation yet (Phase 2).

13.2 Detailed Implementation Steps

dsl::parser hand-rolls a recursive-descent parser over the JS-like DSL subset (P2, §6 — no embedded JS engine, whitelist-only grammar-definition surface). dsl::ast defines the untyped AST. ir::grammar lowers the AST per §8.1's canonicalization rules (optional → choice([a, ε]), repeat/repeat1 → fresh non-terminals). validate.rs enforces: every referenced rule resolves; no left-recursive cycle without a prec annotation (ADR-02's GLR-fork-safety precondition); every field position is unambiguous; every externals entry has a corresponding scanner declaration (ADR-19). Citations applied: Aho/Sethi/Ullman Ch. 4 grammar-normalization discipline (§5); Ford 2004's PEG-vs-CFG ambiguity framing informs why choice ambiguity is deferred to the generator (P1), not resolved at IR time.

13.3 Deliverable

parsekit-grammar compiles the four reference grammars' .js DSL sources (crates/parsekit-grammars/{json,javascript-subset,rust-subset,python-subset}/ grammar.js) to a snapshot-tested IR with zero validation errors.

13.4 Acceptance Criteria

All four reference grammars compile to IR in < 200ms each (single-threaded, reference host, §4); the IR snapshot tests (insta-style) are byte-identical across two consecutive runs (I2, determinism); the validator rejects 12 seeded malformed grammar fixtures (§13.5) with typed, span-located errors — zero false negatives.

13.5 Conformance Fixtures

grammar-dsl/json.js → valid IR, 6 rules. grammar-dsl/left_recursion_no_prec.js → Err(UnresolvedLeftRecursion). grammar-dsl/dangling_rule_ref.js → Err (UnresolvedRuleName). grammar-dsl/external_no_scanner.js → Err (MissingExternalScanner). grammar-dsl/ambiguous_field.js → validator warning (non-fatal), snapshot-tested.

13.6 Pitfalls

  • Allowing arbitrary JS constructs to leak through the whitelist parser — the DSL parser must reject, not silently ignore, unrecognized JS syntax.
  • Treating prec on a non-binary alternation as valid — the validator must flag this common grammar-author mistake (rule N.2, ADR-21 longest-match discipline depends on correctly-scoped precedence).
  • alias applied to a bare terminal literal — legal but rarely intentional; documented, not rejected.

13.7 Performance Concerns

IR lowering allocates one Vec per rule; for grammars with hundreds of rules (e.g. a future full JavaScript grammar, PhaseDeferred("§36")), this is revisited with an arena allocator matching P13's runtime discipline — deferred until Phase-1 profiling shows it matters (no premature optimization at generation time, which is off the hot path per §3).

13.8 Edge Cases

A grammar with zero rules (Err(EmptyGrammar)); a grammar whose start rule is never referenced by any other rule but is also not the declared entry point (validator warning); a token.immediate used outside any token context (Err (InvalidImmediateContext)); Unicode identifiers in rule names (accepted, normalized to NFC).

13.9 Failure Analysis

A validation false-negative (an invalid grammar silently accepted) surfaces downstream as a Phase-2 generator panic or an unbounded LR state count — containment: the Phase-2 generator has its own state-count cap (§4) as a second line of defense. Detection: the generator's cap-exceeded error names the offending rule.

13.10 Operational Notes

14. Phase 2 — LR(1) Table Generator

14.1 Objectives

Build the canonical LR(1) automaton from the grammar IR, detect shift/reduce and reduce/reduce conflicts, resolve what prec/prec.left/prec.right can resolve, and compact the table via the Pager merge (P7, ADR-07).

14.2 Detailed Implementation Steps

lr::item implements the LR(1) item [A -> α • β, a] (Aho/Sethi/Ullman Ch. 4, §5). lr::build computes closure and goto to construct the canonical automaton (DeRemer 1969's LALR contrast informs why canonical LR(1) is built first, then compacted, rather than built LALR-first and losing precision, ADR-07). lr::conflicts classifies shift/reduce conflicts (resolved via prec/prec.left/prec.right, P1) and reduce/reduce conflicts (resolved via prec.dynamic, deferred to runtime, ADR-02). Unresolved conflicts emit a GLR fork instruction (glr::fork) consumed by Phase 4's runtime. lr::pager implements the Pager (1977) merge: group states by LR(0) core, pairwise-test lookahead-set compatibility (no reduce-reduce conflict introduced that did not exist separately), merge compatible pairs, iterate to fixpoint (I4's fork-cap enforcement begins here — the generator warns at compile time when a grammar produces unresolved forks). table::encode serializes to the ParseTable binary (§8.1), row-compressed sparse matrices for action/goto (M8 gate, §4).

14.3 Deliverable

The four reference grammars produce ParseTable binaries; JSON's table is conflict-free and < 50 KB; the Rust-subset table's residual conflicts are covered entirely by bounded GLR forks (no unresolved-conflict compile warning above the I4 soft cap).

14.4 Acceptance Criteria

JSON table size < 50 KB (M8); table generation for the Rust-subset grammar completes in < 2 s on the reference host; the Pager merge reduces state count by ≥ 60% versus canonical LR(1) on the Rust-subset grammar (measured and asserted in pager_merge_reduction_test); regenerating from the same IR twice produces byte-identical tables (I2).

14.5 Conformance Fixtures

lr-tables/json.grammar → table, zero conflicts. lr-tables/dangling_else.grammar (the classic shift/reduce ambiguity fixture) → resolved via prec, zero residual forks. lr-tables/genuinely_ambiguous.grammar → residual GLR fork, snapshot-tested fork count. lr-tables/pathological_state_blowup.grammar → generator error StateCountExceeded (malformed/adversarial-input regression case).

14.6 Pitfalls

  • Skipping the Pager merge "to ship faster" — canonical LR(1) tables for real grammars are 5–10× larger (§14.4), directly blowing the WASM budget (§4).
  • Forking on every shift/reduce conflict instead of resolving with prec — correct but slow (P1's tradeoff clause); the generator's compile-time fork-count warning exists precisely to catch grammar authors doing this by accident.
  • The Pager compatibility test producing a phantom reduce-reduce conflict on a subtle lookahead-set interaction — the pairwise compatibility test (§8) is the documented safety net; any merge failing it is left unmerged, never forced.

14.7 Performance Concerns

Table generation is O(states × terminals) for closure computation; the reference host budget is 2 s for the Rust-subset grammar (§14.4). The Pager merge's pairwise compatibility test is the dominant cost for large grammars; profiled and gated in CI (perf.yml, §10) against a stored baseline, failing the build on > 20% regression.

14.8 Edge Cases

A grammar with a rule that can derive the empty string in every alternative (infinite ambiguity) — rejected at validation (Phase 1) before reaching the generator. A grammar whose canonical LR(1) automaton exceeds the state-count cap (default 100,000 states) — StateCountExceeded, a defense-in-depth backstop for a Phase-1 validation gap (§13.9). A grammar with prec.dynamic on every alternative of a rule (maximal ambiguity deferral) — accepted, but the compile-time warning fires at maximum verbosity.

14.9 Failure Analysis

A miscompiled table (a subtle closure-computation bug) manifests downstream as either a silent wrong-parse (caught by conformance corpus diffing against upstream tree-sitter, §27) or a GLR engine's "no valid action" dead end (caught by I7's recovery fallback, which produces an ERROR tree rather than a panic — but that itself signals a generator bug, tracked via tracing event generator.suspected_bug when recovery fires on a grammar with no genuinely malformed input in the corpus).

14.10 Operational Notes

parsekit-cli compile grammar.js -o lang.bin --emit-conflicts prints every unresolved conflict and its GLR-fork site for grammar authors to inspect; --stats prints pre/post-Pager-merge state counts for the ADR-07 tradeoff to be visible per grammar.

15. Phase 3 — Lexer DFA Generation & External Scanners

15.1 Objectives

For each LR state, generate a DFA over the terminals shiftable in that state (P6, §6); implement the external-scanner hook (ADR-19) for context-sensitive tokens.

15.2 Detailed Implementation Steps

lex::regex_ir compiles token-pattern regex literals to NFAs (Hopcroft/Motwani/Ullman Ch. 2–3, §5); lex::dfa unions per-state terminal NFAs and applies subset construction to produce one DFA per LR state, deduplicating identical sub-DFAs across states (cache locality goal, §29). lex::conflicts implements ADR-21's longest-match-then- precedence disambiguation. The ExternalScanner trait (§11) is wired into runtime::lex::external: scan runs before the generated DFA at states listing an externals entry; serialize/deserialize round-trip the scanner's state across an incremental boundary (I11, feeding Phase 6's reuse predicate, P4).

15.3 Deliverable

The JSON grammar's lexer tokenizes a 50 MB JSON corpus with zero misclassified tokens; a hand-written external scanner for Python-style indentation tokens (INDENT/DEDENT) passes its round-trip serialization property test.

15.4 Acceptance Criteria

Lexer throughput ≥ 200 MB/s on the JSON corpus (reference host, single core); the external-scanner round-trip property test (proptest, ADR-13) passes 10,000 random scanner-state sequences with zero serialization mismatches; token disambiguation matches upstream tree-sitter byte-for-byte on the queries/token-disambiguation conformance bucket (100% match required, no tolerance).

15.5 Conformance Fixtures

lr-tables/lexer/json_50mb.txt → zero misclassified tokens. lexer/type_param_vs_lt.rs — the Vec<T> vs a < b disambiguation fixture exercising §15.6's LR-state-aware lexing. lexer/python_indent.py — external-scanner INDENT/DEDENT round-trip fixture. lexer/heredoc.rb-style fixture for a second external-scanner shape (context-sensitive delimiter matching).

15.6 Pitfalls

  • Treating the lexer as a standalone stage decoupled from LR state — reintroduces the < ambiguity bug class this design exists to avoid (P6).
  • An external scanner that consumes input but emits no token — the runtime's "no progress" detector (§15.7 in the original draft, now enforced via a per-scan token-emission assertion) must bail rather than hang.
  • Two external scanners recognizing an overlapping prefix with no declared preference — a grammar-authoring error the validator (Phase 1) should have caught; the runtime treats it as a nondeterminism bug (I2 violation) if it reaches this phase undetected.

15.7 Performance Concerns

Per-LR-state DFA memoization at each input byte offset avoids quadratic re-lexing during a GLR fork with many simultaneously active states (§16.8); the memo table is reset per parse (arena-scoped, P13).

15.8 Edge Cases

A token regex matching the empty string (rejected at Phase-1 validation, defense-in- depth re-check here); a source byte sequence matching two terminals at the identical length with equal declared precedence (nondeterminism — flagged as a generator warning, must not silently pick arbitrarily, I2); an external scanner invoked at EOF (must return false cleanly, not read past the buffer — fuzzed by fuzz/grammar_compile.rs and a dedicated scanner-boundary fixture).

15.9 Failure Analysis

A lexer DFA bug manifests as either a wrong-token misclassification (caught by cross-engine conformance, §27) or an external-scanner panic (caught by the FFI shim, ADR-19, which converts a Rust panic at the scanner boundary into a typed parse error rather than propagating unwind across the C ABI boundary in Phase 10).

15.10 Operational Notes

tracing event lexer.dfa_cache_hit_rate surfaces per-state DFA dedup effectiveness; the slow-parse.md runbook (§10) documents diagnosing a lexer-bound slowdown via this metric before assuming the GLR engine is the bottleneck.

16. Phase 4 — GLR Runtime Engine

16.1 Objectives

Implement the graph-structured stack (GSS, I3) and the per-token GLR step: push (shift), pop (reduce), fork (conflict), merge (convergence) — Tomita's algorithm (§5) executed against the Phase-2/3 generated tables.

16.2 Detailed Implementation Steps

glr::stack implements the GSS as a DAG of (lr_state, tree_node) nodes with reference-counted edges (ADR-24). glr::step executes one input token against every live stack top: shift pushes a new top with a new green leaf (via runtime::tree:: builder); reduce pops N states and constructs a green internal node; a shift/reduce or reduce/reduce conflict (per the Fork action, §8.1) forks into parallel tops sharing the same predecessor. glr::merge coalesces stack tops sharing (lr_state, predecessor) — the operation that keeps branch count bounded (I4) on real grammars, per Tomita's central insight (§5). Lexing is invoked per active LR state (P6); §15.7's per-position memoization prevents quadratic re-lexing across fork branches. Ambiguity at accept: prec.dynamic accumulation picks a winner (P12 determinism); a genuine tie is a typed AmbiguousParse diagnostic in strict mode or a deterministic first-branch pick in tolerant mode (ADR-02's ambiguity-resolution tradeoff).

16.3 Deliverable

The JSON parser produces trees byte-identical to upstream tree-sitter on a 50 MB corpus; the Rust-subset parser passes the parse-trees/rust-subset conformance bucket at ≥ 99%.

16.4 Acceptance Criteria

Cross-engine determinism corpus (§27) passes ≥ 95% overall, 100% on the JSON bucket (M1, §29); cold-parse throughput ≥ 25 MB/s on the Rust-subset grammar (M4, §4); live branch count never exceeds 64 without a logged glr.fork_cap_warning event (I4) across the full conformance corpus.

16.5 Conformance Fixtures

parse-trees/json_50mb.txt → byte-identical to upstream. parse-trees/ ambiguous_dangling_else.rs-style fixture → deterministic tie-break, snapshot-tested. parse-trees/deep_fork_no_merge.grammar+input — a deliberately pathological fixture exercising the I4 soft-cap warning path. parse-trees/malformed_utf8.bin — replay fixture ensuring non-UTF8 byte sequences never panic the lexer/GLR boundary.

16.6 Pitfalls

  • Getting the GSS merge step wrong — the single hardest correctness surface in this system; the conformance corpus (§27) is the only reliable safety net, not code review alone.
  • Merging branches with different prec.dynamic accumulations — this silently discards the ambiguity-resolution signal (P12 violation); merge must compare accumulated dynamic precedence before coalescing.
  • Long fork sequences with no merges — a performance pathology (§16.7); the generator's compile-time warning (§14.10) is the first line of defense, the I4 runtime cap the second.
  • External scanners mutating state visible outside their own scan call — breaks the GLR contract that branches are independently replayable (ADR-19's determinism requirement).

16.7 Performance Concerns

The GSS's fork/merge pair is what keeps this system sub-cubic in practice despite GLR's theoretical exponential worst case (Tomita, §5): real grammars converge to a small constant number of live branches because merges collapse equivalent parses quickly. The per-token step is allocation-free except for tree-node construction (P13); the bumpalo arena (ADR-23) makes that single allocation a bump-pointer increment.

16.8 Edge Cases

A fork where every branch eventually dies (fails to shift) with no accept state reached — this is a parse-error condition, handed to Phase 7's recovery (§19), not a GLR-engine panic. A grammar producing unbounded forks with no merges ever (a pathological, likely mis-authored grammar) — bounded by I4's soft cap; the parse continues with a warning rather than exhausting memory. A 10-deep fork on a 1 MB file without lexer memoization — quadratic blowup; §15.7's per-position memo is the required mitigation, verified by a dedicated benchmark (bench_huge_file.rs, §10).

16.9 Failure Analysis

A GSS correctness bug's blast radius is total (wrong trees for any grammar exercising the buggy path) but detection is fast: the cross-engine conformance diff (§27) catches divergence from upstream tree-sitter on the very next CI run. Forensic artifact: the tracing span tree for the failing parse (RUST_LOG=parsekit=trace) reconstructs the exact fork/merge sequence for post-mortem replay.

16.10 Operational Notes

tracing events glr.fork, glr.merge, glr.branch_count at debug level; the parse-conflict.md runbook (§10) documents reading a fork/merge trace to diagnose an unexpectedly slow parse traced to excessive forking on a specific grammar rule.

17. Phase 5 — Red/Green Syntax Tree

17.1 Objectives

Implement the green tree (interned, value-typed, arena-allocated) and the red tree (lazy, positioned, parent-aware projection) per §8.2 and ADR-04; implement TreeCursor (P3, §6).

17.2 Detailed Implementation Steps

tree::green implements GreenNode (§8.2) with a hash-cons intern table keyed (kind_id, children_hash) using FxHash (I5); tree::builder constructs green nodes during GLR shift/reduce, allocating from the per-parse bumpalo arena (P13, ADR-23). tree::red implements RedNode<'tree> (§8.2), materialized lazily on Node::child access — the Roslyn/Rowan precedent (§5 Reference Implementations) applied directly: only the path from root to a visited node is materialized eagerly; siblings are constructed on first visit. tree::walker implements TreeCursor as a stack of (RedNode, child_index) pairs with O(1) goto_first_child/goto_next_sibling/ goto_parent (P3's operational implication). Field accessors consult the green node's field_bits bitset against the Language's interned field-name table (§11).

17.3 Deliverable

A 1 MB source file produces a green tree with < 5 MB total allocation (M6, §4); two trees from adjacent non-overlapping edits share ≥ 95% of green-tree storage (measured via arena byte-accounting in bench_incremental.rs).

17.4 Acceptance Criteria

Green-tree memory ≤ 5 bytes per source byte on the four reference-grammar corpora (M6); intern-table hit rate ≥ 70% on the Rust-subset 1 MB corpus (tree.intern_hit_rate telemetry, I5); red-node first-visit latency ≤ O(depth) verified via a depth- parameterized benchmark asserting linear (not superlinear) scaling.

17.5 Conformance Fixtures

incremental/green_tree_sharing_1mb.rs — asserts ≥ 95% storage sharing across one localized edit. incremental/intern_hit_rate_rust_subset.rs — asserts the 70% hit-rate floor. parse-trees/field_accessor_roundtrip.json — every field()-declared child in the JSON grammar resolves correctly via child_by_field_name.

17.6 Pitfalls

  • Forgetting to intern structurally identical subtrees — direct memory-bound violation (M6); caught by the intern-hit-rate CI gate (§17.4).
  • A red node holding an Rc/Arc-cycle to its parent — creates a leak; the parent link is a borrowed reference bound by 'tree, never a strong-counted cycle (I6).
  • Omitting the kind_id from the intern hash function — two structurally identical trees of different kinds would collide, corrupting the green tree (a correctness bug, not just a performance one).
  • Assuming red-tree materialization is free — the first visit to a deeply nested node is O(depth); this is a documented, not hidden, cost (§17.4's benchmark makes it visible).

17.7 Performance Concerns

The intern table's hash function (FxHash) is chosen for speed over cryptographic quality — collision risk is bounded and measured (§29); an editor walking the visible viewport once per frame pays the O(depth) red-materialization cost once per session per path, then O(1) thereafter — the runtime pre-warms the viewport path on each tree commit to amortize this (§21.1's highlight driver depends on this).

17.8 Edge Cases

A tree with a single root leaf (degenerate one-token input); a tree deep enough that red-node materialization's O(depth) cost becomes visible (>500 nesting levels — a pathological-input fuzz target, parser_runtime.rs); a cursor held across a Tree::edit call — must panic deterministically (I10), never silently return stale data.

17.9 Failure Analysis

A missing-intern bug manifests as unbounded memory growth under repeated incremental edits — detected by the bench_incremental.rs memory-ceiling assertion in CI, not just by manual profiling. A red-tree parent-cycle bug manifests as a memory leak detectable via miri's leak-checking mode (ADR-16) before it reaches production.

17.10 Operational Notes

Tree::print_dot (debug-only) emits a Graphviz DOT rendering of the green tree for visual inspection; the docs/architecture/red-green-tree.md runbook explains reading an intern-hit-rate regression back to a specific grammar-authoring pattern (e.g., a rule producing many near-but-not-quite-identical subtrees).

18. Phase 6 — Incremental Re-parse

18.1 Objectives

Implement InputEdit application and the incremental cursor (§8.3) that reuses unchanged green subtrees and re-parses only the affected span (P4, Wagner & Graham §5).

18.2 Detailed Implementation Steps

incremental::edit implements InputEdit construction with I8 validation (monotonic, non-overlapping byte ranges). incremental::cursor walks the old tree and new source in lock-step (§8.3's worked example is the reference behavior), at each step deciding reuse / descend / re-parse / resync / bail (the five-way decision from Ghezzi & Mandrioli's 1979 incremental-parsing formalization, §5). incremental::reuse implements the subtree-reuse predicate (§8.2): byte range outside the edit, kind valid at the cursor's LR state, lookahead token a valid shift. Resync (§18.6) matches the new LR state against a state in the old tree's forward path within the 128-token window (§4); exceeding it triggers Bail — full re-parse to EOF, a documented, not silent, degradation (ADR-08's recovery-vs-latency tradeoff mirrored here).

18.3 Deliverable

A single-byte edit in a 1 MB file produces a new tree via subtree reuse, byte-identical to a full non-incremental re-parse of the final source (I2's determinism extended to the incremental path).

18.4 Acceptance Criteria

Single-byte edit, 1 MB file: p50 < 300 µs, p99 < 1 ms (M2, §4); whole-line edit, 100 KB file: p99 < 100 µs (M3); incremental output byte-identical to non-incremental parse on 100% of the conformance/corpora/incremental corpus (zero tolerance — this is the one bucket with no percentage discount, since any divergence is a correctness bug, not a grammar-ambiguity artifact).

18.5 Conformance Fixtures

incremental/single_byte_edit_1mb.rs — the M2 latency-gated fixture. incremental/ whole_line_edit_100kb.json — the M3 fixture. incremental/edit_crosses_delimiter.rs — an edit that inserts a {, forcing cascading re-parse beyond the immediate edit range (§18.7 pitfall). incremental/edit_at_eof.py — no resync point exists; must re-parse cleanly from edit to new EOF. incremental/resync_window_exceeded.rs — a synthetic 200-token-deep structural edit exceeding the 128-token window, asserting a clean bail rather than a hang or panic.

18.6 Pitfalls

  • Tuning the resync window as a universal constant — it is grammar-dependent; the 144-line detail section documents the heuristic, and per-grammar override is exposed via Language's metadata (docs/architecture/incremental.md).
  • Assuming every edit has a resync point — edits at EOF have none; the cursor must cleanly re-parse edit-to-EOF rather than looping searching for a match that cannot exist (§18.8 edge case).
  • Ignoring external-scanner state at the reuse boundary — I11's serialize/deserialize round-trip is the reuse predicate's fourth (unwritten in Wagner & Graham, added by ADR-19) condition: a subtree spanning an external-scanner boundary is only reusable if the scanner state round-trips identically.
  • An edit that inserts a structural delimiter ({) cascading re-parse far beyond the edit itself — a real, not hypothetical, perf characteristic; documented rather than "fixed" (there is no fix — it is a correct consequence of the grammar's structure).

18.7 Performance Concerns

The dominant cost under P4's contract is the re-lex-plus-reduce work strictly inside the edited span (§8.3's worked example: O(1) for a single-character literal edit); the resync search itself is bounded by the 128-token window (§4), making worst-case incremental cost O(edit_span + window), independent of total file size — the central complexity-theoretic claim this phase's acceptance criteria (§18.4) exist to verify empirically.

18.8 Edge Cases

An edit at byte 0 of an empty file (degenerate); an edit whose old_end_byte equals new_end_byte but whose content differs (a same-length replacement, §8.3's worked example); an edit spanning the entire file (equivalent to a full re-parse, but the cursor must detect this without an special-case branch — the general algorithm degrades to it naturally); nested edits applied in rapid succession without an intervening Tree::edit commit (rejected by I8's monotonic-non-overlapping validation at the API boundary, not silently coalesced).

18.9 Failure Analysis

A reuse-predicate bug (accepting an invalid subtree) manifests as a wrong tree that diverges from the non-incremental oracle — caught by the zero-tolerance conformance gate (§18.4). Blast radius: any editor session doing incremental edits on the affected grammar; recovery: force a full re-parse fallback flag (Parser::set_incremental (false), an emergency operational lever) while the bug is fixed.

18.10 Operational Notes

tracing events incremental.reuse_rate, incremental.resync_bail at info level; the slow-parse.md runbook's second diagnostic branch (after ruling out lexer slowness, §15.10) is checking resync_bail frequency to catch a grammar whose window default (128) is miscalibrated.

19. Phase 7 — Error Recovery

19.1 Objectives

Implement single-token insertion/deletion recovery, N-token skip, and error-node synthesis (§8.4, §8.5, ADR-08, Burke & Fisher 1987, §5) so Parser::parse never fails to return a tree (I7, P5).

19.2 Detailed Implementation Steps

recovery::insert attempts, for each terminal valid to shift in the current LR state, a trial parse as if that terminal were inserted; the trial producing the longest subsequent error-free run wins (Burke & Fisher's core heuristic); the inserted node is marked MISSING with a zero-byte range (§8.4's worked example). recovery::delete attempts deleting the offending token if no insertion succeeds, wrapping it as an ERROR child. recovery::error_node implements the N-token skip (default 4, §4) and re-sync-to-known-token escalation, and the final bail-to-EOF at the 16-token window (§8.5's failure-path example is the reference behavior for this exact escalation chain). Recovery integrates with the incremental cursor (§18) via the same GSS resync mechanism (P4's implementation reuses P1's fork/merge machinery — recovery is structurally "resync after an unexpected token" just as incremental re-parse is "resync after an edit").

19.3 Deliverable

A file with one syntax error per 10 lines produces a tree with correct structure outside the error regions; the recovery-quality benchmark (a fixed, hand-scored corpus of broken files) scores ≥ 0.80 on its 0–1 scale.

19.4 Acceptance Criteria

Recovery-quality benchmark score ≥ 0.80 (M7, named fixture conformance/corpora/ recovery/scored_corpus/); insertion recovery attempted within a bounded trial count (≤ the number of valid-shift terminals in the current state, typically < 20, keeping recovery latency bounded); zero panics across the recovery fuzz target (fuzz_targets/recovery.rs) after a 24-hour local fuzz run (pre-Phase-10's 30-day canary, §22.4).

19.5 Conformance Fixtures

recovery/missing_rhs_expr.rs — the let x = ; fixture from §8.4, asserting a MISSING identifier node at the correct offset. recovery/unterminated_string.py — the §8.5 failure-path fixture, asserting a single ERROR node spans exactly the unterminated region plus the bail window. recovery/one_error_per_10_lines.rs — the M7 scored-corpus fixture. recovery/cascading_brace_mismatch.rs — nested delimiter mismatch exercising N-token skip escalation.

19.6 Pitfalls

  • Recovering too eagerly — producing a tree that diverges from the author's intent; the recovery window (§4) is the explicit throttle against this (documented tradeoff, not tuned away).
  • Inserting MISSING tokens without a zero-byte range — breaks editor highlighting, which assumes every node has a valid (if empty) range (I13).
  • Assuming a unique best recovery exists — an ambiguous grammar can yield multiple equally-good recoveries; the deterministic first-found tie-break (P12) is chosen over an arbitrary or random pick.
  • Treating insertion and deletion as independent of the resync/bail escalation chain — they are one algorithm with four escalating tiers (§19.2), not four separate strategies tried in isolation per error site.

19.7 Performance Concerns

Insertion recovery's trial-parse cost is bounded by the current state's valid-shift terminal count (typically small, §19.4); the worst-case recovery latency is therefore bounded by O(valid_shifts × recovery_window), gated as a benchmark (bench_incremental.rs extended with a recovery-latency case in Phase 7).

19.8 Edge Cases

A file that is entirely malformed (e.g., binary garbage fed to a text-grammar parser) — must bail to a single top-level ERROR node covering the whole file, not loop or exhaust the recovery budget repeatedly (§8.5's exact scenario, generalized). Two adjacent syntax errors within the recovery window of each other — the second error's recovery must not assume the first error's MISSING/ERROR nodes are real tokens (reuse predicate exclusion, cross-referenced to §18.2). A recovery site at the very start of the file (no preceding valid tokens to anchor a resync search backward).

19.9 Failure Analysis

A recovery bug that loops without making progress is contained by the bail-window cap (16 tokens, §4) as a hard backstop, independent of the specific bug — this is a structural defense (I7's enforcement point), not a per-bug fix. Detection: the recovery fuzz target's timeout-based liveness check (fuzz.yml, §10). Forensics: the recovery-trap.md runbook documents extracting the exact token sequence that triggered a pathological recovery from a fuzz crash artifact.

19.10 Operational Notes

tracing events recovery.insert_attempt, recovery.delete_attempt, recovery.error_node_synthesized, recovery.bail_to_eof at debug/warn; the recovery-trap.md runbook's primary diagnostic is filtering these spans by file to identify which grammar rule's recovery is most frequently escalating to bail.

20. Phase 8 — Query Engine

20.1 Objectives

Implement the S-expression query DSL parser, NFA-based pattern compiler with capture slots, streaming QueryCursor, and the standard predicate set (P8, ADR-09).

20.2 Detailed Implementation Steps

query::parse parses the S-expression surface ((function_declaration name: (identifier) @name), node patterns, wildcards _, anchors ./;, alternation [(a) (b)], quantifiers */+/?, negation !field, captures @name, predicates (#eq? @a "x")). query::compile lowers the pattern AST to a shared NFA (Chase 1987's tree-pattern-matching background, §5) where states correspond to tree-walk positions and transitions are labeled by node kind, child index, or predicate id; multiple patterns in one query share a single NFA with alternation at the start state. query::matcher walks the tree via TreeCursor (§17), consulting NFA transitions per node; query::cursor implements the streaming, restartable QueryCursor (each matches() call resumes from the last yielded match, generation-checked against the tree per I10). query::predicate implements #eq?/#not-eq?/#match?/#not-match?/ #any-of?/#not-any-of?, evaluated at match-emit time (not during the walk), consulting captured node text against the source buffer.

20.3 Deliverable

The Rust-subset highlight query matches upstream tree-sitter-rust's highlight-query match set on the standard corpus; QueryCursor throughput ≥ 50 MB/s on the highlight corpus.

20.4 Acceptance Criteria

Query-match throughput ≥ 50 MB/s (M9, §4-adjacent target, reference host); highlight- query parity with upstream ≥ 95% match rate (M-table row, §29); a malformed query pattern returns a typed QueryError (never a panic) across 5,000 proptest-generated malformed patterns.

20.5 Conformance Fixtures

queries/rust_highlight.scm — the upstream-parity fixture (§20.4). queries/ capture_slot_overlap.scm — nested captures at the same byte range, asserting most-specific-wins resolution (shared with §21.7's highlight-driver logic). queries/predicate_eq_match.scm — #eq?/#match? composite fixture. queries/malformed_pattern_fuzz_corpus/ — the proptest seed corpus for §20.4's malformed-pattern property test.

20.6 Pitfalls

  • Evaluating predicates during the tree walk instead of at match-emit — couples predicate cost to walk depth unnecessarily; ADR-09's NFA-sharing design assumes predicates are a post-filter.
  • A #match? predicate whose regex risks catastrophic backtracking (a ReDoS-shaped pattern) — mitigated by compiling query predicate regexes through a linear-time engine (not the runtime's own lexer-NFA machinery, ADR-22's boundary: query predicates are the only place a regex engine is consulted at runtime).
  • Quantifiers combined with negation producing a pattern that never matches — a grammar-author usability issue, not a system bug, but documented in docs/ architecture/query.md per the tree-sitter query reference (§5 RFCs).

20.7 Performance Concerns

The NFA's per-node transition lookup is a single table access (§29); the capture- slot vector is per-cursor and reused across matches (no per-match allocation on the steady-state path, consistent with P13 applied beyond the parser core).

20.8 Edge Cases

A query with a deeply nested wildcard producing combinatorially many candidate matches — bounded by a per-match work budget (a query-engine analogue of I4's fork cap), surfacing a tracing warning rather than unbounded CPU consumption. A predicate referencing a capture not bound by any preceding pattern element — rejected at compile time (query::compile) as Err(UnboundCapture). An empty query (zero patterns) — Err(EmptyQuery).

20.9 Failure Analysis

A pattern-compilation bug producing a subtly wrong NFA manifests as either false- negative matches (silent, caught only by the upstream-parity conformance bucket, §20.4) or false-positive matches (usually caught faster, since highlight output visibly diverges). Detection relies on the conformance bucket, not unit tests alone — documented as a known blind spot mitigated by the 95% parity gate.

20.10 Operational Notes

tracing event query.match_budget_exceeded at warn; the query-miss.md runbook (§10) documents the standard diagnostic: re-run the failing query with QueryCursor::set_byte_range narrowed to isolate which subtree the miss originates from.

21. Phase 9 — Front-Ends: Highlight, Fold, Symbols, Indent, Injection

21.1 Objectives

Build the query-driven front-ends: highlight (token classes), fold (collapsible ranges), symbols (outline), indent, and language injection (embedded-language grafting), each a query plus a small driver (P8's design carried to its consumers).

21.2 Detailed Implementation Steps

parsekit-highlight walks query matches in document order, resolving each capture's token class via (#set! "class" ...)-style metadata; overlapping captures resolve most-specific-(most-nested)-wins via an active-capture stack (shared logic with §20.5's fixture). The driver is incremental: a Tree::edit invalidates only spans whose underlying subtree changed (P4 extended to a downstream consumer), reusing the rest of the highlight stream. parsekit-fold and parsekit-symbols are thin drivers over dedicated fold/symbol queries, producing (start_byte, end_byte) ranges and an outline tree respectively. parsekit-injection resolves @injection.content/ @injection.language capture pairs, looks up the child language via the embedder's language registry, invokes a child Parser, and grafts the resulting Tree as a LanguageInjection overlay; an edit inside an injection re-parses only the injection (consistent with P4); an edit changing the injection's containing node re-parses the parent and re-derives the injection membership.

21.3 Deliverable

Highlight, fold, symbol, and indent queries for the four reference grammars are checked in under parsekit-grammars/*/queries/; CSS-in-<style>-tag injection works end to end against an HTML-subset host grammar.

21.4 Acceptance Criteria

Highlight/fold/symbol/injection conformance buckets each ≥ 95% parity with upstream tree-sitter's equivalent query outputs (M10, §29); the highlight driver's incremental update path re-renders only the edited span's token-class stream, verified by an assertion counting re-emitted tuples versus total tuples on a localized edit (< 5% of the file's tuples re-emitted for a single-line edit in a 10,000-line file).

21.5 Conformance Fixtures

highlight/rust_subset_vs_upstream.rs — the parity fixture (§21.4). fold/nested_ blocks.json — fold-range correctness on nested structures. symbols/outline_ duplicate_names.py — two declarations sharing a name, asserting the outline disambiguates by byte range, not name alone. injection/css_in_style_tag.html — the end-to-end injection fixture (§21.3).

21.6 Pitfalls

  • Emitting overlapping highlight captures without a most-specific-wins rule — produces visibly wrong (usually parent-class) highlighting; the active-capture stack (§21.2) is the fix, not a special case per grammar.
  • Injection across nested injections (e.g., HTML > CSS > a CSS @media construct resembling further nesting) — requires careful resynchronization at the injection boundary; documented in docs/architecture/injection.md, not silently approximated.
  • Treating theme/color mapping as in-scope — it is explicitly out of scope (§1 system boundaries); the engine emits token classes only.
  • An indent query producing conflicting indent/outdent signals at the same line — a grammar-authoring bug; the driver surfaces a diagnostic rather than silently picking one signal.

21.7 Performance Concerns

The highlight driver's incremental invalidation depends on the query engine's own per-match cost (§20.7) plus a tree-diff step bounding re-evaluation to subtrees whose green-tree identity changed (I5's interning makes "did this subtree change" an O(1) pointer-identity check, not a structural diff) — the key performance leverage point carried down from Phase 5's design (§17).

21.8 Edge Cases

An injection whose content itself contains the injection delimiter (e.g., a <style> literal nested inside CSS text) — the precise corner case docs/architecture/ injection.md documents with a worked example. A symbol query matching the same declaration twice via two different capture patterns — de-duplicated by byte range in the outline driver. A fold query whose range is zero-width — silently dropped (not an error; a zero-width fold range has no editor-visible effect).

21.9 Failure Analysis

A highlight-driver bug manifests as visibly wrong colors in an editor — usually caught fast by a human, but the CI parity gate (§21.4) catches it before release. An injection-graft bug (wrong byte-range mapping between parent and child trees) manifests as misaligned diagnostics/highlighting inside the injected region; contained by asserting the child tree's root byte range matches the @injection.content capture's range exactly, checked in injection::graft.

21.10 Operational Notes

tracing events highlight.reemit_ratio, injection.graft_count at debug; front-end query files are hot-reloadable in the highlight-tui example (§10) for grammar-author iteration without a full recompile — the workflow the docs/architecture/query.md guide documents end to end.

22. Phase 10 — Editor Integration & Production Hardening

22.1 Objectives

Ship the C ABI (ADR-10), WASM packaging (ADR-11), editor demos, and the full performance/fuzzing/conformance hardening pass gating a first release.

22.2 Detailed Implementation Steps

parsekit-c-abi exposes parsekit_parser_*/parsekit_tree_*/parsekit_node_*/ parsekit_query_* functions (§11's Rust types projected across the FFI boundary, cbindgen-generated header, ADR-10); panics at the FFI boundary are caught and converted to typed error out-parameters, never unwound across extern "C" (a hardening requirement distinct from, but analogous to, I7's parse-level guarantee). parsekit- wasm compiles the runtime to wasm32-unknown-unknown via wasm-bindgen with wee_alloc (ADR-11), producing parsekit.wasm + a JS glue layer; the glue layer's API documents that concurrent re-entrant calls into the WASM module during an in-flight parse are undefined and must not occur (single-threaded WASM constraint). Editor demos (Neovim Lua plugin over the C ABI; VS Code extension over WASM; CodeMirror 6 view) exercise the integration end to end. Hardening: cargo-deny/cargo-audit/miri/ clippy --deny warnings/rustfmt (ADR-16) in CI; a 30-day fuzz canary on the release branch across all fuzz_targets/ (§10) including the new c_abi_roundtrip.rs; cross-engine conformance (§27) run to convergence across every bucket (§29.1-adjacent table, Appendix B M12).

22.3 Deliverable

A binary-compatible (documented subset) C header versus tree-sitter's; a WASM bundle < 200 KB compressed for the four reference grammars; the Neovim plugin highlights Rust source interactively; the VS Code extension highlights Markdown with embedded fenced code blocks via injection (§21).

22.4 Acceptance Criteria

30-day fuzz canary: zero crashes, zero miri-detected UB across all fuzz targets (M-table row, §29); WASM bundle < 200 KB compressed (M11, §4); C ABI conformance test (binary layout comparison against a pinned tree-sitter header version) passes on the documented function subset (§22.2) with zero layout mismatches; cross-engine conformance ≥ 95% aggregate across all buckets (§27), 100% on the JSON bucket.

22.5 Conformance Fixtures

fuzz_targets/c_abi_roundtrip.rs — round-trips a parse through the C ABI and back, asserting tree equality with the pure-Rust path. upstream-treesitter/aggregate_ report.json — the full cross-engine conformance report, checked into CI artifacts per run. wasm/bundle_size_check.rs — asserts the compressed bundle stays under the 200 KB budget, failing CI on regression.

22.6 Pitfalls

  • Letting a Rust panic unwind across the extern "C" boundary — undefined behavior in the C host; every C ABI entry point wraps its body in std::panic::catch_unwind (documented in docs/architecture/overview.md's FFI-safety section).
  • WASM bundle-size creep from an innocuous new dependency — every Cargo.toml change to parsekit-runtime or its transitive deps is reviewed against the WASM budget before merge (a standing PR-template checklist item, not a one-time check).
  • Treating the 30-day fuzz canary as optional because "the unit tests pass" — the canary exists precisely because unit tests cannot enumerate the input space; release is gated on the canary's completion, not bypassed under schedule pressure.
  • Assuming WASM's single-threaded constraint is automatically enforced — it is documented but not compiler-enforced; the JS glue layer's own re-entrancy guard (a simple in-flight flag) is the actual enforcement mechanism.

22.7 Performance Concerns

The WASM build trades some throughput for bundle size (wee_alloc is slower than the system allocator per-allocation but far smaller in code size); this tradeoff is explicitly accepted (ADR-11) because the WASM host's bottleneck is typically network transfer of the bundle, not steady-state allocation throughput.

22.8 Edge Cases

A C host calling parsekit_tree_edit with a stale ParsekitTree* pointer after the tree was already freed — the pointer-stability contract (§22.6) documents this as caller-responsibility undefined behavior, mitigated by a debug-build canary value written into freed memory to make use-after-free crash loudly in testing rather than corrupt silently. A WASM host feeding a source buffer larger than linear memory's practical limit — streaming parse is the eventual answer (PhaseDeferred("§36")); for now, the JS glue layer documents the practical ceiling and returns a clear LanguageError-equivalent JS exception rather than crashing the WASM instance.

22.9 Failure Analysis

A fuzz-canary crash's forensic artifact is the minimized crash input plus the full tracing span tree for the failing parse; blast radius is contained to the specific grammar/input combination (the canary runs per-grammar, so a Python-subset crash does not block a JSON-only release). A C ABI layout mismatch is caught at CI time by the binary-layout conformance test (§22.5), never discovered downstream by an embedder.

22.10 Operational Notes

Release process: version-stamp the parse-table format (I12) and the C ABI version independently; a CHANGELOG.md entry is mandatory per release (enforced by CI checking for a diff to CHANGELOG.md on any release-tagged PR); the WASM artifact and C header are published as versioned release assets, never overwritten in place.

Structured logging. All tracing events carry grammar_name and (where applicable) file_id/edit_generation fields so a multi-file editor session's logs are filterable per document.

Dashboards. Per-grammar p50/p95/p99 parse and reparse latency; fork-cap-warning rate; intern-hit-rate trend; fuzz-canary status (green/red) for the active release branch.

Alerting philosophy. Alert on trend, not single-sample: a fork-cap-warning rate sustained above baseline for > 1 hour on a production grammar is the actionable signal, not a single occurrence (which is expected under P1's tradeoff).

SLOs. M2/M3 latency targets (§4) as the customer-facing SLO; 100% tree-always- returned (I7) as the availability SLO — there is no "parse unavailable" state by design.

Incident response. A latency-SLO breach triages via the slow-parse.md runbook first (lexer vs. GLR vs. resync attribution); a wrong-tree report triages via cross-engine conformance replay against the reported input.

Named runbooks (docs/runbooks/): slow-parse.md, parse-conflict.md, recovery-trap.md, query-miss.md — each referenced from its owning phase's N.10 (§12.10, §16.10, §19.10, §20.10).

Backup/restore. No persistent state to back up (library, stateless per parse); the only durable artifact is the versioned parse-table binary, itself reproducible byte-identically from its source grammar (I2) and thus not a backup concern beyond normal source-control practice.

Deployment topology. In-process library linkage; no independent deployment unit. The C ABI cdylib and WASM bundle are the two artifacts with independent release versioning (§22.10).

Canary / rolling-upgrade / rollback / migration strategy. A new parse-table format version (I12) is additive-only within a major version; an embedder rolls forward by shipping a new Language::load byte blob — no in-place migration of a running parser (parsers are values, recreated per language load, P9).

26. Compatibility & Versioning

Wire/table compatibility. The parse-table binary format is versioned via a magic number + version field (I12); a version bump is additive-only within a major version (new optional fields append; existing field offsets never move) and breaking within a major bump (documented in CHANGELOG.md with a migration note for grammar authors who must recompile).

API stability. The public parsekit facade (§11) follows SemVer: a patch release never changes a public signature; a minor release only adds; a major release may remove/rename, always with a CHANGELOG.md deprecation entry one minor version prior.

C ABI stability. The C ABI (§22.2) is versioned independently of the Rust crate SemVer; a parsekit_abi_version() function lets a C host detect compatibility at runtime before calling any other function (P10's operational implication).

Deprecation policy. A deprecated public item carries #[deprecated(since, note)] for at least one minor version before removal; the note names the replacement.

Rolling-upgrade guarantees. Since parsers are stateless values (P9) with no persisted session state, "rolling upgrade" reduces to "the embedder relinks against a new version" — no in-flight-parse compatibility concern exists because a parse never spans a process restart.

Grammar-schema evolution. A grammar DSL source is versioned implicitly by the parsekit-grammar crate version that compiled it; the IR itself is not persisted across versions (always regenerated from DSL source), so IR-schema evolution carries no migration burden — only the ParseTable binary format needs I12's compatibility discipline.

27. Testing & Verification Strategy

Unit tests. Per-module, colocated (#[cfg(test)]), one test per invariant (I1–I14, §7) plus one per ADR's stated tradeoff boundary where mechanically checkable.

Integration tests. parsekit-bench::sim's deterministic simulator (§7's debugging methodology) drives cross-crate scenarios (grammar → table → parse → edit → recovery) end to end.

Property tests. proptest (ADR-13) for: external-scanner serialize/deserialize round-trips (I11, §15.4), malformed-query-pattern handling (§20.4), InputEdit validation (I8).

Differential tests. Cross-engine conformance against upstream tree-sitter (ADR-17, §9) is the primary differential oracle across parse-trees, incremental, and query buckets (§27.1 below).

Fuzzing. cargo-fuzz targets (§10): grammar_compile, parser_runtime, incremental, recovery, query_compile, cross_engine, c_abi_roundtrip — each gated in fuzz.yml; the 30-day canary (§22.4) is the pre-release fuzzing gate.

Chaos / fault injection. Applied at the external-scanner and C ABI boundaries specifically (the only two places host-supplied or FFI-crossing code executes): scanners that panic, return garbage, or never terminate are injected as test doubles in parsekit-runtime/tests/scanner_chaos.rs.

Deterministic replay. Every fuzz-canary crash is minimized to a regression fixture (§24 FM-10) replayable deterministically (I2) — the replay is the acceptance test for the fix.

Soak testing. The 30-day fuzz canary doubles as the soak test: sustained fuzzing across the release branch with zero crashes and zero miri-detected UB is the soak-test pass criterion (§22.4).

Conformance. conformance/runner.rs executes every corpus bucket (§27.1) and emits conformance.report.json, consumed by CI to gate merges against the per-bucket pass-rate commitments in Appendix B.

Performance-regression gating. perf.yml runs criterion benchmarks (ADR-14) against a stored baseline; a > 20% regression on any M-table (§29) metric fails CI.

29. Performance Engineering

Benchmarking/profiling methodology. criterion (ADR-14) for all M-table targets below; perf/flamegraph for allocation and cache-locality profiling of the per-token GLR step (§16.7) and the lexer DFA transition table (§15.7); valgrind --tool=massif for the green-tree memory-per-byte target (M6).

Allocation analysis. The bumpalo arena (P13, ADR-23) reduces the hot path to bump-pointer increments; criterion's allocation-counting harness asserts zero heap allocations per GLR step outside tree-node construction.

Lock contention. None on the parse hot path — Parser/Tree/Language carry no shared mutable state requiring synchronization (P9, I9); the only lock in the codebase is the intern table's (§17.2), scoped to a single parse's arena and therefore uncontended in the single-parser-per-thread deployment model.

Cache analysis. Lexer DFA transition tables are laid out for locality (adjacent states in memory, §15.7); the green-tree intern table's FxHash is chosen for throughput over cryptographic quality (§17.7).

Syscall analysis. Zero syscalls per parse (in-memory byte slice in, Tree value out); one read syscall per grammar load (Language::load, amortized across the grammar's lifetime).

Tail-latency analysis. p99 (not just p50) is the gated metric for every latency row in §4 and every M-table row below, because editor keystroke-latency perception is tail-dominated, not average-dominated.

30. Scalability Analysis

What stays constant. Per-token GLR step cost (O(1) amortized, bounded by the fork cap I4); incremental reparse cost for a localized edit (O(edit span + resync window), independent of total file size, §18.7); memory per source byte (M6, bounded by interning).

What grows, with Big-O. Cold parse time: O(n) in source size n (single pass, modulo GLR forks which are bounded, not a function of n). Grammar compile time: O(states × terminals) in grammar complexity (§14.7), a one-time offline cost independent of any source file. Query match count: O(matches), bounded per-query by the match-work budget (§20.8) regardless of tree size.

Named bottlenecks, in order. (1) GLR fork count on a poorly-authored ambiguous grammar (mitigated by prec annotations and the I4 soft cap); (2) lexer DFA re-computation across many simultaneously active LR states during a fork (mitigated by per-position memoization, §15.7); (3) red-tree first-visit materialization depth for very deeply nested source (mitigated by viewport pre-warming, §17.7); (4) query match-budget exhaustion on a pathological query pattern (mitigated by the per-match budget, §20.8).

Horizontal scaling. Parsing is embarrassingly parallel across files (each Parser is an independent value, P9); the embedder's own thread pool handles multi-file parallelism — the toolkit does not manage threads internally. Intra-file parallel parsing (splitting one file's parse across cores) is a Phase-2 stretch (PhaseDeferred("§36")), gated on most grammars not admitting safe per-rule parallelism.

Sharding/partitioning. Not applicable to a single-file parse; a code-search index built on top of this toolkit (an embedder concern, out of scope per §1) would shard by file, orthogonal to this system's design.

Coordination overhead. Zero cross-parser coordination by construction (P9); the only "coordination" inside one parse is the GSS merge step itself (§16.2), which is the parsing algorithm, not an incidental overhead.

Practical ceiling and levers beyond it. The practical ceiling for a single parse is bounded by the per-parse memory cap (default 1 GB, T2 §23) and the WASM linear- memory limit on browser hosts; the lever beyond it is streaming/chunked parsing (PhaseDeferred("§36")) — deferred because no reference grammar in this system's initial scope produces files approaching that ceiling.

31. Mental Models & First Principles

  1. MM1 — A parser is a table interpreter, not a program. The generator does the thinking (LR(1) construction, Pager merge); the runtime just walks a table (§16.2). Predicts: correctness bugs live overwhelmingly in the generator (§14), not the runtime loop. Bug class without it: engineers debug the wrong crate when a parse is wrong. Applied in §14, §16.
  2. MM2 — The GSS is a lattice of "what if," not a tree of guesses. Every live branch is a legitimate parse-in-progress, not speculative backtracking (Tomita, §5). Predicts: merge is not an optimization bolted onto backtracking — it is what makes GLR sub-exponential in practice. Bug class without it: engineers "optimize" by deleting merges, reintroducing exponential blowup. Applied in §16.2, §16.7.
  3. MM3 — Green is what the tree IS; red is where the tree IS. Identity (structural sharing) and position (byte offsets, parent pointers) are orthogonal concerns that must never share one representation (ADR-04). Predicts: any "simplification" that stores a byte offset inside a green node is a regression. Bug class without it: FM-4's Roslyn-era conflation. Applied in §17.
  4. MM4 — Incrementality is a reuse predicate, not a diff algorithm. The system never computes a text diff; it asks, per subtree, "is this still valid here" (§18.2). Predicts: incremental correctness reduces to proving the predicate sound, not to diff-algorithm cleverness. Bug class without it: engineers reach for a generic tree-diff library, missing the LR-state-validity check the predicate needs. Applied in §18.
  5. MM5 — Error recovery is resync, and resync is the same operation whether triggered by an edit or a syntax error. Both ask "where can the parser legitimately resume." Predicts: the incremental cursor and the recovery engine can share machinery (§19.2). Bug class without it: two independently-maintained resync implementations drift and disagree. Applied in §18, §19.
  6. MM6 — A query is a second, smaller grammar over the tree, not a string search. The NFA-with-captures design (§20.2) treats structural matching as a first-class parsing problem, not text scanning. Predicts: query performance scales with tree shape, not source length. Bug class without it: implementing queries as a tree-walk-plus-regex hybrid, losing the shared-NFA amortization. Applied in §20.
  7. MM7 — Determinism is a compounding asset, not a nicety. Every downstream gate (conformance, fuzzing, replay) assumes I2; a single nondeterministic tie-break silently invalidates all of them at once. Predicts: any "random" tie-break request ("just pick one") is actually a request to break the entire testing strategy. Bug class without it: flaky CI blamed on "test infrastructure" when the real cause is a nondeterministic parse. Applied in §7 (I2), §27.
  8. MM8 — The C ABI is a second language boundary with its own correctness contract, not a mechanical export of the Rust API. Ownership, panics, and lifetimes do not cross extern "C" for free (§22.2). Predicts: every new public Rust API needs an explicit FFI-safety review, not an automatic re-export. Bug class without it: T7/FM-9's ABI-corruption and layout-mismatch failure modes. Applied in §22.

33. Back-of-Envelope Capacity Model

  1. Cold-parse time for a 5 MB file = size ÷ throughput = 5 MB ÷ 25 MB/s (M4, §4) = 200 ms.
  2. Cold-parse time for a 5 MB JSON file = 5 MB ÷ 100 MB/s (M5) = 50 ms.
  3. Green-tree memory for a 1 MB source file = 1 MB × 5 bytes/byte (M6, §4) = 5 MB ceiling.
  4. GSS peak memory during a fork of depth 64 (I4 soft cap) = 64 branches × 96 bytes/node (§4) × average branch depth (assume 20 live nodes/branch before a merge collapses it) = 64 × 96 × 20 ≈ 123 KB transient peak — negligible against the 1 GB per-parse cap (T2, §23).
  5. Incremental reparse worst-case token cost = edit span (assume 10 tokens) + resync window (128 tokens, §4) = 138 tokens reparsed, independent of file size — the complexity claim underlying M2/M3.
  6. WASM bundle byte budget per reference grammar = 200 KB total (M11) ÷ 4 grammars ≈ 50 KB/grammar average, informing the JSON table-size target (M8: < 50 KB) as a consistent per-grammar slice of the same budget.
  7. Query throughput implies per-match cost = 1 ÷ (50 MB/s ÷ average match density). Assuming a highlight query averages 1 match per 40 source bytes, match rate = 50 MB/s ÷ 40 bytes ≈ 1.25M matches/s, so per-match budget ≈ 800 ns — the number the NFA transition-table lookup (§29) must not exceed on average.
  8. Fuzz-canary coverage = 30 days × 24 h × fuzzing throughput (assume 2,000 execs/s per core, 4 cores) = 30 × 86,400 × 2,000 × 4 ≈ 2.07 × 10^13 execs — the scale the "zero crashes" M12 target is actually claiming confidence over.
  9. Recovery trial-parse cost bound = valid-shift terminal count (typically ≤ 20, §19.7) × recovery window (8 tokens, §4) = ≤ 160 trial-token-steps per error site — bounding worst-case recovery latency per error.
  10. FD budget confirms zero steady-state FD pressure: 0 FDs/parse (§4) × any concurrency level = 0, meaning the per-parser-instance concurrency ceiling in §4 ("unbounded") is not FD-limited — the only limits are memory (T2) and CPU.
  11. Intern-table hit-rate savings: at a 70% hit rate (§17.4) on a 1 MB file whose naive (non-interned) green tree would be ~15 MB (3× the interned M6 ceiling), the intern table saves roughly 10 MB of allocation per file — the concrete payoff quantified from §17's I5 mechanism.
  12. 30-day canary wall-clock cost at CI scale: if the canary runs on a dedicated 4-core runner continuously, that is 2,880 core-hours per release cycle — the number that justifies gating only releases, not every CI push, on the full canary (§28).

Every number above is derived from a System Constraints row (§4) or a Performance Target (§29.1), never asserted independently.

35. Alternative Architectures (Roads Not Taken)

Alt-1: Packrat/PEG with memoized backtracking

source bytes -> recursive-descent rules with memoization table
              -> ordered choice (first match wins, no ambiguity)
              -> parse tree (no fork/merge, no GLR)

Regime where it wins: a single, hand-authored, deliberately unambiguous grammar with no requirement for incremental re-parse (e.g., a one-shot config-file or DSL parser compiled once per process). Real system: many parser-combinator libraries (Rust's nom, Haskell's parsec) embody this. Why rejected here: PEG's ordered-choice semantics make grammar composition non-modular (adding an alternative can silently shadow another), and Packrat's memoization table is O(n × rules) memory in the worst case — unacceptable against the M6 memory budget (§4) at editor scale (ADR-02, §9).

Alt-2: Earley parsing for full context-free generality

source bytes -> Earley chart (state sets per position)
              -> O(n^3) worst case, O(n^2) ambiguous, O(n) unambiguous-bounded
              -> parse forest (all derivations, disambiguated post-hoc)

Regime where it wins: grammars with genuine unbounded ambiguity that GLR's fork/merge would still explode on (natural-language parsing is the classical case Earley targets). Real system: natural-language-processing parsers and some markup grammars needing full CFG generality. Why rejected here: the constant factor is too high for the M4/M5 throughput targets (§4) — a source-code grammar's ambiguity is bounded and local, and GLR's fork/merge already handles it at a far lower constant cost (§5 Earley 1970 citation, ADR-02).

Alt-3: Hand-written recursive-descent with ad hoc recovery (the Roslyn/javac model)

source bytes -> hand-written parser functions per grammar rule
              -> ad hoc panic-mode recovery per call site
              -> typed AST (language-specific, not general-purpose)

Regime where it wins: a single language with a dedicated, well-resourced compiler team that can hand-tune recovery heuristics per construct (this is exactly what Roslyn and javac do). Real system: Roslyn (C#/VB), javac, rustc's own parser. Why rejected here: this system's explicit goal is grammar-agnostic reuse across many languages (§1) — a hand-written parser is not portable across grammars, defeating the entire premise of a generator/runtime split (ADR-05).

Alt-4: Scannerless GLR (no separate lexer stage)

source bytes -> single GLR automaton over characters directly
              -> no DFA-per-LR-state lexer, no external-scanner hook
              -> tokens are just another grammar nonterminal

Regime where it wins: grammars where the lexical/syntactic boundary is itself ambiguous or absent (some natural-language and markup grammars, per Visser 1997, §5). Real system: SDF/SGLR (Visser's own scannerless GLR implementation). Why rejected here: scannerless GLR's tables are substantially larger (every character transition is a grammar transition) and the mode-switching-DFA design already solves this system's actual lexical-ambiguity problem (the < case, §15.6) at a much smaller table-size cost (ADR-06, §9).

37. Glossary

  • ADR. Architectural Decision Record; a locked, justified design choice (§9).
  • Bail (recovery/resync). The final escalation tier: give up finding a resync point and treat the remainder as a single ERROR node (§19.2).
  • bumpalo. The Rust arena-allocation crate used for per-parse allocation (ADR-23).
  • Capture slot. A named binding (@name) recorded during query matching (§20.2).
  • Closure (LR item sets). The set of LR items reachable from a kernel item via epsilon-style expansion (§14.2).
  • Conflict (shift/reduce, reduce/reduce). A state where the LR table cannot determine a single action; resolved by prec or forked to GLR (§14.2).
  • CST. Concrete syntax tree; this system's tree retains every token, unlike an AST (§8.2).
  • DFA. Deterministic finite automaton; the lexer's per-LR-state structure (§15.1).
  • External scanner. A user-supplied function recognizing context-sensitive tokens the LR-state-aware DFA cannot express alone (§11, ADR-19).
  • Field. A named child reference declared via field("name", rule) in the grammar DSL (§8.1).
  • Fork (GLR). Splitting a parse into parallel branches at an unresolved conflict (§16.2).
  • Generation counter. A per-Tree counter incremented on edit(), used to detect stale QueryCursor use (I10, §7).
  • GLR. Generalized LR; the fork-and-merge parsing algorithm (Tomita, §5).
  • Grammar DSL. The JavaScript-like declarative grammar-authoring surface (§8.1).
  • Grammar IR. The canonicalized, validated internal representation the DSL lowers to (§8.1, §13.2).
  • Green tree. The structurally-shared, value-typed, immutable syntax-tree layer (§8.2, §17.2).
  • GSS. Graph-structured stack; the GLR runtime's core data structure (§16.2).
  • InputEdit. A byte-range edit descriptor applied to a Tree (§11).
  • Injection. Embedding a child-language parse inside a parent tree via a query capture pair (§21.2).
  • Intern (hash-cons). Deduplicating structurally identical green subtrees to a single allocation (I5, §7).
  • LALR. Look-Ahead LR; a merged-lookahead approximation of canonical LR(1) (§5, DeRemer 1969).
  • Lookahead set. The set of terminals that may follow a given LR item (§14.1).
  • LR(1). Left-to-right, rightmost-derivation parsing with 1-token lookahead (§14.1).
  • MISSING node. A synthetic, zero-byte-range node inserted by recovery to stand in for an absent required token (§8.4, §19.2).
  • NFA. Non-deterministic finite automaton; the query pattern-compilation target (§20.2) and the token-regex intermediate form (§15.2).
  • Node. A positioned, read-only view into a Tree (§11).
  • Pager merge. The 1977 LR(1) state-compaction algorithm reducing table size toward LALR while preserving LR(1) precision (§14.4, ADR-07).
  • Parse-table binary. The versioned, serialized cross-cut artifact between the generator and the runtime (§8.1, I12).
  • PEG. Parsing expression grammar; a rejected alternative algorithm (§35 Alt-1).
  • prec/prec.left/prec.right/prec.dynamic. Grammar-DSL precedence annotations resolving shift/reduce and reduce/reduce conflicts (§8.1, §14.3).
  • Predicate (query). A post-match filter such as #eq?/#match? (§20.2).
  • QueryCursor. The stateful, streaming, restartable query-match iterator (§11).
  • Recovery window. The token budget (default 8) bounding insertion/deletion recovery attempts before escalating (§4, §19.1).
  • Red tree. The lazily-materialized, positioned, parent-aware projection of the green tree (§8.2, §17.2).
  • Resync window. The token budget (default 128) bounding incremental-reparse resynchronization before bailing to a full reparse (§4, §18.6).
  • Reuse predicate. The three-(really four-)condition test determining whether a green subtree can be reused across an edit without re-parsing (§8.2, §18.2).
  • Soft cap (fork). The live-branch-count ceiling (64) that warns rather than hard-stops (I4, §7).
  • Subset construction. The classical NFA-to-DFA conversion algorithm used per LR state (§15.2, Hopcroft/Motwani/Ullman).
  • Table compaction. Encoding the LR action/goto tables as row-compressed sparse matrices (§14.2, §8.1).
  • Token disambiguation. Longest-match-then-precedence resolution when multiple terminals match at one input position (ADR-21, §15.2).
  • TreeCursor. The stateful O(1)-movement tree walker (§11, §17.2).
  • Wire compatibility. The parse-table binary's cross-version compatibility contract (I12, §26).
