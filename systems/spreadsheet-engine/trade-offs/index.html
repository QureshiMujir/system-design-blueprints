Decisions (§9) · 32 ADRs

001

Implementation language

Chosen

Rust (edition 2021)

Rejected

C++, Go, TypeScript, Zig

When the rejected choice is right

TypeScript wins when the engine is browser-only, bundle size dominates, and p99 GC pauses are acceptable (small interactive sheets, no WASM budget). Go wins for a server-side formula micro-service where team Rust expertise is low and latency headroom >10 ms.

Why: No-GC determinism (p99 stability); enums+exhaustive match for value/error/AST; fearless concurrency for parallel recalc; WASM target; mature fuzz/proptest. C++ = UB/legacy risk; Go = GC pauses + weak enums; TS = JS number/coercion semantics leak.

002

Parser technique

Chosen

Pratt / precedence-climbing

Rejected

recursive-descent only, LALR (yacc/lalrpop), PEG

When the rejected choice is right

LALR (lalrpop) wins when grammar is specified by a standards body (SQL, POSIX shell) and mechanically checked against the grammar — schema-driven correctness outweighs diagnostic flexibility. PEG wins for ambiguous, backtracking-heavy grammars where packrat memoization is needed.

Why: Operator-precedence table maps directly to spreadsheet operators incl. right-assoc ^, reference ops; hand-written → precise errors + spans; LALR overkill + worse diagnostics.

003

AST vs RPN token array

Chosen

AST (tree)

Rejected

RPN token array (POI/LibreOffice style)

When the rejected choice is right

RPN wins in memory-constrained embedded targets (< 64 KB heap) where allocation for a tree per cell is infeasible, or in a JIT pipeline where RPN maps naturally to stack-machine bytecode emission.

Why: AST clearer for array/spill rewriting + structural-edit fixup + tree-walk eval; RPN saves memory but complicates ref fixup. Interning recovers sharing.

004

Cell value representation

Chosen

Tagged enum CellValue (Number f64 / Bool / Text(interned) / Error / Blank)

Rejected

boxed dyn Any, NaN-tagging

When the rejected choice is right

NaN-tagging wins in a pure numeric engine with no error-type diversity (e.g., a SIMD-parallel vector processor) where the 3-bit NaN payload suffices and branch-free dispatch is critical. dyn Any wins when the value type is open-extension (plugin-defined types).

Why: Exhaustive match + no allocation for scalars; interned text dedups; NaN-tagging too fragile for error variants.

005

Cell store layout

Chosen

Sparse columnar (column → interval/run map)

Rejected

dense 2-D array, row-major hashmap of (r,c)

When the rejected choice is right

Dense 2-D wins when the sheet is genuinely dense (scientific/simulation data, ≥90% fill) and column-major access patterns dominate; hashmap wins for extremely sparse, random-access workloads where the fill rate is < 0.01% and column scans are rare.

Why: Sparse (most cells empty); columnar = cache-friendly column scans (SUM A:A) + cheap row/col insert; dense = OOM at grid size; per-cell hashmap = poor locality.

006

Dependency edges

Chosen

Range nodes + per-cell where needed

Rejected

per-cell edges only

When the rejected choice is right

Per-cell edges win in engines with no range formulas (each formula references only individual cells) or when range membership changes so rapidly that maintaining the interval index costs more than materialized edges.

Why: Avoid O(cells) edge blowup for range precedents; bound graph at O(formulas).

007

Topological order

Chosen

Kahn (in-degree queue)

Rejected

DFS post-order

When the rejected choice is right

DFS post-order wins when cycles are impossible by construction (pure DAG, e.g. a compiler IR after SSA) and the post-order is a byproduct of a DFS already running for other reasons (no extra pass).

Why: Kahn detects leftover cycle nodes naturally + supports incremental in-degree updates.

008

Cycle detection

Chosen

Tarjan SCC

Rejected

Kosaraju, Floyd

When the rejected choice is right

Kosaraju wins when the graph is stored in an immutable format (two separate DFS passes are fine) or when simplicity of implementation is paramount and a second pass is not a bottleneck. Floyd wins for tiny fixed-size adjacency matrices where simplicity > asymptotic efficiency.

Why: Single-pass linear SCC; identifies iterative-calc groups; Kosaraju = 2 passes.

009

Incremental recompute

Chosen

Dirty-set forward closure + topo subgraph

Rejected

recompute-on-read (pull), full rebuild

When the rejected choice is right

Pull (recompute-on-read) wins in reactive/demand-driven systems where reads are sporadic, writes are batched, and latency on write is the constraint (e.g., Adapton, build systems with lazy evaluation). Full rebuild wins when the graph is tiny (< 100 cells) and maintaining the dirty-set is more complex than the rebuild.

Why: Push dirty propagation matches edit-driven UX; pull/memoization added as cache; full rebuild violates Principle 2.

010

Parallel recalc

Chosen

rayon-style work-stealing on independent subgraphs

Rejected

OS threads manual, single-thread only, async tokio

When the rejected choice is right

Manual OS threads win when fine-grained control over thread affinity/NUMA pinning is required (e.g., real-time scheduling with CPU isolation). Single-thread wins for correctness-critical embedded targets where determinism is easier to audit with no concurrency. Tokio wins if the recalc is I/O-bound (external data feeds per cell).

Why: Data-parallel over topo layers; deterministic via stable order + per-thread buffers; tokio is for IO not CPU.

011

Concurrency model for reads

Chosen

Snapshot isolation via Arc<Snapshot> + COW

Rejected

global RwLock, lock per cell

When the rejected choice is right

Global RwLock wins when reads are short and rare (< 1% of time) and snapshot overhead (COW, Arc clone) exceeds lock contention cost. Per-cell locks win for fine-grained concurrent write access patterns (multiple writers, each to disjoint cells) — not applicable here (single mutation root).

Why: Readers never block writers; immutable snapshot = trivially Sync; per-cell locks = deadlock + overhead.

012

Float semantics

Chosen

IEEE-754 binary64, documented Excel divergences

Rejected

decimal (rust_decimal), arbitrary precision

When the rejected choice is right

Decimal wins for accounting systems where 0.1 + 0.2 = 0.3 is a legal requirement and Excel compatibility is explicitly not a constraint. Arbitrary precision wins for computer-algebra systems or cryptographic applications where exact symbolic results are required.

Why: Match Excel/Calc (binary64); decimal would diverge from oracle; perf. Provide ROUND/banker's where Excel does.

013

String interning

Chosen

FNV-hashed interner (StringId)

Rejected

String per cell, Arc<str>

When the rejected choice is right

Arc<str> wins when strings are unique (no dedup benefit) and the interner lock/table overhead exceeds the per-cell allocation cost. Raw String wins in single-threaded tools where lifetime is trivial and sharing is unnecessary.

Why: Dedup repeated text + stable ids for determinism; FNV fast for short keys; raw String = memory + slow compare.

014

Hash/iteration determinism

Chosen

FNV + sorted iteration in compute paths

Rejected

default SipHash HashMap iteration

When the rejected choice is right

SipHash (default) wins for public-facing maps where hash-flooding DoS is a concern (user-supplied keys); pay the sort cost only on compute-affecting paths. HashDoS-resistant maps (indexmap with sorted iteration) win when both security and determinism are required simultaneously.

Why: Default HashMap iteration order is randomized → non-deterministic reductions; sort/stable order in any compute-affecting loop.

015

Build system

Chosen

Cargo workspace (multi-crate)

Rejected

single crate, Bazel

When the rejected choice is right

Bazel wins at monorepo scale (> 50 crates, cross-language) where reproducible distributed builds, remote caching, and fine-grained dependency analysis justify the config overhead.

Why: Workspace = clean crate boundaries (Phase-0 list); Cargo native; Bazel overhead unjustified.

016

Serialization (snapshot/wal)

Chosen

Custom binary (versioned) + serde for CSV/JSON edges

Rejected

bincode-only, Protocol Buffers, JSON-only

When the rejected choice is right

Protocol Buffers win when the format must be consumed by polyglot clients (Python, Go, Java) without a shared Rust binary; generated code handles schema evolution mechanically. JSON wins for human-debuggable interchange at small scale (< 10k cells).

Why: Versioned binary for compact/fast snapshot; serde for interchange; protobuf adds dep + schema churn; JSON too big for 1M cells.

017

xlsx I/O

Chosen

Subset via calamine(read) + custom minimal writer

Rejected

full custom OOXML, full xlsxwriter

When the rejected choice is right

Full OOXML wins when the product is a general-purpose spreadsheet application that must round-trip charts, themes, conditional formatting, and pivot tables without loss — the cost of the full OOXML spec is justified by feature completeness.

Why: Subset (cells/formulas/basic fmt); full OOXML deferred (Appendix C (C-5)); calamine mature reader.

018

CSV

Chosen

RFC 4180 via csv crate

Rejected

hand-rolled

When the rejected choice is right

Hand-rolled wins only when the CSV dialect deviates from RFC 4180 in ways the csv crate cannot configure (e.g., a fixed-width variant or a non-standard delimiter set).

Why: Correct quoting/escaping; well-tested.

019

Logging

Chosen

tracing (structured spans)

Rejected

log, custom

When the rejected choice is right

log wins in no_std / deeply embedded targets where tracing's allocator requirements are unavailable; custom wins for ultra-low-overhead hot-path tracing where the tracing dispatcher adds measurable latency.

Why: Spans model recalc tree; sampling; integrates metrics.

020

Metrics

Chosen

metrics facade + prometheus exporter (server)

Rejected

statsd, custom

When the rejected choice is right

StatsD wins when the existing ops stack is StatsD-native (Graphite/DataDog without Prometheus) and the metrics facade migration cost exceeds the benefit. Custom wins for embedded targets with no network and a bespoke telemetry sink.

Why: Standard counters/histograms (recalc latency, dirty-set size).

021

Testing

Chosen

cargo test + proptest + insta snapshots

Rejected

only unit tests

When the rejected choice is right

Unit-tests-only wins for extremely simple, stable modules where the property space is trivially exhausted by hand and maintaining generators is more expensive than the coverage gain.

Why: Property tests for parser/coercion; snapshot tests for formatting/AST; differential vs oracles.

022

Fuzzing

Chosen

cargo-fuzz (libFuzzer)

Rejected

AFL, honggfuzz

When the rejected choice is right

AFL wins when the target binary cannot be compiled with Clang coverage instrumentation (requires GCC) or when persistent mode is unavailable. Honggfuzz wins for hardware-feedback-based fuzzing on baremetal targets.

Why: Targets: parser, evaluator, ref-fixup, xlsx reader; libFuzzer integrates with corpus.

023

Benchmarking

Chosen

criterion + custom workbook harness

Rejected

#[bench] nightly

When the rejected choice is right

#[bench] wins for rapid micro-bench iteration during development on nightly Rust where statistical rigor is secondary to turnaround speed.

Why: Statistical bench; regression gate in CI.

024

Server RPC

Chosen

tonic (gRPC) + JSON-RPC (axum)

Rejected

REST-only, custom proto

When the rejected choice is right

REST-only wins when clients are browser-native (no gRPC-web proxy) and throughput is low (< 1k req/s); typed schema is achievable via OpenAPI. Custom proto wins in constrained embedded environments with no HTTP stack.

Why: gRPC for typed perf clients; JSON-RPC for simple/web; axum lightweight.

025

FFI

Chosen

C ABI via cbindgen

Rejected

manual headers

When the rejected choice is right

Manual headers win when the C API is deliberately minimal (< 10 functions), hand-authored for stability, and cbindgen's generated layout diverges from the required ABI.

Why: Generated stable C header for embedding.

026

WASM

Chosen

wasm-bindgen + wasm-pack

Rejected

hand-rolled

When the rejected choice is right

Hand-rolled wins when the WASM interface is trivially small (1–2 exported functions) and wasm-bindgen's JS glue size is a meaningful fraction of the bundle.

Why: Browser embedding of same core.

027

Determinism testing

Chosen

1-thread vs N-thread byte-diff harness

Rejected

trust-by-review

When the rejected choice is right

Trust-by-review wins only for single-threaded engines where parallel execution is impossible by design — no mechanical test needed because the condition is vacuously satisfied.

Why: Mechanically enforce I4.

028

Date system

Chosen

Configurable 1900 (default) + 1904 epochs

Rejected

hardcode 1900

When the rejected choice is right

Hardcode 1900 wins when the product targets only Windows Excel interop and Mac/1904-epoch files are explicitly out of scope, simplifying date math.

Why: Mac/Win compatibility; replicate 1900 leap bug for Excel parity.

029

Locale data

Chosen

CLDR subset (separators, date order)

Rejected

OS locale, full ICU

When the rejected choice is right

Full ICU wins when the product requires comprehensive Unicode collation (VLOOKUP with locale-aware text ordering), bi-directional text handling, or emoji/grapheme-cluster support in text functions. OS locale wins for desktop-embedded engines where the host app already owns locale and consistency with OS display matters more than reproducibility.

Why: Deterministic + small; full ICU heavy.

030

CI/CD

Chosen

GitHub Actions (matrix: x86-64/aarch64, stable/MSRV)

Rejected

self-hosted only

When the rejected choice is right

Self-hosted wins when the build requires specialized hardware (GPU-accelerated bench, HSM signing, specific OS versions) unavailable on GitHub-hosted runners, or when network egress costs on hosted runners are prohibitive.

Why: Multi-arch determinism + MSRV gate + fuzz smoke + conformance.

031

Licensing

Chosen

Apache-2.0 (lib)

Rejected

MIT, GPL

When the rejected choice is right

GPL wins when the goal is copyleft (force derivative engines open-source); MIT wins when maximum adoption is the goal and the patent grant in Apache-2.0 is irrelevant to the ecosystem.

Why: Patent grant; permissive for embedding; GPL too viral for a library.

032

Reproducible builds

Chosen

pinned toolchain (rust-toolchain.toml) + Cargo.lock committed + SBOM (cargo auditable)

Rejected

floating versions

When the rejected choice is right

Floating versions win during rapid early development (daily nightly, frequent dep updates) before the stability/security requirements that justify pinning — acceptable technical debt in prototype phase.

Why: Bit-reproducible artifacts; supply-chain provenance.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Pull-Based (Lazy / Recompute-on-Read) with Memoization

[Cell Store] ── on read ──▶ [Evaluator] ──── reads ──▶ [Precedent cells (lazy)]
                                 │ memoize result
                                 ▼
                          [Memo Cache (invalidated on write)]

Regime where it wins. Workloads with many writes and few reads (ETL pipelines, batch transforms) where deferring evaluation until read time avoids computing cells that are never read. Self-adjusting computation (Adapton) uses this model for incremental functional programs.

Real system. Adapton (Hammer et al., 2015); also Excel's pre-2007 "manual recalc" mode is a degenerate form (recalc only on user request). Salsa (the Rust incremental query framework used in rust-analyzer) uses pull-based memoization with fine-grained dependency tracking.

Why rejected. Spreadsheet UX is edit-driven: every cell write must produce updated displays synchronously (or near-synchronously). A pull model makes reads expensive (potentially full recompute on every read of a stale cell) and makes cross-cell consistency hard to enforce (two reads of dependent cells may see different recalc states). The dirty-set push model (ADR-009) matches the UX contract directly.

Alt-2: RPN Token-Array Evaluation (LibreOffice / Excel internal model)

Formula text ──lex──▶ [Token Array (RPN)] ──eval──▶ [Stack Machine]
                              │
                         stored per cell
                         (no AST heap)

Regime where it wins. Memory-constrained environments (< 64 MB heap, millions of cells) where the per-cell cost of an AST tree on the heap is prohibitive. RPN maps naturally to a stack-based bytecode interpreter and is trivially JIT-compiled. LibreOffice Calc and the Excel binary formats use this model.

Real system. LibreOffice Calc (sc/source/core/tool/compiler.cxx); Apache POI formula evaluation; the Excel binary format (.xls) stores RPN token streams.

Why rejected. RPN complicates every structural-edit fixup (references are embedded as tokens in a stream; rewriting them requires deserializing the stream, patching tokens, and re-serializing). Dynamic array / spill rewriting is even harder on a token stream. AST interning (ADR-003) recovers the memory efficiency via deduplication. The added complexity of RPN is not justified given this engine's emphasis on edit correctness (Phase P9).

Alt-3: Demand-Driven Collaborative (OT/CRDT + Server-Side Recalc)

[Client A] ──op──▶ [OT/CRDT Transform Server] ──▶ [Server-Side Recalc Engine]
[Client B] ──op──▶      (conflict resolution)       ──▶ [Broadcast results]
                                                          ──▶ [Client A, B, ...]

Regime where it wins. Multi-user collaborative editing where > 1 user edits concurrently and all users must see a consistent, converging view. Google Sheets, Notion, and collaborative BI tools (Mode, Retool) use variants of this architecture. The OT/CRDT layer handles concurrent edit merging; the centralized recalc engine prevents divergent results.

Real system. Google Sheets (server-side recalc over Bigtable-backed cell store, OT for collaborative edits). ShareDB + custom formula server. Apache Wave (historical).

Why rejected. This architecture requires: (a) a centralized recalc server (no offline/WASM embedding), (b) an OT/CRDT layer (significant additional complexity; deferred, see Deferred Features Register C-4), (c) network round-trips on every edit (defeats < 2 ms incremental recalc target, §4). The sheetcalc design targets embeddable, offline, single-user-session engines. Multi-user collaboration is explicitly deferred.

Alt-4: GPU-Parallel / SIMD Bulk Evaluation Engine

[Dependency Graph] ──topo layers──▶ [GPU Kernel / SIMD Lanes]
                                          │ vectorized eval
                                          ▼
                                   [Result Buffers]

Regime where it wins. Financial risk engines, simulation models, or scientific workbooks with millions of cells performing the same arithmetic formula over columnar data arrays (e.g., =A1*B1 repeated 1M times). GPU evaluation of uniform operations achieves orders-of-magnitude throughput over CPU work-stealing. Excel 365 has experimental GPU acceleration for some functions (MMULT on large arrays).

Real system. Apache Arrow Compute (SIMD-accelerated columnar evaluation); Pandas/NumPy (vectorized CPU eval); specialized quant systems (KDB+/q for vector eval).

Why rejected. The spreadsheet formula language is heterogeneous (each cell may have a different formula), making GPU kernel dispatch impractical for the general case. SIMD works only for uniform operations over dense columns — a minor fraction of real workbooks. GPU memory transfer overhead dominates for sparse, formula-diverse workbooks. This is explicitly deferred as PhaseDeferred("Deferred Features Register"). The CPU work-stealing model (ADR-010) covers the 99th-percentile workload.
