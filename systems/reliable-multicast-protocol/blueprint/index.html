Project Name: Reliable Multicast Protocol from Scratch

Status: specification — locked

1. Goal & Scope

Engineering definition. Build a reliable multicast transport protocol and runtime — user-space sequencing, retransmission-based recovery, sender-driven congestion pacing, receiver membership coordination, and persistence-backed replay — layered over unreliable IPv4/IPv6 UDP multicast. The system delivers ordered (or explicitly partial-order) application streams to thousands of receivers from one sender socket, with bounded reorder memory, bounded retransmission amplification, and deterministic crash recovery. This is NACK-based reliable multicast in the lineage of SRM, PGM, and NORM, not a consensus system and not a reliable-broadcast (atomic broadcast) system.

Phase 0 deliverable — crates shipped:

  1. rmcast-core — shared types, error taxonomy, clock abstraction.
  2. rmcast-wire — packet header codec, version negotiation, CRC validation.
  3. rmcast-runtime — scheduler, timer wheel, lifecycle/bootstrap.
  4. rmcast-sender — sender session, sequencer, pacing.
  5. rmcast-receiver — receiver session, reorder buffer, delivery coordinator.
  6. rmcast-repair — NACK handling, suppression, repair queueing.
  7. rmcast-storage — WAL segments, sparse replay index, replay iterators.
  8. rmcast-observability — metrics, tracing, structured logging.
  9. rmcast-cli — operator inspection and replay tooling.
  10. rmcast-conformance — cross-implementation fixture harness.
  11. rmcast-fuzz — decode/replay fuzz targets.
  12. rmcast-bench — throughput and replay benchmarks.
  13. rmcast-chaos — fault-injection harness (loss, duplication, corruption).
  14. rmcast-docs — generated wire/API reference.

System boundaries — provides: multicast packet transport, sequencing and delivery-ordering semantics, NACK-based repair with suppression, sender pacing, WAL-backed replay and late-join sync, receiver membership/heartbeat tracking, metrics/tracing/structured logs for every packet lifecycle transition, operator CLI and conformance/chaos/fuzz harnesses.

Delegates: IP multicast routing correctness (IGMP/PIM) to the network fabric; wall-clock synchronization to PTP/NTP where available (see Design Principle P12); container placement and restart policy to Kubernetes; artifact signing infrastructure to Sigstore; certificate issuance to external PKI.

Does NOT provide: Byzantine fault tolerance, WAN-scale consensus, transactional guarantees, application-layer serialization frameworks, RPC semantics, kernel-bypass (DPDK/AF_XDP) networking, RDMA transports, or hardware-multicast-switch integration. Forward Error Correction, QUIC fallback, topology-aware routing, eBPF classification, and kernel-bypass transports are explicitly deferred (see Deferred Features Register, §35) — none ship in Phase 0–9.

Non-goals: exactly-once application semantics above the transport (the transport guarantees at-least-once delivery with duplicate suppression, not application idempotence); cross-datacenter WAN multicast (network fabric assumption is a single multicast-routed L3 domain or VLAN); dynamic membership consensus (membership is advisory/observational, not a quorum system).

Deployment model. Primary: Linux x86_64, containerized, Kubernetes StatefulSet, host-network UDP mode, on a dedicated multicast VLAN; optional bare-metal. Secondary: edge clusters and hybrid cloud multicast relays (unicast-tunneled repair across relay boundaries); single-node development runtime using loopback multicast for conformance and fuzz testing.

Target operators: network operators (multicast routing/IGMP validation, congestion and loss telemetry, replay storage capacity); platform engineers (stream configuration, schema/wire compatibility, observability wiring); systems engineers (congestion controller tuning, packet scheduler and persistence-adapter extension).

What later phases unlock. Phase 0 (§12) unlocks a bootable, observable runtime shell with no protocol logic. Phase 1 (§13) unlocks interoperable wire framing. Phase 2 (§14) unlocks real packet transit. Phase 3 (§15) unlocks ordering guarantees. Phase 4 (§16) unlocks scalable retransmission timing. Phase 5 (§17) unlocks loss recovery. Phase 6 (§18) unlocks durable replay and late-join. Phase 7 (§19) unlocks congestion safety at scale. Phase 8 (§20) unlocks membership visibility. Phase 9 (§21) unlocks full production observability and chaos-validated readiness.

Recommended language: Rust. Rationale: ownership semantics give compile-time enforcement of the single-owner packet-buffer rule (Design Principle P7) without a GC pause on the hot decode path; enum-driven modeling matches the wire protocol's tagged packet types (§8) exactly, with exhaustive-match compile errors on new variants; the bytes/tokio ecosystem gives zero-copy buffer slicing under packet-rate pressure; cargo-fuzz/proptest give a mature fuzzing and property-testing pipeline for the decode and replay paths (Phase 1, Phase 6). Rejected:

Language Rejection Reason
Go GC pause spikes under sustained packet-rate bursts violate the p99 publish latency budget (§4)
C++ manual buffer-ownership tracking across the sender/repair/WAL boundary raises use-after-free risk on the hot path
Java JIT warmup and GC unpredictability conflict with the <300 µs p50 publish latency budget
Erlang per-process message-passing overhead caps single-node packet throughput below the 5 Gbps target
Zig async/observability ecosystem (tracing, OpenTelemetry, mature fuzzing harness integration) is too immature for a production repair path

Prerequisites: Linux socket internals (epoll, socket buffers), UDP/IP multicast (IGMP, multicast TTL/scoping), TCP congestion-control theory (for pacing analogy, not TCP itself), lock-free/bounded queues, async runtimes (Tokio task model), memory ordering and CPU cache/NUMA behavior, binary serialization, structured logging and distributed tracing, deterministic and property-based testing, WAL/storage-engine fundamentals, crash-recovery semantics.

Estimated timeline. Phase 0: 8–12 weeks (one engineer, repo skeleton + correctness kernel). Full production system (Phases 0–9, hardened and chaos-validated): 9–14 months.

2. Why Build This

Reliable multicast sits in a historically important, narrow niche between unreliable UDP fanout and heavyweight replicated-messaging systems: it trades consensus and total ordering guarantees for fan-out scale — one sender socket, tens of thousands of receivers, no per-receiver unicast state on the sender's hot path. That tradeoff is exactly what makes it hard: recovery, congestion control, and membership must all work without the sender knowing who is listening.

Historically relevant systems: Pragmatic General Multicast (PGM, RFC 3208); NORM (RFC 5740); SRM (Scalable Reliable Multicast); Aeron; Spread Toolkit; TIBCO Rendezvous; Corosync's Totem protocol; Redis Cluster's gossip subsystem (membership analogy, not multicast transport).

Related engineering domains:

Domain Connection
Distributed databases replication transport underlies log shipping
Consensus systems ordered dissemination is a building block, not a replacement, for consensus
Trading infrastructure market-data fanout is the canonical reliable-multicast workload
Multiplayer engines state synchronization under loss and jitter
CDN infrastructure edge replication fan-out patterns
Storage systems WAL replication shares durability-before-ack semantics
Service meshes transport abstraction boundary design
Observability systems metric/log dissemination at fan-out scale

This project exercises engineering muscles rarely touched by application-stack work: timer-wheel design at millions-of-timers scale, sequence-space arithmetic and rollover safety, retransmission suppression under synchronized receiver behavior, bounded-memory recovery instead of unbounded queues, socket-buffer engineering, and tail-latency analysis under bursty loss — each is load- bearing in Phases 3–8 and each fails silently if skipped.

What Mastery Looks Like

  • Can derive a receiver reorder-buffer ceiling from a payload size and a memory budget without guessing, and defend it under burst loss — demonstrated in Phase 3 (§15).
  • Can design a suppression window that prevents synchronized-receiver NACK storms without adding unbounded repair latency — demonstrated in Phase 5 (§17).
  • Can build a timer facility that scales to millions of outstanding deadlines without per-timer heap-insert cost — demonstrated in Phase 4 (§16).
  • Can reason about congestion safety for a protocol with no per-receiver ACK stream, only aggregate loss signals — demonstrated in Phase 7 (§19).
  • Can design a WAL replay format that supports late-join synchronization and deterministic crash recovery from the same on-disk structure — demonstrated in Phase 6 (§18).
  • Can instrument a packet's full lifecycle (ingress → decode → sequence → persist → deliver) as one traced span chain without adding unbounded cardinality — demonstrated in Phase 9 (§21).
  • Can distinguish transport-layer reliability (this system) from consensus and atomic broadcast, and articulate precisely which guarantees are and are not provided — demonstrated in §33.

Sender API Runtime. Application-facing publication interface. Validates stream configuration and payload sizing (§4), stamps sequencing metadata, and enforces publication backpressure (Design Principle P3) — the concurrency boundary between application threads and the sequencing engine. Publisher throttling that fires late here is the single largest cause of downstream packet amplification.

Receiver API Runtime. Subscription-facing delivery interface. Owns delivery cursors, replay- sync windows, and subscriber isolation — the concurrency boundary between the delivery coordinator and application consumer threads. Guarantees application-visible ordering independent of repair timing (Invariant I2).

Sequencing Engine. Sole authority for monotonic packet sequence identifiers, scoped per stream session/epoch (§8). Centralizes rollover handling to avoid distributed sequence arithmetic (Invariant I1).

Delivery Coordinator. Reconciles out-of-order arrivals, retransmissions, replay streams, and duplicate suppression into one application-visible ordered (or partial-order) stream. Owns the bounded reorder buffer — a persistence boundary is crossed only when replay is invoked.

Reliable Multicast Runtime. Protocol core; owns scheduling, repair orchestration, congestion management, membership tracking, and stream lifecycle. Contains the majority of concurrency boundaries and all timing-sensitive behavior in the system.

Timer Wheel. Scalable retransmission and heartbeat scheduling queue — a hierarchical timing wheel (Varghese & Lauck 1987), not a binary heap, because heap insert/remove does not scale to millions of outstanding packet deadlines (ADR-24, §16).

WAL Storage. Persistence boundary. Packets durable here before replay eligibility (Invariant I3, Design Principle P13); enables deterministic crash recovery and late-join synchronization.

Metrics/Trace. Every packet lifecycle transition (ingress, decode, sequence, persist, deliver) emits a span and metric (Design Principle P8); this is a queue-fed sink, never a synchronous dependency of the packet path (§28).

UDP Multicast Transport. Protocol boundary and syscall boundary: socket setup, group membership (IGMP/MLD), MTU-aware packetization, checksum validation, socket-buffer sizing, batch send/receive.

Network Fabric / Repair Unicast. External trust boundaries. The fabric is assumed multicast-routing-correct but reachability is probed continuously (§14); repair unicast is a distinct trust and rate-limiting boundary from multicast ingress (Threat Model, §22).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every replay, sequencing, and retransmission decision must be reproducible from logs and persisted metadata alone · Tradeoff: forbids convenient in-memory-only heuristics · Operational: postmortems replay from WAL, not from live process state · Violated: irreproducible packet gaps and inconsistent recovery behavior across restarts.
  • P2 — Bounded Memory Everywhere. Rule: no queue, reorder buffer, or membership map may grow unbounded · Tradeoff: bounded structures drop or reject under sustained overload instead of buffering indefinitely · Operational: packet storms degrade predictably · Violated: OOM kill under sustained loss bursts, taking down unaffected streams sharing the process.
  • P3 — Backpressure Before Packet Loss. Rule: publishers see explicit throttling (Sender API Runtime, §3) before runtime queue exhaustion · Tradeoff: adds publish-path latency under load (§4 p95/p99 budgets) · Operational: throttle state is a first-class metric · Violated: silent producer-side packet loss indistinguishable from network loss.
  • P4 — Crash-Only Recovery Semantics. Rule: every subsystem recovers from a cold restart, never from in-memory self-healing · Tradeoff: forbids optimizations that assume warm caches survive a crash · Operational: recovery time is bounded and tested (§23) · Violated: undiagnosable divergence between "recovered" and "healthy" state.
  • P5 — Replayability First. Rule: every packet affecting delivery state must be replayable from the WAL · Tradeoff: costs one durable write before delivery eligibility (P13) · Operational: late-join and repair share one replay code path · Violated: late joiners and crash-recovered receivers see different history than live receivers.
  • P6 — Stable Wire Compatibility. Rule: wire protocol evolution supports rolling upgrades within a major version · Tradeoff: reserved/flags fields must stay forward-tolerant, limiting header compactness · Operational: dual-version interoperability tests gate releases (§25) · Violated: a rolling upgrade partitions the multicast group into two incompatible sub-groups.
  • P7 — Explicit Ownership Boundaries. Rule: every packet buffer has exactly one authoritative owner at any instant · Tradeoff: requires explicit hand-off (move, not alias) at every subsystem boundary · Operational: ownership transfer is a compile-time-checked type property in Rust · Violated: use-after-free or double-free under concurrent decode/persist/deliver paths.
  • P8 — Observable State Transitions. Rule: every lifecycle-significant state transition emits a metric or span · Tradeoff: telemetry cardinality must be bounded (P14) · Operational: every packet's ingress→decode→sequence→persist→deliver path is one traceable span chain (§21) · Violated: incidents without causal reconstruction, "it happened but we cannot say why."
  • P9 — Congestion Safety Over Throughput. Rule: packet-flooding behavior under loss is never acceptable, even at the cost of peak throughput · Tradeoff: caps achievable throughput below theoretical link capacity under adverse loss · Operational: retransmit amplification ceiling (§4) is enforced, not advisory · Violated: congestion collapse — repair traffic itself becomes the dominant loss cause.
  • P10 — Isolation of Slow Consumers. Rule: one receiver's backlog or slow drain must never stall delivery to other receivers · Tradeoff: requires per-receiver delivery cursors instead of one shared delivery pointer · Operational: slow receivers transition to DEGRADED (§8) independently · Violated: one misbehaving receiver silently throttles an entire fan-out group.
  • P11 — Monotonic Sequencing. Rule: sequence identifiers within a session/epoch never regress (Invariant I1) · Tradeoff: forces explicit epoch rollover instead of implicit wraparound · Operational: sequence regression is a fatal, session-terminating event · Violated: ambiguous replay ordering, duplicate or dropped delivery.
  • P12 — Time Is Approximate. Rule: the protocol never assumes synchronized clocks for correctness, only for diagnostics · Tradeoff: cannot use wall-clock ordering as a correctness mechanism, only sequence numbers · Operational: PTP sync improves diagnostics precision but is never a dependency of a correctness path · Violated: clock-skew-induced false ordering violations or spurious timeout storms.
  • P13 — Persistence Before Acknowledged Delivery. Rule: a packet must be durable in the WAL before it is replay-eligible · Tradeoff: adds one fsync-batch latency to the replay-eligibility path, not the live-delivery path · Operational: replay durability lag is a first-class metric (§23) · Violated: a "delivered" packet that cannot be replayed after a crash — silent data loss on recovery.
  • P14 — Queue Depth Is a Production Signal. Rule: every bounded queue's occupancy is exported as a metric, not just its overflow event · Tradeoff: adds a metrics-update cost to every enqueue/dequeue (§28 amortizes this via batched sampling) · Operational: queue-depth percentiles feed the DEGRADED-state transition logic (§8) · Violated: queue saturation discovered only after it has already caused packet loss.

A violated invariant fails the simulator run deterministically and reproducibly — the same seed always reproduces the same violation, which is the entire point of Design Principle P1.

8. Domain Model — Wire Protocol and Session State Machines

11. Core Schema & Types

StreamId — global multicast stream identifier; ownership: immutable after creation; mutation: none; concurrency: Copy, shared freely; persistence: WAL segment header; serialization: network byte order, fixed 8 bytes; compatibility: stable since v1, never reused across streams.

SessionEpoch — monotonic generation identifier (I5); ownership: owned by Membership Agent; mutation: increment-only, single writer; concurrency: atomic read, single-writer increment; persistence: WAL segment header and membership snapshot; serialization: u32 network byte order; compatibility: additive only, no rollback.

PacketSequence — u64 monotonic sequence scoped to (StreamId, SessionEpoch) (I1); ownership: Sequencing Engine is sole writer; mutation: increment-only, wraparound forbidden within a session lifetime; concurrency: single-writer, many-reader via atomic snapshot; persistence: WAL record key; serialization: u64 network byte order; compatibility: stable since v1.

struct PacketRecord
    stream_id: StreamId
    epoch: SessionEpoch
    sequence: PacketSequence
    payload_ref: BufferHandle
    checksum: Crc32c
    timestamp: DiagnosticTimestamp
    persistence_offset: WalOffset

Ownership: single owner per P7, transferred (moved) across the decode → sequence → persist → deliver boundary; mutation: immutable once WAL-persisted (I3); concurrency: Send, not Sync — one task owns it at a time; persistence: canonical WAL record; serialization: postcard (ADR-05); compatibility: new optional fields only, no field removal within a major version (P6).

struct DeliveryCursor
    highest_contiguous: PacketSequence
    highest_observed: PacketSequence
    pending_gaps: GapSet
    replay_position: WalOffset

Ownership: Delivery Coordinator, one per (receiver, stream); mutation: advanced only forward, never regressed; concurrency: single-writer per receiver session; persistence: periodic cursor snapshot for crash recovery; serialization: postcard; compatibility: additive fields only.

struct RepairWindow
    stream_id: StreamId
    window_start: PacketSequence
    window_end: PacketSequence
    suppression_deadline: MonotonicInstant

Ownership: Repair Coordinator; mutation: window bounds advance monotonically; concurrency: per-window lock-free CAS on suppression_deadline; persistence: not persisted, rebuilt from WAL on restart; serialization: internal only, never on the wire.

struct MembershipView
    receiver_id: ReceiverId
    join_timestamp: DiagnosticTimestamp
    last_heartbeat: MonotonicInstant
    health_state: HealthState

Ownership: Membership Agent map, keyed by ReceiverId; mutation: heartbeat-driven refresh, eviction on timeout; concurrency: sharded map, one shard lock per hash bucket; persistence: periodic membership snapshot (SNAPSHOT packet type, §8); serialization: postcard for snapshot export; compatibility: additive fields only.

struct CongestionBudget
    allowed_send_rate: BitsPerSecond
    repair_rate: BitsPerSecond
    burst_budget: Bytes
    pacing_interval: Duration

Ownership: Congestion Controller, one per sender session; mutation: recomputed per congestion epoch (§19); concurrency: single-writer, read by Pacing Scheduler via atomic snapshot; persistence: not persisted, recomputed on restart; serialization: internal only.

struct WalSegment
    segment_id: SegmentId
    start_sequence: PacketSequence
    end_sequence: PacketSequence
    checksum: Crc32c
    compression_type: CompressionType

Ownership: Storage engine; mutation: immutable once sealed, rotation creates a new segment; concurrency: append-only writer, many concurrent readers via mmap; persistence: this IS the persistence layer; serialization: fixed segment header, postcard-encoded record stream; compatibility: header versioned (I8 depends on checksum field position stability).

struct TimerSlot
    expiration_tick: WheelTick
    callback_ref: TimerCallbackId
    retry_count: u8

Ownership: Timer Wheel bucket; mutation: rescheduled on retry, cancelled on ack; concurrency: per-bucket lock, no cross-bucket locking (§16); persistence: not persisted, rebuilt from outstanding-repair state on restart; serialization: internal only.

enum RuntimeError
    WireDecodeError
    SequenceViolation
    ReplayCorruption
    CongestionViolation
    StorageUnavailable
    MembershipConflict
    RepairStormDetected
    TimerOverflow

Ownership: propagated by value, Send; mutation: immutable once constructed; concurrency: freely shared, no interior mutability; persistence: logged to structured error stream, not WAL; serialization: Display/tracing::Value, never wire-serialized; compatibility: new variants are additive, matched non-exhaustively at all call sites outside the crate that defines them.

trait PacketScheduler;
trait ReplayStore;
trait CongestionController;
trait MembershipCoordinator;
trait RepairCoordinator;
trait DeliveryPolicy;

Ownership: trait objects held behind Arc at subsystem boundaries; mutation: implementations own their internal mutability behind interior locks, never exposed through the trait surface; concurrency: every trait method signature is Send + Sync-bound; persistence: implementation- specific, not part of the trait contract; compatibility: traits are sealed within the crate that defines them until a major version, preventing external non-exhaustive implementations from breaking on additive method changes.

  1. Non-deterministic config loading order (HashMap iteration) — manifests as flaky boot-sequence fixtures; root cause: unordered map iteration feeding startup log emission; debug via runtime_boot_sequence.json diff; recovery: switch to an ordered map keyed by config-load order.
  2. Global mutable state smuggled into a lazy_static/OnceCell — manifests as test-order-dependent failures; root cause: shared process-global defeats P1 determinism; signal: tests pass alone, fail in a full suite run; recovery: thread state through explicit constructor parameters.
  3. Logger/tracing-subscriber initialization race between two startup hooks — manifests as dropped early log lines; root cause: subscriber not installed before the first tracing::info! call; signal: missing startup-phase log lines in runtime_boot_sequence.json; recovery: make subscriber install the first lifecycle hook, synchronously, before any other hook runs.
  4. Runtime shutdown deadlock between the metrics-flush hook and the WAL-flush hook waiting on each other's completion signal; root cause: circular hook dependency; recovery: enforce a strict linear shutdown-phase order (I10) with a hard per-phase timeout.

12.7 Performance Concerns

  • Allocator fragmentation from early buffer-pool warmup; pre-size pools at startup, not on first use.
  • tracing span overhead on the hot path — deferred concern here since Phase 0 has no packet path, but the subscriber filter level is set conservatively now to avoid a Phase 1+ regression.
  • Startup syscall amplification from redundant stat() calls in the config loader.

12.8 Edge Cases

  • Corrupted or truncated TOML config file — must fail closed with a structured diagnostic, not panic.
  • Partial startup failure (health probe up, metrics registry not yet attached) — must not report /readyz 200.
  • Duplicate metrics registration across two startup hooks — must fail loudly at registration time, not silently overwrite.

12.9 Failure Analysis

Runtime bootstrap failure emits a structured startup-failure event before process exit, preventing any partial subsystem activation (no half-initialized state reachable by a later phase's code). Startup diagnostics are flushed synchronously before exit, since the async telemetry pipeline may not yet be attached at failure time. Blast radius is contained to the single failed process; no shared state exists yet for cross-process contamination.

12.10 Operational Notes

Metrics: rmcast_startup_duration_seconds, rmcast_shutdown_duration_seconds. Tracing spans: runtime.bootstrap, runtime.shutdown. Structured-log fields: build_version, git_revision, feature_flags, runtime_mode. Deployment: this phase ships as the base container image tag every later phase builds on; rollback is a container-image revert with no migration since no persistent state exists yet.

13. Phase 1 — Wire Protocol & Packet Codec Engine

13.1 Objectives

  • Define the canonical wire packet header (§8) and implement deterministic encode/decode.
  • Guarantee malformed-input isolation: no decode input can crash, hang, or leak the decode worker.
  • Establish protocol version negotiation ahead of any transport or delivery logic (P6).

13.2 Detailed Implementation Steps

  1. Implement rmcast-wire/src/header.rs: packet header struct signatures matching §8's layout, fixed network byte order per RFC 3208's PGM header-encoding precedent.
  2. Implement rmcast-wire/src/codec.rs: encode/decode pipeline, CRC32C validation (I8's checksum-before-trust discipline applied identically to wire framing, not just WAL segments).
  3. Implement rmcast-wire/src/version.rs: protocol version negotiation and reserved-flag handling consistent with Design Principle P6 (rolling-upgrade wire compatibility).
  4. Add packet-size validation against the 1400 B payload ceiling (§4) before any downstream buffer allocation.
  5. Add malformed-packet counters wired to rmcast-observability (P8) — decode error is always observable.
  6. Build rmcast-fuzz/fuzz_targets/packet_decode.rs against the decode pipeline from day one.
  7. Create packet-capture replay fixtures and deterministic binary snapshots for regression coverage.
  8. Add MTU-aware fragmentation metadata fields (unused until Phase 2, defined here for wire stability).
  9. Add protocol-compatibility tests: old-decoder-reads-new-encoder and vice versa, per P6.
  10. Create packet-parsing benchmarks in rmcast-bench/benches/throughput_bench.rs.
  11. Add structured decode-error variants distinguishing malformed-CRC from malformed-length from version-mismatch.

13.3 Deliverable

A stable, fuzz-hardened packet codec library, rmcast-wire, linked identically by both sender and receiver runtimes — the single source of wire truth in the workspace.

13.4 Acceptance Criteria

  • Zero panics across 24 continuous hours of cargo-fuzz on packet_decode (ADR-13).
  • Malformed-packet rejection is deterministic: same malformed input always yields the same structured decode-error variant across 1,000 repeated decode calls.
  • Decode throughput > 3,000,000 packets/sec single-core, measured via throughput_bench (feeds §32 C12).

13.5 Conformance Fixtures

  • conformance/packet_valid_data.bin — well-formed DATA packet; expected: successful decode, exact field match.
  • conformance/packet_invalid_crc.bin — valid structure, corrupted CRC32C; expected: WireDecodeError rejection, malformed counter increments.
  • conformance/packet_truncated_header.bin — header shorter than declared header length; expected: rejection without buffer over-read.
  • conformance/packet_future_version.bin — version field ahead of the running decoder's max supported version; expected: rejection tagged as version-mismatch, not generic decode error.

13.6 Pitfalls

  1. Implicit padding bytes read as payload — manifests as off-by-N payload length; root cause: struct field alignment not matching the wire layout exactly; debug via packet_valid_data.bin byte-for-byte diff; recovery: explicit fixed-offset field reads, no derived struct layout.
  2. Endian mismatches between encode and decode paths — manifests as garbage stream_id values on cross-arch replay; root cause: relying on host-endian struct casts instead of explicit network-byte-order conversion; recovery: centralize all endian conversion in header.rs.
  3. Integer overflow on header_length + payload_length when computing total frame size — manifests as buffer over-allocation or panic on crafted input; root cause: unchecked addition; recovery: checked arithmetic with explicit rejection on overflow, exercised by the fuzz target.
  4. Version-negotiation asymmetry — decoder silently accepts a version it does not fully implement; root cause: version check treated as advisory instead of a hard capability gate; recovery: make version support an explicit allow-list, reject anything unlisted (P6).

13.7 Performance Concerns

  • Branch-heavy decode paths on packet-type dispatch — profile with criterion (ADR-17) and prefer a jump-table-friendly match over cascading if chains (still declaration-level, no bodies here).
  • Copy amplification from payload buffer duplication during decode — target zero-copy slicing.
  • Cache-line alignment of the header struct to avoid split loads on the hot decode path.

13.8 Edge Cases

  • Zero-length payload with DATA type — must decode successfully as an empty-payload packet, not reject.
  • Oversized header-length field pointing past the actual packet boundary — must reject, not read out of bounds.
  • Duplicate/contradictory flag bits set simultaneously — must reject with a specific structured error, not silently pick one.

13.9 Failure Analysis

A malformed-packet storm must not exhaust decode worker capacity: decode is bounded per-worker CPU budget with backpressure into the transport layer (Phase 2) rather than unbounded decode-queue growth (P2). Detection is the malformed-packet-rate metric crossing a rate threshold; containment is per-source-address rate limiting at the transport ingress; forensics is the sampled-and-captured malformed packet set persisted for later fuzz-corpus seeding.

13.10 Operational Notes

Metrics: rmcast_decode_errors_total{reason}, rmcast_decode_duration_seconds. Tracing span: packet.decode. Structured-log fields: decode_error_reason, packet_version. Deployment: this crate is compiled into both sender and receiver binaries; a wire-format change requires a coordinated dual-version interoperability test gate (P6) before rollout; rollback is a straight binary revert since the wire format itself did not change mid-rollout.

  • Socket FD usage stays within the 4096 budget (§4) at 200 concurrent streams (§4 horizontal target).

14.5 Conformance Fixtures

  • conformance/multicast_loopback_capture.bin — recorded loopback multicast exchange; expected: byte-identical replay through the transport layer.
  • conformance/socket_buffer_pressure.json — simulated socket-buffer-full scenario; expected: packet-drop accounting matches injected drop count exactly.

14.6 Pitfalls

  1. IGMP misconfiguration on the network fabric silently drops multicast joins — manifests as receivers never seeing DATA packets despite a healthy sender; root cause: fabric-side IGMP snooping not configured for the multicast group; debug via reachability-probe telemetry; recovery: operator runbook escalation, not a code fix.
  2. Socket buffer exhaustion under burst send — manifests as kernel-level silent drops invisible to application-level counters; root cause: default socket buffer size too small for the burst profile; recovery: explicit SO_RCVBUF/SO_SNDBUF sizing tied to §4's throughput budget.
  3. Multicast TTL misconfiguration causing packets to be dropped at the first router hop; root cause: default TTL of 1 assumed sufficient for a routed (non-VLAN-local) topology; recovery: make TTL an explicit, validated configuration field, not a silent default.
  4. Interface flap during an active session — manifests as a burst of spurious packet loss; root cause: no distinction between "route temporarily down" and "sustained partition"; recovery: reachability-probe-driven degraded-state transition instead of immediate session termination.

14.7 Performance Concerns

  • Syscall batching via sendmmsg/recvmmsg is the dominant throughput lever at the 5 Gbps target.
  • Interrupt amplification from NIC IRQ affinity mismatched to the transport worker's CPU affinity.
  • NUMA cross-node memory access when the receive ring buffer is allocated on a different socket than the polling worker — verify with perf stat NUMA counters (§28 tooling).

14.8 Edge Cases

  • Interface flap mid-session (see Pitfall 4) — must transition to degraded reachability state, not terminate.
  • Packet duplication introduced by redundant multicast routing paths — must be idempotent at this layer (dedup is Phase 3's job, not this layer's, but must not crash on it).
  • Transient route loss shorter than the reachability-probe interval — must not false-positive a fabric outage.

14.9 Failure Analysis

Transport instability must surface as a degraded-reachability signal before packet collapse: the reachability-probe failure rate crossing a threshold moves the transport into a degraded state visible to operators, distinct from and prior to actual data-plane packet loss becoming severe. Blast radius is scoped to the affected interface/socket; other transport workers on unaffected interfaces continue unaffected (P10 applied at the transport layer, not just receiver layer).

14.10 Operational Notes

Metrics: rmcast_socket_occupancy, rmcast_packet_drop_total{layer="kernel"}, rmcast_reachability_probe_failures_total. Tracing span: transport.io_poll. Structured-log fields: interface_name, multicast_group, socket_fd. Deployment: host-network mode required in Kubernetes for multicast; rollback reverts to the previous transport binary with no persistent state; migration note: changing socket-buffer defaults requires a canary rollout per §24.

15. Phase 3 — Sequencing & Delivery Engine

15.1 Objectives

  • Implement deterministic ordering semantics on top of the Phase 2 transport (Invariant I1, I2).
  • Support bounded out-of-order delivery via a reorder buffer with a hard memory ceiling (P2, §4).
  • Introduce duplicate suppression at the delivery boundary (I4) ahead of repair logic (Phase 5).

15.2 Detailed Implementation Steps

  1. Implement the Sequencing Engine (rmcast-sender/src/sequencer.rs): monotonic PacketSequence allocation scoped to (StreamId, SessionEpoch), enforcing Invariant I1 at the point of allocation.
  2. Implement DeliveryCursor (§11) tracking in rmcast-receiver/src/delivery.rs.
  3. Implement the bounded reorder buffer in rmcast-receiver/src/reorder.rs, capacity-derived from the 512 MB ceiling (§4, §32 C1) — this is the concrete embodiment of Design Principle P2.
  4. Add duplicate suppression at the delivery boundary using the dedup table referenced by I4.
  5. Implement gap tracking (GapSet in DeliveryCursor) feeding the Phase 5 repair coordinator.
  6. Add sequence-checkpoint persistence for crash-recovered cursor resumption (feeds Phase 6).
  7. Implement delivery barriers enforcing Invariant I2 (no delivery of sequence N+1 before N on an ordered stream, chain-replication-style ordered visibility per van Renesse & Schneider 2004).
  8. Add stream ordering policies: strict-order vs. explicitly-configured partial-order streams.
  9. Add replay-cursor integration points (interfaces only, wired live in Phase 6).
  10. Create ordering property tests (proptest, ADR-12) generating adversarial reorder/duplicate sequences.
  11. Implement delivery metrics: reorder-depth percentile tracking feeding P14's queue-depth signal.
  12. Add cursor-corruption detection: a DeliveryCursor whose highest_contiguous exceeds highest_observed is a hard-fail assertion.

15.3 Deliverable

A reliable, ordered packet delivery engine operating over live transport traffic, verified against the deterministic simulator with zero ordering violations across a seeded adversarial reorder corpus.

15.4 Acceptance Criteria

  • Zero ordering violations (I2) across 10,000 simulator runs with randomized packet reordering under chaos injection (§26).
  • Duplicate suppression verified: 100% of injected duplicate sequences rejected at delivery in the duplicate_packet_fixture.bin fixture.
  • Reorder buffer never exceeds the 512 MB ceiling (§4) under an 8% burst-loss injection profile.

15.5 Conformance Fixtures

  • conformance/reordered_packet_stream.bin — packets delivered out of transport order; expected: in-order delivery to the application cursor.
  • conformance/duplicate_packet_fixture.bin — repeated sequence numbers injected; expected: single delivery per sequence, duplicate counter increments.

15.6 Pitfalls

  1. Sequence rollover math error at the u64 boundary — manifests as a false sequence-regression fault near the wraparound point; root cause: signed/unsigned comparison bug; debug via a rollover-boundary property test; recovery: forbid wraparound within a session lifetime (I1) and assert it explicitly rather than relying on arithmetic to "just work."
  2. Unbounded reorder-buffer growth under sustained high-gap-count loss — manifests as OOM risk; root cause: no eviction policy once the buffer nears the 512 MB ceiling; recovery: bounded eviction with an explicit degraded-state transition (§8 DEGRADED) rather than silent growth.
  3. Delivery starvation when a low-sequence gap never resolves — manifests as all higher sequences stuck behind it; root cause: strict-order delivery barrier has no timeout escape; recovery: a configurable gap-timeout that forces a partial-order fallback or triggers repair escalation.
  4. Cursor corruption from a race between the checkpoint-persistence writer and the live-delivery advancer — manifests as highest_contiguous > highest_observed; recovery: single-writer ownership of the cursor (P7), checkpoint reads a snapshot, never a live-mutated reference.

15.7 Performance Concerns

  • Reorder-buffer heap/tree overhead for gap tracking — prefer a bitmap-backed gap set at bounded window sizes over a general-purpose sorted structure.
  • Lock contention on the DeliveryCursor between the live-delivery path and the metrics-sampling path — resolve with an atomic snapshot read for metrics, never a blocking lock.
  • Reorder-depth percentile computation cost — batch-sample rather than compute per-packet (P14 amortization).

15.8 Edge Cases

  • Delayed repairs arriving after the reorder-buffer eviction window has already passed — must be rejected as stale, not re-inserted into a closed window.
  • Replay-stream and live-stream overlap during a receiver's SYNCING→LIVE transition (§8) — must hand off without a duplicate-delivery window (I4 applies across this handoff too).

15.9 Failure Analysis

A detected sequence-space corruption (I1 or I2 violation) requires immediate session isolation: the affected receiver session transitions to FAILED/TERMINATED rather than continuing with undefined ordering. Blast radius is scoped to the single receiver session; other sessions on the same stream are unaffected (P10). Recovery path is a full replay reconciliation from the last verified checkpoint (Phase 6). Postmortem guidance: capture the reorder-buffer state snapshot at the moment of violation for offline replay against the deterministic simulator.

15.10 Operational Notes

Metrics: rmcast_reorder_depth_bucket, rmcast_duplicate_delivery_total, rmcast_delivery_order_violation_total. Tracing spans: delivery.sequence, delivery.reorder, delivery.barrier. Structured-log fields: cursor_highest_contiguous, cursor_pending_gap_count. Deployment: cursor checkpoint format is versioned (P6); migration requires a cursor-format upgrade tool run before a major-version rollout; rollback restores the prior cursor checkpoint format.

16. Phase 4 — Timer Wheel & Retransmission Scheduler

16.1 Objectives

  • Build a scalable timer facility supporting millions of concurrent retransmission/heartbeat deadlines.
  • Replace any heap-based timer approach with a hierarchical timing wheel (ADR-24) before repair logic (Phase 5) depends on it.
  • Bound timer-tick jitter within the §4 drift budget.

16.2 Detailed Implementation Steps

  1. Implement rmcast-runtime/src/timer_wheel.rs: a hierarchical timing wheel per Varghese & Lauck (1987, SOSP) — O(1) amortized insert/expire, the direct basis for ADR-24.
  2. Add timer-slot rollover handling at each wheel tier boundary (I6: ticks never regress).
  3. Implement retransmission callback dispatch distinct from heartbeat-scheduling dispatch, sharing the wheel but not the callback path.
  4. Add timeout coalescing: multiple pending retries for adjacent sequences collapse into one wheel slot where the suppression window (Phase 5, I9) allows it.
  5. Add pacing-aware retry logic: retry intervals are informed by the Congestion Controller's current pacing interval (Phase 7 dependency, wired here as an interface only).
  6. Implement timer-overflow detection (TimerOverflow variant, §11) when wheel occupancy exceeds the sizing budget derived in §32 C7.
  7. Add wheel-occupancy metrics feeding P14's queue-depth-is-a-signal principle.
  8. Create timer-determinism tests: same seeded event trace produces the same expiration order every run (P1).
  9. Add a timer-replay harness for postmortem reconstruction of a timer-driven incident.
  10. Implement cancellation semantics: a cancelled timer's slot is freed without leaving a dangling callback reference (P7 applied to TimerSlot).
  11. Add wheel-corruption checks: a TimerSlot pointing at an already-freed bucket is a hard-fail assertion (I6 enforcement).

16.3 Deliverable

A production timer subsystem supporting retransmission and heartbeat coordination at the target cardinality, verified deterministic under the replay harness.

16.4 Acceptance Criteria

  • Sustains 5,000,000 concurrently active timers (§32 C7 sizing) without wheel-occupancy overflow.
  • p99 scheduling jitter < 2 ms under full load, measured via timer_rollover.json replay.
  • Zero tick regressions (I6) across a 10,000-cycle clock-jump stress fixture.

16.5 Conformance Fixtures

  • conformance/timer_rollover.json — wheel-tier rollover boundary trace; expected: deterministic expiration order preserved across rollover.
  • conformance/timer_cancel_race.json — concurrent cancel-and-expire race; expected: no dangling callback dispatch, cancellation wins if it precedes expiration.

16.6 Pitfalls

  1. Timer drift accumulating across wheel-tier promotions — manifests as jitter exceeding the 1 ms budget (§4) only after sustained runtime, not immediately; root cause: tick-interval rounding error compounding per promotion; recovery: carry sub-tick remainder explicitly rather than truncating at each tier boundary.
  2. Callback starvation when one wheel bucket accumulates disproportionate load (hot-key sequence ranges under correlated loss) — manifests as delayed retransmission for an unlucky subset of packets; root cause: naive modulo-based bucket assignment; recovery: bucket-load-aware assignment or secondary hashing within a bucket.
  3. Overflow loops when a retry re-schedules itself into an already-overflowing tier — manifests as a runaway retry storm; root cause: no backoff cap on rescheduled retry count; recovery: cap retry_count (§11 TimerSlot) and escalate to repair-storm detection (RepairStormDetected, §11) past the cap.

16.7 Performance Concerns

  • Cache locality of timer buckets — contiguous per-tier bucket arrays outperform pointer-chased structures at this cardinality; verify with L3 cache-miss profiling (§4 L3 > 24 MB assumption).
  • Wakeup amplification: one wheel tick should not require waking every worker thread, only the ones with populated buckets in that tick.

16.8 Edge Cases

  • Clock jumps (NTP step correction) — must not be interpreted as legitimate tick advancement (P12: never trust wall-clock for correctness); the wheel driver uses the monotonic clock exclusively.
  • Delayed scheduler ticks under CPU starvation — must catch up deterministically (process all missed ticks in order) rather than skip to "now."

16.9 Failure Analysis

Timer corruption (I6 violation, or a wheel-occupancy overflow past the TimerOverflow threshold) must fail closed: the affected timer subsystem forces a runtime restart (P4, crash-only recovery) rather than attempting in-memory repair of a corrupted wheel structure. Detection is the tick-monotonicity assertion; blast radius is the whole runtime process since the wheel is a single shared structure, which is why the overflow threshold (§32 C7) is sized with margin.

16.10 Operational Notes

Metrics: rmcast_timer_wheel_occupancy, rmcast_timer_tick_jitter_seconds, rmcast_timer_overflow_total. Tracing span: timer.tick, timer.expire. Structured-log fields: wheel_tier, bucket_id, retry_count. Deployment: wheel sizing constants are compile-time configured per §32 C7's derivation; changing them requires a rebuild, not a config hot-reload; rollback is a binary revert with wheel state rebuilt fresh from outstanding-repair state (not persisted, per §11).

17. Phase 5 — Repair Coordination & NACK Suppression

17.1 Objectives

  • Implement scalable NACK-based packet repair on top of the Phase 3 gap-tracking data (GapSet, §11).
  • Prevent repair storms from synchronized-receiver retry behavior (Invariant I9, Design Principle P9).
  • Keep retransmission amplification within the 1.5x ceiling (§4, Invariant I7) under 8% burst loss.

17.2 Detailed Implementation Steps

  1. Implement rmcast-repair/src/nack.rs: NACK packet handling per the SRM suppression model (Floyd, Jacobson, Liu, McCanne & Zhang 1997) — receiver-side NACK generation gated by the reorder gap set.
  2. Implement rmcast-repair/src/suppression.rs: suppression-window cache enforcing I9 — one active repair request per packet window per suppression interval.
  3. Implement rmcast-repair/src/repair_queue.rs: repair batching and deduplication, feeding the Timer Wheel (Phase 4) for retry scheduling.
  4. Add receiver repair cooldowns: after a NACK is suppressed, the receiver backs off before re-NACKing (P9).
  5. Add repair-retry budgets bounded by TimerSlot.retry_count (§11), escalating to RepairStormDetected (§11) past the cap.
  6. Implement repair prioritization: oldest-gap-first within the retention window (§4).
  7. Add repair tracing spans distinct from live-delivery spans (P8) for postmortem separation.
  8. Create repair chaos tests injecting correlated multi-receiver loss to exercise suppression under the worst case: many receivers NACKing the same gap simultaneously.
  9. Add amplification-protection: reject repair scheduling once the rolling amplification ratio (I7) approaches the 1.5x ceiling, escalating to the Congestion Controller (Phase 7 interface).
  10. Implement suppression caches with bounded memory (P2) — LRU eviction, not unbounded growth.
  11. Add repair-histogram metrics for operator dashboards (§24).
  12. Note: Forward Error Correction as a loss-recovery alternative to NACK-based repair is explicitly out of scope for this phase — PhaseDeferred("§17") (register in §35); NORM (RFC 5740) is the reference design this would draw from if un-deferred.

17.3 Deliverable

A repair subsystem that holds retransmission amplification under the §4 ceiling while surviving burst packet loss and synchronized-receiver NACK storms, verified under chaos injection.

17.4 Acceptance Criteria

  • Retransmission amplification stays < 1.5x (I7) under the repair_gap_burst.bin fixture's 8% burst-loss profile.
  • Repair success rate > 99.5% measured over a 1-hour chaos run with correlated multi-receiver loss.
  • Suppression collisions (I9) resolve deterministically: exactly one active repair per window per suppression interval, verified across 10,000 simulator runs.

17.5 Conformance Fixtures

  • conformance/repair_gap_burst.bin — correlated multi-gap burst loss; expected: amplification ratio stays under 1.5x, all gaps eventually repaired.
  • conformance/nack_suppression_overlap.bin — overlapping NACKs for the same window from multiple receivers; expected: single repair scheduled, suppression collision counter increments for the redundant NACKs, no duplicate REPAIR sent.

17.6 Pitfalls

  1. Repair storms from synchronized receiver retry timers — manifests as a retransmission spike that itself causes further loss; root cause: receivers sharing a common retry backoff schedule with no jitter; debug via the repair-amplification-ratio metric spiking in lockstep with a NACK-rate spike; recovery: jittered receiver backoff plus sender-side suppression (I9).
  2. Duplicate retransmissions for the same gap from two independent suppression-cache shards; root cause: suppression cache sharded by receiver rather than by (stream, window), so two receivers' NACKs for the same gap land in different shards and both get serviced; recovery: shard the suppression cache by (stream_id, window), not by receiver.
  3. Stale repairs delivered after the requesting receiver's reorder-buffer window has already evicted that range (Phase 3 dependency) — manifests as a wasted repair send; root cause: no cross-check between repair-request age and the requester's known eviction policy; recovery: tag NACKs with the requester's current window bound, drop repair requests past it.

17.7 Performance Concerns

  • Hash-table churn in the suppression cache under high gap-cardinality bursts — size the cache against the expected burst profile (8% loss, §4) rather than growing reactively.
  • Repair-queue pressure: prioritized-oldest-first (17.2 step 6) must not starve newer, still-live gaps indefinitely — cap the reprioritization window.

17.8 Edge Cases

  • Simultaneous multi-gap loss spanning multiple suppression windows at once — must not let one window's suppression state leak into an adjacent window's accounting.
  • Stale repairs arriving for a session that has since terminated (Phase 3 FAILED transition) — must be dropped, not misattributed to a new session reusing the same receiver ID.

17.9 Failure Analysis

Repair overload (amplification ratio approaching or exceeding the I7 ceiling) transitions the runtime into a degraded mode (§8 DEGRADED): repair scheduling is throttled before congestion collapse, with the throttle decision escalated to and coordinated with the Phase 7 Congestion Controller. Detection is the amplification-ratio metric; blast radius is bounded to the affected stream's repair traffic, not the whole node, since suppression caches are per-stream.

17.10 Operational Notes

Metrics: rmcast_repair_amplification_ratio, rmcast_repair_suppression_collision_total, rmcast_repair_success_ratio. Tracing spans: repair.nack_receive, repair.suppress, repair.dispatch. Structured-log fields: repair_window_start, repair_window_end, suppression_cache_shard. Deployment: suppression-window sizing (§32 C9) is a hot-reloadable config value; rollback of a bad suppression-window change is immediate without a restart.

18. Phase 6 — WAL Persistence & Replay Engine

18.1 Objectives

  • Implement durable, append-only WAL storage (ADR-04) satisfying Invariant I3 (replay durability before eligibility).
  • Support deterministic crash recovery and late-join synchronization from the same on-disk structure (P5, P4).
  • Enforce the write-amplification budget (§4: < 2.3x) and the replay-backlog ceiling (§4: 50 M packets).

18.2 Detailed Implementation Steps

  1. Implement rmcast-storage/src/segment.rs: WalSegment (§11) format — append-only, sealed on rotation, CRC32C-checksummed (ADR-04's append-only WAL design, enforcing I8).
  2. Implement rmcast-storage/src/wal.rs: append-only writer with fsync batching, modeled on the log-segmentation pattern of Kafka's log subsystem (studied in §5 Reference Implementations).
  3. Implement rmcast-storage/src/index.rs: sparse mmap replay index (ADR-04 sparse mmap index) for O(log n) lookup by sequence without a full B-tree.
  4. Implement rmcast-storage/src/replay.rs: replay iterators shared by both crash-recovery and late-join code paths (P5 — one replay path, not two).
  5. Add segment rotation policy tied to the 50 M-packet replay-backlog ceiling (§4, §32 C3).
  6. Implement retention eviction: oldest segments beyond the retention policy (§8) are reclaimed, never mid-segment-truncated (I8 integrity).
  7. Add mmap read path for zero-copy replay serving to late-joining receivers.
  8. Implement corruption quarantine: a segment failing checksum verification (I8) is isolated, not deleted, and excluded from the replay index without blocking replay of adjacent good segments.
  9. Add replay checkpointing tied to DeliveryCursor persistence (Phase 3 dependency).
  10. Create crash-recovery tests: kill -9 mid-write, restart, verify deterministic recovery to the last fully-fsynced record (van Renesse & Schneider 2004's durability-before-visibility model applied here).
  11. Add WAL metrics: durability lag, segment count, quarantine count.
  12. Implement fsync batching tuned against the RPO budget (§4: < 5 s).
  13. Add replay-snapshot export (SNAPSHOT packet type, §8) for cross-node bootstrap.
  14. Implement WAL compaction metadata (interfaces only) — full compaction logic is out of scope for this phase; persistent snapshot compression specifically is PhaseDeferred("§18") (register in §35).

18.3 Deliverable

A persistent replay engine supporting deterministic crash recovery within the RTO budget and late-join synchronization via the same replay-iterator code path used for recovery.

18.4 Acceptance Criteria

  • Crash recovery completes in < 2 minutes (§4 RTO) on a 50 M-packet backlog, measured from process restart to /readyz 200 with the replay index fully rebuilt.
  • Replay output is byte-identical across repeated runs against wal_replay_snapshot.json (P1 determinism).
  • WAL write amplification stays < 2.3x (§4) measured as bytes-written-to-disk / raw-payload-bytes over a 1-hour sustained-load run.

18.5 Conformance Fixtures

  • conformance/wal_corrupted_segment.bin — a segment with a deliberately corrupted checksum; expected: quarantine, adjacent segments replay normally.
  • conformance/wal_partial_write.bin — a torn write (process killed mid-fsync-batch); expected: recovery truncates to the last verified record, no corrupted tail replayed.
  • conformance/wal_replay_snapshot.json — a recorded full-replay output; expected: byte-identical regression match on every run.

18.6 Pitfalls

  1. Torn writes from a crash mid-fsync-batch — manifests as a segment tail that looks structurally valid but is semantically incomplete; root cause: fsync batch boundary not aligned with a checksum-verifiable record boundary; recovery: checksum each fsync-batch boundary, not just each segment.
  2. mmap invalidation when a segment is rotated out from under an in-progress mmap read — manifests as a read-path segfault or garbage read; root cause: unmap-before-all-readers-done race; recovery: reference-counted segment handles, unmap only after the last reader releases.
  3. Retention-eviction races with an in-progress replay reading from the segment being evicted; root cause: eviction policy has no visibility into active replay readers; recovery: eviction defers to the oldest active replay cursor, never evicts a segment a live replay still needs.

18.7 Performance Concerns

  • fsync latency is the dominant cost on the durability-before-eligibility path (P13) — batch fsyncs against the RPO budget (§4), not per-record.
  • Page-cache pressure from mmap'd replay reads competing with the append-only writer's dirty pages — monitor via perf page-fault counters (§28).

18.8 Edge Cases

  • Disk full during an active append — must fail the write explicitly (transition sender to FAILED, §8) rather than silently drop the record.
  • Partial segment corruption affecting only the tail of an otherwise-valid segment — quarantine must be range-scoped, not whole-segment, where the checksum boundary allows it.

18.9 Failure Analysis

A corrupted WAL segment is isolated (quarantined) without causing a global replay failure — adjacent good segments continue to serve replay traffic. Detection is the checksum-verification failure at read time (I8); blast radius is scoped to the sequence range covered by the quarantined segment; recovery path is re-deriving that range from a peer node's replay (Phase 8 membership awareness) if available, or accepting a bounded data-loss window within the RPO budget.

18.10 Operational Notes

Metrics: rmcast_wal_durability_lag_seconds, rmcast_wal_write_amplification_ratio, rmcast_wal_quarantine_total. Tracing spans: wal.append, wal.fsync, wal.replay_read. Structured-log fields: segment_id, start_sequence, end_sequence. Deployment: WAL segment format is versioned (P6, compatibility §25: forward-readable within a major version); migration requires an offline segment-format upgrade tool for a major-version rollout; rollback restores the prior binary against unmodified on-disk segments since the format did not change mid-rollout.

19. Phase 7 — Congestion Control & Flow Regulation

19.1 Objectives

  • Implement congestion-aware sender pacing (ADR-23: BBR-inspired model-based pacing) stabilizing multicast throughput without a per-receiver ACK stream.
  • Keep retransmission traffic within the amplification ceiling under load (I7, coordinated with Phase 5).
  • Avoid congestion collapse under sustained loss (P9) while meeting the publish-latency budgets (§4).

19.2 Detailed Implementation Steps

  1. Implement rmcast-sender/src/pacing.rs: RTT estimation and a token-bucket pacing scheduler modeled on BBR's bandwidth-and-RTT probing (Cardwell, Cheng, Gunn, Yeganeh & Jacobson 2016) rather than Reno-style loss-reactive AIMD (Jacobson 1988), per ADR-23.
  2. Implement congestion-epoch state (CongestionBudget, §11): allowed_send_rate, repair_rate, burst_budget, pacing_interval, recomputed once per epoch.
  3. Add token-bucket shaping enforcing the epoch's allowed_send_rate at the Sender API Runtime boundary (§3, P3 backpressure).
  4. Add repair-bandwidth budgeting distinct from primary-send budgeting — repair traffic draws from its own sub-budget within the I7 ceiling, coordinated with Phase 5's amplification-protection hook.
  5. Implement burst suppression: a burst budget caps how much of the epoch's rate can be spent instantaneously versus paced.
  6. Implement receiver feedback aggregation: since there is no per-receiver ACK stream, aggregate loss/repair-rate signals from NACK volume (Phase 5) stand in for BBR's delivery-rate signal.
  7. Add adaptive pacing-interval adjustment per congestion epoch based on aggregate loss trend.
  8. Create a congestion simulation harness injecting controlled loss profiles (0–8%, §4 ceiling) to validate pacing stability.
  9. Add overload telemetry: pacing-interval trend, throttle-state transitions.
  10. Implement fairness validation across multiple concurrent streams sharing a sender node (no single stream starves another's pacing budget).
  11. Add sender throttle states (§8 THROTTLED) wired to the epoch's computed allowed_send_rate dropping below the publisher's requested rate.

19.3 Deliverable

A congestion-aware sender that sustains stable throughput under injected loss up to the §4 burst ceiling without triggering congestion collapse, verified against the simulation harness.

19.4 Acceptance Criteria

  • Stable throughput (no collapse, defined as sustained rate not dropping more than 20% below the loss-adjusted theoretical ceiling) maintained under a 5% packet-loss injection for 30 minutes.
  • No congestion collapse observed across the full 0–8% loss sweep (§4 burst ceiling) in the congestion_burst_trace.json fixture.
  • p99 publish latency stays < 10 ms (§4) even while THROTTLED, verified via throttle_transition.json.

19.5 Conformance Fixtures

  • conformance/congestion_burst_trace.json — a recorded loss-injection sweep from 0–8%; expected: pacing-interval trend matches the model prediction, no collapse.
  • conformance/throttle_transition.json — a sender transitioning ACTIVE→THROTTLED and back; expected: publish latency budget (§4) held throughout the transition.

19.6 Pitfalls

  1. Over-aggressive pacing reduction on a transient loss spike that is not sustained congestion — manifests as unnecessary throughput loss; root cause: reacting to instantaneous loss samples rather than a windowed trend; recovery: require a sustained-trend threshold (multiple congestion epochs) before reducing allowed_send_rate, per BBR's model-based (not instantaneous) philosophy.
  2. Feedback oscillation between the pacing scheduler and the aggregated NACK-rate signal — manifests as a throughput sawtooth despite BBR-style pacing being chosen specifically to avoid this (ADR-23's rationale); root cause: congestion-epoch interval too short relative to the RTT used for feedback aggregation; recovery: epoch interval floor tied to measured RTT, not a fixed constant.

19.7 Performance Concerns

  • Timer churn from per-epoch pacing-interval recomputation feeding back into the Phase 4 timer wheel — batch epoch transitions rather than rescheduling every outstanding timer per epoch.
  • Pacing precision: token-bucket refill granularity must be fine enough to hit the p50 publish latency budget (§4: < 300 µs) without coarse-grained scheduling jitter dominating it.

19.8 Edge Cases

  • Asymmetric packet loss (heavy loss to a subset of receivers, none to others) — the aggregate NACK-rate signal must not let a minority of lossy receivers force global sender throttling that penalizes healthy receivers (tension with P10 isolation, resolved via per-receiver-class weighting).
  • Delayed NACKs arriving after the congestion epoch that generated the underlying loss has already closed — must be attributed to the correct historical epoch for accurate rate-trend modeling, not counted against the current epoch.

19.9 Failure Analysis

Congestion instability (repeated epoch-over-epoch rate oscillation past a stability threshold) escalates to sender throttling (§8 THROTTLED) as a deliberate, visible, operator-inspectable state rather than an invisible internal retry loop. Detection is the pacing-interval variance metric; blast radius is the affected sender session only; recovery path is a forced epoch reset to a conservative baseline rate, with telemetry marking the reset event for postmortem correlation.

19.10 Operational Notes

Metrics: rmcast_pacing_interval_seconds, rmcast_congestion_epoch_total, rmcast_sender_throttle_state. Tracing span: congestion.epoch_transition. Structured-log fields: epoch_id, allowed_send_rate_bps, throttle_reason. Deployment: pacing-model constants are hot-reloadable; rollback of a bad pacing-model tuning change takes effect at the next congestion-epoch boundary, not immediately, by design (avoids mid-epoch discontinuity).

20. Phase 8 — Membership & Session Coordination

20.1 Objectives

  • Manage receiver lifecycle state (JOIN/LEAVE/heartbeat) and maintain fan-out membership visibility at the 50,000-receiver target (§4).
  • Enforce membership-epoch monotonicity (Invariant I5) across churn without adopting a token-passing membership protocol (rejected in ADR analysis, §9's Corosync-study note).
  • Support split-brain detection without a full consensus system (explicit non-goal, §1).

20.2 Detailed Implementation Steps

  1. Implement rmcast-runtime membership module: JOIN/LEAVE packet handling (§8) updating the MembershipView map (§11), sharded by receiver-ID hash for concurrent access (P7 ownership: one shard lock per bucket).
  2. Add heartbeat tracking with a configurable interval and staleness timeout.
  3. Implement membership epochs (SessionEpoch, I5) — advisory, observational, not a quorum mechanism, distinguishing this from Corosync's Totem token-ring membership (studied in §5, rejected for this scale in §9 ADR discussion and §34 Alt C).
  4. Add stale-receiver eviction once the heartbeat timeout is exceeded, transitioning the receiver to TERMINATED (§8).
  5. Implement health scoring blending heartbeat recency and delivery-cursor lag (P10 slow-consumer signal).
  6. Add membership snapshots (SNAPSHOT packet type, §8) for operator visibility and cross-node bootstrap.
  7. Implement receiver quarantine: a receiver exhibiting pathological NACK volume (feeding Phase 5's amplification protection) is isolated from suppression-cache sharing without being fully evicted.
  8. Add operator membership APIs (rmcast-cli) for live membership inspection.
  9. Create churn stress tests: high JOIN/LEAVE rate against the 50,000-receiver target, verifying map-sharding scalability.
  10. Add session reconciliation after a network partition heals, resolving divergent membership views.
  11. Implement split-brain detection: two membership views disagreeing on the current epoch trigger a reconciliation event (I5), not a silent merge.

20.3 Deliverable

A membership-aware runtime that tracks receiver lifecycle at the 50,000-receiver target with bounded convergence time and observable health scoring, without adopting a consensus protocol.

20.4 Acceptance Criteria

  • Supports 50,000 concurrent receivers per stream (§4) with the churn stress fixture at a sustained 500 JOIN/LEAVE events/sec.
  • Membership convergence (all shards agree on current epoch) completes in < 10 seconds after a churn burst, measured via membership_churn_trace.json.
  • Stale-receiver eviction fires within 2x the configured heartbeat timeout, verified against receiver_timeout_fixture.json.

20.5 Conformance Fixtures

  • conformance/membership_churn_trace.json — a recorded high-churn JOIN/LEAVE sequence; expected: convergence within the 10 s budget, no epoch regression (I5).
  • conformance/receiver_timeout_fixture.json — a receiver that stops heartbeating; expected: eviction within 2x the heartbeat timeout, health-score degradation visible before eviction.

20.6 Pitfalls

  1. Stale heartbeats processed out of order (a delayed heartbeat arriving after a later one) reset the staleness timer incorrectly — manifests as an unresponsive receiver appearing falsely healthy; root cause: heartbeat timestamp not compared against the last-seen sequence for that receiver; recovery: only accept a heartbeat if its sequence is newer than the last recorded one.
  2. Split-brain membership after a partition heals with two shards holding different epoch values for the same stream — manifests as inconsistent operator-visible membership counts; root cause: no explicit reconciliation trigger on partition-heal detection; recovery: epoch-mismatch detection (20.2 step 11) forces an explicit reconciliation pass, never a silent higher-epoch-wins merge without an audit log entry.

20.7 Performance Concerns

  • Membership-map churn under high JOIN/LEAVE rate — sharding (20.2 step 1) bounds per-shard lock contention, but shard count must scale with the 50,000-receiver target, not a fixed small constant.
  • Heartbeat-processing amplification at scale: 50,000 receivers at even a modest heartbeat interval is a meaningful steady-state packet rate — batch heartbeat processing per polling tick rather than per-packet dispatch.

20.8 Edge Cases

  • Receiver clock skew affecting heartbeat interpretation — heartbeat staleness must be judged by the receiving node's monotonic clock (P12), never by a timestamp embedded by the (possibly skewed) remote receiver.
  • Duplicate receiver IDs from a misconfigured deployment — must be detected and rejected at JOIN time (membership conflict, RuntimeError::MembershipConflict, §11), not silently overwrite the existing membership entry.

20.9 Failure Analysis

Membership corruption (an I5 epoch-regression detection, or an unresolved split-brain past a reconciliation deadline) triggers an epoch rollover: the stream's membership state is reset to a fresh epoch and all receivers are required to re-JOIN, a deliberately visible, disruptive-but-safe recovery rather than attempting a silent partial reconciliation that risks masking the corruption.

20.10 Operational Notes

Metrics: rmcast_membership_cardinality, rmcast_membership_epoch_total, rmcast_receiver_health_score. Tracing spans: membership.join, membership.heartbeat, membership.reconcile. Structured-log fields: receiver_id, health_state, epoch_id. Deployment: membership-shard count is a startup-time (not hot-reloadable) configuration; changing it requires a rolling restart with a membership-snapshot-based rehydration, not a live resharding.

  • Metrics-allocation pressure from per-packet metric updates — batch-sample (P14 amortization, consistent with §15's reorder-depth batching).

21.8 Edge Cases

  • Telemetry backend outage (Prometheus/OTel collector unreachable) — must degrade to local buffering with bounded memory (P2), never block the packet path waiting on a telemetry sink (P8's queue-fed, never-synchronous rule).

21.9 Failure Analysis

An observability-subsystem failure (telemetry backend outage, log disk exhaustion) must not destabilize the packet runtime: every telemetry path is queue-fed with explicit backpressure (P8), so a stalled sink degrades observability fidelity, not packet-path throughput or latency. Blast radius of an observability failure is confined to diagnostic visibility; a full incident postmortem in this state relies on whatever was captured before the outage plus the failure-snapshot dump mechanism, which writes to local disk independent of the network telemetry path.

24. Operational Readiness

Metrics strategy. Six metric classes cover the system: packet throughput, repair efficiency (amplification ratio, I7), replay lag (RPO tracking), congestion state (pacing interval, throttle state), queue occupancy (P14, every bounded queue named in §12–§20), WAL durability latency (fsync-batch lag against the RPO budget, §4). Every metric named in a phase's Operational Notes (§12.10–§21.10) is scraped by the Prometheus exporter (ADR-11) with the cardinality guard (I12) enforced at registration, not at query time.

Tracing strategy. Every packet receives one causal span chain: ingress → decode → sequence → persist → deliver (§3, §21), following the Dapper model (Sigelman et al. 2010). Sampling policy (§21.2) bounds tracing overhead; 100% sampling is reserved for chaos runs and incident replay, not steady-state production traffic, per MM8's never-a-second-failure-domain principle.

Alerting philosophy. Alerts target leading indicators, not just outages: sustained packet loss above the 8% burst-tolerance ceiling (§4) for longer than one suppression window (§32 C9); repair amplification approaching the 1.5x ceiling (I7) before it is breached; replay-lag trending toward the RPO budget; queue-depth percentiles crossing a DEGRADED-state threshold (§8) before actual packet loss; congestion-epoch pacing-interval variance exceeding the stability threshold (§19.9).

Deployment strategy. Canary deployment on a subset of receivers before a full rolling upgrade; dual-version interoperability tests (P6, §25) gate every canary promotion; replay-compatibility validation runs the new binary's replay path against WAL segments written by the previous version before promotion; rolling upgrades proceed one StatefulSet replica at a time with a health-probe gate (§12) between replicas.

26. Testing & Verification Strategy

Unit testing. Packet parsing (§13), timer scheduling (§16), congestion arithmetic (§19) — pure-function-level coverage on decode, sequence allocation, and pacing-interval computation.

Integration testing. Multi-node delivery across a 3-node loopback/LAN topology (§14), replay synchronization between a live sender and a late-joining receiver (§18), rolling-upgrade dual-version interoperability (§25).

Property testing (proptest, ADR-12). Sequence monotonicity (I1) under adversarial reorder input; duplicate suppression (I4) under adversarial replay input; replay determinism (P1) — same seed always produces the same replay output.

Fuzzing (cargo-fuzz, ADR-13). Packet decoders (rmcast-fuzz/fuzz_targets/packet_decode.rs, §13); WAL segment readers and replay iterators (rmcast-fuzz/fuzz_targets/wal_replay.rs, §18) — both run continuously in CI (fuzz.yml) with corpus persistence across runs.

Chaos testing (rmcast-chaos, §21). Injected faults: packet loss (0–8% sweep, §4), packet duplication, packet corruption, latency spikes, and node restarts — run for 4 continuous hours per release candidate (§21.4), validating every invariant in §7 fires its telemetry on violation and that no fault's blast radius exceeds its documented containment boundary (§23).

Deterministic simulator (§7, §21). One assertion per system invariant, fed a seeded adversarial event trace; this is the primary tool for both pre-release verification and postmortem replay — the same seed reproduces the same violation deterministically (P1), which is why it is load-bearing across nearly every phase's Failure Analysis subsection.

Reproducible builds. Pinned dependencies (Cargo.lock, ADR-03), deterministic compiler flags, stable embedded timestamps — a rebuild from the same git SHA on two different machines produces a bit-identical binary (ADR-19), verified in CI (§12.4's acceptance gate).

Artifact signing. All release binaries and container images signed via Sigstore keyless signing (ADR-17); signature verification is enforced at deploy time (T5, T12, §22), not merely advisory.

SBOM generation. CycloneDX SBOM artifacts generated for every release, feeding the dependency- audit gate (cargo-audit, ADR-03) and the supply-chain threat mitigation (T5).

Release channels. Nightly (every merge to main, no compatibility guarantee), beta (weekly, dual-version interoperability tested), stable (monthly, full chaos-suite gated), LTS (quarterly, extended patch-support window) — per ADR-18. 29. Scalability Analysis

Bottlenecks. Repair amplification (§17, I7) is the first ceiling hit under sustained loss — it is deliberately the tightest-coupled constraint in the system (P9). WAL IO bandwidth (§18, §32 C6) is the second — at 1.44 GB/s required sustained write throughput, this is an SSD-mandatory design, not an optimization. Timer-wheel saturation (§16, §32 C7) is the third, bounded by the 5 M active-timer sizing. Receiver-membership churn (§20) is the fourth, bounded by the 5,000 receivers/s heartbeat-processing floor (§32 C10).

Horizontal scaling. Scale by stream partitioning — each stream is independent (no cross-stream coordination beyond shared node resources), so the 200-stream horizontal target (§4) scales by adding sender-side shards, not by making one stream's runtime bigger. Sender sharding splits a single logical stream's publish load across multiple sender processes once a single sender's throughput approaches the 5 Gbps ceiling (§4). Replay isolation ensures one stream's WAL segment set never blocks another's replay reader (§18.6 pitfall 3's fix generalizes here).

Vertical scaling. CPU affinity pins transport workers (§14) and timer-wheel tick drivers (§16) to dedicated cores, avoiding scheduler-induced jitter. NUMA-aware memory allocation (§4 dual-socket assumption) keeps receive ring buffers (§14) local to the polling worker's socket. Socket parallelism (multiple sockets per stream, SO_REUSEPORT-style fan-out) is the mechanism by which the 64-core vertical target (§4, §32 C12) is actually reached without one socket becoming a serialization point.

30. Mental Models & First Principles

  • MM1 — Suppression Is a Rate Limiter, Not a Correctness Mechanism. Suppression windows bound repair-traffic rate; they do not by themselves guarantee eventual delivery. Predicts: sustained loss still needs a retry/timeout escalation path beyond suppression alone. Bug class without it: assuming "suppressed" means "handled" and omitting the escalation path, causing silent permanent gaps. Applies in §17.
  • MM2 — Bounded Memory Beats Optimal Memory. A hard ceiling with predictable degradation (P2) beats an unbounded structure that is usually smaller but occasionally OOMs. Predicts: burst loss eventually hits the ceiling, so eviction policy is never optional. Bug class without it: sizing structures for the common case and getting paged on the tail case. Applies in §15.
  • MM3 — No Per-Receiver ACK Means Aggregate Signals Only. Multicast congestion control cannot see individual receiver health directly, only aggregate NACK volume. Predicts: any per-receiver fairness mechanism must be inferred, never directly measured. Bug class without it: designing the controller as if it had a TCP-style per-flow ACK clock. Applies in §19.
  • MM4 — Persistence-Before-Delivery Inverts the Usual Latency Tradeoff. Durability gates replay-eligibility, not live delivery (P13); live delivery is faster than durable-replay-eligible. Predicts: "delivered" and "replayable" are different guarantees with different latencies. Bug class without it: assuming delivered implies replayable and being surprised by a post-crash recovery gap. Applies in §18.
  • MM5 — A Timer Facility's Scaling Bound Is Insert/Expire Cost, Not Storage. At millions of timers, per-operation complexity (O(1) wheel vs. O(log n) heap) dominates, not raw memory. Predicts: a heap-based timer looks fine in a unit test and fails only at production cardinality. Bug class without it: benchmarking a timer facility at the wrong scale and shipping a heap. Applies in §16.
  • MM6 — Membership Is Advisory, Not a Quorum. This system's membership view optimizes repair targeting and telemetry; it is never a correctness dependency. Predicts: a split-brain membership view degrades efficiency, not correctness. Bug class without it: building delivery-ordering logic that depends on membership agreement, silently reintroducing the consensus dependency the architecture explicitly avoided. Applies in §20.
  • MM7 — Sequence Numbers Are the Only Trustworthy Clock. Wall-clock and cross-node monotonic-clock readings cannot be trusted for ordering (P12); only the single-authority sequence number can. Predicts: any ordering logic keyed on timestamp instead of sequence misorders under clock skew. Bug class without it: a "sort by timestamp" shortcut that works with synced dev clocks and misorders in production. Applies in §15.
  • MM8 — Observability Must Never Become a Second Failure Domain. Telemetry paths are queue-fed and backpressured (P8) specifically so a telemetry outage cannot cause a packet-path outage. Predicts: any synchronous telemetry call on the hot path reintroduces exactly the coupling this principle forbids. Bug class without it: a "temporary" synchronous metrics-export call that becomes a production outage cause. Applies in §21.

  • Aeron — chose term-buffer credit-based flow control over a suppression-window NACK model; wins where IPC-grade single-digit-microsecond latency matters more than fan-out-scale reliable-multicast recovery.
  • Apache Kafka — chose broker-replicated log ordering with client pull over push-based multicast fan-out; wins where consumers tolerate broker-mediated delivery and want strong per-partition ordering with replay as a first-class API, not just a recovery path.
  • Corosync (Totem) — chose single-ring token-passing virtual synchrony over NACK-based suppression; wins at small-to-medium cluster membership (tens to low hundreds of nodes) where strict total order matters more than fan-out to tens of thousands of receivers.
  • NATS JetStream — chose a clustered, Raft-backed file store with client-driven replay over a multicast wire protocol; wins where consumers already speak request/reply and WAN-friendly clustering matters more than LAN-multicast fan-out efficiency.

32. Back-of-Envelope Capacity Model

  • C1 — Reorder Buffer Packet Capacity. 512 MB ÷ 1400 B/packet = 536,870,912 / 1400 ≈ 383,479 packets nominal ceiling; with the ~40 B header (§8) included, 536,870,912 / 1440 ≈ 372,827 packets is the realistic per-receiver reorder-buffer capacity (§4, §15).
  • C2 — WAL Raw Retention Floor. 50,000,000 packets × 1440 B/record (payload + header) = 72,000,000,000 B = 72 GB raw WAL floor before the < 2.3x write-amplification budget is applied (§4, §18).
  • C3 — Sustainable Replay Window at Full Rate. 5 Gbps = 625,000,000 B/s ÷ 1400 B/packet ≈ 446,429 pkts/s; 50,000,000 ÷ 446,429 ≈ 112 s ≈ 1.9 minutes — far below the nominal 2-hour retention target (§4), so the 2h default is reachable only at throttled/average rates, not the sustained ceiling.
  • C4 — FD Budget vs. Stream Scaling. 4096 FD ÷ 3 FDs/stream (multicast recv + repair unicast + metrics) = 1365.3 ≈ 1365 max concurrent streams from the FD budget alone, vs. the 200-stream horizontal scaling target (§4) — 6.8x headroom.
  • C5 — Retransmit Amplification Ceiling. 1.5x × 5 Gbps sustained throughput = 7.5 Gbps combined data+repair bandwidth ceiling on a shared link (§4, §17).
  • C6 — WAL Disk Write Throughput Requirement. 2.3x × 625,000,000 B/s = 1,437,500,000 B/s ≈ 1.44 GB/s peak sustained disk write throughput required, driving the SSD-backed storage assumption (§4, §18).
  • C7 — Timer Wheel Memory Footprint. 5,000,000 timers × 17 B/slot (8 B expiration_tick + 8 B callback_ref + 1 B retry_count, §11) = 85,000,000 B ≈ 85 MB wheel memory footprint (§16).
  • C8 — Startup Step Budget. 5 s startup ceiling ÷ 20 bootstrap steps (§12.2) = 250 ms average budget per init step.
  • C9 — Suppression Window Sizing. 25 ms p99 repair-latency ceiling (§4) ÷ 2 = 12.5 ms suppression-window upper bound, keeping duplicate-NACK risk below the first repair's expected arrival (§17).
  • C10 — Membership Heartbeat Processing Floor. 50,000 receivers ÷ 10 s convergence target (§4, §20) = 5,000 receivers/s heartbeat-processing floor.
  • C11 — Availability Incident Budget. 99.95% availability = 0.05% × 8760 h/year = 4.38 h/year downtime budget; 4.38 h × 60 min/h ÷ 2 min RTO/incident (§4) ≈ 131 independent full-RTO incidents/year before breaching the budget.
  • C12 — Per-Core Throughput Budget. 5 Gbps ÷ 64 cores (§4) = 625,000,000 / 64 ≈ 9,765,625 B/s/core ÷ 1400 B/packet ≈ 6,975 pkts/s/core sustained data-rate floor, well inside the > 3,000,000 pkts/s/core decode target (§28 M1) — the gap absorbs retry/repair overhead.

34. Alternative Architectures (Roads Not Taken)

Alt A — Kernel-Bypass / DPDK Transport

+------------------------------------------------+
| Userspace Poll-Mode Driver                      |
|  (busy-poll NIC ring, no kernel socket stack)   |
+------------------------------------------------+
                    |
                    v
+------------------------------------------------+
| NIC (huge-page-pinned buffers, dedicated cores) |
+------------------------------------------------+

Wins where: sub-10 µs tail latency is mandatory, as in HFT market-data fan-out. Real system: Aeron deployments layered on kernel-bypass NIC drivers (Onload/Solarflare-class setups) in low-latency trading infrastructure. Rejected here because: the operational complexity (dedicated NIC driver, huge-page pinning, core isolation) far exceeds the target-operator profile (§1), and the achieved latency reduction is unnecessary against the §4 p99 budget of 10 ms — this is the deferred kernel-bypass item registered at anchor §14 in §35.

Alt B — FEC-Based Reliability (NORM-style)

+-------------+     data + parity blocks      +---------------+
| Sender      | -----------------------------> | Receiver      |
| (RS encode) |   (no NACK round trip needed)  | (RS decode)   |
+-------------+                                +---------------+

Wins where: WAN/satellite-class links with steady-state (not bursty) loss make a NACK round trip too slow to matter. Real system: NORM (RFC 5740) with its optional Reed-Solomon FEC extension. Rejected here because: FEC parity overhead is wasted bandwidth in the LAN/VLAN deployment model this project targets (§1), where loss is bursty rather than steady-state, and the NACK-based repair path's 25 ms budget (§4) already comfortably covers the target loss profile — this is the deferred FEC item registered at anchor §17 in §35.

Alt C — Full Virtual Synchrony via Token-Ring Membership

+--------+  token  +--------+  token  +--------+
| Node A | ------> | Node B | ------> | Node C | --+
+--------+         +--------+         +--------+   |
    ^ (send permission rotates with the token)      |
    +------------------------------------------------+

Wins where: small-to-medium cluster membership (tens to low hundreds of nodes) needs strict total order and virtual synchrony badly enough to accept token-rotation latency. Real system: Corosync's Totem protocol (also the classic ISIS/Horus virtual-synchrony lineage). Rejected here because: token rotation does not scale to the 50,000-receiver fan-out target (§4, §20) — rotation latency grows with membership size, and this project treats membership as advisory (MM6, §20), never a total-order mechanism.

36. Glossary

  • Replay Window — the persistent, recoverable packet range currently servable from WAL segments.
  • Delivery Cursor — per-receiver progress marker tracking contiguous and observed sequence high-water marks.
  • Repair Storm — a retransmission-amplification spike caused by synchronized or excessive receiver NACKs.
  • NACK Suppression — deduplication of redundant repair requests for the same packet window.
  • Session Epoch — a monotonic generation identifier scoping a stream's sequence space.
  • WAL (Write-Ahead Log) — the append-only durable store backing replay and crash recovery.
  • Gap Detection — identification of a missing sequence range at a receiver's delivery cursor.
  • Packet Amplification — the ratio of retransmitted bytes to primary-sent bytes.
  • Congestion Epoch — one pacing-adjustment interval in the congestion controller.
  • Timer Wheel — a hierarchical, bucketed timer structure for O(1) amortized schedule/expire.
  • Stream Retention — the durability window a stream's WAL segments are guaranteed to cover.
  • Ordered Delivery — monotonic, in-order application-visible sequencing on a strict-order stream.
  • Reorder Buffer — bounded, per-receiver temporary storage for out-of-order arrivals.
  • Multicast Group — the shared IP multicast address/scope a stream's packets are addressed to.
  • Receiver Quarantine — isolation of a pathological receiver's NACK traffic from shared suppression state.
  • Replay Snapshot — a persisted, version-tagged recovery checkpoint (SNAPSHOT packet type).
  • Packet Pacing — controlled, rate-limited transmission scheduling driven by the congestion budget.
  • Segment Rotation — the WAL event sealing one segment and opening the next.
  • Heartbeat Interval — the configured liveness-emission period for a receiver's membership state.
  • Sequence Gap — a missing range in an otherwise monotonic sequence stream.
  • Suppression Window — the interval during which only one repair request per packet window is honored.
  • Membership View — the Membership Agent's per-receiver liveness and health record.
  • Health Score — a blended signal of heartbeat recency and delivery-cursor lag driving degraded-state transitions.
  • Split Brain — two membership shards disagreeing on the current epoch after a partition.
  • Crash-Only Recovery — the design discipline of recovering exclusively via cold restart, never in-memory healing.
  • Backpressure — explicit, visible publisher throttling applied before runtime queue exhaustion.
  • Cardinality Guard — the enforcement point rejecting telemetry label combinations past a configured bound.
  • Token Bucket — the rate-shaping structure enforcing a congestion epoch's allowed send rate.
  • Fsync Batching — grouping multiple WAL appends into one durable-sync call to amortize latency.
  • Sparse Index — the mmap-backed, non-exhaustive replay index mapping sequence ranges to segment offsets.
  • Degraded State — the receiver lifecycle state entered under repair saturation or slow-consumer backlog.
  • Delivery Barrier — the mechanism preventing out-of-order application-visible delivery on strict-order streams.
  • Dedup Table — the structure enforcing duplicate-suppression at the delivery boundary (I4).
  • Congestion Budget — the per-epoch computed allowed-send-rate, repair-rate, and burst-budget bundle.
  • Burst Budget — the instantaneous-spend allowance within a congestion epoch's paced rate.
  • Amplification Ratio — the live metric tracking retransmitted-to-primary byte ratio against the I7 ceiling.
  • Suppression Collision — a detected double-entry attempt in the repair suppression cache.
  • Wheel Tier — one level of a hierarchical timing wheel's bucket hierarchy.
  • Wheel Bucket — one slot within a timer-wheel tier holding pending timer callbacks.
  • Quarantined Segment — a WAL segment isolated after failing checksum verification.
  • Late-Join Synchronization — a newly joining receiver's replay-driven catch-up to the live stream.
  • Virtual Synchrony — the total-order, token-ring membership model this project explicitly rejects at scale (§34 Alt C).
  • Total Order — a delivery guarantee stronger than this project provides by default (partial order is configurable, §8).
  • At-Least-Once Delivery — the delivery mode where duplicate suppression is explicitly disabled.
  • Fail-Closed — the design posture of stopping rather than continuing in an undefined state on invariant violation.
  • Suppression Cache Shard — the (stream_id, window)-keyed partition of the suppression cache preventing cross-shard duplicate repairs.
