⬜ Phase 0 — Repository Bootstrap & Deterministic Runtime Foundations §12

Objectives
  • Establish the Cargo workspace and 14-crate boundary layout (§10) before any protocol code exists.
  • Stand up the correctness kernel: structured error hierarchy, deterministic clock abstraction, and observability bootstrap that every later phase depends on.
  • Enforce reproducible-build guarantees (ADR-19) and lint/format policy from commit one.
  • Introduce zero protocol logic — this phase is infrastructure only, gated by Design Principle P1.
Deliverable

A runnable runtime shell binary that boots, validates configuration, attaches the full observability stack, exposes health probes, and shuts down cleanly — with zero multicast, wire, or storage logic. Reproducible Docker image built from a pinned Cargo.lock.

Acceptance
  • All CI workflows green on three consecutive commits; reproducible build hash identical across two independent build machines (ADR-19).
  • Startup time < 5 s (§4) measured from process exec to /readyz returning 200, averaged over 20 runs.
  • Zero clippy warnings at deny(warnings) level; cargo audit reports zero known vulnerabilities.
  • Fixture runtime_boot_sequence.json (§12.5) replays byte-identically across 10 consecutive runs.
Fixtures
  • conformance/config_valid.toml — baseline valid configuration; expected: clean boot, /readyz 200.
  • conformance/config_invalid_unknown_field.toml — malformed config with an unrecognized key; expected: startup failure with structured diagnostic naming the offending field, no partial boot.
  • conformance/runtime_boot_sequence.json — recorded lifecycle-event trace; expected: replay determinism regression case, byte-identical event sequence on every run.
Pitfalls
  1. Non-deterministic config loading order (HashMap iteration) — manifests as flaky boot-sequence fixtures; root cause: unordered map iteration feeding startup log emission; debug via runtime_boot_sequence.json diff; recovery: switch to an ordered map keyed by config-load order.
  2. Global mutable state smuggled into a lazy_static/OnceCell — manifests as test-order-dependent failures; root cause: shared process-global defeats P1 determinism; signal: tests pass alone, fail in a full suite run; recovery: thread state through explicit constructor parameters.
  3. Logger/tracing-subscriber initialization race between two startup hooks — manifests as dropped early log lines; root cause: subscriber not installed before the first tracing::info! call; signal: missing startup-phase log lines in runtime_boot_sequence.json; recovery: make subscriber install the first lifecycle hook, synchronously, before any other hook runs.
  4. Runtime shutdown deadlock between the metrics-flush hook and the WAL-flush hook waiting on each other's completion signal; root cause: circular hook dependency; recovery: enforce a strict linear shutdown-phase order (I10) with a hard per-phase timeout.

⬜ Phase 1 — Wire Protocol & Packet Codec Engine §13

Objectives
  • Define the canonical wire packet header (§8) and implement deterministic encode/decode.
  • Guarantee malformed-input isolation: no decode input can crash, hang, or leak the decode worker.
  • Establish protocol version negotiation ahead of any transport or delivery logic (P6).
Deliverable

A stable, fuzz-hardened packet codec library, rmcast-wire, linked identically by both sender and receiver runtimes — the single source of wire truth in the workspace.

Acceptance
  • Zero panics across 24 continuous hours of cargo-fuzz on packet_decode (ADR-13).
  • Malformed-packet rejection is deterministic: same malformed input always yields the same structured decode-error variant across 1,000 repeated decode calls.
  • Decode throughput > 3,000,000 packets/sec single-core, measured via throughput_bench (feeds §32 C12).
Fixtures
  • conformance/packet_valid_data.bin — well-formed DATA packet; expected: successful decode, exact field match.
  • conformance/packet_invalid_crc.bin — valid structure, corrupted CRC32C; expected: WireDecodeError rejection, malformed counter increments.
  • conformance/packet_truncated_header.bin — header shorter than declared header length; expected: rejection without buffer over-read.
  • conformance/packet_future_version.bin — version field ahead of the running decoder's max supported version; expected: rejection tagged as version-mismatch, not generic decode error.
Pitfalls
  1. Implicit padding bytes read as payload — manifests as off-by-N payload length; root cause: struct field alignment not matching the wire layout exactly; debug via packet_valid_data.bin byte-for-byte diff; recovery: explicit fixed-offset field reads, no derived struct layout.
  2. Endian mismatches between encode and decode paths — manifests as garbage stream_id values on cross-arch replay; root cause: relying on host-endian struct casts instead of explicit network-byte-order conversion; recovery: centralize all endian conversion in header.rs.
  3. Integer overflow on header_length + payload_length when computing total frame size — manifests as buffer over-allocation or panic on crafted input; root cause: unchecked addition; recovery: checked arithmetic with explicit rejection on overflow, exercised by the fuzz target.
  4. Version-negotiation asymmetry — decoder silently accepts a version it does not fully implement; root cause: version check treated as advisory instead of a hard capability gate; recovery: make version support an explicit allow-list, reject anything unlisted (P6).

⬜ Phase 2 — UDP Multicast Transport Runtime §14

Objectives
  • Implement the multicast socket runtime: IPv4/IPv6 group join, socket-buffer sizing, packet IO.
  • Establish the transport worker's concurrency and interface-binding model ahead of any protocol logic above it.
  • Isolate packet IO failures from the decode and sequencing layers above (§3 concurrency boundary).
Deliverable

A functional multicast transport runtime with verified send/receive across a 3-node loopback and LAN topology, integrated with the Phase 1 codec for end-to-end packet transit with no ordering or repair logic yet layered on top.

Acceptance
  • Stable multicast communication verified across 3 physical/virtual nodes for 1 continuous hour.
  • Packet-loss telemetry accurate to within 1% of an independent tcpdump-derived ground truth.
  • Zero file-descriptor leaks over a 10,000-cycle socket open/close stress fixture.
  • Socket FD usage stays within the 4096 budget (§4) at 200 concurrent streams (§4 horizontal target).
Fixtures
  • conformance/multicast_loopback_capture.bin — recorded loopback multicast exchange; expected: byte-identical replay through the transport layer.
  • conformance/socket_buffer_pressure.json — simulated socket-buffer-full scenario; expected: packet-drop accounting matches injected drop count exactly.
Pitfalls
  1. IGMP misconfiguration on the network fabric silently drops multicast joins — manifests as receivers never seeing DATA packets despite a healthy sender; root cause: fabric-side IGMP snooping not configured for the multicast group; debug via reachability-probe telemetry; recovery: operator runbook escalation, not a code fix.
  2. Socket buffer exhaustion under burst send — manifests as kernel-level silent drops invisible to application-level counters; root cause: default socket buffer size too small for the burst profile; recovery: explicit SO_RCVBUF/SO_SNDBUF sizing tied to §4's throughput budget.
  3. Multicast TTL misconfiguration causing packets to be dropped at the first router hop; root cause: default TTL of 1 assumed sufficient for a routed (non-VLAN-local) topology; recovery: make TTL an explicit, validated configuration field, not a silent default.
  4. Interface flap during an active session — manifests as a burst of spurious packet loss; root cause: no distinction between "route temporarily down" and "sustained partition"; recovery: reachability-probe-driven degraded-state transition instead of immediate session termination.

⬜ Phase 3 — Sequencing & Delivery Engine §15

Objectives
  • Implement deterministic ordering semantics on top of the Phase 2 transport (Invariant I1, I2).
  • Support bounded out-of-order delivery via a reorder buffer with a hard memory ceiling (P2, §4).
  • Introduce duplicate suppression at the delivery boundary (I4) ahead of repair logic (Phase 5).
Deliverable

A reliable, ordered packet delivery engine operating over live transport traffic, verified against the deterministic simulator with zero ordering violations across a seeded adversarial reorder corpus.

Acceptance
  • Zero ordering violations (I2) across 10,000 simulator runs with randomized packet reordering under chaos injection (§26).
  • Duplicate suppression verified: 100% of injected duplicate sequences rejected at delivery in the duplicate_packet_fixture.bin fixture.
  • Reorder buffer never exceeds the 512 MB ceiling (§4) under an 8% burst-loss injection profile.
Fixtures
  • conformance/reordered_packet_stream.bin — packets delivered out of transport order; expected: in-order delivery to the application cursor.
  • conformance/duplicate_packet_fixture.bin — repeated sequence numbers injected; expected: single delivery per sequence, duplicate counter increments.
Pitfalls
  1. Sequence rollover math error at the u64 boundary — manifests as a false sequence-regression fault near the wraparound point; root cause: signed/unsigned comparison bug; debug via a rollover-boundary property test; recovery: forbid wraparound within a session lifetime (I1) and assert it explicitly rather than relying on arithmetic to "just work."
  2. Unbounded reorder-buffer growth under sustained high-gap-count loss — manifests as OOM risk; root cause: no eviction policy once the buffer nears the 512 MB ceiling; recovery: bounded eviction with an explicit degraded-state transition (§8 DEGRADED) rather than silent growth.
  3. Delivery starvation when a low-sequence gap never resolves — manifests as all higher sequences stuck behind it; root cause: strict-order delivery barrier has no timeout escape; recovery: a configurable gap-timeout that forces a partial-order fallback or triggers repair escalation.
  4. Cursor corruption from a race between the checkpoint-persistence writer and the live-delivery advancer — manifests as highest_contiguous > highest_observed; recovery: single-writer ownership of the cursor (P7), checkpoint reads a snapshot, never a live-mutated reference.

⬜ Phase 4 — Timer Wheel & Retransmission Scheduler §16

Objectives
  • Build a scalable timer facility supporting millions of concurrent retransmission/heartbeat deadlines.
  • Replace any heap-based timer approach with a hierarchical timing wheel (ADR-24) before repair logic (Phase 5) depends on it.
  • Bound timer-tick jitter within the §4 drift budget.
Deliverable

A production timer subsystem supporting retransmission and heartbeat coordination at the target cardinality, verified deterministic under the replay harness.

Acceptance
  • Sustains 5,000,000 concurrently active timers (§32 C7 sizing) without wheel-occupancy overflow.
  • p99 scheduling jitter < 2 ms under full load, measured via timer_rollover.json replay.
  • Zero tick regressions (I6) across a 10,000-cycle clock-jump stress fixture.
Fixtures
  • conformance/timer_rollover.json — wheel-tier rollover boundary trace; expected: deterministic expiration order preserved across rollover.
  • conformance/timer_cancel_race.json — concurrent cancel-and-expire race; expected: no dangling callback dispatch, cancellation wins if it precedes expiration.
Pitfalls
  1. Timer drift accumulating across wheel-tier promotions — manifests as jitter exceeding the 1 ms budget (§4) only after sustained runtime, not immediately; root cause: tick-interval rounding error compounding per promotion; recovery: carry sub-tick remainder explicitly rather than truncating at each tier boundary.
  2. Callback starvation when one wheel bucket accumulates disproportionate load (hot-key sequence ranges under correlated loss) — manifests as delayed retransmission for an unlucky subset of packets; root cause: naive modulo-based bucket assignment; recovery: bucket-load-aware assignment or secondary hashing within a bucket.
  3. Overflow loops when a retry re-schedules itself into an already-overflowing tier — manifests as a runaway retry storm; root cause: no backoff cap on rescheduled retry count; recovery: cap retry_count (§11 TimerSlot) and escalate to repair-storm detection (RepairStormDetected, §11) past the cap.

⬜ Phase 5 — Repair Coordination & NACK Suppression §17

Objectives
  • Implement scalable NACK-based packet repair on top of the Phase 3 gap-tracking data (GapSet, §11).
  • Prevent repair storms from synchronized-receiver retry behavior (Invariant I9, Design Principle P9).
  • Keep retransmission amplification within the 1.5x ceiling (§4, Invariant I7) under 8% burst loss.
Deliverable

A repair subsystem that holds retransmission amplification under the §4 ceiling while surviving burst packet loss and synchronized-receiver NACK storms, verified under chaos injection.

Acceptance
  • Retransmission amplification stays < 1.5x (I7) under the repair_gap_burst.bin fixture's 8% burst-loss profile.
  • Repair success rate > 99.5% measured over a 1-hour chaos run with correlated multi-receiver loss.
  • Suppression collisions (I9) resolve deterministically: exactly one active repair per window per suppression interval, verified across 10,000 simulator runs.
Fixtures
  • conformance/repair_gap_burst.bin — correlated multi-gap burst loss; expected: amplification ratio stays under 1.5x, all gaps eventually repaired.
  • conformance/nack_suppression_overlap.bin — overlapping NACKs for the same window from multiple receivers; expected: single repair scheduled, suppression collision counter increments for the redundant NACKs, no duplicate REPAIR sent.
Pitfalls
  1. Repair storms from synchronized receiver retry timers — manifests as a retransmission spike that itself causes further loss; root cause: receivers sharing a common retry backoff schedule with no jitter; debug via the repair-amplification-ratio metric spiking in lockstep with a NACK-rate spike; recovery: jittered receiver backoff plus sender-side suppression (I9).
  2. Duplicate retransmissions for the same gap from two independent suppression-cache shards; root cause: suppression cache sharded by receiver rather than by (stream, window), so two receivers' NACKs for the same gap land in different shards and both get serviced; recovery: shard the suppression cache by (stream_id, window), not by receiver.
  3. Stale repairs delivered after the requesting receiver's reorder-buffer window has already evicted that range (Phase 3 dependency) — manifests as a wasted repair send; root cause: no cross-check between repair-request age and the requester's known eviction policy; recovery: tag NACKs with the requester's current window bound, drop repair requests past it.

⬜ Phase 6 — WAL Persistence & Replay Engine §18

Objectives
  • Implement durable, append-only WAL storage (ADR-04) satisfying Invariant I3 (replay durability before eligibility).
  • Support deterministic crash recovery and late-join synchronization from the same on-disk structure (P5, P4).
  • Enforce the write-amplification budget (§4: < 2.3x) and the replay-backlog ceiling (§4: 50 M packets).
Deliverable

A persistent replay engine supporting deterministic crash recovery within the RTO budget and late-join synchronization via the same replay-iterator code path used for recovery.

Acceptance
  • Crash recovery completes in < 2 minutes (§4 RTO) on a 50 M-packet backlog, measured from process restart to /readyz 200 with the replay index fully rebuilt.
  • Replay output is byte-identical across repeated runs against wal_replay_snapshot.json (P1 determinism).
  • WAL write amplification stays < 2.3x (§4) measured as bytes-written-to-disk / raw-payload-bytes over a 1-hour sustained-load run.
Fixtures
  • conformance/wal_corrupted_segment.bin — a segment with a deliberately corrupted checksum; expected: quarantine, adjacent segments replay normally.
  • conformance/wal_partial_write.bin — a torn write (process killed mid-fsync-batch); expected: recovery truncates to the last verified record, no corrupted tail replayed.
  • conformance/wal_replay_snapshot.json — a recorded full-replay output; expected: byte-identical regression match on every run.
Pitfalls
  1. Torn writes from a crash mid-fsync-batch — manifests as a segment tail that looks structurally valid but is semantically incomplete; root cause: fsync batch boundary not aligned with a checksum-verifiable record boundary; recovery: checksum each fsync-batch boundary, not just each segment.
  2. mmap invalidation when a segment is rotated out from under an in-progress mmap read — manifests as a read-path segfault or garbage read; root cause: unmap-before-all-readers-done race; recovery: reference-counted segment handles, unmap only after the last reader releases.
  3. Retention-eviction races with an in-progress replay reading from the segment being evicted; root cause: eviction policy has no visibility into active replay readers; recovery: eviction defers to the oldest active replay cursor, never evicts a segment a live replay still needs.

⬜ Phase 7 — Congestion Control & Flow Regulation §19

Objectives
  • Implement congestion-aware sender pacing (ADR-23: BBR-inspired model-based pacing) stabilizing multicast throughput without a per-receiver ACK stream.
  • Keep retransmission traffic within the amplification ceiling under load (I7, coordinated with Phase 5).
  • Avoid congestion collapse under sustained loss (P9) while meeting the publish-latency budgets (§4).
Deliverable

A congestion-aware sender that sustains stable throughput under injected loss up to the §4 burst ceiling without triggering congestion collapse, verified against the simulation harness.

Acceptance
  • Stable throughput (no collapse, defined as sustained rate not dropping more than 20% below the loss-adjusted theoretical ceiling) maintained under a 5% packet-loss injection for 30 minutes.
  • No congestion collapse observed across the full 0–8% loss sweep (§4 burst ceiling) in the congestion_burst_trace.json fixture.
  • p99 publish latency stays < 10 ms (§4) even while THROTTLED, verified via throttle_transition.json.
Fixtures
  • conformance/congestion_burst_trace.json — a recorded loss-injection sweep from 0–8%; expected: pacing-interval trend matches the model prediction, no collapse.
  • conformance/throttle_transition.json — a sender transitioning ACTIVE→THROTTLED and back; expected: publish latency budget (§4) held throughout the transition.
Pitfalls
  1. Over-aggressive pacing reduction on a transient loss spike that is not sustained congestion — manifests as unnecessary throughput loss; root cause: reacting to instantaneous loss samples rather than a windowed trend; recovery: require a sustained-trend threshold (multiple congestion epochs) before reducing allowed_send_rate, per BBR's model-based (not instantaneous) philosophy.
  2. Feedback oscillation between the pacing scheduler and the aggregated NACK-rate signal — manifests as a throughput sawtooth despite BBR-style pacing being chosen specifically to avoid this (ADR-23's rationale); root cause: congestion-epoch interval too short relative to the RTT used for feedback aggregation; recovery: epoch interval floor tied to measured RTT, not a fixed constant.

⬜ Phase 8 — Membership & Session Coordination §20

Objectives
  • Manage receiver lifecycle state (JOIN/LEAVE/heartbeat) and maintain fan-out membership visibility at the 50,000-receiver target (§4).
  • Enforce membership-epoch monotonicity (Invariant I5) across churn without adopting a token-passing membership protocol (rejected in ADR analysis, §9's Corosync-study note).
  • Support split-brain detection without a full consensus system (explicit non-goal, §1).
Deliverable

A membership-aware runtime that tracks receiver lifecycle at the 50,000-receiver target with bounded convergence time and observable health scoring, without adopting a consensus protocol.

Acceptance
  • Supports 50,000 concurrent receivers per stream (§4) with the churn stress fixture at a sustained 500 JOIN/LEAVE events/sec.
  • Membership convergence (all shards agree on current epoch) completes in < 10 seconds after a churn burst, measured via membership_churn_trace.json.
  • Stale-receiver eviction fires within 2x the configured heartbeat timeout, verified against receiver_timeout_fixture.json.
Fixtures
  • conformance/membership_churn_trace.json — a recorded high-churn JOIN/LEAVE sequence; expected: convergence within the 10 s budget, no epoch regression (I5).
  • conformance/receiver_timeout_fixture.json — a receiver that stops heartbeating; expected: eviction within 2x the heartbeat timeout, health-score degradation visible before eviction.
Pitfalls
  1. Stale heartbeats processed out of order (a delayed heartbeat arriving after a later one) reset the staleness timer incorrectly — manifests as an unresponsive receiver appearing falsely healthy; root cause: heartbeat timestamp not compared against the last-seen sequence for that receiver; recovery: only accept a heartbeat if its sequence is newer than the last recorded one.
  2. Split-brain membership after a partition heals with two shards holding different epoch values for the same stream — manifests as inconsistent operator-visible membership counts; root cause: no explicit reconciliation trigger on partition-heal detection; recovery: epoch-mismatch detection (20.2 step 11) forces an explicit reconciliation pass, never a silent higher-epoch-wins merge without an audit log entry.

⬜ Phase 9 — Observability, Chaos & Operational Tooling §21

Objectives
  • Make every prior phase's runtime state observable: tracing, metrics, structured logs, operator CLI.
  • Enable production diagnostics and reproducible incident replay (P1 applied to the operational surface, not just the protocol core).
  • Validate the entire system under chaos injection (loss, duplication, corruption, latency, restarts) before declaring production readiness (§24).
Deliverable

A complete production operational-tooling suite: every invariant, metric, and lifecycle transition defined in §7 and §12–§20 is observable, and any incident can be captured and deterministically replayed offline.

Acceptance
  • All 12 System Invariants (§7) have a corresponding metric emitted on violation, verified by a test that deliberately triggers each and asserts the metric fires.
  • Incident replay is reproducible: the incident_trace_bundle.jsonl fixture replays to an identical failure-snapshot state across 10 runs (P1).
  • Chaos suite (loss, duplication, corruption, latency, restart) runs for 4 continuous hours with no unhandled panic and no invariant violation outside the injected fault's expected blast radius.
Fixtures
  • conformance/incident_trace_bundle.jsonl — a captured multi-span incident trace; expected: byte-identical replay through the incident-replay harness.
  • conformance/dashboard_snapshot.json — a recorded metrics snapshot at a known system state; expected: dashboard-query output matches the snapshot within numerical tolerance.
Pitfalls
  1. Excessive telemetry cardinality from a well-intentioned but unbounded label (e.g. raw receiver ID as a metric label at 50,000 receivers) — manifests as an observability-backend outage distinct from and caused by the very system meant to prevent outages; root cause: I12's cardinality guard added late instead of enforced from Phase 0; recovery: retrofit the cardinality allowlist and bucket high-cardinality dimensions (e.g. receiver-ID) into a health-state histogram instead of a per-ID label.
  2. Tracing overhead itself distorting the p99 publish-latency measurement it is meant to diagnose — manifests as a Heisenberg effect where enabling full tracing changes the very tail-latency behavior under investigation; root cause: unsampled tracing on the hot path; recovery: sampling policy (21.2 step 13) with a documented sampling-induced-error bound.
