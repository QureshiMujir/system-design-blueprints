Decisions (§9) · 24 ADRs

ADR-01

Primary language

Chosen

Rust

Rejected

Go, C++, Java

When the rejected choice is right

Go wins for a low-packet-rate control-plane-only service where GC pauses cannot violate a latency SLO

Why: ownership-checked buffer lifetime (P7) under packet-rate pressure, no GC pause on hot path

ADR-02

Build system

Chosen

Cargo workspace

Rejected

Bazel

When the rejected choice is right

Bazel wins once the repo spans multiple languages (e.g. embedding a C repair-FEC library) or needs remote build caching at scale

Why: 14-crate workspace fits Cargo's dependency graph without custom rules; Bazel's benefit (hermetic multi-language builds) is unused here

ADR-03

Dependency policy

Chosen

vendored + cargo-audit gated

Rejected

unpinned floating semver ranges

When the rejected choice is right

floating ranges win for a rapidly-iterating internal prototype where reproducibility is not yet a requirement

Why: reproducible builds (P1) require a locked, audited dependency set at every release tag

ADR-04

Storage engine

Chosen

append-only WAL segments

Rejected

SQLite

When the rejected choice is right

SQLite wins when replay volume is low and ad hoc SQL queries over persisted packets are more valuable than raw write throughput

Why: throughput and write-amplification (§4: <2.3x) — SQLite's B-tree page writes add overhead the sequential WAL avoids

ADR-05

Serialization

Chosen

postcard

Rejected

Protocol Buffers

When the rejected choice is right

Protobuf wins when the payload schema is shared across many non-Rust language runtimes and schema evolution tooling matters more than 20–40 bytes/packet

Why: lower per-packet overhead at the 1400 B payload ceiling; no schema-registry dependency for the wire hot path

ADR-06

Packet IO

Chosen

UDP sockets (multicast)

Rejected

raw sockets

When the rejected choice is right

raw sockets win when building custom IP-layer framing (e.g. a kernel-bypass path), which this project explicitly defers

Why: portability across kernels and containers without CAP_NET_RAW; raw sockets buy header control this protocol does not need

ADR-07

Async runtime

Chosen

Tokio

Rejected

async-std

When the rejected choice is right

async-std wins for a minimal dependency footprint where Tokio's scheduler features (work-stealing, cooperative yield) are unused

Why: ecosystem maturity — tracing integration, tokio-console, and the multicast-aware socket crates all target Tokio first

ADR-08

Concurrency model

Chosen

message-passing actors (mpsc/broadcast channels) per subsystem

Rejected

When the rejected choice is right

shared-mutex wins for a single hot counter accessed by many readers where channel overhead exceeds contention cost

Why: matches the explicit-ownership principle (P7); channel backpressure doubles as the P3 throttling signal

ADR-23

Congestion control

Chosen

BBR-inspired model-based pacing

Rejected

Reno-style loss-reactive AIMD

When the rejected choice is right

Reno-style AIMD wins in a network with well-behaved, low-burst loss where BBR's bandwidth-probing overhead is unnecessary complexity

Why: model-based pacing avoids the sawtooth throughput collapse Reno exhibits under the bursty, non-per-flow loss this protocol sees (§19)

ADR-24

Retransmission timer structure

Chosen

hierarchical timing wheel (Varghese & Lauck 1987)

Rejected

binary heap of deadlines

When the rejected choice is right

a binary heap wins at low timer cardinality (thousands, not millions) where its simplicity outweighs the wheel's bucket-management complexity

Why: O(1) amortized insert/expire at millions of outstanding timers (§4, §16); heap insert is O(log n) and dominates CPU at that cardinality

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Kernel-Bypass / DPDK Transport

+------------------------------------------------+
| Userspace Poll-Mode Driver                      |
|  (busy-poll NIC ring, no kernel socket stack)   |
+------------------------------------------------+
                    |
                    v
+------------------------------------------------+
| NIC (huge-page-pinned buffers, dedicated cores) |
+------------------------------------------------+

Wins where: sub-10 µs tail latency is mandatory, as in HFT market-data fan-out. Real system: Aeron deployments layered on kernel-bypass NIC drivers (Onload/Solarflare-class setups) in low-latency trading infrastructure. Rejected here because: the operational complexity (dedicated NIC driver, huge-page pinning, core isolation) far exceeds the target-operator profile (§1), and the achieved latency reduction is unnecessary against the §4 p99 budget of 10 ms — this is the deferred kernel-bypass item registered at anchor §14 in §35.

Alt B — FEC-Based Reliability (NORM-style)

+-------------+     data + parity blocks      +---------------+
| Sender      | -----------------------------> | Receiver      |
| (RS encode) |   (no NACK round trip needed)  | (RS decode)   |
+-------------+                                +---------------+

Wins where: WAN/satellite-class links with steady-state (not bursty) loss make a NACK round trip too slow to matter. Real system: NORM (RFC 5740) with its optional Reed-Solomon FEC extension. Rejected here because: FEC parity overhead is wasted bandwidth in the LAN/VLAN deployment model this project targets (§1), where loss is bursty rather than steady-state, and the NACK-based repair path's 25 ms budget (§4) already comfortably covers the target loss profile — this is the deferred FEC item registered at anchor §17 in §35.

Alt C — Full Virtual Synchrony via Token-Ring Membership

+--------+  token  +--------+  token  +--------+
| Node A | ------> | Node B | ------> | Node C | --+
+--------+         +--------+         +--------+   |
    ^ (send permission rotates with the token)      |
    +------------------------------------------------+

Wins where: small-to-medium cluster membership (tens to low hundreds of nodes) needs strict total order and virtual synchrony badly enough to accept token-rotation latency. Real system: Corosync's Totem protocol (also the classic ISIS/Horus virtual-synchrony lineage). Rejected here because: token rotation does not scale to the 50,000-receiver fan-out target (§4, §20) — rotation latency grows with membership size, and this project treats membership as advisory (MM6, §20), never a total-order mechanism.
