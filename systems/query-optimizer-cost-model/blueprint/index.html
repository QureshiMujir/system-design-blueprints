206 — Query Optimizer Cost Model from Scratch

Project Number: 206

Project Name: Query Optimizer Cost Model from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. A query optimizer cost model subsystem is the component of a relational query engine that, given a normalized logical plan and a statistics snapshot, enumerates a bounded space of semantically-equivalent physical plans, assigns each a scalar+vector cost estimate derived from CPU, IO, memory, network, and spill sub-models, and selects a minimum-cost plan under a search budget — deterministically, replayably, and with every decision inspectable after the fact. This blueprint builds that subsystem, not a database. It is the Selinger/Volcano/Cascades lineage (§5 Papers) rebuilt with modern statistics, vectorization-aware costing, distributed exchange penalties, and closed-loop runtime calibration.

Phase 0 deliverable — crates and binaries (workspace members, Cargo workspace, ADR-02):

  1. sql-ir — relational IR: AST, canonical operators, expression interning, deterministic hashing.
  2. memo — Cascades-style memo: groups, equivalence classes, verifier, search-budget accounting.
  3. statistics — histograms, NDV estimators, sketches, versioned snapshots, persistence.
  4. cardinality — row-count estimation: selectivity, join estimation, correlation, feedback.
  5. cost-model — CPU/IO/network/memory/spill cost equations, calibration profile application.
  6. optimizer-core — session orchestration, phase sequencing, statistics snapshot pinning.
  7. plan-enumerator — join order search: DP, bushy enumeration, pruning, branch-and-bound.
  8. calibration — runtime-feedback fitting, drift detection, q-error tracking, rollback.
  9. explain — structured explain output, pruning-rationale traces, plan diff tooling.
  10. benchmark-harness — TPC-H/TPC-DS/synthetic-skew drivers, Criterion integration.
  11. replay-engine — deterministic replay archive, trace IDs, regression quarantine.
  12. telemetry — OpenTelemetry spans, Prometheus metrics, structured-log field registry.
  13. integration-fixtures — shared conformance fixtures, TPC-H/TPC-DS schema fixtures.
  14. optimizer-cli binary — offline plan inspection, replay, calibration CLI.
  15. optimizer-service binary — network-facing optimizer service (embeddable or standalone).

System boundaries.

  • Provides: relational IR construction from an already-parsed AST, logical rewrite framework, memo-based physical search, cardinality/cost estimation, plan explainability, deterministic replay, runtime calibration ingestion, distributed exchange cost modeling.
  • Delegates: SQL text tokenizing/parsing to an external parser producing the input AST (§8.1 assumes an AST is already available); physical operator execution to an external execution engine; transaction/consistency semantics to an external storage engine; authentication/authorization to the host service.
  • Does NOT provide: a storage engine, a transactional MVCC layer, a full SQL parser, a replication layer, object-storage integration, a BI/UI layer, ML-guided plan search (Deferred Features Register, §35), or distributed-transaction coordination.

Non-goals: OLTP transaction throughput records, general-purpose compiler IR, a competing SQL dialect, GPU execution, learned cardinality estimators (§35), multi-tenant admission control (§35).

Deployment model. Four supported shapes: (1) embedded optimizer library linked into a host execution engine process; (2) standalone optimizer-service behind gRPC, stateless per request except for pinned statistics snapshots; (3) distributed-SQL-engine optimizer plugin invoked per query coordinator; (4) offline calibration/benchmarking environment driven by benchmark-harness and replay-engine against archived traces. All four share the same optimizer-core session API (§11.5 OptimizerSession).

Target operators: database-engine teams embedding a cost-based optimizer into an existing execution engine; SRE/perf teams debugging plan regressions via explain/replay-engine; research teams calibrating cost coefficients against production telemetry via calibration.

What later phases unlock. Phase 0–2 (§12–§14) unlock a deterministic, replayable memo substrate with no costing yet. Phase 3–4 (§15–§16) unlock statistically-grounded cardinality. Phase 5–7 (§17–§19) unlock a complete cost-based physical optimizer. Phase 8 (§20) unlocks operator-facing explainability. Phase 9 (§21) unlocks distributed and adaptive-calibration deployments — the prerequisite for any of the Deferred Features Register (§35) items.

Recommended language: Rust. Rationale, in priority order: (1) ownership semantics make memo group ownership (§7 I1) statically checkable rather than convention-enforced; (2) no GC pause inside a p99 ≤ 1500 ms optimization budget (§4); (3) #[repr]-controlled layouts make CostVector (§11.2) and HistogramBucket (§11.3) cache-predictable (§28); (4) mature async runtime (Tokio, ADR-10) for optimizer-service request fan-out; (5) cargo-fuzz (ADR-12) gives parser/memo/serialization fuzzing without a second toolchain; (6) reproducible release binaries (ADR-19, §27). Rejected languages: C++ — memory-safety footguns in a memo structure with thousands of cross-referencing pointers outweigh its marginally lower FFI friction; Go — GC pauses are incompatible with p99 optimization latency and its generics story was immature relative to the Cascades-style generic rule engine this needs; Java — JVM warm-up and GC pauses conflict with the embedded-library deployment shape and cold-start latency budget (§4).

Secondary tooling: Python for the calibration fitting pipeline's offline analysis and plotting (not on the hot path); shell/SQL for benchmark-harness TPC-H/TPC-DS driver scripts.

Prerequisites: relational algebra, database internals (storage/execution pipelines), cost-based optimization theory, cardinality estimation, dynamic programming and graph algorithms, probabilistic data structures (HyperLogLog, t-digest), memory hierarchy and CPU cache behavior, concurrency primitives, Linux performance tooling (perf, flamegraph), distributed-systems networking basics.

Estimated timeline: Phase 0 — 3 weeks. Full system through Phase 9 — 10–14 months to production maturity; 18–24 months to include any Deferred Features Register (§35) item.

2. Why Build This

Systems knowledge developed. Building a cost-based optimizer from scratch is the fastest path to internalizing memoized search-space exploration, dynamic-programming plan search under a cost metric, statistical approximation under adversarial skew, distributed cost accounting, and closed-loop calibration — skills that transfer directly to compiler optimizer design, distributed scheduler design, and any system that searches a combinatorial space under an estimated objective.

Historical importance. Selinger et al. (1979, §5 Papers) introduced cost-based join-order selection in System R and changed how every subsequent relational engine is built. Graefe's Volcano (1993) and Cascades (1995) frameworks generalized the search into a rule-driven, memoized top-down/bottom-up hybrid that PostgreSQL, SQL Server, Greenplum, CockroachDB, and Apache Calcite all descend from architecturally. The optimizer — not the storage engine — is what determines whether a given hardware footprint can serve a workload at all: a missed join-order choice can turn a 200 ms query into a 20-minute one at the same data size. This is why cardinality estimation quality (Leis et al. 2015, §5 Papers) is treated as a first-class system property here, not an afterthought.

Engineering muscle developed. Algorithmic reasoning (DP over join subsets, branch-and-bound pruning); probabilistic modeling (histogram/NDV/sketch selectivity under correlation); systems benchmarking (TPC-H/TPC-DS discipline); memory-sensitive engineering (memo growth bounds, §4); replay- driven debugging (deterministic trace replay, §20); closed-loop calibration (runtime feedback fitting, §21).

Production engineering concepts exercised. Statistics drift detection, deterministic regression replay, plan explainability, telemetry pipelines, versioned metadata with compatibility guarantees, benchmarking discipline, and optimizer failure containment (bounded memo growth, quarantine on replay divergence) — the same concerns that dominate on-call load for every production query optimizer team.

Related systems. Distributed SQL engines (CockroachDB, TiDB, YugabyteDB), vectorized execution engines (DuckDB, Velox), compiler optimizers (LLVM's cost-model-driven instruction selection is a structural cousin), graph search engines, OLAP columnar databases, adaptive schedulers, and statistics engines all share this blueprint's core shape: enumerate, cost, prune, select, observe, recalibrate.

Calibration value. Completing this blueprint measurably improves capability in: systems architecture under combinatorial search, distributed cost accounting, observability design for opaque search decisions, performance engineering under a latency budget, benchmarking rigor, and deterministic-replay debugging discipline — capabilities that generalize far beyond databases.

What Mastery Looks Like

  • Can explain why memoization (Cascades, §5 Papers) turns exponential plan enumeration into polynomial-bounded search, and can name the exact pruning rule that fails to do so — gained in Phase 2 (§14).
  • Can derive a selectivity estimate from a histogram bucket, quantify its q-error, and explain when the independence assumption (§14.6 pitfall) silently produces a 100x cardinality miss — gained in Phase 4 (§16).
  • Can write a cost equation that accounts for cache-line-aware CPU cost, IO latency, and spill amplification without double-counting network cost — gained in Phase 5 (§17).
  • Can bound a join-order DP search with branch-and-bound and explain the exact table-count threshold where left-deep-only enumeration becomes wrong for a given workload — gained in Phase 6 (§18).
  • Can select a physical join operator (hash/merge/nested-loop) from cost vectors alone and justify the spill-risk margin used to avoid it — gained in Phase 7 (§19).
  • Can produce a byte-identical replay of an optimization decision from an archived trace and diagnose a plan regression purely from explain output — gained in Phase 8 (§20).
  • Can model a distributed exchange operator's network cost and calibrate cost coefficients against runtime feedback without overfitting a single workload — gained in Phase 9 (§21).
  • Can defend every ADR's rejected-alternative column (§9) with a concrete regime where the rejected choice would in fact be correct.

3.2 Box-by-Box

Host/Client caller — external trust boundary A: any AST or RPC payload crossing this edge is untrusted input, validated by sql-ir before entering the memo.

optimizer-core :: OptimizerSession — request-scoped orchestrator (§11.5); owns the immutable statistics-snapshot pin (I3), the phase sequence (§8.5), and the replay-trace id (I2); single point of failure containment per request — a session abort never corrupts another session's memo.

sql-ir — deterministic AST-to-operator-graph compiler; establishes replay-safe canonicalization (alias assignment, predicate ordering, expression hashing) before anything else runs.

telemetry — cross-cutting async export boundary; every other crate emits spans/metrics through it, never directly to a sink, so it is the one place backpressure on export is handled.

memo — the single-writer, per-session equivalence structure (concurrency boundary: exactly one session mutates a given memo instance; freeze-on-select makes it immutable for physical generation).

statistics — persistence boundary: histograms/sketches/snapshots are read through an immutable pinned view; writes happen out-of-band from calibration, never inside a live optimization.

cardinality — pure function of memo shape + statistics snapshot; no persistent state of its own.

cost-model — pure function of cardinality estimates + calibration profile; the only crate allowed to read calibration coefficients during optimization.

plan-enumerator — the search loop; consumes a time/expression budget (I-invariant bound, §7) and must terminate inside it even on adversarial join graphs.

Physical plan generator (inside optimizer-core) — protocol boundary: emits a stable operator tree consumed by an external execution engine; this is the last point at which the optimizer can still be wrong for free.

explain — read-only projection over the frozen memo and cost trace; never mutates optimizer state.

replay-engine — persistence boundary: append-only trace archive; the only path by which a past decision becomes reproducible.

calibration — closed feedback loop: reads replay-engine archives and runtime telemetry, writes back into statistics/cost-model coefficient tables out-of-band, never inside a live request.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: identical inputs (AST + statistics snapshot + calibration profile) must produce byte-identical plans and hashes. · Tradeoff: forbids any wall-clock-seeded or thread-order-dependent tie-break in plan-enumerator. · Operational: enables replay-engine diffing. · Violated: non-reproducible regressions and unusable benchmark deltas (FM-3).
  • P2 — Backpressure Everywhere. Rule: every queue (telemetry export, statistics ingestion, replay write) is bounded with an explicit drop/block policy. · Tradeoff: bounded queues can shed load under burst instead of buffering it. · Operational: exposed as queue-depth gauges (§24). · Violated: unbounded memory growth under load spikes, OOM kill (FM-1).
  • P3 — Observability First. Rule: every pruning decision in plan-enumerator and every cost component in cost-model is inspectable via explain without re-running optimization. · Tradeoff: costs a persisted rationale record per pruned alternative. · Operational: backs the explain crate's structured trace. · Violated: operators cannot diagnose a plan regression (§33 Q3).
  • P4 — Crash-Only Internal Semantics. Rule: every subsystem restarts from persisted replay artifacts, never from in-memory-only recovery logic. · Tradeoff: forgoes a graceful-shutdown code path in favor of one restart path that is exercised constantly. · Operational: bounds restart RTO to §4's 15 s. · Violated: divergent recovery-path bugs that only manifest on ungraceful crash (FM-1).
  • P5 — Stable Serialization. Rule: every persisted statistics/memo/replay record is schema-versioned (ADR-03, ADR-16). · Tradeoff: version-tag overhead on every persisted record. · Operational: enables §25 compatibility guarantees. · Violated: silent misinterpretation of old data after an upgrade (FM-6).
  • P6 — Explicit Resource Accounting. Rule: every optimization phase tracks its own allocation count, CPU time, and memo-growth delta. · Tradeoff: per-phase counters add bookkeeping to the hot path. · Operational: feeds §4's memo soft-warning threshold and §28's M-series targets. · Violated: budget breaches discovered only via OOM instead of graceful abort (I8).
  • P7 — Cost Model Explainability. Rule: every CostVector (§11.2) exposes its five components (CPU, IO, memory, network, spill) separately, never pre-summed only. · Tradeoff: larger cost records than a single scalar. · Operational: backs §33 Q7 debugging. · Violated: operators cannot tell which cost component drove a bad plan choice.
  • P8 — Replayability First. Rule: optimization traces are append-only and byte-replayable from replay-engine archives. · Tradeoff: archive storage grows monotonically until rollover (§4 storage-amplification ceiling). · Operational: backs §20 deterministic replay. · Violated: a production regression cannot be reproduced offline (FM-3).
  • P9 — Compatibility Preservation. Rule: serialized plans and memo formats keep backward-read compatibility within a major version (§25). · Tradeoff: constrains internal refactors of MemoGroup/CostVector layouts. · Operational: enforced by ADR-16 versioning. · Violated: a rolling upgrade breaks in-flight replay archives (FM-6).
  • P10 — Bounded Search Explosion. Rule: memo growth is constrained by pruning, heuristics, and a hard search budget (I8, I9), never by "it usually finishes." · Tradeoff: pruning can discard a globally-optimal plan in adversarial join graphs. · Operational: backs §4's memo hard cap. · Violated: factorial-time enumeration on wide joins (§18.6 pitfall, FM-2).
  • P11 — Single-Writer Memo Ownership. Rule: exactly one OptimizerSession mutates a given memo instance; freeze-on-select makes it immutable thereafter (I1). · Tradeoff: forbids cross-session memo sharing even for identical queries. · Operational: removes an entire class of concurrency bugs from the hot path. · Violated: torn equivalence-class reads under concurrent mutation (I1 violation, FM-1).
  • P12 — Statistics Snapshot Immutability. Rule: a session observes one immutable statistics snapshot for its entire lifetime (I3). · Tradeoff: a session can optimize against slightly stale statistics rather than the latest write. · Operational: makes cardinality estimation reproducible within a session. · Violated: two operators in the same plan see different statistics versions, producing an internally inconsistent cost (FM-2).

I6 A spill cost estimate includes disk amplification, serialization overhead, and repartition penalty as separate terms. Omitting any term underestimates spill risk (§19.6 pitfall). cost-model::spill Structural check that all three terms are non-default. spill_cost_incomplete_total Reject cost estimate; fall back to conservative spill ceiling.
I7 A join graph has no disconnected components unless an explicit cross join node represents the gap. Disconnected joins silently degrade into cartesian products. plan-enumerator::dp_search Graph-connectivity check before enumeration. disconnected_join_detected_total Insert explicit cross-join node or reject plan.
I8 Memo expression count never exceeds the §4 hard cap (25,000,000). Bounds worst-case RSS (§32 C2). memo::budget Counter compared against cap on every insert. memo_group_count Abort optimization at cap; escalate below soft threshold.
I9 plan-enumerator terminates within its allotted time/expression budget on every input, including adversarial join graphs. Without this, p99 latency (§4) is unbounded. plan-enumerator::budget Wall-clock deadline check per DP iteration. plan_enumerator_budget_exhausted_total Fall back to heuristic plan (§18.9), never block indefinitely.
I10 Replay-trace archives are append-only; no in-place mutation of a written record. Precondition for trustworthy replay (P8). replay-engine::archive Write-path assertion rejects any non-append write. replay_archive_illegal_write_total Reject write; open new archive segment.
I11 Calibration coefficient versions increase monotonically; no coefficient set is reused after rollback. Prevents replaying an old regression's exact coefficient bug (§21.9). calibration::fitting Version-monotonicity check on every coefficient publish. calibration_version_regression_total Reject publish; require a new version number.
I12 A statistics-snapshot write is idempotent under retry (same input → same snapshot id). Statistics ingestion crosses an untrusted network boundary and must tolerate retries (§22 T2). statistics::persistence Content-hash comparison on duplicate snapshot-id write. statistics_write_idempotency_violations_total Reject conflicting write; keep first-committed snapshot.

Debugging methodology. Every invariant above has exactly one assertion site and one counter; there is no invariant enforced only "by convention." A deterministic simulator (benchmark-harness::runner in replay mode) drives synthetic and archived-replay workloads through every phase with all twelve assertions active, so an invariant violation is caught at the exact insert/mutation that caused it, not downstream where the blast radius has already spread across the memo.

8. Domain Model — Relational IR, Memo State Machine & Wire Records

8.1 Relational IR — Core Logical Operators

Canonical logical operator set (sql-ir::ast), each a variant of the LogicalOp enum (§11): Scan, Filter, Projection, Aggregate, Join, Sort, Limit, Union, Window, Exchange. Exchange is logical-IR-visible (not execution-only) because distributed cost penalties (§21) attach to it during logical-to-physical costing, not after.

8.2 Join Candidate State Machine

State Meaning Exit Condition
Unexplored No physical/logical alternative generated yet for this memo group. Rule-based enumeration begins (§14.2).
PartiallyExplored A strict subset of applicable rules has fired. Remaining applicable rules still pending, or budget exhausted (I9).
Costed All generated candidates for this group carry a CostVector. Winner selection runs (§17.2).
Pruned Candidate dominated by a cheaper alternative under identical physical properties. Terminal — candidate retained for explain rationale (P3) but never selected.
Materialized Winning candidate selected for this group; group frozen. Terminal — handed to physical plan generator (§19).

8.3 Histogram Model

Supported histogram kinds (statistics::histogram): EquiDepth, Singleton (exact per-value bucket for high-frequency values), TopKFrequency, HybridSkewAware (singleton buckets for detected heavy hitters, equi-depth elsewhere — Poosala et al. 1996, §5 Papers). One-line bucket signature (no body):

struct HistogramBucket { lower_bound: ScalarValue, upper_bound: ScalarValue, row_count: u64, distinct_count: u64, frequency: f64 }

8.4 Wire / Persisted Record Layouts

struct FeedbackMessage { query_hash: QueryHash, plan_hash: PlanHash, operator_id: OperatorId, estimated_rows: u64, actual_rows: u64, cpu_time_ns: u64, spill_bytes: u64, network_bytes: u64, timestamp: Timestamp }
struct StatisticsSnapshotHeader { snapshot_id: SnapshotId, schema_version: u16, created_at: Timestamp, table_count: u32, content_hash: Blake3Hash }
struct ReplayTraceRecord { trace_id: TraceId, session_id: SessionId, plan_hash: PlanHash, phase_spans: Vec<PhaseSpan>, cost_breakdown: CostVector }

FeedbackMessage is the wire record optimizer-core receives from the execution engine post-run (§21.2); StatisticsSnapshotHeader prefixes every persisted snapshot (I3, I12); ReplayTraceRecord is the unit replay-engine appends per optimized query (I10).

8.5 Plan Enumeration Pipeline Sequence

AST (external) -> sql-ir::build -> memo::seed -> [rule firing] -> cardinality::estimate
   -> cost-model::cost -> plan-enumerator::enumerate -> memo::freeze -> physical plan

8.6 Cost Vector Domain Semantics

CostVector (§11.2) components are additive within a plan subtree and are never renormalized — cost-model sums child CostVectors component-wise before adding the parent operator's own contribution (I5 non-negativity applies at every level). Cross-component comparison (e.g., trading IO for CPU) happens only through the single scalar total used by plan-enumerator's dominance check; explain always renders the five components separately (P7).

11. Core Schema & Types

Every load-bearing type below is a signature-only declaration (no method bodies). Each is annotated for ownership, mutation, concurrency, persistence, serialization, and compatibility.

11.1 MemoGroup

struct MemoGroup { group_id: GroupId, logical_exprs: Vec<ExprId>, physical_exprs: Vec<ExprId>, best_expr: Option<ExprId>, cardinality_estimate: CardinalityEstimate, properties: PhysicalProperties }
  • Ownership: owned exclusively by one memo::Memo instance (P11); no external aliasing.
  • Mutation: mutable until Materialized (§8.2), immutable after freeze (I1).
  • Concurrency: single-writer per session; read access via explain only after freeze.
  • Persistence: not persisted directly; ReplayTraceRecord (§8.4) captures a frozen projection.
  • Serialization: none in the hot path; replay projection is Protobuf (ADR-03).
  • Compatibility: internal-only layout; may change within a minor version (not ADR-16-gated).

11.2 CostVector

struct CostVector { cpu_cost: f64, io_cost: f64, memory_cost: f64, network_cost: f64, spill_cost: f64 }
  • Ownership: owned by the MemoExpression it costs; copied into ReplayTraceRecord.cost_breakdown.
  • Mutation: immutable once constructed (I5 enforced at construction).
  • Concurrency: Send + Sync, safe to read from explain concurrently with other sessions.
  • Persistence: persisted verbatim inside ReplayTraceRecord (§8.4).
  • Serialization: Protobuf (ADR-03); every field required, no optional cost components (P7).
  • Compatibility: additive-only field growth permitted within a major version (ADR-16 / §25).

11.3 HistogramBucket

struct HistogramBucket { lower_bound: ScalarValue, upper_bound: ScalarValue, row_count: u64, distinct_count: u64, frequency: f64 }
  • Ownership: owned by a StatisticsSnapshot's per-column histogram vector.
  • Mutation: immutable once a snapshot is published (I3).
  • Concurrency: shared-read across all sessions pinned to the same snapshot.
  • Persistence: persisted as part of statistics::persistence snapshot files.
  • Serialization: Protobuf (ADR-03), schema-versioned (ADR-08 hybrid-histogram tag included).
  • Compatibility: bucket-kind tag is append-only enum (§25).

11.4 RuntimeFeedbackRecord

struct RuntimeFeedbackRecord { query_hash: QueryHash, operator_hash: OperatorHash, estimated_rows: u64, actual_rows: u64, runtime_ns: u64, spill_bytes: u64 }
  • Ownership: constructed by cardinality::feedback from an inbound FeedbackMessage (§8.4).
  • Mutation: immutable once constructed; append-only into the calibration input stream.
  • Concurrency: Send, single-consumer queue into calibration::fitting.
  • Persistence: persisted into the calibration replay archive.
  • Serialization: Protobuf (ADR-03).
  • Compatibility: additive-only (§25).

11.5 OptimizerSession

struct OptimizerSession { session_id: SessionId, snapshot: Arc<StatisticsSnapshot>, trace_id: TraceId, budget: SearchBudget, phase_cursor: Phase }
  • Ownership: owns the memo it drives; request-scoped, dropped at session end.
  • Mutation: phase_cursor advances monotonically through §8.5's pipeline.
  • Concurrency: not Sync — one session, one thread group (P11); snapshot is Arc-shared read-only.
  • Persistence: none directly; emits ReplayTraceRecord on completion.
  • Serialization: none.
  • Compatibility: internal-only.

11.6 AccessPathCandidate

struct AccessPathCandidate { path_kind: AccessPathKind, index_id: Option<IndexId>, estimated_cost: CostVector, estimated_rows: u64 }
  • Ownership: owned by the plan-enumerator candidate set for a scan group.
  • Mutation: immutable once costed.
  • Concurrency: Send + Sync.
  • Persistence: surfaced through explain only, not separately persisted.
  • Serialization: Protobuf (ADR-03) inside explain trace payloads.
  • Compatibility: AccessPathKind is an append-only enum (§25).

11.7 StatisticsSnapshot

struct StatisticsSnapshot { header: StatisticsSnapshotHeader, histograms: HashMap<ColumnId, Vec<HistogramBucket>>, ndv: HashMap<ColumnId, u64> }
  • Ownership: owned by statistics::snapshot; shared via Arc into every pinned OptimizerSession.
  • Mutation: immutable after publish (I3, I12).
  • Concurrency: Send + Sync, many concurrent readers, single writer (versioned swap).
  • Persistence: persisted via statistics::persistence.
  • Serialization: Protobuf (ADR-03), header carries schema_version (P5).
  • Compatibility: ADR-16-gated; major-version bump required to change header layout.

11.8 CalibrationProfile

struct CalibrationProfile { profile_id: ProfileId, version: u32, coefficients: HashMap<CostComponent, f64>, fitted_at: Timestamp }
  • Ownership: owned by calibration::fitting; read-only reference held by cost-model during costing.
  • Mutation: immutable per version; new coefficients publish as a new version (I11).
  • Concurrency: Send + Sync, hot-swappable between optimization requests only (never mid-session).
  • Persistence: persisted alongside statistics snapshots.
  • Serialization: Protobuf (ADR-03).
  • Compatibility: CostComponent enum is append-only (§25).

11.9 ExplainTrace

struct ExplainTrace { trace_id: TraceId, plan_hash: PlanHash, pruned_candidates: Vec<PruningRationale>, cost_breakdown: CostVector, phase_spans: Vec<PhaseSpan> }
  • Ownership: owned by explain::trace; constructed read-only from a frozen memo.
  • Mutation: immutable once constructed.
  • Concurrency: Send + Sync.
  • Persistence: persisted verbatim as the body of a ReplayTraceRecord (§8.4).
  • Serialization: Protobuf (ADR-03), OpenTelemetry span export (ADR-05) for phase_spans.
  • Compatibility: additive-only field growth (§25).

11.10 MemoExpression

struct MemoExpression { expr_id: ExprId, group_id: GroupId, op: LogicalOp, children: Vec<GroupId>, state: CandidateState }
  • Ownership: owned by its MemoGroup (§11.1).
  • Mutation: state transitions per §8.2 state machine; op/children immutable after construction.
  • Concurrency: single-writer per session.
  • Persistence: none.
  • Serialization: none.
  • Compatibility: internal-only.

  • Alias-collision resolution order depends on AST traversal order, which can vary across parser versions upstream. 13.7 Performance Concerns

  • Excessive allocation from re-interning identical subexpressions across sibling branches — mitigated by structural-hash-keyed interning (P6).

Postmortem guidance: a spike in CanonicalizeError rate correlates with an upstream parser change — check parser version first.

  • Feedback ingestion must not block the estimation hot path — FeedbackIngestor runs on a separate bounded queue (P2), never inline with a live optimization session.

16.8 Edge Cases

  • Highly skewed joins where the join key's heavy hitter accounts for > 50% of rows — hybrid histogram's singleton bucket must dominate the estimate, not be averaged away by equi-depth buckets.
  • A predicate on a column with zero histogram coverage (newly added column, no statistics yet) — estimate falls back to a documented default selectivity, tagged Uncertain (I4).
  • Runtime feedback for a query whose plan hash no longer matches any archived plan (schema changed underneath) — feedback is dropped with a counter increment, never mis-attributed to a different plan.

16.9 Failure Analysis

Large estimation divergence (actual vs. estimated rows beyond a q-error ceiling) emits an alert but never aborts the query — a bad cardinality estimate degrades plan quality, it does not make the query incorrect. Detection: cardinality_qerror histogram compared against a rolling threshold. Blast radius: the one plan's cost quality; correctness is unaffected (I4's monotonicity clamp bounds the worst case). Containment: feedback ingestion quarantines feedback whose estimated_rows diverges implausibly (e.g.,

10^6 x) as likely corrupt telemetry rather than a real signal. Recovery: statistics refresh (§15) or calibration refit (§21) as the underlying fix; the estimate itself self-corrects only after refresh.

16.10 Operational Notes

Metrics: cardinality_qerror (histogram), cardinality_monotonicity_violations_total (I4), feedback_ingest_latency_ms. Tracing: cardinality.estimate_filter, cardinality.estimate_join spans. Structured-log fields: predicate_id, selectivity, uncertain. Deployment: no external interface change. Rollback unit: none directly (cardinality has no persisted coefficients of its own — see calibration, §21). Compatibility: CardinalityEstimate field additions are additive-only (§25).

17.6 Pitfalls

  • Double-counted network penalties when a nested exchange's parent operator re-applies a network cost already charged by the child exchange. Manifestation: total plan cost for multi-exchange distributed plans is implausibly high relative to single-exchange plans of similar shape. Root cause: network cost attached at both the Exchange operator and its consuming parent instead of only the operator that performs the transfer. Debugging: fixtures/cost/double_counted_network_regression.plan. Signal: distributed plans are systematically de-prioritized versus single-node plans beyond what their real cost justifies. Recovery: network cost is charged exactly once, at the Exchange node.
  • Recursive cost recomputation when a shared subtree (memo group reused by multiple parents) is costed independently per parent instead of once per group. Root cause: costing implemented as a naive recursive walk over the logical tree rather than the memo's group structure. Debugging: profile cost_model_negative_component_total-adjacent call counts — cost calls should equal group count, not parent-edge count. Signal: p95 optimization latency (§4) grows superlinearly with join count. Recovery: cost per group once, cache the result, reuse across parents (mirrors memo's own deduplication, §14).

17.7 Performance Concerns

  • Recursive cost recomputation (§17.6) is the dominant latency risk on wide, bushy join trees — addressed by per-group caching, not by simplifying the cost formulas.
  • Vectorization-coefficient lookup must be O(1) per operator (a small calibration table indexed by operator kind + batch width bucket), not a per-call model fit.
  • IO cost's page-fetch estimate must avoid re-deriving cardinality — it consumes the already-computed CardinalityEstimate (§16), never recomputes selectivity itself.

17.8 Edge Cases

  • Zero-row pipelines (a filter estimated to pass zero rows) — cost is the minimum fixed overhead, never zero (a zero-cost operator would incorrectly dominate every alternative in plan-enumerator).
  • A plan with no spill risk at all — spill_cost is exactly 0.0, not omitted or None (P7 requires every component present, always).
  • An Exchange operator with RTT below the §4 intra-AZ floor (e.g., co-located shards) — network cost floors at the minimum calibrated constant, never reaches exactly zero (there is always some serialization overhead).

17.9 Failure Analysis

A cost anomaly (a CostVector wildly inconsistent with its inputs, caught by cross-checking against benchmark-harness calibration bounds) triggers replay archival for later analysis rather than an immediate abort — a bad cost estimate degrades plan quality, not correctness. Detection: calibration bound check in CI plus cost_model_negative_component_total in production. Blast radius: the one plan's ranking; other candidates in the same memo are costed independently and unaffected. Containment: anomalous cost estimates are flagged in explain output (P3) so operators see the anomaly, not just a bad plan choice. Recovery: calibration (§21) recalibration is the systemic fix.

17.10 Operational Notes

  • Constraint introduced: disconnected join components are forbidden unless an explicit cross join node represents the gap (I7) — the enumerator never silently treats a disconnected graph as fully joined.

18.2 Detailed Implementation Steps

  • Files touched: crates/plan-enumerator/src/{dp_search.rs,pruning.rs,access_path.rs}.

  • Data structures: JoinGraph (nodes = relations, edges = join predicates, I7 connectivity-checked); per-subset best-cost cache keyed by relation bitmask.
  • Sync primitives: parallel exploration workers (bounded thread pool, sized per §4's 16–64 core assumption) each own a disjoint subset-bitmask range — no shared mutable state, results merged at the end (P11-consistent: still single-writer into the memo, workers only compute candidates).

  • Observability hooks: pruning counters (plan_enumerator_pruned_total), budget-exhaustion counter (plan_enumerator_budget_exhausted_total, I9).
  • Test harness: fixtures/join/* below, including a deliberately adversarial wide-join fixture.

A search-capable optimizer: DpSearch::enumerate returns a deterministic best-plan candidate set for join graphs up to the configured threshold via exact DP, and a bounded heuristic fallback beyond it, always terminating inside the §4 latency budget.

18.4 Acceptance Criteria

  • Deterministic best-plan selection: fixtures/join/10way_join.plan selects the identical join order across 10 repeated runs (P1).

18.5 Conformance Fixtures

  • fixtures/join/10way_join.plan — a 10-relation join graph; expected: deterministic bushy-tree selection.
  • fixtures/join/cross_join.plan — explicit cross join over two otherwise-disconnected subgraphs; expected: accepted, I7 satisfied.
  • fixtures/join/cyclic_join_graph.plan — a join graph with a predicate cycle (self-join style); expected: DP search handles the cycle without infinite subset expansion.
  • fixtures/join/factorial_explosion_regression.plan — 14-relation adversarial graph; expected: budget-bounded fallback fires, total latency stays under the §4 p99 ceiling.

18.6 Pitfalls

  • Factorial search explosion when bushy enumeration is attempted without a join-count threshold for the GEQO-style fallback. Manifestation: enumeration time grows factorially past ~12 relations. Root cause: exact DP over all bushy partitions is exponential in relation count. Debugging: plan_enumerator_budget_exhausted_total spikes on wide-join workloads. Signal: p99 latency (§4) breached specifically on queries with join count above the threshold. Recovery: enforce the GEQO- style fallback threshold (§18.2) unconditionally — never allow exact DP unbounded.
  • Memo contention when parallel exploration workers (§18.2) all attempt to insert candidates into the same memo groups without coordination. Manifestation: memo_verifier_violations_total (I1) rises under parallel search. Root cause: workers compute candidates in parallel but insert must remain single-writer (P11) — a naive implementation lets workers insert directly. Debugging: reproduce with worker count forced to 1 versus > 1. Signal: violation only under concurrency. Recovery: workers return candidates to a single collector thread that performs all memo inserts.

18.7 Performance Concerns

  • Parallel exploration worker count must respect the §4 16–64 core assumption and NUMA-node ceiling (≤ 2 nodes validated) — oversubscribing workers past core count adds scheduling overhead without search speedup.
  • Per-subset best-cost cache must stay within the memo's soft-warning threshold (§4, 5,000,000 expressions) — cache eviction policy needed for join graphs near that boundary.
  • Branch-and-bound pruning's running best-cost bound must be updated promptly (not lazily) or the prune rate degrades and search approaches the unpruned exponential cost.

18.8 Edge Cases

  • Cyclic join graphs (self-join on the same base relation via two different aliases) — DP search must treat each alias as a distinct graph node, never collapse them.
  • A join graph with a single relation (no joins at all) — enumeration short-circuits to the trivial single-candidate case, not a degenerate zero-subset DP table.
  • Search timeout mid-enumeration (budget exhausted before any candidate completes costing) — falls back to the cheapest fully-costed partial result, never returns no plan at all.

18.9 Failure Analysis

A search timeout triggers the heuristic fallback (§18.2 GEQO-style path), never a query failure — this is the one place in the system where "give up on optimal" is the correct, designed behavior (P10). Detection: plan_enumerator_budget_exhausted_total. Blast radius: the one query's plan quality (likely a merely-good rather than optimal join order); correctness is unaffected. Containment: the fallback plan still passes all cost invariants (I5) and connectivity checks (I7). Recovery: no action needed per-incident; a sustained rise in the fallback rate is an operational signal to raise the join- count threshold or add hardware (§29).

18.10 Operational Notes

Metrics: plan_enumerator_pruned_total, plan_enumerator_budget_exhausted_total, plan_enumerator_worker_utilization. Tracing: enumerator.dp_search, enumerator.prune spans. Structured-log fields: join_graph_relation_count, fallback_triggered. Deployment: worker-pool size is a startup config, tunable without a binary redeploy. Rollback: N/A (stateless per session). Compatibility: PlanCandidate internal shape may change freely within a minor version.

  • Branch-heavy costing logic (§19.6) risks both a maintenance and a performance cost if the dominance check is not O(1) per comparison — keep it a direct CostVector comparison, not a re-derivation.

Detection: structural compatibility check in PhysicalGenerator::materialize. Containment: the execution engine never receives a tree the optimizer itself flagged as structurally invalid. Recovery: if re-attempted generation also fails, escalate to a regression-quarantine case for plan-enumerator review (candidates may be insufficient).

  • Constraint introduced: calibration coefficient publication happens strictly between optimization requests, never mid-session (§11 CalibrationProfile concurrency note) — a session's cost model is fixed for its entire lifetime, matching I3's statistics-snapshot pinning.

21.3 Deliverable

A distributed-aware, self-calibrating optimizer: exchange and repartition costs are modeled against real cluster topology and calibrated against runtime feedback, with drift detection and safe, version-monotonic rollback (I11) when a calibration regresses plan quality.

21.4 Acceptance Criteria

  • Network calibration benchmarks: fitted per-byte and per-exchange coefficients reproduce benchmark-harness TPC-H distributed-scale-out latencies within 15% on fixtures/distributed/ distributed_tpch.plan.
  • fixtures/distributed/skew_repartition_regression.plan (heavy-hitter shuffle key) predicts repartition imbalance within 2x of the observed runtime skew.
  • DriftDetector::check flags a calibration profile whose fitted coefficients diverge > 25% from the previous version's validated range, before that profile is published.
  • fixtures/calibration/overfitting_regression.parquet (a single-workload-only feedback sample) is rejected by CalibrationFitter::fit's minimum-diversity check, never silently accepted.

21.5 Conformance Fixtures

  • fixtures/distributed/distributed_tpch.plan — distributed TPC-H exchange-heavy plan; expected: exchange cost matches calibrated network model within 15%.
  • fixtures/distributed/skew_repartition_regression.plan — heavy-hitter shuffle key; expected: skew-aware shuffle cost dominates the naive uniform-shuffle estimate.
  • fixtures/calibration/calibration_replay.parquet — archived runtime feedback batch; expected: CalibrationFitter::fit reproduces the archived coefficient set exactly (P1 applied to calibration).
  • fixtures/calibration/overfitting_regression.parquet — single-workload feedback only; expected: rejected by the minimum-diversity check, not silently fit.

21.6 Pitfalls

  • Underestimating shuffle amplification when skew detection (§15 heavy-hitter tracking) is not consulted during exchange costing, defaulting to uniform distribution. Manifestation: a skewed shuffle key spills one partition while the cost model predicted balance. Root cause: exchange_cost ignores the shuffle key's existing histogram heavy-hitter data. Debugging: fixtures/distributed/skew_repartition_regression.plan + runtime spill_bytes. Signal: skewed-key distributed plans underperform their estimate specifically. Recovery: exchange_cost must consult §15.2's heavy-hitter data, never assume uniformity.
  • Overfitting workloads when CalibrationFitter::fit runs against a feedback sample dominated by one query shape. Manifestation: OLTP accuracy improves while analytical-join accuracy degrades. Root cause: no diversity check pre-fit. Debugging: fixtures/calibration/overfitting_regression.parquet. Signal: cost-anomaly rate rises for analytical queries right after a publish. Recovery: enforce a minimum query-shape diversity threshold before fit accepts a sample.

21.7 Performance Concerns

  • Network model complexity (per-hop RTT + per-byte + skew adjustment) stays O(1) per exchange operator at optimization time — fitting (regression) is entirely offline (§21.2), never on the hot path.
  • DriftDetector::check runs per new CalibrationProfile before publish, not per optimization request — offline-adjacent, matching calibration's out-of-band write discipline (§21.1).
  • Skew-aware shuffle cost reuses §15's heavy-hitter structures rather than a parallel skew estimate — avoids doubling the statistics-subsystem memory footprint (§4 histogram budget).

21.8 Edge Cases

  • A single-node cluster topology — exchange cost is not computed (no Exchange operators generated, per §18's join-graph shape for single-node deployments).
  • A zero-variance calibration feedback batch (every query identical) — rejected by the diversity check, same path as the overfitting pitfall (§21.6).
  • Repartition imbalance severe enough that one partition alone exceeds the §4 histogram/memo memory budget — flagged as a capacity-planning alert (§29), never silently absorbed into a cost number.

21.9 Failure Analysis

A distributed-topology mismatch (the optimizer's ClusterTopology view is stale) is flagged via a topology-version check at session start, not mid-optimization. Detection: version compare against the cluster's live membership service (external input). Blast radius: distributed cost estimates for the affected session only — I3-style pinning means the session finishes with the topology it started with. Containment: sessions against a stale topology are flagged in explain output. Recovery: refresh ClusterTopology and re-optimize; a bad calibration publish rolls back via I11's version-monotonic mechanism (always a new version number, never a republish of an old one).

21.10 Operational Notes

Metrics: calibration_version_regression_total, exchange_cost_skew_adjustment_ratio, calibration_drift_score. Tracing: cost.exchange, calibration.fit, calibration.drift_check spans. Structured-log fields: cluster_topology_version, calibration_profile_version, shuffle_skew_ratio. Deployment: calibration fitting runs as a scheduled offline job (Python tooling, §1), never inside optimizer-service's request path. Rollback unit: calibration coefficients (§24) — roll back to the prior monotonic version (I11); statistics snapshots and optimizer rule sets are the other two rollback units (§24), all three independently versioned.

24. Operational Readiness

Metrics strategy. Every phase registers its counters/gauges/histograms at Phase 0 startup, never lazily on first use (so dashboards never show a metric silently absent). Core cross-phase metrics: optimization_latency_ms, memo_group_count (I8), cardinality_qerror (I4), spill_prediction_error (§19.6), replay_divergence_total (I2, I10), histogram_refresh_age (§15). Every metric named in a phase's Operational Notes subsection is registered before that phase's first request path executes.

Tracing strategy. Every optimization request emits, at minimum: the optimizer.session root span (§12.10), phase-sequencing spans (sqlir.canonicalize, memo.insert/memo.freeze, statistics.publish-adjacent reads, cardinality.estimate_*, cost.compute_*, enumerator.dp_search, physical.materialize, explain.render, replay.append, cost.exchange / calibration.*), and a replay id (ADR-20) correlating all of them. Spans export via OpenTelemetry (ADR-05); span attributes never carry unbounded-cardinality values (mirrors T4's mitigation).

Deployment topology. Three concretely supported shapes (§1 deployment model): standalone optimizer-service behind Kubernetes (ADR-15) with horizontal pod autoscaling keyed on plan_enumerator_worker_utilization; embedded library linked directly into a host execution-engine process, no network hop; distributed-SQL-engine plugin, one optimizer-core instance per query coordinator node, sharing a cluster-wide statistics snapshot store.

Rollback strategy. Three independently versioned rollback units (cross-referenced from §17.10, §20.10, §21.10): calibration coefficients (CalibrationProfile, I11 version-monotonic), statistics snapshots (SnapshotId, I3/I12), and optimizer rule sets (memo rewrite-rule table version). Each rolls back independently — a bad calibration publish never forces a statistics rollback, and vice versa. Rollback of any unit takes effect only for new sessions (I3-style pinning means in-flight sessions finish on their pinned version).

25. Compatibility & Versioning

Wire compatibility. All RPC payloads (Protobuf, ADR-03) are versioned per P5; optimizer-service supports N and N-1 major wire versions simultaneously during a rolling upgrade window. PhysicalPlanTree (§19.2) is Substrait-compatible (ADR-17), giving interoperability independent of this system's own release cadence.

Storage compatibility. Replay archives are immutable (I10) and forward-readable only within a major version — a major-version bump that changes ReplayTraceRecord's layout (§8.4) requires an explicit migration tool, never an in-place archive rewrite. Statistics snapshot headers (StatisticsSnapshotHeader, §11) carry schema_version and are rejected outright (not best-effort-parsed) if the version is unrecognized (P5, FM-6).

Semantic versioning. Major versions may invalidate serialized memo formats (internal-only, §11 — never persisted, so this has zero external migration cost). Minor versions add fields additively only (CostVector, AccessPathCandidate, CalibrationProfile — all explicitly additive-only per §11). Patch versions never touch any serialized or wire format.

Compatibility test gate. CI runs the full fixtures/* suite against both the current version and the immediately prior major version's serialized fixtures before any release artifact (§27) is cut — a compatibility break is a release blocker, not a follow-up ticket.

26. Testing & Verification Strategy

Unit testing. Targets: histogram correctness (§15.4), cost equations (§17.4, I5), memo invariants (§14.4, I1/I8), cardinality monotonicity (I4). Every invariant in §7 has a dedicated unit test that exercises its exact assertion site, not just an end-to-end path that happens to cover it.

Integration testing. Targets: full-pipeline optimizer replay (§20.4), distributed costing (§21.4) against a simulated multi-node ClusterTopology, and cross-phase fixture chains (a fixtures/parser/* input flowing through to a fixtures/physical/* output in one test).

Fuzz testing. Targets (ADR-12, cargo-fuzz): the parser-adjacent AST-ingestion boundary (fuzz/fuzz_targets/parser_fuzz.rs), memo rewrite rules (fuzz/fuzz_targets/memo_rewrite_fuzz.rs, guarding I1), and serialization round-trips (fuzz/fuzz_targets/serialization_fuzz.rs, guarding P5). Fuzz campaigns run continuously in CI (.github/workflows/fuzz.yml) and on every release candidate.

Differential testing. Cardinality and plan-shape outputs are compared against PostgreSQL, DuckDB, and Apache Calcite (the same three reference implementations studied in §5) on the shared TPC-H/TPC-DS corpus — not for byte-identical plans (join orders legitimately differ across optimizers) but for cardinality-estimate q-error parity and for catching a Selinger-lineage cost-model bug this blueprint's own tests missed.

Deterministic-simulator testing. Per §7's debugging methodology: every fixtures/* case runs through benchmark-harness::runner in replay mode with all twelve §7 invariant assertions active, so a violation is caught at its insertion point, never downstream.

27. Build & Release Engineering

Reproducible builds. Pinned dependencies (Cargo.lock committed, ADR-02); deterministic container builds (Dockerfile, multi-stage, no floating base-image tags); cargo build --locked enforced in CI so a lockfile drift fails the build rather than silently resolving new versions.

Release artifacts. optimizer-cli and optimizer-service binaries (per-platform, x86_64 baseline per §4); replay-tooling (the tools/plan_diff and tools/calibration_fit binaries) shipped separately since they are operator utilities, not runtime dependencies.

SBOM generation. SPDX-format SBOM (scripts/generate_sbom.sh) generated per release and attached to the GitHub release artifact (ADR-13); dependency signature verification runs as a release-gate CI job, not a post-release audit (T6 mitigation, §22).

Versioning and tagging. Semantic versioning (§25) drives release tags; a major-version release requires the §25 compatibility test gate to pass and requires an explicit migration-tool release alongside it if any storage format changed.

Container and orchestration. Docker images (ADR-14) built per release, deployed via the Kubernetes templates in /templates/optimizer-service.yaml (ADR-15); docker-compose.yml provides the local integration-testing stack, never used in production.

28. Performance Engineering

29. Scalability Analysis

Bottlenecks. Memo explosion on wide bushy joins (§14.6, §18.6) is the primary CPU/memory bottleneck; histogram scanning under repeated multi-predicate filters (§16.6) is the primary per-request latency bottleneck; distributed search fanout (parallel exploration workers, §18.2) bottlenecks on core count and NUMA topology past the §4 2-node ceiling; replay-archive growth (§20.6) bottlenecks storage, not compute.

Horizontal scaling. optimizer-service workers are stateless per request beyond the pinned statistics snapshot (I3) — horizontal pod autoscaling (Kubernetes, ADR-15) scales linearly with plan_enumerator_worker_utilization up to the point where shared statistics-snapshot fetch latency (§4, ≤ 10 ms p95) becomes the limiter, not CPU.

Vertical scaling. NUMA-aware memory pools (ADR-18 mimalloc configuration) become required, not optional, above 64 cores or beyond the §4 2-NUMA-node validated ceiling — cross-node memo access latency otherwise invalidates the p99 target (M3) even with spare CPU headroom.

Capacity planning trigger. A sustained rise in plan_enumerator_budget_exhausted_total (FM-7) or in memo_group_count approaching the §4 soft-warning threshold, sustained across multiple hours, is the operational signal to add optimizer-service replicas rather than to first suspect a code regression.

30. Mental Models & First Principles

  • MM1 — Memoization turns exponential into polynomial-bounded. Compressed insight: deduplicating structurally-identical subplans (Cascades, §5) converts an exponential enumeration into one bounded by memo size, not join-order permutation count. Predicts: search cost scales with distinct subplan shapes, not with n!. Bug class without it: reimplementing join search as a flat permutation loop that silently explodes past ~10 relations. Applies in §14 and §18.
  • MM2 — Cost is additive, never re-derived. Compressed insight: a CostVector's components sum strictly up the plan tree (I5, P7); any place a component is recomputed from another component instead of propagated is a double-counting bug waiting to happen. Predicts: any "cost looks too high for multi-exchange plans" report is a double-counting bug, not a calibration bug. Bug class without it: the exact §17.6 double-counted-network pitfall. Applies in §17.
  • MM3 — Cardinality error compounds multiplicatively up a join tree. Compressed insight: a 2x per-predicate cardinality miss on a 5-join query can compound to a 32x miss at the root under independence-assumption chaining. Predicts: q-error grows with join depth even when every individual histogram is locally accurate. Bug class without it: blaming a single "bad histogram" for a plan regression that is actually compounding error. Applies in §16.
  • MM4 — Determinism is a precondition for observability, not a nice-to-have. Compressed insight: you cannot debug what you cannot replay (P1, P8); every debugging tool downstream (explain, replay-engine) assumes byte-identical replay is possible. Predicts: any nondeterminism bug (a timestamp leak, an unpinned iteration order) manifests first as "unreproducible" bug reports, not as a crash. Bug class without it: the §13.6/§20.6 hash-instability and trace-ID pitfalls. Applies in §13 and §20.
  • MM5 — A search budget is a correctness boundary, not a performance nicety. Compressed insight: without I9's hard termination guarantee, "slow" and "hung forever" are the same failure mode under an adversarial join graph. Predicts: any latency SLO (§4 p99) is actually an availability SLO once an adversarial or merely very-wide query is possible. Bug class without it: an unbounded DP search taken down by a single 20-way-join query. Applies in §18.
  • MM6 — Staleness is safer than absence for pinned state. Compressed insight: I3's snapshot pinning means a session with slightly-stale statistics is always preferable to a session that blocks waiting for the newest write. Predicts: statistics availability (§4, 99.9%) can be looser than optimizer availability (99.95%) precisely because stale-but-available is an acceptable degraded mode. Bug class without it: over-engineering a statistics-freshness barrier that hurts availability for no cardinality benefit. Applies in §15.
  • MM7 — Calibration must be more diverse than any single workload it is fit against. Compressed insight: a coefficient fit is only as general as its input diversity (I11, §21.6); fitting against one workload optimizes that workload at other workloads' expense. Predicts: an isolated calibration improvement for one query shape, paired with a regression elsewhere, is overfitting, not a fitting bug. Bug class without it: shipping a calibration profile validated only against the workload that triggered the recalibration request. Applies in §21.
  • MM8 — Every pruned alternative is a future debugging question. Compressed insight: P3's observability-first principle means a pruning decision not captured today is an unanswerable "why didn't it pick X" question tomorrow. Predicts: explain output quality directly determines mean time-to-diagnosis for every future plan-regression incident. Bug class without it: capturing only the winning plan and discovering, mid-incident, that the rejected alternative's cost was never recorded. Applies in §20.

32. Back-of-Envelope Capacity Model

  • C1 — Memo expression average size. MemoExpression (§11.10: 8+8+16+24+1 B fields, padded) = 64 B/expression (57 B raw + 7 B alignment padding).
  • C2 — Memo RAM at hard cap. 25,000,000 expressions × 64 B (C1) = 1.6 GB, + 18% allocator/Robin-Hood slack (ADR-18) = 1.89 GB, inside the §4 4 GB Phase-0 RSS ceiling.
  • C3 — Histogram RAM at budget. 512 MB ÷ 40 B/bucket (§11.3 HistogramBucket) = 13,421,772 buckets = ≈ 52,428 columns at 256 buckets/column, well above any real schema's column count.
  • C4 — Statistics snapshot fetch bound. 50 GB cluster-wide (§4) ÷ 10 ms p95 fetch target (§4) = 5,000 GB/s if fetching the whole store, but a real per-session fetch touches only its own tables (< 5 MB), not the total.
  • C5 — Optimization latency budget per DP subset. 1,500 ms p99 (§4) ÷ 2^14 subsets (14-relation adversarial graph, §18.4) = 91.6 µs/subset average before the §18.2 GEQO-style fallback must engage.
  • C6 — Concurrent throughput sizing. 50 complex queries/sec (§4) × 1,500 ms p99 (§4) = 75 concurrent in-flight complex sessions, sizing the §19 worker-pool lane at ≥ 75 workers.
  • C7 — Replay archive daily growth. 10,000 replays/hour (§4) × 24 h × 8 KB/record (§20.6 capped) = 1.92 GB/day raw, × 3× ceiling (§4) = 5.76 GB/day worst case, ÷ 4x Parquet compression = 1.44 GB/day expected.
  • C8 — FD budget vs. concurrent sessions. 65,536 FDs (§4) ÷ 4 FDs/session = 16,384 concurrent sessions supportable, well above C6's 75-session complex-query lane.
  • C9 — NUMA cross-node penalty threshold. 100 ns cross-node latency × 10^7 memo accesses (wide join) = 1 ms of cross-node latency once traffic crosses the §4 2-node NUMA validation ceiling, a material fraction of the 30 ms p50 budget (§4).
  • C10 — Mimalloc fragmentation slack derivation. (1.89 GB − 1.6 GB) ÷ 1.6 GB = 0.181, the 18% overhead figure used consistently in C2 (§4, ADR-18).
  • C11 — Calibration replay batch size. 22 TPC-H queries (§16.4) × 50 records/query × 40 B/record = 44 KB/calibration run, inside the §21.6 diversity-check minimum-sample bound.
  • C12 — Availability budget in absolute minutes. 0.05% of 30 days × 1,440 min/day = 21.6 min/month (§4), ÷ 15 s optimizer-restart RTO (§4) = 86.4 incidents/month before breach.

33. Hard Questions (Self-Examination)

  • Q1. If the memo hard cap (§4, I8) is hit mid-optimization, does the system return the best plan found so far or fail outright, consistent with §18's "always terminate" guarantee (I9)?
  • Q2. How does the independence-assumption failure (§16) interact with the correlation heuristic's own confidence — can a low-confidence correlation estimate be silently preferred over a high-confidence independence estimate (§7 I4)?
  • Q3. When explain (§20) shows a pruned candidate's cost, is it computed with the same CalibrationProfile version as the winner, across a mid-fleet calibration rollout (§21)?
  • Q4. §17's double-counted-network pitfall and §21's skew-underestimation pitfall both live in Exchange costing — could one structural fix eliminate both classes at once?

34. Alternative Architectures (Roads Not Taken)

Alt A — Pure Heuristic, No Cost Model

AST -> canonicalize -> fixed rule order (pushdown, pruning,
       join-order-by-heuristic) -> physical plan
       (no CostVector anywhere in the pipeline)

Regime where it wins: embedded/resource-constrained engines where optimization latency itself must be near-zero and query shapes are simple enough that heuristic join ordering (smallest-table-first, foreign-key-direction rules) is reliably close to optimal. Real system embodying it: SQLite's query planner for the common case (cost-based join reordering is limited and heuristics dominate for small schemas). Rejected here because: this blueprint's target workloads include wide analytical joins and skewed distributions (§1) where heuristic ordering diverges badly from cost-based ordering, exactly the gap Selinger et al. (1979, §5) identified as the reason cost-based optimization exists at all.

Alt B — Genetic-Algorithm Join Ordering as the Primary Search (not just a fallback)

Population of join-order permutations -> fitness = 1/cost
   -> selection + crossover + mutation -> converge over
      generations -> best-found order

Regime where it wins: extremely wide joins (30+ relations) where even a bounded DP/branch-and-bound search (§18) cannot terminate inside a reasonable latency budget at any join-count threshold, and an approximate answer found via evolutionary search is strictly better than a purely greedy heuristic. Real system embodying it: PostgreSQL's GEQO, used as its primary strategy above geqo_threshold. Rejected as the primary strategy here because: GEQO's convergence is nondeterministic across runs unless heavily seed-pinned, in tension with P1 (Determinism Over Convenience) — this blueprint instead uses a GEQO-style approach only as the bounded §18.2 fallback, seeded deterministically from the session's fixed inputs, never as the default path.

Alt C — Learned Cost Models / Learned Cardinality Estimators

Historical (plan, actual_cost) pairs -> train a model
   (e.g., a tree ensemble or neural estimator) -> replace
   histogram-based selectivity with model inference

Regime where it wins: stable, high-volume, repetitive workloads (the same query templates run thousands of times) where a learned model can specialize far beyond what generic histograms capture, and where retraining infrastructure is already operationally mature. Real system embodying it: Neo-style learned query optimizers and DB2's LEO lineage taken further into full model-based estimation. Rejected here (deferred, §35, PhaseDeferred("§16")) because: model staleness/drift under workload shift is harder to bound and explain than histogram staleness (§15.6), and P3's observability-first principle is much harder to satisfy for a learned model's "why did it estimate this" question than for a histogram bucket lookup — the calibration feedback loop (§21) already gives most of the accuracy benefit LEO-style learning provides, at far lower explainability cost.

Alt D — Eddies-Style Continuous Adaptive Routing (No Static Plan)

Tuples routed operator-by-operator through a router that
   re-decides routing per-tuple-batch based on live operator
   performance -- no fixed plan ever fully committed

Regime where it wins: highly unpredictable workloads where statistics are unreliable or absent and the cost of a wrong static plan is far higher than the overhead of continuous per-batch routing decisions — exploratory/ad hoc analytical environments. Real system embodying it: the Eddies research system (Avnur & Hellerstein 2000, §5 Papers) and its adaptive-query-processing descendants. Rejected here (deferred, §35, PhaseDeferred("§21")) because: continuous routing overhead conflicts directly with the §4 p50/p95/p99 latency budgets for OLTP-shaped queries, and P8's replayability-first principle is fundamentally harder to satisfy when "the plan" is a moving target rather than a fixed, hashable artifact (I2).

36. Glossary

  • Access Path — the chosen strategy (table scan, index scan) for retrieving a base relation's rows.
  • ADR — Architectural Decision Record; a locked technology/design choice with a named rejected alternative and the regime where that alternative would win (§9).
  • Bushy Join — a join tree that is not left-deep; both children of an internal join node may themselves be joins.
  • Calibration — the process of fitting cost-model coefficients against observed runtime feedback.
  • Cardinality — the estimated (or actual) row count produced by a relational operator.
  • Cascades — the top-down, memoized, rule-driven query-optimization framework (Graefe 1995) this blueprint's memo crate is architecturally descended from.
  • CostVector — the five-component (CPU, IO, memory, network, spill) cost estimate attached to a physical candidate (§11.2).
  • Cost-Based Optimization — selecting among semantically-equivalent plans by estimated execution cost rather than by fixed heuristic rules alone.
  • Deferred Feature — a capability intentionally excluded from the current build, registered in §35 with an explicit un-defer trigger.
  • Determinism — the property that identical inputs produce byte-identical outputs (P1); the precondition for replay (P8).
  • Eddies — an adaptive, per-tuple-batch routing query-processing architecture (Avnur & Hellerstein
    1. that forgoes a fixed static plan (§34 Alt D).
  • Equi-Depth Histogram — a histogram whose buckets each cover approximately equal row counts.
  • Exchange — the distributed data-movement operator that redistributes rows across nodes.
  • Explain — the subsystem exposing optimizer reasoning, cost breakdowns, and pruning rationale without re-running optimization (§20).
  • Expression Interning — deduplicating structurally-identical expressions into a single canonical ExprId.
  • GEQO — Genetic Query Optimizer; PostgreSQL's evolutionary-search fallback for wide joins (§18.2, §34 Alt B).
  • Heavy Hitter — a value in a column's distribution occurring frequently enough to warrant its own singleton histogram bucket rather than being averaged into an equi-depth bucket.
  • Histogram — a statistical summary of a column's value distribution used for selectivity estimation.
  • Independence Assumption — the (often false) assumption that two predicates' selectivities multiply independently; a major cardinality-estimation failure mode (§16.6).
  • Join Graph — the graph whose nodes are relations and whose edges are join predicates.
  • Materialized (memo state) — the terminal memo-group state after a winning candidate has been selected and the group frozen (§8.2).
  • Memo — the equivalence-class data structure storing all logical and physical alternatives considered during optimization (§14).
  • NDV — Number of Distinct Values; an estimate of a column's cardinality of unique values.
  • Physical Property — a characteristic (sort order, partitioning) a physical operator produces or requires, enforced top-down in a Cascades-style memo (ADR-09).
  • Plan Enumeration — the search process generating and costing candidate physical plans.
  • Plan Hash — the deterministic identity of a selected plan, used for replay comparison (I2).
  • Pruning — eliminating a dominated (strictly worse, same physical properties) candidate from further consideration (§8.2).
  • q-error — the ratio between an estimated and an actual cardinality, taken in whichever direction exceeds 1 (Leis et al. 2015); the scale-invariant accuracy metric used throughout this blueprint.
  • Replay — the deterministic reproduction of a past optimization decision from an archived trace.
  • Replay Trace — the persisted, append-only record of one optimization's full decision history (§8.4, I10).
  • Runtime Feedback — observed execution telemetry (actual rows, runtime, spill bytes) fed back into cardinality and calibration (§16, §21).
  • Search Budget — the bounded time/expression allotment a search must terminate within (I9).
  • Selectivity — the fraction of rows passing a predicate.
  • Singleton Bucket — a histogram bucket covering exactly one distinct value, used for heavy hitters.
  • Skew — a non-uniform value distribution where some values occur far more frequently than others.
  • Snapshot (statistics) — an immutable, versioned view of statistics pinned for a session's lifetime (I3).
  • Spill — materializing intermediate data to disk when it exceeds an in-memory budget.
  • Spill Penalty — the additional cost (disk amplification, serialization, repartition) from a spill (I6).
  • Top-K Frequency — tracking the K most frequent values in a column for heavy-hitter detection.
  • Vectorized Execution — a batch-oriented (rather than tuple-at-a-time) execution model whose cost profile this blueprint's CPU cost sub-model accounts for explicitly (Neumann 2011, §5).
  • Volcano — the bottom-up, rule-driven, extensible query-optimization framework (Graefe & McKenna
    1. that Cascades generalized.
