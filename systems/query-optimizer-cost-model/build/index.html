⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives
  • Stand up the 15-member Cargo workspace (§1 Phase 0 deliverable list; ADR-02) so every later phase has a compiling target to extend, not a greenfield decision to make.
  • Establish the sql-ir skeleton: LogicalOp enum (§8.1), expression interning table, no normalization logic yet.
  • Establish the memo skeleton: MemoGroup/MemoExpression signatures (§11), a verifier entry point that will grow into the I1 enforcement site, and the expression-budget counter that will enforce I8.
  • Wire telemetry span and metric registries end-to-end (root span emitted, one counter exported) so every later phase adds telemetry to an already-working pipe, never builds the pipe itself.
  • Wire CI (ADR-13), the fuzz-target skeleton (ADR-12), and the Makefile automation entrypoints.
  • Constraint introduced: the memo hard cap (25,000,000 expressions, §4) must be a compiled-in constant checked at insert time even though nothing yet inserts enough expressions to hit it (P6, P10).
Deliverable

cargo build --workspace produces all 10 library crates and 2 stub binaries. The memo skeleton compiles with a verifier that accepts any well-formed insert sequence (real I1 checks land in §14). optimizer-cli emits one root span per invocation, visible via the OpenTelemetry stdout exporter (ADR-05) — the first operator-inspectable artifact this system produces.

Acceptance
  • cargo build --workspace and cargo test --workspace succeed on CI (ADR-13) with zero warnings under -D warnings.
  • memo::budget::check_cap rejects an insert at count 25,000,001 and accepts at 25,000,000, verified by a unit test at both boundary values (§4 hard cap).
  • fixtures/skeleton/workspace_smoke.toml parses via cargo metadata in < 5 ms.
  • fixtures/skeleton/malformed_workspace.toml fails the build with a diagnosable Cargo error, not a panic or hang.
Fixtures
  • fixtures/skeleton/workspace_smoke.toml — minimal valid workspace manifest; expected: cargo metadata succeeds, all 15 members resolve.
  • fixtures/skeleton/invariant_smoke.case — a synthetic 10-insert memo sequence; expected: verifier stub accepts, memo_group_count reaches 10.
  • fixtures/skeleton/malformed_workspace.toml — manifest with a duplicate crate name; expected: build fails with Cargo's duplicate-package diagnostic, not a panic.
Pitfalls
  • Workspace-wide feature unification silently changes a dependency's default features between crates. Manifestation: a crate compiles alone but fails once pulled into the workspace build. Root cause: Cargo feature unification across the whole workspace graph. Debugging: cargo tree -e features. Signal: CI green on a single-crate job, red on the workspace job. Recovery: pin default-features = false explicitly per dependency.
  • The verifier stub always returns Ok(()), silently masking a real future I1 violation if left un-upgraded. Root cause: a placeholder never revisited. Debugging: grep for the Ok(()) sentinel in verifier.rs before Phase 2 sign-off. Signal: none until Phase 2 fixtures pass suspiciously easily. Recovery: verifier must gain real group-consistency checks before Phase 2 acceptance (§14.4).
  • mimalloc (ADR-18) global-allocator override applied inconsistently between binary and library crates. Root cause: #[global_allocator] only takes effect in the final binary crate, not in a library. Debugging: inspect the linked binary's allocator symbols. Signal: RSS above the §4 budget despite the mimalloc dependency being present. Recovery: set the global allocator only in bin/optimizer-cli and bin/optimizer-service.

⬜ Phase 1 — Relational IR & Deterministic Parsing §13

Objectives
  • Turn the Phase 0 sql-ir skeleton into a working deterministic AST-to-operator-graph compiler: canonicalization, deterministic hashing, expression interning, and replay-safe serialization (§3.2).
  • Establish the invariants later phases assume without re-checking: deterministic alias assignment, normalized predicate ordering, stable expression hashing (I2).
  • Scope boundary introduced: this phase assumes an external SQL parser has already produced an AST (§1 system boundaries — "delegates" parsing); sql-ir never tokenizes SQL text itself.
Deliverable

A runnable IR-compiler frontend: given a fixed AST, sql-ir deterministically emits a canonical OperatorGraph with stable ExprHashes, inspectable via explain_printer, and consumable by memo.

Acceptance
  • 10 consecutive canonicalization runs over fixtures/parser/joins.sql produce byte-identical ExprHash sequences (I2).
  • fixtures/parser/malformed_alias.sql is rejected with a structured diagnostic in < 1 ms, never a panic.
  • Alias-collision resolution is deterministic across 3+ independent runs on fixtures/parser/nested_subqueries.sql (same renamed aliases every time).
Fixtures
  • fixtures/parser/joins.sql — multi-table join AST; expected: stable canonical form, hash-stable.
  • fixtures/parser/nested_subqueries.sql — correlated subquery AST; expected: deterministic alias renaming, decorrelation deferred to §14.
  • fixtures/parser/malformed_alias.sql — duplicate alias with unresolvable collision; expected: structured rejection, not a panic.
  • fixtures/parser/replay_hash_regression.case — archived AST + expected hash pair; expected: hash recomputation matches archive exactly (I2 regression guard).
Pitfalls
  • Alias-collision resolution order depends on AST traversal order, which can vary across parser versions upstream. Manifestation: identical query text hashes differently after an unrelated parser upgrade. Root cause: traversal order was never pinned as part of the canonical form. Debugging: diff the pre-canonicalization AST between versions. Signal: replay_divergence_total (I2) spikes after a deploy. Recovery: pin traversal order explicitly in normalize.rs, independent of parser AST shape.
  • Expression-normalization drift: two semantically-equivalent predicates canonicalize to different forms because the total order over (operator_kind, column_id) is incomplete for a new operator kind added later. Root cause: normalization total order not extended when LogicalOp grows. Debugging: fixtures/parser/replay_hash_regression.case catches this on the next CI run. Signal: two logically-identical queries land in different memo groups later (§14). Recovery: extend the total order, re-derive golden hashes.
  • Replay hash mismatch after a rustc/dependency float-formatting change touches a literal's canonical string form. Manifestation: ExprHash changes for numeric-literal-bearing queries only. Root cause: hashing the literal's display string instead of its canonical binary representation. Debugging: bisect by hashing binary vs. display form. Signal: replay_divergence_total isolated to numeric literals. Recovery: hash canonical binary representation, never a formatted string.

⬜ Phase 2 — Memo Engine & Equivalence Search Substrate §14

Objectives
  • Implement the Cascades-style memo (Graefe 1995, §5 Papers; ADR-09): equivalence-class grouping, rule dispatch, and the search-budget accounting stubbed in Phase 0.
  • Turn the Phase 0 verifier stub into the real I1 (group consistency) enforcement site.
  • Introduce cycle detection so self-referential rewrites cannot corrupt the memo (I1, I9 boundary).
  • Constraint introduced: memo mutation is exclusively through memo crate APIs (P11) — no external crate ever mutates a MemoGroup field directly.
Deliverable

A memoized optimization substrate: Memo::insert deduplicates structurally-identical expressions, Memo::freeze produces an immutable FrozenMemo, and Verifier::check catches every group-consistency violation in the deterministic simulator before it reaches costing.

Acceptance
  • Zero duplicate ExprIds for structurally-identical expressions across 1,000 synthetic inserts (verified by fixtures/memo/bushy_join.memo).
  • fixtures/memo/cyclic_expression.memo is rejected by cycle detection in < 2 ms, never inserted.
  • Memo replay is deterministic: re-running fixtures/memo/replay_memo_regression.memo through Memo::insert in the same order reproduces the identical group/expression id assignment.
  • Verifier::check runs in O(memo size) and completes in < 50 ms at the §4 soft-warning threshold (5,000,000 expressions).
Fixtures
  • fixtures/memo/bushy_join.memo — a bushy 6-relation join memo snapshot; expected: no duplicate expressions, verifier passes.
  • fixtures/memo/cyclic_expression.memo — a rewrite rule that would self-reference; expected: cycle detection rejects before insert.
  • fixtures/memo/malformed_group_ref.memo — an expression referencing a nonexistent GroupId; expected: Verifier::check returns VerifierViolation::DanglingGroupRef.
  • fixtures/memo/replay_memo_regression.memo — archived insert sequence + expected final group count; expected: exact reproduction (I2 applied to memo state, not just IR hashes).
Pitfalls
  • Exponential memo explosion on wide join graphs when pruning is disabled for debugging. Manifestation: memo size crosses the §4 soft-warning threshold within seconds. Root cause: every commutative/ associative join rewrite fires unconditionally without a budget check. Debugging: memo_group_count growth-rate graph. Signal: plan_enumerator_budget_exhausted_total spikes downstream (§18). Recovery: re-enable the search budget (I9) — this pitfall only occurs when it was deliberately disabled.
  • Stale equivalence references after a merge_groups call that doesn't update every expression's group_id field. Root cause: partial union-find update, cheaper to write but incorrect. Debugging: Verifier::check's DanglingGroupRef case (I1). Signal: verifier violation count > 0 immediately after a merge-heavy fixture run. Recovery: union-find must update all member references atomically within the single-writer session, not lazily.
  • Hash-table churn from resizing the interning table during a large batch insert. Root cause: no pre-sizing hint from the caller. Debugging: allocator profiling (heaptrack, §29) shows resize storms. Signal: sqlir_canonicalize_latency_ms p99 outlier correlated with query complexity, not query text. Recovery: pre-size the interning table from the AST's node count estimate.

⬜ Phase 3 — Statistics Infrastructure & Histogram Engine §15

Objectives
  • Build the persisted statistics subsystem: histogram construction, NDV estimation, versioned snapshot publication (I3, I12), and stale-statistics detection.
  • Implement the hybrid histogram model (ADR-08; Poosala et al. 1996, §5 Papers): equi-depth buckets with singleton buckets for detected heavy hitters.
  • Constraint introduced: statistics writes happen out-of-band from any live optimization session (§3.2 persistence-boundary framing) — no session ever triggers a statistics write as a side effect.
Deliverable

A persistent statistics subsystem: HistogramBuilder produces validated hybrid histograms, SnapshotPublisher publishes immutable versioned snapshots idempotently, and stale-snapshot detection raises histogram_refresh_age alerts before cardinality quality degrades silently.

Acceptance
  • Histogram validation passes on fixtures/statistics/skewed_distribution.stats: every bucket's row_count and distinct_count are non-negative and buckets are non-overlapping (100% of buckets).
  • Skew detection identifies all heavy hitters above a 1% frequency threshold in fixtures/statistics/skewed_distribution.stats with zero false negatives.
  • fixtures/statistics/null_heavy.stats (≥ 90% NULL column) produces a valid histogram with an explicit NULL-fraction field, never a divide-by-zero.
  • Snapshot publish latency stays ≤ 10 ms p95 (§4 statistics-fetch budget) for a 50-column table.
Fixtures
  • fixtures/statistics/skewed_distribution.stats — heavy-tailed column distribution; expected: hybrid histogram with correct singleton/equi-depth split.
  • fixtures/statistics/null_heavy.stats — ≥ 90% NULL column; expected: valid histogram, explicit NULL-fraction, no divide-by-zero.
  • fixtures/statistics/malformed_histogram.stats — overlapping bucket bounds; expected: rejected at validation, quarantined (not published).
  • fixtures/statistics/stale_snapshot_regression.stats — a snapshot aged past the alert threshold; expected: histogram_refresh_age alert fires, snapshot still usable (I3 tolerates staleness).
Pitfalls
  • Histogram drift: bucket boundaries computed from a sample taken before a bulk data load no longer reflect the true distribution. Manifestation: cardinality estimates (§16) systematically miss after a bulk load. Root cause: no automatic re-histogram trigger tied to write volume. Debugging: compare histogram_refresh_age against known load-job timestamps. Signal: q-error spike correlated with a load-job completion event. Recovery: trigger re-histogramming on a write-volume threshold, not only on a fixed schedule.
  • Stale NDV estimates after a column's distinct-value count changes sharply (e.g., a dimension table truncate-and-reload). Root cause: NDV sketch not invalidated on truncate. Debugging: compare NDV sketch's internal cardinality against a fresh COUNT(DISTINCT) sample. Signal: join-selectivity estimates (§16) diverge specifically for the truncated table's join keys. Recovery: invalidate NDV sketches explicitly on any truncate/reload event, not only on incremental updates.

⬜ Phase 4 — Cardinality Estimation Engine §16

Objectives
  • Build the row-count estimation engine: filter selectivity, join selectivity, multi-column correlation heuristics, and uncertainty propagation (I4).
  • Integrate runtime feedback (RuntimeFeedbackRecord, §11) so cardinality estimates improve across repeated executions of structurally similar queries (Stillger et al. 2001 LEO, §5 Papers).
  • Adopt the q-error methodology (Leis et al. 2015, §5 Papers) as the acceptance metric, not raw absolute error — q-error is scale-invariant and catches both over- and under-estimation symmetrically.
Deliverable

A working cardinality engine: every MemoGroup carries a CardinalityEstimate with an explicit confidence/uncertainty tag, computed deterministically from the pinned statistics snapshot, and improvable over time via ingested runtime feedback.

Acceptance
  • Median q-error ≤ 2.0 and p95 q-error ≤ 10.0 across the TPC-H Q1–Q22 calibration suite (benchmark-harness::runner, TPC-H scale factor 10).
  • fixtures/cardinality/correlated_columns.case triggers the correlation-heuristic path (not plain independence) whenever multi-column statistics exist for the predicate's columns.
  • fixtures/cardinality/skewed_joins.case produces an estimate within 5x of the runtime-observed row count (skew-tolerant bound, looser than the median target above).
  • I4 monotonicity holds on 100% of fixtures/cardinality/* — no post-filter estimate exceeds its source row count without an explicit Uncertain tag.
Fixtures
  • fixtures/cardinality/correlated_columns.case — two correlated filter columns; expected: correlation heuristic overrides independence assumption.
  • fixtures/cardinality/skewed_joins.case — join on a heavy-hitter key; expected: hybrid-histogram singleton bucket drives the estimate, not the equi-depth average.
  • fixtures/cardinality/malformed_feedback.case — a FeedbackMessage with actual_rows unset; expected: rejected by FeedbackIngestor, not silently defaulted to zero.
  • fixtures/cardinality/qerror_regression.case — archived query + expected q-error bound; expected: re-run stays within the archived bound (regression guard against estimator drift).
Pitfalls
  • Independence-assumption failures on correlated columns produce order-of-magnitude cardinality misses even with perfectly accurate single-column histograms. Manifestation: a filter on two correlated columns estimates far fewer rows than actually pass. Root cause: multiplying single-column selectivities assumes independence that does not hold. Debugging: compare estimated vs. runtime-fed actual rows via cardinality_qerror. Signal: q-error outliers cluster on a specific column pair. Recovery: build or consult multi-column statistics for that pair (§16.2 correlation heuristic).
  • Repeated histogram scans for multi-predicate filters recompute the same bucket lookup redundantly. Root cause: no per-request memoization of intermediate selectivity lookups. Debugging: flamegraph shows histogram::lookup as a hot path disproportionate to predicate count. Signal: p95 optimization latency (§4) creeps up specifically on multi-predicate queries. Recovery: memoize bucket lookups within a single estimation call.

⬜ Phase 5 — Cost Model Framework §17

Objectives
  • Implement the pluggable, component-wise cost framework (CostVector, §11.2): CPU, IO, memory, network, and spill sub-models, each independently calibratable (P7).
  • Integrate vectorization-aware CPU costing (Neumann 2011, §5 Papers) so batch-oriented execution is not costed as if it were tuple-at-a-time.
  • Constraint introduced: every cost component must be non-negative (I5) and no component may be double-counted across sibling subtrees (§17.6 pitfall) — cost composition is strictly additive, never re-derived from a different component.
Deliverable

A composable cost engine: every physical candidate carries a five-component CostVector, summed component-wise up the plan tree without double-counting, consumable by plan-enumerator's dominance check (§18) and fully explainable component-by-component (P7).

Acceptance
  • Deterministic cost replay: identical (memo shape, cardinality, calibration profile) inputs produce byte-identical CostVectors across 10 consecutive runs.
  • Zero cost_model_negative_component_total increments across the full fixtures/cost/* suite (I5).
  • fixtures/cost/spill_heavy.plan cost estimate is within 20% of the benchmark-harness calibration ground truth for disk amplification + serialization overhead.
  • fixtures/cost/distributed_exchange.plan network cost falls within the §4 intra-AZ/inter-AZ RTT bounds for the fixture's declared topology.
Fixtures
  • fixtures/cost/spill_heavy.plan — a plan forcing a hash-join spill; expected: spill cost includes all three I6 terms, none defaulted to zero.
  • fixtures/cost/distributed_exchange.plan — a plan with a cross-node exchange; expected: network cost scales with the fixture's declared RTT.
  • fixtures/cost/malformed_cost_vector.plan — a candidate with a negative IO cost injected; expected: rejected at construction (I5), never reaches plan-enumerator.
  • fixtures/cost/double_counted_network_regression.plan — a nested-exchange plan previously known to double-count network cost; expected: single-counted total matches the archived correct value.
Pitfalls
  • Double-counted network penalties when a nested exchange's parent operator re-applies a network cost already charged by the child exchange. Manifestation: total plan cost for multi-exchange distributed plans is implausibly high relative to single-exchange plans of similar shape. Root cause: network cost attached at both the Exchange operator and its consuming parent instead of only the operator that performs the transfer. Debugging: fixtures/cost/double_counted_network_regression.plan. Signal: distributed plans are systematically de-prioritized versus single-node plans beyond what their real cost justifies. Recovery: network cost is charged exactly once, at the Exchange node.
  • Recursive cost recomputation when a shared subtree (memo group reused by multiple parents) is costed independently per parent instead of once per group. Root cause: costing implemented as a naive recursive walk over the logical tree rather than the memo's group structure. Debugging: profile cost_model_negative_component_total-adjacent call counts — cost calls should equal group count, not parent-edge count. Signal: p95 optimization latency (§4) grows superlinearly with join count. Recovery: cost per group once, cache the result, reuse across parents (mirrors memo's own deduplication, §14).

⬜ Phase 6 — Join Enumeration & Plan Search §18

Objectives
  • Implement the join-order search: left-deep and bushy dynamic-programming enumeration, pruning heuristics, and branch-and-bound elimination (anchor: Selinger et al. 1979; Graefe & McKenna 1993, §5 Papers).
  • Bound search explosion (P10, I9): the search must terminate inside its time/expression budget on every input, including adversarial join graphs, falling back to a heuristic plan rather than blocking indefinitely.
  • Constraint introduced: disconnected join components are forbidden unless an explicit cross join node represents the gap (I7) — the enumerator never silently treats a disconnected graph as fully joined.
Deliverable

A search-capable optimizer: DpSearch::enumerate returns a deterministic best-plan candidate set for join graphs up to the configured threshold via exact DP, and a bounded heuristic fallback beyond it, always terminating inside the §4 latency budget.

Acceptance
  • Deterministic best-plan selection: fixtures/join/10way_join.plan selects the identical join order across 10 repeated runs (P1).
  • TPC-H plan stability: join order for TPC-H Q5, Q8, Q9 (the classic wide-join queries) matches the benchmark-harness golden plan across 3 consecutive calibration runs.
  • fixtures/join/factorial_explosion_regression.plan (14-relation adversarial join graph) completes enumeration within the §4 p99 budget (≤ 1,500 ms) via the GEQO-style fallback, not exact DP.
  • fixtures/join/cross_join.plan (intentionally disconnected graph with an explicit cross join) is accepted; any disconnected graph lacking the explicit node is rejected (I7).
Fixtures
  • fixtures/join/10way_join.plan — a 10-relation join graph; expected: deterministic bushy-tree selection.
  • fixtures/join/cross_join.plan — explicit cross join over two otherwise-disconnected subgraphs; expected: accepted, I7 satisfied.
  • fixtures/join/cyclic_join_graph.plan — a join graph with a predicate cycle (self-join style); expected: DP search handles the cycle without infinite subset expansion.
  • fixtures/join/factorial_explosion_regression.plan — 14-relation adversarial graph; expected: budget-bounded fallback fires, total latency stays under the §4 p99 ceiling.
Pitfalls
  • Factorial search explosion when bushy enumeration is attempted without a join-count threshold for the GEQO-style fallback. Manifestation: enumeration time grows factorially past ~12 relations. Root cause: exact DP over all bushy partitions is exponential in relation count. Debugging: plan_enumerator_budget_exhausted_total spikes on wide-join workloads. Signal: p99 latency (§4) breached specifically on queries with join count above the threshold. Recovery: enforce the GEQO- style fallback threshold (§18.2) unconditionally — never allow exact DP unbounded.
  • Memo contention when parallel exploration workers (§18.2) all attempt to insert candidates into the same memo groups without coordination. Manifestation: memo_verifier_violations_total (I1) rises under parallel search. Root cause: workers compute candidates in parallel but insert must remain single-writer (P11) — a naive implementation lets workers insert directly. Debugging: reproduce with worker count forced to 1 versus > 1. Signal: violation only under concurrency. Recovery: workers return candidates to a single collector thread that performs all memo inserts.

⬜ Phase 7 — Physical Operator Selection & Plan Generation §19

Objectives
  • Select concrete physical operators (hash join, merge join, nested-loop join, index/table scan) from cost vectors and generate a stable, execution-engine-consumable operator tree (§3.2 protocol boundary).
  • Integrate spill-risk margin into operator selection so a marginally-cheaper hash join is not chosen when its spill risk (§17.6) is materially higher than a merge join's.
  • Constraint introduced: the physical plan generator never mutates the frozen memo (§14.3) — it is a pure read projection, matching explain's read-only contract (§3.2).
Deliverable

Physical plan generation: a stable PhysicalPlanTree selecting concrete operators for every memo group, with every join-operator choice traceable to the cost vectors and spill-risk margin that justified it.

Acceptance
  • Operator compatibility checks pass 100% of fixtures/physical/*: every selected operator's required physical properties (sort order, partitioning) are satisfied by its children, verified structurally.
  • fixtures/physical/merge_join_sorted.plan selects merge join only when both inputs are pre-sorted on the join key at zero additional sort cost — otherwise hash join must win on cost.
  • fixtures/physical/tiny_dimension_table.plan (a < 1,000-row dimension table) selects nested-loop join, not hash join, when the cost model shows nested-loop cheaper below that row-count threshold.
  • Invalid operator trees (a selected operator whose required properties are unmet) are rejected before reaching the execution-engine handoff — zero occurrences across the fixture suite.
Fixtures
  • fixtures/physical/merge_join_sorted.plan — both join inputs pre-sorted; expected: merge join selected over hash join.
  • fixtures/physical/tiny_dimension_table.plan — small dimension table join; expected: nested-loop join selected, spill-risk margin irrelevant at this size.
  • fixtures/physical/malformed_operator_tree.plan — a hand-crafted tree with unmet sort-order requirements; expected: rejected by the operator-compatibility check.
  • fixtures/physical/spill_underestimate_regression.plan — a case previously known to underestimate hash-join spill risk; expected: merge join now wins per the corrected margin.
Pitfalls
  • Underestimating spill risk when the hash-join cost model's memory-pressure term does not account for concurrent queries sharing the same memory budget. Manifestation: hash join selected, then spills unexpectedly at runtime under concurrent load. Root cause: spill-risk margin computed against a single-query memory budget, not the §4 concurrency assumption (500/50 queries per sec). Debugging: fixtures/physical/spill_underestimate_regression.plan plus runtime spill_bytes feedback (§16). Signal: runtime feedback shows spill on plans the optimizer rated spill-free. Recovery: derate the per-query memory budget by the expected concurrent-query count before computing spill-risk margin.
  • Branch-heavy costing logic (many nested if/else-equivalent cost-selection branches across operator kinds) becomes a maintenance and correctness risk as operator variety grows. Root cause: ad hoc operator-selection logic added incrementally without a shared dominance-check abstraction. Debugging: code review against the Pruning::dominates (§18.2) abstraction — selection should reuse it, not reimplement comparison per operator pair. Signal: two operator kinds compared inconsistently (A beats B, B beats A, on the same inputs) — a correctness bug, not just a style issue. Recovery: route every operator-selection decision through one shared dominance-check function.

⬜ Phase 8 — Explainability, Tracing & Deterministic Replay §20

Objectives
  • Implement structured explain output exposing every pruning decision and cost breakdown (P3, P7) without re-running optimization.
  • Implement the append-only replay archive (replay-engine, I10) and deterministic trace IDs (ADR-20) so any past optimization decision is byte-reproducible.
  • Constraint introduced: explain and replay-engine are strictly read/append, never mutating optimizer state — a bug in either can never corrupt a live session (§3.2).
Deliverable

Replayable optimizer traces: explain renders every pruning decision and cost component for any completed optimization without re-running it, and replay-engine makes any archived decision byte-reproducible from its ReplayTraceRecord.

Acceptance
  • Replay determinism validation: re-executing fixtures/replay/replay_regression.trace's input through the full pipeline reproduces a byte-identical ReplayTraceRecord (I2, I10) in 100% of runs.
  • Explain generation latency stays ≤ 50 ms p95 (§4) for a 10-way-join ExplainTrace.
  • Zero replay_archive_illegal_write_total increments across the fixtures/replay/* suite (I10).
  • fixtures/replay/partial_telemetry.trace (missing phase_spans for one phase) still renders a complete explain output with the missing phase marked explicitly, never omitted silently.
Fixtures
  • fixtures/replay/replay_regression.trace — a full archived optimization trace; expected: byte-identical replay.
  • fixtures/replay/nondeterministic_timestamp.trace — a trace with a wall-clock-derived trace ID (a deliberately introduced regression case); expected: rejected at ingestion, since trace IDs must derive from UUIDv7 session seeding, not ambient wall-clock reads.
  • fixtures/replay/malformed_trace.trace — a trace record with a missing plan_hash; expected: ReplayArchive::append rejects it structurally.
  • fixtures/replay/partial_telemetry.trace — one phase's spans missing; expected: explain still renders, missing phase flagged.
Pitfalls
  • Nondeterministic timestamps leaking into trace-ID generation break I2/I10's replay guarantee. Manifestation: two replays of the identical archived input produce different trace IDs (though the same plan). Root cause: trace-ID seeding accidentally reads ambient wall-clock time instead of the session's fixed start time. Debugging: fixtures/replay/nondeterministic_timestamp.trace. Signal: replay_divergence_total (I2) counts trace-ID mismatches specifically, not plan-hash mismatches. Recovery: seed trace-ID generation exclusively from the session's recorded start time, never from a fresh clock read during replay.
  • Oversized trace payloads when pruned_candidates (§11 ExplainTrace) captures every dominated candidate on a wide join graph without a cap. Manifestation: ReplayTraceRecords for wide joins approach the §4 storage-amplification ceiling on their own. Root cause: no cap on pruned-candidate capture count. Debugging: archive size distribution by join-graph width. Signal: storage growth rate correlates with join complexity, not query volume. Recovery: cap captured pruned-candidate detail at a configurable depth, retaining aggregate counts beyond the cap (still satisfies P3's "inspectable," loses only per-candidate granularity beyond the cap).

⬜ Phase 9 — Distributed Costing & Runtime Calibration §21

Objectives
  • Model distributed execution cost: exchange operator costing, repartition penalties, skew-aware shuffle cost, and topology-aware latency penalties (§4 network RTT budgets).
  • Close the calibration feedback loop: ingest runtime telemetry, fit cost coefficients, detect drift, and support safe rollback (I11) — the LEO-style closed loop (Stillger et al. 2001, §5 Papers).
  • Constraint introduced: calibration coefficient publication happens strictly between optimization requests, never mid-session (§11 CalibrationProfile concurrency note) — a session's cost model is fixed for its entire lifetime, matching I3's statistics-snapshot pinning.
Deliverable

A distributed-aware, self-calibrating optimizer: exchange and repartition costs are modeled against real cluster topology and calibrated against runtime feedback, with drift detection and safe, version-monotonic rollback (I11) when a calibration regresses plan quality.

Fixtures

  • fixtures/calibration/overfitting_regression.parquet — single-workload feedback only; expected: rejected by the minimum-diversity check, not silently fit.
Pitfalls
  • Underestimating shuffle amplification when skew detection (§15 heavy-hitter tracking) is not consulted during exchange costing, defaulting to uniform distribution. Manifestation: a skewed shuffle key spills one partition while the cost model predicted balance. Root cause: exchange_cost ignores the shuffle key's existing histogram heavy-hitter data. Debugging: fixtures/distributed/skew_repartition_regression.plan + runtime spill_bytes. Signal: skewed-key distributed plans underperform their estimate specifically. Recovery: exchange_cost must consult §15.2's heavy-hitter data, never assume uniformity.
  • Overfitting workloads when CalibrationFitter::fit runs against a feedback sample dominated by one query shape. Manifestation: OLTP accuracy improves while analytical-join accuracy degrades. Root cause: no diversity check pre-fit. Debugging: fixtures/calibration/overfitting_regression.parquet. Signal: cost-anomaly rate rises for analytical queries right after a publish. Recovery: enforce a minimum query-shape diversity threshold before fit accepts a sample.
