33. Hard Questions (Self-Examination)

  • Q1. If the memo hard cap (§4, I8) is hit mid-optimization, does the system return the best plan found so far or fail outright, consistent with §18's "always terminate" guarantee (I9)?
  • Q2. How does the independence-assumption failure (§16) interact with the correlation heuristic's own confidence — can a low-confidence correlation estimate be silently preferred over a high-confidence independence estimate (§7 I4)?
  • Q3. When explain (§20) shows a pruned candidate's cost, is it computed with the same CalibrationProfile version as the winner, across a mid-fleet calibration rollout (§21)?
  • Q4. §17's double-counted-network pitfall and §21's skew-underestimation pitfall both live in Exchange costing — could one structural fix eliminate both classes at once?
  • Q5. §4 sets optimizer-service availability (99.95%) tighter than statistics availability (99.9%, MM6, §30) — does a prolonged statistics degraded-mode window risk a stale §21 calibration publish decision?
  • Q6. The §18 GEQO-style fallback trades optimality for termination — how is "the fallback rate is too high" distinguished operationally (§29) from "the join-count threshold was too conservative," given both emit the same counter (I9)?
  • Q7. §17's cost model and §16's cardinality engine are pure functions of the pinned snapshot (I3) — but §21's coefficients change between sessions; can a long-lived client observe two CalibrationProfile versions in a way that looks like a P1 violation even though I11 holds?
  • Q8. §14's cycle-detection walk is bounded by depth, not memo size (I1) — for an adversarial deep-but-narrow rewrite chain, does this bound hold, or degrade toward the §18 memo-size bound?
  • Q9. §19's spill-risk margin is derated by expected concurrency (§4's 500/50 per-sec figures) — does §29's autoscaling recompute that derating, or does it drift stale against §29's scaling reality?
  • Q10. §20's pruned_candidates capture-depth cap bounds trace size — does it ever hide the alternative an operator needs for a §33 Q3-style investigation, and is the §23 FM-3 aggregate fallback sufficient?
  • Q11. §21's DriftDetector flags a > 25% coefficient divergence (I11) — is that threshold derived from §4 anywhere, or should it scale with §32 C11's batch-size-derived confidence interval?
  • Q12. §18's parallel workers return candidates to a single collector thread (P11) — is the §29 "distributed search fanout" bottleneck actually in plan-enumerator (§18) or in memo's single-writer discipline (§14)?
  • Q13. §25 allows CostVector/CalibrationProfile to grow fields additively — at what field count does that growth threaten §32 C2's per-expression memory derivation (§11)?
  • Q14. §22 T9 delegates exchange transport security to the execution engine — does §21's exchange-cost model assume a payload size that a transport change would silently violate, undetected by §21's calibration-accuracy target?
  • Q15. §15's histogram-drift and §16's independence-assumption pitfalls produce the same q-error-spike symptom (§23 FM-2) — what §20 explain evidence actually distinguishes them today?
  • Q16. §30 MM5 frames the search budget (I9) as a correctness boundary — is there an invariant in §7 the §18 fallback path is exempted from that the exact-DP path is not?
  • Q17. §32 C6 sizes the §19 worker-pool lane from p99 latency and throughput — does that sizing account for the §18 collector-thread serialization overhead, or assume unachievable perfectly parallel throughput?
  • Q18. §9 ADR-11 keeps Criterion under benchmark-harness alongside §26's differential testing — does §23's failure-mode table have a class for a simultaneous performance-and-correctness divergence from one root-cause commit?
  • Q19. §35's deferred learned-cardinality-estimator anchors to §16 — would it replace the §16 Estimator entirely or run as a second opinion, and does §11's CardinalityEstimate shape allow that without an additive-only §25 change?
  • Q20. §21's topology-mismatch handling refreshes ClusterTopology at the next session — but §3's OptimizerSession pins inputs for its whole lifetime (I3); what is the worst-case staleness window for a single long-running session's distributed cost estimate (§29)?

30. Mental Models & First Principles

  • MM1 — Memoization turns exponential into polynomial-bounded. Compressed insight: deduplicating structurally-identical subplans (Cascades, §5) converts an exponential enumeration into one bounded by memo size, not join-order permutation count. Predicts: search cost scales with distinct subplan shapes, not with n!. Bug class without it: reimplementing join search as a flat permutation loop that silently explodes past ~10 relations. Applies in §14 and §18.
  • MM2 — Cost is additive, never re-derived. Compressed insight: a CostVector's components sum strictly up the plan tree (I5, P7); any place a component is recomputed from another component instead of propagated is a double-counting bug waiting to happen. Predicts: any "cost looks too high for multi-exchange plans" report is a double-counting bug, not a calibration bug. Bug class without it: the exact §17.6 double-counted-network pitfall. Applies in §17.
  • MM3 — Cardinality error compounds multiplicatively up a join tree. Compressed insight: a 2x per-predicate cardinality miss on a 5-join query can compound to a 32x miss at the root under independence-assumption chaining. Predicts: q-error grows with join depth even when every individual histogram is locally accurate. Bug class without it: blaming a single "bad histogram" for a plan regression that is actually compounding error. Applies in §16.
  • MM4 — Determinism is a precondition for observability, not a nice-to-have. Compressed insight: you cannot debug what you cannot replay (P1, P8); every debugging tool downstream (explain, replay-engine) assumes byte-identical replay is possible. Predicts: any nondeterminism bug (a timestamp leak, an unpinned iteration order) manifests first as "unreproducible" bug reports, not as a crash. Bug class without it: the §13.6/§20.6 hash-instability and trace-ID pitfalls. Applies in §13 and §20.
  • MM5 — A search budget is a correctness boundary, not a performance nicety. Compressed insight: without I9's hard termination guarantee, "slow" and "hung forever" are the same failure mode under an adversarial join graph. Predicts: any latency SLO (§4 p99) is actually an availability SLO once an adversarial or merely very-wide query is possible. Bug class without it: an unbounded DP search taken down by a single 20-way-join query. Applies in §18.
  • MM6 — Staleness is safer than absence for pinned state. Compressed insight: I3's snapshot pinning means a session with slightly-stale statistics is always preferable to a session that blocks waiting for the newest write. Predicts: statistics availability (§4, 99.9%) can be looser than optimizer availability (99.95%) precisely because stale-but-available is an acceptable degraded mode. Bug class without it: over-engineering a statistics-freshness barrier that hurts availability for no cardinality benefit. Applies in §15.
  • MM7 — Calibration must be more diverse than any single workload it is fit against. Compressed insight: a coefficient fit is only as general as its input diversity (I11, §21.6); fitting against one workload optimizes that workload at other workloads' expense. Predicts: an isolated calibration improvement for one query shape, paired with a regression elsewhere, is overfitting, not a fitting bug. Bug class without it: shipping a calibration profile validated only against the workload that triggered the recalibration request. Applies in §21.
  • MM8 — Every pruned alternative is a future debugging question. Compressed insight: P3's observability-first principle means a pruning decision not captured today is an unanswerable "why didn't it pick X" question tomorrow. Predicts: explain output quality directly determines mean time-to-diagnosis for every future plan-regression incident. Bug class without it: capturing only the winning plan and discovering, mid-incident, that the rejected alternative's cost was never recorded. Applies in §20.

5. Required Reading

Books

  • Database System Concepts — Silberschatz, Korth & Sudarshan (7th ed., 2019), ch. 15–16 (query optimization) and ch. 11–14 (indexing, storage): canonical selectivity and cost-formula vocabulary; applied in §16 and §17.
  • Readings in Database Systems — Hellerstein & Stonebraker (eds.), 4th ed. (2005): reprints the Selinger, Volcano, and Cascades papers with retrospective commentary on their tradeoffs; applied in §14 and §18.
  • Designing Data-Intensive Applications — Kleppmann (2017), ch. 5–7 and ch. 12: distributed-execution tradeoff framing reused for exchange-cost modeling; applied in §21.
  • Database Internals — Petrov (2019), part II (distributed systems) and part I ch. 4–6 (storage engines): grounding for statistics persistence and cross-shard cost accounting; applied in §15 and §21.
  • Computer Architecture: A Quantitative Approach — Hennessy & Patterson (6th ed., 2017), ch. 2 and appendix B: cache-line-aware CPU costing basis; applied in §17.
  • The Art of Computer Programming, Vol. 3: Sorting and Searching — Knuth (2nd ed., 1998), ch. 5.4: external-sorting cost model, direct ancestor of merge-join and spill cost derivation; applied in §19.
  • Transaction Processing: Concepts and Techniques — Gray & Reuter (1992), ch. 13: query-processing spill and materialization cost accounting lineage; applied in §19.

Papers

  • "Access Path Selection in a Relational Database Management System" — Selinger et al., 1979, SIGMOD: founding cost-based join-order selection and access-path costing → direct ancestor of §18 DP search and §17 cost equations; applied in §18.
  • "The Volcano Optimizer Generator: Extensibility and Efficient Search" — Graefe & McKenna, 1993, ICDE: rule-driven extensible search framework → basis for plan-enumerator rule dispatch; applied in §14.
  • "The Cascades Framework for Query Optimization" — Graefe, 1995, IEEE Data Eng. Bull.: top-down memoized search with physical-property enforcement → direct basis for the memo crate; applied in §14.
  • "How Good Are Query Optimizers, Really?" — Leis et al., 2015, VLDB: q-error methodology and cardinality-estimation failure taxonomy → basis for §16 acceptance criteria and §21 calibration metrics; applied in §16.
  • "Efficiently Compiling Efficient Query Plans for Modern Hardware" — Neumann, 2011, VLDB: vectorized/compiled execution's cost implications → basis for the vectorization coefficients in the cost model; applied in §17.
  • "An Overview of Query Optimization in Relational Systems" — Chaudhuri, 1998, PODS: survey framing of the search-space / cost-model separation → basis for the §3 architecture split; applied in §3.
  • "Improved Histograms for Selectivity Estimation of Range Predicates" — Poosala, Ioannidis, Haas & Shekita, 1996, SIGMOD: equi-depth and skew-aware histogram construction → direct basis for statistics::histogram; applied in §15.
  • "Eddies: Continuously Adaptive Query Processing" — Avnur & Hellerstein, 2000, SIGMOD: adaptive runtime routing as an alternative to static cost-based plan selection → informs the Alt D rejection; applied in §34.
  • "LEO — DB2's LEarning Optimizer" — Stillger, Lohman, Markl & Kandil, 2001, VLDB: runtime-feedback-driven cardinality correction → direct basis for the calibration crate feedback loop; applied in §21.

Reference Implementations

  • postgres/postgres — study src/backend/optimizer/: mature heuristic-pruned Cascades-adjacent planner with GEQO fallback above the join-count threshold; pitfall: do not copy its ad hoc selectivity fallback constants uncritically; applied in §18.
  • duckdb/duckdb — study src/optimizer/: vectorized-execution-aware cost integration inside a single-node columnar engine; pitfall: do not copy its single-node-only exchange-cost omission; applied in §17.
  • apache/calcite — study core/src/main/java/org/apache/calcite/plan/volcano/: extensible rule-and-memo planner (VolcanoPlanner) with pluggable cost models; pitfall: do not copy its unbounded rule-firing loop absent a search budget; applied in §14.
  • cockroachdb/cockroach — study pkg/sql/opt/: memo normalization rules and distributed exchange-cost placement inside a real MPP planner; pitfall: do not copy its early cost model's lack of calibration feedback; applied in §21.
  • pingcap/tidb — study planner/core/: distributed cost estimation with network-aware physical-property enforcement; pitfall: do not copy its coupling of statistics-staleness handling into the planner itself; applied in §21.
  • facebookincubator/velox — study velox/core/: vectorized operator cost modeling inside a standalone execution library; pitfall: do not copy its execution-engine coupling — this blueprint keeps costing execution-engine-agnostic; applied in §17.

Glossary (§36) · 41 terms · site-wide glossary

Access Path
the chosen strategy (table scan, index scan) for retrieving a base relation's rows.
ADR
Architectural Decision Record; a locked technology/design choice with a named rejected alternative and the regime where that alternative would win (§9).
Bushy Join
a join tree that is not left-deep; both children of an internal join node may themselves be joins.
Calibration
the process of fitting cost-model coefficients against observed runtime feedback.
Cardinality
the estimated (or actual) row count produced by a relational operator.
Cascades
the top-down, memoized, rule-driven query-optimization framework (Graefe 1995) this blueprint's memo crate is architecturally descended from.
CostVector
the five-component (CPU, IO, memory, network, spill) cost estimate attached to a physical candidate (§11.2).
Cost-Based Optimization
selecting among semantically-equivalent plans by estimated execution cost rather than by fixed heuristic rules alone.
Deferred Feature
a capability intentionally excluded from the current build, registered in §35 with an explicit un-defer trigger.
Determinism
the property that identical inputs produce byte-identical outputs (P1); the precondition for replay (P8).
Eddies
an adaptive, per-tuple-batch routing query-processing architecture (Avnur & Hellerstein 2000) that forgoes a fixed static plan (§34 Alt D).
Equi-Depth Histogram
a histogram whose buckets each cover approximately equal row counts.
Exchange
the distributed data-movement operator that redistributes rows across nodes.
Explain
the subsystem exposing optimizer reasoning, cost breakdowns, and pruning rationale without re-running optimization (§20).
Expression Interning
deduplicating structurally-identical expressions into a single canonical ExprId.
GEQO
Genetic Query Optimizer; PostgreSQL's evolutionary-search fallback for wide joins (§18.2, §34 Alt B).
Heavy Hitter
a value in a column's distribution occurring frequently enough to warrant its own singleton histogram bucket rather than being averaged into an equi-depth bucket.
Histogram
a statistical summary of a column's value distribution used for selectivity estimation.
Independence Assumption
the (often false) assumption that two predicates' selectivities multiply independently; a major cardinality-estimation failure mode (§16.6).
Join Graph
the graph whose nodes are relations and whose edges are join predicates.
Materialized (memo state)
the terminal memo-group state after a winning candidate has been selected and the group frozen (§8.2).
Memo
the equivalence-class data structure storing all logical and physical alternatives considered during optimization (§14).
NDV
Number of Distinct Values; an estimate of a column's cardinality of unique values.
Physical Property
a characteristic (sort order, partitioning) a physical operator produces or requires, enforced top-down in a Cascades-style memo (ADR-09).
Plan Enumeration
the search process generating and costing candidate physical plans.
Plan Hash
the deterministic identity of a selected plan, used for replay comparison (I2).
Pruning
eliminating a dominated (strictly worse, same physical properties) candidate from further consideration (§8.2).
q-error
the ratio between an estimated and an actual cardinality, taken in whichever direction exceeds 1 (Leis et al. 2015); the scale-invariant accuracy metric used throughout this blueprint.
Replay
the deterministic reproduction of a past optimization decision from an archived trace.
Replay Trace
the persisted, append-only record of one optimization's full decision history (§8.4, I10).
Runtime Feedback
observed execution telemetry (actual rows, runtime, spill bytes) fed back into cardinality and calibration (§16, §21).
Search Budget
the bounded time/expression allotment a search must terminate within (I9).
Selectivity
the fraction of rows passing a predicate.
Singleton Bucket
a histogram bucket covering exactly one distinct value, used for heavy hitters.
Skew
a non-uniform value distribution where some values occur far more frequently than others.
Snapshot (statistics)
an immutable, versioned view of statistics pinned for a session's lifetime (I3).
Spill
materializing intermediate data to disk when it exceeds an in-memory budget.
Spill Penalty
the additional cost (disk amplification, serialization, repartition) from a spill (I6).
Top-K Frequency
tracking the K most frequent values in a column for heavy-hitter detection.
Vectorized Execution
a batch-oriented (rather than tuple-at-a-time) execution model whose cost profile this blueprint's CPU cost sub-model accounts for explicitly (Neumann 2011, §5).
Volcano
the bottom-up, rule-driven, extensible query-optimization framework (Graefe & McKenna 1993) that Cascades generalized.
