Project Number: 419

Project Name: Map / Road-Network Routing Engine from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch, a continental-scale road-network shortest-path routing engine: ingest a road graph, preprocess it, and answer point-to-point, one-to-many, and isochrone queries in sub-millisecond time at country/continent scale. Correctness-first, observability-second, maintainability-third, performance-fourth — speedup techniques never trade exactness for speed.

Core capability surface:

  • Graph core — directed weighted graph; node = intersection, edge = road segment weighted by travel-time or distance; CSR (compressed sparse row) forward + reverse adjacency; node-based and edge-based (edge-expanded) representations.
  • OSM ingest — parse OSM PBF (protobuf blocks: nodes/dense-nodes/ways/relations); filter highway=*; honor oneway; extract turn-restriction relations; apply a speed/access profile.
  • Dijkstra — label-setting; 4-ary heap; predecessor-array path extraction; the exact correctness oracle for every later technique (PR1).
  • Bidirectional Dijkstra — forward on G + backward on G_rev; correct meeting/stopping criterion.
  • A* — admissible + consistent heuristic (PR2); Haversine great-circle lower bound; reduced-cost reformulation; bidirectional A* with symmetric potentials.
  • ALT — A*, Landmarks, Triangle inequality (PR3); landmark selection (avoid / farthest / planar); precomputed landmark distance tables; tight admissible lower bounds.
  • Contraction Hierarchies (CH) — node ordering by importance; node contraction with witness search (PR4); shortcut insertion; bidirectional up-graph query with stall-on-demand; shortcut unpacking.
  • CRP (Customizable Route Planning) — metric-independent multilevel partition (PR5); one-time topology preprocessing; fast customization (seconds) for live traffic; multilevel overlay query.
  • Turn restrictions / costs — no-left-turn, U-turn penalty, via-node restrictions; edge-expanded graph and turn tables; CH on the edge-expanded graph.
  • Time-dependent routing — piecewise-linear travel-time functions with the FIFO property (PR8); TD-Dijkstra; time-dependent CH (TCH) (PR7); earliest-arrival and profile queries.
  • Isochrones / batched — one-to-many / one-to-all; PHAST / RPHAST (PR9); isochrone polygonization (GeoJSON); many-to-many distance matrices (PR10).
  • Alternatives — penalty, plateau, via-node admissible alternatives (PR11).

Arc-flags region-based pruning (PR6, PR15) and full Hub Labeling (PR13) are studied and compared but not built in this blueprint — both are covered as fully-worked alternatives in Alternative Architectures (Roads Not Taken), not as Phase-0 deliverables.

Boundaries: a library (linkable crate) + a route CLI + an optional routed HTTP service (OSRM/GraphHopper-shaped JSON). It is a routing engine, not a map application.

Explicit non-goals:

  • NOT a map renderer / tile server — no raster/vector tiles, no styling; geometry is emitted as coordinate lists / GeoJSON only.
  • NOT a geocoder / address search — input is NodeId or (lat,lon) snapped to the nearest edge; forward/reverse geocoding is a separate project.
  • NOT map-matching (GPS trace → road sequence) — PhaseDeferred("§1. Goal & Scope"); see Deferred Features Register.
  • NOT transit / multimodal routing — GTFS / RAPTOR / CSA are out of scope; GTFS noted as a format only, never ingested.
  • NOT traffic prediction — live traffic is a consumed input metric (CRP customization), never an ML forecasting model.
  • NOT continuous-space motion planning — #287 (Robotics Motion Planner) covers configuration-space sampling/optimization. This project is discrete road-GRAPH routing; the two are kept strictly distinct (see §2 cross-links). No RRT, no PRM, no trajectory optimization here.
  • NOT turn-by-turn voice/visual guidance — path + maneuver list is emitted; narration is a downstream concern.

Deployment model:

  • A no_std-friendly algorithms core (CSR, Dijkstra, A*, CH/CRP query) — zero allocation on the hot query path, usable embedded/WASM.
  • A std ingest + preprocess stage (PBF parse, CH/CRP build) — multi-threaded (rayon), offline, produces a versioned binary routing index.
  • A CLI (route) — build index, query, isochrone, matrix, differential-validate.
  • An optional HTTP service (routed) — loads a memory-mapped index, serves concurrent read-only queries.

Target users: navigation/logistics backend engineers; researchers comparing speedup techniques; anyone needing a trustworthy, exact routing substrate rather than an opaque hosted API.

Rust chosen: cache-friendly CSR with full layout control, performance parity with C++, memory safety on adversarial OSM parsing and on multi-gigabyte index arrays, and fearless data-parallel preprocessing via rayon. The Rust Fast Paths crate (R6) is a canonical CH reference. C++ (RoutingKit R2 / OSRM R1) is the performance peer but carries the UB/bounds-error class on raw pointer arithmetic over giant arrays. Go/JVM are rejected because GC pauses destroy the tail latency that a sub-millisecond query engine exists to guarantee, and because boxed object graphs defeat the CSR cache discipline (§8.2) that the whole design depends on.

Prerequisites:

  • Graph algorithms — Dijkstra, bidirectional search, A*, shortest-path trees; priority-queue mechanics (decrease-key vs lazy deletion).
  • Data-oriented design — CSR/CSC layout, cache lines, branch prediction, SoA vs AoS, prefetch behavior.
  • Computational geometry basics — great-circle (Haversine) distance, planar partition, alpha-shapes (isochrone hull).
  • Binary-format parsing — protobuf wire format, zlib inflate, delta/zig-zag decoding (OSM dense nodes).
  • Parallelism — work-stealing, data-parallel map/reduce, lock-free read sharing, false-sharing avoidance.
  • Algorithm engineering — preprocessing/query tradeoffs, witness search, partitioning, profile (function) search.

2. Why Build This

Unique systems knowledge taught:

  • Preprocessing-vs-query tradeoff space — the central idea of route planning: pay offline (CH minutes, CRP topology once) to make online queries sub-millisecond, without sacrificing exactness. CH (fast query, slow rebuild) vs CRP (fast recustomization, slightly slower query) is the canonical engineering choice.
  • Exact speedup techniques — the deep lesson that CH, CRP, ALT, and bidirectional search shrink the search space, not the answer: every one returns the provably optimal path. A* with an admissible heuristic is exact. Approximation is a separate, opt-in decision (approximate TCH), never an accident.
  • Data-oriented graph layout — why CSR beats adjacency-list-of-pointers by an order of magnitude on a 50 M-node graph; how cache lines, not Big-O, dominate real query latency.
  • Goal direction — heuristics (Haversine, landmark lower bounds, consistent potentials) and why admissibility/consistency are correctness properties, not tuning knobs.
  • Hierarchy and partition — node importance ordering (CH) and multilevel graph partitioning (CRP) as two different ways to exploit the near-tree structure of road networks.
  • Time-dependence — travel-time functions instead of scalars; the FIFO/non-overtaking property as the precondition that keeps Dijkstra correct; function composition/min in profile search.

Historical/architectural significance:

  • Dijkstra (1959, PR1) — the foundational label-setting algorithm; every technique here is a way to avoid relaxing the whole continent with it.
  • A* (Hart–Nilsson–Raphael 1968, PR2) — goal-directed search; the admissible-heuristic correctness argument.
  • Contraction Hierarchies (Geisberger–Sanders–Schultes–Delling 2008/2012, PR4) — the result that made continental sub-millisecond exact routing routine; shipped in OSRM, GraphHopper.
  • CRP (Delling–Goldberg–Pajor–Werneck 2011/2017, PR5) — the production answer to live traffic: separate metric-independent topology from fast per-metric customization; deployed at web-map scale.
  • Bast et al. 2016, "Route Planning in Transportation Networks" (PR14) — the master survey unifying ALT, CH, CRP, arc-flags, hub labels, time-dependent and multimodal routing; the single most important reading for this project.

Engineering muscles developed: data-oriented design under cache constraints; offline/online pipeline separation; differential conformance against an exact oracle; bounded-resource parsing of adversarial input; parallel preprocessing; algorithm engineering with measured speedups.

Production engineering concepts exercised: versioned immutable indexes (rebuild on new OSM extract), memory-mapped read-only data shared across query threads, customization for live metrics, isochrone/matrix batch APIs for logistics, observability of a compute-bound service (search-space size, settled-node counts, queue pressure).

Cross-links:

  • #287 Robotics Motion Planner — continuous configuration-space planning (sampling: RRT/PRM; optimization: CHOMP/TrajOpt). This project is discrete road-graph routing: a fixed finite graph, integer weights, exact shortest paths. They share the word "planning" and nothing else; the boundary is deliberate and load-bearing.
  • Compilers / IR — CH preprocessing is a "lowering": the contracted up/down graph is a compiled form of the original, unpacked back to source edges at query time, exactly as IR lowers and a debugger maps back to source lines.
  • Databases / query optimizer — CRP's metric-independent topology + per-metric customization mirrors a prepared statement / plan cache: compile the shape once, bind parameters (weights) cheaply.
  • Distributed systems — the read-only memory-mapped index shared across query workers is the same pattern as an immutable replicated segment; rebuilds are atomic index swaps.
  • GIS / geometry — Haversine, partition, and isochrone polygonization tie into the computational-geometry kernel project.

Calibration value: routing looks like "just run Dijkstra," and is in fact a preprocessing-pipeline + data-layout + algorithm-engineering problem where the naive answer is 1000× too slow and the fast answers are subtle to keep exact. Building CH and CRP and proving them bit-identical to a Dijkstra oracle permanently recalibrates an engineer's intuition for "how is this real product so fast," and instills the discipline of validating every optimization against a ground-truth oracle.

What Mastery Looks Like — after building this, an engineer can:

  • Explain, from first principles, why CH query is < 1 ms while CRP query is 1–2 ms, and why that 1 ms costs CRP a live-traffic capability CH cannot cheaply offer (Phase 7, Phase 10).
  • Design a differential-testing harness for any optimization against a ground-truth oracle, not just this one (Phase 2, Phase 13, I1).
  • Reason about cache-line-driven performance (CSR vs pointer graphs) independent of Big-O (Phase 0, §8.2).
  • Prove a heuristic admissible/consistent before trusting its speed, distinguishing a correctness property from a tuning knob (Phase 3, Phase 4, I4/I5).
  • Diagnose a "silently wrong but fast" bug class unique to shortcut/overlay-based systems (unpacking, witness search) (Phase 6, Phase 7, I7/I8).
  • Model the FIFO precondition that makes time-dependent Dijkstra valid, and recognize the same non-overtaking pattern in other temporal-ordering systems (Phase 8, I11).
  • Compare partition-based (CRP) vs ordering-based (CH) vs labeling-based (Hub Labeling) architectures for the same exact problem, and justify the choice for a given deployment regime (Comparative Architecture Table, Alternative Architectures).

Query engine output shapes (five, fanning out from the box above): P2P (single least-cost path + cost), one-to-many (reachable set / distances to many targets), isochrone (a time-budget polygon, GeoJSON), matrix (a dense |S|×|T| cost matrix), alternatives (a small set of admissible near-optimal paths).

Per-box detail:

  • OSM PBF FILE — the untrusted input: a .osm.pbf extract (city to planet). A sequence of length-prefixed Blobs, each zlib-compressed protobuf (OSMHeader once, then many OSMData/PrimitiveBlock). May be truncated, oversized, or hostile. Read-only, streamed; never fully materialized when avoidable.
  • PBF PARSER — reads BlobHeader (length-prefixed), inflates the zlib blob, decodes the protobuf PrimitiveBlock: a string table plus primitive groups of dense-nodes (delta + zig-zag packed), ways (node-ref deltas + tags), relations (members + tags). Bounds-checks every length; caps allocation by declared sizes. Emits a stream of (NodeRecord | WayRecord | RelationRecord).
  • PROFILE — maps OSM tags to routing semantics: access (is this way routable for the mode?) and speed (→ travel-time weight) and turn/penalty defaults. Ships as a hardcoded car profile; the general tag→weight DSL is PhaseDeferred("Phase 1 — OSM PBF Ingest → Routing Graph"). Pure function of tags; deterministic.
  • GRAPH BUILDER — the topology compiler: identifies intersections (nodes referenced by ≥2 ways, or way endpoints), collapses interior geometry nodes of a way into a single weighted edge (preserving polyline for output), applies oneway direction, and lowers turn-restriction relations into either forbidden turns (edge-expanded) or turn-table entries. Produces node/edge id assignment.
  • CSR GRAPH (fwd + rev) — the in-memory routing graph in compressed-sparse-row form: head[n+1] offsets, edges[m] of {target, weight}; a parallel reverse CSR for backward search; coords[n] for heuristics and output. Optionally an edge-expanded form when turn costs are active. Immutable after build; the hot data structure all search scans.
  • ALT PREPROCESS — selects landmarks (avoid / farthest / planar), runs a full Dijkstra forward and backward from each landmark, stores dist(L,·) and dist(·,L) tables. Output feeds triangle-inequality lower bounds at query time.
  • CH PREPROCESS — orders nodes by importance (edge difference, deleted neighbors, etc.), contracts them lowest-first, running witness searches to decide which shortcuts are necessary, and emits the up/down graph + ranks + per-shortcut middle node. Slow (minutes–1 h), metric-bound (re-run on weight change).
  • CRP PREPROCESS — computes a metric-independent multilevel partition (inertial flow / PUNCH-style) and the overlay topology (which boundary vertices connect within each cell) — once. The CUSTOMIZE step then computes overlay arc weights for a given metric (live traffic), bottom-up, in seconds.
  • ROUTING INDEX — the versioned, immutable, memory-mappable artifact bundling every preprocessed structure plus a metadata header (OSM extract SHA, profile id, tool version, technique set). Atomically swapped on rebuild; shared read-only across query threads.
  • QUERY ENGINE — loads the index and answers queries: snap a coordinate to the nearest routable edge, then run the chosen algorithm (bidirectional Dijkstra, A*/ALT, CH with stall-on-demand + unpacking, CRP overlay search, TD-Dijkstra for a departure time, PHAST for one-to-all). Stateless per query; the index is read-only.

6. Design Principles

Fourteen non-negotiable principles. Each: tradeoff, operational implication, breakage-on-violation.

  1. P1: Exactness is not negotiable; speedups shrink the search, not the answer. CH, CRP, ALT, and bidirectional search, and A*(admissible), all return the provably optimal path — identical to the Dijkstra oracle. Tradeoff: preprocessing cost and code complexity. Operational: every technique is graded against the oracle in CI. Violation: an "optimization" that returns a 1.02× path is a bug, not a speed/quality knob — silent wrong routes erode all trust.
  2. P2: The Dijkstra oracle is ground truth. Plain Dijkstra (Phase 2) is implemented first, kept forever, and is the differential reference for every later technique. Tradeoff: must keep a slow path maintained. Operational: route --validate re-runs the oracle. Violation: without an oracle, a subtle CH ordering bug ships undetected and corrupts a fraction of routes.
  3. P3: Non-negative weights, always. Dijkstra/CH/CRP correctness requires weight ≥ 0. Tradeoff: cannot model "rebates"; turn bonuses must be re-based to non-negative. Operational: the profile and turn tables assert ≥ 0 at build. Violation: a single negative edge breaks the label-setting invariant → wrong distances, possibly non-termination.
  4. P4: Heuristic admissibility + consistency are correctness properties. A* potentials must never overestimate (admissible) and should satisfy h(u) ≤ w(u,v)+h(v) (consistent). Tradeoff: Haversine must use the network's max speed (a loose but safe bound). Operational: potentials are unit-tested for admissibility on fixtures. Violation: an inadmissible heuristic yields fast but wrong (suboptimal) paths.
  5. P5: CSR is the canonical layout; the graph is immutable after build. Forward + reverse CSR, SoA, u32 ids. Tradeoff: edits require rebuild. Operational: the index is memory-mapped and shared read-only. Violation: an adjacency-list-of-Box graph is ~10× slower and defeats every cache-locality assumption the latency targets depend on.
  6. P6: Offline preprocessing is separate from online query. Ingest + build write a versioned index; the query engine only reads it. Tradeoff: a build/serve split and an index format to version. Operational: rebuilds are atomic swaps; queries never block on a build. Violation: building inside the query path reintroduces the latency the whole project exists to remove.
  7. P7: Bounded, total parsers. PBF/protobuf/zlib parsing handles every byte sequence: valid → graph, invalid → typed ParseError; allocation bounded by validated counts. Tradeoff: no unwrap on input paths. Operational: fuzzers must find zero panics/OOMs. Violation: a crafted .osm.pbf panics or OOMs the build host.
  8. P8: Determinism + reproducibility. Identical (OSM extract SHA + profile + tool version) ⇒ byte-identical index and byte-identical paths; ties broken by ascending NodeId. Tradeoff: must pin inputs and avoid float in cost. Operational: index header records all input SHAs; incidents reproduce from them. Violation: nondeterministic tie-breaks make "why did the route change" unbisectable.
  9. P9: The FIFO property is the precondition for time-dependent correctness. Every travel-time function must satisfy τ1 ≤ τ2 ⇒ τ1+f(τ1) ≤ τ2+f(τ2) (no overtaking). Tradeoff: raw probe data must be FIFO-repaired at build. Operational: TTFs are validated at build; non-FIFO → NonFifoTtf. Violation: TD-Dijkstra silently returns wrong arrivals if a function lets a later departure arrive earlier.
  10. P10: Customization is metric-independent topology + cheap weights (CRP). The partition and overlay shape are computed once; only arc weights are recomputed per metric. Tradeoff: a partition/overlay layer to maintain. Operational: live traffic updates run in seconds, not the CH rebuild hour. Violation: coupling topology to the metric forces a full re-preprocess on every traffic tick — unusable for live data.
  11. P11: Partition cells are disjoint and covering. Every node belongs to exactly one cell per level; levels nest. Tradeoff: partitioner must guarantee this. Operational: asserted at build; overlay correctness depends on it. Violation: overlapping/missing cells corrupt overlay arcs → wrong or missing CRP paths.
  12. P12: Unpacking yields a valid original-edge path with identical cost. A CH/CRP shortcut expands to a sequence of original edges whose summed weight equals the shortcut weight. Tradeoff: store middle nodes / edge ids. Operational: unpack is checked against the shortcut weight in tests. Violation: an unpacking bug returns a path whose geometry/cost disagrees with the reported distance.
  13. P13: Bounded resource usage per query. Per-query scratch (dist, parent) is O(n) but pooled/reused; isochrone/matrix sizes are capped; PHAST sweeps are bounded. Tradeoff: pre-allocate scratch pools. Operational: concurrent queries reuse thread-local buffers; no per-query 50 M-element allocation churn. Violation: allocating O(n) per request thrashes the allocator and spikes tail latency.
  14. P14: Observability of search, not just outcome. Every query can report settled-node count, relaxed-edge count, max queue size, and (for CH) unpacked-shortcut count. Tradeoff: a few counters per search. Operational: "this query was slow" is debuggable via search-space metrics. Violation: a latency regression with no search-space telemetry is undiagnosable.

8. Domain Model / Protocol / Data Model

8.1 The road graph

A directed weighted graph G = (V, E). A node is an intersection (a point where routing decisions happen); an edge is a directed road segment from one intersection to the next, weighted by a metric (travel time or distance). A two-way street is two directed edges. weight: u32 is travel time in deciseconds (0.1 s units → 119 h fits in u32 minus the INF sentinel) or distance in meters, chosen per metric. u32::MAX is reserved as INF / unreachable (I16). Coordinates Coord{lat_e7, lon_e7} are fixed-point degrees × 10⁷ (i32), exact and float-free for snapping/output; floats appear only in the Haversine bound and geometry export.

Road networks have exploitable structure: near-planar, low average degree (~2–3), sparse (m ≈ 2.5n), with a natural hierarchy (few high-speed arterials carry most long routes). CH exploits the hierarchy via importance ordering; CRP exploits near-planarity via small partition cuts; A*/ALT exploit the geometric embedding.

8.2 CSR (Compressed Sparse Row) layout

The canonical adjacency layout for a static graph. Two arrays:

head:  [u32; n+1]      // head[v]..head[v+1] is v's out-edge range
edges: [Edge; m]       // Edge { target: u32, weight: u32 }   (sorted by source, then target)

Out-neighbors of v = edges[head[v] .. head[v+1]] — a contiguous slice, so neighbor iteration is a linear cache-friendly scan. head[v+1]-head[v] is v's out-degree; head[n]==m (I3). Memory: 4(n+1) + 8m bytes ≈ for 50 M nodes / 120 M edges ≈ 0.2 GB + 0.96 GB. Contrast adjacency-list-of-Vec: ~24 B overhead/node + pointer-chasing per neighbor → ~10× slower and cache-hostile (P5).

Reverse CSR (rev): the transpose, built by counting in-degrees then scattering — needed for backward search (bidirectional Dijkstra, CH/CRP backward, ALT backward tables). Built once at index time.

ASCII: node 0 has edges to {1,2}; node 1 to {2}; node 2 to {0}
head  = [0,        2,     3,    4]
edges = [(1,w),(2,w), (2,w), (0,w)]
         \__node0__/  node1  node2

8.3 Node-based vs edge-based (edge-expanded) graph

Node-based Edge-based (edge-expanded)
Node = intersection a directed road segment
Edge = road segment a turn between two segments
Turn costs not representable on edges natural: weight on the turn-edge
Turn restrictions special-cased omit the forbidden turn-edge
Size n nodes, m edges ~m nodes, ~Σ deg² turn-edges (≈2–4× blow-up)

The edge-expanded graph (OSRM's representation, R1) makes turn modeling first-class: a U-turn penalty or a no-left-turn restriction is just a turn-edge weight or a missing turn-edge. CH and CRP then run on the edge-expanded graph unchanged. The cost is size; the build collapses degree-2 chains and shares turn tables to limit blow-up.

8.5 OSM PBF format

A .osm.pbf file is a sequence of blobs, each a length-prefixed pair (BlobHeader, Blob):

[ 4-byte BE length ][ BlobHeader (protobuf) ][ Blob (protobuf) ]   repeated
BlobHeader { type: "OSMHeader"|"OSMData", datasize: i32 }
Blob       { raw | zlib_data (+ raw_size) }     // payload is zlib-compressed protobuf

The first blob is OSMHeader (bbox, required features, writing program). Subsequent OSMData blobs each inflate to a PrimitiveBlock:

PrimitiveBlock {
  stringtable: [bytes]          // all strings (keys/values) interned; index 0 = ""
  primitivegroup: [PrimitiveGroup]
  granularity: i32 (default 100 nm)   lat_offset, lon_offset
}
PrimitiveGroup = oneof { dense: DenseNodes | ways: [Way] | relations: [Relation] | nodes:[Node] }

DenseNodes (the common node encoding) packs ids, lats, lons as delta-encoded zig-zag varints (each value is a delta from the previous), and tags as a flat keys_vals stream of stringtable indices terminated by 0. Way: id, delta-encoded refs (node ids), and keys/vals (stringtable indices). Relation: id, members (type, ref, role) and tags — turn restrictions live here.

Decoding requires: protobuf varint/zig-zag decode, zlib inflate, delta accumulation, granularity scaling (coord = (offset + granularity·value) / 100). Every length and count is bounds-checked; declared sizes cap allocation (P7, T1/T2).

8.6 Profile (tag → weight)

A profile maps OSM tags to routing semantics for a transport mode. Hardcoded car profile (the DSL is PhaseDeferred("Phase 1 — OSM PBF Ingest → Routing Graph")):

highway= car access default speed (km/h) notes
motorway / motorway_link yes 110 / 60 maxspeed tag overrides
trunk / primary yes 90 / 70
secondary / tertiary yes 60 / 50
residential / unclassified yes 30
service / living_street yes 10–20
footway / cycleway / path / steps no — excluded for car
construction / proposed no — excluded

Weight = length_m / speed_mps → deciseconds, rounded. oneway=yes → forward edge only; oneway=-1/reverse → backward only; oneway=no/absent → both; motorways imply oneway=yes unless tagged otherwise. access=no/private removes the way. The profile is a pure deterministic function of tags (P8); the same tags always yield the same weight.

8.7 Turn restrictions and costs

OSM models restrictions as type=restriction relations: members from (way), via (node or way(s)), to (way), tag restriction=no_left_turn | no_right_turn | no_u_turn | no_straight_on | only_left_turn | …. The graph builder lowers these onto the edge-expanded graph: a no_* restriction deletes the corresponding turn-edge; an only_* restriction deletes all other turn-edges from the from segment at the via. Turn costs (default U-turn penalty, e.g. 300 s; left-turn penalty across traffic) are weights on turn-edges. All turn weights are re-based non-negative (I2, P3). Via-way (multi-segment) restrictions require expanding the via path — handled in Phase 5.

8.8 Time-dependent travel-time functions (TTF)

For time-dependent routing an edge weight is a function f: τ ↦ travel_time of departure time-of-day τ, not a scalar. Represented as piecewise-linear, periodic with period T = 86400 s (one day):

Ttf { points: [(τ_i: u32 /*s of day*/, t_i: u32 /*travel time s*/)], period: 86400 }
// linear interpolation between consecutive breakpoints; wraps at period

FIFO / non-overtaking property (I11, P9): τ1 ≤ τ2 ⇒ τ1 + f(τ1) ≤ τ2 + f(τ2). Equivalently the arrival function a(τ) = τ + f(τ) is non-decreasing, i.e. f'(τ) ≥ -1 on every linear piece. FIFO means departing later never lets you arrive earlier — the precondition that keeps label-setting Dijkstra correct on a time-dependent graph. Probe/measured data is FIFO-repaired (lower later values to respect the bound) or rejected (NonFifoTtf).

Two query types: earliest-arrival (fix departure τ0, minimize arrival at t) via TD-Dijkstra evaluating f at each node's arrival time; profile (compute arrival as a function of all departures) via function composition (link: f∘g) and minimum (merge: pointwise min of two PWL functions). TCH shortcuts store composed TTFs and grow large → approximate TCH (PhaseDeferred("Phase 8 — Time-Dependent Routing (TD-Dijkstra + TCH)")) bounds breakpoint count with a max-error tolerance.

8.10 Bidirectional search meeting/stopping criterion

Forward search settles from s on G; backward from t on G_rev. Maintain μ = best known dist_f[v] + dist_b[v] over nodes settled (or relaxed) in both directions. Stop when min_key(Q_f) + min_key(Q_t) ≥ μ (I6). The shortest path need not pass through the first node settled in both directions; μ must be updated on every edge relaxation that touches an oppositely-reached node. Naive "stop at first common settled node" is a classic bug → suboptimal paths.

8.11 CH query mechanics

After preprocessing, each node has a rank (contraction order). The query runs bidirectional Dijkstra on the up-graph: forward from s relaxes only edges to higher-ranked nodes; backward from t (on the reverse up-graph) likewise. They meet at high-rank nodes. Stall-on-demand: before expanding a node u, if some already-settled higher-ranked neighbor w gives dist[w] + w(w,u) < dist[u], then u is reached suboptimally on the up-graph and is stalled (not expanded) — a major pruning. The result is an up-down path of shortcuts; unpacking recursively replaces each shortcut by its two constituent edges (via the stored middle node) until only original edges remain (I8).

8.12 CRP overlay query mechanics

The multilevel partition gives, per cell, an overlay of arcs between the cell's boundary vertices (precomputed shapes; weights from customization). A query runs bidirectional Dijkstra on a graph that uses: original edges inside the source and target cells, and overlay arcs at the coarsest level possible between them (climbing levels away from s/t, descending toward them). Customization (I10) guarantees each overlay arc weight equals the true in-cell shortest distance between its endpoints for the current metric, so the overlay search is exact. Path unpacking descends overlay levels back to original edges.

11. Core Schema & Types

Normative signatures; no bodies. Ids are u32; weights u32 deciseconds with u32::MAX = INF. Distances accumulate in u64 to prove no overflow (I15), then fit back in u32 for storage where bounded.

// ---- identifiers & primitives ----
type NodeId = u32;                  // < n; tie-break order (I19)
type EdgeId = u32;                  // < m
type Weight = u32;                  // deciseconds/meters; u32::MAX = INF (I16)
const INF: Weight = u32::MAX;
struct Coord { lat_e7: i32, lon_e7: i32 }   // fixed-point deg ×1e7 (ADR-6)

// ---- CSR graph ----
struct Edge { target: NodeId, weight: Weight }
struct Csr  { head: Vec<u32> /*len n+1*/, edges: Vec<Edge> /*len m*/ }   // I3
struct Graph { fwd: Csr, rev: Csr, coords: Vec<Coord>, n: u32, m: u32 }
impl Graph {
  fn out(&self, v: NodeId) -> &[Edge];        // edges[head[v]..head[v+1]]
  fn r#in(&self, v: NodeId) -> &[Edge];       // reverse adjacency
}

// ---- priority queue (4-ary, lazy-delete) ----
struct Queue { heap: Vec<(Weight, NodeId)>, /* dist owned by search */ }   // ADR-8
fn push(&mut self, w: Weight, v: NodeId);
fn pop_min(&mut self) -> Option<(Weight, NodeId)>;   // skip stale entries

// ---- search scratch (pooled, reused per thread; I13/P13) ----
struct SearchSpace { dist: Vec<Weight>, parent: Vec<EdgeId>, touched: Vec<NodeId> }
fn reset(&mut self);                          // clear only touched entries (O(touched))

// ---- results ----
struct Path { edges: Vec<EdgeId>, nodes: Vec<NodeId>, cost: Weight, geometry: Vec<Coord> }
enum RouteError { Disconnected, NodeOutOfRange, NegativeWeight, NonFifoTtf,
                  BudgetExceeded, ParseError, BuildError, PhaseDeferred(&'static str) }

// ---- heuristic / ALT ----
trait Heuristic { fn h(&self, v: NodeId, t: NodeId) -> Weight; }   // admissible (I4)
struct Haversine<'a> { coords: &'a [Coord], inv_max_speed: u32 }
struct Alt { landmarks: Vec<NodeId>, to_l: Vec<Weight>, from_l: Vec<Weight> }  // k×n each

Remaining types — CH, CRP, time-dependent, batched outputs, and the on-disk index:

// ---- contraction hierarchies ----
struct ChGraph { rank: Vec<u32> /*per node*/, up: Csr, down: Csr,
                 shortcut_mid: Vec<NodeId> /*per shortcut edge; NONE for original*/ }
struct Shortcut { from: NodeId, to: NodeId, weight: Weight, middle: NodeId }
fn ch_query(&self, s: NodeId, t: NodeId) -> Result<Weight, RouteError>;    // bidir up-graph
fn unpack(&self, e: EdgeId, out: &mut Vec<EdgeId>);                         // I8, recursive

// ---- customizable route planning ----
struct Partition { levels: u8, cell_of: Vec<Vec<u32>> /*[level][node]*/ }   // I9
struct OverlayTopology { /* boundary vertices + arc shapes per cell/level */ }
struct Metric { base: Vec<Weight> /*per edge*/, overlay: Vec<Weight> /*per overlay arc*/ }
fn customize(&self, topo: &OverlayTopology, base: &[Weight]) -> Metric;     // seconds (I10)
fn crp_query(&self, m: &Metric, s: NodeId, t: NodeId) -> Result<Weight, RouteError>;

// ---- time-dependent ----
struct Ttf { points: Vec<(u32, u32)>, period: u32 }     // PWL, FIFO (I11/I12)
fn eval(&self, tau: u32) -> Weight;                     // interpolate + wrap
fn link(&self, g: &Ttf) -> Ttf;                         // composition f∘g (profile)
fn merge(&self, g: &Ttf) -> Ttf;                        // pointwise min
fn td_dijkstra(&self, s: NodeId, t: NodeId, depart: u32) -> Result<Weight, RouteError>;

// ---- batched ----
fn phast(&self, s: NodeId) -> Vec<Weight>;              // one-to-all (I20)
fn isochrone(&self, s: NodeId, budget: Weight) -> GeoJsonPolygon;
fn matrix(&self, src: &[NodeId], tgt: &[NodeId]) -> Vec<Weight>;  // |S|*|T|, bucket-CH

// ---- routing index (versioned, immutable, mmap) ----
struct IndexHeader { magic: [u8;8], version: u32, extract_sha: [u8;32],
                     profile_id: u32, techniques: u32 /*bitset*/, n: u32, m: u32 }
struct RoutingIndex { header: IndexHeader, graph: Graph, ch: Option<ChGraph>,
                      crp: Option<(Partition, OverlayTopology)>, alt: Option<Alt>,
                      ttf: Option<Vec<Ttf>> }   // I17/I18

Ownership: Graph/ChGraph/RoutingIndex are immutable after build, shared as Arc<RoutingIndex> and Send+Sync (I17); query threads borrow & and own only their SearchSpace scratch (pooled, P13). Metric is the one mutable-per-customization artifact (CRP), swapped atomically (ArcSwap) on a live-traffic update. Serialization: the index is a custom little-endian mmap-friendly format (ADR-18) with a versioned header (I18); paths/geometry serialize to GeoJSON/polyline (ADR-24). Compatibility: results are pinned to a recorded OSM extract SHA + profile id (Compatibility & Versioning).

Phase 0 — Repo Skeleton + Graph Core (CSR) + Core Types + Index Format

Fourteen phases (Phase 0 – Phase 13). Each ends in a runnable, measurable artifact with explicit acceptance criteria. The exactness gate is differential agreement with the Dijkstra oracle (Phase 2, P2, I1) on a fixed random OD sample; preprocessing techniques add no error, only speed.

0.1 Objectives

Bootstrap the workspace; define NodeId/EdgeId/Weight/Coord, the Edge/Csr/Graph types, the 4-ary Queue, pooled SearchSpace, RouteError, and the versioned RoutingIndex header + writer/loader. Establish forward+reverse CSR construction. Constraint introduced: every array is u32-indexed and POD-typed from the first line of code (ADR-3, ADR-4) — retrofitting layout later is a rewrite, not a patch.

0.2 Detailed Implementation Steps

  • graph/csr.rs — build CSR from an edge list: count out-degrees → prefix-sum head → scatter edges; validate head monotone, head[n]==m, target<n (I3, P5).
  • graph/builder.rs — reverse-CSR via transpose (count in-degrees, scatter); parallel-edge collapse (min weight); self-loop drop.
  • graph/weight.rs — Weight, INF, saturating add in u64 then check < INF (I15/I16).
  • index/format.rs + writer.rs + loader.rs — magic+version+SHA header (I18, ADR-18); little-endian aligned arrays; mmap load.
  • search/heap.rs — 4-ary binary heap with lazy deletion (ADR-8); SearchSpace with touched-list reset (O(touched), P13).
  • cli/main.rs — stub route stats <index> subcommand wired to the loader.

0.3 Deliverable

A library that loads a hand-written tiny edge list into a Graph, writes/loads a RoutingIndex, and a CLI route stats <index> printing n, m, and degree distribution.

0.4 Acceptance Criteria

CSR round-trips an edge list bit-exactly on the graph/example8.json fixture; reverse CSR matches the transpose; index write→load preserves all arrays; header version mismatch is refused with RouteError::ParseError (I18); 4-ary heap passes a sort-property test over 10,000 random pushes.

0.5 Conformance Fixtures

graph/csr_roundtrip.json (edge list → expected head/edges); graph/reverse.json; index/header_mismatch.bin; the §8.4 eight-node graph as graph/example8.json.

0.6 Pitfalls

Off-by-one in head prefix-sum (drops or duplicates the last node's edges) — detect via the head[n]==m assertion; forgetting head[n]==m entirely; target not bounds-checked → OOB read at query time, not build time; using usize ids and silently doubling memory on 64-bit hosts; treating the heap's lazy-deleted stale entries as valid pops.

0.7 Performance Concerns

Edge is 8 bytes (two u32) → two edges per 16-byte half-cache-line; keep Edge POD and #[repr(C)] (ADR-3); SearchSpace::reset must be O(touched), never O(n) per query (P13) — this is the single highest-leverage micro-optimization in the whole system, since every later phase reuses this scratch.

0.8 Edge Cases

Empty graph (n=0); single node, no edges; node with zero out-degree; maximal u32 node count near 4.29e9 (document the planet boundary, ADR-4); an index file truncated mid-write.

0.9 Failure Analysis

A malformed head corrupts every adjacency lookup downstream; caught by the CSR-validate fixtures before any search runs. Blast radius: unbounded (every phase depends on Graph), which is why the validation lives at build time, not query time.

0.10 Operational Notes

Establish CI (fmt, clippy, test, no_std build) here; the index header is the version/observability anchor for all later phases. No metrics exist yet beyond CI green/red — Phase 12 wires runtime telemetry.

Phase 1 — OSM PBF Ingest → Routing Graph

1.1 Objectives

Parse OSM PBF (blobs, zlib, protobuf, dense nodes), filter highway=*, apply the hardcoded car profile, honor oneway, detect intersections, collapse geometry, and emit the CSR Graph. Turn restrictions are recorded here; lowered in Phase 5. Profile DSL is PhaseDeferred("Phase 1 — OSM PBF Ingest → Routing Graph").

1.2 Detailed Implementation Steps

  • osm/blob.rs — read [len][BlobHeader][Blob]; inflate zlib (miniz_oxide); bound datasize/raw_size (P7, ADR-19, §8.13).
  • osm/pbf.rs + primitive.rs — protobuf varint/zig-zag; PrimitiveBlock string table; dense-node delta decode; way ref-delta decode; relation members.
  • osm/filter.rs + profile.rs — keep routable ways; tag→(access,speed) (§8.6); compute edge weight = length/speed; Haversine segment length from consecutive node coords.
  • graph/builder.rs — mark a node as an intersection if referenced by ≥2 kept ways or is a way endpoint; collapse interior nodes into one edge, retaining the polyline as geometry; apply oneway.
  • record turn-restriction relations into a side table keyed by via node (for Phase 5).
  • tools/osm-stats/ — standalone node/way/relation counter for validating against osmium fileinfo.

1.3 Deliverable

route build --in extract.osm.pbf --out region.idx produces a routing index; tools/osm-stats prints node/way/relation counts; route stats shows the routing graph size.

1.4 Acceptance Criteria

Node/way/relation counts match osmium fileinfo on fixtures; routing-graph n/m within tolerance of a reference build; truncated/oversized PBF rejected with ParseError (no panic); deterministic id assignment (rerun → identical index, I19/P8).

1.5 Conformance Fixtures

osm/monaco.osm.pbf (small real extract) with expected counts; osm/truncated.pbf; osm/zipbomb.pbf; osm/oneway_cases.pbf; osm/dense_nodes.pbf.

1.6 Pitfalls

Forgetting delta-decode resets per group (ids drift); granularity/offset scaling wrong (coords off by 100×); treating every node as an intersection (graph 10× too big); not collapsing degree-2 chains; oneway=-1 direction inverted; assuming a .osm.pbf is small enough to load fully into memory (planet extracts are tens of GB).

1.7 Performance Concerns

Stream blobs; don't hold the whole file; parse blobs in parallel (rayon, ADR-20) then merge; intern strings per block; the node-id → internal-id map is the memory peak (use a sorted Vec + binary search or a perfect hash, not a HashMap of 50 M entries, per the Scalability Analysis bottleneck list).

1.8 Edge Cases

Ways with one node (drop); refs to missing nodes (drop edge, count it); roundabouts (implicit oneway); maxspeed non-numeric (walk, none) → profile default; ferries (defer / exclude).

1.9 Failure Analysis

A profile/oneway bug silently routes the wrong direction or excludes a road class; caught by oneway_cases fixtures and by downstream oracle diffs on real extracts (Phase 2, Phase 13, I1).

1.10 Operational Notes

Pin the extract by SHA + date in the index header (ADR-31); ingest is offline; log dropped-edge/skipped-restriction counters for data-quality visibility.

Phase 2 — Dijkstra + Heap + Path Extraction (the Exact Oracle)

2.1 Objectives

Implement plain Dijkstra (label-setting) with the 4-ary heap and predecessor-array path extraction. This is the permanent ground-truth oracle (P2, I1) for every later technique.

2.2 Detailed Implementation Steps

  • search/dijkstra.rs — init dist[s]=0; pop min; settle; relax out-edges with u64 accumulator → Weight (I15); lazy-delete stale heap entries; tie-break by NodeId (I19, P8).
  • search/path.rs — store parent[v]=edge; backtrack from t; reconstruct node/edge list + geometry + cost.
  • early termination when t is settled; Disconnected if heap empties first (I14).
  • route query --algo dijkstra s t CLI.

2.3 Deliverable

Exact P2P routing on any built index; route query prints cost, node count, and geometry; route --validate infrastructure seeded (oracle is itself).

2.4 Acceptance Criteria

Matches hand-computed costs on example8 (0→7 = 115, §8.4); settles nodes in non-decreasing distance order; Disconnected on a disconnected fixture; deterministic across reruns (I19).

2.5 Conformance Fixtures

graph/example8_dijkstra.json (settle order + dist); graph/disconnected.json; graph/random_od_oracle.json (OD pairs + exact costs — the master differential set used from Phase 3 onward).

2.6 Pitfalls

Decrease-key vs lazy-delete confusion (settling a stale entry); not skipping already-settled nodes; integer overflow on weight sum (use u64, I15); wrong tie-break → nondeterministic paths (I19); trusting the oracle before hand-verifying it on small graphs.

2.7 Performance Concerns

The hot loop is pop_min + neighbor scan; dist/parent are O(n) arrays reused from the pool (P13); 4-ary heap reduces cache misses vs binary (ADR-8); avoid per-pop allocation.

2.8 Edge Cases

s==t (cost 0, empty path); zero-weight edges (allowed, ≥0, I2); a node reachable only via INF (unreachable); very long paths near u32 cost (I15).

2.9 Failure Analysis

If the oracle is wrong, every differential test is wrong; hence the oracle itself is hand-verified on small graphs and property-tested (triangle inequality, sub-path optimality) before it is trusted anywhere else in the system.

2.10 Operational Notes

Expose settled/relaxed counters (P14); route query --algo dijkstra is the slow-but-trusted fallback shipped forever for --validate.

Phase 3 — A* + Bidirectional Dijkstra

3.1 Objectives

Two exact, preprocessing-free speedups: goal-directed A* with an admissible + consistent Haversine/max-speed heuristic (I4/I5, PR2), and bidirectional Dijkstra with the correct meeting/stopping criterion (I6, §8.10). Bidirectional roughly halves the searched area; A* prunes toward the target 2–10×. Both remain identical to the oracle (I1). Bidirectional's meeting logic (§8.10) is the reusable substrate for CH/CRP queries (Phase 7, Phase 10).

3.2 Detailed Implementation Steps

  • search/bidir.rs — two SearchSpaces + two queues; alternate or balance by smallest min-key; backward search runs on G_rev (the reverse CSR); track μ = best dist_f[v]+dist_b[v], updated on every edge relaxation touching an oppositely-reached node (not only on settle); stop when min_key(Q_f)+min_key(Q_t) ≥ μ (I6); reconstruct via the meeting node's forward+backward parents.
  • search/astar.rs — Heuristic trait; Haversine computes great-circle distance from coords, divides by network max speed → admissible travel-time lower bound (h(v,t), ADR-9, P4); priority key g+h.
  • reduced-cost reformulation w'(u,v)=w(u,v)-h(u)+h(v) ≥ 0 (consistency, I5) → no node re-expansion; the standard 4-ary heap works unchanged.
  • bidirectional A* — symmetric potential p_f(v)=(h_t(v)-h_s(v))/2, p_b(v)=-p_f(v) to keep both directions consistent; reuse the §8.10 bidirectional meeting logic.
  • meeting condition for A*: terminate when top_f + top_b ≥ μ measured on reduced keys, re-based by the chosen potentials.

3.3 Deliverable

route query --algo bidir | --algo astar | --algo bidir-astar; each reports forward/backward settled counts, the meeting node, and settled-count speedup vs plain Dijkstra.

3.4 Acceptance Criteria

Identical cost to the Dijkstra oracle on the random OD set (I1); bidirectional settled-count strictly below unidirectional on average; a test that would fail under the naive "first common settled node" stop passes (I6); A* admissibility property holds (h(v) ≤ oracle_dist(v,t) on samples, I4); A* settles 2–10× fewer nodes on long queries (M5).

3.5 Conformance Fixtures

graph/bidir_meeting.json (optimum does NOT cross the first common node); graph/bidir_vs_oracle.json; graph/astar_admissible.json (h ≤ true dist ∀ node); graph/astar_vs_oracle.json; graph/maxspeed.json (the bound's denominator).

3.6 Pitfalls

Bidir: stopping at the first node settled in both directions (classic suboptimality bug); updating μ only on settle not on relaxation; using G instead of G_rev backward; double-counting the meeting edge. A*: average not max speed (inadmissible → wrong path); Euclidean on raw lat/lon (distortion → inadmissible at high latitude); inconsistent potentials → re-expansions; unit mixing (m vs deciseconds).

3.7 Performance Concerns

Balance the two frontiers by smallest min-key; share nothing mutable between directions; the meeting check is O(1) per relaxation. Haversine has sin/cos/sqrt per node — cache h per settled node or compute lazily; the reduced-cost view keeps the heap untouched.

3.8 Edge Cases

s==t (cost 0); one-directional connectivity (s→t exists, t→s does not — backward must use rev); symmetric vs asymmetric weights; h(t)=0; antipodal coordinates; date-line crossing; nodes with missing coords (fall back to h=0, still admissible).

3.9 Failure Analysis

A wrong bidir stop returns a path 1–5% too long; an inadmissible heuristic returns a fast wrong answer — both plausible, so only the oracle diff (I1) catches them; I4/I6 are CI-gated, never eyeballed.

3.10 Operational Notes

A*/bidir need no preprocessing — they are the "interactive, no-index-yet" path; document that A*'s speedup depends on the metric (distance helps more than time). Bidirectional's meeting logic is reused by CH/CRP, so its tests are foundational.

Phase 4 — ALT (A*, Landmarks, Triangle Inequality)

4.1 Objectives

Replace the geometric heuristic with landmark lower bounds (PR3): precompute distances to/from a few landmarks; derive tight admissible bounds via the triangle inequality; 10–50× fewer settled nodes than Dijkstra (M6).

4.2 Detailed Implementation Steps

  • search/alt.rs — select k landmarks (avoid algorithm default, farthest fallback, ADR-10); run forward+backward Dijkstra from each → to_l[k][n], from_l[k][n].
  • lower bound h(v,t)=max_L max( from_l[L][v]-from_l[L][t], to_l[L][t]-to_l[L][v] ) (triangle inequality, I4); admissible + consistent (I5).
  • store landmark tables in the index (Alt type, §11); pick the 2–4 most useful landmarks per query for speed.
  • extend route build --landmarks N to invoke landmark selection + table construction.

4.3 Deliverable

route query --algo alt; route build --landmarks 16 adds ALT tables to the index.

4.4 Acceptance Criteria

Identical cost to the oracle (I1); landmark bound ≥ Haversine bound (tighter) on samples; settled count 10–50× lower (M6); table memory matches 2·k·n·4 B (M13, §4).

4.5 Conformance Fixtures

graph/alt_bounds.json (landmark bound ≤ true dist, ≥ Haversine); graph/alt_vs_oracle.json; graph/landmark_selection.json.

4.6 Pitfalls

Wrong triangle-inequality sign (bound exceeds true dist → inadmissible → wrong path, I4); too few landmarks (weak bound); too many (memory blow-up, M13); not using both to_l and from_l (loses half the bound); landmark selection that clusters (poor coverage).

4.7 Performance Concerns

Tables are 2kn·4 B — 16 landmarks × 50 M × 8 B ≈ 6.4 GB → tune k vs memory (§4, M13); querying all k landmarks per node is costly → dynamically pick the few tightest; tables are read-only and shared (I17).

4.8 Edge Cases

Landmark unreachable from a node (INF entry — skip in the max); disconnected components (landmarks per component); s or t equal to a landmark (bound exact).

4.9 Failure Analysis

A sign error makes a fraction of routes suboptimal in a metric-dependent way; only the oracle diff catches it (I1, I4).

4.10 Operational Notes

ALT is the "fast without a hierarchy" option and a stepping-stone to CH; landmark tables dominate index size — expose alt_table_bytes telemetry.

Phase 5 — Turn Restrictions / Edge-Based (Edge-Expanded) Graph

5.1 Objectives

Model turn costs and restrictions exactly by building the edge-expanded graph (nodes = directed segments, edges = turns, §8.3), lowering OSM type=restriction relations, and applying a default U-turn penalty — so every later technique (CH/CRP) handles turns unchanged on the expanded graph. Constraint introduced: turns become first-class, the routing graph 2–4× larger (ADR-13); the node-based Dijkstra oracle (Phase 2) is paired with an edge-expanded oracle for turn-aware ground truth.

5.2 Detailed Implementation Steps

  • osm/restriction.rs — parse from/via/to; classify no_left_turn/no_right_turn/no_u_turn/no_straight_on (delete the turn-edge) and only_* (delete all other turn-edges from from at the via); resolve via node and via-way chains (multi-segment via paths, §8.7).
  • graph/builder.rs (edge-expand mode) — each directed edge → a node; for each incoming/outgoing segment pair at an intersection emit a turn-edge weighted by the turn cost; omit forbidden turns; add a default U-turn penalty (e.g. 300 s) re-based ≥0 (I2, P3).
  • keep a compact per-intersection turn table to bound blow-up; collapse degree-2 chains before expansion to limit Σdeg² growth.
  • search/ runs unchanged on the expanded CSR; add an edge-expanded Dijkstra oracle (Dijkstra on the expanded graph) for differential turn-aware checks (I1 analog).

5.3 Deliverable

route build --turn-costs produces an edge-expanded index; route query respects no-left-turn and U-turn penalties; tools/route-explain shows the turn taken at each junction.

5.4 Acceptance Criteria

Routes obey restriction fixtures (a banned left turn is not taken); the U-turn penalty changes the chosen path predictably; the edge-expanded oracle matches hand-computed turn-aware costs; expanded n,m within the documented 2–4× of node-based (§4).

5.5 Conformance Fixtures

osm/no_left_turn.pbf (+ expected avoided turn); osm/uturn_penalty.json; osm/via_way_restriction.pbf (multi-segment via); osm/only_turn.pbf; graph/edge_expanded_oracle.json.

5.6 Pitfalls

Graph blow-up (2–4×) if degree-2 chains aren't collapsed first; via-way restrictions (multi-segment) mis-lowered; double-counting segment vs turn cost; a negative re-based turn bonus (I2); U-turns silently allowed where banned, or silently banned at dead-ends where required.

5.7 Performance Concerns

Edge-expanded n,m grow → all arrays (incl. ALT tables, CH shortcuts) grow; turn tables share structure to limit memory; CH/CRP preprocessing now runs on the larger graph (re-measure §4 budgets); the expansion is the build-memory peak.

5.8 Edge Cases

Dead-end (U-turn is the only legal move — must be allowed there despite the penalty); complex junctions (many turns); only_* restrictions (delete all other turns); a via-way longer than 1 segment; restriction with a dangling/missing via (skip, count restriction_skipped).

5.9 Failure Analysis

A mis-lowered restriction produces an illegal route (a real safety/legal issue) or an over-restricted disconnect; restriction fixtures + the edge-expanded oracle catch both; blast radius is every route through that junction.

5.10 Operational Notes

Turn handling roughly doubles graph size — document the memory/preprocessing impact; make --turn-costs opt-in so distance-only builds stay small; expose turn_edges, restrictions_applied, restriction_skipped counters.

Phase 6 — Contraction Hierarchies Preprocessing

6.1 Objectives

Build a Contraction Hierarchy (PR4): order nodes by importance, contract them lowest-first, run witness searches to suppress unnecessary shortcuts, and emit the up/down graph + ranks + per-shortcut middle node. The output must preserve exact distances (I7, P12, ADR-11).

6.2 Detailed Implementation Steps

  • ch/order.rs — priority queue keyed by importance = edge_difference + deleted_neighbors + contracted_neighbors (+ search_depth) (ADR-11); lazy update: pop the min, recompute its priority, if still ≤ new min contract it, else re-insert; periodic full recompute.
  • ch/contract.rs — to contract v: for each pair (u→v),(v→w) with u,w uncontracted, the path u→v→w needs a shortcut iff it is the unique shortest u→w path.
  • ch/witness.rs — local Dijkstra from u (ignoring v), bounded by dist(u,v)+dist(v,w) and a hop limit (e.g. 5); if it finds ≤ that bound, a witness exists → no shortcut; else add Shortcut{u,w, weight=d(u,v)+d(v,w), middle=v} (I7).
  • ch/shortcut.rs — accumulate shortcuts; after full contraction, assign ranks and split edges into up (to higher rank) and down CSRs.
  • parallelize independent contractions (nodes far apart) via rayon (ADR-20); recompute priorities for affected neighbors only.

6.3 Deliverable

route build --ch adds a ChGraph to the index; tools/route-explain shows shortcut count and node ranks.

6.4 Acceptance Criteria

Shortcut count ≈ 1.0–1.5× original edges (§4, M8); preprocessing completes within the time budget (M7); a post-build sample of OD pairs queried via plain Dijkstra on the CH up/down graph matches the oracle (I7); witness hop-limit tuned so exactness holds.

6.5 Conformance Fixtures

ch/order_example8.json (a fixed importance order + expected shortcuts for §8.4); ch/shortcut_witness.json (cases with/without a witness); ch/preprocess_stats.json (shortcut ratio bounds).

6.6 Pitfalls

Witness search unbounded (correct but O(slow) — must cap hops/distance); hop limit too tight (adds unnecessary shortcuts but stays exact) vs witness bound too loose (misses a needed shortcut → wrong distance, I7); not updating neighbor priorities after a contraction (poor order → too many shortcuts); non-deterministic order across runs (I19).

6.7 Performance Concerns

Contraction is the expensive phase (minutes–1 h, M7); witness search dominates — bound it aggressively; the importance recompute must be incremental; memory peaks while both original edges and growing shortcuts are held — stream/compact.

6.8 Edge Cases

A node whose contraction adds many shortcuts (high-degree junction — order it late); already-shortcut edges contracted again (nested shortcuts, store middle recursively); disconnected components (contract independently).

6.9 Failure Analysis

A witness bug that misses a needed shortcut yields a CH that returns slightly-too-long paths for a subset of OD pairs — caught only by the post-build oracle sample (I7); block release on any mismatch.

6.10 Operational Notes

CH is metric-bound: any weight change (new extract, profile tweak, traffic) requires a full re-preprocess (minutes–1 h) — this is precisely why CRP (Phase 10) exists for live traffic. Record preprocessing time + shortcut ratio in the index header. Real systems: OSRM (R1) and GraphHopper (R3) ship CH; RoutingKit (R2) and Fast Paths (R6) are the canonical clean references.

Phase 7 — Contraction Hierarchies Query

7.1 Objectives

Answer P2P in < 1 ms (M1) via bidirectional Dijkstra on the CH up-graph, with stall-on-demand pruning and shortcut unpacking to recover the original-edge path (I8). Exactness identical to the oracle (I1).

7.2 Detailed Implementation Steps

  • ch/query.rs — forward search from s relaxes only up edges (to higher rank); backward from t relaxes only reverse-up (i.e. down reversed); maintain μ (reuse Phase 3 meeting logic, I6); meet at high-rank nodes.
  • stall-on-demand: before expanding u, if any settled higher-rank neighbor w gives dist[w]+w(w,u) < dist[u], stall u (don't expand) — large pruning.
  • ch/unpack.rs — the up-down path is shortcuts; recursively replace each by its two halves via middle until only original edges remain; verify summed weight == reported cost (I8, P12).

7.3 Deliverable

route query --algo ch returns cost + unpacked geometry in < 1 ms warm; reports settled count (few hundred) and unpacked-shortcut count.

7.4 Acceptance Criteria

Identical cost to the oracle on the full random OD set (I1); p99 query < 1 ms warm (M1, §4); settled nodes in the hundreds; unpacked path cost == query cost (I8); stall-on-demand reduces settled count materially vs no-stall.

7.5 Conformance Fixtures

ch/query_example8.json (0→7 via up-graph = 115, unpacked to 0→1→4→5→7); ch/stall_cases.json; ch/unpack_cost.json; the shared graph/random_od_oracle.json.

7.6 Pitfalls

Relaxing down edges in the forward search (breaks the up-graph invariant); wrong meeting/stop reused incorrectly (I6); unpack recursion missing a level (path cost ≠ geometry, I8); stall-on-demand bug that stalls a node that was actually optimal (suboptimal result) — must be exact.

7.7 Performance Concerns

The few-hundred-node search is cache-resident; stall checks add per-node work but cut the frontier; unpacking is O(path shortcuts) — memoize hot shortcuts; keep up/down CSRs adjacent for locality.

7.8 Edge Cases

s==t; s or t is a very high-rank node; a path that is entirely original edges (no shortcuts to unpack); a shortcut whose middle is itself a shortcut (deep unpack).

7.9 Failure Analysis

A stall or up-graph bug yields a fast, plausible, wrong route; the oracle diff (I1) on a large OD sample is the only reliable detector — it is a hard CI gate.

7.10 Operational Notes

CH query is the production interactive path; expose ch_settled, ch_stalled, ch_unpacked metrics (P14). The CH query and its unpacking are reused by PHAST (Phase 9) and the CH matrix (Phase 13).

Phase 8 — Time-Dependent Routing (TD-Dijkstra + TCH)

8.1 Objectives

Support edge weights that are travel-time functions of departure time-of-day (§8.8), satisfying the FIFO non-overtaking property (I11, P9). Implement TD-Dijkstra (earliest-arrival for a fixed departure), time-dependent CH (TCH) with travel-time-function shortcuts (PR7), and profile queries (arrival as a function of all departures, PR8). Approximate TCH (bounded-error function compaction) is PhaseDeferred("Phase 8 — Time-Dependent Routing (TD-Dijkstra + TCH)"); exact TCH is the default. Constraint introduced: edge weights become functions; the index gains per-edge TTF arrays and is larger.

8.2 Detailed Implementation Steps

  • td/ttf.rs — piecewise-linear periodic Ttf (period 86400 s); eval(τ) interpolate + wrap (I12); FIFO validate (f'(τ) ≥ -1 on every piece) and FIFO-repair or reject (NonFifoTtf, I11); link (composition a(τ)=g(τ)+f(τ+g(τ)) i.e. f∘g) and merge (pointwise min of two PWL functions).
  • td/td_dijkstra.rs — label-setting on arrival time: relax arrive(w)=arrive(v)+f_{v→w}(arrive(v)); FIFO guarantees label-setting (Dijkstra) correctness (I11); early-stop at t; earliest-arrival for a fixed departure τ0. This is the TD oracle (I1 analog) for TCH.
  • td/tch.rs — contract on the time-dependent graph; shortcuts store composed TTFs (via link); witness search compares functions (min over the day) not scalars; functions grow → cap breakpoints (approximate, deferred, opt-in with a stated error bound — never silent, P1).
  • td/profile.rs — profile query computes arrival as a function of departure via repeated link/merge; reproduces earliest-arrival when sampled at one departure.

8.3 Deliverable

route query --algo td --depart 08:00 (earliest arrival); route profile s t (arrival-vs-departure curve); a time-dependent index variant carrying per-edge TTFs.

8.4 Acceptance Criteria

Earliest-arrival matches the TD-Dijkstra oracle on the time-dependent graph (I1 analog); FIFO enforced at build (I11); a profile query reproduces earliest-arrival when sampled at a departure; TTF eval continuous at breakpoints and across the period wrap (I12); rush-hour vs night departures yield different paths/times.

8.5 Conformance Fixtures

td/fifo_valid.json / td/fifo_violation.json; td/earliest_arrival.json (rush-hour vs night differ); td/profile_curve.json; td/link_merge.json (function-algebra unit cases); td/overnight.json (period-wrap route).

8.6 Pitfalls

Non-FIFO functions (a later departure arrives earlier → Dijkstra wrong, I11); off-by-one at the period wrap; function blow-up in TCH (breakpoints explode — needs the deferred approximation); confusing earliest-arrival (scalar) with profile (function); interpolation rounding that pushes f'(τ) < -1.

8.7 Performance Concerns

TTF eval runs per relaxation — keep functions small (few breakpoints); link/merge are the costly ops in profile/TCH and dominate preprocessing; approximate TCH trades a bounded error for tractable function size (deferred, opt-in); the time-dependent index can be several × the static size.

8.8 Edge Cases

Constant TTF (degenerates to scalar Dijkstra); departure exactly at a breakpoint; overnight routes (cross the period boundary); a single-point function (constant); empty/degenerate time window.

8.9 Failure Analysis

A FIFO violation or wrap bug returns an impossible (too-early) arrival; FIFO fixtures + the TD oracle catch it; profile bugs surface as a curve that disagrees with sampled earliest-arrivals; blast radius is all time-dependent queries on the affected edges.

8.10 Operational Notes

Time-dependent indexes are larger (functions per edge) — document the size multiplier; exact TCH is the default, approximate TCH is explicitly opt-in with a stated error bound (P1, never accidental). Expose ttf_breakpoints, td_settled, profile_link_ops.

Phase 9 — Isochrones + One-to-All (PHAST)

9.1 Objectives

One-to-all shortest-path trees and isochrones: run a one-to-all Dijkstra (or PHAST rank-order sweep on the CH, PR9) to a time/distance horizon, then extract the reachable region as a polygon (concave hull / alpha-shape over reached nodes → GeoJSON). Isochrone monotonicity: a larger budget's region contains a smaller budget's region. Constraint introduced: the one-to-all output shape and geometry polygonization.

9.2 Detailed Implementation Steps

  • batch/phast.rs — forward CH (up) search from s, then sweep all nodes in descending rank order applying down edges to settle every node's exact distance (vectorizable, parallel, PR9); one-to-all distances == per-target Dijkstra (I20). RPHAST (restricted sweep to a target subgraph) deferred to Phase 13's matrix support.
  • batch/isochrone.rs — run PHAST (or a bounded one-to-all Dijkstra) to budget T; collect reached edges (an edge is reachable iff both endpoints' settle times bracket T, with partial-edge interpolation at the boundary); polygonize via alpha-shape / concave hull (ADR-23, B5) with a grid-raster fallback; emit GeoJSON (RFC 7946).
  • batch/geojson.rs — polygon / multi-polygon / linestring serialization; holes for unreachable enclaves.

9.3 Deliverable

route isochrone s --budget 15m emits a GeoJSON polygon; one-to-all distance vector available via the library; reports reached-node count and sweep time.

9.4 Acceptance Criteria

PHAST one-to-all distances == per-target Dijkstra (I20); the isochrone contains exactly the nodes within budget (boundary-correct); monotonicity holds (budget T1<T2 ⇒ region(T1) ⊆ region(T2)); sweep time tens of ms continental (M10, §4).

9.5 Conformance Fixtures

batch/phast_vs_oracle.json (all-node distances == oracle); batch/isochrone_15min.geojson (golden polygon); batch/isochrone_monotone.json (nested budgets); batch/isochrone_disconnected.json (multi-polygon).

9.6 Pitfalls

PHAST sweep in the wrong rank order (must be descending — a node settles before it is used); isochrone hull too convex (overstates reachability) or too tight (spurious holes); budget boundary ambiguity (include a node at exactly T?); an unbounded budget (cap it, P13).

9.7 Performance Concerns

PHAST's rank-order sweep is sequential-friendly and parallelizable (the headline of PR9); the polygonization is the geometry cost, not the search; bound the budget to bound work; reuse the CH (Phase 7) up-search.

9.8 Edge Cases

Budget smaller than the nearest edge (single-point/empty isochrone); disconnected reachable set (multi-polygon GeoJSON); island/ferry-excluded regions (holes); a horizon that reaches the whole graph (full-coverage polygon).

9.9 Failure Analysis

A PHAST sweep-order bug corrupts a fraction of one-to-all distances (I20); isochrone shape bugs are visual but drive service-area / coverage decisions — gate on the golden GeoJSON; blast radius is every isochrone/one-to-all query.

9.10 Operational Notes

Isochrones are the analytics/coverage surface (delivery zones, store catchments); expose phast_sweep_ms, isochrone_nodes, isochrone_polygons; cap budgets to bound cost. Real systems: Valhalla (R4) and GraphHopper (R3) expose isochrone APIs.

Phase 10 — CRP (Customizable Route Planning) + Hub-Labeling Contrast

10.1 Objectives

Implement Customizable Route Planning (PR5): a metric-independent multilevel partition + overlay topology (computed once), fast customization of overlay weights (seconds) for a live metric, and an exact overlay query (~1–2 ms). Contrast CH (Phase 6–Phase 7): CRP recustomizes for traffic in seconds where CH needs a full rebuild (minutes–1 h). Also document the Hub Labeling (HL) / Pruned Landmark Labeling alternative (PR13) as a fastest-query index — the tradeoff: HL answers via O(label-size) table merges (fastest of all techniques, no graph search) but stores large per-node label sets (tens of GB continental) and is not cheaply customizable — so CRP is chosen for live-traffic; a full HL build is PhaseDeferred("Phase 10 — CRP (Customizable Route Planning) + Hub-Labeling Contrast").

10.2 Detailed Implementation Steps

  • crp/partition.rs — metric-independent multilevel partition (e.g. 4 levels) via inertial flow (project coords on a line, min-cut between extremes, ADR-17) + natural cuts (PUNCH-style); assert cells disjoint + covering + nested (I9, P11).
  • crp/overlay.rs — for each cell, identify boundary vertices and the overlay-arc shape (which boundary pairs connect); build the multilevel overlay graph topology (metric-independent).
  • crp/customize.rs — bottom-up: compute each overlay arc weight as the shortest path within the cell between its boundary vertices for the current base metric (I10, P10); parallel over cells; produce a Metric.
  • crp/query.rs — bidirectional Dijkstra over {original edges in source/target cells} ∪ {overlay arcs at the coarsest applicable level}; unpack overlay arcs down to original edges.

10.3 Deliverable

route build --crp (topology once) + route customize --traffic feed.json (seconds) + route query --algo crp; recustomization swaps the Metric atomically (ArcSwap). The customization mechanism ships; live-traffic feed adapters are PhaseDeferred("Phase 10 — CRP (Customizable Route Planning) + Hub-Labeling Contrast").

10.4 Acceptance Criteria

Identical cost to the oracle (I1); customization < 5 s on the continental graph (M3); query 1–2 ms (M2); overlay arc weights == in-cell shortest distances (I10); a traffic change reflected after a seconds-scale customize (no topology rebuild).

10.5 Conformance Fixtures

crp/partition_valid.json (disjoint/covering/nested checks); crp/overlay_example8.json; crp/customize_vs_incell.json (overlay weight == in-cell Dijkstra); crp/traffic_update.json (weight change → new optimal path).

10.6 Pitfalls

Poor partition (large cuts → huge overlay → slow query/customize); cells not nested across levels (I9); overlay weight computed against the wrong metric snapshot; customization not parallel (too slow); forgetting to unpack overlay arcs (geometry wrong).

10.7 Performance Concerns

Partition quality dominates everything — invest in a real partitioner (ADR-17); customization is embarrassingly parallel over cells; the overlay is the hot query structure — keep it compact; Metric swap must not block readers (ArcSwap).

10.8 Edge Cases

s and t in the same lowest-level cell (pure local search, no overlay); boundary vertex shared by many cells; a cell with one boundary vertex; a metric that disconnects a cell internally.

10.9 Failure Analysis

A partition/overlay bug yields wrong CRP routes while CH stays correct — differential CRP-vs-oracle (I1) and overlay-vs-in-cell (I10) localize it to a cell/level.

10.10 Operational Notes

CRP is the live-traffic path: topology is stable, only Metric changes; expose customize_seconds, overlay_arcs, partition_cut_size; the runbook customization-too-slow.md points at partition quality. Real systems: CRP/MLD ships in OSRM (R1) and RoutingKit CCH (R2, R8) is the customizable-CH cousin.

Phase 11 — Alternative Routes + Turn-by-Turn Instructions

11.1 Objectives

Produce a small set of admissible alternative routes (not just the single optimum, PR11) and generate human-usable turn-by-turn instructions (maneuvers + road names) from a path. Constraint introduced: alternatives must be reasonable (limited overhead, limited sharing, locally optimal); instruction generation reads geometry + turn metadata, not just cost.

11.2 Detailed Implementation Steps

  • search/alternatives.rs — ship the penalty method (iteratively penalize edges of the found path, re-run a fast query, accept a new path if it meets admissibility) and via-node / plateau (find shared sub-paths "plateaus" on the bidirectional search, route via plateau endpoints). Admissibility tests: total length ≤ (1+ε)·optimum, sharing with optimum ≤ σ, each segment locally optimal (PR11). Full via-node alternatives with rigorous local-optimality tests are PhaseDeferred("Phase 11 — Alternative Routes + Turn-by-Turn Instructions").
  • search/instructions.rs — maneuver detection: at each via node compare in/out bearings → classify turn (left/right/slight/straight/U-turn/roundabout exit n); aggregate consecutive same-road segments ("continue 1.2 km on Main St"); attach road names/refs carried from OSM tags through the builder; emit an ordered maneuver list with distance/time per step.
  • bearing/geometry helpers reuse the Haversine/coord math (§8.1, P4, Phase 3).

11.3 Deliverable

route query --alternatives 3 returns the optimum + up to 3 admissible alternatives; route query --instructions emits a turn-by-turn maneuver list (JSON), road-name-aggregated.

11.4 Acceptance Criteria

Each alternative passes the admissibility tests: length ≤ 1.15× optimum (ε=0.15), sharing ≤ 0.80 of edges with the optimum (σ=0.80), locally optimal on its own corridor; the optimum is always returned and is exact (I1); maneuver classification matches instr/maneuvers_grid.json at all 12 fixture junctions; instruction distances sum to the path length within 1 m.

11.5 Conformance Fixtures

alt/penalty_three.json (optimum + 3 alternatives with metrics); alt/admissibility.json (a rejected too-similar candidate); instr/maneuvers_grid.json (turn classifications); instr/roundabout.json; instr/road_name_aggregation.json.

11.6 Pitfalls

Alternatives that are trivial detours (fail sharing/overhead tests) or that are not shortest on their own corridor (fail local optimality); maneuver mis-classification at slip roads / forks; road-name flapping (over-segmented instructions); roundabout exit miscount; U-turn maneuver vs penalized U-turn-edge confusion (Phase 5).

11.7 Performance Concerns

The penalty method re-runs a fast (CH/CRP) query per alternative — bounded by --alternatives k; plateau detection reuses one bidirectional search; instruction generation is O(path length), cheap relative to search.

11.8 Edge Cases

No reasonable alternative exists (return only the optimum); a path with no turns (single instruction); degenerate roundabout; a path entirely on one road (one aggregated maneuver); s==t (empty instruction list).

11.9 Failure Analysis

A bad alternative is a UX problem, not a correctness one (the optimum is still exact); an instruction bug ("turn left" where right is meant) is a real safety issue — gate maneuver fixtures hard; blast radius is guidance, not routing distance.

11.10 Operational Notes

Alternatives/instructions are the navigation surface; expose alternatives_returned, alternatives_rejected, maneuvers_emitted. Turn-by-turn voice/visual narration remains a downstream concern (§1 non-goals). Real systems: GraphHopper (R3) and Valhalla (R4) generate guidance from a similar maneuver pass.

Phase 12 — Persistence (Index Serialization / mmap) + Observability

12.1 Objectives

Make the routing index durable and fast-loading: serialize the CH/CRP/graph/ALT/TTF structures to the versioned custom binary format (ADR-18), load via mmap for near-instant warm starts and atomic rebuild swaps; and wire observability — query latency, settled-node count, preprocessing time — end to end. Constraint introduced: on-disk layout is now a compatibility surface (I18); metrics are a first-class output (P14).

12.2 Detailed Implementation Steps

  • index/format.rs + writer.rs — little-endian, aligned arrays, section table; header {magic, version, extract_sha, profile_id, techniques bitset, n, m} (I18, ADR-18); CRC over each section.
  • index/loader.rs — mmap the file (zero-copy slices into head/edges/up/down/labels); validate magic + version (refuse mismatch, I18); lazily fault pages; Arc<RoutingIndex> shared read-only (I17). Atomic rebuild = write new file + atomic rename + swap the Arc.
  • obs/metrics.rs — metrics facade (ADR-27): per-query settled, relaxed, stalled, unpacked, queue_max, latency_us; build-time preprocess_seconds, shortcut_ratio, partition_cut, index_bytes, customize_seconds.
  • obs/trace.rs — tracing spans (ADR-26) around build/query, feature-gated, no-op in core.

12.3 Deliverable

route build writes a mmap-friendly index; routed/CLI load it in < 100 ms cold / instant warm; every query and build emits the metric set; route stats --verbose dumps header + telemetry.

12.4 Acceptance Criteria

Index write→mmap-load round-trips every structure bit-exactly; version/magic mismatch refused (I18); warm load is instant, cold < 100 ms (M9, §4); the index is Send+Sync, shared & across threads with no interior mutation (I17); metrics emitted for all query types.

12.5 Conformance Fixtures

index/full_roundtrip.bin (CH+CRP+ALT+TTF → reload → identical queries); index/version_mismatch.bin (refused); index/truncated.bin (rejected, no over-read); obs/metrics_golden.json (expected counters for example8 queries).

12.6 Pitfalls

Misaligned mmap arrays (UB / slow unaligned loads — assert alignment); endian assumptions (pin little-endian); forgetting to bump version on a layout change (silent corruption on old readers — I18); a metric on the hot path that allocates (latency spike — counters must be lock-free/atomic); page-fault storms on first query after a cold mmap (pre-touch hot pages optionally).

12.7 Performance Concerns

mmap gives zero-copy and shared-page residency across query threads (no per-thread index copy); aligned SoA arrays preserve the §8.2 cache discipline; CRC validation is one-time at load; metric counters are per-thread atomics merged on scrape (no contention on the hot loop).

12.8 Edge Cases

A partially written index (crash mid-write) — the atomic rename guarantees readers see only the old or the fully-new file; a version-N reader vs version-N+1 file (refuse, I18); an index larger than RAM (mmap + lazy fault, page cache evicts cold sections); concurrent rebuild + serve (atomic Arc swap, in-flight queries finish on the old index).

12.9 Failure Analysis

A format/version bug corrupts loads cluster-wide — caught by the round-trip + version-mismatch fixtures before deploy; an mmap alignment bug is platform-specific (gate on CI across x86_64/aarch64); blast radius of a bad index is every query until rollback (atomic swap back to the previous index file).

12.10 Operational Notes

The index file is the unit of versioning, deployment, and atomic swap (P6, I18); rebuilds are immutable-artifact swaps (like a replicated read-only segment); expose index_bytes, index_version, load_ms; the runbook wrong-route-after-rebuild.md checks the header SHAs first.

Phase 13 — Conformance + Differential Testing + Benchmarking + CLI/HTTP Service

13.1 Objectives

Reach the production bar: differential conformance (every speedup technique's result == plain-Dijkstra ground truth on random OD pairs, I1/I20), many-to-many distance matrices (bucket-based CH, PR10, the last batched shape), fuzzing of all parsers/queries, a benchmark suite (preprocessing time/space, query-latency distribution) with regression gates, and the optional routed read-only HTTP service.

13.2 Detailed Implementation Steps

  • conformance/ harness — for a large random OD sample assert cost(dijkstra) == cost(bidir) == cost(astar) == cost(alt) == cost(ch) == cost(crp) (I1), td == td-oracle (I1 analog), and phast/matrix == oracle (I20, I1); dump the OD pair + both costs + divergent prefix on any mismatch.
  • batch/matrix.rs — bucket-based CH (PR10): one backward CH search per target fills buckets at meeting nodes; one forward CH per source scans buckets → |S|×|T| matrix at µs/cell (M11); reuses CH query (Phase 7). RPHAST restriction for one-to-many targets.
  • fuzz targets pbf_parse, profile_apply, ttf_eval, query_random (no panic, no wrong path); ASAN; CI smoke + nightly long-run (≥ 24 h, M14).
  • benchmarks/ — criterion suites + fixed OD sets; record preprocessing time/space and the query-latency distribution (p50/p95/p99); flamegraphs; regression thresholds gate CI.
  • service/main.rs — routed: mmap an index, serve concurrent read-only /route, /isochrone, /matrix, /table (OSRM/GraphHopper-shaped JSON), behind feature="service".

13.3 Deliverable

A conformance-green, fuzzed, benchmarked engine with a CLI and an optional HTTP service; route matrix emits a |S|×|T| matrix; make oracle-diff is the release gate.

13.4 Acceptance Criteria

Zero exactness mismatches across the OD sample for every technique (I1, I20) — every CH/A*/ALT/CRP/PHAST/matrix result equals the Dijkstra ground truth; matrix cells == oracle pairwise distances at µs/cell warm (M11, §4); ≥ 24 h fuzz with no crashes/panics (M14); benchmarks meet §4 latency targets (Dijkstra ms, CH µs) and gate regressions; routed serves concurrent queries with the index shared read-only (I17).

13.5 Conformance Fixtures

conformance/graph/random_od_oracle.json (master differential set); per-technique *_vs_oracle.json; batch/matrix_small.json (full pairwise vs oracle); batch/phast_vs_oracle.json; fuzz/corpus/; benchmarks/od_sets/; service/golden_responses/.

13.6 Pitfalls

Oracle and fast path disagreeing only on ties (fix the tie-break I19, not the oracle); fuzz corpus too small (seed from real extracts); benchmark variance (pin CPU governor, warm cache, fixed OD); matrix bucket collisions mishandled; the service mutating shared state (must be read-only, I17).

13.7 Performance Concerns

The full OD differential sweep is long — shard across CI; the matrix reuses one backward search per target (the bucket trick) — never |S| full Dijkstras; the service shares one mmap'd index across worker threads (no per-thread copy); per-query scratch is pooled (P13).

13.8 Edge Cases

A technique correct on small graphs but divergent at continental scale (run the sweep on a real extract); a fuzz input that is valid PBF but a pathological graph (huge degree); concurrent customize + query (atomic Metric swap); |S| or |T|=1 (degenerate matrix); a disconnected OD pair in the sample (both must report Disconnected, I14).

13.9 Failure Analysis

Any exactness mismatch blocks release (I1); triage by technique + OD pair + divergent prefix; the differential harness pinpoints which preprocessing structure (CH shortcut, CRP overlay, ALT bound) is wrong; a fuzz panic is a parser bug (P7); benchmark regression is a perf bug, gated separately.

13.10 Operational Notes

routed is the deployment surface: mmap'd immutable index, atomic swap on rebuild, read-only sharing; expose all search-space + per-technique metrics (P14); the Dijkstra oracle ships forever for route --validate in production. Deployment Topology, Canary, Rollback, Migration

  • Topology: routed workers each mmap the same immutable index (shared page cache); a stateless load balancer fans queries; preprocessing runs on a separate offline build host.
  • Canary: deploy a new index to one worker; run the differential oracle sample + compare query latency vs the fleet before fleet-wide swap.
  • Rolling upgrade: new index written + atomically renamed; workers swap the Arc<RoutingIndex>; in-flight queries finish on the old index (no blocking).
  • Rollback: keep the previous index file; swap the Arc back (seconds).
  • Migration: index-format version bump requires rebuilding the index for the new binary (I18); the binary refuses an older/newer format rather than misreading it.

Mental Models & First Principles

  • MM1 — A road network is a near-planar sparse graph with an emergent hierarchy; CH ordering discovers that hierarchy, it does not impose one. Predicts: order quality, not code cleverness, dominates CH speed. Bug class without it: uniform/random contraction order → shortcut explosion, blown preprocessing time and memory. Applied in Phase 6, ADR-11.
  • MM2 — A shortcut is a memoized subpath, not a new fact; CH is dynamic programming over path concatenation, exactly like compiler constant-folding. Predicts: unpacking must reproduce the exact original edges, never an approximation. Bug class without it: treating shortcuts as opaque distances and losing geometry/turn fidelity on unpack. Applied in Phase 6, Phase 7, I7/I8.
  • MM3 — Preprocessing buys a view of the graph, not a smaller graph; CRP's overlay is a materialized query plan, exactly like a database query-optimizer's plan cache. Predicts: customization cost scales with plan-rebind cost (cheap), not with graph size. Bug class without it: treating CRP as "CH but slower" and missing why it is chosen for live traffic. Applied in Phase 10, ADR-12, P10.
  • MM4 — Admissibility is a promise about the future (never overestimate to the goal); consistency is a promise about consecutive steps. Conflating them causes silent A* correctness bugs that present as performance bugs (extra re-expansions) rather than wrong answers, or vice versa. Applied in Phase 3, Phase 4, I4/I5.
  • MM5 — FIFO is what makes "time" behave like a total order for shortest-path purposes; break FIFO and Dijkstra's core exchange argument breaks with it. Predicts exactly which correctness argument fails (settled-node finality) when probe data isn't repaired. Applied in Phase 8, I11, P9.
  • MM6 — CSR is a graph frozen into a columnar database: "ALTER TABLE" (structural edit) is expensive, "SELECT" (traversal) is nearly free. Predicts that any workload requiring frequent graph edits is a poor fit for this design regardless of query speed. Applied in §8.2, Phase 0, ADR-3.
  • MM7 — The Dijkstra oracle is not a testing convenience, it is the specification; every optimization is a compiler correctness proof against it. Predicts that "the fast path disagrees with the oracle" is always a bug in the fast path, never grounds to "fix" the oracle. Applied in Phase 2, Phase 13, I1, P2.
  • MM8 — A road network's "difficulty" is measured in cut size, not node count; CRP/partition quality is the real scaling variable, not graph size. Predicts that a bigger-but-well-partitioned continent can customize/query faster than a smaller-but-badly-cut region. Applied in Scalability Analysis, ADR-17, Phase 10.

Back-of-Envelope Capacity Model

Twelve numbers, each derived from the System Constraints table (§4), formula shown:

  1. CSR edge-array bytes = m × 8 B = 120 M × 8 B = 0.96 GB (from §4 edge count × Edge{u32,u32} size).
  2. CSR head-array bytes = (n+1) × 4 B ≈ 50 M × 4 B = 0.2 GB (from §4 node count).
  3. Coords-array bytes = n × 8 B (two i32) = 50 M × 8 B = 0.4 GB (from §4 node count, ADR-6).
  4. Total warm graph-only index = edges + head + coords = 0.96 + 0.2 + 0.4 = ≈ 1.56 GB (sum of 1–3).
  5. ALT table memory = 2 · k · n · 4 B; with k=16 landmarks: 2×16×50 M×4 B = 6.4 GB (from §4's stated formula, matches M13).
  6. CH shortcut memory = m × 1.25 × 8 B (midpoint of the 1.0–1.5× ratio, M8) = 120 M × 1.25 × 8 B ≈ 1.2 GB additional.
  7. Per-query scratch (plain Dijkstra) = n × (4 B dist + 4 B parent) = 50 M × 8 B = 0.4 GB per in-flight full-graph search (worst case, before pooling).
  8. Plain-Dijkstra concurrent-search ceiling at a 16 GB scratch budget = 16 GB / 0.4 GB = ≈ 40 concurrent full searches (derived from 7; motivates why CH, not plain Dijkstra, is the production query path).
  9. CH concurrent-search ceiling at the same 16 GB budget = touched-set ≈ few hundred nodes × 8 B ≈ 2.4 KB/search ⇒ 16 GB / 2.4 KB ≈ 6.7 M concurrent CH searches (derived from the M1 few-hundred-settled-node target, contrasted with 8 — the reason pooled SearchSpace reset is O(touched), P13).
  10. Cold index load time (SSD ≈ 2 GB/s sequential) = 1.56 GB / 2 GB/s ≈ 0.78 s worst-case fully-faulted read, vs the < 100 ms M9 target achieved because mmap lazily faults only the pages a query actually touches (derived from 4).
  11. CRP customization work = cells × avg-in-cell-Dijkstra-cost, parallelized over P cores ⇒ wall time ≈ (cells × cost) / P; at thousands of cells and sub-ms per-cell Dijkstras on a 32-core host this lands in the 0.5–5 s M3 target (derived from the partition granularity implied by §4's CRP query settled-node count).
  12. Theoretical single-core CH query throughput = 1000 ms / 0.5 ms per query = 2000 qps/core; at 32 cores ≈ 64,000 qps theoretical ceiling before contention/networking overhead (derived from M1's 0.1–0.5 ms typical latency).

Alternative Architectures (Roads Not Taken)

1. Tiled hierarchical graph + query-time dynamic costing (Valhalla-style, R4).

+--------+  +--------+  +--------+
| TILE 1 |  | TILE 2 |  | TILE 3 |   (baldr: hierarchical geographic tiles,
+--------+  +--------+  +--------+    coarser tiles for long-haul edges)
     \          |          /
      \         |         /
     +-----------------------+
     | THOR: A*/bidir search |   costing function evaluated PER-EDGE
     | over tiles, dynamic   |   AT QUERY TIME (elevation, live rules,
     | per-request costing   |   vehicle profile — no CH shortcuts)
     +-----------------------+

Regime where it wins: deployments needing rich, request-time-configurable costing (elevation-aware cycling, per-vehicle live restrictions) where the cost function itself changes per request faster than any customization mechanism could track. Real system: Valhalla (R4). Why rejected here: this blueprint optimizes for sub-millisecond exact query latency on a small number of well-defined metrics (P1); dynamic per-request costing without precomputed shortcuts cannot hit the M1 target, and this blueprint's live-traffic need is served more cheaply by CRP customization (seconds, not per-request).

2. Highway Hierarchies / Highway Node Routing (Sanders & Schultes, PR12).

level 2:  ======highway-only skeleton======
level 1:      \\   core roads   //
level 0:  (original graph, all roads)
query: search up through levels, prune low-importance roads early

Regime where it wins: when full witness-search contraction (CH) is too slow to run on the available build hardware, but a coarser, cheaper-to-compute multi-level highway extraction is affordable and "good enough" query speed (tens of ms, not sub-ms) is acceptable. Real system: the original Sanders/Schultes prototype, the direct historical precursor to CH. Why rejected here: CH (PR4) strictly dominates it in query latency for the same exactness guarantee once the one-time contraction cost is paid, and the M7 preprocessing budget (minutes–1 h) is affordable on this project's assumed single-box build host (§4).

3. Hub Labeling / 2-hop labels (Delling et al. 2014, PR13; surveyed in Bast et al. 2016, PR14).

each node v: OUT-label(v) = {(hub, dist)...}   IN-label(v) = {(hub, dist)...}
query(s,t): merge OUT-label(s) x IN-label(t), min over shared hubs   (O(label size), no graph search)

Regime where it wins: read-dominated deployments where the metric almost never changes and query volume vastly exceeds update frequency — the O(1)-ish table-merge query is the fastest known technique, faster even than CH. Real system: the Hub Labeling construction and results described by Delling, Goldberg, Pajor & Werneck (PR13). Why rejected here: label sets are tens of GB continental and are not cheaply customizable — a live-traffic update effectively requires relabeling — which directly conflicts with this project's Phase 10 requirement for seconds-scale traffic recustomization (ADR-12).

4. Arc-flags region-based pruning (Lauther 2004, PR15; Hilger et al. 2009, PR6).

regions:  [ R1 ][ R2 ][ R3 ][ R4 ]   (static partition)
per edge: K-bit flag "lies on a shortest path INTO region r"
query: prune any edge whose flag for target's region is unset

Regime where it wins: memory-constrained, offline, single-metric deployments (historically, in-vehicle navigation systems) where a coarse static partition is affordable to precompute and recompute is rare. Real system: the technique described by Lauther (2004) and Hilger et al. (2009), historically used in offline in-vehicle navigation before CH became the mainstream production technique. Why rejected here: arc-flags' pruning power is weaker than CH's shortcut-based search-space reduction for the same preprocessing budget, and — like Hub Labeling — a live-traffic metric change requires recomputing the region shortest-path trees, which conflicts with the seconds-scale customization requirement that CRP (ADR-12) satisfies instead.
