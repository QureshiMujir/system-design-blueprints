1. Goal & Scope

Lex is a protocol-level trust substrate for autonomous AI agents transacting across vendor boundaries. It defines a DID-rooted agent identity format (Agent Passport), a signed and hash-chained per-agent action record (SignedActionLog), a machine-readable bilateral agreement format with a formal clause sublanguage (Constitution), a negotiation protocol that binds two agents to an executable agreement (MicroContract), and a federated model-judge dispute-resolution network with zero-knowledge evaluation proofs (Adjudication Mesh). Two agents built by different vendors can thereby establish verifiable identity, log actions non-repudiably, bind themselves to explicit machine-readable rules, and resolve disputes without a shared parent company or shared jurisdiction of convenience.

Phase-0 deliverable — numbered modules shipped by the end of Phase 0 (§12):

  1. spec/00-charter.md — the four-primitive charter and terminology lock.
  2. lex-actionlog-py v0.0.x — reference hash-chain + signing kernel (Python).
  3. conformance/ harness skeleton — the test-vector runner every later SDK must pass.
  4. did:lex method draft — resolution rules (registration with W3C is Phase 1, §13).

System boundaries:

  • Provides: identity issuance format, signed action logging, machine-readable bilateral contracts, dispute adjudication, evidence packaging for human courts.
  • Delegates: model inference for judge opinions (Lex specifies the opinion schema, §11, not the model itself), anchor-chain consensus (to Ethereum L1/L2 validators), sovereign law.
  • Does NOT provide: an agent runtime/framework, model hosting or inference-as-a-service, a general-purpose blockchain, a consumer-facing app, a substitute for sovereign courts.

Non-goals (permanent, unless re-scoped by a superseding ADR): building agents; hosting models; running a chain; replacing courts; underwriting insurance directly.

Deployment model: Issuer, Aggregator, Constitution Registry, Negotiation Broker, Mesh Coordinator, and Mesh Node are each independently deployable services (§10); every one is self-hostable (Docker/OCI, ADR-15 §9) or consumable via a hosted convenience tier (P6, §6).

Target users/operators: agent framework vendors (integrate the SDK), enterprises (self-host Issuer/Aggregator), independent mesh-node operators (run Mesh Node for stake rewards), insurance carriers and regulators (read-only APIs, Phase 8–9).

Later phases unlock: cross-vendor binding contracts (Phase 4–5), automated dispute resolution (Phase 6–7), underwriting-grade telemetry and regulator visibility (Phase 8–9).

Recommended language: Rust for every spec-critical service (Issuer, Aggregator, Mesh Node, Mesh Coordinator) — memory safety without GC pauses in the signing/verification hot path, and a mature no_std story for edge/embedded agent SDKs (ADR-01, §9). Python for the first reference SDK and academic/pilot tooling — fastest path to a runnable, readable reference implementation (ADR-02, §9). Rejected: Go (no no_std embedded story; GC pauses unacceptable in the signing hot path); JVM languages (cold-start/packaging friction for a self-hostable single-binary Issuer); C/C++ (unacceptable memory-safety risk in a cryptographic-signing codebase built solo with AI assistance and no dedicated security team).

Prerequisites (systems knowledge required to build this): applied cryptography (digital signatures, hash functions, zk-SNARKs), distributed systems (BFT quorum, replicated logs), PKI/credential-revocation design, and formal-language design for the Lex Clause Language (LCL) grammar (§8).

Estimated timeline: Phase 0 in 4 weeks; the full ten-phase system (Phase 0–9, §12–§21) in approximately 78 weeks (~18 months) of solo-plus-AI-assisted engineering effort.

Deferred features, each flagged PhaseDeferred("§N.s") and registered in the Deferred Features Register (§35): ISO/IETF standards-body engagement PhaseDeferred("§21.3 Deliverable"); sovereign-immunity attestation handling PhaseDeferred("§13.8 Edge Cases"); PLONK/STARK zk-proof migration PhaseDeferred("§19.10 Operational Notes"); multi-language spec translation PhaseDeferred("§21.1 Objectives"); full reinsurance-market data product PhaseDeferred("§20.3 Deliverable").

2. Why Build This

Unique systems knowledge it teaches: cross-organizational trust without a shared root of authority — the problem TCP/IP, X.509, and DNS solved for computers, and contract law and arbitration solved for humans, now applied to a party neither side fully controls (an autonomous agent). Building Lex forces mastery of append-only hash-chained logs under adversarial replay (§8, §22), BFT-adjacent quorum selection under operator collusion (§18, §22), zero-knowledge proofs used as a check on process not outcome (MM6 §30, §19), and content-addressed, canonicalized documents that must stay byte-identical across independent implementations (I5 §7, §8).

Why it matters architecturally/historically: every layer humans built for cross-party trust — TCP/IP (transport), X.509/PKI (identity), contract law (agreement), arbitration bodies (dispute resolution) — took decades and assumed human-paced disputes (courts, weeks-long arbitration). Autonomous agents act at machine speed and volume; a protocol that assumes human timescales cannot keep pace. Lex asks what each of those four layers looks like when the actor is non-human and the dispute rate is orders of magnitude higher.

Engineering muscles it builds: designing invariants that hold under a Byzantine judge pool (§7); building a formal clause language with deterministic canonicalization (§8); reasoning about anchor-cost economics — anchor only what's disputed (§32 C8) instead of writing every event to a chain; designing revocation with a hard latency SLO (I11, M10) instead of "eventually."

Concrete cross-links to sibling systems: shares the append-only hash-chained log problem with Certificate Transparency and Sigstore/Rekor (§31); shares the BFT-quorum-under-adversarial- operators problem with Tendermint/CometBFT (§5, §18); shares the crowdsourced-adjudication problem with Kleros (§31, §34).

Calibration value: Lex is deliberately not a runtime or a chain — building it calibrates the difference between a protocol that must be adopted by others (spec-first, standards-track) and a product that only needs internal users; that distinction disciplines every ADR (§9) toward interoperability over convenience.

What Mastery Looks Like (competencies, each tied to the phase that builds it):

  • Design and canonicalize a content-addressed document format byte-identically across two languages — Phase 4 (§16).
  • Implement a hash-chained, replay-resistant signed log against a documented invariant set — Phase 2–3 (§14, §15).
  • Stand up a DID-rooted issuer with revocation-latency SLOs — Phase 1 (§13).
  • Build a stake-weighted, collusion-resistant quorum-selection algorithm — Phase 6 (§18).
  • Integrate a zk-SNARK as a process-integrity check, not a correctness oracle — Phase 7 (§19).
  • Reason about anchor-cost economics and dual-anchor censorship resistance — Phase 8 (§20).
  • Produce a court-admissible evidence package validated against real evidentiary rules — Phase 9 (§21).

Agent Runtime (untrusted). Runs the agent process; may be malicious, buggy, or compromised. Never crosses the trust boundary holding a private key (P14, §6); the SDK signs using a KMS/HSM-rooted key the runtime cannot extract (ADR-16, §9).

SDK (signing boundary). Constructs and signs ActionEnvelopes (§8), maintains the local hash chain, ships to the Aggregator synchronously, batched, or end-of-session.

Passport Issuer. Mints AgentPassport Verifiable Credentials bound to a DID; HSM-signed (ADR-16); publishes a revocation endpoint with a 60 s propagation SLO (I11, M10).

DID Registry. Resolves did:lex:/did:web:/did:key: identifiers to the public key material used to verify passport and envelope signatures (I3).

Aggregator. Append-only, ingest-time signature and hash-chain verification (I1–I3), periodic Merkle-root anchoring of disputed outcomes only (P4), never every action.

Constitution Registry. Content-addressed store (I5) for JSON-LD Constitutions; publishes by BLAKE3(JCS(canonical_form)) hash, never a mutable identifier (P11).

Negotiation Broker. Carries offer/counter/accept messages between two agents' SDKs and emits a signed MicroContract on mutual acceptance; optional — agents may negotiate peer-to-peer without a broker (Phase 5, §17).

Mesh Coordinator + Judge Pool. Selects a stake-weighted quorum (I7) of independently operated model judges per DisputeCase; each judge emits a structured opinion plus a zk proof of evaluation (I10); ties default to inconclusive (I13).

Insurance API / Regulator Dashboard / Court Evidence Package. Three read-only consumers of AdjudicationOutcome: a carrier claims trigger, a jurisdictionally-scoped aggregate dashboard, and a courtroom-admissible evidence bundle (Phase 8–9, §20–§21).

The one defining property: Lex is asymmetric by design — the write path (signing, hash- chaining, ingest) must scale to millions of entries/week at sub-20ms verification cost, while the dispute path (quorum selection, zk-proof, adjudication) is deliberately rare and expensive per-unit (P4, anchor-only-what's-disputed). Any design that makes the two paths symmetric in cost has broken the core economic assumption of the protocol.

6. Design Principles

  1. P1 — Neutrality above all. Lex must be acceptable to a frontier lab, a sovereign government, an open-source project, and a small enterprise simultaneously. Tradeoff: forfeit exclusive deals and preferential integrations. Operational implication: every partnership contract is reviewed against this principle before signature. Violating it: the spec becomes one vendor's internal tool, destroying the standards-capture moat (§2).
  2. P2 — Spec before surface. Every commercial feature is downstream of a published, versioned spec; no closed-source feature requiring a closed-source format. Tradeoff: slower time-to-revenue. Violating it: the spec stops being the moat and becomes marketing collateral for a product.
  3. P3 — Cryptographic finality. Every artifact (passport, log entry, constitution, microcontract, outcome) is signed and independently verifiable offline with only public material. Tradeoff: no "trust us" convenience features. Violating it: any "trust the dashboard" surface becomes a single point of forgeable truth.
  4. P4 — Anchor only what is disputed. Default path is signed-but-not-anchored; only disputed outcomes and constitution registrations get an external-chain anchor. Tradeoff: routine actions have no chain-level finality, only aggregator-level. Violating it: cost and latency scale linearly with total action volume instead of dispute volume (§32 C8).
  5. P5 — Jurisdictional honesty. Constitutions and disputes name a jurisdiction; Lex never pretends to override sovereign law. Tradeoff: some disputes remain gated on slow sovereign process. Violating it: outcomes become legally unenforceable theater.
  6. P6 — No agent left behind. The free tier of the SDK and reference mesh must be usable by a hobbyist agent; identity is never gated behind a credit card. Tradeoff: subsidizes low-value usage. Violating it: Lex becomes an enterprise-only tool and loses the long-tail adoption that builds citation authority (§2).
  7. P7 — Adjudication transparency. Every AdjudicationOutcome publishes a redacted reasoning trace; black-box arbitration is not arbitration. Tradeoff: reasoning-trace storage and redaction engineering cost. Violating it: outcomes are unappealable fiat, defeating the court-admissibility goal (§21).
  8. P8 — Backwards compatibility from v1.0. Once a spec (Passport, ActionLog, Constitution, MicroContract) hits 1.0, it is extended, never broken; breaking changes ship as vN.0 with a 24-month dual-stack window. Tradeoff: legacy fields accumulate. Violating it: every integrator must re-certify on every release, destroying the "Lex Conformant" mark's value.
  9. P9 — Standards-track syntax from day one. Every spec is written to be IETF-publishable from its first draft. Tradeoff: more upfront rigor than a move-fast internal format needs. Violating it: Phase 9 standards submission requires a rewrite, wasting the accumulated citation authority.
  10. P10 — Fail-closed validation. Malformed or unverifiable envelopes are rejected at ingest, never logged as best-effort. Tradeoff: a buggy SDK's entries are dropped, not salvaged. Violating it: I1–I3 (§7) become advisory instead of enforced, and the aggregator's append-only guarantee is meaningless.
  11. P11 — Content-addressing over mutable identifiers. Constitutions and MicroContracts are identified by the hash of their canonical form, never mutated in place. Tradeoff: any amendment is a new document with a new address. Violating it: I5 (§7) cannot hold, and two parties can silently diverge on "the same" agreement's text.
  12. P12 — Federated judge diversity over throughput. Quorum selection favors operator and jurisdictional diversity over minimizing latency. Tradeoff: higher Time-to-Outcome (M7–M8) than a centralized judge pool would achieve. Violating it: a fast but concentrated judge pool is trivially capturable (T4, FM-4, §22–§23).
  13. P13 — Delegation depth bounding. Capability delegation chains are bounded to depth 5 (I6, §7). Tradeoff: some legitimate deep-delegation use cases (agent-of-agent-of-agent) are unsupported. Violating it: an unbounded chain makes blast-radius analysis after a compromise computationally unbounded.
  14. P14 — Minimal trusted computing base at the signing boundary. The agent runtime is always untrusted; only KMS/HSM-rooted key material crosses the signing boundary (ADR-16, §9). Tradeoff: raw-software-key mode exists for hobbyists but is flagged in the passport. Violating it: a single runtime compromise (T9, §22) becomes a silent, undetectable identity theft instead of a flagged, revocable event.

Malformed-Input Example

A submitted ActionEnvelope with sequence=4822 but prior_hash pointing to entry 4820 (skipping 4821) violates I1/I2. The Aggregator's chain-walk detects the discontinuity at ingest, rejects with actionlog_chain_break_total{agent_did=...} incremented, and quarantines the entry (FM-1, §23) rather than appending a best-effort record (P10 fail-closed).

Failure-Path Example

During OpinionsCollecting for DisputeCase 5e7d..., the zk-Proof Verifier rejects judge J4's proof (I10 violation): J4's operator shares infrastructure with two other quorum members (detected via the operator-diversity check, T4/FM-4, §22–§23). 12.6 Pitfalls

  • Running the property suite without a fixed RNG seed — non-reproducible CI failures. Pin a seed and log it on every run.

12.7 Performance Concerns

Empty chain (zero entries) must verify trivially true. A chain of exactly one entry has no prior_hash predecessor — define the genesis convention (prior_hash = blake3("")) in the charter now, since Phase 1+ Issuer/Aggregator code will assume it.

13.6 Pitfalls

  • Per-passport revocation-check API leaking which passport was checked (timing/traffic analysis) — mitigate via the batched revocation-list publication pattern (Aries lesson, §5).
  • Treating did:lex: resolution as safe once "registered" — registration and resolution security are separate; pin resolver logic to the spec, not to registry status (§5 ref-impl lesson #1).
  • HSM/PKCS#11 vendor quirks (session handle exhaustion under concurrent signing) — pool and cap concurrent HSM sessions explicitly rather than trusting the vendor SDK's defaults.

13.7 Performance Concerns

Issuance is HSM-bound (network round-trip to the HSM/KMS adds 5–20 ms per signature); batch non-urgent issuance requests where possible. Revocation-list publication must stay under the 60 s SLO (M10) even as the list grows — use an incremental Bloom-filter or delta-publication scheme (capacity math in §32 C9) rather than republishing the full list each cycle.

13.8 Edge Cases

Simultaneous revoke-and-verify race (a passport revoked at t=0 checked at t=0+ε before propagation) — I11's 60 s bound is a maximum, not a guarantee of t=0 visibility; downstream consumers (Aggregator) must treat a just-issued verification as provisionally valid, not final, until the propagation window elapses. Delegation cycles (A delegates to B delegates back to A) — rejected at issuance via cycle detection, not just depth counting (FM-12, §23).

13.9 Failure Analysis

Issuer key compromise (T10, §22) is the phase's most severe failure: detection via issuance-rate anomaly (§23 FM-3), automatic issuance freeze on threshold breach, followed by a manual root-key rotation ceremony and cascade-revocation of all post-compromise issuances. Blast radius is bounded by how quickly the anomaly detector fires — budget this detector's sensitivity against the M10 propagation SLO.

13.10 Operational Notes

Metrics: passport_issue_total, passport_verify_fail_total (I3), revocation_propagation_ seconds (I11). Runbook docs/runbooks/issuer-key-rotation.md documents the rotation ceremony. Rollback: issuer is stateless aside from Postgres + HSM key material — a bad deploy rolls back via standard blue/green without data migration (§25 Compatibility & Versioning).

14.6 Pitfalls

  • KMS signing latency variance (network-dependent) silently blowing the local M1 append- latency budget — separate "local append" (kernel-only) from "durable append" (post-KMS- round-trip) in the metric taxonomy so the two are not confused.

KMS round-trip dominates signing latency (5–20 ms typical); batch where the agent's workload tolerates it. Hash-chain verification (M4) is CPU-bound and embarrassingly parallel across independent agent chains — the verifier should shard by agent_did to use all cores.

14.9 Failure Analysis

17. Phase 5 — MicroContract Negotiation Protocol

17.1 Objectives

Ship the offer/counter/accept/abandon negotiation protocol, a reference broker (lex-broker), a peer-to-peer no-broker mode, and stake-based bonding against dispute-spam (Back's Hashcash framing, §5) at the negotiation layer. Duration: 6 weeks (weeks 33–38).

17.2 Detailed Implementation Steps

Define the negotiation message schema (offer, counter, accept, abandon) referencing a Constitution by content-address (I5, §7) and producing a signed MicroContract (§11) on mutual acceptance — both parties append a ConstitutionBound-equivalent ActionEnvelope entry to their own logs (I1–I3 preserved end-to-end, §3 data flow). Implement lex-broker as a trustless message relay — it cannot forge offers (every message individually signed) and never holds funds or capabilities (P3 cryptographic finality). Implement peer-to-peer mode (no broker) for agents that can reach each other directly. Handle double-sign attacks (a party signs two conflicting MicroContracts referencing the same offer) by making the offer itself content-addressed and single-use — a second acceptance of a consumed offer is rejected at the broker (or, in P2P mode, detectable by either party from the signed offer's nonce). Implement abandonment (a party withdraws mid-negotiation) as an explicit signed message, not a silent timeout, so abandonment is itself an auditable ActionEnvelope.

17.3 Deliverable

lex-broker service plus a P2P negotiation library, demonstrated in a two-party MicroContract negotiation across two different agent framework integrations, passing lex-microcontract- conformance.

17.4 Acceptance Criteria

100% pass on lex-microcontract-conformance (≥ 100 vectors: round-trips, double-sign attacks, abandonment); double-sign attack fixture set (20 cases) rejected 100% of the time; broker message relay latency p95 ≤ 100 ms (local network); zero MicroContracts bound without both signatures present (I-adjacent binding check).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
microcontract-happy-path.json offer→counter→accept valid signed MicroContract
microcontract-double-sign.json same offer accepted twice second acceptance rejected
microcontract-abandon.json party withdraws mid-negotiation signed AbandonEnvelope logged, no MicroContract produced
microcontract-p2p-noBroker.json negotiation without broker identical output to brokered path

17.6 Pitfalls

  • Treating broker silence (no relay confirmation) as equivalent to abandonment — a network partition is not consent to withdraw; require an explicit signed abandonment message (§17.2).
  • Reusing an offer's content-address as its single-use nonce without also binding a timestamp window — a replayed offer from an old, expired negotiation could otherwise be "accepted" long after context has changed.
  • Broker operators quietly logging plaintext offer contents beyond what's needed for relay — violates P3/P6 spirit even though the broker is "trustless" for forgery purposes; scope the broker's data retention explicitly in its self-host docs.

17.7 Performance Concerns

Negotiation round-trip latency is dominated by agent-side decision time, not protocol overhead; the broker's relay hop should stay well under 100 ms (§17.4) so it is never the bottleneck. P2P mode removes the broker hop entirely at the cost of requiring direct reachability between agents.

17.8 Edge Cases

Simultaneous counter-offers from both parties (race condition in a bidirectional negotiation) — resolved by requiring each counter-offer to reference the specific prior offer's content- address it responds to, making the negotiation a strict content-addressed chain, not a mutable shared state.

17.9 Failure Analysis

A stuck negotiation (one party stops responding without abandoning) has no automatic recovery by design — Lex does not impose a timeout-based auto-abandon, since that would let a network-blip silently kill a legitimate slow negotiation; the operational answer is a dashboard-visible "stale negotiation" alert for human/agent-controller follow-up, not silent protocol-level cancellation.

17.10 Operational Notes

Metrics: negotiation_double_sign_rejected_total, broker_relay_latency_seconds. No persistent broker state survives a restart by design (trustless relay, §17.2) — a broker restart mid-negotiation requires the agents to resume from their own signed message history.

19. Phase 7 — zk-Proof Integration & Slashing

19.1 Objectives

Integrate a Groth16/BN254 zk-proof (Groth 2016, §5) attesting that each judge opinion was produced from the supplied inputs (I10, §7), and implement the slashing protocol for judges who fail proof verification or are flagged for collusion. Duration: 8 weeks (weeks 49–56).

19.2 Detailed Implementation Steps

Design the "judge evaluated these inputs" circuit using circom (iden3 reference toolchain, §5 ref-impls) — the circuit attests to input-binding, not to judgment correctness (Thaler's proofs-vs-arguments distinction, §5; MM6, §30). Integrate snarkjs proof generation into lex-mesh-node's opinion-emission path and Groth16 verification into lex-mesh-coordinator's tally step, enforcing I10 (opinion discarded on proof failure). Run the circuit's trusted setup as a multi-party computation (mitigating the ref-impl's flagged pitfall, §5) with ≥ 9 independent contributors matching the testnet's operator diversity. Implement the slashing protocol: judges post stake at node registration; a proven-malfeasant judge (I10 failure, or a TSC-confirmed collusion finding from Phase 6) has a defined fraction of stake burned or redistributed to the affected dispute's parties.

19.3 Deliverable

A running zk-proof pipeline where every accepted opinion in the Phase 6 testnet carries a verified Groth16 proof, and a documented, executed slashing event against a deliberately misbehaving test judge.

19.4 Acceptance Criteria

zk-proof generation latency ≤ 2 s per opinion (M5) measured over 500 proofs; zk-proof verification latency ≤ 50 ms (M6); 100% of opinions with an invalid/missing proof are excluded from tally (I10) over a 200-case adversarial fixture set; trusted-setup MPC ceremony completes with ≥ 9 independent contributions, publicly attested.

19.5 Conformance Fixtures

Fixture Purpose Expected Output

19.6 Pitfalls

  • Mistaking "zk proof verifies" for "the judge's verdict is correct" — the proof only attests the judge processed the claimed inputs (MM6, §30); a judge can still render a bad-faith verdict on correctly-bound inputs. This is why I8 (conflict exclusion) and P12 (diversity) remain necessary even after zk integration.
  • Trusted-setup ceremony run by a single party "for speed" — reintroduces exactly the single-point-of-trust the zk proof was meant to remove; the MPC requirement (§19.2) is not optional.
  • Circuit constraint count growing unboundedly with opinion complexity, blowing the 2 s generation budget (M5) — bound the circuit's input size (e.g., a fixed-size action-log slice window) rather than accepting arbitrary-length inputs.

19.7 Performance Concerns

Groth16 proof generation is the most computationally expensive step in the dispute path (seconds, vs. sub-20ms for everything upstream, §4) — this is acceptable precisely because disputes are rare relative to actions (P4, §32 C6-C7); do not let proof-generation cost pressure erode the anchor-only-disputed economic model by, e.g., pre-generating proofs speculatively for undisputed actions.

19.8 Edge Cases

A judge's circuit inputs legitimately exceed the fixed-size window (a very long-running dispute's evidence slice) — the spec must define a windowing/pagination convention for large evidence sets rather than silently truncating evidence, which would bias verdicts.

19.9 Failure Analysis

Repeated proof failures from one judge (slashing fixture, §19.5) trigger automatic stake slashing; a single proof failure could be a transient bug rather than malfeasance, so the slashing threshold (3 consecutive failures, §19.5) is deliberately conservative to avoid punishing honest-but-buggy operators while still bounding a malicious operator's exposure window.

25. Compatibility & Versioning

Wire compatibility: every wire schema (§11) is additive-only post-v1.0 (P8) — new optional fields only; removing or repurposing a field requires a new major version with a 24-month dual-stack window. Storage compatibility: Aggregator and Registry storage schemas migrate via additive Postgres columns and object-store path versioning (v1/, v2/ prefixes), never in-place field reinterpretation. API stability: REST/gRPC contracts (ADR-06) follow SemVer; a minor version never removes a field or endpoint. Deprecation policy: a deprecated field/ endpoint is marked in the spec with a removal-eligible date ≥ 24 months out, mirrored in CHANGELOG.md. Rolling-upgrade guarantees: any two adjacent minor versions of lex-aggregator interoperate in the same Raft cluster for the duration of a rolling upgrade (§15.10); no two-version skip is supported without an intermediate hop.

29. Scalability Analysis

What stays constant vs. grows: signature-verification cost per entry is O(1) and constant regardless of network size (§4 M2); hash-chain rebuild is O(n) in an agent's own log length but embarrassingly parallel across agents (§14.7); Merkle-anchor construction is O(n) build / O(log n) per-proof in batch size (§32 C10); mesh quorum draw is O(operators) to weight-sample but bounded to a constant quorum size (I7, [3,21]) regardless of network size — this is the single most important scaling property, since it means dispute-resolution cost does not grow with total agent population, only with dispute count.

Named bottlenecks in order: (1) Mesh Coordinator cross-region fan-out latency as jurisdictional diversity requirements grow (§18.7, MM4 §30) — the first ceiling hit as the mesh federates further; (2) Aggregator Raft-replication write path as ingest volume approaches the M3 50,000/sec cluster target (§15.7); (3) Issuer HSM session throughput under issuance bursts (§13.7); (4) zk-proof generation latency (M5) if dispute volume ever approached ingest volume, which P4's anchor-only-disputed design structurally prevents (§32 C7).

Horizontal/vertical scaling: Aggregator scales horizontally by sharding on agent_did hash (embarrassingly parallel per §14.7); Mesh Nodes scale horizontally by onboarding new independent operators (P12, capped only by I8 conflict-exclusion pool size); Issuer scales vertically per jurisdiction (data-residency constraints limit horizontal sharding across jurisdictions, §24). Sharding/partitioning: Aggregator partitions by agent_did; Constitution Registry partitions by content-address prefix (uniform hash distribution, no hot-shard risk). Coordination overhead: Raft consensus overhead grows with replica count — capped at 3-5 replicas per Aggregator shard, more replicas trade availability for write latency without proportional benefit past that point. Practical ceiling and the levers beyond it: the practical ceiling on NSM growth (§4) is Aggregator ingest throughput (M3); the lever beyond it is horizontal shard count, not per-shard optimization, once M3's 50,000/sec/cluster is saturated — add shards, not faster hardware.

30. Mental Models & First Principles

  • MM1 — A passport is a claim, not a fact. The insight: identity documents assert, they don't guarantee; a passport's truth depends on the issuer's continued trustworthiness and the revocation channel's freshness. Predicts: revocation and issuer-chain trust must be first-class, not afterthoughts. Bug class without it: treating identity as permanent once issued. Applies in §13 (Phase 1 Issuer), I11 (§7).
  • MM2 — An action log is a ledger of intent, not truth. The insight: a signed entry proves the agent asserted an action happened, not that the physical/business outcome was as claimed. Predicts: disputes center on interpretation of a truthful-but-incomplete log, not just forged entries. Bug class without it: assuming "signed" means "undisputable." Applies in §8 Domain Model, §22 Threat Model.
  • MM3 — Anchoring is a scarcity decision. The insight: writing to an external chain is never free, so a protocol must decide what's worth that cost. Predicts: the anchor-only- disputed design (P4) is not an optimization, it's the model. Bug class without it: cost scaling linearly with ingest instead of dispute volume. Applies in §4 System Constraints, §32 Capacity Model, §21 Phase 9.
  • MM4 — Quorum size trades latency for capture-resistance. The insight: every additional judge in a quorum raises the cost of collusion but also raises fan-out latency. Predicts a latency/security curve, not a single "right" quorum size. Bug class without it: optimizing quorum size for speed alone, reintroducing capture risk. Applies in I7 (§7), §18 Phase 6.
  • MM5 — A constitution is a compiled contract, not prose. The insight: natural-language agreements are ambiguous at machine speed; a formal predicate layer (LCL) is what makes automated evaluation possible. Predicts the need for a grammar with deterministic semantics. Bug class without it: two agents disagreeing on what "the same" clause means. Applies in §8 Domain Model, §16 Phase 4.
  • MM6 — A zk proof proves computation happened, not that it was correct. The insight: Groth16/BN254 attests input-binding, not judgment quality. Predicts collusion risk persists even with zk integration. Bug class without it: over-trusting zk as a correctness oracle instead of a process-integrity check. Applies in §19 Phase 7.
  • MM7 — Delegation is capability erosion. The insight: every hop in a delegation chain is a chance for scope creep or compromise amplification. Predicts deeper chains carry proportionally higher risk, justifying a hard depth bound. Bug class without it: unbounded blast-radius analysis after a compromise. Applies in P13 (§6), §22 Threat Model.
  • MM8 — Standards capture is a lagging, not leading, indicator. The insight: citation authority (ISO/IETF adoption) follows deployed usage; it cannot be won by lobbying alone. Predicts premature standards engagement wastes scarce founder attention before Phase 8-9 telemetry exists to point to. Bug class without it: chasing prestige before proof. Applies in §2 Why Build This, §21 Phase 9.

Certificate Transparency made one decision differently: log everything (every cert) and rely on gossip/audit to catch equivocation, rather than adjudicate. It wins in the regime where the only question is "did this happen" (issuance), not "was this action a breach of an agreement" — a question CT was never designed to answer.

Sigstore/Rekor made the same "log everything, adjudicate nothing" choice but for software artifacts, using keyless OIDC identity instead of long-lived keys. It wins for supply-chain provenance where the identity is a CI pipeline, not an autonomous decision-maker whose actions can be disputed on substance.

Hyperledger Aries/Indy wins in closed enterprise-consortium identity exchange where a credential's validity, not an agent's behavioral history, is the object of trust — it has no answer for "did the agent that held this credential act within the rules," which is Lex's core question.

Arbitrum's fraud-proof rollup wins when every disputed computation is a deterministic state transition that can be re-executed and checked on-chain step-by-step — a regime Lex explicitly rejects for its primary path (§34 Alt. 1) because agent-to-agent disputes turn on natural-language clause interpretation, not deterministic re-execution.

Kleros wins for low-stakes, high-volume, purely on-chain micro-disputes (e.g., marketplace escrow releases) where crowdsourced juror judgment and gas-cost tolerance are both acceptable — it is Lex's closest real-world analogue for the Adjudication Mesh, and the primary comparator considered and rejected as the sole mechanism (§34 Alt. 1) because Lex's dispute volume and latency targets (M7-M8) require model judges, not human jurors, as the default tier.

32. Back-of-Envelope Capacity Model

  • C1 — Weekly ActionLog ingest bandwidth at Phase-3 NSM target. Bandwidth = NSM_target × entry_size / seconds_per_week = 10,000,000 × 620 bytes / 604,800 s ≈ 10.25 KB/s sustained; at a 10x diurnal burst multiplier ≈ 102.5 KB/s peak (§4 entry-size row).
  • C2 — Annual cold-storage footprint at Phase-3 volume. 10,000,000/week × 52 weeks × 620 bytes ≈ 322.4 GB/year uncompressed; ×3 replication (Postgres + object-store + backup, §24) ≈ 967 GB/year.
  • C3 — Aggregator peak throughput vs. M3 target. 10,000,000/week ÷ 604,800 s/week ≈ 16.5 entries/sec average; ×100 burst multiplier (pilot-observed diurnal pattern) ≈ 1,650 entries/sec peak — vs. M3's 50,000/sec cluster target, a ≈30x headroom margin.
  • C4 — Aggregator FD budget at max concurrency. §4's 10,000 concurrent-connections/node ceiling × 1.2 (internal RPC + DB pool overhead) ≈ 12,000 FDs/node — the ulimit floor for ADR-04's deployment.
  • C5 — Signature-verification headroom vs. ingest peak. M2's 8,000 verify/sec/core ÷ C3's 1,650 entries/sec peak ≈ 4.8x single-core headroom — no horizontal scaling of the verification step alone is needed at Phase-3 volume.
  • C6 — zk-proof storage per dispute. I7's default quorum (7 judges) × ≈200 bytes/proof (Groth16/BN254 proof size) ≈ 1.4 KB/dispute; at a Phase-8 target of 1,000 disputes/week (§38 Milestone Summary) → 1.4 MB/week zk-proof storage.
  • C7 — Mesh judge-evaluation load. 1,000 disputes/week × quorum 7 = 7,000 judge- evaluations/week ÷ 604,800 s ≈ 0.012 evaluations/sec network-wide average — confirming quorum size (I7) is bounded by capture-resistance (MM4, §30), not by throughput need.
  • C8 — Anchor cost budget. Dual-anchor policy applies to an estimated 5% of 1,000 disputes/week exceeding the $10k threshold = 50 dual-anchored outcomes/week × 2 chains × ≈$0.05/L2-anchor-tx (typical low-fee-L2 order of magnitude) ≈ $5/week anchoring cost — confirming P4 keeps anchor cost sub-linear in ingest volume (cf. C1's 10M/week ingest).
  • C9 — Revocation-list working-set size. At the Phase-3 AAP target of 100,000 active passports (§4), a Bloom filter sized for 100,000 entries at a 1% false-positive rate ≈ 120 KB in memory — small enough to sit in an L2-cache-adjacent working set for hot revocation checks.
  • C10 — Merkle-anchor batch size at the M9 interval. C3's 1,650 entries/sec peak × 600 s (10-min interval, M9) ≈ 990,000 entries/batch upper bound; a Merkle tree over that batch needs ⌈log2(990,000)⌉ = 20 levels.

34. Alternative Architectures (Roads Not Taken)

Alt. 1 — Fully on-chain smart-contract adjudication.

DisputeCase --> [ Smart Contract: evidence hash + juror stake ] --> On-chain Vote --> Verdict

Regime where it wins: low-value, high-volume, purely on-chain micro-disputes (marketplace escrow releases) where gas cost per dispute is acceptable and the claim is objectively verifiable from on-chain state alone. Real system: Kleros (§31). Rejected for Lex's primary path because most agent-to-agent disputes turn on natural-language clause interpretation (§8 Domain Model) that on-chain jurors voting via a smart contract cannot evaluate at the volume/latency Lex targets (M7-M8); Lex's model-judge mesh is used instead, with Kleros-style on-chain adjudication left as a viable tier-3 escalation path for narrow, objectively- verifiable clause types (registered as a future extension, not built in Phase 0-9).

Alt. 2 — Centralized trusted arbiter.

DisputeCase --> [ Single Company's Arbitration Desk ] --> Verdict (published, not verifiable)

Regime where it wins: low dispute volume, latency-sensitive, single-brand-trusted environments (e.g., a single marketplace's internal dispute desk). Real-system analogue: a digitized American Arbitration Association (AAA) case-management flow. Rejected because a single arbiter — however competent — cannot satisfy P1 (neutrality) once Lex spans competing vendors; it also reintroduces the single-point-of-capture risk the federated mesh (§18) was built specifically to remove.

Alt. 3 — Blockchain-native identity and action log (no off-chain Aggregator).

Every ActionEnvelope --> On-chain transaction --> Global consensus finality per action

Regime where it wins: fully trustless environments where every party is willing to pay gas per action and where "every action must be globally, immediately final" is a hard requirement (e.g., on-chain derivatives settlement). Real system: a fully on-chain order book such as dYdX v3's predecessor generation. Rejected because Lex's NSM target (10M+ entries/week, §4) would be economically infeasible at per-action gas cost — this is precisely why P4 (anchor only what's disputed) exists.

Alt. 4 — Peer-to-peer web-of-trust, no central spec body.

Agent A <--mutual signing--> Agent B <--mutual signing--> Agent C   (no registry, no mesh)

Regime where it wins: small, high-trust communities where reputational webs suffice and no enterprise/regulator legibility is required. Real system: PGP/GPG web-of-trust keyservers. Rejected because Lex's beachhead (agent framework vendors needing enterprise-procurement-grade identity, §2) and later regulator/insurance consumers (§20-§21) require a legible, auditable root of trust — a property a purely peer-to-peer web of trust structurally cannot provide at enterprise/regulatory scale.

36. Glossary

  • AAP — Active Agent Passport: a passport with at least one signed action in the last 7 days.
  • Adjudication Mesh: the federated network of model-judge operators that resolves disputes per a constitution's adjudication_policy (§18).
  • AdjudicationOutcome: the signed, content-addressed verdict produced by the mesh (§8, §11).
  • ActionEnvelope: the signed, hash-chained unit an SDK produces per agent action (§11).
  • Agent Passport: the DID-rooted, Verifiable-Credential-bundled identity of an autonomous agent.
  • Anchor: publication of a content hash to an external chain for finality (P4).
  • BFT — Byzantine Fault Tolerance: the property of reaching agreement despite malicious participants (Lamport/Shostak/Pease, §5).
  • Bloom Filter: a probabilistic set membership structure used for the revocation-list working set (§32 C9).
  • CIF — Constitutions In Force: registered constitutions whose effective date has passed and whose expiry has not.
  • Constitution: a JSON-LD document specifying the rules of engagement between two parties' agents (§8, §16).
  • Content-address: an identifier equal to the hash of a document's canonical form (I5).
  • Controller: the human or organization legally responsible for an agent (controller_did).
  • DID — Decentralized Identifier: W3C-standard URI scheme for self-sovereign identity.
  • Delegation Chain: the ordered list of capability-delegation links bounded to depth 5 (I6).
  • DisputeCase: a filed allegation that a MicroContract's terms have been breached (§8).
  • Ed25519: the default digital-signature scheme used for passport and action-log signing.
  • Groth16: the zk-SNARK proving system used for opinion-evaluation proofs (ADR-22, §19).
  • Hash-chain: the linked-by-hash structure making an ActionLog tamper-evident (I1).
  • HSM — Hardware Security Module: a physical device custodying signing keys (ADR-16).
  • Issuer: an entity authorized to mint Verifiable Credentials for agent passports (§13).
  • JCS — JSON Canonicalization Scheme: RFC 8785, the deterministic serialization used for content-addressing (I5).
  • KMS — Key Management Service: a cloud-hosted signing-key custody service (ADR-16).
  • LCL — Lex Clause Language: the Datalog-subset formal predicate language for constitution clauses (§8, §16).
  • Merkle Root: the single hash summarizing a batch of entries for anchoring (§32 C10).
  • Mesh Coordinator: the service that draws quorums and tallies opinions (§18).
  • Mesh Node: an independently operated participant in the Adjudication Mesh.
  • MicroContract: a binding executable agreement between two agents under a constitution (§8, §17).
  • NSM — North-Star Metric: SignedActionLog entries per week from production (non-pilot) agents (§4).
  • Nonce: a single-use value preventing offer/action replay (§17.8).
  • Passport Issuer: a service that mints Agent Passport VCs (§13).
  • PKCS#11: the standard interface for HSM-backed signing operations (ADR-16).
  • Quorum: the constitution-defined number of mesh judges required for an outcome (I7).
  • Revocation List: issuer-published list of passports no longer valid (§13, I11).
  • RTO — Recovery Time Objective: maximum acceptable time to restore service after failure (§24).
  • Self-hash: the hash of an ActionLog entry's own content, chained by the next entry's prior_hash (§11).
  • Sequence: the strictly increasing per-agent entry counter (I2).
  • Sigstore/Rekor: the transparency-log reference system informing Aggregator design (§5, §31).
  • SignedActionLog: the per-agent, hash-chained, signed log of agent actions.
  • Slashing: the economic penalty applied to a judge's staked collateral for proven malfeasance (§19).
  • Stake-weighting: biasing quorum selection probability by a judge's posted collateral (§18).
  • Sybil Attack: the creation of many cheap fake identities to gain disproportionate influence (Douceur, §5; T5, §22).
  • TSC — Technical Steering Committee: the governance body holding the merge bit on spec changes (§27).
  • TTO — Time-to-Outcome: elapsed time from DisputeCase filing to AdjudicationOutcome.
  • VC — Verifiable Credential: W3C-standard cryptographically verifiable claim.
  • Weak Subjectivity: the checkpoint mechanism preventing long-range consensus-history rewrites (Tendermint/CometBFT lesson, §5, §18).
  • zk proof: a zero-knowledge proof asserting a statement without revealing the underlying witness — here, that a judge evaluated the supplied inputs (I10, MM6 §30).
