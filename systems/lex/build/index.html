⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the public repository skeleton (§10), lock the four-primitive charter, and ship a runnable hash-chain + signing kernel that later SDKs (Phase 2–3) extend rather than redesign. Duration: 4 weeks. Introduces no external network surface yet — this phase is single-process, local-only.

Deliverable

A cloned lex/ repository where make test runs the kernel's unit and property suite green, lex-actionlog-py can append 1,000 locally-generated entries and a separate verifier process can rebuild and validate the chain from zero using only public key material.

Acceptance

conformance/actionlog/kernel-1k.json fixture (1,000 entries) verifies with zero I1/I2 violations; property suite runs ≥ 10,000 randomized cases with zero shrink-failures; make test completes in ≤ 90 s on a 4-core CI runner; charter document reviewed and merged (1 approving review, solo + AI-assist per §20-equivalent Build & Release Engineering, §27).

Fixtures
Fixture Purpose Expected Output
kernel-1k.json baseline 1,000-entry chain verifies clean, 0 violations
kernel-broken-chain.json entry 512's prior_hash altered I1 violation detected at position 512
kernel-sequence-gap.json sequence jumps 40→42 I2 violation detected at position 41
kernel-bad-sig.json entry 700 signature corrupted 1 byte I3 violation, verify() returns false
Pitfalls
  • Treating BLAKE3 and SHA-256 as interchangeable in fixtures — they are not byte-compatible; pin BLAKE3 as default (ADR/§9 crypto suite) and generate fixtures with the pinned hash only.
  • Off-by-one in sequence starting at 0 vs. 1 — lock the convention (0-indexed) in the charter before any fixture is generated, or every downstream SDK diverges (P8 risk pre-empted early).
  • Running the property suite without a fixed RNG seed — non-reproducible CI failures. Pin a seed and log it on every run.

⬜ Phase 1 — Agent Passport Spec & Issuer Service §13

Objectives

Freeze the did:lex method draft, the AgentPassport JSON-LD schema (§11), and ship lex-issuer — a self-hostable Rust service that mints, resolves, and revokes passports. Duration: 8 weeks (weeks 5–12). Introduces the first network-facing trust boundary (Issuer, §3).

Deliverable

A running lex-issuer binary (Docker/OCI, ADR-15) that issues an AgentPassport VC, resolves its did:lex: identifier, and propagates a revocation within the M10 SLO — demonstrated end-to-end against lex-passport-conformance.

Acceptance

100% pass on lex-passport-conformance (≥ 200 vectors); revocation-propagation p99 ≤ 60 s (I11, M10) measured over 100 revocation events; Ed25519 verification throughput ≥ 8,000 ops/sec/core (M2) on the issuance-verification path; zero I6 violations accepted (delegation depth ≤ 5 enforced at issuance, 100% of a 500-case delegation-chain fixture set).

Fixtures
Fixture Purpose Expected Output
passport-issue-basic.json happy-path issuance valid VC, resolvable DID
passport-revoke-latency.json 100 revoke events, timed p99 ≤ 60s
passport-delegation-depth-6.json delegation chain of depth 6 rejected, I6 violation
passport-expired-reject.json action from expired passport rejected, I4 violation
Pitfalls
  • Per-passport revocation-check API leaking which passport was checked (timing/traffic analysis) — mitigate via the batched revocation-list publication pattern (Aries lesson, §5).
  • Treating did:lex: resolution as safe once "registered" — registration and resolution security are separate; pin resolver logic to the spec, not to registry status (§5 ref-impl lesson #1).
  • HSM/PKCS#11 vendor quirks (session handle exhaustion under concurrent signing) — pool and cap concurrent HSM sessions explicitly rather than trusting the vendor SDK's defaults.

⬜ Phase 2 — SignedActionLog SDK: Python Reference §14

Objectives

Harden the Phase 0 kernel into a publishable lex-actionlog-py package with a KMS signing adapter, and freeze spec/02-actionlog.md v0.9 for public RFC. Duration: 4 weeks (weeks 13–16). Builds directly on the Phase 0 correctness kernel (§12).

Deliverable

lex-actionlog-py 0.1 on PyPI, KMS-backed, passing 100% of lex-actionlog-conformance, with ≥ 80% line coverage on the signing/hash-chain module.

Acceptance

Hash-chain rebuild/verify speed ≥ 1,000,000 entries/sec/core (M4) on the reference verifier; KMS-adapter round-trip (sign + verify) p99 ≤ 20 ms (§4 verification latency ceiling, KMS network hop included); 100% conformance pass on ≥ 300 vectors; PyPI package installs cleanly on a clean Python 3.11 virtualenv with zero manual steps.

Fixtures
Fixture Purpose Expected Output
actionlog-kms-1k.json 1,000 KMS-signed entries verifies clean
actionlog-replay.json entry 200 resubmitted verbatim rejected, I2 violation (duplicate sequence)
actionlog-reorder.json entries 50/51 swapped in transit rejected, I1 violation
actionlog-cross-sdk.json fixture generated once, verified by 2 independent implementations byte-identical hash/signature fields
Pitfalls
  • KMS signing latency variance (network-dependent) silently blowing the local M1 append- latency budget — separate "local append" (kernel-only) from "durable append" (post-KMS- round-trip) in the metric taxonomy so the two are not confused.
  • Treating "80% line coverage" as sufficient for a signing module — line coverage does not catch adversarial-input classes; pair with the property suite from Phase 0 (ADR-11).
  • JSON key ordering non-determinism breaking cross-language byte-identical hashing before JCS is formally adopted (JCS lands in Phase 4, §16) — pin a temporary deterministic key-sort rule in the Python kernel now so Phase 3's Rust/JS ports match without rework.

⬜ Phase 3 — SignedActionLog SDK: Rust + JS Parity & Aggregator §15

Objectives

Port the Python kernel to Rust (lex-actionlog-rs, no_std-compatible core + C-FFI for embedded agents) and JavaScript/TypeScript (@lex/actionlog), and ship lex-aggregator — the first durable, append-only, multi-agent ingest service. Duration: 8 weeks (weeks 17–24).

Deliverable

Three interoperable SDKs (Python/Rust/JS) at v0.1+, and a 3-node lex-aggregator cluster ingesting entries from all three with I1–I3 enforced and a working Merkle-anchor scheduler.

Acceptance

Cross-SDK conformance: 100% byte-identical hash/signature output across all 3 SDKs on a shared 500-vector fixture set; Aggregator cluster ingest throughput ≥ 50,000 entries/sec (M3); Aggregator availability ≥ 99.9% over a 30-day soak test (§24); Merkle anchor batch interval ≤ 10 min (M9) measured over 100 cycles.

Fixtures
Fixture Purpose Expected Output
cross-sdk-500.json 500 entries, 3 SDKs byte-identical hash/sig across all 3
aggregator-partition.json 1 of 3 nodes killed mid-ingest cluster remains available, no I1 violations on rejoin
merkle-anchor-batch.json 990,000-entry batch (§32 C10) Merkle root computed, 20-level tree
no-std-ffi-roundtrip.json Rust core via C-FFI, embedded harness identical output to native Rust path
Pitfalls
  • Divergent floating-point or locale-dependent timestamp formatting across Python/Rust/JS breaking byte-identical hashing — pin RFC 3339 UTC formatting (ADR-19) with no locale dependence in any SDK.
  • Raft leader-election flapping under network jitter causing spurious unavailability — tune election timeouts against the measured cross-region RTT budget (§4, 150 ms).
  • Anchoring every batch regardless of dispute status (violating P4) because "it was easy to just anchor everything" — the scheduler must gate on dispute status, not batch readiness alone.

⬜ Phase 4 — Constitution Format & Registry §16

Objectives

Freeze the Constitution JSON-LD context, define and implement the Lex Clause Language (LCL — a Datalog subset, Lessig's "code is law" framing applied, §5/§2), and ship the content- addressed Constitution Registry. Duration: 8 weeks (weeks 25–32).

Deliverable

spec/03-constitution.md v1.0, a running Constitution Registry service, an LCL reference interpreter passing lex-constitution-conformance, and 10 seed templates.

Acceptance

100% pass on lex-constitution-conformance (parsing, canonicalization, clause-language semantics, inheritance) across ≥ 150 vectors; canonicalization + hash compute ≤ 5 ms/doc (M11); zero registry writes accepted with a mismatched content-address over a 1,000-write adversarial fixture run (I5); clause linter flags 100% of a 20-case adversarial-clause fixture set (T3).

Fixtures
Fixture Purpose Expected Output
constitution-canon-roundtrip.json canonicalize→hash→re-canonicalize identical id both passes
constitution-bad-hash.json claimed id doesn't match content rejected, I5 violation
constitution-clause-cycle.json inherited clause graph has a cycle rejected at registry write
constitution-linter-onesided.json obligation clause with no remedy path flagged by linter (T3)
Pitfalls
  • Unicode normalization differences between canonicalizer implementations (Rust unicode- normalization crate vs. a naive byte-sort) producing different hashes for "the same" text — pin NFC normalization explicitly in the JCS pipeline before hashing (FM-9, §23).
  • Allowing clause inheritance cycles to be caught only at evaluation time instead of registry-write time — by then two parties may already believe they're bound to different effective rule sets.
  • LCL predicates that reference fields not present in the ActionEnvelope schema (§11) — the interpreter must fail closed (P10) on an undefined-field reference, not treat it as vacuously true.

⬜ Phase 5 — MicroContract Negotiation Protocol §17

Objectives

Ship the offer/counter/accept/abandon negotiation protocol, a reference broker (lex-broker), a peer-to-peer no-broker mode, and stake-based bonding against dispute-spam (Back's Hashcash framing, §5) at the negotiation layer. Duration: 6 weeks (weeks 33–38).

Deliverable

lex-broker service plus a P2P negotiation library, demonstrated in a two-party MicroContract negotiation across two different agent framework integrations, passing lex-microcontract- conformance.

Acceptance

100% pass on lex-microcontract-conformance (≥ 100 vectors: round-trips, double-sign attacks, abandonment); double-sign attack fixture set (20 cases) rejected 100% of the time; broker message relay latency p95 ≤ 100 ms (local network); zero MicroContracts bound without both signatures present (I-adjacent binding check).

Fixtures
Fixture Purpose Expected Output
microcontract-happy-path.json offer→counter→accept valid signed MicroContract
microcontract-double-sign.json same offer accepted twice second acceptance rejected
microcontract-abandon.json party withdraws mid-negotiation signed AbandonEnvelope logged, no MicroContract produced
microcontract-p2p-noBroker.json negotiation without broker identical output to brokered path
Pitfalls
  • Treating broker silence (no relay confirmation) as equivalent to abandonment — a network partition is not consent to withdraw; require an explicit signed abandonment message (§17.2).
  • Reusing an offer's content-address as its single-use nonce without also binding a timestamp window — a replayed offer from an old, expired negotiation could otherwise be "accepted" long after context has changed.
  • Broker operators quietly logging plaintext offer contents beyond what's needed for relay — violates P3/P6 spirit even though the broker is "trustless" for forgery purposes; scope the broker's data retention explicitly in its self-host docs.

⬜ Phase 6 — Reference Adjudication Mesh: Judge Pool & Quorum Coordinator §18

Objectives

Ship lex-mesh-node and lex-mesh-coordinator: the reference implementation of stake- weighted, conflict-of-interest-excluded quorum selection (I7, I8, §7) over a federated model- judge pool. Duration: 10 weeks (weeks 39–48) — the largest phase, reflecting the BFT-adjacent design surface (Lamport/Shostak/Pease, Castro & Liskov, §5).

Deliverable

A 9-node federated mesh testnet resolving a cross-vendor DisputeCase end-to-end in under 60 s median (M7), with a published operator-diversity dashboard (P12 visibility).

Acceptance

Time-to-Outcome p50 < 60 s for routine disputes (M7) measured over 100 test disputes across the 9-node testnet; zero quorum draws violating I8 (conflict-of-interest exclusion) over a 1,000-draw adversarial fixture set; quorum size stays within I7's [3,21] bound on 100% of constitution-driven draws; tie-vote fixture routes to inconclusive + appeal path 100% of the time (I13).

Fixtures
Fixture Purpose Expected Output
mesh-quorum-draw-1000.json 1,000 adversarial COI scenarios 0 I8 violations
mesh-tto-routine.json 100 routine disputes, 9-node testnet p50 < 60s
mesh-tie-vote.json 3-3-1 vote split outcome = inconclusive, routed to appeal
mesh-partition-stall.json 4 of 9 nodes unreachable quorum draw radius expands, no silent stall (FM-5)
Pitfalls
  • Stake-weighting that inadvertently favors large, well-capitalized operators into every quorum — defeats P12's diversity goal even while nominally "random." Cap any single operator's per-quorum draw probability regardless of stake size.
  • Treating "9 nodes" as sufficiently decentralized without checking jurisdictional/operator overlap — federation count alone doesn't satisfy I8's spirit if 9 nodes share one hosting provider.
  • Silent quorum-fill timeout with no operator-visible signal — must surface as PartitionStalled (§8, DisputeCase State Transitions), never an indefinite hang.

⬜ Phase 7 — zk-Proof Integration & Slashing §19

Objectives

Integrate a Groth16/BN254 zk-proof (Groth 2016, §5) attesting that each judge opinion was produced from the supplied inputs (I10, §7), and implement the slashing protocol for judges who fail proof verification or are flagged for collusion. Duration: 8 weeks (weeks 49–56).

Deliverable

A running zk-proof pipeline where every accepted opinion in the Phase 6 testnet carries a verified Groth16 proof, and a documented, executed slashing event against a deliberately misbehaving test judge.

Acceptance

zk-proof generation latency ≤ 2 s per opinion (M5) measured over 500 proofs; zk-proof verification latency ≤ 50 ms (M6); 100% of opinions with an invalid/missing proof are excluded from tally (I10) over a 200-case adversarial fixture set; trusted-setup MPC ceremony completes with ≥ 9 independent contributions, publicly attested.

Fixtures
Fixture Purpose Expected Output
zkproof-valid-500.json 500 valid opinion+proof pairs 100% verify, ≤ 50ms each
zkproof-tampered-input.json proof generated, then opinion input altered post-hoc verification fails, I10
zkproof-missing.json opinion submitted with no proof opinion excluded from tally
slashing-malfeasance.json judge fails proof 3 consecutive times stake slashed per policy
Pitfalls
  • Mistaking "zk proof verifies" for "the judge's verdict is correct" — the proof only attests the judge processed the claimed inputs (MM6, §30); a judge can still render a bad-faith verdict on correctly-bound inputs. This is why I8 (conflict exclusion) and P12 (diversity) remain necessary even after zk integration.
  • Trusted-setup ceremony run by a single party "for speed" — reintroduces exactly the single-point-of-trust the zk proof was meant to remove; the MPC requirement (§19.2) is not optional.
  • Circuit constraint count growing unboundedly with opinion complexity, blowing the 2 s generation budget (M5) — bound the circuit's input size (e.g., a fixed-size action-log slice window) rather than accepting arbitrary-length inputs.

⬜ Phase 8 — Production Mesh Hardening & Insurance Integration §20

Objectives

Productionize the mesh to SLA (99.9% availability, tiered judge pools) and ship the insurance carrier integration layer. Duration: 12 weeks (weeks 57–68).

Deliverable

A production-grade, 25-operator, 5-jurisdiction mesh meeting 99.9% availability over a 30-day window, with tier-1/2/3 routing operational and one insurance-bridge integration live against a test carrier endpoint.

Acceptance

Mesh availability ≥ 99.9% over 30 days (§4); dual-anchor outcomes confirm on both chains within M9's interval-adjacent budget (≤ 10 min each); insurance-bridge webhook delivery success rate ≥ 99.5% over 1,000 test triggers; anomaly-detection gate blocks 100% of a 50-case synthetic arbitrage fixture set (T8) prior to claim approval.

Fixtures
Fixture Purpose Expected Output
mesh-tier-routing.json dispute complexity classifier routed to correct tier (1/2/3)
dual-anchor-10k.json $12k remedy outcome anchored on 2 independent chains
insurance-webhook-1000.json 1,000 trigger events ≥ 99.5% delivery success
insurance-arbitrage-50.json synthetic claim-without-loss patterns 100% blocked pre-approval
Pitfalls
  • Tier misclassification routing a genuinely complex dispute to tier-1's fast-but-shallow judges — validate the complexity classifier against a labeled historical dispute set before trusting it in production.
  • Dual-anchor "independence" undermined by both chosen chains sharing a sequencer/bridge operator — verify true operational independence, not just distinct chain IDs.
  • Insurance telemetry anonymization that's reversible via correlation with public passport DIDs — anonymization must survive a determined re-identification attempt, not just remove obvious identifiers.

⬜ Phase 9 — Regulator Dashboard & Court-Admissible Evidence Package §21

Objectives

Ship the read-only, jurisdictionally-scoped Regulator Dashboard and the court-admissible evidence package generator; validate admissibility with cooperating law firms in ≥ 2 jurisdictions. Duration: 10 weeks (weeks 69–78) — the final phase before standards-body work (deferred, §35).

Deliverable

A running Regulator Dashboard with one pilot regulator connected read-only, and an evidence package validated as admissible-in-principle by cooperating counsel in ≥ 2 jurisdictions.

Acceptance

Dashboard query p95 latency ≤ 500 ms (M12); mTLS + PKI auth rejects 100% of a 100-case unauthorized-client fixture set (T12); evidence package independently re-verified offline by a third party with zero Lex-hosted service dependency, on 20/20 test bundles; admissibility review completed and documented favorably in ≥ 2 jurisdictions.

Fixtures
Fixture Purpose Expected Output
dashboard-query-p95.json 1,000 aggregate queries p95 ≤ 500ms
dashboard-unauth-100.json 100 unauthorized client-cert attempts 100% rejected
evidence-package-offline-verify.json 20 bundles, no network access 20/20 verify independently
evidence-drilldown-no-court-order.json per-action query without court order rejected at Issuer gate
Pitfalls
  • Dashboard aggregate metrics granular enough to re-identify individual agents when cross- referenced with public passport data — apply k-anonymity-style thresholds on any breakdown small enough to be identifying.
  • Evidence-package verification silently depending on a Lex-hosted API (e.g., a "check this hash online" convenience) — breaks the "verifiable by a third party with only public material" requirement (P3); the offline-verification path must be first-class, not a fallback.
  • Assuming admissibility rules are uniform across jurisdictions — the Federal Rules of Evidence (US), CPR (UK), and EU-member equivalents differ materially on chain-of-custody formality; validate per-jurisdiction, not once globally.
