⬜ Phase 0 — Skeleton & Correctness Kernel §12

Objectives

Stand up the repo skeleton, governance docs, CI, and licensing (P10, ADR-11, ADR-25). Land the minimal correctness kernel — SequenceNumber/ValueKind/FileId/Level (§11.1), Error enum (§11.10), a stub Wal and MemTable sufficient for a round-trip smoke test. No compaction, no SSTable yet.

Deliverable

make bootstrap && make build && make test exit 0 on a clean checkout. "Hello, MemTable" smoke test: open a temp dir, append Put(seq=1,"hello","world") to the stub WAL, fsync, reopen, replay, memtable.get returns Some("world"). A BUILD_PLAN.md filed at repo root cites ADR-01, 02, 03, 05, 06, 08, 11, 14, 17.

Acceptance

make test passes with ≥1 test exercising the full smoke-test round trip. CI green on a fresh clone in ≤10 minutes wall-clock (ci.yml). 9 governance files present and non-empty (README, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY, CHANGELOG, LICENSE, Makefile, Dockerfile, Cargo.toml).

Fixtures
  • conformance/corpora/wal/00-single-put.bin — one valid Put record; runner asserts recovered (key,value) matches.
  • conformance/corpora/wal/01-bad-crc.bin — CRC bit-flipped; runner asserts Error::WalCorrupt.
Pitfalls
  • Treating the stub WAL/MemTable as throwaway and skipping fsync "because it's Phase 0" — the smoke test must mean what it says (P1) from day one, or Phase 1 inherits an untested contract.
  • Under-specifying Error's shape now and bolting on variants ad hoc later — every later phase's additions must still satisfy P10; design the enum's shape, not every variant, now.
  • Skipping cargo-deny (ADR-25) at Phase 0 — dependency drift is cheapest to catch before the graph grows.

⬜ Phase 1 — WAL Adapter & Group Commit §13

Objectives

Ship the engine's single durable write boundary (I1, P1, P6). Every put/delete/ single-delete/range-delete passes through it before reaching the memtable. Implements group commit, fsync discipline, recovery replay, and truncation.

Deliverable

A Wal open/append/fsync/replay/truncate round trip exercised by tests. cargo bench baseline for append throughput at payload sizes 64B/256B/1KiB/4KiB.

Acceptance

100K-iteration smoke test appends a known pattern, fsyncs, restarts, replays, asserts equality. Group-commit test: 64 concurrent writers sustain ≥ 100,000 records/s at payload_len=256 on the reference NVMe (M1/M2 precursor, §30). Recovery test: StrictRedo rejects a manifest-durable truncation with Error::WalTruncated.

Fixtures
  • conformance/corpora/wal/single-put.bin, group-commit.bin (16 interleaved batches; seq-order recovery asserted).
  • conformance/corpora/crash/kill-mid-append.bin — torn pwrite; partial record discarded.
  • conformance/corpora/crash/kill-after-fsync.bin — fsync'd record survives, next pwrite does not; post-recover state matches recorded post-fsync state (I1).
Pitfalls
  • Ordering trap: fsync(WAL); ack(writer) is correct; ack(writer); fsync(WAL) is not (P1) — the group-commit leader must hold every follower on the condvar until fsync returns.
  • CRC must cover seq itself; otherwise a corrupt header's seq is trusted and recovery walks into an unbounded sequence-number space.
  • fdatasync returning success is durable to the disk's volatile cache, not necessarily to the platter (MM6, §24 T6) — document in docs/threat-model/overview.md, never paper over it.

⬜ Phase 2 — Skip-List MemTable & Immutable Queue §14

Objectives

Ship the in-memory write absorber: single-writer, multi-reader skip-list keyed by InternalKey (§11.2), plus the immutable-memtable queue and rotation protocol that feeds Phase 3's flush path.

Deliverable

A MemTable surviving a 1M-insert random workload with zero leaked arena bytes, zero lost keys (oracle: BTreeMap). A 64-thread concurrent-reader benchmark against a writing memtable.

Acceptance

Read throughput under concurrent write load does not collapse below 80% of no-write-load baseline. approximate_memory_usage() is within 10% of actual heap footprint at 64 MiB write_buffer_size. Immutable queue depth 2 + active gives a 3× burst capacity before WriteStall (§34 #5 derives the exact byte number).

Fixtures
  • conformance/corpora/ops/memtable-random-1k.jsonl — 1K random ops, expected post-state.
  • conformance/corpora/ops/memtable-snapshot-isolation.jsonl — writes interleaved with snapshot reads; each snapshot read must return the value visible at its pin point (I10).
Pitfalls
  • The arena's lifetime must outlive every reader; the retirement protocol must wait on a refcount before dropping the arena, or a reader mid-iteration use-after-frees.
  • Seq-descending order inside a user-key bucket means get must scan forward, never stop at the first hit — stopping early misses an older-but-still-visible version under a pinned snapshot (I10).
  • Range deletes live in the side table, not the skip-list — a writer that forgets to update the side table on delete_range silently drops the range delete. PhaseDeferred("§14.6: lock-free concurrent skip-list (RocksDB InlineSkipList style); required past 1M writes/s on a many-core host") — registered §37 row 1.

⬜ Phase 3 — SSTable Writer & Block Format §15

Objectives

Turn an immutable memtable (or a compaction output stream) into a sealed, immutable SSTable file (P2, I2): data blocks → filter block → metaindex block → index block → footer (§8.1).

Deliverable

An SstWriter round-tripping a 100K-entry SSTable with deterministic output bytes, recorded in conformance/corpora/sst/. A microbenchmark: 100 MiB of random KV pairs written in ≤ 2 s on the reference NVMe.

Acceptance

Byte-identical output across two runs given identical input order (conformance predicate, §21.3). Property test: random KV stream → SSTable → read back → matches. Write throughput ≥ 50 MiB/s single-threaded (feeds M3 bulk-ingest target, §30).

Fixtures
  • conformance/corpora/sst/100k-snappy.sst — known content; reader returns identical bytes.
  • conformance/corpora/sst/range-del-block.sst — one range delete; range-del block decodes to the recorded entries.
Pitfalls
  • Off-by-one on block-size target: stopping mid-entry produces an empty terminal block — always finish the entry that crosses the threshold.
  • Shortest-separator edge case a == b: return a unmodified; over-shortening produces a separator < max_key(block), breaking index lookup (§8.5 read-path relies on this invariant holding).
  • Directory fsync after rename is mandatory on Linux — without it, a crash can lose the rename even though the file itself is fsync'd (I2, §8.8).

⬜ Phase 4 — SSTable Reader & Bloom Filter §16

Objectives

Ship the read path's single entry to disk: open, parse footer, materialize index, expose per-key lookup and range iteration. Every read walks footer → index → filter → data block → entry (§8.5).

Deliverable

An SstReader point-lookup ≤5 µs warm / ≤100 µs cold on a 100K-entry SSTable on the reference NVMe (feeds M4/M6). Range-scan benchmark ≥1 GiB/s warm (feeds M7).

Acceptance

Bloom FPR ≤1.5% at bloom_bits_per_key=10 sampled against 10K never-inserted keys (conformance predicate §21.6). Footer parse rejects files <48 bytes with Error::BlockCorrupt, never panics.

Fixtures
  • conformance/corpora/sst/get-hit.jsonl — 1K (key, expected_value) pairs.
  • conformance/corpora/sst/get-bloom-miss.jsonl — 1K never-inserted keys; filter rejects every one modulo recorded FPR.
  • conformance/corpora/sst/scan-1k.jsonl — expected ordered (key,value) sequence.
Pitfalls
  • Block cache key must include file_id, not just offset — two SSTables can share an offset; keying on offset alone collides across files and returns wrong data.
  • Range-delete tracker must run after candidate emission, before the caller sees it — running it earlier as a per-source pre-filter misses deletes that apply across sources (I12). PhaseDeferred("§16.6: per-block prefix Bloom filters (RocksDB FilterPolicy); wins for prefix/time-range scan workloads") — registered §37 row 7.

⬜ Phase 5 — Merging Iterator, MVCC Snapshots & Range Deletes §17

Objectives

Ship the read path's single unification point: a read at snapshot S merges the active memtable, immutable memtables, L0, and L1+ into one ordered, snapshot-filtered, range-delete-aware stream (I10, I12). Ship the public Snapshot lifecycle — this blueprint's entire MVCC mechanism (P11, ADR-09).

Deliverable

A merging iterator producing ordered output across MemTable + 4 ImmMemTables + 8 L0 files + 6 L1+ levels. A long-running reader holds a snapshot for 1 hour while the writer performs 1M puts; the reader's view is unchanged at the end.

Acceptance

Property test: random put/delete/range-delete sequences, snapshots at random points, output compared against a BTreeMap oracle — zero mismatches over 1M generated cases. Forward iteration ≥2 GiB/s warm cache (feeds M7). Reverse scan throughput ≥50% of forward on warm data.

Fixtures
  • conformance/corpora/ops/merging-iter.jsonl, range-del.jsonl — multi-source workloads with expected snapshot reads / filtered keys.
  • conformance/corpora/e2e/snapshot-isolation.jsonl, snapshot-pins-files.jsonl — writer+reader interleaving; file-count does not drop until the snapshot drops.
Pitfalls
  • Heap must order by InternalKey, never user-key alone — user-key-only ordering produces stale reads (I10, §7 table).
  • Bottommost tombstone GC must consult min_live_snapshot, not the current sequence number — premature GC against a long-running snapshot is a correctness bug lasting until the snapshot drops (I6).
  • Snapshot's seq must be captured before the version is pinned — a concurrent put racing between capture and pin reads the wrong key set.
  • A snapshot does not pin WAL records — once a memtable is flushed, its WAL records can be truncated regardless of snapshots (P6); snapshots only pin SSTables and bound tombstone GC. PhaseDeferred("§17.2: full MVCC/OCC transactional layer — read-set tracking + commit-time validation on top of these snapshot reads") — registered §37 row 14.

⬜ Phase 6 — Manifest, VersionSet & Crash Recovery §18

Objectives

Ship the metadata-side durability primitive (P3, P6): every flush/compaction/WAL rotation produces a VersionEdit; the VersionSet applies edits in order and exposes the current Version via atomic Arc swap (I11).

Deliverable

A VersionSet applying 100K edits in ≤2 s without losing any (feeds M-mani milestone). A recovery test killing the engine at every byte boundary in a 10K-edit workload; post- recover state matches the recorded post-fsync state (M15 precursor).

Acceptance

24-hour soak: continuous flush+compact+periodic-snapshot+periodic-kill, zero missing files, zero orphan-file accumulation, zero manifest corruption (feeds M13). Recovery throughput ≥50,000 WAL records/s on open (M12).

Fixtures
  • conformance/corpora/manifest/single-edit.bin, snapshot-rotate.bin.
  • conformance/corpora/crash/kill-mid-current-rename.bin — post-recover state names a valid manifest (I11).
Pitfalls
  • CURRENT rename must precede the directory fsync — without the directory fsync, the rename itself is not durable on Linux (§8.8).
  • Manifest snapshot must include next_file_number and last_sequence — omitting either causes post-recover state to either re-allocate colliding file ids or skip sequence numbers visible to readers (I4).
  • Vacuum must snapshot Version before listing the directory, never after — reversing the order reintroduces the race it was designed to avoid.

⬜ Phase 7 — Leveled Compaction: Picker, Runner, Rate Limiter §19

Objectives

Ship the background pipeline that keeps I3 (level non-overlap) and bounded read/space amplification true (P4): the picker (which files), the runner (how to merge), the rate limiter (how fast), the output protocol (installing via the manifest).

Deliverable

A leveled picker driving a 1 GB random-write workload to steady state with write-amp ≤ 30× (derived §34 #1). A 4-thread parallel-compaction 24-hour soak: no L0 stall, no manifest growth past 100 MiB.

Acceptance

Write amplification ≤30× steady state (M10); space amplification ≤1.3× (M11). A YCSB-A benchmark stays within 20% of the no-compaction baseline throughput.

Fixtures
  • conformance/corpora/compact/leveled-l0-l1.jsonl — picker output matches recorded set.
  • conformance/corpora/compact/bottommost-gc.jsonl — output contains zero tombstones.
  • conformance/corpora/compact/range-del-propagation.jsonl — output range-del block correct.
Pitfalls
  • Smallest-overlap heuristic must operate on a Version snapshot, not live mutable state — a picker reading stale metadata picks wrong files (I3).
  • Bottommost tombstone GC must consult min_live_snapshot (§18.2), not current seq — a long-running snapshot pins tombstones until dropped (I6).
  • A failed compaction after partial output writes leaves orphan files — never rely on the runner to self-clean; always rely on the manifest as truth (I7, vacuum §18.2). PhaseDeferred("§19.6: size-tiered / universal / lazy-leveling compaction pickers; Cassandra-style / RocksDB-Universal-style / Dostoevsky-style respectively") — registered §37 rows 3-5.

⬜ Phase 8 — Block Cache & Table Cache §20

Objectives

Ship the read path's working-set primitive (P9): without it every read costs ≥1 pread; with it, hot blocks stay resident and disk is touched only for cold blocks.

Deliverable

A block cache sustaining ≥90% hit rate on a YCSB-B benchmark at 256 MiB capacity (M17). Hit-path latency ≤100 ns per get_or_load (microbenchmark).

Acceptance

Pin-correctness test: 1M concurrent pins, zero double-evict, zero use-after-free under Miri. Cache-overflow test: workload exceeding capacity still returns correct values for every read (correctness over hit-rate).

Fixtures
  • conformance/corpora/ops/cache-hit-miss.jsonl — recorded reads with expected hit/miss given a known cache size.
  • conformance/corpora/ops/cache-eviction.jsonl — overflow workload; every read still correct.
Pitfalls
  • Shard count must be a power of two (cheap bit-mask shard-pick); document in docs/architecture/block-cache.md.
  • Cache key must include file_id — a key using only offset collides across files and returns wrong data (a correctness bug, not just a performance one).
  • Arc<Block> clone cost is negligible at 16 KiB blocks; switching to per-entry caching later would need re-evaluating this. PhaseDeferred("§20.6: LRU-K block-cache policy (RocksDB-style high-pri pool); cite cross-peer rank-59 LRU-LFU-Cache") — registered §37 row 6.

⬜ Phase 9 — Public API, Bulk-Ingest & Benchmark Harness §21

Objectives

Surface the complete public contract (§11.10): Db::open/put/get/delete/delete_range/ write/snapshot/iter/flush/compact_range/close. Add the bulk-ingest fast path and stand up the benchmark harness that gates every M-target in §30.

Deliverable

Bulk-ingest of 100M sorted entries into a fresh database in ≤5 minutes (feeds M3). db_bench fillrandom sustaining ≥200,000 writes/s (M1); readrandom after warm-up ≥1,000,000 reads/s warm, ≥100,000 cold (M4, M6).

Acceptance

All public API methods covered by an integration test exercising the full write→flush→ compact→read cycle. Bulk-ingest of 4 disjoint SSTables lands each at the lowest level it fits (I3); 2 overlapping SSTables hold the second back to a higher level, or fail under fail_if_not_bottommost.

Fixtures
  • conformance/corpora/ops/bulk-ingest-disjoint.jsonl, bulk-ingest-overlap.jsonl.
  • conformance/corpora/e2e/ycsb-a.jsonl — full end-to-end YCSB-A run, zero errors.
Pitfalls
  • Global seqno assignment is critical — trusting an ingested file's original seqs produces wrong-snapshot reads (I4, I10 violation).
  • Ingest is one transaction from the engine's perspective — partial ingest of one of N inputs is corruption; validate every input (footer/CRC, §16.2) before landing the single edit.
  • move_files requires same-filesystem; cross-FS rename returns EXDEV, requiring an explicit fallback path, not a silent hang.

⬜ Phase 10 — Checkpoint & Consistent Snapshot Export §22

Objectives

Ship Db::checkpoint(dst) (§1 in-scope deliverable): a consistent, point-in-time, non-blocking export of the database to a destination directory (ADR-30).

Deliverable

Db::checkpoint(path) producing a directory that opens as a fully independent, correct Db instance. A checkpoint of a 10 GB database completes in ≤5 s on the same filesystem (hard-link path, feeds M16).

Acceptance

Checkpoint export throughput ≥10,000 files/s on the hard-link path (M16). A checkpoint taken concurrently with an active write+compaction workload contains exactly the data visible at the snapshot's sequence number — verified by comparing against a get/iter pass on the source at the same snapshot (property test).

Fixtures
  • conformance/corpora/e2e/checkpoint-consistency.jsonl — concurrent writer + checkpoint; exported directory's full scan matches the source snapshot's scan byte-for-byte.
  • conformance/corpora/crash/kill-mid-checkpoint.bin — crash mid-export; either no checkpoint directory is left openable, or a fully-consistent one is (never a partial, openable-but-wrong one).
Pitfalls
  • Dropping the internal pinning snapshot before every hard-link completes lets the source vacuum a file the checkpoint still needs — order matters (§22.2).
  • Assuming hard-link always succeeds — cross-device dst requires the byte-copy fallback; a silent hang on EXDEV is a P8 violation (no silent fallbacks means the choice to copy must be explicit and logged, not silently different behavior).
  • Treating the checkpoint's manifest as a plain copy without re-running the atomic install protocol — a torn checkpoint-manifest write leaves an unopenable directory.

⬜ Phase 11 — Observability, CLI & Release Hardening §23

Objectives

Close the operational loop: metrics, tracing, structured logging, the lsmctl CLI, the runbook set, and the fuzzing/crash-injection campaign that gates Sealed (M14).

Deliverable

cargo run -p lsm-cli -- open /tmp/db.lsm returns a working REPL. lsmctl fsck walks a 10 GB database in ≤5 minutes asserting every block CRC. A Grafana dashboard (ops/) graphing L0 files, immutable memtables, write/read-amp, p99 latencies, fsync latency, per-level file counts.

Acceptance

30-day fuzz campaign across all four targets: zero crashes, zero UB under Miri/ASan (M14, gates Sealed). 24-hour soak with the full observability stack live: zero unhandled errors, zero memory growth, zero on-disk corruption (M13).

Fixtures
  • conformance/report_schema.json-validated conformance.report.json from every CI run (make conformance).
  • conformance/corpora/crash/* full matrix run on every push to main plus nightly (crash.yml).
Pitfalls
  • Treating fuzz-target crashes found late in the 30-day campaign as "one-offs" — every crash blocks Sealed until root-caused and fixed, per M14's gate semantics.
  • Sampling traces at 1% during an actual incident — the runbook must instruct raising the sample rate via config reload, not leave the operator blind during the exact window they need visibility.
  • Wiring metrics without wiring the runbooks that consume them — a metric with no corresponding runbook branch is dead observability.
