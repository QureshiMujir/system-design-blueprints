Three properties recur through this document. First, the data path is one-way on write (WAL → memtable → frozen → SSTable → sideways-only via compaction) and merge-shaped on read (memtable down through L0..Ln, merged, never mutated) — I2 and I3 are direct consequences. Second, every cross-cutting type (SequenceNumber, InternalKey, BlockHandle, FileId) lives in lsm-engine::core and is threaded through every crate unchanged — the terminology-lock discipline this document holds itself to. Third, the manifest is the durability primitive on the metadata side exactly as the WAL is on the data side (I1 vs I7); an SSTable that exists on disk is irrelevant to the engine's worldview unless the manifest references it. The trust boundary is the library/caller edge (§24 T1); the concurrency boundary is the single per-memtable insert mutex (P5); the persistence boundary is every arrow crossing into the File I/O layer; there is no protocol boundary or network queue — this is a library, not a server (§1 non-goals).

8. Domain Model

8.1 SSTable On-Disk Format

SSTable file := data_block+ filter_block metaindex_block index_block footer

data_block   := entry+ restart_array[u32]+ num_restarts[u32] trailer[5]
entry        := shared_len[varint] unshared_len[varint] value_len[varint]
                unshared_key_bytes value_bytes
trailer      := compression_type[u8] crc32c[u32]     # covers data ++ compression_type

filter_block := bloom_bits[u8*] header{bits_per_key, k_hashes, offset_table}
index_block  := (separator_key, BlockHandle)+          # same restart-array layout as data
metaindex_block := (block_name[str], BlockHandle)+     # names "filter.bloomv1", "rangedel.v1"
footer       := metaindex_handle[16] index_handle[16] padding[8] magic[u64]   # 48 bytes fixed

Every restart point stores a full key; intermediate entries delta-encode against the previous key (ADR-18) — 30–60% space saving on string-key workloads (§15.2). Compression (ADR-16) is applied per-block before the CRC is computed, so the trailer's compression_type names the codec used on the preceding bytes.

8.2 WAL Record Format

WAL record := seq[u64] kind[u8] pad[3] payload_len[u32] crc32c[u32] payload[payload_len]

Header is fixed 24 bytes; CRC32C covers (seq, kind, payload_len, payload). Records do not span segment files (§13.2); a record that would not fit rotates to a new segment.

8.3 Manifest / VersionEdit Format

manifest record := plen[u32] crc32c[u32] record_kind[u8] payload[varint-encoded]
record_kind      := Edit | Snapshot | Sentinel

VersionEdit fields: log_number?, prev_log_number?, next_file_number?, last_sequence?, deleted_files: [(Level,FileId)], added_files: [AddedFile], comparator_name?. AddedFile fields: level, file_id, file_size, smallest, largest, smallest_seq, largest_seq, num_entries, num_deletions, raw_key_size, raw_value_size (§11.6). A VersionSnapshot record (every 1,000 edits, §18.4) folds the entire live file set into one record and the manifest is truncated to start fresh — bounding recovery replay cost (I4, I7).

8.4 Key Encoding (InternalKey)

Field Bytes Notes
user_key variable caller-supplied bytes, sorted lexicographically
trailer 8 (u64 LE) (seq << 8) | kind

Comparator order: user_key ascending, then seq descending (newest first), then kind descending. The "newest first" rule is what lets the merging iterator (§17) emit only the most recent visible version per key without a second pass.

8.5 Worked Read-Path Example

get(key="user:42", snapshot=S=1050) walks:

  1. Active memtable: skip-list lookup for smallest InternalKey ≥ (user:42, seq=∞); if found with seq ≤ 1050, return.
  2. Immutable memtable queue (newest→oldest): same lookup per memtable.
  3. L0 (newest file→oldest, files overlap): Bloom filter probe per file; on a "maybe", binary-search index block, load data block via cache, in-block search (§16.5–16.6).
  4. L1..L6 (files non-overlapping per level): binary-search the level's file list by key range to find the ≤1 candidate file, then the same file-internal lookup as L0.
  5. First hit with seq ≤ 1050 and kind ∈ {Value, Deletion, SingleDeletion} terminates the walk; a Deletion hit returns NotFound; exhausting every source returns NotFound.

Expected block reads: ≈1.1 (§34 #3) because Bloom filters reject all-but-one non-owning level before any pread executes.

8.6 Compaction State-Transition Table

State Entered when Exits to On crash mid-state
Idle no level exceeds score 1.0 (§19.2) Picked n/a
Picked picker selects a CompactionJob (§19.2) Reading job discarded; re-pick next tick
Reading runner opens SstReaders for all inputs (§19.6) Merging job discarded; inputs untouched
Merging MergingIter walks inputs, drops invisible/GC'd entries (§19.6) Writing job discarded; inputs untouched
Writing SstWriter emits output file(s) (§15.2) Installing orphan .tmp file; vacuum-eligible (§18.7)
Installing VersionEdit appended + manifest fsync'd (§18.2, I11) Retiring manifest either has the edit or doesn't — both valid (I11)
Retiring old input files unlink'd (§18.7) Done orphan input files remain briefly; vacuum-eligible, harmless (I7)
Done edit visible via Arc<Version> swap Idle n/a
Aborted any prior state's precondition invalidated (e.g. picked files now in another job) Idle n/a — no partial manifest write occurred

8.7 Malformed-Block Failure Example

A data block's trailer CRC32C is computed over (block_bytes, compression_type). Given a block whose 9th byte was flipped by a disk bit-rot event: the reader loads the block via pread, recomputes CRC32C over the bytes read, compares against the trailer's stored value, finds a mismatch, and returns Error::BlockCorrupt(file_id, block_handle) (I8) without attempting to parse the (possibly attacker- or corruption-controlled) entry data — bounded reads and CRC-before-parse together prevent an out-of-bounds shared_len/ unshared_len from ever being trusted (§24 T2).

8.8 Torn-Write Failure Example

Crash sequence: SstWriter::finalise has fsync'd the SSTable and renamed 0000042.sst.tmp → 0000042.sst, but the process is killed before the directory fsync that makes the rename durable, and before the manifest edit referencing file 42 is appended. On reopen: the manifest replay (§18.5) has no record of file 42 (the edit never landed), so file 42 — whether or not the rename survived the crash — is an orphan by definition (I7); the vacuum (§18.7) unlinks it on the next pass. No data is lost because the WAL records that produced the flush have not yet been truncated (P6) — recovery replays them into a fresh memtable and the flush is retried.
