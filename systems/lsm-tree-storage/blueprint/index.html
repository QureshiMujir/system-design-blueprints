68 — LSM-Tree Storage Engine

Project Number: 68

Project Name: LSM-Tree Storage Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build an embedded, log-structured-merge key-value storage engine in Rust that absorbs hundreds of thousands of writes per second on commodity NVMe, bounds write/space/read amplification within the constraints of §4, and answers point lookups against terabyte-scale datasets in microseconds. The engine is a process-local library — it owns one or more directories on disk and exposes a transactional-adjacent KV interface (put, get, delete, snapshot, range scan, range delete, iterator, flush, compact-range, checkpoint) optimized for write-heavy workloads. It is embedded into a database server, a metrics store, an event log, a query-planner index, or any component needing write-amplification-bounded persistence.

Phase-0 deliverable — numbered modules/crates:

  1. lsm-engine — public crate; Db, DbOptions, Snapshot, Iter, Error.
  2. lsm-wal — append-only WAL adapter, group commit, replay.
  3. lsm-memtable — skip-list memtable, immutable queue.
  4. lsm-sst — SSTable writer/reader, block format, footer/index/filter blocks.
  5. lsm-filter — per-file Bloom filter.
  6. lsm-manifest — manifest log, VersionSet, VersionEdit.
  7. lsm-compact — leveled compaction picker + runner.
  8. lsm-cache — sharded block cache, table cache.
  9. lsm-rate-limit — token-bucket compaction throttle.
  10. lsm-cli — lsmctl operator CLI.
  11. lsm-bench — db_bench-style benchmark binaries.

System boundaries.

  • Provides: durable single-node KV storage, snapshot-isolated (MVCC via sequence number) reads, range scan/delete, background compaction, crash recovery, checkpoint export, observability hooks.
  • Delegates: SQL parsing/query planning (out of scope entirely), distributed consensus/replication (out of scope; see §3, §37 row 13), network protocol (out of scope — the engine is a library, not a server).
  • Does NOT provide: multi-statement serializable transactions (deferred, §37 row 14), encryption at rest in Phase 0 (deferred, §37 row 9), column families in Phase 0 (deferred, §37 row 11), multi-node anything.

Non-goals: becoming a general-purpose database; matching every RocksDB configuration knob; supporting every compaction strategy in Phase 0 (leveled ships as default per ADR-03; alternatives documented, not built, until deferred).

Deployment model: compiled into the host application's binary; owns a data directory; single OS process, single or multi-threaded within that process.

Target users/operators: systems engineers embedding a storage engine into a larger service; SREs operating that service via the runbooks in §26.

Later phases unlock: MVCC transactions (OCC), column families, remote/tiered storage, replication adapters, alternative compaction strategies — all in the Deferred Features Register (§37).

Recommended language: Rust, stable, edition 2021 (ADR-01). Rejected: C++ (no memory-safety story for the unsafe boundaries this engine needs — block decoder, WAL adapter, Bloom probe inner loop, page-aligned buffer pool — without sanitizers in every CI run); Go (GC pauses of 1–10 ms are incompatible with the p99 targets in §4); Java/JVM (same GC-pause argument, plus JNI cost for pread/pwrite/fsync). Rationale in ADR-01.

Prerequisites: LSM algorithmics at the level of O'Neil et al. 1996 (§5); intermediate Rust (lifetimes, Send/Sync, unsafe discipline, MaybeUninit); the storage stack from VFS to block device (page cache, fsync, O_DIRECT, write barriers); WAL/ARIES-level durability reasoning (§5); Bloom-filter math (§5, Bloom 1970).

Estimated timeline: Phase 0 — 1 week. Full system (Phases 0–11) — 9–10 weeks core engineering, 4–6 months to a fully hardened, fuzzed, benchmarked v1.0 including the 30-day fuzz campaign (M14, §30).

Deferred features (all flagged PhaseDeferred("§N.s"), all registered in §37): lock-free memtable (§14.6), io_uring WAL path (§13.7), size-tiered/universal/lazy-leveling pickers (§19.6), LRU-K cache policy (§20.6), per-block prefix filters (§16.6), key-value separation (§36), encryption at rest (§24), merge operator (§11), column families (§9 ADR-28), remote/tiered storage (§31), replication adapter (§3), full MVCC/OCC transactions (§17.2), continuous online backup (§22.2).

2. Why Build This

  • Teaches the full LSM surface in one deliverable: WAL durability boundary, skip-list memtable absorption, SSTable block/filter/index/footer encoding, manifest-as-truth recovery, leveled compaction scheduling, block-cache sharding, snapshot MVCC, range tombstones — no piece is elided.
  • Historically load-bearing architecture: the LSM shape (O'Neil 1996) underlies LevelDB, RocksDB, Cassandra, ScyllaDB, HBase, and most modern write-optimized engines; understanding it from first principles transfers directly to reading any of their source trees.
  • Builds the "amortize the expensive operation" muscle: every design decision here is a bet that background compaction (cheap in aggregate, deferred) beats foreground in-place update (expensive per-operation, immediate) — the same trade appears in GC, copy-on-write filesystems, and log-structured everything.
  • Sibling cross-links: the B+tree engine (workspace rank 67) is the read-optimized counterpart (ADR-02); the WAL project (rank 69) is the durability-primitive sibling whose trait surface this engine mirrors (§21.1); the Bloom-Filter/CMS project (rank 70) is the filter-block reference (§9 ADR-17); the LRU-LFU-Cache project (rank 59) is the block-cache reference (§9 ADR-07); the Rate-Limiter project (rank 41) is the compaction-throttle reference (§9 ADR-26).
  • Calibration value: a correct leveled compaction picker, a correct crash-recovery loop, and a correct merging iterator are the three hardest-to-get-right subsystems in any storage engine; shipping all three to the conformance bar in §28 is a genuine systems-engineering credential.

What Mastery Looks Like (after finishing all phases, a reader/builder can):

  • Derive write/space/read amplification from level multiplier and fanout, not just quote numbers (§34; built in Phase 7, §19).
  • Explain why fsync is not a durability oracle and design around a lying disk (§6 P8; built in Phase 1, §13).
  • Debug a write stall from first principles using L0 file count and compaction score (§19.10; operational competency built in Phase 11, §23).
  • Reason about MVCC correctness using sequence numbers alone, without a version-chain mental model (§17; built in Phase 5).
  • Choose leveled vs size-tiered vs lazy-leveling for a given workload, citing the Dayan/Idreos trade-off space, not by habit (§36; built across Phase 7, §19, and §9 ADR-03).
  • Design a crash-safe atomic install protocol (write-tmp, fsync, rename, fsync-dir) for any metadata-plus-data system, not just this one (§8.3, §18.6; built in Phase 6).
  • Size a Bloom filter from a target false-positive budget and a RAM ceiling (§34 #3, #4; built in Phase 4, §16).
  • Explain, with a concrete regime, when each of the four Alternative Architectures (§36) is the correct choice instead of a strictly worse LSM.

Three properties recur through this document. First, the data path is one-way on write (WAL → memtable → frozen → SSTable → sideways-only via compaction) and merge-shaped on read (memtable down through L0..Ln, merged, never mutated) — I2 and I3 are direct consequences. Second, every cross-cutting type (SequenceNumber, InternalKey, BlockHandle, FileId) lives in lsm-engine::core and is threaded through every crate unchanged — the terminology-lock discipline this document holds itself to. Third, the manifest is the durability primitive on the metadata side exactly as the WAL is on the data side (I1 vs I7); an SSTable that exists on disk is irrelevant to the engine's worldview unless the manifest references it. The trust boundary is the library/caller edge (§24 T1); the concurrency boundary is the single per-memtable insert mutex (P5); the persistence boundary is every arrow crossing into the File I/O layer; there is no protocol boundary or network queue — this is a library, not a server (§1 non-goals).

4. System Constraints

Reference host: 16-core x86-64, 64 GiB RAM, NVMe SSD (fsync ≈ 150 µs), ext4. Reference workload: 16-byte keys, 100-byte values, 1B-key dataset (≈136 GB raw).

6. Design Principles

  • P1. Crash safety is the ground truth. Every write acknowledged by put() survives kill -9 + power cut, except: writes acknowledged with WriteOptions::sync = false may be lost, but only as a contiguous suffix of the recovered log. Tradeoff: sync = true costs one fsync per group-commit round (§34 #7). Operational: the choice is per-write, not global. Violation breaks: silent, unbounded data loss with no way to identify which acked writes vanished — the worst production failure class (§25 FM1).
  • P2. The SSTable is immutable. Once installed in the manifest, its bytes never change; new data is new SSTables, deletions are tombstones, merges retire inputs atomically (I2). Tradeoff: no in-place update path, so a single-byte fix requires a rewrite. Operational: simplifies concurrent reads to zero-lock. Violation breaks: any concurrent reader holding a stale Arc<Block> now sees corrupted data mid-read.
  • P3. The manifest is the single source of truth for the file set. A file not referenced by the manifest is garbage (I7); a referenced file missing on disk is fatal. Tradeoff: every flush/compaction pays one manifest fsync. Operational: lsmctl fsck diffs manifest vs directory. Violation breaks: recovery either resurrects deleted data or references phantom files (§25 FM4, FM5).
  • P4. Compaction is a background pipeline, not a foreground stall. Reads/writes never wait on compaction below level0_slowdown_writes_trigger (default 8); above level0_stop_writes_trigger (default 12), writes stall (§19.10). Tradeoff: bounded foreground latency costs unbounded compaction debt if ignored. Operational: runbook write-stall.md (§23.10). Violation breaks: either write stalls become the default behavior (foreground blocked) or compaction debt runs away invisibly (§25 FM6, FM9).
  • P5. One writer-thread per memtable; many lock-free readers against snapshots. Tradeoff: single insert mutex bounds single-memtable write throughput (deferred lock-free alternative, §37 row 1). Operational: read path never blocks on write path. Violation breaks: adding a lock to "fix" a read race (MM8) regresses read p99 for no correctness gain.
  • P6. The WAL is the data-side durability boundary; the manifest is the metadata-side boundary. They are independent facts, never conflated. Tradeoff: two fsync paths instead of one, at the benefit of independent recovery reasoning. Operational: db.flush truncates WAL only after the manifest edit lands (§18.1). Violation breaks: truncating WAL before the manifest edit is durable loses data that the manifest still expects.
  • P7. No silent corruption. Every block/record/edit carries CRC32C (I8); a bad read returns Error::BlockCorrupt/WalCorrupt/ManifestCorrupt, never a silent re-read or repair. Tradeoff: one CRC computation per block/record on every read/write. Operational: lsmctl repair is a separate, explicit, audited action. Violation breaks: an engine that "heals" silently hides the very corruption an operator needs to see.
  • P8. No silent fallbacks. O_DIRECT unavailable → error, not silent buffered fallback; short pwritev → error; fsync returning EIO → refuse further writes until reopened. Tradeoff: stricter failure surface than a "best-effort" engine. Operational: auditability the operator relies on. Violation breaks: a silently-degraded durability mode that the operator believes is still strict (§24 T6, MM6).
  • P9. Bounded memory everywhere. Active memtable ≤ write_buffer_size; immutable queue ≤ max_immutable; block cache ≤ capacity_bytes; compaction buffers pre-allocated per job. Tradeoff: a workload that needs more headroom must reconfigure, not rely on unbounded growth. Operational: OOM is a config error, not a runtime surprise. Violation breaks: an unbounded queue anywhere turns a slow consumer into an OOM (§25 FM6 analog).
  • P10. One config struct, one error enum, one telemetry trait. All knobs on DbOptions; all errors are thiserror-derived Error variants; all metrics through trait Telemetry. Tradeoff: no plugin runtime — new behavior ships behind cfg(feature). Operational: one place to read for the entire contract surface. Violation breaks: config/error/telemetry drift across crates makes the engine's contract unauditable.
  • P11. Sequence numbers are the universal timeline. Every write is tagged with a monotonic SequenceNumber (I4); a snapshot is a SequenceNumber; visibility is "highest seq ≤ S" (I10). Tradeoff: no per-row version chain, no per-transaction read set (full MVCC/OCC deferred, §37 row 14). Operational: the only isolation mechanism — simple to reason about, simple to implement. Violation breaks: any code path that compares by wall-clock time instead of sequence number breaks total ordering under clock skew.
  • P12. Tombstones are first-class data. delete(k) and delete_range(a..b) write records, not in-place removals; tombstones survive until bottom level and below min-live-snapshot seq (I6). Tradeoff: deleted keys cost disk space until GC'd. Operational: a long-lived snapshot delays reclamation (§25 FM8, MM7). Violation breaks: premature tombstone GC resurrects deleted keys under a live snapshot.

8. Domain Model

8.1 SSTable On-Disk Format

SSTable file := data_block+ filter_block metaindex_block index_block footer

data_block   := entry+ restart_array[u32]+ num_restarts[u32] trailer[5]
entry        := shared_len[varint] unshared_len[varint] value_len[varint]
                unshared_key_bytes value_bytes
trailer      := compression_type[u8] crc32c[u32]     # covers data ++ compression_type

filter_block := bloom_bits[u8*] header{bits_per_key, k_hashes, offset_table}
index_block  := (separator_key, BlockHandle)+          # same restart-array layout as data
metaindex_block := (block_name[str], BlockHandle)+     # names "filter.bloomv1", "rangedel.v1"
footer       := metaindex_handle[16] index_handle[16] padding[8] magic[u64]   # 48 bytes fixed

Every restart point stores a full key; intermediate entries delta-encode against the previous key (ADR-18) — 30–60% space saving on string-key workloads (§15.2). Compression (ADR-16) is applied per-block before the CRC is computed, so the trailer's compression_type names the codec used on the preceding bytes.

8.2 WAL Record Format

WAL record := seq[u64] kind[u8] pad[3] payload_len[u32] crc32c[u32] payload[payload_len]

Header is fixed 24 bytes; CRC32C covers (seq, kind, payload_len, payload). Records do not span segment files (§13.2); a record that would not fit rotates to a new segment.

8.3 Manifest / VersionEdit Format

manifest record := plen[u32] crc32c[u32] record_kind[u8] payload[varint-encoded]
record_kind      := Edit | Snapshot | Sentinel

VersionEdit fields: log_number?, prev_log_number?, next_file_number?, last_sequence?, deleted_files: [(Level,FileId)], added_files: [AddedFile], comparator_name?. AddedFile fields: level, file_id, file_size, smallest, largest, smallest_seq, largest_seq, num_entries, num_deletions, raw_key_size, raw_value_size (§11.6). A VersionSnapshot record (every 1,000 edits, §18.4) folds the entire live file set into one record and the manifest is truncated to start fresh — bounding recovery replay cost (I4, I7).

8.4 Key Encoding (InternalKey)

Field Bytes Notes
user_key variable caller-supplied bytes, sorted lexicographically
trailer 8 (u64 LE) (seq << 8) | kind

Comparator order: user_key ascending, then seq descending (newest first), then kind descending. The "newest first" rule is what lets the merging iterator (§17) emit only the most recent visible version per key without a second pass.

8.5 Worked Read-Path Example

get(key="user:42", snapshot=S=1050) walks:

  1. Active memtable: skip-list lookup for smallest InternalKey ≥ (user:42, seq=∞); if found with seq ≤ 1050, return.
  2. Immutable memtable queue (newest→oldest): same lookup per memtable.
  3. L0 (newest file→oldest, files overlap): Bloom filter probe per file; on a "maybe", binary-search index block, load data block via cache, in-block search (§16.5–16.6).
  4. L1..L6 (files non-overlapping per level): binary-search the level's file list by key range to find the ≤1 candidate file, then the same file-internal lookup as L0.
  5. First hit with seq ≤ 1050 and kind ∈ {Value, Deletion, SingleDeletion} terminates the walk; a Deletion hit returns NotFound; exhausting every source returns NotFound.

Expected block reads: ≈1.1 (§34 #3) because Bloom filters reject all-but-one non-owning level before any pread executes.

8.7 Malformed-Block Failure Example

A data block's trailer CRC32C is computed over (block_bytes, compression_type). Given a block whose 9th byte was flipped by a disk bit-rot event: the reader loads the block via pread, recomputes CRC32C over the bytes read, compares against the trailer's stored value, finds a mismatch, and returns Error::BlockCorrupt(file_id, block_handle) (I8) without attempting to parse the (possibly attacker- or corruption-controlled) entry data — bounded reads and CRC-before-parse together prevent an out-of-bounds shared_len/ unshared_len from ever being trusted (§24 T2).

8.8 Torn-Write Failure Example

Crash sequence: SstWriter::finalise has fsync'd the SSTable and renamed 0000042.sst.tmp → 0000042.sst, but the process is killed before the directory fsync that makes the rename durable, and before the manifest edit referencing file 42 is appended. On reopen: the manifest replay (§18.5) has no record of file 42 (the edit never landed), so file 42 — whether or not the rename survived the crash — is an orphan by definition (I7); the vacuum (§18.7) unlinks it on the next pass. No data is lost because the WAL records that produced the flush have not yet been truncated (P6) — recovery replays them into a fresh memtable and the flush is retried.

13. Phase 1 — WAL Adapter & Group Commit

13.1 Objectives

Ship the engine's single durable write boundary (I1, P1, P6). Every put/delete/ single-delete/range-delete passes through it before reaching the memtable. Implements group commit, fsync discipline, recovery replay, and truncation.

13.2 Detailed Implementation Steps

  • Wal::open/append/flush_through/last_durable_seq/replay/truncate_through (§11.4-shape trait, full surface in §21.1) — applies ADR-05 (redo-only), ADR-06 (CRC32C), ADR-14 (fdatasync).
  • Segment files (wal/000001.log, ...), fixed size default 64 MiB; records never span segments (§8.2 record format); rotation fsyncs the segment and the directory. Record header: WalRecordHeader (§11.4), 24 bytes fixed, CRC32C over (seq, kind, payload_len, payload) (I8). Group commit: first writer to acquire the segment mutex becomes leader, batches queued payloads (cap 1 MiB), fdatasyncs once; followers wait on a condvar (P1, P5). Applies the ARIES redo-only discipline (Mohan 1992, §5) minus undo, per ADR-05.
  • Durability modes: NoSync (page-cache only), Synced (fdatasync per commit), FsyncBatch{interval} (batched fdatasync every interval, default 1 ms) — throughput numbers derived in §34 #7.
  • Recovery: read manifest's log_number (§18.5 step 2), walk segments from there, verify CRC per record (I8), stop at first bad CRC per RecoveryPolicy (StrictRedo default: fail if truncation is inside a manifest-durable range; BestEffort: log and continue — forensics only).
  • Truncation: truncate_through(seq) called from Db::flush's success path (P6) — unlinks fully-obsolete segments only.

13.3 Deliverable

A Wal open/append/fsync/replay/truncate round trip exercised by tests. cargo bench baseline for append throughput at payload sizes 64B/256B/1KiB/4KiB.

13.4 Acceptance Criteria

100K-iteration smoke test appends a known pattern, fsyncs, restarts, replays, asserts equality. Group-commit test: 64 concurrent writers sustain ≥ 100,000 records/s at payload_len=256 on the reference NVMe (M1/M2 precursor, §30). Recovery test: StrictRedo rejects a manifest-durable truncation with Error::WalTruncated.

13.5 Conformance Fixtures

  • conformance/corpora/wal/single-put.bin, group-commit.bin (16 interleaved batches; seq-order recovery asserted).
  • conformance/corpora/crash/kill-mid-append.bin — torn pwrite; partial record discarded.
  • conformance/corpora/crash/kill-after-fsync.bin — fsync'd record survives, next pwrite does not; post-recover state matches recorded post-fsync state (I1).

13.6 Pitfalls

  • Ordering trap: fsync(WAL); ack(writer) is correct; ack(writer); fsync(WAL) is not (P1) — the group-commit leader must hold every follower on the condvar until fsync returns.
  • CRC must cover seq itself; otherwise a corrupt header's seq is trusted and recovery walks into an unbounded sequence-number space.
  • fdatasync returning success is durable to the disk's volatile cache, not necessarily to the platter (MM6, §24 T6) — document in docs/threat-model/overview.md, never paper over it.

13.7 Performance Concerns

Group-commit throughput is fsync-rate-bound: ≈150 µs/fsync on the reference NVMe → ≈6,667 fsyncs/s if unbatched; batching amortizes this (§34 #7 derives the batch size needed for M2). PhaseDeferred("§13.7: io_uring write+fsync chain; expected 3-5x throughput on Linux 5.10+; ships behind Cargo feature io_uring") — registered §37 row 2.

13.8 Edge Cases

Segment rotation mid-batch (a batch's records split across two segments must not happen — hold back and pad); WAL directory with a gap in segment numbering (crash between allocate-next and write-first-record) — recovery must not assume contiguous numbering, only monotonic.

13.9 Failure Analysis

A torn append (FM1, §25) is detected by CRC/header-length check; blast radius is bounded to the tail of one segment; containment is StrictRedo's refusal to replay past the tear when the manifest expects durability there; recovery path replays the WAL from log_number regardless.

13.10 Operational Notes

lsm_wal_fsync_latency_seconds and lsm_wal_bytes_appended_total feed runbooks/write-stall.md (§23.4) diagnosis. Rollback/compatibility: the WAL record format is versioned by WalRecordKind discriminants only — new kinds are additive, never renumbered (§27).

14. Phase 2 — Skip-List MemTable & Immutable Queue

14.1 Objectives

Ship the in-memory write absorber: single-writer, multi-reader skip-list keyed by InternalKey (§11.2), plus the immutable-memtable queue and rotation protocol that feeds Phase 3's flush path.

14.2 Detailed Implementation Steps

  • MemTable (§11.6 trait) backed by a skip-list (Pugh 1990, §5) over a bumpalo::Bump arena — applies ADR-08 (single writer, lock-free readers) and P5.
  • Comparator shared with the SSTable reader (§8.4): user-key ascending, seq descending — get scans forward from the first user-key match, never stops at the first hit (I10).
  • Range-delete side table keyed by start-key, consulted by the range-delete tracker (§17.2) alongside per-SSTable range-del blocks.
  • Rotation (I9, P9): when bytes_written > write_buffer_size, atomically promote active → head of immutable queue, allocate a fresh active memtable with the next WAL log_number, schedule a flush job. If immutable depth exceeds max_immutable, the writer stalls with Error::WriteStall until a flush completes.

14.3 Deliverable

A MemTable surviving a 1M-insert random workload with zero leaked arena bytes, zero lost keys (oracle: BTreeMap). A 64-thread concurrent-reader benchmark against a writing memtable.

14.4 Acceptance Criteria

Read throughput under concurrent write load does not collapse below 80% of no-write-load baseline. approximate_memory_usage() is within 10% of actual heap footprint at 64 MiB write_buffer_size. Immutable queue depth 2 + active gives a 3× burst capacity before WriteStall (§34 #5 derives the exact byte number).

14.5 Conformance Fixtures

  • conformance/corpora/ops/memtable-random-1k.jsonl — 1K random ops, expected post-state.
  • conformance/corpora/ops/memtable-snapshot-isolation.jsonl — writes interleaved with snapshot reads; each snapshot read must return the value visible at its pin point (I10).

14.6 Pitfalls

  • The arena's lifetime must outlive every reader; the retirement protocol must wait on a refcount before dropping the arena, or a reader mid-iteration use-after-frees.
  • Seq-descending order inside a user-key bucket means get must scan forward, never stop at the first hit — stopping early misses an older-but-still-visible version under a pinned snapshot (I10).
  • Range deletes live in the side table, not the skip-list — a writer that forgets to update the side table on delete_range silently drops the range delete. PhaseDeferred("§14.6: lock-free concurrent skip-list (RocksDB InlineSkipList style); required past 1M writes/s on a many-core host") — registered §37 row 1.

14.7 Performance Concerns

Skip-list insert is O(log n) expected; arena allocation avoids per-node malloc overhead. Cache-line locality (Hennessy & Patterson, §5) motivates the arena's contiguous-bump layout over a per-node heap allocator.

14.8 Edge Cases

Rotation racing a concurrent get mid-lookup on the memtable being promoted — the promoted memtable must remain readable (immutable, not dropped) until every in-flight reader releases it. Empty memtable flush (rotation triggered with zero entries, e.g. by an explicit flush() call) must produce a valid empty-but-well-formed SSTable or skip the flush entirely (documented choice: skip).

14.9 Failure Analysis

A leaked arena reference (reader outlives retirement) manifests as unbounded RSS growth, detected via lsm_memtable_size_bytes staying nonzero after rotation completes; blast radius is one process's memory, contained by the refcount-gated arena drop (§14.6).

14.10 Operational Notes

lsm_memtable_size_bytes and lsm_immutable_memtables gauges feed runbooks/ write-stall.md. No wire/storage format compatibility concern — memtables are never persisted directly (rebuilt from WAL replay, §13.2).

15. Phase 3 — SSTable Writer & Block Format

15.1 Objectives

Turn an immutable memtable (or a compaction output stream) into a sealed, immutable SSTable file (P2, I2): data blocks → filter block → metaindex block → index block → footer (§8.1).

15.2 Detailed Implementation Steps

  • SstWriter (§11.7 trait) accumulates entries in key order into a BlockBuilder (restart interval default 16, ADR-18 shared-prefix delta encoding) until block_size_target (default 4 KiB, ADR-04) is exceeded — stop after the entry that crosses the threshold, never before, avoiding empty terminal blocks.
  • Index block: one entry per data block keyed by the shortest separator string ≥ max_key(block) and < min_key(next_block) (§8.1); value is the block's BlockHandle (§11.3).
  • Filter block: one Bloom filter over every data entry's user-key (ADR-17), built via lsm-filter::BloomFilter (§11.9); sized per Monkey's per-level analysis (Dayan et al. 2017, §5) — applied at compaction-output time per level (§19.2).
  • Metaindex block names filter.bloomv1 and rangedel.v1 by string key (§8.1) — extensible without breaking the file format.
  • Footer: 48 bytes, metaindex_handle + index_handle + magic (§11.3, §8.1).
  • Atomic install (I2): write path.tmp, fsync, rename to path, fsync directory — before the manifest edit referencing the file is appended (P6). A crash between rename and manifest append leaves an orphan, cleaned by vacuum (§18.7).
  • Compression (ADR-16): Snappy default, Zstd for bottommost (DbOptions:: bottommost_compression), Lz4 optional — applied per-block before CRC (§8.1).

15.3 Deliverable

An SstWriter round-tripping a 100K-entry SSTable with deterministic output bytes, recorded in conformance/corpora/sst/. A microbenchmark: 100 MiB of random KV pairs written in ≤ 2 s on the reference NVMe.

15.4 Acceptance Criteria

Byte-identical output across two runs given identical input order (conformance predicate, §21.3). Property test: random KV stream → SSTable → read back → matches. Write throughput ≥ 50 MiB/s single-threaded (feeds M3 bulk-ingest target, §30).

15.5 Conformance Fixtures

  • conformance/corpora/sst/100k-snappy.sst — known content; reader returns identical bytes.
  • conformance/corpora/sst/range-del-block.sst — one range delete; range-del block decodes to the recorded entries.

15.6 Pitfalls

  • Off-by-one on block-size target: stopping mid-entry produces an empty terminal block — always finish the entry that crosses the threshold.
  • Shortest-separator edge case a == b: return a unmodified; over-shortening produces a separator < max_key(block), breaking index lookup (§8.5 read-path relies on this invariant holding).
  • Directory fsync after rename is mandatory on Linux — without it, a crash can lose the rename even though the file itself is fsync'd (I2, §8.8).

15.7 Performance Concerns

Restart-interval choice (16) trades index-scan cost (larger interval → cheaper restart array, more linear scan per lookup) against space (smaller interval → larger restart array). Block compression adds CPU per write; Snappy's near-zero decompression cost dominates the choice for the hot path (ADR-16).

15.8 Edge Cases

A compaction output whose every input entry was deleted (empty output) — writer must finalize a zero-entry file or the runner must skip emitting one (documented: skip, no zero-entry SSTable ever installed). A key exactly at a block boundary — index separator computation must still produce a value ≥ the boundary key.

15.9 Failure Analysis

A crash between fsync and directory-fsync of the rename (§8.8 worked example) — detection is implicit (manifest never references the file); recovery treats it as an orphan (I7), vacuumed on the next pass; no data loss because WAL records for the flush have not been truncated yet (P6).

15.10 Operational Notes

lsm_flush_total / lsm_flush_duration_seconds metrics; OpenTelemetry span sst.write nested under db.flush and compaction.run (§23.3). Format compatibility: the footer magic number gates cross-version file compatibility (§27).

16. Phase 4 — SSTable Reader & Bloom Filter

16.1 Objectives

Ship the read path's single entry to disk: open, parse footer, materialize index, expose per-key lookup and range iteration. Every read walks footer → index → filter → data block → entry (§8.5).

16.2 Detailed Implementation Steps

  • SstReader (§11.7 trait): open does pread(file, 48, file_size-48) for the footer (§11.3), rejects mismatched magic, loads the index block into memory for the reader's lifetime (small: ≈ file_size/block_size × 32B, derived §34 #8).
  • Bloom probe (ADR-17, Bloom 1970 §5): "definitely not" → immediate NotFound; "maybe" → proceed to data block. Cost ≈1 cache line per hash function (Hennessy & Patterson, §5); at bloom_bits_per_key=10 and 7 hashes, expected FPR ≈0.8% (§34 #3).
  • Data block load: binary-search index for smallest separator ≥ key, follow BlockHandle, fetch via BlockCache::get_or_load (§20.1), binary-search restart array, linear-walk forward from the largest restart ≤ search_key to the first ≥ search_key (in-block search, §8.5 step 3).
  • Range scan: pin a data block via the cache, walk forward, advance to next block via index lookup on exhaustion; snapshot filter skips seq > snapshot; RangeDelTracker (§17.2) is consulted after the merging iterator emits a candidate.
  • TableProperties: smallest/largest key+seq, entry/deletion counts, raw key/value bytes, filter params, free-form user_collected_properties — written by the writer (§15.2), read at open.

16.3 Deliverable

An SstReader point-lookup ≤5 µs warm / ≤100 µs cold on a 100K-entry SSTable on the reference NVMe (feeds M4/M6). Range-scan benchmark ≥1 GiB/s warm (feeds M7).

16.4 Acceptance Criteria

Bloom FPR ≤1.5% at bloom_bits_per_key=10 sampled against 10K never-inserted keys (conformance predicate §21.6). Footer parse rejects files <48 bytes with Error::BlockCorrupt, never panics.

16.5 Conformance Fixtures

  • conformance/corpora/sst/get-hit.jsonl — 1K (key, expected_value) pairs.
  • conformance/corpora/sst/get-bloom-miss.jsonl — 1K never-inserted keys; filter rejects every one modulo recorded FPR.
  • conformance/corpora/sst/scan-1k.jsonl — expected ordered (key,value) sequence.

16.6 Pitfalls

  • Block cache key must include file_id, not just offset — two SSTables can share an offset; keying on offset alone collides across files and returns wrong data.
  • Range-delete tracker must run after candidate emission, before the caller sees it — running it earlier as a per-source pre-filter misses deletes that apply across sources (I12). PhaseDeferred("§16.6: per-block prefix Bloom filters (RocksDB FilterPolicy); wins for prefix/time-range scan workloads") — registered §37 row 7.

16.7 Performance Concerns

Cold-read cost is dominated by one pread per level touched (§8.5); Bloom filters reduce expected touches from L0_files + levels (§34 #3, worst case ≈14) to ≈1.1 expected. Warm-read cost is dominated by cache-shard lookup + binary search (O(log entries_per_block)).

16.8 Edge Cases

A key exactly equal to a restart-point key (must match on the first comparison, not require a linear scan past it). A file with zero entries but a valid footer (writer-side prevented per §15.8, reader must still not crash if one is ever encountered via external tooling).

16.9 Failure Analysis

A Bloom false negative would be a correctness bug (never allowed, §21.6 predicate) — distinguished from an expected false positive (extra data-block fetch, no correctness impact, only cost). Detection: property test asserting zero false negatives across 10M random inserts.

16.10 Operational Notes

lsm_bloom_total{result} and lsm_block_cache_total{result} feed runbooks/ read-amp.md (§23.4). A low Bloom hit rate signals either undersized bloom_bits_per_key or a key distribution defeating the filter — the runbook's first branch point.

17. Phase 5 — Merging Iterator, MVCC Snapshots & Range Deletes

17.1 Objectives

Ship the read path's single unification point: a read at snapshot S merges the active memtable, immutable memtables, L0, and L1+ into one ordered, snapshot-filtered, range-delete-aware stream (I10, I12). Ship the public Snapshot lifecycle — this blueprint's entire MVCC mechanism (P11, ADR-09).

17.2 Detailed Implementation Steps

  • MergingIter (§11.8): min-heap ordered by InternalKey (never user-key alone — user- key-only ordering breaks the newer-first rule, I10). Pops smallest, advances its source, re-pushes, emits if visible-at-snapshot and not range-del-covered.
  • Snapshot filter (§8.5): seq > snapshot → skip; same user-key as prior emission → skip; kind == Deletion → mark "swallow next visible version"; otherwise emit.
  • L0 vs L1+ access: L0 gets one child iterator per file (files overlap, newest-first, typically 4-8 files); L1+ gets one "concatenating" child per level (files non-overlapping, binary-searched by smallest-key list, I3).
  • Bottommost tombstone GC: only at the bottom level, only when seq < min_live_snapshot (I6, §17.5) — the compaction picker decides eligibility, the iterator does not decide on its own.
  • RangeDelTracker (§11.8-adjacent): a key is covered iff start ≤ key < end, entry_seq > key_seq, entry_seq ≤ snapshot (I12); consulted on every emitted candidate.
  • Snapshot lifecycle (ADR-09): Db::snapshot() reads last_sequence, pins it in the VersionSet's BTreeMap<SequenceNumber, refcount>, returns a Snapshot handle; drop decrements the refcount. min_live_snapshot() bounds tombstone GC (I6) and pins SSTables (a file whose largest_seq < min_live_snapshot cannot be retired).
  • Reverse iteration: max-heap instead of min-heap; memtable via skip-list predecessor; SSTable via restart-array backward walk (jump to next restart, walk back to the last restart ≤ key).

17.3 Deliverable

A merging iterator producing ordered output across MemTable + 4 ImmMemTables + 8 L0 files + 6 L1+ levels. A long-running reader holds a snapshot for 1 hour while the writer performs 1M puts; the reader's view is unchanged at the end.

17.4 Acceptance Criteria

Property test: random put/delete/range-delete sequences, snapshots at random points, output compared against a BTreeMap oracle — zero mismatches over 1M generated cases. Forward iteration ≥2 GiB/s warm cache (feeds M7). Reverse scan throughput ≥50% of forward on warm data.

17.5 Conformance Fixtures

  • conformance/corpora/ops/merging-iter.jsonl, range-del.jsonl — multi-source workloads with expected snapshot reads / filtered keys.
  • conformance/corpora/e2e/snapshot-isolation.jsonl, snapshot-pins-files.jsonl — writer+reader interleaving; file-count does not drop until the snapshot drops.

17.6 Pitfalls

  • Heap must order by InternalKey, never user-key alone — user-key-only ordering produces stale reads (I10, §7 table).
  • Bottommost tombstone GC must consult min_live_snapshot, not the current sequence number — premature GC against a long-running snapshot is a correctness bug lasting until the snapshot drops (I6).
  • Snapshot's seq must be captured before the version is pinned — a concurrent put racing between capture and pin reads the wrong key set.
  • A snapshot does not pin WAL records — once a memtable is flushed, its WAL records can be truncated regardless of snapshots (P6); snapshots only pin SSTables and bound tombstone GC. PhaseDeferred("§17.2: full MVCC/OCC transactional layer — read-set tracking + commit-time validation on top of these snapshot reads") — registered §37 row 14.

17.7 Performance Concerns

The snapshot table's BTreeMap is consulted on every compaction's bottommost decision — the hottest read path on that structure; O(log S) per lookup where S = live snapshot count, bounded in practice (§4 constraints).

17.8 Edge Cases

A range-delete whose end key is unbounded (delete-to-infinity) — tracker must treat a missing upper bound as +∞, not silently no-op. Concurrent snapshot creation racing a flush that changes last_sequence mid-read.

17.9 Failure Analysis

A merging-iterator bug that emits a stale version manifests as a snapshot-isolation test failure (§17.5 fixture) — detection via the BTreeMap-oracle property test; blast radius is every read path simultaneously, since all reads funnel through one MergingIter type.

17.10 Operational Notes

lsm_snapshots_alive gauge feeds runbooks/triage.md's first-ten-minutes checklist (§23.4) — a monotonically rising count with no drops is the FM8 (§25) leak signature.

18. Phase 6 — Manifest, VersionSet & Crash Recovery

18.1 Objectives

Ship the metadata-side durability primitive (P3, P6): every flush/compaction/WAL rotation produces a VersionEdit; the VersionSet applies edits in order and exposes the current Version via atomic Arc swap (I11).

18.2 Detailed Implementation Steps

  • ManifestLog::open/append/snapshot/replay (§11.5-adjacent) — record framing per §8.3; CRC32C over (plen, kind, payload) (I8, ADR-06).
  • VersionEdit application (§8.3, §11.5) is pure: apply deleted/added files, update last_sequence/log_number; the VersionSet swaps Arc<Version> only after the manifest append's fsync returns (P6, I11).
  • VersionSet::log_and_apply serializes edits under the manifest mutex, appends, fsyncs, swaps — the fsync is the durability point (I1-analog on the metadata side).
  • Manifest snapshot rotation (§8.3): every 1,000 edits, write a full VersionSnapshot, truncate — bounds recovery replay cost (without it, an unbounded manifest makes db.open take minutes, §25 FM11).
  • Recovery (§8.5-adjacent, full sequence): read CURRENT (names active manifest) → replay every record into a fresh Version → verify every referenced file exists (I7, else MissingFile) → walk WAL from version.log_number, replay into a fresh memtable (§13.2) → engine now equivalent to state at last fsync.
  • Atomic CURRENT swap (I11, §8.6 state table): write MANIFEST-NNNNNN, fsync, write CURRENT.tmp, fsync, rename to CURRENT, fsync directory — a crash anywhere leaves either the old or the new manifest valid, never an inconsistent intermediate.
  • Vacuum (§8.8): take a Version snapshot, list directory, unlink files absent from the snapshot — safe against concurrent flushes because a file landing between snapshot and unlink is in the new Version, excluded from the orphan list by construction.

18.3 Deliverable

A VersionSet applying 100K edits in ≤2 s without losing any (feeds M-mani milestone). A recovery test killing the engine at every byte boundary in a 10K-edit workload; post- recover state matches the recorded post-fsync state (M15 precursor).

18.4 Acceptance Criteria

24-hour soak: continuous flush+compact+periodic-snapshot+periodic-kill, zero missing files, zero orphan-file accumulation, zero manifest corruption (feeds M13). Recovery throughput ≥50,000 WAL records/s on open (M12).

18.5 Conformance Fixtures

  • conformance/corpora/manifest/single-edit.bin, snapshot-rotate.bin.
  • conformance/corpora/crash/kill-mid-current-rename.bin — post-recover state names a valid manifest (I11).

18.6 Pitfalls

  • CURRENT rename must precede the directory fsync — without the directory fsync, the rename itself is not durable on Linux (§8.8).
  • Manifest snapshot must include next_file_number and last_sequence — omitting either causes post-recover state to either re-allocate colliding file ids or skip sequence numbers visible to readers (I4).
  • Vacuum must snapshot Version before listing the directory, never after — reversing the order reintroduces the race it was designed to avoid.

18.7 Performance Concerns

Manifest-snapshot rotation cadence (every 1,000 edits) trades recovery-replay cost against per-rotation fsync cost — too frequent wastes I/O, too infrequent risks the FM11 slow-open failure mode.

18.8 Edge Cases

A crash exactly between manifest-fsync and Arc<Version> swap (edit is durable but not yet visible to readers) — recovery must re-derive the same Version from the manifest, making the in-memory swap's timing irrelevant to correctness. A manifest referencing a file deleted by an out-of-band operator action (rm on the data directory) — open must fail loudly (MissingFile), never silently skip the level.

18.9 Failure Analysis

FM2/FM3/FM4/FM5/FM11 (§25) are this phase's failure surface. Blast radius of a manifest bug is total — the entire file set becomes unreadable — which is why every manifest mutation goes through one serialized, fsync'd path (§18.2) rather than being distributed across compaction/flush code paths.

18.10 Operational Notes

lsm_recovery_duration_seconds histogram gates the RTO constraint (§4). lsmctl fsck diffs manifest vs directory listing for runbooks/corruption.md (§23.4).

19. Phase 7 — Leveled Compaction: Picker, Runner, Rate Limiter

19.1 Objectives

Ship the background pipeline that keeps I3 (level non-overlap) and bounded read/space amplification true (P4): the picker (which files), the runner (how to merge), the rate limiter (how fast), the output protocol (installing via the manifest).

19.2 Detailed Implementation Steps

  • CompactionPicker trait (§21.4): pure function Version → Option<CompactionJob>. Phase 0 ships leveled (ADR-03); size-tiered/universal/lazy-leveling are documented, deferred (§37 rows 3-5).
  • Leveled picker: score(L) = sizeof(L) / max_bytes_for_level(L); highest score >1.0 wins; smallest-overlap heuristic picks the file overlapping fewest next-level files, expands input set to every overlapping next-level file (bLSM-style bounded merge scheduling, Sears & Ramakrishnan 2012, §5). L0 is special: every L0 file joins any L0→L1 job (L0 files overlap).
  • Runner (§8.6 state table): opens SstReaders for inputs → MergingIter over them → walks, dropping invisible entries and bottommost tombstones (I6, §17.5) → writes output via SstWriter (§15.2), cutting a new file when it exceeds target_file_size_base × target_file_size_multiplier^level_out → emits one VersionEdit (retired inputs + added outputs) → VersionSet::log_and_apply (§18.2).
  • Parallelism (ADR-27): default 4 concurrent jobs; L0→L1 jobs picked with disjoint key ranges are safely concurrent.
  • Rate limiting (ADR-26): RateLimiter::request(bytes) blocks before every block write — token-bucket mirrors RocksDB's GenericRateLimiter; cite cross-peer rank-41 Rate-Limiter project (§21.5).
  • Priority: L0 file count near level0_slowdown_writes_trigger → high priority; per- level score >>1 → high priority; tombstone density → high priority (tombstones must reach bottom to GC, I6).
  • Slowdown/stall (P4): L0 count > level0_slowdown_writes_trigger (default 8) → writer sleeps slowdown_microseconds(pending_l0); > level0_stop_writes_trigger (default 12) → Error::WriteStall.

19.3 Deliverable

A leveled picker driving a 1 GB random-write workload to steady state with write-amp ≤ 30× (derived §34 #1). A 4-thread parallel-compaction 24-hour soak: no L0 stall, no manifest growth past 100 MiB.

19.4 Acceptance Criteria

Write amplification ≤30× steady state (M10); space amplification ≤1.3× (M11). A YCSB-A benchmark stays within 20% of the no-compaction baseline throughput.

19.5 Conformance Fixtures

  • conformance/corpora/compact/leveled-l0-l1.jsonl — picker output matches recorded set.
  • conformance/corpora/compact/bottommost-gc.jsonl — output contains zero tombstones.
  • conformance/corpora/compact/range-del-propagation.jsonl — output range-del block correct.

19.6 Pitfalls

  • Smallest-overlap heuristic must operate on a Version snapshot, not live mutable state — a picker reading stale metadata picks wrong files (I3).
  • Bottommost tombstone GC must consult min_live_snapshot (§18.2), not current seq — a long-running snapshot pins tombstones until dropped (I6).
  • A failed compaction after partial output writes leaves orphan files — never rely on the runner to self-clean; always rely on the manifest as truth (I7, vacuum §18.2). PhaseDeferred("§19.6: size-tiered / universal / lazy-leveling compaction pickers; Cassandra-style / RocksDB-Universal-style / Dostoevsky-style respectively") — registered §37 rows 3-5.

19.7 Performance Concerns

Write amplification derivation (§34 #1): WA ≈ (non_L0_levels) × (level_multiplier/2) — with defaults (6 non-L0 levels, multiplier 10) ≈30×. Reducing level_multiplier lowers write-amp but raises the tree height (more levels), raising read-amp — the classic LSM trade Monkey/Dostoevsky formalize (§5, §36).

19.8 Edge Cases

A compaction whose output set is empty (every input entry deleted) — must still emit a valid VersionEdit that retires the inputs with zero added files. A compaction picking one L0 file and zero L1 files (no overlap) — must still be a legal, useful job (pure promotion). Hardcoded level-multiplier assumption: changing it from 10 to 8 changes tree height from 7 to 9 levels at 1 TB scale, changing read-amp (documented, not silently absorbed).

19.9 Failure Analysis

FM6 (write stall) and FM9 (compaction debt runaway) are this phase's primary failure modes (§25) — both detected via lsm_l0_files / lsm_bytes_per_level gauges, both addressed by raising max_background_compactions or rate_limiter_bytes_per_sec (runbooks/write-stall.md, compaction-debt.md, §23.4).

19.10 Operational Notes

lsm_compactions_total{level_in,level_out,result}, lsm_write_amp, lsm_space_amp, lsm_read_amp rolling-window gauges. level0_stop_writes_trigger < level0_slowdown_writes_trigger is a misconfiguration the engine refuses at open() (P4 consistency check).

20. Phase 8 — Block Cache & Table Cache

20.1 Objectives

Ship the read path's working-set primitive (P9): without it every read costs ≥1 pread; with it, hot blocks stay resident and disk is touched only for cold blocks.

20.2 Detailed Implementation Steps

  • BlockCache (ADR-07): sharded LRU, 16 shards default, keyed by (file_id, block_offset) (never offset alone — collides across files, §16.6). Sharding hashes the key mod n_shards (must be a power of two for cheap bit-mask shard-pick).
  • Eviction: doubly-linked list per shard, insert-at-head, access-promotes-to-head, evict-from-tail, O(1).
  • Pinning: get_or_load returns Arc<Block>; a block with nonzero external refcount is not evicted on its turn, moved back to head instead — a pinned block that's the only eviction candidate triggers temporary over-commit (documented, operator sizes cache accordingly).
  • Table cache: separate cache of open SstReader handles keyed by FileId, bounded by max_open_files (§4); eviction closes the underlying FD.

20.3 Deliverable

A block cache sustaining ≥90% hit rate on a YCSB-B benchmark at 256 MiB capacity (M17). Hit-path latency ≤100 ns per get_or_load (microbenchmark).

20.4 Acceptance Criteria

Pin-correctness test: 1M concurrent pins, zero double-evict, zero use-after-free under Miri. Cache-overflow test: workload exceeding capacity still returns correct values for every read (correctness over hit-rate).

20.5 Conformance Fixtures

  • conformance/corpora/ops/cache-hit-miss.jsonl — recorded reads with expected hit/miss given a known cache size.
  • conformance/corpora/ops/cache-eviction.jsonl — overflow workload; every read still correct.

20.6 Pitfalls

  • Shard count must be a power of two (cheap bit-mask shard-pick); document in docs/architecture/block-cache.md.
  • Cache key must include file_id — a key using only offset collides across files and returns wrong data (a correctness bug, not just a performance one).
  • Arc<Block> clone cost is negligible at 16 KiB blocks; switching to per-entry caching later would need re-evaluating this. PhaseDeferred("§20.6: LRU-K block-cache policy (RocksDB-style high-pri pool); cite cross-peer rank-59 LRU-LFU-Cache") — registered §37 row 6.

20.7 Performance Concerns

Per-shard mutex removes cross-core contention entirely (Hennessy & Patterson cache-line argument, §5) — the shard count (16) is chosen to keep per-shard contention low at the reference host's 16 cores (§4) without over-fragmenting capacity.

20.8 Edge Cases

A block larger than one shard's fair-share capacity (e.g. a misconfigured 1 MiB block size on a small cache) — the shard must still hold it, temporarily exceeding its fair-share bound rather than refusing to cache. Concurrent eviction racing a fresh get_or_load for the same key — must not double-insert.

20.9 Failure Analysis

Cache-key collision (FM10-adjacent, §25) manifests as a wrong-value read — the single highest-severity bug class this phase can produce, which is why the key includes file_id unconditionally (§20.2) rather than as an optimization.

20.10 Operational Notes

lsm_block_cache_total{result}, lsm_block_cache_used_bytes feed runbooks/ read-amp.md. Table-cache FD usage feeds the FD-budget constraint in §4.

21. Phase 9 — Public API, Bulk-Ingest & Benchmark Harness

21.1 Objectives

Surface the complete public contract (§11.10): Db::open/put/get/delete/delete_range/ write/snapshot/iter/flush/compact_range/close. Add the bulk-ingest fast path and stand up the benchmark harness that gates every M-target in §30.

21.2 Detailed Implementation Steps

  • Db::put/get/delete route through WAL (§13.2) → memtable (§14.2) → ack (I1); get routes through the merging iterator's single-key path (§17.2).
  • ingest_external_sst(paths, opts) / write_external_sst(path, items) (ADR-21): caller builds SSTables externally, engine picks the lowest non-overlapping level per file (I3), assigns a global seqno (last_sequence + 1 — the original seqs inside the ingested file are overwritten, not trusted), lands one VersionEdit per ingest (atomic — partial ingest of N inputs is treated as corruption, so validate every input before landing the edit).
  • IngestOptions{move_files, allow_global_seqno, fail_if_not_bottommost} — move_files uses rename(2), requiring same-filesystem source/destination; cross-FS EXDEV falls back to copy.
  • lsm-bench::db_bench (RocksDB-modeled): fillrandom, fillseq, readrandom, readwhilewriting, seekrandom, mixedworkload (YCSB-B-shaped, Zipfian 0.99). Each workload emits benchmarks/results/<host>/<date>/<workload>.json with throughput, p50/p99/p999, write/space/read-amp.

21.3 Deliverable

Bulk-ingest of 100M sorted entries into a fresh database in ≤5 minutes (feeds M3). db_bench fillrandom sustaining ≥200,000 writes/s (M1); readrandom after warm-up ≥1,000,000 reads/s warm, ≥100,000 cold (M4, M6).

21.4 Acceptance Criteria

All public API methods covered by an integration test exercising the full write→flush→ compact→read cycle. Bulk-ingest of 4 disjoint SSTables lands each at the lowest level it fits (I3); 2 overlapping SSTables hold the second back to a higher level, or fail under fail_if_not_bottommost.

21.5 Conformance Fixtures

  • conformance/corpora/ops/bulk-ingest-disjoint.jsonl, bulk-ingest-overlap.jsonl.
  • conformance/corpora/e2e/ycsb-a.jsonl — full end-to-end YCSB-A run, zero errors.

21.6 Pitfalls

  • Global seqno assignment is critical — trusting an ingested file's original seqs produces wrong-snapshot reads (I4, I10 violation).
  • Ingest is one transaction from the engine's perspective — partial ingest of one of N inputs is corruption; validate every input (footer/CRC, §16.2) before landing the single edit.
  • move_files requires same-filesystem; cross-FS rename returns EXDEV, requiring an explicit fallback path, not a silent hang.

21.7 Performance Concerns

Bulk-ingest is 5-10× faster than the per-key path (ADR-21) because it bypasses memtable/WAL entirely — the bottleneck is the disk write (or the rename, with move_files=true), not CPU.

21.8 Edge Cases

An ingest_external_sst call racing a concurrent compaction that changes the target level's file set between validation and edit-application — the manifest append must re-validate non-overlap under the manifest mutex (§18.2), not trust the pre-validation snapshot blindly.

21.9 Failure Analysis

A partially-validated bulk ingest that lands anyway (bug, not designed behavior) would violate I3 — caught by the compact.leveled-style overlap assertion extended to ingest paths (§21.5 fixtures).

21.10 Operational Notes

db_bench JSON output feeds the CI performance-regression gate (§28, §29). Public API stability is covered under §27 (Compatibility & Versioning) — Db's method signatures are the engine's SemVer-relevant surface.

22. Phase 10 — Checkpoint & Consistent Snapshot Export

22.1 Objectives

Ship Db::checkpoint(dst) (§1 in-scope deliverable): a consistent, point-in-time, non-blocking export of the database to a destination directory (ADR-30).

22.2 Detailed Implementation Steps

  • Take an internal Db::snapshot() (§17.2) to pin the file set and the sequence number at the checkpoint boundary — no writer pause required (P4-consistent with the background-pipeline principle).
  • For every SSTable referenced by the pinned Version: hard-link (same-filesystem fast path, ADR-30) into dst/; if dst is cross-device, fall back to a byte-copy per file (documented EXDEV handling, mirroring §21.2's ingest fallback).
  • Copy the current manifest (or write a fresh minimal manifest containing exactly the pinned file set) and a CURRENT file into dst/ using the same atomic write-tmp + fsync + rename + fsync-dir protocol as §18.2 (I11) — the checkpoint directory must itself be crash-consistent to open.
  • Drop the internal snapshot only after every hard-link/copy completes and the checkpoint's own CURRENT is durable — until then the source database's vacuum (§18.2) must not reclaim a file the checkpoint still references (I6/I7-analog: checkpoint pins exactly like a live snapshot).
  • dst is immediately openable as an independent Db — no replay-from-WAL step needed, since only sealed SSTables (never a mutable memtable) are exported.

22.3 Deliverable

Db::checkpoint(path) producing a directory that opens as a fully independent, correct Db instance. A checkpoint of a 10 GB database completes in ≤5 s on the same filesystem (hard-link path, feeds M16).

22.4 Acceptance Criteria

Checkpoint export throughput ≥10,000 files/s on the hard-link path (M16). A checkpoint taken concurrently with an active write+compaction workload contains exactly the data visible at the snapshot's sequence number — verified by comparing against a get/iter pass on the source at the same snapshot (property test).

22.5 Conformance Fixtures

  • conformance/corpora/e2e/checkpoint-consistency.jsonl — concurrent writer + checkpoint; exported directory's full scan matches the source snapshot's scan byte-for-byte.
  • conformance/corpora/crash/kill-mid-checkpoint.bin — crash mid-export; either no checkpoint directory is left openable, or a fully-consistent one is (never a partial, openable-but-wrong one).

22.6 Pitfalls

  • Dropping the internal pinning snapshot before every hard-link completes lets the source vacuum a file the checkpoint still needs — order matters (§22.2).
  • Assuming hard-link always succeeds — cross-device dst requires the byte-copy fallback; a silent hang on EXDEV is a P8 violation (no silent fallbacks means the choice to copy must be explicit and logged, not silently different behavior).
  • Treating the checkpoint's manifest as a plain copy without re-running the atomic install protocol — a torn checkpoint-manifest write leaves an unopenable directory.

22.7 Performance Concerns

Hard-link cost is O(1) per file, independent of file size — checkpoint throughput is bounded by file count, not database size (M16's files/s framing, not bytes/s). Byte-copy fallback cost is bounded by disk bandwidth instead, a materially different performance regime the operator must know about before choosing a cross-device destination.

22.8 Edge Cases

A checkpoint destination that already exists and is non-empty — must fail loudly (P8), never merge or silently overwrite. A checkpoint taken while a manifest snapshot rotation (§18.2) is in flight — the pinning snapshot must reference a single consistent Version, never a torn view spanning the rotation.

22.9 Failure Analysis

FM12 (§25, cross-filesystem checkpoint failure) is this phase's primary named failure mode — EXDEV surfaced immediately as a Result error, never retried silently, with the byte-copy fallback as an explicit opt-in, not an automatic retry.

22.10 Operational Notes

lsmctl checkpoint <path> operator command. Checkpoints are the backup primitive runbooks/triage.md points to; continuous/streaming backup beyond periodic checkpoints is deferred (PhaseDeferred("§22.2: continuous/streaming online backup; required when RPO is tighter than the periodic checkpoint cadence") — registered §37 row 15).

24. Threat Model

24.1 Trust Boundaries

  1. Library boundary — the engine is a library; the host application is the trust root. Bad arguments raise Error::*; they never corrupt engine state (T1).
  2. File boundary — SSTable/WAL/manifest bytes come from disk; treated as untrusted. Parsers must not overflow on a malformed block, must not allocate unboundedly on a malformed length, must not panic on truncation (T2-T4, T10).
  3. Memory boundary — the block cache holds decompressed bytes; a caller who can write SSTable files (bulk-ingest) can place chosen bytes in the cache, but the cache itself has no parsing logic — only the readers do (T5, T8).

Incident response. runbooks/triage.md is the first-ten- minutes checklist (§23.2); each subsequent runbook is a named branch keyed to one Failure Mode class (§25). Backup/restore. Db::checkpoint() (§22) is the primitive; restore is Db::open() against the checkpoint directory — no special restore code path. Deployment topology. Single process, single data directory, no clustering (§1 non-goals; §31). Canary/rolling-upgrade/rollback. Engine crate and lsmctl share one version; on-disk format compatibility gated by footer magic + manifest comparator_name (§27) — a canary host runs the new engine version against a checkpoint of production data before a fleet-wide rollout; rollback is safe only within the same on-disk-format major version (§27). Migration strategy. Format changes ship as an additive VersionEdit/WalRecordKind/block-trailer field, never a renumbering (§27) — old readers must reject, never misinterpret, a newer format they don't understand.

27. Compatibility & Versioning

Wire compatibility. N/A — this is a library, not a network service (§1 non-goals); "wire" format here means the on-disk SSTable/WAL/manifest byte layout. Storage compatibility. The footer magic (§8.1, §11.3) gates SSTable format compatibility; an unrecognized magic is a hard open-time rejection, never a best-effort parse. Schema evolution. VersionEdit's comparator_name field (§11.5) is checked at manifest replay — a database opened with a different key comparator than it was created with is rejected, not silently misordered. New WalRecordKind/ValueKind discriminants are additive only (§11.1, §11.4) — existing discriminants are never renumbered or reused. API stability. Db's public methods (§11.10, §21.1) are the SemVer-relevant surface; DbOptions additions are additive with defaults matching current behavior (adding a field never silently changes an existing deployment's behavior). Migration. A major on-disk format bump ships with an lsmctl migrate path that reads the old format and re-writes via the bulk-ingest path (§21.2) — never an in-place byte-level rewrite. Deprecation policy. A deprecated DbOptions field is honored for ≥2 minor versions with a startup warning log before removal. SemVer policy. Patch = bugfix, no format change; minor = additive DbOptions/API surface, backward-compatible on-disk format; major = on-disk format bump, requires lsmctl migrate. Rolling-upgrade guarantees. A fleet of independent single-node engine instances (no shared state, §1) means rolling-upgrade is per-instance-independent — the harder cross-node guarantee a replicated system would need is out of scope (§37 row 13).

31. Scalability Analysis

Constant regardless of dataset size: point-lookup latency (Bloom-gated, ≈1.1 expected block reads, §34 #3), memtable memory footprint (bounded, I9), block-cache memory footprint (bounded, I9). Grows with dataset size (Big-O): tree height O(log_T(N)) where T = level_multiplier (§9 ADR-04-adjacent), index-block memory O(N/block_size) (§34 #8), manifest size between snapshot rotations O(edits since rotation) (bounded by rotation cadence, §18.2), total disk footprint O(N × space_amp) (§34 #9). Named bottlenecks in order: (1) single memtable insert mutex (ADR-08) — the first ceiling past ~1M writes/s/node (§37 row 1); (2) fsync rate on the WAL (§34 #7) — the ceiling below group-commit batching; (3) compaction I/O bandwidth shared with foreground reads (rate-limited, ADR-26) — the ceiling for sustained write rate before write-amp-driven I/O saturates the device. Horizontal scaling is explicitly the embedder's responsibility (§1 non-goals) — this engine is single-node; sharding N independent Db instances behind an application-level router is the documented pattern (cf. ScyllaDB's shard-per-core taken to the process level, §5, §33). Vertical scaling — more cores help read parallelism (lock-free reads, P5) and compaction parallelism (ADR-27) up to the fsync-rate and mutex ceilings above; more RAM raises the block-cache hit rate (§34 #6) and lets the working set stay resident longer. Sharding/partitioning — out of scope in Phase 0-11 (single keyspace, ADR-28); the column-family deferred item (§37 row 11) is the intra-process partitioning primitive a future phase would add. Coordination overhead — zero today (single process, no consensus, §1); the moment a replication adapter (§37 row 13) is added, coordination overhead becomes the dominant new cost. Practical ceiling and the levers beyond it — at defaults, the practical single-node ceiling is ≈1.5M writes/s (M2) and ≈8M reads/s (M5); the levers beyond it are, in order: lock-free memtable (§37 row 1), io_uring WAL path (§37 row 2), and ultimately horizontal sharding at the application layer.

32. Mental Models & First Principles

  • MM1 — "An SSTable is a frozen fact, not a file." Insight: once installed, treat it as immutable evidence, never mutable storage. Predicts: any code path re-opening an SSTable for writing after finalise() is a bug. Bug class without it: silent corruption from an in-place patch. Applies in §7 I2, §15.2.
  • MM2 — "The manifest is the database; data files are its cache." Insight: file existence is irrelevant without a manifest reference. Predicts: recovery must always start from the manifest, never a directory listing. Bug class without it: phantom-file bugs trusting a directory scan over the VersionSet. Applies in §7 I7, §18.5.
  • MM3 — "A sequence number is a clock, not an identifier." Insight: its only job is total ordering for visibility, not identity. Predicts: reusing or de-monotonizing a seq breaks every snapshot. Bug class without it: stale-read bugs. Applies in §7 I4, §17.2.
  • MM4 — "Compaction is entropy reduction, not cleanup." Insight: it exists to keep the level-size invariant (I3) true; tombstone deletion is a side effect, not the goal. Predicts: a picker tuned purely to "reclaim space" mis-prioritizes and starves read-amp control. Bug class without it: read-amp regressions from a size-only picker. Applies in §19.2, §19.9.
  • MM5 — "A Bloom filter is a probabilistic firewall, not a cache." Insight: it only ever says "definitely not" or "maybe" — never trust "maybe" as "yes." Predicts: code returning a value on filter-hit without checking the data block is wrong. Bug class without it: phantom-read bugs. Applies in §16.2, §34 #3.
  • MM6 — "fsync is a promise about your disk, not the platter." Insight: durability terminates at the device's cache-flush honesty. Predicts: any "fsync = physically durable" claim without qualifying the device over-promises. Bug class without it: false-durability incidents (industry-documented). Applies in §6 P8, §24 T6.
  • MM7 — "A snapshot is a debt against future compaction." Insight: every open snapshot pins bytes that would otherwise be reclaimed. Predicts: long-lived snapshots correlate with rising space-amp. Bug class without it: unbounded disk growth misattributed to "a compaction bug." Applies in §17.5, §25 FM8.
  • MM8 — "The write path and read path are different concurrency universes." Insight: one mutex serializes writes; the read path is designed to need none. Predicts: adding a lock to "fix" a read race is almost always the wrong fix. Bug class without it: read-path latency regressions from over-locking. Applies in §6 P5, §20.2.

34. Back-of-Envelope Capacity Model

Every number below is derived from §4's constraints, formula shown, none asserted.

  1. Write amplification (leveled, steady state). WA ≈ non_L0_levels × (T/2) where T = level_multiplier = 10 (§4) and non_L0_levels = MAX_LEVELS - 1 = 6 (§11.1). WA ≈ 6 × 5 = 30 → M10 target ≤30×.
  2. Space amplification (leveled, steady state). SA ≈ T / (T-1) = 10/9 ≈ 1.11; M11 target ≤1.3× leaves margin for tombstone lag before bottommost GC (I6).
  3. Read amplification, worst case pre-Bloom. RA_worst ≈ L0_files + non_L0_levels = 8 + 6 = 14 block reads (one per level potentially touched, §8.5). Post-Bloom expected: RA_expected ≈ 1 + RA_worst × FPR = 1 + 14 × 0.008 ≈ 1.11 block reads (Bloom 1970, Monkey per-level sizing, §5).
  4. Bloom filter RAM budget. bits_per_key(10) × keys(1e9) / 8 = 1.25 GB for the reference 1B-key dataset (§4) — the dominant non-cache RAM line item.
  5. Memtable burst capacity before write-stall. (max_immutable + 1) × write_buffer_size = (2+1) × 64 MiB = 192 MiB before Error::WriteStall (§14.2, §37 row 1's trigger threshold references this number).
  6. Block cache blocks held. capacity_bytes / block_size = 256 MiB / 4 KiB = 65,536 resident blocks at default config (§20.1).
  7. Group-commit batch size needed for M2. fsync_latency(150 µs) → 1/150µs ≈ 6,667 fsyncs/s unbatched; to hit M2 (1,500,000 writes/s) at a 1 ms batch interval requires 1,500,000 × 0.001 = 1,500 writes/batch — the number FsyncBatch{interval} must amortize over (§13.2).
  8. Index block size per SSTable. (target_file_size_base(64 MiB) / block_size(4 KiB)) × 32 bytes/entry = 16,384 × 32B = 512 KiB — small enough to stay resident for the reader's lifetime (§16.2).
  9. Total on-disk footprint, reference workload. 1e9 keys × (16B key + 100B value + ~20B overhead) = 136 GB raw × space_amp(1.11) ≈ 151 GB total (§4 reference workload).
  10. FD budget check. Bottom-level target file size ≈ target_file_size_base × multiplier^levels; at 151 GB total and typical multi-GB bottom files, total SSTable count stays in the low hundreds — well under the max_open_files = 5,000 ceiling (§4), leaving headroom for WAL segments (~16) and the manifest (1).

36. Alternative Architectures (Roads Not Taken)

1. Size-tiered LSM (Cassandra-style).

tier0: [run][run][run][run]   (similar-sized, unsorted-vs-each-other)
tier1: [ merge of N tier0 runs -> 1 larger run ]
tier2: [ merge of N tier1 runs -> 1 larger run ]

Regime: high write throughput, tolerant of space-amp and read-amp, immutable time- series/event data. Real system: Apache Cassandra (STCS). Rejected because this blueprint's target workload (§4) needs bounded read-amp and space-amp for OLTP point lookups — leveled is the default (§9 ADR-03); size-tiered is documented and deferred (§37 row 3), not built.

2. In-place B+tree (WiredTiger btree mode / classic B-tree).

        [ root page ]
        /          \
 [internal]      [internal]
   /    \           /    \
[leaf] [leaf]   [leaf]  [leaf]     <- in-place update on write

Regime: read-heavy, small in-place updates, bounded fanout. Real system: WiredTiger (btree mode); the sibling B+tree project (workspace rank 67). Rejected: random in-place page-write amplification is unacceptable for the write-heavy target workload (§4) — the precise trade documented in §9 ADR-02.

3. Copy-on-write B-tree (LMDB-style).

old root -> [subtree A][subtree B modified: COW copy][subtree C]
new root -> [subtree A][subtree B'][subtree C]     <- atomic root swap

Regime: read-mostly, single-writer, memory-mapped, wants zero-copy reads. Real system: LMDB. Rejected: single-writer-process-wide serialization and space-doubling on write bursts conflict with the concurrent-compaction, write-heavy target (§4, §19).

4. Log-structured filesystem as the storage layer itself.

[segment N-2: data+inode][segment N-1: data+inode][segment N: being written]
                    cleaner reclaims cold segments -> new free segment

Regime: the entire filesystem should be write-optimized, not just one KV store. Real system: Sprite LFS (Rosenblum & Ousterhout 1991, §5). Rejected: this engine deliberately stays a userspace library atop a conventional filesystem (ext4/xfs, §3), avoiding the operational complexity of a custom on-disk filesystem — compaction retains the "cleaner" analogy conceptually (§8.6) without owning the whole FS.

38. Glossary

  • LSM-tree — log-structured merge tree; write-optimized structure absorbing writes in memory, flushing sorted runs, merging via background compaction (§3).
  • Memtable — in-memory, mutable, single-writer write absorber keyed by InternalKey (§14).
  • Immutable memtable — a frozen memtable awaiting flush to an SSTable (§14.2).
  • WAL — write-ahead log; the data-side durability boundary (§13).
  • SSTable — Sorted String Table; immutable, sorted, on-disk file (§8.1, §15).
  • Manifest — append-only log of VersionEdits; the metadata-side durability primitive (§18).
  • VersionSet — in-memory structure tracking the current Version + snapshot table (§18.2).
  • VersionEdit — one atomic change to the file set (flush or compaction result) (§8.3, §11.5).
  • Compaction — background merge of SSTables to bound amplification and reclaim space (§19).
  • Leveled compaction — non-overlapping per-level files, bounded read/space-amp (§9 ADR-03).
  • Size-tiered compaction — merge N similarly-sized runs; lower write-amp, higher space-amp (§36).
  • Universal compaction — RocksDB's tiered-at-top, leveled-at-bottom strategy (§37).
  • Lazy leveling — Dostoevsky's size-tiered-non-bottom, leveled-bottom hybrid (§37).
  • Write amplification — bytes written to disk per byte of logical write (§34 #1).
  • Read amplification — block reads per logical read (§34 #3).
  • Space amplification — on-disk bytes per logical byte stored (§34 #2).
  • Bloom filter — probabilistic membership structure; false positives allowed, false negatives never (§16, Bloom 1970).
  • False-positive rate (FPR) — probability a Bloom filter says "maybe" for an absent key (§34 #3).
  • Block cache — sharded LRU cache of decompressed blocks (§20).
  • Table cache — cache of open SstReader file handles (§20.2).
  • LRU — least-recently-used eviction policy (§20.3).
  • Restart point — a data-block entry storing a full key, anchoring delta-encoded entries after it (§8.1).
  • Shared-prefix encoding — delta-encoding a key against the prior key via a shared byte count (§9 ADR-18).
  • Tombstone — a Deletion-kind record marking a key logically deleted (§11.1).
  • Range tombstone — a RangeDeletion record covering [start,end) (§8.4, §17).
  • Sequence number — monotonic write-order clock; the sole MVCC mechanism (§11.1, P11).
  • Snapshot — a pinned SequenceNumber; the read-isolation unit (§17.1).
  • MVCC — multi-version concurrency control; here, snapshot-based via sequence numbers only (§17).
  • Checkpoint — a consistent, point-in-time export of the database (§22).
  • Group commit — batching concurrent writers' fsyncs into one (§13.2).
  • fsync / fdatasync — POSIX calls flushing data (and, for fsync, metadata) to the storage device (§13.2, §5 RFC/spec).
  • O_DIRECT — bypasses the OS page cache for predictable I/O latency (§9 ADR-15).
  • CRC32C — the Castagnoli CRC32 variant; hardware-accelerated checksum (§9 ADR-06).
  • Footer — the fixed 48-byte trailer of every SSTable naming its index/metaindex handles (§8.1).
  • Index block — per-SSTable block mapping separator keys to data-block handles (§8.1).
  • Filter block — per-SSTable Bloom filter bytes (§8.1).
  • Metaindex block — names auxiliary blocks (filter, range-del) by string key (§8.1).
  • Data block — the unit of compressed, checksummed key-value storage (§8.1).
  • Block trailer — 5-byte compression-type + CRC32C suffix on every block (§8.1).
  • InternalKey — user_key || (seq<<8|kind) encoding used everywhere internally (§8.4, §11.2).
  • UserKey — the caller-supplied key bytes, without seq/kind trailer (§11.2).
  • FileId — stable identifier for an SSTable file (§11.1).
