Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust, stable, edition 2021

Rejected

C++ (LevelDB/RocksDB/Pebble ecosystem); Go (Pebble); Java (Cassandra/HBase)

When the rejected choice is right

C++ wins linking into an existing C++-only host with no FFI budget; Go wins when the team's ecosystem is already Go and 1–10ms GC pauses are tolerable (Pebble/CockroachDB)

Why: Auditable unsafe boundaries without sanitizers; no GC pause on hot path

ADR-02

Storage discipline vs sibling engine

Chosen

LSM-tree, write-optimized

Rejected

B+tree in-place update engine (rank-67 project)

When the rejected choice is right

B+tree wins for read-heavy workloads with small in-place updates and bounded fanout

Why: Workload is write-heavy, append-friendly, tolerates read/space amp for write throughput

ADR-03

Compaction strategy default

Chosen

Leveled compaction

Rejected

Size-tiered (Cassandra); Universal/Tiered+Leveled (RocksDB); Lazy leveling (Dostoevsky)

When the rejected choice is right

Size-tiered wins for time-series/immutable-event ingest where write-amp must be minimized and space-amp is cheap

Why: Bounds space-amp and read-amp for OLTP-shaped point lookups (§4)

ADR-04

Default block size

Chosen

4 KiB, configurable 8/16/32 KiB

Rejected

8 KiB default (HBase norm); unbounded variable-size records

When the rejected choice is right

16 KiB wins for scan-heavy analytics over large values, amortizing per-block header cost

Why: Matches page-cache granule and reference-host NVMe sector size

ADR-05

WAL redo policy

Chosen

Redo-only WAL

Rejected

Redo+undo (full ARIES protocol)

When the rejected choice is right

Undo-log matters for engines with in-place page updates or pre-commit multi-statement rollback (B+tree engines)

Why: LSM writes are append-only; nothing to undo in place

ADR-06

Checksum algorithm

Chosen

CRC32C (Castagnoli)

Rejected

XXH3; SHA-256; Adler-32

When the rejected choice is right

SHA-256 wins when the corruption model must include adversarial tampering, not just bit-rot (cross-tenant object storage)

Why: Hardware-accelerated (SSE4.2, ARMv8 crc32cx); sufficient for single-block accidental corruption

ADR-07

Block cache eviction policy

Chosen

Sharded LRU, 16 shards

Rejected

Global LRU (single mutex); LRU-K/LFU (rank-59)

When the rejected choice is right

LRU-K wins under scan-then-point-lookup workloads where one large scan must not evict the point-lookup working set

Why: Shard-per-hash removes cross-core contention

ADR-08

Write concurrency model

Chosen

One writer thread per memtable, lock-free readers

Rejected

Lock-free concurrent skip-list (RocksDB InlineSkipList); global write mutex across memtables

When the rejected choice is right

Lock-free skip-list wins past ~1M writes/s on a many-core host where the insert mutex bottlenecks (§37 row 1)

Why: One insert mutex keeps rotation/recovery reasoning simple; readers never block

ADR-09

Snapshot mechanism

Chosen

Sequence-number pin + refcount

Rejected

Per-row MVCC version chain (Postgres-style); copy-on-write B-tree snapshot (LMDB-style)

When the rejected choice is right

Per-row version chains win for long-running read-modify-write transactions needing fine-grained conflict detection

Why: O(1) snapshot creation; no per-row version chain to maintain

ADR-10

Manifest durability model

Chosen

Append-only edit log + periodic snapshot

Rejected

Single mutable version file with a lock; rollback-journal style

When the rejected choice is right

A locked mutable file wins in a single-process system with no crash-safety requirement on metadata

Why: Bounds recovery replay cost; every edit is an fsync'd fact

ADR-11

License

Chosen

Apache-2.0 (engine)

Rejected

MIT; AGPL-3.0; BSL/ELv2

When the rejected choice is right

ELv2 wins once a hosted control-plane product is built on top and resale-prevention matters

Why: Matches LevelDB/RocksDB/Pebble ecosystem norms; patent grant needed for commercial embedding

ADR-12

Mutex implementation

Chosen

parking_lot::Mutex hot path, std::sync::Mutex cold path

Rejected

std::sync::Mutex everywhere; spin::Mutex; tokio::sync::Mutex

When the rejected choice is right

tokio::sync::Mutex wins if the public API becomes async end-to-end (rejected, ADR-19)

Why: Smaller, faster uncontended, adaptive spin; std suffices for long I/O-bound holds

ADR-13

File I/O addressing

Chosen

pwrite/pread, explicit offsets

Rejected

Buffered Write/Read with shared file cursor

When the rejected choice is right

Cursor-based I/O wins for a strictly single-threaded sequential writer (the WAL segment writer itself)

Why: Eliminates seek-then-write races between compactor and writer on one FD

ADR-14

Fsync discipline

Chosen

fdatasync for WAL, fsync for manifest/CURRENT

Rejected

fsync everywhere; sync_file_range only

When the rejected choice is right

sync_file_range wins on copy-on-write filesystems (btrfs/ZFS) where metadata is already versioned safely

Why: WAL never changes metadata after preallocation; manifest grows and needs full fsync

ADR-15

Direct I/O

Chosen

Optional O_DIRECT, default off

Rejected

Always O_DIRECT; always buffered

When the rejected choice is right

Always-O_DIRECT wins on a dedicated appliance owning 100% of RAM with no double-buffering benefit

Why: Bypasses page-cache reclaim storms for predictable p99; off-by-default keeps small deployments simple

ADR-16

Default block compression

Chosen

Snappy (hot), Zstd opt-in (bottommost)

Rejected

LZ4 default; no compression default; Zstd everywhere

When the rejected choice is right

Zstd-everywhere wins for cold-archival-dominated datasets where CPU is cheap and storage cost dominates

Why: Snappy is the LevelDB/RocksDB-proven balance of ratio vs CPU for OLTP values

ADR-17

Filter block

Chosen

One Bloom filter per SSTable

Rejected

Per-block prefix filters (RocksDB FilterPolicy); no filter

When the rejected choice is right

Per-block prefix filters win for prefix/time-range-scan-heavy workloads (§37 row 7)

Why: Simpler to build/serialize; sufficient FPR at 10 bits/key for point lookups

ADR-18

In-block key encoding

Chosen

Shared-prefix (restart-point) delta encoding

Rejected

Fixed-width keys; full-key-per-entry storage

When the rejected choice is right

Fixed-width keys win for already-small fixed-size integer/hash keys where delta-encoding overhead exceeds savings

Why: 30–60% space saving on string keys with common prefixes

ADR-19

Concurrency runtime

Chosen

Sync threads + thread pool for compaction/flush

Rejected

Async/await end-to-end (tokio)

When the rejected choice is right

Async wins once the engine grows a network-facing replication protocol multiplexing thousands of connections

Why: Storage I/O is blocking syscalls; async adds an executor with no throughput win here

ADR-20

Range-delete representation

Chosen

First-class range-tombstone record

Rejected

Per-key point tombstones only

When the rejected choice is right

Point tombstones alone win for workloads that only delete individual keys, not contiguous ranges

Why: O(1) records for an M-key delete-range instead of O(M)

ADR-21

Bulk-load path

Chosen

External-sorter-fed ingest_external_sst

Rejected

Per-key put path only

When the rejected choice is right

The per-key path alone wins for continuously-arriving data with no batch boundary

Why: 5–10x faster cold-start bulk loads, bypassing memtable/WAL entirely

ADR-22

Hashing for dedup/prefix cache

Chosen

xxHash3 (64-bit)

Rejected

SipHash; FNV-1a; reused CRC32C

When the rejected choice is right

SipHash wins if the hash table is exposed to adversarial caller-chosen keys (HashDoS)

Why: Fastest non-cryptographic hash with acceptable collisions for non-durability keying

ADR-23

Tracing

Chosen

OpenTelemetry spans, 1% sampling default

Rejected

Custom trace format; no tracing

When the rejected choice is right

100% sampling wins during an active incident (operator raises rate via config reload)

Why: Standard OTLP exporters integrate with existing ops stacks

ADR-24

Metrics

Chosen

Prometheus, pull-based

Rejected

StatsD push-based; custom binary protocol

When the rejected choice is right

StatsD push wins where Prometheus scraping cannot reach short-lived batch jobs

Why: Well-understood, integrates with the runbook and dashboards

ADR-25

Dependency policy

Chosen

cargo-deny license+advisory gate in CI

Rejected

No automated policy; manual quarterly review

When the rejected choice is right

Manual review wins for a one-person hobby fork with no CI budget

Why: Dependency graph kept intentionally small; automated gate catches drift per PR

ADR-26

Compaction throttle

Chosen

Token-bucket rate limiter (rank-41 trait)

Rejected

No throttle (best-effort); fixed-delay throttle

When the rejected choice is right

No throttle wins on a dedicated single-tenant box with over-provisioned NVMe bandwidth

Why: Bounds compaction I/O so foreground reads don't starve; smooth refill vs bursty delay

ADR-27

Compaction parallelism default

Chosen

4 concurrent background jobs

Rejected

1 (serial); unbounded

When the rejected choice is right

Serial (1) wins on constrained 2–4 core hosts where parallel jobs would contend with the foreground path

Why: Matches the 16-core reference host without starving foreground CPU

ADR-28

Column family support

Chosen

Single keyspace only (Phase 0–11)

Rejected

Column families sharing one WAL (RocksDB-style)

When the rejected choice is right

Column families win once the engine hosts multiple independent keyspaces needing independent compaction schedules

Why: Keeps the manifest/version model simple for the initial engine

ADR-29

Transaction layer

Chosen

None (snapshot reads only); full MVCC/OCC deferred

Rejected

Full serializable transaction layer built into Phase 0

When the rejected choice is right

A built-in transaction layer wins when the primary consumer is a SQL layer unable to implement its own OCC (RocksDB's separate TransactionDB)

Why: Keeps the correctness kernel small; most embedders build conflict detection above snapshot reads

ADR-30

Checkpoint mechanism

Chosen

Hard-link-based consistent directory export

Rejected

Full byte-copy export; continuous streaming replication

When the rejected choice is right

Byte-copy export wins when the checkpoint must cross filesystem/volume boundaries (hard-link requires same device)

Why: Hard-links are near-instant, space-free on the same filesystem; consistent because SSTables are immutable

36. Alternative Architectures (Roads Not Taken)

1. Size-tiered LSM (Cassandra-style).

tier0: [run][run][run][run]   (similar-sized, unsorted-vs-each-other)
tier1: [ merge of N tier0 runs -> 1 larger run ]
tier2: [ merge of N tier1 runs -> 1 larger run ]

Regime: high write throughput, tolerant of space-amp and read-amp, immutable time- series/event data. Real system: Apache Cassandra (STCS). Rejected because this blueprint's target workload (§4) needs bounded read-amp and space-amp for OLTP point lookups — leveled is the default (§9 ADR-03); size-tiered is documented and deferred (§37 row 3), not built.

2. In-place B+tree (WiredTiger btree mode / classic B-tree).

        [ root page ]
        /          \
 [internal]      [internal]
   /    \           /    \
[leaf] [leaf]   [leaf]  [leaf]     <- in-place update on write

Regime: read-heavy, small in-place updates, bounded fanout. Real system: WiredTiger (btree mode); the sibling B+tree project (workspace rank 67). Rejected: random in-place page-write amplification is unacceptable for the write-heavy target workload (§4) — the precise trade documented in §9 ADR-02.

3. Copy-on-write B-tree (LMDB-style).

old root -> [subtree A][subtree B modified: COW copy][subtree C]
new root -> [subtree A][subtree B'][subtree C]     <- atomic root swap

Regime: read-mostly, single-writer, memory-mapped, wants zero-copy reads. Real system: LMDB. Rejected: single-writer-process-wide serialization and space-doubling on write bursts conflict with the concurrent-compaction, write-heavy target (§4, §19).

4. Log-structured filesystem as the storage layer itself.

[segment N-2: data+inode][segment N-1: data+inode][segment N: being written]
                    cleaner reclaims cold segments -> new free segment

Regime: the entire filesystem should be write-optimized, not just one KV store. Real system: Sprite LFS (Rosenblum & Ousterhout 1991, §5). Rejected: this engine deliberately stays a userspace library atop a conventional filesystem (ext4/xfs, §3), avoiding the operational complexity of a custom on-disk filesystem — compaction retains the "cleaner" analogy conceptually (§8.6) without owning the whole FS.
