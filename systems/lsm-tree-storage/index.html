In one paragraph

This is an embedded key-value storage engine written in Rust and compiled into the host program: it owns a data directory and offers put, get, delete, snapshot, range scan, range delete, flush, compact-range and checkpoint (§1). Its shape is the log-structured merge tree (LSM-tree): writes go to an append-only log and an in-memory table, become sorted files that never change, and are merged in the background (§3). It targets hundreds of thousands of writes per second on commodity NVMe and microsecond point lookups over terabyte-scale data, with write, space and read amplification derived by formula, not asserted (§1, §34). Systems engineers embed it; availability is the host process's, and the engine owns its own crash recovery (§1, §4).

The problem, concretely

The blueprint's reference workload is one billion 16-byte keys with 100-byte values, about 136 GB raw, on a 64 GiB host where the engine may use at most 8 GiB (§4); the write target is ≥ 200,000 ops/s with an fsync on every commit (§4, M1). Every write acknowledged by put() must survive kill -9 plus a power cut, except writes acknowledged with sync = false, which may be lost only as a contiguous suffix of the log (P1). The classic disk structure, a tree whose pages are updated in place (B+tree), is rejected here because random in-place page-write amplification is unacceptable for a write-heavy workload (§36 alternative 2, ADR-02). The LSM bet is the opposite: background compaction, cheap in aggregate and deferred, beats foreground in-place update, expensive per operation and immediate (§2). The blueprint derives the price: about 30 bytes written per logical byte (§34 #1), about 1.11× on-disk bytes per logical byte (§34 #2), and up to 14 block reads per point lookup before Bloom filters help (§34 #3). A crash adds a WAL record torn mid-write (FM-1) and an SSTable on disk the manifest never recorded (§8.8, FM-4); the answer is a recovery story in which the manifest alone decides the file set (I7).

How it works, end to end

One write. Db::put(key, value) in lsm-engine (§21.2) goes first to the write-ahead log (WAL) in lsm-wal: a 24-byte header carrying a CRC32C over sequence number, kind, length and payload is appended to the current 64 MiB segment (§8.2, §13.2, I8). Concurrent writers do not each pay a disk flush: the first to take the segment mutex becomes the leader, batches the queued payloads (cap 1 MiB), calls fdatasync once, and releases the followers — group commit (§13.2, P1). Only then is the record inserted into the active memtable in lsm-memtable, a skip-list ordered by InternalKey, and the call returns (I1). When the memtable passes write_buffer_size (64 MiB by default, §4) it is frozen onto an immutable queue, a fresh memtable takes over with the next WAL log_number, and a flush job writes the frozen one out as a sorted, never-again-modified file — an SSTable — using lsm-sst (§14.2, §15.1). The new file is installed in a fixed order: write path.tmp, fsync, rename, fsync the directory, and only then append a VersionEdit to the manifest in lsm-manifest (§15.2, P6). The WAL segment that fed the flush is truncated only after that manifest edit has landed (§13.2, P6).

One read. Db::get(key) at snapshot S walks the sources newest to oldest (§8.5): the active memtable, each immutable memtable, every L0 file (they overlap, so each is checked, newest first), then levels 1 to 6, where files do not overlap and a binary search over the level's file list names at most one candidate (§8.5, I3). Each candidate file is asked its Bloom filter first; a "definitely not" skips the file before any pread (§8.5, MM5). On a "maybe", the reader binary-searches the file's in-memory index block, fetches the data block through lsm-cache, and searches inside the block (§16.2, §20.2). The first entry with seq ≤ S ends the walk; if it is a deletion marker the answer is "not found" (§8.5, I10).

In the background. lsm-compact scores each level as size / max_bytes_for_level, picks the level with the highest score above 1.0, merges the chosen file with every overlapping file in the level below, writes new files, and installs them with one manifest edit (§19.2, §8.6). Four such jobs run at once by default (ADR-27), each throttled by a token-bucket rate limiter in lsm-rate-limit so foreground reads keep their share of the disk (ADR-26). A vacuum pass deletes any file on disk that the current Version does not reference (§18.2, I7).

The core ideas

Durable before acknowledged, with one fsync for many writers (§13.2, I1)

The rule is I1: put() does not return success until its record is fsync'd (sync=true) or queued in group commit (sync=false) (I1). Three durability modes exist: NoSync (page cache only), Synced (one fdatasync per commit) and FsyncBatch{interval} (one fdatasync per interval, 1 ms by default) (§13.2). The blueprint's arithmetic shows why batching matters: at about 150 µs per fsync on the reference NVMe, an unbatched stream caps at ≈ 6,667 fsyncs/s, and reaching M2's 1,500,000 writes/s at a 1 ms interval needs ≈ 1,500 writes per batch (§34 #7). The same document sets M1 at ≥ 200,000 ops/s fsync-on-commit, single stream (§4, §30), and never reconciles M1 with that ≈ 6,667 fsyncs/s ceiling (§34 #7). The log is redo-only: LSM writes are append-only, so there is nothing to undo in place (ADR-05). Recovery walks the WAL from the manifest's log_number, verifies every record's CRC and stops at the first bad one; the default StrictRedo fails if that truncation falls inside a manifest-durable range, while BestEffort logs and continues, for forensics only (§13.2). fdatasync returning success means the bytes reached the disk's volatile cache, not necessarily the platter (§13.6, MM6, T6).

One key, many versions, newest first (§8.4, I10, ADR-09)

Every write is stamped with a strictly increasing sequence number (I4, P11). Inside the engine a key is the caller's bytes plus an 8-byte trailer (seq << 8) | kind — the InternalKey — and the sort order is user key ascending, then sequence number descending, then kind descending (§8.4). A snapshot is nothing more than a pinned sequence number with a reference count (ADR-09, §17.2), and a read at snapshot S returns, per key, the version with the highest seq ≤ S (I10). The merging iterator pops entries in InternalKey order and applies four rules (§17.2):

Entry popped from the merge heap What the snapshot filter does
seq > S skip — written after the snapshot
same user key as the previous emission skip — an older version of a key already answered
kind == Deletion mark "swallow the next visible version"
anything else emit, unless a live range tombstone covers it (I12)

Because newer versions sort first, the iterator emits only the most recent visible version of each key without a second pass (§8.4); a Deletion hit on a point lookup returns NotFound (§8.5). A deletion is a record — a tombstone — not a removal (P12), and it is physically dropped only at the bottom level and only once its sequence number is below every live snapshot's (I6). Snapshots pin SSTables and hold back tombstone collection; they do not pin WAL records, which can be truncated as soon as their memtable is flushed (§17.6, P6).

The SSTable: a frozen, sorted file with its map at the end (§8.1, I2, MM1)

An SSTable is laid out as data blocks, then a filter block, a metaindex block, an index block and a fixed 48-byte footer that holds the handles of the metaindex and index blocks (§8.1). Data blocks aim at 4 KiB (ADR-04); inside one, each entry stores only the bytes its key does not share with the previous key, with a full key written at every 16th entry (a restart point) — 30–60% smaller on string keys with common prefixes (§8.1, §15.2, ADR-18). Every block ends in a trailer naming its compression codec plus a CRC32C (§8.1); the CRC is checked before any byte is parsed, so a bit flipped by bit-rot returns Error::BlockCorrupt instead of a length field the parser would trust (§8.7, I8). The index block holds one entry per data block, keyed by the shortest string that is ≥ the block's largest key and < the next block's smallest (§15.2); a reader loads it once at open and keeps it — about 512 KiB for a 64 MiB file (§16.2, §34 #8). Once the manifest references the file, its bytes never change (I2). Each file also carries one Bloom filter over its keys (ADR-17): at 10 bits per key and 7 hashes the expected false-positive rate is about 0.8% (§16.2), the billion-key reference set needs 1.25 GB of filter memory (§34 #4), and the expected cost of a lookup is 1 + 14 × 0.008 ≈ 1.11 block reads (§34 #3). §4 states the budget as ≤ 1.1, "derived §34 #3", and §8.5 rounds to ≈ 1.1; the blueprint does not reconcile 1.11 with ≤ 1.1.

Leveled compaction and the three amplifications (§19.2, §34, I3, P4)

Files are arranged in levels. L0 files overlap one another (§17.2); from L1 down, files within a level are sorted and non-overlapping (I3), and the per-level size ratio (level multiplier) is T = 10 (§34 #1, §38). The picker is a pure function of the current Version: score(L) = sizeof(L) / max_bytes_for_level(L), the highest score above 1.0 wins, and within that level the file overlapping the fewest next-level files is chosen and merged together with all of them (§19.2). The runner moves through Idle → Picked → Reading → Merging → Writing → Installing → Retiring → Done; a crash in any state before Installing leaves the inputs untouched and at worst an orphan .tmp file for the vacuum (§8.6). The costs, with the blueprint's formulas: write amplification WA ≈ non_L0_levels × (T/2) = 6 × 5 = 30 (§34 #1); space amplification SA ≈ T/(T−1) = 10/9 ≈ 1.11 (§34 #2); worst-case read amplification L0_files + non_L0_levels = 8 + 6 = 14 block reads before the Bloom filters do their work (§34 #3). Lowering T lowers write amplification but adds levels and therefore read amplification — the trade Monkey and Dostoevsky formalise (§19.7). Compaction never blocks the foreground until it falls behind: above 8 L0 files the writer sleeps slowdown_microseconds(pending_l0), above 12 it gets Error::WriteStall (§19.2, P4), and the memtable side gives a (2 + 1) × 64 MiB = 192 MiB burst before the same stall (§34 #5).

The manifest is the database; data files are its cache (§8.3, §18.2, I7, I11, MM2)

The manifest is an append-only log of VersionEdit records, each naming the files added (level, id, size, key range, sequence range) and removed, plus the new log_number and last_sequence (§8.3). VersionSet::log_and_apply serialises edits under a mutex, appends, fsyncs, and only then swaps the in-memory Arc<Version> — the fsync is the durability point (§18.2). Every 1,000 edits a full VersionSnapshot is written and the log truncated, which bounds how long recovery can take (§8.3, §18.2). A one-line CURRENT file names the active manifest and is replaced only by write-tmp, fsync, rename, fsync-directory, so a crash leaves either the old or the new manifest valid, never a half-written pointer (I11, §18.2). Recovery is therefore mechanical: read CURRENT, replay the manifest into a Version, verify every referenced file exists (fatal MissingFile otherwise, I7), then replay the WAL from version.log_number (§18.2). The blueprint's torn-write example shows the payoff: the engine dies after fsyncing and renaming 0000042.sst.tmp to 0000042.sst, but before the directory fsync and before the manifest edit lands; on reopen the manifest has never heard of file 42, so it is garbage by definition and the vacuum unlinks it, and nothing is lost because the WAL records behind that flush were never truncated (§8.8, P6).

The trade-offs — where engineers disagree

Compaction strategy: leveled (ADR-03)

Chosen: leveled compaction, because it bounds space and read amplification for OLTP-shaped point lookups (§4). Rejected: size-tiered (Cassandra), universal (RocksDB), lazy leveling (Dostoevsky) — documented and deferred (§37 rows 3–5). When the rejected choice is right: size-tiered wins for time-series or immutable-event ingest where write amplification must be minimised and space is cheap.

WAL policy: redo-only (ADR-05)

Chosen: a redo-only log — LSM writes are append-only, so there is nothing to undo in place. Rejected: redo plus undo, the full ARIES protocol. When the rejected choice is right: engines with in-place page updates or pre-commit multi-statement rollback — B+tree engines — need the undo log.

Write concurrency: one writer thread per memtable (ADR-08)

Chosen: a single insert mutex per memtable with lock-free readers, which keeps rotation and recovery reasoning simple and never blocks a read (P5, MM8). Rejected: a lock-free concurrent skip-list (RocksDB InlineSkipList) or a global write mutex across memtables. When the rejected choice is right: the lock-free skip-list wins past about 1M writes/s on a many-core host, where the insert mutex becomes the bottleneck (§37 row 1).

Snapshots: a pinned sequence number (ADR-09)

Chosen: pin a sequence number and count references — snapshot creation is O(1) and there is no per-row version chain to maintain. Rejected: per-row MVCC version chains (Postgres-style) and copy-on-write B-tree snapshots (LMDB-style). When the rejected choice is right: per-row version chains win for long-running read-modify-write transactions that need fine-grained conflict detection.

Fsync discipline: fdatasync for the WAL, fsync for the manifest (ADR-14)

Chosen: fdatasync on WAL segments, which never change file metadata after preallocation, and full fsync on the manifest and CURRENT, since the manifest grows. Rejected: fsync everywhere, or sync_file_range only. When the rejected choice is right: sync_file_range wins on copy-on-write filesystems such as btrfs or ZFS, where metadata is already versioned safely.

Filter granularity: one Bloom filter per SSTable (ADR-17)

Chosen: a single per-file filter — simpler to build and serialise, and sufficient at 10 bits per key for point lookups. Rejected: per-block prefix filters (RocksDB FilterPolicy) or no filter. When the rejected choice is right: per-block prefix filters win for workloads dominated by prefix or time-range scans (§37 row 7).

Checkpoint: hard-link export (ADR-30)

Chosen: hard-link every SSTable the pinned Version references into the destination — near-instant and space-free on the same filesystem, and consistent precisely because SSTables are immutable (§22.2). Rejected: a full byte copy, or continuous streaming replication. When the rejected choice is right: byte copy wins when the checkpoint must cross a filesystem or volume boundary, since a hard link needs the same device (FM-12).

Roads not taken (§36)

Size-tiered LSM merges several similar-sized runs into one larger run; it wins for high write throughput over immutable time-series or event data where space and read amplification are tolerable. Real system: Apache Cassandra (STCS) (§36 alternative 1).

In-place B+tree wins for read-heavy work with small in-place updates and bounded fanout (WiredTiger's btree mode, the sibling B+tree project); it loses here on random page-write amplification (§36 alternative 2, ADR-02).

Copy-on-write B-tree (LMDB) wins for read-mostly, single-writer, memory-mapped use that wants zero-copy reads; its process-wide write serialisation and space-doubling on bursts conflict with concurrent compaction (§36 alternative 3).

A log-structured filesystem (Sprite LFS) wins when the whole filesystem should be write-optimised; this engine stays a userspace library over ext4 or xfs, keeping only the "cleaner" analogy for compaction (§36 alternative 4).

The deferred register adds un-defer triggers: key-value separation (WiscKey) once median values pass 1 KiB, a lock-free memtable past 1M writes/s, encryption at rest when a customer contract requires SOC-2 CC6.1 (§37).

What must never be false

  • I1 — put() does not return success before its record is fsync'd or queued in group commit. Noticed by the crash fixture kill-after-fsync; lsm_wal_fsync_latency_seconds.
  • I2 — once a VersionEdit references an SSTable, its bytes never change. Noticed by the sst_block fuzz target and any CRC mismatch; lsm_reads_total{corrupt}.
  • I3 — L1+ files in a level are sorted and non-overlapping. The compact.leveled fixture asserts no overlap; lsm_files_per_level; a violating edit is rejected.
  • I4 — sequence numbers strictly increase and are never reused. Property test against a monotonic oracle; recovery recomputes last_sequence from manifest plus WAL tail.
  • I5 — compaction loses nothing: output visible keys equal input visible keys minus collected tombstones. Property test against a BTreeMap oracle; lsm_compactions_total.
  • I6 — a tombstone is dropped only at the bottom level and below every live snapshot. Property test with a pinned snapshot; lsm_snapshots_alive.
  • I7 — the manifest is truth: an unreferenced file is garbage, a referenced-but-missing file is fatal. lsmctl fsck diffs manifest against directory.
  • I8 — every WAL record, block and manifest record carries a CRC32C. Every read verifies it first; lsm_reads_total{corrupt}; lsmctl repair is the explicit fix.
  • I9 — memory is bounded: memtable, immutable queue and cache each have a cap. Gauges lsm_memtable_size_bytes and lsm_block_cache_used_bytes against the configured caps.
  • I10 — a read at snapshot S returns the highest seq ≤ S per key. Property test of a pinned snapshot against recorded state; lsm_reads_total{hit_or_miss}.
  • I11 — CURRENT changes only via write-tmp, fsync, rename, fsync-dir. Crash fixture kill-mid-current-rename; lsm_recovery_duration_seconds.
  • I12 — a key under a live range tombstone is never returned. Property test range-del.jsonl.

What breaks in production

  • FM-1 — a torn WAL write. Recovery stops mid-segment because a crash interrupted a pwrite; the CRC and header-length check catches it (§13.2); the trailing partial record is discarded and replay resumes from the last valid one, though StrictRedo may insist on replay from the prior fsync point. The segment is kept for offline analysis.
  • FM-4 — an orphan SSTable. Disk usage exceeds what the manifest accounts for after a crash between the file's fsync and the manifest append; the vacuum's manifest-versus- directory diff finds it (§18.2) and Db::vacuum() unlinks it on schedule, logging the path.
  • FM-6 — a write stall. put() latency spikes and Error::WriteStall appears because compaction fell behind L0 growth (throttle too low, slow disk, starved CPU); watch lsm_l0_files against level0_stop_writes_trigger. Nothing recovers automatically by design (P4): raise max_background_compactions or the rate limit (runbooks/write-stall.md).
  • FM-7 — a Bloom false-positive storm. Read p99 regresses and disk IOPS spike because bloom_bits_per_key is undersized or the workload defeats locality; the lsm_bloom_total{result} ratio shows it; raise the bits per key and rebuild via compaction.
  • FM-8 — a snapshot leak. Disk grows without bound and tombstones are never collected because an application holds a Snapshot forever; lsm_snapshots_alive trends up with no drops. Nothing recovers automatically by design (I6); the operator identifies and stops the leaking client (§25, MM7).
  • FM-9 — compaction debt runaway. Per-level scores sit far above 1 and read amplification climbs because the write rate exceeds the compaction budget; lsm_bytes_per_level against max_bytes_for_level is the tell; scale the rate limiter and parallelism or reduce writes.
  • FM-11 — a slow open. db.open() takes minutes because the manifest grew unbounded (a missed snapshot rotation) or the WAL tail is huge; lsm_recovery_duration_seconds trends up; rotation bounds it by design (§18.2) and lsmctl compact-manifest forces one.
  • FM-12 — a cross-filesystem checkpoint. checkpoint() returns EXDEV because the destination is on a different device than the hard-link source; the error surfaces immediately (§25). The blueprint is split on the fallback: §22.2 says a cross-device dst falls back to a byte copy per file; §22.9 makes it an explicit opt-in, never automatic (§25).

Threats a reader should know (§24): T2 a malformed or corrupted block, answered by CRC-before-parse and bounded length checks (§8.7, I8); T6 a disk that lies about fsync — undetectable from userspace, so the operator must choose NVMe with power-loss protection (MM6); T8 a hand-crafted .sst fed to ingest_external_sst, which the reader validates exactly as it would any other file and rejects atomically (§21.6); T10 a crafted payload_len meant to exhaust memory during replay, defeated by checking the length against the remaining bytes before allocating; T11 data at rest is readable by anyone with filesystem access until encryption at rest ships (§37 row 9) — use dm-crypt meanwhile.

How it compares

  • LevelDB is the ancestor this blueprint studies most closely: leveled only, per-file Bloom, a single LRU, and a global mutex around Version that bounds read parallelism at extreme scale, which this design avoids with an Arc<Version> swap (§33). It ships the smallest possible correct LSM (§33).
  • RocksDB generalised LevelDB with column families, pluggable compaction and the production rate limiter ADR-26 mirrors; its "one engine, every workload" niche costs a 300-plus-option configuration surface this blueprint avoids (§33). Pebble is the Go re-implementation in the same lineage (§33).
  • Cassandra made compaction a per-table choice (size-tiered, leveled, TWCS) from day one, which this blueprint documents but defers; its niche is built-in multi-DC replication, out of scope for a library (§1, §33). ScyllaDB is the shard-per-core rewrite (§33).
  • WiredTiger ships B-tree and LSM modes behind one API, showing the ADR-02 choice is an interface-compatible configuration; its LSM mode merges more eagerly than RocksDB's, trading write amplification for simpler merge code, and it has no built-in filter (§33).

  2. How does the minimum live snapshot bound tombstone GC, and what production symptom appears when a snapshot is held open for days? (§17.2, §25 FM8) — Hint: I6, MM7, FM-8.
  3. Why does leveled compaction's write-amplification formula predict ≈30× rather than a naive per-level T×, and what lever reduces it? (§34 #1, §9 ADR-03, §37 row 5) — Hint: see §19.7.

If you only remember three things

Writes are never done in place: they are appended to a log, absorbed in memory, frozen into immutable sorted files and merged later, and the blueprint derives the price — write, space and read amplification — from formulas rather than asserting it (§2, §34). The manifest, not the directory, decides which files exist, and the WAL decides which writes happened — two independent durability boundaries, never conflated (P3, P6, I7). A snapshot is just a pinned sequence number: O(1) to take, but every open one is a debt against future compaction (ADR-09, MM7).
