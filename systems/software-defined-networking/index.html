In one paragraph

A software-defined network (SDN) splits a network into a part that thinks and a part that forwards: one logically central controller decides what every switch should do, and the switches only follow the rules they are handed (§2). This design builds both halves from scratch in Rust: a wire protocol in the style of OpenFlow 1.3, a rule-matching software switch, topology discovery, a compiler from declarative policy to rules, a three-node Raft-replicated controller cluster, and a replayable event journal (§1). Its design targets include 10,000 switch sessions and a 250,000-flow table (§4). Datacenter network SREs operate the controller quorum, and security policy teams author intents through its northbound API (§1).

The problem, concretely

The old way is that every switch runs its own routing logic. SDN has a controller compute policy and program simple forwarding elements instead (§2). Centralizing the brain is easy to say and hard to make safe. Suppose an operator submits a policy and the controller pushes rules to switches. Four things go wrong if the push is naive:

  • Reordering. Rule updates must reach a switch in order, or multi-table goto-table chains are corrupted (§2, I1).
  • Duplicates. A TCP retransmit can deliver a rule twice. Without a transaction ID the rule is applied twice, under exactly the packet-loss conditions the system must tolerate (P12).
  • Lost promises. If the controller says "done" and crashes before the record is on disk, an acknowledged intent is gone (I4).
  • Two writers. The controller is replicated so that no single node's crash loses acknowledged intent (§3). In a partition two leaders could then issue conflicting rules (§2, P11). The blueprint calls this the single worst failure in the system (§19.9).

The design answers these with ordered, idempotent flow-mods (§16.2, P12), write-ahead durability (§18) and lease-fenced leadership (§19), all made replayable by an event journal (P1, P8).

How it works, end to end

Follow one policy through the boxes of §3's diagram (adapted from §3, shortened):

 Northbound clients (CLI, REST/gRPC SDK, dashboards, CI)        [untrusted]
   v  AuthN/AuthZ/RBAC/rate-limit/audit  (northbound-api)
 API Gateway  (stateless, horizontally scalable)
   v  intents / queries
 SDN Controller Cluster  [control-plane trust boundary]
   controller-core + intent-engine + flow-compiler + topology-engine, 3-node Raft quorum
   leader-only writes; followers serve reads from snapshots
   | WAL append                        | replicate (Raft, controller-cluster)
   v                                   v
 persistence-layer                   event-journal (replay)
 WAL + snapshots                     append-only, replay cursor
   v  flow_mod / packet_in / stats  (mTLS session, southbound-protocol)
 Southbound Session Layer  (per-switch actor, switch-agent)   [protocol boundary]
   v
 Software Switch Dataplane  (dataplane-runtime)               [concurrency boundary]
   packet-parser -> flow-table-engine (match/action) -> exec
   v
 Linux Networking (TAP/veth/bridge/namespaces/NIC)
 Cross-cutting: metrics-runtime + tracing-runtime; conformance-harness + replay-framework
  1. Gateway (northbound-api). Clients are untrusted, so each request passes authentication, authorization, rate limiting and audit first. The gateway is stateless (§3, T1, T9).
  2. Controller cluster (controller-core, intent-engine, flow-compiler, topology-engine, controller-cluster). It is the sole writer of desired state: only the Raft leader writes, and followers serve reads from snapshots (§3, P11). A policy (an intent) is checked for dependency cycles on admission, then compiled to flow rules (§20.2).
  3. Persistence (persistence-layer, event-journal). Rules go to the WAL (write-ahead log); a flow-mod is acknowledged to the compiler only after its WAL transaction fsyncs (§8, I11). The WAL is the durability primitive, the journal the replay primitive; both are filled in one transaction boundary (§3, ADR-16).
  4. Southbound session (southbound-protocol, switch-agent). Each switch has its own supervised task. Every message is length-framed, versioned and validated before it can touch flow-table state (§3, §13.2, ADR-09).
  5. Dataplane (dataplane-runtime). packet-parser extracts match fields through bounds-checked zero-copy views, then flow-table-engine runs the match/action pipeline. It is deliberately the least clever part; correctness lives in the controller (§3, §14.2).
  6. Cross-cutting. metrics-runtime and tracing-runtime attach to every queue and async boundary (P4). conformance-harness and replay-framework replay journal streams offline against the same code (§3, P8).

§1 lists Phase 0 as seven items "as running crates", including a frame codec, parsers and a WAL writer (§1); §12 scopes it to skeleton types in 18 crates, with no networking (§12.1, §12.2).

The core ideas

Desired state vs observed state: the reconciliation loop (§16, MM1)

The controller keeps two records per flow: what it wants (desired state) and what the switch reports (observed state). A FlowDescriptor holds flow_id, version, switch_id, desired_state, observed_state (optional) and install_epoch; only desired state is written to the WAL, and observed state is rebuilt from switch statistics (§11). A diff engine computes the delta between the two for each flow, the core of the reconciliation loop (§16.2, §36).

If the engine cannot tell "already applied" from "needs reapply", one rule is reinstalled every cycle (§16.6, FM-9); the fix is a version gate, reinstall only if observed.version < desired.version, and MM1 keeps the two clocks separate. Three traces show the loop (§16.5):

  1. A switch drops and reconnects mid-churn: the table re-syncs with no duplicate installs.
  2. Two overlapping requests for one rule arrive: one install, the second is a no-op (P12).
  3. Statistics report a rule installed after it was superseded: the stale observation is discarded.

There is no separate rollback path: "rollback" means submitting a new desired state (§16.10). The loop tracks a dirty set of flows needing attention, to avoid full rescans (§16.6, §36).

Write it down before you say yes: WAL and fsync-before-ack (§18, MM4)

A write-ahead log is a file where every change is appended before it is acted on, so a crash can be repaired by replaying it. MM4 says durability is an ordering constraint, not a timer: the flush comes before the acknowledgement. The reactive path shows the order (copied from §8):

Switch                Controller                         Dataplane
  | PacketIn(match)  ->  |
  |                      | topology lookup (topology-engine)
  |                      | path compute (ECMP candidate set)
  |                      | compile rule (flow-compiler)
  |                      | WAL append + fsync (persistence-layer, I11)
  | <-  FlowMod           |
  | install (I1 order)   |
  | -> FlowModAck         |
  |                      | journal append (event-journal, P8)

I4 says no acknowledged intent may exist outside durable WAL storage, and I11 is its enforcement point: a flow-mod is acknowledged only after its WAL transaction fsyncs. Recovery is crash-only (P3): load the latest valid snapshot, replay the WAL tail from the snapshot's cursor, verify checksums, and quarantine (never delete) any failing segment. The WAL is truncated only after a snapshot durably covers that range (§18.2). Each EventRecord carries a CRC32c checksum (§11).

One tension stays unresolved. I11 acks a flow-mod only after its WAL transaction fsyncs (I11, I4). Yet §4 calls RPO ≤ 1 s the "WAL fsync interval ceiling", §18.2 batches fsync to it, §18.7 prefers that to per-record fsync, and §5 contrasts etcd's fsync-every-append (§4, §18, §5).

Only one writer: lease epochs and the controller state machine (§19, MM3)

Raft elects one leader, and only the leader may change desired state (P11, ADR-05). Trusting "the current leader" is not enough during a partition, so every write carries a lease epoch, a counter that only goes up: a fencing token (MM3). A LeaseGrant holds epoch, holder, granted_at and ttl, and is Raft-replicated before use; a stale-epoch node's writes are rejected mechanically (§11, §19.9). I3 says at most one leader issues authoritative commands per epoch, and I12 says epochs strictly increase and are never reused.

Each controller process is in one of five states, and no other section may add one (§8):

State Meaning Enters from Exits to
FOLLOWER passive replica, serves reads from the last snapshot RECOVERING, LEADER CANDIDATE
CANDIDATE election in progress FOLLOWER LEADER, FOLLOWER
LEADER sole writer CANDIDATE FOLLOWER, DEGRADED
DEGRADED partial quorum, reads only, no new leases LEADER, FOLLOWER LEADER, RECOVERING
RECOVERING snapshot + WAL-tail replay process start, DEGRADED FOLLOWER

Two fixtures make this concrete (§19.5). A leader that loses quorum steps down to DEGRADED and rejects writes until quorum returns; 10 consecutive elections within 30 seconds must end in a stable leader with no epoch reuse. Election timeouts are randomized so nodes do not all time out together and split the vote (§19.2, §19.6).

Readers never wait: RCU snapshots of the topology (§17, MM2)

The map of switches and links is a TopologyGraph with a generation number (§11). Instead of locking it, the writer builds a new copy and publishes it, and readers keep using the old generation until they let go. This is RCU (read-copy-update): reads and writes never contend (MM2, §11). Two invariants keep it honest: a link needs two registered endpoint nodes (I2), and generation numbers strictly increase (I6). Around the graph:

  • Discovery probes are LLDP-like and jittered per switch (§17.2, §17.6).
  • A link not refreshed within N missed probes is pruned; a node with no live links is marked isolated, not deleted, so postmortems keep history (§17.2, P8).
  • Equal-cost path candidates (ECMP) are recomputed on topology change, not per packet (§17.2).
  • A link that flaps 50 times in 10 seconds must end in the right state with a bounded number of recomputes, because changes are debounced (§17.5, §17.6).

The flow table reuses the pattern: install, replace and delete publish a new snapshot, and a burst of flow-mods becomes one publish (§15.2). Q3 asks why it does not extend to ControllerContext itself (§33 item 3).

One task per switch: sessions, framing and idempotent flow-mods (§13, ADR-09)

Each switch session is its own supervised Tokio task with a bounded inbound queue, so one bad switch cannot starve the others (§13.2, P10, P2). Frames are length-prefixed with a hard maximum size, which prevents unbounded-allocation attacks (§13.2). A session opens with Hello, FeaturesRequest and FeaturesReply, negotiating a version and a capability bitmap; a mismatch quarantines that switch's cached capabilities (§13.2, I9). A switch has at most one controller session; on a duplicate the older session is evicted (I5).

Every FlowMod carries a TxnId in monotonic per-switch order, so a retried delivery changes nothing the second time (P12, I1). Heartbeats are jittered by plus or minus 20% per session so thousands of sessions do not fire in lock-step (§13.6). The Phase 1 fixtures (§13.5):

  1. A truncated length prefix gets an ErrorReply with BAD_FRAME; the session stays up.
  2. An unsupported version in Hello is rejected before FeaturesRequest.
  3. A replayed FlowMod TxnId gets a no-op ack, not a double apply.

Compile policy, do not hand-write rules: deterministic intents (§20, MM7)

An Intent has a kind (ACL, VLAN or path), a spec and a dependency list; once admitted it is immutable, and a change is a new IntentId (§11). Identical input must give byte-identical compiled output (§20.2, P1). Cycles among intents are rejected at admission, before compiling (§20.2, §20.5). The conflict_detector finds overlapping ACLs and shadowed rules before install, because catching overlap at compile time is cheaper than hunting a silently shadowed rule in production (MM7, FM-8). Deployment is all-or-nothing: a half-applied batch is rolled back by reissuing deletes (§20.1, §20.9, FM-11).

Q20 contrasts cycle detection in the compiler with group-reference checks at install time (§33 item 20, I10). §8 has flow-compiler check goto-table cycles at compile time, while §15.8 rejects them at install with a static cycle check (§8, §15.8). A dry run and the later deploy share one topology generation, and the deploy aborts if it advanced (§20.6, I6).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust, because ownership prevents data races in shared flow-table and topology state without GC pauses (ADR-01). The text adds that Go's GC pauses interact badly with p99 flow-mod ack targets and C++ is risky for a parser facing untrusted input (§1). Rejected: Go, C++. When the rejected choice is right: Go, for throwaway ops scripts where startup time and GC pauses do not matter and hiring breadth outweighs memory safety (ADR-01).

Persistence engine: RocksDB (ADR-04)

Chosen: RocksDB, for WAL and compaction flexibility under high-write metadata (ADR-04). Rejected: LMDB. When the rejected choice is right: read-dominated workloads needing zero-copy mmap reads and minimal write amplification (ADR-04). Caveat: RocksDB appears nowhere else; §18.2 has persistence-layer implement its own segment writer, snapshots and compaction.

Consensus: Raft (ADR-05)

Chosen: Raft, because leader-based writes match the single-writer rule P11 and give operators a simpler mental model (ADR-05). Rejected: Multi-Paxos. When the rejected choice is right: when leaderless concurrent writes are required and higher operational complexity is acceptable (ADR-05). The price is a cluster capped at 3 to 5 nodes by quorum write amplification (§29, §19.6).

Concurrency model: one actor per southbound session (ADR-09)

Chosen: an actor per session, so one bad switch cannot starve the others, at a memory cost over a shared pool (ADR-09, P10); ADR-19 repeats the choice (ADR-19). Rejected: a shared thread pool. When the rejected choice is right: when the session count is small (under 100) and the isolation overhead is not worth it (ADR-09).

Event journal: a local append-only log (ADR-16)

Chosen: an append-only local segment log, for simple local determinism with no external broker for single-cluster replay (ADR-16). Rejected: a Kafka-backed journal. When the rejected choice is right: when independent external systems must consume the journal, not just internal replay (ADR-16).

Roads not taken

No central controller (Alt A, §34): each node enforces policy locally from synced state, as Cilium does. It wins in single-cluster Kubernetes networking where in-kernel enforcement latency matters more than central visibility. It was rejected because this project's goal is the centralized mechanisms of reconciliation, consensus and fencing (§34, §1, §2).

Hardware-offloaded P4 dataplane (Alt B, §34): the controller talks P4Runtime to an ASIC or SmartNIC. It wins where line-rate forwarding is needed and software rates are structurally insufficient. It was rejected as an explicit Non-Goal (§1, §34), with a P4 backend deferred to §20 (§35).

Eventually consistent multi-master control (Alt C, §34): controllers accept writes concurrently and merge them. It wins where write availability during partitions matters more than strict consistency, such as additive-only ACL policy. It was rejected because P11 and I3 are load-bearing and multi-master issuance reopens the split-brain failure FM-7 (§34, §7).

The deferred register (§35) lists seven features, each with an un-defer trigger: WAN or multi-region federation, BGP-LS/EVPN interoperability, hardware TCAM offload, eBPF-accelerated execution, multi-region cluster federation, a P4 compiler backend, and SAT-solver conflict detection (§35).

What must never be false

Each of the twelve invariants (§7) has one assertion in the deterministic simulator (conformance-harness), run on every recorded and synthetic journal trace before merge; a violation fails CI with the invariant ID in the message (§7). Each line gives the detection, then the telemetry:

  • I1: transaction IDs apply in increasing per-switch order. Sequence-gap check; sb_txn_seq_gap_total.
  • I2: a link never exists without two registered endpoints. Referential check; topo_orphan_link_total.
  • I3: at most one leader issues authoritative commands per lease epoch. Epoch mismatch on write; cluster_stale_writer_rejected_total.
  • I4: no acknowledged intent exists outside durable WAL. fsync-before-ack assertion; wal_ack_before_fsync_total (should be 0).
  • I5: a switch has at most one controller session. Duplicate datapath_id check; sb_duplicate_session_rejected_total.
  • I6: topology generation numbers strictly increase. Monotonicity assert; topo_snapshot_generation.
  • I7: replaying a journal segment twice gives the same state hash. Hash comparison; replay_divergence_total.
  • I8: every queue has a declared capacity and shed policy. Build-time lint; queue_depth{queue}.
  • I9: a capability cache is quarantined on a version mismatch. Mismatch on Hello/FeaturesReply; sb_capability_quarantine_total.
  • I10: every group reference in an installed rule points at a live group. Referential check on apply; ft_orphan_group_ref_total.
  • I11: a flow-mod is acknowledged only after its WAL transaction fsyncs. Ordering assertion; wal_fsync_before_ack_latency_ms.
  • I12: lease epochs strictly increase across elections. Monotonicity check on grant; cluster_lease_epoch.

I4 and I11 have no runtime recovery: a violation is a design-time, build-blocking bug (§7).

What breaks in production

  • FM-1: sessions stall and reconciliation halts. Cause: leader crash, OOM or partition. Detected by heartbeat timeout in controller-cluster. An election promotes a new leader (§23).
  • FM-2: WAL replay fails its checksum. Cause: bit-rot or a torn write. Detected by the checksum mismatch. The segment is quarantined and replay resumes from the last valid record (§23, §18.5).
  • FM-3: two replays of one segment diverge. Cause: a non-deterministic path that violates P1. Detected by the I7 hash mismatch. No automatic recovery, since it is a defect: the operator binary-searches for the divergence point (§23).
  • FM-6: the controller's graph diverges from the network. Cause: a partition affecting discovery probes. Detected by a generation mismatch on rejoin (I6). The graph is fenced and rebuilt from live discovery (§23). A single switch's heartbeat loss (FM-4) is different: the topology recompute just reroutes around it (§23, §33 item 10).
  • FM-7: two nodes issue conflicting flow-mods. Cause: a lease-epoch bug, clock skew or a config error. Detected by an epoch mismatch (I3, I12). The stale writer is mechanically rejected and the epoch bug is treated as a defect (§23).
  • FM-9: the same flow is reinstalled repeatedly. Cause: a version-gating bug in the diff engine. Detected by recon_reinstall_total climbing without bound. A bounded retry window caps the damage, then a patch (§23, §16.6).
  • FM-10: the metrics backend's memory grows without limit. Cause: a per-flow label. Detected when the series count crosses its budget. It needs a code change (§23, §21.6). §32 C8 rejects per-flow_id labels outright, while §16.10 lists recon_reinstall_total{flow_id} as "cardinality-bounded by sampling" (§32 C8, §16.10).

Threats worth knowing (§22):

  • T1: forged intents on the northbound API. Mitigated by mTLS, RBAC and fail-closed admission (P9).
  • T2: an oversized-frame flood from a compromised switch. Mitigated by the max-frame-size bound and per-session isolation; the session ends and its capability cache is quarantined (I9).
  • T4: a tampered journal or WAL segment fed to replay. Mitigated by per-record checksums; the segment is quarantined and replay restarts from the last verified record.
  • T10: a TLS downgrade. Mitigated by TLS 1.3-only rustls (ADR-21); mismatches are rejected.

How it compares

  • Open vSwitch kept the control plane out of process from the kernel datapath and tuned the kernel megaflow cache instead of building a distributed controller (§31). That is fine for a single host that wants a fast software switch with no cluster-wide policy (§31).
  • ONOS made an Intent Framework the main abstraction over raw flow-mods and spreads state across the cluster with eventual consistency, not one leader (§31). That suits multi-vendor production networks that need one stable high-level API over mixed hardware (§31, §34 Alt C). The same table lists its consensus mechanism as "Atomix (Raft-based)" (§31).
  • OpenDaylight chose a pluggable MD-SAL data store with separate config and operational trees, trading simplicity for protocol breadth (§31). That fits telco and NFV settings that need many southbound plugins behind one store (§31).
  • Cilium rejected a separate SDN control plane and compiles policy to per-node eBPF programs (§31). That wins in Kubernetes, where in-kernel enforcement latency beats a central round trip (§31).

Questions to test yourself

  1. Why must WAL fsync happen before flow-mod ack rather than after, and what invariant would break if the order were reversed? (§18, §7) — Hint: I4 and I11 in §7, MM4 in §30, and the fsync policy in §18.2.
  2. Under what conditions could the reconciliation diff-engine's incremental dirty-set optimization (§16) produce a different convergence outcome than a full rescan, and why must it not? (§16, §7) — Hint: the dirty-set pitfall in §16.6 and the determinism check I7.
  3. Why can't the cluster simply grow quorum size to improve availability, given the write-amplification tradeoff behind ADR-05 and §19? (§9, §19) — Hint: the quorum write amplification pitfall in §19.6 and the horizontal scaling paragraph of §29.
  4. Why is the single-writer invariant (P11) enforced via a lease epoch (I12) rather than via an external distributed lock service like Chubby, given Chubby is explicitly cited in required reading? (§6, §7) — Hint: MM3 in §30, lease.rs in §19.2 and the failure analysis in §19.9.
  5. The event journal (§11) and the WAL (§18) are both append-only logs — why does this system maintain them as two separate structures instead of one? (§11, §18) — Hint: the paragraph under the §3 diagram, the EventRecord comments in §11, and §18.2.

If you only remember three things

A central controller is only safe if its one writer is provable: a lease epoch that only goes up fences out stale leaders (MM3, I3, I12). Nothing is acknowledged until it is durable, and nothing is applied twice, because writes are fsynced before the ack and every flow-mod carries a transaction ID (MM4, I11, P12). Everything is deterministic and replayable, so a bad night can be replayed and debugged instead of guessed at (P1, P8, I7).

Words used here

  • Controller: the central program that computes policy and programs the switches (§2).
  • Flow rule: a match/action forwarding entry scoped to a table and priority (§8, §36).
  • FlowMod: the message that installs, modifies or deletes a flow rule on a switch (§36).
  • Intent: a declarative policy (ACL, VLAN or path) that the compiler turns into rules (§36, §11).
  • Reconciliation: the continuous loop that diffs desired state against observed state (§36).
  • WAL (write-ahead log): the durability primitive underlying I4 and I11 (§36).
  • RCU (read-copy-update): readers hold an immutable snapshot while writers publish new ones (§36).
  • Lease epoch: the ever-increasing fencing token naming the current authoritative leader (§36).
  • Split-brain: more than one node believing it holds sole write authority (§36).
  • ECMP: equal-cost multipath routing, where traffic spreads over several equal-cost paths (§36).
