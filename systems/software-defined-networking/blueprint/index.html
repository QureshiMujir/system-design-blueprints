1. Goal & Scope

Engineering definition. Build a logically-centralized SDN control plane and a programmable software-switch dataplane that together implement OpenFlow-1.3-class semantics end to end: a southbound wire protocol for controller-switch sessions, a multi-table match/action forwarding pipeline, topology discovery and graph computation, an intent compiler that turns declarative policy into flow rules, a Raft-replicated controller cluster for HA, and a replayable event journal that makes every control-plane decision deterministic and auditable. This is not a research prototype of OpenFlow — it is a from-scratch reimplementation of the mechanisms that made OpenFlow/OVS/ONOS-class systems operable in production: reconciliation loops, WAL-backed persistence, RCU topology snapshots, and lease-fenced leadership.

Phase-0 deliverable — the correctness kernel, as running crates:

  1. controller-core — ControllerContext, reconciliation loop skeleton, transaction sequencing.
  2. southbound-protocol — wire schema (openflow_like.proto), frame codec, session state machine.
  3. packet-parser — Ethernet/VLAN/IPv4/TCP/UDP/ICMP parsers with bounds-checked zero-copy views.
  4. persistence-layer — WAL writer, checksum format, snapshot manifest (no replay yet).
  5. metrics-runtime / tracing-runtime — process-wide metrics registry and span propagation.
  6. conformance-harness — fixture runner wired to fixtures/ (empty corpus, non-empty framework).
  7. CI: reproducible build, cargo deny, cargo clippy --deny warnings, deterministic containers.

System boundaries.

  • Provides: OpenFlow-like southbound protocol, multi-table forwarding pipeline, topology graph, intent-to-flow compilation, controller HA via Raft, WAL/snapshot persistence, deterministic replay, northbound REST/gRPC API, full observability (metrics/traces/structured logs).
  • Delegates: TCP/IP stack and physical link layer to the host kernel (Linux networking — TAP/veth/ bridge/namespaces); TLS record layer to rustls; consensus algorithm correctness proofs to the published Raft paper (this blueprint implements Raft, does not re-derive it); container runtime and scheduling to Docker/Kubernetes.
  • Does NOT provide: ASIC/TCAM programming, a P4 compiler backend, MPLS, VXLAN-EVPN control plane, BGP, SRv6, DPDK/SmartNIC offload, kernel-bypass dataplane, or ONOS/OpenDaylight ecosystem compatibility. These are Non-Goals, not oversights — see §1 Non-Goals below.

Non-goals. Hardware-speed forwarding (Phase 0-8 target is 1-10 Mpps in software, not line-rate ASIC throughput); wide-area/inter-datacenter federation (single-region only, WAN federation is PhaseDeferred("§17")); full protocol parity with the OpenFlow 1.3 spec (subset: the match fields and actions in §8 only); multi-vendor hardware switch support (software switch only — dataplane-runtime is the only forwarding element).

Deployment model. Primary: 3-node controller quorum (Raft) behind an ingress gateway, 10-500 software switches (switch-agent + dataplane-runtime per node), east-west controller replication over mTLS, Kubernetes StatefulSet for controllers / DaemonSet for switch agents (see deployment-assets/k8s/). Secondary: single-node laptop/CI deployment for deterministic conformance runs — same binaries, docker-compose.yml topology, no HA.

Target operators. Datacenter network SREs operating the controller quorum; security policy teams authoring intents via northbound API; systems/distributed-systems engineers extending the reconciliation and clustering layers; observability engineers consuming the metrics/trace surface defined in §24.

What later phases unlock. Phase 1 unlocks authenticated switch sessions; Phase 2-3 unlock a running forwarding pipeline; Phase 4-5 unlock closed-loop reconciliation and live topology; Phase 6-7 unlock crash-safe persistence and HA; Phase 8 unlocks declarative policy; Phase 9 unlocks full production observability — the system is not "done" (operable) until Phase 9.

Recommended language: Rust. Rationale: ownership model gives deterministic drop-based resource cleanup (critical for WAL fsync ordering and session teardown), a data race at compile time would silently corrupt flow-table state in a GC'd language, the async ecosystem (Tokio) matches the actor-per-session model in ADR-19, and cargo fuzz/proptest give the parser and protocol-decoder fuzzing coverage this domain requires (malicious or malformed switches are an explicit threat surface, §22). Rejected: Go — GC pauses interact badly with p99 flow-mod ack targets (§4) and its weaker generic/ownership story complicates the zero-copy packet-parser (packet-parser/src/*.rs); C++ — memory-safety risk in a parser that faces untrusted network input is unacceptable given the threat model (§22), and its tooling for reproducible builds/fuzzing is weaker than Rust's. Go and Python remain secondary languages for operational tooling and topology simulation respectively (the language-choice detail above is folded into ADR-01).

Prerequisites. TCP/IP and Ethernet switching fundamentals, Raft/Paxos consensus, async Rust (Tokio), Linux networking (bridges, namespaces, TAP/veth), WAL/snapshot persistence patterns, lock-free/RCU concurrency, TLS/PKI, and enough packet-processing background to reason about zero-copy parsing and cache-line layout.

Estimated timeline. Phase 0: 6-10 weeks. Full system (Phase 0-9, single-operator pace): 9-14 months. HA + scale hardening beyond Phase 9: additional 4-6 months. Full conformance + operational maturity (fixture corpus breadth, chaos-test coverage): additional 3-5 months.

2. Why Build This

SDN decoupled forwarding from control: instead of every switch running distributed routing logic, a logically centralized controller computes policy and programs dumb (or programmable) forwarding elements. OpenFlow (McKeown et al., SIGCOMM 2008) made this concrete with a wire protocol; Onix and ONOS turned "centralized" into "distributed-but-consistent"; production hyperscale networks (Google B4) proved SDN traffic engineering at WAN scale. Building this system from scratch forces mastery of the exact mechanisms that make centralized control safe: deterministic reconciliation (desired vs. observed state), lease-fenced leadership (no split-brain flow programming), WAL-backed crash recovery, and RCU-style topology snapshots that let readers never block writers.

This is the same skeleton as a distributed database (controller cluster = replicated state machine), a message broker (event journal = append-only log with consumer cursors), and a stream processor (reconciliation loop = continuous diff-and-converge) — wearing a networking costume. The transferable muscle is: consensus-backed control planes, protocol engineering against adversarial peers, and deterministic replay as a debugging primitive.

What Mastery Looks Like

  • Can explain why flow-mod ordering must be monotonic per-switch and what breaks if it is not (transaction reordering corrupts multi-table goto-table chains) — Phase 4 (§16).
  • Can design and defend a lease-fencing scheme that prevents two Raft leaders from ever issuing conflicting flow-mods during a network partition — Phase 7 (§19).
  • Can build a zero-copy, bounds-checked packet parser that survives an AFL/cargo-fuzz corpus without panics or OOB reads — Phase 2 (§14).
  • Can reason about RCU-snapshot topology reads under concurrent graph mutation without introducing torn reads — Phase 5 (§17).
  • Can design a WAL + snapshot compaction scheme with a bounded recovery-time objective and prove it against injected corruption — Phase 6 (§18).
  • Can compile a declarative intent (ACL/VLAN/path) into conflict-free flow rules with deterministic output for the same input — Phase 8 (§20).
  • Can instrument an asynchronous, queue-heavy distributed system so that every state transition is traceable end to end during a live incident — Phase 9 (§21).

Northbound clients are untrusted and cross the API gateway's AuthN/AuthZ/audit boundary before touching controller internals (§22 T1-T2). The controller cluster is the sole writer of desired state; it is a Raft-replicated quorum so no single node's crash loses acknowledged intent (I3-I4). The persistence layer and event journal are two views of the same append-only discipline: the WAL is the durability primitive, the journal is the replay/debugging primitive; both are populated inside the same transaction boundary (ADR-16). The southbound session layer is a hard protocol and trust boundary — every message is length-framed, versioned, and validated before it can reach flow-table-engine state (§22 T3-T5). The dataplane runs one packet-worker per core with NUMA-aware queue partitioning (§4); it is intentionally the least "smart" component — correctness lives in the controller, the dataplane executes what it is told and reports what it observed.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every control-plane state transition must be replayable byte-for-byte from the event journal · Tradeoff: forbids non-deterministic sources (wall-clock branching, unordered map iteration) in hot paths, adds serialization discipline · Operational: enables replay-framework differential testing against production incidents · Violated: unreproducible incidents, silent reconciliation divergence, split-brain masked as "flaky".
  • P2 — Backpressure Everywhere. Rule: every queue (southbound ingress, event-journal, gRPC server) has an explicit bounded capacity and a documented shed policy · Tradeoff: bounded queues reject work under load instead of buffering indefinitely · Operational: queue-depth metrics (§21) are first-class SLO inputs · Violated: unbounded queues cause cascading OOM and latency collapse under any sustained producer/consumer imbalance.
  • P3 — Crash-Only Recovery. Rule: no subsystem may require graceful shutdown to remain correct; recovery is always WAL replay + snapshot load, never in-memory state migration · Tradeoff: forces every mutation through the WAL even when a graceful path exists · Operational: chaos tests kill -9 every process, never SIGTERM-only · Violated: "clean shutdown" bugs hide until the first unclean one, then cause data loss.
  • P4 — Observability By Default. Rule: every async boundary emits a metric, a span, and a structured-log correlation ID before it ships · Tradeoff: instrumentation overhead budgeted into §4's CPU targets, not treated as free · Operational: tracing-runtime spans are mandatory code-review gates, not optional annotations · Violated: incidents become undebuggable; blast radius cannot be bounded (§23).
  • P5 — Explicit Ownership. Rule: no shared-mutable state without a documented single-writer or RCU-reader contract in the type's doc comment · Tradeoff: more boilerplate ownership annotation in controller-core/topology-engine types · Operational: code review checklist item, enforced by clippy lint config where mechanically possible · Violated: data races become logic races — harder to detect, identical blast radius.
  • P6 — Stable Wire Compatibility. Rule: southbound protocol changes are version-gated (Hello capability negotiation) and additive within a major version · Tradeoff: cannot remove a message type without a major-version southbound break · Operational: southbound-protocol conformance fixtures pin every wire version pairwise; applied via ADR-03 · Violated: a controller upgrade silently drops legacy switches mid-migration.
  • P7 — Bounded Resource Usage. Rule: every subsystem declares a memory ceiling, a queue ceiling, and a CPU budget in §4 before it ships code · Tradeoff: requires upfront capacity modeling (§32) rather than "measure in prod and fix later" · Operational: ceilings are enforced via cgroups in deployment-assets/k8s/ · Violated: one subsystem's leak starves the entire node — no failure isolation.
  • P8 — Replayability First. Rule: every event with control-plane consequence is serialized into event-journal before it is considered "handled" · Tradeoff: adds a serialization/append step to every hot-path decision · Operational: replay-framework is a first-class CI gate, not a debugging afterthought · Violated: incident reconstruction becomes guesswork; postmortems lack ground truth (§23).
  • P9 — Fail Closed. Rule: authentication, authorization, or schema-validation failure always rejects the operation; there is no permissive fallback path · Tradeoff: a misconfigured auth policy blocks legitimate traffic rather than degrading silently · Operational: audit log emits every rejection with reason code · Violated: a single auth bug becomes an open control plane (§22 T1).
  • P10 — Isolation of Failure Domains. Rule: a single switch's malformed session, crash, or Byzantine behavior must not destabilize the controller quorum or other switch sessions · Tradeoff: per-session actor isolation costs more memory than a shared connection pool · Operational: switch-agent sessions run as independently-supervised tasks (ADR-19) · Violated: one bad switch takes down the whole control plane — the opposite of "logically centralized".
  • P11 — Single-Writer Invariant. Rule: only the current Raft leader may mutate desired state; followers serve reads from immutable snapshots · Tradeoff: write availability is bounded by quorum health, not per-node · Operational: enforced by lease-epoch checks (I12) at every mutation entry point · Violated: concurrent writers produce conflicting flow-mods — I3 breaks, dataplane state diverges from any single source of truth.
  • P12 — Idempotent Southbound Operations. Rule: every flow-mod carries a transaction ID such that a retried delivery has no additional effect beyond the first application · Tradeoff: switch-side dedup state must be bounded and aged (interacts with P7) · Operational: retried flow-mods are visible in metrics-runtime as a distinct counter from first-attempts · Violated: TCP-retransmit-driven duplicate delivery double-applies a rule, corrupting flow-table state under exactly the conditions (packet loss, §4) the system is meant to tolerate.

8. Domain Model — Protocol & Forwarding State

Switch identity. A switch is identified by an immutable (datapath_id, generation) pair; the generation increments only on controller-initiated re-registration (never on transient link flap), preventing a stale switch record from being mistaken for a live one after a reconnect. Capability bitmaps are negotiated once per session and quarantined under I9.

Flow rule model. A flow rule is scoped to (table_id, priority) and carries match fields, an ordered instruction list, a cookie (operator-assigned correlation token, not a security token), and independent idle/hard timeouts. Priority resolves overlapping matches within a table; goto-table instructions chain rules across tables and must not cycle (checked at compile time by flow-compiler, §20).

Match fields (subset of OpenFlow 1.3): ingress port, Ethernet src/dst, VLAN ID, IPv4 src/dst, TCP src/dst port, UDP src/dst port, IP protocol number, and one 64-bit metadata register for cross-table pipeline state. Each field is independently maskable (wildcard match).

Action semantics: output(port), drop, set-field(field, value), push-vlan(tpid), pop-vlan, goto-table(id), group(id). Actions execute in list order within an instruction; goto-table must be the terminal instruction in its list (enforced at parse time, not runtime branching — a static structural check, §14).

11. Core Schema & Types

Signatures only — no method bodies. Every type is annotated for ownership, mutation, concurrency, persistence, serialization, and compatibility.

struct SwitchId { datapath_id: u64, generation: u64, capabilities: CapabilityBitmap }
// ownership: owned by topology-engine registry, immutable after construction (I5/I9)
// mutation: none — a capability renegotiation constructs a new SwitchId with generation+1
// concurrency: Copy + Send, safe to share across session actors without locking
// persistence: WAL-logged on registration; snapshot field
// serialization: protobuf, stable field numbers (ADR-06); compatibility: additive-only (P6)

struct FlowRule { table_id: u8, priority: u16, match_fields: MatchFields,
    instructions: InstructionList, cookie: u64, idle_timeout: Duration, hard_timeout: Duration }
// ownership: owned by flow-table-engine::Table, single-writer per table (P11)
// mutation: replace-only (atomic install/replace, never in-place edit) — flow-table-engine
// concurrency: read via RCU snapshot (topology-engine::graph pattern reused, I6)
// persistence: WAL entry per install/replace/delete; not itself snapshotted (derived from WAL)
// serialization: protobuf; compatibility: table_id/priority/cookie are wire-stable since v1

struct FlowDescriptor { flow_id: FlowId, version: u32, switch_id: SwitchId,
    desired_state: FlowRule, observed_state: Option<FlowRule>, install_epoch: LeaseEpoch }
// ownership: controller-core::diff_engine, single authoritative copy per leader
// mutation: desired_state set by flow-compiler; observed_state set by southbound stats collector
// concurrency: guarded by per-flow_id shard lock (bounded shard count, §4 FD budget)
// persistence: desired_state WAL-logged; observed_state is not durable (rebuilt from stats)
// serialization: protobuf; compatibility: backward-compatible field addition only (P6)
enum SouthboundMessage { Hello(ProtocolVersion), EchoRequest(Nonce), EchoReply(Nonce),
    FeaturesRequest, FeaturesReply(CapabilityBitmap), FlowMod(FlowRule, TxnId),
    PacketIn(PacketView, IngressPort), PacketOut(Buffer, ActionList),
    ErrorReply(ErrorCode, TxnId), StatsRequest(StatsQuery), StatsReply(StatsPayload) }
// ownership: constructed per-message, moved through southbound-protocol::frame codec
// mutation: immutable once constructed
// concurrency: Send, one decode/encode per session actor (ADR-09)
// persistence: FlowMod/PacketIn variants journaled (P8); Echo/Stats are not
// serialization: protobuf tagged union; compatibility: new variants require version bump (P6)

struct EventRecord { sequence_no: u64, timestamp: MonotonicTs, actor: ActorId,
    event_type: EventType, payload: Bytes, checksum: Crc32c }
// ownership: event-journal, append-only writer, single sequence generator per node
// mutation: none post-append (I7 replay determinism depends on immutability)
// concurrency: Sync via single-writer append + Arc-shared read snapshots
// persistence: this IS the persistence primitive — journal segment record
// serialization: length-framed protobuf + checksum; compatibility: sequence_no never reused

struct TopologyGraph { nodes: NodeMap, edges: EdgeMap, adjacency_index: AdjacencyIndex,
    generation: u64 }
// ownership: topology-engine, single mutator (leader only, P11)
// mutation: copy-on-write publish, old generation retained until last reader drops (RCU, I6)
// concurrency: Arc<TopologyGraph> snapshot handed to readers, no locking on read path
// persistence: periodic snapshot; incremental deltas WAL-logged (persistence-layer)
// serialization: protobuf; compatibility: adjacency_index is derived, never serialized directly
struct ControllerContext { node_id: NodeId, leadership_state: ControllerState,
    topology_snapshot: Arc<TopologyGraph>, flow_registry: FlowRegistry,
    replay_cursor: ReplayCursor, metrics_registry: Arc<MetricsRegistry> }
// ownership: one per controller process, root of the reconciliation loop
// mutation: leadership_state transitions via controller-cluster (§8 state machine)
// concurrency: interior fields individually guarded; struct itself is not Clone
// persistence: replay_cursor is the durable field; rest is derived/rebuilt on recovery
// serialization: not directly serialized — reconstructed from WAL + snapshot on startup

struct Intent { intent_id: IntentId, kind: IntentKind, spec: IntentSpec,
    dependency_ids: Vec<IntentId>, compiled_epoch: Option<LeaseEpoch> }
// kind ranges over Acl | Vlan | Path
// ownership: intent-engine, submitted via northbound-api, owned until compiled or rejected
// mutation: immutable after admission; superseding intent is a new IntentId (P1 determinism)
// concurrency: Send + Sync, read by flow-compiler's dependency_graph without locking
// persistence: WAL-logged on admission and on compile/rollback transitions
// serialization: JSON over gRPC/REST at the edge, protobuf internally; compatibility: additive

struct LeaseGrant { epoch: LeaseEpoch, holder: NodeId, granted_at: MonotonicTs, ttl: Duration }
// ownership: controller-cluster, one active grant cluster-wide (I3, I12)
// mutation: replace-only via new election; epoch strictly increasing
// concurrency: read via atomic load on the hot write-admission path
// persistence: WAL-logged and Raft-replicated (this is the fencing token)
// serialization: protobuf; compatibility: epoch/holder fields wire-stable since v1

struct PacketView<'a> { raw: &'a [u8], offsets: FieldOffsets }
// ownership: borrowed, zero-copy view into a receive buffer owned by dataplane-runtime::pipeline
// mutation: none — parsing never mutates the underlying buffer
// concurrency: not Send (borrows a per-worker buffer); confined to one packet-worker task
// persistence: never persisted directly; PacketIn re-encodes a copy for the wire
// serialization: not serialized — internal-only zero-copy accessor (ADR-18)

12.1 Objectives

Stand up a reproducible Rust workspace and the correctness primitives every later phase depends on: the error taxonomy, the ControllerContext/EventRecord skeleton types (§11), and a CI gate that makes non-determinism (P1) visible before it ships. No networking, no dataplane yet — this phase's scope is the build system and the type/observability skeleton only.

12.2 Detailed Implementation Steps

Create the Cargo workspace with the 18 member crates from §10; wire deny.toml (ADR-03) and cargo audit into CI (ci.yml). Land the workspace-wide error taxonomy (thiserror-based, one enum family per crate boundary, no anyhow in library code) referenced by every later phase's N.2. Land skeletal ControllerContext, EventRecord, and SwitchId (§11) with derives only — no logic. Stand up tracing-runtime::spans bootstrap (P4) so every subsequent crate can emit a span from day one. Configure rustfmt/clippy --deny warnings as a merge-blocking gate. Build deterministic, hash-stable Docker images (pinned base digest, no apt-get upgrade) per ADR-20. Write the module-naming convention doc (docs/adr/0001-language-choice.md carries the ADR-01 narrative this phase operationalizes).

12.3 Deliverable

A workspace that compiles, lints clean, and produces a hash-identical container image across two consecutive CI runs on the same commit; cargo test --workspace passes with zero tests failing (zero tests exist yet — this asserts the harness itself runs).

12.4 Acceptance Criteria

CI green on Linux x86_64 and ARM64 (§4 NUMA/CPU assumption); container image digest identical across 2 consecutive builds of the same commit; zero unsafe blocks outside packet-parser (reserved for Phase 2); cargo deny check zero advisories; workspace builds in < 4 minutes cold.

12.5 Conformance Fixtures

  • fixtures/build/reproducible-build.txt — expected digest manifest for the deterministic image.
  • fixtures/ci/workspace-lint.json — golden clippy/rustfmt output, zero warnings expected.
  • fixtures/ci/malformed-cargo-toml.txt — a workspace member with a syntax error; expected: CI fails at the manifest-parse step, not mid-build.

12.6 Pitfalls

  • Dependency drift: a transitive dependency updates between CI runs without a Cargo.lock commit — manifestation: non-deterministic CI failures unrelated to the diff; root cause: lock file not committed or not verified in CI; debugging: cargo lock diff against the previous green commit; signal: cargo audit flags a version the PR didn't touch; recovery: pin via deny.toml and re-vendor.
  • Toolchain skew: contributors on different Rust versions produce different clippy lint sets; root cause: no rust-toolchain.toml enforcement; recovery: rustup show active-toolchain check in CI preflight.

12.7 Performance Concerns

CI wall-clock time grows with workspace crate count — mitigate with sccache and incremental per-crate caching, not by skipping crates. Container layer invalidation from unpinned base images forces full rebuilds; pin digests (ADR-20) to keep layer cache hit rate high.

12.8 Edge Cases

Cross-platform path normalization (Windows contributors are unsupported but CI must fail clearly, not silently mis-lint); ARM64 build variance in transitive C-dependency crates (ring via rustls, ADR-21) requires an explicit ARM64 CI runner, not emulation.

12.9 Failure Analysis

Primary risk: irreproducible environments make every later phase's bug reports untrustworthy. Detection: digest-mismatch alarm on the reproducible-build fixture. Containment: pinned toolchain + pinned base image + Cargo.lock committed. Blast radius if this phase is wrong: every later phase inherits it silently — this is why it is Phase 0, not a "later cleanup".

12.10 Operational Notes

Operators must be able to reproduce any released build from its Git tag and verify the SBOM (legal/NOTICE + generated CycloneDX) and image signature before deploying. Metric: ci_build_duration_seconds. No rollback concept yet — nothing is deployed.

13. Phase 1 — Southbound Protocol Foundation

13.1 Objectives

Implement the authenticated, versioned wire transport between controller and switch: session negotiation, heartbeats, and message framing, per the OpenFlow Switch Specification 1.3.5 subset (§8) and RFC 8446 (TLS 1.3). No flow-table logic yet — sessions only.

13.2 Detailed Implementation Steps

Define the protobuf schema (southbound-protocol/proto/openflow_like.proto, ADR-06) for the SouthboundMessage enum (§11). Implement frame.rs — length-prefixed frame encoder/decoder with a hard max-frame-size bound (prevents unbounded-allocation DoS, ties to P7). Implement negotiation.rs — Hello/FeaturesRequest/FeaturesReply handshake with capability bitmap negotiation (I9). Implement session.rs as one Tokio task per switch (ADR-09, P10 failure isolation) with a bounded inbound queue (P2, I8). Add jittered heartbeat scheduling (avoids the thundering-herd pitfall below). Wire rustls (ADR-21) for mTLS. Add cargo-fuzz targets (fuzz/fuzz_targets/protocol_fuzz.rs, ADR-14) against the frame decoder from day one.

13.3 Deliverable

Controller and a simulated switch (test harness, not real hardware) complete a TLS handshake, negotiate protocol version and capabilities, and sustain heartbeats without operator intervention.

13.4 Acceptance Criteria

10,000 concurrent sessions stable for 10 minutes (§4 concurrency budget); heartbeat RTT p95 < 500 ms under nominal load; fuzz corpus of 50,000 executions with zero panics/OOB; malformed frame rejection verified against all fixtures below.

13.5 Conformance Fixtures

  • fixtures/southbound/malformed-frame.bin — truncated length prefix; expected: ErrorReply with BAD_FRAME, session not torn down.
  • fixtures/southbound/invalid-version.bin — unsupported protocol version in Hello; expected: session rejected before FeaturesRequest.
  • fixtures/southbound/duplicate-transaction.bin — replayed FlowMod TxnId; expected: second delivery is a no-op ack (P12 idempotence), not a double-apply.

13.6 Pitfalls

  • Heartbeat storms: manifestation — CPU spike every N seconds across all sessions; root cause — unjittered fixed-interval timers synchronized at session-start; debugging — histogram of heartbeat send timestamps shows clustering; signal — sb_heartbeat_batch_size metric spikes; recovery — jittered scheduling (±20% of interval) per session.
  • TLS handshake amplification under connection-storm reconnect: manifestation — CPU-bound handshake queue backs up after a controller restart when all switches reconnect at once; root cause — no reconnect jitter on the switch-agent side; recovery — exponential backoff + jitter on reconnect.

13.7 Performance Concerns

TLS handshake CPU cost dominates at 10k-session cold-start (mitigate: session resumption tickets); serialization allocation churn per message (mitigate: buffer pooling in frame.rs); syscall overhead from per-message write() (mitigate: batched flow-mod delivery, §16.7 for the compiler side of batching).

13.8 Edge Cases

Half-open TCP sessions (peer crashed without FIN) — detected only by heartbeat timeout, not TCP keepalive alone; TxnId sequence rollover at 2^64 (effectively unreachable but must not panic); simultaneous Hello from both sides during reconnect race.

13.9 Failure Analysis

Failure class: controller session-table exhaustion under a reconnect storm. Detection: FD-budget alarm (§4 FD budget = 65,536). Blast radius: new session admission blocked, existing sessions unaffected (P10 isolation holds). Recovery: connection shedding with exponential backoff signaled to switches via ErrorReply(BUSY).

13.10 Operational Notes

Metrics: sb_active_sessions, sb_heartbeat_rtt_ms, sb_queue_depth{session}. Tracing span: southbound.session.lifecycle. Structured-log fields: datapath_id, session_id, txn_id. Rolling a southbound protocol change requires a version bump negotiated at Hello (P6, ADR-06).

14. Phase 2 — Packet Parser and Match Engine

14.1 Objectives

Implement deterministic, zero-copy, bounds-checked parsing for Ethernet/VLAN/IPv4/TCP/UDP/ICMP (RFC 791, RFC 793, Stevens ch. 3-9) and the match-field extraction the flow-table engine (Phase 3) will consume. This is the only crate permitted unsafe (ADR-18), and only inside bounds-checked accessor functions.

14.2 Detailed Implementation Steps

Implement one parser module per protocol (ethernet.rs, vlan.rs, ipv4.rs, tcp.rs, udp.rs, icmp.rs) returning PacketView (§11) — an offset table over the original buffer, never a copy. Every accessor bounds-checks against raw.len() before indexing (ADR-18's "control over ownership" rationale exists precisely so this check is auditable in one place). Implement the match trie (dataplane-runtime::match_engine) as a priority-ordered wildcard/prefix structure keyed on the §8 match-field set. Add differential testing against a second, naive reference parser (P1 determinism — two independent implementations must agree byte-for-byte). Land fuzz/fuzz_targets/parser_fuzz.rs (ADR-14) seeded from Stevens' worked examples.

14.3 Deliverable

A library that takes a raw Ethernet frame and returns either a fully-decoded MatchFields (§8) or a typed parse error — no panics, no OOB reads, for any byte sequence of any length.

14.4 Acceptance Criteria

100% pass on a 200-case parser conformance corpus (fixtures/parser/corpus/); zero cargo-fuzz-discovered OOB/panic after a 24-hour fuzz run; deterministic parser replay: same input bytes produce a byte-identical MatchFields across 1,000 repeated parses (I7-style check scoped to this crate).

14.5 Conformance Fixtures

  • fixtures/parser/malformed-ipv4.bin — header length field exceeds buffer; expected: ParseError::Truncated, no panic.
  • fixtures/parser/truncated-vlan.bin — VLAN tag present but EtherType field missing; expected: ParseError::Truncated at the correct offset.
  • fixtures/parser/oversized-header.bin — IHL claims 60-byte IPv4 header on a 40-byte buffer; expected: rejected before any field read.

14.6 Pitfalls

  • Unaligned memory access: manifestation — SIGBUS on ARM64 for a naive *const u32 cast over an odd-offset field; root cause — VLAN tag insertion shifts subsequent header alignment; debugging — reproduce under qemu-user ARM64; signal — crash only on ARM64 CI runner, never x86_64; recovery — use u32::from_be_bytes on a copied 4-byte slice, never a pointer cast (also closes the ADR-18 "control over ownership" gap).
  • Off-by-one in wildcard mask application: manifestation — a /31 vs /32 match silently matches one extra host; root cause — mask arithmetic using << without clamping at bit-width; signal — differential test against the naive reference parser disagrees on exactly boundary addresses.

14.7 Performance Concerns

Branch-prediction misses in protocol-dispatch (mitigate: jump table keyed on EtherType/IP protocol, not a chained if-ladder — described as dispatch structure, not control flow); trie cache locality for the match engine (mitigate: node layout sized to cache-line width, ties to Mara Bos ch. 2 memory-ordering discussion in §5); per-packet allocation must be zero on the hot path (PacketView borrows, never allocates, §11).

14.8 Edge Cases

Nested/double VLAN tags (QinQ) — must not double-decrement the "remaining bytes" budget; malformed IPv4/TCP checksums (must be reported, not silently corrected); zero-length UDP payload; ICMP messages carrying a truncated inner IP header (used for path-MTU discovery, must not crash the inner-header parser).

14.9 Failure Analysis

Blast radius if the parser crashes: destabilizes the whole switch-runtime process, not just one flow (P10 violation risk — this is why parser isolation matters more here than anywhere else). Mitigation: run parser invocation inside a per-worker task with a panic boundary (catch_unwind at the task boundary only, not used for control flow) so one malformed packet degrades to a dropped packet, not a crashed dataplane.

14.10 Operational Notes

Metrics: parser_malformed_total{protocol}, parser_latency_ns histogram. Structured-log field: drop_reason on every discard. No wire-compatibility concern — this crate has no external protocol surface, only internal buffer contracts.

15. Phase 3 — Flow Table Runtime

15.1 Objectives

Implement the multi-table match/action pipeline (§8) with priority ordering, timeouts, group tables, and RCU-snapshot reads, consuming Phase 2's MatchFields and enforcing I1 (ordering) and I10 (no orphan group refs). Hardware TCAM offload and eBPF-accelerated execution stay software- only for now — both are PhaseDeferred("§15"), un-deferred only if the software Mpps ceiling (§4) proves insufficient for a target deployment.

15.2 Detailed Implementation Steps

Implement table.rs as a priority-ordered rule set per table_id (§8), backed by the match trie from Phase 2. Implement atomic flow replacement: install/replace/delete publish a new RCU snapshot (Arc-swap), never mutate in place — matches the TopologyGraph pattern in §11 and enforces I6-style generation monotonicity for flow tables. Implement aging.rs — idle/hard timeout scheduler as a min-heap keyed on expiry, one sweep task per table shard. Implement group_table.rs with referential integrity checked at install time (I10). Implement gc.rs for expired-rule reclamation, batched (P7 bounded resource usage). Add flow statistics counters consumed by Phase 9's metrics surface. Batch-install support: a single southbound FlowMod burst applies as one atomic snapshot publish, not N separate publishes (performance, ties to ADR-17's columnar index rationale).

15.3 Deliverable

A switch runtime that installs, matches, executes, ages out, and garbage-collects flow rules across multiple tables with goto-table chaining, observable via a flow-dump CLI command.

15.4 Acceptance Criteria

Sustains 250,000 installed flows (§4 flow-table capacity target) with p99 lookup latency < 50 microseconds; zero leaked rules 60 seconds after hard-timeout expiry in a 10,000-flow churn test; deterministic replay equivalence: replaying the same install/expire sequence twice yields an identical table snapshot hash (I7).

15.5 Conformance Fixtures

  • fixtures/flow-table/overlapping-rules.json — two rules, same table, overlapping wildcard match, different priority; expected: higher priority wins deterministically.
  • fixtures/flow-table/timeout-expiry.json — rule with 1s idle timeout, no traffic; expected: expired and GC'd within one sweep interval.
  • fixtures/flow-table/invalid-goto-table.json — goto-table instruction not terminal in its list; expected: rejected at install, ErrorReply(BAD_INSTRUCTION).

15.6 Pitfalls

  • Rule shadowing: manifestation — a broad low-priority rule never fires because a wildcard higher-priority rule shadows it entirely; root cause — compiler (Phase 8) didn't detect the shadow before install; debugging — flow_dump overlap-report tool; signal — flow-hit counter stuck at zero for a rule expected to match traffic; recovery — none at runtime (this is a compile-time defect, surfaced back to flow-compiler's conflict_detector, §20).
  • Timeout-scheduler starvation under table-shard imbalance: manifestation — one shard's sweep task falls behind under skewed flow distribution; root cause — sharding key doesn't account for hot switches; recovery — per-shard sweep-lag metric triggers rebalance.

15.7 Performance Concerns

Flow-table fragmentation from high churn (mitigate: periodic compaction of the RCU-snapshot generation chain so old generations don't pin memory, P7); lock contention on the group-table referential check under concurrent install bursts (mitigate: per-table_id sharding, matches ADR-09's isolation philosophy at a finer grain).

15.8 Edge Cases

Cyclic goto-table references (table 3 -> table 5 -> table 3) — rejected at install by a static cycle check, not detected at runtime via recursion depth; conflicting metadata-register writes across chained tables; a flow whose hard_timeout fires mid-lookup (must not return a half-evicted rule — RCU snapshot read is the fix, since the reader holds a consistent generation).

15.9 Failure Analysis

Failure: observed flow-table state diverges from controller's desired state (e.g. after a partial batch-install crash mid-publish). Detection: reconciliation diff-engine (Phase 4) flags mismatch. Containment: RCU snapshot publish is atomic — a crash mid-publish leaves the prior generation intact, never a torn table. Recovery: reconciliation replay re-issues the batch.

15.10 Operational Notes

Operators require flow_dump (table occupancy, per-rule hit counters) and ft_table_occupancy{table_id} / ft_gc_reclaimed_total metrics. Rollback of a bad flow-table change is a new install, not a schema migration — flow tables have no persistent schema beyond FlowRule's wire-stable fields (§11).

16. Phase 4 — Controller Core and Reconciliation

16.1 Objectives

Build the authoritative reconciliation loop: desired-state registry, observed-state collector, diff engine, and transaction scheduler that together keep dataplane state converged with controller intent under P1 (determinism) and P11 (single-writer).

16.2 Detailed Implementation Steps

Implement context.rs (ControllerContext, §11) as the reconciliation loop's root. Implement diff_engine.rs computing desired-vs-observed deltas per FlowDescriptor (§11), following the Onix model (Koponen et al. 2010, §5) of separating authoritative intent from derived observed state. Implement rule_planner.rs for dependency ordering (a goto-table target must exist before the referencing rule installs — I10 enforcement point). Implement transaction_scheduler.rs assigning monotonic per-switch TxnIds (I1). Implement idempotent retries (P12) keyed on TxnId. Implement drift_detector.rs comparing stats-collector snapshots against desired state on a fixed interval, feeding the reconciliation-lag metric (Phase 9).

16.3 Deliverable

A controller that, given a desired-state set and a live switch session, converges dataplane flow-table contents to match — and reconverges automatically after a switch restart or observed mismatch, without operator intervention.

16.4 Acceptance Criteria

Eventual convergence within 200 ms p95 (§4 reconciliation p95) after a simulated switch restart in a 10,000-flow test topology; zero duplicate rule installs across 100 injected reconnect events; deterministic replay output — two reconciliation runs over the same event-journal segment produce identical install/delete sequences (I7).

16.5 Conformance Fixtures

  • fixtures/reconciliation/switch-restart.trace — switch drops and reconnects mid-flow-churn; expected: full flow-table re-sync within the p95 target, no duplicate installs.
  • fixtures/reconciliation/duplicate-flow.trace — two overlapping FlowMod requests for the same desired rule; expected: single install, second is a no-op (P12).
  • fixtures/reconciliation/stale-observed-state.trace — stats collector reports a rule installed 1 minute after it was superseded; expected: stale-observation detector discards it.

16.6 Pitfalls

  • Reconciliation oscillation: manifestation — the same rule is repeatedly reinstalled every diff cycle; root cause — observed-state timestamps aren't monotonic relative to desired-state versions, so the diff engine can't tell "already applied" from "needs reapply"; debugging — compare FlowDescriptor.version sequences across cycles; signal — recon_reinstall_total for a single flow_id climbing without bound; recovery — version-gate the diff (only reinstall if observed.version < desired.version).
  • Diff-engine cost blowup on large topologies: manifestation — reconciliation p95 exceeds budget under 200k+ tracked flows; root cause — full-scan diff instead of incremental dirty-set tracking; recovery — dirty-flow queue fed by drift_detector instead of full rescans.

16.7 Performance Concerns

Diff-engine CPU amplification on full rescans (mitigate: incremental dirty-set, above); queue fanout when one topology event triggers reconciliation across many switches simultaneously (mitigate: batched transaction scheduling per switch, ties to §13.7's batched flow-mod delivery).

16.8 Edge Cases

Partial switch connectivity (session up, but stats collection channel degraded) — must not be conflated with full disconnect; stale acknowledgements arriving after a TxnId has already timed out and been retried under a new TxnId; a desired-state change arriving mid-reconciliation-cycle for the same flow_id.

16.9 Failure Analysis

Risk: reconciliation retry loops overwhelm a struggling switch, worsening its condition (a resource-exhaustion feedback loop). Detection: retry-rate metric per switch exceeding a threshold. Containment: bounded retry windows with exponential backoff per switch, not global. Recovery: circuit-break reconciliation for a specific switch while continuing for the rest — P10 isolation applied to a control-plane loop, not just sessions.

16.10 Operational Notes

Metrics: recon_convergence_duration_ms, recon_queue_depth, recon_reinstall_total{flow_id} (cardinality-bounded by sampling, ties to Phase 9's cardinality pitfall). Tracing span: controller.reconcile.cycle. Rollback: reconciliation has no separate rollback path — desired state is always the source of truth; "rollback" means submitting a new desired state.

17. Phase 5 — Topology Discovery and Graph Engine

17.1 Objectives

Build the authoritative topology model: LLDP-like discovery, an RCU-snapshot graph (§11 TopologyGraph), ECMP path generation, and failure-driven recomputation, enforcing I2 (no orphan links) and I6 (snapshot generation monotonicity). BGP-LS ingestion and EVPN control-plane interoperability are PhaseDeferred("§17") — this phase's graph is discovery-only, not a BGP speaker.

17.2 Detailed Implementation Steps

Implement discovery.rs — periodic LLDP-like probe emission and reception per switch port, jittered (avoids the discovery-storm pitfall below). Implement graph.rs and adjacency_index.rs as the copy-on-write structure described in §11: mutation publishes a new Arc<TopologyGraph> generation, readers hold the old generation until they drop it (RCU, per Mara Bos ch. 5-7, §5). Implement path_cache.rs and ecmp.rs — equal-cost multipath candidate generation recomputed on topology change, not per-packet. Implement link aging (a link not refreshed within N missed probes is pruned, I2). Implement partition handling — a node with zero live links is marked isolated, not deleted (preserves historical topology for postmortems, P8). Expose operator inspection APIs (topology diff streams) for Phase 9's dashboards.

17.3 Deliverable

A controller that discovers a live network graph from switch LLDP-like exchanges, recomputes ECMP paths on link failure, and publishes an immutable, versioned snapshot readers can consume without blocking the discovery writer.

17.4 Acceptance Criteria

Link-failure-to-recomputed-path convergence < 2 seconds p99 (§4 topology convergence target) in a 32-switch leaf-spine test topology (examples/topologies/leaf-spine.yaml); zero orphan links after 1,000 injected flap events; topology snapshot hash reproducible across two replays of the same discovery event sequence (I7).

17.5 Conformance Fixtures

  • fixtures/topology/topology-flap.trace — a link toggles up/down 50 times in 10 seconds; expected: converges to correct final state, no orphan links, bounded recompute count (not one recompute per flap — debounced).
  • fixtures/topology/asymmetric-link.trace — LLDP seen in one direction only; expected: link not admitted until bidirectional confirmation.
  • fixtures/topology/stale-lldp.trace — probe replay from a previous session generation; expected: rejected via generation fencing (I6).

17.6 Pitfalls

  • Discovery storms: manifestation — CPU/bandwidth spike as all switches probe simultaneously after a controller restart; root cause — unjittered fixed-interval LLDP emission, same class of bug as §13.6's heartbeat storm; recovery — jittered emission per switch.
  • Graph recompute explosion: manifestation — a single link flap triggers a full graph-wide ECMP recompute repeatedly; root cause — no debounce window between topology-change events; signal — topo_recompute_total far exceeds topo_link_change_total; recovery — coalesce changes within a short debounce window before triggering recompute.

17.7 Performance Concerns

Graph recompute cost scales with topology size — mitigate with incremental ECMP update (only recompute paths touching the changed link's endpoints) rather than full-graph Dijkstra/ECMP rerun; adjacency-index cache locality matters at 500-switch scale (§4 concurrency budget).

17.8 Edge Cases

One-way (asymmetric) links; duplicate switch IDs from a misconfigured switch reusing a datapath_id; a link whose two LLDP-reported endpoints disagree on link speed/capability; graph updates arriving out of causal order relative to switch-session registration.

17.9 Failure Analysis

Failure: topology split-brain — two controller views of the graph disagree during a network partition. Detection: generation-number divergence between expected and observed on rejoin. Containment: generation fencing (I6) — a stale generation's writes are rejected outright, never merged. Recovery: full graph rebuild from the current leader's live discovery state, old generation discarded.

17.10 Operational Notes

Metrics: topo_link_change_total, topo_recompute_total, topo_snapshot_generation, topo_orphan_link_total (I2). Tracing span: topology.discovery.probe. Operators consume topology diff streams via the northbound API for dashboard rendering (Phase 9).

18. Phase 6 — Persistence and Replay Infrastructure

18.1 Objectives

Implement the WAL and snapshot subsystem backing I4 (durability) and I11 (fsync-before-ack), and the replay cursor mechanics that make P1/P8 (determinism, replayability) enforceable rather than aspirational.

18.2 Detailed Implementation Steps

Implement wal.rs — segment writer with per-record CRC32c checksums (§11 EventRecord), segment rotation at a fixed size boundary, and an fsync policy batched to the RPO=1s ceiling (§4), per Petrov's WAL chapter (Database Internals, §5). Implement snapshot.rs and compaction.rs — periodic snapshot with version metadata, WAL truncation only after a snapshot durably covers the truncated range (never truncate speculatively). Implement cursor.rs (event-journal) as the replay-position bookmark, itself WAL-logged so a crash mid-replay resumes correctly. Implement crash recovery: on startup, load latest valid snapshot, replay WAL tail from the snapshot's cursor, verify checksums, quarantine (not delete) any segment that fails checksum. Add fuzz/fuzz_targets/wal_fuzz.rs targeting the segment parser (ADR-14).

18.3 Deliverable

A controller that survives kill -9 at any point and recovers to a consistent state — verified by replaying its own WAL — within the RTO/RPO budget (§4).

18.4 Acceptance Criteria

Replay reproduces identical state across 3 repeated recovery runs from the same WAL (I7); WAL corruption detection verified against 20 injected single-byte-flip fixtures with zero false negatives; snapshot restore completes in < 60 seconds for a 250,000-flow snapshot (§4 snapshot recovery target).

18.5 Conformance Fixtures

  • fixtures/persistence/corrupted-wal.bin — single-byte checksum mismatch mid-segment; expected: quarantine from that record forward, recovery proceeds from the last valid record.
  • fixtures/persistence/partial-snapshot.bin — snapshot file truncated mid-write (simulated crash during snapshot); expected: rejected at load, fall back to the prior snapshot + full WAL replay.
  • fixtures/persistence/replay-divergence.trace — two replays of the same segment intentionally fed a non-deterministic hook (test-only); expected: divergence detector (I7) fires.

18.6 Pitfalls

  • Torn writes: manifestation — a segment record is partially written when the process is killed mid-fsync; root cause — write() without an atomic record boundary; debugging — checksum covers the full record including length prefix, so a torn write always fails checksum, never silently parses as a different valid record; recovery — fsync at record boundaries only (ADR-16), never mid-record.
  • Compaction stalls: manifestation — snapshot write blocks the WAL append path; root cause — snapshot taken synchronously on the hot path instead of on a background task with its own memory budget; recovery — background compaction task, WAL continues appending concurrently.

18.7 Performance Concerns

fsync latency spikes on spinning disks or contended cloud volumes (mitigate: batched fsync within the RPO=1s ceiling, §4, rather than per-record fsync — the etcd wal/ pitfall noted in §5); compaction I/O competing with WAL append I/O (mitigate: separate volumes or I/O priority classes in deployment-assets/k8s/).

18.8 Edge Cases

Snapshot/WAL version mismatch after a binary upgrade (must reject and force full resync, not attempt a lossy in-place migration); disk-full mid-fsync (must fail the write loudly, never silently drop); clock skew affecting MonotonicTs fields (§11) — mitigated by ADR-23's monotonic-for-intervals rule, but cross-node comparison in cluster contexts needs explicit handling (Phase 7).

18.9 Failure Analysis

Failure: replay divergence — two replays of the same segment produce different state hashes. Detection: I7 assertion in conformance-harness. Blast radius: any downstream decision made from the diverged state is suspect; containment is to halt reconciliation for the affected node rather than proceed on unverified state. Recovery: binary-search the segment for the first diverging record, which localizes the non-determinism bug for the postmortem.

18.10 Operational Notes

Operators require WAL inspection (tools/wal-inspect.sh) and snapshot verification tooling. Metrics: wal_fsync_latency_ms, wal_segment_rotation_total, snapshot_restore_duration_ms. Migration: a WAL/snapshot format version bump requires a documented one-way migration path, never silent dual-format support.

19. Phase 7 — Controller Clustering and Consensus

19.1 Objectives

Implement the highly-available clustered controller: Raft-based leader election, log replication, and lease fencing (I3, I12), following Ongaro & Ousterhout 2014 and Burrows 2006 (§5).

19.2 Detailed Implementation Steps

Implement raft_transport.rs — RPC layer for RequestVote/AppendEntries over the same mTLS transport as southbound (reuse, not reimplementation, of the TLS stack). Implement election.rs with randomized election timeouts (avoids thrashing, below) per the Raft paper's exact recommendation. Implement lease.rs — the fencing token (§11 LeaseGrant) that closes the split-brain window Chubby-style (Burrows 2006, I12). Implement log_replication.rs and membership.rs for cluster reconfiguration. Implement read-index optimization so followers can serve stale-bounded reads without a full round trip. Implement heartbeat coalescing to bound control traffic at cluster scale. Add fixtures/cluster/ partition-injection tests exercising conformance-harness's chaos hooks.

19.3 Deliverable

A 3-node controller quorum that survives a leader crash with automatic failover, rejects split-brain writes under network partition, and replicates the WAL tail to followers with bounded lag.

19.4 Acceptance Criteria

Automatic failover completes within 5 seconds of leader crash detection (bounds into the RTO budget, §4); zero acknowledged-state loss across 50 injected leader-crash trials; stable quorum maintained under 20% random message loss for 10 minutes; replication lag p95 < 100 ms under nominal load.

19.5 Conformance Fixtures

  • fixtures/cluster/partition-majority.trace — the leader's partition retains quorum; expected: continues serving writes, minority partition steps down to FOLLOWER.
  • fixtures/cluster/partition-minority.trace — the leader's partition loses quorum; expected: leader steps down to DEGRADED (§8 state machine), rejects writes until quorum restored.
  • fixtures/cluster/rapid-election.trace — 10 consecutive elections within 30 seconds (adversarial timer injection); expected: eventual stable leader, no epoch reuse (I12).

19.6 Pitfalls

  • Election thrashing: manifestation — repeated elections with no stable leader; root cause — election timeouts synchronized across nodes (all nodes time out simultaneously and split the vote); debugging — plot election-start timestamps per node; signal — cluster_election_total climbing without a corresponding stable-leader period; recovery — randomized timeout jitter per the Raft paper's exact prescription (§5).
  • Quorum write amplification: manifestation — write latency degrades disproportionately as cluster size grows past 3-5 nodes; root cause — synchronous replication to every follower before ack; recovery — this system caps cluster size at odd counts ≤5 by design; larger clusters are PhaseDeferred("§19") (multi-region federation, deferred).

19.7 Performance Concerns

Quorum write amplification (above) bounds cluster size; heartbeat/AppendEntries coalescing reduces per-heartbeat overhead at the cost of slightly higher replication latency, a tradeoff tuned against the §4 controller-RTT assumption (0.5-5 ms intra-DC).

19.8 Edge Cases

Partial snapshot replication (a follower receives a snapshot chunk stream interrupted mid- transfer — must resume, not restart from zero); simultaneous candidate timeouts producing a split vote; a membership change committed but not yet applied when a crash occurs (must resume the configuration change from the log, not lose it).

19.9 Failure Analysis

Failure: split-brain leader issuance — two nodes both believe they hold the lease. Detection: epoch comparison at every write-admission check (I3/I12). Mitigation: lease epochs are monotonically increasing and Raft-replicated before use — a stale-epoch node's writes are mechanically rejected by any follower or switch that tracks the current epoch. Blast radius if this fails: conflicting flow-mods reach the dataplane — the single worst failure mode in this entire system, which is why I3/I12 exist as hard invariants, not best-effort checks.

19.10 Operational Notes

Metrics: cluster_quorum_health, cluster_replication_lag_ms, cluster_election_total, cluster_lease_epoch. Operator failover API allows a manual step-down for planned maintenance (graceful leadership transfer, avoids an election-induced write gap). Rollback of a cluster software upgrade requires quorum-by-quorum rolling restart, never a simultaneous restart of all three nodes.

20. Phase 8 — Intent Engine and Policy Compilation

20.1 Objectives

Build the declarative policy layer: ACL/VLAN/path intents (§11 Intent), conflict detection, and deterministic compilation into FlowRule sets, with atomic all-or-nothing deployment. A P4-target compiler backend and SAT-solver-based conflict detection are both PhaseDeferred("§20") — this phase ships a heuristic conflict detector and a single software-pipeline compiler target only.

20.2 Detailed Implementation Steps

Implement intent_schema.rs and acl_model.rs (§11 IntentKind). Implement dependency_graph.rs — intents may depend on other intents (a path intent depending on a VLAN intent's segmentation); cycles are rejected at admission, not at compile time (fail fast). Implement conflict_detector.rs — overlapping-ACL and shadow-rule detection (closes the gap noted in §15.6's rule-shadowing pitfall, moving detection upstream of install). Implement rule_compiler.rs — deterministic intent-to-FlowRule compilation (P1): identical intent input must produce byte-identical compiled output. Implement dry_run.rs for operator preview before commit and rollback.rs for transactional rollback of a partially-applied intent batch. Emit policy audit events (P4, feeds §22 T1 mitigation).

20.3 Deliverable

Operators submit declarative ACL/VLAN/path intents via the northbound API and receive either a compiled, deployed flow-rule set or a structured conflict report — never a partial, silent deployment.

20.4 Acceptance Criteria

Deterministic compilation verified across 500 repeated compiles of the same intent (byte- identical output, P1); conflict-detection coverage ≥ 95% on a 50-case adversarial ACL-overlap corpus (fixtures/intent/); rollback correctness: 100 injected partial-deployment failures all resolve to either fully-applied or fully-rolled-back, zero partial states observed.

20.5 Conformance Fixtures

  • fixtures/intent/conflicting-acl.yaml — two ACL intents with overlapping match and contradictory actions; expected: rejected with a structured conflict report naming both intent_ids.
  • fixtures/intent/cyclic-intent.yaml — intent A depends on B depends on A; expected: rejected at admission (dependency_graph.rs), before compilation is attempted.
  • fixtures/intent/invalid-vlan.yaml — VLAN ID outside the 1-4094 valid range; expected: schema validation rejection with the offending field named.

20.6 Pitfalls

  • Intent explosion: manifestation — a single high-level intent compiles into an unexpectedly large number of flow rules; root cause — combinatorial expansion when an ACL intent covers a wide address range crossed with many existing VLAN intents; debugging — compilation trace (compilation_traces in N.2) shows the expansion step; signal — intent_compiled_rule_count for one intent_id far exceeds the historical p99; recovery — compiler-side rule-count budget per intent, rejected with a diagnostic above the budget rather than silently overwhelming the flow table (§4 flow-table capacity).
  • Diff preview drift: manifestation — a dry-run preview doesn't match what actually deploys moments later because topology changed in between; root cause — dry-run reads a topology snapshot that isn't pinned through to the actual deploy; recovery — dry-run and deploy share the same topology generation number (I6), deploy aborts if the generation advanced.

20.7 Performance Concerns

Large-graph recomputation cost when a path intent's candidate route set must be recomputed (shares the ECMP recompute cost model from §17.7); conflict detection is worst-case quadratic in intent count on naive overlap checking — mitigated by indexing intents by match-field ranges rather than pairwise comparison.

20.8 Edge Cases

Overlapping wildcard ACLs where neither fully shadows the other (partial overlap — must be flagged, not silently resolved by priority alone); an intent referencing a switch or VLAN that does not yet exist in the topology (deferred-until-resolved, not immediately rejected, since topology discovery is asynchronous relative to intent submission); intent resubmission with the same intent_id but different spec (must be treated as a new version, not an in-place mutation — P1).

20.9 Failure Analysis

Failure: partial intent deployment — a multi-rule intent batch installs some rules before a mid-batch failure (e.g. a switch disconnects). Detection: the atomic-deployment-group tracker (N.2) observes an incomplete ack set. Recovery: transactional rollback (rollback.rs) reissues delete-flow-mods for the partially-installed subset, restoring pre-intent state, then surfaces the failure to the submitting operator with a retry token.

20.10 Operational Notes

Operators require dry-run previews and impact analysis (which existing flows/intents does a new intent shadow or conflict with) before committing. Metrics: intent_compile_duration_ms, intent_conflict_detected_total, intent_rollback_total. Compatibility: intent schema changes follow northbound API semantic versioning (§25).

21. Phase 9 — Observability and Operational Tooling

21.1 Objectives

Deliver production-grade observability across every subsystem built in Phases 0-8: structured logs, metrics, distributed traces, and operator tooling sufficient to diagnose a live incident without attaching a debugger.

21.2 Detailed Implementation Steps

Wire tracing-runtime::spans (bootstrapped in Phase 0, P4) through every async boundary identified in §3's architecture diagram. Implement Prometheus metric export (ADR-12) for every counter/histogram named across §12-§20's Operational Notes subsections. Implement OpenTelemetry trace export (ADR-11) with correlation IDs threaded from northbound request through southbound flow-mod delivery — one trace per intent-to-dataplane path. Implement cardinality-bounded flow metrics (learn from Cilium's Hubble approach, §5) to avoid the per-flow-label explosion in the pitfall below. Implement the debug CLI (cli-tooling::flow_dump) and failure-capture bundles (automatic evidence collection — recent journal segment, metric snapshot, active spans — on invariant-violation panics). Implement local ring-buffer log/metric buffering so observability degrades gracefully rather than disappearing during a control-plane outage (P4 applied to itself).

21.3 Deliverable

An operator can trace a single intent submission end-to-end through compilation, reconciliation, and southbound delivery using one correlation ID, and can pull a failure-capture bundle for any invariant violation without SSH access to the affected node.

21.4 Acceptance Criteria

100% of the counters/histograms named in §12-§20's N.10 subsections are exported and scraped successfully in a 24-hour soak test; trace completeness ≥ 99% for intent-to-flow-mod paths under nominal load; alert-rule coverage validated against all 12 §7 invariants and all 11 §23 failure classes; dashboard completeness verified against the metric list above (zero orphan panels, zero un-dashboarded critical metrics).

21.5 Conformance Fixtures

  • fixtures/observability/missing-trace-id.trace — a southbound message arrives without a propagated correlation ID (legacy-path simulation); expected: a new root span is created and flagged as orphaned, not silently dropped.
  • fixtures/observability/malformed-metrics.prom — a metrics endpoint emits an invalid Prometheus exposition line; expected: scrape parser reports the line and continues, doesn't abort the whole scrape.

21.6 Pitfalls

  • Cardinality explosion: manifestation — Prometheus memory usage grows unbounded; root cause — per-flow labels (e.g. flow_id as a label value) on a high-churn counter; debugging — top-N label-cardinality report from the metrics registry; signal — metrics_runtime_series_count crosses the budgeted ceiling; recovery — remove high-cardinality labels, use exemplars/traces for per-flow detail instead of per-flow metric series (this is exactly the tradeoff Cilium's Hubble makes, §5).
  • Trace sampling skew: manifestation — rare, important error traces are sampled away at the same rate as routine traces; root cause — uniform sampling without error-biasing; recovery — always sample traces that terminate in an error or invariant violation, regardless of the base rate.

21.7 Performance Concerns

Telemetry overhead is budgeted, not free (P4's tradeoff clause) — span creation and metric increment cost is counted against the §4 CPU budget on the hot packet/flow-mod path; batch metric export rather than per-event push to bound syscall overhead.

21.8 Edge Cases

Trace context propagation across a southbound session that predates the correlation-ID feature (legacy fixture above); metric registry restart mid-scrape (must not double-count on restart); log-field cardinality drift when a new field is added without a cardinality review.

21.9 Failure Analysis

Failure: observability outage masks a concurrent control-plane incident. Detection: a heartbeat/self-check metric for the observability pipeline itself (metrics about metrics). Mitigation: local ring buffers (N.2) mean the node keeps functioning and keeps local evidence even if the remote metrics/trace backend is unreachable — the failure-capture bundle is assembled locally, not fetched from a possibly-down aggregator.

21.10 Operational Notes

This phase's own metrics: obs_export_failures_total, obs_ring_buffer_dropped_total, obs_trace_sample_rate. Observability must remain locally operational during degraded cluster conditions (DEGRADED/RECOVERING states, §8) — this is the one subsystem that must never itself be gated behind cluster health.

24. Operational Readiness

Metrics strategy. Mandatory metrics span every phase's N.10 (§12-§21): flow-install latency, reconciliation lag, queue depth, WAL fsync latency, topology convergence, election duration, lease epoch, replication lag, cardinality-bounded flow counters. Every metric name used in a phase Operational Notes section is exported (verified in §21 acceptance criteria).

Alerting philosophy. Alert on sustained degradation (not single-sample blips), quorum instability (any DEGRADED/RECOVERING transition lasting > 30s), replay divergence (I7, always page — this is a correctness bug, not a capacity issue), and reconciliation backlog exceeding the §4 throughput budget for > 2 consecutive intervals. Do not alert on transient southbound packet loss (§4 tolerates 5%) or short-lived retries within the bounded-retry window (§16.9).

Backup strategy. Periodic snapshots (interval tuned to the RPO=1s WAL-fsync ceiling plus a snapshot cadence bounding recovery time, §4) archived off-node; WAL segment archival for point-in-time replay beyond the latest snapshot; integrity verification (checksum scan) runs on every archived segment on a schedule, not only at recovery time.

On-call runbooks. docs/runbooks/controller-failover.md for FM-1/FM-7; docs/runbooks/ wal-corruption.md for FM-2/FM-3. Both runbooks reference the invariant ID (I-prefixed) or failure class (FM-prefixed) they respond to, so the on-call engineer starts from the same vocabulary as this blueprint, not an ad hoc description.

Capacity planning. §32's back-of-envelope model is the input to per-deployment capacity planning; operators re-derive C1-C8 with their own switch count and flow-churn rate rather than reusing this blueprint's example numbers verbatim.

25. Compatibility & Versioning

Wire compatibility. Southbound protocol changes are version-gated at the Hello handshake (P6, ADR-06); a major-version bump may remove message types, a minor-version bump may only add them. Conformance fixtures pin every supported version pair (§13.5).

Storage compatibility. WAL segment and snapshot formats carry explicit version metadata (§18.2); a controller refuses to load a snapshot from a newer major version and requires an explicit, documented migration tool rather than attempting in-place upgrade.

API stability. Northbound REST/gRPC APIs follow semantic versioning; a breaking change to an intent schema field (§11 Intent) requires a new API version path, old versions remain served for a documented deprecation window.

Migration policy. Any format version bump ships with: a migration tool, a rollback procedure, and a conformance fixture exercising the old-to-new transition (fixtures/persistence/ gains a version-mismatch case per bump, extending §18.5).

26. Testing & Verification Strategy

Unit testing. Mandatory for parsers (§14), match/action logic (§15), graph algorithms (§17), and the diff engine (§16) — each crate's tests/ directory (§10) holds these.

Integration testing. Required for controller/switch interoperability (southbound session lifecycle end-to-end, §13) and replay consistency (I7, exercised by replay-framework).

Property-based testing. proptest (ADR-13) generates the malformed/edge-case input space for the packet parser and the intent compiler's conflict detector — chosen because both have input spaces too large to enumerate by hand.

Fuzzing. cargo-fuzz (ADR-14) targets: packet-parser (§14), the southbound frame decoder (§13), and the WAL segment parser (§18) — the three components that parse untrusted or potentially-corrupted bytes.

Chaos testing. conformance-harness injects network partitions, packet loss, and WAL corruption against the full stack, not individual crates — this is where I3/I7/I12 get exercised under adversarial scheduling, not just unit-level assertion.

Conformance testing. Every phase's N.5 fixtures are collected under conformance/fixtures/ (indexed by manifest.json) and run on every PR via conformance-harness::runner.

27. Build & Release Engineering

Reproducible builds. Pinned toolchain (rust-toolchain.toml) and deterministic container layers (pinned base image digests, ADR-20) ensure a given commit produces a byte-identical image across CI runs (§12.4's acceptance criterion).

Release channels. nightly (every merge to main), rc (release-candidate, conformance suite must be 100% green), stable (tagged, signed) — per ADR-22's SemVer rationale.

Artifact signing. All release binaries and container images are signed; signature verification is a documented step in every deployment runbook, not an optional extra.

SBOM. Every release generates a CycloneDX SBOM (legal/NOTICE plus generated artifact); operators verify the SBOM before promoting a build past rc.

29. Scalability Analysis

Bottlenecks. Reconciliation fanout when one topology event triggers recompute across many switches (§16.7, §17.7); graph recomputation cost scaling with topology size (mitigated by incremental ECMP update, §17.7); WAL fsync latency under sustained flow-mod throughput (§18.7, bounded by the RPO=1s batching window).

Horizontal scaling. Controller cluster size is capped at small odd counts (3-5) by Raft's quorum write-amplification tradeoff (ADR-05, §19.7) — this is a deliberate ceiling, not an oversight; scaling beyond one region is PhaseDeferred("§19"). Southbound session capacity scales by adding controller replicas behind session-affinity routing, not by growing a single quorum.

Vertical scaling. Per-node flow-table capacity (250,000 flows, §4) is bounded by the FlowDescriptor memory budget (§11) and switch-runtime RSS ceiling (§32 C2); increasing it requires either a smaller per-flow metadata footprint or a higher RSS ceiling, both explicit tradeoffs against §4, not free.

Sharding. Switch capability/metadata caches are sharded by datapath_id (ADR-17's columnar index) to bound per-shard lock contention (§15.7) as switch count grows toward the 500-switch deployment target (§1).

30. Mental Models & First Principles

  • MM1 — Desired vs. Observed Are Two Independent Clocks. Compressed insight: version desired state and observed state independently, never collapse them into one mutable value · predicts: without this split, a retry and a stale observation become indistinguishable · bug class: reconciliation oscillation (FM-9) · applies in §16.
  • MM2 — RCU Read Paths Never Block. Insight: readers hold an immutable generation while writers publish new ones, so reads and writes never contend · predicts exactly where lock contention would appear in a naive mutable-graph design · bug class: torn reads under concurrent mutation · applies in §17.
  • MM3 — Fencing Tokens Beat Trust. Insight: a monotonically increasing epoch, checked at every write, replaces "trust the current leader" with "verify the epoch" · predicts why heartbeat-based leader trust alone is insufficient during a partition · bug class: split-brain flow-mod issuance (FM-7) · applies in §19.
  • MM4 — Durability Is a Program Order, Not a Timer. Insight: fsync-before-ack is a causal ordering constraint, not a periodic housekeeping task · predicts what breaks if ack races fsync (acknowledged-then-lost intent) · bug class: durability violation (I4/I11) · applies in §18.
  • MM5 — Replay Is a Test, Not a Feature. Insight: if a system can't replay its own history, it can only assert determinism, never prove it · predicts silent non-determinism that "usually works" until it doesn't · bug class: replay divergence (FM-3) · applies in §26.
  • MM6 — Backpressure Is a Contract, Not a Buffer Size. Insight: every queue needs a documented shed policy, not merely a capacity number · predicts cascading OOM under any sustained producer/consumer imbalance · bug class: queue saturation (FM-5) · applies in §16.
  • MM7 — Compile-Time Conflict Detection Beats Runtime Shadowing. Insight: catching rule overlap at intent-compile time is strictly cheaper than debugging a silently-shadowed rule already in production · predicts where a "why doesn't my rule fire" incident originates · bug class: rule shadowing (FM-8) · applies in §20.
  • MM8 — Observability Must Outlive What It Observes. Insight: the telemetry pipeline needs its own degraded-mode path or it vanishes exactly when it is needed most · predicts masked incidents during cluster-health outages · bug class: masked concurrent incident (§21.9) · applies in §21.

32. Back-of-Envelope Capacity Model

  • C1 — Controller RSS Budget. 500 switches × 4 MB metadata = 2,000 MB + 250,000 flows × 512 B = 128 MB + ~500 MB baseline runtime = 2.63 GB, inside the 8 GB soft ceiling (§4) with 3× margin.
  • C2 — Flow-Table Capacity Ceiling. 2 GB switch-runtime hard ceiling (§4) minus 500 MB packet-buffer/parser-scratch reservation = 1.5 GB ÷ 512 B/flow = 2,929,687 theoretical max; the 250,000-flow target (§4) leaves headroom for group-table and index overhead.
  • C3 — Southbound FD Budget. 10,000 sessions × 2 FDs (socket + WAL handle) = 20,000 + ~1,000 northbound listener FDs = 21,000, inside the 65,536 FD budget (§4) with 3× headroom.
  • C4 — WAL Write Rate. 1 KB logical payload/event × 1.3× checksum/framing overhead (§4) = 1.3 KB on-disk/event; at 50,000 flow-mods/sec (§4) sustained = 65 MB/sec raw WAL write rate.
  • C5 — Snapshot Recovery Time. 250,000 flows × 512 B = 128 MB + 500 switches × 4 MB = 2,000 MB (dominant term) = ~2.13 GB total ÷ 500 MB/s disk read = 4.3 s decode, inside the 60 s target (§4) with >10× margin for validation/index-rebuild overhead.
  • C6 — Reconciliation Concurrency. 250,000 ops/minute (§4) ÷ 60 = 4,167 ops/sec sustained; at a 200 ms p95 diff-cycle (§4), naive per-flow single-threaded diffing would need 4,167 × 0.2 s = 833 concurrent in-flight diffs, met via batched dirty-set diffing (§16.7) rather than per-flow loops.
  • C7 — Cluster Replication Bandwidth. 3-node quorum, 50,000 flow-mods/sec × ~200 B compact log entry = 10 MB/sec leader-to-follower stream × 2 followers = 20 MB/sec aggregate, negligible against a typical intra-DC 10+ Gbps link (§4's 0.5-5 ms RTT assumption confirms same-DC placement).
  • C8 — Metrics Cardinality Ceiling. 200,000 active series/node (Prometheus-recommended ceiling) ÷ ~20 label combinations/family = 10,000 metric-family budget, which is why per-flow_id labels (FM-10) are rejected outright rather than budgeted against.

34. Alternative Architectures (Roads Not Taken)

Alt A — Fully Distributed, No Central Controller

 [Node A]agent<--policy sync-->[Node B]agent<--policy sync-->[Node C]agent
    |  local eBPF/iptables            |                          |
    v  enforcement only               v                          v
 dataplane                       dataplane                  dataplane
   (no logically-centralized state; each node computes its own
    forwarding/policy decisions from locally-synced state)

Regime where it wins: single-cluster Kubernetes networking where per-node in-kernel enforcement latency matters more than centralized policy visibility, and where node-to-node policy sync can tolerate eventual consistency. Real system: Cilium (eBPF-based node agents, no SDN controller). Rejected here because: this project's explicit goal (§1, §2) is to build and understand the centralized-control-plane mechanisms (reconciliation, consensus, lease fencing) that Cilium's architecture deliberately avoids needing — building Alt A would teach a different, also valuable, but disjoint skill set from the one this blueprint targets.

Alt B — Hardware-Offloaded P4 Dataplane

 Controller Cluster (unchanged: §12-§21 control plane)
        |  P4Runtime (instead of southbound-protocol/openflow_like.proto)
        v
 P4-programmed ASIC/SmartNIC pipeline
   (parser + match/action tables compiled from a P4 program,
    executed at hardware line rate, not by dataplane-runtime)

Regime where it wins: production networks needing line-rate (100+ Gbps) forwarding where software Mpps ceilings (§4, 1-10 Mpps) are structurally insufficient. Real system: P4-programmable switches using P4Runtime as a southbound protocol (the model ONOS's P4Runtime provider supports). Rejected here because: this is an explicit Non-Goal (§1) — a P4 compiler backend is PhaseDeferred("§20") — the engineering value of this blueprint is in the software control/data plane mechanisms, and adding a hardware target would substitute vendor SDK integration work for the systems-engineering this project teaches.

Alt C — Eventually-Consistent Multi-Master Control

 [Ctrl A]<--gossip/CRDT merge-->[Ctrl B]<--gossip/CRDT merge-->[Ctrl C]
    |  all three accept writes concurrently, conflicts merged   |
    v  via last-writer-wins or CRDT semantics, not a single      v

Regime where it wins: deployments prioritizing write availability during partitions over strict consistency, where conflicting flow-mods can be tolerated or merged (e.g. additive-only ACL policy where conflicts degrade gracefully rather than corrupt state). Real system: ONOS's distributed core, which accepts intents on any node and reconciles eventually across the cluster rather than routing all writes through one Raft leader. Rejected here because: P11 (single-writer) and I3 (single authoritative leader) are load-bearing invariants for this blueprint's flow-mod correctness guarantees (§7) — multi-master flow-mod issuance reopens exactly the split-brain failure mode (FM-7) this design spends its clustering phase (§19) closing.

36. Glossary

  • Action list — ordered set of dataplane operations (output/drop/set-field/push-vlan/ pop-vlan/goto-table/group) attached to a flow rule.
  • Actor (concurrency model) — one supervised async task per session/worker, isolating failure per ADR-09/P10.
  • Cardinality — number of distinct label-value combinations for a metric; unbounded cardinality is FM-10.
  • Capability bitmap — negotiated set of features a switch supports, cached and quarantined under I9.
  • Chaos testing — fault injection (partition, packet loss, corruption) against the full running stack, not a single crate.
  • Conformance fixture — a named input/expected-output pair under conformance/fixtures/ exercised by every phase's N.5.
  • Correlation ID — trace/log identifier threaded across an async boundary so one operation is traceable end to end (P4).
  • Diff engine — computes desired-vs-observed deltas per flow, the core of the reconciler (§16).
  • Dirty set — the incrementally-tracked set of flows needing reconciliation, avoiding full rescans (§16.7).
  • Drift — divergence between desired and observed state, detected by drift_detector.rs.
  • ECMP — equal-cost multipath routing; multiple paths of equal cost load-balanced across.
  • Event journal — append-only, replayable log of control-plane decisions (§11 EventRecord).
  • Fail closed — a security-relevant failure rejects the operation rather than degrading permissively (P9).
  • Fencing — epoch-based mechanism preventing a stale leader/writer from taking effect (I12).
  • FlowMod — the flow-programming operation (install/modify/delete) sent to a switch.
  • Flow rule — a match/action forwarding entry scoped to a table and priority (§8, §11).
  • Generation — a monotonically increasing version number on a snapshot or switch registration (I5, I6).
  • Goto-table — an instruction chaining evaluation from one flow table to another.
  • Group table — a table of shared action groups referenced by flow rules (I10).
  • Hard timeout — a fixed expiry independent of traffic activity, as opposed to idle timeout.
  • Idle timeout — expiry triggered by an absence of matching traffic for a duration.
  • Intent — a declarative network policy (ACL/VLAN/path) submitted via the northbound API (§11).
  • Lease epoch — the monotonically increasing fencing token identifying the current authoritative leader (§11 LeaseGrant, I12).
  • LLDP — Link Layer Discovery Protocol; the model for this project's topology-discovery probes.
  • Match field — one matchable packet attribute (ingress port, Ethernet/IP/TCP/UDP fields, metadata register).
  • mTLS — mutually authenticated TLS, used for southbound and cluster-replication channels.
  • Northbound — the operator/client-facing interface (REST/gRPC) into the controller.
  • Packet-in — an event sent from switch to controller when no installed rule matches a packet.
  • Quorum — the majority set of cluster nodes required to commit a Raft write.
  • RCU — read-copy-update; a concurrency pattern where readers hold immutable snapshots while writers publish new generations without locking readers out.
  • Reconciliation — the continuous desired-vs-observed convergence loop (§16).
  • Replay cursor — the durable bookmark tracking replay progress through the event journal.
  • RPO — Recovery Point Objective; maximum acceptable data loss window (§4: ≤ 1 second).
  • RTO — Recovery Time Objective; maximum acceptable time to restore service (§4: ≤ 5 minutes).
  • SBOM — Software Bill of Materials; generated per release for supply-chain verification.
  • Shed policy — the documented behavior a bounded queue follows once full (reject, drop-oldest, etc.) — required by P2.
  • Single-writer invariant — only the current leader may mutate desired state (P11, I3).
  • Snapshot — a compacted, versioned point-in-time copy of persistent state.
  • Southbound — the controller-to-switch protocol interface.
  • Span — a single traced unit of work within a distributed trace (OpenTelemetry, §21).
  • Split-brain — a state where more than one node believes it holds sole write authority.
  • Tail latency — high-percentile (p95/p99) latency, the metric class most §4 targets are expressed in.
  • Topology graph — the canonical, RCU-snapshotted network representation (§11 TopologyGraph).
  • TxnId — a per-switch monotonically increasing transaction identifier enforcing I1 ordering.
  • WAL — Write-Ahead Log; the durability primitive underlying I4/I11.
