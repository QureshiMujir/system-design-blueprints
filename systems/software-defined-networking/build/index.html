⬜ Phase 0 — Repository Bootstrap & Correctness Kernel §12

Objectives

Stand up a reproducible Rust workspace and the correctness primitives every later phase depends on: the error taxonomy, the ControllerContext/EventRecord skeleton types (§11), and a CI gate that makes non-determinism (P1) visible before it ships. No networking, no dataplane yet — this phase's scope is the build system and the type/observability skeleton only.

Deliverable

A workspace that compiles, lints clean, and produces a hash-identical container image across two consecutive CI runs on the same commit; cargo test --workspace passes with zero tests failing (zero tests exist yet — this asserts the harness itself runs).

Acceptance

CI green on Linux x86_64 and ARM64 (§4 NUMA/CPU assumption); container image digest identical across 2 consecutive builds of the same commit; zero unsafe blocks outside packet-parser (reserved for Phase 2); cargo deny check zero advisories; workspace builds in < 4 minutes cold.

Fixtures
  • fixtures/build/reproducible-build.txt — expected digest manifest for the deterministic image.
  • fixtures/ci/workspace-lint.json — golden clippy/rustfmt output, zero warnings expected.
  • fixtures/ci/malformed-cargo-toml.txt — a workspace member with a syntax error; expected: CI fails at the manifest-parse step, not mid-build.
Pitfalls
  • Dependency drift: a transitive dependency updates between CI runs without a Cargo.lock commit — manifestation: non-deterministic CI failures unrelated to the diff; root cause: lock file not committed or not verified in CI; debugging: cargo lock diff against the previous green commit; signal: cargo audit flags a version the PR didn't touch; recovery: pin via deny.toml and re-vendor.
  • Toolchain skew: contributors on different Rust versions produce different clippy lint sets; root cause: no rust-toolchain.toml enforcement; recovery: rustup show active-toolchain check in CI preflight.

⬜ Phase 1 — Southbound Protocol Foundation §13

Objectives

Implement the authenticated, versioned wire transport between controller and switch: session negotiation, heartbeats, and message framing, per the OpenFlow Switch Specification 1.3.5 subset (§8) and RFC 8446 (TLS 1.3). No flow-table logic yet — sessions only.

Deliverable

Controller and a simulated switch (test harness, not real hardware) complete a TLS handshake, negotiate protocol version and capabilities, and sustain heartbeats without operator intervention.

Acceptance

10,000 concurrent sessions stable for 10 minutes (§4 concurrency budget); heartbeat RTT p95 < 500 ms under nominal load; fuzz corpus of 50,000 executions with zero panics/OOB; malformed frame rejection verified against all fixtures below.

Fixtures
  • fixtures/southbound/malformed-frame.bin — truncated length prefix; expected: ErrorReply with BAD_FRAME, session not torn down.
  • fixtures/southbound/invalid-version.bin — unsupported protocol version in Hello; expected: session rejected before FeaturesRequest.
  • fixtures/southbound/duplicate-transaction.bin — replayed FlowMod TxnId; expected: second delivery is a no-op ack (P12 idempotence), not a double-apply.
Pitfalls
  • Heartbeat storms: manifestation — CPU spike every N seconds across all sessions; root cause — unjittered fixed-interval timers synchronized at session-start; debugging — histogram of heartbeat send timestamps shows clustering; signal — sb_heartbeat_batch_size metric spikes; recovery — jittered scheduling (±20% of interval) per session.
  • TLS handshake amplification under connection-storm reconnect: manifestation — CPU-bound handshake queue backs up after a controller restart when all switches reconnect at once; root cause — no reconnect jitter on the switch-agent side; recovery — exponential backoff + jitter on reconnect.

⬜ Phase 2 — Packet Parser and Match Engine §14

Objectives

Implement deterministic, zero-copy, bounds-checked parsing for Ethernet/VLAN/IPv4/TCP/UDP/ICMP (RFC 791, RFC 793, Stevens ch. 3-9) and the match-field extraction the flow-table engine (Phase 3) will consume. This is the only crate permitted unsafe (ADR-18), and only inside bounds-checked accessor functions.

Deliverable

A library that takes a raw Ethernet frame and returns either a fully-decoded MatchFields (§8) or a typed parse error — no panics, no OOB reads, for any byte sequence of any length.

Acceptance

100% pass on a 200-case parser conformance corpus (fixtures/parser/corpus/); zero cargo-fuzz-discovered OOB/panic after a 24-hour fuzz run; deterministic parser replay: same input bytes produce a byte-identical MatchFields across 1,000 repeated parses (I7-style check scoped to this crate).

Fixtures
  • fixtures/parser/malformed-ipv4.bin — header length field exceeds buffer; expected: ParseError::Truncated, no panic.
  • fixtures/parser/truncated-vlan.bin — VLAN tag present but EtherType field missing; expected: ParseError::Truncated at the correct offset.
  • fixtures/parser/oversized-header.bin — IHL claims 60-byte IPv4 header on a 40-byte buffer; expected: rejected before any field read.
Pitfalls
  • Unaligned memory access: manifestation — SIGBUS on ARM64 for a naive *const u32 cast over an odd-offset field; root cause — VLAN tag insertion shifts subsequent header alignment; debugging — reproduce under qemu-user ARM64; signal — crash only on ARM64 CI runner, never x86_64; recovery — use u32::from_be_bytes on a copied 4-byte slice, never a pointer cast (also closes the ADR-18 "control over ownership" gap).
  • Off-by-one in wildcard mask application: manifestation — a /31 vs /32 match silently matches one extra host; root cause — mask arithmetic using << without clamping at bit-width; signal — differential test against the naive reference parser disagrees on exactly boundary addresses.

⬜ Phase 3 — Flow Table Runtime §15

Objectives

Implement the multi-table match/action pipeline (§8) with priority ordering, timeouts, group tables, and RCU-snapshot reads, consuming Phase 2's MatchFields and enforcing I1 (ordering) and I10 (no orphan group refs). Hardware TCAM offload and eBPF-accelerated execution stay software- only for now — both are PhaseDeferred("§15"), un-deferred only if the software Mpps ceiling (§4) proves insufficient for a target deployment.

Deliverable

A switch runtime that installs, matches, executes, ages out, and garbage-collects flow rules across multiple tables with goto-table chaining, observable via a flow-dump CLI command.

Acceptance

Sustains 250,000 installed flows (§4 flow-table capacity target) with p99 lookup latency < 50 microseconds; zero leaked rules 60 seconds after hard-timeout expiry in a 10,000-flow churn test; deterministic replay equivalence: replaying the same install/expire sequence twice yields an identical table snapshot hash (I7).

Fixtures
  • fixtures/flow-table/overlapping-rules.json — two rules, same table, overlapping wildcard match, different priority; expected: higher priority wins deterministically.
  • fixtures/flow-table/timeout-expiry.json — rule with 1s idle timeout, no traffic; expected: expired and GC'd within one sweep interval.
  • fixtures/flow-table/invalid-goto-table.json — goto-table instruction not terminal in its list; expected: rejected at install, ErrorReply(BAD_INSTRUCTION).
Pitfalls
  • Rule shadowing: manifestation — a broad low-priority rule never fires because a wildcard higher-priority rule shadows it entirely; root cause — compiler (Phase 8) didn't detect the shadow before install; debugging — flow_dump overlap-report tool; signal — flow-hit counter stuck at zero for a rule expected to match traffic; recovery — none at runtime (this is a compile-time defect, surfaced back to flow-compiler's conflict_detector, §20).
  • Timeout-scheduler starvation under table-shard imbalance: manifestation — one shard's sweep task falls behind under skewed flow distribution; root cause — sharding key doesn't account for hot switches; recovery — per-shard sweep-lag metric triggers rebalance.

⬜ Phase 4 — Controller Core and Reconciliation §16

Objectives

Build the authoritative reconciliation loop: desired-state registry, observed-state collector, diff engine, and transaction scheduler that together keep dataplane state converged with controller intent under P1 (determinism) and P11 (single-writer).

Deliverable

A controller that, given a desired-state set and a live switch session, converges dataplane flow-table contents to match — and reconverges automatically after a switch restart or observed mismatch, without operator intervention.

Acceptance

Eventual convergence within 200 ms p95 (§4 reconciliation p95) after a simulated switch restart in a 10,000-flow test topology; zero duplicate rule installs across 100 injected reconnect events; deterministic replay output — two reconciliation runs over the same event-journal segment produce identical install/delete sequences (I7).

Fixtures
  • fixtures/reconciliation/switch-restart.trace — switch drops and reconnects mid-flow-churn; expected: full flow-table re-sync within the p95 target, no duplicate installs.
  • fixtures/reconciliation/duplicate-flow.trace — two overlapping FlowMod requests for the same desired rule; expected: single install, second is a no-op (P12).
  • fixtures/reconciliation/stale-observed-state.trace — stats collector reports a rule installed 1 minute after it was superseded; expected: stale-observation detector discards it.
Pitfalls
  • Reconciliation oscillation: manifestation — the same rule is repeatedly reinstalled every diff cycle; root cause — observed-state timestamps aren't monotonic relative to desired-state versions, so the diff engine can't tell "already applied" from "needs reapply"; debugging — compare FlowDescriptor.version sequences across cycles; signal — recon_reinstall_total for a single flow_id climbing without bound; recovery — version-gate the diff (only reinstall if observed.version < desired.version).
  • Diff-engine cost blowup on large topologies: manifestation — reconciliation p95 exceeds budget under 200k+ tracked flows; root cause — full-scan diff instead of incremental dirty-set tracking; recovery — dirty-flow queue fed by drift_detector instead of full rescans.

⬜ Phase 5 — Topology Discovery and Graph Engine §17

Objectives

Build the authoritative topology model: LLDP-like discovery, an RCU-snapshot graph (§11 TopologyGraph), ECMP path generation, and failure-driven recomputation, enforcing I2 (no orphan links) and I6 (snapshot generation monotonicity). BGP-LS ingestion and EVPN control-plane interoperability are PhaseDeferred("§17") — this phase's graph is discovery-only, not a BGP speaker.

Deliverable

A controller that discovers a live network graph from switch LLDP-like exchanges, recomputes ECMP paths on link failure, and publishes an immutable, versioned snapshot readers can consume without blocking the discovery writer.

Acceptance

Link-failure-to-recomputed-path convergence < 2 seconds p99 (§4 topology convergence target) in a 32-switch leaf-spine test topology (examples/topologies/leaf-spine.yaml); zero orphan links after 1,000 injected flap events; topology snapshot hash reproducible across two replays of the same discovery event sequence (I7).

Fixtures
  • fixtures/topology/topology-flap.trace — a link toggles up/down 50 times in 10 seconds; expected: converges to correct final state, no orphan links, bounded recompute count (not one recompute per flap — debounced).
  • fixtures/topology/asymmetric-link.trace — LLDP seen in one direction only; expected: link not admitted until bidirectional confirmation.
  • fixtures/topology/stale-lldp.trace — probe replay from a previous session generation; expected: rejected via generation fencing (I6).
Pitfalls
  • Discovery storms: manifestation — CPU/bandwidth spike as all switches probe simultaneously after a controller restart; root cause — unjittered fixed-interval LLDP emission, same class of bug as §13.6's heartbeat storm; recovery — jittered emission per switch.
  • Graph recompute explosion: manifestation — a single link flap triggers a full graph-wide ECMP recompute repeatedly; root cause — no debounce window between topology-change events; signal — topo_recompute_total far exceeds topo_link_change_total; recovery — coalesce changes within a short debounce window before triggering recompute.

⬜ Phase 6 — Persistence and Replay Infrastructure §18

Objectives

Implement the WAL and snapshot subsystem backing I4 (durability) and I11 (fsync-before-ack), and the replay cursor mechanics that make P1/P8 (determinism, replayability) enforceable rather than aspirational.

Deliverable

A controller that survives kill -9 at any point and recovers to a consistent state — verified by replaying its own WAL — within the RTO/RPO budget (§4).

Acceptance

Replay reproduces identical state across 3 repeated recovery runs from the same WAL (I7); WAL corruption detection verified against 20 injected single-byte-flip fixtures with zero false negatives; snapshot restore completes in < 60 seconds for a 250,000-flow snapshot (§4 snapshot recovery target).

Fixtures
  • fixtures/persistence/corrupted-wal.bin — single-byte checksum mismatch mid-segment; expected: quarantine from that record forward, recovery proceeds from the last valid record.
  • fixtures/persistence/partial-snapshot.bin — snapshot file truncated mid-write (simulated crash during snapshot); expected: rejected at load, fall back to the prior snapshot + full WAL replay.
  • fixtures/persistence/replay-divergence.trace — two replays of the same segment intentionally fed a non-deterministic hook (test-only); expected: divergence detector (I7) fires.
Pitfalls
  • Torn writes: manifestation — a segment record is partially written when the process is killed mid-fsync; root cause — write() without an atomic record boundary; debugging — checksum covers the full record including length prefix, so a torn write always fails checksum, never silently parses as a different valid record; recovery — fsync at record boundaries only (ADR-16), never mid-record.
  • Compaction stalls: manifestation — snapshot write blocks the WAL append path; root cause — snapshot taken synchronously on the hot path instead of on a background task with its own memory budget; recovery — background compaction task, WAL continues appending concurrently.

⬜ Phase 7 — Controller Clustering and Consensus §19

Objectives

Implement the highly-available clustered controller: Raft-based leader election, log replication, and lease fencing (I3, I12), following Ongaro & Ousterhout 2014 and Burrows 2006 (§5).

Deliverable

A 3-node controller quorum that survives a leader crash with automatic failover, rejects split-brain writes under network partition, and replicates the WAL tail to followers with bounded lag.

Acceptance

Automatic failover completes within 5 seconds of leader crash detection (bounds into the RTO budget, §4); zero acknowledged-state loss across 50 injected leader-crash trials; stable quorum maintained under 20% random message loss for 10 minutes; replication lag p95 < 100 ms under nominal load.

Fixtures
  • fixtures/cluster/partition-majority.trace — the leader's partition retains quorum; expected: continues serving writes, minority partition steps down to FOLLOWER.
  • fixtures/cluster/partition-minority.trace — the leader's partition loses quorum; expected: leader steps down to DEGRADED (§8 state machine), rejects writes until quorum restored.
  • fixtures/cluster/rapid-election.trace — 10 consecutive elections within 30 seconds (adversarial timer injection); expected: eventual stable leader, no epoch reuse (I12).
Pitfalls
  • Election thrashing: manifestation — repeated elections with no stable leader; root cause — election timeouts synchronized across nodes (all nodes time out simultaneously and split the vote); debugging — plot election-start timestamps per node; signal — cluster_election_total climbing without a corresponding stable-leader period; recovery — randomized timeout jitter per the Raft paper's exact prescription (§5).
  • Quorum write amplification: manifestation — write latency degrades disproportionately as cluster size grows past 3-5 nodes; root cause — synchronous replication to every follower before ack; recovery — this system caps cluster size at odd counts ≤5 by design; larger clusters are PhaseDeferred("§19") (multi-region federation, deferred).

⬜ Phase 8 — Intent Engine and Policy Compilation §20

Objectives

Build the declarative policy layer: ACL/VLAN/path intents (§11 Intent), conflict detection, and deterministic compilation into FlowRule sets, with atomic all-or-nothing deployment. A P4-target compiler backend and SAT-solver-based conflict detection are both PhaseDeferred("§20") — this phase ships a heuristic conflict detector and a single software-pipeline compiler target only.

Deliverable

Operators submit declarative ACL/VLAN/path intents via the northbound API and receive either a compiled, deployed flow-rule set or a structured conflict report — never a partial, silent deployment.

Acceptance

Deterministic compilation verified across 500 repeated compiles of the same intent (byte- identical output, P1); conflict-detection coverage ≥ 95% on a 50-case adversarial ACL-overlap corpus (fixtures/intent/); rollback correctness: 100 injected partial-deployment failures all resolve to either fully-applied or fully-rolled-back, zero partial states observed.

Fixtures
  • fixtures/intent/conflicting-acl.yaml — two ACL intents with overlapping match and contradictory actions; expected: rejected with a structured conflict report naming both intent_ids.
  • fixtures/intent/cyclic-intent.yaml — intent A depends on B depends on A; expected: rejected at admission (dependency_graph.rs), before compilation is attempted.
  • fixtures/intent/invalid-vlan.yaml — VLAN ID outside the 1-4094 valid range; expected: schema validation rejection with the offending field named.
Pitfalls
  • Intent explosion: manifestation — a single high-level intent compiles into an unexpectedly large number of flow rules; root cause — combinatorial expansion when an ACL intent covers a wide address range crossed with many existing VLAN intents; debugging — compilation trace (compilation_traces in N.2) shows the expansion step; signal — intent_compiled_rule_count for one intent_id far exceeds the historical p99; recovery — compiler-side rule-count budget per intent, rejected with a diagnostic above the budget rather than silently overwhelming the flow table (§4 flow-table capacity).
  • Diff preview drift: manifestation — a dry-run preview doesn't match what actually deploys moments later because topology changed in between; root cause — dry-run reads a topology snapshot that isn't pinned through to the actual deploy; recovery — dry-run and deploy share the same topology generation number (I6), deploy aborts if the generation advanced.

⬜ Phase 9 — Observability and Operational Tooling §21

Objectives

Deliver production-grade observability across every subsystem built in Phases 0-8: structured logs, metrics, distributed traces, and operator tooling sufficient to diagnose a live incident without attaching a debugger.

Deliverable

An operator can trace a single intent submission end-to-end through compilation, reconciliation, and southbound delivery using one correlation ID, and can pull a failure-capture bundle for any invariant violation without SSH access to the affected node.

Acceptance

100% of the counters/histograms named in §12-§20's N.10 subsections are exported and scraped successfully in a 24-hour soak test; trace completeness ≥ 99% for intent-to-flow-mod paths under nominal load; alert-rule coverage validated against all 12 §7 invariants and all 11 §23 failure classes; dashboard completeness verified against the metric list above (zero orphan panels, zero un-dashboarded critical metrics).

Fixtures
  • fixtures/observability/missing-trace-id.trace — a southbound message arrives without a propagated correlation ID (legacy-path simulation); expected: a new root span is created and flagged as orphaned, not silently dropped.
  • fixtures/observability/malformed-metrics.prom — a metrics endpoint emits an invalid Prometheus exposition line; expected: scrape parser reports the line and continues, doesn't abort the whole scrape.
Pitfalls
  • Cardinality explosion: manifestation — Prometheus memory usage grows unbounded; root cause — per-flow labels (e.g. flow_id as a label value) on a high-churn counter; debugging — top-N label-cardinality report from the metrics registry; signal — metrics_runtime_series_count crosses the budgeted ceiling; recovery — remove high-cardinality labels, use exemplars/traces for per-flow detail instead of per-flow metric series (this is exactly the tradeoff Cilium's Hubble makes, §5).
  • Trace sampling skew: manifestation — rare, important error traces are sampled away at the same rate as routine traces; root cause — uniform sampling without error-biasing; recovery — always sample traces that terminate in an error or invariant violation, regardless of the base rate.
