Decisions (§9) · 27 ADRs

ADR-01

Implementation language

Chosen

Rust 2021, MSRV 1.78, std-only core

Rejected

C/C++; Go; Python; OCaml

When the rejected choice is right

C wins if integrating with an existing C-based EDA tool chain (e.g. embedding inside Cadence or Synopsys flows where ABI compatibility dominates).

Why: Manual layout + safety over giant StateTable/BDD tables; enums model LTL/CTL AST + automaton states w/ exhaustive match. C/C++ unsafe over untrusted state graphs; Go GC pauses + weak unique-table layout control hurt inner loop; Python 100-1000x too slow for state-space exploration.

ADR-02

Repo structure

Chosen

Cargo workspace, 7 crates mc-types · mc-lang · mc-ltl · mc-explicit · mc-bdd · mc-symbolic · mc-cli

Rejected

Single monolithic crate; one crate per algorithm (>20)

When the rejected choice is right

Monolith wins if the team is one person and compile times are not a bottleneck — fewer pub boundaries to maintain.

Why: Crate = trust/dependency seam: mc-types semantic core depended on by all; mc-bdd substrate isolated for reuse; engines parallel-developable, separately fuzzable. Monolith blocks incremental compile + clean layering.

ADR-03

State representation

Chosen

Bit-packed State { bits: BitVec } + StateEncoder (var→bit-range)

Rejected

Tagged struct of typed fields; Vec<i64> valuation; serialized-string key

When the rejected choice is right

Tagged struct wins when debugging priority exceeds memory — human-readable state dumps without a decoder step.

Why: StateTable is dominant memory cost → bytes/state decides if model fits RAM. Bit-packing: a 32-var model fits in ≤8 bytes vs ~hundreds for a struct.

ADR-04

Visited set

Chosen

Open-addressing StateTable (State→StateId), Robin-Hood / linear probe

Rejected

std::HashSet<State>; HashMap; Bloom filter only; bit-state hashing default

When the rejected choice is right

Bloom/bitstate wins when RAM is the hard constraint and a small false-negative rate is acceptable (SPIN's bitstate mode is exactly this tradeoff).

Why: Need exact membership at maximum density + cache locality on the hot path (one lookup per generated state). Open addressing: no per-entry allocation, 1-2 cache lines/probe.

ADR-05

Explicit search strategy

Chosen

On-the-fly DFS/BFS over next(); states materialized lazily

Rejected

Build full KripkeStructure graph then search

When the rejected choice is right

Full graph wins for explicit CTL labeling (Phase 7), which needs the predecessor relation; and for re-verification without re-exploring (e.g. iterative predicate-abstraction).

Why: On-the-fly never stores the transition graph — only the visited set — so a CEX can be found before the exponential space is built.

ADR-06

Safety CEX search order

Chosen

BFS for check_invariant shortest-path CEX

Rejected

DFS-found (possibly long) CEX

When the rejected choice is right

DFS wins when fast first-hit matters more than trace length — e.g. fuzz oracle looking for any violation quickly.

Why: BFS yields the minimal-length counterexample → shortest debuggable trace. DFS reaches a violating state faster but produces non-minimal traces.

ADR-07

LTL verification approach

Chosen

Automata-theoretic: Buchi(!phi) × system, language emptiness via accepting cycle

Rejected

Direct tableau/local LTL checking; ω-automata other than Büchi

When the rejected choice is right

Local/tableau wins when a formula has a very specific shape (e.g. pure safety) where a bespoke checker avoids building a Buchi automaton at all.

Why: Check !phi: a reachable accepting cycle = lasso CEX to phi. Standard, on-the-fly-friendly (Vardi-Wolper), composes with next() generation.

ADR-08

LTL→Büchi construction

Chosen

Tableau / GPVW (ltl_to_buchi), generalized→degeneralized + state simplification

Rejected

LTL2BA (alternating-automata/VWAA); Safra/determinization; Spot binding

When the rejected choice is right

LTL2BA/VWAA wins when automaton size is the dominant cost and the extra implementation complexity is worth the smaller automata (e.g. large nested-Until specs).

Why: GPVW is the canonical from-scratch on-the-fly tableau — closure/elementary sets map directly to Rust enums; produces a generalized Büchi we degeneralize + simplify.

ADR-09

Emptiness / liveness check

Chosen

nested_dfs accepting-cycle detection

Rejected

Tarjan/Couvreur SCC-based emptiness; one-pass GBA emptiness

When the rejected choice is right

SCC (Tarjan/Couvreur) wins when generalized Buchi acceptance (multiple sets) is needed without degeneralization — Couvreur handles GBA directly without the state blowup of degeneralization.

Why: Nested-DFS is O(states+transitions), 2 extra color bits/state, fully on-the-fly, reconstructs the lasso from the DFS stacks.

ADR-10

CTL verification

Chosen

Both: explicit fixpoint labeling (Phase 7) and symbolic BDD fixpoint (check_ctl, Phase 9)

Rejected

Symbolic-only; explicit-only; CTL*→ automata

When the rejected choice is right

Explicit-only wins when the state space is tiny and BDD infrastructure is not worth building; symbolic-only wins for large structured hardware models (NuSMV use case).

Why: Explicit labeling validates the fixpoint semantics on small Kripke structures (oracle); symbolic scales to 10^20 states. Two engines = differential cross-check.

ADR-11

BDD package

Chosen

From-scratch ROBDD mc-bdd (BddManager: unique table + computed cache)

Rejected

Bind CUDD; bind BuDDy/Sylvan; use a generic decision-diagram crate

When the rejected choice is right

CUDD binding wins in a production EDA context where CUDD's 30-year performance tuning and multi-terminal BDD support are needed and time-to-market dominates pedagogy.

Why: From-scratch is the project's core symbolic deliverable; full control of node layout, hashing, GC, reordering. External C binding = unsafe FFI + opaque inner loop.

ADR-12

BDD edge encoding

Chosen

Complemented edges (BddRef = signed/complemented index)

Rejected

Plain (uncomplemented) edges; dual-rail nodes

When the rejected choice is right

Plain edges win when implementation simplicity is paramount — no complement-normalization invariants to maintain; useful for teaching BDDs without the encoding subtlety.

Why: Complemented edges halve the node table + make not O(1) (flip the sign bit). Canonicity preserved by the regular-then-child rule.

ADR-13

Core BDD operation

Chosen

Single universal ite(f,g,h); and/or/not/exists/restrict derived

Rejected

Per-operator apply family (and/or/xor each bespoke)

When the rejected choice is right

Per-operator apply wins when different operators need different caching strategies (e.g. ZDD union/intersection with different cache keys for sparse sets).

Why: One memoized recursion (ite) + one computed cache covers all binary/ternary ops → less code, one cache to tune. and(a,b)=ite(a,b,0).

ADR-14

BDD variable ordering

Chosen

Static order from StateEncoder interleaving current/next vars + dynamic sifting (Phase 11)

Rejected

Fixed order only; exhaustive optimal ordering; window permutation only

When the rejected choice is right

Fixed order wins when ordering is known to be near-optimal from domain knowledge (e.g. hardware designs where signal groupings are published), avoiding sifting overhead.

Why: Variable order can mean exponential vs polynomial BDD size. Good static interleaving (s,s' bits adjacent) keeps the transition relation small; sifting (Rudell) reorders on a growth trigger.

ADR-15

Transition relation encoding

Chosen

Monolithic BDD TransitionRelation { bdd }, with partitioned conjuncts as PhaseDeferred

Rejected

Always-partitioned (conjunctive) TR; explicit relation only

When the rejected choice is right

Partitioned TR wins for large asynchronous systems (e.g. cache-coherence protocols with many independent modules) where monolithic TR blows up the BDD and early-quantification in a conjunctive schedule is the only way to scale.

Why: Monolithic is simplest correct image/pre_image substrate. Conjunctively-partitioned TR (early quantification) is the known scaling fix for large asynchronous models.

ADR-16

Symbolic fixpoints

Chosen

pre_image-based EX; EG = gfp (p ∧ EX Z); E[pUq] = lfp (q ∨ (p ∧ EX Z))

Rejected

Forward-image-only reachability for all operators

When the rejected choice is right

Forward-only wins for pure safety/reachability checks (no CTL liveness) where image is sufficient and no backward predecessor computation is needed.

Why: Backward pre_image directly realizes CTL existential operators as set fixpoints over BDDs (states are sets, never enumerated).

ADR-17

BMC backend

Chosen

Delegate unrolling CNF to the project-277 SAT engine (bmc() → CNF → SAT core)

Rejected

Embed a CDCL solver in mc-bmc; SMT (#278); BDD-only

When the rejected choice is right

Embedded solver wins when the SAT interface latency (CNF marshaling, FFI) exceeds per-k solve time — e.g. trivial models where k is tiny and FFI overhead dominates.

Why: Project novelty is the model-checking layer, not CDCL — reuse the audited #277 engine.

ADR-18

BMC completeness

Chosen

Bounded CEX up to k; completeness threshold (recurrence diameter) as PhaseDeferred proof

Rejected

Claim soundness for "holds" without a bound

When the rejected choice is right

Full completeness threshold wins when BMC is the primary proof engine — e.g. k-induction for industrial safety properties where the diameter is known to be small.

Why: BMC is a bug-finder: UNSAT up to k only proves phi once k ≥ completeness threshold. Baseline reports "no CEX within k".

ADR-19

State-space reduction (explicit)

Chosen

Partial-order reduction via ample sets + symmetry reduction (Phase 11)

Rejected

No reduction; sleep-sets/stubborn-sets; persistent-sets

When the rejected choice is right

Stubborn sets win when the independence relation is hard to compute statically but action dependency is available at the stub level (common in process-algebra models).

Why: Ample-set POR prunes independent+invisible interleavings while preserving the checked LTL property (Peled). Symmetry collapses interchangeable processes.

ADR-20

Fairness handling

Chosen

Weak/strong fairness folded into the LTL/Büchi pipeline as constraints (Phase 12)

Rejected

Dedicated fair-cycle (Emerson-Lei) engine only; ignore fairness

When the rejected choice is right

Dedicated Emerson-Lei fair-EG wins when fairness is the dominant property class (most specs are CTL-fairness formulas) and the overhead of folding fairness into Buchi degeneralization is measurable.

Why: Express fairness as LTL premises absorbed into Buchi(!phi) → reuses nested-DFS unchanged.

ADR-21

Abstraction

Chosen

Lite predicate-abstraction / CEGAR with spurious-CEX refinement (Phase 12)

Rejected

Full software-CEGAR over real programs; no abstraction

When the rejected choice is right

Full CEGAR wins when the target is a software program (heap-manipulating, infinite-data) rather than a finite-state hardware/protocol model — exactly the SLAM/BLAST use case, which is out of scope here.

Why: Abstraction introduced only in lite form to demo spurious-CEX refinement. Source-code/program CEGAR is an explicit NON-GOAL.

ADR-22

Counterexample format

Chosen

Lasso Trace { prefix, cycle: Option } (cycle ⇒ liveness lasso)

Rejected

Single linear path only; SCC witness; HTML report

When the rejected choice is right

HTML/rich report wins in a user-facing verification IDE where developers need annotated diff views of the CEX against the model source, not raw state sequences.

Why: Liveness CEX is intrinsically a lasso; one Trace type serves safety (cycle=None) + liveness. Validated by replay.

ADR-23

Trace replay/validation

Chosen

mcheck simulate re-executes a Trace against next()/label()

Rejected

Trust the engine's emitted trace; no replay

When the rejected choice is right

Trusting the engine wins if the engine is formally verified (e.g. extracted from a Coq/Isabelle proof), making replay redundant overhead.

Why: Independent replay catches CEX-reconstruction bugs by re-checking each step against the semantic model — a built-in oracle.

ADR-24

Differential oracle

Chosen

Cross-engine agreement (explicit vs symbolic vs BMC) + re-check NuSMV/SPIN example models (Phase 13)

Rejected

Hand-written expected outputs only; single-engine trust

When the rejected choice is right

Single-engine trust wins for a formally-verified implementation where the proof certificate IS the oracle and running three engines is unnecessary redundancy.

Why: Three independent engines on the same TransitionSystem must agree on sat/unsat; canonical NuSMV/SPIN models pin correctness.

ADR-25

Fuzzing

Chosen

cargo-fuzz (libFuzzer) on parse_model + a random model generator feeding all engines

Rejected

Manual test cases only; AFL via FFI

When the rejected choice is right

AFL via FFI wins in an existing C-language project where the team already has AFL infrastructure and switching fuzzers has integration cost.

Why: Untrusted model text is the trust boundary → fuzz the parser for panics/UB; random Module generator stress-tests cross-engine agreement.

ADR-26

Benchmarking

Chosen

criterion + a standard model suite (dining philosophers, Peterson, leader election, NuSMV examples)

Rejected

Ad-hoc Instant timing; no fixed suite

When the rejected choice is right

Ad-hoc timing wins for a prototype where benchmarking infrastructure cost exceeds the value — criterion setup time amortized only over many perf-sensitive iterations.

Why: Track states/sec (explicit), peak StateTable bytes, BDD node count/peak, time-to-CEX vs k across versions; criterion gives statistical regression detection.

ADR-27

CI / dependency / licensing

Chosen

GitHub Actions (build · test · clippy -D warnings · fuzz-smoke · MSRV 1.78); minimal-dependency policy (std + criterion/cargo-fuzz dev-only); MIT OR Apache-2.0

Rejected

Heavy 3rd-party graph/BDD crates; permissive deps in core; single license

When the rejected choice is right

Heavy deps win if this were a production tool (not a learning project) and time-to-feature mattered — CUDD + Spot + an existing SAT library would deliver a working tool in weeks, not months.

Why: Minimal deps keep the inner loop auditable + the from-scratch claim honest. Dual MIT/Apache matches Rust-ecosystem norm.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Monolithic Explicit Checker with Full KripkeStructure

mc-lang → KripkeStructure (states[], trans[], labels[]) → CTL labeler → LTL nested-DFS
           ↑ pre-build full adjacency + label arrays

Regime: small models (≤10^5 states) where the full graph fits comfortably in RAM and fast predecessor lookups justify the upfront cost.

Real system: explicit-state CTL labeling in Clarke-Emerson 1981; NuSMV's explicit-CTL mode; standard textbook presentation (B1 Ch4, B2 Ch6).

Rejection rationale: on-the-fly (ADR-05) avoids materializing the full adjacency list — a CEX can be found before the exponential graph is built, and memory is dominated by the StateTable only. The CTL explicit labeler (Phase 7) does materialize a KripkeStructure as a local oracle for small models only; it is never the primary engine for large ones. Wins for: repeated re-verification of the same model (cached predecessors amortize cost), interactive CTL query evaluation over a fixed state space.

Alt-2 — BDD-Only (Symbolic-Only) without Explicit Engine

mc-lang → TransitionRelation (BDD) → BDD fixpoints for ALL operators (LTL+CTL)
           skip explicit StateTable entirely

Regime: structured hardware-like models (synchronous, regular, wide datapaths) where BDD sizes stay bounded and |states| is too large for explicit enumeration.

Real system: SMV (McMillan 1992), early NuSMV, CUDD-based EDA flows.

Rejection rationale: BDDs can blow up exponentially on asynchronous/irregular models where the variable interaction is dense. The explicit engine handles these cases efficiently (POR + small hash table), while BDDs struggle with the unstructured interleaving. Our three-engine design keeps explicit for irregular protocols and symbolic for structured datapaths. Wins for: verifying synchronous hardware designs with millions of states but highly regular transition structure — exactly NuSMV's original use case.

Alt-3 — Pure SAT / IC3/PDR without BDD or Explicit Engine

mc-lang → CNF encoding (all depths k) → IC3/Property-Directed Reachability
           no StateTable, no BDD unique table

Regime: safety properties (invariants) on large industrial hardware where IC3/PDR outperforms BDD fixpoints and where property-directed over-approximation allows scalable proofs.

Real system: IC3 / PDR (Bradley 2011, Een/Mishchenko/Brayton 2011) as used in ABC, nuXmv, JasperGold.

Rejection rationale: IC3/PDR is a significant algorithmic complexity beyond the scope of this project and requires a mature SAT solver with incremental/assumption mode as a deeply integrated substrate, not just a delegated backend. Our BMC (Phase 10) already uses the project-277 SAT engine for bounded checking; full IC3 is PhaseDeferred. It wins for: industrial safety proofs where the recurrence diameter is unknown and BMC cannot reach it, but the property is an invariant with a small inductive strengthening.
