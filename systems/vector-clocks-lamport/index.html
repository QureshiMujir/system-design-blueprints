In one paragraph

A logical clock is a small value that lets software tell whether one event came before another or the two were unrelated. This design is a Rust library plus a command-line inspector, not a service: no network listener of its own (§1). It exposes six clock families (Lamport, vector, version vector, dotted version vector, hybrid logical, interval tree) behind one CausalClock trait, plus crash-safe storage, a versioned wire format and pruning (§1). It is linked into key-value stores, CRDT engines, tracing collectors and message brokers that need causal ordering as a primitive (§1). The trade it makes: a small fixed cost per operation buys a correct answer to "did A happen before B, or were they concurrent" (§4).

The problem, concretely

A server S holds one key, and two clients A and B both read it, each receiving the same version {S:5} (§8.3 steps 1-2). Each then writes back without knowing about the other's write (§8.3 steps 3-4). If the server tracks versions with a plain version vector, the later write's version silently dominates and overwrites the earlier one, and one client's update is lost (§8.3 step 5, ADR-20). This is the "client-server anomaly", and the blueprint says Riak ran plain vectors in production for two years before fixing it (P1, §15.6).

Timestamps from the wall clock do not rescue this. The blueprint's stated reason for logical clocks is that no system relying on wall-clock time alone can answer the happens-before question under partition, replay and crash, without bounded-error hardware such as TrueTime, which it excludes permanently (§4, §1). Each of eventual consistency, CRDTs, snapshot isolation, tracing and exactly-once delivery turns into races when the clock is wrong (§2). The families are not interchangeable: picking the wrong one "ships a bug class that survives years" of incident reviews (§2, P1). So the design ships all of them and a trait that makes them look alike to callers (P1, P2).

How it works, end to end

One clock value passes through the boxes of §3's diagram:

└───────────────────────────────────────────────────────────────────────────┘
  1. Consumer APIs (CRDT recipes, snapshot isolation, tracing, exactly-once; §21) never touch a concrete clock type. They call the CausalClock trait (tick, merge, partial_cmp) and so do not know whether a vector clock or a DVV is underneath (§3, P2, §11.1). concurrent_with is a derived method of partial_cmp, never written separately (P2, I3).
  2. Clock-type layer: five crates, one shared contract. clocks-core holds ActorId, LamportTs, TotalOrder<A> and the trait; clocks-vector holds VectorClock<A>; clocks-version holds version vectors and DVVs; clocks-hlc holds Hlc; clocks-itc holds the interval tree clock (§10, §11, §1). Each crate implements its own partial_cmp, because the representation of the partial order differs while the contract is the same (§3).
  3. Wire format (clocks-net): once a value leaves process memory it is bytes with a one-byte version prefix. Nothing downstream may assume the in-process shape, and an unknown version is rejected, never guessed (§3, P6, I7, §10).
  4. Persistence (clocks-storage): atomic_write does temp-file write, fsync, rename, then an fsync of the parent directory, with sled as the default backend and RocksDB behind a feature flag (§3, I6, §7, ADR-06, ADR-07).
  5. Pruning (clocks-gc): a cross-cutting box rather than a layer. It is opt-in per deployment because its safety rule needs knowledge of the deployment topology that the library cannot infer (§3, P4, ADR-18, I9).

Retry, transport and conflict-resolution policy belong to the caller (§1, P10, §8.5). The workspace also holds clocks-cli (inspect, prune; T10), clocks-fuzz and a conformance/runner that emits conformance.report.json (§10, §1).

The core ideas

Happens-before and Lamport timestamps (§8.1, §8.2)

The relation "could have influenced" (happens-before, written →) is generated by three things: order within one process, a send before its receive, and chaining of those (§8.1). Two events are concurrent (a ∥ b) when neither precedes the other (§8.1). Every clock here is a finite representation of this relation, and the design space differs only in what each tracks (§8.1).

A Lamport timestamp is one counter per process (§8.2). A local event does ts := ts + 1; a send attaches the current ts; a receive does ts := max(ts, r) + 1, so the result exceeds both the incoming r and the old ts (§8.2). The pitfall list notes that max(ts, r) + 1 and max(ts, r + 1) differ exactly when ts == r, and the wrong form breaks per-actor monotonicity (I1, §13.6).

What it gives and withholds: a total order consistent with →, but it loses concurrency (§8.1). So LamportTs exposes no concurrent_with at all, by design (P11). To get a strict total order, the wrapper TotalOrder<A> breaks ties by (ts, actor); LamportTs itself stays partial-order only so the arbitrary tie-break is visible (P9, I13). A clock value can only answer before, after or concurrent, never "how much later" (MM1).

P11 says comparing raw scalars would give false concurrency answers because "two causally-related events can share a scalar timestamp", while §8.2's receive rule leaves the receiver strictly greater than the sender's value. The blueprint does not reconcile these (P11, §8.2).

Vector clocks: one counter per actor (§8.2, I2, I5)

State is a map from actor to u64, with a missing entry meaning 0 (§8.2, I5). A local event on actor a does V[a] := V[a] + 1. A send attaches the whole map. A receive takes the entry-wise maximum with the incoming map, then bumps the receiver's own entry (§8.2). Comparison is the Fidge-Mattern rule: V_a ≤ V_b entry-wise exactly when a → b, so if neither map dominates the other, the events are concurrent (I2, §2).

The blueprint's smoke trace uses three actors in a relay (§12.5):

  1. A ticks and a snapshot of its clock is kept.
  2. B merges A's clock and ticks.
  3. C merges B's clock and ticks.

The expected result is that A's snapshot compares Some(Less) against C, and is not concurrent with it (§12.5).

Two details matter when implementing. Comparison must iterate the union of both maps' keys, and every read must go through get() so that "missing = 0" is applied everywhere (I5, MM3, §12.6, §14.2). None from partial_cmp means concurrent and is never the same as Some(Equal) (P8). The price is size: metadata grows with the number of actors, and Charron-Bost 1991 is cited as showing this is tight in the worst case (P3).

Dotted version vectors: keeping both writes (§8.2, §8.3, I8)

A version vector is the same structure used to track replicas of data (§15.1). A dotted version vector adds a causal context cc (what the writer had seen) and a set of dots, each an (actor, counter) pair naming one write (§8.2, §36). On a server write whose client context is dominated by or equal to the server's cc, the server mints a new dot (server_id, cc[server_id]+1) and adds it to dots (§8.2). Merging takes the max of the two ccs and the union of the dots minus those already covered by the new cc (§8.2). Compaction drops any dot whose counter is at most cc[actor] (§8.2, I8).

The worked scenario (§8.3): after both clients read {S:5}, A's write yields dot (S,6) and B's write, made without knowing about A's, yields dot (S,7). The next reader receives both dots as sibling values instead of the plain-vector outcome where one overwrites the other; a last-writer-wins consumer then picks the higher counter, while an OR-Set-style consumer keeps both (§8.3, §21.2). What is concurrent is the clock's finding; whether it conflicts is a policy decision for the application (P10, MM2).

Step 3 ("S.cc = {S:6} is not yet merged") leaves unclear what cc holds; read as cc = {S:6}, the dot (S,6) is covered by cc, which I8 and the compaction rule forbid (§8.3, I8, §8.2). Step 5 points to "§8.4 below" for the plain-vector outcome; §8.4 lists malformed inputs.

Hybrid logical clocks: a logical clock tied to wall time (§8.2, §16.2, I10)

State is (wall, logical) (§8.2). On a local event, read physical time pt: if pt > wall, set (wall, logical) := (pt, 0); otherwise logical += 1 (§8.2, §16.2). A receive takes nw := max(pt, wall, m.wall) and branches four ways on which of the three equals nw; every branch must be present or monotonicity breaks (§8.2, §16.2). The result is a timestamp comparable with wall-clock time, but it is "Lamport with a physical anchor": it cannot say whether two events were concurrent (MM5).

The guarantee holds only while clocks are within a bound: the physical component never exceeds the local NTP or PTP wall clock by more than max_offset (I10). The check is strict greater-than, so exactly max_offset apart is allowed (§16.2, §16.8). A physical clock that jumps backwards, for example by 2 seconds after an NTP step, makes tick return ClockRegression rather than reuse the stale value (§8.4).

Interval tree clocks: membership that changes (§8.2, I11, §17.2)

A vector clock needs a fixed, known actor set (§8.1). An interval tree clock keeps a pair of trees, an id tree and an event tree (§8.2). fork splits the id into two halves that share the event tree; event increments the event tree at the leaf that the id owns; join recombines the ids and takes the max of the event trees (§8.2, §17.2). After every operation the tree must be in normal form, a canonical reduced shape, because otherwise equal values have several representations and equality and serialization break (I11, §17.6). A typical value is 5 to 20 bytes (§4, ADR-10). The cost traded away is tree depth growth under heavy fork/join churn (§29).

Crash-safe writes: durability is a path, not a database (§8.5, I6, MM6)

atomic_write writes a temp file, fsyncs it, renames it into place, then fsyncs the parent directory (I6, §18.2). The blueprint's failure trace (§8.5): replica R2 begins writing a merged clock after a partition heals and is killed after the temp file's fsync but before the rename. On restart the persistence layer finds the temp file, sees that the rename never completed, discards it and falls back to the last fsynced value (§8.5). No partial value is ever visible (I6). But the merge from R1 is lost and must be re-sent by the caller's anti-entropy layer; the contract is "no corruption", not "no loss on an unacknowledged crash" (§8.5). Skipping the parent-directory fsync loses the rename on power failure even though the data was synced, and the blueprint calls that the most common storage-engine bug in this domain (P7, FM-7).

The trade-offs — where engineers disagree

Version-vector anomaly: dots for client-server writes (ADR-20)

Chosen: dotted version vectors as the normative choice for client-server writes (ADR-20). Rejected: plain version vectors only, which lose writes under concurrent client-server writes (ADR-20, §8.3, §15.2). When the rejected choice is right: when writer identity is the replica identity, meaning server-to-server replication only with no client-direct writes (ADR-20).

Vector-clock map: an ordered tree (ADR-03)

Chosen: BTreeMap<ActorId,u64>, for deterministic iteration when serializing and a log-n bound on small n (ADR-03, §11.3). Rejected: HashMap and SortedVec (ADR-03). When the rejected choice is right: SortedVec wins above roughly 50 actors, where cache-linear scans beat tree traversal, checked in a hardening pass ADR-03 calls "Phase-10" though §21 is Phase 9 and §14.7 calls it "Phase 9 hardening" (ADR-03, §21.2, §14.7).

How to garbage-collect old actors: tombstone plus epoch (ADR-12)

Chosen: a tombstone marker plus a per-clock epoch counter, since reference counting needs global knowledge that is unavailable under partition (ADR-12). Rejected: reference counting (ADR-12). When the rejected choice is right: a single-process, no-partition deployment such as an embedded single-node cache, where global knowledge is trivially available (ADR-12). Either way pruning is opt-in and the operator supplies the policy (P4, ADR-18).

Detecting dead actors: a fixed timeout (ADR-19)

Chosen: heartbeat timeout, the simpler primitive, with phi-accrual able to layer on top (ADR-19). Rejected: a phi-accrual failure detector (ADR-19). When the rejected choice is right: wide-area deployments with highly variable round-trip times, where a fixed timeout produces too many false-positive death detections (ADR-19).

How far the HLC may drift: 500 ms (ADR-21)

Chosen: max_offset default of 500 ms, the CockroachDB production default, balancing false skew errors against the divergence bound (ADR-21, §16.6). Rejected: 50 ms and 5 s (ADR-21). When the rejected choice is right: 50 ms wins in a single datacenter with PTP-disciplined clocks, where a tighter bound catches real skew faster (ADR-21). Too tight makes spurious errors; too loose defeats the bounded-divergence guarantee (§16.6).

Wire encoding: custom framing (ADR-05)

Chosen: custom versioned binary framing, since 16-byte clocks do not amortize Protobuf's schema and reflection overhead (ADR-05, §19.1). Rejected: Protobuf, CBOR, MessagePack (ADR-05). When the rejected choice is right: Protobuf wins when the clock crosses a polyglot service boundary with existing Protobuf tooling and 16 bytes versus about 40 is not the bottleneck (ADR-05).

The blueprint calls ADR-03, ADR-08, ADR-09, ADR-20 and ADR-21 load-bearing: overturning one forces a re-derivation of the §4 numbers and the phase acceptance criteria that depend on them (§9).

Roads not taken

A single global sequencer (§34, Alternative 1): one leader assigns a monotonic offset. It wins when every write already routes through a consensus-backed leader and only an offset is needed; a single-partition Kafka topic is the example (§34). It is rejected because the targets are decentralized and partition-tolerant, and a leader is the coordination the toolkit exists to avoid (§34, §29).

Bloom-clock approximate causality (§34, Alternative 2): a lossy "may have seen" set instead of an exact vector. It wins for huge, highly dynamic actor populations that tolerate occasional false positives (§34). It is rejected because bit-for-bit conformance is the contract and a false positive is an I2/I3 violation (§34, P14, ADR-22). It is parked as deferred (§35).

TrueTime-style bounded physical clocks (§34, Alternative 3): GPS and atomic-clock hardware per datacenter, as Spanner uses. It wins when that hardware exists and linearizable cross-region transactions are needed (§34). It is rejected permanently, not deferred, as a hardware concern outside a library's scope (§34, §1).

Single writer per key (§34, Alternative 4): all writes go through one primary, so no concurrent write detection is needed. It wins when a single write-serialization point is acceptable, as in a primary-replica relational database (§34). It is rejected because the target is multi-writer and partition-tolerant (§34, §1).

The deferred register (§35) lists eight stretch items, each with an un-defer trigger. For example, clocks-bft waits until a deployment enters an untrusted multi-tenant threat model (T1), and TLA+ for HLC waits until HLC sits in a safety-critical financial-settlement path (§35).

What must never be false

  • I1: each event on an actor gets a strictly greater timestamp than any earlier one. Noticed by a 100K-sequence property test; clock_monotonicity_violation_total (§7).
  • I2: V_a ≤ V_b entry-wise exactly when a → b. Kani depth-5 check and a 100K-pair proptest (§7).
  • I3: concurrent_with is exactly partial_cmp(..).is_none(). Conformance cross-check; concurrent_with_drift_total (§7).
  • I4: merge is commutative, associative and idempotent. Proptest; merge_axiom_violation_total (§7).
  • I5: a missing actor entry means 0, everywhere. Sparse-set property test; no telemetry (§7).
  • I6: a clock is never on disk partly written. kill -9 fault injection 10,000 times; storage_partial_write_detected_total must stay 0 (§7).
  • I7: every wire frame has a valid version byte; unknown versions are rejected. frame_version_rejected_total (§7).
  • I8: no dot sits in both cc and dots. Post-compact size test; dvv_set_size gauge (§7).
  • I9: no actor is evicted while a reachable causally-prior event may reference it. Merge-after-prune fixtures; pruning_safety_violation_total must stay 0 (§7).
  • I10: an HLC never runs ahead of the local wall clock by more than max_offset. SkewError synchronously; hlc_skew_error_total (§7).
  • I11: an ITC is in normal form after every operation. Idempotency test over 100K values; itc_non_normal_form_total must stay 0 (§7).
  • I12: no two live actors share an ActorId. A heuristic only, actor_id_collision_suspected_total (§7).
  • I13: TotalOrder<A> never reports Equal for distinct (ts, actor) pairs. Property test on 100K pairs (§7).
  • I14: u64 counters never silently wrap; overflow is an error. Fuzz target; counter_overflow_total (§7).

What breaks in production

  • FM-3: a write is lost to the client-server anomaly. Cause: a plain VersionVector where a DVV was required (ADR-20). Detection: the version.client_server_anomaly conformance bucket, or in production only unexpected data-loss reports. Recovery: migrate to DottedVersionVector; writes already lost are not recovered automatically (§23).
  • FM-4: HLC skew violation. Cause: max_offset misconfigured, or an NTP/PTP source compromised (T5). Detection: a spike in hlc_skew_error_total. The request is rejected synchronously with SkewError; the operator re-syncs the physical clock source or adjusts max_offset (§23, I10).
  • FM-6: vector clocks grow without bound. Cause: no pruning policy on a long-running deployment (P3, P4). Detection: the vector_clock_actor_count gauge heading for 50,000. No automatic recovery; the operator sets a tombstone TTL or truncation threshold and restarts with pruning on (§23).
  • FM-7: a partial write is seen on recovery. Cause: a missing parent-directory fsync on Linux, or a tmpfs/overlayfs deployment. Detection: storage_partial_write_detected_total, which must stay 0, and the fault-injection harness. The system refuses to start with RecoveryError rather than serve corrupt data; the operator restores from backup (§23, I6).
  • FM-9: a pruning safety violation, silent lost updates. Cause: tombstone TTL shorter than the maximum in-flight message delay, or uncoordinated pruning across replicas (§20.6). Detection: pruning_safety_violation_total and a forensic CRDT-state audit; the blueprint calls it an undetected-until-audited class. Recovery: restore from backup, replay from the last good clock (§23, I9).

Threats a reader should know (§22):

  • T1: a malicious actor advances its own counter to 2^63 to win every concurrent LWW comparison. LWW over bare clocks is discouraged for untrusted writers (P10); signed clocks are deferred to clocks-bft.
  • T3: replaying an old captured clock value. The default wire format is unauthenticated, so the receiver keeps "last clock observed from sender" and drops strictly older values.
  • T5: manipulating the NTP source of an HLC node. The max_offset check (I10) rejects gross deviations; PTP-disciplined clocks suit high-trust deployments.
  • T7: premature eviction when a TTL is shorter than message time in flight. The mitigation is a documented requirement that the TTL exceed the maximum in-flight time, plus epoch-based rejection (§20.2).

How it compares

  • Riak chose dotted version vectors, adopted in its 2.0 release after two years of plain vectors in 1.x (§31). That is the same problem and fix as this design's DVV, in a replicated key-value store with many clients (§31).
  • CockroachDB chose hybrid logical clocks only, giving up concurrency detection for a fixed-size, wall-clock-comparable timestamp on every transaction (§31). That fits distributed SQL, where MVCC snapshot isolation needs a total order more than explicit concurrency detection (§31, P1).
  • DynamoDB chose version vectors truncated to the 10 most recent entries (§31). The blueprint calls this unsafe in general but acceptable because its actors are a small, well-known set of coordinator nodes (§31).
  • Spanner chose TrueTime, bounded-error physical time from GPS and atomic clocks, in place of logical clocks (§31). It wins on external consistency at the cost of a hardware dependency that a library-only deployment cannot assume (§31, §1).

Questions to test yourself

  1. Why must partial_cmp iterate the union of both clocks' actor keys rather than just one side's, and what specific comparison silently misfires if you don't? — Hint: §14.6 and the "missing = 0" invariant I5.
  2. Why is concurrent_with derived from partial_cmp rather than implemented independently, and which invariant silently breaks if a developer "optimizes" it into a separate implementation? — Hint: P2 and MM8.
  3. Walk through the exact event sequence in the client-server VV anomaly and identify precisely which structural element of the DVV design (not just "using DVVs generally") prevents it. — Hint: §8.3 and §8.2's DVV table.
  4. Why does the HLC bounded-skew guarantee require max_offset to exceed worst-case RTT plus NTP skew, and what are the operational symptoms of setting it too tight versus too loose? — Hint: §16.6 and the §4 round-trip row.
  5. Trace the crash-mid-write failure path (§8.5) and state precisely which invariant guarantees no corruption occurs — and which guarantee is explicitly not made by the same mechanism. — Hint: §8.5 and I6.

If you only remember three things

A logical clock records "before, after or concurrent", never "how long", and each of the six families answers that at a different price in metadata size and in what it loses (MM1, MM4, P1). Concurrent is not the same as conflicting, so the library reports concurrency and the application decides what to do with it, which is why plain version vectors lose writes that dotted version vectors keep (P10, ADR-20). Durability and pruning are safety properties of a protocol, so the parent-directory fsync and the "never evict a reachable actor" rule matter more than the choice of storage engine or the cleverness of the clock (MM6, MM7, I6, I9).

Words used here

  • Happens-before: the order generated by program order, send before receive, and chaining (§8.1).
  • Concurrent: neither event happens before the other (§8.1, §36).
  • Lamport timestamp: a single counter giving a total order consistent with happens-before (§36).
  • Vector clock: a counter per actor, giving exact before/after/concurrent answers (§36, I2).
  • Version vector: a vector clock used to track updates across replicas of data (§36).
  • Dot: an (actor, counter) pair naming one write (§36).
  • Causal context (cc): the "seen as of this write" version vector inside a DVV (§36).
  • Hybrid logical clock (HLC): a (physical, logical) clock with bounded skew (§36, I10).
  • Interval tree clock (ITC): a fork/event/join clock for changing actor sets (§36).
  • Normal form: the canonical reduced shape an ITC must be in before serialization (§36, I11).
  • fsync: the call that forces data, and separately directory metadata, to disk (§36).
