⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the full repository (§10) from one commit; land the minimal correctness kernel — LamportTs and VectorClock<u8> with tick/merge/partial_cmp only — sufficient to prove the happens-before relation end to end in one smoke test. No persistence, no wire format, no pruning yet (those are Phases 1–8). Constraint introduced: every subsequent phase builds only on types declared here or in §11.

Deliverable

make bootstrap && make build && make test all exit 0 on a clean checkout. A "Hello, Causality" fixture (§12.5) proves A's clock happens-before C's clock through a three- actor relay using only VectorClock::partial_cmp. clocks-cli inspect round-trips a literal vector-clock value to its Debug string.

Acceptance

cargo build --workspace completes in ≤ 60 s on a cold cache (CI runner baseline). Exactly 1 passing integration test (tests/hello_causality.rs). cargo clippy --workspace -D warnings reports 0 warnings. conformance.report.json validates against conformance/report_schema.json and reports outcome: "Pass" with cases_pass: 1, cases_fail: 0. ADRs ADR-01, ADR-02, ADR-03, ADR-14 committed as files under docs/adr/.

Fixtures

tests/hello_causality.rs — three actors A,B,C; A.tick(0), snapshot; B.merge(&A); B.tick(1); C.merge(&B); C.tick(2); expected: A_snapshot.partial_cmp(&C) == Some(Less), !A_snapshot.concurrent_with(&C). conformance/corpora/lamport_paper/ figure2_smoke.json — a 3-event single-actor Lamport monotonicity check (malformed-input sibling case deferred to §14.5).

Pitfalls
  • Comparing two VectorClocks' underlying BTreeMaps with == instead of via get() (I5) silently miscompares clocks with different-but-zero-equivalent actor sets.
  • Forgetting the union-of-keys iteration in partial_cmp (only iterating self's keys) misses actors present only in other — the §11.3 implementation must iterate the union.
  • Treating Cargo.toml workspace member stubs as "done" without a lib.rs that at least compiles empty — CI's cargo build --workspace will fail opaquely otherwise.

⬜ Phase 1 — Lamport Scalar Timestamps §13

Objectives

Complete LamportTs (§11.4) to full conformance with Lamport 1978 §3–§4: the local-event rule, the receive rule, and the (ts, actor) total-order extension via TotalOrder<A>. Constraint: LamportTs must never expose a concurrency-detection API (P11 §6) — this phase's exit test explicitly asserts the method does not exist (a compile-fail fixture).

Deliverable

cargo run --example 01_lamport_total_order reproduces Lamport 1978 Figure 2's timestamp sequence exactly and prints a strictly totally-ordered trace via TotalOrder<u8>.

Acceptance

LamportTs::tick/observe pass property tests for per-actor monotonicity (I1) over 100,000 random event sequences with zero violations. TotalOrder<u8> is a strict total order (no two distinct (ts,actor) pairs compare Equal) over 100,000 random pairs (I13). conformance/corpora/lamport_paper/figure2.json fixture matches bit-for-bit. cargo clippy -p clocks-core -D warnings reports 0 warnings.

Fixtures

lamport_paper/figure2.json — Lamport 1978 Figure 2 process trace, expected timestamp per event. lamport_monotonicity_100k.seed — a seeded proptest corpus regenerated on CI, regression-pinned by seed value. lamport_malformed/observe_before_init.json — an observe call with r = u64::MAX immediately after ZERO, expecting Err(Overflow) not a silent wrap (I14).

Pitfalls
  • Implementations that store (ts, actor) together and increment ts without re-checking the tie-break can produce duplicate (ts, actor) pairs across actors — always keep LamportTs bare and let TotalOrder add the tie-break (P9).
  • observe is max(ts, r) + 1, not max(ts, r + 1) — they differ exactly when ts == r; getting this wrong violates I1 on tied receives.
  • Assuming all actors start at the same timestamp — LamportTs::ZERO is a convenience default, not a protocol requirement; the max rule handles asymmetric starts.

⬜ Phase 2 — Vector Clocks (Fidge/Mattern) §14

Objectives

Bring VectorClock<A> (§11.3) to full Fidge-Mattern conformance (I2): entry-wise merge, correct partial_cmp over the union of actor key sets, and a machine-checked bound on the partial-order axioms. Constraint introduced: every comparison must handle asymmetric, sparse actor sets correctly (I5) — this is the phase where that convention is proven, not assumed.

Deliverable

cargo run --example 02_vector_clock_three_actors reproduces Mattern 1989 Figure 1's partial-order matrix exactly. cargo kani -p clocks-vector passes the depth-5 bounded model check on I2 with no counterexample.

Acceptance

VectorClock::partial_cmp agrees with the Fidge-Mattern theorem on 100,000 random event sequences (I2), zero mismatches. Merge commutativity/associativity/idempotency (I4) hold on 100,000 random triples/pairs each. The Kani proof at depth 5 (five actors, three events per actor) reports no counterexample. examples/02_vector_clock_three_actors output matches conformance/corpora/fidge_mattern/mattern_fig1.json bit-for-bit.

Fixtures

fidge_mattern/mattern_fig1.json — Mattern 1989 Figure 1 worked trace. vector_axioms_ 100k.seed — proptest corpus for I2/I4 (regression-pinned). vector_malformed/asymmetric_ sparse.json — two clocks with disjoint actor sets, expecting correct Some(Less) / None per the union-iteration rule (I5), not a spurious None. vector_replay/ duplicate_merge.json — merging the same remote clock twice, expecting idempotency (I4) to leave the result unchanged after the second merge.

Pitfalls
  • partial_cmp returning Some(Equal) for two distinct concurrent clocks (conflating equality with "neither dominates") — a direct I2/I3 violation; the conformance suite's vector.axioms bucket catches this via antisymmetry checks.
  • Iterating only self.entries.keys() in partial_cmp misses actors present only in other (I5) — always iterate the union, as specified in §11.3's contract.
  • Unbounded growth: a deployment running vector clocks for two years without pruning reaches the 400 KB/clock ceiling at 50,000 actors (§4 row 1, P3 §6) — Phase 8 (§20) is mandatory reading before production deployment, not optional hardening.

⬜ Phase 3 — Version Vectors & Dotted Version Vectors §15

Objectives

Implement VersionVector<A> (structurally identical to VectorClock but the replica- conflict-detection interpretation, Parker 1983) and DottedVersionVector<A> + DvvSet (§11.5) fixing the client-server anomaly (§8.3, Preguiça 2010/2012). Constraint: the DVV dots set must stay closed under I8 (no dot both present in dots and covered by cc) after every operation.

Deliverable

cargo run --example 03_dvv_client_server reproduces the exact Preguiça 2012 §2 scenario: two concurrent client writes through one server produce two DVV siblings; the plain-VV equivalent (run side-by-side in the same example) demonstrably loses one write.

Acceptance

DottedVersionVector::descends agrees with Preguiça 2010 §4 examples bit-for-bit. The client-server anomaly test passes: 2 concurrent client writes yield 2 surviving DVV siblings vs. 1 surviving plain-VV value. Differential test against Riak's DVV implementation (via differential/riak_dvv/ shim) reports bit-identical merge/compare outputs on 10,000 random sequences (I8, ADR-22).

Fixtures

preguica_dvv/section4_examples.json — Preguiça 2010 §4 worked cases. preguica_dvv/ client_server_anomaly.json — the §8.3 two-client scenario, expected: 2 DVV siblings, 1 plain-VV value (documenting the loss). dvv_malformed/non_canonical_dot.json — a dot already covered by cc present in dots (I8 violation), expecting compact to remove it on ingest. differential/riak_dvv/10k_random.seed — the differential corpus.

Pitfalls
  • Using Vec<Dot> instead of BTreeSet<Dot> for dots (ADR-04) — order-sensitive representations hash differently for logically identical values, breaking content- addressable storage use cases.
  • Omitting the dot-set superset check in descends (only checking cc domination) breaks the no-lost-write invariant (I8) — both checks are required per Preguiça 2010 §4.
  • Exposing plain VersionVector without the "writer identity = replica identity only" documentation (ADR-20) — Riak shipped this exact anomaly in production for two years (2010–2012, Klophaus 2010 vs. Preguiça 2012) before the DVV migration.
  • Forgetting to call DvvSet::compact after every merge (I8) — the set grows unboundedly even when the underlying value has stabilized (§20.5 cross-reference).

⬜ Phase 4 — Hybrid Logical Clocks §16

Objectives

Implement Hlc (§11.6) to Kulkarni 2014 conformance: the three-rule algorithm (local event, send, receive), the bounded-skew guarantee (I10), and PhysicalClockSource integration for NTP/PTP/mocked sources. Constraint introduced: max_offset (ADR-21, default 500 ms) must be enforced synchronously on every tick/observe call, never asynchronously or best-effort.

Deliverable

cargo run --example 04_hlc_two_node_ntp simulates two nodes with NTP-driven physical clocks and reports zero monotonicity violations over 10,000 iterations, with at least one injected clock-skew event correctly rejected via SkewError.

Acceptance

Hlc::tick/observe agree with Kulkarni 2014 §4 worked examples on 1,000 random sequences, zero mismatches. The bounded-skew guarantee (I10) is enforced: a SkewError is returned in 100% of injected-skew cases exceeding max_offset = 500 ms (ADR-21). Differential test against CockroachDB's HLC (differential/cockroachdb_hlc/ shim) reports bit-identical outputs on 10,000 random (local_time, remote_clock) pairs.

Fixtures

kulkarni_hlc/figure1_trace.json — Kulkarni 2014 Figure 1 worked example. hlc_skew/ injected_backwards_jump.json — a physical-clock regression scenario, expecting Err(SkewError::ClockRegression) (§8.4). hlc_malformed/oversized_max_offset.json — a max_offset configured below the measured RTT, expecting spurious-SkewError-rate documentation, not a silent pass. differential/cockroachdb_hlc/10k_random.seed.

Pitfalls
  • Omitting any of the four observe branches (§16.2) — Kulkarni 2014 Figure 1 is the canonical reference; transcribe every branch, or property tests over 1,000 sequences will surface a monotonicity gap eventually but a code review should catch it first.
  • Trusting CLOCK_REALTIME without backwards-jump detection — an NTP step adjustment can move the wall clock backwards; use CLOCK_MONOTONIC_RAW where available or explicitly check pt < prior_observed_pt (§8.4 malformed-input example).
  • Setting max_offset too tightly (below RTT + NTP skew) produces spurious SkewError storms; too loosely defeats the bounded-divergence guarantee entirely — 500 ms (ADR-21) is the CockroachDB-validated compromise, not an arbitrary default.

⬜ Phase 5 — Interval Tree Clocks §17

Objectives

Implement IntervalTreeClock (§11.7) to Almeida 2008 conformance: fork/event/join, normal-form invariant (I11) after every operation, and the bit-packed serialization (§17.4). Constraint introduced: no operation may leave a non-normalized tree observable outside the crate boundary.

Deliverable

cargo run --example 05_itc_fork_event_join reproduces the Almeida 2008 §6 example exactly, printing both the Id and Event trees at each step in normal form.

Acceptance

fork/event/join agree with Almeida 2008 §6 worked examples bit-for-bit. Normalization is idempotent: normalize(normalize(x)) == normalize(x) on 100,000 random ITCs (I11). The bit-packed serialization round-trips (decode(encode(x)) == x) on 100,000 random ITCs, encoding to 5–20 bytes typical (§4). Differential test against the Almeida reference C implementation reports bit-identical outputs on 10,000 random operation sequences.

Fixtures

almeida_itc/section6_worked_example.json — the Almeida 2008 §6 trace. itc_normal_form/ 100k_random.seed — the idempotency proptest corpus. itc_malformed/non_normalized_ wire_input.json — an Id::Node(Leaf(0),Leaf(0)) arriving on the wire instead of Leaf(0), expecting the decoder to normalize on ingest (§8.4, I11). differential/ itc_c_reference/10k_random.seed.

Pitfalls
  • fork implemented as "allocate a new node" instead of Almeida §3's specific id-splitting recursion silently corrupts the partial order — this is the most common ITC bug (§8.2's fork transition table is the exact contract).
  • Skipping normalization after any single operation — an un-normalized ITC has multiple representations for the same logical value; equality and serialization determinism both break (I11).
  • Little-endian bit-packing (Almeida §7 specifies big-endian within bytes) — produces wire-incompatible output that round-trips with itself but not with any conformant peer.
  • Unbounded recursion depth in fork on a deeply-forked history — the Rust port must bound recursion explicitly (the C reference implementation does not, a documented pitfall not to copy, §5 Reference Implementations).

⬜ Phase 6 — Persistence & Crash Recovery §18

Objectives

Implement clocks-storage (§11.8): the atomic_write primitive, ClockStore trait, and sled/RocksDB backends, satisfying the crash-recovery invariant I6 (P7 §6). Constraint introduced: every write must be atomic at clock-value granularity, verified by fault injection, not just code review.

Deliverable

clocks-storage round-trips every clock type (Lamport, VC, DVV, HLC, ITC) through both backends. The fault-injection harness runs 10,000 kill -9 trials against atomic_write with zero observed partial writes.

Acceptance

atomic_write survives kill -9 + power-loss simulation on 10,000 random writes with 0 partial writes observed (I6). The sled backend round-trips 100,000 random clock values across all five types. The RocksDB backend round-trips the same corpus. Recovery test: write 1,000 clocks, crash mid-write 10,000 times via fault injection; on restart the recovered clock is always one of the previously-fsynced values (never a corruption) — 100% pass rate required.

Fixtures

storage.atomic_write bucket — the 10,000-trial fault-injection corpus. storage. recovery bucket — the crash-mid-write-10,000-times corpus. storage_malformed/ truncated_sled_file.json — a deliberately truncated sled data file, expecting RecoveryError, not a silent empty-store start. storage_failure_path/tmpfs_no_fsync.md — documented (not automated) fixture: a tmpfs-backed store, expecting the operator runbook to flag "no durability" per §18.7.

Pitfalls
  • fsync on the data file alone is insufficient on Linux — the parent-directory fsync is required for the rename itself to be durable (I6, the single most common storage- engine bug in this domain).
  • tmpfs/overlayfs silently ignore fsync (no backing store) — document the real- filesystem requirement explicitly; a deployment on tmpfs has zero durability despite every fsync call "succeeding".
  • sled's flush is best-effort; only flush_async's completed future guarantees durability — calling insert and returning without awaiting flush ships silent corruption risk.
  • RocksDB's default WriteOptions do not fsync — set_sync(true) (ADR-07) is required for clock writes; the throughput cost is the price of the durability guarantee (§4 row 8).

⬜ Phase 7 — Wire Format & Framing §19

Objectives

Implement clocks-net's versioned binary Frame (§11.8) satisfying compatibility invariant I7: a 1-byte version prefix, type tag, varint length, type-specific payload. Constraint introduced: an unknown version must be rejected, never guessed or silently downgraded (P6 §6).

Deliverable

The frame encoder/decoder round-trips every clock type through the wire format. The 24-hour fuzz canary (fuzz_targets/frame_decode.rs) completes with zero panics. docs/architecture/wire-format.md documents the format with byte-level worked examples.

Acceptance

The frame encoder/decoder round-trips on 100,000 random clocks of every type with 0 mismatches. The version-mismatch test rejects both v0 and v2 frames against a v1 decoder with the correct typed error (I7). The 24-hour fuzz canary (audits/fuzz/canary-24h-<sha>.md) reports 0 panics. Frame encode/decode throughput hits M11/M12 (≥1 GB/s for a 100-actor vector clock, §4).

Fixtures

net.frame_roundtrip bucket — 100,000-frame proptest corpus across all six types. net.version_mismatch bucket — crafted v0/v2 frames against the v1 decoder. net_ malformed/truncated_length.json — declared length exceeds remaining buffer (§8.4), expecting FrameError::Truncated. net_malformed/non_canonical_varint.json — a varint with a non-canonical leading-zero-byte encoding, expecting rejection (hash-collision risk if used as a content address, §19.6).

Pitfalls
  • Confusing LEB128's little-endian varint convention with the big-endian convention used for u32/u64/UUID actor IDs — mixing them ships a wire-incompatible format across otherwise-conformant implementations.
  • Treating length as the total frame length instead of the payload length — decoders computing "next frame offset" must add the header size, or every subsequent frame in a stream misparses.
  • Accepting non-canonical varint encodings (extra leading zero bytes) — breaks hash-based content addressing if the wire format is ever reused for that purpose (documented, not currently exercised, but a fuzz-target regression case per §19.5).

⬜ Phase 8 — Pruning & Garbage Collection §20

Objectives

Implement clocks-gc (§11.9): heartbeat-based actor-death detection, tombstones, threshold-based truncation, and DVV compaction, all subordinate to the safety invariant I9 (P4 §6: never evict an actor reachable from a causally-prior event). Constraint introduced: every pruning primitive must be opt-in and documented with its specific safety caveat — no "just works" default (P4).

Deliverable

HeartbeatDetector correctly identifies dead actors in a simulated fleet. Tombstoned entries preserve causal correctness during the TTL window in a simulated merge sequence. docs/architecture/pruning-policy.md documents the safety invariant and per-strategy tradeoffs.

Acceptance

HeartbeatDetector correctly identifies dead actors over 10,000 random heartbeat schedules with detection latency within 2× the configured timeout (ADR-19). truncate_to_k_recent agrees with Dynamo section 6.3 specification on published test vectors. Tombstones preserve causal correctness during the TTL window on 10,000 simulated merge sequences (I9), 0 safety violations. DvvSet::compact agrees with Riak's compaction behavior on 10,000 random sequences.

Fixtures

gc.tombstone_ttl bucket — 10,000-schedule proptest corpus, asserting I9 holds throughout the TTL window. gc.heartbeat_detector bucket — detection-latency proptest. gc_ malformed/prune_referenced_actor.json — a deliberately unsafe prune (evicting an actor still referenced by an in-flight event), expecting the safety-check layer to reject it, not silently proceed. gc_failure_path/ttl_shorter_than_message_delay.md — documented fixture: a message arriving after tombstone-TTL expiry, demonstrating the "lost update in disguise" failure mode operators must guard against via TTL configuration (§20.8).

Pitfalls
  • Tombstone TTL shorter than the maximum message-in-flight time — a late message arrives "after" the tombstone drops, its actor entry is treated as fresh, and a lost update results in disguise (the single most common pruning production incident, per the Riak and Dynamo operational literature, §5).
  • Truncation (truncate_to_k_recent) is unsafe in general — the Dynamo pattern works because the actor population (coordinator nodes) is bounded and known; an unbounded- actor deployment cannot safely truncate without a separate consistency mechanism (P3).
  • Skipping DvvSet::compact after a custom merge path — the set grows unboundedly even when the underlying value is stable (cross-referenced from §15.6, I8).
  • Pruning uncoordinated across replicas — if replica A prunes actor X but replica B does not, B's clock carries an entry A cannot interpret; the epoch mechanism (§20.2) handles this, but only if every replica participates.

⬜ Phase 9 — Public API, Integration & Performance Hardening §21

Objectives

Ship the top-level clocks facade crate re-exporting every sub-crate's public surface, the four consumer-integration recipes (CRDT, snapshot isolation, tracing, exactly-once), and the performance-hardening pass (SoA layout, SIMD comparison, lazy serialization) against the M1–M17 targets (§28). Constraint: hardening must not change any CausalClock contract (§11.1) — only internal representation.

Deliverable

All four integration examples run and produce their documented expected output. clocks-bench reports every M1–M12 target (§28) met or exceeded on the CI reference runner. A 24-hour soak at 1M ticks/s shows zero memory growth (Phase-0 gate toward the 30-day Sealed gate, M17).

Acceptance

cargo run --example 06_lww_register_over_vv produces the documented LWW resolution on a 3-actor concurrent-write scenario. cargo run --example 07_orset_over_dvv produces the documented OR-Set state after an add-then-concurrent-remove sequence. cargo run --example 08_trace_causality reconstructs a distributed trace with 0 causality inversions. cargo run --example 09_exactly_once_delivery deduplicates 10,000 messages over a simulated flaky-network replay with 0 false negatives. clocks-bench meets all M1–M12 targets (§28) on the CI reference runner.

Fixtures

examples/06_lww_register_over_vv expected-output fixture: the higher-tiebreak write survives. examples/07_orset_over_dvv expected-output fixture: add-then-concurrent-remove yields the element present (remove's context did not dominate the concurrent add's dot). examples/08_trace_causality fixture: 0 inversions over 10,000 simulated cross-node spans. examples/09_exactly_once_delivery fixture: 10,000-message dedup corpus with injected redelivery.

Pitfalls
  • LWW tie-breaking by (actor, ts) is not equivalent to wall-clock LWW — document the tie-break policy at every call site; a caller expecting "most recent by wall time" will be surprised by an actor-ID tiebreak on true ties.
  • OR-Set removes must carry the causal context, not just the dot — storing only the dot loses the ability to correctly detect "add after remove" as a new, surviving add.
  • Distributed tracing causality via HLC works only within the max_offset bound (§16) — cross-region traces with >500 ms RTT and weak NTP discipline can still produce inversions; document the requirement rather than silently tolerating it.
  • The SoA layout (§21.2 hardening) has real overhead below n≈50 actors — always benchmark the crossover for the target deployment rather than assuming SIMD always wins.
