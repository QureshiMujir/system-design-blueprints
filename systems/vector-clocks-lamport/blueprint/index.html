95 — Vector Clocks + Lamport Timestamps

Project Number: 95

Project Name: Vector Clocks + Lamport Timestamps

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade causal-ordering toolkit — a single Rust workspace exposing every major logical-clock family (Lamport scalar timestamps, vector clocks, version vectors, dotted version vectors, hybrid logical clocks, interval tree clocks) behind one CausalClock trait (§11.1), plus the production glue the literature assumes but never specifies: durable crash-safe persistence, versioned wire framing, actor pruning/garbage collection, and CRDT/snapshot-isolation/tracing/exactly-once integration recipes. The system is a library and CLI, not a service: it has no network listener of its own; it is linked into distributed-systems components (KV stores, CRDT engines, tracing collectors, message brokers) that need causal ordering as a primitive.

Phase-0 deliverable (numbered modules, §10 Repository Layout has the full tree):

  1. clocks-core — ActorId trait, LamportTs, TotalOrder<A>, CausalClock trait.
  2. clocks-vector — VectorClock<A> (skeleton: tick/merge/partial_cmp only).
  3. clocks-cli — clocks binary: inspect subcommand only in Phase 0.
  4. conformance/runner — emits conformance.report.json; one bucket wired.
  5. Repository scaffold — governance files, CI skeleton, Makefile, Dockerfile (§12).

System boundaries.

  • Provides: clock value types, tick/merge/compare/serialize operations, crash-safe persistence primitives, versioned wire framing, pruning primitives (tombstone, epoch, heartbeat-death-detection), conformance fixtures against six published papers plus three production systems.
  • Delegates: network transport (the caller owns sockets/gRPC/HTTP), conflict resolution policy (the library reports concurrent_with; the caller decides LWW / merge / surface-to-user), actor-identity assignment (the caller mints ActorIds), the physical time source for HLC (a PhysicalClockSource the caller implements against NTP/PTP/TSC).
  • Does NOT provide: a full CRDT library (§21 ships integration recipes, not a shipped CRDT crate — PhaseDeferred("§21.2")), Byzantine-fault-tolerant / cryptographic clocks (PhaseDeferred("§22")), TrueTime-style bounded-error physical clocks (out of scope permanently — requires GPS/atomic-clock hardware, a separate infrastructure concern), Bloom-clock approximations (PhaseDeferred("§34")).

Non-goals. Not a distributed database. Not a consensus protocol (no leader election, no Raft/Paxos log). Not a network protocol implementation (framing only, no transport). Not a UI. Not a general-purpose serialization framework (the wire format is clock-specific).

Deployment model. A Rust crate (clocks facade + six sub-crates) consumed via Cargo.toml dependency; clocks-cli ships as a standalone binary (Linux/macOS/Windows, static-linked via cross) for offline clock inspection and operator tooling. No daemon, no persistent network port; clocks-storage opens a local sled/RocksDB directory the host process owns.

Target users/operators. Distributed-systems engineers building CRDT engines, replicated key-value stores, distributed tracing collectors, or exactly-once message brokers; SREs who must debug a causality violation (a stale read, a lost update, a trace with negative latency) at 3 a.m. and need named runbooks, not a re-derivation of Lamport 1978 under pressure.

What later phases unlock. Phase 1 (Lamport, §13) unlocks total-order replicated logs. Phase 2 (vector clocks, §14) unlocks concurrency detection. Phase 3 (version vectors/DVVs, §15) unlocks replica conflict detection without the client-server anomaly. Phase 4 (HLC, §16) unlocks causally-consistent snapshots with wall-clock-comparable timestamps. Phase 5 (ITC, §17) unlocks dynamic-membership causality with no metadata growth. Phases 6–7 (§18–§19) unlock crash-safe persistence and cross-version wire compatibility. Phase 8 (§20) unlocks bounded-memory long-running deployments. Phase 9 (§21) unlocks the CRDT/tracing/exactly-once consumer recipes.

Recommended language: Rust 1.78+ (edition 2021). Rationale: the borrow checker statically eliminates the mutable-aliasing class of bugs (a vector-clock entry mutated through two aliases mid-merge) that has produced real CVEs in C++ distributed-systems libraries; no_std + alloc-optional support lets clocks-core and clocks-vector link into embedded actors, WASM peers, and kernel-resident replicas without a second implementation; zero-cost abstractions keep the CausalClock trait dispatch free of runtime overhead on the hot tick/merge path (M2–M10, §28). Rejected: Go (GC pauses are incompatible with the ≤200 ns HLC tick target, M6, §28; no no_std story for embedded replicas); OCaml (excellent for the domain model but the ecosystem for no_std/embedded and for cargo-fuzz-equivalent tooling is thin); Erlang/Elixir (BEAM's process model is a poor fit for a linked library — this is not a service with its own supervision tree); C++ (no memory-safety guarantee for a library every downstream consumer trusts with correctness- critical merge logic; ADR-01, §9).

Prerequisites. The happens-before relation (Lamport 1978 §2); partial orders vs. total orders; the distinction between concurrent (a clock-level property, P10 §6) and conflicting (an application-level decision layered on top); the O(n_actors) cost model of vector-sized metadata (Charron-Bost 1991); ability to read Mattern 1989 §3 and explain why vector clocks are tight without flipping pages. Familiarity with one production causal-clock deployment (Riak DVVs, CockroachDB HLC, Cassandra hybrid timestamps) helps but is not required — §5 and §30 (Comparative Architecture) supply it.

Estimated timeline. Phase 0: 1 week. Full system (Phases 0–9, all conformance/ differential/fuzz/soak gates): 22–26 weeks (≈5–6 months), matching the phase-by-phase weekly estimates in §12–§21.

Deferred features (full table: Deferred Features Register, §35):

  • Bloom-Clock approximate causality — PhaseDeferred("§34").
  • BFT / cryptographic vector clocks (clocks-bft) — PhaseDeferred("§22").
  • TLA+ specification of HLC monotonicity — PhaseDeferred("§26").
  • Coq/F* formal proof of the Fidge-Mattern theorem (beyond the Phase-2 Kani bound) — PhaseDeferred("§14.5").
  • Treedoc-style structured clocks (Preguiça-Marques-Shapiro-Letia 2009) — PhaseDeferred("§21.2").
  • Differential testing against Cassandra hybrid timestamps — PhaseDeferred("§26").
  • Wait-free HLC-MVCC integration (Wang-Faleiro-Abadi 2017) — PhaseDeferred("§21.2").
  • Kubernetes-native clocks-gc sidecar — PhaseDeferred("§20.10").

2. Why Build This

Causality is the substrate every distributed abstraction sits on: eventual consistency, CRDTs, anti-entropy gossip, snapshot isolation, distributed-tracing causality, and exactly-once delivery all collapse into incoherent races the moment the underlying clock is wrong. Every production system that survives past a single node routes through one of the six families here — DynamoDB carries version vectors per item (DeCandia et al. SOSP 2007 section 4.4), Riak carries dotted version vectors (Preguiça et al. 2012), CockroachDB carries HLCs on every transaction (Kulkarni et al. 2014), Spanner carries TrueTime intervals (a real-clock variant of the same problem, Corbett et al. OSDI 2012), and every CRDT system from Redis CRDB to Automerge to Y.js carries some scheme. The families are not interchangeable (P1, §6); picking the wrong one ships a bug class that survives years of incident reviews before someone reads the original paper.

Why it matters architecturally. This is the rare subsystem where the theory (Lamport 1978, Fidge 1988, Mattern 1989) and the production deployment story (Dynamo, Riak, CockroachDB) are both fully public and cross-checkable — a conformance suite can validate bit-for-bit against the papers and differentially against real systems (§14.5, §15.5, §16.5, §26). Few subsystems offer that combination of rigor and grounding.

Why it matters historically. Lamport 1978 is arguably the paper that founded distributed-systems theory as a discipline; Fidge 1988 and Mattern 1989's independent derivation of the same vector structure is a textbook case of convergent discovery; the Riak VV→DVV migration (2010–2012) is a canonical "the theory paper preceded the production fix by years" story (Klophaus 2010 vs. Preguiça 2012).

Engineering muscles built. Reading and implementing a theorem-grade paper to bit-for-bit conformance (not just "the gist"); building a differential test harness against a foreign-language reference implementation; designing a trait that lets six structurally different value types share one calling convention (CausalClock); reasoning about unbounded-metadata-growth failure modes that only manifest after months of production uptime; writing a pruning safety invariant and proving no unsafe eviction path exists.

Cross-links to sibling systems (by name, referenced throughout): a CRDT library (LWW- register, OR-Set, RGA) sits directly on top of this project's clocks (§21.2); an anti-entropy gossip layer (Demers et al. 1987) needs version vectors for delta reconciliation; a distributed tracing collector (Jaeger/Zipkin-equivalent) needs HLC-style causal ordering across spans (§21.3); an exactly-once message broker (Kafka-transactions- equivalent) needs DVV-backed idempotency keys (§21.4).

Calibration value. A causal-ordering toolkit is small enough to finish in months (unlike a full database) yet deep enough that finishing it correctly requires reading eight theorem-bearing papers end to end and reconciling their notations (Lamport's C(a), Fidge's vector, Mattern's lattice framing, Preguiça's dots) into one coherent API. It calibrates "can I take a paper to production" better than almost any other single-quarter project.

What Mastery Looks Like.

  • Derive the Fidge-Mattern theorem's contrapositive (concurrent ⟺ neither dominates) from the entry-wise partial order and defend it against a skeptical reviewer — tied to Phase 2 (§14).
  • Explain, with the exact sentence citation, why plain version vectors lose a write under concurrent client-server writes, and why the DVV dot/context split fixes it — tied to Phase 3 (§15).
  • Derive the HLC bounded-skew guarantee from the max(physical, logical)+1 rule and state the exact assumption (bounded clock skew) it depends on — tied to Phase 4 (§16).
  • Explain why Interval Tree Clocks solve the fixed-actor-set problem that vector clocks cannot, using the fork/event/join normal-form argument — tied to Phase 5 (§17).
  • Design a crash-recovery invariant for a clock-value store and identify the exact fsync ordering bug that breaks it on Linux (parent-directory fsync) — tied to Phase 6 (§18).
  • State the safety invariant that makes clock pruning sound ("never evict an actor reachable from a causally-prior event") and name two concrete violations of it — tied to Phase 8 (§20).
  • Choose the correct clock family for a named scenario (replicated log, CRDT store, distributed trace, exactly-once broker) and justify the rejection of the other five — tied to Phase 9 (§21) and the Comparative Architecture Table (§30).

Consumer APIs box. Never touches a concrete clock type; drives everything through CausalClock (P2, §6). A CRDT does not know whether it runs over a vector clock or a DVV — this is the load-bearing decoupling boundary of the whole system.

Clock-type layer box. Five independent crates, one shared trait. Each crate owns its own partial_cmp implementation because the representation of the partial order differs (entry-wise max on a map vs. dot-set containment vs. tree dominance) even though the contract (§11.1) is identical.

Wire format box. A concurrency boundary as much as a serialization boundary: once a clock value leaves process memory it is a byte string with a version prefix (§19.1); nothing downstream may assume in-process representation.

Persistence box. The durability boundary. Everything above this line can be rebuilt from a crash by replaying from the last fsynced clock value; nothing below it (disk, kernel page cache, filesystem semantics) is this project's responsibility beyond documented assumptions (§4).

Pruning/GC box. A cross-cutting concern, not a layer: it operates on every clock type's on-disk and in-memory representation and is opt-in per deployment (P4, §6) because the safety invariant needs deployment-topology knowledge the library cannot infer.

All later sections stay consistent with this diagram; a component introduced in a later section must appear in one of these five boxes or be flagged non-goal (§1).

6. Design Principles

  1. P1 — Four families serve four purposes; ship all four (plus HLC and ITC). Lamport is for total-order extension on a small log. Vector clocks are for partial-order detection between processes with stable identities. Version vectors are for replicated- data conflict detection between server-side replicas. DVVs are for the same when writers are clients. HLCs add approximate physical time. ITCs handle dynamic membership. Tradeoff: five times the maintenance surface of one scheme. Operational implication: the Comparative Architecture Table (§30) is mandatory reading before picking one. Violating this (shipping only vector clocks "because it's simplest") reproduces the exact client-server VV anomaly Riak spent two years fixing (§15.2).
  2. P2 — The CausalClock trait is the integration contract. Every scheme implements tick, merge, partial_cmp (§11.1), serialize/deserialize. concurrent_with is a derived default method, never independently implemented. Tradeoff: trait-object dispatch has a small vtable cost vs. monomorphized generics (mitigated: consumers are generic over C: CausalClock, ADR-13). Violating this by hand-rolling concurrent_with risks it drifting from partial_cmp — caught by I3 (§7).
  3. P3 — Vector-clock size is O(n_actors); the library refuses silent unboundedness. Charron-Bost 1991 is tight on the worst case. Tradeoff: every vector-clock deployment must pair with a pruning policy (§20) or accept the 400 KB/clock ceiling documented in §4. Violating this ships the two-year-unpruned-deployment failure mode (FM-6, §23).
  4. P4 — Pruning is mandatory in production; the library supplies primitives, the operator supplies policy. The safety invariant I9 (§7) requires deployment-topology knowledge the library cannot infer. Tradeoff: no "just works" default GC; every deployment must configure a tombstone TTL or truncation threshold explicitly. Operational implication: docs/runbook/pruning-incident.md (§10) is required reading for any operator running this in production. Violating I9 causes silent lost updates.
  5. P5 — HLC requires a documented clock-skew bound and physical-clock source. Kulkarni 2014's monotonicity guarantee assumes bounded skew between nodes. Tradeoff: the Hlc constructor refuses to produce a value when the local clock is observed jumping backwards beyond max_offset (ADR-21). Violating this breaks the bounded-divergence guarantee silently (FM-4, §23).
  6. P6 — Serialization format is part of the API contract, versioned from day one. A clock persisted by version 0.3.0 must be readable by 0.4.0. Tradeoff: a 1-byte version prefix on every frame (§19.1) costs bytes on the wire in exchange for zero flag-day migrations. Violating this (skipping the version byte "to save space") forces a coordinated fleet-wide upgrade instead of a rolling one — a Compatibility & Versioning (§25) failure.
  7. P7 — Persistence is atomic at the clock-value granularity. A partial write must never be observable on recovery (I6, §7). Tradeoff: every write pays an fsync (data)
    • fsync (parent directory) cost (M13, §4) instead of a buffered write. Violating this on Linux specifically (skipping the parent-dir fsync) loses the rename on power-failure even though the data itself was fsynced — the single most common storage-engine bug in this domain (FM-7, §23).
  8. P8 — Comparison operators are total-order-compatible with partial-order semantics. partial_cmp returns Some(Less/Equal/Greater) or None (concurrent); None is never conflated with Some(Equal). Tradeoff: callers cannot use Ord/< directly on a raw clock — they must handle None explicitly or opt into TotalOrder<A> (P9). Violating this is I3's core failure mode.
  9. P9 — Ord is opt-in via a separate TotalOrder<A> wrapper. Lamport's (ts, actor) tie-break is exposed only through TotalOrder<LamportTs>; LamportTs itself implements only PartialOrd. Tradeoff: one extra type for callers who want a total order. Violating this (implementing Ord directly on LamportTs) silently hides the fact that concurrent-looking events got an arbitrary tie-break.
  10. P10 — Concurrent is a clock property; conflicting is an application decision. Two writes whose clocks are concurrent are eligible to conflict; whether they do is the consumer's resolution policy (LWW / OR-Set union / manual surfacing). Tradeoff: the library never resolves conflicts itself, so every consumer must supply a policy (§21). Violating this by baking in a default resolution (e.g. "last write by wall-clock wins") silently drops correct concurrent updates for consumers that needed a different policy.
  11. P11 — Lamport timestamps cannot detect concurrency, by design, not by omission. Callers that need concurrency detection are pointed to vector clocks or DVVs; the API surface does not expose a concurrent_with on LamportTs at all. Tradeoff: a caller who only needs total order pays no vector-sized metadata cost. Violating this (bolting concurrent_with onto Lamport by comparing raw scalars) produces false concurrency answers — two causally-related events can share a scalar timestamp.
  12. P12 — Actor identity is a bounded type parameter, Uuid by default. ActorId: Copy + Ord + Hash + Serialize + Deserialize. Tradeoff: generic code is slightly harder to read than a hard-coded Uuid everywhere, in exchange for u8 in tests (compact output) and u64 in benchmarks (tight memory) without duplicating implementations. Violating this (hard-coding Uuid) blocks the embedded/WASM use case in §1.
  13. P13 — No unsafe anywhere in the workspace. ITC bit-packing (§17.4) is pure safe Rust. Tradeoff: some hand-rollable bit tricks are left on the table; revisited only if a profiler shows a documented >20% win on a hot path unreachable safely (none found to date). Violating this reintroduces the memory-safety risk class Rust was chosen to eliminate (§1 language rationale).
  14. P14 — Conformance is the contract, not a nice-to-have. Every partial-order axiom (reflexivity, antisymmetry, transitivity), merge commutativity/associativity/ idempotency, HLC bounded-skew tolerance, and ITC normal form is a property test; three differentials (Riak, CockroachDB, Almeida's ITC C reference) run in CI. Tradeoff: CI wall-clock time (M14, §28) grows with the corpus. Violating this (merging a scheme without its differential) is exactly the failure class that let the Riak VV anomaly ship for years (§2).

8. Domain Model

8.1 The causality model

The happens-before relation → (Lamport 1978 §2) is the strict partial order generated by: (a) program order within one actor; (b) send-before-receive across actors; (c) transitive closure. Two events a, b are concurrent (a ∥ b) iff neither a → b nor b → a. Every clock in this system is a finite representation of a prefix of this relation, with a scheme-specific comparison operator that must agree with →/∥ exactly (I2). The design space differs only in what is tracked: Lamport tracks a linearization consistent with → (loses ∥); vector/version clocks track exact →/∥ for a known, stable actor set; DVVs track it for a client-server topology where the writer and the replica have different identities; HLC adds an approximately-synchronized physical-time component; ITC tracks it for a dynamically changing actor set with no metadata growth.

8.2 Clock update-rule state tables

Lamport scalar (state = ts: u64):

Event Precondition Transition Postcondition
Local event none ts := ts + 1 ts strictly increases
Send none attach current ts to message unchanged
Receive (r) none ts := max(ts, r) + 1 ts > r and ts > prior ts

Vector clock (state = V: Actor ⇀ u64, missing = 0):

Event Precondition Transition Postcondition
Local event on a none V[a] := V[a] + 1 V[a] strictly increases
Send none attach V (full snapshot) unchanged
Receive (V_msg) on a none V := entrywise_max(V, V_msg); V[a] += 1 V ≥ V_msg entrywise, V[a] strictly increases

Version vector / DVV (state = cc: VV, dots: {Dot}):

Event Precondition Transition Postcondition
Client read none client receives cc (causal context) —
Server write, client context cc_r cc_r dominated by or equal to server cc new dot (server_id, cc[server_id]+1); dots += {dot} dot uniquely identifies this write
Merge two DVVs none cc := max(cc1, cc2); dots := (dots1 ∪ dots2) \ covered_by(cc) I8 holds post-merge
Compact dots non-empty drop any dot with counter ≤ cc[actor] dots minimal

Hybrid Logical Clock (state = (wall: u64, logical: u32)):

Event Precondition Transition Postcondition
Local event pt := now() if pt > wall: (wall,logical) := (pt,0); else logical += 1 I1, I10 hold
Receive (m) pt := now(); nw := max(pt, wall, m.wall) four-way branch on which of wall/m.wall/pt equals nw (§16.2) nw ≥ wall, nw ≥ m.wall, I10 holds

Interval Tree Clock (state = (id: IdTree, event: EventTree)):

Event Precondition Transition Postcondition

event none increment event at the leaf id owns normal form (I11)
join two ITCs to merge recombine id trees; event := entrywise_max on trees normal form (I11)

8.3 Worked example: three actors, one DVV anomaly, one resolution

Actors A, B (clients), S (server holding a key). Initial state: S.cc = {S:5}.

  1. A reads: receives context {S:5}.
  2. B reads: receives context {S:5} (concurrently with step 1).
  3. A writes back with context {S:5} → server mints dot (S,6); S.dots = {(S,6)}, S.cc = {S:6} is not yet merged — the dot is held separately until compaction.
  4. B writes back with context {S:5} (unaware of A's write) → server mints dot (S,7); S.dots = {(S,6),(S,7)}.
  5. A reader now receives both dots as sibling values — the DVV-Set (§15.4) surfaced both concurrent writes instead of the plain-VV outcome (§8.4 below) where (S,7) silently dominates and overwrites (S,6).
  6. Resolution: the consumer's LWW policy (§21.2) picks the higher dot counter, or an OR-Set-style consumer keeps both as siblings for a manual merge.

8.4 Malformed-input examples

  • Non-canonical DVV: a dots set containing (S,4) while cc = {S:6} — the dot is already covered by the causal context (I8 violated). DvvSet::compact must reject or silently drop this on ingest, logging dvv_non_canonical_input_total.
  • Corrupt wire frame: a frame with type = 0x09 (undefined clock-type tag, valid range is 0x01–0x06, §19.1) — Frame::decode returns Err(FrameError::UnknownType(0x09)), never silently defaulting to Lamport.
  • Truncated frame: length field declares 40 bytes but only 12 remain in the buffer — Frame::decode returns Err(FrameError::Truncated { expected: 40, got: 12 }); the frame-fuzz target (clocks-fuzz/fuzz_targets/frame_decode.rs) exercises this specifically and must never panic (M16, §28).
  • Un-normalized ITC on the wire: Id::Node(Leaf(0), Leaf(0)) arrives instead of the normal-form Leaf(0) — the decoder normalizes on ingest rather than trusting the wire representation, per I11.
  • Backwards-jumping physical clock (HLC): PhysicalClockSource::now_ns() returns a value 2 seconds behind the previous call (NTP step adjustment) — Hlc::tick detects pt < prior_observed_pt and returns Err(SkewError::ClockRegression) rather than silently using the stale value (I10).

8.5 Failure-path example: crash mid-write during a partition heal

Topology: replicas R1, R2 partitioned for 10 minutes, each accumulating local vector- clock ticks. Partition heals; R1 sends its accumulated clock to R2. R2 begins atomic_write of the merged clock (tmp-file write, §18.2) and the process is killed (SIGKILL) after the tmp-file fsync but before the rename. On restart: R2's persistence layer (§18.5) finds the tmp file, verifies its checksum, and — because the rename never completed — discards it and falls back to the last-fsynced prior value (the pre-merge clock). R2 correctly reports MonotonicityError is not triggered (no partial value was ever exposed, I6 holds) but the merge from R1 is lost and must be re-delivered — the anti-entropy layer (Demers et al. 1987, referenced §2) is responsible for retry, not this library. This is the documented contract: persistence guarantees no corruption, not no data loss on unacknowledged crash — delivery guarantees are the caller's layer, matching the Repository/consumer boundary in §1.

11.1 The CausalClock trait — crates/clocks-core/src/causal_clock.rs

pub trait CausalClock: Sized + Clone {
    type Actor: ActorId;
    type Error;

    fn tick(&mut self, actor: Self::Actor);
    fn merge(&mut self, other: &Self);
    fn partial_cmp(&self, other: &Self) -> Option<core::cmp::Ordering>;
    fn concurrent_with(&self, other: &Self) -> bool;   // default: derived, I3
    fn serialize(&self, out: &mut Vec<u8>);
    fn deserialize(bytes: &[u8]) -> Result<Self, Self::Error>;
}

Ownership: value type, owned by caller. Mutation: &mut self only (single-writer, ADR-13). Concurrency: none provided — caller wraps in Mutex/actor-model. Persistence: via serialize/deserialize, not Clone. Serialization: scheme-specific binary (§19). Compatibility: Error associated type lets each scheme define its own decode-failure enum.

17. Phase 5 — Interval Tree Clocks

17.1 Objectives

Implement IntervalTreeClock (§11.7) to Almeida 2008 conformance: fork/event/join, normal-form invariant (I11) after every operation, and the bit-packed serialization (§17.4). Constraint introduced: no operation may leave a non-normalized tree observable outside the crate boundary.

17.2 Detailed Implementation Steps

Implement Id and Event recursive tree types (§11.7) in crates/clocks-itc/src/{id, event}.rs. Implement IntervalTreeClock::fork (Almeida 2008 §3: splits the id tree, both halves share the event tree — P1 §6, dynamic membership without metadata growth). Implement event (Almeida §4: increments the event tree leaf the id tree owns). Implement join (Almeida §3: recombines id trees, entry-wise-max on event trees). Implement normalize in crates/clocks-itc/src/normalize.rs applying the four Almeida §5 reduction rules after every operation (I11). Implement the bit-packed encoding (Almeida §7) in crates/clocks-itc/src/bitpack.rs: length-prefixed recursive bit layout, big-endian bit ordering within bytes (ADR-10). Wire examples/05_itc_fork_event_join.rs to walk the Almeida §6 example. Add itc.almeida_paper, itc.normal_form, itc.bitpack_roundtrip, differential.itc_c_reference buckets.

17.3 Deliverable

cargo run --example 05_itc_fork_event_join reproduces the Almeida 2008 §6 example exactly, printing both the Id and Event trees at each step in normal form.

17.4 Acceptance Criteria

fork/event/join agree with Almeida 2008 §6 worked examples bit-for-bit. Normalization is idempotent: normalize(normalize(x)) == normalize(x) on 100,000 random ITCs (I11). The bit-packed serialization round-trips (decode(encode(x)) == x) on 100,000 random ITCs, encoding to 5–20 bytes typical (§4). Differential test against the Almeida reference C implementation reports bit-identical outputs on 10,000 random operation sequences.

17.5 Conformance Fixtures

almeida_itc/section6_worked_example.json — the Almeida 2008 §6 trace. itc_normal_form/ 100k_random.seed — the idempotency proptest corpus. itc_malformed/non_normalized_ wire_input.json — an Id::Node(Leaf(0),Leaf(0)) arriving on the wire instead of Leaf(0), expecting the decoder to normalize on ingest (§8.4, I11). differential/ itc_c_reference/10k_random.seed.

17.6 Pitfalls

  • fork implemented as "allocate a new node" instead of Almeida §3's specific id-splitting recursion silently corrupts the partial order — this is the most common ITC bug (§8.2's fork transition table is the exact contract).
  • Skipping normalization after any single operation — an un-normalized ITC has multiple representations for the same logical value; equality and serialization determinism both break (I11).
  • Little-endian bit-packing (Almeida §7 specifies big-endian within bytes) — produces wire-incompatible output that round-trips with itself but not with any conformant peer.
  • Unbounded recursion depth in fork on a deeply-forked history — the Rust port must bound recursion explicitly (the C reference implementation does not, a documented pitfall not to copy, §5 Reference Implementations).

17.7 Performance Concerns

fork/event/join must hit M8/M9/M10 respectively (≤2 µs/≤1 µs/≤3 µs p50, §4). Cost is O(depth), not O(n_actors) (P1 §6) — the win over vector clocks for dynamic membership, at the cost of tree-depth growth under sustained fork/join churn (documented as a Phase-1+ re-balancing concern, out of scope here, §36).

17.8 Edge Cases

join of two ITCs whose id trees do not form a valid complementary pair (a programming-error input, not a wire input) — must return Err, not panic or silently produce an invalid tree. A freshly-seeded IntervalTreeClock::seed() forked 1,000 times in a row (extreme fan-out) — normal form must hold at every step; the depth grows but the byte size stays within the documented 5–20-byte typical range for realistic histories.

17.9 Failure Analysis

A normalization bug (I11) manifests as two logically-identical ITC values comparing unequal, breaking any content-addressed storage or deduplication built on top. Detection: the itc.normal_form conformance bucket (idempotency property test) at build time; no runtime detection exists because this is a pure logic defect. Blast radius: any consumer relying on ITC equality (e.g. an exactly-once check using ITC instead of DVV, §21.4). Containment: CI merge-block.

17.10 Operational Notes

No dedicated telemetry beyond the shared clock_monotonicity_violation_total (I1). The docs/architecture/itc.md file documents the fork/event/join operational model for operators onboarding a dynamic-membership deployment (actor churn) where vector clocks were previously the (wrong) choice.

18. Phase 6 — Persistence & Crash Recovery

18.1 Objectives

Implement clocks-storage (§11.8): the atomic_write primitive, ClockStore trait, and sled/RocksDB backends, satisfying the crash-recovery invariant I6 (P7 §6). Constraint introduced: every write must be atomic at clock-value granularity, verified by fault injection, not just code review.

18.2 Detailed Implementation Steps

Implement atomic_write (§11.8): write to a .tmp sibling file, fsync the data, rename (atomic on POSIX and via MoveFileEx on NTFS), then fsync the parent directory (the step Linux engineers learn about after their first power-loss incident — without it the rename itself can be lost on crash, I6). Implement ClockStore for sled (SledStore, ADR-06: pure-Rust, atomic per-key insert) and RocksDB (RocksStore, ADR-07, feature-gated: batches the clock-value write and metadata write in one WriteBatch with WriteOptions::set_sync(true)). Implement recovery.rs: on startup, read the latest clock value; on a backend-reported corruption (sled checksum failure, RocksDB compaction error), emit RecoveryError and refuse to start (never guess a value). Build the fault-injection harness (scripts/fault_inject.sh + libfaketime) that drives kill -9 mid-write across 10,000 trials.

18.3 Deliverable

clocks-storage round-trips every clock type (Lamport, VC, DVV, HLC, ITC) through both backends. The fault-injection harness runs 10,000 kill -9 trials against atomic_write with zero observed partial writes.

18.4 Acceptance Criteria

atomic_write survives kill -9 + power-loss simulation on 10,000 random writes with 0 partial writes observed (I6). The sled backend round-trips 100,000 random clock values across all five types. The RocksDB backend round-trips the same corpus. Recovery test: write 1,000 clocks, crash mid-write 10,000 times via fault injection; on restart the recovered clock is always one of the previously-fsynced values (never a corruption) — 100% pass rate required.

18.5 Conformance Fixtures

storage.atomic_write bucket — the 10,000-trial fault-injection corpus. storage. recovery bucket — the crash-mid-write-10,000-times corpus. storage_malformed/ truncated_sled_file.json — a deliberately truncated sled data file, expecting RecoveryError, not a silent empty-store start. storage_failure_path/tmpfs_no_fsync.md — documented (not automated) fixture: a tmpfs-backed store, expecting the operator runbook to flag "no durability" per §18.7.

18.6 Pitfalls

  • fsync on the data file alone is insufficient on Linux — the parent-directory fsync is required for the rename itself to be durable (I6, the single most common storage- engine bug in this domain).
  • tmpfs/overlayfs silently ignore fsync (no backing store) — document the real- filesystem requirement explicitly; a deployment on tmpfs has zero durability despite every fsync call "succeeding".
  • sled's flush is best-effort; only flush_async's completed future guarantees durability — calling insert and returning without awaiting flush ships silent corruption risk.
  • RocksDB's default WriteOptions do not fsync — set_sync(true) (ADR-07) is required for clock writes; the throughput cost is the price of the durability guarantee (§4 row 8).

18.7 Performance Concerns

sled persistence write latency must hit M13 (≤50 µs p50 / ≤200 µs p99 for a 16-byte clock, §4). The fsync cost dominates; batching multiple clock writes into one WriteBatch (RocksDB) amortizes this where the caller can tolerate slightly higher latency for higher throughput (a documented tradeoff, not a default).

18.8 Edge Cases

A crash during the parent-directory fsync itself (not just the data write) — recovery must tolerate finding both the old and new file present and pick deterministically (the rename's atomicity guarantee from the OS, not from this library, holds here). Disk full mid-write — atomic_write must return Err(io::Error) cleanly, never leave a half- written tmp file mistaken for a valid value on restart (recovery only trusts a file that passed through a completed rename).

18.9 Failure Analysis

Storage corruption (a checksum failure) manifests as RecoveryError on startup — this is the intended, safe failure mode (I6: refuse to start rather than serve a guessed value). Detection: process fails to start, alerting via standard process-supervision monitoring. Blast radius: the single store/replica; other replicas are unaffected (assuming they use independent storage). Recovery: restore from the most recent backup, replay the message log from the last known-good clock value (runbook docs/runbooks/clock-skew-incident.md, §10), then alert if the recovered clock is ever behind its previous on-disk value (a monotonicity violation, I1).

18.10 Operational Notes

storage_partial_write_detected_total (must stay 0, I6 telemetry) and storage_recovery_error_total are the primary alerts. Deployment topology requires a real filesystem (ext4/xfs/APFS/NTFS) — documented as a hard requirement, checked by a make preflight target that warns on tmpfs/overlayfs mounts. Backup/restore procedure is backend-specific (sled: directory copy while stopped or via its export API; RocksDB: checkpoint API) and documented per-backend in docs/architecture/.

19. Phase 7 — Wire Format & Framing

19.1 Objectives

Implement clocks-net's versioned binary Frame (§11.8) satisfying compatibility invariant I7: a 1-byte version prefix, type tag, varint length, type-specific payload. Constraint introduced: an unknown version must be rejected, never guessed or silently downgraded (P6 §6).

19.2 Detailed Implementation Steps

Implement the frame layout: ver(1B) | type(1B) | length(varint) | payload. type values 0x01–0x06 map to Lamport/VectorClock/VersionVector/DVV/HLC/ITC respectively (§8.4 malformed-input: 0x09 must reject, never default). Implement type-specific encodings (§11 annotations): Lamport as 8-byte big-endian; VectorClock/VersionVector as varint actor-count + sorted (actor_id, varint counter) pairs (ADR-03/04 ordering carries through to the wire); DVV as VectorClock-encoded cc + varint dot-count + dot pairs; HLC as 8+4+2-byte fixed fields; ITC via the Almeida §7 bit-packed form (§17.4). Implement Frame::decode's version-mismatch handling (P6): reject an unsupported version with FrameError::UnsupportedVersion, or — only if the operator opts into "tolerant" mode — attempt the prior codec and emit a frame_tolerant_decode_total metric. Wire the clocks-fuzz/fuzz_targets/frame_decode.rs fuzz target for a 24-hour canary (Phase 0 gate, M16 full 30-day gate at Sealed). Add net.frame_roundtrip, net.version_mismatch buckets.

19.3 Deliverable

The frame encoder/decoder round-trips every clock type through the wire format. The 24-hour fuzz canary (fuzz_targets/frame_decode.rs) completes with zero panics. docs/architecture/wire-format.md documents the format with byte-level worked examples.

19.4 Acceptance Criteria

The frame encoder/decoder round-trips on 100,000 random clocks of every type with 0 mismatches. The version-mismatch test rejects both v0 and v2 frames against a v1 decoder with the correct typed error (I7). The 24-hour fuzz canary (audits/fuzz/canary-24h-<sha>.md) reports 0 panics. Frame encode/decode throughput hits M11/M12 (≥1 GB/s for a 100-actor vector clock, §4).

19.5 Conformance Fixtures

net.frame_roundtrip bucket — 100,000-frame proptest corpus across all six types. net.version_mismatch bucket — crafted v0/v2 frames against the v1 decoder. net_ malformed/truncated_length.json — declared length exceeds remaining buffer (§8.4), expecting FrameError::Truncated. net_malformed/non_canonical_varint.json — a varint with a non-canonical leading-zero-byte encoding, expecting rejection (hash-collision risk if used as a content address, §19.6).

19.6 Pitfalls

  • Confusing LEB128's little-endian varint convention with the big-endian convention used for u32/u64/UUID actor IDs — mixing them ships a wire-incompatible format across otherwise-conformant implementations.
  • Treating length as the total frame length instead of the payload length — decoders computing "next frame offset" must add the header size, or every subsequent frame in a stream misparses.
  • Accepting non-canonical varint encodings (extra leading zero bytes) — breaks hash-based content addressing if the wire format is ever reused for that purpose (documented, not currently exercised, but a fuzz-target regression case per §19.5).

19.7 Performance Concerns

Frame encode/decode must hit M11/M12 (≥1 GB/s, §4) via zero-copy deserialization (the decoder borrows from the input buffer where possible, per ADR-05's rejection of Protobuf's reflection overhead) and pre-allocated output buffers (&mut Vec<u8> API, avoiding a per-call allocation on the hot encode path).

19.8 Edge Cases

A frame with length = 0 (an empty payload) — valid for no current clock type but must not panic the decoder; returns FrameError::EmptyPayload for a defined, typed clock. A frame exactly at the u32-varint boundary for length — varint encoding must handle the multi-byte case correctly, exercised by the fuzz target's boundary-value generator.

19.9 Failure Analysis

A frame-format bug manifests as a cross-version deployment silently misinterpreting clock values during a rolling upgrade — the worst-case failure in this entire project because it corrupts causality data without an immediate crash. Detection: net.version_mismatch conformance bucket at build time, plus frame_version_rejected_total in production (I7 telemetry). Blast radius: every message exchanged between mismatched-version nodes during the upgrade window. Recovery: halt the rolling upgrade, roll back the ahead nodes, re-validate via the differential suite before resuming (§26).

19.10 Operational Notes

frame_version_rejected_total and frame_tolerant_decode_total (if tolerant mode is enabled) are the primary dashboards. The Compatibility & Versioning section (§25) governs the rolling-upgrade procedure that depends on this phase's version-prefix guarantee (I7).

20. Phase 8 — Pruning & Garbage Collection

20.1 Objectives

Implement clocks-gc (§11.9): heartbeat-based actor-death detection, tombstones, threshold-based truncation, and DVV compaction, all subordinate to the safety invariant I9 (P4 §6: never evict an actor reachable from a causally-prior event). Constraint introduced: every pruning primitive must be opt-in and documented with its specific safety caveat — no "just works" default (P4).

20.2 Detailed Implementation Steps

Implement HeartbeatDetector<A> (§11.9): observe records Instant::now() per actor; dead() returns actors with now() - last_seen > timeout (ADR-19: heartbeat-timeout chosen over phi-accrual, Hayashibara et al. 2004, for primitive simplicity — phi-accrual layers on top if an operator needs it). Implement Tombstone<A> (§11.9): replaces a dead actor's vector-clock entry with a marker retained for a configured tombstone_ttl (Riak's pattern, Klophaus 2010 §6, default informed by vnode-handoff practice — operator- tunable, not hard-coded). Implement truncate_to_k_recent in crates/clocks-gc/src/threshold.rs (Dynamo DeCandia 2007 section 6.3 pattern): truncates to the k most-recent entries by counter value, documented "use only when actor population is bounded" (P3 §6). Implement the epoch mechanism (epoch.rs): a per-clock counter incremented on every prune, carried in the wire format (§19, additive field per §11.9) so a receiver can reject a clock with a stale epoch as "too old to merge safely" — a Phase-1+ extension layered on the tombstone-TTL baseline. Wire DvvSet::compact invocation into every sync call path (I8, cross-referencing §15).

20.3 Deliverable

HeartbeatDetector correctly identifies dead actors in a simulated fleet. Tombstoned entries preserve causal correctness during the TTL window in a simulated merge sequence. docs/architecture/pruning-policy.md documents the safety invariant and per-strategy tradeoffs.

20.4 Acceptance Criteria

HeartbeatDetector correctly identifies dead actors over 10,000 random heartbeat schedules with detection latency within 2× the configured timeout (ADR-19). truncate_to_k_recent agrees with Dynamo section 6.3 specification on published test vectors. Tombstones preserve causal correctness during the TTL window on 10,000 simulated merge sequences (I9), 0 safety violations. DvvSet::compact agrees with Riak's compaction behavior on 10,000 random sequences.

20.5 Conformance Fixtures

gc.tombstone_ttl bucket — 10,000-schedule proptest corpus, asserting I9 holds throughout the TTL window. gc.heartbeat_detector bucket — detection-latency proptest. gc_ malformed/prune_referenced_actor.json — a deliberately unsafe prune (evicting an actor still referenced by an in-flight event), expecting the safety-check layer to reject it, not silently proceed. gc_failure_path/ttl_shorter_than_message_delay.md — documented fixture: a message arriving after tombstone-TTL expiry, demonstrating the "lost update in disguise" failure mode operators must guard against via TTL configuration (§20.8).

20.6 Pitfalls

  • Tombstone TTL shorter than the maximum message-in-flight time — a late message arrives "after" the tombstone drops, its actor entry is treated as fresh, and a lost update results in disguise (the single most common pruning production incident, per the Riak and Dynamo operational literature, §5).
  • Truncation (truncate_to_k_recent) is unsafe in general — the Dynamo pattern works because the actor population (coordinator nodes) is bounded and known; an unbounded- actor deployment cannot safely truncate without a separate consistency mechanism (P3).
  • Skipping DvvSet::compact after a custom merge path — the set grows unboundedly even when the underlying value is stable (cross-referenced from §15.6, I8).
  • Pruning uncoordinated across replicas — if replica A prunes actor X but replica B does not, B's clock carries an entry A cannot interpret; the epoch mechanism (§20.2) handles this, but only if every replica participates.

20.7 Performance Concerns

HeartbeatDetector::dead() scans the full last_seen map — O(n_actors), acceptable at the documented actor-count ceiling (§4 row 11, 50,000) but a candidate for a min-heap-by- deadline optimization if that ceiling is exceeded (deferred, not required for Phase 8 acceptance). Tombstone storage adds a fixed per-pruned-actor overhead (actor ID + counter + epoch, ~24 bytes) that is strictly smaller than the entry it replaces.

20.8 Edge Cases

An actor that "dies" (heartbeat timeout) and then reappears within the tombstone TTL window — the tombstone's retained counter acts as the merge floor, so the reappearing actor's clock correctly merges without data loss (this is the TTL window's entire purpose). An actor reappearing after TTL expiry is, by design, treated as fresh — documented as the boundary condition operators must budget for via TTL sizing (§20.6). Simultaneous pruning decisions on two replicas for the same actor at different epochs — the epoch mechanism's "reject older epoch" rule resolves the conflict deterministically.

20.9 Failure Analysis

A safety-invariant (I9) violation manifests as a silently dropped update in a CRDT or key-value consumer — the single worst failure mode in this entire project because it is silent: no crash, no error, just a merge that quietly discarded causally-relevant history. Detection: pruning_safety_violation_total (must stay 0) and, forensically, a mismatch between an expected and observed CRDT state during an audit. Blast radius: every key/value touched by the prematurely-pruned actor. Recovery: manual — restore from backup, replay from the last-known-good clock value (runbook docs/runbooks/pruning-incident.md).

20.10 Operational Notes

pruning_safety_violation_total, tombstone_active_count, and actor_death_detected_ total are the primary dashboards. The runbook docs/runbooks/pruning-incident.md (§10) covers TTL-sizing guidance per deployment topology (WAN vs. LAN message-delay bounds). A Kubernetes-native clocks-gc sidecar for centralized fleet-wide pruning policy is deferred — PhaseDeferred("§20.10"), see the Deferred Features Register (§35).

21. Phase 9 — Public API, Integration & Performance Hardening

21.1 Objectives

Ship the top-level clocks facade crate re-exporting every sub-crate's public surface, the four consumer-integration recipes (CRDT, snapshot isolation, tracing, exactly-once), and the performance-hardening pass (SoA layout, SIMD comparison, lazy serialization) against the M1–M17 targets (§28). Constraint: hardening must not change any CausalClock contract (§11.1) — only internal representation.

21.2 Detailed Implementation Steps

Re-export clocks_core::{LamportTs, TotalOrder, CausalClock}, clocks_vector:: VectorClock, clocks_version::{VersionVector, DottedVersionVector, DvvSet, Dot}, clocks_hlc::{Hlc, PhysicalClockSource, NtpDisciplinedClockSource}, clocks_itc:: IntervalTreeClock, clocks_storage::{AtomicFile, SledBackend}, clocks_net::Frame, clocks_gc::{HeartbeatDetector, truncate_to_k_recent} from the clocks facade crate. Build examples/06_lww_register_over_vv.rs (LWW-register over VersionVector: (value, vv, tiebreak), dominant vv wins, (actor, ts) lexicographic tiebreak resolves ties, P10 §6). Build examples/07_orset_over_dvv.rs (OR-Set over DottedVersionVector: each element carries its add-dot; a remove carries the causal context that observed the add; remove succeeds iff its context dominates the add's dot — Shapiro et al. 2011 §3, applied here — PhaseDeferred("§21.2") covers the deeper Treedoc-style structured-clock variant, Preguiça-Marques-Shapiro-Letia 2009). Build examples/08_trace_causality.rs (HLC-tagged spans, parent/child inferred from HLC < order plus span-id reference). Build examples/09_exactly_once_delivery.rs (idempotency key + DVV; seen: DvvSet<MessageId>; a message dominated by an existing seen entry is a duplicate — PhaseDeferred("§21.2") covers the wait-free HLC-MVCC variant, Wang-Faleiro-Abadi 2017). Perform the Phase-10- equivalent hardening pass: benchmark BTreeMap vs. SoA (Vec<(ActorId,u64)>) vector-clock layout (ADR-03's documented crossover point); benchmark AVX2 SIMD comparison at n≥256; implement lazy/cached serialization (Cell<Option<Vec<u8>>>, invalidated on mutation) for static "observed up to here" snapshots sent repeatedly.

21.3 Deliverable

All four integration examples run and produce their documented expected output. clocks-bench reports every M1–M12 target (§28) met or exceeded on the CI reference runner. A 24-hour soak at 1M ticks/s shows zero memory growth (Phase-0 gate toward the 30-day Sealed gate, M17).

21.4 Acceptance Criteria

cargo run --example 06_lww_register_over_vv produces the documented LWW resolution on a 3-actor concurrent-write scenario. cargo run --example 07_orset_over_dvv produces the documented OR-Set state after an add-then-concurrent-remove sequence. cargo run --example 08_trace_causality reconstructs a distributed trace with 0 causality inversions. cargo run --example 09_exactly_once_delivery deduplicates 10,000 messages over a simulated flaky-network replay with 0 false negatives. clocks-bench meets all M1–M12 targets (§28) on the CI reference runner.

21.5 Conformance Fixtures

examples/06_lww_register_over_vv expected-output fixture: the higher-tiebreak write survives. examples/07_orset_over_dvv expected-output fixture: add-then-concurrent-remove yields the element present (remove's context did not dominate the concurrent add's dot). examples/08_trace_causality fixture: 0 inversions over 10,000 simulated cross-node spans. examples/09_exactly_once_delivery fixture: 10,000-message dedup corpus with injected redelivery.

21.6 Pitfalls

  • LWW tie-breaking by (actor, ts) is not equivalent to wall-clock LWW — document the tie-break policy at every call site; a caller expecting "most recent by wall time" will be surprised by an actor-ID tiebreak on true ties.
  • OR-Set removes must carry the causal context, not just the dot — storing only the dot loses the ability to correctly detect "add after remove" as a new, surviving add.
  • Distributed tracing causality via HLC works only within the max_offset bound (§16) — cross-region traces with >500 ms RTT and weak NTP discipline can still produce inversions; document the requirement rather than silently tolerating it.
  • The SoA layout (§21.2 hardening) has real overhead below n≈50 actors — always benchmark the crossover for the target deployment rather than assuming SIMD always wins.

21.7 Performance Concerns

The SoA vector-clock layout targets a 2–3× speedup over the BTreeMap baseline at n=1,000 actors; AVX2 SIMD comparison targets a further 2× on capable hosts (both measured, not asserted — recorded in benchmarks/results/, cross-referenced §28 M2–M4). Lazy serialization cache invalidation must be exercised by a property test ("serialized form after mutation always matches fresh serialization") to avoid the classic stale-cache bug class.

21.8 Edge Cases

A vector clock crossing the SoA/BTreeMap crossover threshold mid-lifetime (actor count growing past the documented crossover, §14.7) — the implementation picks the layout based on n_actors at construction/rehydration time, not per-operation, to avoid layout oscillation. A cached serialized form read concurrently with a mutation (single-writer contract, ADR-13, violated by caller error) — documented as undefined behavior at the caller's boundary, not a library-internal race (the library itself has no interior mutability beyond the documented Cell).

21.9 Failure Analysis

An integration-recipe bug (e.g. OR-Set remove not carrying causal context) manifests as a "resurrected" deleted element after a concurrent add/remove race — the CRDT-level equivalent of the DVV client-server anomaly (§15.2) one layer up the stack. Detection: the example fixtures' expected-output assertions (§21.5) at build time; in production, an operator notices via unexpected element counts in an OR-Set-backed feature. Blast radius: every OR-Set instance using the flawed recipe. Recovery: fix the recipe, replay from the DVV history (which remains correct — the bug is in the recipe layer, not the underlying clock, illustrating why P2's trait boundary matters).

21.10 Operational Notes

clocks-bench results feed the CI performance-regression gate (§27, §28); a benchmark regressing past its M-target by more than 10% fails the build. The four example recipes double as the primary onboarding documentation for new consumers integrating a CRDT, tracing, or exactly-once system on top of this toolkit — referenced from README.md (§10).

24. Operational Readiness

Metrics. Every telemetry name in §7 (I1–I14) and §22–§23 (T1–T12, FM-1–FM-12) is a Prometheus-style counter or gauge exported by the host process via a caller-supplied registry (the library never opens its own metrics port — deployment-model boundary, §1).

Tracing. Each CausalClock operation (tick/merge/partial_cmp) is instrumented with an optional tracing crate span (feature-gated traced, zero-cost when disabled) so a consumer's distributed trace (§21.3) can show clock operations inline with application spans.

Structured logging. All error paths (FrameError, SkewError, RecoveryError, StoreError) implement std::error::Error with a stable Display message referencing the owning invariant/ADR ID, so a log line is directly greppable back to this document.

Dashboards. Three tiers: (1) per-clock-type health (monotonicity, axiom violations — build-time only, never expected in production); (2) storage health (storage_recovery_ error_total, storage_partial_write_detected_total); (3) pruning/GC health (pruning_ safety_violation_total, dvv_set_size, vector_clock_actor_count).

Alerting philosophy. Alert on rate-of-change for gauges approaching a documented ceiling (§4) before the ceiling is hit (e.g. vector_clock_actor_count at 80% of 50,000), not only on hard-failure counters. Every "must stay 0" counter (I6, I8, I9 tables, §7) pages immediately on any nonzero observation.

SLOs. Persistence write p99 ≤ 200 µs (M13); zero corrupted reads across 10,000 simulated crashes (§4 row 17); zero pruning-safety violations, ever (I9) — this SLO has no error budget, unlike latency SLOs, because a violation is silent data loss.

Incident response. Named runbooks (§10 docs/runbooks/): triage.md (first 15 minutes), clock-skew-incident.md (HLC/storage recovery), pruning-incident.md (I9 violation response), conformance-failure.md (a CI conformance regression that reached production before the gate caught it — a process-failure postmortem template).

Backup/restore. sled: directory-level copy while stopped, or the export API for live backup; RocksDB: checkpoint API. Both documented per-backend in docs/architecture/.

Deployment topology. Linked library within each replica process; no separate clock service. Rolling upgrades follow the Compatibility & Versioning contract (§25); canary nodes run one minor version ahead with tolerant-mode decoding (T8) during the upgrade window, then strict mode resumes fleet-wide once the canary validates.

25. Compatibility & Versioning

Wire compatibility. Governed by the Frame version byte (I7, §19.1). A backward-incompatible payload change requires a major version bump; the decoder rejects unknown versions by default (strict mode) or falls back to the prior codec (tolerant mode, metered via frame_tolerant_decode_total) only when the operator opts in.

Storage compatibility. A clock persisted by version 0.3.0 must be readable by 0.4.0 (P6, §6) — enforced by a dedicated cross-version round-trip conformance bucket added whenever the wire format changes.

Schema evolution. New ActorId blanket impls (§11.2) are additive, never breaking. New clock types get a new Frame type tag (0x07+) — never reuse a retired tag.

API stability. The CausalClock trait (§11.1) is the frozen public contract post-1.0; adding a method requires a default implementation (backward-compatible) or a major version bump.

Migration. A wire-format major bump ships with a documented migration path (a converter binary or library function reading the old format and re-encoding the new) — required before the old version is dropped from the decoder's tolerant-mode fallback list.

Deprecation policy. A deprecated API surface carries a #[deprecated(since, note)] attribute for at least one minor version cycle before removal, referencing the replacement in the note.

SemVer policy. Strict SemVer: patch = bugfix, no API change; minor = additive, backward-compatible; major = breaking change to CausalClock, wire format, or storage format.

Rolling-upgrade guarantees. Any two adjacent minor versions can coexist in a fleet during a rolling upgrade, provided tolerant-mode decoding (T8) is enabled for the duration; strict mode is the steady-state default.

26. Testing & Verification Strategy

Unit tests. Per-module, colocated in each crate (crates/*/src/*.rs #[cfg(test)] blocks) — cover the state tables in §8.2 directly, one test per transition row.

Integration tests. tests/hello_causality.rs (Phase 0, §12.5) and the nine examples/*.rs binaries (§13–§21) double as integration tests, each asserting a documented expected output.

Property tests. proptest (ADR-16) drives every axiom in §7 (I1–I14) at the sample counts specified in each phase's N.4 (100K for most schemes, 10K for cross-crate scenarios).

Differential tests. Three shims (differential/{riak_dvv,cockroachdb_hlc, itc_c_reference}/) exercise a foreign reference implementation and assert bit-identical outputs against the Rust implementation (§15.4, §16.4, §17.4) — this is the check that catches representation-level bugs no single-language test suite can find (ADR-22). PhaseDeferred("§26") covers the Cassandra hybrid-timestamp differential, added only once a Cassandra-interop consumer is onboarded (see Deferred Features Register, §35).

Fuzzing. Six cargo-fuzz targets (clocks-fuzz/fuzz_targets/, §10) target the merge/ serialize paths of every scheme plus the frame decoder; a 24-hour canary gates every merge to main (M15-equivalent, Phase 0+), a 30-day canary gates the Sealed milestone (M16, §28).

Chaos / fault injection. scripts/fault_inject.sh drives kill -9 + libfaketime power-loss simulation against atomic_write (§18.4) — 10,000 trials, zero tolerated partial writes (I6).

Deterministic replay. The conformance simulator (§7 methodology) replays scripted actor topologies (fan-out, fan-in, partition-then-heal) with one assertion per invariant (I1–I14), giving bit-for-bit reproducible failure traces for debugging.

Soak testing. A 24-hour soak (Phase 9 gate, §21.3) and a 30-day soak at 1M ticks/s (Sealed gate, M17) both assert zero memory growth and zero panics.

Conformance. conformance/runner (§10) aggregates every paper-derived and production-differential bucket into conformance.report.json; the overall outcome is Pass iff every non-Deferred bucket passes (§14.5-pattern schema).

Performance-regression gating. clocks-bench (criterion) results are compared against the M1–M17 targets (§28) on every PR touching a hot-path crate; a regression past 10% of target fails the build (§21.10, §27).

Tie-back to invariants and fixtures. Every test class above maps to a named fixture in some phase's N.5 (§12.5–§21.5) and to an invariant in §7 — there is no test in this project without a traceable invariant it protects.

29. Scalability Analysis

What stays constant. Lamport (O(1) per clock, 8 bytes); HLC (O(1), 18 bytes) — both independent of n_actors by construction (P1, §6).

What grows, and the Big-O. Vector clocks and version vectors: O(n_actors) metadata size and merge cost (Charron-Bost 1991 tight lower bound, §4). DVVs: O(concurrent_ writers), not O(total_actors) — the dot set only grows with unresolved concurrency, not total history (§15). ITCs: O(log n_actors) typical via tree structure, O(depth) per operation, with depth growing under sustained fork/join churn absent periodic re-balancing (a documented Phase-1+ concern, §17.6).

Named bottlenecks in order. (1) Vector-clock merge cost at high n_actors without pruning (§4 row 1, FM-6) — the dominant bottleneck in any unpruned long-running deployment. (2) fsync latency on the persistence write path (M13) — dominant at high write rates on spinning disk, less so on NVMe. (3) DVV-Set size under sustained high- concurrency writes without compaction (FM-8). (4) Frame encode/decode allocation overhead at very high message rates absent the lazy-serialization cache (§21.2).

Horizontal/vertical scaling. This is a library, not a service — "scaling" here means scaling the number of actors/replicas a deployment can support, not scaling the library's own compute. Vertical: faster CPU/cache improves M1–M12 linearly; no vertical ceiling. Horizontal: adding replicas grows n_actors proportionally, which is exactly the axis bounded by §4 row 11 (50,000 actor ceiling, unpruned) — pruning (§20) is the horizontal- scaling lever.

Sharding/partitioning. Not applicable within a single clock value; a deployment shards by key (each key has its own DVV-Set, §15.4), and this project's contribution is that each shard's clock cost is independent of the others.

Coordination overhead. Zero built-in coordination (ADR-13: no consensus, no leader election) — the entire point is to detect causality without coordination; anti-entropy gossip (Demers et al. 1987) is the caller's chosen coordination-avoidance mechanism on top.

The practical ceiling and the levers beyond it. 50,000 actors unpruned (§4); beyond that, the levers are (in order of first resort): enable tombstone-TTL pruning (§20), migrate hot-path clocks from vector clocks to DVVs (bounds by concurrency, not actor count) or ITCs (bounds by log n), or migrate to HLC where concurrency detection is not required and only approximate physical-time ordering is needed (§30 has the full decision table).

30. Mental Models & First Principles

  • MM1 — A clock is a compressed representation of a partial order, not a duration. Predicts: any two clock values can only answer "before / after / concurrent", never "how much later". Bug class without it: computing a "latency" from a Lamport-timestamp difference — meaningless, since ticks accrue on every local event, not on wall time. Applied in §8.1, §14.
  • MM2 — Concurrent is not conflicting. (P10, §6) Predicts an application can have concurrent writes to disjoint state that never need resolution. Bug class without it: over-eager conflict resolution that merges/rejects non-conflicting concurrent writes, silently losing data the application never needed to reconcile. Applied in §6, §21.
  • MM3 — "Missing = zero" is a chosen convention, not a law of nature; violate it once and every downstream comparison is wrong. Predicts sparse, asymmetric actor sets compare correctly if and only if every accessor goes through get() (I5). Bug class without it: comparing raw maps with == instead of the union-of-keys partial_cmp. Applied in §8.2, §14.6.
  • MM4 — Metadata size is the tax paid for exactness; approximate schemes trade exactness for boundedness. Predicts why Bloom-clocks and ITCs exist at all — vector clocks are exact but O(n); the alternatives compress at the cost of introducing false positives (Bloom) or requiring a tree structure (ITC). Bug class without it: assuming vector clocks scale to unbounded actor counts "because they're correct". Applied in §4, §29, §34.
  • MM5 — HLC is a bridge between logical and physical time, not a replacement for either. Predicts HLC gives you a total order comparable to wall-clock time but not concurrency detection — it is Lamport-with-a-physical-anchor, not a vector clock. Bug class without it: assuming an HLC comparison tells you whether two events were concurrent (it cannot; only vector/DVV/ITC can). Applied in §16, §6 P11 (by analogy).
  • MM6 — Durability is a property of the write path (fsync ordering), not the storage engine's marketing claim. Predicts that the choice of sled vs. RocksDB matters far less than whether the parent-directory fsync happens at all. Bug class without it: trusting "we use a database" as a durability argument without checking the fsync contract. Applied in §18, T6/FM-7.
  • MM7 — Pruning safety is a global invariant enforced by cheap local primitives (tombstone + epoch), never by omniscience. Predicts why GC here is opt-in with operator-supplied policy rather than an automatic language-runtime-style collector. Bug class without it: assuming clock GC "just works" like a GC'd language's heap — it cannot, because the safety invariant needs deployment-topology knowledge no local process has. Applied in §20, P4 (§6).
  • MM8 — A trait is a promise about behavioral consistency, not just a method signature; deriving concurrent_with from partial_cmp keeps that promise from drifting. Predicts any override of the derived method is a latent I3 violation waiting for a differential test to catch it. Bug class without it: two "obviously equivalent" implementations of concurrency-checking silently diverging over time as one is optimized and the other isn't. Applied in §11.1, §7.

Riak chose dotted version vectors specifically to fix the client-server VV anomaly (§15.2) in its 2.0 release after two years running plain VVs in 1.x — the one decision it made differently from a naive VV design, and the niche where it wins is exactly the replicated-KV-with-many-clients topology this project's DVV design also targets (§30 MM context: same problem, same fix, independently validated in production).

CockroachDB chose HLC over vector clocks entirely, accepting the loss of concurrency detection in exchange for a fixed-size, wall-clock-comparable timestamp on every transaction — it wins in the distributed-SQL regime where snapshot isolation via MVCC needs a total order more than it needs explicit concurrency detection, exactly the tradeoff formalized in P1 (§6).

DynamoDB chose version vectors with aggressive truncation (10 most-recent entries, DeCandia 2007 section 6.3) — an explicitly unsafe-in-general choice that Dynamo accepts because its actor population (coordinator nodes) is small and well-known, the exact caveat this project's truncate_to_k_recent (§20.2) documents rather than hides.

Spanner rejected logical clocks entirely in favor of TrueTime — bounded-error physical time backed by GPS and atomic clocks in every datacenter — winning on external consistency (linearizable cross-region transactions) at the cost of a hardware dependency this project's library-only deployment model (§1) explicitly cannot assume.

32. Back-of-Envelope Capacity Model

  1. Unpruned vector-clock heap at the documented ceiling. 50,000 actors × (16 B UUID + 8 B counter) × 1.6 BTreeMap overhead factor = 50,000 × 24 B × 1.6 ≈ 1.92 MB per clock value at the worst-case actor count (chained from §4 row 1's n=10,000 → 400 KB baseline: 10,000 × 24 B × 1.6 ≈ 384 KB ≈ 400 KB, confirming the multiplier).
  2. Frame throughput in frames/sec. A 100-actor vector-clock frame is 4 B header + 1 B varint count + 100 × (4 B actor_id + ~1–2 B varint counter) ≈ 505 B. At M11's ≥1 GB/s target: 1×10⁹ B/s ÷ 505 B/frame ≈ 1.98 M frames/sec sustainable encode/decode rate.
  3. RAM for 1,000,000 open HLC-tagged keys. 1,000,000 × 18 B (Hlc fixed width, §4) = 18 MB — the entire live-key HLC working set for a million-key shard.
  4. File-descriptor budget across a 100-shard node. 32 FDs/store (§4 row 12) × 100 shards = 3,200 FDs, comfortably under a typical 65,536 ulimit -n.
  5. Synchronous single-writer persistence ceiling. 1 ÷ 50 µs (M13 p50) = 20,000 writes/sec per unbatched synchronous writer — the number that forces batching (WriteBatch, ADR-07) once sustained write rate exceeds it.
  6. HLC cluster-size ceiling. node_id: u16 → 2¹⁶ = 65,536 maximum addressable nodes (§11.6 annotation) — a hard ceiling from the wire-format field width, not a soft estimate.
  7. Counter headroom at the 30-day soak rate. 1,000,000 ticks/s × 86,400 s/day × 30 days ≈ 2.59×10¹² ticks consumed of a u64's 2⁶⁴ ≈ 1.84×10¹⁹ capacity — ≈ 1.4×10⁻⁷ of the counter space, confirming ADR-08's "585 years at 1/ns" claim is conservative even under the Sealed-gate soak load.
  8. Heartbeat ingestion rate at the actor ceiling. With timeout T = 30 s and a heartbeat interval of T/10 = 3 s (standard failure-detector practice) across 50,000 actors: 50,000 ÷ 3 s ≈ 16,667 heartbeats/sec sustained ingestion the HeartbeatDetector (§20.2) must handle.
  9. Worst-case storage amplification per day (illustrative upper bound). 1,000,000 ticks/s × 86,400 s × 24 B (10-actor clock) × 3× amplification (§4 row 15) ≈ 6.22 TB/ day if every tick were persisted synchronously and unbatched — the number that makes the case for snapshotting/batching rather than per-tick fsync in any real deployment.
  10. DVV dot-set bound under realistic concurrency. For 10–100 concurrent writers to one key within one anti-entropy round: dot-set size ≈ 10–100 × 9 B (Dot encoding) = 90 B – 900 B — three to four orders of magnitude below the unpruned vector-clock ceiling (item 1), the quantified case for DVV's O(concurrent writers) bound over O(total actors) (§29).

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Single global sequencer (total-order broadcast), no per-actor clocks.

  writer1 ─┐
  writer2 ─┼──▶ [ leader / sequencer ] ──▶ single monotonic log ──▶ all readers
  writer3 ─┘

Regime where it wins: every write already routes through one leader (a consensus-backed system paying that cost anyway) and only a monotonic offset is needed, not multi-writer causality. Real system: a single-partition Kafka topic (the partition leader assigns offsets). Rejected here because this project's target deployments are decentralized and partition-tolerant (AP-leaning, §1) — a leader dependency is exactly the coordination overhead the whole toolkit exists to avoid (§29 "coordination overhead" row).

Alternative 2 — Bloom-Clock approximate causality (no exact vector).

  event ──▶ [ Bloom filter over observed actor IDs ] ──▶ compact, lossy "may-have-seen" set

Regime where it wins: extremely large, highly dynamic actor populations where an occasional false positive ("may have happened-before" when actually concurrent) is tolerable and boundedness matters more than exactness. Real system: the schemes described in Ramabaja 2019 and Tomar 2022 (research prototypes, not yet a production deployment at the scale of Riak/CockroachDB). Rejected here because P14 (§6) makes bit-for-bit conformance the contract — a false positive is an I2/I3 violation by definition, which this project's differential-testing mandate (ADR-22) cannot tolerate; tracked as a deferred stretch (PhaseDeferred("§34"), Deferred Features Register §35).

Alternative 3 — TrueTime-style bounded physical clocks, no logical clock at all.

  [ GPS + atomic clock ensemble per datacenter ] ──▶ [ε]-bounded timestamp ──▶
      commit-wait until ε elapses ──▶ externally consistent order

Regime where it wins: the deployment already has GPS/atomic-clock hardware in every datacenter and needs externally consistent, linearizable cross-region transactions, not merely causal order. Real system: Spanner (Corbett et al. 2012, OSDI). Rejected here permanently (not deferred, §1) because it requires infrastructure investment (dedicated timekeeping hardware) outside a library's scope — the exact non-goal boundary in §1.

Alternative 4 — Single-writer-per-key log, no concurrent-write detection needed.

  all writers ──▶ [ single primary for key K ] ──▶ append-only log ──▶ replicas (read-only)

Regime where it wins: the deployment can tolerate a single point of write serialization per key (true multi-master is not required) and never needs concurrent-write conflict detection because there is structurally only one writer at a time. Real system: a traditional primary-replica RDBMS (e.g. PostgreSQL streaming replication). Rejected here because this project explicitly targets multi-writer, partition-tolerant deployments where a single primary is unavailable during a network partition — precisely the problem vector clocks and DVVs exist to solve (§1 deployment model, §15).

36. Glossary

  • Happens-before (→) — the causal partial order generated by program order and send/receive (Lamport 1978 §2).
  • Concurrent (∥) — two events where neither happens-before the other.
  • Partial order — an order relation admitting incomparable pairs.
  • Total order — an order relation where every pair is comparable.
  • Lamport timestamp — a scalar logical clock giving a total order consistent with →.
  • Vector clock — a per-actor counter vector giving exact →/∥ detection (Fidge 1988, Mattern 1989).
  • Version vector — a vector clock applied to per-replica update tracking (Parker 1983).
  • Dotted Version Vector (DVV) — a version vector plus a dot set, fixing the client-server anomaly (Preguiça 2010/2012).
  • Dot — an (actor, counter) pair uniquely identifying one write event.
  • Causal context (cc) — the "observed as of this write" version vector inside a DVV.
  • Hybrid Logical Clock (HLC) — a (physical, logical) pair clock with bounded skew (Kulkarni et al. 2014).
  • Interval Tree Clock (ITC) — a fork/event/join clock for dynamic actor membership (Almeida, Baquero, Fonte 2008).
  • Actor — the identity unit that ticks a clock (an ActorId).
  • Fidge-Mattern theorem — V_a ≤ V_b entry-wise iff a → b.
  • Charron-Bost lower bound — any exact partial-order-detecting clock needs ≥n integers for n actors (Charron-Bost 1991).
  • Merge — combining two clock values (entry-wise max for VC/VV; union+compact for DVV; four-branch max for HLC; tree recombination for ITC).
  • Tick — advancing a clock to record a local event.
  • Monotonicity — a clock's per-actor value never decreases across events (I1).
  • Bounded skew — HLC's physical component never diverges from the local wall clock by more than max_offset (I10).
  • max_offset — the configurable HLC skew bound (ADR-21, default 500 ms).
  • Tombstone — a marker retained after pruning an actor's clock entry (§20.3).
  • Epoch — a per-clock counter incremented on every prune, used to reject stale clocks (§20.2).
  • Truncation — pruning to the k most-recent entries by counter value (Dynamo pattern, DeCandia 2007 section 6.3).
  • Client-server VV anomaly — a lost write under concurrent client writes through a plain version vector (Preguiça 2012 §2).
  • Anti-entropy — gossip-based state reconciliation requiring version vectors (Demers et al. 1987).
  • CRDT — Conflict-free Replicated Data Type.
  • LWW-register — Last-Writer-Wins register CRDT.
  • OR-Set — Observed-Remove Set CRDT.
  • RGA — Replicated Growable Array CRDT (ordered-sequence CRDT).
  • Snapshot isolation — an MVCC-based read-consistency model.
  • Exactly-once delivery — an idempotent message-processing guarantee.
  • Wire frame — the versioned binary envelope wrapping a serialized clock value (§11.8).
  • Varint — a variable-length integer encoding (LEB128).
  • fsync — the syscall forcing a durable write of data (and, separately, directory metadata) to disk.
  • Atomic write — the write-fsync-rename-fsync pattern guaranteeing no partially- written value is ever observable (I6).
  • Normal form (ITC) — the canonical, reduced tree representation an ITC value must be in before serialization (I11).
  • Bit-packed encoding — Almeida §7's compact binary ITC serialization.
  • Conformance suite — the paper-derived and production-differential test harness (conformance/, §10, §26).
  • Differential testing — cross-implementation behavioral comparison against a foreign reference implementation (§26, ADR-22).
  • Phi-accrual failure detector — a probabilistic liveness detector (Hayashibara et al. 2004), a layered stretch over the heartbeat-timeout primitive (ADR-19).
  • TrueTime — Spanner's bounded-error physical clock (Corbett et al. 2012), rejected as a permanent non-goal here (§1, §34).
  • NTP / PTP — Network Time Protocol (RFC 5905) / Precision Time Protocol (IEEE 1588-2019), the physical-clock synchronization sources HLC depends on.
  • Actor-death detection — the heartbeat-timeout mechanism marking an actor presumed dead for pruning purposes (§20.2).
  • Safety invariant (pruning) — the rule that no actor entry may be evicted while still reachable from a causally-prior event (I9).
