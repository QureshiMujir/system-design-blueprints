⬜ Phase 0 — Skeleton + Correctness Kernel §12

Objectives

Stand up the workspace, licensing, CI skeleton, and the smallest vertical slice that proves the data model round-trips: register a Counter, expose it, scrape it, ingest it, and see the value come back. This is the "correctness kernel" required by §7: no query language yet, just identity and durability.

Deliverable

A binary that: registers http_requests_total, increments it, serves /metrics, parses its own output back into Samples, and asserts round-trip equality — runnable via make bootstrap && make test.

Acceptance

Round-trip test passes for ≥ 3 fixture families (counter, gauge, histogram). cargo-deny reports zero license violations. CI green on ci.yml. Fixture conformance/corpora/exposition/ smoke_roundtrip.txt byte-identical after parse→write→parse.

Fixtures
Fixture Purpose Expected Output
smoke_roundtrip.txt counter/gauge/histogram round-trip byte-identical re-serialization
malformed_missing_brace.txt parser error path (§8.4) parse_errors_total{reason="unterminated_label_block"} incremented, no panic
duplicate_labels.txt canonicalization (P1) last-write-wins label survives, single series ID
Pitfalls

Shipping the PromQL parser before the data model is the classic misordering — resist (the data model is P1/I1, load-bearing for everything downstream). cargo-deny will flag an unpinned license; pin at Phase 0 rather than later. A Vec-backed head with no WAL is a Phase-0-only stopgap — do not let it leak into Phase 4's design.

⬜ Phase 1 — Data Model + Exposition Format §13

Objectives

Complete the four metric types and both exposition dialects to conformance-corpus-grade correctness (P1, P3-adjacent — PromQL will consume this data model unchanged).

Deliverable

tempora-exposition crate passing the Prometheus official parser test corpus at 100%, both text and OpenMetrics dialects, with a documented throughput benchmark.

Acceptance

Parser throughput ≥ 500 MB/s single-core (M4, §30). 100% pass on conformance/corpora/exposition/ and corpora/openmetrics/ (named fixture sets). Zero panics across the exposition_parse fuzz target after a 1-hour corpus run.

Fixtures
Fixture Purpose Expected Output
escaped_label_values.txt \", \n, \\ escaping exact byte round-trip
openmetrics_exemplar.txt exemplar suffix parsing exemplar trace_id captured, sample value unaffected
stale_marker.txt NaN convention (I11) decoder marks series ended, does not error
prometheus_official_corpus/* upstream parser test suite 100% pass rate
Pitfalls

Label-value escaping edge cases are easy to get subtly wrong — the corpus, not intuition, is the oracle (I8-adjacent determinism). OpenMetrics exemplars are the load-bearing extension Prometheus's own parser doesn't require — support it anyway since it's in scope. The stale-marker NaN (I11) must use the exact reserved bit pattern, not "any NaN," or reset-vs-stale ambiguity corrupts rate (§20.6).

⬜ Phase 2 — Client Library + Instrumentation §14

Objectives

Deliver tempora-client as a production-grade instrumentation library: lock-free where possible (P1, Gjengset ch. 6), with a client-side cardinality guard (P5) so a single misused label doesn't crash the producer either.

Deliverable

A /metrics HTTP handler serving all four types at the target throughput, with the client-side cap verifiably rejecting the 10,001st distinct label combination for one metric.

Acceptance

/metrics endpoint serves ≥ 100,000 samples/sec/core (M5, §30). A counter incremented 1,000,000 times serially reports exactly 1,000,000. The 10,001st new label combination for one metric is rejected and counted, not silently dropped without telemetry.

Fixtures
Fixture Purpose Expected Output
histogram_overflow_bucket.txt value larger than largest le still counted in _count/_sum
cardinality_cap_10001.rs (test) client-side cap (P5/I6) 10,001st combination dropped + counted
concurrent_inc_1e6.rs (test) atomic correctness under contention final value exactly 1,000,000
Pitfalls

A LabelSet construction that allocates per call is the canonical perf bug — cache the canonicalized form per (name, labels) pair (§13.7 pattern reused here). Counter::reset() does not exist by design — counters are monotonic; a process restart is detected downstream by rate() (§20.6), not here. A Histogram::observe for v above the largest bucket must still land in _count/_sum — easy to forget.

⬜ Phase 3 — Service Discovery + Scrape Pipeline §15

Objectives

Deliver target discovery (static/file/DNS/K8s) and the scrape loop against 10⁴ targets at 15 s intervals without herd effects (P4, §4).

Deliverable

A scraper that discovers targets via FileSd, applies a hashmod-based shard relabel rule, and completes a 10,000-target scrape cycle within the 15 s interval.

Acceptance

10,000-target scrape completes within its 15 s interval budget (M6, §30). Stale-marking verified for a target whose series set shrinks between scrapes. Relabel drop-all-targets misconfiguration is detectable via tempora_active_targets dropping to zero (not just silently empty).

Fixtures
Fixture Purpose Expected Output
relabel_hashmod_shard.yaml sharding via hashmod (§15.2) replica N sees only hash%N==shard_id targets
relabel_drop_all.yaml operator misconfiguration tempora_active_targets=0, warning logged
scrape_body_too_large.txt body-size-limit enforcement scrape dropped + scrape_failed_total{reason="body_too_large"}
Pitfalls

Missing scrape jitter causes every target to be hit at second boundaries, spiking network usage (P4-adjacent — the jitter is not optional). The relabel DSL has dozens of corner cases across seven actions — the conformance corpus, not intuition, is the oracle (I8 determinism pattern reused). __tmp_* labels are convention for intermediate relabel state; final rulesets must drop them.

⬜ Phase 4 — TSDB Head Block + Write-Ahead Log §16

Objectives

Build the crash-safe append path: head block (P7, queryable while appending) plus WAL (P8, ARIES- style durability, applied per §5).

Deliverable

A Tsdb::append path that survives a kill -9 mid-write: on restart, replay recovers every fsynced sample and cleanly truncates at the first corrupt record.

Acceptance

Ingest ≥ 1,000,000 samples/sec/node (M1, §4). WAL replay of 100 GB completes in < 60 s (M2, §4). Head queries return an appended sample within 1 ms of append (M3). Crash-injection test (kill -9 at 50 random points during a fixed workload) recovers with zero panics and a deterministic truncation point each run.

Fixtures
Fixture Purpose Expected Output
wal_crc_mismatch.bin corrupted trailing record (§8.5) replay truncates at bad record, wal_truncated_replay_total incremented
checkpoint_interrupted.bin crash mid-checkpoint rename previous checkpoint remains valid (atomic rename, I4)
1e8_sample_replay.bin replay throughput (M2) < 60 s wall time
Pitfalls

The fsync-every-batch vs fsync-every-N-batches tradeoff (P8) is configurable, default 100 ms — document the RPO consequence explicitly, don't bury it. Head memory is proportional to series count × samples/series; the cardinality cap (§14, I6) bounds the first factor, hourly chunk rotation bounds the second. A checkpoint is published via atomic rename — an interrupted checkpoint must leave the prior one intact (I4). A new series created mid-compaction must land in the next checkpoint — the compactor is single-writer to preserve this ordering (I5).

⬜ Phase 5 — Gorilla Chunk Encoding §17

Objectives

Implement the Facebook Gorilla compression scheme (Pelkonen et al. 2015, applied here per §5 and ADR-04) for the in-progress and sealed chunk formats, hitting the ~11.4× compression target from §4.

Deliverable

tempora-tsdb::chunk::gorilla encode/decode pair achieving the target ratio on a representative 15 s-interval fixture set, decodable only forward (random access requires decode-from-chunk-start, documented as a known cost — see §17.7).

Acceptance

Encode ≥ 10,000,000 samples/sec/core; decode ≥ 10,000,000 samples/sec/core (M7, §30). Compression ratio ≥ 1.5 bytes/sample on the typical_scrape_15s.fixture corpus (target from Pelkonen 2015's 1.37 B/sample measurement, ADR-04).

Fixtures
Fixture Purpose Expected Output
typical_scrape_15s.fixture ratio benchmark ≤ 1.5 bytes/sample average
constant_value_series.fixture XOR-zero fast path ~1 bit/sample after the first value
nanosecond_precision_ts.fixture compression-killer case (§17.9) ratio degrades gracefully, no correctness loss
stale_marker_mid_chunk.fixture I11 encoding decoder yields NaN, resumes correctly after
Pitfalls

The variable-length DoD codes are easy to get off-by-one on prefix-bit counts — the conformance corpus (not manual derivation) is the oracle (I8 pattern). NaN stale markers need the dedicated full-format encode path, not the common-case XOR path. The chunk format is on-disk-stable (I4) — never change it without a ChunkHeader.version bump and a migration note (§27).

⬜ Phase 6 — Chunk Persistence + Inverted Index + Compaction §18

Objectives

Move sealed chunks to disk, build the label→series inverted index, and run background compaction (hourly WAL→chunk, daily small→large) without blocking the append path (P7, I5).

Deliverable

A background compactor that runs concurrently with live ingest, publishing hourly chunks that pass the I5 sample-count invariant check, plus a daily merge job and a retention GC pass.

Acceptance

Hourly compaction completes within 50% of the hour budget (M8, §4/§30). A 30-day range query against cold-tier chunks completes p99 < 30 s (§4). I5 sample-count assertion never fails across a 1-hour soak of continuous ingest + compaction.

Fixtures
Fixture Purpose Expected Output
compaction_sample_count_invariant.rs (test) I5 pre == post sample count across 100 compaction cycles
daily_merge_small_chunks.fixture small→large merge merged chunk's index resolves every constituent series
retention_boundary_gc.fixture I9 only fully-expired chunks deleted, no partial-range deletion
cold_tier_fetch_timeout.fixture object-store slow path bounded retry, no query-thread block beyond timeout
Pitfalls

mmap'd chunk reads are page-fault-bound on first access — pre-warming the cache is a real perf knob, not a nice-to-have (§17.7-adjacent). Cold-tier fetches are second-scale — cache aggressively or the 30 s p99 (§4) is unreachable. A compaction that overruns its hour is the canonical "falling behind" incident (§26 runbook compaction-stuck.md). Symbol-table dedup is per-chunk-file only; cross-chunk dedup is PhaseDeferred("§37").

⬜ Phase 7 — PromQL Lexer + Parser + AST §19

Objectives

Build the PromQL front end: lexer, Pratt operator-precedence parser, typed AST with source spans (P3, P14), passing the Prometheus PromQL parser test corpus at 100%.

Deliverable

tempora-promql::{lexer,parser,ast} parsing the full Prometheus PromQL grammar including subqueries, with error messages that cite the offending byte range.

Acceptance

100% pass on the Prometheus PromQL parser test corpus (M9, §30). Every parse error identifies a SourceSpan resolvable to the offending substring (no "parse error" with no location).

Fixtures
Fixture Purpose Expected Output
prometheus_promql_parser_corpus/* upstream grammar coverage 100% pass
subquery_nested.promql expr[30m:1m] nesting correct AST shape, resolvable span
regex_matcher_go_flavor.promql =~/!~ Go-regex semantics matches Prometheus's regex engine behavior
unterminated_paren.promql malformed input typed parse error with span, no panic
Pitfalls

The =~/!~ matcher operators use Go-flavored regex syntax — transcribe the dialect precisely, do not substitute Rust's default regex crate semantics unchecked (subtle class/anchor differences). Subqueries are a comparatively recent PromQL addition — easy to under-test; the corpus fixture above is the guard.

⬜ Phase 8 — PromQL Evaluator + Function Library §20

Objectives

Implement the recursive AST evaluator: instant/range vector resolution, the ~50-function library, vector matching, and range-query stitching (P13 determinism is the acceptance bar throughout).

Deliverable

tempora-promql::eval passing the Prometheus PromQL evaluator conformance corpus, with rate() and histogram_quantile() verified against hand-computed reference values.

Acceptance

≥ 99% pass rate on the Prometheus PromQL evaluator test corpus vs the reference implementation (M10, §30). A 24-hour rate(http_requests_total[5m]) query over 1,000,000 series completes in < 30 s (M11, derived from Capacity Model CM8, §34). A query requesting more than max_resolution_points (11,000 default) is rejected with a typed error, not truncated silently.

Fixtures
Fixture Purpose Expected Output
prometheus_promql_eval_corpus/* upstream evaluator coverage ≥ 99% pass vs reference
rate_counter_reset.fixture reset detection (§20.2) rate treats decrease as reset, no negative rate
histogram_quantile_10bucket.fixture interpolation accuracy within documented ~10% error bound (factor-of-2 spacing)
vector_matching_group_left.fixture many-to-one matching extra labels from the "many" side propagate correctly
max_resolution_exceeded.promql resolution-limit rejection typed error, not truncated silent result
Pitfalls

The rate() boundary case — last sample of one range vs first sample of the next — is the canonical bug source; the corpus, not intuition, is the oracle (I8). histogram_quantile requires strictly cumulative le-ordered buckets (ADR-24); a non-cumulative input returns NaN, not a wrong number. label_replace with a non-matching regex is a documented no-op — this surprises users enough to warrant an explicit note in docs/api/.

⬜ Phase 9 — Rule Engine + Alertmanager Integration §21

Objectives

Deliver the periodic rule evaluator (I10: strictly sequential within a group) for recording and alerting rules, independent of the user-query path (ADR-20).

Deliverable

A rule engine running 1,000 rules across multiple groups every 15 s, with a recording rule's output queryable as an ordinary series and an alerting rule correctly transiting its for-duration state machine.

Acceptance

1,000 rules evaluated every 15 s within the interval budget (M12, §30). Alert for-duration state survives a simulated rule-engine restart (I14 test) with the correct pending timer resumed, not reset to zero. A recording rule whose name collides with an existing scraped series is flagged by a linter, not silently overwritten.

Fixtures
Fixture Purpose Expected Output
rule_group_sequential.fixture I10 rule 2 sees rule 1's writeback within the same evaluation
alert_for_duration_fsm.fixture state machine transitions (§21.2) exact Inactive→Pending→Firing→Resolved sequence
alert_state_restart_recovery.fixture I14 pending timer resumes correctly after simulated crash
recording_rule_name_collision.fixture linter check collision flagged, not silently overwritten
Pitfalls

A rule whose expression takes longer than the group's evaluation interval is the canonical degradation — the runbook (§26) documents the diagnostic (tempora_rule_group_duration_seconds exceeding the interval). The for-duration state is keyed by (alert name, label set) — a rule label-set change effectively resets tracked state; document this explicitly (I14 caveat). An alerting rule whose label set explodes in cardinality creates a proportional number of state machines — cross-reference §23's cardinality defense.

⬜ Phase 10 — HTTP API + Federation + Remote Write/Read §22

Objectives

Expose the Prometheus-compatible HTTP surface (P10) — query, series/labels metadata, federation, and remote-write/read — so Grafana and hierarchical Prometheus deployments interoperate unchanged.

Deliverable

A running instance that Grafana renders dashboards against unmodified, that a hierarchical Prometheus federates from, and that accepts remote-write from an upstream Prometheus.

Acceptance

query_range p99 < 5 s for a 24 h window (M6, §4). Remote-write ingest sustains the per-node ceiling (M1) under Snappy-compressed load. Federation response for a 100,000-series match set streams without unbounded memory growth (bounded by a documented per-response cap).

Fixtures
Fixture Purpose Expected Output
api_v1_query_envelope.fixture JSON envelope shape (P10) byte-compatible with Prometheus's schema
federate_match_selector.fixture ADR-22 pull semantics most-recent-value-only per series
remote_write_snappy_corpus/* wire compatibility 100% decode success
remote_write_429_backpressure.fixture rate-limit signal client observes 429, server does not OOM
Pitfalls

The Prometheus HTTP API has cross-version drift — pin the exact version targeted and track it in docs/api/. Federation's most-recent-value-only semantic means multi-sample series do not federate — a documented limitation, not a bug (ADR-22). A remote-write client sending faster than the server accepts must be back-pressured via 429, never silently dropped without signal.

⬜ Phase 11 — Cardinality Defense + Multi-Tenancy + Hardening §23

Objectives

Close the loop on P5/P9/I6/I7: enforce cardinality caps end-to-end, isolate tenants at the storage layer, and run the conformance/perf/soak hardening pass that gates a release.

Deliverable

A multi-tenant instance where tenant A's cardinality explosion (driven to the cap) measurably does not raise tenant B's query p99 beyond its normal budget, plus a clean 30-day soak report.

Acceptance

Cardinality cap enforces at exactly the configured threshold (default 10,000/tenant/metric, verified by a fixture driving to 10,001). Tenant B's query p99 stays within its §4 budget while tenant A is at its cardinality cap (isolation test). 30-day soak: zero crashes, zero panics, tempora_wal_truncated_replay_total unchanged from baseline.

Fixtures
Fixture Purpose Expected Output
cardinality_cap_server_side.fixture I6 server enforcement 10,001st series dropped + counted, existing untouched
tenant_isolation_query_latency.fixture I7 isolation tenant B p99 unaffected by tenant A at cap
forged_tenant_header.fixture T-8 threat (§24) rejected when auth token required, accepted only via token path
soak_30day_report.fixture hardening gate zero crash/panic count over the run
Pitfalls

A misconfigured cap (set too low) is the canonical "I lost my data" incident — distinguishable from a real cardinality attack only by checking whether the dropped combinations are legitimate (runbook cardinality-explosion.md, §26). The X-Tempora-Tenant header is forgeable in an untrusted network — never rely on it alone in production (auth tokens are the gate, T-8 §24).
