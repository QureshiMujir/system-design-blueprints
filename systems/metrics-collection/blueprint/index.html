Project Number: 133

Project Name: Metrics Collection + Query

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Build a Prometheus-compatible metrics collection and query system in Rust: a dimensional time-series data model (metric name + label set → series), a pull-based scrape engine with service discovery, an embedded TSDB (WAL + in-memory head block + immutable Gorilla-compressed on-disk blocks + inverted label index), a PromQL-compatible query engine (instant/range vectors, operator/function library), a periodic rule engine (recording + alerting), remote-write/remote-read for long-term storage interop, retention/compaction/downsampling, and cardinality-explosion defenses — so that an operator can scrape a fleet, query it with the PromQL the ecosystem already knows, and trust the system not to fall over when a label goes wrong.

Phase-0 deliverable (numbered, matches §10/§11 naming exactly):

  1. tempora-model — label-set canonicalization, Sample, the four metric types.
  2. tempora-exposition — Prometheus text-format + OpenMetrics parser/writer.
  3. tempora-client — in-process MetricRegistry, /metrics handler.
  4. tempora-tsdb (head + WAL subset only) — append path, crash-safe replay.
  5. tempora-cli — ingest, query (literal series lookup only), dump-wal.
  6. conformance/corpora/exposition/ — the round-trip fixture set (§13.5).

System boundaries.

  • Provides: dimensional metric ingestion (pull + push), crash-safe local storage, PromQL query evaluation, recording/alerting rules, a Prometheus-compatible HTTP API, remote-write ingest and emit, per-tenant cardinality and retention control.
  • Delegates: alert routing/silencing/grouping (to an external Alertmanager, §21); dashboarding (to Grafana or equivalent); long-term object storage durability (to the configured object store, §18); distributed consensus for multi-region deployment (not attempted — see Alternative Architectures, §36, alternative 4).
  • Does NOT provide: logs or traces (a different system by design — see Why Build This, §2); a general-purpose SQL query surface (PromQL only, ADR-05); synchronous write acknowledgement across regions (single-region durability only, §27).

Non-goals: log aggregation, distributed tracing, general OLAP, a competing query language, active-active multi-region write replication.

Deployment model: a single binary (tempora) per shard, stateless service-discovery inputs, local disk for WAL + hot chunks, optional object-store for cold chunks (§18.5). Shards are independent processes; a tenant's data lives on exactly one shard (or a documented replica set — see Deferred Features Register, PhaseDeferred("§37"), for active replication).

Target users/operators: SRE/platform teams operating a mid-size fleet (10³–10⁷ active series) who want Prometheus-ecosystem compatibility without adopting the full Prometheus/Thanos/Mimir operational surface area.

What later phases unlock: Phase 4–6 (§16–18) unlock durable, queryable local storage; Phase 7–8 (§19–20) unlock the query language; Phase 9 (§21) unlocks alerting; Phase 10 (§22) unlocks Grafana/federation/remote-write interop; Phase 11 (§23) unlocks safe multi-tenant operation at scale.

Recommended language: Rust 2024 (ADR-01). Rationale: per-sample memory predictability with no GC pause under a 10⁷-series working set (Gjengset, Rust for Rustaceans, applied §14/§16); a crashed process's WAL replay is a pure decode loop with no allocator jitter. Rejected: Go (the Prometheus reference language — GC pauses of 100–200 ms are the documented cause of scrape misses at high cardinality); C++ (comparable performance, materially higher memory-safety defect rate for a WAL/mmap-heavy codebase); Java/JVM (GC pause profile similar to Go; heap-off-heap split adds operational complexity for mmap'd chunks).

Prerequisites: dimensional data modeling, append-only log design, bit-level compression (delta/XOR coding), recursive-descent/Pratt parsing, async I/O and backpressure, inverted indexes, multi-tenant isolation.

Estimated timeline: Phase 0 — 1 week. Full system (Phases 0–11) — 29 weeks (~7 months).

Every deferred feature is flagged PhaseDeferred("§37") inline and registered in the Deferred Features Register (§37): native (sparse) histograms, trace exemplars, HTTP/3 ingest, AI-based anomaly detection, OpenTSDB/InfluxDB ingest compatibility, browser-side ingest, mobile SDKs, OSS-Fuzz onboarding, active multi-region replication.

2. Why Build This

A metrics system is the canonical example of a design whose one-line insight — a metric is a name plus a label set plus a stream of timestamped samples; a query is a function over those streams — hides a multi-year engineering tail: a label-set model where every distinct combination is a separate series that costs memory and disk forever (cardinality); an exposition format parsed at hundreds of MB/sec; a scrape scheduler serving 10⁴ targets every 15 s without network herd effects; a head block queryable while being appended; a WAL replayed in under a minute after a crash; a compression scheme giving double-digit ratios on real time-series shapes (Gorilla); a query language with a hundred-page semantic spec; a rule engine competing with user queries for the same storage; and a multi-tenant boundary that keeps one tenant's cardinality explosion from starving another's dashboard.

Teams that adopt Prometheus + Grafana + a long-term-storage backend (Thanos/Mimir/VictoriaMetrics) learn these lessons in production, mid-incident: 15-day local retention runs out; a federation hierarchy has a hot spot dropping samples; a pod_name label's cardinality explosion OOMs the process every 30 minutes; a wide-range Grafana query times out; a recording-rule typo makes an alert silently never fire. Building a focused system — rather than only operating one — is what turns "I run Prometheus" into "I know why Prometheus is built the way it is, and where it would break."

This project is the smallest system that still exercises the full surface: the dimensional data model, the pull/scrape model with service discovery, the TSDB (WAL, head, immutable blocks, Gorilla chunks, inverted index), PromQL (lexer, Pratt parser, evaluator, ~50-function library), the rule engine, the HTTP API, remote-write/read, retention/compaction, and cardinality defense — cross-linked throughout to Cortex/Mimir (multi-tenant sharding), Thanos (object-store federation), VictoriaMetrics (an alternative, more aggressive encoding), M3DB (a sharded-index alternative), and Monarch (planet-scale ingestion). The calibration value: after this, "add a metric" and "why did this query time out" both have a specific, traceable answer instead of a shrug.

  • Explain why label-set identity, not metric name, is the unit of cardinality cost, and derive the memory blast radius of one exploding label — §16 (TSDB Head Block + WAL), §23 (Cardinality Defense).
  • Derive, from first principles, why delta-of-delta timestamp coding plus XOR value coding achieves ~11× compression on real scrape data, and when it does not — §17 (Gorilla Chunk Encoding).
  • Explain why Prometheus chose pull over push, and name the concrete regime where push wins instead — §15 (Service Discovery + Scrape Pipeline), §36 (Alternative Architectures).
  • Trace exactly which subsystems execute, in order, when a rate(x[5m]) query runs across 24 h of data, including counter-reset handling and extrapolation — §20 (PromQL Evaluator).
  • Design a WAL + checkpoint recovery protocol that bounds replay time as a function of WAL size, citing the ARIES precedent — §16 (TSDB Head Block + WAL).
  • Reason about horizontal scaling of a sharded TSDB: what stays O(1) per shard, what needs cross-shard coordination, and where the ceiling is — §31 (Scalability Analysis).
  • Redesign the system around a fundamentally different ingestion or storage model and state precisely what is gained and lost — §36 (Alternative Architectures).

Four properties hold throughout and are referenced by ID below. (a) Label-set identity (I1): two samples with the same metric name and the same canonical label set are the same series; different sets are different series — the canonicalized-label-set hash is the series ID, and it is the single load-bearing lookup key for every subsystem above. (b) Append-only write, range- scan read (I3, I4): samples are appended to the head; the head rotates to an immutable chunk on the hour; a query scans only the chunks whose time range intersects the query window. (c) PromQL is a functional evaluator over vectors (I8): an instant vector is (series, value@t); a range vector is (series, [(value, ts) …]); every operator/function is a pure transform over these, driven by a recursive AST walk. (d) Multi-tenancy is per-tenant storage (I7): each tenant owns its own head, WAL, chunk directory, and retention policy; cross-tenant reads are blocked at the storage boundary, not merely the API layer.

The crate prefix tempora- is normative (ADR-01/§10); every phase, the Repository Layout (§10), and Core Schema & Types (§11) reuse these exact names.

6. Design Principles

  1. P1 — Label set is identity. Name + canonical label set define a series; two samples that canonicalize identically are the same series. Tradeoff: canonicalization cost per append. Operational implication: series-ID hash collisions must be provably impossible within budget (64-bit FNV1a + sorted-tuple equality check). Violating this silently merges or splits series.
  2. P2 — Append-only write, range-scan read. Writes never mutate history; queries only scan. Tradeoff: no in-place correction (corrections are new samples). Violating this (e.g. mutable chunks) breaks crash-consistency guarantees.
  3. P3 — PromQL is the query language, not an invented one. Tradeoff: inherits PromQL's semantic quirks. Violating this breaks Grafana/ecosystem compatibility (ADR-05).
  4. P4 — Pull is the default transport. Scrape interval is operator-configured; push (remote-write) is secondary. Tradeoff: producers must expose an HTTP endpoint. Violating this (push-only) removes the manual-curl-inspectability property (§2).
  5. P5 — Cardinality is gated, not merely observed. Per-tenant per-metric label-set caps are enforced before allocation. Tradeoff: legitimate high-cardinality use cases must raise the cap explicitly. Violating this is the single largest cause of production OOM (FM-2).
  6. P6 — Compression is on by default, end to end. Gorilla in-memory, ZSTD on-disk cold tier, Snappy on the wire. Tradeoff: CPU for compress/decompress. Violating this multiplies storage cost ~11×.
  7. P7 — The head block is queryable, not just append-only. Recent (uncompacted) samples must answer queries with the same interface as compacted chunks. Tradeoff: read/write concurrency control on the head. Violating this creates a visibility gap of up to one compaction interval.
  8. P8 — WAL precedes acknowledgement. A sample is durable (fsynced within the batching window) before the append call returns success. Tradeoff: fsync latency vs throughput (§4 RPO). Violating this loses samples silently on crash.
  9. P9 — Retention is per-tenant, not global. Tradeoff: per-tenant bookkeeping overhead. Violating this lets one tenant's volume dictate another's retention.
  10. P10 — The HTTP API is byte-for-byte Prometheus-compatible where specified. Tradeoff: cannot unilaterally change response shape. Violating this breaks every existing Grafana dashboard.
  11. P11 — Federation is a query; remote-write is a push. Different correctness contracts (pull freshness vs push durability). Conflating them (e.g. treating federation as durable) loses samples silently between scrapes.
  12. P12 — No global mutable state; a Tsdb is a value. Multiple instances coexist in one process (tests, multi-tenant). Violating this makes deterministic testing impossible.
  13. P13 — Determinism in the evaluator. A query against a fixed sample set produces a bit- identical result every time. Tradeoff: no wall-clock-dependent evaluation shortcuts. Violating this makes the conformance harness (§13.5 pattern, §28) unusable.
  14. P14 — Errors are typed and carry position/path. Query errors carry the offending AST span; storage errors carry the file path and offset. Violating this turns every incident into a guessing game (§25).

8. Domain Model

8.1 Time-Series Data Model

MetricFamily   { name: str, help: str, type: MetricType, unit: Option<str> }
MetricType     = Counter | Gauge | Histogram | Summary
LabelSet       = sorted, deduped Vec<(name: str, value: str)>, interned per tenant
Series         = { series_id: u64 (= FNV1a(canonical LabelSet)), family: str, labels: LabelSet }
Sample         = { series_id: u64, timestamp_ms: i64, value: f64 }   // NaN = stale marker (I11)

Two samples are the same series iff their canonical LabelSet (sorted, deduped, interned) hashes equal (I1). A Histogram sample set is itself a family of series: name_bucket{le="…"}, name_sum, name_count — each a distinct series under the invariants above.

8.2 Exposition Grammar (Prometheus text format, EBNF fragment)

exposition   ::= (metric_family)* eof
metric_family::= help_line? type_line? sample_line+
help_line    ::= '#' 'HELP' metric_name text_line
type_line    ::= '#' 'TYPE' metric_name metric_type
sample_line  ::= metric_name label_block? ws value (ws timestamp)? newline
label_block  ::= '{' (label (',' label)*)? '}'
label        ::= label_name '=' quoted_string
value        ::= float | 'NaN' | '+Inf' | '-Inf'

OpenMetrics extends this with # UNIT, a mandatory # EOF terminator, and exemplar suffixes (# {trace_id="…"} value timestamp) — the parser (§13) accepts both dialects on one code path.

8.3 Worked Example — Ingest to Query

Scrape line: http_requests_total{job="api",code="200"} 12.0 1700000000000 → canonicalize labels [(code,"200"),(job,"api")] → series_id = FNV1a(...) → append Sample{ series_id, ts=1700000000000, value=12.0} to head + WAL. A later scrape appends value=15.0 at ts+15000. Query rate(http_requests_total{job="api"}[1m]) at ts+15000: evaluator resolves the range vector (two points), computes (15.0-12.0)/(15.0s)=0.2/s, applies boundary extrapolation (§20.6) since only one interval is covered, returns instant vector {code="200",job="api"} 0.2.

8.4 Malformed-Input Example

http_requests_total{job="api" 12.0 (missing closing brace and =) — the lexer emits Token:: Error at byte offset of the first unmatched {; the parser aborts the current metric family, counts tempora_exposition_parse_errors_total{reason="unterminated_label_block"}, and resumes at the next \n — a single malformed line never drops the rest of a scrape (§13.7).

8.5 Failure-Path Example — WAL Segment Corruption

A power loss mid-fsync leaves a WAL segment's trailing record with a CRC32C mismatch (I4/I13 cross-check). On replay (§16.6): segments before the bad record replay normally; the bad record and everything after it in that segment is discarded; tempora_wal_truncated_replay_total increments; the head resumes from the last good record; samples between the last good record and the crash are lost (bounded by the fsync interval, ≤ 100 ms per §4 RPO) — this is the documented, budgeted loss window, not a bug.

8.6 TSDB On-Disk Layout

WAL record   : type(4B) | length(4B) | payload(length B) | crc32c(4B)
WAL types    : Series{id,labels} | Sample{id,ts,value} | Tombstone{id} | Checkpoint marker
Chunk file   : header{magic,version,count} | per-series{id,ts_range,gorilla_bytes} | trailer{crc}
Index file   : symbol_table{dedup strings} | postings{(name,value)→sorted series_id[]} |
               series{id→(labels,chunk_offsets)} | postings_offset_table

8.7 Scrape / Pull State Machine

State Meaning Transitions
Unknown target discovered, not yet scraped → Up (scrape ok) / → Down (scrape fails)
Up last scrape succeeded → Down (failure) / → Up (success, self-loop)
Down last scrape failed (timeout, 5xx, parse error) → Up (success) / → Dropped (relabel drop or discovery removal)
Dropped target no longer discovered or explicitly dropped terminal (target removed from pool)

8.8 PromQL Vector Types

Instant Vector = {(Series, value@t)}; Range Vector = {(Series, [(value,ts) … over [t-d,t]])}; Scalar = f64; String = str (rare, mostly label_join/debug). Binary operators between two instant vectors require vector matching (§20.2): one-to-one by default, ignoring()/on() to adjust the match key, group_left()/group_right() for many-to-one.

12.1 Objectives

Stand up the workspace, licensing, CI skeleton, and the smallest vertical slice that proves the data model round-trips: register a Counter, expose it, scrape it, ingest it, and see the value come back. This is the "correctness kernel" required by §7: no query language yet, just identity and durability.

12.2 Detailed Implementation Steps

Lay out crates/ per §10 exactly. Implement tempora-model::LabelSet::build (P1, I1) with sort+dedup+intern and series_id() via FNV1a. Implement a minimal tempora-exposition::text::parser sufficient for the round-trip fixture. Makefile targets: bootstrap build test lint conformance bench fuzz miri compose-up compose-down release-check clean.

12.3 Deliverable

A binary that: registers http_requests_total, increments it, serves /metrics, parses its own output back into Samples, and asserts round-trip equality — runnable via make bootstrap && make test.

12.4 Acceptance Criteria

Round-trip test passes for ≥ 3 fixture families (counter, gauge, histogram). cargo-deny reports zero license violations. CI green on ci.yml. Fixture conformance/corpora/exposition/ smoke_roundtrip.txt byte-identical after parse→write→parse.

A panic in the parser on malformed input is a Phase-0 blocking bug (violates P14 — errors must be typed, never a panic); every fixture in corpora/exposition/ must be panic-free by construction (fuzz target exposition_parse, wired even at Phase 0 per ADR-14/18).

No production deployment at this phase. tracing (ADR-16) is wired from the first commit so every later phase inherits structured spans rather than retrofitting them.

14. Phase 2 — Client Library + Instrumentation

14.1 Objectives

Deliver tempora-client as a production-grade instrumentation library: lock-free where possible (P1, Gjengset ch. 6), with a client-side cardinality guard (P5) so a single misused label doesn't crash the producer either.

14.2 Detailed Implementation Steps

Counter/Gauge as AtomicU64 (f64 bit-cast) per ADR-01's no-GC rationale. Histogram: one AtomicU64 per bucket plus _sum/_count; observe(v) increments the bucket with the smallest le ≥ v (P1-adjacent identity, no lock). Summary: a per-quantile Mutex<TDigest> (Dunning/Ertl 2019, applied here per §5) since t-digest merge is not lock-free — document this as the one deliberate lock in the hot path (I2-adjacent: this lock never blocks WAL durability, it's purely client-side). MetricRegistry::new_label_combination checks the client-side cardinality cap (default 10,000, ADR-08) before allocating a new series, incrementing dropped_label_combinations_total on rejection (P5, I6).

14.3 Deliverable

A /metrics HTTP handler serving all four types at the target throughput, with the client-side cap verifiably rejecting the 10,001st distinct label combination for one metric.

14.4 Acceptance Criteria

/metrics endpoint serves ≥ 100,000 samples/sec/core (M5, §30). A counter incremented 1,000,000 times serially reports exactly 1,000,000. The 10,001st new label combination for one metric is rejected and counted, not silently dropped without telemetry.

Fixture Purpose Expected Output

cardinality_cap_10001.rs (test) client-side cap (P5/I6) 10,001st combination dropped + counted

14.6 Pitfalls

A LabelSet construction that allocates per call is the canonical perf bug — cache the canonicalized form per (name, labels) pair (§13.7 pattern reused here). Counter::reset() does not exist by design — counters are monotonic; a process restart is detected downstream by rate() (§20.6), not here. A Histogram::observe for v above the largest bucket must still land in _count/_sum — easy to forget.

14.7 Performance Concerns

Atomic contention on a single hot Counter under many threads is the dominant cost at extreme fan-in; sharded counters (N atomics, summed on read) are the documented escape hatch, not implemented by default (PhaseDeferred, §37) since most metrics are not this hot.

14.8 Edge Cases

Two threads racing to create the same new label combination (only one must win the cardinality-cap check; the other must observe the already-created series, not double-count against the cap). Summary under concurrent observe and /metrics read (the digest lock must not starve the scrape path beyond the scrape timeout).

14.9 Failure Analysis

A cardinality-cap misconfiguration (set too low) silently drops legitimate series — detection is dropped_label_combinations_total > 0 sustained, not a crash; the runbook (docs/runbooks/cardinality-explosion.md) is the operator's first stop.

14.10 Operational Notes

Every dropped combination increments a counter with the offending metric name as a label (bounded cardinality itself — one series per metric family, not per dropped combination, to avoid a cardinality-defense mechanism that itself explodes cardinality).

15. Phase 3 — Service Discovery + Scrape Pipeline

15.1 Objectives

Deliver target discovery (static/file/DNS/K8s) and the scrape loop against 10⁴ targets at 15 s intervals without herd effects (P4, §4).

15.2 Detailed Implementation Steps

Discovery trait (ADR-21) with four implementations: Static, FileSd (inotify/poll watcher), DnsSd (A/SRV lookup), KubernetesSd (API watch on pods/services/endpoints/nodes). Each target carries {url, scheme, labels, scrape_interval, scrape_timeout}. Relabeling (§8.2-adjacent DSL, reused from Prometheus verbatim, applied per P4): replace, keep, drop, hashmod, labelmap, labeldrop, labelkeep, applied in order, drop terminal. Scrape execution: per-target jittered schedule (avoids second-boundary herd — the jitter seed is hash(target_url) % interval), HTTP GET via a pooled client (max 256 concurrent, §4), inject job/instance labels, route parsed samples into the TSDB append path (§16). A target whose prior scrape had a series absent from the current scrape gets that series stale-marked (I11).

15.3 Deliverable

A scraper that discovers targets via FileSd, applies a hashmod-based shard relabel rule, and completes a 10,000-target scrape cycle within the 15 s interval.

15.4 Acceptance Criteria

10,000-target scrape completes within its 15 s interval budget (M6, §30). Stale-marking verified for a target whose series set shrinks between scrapes. Relabel drop-all-targets misconfiguration is detectable via tempora_active_targets dropping to zero (not just silently empty).

Fixture Purpose Expected Output

15.6 Pitfalls

Missing scrape jitter causes every target to be hit at second boundaries, spiking network usage (P4-adjacent — the jitter is not optional). The relabel DSL has dozens of corner cases across seven actions — the conformance corpus, not intuition, is the oracle (I8 determinism pattern reused). __tmp_* labels are convention for intermediate relabel state; final rulesets must drop them.

15.7 Performance Concerns

max_concurrent_scrapes=256 bounds in-flight HTTP connections; at 10,000 targets / 15 s, required throughput is ~667 scrapes/sec, comfortably inside the 256-concurrency budget when average scrape latency stays under ~400 ms (§4 RTT assumption).

15.8 Edge Cases

DNS-SD resolution flapping (target added/removed every poll — debounce required); a target that returns 200 with a truncated body (parse error, not a network error — counted separately); Kubernetes API watch disconnect (must resume from last resource version, not full-relist every time, to avoid discovery storms).

15.9 Failure Analysis

A relabel rule that drops every target is the canonical "I lost my targets" incident — the scrape-misses.md runbook (§26) walks: check tempora_active_targets, check the relabel config diff, roll back. A target body_size_limit breach is silently survivable (scrape counted as failed, others unaffected) — verify via scrape_failed_total, not target-count.

15.10 Operational Notes

tempora_active_targets, tempora_scrape_duration_seconds, tempora_scrape_failed_total{reason} are the three dashboards operators need first. Discovery-source outages (e.g. Kubernetes API unreachable) must degrade to "keep last known target list," not "drop all targets."

16. Phase 4 — TSDB Head Block + Write-Ahead Log

16.1 Objectives

Build the crash-safe append path: head block (P7, queryable while appending) plus WAL (P8, ARIES- style durability, applied per §5).

16.2 Detailed Implementation Steps

HeadBlock shards by a 2-hour time window (§11); each series holds a chunk-in-progress (GorillaChunkBuilder, sealed at hour boundary into Phase 5's format, §17). WAL is segmented (128 MiB default, Petrov ch. 7 applied here); records are Series | Sample | Tombstone | Checkpoint (§11), each framed type(4B)|len(4B)|payload|crc32c(4B) (I4/I13 cross-check basis). fsync policy: batched every 100 ms (P8, tunable — the RPO/throughput knob, §4). Recovery (ARIES redo-only replay, Mohan 1992, applied here): load latest checkpoint into the head, replay WAL records after the checkpoint offset, rebuild the head-series map and inverted index incrementally. A CRC mismatch truncates replay at that record (I4, §8.5 worked failure path).

16.3 Deliverable

A Tsdb::append path that survives a kill -9 mid-write: on restart, replay recovers every fsynced sample and cleanly truncates at the first corrupt record.

16.4 Acceptance Criteria

Ingest ≥ 1,000,000 samples/sec/node (M1, §4). WAL replay of 100 GB completes in < 60 s (M2, §4). Head queries return an appended sample within 1 ms of append (M3). Crash-injection test (kill -9 at 50 random points during a fixed workload) recovers with zero panics and a deterministic truncation point each run.

16.5 Conformance Fixtures

Fixture Purpose Expected Output
wal_crc_mismatch.bin corrupted trailing record (§8.5) replay truncates at bad record, wal_truncated_replay_total incremented
checkpoint_interrupted.bin crash mid-checkpoint rename previous checkpoint remains valid (atomic rename, I4)
1e8_sample_replay.bin replay throughput (M2) < 60 s wall time

16.6 Pitfalls

The fsync-every-batch vs fsync-every-N-batches tradeoff (P8) is configurable, default 100 ms — document the RPO consequence explicitly, don't bury it. Head memory is proportional to series count × samples/series; the cardinality cap (§14, I6) bounds the first factor, hourly chunk rotation bounds the second. A checkpoint is published via atomic rename — an interrupted checkpoint must leave the prior one intact (I4). A new series created mid-compaction must land in the next checkpoint — the compactor is single-writer to preserve this ordering (I5).

16.7 Performance Concerns

Hot-path append cost ≈ 130 ns/sample (hash 20 ns + head lookup 30 ns + Gorilla encode 50 ns + WAL ring-buffer append 30 ns, §30.1) — at the 1M samples/sec ceiling this is ~13% of one core (Capacity Model CM3, §34). WAL write bandwidth at ceiling ≈ 24 MB/s/node (CM4).

16.8 Edge Cases

Out-of-order sample arrival within a batch (I3 — routed to an out-of-order buffer or dropped per policy, PhaseDeferred("§37") for full OOO support); a WAL segment that fills exactly at a record boundary (must roll to a new segment without splitting a record); two concurrent checkpoints racing (prevented by the single-writer compactor lock, I5); clock skew making a sample's timestamp appear before the series' last-seen timestamp (handled identically to out-of-order).

16.9 Failure Analysis

WAL corruption blast radius is bounded to the samples since the last good record in that segment (§8.5) — never the whole WAL, because segments are independently checksummed. Detection: wal_truncated_replay_total > 0 on any restart is a page-worthy signal if it recurs (indicates disk or power instability, not application logic). Recovery path: replay, then re-scrape naturally refills the lost window within one scrape interval for pull-based series (push/remote-write series have a genuine gap, logged).

16.10 Operational Notes

tempora_wal_fsync_seconds (I2 evidence), tempora_head_series, tempora_out_of_order_samples_total (I3 evidence) are the head/WAL dashboard trio. Rolling upgrade: a new binary must be able to replay a WAL segment written by the immediately-prior minor version (§27 compatibility policy).

17. Phase 5 — Gorilla Chunk Encoding

17.1 Objectives

Implement the Facebook Gorilla compression scheme (Pelkonen et al. 2015, applied here per §5 and ADR-04) for the in-progress and sealed chunk formats, hitting the ~11.4× compression target from §4.

17.2 Detailed Implementation Steps

Timestamp delta-of-delta coding: first timestamp stored raw; subsequent deltas' second difference is coded with variable-length prefixes (0→1 bit for zero DoD; 10+7 bits; 110+9 bits; 1110+12 bits; 1111+32 bits) — most scrape series have constant intervals, so the common case is 1 bit/sample (ADR-04, Pelkonen 2015 applied). Value XOR coding: first value raw (64 bits); subsequent values XORed with the previous; a zero XOR costs 1 bit; a nonzero XOR reuses the prior leading/trailing-zero window when it fits (2-bit tag) or stores a fresh window (5-bit leading-zero count + 6-bit meaningful-bit count + the bits). Stale markers (I11): the reserved NaN bit pattern is encoded as a full-format value, never compressed away. Reset detection (counter wrap, §20.6's consumer) is a query-time concern — the chunk stores raw values only (P2).

17.3 Deliverable

tempora-tsdb::chunk::gorilla encode/decode pair achieving the target ratio on a representative 15 s-interval fixture set, decodable only forward (random access requires decode-from-chunk-start, documented as a known cost — see §17.7).

17.4 Acceptance Criteria

Encode ≥ 10,000,000 samples/sec/core; decode ≥ 10,000,000 samples/sec/core (M7, §30). Compression ratio ≥ 1.5 bytes/sample on the typical_scrape_15s.fixture corpus (target from Pelkonen 2015's 1.37 B/sample measurement, ADR-04).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
typical_scrape_15s.fixture ratio benchmark ≤ 1.5 bytes/sample average
constant_value_series.fixture XOR-zero fast path ~1 bit/sample after the first value
nanosecond_precision_ts.fixture compression-killer case (§17.9) ratio degrades gracefully, no correctness loss
stale_marker_mid_chunk.fixture I11 encoding decoder yields NaN, resumes correctly after

17.6 Pitfalls

The variable-length DoD codes are easy to get off-by-one on prefix-bit counts — the conformance corpus (not manual derivation) is the oracle (I8 pattern). NaN stale markers need the dedicated full-format encode path, not the common-case XOR path. The chunk format is on-disk-stable (I4) — never change it without a ChunkHeader.version bump and a migration note (§27).

17.7 Performance Concerns

Decoding is strictly forward-only; random access within a chunk requires a full decode from the chunk's start — this is why chunks are kept small (hourly rotation) rather than spanning days. Subnormal-precision f64 values encode to many meaningful bits, making the compression ratio workload-dependent, not a fixed constant.

17.8 Edge Cases

A timestamp series with nanosecond-level jitter (non-uniform deltas) — the canonical compression killer, since DoD assumes near-constant intervals; ratio degrades toward the raw 16 B/sample floor but correctness is unaffected. A value sequence alternating between two very different magnitudes every sample (worst case for XOR — full window every time).

17.9 Failure Analysis

A chunk whose trailer checksum fails on read (I4) is quarantined; the WAL segment covering that chunk's time range is replayed to reconstruct it (§16, §8.5 pattern) — detection via tempora_chunk_checksum_mismatch_total, recovery is automatic and logged.

17.10 Operational Notes

tempora_chunk_encode_seconds, tempora_chunk_decode_seconds, and tempora_chunk_compression_ratio (a gauge, sampled per compaction) are the dashboard trio; a sustained ratio drop below ~3× on a stable workload is a signal worth investigating (often a client-library regression sending jittered timestamps).

18. Phase 6 — Chunk Persistence + Inverted Index + Compaction

18.1 Objectives

Move sealed chunks to disk, build the label→series inverted index, and run background compaction (hourly WAL→chunk, daily small→large) without blocking the append path (P7, I5).

18.2 Detailed Implementation Steps

Chunk file layout: header{magic,version,count} | per-series{id,ts_range,gorilla_bytes} | trailer{crc} (§11), mmap'd for read (kernel page cache as LRU). Index file: symbol table (deduplicated label strings) + postings (delta-encoded sorted series-ID lists per label pair) + series table + postings-offset table (§8.6, Rabenstein/Volz design docs applied here per §5). Hourly compaction: snapshot the head (brief in-flight-append flush), encode each series' chunk-in-progress to Gorilla bytes (§17), write the chunk file, build the index, atomically rename to publish, truncate the WAL up to the snapshot point (I5 — pre/post sample-count assertion enforced here). Daily compaction merges small hourly chunks into larger ones, rebuilding the index for the merged range (Kleppmann ch. 3 log-structured-merge pattern applied here per §5). Retention GC (I9) deletes chunks whose entire range is outside the tenant's retention window. Cold tier (ADR-12): daily-compacted chunks may upload to S3/GCS/Azure/fs; queries fetch on demand into a bounded local LRU cache (chunk_cache_bytes, default 4 GiB).

18.3 Deliverable

A background compactor that runs concurrently with live ingest, publishing hourly chunks that pass the I5 sample-count invariant check, plus a daily merge job and a retention GC pass.

18.4 Acceptance Criteria

Hourly compaction completes within 50% of the hour budget (M8, §4/§30). A 30-day range query against cold-tier chunks completes p99 < 30 s (§4). I5 sample-count assertion never fails across a 1-hour soak of continuous ingest + compaction.

18.5 Conformance Fixtures

Fixture Purpose Expected Output

retention_boundary_gc.fixture I9 only fully-expired chunks deleted, no partial-range deletion

18.6 Pitfalls

mmap'd chunk reads are page-fault-bound on first access — pre-warming the cache is a real perf knob, not a nice-to-have (§17.7-adjacent). Cold-tier fetches are second-scale — cache aggressively or the 30 s p99 (§4) is unreachable. A compaction that overruns its hour is the canonical "falling behind" incident (§26 runbook compaction-stuck.md). Symbol-table dedup is per-chunk-file only; cross-chunk dedup is PhaseDeferred("§37").

18.7 Performance Concerns

Postings-list intersection for a multi-matcher query is ~20 ns/series (sorted-list intersection); for 1M series with two matchers, ~20 ms (§30.2). SIMD-accelerated intersection (AVX2, ~2× speedup) is a documented stretch, PhaseDeferred("§37").

18.8 Edge Cases

A series created during compaction's head-snapshot window (must land correctly in the next checkpoint, not be lost — single-writer compactor, I5). A chunk file whose index publish succeeds but whose chunk-file rename fails (must not leave an index pointing at a missing chunk — I13 cross-check catches this on next read, triggers index rebuild). Object-store transient 5xx during cold-tier upload (retried with backoff, never silently drops the chunk — local copy retained until upload confirmed).

18.9 Failure Analysis

An I13 orphan-postings detection (index references a series absent from the chunk) triggers an automatic index rebuild from the chunk file — bounded by chunk-file size, logged as tempora_index_orphan_postings_total. A stuck compactor (exceeding the hourly budget repeatedly) is diagnosed via tempora_compaction_duration_seconds trending upward — the runbook's first check is head-series-count growth (cardinality creep, cross-referencing §23).

18.10 Operational Notes

tempora_compaction_duration_seconds, tempora_gc_deletions_total, tempora_chunk_cache_hit_ratio are the operator-facing trio. Rolling upgrade: the chunk-file and index-file formats are versioned (ChunkHeader.version) so an old binary refuses to read a newer format rather than silently misinterpreting it (§27).

19.1 Objectives

20. Phase 8 — PromQL Evaluator + Function Library

20.1 Objectives

Implement the recursive AST evaluator: instant/range vector resolution, the ~50-function library, vector matching, and range-query stitching (P13 determinism is the acceptance bar throughout).

20.2 Detailed Implementation Steps

Evaluator walks Expr recursively (I8): a VectorSelector resolves via the inverted index (§18) to (series, value@t) pairs; a MatrixSelector resolves to (series, [(value,ts)…]) over the window; BinaryOp resolves both sides then applies vector matching — one-to-one by default, ignoring()/on() to adjust the match key, group_left()/group_right() for many-to-one (Prometheus semantics reproduced exactly, applied per ADR-05/P3). Function dispatch (~50 functions: rate irate increase delta idelta sum avg min max count topk bottomk quantile histogram_quantile label_replace label_join …, §11) by name. rate(m[5m]): sum the increase across the window adjusting for counter resets (value decreasing without a documented reset is still treated as a reset, per Brazil 2018 ch. 3 applied here), divide by window duration, then extrapolate toward the window boundary (±20% jitter-sensitivity without this, per Prometheus's documented rationale) — I8 determinism requires this extrapolation to be a pure function of the window's sample set. histogram_quantile(φ, buckets): rate each bucket, cumulate by ascending le, find the bucket crossing φ × total, linearly interpolate between bucket boundaries (Tene's HdrHistogram error-bound reasoning applied here per §5) — bucket-boundary spacing bounds the estimate error (ADR-24). query_range(expr,start,end,step) evaluates at each step timestamp, reusing the matched-series set across steps (§30.6 optimization).

20.3 Deliverable

tempora-promql::eval passing the Prometheus PromQL evaluator conformance corpus, with rate() and histogram_quantile() verified against hand-computed reference values.

20.4 Acceptance Criteria

≥ 99% pass rate on the Prometheus PromQL evaluator test corpus vs the reference implementation (M10, §30). A 24-hour rate(http_requests_total[5m]) query over 1,000,000 series completes in < 30 s (M11, derived from Capacity Model CM8, §34). A query requesting more than max_resolution_points (11,000 default) is rejected with a typed error, not truncated silently.

20.6 Pitfalls

The rate() boundary case — last sample of one range vs first sample of the next — is the canonical bug source; the corpus, not intuition, is the oracle (I8). histogram_quantile requires strictly cumulative le-ordered buckets (ADR-24); a non-cumulative input returns NaN, not a wrong number. label_replace with a non-matching regex is a documented no-op — this surprises users enough to warrant an explicit note in docs/api/.

20.7 Performance Concerns

Chunk decode at 10,000,000 samples/sec/core (§17) is the dominant cost for wide range queries; Capacity Model CM8 (§34) shows a full-shard 1M-series/24h scan needs index-based pruning to matched series (typically < 1% selectivity) to stay inside the 5 s p99 budget (§4) — full-shard scans without pruning miss the SLO by ~7×.

20.8 Edge Cases

A quantile_over_time requiring every sample in a wide range held in memory simultaneously — documented memory cost, not silently unbounded.

20.9 Failure Analysis

A query exceeding a per-tenant query-time budget is cancelled cooperatively (cancellation token checked between evaluation steps) rather than left to run — detection via tempora_query_duration_seconds histogram, tempora_query_cancelled_total counter.

20.10 Operational Notes

tempora_query_duration_seconds{query_hash} (bounded-cardinality via query hash, not raw query text) is the primary slow-query diagnostic, cross-referenced in docs/runbooks/slow-query.md (§26).

21. Phase 9 — Rule Engine + Alertmanager Integration

21.4 Acceptance Criteria

1,000 rules evaluated every 15 s within the interval budget (M12, §30). Alert for-duration state survives a simulated rule-engine restart (I14 test) with the correct pending timer resumed, not reset to zero. A recording rule whose name collides with an existing scraped series is flagged by a linter, not silently overwritten.

26. Operational Readiness

Metrics/tracing/logging. Every subsystem emits tracing spans (ADR-16) correlated by a per-request trace ID; the system's own metrics (tempora_*, dogfooded via tempora-client, §14) cover ingest, compaction, query, and rule evaluation. Structured JSON logs at info for lifecycle events, warn for recoverable anomalies (T-1..T-12), error for operator-actionable faults.

Dashboards. Three tiers: fleet overview (tempora_active_targets, tempora_head_series, ingest rate), per-tenant (§23.10 trio), and subsystem-deep (WAL/compaction/query, per-phase operational notes §16.10/§18.10/§20.10).

Alerting philosophy. Alert on symptom (query p99 breach, WAL truncation, cardinality-cap saturation), not on cause — causes are diagnosed via the runbooks below once a symptom alert fires.

SLOs. 99.9% query-path availability monthly (§4); query p99 budgets per §4; ingest-loss budget bounded by the fsync interval (RPO ≤ 100 ms).

Incident response. Named runbooks: cardinality-explosion.md, scrape-misses.md, slow-query.md, wal-corruption.md, compaction-stuck.md (§10) — each maps a symptom (§25) to a first-three-checks sequence and a rollback/mitigation path.

Backup/restore. Cold-tier object-store copies (§18.5) are the durable backup; a full-node restore replays the latest cold-tier chunk manifest plus any WAL since the last upload.

Deployment topology. One tempora process per shard; shards are independent (shared-nothing, I7); a load balancer routes by tenant-hash to the owning shard.

Canary/rolling upgrade/rollback. New binaries are canaried against a shadow-traffic tenant before fleet-wide rollout; rollback is a binary swap plus WAL-format-compatibility check (§27); no schema migration is required for a same-major-version rollback.

27. Compatibility & Versioning

Wire compatibility. The Prometheus HTTP API JSON envelope (P10) is stable within a major version; remote-write/read follow the Prometheus remote-write spec versions 1.0 and 2.0 (applied §5) with content-negotiation via headers.

Storage compatibility. ChunkHeader.version and the WAL record format version are checked at open time; a binary refuses to read a newer on-disk format rather than misinterpreting it (§18.10); a WAL segment written by the immediately-prior minor version must remain replayable (§16.10).

Schema evolution. New MetricType variants or WalRecord variants are additive only within a minor version; removing a variant is a major-version change with a documented migration in docs/adr/.

API stability. /api/v1/* endpoints are stable; a breaking change requires a /api/v2/* namespace, never an in-place semantic change to /api/v1/*.

Deprecation policy. A deprecated field/endpoint is marked in docs/api/ for at least one minor version before removal, with a Deprecation response header.

SemVer policy. MAJOR: storage-format or wire-protocol breaking change. MINOR: additive feature (new PromQL function, new discovery backend). PATCH: bug fix, no format/API change.

Rolling-upgrade guarantees. A fleet may run mixed adjacent-minor-version nodes during a rolling upgrade; cross-node protocols (remote-write between shards, if configured) are versioned and negotiate the lowest common format.

Unit. Per-crate, focused on pure functions: LabelSet::build, Gorilla encode/decode, PromQL lexer tokens.

Integration. Cross-crate: scrape→TSDB append→query round trip; rule-engine writeback→query visibility.

Property-based (proptest, ADR-14). LabelSet canonicalization is order-independent for any permutation of input pairs; Gorilla encode/decode round-trips for any generated f64/i64 stream including NaN/Inf.

Differential. PromQL evaluator results compared against the Prometheus reference implementation on the shared conformance corpus (§28's cross_engine fuzz target and the §20 conformance fixtures) — this is the primary mechanism enforcing I8.

30. Performance Engineering

Benchmarking/profiling methodology. criterion (ADR-15) for micro-benchmarks (encode/decode, label canonicalization); the USE method (Gregg 2020, applied here per §5) for system-level profiling — utilization, saturation, errors per resource (CPU, disk, network, FD).

30.1 Ingest Hot Path

Per-sample append: hash label set (~20 ns, FNV1a) → head-shard lookup (~30 ns) → Gorilla encode (~50 ns) → WAL ring-buffer append (~30 ns) ≈ 130 ns/sample total. At the 1,000,000 samples/sec/node ceiling this is ~13% of one core (Capacity Model CM3, §34).

30.2 Index Lookup

Postings-list intersection for a two-matcher query over 1,000,000 series: ~20 ns/series compare, ~20 ms total (§18.7).

30.3 Chunk Decode

Forward-only Gorilla decode at ~10,000,000 samples/sec/core; a pruned (index-selective) 24 h range query over the matched series set stays inside the 5 s p99 budget, while a full-shard unpruned scan does not (Capacity Model CM8, §34; §20.7).

30.4 Memory Budget

Per-node head at 1,000,000 series: ~100 bytes/series label overhead + ~1 KB/series open-chunk buffer ≈ 1.07 GB (Capacity Model CM1, §34); cardinality cap (§14/§23) is the primary memory dial.

30.5 SIMD Opportunities

Postings-list intersection is SIMD-friendly (sorted u64 compare); AVX2 gives ~2× speedup — PhaseDeferred("§37").

30.6 Query Plan Reuse

query_range (§22.2) matches series once and reuses the matched set across every step timestamp; constant folding (1+2→3 at parse time) and selector dedup (a+a evaluates a once) are additional evaluator-level optimizations applied at Phase 8 (§20).

30.7 Scrape Budget

A single scrape is network-bound (5–100 ms typical RTT, §4) plus ~10 ns/byte exposition parse (§13.7); at 256 concurrent scrapes and a 15 s interval, 10,000 targets require ~667 scrapes/sec, inside budget.

30.8 Chunk Cache

A per-process LRU (chunk_cache_bytes, default 4 GiB) keeps recently-queried chunks warm; cold queries page in from disk or object store (§18.5).

30.9 Series-Creation Hot Path

A new series: hash label set → head-map lookup (miss) → allocate SeriesHandle + open chunk → insert into head-map (brief write lock) → append to inverted index (per-label-pair write) ≈ 5 µs; the lock is the dominant cost. The cardinality cap check (I6) happens before allocation, here.

31. Scalability Analysis

Stays O(1) per shard: ingest hot-path cost (§30.1), head-series lookup, series-creation cost (§30.9) — all independent of fleet-wide series count because each shard only knows its own tenant's data (I7, shared-nothing).

Grows with fleet size: total head memory (linear in series count, CM1/CM2 §34); postings-list intersection cost (near-linear in matched-series count, §30.2); compaction snapshot size (linear in per-shard series count).

Named bottlenecks in order: (1) single-shard head memory ceiling (bounded by node RAM, forces sharding beyond ~10⁷ series/node); (2) compactor single-writer serialization (I5) — a shard cannot parallelize compaction across its own series without breaking the sample-count invariant's snapshot semantics; (3) cross-shard query fan-out coordination (not built in this design — see Deferred Features Register, §37, and Alternative Architectures alternative 4, §36) once a query must span tenants sharded across nodes.

Horizontal scaling. Tenant-hash sharding (Dynamo-style, DeCandia 2007 applied §5): adding a shard redistributes a bounded fraction of tenants (consistent hashing), not the whole fleet.

Vertical scaling. More RAM raises the per-shard series ceiling (CM1); more cores raise the per-shard ingest and query-decode ceiling (§30.1, §30.3) roughly linearly to the point where head lock contention (§30.9) dominates.

Coordination overhead. O(1) per shard by design (I7) — no cross-shard consensus is required for single-tenant reads/writes; a query spanning multiple tenants' shards (rare, e.g. an operator's fleet-wide dashboard) is deferred (§37) rather than built into the core path.

Practical ceiling and levers beyond it. ~10⁷ active series/node before head memory or ingest CPU dominates (§4); the lever beyond it is adding shards (near-linear scaling to ≥10⁸ fleet-wide series, per Monarch's demonstrated planet-scale pattern, Adams et al. 2020, applied §5) rather than scaling a single shard vertically without bound.

32. Mental Models & First Principles

  • MM1 — A series is a label set, not a name. The compressed insight: cardinality is the number of distinct label-set values, not the number of metric names. Predicts: adding one high- cardinality label multiplies cost by that label's cardinality, not by 1. Bug class without it: "we only have 50 metrics, why is memory exploding" (FM-2). Applied §16, §23.
  • MM2 — Compaction is a scheduled rewrite, not a cleanup. The insight: compaction exists to convert append-cost into read-cost amortization (Kleppmann's log-structured pattern). Predicts: a compactor falling behind degrades query latency before it degrades ingest. Bug class without it: treating compaction as optional housekeeping. Applied §18.
  • MM3 — A WAL trades latency for durability at a knob, not a binary. The insight: fsync batching is a continuous RPO/throughput tradeoff (Mohan 1992's steal/no-force framing). Predicts: the "right" fsync interval depends on the workload's tolerance for a bounded loss window. Bug class without it: assuming "WAL present" means "zero data loss." Applied §16.
  • MM4 — PromQL evaluation is a pure function of the AST and the sample set. The insight: determinism (I8) is what makes differential testing against the Prometheus reference possible at all. Predicts: any evaluator behavior depending on wall-clock time outside the query's own time parameter is a correctness bug. Bug class without it: flaky conformance tests. Applied §20, §28.
  • MM5 — Cardinality defense must happen before allocation, not after observation. The insight: a cap checked post-hoc has already paid the memory cost it was meant to prevent. Predicts: a "cardinality alert" without a pre-allocation cap is a warning, not a mitigation. Bug class without it: OOM despite dashboards showing the warning fired. Applied §14, §23.
  • MM6 — Multi-tenancy is a storage-layer property, not an API-layer filter. The insight: an API-level tenant filter can be bypassed by a bug anywhere upstream of it; a storage-layer partition cannot. Predicts: I7 violations are caught even when the API layer has a bug. Bug class without it: cross-tenant data leaks from an unrelated API regression. Applied §23, §24 (T-8).
  • MM7 — Pull inverts the trust and failure direction of push. The insight: with pull, the consumer controls load and can always inspect a producer manually; with push, the producer controls load and the consumer must defend itself. Predicts: pull systems fail closed (missing data, visible as gaps) where push systems fail open (overload) absent explicit backpressure. Bug class without it: building push-style backpressure into a pull system unnecessarily. Applied §15, §36.
  • MM8 — Compression ratio is a property of the data's temporal locality, not a fixed constant. The insight: Gorilla's ratio depends on scrape-interval regularity and value-change frequency. Predicts: nanosecond-jittered timestamps or highly volatile values degrade the ratio toward the raw floor. Bug class without it: benchmarking compression on synthetic constant data and shipping a false expectation. Applied §17.

Thanos differs by treating long-term storage as a pure object-store-backed federation layer over otherwise-unmodified Prometheus instances, winning where teams already run Prometheus and want long-term storage bolted on without changing the ingestion path — at the cost of a Store-API fan-out query path that this design's single-process query engine avoids.

34. Back-of-Envelope Capacity Model

  • CM1 — Per-node head memory: 1,000,000 series × (100 B label overhead + 1,024 B open-chunk buffer) ≈ 1.07 GB. Formula: series × (label_bytes + chunk_bytes).
  • CM2 — Fleet-wide head memory (15 shards): 15 × 1.07 GB ≈ 16 GB total (excludes WAL/index). Formula: shards × per-shard head memory (CM1).
  • CM3 — Per-node ingest CPU at ceiling: 1,000,000 samples/sec × 130 ns/sample = 0.13 core-seconds/sec ⇒ ~13% of one core. Formula: throughput × per-sample cost (§30.1).
  • CM4 — WAL write bandwidth at ceiling: 1,000,000 samples/sec × 24 B/record ≈ 24 MB/s. Formula: throughput × WAL record size (§16.2).
  • CM5 — WAL replay throughput requirement: 100 GB ÷ 60 s = 1.67 GB/s, ~70× the live WAL write bandwidth (CM4) — achievable because replay skips fsync and network I/O. Formula: WAL size ÷ time budget, compared against CM4.
  • CM6 — Per-node daily chunk volume: 1,000,000 series × 5,760 samples/series/day (15 s interval) × 1.4 B/sample (Gorilla) ≈ 8.06 GB/day/node. Formula: series × samples/day × bytes/sample.
  • CM7 — 15-day local retention footprint/node: 8.06 GB/day × 15 ≈ 121 GB/node. Formula: daily volume (CM6) × retention days.
  • CM8 — 24h range-query decode cost: at 1% index-selectivity (10,000 of 1,000,000 series matched) × 5,760 samples/series ≈ 57.6M samples; at 10,000,000 samples/sec/core (§17) ≈ 0.36 s/core — well inside the 5 s p99 budget (§4); an unpruned full-shard scan (5.76B samples) would take ~576 s/core, ~36 s across 16 cores — still over budget, which is why index pruning (§18) is load-bearing, not an optimization. Formula: matched_series × samples/series ÷ (decode_rate × cores).
  • CM9 — Fleet-wide FD budget: 256 concurrent scrapes/node × ~100 shards worst case ≈ 25,600 sockets, inside the 65,536 FD ulimit (§4) with headroom for ~10,000 WAL/chunk file descriptors. Formula: concurrency × node_count vs FD ceiling.
  • CM10 — Cardinality-cap worst-case single-metric memory: 10,000 series × 1.07 KB/series (CM1's per-series share, 1.07 GB ÷ 1,000,000) ≈ 10.7 MB — a capped runaway metric costs a rounding error against the 1.07 GB node budget. Formula: cap × per-series overhead (CM1).
  • CM11 — Failure tolerance under the availability budget: 43.2 min/month (99.9%, §4) ÷ 5 min/incident RTO ⇒ the system tolerates ≤ 8 independent full-node failures/month before breaching the SLO (assuming non-concurrent failures). Formula: monthly downtime budget ÷ RTO per incident.
  • CM12 — End-to-end compression amplification: 16 B/sample raw → 1.4 B/sample Gorilla (11.4×) → ~1.1 B/sample after ZSTD cold-tier (additional ~1.27×) ⇒ ~14.5× total; the 121 GB/node hot-tier retention (CM7) becomes ~9.5 GB/node once migrated cold. Formula: hot_tier_bytes ÷ total_compression_factor.

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Push-based ingestion (StatsD/Datadog-agent style).

[App] --UDP/local-agent--> [Local Aggregator] --push(interval)--> [Collector] --store-->

Regime where it wins: ephemeral/serverless workloads (Lambda, short-lived batch jobs) that cannot expose a stable scrape endpoint. Real system: Datadog Agent / OpenTelemetry push-mode collectors. Rejected because: push loses the "any operator can curl the endpoint" inspectability property (P4) and shifts cardinality control to the producer side, which this design's pull model keeps centrally enforceable (P5).

Alternative 2 — SQL-over-time on a general relational store.

[App] --insert--> [Postgres + TimescaleDB hypertable] <--SQL-- [Dashboards]

Regime where it wins: teams needing ad hoc relational joins across metrics and other business data that PromQL cannot express. Real system: TimescaleDB. Rejected because: it abandons PromQL/Grafana ecosystem compatibility (ADR-05) and a general relational engine's write path does not naturally give the Gorilla-level compression ratio this design targets (§4).

Alternative 3 — General-purpose LSM/columnar store as the backing engine.

[Scrape] --> [ClickHouse MergeTree table] <-- [PromQL-to-SQL translation layer] <-- [Query]

Regime where it wins: write-heavy workloads needing arbitrary ad hoc schema alongside metrics (logs, traces, metrics unified). Real system: ClickHouse (and M3DB's Cassandra-backed heritage). Rejected because: a general LSM engine's read amplification and generic compaction are not tuned to time-series-shaped data the way purpose-built Gorilla chunks are (§17), and a translation layer adds a permanent semantic-gap risk against PromQL (I8).

Alternative 4 — Fully disaggregated, remote-write-only ingestion with object-store query (Cortex/Mimir blocks-storage style).

[Scrape/Push] --> [Distributor] --shard--> [Ingesters] --flush--> [Object Store] <--query-- [Store-Gateway]

Regime where it wins: massive multi-tenant SaaS scale (Mimir/Cortex's actual regime) where tenants number in the thousands and durability must survive whole-node loss without local-disk reliance. Real system: Grafana Mimir / Cortex (blocks storage). Rejected because: it adds several independent services (distributor, ingester, store-gateway, compactor) and their coordination overhead — not justified below the tenant-count and fleet-size threshold this design targets (§4); tracked as a possible evolution path, PhaseDeferred("§37").

38. Glossary

  • Alert. A rule instance that transitions to Firing when its expression matches for its for-duration.
  • Alertmanager. The external component (delegated, §1) responsible for alert routing, grouping, and silencing.
  • Cardinality. The number of distinct label-set values for a given metric.
  • Checkpoint. A snapshot of the head block that lets WAL replay start from a later offset.
  • Chunk. An immutable, Gorilla-compressed block of samples for one series over one time window.
  • Cold tier. Object-store-backed long-term storage for daily-compacted chunks.
  • Compaction. The background process converting WAL/head data into immutable chunk files (hourly) and merging small chunks into larger ones (daily).
  • Counter. A monotonically non-decreasing metric type.
  • Delta-of-delta. The second-order difference of consecutive timestamps, the basis of Gorilla's timestamp compression.
  • Discovery (service discovery). The pluggable mechanism (static/file/DNS/K8s) producing the scrape target list.
  • Federation. A pull query (/federate) composing the most-recent value across matching series, not a durable forward.
  • Gauge. A metric type whose value can move up or down arbitrarily.
  • Gorilla. The Facebook Pelkonen et al. 2015 in-memory time-series compression scheme (delta-of-delta timestamps + XOR values).
  • Head block. The in-memory, queryable, currently-being-appended-to store for the most recent time window.
  • Histogram. A metric type recording cumulative le-bucketed observation counts plus sum and count.
  • Instant vector. A PromQL result type: one value per series at a single timestamp.
  • Inverted index. The label-pair → series-ID-set structure enabling selective series lookup.
  • Label set. The canonical, sorted, deduplicated set of (name, value) pairs identifying a series.
  • Matcher. A label-pair predicate (=, !=, =~, !~) used in a PromQL vector selector.
  • Multi-tenancy. Storage-layer isolation of independent tenants' data (I7).
  • OpenMetrics. The CNCF successor exposition format to Prometheus text format.
  • PromQL. The Prometheus Query Language; this system's query language (ADR-05).
  • Pull (scrape). The default ingestion model: the system fetches /metrics from targets on its own schedule.
  • Push (remote-write). The secondary ingestion model: a producer sends samples to the system.
  • Range vector. A PromQL result type: a series of (value, timestamp) pairs over a duration, per series.
  • Recording rule. A periodically-evaluated rule whose result is written back to the TSDB as a new series.
  • Relabeling. Per-target label transformation applied before scrape (rename/drop/keep/shard).
  • Remote read. The protocol serving streamed sample chunks to an external reader.
  • Remote write. The protocol accepting pushed samples via Snappy-compressed Protobuf.
  • Reset detection. The rate()-time heuristic treating a counter decrease as a process restart.
  • Retention. The per-tenant duration after which chunks become eligible for deletion (I9).
  • Sample. A (series_id, timestamp_ms, value) triple.
  • Series. A unique time series identified by metric name + canonical label set.
  • Series ID. The 64-bit FNV1a hash of a canonical label set (I1).
  • Shard. An independent process/storage partition serving one or more tenants (never split across a single tenant, I7).
  • Stale marker. The reserved NaN bit-pattern signaling a series has ended (I11).
  • Summary. A client-aggregated quantile metric type (t-digest-backed).
  • Tenant. The unit of storage and query isolation (ADR-07, I7).
  • TSDB. Time-Series Database — this system's storage engine (head + WAL + chunks + index).
  • Vector matching. The PromQL rule set (one-to-one, ignoring/on, group_left/ group_right) governing how two vectors combine in a binary operation.
  • WAL (Write-Ahead Log). The append-only, checksummed, segmented durability log underlying crash recovery (I2, I4).
  • XOR encoding. Gorilla's value-compression technique: XOR each value with its predecessor and store only the changed bit window.
