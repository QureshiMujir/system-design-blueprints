Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same problem (not parameter tweaks). Each: sketch, winning regime, the real system embodying it, why this blueprint rejected it.

ALT-A — Term-At-A-Time (TAAT) with score accumulators. Instead of DAAT (all postings walked in lock-step by docId), process one term's entire posting list at a time, accumulating partial scores in a per-doc accumulator array, then sort accumulators for top-k.

  for each term t (rarest→common):
      for each (doc, tf) in postings(t):
          acc[doc] += contribution(t, doc)     # whole list, one term
  topk = partial_sort(acc, k)                   # after all terms

Winning regime: disjunctive queries over small/medium collections where the accumulator array fits in cache and you want simple, branch-predictable inner loops; also score-at-a-time variants with impact-ordered postings and early termination. Real system: classic TREC-era engines and Anh & Moffat impact-ordered designs; the framing in Turtle & Flood (P3). Why rejected here: the accumulator array is O(N) memory per query (100M docs/shard, §4) and TAAT does not naturally exploit the collector threshold for document skipping — DAAT + WAND/BMW prunes on θ as the heap fills (MM1), hitting the ≤ 20%-scored target (§4) that TAAT cannot. DAAT is the model in Phase 4/9/10.

ALT-B — Build the index too (own the codec, no index-api seam). Collapse the index-api boundary; the planner and a bespoke postings codec/IndexWriter are one coupled unit, with scorers inlined against the concrete posting format.

  IndexWriter ─▶ [own codec: postings + skip + block-max] ─▶ Searcher
       └────────────── one crate, no trait indirection ─────────┘

Winning regime: a single-product engine that will never swap formats and needs the last few percent of advance/block_max performance by inlining the concrete iterator (no vtable, no generic seam). Real system: Tantivy (R2) and Lucene (R1) both own their codecs. Why rejected here: it conflates two hard problems (index construction and query planning) and makes the planner untestable without a full indexer — the mock-index (Phase 0, MM6) and codec-agnostic IO-cost modeling depend on the ADR-02 seam. Index construction is an explicit non-goal (Goal §1). The "when rejected wins" cell of ADR-02 names this exact regime.

ALT-C — Selinger-style cost-based plan enumeration. Replace the heuristic rarest-first + strategy-threshold optimizer with full dynamic-programming enumeration of join/evaluation orders and strategies, costing each candidate plan and picking the global minimum.

  enumerate all evaluation orders × strategies → cost each → argmin
  (DP over subsets, à la System R join ordering)

Winning regime: complex relational queries with many joins where plan-space exploration pays off and queries are expensive enough to amortize a millisecond of planning. Real system: relational query optimizers (System R / its descendants in PostgreSQL etc.; the model in book B6). Why rejected here: boolean search queries are tree-shaped, not join-graphs; the optimizer must run in microseconds vs the query it optimizes (Phase 8's own Performance Concerns, 8.7), and rarest-first ordering plus a few strategy thresholds capture nearly all the available win (MM4). Full enumeration would blow the planning budget (HQ10) for negligible plan improvement. The plan cache (Phase 11) further amortizes the cheap optimizer to ~0.

ALT-D — Single fat index, no sharding (vertical-only). One enormous segment/searcher holds the whole collection on one very large machine; no scatter-gather, no global-IDF gather, no partial results.

  client ─▶ searchd ─▶ [one searcher: all docs, all segments] ─▶ ranked hits

Winning regime: collections that fit one machine's RAM/disk where avoiding cross-shard tail-latency (MM7) and global-IDF complexity is worth the vertical-scaling ceiling; also the embeddable library deployment (Goal §1) where there is exactly one shard. Real system: single-node PISA (R3) and any embedded Lucene/Tantivy use. Why rejected as the default here: DocId=u32 caps a segment at 2³¹ docs (ADR-04, HQ13) and §4 targets up to ~5B cluster docs, which no single node holds; so the design supports the single-shard case (it is literally fan-out 1) but builds scatter-gather (Phase 12) for the headline scale. This is the regime in ADR-13's "all-sync wins" cell.
