Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints table (§4). Formulas shown; inputs are §4 values.

  • C1 — Postings bytes per doc (per shard). 200 GB postings ÷ 100M docs/shard ≈ 2,000 bytes/doc of postings on average across all its terms. Frames the IO budget: the hot loop must skip most of this, not decode it (Phase 4 skip-list advance).

  • C2 — Average postings bytes per unique term. 200 GB ÷ 50M unique terms ≈ 4 KB/term average posting-list size. With a 128-doc block (§4), a 4 KB list is ~tens of blocks → skip-list jumps (Phase 4) save decoding ~all but the landed block.

  • C3 — Docs scored per pruned top-10 query. §4 sets WAND/BMW ≤ 20% of candidates scored. For a 3-term OR where each term has df ≈ 1M: full-OR candidate set ≈ |t1 ∪ t2 ∪ t3| ≤ 3M; pruned scoring ≤ 0.20 × 3M = 600K score calls, target ≥ 5× wall-time speedup (Phase 9/10). This is the headline efficiency metric (docs_scored / docs_matched).

  • C4 — Score-call budget at p50. p50 ≤ 5 ms (§4) for a warm 2–4 term top-10 query. If a BM25 score() + heap op costs ~50 ns (table-lookup norm, no pow/log in the loop, Phase 5), then 5 ms ÷ 50 ns = 100,000 score calls fit the p50 budget — consistent with pruning keeping scored docs in the 10⁴–10⁵ range, not the 10⁶ full-OR range. Confirms C3: without pruning, p50 is unattainable.

  • C5 — Single-node QPS vs core budget. §4: ≥ 2,000 simple QPS/node and thread pool = #cores. On a 16-core node, 2,000 QPS ÷ 16 cores = 125 queries/core/s → 8 ms/query/core of CPU budget for a simple query — leaving headroom under the 5 ms p50 for queueing and merge. Complex queries (≥ 300 QPS/node) get 16 cores ÷ 300 ≈ 53 ms·core budget, matching the heavier phrase+filter path.

  • C6 — Filter cache RAM ceiling. §4: filter cache default 10% of heap; Roaring ≈ 1 bit/doc worst case. For a 100M-doc shard, one dense filter bitmap ≈ 100M ÷ 8 = 12.5 MB; a 4 GB heap → 0.10 × 4 GB = 400 MB budget holds ≈ 400 MB ÷ 12.5 MB ≈ 32 dense filters (far more when sparse, since Roaring compresses). Sets the eviction pressure point (Phase 11, ADR-24).

  • C7 — Query cache footprint. §4: query cache default 1% of heap. A cached merged TopK of k=100 ScoreDoc{score:f32, doc:u64} ≈ 100 × 12 bytes ≈ 1.2 KB. A 4 GB heap → 0.01 × 4 GB = 40 MB → 40 MB ÷ 1.2 KB ≈ 33,000 cached top-100 results — ample for hot repeated queries, hence "conservative, disabled for heavy queries" (Phase 11).

  • C8 — Cross-shard fan-out bandwidth (query phase). §4: 50 shards, query phase returns top-k ids+scores only. For k=100: each shard returns 100 × 12 bytes ≈ 1.2 KB; full fan-out gather ≈ 50 × 1.2 KB = 60 KB per query — trivial. This is why query-then-fetch exists: the fetch phase moves real documents only for the global top-k, not 50× candidate sets (Scalability Analysis).

  • C9 — Tail-latency amplification at fan-out 50. Per MM7, if a single shard's p99 single-shard latency is 80 ms (§4) and shard latencies were independent, the probability all 50 beat 80 ms is 0.99^50 ≈ 0.61 — i.e. ~39% of queries would have some shard at its p99. This is exactly why §4 budgets cross-shard p99 at 150 ms (not 80 ms) and why partial results + hedging are mandatory (Principle 9, Phase 12), not optional.

  • C10 — Startup mmap/stat budget. §4: searcher open ≤ 500 ms/shard for 100M docs. Loading per-term stats for 50M terms in 500 ms demands 50M ÷ 0.5 s = 100M stat-entries/s — only feasible if stats are precomputed and mmap'd (read, not parsed), confirming the index-api "stats precomputed at index time" assumption (Core Types §11.8) and the ≤ 1 s RTO (§4).

  • C11 — Segment parallelism ceiling. §4: 10–100 segments/shard, one query ≤ #segments threads (bounded). On a 16-core node a single query uses ≤ 16 threads even at 100 segments, so segments are batched ~100 ÷ 16 ≈ 7 per thread → bounded per-query CPU, preventing one heavy query from starving the pool (ADR-12, Scalability Analysis scheduler saturation).

  • C12 — Deadline-check overhead amortization. §4: deadline checked at block boundaries (128 docs), default budget 1 s. A per-block check over a 600K-doc scored set (C3) is 600K ÷ 128 ≈ 4,700 checks — negligible vs per-doc checking (600K), which is exactly why the deadline is amortized per block, not per doc (Principle 8, INV-9, Phase 12).
