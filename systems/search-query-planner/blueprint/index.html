Project Name: Search Query Planner from Scratch

Owner: Mujir Qureshi

Status: specification — locked

1. Goal

Build a cost-based query planner + executor over an existing inverted index (Lucene / Tantivy-class). Pipeline, end to end:

query DSL text -> lexer -> query AST -> query-time analysis/rewrite -> logical plan
  -> cost-based optimization (rewrite/reorder/strategy select) -> physical plan (scorers/iterators)
  -> top-k execution with dynamic pruning -> collectors -> multi-segment / multi-shard merge -> ranked hits

The index is assumed to exist. We consume an index-api abstraction: postings lists, term dictionary (FST), doc-values columns, live-docs bitset, per-segment statistics. We do not build the indexer, analyzer training corpus, codec/compression, or storage engine.

Precise terms. Query planner = the component translating a parsed query into an executable physical plan and selecting an evaluation strategy by cost. Executor = the iterator/scorer machinery that walks postings and produces a ranked top-k. Dynamic pruning = skipping documents/blocks that provably cannot enter top-k (WAND, BlockMax WAND, MaxScore). Two-phase iteration = cheap approximation (superset) followed by exact confirmation.

System boundaries (in scope).

  • DSL lexing + parsing -> query AST (full grammar: terms, phrases, boolean, fields, ranges, wildcard, prefix, fuzzy, boost, grouping).
  • Query-time analysis (tokenize/lowercase/stem/stopword/synonym), rewrite/normalization (flatten, dedupe, NOT push-down, constant-score promotion).
  • Multi-term expansion (wildcard/prefix/fuzzy) via FST enumeration + Levenshtein automaton/DFA.
  • Logical plan + statistics/catalog (df, cf, doc-count, sum-tf, field norms summary).
  • Cost-based optimization: rarest-term-first ordering, clause cost model, strategy selection (bitset vs leap-frog iterator vs PQ disjunction).
  • Physical plan: DocIdSetIterator, Scorer, conjunction (leap-frog/galloping), disjunction (PQ), two-phase iterators.
  • Scoring: BM25 with k1/b, field norms, explain() tree.
  • Top-k collectors, heap, deterministic tie-break.
  • Dynamic pruning: WAND, BlockMax WAND, MaxScore.
  • Filters vs queries, ConstantScore, Roaring filter cache, query cache, eviction.
  • Phrase/positional queries with slop, positional two-phase.
  • Pagination (from/size, search_after), total-hit counting / track_total_hits.
  • Multi-segment parallel execution; multi-shard scatter-gather (query phase + fetch phase); partial results on timeout/shard failure.
  • Conformance + differential testing vs reference, fuzzing, perf regression.

Explicit non-goals.

  • NOT building the indexer / ingest pipeline — PhaseDeferred("Deferred Features Register") for index construction; we read a prebuilt index.
  • NOT building the analyzer corpus / stemmer training — we consume pluggable token filters; building stem dictionaries is out.
  • NOT a storage engine / codec — postings compression (Elias-Fano, PForDelta) is a property of index-api, treated as opaque; we model its IO cost only.
  • NOT a distributed control plane (cluster membership, shard allocation, replication) — coordinator assumes a static shard map.
  • NOT relevance-model research (LTR, neural rerank, dense vectors) — BM25 + boolean + phrase only; learning-to-rank is PhaseDeferred("Deferred Features Register").
  • NOT a SQL engine — DSL is a search-query language, not relational algebra.

Deployment model. Dual: (a) embeddable query library (crates/* linked into a host process holding the index in-process), and (b) query service (searchd HTTP/gRPC front, stateless query coordinator, talks to per-shard searchers). Same planner core in both.

Target users. Search-platform engineers embedding the planner; SREs operating searchd; relevance engineers tuning BM25/boosts via explain(); library consumers building vertical search.

Phase-0 numbered module list (crates).

  1. index-api — traits for postings, term dict (FST), doc-values, live-docs, statistics; in-memory mock-index impl + fixtures.
  2. query-parser — lexer + recursive-descent parser -> query AST; error recovery.
  3. query-ast — AST node catalog + visitor; pretty-printer.
  4. analysis — query-time token pipeline (tokenize/lowercase/stem/stopword/synonym).
  5. rewrite — normalization, flatten/dedupe, NOT push-down, constant-score promotion.
  6. expansion — wildcard/prefix/fuzzy term enumeration (FST walk + Levenshtein DFA).
  7. catalog — statistics provider (df, cf, doc-count, norms summary, selectivity est).
  8. planner — logical plan, cost model, optimizer, physical-plan builder.
  9. exec — DocIdSetIterator, conjunction/disjunction, two-phase, WAND/BMW/MaxScore.
  10. scoring — BM25/Similarity, Weight, explain() tree.
  11. collect — collectors, top-k heap, tie-break, total-hit counter.
  12. cache — Roaring filter cache, query cache, eviction.
  13. coordinator — segment parallelism + shard scatter-gather + partial results.
  14. searchd — service front (HTTP/gRPC), DSL endpoint, paging API.
  15. conformance / fuzz / benchmarks — differential vs reference, fuzz harness, perf gates.

What later phases unlock. P0 gives a queryable mock index + fixtures. P1–P3 give a full DSL front-end. P4–P7 give a correct (un-pruned) scoring executor. P8–P10 give cost-based planning and dynamic pruning (the performance payoff). P11–P13 give filters/caches, phrases, paging. P14 gives distribution. P15 locks correctness against a reference.

Deferred features. Index construction PhaseDeferred("Deferred Features Register"); postings codec internals PhaseDeferred("Deferred Features Register"); learning-to-rank / neural rerank PhaseDeferred("Deferred Features Register"); cross-cluster federation PhaseDeferred("Deferred Features Register"); persistent query result cache across restarts PhaseDeferred("Deferred Features Register"); geo/spatial queries PhaseDeferred("Deferred Features Register").

Estimated timeline. Phase-0 (modules 1–3, queryable skeleton + parser + fixtures): 6–9 weeks for one engineer. Through correct un-pruned executor (P0–P7): ~4 months. Full pruning + distribution + conformance (P0–P15): 8–11 months for a 2–3 engineer team.

Recommended language: Rust. Rationale in §9 ADR-01; summary: zero-cost iterator abstractions (the executor is iterators-on-iterators; trait objects + monomorphization avoid virtual-call tax on hot advance), cache-friendly struct layout (postings blocks, heap arrays), no GC pauses (tail-latency p99 is a hard target), exhaustive enum for plan nodes + match for the optimizer.

Prerequisites. Information retrieval (boolean + ranked retrieval, BM25, inverted files); data structures (heaps/priority queues, skip lists, tries/FSTs, Roaring bitmaps, finite automata/DFA); cost models + selectivity estimation (DB query-planner intuition); concurrency (work-stealing, scatter-gather, partial-result semantics); Rust (traits, lifetimes, enum-driven dispatch).

2. Why Build This

  • Unique knowledge taught. How a search engine actually executes a query — not the textbook BM25 formula, but the iterator algebra, dynamic pruning, and cost-based planning that make it fast over billions of docs. The gap between "score every doc" (O(N)) and "WAND skips 90%+" (sublinear in practice) is the entire game.
  • Historical / architectural significance. WAND (Broder 2003) and BlockMax WAND (Ding & Suel 2011) are the algorithms behind Lucene/Elasticsearch/Solr at planetary scale. MaxScore (Turtle & Flood 1995) predates them. Understanding why scorer upper-bounds must be true upper bounds (a single safety invariant) is what separates a correct pruning engine from one that silently drops results.
  • Engineering muscles. Iterator/trait design under tight latency budgets; cost-model design and selectivity estimation (DB-grade planning); priority-queue and heap discipline; finite-automata construction (Levenshtein DFA); cache-aware data layout; scatter-gather distributed execution with partial-result correctness; differential testing against a mature reference.
  • Production engineering concepts exercised. Tail-latency control; backpressure/timeout budgets; cache eviction under memory pressure; deterministic tie-break for stable pagination; deep-paging cost; partial-result degradation; observability of a query's chosen plan (explain() + plan dump).
  • Cross-links. Compilers (parser -> AST -> logical -> physical plan is exactly a compiler pipeline; the optimizer is a rewrite-rule engine). Databases (cost-based optimization, selectivity, push-down, the bitset-vs-iterator choice mirrors index-scan-vs-seq-scan). Distributed systems (scatter-gather, partial results, the two-phase query/fetch protocol). Observability stacks (an inverted index is a log-search backend). Storage engines (postings IO cost model echoes LSM read amplification).
  • Calibration value. After this you can reason about any search system's latency profile, debug a "why is this query slow" incident by reading a plan dump, and know precisely which knob (rarest-first ordering, block-max threshold, filter cache) to turn. It permanently upgrades intuition for cost-based execution in general.

What Mastery Looks Like. After building this, the engineer can:

  • Prove a pruning algorithm safe. State and defend the upper-bound contract (max_score()/block_max_score() ≥ any real score, INV-1) and explain exactly why a single loose-but-valid bound is correct while a single too-tight bound silently corrupts top-k — the central skill cemented in Phase 9 — Dynamic Pruning: WAND and Phase 10 — BlockMax-WAND + MaxScore.
  • Read a plan dump and predict latency. Look at a chosen physical plan (lead order, strategy, prune mode, est-vs-actual cardinality) and say which clause dominates and which knob fixes it — the literacy built in Phase 8 — Cost Model + Logical→Physical Planner.
  • Derive BM25 from first principles and bound it. Reproduce the score, explain k1/b saturation and length-norm, and compute a true tight upper bound from term stats — from Phase 5 — BM25 Scoring, Weight Factory, Top-K Collector.
  • Design an iterator algebra under a latency budget. Reason about leap-frog/galloping, two-phase superset semantics (INV-5), and skip-list advance amortization — from Phase 4 — Physical Iterator Operators and Phase 12 — Phrases (two-phase).
  • Estimate selectivity and order joins. Apply rarest-first ordering, the independence assumption and its failure on correlated terms, and know when it costs latency vs correctness (Principle 7) — from Phase 7 — Statistics / Catalog + Selectivity and Phase 8.
  • Engineer a correctness-neutral cache. Generation-key every cached bitset/result so a cache hit always equals recomputation (INV-6/INV-13) — from Phase 11 — Filters, Facets, Predicate Pushdown, Caching.
  • Run a distributed top-k correctly under failure. Build scatter-gather query-then-fetch with mergeable per-shard top-k (INV-11) and partial-result degradation over fail-closed (Principle 9, INV-9) — from Phase 12 — Distribution.
  • Gate pruning on an exact oracle forever. Keep the exhaustive DAAT baseline as a permanent --exact differential and shadow canary so no optimization ever ships an undetected ranking regression — the discipline established in Phase 5 and enforced through Phase 12 — Conformance.

One paragraph per box.

(A) Lexer. Converts DSL text into a token stream (terms, operators + - AND OR NOT, field separators :, quote ", range brackets [ ] { }, TO, wildcard * ?, fuzzy ~, boost ^, parens, whitespace). Tracks byte spans for error reporting. Handles escaping (\:, \"). Pure, deterministic, no index access. Owns no state beyond the cursor.

(B) Parser. Recursive-descent + Pratt precedence for boolean operators; produces the query AST (§8). Resolves operator precedence (NOT > AND > OR; explicit grouping overrides), default operator (OR or AND configurable), +/- must/must-not semantics. Error recovery: on malformed token, emits a diagnostic with span and attempts resync at the next clause boundary. No analysis yet — terms are raw.

(C) Query-time analysis. Applies the field's analyzer chain to term/phrase text: tokenize, lowercase, stem, stopword removal, synonym expansion. A single TermQuery("running") may become TermQuery("run") (stemming) or a synonym SynonymQuery/disjunction. Must mirror index-time analysis or recall breaks. Stateless given the analyzer config; reads no postings.

(D) Rewrite/Normalize. Algebraic simplification on the analyzed AST: flatten nested booleans of same type, dedupe identical clauses, push NOT down (De Morgan where it lowers cost), drop empty clauses, promote subtrees that don't need scoring into ConstantScoreQuery. Idempotent rewrite-rule engine; each rule is cost-monotone or cost-neutral. Pure AST->AST.

(E) Expansion. Turns multi-term queries (wildcard te*, prefix, fuzzy term~2) into concrete term sets by walking the term dictionary FST under an automaton (prefix DFA, Levenshtein-k DFA). Bounds expansion (max-expansions); above the bound, rewrites to ConstantScoreQuery over a bitset to avoid scoring blow-up. Reads the term dictionary (an index-api call) but not postings.

(F) Statistics / Catalog. Per-collection and per-term stats: doc-count N, document frequency df(t), collection frequency cf(t), sum of doc lengths, average field length, field norms summary. Source: index-api (precomputed at index time). Feeds IDF (scoring), selectivity (optimizer), and clause cost. Read-mostly, cached per searcher generation.

(G) Logical planner. Lowers the rewritten AST into a logical operator tree (LogicalScan(term), LogicalAnd, LogicalOr, LogicalNot, LogicalConstantScore, LogicalPhrase). Decouples what (logical) from how (physical). Annotates each node with estimated cardinality from (F).

(H) Cost-based optimizer. Rewrites/reorders the logical plan to minimize estimated cost: orders conjunction children rarest-first (lowest df leads, drives leap-frog), chooses per-node physical strategy (sorted bitset intersection vs leap-frog iterator vs PQ disjunction vs MaxScore), decides whether a clause is a filter (cacheable bitset, no score) or a scored query, and selects the pruning algorithm (WAND vs BMW vs MaxScore vs none). Uses a clause cost model (Phase 8). Produces an annotated physical plan request.

(I) Physical plan builder. Instantiates concrete Scorer/DocIdSetIterator objects from the optimized plan: Bm25Scorer leaves, ConjunctionIterator (leap-frog), DisjunctionIterator (PQ), WandScorer/BlockMaxWandScorer/MaxScoreScorer, TwoPhaseIterator wrappers for phrases/expensive predicates, ConstantScoreScorer for filters. Binds postings handles from index-api. Per segment.

(J) Executor. Drives the iterator tree to completion per segment. DocIdSetIterator advances monotonically (next_doc, advance(target)). Conjunctions leap-frog (advance the lead, sync others, gallop). Disjunctions merge via a PQ keyed by docId. Two-phase iterators do cheap matches()/approximation() then expensive confirm(). Dynamic pruning (WAND/BMW/MaxScore) uses scorer upper bounds + the collector's current min-competitive score to skip docs/blocks. Single-threaded per segment; parallel across segments.

(K) Scoring. Computes per-doc relevance: BM25 with parameters k1, b, IDF form, doc-length norm (field norm, quantized). Each Scorer exposes score(), max_score() (a true upper bound — safety invariant), and block-level block_max_score() for BMW. explain() produces a tree of score contributions for debugging/tuning. Composed bottom-up matching the iterator tree.

(L) Collector / top-k heap. Maintains the running top-k via a min-heap of size k keyed by (score, docId). Exposes the current min-competitive score (heap root) back to (J) so pruning can raise its threshold as the heap fills. Tie-break deterministically by ascending docId (or a configured secondary sort). Also counts total hits subject to track_total_hits (exact, capped, or approximate via early termination).

(M) Segment/shard coordinator. Within a node: schedules per-segment executor tasks across a thread pool, merges segment top-ks into a node top-k. Across nodes: the query phase scatters the query to each shard, gathers per-shard top-k doc ids + scores, merges to a global top-k; the fetch phase asks the owning shards for the actual documents/fields of the global top-k. On timeout or shard failure, returns partial results with a partial: true flag and which shards were missing.

(N) Caches. Filter cache: Roaring bitmaps of doc-id sets for cacheable filter clauses (e.g. status:active), keyed by (segment-generation, filter), cost-aware LRU eviction. Query cache: optional cache of fully-scored top-k per (query, shard, generation) for repeated queries; conservative, invalidated on generation bump. Both bounded by a memory ceiling (§4).

4. System Constraints

Quantified engineering targets. These are the contract the design optimizes against.

Dimension Target
Index size (per shard) up to 100M docs; up to 50M unique terms; postings up to ~200 GB on disk
Index size (cluster) up to 50 shards -> ~5B docs
Segments per shard 10–100 (post-merge); planner must parallelize across them
Query latency p50 ≤ 5 ms (warm cache, 2–4 term boolean, top-10, single shard)
Query latency p95 ≤ 25 ms (single shard); ≤ 60 ms (cross-shard scatter-gather)
Query latency p99 ≤ 80 ms single shard; ≤ 150 ms cross-shard; hard cap via timeout budget
QPS (per node) ≥ 2,000 simple queries/s; ≥ 300 complex (phrase + filters) /s
Top-k sizes k ∈ {10, 100, 1000}; deep paging beyond 10k discouraged -> search_after
Postings IO block-decode amortized ≤ 64 docs/decode; skip-list jumps to avoid full decode
Pruning speedup WAND/BMW must evaluate ≤ 20% of candidate docs vs full OR for top-10 on typical queries; target ≥ 5× wall-time speedup
Filter cache memory ceiling configurable, default 10% of heap/RSS; Roaring keeps it ~1 bit/doc worst case, far less when sparse/dense
Query cache memory default 1% of heap; disabled for non-deterministic/heavy queries
Timeout budget per-request deadline (default 1 s), propagated to every shard + every segment task; checked at block boundaries
Startup time searcher open (mmap + stats load) ≤ 500 ms per shard for 100M docs
Shutdown drain in-flight queries ≤ deadline, then hard cancel; no torn cache state
Concurrency per-node thread pool = #cores; one query may use ≤ #segments threads (bounded)
CPU/cache hot loop (advance + score) fits L1/L2; postings block = 128 docs (cache-line friendly)
NUMA pin searcher + its segments to a NUMA node; avoid cross-node postings reads
Network RTT (cross-shard) assume 0.2–1 ms intra-DC; scatter-gather fanout = #shards
File descriptors mmap-based; FD budget = O(#segments × #files-per-segment); cap via merge policy (out of scope)
Availability query service target 99.9%; degrade to partial results rather than fail closed
Recovery (RTO) searcher reopen on new generation ≤ 1 s; no query-path persistent state to recover
Horizontal scaling add shards -> scatter-gather fanout grows; coordinator is stateless, scales with replicas
Vertical scaling more cores -> more segment parallelism + more concurrent queries

6. Design Principles

Each: bold title — explanation; tradeoff; operational implication; violation example.

  1. Correctness before speed; pruning must be provably safe. Dynamic pruning may skip a doc only if it provably cannot enter top-k. Tradeoff: safe upper bounds are looser than exact, so fewer skips. Operational: a --exact flag disables all pruning to A/B verify results. Violation: a scorer whose max_score() underestimates -> WAND skips a true top-k hit -> silent recall loss (the worst class of bug).

  2. Scorer upper bounds are a contract, not a hint. max_score() (and block_max_score()) MUST be ≥ any real score the scorer can produce for any doc (in the block). Tradeoff: computing tight-yet-safe bounds is subtle (BM25 monotonicity). Operational: invariant check INV-1 fuzzes score ≤ max_score on every doc in conformance. Violation: see #1.

  3. Iterators advance monotonically. next_doc/advance(target) never go backward; advance(t) lands on the first doc ≥ t. Tradeoff: forces leap-frog/galloping discipline; no random access. Operational: debug assertions on doc-id monotonicity in dev builds. Violation: non-monotonic advance -> conjunction sync loops forever or skips matches.

  4. Determinism: identical query + identical index generation -> identical ranked ids and scores. Tie-break by ascending docId. Tradeoff: secondary sorts cost a comparator. Operational: stable pagination depends on this; search_after correctness relies on it. Violation: nondeterministic tie-break -> the same doc appears on two pages or is skipped.

  5. Two-phase approximation is always a superset. A TwoPhaseIterator's approximation must match a superset of true matches; confirm() removes false positives. Tradeoff: approximation cost vs how many false positives confirm must reject. Operational: phrase queries, expensive predicates use this. Violation: approximation missing a true match -> recall loss that pruning cannot detect.

  6. Filters do not score. A clause used only to constrain (not rank) is evaluated as a 0/1 bitset and contributes constant score. Tradeoff: must classify clauses (filter vs query) correctly in the optimizer. Operational: filters are cacheable (Roaring); queries generally are not. Violation: scoring a filter wastes CPU and pollutes relevance; caching a scored query returns stale scores.

  7. Cost estimates drive ordering, never correctness. A wrong cost estimate yields a slower plan, never a wrong result. Tradeoff: invest in good df-based estimates but never let them gate output. Operational: a bad estimate is a perf incident, debuggable via plan dump; not a correctness incident. Violation: conflating "estimated empty" with "is empty" -> dropping a clause.

  8. Bounded resource usage; every loop has a deadline. Timeout budget propagates to every shard and every segment task; checked at block boundaries. Tradeoff: deadline checks add a branch in the hot loop (amortized per block, not per doc). Operational: partial results on deadline, never a hung query. Violation: an unbounded fuzzy expansion or deep-page sort OOMs or stalls the pool.

  9. Backpressure + partial results over failure. A slow/failed shard degrades the result (flagged partial), it does not fail the request. Tradeoff: callers must handle partial results. Operational: SLO favors availability; partial is a first-class field + metric. Violation: fail-closed on one slow shard -> whole-query unavailability.

  10. Observability by default: every query can explain its plan and its score. explain() for scores; plan dump for the chosen physical plan + costs + pruning mode. Tradeoff: explain path is slower; gated by a request flag. Operational: "why is this slow / why did this rank here" is answerable without a debugger. Violation: opaque planner -> unfixable relevance/latency incidents.

  11. Analysis parity: query-time analysis must match index-time analysis. Same tokenizer/stemmer/normalizer or recall silently drops. Tradeoff: analyzer config is shared state between indexer (out of scope) and planner. Operational: analyzer version stamped in catalog; mismatch warns. Violation: query stems "running"->"run" but index stored "running" -> zero matches.

  12. Plan nodes are an explicit, exhaustive type. Logical and physical plans are enums; the optimizer is a total match. Tradeoff: adding a node touches all match sites (compiler-enforced completeness — a feature). Operational: no "unknown node" runtime path. Violation: stringly-typed plans -> silent mishandling of a new node.

  13. Segment isolation; merge is the only cross-segment step. Each segment executes independently to a local top-k; the coordinator merges. Tradeoff: per-segment overhead (small heaps) vs trivial parallelism + isolation. Operational: one corrupt/slow segment is contained. Violation: shared mutable scorer across segments -> data races, nondeterminism.

  14. Caches are correctness-neutral and generation-keyed. A cache hit must equal recomputation; all caches key on the immutable searcher generation. Tradeoff: generation bump invalidates caches (cold start). Operational: never serve a cached bitset/score from a stale generation. Violation: reusing a filter bitmap across a generation that deleted docs -> returns deleted docs.

  15. Reference-equivalence is the bar. For the supported query subset, results must match a reference engine (Lucene/Tantivy) modulo documented score-formula differences. Tradeoff: constrains scoring-formula freedom. Operational: differential tests gate release (Phase 12). Violation: "looks reasonable" scoring with no oracle -> undetectable ranking regressions.

7. System Invariants

Each: statement — why · where enforced · detection · telemetry · recovery · debugging.

  • INV-1 — Scorer upper-bound safety. score(d) ≤ max_score() for all d; score(d) ≤ block_max_score(block(d)) for all d in block. Why: WAND/BMW correctness — pruning uses these bounds. Where: Scorer impls; checked in conformance + dev assertions. Detection: fuzz harness scores every doc and compares; max_score < observed triggers a hard fail. Telemetry: inv1_violations_total (must be 0). Recovery: disable pruning (--exact) for the affected query class; fix bound. Debugging: dump the doc, its computed score, the claimed max, the term stats feeding the bound.

  • INV-2 — Advance monotonicity. For any iterator, successive doc_id() values are strictly increasing; advance(t) returns the first d ≥ t (or NO_MORE_DOCS). Why: conjunction/disjunction sync correctness. Where: all DocIdSetIterator impls. Detection: dev-build assertion new_doc > prev_doc; conformance replays. Telemetry: iter_monotonicity_violations_total. Recovery: none at runtime (it is a logic bug); fail fast in dev. Debugging: log the iterator type + (prev, new, target).

  • INV-3 — Top-k completeness under pruning. The top-k returned with pruning equals the top-k returned without pruning (same ids, same scores, same order), given INV-1. Why: pruning is an optimization, not a semantic change. Where: executor + collector. Detection: differential test pruned-vs-exact on every fixture. Telemetry: pruned_vs_exact_mismatch_total. Recovery: --exact fallback. Debugging: re-run both modes, diff heaps doc-by-doc, find the first divergence.

  • INV-4 — Deterministic tie-break. Equal scores break by ascending docId (then configured secondary key); same input -> same output ordering. Why: stable pagination / search_after. Where: collector comparator. Detection: run query twice, byte-compare result ids. Telemetry: nondeterministic_result_total. Recovery: none (logic bug). Debugging: inspect comparator and heap pop order.

  • INV-5 — Two-phase superset. A two-phase approximation matches ⊇ true matches; matches() only ever removes, never adds. Why: no true match may be dropped pre-confirmation. Where: TwoPhaseIterator impls (phrase, expensive filter). Detection: differential vs a brute-force exact matcher on fixtures. Telemetry: twophase_false_negative_total (must be 0). Recovery: fall back to exact (non-two-phase) matcher. Debugging: dump approximation set vs exact set difference.

  • INV-6 — Generation immutability of caches. A cache entry is valid only for the generation it was computed under; reads check generation. Why: deleted/updated docs must not resurface. Where: cache crate keys. Detection: assert entry-generation == reader-generation on hit. Telemetry: cache_stale_generation_hits_total (must be 0). Recovery: drop the entry, recompute. Debugging: log (key, entry_gen, reader_gen).

  • INV-7 — Score non-negativity & finiteness. Every score is finite and ≥ 0 (BM25 with standard params). Why: heap comparisons + threshold math assume finite, ordered, non-negative. Where: Bm25Scorer. Detection: assert score.is_finite() && score >= 0 in dev. Telemetry: score_nan_or_neg_total. Recovery: clamp + log (last resort); root-cause the stat (e.g. negative IDF from df>N). Debugging: print df, N, tf, norm.

  • INV-8 — Live-docs honored. Deleted docs (live-docs bitset = 0) never appear in results. Why: deletes are logical until merge; query must filter them. Where: leaf iterators wrap live-docs; or a final filter. Detection: fixture with deletes; assert none returned. Telemetry: deleted_doc_returned_total (must be 0). Recovery: re-apply live-docs filter. Debugging: check the live-docs bitset for the segment + the leaf wrapper.

  • INV-9 — Timeout budget monotonicity. Once a deadline passes, no new block is decoded; the query returns partial. Why: bounded latency (§4). Where: executor block-boundary check + coordinator. Detection: inject tiny deadline, assert partial=true and bounded work. Telemetry: deadline_exceeded_total, partial_results_total. Recovery: return what is collected, flag partial. Debugging: trace deadline propagation + last-checked timestamp.

  • INV-10 — Plan determinism given stats. The optimizer produces the same physical plan for the same logical plan + same stats snapshot. Why: reproducible perf, debuggable plan dumps. Where: planner (pure function of inputs). Detection: plan twice, compare plan dump. Telemetry: plan_nondeterminism_total. Recovery: none (logic bug). Debugging: diff plan dumps; check for nondeterministic map iteration / hashing.

  • INV-11 — Shard result mergeability. Per-shard top-k are independently sorted by (score, shard-local global docId mapped to a global id) such that a k-way merge yields the global top-k. Why: scatter-gather correctness. Where: coordinator merge. Detection: compare scatter-gather result to a single-shard "fat" index of the same docs. Telemetry: shard_merge_mismatch_total. Recovery: re-fetch; flag partial. Debugging: dump per-shard top-k + merged top-k.

  • INV-12 — Field-norm consistency. The norm used in scoring matches the norm stored at index time for that (doc, field). Why: BM25 length normalization correctness + analysis parity. Where: scoring reads norms via index-api. Detection: explain() shows norm; compare to expected for a fixture doc. Telemetry: norm_mismatch_total. Recovery: reload norms; check analyzer version. Debugging: compare quantized norm byte to expected.

  • INV-13 — Cache correctness (hit == recompute). A cache hit (filter bitset or query top-k) is bit-for-bit indistinguishable from a fresh recomputation under the same generation. Why: a cache must add no semantics (Principle 14) — it is either fully transparent or a correctness bug. Where: cache crate (FilterCache/QueryCache lookups). Detection: randomized differential — force-recompute a sampled cache-hit key and diff against the served value. Telemetry: cache_correctness_mismatch_total (must be 0). Recovery: evict the offending entry, recompute, alarm. Debugging: replay the query with caching disabled and diff against the cached result.

8.2 EBNF Grammar

query        = disjunction ;
disjunction  = conjunction , { "OR" , conjunction } ;          (* default op configurable *)
conjunction  = unary , { [ "AND" ] , unary } ;                 (* juxtaposition = default op *)
unary        = [ occur ] , boostable ;
occur        = "+" | "-" | "NOT" ;                             (* + must, - / NOT must_not *)
boostable    = primary , [ "^" , float ] ;
primary      = group | fielded | clause ;
group        = "(" , query , ")" ;
fielded      = field , ":" , ( group | clause ) ;
field        = identifier ;
clause       = phrase | range | term_clause | matchall ;
matchall     = "*" ;
phrase       = '"' , { token } , '"' , [ "~" , uint ] ;        (* ~slop *)
range        = ( "[" | "{" ) , range_end , "TO" , range_end , ( "]" | "}" ) ;
range_end    = term | "*" ;                                    (* * = unbounded *)
term_clause  = term , [ fuzzy | wildcard_marker ] ;
fuzzy        = "~" , [ uint ] ;                                (* default 2, clamp ≤2 *)
term         = identifier_with_wildcards ;                     (* may contain * ? -> wildcard/prefix *)
float        = digit , { digit } , [ "." , { digit } ] ;
uint         = digit , { digit } ;
identifier   = letter , { letter | digit | "_" | "." | "-" } ;

Precedence (high->low): grouping/field-scope > boost ^ > unary occur (+ - NOT) > implicit/AND > OR. Default operator (when two clauses are juxtaposed with no operator) is configurable: OR (Lucene default) or AND (more precise). Locked default: OR, overridable per request.

8.3 Query AST Catalog

AST node Fields Scored? Notes
MatchAllQuery (boost) constant matches every live doc
TermQuery field, term yes (BM25) leaf; the workhorse
PhraseQuery field, [terms], slop yes positional; two-phase
BooleanQuery [(occur, sub)], minShouldMatch yes occur ∈ {MUST,SHOULD,MUST_NOT,FILTER}

occur semantics inside BooleanQuery:

  • MUST (+): must match; contributes to score. AND lowers to all-MUST.
  • SHOULD: optional; contributes to score; minShouldMatch controls how many SHOULD must match (default 0 if any MUST present, else 1).
  • MUST_NOT (-/NOT): must not match; no score; excludes.
  • FILTER: must match; no score (constant); cacheable. Produced by the optimizer from non-scoring constraints.

8.4 Rewrite / Normalization Rules (analyzed AST -> normalized AST)

Rule Transform Guard
RW-1 analyze term/phrase text -> analyzer tokens (lowercase/stem/stop/synonym) per field analyzer
RW-2 flatten BooleanQuery whose child is same-occur BooleanQuery -> merge only MUST∪MUST, SHOULD∪SHOULD
RW-3 dedupe identical sibling clauses collapse (sum boosts) structural equality
RW-4 NOT push-down NOT (A OR B) -> NOT A AND NOT B (De Morgan) only if it lowers estimated cost
RW-5 single-clause unwrap BooleanQuery with one MUST/SHOULD -> the clause preserve boost
RW-6 empty drop clause that analyzed to empty (all-stopwords) -> remove warn if whole query empties
RW-7 const-score promote WildcardQuery/PrefixQuery/RangeQuery exceeding maxExpansions -> ConstantScoreQuery over bitset expansion > threshold

8.5 Expansion (multi-term) — worked

title:te* (prefix) -> walk term-dict FST from prefix te -> enumerate {tea, team, tech, ...} -> if count ≤ maxExpansions: BooleanQuery(SHOULD: TermQuery(tea), TermQuery(team), ...) (each scored, blended); else: ConstantScoreQuery over the union bitset (no per-term scoring; one constant score).

name:jon~2 (fuzzy, maxEdits=2) -> build Levenshtein-2 DFA for jon -> intersect DFA with term-dict FST -> enumerate terms within edit distance 2 {jon, john, joan, jan, ...} -> bounded the same way; scores blended, optionally distance-weighted boost.

ADR-10 Term dictionary FST (minimal acyclic FSA) via index-api Hash map, sorted block Prefix/wildcard/fuzzy enumeration by automaton intersection (Daciuk 2000; Phase 3); compact A hash map wins when the workload is exact-term lookup only (no prefix/wildcard/fuzzy) and O(1) point lookup beats the FST's byte-walk; a sorted block index wins when the term dict is too large to hold the FST in RAM and you accept block-seek + binary-search from disk
ADR-11 Fuzzy matching Levenshtein automaton (DFA), max edits = 2 Trie + DP per term, BK-tree Linear scan of FST under DFA (Schulz&Mihov 2002); bounded edits keeps DFA small BK-tree wins for a standalone spell-corrector over a modest lexicon (no inverted index to intersect against), where metric-tree pruning beats building a DFA per query; trie + per-term DP wins when edit distances exceed 2 (DFA state blow-up) and the candidate set is already small
ADR-12 Concurrency model Per-segment task on a work-stealing pool (rayon-style); per-query thread budget bounded One thread/query, async runtime Segment parallelism is embarrassingly parallel; bounded threads prevent pool starvation; sync code, no async coloring on hot path An async runtime wins when postings live on remote/object storage so the executor is IO-bound (overlapping thousands of in-flight fetches beats blocking threads); one-thread-per-query wins for a low-QPS embedded library where pool machinery is overkill and simplicity wins
ADR-13 Coordinator transport (service) tokio async for searchd front + shard fanout; sync executor inside All-sync, all-async Async only at the IO/fanout boundary (scatter-gather, timeouts); CPU executor stays sync All-async wins once even leaf postings access is remote (the executor itself becomes IO-bound, §4 NUMA assumption breaks); all-sync wins for a single-shard embedded deployment with no network fanout, where a thread-per-request server is simpler and the tokio reactor is dead weight
ADR-14 Tie-break / determinism Ascending docId secondary key, baked into collector comparator Insertion order, score-only INV-4 stable pagination; search_after correctness Score-only (no secondary key) wins when results are never paginated and a stable total order is not required (one-shot top-k where ties may break arbitrarily) — it skips the docId comparator; insertion order wins for a debug/trace mode that must reflect raw collection order
ADR-15 Error model thiserror enums per crate; coded diagnostics (E-LEX/E-PARSE/E-SEM/E-RESOURCE); no panics on user input anyhow everywhere, panics Typed, matchable, coded errors; parser recovers not panics (Domain Model §8.7); panic = abort only on invariant breach anyhow wins in throwaway tooling and the tools//scripts/ glue where no caller matches on error variants and a stack-trace-with-context is all you need; the per-crate enum boilerplate is pure overhead there
ADR-16 Serialization (DSL JSON) serde + serde_json Hand-rolled Mature; JSON DSL <-> AST round-trips; request/response (RFC 8259) A hand-rolled parser wins only if JSON parsing is profiled as the request bottleneck (megabyte-scale DSL payloads at very high QPS) and a zero-copy/SIMD JSON path (simd-json-class) beats serde_json — otherwise serde always wins on safety and maintenance
ADR-17 Numeric range encoding Points/BKD via index-api; fallback term-range expansion Always term expansion Dense numeric ranges as bitset filter; avoid huge term enumeration Always-term-range wins when index-api exposes no points/BKD structure (a text-only codec) and the numeric field has low cardinality, so enumerating the term range is cheaper than maintaining a separate point tree
ADR-18 Heap / top-k structure Fixed-capacity binary min-heap (size k), root = min-competitive Sorted insert, full sort at end O(log k) insert; root feeds pruning threshold (P7/P9); standard TopScoreDocCollector shape Sorted insert / full-sort-at-end wins for tiny k (≤4) where a branchless linear scan beats heap sift, and for count-only queries (k=0) where no ordered structure is needed at all
ADR-19 Build / workspace Cargo workspace, one crate per module (§1) Single crate Compile isolation, clear API seams, per-crate fuzz/bench A single crate wins for a small embedded build where cross-crate generic monomorphization and many Cargo.tomls slow compiles, and where the API-seam discipline of separate crates is not worth the link-time and feature-flag plumbing
ADR-20 Min Rust version (MSRV) Pinned MSRV (stable, edition 2021), rust-toolchain.toml Track nightly Reproducible builds; nightly only behind a feature for SIMD intrinsics Tracking nightly wins for a research fork that needs portable-SIMD / specialization / generic-const features now and controls its own deploy toolchain, trading reproducibility for capability (the PISA-style perf-research regime)
ADR-21 SIMD intersection std::simd/intrinsics behind a feature flag; scalar fallback default Always SIMD, never SIMD Optional fast sorted-int intersection (Lemire 2016) for bitset strategy (Phase 8); portability via fallback Always-SIMD wins on a fixed, known target ISA (AVX-512 fleet) where dense sorted-int intersection is the proven hot loop and the scalar path is dead weight; never-SIMD wins when galloping over sparse skip-listed postings is the only access pattern and intersection never dominates
ADR-22 Observability tracing spans + structured fields; plan dump + explain() as first-class outputs log only, ad-hoc prints Per-query plan/score introspection (Principle 10); metrics counters named per invariant Plain log wins for the embedded library mode with no service surface, where per-query span trees are noise and a consumer just wants a log line — the tracing subscriber machinery is overhead with no collector attached
ADR-23 Config Typed config struct, per-request overrides (default-op, k1/b, maxExpansions, timeout, track_total_hits) Global mutable statics Determinism (INV-10); per-request tuning without redeploy Global statics win for a single-tenant appliance with one fixed config for the process lifetime, where threading a &QueryConfig through every call is pure ceremony and per-request overrides are never used
ADR-24 Memory accounting Explicit byte budgets for caches + expansion (circuit breaker) Trust the allocator Bounded usage (Principle 8); reject (E-RESOURCE-*) before OOM Trusting the allocator wins in a trusted single-user embedded context with no adversarial queries and ample headroom, where the budget-accounting branches add latency for a DoS class that cannot occur
ADR-25 Test oracle Differential vs Lucene + Tantivy on a shared fixture index; brute-force exact matcher for INV-3/INV-5 Self-consistency only Reference-equivalence is the bar (Principle 15); pruned-vs-exact internal oracle Self-consistency-only wins when no reference engine implements your exact scoring/semantics (a novel Similarity with no Lucene equivalent) — then the brute-force exact matcher is the only oracle and external differential would just flag intended formula differences

11. Core Schema and Core Types

Normative signatures only (CRITICAL RULE 10 — no implementations). Each block: ownership · mutation · concurrency · persistence · serialization · compatibility. Rust-flavoured pseudosignatures; field types indicative.

11.1 Identifiers, sentinels, scalars

type DocId = u32;                 // ADR-04; 0..N-1 per segment
const NO_MORE_DOCS: DocId = u32::MAX;   // iterator exhaustion sentinel
type GlobalDocId = u64;           // (shard_id<<48) | (segment_ord<<32) | local DocId
type Generation = u64;            // monotonic searcher generation; cache key (INV-6)
type Score = f32;                 // BM25 output; finite, >= 0 (INV-7)
type FieldId = u16;               // resolved field handle (schema lookup)
type TermBytes = Box<[u8]>;       // analyzed term, UTF-8 NFC
  • Ownership: value types, Copy where small. GlobalDocId constructed only at the coordinator merge boundary (INV-11). Mutation: none (immutable scalars). Concurrency: Send + Sync, shared freely. Persistence: none (runtime). Serialization: GlobalDocId/Score cross the wire in protobuf (ADR-09); DocId never leaves a segment. Compatibility: DocId=u32 is a hard ABI assumption of index-api; widening to u64 is a breaking change.

11.4 Logical & physical plan (planner::logical, planner::physical)

enum LogicalOp {

  • Ownership: plans owned by value, built by the optimizer, consumed by the physical builder. Mutation: immutable after build (INV-10 determinism). Concurrency: a physical plan is cloned per segment (postings handles rebound to that segment); never shared mutably across segment threads (Principle 13). Persistence: plan dump (text/JSON) for observability only — not executed from disk. Serialization: dump.rs emits a stable plan-dump format (versioned, Compatibility §). Compatibility: enum exhaustiveness (Principle 12) — adding a variant is a compile-time fan-out; plan-dump format is versioned independently of the API.

11.5 Iterator core (exec::disi)

trait DocIdSetIterator {
    fn doc_id(&self) -> DocId;                 // current; NO_MORE_DOCS if exhausted
    fn next_doc(&mut self) -> DocId;           // advance to next match (INV-2)
    fn advance(&mut self, target: DocId) -> DocId; // first match >= target (INV-2)
    fn cost(&self) -> u64;                      // est. #docs (drives ordering)
}
trait TwoPhaseIterator {
    fn approximation(&self) -> &dyn DocIdSetIterator; // superset (INV-5)
    fn matches(&mut self) -> bool;             // confirm current doc (may remove)
    fn match_cost(&self) -> f32;               // est. confirm cost
}
  • Ownership: iterators own their postings cursors (&mut self advance). Mutation: stateful cursor; single-threaded per segment. Concurrency: !Sync by design — never share an iterator across threads. Persistence: none. Serialization: none. Compatibility: this trait is the executor's central ABI; cost() is advisory (Principle 7); changing advance semantics is a major break.

11.6 Conjunction / Disjunction (exec::conjunction, exec::disjunction)

struct ConjunctionIterator { lead: Box<dyn DocIdSetIterator>,        // rarest (lowest cost)
                             others: Vec<Box<dyn DocIdSetIterator>>, // sorted by cost asc
                             two_phase: Vec<Box<dyn TwoPhaseIterator>> }

                             scratch: Vec<usize> }                   // current matchers

  • Ownership: parent owns children (Box). Mutation: advance mutates lead then syncs others (leap-frog/gallop). Concurrency: !Sync. Persistence/serialization: none. Compatibility: internal. Invariant: conjunction output ⊆ each child (INV-2-derived); lead is always the lowest-cost child after optimizer ordering (rarest-first).

1.2 Detailed Implementation Steps

  • Applies ADR-15 (coded thiserror diagnostics, no panics on user input), ADR-16 (serde JSON DSL), ADR-23 (per-request QueryConfig default-op), Principle 12 (AST as an exhaustive enum), and MM5 (parser→AST→plan is a compiler front-end). Grammar per the Domain Model §8.2.

1.6 Pitfalls

  • Boost binding ambiguity — a^2 b vs (a b)^2: manifestation wrong scores later. Root cause: ^ precedence. Debug: print AST; assert boost attaches to primary not the clause list.

Containment: bounded recovery iterations; on exhaustion, return best-effort AST + diagnostics. Recovery: client fixes query. Forensics: log the offending byte span + token trace at debug level.

Phase 3 — Term Expansion (Wildcard / Prefix / Fuzzy)

3.1 Objectives

  • Expand Wildcard/Prefix/Fuzzy/Range queries to concrete term sets via FST enumeration under an automaton (prefix DFA, glob NFA→DFA, Levenshtein-k DFA), bounded by maxExpansions with RW-7 const-score promotion (Domain Model §8.5).

3.2 Detailed Implementation Steps

  • Applies papers P11 (Daciuk — minimal FSA) and P12 (Schulz & Mihov — Levenshtein automaton), ADR-10/11/17 (FST term dict, Levenshtein DFA max-2, points/BKD ranges), ADR-24 + Principle 8 (bounded expansion via maxExpansions + memory budget), rule RW-7 (const-score promotion), and MM3 (expansion is automaton ∩ FST; the bound exists because an unbounded enumeration is a DoS, not a feature). Worked examples in Domain Model §8.5.
  • expansion/src/prefix.rs: prefix as a trivial DFA; walk TermDictionary::enumerate(prefix_dfa).
  • wildcard.rs: compile glob (* ?) → NFA → DFA (Thompson + subset construction); reject leading * unless allow_leading_wildcard (Domain Model §8.8).
  • levenshtein.rs: Schulz & Mihov universal Levenshtein automaton for k ∈ {0,1,2} (clamp ≤2, ADR-11); optional prefix_len exact-prefix to shrink the automaton.
  • intersect.rs: intersect the automaton with the term-dict FST, enumerate matching terms (TermEnum); collect (term, df).
  • bounds.rs: if count ≤ maxExpansions → build BooleanQuery(SHOULD: TermQuery…) (blended/SynonymQuery for fuzzy, distance-weighted boost optional); else RW-7 → ConstantScoreQuery over the union (deferred to a bitset at execution, no per-term scoring). If even the bitset would exceed the memory budget → ResourceError::ExpansionTooLarge (Domain Model §8.8, ADR-24).
  • Range (term range) enumerates [lo, hi] via FST; numeric range prefers points/BKD via index-api (ADR-17) → bitset filter; falls back to term enumeration.

3.3 Deliverable

  • expand(Query<FieldId>, &SegmentReader, &QueryConfig) -> Query<FieldId> (expanded); examples show te* and jon~2 expansions + the const-score fallback.

3.4 Acceptance Criteria

  • Prefix/wildcard/fuzzy enumerations match a brute-force scan of the term dictionary under the same predicate (differential).
  • maxExpansions honored; over-limit → const-score bitset; over-budget → ExpansionTooLarge.
  • Levenshtein correctness: enumerated terms are exactly those within edit distance ≤ k (verified vs naive DP).
  • Leading wildcard rejected by default; allowed under flag.

3.5 Conformance Fixtures

  • queries/P3_prefix.jsonl, P3_wildcard.jsonl, P3_fuzzy.jsonl (each: pattern → expected term set golden), P3_overlimit.jsonl (→ const-score), P3_overbudget.jsonl (→ error), P3_leading_wildcard.jsonl.

3.6 Pitfalls

  • Automaton/FST desync — enumeration misses or over-includes terms. Root cause: subtle DFA transition bug. Debug: diff vs naive scan; visualize the DFA (tools/). Instrument: expansion_mismatch_total.
  • Fuzzy explosion — a~2 on a huge dict enumerates millions. Root cause: no prefix_len, low selectivity. Debug: cap + const-score fallback; require prefix_len ≥ 1 for short terms (config).
  • Levenshtein off-by-one — includes distance-3 terms. Debug: cross-check the universal automaton against textbook DP for a sample.
  • Const-score score discontinuity — same query scores differently above/below maxExpansions (scored disjunction vs constant). Document as expected; test both branches; warn in explain().
  • Leading-wildcard footgun — *term accidentally allowed → full-dict scan. Debug: default-reject; require explicit opt-in.

3.7 Performance Concerns

  • DFA size grows with k and pattern complexity; cap k≤2 and DFA states. FST enumeration is the cost — bounded by maxExpansions. Const-score path avoids per-term scoring (the real win). Cache compiled automata for repeated patterns.

3.8 Edge Cases

  • Empty prefix (*) → matchall (reject as wildcard, route to MatchAll). Pattern matching zero terms → empty clause (RW-6 drops). ? on a 1-char term. Fuzzy on a term not in dict but neighbors exist. Range where lo > hi → empty. Unicode edit distance (codepoints, not bytes).

3.9 Failure Analysis

  • Breaks: unbounded expansion → CPU/memory blow-up (DoS class, Threat Model). Detection: expansion-count + memory circuit breaker (ADR-24). Blast radius: one query starves the pool. Containment: maxExpansions + memory budget reject before damage. Recovery: reject with ExpansionTooLarge + guidance. Forensics: log pattern, field, enumerated count, decision (scored/const/reject).

3.10 Operational Notes

  • Metrics: expansion_terms{decision}, expansion_rejected_total. explain()/plan dump must show whether a multi-term query was scored or const-scored (relevance debugging). maxExpansions and allow_leading_wildcard are per-request overrides (ADR-23). Document the scored↔const-score relevance cliff for operators.

Phase 4 — Physical Iterator Operators (Conjunction / Disjunction / AndNot / Skip)

4.1 Objectives

  • The executor core (Core Types §11.5–11.6): DocIdSetIterator, leaf PostingsIterator binding, ConjunctionIterator (leap-frog + galloping), DisjunctionIterator (PQ), AndNotIterator, skip-list/advance usage. No scoring yet — pure boolean matching to validate iterator algebra (INV-2) before scoring/pruning layer on top.

4.2 Detailed Implementation Steps

  • Applies Principle 3 (iterators advance monotonically) + INV-2, Principle 13 (segment isolation), INV-8 (live-docs honored), ADR-03/ADR-04/ADR-05 (dispatch, DocId/NO_MORE_DOCS, PQ disjunction), galloping per book B5 (CLRS amortized analysis), and MM2 (a DocIdSetIterator is a monotone cursor; the executor is a lock-step merge of cursors).
  • exec/src/disi.rs: trait + NO_MORE_DOCS; EmptyIterator, AllDocsIterator (matchall over live-docs).
  • Leaf: wrap index-api::PostingsIterator; advance(target) uses skip-list/block seek (BlockMaxMeta/skip data) to avoid full block decode (§4 IO target). cost() = df.
  • conjunction.rs: order children by cost() ascending (rarest = lead, set by optimizer later; here ascending by df). Algorithm: advance lead → next_doc; for each other, advance(lead_doc); if any returns > lead_doc, set lead = that doc and restart sync; else all aligned → match. Galloping: when a child is far ahead/behind, exponential probe then binary search within the block (amortized, CLRS B5).
  • disjunction.rs: min-heap of (doc_id, child_idx); next_doc pops all children at the min doc, advances them, re-pushes; current matchers = the popped set (needed for scoring/positions later).
  • AndNotIterator: advance include; for each, advance exclude to that doc; if exclude matches, skip; else emit.
  • Wrap leaves with live-docs (INV-8): a FilteredIterator that skips docs where live-docs=0 (or push the bitset into advance).
  • deadline.rs: a hook checked at block boundaries (wired fully in P14) — placeholder no-op now.

4.3 Deliverable

  • A boolean matcher: given an expanded Query<FieldId> (no scoring), enumerate matching doc ids per segment via the iterator tree. examples/embed_search.rs prints matching ids for +a +b -c.

4.4 Acceptance Criteria

  • For all boolean fixtures, iterator-tree doc-id set == brute-force set intersection/union/difference over postings (differential).
  • INV-2 (monotonic advance) holds under a dev-build assertion across the whole corpus + fuzz (iterator_monotonic target smoke).
  • Live-docs honored (INV-8): deleted docs never emitted.
  • advance(target) lands on first doc ≥ target (skip correctness) — verified against linear scan.

4.5 Conformance Fixtures

  • queries/P4_conjunction.jsonl, P4_disjunction.jsonl, P4_andnot.jsonl, P4_skip.jsonl (advance targets → landing doc golden), P4_livedocs.jsonl (deletes excluded), P4_matchall.jsonl.

4.6 Pitfalls

  • Conjunction restart loop — lead never converges. Root cause: a child returns a doc < lead (INV-2 violation) or off-by-one in sync. Debug: log (lead, child, returned) on each sync; assert monotonicity. Recovery: fail fast in dev.
  • Disjunction current-matchers wrong — heap pops the wrong subset → scoring/positions later use wrong children. Debug: assert all popped children have doc_id == current.
  • Galloping overshoot — binary search lands past the target. Debug: invariant result ≥ target; unit-test the gallop boundary.
  • Skip-list misuse — advance decodes a full block when a skip pointer existed. Manifestation: latency, not wrong results. Debug: count blocks decoded vs skipped (postings_blocks_decoded_total).
  • AndNot exclude desync — exclude iterator advanced past then can't go back. Root cause: exclude shared/advanced incorrectly. Debug: exclude must only ever advance forward to the include's current doc.

4.7 Performance Concerns

  • Hot loop = advance + sync. Cache locality: leaf reads decode 128-doc blocks (§4); keep the decoded block in L1/L2; gallop within a decoded block before crossing block boundaries. Avoid per-doc allocation; the PQ uses a flat array. Monomorphize the common conjunction arity (ADR-03). Branch prediction: the "all aligned" fast path should be the predicted branch.

4.8 Edge Cases

  • One child empty → conjunction empty immediately (short-circuit). All children identical postings. Disjunction of 1 child = passthrough. AndNot where exclude ⊇ include → empty. advance past max_doc → NO_MORE_DOCS. Single-doc postings. Block boundary exactly at target.

4.9 Failure Analysis

  • Breaks: an iterator bug drops or duplicates matches → wrong results (caught by differential vs brute-force). Detection: P4 fixtures + INV-2/INV-8 assertions + fuzz. Blast radius: every query of that shape. Containment: brute-force oracle in CI; dev assertions. Recovery: this is a logic bug — fix + regression fixture. Forensics: replay the query in --exact brute-force mode, diff the doc sets.

4.10 Operational Notes

  • Metrics: postings_blocks_decoded_total, postings_blocks_skipped_total, iter_advance_calls_total. These quantify skip effectiveness (the §4 IO target) before pruning exists. No scoring telemetry yet. Single-threaded per segment (Principle 13).

Phase 5 — BM25 Scoring, Weight Factory, Top-K Collector (Exhaustive Baseline)

5.1 Objectives

  • Scoring (Core Types §11.7): Similarity/Weight/Bm25Scorer with k1/b, IDF, field-norm; explain() tree; max_score() as a true upper bound (INV-1). Top-k collector (Core Types §11.10): min-heap, deterministic tie-break (INV-4), track_total_hits. This is the exhaustive DAAT baseline — score every match, no pruning — the oracle for INV-3.

5.2 Detailed Implementation Steps

  • Applies paper P4 (Robertson & Zaragoza, BM25), ADR-07 (BM25 + pluggable Similarity), ADR-18 (fixed-cap min-heap top-k), INV-1 (true max_score) + INV-4 (deterministic tie-break) + INV-7 (finite, non-negative) + INV-12 (norm consistency), Principle 1 (this exhaustive baseline is the permanent --exact oracle), and MM1/MM3 (the bound exploits BM25 monotonicity; the heap root is the pruning threshold). Top-k heap discipline per book B5.
  • scoring/src/similarity.rs: Similarity trait → Weight (per-term, holds idf, avg_len, k1, b, boost). bm25.rs: score = boost · idf · (tf·(k1+1)) / (tf + k1·(1 - b + b·len/avg_len)); IDF = ln(1 + (N - df + 0.5)/(df + 0.5)) (always ≥0, INV-7). norms.rs: decode quantized field-norm byte → length via a 256-entry table (matches index-time quantization, INV-12).
  • max_score(): BM25 is monotone increasing in tf and decreasing in len; the upper bound uses tf→∞ (saturates to idf·(k1+1)) and the minimum possible norm (shortest doc) → a true, tight-ish upper bound (INV-1). Computed once at scorer construction from term stats.
  • block_max_score() (stub here; real in P10): return max_score() for now (still a valid, loose bound).
  • explain.rs: Explanation{value, description, details} tree mirroring the scorer tree (idf, tf, norm contributions).
  • collect/src/topk.rs: fixed-cap min-heap of Reverse<ScoreDoc> (size k); collect(doc) scores via the bound scorer, pushes if score > min_competitive (or heap not full), pops min when over capacity. ScoreDoc Ord = score desc then doc asc (INV-4). min_competitive_score() = heap root (or -inf until full) — the feedback signal for pruning (P9).
  • total_hits.rs: exact count (count all matches) or capped (track_total_hits=N → stop counting precisely at N, report AtLeast(N)).
  • Executor drives leaf scorers up the tree; conjunction/disjunction sum child scores (BooleanQuery scoring = sum of MUST+SHOULD scorer scores; MUST_NOT/FILTER contribute 0).

5.3 Deliverable

  • End-to-end exhaustive ranked search over the mock index: query → expanded AST → physical scorer tree → top-k ranked (doc, score) with explain(). examples/explain_query.rs prints the explanation tree.

5.4 Acceptance Criteria

  • BM25 numeric oracle: for hand-computed fixtures (known df/tf/len/N), scores match to f32 tolerance.
  • INV-1: fuzz score(d) ≤ max_score() for all d (smoke here, full in P15) — zero violations.
  • INV-4: same query twice → byte-identical ranked ids (deterministic tie-break).
  • INV-7: all scores finite, ≥0.
  • explain() value == score() for the explained doc (tree sums correctly).
  • Differential vs reference (Lucene/Tantivy) BM25 ranking on the shared corpus modulo documented formula constants (Principle 15).

5.5 Conformance Fixtures

  • queries/P5_bm25_oracle.jsonl (df/tf/len → expected score), P5_topk.jsonl (query → ranked ids+scores golden), P5_tiebreak.jsonl (equal-score docs → ascending-doc order), P5_total_hits.jsonl, P5_explain.jsonl (explanation tree golden), P5_ref_diff.jsonl (vs Lucene/Tantivy export).

5.6 Pitfalls

  • Loose max_score kills future pruning — manifestation: WAND barely skips in P9. Root cause: bound uses global-min norm regardless of which docs the term hits. Debug: compare bound to observed max score per term; tighten with per-term norm stats if available. (Still must stay a true bound — INV-1 first.)
  • IDF negative — df > N (stale stats) → negative IDF → negative score (breaks INV-7 + heap). Debug: clamp IDF ≥ 0; root-cause the stat.
  • Tie-break instability — heap pops in nondeterministic order for equal scores. Root cause: comparator ignores doc id. Debug: assert ScoreDoc Ord includes doc asc; run twice and diff.
  • Norm decode mismatch — wrong quantization table → wrong length → wrong score (INV-12). Debug: explain() shows norm; compare to index-time value.
  • SHOULD scoring with minShouldMatch — clauses that don't meet the threshold still scored. Debug: enforce minShouldMatch before scoring contribution.
  • Heap "full" semantics — first k docs must all enter regardless of score; only after full does min_competitive gate. Debug: test with k > #matches.

5.7 Performance Concerns

  • Scoring is the per-doc cost the planner later minimizes. Precompute IDF, k1·(1-b), etc. once per scorer. Norm decode via table lookup (no pow/log in the hot loop). Heap ops O(log k); for tiny k consider linear scan (ADR-18 revisit). f32 (not f64) for cache + SIMD friendliness (ADR-21 future). Avoid boxing scores.

5.8 Edge Cases

  • Zero matches → empty top-k, total=0. Fewer matches than k → all returned. All equal scores → pure doc-order. Single term, single doc. tf very large (saturation). len=0 (empty field) → norm handling. k=0 (count-only). NaN guard (INV-7).

5.9 Failure Analysis

  • Breaks: wrong scores → wrong ranking (silent relevance regression). Detection: BM25 oracle + reference differential in CI. Blast radius: all ranked queries. Containment: oracle fixtures gate release. Recovery: fix formula/stats; regression fixture. Forensics: explain() the divergent doc, compare contribution-by-contribution to the reference's explain.

5.10 Operational Notes

  • explain() is the primary relevance-debugging tool (Principle 10); exposed via searchd ?explain=true. Metrics: score_calls_total, topk_heap_replacements_total, score_nan_or_neg_total (must be 0). k1/b are per-request overrides (ADR-23) for relevance tuning without redeploy. This baseline is permanently retained as the --exact oracle (Principle 1).

Phase 6 — Query Rewriting / Normalization + Boolean Simplification

6.1 Objectives

  • The rewrite engine (Domain Model §8.4, Core Types §11.3): RW-2..RW-10 — flatten, dedupe, NOT push-down (De Morgan), single-clause unwrap, empty drop, const-score promote, boost fold, matchall absorb, filter classify. Idempotent, cost-monotone (Principle 7), to fixpoint.

6.2 Detailed Implementation Steps

  • Applies Principle 7 (rewrites are cost-monotone/neutral; never result-changing), Principle 12 (plan/AST nodes are an exhaustive enum), INV-10 (determinism via canonical clause order), rules RW-2..RW-10 from Domain Model §8.4, and MM5 (the rewrite engine is an algebraic optimizer iterated to fixpoint, exactly a compiler's simplification pass). FILTER classification (RW-10) feeds Phase 11 caching.
  • rewrite/src/rules.rs: each RW rule as a RewriteRule (Core Types §11.3). engine.rs: apply rules over the AST (post-order visitor) repeatedly to fixpoint (bounded max_iters, e.g. 8 — DoS bound for adversarial nesting).
  • RW-2 flatten: merge same-occur nested booleans. RW-3 dedupe: structural-equality dedup of siblings (canonical hash), sum boosts. RW-4 NOT push-down: De Morgan only when est_cost drops (needs P7 stats; until then a structural heuristic, refined in P8). RW-5 unwrap single clause. RW-6 drop empty (all-stopword) clauses; if the whole query empties → MatchNone + W-SEM-EMPTY. RW-8 boost fold. RW-9 matchall absorb.
  • classify.rs (RW-10): mark clauses that need no score as FILTER (e.g. ConstantScore, range used only to constrain, MUST_NOT). Filters become cacheable bitsets (P11). Heuristic now; cost-aware in P8.
  • Canonicalization: define a total order on clauses (by field, then term, then occur) so dedupe + plan determinism (INV-10) are stable.

6.3 Deliverable

  • rewrite(Query<FieldId>) -> Query<FieldId> (normalized, fixpoint); plan-dump shows pre/post-rewrite AST. Examples demonstrate flatten/dedupe/NOT-pushdown/const-score.

6.4 Acceptance Criteria

  • Idempotence: rewrite(rewrite(q)) == rewrite(q) for all fixtures.
  • Semantic equivalence: rewritten query returns the same doc set + scores as the unrewritten query (differential vs P5 baseline) — rewrite changes shape, never results (except documented const-score relevance cliffs and empty-drop).
  • Cost-monotonicity: estimated cost of rewritten ≤ original (where stats exist; P8 closes the loop).
  • Fixpoint terminates within max_iters; adversarial nesting bounded.

6.5 Conformance Fixtures

  • queries/P6_flatten.jsonl, P6_dedupe.jsonl, P6_demorgan.jsonl, P6_unwrap.jsonl, P6_empty_drop.jsonl, P6_const_promote.jsonl, P6_idempotence.jsonl, P6_equivalence.jsonl (rewritten vs baseline doc set).

6.6 Pitfalls

  • Rewrite changes results — a rule isn't actually equivalence-preserving. Manifestation: differential mismatch vs baseline. Root cause: e.g. De Morgan on a SHOULD with minShouldMatch, or dedupe collapsing clauses with different boosts. Debug: run rewritten vs unrewritten through P5, diff; bisect rules. Instrument: rewrite_equivalence_mismatch_total. Recovery: disable the offending rule.
  • Non-idempotent rule — fixpoint never reached → hits max_iters. Root cause: two rules undo each other (flatten ↔ unwrap). Debug: log rule firing sequence; assert convergence.
  • Dedupe boost loss — collapsing a^2 and a^3 to one. Debug: sum/choose boosts per documented semantics; test.
  • Empty-query surprise — RW-6 silently empties a query. Debug: emit W-SEM-EMPTY; never silent.
  • Filter misclassification — classifying a scored clause as FILTER → relevance changes. Root cause: RW-10 heuristic too aggressive. Debug: only classify clauses provably score-irrelevant; differential check.

6.7 Performance Concerns

  • Rewrite is per-query, bounded by max_iters and AST size. Canonical hashing for dedupe must be cheap + collision-safe (128-bit). Avoid re-allocating the whole AST each iteration — rewrite in place where the rule is local.

6.8 Edge Cases

  • Deeply nested same-occur booleans (flatten depth). Query that fully empties. Mutually-recursive rule pairs. Boolean with only MUST_NOT (no positive clause) → matches-all-except (must add implicit MatchAll). Boost on a MatchNone. Dedup across grouping boundaries.

6.9 Failure Analysis

  • Breaks: a non-equivalence-preserving rewrite → silent wrong results. Detection: P6 equivalence fixtures (rewritten vs P5 baseline) in CI; this is the critical gate. Blast radius: every query the rule touches. Containment: rules are individually toggleable (config) to bisect. Recovery: disable rule, ship fix + fixture. Forensics: plan-dump pre/post-rewrite + the doc-set diff.

6.10 Operational Notes

  • Plan dump shows the rewrite (pre→post AST) so operators see what the planner did to their query (Principle 10). Metrics: rewrite_rules_fired_total{rule}, rewrite_iterations, rewrite_query_emptied_total. Rules toggleable per-request (debugging) but default-locked. Document the const-score promotion relevance implication for operators.

Phase 7 — Statistics / Catalog + Selectivity & Cardinality Estimation

7.1 Objectives

  • The catalog (Core Types §11.8): per-generation cached stats (df, cf, N, sum_tf, avg_len, norms summary) from index-api; selectivity + cardinality estimation for the optimizer (Core Types §11.9). Estimates drive ordering, never correctness (Principle 7).

7.2 Detailed Implementation Steps

  • Applies Principle 7 (cost estimates drive ordering, never correctness), INV-6 (generation-keyed stat cache), MM4 (selectivity is the planner's only knowledge of the future), book B6 (DB cost estimation / selectivity), and feeds Phase 8 ordering. Independence assumption is the documented approximation (see Hard Question HQ7).
  • catalog/src/stats.rs: a StatsProvider wrapper that caches CollectionStatistics/TermStatistics per generation; refresh on generation bump (INV-6). Aggregates multi-segment stats into collection-level (sum df, etc.).
  • selectivity.rs:
    • Term selectivity ≈ df(t) / N.
    • Conjunction cardinality ≈ N · Π sel(child) (independence assumption — documented, often wrong but adequate for ordering).
    • Disjunction cardinality ≈ N · (1 - Π(1 - sel(child))) (inclusion-exclusion approx).
    • AndNot ≈ card(include) · (1 - sel(exclude)).
    • Phrase cardinality ≈ min(df) · positional-factor (heuristic; phrases are rarer than the rarest term).
    • Range: from points/BKD count if available (exact), else estimate from term df sum.
  • norms.rs: expose avg_field_len (for BM25) + norm summary.
  • Cross-shard: for distributed scoring consistency (Phase 12), the coordinator can gather global df/N so IDF is computed against the collection, not per-shard (config: local vs global IDF).
  • Cache invalidation: generation-keyed (INV-6); a new searcher generation drops the stats cache.

7.3 Deliverable

  • StatsProvider with cached stats + estimate_cardinality(LogicalOp) -> u64; plan dump annotates each node with estimated cardinality. Examples print estimates for a boolean query.

7.4 Acceptance Criteria

  • Stats correctness: cached df/cf/N == index-api source == brute-force over the corpus.
  • Estimation sanity: estimated cardinality is within an order of magnitude of actual on the fixture set (estimates need only be good enough to order, not exact).
  • Estimates are monotone where expected (adding a MUST clause never increases conjunction estimate).
  • Generation bump invalidates the cache (INV-6); no stale stats served.

7.5 Conformance Fixtures

  • queries/P7_stats.jsonl (term → df/cf golden), P7_card_conj.jsonl, P7_card_disj.jsonl, P7_card_andnot.jsonl (logical op → estimated vs actual), P7_generation.jsonl (stat refresh on bump).

7.6 Pitfalls

  • Independence assumption wildly off — correlated terms (e.g. "new york") → conjunction grossly over-/under-estimated. Manifestation: suboptimal ordering (slow, not wrong). Root cause: independence assumption. Debug: log estimated vs actual cardinality (the plan-dump est_card vs collector's actual count); it is a perf signal only (Principle 7). Mitigation: optional 2-term co-occurrence stats (deferred).
  • Stale stats after merge — generation not bumped → old df. Manifestation: wrong IDF + wrong ordering. Debug: assert stats generation == reader generation (INV-6).
  • Divide-by-zero — N=0 empty index. Debug: clamp; selectivity 0.
  • Global vs local IDF confusion — per-shard IDF differs from global → cross-shard score incomparability. Root cause: distributed scoring without global stats. Debug: config flag; gather global df when consistency matters (Phase 12).

7.7 Performance Concerns

  • Stats lookups are O(1) cached; the FST term lookup for df is the cost on first touch — cache per query. Estimation is arithmetic, negligible. Cross-shard global-stats gather adds an RTT (cache per generation). Avoid recomputing IDF per segment — compute once per term per query.

7.8 Edge Cases

  • Empty index (N=0). Term absent (df=0 → IDF max, but zero matches). All docs contain the term (df=N → IDF=0). Single segment vs many. Stats requested for an unknown field. Range with no points index.

7.9 Failure Analysis

  • Breaks: bad stats → bad plan (slow) or, if used for IDF, wrong scores (the IDF path is correctness-relevant; ordering is not). Detection: stats-vs-oracle fixtures; cardinality est-vs-actual telemetry. Blast radius: ordering = perf only; IDF = relevance. Containment: separate the two uses; IDF stats are validated, ordering estimates are advisory. Recovery: refresh stats; bump generation. Forensics: plan dump est_card vs actual.

7.10 Operational Notes

  • Plan dump shows est_card per node; compare to actual (collector counts) post-execution = the estimation-quality signal. Phase 8 — Cost Model + Logical→Physical Planner

8.1 Objectives

  • The optimizer (Core Types §11.9): a clause cost model, rarest-term-first conjunction ordering, strategy selection (sorted-bitset intersection vs leap-frog iterator vs PQ disjunction vs MaxScore), filter-vs-query finalization, and plan-shape decisions (AND vs OR evaluation). Pure function of (logical plan, stats, config) → physical plan (INV-10). This is the brain that turns correct-but-naive execution into a good plan.

8.2 Detailed Implementation Steps

  • Applies Principle 7 (cost drives ordering, never correctness) + Principle 12 (exhaustive plan enum), INV-10 (deterministic plan from inputs), ADR-21 (optional SIMD bitset strategy), book B6 (DB cost-based optimization), and MM4 (rarest-term-first: the lead's df bounds the conjunction's work, so order by selectivity). A heuristic rule-based optimizer (not Selinger enumeration — see Alternative Architectures, ALT-C). Feeds pruner selection in Phase 9/10.
  • planner/src/cost.rs: CostModel with weights (io_block, decode_doc, score_doc, heap_op, gallop). Per-operator cost:
    • TermScan cost ≈ est_docs · (decode_doc + score_doc) + io_blocks · io_block.
    • Conjunction cost dominated by the lead (rarest) child's scan + sync probes on others; ordering children rarest-first minimizes total advance work (the lead drives, others are advance-probed).
    • Disjunction cost ≈ Σ child scans + heap ops (mitigated by pruning, P9/P10).
  • optimizer.rs:
    • Rarest-first: sort conjunction children ascending by cost() (≈ df); set the lowest as lead (Principle: rarest term first).
    • Strategy select per node (Phase 8 cost compare): (a) sorted-bitset intersection when children are dense and a precomputed/cacheable bitset exists (SIMD intersection, ADR-21); (b) leap-frog iterator when sparse / skip-friendly; (c) PQ disjunction for OR; (d) MaxScore vs WAND/BMW chosen in P9/P10 by clause profile.
    • Filter vs query finalization (RW-10 + cost): a non-scoring constraint with high reuse → FILTER (bitset, cacheable, P11); else a scored leaf.
    • Plan shape: choose conjunctive (AND/leap-frog) vs disjunctive (OR/PQ) evaluation; e.g. a SHOULD-heavy query with a selective MUST → drive by the MUST conjunction, treat SHOULD as scoring contributors.
    • Output: PhysicalOp tree (Core Types §11.4) with lead_order, PruneMode, strategy tags.
  • physical.rs: build PhysicalOp from the optimized logical plan; dump.rs: emit the chosen plan + per-node cost + strategy + prune mode (the operator-facing artifact).
  • Determinism (INV-10): stable sort, deterministic tie-breaks in ordering, no hashmap-iteration-order dependence.

  • optimize(LogicalOp, &StatsProvider, &CostModel, &QueryConfig) -> PhysicalOp; plan dump shows ordering + strategy + cost. examples/plan_dump.rs prints the chosen plan for a complex query.

8.4 Acceptance Criteria

  • Rarest-first: for conjunctions, the lead child is the lowest-df clause (verified on fixtures).
  • Plan determinism (INV-10): same inputs → byte-identical plan dump (run twice).
  • Strategy correctness: the chosen strategy never changes results vs the P5 baseline (differential) — only latency (Principle 7).
  • Measured improvement: rarest-first ordering reduces advance calls / decoded blocks vs naive (left-to-right) ordering by a meaningful margin on the benchmark set.

8.5 Conformance Fixtures

  • queries/P8_rarest_first.jsonl (conjunction → expected lead/order), P8_strategy.jsonl (clause profile → chosen strategy golden), P8_plan_determinism.jsonl, P8_filter_classify.jsonl, P8_equivalence.jsonl (optimized vs baseline results identical).

8.6 Pitfalls

  • Cost model overfit — weights tuned to one corpus, bad on another. Manifestation: regressions on a different dataset. Root cause: hardcoded weights. Debug: weights are config (ADR-23); A/B with plan dump + actual latency.
  • Ordering changes results — a "smart" reorder that isn't equivalence-preserving (e.g. reordering across a MUST_NOT incorrectly). Debug: differential vs baseline (P8 equivalence fixtures); ordering must be result-neutral. Instrument: plan_equivalence_mismatch_total.
  • Nondeterministic plan — hashmap iteration in ordering → flaky plan dumps + unreproducible perf. Debug: assert plan-dump stability; use ordered maps / stable sort (INV-10).
  • Bitset chosen when sparse — dense-strategy on sparse postings wastes memory. Debug: cost compare must include materialization cost; threshold by density.
  • Estimate-driven wrong lead — bad cardinality est picks a non-rarest lead → slow. Manifestation: latency. Debug: plan dump est_card vs actual; refine stats (P7). Not a correctness bug (Principle 7).

8.7 Performance Concerns

  • The optimizer runs once per query (per shard) before execution — must be cheap (microseconds) vs the query it optimizes. Avoid expensive enumeration of plan alternatives; this is a heuristic rule-based optimizer (rarest-first + strategy thresholds), not an exhaustive cost-based search (Selinger-style join enumeration is overkill for tree-shaped boolean queries). Cache nothing here (pure); the plan may be cached downstream (P11).

8.8 Edge Cases

  • Single-term query (no ordering). All clauses equal df (stable tie-break). Conjunction with one empty child → empty plan (short-circuit). Pure disjunction (no conjunction to lead). FILTER-only query (no scoring). Deeply nested mixed AND/OR. Estimate = 0 vs actually-nonempty (must not drop — Principle 7).

8.9 Failure Analysis

  • Breaks: (a) a result-changing reorder → wrong results (caught by equivalence fixtures — the hard gate); (b) a bad plan → slow query (perf incident, not correctness). Detection: equivalence differential (correctness) + latency benchmark (perf). Blast radius: correctness bug = all queries of that shape; perf bug = latency only. Containment: equivalence fixtures gate release; --exact/naive-order fallback flag for A/B. Recovery: fix ordering rule or retune weights. Forensics: plan dump (est vs actual cardinality, chosen strategy) is the primary artifact.

8.10 Operational Notes

  • Plan dump is the operator's window into "why is this query slow" (Principle 10): shows order, strategy, prune mode, est vs (post-exec) actual cardinality. Metrics: plan_build_micros, plan_strategy_total{strategy}, card_estimate_error_ratio. Cost weights + strategy thresholds are tunable config (ADR-23) — a perf knob, never a correctness knob. Phase 9 — Dynamic Pruning: WAND

9.1 Objectives

  • WAND (Broder 2003, Core Types §11.7): pivot-based skipping over a disjunction using per-term max_score() upper bounds + the collector's min_competitive_score() threshold. Safe pruning — identical top-k to the exhaustive baseline (INV-3), the central correctness gate of this phase.

9.2 Detailed Implementation Steps

  • Applies paper P1 (Broder et al., WAND, CIKM 2003), Principle 1/2 (pruning provably safe; upper bounds are a contract), INV-1 (true upper bound) + INV-3 (top-k identical to exhaustive), and MM1 (pruning is a proof: a doc is dropped only when its score provably cannot reach the threshold). The exhaustive Phase 5 scorer is the permanent oracle.
  • exec/src/wand.rs: WandScorer over N term scorers. Algorithm (as steps, not code):
    1. Keep scorers sorted by current doc_id.
    2. Compute the pivot: accumulate max_score() of scorers in doc-id order until the running sum ≥ threshold (= collector min_competitive_score); the scorer at which the sum first exceeds threshold defines the pivot doc = that scorer's current doc.
    3. If the sum of all max_score() < threshold → no remaining doc can compete → done.
    4. If the scorers before the pivot are all already at the pivot doc → it's a candidate: fully score it (sum of matching scorers' real scores); if > threshold, push to heap (threshold rises).
    5. Else advance the lagging pre-pivot scorers to the pivot doc (skip the gap — this is the pruning), re-sort, repeat.
  • Threshold feedback: after each heap insertion, WandScorer.threshold = collector min_competitive_score() (monotonically non-decreasing, INV-3 enabler). Once the heap is full, the threshold gates aggressively.
  • max_score() from P5 (true upper bound, INV-1) — WAND's safety depends entirely on this.
  • A --exact config disables WAND → falls back to the P5 exhaustive scorer (the oracle).

9.3 Deliverable

  • WandScorer integrated as a PruneMode::Wand disjunction; the optimizer (P8) selects it for SHOULD-heavy / disjunctive top-k queries. Plan dump shows prune=Wand. examples/ runs WAND vs exact and diffs.

9.4 Acceptance Criteria

  • INV-3 (the gate): WAND top-k == exhaustive top-k (same ids, scores, order) on every fixture + fuzz (pruned_vs_exact target). Zero mismatches.
  • Pruning effectiveness: WAND scores ≤ ~20% of the candidate docs vs full OR for top-10 on typical queries (§4 target); measured docs_scored_wand / docs_scored_exact.
  • Threshold monotonicity: threshold never decreases during a query (asserted).
  • Latency: ≥ a few× wall-time speedup vs exhaustive on the disjunction benchmark.

9.5 Conformance Fixtures

  • queries/P9_wand_vs_exact.jsonl (query → must equal exhaustive top-k), P9_pruning_ratio.jsonl (records docs-scored ratio), P9_threshold.jsonl (monotonicity trace), P9_unsafe_bound.jsonl (a deliberately-loose-but-valid bound still yields correct top-k), P9_few_terms.jsonl (degenerate: WAND ≈ exhaustive).

9.6 Pitfalls

  • Unsafe upper bound → silent recall loss — the worst bug class. Manifestation: WAND drops a true top-k hit; no error, just wrong results. Root cause: max_score() underestimates (INV-1 violated). Debug: pruned_vs_exact differential pinpoints the missing doc; then check that doc's real score vs its scorer's claimed max. Instrument: inv1_violations_total, pruned_vs_exact_mismatch_total (both must be 0). Recovery: --exact fallback + fix the bound.
  • Threshold set before heap full — pruning starts too early, the first k docs aren't all admitted. Debug: threshold = -inf until heap has k entries; assert.
  • Pivot computation off-by-one — wrong pivot scorer → skips a candidate or never converges. Debug: unit-test pivot selection against a hand-traced example; log (sorted docs, max_scores, running sum, pivot).
  • Non-monotone threshold — a heap replacement that lowers the root (impossible if correct) → broken pruning. Debug: assert min_competitive non-decreasing.
  • Scorer re-sort cost — re-sorting N scorers every step dominates for large N. Debug: use a small structure / partial re-sort; measure (this is a perf, not correctness, issue).

9.7 Performance Concerns

  • WAND wins by skipping postings via advance (skip lists). The cost is the per-step pivot computation + scorer re-sort (O(N log N) for N terms; N usually small). The big save is not decoding/scoring skipped docs. Keep max_score reads cheap (precomputed). Threshold rising fast (good first-k docs) maximizes skipping — order matters (interacts with P8). f32 sums; watch float accumulation in the pivot sum (use a consistent order for determinism).

9.8 Edge Cases

  • Single term (WAND degenerates to a scan — must still be correct). All terms identical max_score. Threshold never rises (all docs score similarly) → WAND ≈ exhaustive (no harm). k larger than #matches. A term with empty postings. Ties at the threshold boundary (a doc scoring exactly = threshold: include or exclude — define consistently with the heap's > vs ≥, must match exhaustive).

9.9 Failure Analysis

  • Breaks: unsafe pruning → silent top-k corruption. Detection: pruned_vs_exact differential in CI + fuzz; production canary running --exact on a sample and diffing. Blast radius: every pruned query (potentially all ranked queries). Containment: --exact global kill-switch; per-query-class disable. Recovery: disable WAND, ship bound fix + regression fixture. Forensics: the differential diff names the dropped doc; explain() both modes.

9.10 Operational Notes

  • This phase introduces the single most dangerous failure mode (silent recall loss) and its single most important guardrail (pruned_vs_exact + --exact). Metrics: wand_docs_scored_total, wand_pruning_ratio (histogram), wand_pivot_skips_total, inv1_violations_total, pruned_vs_exact_mismatch_total. Plan dump shows prune=Wand + the threshold trajectory (debug). A production policy: run a small % of traffic in --exact shadow mode and alert on any divergence (Operational Readiness).

Phase 10 — BlockMax-WAND + MaxScore + Block-Max Metadata

10.1 Objectives

  • BlockMax-WAND (Ding & Suel 2011) and MaxScore (Turtle & Flood 1995), the production-default pruners (ADR-06): tighter, block-level upper bounds (block_max_score(), INV-1) for far more skipping; MaxScore's essential/non-essential partitioning for low-k/few-term cases. Both must still satisfy INV-3.

10.2 Detailed Implementation Steps

  • Applies paper P2 (Ding & Suel, BlockMax-WAND, SIGIR 2011) for the block-level skip, paper P3 (Turtle & Flood, MaxScore, IP&M 1995) for essential/non-essential partitioning, ADR-06 (BMW default, mode selectable by clause profile), INV-1 (block bound is a true per-block upper bound) + INV-3, and MM1/MM3 (tighter bound ⇒ more skips, but a too-tight bound silently corrupts top-k). Builds directly on Phase 9 — WAND.
  • Block-max metadata: index-api::BlockMaxMeta exposes per-block (128-doc) max impact; scoring binds it so Bm25Scorer::block_max_score() returns a true upper bound for the current block (INV-1) — far tighter than the global max_score().
  • exec/src/block_max_wand.rs: BlockMaxWandScorer. Two-level skipping:
    1. WAND pivot using global max_score() (shallow, no decode) to find a candidate pivot doc — advance_shallow moves block cursors without decoding postings.
    2. At the pivot, refine with block block_max_score() sums: if the block-level sum < threshold, skip the whole block (advance_shallow past it) — the BMW win.
    3. Only when block-level sum ≥ threshold do we decode + fully score the doc.
  • exec/src/max_score.rs: MaxScoreScorer. Partition scorers into essential (those whose max_score sum could exceed threshold) and non-essential (the rest); iterate only essential scorers' postings (DAAT over essentials), then check non-essentials by advance/score only when the partial score + remaining max could compete. Repartition as threshold rises.
  • Optimizer (P8) selects: BMW default for SHOULD-heavy top-k OR; MaxScore for low-k / few-term; WAND fallback when block-max meta absent; None for tiny result sets or --exact.
  • advance_shallow (block cursor move w/o decode) added to BlockMaxScorer (Core Types §11.7).

10.3 Deliverable

  • BlockMaxWandScorer + MaxScoreScorer as PruneMode::BlockMaxWand/MaxScore; optimizer auto-selects; plan dump shows the chosen pruner. Benchmark compares full-OR vs WAND vs BMW vs MaxScore.

10.4 Acceptance Criteria

  • INV-3: BMW top-k == MaxScore top-k == WAND top-k == exhaustive top-k on every fixture + fuzz. Zero mismatch across all four modes.
  • BMW pruning effectiveness > WAND (fewer docs scored, fewer blocks decoded) on the benchmark — the block-level skip pays off.
  • MaxScore beats BMW for the low-k/few-term fixture class (validates the optimizer's selection rule).
  • block_max_score() is a true bound (INV-1) per block — fuzzed.

10.5 Conformance Fixtures

  • queries/P10_bmw_vs_exact.jsonl, P10_maxscore_vs_exact.jsonl, P10_all_modes_agree.jsonl (4-way equality), P10_block_bounds.jsonl (block_max_score ≥ all in-block scores), P10_mode_selection.jsonl (clause profile → chosen pruner), P10_blocks_skipped.jsonl (effectiveness).

10.6 Pitfalls

  • Block-max bound not per-block-true — block_max_score() underestimates a doc in the block. Manifestation: BMW drops a true hit (silent recall loss). Root cause: block-max meta stale/wrong, or scorer ignores the current block. Debug: pruned_vs_exact; fuzz score(d) ≤ block_max_score(block(d)). Instrument: inv1_violations_total. Recovery: fall back to WAND (global bound) or --exact.
  • advance_shallow decodes postings — defeats the purpose (no speedup). Manifestation: BMW not faster than WAND. Debug: assert shallow advance touches only block metadata, not posting bytes; count decoded blocks.
  • MaxScore partition wrong — a scorer wrongly classified non-essential → its docs missed. Debug: differential; re-derive the partition threshold; the partition must be recomputed as threshold rises.
  • Mode selection backfires — optimizer picks BMW where MaxScore wins (or vice versa). Manifestation: latency only. Debug: plan dump + per-mode benchmark; refine selection rule (Principle 7 — perf, not correctness).
  • Float drift across modes — different summation order → different last-decimal scores → spurious INV-3 "mismatch". Debug: compare scores within an epsilon; define a canonical summation order or epsilon tolerance consistently with the baseline.

10.7 Performance Concerns

  • BMW's edge is decoding far fewer postings blocks (the dominant IO/CPU cost). advance_shallow must be metadata-only (cache-resident block-max array). Block size (128) trades metadata granularity vs overhead (§4). MaxScore's repartitioning cost must be amortized. The whole point is to push docs_scored and blocks_decoded toward the theoretical minimum for top-k. Measure both relentlessly.

10.8 Edge Cases

  • No block-max meta (old index) → fall back to WAND (graceful). Single block (small postings). All blocks above threshold (no skip — degenerate, must be correct). Threshold rises mid-block. MaxScore with all terms essential (= exhaustive). k=1 (MaxScore strongly favored). Block boundary exactly at a candidate.

10.9 Failure Analysis

  • Breaks: same dangerous class as P9 — unsafe block bound → silent recall loss, now with a tighter (more error-prone) bound. Detection: 4-way differential (all modes == exhaustive) + block-bound fuzz, in CI + canary shadow. Blast radius: all pruned queries. Containment: per-mode kill-switch → WAND → --exact ladder. Recovery: disable the broken mode, fix bound/meta, regression fixture. Forensics: differential names the doc; dump its block, the block-max claimed, and its real score.

10.10 Operational Notes

  • Production default is BMW (ADR-06); MaxScore/WAND/None are selectable per query class (optimizer) or forced per request. Metrics: bmw_blocks_skipped_total, bmw_docs_scored_total, maxscore_essential_terms (histogram), per-mode pruning_ratio, inv1_violations_total (must be 0). Plan dump shows the pruner + block-skip stats. The --exact shadow canary (P9) now also validates BMW/MaxScore. Block-max meta is an index-api capability — its absence degrades gracefully to WAND (Compatibility §).

Phase 11 — Filters, Facets, Predicate Pushdown, Caching + EXPLAIN + Plan Cache

11.1 Objectives

  • Filters (non-scoring constraints) as cacheable Roaring bitsets (§11.11); predicate pushdown (filter before score); filter cache + query cache (generation-keyed, INV-6); the EXPLAIN facility (plan tree + estimated-vs-actual + score explain()) and a plan cache for repeated query shapes. Basic faceting (term/range aggregation over the filtered set).

11.2 Detailed Implementation Steps

  • Applies Principle 6 (filters do not score) + Principle 14 (caches are correctness-neutral, generation-keyed), INV-6 (generation immutability) + INV-13 (cache == recompute), ADR-08 (Roaring) + ADR-24 (memory budgets), paper P6 (Roaring bitmaps), Principle 10 (EXPLAIN as first-class output), and MM6 (a cache hit must be indistinguishable from recomputation — the generation key is the proof). FILTER clauses arrive from RW-10 / Phase 8.
  • cache/src/filter_cache.rs: cache RoaringHandle per FilterKey{generation, segment, query_digest} (INV-6). On a FILTER clause (from RW-10 / Phase 8): look up; on miss, execute the filter iterator to a Roaring bitmap, insert (cost-aware). roaring_ops.rs: and/or/andnot/rank/select.
  • Predicate pushdown / filter-before-score: the executor intersects the scored-query iterator with the filter bitset before scoring — a filter advance is a cheap Roaring rank/select, so scoring only touches docs passing the filter (Principle 6). Implemented as a FilteredScorer wrapping the scorer with a bitset DocIdSetIterator.
  • query_cache.rs: optional cache of merged TopK per QueryKey{generation, shard, query_digest, k}; conservative — only deterministic queries, disabled for heavy/expensive plans (ADR-24), invalidated on generation bump. INV-6 + INV-13 (cache == recompute).
  • eviction.rs: cost-aware LRU; memory budget (ADR-24); evict by (size × recency × build-cost).
  • EXPLAIN: extend planner::dump + scoring::explain into a unified Explain output: (a) the physical plan tree (operators, chosen strategy, prune mode), (b) per-node estimated vs actual cardinality (actual filled post-execution), (c) per-doc score explanation (BM25 contributions). Gated by ?explain=true.
  • Plan cache: cache the optimized PhysicalOp shape (parameterized by terms) keyed by normalized-query digest + generation, so repeated query shapes skip re-optimization (the optimizer is pure, INV-10 — safe to cache). Distinct from the query (result) cache.
  • Faceting (basic): after filtering, aggregate doc-values (index-api::DocValues) into term/range buckets over the matching set; bounded bucket count.

11.3 Deliverable

  • Filters cached + pushed below scoring; ?explain=true returns the plan tree + est/actual + score explanation; plan cache + query cache operational with eviction. Example shows a filtered+faceted query with EXPLAIN.

11.4 Acceptance Criteria

  • INV-6: no cache entry served across a generation bump (asserted; cache_stale_generation_hits_total = 0).
  • INV-13 (cache correctness): cache hit == fresh recomputation (differential, randomized).
  • Filter-before-score: scored-doc count with a selective filter ≈ filter cardinality, not total matches (measured score_calls_total drops).
  • EXPLAIN: plan-tree explain() value == actual score(); est cardinality present per node; actual filled.
  • Filter cache hit-rate target met on a repeated-filter workload (§4); memory stays under budget (eviction works).

11.5 Conformance Fixtures

  • queries/P11_filter.jsonl, P11_filter_cache.jsonl (hit/miss + generation invalidation), P11_pushdown.jsonl (score-call reduction), P11_query_cache.jsonl (hit==recompute), P11_explain.jsonl (plan tree + score golden), P11_plan_cache.jsonl, P11_facets.jsonl, P11_eviction.jsonl (budget enforcement).

11.6 Pitfalls

  • Stale cache across generation — serving a bitset/result from a generation that deleted docs (INV-6 / INV-8 violation). Manifestation: deleted docs reappear; wrong counts. Root cause: key missing generation, or generation not bumped on reopen. Debug: assert entry.generation == reader.generation on hit; cache_stale_generation_hits_total. Recovery: drop entry, recompute.
  • Scoring a filter — a FILTER clause leaks into scoring → wrong relevance + wasted CPU (Principle 6). Debug: assert FILTER scorers contribute constant 0; explain() shows no filter contribution.
  • Query cache returns stale scores — caching a query whose scoring inputs changed. Debug: key on generation + normalized plan; disable for non-deterministic queries.
  • Eviction thrash — budget too small → constant evict/rebuild. Manifestation: low hit-rate + high CPU. Debug: hit-rate + eviction-rate metrics; raise budget or scope cacheable filters.
  • EXPLAIN cost — explain path much slower, accidentally on by default. Debug: gate by request flag; never compute explanation unless asked.
  • Plan-cache aliasing — two different queries hash to the same digest → wrong plan. Root cause: weak digest. Debug: 128-bit digest of the fully normalized plan including field ids + occur + boosts.

11.7 Performance Concerns

  • Roaring ops are fast + compressed (ADR-08); filter-before-score is the big latency win for selective filters (avoid scoring filtered-out docs). Cache lookups are sharded to avoid lock contention (§11.11). Plan cache turns optimizer cost (P8) to ~0 for repeated shapes. Faceting over doc-values is a sequential column scan over the filtered set — bound bucket count + cardinality. Watch cache memory pressure interacting with the postings page cache (§4 budgets).

11.8 Edge Cases

  • Empty filter (matches nothing) → empty result fast. Filter matches all → no-op (skip the intersection). Generation bump mid-flight (must use a consistent reader for the whole query). Cache key collision (digest). Facet field absent. Very high-cardinality facet (bound + warn). Query cache for a search_after page (must include cursor in key or disable).

11.9 Failure Analysis

  • Breaks: stale cache → deleted/wrong docs (correctness); eviction thrash → latency. Detection: INV-6/INV-13 differentials + cache_stale_generation_hits_total (correctness) + hit/eviction-rate (perf). Blast radius: stale cache = any query hitting the entry; thrash = latency only. Containment: caches are correctness-neutral by design (Principle 14) — a cache bug is contained by the generation key; worst case disable the cache (config) with only a perf cost. Recovery: flush caches on reopen; disable suspect cache. Forensics: log (key, entry_gen, reader_gen) on any stale hit.

11.10 Operational Notes

  • EXPLAIN is the operator/relevance-engineer workhorse (Principle 10): ?explain=true returns plan + est/actual + score breakdown; auto-captured for slow queries (Operational Readiness). Caches are flushed on searcher reopen (generation bump). Metrics: filter_cache_hit_ratio, query_cache_hit_ratio, cache_evictions_total, cache_bytes, cache_stale_generation_hits_total (0), plan_cache_hit_ratio, facet_buckets. Caches can be disabled per-request (debugging) and globally (incident) with only a latency cost. Document the memory-budget config + interaction with page cache.

Phase 12 — Phrases, Pagination, Distribution, Performance Hardening + Conformance

12.1 Objectives

  • Positional / phrase queries with slop via TwoPhaseIterator (approx + positional confirm, INV-5); pagination (from/size, search_after, track_total_hits); distribution (segment parallelism + shard scatter-gather query/fetch with partial results, INV-9/INV-11); performance hardening + the IR-effectiveness/latency benchmark + conformance harness (the release gate, Principle 15). This phase makes the planner production-shaped and locks correctness against a reference.

12.2 Detailed Implementation Steps

  • Applies Principle 5 (two-phase approximation is always a superset) + INV-5, Principle 9 (partial results over failure) + INV-9 (deadline) + INV-11 (shard mergeability), Principle 13 (segment isolation), INV-4 (search_after total order), ADR-09/12/13 (protobuf, work-stealing pool, tokio fanout) + ADR-25 (reference differential), paper P14 (Dean — tail latency, shard fanout), and MM7/MM8 (tail latency is the slowest-of-N; the cursor is the total order). Distribution detail extends the Architectural Overview §3 Panel 2 (M).
  • Phrases (exec/src/two_phase.rs): PhraseQuery → a two-phase iterator: approximation = conjunction of the term postings (docs containing all terms, a superset, INV-5); confirm = positional check (terms appear in order within slop) via PositionIterator (Core Types §11.12). Exact phrase = slop 0; sloppy phrase allows reordering within the window. The optimizer wraps it as PhysicalOp::TwoPhase.
  • Pagination (collect/src/search_after.rs, searchd/src/paging.rs): from/size (skip + take from the merged top-k, discouraged beyond 10k — §4); search_after (a SearchAfter{score, doc} cursor; collect only docs ranking after the cursor under the INV-4 total order — stable, deep-page-safe); track_total_hits (exact / capped-at-N / early-termination).
  • Distribution:
    • coordinator/src/segment_exec.rs: schedule per-segment executor tasks on a bounded work-stealing pool (ADR-12); each segment produces a local top-k; merge to node top-k (Principle 13). Deadline propagated (INV-9), checked at block boundaries (exec::deadline).
    • coordinator/src/query_phase.rs: scatter the (parsed+planned) query to each shard (gRPC, ADR-09); gather per-shard top-k ScoreDocs (ids+scores, global-id mapped); k-way merge to the global top-k (INV-11). Global IDF option (P7) for cross-shard score comparability.
    • coordinator/src/fetch_phase.rs: for the global top-k ids, fetch documents/fields from owning shards (second round-trip — classic query-then-fetch).
    • coordinator/src/partial.rs: on shard timeout/failure, return partial results flagged partial: true + the missing-shard list (Principle 9, INV-9).
    • searchd: tokio front + fanout (ADR-13); sync executor inside; per-request deadline budget.
  • Performance hardening: wire exec::deadline block-boundary checks fully (INV-9); profile + tune the hot loop (advance/score/heap); enable SIMD intersection behind the feature flag (ADR-21); NUMA pinning (§4); allocation audit (no per-doc alloc).
  • Conformance + benchmark harness (conformance/, benchmarks/): differential runner (ours vs Lucene-export vs Tantivy on the shared corpus, ADR-25); IR-effectiveness eval (nDCG/MAP on a labelled test collection); latency benchmark (p50/p95/p99 vs §4) with a committed baseline + regression gate (bench.yml).

12.3 Deliverable

  • Phrase/slop queries; from/size + search_after + track_total_hits; multi-segment + multi-shard execution with partial results; the full conformance + bench + IR-eval harness gating CI. docker-compose.yml runs searchd + 3 mock shards + load-gen.

12.4 Acceptance Criteria

  • Phrase correctness: phrase + slop results match a brute-force positional matcher (INV-5; differential vs reference for exact + sloppy).
  • Pagination: search_after over the whole result set, page by page, visits every doc exactly once in INV-4 order (no dup, no skip) — the deep-paging correctness test.
  • Distribution: scatter-gather top-k == a single "fat" index of the same docs (INV-11 differential); partial results flagged correctly under injected shard timeout/failure (INV-9).
  • Performance: p50/p95/p99 within §4 targets on the benchmark; pruning ratios (P9/P10) hold under load; no regression vs committed baseline (bench.yml gate).
  • IR effectiveness: nDCG/MAP on the labelled collection within tolerance of the reference engine (Principle 15) — ranking quality, not just mechanics.
  • Reference-equivalence: full supported-subset differential vs Lucene/Tantivy green (modulo documented formula constants).

12.5 Conformance Fixtures

  • queries/P12_phrase.jsonl, P12_slop.jsonl (vs positional brute force), P12_search_after.jsonl (full-set walk, no dup/skip), P12_total_hits.jsonl, P12_scatter_gather.jsonl (vs fat-index, INV-11), P12_partial.jsonl (injected failure → partial flag), P12_ir_eval/ (labelled qrels → nDCG/MAP), P12_latency/ (perf baselines), P12_ref_diff_full.jsonl (vs Lucene/Tantivy).

12.6 Pitfalls

  • Phrase approximation misses a match — two-phase approximation isn't a true superset (INV-5). Manifestation: silent recall loss on phrases (pruning can't catch it). Root cause: approximation = wrong conjunction, or positions misread. Debug: differential vs brute-force positional; dump approx set vs exact set diff. Instrument: twophase_false_negative_total (0). Recovery: fall back to exact positional matcher.
  • search_after dup/skip — a doc appears on two pages or none. Root cause: nondeterministic tie-break (INV-4 violated) or cursor comparison off-by-one (> vs ≥). Debug: walk the full set page-by-page, assert a partition; the cursor compare must mirror the heap's total order exactly. Instrument: paging_dup_or_skip_total (0).
  • Cross-shard score incomparability — per-shard local IDF makes scores from different shards non-comparable → wrong global merge. Root cause: local vs global stats. Debug: enable global IDF (P7) or document the approximation; INV-11 differential vs fat index.
  • Partial-result silent data loss — a slow shard's results dropped without flagging. Manifestation: fewer/worse results, no signal. Root cause: missing partial propagation (Principle 9 / INV-9). Debug: inject shard delay, assert partial=true + missing-shard list; partial_results_total.
  • Deadline not propagated — a segment task runs past the request deadline. Debug: assert every block-boundary checks the shared deadline; inject a tiny deadline, assert bounded work + partial. Instrument: deadline_exceeded_total.
  • Deep-page OOM — from=1_000_000 materializes a huge intermediate. Debug: cap from+size; steer to search_after; reject beyond a configured depth (DoS).
  • Float nondeterminism cross-shard — different summation order per shard → unstable global order. Debug: canonical order + epsilon, consistent with INV-4.

12.7 Performance Concerns

  • Phrases are expensive (positional decode) → two-phase keeps the cheap approximation gating; position lists are larger than doc/freq (IO). Scatter-gather adds 1–2 RTT (query + fetch) — fetch only the final top-k (not all candidates) to bound network. Segment parallelism is the main intra-node lever (bounded threads, ADR-12). Deadline checks are amortized per block (not per doc, §4). SIMD intersection (ADR-21) for dense filter strategies. Tail latency dominated by the slowest shard (Dean P14) → hedging/partial-results mitigate. NUMA-pin searchers (§4). Watch position-list decode + heap-merge allocation.

12.8 Edge Cases

  • Phrase with repeated terms ("the the"). Slop larger than the doc. Phrase term absent → empty (short-circuit). search_after cursor for a doc that no longer exists (generation changed). from beyond total hits → empty page. track_total_hits=0 (count nothing). One shard empty / all shards empty. All shards time out → empty + partial. Single-segment single-shard (degenerate distribution). Clock skew across shards (deadlines use the coordinator's monotonic clock, not wall-clock comparison).

12.9 Failure Analysis

  • Breaks: (a) phrase false-negative → silent recall loss (INV-5); (b) paging dup/skip → user-visible pagination corruption (INV-4); (c) unflagged partial → silent incompleteness (INV-9); (d) bad cross-shard merge → wrong global ranking (INV-11); (e) perf regression → SLO breach. Detection: respective differentials + *_total counters in CI + canary. Blast radius: per failure — phrase queries / paged queries / multi-shard queries / latency. Containment: --exact (phrases), single-shard fallback, partial-flag contract, bench gate. Recovery: per-feature kill-switch; ship fix + regression fixture. Forensics: differential diffs name the bad doc/page/shard; plan dump + per-shard top-k captured.

12.10 Operational Notes

  • This phase produces the release gate: conformance (reference-equivalence, Principle 15) + IR-eval (nDCG/MAP) + latency-regression must all be green to ship. Metrics: phrase_confirm_calls_total, twophase_false_negative_total (0), paging_dup_or_skip_total (0), partial_results_total, deadline_exceeded_total, shard_merge_mismatch_total (0), per-stage latency (parse/plan/exec/merge/fetch), qps, p50/p95/p99 histograms. Failure Modes & Recovery

Taxonomy. Each: symptoms · root causes · detection · automatic recovery · manual recovery · operator actions · forensic artifacts · long-term mitigation.

FM-1 — Planner picks a bad plan (slow, not wrong)

  • Symptoms: a query class is suddenly slow; p95/p99 spike; CPU up; results correct. Root causes: bad cardinality estimate (correlated terms, P7 independence assumption), stale stats, mis-tuned cost weights, wrong strategy/pruner selection (P8/P10). Detection: latency SLO alarm; card_estimate_error_ratio high; plan dump shows wrong lead/strategy. Auto recovery: none (correct, just slow); deadline caps the damage (partial). Manual: retune cost weights (config, no redeploy); refresh stats; force a pruner/strategy per query class. Operator: EXPLAIN-on-slow-query → read plan dump → compare est vs actual cardinality. Forensics: captured plan dump + per-stage timing. Long-term: co-occurrence stats; adaptive plan feedback (deferred).

FM-2 — Unsafe pruning changes results (silent recall loss) — CRITICAL

  • Symptoms: a true top-k hit missing; no error; relevance regression reports. Root causes: max_score/block_max_score underestimate (INV-1), block-max meta stale/wrong, MaxScore partition bug. Detection: pruned_vs_exact_mismatch_total > 0, inv1_violations_total > 0; --exact shadow canary divergence. Auto recovery: fall back to --exact for the affected class (kill-switch). Manual: fix the bound / reindex block-max meta. Operator: flip the pruning kill-switch immediately; this is sev-1. Forensics: differential names the dropped doc; dump its real score vs claimed bound + the feeding term stats. Long-term: keep the exhaustive oracle permanent; expand fuzz; shadow-canary always-on.

FM-3 — Stale statistics → mis-estimation / wrong IDF

  • Symptoms: bad ordering (slow) and/or shifted scores (relevance) after a merge/reopen. Root causes: generation not bumped, stats cache not invalidated (INV-6), df>N. Detection: stats-vs-oracle drift; INV-7 (negative IDF); stats_cache_hit_ratio anomalies. Auto recovery: generation bump drops the cache; IDF clamp (INV-7). Manual: force a searcher reopen; verify stats source. Operator: trigger reopen; check analyzer/stats version. Forensics: log (term, df, N, generation). Long-term: assert generation consistency on every stats read.

FM-4 — Iterator desync vs index (wrong/duplicate/missing docs)

  • Symptoms: results differ from brute-force; INV-2/INV-8 assertion fires (dev). Root causes: non-monotonic advance, skip-list misuse, live-docs not applied, conjunction sync bug. Detection: brute-force differential (P4); iter_monotonicity_violations_total, deleted_doc_returned_total. Auto recovery: none (logic bug); dev builds fail fast. Manual: replay in brute-force mode, diff doc sets, bisect. Operator: file sev-2; disable the affected operator path if possible. Forensics: iterator type + (prev, new, target) trace. Long-term: keep dev assertions + brute-force oracle in CI; fuzz iterator_monotonic.

FM-5 — Plan-cache / query-cache staleness (deleted docs resurface, wrong counts)

  • Symptoms: deleted docs in results; stale scores/counts. Root causes: cache key missing generation (INV-6), generation not bumped. Detection: cache_stale_generation_hits_total > 0; INV-13 differential. Auto recovery: generation key drops stale entries; flush on reopen. Manual: disable cache (config, perf-only cost). Operator: flush caches; verify reopen bumped generation. Forensics: (key, entry_gen, reader_gen) log. Long-term: caches correctness-neutral by design (Principle 14); assert on every hit.

FM-6 — OOM on disjunction heap / expansion / caches

  • Symptoms: RSS climb; allocator pressure; OOM-kill. Root causes: huge OR arity, unbounded expansion, cache budget too high, deep paging. Detection: memory budget breakers; RSS alarm; memory_budget_rejections_total. Auto recovery: reject over-budget (ExpansionTooLarge / deep-page reject); evict caches. Manual: lower budgets; cap arity. Operator: tighten config; identify the offending query (slow-query log). Forensics: query + expansion count + cache bytes at OOM. Long-term: every unbounded structure gets a budget (ADR-24, Principle 8).

FM-7 — Partial results / shard failure

  • Symptoms: fewer results than expected; partial: true; missing-shard list. Root causes: shard timeout, shard crash, network. Detection: partial_results_total, per-shard latency/error. Auto recovery: return partial flagged (Principle 9, INV-9); optional hedged retry to a replica. Manual: investigate the slow/failed shard. Operator: check shard health; partial is degraded-but-available (by design). Forensics: which shards missing, their last latency. Long-term: replica hedging; adaptive timeout.

FM-8 — Analysis parity break (silent recall loss on a field)

  • Symptoms: zero/poor results for a field; no error. Root causes: query analyzer ≠ index analyzer (Principle 11). Detection: analysis_parity_miss_total; canary recall vs known-good. Auto recovery: none (config mismatch). Manual: realign analyzer; reindex if index-side changed. Operator: check analyzer version stamp; sev-2. Forensics: query tokens vs terms() enumeration diff. Long-term: analyzer version stamp + mismatch alarm; treat analyzer change as reindex-class.

FM-9 — Nondeterministic results / pagination corruption

  • Symptoms: same query returns different order; a doc on two pages or none. Root causes: tie-break not deterministic (INV-4), float summation order, hashmap iteration in planner (INV-10). Detection: run-twice byte compare; nondeterministic_result_total, paging_dup_or_skip_total. Auto recovery: none (logic bug). Manual: enforce INV-4 comparator + canonical float order + ordered maps. Operator: sev-2 (breaks pagination). Forensics: two result sets diffed. Long-term: determinism fuzz (run-twice) in CI.

FM-10 — Query-of-death / single-query resource exhaustion (DoS class)

  • Symptoms: one crafted query spikes CPU/RSS or stalls a pool thread while aggregate load is normal (distinct from FM-6's aggregate OOM); p99 spike traceable to a single request shape. Root causes: unbounded wildcard/fuzzy expansion (a*, a~2 on a huge dict), deeply-nested boolean / huge clause count, from=1e7 deep paging, or an expensive-plan combination (many SHOULD × phrases × no filter). Detection: pre-execution circuit breakers — maxExpansions + memory budget (ADR-24), AST depth/byte/clause caps (Phase 1), deep-page cap (Phase 12), cost estimate > budget (Threat Model); query_rejected_total{reason}, expansion_rejected_total, deadline_exceeded_total. Auto recovery: reject before damage (ResourceError::ExpansionTooLarge / deep-page reject), or bound at the deadline → partial (INV-9). Manual recovery: tighten per-request limits (config, no redeploy); identify the offending shape via the slow-query log. Operator: sev-2; the limits are perf/availability knobs, never correctness (Principle 7/8). Forensics: rejected query + pattern/field + enumerated count + decision (scored/const/reject). Long-term: every unbounded structure carries a budget (ADR-24, Principle 8); fuzz the parser (Phase 1) and expansion (Phase 3) bounds; admission control sheds over-budget queries (Scalability Analysis).

  • Canary / rolling upgrade / rollback. Canary a new planner build on a traffic slice with --exact shadow + differential before promotion. Rolling upgrade drains in-flight queries (deadline) per node, then restarts; the planner is stateless so rollback = redeploy the prior binary. Plan-dump/EXPLAIN format is versioned (Compatibility §) so dashboards/tooling survive upgrades.
  • Stat refresh ops. Searcher reopen on a new index generation refreshes stats + flushes caches (INV-6). Global-IDF gather (cross-shard) is cached per generation; refresh on bump. Operators trigger reopen; the planner never mutates the index.

Scalability Analysis

  • Bottlenecks (single node). Postings IO/decode on the hot loop; disjunction heap ops at high OR-arity; scoring CPU; cache memory pressure. Mitigations: pruning (skip postings), bounded arity + pruning (heap), precomputed BM25 terms, budgets + eviction (memory).
  • Scaling ceilings. Per-shard: ~100M docs / 50M terms / ~200 GB postings (§4) — beyond this, shard. DocId=u32 caps a segment at 2³¹ docs (ADR-04); cross-shard GlobalDocId=u64. FST term-dict size bounds RAM for enumeration.
  • Horizontal scaling. Add shards → scatter-gather fanout grows (= #shards); coordinator is stateless → add replicas for QPS. Fanout cost is the tradeoff: more shards = more parallelism but more tail-latency exposure (slowest-of-N) → partial results + hedging.
  • Vertical scaling. More cores → more segment parallelism (one query ≤ #segments threads, bounded) + more concurrent queries; more RAM → bigger caches + more of the index resident.
  • Sharding / partitioning. Static shard map (P12); document→shard by hash or routing key. Re-sharding is an indexer concern (out of scope). Per-shard segment merge (indexer) reduces #segments → fewer per-query tasks (faster) but is an index-side operation.
  • Replication pressure. Replicas serve reads (QPS) + provide hedge targets for tail latency; the planner is read-only so replicas are trivially consistent per generation.
  • Coordination overhead. Two-round query-then-fetch (P12): query round returns ids+scores (small), fetch round returns docs (only the final top-k) — bounds network. Global-IDF gather adds one cached round per generation (consistency vs latency tradeoff).
  • Network fanout. = #shards per query; HTTP/2 multiplexing (ADR-09) amortizes connections; per-shard deadline + partial bounds the worst case.
  • Scheduler saturation. Bounded per-query thread budget prevents one heavy query from starving the pool (ADR-12); work-stealing balances segments; admission control (cost circuit breaker) sheds over-budget queries.
  • Storage growth. Index growth is the indexer's domain; the planner's RAM grows with term-dict + caches + resident postings — bounded by budgets and shard count.
  • Metadata scaling. Stats cache + global-IDF gather scale with #terms × #shards; cached per generation; refresh cost amortized over the generation's query volume.
  • Distributed planning (future). Cross-cluster federation + adaptive/feedback planning are PhaseDeferred("Deferred Features Register"); the current coordinator assumes a static shard map and per-query independent planning.

Mental Models & First Principles

The compressed insights an expert holds about this system. Each: the model, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — Dynamic pruning is a proof, not a heuristic. A doc is skipped only when its provable upper bound (sum of max_score()/block_max_score()) cannot reach the heap threshold θ. Predicts: pruning correctness hinges entirely on one property — bounds are true upper bounds (INV-1); everything else is just how aggressively you skip. Bug class without it: treating max_score as "approximately the max" → silently dropped top-k hits (FM-2). Applied: Principle 1/2, INV-1/INV-3, Phase 9 — WAND, Phase 10 — BlockMax-WAND + MaxScore.

  • MM2 — A DocIdSetIterator is a monotone cursor; the executor is a lock-step merge of cursors. Every operator (conjunction, disjunction, AndNot, two-phase) is a way to combine monotone streams that only ever move forward. Predicts: any backward advance or non-monotone doc_id() corrupts every operator above it; correctness reduces to one invariant (INV-2) at the leaves. Bug class without it: conjunction sync loops forever, or skips matches, when a leaf returns a doc < the lead. Applied: Principle 3, INV-2, Core Types §11.5–11.6, Phase 4 — Physical Iterator Operators.

  • MM3 — A tighter bound buys more skips but a too-tight bound silently corrupts results; the asymmetry is everything. Loosening a bound only costs latency; tightening it past truth costs correctness. Predicts: BMW (block bounds) skips far more than WAND (global bound) but is more error-prone — invest fuzzing effort proportional to bound tightness. Bug class without it: shipping a block-max bound that is right "almost always" → intermittent recall loss only on certain blocks. Applied: Principle 1/2, INV-1, Phase 5 — BM25 (bound derivation), Phase 10 (block bounds), Phase 3 (expansion bounds).

  • MM4 — Selectivity is the planner's only knowledge of the future; order by it. The rarest clause (lowest df) seen first drives the fewest advance probes — rarest-term-first conjunction ordering is the single highest-leverage plan decision. Predicts: a wrong cardinality estimate yields a slow plan, never a wrong result (the estimate/result firewall); correlated terms (independence assumption fails) are a latency incident, not a correctness one. Bug class without it: ordering by clause text position → the densest term leads → orders of magnitude more decode work. Applied: Principle 7, Phase 7 — Selectivity & Cardinality, Phase 8 — Cost Model + Planner.

  • MM5 — A query planner is a compiler. Text → tokens → AST → logical plan → optimized logical plan → physical plan is exactly lex → parse → IR → optimization passes → codegen; the rewrite engine is a fixpoint simplification pass; plan nodes are an exhaustive IR enum. Predicts: every compiler discipline transfers — total match over node types, equivalence-preserving rewrites, deterministic lowering — and stringly-typed plans rot the same way stringly-typed IR does. Bug class without it: ad-hoc plan handling that silently mishandles a new node type. Applied: Principle 12, Phase 1 — Lexer/Parser/AST, Phase 6 — Rewrite, Phase 8 — Planner.

  • MM6 — A cache is correct only if a hit is indistinguishable from recomputation; the generation key is the proof. Caches add no semantics — a FilterKey/QueryKey that pins the immutable searcher generation guarantees a hit equals a fresh compute. Predicts: every cache correctness bug reduces to a stale key (missing generation, or generation not bumped on reopen), so the cache is contained: worst case, disable it for a pure latency cost. Bug class without it: a filter bitmap reused across a generation that deleted docs → deleted docs resurface (FM-5, INV-6/INV-8). Applied: Principle 14, INV-6/INV-13, Phase 11 — Filters & Caching; also the cheapest oracle is a mock (mock-index, Phase 0).

  • MM7 — At fan-out N, tail latency is the slowest-of-N, not the average. A scatter-gather query is only as fast as its slowest shard; p99 of the whole is driven by the p99 of any single shard amplified by N. Predicts: adding shards improves throughput and per-shard work but worsens tail-latency exposure — so partial results + hedging are not optional features, they are the structural answer to fan-out. Bug class without it: fail-closed on one slow shard → whole-query unavailability; or unbounded waits that ignore the deadline. Applied: Principle 9, INV-9/INV-11, paper P14 (Dean), Phase 12 — Distribution, Scalability Analysis, Back-of-Envelope Capacity Model.

  • MM8 — Stable pagination requires a total order, and the cursor must be that order. Top-k is a partial order on score; pagination needs a total order, so ties break by ascending docId (INV-4) and search_after compares against exactly that (score, docId) tuple. Predicts: any divergence between the heap comparator and the cursor comparator (or any nondeterministic tie-break / float-sum order) makes a doc appear on two pages or none. Bug class without it: search_after dup/skip under equal scores. Applied: Principle 4, INV-4/INV-10, Core Types §11.10, Phase 12 — Pagination.

  • Tantivy. The one different decision: Tantivy is a single-codec Rust monorepo — its postings format, scorers, and collectors are co-designed and tightly coupled — where this blueprint inserts a codec-agnostic index-api seam. Tantivy wins when you want a fast, embeddable Rust search library and will never swap the postings format, so the indirection this design pays for buys nothing (R2).   • PISA. The one different decision: PISA is an offline-built, read-only research engine optimized for benchmarking pruning algorithms over a fixed index, with minimal operational surface.   • Vespa. The one different decision: Vespa is a natively distributed serving engine that fuses structured search, tensor/ML ranking, and real-time writes in one cluster with its own dispatch and content layers — far beyond this blueprint's static-shard, BM25-only, read-only coordinator. It wins for large-scale low-latency serving that needs ML ranking and live updates as first-class concerns (its weakAnd is the WAND-class operator this design mirrors, R6); this blueprint intentionally scopes those out (non-goals, Goal §1).

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints table (§4). Formulas shown; inputs are §4 values.

  • C1 — Postings bytes per doc (per shard). 200 GB postings ÷ 100M docs/shard ≈ 2,000 bytes/doc of postings on average across all its terms. Frames the IO budget: the hot loop must skip most of this, not decode it (Phase 4 skip-list advance).

  • C2 — Average postings bytes per unique term. 200 GB ÷ 50M unique terms ≈ 4 KB/term average posting-list size. With a 128-doc block (§4), a 4 KB list is ~tens of blocks → skip-list jumps (Phase 4) save decoding ~all but the landed block.

  • C3 — Docs scored per pruned top-10 query. §4 sets WAND/BMW ≤ 20% of candidates scored. For a 3-term OR where each term has df ≈ 1M: full-OR candidate set ≈ |t1 ∪ t2 ∪ t3| ≤ 3M; pruned scoring ≤ 0.20 × 3M = 600K score calls, target ≥ 5× wall-time speedup (Phase 9/10). This is the headline efficiency metric (docs_scored / docs_matched).

  • C4 — Score-call budget at p50. p50 ≤ 5 ms (§4) for a warm 2–4 term top-10 query. If a BM25 score() + heap op costs ~50 ns (table-lookup norm, no pow/log in the loop, Phase 5), then 5 ms ÷ 50 ns = 100,000 score calls fit the p50 budget — consistent with pruning keeping scored docs in the 10⁴–10⁵ range, not the 10⁶ full-OR range. Confirms C3: without pruning, p50 is unattainable.

  • C5 — Single-node QPS vs core budget. §4: ≥ 2,000 simple QPS/node and thread pool = #cores. On a 16-core node, 2,000 QPS ÷ 16 cores = 125 queries/core/s → 8 ms/query/core of CPU budget for a simple query — leaving headroom under the 5 ms p50 for queueing and merge. Complex queries (≥ 300 QPS/node) get 16 cores ÷ 300 ≈ 53 ms·core budget, matching the heavier phrase+filter path.

  • C6 — Filter cache RAM ceiling. §4: filter cache default 10% of heap; Roaring ≈ 1 bit/doc worst case. For a 100M-doc shard, one dense filter bitmap ≈ 100M ÷ 8 = 12.5 MB; a 4 GB heap → 0.10 × 4 GB = 400 MB budget holds ≈ 400 MB ÷ 12.5 MB ≈ 32 dense filters (far more when sparse, since Roaring compresses). Sets the eviction pressure point (Phase 11, ADR-24).

  • C7 — Query cache footprint. §4: query cache default 1% of heap. A cached merged TopK of k=100 ScoreDoc{score:f32, doc:u64} ≈ 100 × 12 bytes ≈ 1.2 KB. A 4 GB heap → 0.01 × 4 GB = 40 MB → 40 MB ÷ 1.2 KB ≈ 33,000 cached top-100 results — ample for hot repeated queries, hence "conservative, disabled for heavy queries" (Phase 11).

  • C8 — Cross-shard fan-out bandwidth (query phase). §4: 50 shards, query phase returns top-k ids+scores only. For k=100: each shard returns 100 × 12 bytes ≈ 1.2 KB; full fan-out gather ≈ 50 × 1.2 KB = 60 KB per query — trivial. This is why query-then-fetch exists: the fetch phase moves real documents only for the global top-k, not 50× candidate sets (Scalability Analysis).

  • C9 — Tail-latency amplification at fan-out 50. Per MM7, if a single shard's p99 single-shard latency is 80 ms (§4) and shard latencies were independent, the probability all 50 beat 80 ms is 0.99^50 ≈ 0.61 — i.e. ~39% of queries would have some shard at its p99. This is exactly why §4 budgets cross-shard p99 at 150 ms (not 80 ms) and why partial results + hedging are mandatory (Principle 9, Phase 12), not optional.

  • C10 — Startup mmap/stat budget. §4: searcher open ≤ 500 ms/shard for 100M docs. Loading per-term stats for 50M terms in 500 ms demands 50M ÷ 0.5 s = 100M stat-entries/s — only feasible if stats are precomputed and mmap'd (read, not parsed), confirming the index-api "stats precomputed at index time" assumption (Core Types §11.8) and the ≤ 1 s RTO (§4).

  • C11 — Segment parallelism ceiling. §4: 10–100 segments/shard, one query ≤ #segments threads (bounded). On a 16-core node a single query uses ≤ 16 threads even at 100 segments, so segments are batched ~100 ÷ 16 ≈ 7 per thread → bounded per-query CPU, preventing one heavy query from starving the pool (ADR-12, Scalability Analysis scheduler saturation).

  • C12 — Deadline-check overhead amortization. §4: deadline checked at block boundaries (128 docs), default budget 1 s. A per-block check over a 600K-doc scored set (C3) is 600K ÷ 128 ≈ 4,700 checks — negligible vs per-doc checking (600K), which is exactly why the deadline is amortized per block, not per doc (Principle 8, INV-9, Phase 12).

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same problem (not parameter tweaks). Each: sketch, winning regime, the real system embodying it, why this blueprint rejected it.

ALT-A — Term-At-A-Time (TAAT) with score accumulators. Instead of DAAT (all postings walked in lock-step by docId), process one term's entire posting list at a time, accumulating partial scores in a per-doc accumulator array, then sort accumulators for top-k.

  for each term t (rarest→common):
      for each (doc, tf) in postings(t):
          acc[doc] += contribution(t, doc)     # whole list, one term
  topk = partial_sort(acc, k)                   # after all terms

Winning regime: disjunctive queries over small/medium collections where the accumulator array fits in cache and you want simple, branch-predictable inner loops; also score-at-a-time variants with impact-ordered postings and early termination. Real system: classic TREC-era engines and Anh & Moffat impact-ordered designs; the framing in Turtle & Flood (P3). Why rejected here: the accumulator array is O(N) memory per query (100M docs/shard, §4) and TAAT does not naturally exploit the collector threshold for document skipping — DAAT + WAND/BMW prunes on θ as the heap fills (MM1), hitting the ≤ 20%-scored target (§4) that TAAT cannot. DAAT is the model in Phase 4/9/10.

ALT-B — Build the index too (own the codec, no index-api seam). Collapse the index-api boundary; the planner and a bespoke postings codec/IndexWriter are one coupled unit, with scorers inlined against the concrete posting format.

  IndexWriter ─▶ [own codec: postings + skip + block-max] ─▶ Searcher
       └────────────── one crate, no trait indirection ─────────┘

Winning regime: a single-product engine that will never swap formats and needs the last few percent of advance/block_max performance by inlining the concrete iterator (no vtable, no generic seam). Real system: Tantivy (R2) and Lucene (R1) both own their codecs. Why rejected here: it conflates two hard problems (index construction and query planning) and makes the planner untestable without a full indexer — the mock-index (Phase 0, MM6) and codec-agnostic IO-cost modeling depend on the ADR-02 seam. Index construction is an explicit non-goal (Goal §1). The "when rejected wins" cell of ADR-02 names this exact regime.

ALT-C — Selinger-style cost-based plan enumeration. Replace the heuristic rarest-first + strategy-threshold optimizer with full dynamic-programming enumeration of join/evaluation orders and strategies, costing each candidate plan and picking the global minimum.

  enumerate all evaluation orders × strategies → cost each → argmin
  (DP over subsets, à la System R join ordering)

Winning regime: complex relational queries with many joins where plan-space exploration pays off and queries are expensive enough to amortize a millisecond of planning. Real system: relational query optimizers (System R / its descendants in PostgreSQL etc.; the model in book B6). Why rejected here: boolean search queries are tree-shaped, not join-graphs; the optimizer must run in microseconds vs the query it optimizes (Phase 8's own Performance Concerns, 8.7), and rarest-first ordering plus a few strategy thresholds capture nearly all the available win (MM4). Full enumeration would blow the planning budget (HQ10) for negligible plan improvement. The plan cache (Phase 11) further amortizes the cheap optimizer to ~0.

ALT-D — Single fat index, no sharding (vertical-only). One enormous segment/searcher holds the whole collection on one very large machine; no scatter-gather, no global-IDF gather, no partial results.

  client ─▶ searchd ─▶ [one searcher: all docs, all segments] ─▶ ranked hits

Winning regime: collections that fit one machine's RAM/disk where avoiding cross-shard tail-latency (MM7) and global-IDF complexity is worth the vertical-scaling ceiling; also the embeddable library deployment (Goal §1) where there is exactly one shard. Real system: single-node PISA (R3) and any embedded Lucene/Tantivy use. Why rejected as the default here: DocId=u32 caps a segment at 2³¹ docs (ADR-04, HQ13) and §4 targets up to ~5B cluster docs, which no single node holds; so the design supports the single-shard case (it is literally fan-out 1) but builds scatter-gather (Phase 12) for the headline scale. This is the regime in ADR-13's "all-sync wins" cell.

Glossary

  • Posting list — the list of (docId, freq, [positions]) for one term in one field; the unit of the inverted index.
  • Inverted index — term → posting list map + term dictionary; the read-only structure the planner queries (index-api).
  • Term dictionary — sorted/FST map from term bytes to posting-list location + stats; supports prefix/wildcard/fuzzy enumeration by automaton.
  • FST (finite-state transducer) — minimal acyclic automaton over terms; compact term dictionary enabling automaton-intersection enumeration (ADR-10).
  • DAAT (Document-At-A-Time) — evaluate all terms' postings in lock-step by ascending docId, scoring each candidate doc fully before moving on; the model WAND/BMW/MaxScore use.
  • TAAT (Term-At-A-Time) — process one term's whole posting list (accumulating partial scores) before the next; alternative to DAAT, weaker for top-k pruning.
  • DocIdSetIterator (DISI) — the iterator over a doc-id set; next_doc/advance(target)/doc_id/cost (INV-2).
  • Conjunction (leap-frog) — AND of iterators: advance the lead (rarest), sync others to it; the doc all share is a match.
  • Galloping (exponential search) — advancing an iterator far ahead by exponential then binary probing within a block; amortized-cheap advance.
  • Disjunction — OR of iterators, merged via a min-heap (priority queue) keyed by docId.
  • AndNot — include-iterator minus exclude-iterator (MUST_NOT exclusion).
  • Skip list / skip pointers — sparse index over a posting list enabling advance to jump without decoding every block.
  • Block-max metadata — per-block (e.g. 128-doc) maximum impact/score, enabling block-level skipping (BMW); read via index-api (P10).
  • Two-phase iterator — cheap approximation (a superset, INV-5) + expensive confirm (matches()); used for phrases/expensive predicates.
  • Selectivity — fraction of docs a clause matches (≈ df/N); low selectivity (rare) = good lead for conjunction.
  • Cardinality estimation — predicted #docs a (sub)plan matches; drives ordering, never correctness (Principle 7).
  • df (document frequency) — #docs containing a term; cf (collection frequency) — total occurrences across the collection.
  • IDF (inverse document frequency) — ln(1 + (N-df+0.5)/(df+0.5)); rarer terms weigh more; always ≥ 0 (INV-7).
  • BM25 — the probabilistic ranking function (k1, b, IDF, length-norm); the score the planner optimizes around (Robertson & Zaragoza).
  • k1 / b — BM25 params: k1 = tf saturation, b = length-normalization strength.
  • Field norm — quantized doc-field length used in BM25 length normalization; must match index-time (INV-12).
  • Impact / impact-ordered postings — postings ordered by score contribution rather than docId; enables score-at-a-time pruning (optional, ImpactsMeta).
  • Top-k — the k highest-scoring docs; maintained in a fixed-capacity min-heap (root = least competitive).
  • Threshold (θ) / min-competitive score — the heap root's score; the bar a doc must beat to enter top-k; rises as the heap fills; feeds pruning (INV-3).
  • WAND — Weak-AND / pivot pruning: skip docs whose summed term upper bounds can't reach θ (Broder 2003).
  • BlockMax-WAND (BMW) — WAND refined with per-block upper bounds to skip whole blocks (Ding & Suel 2011); production default (ADR-06).
  • MaxScore — partition terms into essential/non-essential by upper bound; iterate only essentials, probe non-essentials when they could compete (Turtle & Flood 1995).
  • Pivot — in WAND, the doc/term at which accumulated upper bounds first reach θ; the next candidate to consider.
  • Safe pruning — pruning that provably never changes the top-k vs exhaustive (depends on true upper bounds, INV-1/INV-3).
  • Upper bound (max_score / block_max_score) — a value ≥ any real score the scorer can produce (for the block); the pruning contract (INV-1, Principle 2).
  • Exhaustive DAAT baseline — scoring every match with no pruning; the correctness oracle for INV-3 (--exact).
  • Predicate pushdown / filter-before-score — applying a non-scoring filter (bitset) before scoring so only passing docs are scored (Principle 6).
  • Filter vs query — a filter constrains (0/1, cacheable, no score); a query ranks (scored). FILTER occur (RW-10).
  • ConstantScore — wraps a matcher to contribute a fixed score (no per-doc scoring); used for filters + over-limit expansions.
  • Roaring bitmap — compressed doc-id-set representation (array/bitmap/run containers) for the filter cache; fast and/or/andnot/rank/select (ADR-08).
  • Plan cache — cache of the optimized physical plan shape for repeated query shapes (optimizer is pure, INV-10).
  • Query cache — optional cache of merged top-k results per (query, shard, generation) (INV-6/INV-13).
  • EXPLAIN — first-class output: the physical plan tree + estimated-vs-actual cardinality + per-doc BM25 score breakdown (Principle 10).
  • Plan dump — textual/JSON rendering of the chosen physical plan + costs + prune mode; the operator's window into the planner.
  • Generation — a monotonic id for an immutable searcher snapshot; the cache key (INV-6) and reproducibility anchor.
  • Live-docs — bitset marking non-deleted docs; deletes are logical until merge; results must honor it (INV-8).
  • Segment — an immutable sub-index; queries execute per segment then merge (Principle 13).
  • Shard — a horizontal partition of the collection across nodes; scatter-gather queries fan out to shards.
  • Scatter-gather (query-then-fetch) — the distributed protocol: query phase gathers top-k ids+scores, fetch phase retrieves the docs (P12).
  • Partial results — a degraded result (some shards missing) flagged partial: true instead of failing (Principle 9, INV-9).
  • search_after — cursor-based deep pagination using the (score, docId) of the last seen doc under the INV-4 total order.
  • track_total_hits — controls total-hit counting: exact, capped-at-N (AtLeast), or early-terminated.
  • Levenshtein automaton — DFA accepting all strings within edit distance k of a term; intersected with the FST for fuzzy enumeration (Schulz & Mihov, ADR-11).
  • maxExpansions — bound on multi-term (wildcard/prefix/fuzzy) expansion; over-limit → ConstantScore bitset (RW-7).
  • Slop — the positional tolerance of a phrase query (max term displacement); slop 0 = exact phrase.
  • Analysis parity — query-time analysis matching index-time analysis; required or recall silently drops (Principle 11).
