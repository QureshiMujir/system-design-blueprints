Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Raft — strong leader, term-indexed log

Client -> Leader --AppendEntries(term,index)--> Followers
                <----- ack(term,index) ---------
Leader commits on majority ack; followers never independently propose.

Regime: small-to-medium clusters where operational simplicity and a single state diagram matter more than "any node can drive Phase 1." Real system: etcd/raft, Consul, CockroachDB's Raft-based ranges. Why rejected: safety, not merely liveness, depends on the leader-election protocol being airtight (MM4's counterpoint) — this blueprint wants a safety proof holding with zero, one, or transiently many "leaders."

EPaxos — leaderless, dependency-graph ordering

Client -> any Replica --PreAccept--> Replica quorum
       <---- merge dependency-graph votes ----
Commit occurs once the quorum agrees on the dependency set;
execution order is a topological sort of the graph, not a log index.

Regime: geo-distributed, low-conflict workloads where saving the leader-forwarding hop matters more than protocol complexity. Real system: EPaxos (Moraru, Andersen, Kaminsky 2013). Why rejected: dependency-graph execution ordering is materially harder to audit line-by-line against a paper (P12) than Basic Paxos's two-phase protocol — this project's goal is a from-scratch teaching implementation of the original algorithm.

Viewstamped Replication — primary-backup, view-numbered

Client -> Primary --Prepare(op,view,opnum)--> Backups
                <------- PrepareOK ----------
Primary commits on majority PrepareOK; a view-change protocol
elects a new primary on suspected failure (view number strictly increases).

Regime: teams wanting an explicit, named view-change protocol rather than an ambient failure-detector-driven leader overlay. Real system: Oki & Liskov 1988's VR and its modern descendants. Why rejected: VR couples safety to the current view/primary the same way Raft does — this blueprint specifically wants classic Paxos's leader-optional safety argument.

Chain Replication — primary-order chain, no quorum voting

Client-write -> Head -> Node2 -> ... -> Tail -> ack -> Client
Client-read  -> Tail   (always fully replicated; no quorum check needed)

Regime: high-throughput, low-read-latency workloads where a full-chain write latency is an acceptable trade for reads needing zero quorum coordination. Real system: van Renesse & Schneider 2004's Chain Replication. Why rejected: failure recovery needs a separate, carefully-ordered chain-reconfiguration protocol (not quorum-based), and write latency scales linearly with chain length rather than being bound to one quorum round-trip.
