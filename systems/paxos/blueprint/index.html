Project Number: 93

Project Name: Paxos

Status: specification — locked

1. Goal & Scope

Build classic Lamport Paxos — Basic Paxos (single-decree) per The Part-Time Parliament (Lamport 1998) and Paxos Made Simple (Lamport 2001), plus Multi-Paxos log replication per Paxos Made Live (Chandra, Griesemer, Redman 2007) — as a reusable Rust consensus library and reference deployment: durable acceptor state (WAL + fsync), a Phi-accrual/Ω failure-detector leader-election overlay, log replication with snapshotting and compaction, α-parameter membership reconfiguration, a TCP transport, a linearizable client API, a deterministic simulator, and TLA+/Jepsen/Maelstrom conformance harnesses. The deliverable is the original Lamport protocol — not Raft, not Viewstamped Replication, not Zab — built so every safety argument in Paxos Made Simple section 2.2 (P1, P2, P2a, P2b, P2c) maps onto one named type or function in the source tree.

Phase-0 deliverable — numbered module/crate list:

  1. paxos-core — ballot, message, acceptor/proposer/learner state machines (no_std-friendly).
  2. paxos-storage — WAL + content-addressable snapshots, fsync-before-respond durability.
  3. paxos-failure-detector — Phi-accrual detector (Hayashibara 2004) + Ω wrapper (Chandra-Toueg 1996).
  4. paxos-multi — Multi-Paxos log, stable-leader optimisation, gap-fill, reconfiguration.
  5. paxos-net — TCP transport, batching, pipelining.
  6. paxos — public client API (linearizable / read-index / lease reads).
  7. paxos-sim — deterministic single-threaded simulator + TLA+ trace replay.
  8. paxos-cli, paxos-bench, paxos-fuzz — operational and verification tooling.

System boundaries.

  • Provides: safe single-decree and multi-decree consensus over a replicated log; durable crash-recover acceptor state; leader-based throughput optimisation; live membership reconfiguration; linearizable client reads/writes.
  • Delegates: application state-machine semantics (the caller supplies a deterministic SM, I11); transport encryption (mTLS is PhaseDeferred("§19.10")); any distributed-transaction layer above the log (out of scope — a Paxos log is a building block, not a database).
  • Does NOT provide: Byzantine fault tolerance (crash-stop + omission only — Byzantine acceptors are Blueprint #94, PBFT); a query/SQL layer; automatic geo-sharding.

Non-goals: Byzantine tolerance; EPaxos/Fast Paxos/Generalized Paxos/Vertical Paxos/Disk Paxos as shipped main-line features (see Alternative Architectures §36 and Deferred Features Register §37); a general-purpose database.

Deployment model: one process per node, 3/5/7/9-node clusters (odd cardinality), private network (VPN or datacenter LAN — plaintext TCP is not safe on a public network until PhaseDeferred("§19.10") lands), Docker/Kubernetes reference topology (§10, §26).

Target users/operators: distributed-systems engineers building a replicated-log, lock- service, or config-store primitive on top; SRE operators running the reference deployment who consult the runbooks in §26.

What later phases unlock: Phase 0 (§12) unlocks a running skeleton and governance scaffold; each subsequent phase raises a maturity rung, culminating in a chaos-soaked, TLA+-verified, Jepsen-clean candidate at Phase 11 (§23).

Recommended language: Rust 1.78+ (edition 2021). Rationale: the borrow checker statically forecloses the aliased-mutable-state class of bug that is the most common root cause of hand-rolled Paxos defects — concurrent mutation of AcceptorState (§11.4) without synchronisation; zero-cost async/await via tokio (ADR-03); no_std capability keeps the safety-critical paxos-core crate embeddable. Rejected: Go — no compile-time aliasing control (the production etcd/Raft codebase leans on the runtime race detector, not prevention); C++ — manual memory-safety burden with no matching safety payoff for this domain; Java — GC pause tail latency conflicts directly with the p99 commit-latency target in §4; Erlang/Elixir — excellent supervision-tree ergonomics but weak zero-copy binary handling for a WAL-bound workload.

Prerequisites: FLP impossibility (§5 Papers), the CAP theorem, the two-generals problem, Lamport logical clocks, quorum systems (majority and flexible), state-machine replication theory (Schneider 1990), and the ballot/proposal numbering scheme. A reader should be able to state P1/P2/P2a/P2b/P2c (§8.2) from memory before starting Phase 1.

Estimated timeline: Phase 0 in 1 week; full system (Phase 0 → Phase 11) in 5–7 months at one engineer, part-time.

Deferred features (registered in full at §37 Deferred Features Register):

  • mTLS inter-node transport → PhaseDeferred("§19.10").
  • QUIC transport backend → PhaseDeferred("§19.10").
  • Byzantine fault tolerance → PhaseDeferred("§24") (see Blueprint #94, PBFT).
  • Fast Paxos / EPaxos as shipped features → PhaseDeferred("§36").
  • Joint-consensus reconfiguration (Raft-style, vs. the α-parameter default) → PhaseDeferred("§18.6").
  • WASM build target → PhaseDeferred("§22.10").
  • Formal (Coq/Isabelle) verification of the acceptor step function → PhaseDeferred("§29").
  • Geo-distributed multi-AZ deployment recipe → PhaseDeferred("§31").

2. Why Build This

Paxos is the consensus algorithm the literature has spent thirty-five years explaining badly, and the one every serious replicated state machine on the planet runs or derives from. Google Chubby is Paxos (Burrows 2006). Google Spanner runs Multi-Paxos inside each participant group, under TrueTime (Corbett et al. 2012). Google Megastore is a per-entity-group Paxos that Spanner inherited (Baker et al. 2011). Apache Cassandra's lightweight-transactions path is Basic Paxos per partition. The CockroachDB/etcd lineage chose Raft because Raft is easier to teach — but every senior engineer at those shops has read Paxos Made Live and knows precisely which corners Raft cuts to get there (Howard & Mortier 2020, §5 Required Reading).

This project is the smallest stack that still teaches the full surface: the ballot/proposal numbering scheme (P3 — the #1 source of hand-rolled bugs is reusing a round number across restarts); the two-phase protocol (§8.2 — Prepare/Promise/Accept/Accepted, whose state machine you should be able to reproduce from memory); durable acceptor state (§8.3, I2 — the fsync-before-respond invariant; recovery from any WAL prefix, I7); a real failure detector (Ω per Chandra-Toueg 1996, implemented as Phi-accrual per Hayashibara 2004, Phase 3/§15); the leader-election overlay that Multi-Paxos needs for liveness but not safety (P5 — the exact line that separates Paxos from Raft); Multi-Paxos's skip-Phase-1 log-replication trick (Paxos Made Live section 4, Phase 4/§16); snapshots and log compaction (Phase 5/§17, without which crash-recovery time grows unbounded); the α-parameter reconfiguration protocol (Paxos Made Live section 5.3, Phase 6/§18); and the client-API layer (linearizable reads via leader, read-index, lease reads as an opt-in with an explicit clock-assumption ADR-18, Phase 8/§20).

By the end of Phase 11 (§23) you know exactly why Raft chose a strong leader where Paxos allows any acceptor to drive Phase 1 (Comparative Architecture Table §33); exactly which sentence of Paxos Made Simple the EPaxos optimisation generalises (Alternative Architectures §36); exactly which fault-tolerance guarantee survives a network partition healing into a quorum without a leader (Failure Modes & Recovery §25, FM7); and exactly which lines of your code execute when a five-node Paxos cluster commits a value mid-leader-handoff (Phase 4 §16, Phase 9 §21 simulator trace).

The deliverable stays small enough to actually finish: no Byzantine tolerance (Blueprint #94); no Fast Paxos/EPaxos/Generalized Paxos/Vertical Paxos/Disk Paxos in the main line (Alternative Architectures §36, Deferred Features Register §37); no distributed-transaction layer on top. One stack, the original algorithm, done correctly — that tight focus is the only reason the timeline is months and not years.

You build this so that when a production replicated state machine misbehaves at 3 a.m. — a leader hand-off that drops a slot, a learner that disagrees with the acceptors, a reconfiguration that produces two non-intersecting quorums, a partition-heal that produces split-brain because someone violated P2c under time pressure — you know which page of The Part-Time Parliament, which paragraph of Paxos Made Live, and which line of your own code to open.

  • Explain why the fsync-before-respond ordering (I2) is what makes crash-recover safe rather than merely "durable," and reproduce the ordering bug from memory — Phase 2 (§14).

Three properties of this architecture are referenced throughout and must never be violated by a later phase. First, proposer/acceptor/learner are state-machine traits (§11), not threads or processes; one physical node hosts all three roles and routes locally-produced messages through the identical dispatch path used for remote messages (§14.2), so paxos-sim (§21) can substitute one for the other with zero behaviour change. Second, acceptor state and proposer state are strictly separated (P12, I1): an acceptor's promised_ballot is durable disk state under fsync; a proposer's in-flight ballot is RAM-only and resets on restart — conflating the two produces the canonical "restart re-issues a promised ballot" safety bug (Phase 1 §13.6). Third, the protocol layer (proposer/acceptor/learner, §13) has zero knowledge of leaders, failure detectors, batching, or pipelining — those are optimisations layered on top per Paxos Made Live §4 (P5), and removing any of them must not affect safety, only throughput. A "leader" or "batching" code path discovered inside the protocol layer is a design defect.

6. Design Principles

P1 — Correctness over performance, every time. The safety properties (I1–I9) are non-negotiable; no optimisation ships if it can violate them. Tradeoff: slower shipping of throughput features. Operational implication: every perf feature (batching, pipelining, lease reads) is gated behind a feature flag plus an ADR naming the safety property it interacts with. Violation cost: silent split-brain in production.

P2 — Single-decree before multi-decree. Phase 1 (§13) ships Basic Paxos in isolation before Phase 4 (§16) ships the log. Tradeoff: slower path to a "useful" system. Operational implication: a single-decree unit test never touches Multi-Paxos machinery. Violation cost: an invariant bug that is actually in the single-decree core gets misdiagnosed as a log bug.

P3 — Classic ballot/proposal numbering: (round: u64, proposer_id: NodeId), lexicographic, monotonic per proposer, persisted across restarts. Tradeoff: 12 bytes per ballot instead of 8. Operational implication: round must be fsync'd (or wall-clock-derived) before use, I13. Violation cost: ballot reuse across a restart, the most common hand-rolled-Paxos bug.

P4 — Persistent state on disk before promises (fsync-before-respond, I2). An acceptor must not reply Promise until promised_ballot is durable, nor Accepted until accepted_ballot/ accepted_value are durable. Tradeoff: every reply pays one fsync (amortised by batching, ADR-12). Operational implication: enforced at the dispatch boundary (§14.2), not at call sites. Violation cost: crash-recover becomes a safety violation, not merely a liveness blip.

P5 — Leader-based optimisation is a liveness lever only; Paxos safety never depends on it. This is the line that separates Paxos from Raft (Comparative Architecture Table, §33). Two nodes both believing they lead compete via ballots; one wins each slot; safety holds, throughput suffers. Tradeoff: duelling-proposer livelock is possible without a detector. Operational implication: Phase 3 (§15) adds Ω/Φ purely to raise throughput. Violation cost: if you find yourself gating safety on "am I the leader," you have silently built Raft without its proofs.

P6 — Lease reads are opt-in with an explicit clock assumption (ADR-18); linearizable reads (leader no-op) are the safe default. Tradeoff: linearizable reads cost one Paxos round; lease reads cost none but require bounded clock skew. Operational implication: the clock assumption is documented, not silent. Violation cost: an undocumented lease assumption produces stale reads the operator cannot explain.

P7 — Recovery is correct from any prefix of disk state (I7). The WAL is append-only; a torn tail is truncated to the last CRC-valid record. Tradeoff: recovery code is the only WAL reader — a second code path would double the audit surface. Operational implication: WAL records are written in causal order so a Promise record always precedes any dependent Accepted record. Violation cost: a partial-write recovery bug reintroduces a promise the acceptor never actually made.

P8 — Snapshots are content-addressable (I8). A snapshot is (slot, BLAKE3-hash, bytes); two acceptors snapshotting the same slot of a deterministic SM (I11) produce the same hash. Tradeoff: one BLAKE3 pass per snapshot. Operational implication: learner catch-up (§16.3) short-circuits via hash comparison. Violation cost: a non-deterministic SM silently produces divergent hashes that catch-up code cannot distinguish from corruption.

P9 — Reconfiguration via the α-parameter trick (Paxos Made Live section 5.3), not joint consensus, in the main line. Tradeoff: joint consensus is conceptually cleaner but needs two reconfiguration rounds; α needs one but couples reconfig timing to in-flight slot count. Operational implication: α ≥ 1 is a hard safety floor (I10); α=3 is the liveness-tuned default. Violation cost: α=0 loses a value chosen under the old config (§18.3).

P10 — Quorum intersection is a type-level invariant (I6). Quorum<'a> cannot be constructed from a sub-majority slice (§11.2). Tradeoff: a small amount of type-system ceremony. Operational implication: is_quorum_satisfied cannot compile against fewer than a majority. Violation cost: without the type gate, a refactor could silently accept a minority as a quorum.

P11 — Determinism is a property of the application state machine, not the network (I11). Replaying the log from slot 0 must produce identical state on every replica (Schneider 1990). Tradeoff: the library cannot enforce this at compile time; it documents and canary-tests it. Operational implication: paxos-sim (§21) runs a determinism canary per SM implementation. Violation cost: a HashMap-ordered SM silently diverges its BLAKE3 snapshot hash (P8) across replicas.

P12 — Protocol code is auditable line-by-line against the paper. Every paxos-core function carries a doc-comment citing the exact section of Paxos Made Simple or Paxos Made Live it implements. Tradeoff: documentation discipline overhead. Operational implication: a reviewer can verify P2c with the paper open and no other tooling. Violation cost: protocol drift goes undetected until a conformance fixture (N.5) fails.

P13 — Conformance is the contract, not a suggestion. TLA+ trace conformance, Jepsen linearizability, Maelstrom workloads, and the 30-day chaos soak (§23.5, §28) gate every release; a regression is a merge block. Tradeoff: CI wall-clock cost. Operational implication: conformance/runner emits a machine-readable report (§23.5) consumed by CI. Violation cost: a silent regression ships and is discovered in production instead of CI.

P14 — Byzantine faults are explicitly out of scope. This stack tolerates crash-stop and omission only; an acceptor that violates the protocol (rather than merely crashing) is not tolerated (§24). Tradeoff: a smaller, faster, more auditable system than a BFT one. Operational implication: the threat model (§24) states this boundary explicitly rather than leaving it implicit. Violation cost: deploying this stack in an adversarial-acceptor environment is a misuse, not a bug — Blueprint #94 (PBFT) is the correct tool there.

8. Domain Model / Protocol / Data Model

8.1 Message Taxonomy

Five wire messages carry Basic Paxos end to end (exact field signatures in §11.3): Prepare, Promise, Accept, Accepted, Learn. Multi-Paxos (§16) adds Heartbeat, CatchupRequest, CatchupResponse, ReconfigPropose — all composed from the same five primitives plus a SlotId.

8.2 The Safety Property Set (Paxos Made Simple section 2.2, verbatim)

  • P1. An acceptor must accept the first proposal that it receives.
  • P2. If a proposal with value v is chosen, every higher-numbered proposal that is chosen has value v.
  • P2a. If a proposal with value v is chosen, every higher-numbered proposal accepted by any acceptor has value v.
  • P2b. If a proposal with value v is chosen, every higher-numbered proposal issued by any proposer has value v.
  • P2c. For any v and ballot n: if a proposal (n, v) is issued, there exists a majority set S of acceptors such that either (a) no acceptor in S has accepted any proposal numbered < n, or (b) v is the value of the highest-numbered proposal < n accepted by any acceptor in S.

P2c is load-bearing: I5 (Promise carries both fields as one unit) and I6 (quorum intersection) exist solely to keep P2c provable; §16.1's "adopt the highest-accepted value from the quorum" rule is P2c's direct implementation.

8.3 Two-Phase Sequence — Single-Decree (canonical trace)

8.7 Worked Example — 3-Acceptor Single-Decree Commit

Node A proposes "hello" at ballot (1, A) against {A, B, C} (quorum = 2, §4 row 2). Prepare reaches all three; none has prior state, so each promises and fsyncs promised_ballot=(1,A). A collects the quorum, sees no prior accepted value in any Promise, so P2c case (a) applies: A proposes its own value, "hello". Accept reaches all three; each has promised_ballot <= (1,A), so each fsyncs accepted_ballot=(1,A), accepted_value="hello" and replies Accepted. The learner counts 2 Accepted(1,A) — quorum met (I9) — and emits Learn(slot=0, (1,A), "hello"). Final acceptor states are bit-identical across A, B, C: {promised:(1,A), accepted:(1,A), value:"hello"}.

8.9 Failure-Path Example — Leader Crash Mid-Round

Leader L at ballot (5,L) broadcasts Accept(5,L,slot=42,"v") to {A,B,C}. A acks Accepted; L crashes before B/C reply. Ω (§15) elects L', which issues a bulk Prepare at ballot (6,L') covering slot 42 (§16.1). A's Promise reveals accepted=(5,L,"v") — the only accepted pair in L''s quorum. P2c forces L' to re-propose "v" (never a new client value) for slot 42; L' broadcasts Accept(6,L',42,"v"); on quorum, slot 42 commits with the original value. No data loss, no client-visible divergence (§16.2 fill_gaps, FM4).

11. Core Schema & Types

All load-bearing types, as signatures only (no bodies, per the no-code rule). Every type below is used identically across §10, the phases, and Appendix A (§39).

Foundational aliases (crates/paxos-core/src/lib.rs), used by every type in this section: pub struct SlotId(pub u64) — the log-position index (§8.4, §11.9); pub type Value = Vec<u8> — the opaque, application-defined payload carried by Accept/Accepted/Learn (§8.4) and interpreted only by the caller's StateMachine (§11.7). Both are Copy/Clone, wire-stable (ADR-04), and never persisted independently of the WalRecord/Message that embeds them.

11.1 Ballot (crates/paxos-core/src/ballot.rs)

pub struct Ballot { pub round: u64, pub proposer_id: NodeId }   // P3, ADR-08
impl Ballot {
    pub const BOTTOM: Self;
    pub fn next(self) -> Self;                                  // round += 1, same proposer_id
}
impl Ord for Ballot { /* lexicographic: round, then proposer_id — I3, I13 */ }

Ownership: value type, Copy. Mutation: immutable; replaced via next(). Concurrency: none (RAM-only in ProposerState, §11.5). Persistence: not itself persisted; embedded in WalRecord::Promise/Accepted (§11.8). Serialization: bincode, 12 bytes (ADR-04, ADR-08). Compatibility: field order is wire-stable; adding a field is a breaking change (§27).

11.2 NodeId and Quorum (crates/paxos-core/src/node.rs)

pub struct NodeId(pub u32);                                     // ADR-09
pub struct Quorum<'a> { members: &'a [NodeId], cluster_size: usize }
impl<'a> Quorum<'a> {
    pub fn try_new(members: &'a [NodeId], cluster_size: usize) -> Option<Self>;  // I6, P10
    pub fn members(&self) -> &[NodeId];
}

Ownership: Quorum borrows; never owns. Mutation: immutable once constructed. Concurrency: Send + Sync (read-only). Persistence: not persisted; recomputed from live membership state (§11.11). Serialization: n/a (control-plane type only). Compatibility: try_new's majority check is I6 — narrowing it is an automatic safety regression.

11.3 Protocol Messages (crates/paxos-core/src/message.rs)

pub struct Prepare { pub ballot: Ballot, pub slot: SlotId }
pub struct Promise  { pub ballot: Ballot, pub slot: SlotId, pub accepted: Option<(Ballot, Value)> }
pub struct Accept   { pub ballot: Ballot, pub slot: SlotId, pub value: Value }
pub struct Accepted { pub ballot: Ballot, pub slot: SlotId }
pub struct Learn    { pub slot: SlotId, pub ballot: Ballot, pub value: Value }
pub enum Message { Prepare(Prepare), Promise(Promise), Accept(Accept), Accepted(Accepted),
                   Learn(Learn), Heartbeat(Heartbeat), CatchupRequest(CatchupRequest),
                   CatchupResponse(CatchupResponse), ReconfigPropose(ReconfigPropose) }

Ownership: owned, Clone. Mutation: immutable once constructed (§8.4). Concurrency: sent across mpsc channels (§14.2) / TCP (§19.1). Persistence: not persisted directly; the subset relevant to safety is mirrored into WalRecord (§11.8) before any reply is sent (I2). Serialization: bincode, length-prefixed on the wire (§8.5, ADR-04). Compatibility: Message is a wire-stability boundary — a new variant is additive-only (§27).

11.4 Acceptor State (crates/paxos-core/src/acceptor.rs)

pub struct AcceptorState {
    pub promised_ballot: Option<Ballot>,     // I2, I4 — disk-resident
    pub accepted_ballot: Option<Ballot>,     // I2, I5 — disk-resident
    pub accepted_value: Option<Value>,       // I2, I5 — disk-resident, atomic with accepted_ballot
}
impl AcceptorState {
    fn handle_prepare(&mut self, msg: &Prepare) -> Option<Promise>;  // I4; caller must fsync first (I2)
    fn handle_accept(&mut self, msg: &Accept) -> Option<Accepted>;   // I4; caller must fsync first (I2)
}

Ownership: one instance per (node, slot), owned by the acceptor role. Mutation: mutated only by handle_prepare/handle_accept, both gated behind the dispatch-boundary fsync (§14.2). Concurrency: single-writer per slot; no internal locking required if dispatch is serialized per slot. Persistence: the entire struct is disk state (P4, I2) — the canonical "this must survive a crash" type in the whole system. Serialization: bincode for WalRecord. Compatibility: schema change here is an ADR-level event (original blueprint pitfall retained, §13.6).

11.5 Proposer State (crates/paxos-core/src/proposer.rs)

pub struct ProposerState { pub our_node: NodeId, pub cluster_size: usize,
                            pub current_ballot: Ballot, pub phase: ProposerPhase }
pub enum ProposerPhase {
    Idle,
    Preparing { ballot: Ballot, promises: Vec<Promise>, proposed_value: Value },
    Accepting { ballot: Ballot, value_being_committed: Value, accepts: Vec<Accepted> },
}
impl ProposerState {
    fn start_round(&mut self, value: Value) -> Prepare;                 // P3, I13
    fn handle_promise(&mut self, p: Promise) -> Option<Accept>;         // P2c value-derivation, §16.1
}

Ownership: one instance per proposer role per slot-in-flight. Mutation: RAM-only — current_ballot resets on restart and is re-derived from max_observed_round + 1 (I13, P3). Concurrency: single-writer; Multi-Paxos (§16) runs many ProposerPhase instances keyed by SlotId. Persistence: never persisted — persisting this would be the acceptor/proposer confusion bug (§13.6). Serialization: n/a. Compatibility: internal only, not wire-visible.

11.6 Learner State (crates/paxos-core/src/learner.rs)

pub struct LearnerState { cluster_size: usize,
    accepts: BTreeMap<(SlotId, Ballot), BTreeSet<NodeId>>, chosen: BTreeMap<SlotId, Value> }
impl LearnerState {
    fn observe(&mut self, from: NodeId, msg: &Accepted, value: &Value) -> Option<Learn>;  // I9
}

Ownership: one instance per learner role. Mutation: observe only; quorum-gated (I9). Concurrency: single-writer. Persistence: chosen is re-derivable from acceptor state on restart (§13.6 pitfall 18) — persisting it is an optimisation, not a requirement. Serialization: optional (bincode) if persisted. Compatibility: internal.

11.7 State Machine Contract (crates/paxos-multi/src/state_machine.rs)

pub trait StateMachine {
    type Snapshot;
    fn apply(&mut self, slot: SlotId, value: &Value);       // must be deterministic — I11, P11
    fn encode_state(&self) -> Self::Snapshot;               // must be order-stable — P8
    fn decode_state(bytes: &Self::Snapshot) -> Self;
}

Ownership: application-supplied, owned by the host process. Mutation: apply is the only mutator, called strictly in slot order (§16, commit_index cursor). Concurrency: single applier thread. Persistence: the application's concern; the library only durs the log/snapshot around it. Serialization: application-defined Snapshot type. Compatibility: changing the encoding is an application-level schema-migration event (§27).

11.8 WAL Record (crates/paxos-storage/src/record.rs)

pub enum WalRecord {
    Promise  { slot: SlotId, ballot: Ballot },
    Accepted { slot: SlotId, ballot: Ballot, value: Value },
    Snapshot { up_to_slot: SlotId, hash: [u8; 32] },
}

Ownership: owned by paxos-storage::wal. Mutation: append-only, never rewritten in place. Concurrency: single-writer per node (one WAL file). Persistence: is the persistence layer (I2, I7). Serialization: [u32 len][u32 crc32c][bincode payload] (§8.5). Compatibility: a new variant is additive; removing/reordering fields breaks recovery of old WALs (§27).

11.9 Multi-Paxos Log (crates/paxos-multi/src/log.rs)

pub struct LogEntry { pub slot: SlotId, pub chosen_ballot: Ballot, pub value: Value }
pub struct PaxosLog { entries: BTreeMap<SlotId, LogEntry>,
                       snapshot_up_to: SlotId, first_uncommitted: SlotId }

Ownership: one per node, owned by the Multi-Paxos layer. Mutation: entries inserted on Learn, truncated on compaction (§17.4, I12). Concurrency: single-writer; read access is serialized behind the commit_index cursor. Persistence: mirrored to the WAL (§11.8); PaxosLog itself is the in-memory index. Serialization: n/a in-memory; entries derive from WalRecord::Accepted. Compatibility: internal.

11.10 Leader / Bulk-Prepare (crates/paxos-multi/src/leader.rs)

pub struct Leader { pub our_node: NodeId, pub leader_ballot: Ballot,
                     pub next_uncommitted: SlotId, prepared: BTreeMap<SlotId, BulkPrepareEntry> }
pub struct BulkPrepareEntry { promises: usize, highest_accepted: Option<(Ballot, Value)> }

Ownership: one per node believing itself leader (may be zero or, transiently, more than one — P5). Mutation: prepared grows as bulk-Prepare promises arrive; per-slot, never shared across slots (I14). Concurrency: single-writer; per-slot map entries are independently droppable. Persistence: RAM-only; a demoted/crashed leader's Leader state is simply discarded and rebuilt by whichever node Ω elects next. Compatibility: internal.

11.11 Membership / Reconfiguration (crates/paxos-multi/src/reconfig/alpha.rs)

pub struct Membership { pub members: Vec<NodeId>, pub epoch: u64 }
pub struct ReconfigPropose { pub slot: SlotId, pub new_membership: Membership }
pub const ALPHA_DEFAULT: u64 = 3;                                 // ADR-16, I10

Ownership: the current membership is process-wide, versioned by epoch. Mutation: only via a chosen ReconfigPropose value at slot s, effective at s + ALPHA (§18.1). Concurrency: read by every quorum-check call; a new Membership is swapped atomically at its effective slot. Persistence: every membership change is itself a chosen log value — durable by construction. Compatibility: epoch must be monotonic; the joint-consensus alternative (reconfig/joint.rs, ADR-16b) uses a different Membership transition shape, documented separately.

11.12 Client API Types (crates/paxos/src/client.rs)

pub struct Client { leader_hint: Mutex<Option<NodeId>>, transport: Arc<dyn Transport> }
pub enum RpcRequest  { Propose(Value), Read(ReadMode) }
pub enum RpcResponse { Committed(SlotId, Value), NotLeader(Option<NodeId>), Timeout }
pub enum ReadMode { Linearizable, ReadIndex, Lease }              // ADR-19, ADR-18

Ownership: one Client per application connection. Mutation: leader_hint updated on NotLeader responses. Concurrency: Client is Send + Sync; safe for concurrent callers. Persistence: none — purely a routing cache. Serialization: RpcRequest/RpcResponse over the same transport as protocol messages. Compatibility: additive ReadMode variants only.

11.13 Trace Event (crates/paxos-core/src/trace.rs)

pub struct TraceEvent<'a> { pub virtual_time: u64, pub node: NodeId, pub kind: TraceKind<'a> }
pub enum TraceKind<'a> { SendPrepare(&'a Prepare), RecvPrepare(&'a Prepare),
    FsyncPromise(&'a AcceptorState), SendPromise(&'a Promise), SendAccept(&'a Accept),
    RecvAccepted(&'a Accepted), Learn(&'a Learn) }

Ownership: borrowed, emitted per message send/receive/fsync. Mutation: immutable, append-only event stream. Concurrency: one stream per simulated node (§21). Persistence: written to the simulator's trace log for TLA+ diff (§21.4); not used in production builds (compiled out or sampled). Compatibility: internal tooling format, versioned independently of the wire protocol.

11.14 Error Types (crates/paxos-core/src/error.rs, crates/paxos-storage/src/lib.rs)

pub enum ProtocolError { StaleBallot, MalformedMessage(&'static str), QuorumUnavailable }
pub enum StorageError  { Io(std::io::Error), CrcMismatch { offset: u64 }, TornWrite { offset: u64 } }

Ownership: returned by value from fallible operations. Mutation: n/a (immutable enums). Concurrency: Send. Persistence: n/a. Compatibility: additive variants only; a removed variant is a breaking change to any downstream match.

13. Phase 1 — Single-Decree Basic Paxos

13.1 Objectives

Implement the full two-phase protocol (§8.2, §8.3) as the load-bearing safety core of the entire stack. Get this phase wrong and every later phase is wrong (P2).

13.2 Detailed Implementation Steps

  • Implement Ballot (§11.1, P3) and NodeId/Quorum (§11.2, P10/I6).
  • Implement AcceptorState::handle_prepare/handle_accept exactly per the §8.6 state table, enforcing the asymmetric guard of I4.
  • Implement ProposerState::start_round/handle_promise, implementing the P2c value-derivation rule (§8.2): adopt the highest-accepted_ballot value seen in the quorum, else the proposer's own value.
  • Implement LearnerState::observe enforcing I9 (quorum-count gate before Learn).
  • invariants.rs: encode I1, I3, I4, I5, I6, I9 as debug_assertions.
  • trace.rs: emit TraceEvent (§11.13) at every message boundary for later TLA+ diffing (§21).

13.3 Deliverable

paxos-core compiles no_std-clean (ADR-02); single-decree Paxos passes against 3/5/7/9- acceptor topologies in unit tests.

13.4 Acceptance Criteria

  • Property test property.agreement: 100,000 random Prepare/Promise/Accept/Accepted interleavings never violate I1 (only one value ever chosen for slot 0).
  • tla.basic_paxos (§23.5) Pass: every TLA+-generated trace from notes/tla-spec/BasicPaxos.tla replays bit-identically against the implementation.
  • cargo build --no-default-features --target thumbv7em-none-eabihf -p paxos-core succeeds (the no_std proof, ADR-02).

13.5 Conformance Fixtures

Fixture Purpose Expected Output

13.6 Pitfalls

  • Prepare requires strictly >, Accept requires >= (I4) — asymmetric; reversed, either liveness or safety breaks.
  • P2c case (b) uses "< n", never "<= n" — including n itself creates a circular dependency when a proposer's own Accept reaches one acceptor before its Promise returns.
  • The proposer's ballot is RAM-only but must be monotonic across restarts (I13) — derive the next round from a persisted max_observed_round + 1 or wall-clock-microseconds.
  • Promise must carry (accepted_ballot, accepted_value) as one atomic pair (I5) — never reconstruct one field from context.

13.7 Performance Concerns

Single-decree Paxos costs 2 network rounds + 2 fsyncs per decision cold (§4 row 3); no batching or pipelining yet (Phase 10, §22) — this phase is a correctness baseline, not a throughput one.

13.8 Edge Cases

Simultaneous Prepare from two proposers (duelling, fixture above); an Accept arriving before its own Prepare's Promise quorum completes (tolerated — Accept still checks >= promised_ballot independently); an acceptor set of exactly 1 (degenerate quorum=1).

13.9 Failure Analysis

14. Phase 2 — Durable Acceptor State (WAL)

14.1 Objectives

Close the crash-recover safety gap left open by Phase 1: land paxos-storage, enforcing P4/I2/I7.

14.2 Detailed Implementation Steps

  • wal.rs: append-only log; record format [u32 len][u32 crc32c][bincode payload] (§8.5, §11.8); CRC32C computed over the length prefix and payload (§14.6).
  • Dispatch boundary (the single call site enforcing I2, per P4): outbound Promise/Accepted messages are held until wal.append_and_sync returns.
  • fsync_policy.rs: always (ADR-07 default) / group (opt-in, batches ≤ 64 per ADR-12) / periodic rejected at the type level — no such variant exists to construct.
  • Recovery: read oldest→newest; a CRC mismatch truncates to the prior record (I7); apply each record to a fresh AcceptorState; discard everything preceding the latest Snapshot record.

14.3 Deliverable

WAL append+fsync+recovery library; a "crash-recover" simulator scenario (early use of the §21 tooling) asserting idempotent re-Prepare handling after any crash point.

14.4 Acceptance Criteria

  • simulator.crash_recover_1k (§23.5): 1,000 random crash points between fsync and transmit, zero I1/I2 violations.
  • Recovery time for a 100 MB WAL on NVMe ≤ 500 ms (M11).
  • Property test: a CRC mismatch always truncates cleanly, never panics.

14.5 Conformance Fixtures

Fixture Purpose Expected Output
fixtures/wal_torn_tail.bin §8.8 torn write truncated to last valid record
fixtures/crc_missing_length_prefix.bin regression: CRC computed without length prefix rejected as forged (§14.6)

14.6 Pitfalls

  • sync_data (fdatasync) does not sync metadata; append-only file-size growth needs data=ordered ext4 (or equivalent) — documented in docs/runbook/slow-disk.md (§26).
  • CRC32C must cover the length prefix, not only the payload — omitting it leaves a forgeable-record hole.
  • The snapshot file's own fsync must precede the WAL Snapshot record's fsync (§17.2) — reversed order strands recovery with a WAL pointer to a non-existent snapshot file.

14.7 Performance Concerns

always fsync costs ~100µs–1ms per record on NVMe/SATA respectively; group batching (ADR-12) amortises this roughly 64× at the cost of per-appender latency up to the 1ms batch window.

14.8 Edge Cases

A torn write exactly at the CRC boundary; disk-full mid-fsync (StorageError::Io); a snapshot trigger firing concurrently with a normal append (must serialise, §17).

14.9 Failure Analysis

A TornWrite at the tail is expected and handled (I7). A CrcMismatch deeper than the tail (mid-file corruption) is not expected and escalates to the docs/runbook/slow-disk.md bit-rot procedure (FM9).

14.10 Operational Notes

paxos_wal_fsync_duration_seconds histogram (§26); paxos_wal_torn_write_truncations_total counter; alert if the latter is nonzero outside a deliberate chaos test.

15. Phase 3 — Failure Detection & Leader Election

15.1 Objectives

Ship the liveness-only overlay (P5) that Multi-Paxos needs for throughput: Phi-accrual (Hayashibara 2004, ADR-10) wrapped as Chandra-Toueg's Ω (1996).

15.2 Detailed Implementation Steps

  • phi.rs: PhiDetector retains the last 1,000 inter-arrival samples; running mean/variance per Hayashibara §3; phi(now) = -log10(survival_function(Δ)).
  • omega.rs: OmegaDetector::leader() returns the lowest-NodeId peer with Φ < threshold (default 8, ADR-11) — an opinion, never a fact (P5).
  • Leader stickiness: the current leader is retained until either Φ > 8 from this node's own view, or a higher-ballot Prepare is observed from another node (§15.6).
  • Heartbeats piggy-back on Accept when in-flight traffic exists; an explicit Heartbeat message fires every heartbeat_period / 3 when idle.

15.3 Deliverable

paxos-failure-detector crate passing the Hayashibara 2004 §5 evaluation; a partition_heal simulator scenario.

15.4 Acceptance Criteria

  • False-positive rate < 1/hour at Φ-threshold=8 under 50ms±10ms simulated jitter (M13).
  • simulator.partition_heal_1k (§23.5): Ω converges on a single leader within 3s of heal across 1,000 trials.
  • slow_disk scenario: a node with 100× slow disk is detected by Ω within the configured threshold.

15.5 Conformance Fixtures

Fixture Purpose Expected Output
fixtures/phi_jitter_50ms.yaml Hayashibara §5 evaluation replay FP rate < 1/hr

15.6 Pitfalls

Use a monotonic clock only (CLOCK_MONOTONIC / mach_absolute_time), never SystemTime — wall-clock jumps produce nonsense Φ values. Heartbeat piggy-backing needs an explicit idle-heartbeat fallback. 15.7 Performance Concerns

Φ computation is O(1) amortised per sample (running mean/variance, never a full recompute); the 1,000-sample ring buffer bounds memory per peer.

15.8 Edge Cases

A peer that never sends a heartbeat (immediate Φ = ∞); guarded misuse of SystemTime instead of the monotonic clock (an API-level guard, not a runtime check); Φ miscalibration under bursty scheduling pauses on a heavily oversubscribed host.

15.9 Failure Analysis

15.10 Operational Notes

16. Phase 4 — Multi-Paxos Log Replication

16.1 Objectives

Turn single-decree Paxos into a useful replicated log: a stable leader skips Phase 1 across slots (Chandra/Griesemer/Redman 2007 §4), cutting the steady-state cost from 2 rounds to 1 (§4 row 4).

16.2 Detailed Implementation Steps

  • leader.rs: Leader/BulkPrepareEntry (§11.10); propose() skips Prepare entirely when the target slot is already covered by a quorum of bulk-Prepare promises.
  • gap_fill.rs: fill_gaps for slots a deposed leader left incomplete; P2c forces re-proposing any revealed prior value, else a no-op fills the slot (§8.9 worked example).
  • catchup.rs: CatchupRequest/CatchupResponse; snapshot-then-tail strategy (ADR-17).
  • New-leader ballot must exceed max_observed_round cluster-wide (I13); a leader demotes itself on observing a higher-ballot Prepare rather than continuing to issue Accepts (P5).
  • Per-slot quorum tracking is independent from the start (I14) — Phase 10's pipelining (§22) only stresses an invariant already true here.

16.3 Deliverable

A 3-node Multi-Paxos cluster commits 100,000 values to a key-value state machine; all three nodes reach bit-identical final state.

16.4 Acceptance Criteria

  • leader_handoff simulator scenario: new leader elected ≤ 3s after failure, gap-fills any in-flight slots correctly, resumes throughput.
  • Pre-hardening bench.steady_state: ≥ 20,000 commits/sec on 3-node localhost, p99 ≤ 10ms (Phase 10, §22, raises this to M1/M5).
  • tla.multi_paxos (§23.5) Pass against notes/tla-spec/MultiPaxos.tla.

gap_fill_regression.yaml slot with a revealed prior accepted value re-proposes prior value, never a new client value
tla_traces/multi_paxos/* TLA+ conformance bit-identical replay

16.6 Pitfalls

The bulk-Prepare ballot must exceed any ballot the deposed leader used in its own gap-fills (I13) or P2c breaks. A leader that detects a higher ballot must demote, not continue issuing Accepts — technically safe either way, but "two leaders both winning slots" is a throughput disaster (P5). The application SM must be deterministic (I11) or replicas silently diverge.

16.7 Performance Concerns

Skip-Phase-1 reduces the steady-state cost to 1 round per decision (§4 row 4) versus 2 cold (row 3). Gap-fill after a leader change costs one extra round per incomplete slot — bounded by the pipeline window (§4 row 11).

16.8 Edge Cases

Overlapping leader changes (a second handoff mid-gap-fill); a gap slot with no accepted value anywhere in the quorum (filled with a no-op); a slot arriving out of order at a learner (tolerated — the learner indexes by (slot, ballot)).

16.9 Failure Analysis

Two leaders racing is safe (I1 holds) but throughput-degrading — detection is the Φ-flap metric (§15.10); a leader crashing mid-gap-fill recovers via a third leader re-running Phase 1 for the same gap (§8.9 pattern, generalised).

16.10 Operational Notes

paxos_leader_changes_total, paxos_log_length gauge (§26); docs/runbook/partition.md documents the leader-handoff diagnostic flow.

17. Phase 5 — Snapshots & Log Compaction

17.1 Objectives

Bound WAL growth and crash-recovery time (ADR-14, ADR-15) — without this, recovery time grows proportional to lifetime throughput.

17.2 Detailed Implementation Steps

  • take_snapshot: sm.encode_state() (must be order-stable, P8/I11) → BLAKE3 hash (ADR-05) → write the snapshot file and fsync it ((a)) → append WalRecord::Snapshot and fsync ((b)), strictly ordered (a) before (b) (I2, §14.6).
  • compaction.rs: truncate the log to snapshot_slot − 16 (I12, ADR-15) after (b) completes.
  • Trigger check runs after every Learn is applied (ADR-14: 64 MB WAL or 1M entries, whichever first).

17.3 Deliverable

A 1M-write soak produces ≤ 20 snapshots, the WAL never exceeds 80 MB, and crash-recovery time stays under 500 ms.

17.4 Acceptance Criteria

  • crash_after_snapshot_file_before_wal_pointer scenario: post-recovery, the orphaned snapshot file is detected and either hash-matched-and-reused or garbage-collected (I8, I12).
  • Learner catch-up via a 64 MB snapshot completes in ≤ 1s (M10).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
snapshot_hash_mismatch.yaml non-deterministic SM canary mismatch detected, alarm raised (I8)
orphaned_snapshot_gc.yaml crash between fsyncs (a) and (b) orphan reused or GC'd, no safety impact

17.6 Pitfalls

A naive snapshot blocks the apply path while encode_state() runs — a multi-second stall for large SMs (the copy-on-write fix lands in Phase 10, §22). SM state must use BTreeMap, never HashMap — iteration-order divergence silently breaks P8/I8. Per-node GC deletes any snapshot file whose hash does not match the current snapshot.

17.7 Performance Concerns

Snapshot apply time scales with SM state size; the copy-on-write optimisation (deferred to §22) is what removes the apply-path stall at scale.

17.8 Edge Cases

A snapshot trigger firing mid-reconfiguration (must not race the reconfig's own log entries); a snapshot larger than available disk (fails loudly — must never corrupt the WAL to make room).

17.9 Failure Analysis

A crash between fsyncs (a) and (b) leaves an orphaned snapshot file — handled by GC or hash-reuse, zero safety impact because the ordering invariant (I2) guarantees the WAL pointer never references a non-existent file.

17.10 Operational Notes

paxos_snapshot_slot gauge, paxos_log_length gauge (§26); docs/runbook/slow-disk.md covers snapshot-fsync stalls specifically.

18. Phase 6 — Membership Reconfiguration

18.1 Objectives

Change cluster membership online without violating quorum intersection (I6/I10) — the α-parameter trick (Paxos Made Live section 5.3, ADR-16) is the default mechanism.

18.2 Detailed Implementation Steps

  • alpha.rs: quorum_for_slot looks up the membership in effect via effective_slot = proposal_slot + ALPHA (§11.11); ALPHA_DEFAULT = 3.
  • joint.rs: the joint-consensus alternative (ADR-16b, PhaseDeferred("§18.6") from the main line) for operators preferring the Raft-derived two-round mental model.
  • Reconfig API rejects any membership delta touching more than ⌊n/2⌋ members at once (I10).
  • A removed node is marked "draining," not "gone," until the α-window of in-flight commits clears. An added node joins as a non-voting learner and is promoted to voter only once its log is within 16 entries of the leader's.

18.3 Deliverable

Adding a node to a 3-node cluster: throughput continues uninterrupted, the new node catches up via snapshot, and the cluster reaches a stable 4-node (2,3)-quorum configuration within 10s.

18.4 Acceptance Criteria

  • jepsen.membership_change (§23.5, §28): linearizability holds across a 60s run with 5 add/remove operations.
  • reconfig_under_partition scenario: a reconfiguration proposed during a partition is either fully applied or fully rolled back — never half-applied.
  • Reconfiguration completion time ≤ 10s (M12, α=3, 3→4 nodes).

18.5 Conformance Fixtures

Fixture Purpose Expected Output
reconfig_alpha_offbyone.yaml α=0 regression guard rejected — I10 requires α ≥ 1
reconfig_nonintersecting_quorum.yaml C={1,2,3} → C'={4,5,6} rejected at the API (I10)

18.6 Pitfalls

α off-by-one is the single most subtle correctness invariant in the stack: α=0 loses safety (§8.2's P2c argument no longer closes across the boundary); confusing < with <= in the effective-slot lookup costs consistency. A removed node must remain reachable until its α-window clears. The joint-consensus alternative (PhaseDeferred("§18.6"), ADR-16b) exists for operators who want it, but is not exercised by the main-line conformance suite.

18.7 Performance Concerns

Reconfiguration completion is bounded at ≤ 10s (M12); α=3 is chosen specifically to overlap with the batching/pipelining windows of §4 rows 11–12 rather than serialising behind them.

18.8 Edge Cases

A reconfiguration proposed during an active partition; two concurrent reconfiguration proposals racing for the same slot (the protocol itself resolves this — only one can be chosen); a membership delta larger than ⌊n/2⌋ (rejected at the API, I10).

18.9 Failure Analysis

A half-applied reconfiguration would produce two non-intersecting quorums — catastrophic. The API-level size cap on membership deltas (I10) is the primary defence; FM8 (§25) covers detection if a defect ever slips past it.

18.10 Operational Notes

paxos_reconfig_events_total (§26); docs/runbook/reconfig-rollback.md documents emergency rollback of a botched reconfiguration.

19. Phase 7 — Network Transport

19.1 Objectives

Replace the in-process channel used through Phase 6 with a real TCP transport (ADR-20).

19.2 Detailed Implementation Steps

  • tcp.rs: TcpTransport/PeerConn (§11); length-prefixed bincode frames; one connection per peer pair, lower NodeId initiates.
  • reconnect.rs: exponential backoff 100ms × 2^n with jitter, capped at 5s.
  • Two writer streams per peer: TCP_NODELAY on the heartbeat stream, Nagle left on for the batch/Accept stream (§19.7).
  • SO_KEEPALIVE with a 30s probe as a belt-and-braces liveness signal alongside Φ (§15).
  • mTLS and QUIC are explicitly out of this phase — PhaseDeferred("§19.10") (ADR-26, ADR-20's rejected alternative).

19.3 Deliverable

A 3-node Docker-Compose deployment commits 100,000 values across the real network at p99 ≤ 10ms (pre-hardening; §22 lowers this to M5's 5ms).

19.4 Acceptance Criteria

  • tcpkill-injected partitions cause Φ to spike and a new leader to be elected; throughput resumes automatically.
  • maelstrom.lin_kv (§23.5) Pass against a network-deployed 3-node cluster.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
network_partition_docker.yaml Docker-Compose partition injection Φ spike, leader re-election, resumed throughput
half_open_connection.yaml one side crashes without closing SO_KEEPALIVE detects within 30s

19.6 Pitfalls

Nagle batches small heartbeat writes by default — set TCP_NODELAY on that stream only. A half-open connection is undetectable without keepalive or application heartbeats. Message ordering is FIFO per connection but not across reconnects — the leader's ballot-tracking code must not assume in-order arrival across a reconnect boundary.

19.7 Performance Concerns

Batching and pipelining are previewed here and hardened in Phase 10 (§22); this phase's transport is otherwise unoptimised (one message per write where unbatched).

19.8 Edge Cases

A reconnection storm after a rolling restart (backoff + jitter caps fan-in); a peer reachable via two paths after a reconnect (reordering across paths, tolerated per protocol design, §8.6).

19.9 Failure Analysis

A dropped connection with Accepts in flight is safe (idempotent retries, I4) but visible as a throughput dip — FM3 (§25) covers detection and telemetry.

19.10 Operational Notes

mTLS and QUIC remain PhaseDeferred here; operators must deploy on a private network or VPN until mTLS lands (ADR-26). Documented in docs/runbook/partition.md.

20. Phase 8 — Client API & Linearizable Reads

20.1 Objectives

Ship the linearizable read/write surface applications actually call: Client (§11.12), ReadMode::{Linearizable, ReadIndex, Lease} (ADR-19, ADR-18).

20.2 Detailed Implementation Steps

  • Client::propose: routes to leader_hint; on RpcResponse::NotLeader, updates the hint and retries (retry budget 5, §20.6).
  • Linearizable read (default, ADR-19): the leader proposes a no-op via Paxos and waits for its commit before serving the read — no clock assumption.
  • Read-index (opt-in): the leader confirms it is still leader via a heartbeat-quorum round, then serves from local commit_index state — cheaper, one quorum RTT instead of a full Paxos round.
  • Lease read (opt-in, ADR-18): the leader serves from local state within a quorum-granted lease, zero network round-trip, under the explicit bounded-clock-skew assumption.

20.3 Deliverable

examples/linearizable_kv.rs runs a key-value store over 3-node Paxos with all three read modes selectable.

20.4 Acceptance Criteria

  • jepsen.linearizable_register (§23.5): Pass under a 5-minute partition-and-rejoin chaos workload.
  • Linearizable read p50 ≤ 2ms, p99 ≤ 8ms (M6, M7); read-index p50 ≤ 1ms; lease read p50 ≤ 100µs (M8).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
linearizable_read_regression.yaml leader no-op read path linearizable under partition-and-rejoin
non_leader_read_rejected.json read routed to a non-leader rejected at the public API
lease_clock_skew_failure.yaml documents ADR-18's failure mode stale read reproduced under injected skew, as expected

20.6 Pitfalls

A read served from a non-leader is not linearizable — the library refuses it at the API; there is no "read any node for load balancing" escape hatch (use read-index instead). leader_hint can be stale; the client retries up to 5 times, then surfaces an error the application must handle. Read-index and lease reads are not "free" linearizability — they buy it under an additional, named assumption the caller must understand (ADR-18, ADR-19).

20.7 Performance Concerns

Linearizable read costs one full Paxos round; read-index costs one quorum-heartbeat RTT; lease read costs zero RTT within a valid lease.

20.8 Edge Cases

Leader deposed mid-read (client retries against the new hint); a client retry storm against a stale hint after a fast leader flap; a lease expiring exactly during a served read (the leader re-checks lease validity immediately before responding, not only at request start).

20.9 Failure Analysis

A stale lease read served past the clock-skew bound is the ADR-18 documented hazard — FM10 (§25) covers detection and the operator-facing signal.

20.10 Operational Notes

paxos_reads_total{mode=...} counter (§26); operator docs state plainly: "opt into read-index or lease only if you understand the assumption it buys."

21. Phase 9 — Deterministic Simulator & TLA+ Conformance

21.1 Objectives

Build the primary safety oracle referenced by §7's debugging methodology: a deterministic, seed-reproducible simulator (ADR-21) plus TLA+ trace replay (ADR-22).

21.2 Detailed Implementation Steps

  • scheduler.rs: single-threaded discrete-event loop, seeded ChaCha20Rng, drives time, message delivery, and disk-fsync latency identically for a given seed.
  • Injectable faults: network partition (drop between node pairs for a duration), slow disk (fsync-latency multiplier), node crash/recover, clock skew.
  • workload.rs: YAML scenario DSL — single_decree, leader_handoff, partition_heal, slow_disk, reconfig, 30day_soak (matching simulator/scenarios/, §10).
  • TLA+ trace replay: notes/tla-spec/{BasicPaxos,MultiPaxos}.tla generate traces via TLC; the simulator injects the identical message-delivery order and asserts implementation state matches spec state at every step.
  • tools/trace-bisect: given a failing seed, finds the minimum-prefix trace reproducing the violation (§21.4 evidence attachment used since Phase 1, §13.9).

21.3 Deliverable

The simulator runs at 10,000× real-time on a single core for a 3-node cluster (a 1-hour scenario completes in < 1s); 1,000,000 random scenarios run nightly with zero safety violations.

21.4 Acceptance Criteria

  • tla.basic_paxos and tla.multi_paxos (§23.5) both Pass.
  • Simulator throughput ≥ 1,000,000 events/sec, single core (M14).
  • A failing seed bisects to its minimal reproduction automatically, attached to the CI failure.

21.5 Conformance Fixtures

The six named scenarios under simulator/scenarios/ (§10); the regression seed corpus under conformance/corpora/invariants/.

21.6 Pitfalls

Determinism is fragile: HashMap iteration order is forbidden inside SimNode (BTreeMap only, P8/I11). Production code must route "now" through the Clock trait (§11), never call Instant::now() directly, or the simulator loses control of time. A single-threaded simulator never exhibits a race that only manifests under true parallelism — audit any code path that "assumes the simulator can't reach me."

21.7 Performance Concerns

The 10,000× real-time target (M14) and a bounded per-bisection wall-clock budget (≤ 5 minutes in CI) are both load-bearing for the nightly-soak and PR-gating workflows to stay fast.

21.8 Edge Cases

A scenario with zero live nodes (degenerate, rejected at scenario-load time); simultaneous crash-and-reconfig injected in the same simulated tick; an RNG reseed mid-run (forbidden — breaks reproducibility by construction).

21.9 Failure Analysis

Any simulator-detected I1–I14 violation is release-blocking; the bisected minimal seed is attached to the bug report automatically — no manual reproduction step required.

21.10 Operational Notes

Nightly simulator results publish under simulator/results/; the simulator.yml CI workflow fails the build on any violation, with no override path.

22. Phase 10 — Performance Hardening

22.1 Objectives

Reach the M1–M16 throughput/latency targets (§4, §30): batching, pipelining, an optional io_uring backend, copy-on-write snapshotting, and memory pooling.

22.2 Detailed Implementation Steps

  • batching.rs: ≤ 64 WAL records/Accepts per fsync, flush at 1ms (ADR-12).
  • pipeline.rs: 16 in-flight Accept rounds per peer (ADR-13), backed by the per-slot quorum map established in Phase 4 (I14) — never a shared "outstanding" counter.
  • Copy-on-write snapshot: closes the §17.6 pitfall — the SM hands the snapshot thread a read-only view of state-at-slot-N while continuing to apply slots N+1, N+2, ….
  • io_uring.rs: optional Linux-only backend (ADR-27), reducing per-fsync latency from ~100µs to ~30µs on modern NVMe; std::fs remains the portable default.
  • Memory pooling: pre-allocated BytesMut pool for WAL records; Ballot/SlotId already fit in 16 bytes combined (§11.1, §11.3).

22.3 Deliverable

Steady-state throughput ≥ 100,000 commits/sec on 3-node localhost (M1); p50 ≤ 2ms, p99 ≤ 5ms (M4, M5); leader-failover RTO ≤ 5s (M9).

22.4 Acceptance Criteria

bench.steady_state meets M1/M2/M3 across localhost/LAN/WAN profiles; bench.leader_failover meets M9; parallel Learn-WAL-append and SM-apply preserve commit_index ordering under load.

22.5 Conformance Fixtures

crates/paxos-bench/benches/{steady_state,leader_failover,snapshot,reconfig}.rs (§10), each asserting its respective M-target as a hard CI gate (§30).

22.6 Pitfalls

Batching amortises fsync cost but adds up to 1ms of latency to the first proposal in a batch — tunable, defaults bias throughput. Pipelining requires the I14 per-slot map; a shared "outstanding" counter silently corrupts independent-slot commitment. io_uring is Linux-only, feature-gated — the std::fs fallback must be exercised in CI on every platform.

22.7 Performance Concerns

Disk-scheduler queue depth under io_uring interacts with batch size — over-deep queues can increase tail latency even as they raise throughput; the batch-size/window tunables trade p50 for aggregate throughput and must be re-tuned per storage medium (§30).

22.8 Edge Cases

A batch window expiring with zero proposals queued (no-op, no wasted fsync); the pipeline window exhausted mid-burst (caller blocks or receives a retryable backpressure error); an unsupported kernel for io_uring (explicit startup fallback to std::fs, never silent).

22.9 Failure Analysis

A batching/pipelining regression that violates I14 manifests as per-slot quorum-tracking corruption, caught by the same property tests introduced in Phase 4 (§16.4) re-run under the hardened code path.

22.10 Operational Notes

paxos_batch_size histogram, paxos_pipeline_window_depth gauge (I14 telemetry, §26). The WASM build target and formal (Coq/Isabelle) verification of the acceptor step function are PhaseDeferred("§22.10") stretch items noted here for the record (§37).

26. Operational Readiness

Metrics. Every counter/gauge/histogram introduced across §12–§23 is exported via a Prometheus endpoint; the full list is consolidated at §23.2. Naming convention: paxos_<noun>_<unit> for counters/histograms, bare paxos_<noun> for gauges.

Dashboards. The Grafana dashboard (ops/, §10, §23.3) has four panels: (1) commit throughput & latency (M1–M9), (2) leader stability (paxos_leader_changes_total, per-peer Φ), (3) storage health (fsync latency, WAL size, snapshot cadence), (4) conformance status (last bucket-table run, §23.5).

Alerting philosophy. Alert on rate and sustained conditions, never on a single sample — Φ spikes and single fsync-latency outliers are expected noise (§15.10, FM6); alert on paxos_leader_changes_total rate exceeding 3/minute sustained for 5 minutes, or paxos_agreement_violations_total being nonzero at all (P0, page immediately).

SLOs. Commit p99 ≤ 5ms (M5) measured over rolling 5-minute windows, 99.9% of windows compliant per month; availability (majority-quorum uptime) ≥ 99.95% monthly, explicitly excluding minority-partition unavailability (§4 row 24, the CP trade).

Incident response. Triage entry point is docs/runbook/triage.md; role-specific runbooks (partition.md, slow-disk.md, leader-flap.md, reconfig-rollback.md) are invoked from there based on the dashboard panel showing the anomaly.

Backup/restore. The latest snapshot plus the retained WAL tail (§17.4) is the backup unit; paxos-admin dump-wal and the snapshot files under snapshots/ are copied to durable object storage on a schedule; restore is "install the snapshot, replay the WAL tail, rejoin as a learner" (§18.2's non-voting-learner path, reused for restore).

Deployment topology. Reference: 3 or 5 nodes, one per availability zone within a region for the v1 scope (multi-region is PhaseDeferred("§31")); Kubernetes StatefulSet with a PodDisruptionBudget capping simultaneous voluntary disruptions at ⌊(n-1)/2⌋ (matching I10's crash-stop tolerance, never coincidentally).

Canary / rolling upgrade / rollback / migration. Rolling upgrade: one node at a time, draining its leader role first (force a leader change via paxos-admin) before restart; the next node starts only after the previous rejoins and its Φ stabilises below threshold. Canary: a single node runs the new version for a soak period (default 24h) before the rollout proceeds. Rollback: redeploy the previous binary; WAL/wire compatibility rules (§27) guarantee a clean downgrade within the same major version. Migration: schema changes to WalRecord or wire messages follow the additive-only rule of §27; a breaking change requires a documented two-phase migration (deploy readers of both formats, then writers of the new format, then retire the old reader path).

27. Compatibility & Versioning

Wire compatibility. Message (§11.3) and its variants are additive-only within a major version; field order is wire-stable (bincode is order-dependent, ADR-04) — reordering fields is a breaking change equivalent to adding one incorrectly. New Message variants must be ignorable by an old-version peer (explicit Unknown catch-all reserved for this).

Storage compatibility. WalRecord (§11.8) follows the same additive-only rule; a WAL written by version N must remain replayable by version N+1 within a major version. A storage-format breaking change requires an offline migration tool (paxos-admin migrate-wal) and a documented downtime window.

Schema evolution. The application-supplied StateMachine::Snapshot type (§11.7) is outside this library's compatibility contract — application authors own their own SM schema-evolution policy; the library only guarantees the snapshot transport (content-addressed, §8.5) is version-stable.

API stability. The paxos crate's public Client API (§11.12) follows SemVer: breaking changes bump the major version; ReadMode gains variants only additively (minor-version safe).

Migration. A membership or storage-format migration always goes through the reconfiguration protocol (§18) or the offline migrate-wal tool — never a direct file edit (T2, T7's mitigation depends on this).

Deprecation policy. A deprecated ADR-locked choice (e.g., replacing bincode) requires: (1) a new ADR row recording the change and its "when the old choice wins" regime, (2) one full minor version where both are supported behind a feature flag, (3) removal only in the next major version.

SemVer policy. MAJOR.MINOR.PATCH; PATCH = bugfix, no behavioural contract change; MINOR = additive (new Message/WalRecord variant, new ReadMode, new metric); MAJOR = any change to I1–I14's enforcement, wire/storage breaking change, or a Repository Layout rename.

Rolling-upgrade guarantees. Any two adjacent MINOR versions can run mixed in the same cluster during a rolling upgrade (§26); a MAJOR-version upgrade requires the full documented migration path and is never mixed-version beyond the migration window.

28. Testing & Verification Strategy

  • Unit. Per-type tests for every §11 signature (Ballot::next, AcceptorState::handle_*, Quorum::try_new, …); each I1–I14 invariant has a dedicated unit test that fails when the invariant is deliberately broken (mutation-tested, §29).
  • Integration. Phase-level fixtures (each phase's N.5, §12–§23), culminating in examples/linearizable_kv.rs (§20.3) as the end-to-end integration smoke test.
  • Property. property.agreement (100K random interleavings, I1), property.validity (only proposed values are ever chosen), property.termination (under partial synchrony, eventually one value is chosen) — all three gate every PR (§23.5).
  • Differential. cross.etcd_raft: the same linearizable-register workload run against this stack and against etcd's Raft; histories must be equally valid under Knossos, quantifying only latency/throughput deltas, never correctness deltas.
  • Fuzzing. Four cargo-fuzz targets (crates/paxos-fuzz/fuzz_targets/, §10): message_parse, wal_replay, acceptor_step, proposer_step, snapshot_decode; nightly short runs in CI, a 24h canary before every release (M16).
  • Chaos. Jepsen nemeses: partition, crash-recover, slow-disk, membership-change (§23.5); Maelstrom workloads for protocol-conformance chaos.
  • Deterministic replay. Every simulator scenario (§21) is replayable byte-for-byte from its seed; every CI failure attaches the minimal bisected seed (§21.4).
  • Soak. The 30-day continuous simulator soak (M15) plus a real-cluster 30-day chaos soak before any Sealed milestone (Appendix B, §40).
  • Fault injection. The simulator's injectable faults (§21.2) are the primary fault-injection surface; tcpkill and Docker network partitioning (§19.4) cover the real-network path.
  • Conformance. The bucket table (§23.5) is the release gate; conformance/runner output is the artifact CI checks.
  • Performance-regression gating. Every M-target (§30) is a criterion benchmark assertion in CI; a regression beyond a configured tolerance (default 10%) fails the build, not merely warns.

Every fixture named in any phase's N.5 traces back to at least one invariant (I1–I14) or ADR; the reverse mapping (invariant → fixtures that exercise it) is maintained in conformance/report_schema.json's invariant_coverage field.

31. Scalability Analysis

Constant vs. grows. Constant regardless of cluster size n: per-decision message size (one Ballot + one Value, §11.1/§11.3), per-acceptor WAL record size. Grows with n: quorum size O(n) (⌈(n+1)/2⌉, §34), leader fan-out O(n) per Accept broadcast, FD count O(n) per node (§4 row 18). Grows with sustained write rate: WAL length between snapshots (bounded by ADR-14's trigger, so effectively O(1) amortised via compaction, I12).

Named bottlenecks, in order. (1) Leader fan-out — every Accept is O(n) messages from one node; this is the first bottleneck to saturate as n grows (mitigated by IP-multicast per Ring-Paxos, §5 ref-impls, at the cost of multicast-reliability assumptions). (2) fsync latency — the floor on commit latency regardless of batching (§4 row 8; batching amortises syscall count, not the underlying disk latency floor). (3) Quorum RTT — steady-state throughput is fundamentally RTT-bound without pipelining (§4 rows 5–7); pipelining trades memory (§4 row 17) for RTT-hiding. (4) Single-writer dispatch per slot — I2's ordering requirement means one node cannot parallelise fsyncs within a single acceptor beyond the batch mechanism (ADR-12).

Horizontal scaling. Adding acceptors (n↑) increases fault tolerance but decreases throughput headroom (larger quorum, more fan-out) — Paxos scales fault tolerance horizontally, not throughput; throughput scales by adding independent Paxos groups (sharding, below), not by adding acceptors to one group.

Vertical scaling. Faster disk (io_uring + NVMe, ADR-27) directly raises the fsync-latency floor (bottleneck 2); faster network directly raises the quorum-RTT floor (bottleneck 3, until pipelining's window becomes the binding constraint again, §4 row 11).

Sharding/partitioning. Not implemented in the main line (out of scope, §1) — the Megastore/Spanner pattern (per-entity-group Paxos, §5 books/papers) is the standard lever: run many independent Paxos groups, each with its own quorum, and route by shard key above this library. This blueprint provides one group; sharding is an application-layer composition of many groups.

Coordination overhead. Reconfiguration (§18) is the only operation with cross-slot coordination cost (the α-window); steady-state commits have zero coordination cost beyond their own quorum (no cross-slot locking, I14).

Practical ceiling and levers beyond it. The practical ceiling for one Paxos group is bottleneck (1) — leader fan-out — typically around n=7 to n=9 before fan-out-driven leader CPU/NIC saturation dominates (§34's derived throughput numbers make this concrete for this stack's targets). Levers beyond that ceiling: (a) IP-multicast fan-out (Ring-Paxos, §5), (b) sharding into multiple groups (above), (c) Flexible Paxos's smaller Phase-2 quorums (Howard et al. 2016, §36) trading fan-out for read-quorum size, (d) EPaxos's leaderless model removing the single-leader fan-out bottleneck entirely at the cost of dependency-graph ordering overhead (§36).

32. Mental Models & First Principles

MM1 — An acceptor's disk state is the database; a proposer's ballot is a stateless client cache. Predicts: any code that persists proposer state or fails to persist acceptor state is wrong by construction. Bug class without it: promised-ballot violations after a restart that re-issues a ballot already promised away. Applied in §11.4/§11.5, §13.6.

MM2 — A ballot is a fencing token with a total order, not a timestamp. Predicts: two ballots from different proposers must never compare equal, and the ordering must be total, not partial. Bug class without it: duelling proposers deadlock, or a comparison tie silently lets a lower-priority proposal win. Applied in §11.1, P3.

MM3 — Quorums are set intersections, not head-counts. Predicts: any two quorums under one membership must share a member; a membership change must preserve this pairwise property, not merely the numeric majority size. Bug class without it: a reconfiguration producing two non-intersecting quorums (T7, FM8). Applied in §11.2, I6, §18.

MM4 — The leader is a cache for liveness, never an oracle for safety. Predicts: the safety proof must hold with zero leaders, one leader, or transiently many. Bug class without it: accidentally re-deriving Raft's safety-via-leader coupling without Raft's corresponding proofs. Applied in P5, §33.

MM5 — fsync-before-respond is the linearizability boundary, not a durability nicety. Predicts: any reordering of fsync versus reply reopens a crash-recover safety hole even though "everything eventually gets written to disk." Bug class without it: a crash between reply and fsync silently loses a promise the acceptor claimed to have made. Applied in I2, §14.2.

MM6 — A snapshot is a compaction of history, never a semantic change to what was agreed. Predicts: snapshot+compaction must be provably equivalent to replaying the full log; content-addressing (a hash) is how that equivalence is checked mechanically rather than trusted. Bug class without it: divergent replica state from a non-deterministic encode_state. Applied in P8, I8, §17.

MM7 — A failure detector is a probabilistic oracle whose only guarantee is eventual agreement, never point-in-time truth. Predicts: no code path may treat "not currently suspected" as proof of aliveness; the protocol must tolerate the detector being wrong at any single instant. Bug class without it: safety code (rather than only throughput code) gated on Φ. Applied in P5, §15.

MM8 — Reconfiguration is consensus on membership, not a side channel. Predicts: the same machinery (ballots, quorums) that protects data values must protect membership changes — a membership change is itself a chosen log value, never an out-of-band operation. Bug class without it: a reconfiguration protocol that bypasses quorum-intersection reasoning entirely (the precise mistake the α-parameter trick is designed to prevent). Applied in §11.11, §18.

Raft made the one decision this blueprint explicitly refuses — coupling safety, not just liveness, to the leader (P5, MM4) — because it dramatically simplifies the mental model into a single state diagram. It wins in the "ship a correct implementation with a small team, fast" regime (etcd, Consul, CockroachDB's Raft ranges), at the cost of a leader-election protocol that must itself be airtight for safety (Howard & Mortier 2020).

Zab couples a primary-order atomic-broadcast model tightly to ZooKeeper's own session/watch semantics. It wins when the workload is read-dominated and hierarchical — ZooKeeper's own config/lock-service use case — at the cost of a protocol that is difficult to reuse outside that specific session model.

EPaxos removes the leader-fan-out bottleneck (§31) entirely by ordering commands via a per-command dependency graph. It wins in geo-distributed, low-conflict workloads where saving the leader-forwarding hop matters more than protocol complexity, at the cost of a conflict-resolution path that is materially harder to audit line-by-line against the paper (P12) than Basic Paxos's two-phase protocol.

Viewstamped Replication (Oki & Liskov 1988) independently co-invented the primary-backup replicated-log idea before Paxos was widely understood. It wins when an operations team wants an explicit, named view-change protocol instead of an ambient failure-detector-driven leader overlay, at the cost of coupling safety to the current view/primary the same way Raft does (MM4's counterpoint).

Chubby is literally Multi-Paxos in production (Chandra, Griesemer, Redman 2007) with master leases layered on top. It proves the lease-read optimisation (this blueprint's ADR-18) is safe at scale, but only under a TrueTime-class bounded-skew clock. It wins whenever the deployment already has such a clock source; this blueprint keeps the same optimisation strictly opt-in because most deployments do not.

34. Back-of-Envelope Capacity Model

Every number below is derived from the System Constraints table (§4); none is asserted without its formula. Assumes n=5 (quorum=3) and M1's workload profile (1KB values, batch=64, pipeline=16) unless stated otherwise.

  1. Quorum size. quorum = ⌊n/2⌋ + 1. For n=5: ⌊5/2⌋+1 = 3 (§4 row 2).
  2. Messages per decision, steady state. 1 round (§4 row 4) × (n-1) Accept sends + (n-1) Accepted replies = 2×(n-1) = 8 messages for n=5.
  3. Leader outbound bandwidth at M1. throughput × avg_msg_size × fanout = 100,000/s × 1,088 B × (n-1=2, at the n=3 localhost bench in §4 row 5) ≈ 217.6 MB/s.
  4. WAL growth rate at M1. throughput × record_size = 100,000/s × 1,052 B (12B ballot + 8B slot + 8B header + 1,024B value) ≈ 105.2 MB/s raw write rate before compaction.
  5. Snapshot cadence at M1. trigger_size ÷ growth_rate = 64 MB ÷ 105.2 MB/s ≈ 0.61s per snapshot at full M1 throughput (ADR-14) — over a 1M-write soak (§17.3) this predicts 1,052,000,000 B ÷ 64,000,000 B ≈ 16.4 snapshots, consistent with the "≤ 20 snapshots" acceptance criterion in §17.4.
  6. In-flight pipeline memory. window × msg_size × peers = 16 × 1,052 B × 4 ≈ 67.3 KB per leader for n=5 — trivial next to the 256 MB ceiling (§4 row 17), showing the ceiling is dominated by log/snapshot memory, not pipeline buffers.
  7. Steady-state log-memory headroom. Bounded by the snapshot trigger (64 MB) plus one in-flight batch (64 × 1,052 B ≈ 67 KB) ≈ 64.07 MB steady state versus the 256 MB ceiling (§4 row 17) — ~4× headroom for burst absorption before the ceiling is at risk.
  8. FD budget at n=5. (n-1) peer sockets + 1 WAL fd + 1 snapshot fd = 6 FDs; during a reconfiguration (§18, transient double-connections) this roughly doubles to 12 FDs — still well under the 32-FD budget (§4 row 18).
  9. Storage amplification, steady state. (snapshot_size + retention_window × record_size) ÷ logical_size. For 1M keys at ~1KB logical average (~1 GB logical data), the 16-entry retention window (ADR-15) contributes 16 × 1,052 B ≈ 16.8 KB — negligible — giving ≈1.0–1.05× amplification steady state, well under the ≤2× budget (§4 row 23); the 2× budget covers the transient window where two full snapshots briefly coexist before GC.
  10. Reconfiguration overlap window, logical time. α ÷ throughput = 3 ÷ 100,000/s = 30 microseconds of logical slot-time at M1 — the 10-second wall-clock completion target (M12) is therefore dominated by the new node's snapshot catch-up time (M10: ≤1s for 64MB), not by the α-window itself.
  11. WAN throughput ceiling via batching. At WAN RTT=30ms (§4 row 19) and 1 round/decision steady-state (§4 row 4), one unpipelined proposer caps at 1 ÷ 0.030s ≈ 33 decisions/sec. Reaching M3 (≥5,000 commits/sec) needs pipeline_window × batch_size ÷ RTT = 16 × 64 ÷ 0.030s ≈ 34,133 values/sec theoretical ceiling — comfortably covering M3 with headroom, confirming batching (ADR-12), not raw pipeline depth, is the WAN lever.

36. Alternative Architectures (Roads Not Taken)

36.1 Raft — strong leader, term-indexed log

Client -> Leader --AppendEntries(term,index)--> Followers
                <----- ack(term,index) ---------
Leader commits on majority ack; followers never independently propose.

Regime: small-to-medium clusters where operational simplicity and a single state diagram matter more than "any node can drive Phase 1." Real system: etcd/raft, Consul, CockroachDB's Raft-based ranges. Why rejected: safety, not merely liveness, depends on the leader-election protocol being airtight (MM4's counterpoint) — this blueprint wants a safety proof holding with zero, one, or transiently many "leaders."

36.2 EPaxos — leaderless, dependency-graph ordering

Client -> any Replica --PreAccept--> Replica quorum
       <---- merge dependency-graph votes ----
Commit occurs once the quorum agrees on the dependency set;
execution order is a topological sort of the graph, not a log index.

Regime: geo-distributed, low-conflict workloads where saving the leader-forwarding hop matters more than protocol complexity. Real system: EPaxos (Moraru, Andersen, Kaminsky 2013). Why rejected: dependency-graph execution ordering is materially harder to audit line-by-line against a paper (P12) than Basic Paxos's two-phase protocol — this project's goal is a from-scratch teaching implementation of the original algorithm.

36.3 Viewstamped Replication — primary-backup, view-numbered

Client -> Primary --Prepare(op,view,opnum)--> Backups
                <------- PrepareOK ----------
Primary commits on majority PrepareOK; a view-change protocol
elects a new primary on suspected failure (view number strictly increases).

Regime: teams wanting an explicit, named view-change protocol rather than an ambient failure-detector-driven leader overlay. Real system: Oki & Liskov 1988's VR and its modern descendants. Why rejected: VR couples safety to the current view/primary the same way Raft does — this blueprint specifically wants classic Paxos's leader-optional safety argument.

36.4 Chain Replication — primary-order chain, no quorum voting

Client-write -> Head -> Node2 -> ... -> Tail -> ack -> Client
Client-read  -> Tail   (always fully replicated; no quorum check needed)

Regime: high-throughput, low-read-latency workloads where a full-chain write latency is an acceptable trade for reads needing zero quorum coordination. Real system: van Renesse & Schneider 2004's Chain Replication. Why rejected: failure recovery needs a separate, carefully-ordered chain-reconfiguration protocol (not quorum-based), and write latency scales linearly with chain length rather than being bound to one quorum round-trip.

38. Glossary

  • Acceptor — the disk-resident role that promises/accepts ballots (§11.4).
  • ADR — Architecture Decision Record; a locked choice with rejected alternatives (§9).
  • Agreement — the safety property that only one value is ever chosen per slot (I1).
  • Α-parameter (alpha) — the reconfiguration offset controlling how many slots overlap the old and new membership (§18.1, ADR-16).
  • Ballot — (round, proposer_id), the totally-ordered proposal number (§11.1, P3).
  • Basic Paxos — the single-decree ("synod") protocol choosing one value (§13).
  • Batching — grouping multiple proposals into one fsync/network write (ADR-12).
  • BLAKE3 — the hash function used for content-addressable snapshots (ADR-05, I8).
  • Bisection — finding the minimal seed prefix that reproduces a simulator-detected violation (§21.4).
  • Byzantine fault — a node that violates the protocol rather than merely crashing; out of scope here (P14).
  • Catch-up — a lagging learner's process for reaching current state via snapshot + log tail (§16.3).
  • CAP theorem — the impossibility of simultaneous Consistency, Availability, and Partition tolerance; this system is CP (§4, §31).
  • Chain Replication — a primary-order, quorum-free replication architecture (§36.4).
  • Chosen — a value with a quorum of Accepted acknowledgements, distinct from applied (§8.6, §20.9).
  • Chubby — Google's production Paxos-based lock service (§5, §33).
  • Content-addressable storage — data identified by the hash of its contents, used for snapshots (P8, I8).
  • Copy-on-write snapshot — a snapshot mechanism that avoids blocking the apply path (§22.2).
  • CRC32C — the checksum protecting each WAL record against torn writes (§8.5, I7).
  • Crash-recover failure — a node halts and later restarts with disk intact (FM2).
  • Crash-stop failure — a node halts and never returns (FM1).
  • Determinism canary — a test asserting the application state machine's apply is order-independent (I11, P11).
  • EPaxos — the leaderless, dependency-graph-ordered Paxos variant (§5, §33, §36.2).
  • Fencing token — a monotonically increasing value that invalidates stale holders; the mental model for a ballot (MM2).
  • Flexible Paxos — the observation that Phase-1 and Phase-2 quorums need only intersect pairwise, not both be majorities (§5, §31).
  • FLP impossibility — the proof that asynchronous consensus cannot guarantee both safety and termination (§5, §7).
  • fsync-before-respond — the rule that a reply must follow its WAL fsync (I2, P4).
  • Gap-fill — a new leader's process for completing slots a deposed leader left incomplete (§16.2).
  • Group commit — batching multiple WAL appends behind one fsync call (ADR-07).
  • Invariant (I1–I14) — a property enforced structurally or by assertion throughout the system (§7).
  • Jepsen — the chaos/linearizability-testing framework (§5, §28).
  • Joint consensus — Raft-style two-phase reconfiguration; this project's rejected default (ADR-16, §36.1).
  • Leader stickiness — retaining the current leader until Φ crosses the step-down threshold or a higher ballot is observed (§15.3).
  • Learner — the role that observes Accepted messages and determines chosen values (§11.6).
  • Lease read — an opt-in read path serving from local state under a bounded-clock-skew assumption (ADR-18).
  • Linearizability — the strongest single-object consistency model; the default read/write guarantee here (§5, §20).
  • Log compaction — truncating the WAL after a snapshot, retaining a small tail (§17.4, I12).
  • Maelstrom — the lightweight protocol-conformance workload runner (§5, §23.5).
  • Membership — the current set of acceptors plus an epoch (§11.11).
  • Multi-Paxos — the log-replication extension of Basic Paxos using a stable leader (§16).
  • Omega (Ω) — the weakest failure detector for which consensus is solvable (Chandra-Toueg 1996, §15.2).
  • P1/P2/P2a/P2b/P2c — the five safety properties from Paxos Made Simple section 2.2 (§8.2).
  • Phi (Φ) accrual failure detector — an adaptive, jitter-tolerant suspicion-level detector (Hayashibara 2004, §15.1).
  • Pipelining — sending multiple Accept rounds without waiting for prior ones to complete (ADR-13, I14).
  • Prepare/Promise/Accept/Accepted/Learn — the five wire messages of the protocol (§8.4).
  • Principle (P1–P14) — a numbered design principle governing every later decision (§6).
  • Proposer — the RAM-resident role that drives ballots and derives values per P2c (§11.5).
  • Quorum — a majority subset of acceptors; any two quorums intersect (§11.2, I6).
  • Read-index — an opt-in read path confirming leadership via a heartbeat-quorum round (ADR-19).
  • Reconfiguration — a membership change, chosen as an ordinary log value (§18, MM8).
  • RTO (Recovery Time Objective) — the maximum acceptable time to restore service after a failure (§4 row 20, M9).
  • Slot — a position in the replicated log, each an independent Basic Paxos instance (§8.4, §11.9).
  • Snapshot — a content-addressed, point-in-time encoding of the application state machine (§17.2, I8).
  • Split-brain — two partitions each believing they hold a valid quorum; prevented by I6 (T6, FM7).
  • State Machine Replication (SMR) — Schneider 1990's model of consensus-driven determinism (§5, I11).
  • TLA+ — the formal specification language used to generate conformance traces (§5, §21).
  • Viewstamped Replication (VR) — the primary-backup replicated-log architecture co-discovered before Paxos was widely understood (§5, §36.3).
  • WAL (Write-Ahead Log) — the append-only durability log underlying acceptor state (§8.5, §14).
