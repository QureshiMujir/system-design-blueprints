⬜ Phase 0 — Skeleton, Governance & Single-Decree Smoke Test §12

Objectives

Stand up the repository (§10) and governance scaffold; land CI; prove a 3-acceptor in-process Basic Paxos round commits a value end to end with no persistence yet (P2: single-decree before multi-decree; durability is Phase 2's job, §14).

Deliverable

make bootstrap && make build && make test all exit 0; one passing integration test (single_decree_smoke) proving Basic Paxos commits "hello" across 3 in-process acceptors.

Acceptance
  • make test exits 0 with ≥ 1 passing test.
  • All 3 acceptors report accepted_value = Some("hello"); the learner reports chosen[SlotId(0)] = "hello".
  • CI green on ci.yml for a fresh clone; cold-cache build ≤ 5 minutes on a 4-vCPU runner.
  • ADR-01, ADR-02, ADR-03, ADR-04, ADR-22, ADR-25 written as long-form docs under docs/adr/.
Fixtures
Fixture Purpose Expected Output
single_decree_smoke.rs end-to-end 3-node commit all acceptors + learner agree on "hello"
fixtures/empty_cluster.json malformed: cluster_size=0 Quorum::try_new returns None
fixtures/single_acceptor.json degenerate n=1 cluster quorum=1; commits immediately (regression guard)
Pitfalls
  • A timing-dependent smoke test flakes under CI scheduler jitter — use Notify, never sleep.
  • Running all three roles in one task can hide bugs the simulator (§21) would later catch: the dispatch path used here must be the same one Phase 7's network layer uses (§3, boundary 1).

⬜ Phase 1 — Single-Decree Basic Paxos §13

Objectives

Implement the full two-phase protocol (§8.2, §8.3) as the load-bearing safety core of the entire stack. Get this phase wrong and every later phase is wrong (P2).

Deliverable

paxos-core compiles no_std-clean (ADR-02); single-decree Paxos passes against 3/5/7/9- acceptor topologies in unit tests.

Acceptance
  • Property test property.agreement: 100,000 random Prepare/Promise/Accept/Accepted interleavings never violate I1 (only one value ever chosen for slot 0).
  • tla.basic_paxos (§23.5) Pass: every TLA+-generated trace from notes/tla-spec/BasicPaxos.tla replays bit-identically against the implementation.
  • cargo build --no-default-features --target thumbv7em-none-eabihf -p paxos-core succeeds (the no_std proof, ADR-02).
Fixtures
Fixture Purpose Expected Output
fixtures/prepare_bottom_ballot.bin §8.8 malformed input rejected
fixtures/stale_accept.bin §8.8 dropped, no reply, no fsync
fixtures/malformed_promise_split.bin §8.8, I5 rejected at deserialisation
fixtures/duelling_proposers.yaml two proposers racing ballots eventually exactly one commits; I1 never violated
Pitfalls
  • Prepare requires strictly >, Accept requires >= (I4) — asymmetric; reversed, either liveness or safety breaks.
  • P2c case (b) uses "< n", never "<= n" — including n itself creates a circular dependency when a proposer's own Accept reaches one acceptor before its Promise returns.
  • The proposer's ballot is RAM-only but must be monotonic across restarts (I13) — derive the next round from a persisted max_observed_round + 1 or wall-clock-microseconds.
  • Promise must carry (accepted_ballot, accepted_value) as one atomic pair (I5) — never reconstruct one field from context.

⬜ Phase 2 — Durable Acceptor State (WAL) §14

Objectives

Close the crash-recover safety gap left open by Phase 1: land paxos-storage, enforcing P4/I2/I7.

Deliverable

WAL append+fsync+recovery library; a "crash-recover" simulator scenario (early use of the §21 tooling) asserting idempotent re-Prepare handling after any crash point.

Acceptance
  • simulator.crash_recover_1k (§23.5): 1,000 random crash points between fsync and transmit, zero I1/I2 violations.
  • Recovery time for a 100 MB WAL on NVMe ≤ 500 ms (M11).
  • Property test: a CRC mismatch always truncates cleanly, never panics.
Fixtures
Fixture Purpose Expected Output
fixtures/wal_torn_tail.bin §8.8 torn write truncated to last valid record
fixtures/crc_missing_length_prefix.bin regression: CRC computed without length prefix rejected as forged (§14.6)
fixtures/snapshot_before_wal_pointer_crash.yaml crash between snapshot fsync and WAL-pointer fsync orphaned snapshot detected, reused or GC'd (I8, I12)
Pitfalls
  • sync_data (fdatasync) does not sync metadata; append-only file-size growth needs data=ordered ext4 (or equivalent) — documented in docs/runbook/slow-disk.md (§26).
  • CRC32C must cover the length prefix, not only the payload — omitting it leaves a forgeable-record hole.
  • The snapshot file's own fsync must precede the WAL Snapshot record's fsync (§17.2) — reversed order strands recovery with a WAL pointer to a non-existent snapshot file.

⬜ Phase 3 — Failure Detection & Leader Election §15

Objectives

Ship the liveness-only overlay (P5) that Multi-Paxos needs for throughput: Phi-accrual (Hayashibara 2004, ADR-10) wrapped as Chandra-Toueg's Ω (1996).

Deliverable

paxos-failure-detector crate passing the Hayashibara 2004 §5 evaluation; a partition_heal simulator scenario.

Acceptance
  • False-positive rate < 1/hour at Φ-threshold=8 under 50ms±10ms simulated jitter (M13).
  • simulator.partition_heal_1k (§23.5): Ω converges on a single leader within 3s of heal across 1,000 trials.
  • slow_disk scenario: a node with 100× slow disk is detected by Ω within the configured threshold.
Fixtures
Fixture Purpose Expected Output
fixtures/phi_jitter_50ms.yaml Hayashibara §5 evaluation replay FP rate < 1/hr
fixtures/two_leaders_transient.yaml partition-heal race I1 holds; throughput dips; converges ≤ 3s
Pitfalls

Use a monotonic clock only (CLOCK_MONOTONIC / mach_absolute_time), never SystemTime — wall-clock jumps produce nonsense Φ values. Heartbeat piggy-backing needs an explicit idle-heartbeat fallback. Two simultaneous "leaders" are safe but a throughput disaster — Phase 4 (§16) adds "demote on observing a higher ballot."

⬜ Phase 4 — Multi-Paxos Log Replication §16

Objectives

Turn single-decree Paxos into a useful replicated log: a stable leader skips Phase 1 across slots (Chandra/Griesemer/Redman 2007 §4), cutting the steady-state cost from 2 rounds to 1 (§4 row 4).

Deliverable

A 3-node Multi-Paxos cluster commits 100,000 values to a key-value state machine; all three nodes reach bit-identical final state.

Acceptance
  • leader_handoff simulator scenario: new leader elected ≤ 3s after failure, gap-fills any in-flight slots correctly, resumes throughput.
  • Pre-hardening bench.steady_state: ≥ 20,000 commits/sec on 3-node localhost, p99 ≤ 10ms (Phase 10, §22, raises this to M1/M5).
  • tla.multi_paxos (§23.5) Pass against notes/tla-spec/MultiPaxos.tla.
Fixtures
Fixture Purpose Expected Output
leader_handoff.yaml mid-flight leader crash gap-filled correctly, no data loss
gap_fill_regression.yaml slot with a revealed prior accepted value re-proposes prior value, never a new client value
tla_traces/multi_paxos/* TLA+ conformance bit-identical replay
Pitfalls

The bulk-Prepare ballot must exceed any ballot the deposed leader used in its own gap-fills (I13) or P2c breaks. A leader that detects a higher ballot must demote, not continue issuing Accepts — technically safe either way, but "two leaders both winning slots" is a throughput disaster (P5). The application SM must be deterministic (I11) or replicas silently diverge.

⬜ Phase 5 — Snapshots & Log Compaction §17

Objectives

Bound WAL growth and crash-recovery time (ADR-14, ADR-15) — without this, recovery time grows proportional to lifetime throughput.

Deliverable

A 1M-write soak produces ≤ 20 snapshots, the WAL never exceeds 80 MB, and crash-recovery time stays under 500 ms.

Acceptance
  • crash_after_snapshot_file_before_wal_pointer scenario: post-recovery, the orphaned snapshot file is detected and either hash-matched-and-reused or garbage-collected (I8, I12).
  • Learner catch-up via a 64 MB snapshot completes in ≤ 1s (M10).
Fixtures
Fixture Purpose Expected Output
snapshot_hash_mismatch.yaml non-deterministic SM canary mismatch detected, alarm raised (I8)
orphaned_snapshot_gc.yaml crash between fsyncs (a) and (b) orphan reused or GC'd, no safety impact
Pitfalls

A naive snapshot blocks the apply path while encode_state() runs — a multi-second stall for large SMs (the copy-on-write fix lands in Phase 10, §22). SM state must use BTreeMap, never HashMap — iteration-order divergence silently breaks P8/I8. Per-node GC deletes any snapshot file whose hash does not match the current snapshot.

⬜ Phase 6 — Membership Reconfiguration §18

Objectives

Change cluster membership online without violating quorum intersection (I6/I10) — the α-parameter trick (Paxos Made Live section 5.3, ADR-16) is the default mechanism.

Deliverable

Adding a node to a 3-node cluster: throughput continues uninterrupted, the new node catches up via snapshot, and the cluster reaches a stable 4-node (2,3)-quorum configuration within 10s.

Acceptance
  • jepsen.membership_change (§23.5, §28): linearizability holds across a 60s run with 5 add/remove operations.
  • reconfig_under_partition scenario: a reconfiguration proposed during a partition is either fully applied or fully rolled back — never half-applied.
  • Reconfiguration completion time ≤ 10s (M12, α=3, 3→4 nodes).
Fixtures
Fixture Purpose Expected Output
reconfig_alpha_offbyone.yaml α=0 regression guard rejected — I10 requires α ≥ 1
reconfig_nonintersecting_quorum.yaml C={1,2,3} → C'={4,5,6} rejected at the API (I10)
Pitfalls

α off-by-one is the single most subtle correctness invariant in the stack: α=0 loses safety (§8.2's P2c argument no longer closes across the boundary); confusing < with <= in the effective-slot lookup costs consistency. A removed node must remain reachable until its α-window clears. The joint-consensus alternative (PhaseDeferred("§18.6"), ADR-16b) exists for operators who want it, but is not exercised by the main-line conformance suite.

⬜ Phase 7 — Network Transport §19

Objectives

Replace the in-process channel used through Phase 6 with a real TCP transport (ADR-20).

Deliverable

A 3-node Docker-Compose deployment commits 100,000 values across the real network at p99 ≤ 10ms (pre-hardening; §22 lowers this to M5's 5ms).

Acceptance
  • tcpkill-injected partitions cause Φ to spike and a new leader to be elected; throughput resumes automatically.
  • maelstrom.lin_kv (§23.5) Pass against a network-deployed 3-node cluster.
Fixtures
Fixture Purpose Expected Output
network_partition_docker.yaml Docker-Compose partition injection Φ spike, leader re-election, resumed throughput
half_open_connection.yaml one side crashes without closing SO_KEEPALIVE detects within 30s
Pitfalls

Nagle batches small heartbeat writes by default — set TCP_NODELAY on that stream only. A half-open connection is undetectable without keepalive or application heartbeats. Message ordering is FIFO per connection but not across reconnects — the leader's ballot-tracking code must not assume in-order arrival across a reconnect boundary.

⬜ Phase 8 — Client API & Linearizable Reads §20

Objectives

Ship the linearizable read/write surface applications actually call: Client (§11.12), ReadMode::{Linearizable, ReadIndex, Lease} (ADR-19, ADR-18).

Deliverable

examples/linearizable_kv.rs runs a key-value store over 3-node Paxos with all three read modes selectable.

Acceptance
  • jepsen.linearizable_register (§23.5): Pass under a 5-minute partition-and-rejoin chaos workload.
  • Linearizable read p50 ≤ 2ms, p99 ≤ 8ms (M6, M7); read-index p50 ≤ 1ms; lease read p50 ≤ 100µs (M8).
Fixtures
Fixture Purpose Expected Output
linearizable_read_regression.yaml leader no-op read path linearizable under partition-and-rejoin
non_leader_read_rejected.json read routed to a non-leader rejected at the public API
lease_clock_skew_failure.yaml documents ADR-18's failure mode stale read reproduced under injected skew, as expected
Pitfalls

A read served from a non-leader is not linearizable — the library refuses it at the API; there is no "read any node for load balancing" escape hatch (use read-index instead). leader_hint can be stale; the client retries up to 5 times, then surfaces an error the application must handle. Read-index and lease reads are not "free" linearizability — they buy it under an additional, named assumption the caller must understand (ADR-18, ADR-19).

⬜ Phase 9 — Deterministic Simulator & TLA+ Conformance §21

Objectives

Build the primary safety oracle referenced by §7's debugging methodology: a deterministic, seed-reproducible simulator (ADR-21) plus TLA+ trace replay (ADR-22).

Deliverable

The simulator runs at 10,000× real-time on a single core for a 3-node cluster (a 1-hour scenario completes in < 1s); 1,000,000 random scenarios run nightly with zero safety violations.

Acceptance
  • tla.basic_paxos and tla.multi_paxos (§23.5) both Pass.
  • Simulator throughput ≥ 1,000,000 events/sec, single core (M14).
  • A failing seed bisects to its minimal reproduction automatically, attached to the CI failure.
Fixtures

The six named scenarios under simulator/scenarios/ (§10); the regression seed corpus under conformance/corpora/invariants/.

Pitfalls

Determinism is fragile: HashMap iteration order is forbidden inside SimNode (BTreeMap only, P8/I11). Production code must route "now" through the Clock trait (§11), never call Instant::now() directly, or the simulator loses control of time. A single-threaded simulator never exhibits a race that only manifests under true parallelism — audit any code path that "assumes the simulator can't reach me."

⬜ Phase 10 — Performance Hardening §22

Objectives

Reach the M1–M16 throughput/latency targets (§4, §30): batching, pipelining, an optional io_uring backend, copy-on-write snapshotting, and memory pooling.

Deliverable

Steady-state throughput ≥ 100,000 commits/sec on 3-node localhost (M1); p50 ≤ 2ms, p99 ≤ 5ms (M4, M5); leader-failover RTO ≤ 5s (M9).

Acceptance

bench.steady_state meets M1/M2/M3 across localhost/LAN/WAN profiles; bench.leader_failover meets M9; parallel Learn-WAL-append and SM-apply preserve commit_index ordering under load.

Fixtures

crates/paxos-bench/benches/{steady_state,leader_failover,snapshot,reconfig}.rs (§10), each asserting its respective M-target as a hard CI gate (§30).

Pitfalls

Batching amortises fsync cost but adds up to 1ms of latency to the first proposal in a batch — tunable, defaults bias throughput. Pipelining requires the I14 per-slot map; a shared "outstanding" counter silently corrupts independent-slot commitment. io_uring is Linux-only, feature-gated — the std::fs fallback must be exercised in CI on every platform.

Every bucket below reports Pass except those explicitly Deferred; the 30-day soak (M15) shows zero safety violations and zero memory growth; the 30-day fuzz canary (M16) shows zero panics/hangs across all four fuzz targets.
