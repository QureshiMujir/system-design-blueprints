Three properties of this architecture are referenced throughout and must never be violated by a later phase. First, proposer/acceptor/learner are state-machine traits (§11), not threads or processes; one physical node hosts all three roles and routes locally-produced messages through the identical dispatch path used for remote messages (§14.2), so paxos-sim (§21) can substitute one for the other with zero behaviour change. Second, acceptor state and proposer state are strictly separated (P12, I1): an acceptor's promised_ballot is durable disk state under fsync; a proposer's in-flight ballot is RAM-only and resets on restart — conflating the two produces the canonical "restart re-issues a promised ballot" safety bug (Phase 1 §13.6). Third, the protocol layer (proposer/acceptor/learner, §13) has zero knowledge of leaders, failure detectors, batching, or pipelining — those are optimisations layered on top per Paxos Made Live §4 (P5), and removing any of them must not affect safety, only throughput. A "leader" or "batching" code path discovered inside the protocol layer is a design defect.

8. Domain Model / Protocol / Data Model

8.1 Message Taxonomy

Five wire messages carry Basic Paxos end to end (exact field signatures in §11.3): Prepare, Promise, Accept, Accepted, Learn. Multi-Paxos (§16) adds Heartbeat, CatchupRequest, CatchupResponse, ReconfigPropose — all composed from the same five primitives plus a SlotId.

8.2 The Safety Property Set (Paxos Made Simple section 2.2, verbatim)

  • P1. An acceptor must accept the first proposal that it receives.
  • P2. If a proposal with value v is chosen, every higher-numbered proposal that is chosen has value v.
  • P2a. If a proposal with value v is chosen, every higher-numbered proposal accepted by any acceptor has value v.
  • P2b. If a proposal with value v is chosen, every higher-numbered proposal issued by any proposer has value v.
  • P2c. For any v and ballot n: if a proposal (n, v) is issued, there exists a majority set S of acceptors such that either (a) no acceptor in S has accepted any proposal numbered < n, or (b) v is the value of the highest-numbered proposal < n accepted by any acceptor in S.

P2c is load-bearing: I5 (Promise carries both fields as one unit) and I6 (quorum intersection) exist solely to keep P2c provable; §16.1's "adopt the highest-accepted value from the quorum" rule is P2c's direct implementation.

Wire format: [u32 len][u32 crc32c][bincode payload]; CRC32C covers the length prefix and the payload (§14.6 pitfall — omitting the length prefix from the CRC is a known forgery hole).

8.7 Worked Example — 3-Acceptor Single-Decree Commit

Node A proposes "hello" at ballot (1, A) against {A, B, C} (quorum = 2, §4 row 2). Prepare reaches all three; none has prior state, so each promises and fsyncs promised_ballot=(1,A). A collects the quorum, sees no prior accepted value in any Promise, so P2c case (a) applies: A proposes its own value, "hello". Accept reaches all three; each has promised_ballot <= (1,A), so each fsyncs accepted_ballot=(1,A), accepted_value="hello" and replies Accepted. The learner counts 2 Accepted(1,A) — quorum met (I9) — and emits Learn(slot=0, (1,A), "hello"). Final acceptor states are bit-identical across A, B, C: {promised:(1,A), accepted:(1,A), value:"hello"}.

8.9 Failure-Path Example — Leader Crash Mid-Round

Leader L at ballot (5,L) broadcasts Accept(5,L,slot=42,"v") to {A,B,C}. A acks Accepted; L crashes before B/C reply. Ω (§15) elects L', which issues a bulk Prepare at ballot (6,L') covering slot 42 (§16.1). A's Promise reveals accepted=(5,L,"v") — the only accepted pair in L''s quorum. P2c forces L' to re-propose "v" (never a new client value) for slot 42; L' broadcasts Accept(6,L',42,"v"); on quorum, slot 42 commits with the original value. No data loss, no client-visible divergence (§16.2 fill_gaps, FM4).

Design principles (§6)

  • Operational implication: round must be fsync'd (or wall-clock-derived) before use, I13.
