Hard questions (§37)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does a linearizable read cost a network round trip while a serializable read does not, and what specifically would break if that were reversed? (§4, I3)
  2. Trace exactly what happens to an in-flight Compare/Then/Else transaction if the leader crashes after proposing but before the client observes the result — cite the invariant that guarantees no partial application. (§20, I6)
  3. Why is the lease manager's map follower-replicated even though only the leader runs the expiry scan? What would leak if it were leader-local only? (§19, MM4, I5)
  4. Derive the write-amplification threshold at which bbolt should be swapped for an LSM backend, and name the ADR governing that swap. (§36 C4, §9 ADR-05)
  5. Why does compaction need to consult the watch hub's fence before removing a revision, and what invariant would break without that check? (§14, §15, I7)
  6. A client retries a Put after an ambiguous timeout. Walk through exactly how the system guarantees the retry does not double-apply, naming both the client-side and apply-side mechanism. (§16.6, I13, P14)
  7. Why is the cross-project trait surface exactly five traits, no more, no fewer — what would break architecturally if Transport were folded into StateMachine? (§11.7, P11)
  8. Contrast this design's read-fencing approach to linearizability (ReadIndex) against Spanner's TrueTime approach — what does each assume, and what does each cost? (§37 draws on §1, §5, §38 AA-2)
  9. Why is RangeEnd < Key defined as "empty result" rather than an error, and what downstream consumer behavior does that choice protect? (§8.7, §13.6)
  10. Explain why the mini-txn's 128-op cap and 8-level nesting cap both exist, and what would degrade if either were removed. (§4, §20, I12)
  11. A learner node is added mid-snapshot-transfer to another learner. Why is a second concurrent membership change rejected here, and what Raft-level property does that rejection protect? (§17, I10)
  12. Why does restoring from a snapshot require rewriting the cluster id, and what specific failure mode does skipping that step create? (§18.6, I8, FM-8)
  13. Derive the peak replication bandwidth at the M1 throughput target and explain why it is not the binding constraint on cluster size — what is? (§36 C1, §33)
  14. Why is a "fast read" optimization disabled by default, and under what specific network condition does it violate linearizability? (§25.6, MM5, I3, T1)
  15. Compare the audit-log-driven detection strategy for RBAC over-grant (T10) against a preventive-only strategy (e.g., mandatory code review of role changes) — what does the design gain by having both? (§26, §21)
  16. Why does the key index need a full rebuild from the backend on cold start rather than being itself persisted and loaded directly? (§14.6, I9, MM8)
  17. Explain why full (non-mini) cross-key OCC is deferred rather than built, tracing the specific complexity it would add to the single apply goroutine. (§20.10, §39, P5)
  18. Using the C2 and C4 capacity numbers, at what approximate sustained write rate would this design's single-Raft-group ceiling be reached, and what is the documented lever beyond it? (§36, §33)
  19. Why must the watch hub's Notify call be non-blocking with respect to any individual slow watcher, given that Notify is invoked inline from the apply path? (§15.9, MM3, MM7)
  20. What specific property of Raft's joint-consensus mechanism makes it safe to expose only coarse-grained member add/promote/remove verbs to operators rather than raw configuration edits? (§17.2, §5 Ongaro dissertation)
  21. Contrast this design's mini-transaction boundary with FoundationDB's full ACID model — what operational simplicity does the narrower boundary buy, and what capability does it forfeit? (§35, §5 FoundationDB paper, ADR-09)
  22. Why is Byzantine fault tolerance explicitly out of scope rather than "future work" without qualification, and what deployment assumption makes that acceptable? (§26 T4, §38 AA-3, §1)
  23. Trace how a client's (client_id, sequence) pair interacts with both idempotent retries (I13) and read-your-writes within a transaction (§20.2) — are these the same mechanism or two distinct ones?

34. Mental Models & First Principles

MM1. A replicated KV store is a log with a deterministic reducer. The Raft log is the source of truth; mvcc.Apply.Apply is the fold function. Predicts: any two nodes that applied the same log prefix must hold identical state, with no exceptions. Bug class without it: engineers "helpfully" add non-deterministic behavior (wall-clock reads, random tie-breaks) inside Apply, causing irreproducible per-node divergence that no amount of retry logic fixes. Applied in Phase 4 (§16), I1.

MM2. MVCC turns time into a first-class index dimension. A revision is not a version number bolted onto a mutable record — it is the primary key's second dimension. Predicts: any read API that does not accept an explicit revision is incomplete for this domain. Bug class without it: "current value only" thinking leaks into watch/historical-read design and silently drops the audit trail Kubernetes-style controllers depend on. Applied in Phase 2 (§14), §8.

MM3. A watch is a materialized diff stream, not a poll. The hub pushes; it never waits to be asked. Predicts: backpressure is mandatory the moment any consumer can be slower than the producer, which is always eventually true. Bug class without it: an unbounded per-watcher buffer that appears fine in testing and OOMs the server under one slow production consumer. Applied in Phase 3 (§15), I4.

MM4. Leases are distributed timers with consensus-anchored truth, not client-side timers. Expiry is a decision, made once, by whichever node currently holds the authority to decide (the leader), over replicated state. Predicts: a lease implementation that lives only on the leader leaks state on leader change; one that lives only on the client can split-brain under partition. Bug class without it: "just use a local time.AfterFunc" reappears every time a new engineer touches this subsystem. Applied in Phase 7 (§19), I5, P4.

MM5. Linearizability is a read-your-own-commit contract enforced by fencing, not by clock sync. ReadIndex fences a read against a confirmed commit point; it does not require synchronized clocks (contrast with Spanner's TrueTime, §5, §38 AA-2). Predicts: any read-latency optimization that skips the fencing step (a "fast read") reintroduces staleness under partition. Bug class without it: engineers assume "the leader is always right about now" and build a clock-based shortcut that breaks I3 exactly when the network is unreliable — precisely when correctness matters most. Applied in Phase 4 (§16), I3, T1/FM-3.

MM6. A transaction is a single proposal, not a sequence of operations. Atomicity is a property of the proposal boundary, not of application-level bookkeeping. Predicts: any implementation that proposes a txn's ops individually and reconciles afterward has already lost atomicity. Bug class without it: "we'll just retry the failed sub-op" logic that silently produces partial application under a crash. Applied in Phase 8 (§20), I6.

MM7. Backpressure is a queue with an explicit eviction policy, not the absence of a queue. Every bounded channel needs a defined behavior at capacity (drop, block, or evict-and-signal) — "we'll just make the buffer big enough" is not a policy, it is a deferred incident. Predicts: any unbounded buffer in the design is a future OOM, regardless of how unlikely overflow "feels" today. Bug class without it: memory growth that only manifests after days of slow-consumer accumulation, invisible in short test runs. Applied in Phase 3 (§15), I4, I12, P12.

MM8. The storage backend is a durability oracle; the apply layer is a correctness oracle. These are different responsibilities deliberately kept behind a narrow interface (backend.Backend, §11.6) — the backend promises "what I told you I wrote, survives a crash"; the apply layer promises "what I told you happened, happened exactly once, in this order." Predicts: conflating the two (e.g., letting the apply layer assume backend-internal transaction semantics it hasn't contracted for) breaks backend swappability (P10). Bug class without it: a backend-specific optimization leaks into mvcc.Apply, silently locking the project to one storage engine despite ADR-05's stated alternates. Applied in Phase 2 (§14), P10, ADR-05.

5. Required Reading

Books

  • Martin Kleppmann, Designing Data-Intensive Applications (O'Reilly, 2017). Ch. 5 (Replication), Ch. 7 (Transactions), Ch. 9 (Consistency and Consensus). Extract: the linearizability/serializability distinction and the replication-lag failure modes. Applied in §3, §8, Phase 4 (§16).
  • Alex Petrov, Database Internals (O'Reilly, 2019). Part I ch. 2–7 (B-Trees, page layout, copy-on-write), Part II ch. 11–14 (replication, consensus, transactions). Extract: storage-record layout discipline and how B+Tree engines interact with MVCC. Applied in §8, §11, Phase 2 (§14).
  • Andrew S. Tanenbaum & Maarten van Steen, Distributed Systems (3rd ed., 2017). Ch. 7 (Consistency and Replication), Ch. 8 (Fault Tolerance). Extract: the quorum-intersection argument and failure-detector taxonomy. Applied in §7 (invariants), §27 (Failure Modes & Recovery).
  • Roberto Vitillo, Understanding Distributed Systems (2021). Ch. on Consensus, ch. on Replication, ch. on Time & Order. Extract: a practitioner-level derivation of why leases need a consensus anchor. Applied in Phase 7 (§19), MM4.
  • Betsy Beyer, Chris Jones, Jennifer Petoff, Niall Murphy (eds.), Site Reliability Engineering (O'Reilly/Google, 2016). Ch. 4 (SLOs), Ch. 6 (Monitoring Distributed Systems), Ch. 14 (Managing Incidents). Extract: the SLO/alerting philosophy this store's operational readiness section adopts. Applied in §28 (Operational Readiness).
  • Michael T. Nygard, Release It! (2nd ed., Pragmatic Bookshelf, 2018). Ch. on Stability Patterns (Circuit Breaker, Bulkhead, Timeout). Extract: the bounded-resource discipline (P12) behind every cap in §4. Applied in §4, Phase 3 (§15) backpressure design.

Papers

  • Diego Ongaro & John Ousterhout, "In Search of an Understandable Consensus Algorithm (Raft)", USENIX ATC 2014. Contribution: the Raft algorithm this project's consensus dependency implements. Applied in Phase 4 (§16), ADR-02, I2.
  • Diego Ongaro, Consensus: Bridging Theory and Practice, PhD dissertation, Stanford, 2014. Contribution: the full derivation including joint-consensus membership changes and log compaction. Applied in Phase 5 (§17), I10.
  • Patrick Hunt, Mahadev Konar, Flavio P. Junqueira, Benjamin Reed, "ZooKeeper: Wait-free coordination for Internet-scale systems", USENIX ATC 2010. Contribution: the original coordination-primitive design (znodes, ephemeral/sequential nodes) this design diverges from. Applied in §34 (Comparative Architecture Table).
  • James C. Corbett et al., "Spanner: Google's Globally-Distributed Database", OSDI 2012. Contribution: TrueTime-based external consistency — the model this store explicitly does not build. Applied in §1 (non-goals), §38 (Alternative Architectures, AA-2 contrast).
  • Jingyu Zhou et al., "FoundationDB: A Distributed Unbundled Transactional Key-Value Store", SIGMOD 2021. Contribution: layered transactional KV design; the serious-mode reference for what a full (non-mini) transaction layer would cost. Applied in Phase 8 (§20), ADR-09.
  • Heidi Howard, Dahlia Malkhi, Alexander Spiegelman, "Flexible Paxos: Quorum Intersection Revisited", OPODIS 2016. Contribution: quorum-overlap flexibility framing used for the read/write quorum reasoning in §36's capacity model. Applied in §36 (Back-of-Envelope Capacity Model), I3.
  • Daniel J. Abadi, "Consistency Tradeoffs in Modern Distributed Database System Design", IEEE Computer 45(2), 2012. Contribution: the PACELC framing for why this design picks PC/EC over PA/EL. Applied in §1 (non-goals), §34.
  • Leslie Lamport, "The Part-Time Parliament", ACM TOCS 16(2), 1998. Contribution: Paxos, the historical baseline every modern consensus protocol (including Raft) is measured against. Applied in §38 (Alternative Architectures, AA-4 contrast).
  • Giuseppe DeCandia et al., "Dynamo: Amazon's Highly Available Key-value Store", SOSP 2007. Contribution: the AP-side counterpoint (vector clocks, sloppy quorums, read-repair) this design rejects for a CP store. Applied in §34, §38 (AA-2).
  • Philip A. Bernstein & Nathan Goodman, "Concurrency Control in Distributed Database Systems", ACM Computing Surveys 13(2), 1981. Contribution: the MVCC/2PL taxonomy underlying this store's revision model. Applied in §8 (Domain / Data Model), Phase 2 (§14).

Reference Implementations

  • etcd-io/etcd (Apache-2.0). Study server/etcdserver/, server/storage/mvcc/, server/storage/wal/, server/storage/backend/, server/lease/. Lesson: the MVCC revision/key-index split this project mirrors almost directly. Pitfall: do not import or vendor etcd source — read it, do not copy it (§25 Phase 13 pitfall). Applied in §8, §11, Phase 2 (§14), Phase 7 (§19).
  • hashicorp/consul (MPL-2.0). Study agent/consul/state/, agent/structs/txn.go, agent/consul/leader.go. Lesson: the session-with-health-check alternative to leases. Pitfall: Consul's prepared queries are a different consistency model — do not conflate with mini-txns. Applied in §34, Phase 7 (§19), Phase 8 (§20).
  • tikv/tikv (Apache-2.0). Study the raftstore and txn_types components. Lesson: sharded multi-Raft group management. Pitfall: TiKV's region-split complexity is exactly what Phase-0 scope defers (§33, AA-1). Applied in §33 (Scalability Analysis), §38 (AA-1).
  • cockroachdb/cockroach (BSL). Study pkg/kv/kvserver/. Lesson: MVCC timestamp-ordered transactions layered under a SQL engine. Pitfall: CockroachDB's transaction model is full OCC — do not adopt it wholesale, this project's mini-txn (ADR-09) is deliberately narrower. Applied in §34, Phase 8 (§20).
  • etcd-io/bbolt (MIT). Study db.go, tx.go, bucket.go. Lesson: the mmap'd copy-on-write B+Tree layout this project's default backend wraps directly. Pitfall: bbolt write transactions are single-writer — the apply layer must serialize through one BatchTx at a time (Phase 2, I9). Applied in §11 (Core Schema & Types), Phase 2 (§14).

RFCs / Specifications

  • RFC 8446 — TLS 1.3. The mutual-TLS transport security baseline; applied in ADR-10, Phase 9 (§21), Phase 4 (§16, peer transport).
  • Protocol Buffers Language Guide (proto3), Google. The wire-schema discipline for every message in api/proto/; applied in §8, §11, Phase 0 (§12).
  • OpenTelemetry Specification (CNCF). The tracing/metrics data model; applied in ADR-16, §28 (Operational Readiness).

Glossary (§40) · 38 terms · site-wide glossary

Apply
The act of feeding a committed Raft log entry into the MVCC apply layer (§8.5, I1).
ApplyEnvelope
The proto3 oneof wrapper carrying one committed operation (Put/Delete/Txn/ LeaseGrant/LeaseRevoke/ConfigChange) to the state machine (§8.5).
bbolt
The default Go-native, mmap'd, copy-on-write B+Tree storage backend (ADR-05, §11.6).
Backend
The narrow, pluggable persistence interface the MVCC apply layer depends on (§11.6, P10).
Cluster id
A 64-bit identifier minted once at bootstrap and never changed thereafter (I8).
Compaction
Removing revisions older than a watermark, gated by active watchers' fence (§14, I7).
Compare → Then → Else
The mini-transaction shape: evaluate comparisons, execute one of two branches atomically in a single Raft proposal (§8.5, ADR-09, I6).
Conformance suite
The ~200-fixture ephemeral-cluster wire-protocol verification runner (§24).
Consensus
The agreement protocol (Raft, rank #39) guaranteeing all nodes apply the same log in the same order (I1, I2).
CRC32C
The checksum algorithm used in snapshot trailers to detect corruption (§8.4, I14).
Cross-project trait surface
The five-trait (StateMachine, LogStorage, StableStore, Snapshotter, Transport) locked boundary with the rank-39 Raft library (§11.7, P11).
Deferred feature
A capability explicitly out of this blueprint's build scope, registered with an anchor, building phase, and un-defer trigger (§39).
Election
The process by which Raft nodes agree on a new leader after the previous one becomes unreachable (I2).
Expiry scan
The leader-only goroutine that proposes LeaseRevoke for TTL-expired leases (§19.2, MM4).
Fencing (read fencing)
Confirming a read against a specific confirmed commit index before serving it, the mechanism underlying linearizable reads (I3, MM5).
Generation
A KeyIndex sub-list spanning one create-to-tombstone lifecycle of a key (§8.2, §11.1).
gRPC-gateway
The generated reverse-proxy translating JSON HTTP requests into gRPC calls (P6, ADR-04).
History store
The bbolt key bucket holding (revision, KeyValue) pairs (§8.4).
Joint consensus
Raft's two-phase membership-change protocol ensuring safety during reconfiguration (§17.2, I10).
Key index
The in-memory btree tracking each key's generations and revisions (§8.2, §11.1, I9).
Learner
A non-voting cluster member replicating the log but not counted toward quorum, used during member add before promotion (§17.2).
Lease
A TTL'd, consensus-anchored handle to which keys can be attached for service-discovery semantics (§11.3, ADR-08, MM4).
Linearizable read
A read guaranteed to reflect every write committed before the read began (I3, P1).
Mini-transaction
This project's bounded transaction model (Compare/Then/Else, ≤128 ops), contrasted with general OCC (P5, ADR-09).
MVCC
Multi-version concurrency control — every mutation is a new, immutable, revision-stamped record rather than an in-place update (P2, §8, MM2).
Proposer
The raftnode.Node component that wraps client operations into Raft proposals and correlates results back to callers (§11.5, §16).
ReadIndex
The Raft mechanism confirming a read is fenced against the latest committed index without appending a new log entry (I3, MM5).
RBAC
Role-based access control mapping roles to (key_prefix, permission) grants (§21.2, ADR-11).
Revision
A (Main, Sub) monotonic logical clock stamping every mutation (§11.1, I1, MM2).
Serializable read
A read that may observe a stale local snapshot but is internally consistent, skipping ReadIndex confirmation for lower latency (P1, §4).
Single-writer discipline
The rule that all mutation to shared apply-layer state flows through exactly one goroutine, eliminating an entire class of races (I1, MM1, MM8).
Snapshot
A consistent point-in-time capture of the backend and lease-manager state, used for restore and for catching up lagging followers (§18, I14).
State machine
The StateMachine trait implementation (StateMachineAdapter) the Raft library calls into on every commit (§11.5, §11.7).
Tombstone
The revision at which a key's generation ends (a Delete), distinct from the key simply never having existed (§8.2).
Token store
The replicated, TTL-bounded store of authentication tokens (§21.2, ADR-12, I12).
Watch
A long-lived, server-filtered, backpressured gRPC stream of key-range change events (§11.3, §15, I4, MM3).
Watch hub
The single per-server component dispatching committed events to registered watchers (§11.3, P3, MM3).
WAL
The write-ahead log (owned by the rank-39 Raft library's LogStorage/StableStore) that incremental backups replay from since the last snapshot (§18.2, P7).
