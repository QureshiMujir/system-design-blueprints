38 — Distributed Key-Value Store

Project Number: 38

Project Name: Distributed Key-Value Store

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade, strongly-consistent, replicated key-value store — an etcd/Consul-class coordination substrate — in Go: gRPC + JSON-HTTP-gateway APIs, MVCC with per-key revision history, long-lived server-streaming watches, TTL leases, mini-transactions (Compare → Then → Else), Raft-driven cluster membership (joint consensus), snapshot + incremental-WAL backup/restore, mutual TLS with prefix-scoped RBAC, and an operator CLI (kvctl) plus an embedded read-only dashboard. The store consumes consensus as a library: log replication, leader election, snapshotting mechanics, and ReadIndex confirmation are implemented by the Raft library from project #39 (Raft-Consensus) and consumed across a locked trait boundary (§11.7); this project owns the MVCC engine and every user-facing surface.

Phase-0 deliverable (numbered modules/services):

  1. cmd/kvd — the server binary (gRPC + HTTP gateway + Raft node).
  2. cmd/kvctl — the operator CLI.
  3. cmd/kvbench — the benchmark driver.
  4. internal/mvcc — the MVCC apply layer (state machine).
  5. internal/backend — the pluggable storage-backend interface + bbolt default.
  6. internal/api/{kv,watch,lease,cluster,auth} — the five request-handling subsystems.
  7. internal/raftnode — the adapter implementing the rank-39 trait surface.
  8. pkg/sdk/go and pkg/sdk/ts — client SDKs.
  9. conformance/ — the wire-protocol conformance runner (~200 fixtures).
  10. dashboard/ — the embedded read-only React UI.

System boundaries.

  • Provides: linearizable reads/writes, MVCC history reads, watches, leases, mini-transactions, membership changes, snapshot/restore, mTLS + RBAC, an operator CLI, a conformance suite.
  • Delegates (to rank #39 Raft-Consensus): log replication, leader election, joint-consensus membership mechanics, ReadIndex computation, log/stable storage, snapshot transport chunking.
  • Does NOT provide: SQL or a query language, general (non-mini) transactions/OCC across arbitrary key sets, Byzantine fault tolerance, geo-replication with external consistency (Spanner-style TrueTime), built-in encryption at rest (v1).

Non-goals: replacing a relational database; multi-tenant hostile-workload isolation; serving as a general document store (values are opaque byte blobs, no secondary indexing).

Deployment model: a fixed-size cluster (3, 5, or 7 nodes) of homogeneous kvd processes, one Raft group, deployed via docker-compose (dev) or a Kubernetes StatefulSet (production, out of this blueprint's build scope but assumed by the operator guide). Clients connect over gRPC directly or through the JSON-HTTP gateway.

Target users/operators: platform teams running the store as the coordination substrate for service discovery, leader election, feature flags, and configuration for their own distributed systems (naming the sibling portfolio projects: the Distributed Job Queue at rank 40, the Service Discovery System at rank 42).

What later phases unlock: Phase 4 (Raft integration, §16) unlocks every consistency guarantee this store makes; Phase 7 (Leases, §19) and Phase 8 (Mini-Transactions, §20) unlock the primitives downstream coordination patterns (leader election, service registries) depend on; Phase 11–13 (§23–§25) unlock production readiness (performance validation, protocol conformance, adversarial hardening).

Recommended language: Go 1.22+. Rationale: the reference ecosystem (etcd, Consul, Dgraph, the KV layer of CockroachDB, NATS) is overwhelmingly Go; gRPC/protobuf codegen is first-class; bbolt is a mature Go-native mmap B+Tree with no cgo dependency for the default backend. Rejected: Rust — stronger type-level guarantees and no GC pauses, but the cross-project boundary with the rank-39 Raft library (Rust) is deliberately kept narrow (five traits, §11.7) so a Go consumer process is the correct forcing function for that seam, and Rust's async ecosystem maturity for long-lived bidirectional gRPC streaming (watches) trailed Go's at design time. Rejected: Java — JVM GC pauses directly threaten p99 latency targets (§4) under the throughput profile targeted here.

Prerequisites: concurrent Go (channels, context, sync primitives); gRPC + protobuf; MVCC and snapshot-isolation fundamentals; the rank-39 Raft library's trait surface (StateMachine, LogStorage, StableStore, Snapshotter, Transport); the Raft consensus algorithm (Ongaro & Ousterhout, §5).

Estimated timeline: Phase 0 (repo skeleton + correctness kernel) — 3 weeks. Full system through Phase 13 (§25) — 8–9 months at one senior-engineer-equivalent pace (Appendix B, §42, sums the per-phase durations to 37 weeks).

Deferred features (flagged, anchored to where they are analyzed in this document):

  • Multi-Raft / sharded key-range partitioning — PhaseDeferred("§33").
  • Geo-distributed placement with WAN-tuned timeouts — PhaseDeferred("§33").
  • Per-key-prefix encryption at rest — PhaseDeferred("§26").
  • Full (non-mini) cross-key OCC / general transactions — PhaseDeferred("§20").
  • gRPC-Web first-class browser transport (no gateway hop) — PhaseDeferred("§22").
  • Byzantine fault tolerance — PhaseDeferred("§38").
  • etcdctl-compatible CLI mode — PhaseDeferred("§22").
  • Read-only eventually-consistent learner replicas — PhaseDeferred("§17").

Every deferred feature above is registered with its building phase and un-defer trigger in the Deferred Features Register (§39).

2. Why Build This

  • Linearizability is not free. Every linearizable read costs a heartbeat round trip (ReadIndex), a leader lease, or a hard pin to the leader — the choice governs behavior under partition (P1, I3).
  • MVCC is the primitive, not an add-on. Without revisions and watches the store cannot drive Kubernetes-style level-triggered controllers; with them it becomes the substrate for reactive systems (P2, §8).
  • Watches are the hardest contract to get right. Long-lived, server-filtered, backpressured gRPC streams are where most "etcd-clone" side projects silently fail (§15, MM3).
  • Consensus is rented, not owned. Building Raft is project #39; consuming it across a five-trait boundary (§11.7) is this project — the boundary is the most architecturally interesting seam in the portfolio and must survive refactors on both sides (P11).
  • Operability is the product, not an afterthought. The store is run by humans at 3 a.m.; kvctl, the runbooks (§28), and the audit log are first-class deliverables, tied to explicit acceptance criteria in every phase (N.4).
  • Cross-links: the Distributed Job Queue (rank 40) and Service Discovery System (rank 42) both assume this store's lease and watch primitives exist; building them late means rebuilding those consumers later.
  • Calibration value: this is the only project in the portfolio that forces reconciling consensus theory (Raft), storage-engine mechanics (B+Tree MVCC), and network-facing API design (long-lived streaming RPC) in one system.

This blueprint takes etcd 3.x as its center of gravity and HashiCorp Consul's KV layer as its second reference — the two converged on similar shapes from different starting points, which is evidence the common subset is sound. Where they disagree (Consul's session-with-health-check model vs etcd's pure lease; Consul's prepared queries vs etcd's transactions) this blueprint follows etcd because Kubernetes' continued dependence on it means the protocol surface is the most battle-tested in the class (§34 compares both formally).

What Mastery Looks Like

  • Consensus-as-a-library boundary design — can draw the exact five-trait seam (§11.7) a KV store needs from a Raft library and defend why each trait lives where it does (Phase 4, §16).
  • MVCC storage-engine design — can derive a revisioned key index and history-store layout from first principles and explain compaction's interaction with live watchers (Phase 2, §14; I7).
  • Backpressured streaming protocol design — can design a bounded-outbox watch hub that never blocks its single-writer notify path under a slow consumer (Phase 3, §15; MM3, MM7).
  • Distributed timer design under partition — can explain why leases must be consensus-anchored and follower-replicated rather than leader-local (Phase 7, §19; MM4).
  • Bounded transaction design — can explain why Compare → Then → Else is chosen over general OCC and derive the failure mode a full multi-key lock manager would introduce (Phase 8, §20; ADR-09).
  • Cluster lifecycle operations — can run a 3→5→3 membership change and a snapshot/restore round-trip and explain every invariant (I8, I10, I14) that must hold across each (Phase 5–6, §17–§18).
  • Threat-model-driven hardening — can enumerate the adversary classes this design tolerates vs. documents as out-of-scope and justify the boundary (Phase 13, §25; §26).
  • Capacity reasoning — can derive every number in §36 from the §4 constraints table without looking either up, reproducing the formulas by hand.

Clients. kvctl, the Go/TS SDKs, and higher-level controllers issue gRPC calls directly or via the JSON-HTTP gateway; the gateway is generated, never hand-written (P6, ADR-04).

Request Pipeline. Every inbound call passes through request-id assignment, authentication (mTLS CN or token, §21), authorization (RBAC, §21), and routing (writes and linearizable reads to the leader; serializable reads locally) before reaching a handler (I3).

Proposer (raftnode.Node). Wraps writes/txns/config-changes into an ApplyEnvelope, calls the rank-39 library's propose API, and correlates the eventual Apply callback back to the waiting caller via a per-proposal channel (§16, I13).

Watcher hub (api/watch.Hub). A single per-server hub; the MVCC apply layer's Notify posts every committed event to it; each watcher owns a bounded outbox and a dedicated goroutine (§15, I4, MM3).

Lease manager (api/lease.Manager). A follower-replicated map of TTL'd leases; only the current leader runs the expiry-scanning goroutine, but the map itself is written via the same Raft proposal path as any other mutation (§19, I5, MM4).

MVCC Apply Layer (internal/mvcc). The StateMachine implementation the Raft library calls into. Owns the revision counter, the in-memory key index, the bbolt-backed history store, and the background compactor (§14, I1, I7, I9).

Backend interface (internal/backend). A narrow, swappable persistence contract; bbolt is the locked default, pebble and the rank-67 B-Tree engine are build-tag alternates (P10, ADR-05).

Raft library (rank #39). Owns log replication, leader election, joint-consensus membership, ReadIndex computation, and snapshot chunked transport; consumed across the five-trait boundary in §11.7 (P11, ADR-02).

6. Design Principles

P1. Strong consistency by default. Rule: writes are linearizable; reads are linearizable via ReadIndex unless the caller explicitly requests Serializable. Tradeoff: a heartbeat round trip on every default read vs. a stale-read risk on the explicit escape hatch. Operational implication: p99 read latency (§4) is bounded below by RTT to the leader, not by disk. Violating it breaks: silent stale reads corrupt any leader-election or lease-based consumer that assumes "read reflects last write."

P2. MVCC is the only data model. Rule: every mutation increments the global Revision; nothing is mutated in place. Tradeoff: history retention costs storage until compacted. Operational implication: compaction (I7) becomes a first-class scheduled operation, not an afterthought. Violating it breaks: watches and historical reads both depend on revision-addressable state — lose MVCC and you lose both.

P3. One watch hub, one notify path per server. Rule: all committed events pass through a single api/watch.Hub.Notify call, in commit order. Tradeoff: the hub is a potential serialization point. Operational implication: hub throughput must exceed apply throughput with margin (§32, M4). Violating it breaks: out-of-order or duplicated events silently desynchronize every downstream controller (I4).

P4. Leases are consensus-anchored timers, not client-side timers. Rule: a lease's expiry is decided by Raft-replicated state and enforced by the current leader's single expiry-scan goroutine. Tradeoff: expiry precision is bounded by scan interval (100 ms, §19) not wall-clock TTL exactness. Operational implication: a leader change must hand off the expiry timer without losing or double-firing leases (I5). Violating it breaks: client-side timers permit split-brain lease interpretation across a partition.

P5. Transactions are mini, not general. Rule: Compare → Then → Else over ≤128 ops (I12), no multi-key optimistic concurrency control across arbitrary keys, no lock manager. Tradeoff: cannot express general cross-key invariants a full OCC engine could. Operational implication: the apply path stays O(txn size), never O(keyspace). Violating it breaks: unbounded transaction scope reintroduces the coordination complexity (deadlock, livelock) this design explicitly avoids (ADR-09).

P6. gRPC is the wire; JSON HTTP is a generated gateway. Rule: every handler is implemented once, against the protobuf service; grpc-gateway generates the REST/JSON shim. Tradeoff: gateway consumers pay one extra hop. Operational implication: there is exactly one source of truth for request/response schemas. Violating it breaks: a hand-rolled parallel REST implementation drifts from the gRPC contract silently (ADR-04).

P7. Backups are incremental, restore is deterministic replay. Rule: a periodic full snapshot plus the WAL since that snapshot; restore = snapshot + WAL replay, nothing else. Tradeoff: restore time scales with WAL depth since the last snapshot. Operational implication: snapshot cadence is a tunable operational knob (--snapshot-count), not a fixed constant. Violating it breaks: ad hoc backup formats make disaster recovery untestable (I14).

P8. Mutual TLS + RBAC by default; plaintext is opt-in and loud. Rule: --client-cert-auth defaults true; disabling TLS requires an explicit flag and produces a periodic WARN (§25 Phase 13). Tradeoff: operators must manage a CA and certificate rotation (rotate-tls.md, §28). Operational implication: every peer and client handshake is auditable. Violating it breaks: silent plaintext deployment is invisible until an incident (T-1, §26).

P9. kvctl is the operator primitive. Rule: every administrative action (member add/remove, snapshot, restore, auth, compaction, defrag) has a kvctl subcommand emitting a documented JSON schema under --write-out=json. Tradeoff: CLI surface must be versioned alongside the API. Operational implication: every runbook (§28) is expressible as a kvctl script. Violating it breaks: web-dashboard-only administration is unscriptable and fails the 3 a.m. test.

P10. The storage backend is pluggable behind a narrow interface. Rule: backend.Backend (§11.6) is the only contract the MVCC apply layer depends on; bbolt is the locked default, pebble and the rank-67 B-Tree engine are build-tag alternates. Tradeoff: the interface must stay narrow enough that alternates are actually swappable, which caps how backend-specific an optimization can be. Operational implication: a backend swap is a build-tag change, not a rewrite. Violating it breaks: backend-specific assumptions leak into the apply layer and lock the project to one engine (ADR-05).

P11. Consensus is rented, not owned. Rule: this project consumes exactly five traits (StateMachine, LogStorage, StableStore, Snapshotter, Transport) from rank #39 Raft-Consensus; any change to the boundary requires paired ADRs in both repositories. Tradeoff: this project cannot unilaterally optimize across the seam. Operational implication: the seam is documented once (docs/cross-project/raft-trait-surface.md) and mirrored, never duplicated with drift. Violating it breaks: an un-paired change on either side desynchronizes the two projects' assumptions about apply ordering (I1) or transport guarantees.

P12. Every resource has a hard bound. Rule: txn ops, watchers, leases, tokens, in-flight proposals, and concurrent streams (§4) are all capped and rejected with typed errors past the cap. Tradeoff: legitimate high-scale clients must shard load across bounds rather than assume infinite headroom. Operational implication: every cap is a Prometheus gauge with a corresponding alert (§28). Violating it breaks: unbounded growth in any one resource degrades every other tenant of the same node (I12).

P13. Observability is emitted at the point of decision. Rule: every state transition (apply, propose, watch notify, lease expire, membership change) emits its metric/event inline, not reconstructed from logs after the fact. Tradeoff: instrumentation is written once per code path, adding a small but constant overhead. Operational implication: every N.10 (Operational Notes) names the exact metric emitted at that step. Violating it breaks: post-incident forensics degrade to log archaeology instead of metric replay (§27).

P14. Idempotency by construction. Rule: every client-facing mutation carries (client_id, sequence); the apply layer deduplicates via a bounded per-client window (I13). Tradeoff: the apply layer carries a small amount of extra state per active client. Operational implication: proposer retries after ambiguous failures (leader step-down mid-proposal) are safe by default. Violating it breaks: a naive retry after a timeout can silently double-apply a write (Phase 4 pitfall, §16.6).

8. Domain / Data Model

8.1 The KV data model

A key is an opaque []byte; a value is an opaque []byte; every mutation is timestamped with a Revision{Main, Sub} (§11.1). A KeyValue record additionally carries CreateRevision (the revision at which the key first appeared in its current generation), ModRevision (the revision of the most recent write), Version (a per-generation write counter reset to 0 on delete), and an optional Lease attachment (§11.3).

8.2 MVCC generations

Each key's KeyIndex (§11.1) holds a list of generations; a generation begins at a Put on a previously-absent (or previously-tombstoned) key and ends at a Delete (recording a Tombstone revision). Historical reads at revision R resolve to the generation whose [Created, Tombstone) interval contains R, or "not found" if no generation covers it or R predates the compaction floor (I7).

8.3 Wire format

All request/response/event/txn messages are proto3 (RFC: Protocol Buffers Language Guide, §5); every message reserves field numbers for forward compatibility (this project's schema-evolution policy is stated fully in §29 Compatibility & Versioning). The five top-level services are KV, Watch, Lease, Cluster, Auth (api/proto/kv/v1/*.proto), plus the internal RaftBridgeService (api/proto/raftbridge/v1/raftbridge.proto).

8.4 Storage record layout (bbolt)

Bucket key: keys are 16-byte big-endian (revision_main uint64, revision_sub uint64) tuples so byte-order iteration is revision order; values are the serialized KeyValue. Bucket meta: singleton keys finishedCompactRev, consistentIndex, clusterID. Bucket lease: LeaseID → Lease plus a lease-key bucket mapping LeaseID → [keys] for O(lease size) revocation (I5). Big-endian keys are chosen so bbolt's natural byte-order iteration is also revision order — no secondary sort step.

8.5 State machine (ApplyEnvelope dispatch)

One proto oneof routes every committed Raft entry to exactly one handler:

Envelope variant Handler Effect Invariant touched
Put mvcc.Apply.ApplyPut new revision, new/updated generation, watch notify I1, I4, I9

8.6 Worked example — Put with lease then Get at revision

Client issues Put(key="/svc/a", value="10.0.0.5:9090", lease=77). Leader proposes; on commit at Main=42, ApplyPut writes (42,0) → KeyValue{Key:"/svc/a", Value:"10.0.0.5:9090", CreateRevision:42, ModRevision:42, Version:1, Lease:77} and attaches the key to lease 77's index. A subsequent Range(key="/svc/a", Revision=42) resolves via the key index to generation covering 42, returns the record above. A Range at Revision=41 (before the key existed) returns not-found.

8.7 Malformed-input example

RangeRequest{Key: "/svc/a", RangeEnd: "/svc/"} — RangeEnd lexically precedes Key, which the domain model defines as empty range, not an error (etcd-compatible semantics); the handler must special-case RangeEnd < Key as "return zero rows", not propagate a negative-length slice. A PutRequest{IgnoreValue: true, IgnoreLease: true} (refresh nothing) is rejected at validation with INVALID_ARGUMENT before it ever reaches the proposer.

8.8 Failure-path example

A Txn proposal commits on a 3-node cluster, but the client's connection drops before the response is delivered (leader received the RPC, proposed, committed, but the response frame never reaches the client). The client retries with the same (client_id, sequence) (I13); the apply layer recognizes the duplicate and returns the cached ApplyResult without re-executing Then/Else a second time — critical for txns with side-effecting compares (e.g., a counter increment) where naive re-application would double-count.

Snapshot capture must not block the apply path — backend.Snapshot() uses bbolt's own MVCC-style read transaction, isolated from the writer (Petrov ch. 2–7, §5). Rate-limit snapshot transfer (shared token bucket with §17.7) to protect foreground throughput.

18.8 Edge Cases

A snapshot requested while a membership change is in flight — deferred until the change completes (I10 interaction). A restore pointed at a truncated/corrupted snapshot file — must fail closed with SnapshotVerifyFailed, never partially restore. Concurrent kvctl snapshot save calls — the second observes the first's in-progress capture and either queues or rejects with a typed error, never double-captures.

18.9 Failure Analysis

A crash mid-restore leaves a partially-initialized data directory — detection is a sentinel file (restore.in-progress) checked at startup; recovery is deleting the partial directory and retrying restore from the same snapshot (idempotent by design, since restore only reads).

18.10 Operational Notes

Metrics: cluster.snapshot.start{index,term}, cluster.snapshot.done{index,term,bytes}, snapshot_verify_fail_total (I14), backup_retention_pruned_total. Runbooks: take-snapshot.md, restore-from-snapshot.md target this phase's exact kvctl verbs.

19. Phase 7 — Leases

19.1 Objectives

Add TTL-bound keys (P4, ADR-08) — the foundation for service discovery and leader election, following etcd's lease model over Consul's session/health-check alternative (§5, §34).

19.2 Detailed Implementation Steps

Implement lease.Manager (§11.3): Grant(ttl) → LeaseID, Attach(id, key), Revoke(id), KeepAlive(id) — all writes flow through Raft (P4, I5). Implement the leader-only expiry-scan goroutine (internal/api/lease/timer.go): a min-heap (expiryQ) keyed by deadline, ticking at 100 ms (§4), proposing LeaseRevoke for expired leases — never mutating lease state locally, always via proposal (MM4: leases are distributed timers with consensus-anchored truth). Implement the bidirectional LeaseKeepAlive gRPC stream: client keeps a lease alive with periodic pings; the leader resets the TTL deadline on each. Implement the lease-key bucket (§8.4) for O(lease size) revocation: on revoke, the apply layer deletes every attached key in the same Raft proposal (I5, I6). Implement crash semantics: a client crash silently expires the lease at TTL; a leader crash hands the expiry-scan responsibility to the new leader on its first Apply (the map itself is follower-replicated, only the scanning goroutine is leader-gated).

19.3 Deliverable

examples/leader-election/ and examples/service-registry/ — both built on Compare → Then → Else (Phase 8 dependency, forward-declared here) plus a lease — demonstrating the primitive end-to-end.

19.4 Acceptance Criteria

A lease with TTL=5s expires and deletes its attached keys within 5.2 s of the last keep-alive (fixtures/lease/expiry_timing.json, 100 ms scan granularity + margin). A leader-crash test asserts zero lease leakage: after killing the leader mid-TTL, the new leader's expiry scan picks up every lease and expires it correctly, verified against the pre-crash lease set. Active-lease count is capped at 100,000 (§4); a request past the cap is rejected with LeaseTooMany, not silently queued.

19.6 Pitfalls

Implementing the lease manager as leader-local-only state — leaks every lease on leader change; the Manager's map must be follower-replicated even though the scan goroutine is leader-gated (P4). Tuning TTLs too aggressively against network jitter causes spurious expiry — document tuning advice in the operator guide. Granting many short-TTL leases is a scan-loop performance footgun — the expiry queue has a hard cap (LeaseTooMany) rather than degrading silently.

19.7 Performance Concerns

The expiry-scan tick (100 ms) touches only the heap's due items, not the full lease set — must stay O(due count), not O(total leases), to hold at 100,000 active leases (§4). LeaseKeepAlive streams share the same concurrent-stream budget as watches (§4 cap); document the interaction.

19.8 Edge Cases

A LeaseGrant requested with ttl=0 — reject (InvalidArgument), never interpret as "no expiry." A key attached to a lease that is later attached to a different lease via a second Put — detaches from the first (§8.6 semantics), verified explicitly. A LeaseRevoke racing a LeaseGrant reusing the same freshly-freed LeaseID — IDs are never reused (monotonic allocator), eliminating the race by construction.

19.9 Failure Analysis

A stuck expiry-scan goroutine (deadlock or panic) silently stops all TTL enforcement — detection via a lease_expiry_scan_last_tick_seconds staleness gauge alerted past 3× the tick interval; recovery is restarting the leader's expiry loop (supervised goroutine with panic-recover-relaunch).

19.10 Operational Notes

20. Phase 8 — Mini-Transactions

20.1 Objectives

Add the Compare → Then → Else transaction (P5, ADR-09) bounded to ≤128 ops (§4, I12) — the compare-and-swap primitive every downstream coordination pattern depends on.

20.2 Detailed Implementation Steps

Implement TxnRequest/Compare evaluation (§11.4, §8.5): comparison targets version, create_revision, mod_revision, value, lease; operators EQUAL, GREATER, LESS, NOT_EQUAL (Bernstein & Goodman's MVCC/2PL taxonomy informs the comparison-then-branch shape, §5). Evaluate all comparisons against the revision current at apply time; dispatch the Then branch if all hold, else Else — both are lists of Put/Delete/Get/nested Txn (nesting depth capped at 8, per §4). Wrap the entire txn as a single ApplyEnvelope / single Raft proposal (I6) — this is the atomicity contract; do not decompose into per-op proposals. Implement read-your-writes within one txn via sub-revision ordering (§8.1: Sub increments within one txn's writeset). Implement the max_txn_ops bound (128, §4, I12) rejecting oversized txns with a typed error before proposing.

20.3 Deliverable

A counter example (optimistic concurrency via a version compare) and a leader-election example (if create_revision==0 then put-with-lease else get-leader) — both under examples/.

20.4 Acceptance Criteria

A read-your-writes test within a single txn (fixtures/txn/read_your_writes.json) confirms a later op in the same Then branch observes an earlier op's write. An atomicity-under-crash test confirms no partial application: killing the leader mid-apply and replaying from the Raft log yields either the full Then branch or none of it, never a subset (fixtures/txn/atomic_crash_recovery.json). A txn exceeding 128 ops is rejected pre-proposal with TxnTooLarge (I12).

20.6 Pitfalls

Forgetting to wrap the txn in a single Raft proposal — silently breaks atomicity (I6); this is the single most consequential mistake in this phase. Allowing arbitrarily deep nesting — eats apply-path budget disproportionately; cap at 8 (§4). Mishandling comparison against a non-existent key — must compare against the zero value of every target field, not error out or skip the comparison.

20.7 Performance Concerns

Txn evaluation is O(compare count) plus O(op count) inside the single apply call — bounded by the 128-op cap (§4) so worst-case apply latency stays predictable; profile this path explicitly since it shares the apply goroutine with every other envelope type (I1 single-writer).

20.8 Edge Cases

A Then/Else branch containing a nested Txn whose own comparisons reference a key modified earlier in the same outer txn — must resolve against the sub-revision-ordered intermediate state (read-your-writes), not the pre-txn state. A comparison on lease target against a key with no lease attached — compares against LeaseID(0). Two clients racing the same CAS — exactly one succeeds, the loser observes the post-CAS version and can retry (standard optimistic-concurrency shape, no special-casing needed beyond correct version comparison).

20.9 Failure Analysis

A bug that mis-wraps a txn as multiple proposals would surface as I6's partial-apply assertion firing (§7) — this is deliberately a hard-crash detection, not a soft-logged warning, because partial txn application is a correctness violation with no safe automatic recovery; manual audit of the affected keys' revision history is the forensic path.

20.10 Operational Notes

Metrics: kv.txn{compare_count,then_count,else_count,succeeded}, txn_partial_apply_total (I6, should be permanently zero), resource_limit_rejected_total{resource="txn_ops"} (I12). Full (non-mini) cross-key OCC remains explicitly deferred (PhaseDeferred("§20"), registered §39) — un-defer trigger is a downstream consumer needing invariants this bounded model cannot express.

28. Operational Readiness

Metrics. Prometheus is the metrics sink (ADR-16); every metric named in I1–I14's Telemetry column and every phase's N.10 is exported. High-cardinality event counters (kv.put, watch.event, lease.grant, etc., §11 Appendix-style event list folded here) are exported via OpenTelemetry and mapped to Prometheus for aggregation.

Tracing. OpenTelemetry spans wrap every request-pipeline stage (§13.2): id assignment → authn → authz → route → handler → response. Span attributes include request_id, client_id, method.

Structured logging. One JSON line per request at INFO (request_id, method, duration_ms, code); WARN for irreversible operations (kvctl compact, insecure-mode ticks, T1); audit events (auth.login, auth.deny, membership changes) at a dedicated audit sink, never comingled with debug logs.

Dashboards. The embedded read-only dashboard (§22, ADR-18) covers topology/leader/watchers/ leases/per-node metrics; a separate Grafana dashboard (importable JSON under docs/performance/) covers the full M-series targets (§32) for on-call use.

Alerting philosophy. Alert on symptom metrics tied directly to an invariant or failure class (§7, §27), not on raw resource counters alone — e.g., alert on resource_limit_rejected_total rate crossing a threshold (client-visible impact), not merely on the underlying resource gauge approaching its cap (which may be healthy steady-state behavior).

SLOs. 99.9% of linearizable reads complete within the p99 target (M2, §32) over a rolling 28-day window (Beyer et al. ch. 4, §5); error budget policy: exceeding budget freezes non-essential membership/config changes until burn rate recovers.

Incident response. Every FM-1..FM-12 (§27) row doubles as an incident playbook entry; the on-call runbook index (docs/runbooks/) cross-references failure class → runbook.

Named runbooks (§10): bring-up-cluster.md, add-member.md, remove-member.md, replace-failed-member.md, promote-learner.md, rotate-tls.md, rotate-rbac.md, take-snapshot.md, restore-from-snapshot.md, compact-history.md, diagnose-watch-lag.md, tune-throughput.md.

Backup/restore. Governed by P7/ADR-14 (§18); RPO=0 for quorum-acknowledged writes, RPO bounded by snapshot interval for the periodic path (§4).

Deployment topology. One Raft group, 3/5/7 homogeneous nodes, docker-compose (dev) or a Kubernetes StatefulSet (production, assumed by the operator guide, out of build scope per §1).

Canary/rolling-upgrade/rollback. Rolling upgrade: one node at a time, waiting for the replaced node to rejoin and catch up (I10 gates concurrent changes) before proceeding; rollback is the same procedure in reverse, gated by the Compatibility & Versioning policy (§29).

29. Compatibility & Versioning

Wire compatibility. Every proto3 message reserves field numbers (§8.3); adding a field is non-breaking, removing or renumbering one is a major-version change. Until v1.0, every message carries a reserved block for unknown future fields.

Storage compatibility. The bbolt bucket layout (§8.4) is versioned via the meta bucket's schema-version key; a minor storage-layout change ships with an automatic migration on startup, a major change requires an explicit kvctl migration command and a documented downtime window.

API stability. Each service is namespaced by major version (kv.v1.KV); breaking changes require a new major-version path (kv.v2.KV) and a deprecation cycle (minimum one minor release overlap) documented in the operator guide.

Migration. Schema and storage migrations are forward-only; there is no supported downgrade path across a major storage-layout version — the documented recovery is restore-from-snapshot taken before the upgrade (§18, P7).

Deprecation policy. A deprecated API or kvctl subcommand emits a WARN-level log for a full minor-version cycle before removal; CHANGELOG.md (§10) records every deprecation with its removal version.

SemVer policy. Patch: bug fixes, no wire/storage change. Minor: additive wire fields, new kvctl subcommands, no breaking change. Major: any breaking wire, storage, or API change.

Rolling-upgrade guarantees. A cluster running a mix of N and N+1 (same major version) must interoperate for the duration of a rolling upgrade; this is validated by a dedicated fixtures/cluster/mixed_version_rolling_upgrade.json conformance fixture (§24) exercising every RPC against a mixed-version 5-node cluster.

30. Testing & Verification Strategy

Unit tests. Per-package, colocated with source (internal/mvcc/*_test.go, etc.); cover every signature in §11 at the boundary level.

Integration tests. make integration (introduced Phase 1, §13.4) exercises the full request-pipeline against a real (single- or multi-node) cluster.

Property-based tests. MVCC revision monotonicity (I1) and key-index/backend consistency (I9) are checked via property tests generating random write/delete/compact sequences and asserting the invariant holds after every step, not just at fixed checkpoints.

Differential testing. Where behavior mirrors etcd (P1 alignment decisions, §5), differential fixtures compare this store's response shape against etcd's documented semantics for the same request (e.g., RangeEnd < Key behavior, §8.7) — without importing or running etcd's code (§5 pitfall), only comparing against its published API semantics.

Fuzzing. fuzz/kv_fuzz_test.go (ADR-22) against every protobuf message type; the 30-day continuous corpus run is validated in Phase 13 (§25.4).

Chaos / fault injection. The Jepsen-style harness borrowed from rank-39's raft-jepsen (§25.2), run against the transfer workload (§25.4).

Deterministic replay. The invariant-debugging simulator (§7, end of table) drives a single-process multi-node cluster with a controllable clock/network and replays failures byte-for-byte from a recorded seed.

Soak testing. A 72-hour continuous-load soak (mixed KV/watch/lease/txn traffic at 50% of M1 throughput) run before every major release, watching for slow memory growth (steady-state heap budget, §4) or FD leaks.

Conformance. §24's ~200-fixture suite is the single source of protocol-correctness truth, CI-gating on every PR.

Performance-regression gating. Once M-series numbers stabilize post-Phase-11 (§23.9), bench. yml becomes gating: any M-series regression >10% release-over-release blocks the release.

Every invariant (§7) and every phase's N.5 fixtures feed this strategy; no invariant exists without at least one property test or conformance fixture exercising it.

32. Performance Engineering

Benchmarking/profiling methodology. cmd/kvbench (§23.2) is the single benchmark driver; pprof --alloc_space, pprof --mutex, and syscall sampling are run against the M1 workload each release and archived in benchmarks/profiles/.

Allocation analysis. The single-writer apply path (I1) is profiled specifically for per-op allocation count; KeyValue and ApplyEnvelope construction are pooled where profiling shows measurable GC pressure at the M1 throughput target.

Lock contention. Hub.mu (§11.3) and Node.pending's mutex (§11.5) are the two highest-risk contention points identified by design (both guard cross-goroutine shared state on the hot path); profiled explicitly each release.

Cache/NUMA analysis. Single-NUMA-node assumption (§4) is validated by pinning a benchmark run to one socket and confirming no measurable improvement from explicit cross-socket avoidance — revisit only past the M1 ceiling (§33).

Syscall analysis. fsync frequency (one per committed BatchTx, §11.6) is the dominant syscall cost at the M1 target; batching multiple client proposals into fewer Raft log entries (§16.7) directly reduces this.

Tail-latency analysis. p99.9 (beyond the M-series' p99 targets) is tracked specifically for GC-pause and compaction-cycle correlation — a compaction cycle (§14) running concurrently with peak load is the primary known p99.9 outlier source, documented in tune-throughput.md.

33. Scalability Analysis

What stays constant. Per-request RBAC evaluation cost (O(role × permission count), §21.7); per-event watch-hub dispatch cost (O(1) amortized via the interval tree, §15.7) — both independent of total keyspace size.

What grows, and the Big-O. Key-index size: O(live keys), bounded by the §4 backend-size cap. Cold-start rebuild time: O(keys in backend) (I9, §14.7) — this is the first bottleneck encountered past the single-Raft-group design's practical ceiling, since rebuild time grows linearly with keyspace while the §4 cold-start budget (3 s) is fixed. Compaction cycle duration: O(revisions between compaction points) (§14). Snapshot size and transfer time: O(backend size) (M6, M8).

Named bottlenecks in order (single-Raft-group ceiling):

  1. Apply-path single-writer throughput (I1) — every write serializes through one goroutine; this is the hard ceiling on M1 before any sharding.
  2. Leader network fan-out — a single leader's outbound replication bandwidth to N−1 followers caps cluster size before it caps per-key throughput.
  3. Cold-start rebuild time (I9) — grows with keyspace, eventually exceeding the M9 budget.
  4. bbolt write amplification — copy-on-write page churn grows with write rate past ADR-05's assumed regime.

Horizontal scaling. Not supported within one Raft group beyond the above ceilings; the lever is multi-Raft sharding by key range (deferred, PhaseDeferred("§33"), registered §39; embodied by TiKV/CockroachDB, §34, §38 AA-1).

Vertical scaling. Faster NVMe reduces fsync latency (directly improves M1); more CPU cores help only up to the single-writer apply-path ceiling (bottleneck 1) — beyond that, vertical scaling has diminishing returns, which is precisely why sharding (not bigger machines) is the documented lever past the ceiling.

Sharding/partitioning (the lever beyond the ceiling). Multiple independent Raft groups, each owning a contiguous key range, sharing transport and disk — TiKV's raftstore and CockroachDB's pkg/kv/kvserver/ are the reference implementations (§5); deferred from v1 scope deliberately (§1, §38 AA-1) because it multiplies operational complexity (per-range leader placement, cross-shard txn semantics beyond the mini-txn model, ADR-09) beyond what Phase-0 through Phase-13 need to prove the core design.

Coordination overhead. Every membership change (I10) and every snapshot transfer (§18.7) competes with foreground client traffic for leader bandwidth — rate-limited via the shared token bucket (§17.7, §18.7) to bound this overhead explicitly rather than let it grow unbounded.

The practical ceiling and the levers beyond it. The practical ceiling for this design, as built, is the M1 throughput number (§32) on a single Raft group at the §4 backend-size cap; the lever beyond it is multi-Raft sharding (deferred, §38 AA-1) or, for read-heavy workloads specifically, read-only learner replicas (deferred, PhaseDeferred("§17")).

34. Mental Models & First Principles

MM1. A replicated KV store is a log with a deterministic reducer. The Raft log is the source of truth; mvcc.Apply.Apply is the fold function. Predicts: any two nodes that applied the same log prefix must hold identical state, with no exceptions. Bug class without it: engineers "helpfully" add non-deterministic behavior (wall-clock reads, random tie-breaks) inside Apply, causing irreproducible per-node divergence that no amount of retry logic fixes. Applied in Phase 4 (§16), I1.

MM2. MVCC turns time into a first-class index dimension. A revision is not a version number bolted onto a mutable record — it is the primary key's second dimension. Predicts: any read API that does not accept an explicit revision is incomplete for this domain. Bug class without it: "current value only" thinking leaks into watch/historical-read design and silently drops the audit trail Kubernetes-style controllers depend on. Applied in Phase 2 (§14), §8.

MM3. A watch is a materialized diff stream, not a poll. The hub pushes; it never waits to be asked. Predicts: backpressure is mandatory the moment any consumer can be slower than the producer, which is always eventually true. Bug class without it: an unbounded per-watcher buffer that appears fine in testing and OOMs the server under one slow production consumer. Applied in Phase 3 (§15), I4.

MM4. Leases are distributed timers with consensus-anchored truth, not client-side timers. Expiry is a decision, made once, by whichever node currently holds the authority to decide (the leader), over replicated state. Predicts: a lease implementation that lives only on the leader leaks state on leader change; one that lives only on the client can split-brain under partition. Bug class without it: "just use a local time.AfterFunc" reappears every time a new engineer touches this subsystem. Applied in Phase 7 (§19), I5, P4.

MM5. Linearizability is a read-your-own-commit contract enforced by fencing, not by clock sync. ReadIndex fences a read against a confirmed commit point; it does not require synchronized clocks (contrast with Spanner's TrueTime, §5, §38 AA-2). Predicts: any read-latency optimization that skips the fencing step (a "fast read") reintroduces staleness under partition. Bug class without it: engineers assume "the leader is always right about now" and build a clock-based shortcut that breaks I3 exactly when the network is unreliable — precisely when correctness matters most. Applied in Phase 4 (§16), I3, T1/FM-3.

MM6. A transaction is a single proposal, not a sequence of operations. Atomicity is a property of the proposal boundary, not of application-level bookkeeping. Predicts: any implementation that proposes a txn's ops individually and reconciles afterward has already lost atomicity. Bug class without it: "we'll just retry the failed sub-op" logic that silently produces partial application under a crash. Applied in Phase 8 (§20), I6.

MM7. Backpressure is a queue with an explicit eviction policy, not the absence of a queue. Every bounded channel needs a defined behavior at capacity (drop, block, or evict-and-signal) — "we'll just make the buffer big enough" is not a policy, it is a deferred incident. Predicts: any unbounded buffer in the design is a future OOM, regardless of how unlikely overflow "feels" today. Bug class without it: memory growth that only manifests after days of slow-consumer accumulation, invisible in short test runs. Applied in Phase 3 (§15), I4, I12, P12.

MM8. The storage backend is a durability oracle; the apply layer is a correctness oracle. These are different responsibilities deliberately kept behind a narrow interface (backend.Backend, §11.6) — the backend promises "what I told you I wrote, survives a crash"; the apply layer promises "what I told you happened, happened exactly once, in this order." Predicts: conflating the two (e.g., letting the apply layer assume backend-internal transaction semantics it hasn't contracted for) breaks backend swappability (P10). Bug class without it: a backend-specific optimization leaks into mvcc.Apply, silently locking the project to one storage engine despite ADR-05's stated alternates. Applied in Phase 2 (§14), P10, ADR-05.

36. Back-of-Envelope Capacity Model

Every number below derives from §4's System Constraints table; formula shown for each.

C1. Peak write bandwidth (leader → followers). M1 throughput (10,000 ops/s) × 256-byte payload × (N−1) followers in a 5-node cluster = 10,000 × 256 B × 4 = 10.24 MB/s replication bandwidth at steady state — well under a 1 Gbps (125 MB/s) link, confirming the M8 snapshot-bandwidth budget (§4) is the actual constraint, not steady-state replication.

C2. Steady-state key count at the backend size cap. §4's 8 GiB default --quota-backend-bytes ÷ average record size. Assuming a 256-byte value + ~64-byte KeyValue overhead (key, revision metadata) = 320 bytes/record: 8 GiB ÷ 320 B ≈ 26.8M live records before the default quota is hit — the number that drives the ADR-05 "switch to pebble/LSM past this regime" trigger (§9).

C3. Key-index memory footprint at C2's key count. Assuming ~96 bytes per in-memory KeyIndex btree node entry (key pointer + revision list overhead, §11.1): 26.8M × 96 B ≈ 2.57 GiB — consistent with, but not exceeding, the §4 512 MiB steady-state heap target only because that target (M5) is measured at the M1 throughput benchmark's dataset size, not at the full 8 GiB quota; operators approaching C2's key count must budget heap separately, documented in tune-throughput.md.

C4. Write amplification ceiling before an LSM backend wins (ADR-05). bbolt's copy-on-write page churn scales with page size (default 4 KiB) × dirty-page count per commit. At M1's 10,000 commits/s with 256-byte payloads (well under one page), the amplification factor stays near 1 page/commit = 40 MB/s of page churn at steady state — comfortably under NVMe write bandwidth (typically ≥500 MB/s), which is exactly why bbolt is viable at M1 and why the ADR-05 rejected-alternative column names ">50k writes/s sustained" as the regime where pebble/LSM wins (§9): 5× M1 pushes page churn to ~200 MB/s, eroding the margin.

C5. Concurrent-stream FD budget. §4's 1,024 max concurrent gRPC streams + bbolt's 1 mmap FD + peer-transport connections (N−1 = 4 in a 5-node cluster, each ~2 FDs for bidirectional streams) = 1,024 + 1 + 8 = 1,033 FDs, comfortably under the §4 4,096 FD budget, leaving headroom for OS and library overhead.

C6. Snapshot transfer bandwidth requirement (M8). 1 GiB ÷ 60 s target = 17.9 MB/s required throughput — well under a 1 Gbps link's 125 MB/s capacity, meaning the M8 target is dominated by disk-read and serialization overhead on the sending side, not network bandwidth; this is the justification for rate-limiting snapshot transfer (§18.7) rather than treating the network as the bottleneck.

C7. Cold-start rebuild time budget vs. key count (M9 vs. C2). M9's 3-second cold-start budget (no snapshot) ÷ a target rebuild rate: to rebuild C2's 26.8M keys within 3 s requires scanning ≈8.9M keys/s — this is the number that makes clear the M9 budget assumes a much smaller live dataset in practice (the §4 M9 number is validated at the Phase-2 baseline dataset size, §14.4, not at the full C2 quota), and is the quantitative reason large-dataset cold starts are documented as taking longer than 3 s in the operator guide.

C8. Lease-manager memory footprint at the 100,000-lease cap (§4). Each Lease entry (§11.3): ID (8B) + TTL+Granted+LastTouch (24B) + a slice header for Keys (24B) + average 2 attached keys × 24B pointer/len overhead ≈ 104 bytes/lease × 100,000 = 10.4 MB — negligible against the M5 512 MiB heap budget, confirming the lease cap is set for operational sanity (I12), not memory pressure.

C9. Watcher outbox memory ceiling at the 50,000-watcher cap (§4). Each watcher's bounded outbox (§15.2, capacity 1,000 events per I4/§15.4) × an average Event size (~350 bytes: KeyValue + type

  • optional PrevKv) = 1,000 × 350 B = 350 KB/watcher worst case (fully saturated outbox) × 50,000 watchers = 17.5 GB worst case — this is why overflow triggers eager cancellation (WATCHER_ OVERFLOW, P3) rather than allowing outboxes to approach this worst case; steady-state (near-empty outboxes) is the assumed operating point, not the ceiling.

C10. Token-store memory footprint at the 10,000-token cap (§4). Each token entry: opaque token (32B) + username reference (≈16B) + TTL timestamp (8B) ≈ 56 bytes/token × 10,000 = 560 KB — negligible, confirming the cap (I12) is an operational-sanity bound, not a memory-pressure mitigation, matching the reasoning pattern of C8.

38. Alternative Architectures (Roads Not Taken)

AA-1. Sharded Multi-Raft (region-per-shard)

Show the original text diagram
+------+  +------+  +------+        Region A: Raft group {N1,N2,N3}
| N1   |  | N2   |  | N3   |        Region B: Raft group {N2,N3,N4}
| RgA  |  | RgA  |  | RgA  |        (regions overlap nodes; each node
| RgB  |  | RgB  |  |      |         hosts many independent Raft groups)
+------+  +------+  +------+
   Shared transport + shared per-node storage engine (RocksDB-style)
   Cross-shard txns require 2PC or a distributed-txn layer on top.

Regime where it wins: dataset size or write throughput exceeds one Raft group's ceiling (§33's apply-path single-writer bottleneck) — hundreds of GB to TB scale. Real embodying system: TiKV (raftstore), CockroachDB (pkg/kv/kvserver/), §5. Why rejected here: this project's target scale (§4: 8 GiB default quota, 10,000 ops/s) sits comfortably under a single Raft group's ceiling, and region-split/rebalancing machinery would multiply Phase 5–6 (§17–§18) complexity several-fold for no benefit at this scale — deferred (PhaseDeferred("§33")) rather than built, with a concrete un-defer trigger registered in §39.

AA-2. Globally-Distributed External Consistency (TrueTime-style)

Show the original text diagram
+---------+     +---------+     +---------+
| Region  |     | Region  |     | Region  |
| US      |<--->| EU      |<--->| APAC    |
+----+----+     +----+----+     +----+----+
     |  each region: local Paxos/Raft group,
     |  commit-wait bounded by TrueTime uncertainty interval
     +--------- cross-region 2PC coordinator ---------------+

Regime where it wins: multi-region deployments needing externally-consistent transactions without per-read coordination round trips across oceans. Real embodying system: Spanner (Corbett et al., OSDI 2012, §5). Why rejected here: requires a TrueTime-equivalent bounded-clock-uncertainty service this project has no mandate to build (§1 non-goals), and this store's coordination-substrate use case (service discovery, leader election, feature flags, §2) does not need cross-region external consistency — deferred (PhaseDeferred("§33"), geo-distributed placement) rather than built.

AA-3. Byzantine Fault Tolerant Replication

Show the original text diagram
Client --> [N1] [N2] [N3] [N4]   (N >= 3f+1 for f Byzantine faults)
              \   |   |   /
               PBFT-style 3-phase agreement (pre-prepare/prepare/commit)
               with cryptographic message authentication per node

Regime where it wins: untrusted or multi-tenant-hostile deployment models where a compromised node must not be able to violate safety, not just liveness. Real embodying system: PBFT (Castro & Liskov) and its descendants used in permissioned-blockchain KV stores. Why rejected here: this project's deployment model (§1) assumes trusted operator-controlled infrastructure — the threat model (§26 T4) explicitly documents Byzantine nodes as out of scope; adding BFT would roughly triple the message complexity per commit (3 phases + signatures vs. Raft's single round trip) for a threat this deployment model does not need to tolerate — deferred (PhaseDeferred("§38")).

AA-4. Multi-Paxos with Flexible Quorums (no distinguished log-replication leader per se)

Show the original text diagram
Proposer --> Acceptors {A1..A5} --> Learners
   any node can propose; overlapping-but-flexible read/write quorums
   (Howard et al., Flexible Paxos, OPODIS 2016, §5) replace Raft's
   fixed-majority quorum requirement

Regime where it wins: workloads wanting to trade write-quorum size against read-quorum size independently (e.g., read-heavy clusters accepting larger write quorums for smaller/faster read quorums). Real embodying system: classic Multi-Paxos deployments (historically, Google's Chubby; theoretically, Lamport's "Part-Time Parliament", §5) and Flexible Paxos-based systems. Why rejected here: Raft's understandability and its natural fit with the rank-39 sibling project's existing implementation (P11, ADR-02) outweigh Flexible Paxos's quorum-tuning flexibility, which this project's read/write ratio (dominated by linearizable reads via ReadIndex, not raw quorum reads) does not need — Raft's fixed-majority model is simpler to reason about for the operators this store targets (§1).

40. Glossary

  • Apply. The act of feeding a committed Raft log entry into the MVCC apply layer (§8.5, I1).
  • ApplyEnvelope. The proto3 oneof wrapper carrying one committed operation (Put/Delete/Txn/ LeaseGrant/LeaseRevoke/ConfigChange) to the state machine (§8.5).
  • bbolt. The default Go-native, mmap'd, copy-on-write B+Tree storage backend (ADR-05, §11.6).
  • Backend. The narrow, pluggable persistence interface the MVCC apply layer depends on (§11.6, P10).
  • Cluster id. A 64-bit identifier minted once at bootstrap and never changed thereafter (I8).
  • Compaction. Removing revisions older than a watermark, gated by active watchers' fence (§14, I7).
  • Compare → Then → Else. The mini-transaction shape: evaluate comparisons, execute one of two branches atomically in a single Raft proposal (§8.5, ADR-09, I6).
  • Conformance suite. The ~200-fixture ephemeral-cluster wire-protocol verification runner (§24).
  • Consensus. The agreement protocol (Raft, rank #39) guaranteeing all nodes apply the same log in the same order (I1, I2).
  • CRC32C. The checksum algorithm used in snapshot trailers to detect corruption (§8.4, I14).
  • Cross-project trait surface. The five-trait (StateMachine, LogStorage, StableStore, Snapshotter, Transport) locked boundary with the rank-39 Raft library (§11.7, P11).
  • Deferred feature. A capability explicitly out of this blueprint's build scope, registered with an anchor, building phase, and un-defer trigger (§39).
  • Election. The process by which Raft nodes agree on a new leader after the previous one becomes unreachable (I2).
  • Expiry scan. The leader-only goroutine that proposes LeaseRevoke for TTL-expired leases (§19.2, MM4).
  • Fencing (read fencing). Confirming a read against a specific confirmed commit index before serving it, the mechanism underlying linearizable reads (I3, MM5).
  • Generation. A KeyIndex sub-list spanning one create-to-tombstone lifecycle of a key (§8.2, §11.1).
  • gRPC-gateway. The generated reverse-proxy translating JSON HTTP requests into gRPC calls (P6, ADR-04).
  • History store. The bbolt key bucket holding (revision, KeyValue) pairs (§8.4).
  • Joint consensus. Raft's two-phase membership-change protocol ensuring safety during reconfiguration (§17.2, I10).
  • Key index. The in-memory btree tracking each key's generations and revisions (§8.2, §11.1, I9).
  • Learner. A non-voting cluster member replicating the log but not counted toward quorum, used during member add before promotion (§17.2).
  • Lease. A TTL'd, consensus-anchored handle to which keys can be attached for service-discovery semantics (§11.3, ADR-08, MM4).
  • Linearizable read. A read guaranteed to reflect every write committed before the read began (I3, P1).
  • Mini-transaction. This project's bounded transaction model (Compare/Then/Else, ≤128 ops), contrasted with general OCC (P5, ADR-09).
  • MVCC. Multi-version concurrency control — every mutation is a new, immutable, revision-stamped record rather than an in-place update (P2, §8, MM2).
  • Proposer. The raftnode.Node component that wraps client operations into Raft proposals and correlates results back to callers (§11.5, §16).
  • ReadIndex. The Raft mechanism confirming a read is fenced against the latest committed index without appending a new log entry (I3, MM5).
  • RBAC. Role-based access control mapping roles to (key_prefix, permission) grants (§21.2, ADR-11).
  • Revision. A (Main, Sub) monotonic logical clock stamping every mutation (§11.1, I1, MM2).
  • Serializable read. A read that may observe a stale local snapshot but is internally consistent, skipping ReadIndex confirmation for lower latency (P1, §4).
  • Single-writer discipline. The rule that all mutation to shared apply-layer state flows through exactly one goroutine, eliminating an entire class of races (I1, MM1, MM8).
  • Snapshot. A consistent point-in-time capture of the backend and lease-manager state, used for restore and for catching up lagging followers (§18, I14).
  • State machine. The StateMachine trait implementation (StateMachineAdapter) the Raft library calls into on every commit (§11.5, §11.7).
  • Tombstone. The revision at which a key's generation ends (a Delete), distinct from the key simply never having existed (§8.2).
  • Token store. The replicated, TTL-bounded store of authentication tokens (§21.2, ADR-12, I12).
  • Watch. A long-lived, server-filtered, backpressured gRPC stream of key-range change events (§11.3, §15, I4, MM3).
  • Watch hub. The single per-server component dispatching committed events to registered watchers (§11.3, P3, MM3).
  • WAL. The write-ahead log (owned by the rank-39 Raft library's LogStorage/StableStore) that incremental backups replay from since the last snapshot (§18.2, P7).
