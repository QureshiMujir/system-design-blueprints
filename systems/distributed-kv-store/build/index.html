Objectives

Deliverable

A buildable, lintable, containerizable repo skeleton: docker-compose up brings up a 3-node cluster of Phase-0 kvd processes that each return the PhaseDeferred sentinel on every RPC, proving the gRPC/HTTP/TLS wiring is live before any domain logic exists.

Acceptance

make test exits 0 (Phase-0 sanity tests only, ≥5 test cases). make lint exits 0 with zero golangci-lint findings. make proto regenerates all five service stubs with zero diff on a second run (idempotent codegen). All 5 .github/workflows/*.yml pipelines are green on first push. Fixture fixtures/phase0/bootstrap.json (§12.5) passes.

⬜ Phase 1 — Single-Node KV Server Skeleton §13

Objectives

Stand up the gRPC + HTTP-gateway server with a single-node, no-Raft, no-MVCC in-memory backend, to pin the request pipeline and wire format (P6) before the apply layer lands.

Deliverable

A single-node kvd binary serving kvctl put k v, kvctl get k, and kvctl get --prefix k against the in-memory map, over both gRPC and the JSON gateway.

Acceptance

make integration exercises every Phase-1 endpoint end-to-end and exits 0 (≥12 test cases across Get/Put/Delete/Range). p99 latency for Put on the in-memory map ≤ 1 ms (sanity bound, not the final target — M2/M3 apply from Phase 4 onward). The Prometheus dashboard renders QPS, p50/p99 latency, and error rate with non-zero data after a 60-second load-test run.

Fixture Purpose Expected Output
fixtures/kv/put_get_roundtrip.json basic Put then Get value matches
fixtures/kv/range_prefix.json prefix range scan all matching keys, sorted by key
fixtures/kv/malformed_range_end.json RangeEnd < Key (§8.7) zero rows, not an error
fixtures/kv/delete_then_get.json Delete then Get not-found
Pitfalls

Using interface{}/any keys in the in-memory store instead of []byte — string keys mishandle null bytes, which the wire format explicitly permits (§8.1). Returning generic codes.Internal for every application error instead of a typed code per failure mode now — retrofitting typed errors after clients depend on the untyped ones is a breaking change (§29). Skipping the HTTP gateway to save time — browsers and curl-based operators are first-class per P6.

⬜ Phase 2 — MVCC Apply Layer §14

Objectives

Replace the in-memory map with the real MVCC engine (P2, §8): revisioned writes, historical reads, and compaction — still single-node, no Raft. This is the same code that later phases wire behind the Raft StateMachine.

Deliverable

A single-node server serving revisioned reads/writes against bbolt: kvctl get --rev=N k returns the value at revision N; kvctl compact N removes revisions below N.

Acceptance

make bench-mvcc reports ≥5,000 ops/s sustained on commodity NVMe as the Phase-2 baseline (pre-Raft; M1's 10,000 target is a Phase-11 cluster number). Key-index rebuild from a 1M-key backend completes in ≤ 3 s (matches the §4 cold-start bound). A cold-start-then-read test (fixtures/mvcc/cold_start_ rebuild.json) returns identical results pre- and post-restart for 100 random keys at 10 random revisions each.

Fixtures
Fixture Purpose Expected Output
fixtures/mvcc/revision_monotonic.json 10k sequential writes Main strictly increasing, no gaps (I1)
fixtures/mvcc/historical_read.json read at a past revision matches the value at that revision, not current
fixtures/mvcc/cold_start_rebuild.json restart, rebuild key index reads match pre-restart values (I9)
fixtures/mvcc/compaction_below_watermark.json compact then read a compacted revision COMPACTED typed error
Pitfalls

Letting the key index drift from the backend — always rebuild from the backend on cold start (I9), never trust a persisted-but-possibly-stale index. Skipping the Version field — clients depend on it for compare-and-swap in Phase 8 (§20). Racing the compactor against in-flight reads — the compactor must use a dedicated ReadTx snapshot, never the apply path's BatchTx.

⬜ Phase 3 — Watches §15

Objectives

Add long-lived watch streams (P3, ADR-07) with server-side range filtering and backpressure, still single-node.

Deliverable

A single-node server where kvctl watch /prefix/ emits events on every matching change, with demonstrated backpressure cancellation and historical resume.

Acceptance

M4 target from Phase 11 is validated early here at single-node scale: p95 event-commit-to-delivery ≤ 50 ms under 1,000 concurrent watchers and 1,000 writes/s. A slow-consumer test (fixtures/watch/backpressure_overflow.json) asserts the watcher — not the server — is cancelled within 2 s of outbox saturation (outbox depth 1,000, per I12). A resume test replays ≥100 historical events correctly ordered (I4).

fixtures/watch/put_delete_events.json basic event delivery PUT then DELETE events, in order
fixtures/watch/backpressure_overflow.json slow consumer watcher cancelled with WATCHER_OVERFLOW, server unaffected
fixtures/watch/resume_from_old_revision.json resume mid-history historical events delivered in revision order
fixtures/watch/watch_too_old.json resume before compaction floor WATCH_TOO_OLD typed error

Pitfalls

Holding Hub.mu while sending on a watcher's channel — use tryEnqueue's non-blocking select instead (P3). Leaking a watcher's goroutine on cancellation — each watcher owns exactly one goroutine; cancellation must close the outbox and the goroutine must exit observably (verify via goroutine-count assertion in tests). Letting a WATCH_TOO_OLD client silently lose events — the SDK (pkg/sdk/go/watch.go) must surface this and trigger an automatic reseed.

⬜ Phase 4 — Raft Integration (Cross-Project Seam) §16

Objectives

Wire the single-node MVCC apply layer to the rank #39 Raft-Consensus library across the five-trait boundary (§11.7, P11, ADR-02), turning the store into a real replicated cluster.

Deliverable

A 3-node cluster (via docker-compose up) that elects a leader, replicates writes, and survives a single node kill without losing committed data.

Acceptance

make integration covers: linearizable read after partition heal succeeds within 200 ms of heal (M7); a write proposed during a minority partition is rejected with NotLeader or times out, never silently succeeds; a write retried with the same (client_id, sequence) after an ambiguous timeout is applied exactly once (I13, fixtures/raft/idempotent_retry.json). The cross-project trait-surface doc (docs/cross-project/raft-trait-surface.md) is locked and matches §11.7 exactly.

Fixtures
Fixture Purpose Expected Output
fixtures/raft/leader_election.json 3-node bring-up exactly one leader elected within 1 s
fixtures/raft/partition_minority_write.json write to minority side rejected or times out, no silent success
fixtures/raft/idempotent_retry.json duplicate (client_id, seq) after timeout applied exactly once (I13)
fixtures/raft/readindex_linearizable.json linearizable read across leader change never observes a stale value
Pitfalls

A proposal can commit and apply without the proposer ever observing the result (proposer crashed mid-wait) — the client must reissue with the same (client_id, sequence); the apply layer dedupes (I13, P14). Assuming Apply runs on the same goroutine as Propose — it does not; the pending map is shared mutable state and must be locked (§11.5). Assuming the leader cannot step down between accepting and applying a proposal — it can; the proposer must surface NotLeader and retry against the new leader. Skipping mTLS for peer transport once Phase 4 lands — the default config must refuse non-TLS peers from this phase forward (I11).

⬜ Phase 5 — Cluster Bootstrap & Membership Changes §17

Objectives

Make the cluster operationally manageable: bootstrap modes, member add/remove/promote, and joint-consensus-backed reconfiguration (I10).

Deliverable

A 3-to-5-to-3 membership lifecycle demonstrated end-to-end via kvctl member add/promote/remove against a live cluster with zero committed-entry loss.

Acceptance

Grow 3→5: both new learners catch up (apply lag → 0) within 30 s on a 1 GiB dataset, then promote succeeds for both (fixtures/cluster/grow_3_to_5.json). Shrink 5→3: two member remove calls succeed, cluster continues serving at 3 (fixtures/cluster/shrink_5_to_3.json). A member transfer-leader completes and the new leader serves writes within 4× the heartbeat interval (200 ms default, M7).

Fixtures
Fixture Purpose Expected Output
fixtures/cluster/grow_3_to_5.json add two learners, promote both 5 voters, no entry loss
fixtures/cluster/shrink_5_to_3.json remove two voters 3 voters, quorum intact
fixtures/cluster/promote_lagging_learner.json promote before catch-up rejected with LearnerNotCaughtUp
fixtures/cluster/concurrent_membership_change.json two config changes in flight second rejected (I10)
fixtures/cluster/cluster_id_mismatch.json join with wrong cluster id rejected (I8)
Pitfalls

Allowing membership changes during an in-flight snapshot delivery to a learner — the rank-39 library rejects this; surface the rejection as a friendly typed error, not a raw library panic. Allowing an operator to demote the last remaining voter — refuse with a typed error (LastVoterProtected). A removed node that keeps running can serve stale reads to confused clients — the server must shut itself down on observing its own MEMBER_REMOVED event; the runbook documents the expected sequence.

⬜ Phase 6 — Snapshots & Backups §18

Objectives

Make the cluster recoverable: Raft-driven and operator-driven snapshots, incremental backups, and deterministic restore (P7, I14).

Deliverable

A snapshot/restore round trip on a 1 GiB dataset and a multi-node restore that reforms a working 3-node cluster from one snapshot.

Acceptance

M6 target: restore from a 1 GiB snapshot reaches serving state in ≤ 15 s. M8 target: a 1 GiB snapshot streams to a lagging follower in ≤ 60 s on a 1 Gbps link. fixtures/snapshot/round_trip. json verifies byte-for-byte key/value/revision equivalence between pre-snapshot and post-restore state across 10,000 keys. A backup-retention test confirms exactly N retained snapshots per the configured policy, never N+1.

Fixtures
Fixture Purpose Expected Output
fixtures/snapshot/round_trip.json snapshot then restore identical keys/values/revisions
fixtures/snapshot/multi_node_restore.json 3 fresh nodes from one snapshot cluster forms, serves at snapshot revision
fixtures/snapshot/retention_prune.json backup retention policy exactly configured count retained
fixtures/snapshot/corrupted_trailer.json CRC32C mismatch on restore SnapshotVerifyFailed, fallback to prior snapshot (I14)
Pitfalls

Restoring while reusing the original cluster id — this can split-brain a recovered cluster against survivors of the original; always rewrite (I8). Placing backups inside the data directory — can fill the disk and corrupt the live backend; document the separation in the operator guide.

⬜ Phase 7 — Leases §19

Objectives

Add TTL-bound keys (P4, ADR-08) — the foundation for service discovery and leader election, following etcd's lease model over Consul's session/health-check alternative (§5, §34).

Deliverable

examples/leader-election/ and examples/service-registry/ — both built on Compare → Then → Else (Phase 8 dependency, forward-declared here) plus a lease — demonstrating the primitive end-to-end.

Acceptance

A lease with TTL=5s expires and deletes its attached keys within 5.2 s of the last keep-alive (fixtures/lease/expiry_timing.json, 100 ms scan granularity + margin). A leader-crash test asserts zero lease leakage: after killing the leader mid-TTL, the new leader's expiry scan picks up every lease and expires it correctly, verified against the pre-crash lease set. Active-lease count is capped at 100,000 (§4); a request past the cap is rejected with LeaseTooMany, not silently queued.

Fixtures
Fixture Purpose Expected Output
fixtures/lease/expiry_timing.json TTL expiry without keep-alive keys deleted within 5.2 s
fixtures/lease/keepalive_extends.json keep-alive resets TTL lease survives past original TTL
fixtures/lease/leader_crash_no_leak.json kill leader mid-TTL new leader still expires correctly
fixtures/lease/lease_too_many.json exceed 100,000 active leases LeaseTooMany typed error
fixtures/lease/revoke_atomic_with_keys.json manual revoke attached keys removed in the same proposal (I5, I6)
Pitfalls

Implementing the lease manager as leader-local-only state — leaks every lease on leader change; the Manager's map must be follower-replicated even though the scan goroutine is leader-gated (P4). Tuning TTLs too aggressively against network jitter causes spurious expiry — document tuning advice in the operator guide. Granting many short-TTL leases is a scan-loop performance footgun — the expiry queue has a hard cap (LeaseTooMany) rather than degrading silently.

⬜ Phase 8 — Mini-Transactions §20

Objectives

Add the Compare → Then → Else transaction (P5, ADR-09) bounded to ≤128 ops (§4, I12) — the compare-and-swap primitive every downstream coordination pattern depends on.

Deliverable

A counter example (optimistic concurrency via a version compare) and a leader-election example (if create_revision==0 then put-with-lease else get-leader) — both under examples/.

Acceptance

A read-your-writes test within a single txn (fixtures/txn/read_your_writes.json) confirms a later op in the same Then branch observes an earlier op's write. An atomicity-under-crash test confirms no partial application: killing the leader mid-apply and replaying from the Raft log yields either the full Then branch or none of it, never a subset (fixtures/txn/atomic_crash_recovery.json). A txn exceeding 128 ops is rejected pre-proposal with TxnTooLarge (I12).

Fixtures
Fixture Purpose Expected Output
fixtures/txn/counter_cas.json version-compare CAS succeeds once, fails on retry with stale version
fixtures/txn/read_your_writes.json intra-txn visibility later op sees earlier op's write

Pitfalls

Forgetting to wrap the txn in a single Raft proposal — silently breaks atomicity (I6); this is the single most consequential mistake in this phase. Allowing arbitrarily deep nesting — eats apply-path budget disproportionately; cap at 8 (§4). Mishandling comparison against a non-existent key — must compare against the zero value of every target field, not error out or skip the comparison.

⬜ Phase 11 — Performance, Benchmarking & Tuning §23

Objectives

Calibrate and measure the cluster against the §4/§32 targets (M1–M10) under realistic load, and produce the tuning runbook operators need.

Deliverable

benchmarks/REPORT.md populated with a real run's hardware spec, configuration, and numbers, regenerated on every tagged release.

Acceptance

make bench reports a throughput number that is ≥ 50% of the M1 target (5,000 writes/s minimum) on commodity hardware in CI, and the full M1 target (10,000 writes/s) on the documented reference hardware profile recorded in REPORT.md. p99 linearizable read ≤ 10 ms (M2) and p99 serializable read ≤ 1 ms (M3) on the same reference profile. Election/write-resumption after a forced leader kill completes within 200 ms (M7) in ≥ 95% of 20 repeated trials.

Fixtures
Fixture Purpose Expected Output
fixtures/perf/throughput_m1.json sustained write load ≥5,000/s in CI, ≥10,000/s on reference hw
fixtures/perf/read_latency_m2_m3.json linearizable vs serializable read p99 ≤10ms / ≤1ms respectively
fixtures/perf/election_resumption_m7.json forced leader kill × 20 ≥95% resume within 200ms
Pitfalls

Trusting microbenchmarks over end-to-end "ops/s under load" — isolated function timings hide lock contention and GC pauses that only appear under concurrent load (Nygard, §5). Ignoring macOS's F_FULLFSYNC throughput penalty — document the tradeoff in the operator guide rather than letting dev-machine numbers mislead production expectations.

⬜ Phase 13 — Threat Hardening & Fault Injection §25

Objectives

Harden the cluster against the adversary classes in the Threat Model (§26) and validate linearizability under adversarial network/process conditions via Jepsen-style fault injection.

Deliverable

A documented, evidence-backed threat model (docs/threat-model/overview.md) covering every row of §26, plus a recorded 60-minute Jepsen-style run and a 30-day fuzz corpus run with zero unexpected panics.

Acceptance

A 60-minute Jepsen-style run against a 5-node cluster with random partitions and leader kills asserts linearizability of the transfer workload with zero violations (fixtures/jepsen/60min_transfer_ workload.json). The fuzz harness runs go-fuzz/testing.F against every protobuf message type for 30 days of cumulative fuzzing time without an unhandled panic (fixtures/fuzz/30day_corpus_report. json). The audit-log completeness check confirms 100% of admin actions/auth decisions/membership changes across the full conformance suite (§24) emit a corresponding audit event.

Fixtures
Fixture Purpose Expected Output
fixtures/jepsen/60min_transfer_workload.json partition + leader-kill chaos zero linearizability violations
fixtures/fuzz/30day_corpus_report.json sustained fuzzing zero unhandled panics
fixtures/security/fast_read_disabled_by_default.json attempt a non-ReadIndex read rejected unless explicitly enabled
fixtures/security/audit_log_completeness.json run full conformance suite 100% of admin/auth/membership actions logged
Pitfalls

Shipping a "fast read" optimization enabled by default — silently breaks linearizability under partition (I3); off by default is the only safe posture, and enabling it must require an explicit, loudly-logged flag. Long-lived watchers outliving their authentication context — accumulate silently unless the watcher's principal is re-checked on every event, not just at subscription (revisits §21.6 pitfall from the fault-injection angle). Operator footguns like running with --insecure in production going unnoticed — the server must log a WARN every 5 seconds while running insecure (T-1, §26). Do not import etcd source directly during this phase's threat-model research — read it, never copy it (§5 reference-implementation pitfall, restated here since this phase is where teams are most tempted to "just check how etcd did it").
