In one paragraph

A strongly consistent, replicated key-value store of the etcd/Consul kind, written in Go, that platform teams run as the coordination substrate for service discovery, leader election, feature flags and configuration (§1). It offers gRPC and JSON APIs, per-key revision history, watches, TTL leases, small Compare → Then → Else transactions, membership changes, snapshot and restore, mutual TLS with prefix-scoped RBAC, and an operator CLI (§1). Consensus is consumed, not built: log replication, leader election and ReadIndex come from the sibling Raft library across a five-trait seam, and this project owns the MVCC engine and every user-facing surface (§1, §11.7). Every write is linearizable; every read chooses linearizable or possibly-stale serializable — "there is no silent middle ground" (§4, P1).

The problem, concretely

The blueprint's own example is a service registering itself: a client writes the key /svc/a with the value 10.0.0.5:9090, attached to lease 77, so the entry belongs to that lease (§8.6). The same store backs service discovery, leader election, feature flags and configuration for other systems (§1). The naive versions of this each fail in a way the blueprint names. Serve a read from whichever copy is nearest, and a leader-election or lease-based client acts on a stale answer, because it assumes "read reflects last write" (P1); the blueprint's first lesson is that linearizability costs a round trip, and that choice governs behaviour under partition (§2). Keep the lease timer only on the client and it can split-brain under a partition; keep it only in the leader's memory and it leaks on a leader change (§34 MM4). Retry a timed-out transaction blindly and a counter increment is counted twice (§8.8, P14). Buffer change notifications without a limit and a buffer that looks fine in testing runs the server out of memory under one slow consumer (§34 MM3). The store's answer: a write is committed once a quorum acknowledges it (§4), every read states whether it must be current (§4, P1), retries are deduplicated (I13), and every resource has a hard cap (P12).

How it works, end to end

The blueprint's diagram stacks the server on top of the consensus library, with the state machine in between as the single concurrency boundary (§3), drawn here and coloured by role:

A write enters through the gRPC API or the generated JSON gateway (§3, P6) and passes the request pipeline (internal/server/pipeline.go): request-id assignment, authentication by mTLS CN or token, authorization against RBAC, then routing — writes and linearizable reads go to the leader, serializable reads are served locally (§3, §10). On the leader, the proposer (raftnode.Node) wraps the write in an ApplyEnvelope and calls the Raft library's propose API (§3). Once the entry commits, the library calls into the MVCC apply layer (internal/mvcc), which runs on a single apply goroutine: ApplyPut creates a new revision, updates the generation in the key index, and notifies the watcher hub (api/watch.Hub), where each watcher owns a bounded outbox and a dedicated goroutine (§3, §8.5, I1, I4). The proposer correlates the Apply callback back to the waiting caller through a per-proposal channel (§3, §16.2). A linearizable read is served only after ReadIndex confirmation in raftnode.Node; a serializable read skips that and may be stale (§3, I3, §4). The lease manager (api/lease.Manager) holds a follower-replicated map of leases; only the leader runs the expiry scan, and an expiry becomes a LeaseRevoke proposal that deletes the attached keys in one proposal (§3, §8.9, I5). Everything persists through the backend interface (internal/backend): bbolt is the locked default, pebble and the rank-67 B-Tree engine are build-tag alternates (§3, P10, ADR-05).

The core ideas

Time is the second dimension of the key (§8.1, §8.2, MM2)

Every mutation is stamped with a Revision{Main, Sub}; a KeyValue record also carries CreateRevision, ModRevision, a per-generation Version counter reset to 0 on delete, and an optional lease (§8.1). A key's key index holds generations: one begins at a Put on an absent or tombstoned key and ends at a Delete, which records a tombstone revision (§8.2). A read at revision R resolves to the generation whose [Created, Tombstone) interval contains R, or "not found" if none does or R predates the compaction floor (§8.2, I7). The worked example (§8.6):

Step What happens
Put(/svc/a, 10.0.0.5:9090, lease=77) commits at Main=42 (42,0) → {CreateRevision:42, ModRevision:42, Version:1, Lease:77}; key attached to lease 77
Range(/svc/a, Revision=42) the generation covering 42 is found; the record above is returned
Range(/svc/a, Revision=41) before the key existed: not found

The mental model: "a revision is not a version number bolted onto a mutable record — it is the primary key's second dimension" (§34 MM2). The storage layout follows it: bbolt keys are big-endian (revision_main, revision_sub) tuples, so byte order is revision order with no secondary sort (§8.4).

A log with a deterministic reducer (§8.5, MM1)

The Raft log is the source of truth and mvcc.Apply.Apply is the fold function (§34 MM1). One proto oneof routes every committed entry to exactly one handler (§8.5):

Envelope Handler Effect
Put mvcc.Apply.ApplyPut new revision, new/updated generation, watch notify
Delete mvcc.Apply.ApplyDelete tombstone revision, generation closed
Txn mvcc.Apply.ApplyTxn evaluate Compare, dispatch Then/Else atomically
LeaseGrant / LeaseRevoke lease.Manager.Grant / Revoke new lease / delete attached keys + lease, one proposal
ConfigChange raftnode joint-consensus callback membership table update

Any two nodes that applied the same log prefix must hold identical state; the bug this prevents is wall-clock reads or random tie-breaks inside Apply, which cause per-node divergence that no retry fixes (§34 MM1, I1).

Linearizable reads are fenced, not clock-synchronised (§4, I3, MM5)

ReadIndex fences a read against a confirmed commit point, without appending a log entry and without synchronised clocks — in contrast with Spanner's TrueTime (§34 MM5, §38 AA-2, §40). The price is in the constraints: linearizable reads are budgeted at p99 ≤ 10 ms because "ReadIndex round trip dominates", serializable reads at p99 ≤ 1 ms because there is "no consensus round trip" (§4, M2, M3). A "fast read" that skips the fence reintroduces staleness under partition, so it ships off by default and enabling it requires an explicit, loudly-logged flag (§34 MM5, §25.6, FM-3).

Watches are a diff stream with bounded outboxes (§15.2, I4, MM3, MM7)

Watchers register a key range and start revision against an interval tree; the apply layer calls Hub.Notify after every put, delete and transaction, and each watcher receives events in strict revision order with no gaps (§15.2, I4). Delivery is a non-blocking tryEnqueue into a bounded outbox, and overflow force-cancels the watcher with WATCHER_OVERFLOW (§15.2). The rule behind it: every bounded channel needs a defined behaviour at capacity, because "we'll just make the buffer big enough" is not a policy (§34 MM7). The capacity model shows the stakes: 1,000 events × ~350 B × 50,000 watchers = 17.5 GB worst case, which is why overflow cancels eagerly and near-empty outboxes are the assumed operating point (§36 C9). The acceptance test: the watcher, not the server, is cancelled within 2 s of outbox saturation (§15.4). A resume from a revision below the compaction floor returns WATCH_TOO_OLD and the client reseeds with a Range read (§15.2, I7).

Leases are consensus-anchored timers (§8.9, I5, MM4)

The lease lifecycle is a small state machine (§8.9):

  1. LeaseGrant(ttl) is replicated through Raft; the lease is Active and its TTL starts at commit.
  2. Each LeaseKeepAlive makes the leader reset the deadline, with no new revision.
  3. When the leader's expiry scan sees the deadline pass, the lease is Expiring and the leader proposes LeaseRevoke; when that commits, the lease is Revoked and its keys are deleted atomically. A lease id is never reused.

The scan is a min-heap keyed by deadline, ticking at 100 ms (§19.2). The map is follower-replicated even though only the leader scans, so a new leader picks up the expiry work on its first Apply (§19.2, §34 MM4). The acceptance test: a lease with TTL 5 s deletes its keys within 5.2 s of the last keep-alive (§19.4).

A transaction is one proposal (§8.5, I6, MM6)

A mini-transaction evaluates a Compare list, then runs either the Then or the Else branch, atomically, as one ApplyEnvelope — at most 128 operations (§4, §8.5, I6, ADR-09). "Atomicity is a property of the proposal boundary": proposing the operations one by one has already lost it (§34 MM6). Retries are safe because every client-facing mutation carries (client_id, sequence) (P14). The failure-path example (§8.8): a Txn commits on a 3-node cluster, the client's connection drops before the response arrives, the client retries with the same pair, and the apply layer returns the cached ApplyResult without re-running the branch — which matters for a counter increment that would otherwise be counted twice (I13).

The trade-offs — where engineers disagree

Implementation language: Go (ADR-01)

Chosen: Go 1.22+, for ecosystem fit with etcd and Consul, gRPC tooling, and a bbolt backend with no cgo (ADR-01). Rejected: Rust; Java (ADR-01). When the rejected choice is right: Rust wins when the whole stack, including the Raft library, is single-language and cgo-free is mandatory (ADR-01).

Consensus provider: the sibling Raft library across a trait seam (ADR-02)

Chosen: the rank-39 Raft-Consensus library (Rust) via the five-trait boundary of §11.7, for workspace coherence, with the seam itself a deliberate teaching goal (ADR-02). Rejected: etcd/raft; hashicorp/raft (both Go) (ADR-02). When the rejected choice is right: an in-Go Raft wins when there is no sibling Raft project to consume and the cgo/RPC boundary overhead is unacceptable (ADR-02).

Default backend: bbolt, not an LSM (ADR-05)

Chosen: bbolt, a memory-mapped B+Tree with no cgo, for crash-safety and because it is proven at etcd's scale (ADR-05). Rejected: pebble (LSM); badger (ADR-05). When the rejected choice is right: pebble/LSM wins once write amplification from bbolt's copy-on-write pages dominates at more than 50k writes/s sustained — the capacity model puts page churn at ~40 MB/s at M1's 10,000 commits/s and ~200 MB/s at 5× M1 (ADR-05, §36 C4).

Revision clock: a monotonic pair, not hybrid logical clocks (ADR-06)

Chosen: a monotonic (Main, Sub) pair, for etcd alignment and a simpler total order with no clock-skew reasoning (ADR-06). The ADR row calls the pair "64-bit", while the type in §11.1 declares Main uint64; Sub uint64 and §8.4 stores it as a 16-byte key — the blueprint gives both. Rejected: hybrid logical clocks (HLC) (ADR-06). When the rejected choice is right: HLC wins when cross-cluster causal ordering, not just single-cluster commit order, is required (ADR-06).

Watch transport: bidirectional gRPC streams (ADR-07)

Chosen: long-lived bidirectional gRPC streaming, with native backpressure via HTTP/2 flow control (ADR-07). Rejected: polling; WebSockets (ADR-07). When the rejected choice is right: WebSockets win when browser-only clients with no gRPC-Web infrastructure must be supported natively (ADR-07).

Leases as TTL handles, not health-checked sessions (ADR-08)

Chosen: TTL'd revocable handles anchored in consensus, for fewer moving parts and no external health-check plugin surface (ADR-08). Rejected: health-check-based sessions, Consul-style (ADR-08). When the rejected choice is right: sessions with health checks win when liveness must reflect application-level health, not just a timer (ADR-08).

Mini-transactions, not general multi-key OCC (ADR-09)

Chosen: Compare → Then → Else with at most 128 ops, for bounded apply-path complexity and no lock manager (ADR-09). Rejected: full multi-key OCC (ADR-09). When the rejected choice is right: when the workload needs arbitrary cross-key invariants, such as a SQL layer — explicitly out of scope (ADR-09, §1).

Roads not taken (§38)

Sharded multi-Raft, one Raft group per key range as in TiKV and CockroachDB, wins when dataset size or write throughput exceeds one Raft group's ceiling — hundreds of GB to TB. It is rejected because the 8 GiB default quota and 10,000 ops/s target sit under that ceiling, and region splitting would multiply Phase 5–6 complexity several-fold; it is deferred with an un-defer trigger in §39 (§38 AA-1, §4).

Globally distributed external consistency in Spanner's style wins for multi-region deployments needing externally consistent transactions without cross-ocean round trips per read. It is rejected because it needs a TrueTime-equivalent clock-uncertainty service this project has no mandate to build, and a coordination substrate does not need cross-region external consistency (§38 AA-2).

Byzantine fault tolerance wins in untrusted or hostile multi-tenant deployments where a compromised node must not violate safety. It is rejected because the deployment model assumes trusted infrastructure (§26 T4) and BFT would roughly triple the message complexity per commit (§38 AA-3).

Multi-Paxos with flexible quorums wins when a workload wants to trade write-quorum size against read-quorum size. It is rejected because Raft's understandability and the sibling library outweigh that flexibility, which a workload dominated by ReadIndex reads does not need (§38 AA-4).

What must never be false

  • I1 — the revision Main only moves forward across the cluster (the row words it as "strictly monotonic non-decreasing"); an assertion on every Apply call catches a regression.
  • I2 — at most one leader is active per Raft term; a term/leader mismatch check on Propose.
  • I3 — a linearizable read reflects every write committed before it began; a read-fencing check against the confirmed index.
  • I4 — watch events reach a watcher in strict revision order with no gaps; a per-watcher expected-next-revision counter.
  • I5 — a lease's keys are removed exactly when it is revoked, in the same proposal; a periodic lease-key index cross-check job.
  • I6 — all ops of a transaction's chosen branch commit atomically, or none do; a partial-apply assertion that should never fire.
  • I7 — compaction never removes a revision at or above any active watcher's fence; a compactor precondition check before each cycle.
  • I8 — the cluster id minted at bootstrap never changes; a cluster-id mismatch check on every join and request.
  • I9 — the in-memory key index always matches the backend's history store; a periodic background consistency scan.
  • I10 — at most one membership change is in flight; concurrent ChangeMembership calls are rejected.
  • I11 — once bootstrapped with mTLS, non-TLS peer connections are rejected at the handshake, with no fallback path.
  • I12 — every bounded resource (txn ops, leases, watchers, tokens, in-flight proposals, streams) rejects new work past its cap; the bound check returns a typed error before admission.
  • I13 — applying the same (client_id, sequence) twice returns the cached first result; a duplicate-sequence check on Apply.
  • I14 — a snapshot is a consistent point-in-time image of backend plus lease state, atomic with the last-applied index; checksum and index verification on restore.

What breaks in production

  • FM-1 — a revision goes backwards. A bug bypasses the single-writer path; the assertion in mvcc.Apply fires (the row lists these two in swapped columns), the node crashes and replays from the Raft log, and the code path that mutated rev outside Apply is audited.
  • FM-3 — stale linearizable reads. ReadIndex confirmation was skipped or a "fast read" left enabled; the read is rejected if the fencing check fails, the fast-read flag is disabled and the read path audited.
  • FM-4 — watch gaps or duplicates. Hub.Notify broke its ordering discipline; the per-watcher expected-next-revision counter mismatches, the watcher is cancelled and reseeded, and the bug is fixed with a regression fixture.
  • FM-5 — orphaned lease-attached keys. The lease-key index desynced from the revoke path; the periodic cross-check finds them and a reconciliation sweep deletes them.
  • FM-6 — partial transaction application. A txn was wrapped as several proposals instead of one; the partial-apply assertion fires, there is no auto-recovery, and the key-by-key revision history is audited by hand.
  • FM-7 — a watcher is served compacted data. The compactor removed a revision a live watcher still fenced; the precondition check defers the compaction cycle and the fence computation in Hub is audited.
  • FM-8 — split brain after a restore. The restored cluster reused the original cluster id; the mismatch check rejects the join and the cluster is rebuilt with a fresh id.
  • FM-11 — a plaintext peer connection is accepted. mTLS enforcement was bypassed after bootstrap; the signal is the absence of peer_tls_reject_total, and the response is to treat it as an active incident, patch the transport config and rotate every peer certificate.

Threats a reader should know (§26): T1 a silent plaintext downgrade when an operator runs --insecure in production, answered by mandatory mTLS after bootstrap and a loud periodic warning; T3 disk bit corruption, answered by CRC32C trailers on snapshots and bbolt's page checksums, with fallback to the prior snapshot plus WAL replay; T6 replayed requests, defeated by mTLS and term checks and absorbed by idempotent dedup; T7 floods of transactions, watchers, leases, tokens or streams, answered by hard per-resource caps; T8 a watcher whose authorization is revoked mid-stream, answered by re-checking authorization on every event.

How it compares

  • etcd is the closest sibling; this design deliberately mirrors its MVCC, lease and mini-transaction shape, because Kubernetes' sustained dependence on etcd is the strongest evidence that shape is production-sound (§35).
  • Consul differs on leases (sessions with health checks) and transactions (prepared queries); its model wins when liveness must reflect application health rather than a bare timer (§35).
  • TiKV shards from day one with multi-Raft over per-region groups; that wins at hundreds of GB per cluster and when horizontal write scaling is needed, which this design defers (§35, §38 AA-1).
  • FoundationDB offers full ACID distributed transactions in an unbundled layered architecture; it wins when the workload needs cross-key invariants a mini-transaction cannot express (§35, ADR-09).
  • ZooKeeper has no MVCC and no transactions, only versioned writes with ephemeral and sequential nodes; it wins when the consumer needs only coordination primitives such as leader election and locks (§35).

Questions to test yourself

  1. Why does a linearizable read cost a network round trip while a serializable read does not, and what specifically would break if that were reversed? — Hint: the read-latency rows in §4 and invariant I3.
  2. Why is the lease manager's map follower-replicated even though only the leader runs the expiry scan? What would leak if it were leader-local only? — Hint: §19, mental model MM4 and I5.
  3. Why does compaction need to consult the watch hub's fence before removing a revision, and what invariant would break without that check? — Hint: §14, §15 and I7.
  4. A client retries a Put after an ambiguous timeout. Walk through exactly how the system guarantees the retry does not double-apply, naming both the client-side and apply-side mechanism. — Hint: the §16.6 pitfall, I13 and P14.
  5. Why does restoring from a snapshot require rewriting the cluster id, and what specific failure mode does skipping that step create? — Hint: §18.6, I8 and FM-8.

If you only remember three things

The store is a replicated log with a deterministic reducer: every node that applied the same log prefix holds the same state, so nothing non-deterministic may run inside Apply. A revision is the key's second dimension, which is what makes history reads, watches and compaction coherent. Reads choose explicitly between paying the ReadIndex fence for linearizability and reading locally at the risk of staleness, and every resource — txn ops, watchers, leases, tokens, proposals, streams — has a hard cap with a typed rejection past it.

Words used here

  • Revision — the monotonic (Main, Sub) stamp on every mutation; the key's second dimension.
  • Generation — one create-to-tombstone lifetime of a key inside its key index.
  • Key index — the in-memory btree tracking each key's generations and revisions.
  • Apply envelope — the proto oneof wrapper carrying one committed operation to one handler.
  • ReadIndex — the Raft mechanism that fences a read against the latest committed index.
  • Linearizable vs serializable read — fenced and current, versus local and possibly stale.
  • Watch / watch hub — a long-lived stream of key-range change events, and the single per-server component that dispatches them.
  • Lease — a TTL'd, consensus-anchored handle; keys attached to it are deleted when it is revoked.
  • Mini-transaction — Compare → Then → Else, at most 128 operations, one proposal.
  • Joint consensus — Raft's two-phase membership-change protocol; one change in flight at a time.
  • Learner — a non-voting member that replicates the log and is promoted once it has caught up.
  • Compaction — removing old revisions, never at or above a live watcher's fence.
  • bbolt — the default memory-mapped copy-on-write B+Tree backend.
  • Cluster id — the id minted at bootstrap; a restored cluster must get a fresh one.
  • mTLS / RBAC — mutual TLS for identity, and roles mapped to (key_prefix, permission) grants.
