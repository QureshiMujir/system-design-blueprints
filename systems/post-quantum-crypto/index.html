In one paragraph

This design is a from-scratch Rust library with a small command-line tool. It implements two NIST standards meant to survive quantum computers: a way for two parties to agree on a shared secret (a key encapsulation mechanism, ML-KEM, FIPS 203) and a way to sign messages (a digital signature, ML-DSA, FIPS 204) (§1.1). Both do their arithmetic on polynomials with 256 terms and share one fast multiplier and one hashing core (§1.1). Its defining demand is exactness: outputs must match the official test vectors byte for byte, and any step that touches a secret must behave the same whatever the secret is (P2, P1). It ships as a library plus a CLI, with no daemon (§4.1).

The problem, concretely

Imagine a server that holds an ML-KEM private key and accepts ciphertexts from anyone. The obvious code decrypts, checks that the result is consistent, and returns an error if not (P3). The blueprint rules this out for three separate reasons, each with its own "what goes wrong" example.

First, an error is a signal. decaps must never return an error: it always returns a 32-byte secret, and for a tampered ciphertext that secret is a pseudo-random stand-in (P3, I4, §8.4). An error return, or even one early exit after the check, tells the sender whether the check passed (HQ-01). The blueprint calls that a break of chosen-ciphertext security (P3, §8.4).

Second, time is a signal. The blueprint's example is a single if on the comparison result inside decaps: it leaks one bit per query (P1). Hence no branch or memory index may depend on a secret, and the 32-byte ciphertext comparison costs a few extra nanoseconds that the design pays unconditionally (P1).

Third, "almost right" is wrong. The blueprint's example is a bit-packing loop that shifts by d instead of d-1. Public keys then decode to slightly different numbers, the re-encryption inside decaps never matches, and every ciphertext, including valid ones, gets the stand-in secret (P2). That is why byte-exact test vectors gate every merge (P2, I1).

How it works, end to end

Follow one key exchange through the blueprint's architecture diagram (§3.1), compressed here:

  pqc-cli (keygen | encaps | decaps | sign | verify | kat)
     |                                   |
  pqc-kem  (CPA PKE + Fujisaki-Okamoto)  pqc-sign (Fiat-Shamir with aborts)
     |                                   |
  pqc-sample   pqc-encode   <------>  pqc-sample   pqc-encode   norm/hint checks
     |                                   |
  pqc-ntt (NTT, pointwise multiply)   pqc-poly (ring add / sub / reduce)
     |
  pqc-hash (SHA3 + SHAKE: G, H, PRF, XOF)
     |
  pqc-ct (constant-time compare / select / zeroize)     pqc-kat (FIPS ACVP vectors)
  1. pqc-cli reads files, validates them, and calls the scheme crates; it holds no cryptography (§3.2).
  2. pqc-core holds the six parameter sets, the Zq number type and the shared error type (§1.2).
  3. pqc-kem encaps hashes a random message and the public-key hash with G to get a key and randomness, then encrypts the message with that randomness (§3.2, §8.4).
  4. pqc-sample turns seeds into polynomials: public matrix entries by rejection sampling, secret noise by a constant-time bit-counting sampler (§3.2, P7).
  5. pqc-ntt and pqc-poly do the polynomial products: the NTT is the multiplier and pqc-poly::schoolbook_mul is a slow checker used only in tests (§3.2, P5).
  6. pqc-encode squeezes polynomials into bytes with Compress/ByteEncode (§3.2).
  7. pqc-hash supplies G (SHA3-512), H (SHA3-256), PRF (SHAKE256) and XOF (SHAKE128) (§3.2, §8.7).
  8. pqc-kem decaps decrypts, re-encrypts, compares using pqc-ct, and returns the real key or the stand-in (§3.2, §8.4).
  9. pqc-sign runs keygen, a retry loop for signing, and verification, using the same lower crates (§3.2, §8.5).
  10. pqc-ct has no dependency on other pqc-* crates and all of them depend on it; pqc-kat drives both scheme crates through the official vectors and stops at the first mismatch (§3.2).

The core ideas

Polynomials as numbers, and the NTT as a shortcut (§8.6, P5)

Both schemes work in the ring of 256-coefficient polynomials where X^256 = -1, written R_q (§1.1, §8.6). Multiplying two such polynomials the school way takes about 65,536 coefficient multiplications; the number-theoretic transform (NTT), a Fourier transform over integers mod q, takes about 2,048, a ratio of roughly 32 (P5). In the transformed domain a product is just element-by-element multiplication (§8.6).

For ML-KEM, q = 3329 and the root is zeta = 17 (§8.6). The blueprint names its order two ways: §8.6 calls it a primitive 512th root of unity, while §3.2 says the table comes from a primitive 256th root; this explainer leaves that open (§8.6, §3.2). The forward transform is 7 layers of Cooley-Tukey butterflies on 256 numbers; the inverse is Gentleman-Sande, followed by multiplying by n^{-1} = 3303 (§8.6). The twiddle table is stored in bit-reversed order as Montgomery-encoded constants (§8.6, ADR-09). Every product follows four steps: transform the first input, transform the second, multiply pointwise, transform back (P5). The schoolbook_mul oracle checks this on 10,000 random pairs (P5, I5). A Domain tag, Normal or Ntt, marks which form a polynomial is in (§8.3).

Keeping numbers small: Montgomery and Barrett (§8.8)

Reducing a product mod q by division is expensive, and the side-channel audit allows no division on reviewed paths (MM-07, §4.1). Montgomery reduction replaces it with a multiply by a precomputed inverse and a shift (MM-07). Blueprint steps for q = 3329 with R = 2^16 (§8.8):

Step Operation Result range
input product a*b held in i64 [0, q²·R)
1 m = (a*b mod R) * q_inv mod R [0, R)
2 t = (a*b + m*q) >> 16 (-q, q)
3 add q if t < 0 [0, q)

Barrett reduction instead estimates the quotient with a precomputed constant (k = 80635 for q = 3329) and subtracts, leaving [0, 2q) and then one conditional subtract (§8.8). Values are stored as i32 with i64 intermediates, which holds both q = 3329 and q = 8380417 (ADR-08, §8.1). Invariant I8 says every value after reduction lies in [0, q) (§7).

ML-KEM: hiding a message behind noise (§8.4, §8.6, §8.10)

The security idea is Module-LWE: given a public matrix A and t = A*s + e where s and e are small random polynomials, t looks random, so s stays hidden (MM-01). Key generation expands A from a public seed rho, draws small s and e, and publishes rho with t (§8.4, §8.6). Encryption draws fresh small noise, computes u = A^T*r + e1 and v = t*r + e2 + (message bits), then compresses both (§8.6, §8.10). Compression is deliberately lossy: Compress(x, d) = round(x · 2^d / q) mod 2^d, with an error bound the standard fixes (§8.7, I9). The blueprint's worked ML-KEM-512 trace uses du = 10, dv = 4, eta1 = 3, eta2 = 2 (§8.10, §8.2). Its stated sizes there (u = 320 B, ciphertext = 448 B) disagree with the §8.2 table's 768-byte ML-KEM-512 ciphertext and with §8.7's 32·du·K rule for u; this explainer does not resolve that (§8.10, §8.2, §8.7).

Noise polynomials come from a centered binomial sampler: count one group of bits, subtract a second group, so every coefficient lies in [-eta, eta] (§8.8).

The Fujisaki-Okamoto transform: no failure you can see (§8.4, P3)

The encryption above is only CPA-secure, the weaker base level (Glossary: "CPA security"). The Fujisaki-Okamoto (FO) transform upgrades it to chosen-ciphertext safety: the encryptor's randomness is derived from the message through G, so a receiver can re-do the encryption and see whether the ciphertext was honest (MM-02, P3, §8.4). Three steps on the receiving side (P3):

  1. Decrypt to a message m', derive (K, r) = G(m', H(pk)), and re-encrypt to c'.
  2. Compare c and c' with the constant-time ct_eq.
  3. Return ct_select(K, PRF(z, c), eq): the real key if equal, else a pseudo-random value from a secret seed z kept in the private key. This is implicit rejection (§8.1, P3).

Honest input returns the same K the encryptor made; a tampered one returns PRF(z, c) with no timing difference, so the caller cannot tell success from failure (§8.4, I4).

ML-DSA: sign, check, and retry (§8.5, P4)

The response must not reveal the secret s1, so the signer hides it behind a random "mask" vector y (MM-03, §8.5). Fiat-Shamir with aborts is the loop (§8.5, P4):

  1. Pick fresh y; compute w = A*y and keep only its high bits w1.
  2. Hash tr, the message and w1 into a challenge seed; expand to a sparse polynomial c with exactly tau entries of ±1 (§8.1, §8.5).
  3. Compute z = y + c*s1 and test the bounds. Throw everything away and restart if ||z|| is too large, if the low bits of w - c*s2 are too large, if the c*t0 bound fails, or if the hint has more than omega set bits (§8.5).

Why retry? Only accepted z values are statistically independent of s1; y must come from a fresh stream each time or reuse correlates the outputs (P4). The verifier recomputes w1' using the hint h, small carry-correction bits that stand in for the secret low part, and accepts only if the challenge matches and z and h are within bounds (§8.5, Glossary: "Hint"). Rejection thresholds use constants from §8.2: beta = 78, 196, 120 for ML-DSA-44, -65, -87 and omega = 80, 55, 75 (§8.2).

Constant-time: separate public work from secret work (P1, P7, §8.11)

"Constant-time" means execution time and memory access pattern do not depend on secret values (I2). Where data is public the code may be variable-time: matrix A is built by rejection sampling that discards candidates 3329 or above, and the blueprint says this saves about 40% of keygen time (P7, §8.8). Where data is secret (noise, the mask y, the FO comparison) the code must not branch (P7, §8.11). P4 and §8.11 let the signing loop's iteration count vary, calling it not secret; T5 disagrees (P4, §8.11, T5). Secrets are wiped on drop with volatile writes plus a compiler fence (P8).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust 2021, for memory safety without a garbage collector and the zeroize/subtle libraries (§9). Rejected: C, C++, Go, Python, Zig. When the rejected choice is right: C, for embedded security-module targets with no Rust toolchain or where a certified C compiler is mandatory (§9).

Constant-time tools: the subtle crate (ADR-04)

Chosen: subtle (Choice, ConditionallySelectable), because it is audited and has compiler barriers (§9). Rejected: hand-rolled volatile reads, inline assembly. When the rejected choice is right: inline assembly, on deeply embedded targets where the compiler cannot be trusted to keep the barriers, or where a hardware-level proof is required (§9).

Hashing: write Keccak yourself (ADR-06)

Chosen: pqc-hash, a from-scratch Keccak-f[1600], for control over absorb/squeeze and byte-exact vector checks (§9). Rejected: the sha3 crate, openssl. When the rejected choice is right: the sha3 crate, when a production library has to audit one well-maintained dependency instead of owning a Keccak implementation and has limited crypto headcount (§9).

Number storage: i32 with i64 intermediates (ADR-08)

Chosen: i32 storage, i64 for products, so one type covers both moduli (§9). Rejected: u16, u32 or i64 throughout. When the rejected choice is right: u16, in a vectorised NTT (16 values per AVX2 register) built for ML-KEM only; it needs a separate ML-DSA path (§9).

Preventing domain mix-ups (ADR-10, P6)

Chosen: a Domain tag on Poly, with a runtime assert in debug builds and "type-level in release"; the tag costs 1 byte (§9). Rejected: a separate PolyNtt type, or no enforcement. When the rejected choice is right: a separate type, for older compilers with weak const-generics support or when a trusted wrapper enforces the discipline (§9). The blueprint is not consistent here. P6 and Phase 2's acceptance table want domain confusion to be a compile-time error at zero runtime cost; ADR-10 relies on a debug-build runtime assert and calls stable type-level support marginal; HQ-08 and MM-04 describe a 1-byte field "or" a const-generic tag (P6, Phase 2, ADR-10, HQ-08, MM-04).

Where randomness comes from (ADR-11)

Chosen: the caller passes an RNG, or a fixed seed for test vectors, so core crates are no_std and tests are reproducible (§9). Rejected: an OS RNG inside the core, getrandom. When the rejected choice is right: getrandom directly, for a higher-level library on WASM or a TEE where the caller cannot easily supply an RNG handle (§9). §4.1 names getrandom for the keygen RNG, and T7 says to delegate to the OS and never accept caller seeds in production, which cuts against this ADR (§4.1, T7, ADR-11).

Roads not taken

Hash-based signatures (SLH-DSA, Alt-1). Wins when even lattice hardness is doubted or regulation forbids lattices; rejected as primary because its signatures are far larger (7856 to 49856 bytes against 3309) and signing is far slower (Alternative Architectures, Alt-1).

Code-based encryption (Classic McEliece, Alt-2). Wins where a long security track record matters and key size does not; rejected because public keys of 261 KB to 1 MB do not fit TLS-sized budgets of at most 2 KB (Alternative Architectures, Alt-2, DF-10).

Ring-LWE without a module (Alt-3). Wins on very constrained devices where a matrix of polynomials is too much memory; rejected because FIPS 203 standardises Module-LWE (Alternative Architectures, Alt-3).

Isogeny-based schemes (Alt-4). Once offered the smallest keys; rejected because the SIKE scheme was broken in 2022 and including it would violate P12 (Alternative Architectures, Alt-4).

Deferred, not rejected. SIMD NTT (DF-03, DF-04), power-analysis masking (DF-05, wins under a physical-access threat model), formal constant-time proofs (DF-06), Falcon (DF-02), and hybrid TLS integration (DF-08) are held back with named re-evaluation triggers (Deferred Features Register).

What must never be false

  • I1: all outputs match FIPS 203/204 ACVP vectors byte for byte, for all six parameter sets. Noticed by pqc-kat in CI, which blocks merge; counters kat_pass_count, kat_fail_count (§7).
  • I2: timing and memory access on secret paths do not depend on secrets. Noticed by a dudect harness with threshold |t| < 4.5, plus ctgrind; metric timing_variance_histogram_ns (§7).
  • I3: decaps(sk, encaps(pk).ct) equals the encapsulated secret, except with negligible probability. Noticed by prop_kem_correctness; counter kem_decap_failure_count (§7).
  • I4: a bad ciphertext gives Ok(PRF(z, c)), never an error. Noticed by the one-bit-flip test over every ciphertext byte plus a timing-equality test; decaps_rejection_count (§7).
  • I5: inverse NTT undoes the forward NTT, and NTT multiplication equals schoolbook. Noticed by two property tests that must pass before any higher crate builds (§7).
  • I6: a signature from an honest key verifies. Noticed by prop_sign_verify; counter sign_verify_fail_count (§7).
  • I7: every output signature has ||z|| below gamma1 - beta and at most omega hint bits. Noticed by a debug assertion and a property check; sign_reject_loop_iterations_histogram (§7).
  • I8: every Zq after reduction is in [0, q) with no overflow. Noticed by debug assertions and prop_reduction_range (§7).
  • I9: lossless encodings round-trip and lossy compression stays within its error bound. Noticed by prop_encode_roundtrip (§7).
  • I10: malformed ciphertexts, signatures or keys return an error, never a panic or leak. Noticed by fuzzing; counter malformed_input_reject_count (§7).
  • I11: Debug/Display on secret types never prints raw bytes. Noticed by a unit test and a lint denying derived Debug; counter secret_debug_format_total (§7).
  • I12: a parameter-set mismatch returns Err(ParamMismatch). Noticed by a per-pairing unit test; counter param_mismatch_reject_total (§7).

What breaks in production

The blueprint's failure table has named classes rather than numbers, so each item below cites its class (Failure Modes & Recovery).

  • KAT mismatch. Symptom: an ACVP vector test fails with different bytes. Cause: an off-by-one in bit-packing, a wrong twiddle constant or a wrong reduction order. Detection: the KAT harness in CI, which logs the first diverging vector and byte offset. Recovery: no automatic recovery; halt the release and bisect by parameter set and phase (I1).
  • NTT identity failure. Symptom: inverse NTT does not undo the forward NTT, or NTT product differs from schoolbook. Cause: wrong root ordering or a missing normalisation factor. Detection: the Phase 3 property tests. Recovery: audit table generation and the 1/256 factor (I5).
  • Implicit rejection failure. Symptom: a tampered ciphertext returns the real secret. Cause: a non-constant-time comparison with an early exit, or a wrong z. Detection: the Phase 8 test that a tampered input must give PRF(z, c). Recovery: fix the FO path and rerun timing tests (I4, P3).
  • Signature verification false negative. Symptom: an honest signature is refused. Cause: wrong hint application or a high/low-bits split mismatch. Detection: the Phase 11 tests and vectors. Recovery: re-derive the helper functions from the standard (I6).
  • Constant-time violation. Symptom: timing variance correlates with a secret. Cause: a branch on a secret coefficient or on the FO comparison. Detection: dudect plus cargo careful. Recovery: replace the branch with ct_select, rewrite, retest (I2, P1).
  • Secret left in memory. Symptom: key bytes visible in freed memory under Valgrind or a sanitizer. Cause: missing zeroize on drop, or an early return before wiping. Detection: sanitizers in CI. Recovery: add the drop guard, audit return paths and rotate affected keys (P8).
  • Panic on malformed input. Symptom: a process crash from untrusted bytes. Cause: unchecked slice index or unwrap on parsed data. Detection: fuzzing. Recovery: add a bounds check at the parse site and redeploy (I10, P9).

Threats worth knowing (Threat Model): T1 malformed ciphertexts, answered by strict length checks before decoding (I10); T4 timing side channel on the FO comparison, answered by ct_eq with no early exit, enforced by a CI timing gate (I2, P1, P3); T7 weak randomness at key generation, answered by hard failure with no silent fallback; T11 a signing loop that runs too long, answered by a maximum iteration count and an alert above twice the expected mean; T13 reused ephemeral state, answered by drawing fresh m or y every call and persisting no ephemeral state. On the rejection-loop count the blueprint splits: T5 treats it as a timing leak of s1/s2, and P10's example says per-key retry counts point to high-norm keys, while P4 and §8.11 say the count is not secret. This explainer does not choose (T5, P10, P4, §8.11).

How it compares

  • liboqs (Open Quantum Safe). It covers many post-quantum families beyond ML-KEM and ML-DSA, links OpenSSL for hashing, and does not promise constant-time behaviour on every compiler. That is fine for research servers or proxies that need algorithm agility more than timing rigour (Comparative Architecture Table).
  • BoringSSL / Google deployment. It uses hand-audited assembly with timing regression tests, is not no_std, and is tied to the Chromium build. That fits high-traffic TLS where a validated module boundary is contractually required and embedded use is off the table (Comparative Architecture Table).
  • Cloudflare CIRCL (Go). It is portable Go with the NTT in plain Go, and documents that Go makes constant-time properties harder to verify. That suits a Go team that wants speed to deploy and has no local timing adversary (Comparative Architecture Table).
  • NIST reference implementations (pq-crystals, C). They are correctness-first with no external dependencies and are not constant-time on all platforms. They suit use as the oracle every other implementation must match, and as reading material (Comparative Architecture Table).

This blueprint's own column differs by being Rust with a no_std core, subtle barriers plus a statistical timing test, and checked-in vectors, at the cost of covering only ML-KEM and ML-DSA (Comparative Architecture Table, §1.1).

Questions to test yourself

  1. Why does FO decapsulation return Ok(PRF(z,c)) on a bad ciphertext rather than Err(InvalidCiphertext), and what is the exact attack if you return an error instead? — Hint: P3 and the failure-path sequence in §8.4.
  2. Can you reuse the masking vector y across two signing attempts? Why or why not? — Hint: P4's resampling requirement and MM-03.
  3. Why does pqc-ntt need both a Montgomery reduction AND a Barrett reduction? Can you use only one? — Hint: §8.8 and P5.
  4. What is the "hint" vector in ML-DSA, why is it needed, and what happens if MakeHint produces more than ω hints? — Hint: §8.5, verification sequence, and I7.
  5. What is the difference between a constant-time function and a constant-time implementation, and why does the difference matter for Rust on different targets? — Hint: P1 and §8.11.

If you only remember three things

Everything is polynomial arithmetic in one ring, made fast by the NTT and checked against a slow schoolbook oracle (P5, §8.6). The scheme hides its failures on purpose: decapsulation always returns a secret and signing retries silently, so nothing observable depends on the secret (P3, P4, I4). And exactness is the product: byte-identical to the FIPS vectors, constant-time on secret paths, with every secret wiped (P2, P1, P8).

Words used here

  • Ring R_q: polynomials with 256 coefficients mod q where X^256 = -1 (§1.1).
  • NTT: a transform that turns polynomial multiplication into element-wise multiplication (§8.6).
  • Module-LWE: the hard problem behind ML-KEM; recovering a small secret from a noisy matrix product (MM-01).
  • KEM: a public-key tool whose output is a shared secret plus a ciphertext, not an encrypted message (Glossary: "KEM").
  • Fujisaki-Okamoto transform: re-encrypt and compare on decapsulation to reach chosen-ciphertext safety (P3).
  • Implicit rejection: returning a pseudo-random value PRF(z, c) instead of an error (I4).
  • Fiat-Shamir with aborts: sign by masking with random y and retrying until the response is safe (P4).
  • Hint: carry-correction bits that let the verifier rebuild w1 without the secret low part (§8.5).
  • Montgomery / Barrett reduction: two ways to compute mod q without slow division (§8.8).
  • Constant-time: timing and memory access that do not depend on secret values (I2).
  • KAT / ACVP: known-answer tests from NIST that fix exact output bytes (I1).
