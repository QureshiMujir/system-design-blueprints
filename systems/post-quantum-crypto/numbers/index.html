Back-of-Envelope Capacity Model

All inputs taken from §4 System Constraints unless otherwise noted. Each number is derived step-by-step.

1. ML-KEM-768 public key size. Formula: |ek| = k·ρ·256·d_bits/8 + 32 bytes seed where k=3, d=12 bits (t vector), ρ=1 byte seed appended. Calculation: 3 polynomials × 256 coefficients × 12 bits / 8 = 3 × 384 = 1152 bytes, plus 32-byte seed = 1184 bytes (matches FIPS 203 sec. 2.4 Table 1).

2. ML-KEM-768 ciphertext size. Formula: |c| = k·du·256/8 + dv·256/8 where du=10, dv=4. Calculation: 3 × 10 × 256 / 8 = 960 bytes (u vector) + 4 × 256 / 8 = 128 bytes (v scalar) = 1088 bytes (matches FIPS 203 Table 1).

3. ML-DSA-65 signature size. Formula: |sig| = λ/4 + l·γ1·256·(1+ceil(log2(2γ1)))/8 + ceil(k·ω/8) + ω bytes. Simplified per FIPS 204 sec. 2.5: |sig| = 32 + l·(2γ1 bits) · 256/8 + (ω + k) bytes. Calculation: 32 + 5 × (2^20 × 256 / 8) + (55 + 6) bytes = 32 + 5 × 32768 + 61 = 32 + 163840 + 61 = 3309 bytes (matches FIPS 204 Table 1: 3309 bytes).

4. TLS 1.3 hybrid handshake bandwidth (X25519MLKEM768). Components: X25519 key share (32 B) + ML-KEM-768 ciphertext (1088 B) + ML-KEM-768 public key (1184 B). One-shot server→client data: ciphertext only (client already sent pk): 1088 + 32 = 1120 bytes. Total handshake key-exchange overhead vs. classical X25519: 1120 − 64 = +1056 bytes per handshake. At 10 000 TLS handshakes/s: additional bandwidth = 1056 × 10 000 = 10.56 MB/s additional key-exchange traffic.

5. Per-operation latency budget (ML-KEM-768 decaps, ARM Cortex-A72, single-core). From §4 System Constraints: target ≤ 500 µs decaps on Cortex-A72. NTT dominates at 45 % of decaps time → NTT budget: 0.45 × 500 µs = 225 µs. ML-KEM-768 decaps requires 2 forward NTTs and 1 inverse NTT for the re-encryption. Per-NTT budget: 225 µs / 3 = 75 µs → NTT must run in ≤ 75 µs on a 1.5 GHz Cortex-A72. At 1.5 GHz with ~8 cycles per butterfly: 128 NTT layers × 128 butterflies/layer × 8 cycles = 131072 cycles = 87 µs — within 20 % margin, requires single-cycle multiply (hardware multiplier present on A72).

6. Signing rejection-loop expected iterations (ML-DSA-65). Acceptance probability per iteration: p ≈ (1 − 2β/γ1)^{256L} where β=196, γ1=2^19=524288, L=5. 2β/γ1 = 392/524288 ≈ 0.000748; (1 − 0.000748)^1280 ≈ e^{−0.000748×1280} = e^{−0.958} ≈ 0.384. Expected iterations E[N] = 1/p ≈ 2.6 iterations per signature (FIPS 204 sec. 3.3 states expected ~2.5 iterations for ML-DSA-65 — consistent).

7. Memory footprint per ML-KEM-768 decapsulation (stack, no alloc). State during decaps: dk (2400 B) + m' (32 B) + (K, r) from G (64 B) + c' reconstruction (1088 B) + intermediate polys (3 × 256 × 4 B = 3072 B). Peak stack: 2400 + 32 + 64 + 1088 + 3072 ≈ 6656 bytes — fits within a 16 KB embedded stack.

8. NTT twiddle table size. Forward NTT for q=3329: 128 Montgomery-encoded zetas × 4 bytes each = 512 bytes (fits in L1 cache; 8 KB L1 on Cortex-A72). For q=8380417 (ML-DSA): 256 zetas × 4 bytes = 1024 bytes — also L1-resident.

9. ACVP KAT vector file size. Each ML-KEM vector: seed (48 B hex) + ek (1184 B hex) + dk (2400 B hex) + m (32 B) + c (1088 B) + K (32 B) ≈ 4784 B per vector. Standard ACVP test group: 100 vectors per parameter set × 3 KEM + 3 DSA sets = 600 total vectors. Total JSON size: 600 × 4784 B × 2 (hex encoding overhead) ≈ 5.7 MB of JSON files — negligible in CI.

10. Constant-time comparison cost. ct_eq_bytes for 32-byte shared secret: XOR 32 bytes, OR-reduce, mask — approximately 32 × 2 = 64 instructions. At 1.5 GHz: 64 / 1.5 × 10^9 ≈ 43 ns per comparison — adds 0.008 % overhead to a 500 µs decaps.

11. Signing key size (ML-DSA-65). From FIPS 204 Table 1: |sk| = 32 + 32 + 64 + 32(l+k)·eta_bits where eta=4, l=5, k=6. = 32 (ρ) + 32 (K) + 64 (tr) + 32×5×3 + 32×6×3 = 32 + 32 + 64 + 480 + 576 = 4032 bytes (matches FIPS 204: 4032 bytes).
