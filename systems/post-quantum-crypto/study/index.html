Hard Questions

Each question names the resolving § and requires synthesis of at least two sections to answer.

HQ-01. Why does FO decapsulation return Ok(PRF(z,c)) on a bad ciphertext rather than Err(InvalidCiphertext), and what is the exact attack if you return an error instead? Resolves §6 P3 + §8 (Phase 8). An error return tells an adversary whether their tampered ciphertext passed the re-encryption check; 256 binary oracle queries binary-search the 256-bit comparison to recover the shared secret K. PRF(z,c) is pseudorandom and unconditionally hides the oracle result.

HQ-02. FIPS 203 Appendix A specifies NTT zeta ordering as bit-reversed. What precisely does bit-reversal mean for a 128-element table, and what would happen if you used natural order? Resolves Phase 3 §3.2 + Phase 4 §4.2. Bit-reversal reorders the primitive 256th root's powers so each butterfly reads its twiddle from position bitrev(layer_index). Natural order would compute the correct product for layer 0 but produce wrong twiddles for all subsequent layers, causing the inverse NTT to fail to cancel the forward NTT; schoolbook-NTT output comparison (I5) would catch this in Phase 4.

HQ-03. Can you reuse the masking vector y across two signing attempts? Why or why not? Resolves §6 P4 + Phase 8 §8.2 (Pa-7). If y is reused across two accepted signatures (z1 = y + c1·s1, z2 = y + c2·s1), then z1 − z2 = (c1 − c2)·s1. Since c1 and c2 are known, this is a linear equation in s1; a lattice-reduction attack on the resulting short-vector instance recovers s1 from a small number of such pairs.

HQ-04. ML-KEM-512 targets "Category 1" (AES-128 equivalent). What does that mean concretely, and why does it NOT mean the key is 128 bits? Resolves §4 System Constraints + §6 P8 (Pa-1, Pa-2). Category 1 means the best known quantum attack requires at least as many quantum gates as exhaustive search on AES-128. The RLWE problem dimension (n=256, k=2) determines the concrete hardness; the shared secret is 32 bytes (256 bits) of output, but the security level is measured against the hardest known lattice attack (BKZ with quantum subroutines), not key size.

HQ-05. What is the decryption failure rate δ for ML-KEM-768, and why does it matter for long-term key pairs? Resolves §4 System Constraints + Threat Model (Pa-2). δ ≈ 2^{-164} for ML-KEM-768 (FIPS 203 sec. 3.3). For a key pair used in 10^9 encapsulations (CDN-scale), the probability of any failure is 10^9 × 2^{−164} ≈ 0 for practical purposes. A non-negligible δ would allow an attacker to submit ciphertexts crafted near the decryption boundary and use the failure signal as an oracle — the tight δ prevents this.

HQ-06. What exactly does "implicit rejection" mean, and how does it differ from "explicit rejection"? Resolves §6 P3 + Phase 7 §7.2 (S5). Implicit rejection: on FO mismatch, return PRF(z, c) (a pseudorandom value determined only by the stored z and the ciphertext, not by the message). Explicit rejection: return an error or a distinguished constant. Implicit is stronger because the adversary cannot determine from the output whether decapsulation succeeded; explicit leaks a binary bit per query.

HQ-07. Why does pqc-ntt need both a Montgomery reduction AND a Barrett reduction? Can you use only one? Resolves Phase 3 §3.2 + §6 P5. Montgomery reduction is optimized for the inner NTT butterfly loop (multiply by a precomputed constant — the Montgomery-encoded zeta); it avoids division but requires the input to be in Montgomery form. Barrett reduction is used for general one-off reductions of arbitrary products (e.g., after accumulating coefficients in an inner product). Using Montgomery everywhere would require entering/exiting Montgomery form for every non-NTT operation; using Barrett everywhere is slower in the NTT inner loop.

HQ-08. How does the Domain phantom tag eliminate an entire class of NTT correctness bugs, and what is the performance cost? Resolves ADR-10 + Phase 2 §2.2. The tag adds 1 byte to the Poly struct (or zero bytes if const-generic), but the primary benefit is that poly_add(a: Poly<Normal>, b: Poly<Ntt>) becomes a type error at compile time. The runtime cost is zero in release mode (the field is stripped or inlined); the debug-mode assert costs one conditional check per operation.

HQ-09. If you replace SHAKE128 with AES-256-CTR as the XOF for matrix A expansion, what changes and what breaks? Resolves §6 P6 + Phase 5 §5.2 (Pa-8). AES-256-CTR is a valid PRF but it is not a standardized ML-KEM XOF; FIPS 203 mandates SHAKE128 for expand_A. Switching breaks FIPS 203 ACVP KAT vectors immediately (byte-level mismatch). Additionally, AES hardware acceleration varies more across embedded targets than SHAKE; on constrained targets without AES-NI, CTR is slower than SHAKE.

HQ-10. The signing loop iterates until norm bounds pass. Can an adversary influence how many iterations occur, and does that leak anything? Resolves §6 P4 + Phase 8 §8.2 + Threat Model (T5). The number of iterations is a function of the random y draws and the challenge c, both derived from public values (message, seed). The iteration count is variable-time (ADR-11 allows variable-time loop count) because it leaks only statistical information about the public y/c relationship — it does not directly reveal s1. An adversary observing timing can count iterations but cannot invert the one-way function from iteration count to s1.

HQ-11. What is the "hint" vector in ML-DSA, why is it needed, and what happens if MakeHint produces more than ω hints? Resolves Phase 9 §9.2 + Phase 10 §10.2 (Pa-6). The hint vector h encodes carry-correction bits: the verifier has t1 (the high-order bits of t) but needs to reconstruct HighBits(w − c·s2 + c·t0, 2γ2). UseHint corrects for the rounding done during key generation. If popcount(h) > ω, the signature exceeds the hint budget — the signing loop discards this y sample and retries. Without this bound, an adversary could craft high-hint signatures that leak information about t0 or s2.

HQ-12. How does the KAT architecture ensure byte-exact FIPS 203/204 compliance rather than just functional correctness? Resolves Phase 13 §13.2 + §4 System Constraints (S7). Functional correctness (keygen → encaps → decaps → matching key) is necessary but not sufficient: the shared secret byte string must match the ACVP-specified expected output for a given 48-byte seed. pqc-kat feeds the seed into the same deterministic DRBG specified in ACVP, calls the API, and compares every output byte. A "functionally correct" but byte-incompatible implementation would interoperate with nothing in the PQC ecosystem.

HQ-13. Why does ML-DSA use a 48-byte (384-bit) signing key seed rather than a 32-byte seed? Resolves Phase 9 §9.2 + §6 P8. The seed expands via SHAKE-256 to (ρ, ρ', K), three 32-byte values: ρ for A expansion, ρ' for s1/s2 expansion, K for signing randomization. A 32-byte seed would allow only two 256-bit derivations, forcing key reuse or a second derivation step. FIPS 204 sec. 5.1 specifies the 32+32+32 derivation explicitly; the 48-byte external representation in some contexts is a different representation of the same seed material.

HQ-14. What is the difference between a constant-time function and a constant-time implementation, and why does the difference matter for Rust on different targets? Resolves §6 P1 + Phase 12 §12.2 (Pa-14). A function is constant-time if its execution time is independent of secret inputs at the mathematical level. A constant-time implementation is one where the compiled machine code on a specific target CPU exhibits no secret-dependent timing. Rust can compile the same source to a cmov (CT) on x86-64 but to a beq/bne branch (non-CT) on some RISC-V targets without hardware conditional-move. dudect must be run on the deployment target, not just x86-64.

HQ-15. What would it cost to add masking (t-order) to pqc-kem's decapsulation to defend against higher-order power analysis, and is it worth it? Resolves Phase 12 §12.2 + Phase 14 §14.2 (Pa-13). First-order masking doubles the number of polynomial operations (all operate on shares); second-order masking quadruples it. For ML-KEM-768 decaps (≈300 µs baseline), t=1 masking adds ≈300 µs overhead — 600 µs total. This exceeds the §4 target of 500 µs. Masking is worth it only in a physical-access threat model (smart card, HSM) where power traces are observable; in a pure network threat model (no physical access), timing-only CT is sufficient.

HQ-16. If the NTT pointwise multiplication step has a bug that affects only one of the 128 coefficient positions, will the KAT catch it? Resolves Phase 4 §4.2 + Phase 13 §13.2. Yes. The KAT vectors are derived from known-good implementations where every coefficient of the output polynomial is fixed. A bug affecting position k produces a wrong coefficient in the output ciphertext or shared secret; the KAT byte comparison reports a mismatch on the first byte position affected. The schoolbook reference oracle (I5) in Phase 4 would also catch this independently before KAT.

HQ-17. What are the exact conditions under which Barrett reduction produces output outside [0, q), and how does pqc-ntt handle this? Resolves Phase 3 §3.2 + I6 (invariant on coefficient range). Barrett reduction approximates floor(a/q) using a precomputed magic number; the approximation error is ±1 for inputs in the allowed range. If the input exceeds 2^{2k}/q (the overflow threshold for the chosen k), the output can exceed q by 1. pqc-ntt applies a final conditional subtract (if coeff >= q { coeff -= q }) implemented as a constant-time conditional move to bring the result into [0, q).

HQ-18. How does the pqc-cli kat subcommand differ from the pqc-kat library, and what would break if they were merged? Resolves Phase 13 §13.2 + Phase 14 §14.2. pqc-kat is a no_std + optional alloc library crate with no I/O; it takes pre-loaded vectors and returns pass/fail results. pqc-cli is a binary with std, file I/O, and user-facing formatting. Merging them would pull std (and clap, and file I/O) into the core library, breaking the no_std constraint that makes pqc-kat usable in embedded test harnesses. The separation follows ADR-12.

Mental Models & First Principles

These models compress expertise into load-bearing intuitions. Each names the insight, what it predicts, the bug class that emerges without it, and the resolving section.

MM-01. Lattice problems are hard because small things are short but look random. The insight: a short vector s drawn from a small distribution (|s_i| ≤ η) satisfies As+e = b, but b is computationally indistinguishable from uniform — this is Module-LWE hardness (Regev 2005, Pa-1). What it predicts: no polynomial-time algorithm can recover s from (A, b) without knowing the noise distribution, even given many samples. Bug class without it: choosing η too large (η ≥ 6) makes the noise distribution distinguishable from uniform, collapsing IND-CCA2 to distinguishing; choosing η = 0 (no noise) reduces to a linear-algebra problem solvable by Gaussian elimination. Resolving §: §6 P8 (parameter provenance), Phase 1 §1.2 (KemParams/SignParams constants from FIPS 203/204).

MM-02. The Fujisaki-Okamoto transform plugs a single-use-key hole. The insight: CPA-secure encryption leaks nothing about a single fresh message, but an adversary who can submit many ciphertexts and see decryption results (CCA2 oracle) can recover the key. FO patches this by making the encapsulated key deterministic in the message (re-derive r from m via G), so a tampered ciphertext decapsulates to the same PRF output regardless of tampering (Hofheinz-Hövelmanns-Kiltz 2017, Pa-5). What it predicts: a decapsulation routine that ever returns an error (rather than PRF(z, c)) is CCA2-broken — the error is an oracle. Bug class without it: any early-exit error path in decaps (malformed ciphertext before the FO path) leaks one bit per query; 256 queries suffice to determine the shared secret. Resolving §: §6 P3 (FO CCA2 mandate), Phase 7 §7.2 (decaps design).

MM-03. Rejection sampling makes the response distribution secret-independent. The insight: Lyubashevsky's Fiat-Shamir with aborts (2009, Pa-7) masks s1 with a uniform vector y. The response z = y + c·s1 is distributed over a hypercube only if the norm bound is satisfied — conditioned on acceptance, z's distribution is independent of s1. What it predicts: the acceptance probability per iteration is approximately (1 − 2β/γ1)^256L; for ML-DSA-65 this is about 80 %. Bug class without it: if rejection is removed, z leaks c·s1 directly; if y is reused across iterations, successive z_i values share a bias that allows lattice-reduction recovery of s1. Resolving §: §6 P4 (rejection-sampling principle), Phase 8 §8.2 (signing loop).

MM-04. Phantom-type domain tags prevent a class of NTT correctness bugs at zero runtime cost. The insight: a polynomial in Normal domain and a polynomial in NTT domain are the same bit pattern — the ring isomorphism is invisible to the type system unless you tag it. Adding Domain { Normal, Ntt } as a field (or const generic tag) lets the compiler reject poly_add(a_ntt, b_normal) at compile time. What it predicts: without the tag, pointwise multiplication of two Normal polynomials silently produces garbage that passes coefficient-range checks (coefficients are in [0, q)) but is semantically wrong — the error surfaces only in the final KAT or in rare bit-flip patterns. Bug class without it: incorrect-domain composition; silent KAT failures; non-deterministic test failures depending on optimizer's polynomial reordering. Resolving §: ADR-10, Phase 2 §2.2 (Domain tag design), Phase 4 §4.2 (NTT/polynomial integration).

MM-05. A constant-time comparison is a conditional move, not a conditional branch. The insight: (a == b) in C or Rust compiles to sete / setne followed by a branch at the call site if the result is used in an if. subtle::ConstantTimeEq returns a Choice that is #[repr(transparent)] over u8; the black_box barrier prevents LLVM from widening it to bool and folding it into a branch. The selected value is produced by arithmetic: (mask & a) | (!mask & b) emitting cmov or equivalent. What it predicts: LLVM at -O2 will collapse -(a ^ b) >> 63 to cmov on x86-64 and to csel on AArch64 — but only if the value is never widened to bool. Bug class without it: timing side-channel in FO decapsulation comparison; 1-bit leak per query; 256 queries determine the shared secret. Resolving §: §6 P1 (constant-time mandate), Phase 12 §12.2 (pqc-ct design), Pa-14 (Bernstein-Yang barrier pattern).

MM-06. Every hash function in the ML-KEM/ML-DSA protocol is a domain-separated sponge. The insight: SHA3-256, SHA3-512, SHAKE128, SHAKE256 are all instantiations of Keccak-f[1600] with different rate/capacity splits and different padding suffixes: 0x06 (SHA-3) vs 0x1F (SHAKE). ML-KEM assigns G = SHA3-512, H = SHA3-256, PRF = SHAKE256, XOF = SHAKE128; ML-DSA assigns H = SHAKE256. Each usage is domain-separated by the function identity, not by an extra prefix. What it predicts: substituting SHAKE128 for SHA3-256 (H) produces the same output length but breaks IND-CCA2 because the 128-bit capacity is insufficient for the 256-bit binding security claim. Bug class without it: silent security-level downgrade; byte-identical outputs for different security levels when the same seed is used; KAT mismatch if padding byte is wrong. Resolving §: §6 P6 (hash-based domain separation), Phase 5 §5.2 (pqc-hash XOF interface), Pa-8 (FIPS 202 Keccak spec).

MM-07. Montgomery reduction keeps coefficients normalized without an explicit modular division. The insight: Montgomery multiplication computes (a · b · R^{-1}) mod q where R = 2^k for a chosen k (R = 2^16 for q = 3329, R = 2^23 for q = 8380417). The trick: replace the expensive div by q with a mul by q^{-1} mod R followed by a right-shift — all operations are integer multiply and shift. The output is in (-q, q), not [0, q), so one conditional add (constant-time) reduces to canonical form. What it predicts: after 256 pointwise NTT multiplications, coefficients drift into the range (-q · N, q · N) unless Barrett or Montgomery normalization is applied at each butterfly layer. Bug class without it: coefficient overflow in i32 midway through a 128-layer NTT; silent wrap-around producing wrong coefficients that still pass range checks but fail KATs. Resolving §: §6 P5 (reduction principle), Phase 3 §3.2 (Montgomery/Barrett implementation), Pa-3 (original Kyber spec, §1.1).

MM-08. Zeroization requires a volatile write or a compiler barrier; otherwise it is a no-op. The insight: a compiler with knowledge that a variable is never read after memset(p, 0, n) is free to delete the memset as dead code. The zeroize crate prevents this by writing through a volatile raw pointer or by calling compiler_fence(SeqCst) after the write, forcing the store to survive optimization. What it predicts: without the barrier, LTO (Link-Time Optimization) erases the zeroize call in release builds, leaving secret key material in stack/heap memory until overwritten by the next allocation — exploitable via cold-boot or heap-dump attacks. Bug class without it: secret key material persists in memory after drop(signing_key); exploitable in WASM (linear memory dump), TEE (attestation snapshot), or after panic unwind. Resolving §: §6 P8 (secret erasure principle), Phase 12 §12.2 (ZeroizeOnDrop barrier), ADR-05.

  • Relevance: the pqc-ntt butterfly loop implements this merged strategy; the precomputed twiddle table ZETAS[256] is laid out in bit-reversed order as described.
  • Applied in: Phase 3 §3.2 (NTT implementation strategy), Phase 1 §1.2 (Montgomery R selection), §8.8 reduction model, Back-of-Envelope Capacity Model (NTT latency derivation).

Pa-9. Avanzi, Bos, Ducas et al. (2022) — "CRYSTALS-Kyber: a CCA-secure module-lattice-based KEM"

  • Venue: IEEE S&P 2022.
  • Contribution: Formal security proof for the complete two-level Kyber scheme; tight ROM reduction from Module-LWE to IND-CCA2 KEM.
  • Extract: the re-encryption must use r = H(m, H(pk)) (the same deterministic derivation as encapsulation); the proof breaks if re-encryption uses a different r.
  • Relevance: confirms the exact G(m, H(pk)) = (K, r) construction in pqc-kem::encaps and pqc-kem::decaps; Phase 8 implementation must match.
  • Applied in: Phase 8 §8.2 (G-split construction), Phase 8 §8.6 pitfall (G split point), Comparative Architecture Table (BoringSSL/Google PQC comparison — same FO structure).

Pa-10. Ducas et al. (2018) — "CRYSTALS-Dilithium: A Lattice-Based Digital Signature Scheme"

  • Venue: TCHES 2018(1).
  • Contribution: HighBits_α(r), LowBits_α(r), MakeHint_α(z,r), UseHint_α(h,r) integer definitions; hint correctness proof; deconstruction of the signing loop.
  • Extract: HighBits(r,α) = (r - r mod α) / (α/2) for α = 2*γ2; LowBits(r,α) = r mod α; UseHint(h,r,α) corrects the high bits using the carry hint bit h.

  • Applied in: Phase 6 §6.2 (HighBits/LowBits in dilithium_pack.rs), Phase 10 §10.2 (make_hint), Phase 11 §11.2 (use_hint), §8.5 DSA signing state machine.

Pa-11. Kocher (1996) — "Timing Attacks on Implementations of Diffie-Hellman, RSA, DSS, and Other Systems"

  • Venue: CRYPTO 1996 (LNCS 1109).
  • Contribution: First practical timing side-channel; variable-time Montgomery exponentiation leaks secret exponent bits via statistical analysis of modular reduction timing differences.
  • Extract: the attack requires only timing measurements and the public key; applies to any variable-time modular arithmetic on secret inputs.
  • Relevance: motivates P1, I2, Phase 12; the argument extends to polynomial arithmetic in pqc-ntt and the FO comparison in pqc-kem.
  • Applied in: §6 P1 (constant-time mandate), Phase 12 §12.2 (CT audit checklist motivating ct_eq), Threat Model T4, Mental Models MM2.

Pa-12. Bernstein (2005) — "Cache-Timing Attacks on AES"

  • Venue: Preprint, cr.yp.to/antiforgery.
  • Contribution: Cache-timing attack via table-lookup: T-table AES leaks the secret key through cache-hit/miss patterns on lookup tables.
  • Extract: any table indexed by a secret value (even a seemingly innocent 256-byte S-box) leaks ~1 bit per cache miss; cache lines of 64 bytes expose 4 table entries per query.
  • Relevance: pqc-ct must avoid tables indexed by secret; NTT zeta table is indexed by public loop counter (safe); CBD sampling must not use a lookup table.
  • Applied in: §6 P1 (no secret-indexed table), Phase 5 §5.2 (CBD constant-time bit extraction, no lookup), Phase 12 §12.2 (variable-time exceptions documenting NTT zeta table is public), Phase 4 §4.2 (no lookup tables in Keccak).

Pa-13. Becker et al. (2023) — "Masking the Kyber Decapsulation"

  • Venue: CHES 2023.
  • Contribution: First-order masked ML-KEM decapsulation; cost model for masked FO comparison; hardest-to-mask operations identified.
  • Extract: the FO implicit-rejection select (ct_select(K_good, K_bad, eq_bit)) is the highest-cost masking point; requires a 32-byte masked conditional copy.
  • Relevance: context for future Phase 12 extensions; shows where I2 is most expensive to enforce when first-order masking is required.
  • Applied in: Phase 14 §14.2 (side-channel review cost model), Phase 12 §12.2 (ct_cmov design justification), Hard Questions HQ-15 (masking cost tradeoff question).

Pa-14. Bernstein & Yang (2019) — "Fast Constant-Time GCD and Modular Inversion"

  • Venue: TCHES 2019(3).
  • Contribution: divstep algorithm: constant-time GCD/modular inversion via a simple iteration; no secret-dependent branches.
  • Extract: the black_box barrier pattern preventing compiler optimisation of constant-time code; the principle of expressing conditional operations as arithmetic.

Glossary · 44 terms · site-wide glossary

ACVP
Automated Cryptographic Validation Protocol — NIST framework supplying the JSON-encoded KAT vectors used in pqc-kat.
Barrett reduction
Integer division by a fixed modulus via precomputed reciprocal multiply and shift; avoids hardware divide; used for ML-DSA's q=8380417.
CBD / Centered Binomial Distribution
CBD_eta: sample eta pairs of bits, return difference; exact distribution for secret/noise poly coefficients in ML-KEM; constant-time from PRF output.
CCA2 security
Chosen-ciphertext attack (adaptive) — an adversary who can query a decryption oracle on any ciphertext except the challenge cannot distinguish shared secrets; achieved here by the Fujisaki-Okamoto transform.
Challenge polynomial (c)
Sparse polynomial with exactly tau coefficients in {+1, -1} and the rest 0; derived by hashing (tr, msg, w1) in ML-DSA signing; defines the Fiat-Shamir binding.
CPA security
Chosen-plaintext attack — the weaker base security of the Module-LWE PKE before the FO transform lifts it to CCA2.
Compression / Decompress_q
Lossy rounding: Compress_q(x,d) = round(2^d/q * x) mod 2^d; Decompress_q reverses; used on KEM ciphertext components (u,v) to reduce bandwidth; introduces bounded noise.
Decapsulation failure
Event where decaps(sk, encaps(pk)) ≠ intended shared secret; negligible probability bounded by the module-LWE noise parameters; analyzed per parameter set in FIPS 203.
Domain tag
enum Domain { Normal, Ntt } — a Poly carries its domain; the type system prevents multiplying a Normal poly against an NTT poly without explicit conversion.
Fiat-Shamir with aborts
Lyubashevsky's signature paradigm: commit, receive challenge, respond with z = y + c·s1; abort and retry if z or residual exceeds the norm bound, to prevent secret leakage via response distribution.
FIPS 203
NIST Federal Information Processing Standard 203 — the normative ML-KEM specification; defines parameter sets 512/768/1024, all encodings, and the KAT vectors.
FIPS 204
NIST Federal Information Processing Standard 204 — the normative ML-DSA specification; defines parameter sets 44/65/87, all encodings, signing/verification algorithms, and the KAT vectors.
Fujisaki-Okamoto (FO) transform
Converts a CPA-secure PKE into a CCA2-secure KEM: re-encrypt on decapsulation and constant-time compare; mismatch returns PRF(z,c) (implicit rejection).
G (hash function)
SHA3-512 as defined in FIPS 203; used to derive (K,r) from the message and public-key hash during KEM encapsulation.
H (hash function)
SHA3-256 as defined in FIPS 203/204; used to hash the public key into the KEM secret key (H(pk)) and in signature tr.
Hint (h)
Carry-correction bits in ML-DSA signatures; allow verifier to reconstruct w1' from A·z - c·t1·2^d without access to the secret t0.
High bits / Low bits
HighBits(r, alpha): upper portion of r mod q used in ML-DSA commitment w1; LowBits: remainder; decomposition defined in FIPS 204 Algorithm 9/10.
Implicit rejection
On decapsulation failure the KEM returns PRF(z, c) instead of an error; the caller cannot distinguish valid from invalid ciphertext by the returned value or timing.
KAT (Known-Answer Test)
A deterministic test vector pairing a seed/input with an exact expected output; pqc-kat asserts byte-exact agreement with FIPS 203/204 ACVP vectors for every parameter set.
Keccak-f[1600]
The underlying permutation of SHA-3 and SHAKE; a 1600-bit state updated via 24 rounds of theta/rho/pi/chi/iota steps; implemented from scratch in pqc-hash.
KEM (Key Encapsulation Mechanism)
A public-key primitive outputting a shared secret and a ciphertext; the shared secret is never transmitted; here constructed via Module-LWE PKE + FO transform.
Lattice / Module lattice
A discrete additive subgroup of R^n; Module-LWE and Module-SIS are hard problems over module lattices of rank k over a polynomial ring; hardness is quantum-resistant.
LWE (Learning With Errors)
Computational problem: given A, b = A·s + e (e small noise), find s; believed hard classically and quantumly; the security foundation of ML-KEM.
ML-DSA
Module-Lattice-Based Digital Signature Algorithm — the FIPS 204 standard; concrete parameter sets replace the submission-era "Dilithium" names.
ML-KEM
Module-Lattice-Based Key-Encapsulation Mechanism — the FIPS 203 standard; concrete parameter sets replace the submission-era "Kyber" names.
Module-LWE
LWE over a module of rank k over R_q = Z_q[X]/(X^256+1); the matrix A is k×k (KEM) or k×l (DSA); larger k raises security at cost of key size.
Module-SIS
Short Integer Solution problem over modules; the computational assumption underlying ML-DSA binding.
Montgomery reduction
Multiplication mod q using a precomputed R=2^16 (ML-KEM) or R=2^23 (ML-DSA) such that Montgomery_reduce(a·b) = a·b·R^{-1} mod q; avoids division; used in NTT butterflies.
Negacyclic convolution
Polynomial multiplication modulo X^256+1 (not X^256-1); the NTT exploits the negacyclic structure via 2n-th roots of unity.
Norm bound
ML-DSA: signing accepts z only when
NTT (Number-Theoretic Transform)
Discrete Fourier transform over Z_q using q-th roots of unity; converts polynomial multiplication to pointwise multiplication in O(n log n); pqc-ntt implements Cooley-Tukey forward and Gentleman-Sande inverse.
Parameter set
A named tuple of cryptographic constants (k, l, eta, du, dv, gamma1, gamma2, tau, …) defining a security level; ML-KEM-512/768/1024 and ML-DSA-44/65/87 are the six sets.
Pointwise multiplication
Element-wise multiply of two NTT-domain PolyVecs; equivalent to polynomial multiplication in R_q after inverse NTT.
PRF
Pseudo-random function — instantiated as SHAKE256 in FIPS 203/204; used to generate CBD noise from a seed and a counter byte.
Rejection sampling
In ML-KEM: discard uniform XOF output bytes ≥ 19·q mod q (keeps distribution uniform mod q) to generate matrix A. In ML-DSA: discard a candidate signature when norm bounds are exceeded.
rho
32-byte public seed embedded in public keys; deterministically expands via XOF to the full public matrix A; not secret.
R_q
The quotient ring Z_q[X]/(X^256+1); elements are degree-255 polynomials with coefficients in Z_q; the algebraic structure underlying both ML-KEM and ML-DSA.
Seed (rho / sigma / K)
32-byte octet strings fed to SHAKE for deterministic expansion; rho generates A (public), sigma generates s1/s2/e (secret), K is used in implicit rejection.
SHAKE128 / SHAKE256
Extendable-output functions (XOF) from the SHA-3 family; squeeze arbitrary bytes; SHAKE128 seeds A expansion (XOF), SHAKE256 used as PRF/G/H per FIPS.
Shared secret (K)
The 32-byte KEM output agreed by encapsulator and decapsulator; derived from H(m, H(pk)) on success or PRF(z, c) on failure.
Twiddle factor / Zeta
A primitive 2n-th root of unity mod q used in NTT butterfly stages; precomputed into a table of 128 zeta values for n=256.
XOF
Extendable-Output Function — SHAKE128 used as the matrix-expansion XOF; takes a seed and (i,j) indices, squeezes coefficients for rejection sampling.
Zeroization
Overwriting secret-key and intermediate buffers (s1, s2, t0, y, m) with zeros before deallocation; implemented via the zeroize crate or equivalent barrier write in pqc-ct.
Zq
A single coefficient in Z_q; stored as i32 to allow signed intermediates during Montgomery/Barrett arithmetic; always reduced to [0, q) before serialization.
