Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust (2021 edition)

Rejected

C, C++, Go, Python, Zig

When the rejected choice is right

C wins for embedded HSM targets where no Rust toolchain exists or where a certified C compiler (e.g., IAR) is mandatory for safety certification

Why: Memory safety without GC; zero-cost abstractions; zeroize, subtle ecosystem; no undefined behavior on integer overflow in debug mode

ADR-02

Build system

Chosen

Cargo (workspace)

Rejected

Bazel, CMake, Meson

When the rejected choice is right

Bazel wins in a multi-language monorepo (Rust + C + Proto + Go) where hermetic cross-language build caching across teams is the primary driver

Why: Standard Rust toolchain; workspace unifies all pqc-* crates; reproducible via Cargo.lock

ADR-03

Dependency policy

Chosen

Minimal: zeroize, subtle, sha3 (RustCrypto) optional feature-gated; no rand in core

Rejected

ring, openssl, boringssl

When the rejected choice is right

ring or openssl wins when FIPS 140-3 certified cryptographic module boundaries are required by a customer contract; the from-scratch crate has no such certification

Why: Audit surface; sha3 may be replaced by pqc-hash; subtle for CT primitives; zeroize for secret erasure

ADR-04

Constant-time primitives

Chosen

subtle crate (Choice, CtOption, ConditionallySelectable)

Rejected

Manual volatile_read, inline asm

When the rejected choice is right

Inline assembly wins on deeply embedded targets where LLVM cannot be trusted to preserve barriers, or when formal hardware CT proof is required (e.g., CHERI-based isolation)

Why: subtle is audited; compiler-barrier patterns; integrates with zeroize; no secret-dependent branches

ADR-05

Zeroization

Chosen

zeroize crate (Zeroize + ZeroizeOnDrop derive)

Rejected

Manual memset, SecretBox

When the rejected choice is right

Manual memset_s (C11) or platform-specific SecureZeroMemory (Windows) wins when interfacing with a C ABI layer that owns the allocation; the zeroize crate cannot traverse opaque FFI pointers

Why: Prevents compiler elision; ZeroizeOnDrop on all secret key structs; covers heap and stack

ADR-06

SHA-3 / SHAKE

Chosen

pqc-hash (from-scratch Keccak-f[1600]) cross-ref #88

Rejected

sha3 crate, openssl

When the rejected choice is right

The sha3 RustCrypto crate wins in a production library that must audit a single well-maintained dependency rather than own a Keccak implementation; applies when cryptographic engineering headcount is limited

Why: Spec compliance; byte-exact ACVP verification; full control over absorb/squeeze interface; reuse with project #88

ADR-07

Serialization format

Chosen

FIPS 203/204 bit-packed binary (custom pqc-encode)

Rejected

serde + JSON/CBOR, bincode

When the rejected choice is right

serde+JSON wins in a REST API context where key material is transported as Base64-encoded JSON and human-readability of intermediate representations is required for debugging by non-specialist operators

Why: No generic serializer; exact FIPS byte layout required; serde adds unnecessary abstraction and cannot express d-bit packing

ADR-08

Integer storage for Zq

Chosen

i32 (signed, 32-bit) with i64 intermediates

Rejected

u16, u32, i64 throughout

When the rejected choice is right

u16 throughout wins in a vectorized SIMD NTT (AVX2 SIMD packs 16×u16); the narrower type doubles parallelism in the butterfly loop, at cost of requiring ML-KEM-only (q=3329, fits 16-bit) and a separate ML-DSA path

Why: i32 holds both q=3329 (fits u12) and q=8380417 (fits i24); intermediate products need i64; Barrett/Montgomery in i64, store as i32

ADR-09

NTT twiddle factor precomputation

Chosen

Static const arrays of Montgomery-encoded zetas

Rejected

Runtime computation, lazy static

When the rejected choice is right

Runtime lazy-static computation wins on a target where ROM is severely constrained (< 4 KB) and the zeta table must be in RAM; embedded MCU with bank-switched flash is the canonical case

Why: Eliminates runtime init; compile-time const eval; no mutex/once overhead; fully inlined

ADR-10

Polynomial domain safety

Chosen

Domain enum tag on Poly + runtime assert (debug) / type-level in release

Rejected

Separate PolyNtt type, no enforcement

When the rejected choice is right

Separate PolyNtt type wins when the codebase targets a pre-stable Rust compiler with limited const-generics support, or when the type discipline is enforced at a higher-level API boundary by a trusted wrapper

Why: Runtime assert in debug catches misuse; type-level requires const generics (Rust stable support marginal); domain tag overhead: 1 byte

Alternative Architectures

Each alternative is fundamentally different from the primary design. For each: ASCII sketch of the conceptual structure, regime where it wins, a real system that chose it, and why it is not the primary choice here.

Alt-1: Hash-Based Signatures (SLH-DSA / SPHINCS+, FIPS 205)

SLH-DSA structure:
  Signing key ──► SK.seed ──SHAKE──► FORS trees + HT layers
                                         │
                  PK = H(FORS.pk ‖ HT.pk)│
                                         ▼
  Sign: choose FORS leaf idx → FORS auth path + FORS sig
        + HT sig (d-layer hash-based Merkle path)
  Verify: recompute FORS root + HT root; check PK

Regime where it wins: maximum confidence in post-quantum security when even lattice hardness is doubted; defense against unknown quantum attacks on algebraic structure; regulatory mandates that prohibit lattice-based algorithms. Real system: SPHINCS+ (Round-3 alternate NIST finalist), now standardized as FIPS 205 SLH-DSA. Why not primary: signatures are 7856 – 49856 bytes (vs ML-DSA-65's 3309 bytes); signing is 10–100× slower due to many hash evaluations; the stateless design requires a huge one-time hash tree. For the KEM use case, hash-based KEM (BIKE, Classic McEliece) has similar drawbacks. ML-DSA at 3309 bytes is a far more practical choice for TLS and code-signing workloads.

Alt-2: Code-Based Cryptography (Classic McEliece)

Classic McEliece structure:
  Public key: n×k binary matrix G (over GF(2))
  Encrypt: m → c = m·G + e  (e = random weight-t error vector)
  Decrypt: Berlekamp-Massey error correction
           → unique m if weight(e) ≤ t

Regime where it wins: highest confidence against quantum attacks among all NIST finalists (McEliece's 50-year security track record); no known structural attacks even with quantum computers; preferred in ultra-high-assurance contexts (nuclear command-and-control, long-lived government communications where 50-year security is required). Real system: Classic McEliece KEM (NIST Round 4 finalist, not yet standardized); liboqs includes McEliece implementations. Why not primary: public keys are 261 KB – 1 MB depending on parameter set; this is impractical for TLS (client hello size limit), code signing, or embedded use; the primary blueprint targets TLS-compatible key sizes (≤ 2 KB public key).

Alt-3: Plain-LWE (Ring-LWE, NTRU) without Module Structure

Ring-LWE structure (degree-n ring, not module):
  a ← R_q[x]/(x^n + 1), s, e ← χ_σ
  b = a·s + e  (product in ring, not matrix-vector)
  KEM encaps: u = a·r + e1, v = b·r + e2 + round(q/2)m

Regime where it wins: smaller key/ciphertext sizes for equal security level when module rank k=1 is sufficient (pure Ring-LWE at n=1024 achieves 256-bit security with smaller keys than ML-KEM-1024 at n=256, k=4); better suited for very constrained MCUs where memory for a k×k matrix is prohibitive. Real system: NTRU (original), NewHope (deprecated NIST candidate, used by Google in an early TLS experiment). Why not primary: FIPS 203 standardizes Module-LWE (ML-KEM), not Ring-LWE; using plain Ring-LWE would produce a non-FIPS-compliant implementation. Module structure also provides algebraic flexibility: the module rank k can be varied to tune security without changing the polynomial degree n=256.

Alt-4: Isogeny-Based Cryptography (SIDH/SIKE — historical only)

SIDH structure (historical, broken 2022):
  E: elliptic curve over GF(p^2)
  Alice: choose secret isogeny φ_A of degree l_A^{e_A}
  Bob:   choose secret isogeny φ_B of degree l_B^{e_B}
  Shared: j-invariant of E / (φ_A ∘ φ_B)

Regime where it wins: historically offered the smallest public keys (~330 bytes for SIKEp434) among all PQC candidates; interesting for extremely bandwidth-constrained protocols. Real system: SIKE (NIST Round-3 alternate finalist); SIKEp434 was the most studied variant. Why not primary: SIKE was completely broken in July 2022 by Castryck-Decru (an efficient classical polynomial-time attack using the torsion-point information leakage); the Castryck-Decru attack is based on a mathematical insight about auxiliary points that SIDH requires for efficiency. No current isogeny-based KEM scheme has survived similar scrutiny at usable parameter sizes; the field is active (CSIDH, SQIsign) but not yet standardized. Including isogeny-based schemes would violate P12 (no implicit cryptographic assumptions) given the 2022 break.
