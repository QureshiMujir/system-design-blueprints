Decisions (§9) · 32 ADRs

ADR-01

Implementation language

Chosen

Rust (stable channel, MSRV 1.78)

Rejected

C++, Go, Python

When the rejected choice is right

Python wins for research prototyping where the NumPy/diffprivlib ecosystem and rapid iteration beat performance and safety

Why: Memory safety without GC; strong type system for newtype invariants; zero-cost abstractions; no undefined behavior for numeric code; portfolio consistency

ADR-02

Build system

Chosen

Cargo workspace with per-crate Cargo.toml

Rejected

Bazel, Buck

When the rejected choice is right

Bazel wins in a polyglot monorepo with remote build caching across many languages and thousands of targets

Why: Cargo is the de-facto Rust build system; workspace deduplicates deps; minimal toolchain surface area

ADR-03

Dependency policy

Chosen

Minimal, pinned, audited (cargo audit); no network deps at runtime

Rejected

liberal transitive deps

When the rejected choice is right

Liberal deps win for a fast-moving research library where breadth of functionality matters more than an auditable supply chain

Why: Privacy engine must be auditable; each dep is a potential attack surface; cargo-vet policy for crate reviews

ADR-04

CSPRNG source

Chosen

rand_chacha (ChaCha20) seeded from OS entropy via getrandom

Rejected

rand default, thread_rng, hardware RDRAND alone

When the rejected choice is right

Hardware-RDRAND-alone wins on constrained embedded targets that lack an OS entropy path, accepting the single-source trust tradeoff

Why: ChaCha20 is deterministic, audited, and portable; OS entropy (getrandom) is the trusted seed; avoids RDRAND-only dependency (NIST concern); required for I5

ADR-05

Laplace sampler

Chosen

Snapping mechanism (Mironov CCS 2012) — clamp to λ·Z, snap to nearest floating-point multiple of λ

Rejected

Naive inverse-CDF on f64

When the rejected choice is right

Naive inverse-CDF wins in a non-adversarial teaching/demo context where the floating-point attack is explicitly out of scope

Why: Naive float Laplace leaks exact input through representable-value gaps; snapping closes the attack; mandatory for P3, I5

ADR-06

Gaussian sampler

Chosen

Discrete Gaussian (Canonne-Kamath-Steinke NeurIPS 2020) or analytic Gaussian with interval refinement

Rejected

Box-Muller on f64, Ziggurat

When the rejected choice is right

Box-Muller/Ziggurat win for fast continuous Gaussian in non-privacy uses (simulation, initialization) where exactness is irrelevant

Why: Continuous Gaussian on floats has bias; discrete Gaussian is exact over integers; analytic for real-valued with documented precision bounds; closes float-DP gap (I5)

ADR-07

Analytic Gaussian calibration

Chosen

Balle-Wang (ICML 2018) tight σ via bisection on the error-function equation

Rejected

Classical σ = Δ·√(2 ln(1.25/δ))/ε

When the rejected choice is right

The classical closed form wins when you need a one-line, dependency-free σ and can absorb 10–30% extra noise (quick estimates)

Why: Classical bound wastes ~10–30% σ; analytic is minimax optimal; bisection converges in <50 iterations; justified in ADR narrative

ADR-08

Privacy accountant (default)

Chosen

RDP accountant (Mironov CSF 2017) with configurable order vector

Rejected

Basic composition only, zCDP only

When the rejected choice is right

Basic composition wins for a handful of Laplace/exponential queries where RDP machinery is overkill and the looser bound is acceptable

Why: RDP gives strictly tighter (ε,δ) than advanced composition for DP-SGD; additive per-order composition is O(k·|orders|); zCDP available as alternate; basic is fallback for Laplace/Exp

ADR-09

zCDP support

Chosen

ZcdpAccountant (Bun-Steinke TCC 2016) alongside RDP

Rejected

Merge into RDP only

When the rejected choice is right

RDP-only wins when every mechanism is Gaussian-family and a single accumulator simplifies the API and avoids dual book-keeping

Why: Some mechanisms (pure Gaussian) are naturally expressed in zCDP; separate accumulator avoids lossy conversion at each step; conversions defined in dp-accountant

ADR-10

Serialization format

Chosen

serde_json for CLI / audit log; optional prost Protobuf for inter-service wire

Rejected

CBOR, MessagePack, custom binary

When the rejected choice is right

CBOR/MessagePack win when audit-log volume is huge and compact binary + decode speed beat human-readability

Why: JSON is human-readable for audit logs (required by P10); Protobuf for service integration is standard; no custom binary to avoid reimplementing encoding bugs

ADR-11

Audit log format

Chosen

Newline-delimited JSON (NDJSON), append-only file

Rejected

SQLite, structured syslog

When the rejected choice is right

SQLite wins when audit logs need rich queryable indexes and transactional integrity on a single node

Why: Append-only = tamper-evident; NDJSON is grep-friendly; no DB dependency in the core engine; rotation via log agent (logrotate / Vector) outside the crate

ADR-12

Concurrency model

Chosen

Synchronous by default; Arc<Mutex<Budget>> for shared mutable budget; no async runtime in core

Rejected

Tokio async throughout, Rayon only

When the rejected choice is right

Tokio-async wins when the engine is embedded in an async service fielding many concurrent network-bound DP queries

Why: DP core is compute-bound, not I/O-bound; async adds complexity; Budget mutex is the only shared state; dp-cli may wrap in Tokio for CLI I/O

ADR-13

Parallelism for DP-SGD

Chosen

rayon data-parallel per-example gradient clipping

Rejected

Manual threads, ndarray-linalg

When the rejected choice is right

Manual threads or a GPU backend win when integrating with an existing thread pool or accelerator that Rayon cannot target

Why: Per-example clip is embarrassingly parallel; Rayon's work-stealing is safe with Rust ownership; no shared mutable state per example

ADR-14

Numeric linear algebra

Chosen

ndarray for tensor ops in dp-dpsgd

Rejected

nalgebra, faer, raw BLAS

When the rejected choice is right

Raw BLAS/faer win for large dense linear algebra where peak FLOPs dominate and the C-FFI risk is acceptable

Why: ndarray has a mature Rust ecosystem; faer considered for future; avoid C FFI in core numeric path to maintain safety guarantees

ADR-15

Error handling

Chosen

thiserror for structured error types per crate; anyhow in dp-cli only

Rejected

Box<dyn Error>, custom string errors

When the rejected choice is right

anyhow wins in binary/CLI code where call-site ergonomics beat programmatic match-on-variant

Why: thiserror produces typed, match-able errors; anyhow is acceptable in binary crates; typed errors are required for programmatic budget-denial handling

ADR-16

Property-based testing

Chosen

proptest for newtype invariant, composition, and sensitivity soundness tests

Rejected

quickcheck, manual fuzz

When the rejected choice is right

quickcheck wins for a tiny test surface where its simpler model suffices and proptest's strategy machinery is unnecessary

Why: proptest has richer shrinking and strategy composition; mandatory for I1–I10 coverage; custom proptest strategies for valid (ε,δ) pairs

ADR-17

Fuzzing

Chosen

cargo-fuzz (libFuzzer) on parser, bounds, mechanism constructors, accountant inputs

Rejected

AFL via afl.rs, honggfuzz

When the rejected choice is right

honggfuzz/AFL win when their instrumentation reaches deeper coverage on a specific hard-to-fuzz target

Why: cargo-fuzz integrates with cargo and CI; targets: malformed PrivacyParams, extreme sensitivity values, adversarial RDP order vectors

ADR-18

Statistical DP validation

Chosen

Custom neighboring-dataset hypothesis tests in dp-validate, modeled on StatDP (Ding et al. CCS 2018)

Rejected

Differential tester only, no statistical test

When the rejected choice is right

A pure differential tester wins as a fast pre-commit smoke test, reserving the expensive statistical suite for release gates

Why: Statistical tests catch calibration bugs invisible to unit tests (e.g., wrong σ by 0.01%); StatDP approach: sample M(D) and M(D'), run KS / chi-squared test on ratio of empirical CDFs

ADR-19

Benchmarking

Chosen

criterion with criterion-perf-events for cycle counting

Rejected

std::time only, hyperfine

When the rejected choice is right

hyperfine wins for quick end-to-end CLI wall-clock comparisons without writing a bench harness

Why: Criterion gives statistical significance; perf-events adds IPC data; benchmarks run in CI on tagged releases; targets: sample throughput, accounting overhead per release

ADR-20

Logging

Chosen

tracing crate with tracing-subscriber (JSON formatter in production)

Rejected

log + env_logger, slog

When the rejected choice is right

log + env_logger win for a minimal CLI where structured spans add no value

Why: tracing is structured, span-aware, and composable; JSON formatter feeds the audit pipeline; spans capture query lifecycle without logging raw data (P10)

ADR-21

Metrics

Chosen

metrics crate facade + metrics-exporter-prometheus in dp-cli

Rejected

OpenTelemetry SDK, custom counters

When the rejected choice is right

OpenTelemetry wins when the deployment standardizes on OTLP traces + metrics across a distributed system

Why: metrics facade allows backend swap; Prometheus is the standard scrape target; counters: budget_spend_total, budget_denied_total, mechanism_invocations

ADR-22

CI/CD

Chosen

GitHub Actions: cargo test --workspace, cargo clippy, cargo fmt --check, cargo audit, fuzz job (10-min budget), criterion regression check

Rejected

Jenkins, CircleCI

When the rejected choice is right

Jenkins wins inside enterprises with self-hosted runners and compliance constraints GitHub-hosted runners cannot meet

Why: GitHub Actions is zero-ops; matrix over stable + MSRV; fuzz in CI catches regressions before merge

ADR-23

Packaging

Chosen

Library crates published to crates.io; dp-cli as a standalone binary via cargo install

Rejected

Docker-only distribution, npm/pip wrapper

When the rejected choice is right

A pip/Docker-only wrapper wins when the primary users are Python data scientists who never touch Cargo

Why: Rust library should be composable; dp-cli binary gives standalone tooling; Docker image for dp-cli provided for server deployments

ADR-24

Container

Chosen

debian:bookworm-slim base for dp-cli Docker image; multi-stage build (builder: rust:1.78, runtime: slim)

Rejected

Alpine (musl edge cases with CSPRNG), distroless

When the rejected choice is right

distroless wins when minimal attack surface is paramount and the musl/getrandom edge cases are independently mitigated

Why: bookworm-slim has glibc (avoids musl getrandom edge cases); multi-stage keeps image small; getrandom syscall access verified in CI

ADR-25

Reproducibility

Chosen

Pinned Cargo.lock checked in; cargo vendor for offline build; MSRV pinned in rust-toolchain.toml

Rejected

Floating deps, no lockfile

When the rejected choice is right

Floating deps win for a canary CI lane whose purpose is to surface upstream breakage as early as possible

Why: Reproducibility is required for security review and auditability; pinned deps allow cargo audit to be meaningful

ADR-26

Licensing

Chosen

MIT OR Apache-2.0 (SPDX dual license)

Rejected

GPL, proprietary

When the rejected choice is right

GPL wins when copyleft is a deliberate strategy to force downstream openness; proprietary when the DP IP is a commercial moat

Why: Dual MIT/Apache-2.0 is the Rust ecosystem norm; compatible with OpenDP and Google-DP reference implementations; no GPL viral risk for library users

ADR-27

Sensitivity declaration model

Chosen

Programmer-declared Bounds + engine-computed sensitivity (not automated sensitivity tracking via type-level proof)

Rejected

Full automated sensitivity type system (as in OpenDP's Rust DSL)

When the rejected choice is right

Automated type-level sensitivity tracking wins in high-assurance settings where correctness-by-construction justifies the API complexity

Why: Automated tracking is powerful but dramatically increases API complexity and compilation time; declared+audited model is simpler, more approachable, auditable via dp-validate; noted as a future evolution path

ADR-28

Floating-point determinism

Chosen

Best-effort: snapping mechanism normalizes float representation; tests tolerance-bounded not bit-exact

Rejected

Require bitwise reproducibility across platforms

When the rejected choice is right

Bitwise reproducibility wins when regulation mandates identical output across machines for audit, accepting the FPU-optimization loss

Why: True bitwise repro across x86/ARM requires disabling FPU optimizations; snapping already reduces float-space to a discrete grid; statistical tests use tolerance bands

ADR-29

Sensitivity declaration vs. type-level proof

Chosen

Programmer-declared Bounds checked at runtime + audited by dp-validate

Rejected

Full type-level proof system (OpenDP-style Haskell/Rust DSL)

When the rejected choice is right

A full proof system wins for formally-verified deployments that must ship a machine-checked privacy proof with every release

Why: Type-level proofs are correct-by-construction but significantly raise API complexity and compilation time; declared+validate is pragmatic, auditable, and composable

ADR-30

Budget-per-dataset vs. global budget

Chosen

Per-dataset Budget with optional per-analyst sub-budget

Rejected

Single global budget for all queries

When the rejected choice is right

A single global budget wins for a single-tenant, single-dataset deployment where isolation is irrelevant and simplicity matters

Why: Datasets have independent privacy guarantees; per-dataset budgets enforce isolation (I3); sub-budgets allow multi-analyst deployments without one analyst exhausting another's quota

ADR-31

Neighboring relation model

Chosen

Add/remove (unbounded DP) as default; replace (bounded DP) opt-in via API flag

Rejected

Replace-one only, or both silently

When the rejected choice is right

Replace-one (bounded DP) as default wins when all analyses are fixed-size means/sums and the lower sensitivity is worth the bounded-DP proof

Why: Add/remove is the conservative default (higher sensitivity); replace-one gives lower sensitivity for mean/sum but requires different proof; caller must declare; sensitivity depends on the choice

ADR-32

Sparse vector technique isolation

Chosen

Dedicated dp-svt crate with its own SVTState; not merged into dp-mechanism

Rejected

Merge into dp-mechanism

When the rejected choice is right

Merging SVT into dp-mechanism wins for a minimal build needing only one or two SVT queries that wants fewer crates

Why: SVT has unique stateful semantics (above_limit, mixed threshold/answer epsilon); isolation prevents misuse of privacy accounting (only one threshold cost, answer costs are conditional)

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Type-level sensitivity calculus (OpenDP-style)

Transformation: f with stability c  ┐
                                     ├─chain─▶ Measurement (ε,δ)   (sensitivity proven by types)
Measurement: M with privacy (ε,δ)   ┘

Transformations and measurements compose with compile-time stability tracking; sensitivity is proven, not declared. Wins in high-assurance settings that want correct-by-construction sensitivity. Real system: OpenDP (the transformation/measurement framework). Rejected here because it dramatically raises API complexity and compile time (ADR-27, ADR-29); the declared-and-audited model is more approachable and is validated empirically by dp-validate.

Alt-2 — Syntactic anonymization (k-anonymity / l-diversity)

quasi-identifiers ──generalize/suppress──▶ each record indistinguishable among k
(no noise; deterministic transform of the table)

Generalize or suppress quasi-identifiers so every record is hidden among k peers. Wins for simple, interpretable static releases where formal DP is not required and analysts want to read the released table directly. Real systems: ARX, Mondrian, Datafly. Rejected here because it provides no formal privacy guarantee and is vulnerable to composition and linkage attacks — precisely the failure mode that motivated DP (Dwork et al. 2006).

Alt-3 — Local DP only (no trusted curator)

each user ──randomize on device (RR)──▶ aggregator sees only randomized reports
                                         (curator never holds raw data)

Every user randomizes their own data before it leaves the device; the aggregator never sees raw values. Wins when no trusted curator can exist — large-scale telemetry. Real systems: Google RAPPOR, Apple's LDP telemetry. Rejected as the default because local DP needs far more users for the same accuracy; this engine offers it at Phase 13 but centers the more accurate trusted-curator model.

Alt-4 — Secure aggregation / MPC curator replacement

parties ──MPC / secure aggregation──▶ noised aggregate revealed
         (no single party sees raw data or the un-noised sum)

Parties compute the noised aggregate under MPC so no single party sees raw data or the clean sum — central-DP accuracy without a trusted curator. Wins for federated learning across mutually distrustful parties. Real systems: secure aggregation in federated learning (Bonawitz et al. 2017). Rejected here (deferred; cross-links #392 MPC and #407 Federated Learning) because it adds a cryptographic protocol layer orthogonal to the DP accounting this engine teaches.
