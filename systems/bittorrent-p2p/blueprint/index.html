1. Goal & Scope

Build, from first principles, an interoperable BitTorrent peer-to-peer stack: a bencode codec, a .torrent/magnet metainfo parser, HTTP and UDP tracker clients, a peer-wire-protocol engine (BEP 3) with the fast extension (BEP 6) and extension protocol (BEP 10), rarest-first piece selection with endgame, Cohen tit-for-tat choking, a sparse-file storage backend with SHA-1 / SHA-256 verification, a Mainline DHT node (BEP 5, Kademlia), peer exchange (BEP 11) and local service discovery (BEP 14), magnet-link metadata exchange (BEP 9), a µTP/LEDBAT transport (BEP 29) and MSE obfuscation (BEP 8), and BitTorrent v2 (BEP 52) hybrid-swarm support — packaged as a library (libswarm), a daemon (swarmd), and a CLI (swarmctl), interoperating at the byte level with libtorrent, Transmission, and qBittorrent.

Phase-0 deliverable (numbered list of crates stood up, even as placeholder facades, by the end of Phase 0):

  1. swarm-bencode — bencode codec facade
  2. swarm-metainfo — .torrent / magnet parsing facade
  3. swarm-tracker — HTTP/UDP tracker client facade
  4. swarm-wire — peer wire protocol facade
  5. swarm-storage, swarm-picker, swarm-choke — storage/piece-picking/choking facades
  6. swarm-peer — per-peer connection facade
  7. swarm-dht, swarm-pex, swarm-lsd — peer-discovery facades
  8. swarm-utp, swarm-mse — transport / obfuscation facades
  9. swarm-session, swarmd, swarmctl — daemon / CLI facades
  10. conformance/ runner + first fixture: parse ubuntu-24.04.torrent, print metadata JSON

System boundaries. Provides: the full protocol stack listed above end to end. Delegates: DNS resolution, NAT/router firmware behavior, OS filesystem semantics, TLS trust roots (rustls + system verification, Phase 11), tracker operator policy, any private-tracker auth beyond passkey query-string secrets. Does not provide: a GUI, a DHT bootstrap node, seedbox hosting, IPFS bridging, private-tracker account management, or production-hardened WebTorrent (Phase 13 is a stretch phase only).

Non-goals. Anti-censorship guarantees beyond what MSE's obfuscation already buys; payment rails; content moderation or inspection — the daemon is content-agnostic by Principle P12/I10.

Deployment model. Single long-running daemon (swarmd) per host with a local Unix-socket control plane; libswarm is also consumable as an embedded library by a host process that wants no separate daemon.

Target users/operators. Systems engineers building or operating P2P file-distribution infrastructure, and on-call engineers debugging swarm behavior — not a consumer product.

What later phases unlock. Phase 6 unlocks a functioning leech/seed loop; Phase 9 unlocks magnet-only onboarding with no .torrent file; Phase 10 unlocks NAT-hostile networks (µTP) and DPI-hostile networks (MSE); Phase 12 unlocks v2/hybrid swarms; Phase 13 unlocks browser peers.

Language: Rust, edition 2021, MSRV 1.78. Rationale: the peer-connection state machine holds many short-lived buffers and per-peer mutable state under concurrent I/O; the borrow checker turns "peer state machine has a use-after-free" into a compile error, and tokio gives a task-per-connection model at a memory cost C++ requires hand-rolled reference counting to match (ADR-01). Rejected: C++ — libtorrent already owns the mature C++ reference implementation; re-deriving it in C++ teaches less than re-deriving it under a different memory model (ADR-01). Rejected: Go — GC pauses interact badly with the 10 s choke-tick determinism requirement (P4, ADR-02).

Prerequisites. Intermediate Rust (lifetimes, async, Pin, Send/Sync bounds, structured cancellation); BEP 3 read end to end; TCP/UDP socket programming; the Kademlia paper; RFC 6817; the understanding that MSE's RC4 is an obfuscation primitive, not a confidentiality one.

Estimated timeline. Phase 0 — 1 week. Full 14-phase system (through the BEP 52 / WebTorrent stretch) — 7–9 months at half-time for one engineer, 4–5 months at full-time with Phase 13 optional.

Deferred features (each anchored to the phase that would build it; all rows live in the Deferred Features Register, §39): BEP 16 super-seeding PhaseDeferred("§18"); BEP 32 IPv6 DHT PhaseDeferred("§20"); BEP 33 DHT scrape PhaseDeferred("§20"); BEP 42 DHT security extension PhaseDeferred("§20"); BEP 47 padding-file / extended attributes PhaseDeferred("§14"); BEP 7 IPv6 tracker extension PhaseDeferred("§15"); mTLS on the swarmd gRPC control API PhaseDeferred("§23"); WebTorrent production ICE/TURN hardening PhaseDeferred("§25").

2. Why Build This

BitTorrent is the most successful peer-to-peer protocol ever shipped, and almost every team that has tried to write a client from the spec alone has been bitten by something the spec does not say out loud: a tracker that returns a binary peers field instead of a dict-list and a client that panics on the wrong form; a peer that sends a bitfield with trailing bits set when the spec says they must be zero; a magnet link whose metadata never arrives because the ut_metadata handshake races the piece-request loop; a DHT node that answers with the wrong K-bucket because the routing-table split rule was implemented as "split any full bucket" instead of "split only the bucket that contains our own ID"; a µTP connection that deadlocks because LEDBAT ramped the window down to one packet and never recovered. The teams who debug those surprises in the bytes on the wire are the teams who built their own client end to end while reading the BEPs.

This project is the smallest stack that still teaches the full protocol surface: bencode, metainfo, trackers, the peer wire protocol, choking, the piece picker, storage, the DHT, magnet links, PEX, LSD, the fast extension, BEP 52, µTP, and MSE. It does not own a GUI, a DHT bootstrap node, or seedbox infrastructure. By the end of Phase 12 the reader understands exactly why libtorrent's piece_picker.cpp is shaped the way it is, exactly why qBittorrent's choke decisions land where they do, and exactly which bytes leave the socket in response to request 0x000003e8 0x00000000 0x00004000. There is nowhere left for magic to hide.

It is also small enough to actually finish: two transports (TCP, µTP), one DHT (Mainline), the BEPs enumerated in §5, and interoperability tested against three real clients (libtorrent, Transmission, qBittorrent) rather than an invented conformance target. That tight focus is why the timeline is months, not years.

This project cross-links to two siblings in the wider portfolio: any project implementing a gossip-based overlay (Chord/Pastry-style DHTs) reuses the XOR-metric/K-bucket reasoning of §8/§20 directly; any project implementing a custom wire protocol over TCP reuses the framed-codec and backpressure reasoning of §16 directly. The engineering muscles built here — a byte-exact wire codec, a congestion-controlled UDP transport, a trust-minimized DHT, and an incentive-compatible scheduling algorithm — recur in every serious distributed-systems project.

What Mastery Looks Like (competencies gained, each tied to a phase):

  • Can write a canonical-form serializer for any length-prefixed, sorted-dict wire format and explain why re-serialization breaks content-addressed identifiers (Phase 1/2).
  • Can design and defend a fixed-cadence, reciprocity-based scheduling algorithm against a "smarter" adaptive alternative (Phase 6, P4).
  • Can implement and debug a Kademlia routing table, including its non-obvious bucket-split rule and iterative lookup termination condition (Phase 8).
  • Can build a UDP-based reliable transport with delay-based congestion control and reason about its fairness contract with TCP (Phase 10).
  • Can design a trust boundary around a content-hash commitment so that untrusted peers can supply arbitrary bytes safely (Phase 9, I3).
  • Can operate a swarm-facing daemon: choose the metrics that matter, write the runbooks that matter, and reason about the failure modes that matter (Phase 11, §26–§28).

Data flows in one direction and back: bytes flow up from the socket through the wire protocol into the picker; verified pieces flow down from the picker into storage; requests flow back out. The transport is a trait (§11 Transport) with two implementations (TCP, µTP); the wire protocol and the choking algorithm cannot tell which one backs a given peer (P9). Every cross-cutting concern — bencode, hashing, bandwidth accounting — is owned by exactly one module and reached by trait or function call, never duplicated (P2, P11). swarmd composes the whole stack behind a Unix-socket control plane; swarmctl is a thin gRPC client with no protocol logic of its own. The DHT (Phase 8) and PEX/LSD (Phase 7) sit beside the tracker manager as independent peer-discovery sources feeding the same peer manager; none of them shares mutable state with the choking/picking core (I6).

The one defining property: the choke tick is the system's heartbeat. 6. Design Principles

  1. P1 — Wire correctness is the ground truth. Every peer message round-trips through a hand-coded encoder/decoder tested against fixtures captured from libtorrent and Transmission. Violating it: an encoder change that silently perturbs one byte breaks interop invisibly until a real swarm test catches it (§30 conformance gating).
  2. P2 — Bencode is a single module. One parser, one encoder, in swarm-bencode; every other crate reaches for it by call, never re-implements it. Violating it: two bencode implementations drift and produce two different infohashes for the same bytes (I2).
  3. P3 — The infohash is computed once. Captured at parse time from the raw byte range; never re-bencoded and re-hashed. Violating it: a "canonical" re-serialization of a non-canonical real-world .torrent computes the wrong infohash (I3, Phase 2 Pitfall).
  4. P4 — The choke tick runs every 10,000 ms, exactly. Not "approximately when convenient." The optimistic-unchoke slot rotates every 30,000 ms. Violating it: tit-for-tat reciprocity degrades in ways invisible below swarm sizes a unit test can reach (I4, Cohen 2003).
  5. P5 — Piece selection is the picker's property, not the peer's. A peer asks the picker "what next"; it never holds piece statistics itself. Violating it: rarity computation and endgame transition logic duplicate and diverge across peer connections.
  6. P6 — Storage is opaque to the peer. A peer calls storage.read/storage.write; it never opens a file descriptor itself. Violating it: sparse-file layout, mmap-vs-pwrite choice, and move-on-rename all become un-replaceable (§17 Phase 5).
  7. P7 — Hash verification gates every write. No unverified piece reaches a durable fsync. Violating it: a single malicious peer can poison the on-disk payload silently (I5).
  8. P8 — The DHT is a separate state machine. Its own UDP socket, its own task; shares state with the peer manager only through announce/lookup channels. Violating it: a DHT bug can stall a download, or vice versa (I6).
  9. P9 — The transport is a trait, not an enum. TCP and µTP both implement Transport; the peer state machine cannot branch on which one it holds. Violating it: choking/picking logic accretes transport-specific special cases (I7, MM5).
  10. P10 — Determinism is the default for tests. Randomness is seeded (StdRng), time is paused (tokio::time::pause) in every test; production code uses real time/entropy. Violating it: flaky tests mask real races (I8).
  11. P11 — Bandwidth is metered at the trait boundary, owned by the session. A request debits the upload accountant; a piece arriving credits the download accountant, at the session level, not per-peer. Violating it: per-peer accounting drifts from the session total (I9).
  12. P12 — Private torrents are quarantined at exactly one check point. info.private = 1 is checked once, at the session boundary, and propagated; subsystems never re-check it. Violating it: a private swarm silently leaks to DHT/PEX/LSD (I10).

These are enforced at the type level where possible (Transport, Storage, Picker traits) and by code review otherwise; §30 (Testing & Verification Strategy) names the exact test class that exercises each one.

8. Domain Model / Protocol / Data Model

Bencode grammar (EBNF). The wire encoding underlying every metainfo, tracker, and DHT message:

value      = integer | bytestring | list | dict ;
integer    = "i", ["-"], digit_nz, {digit}, "e" | "i0e" ;
bytestring = length, ":", byte, {byte} ;
length     = digit_nz, {digit} | "0" ;
list       = "l", {value}, "e" ;
dict       = "d", {bytestring, value}, "e" ;   (* keys sorted ascending by byte value *)
digit_nz   = "1" … "9" ;
digit      = "0" … "9" ;

Canonical-form rule (I3, P3): dict keys sorted ascending by raw byte value (not locale collation); no leading zeros on integers except i0e; no re-serialization of captured info-dict bytes. A dict with keys out of order, or a duplicate key, is Error::NonCanonicalDict — rejected, not repaired.

Peer-wire handshake (68 bytes, BEP 3):

[1 byte ] 0x13                     (length of "BitTorrent protocol")
[19 bytes] "BitTorrent protocol"
[8 bytes] reserved (extension bits, see table below)
[20 bytes] infohash (v1 SHA-1, or the v2 SHA-256 truncated to 20 bytes)

Malformed-input example: a peer sends bitfield as its second message (after an initial have). Per BEP 3/6, bitfield (or have-all/have-none) is legal only as the first message. The wire codec returns Error::UnexpectedBitfield; the peer connection closes without propagating any state change to the picker (I1, Phase 4 Edge Case).

Failure-path example: a piece message arrives whose SHA-1 does not match the metainfo's pieces entry. The verifier (I5) marks the piece Quarantined { failures: 1 }, attributes the bytes to the sending peer, and the picker re-issues the block to a different peer; after 3 failures from the same peer that peer is disconnected and banned for 1 hour (Phase 5 Failure Analysis, §26 Threat 3).

BitTorrent v2 (BEP 52) piece-layers model. The metainfo carries a top-level piece layers dict (sibling of info, keyed by 32-byte SHA-256 merkle root, value = concatenated layer-hashes at the granularity matching piece length), plus a per-file file tree leaf {"": {length, pieces root}} where pieces root is the SHA-256 merkle root over 16 KiB leaf blocks (zero-padded to a power of two). No BLAKE3 is used anywhere in BEP 52 — the spec mandates SHA2-256 for both the info-hash and the merkle tree.

DHT state machine (Phase 8 preview): Idle -> Bootstrapping -> Warm -> LookupInFlight -> Warm, where Bootstrapping pings the well-known routers, Warm means the routing table has ≥1 node per populated bucket range, and LookupInFlight is the iterative get_peers traversal of §20.

13. Phase 1 — Bencode Codec

1.1 Objectives

Deliver a byte-identical encode/decode pair against the libtorrent reference for every fixture in conformance/corpora/bencode/, implementing P2 (single bencode module) and laying the groundwork for I3 (infohash computed once from captured bytes).

1.2 Detailed Implementation Steps

Implement the EBNF grammar of §8 in swarm-bencode::decode/encode (ADR-03: hand-rolled, not bendy/serde_bencode). The decoder is a Parser<'a> { input: &'a [u8], position: usize } with one method per production (parse_int, parse_bytes, parse_list, parse_dict); it records byte-range offsets for every parsed value (consumed directly by Phase 2's locate_info_bytes, I3). The dict parser validates ascending byte-order key sort and rejects duplicates (Error::NonCanonicalDict, P2). The encoder emits BTreeMap iteration order (already ascending), no leading zeros, insertion-order lists — deterministic per input Value. A second, incremental "streaming" decoder (a state machine returning Status::NeedMore until a full value arrives) backs the peer-wire path in Phase 4, because TCP delivers fragments.

1.3 Deliverable

swarm_bencode::decode/encode pass every fixture in conformance/corpora/bencode/; cargo fuzz run bencode_decode runs clean for 300 s with zero crashes.

1.4 Acceptance Criteria

1,024/1,024 positive fixtures round-trip (encode(decode(x)) == x); 256/256 negative fixtures return the documented Error variant, none panic; cargo fuzz run bencode_decode -- -max_total_time=300 exits 0 with zero crash artifacts (M11 gate).

1.5 Conformance Fixtures

corpora/bencode/positive/*.bin (1,024: integers incl. zero/negative/i64 bounds, byte strings incl. empty/non-UTF-8/embedded-NUL, nested lists/dicts, real .torrent files) | corpora/bencode/negative/*.bin (256: i01e leading zero, 01:a leading-zero length, non-canonical dict d2:bbi0e1:ai0ee, truncated input, integer overflow) | fuzz/artifacts/* (crashes discovered by fuzzing, converted to permanent negative fixtures).

1.6 Pitfalls

The integer grammar is "one or more digits, no leading zeros, optional leading -, 0 itself legal, -0 illegal" — real-world .torrent files have shipped i-0e and must be rejected, not silently coerced to zero. Dict-key sort is by raw byte value, not locale string comparison — a key b"\xff" sorts after b"foo". The pieces field is a single byte string of length 20 * piece_count (or 32 * piece_count for v2); never list-decode it (Phase 0 Pitfall, recurring). A trailing byte after the top-level value is tolerated by BEP 3's own text ("files containing extra characters are tolerated") but rejected by our strict round-trip mode; a separate lenient mode (used only for .torrent parsing) tolerates and reports the byte count.

1.7 Performance Concerns

The decoder must avoid per-byte-string heap copies where possible — Value::Bytes currently copies into Vec<u8>; a future optimization (not required for Phase 1 gating) would slice into the original Bytes buffer instead. Streaming-decoder state must not re-scan already-consumed input on partial arrival (O(n) total across all NeedMore calls, not O(n^2)).

1.8 Edge Cases

Nested lists/dicts to depth 64 must not blow the call stack — the parser is recursive-descent with an explicit depth counter that errors (Error::TooDeep) past a 64-level bound rather than stack-overflowing. Integer values at i64::MIN/i64::MAX boundaries. A dict whose only key is the empty byte string.

1.9 Failure Analysis

A crash in the decoder is contained to the parsing call; no partial state escapes because decode returns Result and never mutates shared state before success. Fuzzing crashes are committed as regression fixtures (see 1.5 above) so a fix can never silently regress.

1.10 Operational Notes

swarm-bencode emits no runtime telemetry (it is a pure, allocation-light library); its correctness is entirely a build-time/CI gate (bencode.report.json bucket, §30).

Turn parsed bencode into a Metainfo (§11) and compute the infohash exactly once from the captured byte range (P3, I3, ADR-04), closing out the metainfo half of BEP 3 and BEP 52.

2.2 Detailed Implementation Steps

swarm_metainfo::parse_metainfo calls swarm_bencode::decode, locates the info value's original byte range via the offset side-table Phase 1 recorded (locate_info_bytes), and hashes that exact slice: SHA-1 for InfoHashV1 always; SHA-256 for InfoHashV2 when meta version == 2 is present (I3, ADR-04). Parse announce/announce-list (BEP 12 tiers; tier ordering semantics: tier i before i+1, shuffled within a tier at session start — full peer-exchange growth is §19/Phase 7's concern, not this phase's). Parse magnet URIs (BEP 9's xt=urn:btih: field is the only officially specified form the reader must trust; the widely deployed xt=urn:btmh: v2 multihash convention used by libtorrent/qBittorrent is accepted opportunistically but is not a ratified BEP — treat BEP 9 + BEP 52's hybrid-infohash rule as the normative path, §8). Parse the v2 file tree recursively into FileTreeNode, and the top-level piece layers dict (§8) into a side-table keyed by pieces_root, consulted lazily by Phase 12's hash-request handling.

2.3 Deliverable

swarm_metainfo::Metainfo::from_bytes parses every fixture in conformance/corpora/metainfo/ with infohash(es) matching the recorded reference value.

2.4 Acceptance Criteria

32/32 reference torrents (Ubuntu, Debian, Internet Archive, hybrid v1/v2, private, non-UTF-8 names, multi-file, single-file) infohash-match the published values byte-for-byte; magnet-link parsing handles all BEP-9-defined field permutations (xt, dn, tr repeatable, x.pe, ws) across 8 fixture URIs.

2.5 Conformance Fixtures

corpora/metainfo/v1/*.torrent, corpora/metainfo/v2/*.torrent, corpora/metainfo/hybrid/* (v1

  • v2 fields present, both infohashes verified) | corpora/metainfo/magnet/*.uri (8 permutations) | fixtures/metainfo/non_canonical_info.torrent (a real-world torrent whose info-dict keys are not strictly sorted — infohash must still match the on-disk bytes, not a "corrected" canonical re-encode).

2.6 Pitfalls

The info byte-range must be captured during parsing, never reconstructed by re-bencoding — some real-world torrents have non-canonical info dicts and the infohash is computed against the on-disk bytes (P3). Multi-file path entries are lists of byte strings; the OS path separator is not embedded — rebuild with PathBuf::push per element, and sanitize ./.. components (BEP 52 explicitly calls out directory-traversal sanitization for file tree keys). A hybrid torrent's meta version field is 2; pure v1 torrents conventionally omit it — meta version >= 3 is unknown and rejected, not silently accepted (Phase 0 fixture, recurring).

2.7 Performance Concerns

locate_info_bytes must be O(1) given the offset side-table from Phase 1, not a re-scan of the whole file. Parsing a 32 GiB torrent's pieces field (millions of 20-byte hashes for tiny piece lengths) must not copy the whole array more than once.

2.8 Edge Cases

A torrent whose total_length % piece_length == 1 (the shortest possible last piece) — the canonical off-by-one fixture used throughout this blueprint. A file tree whose root dictionary itself is (incorrectly) a file leaf — BEP 52 explicitly forbids this; reject with a named error. A magnet URI with both xt=urn:btih: and an unofficial xt=urn:btmh: — accept both, verify against whichever the metadata exchange (Phase 9) ultimately supplies.

2.9 Failure Analysis

An infohash mismatch (computed vs. expected, e.g., from a magnet link) never partially populates a Metainfo — parse-then-verify is atomic; a failed torrent is rejected whole, not accepted with a "best effort" partial structure that later code might trust.

2.10 Operational Notes

metainfo_infohash_mismatch_total (I3 telemetry) is the single most useful early-warning metric for a corrupted or adversarial .torrent/magnet source; alert on any nonzero rate sustained over 5 minutes.

15. Phase 3 — Tracker Client (HTTP + UDP)

3.1 Objectives

Implement both tracker transports (BEP 3 HTTP, BEP 15 UDP), BEP 12 multi-tracker tiers, and BEP 23 compact peer lists — the first live peer-discovery source.

3.2 Detailed Implementation Steps

HTTP: announce_http builds a GET with binary info_hash/peer_id percent-encoded byte-for-byte (not "safe-byte" heuristics some URL libraries apply), parses the bencoded response (AnnounceResponse, §11) including BEP 23's compact 6-byte peer form and BEP 7's 18-byte IPv6 form (BEP 7 itself deferred per §39, but the compact-peer parsing path handles both shapes now). UDP (BEP 15, ADR referenced inline): two-step connect (0x41727101980 magic + transaction_id, receive connection_id, valid 60 s) then announce (connection_id + fields packed big-endian); retry backoff is 15 * 2^n seconds, n = 0..=8 (BEP 15 mandate, not a tunable). TrackerTier (§11-adjacent internal type) holds shuffled-at-session-start URLs per tier; a successful announce moves that URL to the front of its tier (BEP 12). Scrape mirrors announce on both transports.

3.3 Deliverable

swarm_tracker::announce_http/announce_udp complete real announces against tracker.opentrackr.org and a local chihaya reference-tracker container.

3.4 Acceptance Criteria

100/100 sequential announces with synthetic random transaction IDs parse correctly; HTTP compact and dict peer-list forms both parse to the same Vec<SocketAddr>; a tracker failure reason response is propagated as an error, never retried within the same tier pass (BEP 15 backoff respected, verified against a fixture asserting no re-announce inside 15 s).

3.5 Conformance Fixtures

corpora/tracker/http/*.req-resp (dict form, compact form) | corpora/tracker/udp/*.req-resp (announce + scrape, IPv4 and BEP-7-shaped IPv6 compact peers) | fixtures/tracker/oversized.bin (a >1 MiB HTTP response, expect Error::ResponseTooLarge, capped by design).

3.6 Pitfalls

info_hash/peer_id are raw 20-byte binary, not hex — percent-encoding every byte (not just "unsafe" ones) is mandatory; several URL-encoding libraries under-encode and produce corrupt queries. UDP is unreliable — the 15 * 2^n backoff is not optional; re-announcing every second gets the client rate-limited or banned. The UDP connection_id is per-tracker-instance, not a durable session token — cache but do not assume permanence across tracker restarts. A failure reason response means "do not retry immediately," not "the network is down."

3.7 Performance Concerns

Cap HTTP tracker responses at 1 MiB (a popular torrent's dict-form peer list can be tens of KiB; anything past 1 MiB is refused and logged, §26 Threat 9 disk/memory-fill guard). UDP retries must not busy-loop; each retry is a scheduled timer, not a spin.

3.8 Edge Cases

A tracker that returns zero peers but interval: 1800 (valid — just an empty swarm at that moment). A multi-tracker tier whose every URL fails — the whole TrackerManager::announce returns Error::AllTrackersFailed, not a silent empty peer list. A UDP tracker whose connection_id expires mid-retry-sequence — reconnect transparently, do not surface the expiry as a user-visible error.

3.9 Failure Analysis

Total tracker unavailability degrades gracefully: DHT (Phase 8) and PEX/LSD (Phase 7) are independent peer-discovery sources per the architecture (§3), so a torrent continues finding peers with zero working trackers, at reduced discovery rate — verified in the interop suite (e2e.dht bucket without any tracker configured).

3.10 Operational Notes

swarmd_tracker_announce_latency_seconds{tracker} (histogram) is the primary tracker-health signal; the runbooks/tracker-outage.md runbook walks the on-call through confirming outage via the multi-tracker tier list before escalating.

16. Phase 4 — Peer Wire Protocol

4.1 Objectives

Implement the BEP 3 handshake and message frame, BEP 6's fast extension, and BEP 10's extension protocol envelope — the first live peer-to-peer byte exchange (P1, I1, ADR-15 for Bytes buffers).

4.2 Detailed Implementation Steps

handshake_outbound/handshake_inbound implement the 68-byte exchange of §8 exactly, validating the protocol string, comparing infohash, and rejecting self-connects (peer_id equals our own). WireCodec (a tokio_util::codec::Encoder/Decoder pair) implements the [4-byte length][1-byte opcode][payload] frame (§8 opcode table) with MAX_MESSAGE_SIZE = 16 MiB + 64 B (P1, I1). BEP 6 support is negotiated via reserved[7] & 0x04; have-all/have-none replace bitfield when both peers signal it. BEP 10's extended (opcode 20) carries a bencoded handshake dict with m (extension-name → local id map), p (listen port), v (client version string), and reqq (max outstanding requests, libtorrent default 250) — per the verified BEP 10 text, metadata_size is not a BEP-10 field; it belongs to BEP 9's ut_metadata namespace and is handled in Phase 9. The per-peer connection runs as one Tokio task (P9, ADR-02) owning its Transport, WireCodec, and PeerState (§11), selecting between inbound frames, an outbound channel, and a 120 s keep-alive timer.

4.3 Deliverable

The codec round-trips every fixture in corpora/wire/; a peer connection exchanges a single verified piece end-to-end against a libtorrent reference container in docker-compose.yml.

4.4 Acceptance Criteria

100% of corpora/wire/*.bin round-trip through encode+decode; the handshake test suite rejects mismatched protocol string, mismatched infohash, and self-connect in 3/3 dedicated fixtures; a malformed mid-stream bitfield (sent as the second message) closes the connection within one codec tick, verified by fixtures/wire/late_bitfield.bin.

4.5 Conformance Fixtures

corpora/wire/*.bin (every opcode, valid and boundary-length payloads) | corpora/wire/handshake/*.bin (byte-exact reference handshakes) | fixtures/wire/late_bitfield.bin, fixtures/wire/self_connect.bin, fixtures/wire/oversized_piece.bin (a piece claiming a length past MAX_MESSAGE_SIZE).

4.6 Pitfalls

Length prefix is big-endian u32 — the native-endian path is wrong on every architecture worth caring about. bitfield/have-all/have-none are legal only as the very first post-handshake message (BEP 3/6 both say so); a peer sending one mid-stream is malformed. A request for a piece not yet had, or a block past the piece boundary, is malformed — some clients fuzz exactly this. The piece payload length is block_length bytes, not frame_length - 9; an off-by-9 bug has shipped in real clients and silently corrupts the last block of a piece.

4.7 Performance Concerns

bytes::Bytes (ADR-15) avoids a copy from socket buffer through to the hashing path in Phase 5; a Vec<u8>-per-message design would double allocator pressure at 4,000 concurrent connections (§4 FD/memory budget). Keep-alives are cheap but mandatory — clients drop silent connections after ~2 minutes.

4.8 Edge Cases

A peer that never sends bitfield/have-all/have-none at all (a peer with zero pieces may legally skip it, per BEP 3). A peer whose reserved bytes claim BEP 6 support but which then sends a pre-fast-extension bitfield mid-stream anyway (malformed regardless of the flag). Two simultaneous inbound+outbound connection attempts to the same peer (BEP 3's tolerated but discouraged case) — the second is dropped once the infohash+peer_id pair matches an existing connection.

4.9 Failure Analysis

Any wire-protocol violation is contained to the one connection: the task returns Err, the connection closes, and no partial state reaches the picker or storage (I1, I5's principle extended one layer up). Blast radius is one peer slot freed for reconnection, never a process-wide fault.

4.10 Operational Notes

Per-connection spans (peer.handshake, peer.bitfield, peer.request, peer.piece) are OpenTelemetry-instrumented from this phase forward (ADR-13); swarmd_peers_connected{infohash} and swarmd_peers_choked{direction} are the two gauges an operator watches first when a torrent looks stalled.

17. Phase 5 — Storage & Hash Verification

5.1 Objectives

Implement the sparse-file storage backend and the SHA-1 verifier gate (P6, P7, I5, I11) — no piece reaches disk unverified, and no verified piece is lost to a crash.

5.2 Detailed Implementation Steps

swarm-storage::sparse pre-allocates the full file at first-piece verification using fallocate(FALLOC_FL_KEEP_SIZE) (Linux), posix_fallocate (macOS), or SetFileValidData (Windows) — ADR-10. Reads are direct pread; writes are direct pwrite followed by fsync only at piece boundaries, never per-block (I11) — libtorrent's disk_io_thread.cpp learned in 2014 that mmap'd writes silently corrupt under page-cache eviction, so mmap is reserved for read-only seeding paths, never writes (P6, Reference Implementations §5). swarm-storage::verify implements verify_piece_v1 (SHA-1 against the metainfo's pieces entry, constant-time compare) sitting directly between the wire codec and the storage write path (P7, I5) — there is no code path from Message::Piece to Storage::write that skips it. swarm-storage::resume persists per-torrent bitfield/partial-piece state to sled (ADR-05); on daemon startup every torrent's bitfield is re-verified against on-disk bytes and any piece whose hash no longer matches resets to Missing (I11).

5.3 Deliverable

An end-to-end test downloads the Ubuntu ISO from the public swarm and the resulting file's SHA-256 matches the published value; a crash-recovery test (kill -9 mid-write, restart) leaves zero corrupted-but-marked-Complete pieces.

5.4 Acceptance Criteria

The verifier passes 1,024/1,024 v1 piece fixtures including the last-piece-shorter-than- piece_length pathological case; resume-verify on a 32 GiB torrent completes in ≤ 60 s on NVMe (M8); zero pieces marked Complete survive a simulated crash without re-verification (I11 gate, fixtures/storage/crash_mid_write.bin).

5.5 Conformance Fixtures

corpora/verify/v1/*.bin (1,024 piece fixtures) | fixtures/storage/last_piece_short.bin (total_length % piece_length == 1) | fixtures/storage/crash_mid_write.bin (simulated kill-and-restart) | tests/integration/test_storage.rs (sparse-file allocation across Linux/ macOS/Windows CI runners).

5.6 Pitfalls

fsync per block costs 5–10 ms and crushes throughput — fsync only at piece boundaries after verification passes; the resume-verify pass recovers any partial piece a crash left behind. Memory-mapped writes silently corrupt under page-cache eviction on memory-pressured hosts — this is a directly documented libtorrent 2014 lesson (Reference Implementations §5), not a hypothetical. The last piece of a torrent is shorter than piece_length; every piece-byte- arithmetic code path must account for it (the second-most-common BitTorrent client bug class).

5.7 Performance Concerns

Resume-verify parallelizes hashing across pieces (bounded by CPU core count) to hit the 60 s/ 32 GiB target (M8); sequential single-threaded verify would miss the target by 4–8x on typical NVMe read bandwidth. Sparse-file allocation must not zero-fill the whole file (defeats the point of sparseness) — FALLOC_FL_KEEP_SIZE reserves space without writing zeros.

5.8 Edge Cases

A piece write that lands exactly at a file-boundary in a multi-file torrent (the write spans two underlying files). A resume database that is present but references a torrent no longer in the session's registry (orphaned resume state — logged and pruned, not silently kept forever). A disk that fills mid-write — Storage::write must surface Error::DiskFull distinctly from a generic I/O error so the picker can stop requesting rather than retry-loop.

5.9 Failure Analysis

A hash-verification failure quarantines the piece (PieceStatus::Quarantined) and attributes it to the contributing peer; three quarantine events from the same peer within one torrent trigger a 1-hour ban (§26 Threat 3). This is the canonical failure-path example of §8: bad bytes never reach durable storage, and blame is attributable per-peer, not swarm-wide.

5.10 Operational Notes

swarmd_pieces_failed_hash_total{infohash} and resume_partial_pieces_total are the two metrics that distinguish "a peer is lying" (rising failed-hash counter, one peer) from "we crashed and are recovering" (a one-time burst of partial pieces at startup, all peers). The dht-cold-start.md runbook is unrelated; storage recovery has no dedicated runbook because the resume-verify pass is fully automatic and requires no operator action (§28).

18. Phase 6 — Piece Selection & Choking

6.1 Objectives

Implement Cohen tit-for-tat choking (P4, I4, Cohen 2003) and rarest-first piece selection with endgame (P5, Legout 2006) — the two algorithms that make a BitTorrent swarm cooperative rather than a free-for-all.

6.2 Detailed Implementation Steps

swarm-choke::tick runs on a tokio::time::interval(10_000ms) with MissedTickBehavior::Skip (I4, P4): sort peers that are peer_interested by download rate to us over the trailing 20 s, unchoke the top 4, optimistically unchoke one additional peer via weighted-random selection (newly-connected peers get 3x weight per Cohen 2003), rotate the optimistic slot every 30,000 ms, choke everyone else. A seed (nothing left to download) subsorts by upload rate from us instead. swarm-picker::rarest computes availability counts from Have/Bitfield messages and picks the least-available piece a given peer has that we lack (P5); the first four pieces are chosen at random rather than rarest-first (BEP 3's explicit "random first piece" recommendation, avoiding a swarm-wide race for one rare piece at start-up). swarm-picker::endgame triggers at 95% completion: every outstanding block is requested from every peer that has it, and cancel is sent the instant a block arrives from any source — a one-way transition, per Legout 2006's validation that this trade (bandwidth for tail latency) is worth making exactly once, late. swarm-picker::sequential and ::priority implement opt-in streaming order and per-file {Skip,Low,Normal,High} weighting (4x/0.25x in the rarity sort) respectively.

6.3 Deliverable

A swarm-simulation test with 8 simulated peers competing for 4 unchoke slots converges to a stable equilibrium within 100 ticks; an end-to-end Ubuntu-ISO download completes with a verified final hash.

6.4 Acceptance Criteria

The choke-tick simulation converges (unchoked set stabilizes) within 100 ticks in 100/100 seeded runs (P10 determinism); the picker matches a reference implementation byte-for-byte across 64 piece-availability snapshot fixtures; endgame tail latency (last piece after entering endgame) is < 30 s at p99 on the reference 100-seeder swarm (M7).

6.5 Conformance Fixtures

corpora/choke/scenario-*.bin (choked-set after 100 ticks, compared to reference) | corpora/picker/snapshot-*.bin (64 availability snapshots) | fixtures/picker/random_first_piece.bin (asserts the first 4 picks are not rarest-first) | fixtures/picker/endgame_transition.bin (95%-completion trigger point).

6.6 Pitfalls

The choke tick must fire at exactly 10,000 ms, not "8–12 seconds" — drift mis-ranks peers and breaks reciprocity in ways invisible below real swarm sizes (I4). Skipping "random first piece" starves the whole swarm (including yourself) racing for piece zero — BEP 3 is explicit; Piatek 2007's critique of tit-for-tat exploitability is a useful caution here too (a too-clever picker can be gamed the same way a too-clever choke algorithm can). Endgame's cancel storm can saturate uplink — cap cancellations to 32/s/peer.

6.7 Performance Concerns

The choke-tick wall-clock cost must stay under 10 ms at p99 even at 4,000 connections (M2) — the sort-by-rate step is O(peers log peers) per torrent per tick, bounded by the §4 peer-count ceiling. The picker's rarity sort is recomputed incrementally on Have arrival, not recomputed from scratch every request.

6.8 Edge Cases

A peer that is a seed itself (nothing to request from) still participates in choke-tick sorting by upload rate. A torrent at exactly 95.0% completion oscillating in and out of endgame due to a requeued failed piece — endgame entry is one-way and does not re-evaluate the threshold once entered (per 6.2 above). Sequential mode's random-first-piece override becomes "piece zero, not random" — the picker carries an explicit mode flag, not an inferred one.

6.9 Failure Analysis

A picker bug that requests the same block from two peers simultaneously outside endgame wastes bandwidth but cannot corrupt data — the verifier (I5) is the actual safety net; the picker bug would show up as elevated swarmd_bytes_downloaded_total relative to unique bytes written, a detectable operational signal (§28).

6.10 Operational Notes

swarmd_choke_tick_duration_seconds (p99 budget 10 ms, M2) and swarmd_endgame_active{infohash} are the two gauges that distinguish "the swarm is healthy but slow" from "the choke tick itself is falling behind schedule," which is the P4/I4 violation signal operators must never ignore.

19. Phase 7 — Peer Exchange & Local Service Discovery

7.1 Objectives

Implement BEP 11 (PEX) and BEP 14 (LSD) as tracker-independent peer-discovery sources, both quarantined for private torrents at the single session-boundary check (P12, I10).

7.2 Detailed Implementation Steps

swarm-pex rides BEP 10's extension protocol under the name ut_pex; every 60 s each connected peer exchanges added/added.f (compact peer + flags: 0x01 MSE, 0x02 seed, 0x04 µTP, 0x08 BEP-55 holepunch support) and dropped (plus the added6/dropped6 IPv6 forms), capped at 50 entries per direction per round to bound amplification (P12 does not apply here — the cap is an independent anti-amplification control, §26 Threat 6). swarm-lsd broadcasts a BT-SEARCH HTTP-like message over UDP multicast to 239.192.152.143:6771 (IPv4) / [ff15::efc0:988f]:6771 (IPv6) every 5 minutes per torrent, carrying Infohash and a random 8-byte cookie used to filter our own announces. Both subsystems check Metainfo.info.private exactly once, at the point they would otherwise register a torrent for exchange (P12, I10) — the check is not repeated inside either subsystem's hot path.

7.3 Deliverable

swarm-pex exchanges messages with a libtorrent reference peer and the resulting peer set is a strict superset of the tracker-supplied list; swarm-lsd discovers a peer across two docker-compose containers sharing an LSD multicast group.

7.4 Acceptance Criteria

A private torrent's PEX and LSD messages are asserted never sent in 100/100 fixture runs (I10 gate); PEX peer sets from a 10-minute simulated session match a reference implementation's set within one exchange round; incoming PEX messages above 200 entries or 50/minute/peer close the connection (§26 Threat 6 enforcement).

7.5 Conformance Fixtures

fixtures/pex/private_torrent_leak_test.bin (asserts zero PEX/LSD traffic) | fixtures/pex/amplification_probe.bin (a peer sending 500-entry PEX, expect disconnect) | tests/interop/test_lsd.rs (two-container multicast discovery).

7.6 Pitfalls

LSD multicast is blocked by many home routers and most datacenter networks — the fallback is silent by design (logging every failed multicast send would flood the log at 5-minute intervals across hundreds of torrents). PEX dropped/added lists can list the same peer in both sets within one window (dropped-then-re-added) — the receiver de-dupes on the latest event, not first. A misbehaving peer amplifying via huge PEX lists is the exact reason for the 200-entry/50-per- minute cap (§26 Threat 6).

7.7 Performance Concerns

PEX/LSD traffic is bounded and periodic (60 s / 5 min cadences), never a hot path relative to the 10 s choke tick or per-block wire traffic — no dedicated performance target beyond staying under the entry caps above.

7.8 Edge Cases

A peer that supports PEX but never sends an initial exchange (some clients delay the first round past 60 s) — treated as "no PEX peers yet," not an error. An LSD cookie collision between two unrelated local daemons on the same subnet (astronomically unlikely at 8 random bytes, but the receiving side degrades gracefully — a false self-filter just means one legitimate LSD peer is missed for one 5-minute cycle).

7.9 Failure Analysis

A compromised or malicious PEX peer can at worst pollute the local peer-discovery cache with bad addresses, which the peer manager's own connection-attempt/backoff logic (Phase 4) filters naturally — bad addresses simply fail to connect and age out, never crash the daemon.

7.10 Operational Notes

Neither subsystem exposes a dedicated metric beyond the shared swarmd_peers_connected gauge; per-discovery-source attribution is not required by any acceptance criterion in this phase.

20. Phase 8 — Mainline DHT (Kademlia)

8.1 Objectives

Implement Mainline DHT (BEP 5) on Kademlia's XOR-metric routing table (Maymounkov & Mazières 2002) — the peer-discovery source that survives a total tracker outage (P8, I6, I12).

8.2 Detailed Implementation Steps

swarm-dht::routing::RoutingTable is a binary trie of Buckets, K = 8 nodes each (Kademlia paper); only the bucket that contains our own NodeId is permitted to split on overflow — every other full bucket evicts its least-recently-seen node after a failed ping (I12; this is the single most consequential subtlety in the whole DHT, and the naïve "split any full bucket" rule produces a routing table that is wrong but plausible-looking, see 8.6 below). swarm-dht::rpc implements the four bencoded RPCs (ping, find_node, get_peers, announce_peer) per BEP 5. Token issuance for announce_peer rotates every 5 minutes: token = sha1(current_minute || requester_ip || secret), accepted for the current or previous minute (a 5–10 minute validity window with no per-requester state, plus a 60 s clock-skew tolerance). swarm-dht::bootstrap pings the well-known routers (router.bittorrent.com:6881, router.utorrent.com:6881, dht.transmissionbt.com:6881, dht.libtorrent.org:25401) and issues find_node for our own ID to seed the table. swarm-dht's iterative get_peers lookup dispatches parallel queries (α is a conventional concurrency parameter from Kademlia-paper practice, not a BEP-5 mandate; we fix it at 3) against a shortlist of the K closest known nodes, terminating when the K closest have all responded with no closer node returned, or a wall-clock deadline fires.

8.3 Deliverable

The DHT bootstraps to a queryable routing table in under 60 s against the canonical routers; a get_peers lookup for the Ubuntu ISO's infohash returns ≥50 peers within 5 s at p99.

8.4 Acceptance Criteria

The routing-table conformance test passes 1,024/1,024 random add_node operations with bucket invariants intact (no duplicate IDs, ≤8 nodes/bucket, only the self-spanning bucket ever splits — I12 gate); DHT bootstrap completes in ≤ 60 s (M-dht); popular-infohash lookup p99 < 1 s, arbitrary- infohash lookup p99 < 5 s (M3/M4).

8.5 Conformance Fixtures

corpora/dht/*.bin (bencoded query/response byte-exact fixtures) | property-based routing-table test, 100,000 proptest iterations | fixtures/dht/bucket_split_naive_trap.bin (a sequence that fails under the "split any full bucket" anti-pattern but passes under I12's correct rule — this fixture exists specifically to catch that regression).

8.6 Pitfalls

The bucket-split rule (8.2 above) is the load-bearing subtlety — implementing "split any full bucket" instead of "only the bucket containing our own ID" produces a routing table that looks reasonable under casual testing but converges to the wrong shape at scale. BEP 5's RPC error format is {"y":"e","e":[code, message]} — the message is a list, not a bare string; some deployed clients send the wrong shape and we accept both for compatibility while emitting the correct form. Token validity needs a clock-skew tolerance (60 s is conventional) or a fast-clocked node rejects our otherwise-valid tokens. announce_peer with implied_port=1 means "use the UDP source port," not the explicit port field — NAT-traversal logic depends on respecting this.

8.7 Performance Concerns

α fixed at 3 balances lookup latency against per-lookup network burst (Kademlia-paper informal guidance) — making it configurable per-torrent is a footgun (too small stalls lookups, too large bursts the network, §4 RTT assumption of 20–250 ms). Routing-table lookups (closest_nodes) must be O(log N) in the bucket trie, never a linear scan of all 1,280 possible node records (I12).

8.8 Edge Cases

A find_node response containing a node whose ID collides with an already-known node at a different address (address change — update, do not duplicate). A get_peers response mixing both values (peers) and nodes (closer nodes) in one reply (tolerate; some deployed implementations do this even though it is non-canonical). Bootstrap when all five canonical routers are simultaneously unreachable — the daemon logs a cold-start failure and retries with exponential backoff rather than blocking indefinitely (runbooks/dht-cold-start.md).

8.9 Failure Analysis

A poisoned or Sybil-heavy neighborhood in the routing table degrades lookup quality but cannot corrupt data (DHT-sourced peers pass through the same handshake/hash-verification gates as any other peer, I1/I5) — the DHT is a hint source, never a trust source (§26 Threat 5, MM3).

8.10 Operational Notes

swarmd_dht_routing_table_size (gauge, target range per I12: up to 1,280) and swarmd_dht_lookup_latency_seconds (histogram, M3/M4 gate) are the two signals distinguishing "the DHT is cold" (near-zero table size after restart, see runbooks/dht-cold-start.md) from "lookups are just slow" (populated table, high latency histogram tail).

21. Phase 9 — Magnet Links & Metadata Exchange

9.1 Objectives

Implement BEP 9 (ut_metadata) so a magnet link — an infohash with no metainfo — resolves to a verified Metainfo (MM8: a magnet link is a hash-addressed promise, not a location).

9.2 Detailed Implementation Steps

Once a peer's BEP 10 handshake advertises ut_metadata in its m dict, we request the info-dict in 16 KiB chunks: {"msg_type":0,"piece":N} (request), answered with {"msg_type":1,"piece":N, "total_size":T} followed by the raw chunk bytes, or {"msg_type":2,"piece":N} (reject). We pipeline up to 16 outstanding chunk requests across every metadata-capable peer; the first chunk back from any peer fills that gap (§8 worked-example pattern extended to metadata). After every chunk arrives, assemble_and_verify concatenates them and hashes the result — SHA-1 against the magnet's xt=urn:btih:, and SHA-256 against a xt=urn:btmh: hash if present (I3's "computed once, from captured bytes" extends here: the assembled bytes are hashed exactly as received, never re-bencoded first). A peer whose chunk fails the hash check is disconnected and its bytes discarded — the trust boundary is the hash comparison, not the peer's honesty (Phase 2 Failure Analysis, extended).

9.3 Deliverable

Given the Ubuntu ISO magnet link, metadata resolves in under 10 s at p99 against the public swarm; a hybrid v1/v2 magnet resolves and verifies against both hash forms.

9.4 Acceptance Criteria

Metadata fetch p99 < 10 s against the public swarm (M5); a peer supplying a chunk that fails hash verification is disconnected within one codec tick, verified by fixtures/metadata/poisoned_chunk.bin; a hybrid magnet successfully verifies both the truncated v2-derived and (if present) v1 SHA-1 forms in 100% of corpora/metainfo/hybrid_magnet/* fixtures.

9.5 Conformance Fixtures

fixtures/metadata/poisoned_chunk.bin (one chunk deliberately corrupted) | fixtures/metadata/metadata_size_absent.bin (peer omits metadata_size; infer piece count from the first response instead) | corpora/metainfo/hybrid_magnet/* (both-hash-form verification).

9.6 Pitfalls

metadata_size is conventionally present in the BEP-10 handshake of ut_metadata-capable peers but some clients omit it — infer it from the total_size field of the first chunk response instead of assuming its absence is fatal. A peer can advertise ut_metadata support and then reject every request — rate-limit to one metadata request per peer per 30 s and tolerate the rejection rather than banning immediately (it may simply not have the metadata yet). The 16 KiB chunk size is convention, not a BEP-9 mandate; trust the byte length actually returned, never assume it.

9.7 Performance Concerns

Pipelining 16 outstanding requests across all metadata-capable peers is what makes the p99 < 10 s target (M5) achievable against a swarm with variable per-peer latency — a strictly sequential one-chunk-at-a-time fetch would be dominated by the single slowest peer.

9.8 Edge Cases

A magnet link whose swarm has zero metadata-capable peers at the moment of the first attempt (retry with backoff, do not fail permanently after one pass). A metadata_size claim of an implausibly large value (e.g., 1 GiB) — capped at 16 MiB (every legitimate info dict is well under this; §26 Threat 8 disk/memory-fill guard). Two peers supplying conflicting bytes for the same chunk index — the first hash-verified-consistent assembly wins; a peer whose bytes are later found inconsistent with the verified whole is treated exactly like a poisoned-chunk sender.

9.9 Failure Analysis

A stalled metadata fetch (all peers rejecting or absent) is operator-visible as "torrent stuck in MetadataFetching state" — distinct from Stalled (a torrent with metadata but no willing peers), so the on-call does not confuse the two failure classes (runbooks/stuck-torrent.md).

9.10 Operational Notes

Metadata-fetch state is a distinct, observable torrent lifecycle state (MetadataFetching -> Stalled -> Downloading -> Seeding, surfaced via swarmctl status --watch, Phase 11) so an operator can distinguish "we don't know what this torrent even is yet" from every later failure mode.

22. Phase 10 — µTP Transport & MSE Obfuscation

10.1 Objectives

Implement µTP/LEDBAT (BEP 29, RFC 6817) and MSE/PE (BEP 8) as a second Transport implementation (P9, I7, MM5, MM6) — NAT-hostile and DPI-hostile network support, without the peer state machine or picker/choke logic ever knowing which transport backs a connection.

10.2 Detailed Implementation Steps

swarm-utp::packet implements the header layout (type:4|version:4, extension byte, 2-byte connection_id, 4-byte timestamp_us, 4-byte timestamp_diff_us, 4-byte wnd_size, 2-byte seq_nr/ack_nr) over ST_SYN/ST_STATE/ST_DATA/ST_FIN/ST_RESET. swarm-utp::ledbat implements RFC 6817's window law: the congestion window grows when measured one-way queuing delay sits below target = 100 ms and shrinks when above it, using the minimum observed one-way delay over a trailing 2-minute window as the delay baseline (real clocks drift ~20 µs/s, so a naive "delay since last packet" baseline diverges) — this is a background transport that yields to TCP by design (RFC 6817, MM6), not a bug to "fix" by raising the target. Selective ACK (extension type 1) is implemented from the start; without it, one lost packet stalls the whole pipeline. swarm-mse implements the BEP-8 Diffie-Hellman (768-bit fixed prime, G=2) handshake followed by RC4 stream encryption with the first 1,024 bytes of keystream discarded on both sides (the standard RC4/FMS mitigation) — crypto_provide/crypto_select negotiate plaintext (0x01) vs. RC4 (0x02); RC4 is documented here, per BEP 8's own community specification, as an obfuscation primitive against deep-packet inspection, never a confidentiality primitive.

10.3 Deliverable

A µTP-only connection between two swarmd instances downloads a 1 GB test torrent in under 90 s on a 100 Mbps link; an MSE-encrypted handshake completes against a qBittorrent peer configured to require encryption.

10.4 Acceptance Criteria

µTP-only 1 GB download completes in < 90 s at 100 Mbps (M-utp fixture); MSE handshake succeeds against a require-encryption qBittorrent peer in tests/interop/test_mse.rs; the selective-ACK extension recovers from a single simulated packet loss without a full-window stall, verified by fixtures/utp/single_loss_recovery.bin.

10.5 Conformance Fixtures

fixtures/utp/single_loss_recovery.bin | fixtures/utp/clock_skew_20us.bin (simulated drifting clock, asserts LEDBAT does not ramp to a 1-packet window) | tests/interop/test_mse.rs (real qBittorrent container) | fixtures/mse/rc4_drop1024_vector.bin (known-answer test for the keystream-discard step).

10.6 Pitfalls

Clock skew is the worst part of LEDBAT in practice — using the raw instantaneous one-way-delay measurement as the baseline instead of a trailing-minimum causes the window to ramp toward one packet and never recover; this is the single most-reported µTP "hang" bug across every implementation that has shipped it. Forgetting the RC4-drop-1024 step produces a stream that decrypts wrong against every compliant peer — a silent, total interop failure, not a partial one. UPnP IGD discovery sends multicast SSDP that some captive-portal networks intercept and answer with a captive-page redirect — validate the SSDP response is a genuine IGD service description before issuing the port-mapping call.

10.7 Performance Concerns

LEDBAT's whole design point is yielding bandwidth to competing TCP flows (RFC 6817, MM6) — a µTP transfer's throughput should drop when TCP traffic appears on the same link; this is correct behavior, not a performance regression, and must not be "fixed" by loosening the target delay.

10.8 Edge Cases

A µTP connection whose peer never sends ST_STATE in response to our ST_SYN (handshake timeout, distinct from a mid-stream stall). Both sides of a holepunch (BEP 55, requires BEP 10 + BEP 29 per its own spec) attempting a ST_SYN simultaneously — BEP 55 explicitly notes this can happen and both attempts are allowed to succeed. An MSE peer that negotiates crypto_select inconsistent with what it advertised in crypto_provide (protocol violation — close connection).

10.9 Failure Analysis

A µTP window collapse (LEDBAT misbehavior) degrades throughput on that one connection only; other connections (TCP or separate µTP sockets) are unaffected because congestion state is per- connection, never shared (I7's transport-opacity principle applied to failure isolation as well as API shape).

10.10 Operational Notes

swarmd_utp_cwnd_bytes{peer} (gauge) is the metric that distinguishes "this one µTP peer is window-collapsed" (near-zero, flat) from "the whole link is just slow" (all peers, TCP and µTP, show reduced throughput); swarmd_mse_handshakes_total{outcome} tracks encrypted-handshake success/failure rates for spotting a DPI-hostile network segment.

23. Phase 11 — Daemon, CLI & Observability

11.1 Objectives

Package the stack as swarmd (long-running daemon) and swarmctl (CLI), with metrics, tracing, and runbooks — the phase that makes the system operable, not just correct (ADR-11, ADR-12, ADR-13).

11.2 Detailed Implementation Steps

swarmd parses /etc/swarmd/config.toml, opens listen ports (default 6881 TCP/UDP), negotiates UPnP IGD/NAT-PMP (ADR-16, best-effort — falls back to PEX/DHT-only inbound discovery), loads the sled resume database (ADR-05), spawns one task per torrent plus the DHT/LSD/PEX subsystem tasks (P8, I6 — independent tasks, no shared locks), and exposes a gRPC API on /run/swarmd.sock (mode 0600, ADR-11) for swarmctl. Prometheus metrics (swarmd_torrents_total{status}, swarmd_peers_connected{infohash}, swarmd_pieces_completed_total{infohash}, swarmd_bytes_uploaded_total{infohash}, swarmd_bytes_downloaded_total{infohash}, swarmd_dht_routing_table_size, swarmd_dht_lookup_latency_seconds, swarmd_tracker_announce_latency_seconds{tracker}, swarmd_choke_tick_duration_seconds, swarmd_endgame_active{infohash}, swarmd_utp_cwnd_bytes{peer}, swarmd_mse_handshakes_total{outcome}) are exposed on :9091/ metrics (ADR-12); OpenTelemetry spans (ADR-13) wrap torrent.add, tracker.announce, dht.lookup, peer.handshake/bitfield/request/piece, verify.piece, storage.write, and choke.tick. swarmctl (add, list, status, peers, pieces, stats --watch, pause, resume, remove, set-priority) is a thin gRPC client with zero protocol logic (ADR-11). Four named runbooks (docs/runbooks/triage.md, stuck-torrent.md, dht-cold-start.md, tracker-outage.md) codify the on-call's first ten minutes for each failure class.

11.3 Deliverable

swarmctl add <magnet> followed by swarmctl status <infohash> --watch shows a torrent transitioning MetadataFetching -> Stalled -> Downloading -> Seeding end to end against the public swarm; /healthz returns 200 once the daemon is running with the resume DB loaded.

11.4 Acceptance Criteria

/metrics exposes all 12 named metrics above; a Grafana dashboard JSON in ops/grafana/ graphs torrents-by-status, peers-connected, bytes/sec up/down, DHT lookup p99, tracker announce p99, and choke-tick p99; a 24-hour soak run shows zero unhandled panics and zero unbounded memory growth (M10 gate, benchmarks/results/soak/24h.json).

11.5 Conformance Fixtures

tests/e2e/test_daemon.rs (full add→download→seed cycle) | tests/grpc.rs (every gRPC method against a recorded fixture) | docs/architecture/trace-example.json (a captured OpenTelemetry trace covering one full torrent lifecycle).

11.6 Pitfalls

UPnP IGD discovery's multicast SSDP request can be answered by a captive-portal network with a fake service description (Phase 10 Pitfall, recurring) — validate before trusting. A Unix socket left world-writable (not mode 0600) turns the local control plane into a local-privilege- escalation surface for any co-resident user (§26 Threat 10). Exposing /metrics on a non-loopback interface without any access control leaks per-torrent infohash and peer-count information to the network.

11.7 Performance Concerns

50,000 total peers across 200 torrents must fit the M6 budget (< 50% CPU, < 4 GiB RSS) — the metrics/tracing overhead itself must stay a small fraction of that budget; span sampling (not 100% trace capture) is the lever if tracing overhead grows unacceptable at scale.

11.8 Edge Cases

A swarmctl command issued while swarmd is mid-restart (the Unix socket briefly absent) — swarmctl retries with a bounded backoff and a clear "daemon unavailable" message, not a raw connection-refused stack trace. A config file with an invalid listen-port range — rejected at startup with a specific error, never silently falling back to an unconfigured default port.

11.9 Failure Analysis

A daemon crash loses in-flight (unfsynced) block data only — every piece boundary already fsync'd survives (I11) and the resume-verify pass on restart (Phase 5) reconstructs exact state within the M8 time budget; RTO for 200 torrents is ≤ 30 s (§4).

11.10 Operational Notes

runbooks/triage.md is the canonical first-ten-minutes checklist (/healthz, /metrics, last 100 structured log lines, active torrent count, DHT routing-table size); every other runbook assumes triage has already narrowed the failure class.

24. Phase 12 — BitTorrent v2 (BEP 52)

12.1 Objectives

Implement BEP 52 in full: SHA-256 info-hash, the file tree + piece layers metainfo shape, the merkle-tree hash-exchange wire messages, and hybrid v1/v2 swarms (ADR-04, ADR-09).

12.2 Detailed Implementation Steps

The v2 info-hash is sha256(info_bytes) (I3 applies identically — captured bytes, never re-bencoded); reserved[7] & 0x10 in the handshake signals v2 support (§8 table, verified against the BEP 52 text directly). swarm-wire::v2 implements the three new base-protocol opcodes (21 hash request, 22 hashes, 23 hash reject, §8) — hash-layer exchange is a base protocol extension, not a BEP-10-wrapped one, a detail the original design mis-modeled as riding on the extension protocol and which this revision corrects. A hash request names a pieces_root, a base_layer (0 = leaf layer), an index (multiple of length), a length (power of two, ≥2, conventionally ≤512), and proof_layers; the responder answers with hashes (the requested layer's hashes plus the minimal uncle-hash proof chain) or hash reject. Hybrid torrents carry both pieces (v1) and file tree/meta version: 2 (v2); multi-file hybrid torrents use BEP 47 padding files so the non-piece-aligned v1 file layout and the piece-aligned v2 layout describe identical byte ranges (BEP 52's own documented upgrade path) — both infohashes are computed and both swarms are joinable, with content validated identical (names, order, piece alignment) before either swarm is trusted.

12.3 Deliverable

A v2-only torrent downloads end to end; a hybrid torrent downloads with a mix of v1-only and v2-only peers in the same logical swarm.

12.4 Acceptance Criteria

The merkle verifier passes 1,024/1,024 v2 piece-layer fixtures including single-block-piece and last-piece-shorter-than-block pathological cases; a hybrid torrent's two infohashes both validate against a reference implementation in corpora/metainfo/hybrid/*; a hash request for an unavailable layer receives hash reject, never a silent timeout, in 100% of fixtures/v2/hash_reject_path.bin runs.

12.5 Conformance Fixtures

corpora/v2/*.bin (merkle-tree fixtures, 1,024 cases) | fixtures/v2/hash_reject_path.bin | fixtures/v2/padding_alignment.bin (BEP-47-padded hybrid multi-file layout) | conformance/v2.report.json bucket.

12.6 Pitfalls

BEP 52 pads a merkle tree whose leaf count is not a power of two with all-zero 32-byte hashes for positions beyond the file's actual data — implementing "repeat the last leaf" instead (a mistake some early implementations made) produces a root that fails against every compliant peer. The pieces root field is the root of the per-file leaf-block tree, not a tree over whole pieces — conflating the two produces a subtly wrong hash that happens to validate for single-piece files and silently fails for multi-piece ones (verify against BEP 52's own worked examples). Treating hash exchange as BEP-10-wrapped instead of base-protocol opcodes 21–23 breaks interop with any strictly spec-compliant peer.

12.7 Performance Concerns

The auth-path proof for a hash request is O(log(blocks_per_piece)) hashes, not the whole tree — a request for a deep base layer with a large length amortizes proof overhead across many leaves in one round trip, which is why BEP 52 recommends length up to 512.

12.8 Edge Cases

A file smaller than one 16 KiB block (no internal tree, pieces root is simply the single leaf hash). An empty file (BEP 52: no pieces root at all — length-zero files are legal and carry no hash). A hash request whose index is not a multiple of length — malformed per BEP 52's own constraint, rejected rather than rounded.

12.9 Failure Analysis

A merkle-verification failure isolates to the specific 16 KiB block whose proof failed, not the whole piece — a v2 swarm can pinpoint and re-request a single bad block, a strictly finer-grained failure isolation than v1's whole-piece SHA-1 re-request (a genuine v2 advantage worth stating plainly, not just parity with v1).

12.10 Operational Notes

conformance/v2.report.json is tracked as a distinct CI bucket from v1's metainfo.report.json so a v2-specific regression is never masked by an all-green v1 suite; the hybrid-swarm join path gets its own trace span (torrent.add carries a swarm_kind attribute: v1, v2, or hybrid).

25. Phase 13 — WebTorrent / WebRTC (Stretch)

13.1 Objectives

Map the peer-wire protocol over WebRTC data channels so a browser tab can be a full swarm peer — explicitly a stretch phase (ADR-17), not required for the core system's Sealed status.

13.2 Detailed Implementation Steps

The WebRTC transport stack — ICE candidate gathering (STUN/TURN), DTLS 1.2 over the ICE- negotiated path, SCTP over DTLS for the data channel — implements Transport (P9, I7) exactly like TCP and µTP do; the peer-wire framing and message opcodes (§8) are unchanged, confirming MM5's prediction that the transport-as-capability design pays for itself here. WebTorrent's own project (not a ratified BEP, per the direct verification in §5) additionally uses a wss:// WebSocket-based tracker variant where peer offer/answer SDP is exchanged via the tracker rather than a direct connection — this blueprint treats that tracker variant as WebTorrent-specific infrastructure, layered beside (not replacing) the BEP-3/BEP-15 tracker clients of Phase 3.

13.3 Deliverable

A browser-hosted WebTorrent peer and a swarmd instance exchange at least one verified piece over a WebRTC data channel in a controlled interop test.

13.4 Acceptance Criteria

tests/interop/test_webrtc.rs completes one full piece exchange with a real WebTorrent-based peer; ICE connectivity establishes within 10 s at p90 on a network with a reachable STUN server (no acceptance criterion is set for TURN-relayed paths — production TURN hardening is registered in the Deferred Features Register, §39).

13.5 Conformance Fixtures

tests/interop/test_webrtc.rs | fixtures/webrtc/ice_stun_only.bin (STUN-reachable path) | fixtures/webrtc/sdp_offer_answer.bin (captured offer/answer exchange for regression testing).

13.6 Pitfalls

Treating WebTorrent's WebSocket tracker or WebRTC transport as governed by an official numbered BEP is a citation error this revision specifically corrects — neither is part of the bittorrent.org BEP process; both are WebTorrent-project-specific and must be described as such, not attributed a BEP number that does not exist for them. NAT traversal reliability without a TURN relay is materially worse than TCP/µTP's; do not treat the two as equivalent-reliability transports in operator-facing status reporting.

13.7 Performance Concerns

SCTP-over-DTLS framing overhead and the ICE negotiation round trip both add latency the TCP/µTP paths do not pay; this phase carries no throughput acceptance criterion beyond "one piece exchanges successfully" (13.4 above) precisely because it is a stretch phase, not a production target.

13.8 Edge Cases

A browser peer behind symmetric NAT with no TURN server configured — ICE fails to connect entirely; this is an accepted limitation of the stretch phase, not a bug to chase down (§39 Un-defer trigger: production TURN relay budget approved).

13.9 Failure Analysis

A failed WebRTC connection attempt affects only that one peer relationship; it has no blast radius into the TCP/µTP-backed portion of the same swarm, by the same transport-isolation argument as Phase 10's failure analysis (I7).

13.10 Operational Notes

WebRTC peers are tagged distinctly in swarmctl peers <infohash> output (transport: webrtc) so an operator never confuses a WebRTC peer's different reliability characteristics with a TCP/µTP peer's.

28. Operational Readiness

Metrics, tracing, logging. Prometheus pull on :9091/metrics (ADR-12, the 12 metrics named in §23 Phase 11's 11.2); OpenTelemetry spans (ADR-13) on every torrent-lifecycle, tracker, DHT, peer, verify, storage, and choke-tick event; structured JSON logs at info for lifecycle transitions, warn for quarantine/ban events, error for daemon-level faults.

Dashboards. The Grafana dashboard (ops/grafana/, §23 Phase 11's 11.4) graphs: torrents-by-status, peers-connected, bytes/sec up/down, DHT lookup p99, tracker announce p99, choke-tick p99, µTP cwnd distribution, MSE handshake outcome rate.

Alerting philosophy. Alert on invariant violations (I5/I9/I10 telemetry nonzero), on SLO breach (M1–M13 sustained miss), and on resource-ceiling approach (§4 FD/memory budgets) — never on transient per-peer noise (a single choked peer, one failed tracker tier) since those self-heal by design (FM1/FM3).

SLOs. Choke-tick p99 < 10 ms (M2); DHT lookup p99 < 1 s popular / < 5 s arbitrary (M3/M4); magnet-to-first-byte p99 < 10 s (M5); 24-hour soak with zero unhandled panics and zero unbounded memory growth (M10).

Incident response. runbooks/triage.md is the entry point for every on-call page; it routes to stuck-torrent.md, dht-cold-start.md, or tracker-outage.md based on the first-ten-minutes checklist (§23 Phase 11's 11.10).

Backup / restore. The sled resume database is the only persistent daemon state beyond downloaded payload bytes themselves; it is backed up via a file-level snapshot of its data directory and restored by replacing that directory before daemon start — the resume-verify pass (Phase 5) reconciles any staleness against on-disk payload bytes automatically.

Deployment topology. One swarmd process per host; horizontal scaling is per-host, not per-torrent-shard (§33 Scalability Analysis expands on the ceiling this implies).

Canary / rolling upgrade / rollback. A new swarmd binary is canaried on a subset of hosts behind the same resume-DB schema version (§29); rollback is a binary swap plus resume-DB replay, bounded by the same ≤ 30 s RTO as a crash recovery (§4).

29. Compatibility & Versioning

Wire compatibility. The peer-wire protocol (BEP 3/6/10/52 opcodes, §8) is permanently backward-compatible by the reserved-bit negotiation scheme (§8 table) — a swarmd that does not support v2 or the fast extension simply never sets those reserved bits and interoperates at the BEP-3 baseline.

Storage/schema compatibility. The sled resume-database schema is versioned; a schema migration on upgrade is additive-only within a major version (new column families may be added, none removed or repurposed) and destructive changes require a major-version bump plus an explicit one-time migration pass logged to BLUEPRINT_LOG.md-style migration notes.

API stability. The gRPC IDL (docs/api/swarmd.proto, ADR-11) follows SemVer: a field may be added without a version bump; removing or repurposing a field is a breaking (major) change; every swarmctl release pins a compatible swarmd API version range and refuses to operate against an incompatible daemon rather than silently misbehaving.

Deprecation policy. A deprecated field or RPC method is marked in the IDL for one full major version cycle before removal, with a deprecated comment naming the replacement.

Rolling-upgrade guarantees. Because torrent state lives in the resume DB (not in-memory-only) and every piece boundary is fsync'd before being marked Complete (I11), a rolling upgrade that restarts swarmd mid-download loses at most the in-flight (unfsynced) blocks of the interrupted moment — bounded by the same ≤ 30 s RTO used for unplanned crashes (§4, §27 FM5).

30. Testing & Verification Strategy

Unit. Per-crate tests for bencode grammar edge cases (Phase 1), infohash computation (Phase 2), wire-codec round-trips (Phase 4), choke-tick sorting (Phase 6) — each ties back to the invariant it protects (§7) and the fixture that exercises it (the phase's N.5).

Integration. tests/integration/test_storage.rs (Phase 5), tests/interop/test_pex.rs/ test_lsd.rs (Phase 7), tests/interop/test_utp.rs/test_mse.rs (Phase 10), tests/e2e/ test_daemon.rs (Phase 11) — each spins up real or containerized peers (libtorrent, qBittorrent, chihaya) rather than mocks, per the interop philosophy of §2.

Property-based. The DHT routing table's bucket invariants (I12) are checked via 100,000- iteration proptest random-insertion sequences (Phase 8); the bencode round-trip property (encode(decode(x)) == x) is checked across all positive fixtures (Phase 1).

Differential. Every wire, tracker, and DHT fixture is captured from a real reference client (libtorrent/Transmission) and compared byte-for-byte against our implementation's output — not just checked for "no crash" (Phases 1–4, 8, 12).

Fuzzing. cargo-fuzz targets on the bencode decoder, wire decoder, metainfo parser, and DHT decoder (ADR-19); CI runs a 5-minute fuzz pass on every PR, and a 30-day continuous fuzz gates M11/Sealed status.

Chaos / fault injection. The crash-recovery fixture (kill -9 mid-write, Phase 5) and the simulated-clock-skew fixture (Phase 10) are the two deliberate fault-injection points; the choke- tick determinism test (P10, I8) uses a paused clock specifically so timing faults are reproducible rather than flaky.

Deterministic replay. Every test that touches randomness or time uses a seeded StdRng and a paused tokio::time clock (P10/I8) — a failing test's seed is logged so the exact sequence replays identically on a second run, the debugging methodology named in §7.

Soak. A 24-hour continuous-operation run (M10) with synthetic swarm traffic asserts zero unhandled panics and zero unbounded memory growth (benchmarks/results/soak/24h.json).

Conformance gating. conformance/runner.rs aggregates every bucket (§30 buckets mirror the phase-by-phase fixtures above) into conformance.report.json; a regression in any bucket (Pass → Fail) blocks merge in conformance.yml. Performance-regression gating ties the Performance Engineering targets (§32) into the same CI pipeline: a benchmark result outside its M-target band fails the build, not just a dashboard alert.

31. Build & Release Engineering

Reproducible builds. Cargo.lock is committed and CI builds from it exactly; rust- toolchain.toml pins 1.78 (ADR-01) so a release binary built today and in six months from the same lockfile is bit-for-bit comparable modulo timestamp/path embedding, which cargo build --locked plus a normalized build environment (the Dockerfile's cargo chef stage) controls for.

Artifact signing. Release binaries are signed (minisign or cosign, chosen at release- engineering time) and the signature published alongside the artifact in the GitHub release; swarmd/swarmctl verify their own version string against the signed manifest at --version.

SBOM. cargo-deny (ADR-20) doubles as the SBOM generator input; a CycloneDX SBOM is emitted per release and attached to the GitHub release artifact.

Release channels. stable (tagged releases only), nightly (main branch, unsigned, for interop testing only) — swarmctl refuses to talk to a nightly swarmd unless an explicit --allow-nightly flag is passed, preventing accidental production use of an unsigned build.

CI/CD topology. ci.yml (build+unit+lint on every PR), conformance.yml (the fixture suite, §30), interop.yml (containerized libtorrent/qBittorrent/chihaya interop), fuzz.yml (5-minute PR fuzz + scheduled 30-day continuous fuzz), security.yml (cargo-deny advisory scan), release.yml (tag-triggered build, sign, SBOM, publish).

Version stamping. The binary embeds its own Git SHA, build timestamp, and Cargo version via build.rs; swarmctl --version and the gRPC handshake both surface it for support/debugging.

Provenance / attestation. release.yml emits a SLSA-style provenance attestation (build platform, source commit, dependency lockfile hash) alongside the signed binary.

Dependency auditing. cargo-deny (ADR-20) gates on license policy (Apache-2.0/MIT-compatible only, per ADR-14), duplicate-crate detection (I2's build-time enforcement), and known-vulnerable advisories — a failing cargo-deny check blocks merge.

Methodology. Benchmarks live in benchmarks/ (bencode.rs, piece_pick.rs, choke_tick.rs, dht_lookup.rs, e2e_throughput.rs) and run under criterion for micro- benchmarks, plus the containerized interop rig for end-to-end numbers. Profiling uses perf + flamegraph for CPU, heaptrack for allocation, and tokio-console for task/lock contention — every M-target below is CI-gated, not a dashboard-only aspirational number (§30).

Allocation/lock/cache/syscall analysis. bytes::Bytes (ADR-15) keeps the hot wire-to-hash path allocation-light; the choke tick's per-tick peer sort is the one place lock contention could show up at 4,000 connections and is measured directly by choke_tick.rs; pwrite/fsync syscall counts are tracked per piece to confirm the "fsync at piece boundary only" rule (I11) holds in practice, not just in code review.

33. Scalability Analysis

What stays constant. Per-message wire-codec cost (O(1) per message, independent of swarm size); bencode decode cost (O(bytes), independent of peer count); the choke tick's 10 s cadence (P4 — constant by design, not by luck).

What grows, and its Big-O. Choke-tick sort cost: O(peers log peers) per torrent per tick — the first named bottleneck, becoming visible as peer-per-torrent count approaches the §4 ceiling (200). DHT routing-table size: bounded at O(log(ID space)) = 160 buckets × 8 = 1,280 regardless of network size (Kademlia's whole point, MM3) — the lookup cost is O(log N) hops in network size N, the second named bottleneck at very large DHT populations. Resume-DB write volume: O(pieces) per torrent, O(torrents) daemon-wide — the third named bottleneck at very high torrent counts (approaching the §4 200-torrent ceiling), since sled's write-amplification grows with concurrent-writer count.

Horizontal vs. vertical scaling. swarmd scales vertically within one host up to the §4 ceilings (200 torrents, 4,000 connections, 4 GiB RSS); horizontal scaling is per-host (run multiple swarmd instances on separate hosts, each with its own resume DB and DHT node) — there is no cross-host torrent sharding or coordination layer in this design (a deliberate simplicity choice; see Alternative Architectures §38 for designs that do shard).

Sharding/partitioning. Not built in; if per-host limits are reached, additional swarmd instances partition torrents by hash-of-infohash across hosts, coordinated only by whatever external orchestration the operator supplies (out of scope, §1 non-goals).

Coordination overhead. Zero cross-swarmd-instance coordination exists in this design; each instance's DHT node, tracker announces, and PEX/LSD traffic are entirely independent, which is precisely why horizontal scaling requires no consensus protocol — the tradeoff is no cross- instance piece-cache sharing (two swarmd instances on the same host duplicate identical downloads if pointed at the same torrent).

Practical ceiling and the levers beyond it. The practical single-host ceiling is the §4 M6 budget (50K peers / 200 torrents / 4 GiB RSS at < 50% CPU); the lever beyond it is horizontal (more hosts), not vertical (a bigger choke-tick sort or a bigger DHT table does not move the ceiling, because the bottleneck is peer-count-per-host, not algorithmic complexity within one host).

34. Mental Models & First Principles

  • MM1 — A torrent is a distributed integrity manifest, not a file. Predicts that hash trees generalize cleanly (flat SHA-1 list in v1, merkle tree in v2, §8). Bug class without it: engineers trust file names/paths instead of the pieces/piece layers data, and silently accept renamed-but-corrupted content. Applies at §8, §14 (Phase 2), §24 (Phase 12).
  • MM2 — The choke algorithm is a repeated iterated prisoner's dilemma, not a scheduler. Predicts optimistic unchoke is structurally required, not a tunable nicety. Bug class without it: engineers "simplify" by removing the optimistic slot and new peers can never demonstrate reciprocity, killing swarm growth. Applies at P4, §18 (Phase 6).
  • MM3 — Kademlia's XOR metric bounds routing-table maintenance by ID-space bit-length, not peer count. Predicts O(log N) lookup hops regardless of network size. Bug class without it: engineers implement an O(N) flood-style discovery expecting it to scale, and it doesn't. Applies at §8, §20 (Phase 8), §33.
  • MM4 — The bencode canonical form is the infohash's identity function. The captured bytes are the hash input, not a value the hash merely describes. Predicts re-serialization breaks compatibility. Bug class without it: silent infohash mismatches against real-world non- canonical torrents. Applies at §8, P3, §14 (Phase 2).
  • MM5 — A Transport is a capability, not a socket type. Predicts choking/picking code stays transport-agnostic across TCP/µTP/WebRTC. Bug class without it: business logic accretes transport-specific special cases that eventually leak into the picker. Applies at P9, §11, §22 (Phase 10), §25 (Phase 13).
  • MM6 — LEDBAT's target delay is a fairness contract with TCP, not a speed knob. Predicts µTP throughput should degrade under TCP competition — that is correct, designed behavior. Bug class without it: engineers "fix" perceived slowness by raising the target delay and quietly break the background-transport promise RFC 6817 makes. Applies at §22 (Phase 10), §5 (RFC 6817).
  • MM7 — Endgame trades bandwidth for tail latency, an explicit admission the picker's model breaks down near completion. Predicts endgame amplifies upload exactly when marginal benefit is lowest, so it must stay capped. Applies at §18 (Phase 6), §32.
  • MM8 — A magnet link is a hash-addressed promise, not a location. Predicts metadata must be re-verified against the hash before any byte is trusted, regardless of which peer supplied it. Bug class without it: engineers trust the first peer's metadata blindly. Applies at §8, §21 (Phase 9).

36. Back-of-Envelope Capacity Model

Every number below is derived from the §4 System Constraints table, formula shown, chained forward — none is asserted in isolation.

  1. Per-torrent peer-connection memory = max_peers_per_torrent (200) × per-peer buffer (256 KiB) = 51.2 MiB per torrent at full peer fan-out.
  2. Daemon-wide peer-connection memory ceiling = max_global_connections (4,000) × 256 KiB = ~1.02 GiB, leaving headroom under the 4 GiB RSS ceiling (M6) for storage buffers, the DHT table, and resume-DB overhead.
  3. Piece-bitmap memory per torrent = piece_count / 8 bytes; for a 32 GiB torrent at 1 MiB pieces, piece_count = 32,768, so bitmap = 4,096 bytes — negligible even × 200 torrents (~800 KiB total).
  4. DHT routing-table memory ceiling = 160 buckets × 8 nodes × record size (~52 bytes: 20-byte NodeId + 18-byte SocketAddr + 8-byte rtt/timestamp + 6-byte flags) = ~66.6 KiB — confirms I12's bound is cheap regardless of overlay size (MM3).
  5. Target throughput needed for M1 = 1 GB torrent / target time; at the stated ≥ 800 Mbps sustained target, a 1 GB (8 Gbit) torrent completes in ≥ 10 s of pure transfer time at that floor rate.
  6. FD budget check = max_global_connections (4,000) + listen sockets (2, TCP+UDP) + DHT socket (1) + LSD socket (1) = 4,004, safely under the 4,096 FD ceiling (§4) with ~92 FDs of slack for storage file handles.
  7. Endgame amplification bandwidth (worst case) = outstanding_blocks_near_completion × avg_peers_per_block × block_size (16 KiB); capped by the 32-cancels/s/peer rule (Phase 6 Pitfall), bounding worst-case redundant upload to 32 × 16 KiB × peers-with-piece per second, not unbounded.
  8. Resume-verify throughput needed for M8 = 32 GiB / 60 s = ~546 MiB/s sustained read + hash throughput — comfortably within single-NVMe sequential-read bandwidth (typically 1–3 GB/s), leaving headroom for the SHA-1/SHA-256 compute cost running in parallel across cores.
  9. DHT lookup fan-out traffic = α (3) × expected_hops (~log₂(1,280) ≈ 10-ish in the worst case, typically far fewer in practice) × RPC size (~100 bytes) ≈ ~3 KB per lookup in typical-case network traffic — trivial relative to piece-transfer bandwidth.
  10. Choke-tick CPU cost at the peer ceiling = 200 peers × O(log 200) comparison cost per tick / 10 s cadence; at even a generous 1 µs per comparison-sort step this is microseconds of CPU per tick per torrent — confirms the M2 (p99 < 10 ms) target has orders of magnitude of headroom at the per-torrent peer ceiling, with the 10 ms budget instead absorbing OS scheduling jitter across up to 200 concurrent torrents' ticks.
  11. Tracker announce traffic (daemon-wide) = 200 torrents × (1 / 1800 s interval) × ~150-byte request ≈ ~17 bytes/s average outbound — negligible relative to payload transfer, confirming trackers are a control-plane, not data-plane, cost.
  12. Aggregate seeding memory for M13 = 1,000 leechers × 256 KiB buffer = 256 MiB, comfortably inside the single-torrent 51.2 MiB-per-200-peers ratio scaled up, confirming the 10 Gbps/1,000-leecher M13 target is memory-bound-safe under the same per-peer buffer constant used throughout this model.

38. Alternative Architectures (Roads Not Taken)

Alternative 1 — Flooding/gossip peer discovery instead of tracker + DHT.

[peer]--query-->[peer]--query-->[peer]--query-->[peer]
   ^_______________TTL-bounded flood______________|

Regime where it wins: very small, closed swarms where every peer already knows a handful of others and the overhead of maintaining a Kademlia routing table is not worth it. Real system: early Gnutella-style flooding overlays. Rejected here because flooding does not scale to internet-wide swarms (the flood traffic itself grows faster than useful discovery, exactly the scaling problem Kademlia's O(log N) structure — MM3 — was built to avoid), and it duplicates work the tracker already does cheaply for the common case.

Alternative 2 — Content-addressed DAG (IPFS/Bitswap-style) instead of a static piece-hash manifest.

[CID root]
   ├─ [chunk CID] ─ dedup across unrelated files
   └─ [chunk CID] ─ mutable via IPNS pointer

Regime where it wins: a general-purpose content-addressed web where files are added incrementally, updated, and shared across unrelated publishers, and cross-file deduplication has real value. Real system: IPFS with Bitswap as its block-exchange protocol. Rejected here because this project's scope is static, immutable-payload interoperability with the existing BEP-3/BEP-52 ecosystem (§1 Goal & Scope) — adopting a DAG model would break byte-level interop with every existing BitTorrent client, the opposite of this project's stated goal.

Alternative 3 — Superpeer hierarchy instead of a flat per-torrent swarm.

        [supernode]
        /    |    \
   [leaf] [leaf] [leaf]   <- ordinary peers attach to nearest supernode

Regime where it wins: very large overlays with sharply heterogeneous peer capacity, where concentrating routing/relay work on high-bandwidth "supernodes" reduces average path length and protects low-capacity peers from relay load. Real system: the historical FastTrack/Kazaa overlay network. Rejected here because BitTorrent's per-torrent swarm segmentation already solves the "who talks to whom" scaling problem without a trusted-supernode election mechanism, which would add a whole new trust/failure class (supernode compromise or churn) this design's threat model (§26) does not need to carry.

40. Glossary

Allowed fast set — the small set of pieces (BEP 6, conventionally k=10) a peer will serve even while choking the requester, used to bootstrap new connections faster. Announce — a tracker request reporting peer state and requesting peers. Bandwidth accountant — the session-owned component that meters upload/download at the transport-trait boundary (P11, I9). Bencode — the length-prefixed, sorted-dict serialization format underlying all BitTorrent metadata and control messages. Bitfield — the first-message bitmap advertising which pieces a peer holds. Block — a sub-piece unit requested/transferred over the wire, conventionally 16 KiB. Choke — a peer-connection state meaning "I will not send you data right now." Compact peer list — the 6-byte (IPv4) or 18-byte (IPv6) per-peer tracker response encoding (BEP 23/BEP 7). Connection ID — the per-session identifier used by both the UDP tracker protocol (BEP 15) and µTP to scope a handshake. Endgame mode — the one-way transition, near completion, to requesting outstanding blocks from every peer that has them. Extension protocol (LTEP) — BEP 10's extended (opcode 20) message framing for negotiated sub-protocols. Fast extension — BEP 6's have-all/have-none/suggest/reject/allowed-fast message set. File tree — BEP 52's recursive per-path metainfo structure for v2 torrents. get_peers — the Kademlia RPC that returns either peers or closer nodes for an infohash. Handshake — the fixed 68-byte exchange that opens every peer-wire connection. Hash reject / hash request / hashes — BEP 52's base-protocol opcodes (23/21/22) for exchanging merkle-tree layer hashes. Have message — announces that a peer has just completed and verified a piece. Holepunch extension (BEP 55) — the ut_holepunch rendezvous/connect/error protocol for NAT-blocked peer pairs. Hybrid torrent — a torrent carrying both v1 (pieces) and v2 (file tree) fields, joinable in both swarms. Infohash — the SHA-1 (v1) or SHA-256 (v2) hash of the bencoded info dict, computed once from captured bytes (I3). Interested / not interested — a peer-connection state expressing desire for at least one block the other side has. K-bucket — a Kademlia routing-table bucket holding up to K=8 known nodes at a given XOR-distance range. Kademlia — the XOR-metric DHT algorithm Mainline DHT implements. LEDBAT — RFC 6817's delay-based, TCP-yielding congestion control algorithm, run by µTP. LSD — Local Service Discovery (BEP 14), UDP-multicast peer discovery on a local network. Merkle root / pieces root — the SHA-256 root of a per-file leaf-block tree in BEP 52. Meta version — the metainfo field distinguishing v1 (absent/1) from v2 (2). Metainfo — the parsed structure of a .torrent file. µTP — BEP 29's UDP-based reliable transport running LEDBAT congestion control. Node ID — a 160-bit Kademlia identifier for a DHT participant. One-way delay — the LEDBAT-measured queuing delay used to drive the congestion window. Optimistic unchoke — the rotating unchoke slot given regardless of upload rate, to let new peers demonstrate reciprocity. Piece — the top-level content-addressed unit a torrent is divided into. Piece layers — BEP 52's top-level metainfo dict of concatenated merkle layer-hashes. Piece length — the configured size of each piece, a power of two between 16 KiB and 16 MiB. Private torrent — a torrent with info.private=1, quarantined from DHT/PEX/LSD (P12, I10). Quarantined piece — a piece that failed hash verification and awaits re-request from a different peer. Rarest-first — the piece-selection policy prioritizing the least-available piece a peer holds. RC4 drop-1024 — the MSE mitigation discarding the first 1,024 bytes of RC4 keystream. Resume database — the sled-backed persistent store of bitfields and partial-piece state (ADR-05). Scrape — a tracker query for aggregate swarm stats without changing peer state. Sequential mode — an opt-in piece-selection policy for streaming playback. Sparse file — a pre-allocated file whose disk usage tracks only verified bytes written. Super-seeding — BEP 16's lone-seeder bootstrap optimization (deferred, §39). Tracker — a server coordinating peer discovery for a swarm via HTTP or UDP announce/scrape. Transport — the trait abstracting TCP, µTP, and WebRTC behind one AsyncRead+AsyncWrite contract (P9, I7). Write-token — the Kademlia anti-spoofing token required before announce_peer is honored, rotated every 5 minutes.
