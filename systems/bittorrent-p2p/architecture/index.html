Data flows in one direction and back: bytes flow up from the socket through the wire protocol into the picker; verified pieces flow down from the picker into storage; requests flow back out. The transport is a trait (§11 Transport) with two implementations (TCP, µTP); the wire protocol and the choking algorithm cannot tell which one backs a given peer (P9). Every cross-cutting concern — bencode, hashing, bandwidth accounting — is owned by exactly one module and reached by trait or function call, never duplicated (P2, P11). swarmd composes the whole stack behind a Unix-socket control plane; swarmctl is a thin gRPC client with no protocol logic of its own. The DHT (Phase 8) and PEX/LSD (Phase 7) sit beside the tracker manager as independent peer-discovery sources feeding the same peer manager; none of them shares mutable state with the choking/picking core (I6).

8. Domain Model / Protocol / Data Model

Bencode grammar (EBNF). The wire encoding underlying every metainfo, tracker, and DHT message:

value      = integer | bytestring | list | dict ;
integer    = "i", ["-"], digit_nz, {digit}, "e" | "i0e" ;
bytestring = length, ":", byte, {byte} ;
length     = digit_nz, {digit} | "0" ;
list       = "l", {value}, "e" ;
dict       = "d", {bytestring, value}, "e" ;   (* keys sorted ascending by byte value *)
digit_nz   = "1" … "9" ;
digit      = "0" … "9" ;

Canonical-form rule (I3, P3): dict keys sorted ascending by raw byte value (not locale collation); no leading zeros on integers except i0e; no re-serialization of captured info-dict bytes. A dict with keys out of order, or a duplicate key, is Error::NonCanonicalDict — rejected, not repaired.

Peer-wire handshake (68 bytes, BEP 3):

[1 byte ] 0x13                     (length of "BitTorrent protocol")
[19 bytes] "BitTorrent protocol"
[8 bytes] reserved (extension bits, see table below)
[20 bytes] infohash (v1 SHA-1, or the v2 SHA-256 truncated to 20 bytes)
[20 bytes] peer_id (BEP 20 convention: "-SW0010-" + 12 random bytes)

Reserved-byte extension bits (verified against BEP 6 / BEP 10 / BEP 52 text directly):

Byte (0-indexed) Bit mask Meaning Source
reserved[5] 0x10 Extension Protocol (LTEP) supported BEP 10
reserved[7] 0x01 DHT port message supported BEP 5
reserved[7] 0x04 Fast Extension supported BEP 6
reserved[7] 0x10 BitTorrent v2 (BEP 52) supported BEP 52

Peer-wire message frame: [4-byte big-endian length][1-byte opcode][payload]; length 0 is keep-alive. Base opcodes (BEP 3 + BEP 6 + BEP 52, all base protocol IDs — not LTEP-wrapped):

Opcode Name Payload Source
0 choke — BEP 3
1 unchoke — BEP 3
2 interested — BEP 3
3 not interested — BEP 3
4 have <index> BEP 3
5 bitfield bitmap, first message only BEP 3
6 request <index><begin><length> BEP 3
7 piece <index><begin><block> BEP 3
8 cancel <index><begin><length> BEP 3
9 port <listen-port> BEP 5
13 suggest piece <index> BEP 6
14 have all — BEP 6
15 have none — BEP 6
16 reject request <index><begin><length> BEP 6
17 allowed fast <index> BEP 6
20 extended <ext-id><payload> BEP 10
21 hash request <pieces_root><base_layer><index><length><proof_layers> BEP 52
22 hashes as above + <hashes> BEP 52
23 hash reject same payload as hash request BEP 52

Worked example — announce + handshake trace (HTTP tracker, then one peer):

GET /announce?info_hash=%aa%bb...&peer_id=-SW0010-...&port=51413

<- [len=16393][op=7][index=0][begin=0][block...]     (piece, 16 KiB)

Malformed-input example: a peer sends bitfield as its second message (after an initial have). Per BEP 3/6, bitfield (or have-all/have-none) is legal only as the first message. The wire codec returns Error::UnexpectedBitfield; the peer connection closes without propagating any state change to the picker (I1, Phase 4 Edge Case).

Failure-path example: a piece message arrives whose SHA-1 does not match the metainfo's pieces entry. The verifier (I5) marks the piece Quarantined { failures: 1 }, attributes the bytes to the sending peer, and the picker re-issues the block to a different peer; after 3 failures from the same peer that peer is disconnected and banned for 1 hour (Phase 5 Failure Analysis, §26 Threat 3).

BitTorrent v2 (BEP 52) piece-layers model. The metainfo carries a top-level piece layers dict (sibling of info, keyed by 32-byte SHA-256 merkle root, value = concatenated layer-hashes at the granularity matching piece length), plus a per-file file tree leaf {"": {length, pieces root}} where pieces root is the SHA-256 merkle root over 16 KiB leaf blocks (zero-padded to a power of two). No BLAKE3 is used anywhere in BEP 52 — the spec mandates SHA2-256 for both the info-hash and the merkle tree.

DHT state machine (Phase 8 preview): Idle -> Bootstrapping -> Warm -> LookupInFlight -> Warm, where Bootstrapping pings the well-known routers, Warm means the routing table has ≥1 node per populated bucket range, and LookupInFlight is the iterative get_peers traversal of §20.

Design principles (§6)

  • P1 — Wire correctness is the ground truth. Every peer message round-trips through a hand-coded encoder/decoder tested against fixtures captured from libtorrent and Transmission. Violating it: an encoder change that silently perturbs one byte breaks interop invisibly until a real swarm test catches it (§30 conformance gating).
  • P2 — Bencode is a single module. One parser, one encoder, in swarm-bencode; every other crate reaches for it by call, never re-implements it. Violating it: two bencode implementations drift and produce two different infohashes for the same bytes (I2).
  • P3 — The infohash is computed once. Captured at parse time from the raw byte range; never re-bencoded and re-hashed. Violating it: a "canonical" re-serialization of a non-canonical real-world .torrent computes the wrong infohash (I3, Phase 2 Pitfall).
  • P4 — The choke tick runs every 10,000 ms, exactly. Not "approximately when convenient." The optimistic-unchoke slot rotates every 30,000 ms. Violating it: tit-for-tat reciprocity degrades in ways invisible below swarm sizes a unit test can reach (I4, Cohen 2003).
  • P5 — Piece selection is the picker's property, not the peer's. A peer asks the picker "what next"; it never holds piece statistics itself. Violating it: rarity computation and endgame transition logic duplicate and diverge across peer connections.
  • P6 — Storage is opaque to the peer. A peer calls storage.read/storage.write; it never opens a file descriptor itself. Violating it: sparse-file layout, mmap-vs-pwrite choice, and move-on-rename all become un-replaceable (§17 Phase 5).
  • P7 — Hash verification gates every write. No unverified piece reaches a durable fsync. Violating it: a single malicious peer can poison the on-disk payload silently (I5).
  • P8 — The DHT is a separate state machine. Its own UDP socket, its own task; shares state with the peer manager only through announce/lookup channels. Violating it: a DHT bug can stall a download, or vice versa (I6).
  • P9 — The transport is a trait, not an enum. TCP and µTP both implement Transport; the peer state machine cannot branch on which one it holds. Violating it: choking/picking logic accretes transport-specific special cases (I7, MM5).
  • P10 — Determinism is the default for tests. Randomness is seeded (StdRng), time is paused (tokio::time::pause) in every test; production code uses real time/entropy. Violating it: flaky tests mask real races (I8).
  • P11 — Bandwidth is metered at the trait boundary, owned by the session. A request debits the upload accountant; a piece arriving credits the download accountant, at the session level, not per-peer. Violating it: per-peer accounting drifts from the session total (I9).
  • P12 — Private torrents are quarantined at exactly one check point. info.private = 1 is checked once, at the session boundary, and propagated; subsystems never re-check it. Violating it: a private swarm silently leaks to DHT/PEX/LSD (I10).
