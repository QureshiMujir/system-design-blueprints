221 — Network Emulator / Simulator from Scratch

Project Number: 221

Project Name: Network Emulator / Simulator from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. A deterministic discrete-event network simulator fused with a real-time network emulation runtime: one event-scheduling core drives both a virtual-time mode (bit-exact replay, no wall-clock coupling) and a real-time mode (Linux namespace/TAP/tc integration) against the same packet pipeline, topology compiler, and fault-injection engine. Packet, flow, and topology behavior must be reproducible bit-for-bit under virtual time and statistically bounded under real time. This is the ns-3 + Mininet + tc/netem problem restated as one deterministic core with two front ends.

Phase 0 deliverable — crates/services shipped:

  1. sim-core — scheduling primitives, IDs, ownership types shared by every other crate.
  2. event-runtime — hierarchical timing-wheel scheduler, deterministic comparator.
  3. packet-engine — packet parser, pools, queue disciplines, corruption engine.
  4. topology-compiler — DSL parser, graph validator, manifest hasher.
  5. virtual-clock — logical/accelerated/paused clock, distributed barrier primitive.
  6. fault-engine — fault DSL, trigger evaluation, injector rule table.
  7. metrics-pipeline — Prometheus exporter, cardinality guard, metric registry.
  8. scenario-runner — scenario DSL executor, deterministic seed propagation.
  9. replay-engine — WAL segment writer/reader, replay cursor, divergence hashing.
  10. cli — operator entrypoint: run, replay, inspect, validate.
  11. orchestrator — coordinator RPCs, shard assignment, worker leases.
  12. storage-engine — segment storage, snapshots, compaction.
  13. tracing-layer — OpenTelemetry span emission, structured log fields.
  14. transport-models — TCP/UDP/QUIC behavior models, congestion windows.
  15. docs-runtime — runbook and ADR rendering for docs/.

System boundaries.

  • Provides: deterministic event scheduling, packet/flow/topology simulation, real-time emulation via Linux namespaces/TAP/TUN/tc/eBPF, fault injection, replay, metrics/tracing export, a scenario DSL, a CLI, and distributed multi-worker coordination.
  • Delegates: actual packet forwarding hardware behavior to the Linux kernel (tc/netem, veth, namespaces) when running in emulation mode; congestion-control conformance to the transport model implementations, not to a full kernel TCP stack; container/K8s scheduling to the host orchestrator when deployed there.
  • Does NOT provide: PHY/RF simulation, ASIC or SDN-controller behavior, GPU packet processing, a commercial GUI, or a kernel replacement networking stack. These are non-goals (below), not future phases.

Non-goals. Full physical-layer radio propagation modeling; hardware NIC/DPDK/SmartNIC offload emulation; GPU-accelerated scheduling; a bundled SDN controller; vendor-specific cloud integrations (see §35 Deferred Features Register for the subset that may return later).

Deployment model. Single-host deterministic simulation (laptop-scale correctness testing); multi-process emulation on one host (namespace-isolated workers); multi-node distributed simulation clusters (orchestrator + N event-runtime workers over gRPC); CI-integrated topology conformance testing (headless, virtual-time only); air-gapped reproducible research clusters (no external network dependency, artifacts vendored); optional Kubernetes-hosted orchestration for long-running chaos campaigns.

Target operators. Primary: systems engineers, distributed-systems researchers, protocol implementers, SRE/chaos-engineering teams, infrastructure-validation engineers, networking researchers. Secondary: academic labs, benchmark authors, observability teams validating alerting under synthetic failure. All operators are assumed comfortable with Linux networking primitives and a CLI-first workflow — this is not an end-user GUI product.

What later phases unlock. Phase 1 (§13) unlocks deterministic replay for anything built after it. Phase 2 (§14) unlocks real packet-shape fixtures for transport work. Phase 3 (§15) unlocks multi-node topologies larger than a hand-written graph. Phase 4 (§16) unlocks chaos-engineering campaigns. Phase 5 (§17) unlocks protocol conformance claims. Phase 6 (§18) unlocks forensic post-incident replay. Phase 7 (§19) unlocks horizontal scale past one host. Phase 8 (§20) unlocks running unmodified real workloads through the emulator. Phase 9 (§21) unlocks production-grade operability (dashboards, alerting, rollback).

Recommended language: Rust. Rationale: deterministic ownership semantics make the single mutable-owner packet invariant (I3, §7) a compile-time guarantee rather than a runtime check; async/Tokio gives a mature, widely-audited concurrency substrate for the event runtime and RPC layer; predictable allocator/memory behavior is required for the p99 scheduling-latency budget (§4); the serialization ecosystem (prost, serde, zstd) covers wire format, replay WAL, and trace export without custom codecs; static binaries simplify reproducible builds (ADR-19, §9) and air-gapped deployment. Rejected: Go — garbage-collector pause behavior is incompatible with the p99 < 500µs scheduling-latency budget and its channel semantics do not enforce single-ownership; C++ — memory-safety burden on a 15-crate, multi-contributor codebase outweighs its raw performance edge, and its build/dependency ecosystem is weaker for reproducible builds than Cargo. Secondary components: Python (orchestration SDK, notebook-style result analysis), TypeScript (topology visualization front end), Bash (operational scripts, §10 scripts/).

Prerequisites. OS internals (scheduling, syscalls, virtual memory); Linux networking (namespaces, veth, tc, eBPF); concurrency and async runtimes; distributed systems (consensus, clock skew, partition handling); discrete-event and queueing-theory fundamentals; transport protocol internals (TCP/QUIC); performance engineering (profiling, allocator behavior); observability (metrics/tracing cardinality); filesystem/WAL semantics; serialization formats.

Estimated timeline. Phase 0 (§12): 10 weeks — repository foundation, event runtime skeleton, correctness kernel. Production-ready single-host runtime (Phases 0–6, §§12–18): 5–7 months. Full distributed simulation platform (Phases 0–9, §§12–21): 9–14 months, one team of 4–6 engineers at steady state.

2. Why Build This

This project teaches deterministic event scheduling under load, packet-lifecycle modeling, transport/congestion-control behavior, reproducible distributed-systems experimentation, Linux-namespace runtime isolation, traffic shaping, replay-driven forensic debugging, and high-cardinality telemetry design — skills that transfer directly to building the event loop of a database, the control plane of a service mesh, or the scheduler of a distributed runtime.

Historically, network emulators and simulators shaped TCP congestion-control evolution (ns-2/ ns-3-validated BBR and CUBIC work), BGP convergence research, distributed-systems resilience engineering (Jepsen-style fault injection owes its lineage to network partition tooling), cloud infrastructure testing (Netflix's chaos tooling, AWS's own fault-injection service), QUIC validation (Google's own emulation harnesses predate the RFC), and CDN architecture validation (Mahimahi-style trace-driven replay). Related systems: distributed databases (replication under partition), service meshes (Envoy's traffic-shaping surface), hypervisors (time virtualization), network operating systems, observability stacks, tracing systems, storage engines (the WAL discipline in §18 is the same discipline as an LSM engine's), RPC runtimes, protocol fuzzers.

Calibration value — after completing this project, an engineer should be able to reason about network-level production failures from first principles, debug transport anomalies from a packet trace rather than a symptom report, design an event-driven runtime with bounded tail latency, build a deterministic replay system for a different domain, analyze congestion-collapse conditions quantitatively, reason about scheduler fairness under shard imbalance, and diagnose distributed timing failures (clock skew, barrier desync) without guessing.

What Mastery Looks Like

  • Can implement a hierarchical timing-wheel scheduler with bounded tick-overflow handling and prove zero scheduler drift under replay — gained in Phase 1 (§13).
  • Can design a single-mutable-owner packet pipeline that eliminates aliasing bugs by construction, not by convention — gained in Phase 2 (§14).
  • Can compile a topology DSL into an immutable, cycle-free, deterministically-hashed manifest — gained in Phase 3 (§15).
  • Can express chaos-engineering campaigns as a declarative, replayable fault DSL rather than ad hoc shell scripts — gained in Phase 4 (§16).
  • Can validate a transport implementation against reference traces (RTT estimators, fast retransmit, congestion windows) with numeric acceptance thresholds — gained in Phase 5 (§17).
  • Can build a WAL-backed replay engine with checksummed segments and forensic divergence detection — gained in Phase 6 (§18).
  • Can coordinate a distributed cluster through leases, heartbeats, and barrier synchronization that survives worker loss without split-brain — gained in Phase 7 (§19).
  • Can bridge a simulated network to real Linux workloads via namespaces/TAP/tc/eBPF without namespace leaks — gained in Phase 8 (§20).

Control plane (scenario-runner, topology-compiler, orchestrator): compiles scenarios into immutable, hash-stable execution plans; never processes a packet; the only path from control plane to runtime worker is the gRPC config/seed/barrier channel (a queue with backpressure, ADR-21 §9). Scenario DSL: declares topologies, traffic generators, failure timelines, timing semantics, observability directives; compiles to a plan whose hash is the replay key (I2, §7). Topology Compiler: validates the graph (cycle detection, connectivity), allocates deterministic node/link IDs, emits an immutable manifest (I5, §7). Simulation Coordinator: runtime registration, shard partitioning, deterministic seed propagation, distributed barrier sync (§19) — the trust boundary between control plane and workers. Virtual Clock: the concurrency boundary anchor — every worker thread reads one logical tick source; decouples simulation time from wall time (Lamport 1978, applied in §13). Event Scheduler: the persistence-adjacent boundary — every dequeue is a potential WAL write; hierarchical timing wheel (Varghese & Lauck 1987) bounds enqueue/dequeue to O(1). Packet Engine: the protocol boundary — parses wire bytes into PacketDescriptor (§11), applies queue discipline, fault injection, and congestion accounting in a fixed pipeline order. Fault Engine: a rule table evaluated per tick against scheduler events; durably logs every injected fault (I7, §7). Transport Models: TCP/UDP/QUIC behavior state machines consuming packet-engine output. Replay Engine: the durability boundary — every scheduler decision, fault injection, and RNG draw is appended to a checksummed WAL (I8, §7) before being visible to metrics. Metrics Pipeline: cardinality-guarded Prometheus export; the observability boundary all subsystems must cross (P5, §6). Storage Engine: persists manifests, WAL segments, snapshots, metrics segments; the only subsystem allowed direct disk I/O outside the WAL append path. External Interfaces: the kernel boundary — TAP/TUN and tc/eBPF are the only components that touch real kernel network state; PCAP/Prometheus/gRPC are the only components external tooling may reach.

6. Design Principles

  • P1 — Determinism Over Throughput. Rule: virtual-time mode never sacrifices replay-bit-exactness for speed · Tradeoff: caps event-scheduler parallelism to shard-local determinism, not global work-stealing · Operational: every scheduler decision logs a replay hash · Violated: replay-hash mismatches surface silently until forensic audit, invalidating every downstream conformance claim.
  • P2 — Bounded Resource Usage. Rule: every queue, cache, and buffer enforces a hard capacity limit · Tradeoff: bounded queues drop under burst rather than buffer unbounded latency · Operational: queue-depth metrics emitted every tick · Violated: unbounded growth exhausts the 8GB per-worker ceiling (§4) and OOM-kills the worker mid-run.
  • P3 — Replayability First. Rule: every scheduler decision, RNG draw, and fault injection is WAL-logged before being externally visible · Tradeoff: adds one WAL append per decision, capping raw throughput below the theoretical scheduler max · Operational: replay verifier re-executes from WAL and diffs hashes · Violated: an unlogged decision makes a captured incident non-reproducible, defeating the replay subsystem.
  • P4 — Crash-Only Recovery. Rule: every component restarts from durable state with no in-memory-only recovery path · Tradeoff: forces mutable state through persistence even when lighter in-memory recovery would suffice · Operational: startup always replays the last snapshot plus WAL tail · Violated: a component with hidden in-memory state loses that state silently on crash, producing an inconsistent restart.
  • P5 — Observability By Default. Rule: every subsystem emits metrics and structured trace spans without opt-in configuration · Tradeoff: baseline telemetry overhead is paid even in throughput-critical hot paths · Operational: the metrics cardinality guard rejects unbounded label sets · Violated: an uninstrumented subsystem becomes a blind spot the first time it degrades.
  • P6 — Stable Wire Compatibility. Rule: every wire protocol is explicitly versioned and append-only · Tradeoff: schema evolution is slower than free-form field changes · Operational: compatibility tests run every release against the last two major versions · Violated: an unversioned field change breaks replay of archived WAL segments (§25).
  • P7 — Explicit Ownership. Rule: every packet buffer has exactly one mutable owner, enforced at compile time · Tradeoff: forecloses zero-copy fan-out patterns that rely on shared mutable buffers · Operational: ownership transfer is the only mutation path, checked by the type system · Violated: aliased mutable access reintroduces the packet-corruption class this architecture exists to prevent.
  • P8 — Backpressure Everywhere. Rule: no unbounded channel exists anywhere in the system · Tradeoff: producers block or shed load under saturation instead of buffering indefinitely · Operational: every channel exposes a depth gauge and a shed-count counter · Violated: an unbounded channel becomes an unbounded memory leak under sustained overload (ADR-21, §9).
  • P9 — Time Is Virtualized. Rule: logical time dominates wall-clock time in every scheduling decision · Tradeoff: real-time emulation mode must explicitly reconcile logical and wall time at the boundary · Operational: virtual-clock exposes both logical tick and wall-clock skew · Violated: wall-clock leakage into scheduling logic breaks determinism the instant the host is under load.
  • P10 — Isolation Over Shared Mutation. Rule: shared mutable state across scheduler shards is minimized to the barrier-synchronization primitive alone · Tradeoff: cross-shard operations pay an explicit synchronization cost · Operational: shard boundaries are enforced by the type system, not convention · Violated: ad hoc cross-shard mutation reintroduces data races the shard model exists to eliminate.
  • P11 — Single Source of Truth. Rule: a topology manifest is immutable once simulation execution begins · Tradeoff: topology changes mid-run require a new manifest and a new run, not a live patch · Operational: manifest hash is checked at every worker registration · Violated: a mutated manifest mid-run makes two workers simulate two different topologies without detection.
  • P12 — Fail Closed. Rule: an invalid simulation state terminates execution rather than continuing degraded · Tradeoff: reduces uptime in favor of correctness — a degraded-but-running simulator is worse than a stopped one · Operational: every invariant violation (§7) triggers panic-safe shutdown · Violated: continuing past a violation produces output indistinguishable from correct output, silently corrupting every downstream conclusion.
  • P13 — Structured Telemetry Only. Rule: no ad hoc unstructured log lines; every log line carries a schema'd field set · Tradeoff: slightly higher per-line emission cost than free-form logging · Operational: log schema is validated in CI against the docs/adr/ field registries · Violated: unstructured logs cannot be correlated across the distributed trace, defeating forensic replay debugging.
  • P14 — Schema Evolution Is Mandatory. Rule: every persisted format (WAL, manifest, metrics segment) carries an explicit schema version · Tradeoff: every format change requires a migration path, not a silent overwrite · Operational: storage-engine rejects segments with an unrecognized schema version · Violated: an unversioned format change silently corrupts old archives on next read.
  • P15 — Operational Simplicity Matters. Rule: avoid runtime dependencies that are not load-bearing for a §4 budget · Tradeoff: sometimes forgoes a more elegant library in favor of fewer moving parts · Operational: every new dependency is justified against an ADR (§9) · Violated: dependency sprawl increases the supply-chain attack surface (§22) and the operational failure surface (§23) without a corresponding capability gain.

Debugging methodology: the deterministic simulator is the primary debugging tool, not a secondary aid — every invariant above maps to exactly one runtime assertion, and every assertion failure is reproducible by replaying the WAL segment that preceded it. An operator never debugs a live worker; they replay the failing seed locally, under the same assertion set, until the invariant violation reproduces deterministically.

8. Domain Model — Network Simulation Entities & Protocol State

Node — represents a host, router, switch, or endpoint. Fields: node_id (u32, stable post-compile per I5), role (enum: Host, Router, Switch, Endpoint), interfaces (Vec<InterfaceId>), routing_table (RouteTable, mutable only via TopologyMutation events), scheduler_binding (ShardId, assigned at compile time).

Link — represents a directed edge between two nodes. Fields: link_id (u32), source / target (NodeId), bandwidth_bps (u64), latency_distribution (LatencyModel), jitter (JitterModel), drop_policy (DropPolicy), corruption_policy (CorruptionPolicy). Immutable after topology-compiler emits the manifest (P11).

Packet — the unit of simulation. Fields: packet_id (u128), flow_id (u128), protocol (enum: TCP, UDP, QUIC), sequence_number (u64), timestamp (logical tick, u64), payload_descriptor (opaque byte-range reference, never a copy — P7), checksum (u32), flags (bitset). Exactly one mutable owner at all times (I3).

Flow — transport-layer connection state, one instance per (source, dest, protocol, ports) tuple. Owns congestion-window state, RTT estimator state, and retransmission-timer state (see transport-models, §17).

Event — the scheduler's unit of work. Variants: PacketIngress, QueueEnqueue, QueueDequeue, LinkTransmit, PacketDrop, FaultInject, Timeout, Retransmit, TopologyMutation. Every event carries a logical tick (I1) and a shard-local sequence number.

Packet lifecycle state machine:

CREATED --> QUEUED --> TRANSMITTING --> DROPPED
                              |
                              +--> CORRUPTED
                              |
                              +--> DELIVERED

Transitions are emitted as Event variants above; DROPPED and CORRUPTED are terminal and both increment fault-domain-tagged counters (I7). Only DELIVERED reaches the metrics pipeline as a successful-delivery sample.

Replay sequence: Scenario -> topology-compiler -> event-runtime scheduler -> replay-engine WAL -> replay snapshot. Every arrow is a durable, checksummed boundary (I8, I11) — a replay can resume from any snapshot without re-deriving upstream state.

Failure example — malformed packet checksum: packet-engine parser rejects the packet on checksum mismatch; a packet.checksum_invalid counter increments; a trace span is emitted with the flow ID and offending byte offset; a replay marker is persisted to the WAL before the packet is dropped (I7); the fault domain (link or node) is tagged for blast-radius analysis (§23). This sequence is the canonical example referenced by the malformed-checksum fixture family in §14.5.

11. Core Schema & Types

struct PacketDescriptor
  packet_id: u128
  flow_id: u128
  protocol: TransportKind
  ingress_tick: u64
  payload_len: u32
  flags: PacketFlags
  • Ownership: single mutable owner, transferred not shared (I3, P7). Mutation: none after creation — fields set once by the parser. Concurrency: Send, never Sync; crosses shard boundaries only via ownership transfer through a bounded channel (P8). Persistence: replay-safe — serialized verbatim into the WAL (I8). Serialization: Prost/protobuf, schema version 1 (ADR-05, P14). Compatibility: append-only field additions permitted; no field ever removed or renumbered (P6).
struct EventEnvelope
  event_id: u128
  logical_tick: u64
  actor_id: u32
  event_type: EventKind
  payload_ref: PayloadRef
  • Ownership: owned by the scheduler shard that produced it until dequeued. Mutation: immutable after enqueue. Concurrency: strictly monotonic ordering per shard (I1); no cross-shard mutation. Persistence: every envelope is WAL-appended before dispatch (P3). Serialization: Prost/protobuf, schema version 1. Compatibility: event_type enum is append-only; unknown variants are a hard parse error, never silently ignored (P12).
struct SchedulerShard
  shard_id: u16
  timing_wheel: TimingWheelHandle
  local_queue: BoundedQueue<EventEnvelope>
  inflight_budget: u32
  metrics_handle: MetricsHandle
  • Ownership: one shard owns exactly one core; no shared mutable state across shards (P10). Mutation: inflight_budget decremented/incremented atomically within the shard thread only. Concurrency: single-threaded execution per shard by construction. Persistence: shard state is snapshotted, not individually WAL-logged (WAL logs events, not shard structs). Serialization: snapshot-only, internal binary format, schema version 1. Compatibility: snapshot format versioned; old snapshots rejected by storage-engine on schema mismatch (I12).
struct LinkModel
  bandwidth_bps: u64
  latency_distribution: LatencyModel
  drop_probability: f32
  corruption_probability: f32
  queue_capacity: u32
  • Ownership: owned by the topology manifest, immutable after compilation (P11). Mutation: none at runtime; a topology change requires a new manifest. Concurrency: Sync, read freely by any worker holding the manifest. Persistence: embedded in the manifest, persisted once. Serialization: Prost/protobuf, schema version 1. Compatibility: append-only.
struct ReplayRecord
  event_hash: [u8; 32]
  seed: u64
  scheduler_state_hash: [u8; 32]
  timestamp: u64
  • Ownership: owned by replay-engine, one record per WAL segment epoch. Mutation: none — write-once. Concurrency: written by exactly one WAL-writer thread per shard. Persistence: the WAL itself (I8, I11). Serialization: fixed binary layout, checksummed (CRC64). Compatibility: hash algorithm is pinned per schema version; changing it requires a major version bump (P6).
struct FaultRule
  selector: TopologySelector
  trigger: TriggerCondition
  action: FaultAction
  duration: TickSpan
  • Ownership: owned by fault-engine's rule table, loaded from the scenario DSL. Mutation: immutable once the scenario plan is compiled (P11). Concurrency: read-only from every worker thread during evaluation. Persistence: the rule table is embedded in the scenario plan hash. Serialization: Prost/protobuf. Compatibility: append-only FaultAction variants; unknown actions are a hard parse error.
struct MetricSample
  metric_id: u32
  timestamp: u64
  labels: LabelSet
  value: f64
  • Ownership: owned by the emitting subsystem until handed to metrics-pipeline's registry. Mutation: none after emission. Concurrency: Send; delivered over a bounded channel (P8, I13). Persistence: aggregated into metrics segments, not individually durable. Serialization: internal binary format for segments; Prometheus exposition format at scrape time (ADR-11). Compatibility: LabelSet cardinality is capped by the metrics cardinality guard (§4); new label keys require a registry entry.
struct TopologyManifest
  manifest_hash: [u8; 32]
  nodes: Vec<NodeDescriptor>
  links: Vec<LinkModel>
  route_tables: Vec<RouteTable>
  compiled_at_tick: u64
  • Ownership: owned by topology-compiler at compile time, then shared read-only across all workers (I5, P11). Mutation: none after compiled_at_tick. Concurrency: Sync. Persistence: persisted once per scenario run, referenced by hash thereafter. Serialization: Prost/protobuf, schema version 1. Compatibility: append-only.
struct WorkerLease
  lease_token: u128
  shard_id: u16
  worker_id: u32
  expires_at_tick: u64
  • Ownership: owned by orchestrator's lease table; exactly one lease per shard at a time (I10). Mutation: expires_at_tick extended on heartbeat, never on any other path. Concurrency: lease grant/revoke is the one operation guarded by a lock in the otherwise lock-free orchestrator (ADR-08 exception, documented there). Persistence: lease table is snapshotted on every barrier epoch. Serialization: internal binary format. Compatibility: schema-versioned like all snapshots (P14).

  • Bootstrap the 15-crate Cargo workspace (§1 Phase 0 deliverable list) with reproducible builds.

  • Stand up the correctness kernel: deterministic seed generation and build-metadata injection that every later phase depends on for replay (P3, I2).

12.2 Detailed Implementation Steps

  • Create the Cargo workspace (Cargo.toml, rust-toolchain.toml) pinning the toolchain exactly (ADR-19); add all 15 member crates as empty lib.rs/main.rs stubs with signatures only.
  • Define the dependency policy: cargo-vet audit manifest, vendored Cargo.lock, CI gate that fails on an unaudited transitive dependency (ADR-03).
  • Configure rustfmt.toml and a clippy.toml deny-list (deny unwrap_used, expect_used in non-test code — enforces P12 Fail Closed at the lint level).
  • Establish tracing-crate span-naming conventions in docs/adr/0001-language-choice.md and a companion field registry (P13).
  • Define the protobuf schema root (sim-core crate) with schema-version 1 for every message type listed in §11 (P14).
  • Implement the configuration loader (TOML) in sim-core::ownership module boundary, rejecting unknown keys (P12).
  • Implement the deterministic seed generator: a ChaCha20-based CSPRNG seeded from an explicit u64, never from OS entropy at runtime (P1, I2) — the single most load-bearing piece of Phase 0.
  • Implement the build-metadata injector: embeds git commit hash, toolchain version, and a reproducibility flag into every compiled binary (ADR-19).
  • Establish the Criterion benchmark harness skeleton in benchmarks/ (ADR-19 empirical basis for later throughput claims, §28).
  • Wire GitHub Actions (ci.yml): build matrix (stable + MSRV), cargo test --workspace, cargo clippy --workspace -- -D warnings, cargo audit.

12.3 Deliverable

A cargo build --workspace --locked that compiles all 15 crates as empty-but-linked stubs, a green CI pipeline, and a deterministic-seed generator whose output is reproducible across two independent build machines given the same seed and toolchain version.

12.4 Acceptance Criteria

  • All 15 crates compile under --locked with zero clippy warnings on the deny-list.
  • CI green on 3 consecutive runs with identical build-metadata hash (build.reproducible_hash).
  • Deterministic seed generator produces bit-identical 10,000-draw sequences across 2 hosts for the same seed — verified against conformance/config-valid.toml.
  • Config loader rejects conformance/config-invalid.toml with a structured error, not a panic.

12.5 Conformance Fixtures

  • conformance/config/config-valid.toml — a minimal valid workspace config; expected: loads without error, all defaults populated.
  • conformance/config/config-invalid.toml — an unknown top-level key; expected: structured ConfigError::UnknownKey rejection, no panic.
  • conformance/build/seed-replay.fixture — a fixed seed value; expected: identical 10,000-value draw sequence on repeat invocation (regression case for I2 introduced this early).

12.6 Pitfalls

  • Dependency version drift between contributors' local Cargo.lock and CI's vendored lock — root cause: cargo update run locally without --locked; signal: CI build-metadata hash differs from a clean-checkout build; recovery: re-vendor and re-audit, never hand-edit the lock.
  • Nondeterministic build metadata from timestamp-based version strings — root cause: using env!("CARGO_PKG_VERSION") plus wall-clock build time; signal: two builds of the same commit produce different build.reproducible_hash; recovery: strip wall-clock from the injector.
  • Silent CSPRNG reseeding from OS entropy on a library upgrade — root cause: a transitive dependency defaulting to OsRng; signal: seed-replay fixture fails intermittently; recovery: pin the RNG crate version and add a unit test asserting the seed path never touches /dev/urandom.

12.7 Performance Concerns

  • Compile-time explosion from 15 crates with proc-macro-heavy dependencies (serde_derive, prost-derive) — mitigate with sccache in CI and minimizing derive macro fan-out per crate.
  • Proc-macro overhead on incremental rebuilds during local development — mitigate by keeping schema definitions in a single low-churn crate (sim-core) rather than duplicated per crate.

12.8 Edge Cases

  • Invalid config merges when both a file and an environment-variable override target the same key — resolved with an explicit precedence order (env > file > default), tested explicitly.
  • Missing required environment variables in CI vs local dev — the loader must fail closed (P12) with a named-variable error, not fall back to an undocumented default.
  • A workspace member crate with a Cargo.toml that omits the pinned toolchain — CI must reject this at the workspace-lint stage, not at a downstream crate's build failure.

12.9 Failure Analysis

CI divergence (different build-metadata hash on ostensibly identical commits) indicates dependency instability upstream of any scheduling code — the failure is caught at the cheapest possible point in the pipeline, before Phase 1 has any code to blame. Blast radius is limited to CI; no runtime component exists yet. Operator visibility: the ci.yml matrix job posts the build-metadata hash as a check annotation, diffable across runs.

12.10 Operational Notes

  • Metric: none yet (no runtime); tracing span: none yet.
  • Signed release artifacts are mandatory from the first tagged release onward (ADR-17) — the signing key and cosign policy are established in this phase even though nothing ships yet.
  • Structured-log field registry (docs/adr/0001-language-choice.md) is the compatibility contract every later phase's tracing spans must conform to (P13).
  • Migration note: schema-version 1 protobuf definitions from this phase are the compatibility floor for §25 — any later schema change is additive only.

13. Phase 1 — Deterministic Event Runtime

13.1 Objectives

  • Implement the hierarchical timing-wheel scheduler and virtual clock — the correctness core every later phase schedules work through.
  • Guarantee monotonic event ordering (I1) and zero scheduler drift under replay (I2, §4).
  • Establish the bounded-channel discipline (P8) that all inter-shard communication will use.

13.2 Detailed Implementation Steps

  • Implement EventEnvelope (§11) in event-runtime::scheduler with the exact field set locked in §11 — no additional mutable fields.
  • Implement the hierarchical timing wheel per Varghese & Lauck 1987 (Hashed and Hierarchical Timing Wheels, SOSP): multi-level wheel with configurable tick resolution (1µs, matching the §4 p50 latency budget), O(1) amortized enqueue/dequeue.
  • Define SchedulerShard (§11) ownership: one shard per core, no cross-shard mutable state (P10, ADR-08).
  • Implement logical-tick advancement in virtual-clock::clock, decoupled from wall-clock reads (P9) — informed by Lamport 1978 logical-clock ordering.
  • Define timing-wheel overflow handling: ticks beyond the current wheel's max horizon roll into an overflow bucket re-inserted on wheel rotation (bounds unbounded wheel growth, P2).
  • Implement replay-seed injection at scheduler-shard startup, threading the Phase 0 CSPRNG through every nondeterministic decision point (I2).
  • Define scheduler metrics: tick-advancement rate, per-shard queue depth, dispatch latency histogram (P5).
  • Implement the deterministic ordering comparator: primary key logical tick, secondary key shard-local sequence number, tertiary key event-type discriminant — total order, no ties (I1).
  • Create bounded MPSC channels (sim-core channel wrapper) for all cross-shard communication, each exposing a depth gauge and shed-count counter (P8, I13).
  • Implement scheduler snapshots: periodic shard-state serialization for crash-only recovery (P4).
  • Add tracing spans for event lifecycle: event.enqueue, event.dispatch, event.complete.

13.3 Deliverable

A standalone event-runtime binary capable of ingesting a synthetic event stream and replaying it deterministically from a fixed seed, exposing scheduler-lag and queue-depth metrics on a local Prometheus endpoint.

13.4 Acceptance Criteria

  • Sustains 10,000,000 events/sec on a single host in virtual-time mode (interim target toward the §4 15M ceiling, reached fully once packet-engine integration lands in §14).
  • Produces bit-identical replay hashes across 100 consecutive replays of conformance/scheduler/replay-determinism.fixture.
  • Zero scheduler-drift events recorded across a 10-million-tick soak run.

13.5 Conformance Fixtures

  • conformance/scheduler/scheduler-ordering.fixture — events with intentionally colliding timestamps; expected: comparator resolves via shard-sequence tiebreak, stable order every run.
  • conformance/scheduler/replay-determinism.fixture — a fixed seed, 1M-event stream; expected: identical replay hash across 100 runs.
  • conformance/scheduler/timing-overflow.fixture — events scheduled beyond the wheel's horizon; expected: correct overflow-bucket rollover, no dropped events.

13.6 Pitfalls

  • Starvation under uneven shard load — manifestation: one shard's queue depth grows unbounded while others idle; root cause: static topology-to-shard assignment ignoring traffic skew; debugging method: replay with per-shard queue-depth trace enabled; signal: queue.depth gauge divergence across shards; recovery: rebalance shard assignment in the topology compiler (§15).
  • Timing-wheel overflow bugs — manifestation: events silently dropped past the wheel horizon; root cause: off-by-one in overflow-bucket rotation; debugging method: replay timing-overflow.fixture with assertion-level tracing; signal: event count mismatch between ingress and delivery; recovery: fix rotation boundary, add regression fixture.
  • Unstable comparator ordering — manifestation: two replays of the same seed diverge; root cause: a non-deterministic tiebreak (e.g. using Instant::now() as a hidden fourth key); debugging method: diff the two replay hash chains to find the first divergent tick; recovery: audit the comparator for any wall-clock or memory-address-derived key.

13.7 Performance Concerns

  • Cache locality for wheel buckets: co-locate hot buckets (near-horizon ticks) in a contiguous array rather than a linked structure to avoid pointer-chasing on the dispatch hot path.
  • Heap allocations in event dispatch: pool EventEnvelope allocations (object pool in sim-core) to avoid per-event malloc/free at 15M events/sec.
  • Lock contention: none by construction (ADR-08) — any observed contention is a design defect, not a tuning problem.

13.8 Edge Cases

  • Two events with identical (tick, shard, type) triple — must be structurally impossible given the sequence-number component of shard-local IDs; tested explicitly.
  • Integer overflow of the logical-tick counter at u64 max — detected proactively, simulation halts (P12) rather than wrapping silently.
  • Replay divergence mid-stream — captured via replay-divergence snapshot persisted to WAL (handed to replay-engine in §18) for forensic analysis.

13.9 Failure Analysis

A scheduler-drift detection immediately halts the affected shard (P12, I1) and persists a divergence snapshot. Blast radius is contained to the shard; other shards continue under P10 isolation. Operator visibility: scheduler.tick.monotonic_violation counter pages on any nonzero value (§4 zero-tolerance budget). Postmortem guidance: replay from the last matching snapshot and diff comparator inputs tick-by-tick.

13.10 Operational Notes

  • Metrics: scheduler.lag_ticks, scheduler.queue_depth{shard}, scheduler.dispatch_latency_us.
  • Tracing spans: event.enqueue, event.dispatch, event.complete, each carrying shard_id and logical_tick fields (P13).
  • Deployment: event-runtime ships as a library linked into cli and orchestrator workers, not a standalone service in this phase.
  • Rollback: scheduler snapshots are schema-versioned (P14); a rollback to a prior binary version requires a snapshot compatible with that version's schema.

  • Implement PacketDescriptor (§11) parsing in packet-engine::parser, validating checksum before any downstream processing touches the packet (fail closed, P12).
  • Implement a packet-buffer pool (packet-engine::pool) to bound allocator churn — informed by Varghese 2004 (Network Algorithmics) buffer-management chapter.
  • Implement queue disciplines in packet-engine::queue: tail-drop (simple bounded FIFO) and RED (Random Early Detection, probabilistic pre-capacity dropping) — RED thresholds informed by Alizadeh et al. 2010 (DCTCP) shallow-queue marking behavior.
  • Implement the packet-corruption engine as a post-queue, pre-delivery stage with a configurable corruption probability (LinkModel, §11), bounded to the < 5% runtime-impact budget (§4).
  • Implement congestion accounting hooks that transport-models (§17) will consume — exposed as read-only counters, never mutated outside the owning flow.
  • Add packet telemetry hooks: per-stage counters (ingress, queued, dropped, corrupted, delivered) feeding metrics-pipeline.
  • Add packet tracing identifiers: every packet carries a trace-correlatable ID from ingress through delivery or drop (P13).
  • Implement packet-cloning restrictions: cloning a PacketDescriptor is a compile-error-level operation outside an explicit duplicate_for_multicast API that produces a new packet_id (preserves I3 even under multicast fan-out).

14.3 Deliverable

A packet-simulation runtime that ingests synthetic packet streams through parse → queue → corrupt → deliver, exposing per-stage counters and enforcing the single-owner invariant at compile time.

14.4 Acceptance Criteria

  • Sustained 5,000,000 packet-state-transitions/sec on a single host (interim milestone toward the §4 aggregate scheduling-throughput budget).
  • Zero packet-ownership violations detected across a 1-hour soak (structurally guaranteed by I3, verified by the absence of any unsafe alias in packet-engine).
  • conformance/packet/queue-overflow.fixture sheds packets at exactly the configured capacity, not one packet before or after.

14.5 Conformance Fixtures

  • conformance/packet/malformed-checksum.fixture — a packet with a corrupted checksum byte; expected: parser rejection, packet.checksum_invalid counter increments, no panic.
  • conformance/packet/packet-reorder.fixture — packets delivered out of send order; expected: sequence numbers preserved, no silent reordering inside the queue discipline itself.
  • conformance/packet/queue-overflow.fixture — a burst exceeding queue capacity; expected: drop count equals burst size minus capacity, exactly.

14.6 Pitfalls

  • Packet aliasing via a well-intentioned "peek" API — manifestation: two code paths mutate the same buffer; root cause: an API that returns a mutable reference instead of transferring ownership; debugging method: unsafe-audit grep across packet-engine; signal: nondeterministic corruption in fixtures that should be deterministic; recovery: replace peek-and-mutate with ownership-transfer-and-return APIs.
  • Queue starvation under RED misconfiguration — manifestation: low-priority flows never drain; root cause: RED threshold set below sustained average queue depth; debugging method: replay with per-flow queue-residency tracing; signal: flow-level p99 latency divergence; recovery: retune RED thresholds against measured traffic profile, not a default guess.
  • Memory fragmentation from variable-size payload descriptors — manifestation: pool allocator churn increases despite pooling; root cause: payload sizes not bucketed before pooling; recovery: bucket the pool by payload-size class (jumbo vs standard).

14.7 Performance Concerns

  • Allocator churn: pool-allocate PacketDescriptor and payload buffers separately, sized by class, to avoid a general-purpose allocator on the 5M/sec hot path.
  • Packet-copy amplification: the pipeline must pass ownership, never clone, between parse and delivery — any observed memcpy on the hot path is a correctness-adjacent performance defect.
  • Corruption-engine overhead: bounded to < 5% of runtime impact (§4) by sampling corruption probability once per packet, not per byte.

14.8 Edge Cases

  • Jumbo frames exceeding the default pool bucket size — routed to an oversized-payload bucket, never silently truncated.
  • Malformed payloads with a valid checksum but invalid protocol field — rejected at the transport-model boundary (§17), not silently passed through as an unknown protocol.
  • Duplicate sequence numbers within one flow — flagged as a packet.duplicate_sequence counter, not silently deduplicated (deduplication is a transport-model decision, not packet-engine's).

14.9 Failure Analysis

Packet-corruption incidents are tagged per flow and per fault domain (link or node) at the moment of corruption, not reconstructed after the fact — this is required for the fault-engine (§16) blast-radius reporting to be accurate. Detection is immediate (checksum or corruption-flag check); containment is per-packet (a corrupted packet never propagates state into the flow's congestion accounting). Operator visibility: queue-depth histograms and per-stage drop counters.

14.10 Operational Notes

  • Metrics: packet.stage_count{stage}, packet.checksum_invalid, queue.depth_histogram.
  • Tracing: packet trace ID propagated as a span attribute from ingress through terminal state.
  • Deployment: packet-engine links into event-runtime workers; no independent deployment unit.
  • Compatibility: PacketFlags bitset is append-only (P6); a new flag bit never reuses a retired bit's position, even after the retiring flag is fully deprecated.

15. Phase 3 — Topology Compiler

15.1 Objectives

  • Compile the scenario DSL's topology declarations into an immutable, hash-stable manifest (P11).
  • Detect invalid graphs (cycles in routing, disconnected components) before any worker registers.
  • Support topologies up to the 1,000,000-node §4 ceiling with tractable compile time.

15.2 Detailed Implementation Steps

  • Implement the DSL parser in topology-compiler::compiler, producing an intermediate graph representation before validation (fail closed on syntax error, P12).
  • Implement the graph validator: cycle detection over routing-table declarations (BGP/OSPF adapters informed by RFC 4271 and RFC 2328 loop-prevention semantics), connectivity check.
  • Allocate deterministic node/link IDs (topology-compiler::graph) via a stable topological ordering, not insertion order, so the same DSL source always compiles to the same ID assignment (I5).
  • Compute route tables per node using shortest-path computation seeded from the OSPF-adapter cost model.
  • Generate the manifest hash: a Merkle-style hash over nodes, links, and route tables, forming the replay key referenced throughout (I2, P11).
  • Implement the schema validator against the §11 TopologyManifest schema-version contract (P14).
  • Add a topology-diff engine for operator tooling: diffs two manifests' node/link sets for pre-deployment review, never used at runtime (runtime manifests are immutable, P11).

15.3 Deliverable

A deterministic topology compiler CLI subcommand (cli topology compile) that turns a .dsl scenario file into a hash-stable TopologyManifest, rejecting cyclic or disconnected graphs with a structured diagnostic.

15.4 Acceptance Criteria

  • Identical DSL source compiles to an identical manifest hash across 50 repeated compilations.
  • Compiles a 1,000,000-node synthetic topology (§4 ceiling) in under 5 seconds (matches the coordinator startup-time budget, §4).
  • conformance/topology/cyclic-topology.fixture and disconnected-graph.fixture are both rejected with a named TopologyError variant, never a panic.

15.5 Conformance Fixtures

  • conformance/topology/cyclic-topology.fixture — a routing declaration forming a loop; expected: TopologyError::RoutingCycle with the offending node IDs named.
  • conformance/topology/disconnected-graph.fixture — two node sets with no connecting link; expected: TopologyError::Disconnected naming the isolated component.
  • conformance/topology/million-node.fixture — a synthetic 1,000,000-node topology generator fixture; expected: compiles within the 5-second budget above.

15.6 Pitfalls

  • Inconsistent ID allocation across compiler versions — manifestation: the same DSL source compiles to a different manifest hash after a compiler upgrade; root cause: a change to iteration order in the topological sort; debugging method: diff two manifests via the topology-diff engine; signal: replay fixtures fail post-upgrade despite unchanged DSL source; recovery: pin the topological-sort tiebreak rule and version it (P6).
  • Hidden route ambiguity when two equal-cost paths exist — manifestation: nondeterministic route selection across compiles; root cause: tiebreak omitted from the shortest-path computation; recovery: add an explicit deterministic tiebreak (lowest node ID) and a regression fixture.

15.7 Performance Concerns

  • Graph-traversal cost at 1,000,000 nodes: cycle detection and shortest-path computation must stay near-linear (adjacency-list traversal, not adjacency-matrix) to hit the 5-second budget.
  • Manifest-hash computation cost scales with node/link count; computed incrementally during traversal rather than as a separate full-manifest pass.

15.8 Edge Cases

  • A topology with exactly one node and no links — valid, trivially connected; must not be misclassified as disconnected.
  • A self-loop link (source equals target) — rejected explicitly, not silently treated as a zero-latency shortcut.
  • A topology at exactly the 1,000,000-node ceiling — must compile within budget, not degrade catastrophically one node past a soft internal limit.

15.9 Failure Analysis

The compiler emits a structured validation trace on any rejection, naming the exact offending node/link IDs — never a generic "invalid topology" message, since operators debugging a million-node scenario need the pinpoint. Blast radius is compile-time only; a rejected topology never reaches a worker (I5 enforced before registration).

15.10 Operational Notes

  • Metrics: topology.compile_duration_ms, topology.node_count, topology.rejected_total{reason}.
  • Manifests are immutable once execution begins (P11) — this is enforced by the orchestrator refusing any manifest-hash change mid-run, not by the compiler itself.
  • Compatibility: manifest schema is append-only (P6); a new node/link field requires a schema version bump, never an in-place field reinterpretation.

16. Phase 4 — Fault Injection Framework

16.1 Objectives

  • Implement deterministic, replayable fault orchestration: drops, latency spikes, corruption bursts, node isolation — driven by a declarative rule table (P3, P1).
  • Guarantee every injected fault is durably attributable (I7) for blast-radius analysis.

16.2 Detailed Implementation Steps

  • Implement the fault DSL in fault-engine::rules, compiled alongside the scenario plan (P11) — a FaultRule (§11) selector, trigger condition, action, and duration.
  • Define trigger conditions evaluated against scheduler events per tick: tick-range triggers, topology-selector triggers, and conditional triggers (e.g. "after N retransmits on flow X").
  • Implement the packet-drop injector as a fault-engine::injectors stage inserted into the packet-engine pipeline (§14) between queue and delivery.
  • Implement latency-spike injection: a temporary LatencyModel override applied to a link selector for the rule's duration, then reverted deterministically.
  • Implement node-isolation injection: severs all links for a selected node for the rule's duration, modeled as a link-level drop-probability override rather than a topology mutation (preserves I5 manifest immutability).
  • Implement corruption-burst injection reusing the Phase 2 (§14) corruption engine with a fault-scoped probability override.
  • Persist every fault event to the replay-engine WAL before the fault takes effect (I7, P3) — this ordering is load-bearing: a fault that is applied before being logged is unrecoverable from an audit perspective.
  • Implement fault timelines: an ordered, replayable sequence of fault events per scenario run, queryable by the trace-analysis tooling (deferred to §21 for the visualization surface).

16.3 Deliverable

A programmable chaos-injection runtime (fault-engine) that applies scenario-declared faults deterministically and replays an identical fault timeline given the same seed.

16.4 Acceptance Criteria

  • 100% of injected faults across conformance/fault/latency-spike.fixture and split-brain.fixture are durably logged before taking effect, verified by WAL-order audit.
  • Deterministic replay of all injected faults across 20 repeated runs of the same scenario seed.
  • Rule-matching overhead stays under 2% of per-tick scheduler budget at 10,000 active rules.

16.5 Conformance Fixtures

  • conformance/fault/latency-spike.fixture — a scripted latency spike on one link; expected: latency reverts exactly at duration expiry, logged fault matches applied fault.
  • conformance/fault/split-brain.fixture — simultaneous node isolation on two coordinator candidates; expected: both isolations logged with overlapping-window metadata for §19 analysis.
  • conformance/fault/overlapping-windows.fixture — two fault rules targeting the same link with overlapping durations; expected: deterministic composition order (rule-declaration order), not last-write-wins by evaluation timing.

16.6 Pitfalls

  • Nondeterministic timer usage inside a fault action — manifestation: a fault's revert time drifts across replays; root cause: using wall-clock Instant instead of logical tick for duration; debugging method: diff fault-timeline logs across two replays of the same seed; signal: replay.hash.mismatch triggered specifically during a fault-active window; recovery: audit every FaultAction implementation for wall-clock reads (P9 violation).
  • Rule-table evaluation order ambiguity — manifestation: two rules targeting the same selector apply in different orders across replays; root cause: rule iteration over an unordered collection; recovery: rules are stored and iterated in declaration order (P11), never a hash-map iteration order.

16.7 Performance Concerns

  • Excessive rule-matching overhead at high rule counts — mitigate with a topology-selector index (node/link ID to applicable-rule-set) computed once per manifest compile, not re-scanned per tick.
  • Fault-application overhead composes with packet-engine corruption overhead; both must stay within the combined < 5% runtime-impact budget (§4).

16.8 Edge Cases

  • Overlapping fault windows on the same target — resolved by declaration-order composition (16.6), tested by overlapping-windows.fixture.
  • A fault rule targeting a node that does not exist in the compiled manifest — rejected at scenario-compile time (fail closed, P12), not silently ignored at evaluation time.
  • A fault duration that outlives the scenario's total run length — the fault simply never reverts within the run; this is valid and must not be treated as an error.

16.9 Failure Analysis

The fault engine emits blast-radius metadata (affected node/link IDs, affected flow count) at the moment a fault is applied, feeding directly into §22 threat-model and §23 failure-mode tooling for chaos-campaign postmortems. Detection is by construction (the rule evaluator knows exactly what it targeted); containment is scoped to the rule's selector, never broader.

16.10 Operational Notes

  • Metrics: fault.applied_total{action}, fault.rule_match_latency_us, fault.active_count.
  • All faults are tagged with the originating scenario ID (P13) for cross-run correlation.
  • Deployment: fault-engine links into event-runtime workers, driven by the compiled scenario plan distributed from the coordinator (§19).
  • Rollback: fault rule-table format is schema-versioned; a scenario compiled under a newer schema is rejected by an older worker rather than silently misapplied (I12).

17. Phase 5 — Transport Models

17.1 Objectives

  • Implement TCP/UDP/QUIC behavior models on top of the packet engine (§14): retransmission, congestion windows, RTT estimation, ACK handling.
  • Validate against real transport traces, not just internal consistency (RFC 793, RFC 9293, RFC 9000 §17).

17.2 Detailed Implementation Steps

  • Implement retransmission timers in transport-models::tcp per RFC 9293 RTO computation (smoothed RTT plus variance), keyed off the logical clock (§13), never wall-clock (P9).
  • Implement congestion windows: CUBIC as the default, with a BBR variant informed by Cardwell et al. 2016 (BBR: Congestion-Based Congestion Control, ACM Queue) bandwidth/RTT-probing model.
  • Implement RTT estimators (Jacobson/Karels-style smoothing) consuming ACK timestamps from the packet-engine telemetry hooks (§14.2).
  • Implement ACK handling: cumulative and selective (SACK) acknowledgment per RFC 9293 section 3.8.
  • Implement the QUIC stream abstraction in transport-models::quic per RFC 9000 §17 packet- numbering and loss-detection intervals — separate loss-detection state per stream, not per connection, matching the RFC's multiplexing model.
  • Implement flow accounting: per-Flow (§11 domain model) byte and packet counters feeding congestion-window decisions.
  • Add retransmission metrics: fast-retransmit count, RTO-triggered retransmit count, spurious- retransmit count (the last requires SACK-based detection).
  • Implement pacing algorithms: BBR-style paced sending to avoid burst-induced queue pressure at the packet-engine queue discipline boundary (§14).

17.3 Deliverable

A transport-capable packet-simulation runtime that reproduces reference TCP and QUIC traces — fast retransmit, RTO backoff, congestion-window growth/collapse — under virtual time.

17.4 Acceptance Criteria

  • Conformance against conformance/transport/tcp-fast-retransmit.fixture: fast retransmit fires on exactly the 3rd duplicate ACK, matching RFC 9293 section 3.8.3.
  • CUBIC congestion-window growth within 5% of the reference trace's window trajectory over a 10,000-packet exchange.
  • QUIC loss detection triggers within the RFC 9000 §17-specified packet-threshold and time- threshold bounds on conformance/transport/quic-loss.fixture.

17.5 Conformance Fixtures

  • conformance/transport/tcp-fast-retransmit.fixture — 3 duplicate ACKs on a known sequence; expected: fast retransmit fires exactly once, congestion window halves per CUBIC.
  • conformance/transport/quic-loss.fixture — a scripted packet-loss pattern; expected: loss detected within RFC 9000 §17 packet/time thresholds, correct stream-level isolation.
  • conformance/transport/ack-storm.fixture — a burst of 10,000 ACKs in one tick; expected: ACK-processing stays within the pacing budget, no congestion-window overreaction.

17.6 Pitfalls

  • Timer explosion under many concurrent flows — manifestation: per-flow RTO timers overwhelm the timing wheel; root cause: one wheel-slot registration per flow instead of batched registration; debugging method: profile timing-wheel bucket occupancy under a 1M-flow load; signal: scheduler.dispatch_latency_us p99 regression; recovery: batch RTO checks per tick rather than per-flow timer registration.
  • Flow-memory leaks from connections that never reach a terminal state — manifestation: flow table grows unbounded; root cause: no idle-flow eviction policy; recovery: add a bounded idle-timeout eviction consistent with P2.

17.7 Performance Concerns

  • Per-flow state amplification: at 50,000,000 max active flows (§4), even a compact per-flow state struct multiplies quickly — bucket flow state by size class like packet buffers (§14.7).
  • ACK-processing batching: process ACKs in per-tick batches rather than one scheduler event per ACK to amortize dispatch overhead.

17.8 Edge Cases

  • ACK storms (17.5 fixture) must not trigger spurious congestion-window collapse.
  • Sequence-number wraparound at u32/u64 boundaries — must use wraparound-safe comparison, not naive integer comparison (a classic TCP implementation bug class, Stevens 1994 ch. 17–21).
  • Simultaneous close on both ends of a flow — must resolve to a single terminal state, not a double-free-style double-teardown of flow state.

17.9 Failure Analysis

Retransmission anomalies (spurious retransmits, RTO storms) are persisted per flow with the triggering packet-engine trace ID (§14.10) attached, so a transport-level anomaly can be traced back to its packet-level cause without re-running the scenario. Blast radius is per-flow; transport-model state corruption in one flow must never propagate into another flow's congestion-window state (isolation enforced by Flow ownership, §11).

17.10 Operational Notes

  • Metrics: transport.retransmit_total{cause}, transport.cwnd_bytes{flow_class}, transport.rtt_estimate_us.
  • Flow-level dashboards are mandatory before this phase is considered done — an aggregate-only view hides per-flow congestion collapse (Alizadeh et al. 2010 DCTCP motivation).
  • Compatibility: congestion-control algorithm selection is a per-scenario config, versioned alongside the scenario plan (P6) so archived scenarios always replay under their original algorithm.

18. Phase 6 — Replay Engine

18.1 Objectives

  • Implement the durable WAL-backed replay subsystem: every scheduler decision, fault injection, and RNG draw becomes forensically reconstructible (P3, I8, I11).
  • Detect replay divergence reliably, not approximately (I2).

18.2 Detailed Implementation Steps

  • Implement the WAL segment writer in replay-engine::wal: append-only, CRC64-checksummed segments (I11), rotated at a configured size threshold (ADR-04 segment-WAL rationale, §9).
  • Implement the replay cursor (replay-engine::cursor): sequential read position over one or more WAL segments, resuming from any snapshot boundary (P4).
  • Implement state snapshots: periodic full-state serialization of scheduler shards and flow tables, schema-versioned (P14, I12).
  • Implement the replay verifier: re-executes a WAL segment against the deterministic scheduler (§13) and diffs the resulting hash chain against the recorded ReplayRecord (§11) hashes (I2).
  • Implement replay diffing: given two divergent replay hash chains, binary-searches the first divergent tick rather than linear-scanning (informed by the debugging methodology closing §7).
  • Implement replay compression: zstd-compressed WAL segments (ADR-15) bounded to the < 1.5x raw-event amplification budget (§4).
  • Add a replay-timeline exporter for the trace-analysis surface (deferred to §21).

18.3 Deliverable

A deterministic replay subsystem (replay-engine) that can reconstruct any prior simulation run from its WAL, detect divergence at tick granularity, and export a compressed archive within the §4 storage-write-amplification budget.

18.4 Acceptance Criteria

  • Replay-divergence detection localizes the first divergent tick within 1 binary-search pass over a 10-million-tick WAL segment (log2(10M) ≈ 24 comparisons).
  • WAL segment amplification measured at < 1.5x raw event size on conformance/replay/replay-divergence.fixture.
  • 100% of replay-divergence.fixture runs correctly identify the injected divergence point.

18.5 Conformance Fixtures

  • conformance/replay/replay-divergence.fixture — a WAL segment with a deliberately injected hash mismatch at a known tick; expected: replay verifier localizes exactly that tick.
  • conformance/replay/wal-partial-corruption.fixture — a WAL segment truncated mid-write; expected: checksum failure detected at the truncation boundary, fallback to last valid snapshot.
  • conformance/replay/compression-ratio.fixture — a representative 1-hour scenario WAL; expected: compressed size within the < 1.5x amplification budget.

18.6 Pitfalls

  • Nondeterministic RNG usage anywhere outside the Phase 0 seeded CSPRNG — manifestation: replay diverges despite an apparently correct WAL; root cause: a library call to rand::thread_rng() instead of the threaded seed; debugging method: grep for any RNG source outside sim-core; signal: replay.hash.mismatch with no corresponding WAL anomaly; recovery: replace with the seeded generator and add a lint rule banning thread_rng outside test code.

18.7 Performance Concerns

  • Replay IO amplification: segment rotation size must balance WAL-write throughput against read-amplification during replay-cursor seeks — tuned empirically against the §4 storage budget, not fixed arbitrarily.
  • Verifier re-execution cost: replay verification re-runs the full scheduler, so continuous background verification (as opposed to on-demand) is budgeted separately from live throughput.

18.8 Edge Cases

  • Partial WAL corruption mid-segment — the reader must recover everything before the corruption point and flag everything after it as untrusted, never silently truncate without flagging.
  • A snapshot taken mid-fault-window — replay from that snapshot must correctly resume the in-progress fault's remaining duration, not restart it.
  • Clock skew between the WAL-writer's logical tick and a snapshot's recorded tick — must be structurally impossible since both derive from the same virtual-clock source (P9); tested as a regression guard rather than a runtime check.

18.9 Failure Analysis

Replay hashes are emitted per epoch (a configurable tick range, e.g. every 100,000 ticks) so a divergence is bounded to one epoch before the binary-search verifier narrows further. Forensics: every divergence investigation starts from the epoch-level hash mismatch, not a from-scratch full-run comparison — this is the operational payoff of the epoch/binary-search design.

18.10 Operational Notes

  • Metrics: replay.hash_mismatch_total, wal.segment_write_latency_us, wal.amplification_ratio.
  • Replay archives are retained for audits per the compatibility guarantee (§25): 2 major versions of backward-readable format support.
  • Migration: a WAL schema version bump requires a documented migration path in docs/runbooks/replay-recovery.md, never a silent reinterpretation of old segments.

19. Phase 7 — Distributed Coordination

19.1 Objectives

  • Enable multi-node simulation: shard assignment, distributed barriers, worker leases, failure detection across an orchestrator-coordinated cluster.
  • Survive worker loss without split-brain (I9, I10).

19.2 Detailed Implementation Steps

  • Implement coordinator RPCs in orchestrator::coordinator (gRPC over Tokio, ADR-06): worker registration, shard assignment, heartbeat, barrier-request.
  • Implement shard assignment: deterministic partitioning of the compiled topology manifest (§15) across available workers, informed by Dean & Ghemawat 2004 (MapReduce, OSDI) worker- failure-tolerant task assignment.
  • Implement distributed barriers (orchestrator::coordinator barrier primitive): all workers must reach a logical-tick checkpoint before any advances past it (I9).
  • Implement time synchronization: workers report logical-tick progress and wall-clock skew; the coordinator rejects a worker exceeding the < 1ms clock-skew budget (§4).
  • Implement the heartbeat protocol: periodic liveness signal with a configurable timeout, feeding failure detection.
  • Implement worker leases (orchestrator::leases, WorkerLease §11): exactly one lease per shard at a time (I10), renewed on heartbeat, revocable on timeout.
  • Add failure detection: a missed-heartbeat threshold triggers lease revocation and shard reassignment, never a silent hang.

19.3 Deliverable

A distributed runtime cluster: one orchestrator coordinator plus N event-runtime workers that jointly simulate a sharded topology, surviving a worker crash via lease revocation and shard reassignment without violating I9 or I10.

19.4 Acceptance Criteria

  • Cluster survives a worker crash injected via conformance/coordination/worker-crash.fixture with shard reassignment completing within the < 60s coordinator-recovery budget (§4).
  • Zero lease conflicts (I10) across 1,000 simulated worker-churn events.
  • Coordinator failover (coordinator-failover.fixture) completes leader election within 15s.

19.5 Conformance Fixtures

  • conformance/coordination/worker-crash.fixture — a worker process killed mid-run; expected: lease revoked on heartbeat timeout, shard reassigned, simulation continues without data loss.
  • conformance/coordination/coordinator-failover.fixture — the coordinator process killed; expected: a standby coordinator wins leader election within 15s, resumes barrier coordination.
  • conformance/coordination/clock-skew.fixture — a worker reporting skew exceeding the 1ms budget; expected: worker registration rejected with a named SkewExceeded error.

19.6 Pitfalls

  • Split-brain coordinators — manifestation: two coordinators both believe they hold leadership; root cause: a leader-election protocol without a strict quorum requirement; debugging method: audit the barrier-epoch sequence for regressions (I9 detection); signal: barrier.epoch_regression counter nonzero; recovery: enforce a strict majority-quorum election and reject any barrier request from a non-quorum-confirmed leader.

19.7 Performance Concerns

  • Barrier synchronization latency: bounded by the slowest worker in the barrier group; mitigate with per-shard progress reporting so a straggler is identified (and potentially reassigned) rather than silently stalling the whole cluster (informed by Dean & Barroso 2013, The Tail at Scale, tail-latency-amplification-under-fanout reasoning).
  • RPC overhead at scale: heartbeat and barrier-request frequency must be tuned against the cluster size to avoid the coordinator becoming the bottleneck.

19.8 Edge Cases

  • Clock skew discovered mid-run (not just at registration) — the worker is quarantined (leases revoked) rather than allowed to continue contributing potentially-divergent barrier votes.
  • Partition healing: a worker that was network-partitioned and rejoins must re-synchronize its logical tick against the coordinator's barrier state before resuming, never resume blind.
  • A barrier request from a worker holding an already-revoked lease — rejected structurally (I10), logged as a lease.conflict event even though no actual conflict occurred (defensive signal).

19.9 Failure Analysis

Coordinator state snapshots are mandatory (P4) so a coordinator failover does not require replaying the entire cluster's history — only the snapshot plus the WAL tail since it. Blast radius of a single worker crash is bounded to that worker's shard set, reassigned without affecting other shards' barrier progress (I9 isolation). Quorum metrics are the primary operator signal for split-brain risk before it manifests as an actual barrier-epoch regression.

19.10 Operational Notes

  • Metrics: orchestrator.quorum_size, lease.active_count, barrier.epoch, worker.heartbeat_lag_ms.
  • Deployment: orchestrator runs as its own service (Kubernetes-optional, §1 deployment model); event-runtime workers register on startup via the coordinator RPC endpoint.
  • Rollback: a coordinator rollback to a prior binary version must use a lease-table snapshot compatible with that version's schema (I12), enforced by storage-engine's schema check.

20.5 Conformance Fixtures

  • conformance/namespace/namespace-routing.fixture — a real traffic generator routed through a simulated link; expected: measured throughput within 10% of configured bandwidth.
  • conformance/namespace/rootless-teardown.fixture — namespace lifecycle under a rootless user; expected: clean teardown, zero leaked namespaces detected by the reference-count check.
  • conformance/namespace/interface-teardown-race.fixture — concurrent teardown requests on the same interface; expected: idempotent teardown, no double-free-style error.

20.6 Pitfalls

  • Namespace leaks — manifestation: ip netns list shows namespaces outstanding after all scenarios complete; root cause: a panic path that skips the teardown handler; debugging method: audit every panic/early-return path in the namespace lifecycle for a matching cleanup guard; signal: namespace.leak_suspected counter nonzero (I14); recovery: wrap namespace creation in a scope-guard pattern (declared, no body shown) that guarantees teardown on drop.
  • Syscall overhead on the hot path — manifestation: throughput far below the LinkModel budget; root cause: per-packet syscalls instead of batched tc configuration; recovery: configure tc/netem once per link, not per packet.

20.7 Performance Concerns

  • Syscall overhead: namespace and tc configuration calls are amortized at link-setup time, not paid per packet — per-packet behavior stays inside the simulated packet-engine pipeline.
  • eBPF probe overhead: XDP-level mirroring is chosen specifically because it runs before the kernel's normal socket-buffer allocation path, minimizing overhead relative to a socket-level mirror.

20.8 Edge Cases

  • Interface teardown races (20.5 fixture) — concurrent teardown must be idempotent.
  • A TAP device created but never attached to a simulated link (operator misconfiguration) — detected and reported, not left as an orphaned, unused device (I14 adjacent).
  • eBPF probe attach failure on an unsupported kernel version — fails closed with an explicit minimum-kernel-version diagnostic, not a silent fallback to unmirrored traffic.

20.9 Failure Analysis

Namespace cleanup audit logs record every creation and teardown event with a monotonic reference count; any process exit with a nonzero outstanding count triggers a forced-teardown sweep on the next cli invocation (I14 recovery path). Blast radius of a leaked namespace is host-level resource exhaustion (FD budget, §4) if left unaddressed across many runs.

20.10 Operational Notes

  • Metrics: namespace.active_count, namespace.leak_suspected, tc.configure_latency_us.
  • Rootless execution is supported and tested explicitly (20.4/20.5) — this is a deployment-model requirement (§1), not an optional hardening feature.
  • Compatibility: tc/netem invocation shape is pinned to the kernel versions listed in the release notes; a kernel major-version bump requires a compatibility-matrix update (§25).

24. Operational Readiness

Metrics strategy. Seven metrics classes cover the system end to end: scheduler (scheduler.*), packet (packet.*), queue (queue.*), replay (replay.*, wal.*), storage (storage.*, snapshot.*), transport (transport.*), orchestration (orchestrator.*, lease.*, barrier.*). Every class is registered in the metrics-pipeline schema (§21) before any subsystem may emit it (fail-closed unregistered-metric rejection, P12).

Alerting philosophy. Page only on: determinism failures (I2, FM-1), replay/WAL corruption (FM-2), coordinator quorum failure (FM-4, FM-8), storage corruption (FM-2, T10). Everything else (queue pressure, clock skew, namespace leaks) is a dashboard-visible warning that escalates to a page only if it persists past a configured duration — this keeps the page volume proportional to genuinely irrecoverable-without-operator-action conditions (P1, P4).

Backup strategy. Snapshot the replay WAL every 15 minutes (bounded by the < 30s graceful-shutdown budget's WAL-flush component, §4); snapshots are schema-versioned (I12) and retained per the §25 compatibility window.

Rolling upgrade strategy. Protocol version negotiation is mandatory at every RPC boundary (coordinator-worker, ADR-06); a worker running an older event-runtime binary negotiates down to the coordinator's minimum supported protocol version rather than being rejected outright, unless the version gap exceeds the §25 two-major-version compatibility window.

25. Compatibility & Versioning

  • Protobuf fields are append-only (P6, ADR-05) — no field is ever removed or renumbered; a deprecated field is marked reserved, never reused.
  • Storage schemas (WAL, snapshots, manifests) are explicitly versioned (P14, I12); the storage-engine rejects a load whose schema version it does not recognize rather than guessing.
  • Replay formats are backward-readable for 2 major versions — a v3 replay-engine can read v1 and v2 WAL segments, but not v0; this bound is what makes the §24 backup-retention policy operationally meaningful.
  • Topology manifests are immutable once released into a running scenario (P11, I5); a manifest format change requires a new schema version, never an in-place reinterpretation of an existing manifest's bytes.
  • tc/netem invocation shape (§20) is pinned to a documented kernel-version compatibility matrix; a host kernel major-version bump requires an explicit matrix update before the Linux Integration phase's fixtures are considered valid on that host.
  • CLI subcommand flags are additive; a flag is never repurposed to mean something different across minor versions (P6 applied to the operator-facing surface, not just the wire format).

26. Testing & Verification Strategy

Test classes: unit tests (per-crate, cargo test), integration tests (cross-crate, e.g. packet-engine + transport-models), deterministic replay tests (§18 verifier against conformance/ fixtures), property tests (proptest, ADR-12 — packet/topology state-space coverage beyond hand-written examples), fuzzing (cargo-fuzz, ADR-13 — parser and topology-DSL targets), chaos tests (fault-engine-driven, §16), soak tests (multi-hour runs verifying zero scheduler drift, I1/I2), differential tests (comparing transport-model output against reference traces, §17.4).

Deterministic replay testing. Every CI run replays the canonical transport fixtures (tcp-fast-retransmit.fixture, quic-loss.fixture), packet-corruption scenarios (malformed-checksum.fixture), and queue-overflow scenarios (queue-overflow.fixture) — a regression in any of these blocks the merge. This is the single most valuable CI gate in the system: it catches the exact nondeterminism-introducing pitfalls documented across §13.6, §16.6, and §18.6 before they reach a tagged release.

Coverage philosophy. Property tests target the packet/topology state space (malformed input, boundary sizes, adversarial graphs); fuzzing targets the two untrusted-input surfaces named in §22 (packet parser, topology DSL parser); differential tests target transport-model conformance against real traces rather than internal self-consistency alone — a transport model that only agrees with itself is not validated (Stevens 1994 ch. 17–21 is the reference truth source here, not the implementation).

29. Scalability Analysis

Bottlenecks. Scheduler shard imbalance (§13.6) is the primary single-host bottleneck — a skewed traffic distribution across shards produces tail-latency amplification (C7, §32) well before aggregate throughput saturates. Replay-storage throughput (§18.7) bounds sustained event rate once WAL write bandwidth approaches the NVMe ceiling (C3, §32). Metrics cardinality (§21.6) bounds dashboard responsiveness independent of simulation throughput. Distributed barriers (§19.7) bound cluster-wide tick-advancement rate to the slowest worker in the barrier group.

Horizontal scaling. Topology partitioning (§15, §19) distributes shards across workers; shard-aware scheduling keeps traffic-heavy shards from co-locating on the same worker where possible (informed by the same shard-imbalance root cause as §13.6); distributed replay archives (§18) shard WAL storage per-worker rather than centralizing it, avoiding a single storage bottleneck at cluster scale.

Vertical scaling. NUMA-aware worker pinning (C9, §32) keeps a worker's memory access local to its assigned cores; lock minimization (ADR-08) is the vertical-scaling analog of shard isolation (P10) — a lock-free design scales cores linearly up to the point where cache-coherency traffic itself becomes the bottleneck, which the NUMA pinning strategy is designed to push out further.

30. Mental Models & First Principles

  • MM1 — Determinism Is a Total Order, Not a Property You Test For. Compressed insight: replay determinism (I2) is only real if every scheduling decision is derivable from a single total order over (tick, shard, sequence); predicts that any "mostly deterministic" system will eventually diverge; the bug class you write without it: hidden nondeterminism from wall-clock or hash-map iteration order (§13.6, §16.6); applies in §13.
  • MM2 — A Shard Is a Trust Boundary, Not a Performance Optimization. Compressed insight: sharding (P10) exists to make cross-shard mutation structurally impossible, and the throughput gain is a side effect; predicts that any "just add a shared cache" request is a correctness regression, not a performance one; the bug class without it: silent cross-shard data races; applies in §13.
  • MM3 — A Queue's Capacity Is a Correctness Parameter. Compressed insight: bounded queues (P2, I4) are not a memory-tuning knob, they are what makes backpressure (P8) exist at all; predicts that "just make the queue bigger" masks a design bug instead of fixing it; the bug class without it: unbounded memory growth mistaken for a tuning problem; applies in §14.
  • MM4 — Logical Time and Wall-Clock Time Must Never Silently Merge. Compressed insight: P9 is violated the instant any code path reads Instant::now() on a path that affects a scheduling or fault decision; predicts intermittent, load-dependent replay divergence; the bug class without it: "it only happens under load" nondeterminism bugs; applies in §16.
  • MM5 — A WAL Entry Logged After Its Effect Is Not an Audit Trail. Compressed insight: I7/I8 exist because "log it eventually" is equivalent to "don't log it" for forensic purposes; predicts that any perf optimization reordering log-then-apply is a correctness regression; the bug class without it: unreconstructable incidents; applies in §18.
  • MM6 — Tail Latency Is a Fan-Out Problem, Not an Average Problem. Compressed insight (Dean & Barroso 2013): p99 latency is dominated by the slowest contributor across a fan-out, not the typical contributor; predicts that barrier synchronization (§19) will be bottlenecked by one straggler shard, not the average shard; the bug class without it: optimizing the average case while the p99 budget (§4) keeps failing; applies in §19.
  • MM7 — A Lease Without an Expiry Is a Lock Without a Timeout. Compressed insight: I10 only prevents split-brain if every lease has a bounded lifetime independent of the holder's cooperation; predicts that a crashed-but-not-detected worker will eventually hold a permanently-stale lease without expiry; the bug class without it: split-brain (FM-8); applies in §19.
  • MM8 — Observability Is Part of the System, Not a View Onto It. Compressed insight (P5): a metric or span that is missing is itself a failure mode (FM-11), not a documentation gap; predicts that "we'll add telemetry later" always ships an unobservable blind spot first; the bug class without it: production incidents with no forensic trail; applies in §21.

32. Back-of-Envelope Capacity Model

  • C1 — Flow table RAM. 50,000,000 flows × 96B/flow = 4.8GB, inside the 8GB §4 per-worker ceiling with 3.2GB headroom for queues.
  • C2 — Node ID space. 1,000,000 nodes × 4B (u32 ID) = 4MB manifest ID footprint, negligible against the 8GB ceiling.
  • C3 — WAL write throughput. 15,000,000 events/sec × 72B/WAL-entry = 1.08GB/sec raw WAL write rate, requiring NVMe sustained write ≥ 1.08GB/s (matches the §4 NVMe assumption).
  • C4 — Replay amplification bound. 72B WAL-entry ÷ 48B raw event = 1.5x, exactly at the §4 amplification ceiling — any added WAL field must be offset by compression (ADR-15).
  • C5 — Metrics cardinality budget. 5,000,000 series ÷ 50,000,000 flows = 0.1 series/flow average, forcing per-flow metrics to sample or aggregate rather than emit unconditionally.
  • C6 — FD budget per worker. 250,000 FDs ÷ 8 workers/host = 31,250 FDs/worker, sized for 31,250 concurrent socket-emulation flows per worker.
  • C7 — p99 scheduling tail budget. 500µs p99 ÷ 10µs p50 = 50x amplification tolerated before the starvation alarm (I1) fires.
  • C8 — Storage amplification headroom. 3x ceiling − 1.5x WAL amplification (C4) = 1.5x remaining budget for snapshot duplication and compaction overhead (§18).
  • C9 — NUMA worker count. 64GB host RAM ÷ 8GB/worker = 8 workers/host, requiring NUMA-aware pinning since 8 workers commonly span ≥ 2 memory controllers on target hardware.
  • C10 — Coordinator recovery split. 60s total (§4) = 15s leader election (§19) + 45s shard re-registration headroom at 1,000,000-node scale.
  • C11 — Corruption overhead budget. 15,000,000 events/sec × 5% (§4 ceiling) = 750,000 events/sec of tolerated corruption-engine overhead before the budget is exceeded.
  • C12 — Availability budget. (1 − 0.9995) × 365.25 days × 24h = 4.38h/year downtime budget for the 99.95% control-plane availability target.

Regime where it wins: validating unmodified real software against real kernel timing behavior where reproducibility is explicitly not required. Real system: Mininet. Why rejected here: without a deterministic core, replay (I2) and forensic fault-timeline reconstruction (§16) are impossible — this blueprint needs both the real-time emulation surface (§20) and the deterministic virtual-time core (§13), not one instead of the other.

Alt C — Work-Stealing Async Scheduler (No Shard Isolation)

   +--------+  steal  +--------+  steal  +--------+
   | Worker |<------->| Worker |<------->| Worker |
   | Thread |         | Thread |         | Thread |
   +--------+         +--------+         +--------+
        (shared work queue, dynamic load balancing)

Regime where it wins: general-purpose async task scheduling where throughput and dynamic load balancing matter more than a reproducible total order of execution. Real system: Tokio's own runtime scheduler. Why rejected here: work-stealing's dynamic task migration makes the (tick, shard, sequence) total order (I1, MM1) unrecoverable — determinism (P1) is the non-negotiable requirement this architecture is built around, and Tokio is used only for the non-scheduling-critical RPC/IO layers (ADR-07), never for the deterministic scheduler core itself.

36. Glossary

  • Event Tick — the logical scheduler timestamp; the unit of time in virtual-time mode (§13).
  • Replay WAL — the append-only, checksummed deterministic event log written by replay-engine (§18).
  • Queue Discipline — the packet dequeue algorithm (tail-drop, RED) applied at a link (§14).
  • Congestion Window — the sender's in-flight-byte limit, adjusted by CUBIC/BBR (§17).
  • Scheduler Shard — an independent, single-threaded event-execution partition (§13, P10).
  • Topology Manifest — the immutable, hash-stable compiled network graph (§15, I5).
  • Packet Descriptor — the immutable, single-owner packet metadata struct (§11, I3).
  • Fault Epoch — a window of time during which one or more faults are active (§16).
  • Deterministic Replay — exact bit-for-bit reproduction of a prior execution from its seed and WAL (I2).
  • Timing Wheel — the O(1) hierarchical timer-scheduling structure (Varghese & Lauck 1987, §13).
  • Flow State — transport-layer connection metadata: congestion window, RTT estimate, retransmit timers (§11, §17).
  • Barrier Sync — the distributed logical-time alignment primitive enforcing I9 (§19).
  • Packet Amplification — extra copies of a packet introduced during processing; must be zero under P7.
  • Namespace Adapter — the Linux network-namespace integration layer (§20).
  • Replay Divergence — a detected mismatch between two replays of the same seed (I2, FM-1).
  • Virtual Clock — the logical/accelerated/paused time source decoupled from wall clock (P9, §13).
  • Manifest Hash — the Merkle-style hash over a compiled topology's nodes/links/routes (§15).
  • Worker Lease — the time-bounded, exclusive right to own a shard's execution (§11, I10).
  • Fault Rule — a declarative selector/trigger/action/duration tuple in the fault DSL (§11, §16).
  • RED (Random Early Detection) — a probabilistic pre-capacity queue-dropping discipline (§14).
  • Tail-Drop — a simple bounded-FIFO queue-dropping discipline (§14).
  • SACK — Selective Acknowledgment, a TCP extension for non-cumulative ACKs (RFC 9293, §17).
  • RTO — Retransmission Timeout, the timer governing when an unacknowledged segment is resent (§17).
  • CUBIC — the default congestion-control algorithm modeled in transport-models (§17).
  • BBR — Bottleneck Bandwidth and RTT, a congestion-control algorithm modeled as an alternative (§17).
  • XDP — eXpress Data Path, the kernel fast-path used for eBPF packet mirroring (§20).
  • eBPF — extended Berkeley Packet Filter, the kernel-level probe mechanism used in §20.
  • PCAP — the packet-capture file format used for live-capture export (§20).
  • OpenTelemetry Span — a distributed-trace unit correlating a subsystem's entry/exit (§21).
  • Cardinality Guard — the metrics-pipeline component rejecting unbounded label sets (§21, §4).
  • WAL Segment — a fixed-size, checksummed, rotated unit of the replay WAL (§18, I11).
  • Snapshot — a periodic, schema-versioned full-state serialization for crash-only recovery (P4).
  • Shard Isolation — the principle that no mutable state crosses a scheduler-shard boundary (P10).
  • Backpressure — the discipline of bounding every channel and shedding load explicitly (P8).
  • Admission Control — rejecting new work at the boundary rather than queueing it unboundedly (§22, T6).
  • Split-Brain — two coordinators simultaneously believing they hold leadership (§19, FM-8).
  • Leader Election — the quorum-based protocol selecting a single active coordinator (§19).
  • Quorum — the majority threshold required for a coordinator election to be valid (§19).
  • Barrier Epoch — the monotonically increasing counter identifying a distributed barrier round (§19, I9).
  • Trace Correlation — pivoting a live trace span to its corresponding WAL epoch and tick range (§21).
  • Schema Version — the explicit version tag on every persisted format, enforced by I12 (P14).
  • Un-defer Trigger — the documented condition under which a deferred feature (§35) is reconsidered.
