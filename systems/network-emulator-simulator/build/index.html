⬜ Phase 0 — Repository Foundation & Correctness Kernel §12

Objectives
  • Bootstrap the 15-crate Cargo workspace (§1 Phase 0 deliverable list) with reproducible builds.
  • Establish CI, lint, and dependency-audit gates before any scheduling code lands.
  • Stand up the correctness kernel: deterministic seed generation and build-metadata injection that every later phase depends on for replay (P3, I2).
  • Introduce zero scheduling code — this phase is scaffolding plus the seed/config substrate.
Deliverable

A cargo build --workspace --locked that compiles all 15 crates as empty-but-linked stubs, a green CI pipeline, and a deterministic-seed generator whose output is reproducible across two independent build machines given the same seed and toolchain version.

Acceptance
  • All 15 crates compile under --locked with zero clippy warnings on the deny-list.
  • CI green on 3 consecutive runs with identical build-metadata hash (build.reproducible_hash).
  • Deterministic seed generator produces bit-identical 10,000-draw sequences across 2 hosts for the same seed — verified against conformance/config-valid.toml.
  • Config loader rejects conformance/config-invalid.toml with a structured error, not a panic.
Fixtures
  • conformance/config/config-valid.toml — a minimal valid workspace config; expected: loads without error, all defaults populated.
  • conformance/config/config-invalid.toml — an unknown top-level key; expected: structured ConfigError::UnknownKey rejection, no panic.
  • conformance/build/seed-replay.fixture — a fixed seed value; expected: identical 10,000-value draw sequence on repeat invocation (regression case for I2 introduced this early).
Pitfalls
  • Dependency version drift between contributors' local Cargo.lock and CI's vendored lock — root cause: cargo update run locally without --locked; signal: CI build-metadata hash differs from a clean-checkout build; recovery: re-vendor and re-audit, never hand-edit the lock.
  • Nondeterministic build metadata from timestamp-based version strings — root cause: using env!("CARGO_PKG_VERSION") plus wall-clock build time; signal: two builds of the same commit produce different build.reproducible_hash; recovery: strip wall-clock from the injector.
  • Silent CSPRNG reseeding from OS entropy on a library upgrade — root cause: a transitive dependency defaulting to OsRng; signal: seed-replay fixture fails intermittently; recovery: pin the RNG crate version and add a unit test asserting the seed path never touches /dev/urandom.

⬜ Phase 1 — Deterministic Event Runtime §13

Objectives
  • Implement the hierarchical timing-wheel scheduler and virtual clock — the correctness core every later phase schedules work through.
  • Guarantee monotonic event ordering (I1) and zero scheduler drift under replay (I2, §4).
  • Establish the bounded-channel discipline (P8) that all inter-shard communication will use.
Deliverable

A standalone event-runtime binary capable of ingesting a synthetic event stream and replaying it deterministically from a fixed seed, exposing scheduler-lag and queue-depth metrics on a local Prometheus endpoint.

Acceptance
  • Sustains 10,000,000 events/sec on a single host in virtual-time mode (interim target toward the §4 15M ceiling, reached fully once packet-engine integration lands in §14).
  • Produces bit-identical replay hashes across 100 consecutive replays of conformance/scheduler/replay-determinism.fixture.
  • Zero scheduler-drift events recorded across a 10-million-tick soak run.
Fixtures
  • conformance/scheduler/scheduler-ordering.fixture — events with intentionally colliding timestamps; expected: comparator resolves via shard-sequence tiebreak, stable order every run.
  • conformance/scheduler/replay-determinism.fixture — a fixed seed, 1M-event stream; expected: identical replay hash across 100 runs.
  • conformance/scheduler/timing-overflow.fixture — events scheduled beyond the wheel's horizon; expected: correct overflow-bucket rollover, no dropped events.
Pitfalls
  • Starvation under uneven shard load — manifestation: one shard's queue depth grows unbounded while others idle; root cause: static topology-to-shard assignment ignoring traffic skew; debugging method: replay with per-shard queue-depth trace enabled; signal: queue.depth gauge divergence across shards; recovery: rebalance shard assignment in the topology compiler (§15).
  • Timing-wheel overflow bugs — manifestation: events silently dropped past the wheel horizon; root cause: off-by-one in overflow-bucket rotation; debugging method: replay timing-overflow.fixture with assertion-level tracing; signal: event count mismatch between ingress and delivery; recovery: fix rotation boundary, add regression fixture.
  • Unstable comparator ordering — manifestation: two replays of the same seed diverge; root cause: a non-deterministic tiebreak (e.g. using Instant::now() as a hidden fourth key); debugging method: diff the two replay hash chains to find the first divergent tick; recovery: audit the comparator for any wall-clock or memory-address-derived key.

⬜ Phase 2 — Packet Engine & Queue Disciplines §14

Objectives
  • Implement the packet lifecycle: parse, pool, queue, corrupt, deliver — the pipeline named in §3.
  • Enforce single-mutable-owner packet semantics (I3, P7) end to end.
  • Introduce queue disciplines (tail-drop, RED) with bounded capacity (I4, P2).
Deliverable

A packet-simulation runtime that ingests synthetic packet streams through parse → queue → corrupt → deliver, exposing per-stage counters and enforcing the single-owner invariant at compile time.

Acceptance
  • Sustained 5,000,000 packet-state-transitions/sec on a single host (interim milestone toward the §4 aggregate scheduling-throughput budget).
  • Zero packet-ownership violations detected across a 1-hour soak (structurally guaranteed by I3, verified by the absence of any unsafe alias in packet-engine).
  • conformance/packet/queue-overflow.fixture sheds packets at exactly the configured capacity, not one packet before or after.
Fixtures
  • conformance/packet/malformed-checksum.fixture — a packet with a corrupted checksum byte; expected: parser rejection, packet.checksum_invalid counter increments, no panic.
  • conformance/packet/packet-reorder.fixture — packets delivered out of send order; expected: sequence numbers preserved, no silent reordering inside the queue discipline itself.
  • conformance/packet/queue-overflow.fixture — a burst exceeding queue capacity; expected: drop count equals burst size minus capacity, exactly.
Pitfalls
  • Packet aliasing via a well-intentioned "peek" API — manifestation: two code paths mutate the same buffer; root cause: an API that returns a mutable reference instead of transferring ownership; debugging method: unsafe-audit grep across packet-engine; signal: nondeterministic corruption in fixtures that should be deterministic; recovery: replace peek-and-mutate with ownership-transfer-and-return APIs.
  • Queue starvation under RED misconfiguration — manifestation: low-priority flows never drain; root cause: RED threshold set below sustained average queue depth; debugging method: replay with per-flow queue-residency tracing; signal: flow-level p99 latency divergence; recovery: retune RED thresholds against measured traffic profile, not a default guess.
  • Memory fragmentation from variable-size payload descriptors — manifestation: pool allocator churn increases despite pooling; root cause: payload sizes not bucketed before pooling; recovery: bucket the pool by payload-size class (jumbo vs standard).

⬜ Phase 3 — Topology Compiler §15

Objectives
  • Compile the scenario DSL's topology declarations into an immutable, hash-stable manifest (P11).
  • Detect invalid graphs (cycles in routing, disconnected components) before any worker registers.
  • Support topologies up to the 1,000,000-node §4 ceiling with tractable compile time.
Deliverable

A deterministic topology compiler CLI subcommand (cli topology compile) that turns a .dsl scenario file into a hash-stable TopologyManifest, rejecting cyclic or disconnected graphs with a structured diagnostic.

Acceptance
  • Identical DSL source compiles to an identical manifest hash across 50 repeated compilations.
  • Compiles a 1,000,000-node synthetic topology (§4 ceiling) in under 5 seconds (matches the coordinator startup-time budget, §4).
  • conformance/topology/cyclic-topology.fixture and disconnected-graph.fixture are both rejected with a named TopologyError variant, never a panic.
Fixtures
  • conformance/topology/cyclic-topology.fixture — a routing declaration forming a loop; expected: TopologyError::RoutingCycle with the offending node IDs named.
  • conformance/topology/disconnected-graph.fixture — two node sets with no connecting link; expected: TopologyError::Disconnected naming the isolated component.
  • conformance/topology/million-node.fixture — a synthetic 1,000,000-node topology generator fixture; expected: compiles within the 5-second budget above.
Pitfalls
  • Inconsistent ID allocation across compiler versions — manifestation: the same DSL source compiles to a different manifest hash after a compiler upgrade; root cause: a change to iteration order in the topological sort; debugging method: diff two manifests via the topology-diff engine; signal: replay fixtures fail post-upgrade despite unchanged DSL source; recovery: pin the topological-sort tiebreak rule and version it (P6).
  • Hidden route ambiguity when two equal-cost paths exist — manifestation: nondeterministic route selection across compiles; root cause: tiebreak omitted from the shortest-path computation; recovery: add an explicit deterministic tiebreak (lowest node ID) and a regression fixture.

⬜ Phase 4 — Fault Injection Framework §16

Objectives
  • Implement deterministic, replayable fault orchestration: drops, latency spikes, corruption bursts, node isolation — driven by a declarative rule table (P3, P1).
  • Guarantee every injected fault is durably attributable (I7) for blast-radius analysis.
Deliverable

A programmable chaos-injection runtime (fault-engine) that applies scenario-declared faults deterministically and replays an identical fault timeline given the same seed.

Acceptance
  • 100% of injected faults across conformance/fault/latency-spike.fixture and split-brain.fixture are durably logged before taking effect, verified by WAL-order audit.
  • Deterministic replay of all injected faults across 20 repeated runs of the same scenario seed.
  • Rule-matching overhead stays under 2% of per-tick scheduler budget at 10,000 active rules.
Fixtures
  • conformance/fault/latency-spike.fixture — a scripted latency spike on one link; expected: latency reverts exactly at duration expiry, logged fault matches applied fault.
  • conformance/fault/split-brain.fixture — simultaneous node isolation on two coordinator candidates; expected: both isolations logged with overlapping-window metadata for §19 analysis.
  • conformance/fault/overlapping-windows.fixture — two fault rules targeting the same link with overlapping durations; expected: deterministic composition order (rule-declaration order), not last-write-wins by evaluation timing.
Pitfalls
  • Nondeterministic timer usage inside a fault action — manifestation: a fault's revert time drifts across replays; root cause: using wall-clock Instant instead of logical tick for duration; debugging method: diff fault-timeline logs across two replays of the same seed; signal: replay.hash.mismatch triggered specifically during a fault-active window; recovery: audit every FaultAction implementation for wall-clock reads (P9 violation).
  • Rule-table evaluation order ambiguity — manifestation: two rules targeting the same selector apply in different orders across replays; root cause: rule iteration over an unordered collection; recovery: rules are stored and iterated in declaration order (P11), never a hash-map iteration order.

⬜ Phase 5 — Transport Models §17

Objectives
  • Implement TCP/UDP/QUIC behavior models on top of the packet engine (§14): retransmission, congestion windows, RTT estimation, ACK handling.
  • Validate against real transport traces, not just internal consistency (RFC 793, RFC 9293, RFC 9000 §17).
Deliverable

A transport-capable packet-simulation runtime that reproduces reference TCP and QUIC traces — fast retransmit, RTO backoff, congestion-window growth/collapse — under virtual time.

Acceptance
  • Conformance against conformance/transport/tcp-fast-retransmit.fixture: fast retransmit fires on exactly the 3rd duplicate ACK, matching RFC 9293 section 3.8.3.
  • CUBIC congestion-window growth within 5% of the reference trace's window trajectory over a 10,000-packet exchange.
  • QUIC loss detection triggers within the RFC 9000 §17-specified packet-threshold and time- threshold bounds on conformance/transport/quic-loss.fixture.
Fixtures
  • conformance/transport/tcp-fast-retransmit.fixture — 3 duplicate ACKs on a known sequence; expected: fast retransmit fires exactly once, congestion window halves per CUBIC.
  • conformance/transport/quic-loss.fixture — a scripted packet-loss pattern; expected: loss detected within RFC 9000 §17 packet/time thresholds, correct stream-level isolation.
  • conformance/transport/ack-storm.fixture — a burst of 10,000 ACKs in one tick; expected: ACK-processing stays within the pacing budget, no congestion-window overreaction.
Pitfalls
  • Timer explosion under many concurrent flows — manifestation: per-flow RTO timers overwhelm the timing wheel; root cause: one wheel-slot registration per flow instead of batched registration; debugging method: profile timing-wheel bucket occupancy under a 1M-flow load; signal: scheduler.dispatch_latency_us p99 regression; recovery: batch RTO checks per tick rather than per-flow timer registration.
  • Flow-memory leaks from connections that never reach a terminal state — manifestation: flow table grows unbounded; root cause: no idle-flow eviction policy; recovery: add a bounded idle-timeout eviction consistent with P2.

⬜ Phase 6 — Replay Engine §18

Objectives
  • Implement the durable WAL-backed replay subsystem: every scheduler decision, fault injection, and RNG draw becomes forensically reconstructible (P3, I8, I11).
  • Detect replay divergence reliably, not approximately (I2).
Deliverable

A deterministic replay subsystem (replay-engine) that can reconstruct any prior simulation run from its WAL, detect divergence at tick granularity, and export a compressed archive within the §4 storage-write-amplification budget.

Acceptance
  • Replay-divergence detection localizes the first divergent tick within 1 binary-search pass over a 10-million-tick WAL segment (log2(10M) ≈ 24 comparisons).
  • WAL segment amplification measured at < 1.5x raw event size on conformance/replay/replay-divergence.fixture.
  • 100% of replay-divergence.fixture runs correctly identify the injected divergence point.
Fixtures
  • conformance/replay/replay-divergence.fixture — a WAL segment with a deliberately injected hash mismatch at a known tick; expected: replay verifier localizes exactly that tick.
  • conformance/replay/wal-partial-corruption.fixture — a WAL segment truncated mid-write; expected: checksum failure detected at the truncation boundary, fallback to last valid snapshot.
  • conformance/replay/compression-ratio.fixture — a representative 1-hour scenario WAL; expected: compressed size within the < 1.5x amplification budget.
Pitfalls
  • Nondeterministic RNG usage anywhere outside the Phase 0 seeded CSPRNG — manifestation: replay diverges despite an apparently correct WAL; root cause: a library call to rand::thread_rng() instead of the threaded seed; debugging method: grep for any RNG source outside sim-core; signal: replay.hash.mismatch with no corresponding WAL anomaly; recovery: replace with the seeded generator and add a lint rule banning thread_rng outside test code.

⬜ Phase 7 — Distributed Coordination §19

Objectives
  • Enable multi-node simulation: shard assignment, distributed barriers, worker leases, failure detection across an orchestrator-coordinated cluster.
  • Survive worker loss without split-brain (I9, I10).
Deliverable

A distributed runtime cluster: one orchestrator coordinator plus N event-runtime workers that jointly simulate a sharded topology, surviving a worker crash via lease revocation and shard reassignment without violating I9 or I10.

Acceptance
  • Cluster survives a worker crash injected via conformance/coordination/worker-crash.fixture with shard reassignment completing within the < 60s coordinator-recovery budget (§4).
  • Zero lease conflicts (I10) across 1,000 simulated worker-churn events.
  • Coordinator failover (coordinator-failover.fixture) completes leader election within 15s.
Fixtures
  • conformance/coordination/worker-crash.fixture — a worker process killed mid-run; expected: lease revoked on heartbeat timeout, shard reassigned, simulation continues without data loss.
  • conformance/coordination/coordinator-failover.fixture — the coordinator process killed; expected: a standby coordinator wins leader election within 15s, resumes barrier coordination.
  • conformance/coordination/clock-skew.fixture — a worker reporting skew exceeding the 1ms budget; expected: worker registration rejected with a named SkewExceeded error.
Pitfalls
  • Split-brain coordinators — manifestation: two coordinators both believe they hold leadership; root cause: a leader-election protocol without a strict quorum requirement; debugging method: audit the barrier-epoch sequence for regressions (I9 detection); signal: barrier.epoch_regression counter nonzero; recovery: enforce a strict majority-quorum election and reject any barrier request from a non-quorum-confirmed leader.

⬜ Phase 8 — Linux Integration (TAP/TUN, tc, eBPF) §20

Objectives
  • Bridge the simulated network to real Linux workloads via network namespaces, TAP/TUN devices, tc queueing disciplines, and eBPF probes.
  • Enable unmodified real applications to run through the emulator without namespace leaks (I14).
Deliverable

A hybrid emulator runtime capable of routing real, unmodified workload traffic through the simulated topology's queue disciplines, fault injection, and telemetry pipeline via Linux namespaces and tc.

Acceptance
  • Real workloads (a reference iperf3-style traffic generator) run through the emulator with measured throughput within 10% of the LinkModel-configured bandwidth on conformance/namespace/namespace-routing.fixture.
  • Zero namespace leaks detected across 1,000 create/teardown cycles (I14).
  • Rootless execution succeeds on conformance/namespace/rootless-teardown.fixture.
Fixtures
  • conformance/namespace/namespace-routing.fixture — a real traffic generator routed through a simulated link; expected: measured throughput within 10% of configured bandwidth.
  • conformance/namespace/rootless-teardown.fixture — namespace lifecycle under a rootless user; expected: clean teardown, zero leaked namespaces detected by the reference-count check.
  • conformance/namespace/interface-teardown-race.fixture — concurrent teardown requests on the same interface; expected: idempotent teardown, no double-free-style error.
Pitfalls
  • Namespace leaks — manifestation: ip netns list shows namespaces outstanding after all scenarios complete; root cause: a panic path that skips the teardown handler; debugging method: audit every panic/early-return path in the namespace lifecycle for a matching cleanup guard; signal: namespace.leak_suspected counter nonzero (I14); recovery: wrap namespace creation in a scope-guard pattern (declared, no body shown) that guarantees teardown on drop.
  • Syscall overhead on the hot path — manifestation: throughput far below the LinkModel budget; root cause: per-packet syscalls instead of batched tc configuration; recovery: configure tc/netem once per link, not per packet.

⬜ Phase 9 — Observability Stack & Release Hardening §21

Objectives
  • Complete production observability: OpenTelemetry tracing, Prometheus metrics, structured logs, replay-aware trace correlation across every subsystem introduced in Phases 0–8.
  • Harden the release pipeline: SBOM, signed artifacts, reproducible builds (ADR-17, ADR-19).
Deliverable

A fully observable, release-hardened system: every subsystem emits metrics and traces, every release artifact is SBOM-documented and signed, and every dashboard is version-controlled.

Acceptance
  • 100% of the 15 crates emit at least one metric and one trace span verified by conformance/observability/metrics-schema.fixture schema validation.
  • SBOM generation and cosign signature verification pass on every tagged release (ADR-17).
  • Dashboard configuration diffs are reviewable in version control with zero manual dashboard-UI edits.
Fixtures
  • conformance/observability/metrics-schema.fixture — the full metric registry; expected: every emitted metric matches a registered schema entry, no unregistered metric names appear.
  • conformance/observability/trace-correlation.fixture — a live trace span; expected: correctly resolves to the corresponding WAL epoch and tick range on pivot.
  • conformance/release/sbom-signature.fixture — a tagged release artifact; expected: SBOM present, cosign signature verifies against the published key.
Pitfalls
  • Metrics cardinality explosion — manifestation: Prometheus query latency degrades past operator tolerance; root cause: an unbounded label (e.g. raw flow ID) added to a metric; debugging method: audit the cardinality guard's rejection log; signal: series count approaching the 5M §4 ceiling; recovery: bucket or hash the offending label, never emit it raw.
  • Tracing overhead on the hot path — manifestation: measurable throughput regression after enabling full tracing; root cause: synchronous span export instead of batched async export; recovery: switch to the batched OTel exporter (21.2), never block the scheduler on export I/O.
