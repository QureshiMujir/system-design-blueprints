Decisions (§9) · 30 ADRs

001

Language (broker/IPC/policy)

Chosen

Rust 2021 ≥1.78

Rejected

C++, C, Go, Zig

When the rejected choice is right

Language is C++ (no memory safety): justified for new, greenfield security-critical code where the memory-corruption class is the dominant escape mechanism and a team controls the full codebase

Why: the privileged broker + IPC parser are the escape surface; Rust removes the memory-corruption bug class behind real sandbox escapes; types encode capabilities/origins; unsafe isolated to syscall seams. C++ rejected: this is new security-critical code where Chromium itself is moving to Rust.

002

Renderer-side trust

Chosen

none (assume compromised)

Rejected

partial trust

When the rejected choice is right

Partial renderer trust: justified when the renderer is a first-party, formally-verified component with a tiny, audited API surface and a separate sandboxing layer exists beneath it

Why: principle 1 — the whole model collapses if any renderer value is trusted

003

OS sandbox: syscall filter

Chosen

seccomp-bpf via seccompiler

Rejected

direct prctl/BPF asm, ptrace-interpose

When the rejected choice is right

ptrace-interpose syscall policy (Systrace model): justified when building a syscall audit/tracer for forensics rather than a hard deny-on-violation sandbox, where TOCTOU latency is acceptable

Why: seccompiler is audited Rust BPF gen; ptrace interposition has TOCTOU pitfalls (Garfinkel) and is slow

004

OS sandbox: filesystem

Chosen

Landlock via landlock crate

Rejected

chroot, bind-mount jail, AppArmor

When the rejected choice is right

chroot jail: justified on systems lacking unprivileged namespaces (older kernels) where root-managed chroot + bind-mounts is the only available filesystem confinement primitive

Why: Landlock is unprivileged, stackable, per-process, no root; chroot is escapable + needs privilege

005

OS sandbox: isolation

Chosen

user namespaces (clone(CLONE_NEWUSER,NEWPID,NEWNET,NEWIPC))

Rejected

setuid sandbox, full container

When the rejected choice is right

setuid sandbox binary (legacy Chrome model): justified on distributions where unprivileged user namespaces are disabled by policy and a setuid helper is the only available escalation path

Why: userns is unprivileged; setuid sandbox is legacy/fragile

006

unsafe boundary

Chosen

confined to bsm-sandbox (BPF install, clone, fd ops) + audited

Rejected

spread across crates

When the rejected choice is right

unsafe spread across crates: justified when the entire codebase is a thin systems shim and every file is already subject to the same audit discipline and unsafe review gate

Why: minimize + audit the privileged/unsafe surface (principle 9)

007

IPC transport

Chosen

socketpair(AF_UNIX, SOCK_SEQPACKET)

Rejected

pipes, shared mem only, TCP

When the rejected choice is right

Shared-memory-only IPC (no message boundaries): justified for extremely high-throughput bulk-data transfers between two mutually-trusted processes where framing overhead is unacceptable

Why: SEQPACKET = message boundaries + SCM_RIGHTS fd passing; datagram framing avoids stream re-sync attacks

008

Handle/fd passing

Chosen

SCM_RIGHTS ancillary data

Rejected

path strings, /proc/pid/fd

When the rejected choice is right

Path strings for handle passing (/proc/pid/fd): justified in a debugging or introspection tool that needs human-readable fd identification and runs entirely in the trusted process context

Why: passing the handle (not a name) is the capability model (I6, principle 4); no re-open race

009

IPC serialization

Chosen

explicit fixed-layout, length-prefixed, hand-validated

Rejected

bincode/serde-auto, protobuf, Cap'n Proto

When the rejected choice is right

Auto-serialization (serde/bincode/Cap'n Proto): justified when both endpoints are co-deployed, version-locked, mutually trusted, and the serialization library has a strong security track record

Why: total bounded parsing on hostile frames (I7); no reflection/type-confusion surface; Mojo-style typed messages

010

Capability model

Chosen

unforgeable broker-minted handles + per-proc CapTable

Rejected

ACL-by-pid, ambient fds

When the rejected choice is right

ACL-by-pid ambient authority: justified for a simple single-process daemon where process identity is stable, auditable, and the ambient authority surface is fully enumerated and small

Why: capabilities not identities (principle 4); revocable via epoch

011

Origin parsing

Chosen

RFC 6454 canonicalization + PSL (eTLD+1) for Site

Rejected

naive string compare

When the rejected choice is right

Naive string comparison for origins: justified only in a minimal, offline URL-equivalence utility that processes pre-canonicalized, controlled input from a trusted source only

Why: origin/site confusion = UXSS; canonical compare (I9)

012

Cross-origin gating

Chosen

CORP + ORB (Opaque Response Blocking) + CORS

Rejected

CORB (legacy) only

When the rejected choice is right

CORB (legacy) only: justified for deployments locked to older Chromium milestones where ORB has not yet shipped and CORB is the only available cross-origin blocking mechanism

Why: ORB is the modern successor to CORB; blocks cross-origin no-cors HTML/JSON/XML (I5)

013

Process isolation policy

Chosen

process-per-SiteInstance (strict site isolation)

Rejected

process-per-tab, single-process

When the rejected choice is right

Process-per-tab isolation: justified when memory pressure is extreme (embedded / mobile) and the threat model accepts same-tab cross-origin Spectre risk in exchange for fewer processes

Why: Spectre defense (Reis 2019, principle 6); OOPIFs for cross-site frames

014

Speculative-exec posture

Chosen

site isolation + COOP/COEP gating for SAB/timers

Rejected

in-process mitigations only

When the rejected choice is right

In-process Spectre mitigations only: justified for a content process that exclusively handles same-origin, fully-trusted, first-party content where co-residency with other origins is structurally impossible

Why: address-space separation is the robust defense; in-process is best-effort

015

OS seam abstraction

Chosen

trait Os (Linux now; Windows job-object/AppContainer, macOS Seatbelt later)

Rejected

Linux-only hardcode

When the rejected choice is right

Linux-only hardcoded sandbox primitives: justified for a short-lived, single-platform project where portability is explicitly out of scope and no future platform targets exist

Why: portability without leaking platform-isms into policy (deferred Phase 8)

016

Process spawn

Chosen

clone/fork+execve of a minimal child stub, then sandbox-install

Rejected

posix_spawn, threads

When the rejected choice is right

posix_spawn (no fresh address space guarantee): justified for lightweight helper processes in a single-origin trusted context where shared address space is acceptable and spawn latency is critical

Why: a fresh address space per role; threads share memory (no isolation)

017

Logging/telemetry

Chosen

tracing structured; every verdict logged

Rejected

printf

When the rejected choice is right

printf/ad-hoc logging: justified for a quick prototype or single-threaded CLI tool where structured, keyed audit logs are not required and human readability is the only goal

Why: auditability (I10, principle 11): allow/deny is a logged pure function

018

Metrics

Chosen

metrics/Prometheus exposition

Rejected

bespoke

When the rejected choice is right

Bespoke metrics format: justified when embedding in a constrained environment (microcontroller, embedded browser) where a Prometheus exposition library is too heavy

Why: SLOs on escape attempts, deny rate, spawn latency

019

Testing

Chosen

cargo test + proptest (policy) + escape red-team harness

Rejected

unit-only

When the rejected choice is right

Unit-only testing (no escape/property tests): justified for a pure-computation library with no privilege boundary, no hostile-input surface, and no OS-level sandbox to verify

Why: the failures that matter are escapes

020

Fuzzing

Chosen

cargo fuzz on IPC parser + policy parser + origin parser

Rejected

none

When the rejected choice is right

No fuzzing: justified only for a deterministic, formally-verified parser where the input grammar is fully specified and all edge cases are covered by a complete proof

Why: the hostile-input surface (I7)

021

Sandbox conformance

Chosen

syscall-escape test battery (attempt every denied syscall)

Rejected

trust the filter

When the rejected choice is right

Trust the seccomp filter without conformance testing: justified when using a vendor-supplied, independently certified filter on a locked kernel version with a frozen ABI

Why: verify the cage actually denies (I8)

022

CI

Chosen

GH Actions: build+clippy+test+miri+fuzz-smoke+escape-tests

Rejected

none

When the rejected choice is right

No CI / manual QA only: justified for a research prototype that will never be deployed and where the cost of CI setup exceeds the expected lifetime of the codebase

Why: gates; escape tests block merge

023

Deps policy

Chosen

minimal, pinned, cargo deny (advisories+licenses)

Rejected

When the rejected choice is right

Many unpinned dependencies: justified for a pure research library with no privileged code path, no security-critical surface, and no production deployment

Floating toolchain / non-reproducible build: justified for an internal development tool with no security provenance requirements and no auditable release artifact

Sanitizers

Chosen

Miri (UB) on safe code; ASAN on unsafe seams

none

No sanitizers (no Miri/ASAN): justified for a pure-safe Rust codebase with zero unsafe blocks and no FFI, where UB is structurally impossible

Versioning

Chosen

SemVer on IPC wire + capability + policy schema

Rejected

implicit

When the rejected choice is right

Implicit / unversioned IPC wire format: justified for a single-binary tool where broker and child are always built and deployed together from the same commit with no independent upgrade path

030

Privilege at start

Chosen

broker drops caps it doesn't need; children start with no_new_privs

Rejected

run as root

When the rejected choice is right

Run broker with full privileges (no cap-drop): justified in a controlled, single-user embedded environment where the broker is the only process on the system and privilege separation is not the threat model

Why: least authority (principle 2) even for the broker

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

SFI-Everything Single Process (In-Process WebAssembly Sandboxing)

┌─────────────────────────────────────────────────────┐
│  SINGLE BROWSER PROCESS                             │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────┐ │
│  │ Renderer tab │  │ Media codecs │  │ Font shaper│ │
│  │  (Wasm SFI)  │  │  (Wasm SFI)  │  │ (Wasm SFI) │ │
│  └──────┬───────┘  └──────┬───────┘  └─────┬─────┘ │
│         │  host calls only (no OS syscalls) │       │
│  ┌──────▼───────────────────────────────────▼─────┐ │
│  │  Wasm runtime (trusted supervisor)              │ │
│  │  memory isolation via linear-memory bounds      │ │
│  └─────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘

Wins when: the OS provides no usable sandbox primitives (embedded platforms, WASI), or the attack surface is dominated by in-process C++ codecs (image/font/media decoders) rather than the renderer runtime itself; RLBox (Firefox) takes exactly this approach for codecs.

Embodied by: Firefox RLBox (USENIX Security 2020, Narayan et al.); extended to the limit this becomes the "compile everything to Wasm in one process" model.

Why rejected here: SFI-in-process does not prevent speculative side channels — all Wasm sandboxes share the process address space, and a Spectre gadget in one sandbox reads the host's memory. For a threat model of "assume the renderer is fully compromised and Spectre exists," process separation (OS-enforced, hardware memory-isolated) is the only robust defense (MM4, I4). This design treats the renderer payload as untrusted from outside a hard OS boundary, not from inside a software-enforced one.

Per-Site Micro-VM Isolation

┌──────────────────────────────────────────────────────────┐
│  HOST BROKER                                             │
│  allocates lightweight VMs per site                      │
└──────────┬───────────────────────┬───────────────────────┘
           │ virtio IPC            │ virtio IPC
┌──────────▼──────────┐  ┌─────────▼─────────────────────┐
│  MICRO-VM: site A   │  │  MICRO-VM: site B              │
│  (disposable VM)    │  │  (disposable VM)               │
│  own guest kernel   │  │  own guest kernel              │
│  own page tables    │  │  own page tables               │
└─────────────────────┘  └────────────────────────────────┘

Wins when: the host kernel's syscall surface is itself large and exploitable, or the threat model includes kernel-level exploits (ring-0 elevation); a compromised renderer exploiting a kernel bug cannot escape a VM boundary. Also wins for forensic isolation (a disposable VM is destroyed after browsing, leaving no host state).

Embodied by: Qubes OS disposable VMs; Bromium (now HP Wolf Security) micro-virtualization; Intel VT-x / AMD-V hardware isolation.

Why rejected here: micro-VM spawn time (100–500 ms per VM) violates the §4 spawn target (≤ 50 ms) and the user-visible navigation latency budget. Per-VM memory overhead (a guest kernel + its page tables + virtio stack) is 3–10× the per-process overhead of this design. The design space between "process + seccomp + userns" and "VM" is covered by the multi-layer model here (MM3); a kernel exploit bypassing seccomp is a residual risk acknowledged in Appendix C.7.

Remote Browser Isolation (Server-Side Rendering)

┌────────────────────────────┐         ┌───────────────────────────────┐
│  USER ENDPOINT             │         │  REMOTE RENDERING CLUSTER     │
│  (thin client)             │         │  ┌──────────────────────────┐ │
│  receives: draw commands   │◄────────│  │ Renderer process         │ │
│            or pixels       │  pixels/│  │ (runs full web content)  │ │
│                            │ drawcmds│  └──────────────────────────┘ │
│  no web content execution  │         │  network isolation; TLS term  │
└────────────────────────────┘         └───────────────────────────────┘

Wins when: the endpoint is untrusted, unmanaged, or locked-down (e.g., a kiosk, a government endpoint, a BYOD device accessing sensitive SaaS); the user device never executes web content, so a browser exploit on the client is irrelevant; the server-side renderer is isolated per-session.

Embodied by: Cloudflare Browser Isolation (uses Chromium-based remote rendering, pixel/draw-command streaming); Authentic8 Silo; Menlo Security.

Why rejected here: this design's goal is an embeddable security model (sbx-browser beneath #266/#305) running on the user's machine. Remote isolation introduces network latency (impractical for interactive content), requires a server-side rendering fleet (operational complexity outside scope), and changes the trust model entirely (the server operator must be trusted). For local browser security, the OS-process model is the right abstraction.

Single-Sandbox Multi-Process Without Site Isolation (Pre-2018 Chrome Model)

┌────────────────────────────────────────────────────────┐
│  BROWSER PROCESS (privileged, trusted)                 │
└──────────────┬────────────────────────────────────────┘
               │ IPC (typed)
┌──────────────▼────────────────────────────────────────┐
│  ONE RENDERER PROCESS  (sandboxed, but multi-site)    │
│  https://news.example, https://bank.example,          │
│  https://ads.example — ALL co-resident in one process │
│  seccomp-bpf + userns (OS cage present)               │
│  BUT: same address space = Spectre-visible            │
└───────────────────────────────────────────────────────┘

Wins when: memory is severely constrained (one renderer process vs N), Spectre is not in the threat model (pre-2018, or a platform with hardware mitigations considered sufficient), and the primary threat is code-execution escape to the host OS rather than cross-origin data leakage.

Embodied by: Chromium before Site Isolation full rollout (pre-Chrome 67, 2018); still the default on Android Chrome below a memory threshold.

Why rejected here: a Spectre gadget in any script on any tab can speculatively read any co-resident cross-origin data — all cookies, tokens, and DOM of every other origin in the same process. The January 2018 Spectre disclosure (Kocher et al.) and the subsequent full-desktop Chrome Site Isolation rollout (Reis et al. 2019) demonstrate that co-residency is not a theoretical risk; it is an exploited attack class. This design's §4 side-channel posture and I4 make site isolation non-negotiable (MM4).
