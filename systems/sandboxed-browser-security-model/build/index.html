⬜ Phase 0 — Process Model, Typed IPC, Broker Skeleton

Objectives

Stand up the trust-boundary skeleton: ProcessRole model + spawn (bsm-process), a typed SEQPACKET IPC channel with framing (bsm-ipc), and a deny-by-default broker stub (bsm-broker) that the sbx-browser launcher drives. Constraint from day one: the broker grants nothing implicitly (I3), and the IPC parser never panics on a malformed frame (I7). No OS sandbox yet (Phase 1) — but the shape (renderer requests, broker decides) is fixed now.

Deliverable

sbx-browser demo launches a broker + one (unsandboxed) child, exchanges one IPC message, and the broker denies it — printing the logged verdict + the process lifecycle transitions.

Acceptance
  • Broker denies 100% of requests (no grant path exists yet) — verified by test (I3).
  • IPC round-trip works for well-formed frames; 1M malformed-frame fuzz-smoke → 0 panics/OOB (I7).
  • Every verdict + lifecycle transition appears in the structured log (I10).
  • Child runs in a separate address space (verified via distinct pid + no shared memory map).
Fixtures

conformance/ipc/{frame_minimal,frame_with_fds,frame_max_len}, conformance/ipc/malformed/{len_overflow,nfds_too_many,truncated_payload,unknown_kind}, conformance/policy/deny_default (asserts empty policy ⇒ deny-all).

Pitfalls
  • Trusting frame len to size an allocation → OOM bomb; cap len ≤ MAX_FRAME before allocating (I2/I7).
  • Stream vs datagram confusion → using SOCK_STREAM loses message boundaries → re-sync attacks; SEQPACKET (ADR-007).
  • fd leak on error path → recv'd fds not closed on a rejected frame → fd exhaustion; RAII OwnedFd.
  • Implicit allow → a missing match arm defaulting to allow → escape; exhaustive match, default-deny (I3).
  • Spawning a thread not a process → shared address space → no isolation; fork+execve (ADR-016).

⬜ Phase 1 — OS Sandbox: seccomp-bpf Allowlist + User Namespaces + Landlock

Objectives

Build the OS cage (bsm-sandbox): a per-role seccomp-bpf syscall allowlist (I8), user namespaces for uid/pid/net/ipc isolation, and Landlock filesystem restriction. After this phase a renderer child can compute but cannot touch the filesystem, network, or other processes directly. Constraint: sandbox install is the irrevocable point of no return (§8.5); unsafe is confined here (ADR-006).

Deliverable

sbx-browser spawn --role renderer launches a child that is sandboxed: an attempt to open("/etc/passwd") or socket() from the child fails (SIGSYS/EPERM), proving the cage (I8).

Acceptance
  • Renderer allowlist ≤ ~150 syscalls (§4); every non-allowlisted syscall denied (verified by the escape/syscall_escape battery, ADR-021).
  • 0 direct file/net syscalls succeed from the renderer (I1/I8).
  • Sandbox install adds ≤ 50 ms to spawn (§4).
  • Miri-clean on safe code; ASAN-clean on the unsafe seam (ADR-026).
Fixtures

conformance/sandbox/{renderer_allowlist,network_allowlist,gpu_allowlist} (expected allow/deny per syscall), conformance/sandbox/landlock/{no_fs,temp_only}, escape/syscall_escape.rs (attempts open/socket/ptrace/execve/clone — all must fail).

Pitfalls
  • Filter-ordering bug: installing seccomp before the namespace/Landlock setup syscalls → setup itself is killed; install seccomp last (§1.2 order).
  • Forgetting no_new_privs → unprivileged seccomp install fails (EPERM); set it first.
  • Allowlisting too much (open, socket, ptrace) → defeats the cage; minimal set, justified per syscall (principle 9).
  • clone/fork flag mistakes → child shares a namespace it shouldn't; explicit flags (ADR-005).
  • Architecture-specific syscall numbers → an x86-64 allowlist on ARM denies the wrong calls; arch-aware tables (Garfinkel-style interposition pitfall).
  • vfork/clone allowed → renderer spawns helpers → broadens surface; deny process-creation syscalls.

⬜ Phase 2 — Broker + Deny-by-Default Capability Brokering

Objectives

Turn the broker stub into a real deny-by-default policy engine (bsm-broker) that performs privileged operations on behalf of sandboxed children after a policy check: file-open, net-connect, GPU-submit. Authority is minted as a Capability and handed back; the renderer never gains ambient authority (I12, principle 3/4). Brokered ops are TOCTOU-safe (§8.8, I9).

Deliverable

sbx-browser broker-demo: a sandboxed renderer requests a brokered file-read it is allowed (gets an fd) and one it is not (gets Deny); both decisions are logged and deterministic.

Acceptance
  • Deny-by-default: any op without an explicit grant → Deny (I3); policy-fuzz finds no implicit-allow path.
  • Broker decision latency p99 ≤ 100 µs (§4) — measured (criterion).
  • Brokered file-open is TOCTOU-safe: a symlink/rename race cannot redirect the opened fd (I9) — verified by escape/path_traversal.
  • Every privileged op goes through the broker (no unmediated path, I12) — verified by a surface audit.
Fixtures

conformance/capability/{mint_file_read,deny_no_grant,revoke_epoch,subset_rights}, conformance/policy/{grant_file_under,deny_outside_subtree}, escape/path_traversal.rs (../, symlink swap, absolute escape — all Deny).

Pitfalls
  • Check-then-open by path (renderer supplies path, broker stats then opens) → classic TOCTOU; instead the broker opens once + validates the resulting fd/inode (I9, §8.8).
  • Trusting requested_rights → renderer asks for more than granted; the broker mints only the intersection with policy (subset, principle 4).
  • Canonicalization after the check → traversal slips through; canonicalize before the policy decision (I9, principle 10).
  • Capability id guessable/sequential → renderer forges one; use an unguessable nonce + server-side table (I6).
  • Forgetting to revoke on tab close → capability outlives its need; revoke + epoch-bump on lifecycle end.

⬜ Phase 3 — Capability-Passing Typed IPC (Handle/fd Passing, No Ambient Authority)

Objectives

Complete the capability-passing IPC (bsm-ipc): typed interfaces bound by capability, handle/fd transfer via SCM_RIGHTS, and the guarantee that a renderer has no ambient authority — it can only act through capabilities it was explicitly handed (I1, principle 4). This is the Mojo-style contract: messages are typed, channels are capabilities, there is no global namespace a renderer can reach.

Deliverable

sbx-browser cap-demo: the broker hands a renderer a single file-read capability (an fd); the renderer uses it; an attempt to use a capability it was never given (forged handle) is rejected (I6). The renderer's authority = exactly its capability set, nothing more (I1).

Acceptance
  • Zero ambient authority: an audit (escape/forged_origin-style + a capability audit) finds no env/identity-derived authority in the renderer (I1).
  • A forged/stale CapHandle → reject, never resolve (I6) — escape/handle_forge.
  • Subset-only delegation: a renderer cannot widen rights on a capability it re-passes (principle 4) — tested.
  • fd passing works + leaks no fds (RAII verified under ASAN).
Fixtures

conformance/capability/{bind_interface,delegate_subset,forge_handle_reject,stale_epoch_reject}, conformance/ipc/{fd_pass_roundtrip,nfds_cap}, escape/handle_forge.rs.

Pitfalls
  • Ambient channel (a renderer can connect to any service by name) → defeats capabilities; channels are only obtained via a held capability (principle 4).
  • Rights widening on delegation → privilege escalation; intersect rights on every transfer (subset-only).
  • fd table confusion → passing the wrong fd (off-by-one in the SCM_RIGHTS array); index carefully.
  • Handle resolves in the wrong CapTable → cross-process authority confusion; resolve in the receiver's table only (I6).
  • Capability outliving the backing object → use-after-free of an fd; epoch + revoke on close.

⬜ Phase 4 — Site Isolation: Process-per-SiteInstance Allocation

Objectives

Make site isolation real (bsm-isolation): allocate one renderer process per SiteInstance, place cross-site iframes in their own process (OOPIFs), and re-evaluate on every navigation commit so cross-origin data is never co-resident (I4, principle 6 — the Spectre defense). This is the 2018 response to Spectre: address-space separation by Site.

Deliverable

sbx-browser isolation-demo: load a top-level site that embeds a cross-site iframe; observe two distinct renderer processes (one per Site); a navigation to a different Site triggers a process swap (logged).

Acceptance
  • Every SiteInstance is in its own process; cross-site iframe ⇒ separate process (I4) — conformance/isolation.
  • A cross-site navigation commit swaps processes (no cross-site co-residency) — verified by escape/coresidency.
  • A co-residency check (cross_site_coresident counter) stays 0 (I4).
  • Process allocation is deterministic given the same navigation sequence (I10).
Fixtures

conformance/isolation/{same_site_reuse,cross_site_oopif,cross_site_navigation_swap,opaque_origin_isolated,subdomain_same_site}, escape/coresidency.rs (attempts to force two Sites into one process — must fail).

Pitfalls
  • Using Origin instead of Site for isolation → over-fragmentation (every subdomain its own process) or under-isolation; Site = eTLD+1 (ADR-011, §8.1).
  • Committing before the swap → a window where cross-site content is briefly co-resident; swap before commit (I4).
  • about:blank/data:/blob: origin inheritance → wrong SiteInstance; opaque origins get their own isolated instance (§8.1).
  • Process reuse across BrowsingInstances → scripting boundary confusion; SiteInstance includes the BrowsingInstance id.
  • Redirect during navigation changes the destination Site mid-flight → re-evaluate on the final origin at commit.

⬜ Phase 5 — Same-Origin Policy Enforcement at the Process Boundary

Objectives

Enforce the Same-Origin Policy (bsm-origin) across the process boundary: DOM/script/storage access between frames is allowed only for same-origin (I5), and — crucially — the check lives on the trusted side, never trusting the renderer's origin claim (I2, principle 5). With OOPIFs (Phase 4), cross-origin DOM access is now an IPC that the browser mediates.

Deliverable

sbx-browser sop-demo: two frames (same-origin and cross-origin); same-origin DOM access succeeds, cross-origin is denied; the denial uses the browser-tracked origin, not the renderer's claim (a forged claim doesn't help).

Acceptance
  • Same-origin access allowed, cross-origin denied (I5) — conformance/sop vectors.
  • A renderer forging its origin gains nothing (the browser uses its own tracked origin, I2) — escape/forged_origin.
  • Origin canonicalization handles tricky inputs (trailing dots, default ports, IDN, uppercase host) deterministically (I9).
  • Storage access is origin-partitioned (a renderer reads only its origin's storage).
Fixtures

conformance/sop/{same_origin_allow,cross_origin_deny,default_port_equiv,idn_host,opaque_deny,postmessage_origin}, escape/forged_origin.rs (renderer lies about its origin — denial unaffected).

Pitfalls
  • Trusting event.origin/the renderer's claimed origin → UXSS; the browser stamps the true origin (I2, principle 5).
  • Port/scheme omission in comparison (http vs https, default port) → origin confusion; canonicalize fully (I9).
  • IDN/punycode mismatch (xn-- vs unicode) → spoofed same-origin; canonicalize to one form.
  • Treating null/opaque origins as equal → cross-origin leak; opaque ≠ opaque (each unique, §8.1).
  • Subdomain confusion (a.example vs example) → wrong same-origin/same-site result; tuple for origin, eTLD+1 for site.

⬜ Phase 6 — CORP / CORB-ORB / COOP / COEP + Network-Process Origin Checks

Objectives

Enforce the cross-origin resource policies in the network process (bsm-net): CORP + ORB gate which response bytes ever reach a renderer (I5); COOP isolates browsing contexts; COEP enables cross-origin isolation (the Spectre-safe SharedArrayBuffer gate, §8.6); Sec-Fetch metadata gives the server request context. Cross-origin bytes never enter a renderer that shouldn't see them (I5, principle 6).

Deliverable

sbx-browser corp-demo: a cross-origin no-cors fetch of a CORP-same-origin resource is blocked at the network process (bytes never reach the renderer, §8.7); a COOP+COEP page becomes cross-origin-isolated (crossOriginIsolated true).

Acceptance
  • CORP/ORB block cross-origin bytes per table §8.6 (I5) — conformance/corp + conformance/orb.
  • Cross-origin response bytes never enter the wrong renderer (I5) — verified end-to-end (the network process drops them).
  • COOP severs cross-origin openers (new BrowsingInstance); COEP require-corp + COOP same-origin ⇒ isolation.
  • Sec-Fetch headers set on the trusted side; a renderer cannot forge them (I2).
Fixtures

conformance/corp/{same_origin_block,cross_origin_allow,same_site_mixed}, conformance/orb/{html_blocked,json_blocked,image_allowed,nosniff}, conformance/coop/{sever_opener,allow_popups}, conformance/coep/{require_corp_block,isolation_enabled}, conformance/cors/{preflight,allow_origin}.

Pitfalls
  • MIME sniffing to bypass ORB → honor X-Content-Type-Options: nosniff; ORB sniffs conservatively (block on doubt, principle 7).
  • Applying CORP after bytes reach the renderer → too late (the leak already happened); gate in the network process before delivery (I5).
  • CORS credentials with wildcard * → credential leak; reject * + credentials.
  • COOP/COEP interaction subtlety → isolation requires both (same-origin COOP AND require-corp COEP); one alone doesn't isolate (§8.6).
  • Trusting a renderer-supplied Origin/Sec-Fetch → spoofed context; the browser sets these (I2, principle 5).
  • Redirect chains changing the response origin → re-evaluate CORP/ORB on the final response.

⬜ Phase 7 — Renderer-Compromise Containment + Escape Red-Team Tests

Objectives

Validate the central thesis end-to-end: a fully-compromised renderer reaches nothing it shouldn't (principle 1). Build the escape/ red-team battery — a suite of attacks (syscall escape, path traversal, handle forge, forged origin, co-residency, IPC abuse) that must fail — and an attacker-controlled stub renderer that exercises them. This phase certifies containment.

Deliverable

make escape-tests runs the full battery; every attack fails (the cage holds). A "compromised renderer reachability" report enumerates exactly what authority a compromised renderer has (its capabilities) and proves it reaches nothing else.

Acceptance
  • 100% of escape-battery attacks fail (no escape) — the release gate (ADR-021).
  • The reachable-surface report matches the audited broker surface (no unmediated authority, I12).
  • A compromised renderer reaches: only its own Site's data + brokered ops it was granted; nothing else (§4 containment).
  • The battery runs in CI on every merge (escape.yml) — a regression blocks merge.
Fixtures

escape/{syscall_escape,path_traversal,handle_forge,forged_origin,coresidency,ipc_abuse}.rs; conformance/containment/reachable_surface (the enumerated authority of a compromised renderer).

Pitfalls
  • A new IPC surface added without a capability gate → a new escape; CONTRIBUTING requires capability-gating + an escape test for every new broker op (principle 9).
  • An escape test that passes for the wrong reason (the attack didn't actually execute) → false confidence; assert the attack ran and was denied.
  • Library code in the renderer with ambient authority (a logging lib that opens a file) → an escape; audit the renderer's transitive authority (I1).
  • A syscall added to the allowlist for convenience → a hole; every allowlist entry needs a justification + a re-run of the battery.
  • Time-of-check races in the broker re-introduced → re-run TOCTOU tests.

⬜ Phase 8 — OS Seams: Windows (Job Object / AppContainer), macOS (Seatbelt)

Objectives

Implement the trait Os (ADR-015) for non-Linux platforms so the same security model holds cross-platform: Windows job objects + AppContainer/restricted tokens, macOS Seatbelt (sandbox profiles). The policy + capability + isolation layers (Phases 2–6) are OS-agnostic; only bsm-sandbox's cage implementation differs (principle: portability without leaking platform-isms).

Deliverable

sbx-browser spawn --role renderer produces an equivalently-sandboxed child on Windows + macOS: the same escape battery (Phase 7) runs + passes per platform.

Acceptance
  • The escape battery passes on Linux, Windows, macOS (per-platform CI) — the cage holds everywhere (I8).
  • The policy → platform-primitive mapping is complete (every Linux guarantee has a Windows + macOS analog) — Appendix D.
  • IPC + capability + isolation layers are unchanged across platforms (OS-isms confined to bsm-sandbox, ADR-006/015).
  • Spawn latency per platform within target (≤ 50 ms + platform overhead).
Fixtures

conformance/sandbox/{windows_lowbox,windows_job,macos_seatbelt} (per-platform allow/deny expectations), the cross-platform escape battery, docs/security/sandbox-os.md (the mapping).

Pitfalls
  • A platform with no eTLD-precise equivalent → use the closest primitive + document the gap (Appendix D).
  • Windows token/job subtleties (handle inheritance, broker handle duplication) → a leaked handle = an escape; explicit handle hygiene.
  • macOS Seatbelt profile gaps (a too-permissive allow) → re-run the battery; Seatbelt profiles are easy to over-grant.
  • Mach port / named-pipe capability semantics differ from Unix fd passing → preserve the capability model (handle, not name, I6).
  • Platform-specific syscalls leaking into policy → keep policy abstract; lower per platform in bsm-sandbox.

⬜ Phase 9 — Crash Isolation + Process Lifecycle Security

Objectives

Guarantee that a renderer crash/kill is contained: it affects only its tab, never the broker or sibling renderers (I11, principle 12), and the lifecycle (spawn→quarantine→kill→respawn) is itself secure (no use-after-free of capabilities/channels, no resurrection of authority). Availability under a hostile/crashing renderer.

Deliverable

sbx-browser crash-demo: kill a renderer mid-request; the broker survives, siblings are unaffected, the tab respawns fresh; the dead renderer's capabilities are all revoked (no leak).

Acceptance
  • A crashed/killed renderer never takes down the broker or siblings (I11) — conformance crash-injection + escape/ipc_abuse flood.
  • On crash, all of the child's capabilities are revoked (no stale authority survives, I6).
  • A half-processed request at crash time is dropped, never partially granted (I7).
  • Respawned renderers start with zero inherited authority (I1).
Fixtures

conformance/lifecycle/{crash_mid_request,kill_on_violation,respawn_fresh_authority,sibling_unaffected}, conformance/lifecycle/{cap_revoked_on_death,broker_survives_flood}.

Pitfalls
  • Capability survives the process (the fd/handle not revoked on death) → a respawned/other process inherits authority; revoke + epoch-bump on every teardown (I6).
  • Broker blocks on a dead child's socket → broker hang (DoS); non-blocking + timeout + broken-pipe handling.
  • A crash during capability mint leaves a dangling table entry → clean up on teardown.
  • Respawn loop (a renderer that crashes immediately) → exponential backoff + a crash-loop breaker (don't burn CPU).
  • Zombie processes (un-reaped children) → reap on SIGCHLD; PID-namespace init reaps in the cage.

⬜ Phase 10 — Hardening: IPC Fuzzing, Policy Fuzzing, Seccomp Escape Tests

Objectives

Make the trusted surface unbreakable on hostile input: fuzz the IPC frame parser, the policy parser, and the origin parser (cargo fuzz, ADR-020); enforce all bounds (I2/I7); run the seccomp escape battery exhaustively (I8); Miri/ASAN the unsafe seams (ADR-026). The broker must never panic or grant on any malformed input.

Deliverable

Green 24h fuzz (0 crashes) on all parsers; Miri-clean safe code; ASAN-clean unsafe; the full seccomp escape battery passes.

Acceptance
  • 0 panics/OOB/overflow across ≥1e9 fuzz execs on every parser (I7).
  • Malformed policy → fail-closed (no process spawns, principle 7) — fuzz-verified.
  • Every non-allowlisted syscall denied per arch (I8) — exhaustive battery.
  • Miri no-UB; ASAN clean on the unsafe seam (ADR-026).
Fixtures

fuzz/corpus/* (seeded from conformance vectors), conformance/policy/malformed/* (fail-closed), conformance/ipc/malformed/*, conformance/sandbox/escape_battery (every denied syscall).

Pitfalls
  • Allocating from an attacker len/count (Vec::with_capacity(frame.len)) → OOM; cap before allocating (I2).
  • A panic path in the broker (an unwrap/array index on hostile input) → a DoS of the trusted process; fuzz finds it (I7).
  • unsafe creeping outside bsm-sandbox → UB risk; a grep/clippy gate (ADR-006).
  • A policy parser that accepts a partial/ambiguous policy → a permissive hole; total parse, fail-closed.
  • Seccomp filter wrong on a second architecture → a hole on that arch; per-arch battery.
  • Fuzzer not reaching deep states (binding required first) → structure-aware fuzzing / seed corpus.

⬜ Phase 11 — Red-Team / Escape-Resistance + Soak + Reproducible Release

Objectives

Final certification: an extended red-team pass (creative escape attempts beyond the battery), a soak under sustained hostile + realistic load (no leaks, bounded resources, broker stays up), and a reproducible, signed release with provenance (ADR-024/025). The artifact: a security model proven to contain a compromised renderer, ready to embed beneath #266/#305.

Deliverable

Green CI (build+clippy+test+miri+fuzz-smoke+escape battery); a soak report (broker uptime, flat memory, 0 escapes); a signed, reproducible release with SBOM + provenance.

Acceptance
  • Extended red-team: 0 successful escapes (the release gate) — every finding fixed + regression-tested.
  • Soak: ≥ 24h, broker uptime 100% (I11), memory flat (no leak), escape_successes=0, cross_site_coresident=0.
  • Reproducible build verified (bit-identical re-build); SBOM + signature present; cargo deny clean.
  • All invariants I1–I12 hold under soak; all 12 principles satisfied (audited).
Fixtures

The full escape/** battery + red-team additions, conformance/** complete suite, the soak harness config, the reproducible-build verification script, the SBOM.

Pitfalls
  • A new surface added late (a feature that bypasses the broker) → re-audit + escape-test before release (principle 9).
  • A leak that only shows under soak (fd/memory slowly growing) → the soak's flat-resource assertion catches it.
  • Oracle/dep drift breaking reproducibility → pin everything (ADR-024).
  • A signed release of an unaudited binary → sign only after the full gate passes (escape + fuzz + soak).
  • Side channels not covered by the battery (a novel speculative gadget) → site isolation is the structural defense; document residual risk.
