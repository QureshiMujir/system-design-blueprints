337 — Sandboxed Browser Security Model from Scratch

Project Number: 337

Project Name: Sandboxed Browser Security Model from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build the security model of a modern multi-process browser: the privilege separation, sandboxing, IPC trust boundary, and web-platform isolation policies (same-origin, site isolation, CORP/COOP/COEP) that contain a compromised renderer and prevent cross-origin data theft. This is the Chromium/Firefox security architecture built as a focused, testable system: a privileged broker process, unprivileged sandboxed child processes (renderer/GPU/network/utility), a capability-passing IPC layer, an OS-level sandbox policy (syscall filtering + namespace/filesystem restriction), and the origin/site-isolation enforcement that decides what each process may load and access.

In scope: the process model + trust boundaries (privileged browser/broker vs untrusted renderer); the renderer sandbox (Linux seccomp-bpf syscall filter + user namespaces + Landlock/filesystem restriction; an Os seam for Windows job-objects/AppContainer + macOS Seatbelt); the broker that performs privileged operations (file open, network connect, GPU access) on behalf of sandboxed children after policy checks; capability-based IPC (Mojo-like: typed messages, handle/capability passing, no ambient authority); site isolation (process-per-site-instance) + same-origin policy enforcement at the process boundary; cross-origin resource policies (CORP/COOP/COEP), Sec-Fetch metadata, and the network-process origin checks; a threat model centered on "assume the renderer is fully compromised."

Explicit non-goals (deferred features — see the Deferred Features Register before the Glossary): the rendering engine itself (HTML/CSS/JS) — that is #305/#266 and is treated as the untrusted payload inside the renderer (containment certified in §7.10); a JS engine (the same untrusted payload, §7.10); full network stack/TLS internals — reuse #64/#234, here only the origin-enforcement seam (§6.10); the multi-process plumbing/lifecycle mechanics in depth — that is #266, cross-linked, while this project focuses on the security of those boundaries (§9.10); GPU driver internals (brokered access only, §2.10); a UI (platform integration only, §8.10).

Deployment model: a library + a sbx-browser test harness that launches a broker + sandboxed child processes, runs a (stub) untrusted "renderer" workload, and demonstrates that the sandbox + policy + IPC contain it. Embeds the security layer beneath #266/#305.

Target users: browser/security engineers reasoning about sandbox escapes + site isolation; OS-security engineers building syscall/capability sandboxes; learners building Chromium's security architecture from first principles.

Phase 0 deliverable (crates/modules):

  1. bsm-types — Origin, SiteInstance, ProcessRole, Capability, IpcMessage, error enum.
  2. bsm-process — process model + spawn (browser/broker/renderer/utility roles).
  3. bsm-ipc — typed message channel (socketpair) with handle passing (skeleton).
  4. bsm-broker — privileged request handler skeleton (deny-by-default).
  5. sbx-browser — launcher that spawns a broker + one child and exchanges a message.

Later phases unlock: the sandbox policy (seccomp/namespaces/Landlock) (Phase 1); the broker + capability brokering (Phase 2); capability-passing IPC + interface binding (Phase 3); site isolation + process allocation (Phase 4); same-origin policy enforcement (Phase 5); CORP/COOP/COEP + network-process checks (Phase 6); renderer-compromise containment + escape testing (Phase 7); OS seams (Windows/macOS) (Phase 8); crash isolation + process lifecycle security (Phase 9); hardening/fuzz/red-team + reproducible release (Phase 10–11).

Timeline: Phase 0 = 6–14 weeks; full = 8–12 months (sandbox policy + site isolation + escape-resistance are the long poles).

Recommended language: Rust (edition 2021, ≥1.78). Rationale: (a) the privileged broker + IPC parsing are the highest-value attack surface — Rust's memory safety removes the entire class of C++ bugs that cause real browser sandbox escapes; (b) the type system encodes capabilities (unforgeable handles) + origins precisely; (c) Send/Sync + ownership model the process/handle boundaries; (d) it isolates the unavoidable unsafe (seccomp BPF install, clone/namespaces, fd passing) into audited modules; (e) shares the workspace with #266/#305. Locked ADR-001. (Chromium is C++ for legacy reasons; new sandbox/IPC code is increasingly Rust — justified over C++ in ADR-001 precisely because this is the security-critical layer.)

Prerequisites: OS process/privilege model; Linux namespaces, seccomp-bpf, Landlock, capabilities(7); IPC + fd passing (SCM_RIGHTS) (#149); the web origin model (RFC 6454), CORS, CORP/COOP/COEP; capability-based security theory; the browser process model (#266); Rust ownership + unsafe discipline.

2. Why Build This

  • Unique knowledge: how to contain a fully-compromised, untrusted code execution environment (a renderer running attacker JS + a memory-unsafe parser) so that owning it yields nothing — no file access, no other origins' data, no host compromise. This is the deepest applied security architecture in consumer software.
  • Historical/architectural: Chromium's 2008 multi-process sandbox + the 2018 Site Isolation response to Spectre redefined browser security; this rebuilds that model (broker/sandbox/IPC/site-isolation) and the threat reasoning behind it.
  • Engineering muscles: privilege separation; least-authority design; OS sandbox mechanisms (seccomp/namespaces/Landlock/job-objects); capability-based IPC (no ambient authority); origin/site reasoning; designing for "assume the renderer is owned."
  • Production concepts: trust boundaries, attack-surface minimization, defense-in-depth, capability passing, deny-by-default brokering, side-channel-aware isolation (Spectre → site isolation).
  • Cross-links: #266 Browser Sandbox / Multi-Process Architecture (the process plumbing this secures), #305 Browser Rendering Engine (the untrusted payload), #50 Sandbox / Code Execution (sibling sandbox), #149 IPC (the channel), #148 Virtual Memory + #153 Hypervisor (isolation primitives), #234 PKI/#64 HTTP (network/origin), #338 WAF (network-side security, adjacent).
  • Calibration: after this you can threat-model any sandbox, reason about what a renderer exploit can and cannot reach, and design least-authority IPC — the core of modern client security.

What Mastery Looks Like — finishing this blueprint means you can:

  • Design a deny-by-default capability broker with TOCTOU-safe mediation and audit every privileged op surface (Phase 2)
  • Build and correctly order a seccomp-bpf + user-namespace + Landlock sandbox cage with no ambient authority in the child (Phase 1)
  • Implement a typed, length-prefixed IPC channel where malformed frames always deny and never grant (Phase 0, Phase 10)
  • Enforce site isolation at the allocator and commit boundary so cross-origin data is never co-resident under Spectre (Phase 4)
  • Apply CORP, ORB, COOP, and COEP in the network process so cross-origin bytes are blocked before reaching the renderer's address space (Phase 6)
  • Enumerate the exact reachable surface of a fully-compromised renderer and prove it via a reproducible escape battery (Phase 7, Phase 11)
  • Port the trust boundary across OS sandbox primitives (Windows job/AppContainer, macOS Seatbelt) without changing the capability or IPC contracts (Phase 8)

Per-box: Browser/broker (privileged) — the only process with real authority (files, sockets, GPU, spawning); runs no untrusted content; enforces policy on every child request (deny-by-default). Renderer (untrusted) — runs the web payload (#305) + attacker-controlled JS; assume it is compromised; it has no ambient authority — it can only do what its sandbox allows (compute) + what it can request over IPC (mediated). Network process (semi-trusted) — performs fetches, enforces origin/CORS/CORP/COOP/COEP so cross-origin bytes never reach a renderer that shouldn't see them. Sandbox policy — the OS-level cage: a seccomp-bpf syscall allowlist, user namespaces, and Landlock filesystem restriction (with an Os seam for Windows/macOS). Security policy — the web-platform layer: Origin/SiteInstance model, Same-Origin Policy, the site→process allocation that makes site isolation real, and the cross-origin resource policies. GPU/utility — additional roles, each least-authority + brokered. The trust boundary (renderer↔broker, renderer↔network) is the red line every message crosses and every check defends.

6. Design Principles

  1. P1 — Assume the renderer is fully compromised. Design every boundary as if attacker code already runs arbitrary instructions in the renderer. Violation: trusting any renderer-supplied value (origin claims, paths, handles) → instant escape/UXSS.
  2. P2 — Least authority (POLA). Each process gets the minimum capability for its role; the renderer gets none ambiently. Violation: a renderer with a stray file capability turns a memory bug into file theft.
  3. P3 — Deny-by-default, complete mediation. The broker denies every request not explicitly allowed by policy; every privileged op is mediated + checked. Violation: an unmediated path = an open door.
  4. P4 — Capabilities, not ambient authority. Authority is an unforgeable handle passed over IPC, not something derived from identity/env. Violation: ambient authority (cwd, env, uid) is reachable by compromised code.
  5. P5 — The trust boundary is the renderer↔broker IPC. All security checks live on the broker side; the renderer's claims are untrusted input. Violation: checking in the renderer = no check.
  6. P6 — Site isolation: cross-origin data is never co-resident. A renderer process only ever holds data for one site; cross-site content lives in another process. Violation: Spectre/UXSS reads another origin's secrets from the same address space.
  7. P7 — Fail safe + fail closed. A policy error, a malformed IPC message, or a broker uncertainty denies the request (and may kill the renderer), never grants. Violation: fail-open turns a bug into a breach.
  8. P8 — Sandboxes are layered (defense in depth). seccomp + namespaces + Landlock + capability IPC + site isolation — no single mechanism is the only line. Violation: one bypassed layer = full compromise.
  9. P9 — Minimize + audit the privileged surface. The broker is small, simple, and memory-safe; the attack surface a renderer can reach is enumerated + tested. Violation: a fat broker is a fat target.
  10. P10 — Validate at the boundary, canonically. IPC messages + origins + paths are parsed/canonicalized on the trusted side before any decision. Violation: path-traversal/origin-confusion via un-canonicalized input.
  11. P11 — Determinism + auditability of decisions. Every allow/deny is a pure function of (policy, request) and is logged. Violation: non-reproducible, unauditable security decisions.
  12. P12 — A renderer crash is contained, not fatal. Killing/crashing a renderer affects only its tab; the broker + other renderers survive. Violation: one site DoSes the browser.

8. Domain Model

The domain has two layers: (a) the web-platform security model — Origin/Site/SiteInstance, Same-Origin Policy, CORP/CORB-ORB/COOP/COEP — enforced on the trusted side; (b) the OS/process security model — ProcessRole, the sandbox cage, and capability-passing IPC across the renderer↔broker trust boundary. The renderer is the adversary; everything below is the containment contract.

8.1 Origin / Site / SiteInstance (the isolation key)

Origin   = (scheme, host, port)                      (RFC 6454 tuple origin)   — SOP key
Site     = (scheme, registrable-domain)              (eTLD+1 via PSL)          — isolation key
SiteInstance = a Site + a BrowsingInstance id        — one renderer process    (I4)
BrowsingInstance = set of windows that can script each other (window.open, frames)
  • Origin is finer than Site: https://a.example.com and https://b.example.com are same-site, cross-origin. SOP uses Origin; site isolation uses Site (so related subdomains can share a process when they can already script each other).
  • One SiteInstance per renderer process (I4). A cross-site iframe ⇒ out-of-process iframe (OOPIF) ⇒ separate process. The SiteInstance→Process map is the broker's allocation table.
  • opaque origin (sandboxed iframe, data:/blob: with no inheritor): a unique, unequal-to-everything origin; never same-origin with any other.

8.2 Policy grammar (EBNF — bsm-policy config that the broker loads)

policy        ::= { rule } ;
rule          ::= role-clause "{" { grant } "}" ;
role-clause   ::= "role" role-name ;
role-name     ::= "browser" | "broker" | "renderer" | "network" | "gpu" | "utility" ;
grant         ::= capability-grant | syscall-grant | fs-grant | net-grant ;
capability-grant ::= "allow" cap-kind [ constraint ] ";" ;     (* deny-by-default: no grant ⇒ deny *)
cap-kind      ::= "file.read" | "file.write" | "net.connect" | "gpu.submit" | "ipc.bind" ;
constraint    ::= "where" predicate ;
predicate     ::= "origin" "==" origin | "path" "under" path | "port" "in" port-set | "site" "==" site ;
syscall-grant ::= "syscall" "{" syscall-name { "," syscall-name } "}" ;   (* seccomp allowlist *)
fs-grant      ::= "fs" ( "ro" | "rw" ) path ;                              (* Landlock ruleset *)
net-grant     ::= "net" "{" addr-family { "," addr-family } "}" ;
origin        ::= scheme "://" host [ ":" port ] ;                        (* canonicalized first, I9 *)
  • Compiles to: a per-role seccomp-bpf program, a Landlock ruleset, and a capability grant table. Every line is a positive grant; the empty set ⇒ deny-all (principle 3, I3).
  • Parser is total: malformed policy ⇒ load fails closed (no process spawns) — never a partial/permissive policy (principle 7).

8.3 Capability model (unforgeable authority)

Capability = (id: u64 nonce, kind: CapKind, resource: ResourceRef, rights: Rights, epoch: u64)
  - minted only by the broker; held as an entry in a per-process CapTable
  - transferred only over IPC by handle index (never by name) — I6
  - backing object: an OS handle (fd on Linux, HANDLE on Windows) passed via SCM_RIGHTS
  - rights: subset-only delegation (a renderer cannot widen rights it was given)
  - epoch: bumped on revoke ⇒ stale capability use ⇒ deny

A capability is a reference + permission that cannot be guessed or forged (the id is a broker-side table index, not a value the renderer chooses). Ambient authority (cwd, env, uid, a path string) is never a capability (principle 4).

8.4 IPC message schema (typed, length-prefixed, fd-carrying)

IpcFrame  = | len: u32 (LE, ≤ MAX_FRAME=64KiB) | channel: u32 | seq: u64 | kind: u16 | nfds: u8 | flags: u8 | payload[len] |
            + ancillary: SCM_RIGHTS array of nfds file descriptors (≤ MAX_FDS=8 per frame)
Request   = BrokerRequest { op, args, requested_rights }                (renderer→broker)
Response  = BrokerResponse { verdict: Verdict, cap?: CapHandle, err? }  (broker→renderer)
Interface = a bound (channel, message-set) pair; binding requires a capability (no ambient channels)
  • Validation order at the broker boundary (every field is hostile, I2/I7): len ≤ MAX_FRAME → nfds ≤ MAX_FDS → kind in role's allowed set → channel bound to caller → decode payload (bounded) → canonicalize args (I9) → policy check (I3) → mediate op. Any failure ⇒ Verdict::Deny (+ optional kill), never grant (I7, principle 7).
  • Wire format is explicit-endian, fixed-layout; no language-native serialization with ambient type confusion. Unknown kind ⇒ deny (forward-compat = additive kinds only).

8.5 Process / trust-boundary state machine

            spawn(role,policy)        sandbox_install (seccomp+userns+Landlock)
  [Unborn] ───────────────────► [Launching] ───────────────────────────────► [Sandboxed]
                                     │ install fails                                │ bind initial cap (IPC chan to broker)
                                     ▼                                              ▼
                                 [Aborted]                                    [Running]
                                                                                   │ malformed IPC / policy violation / crash
                                                                                   ▼

  • A renderer can only ever be Sandboxed→Running; it has no path that grants authority outside brokered requests. Quarantined is the fail-closed sink (principle 7): the broker stops honoring its requests and kills it. A [Dead] renderer never affects the broker or siblings (I11, principle 12).
  • Transition Launching→Sandboxed is the point of no return: after seccomp install the child cannot un-sandbox itself (filters are inherited + irrevocable; no_new_privs set).

8.7 Worked example — cross-origin fetch blocked

1. Renderer (origin https://app.example) runs attacker JS: fetch("https://bank.example/statement", {mode:"no-cors"})
2. Renderer has NO net capability → issues BrokerRequest{op:NetFetch, url, init, initiator=https://app.example} over IPC
3. Network process (trusted) performs the fetch; response carries Cross-Origin-Resource-Policy: same-origin
4. Origin check: initiator (app.example) ≠ resource origin (bank.example); CORP=same-origin ⇒ BLOCK (I5, table §8.6)
5. Response bytes are DROPPED at the network process; renderer receives an opaque/network error — never the bytes
   ⇒ even a fully-compromised renderer cannot read bank.example's response body (no co-residency, no leak)

8.8 Worked example — brokered file-open (TOCTOU-safe)

1. Renderer needs to read a user-picked file (file chooser handled in browser UI, NOT renderer)
2. Browser shows chooser; user selects /home/u/doc.pdf → browser mints Capability{file.read, fd=open(doc.pdf,O_RDONLY)}
3. Broker passes the fd to the renderer via SCM_RIGHTS (handle, not path) — I6
4. Renderer reads via the fd capability ONLY; it cannot open("/etc/passwd") (seccomp denies open*; no path authority — I8)
   ⇒ the renderer never names a path to the broker for opening; the trusted side opened it. No TOCTOU window (the fd
     is already bound to the inode the user chose; a later rename/symlink-swap cannot redirect it). I9 + principle 10.

8.9 Worked example — site-isolation process split (OOPIF)

1. Tab loads https://news.example (top-level) → SiteInstance A → Process P1
2. Page embeds <iframe src="https://ads.example"> (cross-site)
3. Allocator: ads.example is a different Site ⇒ new SiteInstance B ⇒ new Process P2 (OOPIF) — I4
4. P1 (news) and P2 (ads) share NO address space; cross-frame DOM access mediated by SOP across the process boundary
   ⇒ a Spectre gadget in P2 (ads) can only speculatively read P2's own memory — news.example data is not co-resident
     (principle 6 — the Spectre defense). Compositing of the two frames happens in the trusted GPU/browser process.

8.10 Malformed / attack examples (defense in action)

- Forged origin:     renderer sends BrokerRequest{initiator:"https://bank.example"} (lying about who it is)
                     → broker IGNORES renderer-claimed origin; uses the SiteInstance the broker assigned at spawn
                       (origin is broker-tracked state, never a renderer-supplied value) — I2, principle 5. Deny mismatch.
- Path traversal:    renderer requests file.read where path="../../etc/passwd" or "/home/u/doc/../../../etc/shadow"
                     → broker canonicalizes (realpath, resolve symlinks) BEFORE policy check; result escapes the granted
                       Landlock subtree ⇒ Deny (I9). (And renderers don't even get path-based open — §8.8.)
- Handle forge:      renderer crafts BrokerRequest referencing cap id=0x4141414141414141 it never received
                     → broker CapTable lookup miss (id is a server-side table key, not a guessable value) ⇒ Deny (I6).
                     Stale (revoked) cap: epoch mismatch ⇒ Deny.
- Malformed IPC:     frame len=0xFFFFFFFF (claims 4GiB), or nfds=200, or kind=0xDEAD (unknown), or truncated payload
                     → bounded checks (len≤64KiB, nfds≤8, kind∈role-set) fail ⇒ Deny + drop; repeated ⇒ Quarantine→kill.
                       Parser NEVER allocates from attacker length, NEVER grants on malformed (I7, principle 7).
- Syscall escape:    compromised renderer executes open("/etc/passwd"), socket(), ptrace(), execve()
                     → not in the seccomp allowlist ⇒ SIGSYS / EPERM (I8). It can only compute + use passed capabilities.
- Co-residency:      attacker forces two cross-site documents into one process (e.g., via a redirect race)
                     → allocator re-checks Site on every commit; cross-site commit in a single-site process ⇒ process swap
                       (BrowsingInstance/SiteInstance re-evaluation) before the document is committed (I4).

Ownership / capability / serialization notes. Capability is owned by the broker's CapTable; renderers hold only a CapHandle (an index), never the struct — they cannot fabricate one (I6). OwnedFd in IpcMessage transfers OS-handle ownership across the boundary via SCM_RIGHTS (RAII close on drop). IPC payloads are explicit-layout, length-prefixed, validated before any field is interpreted (I7); no native (de)serialization that could type-confuse on hostile bytes (ADR-009). Origin/Site are immutable values; comparison is canonical (I9). All policy decisions (Verdict, CorpDecision) are pure functions of (policy/headers, request) for determinism + auditability (I10, principle 11). unsafe (BPF install, clone, fd dup) is confined to bsm-sandbox (ADR-006).

SemVer (ADR-029). Three independently-versioned contracts: the IPC wire format (MsgKind + frame layout), the capability schema (CapKind/Rights), and the policy grammar (§8.2). Additive message kinds / capability kinds / grant clauses → minor; layout or semantics change → major. Cross-process compatibility (broker↔child across versions) requires wire stability within a major version (principle 11).

Phase 0 — Process Model, Typed IPC, Broker Skeleton

0.1 Objectives

Stand up the trust-boundary skeleton: ProcessRole model + spawn (bsm-process), a typed SEQPACKET IPC channel with framing (bsm-ipc), and a deny-by-default broker stub (bsm-broker) that the sbx-browser launcher drives. Constraint from day one: the broker grants nothing implicitly (I3), and the IPC parser never panics on a malformed frame (I7). No OS sandbox yet (Phase 1) — but the shape (renderer requests, broker decides) is fixed now.

0.2 Detailed Implementation Steps

  • bsm-types: define Origin, Site, SiteInstance, ProcessRole, Capability, CapHandle, IpcMessage, Verdict, BsmError enum (§11). (Saltzer & Schroeder 1975 least-privilege; P2)
  • bsm-process::spawn: fork+execve of a minimal child stub (child_stub.rs) per role; fresh address space (ADR-016, not threads). Parent holds a ChildHandle (pid + the broker-side socket end). (P12, ADR-016)
  • bsm-process::lifecycle: the §8.5 state machine (Unborn→Launching→Sandboxed→Running→Quarantined→Dead); transitions logged.
  • bsm-ipc::frame: encode/decode the §8.4 IpcFrame (len/channel/seq/kind/nfds/flags/payload); explicit LE; len ≤ MAX_FRAME. (I7, ADR-009)
  • bsm-ipc::channel: socketpair(AF_UNIX, SOCK_SEQPACKET) wrapper; send/recv with framing; recv returns Err, never panics.
  • bsm-ipc::validate: the boundary validation order (§8.4) as a reusable guard before payload decode.
  • bsm-broker::engine: handle(caller, req) -> BrokerResponse returning Verdict::Deny for everything (deny-by-default stub); verdict.rs + audit.rs log every decision (I10). (I3, P3)
  • sbx-browser::launcher: spawn a broker + one child; child sends a BrokerRequest; broker denies; assert the round-trip + the logged verdict.

0.3 Deliverable

sbx-browser demo launches a broker + one (unsandboxed) child, exchanges one IPC message, and the broker denies it — printing the logged verdict + the process lifecycle transitions.

0.4 Acceptance Criteria

  • Broker denies 100% of requests (no grant path exists yet) — verified by test (I3).
  • IPC round-trip works for well-formed frames; 1M malformed-frame fuzz-smoke → 0 panics/OOB (I7).
  • Every verdict + lifecycle transition appears in the structured log (I10).
  • Child runs in a separate address space (verified via distinct pid + no shared memory map).

0.5 Conformance Fixtures

conformance/ipc/{frame_minimal,frame_with_fds,frame_max_len}, conformance/ipc/malformed/{len_overflow,nfds_too_many,truncated_payload,unknown_kind}, conformance/policy/deny_default (asserts empty policy ⇒ deny-all).

0.6 Pitfalls

  • Trusting frame len to size an allocation → OOM bomb; cap len ≤ MAX_FRAME before allocating (I2/I7).
  • Stream vs datagram confusion → using SOCK_STREAM loses message boundaries → re-sync attacks; SEQPACKET (ADR-007).
  • fd leak on error path → recv'd fds not closed on a rejected frame → fd exhaustion; RAII OwnedFd.
  • Implicit allow → a missing match arm defaulting to allow → escape; exhaustive match, default-deny (I3).
  • Spawning a thread not a process → shared address space → no isolation; fork+execve (ADR-016).

0.7 Performance Concerns

IPC RTT target p99 ≤ 50 µs (§4): avoid per-message heap churn (reuse buffers); SEQPACKET is one syscall pair per message. Broker decision is a table lookup (Phase 2+); the stub is O(1). Spawn cost dominated by execve + (later) sandbox install — measured in Phase 1.

0.8 Edge Cases

Zero-length payload; frame with nfds>0 but truncated ancillary; child exits before broker replies (broken pipe → Err, not panic); broker socket closed mid-recv; concurrent children sharing the broker (serialized in Phase 2).

0.9 Failure Analysis

A malformed-frame panic in the broker = a DoS of the trusted process = catastrophic → fuzz gate (I7). Blast radius of a child crash here: just that child (broker survives, I11). Detection: ipc_grant_on_malformed counter must stay 0; broker_panic alerts immediately. Postmortem: the frame dump + the validation-stage that failed.

0.10 Operational Notes

Metrics: ipc_rtt_us, ipc_malformed, verdict{allow,deny,kill}, child_spawned, lifecycle_transition. Tracing: span per request (recv→validate→decide→reply). The broker is the audit point — every decision is a structured log line keyed by (caller SiteInstance, op, verdict, reason) (I10). Deployment: the broker is the long-lived parent; children are ephemeral.

Phase 1 — OS Sandbox: seccomp-bpf Allowlist + User Namespaces + Landlock

1.1 Objectives

Build the OS cage (bsm-sandbox): a per-role seccomp-bpf syscall allowlist (I8), user namespaces for uid/pid/net/ipc isolation, and Landlock filesystem restriction. After this phase a renderer child can compute but cannot touch the filesystem, network, or other processes directly. Constraint: sandbox install is the irrevocable point of no return (§8.5); unsafe is confined here (ADR-006).

1.2 Detailed Implementation Steps

  • bsm-sandbox::seccomp: build a SeccompProgram via seccompiler (ADR-003) from the role's allowlist; default action KILL_PROCESS (or ERRNO(EPERM) for graceful syscalls); set no_new_privs first (required before installing a filter unprivileged). (I8, ADR-003; Drewry/Kernel seccomp-bpf docs)
  • bsm-sandbox::namespaces: clone(CLONE_NEWUSER|CLONE_NEWPID|CLONE_NEWNET|CLONE_NEWIPC) (ADR-005); write uid_map/gid_map; the child sees an empty network namespace (no sockets) + its own pid namespace. (P2, ADR-005)
  • bsm-sandbox::landlock: build a LandlockRuleset (ADR-004) granting only the paths the role's policy allows (renderer: none / a temp dir at most); enforce before execve-to-payload. (I8, ADR-004; Salaün Landlock LSM docs)
  • bsm-sandbox::os + os_linux: implement trait Os::install_sandbox ordering: no_new_privs → namespaces → Landlock → seccomp (filter last so setup syscalls aren't blocked).
  • bsm-policy::compile: lower the §8.2 grammar → SandboxPolicy { syscall_allow, fs_rules, namespaces } per role; renderer = the tightest profile.
  • Wire into bsm-process::spawn: child calls install_sandbox immediately after fork, before running any untrusted code. (P1, I1)

1.3 Deliverable

sbx-browser spawn --role renderer launches a child that is sandboxed: an attempt to open("/etc/passwd") or socket() from the child fails (SIGSYS/EPERM), proving the cage (I8).

1.4 Acceptance Criteria

  • Renderer allowlist ≤ ~150 syscalls (§4); every non-allowlisted syscall denied (verified by the escape/syscall_escape battery, ADR-021).
  • 0 direct file/net syscalls succeed from the renderer (I1/I8).
  • Sandbox install adds ≤ 50 ms to spawn (§4).
  • Miri-clean on safe code; ASAN-clean on the unsafe seam (ADR-026).

1.5 Conformance Fixtures

conformance/sandbox/{renderer_allowlist,network_allowlist,gpu_allowlist} (expected allow/deny per syscall), conformance/sandbox/landlock/{no_fs,temp_only}, escape/syscall_escape.rs (attempts open/socket/ptrace/execve/clone — all must fail).

1.6 Pitfalls

  • Filter-ordering bug: installing seccomp before the namespace/Landlock setup syscalls → setup itself is killed; install seccomp last (§1.2 order).
  • Forgetting no_new_privs → unprivileged seccomp install fails (EPERM); set it first.
  • Allowlisting too much (open, socket, ptrace) → defeats the cage; minimal set, justified per syscall (principle 9).
  • clone/fork flag mistakes → child shares a namespace it shouldn't; explicit flags (ADR-005).
  • Architecture-specific syscall numbers → an x86-64 allowlist on ARM denies the wrong calls; arch-aware tables (Garfinkel-style interposition pitfall).
  • vfork/clone allowed → renderer spawns helpers → broadens surface; deny process-creation syscalls.

1.7 Performance Concerns

seccomp-bpf adds a per-syscall BPF evaluation (~tens of ns) — negligible vs the syscall itself; keep the filter program short (linear scan or a bsearch jump table over syscall nr). Namespace + Landlock setup is one-time at spawn (~ms). The cage adds zero steady-state cost to in-process compute (the renderer's hot path never traps).

1.8 Edge Cases

A syscall the renderer legitimately needs but isn't allowlisted (→ add with justification, or broker it); clone3 vs clone (filter both); seccomp KILL vs ERRNO choice (KILL for clearly-hostile, ERRNO where libc must degrade gracefully); userns disabled by the host kernel (/proc/sys/kernel/unprivileged_userns_clone=0) → fail-closed + clear error (scripts/check-userns.sh).

1.9 Failure Analysis

A too-loose allowlist = a latent escape (the renderer can do something it shouldn't) → the escape battery (ADR-021) gates it; blast radius = full sandbox bypass if missed. A too-tight allowlist = the renderer crashes on a needed syscall → detected by the syscall-trace tool + the SIGSYS log. Postmortem: the seccomp filter dump + the trapped syscall nr/args.

1.10 Operational Notes

Metrics: syscall_denied{nr}, sandbox_install_ms, userns_unavailable, landlock_unavailable. The SIGSYS handler logs the offending syscall (debugging aid). Deployment: requires a kernel with seccomp + userns + Landlock (≥5.13); degrade-with-warning on older kernels (Landlock optional, seccomp mandatory). Rollback: a syscall allowlist is data (policy) — tightening/loosening is a policy change, not a code change.

Phase 2 — Broker + Deny-by-Default Capability Brokering

2.1 Objectives

Turn the broker stub into a real deny-by-default policy engine (bsm-broker) that performs privileged operations on behalf of sandboxed children after a policy check: file-open, net-connect, GPU-submit. Authority is minted as a Capability and handed back; the renderer never gains ambient authority (I12, principle 3/4). Brokered ops are TOCTOU-safe (§8.8, I9).

2.2 Detailed Implementation Steps

  • bsm-broker::engine: handle(caller, req) — validate (Phase 0 guard) → canonicalize args (I9) → policy lookup (bsm-policy::grants) → if allowed, perform the op + mint a Capability; else Deny (I3). (I3, I9, P10; Saltzer & Schroeder 1975 complete mediation)
  • bsm-broker::captable: per-process CapTable; mint/revoke/lookup (§11); ids are opaque server-side keys (I6).
  • bsm-broker::brokered_ops:
    • FileOpen: the broker (or the browser UI for user-picked files) opens the path itself, canonicalizing + checking against the Landlock/grant subtree (I9), then passes the fd back (SCM_RIGHTS) — the renderer never names a path it opens (§8.8). (I9, ADR-004; Garfinkel 2003 TOCTOU pitfalls)
    • NetConnect/NetFetch: handed to the network process; initiator is the broker-tracked SiteInstance, never the renderer's claim (I2). (I2, P5)
    • GpuSubmit: validate the command-buffer reference against a capability.
  • bsm-broker::audit: every op + verdict logged with (caller, op, args-canonical, verdict, reason) (I10). (I10, P11; ADR-017)

2.3 Deliverable

sbx-browser broker-demo: a sandboxed renderer requests a brokered file-read it is allowed (gets an fd) and one it is not (gets Deny); both decisions are logged and deterministic.

2.4 Acceptance Criteria

  • Deny-by-default: any op without an explicit grant → Deny (I3); policy-fuzz finds no implicit-allow path.
  • Broker decision latency p99 ≤ 100 µs (§4) — measured (criterion).
  • Brokered file-open is TOCTOU-safe: a symlink/rename race cannot redirect the opened fd (I9) — verified by escape/path_traversal.
  • Every privileged op goes through the broker (no unmediated path, I12) — verified by a surface audit.

2.5 Conformance Fixtures

conformance/capability/{mint_file_read,deny_no_grant,revoke_epoch,subset_rights}, conformance/policy/{grant_file_under,deny_outside_subtree}, escape/path_traversal.rs (../, symlink swap, absolute escape — all Deny).

2.6 Pitfalls

  • Check-then-open by path (renderer supplies path, broker stats then opens) → classic TOCTOU; instead the broker opens once + validates the resulting fd/inode (I9, §8.8).
  • Trusting requested_rights → renderer asks for more than granted; the broker mints only the intersection with policy (subset, principle 4).
  • Canonicalization after the check → traversal slips through; canonicalize before the policy decision (I9, principle 10).
  • Capability id guessable/sequential → renderer forges one; use an unguessable nonce + server-side table (I6).
  • Forgetting to revoke on tab close → capability outlives its need; revoke + epoch-bump on lifecycle end.

2.7 Performance Concerns

The broker is the central authority and must stay fast (§4 p99 ≤ 100 µs). Policy lookup is a hash/trie keyed by (role, cap-kind, constraint) — O(1)/O(log n); avoid per-request allocation; canonicalization (realpath) is the costliest step → cache canonical prefixes for the grant subtree. The broker is single-writer per child; cross-child contention handled by sharding the broker's work queue (see Scalability Analysis).

2.8 Edge Cases

A grant whose path no longer exists (open fails → Deny + diag, not a crash); a capability used after revoke (epoch mismatch → Deny); a renderer flooding the broker with requests (rate-limit + backpressure → the broker never blocks indefinitely); concurrent requests from one child (serialized per child for determinism, I10).

2.9 Failure Analysis

A broker bug that grants when it should deny = a sandbox escape (the worst outcome) → policy-fuzz + the escape battery gate it; blast radius = the granted resource (e.g., a file the renderer shouldn't read). Detection: implicit_allow counter (must be 0); an unexpected Allow in the audit log. Postmortem: the decision trace (which grant matched, the canonicalized args).

2.10 Operational Notes

Metrics: broker_decision_us, verdict{allow,deny,kill}, cap_minted, cap_revoked, implicit_allow(0), toctou_blocked. Every allow/deny is a logged pure function (I10) — the audit log is the security record. Deployment: the broker config (policy) is hot-reloadable but fail-closed (a bad policy doesn't apply; the old one stays). Rollback: policy is versioned (ADR-029).

Phase 3 — Capability-Passing Typed IPC (Handle/fd Passing, No Ambient Authority)

3.1 Objectives

Complete the capability-passing IPC (bsm-ipc): typed interfaces bound by capability, handle/fd transfer via SCM_RIGHTS, and the guarantee that a renderer has no ambient authority — it can only act through capabilities it was explicitly handed (I1, principle 4). This is the Mojo-style contract: messages are typed, channels are capabilities, there is no global namespace a renderer can reach.

3.2 Detailed Implementation Steps

  • bsm-ipc::fdpass: send/recv OwnedFd arrays via SCM_RIGHTS (ADR-008); cap nfds ≤ MAX_FDS; RAII close. (I6, ADR-008; Watson et al. Capsicum 2010)
  • bsm-ipc::interface: an Interface is a (channel, message-set) bound only by presenting a Capability (bind_interface, §11); no ambient channels — a renderer starts with exactly one capability (its broker channel) and can only obtain more by being granted them (principle 4). (P4, I6; Miller Robust Composition 2006)
  • Capability delegation: a process can pass a capability it holds to another with subset-only rights (it cannot widen rights, principle 4); the broker records the delegation. (P4, ADR-010)
  • bsm-ipc::validate: enforce that a received CapHandle resolves in the receiver's CapTable (else Deny, I6); reject handles referencing capabilities the sender never held.
  • Tie the renderer's entire authority to its capability set: remove any path that derives authority from identity/env (audit for ambient authority, I1). (I1, P2)

3.3 Deliverable

sbx-browser cap-demo: the broker hands a renderer a single file-read capability (an fd); the renderer uses it; an attempt to use a capability it was never given (forged handle) is rejected (I6). The renderer's authority = exactly its capability set, nothing more (I1).

3.4 Acceptance Criteria

  • Zero ambient authority: an audit (escape/forged_origin-style + a capability audit) finds no env/identity-derived authority in the renderer (I1).
  • A forged/stale CapHandle → reject, never resolve (I6) — escape/handle_forge.
  • Subset-only delegation: a renderer cannot widen rights on a capability it re-passes (principle 4) — tested.
  • fd passing works + leaks no fds (RAII verified under ASAN).

3.5 Conformance Fixtures

conformance/capability/{bind_interface,delegate_subset,forge_handle_reject,stale_epoch_reject}, conformance/ipc/{fd_pass_roundtrip,nfds_cap}, escape/handle_forge.rs.

3.6 Pitfalls

  • Ambient channel (a renderer can connect to any service by name) → defeats capabilities; channels are only obtained via a held capability (principle 4).
  • Rights widening on delegation → privilege escalation; intersect rights on every transfer (subset-only).
  • fd table confusion → passing the wrong fd (off-by-one in the SCM_RIGHTS array); index carefully.
  • Handle resolves in the wrong CapTable → cross-process authority confusion; resolve in the receiver's table only (I6).
  • Capability outliving the backing object → use-after-free of an fd; epoch + revoke on close.

3.7 Performance Concerns

SCM_RIGHTS adds a kernel fd-dup per passed handle — bounded by MAX_FDS. Interface binding is a one-time capability check, not per-message. Steady-state messaging is the Phase-0 RTT (p99 ≤ 50 µs) — capability resolution is an O(1) table lookup. Avoid re-validating a bound interface on every message (validate at bind, then trust the bound channel — but still bound-check payloads, I7).

3.8 Edge Cases

Passing 0 fds with nfds=0; passing a capability whose backing fd was already closed (revoke caught it → Deny); a process delegating a capability it doesn't hold (reject); receiving more fds than nfds claims (kernel/ancillary mismatch → reject the frame, I7).

3.9 Failure Analysis

An ambient-authority leak (the renderer can reach a resource without a capability) = a containment failure → the capability audit + escape battery gate it; blast radius = whatever the ambient authority reached. A handle-forge that resolves = an escape → forged_handle counter must be 0. Postmortem: the CapTable dump + the handle's claimed vs actual table entry.

3.10 Operational Notes

Metrics: forged_handle(0), cap_delegated, nfds_passed, interface_bound, ambient_auth_found(0). The CapTable is inspectable via tools/cap-inspect (debugging: what does this renderer actually hold?). Deployment: the capability model is the core invariant — any new IPC surface must be capability-gated (CONTRIBUTING rule). Compatibility: new message kinds are additive (ADR-029); a capability schema change is SemVer-major.

Phase 4 — Site Isolation: Process-per-SiteInstance Allocation

4.1 Objectives

Make site isolation real (bsm-isolation): allocate one renderer process per SiteInstance, place cross-site iframes in their own process (OOPIFs), and re-evaluate on every navigation commit so cross-origin data is never co-resident (I4, principle 6 — the Spectre defense). This is the 2018 response to Spectre: address-space separation by Site.

4.2 Detailed Implementation Steps

  • bsm-isolation::browsing_instance: model BrowsingInstance (windows that can script each other); SiteInstance = (Site, BrowsingInstanceId) (§8.1). (I4, ADR-011)
  • bsm-isolation::allocator: process_for(SiteInstance) -> ProcessId — reuse the existing process for the same SiteInstance, else spawn a new sandboxed renderer (Phase 1) for a new Site (I4). (I4, P6; Reis et al. Site Isolation 2019)
  • bsm-isolation::oopif: a cross-site <iframe> ⇒ an out-of-process iframe ⇒ a separate process (§8.9); the parent + child frames communicate only via mediated IPC (SOP across the boundary, Phase 5).
  • bsm-isolation::commit: on_commit(frame, dest_origin) — if a navigation would put a cross-site document in a single-site process, swap the process before committing (I4); never commit cross-site content into the wrong process. (I4, ADR-013)
  • Integrate with bsm-net: the network process tags responses with their origin so the browser can route them to the correct (right-Site) renderer only (Phase 6). (I5, P6)

4.3 Deliverable

sbx-browser isolation-demo: load a top-level site that embeds a cross-site iframe; observe two distinct renderer processes (one per Site); a navigation to a different Site triggers a process swap (logged).

4.4 Acceptance Criteria

  • Every SiteInstance is in its own process; cross-site iframe ⇒ separate process (I4) — conformance/isolation.
  • A cross-site navigation commit swaps processes (no cross-site co-residency) — verified by escape/coresidency.
  • A co-residency check (cross_site_coresident counter) stays 0 (I4).
  • Process allocation is deterministic given the same navigation sequence (I10).

4.5 Conformance Fixtures

conformance/isolation/{same_site_reuse,cross_site_oopif,cross_site_navigation_swap,opaque_origin_isolated,subdomain_same_site}, escape/coresidency.rs (attempts to force two Sites into one process — must fail).

4.6 Pitfalls

  • Using Origin instead of Site for isolation → over-fragmentation (every subdomain its own process) or under-isolation; Site = eTLD+1 (ADR-011, §8.1).
  • Committing before the swap → a window where cross-site content is briefly co-resident; swap before commit (I4).
  • about:blank/data:/blob: origin inheritance → wrong SiteInstance; opaque origins get their own isolated instance (§8.1).
  • Process reuse across BrowsingInstances → scripting boundary confusion; SiteInstance includes the BrowsingInstance id.
  • Redirect during navigation changes the destination Site mid-flight → re-evaluate on the final origin at commit.

4.7 Performance Concerns

Process-per-SiteInstance increases process count (memory + spawn cost) — the known site-isolation tradeoff. Mitigations: a process limit with consolidation of same-site frames; reuse a warm process for a returning Site; the spawn cost (≤ 50 ms, §4) is amortized by reuse. Memory per renderer is the dominant scaling cost (see Scalability Analysis). The allocator lookup is O(1) (a map keyed by SiteInstance).

4.8 Edge Cases

Many cross-site iframes (process explosion → consolidate or cap); a site that opens a popup to another site (COOP severs → new BrowsingInstance, Phase 6); rapid back/forward navigation (process reuse from a cache); a sandboxed iframe (opaque origin → its own isolated process); same Site, different BrowsingInstance (different processes — cannot script each other).

4.9 Failure Analysis

A co-residency bug (two Sites in one process) = the Spectre defense is defeated for those Sites → the co-residency check + escape battery gate it (the highest-severity correctness failure here). Blast radius: cross-origin data theft via a speculative side channel within the shared process. Detection: cross_site_coresident (must be 0). Postmortem: the SiteInstance→Process map + the navigation/commit log.

4.10 Operational Notes

Metrics: renderer_processes, oopif_count, process_swaps, cross_site_coresident(0), process_reuse_rate. The SiteInstance→Process map is inspectable (tools + the audit log). Deployment: site isolation is the memory-vs-security tradeoff; the process limit + consolidation policy is tunable. This is the mechanism that makes the §6-principle-6 claim true.

Phase 5 — Same-Origin Policy Enforcement at the Process Boundary

5.1 Objectives

Enforce the Same-Origin Policy (bsm-origin) across the process boundary: DOM/script/storage access between frames is allowed only for same-origin (I5), and — crucially — the check lives on the trusted side, never trusting the renderer's origin claim (I2, principle 5). With OOPIFs (Phase 4), cross-origin DOM access is now an IPC that the browser mediates.

5.2 Detailed Implementation Steps

  • bsm-origin::origin: RFC 6454 parse + canonicalize (scheme/host/port), opaque-origin handling (§8.1, I9). (I9, ADR-011; Barth RFC 6454)
  • bsm-origin::psl: Public Suffix List → registrable domain (eTLD+1) for Site (scripts/gen-psl.sh bakes the PSL).
  • bsm-origin::sop: same_origin/same_site decision (table §8.6); used for every cross-frame access decision.
  • Cross-process DOM access: a renderer's request to touch another frame's DOM becomes an IPC to the browser, which checks SOP using the broker-tracked origins of both frames (not renderer-supplied, I2) → allow only if same-origin (I5). (I2, I5; Barth Jackson Reis 2008)
  • Storage partitioning: localStorage/cookies/IndexedDB keyed by origin (or partitioned by top-level site) — a renderer accesses only its origin's storage (brokered, I12). (I12, P2)
  • PostMessage: allowed cross-origin but the receiver checks event.origin (the browser stamps the true sender origin, I2). (I2, P5)

5.3 Deliverable

sbx-browser sop-demo: two frames (same-origin and cross-origin); same-origin DOM access succeeds, cross-origin is denied; the denial uses the browser-tracked origin, not the renderer's claim (a forged claim doesn't help).

5.4 Acceptance Criteria

  • Same-origin access allowed, cross-origin denied (I5) — conformance/sop vectors.
  • A renderer forging its origin gains nothing (the browser uses its own tracked origin, I2) — escape/forged_origin.
  • Origin canonicalization handles tricky inputs (trailing dots, default ports, IDN, uppercase host) deterministically (I9).
  • Storage access is origin-partitioned (a renderer reads only its origin's storage).

5.5 Conformance Fixtures

conformance/sop/{same_origin_allow,cross_origin_deny,default_port_equiv,idn_host,opaque_deny,postmessage_origin}, escape/forged_origin.rs (renderer lies about its origin — denial unaffected).

5.6 Pitfalls

  • Trusting event.origin/the renderer's claimed origin → UXSS; the browser stamps the true origin (I2, principle 5).
  • Port/scheme omission in comparison (http vs https, default port) → origin confusion; canonicalize fully (I9).
  • IDN/punycode mismatch (xn-- vs unicode) → spoofed same-origin; canonicalize to one form.
  • Treating null/opaque origins as equal → cross-origin leak; opaque ≠ opaque (each unique, §8.1).
  • Subdomain confusion (a.example vs example) → wrong same-origin/same-site result; tuple for origin, eTLD+1 for site.

5.7 Performance Concerns

SOP checks are pure tuple comparisons (ns-scale) but happen per cross-frame access — with OOPIFs they become IPCs (µs-scale). Mitigate by caching the allow/deny per (frame-pair) when origins are stable. PSL lookup (eTLD+1) is a trie lookup (O(labels)); the PSL is loaded once. Origin parsing/canonicalization is the costlier step → parse once per document, store the canonical origin.

5.8 Edge Cases

file:// origins (each file its own opaque-ish origin); blob:/data: URL origin inheritance; sandboxed iframe (opaque origin, all cross-origin); document.domain legacy relaxation (deprecated — reject or gate); a navigation that changes a frame's origin (re-evaluate); WebSocket/fetch origin (initiator, Phase 6).

5.9 Failure Analysis

A SOP bypass = cross-origin data theft / UXSS = the canonical web vulnerability → conformance vectors + the forged-origin escape gate it. Blast radius: one origin reads another's DOM/storage. Detection: renderer_trusted_value (must be 0 — we never trust a renderer origin claim); an unexpected cross-origin allow in the audit. Postmortem: the two frames' browser-tracked origins + the decision trace.

5.10 Operational Notes

Metrics: sop_allow, sop_deny, renderer_trusted_value(0), origin_parse_us, opaque_origins. The origin of every frame is browser-tracked state (the security record). tools/origin-explain shows why two origins are/aren't same-origin (debugging). Deployment: the PSL must be kept current (an out-of-date PSL → wrong Site boundaries); ship + auto-update it. Compatibility: SOP semantics are web-platform-fixed (not ours to version).

Phase 6 — CORP / CORB-ORB / COOP / COEP + Network-Process Origin Checks

6.1 Objectives

Enforce the cross-origin resource policies in the network process (bsm-net): CORP + ORB gate which response bytes ever reach a renderer (I5); COOP isolates browsing contexts; COEP enables cross-origin isolation (the Spectre-safe SharedArrayBuffer gate, §8.6); Sec-Fetch metadata gives the server request context. Cross-origin bytes never enter a renderer that shouldn't see them (I5, principle 6).

6.2 Detailed Implementation Steps

  • bsm-net::corp: parse Cross-Origin-Resource-Policy; gate response delivery vs the requester relationship (table §8.6, I5). (I5, ADR-012; West Fetch Metadata)
  • bsm-net::orb: Opaque Response Blocking (ADR-012) — for cross-origin no-cors responses, block ORB-eligible MIME types (HTML/JSON/XML) before they reach the renderer; allow opaque-safe types (image/media). The CORB successor. (I5, ADR-012)
  • bsm-net::cors: the CORS protocol (preflight, Access-Control-Allow-Origin) for explicit cross-origin reads.
  • bsm-net::coop: Cross-Origin-Opener-Policy — sever opener relationships across origins, forcing a new BrowsingInstance (new process, ties to Phase 4). (I4, ADR-013; COOP/COEP cross-origin isolation spec)
  • bsm-net::coep: Cross-Origin-Embedder-Policy — require CORP/CORS on all subresources; combined with COOP same-origin ⇒ CrossOriginIsolation ⇒ permit SharedArrayBuffer + high-res timers (§8.6).
  • bsm-net::secfetch: stamp Sec-Fetch-Site/Mode/Dest/User on requests (the browser sets these; the server trusts them because the renderer can't forge them — set on the trusted side, I2).
  • The network process performs the fetch with the broker-tracked initiator origin (I2), applies the checks, and delivers bytes only to the correct-Site renderer (ties to Phase 4 routing). (I2, I5; Barth RFC 6454)

6.3 Deliverable

sbx-browser corp-demo: a cross-origin no-cors fetch of a CORP-same-origin resource is blocked at the network process (bytes never reach the renderer, §8.7); a COOP+COEP page becomes cross-origin-isolated (crossOriginIsolated true).

6.4 Acceptance Criteria

  • CORP/ORB block cross-origin bytes per table §8.6 (I5) — conformance/corp + conformance/orb.
  • Cross-origin response bytes never enter the wrong renderer (I5) — verified end-to-end (the network process drops them).
  • COOP severs cross-origin openers (new BrowsingInstance); COEP require-corp + COOP same-origin ⇒ isolation.
  • Sec-Fetch headers set on the trusted side; a renderer cannot forge them (I2).

6.5 Conformance Fixtures

conformance/corp/{same_origin_block,cross_origin_allow,same_site_mixed}, conformance/orb/{html_blocked,json_blocked,image_allowed,nosniff}, conformance/coop/{sever_opener,allow_popups}, conformance/coep/{require_corp_block,isolation_enabled}, conformance/cors/{preflight,allow_origin}.

6.6 Pitfalls

  • MIME sniffing to bypass ORB → honor X-Content-Type-Options: nosniff; ORB sniffs conservatively (block on doubt, principle 7).
  • Applying CORP after bytes reach the renderer → too late (the leak already happened); gate in the network process before delivery (I5).
  • CORS credentials with wildcard * → credential leak; reject * + credentials.
  • COOP/COEP interaction subtlety → isolation requires both (same-origin COOP AND require-corp COEP); one alone doesn't isolate (§8.6).
  • Trusting a renderer-supplied Origin/Sec-Fetch → spoofed context; the browser sets these (I2, principle 5).
  • Redirect chains changing the response origin → re-evaluate CORP/ORB on the final response.

6.7 Performance Concerns

CORP/ORB checks are header parses + a table lookup (µs-scale) per response — on the fetch path, not the render hot path. ORB sniffing reads a small prefix of the body (bounded). The network process is shared across renderers → its decision throughput matters at fan-out (see Scalability Analysis); the checks are O(1) per response. COOP/COEP are per-document, evaluated once at load.

6.8 Edge Cases

A response with no CORP header (ORB decides by type); a same-site CORP across subdomains; a cross-origin redirect to a same-origin resource; range requests (partial content) under ORB; opaque responses cached and re-served; a COEP credentialless subresource (sent without credentials).

6.9 Failure Analysis

A CORP/ORB bypass = cross-origin data theft (the renderer reads bytes it shouldn't) → conformance vectors gate it; blast radius = the leaked cross-origin response. A COOP/COEP gap that enables SharedArrayBuffer without true isolation = a Spectre exposure → the isolation check must require both policies. Detection: cross_origin_leak (must be 0). Postmortem: the response's CORP/MIME + the requester relationship + the decision.

6.10 Operational Notes

Metrics: corp_block, orb_block, cors_preflight, coop_sever, coep_block, cross_origin_isolated, cross_origin_leak(0). The network process logs every cross-origin gating decision (the leak-prevention record, I10). Deployment: these policies are web-platform-defined; we implement the spec faithfully. tools/origin-explain extends to "why was this response blocked?" Compatibility: spec-fixed semantics.

Phase 7 — Renderer-Compromise Containment + Escape Red-Team Tests

7.1 Objectives

Validate the central thesis end-to-end: a fully-compromised renderer reaches nothing it shouldn't (principle 1). Build the escape/ red-team battery — a suite of attacks (syscall escape, path traversal, handle forge, forged origin, co-residency, IPC abuse) that must fail — and an attacker-controlled stub renderer that exercises them. This phase certifies containment.

7.2 Detailed Implementation Steps

  • sbx-browser::stub_renderer: a deliberately-"compromised" renderer that, on command, attempts every escape: raw syscalls (open/socket/ptrace/execve), forged IPC frames, forged origins, forged capability handles, attempts to read another Site's memory. (P1, P8)
  • escape/syscall_escape: every denied syscall → SIGSYS/EPERM (I8). (I8, ADR-021)
  • escape/path_traversal: every traversal/symlink trick → Deny (I9).
  • escape/handle_forge: every forged/stale CapHandle → reject (I6). (I6, ADR-010)
  • escape/forged_origin: every origin lie → ignored (broker-tracked origin used, I2).
  • escape/coresidency: every attempt to co-locate two Sites → process swap/separation (I4).
  • escape/ipc_abuse: malformed/oversized/flood frames → Deny/drop/quarantine, never grant (I7).
  • Enumerate the reachable surface: precisely what a compromised renderer can do (compute, use its granted capabilities, send IPC the broker mediates) vs cannot (everything else) — documented + tested (principle 9). (P9, I12; Saltzer & Schroeder 1975 complete mediation)

7.3 Deliverable

make escape-tests runs the full battery; every attack fails (the cage holds). A "compromised renderer reachability" report enumerates exactly what authority a compromised renderer has (its capabilities) and proves it reaches nothing else.

7.4 Acceptance Criteria

  • 100% of escape-battery attacks fail (no escape) — the release gate (ADR-021).
  • The reachable-surface report matches the audited broker surface (no unmediated authority, I12).
  • A compromised renderer reaches: only its own Site's data + brokered ops it was granted; nothing else (§4 containment).
  • The battery runs in CI on every merge (escape.yml) — a regression blocks merge.

7.5 Conformance Fixtures

escape/{syscall_escape,path_traversal,handle_forge,forged_origin,coresidency,ipc_abuse}.rs; conformance/containment/reachable_surface (the enumerated authority of a compromised renderer).

7.6 Pitfalls

  • A new IPC surface added without a capability gate → a new escape; CONTRIBUTING requires capability-gating + an escape test for every new broker op (principle 9).
  • An escape test that passes for the wrong reason (the attack didn't actually execute) → false confidence; assert the attack ran and was denied.
  • Library code in the renderer with ambient authority (a logging lib that opens a file) → an escape; audit the renderer's transitive authority (I1).
  • A syscall added to the allowlist for convenience → a hole; every allowlist entry needs a justification + a re-run of the battery.
  • Time-of-check races in the broker re-introduced → re-run TOCTOU tests.

7.7 Performance Concerns

The escape battery is a test suite (off the hot path) but must run fast enough for CI (target ≤ a few minutes); parallelize independent attacks. The containment guarantees themselves add no steady-state cost — they're structural (the sandbox + capabilities + isolation already built). The reachability analysis is a one-time audit per surface change.

7.8 Edge Cases

A renderer that crashes during an escape attempt (still contained, I11); an escape that combines vectors (forged origin + handle forge); a partial compromise (only some renderer state attacker-controlled — still assume full, principle 1); a new OS/kernel that changes syscall behavior (re-run the battery per platform).

7.9 Failure Analysis

A passing escape (an attack that succeeds) = a sandbox escape = the project's defining failure → blocks release, triggers a security incident (the escape-suspected runbook). Blast radius depends on what escaped (file access, cross-origin data, host compromise). Detection: any escape-battery failure. Postmortem: the successful attack's path (which layer failed — syscall filter, broker, capability, isolation, or origin check) + a new regression test.

7.10 Operational Notes

Metrics: escape_attempts, escape_successes(0 — hard SLO), per-vector counters. The escape battery is the primary security SLO (analogous to the parser's fuzz SLO in #333). Deployment: the reachability report is part of the security documentation (SECURITY.md). This phase's artifact is the evidence that the thesis (principle 1) holds. Incident response: any real escape is a P0.

The policy + capability + isolation layers (Phases 2–6) are OS-agnostic; only bsm-sandbox's cage implementation differs (principle: portability without leaking platform-isms).

8.2 Detailed Implementation Steps

  • bsm-sandbox::os_windows: a renderer runs in a job object (limits + kill-on-close), with a restricted/lowbox token (AppContainer) stripping privileges + access; SetProcessMitigationPolicy (DEP/ASLR/CFG/dynamic-code-disable); the broker performs privileged ops the lowbox token can't (the Windows analog of the Linux broker).   • bsm-sandbox::os_macos: a Seatbelt sandbox profile (deny-by-default, allow only the needed operations) applied via sandbox_init/the modern API; the broker brokers what the profile denies. (I8, ADR-015)

8.3 Deliverable

sbx-browser spawn --role renderer produces an equivalently-sandboxed child on Windows + macOS: the same escape battery (Phase 7) runs + passes per platform.

8.4 Acceptance Criteria

  • The escape battery passes on Linux, Windows, macOS (per-platform CI) — the cage holds everywhere (I8).
  • The policy → platform-primitive mapping is complete (every Linux guarantee has a Windows + macOS analog) — Appendix D.
  • IPC + capability + isolation layers are unchanged across platforms (OS-isms confined to bsm-sandbox, ADR-006/015).
  • Spawn latency per platform within target (≤ 50 ms + platform overhead).

8.5 Conformance Fixtures

conformance/sandbox/{windows_lowbox,windows_job,macos_seatbelt} (per-platform allow/deny expectations), the cross-platform escape battery, docs/security/sandbox-os.md (the mapping).

8.6 Pitfalls

  • A platform with no eTLD-precise equivalent → use the closest primitive + document the gap (Appendix D).
  • Windows token/job subtleties (handle inheritance, broker handle duplication) → a leaked handle = an escape; explicit handle hygiene.
  • macOS Seatbelt profile gaps (a too-permissive allow) → re-run the battery; Seatbelt profiles are easy to over-grant.
  • Mach port / named-pipe capability semantics differ from Unix fd passing → preserve the capability model (handle, not name, I6).
  • Platform-specific syscalls leaking into policy → keep policy abstract; lower per platform in bsm-sandbox.

8.7 Performance Concerns

Platform cage setup costs differ (Windows token/job creation, macOS profile compile) — measure per platform; all are one-time at spawn. IPC transport differs (named pipes / Mach ports) — re-measure RTT per platform vs the §4 target. The OS seam adds no steady-state cost (structural cage).

8.8 Edge Cases

An older Windows without AppContainer (fall back to a restricted token + job); macOS App Sandbox vs the lower-level Seatbelt; platform kernel versions changing sandbox behavior; a platform where userns/Landlock has no analog (use the closest, document); cross-platform path canonicalization differences (I9 per platform).

8.9 Failure Analysis

A platform-specific escape (the cage is weaker on one OS) = a containment gap on that platform → per-platform escape battery gates it; blast radius = that platform's users. Detection: a per-platform escape-battery failure. Postmortem: which platform primitive was insufficient + the mapping doc update.

8.10 Operational Notes

Metrics: per-platform sandbox_install_ms, escape_successes(0 each). Deployment: each platform has its own kernel/OS requirements (Linux ≥5.13 for Landlock; Windows 8+ for AppContainer; macOS Seatbelt). docs/security/sandbox-os.md is the per-platform operator guide. Compatibility: the trust boundary + policy are platform-stable; only the cage differs.

Phase 9 — Crash Isolation + Process Lifecycle Security

9.1 Objectives

Guarantee that a renderer crash/kill is contained: it affects only its tab, never the broker or sibling renderers (I11, principle 12), and the lifecycle (spawn→quarantine→kill→respawn) is itself secure (no use-after-free of capabilities/channels, no resurrection of authority). Availability under a hostile/crashing renderer.

9.2 Detailed Implementation Steps

  • bsm-process::lifecycle: on a child crash/exit, the broker detects it (SIGCHLD / handle signal), revokes all its capabilities (epoch-bump, I6), tears down its channels + CapTable, and frees its SiteInstance→Process slot. (I6, I11; P12)
  • Quarantine path (§8.5): on a policy violation / malformed-IPC flood, the broker stops honoring the child's requests + kills it (fail-closed, principle 7) — never grants during teardown. (P7, I3)
  • Respawn: a killed renderer's tab respawns a fresh sandboxed process (Phase 1) with no inherited authority (a new CapTable) — the crash doesn't leak the old process's capabilities. (I1, P2)
  • The broker is hardened against a child's death mid-request (a half-processed request is dropped, not partially granted, I7); broken-pipe → clean teardown, not a broker crash.
  • Resource accounting: per-child fd/memory/CPU budgets so one renderer can't exhaust the broker (DoS containment). (I11, P12)

9.3 Deliverable

sbx-browser crash-demo: kill a renderer mid-request; the broker survives, siblings are unaffected, the tab respawns fresh; the dead renderer's capabilities are all revoked (no leak).

9.4 Acceptance Criteria

  • A crashed/killed renderer never takes down the broker or siblings (I11) — conformance crash-injection + escape/ipc_abuse flood.
  • On crash, all of the child's capabilities are revoked (no stale authority survives, I6).
  • A half-processed request at crash time is dropped, never partially granted (I7).
  • Respawned renderers start with zero inherited authority (I1).

9.5 Conformance Fixtures

conformance/lifecycle/{crash_mid_request,kill_on_violation,respawn_fresh_authority,sibling_unaffected}, conformance/lifecycle/{cap_revoked_on_death,broker_survives_flood}.

9.6 Pitfalls

  • Capability survives the process (the fd/handle not revoked on death) → a respawned/other process inherits authority; revoke + epoch-bump on every teardown (I6).
  • Broker blocks on a dead child's socket → broker hang (DoS); non-blocking + timeout + broken-pipe handling.
  • A crash during capability mint leaves a dangling table entry → clean up on teardown.
  • Respawn loop (a renderer that crashes immediately) → exponential backoff + a crash-loop breaker (don't burn CPU).
  • Zombie processes (un-reaped children) → reap on SIGCHLD; PID-namespace init reaps in the cage.

9.7 Performance Concerns

Crash detection + teardown is event-driven (signal/handle), not polled — low overhead. Respawn cost = spawn cost (≤ 50 ms, §4). The broker's per-child resource accounting is O(1) bookkeeping. A crash-loop breaker prevents pathological CPU burn. The broker stays responsive to siblings during one child's teardown (per-child isolation in the work queue).

9.8 Edge Cases

A renderer killed by the OS OOM-killer (broker treats as a crash); a renderer that ignores SIGTERM (escalate to SIGKILL); simultaneous crash of many renderers (broker handles a teardown storm); a crash during sandbox install (Aborted state, §8.5); a renderer that forks before the cage (denied, Phase 1) — no orphan to reap.

9.9 Failure Analysis

A broker crash caused by a child (broker_crash_on_child) = a total availability failure (every tab dies) = the worst availability outcome → crash-injection tests gate it (I11). Blast radius of a contained crash: one tab. Detection: broker_crash_on_child (must be 0). Postmortem: the crashed child's last request + the broker's teardown log.

9.10 Operational Notes

Metrics: renderer_crashes, broker_crash_on_child(0), respawns, crash_loop_broken, caps_revoked_on_death. The crash log + the per-tab respawn are operator-visible (the renderer-crash runbook). Deployment: a crashing site degrades to a "tab crashed" page, never a browser crash. This invariant (I11) is what makes a hostile site survivable.

Phase 10 — Hardening: IPC Fuzzing, Policy Fuzzing, Seccomp Escape Tests

10.1 Objectives

Make the trusted surface unbreakable on hostile input: fuzz the IPC frame parser, the policy parser, and the origin parser (cargo fuzz, ADR-020); enforce all bounds (I2/I7); run the seccomp escape battery exhaustively (I8); Miri/ASAN the unsafe seams (ADR-026). The broker must never panic or grant on any malformed input.

10.2 Detailed Implementation Steps

  • fuzz/ipc_frame: fuzz the §8.4 frame decoder — random bytes, oversized len, bad nfds, unknown kind, truncated payload, fd-count mismatches → must always Err/Deny, never panic/OOB/grant (I7). (I7, ADR-020)
  • fuzz/policy_parse: fuzz the §8.2 grammar parser → malformed policy must fail closed (no permissive partial policy, principle 7). (P7, ADR-020)
  • fuzz/origin_parse: fuzz RFC 6454 parsing → no panic; canonical + deterministic (I9). (I9, ADR-020; Barth RFC 6454)
  • fuzz/corp_decision: fuzz header inputs to CORP/ORB → deterministic block/allow, never an accidental allow.
  • Seccomp battery: attempt every non-allowlisted syscall (table-driven) → SIGSYS/EPERM (I8); verify per-arch.
  • Miri over safe code; ASAN over bsm-sandbox's unsafe (BPF install, clone, fd ops). (ADR-026, ADR-006)
  • Bounded-work enforcement: per-child request rate caps, frame caps, capability-count caps (DoS guards).

10.3 Deliverable

Green 24h fuzz (0 crashes) on all parsers; Miri-clean safe code; ASAN-clean unsafe; the full seccomp escape battery passes.

10.4 Acceptance Criteria

  • 0 panics/OOB/overflow across ≥1e9 fuzz execs on every parser (I7).
  • Malformed policy → fail-closed (no process spawns, principle 7) — fuzz-verified.
  • Every non-allowlisted syscall denied per arch (I8) — exhaustive battery.
  • Miri no-UB; ASAN clean on the unsafe seam (ADR-026).

10.5 Conformance Fixtures

fuzz/corpus/* (seeded from conformance vectors), conformance/policy/malformed/* (fail-closed), conformance/ipc/malformed/*, conformance/sandbox/escape_battery (every denied syscall).

10.6 Pitfalls

  • Allocating from an attacker len/count (Vec::with_capacity(frame.len)) → OOM; cap before allocating (I2).
  • A panic path in the broker (an unwrap/array index on hostile input) → a DoS of the trusted process; fuzz finds it (I7).
  • unsafe creeping outside bsm-sandbox → UB risk; a grep/clippy gate (ADR-006).
  • A policy parser that accepts a partial/ambiguous policy → a permissive hole; total parse, fail-closed.
  • Seccomp filter wrong on a second architecture → a hole on that arch; per-arch battery.
  • Fuzzer not reaching deep states (binding required first) → structure-aware fuzzing / seed corpus.

10.7 Performance Concerns

Fuzzing is off the critical path (CI/nightly). Bounds checks add O(1) per frame/field — negligible vs the syscall cost. Caps prevent pathological resource use (the DoS guard). The seccomp battery is a test (not steady-state). ASAN/Miri are dev/CI-only (not shipped). Keep the broker's hostile-input path allocation-light.

10.8 Edge Cases

A frame at exactly MAX_FRAME; nfds at exactly MAX_FDS; a policy at the grammar's recursion limit; an origin with maximal label count; a capability-count at the cap; a fuzz input that's valid but adversarial (a real request that probes a boundary).

10.9 Failure Analysis

A fuzz crash in the broker/IPC parser = a potential DoS or escape of the trusted process → blocks release (the security gate, analogous to #333's fuzz SLO). Blast radius: the trusted broker (catastrophic). Detection: any fuzz crash; ipc_grant_on_malformed(0). Postmortem: the crashing input (minimized) + a regression fixture + the fix.

10.10 Operational Notes

Metrics: fuzz_crashes(0), ipc_grant_on_malformed(0), policy_parse_failclosed, syscall_escape(0), alloc_cap_hit. Fuzzing + the escape battery are the dual primary security SLOs. Deployment: hardening is continuous (nightly fuzz, per-merge escape tests). The bounded-work caps are tunable policy. Any new parser surface gets a fuzz target (CONTRIBUTING rule).

11.1 Objectives

Final certification: an extended red-team pass (creative escape attempts beyond the battery), a soak under sustained hostile + realistic load (no leaks, bounded resources, broker stays up), and a reproducible, signed release with provenance (ADR-024/025). 11.2 Detailed Implementation Steps

  • Red-team: combine vectors (forged-origin + handle-forge + IPC-flood), probe new surfaces, attempt side-channel co-residency, try TOCTOU windows, attempt capability-confusion across processes — extend escape/ with every finding (a found gap → a fix → a regression test). 11.5 Conformance Fixtures

11.6 Pitfalls

Threat Model

Core thesis (principle 1): the renderer is fully compromised — attacker code runs arbitrary instructions inside it. The trust boundary is the renderer↔broker (and renderer↔network) IPC; every value crossing it is hostile. The defense is structural: least authority + deny-by-default broker + capability IPC + OS sandbox + site isolation + cross-origin policies. A successful attack must defeat multiple layers (defense in depth, principle 8).

Trust tiers (high→low): Browser/Broker (full authority, no untrusted content) > Network process (semi-trusted: handles bytes, enforces origin policy, narrow sandbox) > GPU/Utility (role-scoped) > Renderer (untrusted, assume owned).

Posture: every security decision fails closed (deny/kill, never grant — principle 7). Documented real-world incidents (the design rationale, not invented):

  • CVE-2019-5786 + CVE-2019-0808 (March 2019). Chrome FileReader use-after-free (CVE-2019-5786): exploited in-the-wild renderer RCE chained with CVE-2019-0808, a win32k privilege-escalation sandbox escape (disclosed by Google TAG, March 2019). Demonstrates that a renderer exploit alone is insufficient — a second broker/OS privilege-escalation vuln is required to escape, validating the layered-sandbox model (P8, MM3).
  • Spectre/Meltdown (January 2018). Drove Chrome's full Site Isolation rollout for all desktop users (documented in Reis et al., USENIX Security 2019). Co-resident cross-origin data in one renderer address space is readable via speculative side channels; structural address-space separation (I4, P6) is the only robust defense (MM4).

Compatibility & Versioning

Three independently SemVer'd contracts (ADR-029, principle 11):

  • IPC wire format (IpcFrame layout + MsgKind set): additive message kinds → minor; layout/field-semantics change → major. Cross-process (broker↔child) compatibility holds within a major version — a newer broker accepts an older child's frames and vice versa within major.
  • Capability schema (CapKind/Rights/Capability): additive cap kinds / rights bits → minor; a semantics change → major. Capabilities are not persisted (process-scoped) — no on-disk migration.
  • Policy grammar (§8.2): additive grant clauses / predicates → minor; a semantics change → major. A policy file declares its schema version; an unknown version → fail-closed (principle 7).

Web-platform semantics (SOP, CORP/ORB, CORS, COOP/COEP, Origin/Site) are spec-fixed (WHATWG/W3C/RFC 6454) — we implement them faithfully; they are not ours to version, but our conformance to a given spec revision is documented. The PSL is data, updated additively (new TLDs) — kept current + shipped. The CLI/harness subcommands are stable; new ones are additive. Diagnostic/verdict codes are stable identifiers. No on-disk state ⇒ no storage-format migration.

Testing & Verification Strategy

  • Unit — per component: origin parse/canonicalize, SOP decision, CORP/ORB tables, frame encode/decode, capability mint/revoke, policy compile.
  • Property (proptest) — "any byte string → the IPC parser yields a typed result or Deny, never a panic/grant" (I7); origin canonicalization idempotence (I9); "deny-by-default: a request with no matching grant always denies" (I3).
  • Conformance — conformance/**: SOP, CORP, ORB, CORS, COOP, COEP, isolation, capability, IPC, sandbox, policy vectors with expected verdicts (the web-platform + cage spec compliance suite).
  • Escape red-team (the defining suite, ADR-021) — escape/**: every attack (syscall/path/handle/origin/co-residency/IPC) must fail; runs per-merge in CI (escape.yml); a regression = a blocked merge.
  • Fuzzing (cargo-fuzz, ADR-020) — IPC frame, policy, origin, CORP-decision parsers; 24h nightly; 0 crashes (I7).
  • Differential — origin/CORP/CORS decisions vs the web-platform-tests (WPT) corpus where applicable (the cross-origin oracle).
  • Chaos / fault injection — crash/kill renderers mid-request (I11); IPC floods; policy-reload races; OOM-killer simulation.
  • Sanitizers — Miri (UB) on safe code; ASAN on the bsm-sandbox unsafe seam (ADR-026).
  • Soak — many renderers/Sites under sustained hostile + realistic load ≥ 24h: 0 escapes, flat memory, broker uptime 100% (I11).
  • Cross-platform — the escape battery + conformance per OS (Linux/Windows/macOS, Phase 8).
  • Perf regression (criterion) — broker decision / IPC RTT / spawn vs §4.

Weighting: the escape battery + fuzzing + co-residency/crash tests dominate — the failures that matter are escapes, leaks, and trusted-process crashes, not functional bugs.

Performance Engineering

Targets (§4): broker decision p99 ≤ 100 µs, IPC RTT p99 ≤ 50 µs, sandboxed spawn ≤ 50 ms, renderer compute hot-path = zero sandbox overhead (the cage only traps on denied syscalls, which a well-behaved renderer never hits). Benchmarks (criterion): broker_decision (validate+canonicalize+lookup+mediate), ipc_rtt (SEQPACKET round-trip), spawn (clone+sandbox install), corp_check. Profiling: perf/cargo flamegraph on the broker decision path — hot spots are path canonicalization (realpath) and policy lookup → cache canonical grant prefixes; keep the policy table O(1). Allocator: the hostile-input path is allocation-light (no Vec::with_capacity(attacker_n), I2); reuse IPC buffers. Syscall analysis: seccomp-bpf adds tens of ns per syscall (negligible); SEQPACKET is one syscall pair per message. Lock analysis: the broker shards work per-child (no global lock on the decision path); the CapTable is per-process. Tail latency: dominated by canonicalization + (cold) spawn → cache + warm-process reuse (Phase 4). The security mechanisms are structural — they impose setup cost (spawn) and per-boundary cost (IPC/decision), but zero steady-state cost on in-renderer computation.

Scalability Analysis

The scaling unit is processes (one renderer per SiteInstance, I4). Bottlenecks: (1) process count / memory — strict site isolation means many processes; per-renderer RSS is the dominant cost → a process limit + same-site consolidation + warm-process reuse (the known site-isolation tradeoff, Phase 4); (2) the broker — the central authority every child funnels through → keep its decision O(1) + shard its work queue per-child so one child's load doesn't starve others; (3) the network process — shared CORP/ORB enforcement across all renderers → O(1) per response, scale horizontally (multiple network processes per partition) if needed. Vertical scaling: more cores/RAM ⇒ more concurrent renderers (memory-bound). Horizontal: N/A within one browser instance, but the model (broker + sandboxed children) is the unit replicated per browser. Coordination overhead: minimal — the broker is the only coordinator; renderers don't coordinate with each other (they're isolated, principle 6). Ceilings: process count is capped by memory; cross-site frame explosion is bounded by consolidation. Metadata scaling: the SiteInstance→Process map + CapTables grow with active Sites/capabilities (bounded, O(active)). The architecture trades memory for isolation — the deliberate Spectre-era choice (Reis 2019).

Mental Models & First Principles

  1. MM1 — Authority is a token you hold, not an identity you claim. Predicts: whether a compromised process can escalate by lying about who it is. Without it: you trust the renderer's claimed origin/pid/uid and every UXSS and forged-broker-request attack succeeds immediately. Applied: §6 P4/P5, §8.3, Phase 3 (capability model), Phase 5 (SOP at broker-tracked origins, I2).

  2. MM2 — Fail-closed dominates fail-open at every policy decision point. Predicts: the blast radius of a policy bug — a missing deny grants; a spurious deny inconveniences. Without it: any policy-engine bug, malformed-input path, or race condition silently becomes an allow, producing sandbox escapes rather than error messages. Applied: §6 P3/P7, §8.2, Phase 2 (deny-by-default broker, I3), Phase 10 (malformed-policy fuzz).

  3. MM3 — Defense in depth: every layer assumes the prior layer failed. Predicts: the minimum number of independent vulnerabilities an attacker needs to chain for a full escape. Without it: you design a single strong perimeter (e.g., the seccomp filter) and stop; one bypass yields total compromise. Applied: §6 P8, Phase 1 (seccomp + userns + Landlock stacked), Phase 7 (escape battery certifies the chain, Appendix C.2).

  4. MM4 — Address-space separation is the only robust defense against speculative side channels. Predicts: whether a Spectre gadget in one document can exfiltrate data from another. Without it: you rely on software-only gadget suppression (timer jitter, index_mask) and every future speculative-execution variant erodes the protection. Applied: §6 P6, Phase 4 (site isolation: one SiteInstance per process, I4), Phase 6 (COOP+COEP as the SAB gate, §8.6).

  5. MM5 — Complete mediation: every access to every protected resource must go through the policy check, every time. Predicts: whether there is an unguarded path to a resource. Without it: you build a broker but leave an ambient file descriptor, an environment variable, or an implicit channel that bypasses it — the broker is irrelevant. Applied: §6 P3, §8.4 (broker pipeline, Appendix D.4), Phase 2 (I12), Phase 3 (I1 zero ambient authority audit).

  6. MM6 — Parse, don't validate: derive structured data from hostile bytes on the trusted side before any decision. Predicts: whether a canonicalization or type-confusion bug in deserialization can produce a result that bypasses the subsequent policy check. Without it: the policy check sees a different (post-sanitize) value than the one that was acted on — classic TOCTOU of the data plane. Applied: §8.4 (IPC frame validation order), Phase 0 (bounded parse before decode), Phase 10 (origin/IPC/policy fuzz, I7/I9).

  7. MM7 — The trust boundary must be physically enforced, not logically assumed. Predicts: whether a "trusted" check in the renderer is meaningful. Without it: you write a check in the renderer (e.g., same-origin comparison, rate limiting) and congratulate yourself — an attacker with arbitrary code execution simply skips it. Applied: §6 P5, Phase 5 (SOP uses broker-tracked origins, I2), Phase 6 (Sec-Fetch set on trusted side), Phase 7 (all escape tests cross the actual OS boundary).

  8. MM8 — Capability revocation requires an epoch/generation counter, not just deletion. Predicts: whether stale capability handles that were already transmitted can be replayed after the capability is logically revoked. Without it: you delete the CapTable entry but the renderer already has a transmitted CapHandle index; it re-presents the index and the lookup finds nothing (good) — but if the table slot is reused, it hits the new entry (use-after-free of authority). Applied: §8.3 (epoch field in Capability), Phase 3 (stale-epoch tests, I6), Phase 9 (epoch-bump on crash teardown).

  9. MM9 — The isolation key (Site) must be coarser than the identity key (Origin) by exactly the intended scripting boundary. Predicts: whether two origins that can already script each other are needlessly split into separate processes (waste) or two origins that cannot script each other share a process (Spectre exposure). Without it: using Origin for isolation over-fragments memory; using just host for isolation under-isolates (co.uk confusion). Applied: §8.1 (Origin vs Site, ADR-011), Phase 4 (SiteInstance = Site + BrowsingInstance, I4), Phase 5 (SOP uses Origin; isolation uses Site).

  10. MM10 — A deny-by-default policy with an explicit positive grant table is equivalent to capability theory at the policy level. Predicts: whether any untested combination of policy clauses can produce an implicit allow. Without it: you write a deny rule for "bad things" and an allow rule for "good things" — your allow list has gaps, and policy complexity means you missed a path. The empty grant set is the safe state. Applied: §6 P3, §8.2 (policy grammar: every line is a positive grant; empty ⇒ deny-all), Phase 2 (I3), Phase 10 (policy fuzz).

Back-of-Envelope Capacity Model

  1. IPC message rate ceiling (§4: p99 RTT ≤ 50 µs). At 50 µs RTT each, one broker channel handles at most 1 / 50 µs = 20 000 round-trips/s per child. With 100 concurrent renderer processes (a realistic loaded-browser scenario), the broker sees ≤ 2 M decisions/s in the extreme-saturation case. Each decision is a hash-table lookup (~100 ns) → 2 M × 100 ns = 200 ms CPU/s per core, well within a single core budget. Design consequence: the broker's work queue must be sharded per-child (not serialized globally) to prevent one flooding child from adding latency to all others (see Scalability Analysis).

  2. Broker decision latency budget breakdown (§4: p99 ≤ 100 µs). Budget: frame recv (kernel copy, ~5 µs) + bounds check (I7, ~1 µs) + arg canonicalize/realpath (~20 µs cold, ~2 µs warm with cached prefix) + policy table lookup (~2 µs, O(1)) + mediate op (fd dup ~5 µs) + log write (~5 µs) = ~40 µs warm path, ~65 µs cold canonicalize. Leaves ~35 µs margin for p99 tail under load. Design consequence: cache canonical grant-path prefixes in the broker (§2.7) and keep the policy table at O(1) to hold the warm-path budget.

  3. Sandboxed spawn overhead budget (§4: ≤ 50 ms). Measured Chromium data: clone + address space setup ~2 ms; seccomp filter install (BPF load) ~3–5 ms; Landlock ruleset build + apply ~2 ms; userns uid/gid map writes ~1 ms; execve child stub ~5–10 ms; total ~13–20 ms on a modern kernel, well within the 50 ms ceiling. Design consequence: warm-process reuse (Phase 4, §4.7) amortizes spawn cost over multiple navigations to the same Site; the 50 ms target is the cold-spawn bound, not the steady-state new-tab latency.

  4. Per-renderer process memory overhead. A Chromium renderer RSS on a simple page: ~50–80 MB. A minimal bsm renderer (stub + IPC socket + CapTable + seccomp filter installed) starts at ~4–8 MB; the payload (#305) adds ~40–60 MB when loaded. Assumption: 50 MB/renderer (§4 + M9 target ≤ 64 MB). At 100 concurrent renderers: 100 × 50 MB = 5 GB. Design consequence: a process limit + same-site process consolidation policy is mandatory at scale (see Scalability Analysis; Phase 4 §4.7); strict site isolation is a deliberate memory-for-security trade (Reis 2019).

  5. seccomp allowlist size vs filter evaluation cost (§4: ≤ 150 syscalls). A BPF filter for 150 syscall rules compiles to ~300–500 BPF instructions. BPF evaluation: ~5–15 ns per syscall on modern kernels. The renderer's hot path (compute + IPC recv/send) hits ~10–20 syscalls per event loop turn; 20 × 15 ns = 300 ns BPF overhead per turn — negligible at even 1 M turns/s. Design consequence: keep the allowlist minimal (≤ 150, §4) for auditability, not for BPF performance; the performance cost is already negligible (§1.7).

  6. fd-passing throughput (§4: IPC RTT ≤ 50 µs, ADR-008: SCM_RIGHTS). SCM_RIGHTS adds one kernel dup per passed fd (~1 µs each). MAX_FDS = 8 per frame (§8.4), so the worst-case overhead is 8 µs extra per message. At 20 000 msgs/s with 8 fds each: 8 × 20 000 × 1 µs = 160 ms CPU/s — still within budget. Design consequence: cap MAX_FDS ≤ 8 (already in §8.4, I2) and prefer passing a single fd capability rather than bulk-passing handles; each fd transfer should represent a real capability grant, not a data channel.

  7. Origin parse + PSL lookup cost (Phase 5: SOP on every cross-frame access). PSL trie depth: ~4–6 labels for most TLDs. Trie lookup: ~200 ns. Origin canonicalization: ~500 ns (string scan + lowercase). Per cross-frame access the SOP check runs once: ~700 ns total. At 10 000 cross-frame accesses/s (a busy page with many OOPIFs): 7 ms CPU/s — negligible. Design consequence: parse origin once per document load and cache the canonical form; do not re-parse on every per-frame-access IPC (§5.7).

  8. CORP/ORB check throughput (Phase 6, §4: policy default deny-by-default). Each network response requires: response-header parse (~2 µs) + requester-relationship check (origin tuple compare, ~100 ns) + CORP table lookup (~200 ns) = ~2.3 µs per response. A renderer loading 100 subresources/page: 100 × 2.3 µs = 230 µs per page load at the network process — negligible. At 1 000 concurrent page loads: 230 ms CPU/s in the network process, well within a single core. Design consequence: CORP/ORB checks are not a performance bottleneck at realistic browser load; invest in correctness (conformance vectors) over optimization (§6.7).

  9. Capability table operation cost (Phase 3, I6). CapTable lookup: O(1) HashMap keyed by (CapId, epoch). At 10 000 IPC requests/s × 1 lookup/request = 10 000 lookups/s. Each lookup ~50 ns (cache-warm HashMap): 0.5 ms CPU/s — negligible. Mint (on brokered file open): ~1 µs (insert + generate nonce). Revoke (on renderer death): O(active caps per renderer), expected ~10–50 entries. Design consequence: per-child CapTable isolation (not a global table) is the correct choice for both security (no cross-child cap confusion) and performance (no global lock; see Scalability Analysis).

  10. Process spawn rate at navigation speed. A user navigating rapidly: ~2–5 cross-site navigations/s, each potentially spawning a new renderer (worst case, no warm reuse). At 5 spawns/s × 50 ms/spawn = 250 ms of spawn CPU/s — acceptable but visible. With warm-process reuse (Phase 4): most navigations to returning Sites skip the spawn, reducing to ~1–2 cold spawns/s. Design consequence: the warm-process cache (Phase 4 §4.7) is load-bearing for user-perceptible latency at rapid cross-site browsing; size it to cover the top-N Sites by visit frequency.

(§8.2, Phase 2, I3, P7, ADR-004, MM2)

Alternative Architectures (Roads Not Taken)

SFI-Everything Single Process (In-Process WebAssembly Sandboxing)

┌─────────────────────────────────────────────────────┐
│  SINGLE BROWSER PROCESS                             │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────┐ │
│  │ Renderer tab │  │ Media codecs │  │ Font shaper│ │
│  │  (Wasm SFI)  │  │  (Wasm SFI)  │  │ (Wasm SFI) │ │
│  └──────┬───────┘  └──────┬───────┘  └─────┬─────┘ │
│         │  host calls only (no OS syscalls) │       │
│  ┌──────▼───────────────────────────────────▼─────┐ │
│  │  Wasm runtime (trusted supervisor)              │ │
│  │  memory isolation via linear-memory bounds      │ │
│  └─────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘

Wins when: the OS provides no usable sandbox primitives (embedded platforms, WASI), or the attack surface is dominated by in-process C++ codecs (image/font/media decoders) rather than the renderer runtime itself; RLBox (Firefox) takes exactly this approach for codecs.

Embodied by: Firefox RLBox (USENIX Security 2020, Narayan et al.); extended to the limit this becomes the "compile everything to Wasm in one process" model.

Why rejected here: SFI-in-process does not prevent speculative side channels — all Wasm sandboxes share the process address space, and a Spectre gadget in one sandbox reads the host's memory. For a threat model of "assume the renderer is fully compromised and Spectre exists," process separation (OS-enforced, hardware memory-isolated) is the only robust defense (MM4, I4). This design treats the renderer payload as untrusted from outside a hard OS boundary, not from inside a software-enforced one.

Per-Site Micro-VM Isolation

┌──────────────────────────────────────────────────────────┐
│  HOST BROKER                                             │
│  allocates lightweight VMs per site                      │
└──────────┬───────────────────────┬───────────────────────┘
           │ virtio IPC            │ virtio IPC
┌──────────▼──────────┐  ┌─────────▼─────────────────────┐
│  MICRO-VM: site A   │  │  MICRO-VM: site B              │
│  (disposable VM)    │  │  (disposable VM)               │
│  own guest kernel   │  │  own guest kernel              │
│  own page tables    │  │  own page tables               │
└─────────────────────┘  └────────────────────────────────┘

Wins when: the host kernel's syscall surface is itself large and exploitable, or the threat model includes kernel-level exploits (ring-0 elevation); a compromised renderer exploiting a kernel bug cannot escape a VM boundary. Also wins for forensic isolation (a disposable VM is destroyed after browsing, leaving no host state).

Embodied by: Qubes OS disposable VMs; Bromium (now HP Wolf Security) micro-virtualization; Intel VT-x / AMD-V hardware isolation.

Why rejected here: micro-VM spawn time (100–500 ms per VM) violates the §4 spawn target (≤ 50 ms) and the user-visible navigation latency budget. Per-VM memory overhead (a guest kernel + its page tables + virtio stack) is 3–10× the per-process overhead of this design. The design space between "process + seccomp + userns" and "VM" is covered by the multi-layer model here (MM3); a kernel exploit bypassing seccomp is a residual risk acknowledged in Appendix C.7.

Remote Browser Isolation (Server-Side Rendering)

┌────────────────────────────┐         ┌───────────────────────────────┐
│  USER ENDPOINT             │         │  REMOTE RENDERING CLUSTER     │
│  (thin client)             │         │  ┌──────────────────────────┐ │
│  receives: draw commands   │◄────────│  │ Renderer process         │ │
│            or pixels       │  pixels/│  │ (runs full web content)  │ │
│                            │ drawcmds│  └──────────────────────────┘ │
│  no web content execution  │         │  network isolation; TLS term  │
└────────────────────────────┘         └───────────────────────────────┘

Wins when: the endpoint is untrusted, unmanaged, or locked-down (e.g., a kiosk, a government endpoint, a BYOD device accessing sensitive SaaS); the user device never executes web content, so a browser exploit on the client is irrelevant; the server-side renderer is isolated per-session.

Embodied by: Cloudflare Browser Isolation (uses Chromium-based remote rendering, pixel/draw-command streaming); Authentic8 Silo; Menlo Security.

Why rejected here: this design's goal is an embeddable security model (sbx-browser beneath #266/#305) running on the user's machine. Remote isolation introduces network latency (impractical for interactive content), requires a server-side rendering fleet (operational complexity outside scope), and changes the trust model entirely (the server operator must be trusted). For local browser security, the OS-process model is the right abstraction.

Single-Sandbox Multi-Process Without Site Isolation (Pre-2018 Chrome Model)

┌────────────────────────────────────────────────────────┐
│  BROWSER PROCESS (privileged, trusted)                 │
└──────────────┬────────────────────────────────────────┘
               │ IPC (typed)
┌──────────────▼────────────────────────────────────────┐
│  ONE RENDERER PROCESS  (sandboxed, but multi-site)    │
│  https://news.example, https://bank.example,          │
│  https://ads.example — ALL co-resident in one process │
│  seccomp-bpf + userns (OS cage present)               │
│  BUT: same address space = Spectre-visible            │
└───────────────────────────────────────────────────────┘

Wins when: memory is severely constrained (one renderer process vs N), Spectre is not in the threat model (pre-2018, or a platform with hardware mitigations considered sufficient), and the primary threat is code-execution escape to the host OS rather than cross-origin data leakage.

Embodied by: Chromium before Site Isolation full rollout (pre-Chrome 67, 2018); still the default on Android Chrome below a memory threshold.

Why rejected here: a Spectre gadget in any script on any tab can speculatively read any co-resident cross-origin data — all cookies, tokens, and DOM of every other origin in the same process. The January 2018 Spectre disclosure (Kocher et al.) and the subsequent full-desktop Chrome Site Isolation rollout (Reis et al. 2019) demonstrate that co-residency is not a theoretical risk; it is an exploited attack class. This design's §4 side-channel posture and I4 make site isolation non-negotiable (MM4).

Appendix C — Worked Threat / Escape Walkthroughs

The defining question: a renderer is fully compromised — what can it reach, what can't it? Each walkthrough traces an attack through the layers (principle 8) and shows where it dies.

C.1 Compromised renderer — reachability map

A fully-compromised renderer (arbitrary code execution inside the renderer process) CAN:
  - compute arbitrarily (CPU, its own address space)
  - read/write ONLY its own process memory (one Site's data — I4)
  - issue IPC to the broker (which deny-by-default mediates — I3)
  - use ONLY the capabilities it was explicitly granted (e.g., one fd for a user-picked file — I6)
  - send postMessage (the browser stamps the true origin — I2)

A fully-compromised renderer CANNOT:
  - call open()/socket()/execve()/ptrace()/clone() — seccomp denies (I8)
  - read the filesystem (no path authority; Landlock + no open syscall — I8/I9)
  - open network sockets (empty net namespace + no socket syscall — I8); fetch is brokered + origin-checked (I5)
  - read another Site's memory (not co-resident — I4, principle 6; the Spectre defense)
  - read cross-origin response bytes (CORP/ORB blocks at the network process — I5)
  - forge a capability (server-side CapTable + nonce — I6) or an origin (broker-tracked — I2)
  - escalate via the broker (deny-by-default + subset rights + canonicalize-first — I3/I9)
  - crash the broker or siblings (crash isolation — I11)
  - spawn helper processes (clone/fork denied — I8)
⇒ owning the renderer yields: its own Site's data + its granted capabilities. Nothing else. (principle 1)

C.2 Escape attempt: memory-corruption → arbitrary syscall

1. Attacker exploits a memory-safety bug in the renderer (the untrusted #305 payload) → arbitrary code in-renderer
2. Attacker shellcode calls open("/etc/passwd", O_RDONLY)
3. Layer 1 (seccomp-bpf, I8): open* not in the renderer allowlist → SIGSYS → process killed (or EPERM)
   Even if open were somehow reached: Layer 2 (Landlock, I9) grants no filesystem paths → EACCES
   Even with a path: Layer 3 (user namespace) — the renderer's view has no sensitive mounts
⇒ DEAD at Layer 1. The memory bug bought arbitrary code but NOT arbitrary authority. (defense in depth, principle 8)

C.3 Escape attempt: broker confusion (forged request)

1. Compromised renderer crafts BrokerRequest{op:FileOpen, path:"/etc/shadow", initiator:"file:///etc"}
2. Broker validates the frame (bounded, I7) → canonicalizes path = "/etc/shadow" (I9)
3. Broker IGNORES the renderer's claimed initiator; uses the SiteInstance it assigned at spawn (I2)
4. Policy lookup: this renderer's role/Site has NO grant for /etc/shadow → Verdict::Deny (I3, deny-by-default)
   (And: a renderer doesn't get path-based FileOpen at all — user files arrive as pre-opened fds, §8.8)
⇒ DEAD at the policy check. Forged values bought nothing — the broker trusts only its own state. (principle 5)

C.4 Escape attempt: cross-origin data theft

1. Compromised renderer (https://evil.example) wants https://bank.example/account.json
2. It has no net capability → must ask the network process (brokered fetch, mode no-cors)
3. Network process fetches; bank.example responds with Cross-Origin-Resource-Policy: same-origin (or it's JSON → ORB)
4. CORP: requester(evil) ≠ resource(bank), CORP=same-origin → BLOCK (I5); OR ORB: cross-origin no-cors JSON → BLOCK
5. The bytes are dropped at the network process; the renderer gets a network/opaque error — never the JSON
⇒ DEAD at the network process. The bytes never entered evil's address space. (I5, no co-residency)

C.5 Escape attempt: Spectre side channel

1. Compromised renderer (ads.example, an OOPIF) runs a Spectre gadget to leak co-resident secrets speculatively
2. Site isolation (I4): ads.example is in its OWN process (P2); news.example (the embedder) is in P1
3. The gadget can only speculatively read P2's OWN address space — which holds only ads.example data
   news.example's cookies/DOM/secrets are in P1 — a different address space, not speculatively reachable
4. For same-process high-res timing/SharedArrayBuffer: gated behind cross-origin isolation (COOP+COEP, §8.6),
   which itself requires the document to be isolated — so SAB is only available where it's safe
⇒ DEAD by address-space separation. Spectre reads memory you share; site isolation ensures you share none cross-origin.
  (principle 6 — the 2018 Reis et al. response to Spectre)

C.6 Escape attempt: capability/handle forge + delegation abuse

1. Compromised renderer holds CapHandle(3)→{file.read, fd=7, rights=READ} for a user-picked file
2. It tries: (a) use CapHandle(99) it never received; (b) widen rights to READ|WRITE on its delegation; (c) reuse a
   handle after the tab closed
   (a) → CapTable lookup miss (ids are server-side, not guessable) → Deny (I6)
   (b) → delegation intersects rights with policy; READ stays READ; WRITE not present → Deny (subset, principle 4)
   (c) → epoch bumped on tab-close revoke → epoch mismatch → Deny (I6)
⇒ DEAD at the CapTable. Authority is unforgeable, un-widenable, and revocable. (principle 4)

C.7 Residual risk (honestly stated)

- A bug IN the broker/IPC parser (the trusted side) could be an escape → mitigated by Rust memory safety (ADR-001),
  fuzzing (I7), minimal surface (principle 9), but never zero. This is why the broker is small + audited.
- A kernel bug in seccomp/namespaces/Landlock itself → out of our control; defense-in-depth (multiple layers) means
  one kernel bug rarely yields full compromise.
- A novel side channel not covered by site isolation → site isolation is the structural defense; we document the gap.
- Supply-chain compromise of a broker dependency → cargo deny + SBOM + pinning (ADR-023/025).
The thesis is "owning the renderer yields nothing" — the residual surface is the TRUSTED code, which is why it is
Rust, small, fuzzed, and escape-tested. (principles 1, 8, 9)

no_new_privs set before install; filter inherited + irrevocable (§8.5). Per-syscall argument filtering (e.g., mmap PROT flags) blocks W^X and dangerous flag combos. The network process gets a different (net-syscall-permitting but file-denying) profile; the GPU process gets GPU-ioctl access only.

D.2 Namespace + Landlock config (renderer)

clone flags:  CLONE_NEWUSER | CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWIPC | CLONE_NEWNS
uid_map:      maps the renderer's uid to an unprivileged uid inside the userns (no real root)
NEWNET:       empty network namespace — no interfaces, no sockets reachable (defense vs socket() even if allowed)
NEWPID:       isolated pid namespace — can't see/signal other processes; a pid-1 reaper handles zombies
