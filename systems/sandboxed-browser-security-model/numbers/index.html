Back-of-Envelope Capacity Model

  1. IPC message rate ceiling (§4: p99 RTT ≤ 50 µs). At 50 µs RTT each, one broker channel handles at most 1 / 50 µs = 20 000 round-trips/s per child. With 100 concurrent renderer processes (a realistic loaded-browser scenario), the broker sees ≤ 2 M decisions/s in the extreme-saturation case. Each decision is a hash-table lookup (~100 ns) → 2 M × 100 ns = 200 ms CPU/s per core, well within a single core budget. Design consequence: the broker's work queue must be sharded per-child (not serialized globally) to prevent one flooding child from adding latency to all others (see Scalability Analysis).

  2. Broker decision latency budget breakdown (§4: p99 ≤ 100 µs). Budget: frame recv (kernel copy, ~5 µs) + bounds check (I7, ~1 µs) + arg canonicalize/realpath (~20 µs cold, ~2 µs warm with cached prefix) + policy table lookup (~2 µs, O(1)) + mediate op (fd dup ~5 µs) + log write (~5 µs) = ~40 µs warm path, ~65 µs cold canonicalize. Leaves ~35 µs margin for p99 tail under load. Design consequence: cache canonical grant-path prefixes in the broker (§2.7) and keep the policy table at O(1) to hold the warm-path budget.

  3. Sandboxed spawn overhead budget (§4: ≤ 50 ms). Measured Chromium data: clone + address space setup ~2 ms; seccomp filter install (BPF load) ~3–5 ms; Landlock ruleset build + apply ~2 ms; userns uid/gid map writes ~1 ms; execve child stub ~5–10 ms; total ~13–20 ms on a modern kernel, well within the 50 ms ceiling. Design consequence: warm-process reuse (Phase 4, §4.7) amortizes spawn cost over multiple navigations to the same Site; the 50 ms target is the cold-spawn bound, not the steady-state new-tab latency.

  4. Per-renderer process memory overhead. A Chromium renderer RSS on a simple page: ~50–80 MB. A minimal bsm renderer (stub + IPC socket + CapTable + seccomp filter installed) starts at ~4–8 MB; the payload (#305) adds ~40–60 MB when loaded. Assumption: 50 MB/renderer (§4 + M9 target ≤ 64 MB). At 100 concurrent renderers: 100 × 50 MB = 5 GB. Design consequence: a process limit + same-site process consolidation policy is mandatory at scale (see Scalability Analysis; Phase 4 §4.7); strict site isolation is a deliberate memory-for-security trade (Reis 2019).

  5. seccomp allowlist size vs filter evaluation cost (§4: ≤ 150 syscalls). A BPF filter for 150 syscall rules compiles to ~300–500 BPF instructions. BPF evaluation: ~5–15 ns per syscall on modern kernels. The renderer's hot path (compute + IPC recv/send) hits ~10–20 syscalls per event loop turn; 20 × 15 ns = 300 ns BPF overhead per turn — negligible at even 1 M turns/s. Design consequence: keep the allowlist minimal (≤ 150, §4) for auditability, not for BPF performance; the performance cost is already negligible (§1.7).

  6. fd-passing throughput (§4: IPC RTT ≤ 50 µs, ADR-008: SCM_RIGHTS). SCM_RIGHTS adds one kernel dup per passed fd (~1 µs each). MAX_FDS = 8 per frame (§8.4), so the worst-case overhead is 8 µs extra per message. At 20 000 msgs/s with 8 fds each: 8 × 20 000 × 1 µs = 160 ms CPU/s — still within budget. Design consequence: cap MAX_FDS ≤ 8 (already in §8.4, I2) and prefer passing a single fd capability rather than bulk-passing handles; each fd transfer should represent a real capability grant, not a data channel.

  7. Origin parse + PSL lookup cost (Phase 5: SOP on every cross-frame access). PSL trie depth: ~4–6 labels for most TLDs. Trie lookup: ~200 ns. Origin canonicalization: ~500 ns (string scan + lowercase). Per cross-frame access the SOP check runs once: ~700 ns total. At 10 000 cross-frame accesses/s (a busy page with many OOPIFs): 7 ms CPU/s — negligible. Design consequence: parse origin once per document load and cache the canonical form; do not re-parse on every per-frame-access IPC (§5.7).

  8. CORP/ORB check throughput (Phase 6, §4: policy default deny-by-default). Each network response requires: response-header parse (~2 µs) + requester-relationship check (origin tuple compare, ~100 ns) + CORP table lookup (~200 ns) = ~2.3 µs per response. A renderer loading 100 subresources/page: 100 × 2.3 µs = 230 µs per page load at the network process — negligible. At 1 000 concurrent page loads: 230 ms CPU/s in the network process, well within a single core. Design consequence: CORP/ORB checks are not a performance bottleneck at realistic browser load; invest in correctness (conformance vectors) over optimization (§6.7).

  9. Capability table operation cost (Phase 3, I6). CapTable lookup: O(1) HashMap keyed by (CapId, epoch). At 10 000 IPC requests/s × 1 lookup/request = 10 000 lookups/s. Each lookup ~50 ns (cache-warm HashMap): 0.5 ms CPU/s — negligible. Mint (on brokered file open): ~1 µs (insert + generate nonce). Revoke (on renderer death): O(active caps per renderer), expected ~10–50 entries. Design consequence: per-child CapTable isolation (not a global table) is the correct choice for both security (no cross-child cap confusion) and performance (no global lock; see Scalability Analysis).

  10. Process spawn rate at navigation speed. A user navigating rapidly: ~2–5 cross-site navigations/s, each potentially spawning a new renderer (worst case, no warm reuse). At 5 spawns/s × 50 ms/spawn = 250 ms of spawn CPU/s — acceptable but visible. With warm-process reuse (Phase 4): most navigations to returning Sites skip the spawn, reducing to ~1–2 cold spawns/s. Design consequence: the warm-process cache (Phase 4 §4.7) is load-bearing for user-perceptible latency at rapid cross-site browsing; size it to cover the top-N Sites by visit frequency.
