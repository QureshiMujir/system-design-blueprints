⬜ Phase 0 — Skeleton, Access-Method Interface, and CI §12

Objectives

Establish the workspace skeleton, the AccessMethod trait boundary (ADR-17), a deterministic build, and a CI pipeline that will gate every later phase.

Deliverable

A runnable skeleton binary that loads configuration, exposes the AccessMethod trait (with a no-op implementation), and exports telemetry, gated by a green CI pipeline.

Acceptance
  • cold startup < 1.0s; reproducible build hash matches across two clean builds; zero clippy warnings; CI green including the empty aie-conformance and convergence.yml gates; malformed config fixture (fixtures/config/malformed.toml) is rejected with AieError, not a panic.
Fixtures
  • fixtures/config/minimal.toml — minimal valid startup config, expect clean start.
  • fixtures/config/malformed.toml — invalid UTF-8 and missing required key, expect AieError::InvalidPredicate-class rejection, not panic.
  • fixtures/build/reproducible.sha256 — expected build hash for reproducibility check.
Pitfalls
  1. Manifestation: CI green locally but red on a clean runner. Root cause: hidden dependency drift from an unpinned transitive crate. Debug method: diff Cargo.lock between runs. Signal: cargo build --locked failure. Recovery: pin the drifting crate explicitly.
  2. Manifestation: reproducible-build hash mismatch. Root cause: embedded build timestamp. Debug method: compare binary diffs byte-by-byte. Signal: reproducible.sha256 mismatch. Recovery: strip timestamps, use SOURCE_DATE_EPOCH.
  3. Manifestation: startup exceeds 1s intermittently. Root cause: telemetry exporter blocking on first flush. Debug method: flamegraph the startup path. Signal: startup_duration_ms telemetry outlier. Recovery: make first flush async/non-blocking.

⬜ Phase 1 — The B+Tree Engine with Latch Coupling §13

Objectives

Implement a durable, concurrent B+Tree with latch-coupled descent (P7, Lehman & Yao 1981) as the ordered-range access path (ADR-02, ADR-04).

Deliverable

A concurrent, durable B+Tree passing the structural verifier under sustained concurrent read/write/split stress.

Acceptance
  • structural verifier reports zero I7 violations across 10M operations; point-lookup p99 < 6ms (§4); zero deadlocks across 1,000 concurrent-stress runs; split replay is deterministic across 100 replay iterations of the same fixture.
Fixtures
  • fixtures/btree/deep_split.bin — forces 5+ levels of cascading splits, expects structural verifier pass.
  • fixtures/btree/duplicate_keys.bin — 100,000 duplicate keys, expects correct fence-key ordering with no separator collisions.
  • fixtures/btree/split_replay.bin — replay of a captured split sequence, expects byte- identical resulting tree across 100 replays (determinism).
  • fixtures/btree/concurrent_stress.trace — 64 concurrent readers/writers, expects zero latch_order_violation_total.
Pitfalls
  1. Manifestation: reader lands on a stale separator after a concurrent split. Root cause: parent latch released before child latch acquired (I5 violation). Debug method: replay concurrent_stress.trace with latch-order audit enabled. Signal: latch_order_violation_total > 0. Recovery: enforce S3-before-S4 ordering (§8.5).
  2. Manifestation: phantom sibling traversal loops. Root cause: stale right-link after a concurrent merge. Debug method: structural verifier sibling-chain walk. Signal: verifier cycle detection. Recovery: rebuild sibling chain from parent scan.
  3. Manifestation: root-split race under high concurrency. Root cause: two concurrent inserts both attempt to split the root without serializing on the root latch. Debug method: targeted root-split stress fixture. Signal: duplicate root page IDs. Recovery: serialize root splits behind a dedicated root-latch epoch.
  4. Manifestation: duplicate-key prefix compression corrupts suffix ordering. Root cause: shared-prefix recompute picked the wrong common prefix length. Debug method: duplicate_keys.bin fixture diff against oracle ordering. Signal: verifier separator- ordering failure. Recovery: recompute page-level prefix from full key set, not a sample.

⬜ Phase 2 — Prefix Compression and Range Scans §14

Objectives

Add page-level prefix compression (§8.5) and hardened range-scan iterators over the B+Tree built in Phase 1.

Deliverable

Prefix-compressed B+Tree pages with a hardened, concurrency-safe range-scan iterator.

Acceptance
  • compression reduces per-key storage by >= 60% on the customer_100xx-style worked-example fixture (§8.5 shows 85.7% on that exact case); range-scan p99 < 20ms for 10k-row scans (§4); zero result divergence against the full-scan oracle across 10,000 randomized range fixtures.
Fixtures
  • fixtures/btree/prefix_worked_example.bin — the §8.5 customer_100xx case, expects 85.7% suffix-size reduction.
  • fixtures/btree/degenerate_prefix.bin — fully divergent keys, expects zero-length shared prefix without error.
  • fixtures/btree/scan_across_split.trace — concurrent split during an active scan, expects zero missed or duplicated rows.
Pitfalls
  1. Manifestation: scan returns a duplicated row after a concurrent split. Root cause: scan cursor re-descended without re-validating the fence key. Debug method: replay scan_across_split.trace. Signal: I2-style differential mismatch. Recovery: add fence-key re-validation on every sibling hop.
  2. Manifestation: prefix recompute after merge produces an incorrect shared prefix. Root cause: recompute used only one half's key sample instead of the full merged set. Debug method: targeted merge-then-verify fixture. Signal: separator-ordering verifier failure. Recovery: recompute over the full merged key set.
  3. Manifestation: scan throughput regresses after enabling compression. Root cause: suffix reconstruction on every key read adds an uncached allocation. Debug method: flamegraph the scan hot path. Signal: scan-throughput benchmark regression in CI. Recovery: reuse a per-scan reconstruction buffer instead of allocating per key.

⬜ Phase 3 — The ART Engine with Adaptive Nodes §15

Objectives

Implement the Adaptive Radix Tree (Leis, Kemper & Neumann 2013) with the four node types (§8.6) and adaptive growth/shrink under hysteresis (P8).

Deliverable

A concurrent ART implementation supporting adaptive node growth/shrink, passing the structural validator under fuzzed concurrent access.

Acceptance
  • structural validator reports zero I4 violations across 1M fuzzed insert/delete operations; point-lookup p99 < 6ms (§4); memory per entry < 52 bytes amortized (§4) across a mixed node-type distribution; zero growth/shrink thrashing events in a 24-hour soak (§28).
Fixtures
  • fixtures/art/node48_transition.bin — inserts exactly 49 children to force the Node48→256 transition, expects correct child migration.
  • fixtures/art/all_duplicate_keys.bin — the §8.11 degenerate case, expects leaf-with- duplicate-list fallback, not a Node256 allocation.
  • fixtures/art/concurrent_growth.trace — concurrent readers during a growth transition, expects zero art_keyset_divergence_total.
Pitfalls
  1. Manifestation: reader observes a torn node mid-growth. Root cause: OLC re-validation skipped after a growth transition. Debug method: replay concurrent_growth.trace. Signal: art_keyset_divergence_total > 0. Recovery: add a post-read generation-counter re-check before returning a result.
  2. Manifestation: growth/shrink thrashing at the Node16/Node48 boundary. Root cause: missing hysteresis margin (P8). Debug method: node_type_distribution telemetry oscillation over a short window. Signal: thrashing-detector alert. Recovery: widen the shrink threshold below the growth threshold.
  3. Manifestation: Node256 allocated for a single distinct key. Root cause: the all-duplicate-keys fallback (step 17) not applied. Debug method: all_duplicate_keys.bin fixture. Signal: memory-per-entry target (§4) exceeded. Recovery: detect single-child-byte-value insert pattern and route to duplicate-list leaf.

⬜ Phase 4 — ART Path Compression §16

Objectives

Add path compression and lazy expansion (§8.6) to the ART built in Phase 3, minimizing node count for long shared-prefix key sets.

Deliverable

Path-compressed, lazily-expanded ART passing the structural validator across the worked-insert regression and fuzzed divergence fixtures.

Acceptance
  • worked-insert fixture ("10"/"100"/"1000") produces the exact node structure described in §8.6 (one Node4 at each divergence point, absorbed prefix "10"); path-compression-ratio

    = 40% on a URL-like key benchmark; zero I4 violations across 500,000 fuzzed divergence inserts; memory per entry remains < 52 bytes (§4).

Fixtures
  • fixtures/art/path_compression.bin — the exact §8.6 worked-insert sequence, expects the documented two-Node4 structure.
  • fixtures/art/prefix_collision.bin — two keys sharing a long prefix that diverge at the last byte, expects a single Node4 at the final divergence point.
  • fixtures/art/divergence_fuzz.trace — 500,000 fuzzed inserts with randomized divergence points, expects zero structural-validator failures.
Pitfalls
  1. Manifestation: compressed prefix silently drops a byte during recompression after a delete. Root cause: re-compression step (16.2 step 9) used the wrong child's prefix as the source of truth. Debug method: path_compression.bin regression after inserting then deleting the middle key. Signal: I4 violation on the structural validator. Recovery: always recompute the collapsed prefix from the surviving child's full path.
  2. Manifestation: OLC traversal returns a wrong result after a concurrent expansion. Root cause: compressed-prefix comparison did not re-validate the generation counter after a partial match. Debug method: concurrent insert-during-expansion fixture. Signal: art_keyset_divergence_total > 0. Recovery: re-validate generation counter immediately after every prefix-compare, not just at node entry.
  3. Manifestation: memory-per-entry target regresses on long-shared-prefix keys. Root cause: inline prefix storage not spilling to the indirect buffer (step 6), inflating every node. Debug method: memory-footprint benchmark on URL-like keys. Signal: §4 memory target exceeded. Recovery: enforce the inline-prefix cap and spill threshold.

⬜ Phase 5 — Database Cracking on a Column with the Cracker Index §17

Objectives

Implement database cracking (Idreos, Kersten & Manegold 2007) as the online, query-driven partitioning engine over a Column, with the CrackerIndex (§8.2) as its structural ledger.

Deliverable

A working cracking engine over a single column that partitions in place on query predicates, preserving the tuple multiset and passing the differential oracle.

Acceptance
  • zero I1/I2 violations across 100,000 randomized crack-then-scan differential fixtures; first-touch crack cost matches the O(n) prediction within 10% on a 1,000,000-row benchmark (§8.1); convergence to a fully-refined 1,000,000-row range in <= 20 queries (§4); piece count never exceeds O(number of distinct query boundaries observed) per the blowup guard.
Fixtures
  • fixtures/cracker/worked_example.bin — the exact §8.1 two-query sequence, expects the documented three-then-four-piece boundary progression.
  • fixtures/cracker/constant_column.bin — all values equal, expects rejection of duplicate boundaries without an infinite loop (§8.11).
  • fixtures/cracker/multiset_differential.trace — 100,000 randomized crack-then-scan sequences diffed against the full-scan oracle, expects zero mismatches.
  • fixtures/cracker/convergence_1m.bin — a 1,000,000-row column under a fixed skewed range, expects full refinement within 20 queries.
Pitfalls
  1. Manifestation: a row disappears after a crack. Root cause: the Hoare-partition swap in C3/C4 double-counted a boundary element. Debug method: replay multiset_differential.trace with per-element checksum tracing. Signal: crack_multiset_mismatch_total > 0. Recovery: fix the partition's inclusive/exclusive boundary handling and re-run the differential fixture.
  2. Manifestation: infinite re-crack loop on a constant column. Root cause: boundary insert did not check for an existing identical boundary (I3). Debug method: constant_column.bin fixture with a crack-count ceiling assertion. Signal: crack-count exceeds a sane bound within a single query. Recovery: reject duplicate-value boundary inserts per §8.11.
  3. Manifestation: piece count grows unbounded under an adversarial workload. Root cause: no cap on distinct boundary insertion rate (Schuhknecht et al. 2013's uncracked- pieces failure mode). Debug method: piece_count telemetry trend over a long soak. Signal: piece-count-blowup guard alert. Recovery: fall back to a secondary piece-index structure (ADR-05's rejected alternative) once the guard threshold is crossed.
  4. Manifestation: crash mid-crack corrupts the next query's result. Root cause: the piece was left in a half-partitioned physical state without reverting to the pre-crack boundary set. Debug method: SIGKILL-injection fixture mid-partition. Signal: I1/I2 violation on the first post-restart query. Recovery: on restart, always treat an unconfirmed boundary insert as not-yet-committed (ADR-14 lazy recovery).

⬜ Phase 6 — Adaptive Merging and Convergence §18

Objectives

Implement adaptive merging (Graefe & Kuno 2010) as an alternative reorganization strategy alongside cracking (ADR-03), and implement the convergence-comparison machinery that lets the router (Phase 8) eventually choose between them.

Deliverable

An adaptive-merging engine coexisting with cracking, both passing the differential oracle, with a measured convergence-comparison report matching the §8.3 contrast table's qualitative shape.

Acceptance
  • zero I2/I8 violations across 100,000 randomized merge-then-scan differential fixtures; first-query cost for adaptive merging exceeds cracking's first-query cost by a measured factor consistent with O(n log k) vs O(n) (within 20% of predicted ratio for k=8); on a stable wide-range workload, adaptive merging reaches full refinement in fewer queries than cracking, matching the qualitative claim in P12; zero I11 violations (merge steps never increase overlapping-run count for the touched range).
Fixtures
  • fixtures/merge/contrast_table.bin — reproduces the §8.3 contrast table's five dimensions as measured numbers on a shared synthetic dataset (n=1,000,000, k=8).
  • fixtures/merge/multiset_differential.trace — 100,000 randomized merge-then-scan sequences diffed against the full-scan oracle.
  • fixtures/merge/single_run_noop.bin — a column with one run, expects M3 to be a true no-op (zero merge_step invocations).
  • fixtures/merge/convergence_stable_wide.bin — a stable, wide-range workload profile, expects adaptive merging to converge in fewer queries than cracking on the same data.
Pitfalls
  1. Manifestation: runs become unsorted after a partial merge. Root cause: M3's merge step used a non-stable merge, reordering equal-valued elements across run boundaries in a way that broke the disjointness assumption. Debug method: replay multiset_differential.trace with run-order assertions enabled. Signal: run_order_violation_total > 0 (I8). Recovery: use a stable merge algorithm and re-verify disjointness after every merge step.
  2. Manifestation: adaptive merging converges slower than cracking even on a stable wide workload, contradicting P12. Root cause: the workload-shape detector (step 7) is misclassifying the workload as narrow/shifting, so the wrong strategy is compared. Debug method: inspect the detector's classification against the actual query log. Signal: convergence_stable_wide.bin fixture fails its comparative assertion. Recovery: widen the detector's stability window or fix its range-overlap heuristic.
  3. Manifestation: a merge step increases the number of runs overlapping a future query (I11 violation for adaptive merging). Root cause: M3 merged two runs but left a third, still-overlapping run un-merged, and the run-count accounting did not detect the partial coverage. Debug method: convergence-monotonicity assertion after every merge step. Signal: convergence_regression_total > 0. Recovery: ensure M2's overlapping-run identification captures all runs overlapping [lo, hi), not just the first found.

⬜ Phase 7 — Statistics Collection and Histograms §19

Objectives

Implement incremental histogram and sketch-based statistics (§8.8, ADR-08, ADR-09) feeding the cost model that the router will consume in Phase 8.

Deliverable

An incremental statistics-collection subsystem producing versioned, staleness-bounded histogram and sketch snapshots consumed by (but not yet driving) the router.

Acceptance
  • cardinality-estimation error < 15% on synthetic benchmark datasets; statistics-collection overhead remains amortized O(1) per write, measured as < 5% throughput regression versus a no-statistics baseline; zero I6 violations (no generation regression) across 1,000 concurrent read/write fixture runs; staleness never exceeds the §4 bound (< 2s or < 10k writes) in a sustained-write soak.
Fixtures
  • fixtures/stats/incremental_update.bin — a sequence of writes with known bucket-boundary crossings, expects exact bucket counts after each write.
  • fixtures/stats/constant_column_histogram.bin — the §8.11 constant-column case, expects a single-bucket histogram spanning the whole domain.
  • fixtures/stats/skew_detection.bin — the §8.11 highly-skewed workload, expects the skew flag to fire within the first 100 queries.
  • fixtures/stats/staleness_bound.trace — a sustained-write soak, expects the staleness bound never exceeded.
Pitfalls
  1. Manifestation: router (once wired in Phase 8) reads a stale histogram generation after a newer one was already visible elsewhere. Root cause: generation counter incremented before the new snapshot was fully published (I6 ordering bug). Debug method: replay staleness_bound.trace with a generation-ordering assertion. Signal: stats_generation_regression_total > 0. Recovery: publish the snapshot atomically before bumping the generation counter, never the reverse order.
  2. Manifestation: cardinality-estimation error exceeds 15% on a skewed dataset. Root cause: equal-depth bucketing under-resolves the dense region of a skewed distribution. Debug method: compare bucket boundaries against the known skew profile in skew_detection.bin. Signal: estimation-error benchmark regression. Recovery: trigger a targeted bucket split in the dense region rather than relying on uniform-depth buckets alone.
  3. Manifestation: statistics-collection overhead regresses write throughput by more than 5%. Root cause: bucket-overflow local split (step 3) is triggering too frequently due to an overly tight overflow threshold. Debug method: flamegraph the write hot path under the overhead benchmark. Signal: overhead-benchmark CI regression. Recovery: widen the overflow threshold (the "2x target depth" constant in §8.8) and re-measure.

⬜ Phase 8 — The Cost-Based Access-Path Router §20

Objectives

Implement the cost-based router (Selinger et al. 1979 framing, ADR-07) that selects among B+Tree, ART, cracked column, and full scan using the CostEstimate equations from §8.7, finally closing the loop on ADR-03's cracking-vs-adaptive-merging strategy selection.

Deliverable

A deterministic, statistics-driven cost-based router selecting among all four access paths, closing the loop on adaptive-strategy selection between cracking and adaptive merging.

Acceptance
  • router decision matches the hand-computed §8.7 worked comparison exactly on the reference fixture; workload-adaptation latency <= 3 queries after a workload-shape change (§4); zero I10 violations (cost estimates non-negative and selectivity-monotonic) across 100,000 randomized cost-model property-test cases; router-decision latency < 1% of the chosen path's own estimated cost at p95; zero plan-divergence-auditor firings absent a statistics- generation change across a 24-hour soak.
Fixtures
  • fixtures/router/selectivity_crossover.bin — the exact §8.7 worked comparison (n=10,000,000, selectivity=0.001), expects the documented three cost values and the converged-cracked-scan winning decision.
  • fixtures/router/first_touch_vs_converged.bin — the same predicate evaluated before and after convergence, expects the router to prefer B+Tree pre-convergence and cracked scan post-convergence (§8.7).
  • fixtures/router/workload_shape_switch.trace — a workload that shifts from narrow-shifting to stable-wide mid-stream, expects a strategy switch within 3 queries.
  • fixtures/router/stale_statistics_fallback.bin — statistics artificially aged beyond the staleness bound, expects a conservative full-scan fallback decision.
Pitfalls
  1. Manifestation: router picks the cracked scan on the very first query, before any partitioning has occurred, incurring the full crack overhead unexpectedly. Root cause: crack_overhead(gen) was not correctly weighted for gen = 0 (first touch). Debug method: replay first_touch_vs_converged.bin. Signal: decision mismatch against the §8.7 worked comparison. Recovery: verify the decay function returns the full log2(n) * c_partition term at generation zero.
  2. Manifestation: router flip-flops between two access paths on every query for the same predicate. Root cause: cost-model calibration (step 9) is overcorrecting, causing oscillation rather than convergence. Debug method: plan-divergence auditor triggered with an unchanged statistics generation. Signal: auditor alert with zero generation delta. Recovery: dampen the calibration correction factor (e.g. exponential moving average instead of instantaneous correction).
  3. Manifestation: router continues using stale statistics past the bound. Root cause: the staleness-bound fallback path (step 10) checks the wrong generation field. Debug method: stale_statistics_fallback.bin fixture. Signal: router uses a non-conservative estimate despite staleness. Recovery: gate every cost lookup on an explicit staleness check before consulting the histogram.

⬜ Phase 9 — Concurrency Control for Reorganization §21

Objectives

Replace the coarse interim latching from Phases 5/6 with the full reorganization-concurrency protocol (Graefe et al. 2012, ADR-10) — copy-on-crack piece versioning and the state machine in §8.9 — so that cracking, adaptive merging, and compaction are all correct under concurrent readers without ever violating I9.

Deliverable

A full reorganization-concurrency protocol implementing the §8.9 state machine end to end, verified by a continuous concurrency fuzzer exercising I1, I2, I9, and I13 simultaneously.

Acceptance
  • zero I1/I2/I9/I13 violations across a 24-hour continuous concurrency-fuzzer run with concurrent readers, crackers, mergers, and injected crashes; reader-invalidation total stays at zero (readers always get a consistent view, per I9, never an error); latch-contention bound < 5% of lookup latency at p95 (§4) even during active reorganization; livelock-detector never escalates more than 0.01% of boundary-insert attempts to the serializing fallback.
Fixtures
  • fixtures/concurrency/reader_during_crack.trace — a long-running scan overlapping an active crack on the same piece, expects the reader to complete against a consistent snapshot with zero reader_invalidation_total.
  • fixtures/concurrency/crash_mid_reorg.trace — SIGKILL injected mid-crack and mid-compaction, expects the state machine to land in Abandoned/RecoveryReplay per §8.9 and recover cleanly.
  • fixtures/concurrency/boundary_race.trace — two concurrent crackers targeting overlapping boundaries, expects the CAS-retry loop to resolve without livelock.
  • fixtures/concurrency/fuzzer_24h.trace — the full 24-hour continuous fuzzer run, recorded for deterministic replay on regression.
Pitfalls
  1. Manifestation: a reader observes a torn view mid-crack (some rows from the old piece, some from the new). Root cause: copy-on-crack publish was not atomic — the boundary array and the physical piece data were updated in two separate steps. Debug method: replay reader_during_crack.trace with a torn-read assertion. Signal: I9 violation via reader_invalidation_total (should be zero, a non-zero torn-read count indicates a bug deeper than the expected fallback). Recovery: publish the boundary-array update and the piece-data swap under a single atomic version bump.
  2. Manifestation: livelock on the boundary-race retry loop under high contention. Root cause: the CAS-retry loop had no backoff or escalation bound. Debug method: boundary_race.trace with a retry-count histogram. Signal: boundary_race_retry_total grows unbounded for a single logical operation. Recovery: add exponential backoff and the bounded escalation-to-serializing-latch fallback (step 13).
  3. Manifestation: ConcurrencyToken regresses after a crash-recovery replay. Root cause: RecoveryReplay restored an older token value instead of continuing the monotonic sequence (I13 violation). Debug method: crash_mid_reorg.trace with a token-monotonicity assertion across the restart boundary. Signal: token_regression_total > 0. Recovery: persist the token's high-water mark separately from the reorganization state it protects, and always resume from the high-water mark.

⬜ Phase 10 — Tiered-Storage-Aware Compaction and Hybrid Access §22

Objectives

Implement the tiered-compaction worker (§8.10, ADR-15) and the hybrid OLTP/OLAP access path (ADR-16), moving segments between hot/warm/cold tiers under backpressure (P10) while keeping row-path and scan-path access consistent.

Deliverable

A tiered-compaction worker moving segments under a backpressure-throttled leveled policy, integrated with a hybrid row/scan access path that resolves identically regardless of tier.

Acceptance
  • write amplification < 4x, read amplification < 2.5x (§4), measured on the compaction benchmark harness; zero I12 violations (no tuple loss/duplication) across 10,000 compaction jobs with injected crashes; compaction throughput > 400 MB/s/core (§4); compaction never pushes foreground p99 lookup latency beyond its §4 bound during a sustained backlog (P10); hybrid-access differential test shows zero result divergence across 100,000 row-path vs scan-path query pairs.
Fixtures
  • fixtures/compaction/amplification_measurement.bin — reproduces the §8.10/§34 arithmetic on a live 4-level, fanout-10 configuration, expects measured WA/RA within 10% of the analytical prediction.
  • fixtures/compaction/crash_mid_move.trace — SIGKILL injected mid-tier-move, expects RecoveryReplay to checksum-verify and either resume or roll back per I12.
  • fixtures/compaction/backpressure_throttle.trace — a sustained write burst, expects compaction to yield bandwidth and foreground p99 to stay within §4's bound.
  • fixtures/compaction/hybrid_access_differential.trace — 100,000 row-path/scan-path query pairs across tiers, expects zero result divergence.
Pitfalls
  1. Manifestation: a tuple is duplicated across two tiers after a crash mid-move. Root cause: the source segment was not marked tombstoned until after the target write, but the crash landed between the target write and the tombstone. Debug method: replay crash_mid_move.trace with tuple-count reconciliation. Signal: compaction_tuple_loss_total (used here for duplication too) > 0 (I12). Recovery: use the manifest to make tombstone-then-cleanup idempotent and checksum-gated, replaying to a single authoritative state regardless of crash point.
  2. Manifestation: foreground p99 latency spikes during a compaction backlog burst. Root cause: the backpressure throttle (step 9) measures average latency, not p99, so it fails to react to tail-latency-only degradation. Debug method: backpressure_throttle.trace with p99-specific latency tracking. Signal: §4 p99 bound violated despite the throttle appearing "active" by its own average-latency metric. Recovery: switch the throttle's trigger metric to p99, not average.
  3. Manifestation: read amplification exceeds the 2.5x bound. Root cause: heat-aware tier routing (step 5) falls back to a level-by-level probe whenever statistics are stale, and staleness is more common than expected. Debug method: correlate amplification_measurement.bin regressions with histogram_staleness_seconds (Phase 7). Signal: RA regression co-occurring with staleness alerts. Recovery: tighten the statistics staleness bound specifically for hotness signals feeding compaction routing.

⬜ Phase 11 — The Scan Accelerator, Conformance, and Performance Hardening §23

Objectives

Implement the SIMD scan accelerator (ADR-19, Boncz, Zukowski & Nes 2005) over both cracked columns and row-path batches, then bring the full system through the §28 conformance and §30 performance-hardening gates.

Deliverable

A SIMD-accelerated scan path, a fully aggregated conformance/fuzzing/chaos/soak test suite, and a performance-hardened system meeting every §4 and §30 target simultaneously.

Acceptance
  • SIMD-accelerated scan throughput >= 4x scalar-fallback throughput on a representative predicate benchmark; full conformance suite (all phases' fixtures) green; differential- oracle suite shows zero divergence against DuckDB's ART and PostgreSQL's nbtree on 50,000 shared-workload queries; 72-hour soak test shows zero memory-bloat trend and zero convergence regressions; every §4 constraint and every §30 M-table target met simultaneously under a combined workload.
Fixtures
  • fixtures/scan/simd_vs_scalar.bin — a representative predicate benchmark, expects >= 4x SIMD speedup.
  • fixtures/scan/differential_duckdb_postgres.trace — 50,000 shared-workload queries diffed against DuckDB's ART and PostgreSQL's nbtree, expects zero result divergence.
  • fixtures/scan/soak_72h.trace — the 72-hour adversarial soak, expects zero memory-bloat trend (bounded RSS growth) and zero convergence regressions.
  • fixtures/scan/end_to_end_latency.bin — the full router-to-storage path under combined point-lookup/range-scan/hybrid-access load, expects every §4 latency target met simultaneously.
Pitfalls
  1. Manifestation: SIMD-accelerated scan produces a different result than the scalar path on a boundary predicate. Root cause: vectorized comparison used a different rounding or truncation rule than the scalar comparator for a boundary-adjacent value. Debug method: simd_vs_scalar.bin differential replay isolating the boundary value. Signal: result divergence at exactly the predicate boundary. Recovery: align the SIMD lane comparison semantics exactly with the scalar comparator, including boundary inclusivity.
  2. Manifestation: the 72-hour soak shows slow, steady memory growth. Root cause: a compaction-manifest or cracker-boundary-array leak that is amortized-invisible at short timescales. Debug method: RSS-trend analysis over the full 72-hour window with periodic heap snapshots. Signal: soak_72h.trace memory-bloat trend detector fires. Recovery: bisect the soak into per-subsystem isolation runs (cracker-only, compaction-only) to localize the leak.
  3. Manifestation: end-to-end latency benchmark meets every per-component target individually but still misses the combined p99. Root cause: tail-latency correlation across components (e.g. a GC-like pause in the statistics bucket-split coinciding with a compaction tier move) that no single-component benchmark exposes. Debug method: run the combined-workload benchmark with per-component tracing spans correlated by request ID. Signal: end_to_end_latency.bin p99 miss despite all component-level benchmarks passing. Recovery: stagger background work (statistics recompute, compaction) to avoid correlated tail-latency spikes.
