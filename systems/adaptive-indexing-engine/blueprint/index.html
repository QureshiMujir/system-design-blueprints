1. Goal & Scope

1.1 System Definition

The Adaptive Indexing Engine (AIE) is a storage-engine-adjacent indexing subsystem, written in Rust, that provides secondary access methods whose physical layout refines incrementally as a side effect of query execution rather than being built up front. AIE integrates with a host OLTP or OLAP engine through a narrow access-method interface and provides four cooperating mechanisms: a latch-coupled B+Tree for ordered range access, an Adaptive Radix Tree (ART) for main-memory point access, a database-cracking / adaptive-merging engine that performs online physical reorganization of a column in response to observed predicates, and a cost-based router that chooses among these paths and a full scan per query using calibrated cost estimates. The intellectual core of the project is adaptive indexing in the sense of Idreos, Kersten & Manegold 2007 and Graefe & Kuno 2010: index refinement is paid for only in the ranges the workload actually touches, never eagerly.

1.2 Phase-0 Deliverable — Crate List

  1. aie-core — shared primitives: IndexId, Key, Rid, error taxonomy.
  2. aie-access — the AccessMethod trait, AccessPath, protocol boundary to the host engine.
  3. aie-btree — the latch-coupled B+Tree engine with prefix compression.
  4. aie-art — the Adaptive Radix Tree engine with path/lazy-expansion compression.
  5. aie-cracker — database cracking and adaptive merging (the reorganization engine).
  6. aie-stats — histograms, sketches, incremental statistics collection.
  7. aie-router — the cost-based access-path router.
  8. aie-concurrency — latching, optimistic lock coupling, and reorganization concurrency tokens.
  9. aie-storage — buffer pool and durable page/segment storage manager.
  10. aie-compaction — tiered-storage-aware compaction worker.
  11. aie-scan — the SIMD scan accelerator runtime.
  12. aie-telemetry — metrics, tracing, structured logging.
  13. aie-cli — operator command-line tool.
  14. aie-conformance — fixture-driven conformance harness (H1–H20-style gates for the code phase).
  15. aie-fuzz — fuzz targets for the metadata parser and key encoders.
  16. aie-bench — benchmarks, including the convergence benchmark.

1.3 Boundaries

Provides: access-method registration, point lookup, range scan, insert/update/delete routing, adaptive reorganization, statistics collection, cost-based path selection, tiered compaction, concurrency control for reorganization, durability of persisted structures.

Delegates to the host engine: transaction management and isolation semantics, SQL parsing and planning above the access-method boundary, authentication/authorization, distributed consensus, client protocol termination. AIE exposes an access-method interface, not a database front end — it is an indexing subsystem, not a full database.

Does NOT provide: a SQL parser, a distributed transaction coordinator, MVCC across tables, a network wire protocol, a BI/reporting layer, object-storage implementation (it integrates with one).

1.4 Non-Goals

Building a general-purpose database; implementing distributed consensus; implementing a full learned-index model (see §36.4, deferred); replacing the host engine's transaction manager; providing a client-facing query language.

1.5 Deployment Model

Two supported deployment models: (1) an embeddable library linked directly into a host OLTP or OLAP engine, sharing its process and buffer memory; (2) an optional standalone index service exposed over a local RPC boundary for engines that cannot embed a Rust library directly. Both models share the same AccessMethod trait (§11); the standalone service is a thin RPC shim over the embedded core.

1.6 Users & Operators

Developers: storage-engine implementers, query-planner engineers integrating a new access path. Operators: database SREs responsible for index health, convergence, and compaction backlog. Researchers: adaptive-indexing and access-method researchers validating cracking and adaptive-merging behavior against the reference papers.

1.7 Later-Phase Unlocks

Completing Phase 11 (§23) unlocks: cross-engine index federation, GPU-assisted vectorized scans, a learned-index access path evaluated against ART/B+Tree on stable workloads, and cross-tier replication of compacted segments. These are explicitly deferred, not built.

1.8 Language Choice & Rejected Alternatives

Primary implementation language: Rust (stable channel). Rationale: deterministic ownership eliminates a whole class of concurrency bugs in a project whose hardest problem is concurrent reorganization (P3); explicit unsafe boundaries make the ART node-pointer tricks auditable; zero-cost abstractions keep the B+Tree/ART hot paths competitive with C++ reference implementations (DuckDB, PostgreSQL).

Language Rejection Reason
C++ manual memory management risk in exactly the pointer-heavy ART/B+Tree code this project depends on

1.9 Prerequisites

Lock-free and latch-based concurrent programming; B+Tree and trie internals; cache-line and NUMA-aware data-structure design; cost-based query optimization fundamentals (Selinger et al. 1979); SIMD programming; the database-cracking and RUM-conjecture literature (§5).

1.10 Timeline

Phase 0: 3 weeks. Phases 1–11: 4–8 weeks each depending on concurrency complexity. Full system: 12–16 months for a single engineer at blueprint-conformance depth.

2. Why Build This

  • adaptive indexing sits at the intersection of storage engines, query optimizers, and workload observability — it is the rare systems project that is simultaneously a data structures problem and a concurrency problem
  • database cracking and adaptive merging are the load-bearing ideas behind modern main-memory analytical engines (MonetDB's cracking origin, DuckDB's ART, HyPer's hybrid execution)
  • the Adaptive Radix Tree is the dominant main-memory point-index structure in production analytical engines today (Leis, Kemper & Neumann 2013)
  • concurrency control for a self-reorganizing structure is one of the least-taught, highest-value systems problems — most engineers only ever touch static structures
  • the RUM conjecture (Athanassoulis et al. 2016) gives a rigorous vocabulary for every index tradeoff an engineer will ever make
  • cost-based access-path routing is the same intellectual core as a SQL optimizer's access-path selection (Selinger et al. 1979), at smaller scale and lower blast radius
  • tiered-storage compaction connects this project to the LSM/RocksDB world without requiring a full LSM implementation
  • historically, adaptive indexing emerged because static index build cost is wasted on unpredictable or exploratory workloads — the motivating observation of Idreos, Kersten & Manegold 2007

What Mastery Looks Like

  • can derive the O(n log n) amortized cracking bound and explain why the first query costs O(n) while convergence spreads the sort across O(log n) touches (Phase 5, §17)
  • can implement latch coupling correctly enough that a structural verifier finds zero violations under concurrent stress (Phase 1, §13)
  • can build ART's four node types and reason about the adaptive-growth hysteresis without triggering growth/shrink thrashing (Phase 3, §15)
  • can demonstrate the cracking-versus-adaptive-merging tradeoff with a measured convergence benchmark on a skewed workload (Phase 6, §18)
  • can build a cost model whose router decisions match a hand-computed selectivity crossover (Phase 8, §20)
  • can defend a specific structure choice under a specific workload using RUM-conjecture vocabulary rather than intuition (Phase 7, §19)
  • can design and verify a reorganization concurrency protocol that never violates tuple-multiset preservation under fuzzed concurrent readers (Phase 9, §21)
  • can connect adaptive indexing to tiered storage and hybrid OLTP/OLAP access, and explain precisely where RocksDB's compaction model contrasts (Phase 10, §22)

Access-Method Interface. The single protocol boundary to the host engine; every request (lookup, scan, mutate) enters here as a Predicate and leaves as an AccessPath result. It owns no state of its own and is where request validation and backpressure (ADR-29) live.

Cost-Based Router. Consults the Statistics Collector for the current generation and consults each candidate engine's CostEstimate before choosing a path (P2); its decisions are deterministic given inputs and are themselves emitted as telemetry.

Statistics Collector. Owns histograms and sketches, updated incrementally on the write path (ADR-09) and consulted, never blocked on, by the router; staleness is a bounded, visible quantity (P9, I6).

B+Tree Engine. Provides ordered range access with latch coupling (P7) and prefix compression; the default path for wide-range, update-heavy workloads.

ART Engine. Provides point-lookup-optimized access via adaptive radix nodes with path compression; the default path for sparse, point-lookup-heavy workloads.

Cracking / Adaptive Reorg Engine. The load-bearing subsystem: performs in-place partitioning (cracking) or run-merging (adaptive merging) as a side effect of query execution, never as a standalone job (P1), and is the only engine whose physical layout changes without an explicit build step.

Concurrency-Control Layer. Owns latches, optimistic lock coupling tokens, and the copy-on-crack versioning that lets reorganization proceed without invalidating active readers (P3, I9); every other engine calls through it rather than implementing its own locking.

Scan Accelerator. SIMD-vectorized predicate evaluation over both cracked columns and raw row batches; consumes ScanBatch units from the storage manager.

Buffer / Storage Manager. The persistence boundary: page/segment caching, eviction, and durable writes; every structure above it is volatile until it flushes through here.

Tiered-Compaction Worker. Moves segments between hot/warm/cold storage tiers under a backpressure-throttled, leveled-compaction policy (ADR-15), never competing unbounded with foreground queries (P10).

6. Design Principles

P1 — Refinement Is a Side Effect of Querying. Rule: index refinement (cracking/merging) happens only as a byproduct of query execution, never as a standalone background job. Tradeoff: workload-blind ranges stay unrefined, possibly forever. Operational implication: operators cannot "pre-warm" an index without issuing representative queries. Violating this breaks the system: a background "auto-crack-everything" job converts adaptive indexing into eager up-front building with none of its workload-selectivity benefit.

P2 — Every Access Path Carries a Cost Estimate. Rule: the router selects among B+Tree, ART, cracked column, and full scan strictly by comparative CostEstimate, never by a fixed rule of thumb. Tradeoff: cost-model errors misroute queries. Operational implication: the cost model must be recalibrated per deployment. Violating this breaks the system: hard-coded routing rules ignore workload and statistics drift and silently degrade to worst case.

P3 — Concurrency for Reorganization Is the Hard Problem. Rule: any reorganization that moves tuples (a crack, a merge, a compaction) must be correct under concurrent readers via latching or logical versioning, never best-effort. Tradeoff: adds concurrency-control overhead to every reorganization step. Operational implication: reorganization throughput is bounded by protocol cost, not raw IO. Violating this breaks the system: unsynchronized reorganization corrupts the tuple multiset (I1) under any concurrent reader.

P4 — Tuple-Multiset Preservation Is Non-Negotiable. Rule: no reorganization step may ever lose, duplicate, or corrupt a row, under any interruption. Tradeoff: every reorg step needs a rollback/verification path, adding latency. Operational implication: a crash mid-crack must be safe to abandon (ADR-14). Violating this breaks the system: a lost row after a crash mid-crack is a silent correctness bug indistinguishable from application data loss.

P5 — The RUM Conjecture Governs Every Structure Choice. Rule: no structure simultaneously optimizes read, update, and memory; an explicit choice among the three is made per access path. Tradeoff: ART's read speed trades against memory; a B+Tree's balanced update trades against ART's raw point-read throughput. Operational implication: operators must know which corner of the RUM triangle each index is tuned for. Violating this breaks the system: assuming one structure "wins on everything" leads to mis-provisioned memory or missed SLOs.

P6 — Cracking Pays Only Where the Workload Looks. Rule: a crack partitions exactly the value range touched by the query predicate, no more. Tradeoff: unrelated ranges remain unrefined and cost full-scan speed until touched. Operational implication: convergence is workload-shaped, not uniform. Violating this breaks the system: cracking a wider range than the predicate wastes CPU proportional to the unused span and pollutes cache with irrelevant data.

P7 — Latch Coupling Is a Correctness Protocol, Not an Optimization. Rule: B+Tree descent holds parent and child latches simultaneously across the handoff, releasing the parent only once the child is safely acquired (Lehman & Yao 1981). Tradeoff: increases instantaneous latch pressure. Operational implication: latch-contention telemetry (I5) must be tracked continuously. Violating this breaks the system: releasing the parent early permits a concurrent split to strand a traverser at a stale separator.

P8 — Adaptive Radix Growth Must Be Reversible and Cache-Aware. Rule: ART nodes grow (Node4→16→48→256) and shrink strictly by fill-factor thresholds, never by insertion order alone. Tradeoff: growth/shrink hysteresis adds bookkeeping. Operational implication: node_type_distribution telemetry must be watched for pathological growth churn. Violating this breaks the system: growing on every insert without hysteresis thrashes cache lines and allocator pools.

P9 — Statistics Must Never Lie About Their Own Age. Rule: every statistics snapshot carries an explicit generation/staleness bound the router can consult (I6). Tradeoff: plans occasionally use a conservative fallback cost when statistics are stale. Operational implication: statistics-staleness alerts gate planner trust. Violating this breaks the system: a planner trusting arbitrarily stale statistics silently degrades to bad plans with no operator signal.

P10 — Compaction Must Never Compete Unbounded With Foreground Queries. Rule: tiered-compaction throughput is throttled by a backpressure signal tied to foreground latency budgets. Tradeoff: compaction backlog can grow under sustained write pressure. Operational implication: compaction_backlog telemetry must carry an explicit SLO. Violating this breaks the system: unthrottled compaction starves point-lookup latency exactly when the system is busiest.

P11 — Convergence Is Monotonic or the Algorithm Is Wrong. Rule: every crack or merge step strictly reduces or holds constant the expected future cost of the touched range (I11). Tradeoff: some crack heuristics trade convergence speed for simplicity. Operational implication: the convergence benchmark (§28) is a release gate, not an optional check. Violating this breaks the system: a non-monotonic cracker can oscillate forever, burning CPU without ever reaching the fully-refined state Idreos et al. 2011 characterize.

P12 — Adaptive Merging Trades First-Query Latency for Faster Convergence. Rule: when the router detects a stable, wide-range workload it prefers adaptive merging over cracking, accepting a higher first-query cost for fewer total queries-to-refinement (Graefe & Kuno 2010). Tradeoff: adaptive merging's up-front merge step is O(n log k) versus cracking's cheaper first touch. Operational implication: the router's strategy choice (ADR-03) must be visible in telemetry as a named decision, not implicit. Violating this breaks the system: applying adaptive merging to a genuinely unpredictable workload wastes the first-query cost cracking was designed to avoid.

P13 — Every Persisted Structure Is Versioned, Every Ephemeral One Is Rebuildable. Rule: on-disk formats (B+Tree pages, ART snapshots, statistics) carry an explicit layout_version; cracker piece state, being ephemeral by ADR-13/ADR-14, is either checkpointed explicitly or reconstructed lazily from base data on restart. Tradeoff: lazy reconstruction re-pays convergence cost after every crash. Operational implication: RTO for an adaptively-built index includes re-convergence time, not just base-data recovery time. Violating this breaks the system: silently persisting cracker state without versioning makes a format change an unrecoverable upgrade hazard.

8. Domain Model

8.1 Database Cracking — Named Steps

  • C1 — Receive predicate. A range predicate lo <= x < hi arrives on column C.
  • C2 — Locate bracketing pieces. Find pieces P_i, P_j in the CrackerIndex whose boundaries bracket lo and hi.
  • C3 — Partition at lo. In-place three-way (Hoare-style) partition of P_i around lo, producing P_i_low (< lo) and P_i_high (>= lo).
  • C4 — Partition at hi. Partition P_j around hi similarly, producing P_j_low (< hi) and P_j_high (>= hi).
  • C5 — Insert boundaries. Insert lo and hi into the sorted boundary array — O(p) where p = current piece count.
  • C6 — Return contiguous run. The now-contiguous sub-range [lo, hi) is returned directly as the scan result — no further sort is required for this exact range again.

Worked example. Column C holds 1,000,000 unsorted values in one piece [.,.). Query 1: C >= 200000 AND C < 400000. Cracking at 200000 and 400000 yields three pieces: [.,200000), [200000,400000), [400000,.). Cost: one O(n) partition pass, n = 1,000,000. Query 2: C >= 250000 AND C < 300000 lands entirely inside the ~200,000-element piece from query 1. Cracking again at 250000 and 300000 subdivides only that piece — cost O(200,000), not O(1,000,000). Each subsequent query in the same neighborhood touches an exponentially smaller piece (P6, P11), converging toward full refinement in O(log n) touches.

8.3 Adaptive Merging — Named Steps and Contrast with Cracking

  • M1 — Initial run split. Partition the column into k sorted runs (one merge pass).
  • M2 — Identify overlapping runs. On a range query, find runs overlapping [lo, hi).
  • M3 — Partial merge. Merge only the overlapping runs within [lo, hi), producing one run for that sub-range.
  • M4 — Update run index. Replace the merged runs' entries in the RunIndex with the new single run.
  • M5 — Repeat. Subsequent queries touching the same region find fewer, larger runs, until one fully sorted run remains for the touched range (Graefe & Kuno 2010).
Dimension Cracking Adaptive Merging
first-query cost O(n) in-place partition O(n log k) partial merge, higher constant
convergence speed (queries to refine a range) O(log n) cracks, cheap per step fewer queries, each costlier
physical operation in-place swap, not stable run merge, stable, more copying
memory overhead boundary array, O(p) run metadata, O(k)
best-fit workload unpredictable, narrow, shifting ranges stable, wide, repeated ranges
convergence character lazy (P1, P6) eager relative to cracking (P12)

8.4 The RUM Conjecture Framing

The RUM conjecture (Athanassoulis et al. 2016) states that no access method minimizes Read overhead, Update overhead, and Memory overhead simultaneously; improving two forces the third to grow. Framed per structure:

Structure Read (R) Update (U) Memory (M)
B+Tree good (logarithmic) good (in-place, amortized splits) moderate (overflow/fill-factor slack)
ART best (key-length bounded, cache-friendly) moderate (node growth/shrink cost) worst (pointer-heavy nodes, P8)
cracked column best after convergence, worst before cheap (append, lazy re-crack) best (no extra structure, just boundaries)
LSM (contrast, §36.3) worst (read amplification across levels) best (append-only) moderate (write-amplified but compact)

Adaptive-node-growth rule (P8): grow Node4→16 on the 5th child; 16→48 on the 17th; 48→256 on the 49th. Shrink is symmetric but hysteresis-gated — a node shrinks only once its fill drops below roughly half the lower tier's capacity, preventing growth/shrink thrashing at the boundary.

Path compression / lazy expansion — worked insert. Insert "10", then "100", then "1000" into an empty ART. Insert "10": a single leaf stores the full path-compressed key "10" with no intermediate nodes (lazy expansion — a unique path needs no branching node). Insert "100": it diverges from "10" at byte position 2 ("10" ends, "100" continues with "0"); this forces expansion — a Node4 is created at the divergence point holding two children: an end-marker leaf for "10" and a continuing leaf for "0". Insert "1000": it diverges further inside "100"'s remaining path, introducing a second Node4 at the new divergence point; the common prefix "10" remains absorbed as the path-compressed prefix on the node above it (I4).

8.7 Cost Model — Display Equations and Worked Comparison

Cost_fullscan            = n * c_scan
Cost_btree_lookup        = c_traverse * log_f(n) + selectivity * n * c_fetch
Cost_cracked_scan(gen)   = touched_piece_size(selectivity, gen) * c_scan + crack_overhead(gen)
crack_overhead(gen)      -> log2(n) * c_partition  as gen -> 0 (first touch)
crack_overhead(gen)      -> 0                      as gen -> converged

Worked comparison. n = 10,000,000 rows, c_scan = 1ns/row, c_fetch = 100ns/row, c_traverse = 50ns, fanout f = 200, selectivity = 0.001 (10,000 matching rows).

  • Cost_fullscan = 10,000,000 * 1ns = 10ms.
  • Cost_btree_lookup = 50ns * log200(10,000,000) ≈ 50ns * 3.1 + 0.001 * 10,000,000 * 100ns ≈ 155ns + 1,000,000ns ≈ 1.0002ms.
  • Cost_cracked_scan (converged) ≈ 10,000 * 1ns = 10µs, crack_overhead ≈ 0.
  • Cost_cracked_scan (first touch) ≈ 10,000 * 1ns + log2(10,000,000) * 1ns * 10,000,000 ≈ dominated by the ≈23ms partition pass.

Router decision: once converged, the cracked scan (10µs) wins over the B+Tree lookup (~1ms) and full scan (10ms); on the very first touch the partition overhead dominates, so the router may still prefer the B+Tree lookup (P2, P11) until convergence is reached.

8.8 Statistics Representation and Incremental-Update Rule

Histogram: equal-depth buckets, bucket i covers [lo_i, hi_i) with count_i. Incremental update rule: on insert of value v, increment the bucket containing v; on bucket overflow (count_i > 2x target depth), locally split that bucket (redistribute only its contents), an amortized O(1) operation per write — never a full histogram recompute (ADR-09).

Sketch: HyperLogLog for cardinality estimation, m = 2^14 registers, standard error ≈ 1.04/√m ≈ 0.8%.

8.10 Tiered-Compaction Model — Amplification Arithmetic

Leveled compaction: level L_i capacity = base_size * fanout^i. Worst-case write amplification WA ≈ fanout * num_levels; for fanout = 10, 4 levels, worst-case WA ≈ 40x, bounded to the < 4x target in §4 by heat-aware skipping of cold levels (only touched levels are rewritten). Worst-case read amplification RA = num_levels if bloom/heat routing misses; bounded to < 2.5x by routing reads directly to the tier the statistics indicate holds the match.

8.11 Malformed / Degenerate Examples

  • Crack on a constant column (all values equal c): the predicate either matches everything or nothing; partitioning would produce a zero-width piece boundary at c — the CrackerIndex must reject a duplicate boundary insert (I3) rather than looping.
  • All-duplicate keys in ART: path compression degenerates to one long chain with no branching; the engine must not allocate a Node256 for a single distinct byte value — it falls back to a leaf carrying a duplicate-key list.
  • Highly-skewed workload defeating convergence: 99% of queries touch a single 0.001%-width range; that range converges immediately, but the router must not "pre-crack" the untouched long tail — doing so violates P6.
  • Concurrent update during a crack: a writer inserts into the exact piece being partitioned; the crack step serializes against the write via the piece latch (the WriterConflict edge implied by §8.9) and either aborts-and-retries or applies the write post-crack against the new boundary.

8.12 Failure-Path Example

A crack on piece P (500,000 elements) begins; partitioning proceeds 60% through; the process receives SIGKILL. On restart, CrackerIndex reload finds P's boundary array unchanged (cracks are not WAL-logged, ADR-13) — P is treated as still fully unrefined at its pre-crack boundaries (ADR-14, lazy recovery). The next query touching P re-executes the crack from scratch. Correctness (I1, I11) is preserved at the cost of repaying the partition once.

  • fixtures/merge/contrast_table.bin — reproduces the §8.3 contrast table's five dimensions as measured numbers on a shared synthetic dataset (n=1,000,000, k=8).
  • fixtures/merge/multiset_differential.trace — 100,000 randomized merge-then-scan sequences diffed against the full-scan oracle.
  • fixtures/merge/single_run_noop.bin — a column with one run, expects M3 to be a true no-op (zero merge_step invocations).
  • fixtures/merge/convergence_stable_wide.bin — a stable, wide-range workload profile, expects adaptive merging to converge in fewer queries than cracking on the same data.

18.6 Pitfalls

  1. Manifestation: runs become unsorted after a partial merge. Root cause: M3's merge step used a non-stable merge, reordering equal-valued elements across run boundaries in a way that broke the disjointness assumption. Debug method: replay multiset_differential.trace with run-order assertions enabled. Signal: run_order_violation_total > 0 (I8). Recovery: use a stable merge algorithm and re-verify disjointness after every merge step.
  2. Manifestation: adaptive merging converges slower than cracking even on a stable wide workload, contradicting P12. Root cause: the workload-shape detector (step 7) is misclassifying the workload as narrow/shifting, so the wrong strategy is compared. Debug method: inspect the detector's classification against the actual query log. Signal: convergence_stable_wide.bin fixture fails its comparative assertion. Recovery: widen the detector's stability window or fix its range-overlap heuristic.
  3. Manifestation: a merge step increases the number of runs overlapping a future query (I11 violation for adaptive merging). Root cause: M3 merged two runs but left a third, still-overlapping run un-merged, and the run-count accounting did not detect the partial coverage. Debug method: convergence-monotonicity assertion after every merge step. Signal: convergence_regression_total > 0. Recovery: ensure M2's overlapping-run identification captures all runs overlapping [lo, hi), not just the first found.

18.7 Performance Concerns

Merge-step copying cost (adaptive merging is not in-place, unlike cracking's swap-based partition); run-metadata bookkeeping cost as k grows; cache behavior of a k-way merge versus cracking's two-way partition.

18.8 Edge Cases

A single-run column (already-merged, M3 must no-op); a query whose range spans zero runs (empty result, no merge triggered); a query range that exactly equals one existing run's bounds (no merge needed, direct return).

18.9 Failure Analysis

A convergence-comparison report showing adaptive merging losing to cracking on every workload profile (not just narrow ones) indicates a bug in the merge step itself, not merely a misclassified workload — distinguished by checking the contrast_table.bin fixture's raw first-query-cost numbers against the O(n log k) prediction independent of the workload-shape detector.

18.10 Operational Notes

Track run_count, merge_step_duration_ns, and the workload-shape classification decision as a named telemetry field (reorg_strategy_selected) so operators can audit why a given column is using cracking versus adaptive merging before Phase 8 makes that choice fully automatic.

20.1 Objectives

Implement the cost-based router (Selinger et al. 1979 framing, ADR-07) that selects among B+Tree, ART, cracked column, and full scan using the CostEstimate equations from §8.7, finally closing the loop on ADR-03's cracking-vs-adaptive-merging strategy selection.

20.2 Detailed Implementation Steps

  1. Implement CostEstimate construction per §11 for each AccessPath variant.
  2. Implement Cost_fullscan, Cost_btree_lookup, Cost_cracked_scan per the display equations in §8.7, parameterized by live statistics from Phase 7.
  3. Implement the crack_overhead(gen) decay function reflecting the touched piece's refined_generation (P11).
  4. Implement the router's selectivity crossover calculation (worked in §8.7, generalized to any n/selectivity pair) as the core decision function (I10: non-negative, monotonic).
  5. Implement router decision telemetry as a named field (router_decision) recording which AccessPath was chosen and why (the compared cost values), satisfying P2's transparency requirement.
  6. Implement the ADR-03 hybrid-strategy selector: given the workload-shape detector from Phase 6, choose cracking or adaptive merging per column, replacing Phase 6's manual flag, with the P12 strategy-switch decision recorded as reorg_strategy_selected telemetry.
  7. Implement the workload-adaptation-latency measurement (§4: strategy switch within 3 queries of a workload-shape change).
  8. Implement cost-model calibration: periodic comparison of predicted vs actual execution cost, feeding a correction factor (not a full ML model, per ADR-07's rejection of learned routers).
  9. Implement the router's fallback path when statistics are stale beyond the bound (P9): use a conservative full-scan cost estimate rather than trusting a stale one.
  10. Implement plan-explain output (operator-facing, feeds §26) and deterministic replay of router decisions given identical statistics snapshots.
  11. Implement the router's interaction with the concurrency-control layer's coarse latching from Phases 5/6 (full integration lands in Phase 9).
  12. Implement router-decision differential testing against a hand-computed reference decision on the §8.7 worked-comparison fixture, and the matching selectivity-crossover fixture (n=10,000,000, selectivity=0.001).
  13. Implement router regression benchmarks measuring decision latency itself (must not dominate the cost of the chosen path).
  14. Implement the plan-divergence auditor: flag when repeated identical queries produce different routing decisions absent a statistics-generation change (ties to I10/determinism).
  15. Implement fixtures/router/* conformance fixtures and regression-test Phases 1–7's fixtures now routed through the full router.

20.3 Deliverable

A deterministic, statistics-driven cost-based router selecting among all four access paths, closing the loop on adaptive-strategy selection between cracking and adaptive merging.

20.4 Acceptance Criteria

  • router decision matches the hand-computed §8.7 worked comparison exactly on the reference fixture; workload-adaptation latency <= 3 queries after a workload-shape change (§4); zero I10 violations (cost estimates non-negative and selectivity-monotonic) across 100,000 randomized cost-model property-test cases; router-decision latency < 1% of the chosen path's own estimated cost at p95; zero plan-divergence-auditor firings absent a statistics- generation change across a 24-hour soak.

20.5 Conformance Fixtures

  • fixtures/router/selectivity_crossover.bin — the exact §8.7 worked comparison (n=10,000,000, selectivity=0.001), expects the documented three cost values and the converged-cracked-scan winning decision.
  • fixtures/router/first_touch_vs_converged.bin — the same predicate evaluated before and after convergence, expects the router to prefer B+Tree pre-convergence and cracked scan post-convergence (§8.7).
  • fixtures/router/workload_shape_switch.trace — a workload that shifts from narrow-shifting to stable-wide mid-stream, expects a strategy switch within 3 queries.
  • fixtures/router/stale_statistics_fallback.bin — statistics artificially aged beyond the staleness bound, expects a conservative full-scan fallback decision.

20.6 Pitfalls

  1. Manifestation: router picks the cracked scan on the very first query, before any partitioning has occurred, incurring the full crack overhead unexpectedly. Root cause: crack_overhead(gen) was not correctly weighted for gen = 0 (first touch). Debug method: replay first_touch_vs_converged.bin. Signal: decision mismatch against the §8.7 worked comparison. Recovery: verify the decay function returns the full log2(n) * c_partition term at generation zero.
  2. Manifestation: router flip-flops between two access paths on every query for the same predicate. Root cause: cost-model calibration (step 9) is overcorrecting, causing oscillation rather than convergence. Debug method: plan-divergence auditor triggered with an unchanged statistics generation. Signal: auditor alert with zero generation delta. Recovery: dampen the calibration correction factor (e.g. exponential moving average instead of instantaneous correction).
  3. Manifestation: router continues using stale statistics past the bound. Root cause: the staleness-bound fallback path (step 10) checks the wrong generation field. Debug method: stale_statistics_fallback.bin fixture. Signal: router uses a non-conservative estimate despite staleness. Recovery: gate every cost lookup on an explicit staleness check before consulting the histogram.

20.7 Performance Concerns

Cost-model evaluation cost itself (must stay well under the cost of the cheapest candidate path); calibration-feedback contention if many concurrent queries update the correction factor; plan-explain output overhead if enabled in the hot path (should be opt-in).

20.8 Edge Cases

A predicate with selectivity exactly at the crossover point (tie-breaking rule must be deterministic, e.g. prefer the lower-variance path); a column with no statistics yet (cold start, must default to a conservative full-scan estimate); a query touching a piece mid-crack (router must account for partial convergence, not just fully-converged or fully-unconverged).

20.9 Failure Analysis

A router consistently choosing the worst-cost path indicates either a sign error in the cost equations (caught by the I10 monotonicity property test) or a statistics-staleness bug (caught by the stale-statistics fallback fixture) — the two are distinguished by whether the chosen path's own reported cost estimate is itself wrong (equation bug) or whether the cost estimate is stale-data-consistent but simply outdated (staleness bug).

20.10 Operational Notes

Track router_decision distribution per AccessPath, router_decision_latency_ns, workload_adaptation_latency_queries; expose plan-explain output via aie-cli for operator debugging of unexpected routing decisions.

21. Phase 9 — Concurrency Control for Reorganization

21.1 Objectives

Replace the coarse interim latching from Phases 5/6 with the full reorganization-concurrency protocol (Graefe et al. 2012, ADR-10) — copy-on-crack piece versioning and the state machine in §8.9 — so that cracking, adaptive merging, and compaction are all correct under concurrent readers without ever violating I9.

21.2 Detailed Implementation Steps

  1. Implement ConcurrencyToken and Version per §11 as the versioning primitive underlying copy-on-crack isolation (ADR-10).
  2. Implement the full §8.9 state machine: Stable, Cracking, BoundaryInsert, Compacting, RecoveryReplay, Quarantined, with every listed transition and failure edge.
  3. Implement copy-on-crack: a crack step operates on a private copy of the touched piece, published atomically only at BoundaryInsert-Committed.
  4. Implement the ReaderConflict deferral edge: a crack step observing an active long-range reader latch on the touched piece defers rather than blocking indefinitely.
  5. Implement the ConcurrentBoundaryRace retry edge: a CAS failure on the boundary array triggers a re-read-and-reapply loop, bounded to prevent livelock.
  6. Implement reader-side snapshot acquisition: a reader captures a Version at scan start and is guaranteed a consistent (possibly stale) view for the scan's duration (I9).
  7. Implement the CrashMidPartition→Abandoned edge (ADR-14, already established in Phase 5, now formalized under the full state machine) and the CrashMidMove→RecoveryReplay edge for compaction (used fully in Phase 10, transition implemented here).
  8. Implement ConcurrencyToken::bump as strictly monotonic (I13), with the monotonicity assertion as a standing property test.
  9. Implement the concurrency fuzzer: concurrent readers, crackers, mergers, and a fault injector running against the same column, verifying I1/I2/I9/I13 continuously, with reader-invalidation telemetry (reader_invalidation_total) confirmed at zero.
  10. Implement the lock-order audit sampler extending Phase 1's B+Tree lock-order audit to cover reorganization latches (single global order per P7's "correctness protocol" framing).
  11. Implement livelock detection on the ConcurrentBoundaryRace retry loop (bounded retry count with escalation to a full serializing latch as a last resort).
  12. Implement chaos fixtures (concurrent readers during a crack, crash mid-reorganization, feeding §28) with deterministic replay of any captured concurrency-fuzzer trace.
  13. Implement the reorganization concurrency protocol's interaction with the router (Phase 8): the router queries "is this piece currently Cracking/Compacting" for partial-convergence cost adjustment.
  14. Add latch_wait_ns, crack_defer_total, boundary_race_retry_total telemetry.
  15. Implement fixtures/concurrency/* conformance fixtures and regression-test all prior phases' fixtures under the full concurrency protocol, replacing every coarse interim latch.
  16. Document the state machine and every failure edge inline, citing Graefe et al. 2012.

21.3 Deliverable

A full reorganization-concurrency protocol implementing the §8.9 state machine end to end, verified by a continuous concurrency fuzzer exercising I1, I2, I9, and I13 simultaneously.

21.4 Acceptance Criteria

  • zero I1/I2/I9/I13 violations across a 24-hour continuous concurrency-fuzzer run with concurrent readers, crackers, mergers, and injected crashes; reader-invalidation total stays at zero (readers always get a consistent view, per I9, never an error); latch-contention bound < 5% of lookup latency at p95 (§4) even during active reorganization; livelock-detector never escalates more than 0.01% of boundary-insert attempts to the serializing fallback.

21.5 Conformance Fixtures

  • fixtures/concurrency/reader_during_crack.trace — a long-running scan overlapping an active crack on the same piece, expects the reader to complete against a consistent snapshot with zero reader_invalidation_total.
  • fixtures/concurrency/crash_mid_reorg.trace — SIGKILL injected mid-crack and mid-compaction, expects the state machine to land in Abandoned/RecoveryReplay per §8.9 and recover cleanly.
  • fixtures/concurrency/boundary_race.trace — two concurrent crackers targeting overlapping boundaries, expects the CAS-retry loop to resolve without livelock.
  • fixtures/concurrency/fuzzer_24h.trace — the full 24-hour continuous fuzzer run, recorded for deterministic replay on regression.

21.6 Pitfalls

  1. Manifestation: a reader observes a torn view mid-crack (some rows from the old piece, some from the new). Root cause: copy-on-crack publish was not atomic — the boundary array and the physical piece data were updated in two separate steps. Debug method: replay reader_during_crack.trace with a torn-read assertion. Signal: I9 violation via reader_invalidation_total (should be zero, a non-zero torn-read count indicates a bug deeper than the expected fallback). Recovery: publish the boundary-array update and the piece-data swap under a single atomic version bump.
  2. Manifestation: livelock on the boundary-race retry loop under high contention. Root cause: the CAS-retry loop had no backoff or escalation bound. Debug method: boundary_race.trace with a retry-count histogram. Signal: boundary_race_retry_total grows unbounded for a single logical operation. Recovery: add exponential backoff and the bounded escalation-to-serializing-latch fallback (step 13).
  3. Manifestation: ConcurrencyToken regresses after a crash-recovery replay. Root cause: RecoveryReplay restored an older token value instead of continuing the monotonic sequence (I13 violation). Debug method: crash_mid_reorg.trace with a token-monotonicity assertion across the restart boundary. Signal: token_regression_total > 0. Recovery: persist the token's high-water mark separately from the reorganization state it protects, and always resume from the high-water mark.

21.7 Performance Concerns

Copy-on-crack's extra memory allocation for the private piece copy; version-counter contention under high concurrent reader volume; backoff-loop CPU cost under sustained boundary races.

21.8 Edge Cases

A reader whose scan spans a piece boundary that is being inserted concurrently (must see either the fully-old or fully-new boundary set, never a partial one); a crash during RecoveryReplay itself (must be idempotent — replaying the replay must be safe); a crack and a compaction targeting the same piece simultaneously (must serialize via the state machine, not silently interleave).

21.9 Failure Analysis

A non-zero reader_invalidation_total under the intended fallback design (I9 allows a reader to fall back and retry, which is expected and non-zero in some designs) must be distinguished from an actual torn-read bug by checking whether the fallback retry itself produces a correct result — the fixture reader_during_crack.trace asserts the final result is always correct even if a fallback occurred, while a torn-read bug produces an incorrect final result.

21.10 Operational Notes

Track reader_invalidation_total, crack_defer_total, boundary_race_retry_total, latch_wait_ns_p95; the docs/runbooks/reorg-corruption.md and docs/runbooks/latch-contention.md runbooks (§26) are the primary operator references for this phase's failure modes.

23.6 Pitfalls

  1. Manifestation: SIMD-accelerated scan produces a different result than the scalar path on a boundary predicate. Root cause: vectorized comparison used a different rounding or truncation rule than the scalar comparator for a boundary-adjacent value. Debug method: simd_vs_scalar.bin differential replay isolating the boundary value. Signal: result divergence at exactly the predicate boundary. Recovery: align the SIMD lane comparison semantics exactly with the scalar comparator, including boundary inclusivity.
  2. Manifestation: the 72-hour soak shows slow, steady memory growth. Root cause: a compaction-manifest or cracker-boundary-array leak that is amortized-invisible at short timescales. Debug method: RSS-trend analysis over the full 72-hour window with periodic heap snapshots. Signal: soak_72h.trace memory-bloat trend detector fires. Recovery: bisect the soak into per-subsystem isolation runs (cracker-only, compaction-only) to localize the leak.
  3. Manifestation: end-to-end latency benchmark meets every per-component target individually but still misses the combined p99. Root cause: tail-latency correlation across components (e.g. a GC-like pause in the statistics bucket-split coinciding with a compaction tier move) that no single-component benchmark exposes. Debug method: run the combined-workload benchmark with per-component tracing spans correlated by request ID. Signal: end_to_end_latency.bin p99 miss despite all component-level benchmarks passing. Recovery: stagger background work (statistics recompute, compaction) to avoid correlated tail-latency spikes.

23.7 Performance Concerns

SIMD lane-width mismatches across target architectures (AVX2 vs NEON); prefetch-distance tuning sensitivity to access pattern; combined-workload resource contention not visible in isolated per-phase benchmarks.

23.8 Edge Cases

A predicate that cannot be vectorized (e.g. a complex multi-column expression delegated by the host engine, out of this project's boundary per §1.3, but the scan accelerator must degrade gracefully to scalar evaluation rather than error); a ScanBatch smaller than one SIMD lane width; a soak workload that itself triggers every degenerate case in §8.11 simultaneously.

23.9 Failure Analysis

A perf-regression-gate failure that appears only under the combined workload (not any single phase's isolated benchmark) is triaged via the correlated-tracing method in pitfall 3 above, since it is definitionally a cross-subsystem interaction the per-phase gates cannot catch.

27. Compatibility & Versioning

On-disk index format versioning. Every persisted structure (B+Tree pages, ART snapshots, statistics snapshots, compaction manifests) carries an explicit layout_version field (§11, P13). A persisted adaptive index's cracker/adaptive-merge state is, per ADR-13/ADR-14, not independently versioned — it is either absent (lazy rebuild) or represented purely as a piece-boundary checkpoint carrying the same layout_version as the column it partitions.

Access-method interface stability. The AccessMethod trait (§11) is additive-only across minor versions; a breaking signature change requires a major version bump and a migration note in CHANGELOG.md.

Statistics format migration. A layout_version bump to the histogram/sketch format triggers a one-time background recompute (the ADR-09 fallback path) rather than an in-place migration, since statistics are inherently reconstructable from base data.

Durability contract for adaptively-built structures. Per ADR-13, a crack or merge step is not individually durable; the durability contract explicitly states that an adaptively-built index's refinement progress is best-effort and may be lost on crash, while the base data and persisted structural checkpoints carry the full durability guarantee of the host engine's storage layer.

API stability, deprecation, SemVer. MAJOR: incompatible on-disk or interface changes. MINOR: additive features (e.g. a new AccessPath variant). PATCH: bug fixes with no format or interface change. Deprecated interface methods carry at least one MINOR version of overlap before removal in the next MAJOR version.

Rolling-upgrade guarantees. A rolling upgrade within the same MAJOR version must tolerate mixed layout_version structures coexisting (older nodes reading newer minor-version-tagged pages as long as the MAJOR version matches); cross-MAJOR-version rolling upgrades are not supported and require an explicit migration window.

31. Scalability Analysis

What stays constant vs grows with Big-O. Cracking amortizes an O(n log n) sort across many O(n)-then-shrinking query-driven partition steps: the first query touching an unrefined range costs O(n) (a full partition of that range), and each subsequent touch of the same neighborhood costs O(remaining piece size), converging to full refinement in O(log n) touches — the total work across all touches sums to O(n log n), identical to a single up-front sort, but spread across the query stream rather than paid before the first query (§8.1, §34). ART lookup cost is bounded by key length, not tree size — a lookup touches at most key_length nodes regardless of how many keys are stored (Leis, Kemper & Neumann 2013). B+Tree lookup is logarithmic in row count, bounded by tree height (log_f(n) for fanout f).

Named bottlenecks in order. (1) latch/version contention on hot pieces/pages under high concurrency (§21.7); (2) cache-line and TLB pressure from ART's pointer-heavy node types at scale (§15.7); (3) compaction backlog growth under sustained write pressure exceeding the backpressure throttle's headroom (§22.7); (4) statistics bucket-split contention under extremely skewed, high-throughput writes (§19.7).

The convergence-versus-adaptivity tradeoff at scale. As n grows, cracking's first-touch cost grows linearly, making the very first query on a large unrefined range increasingly expensive even though the amortized total remains O(n log n); at very large n this motivates either a hybrid up-front partial build (deferred, §36.2) or preferring adaptive merging (P12) for workloads known to be stable and wide from the start.

Concurrency scaling limits under reorganization. Copy-on-crack isolation (§21) bounds the private-copy memory overhead per concurrent crack; beyond a small number of simultaneous in-flight reorganizations per column, the ConcurrentBoundaryRace retry rate (§21.6) begins to dominate, motivating the bounded escalation-to-serializing-latch fallback as the practical scaling ceiling for concurrent reorganization of a single column.

Practical ceilings and levers beyond them. Data-size ceiling: per-node memory targets (§4, M5/M6) bound the practical single-node index size to roughly the per-entry memory budget times available RAM; beyond that, tiered compaction (§22) and cross-tier routing are the primary lever. Workload-skew ceiling: an adversarial, ever-shifting-range workload (T2) defeats convergence by design; the piece-count-blowup guard (T1) and the deferred learned-index alternative (§36.4) are the levers beyond that ceiling. Distributed scale beyond a single node is explicitly deferred (PhaseDeferred("§31 Scalability Analysis — distributed index federation")), delegated to future cross-engine federation.

32. Mental Models & First Principles

MM1 — An adaptive index is a sorting algorithm amortized across the query stream. Insight: cracking pays for the sort only in the ranges the workload actually touches, never for the rest. What it predicts: total cost across all queries converges to the same O(n log n) a full sort would cost, but distributed unevenly, front-loaded on whichever ranges are queried first. Bug class without it: engineers "optimize" cracking by pre-sorting untouched ranges, silently reintroducing the up-front cost adaptive indexing exists to avoid. Resolving §17, §34.

MM2 — The RUM conjecture says you cannot optimize reads, updates, and memory simultaneously. Insight: every index decision is a choice of which of the three to sacrifice. What it predicts: any structure claiming to dominate on all three is either lying or has moved the cost somewhere unmeasured. Bug class without it: choosing ART everywhere without accounting for its memory cost (P5), or B+Tree everywhere without accounting for its point-lookup cost relative to ART. Resolving §8.4, §9.

MM3 — Cracking turns index maintenance from an up-front cost into an on-demand cost, which only wins when the workload is unpredictable. Insight: the entire value proposition collapses if the workload is actually stable and fully known in advance. What it predicts: on a stable, wide-range, repeated workload, adaptive merging (or even up-front build) beats cracking. Bug class without it: applying cracking universally regardless of workload shape, losing to a classical up-front index on predictable workloads. Resolving §18, P12, §36.1.

MM4 — Latch coupling is a correctness protocol, not a performance optimization. Insight: its purpose is preventing a reader from landing on a structure a concurrent writer has partially modified, not making traversal faster. What it predicts: removing latch coupling "for speed" reintroduces exactly the phantom-traversal bug it was designed to prevent (I5). Bug class without it: subtle, rare, hard-to-reproduce corruption under concurrent split/reader races. Resolving §13, P7.

MM5 — Convergence must be monotonic or the whole algorithm is unsound. Insight: if a crack or merge step can ever increase future cost, there is no guarantee the index ever reaches a useful state, no matter how many queries run. What it predicts: a convergence benchmark that plateaus or regresses indicates an algorithmic bug, not just a performance quirk. Bug class without it: silent, permanent performance degradation that looks like "the index just isn't helping," undiagnosable without the monotonicity framing. Resolving I11, P11, §17, §18.

MM6 — Every access path's cost estimate is a bet, and the router is the bookmaker, not the oracle. Insight: the cost model can be wrong, and the system must degrade gracefully (to a conservative estimate) when its inputs (statistics) are stale, rather than trusting the bet blindly. What it predicts: a system with perfect cost equations but stale statistics still misroutes; the fix is staleness-awareness, not a better equation. Bug class without it: chasing cost-model precision while ignoring the much larger error introduced by stale inputs. Resolving §20, P9.

MM7 — A crash during reorganization must be a safe no-op, not a half-finished state. Insight: because reorganization is not individually logged (ADR-13), the system must treat any unconfirmed reorganization step as if it never started. What it predicts: recovery logic that tries to "resume" a partial crack, rather than discarding it, will eventually corrupt state under an adversarial crash timing. Bug class without it: crash-timing-dependent corruption that only reproduces under specific interrupt points. Resolving ADR-14, §8.12, §21.

MM8 — Node growth without hysteresis is cache thrashing in disguise. Insight: a data structure that grows and shrinks at the exact same threshold will oscillate under any workload that hovers near that threshold. What it predicts: apparently "correct" adaptive growth logic that nonetheless burns CPU and fragments the allocator under realistic, noisy insert/delete patterns. Bug class without it: intermittent performance regressions that vanish under synthetic, non-noisy benchmarks and only appear in production. Resolving P8, §15.

MonetDB is the historical home of database cracking (Idreos, Kersten & Manegold 2007): it made the case that an index need not exist before the first query touches its range, and it wins precisely on exploratory, unpredictable analytical workloads where building any index up front is wasted work relative to the queries actually issued.

DuckDB chose an up-front-built ART for its embedded point-lookup and zone-map path, trading away cracking's adaptivity for the simplicity and predictability of a structure that is always fully built — it wins whenever the embedding scenario values predictable performance over adaptivity to an unknown workload.

PostgreSQL committed to the classical latch-coupled B+Tree (Lehman & Yao 1981 lineage) integrated with full MVCC, prioritizing general-purpose correctness and decades of operational maturity over adaptivity — it wins whenever workload predictability is irrelevant because the index is simply always needed.

HyPer integrates hybrid OLTP/OLAP access via chunked columnar transitions under MVCC snapshots rather than adaptive indexing per se — it wins when the dominant problem is isolating OLTP freshness from OLAP scan throughput, a different axis from this project's adaptive-indexing focus.

RocksDB trades read amplification for write throughput via LSM compaction, a fundamentally different point in the RUM triangle (§8.4) than any of the above — it wins on write-heavy, point-lookup-secondary workloads and serves in this project purely as the tiered-compaction contrast (§22, §36.3), not as an index-structure model.

34. Back-of-Envelope Capacity Model

1. Cracking convergence cost for n = 10,000,000. Full sort: n log2(n) ≈ 10,000,000 * 23.25 ≈ 232,500,000 comparisons. Spread across roughly log2(n) ≈ 23 cracks per fully-refined range, each crack costing roughly n/2^k comparisons at depth k: first crack ≈ 10,000,000, second ≈ 5,000,000, … summing geometrically to ≈ 2n ≈ 20,000,000 comparisons for one range's full refinement — far less than the full n log n if only one range is ever queried, converging toward the full n log n total only if every range in the domain is eventually queried.

2. ART memory per key vs B+Tree. For a synthetic key set producing a mixed distribution of 30% Node4, 40% Node16, 20% Node48, 10% Node256 (typical for skewed string keys): average bytes per node ≈ 0.336 + 0.4144 + 0.2640 + 0.12048 ≈ 10.8 + 57.6 + 128 + 204.8 ≈ 401.2B per internal node, amortized over an average fanout of roughly 8 keys per internal node ≈ 50B/key — consistent with the < 52B target (§4, M6). A B+Tree with 16KB pages and ~200 keys/page at ~24B/key overhead (separator + pointer, prefix-compressed) is denser per key but pays a fixed page-fill-factor tax (~70% typical fill) that ART's per-key pointer layout avoids.

3. Scan speed on a cracked vs uncracked column after k cracks. After k cracks touching a specific range, the fraction of the column still requiring a full scan for a query in that range shrinks geometrically: fraction touched ≈ 1/2^k for a range bisected each crack — after k=10 cracks, roughly 1/1024 ≈ 0.1% of the original piece size remains to scan for that range.

4. Statistics memory. For 1,000 columns, 100 equal-depth buckets each, 24 bytes per bucket (lo, hi, count): 1,000 * 100 * 24B = 2,400,000B ≈ 2.29MB total histogram memory — negligible against the per-index memory budget in §4.

5. Selectivity crossover (from §8.7's equations). Setting Cost_btree_lookup = Cost_fullscan: c_traverse * log_f(n) + s*n*c_fetch = n*c_scan → solving for s: s = (n*c_scan - c_traverse*log_f(n)) / (n*c_fetch). For the §8.7 constants (n=10,000,000, c_scan=1ns, c_fetch=100ns, c_traverse=50ns, f=200): s ≈ (10,000,000 - 155) / 1,000,000,000 ≈ 0.01 — i.e. above roughly 1% selectivity, a full scan beats the B+Tree lookup; below it, the B+Tree wins (before accounting for the cracked-scan path, which wins earlier still once converged, per §8.7).

6. Tiered-compaction write amplification and space cost. Fanout = 10, 4 levels: worst-case WA ≈ fanout * levels = 40x; bounded to < 4x (§4, M9) via heat-aware skip of untouched levels, meaning in practice only the levels actually receiving new data are rewritten — for a workload touching only the top 1 of 4 levels per write, effective WA ≈ 10x / (levels skipped factor) ≈ within the 4x target when 3 of 4 levels are skipped on a typical write.

7. Latch-contention throughput ceiling. With a mean latch hold time of 200ns and a target of < 5% latency spent waiting at p95 (§4, M11), the maximum sustainable concurrent-access rate on a single hot page before contention exceeds budget is roughly 0.05 * target_p95_latency / mean_hold_time concurrent accessors — for a 1.5ms p95 point- lookup budget, ≈ (0.05 * 1,500,000ns) / 200ns ≈ 375 concurrent accessors on the same page before latch-wait begins eating into the p95 budget beyond its bound.

36. Alternative Architectures (Roads Not Taken)

36.1 Full Up-Front Index Construction

   +-------------------+
   | Build Phase       |   one-time O(n log n) sort/build
   | (before 1st query)|
   +---------+---------+
             v
   +-------------------+
   | Static B+Tree/ART |   every query pays only O(log n) / O(key_len)
   +-------------------+

Winning regime: predictable, stable query workloads where the index will be queried enough times that the up-front build cost is trivially amortized. Real embodying system: PostgreSQL's nbtree (§33) — built once via CREATE INDEX, never adaptively reorganized. Why rejected here: this project's motivating problem (§1, §2) is specifically the case where the workload is unknown or exploratory at index-creation time, which is exactly where up-front construction wastes work relative to cracking (P1, P6).

36.2 Adaptive Merging as the Sole Strategy

   +-------------------+     +-------------------+
   | k sorted runs     | --> | fewer, larger runs |  (converges faster
   +-------------------+     +-------------------+   per query, costlier
                                                      per query, §8.3)

Winning regime: stable, wide-range, repeatedly-queried workloads (P12). Real embodying system: Graefe & Kuno 2010's adaptive-merging proposal, prototyped in research contexts adjacent to this project's citations. Why rejected as the sole strategy here: it pays a higher first-query cost than cracking (§8.3, §8.7) and loses on the genuinely unpredictable, narrow-range workloads this project also targets — hence the hybrid ADR-03 decision rather than choosing one exclusively.

36.3 LSM-Tree Organization for Write-Heavy Workloads

   writes -> [ memtable ] -> flush -> [ L0 ] -> compact -> [ L1 ] -> ... -> [ Ln ]
                                        ^ read must probe every level (amplification)

Winning regime: write-heavy workloads where point-lookup read amplification is an acceptable tradeoff for append-only write throughput. Real embodying system: RocksDB (§33). Why rejected as the primary structure here: this project's target workloads (§1, §4) are read/scan-latency sensitive with the specific adaptive-indexing intellectual focus, not primarily write- throughput-bound; RocksDB's model is used only as the tiered-compaction amplification contrast (§22, §34), not adopted as the primary index.

36.4 A Learned Index Replacing the Tree with a Predictive Model

   key -> [ learned model: predicts approx. position ] -> [ local search window ] -> Rid

Winning regime: stable, read-heavy, rarely-updated data where the key distribution is smooth enough for a compact model to predict position accurately. Real embodying system: the learned-index research line (not among this project's cited implementations, evaluated only conceptually). Why rejected here: learned indexes are hostile to updates (a model retrain or correction structure is needed on every insert that shifts the distribution) and provide no natural mechanism for workload-adaptive refinement in the cracking sense — the opposite RUM tradeoff from what this project's P5/§8.4 framing targets, and deferred per PhaseDeferred("§36.4 Learned Index (Roads Not Taken)").

38. Glossary

Term Definition
Adaptive indexing index refinement performed incrementally as a side effect of query execution rather than built up front
Database cracking the specific adaptive-indexing algorithm that in-place partitions a column around query predicate boundaries
Cracker index the sorted piece-boundary ledger tracking a cracked column's current partition state
Piece a contiguous physical sub-range of a cracked column between two boundaries
Adaptive merging an alternative adaptive-indexing algorithm that incrementally merges sorted runs on query-touched ranges
Run a sorted, disjoint sub-sequence of a column maintained by adaptive merging
Convergence the process by which repeated queries on a range drive a cracked or merged column toward a fully-refined physical layout
RUM conjecture the principle that no access method can simultaneously minimize read, update, and memory overhead
Access path one of the candidate execution strategies (B+Tree, ART, cracked column, full scan) for resolving a query
Access-path selection the process of choosing among access paths by comparative cost, per Selinger et al. 1979
Selectivity the fraction of rows matching a given predicate
Cost model the set of equations estimating execution cost for each access path given selectivity and structure state
B+Tree a balanced, ordered tree structure supporting logarithmic point lookup and efficient range scan
Latch a short-duration mutual-exclusion primitive protecting a page or node during a structural operation
Latch coupling holding a parent and child latch simultaneously across a descent handoff to prevent phantom traversal
Blink tree a B+Tree variant with right-sibling links tolerating a temporarily-stale separator during concurrent splits
Optimistic lock coupling (OLC) a concurrency protocol validating a generation counter after an unlatched read rather than holding a latch throughout
Prefix compression storing a page-level shared key prefix once and only the differing suffix per entry
ART Adaptive Radix Tree, a main-memory trie structure with four node types sized to their fan-out
Node growth the ART's transition from a smaller node type to a larger one as its child count increases
Path compression collapsing a chain of single-child nodes into one node carrying the shared key path
Lazy expansion deferring the creation of branching nodes until a key's uniqueness is broken by a later insert
Histogram an equal-depth bucketed summary of a column's value distribution used for selectivity estimation
Sketch a probabilistic summary structure (e.g. HyperLogLog) estimating cardinality with bounded error
Cardinality estimation predicting the number of distinct or matching values for a predicate from statistics
Hybrid OLTP/OLAP an access-method design serving both transactional point access and analytical scan access from shared structures
Tiered storage organizing data across hot, warm, and cold storage media by access frequency
Compaction the background process of reorganizing and moving segments across storage tiers or LSM levels
Read amplification the ratio of physical bytes/levels read to logical bytes needed to answer a query
Write amplification the ratio of physical bytes written to logical bytes of new data
Space amplification the ratio of physical storage consumed to logical data size
Column store a storage layout organizing data by column rather than by row
Learned index an access method replacing a tree structure with a model predicting approximate record position
Copy-on-crack the isolation technique of operating a crack step on a private piece copy published atomically
Concurrency token a monotonically increasing counter used to detect concurrent structural changes during optimistic reads
Fence key the low/high key bound stored on a B+Tree page delimiting its valid key range
Tombstone a marker recording a logical deletion pending physical cleanup
Backpressure an explicit signal that causes upstream producers to slow down when a downstream stage is saturated
Admission control rejecting or deferring new requests when system capacity is exceeded
Structural verifier a diagnostic routine walking a structure to confirm its invariants hold
Differential testing comparing this system's output against a reference implementation's output on shared inputs
Convergence benchmark the named CI gate measuring queries-to-refinement on standard skewed workloads
Workload-shape detector the component classifying a query stream as stable/wide or unpredictable/narrow to drive strategy selection
Generation a version counter on a snapshot (statistics, ART node) indicating how many times it has changed
Staleness bound the maximum age or write-count a statistics snapshot may reach before it is considered untrustworthy
Access-method interface the trait-based protocol boundary between the host engine and this project's index engines
