Decisions (§9) · 30 ADRs

ADR-01

Language

Chosen

Rust

Rejected

C++, Go, Java, Zig

When the rejected choice is right

C++ wins when embedding inside a legacy storage-engine plugin ABI that mandates zero-runtime linking

Why: memory safety without GC pauses

ADR-02

Primary index structure

Chosen

hybrid B+Tree + ART

Rejected

B+Tree-only, hash index

When the rejected choice is right

pure B+Tree wins for fixed narrow-integer sequential keys as in classic PostgreSQL nbtree usage

Why: ranges need B+Tree order, sparse point lookups need ART

ADR-03

Adaptive-indexing strategy

Chosen

hybrid cracking + adaptive merging

Rejected

cracking-only, adaptive-merging-only, up-front build

When the rejected choice is right

adaptive-merging-only wins for reporting/OLAP nightly batch scans over the same wide ranges

Why: cracking is cheap on first touch, adaptive merging converges faster on stable wide ranges

ADR-04

Secondary structure per workload

Chosen

ART for point-heavy, B+Tree for range-heavy

Rejected

always-ART, always-B+Tree

When the rejected choice is right

always-ART wins for main-memory column-store execution as in DuckDB where ranges are rare

Why: matches structure to access pattern (RUM, P5)

ADR-05

Cracker-index representation

Chosen

sorted piece-boundary array, in-place partition

Rejected

secondary B+Tree over pieces, hash-bucketed cracker

When the rejected choice is right

secondary B+Tree over pieces wins once piece count grows unbounded under adversarial workload (Schuhknecht et al. 2013)

Why: O(1) partition, O(p) boundary insert is cheap for bounded p

ADR-06

Column vs row storage for cracked data

Chosen

column-major

Rejected

row-major

When the rejected choice is right

row-major wins for OLTP point-lookup-dominant tables where whole-row locality matters more

Why: scan throughput and SIMD-friendliness

ADR-07

Cost model & router design

Chosen

calibrated Selinger-style cost-based router

Rejected

fixed heuristic rule, ML-learned router

When the rejected choice is right

ML-learned router wins for a stable high-volume analytical workload with abundant training signal

Why: transparent, debuggable, matches P2

ADR-08

Statistics representation

Chosen

histograms + HyperLogLog sketches, incremental

Rejected

full recompute on write, sampling-only

When the rejected choice is right

full recompute wins for small cold-start tables where incremental bookkeeping exceeds table size

Why: amortized O(1) update (§8.8)

ADR-09

Statistics collection cadence

Chosen

incremental, amortized on write path

Rejected

periodic batch recompute

When the rejected choice is right

periodic batch recompute wins under extreme append-only ingestion firehose throughput

Why: keeps staleness bound (§4) tight

ADR-10

Concurrency control for reorganization

Chosen

physical latching with copy-on-crack isolation

Rejected

pure logical versioning (MVCC-style), lock-free CAS cracking

When the rejected choice is right

logical versioning wins when the host already carries MVCC snapshots, as in HyPer's chunked columnar design

Why: matches embeddable-library boundary, no host MVCC assumed

ADR-11

Latch protocol

Chosen

latch coupling (B+Tree), optimistic lock coupling (ART)

Rejected

lock-free (Bw-Tree-style) throughout

When the rejected choice is right

lock-free wins under extreme write concurrency across many cores, as in the Bw-Tree/Hekaton design point

Why: simpler to verify (P7) than a full lock-free design

ADR-12

Memory management

Chosen

arena/slab allocator per ART node-type

Rejected

general-purpose malloc, GC

When the rejected choice is right

general malloc wins for a low-QPS embedded deployment where pool bookkeeping isn't amortized

Why: reduces fragmentation for fixed-size node pools (P8)

ADR-13

Durability of adaptively-built index

Chosen

crack ops not individually WAL-logged; only piece-boundary checkpoints persisted

Rejected

log every micro-crack, fully ephemeral rebuild-from-scratch

When the rejected choice is right

per-crack logging wins in a durability-critical financial OLTP system where losing partial index progress is unacceptable

Why: avoids per-crack WAL overhead (P1)

ADR-14

Recovery of index state

Chosen

Rejected

When the rejected choice is right

full index snapshot wins when convergence cost is high relative to snapshot cost on huge immutable analytical tables

Why: matches ADR-13, keeps RTO bounded by base-data recovery

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Full Up-Front Index Construction

   +-------------------+
   | Build Phase       |   one-time O(n log n) sort/build
   | (before 1st query)|
   +---------+---------+
             v
   +-------------------+
   | Static B+Tree/ART |   every query pays only O(log n) / O(key_len)
   +-------------------+

Winning regime: predictable, stable query workloads where the index will be queried enough times that the up-front build cost is trivially amortized. Real embodying system: PostgreSQL's nbtree (§33) — built once via CREATE INDEX, never adaptively reorganized. Why rejected here: this project's motivating problem (§1, §2) is specifically the case where the workload is unknown or exploratory at index-creation time, which is exactly where up-front construction wastes work relative to cracking (P1, P6).

Adaptive Merging as the Sole Strategy

   +-------------------+     +-------------------+
   | k sorted runs     | --> | fewer, larger runs |  (converges faster
   +-------------------+     +-------------------+   per query, costlier
                                                      per query, §8.3)

Winning regime: stable, wide-range, repeatedly-queried workloads (P12). Real embodying system: Graefe & Kuno 2010's adaptive-merging proposal, prototyped in research contexts adjacent to this project's citations. Why rejected as the sole strategy here: it pays a higher first-query cost than cracking (§8.3, §8.7) and loses on the genuinely unpredictable, narrow-range workloads this project also targets — hence the hybrid ADR-03 decision rather than choosing one exclusively.

LSM-Tree Organization for Write-Heavy Workloads

   writes -> [ memtable ] -> flush -> [ L0 ] -> compact -> [ L1 ] -> ... -> [ Ln ]
                                        ^ read must probe every level (amplification)

Winning regime: write-heavy workloads where point-lookup read amplification is an acceptable tradeoff for append-only write throughput. Real embodying system: RocksDB (§33). Why rejected as the primary structure here: this project's target workloads (§1, §4) are read/scan-latency sensitive with the specific adaptive-indexing intellectual focus, not primarily write- throughput-bound; RocksDB's model is used only as the tiered-compaction amplification contrast (§22, §34), not adopted as the primary index.

A Learned Index Replacing the Tree with a Predictive Model

   key -> [ learned model: predicts approx. position ] -> [ local search window ] -> Rid

Winning regime: stable, read-heavy, rarely-updated data where the key distribution is smooth enough for a compact model to predict position accurately. Real embodying system: the learned-index research line (not among this project's cited implementations, evaluated only conceptually). Why rejected here: learned indexes are hostile to updates (a model retrain or correction structure is needed on every insert that shifts the distribution) and provide no natural mechanism for workload-adaptive refinement in the cracking sense — the opposite RUM tradeoff from what this project's P5/§8.4 framing targets, and deferred per PhaseDeferred("§36.4 Learned Index (Roads Not Taken)").
