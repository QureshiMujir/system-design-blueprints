⬜ Phase 0 — Skeleton, Object-Store Adapter, Parquet Bridge, CI §12

Objectives

Establish the workspace, the ObjectStore trait plus a local-filesystem and an S3-compatible adapter, a parquet-bridge wrapping an external Parquet crate for read/write and footer-statistics extraction, and a CI pipeline gating every subsequent phase.

Deliverable

A compiling workspace; ObjectStore trait with two working adapters; a parquet-bridge that round-trips a Parquet file and extracts footer stats into ColumnStats; green CI on every crate.

Acceptance

Round-trip test writes 10K-row Parquet file, reads it back, footer-extracted ColumnStats.lower_bound/upper_bound match a reference computation on 100% of numeric columns; put_if_absent semantics verified via a race test with 50 concurrent callers — exactly one wins, 49 observe CommitConflict-equivalent rejection; CI green on 3 consecutive commits.

Fixtures

fixtures/parquet/basic_10k_rows.parquet; fixtures/parquet/all_null_column.parquet; fixtures/objectstore/cas_race_50_writers/; fixtures/objectstore/local_vs_s3_adapter_parity/.

Pitfalls
  1. Local-filesystem atomic rename is not equivalent to a true CAS across NFS-mounted paths — silently drops the "only one wins" guarantee.
  2. Parquet footer stats can be absent for a column (writer-side stats disabled) — must be treated as "no pruning possible," never as "no rows."
  3. S3 conditional-PUT semantics vary across S3-compatible third-party stores — some silently accept overwrite.
  4. Footer-only stats extraction can be fooled by a Parquet file with corrupted footer but valid data pages — must checksum the footer independently.

⬜ Phase 1 — The Metadata Tree and a Read-Only Table §13

Objectives

Implement TableMetadata, Schema, PartitionSpec, Snapshot, ManifestList, ManifestFile, ManifestEntry, DataFile (§11) with versioned JSON/Avro-shaped (de)serialization, and a read-only table that can load a hand-authored metadata tree and enumerate its data files.

Deliverable

A crate that loads a TableMetadata JSON file, resolves its current snapshot, walks the manifest list and manifests, and returns the full DataFile set — no writes, no commits.

Acceptance

Loads and round-trips the Iceberg-spec-shaped fixture set (§5 RFC entry) byte-identically on re-serialize; walks a 3-level manifest tree (list → 5 manifests → 500 entries) and returns exactly 500 DataFiles in under 50 ms; rejects a metadata file whose format_version exceeds the reader's supported maximum (I12).

Fixtures

fixtures/metadata/table_v2_basic.json; fixtures/metadata/nested_schema.json; fixtures/manifest/500_entry_tree/; fixtures/metadata/unsupported_future_version.json.

Pitfalls
  1. Recursive nested-struct schemas can stack-overflow a naive recursive walker — must be iterative or depth-bounded.
  2. A manifest-list summary referencing a manifest that was deleted (dangling pointer) must fail closed, not skip silently.
  3. JSON key ordering differences between writers break naive byte-equality tests even when semantically identical — golden tests must normalize or the writer must sort keys (ADR-26).
  4. Avro schema evolution of the manifest format itself (not the table's schema) is a distinct concern from table schema evolution — conflating them is a common early bug.

⬜ Phase 2 — Snapshot Model and Scan Planning §14

Objectives

Implement SnapshotRef, sequence numbers, and the full scan-planning pipeline (§8.5): partition-predicate derivation, manifest-list pruning, manifest-entry pruning, data-file pruning, producing ScanPlan/FileScanTask.

Deliverable

A scan planner that takes a Predicate and an optional SnapshotId (default: current) and returns a ScanPlan with correct pruning at both list and file level, benchmarked against the numeric targets in §4.

Acceptance

On the 10,000-file/365-partition fixture (§8.5 worked example), a single-day-equality query prunes to ≤ 30 files scanned via list-level pruning alone (matching the ≈27-file/day worked figure) and issues ≤ 2 object-store GETs to plan it; scan-planning p95 < 100 ms at N=10K files (§4); zero false negatives across 10,000 property-test-generated predicate/file-stats pairs (a file that could match is never pruned).

Fixtures

fixtures/planning/10k_files_365_partitions/; fixtures/planning/predicate_pushdown_cases/; fixtures/planning/null_heavy_columns/; fixtures/planning/false_negative_property_corpus/.

Pitfalls
  1. Over-pruning on a NULL-containing column when the predicate is IS NOT NULL versus a naive min/max check — must special-case null-count.
  2. NaN values in float columns break naive min/max comparisons (NaN is neither less-than nor greater-than) — must be excluded from bound computation, not compared directly.
  3. Multi-manifest scans where two manifests use different partition-spec-ids (post partition-evolution) require per-manifest spec-aware predicate translation, not one global translation (I6).
  4. A predicate on a column added after some files were written (no stats present in older manifests) must default to "cannot prune," never "no match."

⬜ Phase 3 — Atomic-Commit / Optimistic-Concurrency Engine §15

Objectives

Implement the commit engine per the §8.2 sequence table: read-metadata, build-manifest, build-snapshot, build-metadata, CAS-publish, with conflict detection and retry.

Deliverable

A commit engine supporting concurrent independent writers against one table, retrying on conflict with bounded backoff, producing the worked successful and worked conflicting-retry traces of §8.2 as passing integration tests.

Acceptance

50 concurrent writers appending disjoint partitions to one table: 0 lost updates, commit-conflict/retry rate < 5% (§4 target); a fixed two-writer race (§8.2 worked conflict example) deterministically reproduces exactly one CAS success and one CAS failure-then-successful-retry across 1,000 repeated runs; no partial metadata tree is ever observable by a concurrent reader (I4) — verified by a reader thread continuously loading TableMetadata during the stress run and asserting every load resolves a complete tree.

Fixtures

fixtures/commit/two_writer_conflict_deterministic/; fixtures/commit/50_writer_disjoint_partitions/; fixtures/commit/sequence_regression_attempt/ (must be rejected); fixtures/commit/cyclic_parent_attempt/ (must be rejected).

Pitfalls
  1. ABA-style pointer reuse: if a metadata-location naming scheme ever reuses a path, a stale CAS could "succeed" against the wrong generation — naming must be monotonic/UUID-suffixed, never reused.
  2. Retry storms under high contention: naive immediate-retry amplifies conflict rate superlinearly — requires the backoff policy named in ADR list and measured in §4/§30.
  3. A writer that crashes after step 7 (metadata written) but before step 8 (CAS) leaves orphan objects that must never be mistaken for the current state by any reader (failure-path example, §8.10) — reader path must never guess at an uncommitted location.
  4. Clock-based sequence assumptions: sequence numbers must be allocated from the metadata chain, never from wall-clock time, or clock skew across writers silently violates I9.
  5. A catalog backend whose CAS is not truly atomic (e.g., a check-then-set pair, not a single primitive) reintroduces the exact race this whole phase exists to remove — must be excluded at the Catalog trait's contract level, tested via the race fixture from Phase 0.

⬜ Phase 4 — Schema Evolution with Stable Column IDs §16

Objectives

Implement the field-ID allocator and the add/drop/rename/reorder/type-promote validators of §8.3, producing a new Schema object per change without touching any existing DataFile.

Deliverable

A schema-evolution engine exposing add_column, drop_column, rename_column, reorder, promote_type, each returning a new Schema (new schema_id) or a rejection with a specific violated-invariant reason, committed via the Phase-3 engine as a schema-only TableMetadata update.

Acceptance

100% of the §8.3 decision-table rows have a corresponding passing/rejecting test; a rename-then-read-old-file test proves zero data-file rewrite (file mtimes/checksums unchanged pre/post rename); an attempted narrowing type change (long→int) is rejected before any object-store write occurs (zero orphan objects produced by a rejected change); nested-field evolution (add a field inside a struct) passes the same field-ID-stability check recursively.

Fixtures

fixtures/schema/rename_column.json; fixtures/schema/add_nested_field.json; fixtures/schema/reject_narrowing.json; fixtures/schema/reject_field_id_reuse.json; fixtures/schema/promote_int_to_long.json.

Pitfalls
  1. Reordering fields in the JSON schema representation without touching field-IDs can accidentally be conflated with a rename if the validator matches by position instead of ID — must always match by field-id.
  2. Dropping and later re-adding a column with the same name must allocate a new field-id, not resurrect the old one, or old dropped-column data becomes visible under the new column's identity (I5 violation).
  3. Struct-nested field-ID collision: two independently evolved branches of a nested struct schema could allocate overlapping IDs if the allocator isn't table-global — must be a single monotonic counter per table, not per struct.
  4. Type promotion inside a map or list element type needs the same promotion rules applied recursively — easy to implement only at the top level and miss nested containers.

⬜ Phase 5 — Hidden Partitioning and Partition Transforms §17

Objectives

Implement the transform registry (identity, bucket[N], truncate[W], year, month, day, hour), PartitionSpec evolution, and mixed-spec scan planning across manifests written under different specs.

Deliverable

A transform registry usable by both the write path (deriving PartitionValue) and the scan planner (deriving predicate ranges), plus a partition-spec-evolution API (add_partition_field, remove_partition_field) that produces a new spec_id without touching existing manifests.

Acceptance

The §8.4 worked pruning example reproduces exactly: day-partitioned predicate prunes to the single day's manifests with zero false negatives across a 365-partition fixture; a partition-spec evolution mid-table-history (old data under spec 0, new data under spec 1) scans correctly across both specs in one query, verified against a fixture with manifests under both specs; bucket[16] hash stability verified byte-identical across two independent invocations of the transform on 10,000 sample values.

Fixtures

fixtures/partition/day_transform_365/; fixtures/partition/bucket_16_stability/; fixtures/partition/mixed_spec_old_and_new/; fixtures/partition/truncate_string_prefix/.

Pitfalls
  1. null source-column values under a transform must map to a defined "null partition" bucket, not be silently dropped from any partition or crash the transform function.
  2. Timezone handling in day/hour transforms: a source timestamp without explicit UTC normalization produces different partition values depending on reader locale — must normalize to UTC before transform application, always.
  3. truncate[W] on a string column with multi-byte UTF-8 characters must truncate at a byte boundary consistent with the writer's encoding, or two writers on different locales produce different partition values for logically identical input.
  4. Evolving from bucket[16] to bucket[32] on the same source column does not let old bucketed files be reinterpreted under the new bucket count — the planner must never assume old and new bucket values are comparable (I6's "own spec" rule again).

⬜ Phase 6 — Column Statistics and Manifest/File Pruning §18

Objectives

Populate ColumnStats (min/max/null-count/value-count) from the Parquet bridge at write time, and extend the scan planner's step 4 (§8.5) to use them for file-level elimination, closing the loop from §8.5's worked example.

Deliverable

Statistics population wired into the commit path (every new DataFile entry carries populated ColumnStats); the planner's step-4 file-pruning fully implemented and measured against the §4/§8.5 numeric targets (99%+ elimination on the worked selective-query example).

Acceptance

The §8.5 worked example reproduces the stated 11-of-10,000-files result (±10% tolerance) on the reference fixture; a property test asserts zero false negatives across 10,000 generated (predicate, file-stats) pairs (no file that could contain a matching row is ever pruned) — this is the same class of test as §14.4 but now exercising real Parquet-footer-derived stats rather than synthetic ones; pruning-ratio telemetry (§4) matches the measured elimination percentage within rounding.

Fixtures

fixtures/pruning/selective_query_10k_files/; fixtures/pruning/all_null_column_predicate/; fixtures/pruning/nan_float_column/; fixtures/pruning/false_negative_property_corpus_v2/ (now Parquet-footer-backed, not synthetic).

Pitfalls
  1. Parquet writer-side stats can be disabled per-column for wide/rarely-queried columns — the pruning path must treat "stats absent" as "cannot prune this file on this column," never as an error or a false match.
  2. Decimal-typed column bounds require exact fixed-point comparison, not floating-point coercion, or boundary-value predicates silently misprune.
  3. A predicate combining an AND across two columns must apply file-level pruning per-column and combine conservatively (a file survives if it is not provably excluded by either), not optimistically.
  4. Corrupted or adversarially crafted footer stats (T5 in §24) must not cause the planner to trust an out-of-range bound blindly — a defensive sanity check against record_count bounds catches gross corruption.

⬜ Phase 7 — Row-Level Deletes (Copy-on-Write) §19

Objectives

Implement copy-on-write update/delete: given a predicate, rewrite every affected DataFile into new file(s) excluding/updating the matching rows, and commit the replacement atomically.

Deliverable

A copy-on-write delete/update API taking a Predicate, producing a new snapshot whose manifest correctly marks superseded files deleted (metadata-only, I3-respecting) and rewritten files added.

Acceptance

A delete-by-predicate against a 1,000-file fixture rewrites only the files whose stats could not exclude a match (measured against the same pruning-ratio numbers as Phase 6, since the affected-file computation reuses that path); post-delete scan at the new snapshot returns zero rows matching the delete predicate; a scan at the prior snapshot still returns the original rows unchanged (time-travel-visible immutability, P2); write-amplification measured equals rewritten-file-bytes / touched-row-bytes and is reported against the §34 capacity-model formula.

Fixtures

fixtures/cow/delete_by_predicate_1000_files/; fixtures/cow/update_changes_value/; fixtures/cow/prior_snapshot_still_visible/; fixtures/cow/full_file_match_no_rewrite_needed/ (delete-all-rows-in-file case, where the file is simply marked deleted with no rewrite).

Pitfalls
  1. A file that is 100%-matched by the delete predicate should be marked deleted directly, not rewritten as an empty file — rewriting an empty file wastes an object-store write and complicates GC bookkeeping for no benefit.
  2. Concurrent copy-on-write operations on overlapping files must be caught by the Phase-3 OCC engine as a normal commit conflict — a naive implementation that doesn't route through the shared commit path can silently lose one operation's rewrite.
  3. A crash between "new files written" and "commit published" must leave the old files' visibility completely unaffected — the failure-path example of §8.10 applies identically here; orphaned rewritten files are GC-eligible, not a correctness problem.
  4. Rewriting a file changes its statistics (Phase 6) — the new file's ColumnStats must be freshly computed, never copied from the old file's stats under the assumption "the surviving rows have the same bounds."

⬜ Phase 8 — Merge-on-Read Delete Files §20

Objectives

Implement DeleteFile writing (position deletes and equality deletes), sequence-number-scoped applicability, and scan-time delete application (§8.5 step 5, §8.6, I7/I9).

Deliverable

A DeleteFile writer supporting both content types; scan-planner step 5 (delete-file association) fully implemented, attaching applicable deletes to each FileScanTask; engine-facing residual delete application left to the caller per the FileScanTask.delete_files field (ADR-19 boundary).

Acceptance

A position-delete fixture (delete 5% of rows in a 100-file table) shows correct row exclusion on 100% of a 10,000-row differential check against a reference "apply deletes manually" computation; an equality-delete fixture with overlapping predicates from two separate delete commits correctly composes (both apply, sequence-ordered); read amplification (delete-files-applied-per-scan, §4/§8.6) is measured and reported; a delete file with applies_to_seq_ge greater than a candidate data file's sequence number is correctly excluded from that file's task (I9 respected).

Fixtures

fixtures/mor/position_delete_5pct/; fixtures/mor/equality_delete_overlapping/; fixtures/mor/sequence_scoped_applicability/; fixtures/mor/delete_file_wrong_scope_must_not_apply/.

Pitfalls
  1. Position deletes referencing row offsets computed before a concurrent compaction rewrote the target file become invalid — position deletes must be scoped to a specific, immutable file identity (path + a content id), never a mutable row-offset-only reference.
  2. Equality deletes on a column later dropped by schema evolution (Phase 4) must remain interpretable against the schema active when the delete was written, not the current schema — delete-file schema binding follows the same field-ID discipline as data files.
  3. Two equality deletes with contradictory predicates from racing writers must both survive (union of exclusions), never overwrite one another — deletes are additive, resolved by the normal OCC commit path just like any other manifest change.
  4. Applying deletes at scan time without respecting sequence-number scoping (I9) can delete rows from a file that didn't exist yet when the delete was authored, an easy off-by-one if sequence comparison uses <= where the spec requires strict <.
  5. Very high delete-file-count-per-data-file (unbounded read amplification) degrades scan latency invisibly until it crosses a compaction threshold — must be measured, not assumed bounded.

⬜ Phase 9 — Time Travel, Rollback, and Snapshot Refs §21

Objectives

Implement historical-snapshot scan planning (time travel), the rollback-via-commit operation, and named SnapshotRefs (tags/branches) that pin retention.

Deliverable

A time_travel(snapshot_id | timestamp) planning entry point; a rollback(snapshot_id) commit operation; SnapshotRef creation/deletion wired into the retention computation used later by ExpireSnapshots.

Acceptance

A time-travel scan at a historical snapshot returns byte-identical results to what a contemporaneous scan returned at commit time (verified by re-running a recorded scan against a fixture with 10 historical snapshots); time-travel planning latency is statistically indistinguishable from a current-snapshot scan at the same file count (§4 "equal to a normal scan" claim, verified via benchmark comparison, not just asserted); rollback followed by a new commit produces a correctly linear (non-cyclic, I10-respecting) history, not a fork that confuses later planning.

Fixtures

fixtures/timetravel/10_snapshot_history_replay/; fixtures/timetravel/timestamp_to_nearest_snapshot/; fixtures/rollback/simple_rollback_then_commit/; fixtures/refs/tag_survives_expiry_window/.

Pitfalls
  1. Resolving a timestamp to "the nearest snapshot at or before it" versus "nearest overall" is a subtle off-by-one that silently returns future data for a past-dated query — must always resolve to the latest snapshot with timestamp_ms <= target, never a later one.
  2. Rollback does not delete the snapshots it "skips" — they remain in the snapshot-log and are still reachable/GC-safe until independently expired; a naive rollback implementation that truncates the log breaks I11's ordering assumption for any GC pass already in flight.
  3. A branch SnapshotRef that itself receives new commits diverges into a genuine fork — the acyclic-DAG invariant (I10) is per-branch, not global; cross-branch planning must never conflate two branches' histories.
  4. Tag retention interacting with expiry: a tag pinning a very old snapshot indefinitely prevents that snapshot's exclusive files from ever being GC'd — this is correct behavior but must be visible in snapshot-bloat telemetry (Phase 10/§26), not a silent storage leak.

⬜ Phase 10 — Compaction, Expire-Snapshots, and Orphan-File GC §22

Objectives

Implement the maintenance worker: data-file/manifest compaction (bin-packing to target size), ExpireSnapshots, and OrphanFileGc, wired to the two-phase safety ordering of §8.8/I11.

Deliverable

A maintenance daemon exposing compact(table, target_file_size), expire_snapshots(policy), and gc(dry_run: bool), each independently schedulable, with GC defaulting to dry_run = true until explicitly enabled per table.

Acceptance

Compaction on a 10,000-small-file fixture reduces file count by ≥ 90% while preserving row-for-row read equivalence (differential check against pre-compaction scan results); ExpireSnapshots against a 1,000-snapshot history retaining the last 100 and all tagged snapshots removes exactly the expected count (verified against §4's default retention policy); OrphanFileGc in a concurrent-reader stress test (a long-running reader pinned to an old, not-yet-expired snapshot runs throughout a full expire+GC cycle) shows zero read failures and zero incorrectly deleted files (I3 held under concurrency, not just in isolation); dry-run GC output matches actual-run deletion set exactly on a repeat run with no intervening commits.

Fixtures

fixtures/compaction/10k_small_files_bin_pack/; fixtures/expiry/1000_snapshot_history_with_tags/; fixtures/gc/concurrent_reader_during_expire_and_gc/; fixtures/gc/dry_run_matches_real_run/.

Pitfalls
  1. Running OrphanFileGc before the corresponding ExpireSnapshots commit is durably visible to the GC worker's own catalog read (a caching layer serving a stale pointer) violates I11 even if the two calls are issued in the "right" order by the operator — the worker must re-read the catalog fresh, not trust a cached pointer.
  2. Compaction racing a reader that has already planned a scan against pre-compaction files: the reader's FileScanTasks reference the old files by path, and those files must remain valid until no live plan references them — compaction's new snapshot does not retroactively invalidate an in-flight reader's already-issued task list (I1 protects this, but only if compaction never deletes pre-compaction files itself, deferring deletion entirely to a later GC pass).
  3. A LIST operation on the underlying object store that is even briefly stale (violating the ADR-16/27 assumption) during orphan-detection can miss a just-written file and delete it — this is why GC's reachability set is computed from the metadata tree (authoritative), and LIST is used only to find candidates for deletion, never as the source of truth for what's live.
  4. Bin-packing compaction that doesn't account for delete-file association (Phase 8) can silently orphan a delete file whose target data file was just compacted away — delete-file compaction/folding must be coupled to data-file compaction, not run independently.
  5. Default dry_run = true being overridden globally instead of per-table risks accidentally enabling live deletion on a table an operator didn't intend to touch — configuration must be explicit and table-scoped.

⬜ Phase 11 — Multi-Writer Stress, Engine-Integration API, Conformance and Perf Hardening §23

Objectives

Stress the commit engine under realistic multi-writer concurrency with an isolation checker, freeze the engine-integration API (ScanPlan/FileScanTask/Catalog/ObjectStore), and run the full conformance/differential/perf-regression gates to the v2-god bar.

Deliverable

A concurrency-stress CI job (ADR-24) running to zero isolation-checker violations; a frozen, documented engine-integration API; a green cross-engine-compatibility CI job (ADR-24) reading this project's committed tables with an external Iceberg reader.

Acceptance

500-concurrent-writer stress run: 0 lost updates, 0 isolation-checker violations, commit-conflict/retry rate consistent with the model in §4/§34 (not unboundedly worse under load); cross-engine differential read (DuckDB Iceberg extension against a table written by this project) returns row-identical results across 20 conformance fixtures spanning Phases 1–10's feature set; full soak run (30-day-equivalent accelerated schedule) with continuous commits, compactions, and GC passes shows zero I3/I11 violations and zero data loss.

Fixtures

fixtures/stress/500_writer_isolation_checked/; fixtures/crossengine/duckdb_iceberg_read_20_cases/; fixtures/soak/30_day_accelerated_schedule/; fixtures/api/frozen_surface_snapshot_test/ (fails the build if the public API changes without a version bump).

Pitfalls
  1. Isolation-checker false negatives: a checker miscalibrated to snapshot isolation's actual guarantees (versus, say, serializability) can pass a run that genuinely violates I1 under a subtle interleaving — the checker's model itself must be validated against Bailis et al. 2014's isolation-level definitions before being trusted as a gate.
  2. Cross-engine differential tests can pass on the happy path but miss spec corners the external reader doesn't itself exercise (e.g., an external reader that silently ignores a manifest feature this project relies on) — differential testing supplements, never replaces, the Phase-1–10 property/fixture suites.
  3. API freezing too early (before Phase-10's maintenance API stabilizes) forces a breaking change later anyway — the freeze in this phase intentionally comes last, after every phase that shapes the surface.
  4. Soak-test acceleration (compressing 30 real days into a shorter run) can hide time-dependent bugs (e.g., a retention-window edge case that only manifests at real 24-hour boundaries) — the schedule must still exercise at least one real-time-scale retention-window transition, not purely accelerated commits.
