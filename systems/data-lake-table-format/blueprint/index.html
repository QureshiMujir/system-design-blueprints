Project Number: 214

Project Name: Data Lake Table Format (Iceberg/Delta-like)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, an open table-format and metadata-transaction layer that turns a directory of immutable Parquet files on object storage into a transactional table: ACID snapshot isolation via an atomic compare-and-swap on a single metadata pointer, schema evolution with stable column IDs, hidden partitioning with pluggable transforms, time travel and rollback across the snapshot history, and scan planning that prunes files through a manifest tree carrying column- and partition-level statistics. The system is the metadata tree — table metadata, snapshots, manifest lists, manifests, data files, delete files — plus the commit engine, the scan planner, and the maintenance (compaction/GC) workers that operate over that tree. It is a library, not a service: it is linked into query engines and given a Catalog implementation; it never runs its own query execution and never implements its own columnar file codec.

Phase-0 deliverable, as a crate list:

  1. table-metadata — TableMetadata, Schema, PartitionSpec, versioned JSON (de)serialization, format-version gating.
  2. snapshot — Snapshot, SnapshotRef, sequence numbers, snapshot-log, parent lineage.
  3. manifest — ManifestList, ManifestFile, ManifestEntry, Avro-compatible encode/decode, statistics structs.
  4. datafile — DataFile, DeleteFile, FileFormat, ContentType, column-ID-keyed ColumnStats/Metrics.
  5. commit — the optimistic-concurrency compare-and-swap engine, Commit, CommitConflict, retry policy.
  6. catalog — the Catalog trait, a filesystem-catalog and an in-memory-catalog reference implementation.
  7. object-store — the ObjectStore trait wrapping conditional-PUT / GET / LIST against S3-compatible and local backends.
  8. parquet-bridge — thin adapter calling an external Parquet crate for column-chunk footer stats extraction; never reimplements the codec.
  9. scan-planner — partition-predicate evaluation, manifest pruning, file pruning, ScanPlan/FileScanTask construction.
  10. schema-evolution — field-ID allocation, add/drop/rename/reorder/promote validators.
  11. partition-evolution — transform registry (identity/bucket/truncate/year/month/day/hour), spec versioning.
  12. maintenance — compaction, ExpireSnapshots, OrphanFileGc.
  13. conformance — differential fixtures against the Iceberg table spec's expectations.
  14. cli — an operator tool for inspect/expire/compact, built on the above, never a query surface.
  15. bench — Criterion harnesses for commit latency, scan-planning latency, pruning ratio.

Boundaries — provides: the metadata/transaction layer (metadata tree, atomic snapshot commits, schema/partition evolution, scan pruning, delete-file bookkeeping, catalog interface). Delegates: the columnar file codec to Parquet (footer stats are read, never computed by re-decoding row groups); query execution (joins, aggregation, SQL) to an external engine that consumes ScanPlan; durable blob storage and its consistency model to an object store reachable through ObjectStore; multi-table transactions and a full catalog service (only a thin trait is provided, not a metastore).

Non-goals, named against sibling projects: this is not the LSM-Tree-Storage or B-Tree-Storage project (210/211-class) — it holds no page cache, no WAL, no in-process storage engine; a table here is a pointer plus files, not a server. It is not SQL-Database (project 21) — no parser, planner, or executor; it emits ScanPlan/FileScanTask for something else to execute. It is not Object-Storage (project 107) — it consumes an object store through the ObjectStore trait and assumes that project's (or S3's) consistency guarantees; it never implements bucket replication, erasure coding, or multipart-upload internals. It is not the Parquet/ORC Columnar Codec (project 410, open) — row-group encoding, dictionary compression, and page-level decoding are out of scope; this project reads Parquet footer statistics and writes Parquet files through a dependency, and would gain nothing from reimplementing 410's job. Its load-bearing concerns are exactly three: the metadata tree, atomic snapshot commits on object storage, and scan-time pruning.

Deployment model: a Rust library (cdylib/rlib) linked into a host process — an embedded engine, a distributed query engine's coordinator, or a standalone maintenance daemon — plus a small operator CLI. The catalog is either an in-process implementation (single-writer, tests) or a thin client to an external catalog service (Hive metastore, REST catalog, JDBC catalog); this project ships trait + reference implementations only, never a production metastore.

Users/operators: query-engine integrators embedding the crate as their table layer; data-platform SREs running the maintenance daemon (compaction, expire-snapshots, GC) against production tables; data engineers who read the CLI's inspect/history/expire output when diagnosing table health.

Later phases unlock: multi-writer production tables (Phase 3 commit engine), backward-compatible online schema change (Phase 4), partition-scheme migration without data rewrite (Phase 5), selective-file scans at scale (Phase 6), row-level DML without full-file rewrite (Phases 7–8), point-in-time audit and disaster recovery (Phase 9), bounded storage growth and small-file remediation (Phase 10), and safe concurrent production use across many engines (Phase 11).

Language: Rust. Rationale — the metadata tree is a graph of immutable, cheaply Arc-shared structures where ownership bugs are exactly the bugs that cause snapshot-isolation violations; Rust's borrow checker converts a class of lost-update and use-after-free-of-a-GC'd-file bugs into compile errors. serde gives deterministic, versioned (de)serialization for the JSON/Avro metadata formats without a GC pause during commit. Zero-cost async (tokio) suits the object-store-request-bound workload described in §4. Rejected: Java (Iceberg's own implementation language — rejected here because the goal is to internalize the memory and concurrency model from first principles, not lean on a GC and inherit its pause-time tax on commit-path latency); Go (adequate concurrency primitives but weaker ownership guarantees for the shared immutable metadata graph, and no equivalent to serde's zero-copy deserialization); C++ (comparable performance ceiling but no memory-safety guarantee for a parser that is explicitly a threat-model attack surface, T5).

Prerequisites: transactions and optimistic concurrency control (Gray & Reuter); columnar storage fundamentals (Parquet/Dremel); object-storage consistency semantics (S3 strong read-after-write); MVCC/snapshot isolation (Bailis et al.; Gray & Reuter). A reader unfamiliar with compare-and-swap as a concurrency primitive should read Herlihy & Wing 1990 before §7/§8.

Timeline: Phase 0 skeleton — 2 weeks. Phases 1–3 (metadata tree, snapshots/planning, atomic commit) — 6 weeks, reaching a single-writer ACID table. Phases 4–6 (schema/partition evolution, pruning) — 6 weeks. Phases 7–9 (deletes, time travel) — 6 weeks. Phases 10–11 (maintenance, multi-writer hardening) — 4 weeks. Total ≈ 24 weeks to the v2-god bar.

Deferrals: PhaseDeferred("§27 Compatibility & Versioning — v3 spec fields (row lineage, deletion vectors as first-class Puffin blobs)"); PhaseDeferred("§33 Comparative Architecture — REST-catalog server implementation beyond the client trait"); PhaseDeferred("§31 Scalability Analysis — cross-region multi-catalog replication"); PhaseDeferred("§26 Operational Readiness — automated canary-table promotion pipeline").

2. Why Build This

Keyword bullets:

  • atomic metadata-pointer swap as the entire ACID trick
  • immutability of data files as the enabler of cheap time travel
  • manifest-tree pruning versus flat directory listing (the Hive problem)
  • optimistic concurrency control under eventual object-store consistency
  • stable column IDs surviving rename/reorder — schema evolution without data rewrite
  • hidden partitioning eliminating partition-column mismatches
  • copy-on-write versus merge-on-read as a read/write-amplification tradeoff
  • snapshot isolation without locks, without a lock manager
  • GC safety under concurrent long-running readers
  • the small-files problem and why compaction is unavoidable at scale
  • cross-engine interoperability as a distributed-systems compatibility problem
  • Puffin-style sketches as statistics beyond min/max
  • historical significance: Hive metastores scaling poorly under partition explosion; Iceberg/Delta/Hudi redefining warehouse architecture by pulling metadata off a central service and onto object storage itself as plain files
  • engineering muscles developed: building metadata-heavy distributed systems, designing crash-safe commit protocols, modeling immutable data structures, debugging consistency anomalies under real object-store semantics rather than idealized ones
  • related systems worth contrasting while building this: LSM-tree and B-tree storage engines (page/segment-level mutation versus this project's whole-file immutability), MVCC databases, distributed consensus systems, columnar query planners
  • calibration value: this project permanently improves capability in distributed metadata systems, immutable state-machine design, cross-version compatibility management, and correctness-first architecture under weak storage guarantees

What Mastery Looks Like

  • Explaining, from the metadata tree up, why a commit is exactly one compare-and-swap and nothing else needs to be atomic (Phase 3).
  • Tracing a scan from predicate to FileScanTask list and stating the object-store request count at each pruning stage (Phase 6).
  • Designing a schema change that is provably safe under concurrent readers of older snapshots, using column-ID stability (Phase 4).
  • Reasoning correctly about a GC race against a long-running reader and proving the fix from the invariants in §7 (Phase 10).
  • Diagnosing a commit-conflict storm from conflict-retry telemetry and choosing the correct backoff or partitioning fix (Phase 11).
  • Explaining copy-on-write versus merge-on-read as a read/write-amplification tradeoff with real numbers, not intuition (Phases 7–8).
  • Rolling a table back to a prior snapshot and explaining exactly which files remain referenced and why GC must not have run in between (Phase 9).

The catalog is the metadata-pointer holder: it stores exactly one value per table — the location of the current TableMetadata file — and exposes a compare-and-swap primitive over that value; it is the only component that must offer atomicity, and it is what the commit engine calls.

Table metadata is a versioned JSON document holding the schema history, partition-spec history, the snapshot log, and a pointer to the current snapshot; it is rewritten (never mutated) on every commit and is small enough to read in full on every planning call.

The snapshot layer is the append-only history of table states: each Snapshot has an ID, a parent, a sequence number, an operation type, and a pointer to one manifest list; snapshots are what time travel and rollback address.

The manifest list is a per-snapshot index of manifests, carrying each manifest's partition-value summary (min/max per partition field) so the planner can discard whole manifests without opening them.

Manifests are per-write-batch indexes of data/delete files, each entry carrying the file path, partition tuple, column-level ColumnStats, and (for delete files) the content type distinguishing position- from equality-deletes.

Data files are immutable Parquet objects; delete files are Parquet or Puffin objects recording rows logically removed since the referencing data file was written, resolved at read time (merge-on-read) or already reconciled (copy-on-write).

The commit/OCC engine is the only writer path: it reads the current metadata, stages new manifests/files, and attempts a single compare-and-swap of the metadata pointer; failure means another writer won and this writer must reread and retry — this is the atomic-commit boundary marked in the diagram.

The scan planner takes a predicate and a snapshot ID, prunes manifests via partition-value summaries, prunes files via ColumnStats, and emits a ScanPlan of FileScanTasks plus applicable delete files — no data is read during planning.

The compaction/maintenance worker rewrites small files into larger ones, compacts manifests, and runs ExpireSnapshots/OrphanFileGc under the safety condition that no live snapshot may reference a file being deleted.

The schema/partition-evolution engine validates and applies metadata-only changes (add/drop/rename/reorder/promote a column; add/remove a partition field) that never touch existing data files, keyed by stable field IDs.

The object-store adapter wraps GET/PUT/LIST/conditional-PUT against S3-compatible backends; it is the consistency boundary — everything above it assumes at most the read-after-write guarantee that boundary documents (see ADR-27, §9).

6. Design Principles

P1. A commit is an atomic swap of a single metadata pointer, because atomicity on object storage is only available at the granularity of one compare-and-swap, and everything else in the system is built on top of that one primitive.

P2. Data files are immutable — an update writes new files and a new snapshot, never mutates in place — which is what makes snapshot isolation and time travel nearly free (no undo log, no MVCC row versions to garbage-collect separately).

P3. Metadata carries statistics so a scan reads the fewest files possible; pruning at the manifest level is the difference between scanning a table and scanning a partition.

P4. Column identity is a stable integer ID, never a name or a position, so rename/reorder/promote never touch a single existing data file.

P5. Every metadata object, once referenced by a published snapshot, is treated as immutable; corrections are new objects plus a new snapshot, never in-place edits.

P6. The commit path never blocks on a lock; conflict is detected after the fact by CAS failure and resolved by re-derivation and retry (P1 corollary, optimistic concurrency per Gray & Reuter ch. 7).

P7. Garbage collection is safe only if it can prove no live snapshot references a file; when in doubt, do not delete (I3 in §7).

P8. Partitioning is hidden from the writer's predicate language — a query filters on data columns, and the transform-derived partition value is computed by the system, eliminating the whole class of Hive-style partition-column mismatch bugs.

P9. Manifests and manifest lists are themselves files subject to the same immutability and pruning discipline as data files — the metadata tree is self-similar.

P10. A reader pins one snapshot for the life of a scan; the system never mutates what "current" means mid-scan (snapshot isolation, Bailis et al. 2014).

P11. Every metadata format is explicitly versioned so that an old reader can safely ignore new fields (forward compatibility) rather than crash.

P12. Delete files are additive metadata, not data-file edits — a row is "deleted" by recording that fact next to the data, never by rewriting the data file, unless a maintenance job later chooses to compact (copy-on-write is a maintenance decision, not a write-path requirement).

P13. Every object-storage request the system issues is accounted for, because on object storage request count is both the cost and the latency (MM3, §32).

2 Writer GET TableMetadata at that location
3 Writer build new DataFiles, write to object store
4 Writer build new ManifestFile(s) referencing those files, write to object store
5 Writer build new ManifestList referencing old + new manifests, write to object store
6 Writer build new Snapshot (sequence-number = old + 1, parent = old current)
7 Writer build new TableMetadata referencing the new snapshot, write to object store
8 Writer CAS catalog pointer: old-metadata-location → new-metadata-location
9a Catalog CAS succeeds — new state is current
9b Catalog CAS fails (pointer changed) — writer discards its metadata/snapshot objects (orphans, GC-eligible later) and restarts at step 1

Worked successful commit: writer A reads pointer P0 (seq 41). Builds manifest M-A, snapshot S42 (parent 41, seq 42), metadata T-A. CAS(P0→T-A) succeeds because no one else moved the pointer. Table is now at seq 42.

Worked conflicting-commit-and-retry: writer A and writer B both read pointer P0 (seq 41) concurrently. A commits first: CAS(P0→T-A) succeeds, pointer now T-A (seq 42). B attempts CAS(P0→T-B); the catalog's current value is T-A, not P0, so the CAS fails. B rereads T-A, rebuilds its manifest/snapshot on top of seq 42 (parent 42, seq 43), and retries CAS(T-A→T-B'); this second attempt succeeds if no third writer intervened.

8.3 Schema-evolution model

Column identity = field-id, assigned once, never reused, independent of name or position.

Change Safe without rewrite? Rule
Add column yes new field-id, default null for existing files
Drop column yes field-id retired, never reassigned; old files keep the data physically, reader ignores it
Rename yes field-id unchanged; only the name map changes
Reorder yes field-id unchanged; physical file order irrelevant, projection is by ID
Type promote (int→long, float→double, decimal precision increase) yes reader upcasts; field-id unchanged
Type change requiring narrowing (long→int) no rejected by validator (I5)
Reuse a retired field-id for a new column no rejected — would misinterpret old files' values under the new column's meaning

8.4 Hidden partitioning and transforms

Transforms: identity, bucket[N], truncate[W], year, month, day, hour. A PartitionField binds a source column + transform to a partition field-id; the partition value is derived at write time and stored in the manifest, never supplied by the writer's query predicate.

Worked pruning example: table partitioned by day(event_ts), query predicate event_ts >= '2026-08-01' AND event_ts < '2026-08-02'. Planner derives the transform-range day = 2026-08-01, discards every manifest-list entry whose partition-summary range does not intersect that single day, then discards every remaining manifest entry whose day value differs — data-column predicate, zero manual partition-column handling by the query.

8.5 Scan-planning-and-pruning algorithm (named steps)

  1. Partition predicate derivation — translate the data-column predicate into the table's active transform space.
  2. Manifest-list pruning — discard manifests whose partition-value summary cannot satisfy the derived predicate.
  3. Manifest-entry pruning (partition stats) — within surviving manifests, discard entries whose per-file partition tuple cannot satisfy the predicate.
  4. Data-file pruning (column stats) — discard files whose lower/upper-bounds/null-value-counts prove no row can match the residual (non-partition) predicate.
  5. Delete-file association — attach applicable delete files (by partition + sequence-number range) to each surviving data file.
  6. Row filtering — deferred to the engine at execution time via the residual predicate carried in FileScanTask.

Worked example: table has 10,000 files across 365 daily partitions (≈27 files/day). Query: day = X AND price > 1000. Step 2 prunes to the 1 day's manifest(s) (≈27 files' worth of entries survive out of 10,000 — 99.7% eliminated at list level, zero file bytes read). Step 4, using column stats on price, further eliminates files whose upper-bound(price) <= 1000; assume 40% of the day's files qualify → 11 files scanned out of 10,000 (99.89% total elimination), 2 object-store GETs (manifest-list + 1 manifest) to plan it.

8.6 Row-level delete model

Dimension Copy-on-write Merge-on-read
Write cost rewrite every file containing a changed row write only a small delete file
Read cost none (data already reconciled) apply delete file(s) per scan
Write amplification high — full file rewrite per touched file low — bytes proportional to changed rows
Read amplification none grows until compaction folds deletes into data
Delete file kind n/a position delete (file+row-offset) or equality delete (predicate-equivalent values)
Isolation trivial — new snapshot references new files requires sequence-number-ordered application (I7, I9)

8.7 Time travel and rollback

Time travel: plan a scan against any historical snapshot-id (or timestamp resolved to the nearest snapshot ≤ it) still present in the snapshot-log; cost equals a normal scan at that snapshot (§4) — no replay. Rollback: set current-snapshot-id to a prior snapshot via a normal commit (a new "rollback" snapshot whose manifest list is a pointer to the old one); this is itself an atomic-commit (§8.2), so rollback is crash-safe and never partial.

8.8 Expire-snapshots / orphan-file GC

Procedure: (1) select snapshots older than the retention policy and not referenced by a named SnapshotRef (tag/branch); (2) remove them from the snapshot-log in a normal commit; (3) compute the file-reachability set from all remaining live snapshots' manifest trees; (4) list files in the table's data/metadata paths; (5) delete any file not in the reachability set, respecting I3/I11 ordering — expiry (steps 1–2) must be durably committed before reachability (step 3) is computed. Safety condition: no delete proceeds unless the deleting worker's reachability computation was taken after the expiry commit it depends on, and no concurrent commit within the same window added a snapshot referencing an about-to-be-deleted file.

8.9 Table lifecycle state machine

CREATED -> ACTIVE -> (COMMIT)* -> ACTIVE
ACTIVE -> SCHEMA_EVOLVING -> ACTIVE
ACTIVE -> PARTITION_EVOLVING -> ACTIVE
ACTIVE -> MAINTENANCE (compaction/expire/GC) -> ACTIVE
ACTIVE -> DROPPED (catalog entry removed; files orphaned pending GC)

8.10 Malformed / failure examples

  • Two concurrent conflicting commits on overlapping partitions — resolved by CAS failure + retry (§8.2); no lost update because the loser's write is fully discarded, not merged.
  • A schema change that would lose data (narrowing a type) — rejected by validator before any metadata is written (I5).
  • GC racing a long-running read — reader pinned an old snapshot (I1) that GC's reachability computation must still count as live if not yet expired; GC run before expiry commit is a defect (I11).
  • A stale metadata pointer on an eventually-consistent catalog backend — CAS must be backed by the catalog's own strong-consistency guarantee (ADR-27); a catalog without CAS cannot safely host this protocol.
  • A corrupt manifest (bad Avro/JSON, checksum mismatch) — quarantined at read time, scan fails closed rather than silently under-reading (I8).

Failure-path example: writer completes steps 1–7 of §8.2, then crashes before step 8. The written manifest/manifest-list/metadata objects are never referenced by any pointer — they are orphans from birth, discovered and removed by the next OrphanFileGc pass; the table's current pointer never moved, so no reader was ever affected.

8.11 Statistics-sketch extension point

Beyond the mandatory min/max/null-count/value-count carried in every ColumnStats (§8.1, ADR-12), a table may attach a separate sketch file (Puffin-format, referenced by path from the manifest) holding richer per-column summaries — theta sketches for approximate distinct-count, or bloom-filter-style membership sketches for high-cardinality equality predicates that min/max cannot prune.

Sketch kind Use Pruning contribution
Theta sketch (approx. distinct count) cardinality estimation for join/aggregation planning by the consuming engine not used for file elimination directly; informs the engine's own plan, not this project's pruning step
Bloom-filter-style membership sketch equality-predicate pruning on high-cardinality columns where min/max rarely excludes a file extends step 4 of §8.5: a file is eliminated if the sketch proves the predicate value is definitely absent

Because a sketch file is optional, referenced metadata, and additive (P9 — manifests and their referenced statistics are self-similar, immutable objects), a reader that does not understand a given sketch kind simply ignores it and falls back to min/max-only pruning (P11 forward compatibility) — a missing or unrecognized sketch is never an error, only a missed pruning opportunity.

12. Phase 0 — Skeleton, Object-Store Adapter, Parquet Bridge, CI

12.1 Objectives

Establish the workspace, the ObjectStore trait plus a local-filesystem and an S3-compatible adapter, a parquet-bridge wrapping an external Parquet crate for read/write and footer-statistics extraction, and a CI pipeline gating every subsequent phase.

12.2 Detailed Implementation Steps

Workspace laid out per §10. ObjectStore (§11) is designed around P13 — every method call is one accountable request; the local adapter uses atomic rename to emulate put_if_absent (ADR-04's fallback path), the S3 adapter uses conditional PUT per ADR-27's strong-read-after-write assumption. The Parquet bridge never decodes row groups for statistics — it reads only the file footer's per-column-chunk min_value/max_value/null_count (Parquet format spec), matching the non-goal boundary in §1 (delegates the codec to project 410's territory). CI wires cargo test, cargo clippy, cargo fmt --check per ADR-24.

12.3 Deliverable

A compiling workspace; ObjectStore trait with two working adapters; a parquet-bridge that round-trips a Parquet file and extracts footer stats into ColumnStats; green CI on every crate.

12.4 Acceptance Criteria

Round-trip test writes 10K-row Parquet file, reads it back, footer-extracted ColumnStats.lower_bound/upper_bound match a reference computation on 100% of numeric columns; put_if_absent semantics verified via a race test with 50 concurrent callers — exactly one wins, 49 observe CommitConflict-equivalent rejection; CI green on 3 consecutive commits.

12.5 Conformance Fixtures

fixtures/parquet/basic_10k_rows.parquet; fixtures/parquet/all_null_column.parquet; fixtures/objectstore/cas_race_50_writers/; fixtures/objectstore/local_vs_s3_adapter_parity/.

12.6 Pitfalls

  1. Local-filesystem atomic rename is not equivalent to a true CAS across NFS-mounted paths — silently drops the "only one wins" guarantee.
  2. Parquet footer stats can be absent for a column (writer-side stats disabled) — must be treated as "no pruning possible," never as "no rows."
  3. S3 conditional-PUT semantics vary across S3-compatible third-party stores — some silently accept overwrite.
  4. Footer-only stats extraction can be fooled by a Parquet file with corrupted footer but valid data pages — must checksum the footer independently.

12.7 Performance Concerns

Footer read is a ranged GET (last few KB), not a full-file GET — object-store request cost stays O(1) per file regardless of file size.

12.8 Edge Cases

Zero-row Parquet file; Parquet file with zero row-groups; object-store adapter against a bucket with a trailing-slash-sensitive prefix.

12.9 Failure Analysis

An ObjectStore adapter that silently succeeds on a CAS it should have rejected undermines every invariant in §7 built above it — this phase's test suite is a prerequisite gate for Phase 3, not just a Phase-0 nicety.

12.10 Operational Notes

Emit objectstore_request_total{op} from day one so §4's request-count budget is measurable starting in Phase 0, not retrofitted later.

13. Phase 1 — The Metadata Tree and a Read-Only Table

13.1 Objectives

Implement TableMetadata, Schema, PartitionSpec, Snapshot, ManifestList, ManifestFile, ManifestEntry, DataFile (§11) with versioned JSON/Avro-shaped (de)serialization, and a read-only table that can load a hand-authored metadata tree and enumerate its data files.

13.2 Detailed Implementation Steps

Serialization is deterministic (sorted map keys, ADR-26) so golden-file tests are exact-byte-comparable. Field-ID assignment for Schema follows P4/I5 from the first commit onward — even in a read-only phase, the model must already be evolution-safe. The metadata hierarchy is exactly the tree in §8.1: TableMetadata → snapshot-log → Snapshot → ManifestList → ManifestFile → ManifestEntry → DataFile. Dremel's columnar/nested representation (Melnik et al. 2010) informs how nested Schema.fields are flattened for field-ID lookup without recursion blowup.

13.3 Deliverable

A crate that loads a TableMetadata JSON file, resolves its current snapshot, walks the manifest list and manifests, and returns the full DataFile set — no writes, no commits.

13.4 Acceptance Criteria

Loads and round-trips the Iceberg-spec-shaped fixture set (§5 RFC entry) byte-identically on re-serialize; walks a 3-level manifest tree (list → 5 manifests → 500 entries) and returns exactly 500 DataFiles in under 50 ms; rejects a metadata file whose format_version exceeds the reader's supported maximum (I12).

13.5 Conformance Fixtures

fixtures/metadata/table_v2_basic.json; fixtures/metadata/nested_schema.json; fixtures/manifest/500_entry_tree/; fixtures/metadata/unsupported_future_version.json.

13.6 Pitfalls

  1. Recursive nested-struct schemas can stack-overflow a naive recursive walker — must be iterative or depth-bounded.
  2. A manifest-list summary referencing a manifest that was deleted (dangling pointer) must fail closed, not skip silently.
  3. JSON key ordering differences between writers break naive byte-equality tests even when semantically identical — golden tests must normalize or the writer must sort keys (ADR-26).
  4. Avro schema evolution of the manifest format itself (not the table's schema) is a distinct concern from table schema evolution — conflating them is a common early bug.

13.7 Performance Concerns

Tree-walk allocation should reuse buffers across manifest reads; avoid materializing all DataFiles in memory for very large tables — stream via iterator (bounded-memory traversal, foreshadowing P3/§6).

13.8 Edge Cases

Empty snapshot-log (freshly created table, no data yet); a ManifestList with zero manifests; a schema with zero fields (degenerate but must not panic).

13.9 Failure Analysis

A tree-walk bug that silently drops a manifest produces a table that looks fine but under-reads data — the most dangerous class of bug in this phase because nothing crashes; only differential testing against a reference tree catches it.

13.10 Operational Notes

Log the exact object-store paths visited during a load, at debug level, so a read-only-table incident can be replayed path-for-path.

14. Phase 2 — Snapshot Model and Scan Planning

14.1 Objectives

Implement SnapshotRef, sequence numbers, and the full scan-planning pipeline (§8.5): partition-predicate derivation, manifest-list pruning, manifest-entry pruning, data-file pruning, producing ScanPlan/FileScanTask.

14.2 Detailed Implementation Steps

Pruning is implemented as the four named steps of §8.5, each citing its own invariant/principle: list-level pruning uses the partition_value_summary per ADR-08/P3; file-level pruning uses ColumnStats.lower_bound/upper_bound per P3/I8; predicate translation into transform space implements P8 (hidden partitioning) directly — Graefe 1993's pushdown framing is the model for where residual-vs-eliminated predicates split. Snapshot pinning for the duration of planning implements I1.

14.3 Deliverable

A scan planner that takes a Predicate and an optional SnapshotId (default: current) and returns a ScanPlan with correct pruning at both list and file level, benchmarked against the numeric targets in §4.

14.4 Acceptance Criteria

On the 10,000-file/365-partition fixture (§8.5 worked example), a single-day-equality query prunes to ≤ 30 files scanned via list-level pruning alone (matching the ≈27-file/day worked figure) and issues ≤ 2 object-store GETs to plan it; scan-planning p95 < 100 ms at N=10K files (§4); zero false negatives across 10,000 property-test-generated predicate/file-stats pairs (a file that could match is never pruned).

14.5 Conformance Fixtures

fixtures/planning/10k_files_365_partitions/; fixtures/planning/predicate_pushdown_cases/; fixtures/planning/null_heavy_columns/; fixtures/planning/false_negative_property_corpus/.

14.6 Pitfalls

  1. Over-pruning on a NULL-containing column when the predicate is IS NOT NULL versus a naive min/max check — must special-case null-count.
  2. NaN values in float columns break naive min/max comparisons (NaN is neither less-than nor greater-than) — must be excluded from bound computation, not compared directly.
  3. Multi-manifest scans where two manifests use different partition-spec-ids (post partition-evolution) require per-manifest spec-aware predicate translation, not one global translation (I6).
  4. A predicate on a column added after some files were written (no stats present in older manifests) must default to "cannot prune," never "no match."

14.7 Performance Concerns

Manifest-list summaries are read once per plan and should be cached across repeated plans against the same snapshot (motivates the manifest cache named in §26/§31); avoid re-parsing the same manifest file for two overlapping queries.

14.8 Edge Cases

A predicate that matches zero partitions (empty ScanPlan, valid, not an error); a predicate referencing a dropped field-id (must resolve against the schema active at file-write time, not the current schema).

14.9 Failure Analysis

A pruning bug that drops a matching file causes silent data loss in query results — the single most severe correctness class in this phase; the false-negative property test in §14.4 is the primary gate, tied to I8.

14.10 Operational Notes

Emit planner_files_pruned_ratio and planner_objectstore_requests_total per plan call — these are the numbers §30/§34 build capacity models from.

15. Phase 3 — Atomic-Commit / Optimistic-Concurrency Engine

15.1 Objectives

Implement the commit engine per the §8.2 sequence table: read-metadata, build-manifest, build-snapshot, build-metadata, CAS-publish, with conflict detection and retry.

15.2 Detailed Implementation Steps

The engine implements P1/P6/I2/I9/I10 directly: exactly one CAS call per attempt (Catalog::cas_pointer), everything before it is pure local computation with no side effect on shared state. Sequence-number allocation happens as part of building the new Snapshot, validated monotonic against the base (I9); parent-pointer validation prevents cycles (I10). Retry-on-conflict rereads the new base and rebuilds rather than attempting to merge — this is the optimistic-concurrency model from Gray & Reuter ch. 7, applied per ADR-06. Herlihy & Wing 1990's linearizability framing justifies treating the catalog's CAS as the sole linearization point of a commit.

15.3 Deliverable

A commit engine supporting concurrent independent writers against one table, retrying on conflict with bounded backoff, producing the worked successful and worked conflicting-retry traces of §8.2 as passing integration tests.

15.4 Acceptance Criteria

50 concurrent writers appending disjoint partitions to one table: 0 lost updates, commit-conflict/retry rate < 5% (§4 target); a fixed two-writer race (§8.2 worked conflict example) deterministically reproduces exactly one CAS success and one CAS failure-then-successful-retry across 1,000 repeated runs; no partial metadata tree is ever observable by a concurrent reader (I4) — verified by a reader thread continuously loading TableMetadata during the stress run and asserting every load resolves a complete tree.

15.5 Conformance Fixtures

fixtures/commit/two_writer_conflict_deterministic/; fixtures/commit/50_writer_disjoint_partitions/; fixtures/commit/sequence_regression_attempt/ (must be rejected); fixtures/commit/cyclic_parent_attempt/ (must be rejected).

15.6 Pitfalls

  1. ABA-style pointer reuse: if a metadata-location naming scheme ever reuses a path, a stale CAS could "succeed" against the wrong generation — naming must be monotonic/UUID-suffixed, never reused.
  2. Retry storms under high contention: naive immediate-retry amplifies conflict rate superlinearly — requires the backoff policy named in ADR list and measured in §4/§30.
  3. A writer that crashes after step 7 (metadata written) but before step 8 (CAS) leaves orphan objects that must never be mistaken for the current state by any reader (failure-path example, §8.10) — reader path must never guess at an uncommitted location.
  4. Clock-based sequence assumptions: sequence numbers must be allocated from the metadata chain, never from wall-clock time, or clock skew across writers silently violates I9.
  5. A catalog backend whose CAS is not truly atomic (e.g., a check-then-set pair, not a single primitive) reintroduces the exact race this whole phase exists to remove — must be excluded at the Catalog trait's contract level, tested via the race fixture from Phase 0.

15.7 Performance Concerns

Commit latency (§4 p50/p95/p99) is dominated by object-store round trips, not local computation — batch manifest writes where possible and minimize sequential dependent GETs on the hot path.

15.8 Edge Cases

Zero-file commit (schema-only change, empty manifest delta); a retry that discovers the base has advanced by more than one sequence number (multiple competing commits since last read) — must still rebuild against the latest base, not the writer's original.

15.9 Failure Analysis

Conflict-storm behavior under 500+ concurrent writers (§4's upper concurrency assumption) is the primary long-tail risk graduating out of this phase — Phase 11's stress harness (§28's Elle/Jepsen-style checker) is what ultimately certifies this path, but the retry-bound acceptance test here is the first gate.

15.10 Operational Notes

Emit commit_latency_ms histogram, commit_conflicts_total, and commit_retry_depth per attempt from this phase onward — these three series are what §26's commit-conflict-storm runbook keys off.

16. Phase 4 — Schema Evolution with Stable Column IDs

16.1 Objectives

Implement the field-ID allocator and the add/drop/rename/reorder/type-promote validators of §8.3, producing a new Schema object per change without touching any existing DataFile.

16.2 Detailed Implementation Steps

Every change is validated against the decision table in §8.3, directly enforcing P4/I5: field-IDs are allocated monotonically and never reused (retired IDs recorded, not recycled) — this is the mechanism, not just the principle, behind "rename is free." Type-promotion validation implements Kleppmann ch. 3's schema-on-read framing: old files remain byte-identical, only the read-time interpretation of a field-id's type changes. A schema-diff planner (old Schema vs. proposed Schema) computes the field-ID delta and classifies each change against the table in §8.3 before any commit is attempted (fail before write, not after).

16.3 Deliverable

A schema-evolution engine exposing add_column, drop_column, rename_column, reorder, promote_type, each returning a new Schema (new schema_id) or a rejection with a specific violated-invariant reason, committed via the Phase-3 engine as a schema-only TableMetadata update.

16.4 Acceptance Criteria

100% of the §8.3 decision-table rows have a corresponding passing/rejecting test; a rename-then-read-old-file test proves zero data-file rewrite (file mtimes/checksums unchanged pre/post rename); an attempted narrowing type change (long→int) is rejected before any object-store write occurs (zero orphan objects produced by a rejected change); nested-field evolution (add a field inside a struct) passes the same field-ID-stability check recursively.

16.5 Conformance Fixtures

fixtures/schema/rename_column.json; fixtures/schema/add_nested_field.json; fixtures/schema/reject_narrowing.json; fixtures/schema/reject_field_id_reuse.json; fixtures/schema/promote_int_to_long.json.

16.6 Pitfalls

  1. Reordering fields in the JSON schema representation without touching field-IDs can accidentally be conflated with a rename if the validator matches by position instead of ID — must always match by field-id.
  2. Dropping and later re-adding a column with the same name must allocate a new field-id, not resurrect the old one, or old dropped-column data becomes visible under the new column's identity (I5 violation).
  3. Struct-nested field-ID collision: two independently evolved branches of a nested struct schema could allocate overlapping IDs if the allocator isn't table-global — must be a single monotonic counter per table, not per struct.
  4. Type promotion inside a map or list element type needs the same promotion rules applied recursively — easy to implement only at the top level and miss nested containers.

16.7 Performance Concerns

Schema-diff computation is O(fields), trivial next to the object-store round trips of the commit it rides on — no dedicated performance budget beyond Phase 3's commit-latency numbers.

16.8 Edge Cases

Renaming a column to a name that collides with another live column's current name (must reject, since name is a lookup convenience, not identity, but duplicate live names are still disallowed for engine compatibility); promoting a type on a column that has zero data files yet (trivially safe).

16.9 Failure Analysis

A field-ID reuse bug is silent and severe: readers of old snapshots interpret old bytes under the new column's semantics, producing wrong-but-plausible values rather than an error — this is why I5's enforcement point is a hard pre-commit check, not a warning.

16.10 Operational Notes

Every applied schema change is logged with old-schema-id, new-schema-id, and the specific field-ids touched, at info level — schema-evolution audit trail feeds the schema-evolution-rollback runbook (§26).

17. Phase 5 — Hidden Partitioning and Partition Transforms

17.1 Objectives

Implement the transform registry (identity, bucket[N], truncate[W], year, month, day, hour), PartitionSpec evolution, and mixed-spec scan planning across manifests written under different specs.

17.2 Detailed Implementation Steps

Transforms implement P8 directly: the writer computes PartitionValue from the transform + source column at write time, and the planner derives predicate-to-transform translation at plan time (§8.4's worked example) — the query never names a partition column. Partition-spec evolution (I6) keeps old manifests tagged with their original partition-spec-id; the planner evaluates each manifest under its own spec rather than forcing a global translation, directly implementing the "never requires rewriting old data" half of P8. bucket[N] uses a stable hash (must be identical across writer versions — a hash-algorithm change is effectively a breaking spec change and must bump the transform's own version marker).

17.3 Deliverable

A transform registry usable by both the write path (deriving PartitionValue) and the scan planner (deriving predicate ranges), plus a partition-spec-evolution API (add_partition_field, remove_partition_field) that produces a new spec_id without touching existing manifests.

17.4 Acceptance Criteria

The §8.4 worked pruning example reproduces exactly: day-partitioned predicate prunes to the single day's manifests with zero false negatives across a 365-partition fixture; a partition-spec evolution mid-table-history (old data under spec 0, new data under spec 1) scans correctly across both specs in one query, verified against a fixture with manifests under both specs; bucket[16] hash stability verified byte-identical across two independent invocations of the transform on 10,000 sample values.

17.5 Conformance Fixtures

fixtures/partition/day_transform_365/; fixtures/partition/bucket_16_stability/; fixtures/partition/mixed_spec_old_and_new/; fixtures/partition/truncate_string_prefix/.

17.6 Pitfalls

  1. null source-column values under a transform must map to a defined "null partition" bucket, not be silently dropped from any partition or crash the transform function.
  2. Timezone handling in day/hour transforms: a source timestamp without explicit UTC normalization produces different partition values depending on reader locale — must normalize to UTC before transform application, always.
  3. truncate[W] on a string column with multi-byte UTF-8 characters must truncate at a byte boundary consistent with the writer's encoding, or two writers on different locales produce different partition values for logically identical input.
  4. Evolving from bucket[16] to bucket[32] on the same source column does not let old bucketed files be reinterpreted under the new bucket count — the planner must never assume old and new bucket values are comparable (I6's "own spec" rule again).

17.7 Performance Concerns

Bucket-transform hashing must be O(1) per value and vectorizable; avoid per-value heap allocation in the hot write path where millions of rows are bucketed per commit.

17.8 Edge Cases

A PartitionSpec with zero fields (unpartitioned table) — must be a valid, common case, not a special error path; a transform applied to a column that is later dropped via schema evolution (partition field must remain valid by referencing the retired field-id's last known type).

17.9 Failure Analysis

A partition-pruning bug under mixed specs (old data under spec 0 evaluated against spec-1 assumptions) either drops matching files (silent data loss, worse) or fails to prune at all (correct but slow) — the mixed-spec fixture in §17.5 is the primary regression gate because single-spec tests cannot catch this class.

17.10 Operational Notes

Emit partition_selectivity_ratio per scan and active_partition_spec_count per table — a table accumulating many live specs without ever consolidating is an early signal for the small-files/spec-sprawl problem addressed operationally in Phase 10.

18. Phase 6 — Column Statistics and Manifest/File Pruning

18.1 Objectives

Populate ColumnStats (min/max/null-count/value-count) from the Parquet bridge at write time, and extend the scan planner's step 4 (§8.5) to use them for file-level elimination, closing the loop from §8.5's worked example.

18.2 Detailed Implementation Steps

Statistics are extracted at write time from Parquet footers only (P3, non-goal boundary with project 410) and stored keyed by FieldId (P4) so stats survive rename/reorder. File pruning implements Graefe 1993's predicate-pushdown model precisely at the file granularity: a residual predicate is evaluated against lower_bound/upper_bound per column before any row is read, per the four-step algorithm in §8.5. Abadi/Madden/Hachem's column-store execution framing (SIGMOD 2008) motivates why per-column stats — rather than per-row or per-block-only stats — are the right granularity for this workload.

18.3 Deliverable

Statistics population wired into the commit path (every new DataFile entry carries populated ColumnStats); the planner's step-4 file-pruning fully implemented and measured against the §4/§8.5 numeric targets (99%+ elimination on the worked selective-query example).

18.4 Acceptance Criteria

The §8.5 worked example reproduces the stated 11-of-10,000-files result (±10% tolerance) on the reference fixture; a property test asserts zero false negatives across 10,000 generated (predicate, file-stats) pairs (no file that could contain a matching row is ever pruned) — this is the same class of test as §14.4 but now exercising real Parquet-footer-derived stats rather than synthetic ones; pruning-ratio telemetry (§4) matches the measured elimination percentage within rounding.

18.5 Conformance Fixtures

fixtures/pruning/selective_query_10k_files/; fixtures/pruning/all_null_column_predicate/; fixtures/pruning/nan_float_column/; fixtures/pruning/false_negative_property_corpus_v2/ (now Parquet-footer-backed, not synthetic).

18.6 Pitfalls

  1. Parquet writer-side stats can be disabled per-column for wide/rarely-queried columns — the pruning path must treat "stats absent" as "cannot prune this file on this column," never as an error or a false match.
  2. Decimal-typed column bounds require exact fixed-point comparison, not floating-point coercion, or boundary-value predicates silently misprune.
  3. A predicate combining an AND across two columns must apply file-level pruning per-column and combine conservatively (a file survives if it is not provably excluded by either), not optimistically.
  4. Corrupted or adversarially crafted footer stats (T5 in §24) must not cause the planner to trust an out-of-range bound blindly — a defensive sanity check against record_count bounds catches gross corruption.

18.7 Performance Concerns

Stats extraction happens once at write time and is amortized across every future scan that touches the file — this is the core justification for P3's cost model; re-extracting stats at scan time would defeat the entire design.

18.8 Edge Cases

A single-row file (min == max on every column, trivially prunable or trivially matched); an all-null column (null_count == value_count, no valid bounds — must be handled as "no non-null values," not as a bound of zero).

18.9 Failure Analysis

Because pruning bugs are silent-data-loss bugs (as established in Phase 2), this phase's property-test corpus (§18.4) is treated as a release gate, not an optional check — a regression here can ship undetected by ordinary example-based tests for months.

18.10 Operational Notes

Dashboard the pruning-ratio distribution across production queries (§26); a sudden drop in average pruning ratio for a table is an early signal of stats going stale (e.g., a writer path that stopped populating ColumnStats) before it becomes a customer-visible latency regression.

19. Phase 7 — Row-Level Deletes (Copy-on-Write)

19.1 Objectives

Implement copy-on-write update/delete: given a predicate, rewrite every affected DataFile into new file(s) excluding/updating the matching rows, and commit the replacement atomically.

19.2 Detailed Implementation Steps

Copy-on-write is a pure application of P2/P1: an update is "read affected files, write new files without the deleted/changed rows, commit a snapshot whose manifest marks old entries deleted and new entries added" — no in-place mutation anywhere, per §8.6's comparison table. The affected-file set is computed via the Phase-6 pruning path (any file that might contain a matching row must be rewritten, using the same conservative-pruning discipline as scan planning — a false negative here would silently skip a row that should have been deleted). The old files remain physically present and readable by any snapshot that still references them (P2, I3), deleted only by later GC.

19.3 Deliverable

A copy-on-write delete/update API taking a Predicate, producing a new snapshot whose manifest correctly marks superseded files deleted (metadata-only, I3-respecting) and rewritten files added.

19.4 Acceptance Criteria

A delete-by-predicate against a 1,000-file fixture rewrites only the files whose stats could not exclude a match (measured against the same pruning-ratio numbers as Phase 6, since the affected-file computation reuses that path); post-delete scan at the new snapshot returns zero rows matching the delete predicate; a scan at the prior snapshot still returns the original rows unchanged (time-travel-visible immutability, P2); write-amplification measured equals rewritten-file-bytes / touched-row-bytes and is reported against the §34 capacity-model formula.

19.5 Conformance Fixtures

fixtures/cow/delete_by_predicate_1000_files/; fixtures/cow/update_changes_value/; fixtures/cow/prior_snapshot_still_visible/; fixtures/cow/full_file_match_no_rewrite_needed/ (delete-all-rows-in-file case, where the file is simply marked deleted with no rewrite).

19.6 Pitfalls

  1. A file that is 100%-matched by the delete predicate should be marked deleted directly, not rewritten as an empty file — rewriting an empty file wastes an object-store write and complicates GC bookkeeping for no benefit.
  2. Concurrent copy-on-write operations on overlapping files must be caught by the Phase-3 OCC engine as a normal commit conflict — a naive implementation that doesn't route through the shared commit path can silently lose one operation's rewrite.
  3. A crash between "new files written" and "commit published" must leave the old files' visibility completely unaffected — the failure-path example of §8.10 applies identically here; orphaned rewritten files are GC-eligible, not a correctness problem.
  4. Rewriting a file changes its statistics (Phase 6) — the new file's ColumnStats must be freshly computed, never copied from the old file's stats under the assumption "the surviving rows have the same bounds."

19.7 Performance Concerns

Write amplification (§4, §8.6) is the dominant cost here — copy-on-write throughput is bounded by Parquet re-encode throughput (Phase 0's bridge), not by this project's own logic; batch multiple small predicate-matched files into fewer, larger rewritten files where the compaction target size (Phase 10) allows.

19.8 Edge Cases

A predicate matching zero rows in a candidate file after conservative pruning flagged it as possibly-matching (the file is left untouched, not rewritten — pruning conservatism means some rewrites turn out to be no-ops, which is correct behavior, not a bug); a delete predicate matching 100% of all files in the table (degenerates to "replace all data," still one atomic commit).

19.9 Failure Analysis

The single most dangerous bug class here is a delete that silently fails to rewrite a file it should have — because the affected-file computation shares code with scan pruning, a bug in one surfaces identically in the other, which is why the false-negative property corpus from Phase 6 is re-run against this phase's delete path as a regression gate, not just against reads.

19.10 Operational Notes

Track cow_write_amplification_ratio per delete/update operation — this feeds directly into the decision (operator-level, per table) of whether a given table should move to merge-on-read (Phase 8) instead.

20. Phase 8 — Merge-on-Read Delete Files

20.1 Objectives

Implement DeleteFile writing (position deletes and equality deletes), sequence-number-scoped applicability, and scan-time delete application (§8.5 step 5, §8.6, I7/I9).

20.2 Detailed Implementation Steps

Merge-on-read implements the other half of P12: a delete is recorded as a small additive file, never a data-file rewrite. Position deletes (file-path + row-offset) are cheap to write and cheap to apply for a known, stable file; equality deletes (predicate-equivalent values) are used when the position isn't known yet (e.g., streaming upserts) but are more expensive to apply since every row must be checked against the predicate. I7 (applicable delete files must be respected) and I9 (sequence-number monotonicity) together define applicability: a DeleteFile with applies_to_seq_ge = N applies to any DataFile with sequence_number < N, never to files written after the delete (a later file cannot need a delete written before it existed).

20.3 Deliverable

A DeleteFile writer supporting both content types; scan-planner step 5 (delete-file association) fully implemented, attaching applicable deletes to each FileScanTask; engine-facing residual delete application left to the caller per the FileScanTask.delete_files field (ADR-19 boundary).

20.4 Acceptance Criteria

A position-delete fixture (delete 5% of rows in a 100-file table) shows correct row exclusion on 100% of a 10,000-row differential check against a reference "apply deletes manually" computation; an equality-delete fixture with overlapping predicates from two separate delete commits correctly composes (both apply, sequence-ordered); read amplification (delete-files-applied-per-scan, §4/§8.6) is measured and reported; a delete file with applies_to_seq_ge greater than a candidate data file's sequence number is correctly excluded from that file's task (I9 respected).

20.5 Conformance Fixtures

fixtures/mor/position_delete_5pct/; fixtures/mor/equality_delete_overlapping/; fixtures/mor/sequence_scoped_applicability/; fixtures/mor/delete_file_wrong_scope_must_not_apply/.

20.6 Pitfalls

  1. Position deletes referencing row offsets computed before a concurrent compaction rewrote the target file become invalid — position deletes must be scoped to a specific, immutable file identity (path + a content id), never a mutable row-offset-only reference.
  2. Equality deletes on a column later dropped by schema evolution (Phase 4) must remain interpretable against the schema active when the delete was written, not the current schema — delete-file schema binding follows the same field-ID discipline as data files.
  3. Two equality deletes with contradictory predicates from racing writers must both survive (union of exclusions), never overwrite one another — deletes are additive, resolved by the normal OCC commit path just like any other manifest change.
  4. Applying deletes at scan time without respecting sequence-number scoping (I9) can delete rows from a file that didn't exist yet when the delete was authored, an easy off-by-one if sequence comparison uses <= where the spec requires strict <.
  5. Very high delete-file-count-per-data-file (unbounded read amplification) degrades scan latency invisibly until it crosses a compaction threshold — must be measured, not assumed bounded.

20.7 Performance Concerns

Read amplification (§4, §8.6) grows linearly with un-compacted deletes per file — this phase's acceptance criteria explicitly measure it because Phase 10's compaction trigger threshold is calibrated against this number.

20.8 Edge Cases

A data file with zero applicable deletes (common case, must add zero overhead to the scan task); a delete file that logically deletes 100% of its target file's rows (still valid — becomes a compaction candidate, not an error).

20.9 Failure Analysis

An incorrect sequence-number scoping bug either resurrects deleted rows (visible in results, high-severity) or over-deletes rows from files that shouldn't be affected (silent under-read) — both are I7 violations and both are caught by the differential-against-reference check in §20.4, which must run on every PR touching this path.

20.10 Operational Notes

Emit mor_read_amplification_ratio and mor_delete_files_per_datafile_p95 — a sustained rise in the latter is the operational trigger named in Phase 10 for scheduling delete-compaction.

21. Phase 9 — Time Travel, Rollback, and Snapshot Refs

21.1 Objectives

Implement historical-snapshot scan planning (time travel), the rollback-via-commit operation, and named SnapshotRefs (tags/branches) that pin retention.

21.2 Detailed Implementation Steps

Time travel is "plan against a chosen snapshot_id instead of current" — nothing else changes, which is the direct payoff of P2/P1 promised in §8.7: no replay cost because history is a pointer choice. Rollback is implemented as a normal atomic commit (§8.2) whose new snapshot's manifest list is the target historical snapshot's manifest list — crash-safety of rollback is therefore inherited from Phase 3's commit engine for free, per MM2 (§32). SnapshotRefs (tag/branch) extend ExpireSnapshots' retention computation (Phase 10 dependency) — a tagged snapshot is excluded from expiry regardless of age.

21.3 Deliverable

A time_travel(snapshot_id | timestamp) planning entry point; a rollback(snapshot_id) commit operation; SnapshotRef creation/deletion wired into the retention computation used later by ExpireSnapshots.

21.4 Acceptance Criteria

A time-travel scan at a historical snapshot returns byte-identical results to what a contemporaneous scan returned at commit time (verified by re-running a recorded scan against a fixture with 10 historical snapshots); time-travel planning latency is statistically indistinguishable from a current-snapshot scan at the same file count (§4 "equal to a normal scan" claim, verified via benchmark comparison, not just asserted); rollback followed by a new commit produces a correctly linear (non-cyclic, I10-respecting) history, not a fork that confuses later planning.

21.5 Conformance Fixtures

fixtures/timetravel/10_snapshot_history_replay/; fixtures/timetravel/timestamp_to_nearest_snapshot/; fixtures/rollback/simple_rollback_then_commit/; fixtures/refs/tag_survives_expiry_window/.

21.6 Pitfalls

  1. Resolving a timestamp to "the nearest snapshot at or before it" versus "nearest overall" is a subtle off-by-one that silently returns future data for a past-dated query — must always resolve to the latest snapshot with timestamp_ms <= target, never a later one.
  2. Rollback does not delete the snapshots it "skips" — they remain in the snapshot-log and are still reachable/GC-safe until independently expired; a naive rollback implementation that truncates the log breaks I11's ordering assumption for any GC pass already in flight.
  3. A branch SnapshotRef that itself receives new commits diverges into a genuine fork — the acyclic-DAG invariant (I10) is per-branch, not global; cross-branch planning must never conflate two branches' histories.
  4. Tag retention interacting with expiry: a tag pinning a very old snapshot indefinitely prevents that snapshot's exclusive files from ever being GC'd — this is correct behavior but must be visible in snapshot-bloat telemetry (Phase 10/§26), not a silent storage leak.

21.7 Performance Concerns

Because time travel reuses the ordinary scan-planner path unmodified, no separate performance budget exists beyond Phase 2/6's — the acceptance test in §21.4 exists specifically to catch any accidental special-casing that would make it slower.

21.8 Edge Cases

A time-travel request for a snapshot_id that has already been expired and GC'd (must fail clearly — "snapshot no longer available" — never silently return an empty or wrong plan); a rollback target that is itself a rollback snapshot (must work identically, since it's just another node in the DAG).

21.9 Failure Analysis

The main risk graduating from this phase is a rollback that appears to succeed but leaves the catalog pointer referencing a manifest list that a concurrent GC pass, mid-flight, judged unreachable under a stale reachability snapshot — this is exactly the ordering hazard I11 exists to prevent, and this phase's fixtures are run jointly with Phase 10's GC fixtures in integration CI, not in isolation.

21.10 Operational Notes

Log every rollback with old-current-snapshot-id and new-current-snapshot-id at warn level (rollback is an operator-significant event); expose SnapshotRef list and age in the CLI's history command for the snapshot-bloat-cleanup runbook (§26).

22. Phase 10 — Compaction, Expire-Snapshots, and Orphan-File GC

22.1 Objectives

Implement the maintenance worker: data-file/manifest compaction (bin-packing to target size), ExpireSnapshots, and OrphanFileGc, wired to the two-phase safety ordering of §8.8/I11.

22.2 Detailed Implementation Steps

Compaction implements ADR-14's background bin-packing: small files below a target-size threshold are rewritten together into fewer, larger files via a normal copy-on-write-shaped commit (reuses Phase 7's commit machinery, since compaction is semantically "rewrite files, same data, new snapshot"). ExpireSnapshots removes old, unreferenced (no SnapshotRef) snapshot-log entries via a normal commit. OrphanFileGc computes reachability by walking every remaining live snapshot's manifest tree (reusing Phase 1's tree-walk) and deletes only files outside that reachable set — implementing I3/I11's mandatory ordering: expire-commit must be durably visible before the reachability computation that GC bases its deletes on is taken.

22.3 Deliverable

A maintenance daemon exposing compact(table, target_file_size), expire_snapshots(policy), and gc(dry_run: bool), each independently schedulable, with GC defaulting to dry_run = true until explicitly enabled per table.

22.4 Acceptance Criteria

Compaction on a 10,000-small-file fixture reduces file count by ≥ 90% while preserving row-for-row read equivalence (differential check against pre-compaction scan results); ExpireSnapshots against a 1,000-snapshot history retaining the last 100 and all tagged snapshots removes exactly the expected count (verified against §4's default retention policy); OrphanFileGc in a concurrent-reader stress test (a long-running reader pinned to an old, not-yet-expired snapshot runs throughout a full expire+GC cycle) shows zero read failures and zero incorrectly deleted files (I3 held under concurrency, not just in isolation); dry-run GC output matches actual-run deletion set exactly on a repeat run with no intervening commits.

22.5 Conformance Fixtures

fixtures/compaction/10k_small_files_bin_pack/; fixtures/expiry/1000_snapshot_history_with_tags/; fixtures/gc/concurrent_reader_during_expire_and_gc/; fixtures/gc/dry_run_matches_real_run/.

22.6 Pitfalls

  1. Running OrphanFileGc before the corresponding ExpireSnapshots commit is durably visible to the GC worker's own catalog read (a caching layer serving a stale pointer) violates I11 even if the two calls are issued in the "right" order by the operator — the worker must re-read the catalog fresh, not trust a cached pointer.
  2. Compaction racing a reader that has already planned a scan against pre-compaction files: the reader's FileScanTasks reference the old files by path, and those files must remain valid until no live plan references them — compaction's new snapshot does not retroactively invalidate an in-flight reader's already-issued task list (I1 protects this, but only if compaction never deletes pre-compaction files itself, deferring deletion entirely to a later GC pass).
  3. A LIST operation on the underlying object store that is even briefly stale (violating the ADR-16/27 assumption) during orphan-detection can miss a just-written file and delete it — this is why GC's reachability set is computed from the metadata tree (authoritative), and LIST is used only to find candidates for deletion, never as the source of truth for what's live.
  4. Bin-packing compaction that doesn't account for delete-file association (Phase 8) can silently orphan a delete file whose target data file was just compacted away — delete-file compaction/folding must be coupled to data-file compaction, not run independently.
  5. Default dry_run = true being overridden globally instead of per-table risks accidentally enabling live deletion on a table an operator didn't intend to touch — configuration must be explicit and table-scoped.

22.7 Performance Concerns

Compaction throughput (§4, ≥ 500 MB/s/worker) is bound by Parquet re-encode speed, not by this project's bookkeeping; GC's dominant cost is the LIST operation over the table's file prefixes at scale, which the reachability-tree walk (metadata-bound, not listing-bound) is specifically designed to minimize relative to.

22.8 Edge Cases

A table with zero expired snapshots (expire is a no-op commit, not skipped — still produces a snapshot-log update for audit purposes... or is explicitly skipped if nothing changed, per implementation choice, but must never error); GC finding zero orphans (valid, common, not a failure).

22.9 Failure Analysis

Unsafe GC is the single highest-severity failure mode in the entire system — it destroys data irreversibly — which is why dry-run defaults, the concurrent-reader stress fixture, and the GC-safety-incident runbook (§26) all exist specifically for this phase; no other phase in this blueprint has an equivalent "cannot be undone" failure class.

22.10 Operational Notes

Every GC run (dry or real) emits a manifest of exactly which files were identified as orphans and which were deleted, retained for audit; gc_reclaimed_bytes_total and orphan_file_count are the two headline metrics for the GC-safety-incident and snapshot-bloat-cleanup runbooks.

23. Phase 11 — Multi-Writer Stress, Engine-Integration API, Conformance and Perf Hardening

23.1 Objectives

Stress the commit engine under realistic multi-writer concurrency with an isolation checker, freeze the engine-integration API (ScanPlan/FileScanTask/Catalog/ObjectStore), and run the full conformance/differential/perf-regression gates to the v2-god bar.

23.2 Detailed Implementation Steps

The concurrency-stress harness runs many writers (§4's 500-concurrent-writer assumption) against shared and disjoint partitions and pipes the observed commit history through an Elle/Jepsen-style isolation checker validating I1/I2/I9/I10 hold under real contention, not just the fixed two-writer trace from Phase 3 — this is the named gate required by §28. The engine-integration API is frozen per ADR-19's boundary: ScanPlan/FileScanTask is the only execution-facing surface, and this phase's acceptance criteria include a differential check reading this project's tables with an external Iceberg-spec-compliant reader (DuckDB's Iceberg extension) to catch any accidental spec drift accumulated across Phases 1–10.

23.3 Deliverable

A concurrency-stress CI job (ADR-24) running to zero isolation-checker violations; a frozen, documented engine-integration API; a green cross-engine-compatibility CI job (ADR-24) reading this project's committed tables with an external Iceberg reader.

23.4 Acceptance Criteria

500-concurrent-writer stress run: 0 lost updates, 0 isolation-checker violations, commit-conflict/retry rate consistent with the model in §4/§34 (not unboundedly worse under load); cross-engine differential read (DuckDB Iceberg extension against a table written by this project) returns row-identical results across 20 conformance fixtures spanning Phases 1–10's feature set; full soak run (30-day-equivalent accelerated schedule) with continuous commits, compactions, and GC passes shows zero I3/I11 violations and zero data loss.

23.5 Conformance Fixtures

fixtures/stress/500_writer_isolation_checked/; fixtures/crossengine/duckdb_iceberg_read_20_cases/; fixtures/soak/30_day_accelerated_schedule/; fixtures/api/frozen_surface_snapshot_test/ (fails the build if the public API changes without a version bump).

23.6 Pitfalls

  1. Isolation-checker false negatives: a checker miscalibrated to snapshot isolation's actual guarantees (versus, say, serializability) can pass a run that genuinely violates I1 under a subtle interleaving — the checker's model itself must be validated against Bailis et al. 2014's isolation-level definitions before being trusted as a gate.
  2. Cross-engine differential tests can pass on the happy path but miss spec corners the external reader doesn't itself exercise (e.g., an external reader that silently ignores a manifest feature this project relies on) — differential testing supplements, never replaces, the Phase-1–10 property/fixture suites.
  3. API freezing too early (before Phase-10's maintenance API stabilizes) forces a breaking change later anyway — the freeze in this phase intentionally comes last, after every phase that shapes the surface.
  4. Soak-test acceleration (compressing 30 real days into a shorter run) can hide time-dependent bugs (e.g., a retention-window edge case that only manifests at real 24-hour boundaries) — the schedule must still exercise at least one real-time-scale retention-window transition, not purely accelerated commits.

23.7 Performance Concerns

This phase is where §30's full quantified-targets table (M1…) is measured end-to-end for the first time under realistic concurrency, not per-phase in isolation; any target missed here triggers a return to the owning phase, not a patch applied only in Phase 11.

23.8 Edge Cases

A writer that stalls mid-retry for longer than the retention window used by a concurrent ExpireSnapshots pass (its base snapshot could theoretically be expired out from under it) — must be handled by the writer detecting a "base snapshot no longer resolvable" error and restarting from current, not retrying indefinitely against a vanished base.

23.9 Failure Analysis

Any violation surfaced by the isolation checker at this stage is, by construction, a regression that slipped past every earlier phase's narrower tests — this phase's primary value is exactly this final, broad-spectrum net, and a failure here means returning to the specific owning phase (identified by which invariant the checker flagged) rather than patching around the symptom.

23.10 Operational Notes

The frozen API, the cross-engine-compat CI job, and the concurrency-stress CI job together are the three permanent guardrails referenced throughout §26/§28/§29 — every subsequent change to this project runs through all three before merge.

On-call ergonomics: every alert generated from the named metrics above links directly to the specific runbook and to a pre-built dashboard filtered to the affected table, so the first action during an incident is never "figure out where to look."

27. Compatibility & Versioning

Compatibility is treated as a first-class deliverable, not an afterthought bolted on at release time — every rule below traces back to P11 (explicit versioning) and exists specifically to let old readers and new writers coexist safely across the exact kind of multi-engine, rolling-upgrade environment this project's non-goals (§1) assume it will be embedded in.

Table-spec format version: this project targets a v2-style format (row-level delete files, sequence-number-scoped applicability, per-manifest partition-spec-id) as its baseline, matching the Iceberg table spec's v2 semantics; v1-style tables (no delete files, simpler manifest layout) are read-compatible via a version-gated code path (I12).

Forward/backward reader-writer compatibility: a reader must ignore unknown fields in any metadata object (P11); a writer must never write a format_version lower than what a table already records (I12); a v2-aware reader can always read v1 tables, but a v1-only reader cannot read v2-specific constructs (delete files) — this asymmetry is documented, not silently patched over.

Schema-evolution compatibility rules: exactly the decision table in §8.3 — add/drop/rename/reorder/safe-promote are backward and forward compatible by construction (field-ID stability, P4); unsafe narrowing is rejected at commit time, never merely discouraged.

Partition-spec evolution compatibility: old manifests remain valid under their original partition-spec-id indefinitely (I6); a reader must be able to evaluate multiple spec-ids within one scan (§17).

Metadata-format versioning: each metadata object (table metadata, manifest, manifest list) carries its own version marker independent of the others, so, e.g., the manifest Avro schema can evolve without forcing a table-metadata format-version bump.

Engine-API stability: the ScanPlan/FileScanTask/Catalog/ObjectStore surface is frozen at the end of Phase 11 (§23) and versioned with SemVer; a breaking change to any of these requires a major-version bump and a documented migration note.

Migration from Hive tables: a one-time import path reads an existing Hive-style partitioned-directory table's file listing, infers a schema and partition spec, and writes an initial TableMetadata/manifest tree referencing the existing (unmodified) data files — the data files themselves are never rewritten during import, only indexed (§36's alternative-architecture contrast names this exact transition).

Deprecation: a deprecated field or transform is marked in documentation for one full major version before removal; readers must continue accepting it (never error) until the major-version boundary.

Rolling-upgrade window: a mixed-version deployment (some engines on the prior major, some on the current) is supported for the length of one full major-version cycle, matching the deprecation window above, so an organization upgrading many independent engines never has a moment where some engines simply cannot read the table at all.

SemVer: MAJOR for breaking engine-API or table-format-version changes; MINOR for new transforms/statistics kinds that remain backward-compatible; PATCH for bug fixes with no format or API change.

Statistics/sketch format versioning: a Puffin-style sketch file (§8.11) carries its own kind identifier and version, independent of the table-metadata format-version — a reader unfamiliar with a given sketch kind or version skips it (P11), exactly as it would an unrecognized metadata field, never treating an unknown sketch as a parse error.

Cross-implementation version negotiation: because this project's tables are meant to be read by external Iceberg/Delta-spec-compliant readers (§28's differential-testing gate), every version bump to a format this project writes is checked against the oldest external-reader version still in the compatibility matrix before being enabled by default — a new capability ships behind an explicit opt-in until the matrix confirms broad enough support, avoiding a table that this project's own writer can produce but that no other engine can yet read.

28. Testing & Verification Strategy

Unit: metadata/manifest (de)serialization round-trips (Phase 1); transform correctness (Phase 5); schema-evolution decision-table coverage (Phase 4, tied to I5).

Integration: multi-writer commit races (Phase 3, tied to I2/I9/I10); mixed-partition-spec scans (Phase 5, tied to I6); merge-on-read sequence-scoped applicability (Phase 8, tied to I7/I9).

Property: a reader always sees one consistent snapshot (I1, generated concurrent-scan-vs-concurrent-commit interleavings); concurrent commits never lose an update — exactly one wins and the other retries (I2/I9, Phase 3's fixture generator); pruning never drops a file that could contain a matching row (I8, Phase 2/6's false-negative corpus, §14.4/§18.4); schema evolution preserves all existing data readable (I5, Phase 4's fixture generator); expire-snapshots never deletes a file reachable from a live snapshot (I3/I11, Phase 10's concurrent-reader fixture, §22.5).

Differential: read tables written by this format with an external Iceberg-spec-compliant reader (DuckDB's Iceberg extension) and vice-versa where feasible — a named CI gate (cross-engine-compat.yml, ADR-24) validating against the Iceberg table spec's expectations directly, exercised in Phase 11 (§23.4) and re-run on every subsequent change.

Concurrency stress: many writers (up to §4's 500-concurrent assumption) with an Elle/Jepsen-style isolation checker as a named gate (concurrency-stress.yml, ADR-24), validating I1/I2/I9/I10 under real contention (§23.2) — this is the standing gate, not a one-time Phase-11 exercise.

Fuzzing: the manifest and metadata parsers (cargo-fuzz, ADR-23), nightly, tied to T3/T5.

Chaos: object-store eventual-consistency injection (testing the ADR-16/27 assumption boundary itself, FM-10); commit races under injected latency; GC running during an injected long-running-read (§22.5's fixture, extended with chaos-level timing jitter).

Deterministic replay: every commit attempt's inputs (base snapshot, manifest deltas) are replayable from telemetry (§26) to reproduce an incident exactly, used by the metadata-corruption-recovery and GC-safety-incident runbooks.

Soak: 30-day-equivalent accelerated schedule (Phase 11, §23.5) plus at least one real-time-scale retention-window transition (§23.6 pitfall 4).

Fault injection: writer crash at every step of §8.2's nine-step sequence, verified each leaves the table in a valid state per I4 (never a partial tree).

Perf-regression gating: every merge re-runs the §30 targets table (M1…) against the prior release's baseline; a regression beyond a configured tolerance blocks merge.

Test-pyramid discipline: unit tests dominate by count and run on every commit; property and differential tests run on every PR; concurrency-stress, fuzzing, chaos, and soak are scheduled (nightly/pre-release) rather than per-commit, because their runtime cost is disproportionate to the marginal bug-catching rate of running them on every single change — this tiering is itself reviewed whenever a production incident's root cause turns out to be a class of bug none of the per-commit tests could have caught, in which case that specific scenario is promoted into the per-commit tier as a new fixture.

Regression-fixture lifecycle: every incident resolved via a runbook (§26) contributes at least one new conformance fixture reproducing its root cause, checked into conformance/ (§10) — this is how the fixture corpus grows to reflect real production experience rather than only the fixtures anticipated at design time.

29. Build & Release Engineering

Reproducible builds: pinned Cargo.lock (ADR-26) committed to the repo; CI builds from the lockfile only, never a floating dependency resolution.

Artifact signing: release binaries and crate publications signed via Sigstore-style keyless signing (ADR-25).

SBOM: generated per release, covering every transitive dependency, reviewed as part of the dependency-audit gate (T10).

Release channels: stable (tagged releases only), nightly (fuzz/soak-tested but not release-signed), matching the CI topology below.

CI/CD topology: PR gate (ci.yml — build/test/lint, ADR-24) → nightly (fuzz.yml, ADR-23) → pre-release (concurrency-stress.yml + cross-engine-compat.yml, both required green before a release tag) → release.yml (build, sign, SBOM, publish).

Version stamping: build embeds git commit hash, build timestamp, and the frozen engine-API version (§27) into a queryable build-info structure.

Provenance/attestation: release artifacts carry SLSA-style provenance statements linking the artifact to the exact CI run, commit, and signed build environment.

Dependency auditing: cargo audit on every PR and nightly; a known-vulnerable transitive dependency blocks merge until patched or explicitly waived with a documented, time-boxed exception.

Release cadence and support window: stable releases follow the SemVer rules of §27; each MAJOR release is supported (security patches only) for a fixed window after the next MAJOR ships, giving integrating engines a bounded, published deprecation runway rather than an open-ended one.

Multi-arch and reproducible-artifact parity: release builds target both x86_64 and ARM64 (§4 CPU assumptions) from the same pinned lockfile in the same CI run, and the release gate verifies both architectures' test suites pass identically before either artifact is signed — an architecture-specific regression is treated as a full release blocker, not a follow-up patch.

Tail-latency methodology: p99 commit latency (M3) is tracked as a distinct distribution from p50/p95 because it is dominated by the retry path (Phase 3), not by the happy path — a regression in p99 without a corresponding regression in p50/p95 points specifically at conflict-rate or backoff-policy issues, not at raw object-store throughput, and the two failure classes require different fixes (repartition writers versus tune backoff versus investigate object-store health).

Memory profiling: arena-style allocation for manifest-entry parsing (Phase 1) to avoid per-entry heap churn at the 50K-entries-per-manifest scale named in §4; manifest-cache residency tracked against available planner-node memory so cache eviction policy can be tuned before it becomes a scan-planning latency regression rather than after.

31. Scalability Analysis

What stays constant: metadata-tree depth (table metadata → snapshot → manifest list → manifest → file is a fixed five levels regardless of table size, by design, §8.1); commit atomicity granularity (always exactly one CAS, P1, regardless of concurrency level).

What grows, with Big-O: scan-planning cost grows with manifest/file count — O(manifests-surviving-list-prune) after list-level elimination, which is the entire reason manifest-list partition summaries and manifest caching (§14.7, §26) exist; commit contention grows with concurrent-writer count on overlapping partitions — O(conflict-probability) as a function of write-set overlap, motivating the backoff policy (Phase 3) and, at the extreme, table/partition-level write sharding; snapshot history grows unboundedly without ExpireSnapshots — O(commits-since-last-expiry), bounded only by an active retention policy (Phase 10, FM-4).

Named bottlenecks: the small-files problem (many tiny data files inflate manifest-entry count and scan-planning object-store-request count disproportionate to actual data volume) — addressed by compaction (Phase 10, ADR-14); the single-pointer commit as the hard write-concurrency limit (every writer for a given table ultimately serializes through one catalog entry's CAS, P1) — addressed operationally by partitioning write workloads across tables/branches rather than by loosening the atomicity model, since loosening it would break I2/I9/I10.

Horizontal scaling of readers: unbounded — readers only ever GET immutable objects (metadata, manifests, data files) and never contend with each other or with writers (I1), so read throughput scales with object-store GET throughput and reader-process count alone, not with any coordination overhead in this project.

Vertical scaling: primarily useful for maintenance workers (compaction throughput scales with CPU/IO available for Parquet re-encode) and for manifest-cache size (a bigger cache reduces repeated-plan object-store requests, §14.7) — the commit path itself is CPU-light (P6) and does not benefit much from vertical scaling beyond avoiding resource starvation.

Practical table-scale ceiling and the levers beyond it: comfortably into the millions of files and hundreds of thousands of snapshots per §4's stated scale before manifest-tree depth or planning-request-count become the binding constraint; beyond that, the levers are (a) more aggressive/more frequent compaction to keep manifest-entry density down, (b) tighter expiry policies to bound snapshot-log length, and (c) partitioning a single very large logical dataset across multiple physical tables/catalogs — never a change to the atomic-commit model itself, which is deliberately kept simple at the cost of being the ultimate write-concurrency ceiling (P1, named bottleneck above).

Geographic distribution: because readers never contend (I1, horizontal-scaling paragraph above), a table's data and metadata can be replicated read-only to additional regions using the underlying object store's own replication features without this project needing any cross-region protocol of its own; the one component that cannot be naively multi-region is the catalog's CAS, since compare-and-swap requires a single linearization point — a multi-region-writable table therefore needs either a single-region-authoritative catalog (accepted latency penalty for remote writers, the simplest option) or a consensus-backed multi-region catalog (deferred, §37).

Coordination-free reads as the scaling headroom: because the single-pointer commit is the only serialization point in the entire system, and it is on the write path exclusively, this project's read-scaling story has no analog to the usual "read replicas eventually catch up" caveat — a reader at any replica sees a fully consistent snapshot the instant that replica's object-store GET returns the metadata, with no separate replication-lag concept for this layer to reason about (though the underlying object store's own cross-region replication lag, if any, is inherited as-is, not solved).

32. Mental Models & First Principles

These are the compressed intuitions a practitioner should be able to recall instantly and re-derive the rest of the design from — each ties back to a principle (§6) or invariant (§7) already stated formally elsewhere, restated here in the form that is actually useful to think with under time pressure.

MM1. A table format is a database's storage engine with the transaction log and the files pulled apart onto object storage — the metadata pointer is the commit log-head, and everything else hangs off it (§3, §8.1).

MM2. Immutability plus an atomic pointer swap is the entire ACID trick — snapshot isolation, time travel, and rollback all fall out of "never mutate a file, only swap what current means" (P1, P2, §8.7).

MM3. On object storage, the request count is the cost and the latency — the whole design (manifest lists, statistics, caching) is about reading the fewest objects to plan a scan, not about clever algorithms over data already in memory (P13, §4, §30).

MM4. A commit conflict is not a failure, it is the system working — optimistic concurrency expects contention and resolves it by retry, never by blocking (P6, Phase 3).

MM5. A column's identity is a number, not a string — every schema-evolution guarantee in this project reduces to "the field-id didn't change" (P4, §8.3).

MM6. Garbage collection is a proof obligation, not a cleanup script — a file may be deleted only after proving no live snapshot can reach it, and "I'm not sure" must always resolve to "don't delete" (P7, I3).

MM7. Statistics are a bet placed at write time, paid off at every future read — the cost of computing ColumnStats once is amortized across every scan that ever prunes using them (P3, §18.2).

MM8. Partitioning is a derived value, not a schema decision the query has to know about — hiding it behind a transform is what makes "partition evolution without rewriting data" possible at all (P8, §8.4).

MM9. Copy-on-write and merge-on-read are the same tradeoff seen from two different points in the pipeline — pay at write time with full-file rewrite, or pay at read time with delete-file application; neither is "correct," only situationally cheaper (§8.6).

MM10. The metadata tree is self-similar — a manifest list pruning manifests is structurally the same operation as a manifest pruning files, which is why one pruning discipline (P3) generalizes across every level of §8.1's tree.

33. Comparative Architecture

Four real open-table-format/warehouse systems plus the directory-listing predecessor problem they all solve, compared on the dimensions that actually determine correctness and performance rather than surface API differences.

Dimension Apache Iceberg Delta Lake Apache Hudi Hive Tables DuckDB native format
Metadata model manifest tree (list → manifests → entries) with catalog pointer ordered JSON action log (_delta_log) + periodic checkpoints timeline of instants + file groups directory listing, partition = subdirectory single-file/single-process format, no distributed metadata
Commit mechanism atomic pointer swap via catalog CAS atomic append of next-numbered JSON file (filesystem rename or object-store conditional write) timeline-based instant transition, lock-assisted for some storages none — a partition is "committed" by finishing a file write, no cross-file atomicity single-writer, no concurrent-commit model needed

Apache Iceberg builds a manifest tree with a catalog-held pointer, giving list-level pruning as a first-class property of the metadata format itself; this is the direct model this project's §8.1 tree and §8.5 pruning algorithm follow.

Delta Lake instead keeps an ordered JSON transaction log of actions, replayed (with periodic checkpoints to bound replay cost) to reconstruct current state; this is a simpler commit model — appending the next-numbered log entry — at the cost of needing checkpoint-aware replay for planning rather than a purpose-built pruning index; this manifest-tree-versus-ordered-log contrast is the single most important comparative decision named across ADR-03/ADR-04/ADR-08 and §36.

Apache Hudi organizes around a timeline of instants and file groups with a strong emphasis on managed compaction scheduling as an operational primitive, reflecting its origins in high-frequency upsert workloads (mirrored in this project's Phase 8/10 emphasis on delete-file read-amplification triggers).

Hive tables are the predecessor problem both Iceberg and Delta exist to solve: a "table" is nothing but a directory-listing convention, with no metadata layer, no atomicity, and no statistics — listing millions of objects to plan a query is exactly the cost this project's manifest tree eliminates (§36 makes this the first alternative architecture considered and rejected).

DuckDB's native format is included only for contrast: it is a single-process, single-writer, non-distributed format with no need for a catalog, a commit protocol, or cross-engine compatibility — useful as a reminder that this project's entire design surface (metadata tree, OCC, pruning) exists specifically because storage and compute are decoupled and multiple independent engines must agree on table state. Where DuckDB's own format can simply mutate a page in place under a single process's exclusive control, every guarantee this project offers — snapshot isolation, time travel, safe concurrent writers — is purchased specifically by giving up that in-place-mutation convenience in exchange for object-storage-native durability shared across engines.

Taken together, the five systems in the table above sit on a single axis: how much of "table-ness" — atomicity, isolation, statistics, evolvability — is pulled out of a central service (Hive metastore) or a single process (DuckDB) and pushed down into the files themselves as self-describing, catalog-pointed metadata (Iceberg, Delta, Hudi). This project deliberately sits at the pushed-down end of that axis, and every ADR in §9 that chooses "no external service, files on object storage" over "a service that could otherwise do the same job" is a restatement of that same choice.

34. Back-of-Envelope Capacity Model

Every number below is derived from a stated formula chained off §4's constraint table, never asserted as a bare figure — the point is that any reader can re-derive the same estimate from the same inputs and check it, not merely trust it.

  1. Scan-planning object-store requests, this project vs. Hive listing: this project = 1 (metadata) + 1 (manifest list) + k (surviving manifests, from §8.5 step 2) ≈ 3–10 requests for a selective query. Hive-style directory listing of N=10,000 files = ceil(10,000 / 1,000-per-LIST-page) = 10 LIST calls minimum, but with zero pruning — every one of the 10,000 files must still be opened to check predicates, ≈10,010 requests. Pruning win ≈ 1,000x on request count for a selective query.

  2. Metadata size for a table: snapshots × manifest-list bytes + manifests × entry-bytes × data-files. With 100,000 retained snapshots × 2 KB manifest-list ≈ 200 MB snapshot-history overhead; 10,000 manifests × 200 bytes/entry × 500 entries/manifest ≈ 1 GB manifest bytes. Total metadata footprint for a 5M-file table ≈ 1.2 GB — small enough to cache manifest lists in memory on a planner node (§26).

  3. Commit latency: object-store round trips per commit (§8.2, M6 = 2–4) × RTT. Same-region RTT ≈ 2 ms (§4) → 4–8 ms lower bound; observed p50 target of 150 ms (M1) implies ≈140 ms of serialization/validation/write overhead beyond raw network RTT, consistent with writing multi-KB manifest objects, not pure round-trip latency.

  4. Files pruned by partition + column stats (§8.5 worked example, chained): start 10,000 files → list-level partition prune to ≈27 (day granularity, 1/365 of files) → column-stat prune to ≈11 (40% of the day's files survive price filter) → final scanned fraction = 11/10,000 = 0.11%, i.e., 99.89% eliminated across two pruning stages.

  5. Write amplification, copy-on-write update touching 1% of rows uniformly across a 1,000-file, 1 GB/file table: worst case, 1% row-touch could intersect all 1,000 files if uniformly distributed → up to 1,000 GB rewritten to change 10 GB of logical data → 100x amplification in the pathological case; with reasonable clustering (touched rows concentrated in fewer files via partitioning), realistic amplification is closer to (files-touched / files-total) × avg-file-size, e.g., 50 files touched × 1 GB = 50 GB rewritten for 10 GB logical change = 5x.

  6. Read amplification, merge-on-read: delete-files-applied-per-scan (M13) × avg-delete-file-bytes. At 2 delete files/data-file × 50 KB/delete-file average ≈ 100 KB extra read per data file per scan — negligible against a multi-MB data file, until delete-file count grows past the compaction trigger threshold (Phase 8/10), at which point it dominates.

  7. Snapshot-history storage growth: commits/day × metadata-bytes/commit. At 5,000 commits/minute peak (§4) sustained for even 1% of a day (≈72 minutes-equivalent burst) = 360,000 commits × ≈2 KB/manifest-list-and-metadata-delta ≈ 720 MB/day of pure metadata growth at peak-adjacent load — motivating a retention policy (§4 default: 7 days or last 100 snapshots) that bounds this to single-digit GB rather than unbounded accumulation.

  8. Small-files compaction trigger: with a 500 MB target file size (typical Parquet target) and files averaging 5 MB post-high-frequency-ingest, a partition needs ≈100 small files accumulated before one compaction pass yields a single well-sized file — the operational trigger (Phase 10) is calibrated around "average file size below X% of target for Y consecutive commits," not a fixed file count alone.

  9. Manifest-list cache payoff: a planner node caching 100 hot tables' manifest-lists at ≈2 KB each ≈ 200 KB resident — negligible memory cost for eliminating a repeated GET on every one of those tables' subsequent plans (§14.7); the break-even point versus re-fetching is a single repeated query against the same snapshot, meaning the cache pays for itself almost immediately in any interactive workload.

  10. Cross-region planning cost: at 40-120 ms cross-region RTT (§4) versus 1-3 ms intra-region, a scan plan requiring 3 sequential GETs (metadata + manifest-list + 1 manifest) costs ≈9-15 ms intra-region but ≈120-360 ms cross-region if each GET is sequential and uncached — the concrete argument for co-locating the planner with the catalog/object-store region rather than treating region placement as an afterthought.

35. Hard Questions (Self-Examination)

Each question below requires synthesizing at least two sections to answer well — the point is not recall of a single row or paragraph but tracing how a principle (§6), an invariant (§7), and a phase's acceptance criteria (§12–§23) all constrain the same design decision from different angles.

  1. Why is the commit protocol's only atomic operation the catalog CAS, and what would break if manifest-writing were also required to be atomic with it? (§8.2, §6 P1)
  2. How does the field-ID model (§8.3) make rename "free" in a way that a name-based schema model fundamentally cannot? (§9 ADR-11, §32 MM5)
  3. Why must ExpireSnapshots complete and become durably visible before OrphanFileGc computes reachability, and what specific race does violating that order create? (§7 I11, §22.2)
  4. Why does time travel cost the same as a normal scan, and what would make it not true (i.e., what design would introduce a replay cost)? (§8.7, §21.2, §32 MM2)
  5. What is the concrete difference between a manifest-list-level prune and a file-level prune, and why can't the system skip straight to file-level pruning for every query? (§8.5, §18.2)
  6. Why is copy-on-write's write amplification bounded by files-touched rather than rows-touched, and how does partition/clustering strategy change that bound? (§8.6, §34 item 5)
  7. Why does merge-on-read need sequence-number-scoped applicability (I9) rather than simply "the newest delete file always applies"? (§20.2, §7 I7/I9)
  8. What would happen to I1 (snapshot isolation for readers) if the scan planner re-resolved "current snapshot" partway through generating a ScanPlan instead of pinning it up front? (§7 I1, §14.2)
  9. Why is a bare Catalog implementation with only check-then-set semantics unsafe, even if it "usually" works in testing? (§9 ADR-04, §24 T1)
  10. Why does this project delegate the columnar codec to Parquet rather than reimplementing it, and what would leak across that boundary if it didn't? (§1 non-goals, §9 ADR-02)
  11. Why is hidden partitioning (P8) specifically what prevents the class of bug Hive tables are prone to, and what does the query author have to not know for that to work? (§8.4, §33)
  12. Why does a schema-evolution change that is I5-safe still sometimes need the rollback runbook (FM-8)? What gap does that expose between "correct" and "operationally safe"? (§25 FM-8, §16)
  13. Why is manifest-tree depth constant regardless of table size, and what property of the design would be violated if depth grew with file count? (§8.1, §31)
  14. Why must the isolation checker in Phase 11 (§23.2) be validated against Bailis et al.'s actual isolation-level definitions rather than trusted at face value? (§23.6 pitfall 1, §28)
  15. Why does this project treat "I'm not sure this file is unreachable" as equivalent to "this file is reachable" in the GC path, rather than resolving the ambiguity some other way? (§6 P7, §7 I3)
  16. What specific object-storage consistency property does ADR-16/27 assume, and what concrete failure mode (FM-10) appears if that assumption is false for a given backend? (§9 ADR-27, §25 FM-10)
  17. Why does partition-spec evolution (§8.4, I6) avoid rewriting old manifests, and what would a design that did rewrite them cost in comparison? (§17.2, §34)
  18. How do the Phase-6 false-negative property tests and the Phase-7 delete-path reuse of the same pruning code create a shared risk, and why is that considered a feature rather than a duplication problem? (§18.9, §19.9)
  19. Why is the small-files problem an inevitable consequence of high-frequency low-volume commits rather than a bug to be "fixed" at the write path? (§31, §34 item 8)
  20. What makes the manifest tree "self-similar" (MM10), and why does that property let one pruning discipline (P3) generalize across every level instead of needing a bespoke algorithm per level? (§32 MM10, §8.5)

36. Alternative Architectures (Roads Not Taken)

Each alternative below is a fundamentally different way to solve "make a set of files on shared storage behave like a table," not a minor variant of this project's own design — each names the real system that embodies it, the regime where it actually wins, and the specific reason it was rejected as this project's primary architecture.

A1. Hive directory-listing "table" (no metadata layer)

   Query
     |
     v
  LIST s3://table/partition=X/*     <- O(files) request, no stats
     |
     v
  OPEN every returned file to check predicate
     |
     v
  Rows

Winning regime: small, slowly-changing tables where object count never approaches the thousands and no cross-engine transactional guarantee is needed. Real embodying system: classic Hive/Spark "external table over S3 partitioned directories." Why rejected here: zero pruning below the partition-directory level, no atomicity (a partition's files can be half-written and still get listed), and LIST cost grows linearly with file count with no statistics shortcut — exactly the problem this whole project's manifest tree exists to solve (§33).

A2. Delta Lake's ordered-JSON transaction log instead of a manifest tree

_delta_log/
  00000000000000000000.json   <- action: add file, remove file, metaData
  00000000000000000001.json
  ...
  00000000000000000010.checkpoint.parquet   <- periodic snapshot of state

Winning regime: append/upsert-heavy workloads where commit simplicity (append the next-numbered file) matters more than list-level pruning sophistication, and checkpoint cadence can be tuned to bound replay cost. Real embodying system: Delta Lake. Why rejected here (as the primary design, though its commit-simplicity lesson informs ADR-04's rejected-alternatives column): planning cost depends on checkpoint freshness — a stale checkpoint means replaying more log entries — whereas the manifest-tree's list-level partition summaries give bounded planning cost independent of commit frequency (§9 ADR-03/ADR-08); this project chose the tree specifically to make §8.5's pruning algorithm the primary planning mechanism rather than log replay.

A3. A traditional shared-storage database (Aurora-style) instead of open files on object storage

  Compute (stateless)  Compute (stateless)  Compute (stateless)
        \                    |                    /
         \_______  Shared distributed storage  __/
                    (log-structured, page-based,
                     proprietary protocol, not files)

Winning regime: workloads needing serializable multi-row transactions, low-latency point lookups, and no requirement for open-file interoperability with external engines. Real embodying system: Amazon Aurora (compute/storage separation via a proprietary log-structured storage service, not open Parquet files). Why rejected here: the entire value proposition of this project is that data lives in an open, directly-readable columnar format any engine can access without going through a proprietary storage protocol — Aurora-style shared storage solves a different problem (OLTP durability/availability) and would sacrifice the open-format interoperability that is this project's non-negotiable requirement (§1 boundaries).

A4. A metadata service/database as the source of truth instead of files-plus-a-pointer

   Writers/Readers
         |
         v
   Metadata RDBMS/KV-store   <- source of truth is a live service,
   (tables, partitions,        not an object in the same storage
    file-listing rows)          the data lives in
         |
         v
   Data files on object storage

Winning regime: environments already operating a highly-available metadata database and wanting rich query/indexing over table metadata itself (e.g., "find all tables with column X"), and willing to accept that service as a hard availability dependency for every table operation. Real embodying system: the Hive metastore (a JDBC-backed relational database as the metadata source of truth). Why rejected here: this reintroduces exactly the historical "Hive metastore scaled poorly" problem (§2) — the metastore becomes a single service every reader and writer depends on, whereas this project's files-plus-a-pointer design (§3) makes metadata itself just more immutable objects on the same object storage the data already lives on, with the catalog reduced to the smallest possible piece of external state (one pointer per table) rather than a full relational schema of table/partition/file rows.

38. Glossary

Terms below use exactly the identifiers locked in §3/§10/§11/§12–§23/Appendix A — a term defined here never has a second, conflicting name elsewhere in this document.

Table format — the metadata specification and protocol that turns a set of data files into a transactional table.

Data lake — a repository of raw/semi-structured files on cheap object storage, historically without transactional guarantees.

Lakehouse — a data lake augmented with a table format to gain warehouse-like ACID/schema guarantees without leaving object storage.

Object storage — a key-object store (e.g., S3) offering GET/PUT/LIST/conditional-write, not a POSIX filesystem.

Columnar format — a file layout storing values column-by-column rather than row-by-row, enabling per-column statistics and compression.

Parquet — the columnar file format this project delegates data-file encoding to.

Metadata tree — the hierarchy of table metadata, snapshots, manifest lists, manifests, and files (§8.1).

Table metadata — the versioned document holding schema history, partition-spec history, and the snapshot log.

Snapshot — one immutable, complete table state at a point in commit history.

Snapshot isolation — a reader observes exactly one consistent snapshot for the duration of its scan (I1).

Manifest — a file indexing a batch of data/delete files with their statistics.

Manifest list — a per-snapshot index of manifests carrying partition-value summaries for list-level pruning.

Data file — an immutable Parquet object holding table rows.

Delete file — a file recording rows logically removed since a referencing data file was written.

Position delete — a delete file referencing rows by file-path + row-offset.

Equality delete — a delete file referencing rows by predicate-equivalent column values.

Copy-on-write — an update strategy that rewrites affected files rather than recording a separate delete.

Merge-on-read — an update strategy that records a small delete file and reconciles it at scan time.

Atomic commit — a table-state transition that either fully applies or not at all, implemented as one CAS.

Optimistic concurrency — a concurrency model that proceeds without locking and detects conflicts at commit time.

Compare-and-swap (CAS) — an atomic primitive that updates a value only if it still matches an expected prior value.

Catalog — the holder of a table's current metadata-pointer, exposing the CAS primitive.

Time travel — querying the table as of a historical snapshot rather than the current one.

Rollback — committing a new current-snapshot pointer to a prior snapshot.

Schema evolution — safely changing a table's schema (add/drop/rename/reorder/promote) without rewriting data.

Column ID (field-id) — a stable integer identifying a column independent of its name or position.

Hidden partitioning — deriving partition values from a transform automatically, without the query naming a partition column.

Partition transform — a function (identity/bucket/truncate/year/month/day/hour) deriving a partition value from a source column.

Partition pruning — eliminating manifests/files at the partition-value level before reading data.

File pruning — eliminating data files using column-level statistics before reading data.

Column statistics — per-column min/max/null-count/value-count recorded in a manifest entry.

Compaction — rewriting many small files into fewer, larger ones (and folding deletes into data).

Small-files problem — the scan-planning and storage-overhead cost of accumulating many undersized files.

Expire snapshots — removing old, unreferenced snapshot-log entries per a retention policy.

Orphan file — a file not reachable from any live snapshot's manifest tree.

Garbage collection (GC) — deleting orphan files under the safety condition that no live snapshot references them.

Eventual consistency — a storage consistency model where a write may not be immediately visible to subsequent reads (contrasted with the strong read-after-write model this project assumes, ADR-27).

Read amplification — extra read work (e.g., delete-file application) beyond reading the base data.

Write amplification — extra write work (e.g., full-file rewrite) beyond the logical size of a change.

Sequence number — a strictly monotonic counter ordering snapshots, used for merge-on-read applicability.

Snapshot log — the append-only history of a table's committed snapshots.

Snapshot ref — a named pointer (tag/branch) to a specific snapshot, affecting retention.

Partition spec — a versioned set of partition fields/transforms bound to a table.

Partition-spec evolution — changing the active partition spec without rewriting data written under an older spec.

Scan plan — the output of planning: a set of file-scan tasks for a given predicate and snapshot.

File scan task — one data file plus its applicable delete files and residual predicate, handed to an engine.

Residual predicate — the portion of a query predicate not resolvable purely from statistics, left for row-level evaluation.

Puffin — a sketch/statistics file format (referenced as an extension point for statistics beyond min/max, ADR-12).

Manifest entry — one file's presence record (added/existing/deleted) within a manifest.

Content type — whether a manifest entry's file is data, position-deletes, or equality-deletes.

Format version — the table-metadata protocol version gating which fields a reader may rely on.

Differential testing — validating this project's tables against an independent, external spec-compliant reader/writer.

Isolation checker — an Elle/Jepsen-style tool validating that observed commit histories respect a claimed isolation level.

Write amplification factor — the ratio of physical bytes written to logical bytes changed, the headline copy-on-write cost metric.

Read amplification factor — the ratio of extra bytes read (delete-file application) to base-data bytes read, the headline merge-on-read cost metric.

Field-ID allocator — the table-global monotonic counter assigning stable identity to every schema field, retired IDs never reused.

Reachability set — the set of files provably referenced by at least one live snapshot's manifest tree, computed fresh before any GC delete.

Manifest cache — an in-memory cache of parsed manifest/manifest-list bytes, keyed by object path, to avoid re-fetching unchanged metadata across repeated scan plans.

Conformance fixture — a named, checked-in test input/expected-output pair used to gate a phase's acceptance criteria.
