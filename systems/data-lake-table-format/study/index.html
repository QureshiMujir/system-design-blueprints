Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why is the commit protocol's only atomic operation the catalog CAS, and what would break if manifest-writing were also required to be atomic with it? (§8.2, §6 P1)
  2. How does the field-ID model (§8.3) make rename "free" in a way that a name-based schema model fundamentally cannot? (§9 ADR-11, §32 MM5)
  3. Why must ExpireSnapshots complete and become durably visible before OrphanFileGc computes reachability, and what specific race does violating that order create? (§7 I11, §22.2)
  4. Why does time travel cost the same as a normal scan, and what would make it not true (i.e., what design would introduce a replay cost)? (§8.7, §21.2, §32 MM2)
  5. What is the concrete difference between a manifest-list-level prune and a file-level prune, and why can't the system skip straight to file-level pruning for every query? (§8.5, §18.2)
  6. Why is copy-on-write's write amplification bounded by files-touched rather than rows-touched, and how does partition/clustering strategy change that bound? (§8.6, §34 item 5)
  7. Why does merge-on-read need sequence-number-scoped applicability (I9) rather than simply "the newest delete file always applies"? (§20.2, §7 I7/I9)
  8. What would happen to I1 (snapshot isolation for readers) if the scan planner re-resolved "current snapshot" partway through generating a ScanPlan instead of pinning it up front? (§7 I1, §14.2)
  9. Why is a bare Catalog implementation with only check-then-set semantics unsafe, even if it "usually" works in testing? (§9 ADR-04, §24 T1)
  10. Why does this project delegate the columnar codec to Parquet rather than reimplementing it, and what would leak across that boundary if it didn't? (§1 non-goals, §9 ADR-02)
  11. Why is hidden partitioning (P8) specifically what prevents the class of bug Hive tables are prone to, and what does the query author have to not know for that to work? (§8.4, §33)
  12. Why does a schema-evolution change that is I5-safe still sometimes need the rollback runbook (FM-8)? What gap does that expose between "correct" and "operationally safe"? (§25 FM-8, §16)
  13. Why is manifest-tree depth constant regardless of table size, and what property of the design would be violated if depth grew with file count? (§8.1, §31)
  14. Why must the isolation checker in Phase 11 (§23.2) be validated against Bailis et al.'s actual isolation-level definitions rather than trusted at face value? (§23.6 pitfall 1, §28)
  15. Why does this project treat "I'm not sure this file is unreachable" as equivalent to "this file is reachable" in the GC path, rather than resolving the ambiguity some other way? (§6 P7, §7 I3)
  16. What specific object-storage consistency property does ADR-16/27 assume, and what concrete failure mode (FM-10) appears if that assumption is false for a given backend? (§9 ADR-27, §25 FM-10)
  17. Why does partition-spec evolution (§8.4, I6) avoid rewriting old manifests, and what would a design that did rewrite them cost in comparison? (§17.2, §34)
  18. How do the Phase-6 false-negative property tests and the Phase-7 delete-path reuse of the same pruning code create a shared risk, and why is that considered a feature rather than a duplication problem? (§18.9, §19.9)
  19. Why is the small-files problem an inevitable consequence of high-frequency low-volume commits rather than a bug to be "fixed" at the write path? (§31, §34 item 8)
  20. What makes the manifest tree "self-similar" (MM10), and why does that property let one pruning discipline (P3) generalize across every level instead of needing a bespoke algorithm per level? (§32 MM10, §8.5)

32. Mental Models & First Principles

These are the compressed intuitions a practitioner should be able to recall instantly and re-derive the rest of the design from — each ties back to a principle (§6) or invariant (§7) already stated formally elsewhere, restated here in the form that is actually useful to think with under time pressure.

MM1. A table format is a database's storage engine with the transaction log and the files pulled apart onto object storage — the metadata pointer is the commit log-head, and everything else hangs off it (§3, §8.1).

MM2. Immutability plus an atomic pointer swap is the entire ACID trick — snapshot isolation, time travel, and rollback all fall out of "never mutate a file, only swap what current means" (P1, P2, §8.7).

MM3. On object storage, the request count is the cost and the latency — the whole design (manifest lists, statistics, caching) is about reading the fewest objects to plan a scan, not about clever algorithms over data already in memory (P13, §4, §30).

MM4. A commit conflict is not a failure, it is the system working — optimistic concurrency expects contention and resolves it by retry, never by blocking (P6, Phase 3).

MM5. A column's identity is a number, not a string — every schema-evolution guarantee in this project reduces to "the field-id didn't change" (P4, §8.3).

MM6. Garbage collection is a proof obligation, not a cleanup script — a file may be deleted only after proving no live snapshot can reach it, and "I'm not sure" must always resolve to "don't delete" (P7, I3).

MM7. Statistics are a bet placed at write time, paid off at every future read — the cost of computing ColumnStats once is amortized across every scan that ever prunes using them (P3, §18.2).

MM8. Partitioning is a derived value, not a schema decision the query has to know about — hiding it behind a transform is what makes "partition evolution without rewriting data" possible at all (P8, §8.4).

MM9. Copy-on-write and merge-on-read are the same tradeoff seen from two different points in the pipeline — pay at write time with full-file rewrite, or pay at read time with delete-file application; neither is "correct," only situationally cheaper (§8.6).

MM10. The metadata tree is self-similar — a manifest list pruning manifests is structurally the same operation as a manifest pruning files, which is why one pruning discipline (P3) generalizes across every level of §8.1's tree.

Reference Implementations

  • Apache Iceberg — core/src/main/java/org/apache/iceberg/ (TableMetadata, ManifestFiles, SnapshotProducer). Lesson: manifest-list partition summaries make list-level pruning nearly free. Pitfall: forgetting to update the manifest-list summary on manifest rewrite silently disables pruning.
  • Delta Lake — spark/src/main/scala/org/apache/spark/sql/delta/ (OptimisticTransaction, _delta_log JSON actions). Lesson: an ordered JSON action log plus periodic checkpoints is a simpler commit model than a manifest tree. Pitfall: unbounded log growth without checkpointing degrades every reader's startup cost.
  • Apache Hudi — timeline and compaction-scheduling code. Lesson: merge-on-read compaction scheduling is a first-class background job, not an afterthought. Pitfall: unscheduled compaction lets read amplification grow unbounded.
  • iceberg-rust — Rust reference for the same spec this project implements independently. Lesson: cross-check field-ID and manifest-entry layout against a second implementation. Pitfall: diverging on Avro schema evolution rules for manifests themselves.
  • DuckDB's Iceberg/Delta readers (extension/iceberg, extension/delta) — Lesson: a minimal read-only implementation validates the spec's read path independent of any write engine. Pitfall: read-only implementations can mask write-path bugs that only surface under concurrent commits.
  • Trino and Spark Iceberg/Delta connectors — Lesson: these are the actual multi-engine consumers the cross-engine-compat gate (§23, §28) exists to satisfy; their predicate-pushdown translation layers are the reference for what a ScanPlan/FileScanTask consumer expects. Pitfall: an engine connector caching manifest-list summaries independently of this project's own manifest cache (§14.7) can serve stale pruning decisions after a compaction if cache-invalidation signaling isn't part of the integration contract.

38. Glossary

Terms below use exactly the identifiers locked in §3/§10/§11/§12–§23/Appendix A — a term defined here never has a second, conflicting name elsewhere in this document.

Table format — the metadata specification and protocol that turns a set of data files into a transactional table.

Data lake — a repository of raw/semi-structured files on cheap object storage, historically without transactional guarantees.

Lakehouse — a data lake augmented with a table format to gain warehouse-like ACID/schema guarantees without leaving object storage.

Object storage — a key-object store (e.g., S3) offering GET/PUT/LIST/conditional-write, not a POSIX filesystem.

Columnar format — a file layout storing values column-by-column rather than row-by-row, enabling per-column statistics and compression.

Parquet — the columnar file format this project delegates data-file encoding to.

Metadata tree — the hierarchy of table metadata, snapshots, manifest lists, manifests, and files (§8.1).

Table metadata — the versioned document holding schema history, partition-spec history, and the snapshot log.

Snapshot — one immutable, complete table state at a point in commit history.

Snapshot isolation — a reader observes exactly one consistent snapshot for the duration of its scan (I1).

Manifest — a file indexing a batch of data/delete files with their statistics.

Manifest list — a per-snapshot index of manifests carrying partition-value summaries for list-level pruning.

Data file — an immutable Parquet object holding table rows.

Delete file — a file recording rows logically removed since a referencing data file was written.

Position delete — a delete file referencing rows by file-path + row-offset.

Equality delete — a delete file referencing rows by predicate-equivalent column values.

Copy-on-write — an update strategy that rewrites affected files rather than recording a separate delete.

Merge-on-read — an update strategy that records a small delete file and reconciles it at scan time.

Atomic commit — a table-state transition that either fully applies or not at all, implemented as one CAS.

Optimistic concurrency — a concurrency model that proceeds without locking and detects conflicts at commit time.

Compare-and-swap (CAS) — an atomic primitive that updates a value only if it still matches an expected prior value.

Catalog — the holder of a table's current metadata-pointer, exposing the CAS primitive.

Time travel — querying the table as of a historical snapshot rather than the current one.

Rollback — committing a new current-snapshot pointer to a prior snapshot.

Schema evolution — safely changing a table's schema (add/drop/rename/reorder/promote) without rewriting data.

Column ID (field-id) — a stable integer identifying a column independent of its name or position.

Hidden partitioning — deriving partition values from a transform automatically, without the query naming a partition column.

Partition transform — a function (identity/bucket/truncate/year/month/day/hour) deriving a partition value from a source column.

Partition pruning — eliminating manifests/files at the partition-value level before reading data.

File pruning — eliminating data files using column-level statistics before reading data.

Column statistics — per-column min/max/null-count/value-count recorded in a manifest entry.

Compaction — rewriting many small files into fewer, larger ones (and folding deletes into data).

Small-files problem — the scan-planning and storage-overhead cost of accumulating many undersized files.

Expire snapshots — removing old, unreferenced snapshot-log entries per a retention policy.

Orphan file — a file not reachable from any live snapshot's manifest tree.

Garbage collection (GC) — deleting orphan files under the safety condition that no live snapshot references them.

Eventual consistency — a storage consistency model where a write may not be immediately visible to subsequent reads (contrasted with the strong read-after-write model this project assumes, ADR-27).

Read amplification — extra read work (e.g., delete-file application) beyond reading the base data.

Write amplification — extra write work (e.g., full-file rewrite) beyond the logical size of a change.

Sequence number — a strictly monotonic counter ordering snapshots, used for merge-on-read applicability.

Snapshot log — the append-only history of a table's committed snapshots.

Snapshot ref — a named pointer (tag/branch) to a specific snapshot, affecting retention.

Partition spec — a versioned set of partition fields/transforms bound to a table.

Partition-spec evolution — changing the active partition spec without rewriting data written under an older spec.

Scan plan — the output of planning: a set of file-scan tasks for a given predicate and snapshot.

File scan task — one data file plus its applicable delete files and residual predicate, handed to an engine.

Residual predicate — the portion of a query predicate not resolvable purely from statistics, left for row-level evaluation.

Puffin — a sketch/statistics file format (referenced as an extension point for statistics beyond min/max, ADR-12).

Manifest entry — one file's presence record (added/existing/deleted) within a manifest.

Content type — whether a manifest entry's file is data, position-deletes, or equality-deletes.

Format version — the table-metadata protocol version gating which fields a reader may rely on.

Differential testing — validating this project's tables against an independent, external spec-compliant reader/writer.

Isolation checker — an Elle/Jepsen-style tool validating that observed commit histories respect a claimed isolation level.

Write amplification factor — the ratio of physical bytes written to logical bytes changed, the headline copy-on-write cost metric.

Read amplification factor — the ratio of extra bytes read (delete-file application) to base-data bytes read, the headline merge-on-read cost metric.

Field-ID allocator — the table-global monotonic counter assigning stable identity to every schema field, retired IDs never reused.

Reachability set — the set of files provably referenced by at least one live snapshot's manifest tree, computed fresh before any GC delete.

Manifest cache — an in-memory cache of parsed manifest/manifest-list bytes, keyed by object path, to avoid re-fetching unchanged metadata across repeated scan plans.

Conformance fixture — a named, checked-in test input/expected-output pair used to gate a phase's acceptance criteria.
