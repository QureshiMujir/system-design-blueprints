The catalog is the metadata-pointer holder: it stores exactly one value per table — the location of the current TableMetadata file — and exposes a compare-and-swap primitive over that value; it is the only component that must offer atomicity, and it is what the commit engine calls.

Table metadata is a versioned JSON document holding the schema history, partition-spec history, the snapshot log, and a pointer to the current snapshot; it is rewritten (never mutated) on every commit and is small enough to read in full on every planning call.

The snapshot layer is the append-only history of table states: each Snapshot has an ID, a parent, a sequence number, an operation type, and a pointer to one manifest list; snapshots are what time travel and rollback address.

The manifest list is a per-snapshot index of manifests, carrying each manifest's partition-value summary (min/max per partition field) so the planner can discard whole manifests without opening them.

Manifests are per-write-batch indexes of data/delete files, each entry carrying the file path, partition tuple, column-level ColumnStats, and (for delete files) the content type distinguishing position- from equality-deletes.

Data files are immutable Parquet objects; delete files are Parquet or Puffin objects recording rows logically removed since the referencing data file was written, resolved at read time (merge-on-read) or already reconciled (copy-on-write).

The commit/OCC engine is the only writer path: it reads the current metadata, stages new manifests/files, and attempts a single compare-and-swap of the metadata pointer; failure means another writer won and this writer must reread and retry — this is the atomic-commit boundary marked in the diagram.

The scan planner takes a predicate and a snapshot ID, prunes manifests via partition-value summaries, prunes files via ColumnStats, and emits a ScanPlan of FileScanTasks plus applicable delete files — no data is read during planning.

The compaction/maintenance worker rewrites small files into larger ones, compacts manifests, and runs ExpireSnapshots/OrphanFileGc under the safety condition that no live snapshot may reference a file being deleted.

The schema/partition-evolution engine validates and applies metadata-only changes (add/drop/rename/reorder/promote a column; add/remove a partition field) that never touch existing data files, keyed by stable field IDs.

The object-store adapter wraps GET/PUT/LIST/conditional-PUT against S3-compatible backends; it is the consistency boundary — everything above it assumes at most the read-after-write guarantee that boundary documents (see ADR-27, §9).

8. Domain Model

8.1 Metadata hierarchy (tree)

TableMetadata
 |-- current-snapshot-id
 |-- schemas[]            (Schema, keyed by schema-id)
 |-- partition-specs[]    (PartitionSpec, keyed by spec-id)
 |-- snapshot-log[]       (Snapshot, append-only)
      `-- Snapshot
           |-- manifest-list-location
           `-- ManifestList
                |-- manifest-file-summaries[]  (partition value ranges)
                `-- ManifestFile[]
                     `-- ManifestEntry[]
                          |-- DataFile   (Parquet)
                          `-- DeleteFile (position | equality)
Level Field Purpose
TableMetadata format-version, table-uuid, location, current-schema-id, current-snapshot-id table identity and current pointers
Snapshot snapshot-id, parent-snapshot-id, sequence-number, timestamp-ms, manifest-list, summary.operation one committed table state
ManifestList manifest-path, partition-spec-id, added/existing/deleted-files-count, per-manifest partition-value summary list-level pruning input
ManifestFile path, length, partition-spec-id, content (data/deletes), sequence-number file-level index of one write batch
ManifestEntry status (added/existing/deleted), data-file or delete-file, sequence-number one file's presence record
DataFile/DeleteFile file-path, file-format, partition, record-count, column-sizes, value-counts, null-value-counts, lower/upper-bounds pruning statistics

8.2 Atomic-commit protocol (sequence table)

Step Actor Action
1 Writer GET current metadata-pointer from catalog
2 Writer GET TableMetadata at that location
3 Writer build new DataFiles, write to object store
4 Writer build new ManifestFile(s) referencing those files, write to object store
5 Writer build new ManifestList referencing old + new manifests, write to object store
6 Writer build new Snapshot (sequence-number = old + 1, parent = old current)
7 Writer build new TableMetadata referencing the new snapshot, write to object store
8 Writer CAS catalog pointer: old-metadata-location → new-metadata-location
9a Catalog CAS succeeds — new state is current
9b Catalog CAS fails (pointer changed) — writer discards its metadata/snapshot objects (orphans, GC-eligible later) and restarts at step 1

Worked successful commit: writer A reads pointer P0 (seq 41). Builds manifest M-A, snapshot S42 (parent 41, seq 42), metadata T-A. CAS(P0→T-A) succeeds because no one else moved the pointer. Table is now at seq 42.

Worked conflicting-commit-and-retry: writer A and writer B both read pointer P0 (seq 41) concurrently. A commits first: CAS(P0→T-A) succeeds, pointer now T-A (seq 42). B attempts CAS(P0→T-B); the catalog's current value is T-A, not P0, so the CAS fails. B rereads T-A, rebuilds its manifest/snapshot on top of seq 42 (parent 42, seq 43), and retries CAS(T-A→T-B'); this second attempt succeeds if no third writer intervened.

8.3 Schema-evolution model

Column identity = field-id, assigned once, never reused, independent of name or position.

Change Safe without rewrite? Rule
Add column yes new field-id, default null for existing files
Drop column yes field-id retired, never reassigned; old files keep the data physically, reader ignores it
Rename yes field-id unchanged; only the name map changes
Reorder yes field-id unchanged; physical file order irrelevant, projection is by ID
Type promote (int→long, float→double, decimal precision increase) yes reader upcasts; field-id unchanged
Type change requiring narrowing (long→int) no rejected by validator (I5)
Reuse a retired field-id for a new column no rejected — would misinterpret old files' values under the new column's meaning

8.4 Hidden partitioning and transforms

Transforms: identity, bucket[N], truncate[W], year, month, day, hour. A PartitionField binds a source column + transform to a partition field-id; the partition value is derived at write time and stored in the manifest, never supplied by the writer's query predicate.

Worked pruning example: table partitioned by day(event_ts), query predicate event_ts >= '2026-08-01' AND event_ts < '2026-08-02'. Planner derives the transform-range day = 2026-08-01, discards every manifest-list entry whose partition-summary range does not intersect that single day, then discards every remaining manifest entry whose day value differs — data-column predicate, zero manual partition-column handling by the query.

8.5 Scan-planning-and-pruning algorithm (named steps)

  1. Partition predicate derivation — translate the data-column predicate into the table's active transform space.
  2. Manifest-list pruning — discard manifests whose partition-value summary cannot satisfy the derived predicate.
  3. Manifest-entry pruning (partition stats) — within surviving manifests, discard entries whose per-file partition tuple cannot satisfy the predicate.
  4. Data-file pruning (column stats) — discard files whose lower/upper-bounds/null-value-counts prove no row can match the residual (non-partition) predicate.
  5. Delete-file association — attach applicable delete files (by partition + sequence-number range) to each surviving data file.
  6. Row filtering — deferred to the engine at execution time via the residual predicate carried in FileScanTask.

Worked example: table has 10,000 files across 365 daily partitions (≈27 files/day). Query: day = X AND price > 1000. Step 2 prunes to the 1 day's manifest(s) (≈27 files' worth of entries survive out of 10,000 — 99.7% eliminated at list level, zero file bytes read). Step 4, using column stats on price, further eliminates files whose upper-bound(price) <= 1000; assume 40% of the day's files qualify → 11 files scanned out of 10,000 (99.89% total elimination), 2 object-store GETs (manifest-list + 1 manifest) to plan it.

8.6 Row-level delete model

Dimension Copy-on-write Merge-on-read
Write cost rewrite every file containing a changed row write only a small delete file
Read cost none (data already reconciled) apply delete file(s) per scan
Write amplification high — full file rewrite per touched file low — bytes proportional to changed rows
Read amplification none grows until compaction folds deletes into data
Delete file kind n/a position delete (file+row-offset) or equality delete (predicate-equivalent values)
Isolation trivial — new snapshot references new files requires sequence-number-ordered application (I7, I9)

8.7 Time travel and rollback

Time travel: plan a scan against any historical snapshot-id (or timestamp resolved to the nearest snapshot ≤ it) still present in the snapshot-log; cost equals a normal scan at that snapshot (§4) — no replay. Rollback: set current-snapshot-id to a prior snapshot via a normal commit (a new "rollback" snapshot whose manifest list is a pointer to the old one); this is itself an atomic-commit (§8.2), so rollback is crash-safe and never partial.

8.8 Expire-snapshots / orphan-file GC

Procedure: (1) select snapshots older than the retention policy and not referenced by a named SnapshotRef (tag/branch); (2) remove them from the snapshot-log in a normal commit; (3) compute the file-reachability set from all remaining live snapshots' manifest trees; (4) list files in the table's data/metadata paths; (5) delete any file not in the reachability set, respecting I3/I11 ordering — expiry (steps 1–2) must be durably committed before reachability (step 3) is computed. Safety condition: no delete proceeds unless the deleting worker's reachability computation was taken after the expiry commit it depends on, and no concurrent commit within the same window added a snapshot referencing an about-to-be-deleted file.

8.9 Table lifecycle state machine

CREATED -> ACTIVE -> (COMMIT)* -> ACTIVE
ACTIVE -> SCHEMA_EVOLVING -> ACTIVE
ACTIVE -> PARTITION_EVOLVING -> ACTIVE
ACTIVE -> MAINTENANCE (compaction/expire/GC) -> ACTIVE
ACTIVE -> DROPPED (catalog entry removed; files orphaned pending GC)

8.10 Malformed / failure examples

  • Two concurrent conflicting commits on overlapping partitions — resolved by CAS failure + retry (§8.2); no lost update because the loser's write is fully discarded, not merged.
  • A schema change that would lose data (narrowing a type) — rejected by validator before any metadata is written (I5).
  • GC racing a long-running read — reader pinned an old snapshot (I1) that GC's reachability computation must still count as live if not yet expired; GC run before expiry commit is a defect (I11).
  • A stale metadata pointer on an eventually-consistent catalog backend — CAS must be backed by the catalog's own strong-consistency guarantee (ADR-27); a catalog without CAS cannot safely host this protocol.
  • A corrupt manifest (bad Avro/JSON, checksum mismatch) — quarantined at read time, scan fails closed rather than silently under-reading (I8).

Failure-path example: writer completes steps 1–7 of §8.2, then crashes before step 8. The written manifest/manifest-list/metadata objects are never referenced by any pointer — they are orphans from birth, discovered and removed by the next OrphanFileGc pass; the table's current pointer never moved, so no reader was ever affected.

8.11 Statistics-sketch extension point

Beyond the mandatory min/max/null-count/value-count carried in every ColumnStats (§8.1, ADR-12), a table may attach a separate sketch file (Puffin-format, referenced by path from the manifest) holding richer per-column summaries — theta sketches for approximate distinct-count, or bloom-filter-style membership sketches for high-cardinality equality predicates that min/max cannot prune.

Sketch kind Use Pruning contribution
Theta sketch (approx. distinct count) cardinality estimation for join/aggregation planning by the consuming engine not used for file elimination directly; informs the engine's own plan, not this project's pruning step
Bloom-filter-style membership sketch equality-predicate pruning on high-cardinality columns where min/max rarely excludes a file extends step 4 of §8.5: a file is eliminated if the sketch proves the predicate value is definitely absent

Because a sketch file is optional, referenced metadata, and additive (P9 — manifests and their referenced statistics are self-similar, immutable objects), a reader that does not understand a given sketch kind simply ignores it and falls back to min/max-only pruning (P11 forward compatibility) — a missing or unrecognized sketch is never an error, only a missed pruning opportunity.
