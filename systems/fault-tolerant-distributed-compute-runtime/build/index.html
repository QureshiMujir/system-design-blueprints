⬜ Phase 1 — Dataflow model + logical graph

Objectives
  • Define the complete logical dataflow model: Dataset, Dependency, Partitioner, transformation methods, action trigger.
  • Establish lazy DAG semantics: no computation until an action call; graph is a pure data structure.
  • Lock in all types in ftdcr-core and ftdcr-graph that downstream phases depend on.
  • Narrow vs wide dependency classification is the sole basis for stage cutting in Phase 3.
Deliverable

⬜ Phase 3 — DAG scheduler (stages)

Objectives
  • Implement DAGScheduler in ftdcr-driver: walk the DatasetGraph; cut a new Stage at each Dependency::Shuffle; classify ShuffleMapStage vs ResultStage.
  • Build the stage dependency graph (parent stages); submit stages in topological order as their parents complete.
  • Produce correct TaskSet for each stage (one Task per output partition).
  • Invariant I3: a stage is submitted only after every parent stage's map outputs are registered in MapOutputTracker.
Deliverable
  • DAGScheduler produces correct stage graph for: linear chain, reduceByKey, join, multi-stage iterative.
  • Stage submission order is a valid topological sort (parents before children).
  • MapOutputTracker stub correctly gates downstream stage submission on shuffle completion.
  • End-to-end smoke test: wordcount DAG (read → flatMap → reduceByKey) submitted to 2 executors; all tasks dispatched and complete.

⬜ Phase 4 — Task scheduler + dispatch

Objectives
  • Implement TaskScheduler in ftdcr-driver: consume TaskSets from DAGScheduler, assign tasks to executor slots using locality preferences, enforce delay-scheduling backoff, and forward launch RPCs via ftdcr-rpc.
  • Define offer-based dispatch loop: executor offers free cores, scheduler scores tasks against locality tiers, assigns or defers.
  • Track in-flight tasks, attempt numbering, and per-executor slot counts.
  • Expose hooks for ftdcr-ft to resubmit tasks and kill speculative duplicates.
  • Scope: no shuffle logic yet; locality derived from BlockManager reports (Phase 5). Speculative execution wired in Phase 10.
Deliverable
  • TaskScheduler::offer_resources dispatches tasks to executors; verified via multi-executor integration test.
  • Delay scheduling observable: tasks wait for local executor before falling back to ANY.
  • TaskSetManager correctly ages failed tasks and re-enqueues with incremented attempt.
  • Metrics counters emit for each tier; inspectable via /metrics endpoint.

Pitfalls
  • Slot leak on executor crash: in_flight entry never cleared unless ExecutorLost drives cleanup; symptom is free-slot gauge drifting negative; fix: on_executor_lost drains all in_flight entries for that executor.
  • Delay scheduling livelock: if all executors have free slots but no block matches, delay counter never reaches zero; root cause is wrong per-tier reset logic; debug via delay_sched.remaining gauge per stage.
  • Attempt ID collision on speculative copy: naive attempt = retry_count + 1 collides when a speculative task and a retry run concurrently; fix: attempt is a monotonic global counter per (StageId, PartitionId).
  • Stale block locations: BlockManagerMaster reports cached locations before executor eviction propagates; PROCESS_LOCAL launch fails at executor and triggers retry; mitigation: treat launch failure as a block-location invalidation event.
  • Over-subscription on burst: multiple concurrent stages queue TaskSets; scheduler assigns all slots to the first stage; fix: interleave round-robin across active TaskSets when scoring ties.

⬜ Phase 5 — Task execution + block storage

Objectives
  • Implement executor-side task execution: deserialize Task, invoke task.compute(partition_id, parent_iterators), store result in BlockManager.
  • Build BlockManager in ftdcr-executor: in-memory LRU store keyed by BlockId, persistence path for MemAndDisk, and StorageLevel semantics.
  • Implement BlockManagerMaster in ftdcr-driver: location index (BlockId -> Vec<ExecutorId>), insert/remove on block report.
  • Define persist/cache semantics: a Dataset with StorageLevel set will store computed partitions in BlockManager on first pass.
  • Send BlockReport from executor to driver after each task completes.
Deliverable
  • Executor runs ResultTask and returns value or BlockRef.
  • BlockManager stores and retrieves partitions; StorageLevel::MemoryOnly respected.
  • BlockManagerMaster location index updated per block report; TaskScheduler uses locations for locality scoring (Phase 4 integration).
  • persist on a dataset reuses cached partitions on second action invocation (no recomputation).
  • Integration test: two-stage job; first stage result cached; second run of same job skips first stage.

Pitfalls
  • catch_unwind doesn't catch all panics: panics that call abort (e.g. allocator OOM) bypass it; mitigation: executor process restarts via supervisor, driver detects via missed heartbeat.
  • Stale cache after input mutation: user code mutates a persisted block, violating invariant I1's immutable-inputs assumption; enforce Arc<[u8]> (shared immutable slice) as the stored type, no mutable access path.
  • BlockReport lost on RPC failure: driver has no location for the block, locality scoring misses, later fetches fail; fix: retry BlockReport with exponential backoff, executor tracks pending reports.
  • direct_result_max_bytes tuned too high: large inline results inflate RPC message size and spike driver heap; default 128 KB, expose as config, log WARN above 64 KB.
  • Cache key collision: BlockId::Rdd(rdd_id, partition_id) — if RDD IDs are reused across jobs (non-global counter), different data maps to the same key; RDD IDs must be globally monotonic per driver session.

⬜ Phase 6 — Narrow pipelining + disk spill

Objectives
  • Pipeline narrow dependencies within a stage: task_runner chains Dataset.compute iterators without materializing intermediate partitions.
  • Add spill-to-disk to BlockManager: when bytes_in_memory exceeds budget, evict LRU blocks to disk files under MemAndDisk or drop under MemoryOnly.
  • Implement StorageLevel::MemAndDisk fully: blocks live in memory; on eviction, serialized to disk; get promotes from disk.
  • Add MemoryBudget accounting: allocation/release tracked; spill triggered at configurable threshold.
Deliverable
  • task_runner pipelines 3-deep narrow chains without intermediate allocation.
  • BlockManager.put triggers spill when memory budget exceeded; MemAndDisk blocks land on disk.
  • BlockManager.get promotes disk-resident blocks back to memory.
  • Integration test: fill executor memory past budget; assert spill_bytes_total > 0; all blocks still readable.
  • Iterator pipeline test passes with zero intermediate materialization for narrow chains.

Pitfalls
  • Pin leak: task crashes after acquiring pin but before releasing, block permanently pinned; mitigation: RAII BlockPin guard, Drop releases pin count, panic-safe via catch_unwind wrapping the pin scope.
  • Disk spill races under concurrent tasks: two tasks evict the same block simultaneously, both write to {id}.spill; fix: serialize spill writes per BlockId via per-block Mutex.
  • Iterator early drop: a ResultTask dropping the pipeline iterator before exhausting it (e.g. take(n)) must properly drop parent iterators without reading remaining records; test with Drop-counting records.
  • Spill path on tmpfs: if executor_work_dir is on tmpfs, "disk spill" does not free physical RAM; deployment must route spill dir to a real block device; log WARN on startup if spill dir is tmpfs.
  • Memory budget ignores deserializer buffers: try_acquire(data.len()) tracks stored bytes but not transient deserialization buffers during put; add a 2x headroom factor or track separately.
  • LRU eviction starving active partitions: many single-access partitions defeat LRU-by-access-time caching; use an access-frequency hint for persisted datasets, marking them "sticky" with elevated priority.

⬜ Phase 7 — Shuffle

Objectives
  • Map side: after ShuffleMapTask computes, partition output records by Partitioner; write per-reduce shuffle blocks to BlockManager; spill to disk under memory pressure; merge spill files into one final shuffle segment + index file.
  • Register MapStatus (shuffle_id, map_id → per-reduce (executor_id, byte_size)) into MapOutputTracker on driver.
  • Reduce side: ResultTask or downstream ShuffleMapTask queries MapOutputTracker; batches BlockFetchRequest RPCs to upstream executors; streams fetched blocks; merges/aggregates for its reduce partition. Transient fetch errors retry with backoff; FetchFailed after limit propagates to driver for stage resubmission.
  • Invariants enforced: I2 (immutable committed map output), I6 (tracker reflects only committed outputs), I9 (reduce task fetches exactly one committed block per upstream map task). Constraint: BlockId::Shuffle(shuffle_id, map_id, reduce_id) is the canonical shuffle block identity; shuffle files are write-once; map-side commit is final.
Deliverable
  • wordcount job on 100 MB text completes end-to-end with reduceByKey; top-10 counts match reference. Map-side shuffle files (*.data, *.index) visible on executor disk, parseable by ftdcr-cli dump-shuffle.
  • MapOutputTracker returns locations for all map outputs; reduce tasks fetch and merge correctly. Spill path exercised (shuffle.spill_threshold_bytes=4096) with output matching a no-spill run.
  • BlockServer serves blocks to remote executors with non-empty fetch-latency histogram; shuffle_write_bytes_total == shuffle_read_bytes_total within framing overhead.
  • distributed_join example runs end-to-end via shuffle with output matching reference; MapOutputTracker snapshot round-trips (Phase 12 foundation).
  • dump-shuffle <job_id> <shuffle_id> <map_id> reads *.data+*.index and prints per-reduce record counts, for debugging and fixture generation.
  • Block CRC end-to-end test: inject a bit-flip in BlockFetchResponse, verify ChecksumMismatch + retry + job completion.
  • shuffle.combiner_sample_rate=0.001: verify map-output bytes reduced vs no-combiner baseline on wordcount.

Pitfalls
  • Map output lost before reduce fetch: executor dies after registering MapStatus but before reduce fetch; manifests as FetchFailed/BlockNotFound; debug via fetch_failed_total spike + heartbeat timeout; ftdcr-ft resubmits the map stage (Phase 9, §9.2).
  • Spill merge misses in-memory residual: merge loop exits after SpillFiles but skips flushing remaining in-memory buffers; last N records silently dropped; debug by comparing shuffle_write_bytes_total vs spill-file sizes; fix: explicit final flush before the merge loop.
  • u32 overflow in index offsets for large partitions: shuffle block > 4 GB wraps a u32 offset silently, corrupting reads; fix: index always uses u64 offset/len, validated at write and read.
  • Fetch parallelism OOM on reducer: 1000 concurrent BlockFetchRequests buffer 1000 blocks at once, exceeding executor RSS; fix: Semaphore(shuffle.max_concurrent_fetches_per_executor) and pipeline fetch-deserialize-aggregate instead of buffer-all.
  • Stale MapOutputTracker after stage resubmission: previous attempt's outputs remain registered, reduce task fetches a deleted file; fix: unregister_all(shuffle_id) before resubmitting the map stage, gated on unregister completing. FetchFailed swallowed by reduce-side aggregator: a catch-all unwrap_or_default in a user combiner hides it, job appears to complete with silently missing data; fix: FetchFailed is a dedicated enum variant re-raised unconditionally in ShuffleReader::fetch, bypassing user catch-alls.
  • Index-data file desync on crash: crash between fsync(data) and write(index) leaves the index absent/zero-length; detected on open by checking index_end_offset == data_file_size — mismatch is treated as BlockNotFound → retry → FetchFailed → map stage resubmit.

⬜ Phase 8 — Lineage + Recomputation

Objectives
  • Record the full lineage DAG for every Dataset: its Dependency list, compute function reference, Partitioner, and optional CheckpointRef.
  • On partition loss, build a RecomputePlan: walk lineage backward from lost partitions to nearest available ancestor (live cached block, checkpointed partition, or raw input dataset). Execute the plan recomputing only missing partitions.
  • Wide-dep recovery: losing a reduce partition may require re-running upstream map tasks; plan includes synthetic ShuffleMapStage nodes as needed.
  • Invariants: I1 (recomputed partition bit-identical to original), I5 (every in-memory partition recoverable), I8 (checkpoint truncates lineage walk).
  • Integration: ftdcr-lineage consumed by ftdcr-ft (Phase 9) for recovery; by ftdcr-ckpt (Phase 11) for lineage truncation.
Deliverable
  • ftdcr-lineage crate compiles; LineageGraph populated for all jobs. build_recompute_plan returns correct plans for synthetic loss scenarios (§8.5 fixtures).
  • Integration test: executor loses a partition mid-job; DAGScheduler::recover submits only the lost partition's stage; job output is bit-identical to a no-loss run (I1). Wide-dep recovery test: losing a reduce partition triggers map-stage resubmission via plan.
  • ftdcr-cli debug lineage <job_id> emits a DOT-format lineage graph for visual verification.
  • lineage_recompute_partitions_total non-zero after a recovery test; recompute_plan_build_latency_us histogram non-empty; check_recompute_completeness passes after every integration test.

Design decision: narrow vs wide recompute scope — narrow recovery recomputes only the lost partition of the parent dataset (O(1) stages); wide recovery must recompute all upstream map partitions that produced shuffle blocks for the lost reduce partition (up to O(num_map_partitions)). Mandatory optimization: check MapOutputTracker before building the plan and recompute only map tasks whose outputs are actually missing, shrinking plan size from O(M) to O(lost_map_tasks) — implemented as a "narrow-down wide deps" step after the initial BFS.

Pitfalls
  • Wide-dep lineage explosion: losing one reduce partition of a 1000-partition shuffle triggers re-running all 1000 map tasks; mitigation: check MapOutputTracker and include only the map tasks for actually-lost outputs; signal: recompute_stages_submitted >> 1.
  • Non-deterministic compute function: user function reads wall clock, iterates a HashMap randomly, or calls an external service, silently violating I1; detect via optional determinism checker re-running a sample partition (task.determinism_check_sample_rate=0.01).
  • Stale BlockIndex after eviction: block evicted from BlockManager but BlockIndex not atomically updated, so the plan treats it as an available base and recovery skips it; fix: BlockManager::evict removes from BlockIndex inside the same lock scope.
  • Infinite recompute loop: a parent partition is also lost, triggering another recover call; mitigation: build_recompute_plan walks past all contiguously lost ancestors to the first available/raw input in one pass — no recursive recover calls.
  • Checkpointed dataset absent from BlockIndex on driver restart: checkpoint exists on durable store but BlockIndex isn't seeded, so the plan walks past it; fix: on job start, scan the checkpoint store and BlockIndex::insert each checkpointed (dataset_id, partition_id).
  • Concurrent recovery for same partition: two executors lose different ancestors of the same leaf, and two concurrent build_recompute_plan calls both decide to recompute it; mitigation: DAGScheduler::recover checks block_index.available before submitting each RecomputeStage, so the second recovery skips already-submitted stages.

⬜ Phase 9 — Failure Detection + Retry

Objectives
  • Detect executor failure via heartbeat timeout; transition executor to Lost; invalidate its in-memory blocks in BlockManagerMaster; unregister its map outputs from MapOutputTracker; resubmit all running tasks.
  • Handle FetchFailed from reduce tasks: identify the responsible ShuffleMapStage; unregister stale MapStatus; resubmit only the affected map partitions; requeue the failed reduce task.
  • Track retry attempts per (StageId, PartitionId); after ft.max_task_attempts, fail the job with structured MaxAttemptsExceeded error.
  • Invariants enforced: I4 (exactly-once result), I5 (lost partitions recoverable), I6 (MapOutputTracker reflects only committed outputs), I7 (at most one attempt's result accepted per partition).
  • Constraints: speculative execution stubbed here (full impl Phase 10); driver HA / persisted RetryTracker gated to Phase 12.
Deliverable
  • Kill one executor mid-job; driver detects within ft.heartbeat_timeout_ms + ft.heartbeat_check_interval_ms; affected tasks resubmit; job completes with correct output.
  • Inject FetchFailed from a reduce task; map stage resubmits; reduce task re-queued; job completes. Task fails ft.max_task_attempts times: MaxAttemptsExceeded raised with full per-attempt history; job fails cleanly.
  • ftdcr-cli chaos kill-executor <id> triggers a kill with observable recovery metrics; executor state transitions observable via GET /debug/executors/<id>.
  • executor_loss_recovery_latency_ms P99 < 2 × heartbeat_timeout_ms after a kill test.
  • Heartbeat reconciliation test: dropping one heartbeat does not trigger Lost. FetchFailed on an already-committed reduce partition causes no stage resubmit (stage_resubmit_total unchanged).
