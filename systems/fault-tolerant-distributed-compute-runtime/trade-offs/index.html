Decisions (§9) · 28 ADRs

A01

Implementation language

Chosen

Rust (stable channel)

Rejected

Scala, Java, Go, C++

When the rejected choice is right

Scala/Java (JVM) when integrating tightly with the existing Spark/Hadoop ecosystem and GC pauses are tolerable; Go when goroutine simplicity and fast builds outrank zero-pause latency

Why: memory safety without GC pauses; zero-cost abstractions; fearless concurrency; no stop-world

A02

Build system

Chosen

Cargo (workspace with per-crate bins)

Rejected

Bazel, Buck2, Make

When the rejected choice is right

Bazel/Buck2 in a large polyglot monorepo needing remote build caching across languages

Why: native Rust ecosystem; workspace unifies crates; incremental builds; simple CI integration

A03

Async runtime

Chosen

Tokio (multi-thread)

Rejected

async-std, smol, custom executor

When the rejected choice is right

A custom executor when deterministic scheduling for simulation testing is required (FoundationDB-style); smol for a minimal embedded footprint

Why: mature; well-tested under high concurrency; tokio::net, tokio::sync cover all RPC needs

A04

RPC transport

Chosen

custom framed TCP (ftdcr-rpc) over Tokio

Rejected

gRPC/tonic, Cap'n Proto RPC, nanomsg

When the rejected choice is right

gRPC/tonic when cross-language clients and a standard IDL/ecosystem matter more than full control of framing

Why: minimal dependency; full control of framing + backpressure; gRPC overhead not warranted

A05

Serialization (default)

Chosen

bincode 2.x

Rejected

serde_json, postcard, Cap'n Proto, FlatBuffers

When the rejected choice is right

Cap'n Proto/FlatBuffers when zero-copy access to large messages without deserialization is required; postcard for no_std/embedded

Why: fastest Rust binary serde; zero-copy read option; compact; supports serde derive

A06

Serialization (event log)

Rejected

When the rejected choice is right

Why: human-readable; compatible with log-aggregation tooling; low-volume (not on hot path)

A07

Shuffle file format

When the rejected choice is right

Why: matches Spark shuffle design; index enables O(1) reduce-partition seek; no extra dependency

Partitioner implementation

Chosen

Hash (FNV or SipHash-1-3) + Range (sorted bounds vec)

Rejected

When the rejected choice is right

Alternative Architectures (Roads Not Taken)

A1 — Bulk materialization to a DFS between every step (MapReduce model).

input → map → write HDFS → sort/shuffle → reduce → write HDFS → next job

Wins for very large single-pass batch jobs where disk-durable intermediates and dead-simple recovery beat in-memory speed. Embodied by MapReduce/Hadoop. Rejected because iterative jobs (PageRank, ML) re-read from disk every step — lineage + in-memory caching is 10–100× faster (§2, MM1).

A2 — True streaming with distributed snapshots (Chandy-Lamport).

unbounded stream → pipelined operators → periodic barrier snapshot → exactly-once on replay

Wins for unbounded, low-latency continuous processing where micro-batch latency is unacceptable. Embodied by Apache Flink. Rejected for v1 because the target is batch dataflow (§4); streaming/micro-batch is deferred (Register).

A3 — Dynamic bottom-up task/actor scheduling (no static DAG).

tasks spawn tasks at runtime → distributed scheduler places them → object store moves results

Wins for irregular, dynamically-spawned graphs (RL, hyperparameter search) that cannot be planned ahead. Embodied by Ray. Rejected because a static stage DAG enables global scheduling decisions (locality, speculation) and matches the batch-analytics target.

A4 — Active replication of intermediate data (no recompute).

each partition written to k nodes → on loss, read a replica instead of recomputing

Wins when recomputation is prohibitively expensive (very deep lineage, non-reproducible sources) and storage is cheap. Embodied by replicated-state stream processors. Rejected because lineage recompute is cheaper for reproducible transforms (MM1, §4.5), and checkpointing covers the deep-lineage case (Phase 11).
