354 — Fault-Tolerant Distributed Compute Runtime from Scratch

Project Number: 354

Project Name: Fault-Tolerant Distributed Compute Runtime from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal

1.1 Precise Engineering Definition

Build a multi-node, fault-tolerant distributed compute runtime: a single driver process constructs a lazy DAG of typed, partitioned datasets; cuts it into stages at shuffle (wide-dependency) boundaries; schedules locality-aware tasks onto executor processes; materializes shuffle blocks; and recovers from executor failure by recomputing lost partitions from recorded lineage or durable checkpoints — so that single-executor loss is transparent and every job produces an exactly-once result.

1.3 Intended Deployment Model

  • Topology: one driver process + N executor processes; N = 2..64 for development, target 10..1000 for production validation.
  • Network: TCP LAN; executor IPs known at driver start or registered via ftdcr-rpc register message.
  • Storage: a shared-access durable store (local FS for single-machine tests; NFS/S3 for multi-node) used for shuffle spill, checkpoint writes, and block replication.
  • Process model: driver and executors are separate OS processes; crash isolation is the primary FT mechanism.
  • No containers required: the runtime does not mandate any orchestration layer; operators launch executors manually or via a thin wrapper.

1.5 Language Rationale

Rust is required. A distributed dataflow engine must move serialized closures and large data blocks between nodes, detect worker death, and recover lost partitions without corrupting results. Rust gives safe zero-copy serialization framing, precise control over the in-memory/disk block store, and Send/Sync guarantees for the driver's concurrent scheduler. The type system enforces at compile time that block ownership is correctly transferred across executor boundaries, that the lineage graph is accessed without data races, and that task-attempt identifiers are not confused with committed-result identifiers.

2.2 Historical and Architectural Significance

  • MapReduce (OSDI 2004): introduced fault-tolerant batch compute via task re-execution; established the two-phase shuffle.
  • RDD / Spark (NSDI 2012): replaced intermediate HDFS writes with in-memory lineage; generalized MapReduce to arbitrary DAGs; named the design principles this project encodes (P1–P10).
  • Dryad (EuroSys 2007): showed DAG-structured dataflow as a first-class abstraction; influenced stage graphs.
  • Ray (OSDI 2018): extended the task-graph model to dynamic execution and actor state; motivates the driver-as-authoritative-scheduler design (P10).
  • Chandy-Lamport / Flink checkpointing: stateful stream checkpointing; this project applies the checkpoint-truncates-lineage variant for iterative batch.
  • This project is the canonical portfolio demonstration that a developer understands distributed system correctness: exactly-once results despite arbitrary single-node failure, without a distributed transaction protocol.

2.3 Engineering Muscles Developed

  • Concurrent state machine design: driver scheduler runs interleaved stage-ready events, heartbeat timeouts, and task-status callbacks.
  • Zero-copy I/O: shuffle block writes use sendfile/mmap; block reads avoid heap allocation on the hot path.
  • Protocol design: RPC message framing, versioning, and backward compatibility without an IDL dependency.
  • Test harness for distributed systems: deterministic failure injection, network partition simulation, result-determinism assertions.
  • Performance measurement: shuffle throughput, task-dispatch latency, memory pressure behavior under spill.

3.2 Subsystem Descriptions

User program / ftdcr-graph. The user calls transformation methods (map, filter, flatMap, reduceByKey, join) on Dataset values; each call extends the DAG by adding a node and recording its Dependency (narrow or wide). No data moves. An action (collect, count, saveAsFile) triggers job submission to the driver. Data flow in: user closures + parent dataset references. Data flow out: a logical Dataset DAG handed to DAGScheduler. Trust boundary: user-provided closures are serialized and shipped to executors; they are untrusted from a crash-safety standpoint (a panic in a closure kills one executor, not the driver).

DAGScheduler (ftdcr-driver). Receives a job request (a Dataset + action). Walks the DAG in reverse topological order; inserts a stage boundary at every Dependency::Shuffle. Builds a Stage DAG (parent stages → child stages). Submits stages in topological order, gating each stage on its parents' MapStatus being fully registered. Maintains stage state: Pending | Running | Finished | Failed. Data flow in: job request, TaskResult events from TaskScheduler, FetchFailed events from executors. Data flow out: TaskSet submissions to TaskScheduler, stage-resubmit commands on failure.

TaskScheduler (ftdcr-driver). Receives a TaskSet; assigns one task per partition. Tracks executor capacity (free slots, last-known locality). Implements delay scheduling: holds a task for up to a configurable window to wait for a preferred executor; falls back to rack-local then any. Launches tasks via ftdcr-rpc. Receives status updates; reports TaskResult or FetchFailed back to DAGScheduler. Concurrency boundary: the scheduler loop runs in a single tokio task, serializing all dispatch decisions; executor state is protected by an Arc<Mutex<ExecutorPool>>.

MapOutputTracker + BlockManagerMaster (ftdcr-shuffle / ftdcr-block, driver-side). MapOutputTracker is the authoritative registry for shuffle map outputs: maps ShuffleId → [Option<MapStatus>] (one entry per map-task partition). BlockManagerMaster is the location index for all BlockIds across executors: maps BlockId → Vec<ExecutorId>. Both are in-memory data structures on the driver, updated by executor block-report and status-update messages. Persistence boundary: MapOutputTracker state is lost if the driver crashes (driver HA is deferred; I6 is maintained within a session).

Lineage graph (ftdcr-lineage). Records the Dependency edges of every Dataset node. On a PartitionLost event, RecomputePlan::build() walks ancestors until it reaches a cached, checkpointed, or input partition. Returns an ordered list of stages and partitions to recompute. No network I/O; pure in-memory graph traversal. After a checkpoint is confirmed, Lineage::truncate(dataset_id) removes all ancestor edges up to the checkpointed dataset (I8).

Fault-tolerance orchestrator (ftdcr-ft). Runs a heartbeat monitor: each executor sends a Heartbeat every T_hb seconds; the monitor marks an executor Lost after T_timeout = 3 × T_hb with no message. On ExecutorLost: informs BlockManagerMaster (remove all blocks on that executor), informs MapOutputTracker (invalidate map outputs produced by that executor), resubmits running tasks, triggers lineage recomputation for lost cached partitions. Tracks per-task attempt counts; after max_task_failures the job fails. Tracks per-executor failure counts; after max_executor_failures the executor is blacklisted (Phase 12).

Speculative execution (ftdcr-ft, Phase 10). Monitors task runtime within a running TaskSet. Computes the median and 75th-percentile completion time. Tasks running beyond speculative_threshold × p75 are duplicates-launched on a different executor. First attempt to report Finished wins via commit_coordinator; the other is killed. Invariant I7: only one attempt's result is accepted per output partition.

Executor / BlockManager (ftdcr-executor, ftdcr-block). Each executor is an OS process. It registers with the driver on startup, then receives LaunchTask RPC messages. The task-runner deserializes the closure, invokes task.compute(partition_id, block_manager), and writes output to BlockManager. BlockManager manages a memory budget (configurable bytes); on pressure, evicts LRU blocks to disk (spill). Reports block locations to BlockManagerMaster on write. On ShuffleMapTask completion, registers MapStatus with MapOutputTracker. Persistence boundary: in-memory blocks are lost on executor crash; disk-spilled blocks are lost if the disk is co-located (single-machine) or retained if on shared storage.

Shuffle service (ftdcr-shuffle). Map side: after a ShuffleMapTask completes, output is partitioned by Partitioner, written to per-reduce shuffle blocks on the executor's BlockManager, and reported as MapStatus. Reduce side: a ResultTask or downstream ShuffleMapTask queries MapOutputTracker for all map-output locations for its ShuffleId + reduce-partition index, then opens parallel HTTP/TCP fetch connections to each map executor's BlockManager, assembles the blocks, and merges/sorts as needed. Fetch retries on transient failure (I9). FetchFailed on non-transient failure triggers stage resubmission via DAGScheduler.

Checkpoint service (ftdcr-ckpt). On user or driver instruction, serializes all partitions of a selected Dataset to the durable store. On completion, sends a CheckpointComplete event to the driver, which calls Lineage::truncate. During recomputation, RecomputePlan checks the checkpoint store before walking further ancestors (I8). Persistence boundary: checkpoint data outlives the driver and executor processes; correctness depends on the durable store's write-durability guarantee.

RPC layer (ftdcr-rpc). Length-prefixed binary framing over TCP. Message enum covers: Register, Heartbeat, LaunchTask, KillTask, TaskStatus, BlockReport, FetchBlock, MapOutputUpdate. Driver listens on a fixed port; executors connect on startup. Codec is versioned; unrecognized message types are skipped (forward compatibility). Concurrency model: one tokio TCP listener per side; messages dispatched to internal channels consumed by the scheduler loop or task runner.

P1. Lineage over Replication

Recover lost partitions by recomputing from parent partitions, not by eagerly maintaining replica copies.

  • Trade-off: Recovery requires re-executing the parent compute chain, proportional to lineage depth. Eager replication gives O(1) recovery time but costs 2×–3× storage at write time and complicates consistency. Lineage wins for write-heavy ETL; replication wins for frequently-read, expensive-to-recompute cached data (use StorageLevel::MemAndDisk + replication=2 for that subset).
  • Operational: Dataset must record deps: Vec<Dependency> completely at construction. A dataset with an incomplete dep chain (e.g., one that reads from an external system inside compute) is non-recoverable (I5 violation). Mark such datasets explicitly as non-lineage-recoverable; mandate checkpoint before they appear in a long pipeline.
  • Violation consequence: Lineage incomplete → RecomputePlan::build cannot reach a checkpointed or input ancestor → recovery fails → job aborts with "partition X unrecoverable" despite no hardware fault.
  • Reference: ftdcr-lineage; RecomputePlan; Phase 8; I5.

P2. Deterministic Tasks

A task recomputed from identical inputs must yield bit-identical output (I1).

  • Trade-off: Restricts compute fn contracts — no random seeds, no wall-clock timestamps, no non-deterministic external I/O. This is a contract enforced by documentation and testing, not runtime interception; the compiler cannot verify determinism.
  • Operational: ftdcr-core API docs mandate determinism. ftdcr-graph provides #[cfg(test)] fn assert_deterministic(dataset, partition) — runs compute twice on same input, asserts byte equality. Phase 14 chaos suite calls this for all user-provided transformations.
  • Violation consequence: Phase 8 recomputes partition P; P' ≠ P. Any reduce task that already consumed bytes from P now holds inconsistent data relative to P'. Aggregations are wrong; joins produce phantom rows. The error is silent unless Phase 14 bit-identity check is run.
  • Reference: I1; ftdcr-lineage; Phase 8; Phase 14.

P3. Stage Boundaries at Shuffles

Pipeline narrow dependencies within a single stage; cut a new stage at every wide (Dependency::Shuffle) dependency.

  • Trade-off: Coarser stages (more narrow ops fused) reduce scheduling overhead and improve CPU cache locality within a task; however, they increase peak partition memory per task (all fused narrow ops share one partition buffer). The cut point is deterministic and not tunable: Dependency::Shuffle always generates a stage boundary.
  • Operational: DAGScheduler::build_stages walks the Dataset lineage DFS, pushing a new ShuffleMapStage at each Dependency::Shuffle, then a ResultStage at the action. Walk uses a visited set to avoid revisiting shared ancestors (diamond DAGs). Output: directed acyclic Stage graph with topological ordering guaranteed.
  • Violation consequence: A Dependency::Shuffle not cut into its own stage means ShuffleMapTask outputs are never committed to MapOutputTracker; I3 violated; downstream ResultStage launches with no map output locations; every reduce task fails with FetchFailed immediately; job fails after max_stage_retries.
  • Reference: ftdcr-graph; Stage; DAGScheduler; Phase 3; I3; I6.

P4. Idempotent, Attempt-Tagged Commit

Task output is write-once; the commit coordinator accepts the first successful attempt and silently discards all subsequent attempts for the same (stage, partition) slot.

  • Trade-off: Requires a commit coordinator round-trip from executor to driver (one RPC per task completion). Adds ~1 ms latency per task on LAN; negligible for tasks lasting seconds. Alternative (atomic file rename on shared FS) avoids the RPC but requires a distributed filesystem; the RPC model is simpler and works with local executor storage.
  • Operational: TaskId = (stage_id, partition_id, attempt_number). Driver CommitLog (keyed by (stage_id, partition_id)) records which attempt_number committed. On commit RPC: if slot empty → accept, write block location, notify DAGScheduler; if slot occupied → reject (no error, executor discards result).
  • Violation consequence: Commit coordinator absent or uses last-write-wins semantics → two speculative copies both commit → MapOutputTracker records two MapStatus entries for same (ShuffleId, map_partition) → reduce task fetches both blocks → duplicate records in aggregation. I7 violated.
  • Reference: TaskId; TaskAttempt; ftdcr-ft; Phase 10; I4; I7.

P5. At-Least-Once Execution + Idempotent Commit => Exactly-Once Results

The runtime retries failed tasks without bound (up to max_task_attempts); because each commit is idempotent (P4) and deterministic (P2), the job result is equivalent to exactly one execution of every task.

  • Trade-off: Exactly-once output holds iff P2 and P4 both hold. If P2 breaks (non-deterministic compute), multiple accepted committed outputs for different slots may diverge from what a single-execution would produce, but only in correlated ways. If P4 breaks, multiple commits are accepted per slot and output is inflated.
  • Operational: No deduplication in the output writer or in ResultTask. The CommitLog is the single authority. Audit: at job completion, assert CommitLog has exactly num_partitions accepted entries; each maps to exactly one attempt_id.
  • Violation consequence: Shuffle write uses append semantics without attempt gating (e.g., open file in O_APPEND mode without checking prior commit) → retry appends a second copy of the partition → reduce reads 2× bytes → reduceByKey sums doubled; join emits duplicate rows. Phase 14 conformance test catches this.
  • Reference: I4; I10; ftdcr-ft; Phase 9; Phase 14.

P6. Transparent Single-Failure Recovery

Losing one executor must not surface as a job error to the user; the driver detects the failure, marks all that executor's blocks as lost, and recomputes missing partitions automatically.

  • Trade-off: Recovery adds wall-clock time proportional to lineage depth × recomputation cost. For deep iterative jobs without checkpoints, recovery of a late failure can take longer than the original failed computation. Checkpoint (P8) bounds this. Simultaneous loss of K>1 executors: FTDCR still attempts recovery; only if K exceeds available capacity to recompute does the job fail — this is by design, not a bug.
  • Operational: ExecutorInfo.last_seen updated on each heartbeat. ftdcr-ft runs a timer task checking now - last_seen > heartbeat_timeout_ms. On timeout: send ExecutorLost(executor_id) to DAGScheduler; BlockManagerMaster::mark_executor_lost(id) removes all BlockId entries for that executor; MapOutputTracker::remove_executor_map_outputs(id) invalidates shuffle entries; DAGScheduler resubmits affected stages.
  • Violation consequence: BlockManagerMaster not called → stale block locations remain → DAGScheduler dispatches reduce tasks to dead executor → FetchFailed on each → stage resubmission loop; if retry limit reached on FetchFailed, job fails with a confusing error rather than transparent recovery. I5 and I6 both violated.
  • Reference: ExecutorInfo; ftdcr-ft; ftdcr-block; Phase 9; Phase 12; I5; I6.

P7. Speculative Execution Bounds the Tail

A small number of straggling tasks must not dominate total job latency; launch duplicate copies of slow tasks on different executors and accept whichever finishes first.

  • Trade-off: Speculative tasks consume extra CPU and network (shuffle re-read). In under-provisioned clusters, speculation may delay other tasks. Config knobs: speculation_enabled (default true), speculation_quantile (default 0.75), speculation_multiplier (default 1.5), speculation_min_tasks_running (default 3 in stage). Disable for CPU-bound stages where every core is occupied.
  • Operational: ftdcr-ft::SpeculationChecker samples running task durations per stage every speculation_interval_ms. A task with elapsed > quantile * multiplier and elapsed > speculation_min_task_runtime_ms → emit SpeculativeTaskLaunch to TaskScheduler → schedule on different executor from original. P4 commit coordinator accepts first finisher; second commit is a no-op.
  • Violation consequence: Without speculation, one degraded node (network flap, disk degradation, noisy neighbor) running one task per stage holds the entire stage hostage; P99 job latency equals the slowest node, not the median. With speculation but without P4 idempotent commit: double results inserted.
  • Reference: ftdcr-ft; Phase 10; P4; I7.

P8. Checkpoint to Bound Recomputation

Periodically persist selected datasets' partitions to durable storage; truncate lineage at the checkpoint so recovery never replays further than one checkpoint interval.

  • Trade-off: Checkpoint write serializes all partitions of a dataset to object_store — expensive: O(dataset_size) I/O. Too frequent → throughput degradation; too infrequent → deep lineage replay on late failure. Recommended default: checkpoint every N iterations where N * iteration_cost ≈ checkpoint_cost (break-even point). For k-means at 200 iterations, checkpoint every ~10 iterations.
  • Operational: ftdcr-ckpt::Checkpointer::checkpoint(dataset) → writes all partitions → on completion calls ftdcr-lineage::LineageGraph::truncate_at(dataset_id) → removes all ancestor deps. RecomputePlan::build stops recursion at a node marked CheckpointedAt. object_store path: checkpoints/{job_id}/{dataset_id}/part-{partition_id}.bin.
  • Violation consequence: truncate_at not called after checkpoint succeeds → lineage graph retains full history → RecomputePlan still walks to iteration 0 ancestors → recovery cost O(total job runtime). I8 violated.
  • Reference: ftdcr-ckpt; Checkpoint; RecomputePlan; Phase 11; I8.

P9. Backpressure and Spill, Never OOM

When memory is exhausted, write excess data to disk and throttle upstream producers; the runtime degrades to slower I/O-bound operation rather than crashing.

  • Trade-off: Disk spill adds I/O latency (random reads on HDD can be 100×–1000× slower than DRAM). Spill competes with shuffle fetch for disk bandwidth. Over-aggressive eviction (low threshold) causes thrashing; under-aggressive (high threshold) risks OOM. Tunable: executor_memory_fraction (default 0.6 for execution, 0.4 for storage); spill_compress (default lz4).
  • Operational: BlockManager maintains two memory pools: execution_pool (sort buffers, aggregation maps) and storage_pool (cached RDD blocks). When execution_pool overflows: evict LRU storage_pool blocks to disk (StorageLevel::MemAndDisk). When storage_pool overflows under use_disk=true: serialize block to spill file and free memory. Shuffle write: ExternalSorter spills sorted runs at configurable threshold, merges on read (Phase 6, Phase 7).
  • Violation consequence: A Dataset.compute that materializes a large HashMap without spill → heap exhausted → kernel SIGKILL → executor process dead → Phase 9 recovery triggered — recovery cost >> spill cost. Symptom: executor disappears, heartbeat_timeout fires, stage resubmitted.
  • Reference: BlockManager; StorageLevel; ftdcr-block; Phase 6; Phase 13.

P10. The Driver is Authoritative

All scheduling decisions, shuffle map output locations (MapOutputTracker), and block locations (BlockManagerMaster) are managed centrally at the driver; executors are stateless workers that report up.

  • Trade-off: Single driver bottlenecks at ~10K concurrent tasks/s (RPC throughput bound) and is a single point of failure. Horizontal scaling and driver HA are deferred (Phase 12, gated). Benefit: zero distributed consensus overhead; scheduling decisions are O(1) lookups in driver-side state; no Paxos/Raft needed; debugging requires only driver logs.
  • Operational: All executor state changes reported to driver via ftdcr-rpc (StatusUpdate, BlockReport, Heartbeat). Shuffle data blocks transfer peer-to-peer (executor → executor), but location metadata always goes through driver. Executor-side MapOutputTracker cache holds a copy of tracker state with a generation_id; driver broadcasts invalidations on executor loss.
  • Violation consequence: Executor caches stale MapOutputTracker state (executor failed, entries not invalidated in cache) → reduce task fetches dead block location → FetchFailed → driver resubmits producing stage → if cache not invalidated, next reduce attempt hits same dead location → infinite resubmit loop until retry exhaustion. I6 violated; symptom: stage resubmit counter incrementing without progress.
  • Reference: MapOutputTracker; BlockManagerMaster; ftdcr-driver; Phase 12; I6.

P11. Idempotent At-Least-Once Commit

Task outputs commit via atomic rename / commit-coordination so re-execution after a retry never double-writes.

  • Trade-off: P4/P5 describe the RPC-based commit-coordinator path for task results; P11 generalizes the same idempotency guarantee to the byte-level write path — block files, shuffle segments, and checkpoint partitions must each land via an atomic operation (write-to-temp + rename, or store-level put-if-absent) rather than in-place append. This costs one extra rename/put syscall per write but removes an entire class of partial-write corruption on retry, at negligible latency (<1 ms local FS, provider-dependent for object stores).
  • Operational: every durable write path in ftdcr-block, ftdcr-shuffle, and ftdcr-ckpt follows the same pattern — write to <path>.tmp-{attempt}, fsync, then rename(2) to the final path only after the driver-side commit coordinator has accepted that attempt (P4). A retried or speculative attempt that loses the race never reaches rename; its .tmp file is discarded by a periodic sweep keyed on attempt_id.
  • Violation consequence: a write path that appends or truncates a shared file (no atomic rename) under retry produces a corrupted or double-counted file even when the commit coordinator correctly rejected the losing attempt at the RPC level — the byte-level guarantee and the RPC-level guarantee must both hold, or the invariant is broken silently. Symptom: I2/I7 pass metric checks yet output bytes are still wrong.
  • Reference: ftdcr-block; ftdcr-shuffle; ftdcr-ckpt; Phase 4; Phase 5; Phase 7; Phase 11; I2; I4; I7.

P12. Recompute over Replicate (Lineage-First Recovery)

Lost partitions are rebuilt from lineage rather than replicated, trading recompute cost for memory/bandwidth.

  • Trade-off: this is the resource-allocation corollary of P1 — given a finite memory/network budget, FTDCR spends it on nothing (lineage is free until a failure occurs) rather than on standing replica copies. The cost is deferred and probabilistic (paid only on failure, proportional to lineage depth) versus replication's cost, which is certain and paid on every write (2×–3× storage/network at write time). For a cluster whose failure rate × recompute cost stays below its replication overhead, lineage-first strictly dominates; the crossover point is where P(failure) * recompute_cost > replication_overhead, which operators can compute from lineage_depth_at_checkpoint and historical executor_lost_total.
  • Operational: ftdcr-lineage::RecomputePlan is the sole recovery path for MemoryOnly/MemAndDisk partitions; ftdcr-block does not maintain redundant copies unless a dataset is explicitly marked replication=2 (an opt-in exception for hot, expensive-to-recompute data, per P1). Capacity planning treats recompute CPU-seconds, not extra storage bytes, as the primary reserved resource for fault tolerance.
  • Violation consequence: a subsystem that silently begins replicating blocks "for safety" (e.g., a well-meaning cache warm-up path that double-writes to two executors) breaks the resource model this architecture is capacity-planned against — it consumes the network/storage budget P12 assumed was free, without shrinking the recompute-time budget, so the system ends up paying both costs. Detected via checkpoint_lineage_reachability_audit (I12) reporting unexpected extra copies, or storage utilization exceeding the 1× (or explicit 2×) amplification factors documented in §4.5.
  • Reference: ftdcr-lineage; ftdcr-block; Phase 1; Phase 8; Phase 11; I1; I5; I12.

I1 — Deterministic Recomputation

Statement: A recomputed partition is bit-identical to its original.

  • Why it matters: Foundation of P1 (lineage-based recovery); any divergence silently corrupts all downstream aggregations and joins.
  • Enforced in: ftdcr-lineage::RecomputePlan; Dataset.compute API contract (ftdcr-core).
  • Violation detection: Phase 14 chaos test: recompute partition twice, assert_eq!(bytes_a, bytes_b); store sha256(partition) in CommitLog at first commit; re-hash post-recovery; assert equal.
  • Telemetry: Gauge partition.recompute_hash_mismatch; ERROR log {dataset_id, partition_id, original_hash, recomputed_hash}.
  • Recovery: Not self-healing — hash mismatch → job abort with InvariantViolation::I1; user must fix compute fn.
  • Debug: Inspect closure for mutable external state, non-deterministic HashMap iteration (use BTreeMap for determinism), rand::thread_rng() calls; run ftdcr-core::testing::assert_deterministic(dataset, partition).

I2 — Immutable Committed Shuffle Block

Statement: A committed shuffle block for slot (ShuffleId, map_partition_id) is immutable; later attempt commits are no-ops.

  • Why it matters: Prevents double-write from retries and speculative duplicates; prerequisite for P5 and I4.
  • Enforced in: ftdcr-shuffle::MapOutputTracker::try_commit; CommitLog keyed by (ShuffleId, map_partition_id); returns CommitResult::AlreadyCommitted for duplicates.
  • Violation detection: Second try_commit for same slot must return AlreadyCommitted; caller discards block. Test: send two commit RPCs for same slot with different attempt IDs; assert only first accepted.
  • Telemetry: Counter commit.duplicate_rejected_total{shuffle_id}; TRACE log with discarded attempt_id.
  • Recovery: Silently drop duplicate; no error propagated to executor; slot committed to first attempt.
  • Debug: If duplicate_rejected_total unexpectedly high → check CommitLog persistence after coordinator restart; inspect log for interleaved attempt IDs indicating race in coordinator.

I3 — Stage Submission After Parent Map Outputs Registered

Statement: A Stage is submitted only after every parent ShuffleMapStage's outputs are fully registered in MapOutputTracker.

  • Why it matters: Prevents reduce tasks from launching with missing map output locations; eliminates preventable FetchFailed at stage start.
  • Enforced in: ftdcr-driver::DAGScheduler::maybe_submit_stage; calls MapOutputTracker::is_complete(shuffle_id) for all parent shuffles before transitioning stage from Pending to Runnable.
  • Violation detection: Integration test: fire StageSubmit before parent's ShuffleComplete event; assert stage remains in pending_stages. Metric: stage.premature_submit_blocked_total > 0 indicates correct blocking.
  • Telemetry: Counter stage.premature_submit_blocked_total; gauge stage.waiting_on_shuffle_ids (which shuffles are incomplete).
  • Recovery: DAGScheduler holds stage in pending_stages; moves to runnable only on ShuffleComplete(shuffle_id) event matching all parent deps.
  • Debug: If stage hangs in pending: MapOutputTracker::missing_entries(shuffle_id) shows which map partitions have not committed; trace which executors were assigned those map tasks.

I4 — Exactly-Once Job Result

Statement: Job result is independent of the number of task retries or speculative copies executed.

  • Why it matters: Exactly-once output guarantee (P5); user result must not vary based on fault pattern.
  • Enforced in: ftdcr-ft commit coordinator + CommitLog; TaskId uniqueness across retries; P2 (determinism) + P4 (idempotent commit) are the prerequisites.
  • Violation detection: Phase 14: run same job with 0 failures, then 1 executor killed per stage; compare sha256(output_bytes) across runs.
  • Telemetry: Gauge job.result_checksum at completion; counter job.result_checksum_divergence_total across repeated runs (should be 0).
  • Recovery: No automatic recovery — divergence requires root-cause analysis (P2 or P4 violation).
  • Debug: Replay with different fault-injection seeds; bisect to stage where checksum diverges; inspect CommitLog for double-accepted entries; check for non-deterministic compute fn.

I5 — Every Lost Partition Is Recoverable

Statement: Every in-memory partition lost with an executor is recoverable via lineage or checkpoint.

  • Why it matters: Guarantees P6 (transparent single-failure recovery); no partition is permanently unrecoverable.
  • Enforced in: ftdcr-lineage::LineageGraph::can_recover(partition_id); ftdcr-block::BlockManagerMaster::mark_executor_lost triggers recovery check for all that executor's partitions.
  • Violation detection: can_recover returns false for a lost partition → I5 violated; logged as CRITICAL.
  • Telemetry: Counter partition.unrecoverable_total; CRITICAL alert {dataset_id, partition_id, executor_id}.
  • Recovery: Job fails immediately with JobError::UnrecoverablePartition; error message identifies dataset, partition, and missing lineage link.
  • Debug: Audit Dataset construction: did any Dataset omit deps? Did compute fn read from external non-FTDCR source without a prior checkpoint? Run LineageGraph::validate_completeness() at job submission time.

I6 — MapOutputTracker Consistency

Statement: MapOutputTracker for each ShuffleId reflects exactly the committed map outputs — no phantom locations, no missing entries.

  • Why it matters: Reduce tasks query tracker for fetch URLs; stale phantom entries cause FetchFailed loops; missing entries cause premature FetchFailed at stage start.
  • Enforced in: ftdcr-shuffle::MapOutputTracker; on executor loss, BlockManagerMaster::on_executor_lost calls remove_executor_map_outputs(executor_id) atomically before DAGScheduler resubmits stage.
  • Violation detection: FetchFailed from a URL tracker returned → stale entry; reduce_fetched_count < num_map_tasks → missing entry. Metric: tracker.phantom_entries gauge should be 0.
  • Telemetry: Counter tracker.stale_entry_evicted_total; histogram fetch_failed_per_stage; gauge tracker.phantom_entries.
  • Recovery: On executor loss: purge all entries atomically, increment generation_id to invalidate executor-side caches, then trigger stage resubmit.
  • Debug: Snapshot tracker at stage submit; diff against fetch URLs that returned FetchFailed; identify the phantom source — typically remove_executor_map_outputs not called before resubmit.

I7 — Single Accepted Result Per Partition Slot

Statement: For output slot (stage_id, partition_id), at most one task attempt's result is accepted; all others are discarded.

  • Why it matters: Prevents double-counting from speculative copies or retries; prerequisite for I4 (exactly-once) and I10 (correct completion).
  • Enforced in: ftdcr-ft::CommitCoordinator::accept_result; CommitLog keyed by (stage_id, partition_id); second call with different attempt_id returns Rejected.
  • Violation detection: Two accept_result calls for same (stage_id, partition_id) with different attempt_id; second must return Rejected. Test: concurrent speculative tasks both commit; assert only one accepted.
  • Telemetry: Counter commit.conflict_rejected_total; WARN log {stage, partition, winning_attempt, rejected_attempt}.
  • Recovery: Second commit silently rejected; winning attempt's result stands; rejected executor discards its local block.
  • Debug: If conflict_rejected_total is 0 during Phase 10 (speculation active) → check speculation is actually launching; if both are accepted somehow → race condition in CommitCoordinator; add mutex around accept + log.

I8 — Lineage Truncated at Checkpoint Boundary

Statement: A checkpointed dataset's lineage is truncated; RecomputePlan never walks ancestors past a checkpoint node.

  • Why it matters: Bounds recovery cost to O(checkpoint_interval) not O(full job history); essential for P8 on iterative jobs.
  • Enforced in: ftdcr-ckpt::Checkpointer::checkpoint calls ftdcr-lineage::LineageGraph::truncate_at(dataset_id) on durable-write success; RecomputePlan::build checks node.is_checkpointed() and stops recursion.
  • Violation detection: RecomputePlan::build visits a checkpointed node and continues to its ancestors → I8 violated. Counter lineage.checkpoint_bypass_total must be 0.
  • Telemetry: Counter lineage.checkpoint_bypass_total (should be 0 always); assert in CI.
  • Recovery: Not self-healing: if bypass counter > 0, truncate_at was not called post-checkpoint; re-invoke if checkpoint data is confirmed durable.
  • Debug: Query LineageGraph::deps_of(dataset_id) for a checkpointed dataset; assert returns []; if not, confirm checkpoint() returned Ok and the truncate_at call path executed.

I9 — One Block Per Upstream Map Task Per Reduce Partition

Statement: A reduce task fetches exactly one committed block from each upstream map task for its reduce partition.

  • Why it matters: Any duplicated fetch produces duplicate records in reduce aggregation; reduceByKey sums are doubled; joins emit phantom rows.
  • Enforced in: ftdcr-shuffle reduce-side fetch loop; MapOutputTracker::get_locations(shuffle_id, reduce_partition) must return exactly one MapStatus per upstream map task.
  • Violation detection: Reduce task maintains dedup set HashSet<(map_task_id, reduce_partition)>; insertion collision indicates duplicate fetch. Counter shuffle.duplicate_fetch_total > 0 is violation.
  • Telemetry: Counter shuffle.duplicate_fetch_total; WARN log per violation; alert if rate > 0 in production.
  • Recovery: Drop second fetch result silently; log at WARN; alert for investigation.
  • Debug: Assert MapOutputTracker::get_locations returns exactly num_map_tasks elements; inspect for accidental re-insertion in tracker's try_commit path.

I10 — Job Completes Iff All Result Partitions Accepted

Statement: Job completes if and only if every ResultTask partition has exactly one accepted result.

  • Why it matters: Correct termination condition; premature completion → incomplete output; infinite hang → user impact without error signal.
  • Enforced in: ftdcr-driver::DAGScheduler::check_job_complete; result_partition_bitmap: BitVec of size num_result_partitions; JobComplete fired when all bits set and no in-flight ResultTask.
  • Violation detection: Bitmap fully set but JobComplete not fired → logic bug in check_job_complete. Bitmap not fully set but JobComplete fired → premature completion. Both caught by integration test asserting output_rows == expected.
  • Telemetry: Gauge job.pending_result_partitions; histogram job.completion_latency_ms; job.completion_timestamp.
  • Recovery: On hang: verify check_job_complete is called in every ResultTask commit path; trace result_partition_bitmap state; if a task is running and not completing, trigger speculation (P7).
  • Debug: Log result_partition_bitmap at each ResultTask commit; identify the last partition to set; if that task is stuck, inspect executor for straggler conditions (disk full, CPU contention, network partition).

I11 — Deterministic Re-Execution Across the Full Pipeline

Statement: A recomputed partition is bit-identical to the original given the same lineage and inputs.

  • Why it matters: I1 guarantees determinism of a single compute closure; I11 extends the same guarantee end-to-end through shuffle merge order, combiner application, and multi-hop lineage replay — the property P12's whole recompute-over-replicate trade-off depends on. If merge order is not fixed, two "correct" (per-closure) recomputations can still diverge in aggregate.
  • Enforced in: deterministic operators (ftdcr-core API contract, same as I1) plus a fixed shuffle merge/read order in ftdcr-shuffle::ShuffleReader (partitions merged in a canonical (map_id, reduce_id) order, never insertion/arrival order).
  • Violation detection: re-exec differential check — recompute a partition via a full lineage replay (not just a single closure call) and diff against the original committed bytes; run as part of the Phase 14 chaos suite across multi-stage DAGs, not just single-operator fixtures.
  • Telemetry: gauge partition.reexec_diff_mismatch; ERROR log {dataset_id, partition_id, lineage_depth, mismatch_offset}.
  • Recovery: not self-healing — mismatch means either a non-deterministic operator (I1) or non-canonical shuffle merge order; job aborts with InvariantViolation::I11 pending a fix.
  • Debug: bisect lineage depth to find the first ancestor whose recompute diverges; inspect ShuffleReader merge order for non-determinism (e.g., iterating a HashMap of in-flight fetches instead of a sorted Vec).

I12 — Checkpoint-Lineage Coverage

Statement: Every live partition is reachable from a durable checkpoint or replayable lineage; truncation never orphans a partition.

  • Why it matters: I8 stops RecomputePlan from walking past a checkpoint; I12 is the complementary coverage guarantee that the checkpoint (or an unbroken lineage chain) actually exists for every partition truncation claims to cover — without it, truncate_at can silently create a partition with no recovery path at all (worse than slow recovery: no recovery).
  • Enforced in: ftdcr-lineage::LineageGraph::truncate_at runs a reachability check before committing the truncation; ftdcr-ckpt::Checkpointer will not report a dataset checkpoint complete until every partition's durable write is confirmed.
  • Violation detection: a lineage-graph reachability audit (LineageGraph::audit_reachability()) walks every live DatasetNode and asserts a path exists to either a CheckpointedAt node or a raw input node; run in CI after every truncation-path test and periodically against long-running iterative jobs.
  • Telemetry: counter lineage.orphaned_partition_total (must be 0); CRITICAL alert {dataset_id, partition_id} on any orphan found.
  • Recovery: not self-healing — an orphaned partition is unrecoverable by construction; job aborts with JobError::UnrecoverablePartition, same terminal class as an I5 violation, but flagged distinctly (I12) so the root cause (bad truncation, not bad lineage recording) is diagnosed correctly.
  • Debug: re-run audit_reachability() against the pre-truncation graph snapshot (retained per §11.10 retention window) to find which partition's checkpoint write was reported complete but is actually missing or corrupted from the store.

StorageLevel decision matrix:

true false 1 MemoryOnly hot working set, recompute cheap

8.5 Scheduling Semantics

Locality preference hierarchy (Phase 4):

PROCESS_LOCAL > NODE_LOCAL > RACK_LOCAL > ANY

Delay scheduling: hold a task for up to locality_wait_ms (configurable) waiting for preferred executor; if no offer arrives, relax to next level. Never starves: ANY is always accepted.

Offer cycle (TaskScheduler, per heartbeat or slot-free event):

for each executor (sorted by locality match):
  for each pending TaskSet (FIFO or fair):
    assign tasks up to free_slots
    dequeue from TaskSet

Stage submission order (DAGScheduler): topological sort of the stage DAG; stage enqueued only when all parents in state Finished (I3 enforced here).

FetchFailed handling sequence:

Executor → StatusUpdate(FetchFailed, shuffle_id, map_id)
Driver → DAGScheduler.handleFetchFailed()
       → look up producing ShuffleMapStage
       → mark stage Waiting (re-run missing map tasks only)
       → abort downstream stages that read this shuffle
       → re-enqueue stage; dependent stages re-submit after new map outputs registered

8.6 Lineage and Recomputation Semantics

Lineage graph structure:

  • Dataset_D
    • ├── dep: Narrow → Dataset_C (parent[0])
    • └── dep: Shuffle(shuffle_id=3) → Dataset_B (parent[1])
      • └── dep: Narrow → Dataset_A

RecomputePlan construction (Phase 8):

lost := {PartitionId(D, p5)}
walk lineage of D backward:
  D.p5 depends on C.p5 (narrow, 1:1)
  C.p5 depends on A.p5 (narrow, pipelined)
  A.p5 → cached in BlockManager → stop here
plan := [recompute C.p5 from A.p5, recompute D.p5 from C.p5]

Invariant I1 enforced: every fn in compute closure must be pure (no mutable captured state, deterministic on same input iterator).

Checkpoint truncation (Phase 11):

before truncation:   A → B → C → D → E   (lineage chain)
checkpoint D.all_partitions to durable store
after truncation:    [checkpoint(D)] → E
recovery of E.p:     read checkpoint(D).p → compute E.p (no A/B/C needed) (I8)

8.7 Exactly-Once Commit Semantics (I4, I7, P4, P5)

Commit coordinator flow (ShuffleMapTask):

map task completes → write shuffle blocks to local BlockManager (temp files)
                   → send CommitRequest(task_id, attempt_id, shuffle_id, map_id)
                   → coordinator: if (shuffle_id, map_id) not yet committed:
                       accept; rename temp → final; register MapStatus (I6)
                   → coordinator: if already committed (retry/speculative):
                       reject; executor discards temp files

ResultTask output:

result task completes → send ResultCommit(task_id, attempt_id, partition_result)
                      → driver: if partition not yet accepted → accept (I7)
                      → driver: if already accepted → discard (idempotent)

Speculative execution coordination (Phase 10):

stage runtime distribution computed: p75, p95 per task
straggler := task_runtime > max(1.5 × median, p75) AND stage_fraction_done > 0.75
launch duplicate attempt on different executor
first CommitRequest accepted → winner
other attempt(s) → KillTask; CommitRequest rejected (I7)

8.8 Shuffle Protocol (Phase 7)

Map side:

ShuffleMapTask.run(partition_id):
  open records: Iterator<(K, V)>
  for each (k, v):
    r = partitioner.partition(k)          // hash or range
    write (k, v) to partition_buffer[r]
  sort each partition_buffer by key       // sort-based shuffle
  write data + index files to BlockManager disk
  register MapStatus(executor_id, partition_sizes[])

Reduce side fetch (ftdcr-shuffle):

ResultTask / ShuffleMapTask (with shuffle parent):
  query MapOutputTracker: for shuffle_id → [MapStatus(executor, sizes)]
  for each map_id m:
    fetch ShuffleBlock(shuffle_id, m, reduce_id) from executor_m
    retry up to fetch_max_retries on IOException
    on FetchFailed: report to driver → stage resubmit path
  merge/aggregate fetched blocks

MapOutputTracker protocol:

map task done → driver-side MapOutputTracker.registerMapOutput(shuffle_id, map_id, MapStatus)
reduce task start → MapOutputTrackerWorker.getServerStatuses(shuffle_id) → fetch from master
  cache result locally until shuffle_id invalidated (on resubmit)

8.9 Failure Paths — Worked Examples

8.9.1 Normal Path: 3-Stage Job Succeeds

Job: wordcount(lines) = flatMap → map → reduceByKey

Stage 0 (ShuffleMapStage): flatMap + map  [narrow pipeline, Phase 6]
  tasks T0.0..T0.P-1 launched → finish → MapStatus registered (I3)
Stage 1 (ResultStage): reduceByKey per reducer partition
  tasks T1.0..T1.R-1 launched → fetch shuffle blocks → aggregate → ResultCommit
Job result = union of R partition results (I10)

8.9.2 Failure Path: Executor Lost Mid-Shuffle

Stage 0 running: T0.0..T0.4 done, T0.5..T0.9 on E2
E2 heartbeat times out → E2 marked Lost
  → blocks on E2 evicted from BlockManagerMaster
  → T0.5..T0.9 (running on E2) → state Lost → resubmit on E0/E1/E3
  → Stage 0 re-runs T0.5..T0.9 → new MapStatus registered
Stage 1 tasks that fetched from E2 → FetchFailed → resubmit (some already committed: no-op via I7)
Stage 1 re-fetches T0.5..T0.9 outputs from new executors
Job completes; result identical (I1, I4) — user sees no error (P6)

8.9.3 Malformed Path: Non-Deterministic Task (violates I1)

compute fn captures mutable random seed → first run produces partition P
executor lost → recompute → different partition Q
reduce tasks fetching P already committed → job produces mixed P+Q output
INVARIANT I1 VIOLATED: result is incorrect
Detection: conformance fixture (Phase 14) checks wordcount result matches
  reference run; divergence flags non-determinism bug
Prevention: lint + doc requirement; no `thread_local` mutable state in closures

8.9.4 Edge Case: Cascade Lineage Recomputation

Dataset chain: A(checkpoint) → B → C → D → E (result)
E.p3 lost → recompute D.p3 from C.p3
C.p3 also lost → recompute C.p3 from B.p3
B.p3 also lost → recompute B.p3 from A.p3 (checkpoint; I8 stops here)
Total cost: 3 sequential tasks; bounded because A is checkpointed
Without checkpoint A: full re-read of input data
Phase 11 trigger: if lineage_depth > ckpt_threshold, force checkpoint

8.9.5 Edge Case: Speculative Duplicate Commits

T1.p7 running on E1 (slow); speculative copy T1.p7-attempt-2 on E3
E3 finishes first → CommitRequest(p7, attempt-2) accepted (I7 counter set)
E1 finishes later → CommitRequest(p7, attempt-1) rejected by coordinator
Driver: KillTask(E1, T1.p7-attempt-1)
BlockManager on E1: discards temp blocks for attempt-1
MapOutputTracker: only attempt-2 MapStatus retained (I6)

Resource Owner Lifetime Eviction Policy
RDD block (cached) BlockManager until evicted or executor lost LRU; spill to disk if MemAndDisk
Shuffle map output BlockManager until shuffle unregistered disk-backed; no mem eviction
Task execution buffer Executor task task duration spill sorted runs on overflow
Broadcast block BlockManager until unpersist called replicated; pulled on first use

6.2 Detailed Implementation Steps

Anchors: P2, I1, ADR-08. Narrow pipeline (ftdcr-executor/task_runner.rs): when dep is Dependency::Narrow, do not materialize — compose iterators.

Dataset.compute(partition_id, parent_iters) takes Vec<Box<dyn Iterator>> for narrow parents; iterator chain (filter wraps parent iter, map applies fn) allocates no intermediate Vec. struct MemoryBudget { limit: usize, used: AtomicUsize }  // limit = executor_memory * storage_fraction (default 0.6)
impl MemoryBudget { fn try_acquire(&self, bytes: usize) -> bool; fn release(&self, bytes: usize); }

Spill path in put(id, data, level): try_acquire(data.len()), and on failure call evict_until_fit(data.len()), which iterates LRU order — MemAndDisk blocks serialize to disk_dir/{block_id}.spill, release memory budget, update level[id] to disk-only; MemoryOnly blocks are dropped (lineage recompute needed if re-accessed, P1). MemoryOnly --evict--> [gone]

6.6 Pitfalls

  • Pin leak: task crashes after acquiring pin but before releasing, block permanently pinned; mitigation: RAII BlockPin guard, Drop releases pin count, panic-safe via catch_unwind wrapping the pin scope.

6.7 Performance Concerns

  • Iterator chaining overhead: concrete-typed chain/map/filter inline; Box<dyn Iterator> adds vtable dispatch per record — prefer a type-erased enum Iter for common 3–5 op chain depth.

  • AtomicUsize for budget: try_acquire/release use a compare_exchange loop, no mutex on the hot path; contention becomes measurable above 256 threads — use a per-core budget shard.
  • Disk file per block vs single spill file: per-block files are acceptable for Phase 6 (RDD spill only); Phase 7 shuffle uses a merged spill file + index to avoid millions of small files.
  • Evict scan cost: scanning the LRU list under lock is O(evicted); cap eviction batch at 64 blocks per call and retry the outer loop to avoid long lock hold.

  • Block size exceeds entire memory budget: try_acquire always fails and eviction cannot free enough — force to DiskOnly directly, skipping memory when data.len() > budget.limit.
  • Narrow pipeline with 0-record input: iterator immediately exhausted; put stores a zero-byte block; metrics record a 0-byte cache entry.
  • MemAndDisk block on disk when executor shuts down gracefully: spill files left on disk; startup scans blocks/ and re-registers existing spill files (partial crash recovery without recompute).

ShuffleWriter (ftdcr-shuffle/shuffle_writer.rs): ShuffleWriter { shuffle_id: ShuffleId, map_id: u32, partitioner: Partitioner, buffers: Vec<BytesMut>, spill_files: Vec<SpillFile>, spill_threshold: usize }. write(iter) iterates records, calls partitioner.partition(key) → reduce_id, appends serialized record to buffers[reduce_id], checks total_buffered >= spill_threshold after each append. Spill flushes all non-empty buffers to one SpillFile (<shuffle_dir>/map_<map_id>_spill_<n>.tmp), tracking partition_offsets: Vec<(reduce_id, offset, len)>. At task end, merge opens all SpillFiles plus remaining in-memory buffers, concatenates per-reduce_id segments in order into map_<map_id>.data, and writes map_<map_id>.index (Vec<(reduce_id, offset: u64, len: u64)> — u64 to prevent overflow, §7.6). Data file is fsync'd before the index is written; an incomplete index is detected by comparing index end-offset vs data-file size on open. Each BlockId::Shuffle(shuffle_id, map_id, reduce_id) registers into local BlockManager as StorageLevel::DiskOnly and reports to BlockManagerMaster; write returns Vec<ShuffleBlockSize { reduce_id, len_bytes }> used to build MapStatus. MapOutputTracker (ftdcr-shuffle/map_output_tracker.rs, driver-side): MapOutputTracker { map: DashMap<ShuffleId, Vec<Option<MapStatus>>> }. register_map_output(shuffle_id, map_id, statuses) is idempotent (no-op if already Some, per I2/I6); get_map_outputs(shuffle_id) returns Err(ShuffleNotReady) if any entry is None; unregister_map_output(shuffle_id, map_id) sets an entry to None (called by FaultHandler on executor loss or FetchFailed); unregister_all(shuffle_id) clears a whole map stage for resubmission; snapshot() gives a serializable snapshot for driver restart (Phase 12 gate). ShuffleReader (ftdcr-shuffle/shuffle_reader.rs): fetch(shuffle_id, reduce_id, tracker, block_client) queries tracker.get_map_outputs for (executor_id, block_size) per map, groups by executor, batches up to shuffle.max_blocks_per_fetch block ids per BlockFetchRequest, streams BlockFetchResponse bytes and deserializes (K,V) pairs inline. Retries on io::Error/BlockNotFound up to shuffle.fetch_max_retries with exponential backoff (shuffle.fetch_retry_backoff_ms * 2^attempt); after exhaustion raises FetchFailed { shuffle_id, map_id, reduce_id, executor_id }. If a combiner_fn is present, aggregates during iteration; else buffers and sorts by key for merge-sort join. BlockServer (ftdcr-executor/block_server.rs): tokio TCP listener accepting BlockFetchRequest { block_ids }; per block, looks up BlockManager for file path/offset/len and streams via tokio::fs::File/AsyncReadExt or platform sendfile (zero-copy) into a length-prefixed BlockFetchResponse { blocks: Vec<(BlockId, Bytes)> }; back-pressure via Semaphore(shuffle.max_server_concurrent_requests). ftdcr-rpc additions: Msg::ShuffleMapComplete { shuffle_id, map_id, statuses } (executor→driver); Msg::MapOutputQuery { shuffle_id } / Msg::MapOutputReply { statuses } (executor→driver query); Msg::BlockFetchRequest { request_id, block_ids } / Msg::BlockFetchResponse { request_id, blocks: Vec<(BlockId, Result<Bytes, BlockError>)> } (executor↔executor). Shuffle file wire layout:

map_<map_id>.data: [record_bytes...] per reduce_id in order 0..R-1, each record framed { len: u32, bytes: [u8; len] }
map_<map_id>.index (LE binary): magic u32=0xFEED_CAFE, version u16=1, num_partitions u32, entries[i]{offset:u64,len:u64} for i in 0..num_partitions, checksum u32 (CRC32 over entries)

Index is written after the data file is fsync'd; reader validates magic + checksum on open; record framing aligns with BlockFetchResponse framing for direct streaming. Combine-on-map-side (optional): if Dataset carries a Combiner { fn combine(acc: V, val: V) -> V }, apply per-partition within ShuffleWriter before spill to reduce shuffle bytes; must be associative/commutative (enforced by Dataset::reduce_by_key's builder); combiner result type must equal reducer input type, type-checked via PhantomData at DAG construction. 7.6 Pitfalls

  • Map output lost before reduce fetch: executor dies after registering MapStatus but before reduce fetch; manifests as FetchFailed/BlockNotFound; debug via fetch_failed_total spike + heartbeat timeout; ftdcr-ft resubmits the map stage (Phase 9, §9.2).
  • Spill merge misses in-memory residual: merge loop exits after SpillFiles but skips flushing remaining in-memory buffers; last N records silently dropped; debug by comparing shuffle_write_bytes_total vs spill-file sizes; fix: explicit final flush before the merge loop.
  • u32 overflow in index offsets for large partitions: shuffle block > 4 GB wraps a u32 offset silently, corrupting reads; fix: index always uses u64 offset/len, validated at write and read.
  • Fetch parallelism OOM on reducer: 1000 concurrent BlockFetchRequests buffer 1000 blocks at once, exceeding executor RSS; fix: Semaphore(shuffle.max_concurrent_fetches_per_executor) and pipeline fetch-deserialize-aggregate instead of buffer-all.
  • Stale MapOutputTracker after stage resubmission: previous attempt's outputs remain registered, reduce task fetches a deleted file; fix: unregister_all(shuffle_id) before resubmitting the map stage, gated on unregister completing. FetchFailed swallowed by reduce-side aggregator: a catch-all unwrap_or_default in a user combiner hides it, job appears to complete with silently missing data; fix: FetchFailed is a dedicated enum variant re-raised unconditionally in ShuffleReader::fetch, bypassing user catch-alls.
  • Index-data file desync on crash: crash between fsync(data) and write(index) leaves the index absent/zero-length; detected on open by checking index_end_offset == data_file_size — mismatch is treated as BlockNotFound → retry → FetchFailed → map stage resubmit.

7.7 Performance Concerns

  • Sort vs hash partition: hash partition is O(N) with no ordering guarantee; sort partition is O(N log N) but enables merge-side sort-merge-join — chosen per Partitioner variant at ShuffleWriter instantiation.
  • Per-record serialization overhead: batch-encode 256 records at once into BytesMut instead of calling serde per pair, amortizing framing overhead.
  • sendfile vs userspace copy: zero-copy sendfile saves one memcpy per block (Linux sendfile(2), macOS fcopyfile); default to sendfile with a userspace fallback.
  • MapOutputTracker fan-out: 1000 reduce tasks each querying the tracker for the same shuffle_id returns 1000× map_count entries; cache the serialized response per shuffle_id for 5s.
  • Spill merge I/O amplification: N spill files × P partitions naively costs N×P random seeks; arrange as a P-way interleaved merge-read to avoid it.
  • Fetch batching: single-block RPCs waste round trips; batch up to shuffle.max_blocks_per_fetch=200 per RPC, cutting RTT overhead ~200x at equal throughput.
  • Radix partition assignment: partitioning into R buckets (small domain) uses a radix-1 pass, O(N), avoiding comparison sort for Partitioner::Hash(n).

7.8 Edge Cases

  • Reduce partition count = 1 (degenerate shuffle): all records to one bucket, single block written, fetch and merge are trivial. Partition-count mismatch between map/reduce stages: detected at ShuffleReader::fetch when reduce_id > num_reduce_partitions, raising ShuffleSchemaMismatch.
  • Empty partition: MapStatus with len_bytes=0; BlockServer serves a 0-byte block; ShuffleReader returns an empty iterator without error.
  • Executor restart with same ExecutorId: old shuffle files from a previous epoch must be cleared on re-registration; files prefixed <job_id>/<epoch>/ to avoid collisions.
  • Shuffle block > 2 GB: index offsets are u64 not u32 (see §7.6). Partial network read: TCP delivers a partial block, detected by comparing received Bytes::len() vs the declared len, triggering a full retry.
  • Map task retried (speculative or failure): both attempts write shuffle files but only the committed attempt's MapStatus registers (I2); the other lands in an attempt-tagged path map_<map_id>_attempt_<n>.data.
  • Combiner on empty input: must return the neutral element, never panic. CRC mismatch on a received block: treated as transient BlockError::ChecksumMismatch, retried, and raises FetchFailed after fetch_max_retries.
  • Map output tracker entry exists but executor deregistered: ShuffleReader must detect the unreachable executor before batching fetch requests and fall back to FetchFailed immediately rather than waiting on a TCP timeout.

Phase 8 — Lineage + Recomputation

8.1 Objectives

  • Record the full lineage DAG for every Dataset: its Dependency list, compute function reference, Partitioner, and optional CheckpointRef.
  • On partition loss, build a RecomputePlan: walk lineage backward from lost partitions to nearest available ancestor (live cached block, checkpointed partition, or raw input dataset). Execute the plan recomputing only missing partitions.
  • Wide-dep recovery: losing a reduce partition may require re-running upstream map tasks; plan includes synthetic ShuffleMapStage nodes as needed.
  • Invariants: I1 (recomputed partition bit-identical to original), I5 (every in-memory partition recoverable), I8 (checkpoint truncates lineage walk).
  • Integration: ftdcr-lineage consumed by ftdcr-ft (Phase 9) for recovery; by ftdcr-ckpt (Phase 11) for lineage truncation.

8.2 Detailed Implementation Steps

Anchors: I1, I5, I8, P12. LineageGraph (ftdcr-lineage/lineage_graph.rs): LineageGraph { nodes: HashMap<DatasetId, DatasetNode> }, DatasetNode { deps: Vec<Dependency>, num_partitions: u32, compute: ComputeFnRef, checkpoint: Option<CheckpointRef>, partition_available: BitVec }. add_dataset(dataset) recursively inserts the node plus not-yet-present ancestors (called at DAG construction and at persist/checkpoint). ancestors(dataset_id, partition_id) DFS-follows Dependency edges — narrow maps one partition, wide (Shuffle) maps all upstream partitions for the reduce partition. truncate_at_checkpoint(dataset_id) (called by ftdcr-ckpt post-write) sets checkpoint = Some(ref) and removes ancestor nodes no longer reachable without passing the checkpoint (I8). BlockIndex integration (lives in ftdcr-block): BlockIndex { entries: DashMap<(DatasetId, PartitionId), BlockLocation> }, BlockLocation = Memory(ExecutorId) | Disk(ExecutorId, path) | Checkpoint(CheckpointRef) | RawInput. LineageGraph calls block_index.available(d, p) during plan-build; available checks entry exists and executor is live; insert runs on persist_complete/recovery completion; remove runs atomically with BlockManager::evict to prevent stale availability. RecomputePlan builder (ftdcr-lineage/recompute.rs): build_recompute_plan(lost, graph, block_index) is an O(V+E) BFS — seed worklist with lost partitions and a visited set; pop (d,p), and if available or checkpointed mark as a base and stop the walk; if deps.is_empty() it's an unrecoverable raw input (Err(UnrecoverablePartitionLoss)); else add (d,p) to the recompute set and push unvisited ancestors(d,p); after BFS, topologically sort the recompute set and emit Vec<RecomputeStage>. RecomputePlan { stages: Vec<RecomputeStage>, base_inputs: Vec<(DatasetId, PartitionId, BlockLocation)> }; RecomputeStage { dataset_id: DatasetId, partitions: SmallVec<[PartitionId; 32]>, kind: StageKind } (StageKind = ShuffleMap | Result | Narrow). Plan execution (ftdcr-driver/dag_scheduler.rs, recover path): recover(plan) walks RecomputeStages in topological order, reusing a Pending Stage or synthesizing one, and submits via TaskScheduler; on stage completion, BlockIndex::inserts each recovered partition and unblocks/submits downstream stages. Concurrent RecomputePlans (from different lost executors) run concurrently through the DAGScheduler event loop, deduplicated by checking block_index.available before submitting any stage; each synthesized Stage is tagged { recovery: true, original_stage_id } so metrics distinguish recovery tasks. check_recompute_completeness(plan) asserts all lost partitions are available before unblocking downstream stages. LineageGraph serialization: serializable for debug export (ComputeFnRef serialized as an opaque DatasetId+PartitionId pair, not a function pointer); to_dot(job_id) emits Graphviz DOT with nodes labeled DatasetId+num_partitions, edges labeled by Dependency kind, checkpoint nodes highlighted. 8.6 Pitfalls

  • Wide-dep lineage explosion: losing one reduce partition of a 1000-partition shuffle triggers re-running all 1000 map tasks; mitigation: check MapOutputTracker and include only the map tasks for actually-lost outputs; signal: recompute_stages_submitted >> 1.
  • Non-deterministic compute function: user function reads wall clock, iterates a HashMap randomly, or calls an external service, silently violating I1; detect via optional determinism checker re-running a sample partition (task.determinism_check_sample_rate=0.01).
  • Stale BlockIndex after eviction: block evicted from BlockManager but BlockIndex not atomically updated, so the plan treats it as an available base and recovery skips it; fix: BlockManager::evict removes from BlockIndex inside the same lock scope.
  • Infinite recompute loop: a parent partition is also lost, triggering another recover call; mitigation: build_recompute_plan walks past all contiguously lost ancestors to the first available/raw input in one pass — no recursive recover calls.
  • Checkpointed dataset absent from BlockIndex on driver restart: checkpoint exists on durable store but BlockIndex isn't seeded, so the plan walks past it; fix: on job start, scan the checkpoint store and BlockIndex::insert each checkpointed (dataset_id, partition_id).
  • Concurrent recovery for same partition: two executors lose different ancestors of the same leaf, and two concurrent build_recompute_plan calls both decide to recompute it; mitigation: DAGScheduler::recover checks block_index.available before submitting each RecomputeStage, so the second recovery skips already-submitted stages.

8.7 Performance Concerns

  • BFS cost on large DAG: a 500-stage iterative job with 10k partitions/stage could visit 5M nodes; mitigated by early-exit on first available ancestor, I8 checkpoint truncation bounding depth, and a visited set preventing re-traversal.
  • RecomputePlan size in memory: large recoveries can hold thousands of (DatasetId, PartitionId) entries — use SmallVec<[PartitionId; 32]> per stage and BitVec for partition membership.
  • Topological sort on recompute set: standard Kahn's algorithm, O(V+E) over the recompute subset only, not the full DAG.
  • BlockIndex contention: high-frequency inserts from concurrent task completions use a 64-shard DashMap; avoid holding a shard lock across recover calls.
  • Recomputation cascade latency: each recompute stage adds a scheduling round-trip; minimize by submitting all independent stages in parallel (P6 — transparent recovery).
  • Plan build blocks DAGScheduler event loop: run build_recompute_plan in tokio::task::spawn_blocking so the event loop stays unblocked while BFS runs.

8.8 Edge Cases

  • All partitions of a dataset lost simultaneously: plan covers full dataset recompute from raw input — valid but expensive; surfaced as WARN with a recovery ETA estimate.
  • Root partition lost (no deps): build_recompute_plan returns Err(UnrecoverablePartitionLoss); DAGScheduler::fail_job emits a structured diagnostic.
  • Checkpoint written by a previous job attempt with a different schema: the version tag on CheckpointRef must match the current DAG's schema hash; mismatch → ignore checkpoint, walk further back.
  • Partition loss discovered during recompute of another partition: recover is called re-entrantly; BlockIndex state stays consistent, and the plan builder treats newly-submitted-but-incomplete stages as "in-flight, not available" in the new plan.
  • Narrow dep with many-to-one fan-in (e.g. cogroup): one output partition depends on multiple input partitions from different parents; the plan must enumerate all required input partitions per parent.
  • Wide dep spanning multiple levels: a chain of two reduceByKey ops — losing a final reduce partition may require re-running two shuffle map stages in topological order.

Phase 9 — Failure Detection + Retry

9.1 Objectives

  • Detect executor failure via heartbeat timeout; transition executor to Lost; invalidate its in-memory blocks in BlockManagerMaster; unregister its map outputs from MapOutputTracker; resubmit all running tasks.
  • Handle FetchFailed from reduce tasks: identify the responsible ShuffleMapStage; unregister stale MapStatus; resubmit only the affected map partitions; requeue the failed reduce task.
  • Track retry attempts per (StageId, PartitionId); after ft.max_task_attempts, fail the job with structured MaxAttemptsExceeded error.
  • Invariants enforced: I4 (exactly-once result), I5 (lost partitions recoverable), I6 (MapOutputTracker reflects only committed outputs), I7 (at most one attempt's result accepted per partition).
  • Constraints: speculative execution stubbed here (full impl Phase 10); driver HA / persisted RetryTracker gated to Phase 12.

9.2 Detailed Implementation Steps

Anchors: I4, I5, I6, I7, P9. HeartbeatMonitor (ftdcr-ft/heartbeat_monitor.rs): HeartbeatMonitor { last_seen: DashMap<ExecutorId, (Instant, RegistrationEpoch)> }; record_heartbeat(executor_id, epoch, timestamp) updates the entry and ignores stale epochs; a tokio background task polls every ft.heartbeat_check_interval_ms, calling check_timeouts() to return (ExecutorId, RegistrationEpoch) pairs where now - last_seen > ft.heartbeat_timeout_ms, emitting ExecutorEvent::Lost to the FaultHandler channel. FaultHandler::on_executor_lost (fault_handler.rs): BlockManagerMaster::invalidate_executor removes all BlockId locations for that executor and marks affected partitions unavailable; MapOutputTracker::unregister_executor nulls all MapStatus entries written by it; TaskScheduler::resubmit_tasks_on_executor re-queues its Running TaskAttempts and increments RetryTracker; DAGScheduler::check_stages_for_resubmit re-evaluates and resubmits stages now missing map outputs; logs WARN with executor id, epoch, last-seen delta, tasks resubmitted, blocks invalidated. FetchFailed handler (in DAGScheduler): if the reduce partition is already block_index.available (I7), skip; else unregister_map_output(shuffle_id, map_id), mark the shuffle-map stage Pending, RetryTracker::increment, resubmit the ShuffleMapTask, and re-queue the failed reduce task (stage stays Pending until all map outputs re-register). Deduplicated via pending_resubmit: HashSet<(ShuffleId, MapId)> — idempotent per (shuffle_id, map_id); MaxAttemptsExceeded on a map partition fails the whole job without resubmit. FetchFailed may race ahead of ExecutorLost; both paths call unregister_map_output, which is idempotent. RetryTracker (ftdcr-driver/retry_tracker.rs): RetryTracker { attempts: HashMap<(StageId, PartitionId), Vec<TaskAttemptRecord>> }, TaskAttemptRecord { attempt: u32, executor_id: ExecutorId, cause: TaskFailureCause, timestamp: Instant }; increment(stage, partition, cause) appends a record and returns Err(MaxAttemptsExceeded { stage_id, partition_id, history }) at ft.max_task_attempts, driving DAGScheduler::fail_job. ftdcr-rpc heartbeat path (activating the Phase 2 stub): Msg::Heartbeat { executor_id, epoch, timestamp_ms, running_tasks, mem_used_bytes, disk_used_bytes } sent every ft.heartbeat_interval_ms — driver reconciles running_tasks against TaskScheduler state, logging TaskMissingFromHeartbeat (non-fatal) on mismatch. Msg::TaskFailed { task_id, attempt, cause: TaskFailureCause } where TaskFailureCause = FetchFailed(..) | ExecutionError(String) | OomKilled | Timeout | Cancelled. Msg::CancelTask { task_id, reason } requires a Msg::TaskCancelAck within ft.task_cancel_ack_timeout_ms. Msg::ExecutorBlacklisted { executor_id, reason } is a Phase 12 stub broadcast here. Executor state machine:

Registered → Alive → Lost → Deregistered (reconnect with new epoch loops back to Registered)

Transitions: Registered on Msg::RegisterExecutor; Alive on first heartbeat; Lost on timeout; Deregistered on explicit message or after ft.executor_lost_cleanup_delay_ms. Task timeout enforcement: TaskScheduler tracks task_start: HashMap<TaskId, Instant>; a background task checks every ft.task_timeout_check_interval_ms and sends Msg::CancelTask for tasks running past ft.task_timeout_ms; on ack, mark Cancelled, increment RetryTracker, requeue; on ack timeout, declare the executor Suspect, escalating to Lost if no heartbeat arrives within ft.heartbeat_timeout_ms. Instrumentation: counters executor_lost_total, task_retry_total, fetch_failed_total, stage_resubmit_total, job_failed_max_attempts_total, task_timeout_total, task_cancel_ack_timeout_total; histograms executor_loss_recovery_latency_ms, fetch_failed_to_stage_resubmit_latency_ms, task_retry_latency_ms; gauges executors_live, executors_suspect, tasks_running, tasks_pending_retry, stages_pending_resubmit.

9.6 Pitfalls

  • GC pause mis-classified as executor failure: a GC or blocking-task pause delays heartbeat past heartbeat_timeout_ms, causing false ExecutorLost and duplicated work; mitigation: ft.heartbeat_timeout_ms >= 30s, heartbeat carries running-task list for reconciliation, monitor executor_lost_total for false-positive rate.
  • Task result arrives after executor declared lost: result message lands after on_executor_lost runs, risking BlockManagerMaster inconsistency; fix: TaskScheduler::accept_result checks (executor_id, epoch) against the live registry and rejects results from evicted epochs.
  • FetchFailed on partition already committed by speculative copy: driver would resubmit the map stage unnecessarily; fix: handle_fetch_failed checks block_index.available for the reduce partition first and skips if true (I7).
  • Cascading resubmissions from concurrent FetchFaileds: 1000 reduce tasks failing simultaneously for the same map stage risk lock contention from redundant calls; fix: pending_resubmit: HashSet<(ShuffleId, MapId)> dedups all 1000 calls to one resubmit.
  • MaxAttemptsExceeded with misleading last error: transient network errors and OOM get equal weight, obscuring true cause; fix: store the full Vec<TaskAttemptRecord> with TaskFailureCause per attempt and surface all causes. Executor re-registration with same ExecutorId resurfaces old epoch events: fix: record_heartbeat updates epoch, check_timeouts keys events by (ExecutorId, RegistrationEpoch), stale-epoch events discarded by FaultHandler.
  • RetryTracker state lost on driver restart: attempt counters reset, tasks may re-run past the intended budget invisibly; known gap, gated to Phase 12 for durable persistence; documented in the operator runbook.

9.7 Performance Concerns

  • Heartbeat check loop at scale: O(N) per interval is 10k lookups/s at N=10 000 executors and a 1s interval — use a sorted expiry min-heap keyed by (last_seen + timeout) for O(log N) per check.
  • Bulk task resubmission on executor loss: 1000 tasks on one executor must not hold the TaskScheduler lock for the full loop — batch-enqueue via a bounded channel, releasing the lock between batches.
  • DashMap contention on invalidate_executor: bulk delete across shards; amortize by collecting keys in parallel then deleting.
  • FetchFailed stampede under shuffle failure: DAGScheduler's event loop serializes 1000 concurrent handlers, each O(1) after pending_resubmit dedup, for total O(N).
  • Recovery latency dominates job tail (P6): lost-to-resumed time = heartbeat_timeout + check_interval + schedule_latency + task_runtime; minimize by lowering heartbeat_timeout_ms (bounded below by max GC pause + network jitter).

9.8 Edge Cases

  • Executor lost with no tasks assigned: no resubmission needed, but BlockManagerMaster eviction and MapOutputTracker unregister still run unconditionally. FetchFailed for a map task already retried and re-registered: unregister_map_output must check the attempt tag so it removes only the failed attempt's entries, not the new valid one.
  • Task timeout (not heartbeat): task exceeds ft.task_timeout_ms, driver sends CancelTask, executor acks, task re-queued with TaskFailureCause::Timeout and counted against max_task_attempts.
  • MaxAttemptsExceeded on different failure causes across the 4 attempts: structured error surfaces each distinctly so operators can separate infra failure from a logic bug. Two FetchFailed events for the same stage on different driver threads: the event-loop mutex serializes them, and the second sees pending_resubmit.contains and no-ops.
  • Driver restart mid-recovery (Phase 12 gate): recovery state is lost and in-flight tasks must be re-detected; Phase 9 logs WARN: "RetryTracker not persisted; attempt counts reset".
  • Executor Suspect state (cancel-ack timeout but heartbeat still arriving): not yet Lost; tasks are cancelled but the executor isn't evicted, and TaskScheduler::dispatch skips it for new tasks.
  • FetchFailed arrives before TaskFailed for the same task: both call RetryTracker::increment, but only one should count — dedup key is (stage_id, partition_id, attempt).
  • Stage fully succeeded but one result task reports FetchFailed for a reduce partition it already locally cached: the block_index.available check in handle_fetch_failed catches this and skips resubmit.
  • Multiple stages fan into one executor's shuffle outputs; on loss, on_executor_lost must iterate all MapOutputTracker entries for that executor (not just the most recent shuffle) to resubmit every affected shuffle-map stage.

Phase 10 — Speculative Execution

10.1 Objectives

  • Track per-stage task runtime distribution; identify stragglers exceeding a configurable percentile threshold.
  • Launch duplicate speculative task attempts for laggard partitions; first attempt to commit wins.
  • Enforce I7: exactly one result accepted per output partition; duplicates discarded via commit coordinator.
  • Enforce P7: speculative execution bounds tail latency without violating P5 (exactly-once) or I4.
  • Scope: ftdcr-ft (straggler detection + launch trigger), ftdcr-driver (TaskScheduler, commit coordinator), ftdcr-executor (task kill on result superseded).

10.2 Detailed Implementation Steps

Anchors: I7, P7, P5. Straggler Detection (ftdcr-ft::speculative):

Component Details
StageDurationTracker rolling window per StageId; records (TaskId, elapsed_ms) on each heartbeat; computes median + p75 of finished task durations

Speculative Launch (ftdcr-driver::task_scheduler): SpeculativeSet: HashSet<(StageId, PartitionId)> tracks partitions with an outstanding speculative attempt to prevent redundant launches. On straggler identified: create TaskAttempt { attempt: original+1, speculative: true } with the same partition + locality prefs, insert into the free-slot offer queue, record in SpeculativeSet. Both original and speculative attempts run simultaneously and both report status to the driver. Commit Coordinator (ftdcr-driver::commit_coord): state per (StageId, PartitionId):

Pending -> (first CommitRequest accepted) -> Committed(attempt_id)
Committed -> (subsequent CommitRequests) -> Rejected(already_committed)

CommitCoordinator: HashMap<(StageId, PartitionId), CommittedAttempt> is write-once, guarded by a driver-side mutex.

  • CommitRequest { task_id, stage, partition, attempt } is sent by the executor before writing a result to BlockManager; the driver replies Accept or Reject, and the executor discards its result on Reject without writing.
  • On Accept: executor writes the block, sends StatusUpdate::Finished; TaskScheduler marks the partition done and kills competing attempts via KillTask RPC. Kill Path (ftdcr-rpc + ftdcr-executor): RpcMessage::KillTask(task_id) is sent to the executor hosting the losing attempt; the task runner checks a CancellationToken on each iterator yield, exits early, and emits StatusUpdate::Killed. Phase 11 — Checkpointing + Lineage Truncation

11.1 Objectives

  • Persist selected Dataset partitions to a durable store (local FS in tests; pluggable store interface for object storage).
  • After successful checkpoint, truncate the dataset's lineage so recovery reads the checkpoint rather than recomputing ancestors (I8, P8).
  • Bound recovery recomputation cost on iterative jobs (pagerank, k-means) where lineage grows unboundedly across iterations.
  • Scope: ftdcr-ckpt (checkpoint writer/reader, lineage truncation), ftdcr-lineage (truncation API), ftdcr-driver (DAGScheduler triggers checkpoint), ftdcr-executor (BlockManager provides partition bytes).

11.2 Detailed Implementation Steps

Anchors: I8, P8, P12. Checkpoint Store Interface (ftdcr-ckpt::store):

trait CheckpointStore: Send + Sync { fn write_partition(&self, id: CheckpointKey, data: Bytes) -> Result<()>; fn read_partition(&self, id: CheckpointKey) -> Result<Bytes>; fn exists(&self, id: CheckpointKey) -> bool; fn delete(&self, id: CheckpointKey) -> Result<()>; }
// CheckpointKey = (DatasetId, PartitionId)

LocalFsCheckpointStore writes to configurable checkpoint_dir via atomic rename (write .tmp, rename to final). Checkpoint { dataset_id, partition_id, store_path, byte_len, checksum: u64 } metadata persists in a driver-side CheckpointRegistry. Checkpoint Trigger (ftdcr-driver::dag_scheduler):

Trigger mechanism Details
Explicit: dataset.checkpoint() API call user marks a dataset for checkpointing; DAGScheduler schedules a checkpoint pass after the producing stage completes
Automatic: lineage depth threshold lineage_depth_checkpoint_threshold: usize (default 10); DAGScheduler measures depth from root; triggers automatically on iterative jobs
Post-action checkpoint after a job action completes, any dataset marked checkpoint_pending triggers a checkpoint job before the next job starts

Checkpoint Job (ftdcr-driver): once dataset.checkpoint_pending = true after its producing stage finishes, DAGScheduler submits a synthetic CheckpointJob — a ResultStage where each CheckpointTask serializes one partition and calls CheckpointStore::write_partition; once all tasks finish, the driver calls ftdcr-lineage::truncate(dataset_id) and updates CheckpointRegistry to CheckpointState::Complete, so future recovery starts at the checkpoint rather than the lineage root. Lineage Truncation (ftdcr-lineage::truncate): replaces the dataset's Dependency list with Dependency::Checkpoint(key) and drops ancestor edges reachable only through this dataset (invariant I8 — recovery resolves to a checkpoint read, not ancestor compute). LineageGraph stores HashMap<DatasetId, DatasetNode> with deps replaced in-place; truncation is logged to the driver event log and visible in the job UI; GC of orphaned ancestor nodes is deferred until no running job references them. Checksum Validation: write computes xxhash64 over serialized partition bytes and stores it in Checkpoint.checksum; read recomputes the hash and fails the task with CheckpointCorrupted on mismatch, triggering lineage recomputation from the nearest non-corrupted ancestor. 11.7 Performance Concerns

  • Checkpoint write is I/O-bound; use async write (tokio::fs or object-store crate), never blocking the executor task thread.

  • Durable store throughput: shard writes across multiple store paths/prefixes to avoid a single-shard bottleneck.

11.8 Edge Cases

  • Checkpoint of a dataset with zero partitions: no-op; CheckpointState::Complete with an empty partition set, truncation proceeds.

  • Executor holding a partition fails mid-checkpoint write: CheckpointTask::Failed, retried from another executor that can recompute the partition.
  • Checkpoint of a broadcast variable: a separate BroadcastCheckpoint path, not a standard partition, handled by ftdcr-block not ftdcr-ckpt.
  • Lineage truncation while a job is reading that dataset's lineage: LineageGraph uses RwLock; truncation acquires the write lock only after all readers release.
  • Job submitted before checkpoint completes: DAGScheduler defers stage submission until CheckpointState::Complete for all pending partitions.

Phase 12 — Driver-Side Recovery

12.1 Objectives

  • Executor blacklisting: after repeated per-executor failures, remove executor from scheduling pool to prevent job degradation.
  • Lost-executor reconciliation: update BlockManagerMaster and MapOutputTracker to remove entries from a lost executor; trigger recomputation via Phase 9 / Phase 8 lineage machinery.
  • Job-level retry: on job failure (all retry attempts exhausted), support configurable job resubmission from scratch.
  • Driver HA (checkpointed driver state, multi-driver failover) is gated / PhaseDeferred: noted here as design boundary, not implemented in this phase.
  • Scope: ftdcr-ft (blacklisting, reconciliation), ftdcr-driver (DAGScheduler + TaskScheduler reconcile on executor loss), ftdcr-block (BlockManagerMaster cleanup), ftdcr-shuffle (MapOutputTracker cleanup).

Lost-Executor Reconciliation (ftdcr-driver::dag_scheduler + ftdcr-ft): triggered by heartbeat timeout (Phase 9) or explicit DeregisterExecutor RPC. Atomic from the driver's perspective: mark ExecutorState → Lost and remove from the live-executor map; BlockManagerMaster::remove_executor purges all BlockId → executor mappings and marks affected blocks unavailable; MapOutputTracker::remove_executor marks MapStatus entries written by that executor as Lost, returning the affected (ShuffleId, map_partition) set; DAGScheduler::handle_executor_loss then resubmits every running task on that executor as a new TaskAttempt (Phase 9 logic), finds and partially resubmits any completed ShuffleMapStage whose lost partitions were affected, and leaves dependent ResultStage/ShuffleMapStages blocked until resubmit completes; finally the lost executor's blacklist counter increments and an ExecutorLostEvent is emitted to the event log. Partial Stage Resubmission: DAGScheduler::resubmit_partitions(stage_id, partitions) resubmits only a subset of a completed stage's tasks — a new TaskSet with just the lost partitions, reusing the existing StageId with an incremented attempt counter; on completion, MapOutputTracker entries for those partitions update and dependent stages unblock. Job-Level Retry (ftdcr-driver::job_manager): JobRetryPolicy { max_retries: usize (default 1), retry_from_checkpoint: bool }. JobManager tracks retry_count per JobId; on JobFailed with retry_count < max_retries, it re-submits the logical DAG as a new job (same dataset graph, new JobId), reusing lineage/checkpoints from the failed job when retry_from_checkpoint = true; on final failure it sets JobState::Failed with an aggregated error report. Driver HA (PhaseDeferred): design boundary only — driver state (CheckpointRegistry, MapOutputTracker, BlacklistRegistry, DAGScheduler stage graph) must become serializable to durable store for a standby driver to replay; not implemented here, tracked as TODO(driver-ha) in the ftdcr-driver::ha stub module; prerequisite is the Phase 11 checkpoint store + CheckpointRegistry persistence. 12.7 Performance Concerns

  • BlockManagerMaster::remove_executor is O(blocks_on_executor), amortized over executor lifetime; log if it exceeds 50ms.
  • MapOutputTracker::remove_executor is O(shuffle_partitions_on_executor), typically O(1000s) entries; use a HashMap with an executor index for an O(n) sweep without a full scan.
  • Reconciliation on the hot driver path: batch updates in a ReconciliationBatch to avoid per-partition lock cycles.
  • Blacklist check in offer_task: O(blacklisted_executors) per offer; use a HashSet for O(1) lookup.
  • Partial resubmit task creation only allocates TaskAttempts for lost partitions, avoiding a full TaskSet rebuild.

12.8 Edge Cases

  • Executor lost before it registered any blocks: remove_executor is a no-op, no resubmits needed, logged as [LOSS] executor E lost with zero blocks.
  • Executor lost while driver is processing a different executor's loss: re-entrant handle_executor_loss calls are serialized via a queue of loss events.
  • Job with zero running tasks at time of executor loss: no running tasks to resubmit, only committed map-output loss is checked.
  • Blacklist entry for an executor that was never registered: ignored, no phantom entry created.
  • retry_from_checkpoint = true but no checkpoint exists: falls back to full recompute from input with a warning logged.
  • Executor re-registers with same ExecutorId after loss (restart): treated as a new executor, failure count reset (new process); blacklist history retained for the same executor_addr if paranoid mode is enabled.

Phase 13 — Memory mgmt + backpressure + observability

13.1 Objectives

  • Implement unified memory manager splitting JVM-style heap into execution (shuffle/sort buffers) and storage (cached RDD blocks) pools with dynamic borrowing.
  • Enforce spill thresholds: when execution pool exceeds ceiling, spill in-progress aggregation/sort to disk; when storage pool is under pressure, evict LRU cached blocks.
  • Add backpressure on shuffle fetch: rate-limit reduce-side fetches to bound memory use from concurrent map-output streams.
  • Instrument every stage and task with metrics: runtime, shuffle read/write bytes, spill bytes, block cache hits/misses, task deserialization overhead.
  • Emit structured event log (JSON lines) consumed by a job-UI reader; expose Prometheus-compatible /metrics endpoint on the driver.

13.2 Detailed Implementation Steps

Anchors: P13, ADR-12. MemoryManager (ftdcr-block):

Component Responsibility
MemoryManager tracks execution_used, storage_used, pool ceilings; arbitrates grants
MemoryGrant RAII guard returned to caller; drop releases bytes back to pool
StorageMemoryPool LRU eviction queue; calls BlockManager::evict on pressure
ExecutionMemoryPool per-task grant; spill callback when ceiling hit
SpillManager serializes in-progress map/aggregation buffer to temp file under work_dir

Dynamic borrow: if execution is full but storage has free bytes (or vice versa), borrow up to a configured fraction. SpillManager::spill_buffer(task_id, buf) writes a sorted spill file and returns a SpillHandle merged later during shuffle write. Eviction is LRU among StorageLevel::MemoryOnly blocks; MemAndDisk blocks are demoted to disk, not dropped. MemoryManager::try_acquire_execution(bytes) -> Result<MemoryGrant, SpillRequired> is non-blocking — the caller must spill if SpillRequired. Backpressure (ftdcr-shuffle): ShuffleFetchScheduler is a token-bucket per reduce task bounding max_bytes_in_flight outstanding across all map fetches; its VecDeque<FetchRequest> drains only when the bucket has capacity, preferring same-node outputs (FetchRequest::priority) before degrading to remote; on FetchFailed, tokens release, the retry counter increments, and the request re-enqueues. Metrics + event log (ftdcr-driver): TaskMetrics { run_time_ms, shuffle_read_bytes, shuffle_write_bytes, spill_disk_bytes, deserialization_ms, gc_time_ms } aggregates per-stage into StageMetrics from incoming TaskResult envelopes. EventLogger appends JSON-lines events (JobStart, JobEnd, StageSubmitted, StageCompleted, TaskStart, TaskEnd(metrics), ExecutorAdded, ExecutorLost). MetricsExporter serves GET /metrics rendering ftdcr_stage_*/ftdcr_task_*/ftdcr_executor_* in Prometheus text format; SpillCounter is a per-executor counter reported via the heartbeat envelope and aggregated into ExecutorMetrics.

  • MemoryManager enforces pool split; tasks spill when execution ceiling reached rather than OOM.
  • StorageMemoryPool evicts LRU blocks to disk under cache pressure; BlockManager::get reads from disk transparently.
  • Shuffle fetches are token-bucket rate-limited; max_bytes_in_flight respected.
  • Driver emits event log file readable by a companion ftdcr-ui reader (JSON parse only).
  • GET /metrics returns Prometheus text with stage/task counters.

13.7 Performance Concerns

  • MemoryManager lock is on the hot path for every task allocation; use parking_lot::Mutex and minimize the critical section (no I/O inside the lock).
  • StorageMemoryPool LRU queue uses IndexMap (insertion-ordered) for O(1) evict-front, avoiding a full scan.
  • SpillManager serialization uses bincode with a pre-allocated write buffer to avoid per-record allocation.
  • Backpressure token bucket is an AtomicUsize CAS loop (no mutex); watch for false-sharing if placed on the same cache line as the fetch-queue head.
  • TaskMetrics collection is zero-copy, passed by value in the TaskResult envelope; driver accumulates with saturating add.
  • Event log writes are batched via BufWriter, flushed on StageCompleted boundaries, not per-task.
  • Prometheus text render pre-formats metric names at startup and formats only values at scrape time.

13.8 Edge Cases

  • Task cancelled mid-spill: partial spill file exists and must be deleted on the cleanup path.
  • max_bytes_in_flight set to 0 (misconfiguration): fetch loop never starts; detected at startup, enforcing a minimum of one block per fetch.
  • Storage pool at exactly 0 bytes available when execution tries to borrow: borrow returns 0, never negative.
  • Two tasks simultaneously hit the ceiling and both try to evict the same block: eviction is idempotent via a BlockId-keyed map, second eviction is a no-op.
  • Event log reader connects mid-job: must handle partial lines at the tail using newline-terminated JSON records.
  • Prometheus scrape while a stage transitions: metrics snapshot atomically so a partial scrape never shows negative deltas.
  • gc_time_ms on Rust: no GC, field is always 0 but retained for schema compatibility with Spark event log consumers.

Tracing Strategy

  • Propagate JobId, StageId, TaskId, TaskAttempt as OpenTelemetry trace context across RPC calls.
  • Root span: job.submit -> child spans: stage.submit, task.launch, task.execute, shuffle.write, shuffle.fetch, checkpoint.write.
  • Attach locality_level, executor_id, partition_id as span attributes.
  • Sample at 100% for failed tasks; 1% for successful tasks (configurable trace_sample_rate).
  • Store traces in compatible backend (Jaeger / Tempo); retention 7 days minimum.
  • FetchFailed and TaskFailed events always emit a full trace regardless of sample rate.

Structured Logging

  • JSON log lines; mandatory fields: timestamp_ns, level, job_id, stage_id, task_id, attempt, executor_id, event_type.
  • Event types (enum): JobSubmitted, StageSubmitted, TaskLaunched, TaskFinished, TaskFailed, TaskSpeculative, FetchFailed, ExecutorLost, StageResubmit, CheckpointWritten, CheckpointRead, BlockEvicted, HeartbeatTimeout.
  • Log level hierarchy: ERROR for job/stage failure; WARN for task retry, FetchFailed, executor lost; INFO for normal lifecycle; DEBUG for per-block operations.
  • Never log task payload data (PII risk); log only metadata (sizes, IDs, durations).

Incident Response

  1. Triage: check Job Overview dashboard for stalled stages or executor loss spike.
  2. Classify: executor failure vs. shuffle failure vs. driver memory vs. user code.
  3. Executor loss: follow RB-01; check heartbeat logs; identify if single node or rack.
  4. Shuffle failure: follow RB-02; inspect FetchFailed events; check map executor disk.
  5. Driver OOM: follow RB-05; heap dump; restart driver if HA enabled; else job loss.
  6. Checkpoint corrupt: follow RB-06; identify last valid checkpoint; restore or recompute.
  7. Post-incident: preserve event log + trace for root-cause; file lineage-depth + retry-budget tuning ticket.

Runbooks

  • RB-01 — Executor Loss Response: verify heartbeat logs; check OS/hardware; restart executor if transient; blacklist if repeated (Phase 12); adjust executor_timeout_ms.
  • RB-02 — Shuffle / FetchFailed Recovery: identify guilty (ShuffleId, map_id); check disk usage; delete partial shuffle files; let stage resubmit proceed; increase shuffle disk quota if recurrent.
  • RB-03 — Stalled Job: find blocked stage; check if all map outputs registered in MapOutputTracker; inspect task slot availability; kill and resubmit job if no progress after timeout.
  • RB-04 — Shuffle Disk Full: identify top disk consumers by shuffle.disk_used_bytes; prune completed job shuffle dirs; increase quota; reduce concurrency.
  • RB-05 — Driver Heap High: thread dump + heap dump; inspect MapOutputTracker size; enable lineage truncation / more frequent checkpoints; restart driver in HA mode.
  • RB-06 — Checkpoint Corrupt: verify CRC of all checkpoint files; delete corrupt file; identify last clean checkpoint from manifest; trigger recompute for affected partitions.
  • RB-07 — RPC Latency High: check RPC queue depth; identify slow executor; inspect GC time on executor; reduce concurrency or increase timeout.
  • RB-08 — Speculative Rate High: check task runtime histogram for skew; inspect partition size distribution; tune speculative_threshold_percentile; rebalance input partitions.

Backup / Restore Strategy

  • Checkpoint store: configured as durable object store (S3-compatible or HDFS); checkpoint manifest lists all checkpoint files with CRC and generation number.
  • Restore procedure: on driver restart, read latest valid checkpoint manifest; verify CRC of each partition block; truncate lineage to checkpoint depth; resubmit incomplete stages.
  • Event log: append-only event log written by driver for every job event; retained for post-mortem and job UI; rotated per job; stored in durable store.
  • Shuffle data: ephemeral; not backed up; recovered via stage resubmit.
  • Driver state (HA): periodic serialized driver state snapshot to durable store; on restart, load snapshot + replay event log delta.

Deployment Topology

  • Driver: 1 active (+ 1 standby for HA); dedicated node; isolated from executor heap pressure.
  • Executors: N workers; homogeneous or heterogeneous (locality-aware scheduling handles it).
  • Durable store: external (S3, HDFS, GCS); not co-located on executor nodes.
  • RPC port: configurable; default 7700 (driver listen); executors ephemeral port for shuffle.

Canary / Rolling Upgrade / Rollback

  • Canary: deploy new executor binary to 5% of executors; run a representative job; compare output checksums and metrics against baseline; promote if no regression after N jobs.
  • Rolling upgrade: replace executors one at a time (drain: wait for in-flight tasks to finish or timeout, then restart); driver detects executor reconnect via re-registration; ongoing jobs tolerate single-executor replacement under Phase 9 retry.
  • Driver upgrade: quiesce all jobs (or wait for natural completion); upgrade driver; executors re-register on reconnect; no in-flight state lost if executor BlockManagers survive driver restart.
  • Rollback: stop new binary executors; re-register previous binary executors; driver is version-agnostic to executor binary as long as RPC wire format is backward-compatible (see Compatibility Guarantees).
  • Migration strategy: new fields in RPC messages are optional with defaults; old executors ignore unknown fields (proto3 / bincode with version tag); no flag-day migrations.

Schema / Type Evolution

  • BlockId, TaskId, StageId, ShuffleId, PartitionId (ftdcr-core): opaque integer newtypes; stable; no cross-version incompatibility.
  • MapStatus (ftdcr-shuffle): fields append-only; executor_id + block_sizes array locked; new fields optional with defaults.
  • StorageLevel (ftdcr-block): bitfield; new bits appended at high end; old code ignores unknown bits (treats as MemoryOnly subset).
  • Task enum (ftdcr-driver): new variants require minor version bump; old executors receiving unknown variant emit LaunchFailed (safe: task retried on upgraded executor).
  • Checkpoint Partition schema: versioned via manifest; migration path: re-checkpoint on first successful run after upgrade, then truncate old checkpoint.

Deprecation Policy

  • Public API deprecation: mark with #[deprecated(since = "X.Y", note = "...")]; retain for one major version; remove in next major.
  • RPC message field deprecation: keep field in struct with #[deprecated] for one major version; stop populating it; then remove.
  • Checkpoint format deprecation: support N and N-1 simultaneously for one release cycle; emit warning on N-1 read; require re-checkpoint migration guide in release notes.
  • Storage format deprecation: document migration script in MIGRATIONS.md; provide ftdcr-cli migrate-checkpoint command.

Semantic Versioning Policy

  • MAJOR: breaking change to public API (ftdcr-core, ftdcr-graph trait), RPC protocol incompatibility, checkpoint format incompatibility.
  • MINOR: new public API; additive RPC fields; new Dataset transformation; new CLI job.
  • PATCH: bug fix, performance improvement, no interface change.
  • All crates in the workspace share the same version string; they are released as a lockstep bundle.

Rolling-Upgrade Guarantees

  • Executors at version N and N-1 may coexist in the same cluster for the duration of a rolling upgrade.
  • Driver at N speaks to executors at N and N-1 without error; uses lowest-common-denominator RPC feature set.
  • MapStatus and BlockId formats are identical between N and N-1; shuffle fetch between mixed-version executors is safe.
  • Tasks serialized by driver N and executed by executor N-1 succeed if no new task-variant was introduced (minor release); new variants fall back to LaunchFailed on old executor, driver retries on a new executor.
  • Checkpoints written at N-1 are readable at N (N-1 format supported); checkpoints written at N are not required to be readable at N-1.

Allocator Analysis

  • Default: system allocator (std::alloc); optional jemalloc feature (tikv-jemallocator) for executor heavy shuffle path.

  • Allocation hot paths: shuffle block buffer allocation (pre-allocate per partition); avoid per-record alloc in map-side sort inner loop.
  • Target: zero heap allocation in steady-state task polling loop (use pre-allocated buffers).

Lock Analysis

  • parking_lot mutexes; tracing instrumentation on lock acquire > 1 ms.
  • Identify contention: MapOutputTracker write lock under concurrent task completion; BlockManagerMaster location index.
  • Mitigation: shard MapOutputTracker by ShuffleId % N; read-heavy paths use RwLock.
  • loom for deterministic concurrency testing of critical sections (commit coordinator, heartbeat table).

Cache Analysis

  • CPU cache: shuffle sort inner loop arranged for sequential access (sort by key then write).
  • perf stat -e cache-misses,cache-references baseline per benchmark; regression gate: > 5% cache-miss increase.
  • BlockManager: LRU eviction order validated to preserve hot partitions (cache-friendly access patterns in iterative jobs).

Syscall Analysis

  • strace -c profile of executor process; target: < 10% of wall time in syscall overhead during compute-heavy tasks.
  • Shuffle write: batch pwrite calls; avoid per-record write syscall.
  • Network: SO_SNDBUF/SO_RCVBUF tuning for shuffle fetch; measure with ss -ti.

Memory Profiling

  • valgrind --tool=massif on integration tests; assert peak RSS < 2x working set.
  • Soak test: RSS sampled every 60 s; alert on monotone growth > 1% per hour.
  • Spill threshold tuning: execution_memory_fraction + storage_memory_fraction parameters; benchmark shows p99 spill latency < 50 ms for 100 MB block.

Tail-Latency Analysis

  • p50 / p95 / p99 / p99.9 task completion time tracked per stage in event log.
  • Straggler threshold calibrated to median × 1.5 (Phase 10); benchmark validates speculative launch reduces p99 job latency by > 20% under injected 10x slowdowns.
  • Shuffle fetch tail: retry budget 3 attempts; p99 fetch latency target < 2 s for 100 MB block over loopback.

Horizontal Scaling

  • Executor count: task parallelism scales linearly up to scheduler dispatch throughput ceiling (~5 k tasks/s single-driver).
  • Partition count: independent of executor count; more partitions = finer recovery granularity + longer planning.
  • Driver single-point: DAGScheduler + TaskScheduler + MapOutputTracker are single-process; horizontal scaling requires driver HA (Phase 12 gated).
  • Shuffle service: can be collocated or external; external shuffle service (separate process) allows executor restart without losing shuffle output (noted as Phase 12 extension).

Vertical Scaling

  • Driver: more RAM → larger MapOutputTracker + BlockManagerMaster index; more CPU → faster stage scheduling for wide jobs.
  • Executor: more RAM → less spill; more cores → higher task concurrency per executor.
  • Disk bandwidth on executor: shuffle write/read bound; NVMe vs spinning disk ×10 difference in shuffle-heavy jobs.

Coordination Overhead

Task launch 1 RPC driver→executor per task O(tasks); amortize with batch launch
MapStatus registration 1 write to MapOutputTracker per map task completion O(M × shuffles); sharding by ShuffleId reduces contention
Heartbeat 1 read/write per executor per interval O(executors); interval tuning trades detection latency vs throughput

Metadata Scaling

  • MapOutputTracker: for 10 k executors × 1 k shuffles × 1 k partitions = 10^10 entries; impractical at full scale without bloom-filter pre-checks or tiered storage. Practical target: 10 M entries in-process.
  • Lineage graph: adjacency list; 100 k nodes × average 3 deps = 300 k edges; fits in < 10 MB.
  • BlockManagerMaster: hash map BlockId → Vec<ExecutorId>; 1 M entries at 64 bytes/entry = 64 MB driver RAM.
  • Stage event log: append-only; archived per-job to object store after completion; driver holds only live jobs.

Scheduler Scaling Ceiling

  • TaskScheduler offer loop: O(executors × pending tasks) per scheduling round; amortize with batch offers.
  • Locality delay scheduling: degrade to rack/any locality after timeout; prevents starvation at scale.
  • Stage resubmit under failure: O(lost partitions) per recovery event; bounded by partition count.
  • Speculative detection: O(tasks per stage) scan per detection interval (default 100 ms); scales to 10 k tasks/stage.

Storage Scaling

  • BlockManager per executor: bounded by StorageLevel; MemAndDisk scales to disk capacity.
  • Shuffle spill: per-executor local disk; aggregate shuffle data = 2 × input for a single sort-merge; plan disk per executor for peak shuffle amplification.
  • Checkpoint store: durable object store (S3-compatible); scales independently; lineage truncation (I8) prevents unbounded growth.

Mental Models & First Principles

  • MM1 — Lineage is the recovery mechanism: a dataset is defined by how it was computed. Any lost partition is recomputed from its parents, not replicated. Predicts: fault tolerance costs CPU (recompute), not storage. Bug without it: replicating intermediate data instead of remembering lineage → wasted storage. Applied: Phase 1, Phase 8, §4.5.
  • MM2 — The DAG splits at shuffle boundaries. Narrow dependencies pipeline within a stage; a wide (shuffle) dependency forces a stage boundary and a barrier. Predicts: number of stages = number of shuffles + 1; shuffles are where you materialize and where failures hurt. Bug without it: trying to pipeline across a shuffle. Applied: Phase 3, Phase 6.
  • MM3 — A shuffle is a distributed sort/partition. Each map writes one sorted file + index per partition; each reduce fetches its slice from every map. Predicts: shuffle is all-to-all (M×R), the scalability bottleneck. Bug without it: one file per partition → FD exhaustion at 1M partitions. Applied: Phase 7, §4.4, ADR-A07.
  • MM4 — Failure detection is a timeout, so it is a tradeoff, not a fact. Shorter heartbeat = faster detection but more false positives. Predicts: detection latency ≈ 3 × T_hb. Bug without it: treating a slow node as dead → duplicate work and churn. Applied: Phase 9, §4.1.
  • MM5 — Speculation races a straggler against a clone; first to finish wins, the loser is killed. Predicts: it trades extra CPU for tail-latency reduction, and only helps when stragglers are noise, not skew. Bug without it: speculating on data skew → both copies equally slow. Applied: Phase 10.
  • MM6 — Determinism is the precondition for recompute-based recovery. Re-executing a task must yield the same output or lineage recovery produces wrong answers. Predicts: nondeterministic transforms (random, wall-clock) break exactly-once. Bug without it: a task reading current time → recompute diverges. Applied: I1, Phase 8, MM1.
  • MM7 — Checkpointing truncates lineage. Writing a dataset to durable store lets you forget its ancestry, bounding recompute cost for iterative jobs. Predicts: without checkpoints, iterative-job recompute depth grows unbounded. Bug without it: 100-iteration PageRank with no checkpoint recomputes from iteration 0 on any failure. Applied: Phase 11, §4.2.
  • MM8 — The driver is the single point of coordination and of failure. It holds the DAG, lineage, and MapOutputTracker. Predicts: driver loss loses the job (until driver HA); executors are replaceable, the driver is not. Bug without it: keeping unrecoverable state only in executor memory. Applied: Phase 12, §4.6.

  • Apache Spark is the direct lineage; it layered the DataFrame/Catalyst optimizer and Tungsten code-gen over RDDs — it wins for SQL-and-batch analytics where a query optimizer over the same lineage engine pays off.
  • Ray chose a dynamic, bottom-up distributed scheduler and an actor model rather than a static DAG — it wins for ML/RL workloads with irregular, dynamically-spawned task graphs that don't fit a pre-planned DAG.
  • Microsoft Dryad pioneered the explicit dataflow-DAG-of-vertices with channel-based communication — it wins where the computation is best expressed as an arbitrary static graph compiled ahead of time.

Back-of-Envelope Capacity Model

All inputs are taken from §4 (System Constraints); arithmetic is shown.

  1. Failure detection latency. 3 × T_hb + propagation = 3 × 1 s + ε ≈ 3–5 s (matches §4.1 "< 5 s").
  2. Shuffle fan-out. M maps × R reduces = all-to-all; 1000 executors as both → up to 1000 × 1000 = 1e6 logical fetches, capped at min(num_map, 50) concurrent per reducer (§4.4) — a bounded connection pool.
  3. Driver state. 1M partitions → MapOutputTracker ≈ 1e6 × ~16 B = 16 MB; full DAG + lineage for 10K stages < 2 GB (§4.2).
  4. Shuffle throughput. 1 TB/job (§4.3); map write ≥ 200 MB/s × 10 executors = 2 GB/s aggregate → 1e12 / 2e9 ≈ 500 s spill-bound; reduce fetch ≥ 500 MB/s aggregate per executor.
  5. WordCount 10 GB / 10 executors. 1 GB/executor; map read + shuffle write ≈ 1e9 / 200e6 ≈ 5 s + fetch + reduce → < 60 s budget (§4.3).
  6. FD budget. ≤ 4096 FDs/executor (§4.4); one file per 1M partitions would blow it → sort-based single-file+index is mandatory (MM3).
  7. Speculation. straggler detected within ≤ 1 s poll → duplicate launched < 2 s (§4.1); extra CPU = (straggler fraction) × (task runtime).
  8. Checkpoint cost. dataset size S at ≥ 100 MB/s (§4.1), 1× + ≤ 1.2× overhead (§4.5); a 10 GB cached RDD → ~100 s to checkpoint.
  9. Recompute depth. iterative job of K iterations without checkpoint → depth = K; auto-checkpoint every 10 (§4.6) bounds it to ≤ 10.
  10. RTO single executor loss. < 2 × longest-recompute-stage runtime (§4.6); only lost partitions recompute, not the whole stage.
  11. Task dispatch. p50 < 2 ms (§4.1), 10K in-flight (§4.3) → driver must sustain > 5K tasks/s → batched launches + async fan-out.
  12. PageRank 1M nodes, 10 iter, 10 executors. each iteration shuffles the rank vector (1e6 × 8 B = 8 MB) joined with edges; 10 iterations < 10 min (§4.3) → ~60 s/iteration budget.

Alternative Architectures (Roads Not Taken)

A1 — Bulk materialization to a DFS between every step (MapReduce model).

input → map → write HDFS → sort/shuffle → reduce → write HDFS → next job

Wins for very large single-pass batch jobs where disk-durable intermediates and dead-simple recovery beat in-memory speed. Embodied by MapReduce/Hadoop. Rejected because iterative jobs (PageRank, ML) re-read from disk every step — lineage + in-memory caching is 10–100× faster (§2, MM1).

A2 — True streaming with distributed snapshots (Chandy-Lamport).

unbounded stream → pipelined operators → periodic barrier snapshot → exactly-once on replay

Wins for unbounded, low-latency continuous processing where micro-batch latency is unacceptable. Embodied by Apache Flink. Rejected for v1 because the target is batch dataflow (§4); streaming/micro-batch is deferred (Register).

A3 — Dynamic bottom-up task/actor scheduling (no static DAG).

tasks spawn tasks at runtime → distributed scheduler places them → object store moves results

Wins for irregular, dynamically-spawned graphs (RL, hyperparameter search) that cannot be planned ahead. Embodied by Ray. Rejected because a static stage DAG enables global scheduling decisions (locality, speculation) and matches the batch-analytics target.

A4 — Active replication of intermediate data (no recompute).

each partition written to k nodes → on loss, read a replica instead of recomputing

Wins when recomputation is prohibitively expensive (very deep lineage, non-reproducible sources) and storage is cheap. Embodied by replicated-state stream processors. Rejected because lineage recompute is cheaper for reproducible transforms (MM1, §4.5), and checkpointing covers the deep-lineage case (Phase 11).

Glossary

Alphabetical. Each entry is implementation-relevant and operationally precise, grounded in the types and invariants of the codebase.

Action : Dataset method (collect, count, save, foreach) that materializes the lazy DAG. : Triggers a Job submission to DAGScheduler; breaks laziness. : Contrast with Transformation, which only extends the unevaluated DAG.

Attempt (TaskAttempt) : One execution of a Task identified by (task_id, attempt_number). : Retries and speculative duplicates are distinct attempts on the same (stage, partition). : Commit coordinator accepts at most one attempt per (stage, partition); enforces I7.

Backpressure : Flow-control on the reduce-side shuffle fetch pipeline. : Limits concurrent in-flight block requests when BlockManager memory approaches the spill threshold. : Prevents OOM during high-fanout shuffles; governed by P9.

Blacklist : Driver-side policy (ftdcr-ft) suppressing task dispatch to an executor after it exceeds a configured failure count within a job. : Does not permanently remove the executor; resets per job. : Advises TaskScheduler via is_blacklisted(executor_id: ExecutorId) -> bool.

BlockId : enum { Rdd(rdd_id, partition_id), Shuffle(shuffle_id, map_id, reduce_id), Broadcast(broadcast_id) }. : Cluster-wide unique address for any stored block. : Key in BlockManagerMaster's location index and BlockManager's local store.

BlockManager : Per-executor storage subsystem (ftdcr-block). : Stores blocks at a chosen StorageLevel (memory / disk / both). : Reports put/remove events to BlockManagerMaster; evicts via LRU under memory pressure; spills to disk at threshold.

BlockManagerMaster : Driver-side location index: BlockId → Vec<ExecutorId>. : Updated by executor BlockReports; queried by reduce tasks to resolve shuffle and RDD block locations. : Must converge to correct state within one heartbeat cycle after executor loss.

BlockReport : RPC message sent by an executor to the driver listing all locally held blocks (BlockId, StorageLevel, size_bytes). : Sent at registration and on significant delta. : Drives BlockManagerMaster updates; basis for P10 (driver authoritative).

Broadcast variable : A read-only dataset-scoped value shipped to every executor once and cached. : Identified by a Broadcast BlockId; not partitioned. : Used for lookup tables, model parameters, or small configuration structures.

Cache / Persist : Directive on a Dataset to retain computed partitions in BlockManager after first compute. : cache() = MemoryOnly; persist(StorageLevel) = explicit placement. : Eviction possible under memory pressure; re-access triggers recomputation or disk read.

Checkpoint : Durable write of a Dataset's partitions to an external store (HDFS or local path). : After successful write, LineageGraph truncates ancestor edges up to the checkpoint boundary (I8). : Future recovery reads from checkpoint; recomputation cost is bounded for iterative jobs (P8).

Commit coordinator : Driver-side arbiter enforcing I7: for each (stage, partition), only the first accepted task attempt's result is recorded. : Subsequent attempts' commits are acknowledged but discarded without error. : Correctness basis for both retry recovery and speculative execution.

DAGScheduler : Driver component (ftdcr-driver). : Receives a Job from an action; walks the RDD DAG; cuts stages at wide (shuffle) Dependency boundaries. : Submits stages in topological order (I3); handles StageCompleted, StageFailed, FetchFailed events.

Dataset (RDD) : Core user abstraction (ftdcr-graph). : Fields: id, num_partitions, deps: Vec<Dependency>, compute: fn(PartitionId, &[BlockRef]) -> Iterator<Item=Row>. : Logical, partitioned, lazily evaluated. Basis for all transformations, lineage, and recovery.

Delay scheduling : TaskScheduler heuristic: if the highest-locality executor slot is not immediately available, wait a configurable interval before accepting a lower-locality offer. : Improves data-local placement rate; configurable delay_scheduling_ms.

Dependency : enum { Narrow(parent_dataset_id), Shuffle(ShuffleId, parent_dataset_id, Partitioner) }. : Narrow: each output partition reads ≤ 1 input partition; enables pipelining within a stage. : Wide (Shuffle): every output partition reads from all input partitions; forces stage boundary.

Driver : Singleton coordinator process (ftdcr-driver). : Runs DAGScheduler, TaskScheduler, MapOutputTracker, BlockManagerMaster. : Does not execute user compute; authoritative for all cluster state (P10).

Driver HA : High-availability mode: checkpoint driver state so a replacement driver can resume a running job. : Marked PhaseDeferred; not implemented in Phases 1–14. : Required for production multi-hour job reliability; gated on external coordination service.

Exactly-once result : The job output is independent of the number of task retries or speculative copies executed. : Achieved by at-least-once task execution combined with idempotent commit coordination (P5, I4, I10).

ExecutorInfo : Registration record: { id: ExecutorId, host, port, cores: u32, memory_mb: u64, registered_at }. : Stored in driver executor registry; used by TaskScheduler for offer generation.

ExecutorLost : Internal driver event raised when a heartbeat timeout expires for an executor. : Triggers: mark in-memory blocks lost in BlockManagerMaster, resubmit running tasks, invalidate MapOutputTracker entries, optionally blacklist executor.

FetchFailed : Error raised by a reduce-side task when it cannot retrieve a shuffle block. : Causes: network error, executor gone, missing block after executor loss. : Driver response: clear affected MapOutputTracker entries; resubmit the producing ShuffleMapStage (Phase 9).

Heartbeat : Periodic liveness message: (executor_id, timestamp, running_task_ids, memory_stats). : Absence beyond heartbeat_timeout_ms triggers ExecutorLost. : Also carries task progress updates to avoid a separate progress-report channel.

Idempotent commit : Task result written under a content-addressed or attempt-tagged key. : Duplicate writes (retry, speculative copy) are detected by the commit coordinator and ignored. : Precondition for P4 (attempt-tagged write-once) and P5 (exactly-once result).

Job : Unit submitted to DAGScheduler when an action is called on a Dataset. : Contains (root_rdd_id, num_output_partitions, result_handler). : Decomposes into one or more Stages; lifecycle tracked by JobTracker.

Lazy DAG : The unevaluated graph of Dataset transformations built by user code. : Not materialized until an action is called; represented in ftdcr-graph. : Consumed by DAGScheduler at job submission time to produce the Stage graph.

Lineage : The complete record of a Dataset's Dependency chain back to stable input data. : Used by ftdcr-lineage to build a RecomputePlan for lost partitions. : Fundamental to P1 (recover by recomputing, not by eager replication).

Lineage truncation : After checkpoint confirmation, ftdcr-lineage removes ancestor Dependency edges up to the checkpoint boundary. : Bounds recomputation cost for long iterative jobs (P8). : Enforces I8: recovery reads checkpoint, never replays pre-checkpoint history.

Locality preference : Per-task ranked list of preferred execution sites: PROCESS_LOCAL > NODE_LOCAL > RACK_LOCAL > ANY. : Computed from BlockManagerMaster block locations; drives delay scheduling.

MapOutputTracker : Driver-side registry (ftdcr-shuffle): ShuffleId → Vec<Option<MapStatus>>. : Populated when ShuffleMapTasks commit; queried by reduce tasks for fetch locations. : Invalidated entries on executor loss or FetchFailed; must satisfy I6 at all times.

MapStatus : { executor_id, shuffle_id, map_partition_id, reduce_partition_sizes: Vec<u64> }. : Registered by executor when a ShuffleMapTask commits its output. : Consumed by reduce tasks via MapOutputTracker to locate and size-prefetch shuffle blocks.

Memory manager : Unified per-executor memory pool (ftdcr-executor). : Divides heap between execution memory (task sort/spill buffers) and storage memory (cached partitions). : Dynamic boundary; governed by P9 (spill not OOM).

Narrow dependency : A Dependency where each output partition reads from at most one input partition. : Enables pipelining: multiple narrow transformations execute in a single Stage without materializing intermediate partitions.

Partition : Unit of parallelism and recovery. : Identified by PartitionId (u32 index within a Dataset). : One task processes one output partition; smallest granularity recomputed by ftdcr-lineage.

Partitioner : enum { Hash(num_partitions: u32), Range(bounds: Vec<K>) }. : Maps a (key, value) to a reduce-side partition index. : Must be deterministic across task attempts (required by I1: recomputed partition is bit-identical).

PhaseDeferred : Tag for a capability designed but not implemented in Phases 1–14. : Examples: driver HA, rack-aware replication, dynamic executor addition/removal. : Noted in relevant phases; excluded from test scope.

RecomputePlan : Output of ftdcr-lineage for a set of lost (DatasetId, PartitionId) pairs. : Topologically ordered list of (dataset, partition) tasks to re-execute. : Stops at cached, checkpointed, or still-available ancestor partitions; avoids recomputing available data.

ResultStage : A Stage whose tasks (ResultTask) write directly to the job output sink or return data to the driver. : The leaf stage of the job's Stage graph. : Completion of all ResultTask partitions satisfies I10 (job complete).

ShuffleId : Globally unique identifier for one wide Dependency. : Scopes all MapStatus entries and shuffle block keys for that shuffle. : Assigned by DAGScheduler at stage-construction time; immutable thereafter.

ShuffleMapStage : A Stage whose tasks (ShuffleMapTask) partition and write output to BlockManager as shuffle blocks, then register a MapStatus in MapOutputTracker. : Parent of the downstream Stage that reads the shuffle. : Must complete fully before the child stage is submitted (I3).

Shuffle block : Storage unit for map-side shuffle output: one block per (shuffle_id, map_partition_id, reduce_partition_id). : Stored in BlockManager; served by ShuffleService HTTP endpoint; fetched by reduce tasks. : Immutable once committed (I2).

Speculative execution : Launching a second attempt of a straggler task before the first attempt finishes. : First attempt to commit wins; all others discarded by commit coordinator (I7). : Bounds tail latency per P7; motivated by Dean & Barroso CACM 2013.

Spill : BlockManager writing partitions from memory to disk when the storage memory region is exhausted. : Controlled by LRU eviction policy. : Spilled blocks remain accessible at reduced throughput; MemAndDisk StorageLevel.

Stage : Maximal subgraph of narrow-dependency transformations. : Bounded by wide (shuffle) Dependency on at least one side. : Unit of scheduling in DAGScheduler; parents submitted before children (I3).

StorageLevel : { use_memory: bool, use_disk: bool, deserialized: bool, replication: u8 }. : Describes how BlockManager retains a partition. : Core variants: MemoryOnly, MemAndDisk, DiskOnly, with optional replication field.

Straggler : A task whose elapsed runtime exceeds a configurable percentile of finished tasks in the same Stage. : Candidate for speculative duplication by ftdcr-ft. : Default threshold: p75 × 1.5 of finished-task runtimes in the TaskSet.

TaskScheduler : Driver component (ftdcr-driver). : Accepts TaskSets from DAGScheduler; maintains an offer-based dispatch loop over executor free slots. : Applies delay scheduling for locality; tracks per-task state; reports completions back to DAGScheduler.

TaskSet : Set of Tasks generated from one Stage, one task per output partition. : Submitted atomically to TaskScheduler. : Tracked until all partitions have exactly one accepted result (I10).

Transformation : A Dataset method (map, filter, flatMap, reduceByKey, join, groupByKey, sortByKey) returning a new Dataset. : Extends the lazy DAG; no I/O or compute occurs at call time. : Each transformation records the appropriate Dependency (Narrow or Shuffle) in the new Dataset.

Wide dependency : A Dependency (always a Shuffle variant) where every output partition reads from all input partitions. : Forces a stage boundary; map side must fully materialize before reduce side begins. : Requires shuffle materialization, MapOutputTracker registration, and reduce-side fetch.
