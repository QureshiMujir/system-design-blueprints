Decisions · 23 ADRs

ADR-01

Core language

Chosen

Rust 1.75+

Rejected

C++, Go

When the rejected choice is right

C++ when you must embed in an existing C++ kernel module; Go when GC pauses are acceptable and team velocity dominates.

Why: Borrow-checked guarantees make the DLL unsafe auditable; no_std story for WASM.

ADR-02

DLL ownership

Chosen

Intrusive raw-pointer DLL over an arena

Rejected

Box<Node>, Rc<Node>

When the rejected choice is right

Rc<Node> when nodes are shared across structures and safety beats the 2× overhead.

Why: Refcounts double per-node overhead and ruin locality; box-owned lists fragment the heap.

ADR-03

Slot reuse

Chosen

Generational arena

Rejected

plain index reuse

When the rejected choice is right

Plain indices when slots are never freed during a run (append-only cache).

Why: Use-after-free with raw pointers needs a generation tag to distinguish recycled slots.

ADR-04

Shard lock

Chosen

parking_lot::Mutex

Rejected

std::sync::Mutex

When the rejected choice is right

std::Mutex when poisoning-on-panic is a desired safety property.

Why: Faster under contention; no poisoning logic at every call site.

ADR-05

Lock-free reader path

Chosen

Sharded mutex now; RCU later

Rejected

crossbeam-epoch / hazard pointers at v1

When the rejected choice is right

Epoch reclamation when readers vastly dominate and 30–50% extra memory is acceptable.

Why: Correct-then-fast; epoch bugs are brutal to debug atop an unverified mutex path.

ADR-06

Key hash

Chosen

xxhash3 (xx3-64)

Rejected

ahash, SipHash

When the rejected choice is right

SipHash when keys are fully attacker-controlled and DoS-resistance beats speed.

Why: Fastest non-crypto hash with stable cross-version behaviour.

ADR-07

Hash map

Chosen

hashbrown directly

Rejected

std::collections::HashMap

When the rejected choice is right

std::HashMap when the raw-entry API is unneeded and stdlib-only is a constraint.

Why: Raw-entry API, deterministic sizing, swappable hasher.

ADR-08

Policy build order

Chosen

Incremental: LRU/LFU (Phases 1–2) → LRU-K/2Q/ARC (Phase 3) → admission+CLOCK family+SIEVE (Phase 4), not all ten at once

Rejected

ship all ten policies in Phase 0

When the rejected choice is right

Ship-all-first when you have a customer who needs CAR specifically on day one and incremental delivery is not acceptable.

Why: Each policy conformance-gates the next; SIEVE is simple enough to build early but is bundled with the admission/CLOCK cluster because both share the same admission-decision plumbing.

ADR-09

Default admission

Chosen

W-TinyLFU for ARC and SIEVE

Rejected

no admission by default

When the rejected choice is right

No admission for scan-once workloads where the CMS just adds cost.

Why: Caffeine demonstrates the production win.

ADR-10

TTL structure

Chosen

Hierarchical timer wheel

Rejected

binary heap, single-level wheel

When the rejected choice is right

A heap when timeouts are few and you also need ordered iteration of expiries.

Why: Heap is O(log N)/op; single-level covers a fixed range; hierarchical is O(1) over any range (Linux's choice).

ADR-11

Budget unit

Chosen

Rejected

count default

When the rejected choice is right

Count default for fixed-size-value caches where bytes == count × const.

Why: Real systems care about RAM; counts are the special case.

Alternative Architectures (Roads Not Taken)

A1 — Single-threaded event loop (Redis shape).

[clients] → [single thread: command loop → policy → store] → [reply]

Wins when the cache is a network data-structure server and predictable single-thread semantics + rich types matter more than raw multi-core throughput. Embodied by Redis. Rejected here because this is an in-process library primitive; a single event loop would cap multi-core throughput and force an async boundary the embedding application does not want.

A2 — Lock-free epoch-reclaimed reader path (Caffeine shape).

readers → [striped ring buffers] → [async maintenance thread → policy mutation]

Wins on read-dominated workloads inside a managed runtime where async batched eviction amortises maintenance and lock-freedom dominates. Embodied by Caffeine. Rejected for v1 (deferred, ADR-05) because correct-then-fast: an epoch-reclamation bug atop an unverified mutex path is far costlier to debug than the throughput it buys. Un-defers when reader throughput is the binding constraint.

A3 — Slab-allocated segmented LRU (Memcached shape).

[slab classes by size] → [per-class segmented LRU] → [item locks]

Wins for fixed-ish-size values at very large scale where slab fragmentation control beats admission cleverness. Embodied by Memcached. Rejected because the engine targets arbitrary (K,V) with a byte-aware weigher and a policy zoo; slab classes would constrain the value model and add fragmentation accounting the arena avoids.

A4 — Sampling-based approximate eviction (Redis maxmemory shape).

on evict: sample k random keys → evict the worst by recency/frequency estimate

Wins when exact recency/frequency ordering is too expensive and approximate is good enough at huge key counts. Embodied by Redis allkeys-lru. Rejected because the engine's intrusive DLL makes exact O(1) eviction cheap, and the conformance suite demands tight hit-rate parity (1e-4–5e-3) that sampling cannot guarantee against the reference oracles.
