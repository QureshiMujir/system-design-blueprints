⬜ Phase 0 — Skeleton, governance, and the DLL primitive

Objectives

Stand up the repository, governance, build/CI, and the intrusive DLL primitive every later phase rests on. Constraint introduced: the single unsafe chokepoint (P9) must be Miri-clean before any policy is built on it.

Deliverable

make {bootstrap,build,test} all exit 0 on a clean clone; the DLL smoke test inserts and removes 10K keys without leaking and without firing Miri. Inspectable via the cargo geiger CI artifact and the arena leak counter.

Acceptance

make {bootstrap,build,test,miri,loom} all return 0; DLL smoke + oracle + loom tests green across 1e6 randomized operations; cargo geiger unsafe-block count ≤ 10 in dll.rs (I14).

Fixtures
Fixture Purpose Expected
10K insert/remove random order leak detection arena free-list returns to baseline; Miri clean (I3)
DLL vs VecDeque oracle order correctness identical iteration order after every op (I1)
loom 2-thread shared arena concurrency under mutex no race, no deadlock
generation wrap to 1 sentinel safety gen never observed as 0 (I4)
Pitfalls
  • Vec<MaybeUninit<Node>> requires draining live nodes before dropping the Vec; encode in Drop, audit under Miri.
  • Generation wrap must go to 1, never 0 (0 is the "never allocated" sentinel).
  • Unlink-from-the-middle must be exactly two pointer rewrites; if you iterate, you wrote it wrong.

⬜ Phase 1 — Classical LRU

Objectives

Ship the simplest policy: hash map for O(1) lookup, DLL for O(1) recency, evict from the tail. Cache::builder().lru().capacity(N).build() conforms to a textbook oracle. Constraint introduced: the Policy trait (§11.5) and Cache<K,V> facade (§11.6) are fixed here and never change shape for later policies.

Deliverable

src/policy/lru.rs, examples/lru-basic.rs, docs/algorithms/lru.md, benches/lru_get.rs. Operator-inspectable via lrulfu-cli replay --policy lru.

Acceptance

policy.lru conformance bucket green (order matches the OrderedDict oracle at every step, I1); ARC P1 trace hit-rate within 1e-4 of the public reference; lru_get microbench ≥ 100M ops/sec single-thread (M1).

Fixtures
Fixture Purpose Expected
OrderedDict oracle, Zipf ops order conformance iteration order matches every step (I1)
ARC P1 trace replay hit-rate parity within 1e-4 of public reference
existing-key insert moves to front recency correctness hit rate does not degrade over the run
Pitfalls
  • Forgetting move-to-front on existing-key insert: correct but hit rate decays silently. Test explicitly.
  • HashMap::get borrow blocks the move-to-front: read the slot, drop the borrow, then mutate.
  • over_budget is bytes-aware by default; a count-only cache uses weigher→1, never a special case in the policy (P7).

⬜ Phase 2 — O(1) LFU with counter buckets

Objectives

Implement the Pugh-Stevens O(1) LFU: a DLL of frequency buckets, each holding a DLL of nodes. Promote-on-access and eviction are both O(1), matching LRU's cost class (P11).

Deliverable

src/policy/lfu.rs, docs/algorithms/lfu.md, benches/lfu_get.rs. Inspectable via lrulfu-cli replay --policy lfu and the lfu_bucket_count gauge.

Acceptance

policy.lfu conformance bucket green against Caffeine LFU (admission off) within 1e-4 hit-rate; lfu_get throughput within 20% of the LRU baseline (M1-relative); O(1)-cost property test shows linear (not quadratic) pointer-rewrite growth across 1-, 2-, 3-hit passes.

Fixtures
Fixture Purpose Expected
Caffeine LFU (admission off), Zipf hit-rate parity within 1e-4
hit all N keys 1×,2×,3× O(1) cost pointer rewrites scale linearly with hits, not quadratically
single-occupant bucket removal bucket lifecycle empty bucket unlinked exactly once
Pitfalls
  • Bucket DLL vs node DLLs are different DLLs; reuse of head/tail names invites bugs — BucketSlot vs Slot enforces the distinction.
  • Inserting a bucket between two existing buckets: the next-bucket count check is == not <=. Read the Stevens note literally.
  • Pure LFU's lack of aging is wrong for almost every modern workload (MM3); document prominently in docs/algorithms/lfu.md so no one ships it unmodified.

⬜ Phase 3 — Multi-list algorithms: LRU-K, 2Q, ARC

Objectives

Separate recency from frequency by giving each its own list: LRU-K (K-th-reference distance), 2Q (A1in/A1out/Am), ARC (adaptive between recency and frequency). Constraint introduced: bounded ghost lists (P12) must hold from this phase onward.

Deliverable

src/policy/{lru_k,two_q,arc}.rs, docs/algorithms/arc.md, examples/arc-vs-lru-on-trace.rs. Inspectable via arc_p_gauge live during a trace replay.

Acceptance

policy.lru_k, policy.two_q, policy.arc conformance buckets green within 1e-3 of their references; ARC matches Megiddo-Modha paper Tables 1 & 4 within 1e-3; the mid-trace workload-flip property test shows p moving in the theoretically correct direction (I9).

Fixtures
Fixture Purpose Expected
LRU-K K=2 oracle, ARC P1 hit-rate parity within 1e-3
2Q oracle, ARC OLTP hit-rate parity within 1e-3
ARC paper Tables 1 & 4 ARC correctness within 1e-3 of published rates
workload flips recency→frequency mid-trace adaptation p adjusts in the correct direction; I9 holds
disjointness property list invariants T1,T2,B1,B2 disjoint and individually bounded (I8)
Pitfalls
  • ARC's adaptation is easy to sign-wrong; read the Megiddo-Modha pseudocode (Appendix I.2), not a blog summary.
  • 2Q's "do nothing on A1in hit" feels wrong and is correct — keys leak to A1out, where the next hit promotes them (Appendix I.5).
  • LRU-K K=1 == LRU; guard the naive path that costs more for no benefit. Document in docs/algorithms/lru.md.

⬜ Phase 4 — Admission, CLOCK family, SIEVE

Objectives

Land the admission filter (W-TinyLFU = Bloom doorkeeper + 4-bit CMS) and the second-chance algorithms (CLOCK, CLOCK-Pro, CAR) plus SIEVE (2024). This is the densest phase: five algorithms plus a cross-cutting filter.

Deliverable

src/policy/{w_tiny_lfu,clock,clock_pro,car,sieve}.rs, src/admission/*, docs/algorithms/{w_tiny_lfu,clock_pro,sieve}.md, examples/algorithm-shootout.rs. Inspectable via lrulfu-cli replay --all-policies (the shootout table).

Acceptance

All five policies plus admission pass their conformance buckets; SIEVE get within 5% of LRU (M3); Bélády ratio ≥ 0.99 on each policy's target workload class; CMS estimator never underestimates a true count (I10, 1+ε overestimate bound).

Fixtures
Fixture Purpose Expected
CMS vs true counts, Zipf estimator bound estimate ≥ true, within 1+ε (I10)
Caffeine W-TinyLFU, Twitter cluster_001 admission parity within 5e-3
CLOCK ref, ARC S1 CLOCK correctness within 1e-3
CLOCK-Pro ref, LIRS-like trace LIRS approximation within 5e-3
SIEVE 2024 paper, Twitter+CDN SIEVE parity within 5e-3
algorithm shootout comparative hit-rate per-policy table on P1, OLTP, Twitter, YCSB-A
Pitfalls
  • CMS aging: a naive >> 1 leaks the high bit of one nibble into the next. Mask 0x77 after the shift (I10, Appendix I.4).
  • CLOCK-Pro's three hands can lap; handle two hands pointing at the same slot.
  • SIEVE's visited bit must be set on hit; forgetting it makes SIEVE behave like FIFO — a dramatic, silent hit-rate drop (Appendix I.3).

⬜ Phase 5 — Sharded concurrency

Objectives

Lift any policy to a contention-split cache: N independent shards, each guarded by a parking_lot::Mutex, shard = hash(key) & mask. Target ≥ 500M ops/sec on 16 cores, read-heavy (M4).

Deliverable

src/shard.rs, docs/architecture/sharding.md, benches/sharded_concurrent.rs, examples/sharded-concurrent.rs. Inspectable via shard_load_histogram during a load test.

Acceptance

loom 16-reader/4-writer suite green (1000 iterations, no race, no deadlock); ≥ 500M ops/sec on the reference 16-core host, 95/5 read-heavy mix (M4); no shard carries > 2× the mean load (I12).

Fixtures
Fixture Purpose Expected
loom 16-reader 4-writer, 8 shards, 1000 iters concurrency safety no race, no deadlock, consistent post-state
read-heavy 95/5 on 16 cores throughput gate ≥ 500M ops/sec (M4)
key-distribution histogram shard balance no shard > 2× mean load (I12)
Pitfalls
  • A poor hash clusters keys onto a subset of shards and silently halves throughput; xxhash3, not DefaultHasher.
  • Shard count must be a power of two for the & mask fast path; default 16 or 32.
  • Cross-shard iteration under a global lock kills the benefit; document len/clear as approximate.

⬜ Phase 6 — TTL and the timer wheel

Objectives

Per-entry absolute expiry via a hierarchical timer wheel ticked on op; 1M entries at 1s TTL expire within 100 ms (M8).

Deliverable

src/ttl/timer_wheel.rs, docs/architecture/ttl.md, benches/ttl_expiry.rs, examples/ttl-and-refresh.rs. Inspectable via timer_wheel_cascade_total during a long-TTL soak.

Acceptance

ttl.wheel conformance bucket green (every expiry within 1 ms of expected); 1M entries at 1s TTL fully expired within 100 ms (M8); cascade property test green across every level transition.

Fixtures
Fixture Purpose Expected
10K entries, random TTL [1ms,1day], waypoints expiry correctness exactly the elapsed entries evicted
1M entries @ 1s, advance 1s expiry throughput all evicted in < 100 ms (M8)
L3→L2→L1 cascade cascade correctness entries cascade without loss or duplication
get-after-expiry-before-tick read-path expiry reported as miss (I11)
Pitfalls
  • Wall-clock is not monotonic; use Instant, clamp backward jumps (P13).
  • A get after expiry but before the next tick must be a miss, not a hit — check expires_at directly.
  • Cascading is the source of most timer-wheel bugs; test every level transition explicitly.

⬜ Phase 7 — Byte budgets, weights, write modes, refresh-ahead

Objectives

Byte-default budget with custom weigher; write-through/back/around; refresh-ahead with singleflight coalescing. Closes the T2 memory-pressure gap left open since Phase 1.

Deliverable

src/budget/*, src/write.rs, src/refresh.rs, examples/byte-budget.rs. Inspectable via lrulfu_cache_bytes_in_use and writeback_queue_depth during a write-heavy load test.

Acceptance

Byte-budget conformance green (used_bytes exactly matches the external sum of live weights, I2); all four write modes tested against a fake sink; refresh-ahead loom-clean (one loader call per key in flight); write-back queue never exceeds its configured high-water mark.

Fixtures
Fixture Purpose Expected
varying-size inserts budget accounting used_bytes == external sum (I2)
four write modes w/ fake sink write semantics each mode's contract holds
write-back under sustained pressure bounded queue queue ≤ high-water; backpressure applied (I13)
concurrent refresh, loom no-deadlock + coalescing one loader call per key in flight
Pitfalls
  • Weigher returning 0 lets the cache exceed budget without evicting; reject weight==0.
  • Write-back queue must be bounded; configurable high-water + backpressure (block/drop/error).
  • Refresh-ahead can trigger redundant loader calls; coalesce per key (singleflight).

⬜ Phase 8 — Optional persistence (snapshot + AOF)

Objectives

Periodic snapshot + append-only file for caches whose contents are expensive to repopulate. Deferred surface (ADR-17); the Phase-0 gate ships in-memory only — this phase is exercised when a deployment's RTO/RPO needs it (Deferred Features Register).

Deliverable

crates/lrulfu-persistence/src/{snapshot,aof}.rs. Deferred per the Deferred Features Register; inspectable via snapshot_duration_seconds and persistence_load_errors_total.

Acceptance

Snapshot round-trip exact (reloaded cache == pre-snapshot minus expired); AOF replay-since-snapshot RTO ≤ 30 s (§4); malformed-length-field parser bounded (no unbounded allocation, load aborts, in-memory cache untouched); crash-mid-rotation loses zero entries.

Fixtures
Fixture Purpose Expected
snapshot round-trip fidelity reloaded cache == pre-snapshot (minus expired)
AOF replay since snapshot recovery RTO ≤ 30 s for the reference dataset
malformed length field parser safety bounded alloc; load aborts; in-memory untouched (§8.4)
crash mid-rotation atomicity no entries lost
Pitfalls
  • Snapshot serialisation must not freeze readers; capture a consistent view via crossbeam-epoch.
  • AOF rotation must be atomic with snapshot completion or a mid-rotation crash loses entries.
  • Non-Serialize keys cannot persist; reject at builder time.

⬜ Phase 9 — Bindings: Python, Java, WASM

Objectives

Project the Rust API into Python (PyO3), Java (jni-rs), and WASM (wasm-bindgen). Bindings cannot have features the Rust API lacks (P10) — this phase is purely a projection, no new cache semantics.

Deliverable

bindings/{python,java,wasm}/, examples/{python-quickstart.py, wasm-browser/}. Inspectable via pip install lrulfu, the Maven artefact, and the NPM package all resolving and running their quickstarts.

Acceptance

pip install lrulfu, the Maven artefact, and the NPM package all work; the three binding conformance buckets (bindings.python, bindings.java, bindings.wasm) green; all three quickstart examples run end to end.

Fixtures
Fixture Purpose Expected
pytest on PyO3 binding Python parity bindings.python green
JUnit on JNI binding (JDK 17,21) Java parity bindings.java green
wasm-bindgen-test, headless Chromium WASM parity bindings.wasm green
quickstart examples (all 3) end-to-end run clean
Pitfalls
  • PyO3 GIL discipline: calling back into Python from a Rust callback (e.g. a weigher) requires re-acquiring the GIL.
  • JNI local references are function-scoped; long-lived references must be promoted to global, and a leaked global is a memory leak.
  • WASM is single-threaded; the sharded cache reduces to single-shard — document it.

⬜ Phase 10 — Observability, ops, runbook

Objectives

OpenTelemetry spans on every operation, Prometheus metrics, /healthz, /metrics, a Grafana dashboard, and three runbooks. This phase is the operational capstone — it does not add cache semantics, it makes every prior phase's telemetry consumable.

Deliverable

src/stats.rs, ops/grafana/, docs/runbook/*. Inspectable via /metrics scrape and the Grafana dashboard rendering hit-rate, eviction mix, bytes, and p50/p99 panels.

Acceptance

/healthz, /metrics, and the Grafana dashboard all work; every metric named across Appendix O.1 is present on a live scrape; the M-trace milestone (span on every operation) is met.

Fixtures
Fixture Purpose Expected
span emission on each op tracing coverage every op emits a span
/metrics scrape metric completeness all Phase 10.2 metrics present
/healthz liveness health endpoint 200 when alive
Grafana dashboard load dashboard validity renders hit-rate, evict mix, bytes, p50/p99
Pitfalls
  • Span-per-op can dominate cost at 100M ops/sec; sample or make spans feature-gated for the hot path.
  • A hit_rate gauge computed naively per op is a hot-path divide; use an EWMA updated cheaply.
  • Aggregating metrics across all 16 shards on every scrape is itself a scan; cache the aggregate between scrapes rather than recomputing on every Prometheus poll.
