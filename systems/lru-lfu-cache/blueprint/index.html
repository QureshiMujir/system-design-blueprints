57 — LRU/LFU Cache Engine

Project Number: 57

Project Name: LRU/LFU Cache Engine

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

One-line scope. A node-local cache engine in Rust implementing the cache-replacement algorithms production systems actually ship — classical LRU, the O(1) LFU of Pugh/Stevens, LRU-K, 2Q, the Adaptive Replacement Cache (ARC) of Megiddo & Modha, the W-TinyLFU admission scheme of Einziger & Friedman that powers Caffeine, the CLOCK family (CLOCK, CLOCK-Pro, CAR), and the 2024 SIEVE algorithm of Zhang et al. — wired into a hardened, sharded, TTL-aware, byte-budgeted, write-policy-rich library with first-class Python, Java, and WASM bindings. Distributed coordination is out of scope (it is the rank-61 Distributed-Cache project); this engine is the node-local primitive on which the cluster later stands.

Recommended language: Rust 1.75+, with unsafe confined to the intrusive doubly-linked-list primitive in dll.rs and to FFI shims under bindings/. PyO3 for Python, jni-rs for Java, wasm-bindgen for the browser.

§1 Goal & Scope

Goal. Ship a library, a CLI, a benchmark suite, a conformance suite against three public trace corpora, and four bindings (Rust, Python, Java, WASM) that together implement ten cache-replacement policies behind one facade, each conformance-checked against a public reference and measured against the offline Bélády optimum.

In scope.

  • The intrusive DLL primitive every classical algorithm rests on (one unsafe site, fuzzed against a safe oracle).
  • Ten policies: LRU, O(1) LFU, LRU-K, 2Q, ARC, W-TinyLFU, CLOCK, CLOCK-Pro, CAR, SIEVE.
  • W-TinyLFU admission front filter (Bloom doorkeeper + 4-bit count-min sketch with aging).
  • Sharded concurrency wrapper that lifts any policy to a contention-split cache.
  • Per-entry TTL via a hierarchical timer wheel.
  • Byte/weight-aware budget enforcement; write-through / write-back / write-around; refresh-ahead.
  • Optional periodic snapshot + AOF persistence (deferred surface).
  • Observability (OpenTelemetry traces, Prometheus metrics), runbooks, ops packs.

Out of scope (rejected or deferred). Durability beyond optional snapshot+AOF; replication; a wire protocol or process boundary; an admin UI; the distributed cluster surface (rank-61). Each is captured in the Deferred Features Register with an un-defer trigger.

Non-goals. This is not a database, not a message queue, not a CDN. It is the node-local cache primitive — correct, fast, observable — that those systems embed.

§2 Why Build This

Caches are where every production system pays off the gap between the storage layer's actual latency and the application layer's promised latency. They are also where the algorithm family is small, well-studied, and almost universally shipped as a black box the application never gets to look inside. The teams bitten by a cache once — by an LRU that performs catastrophically on a scan-heavy workload, by an LFU that fossilises a long-ago popular key against a freshly viral one, by a TTL implementation whose timer thread is the bottleneck at 4 a.m. when the load shifts, by a write-back cache whose flush ordering corrupted a row at power loss — learn that the cache is not a black box. It is an algorithm with sharp edges, and the team that knows where those edges are can route around them. The team that does not, cannot.

This engine is the smallest deliverable that still teaches the full surface. It owns the intrusive DLL primitive, the O(1) counter-bucket scheme that makes LFU competitive with LRU at admission time, the recent-but-elegant SIEVE algorithm that beats LRU on most production traces with the cost of a single forward pointer, the W-TinyLFU admission filter Caffeine ships in production, and the timer-wheel structure that makes per-entry TTL cheap enough to apply at every read. It owns the sharded concurrency wrapper that splits contention across cores without leaking the algorithm choice, the byte-aware budget enforcement that lets the cache co-tenant with the rest of the process's memory, and the write-through / write-back / write-around / refresh-ahead semantics that show up in every real backend integration.

The deliverable is small enough to finish: a library, a CLI, a benchmark suite, a conformance suite, and four bindings. That tight focus is the only reason the timeline is 4–5 months rather than 4–5 years. The Distributed-Cache project at rank 61 is the natural successor — a cluster around this engine, with a consistent-hashed coordinator, vnode placement, copy-on-write rebalancing, and a gossip layer — but the cluster only works because each node is correct, fast, and observable, and that is what this project is about.

What Mastery Looks Like

  • You can open dll.rs, read fifty lines, and explain why unlink-from-the-middle is exactly two pointer rewrites and never a loop (Phase 0).
  • You can state, without notes, why textbook LFU is O(log N) and the Pugh-Stevens variant is O(1), and point at the bucket-DLL operation that makes it so (Phase 2).
  • You can derive ARC's adaptation rule from first principles and predict the sign of the p adjustment for a B1 hit vs a B2 hit (Phase 3).
  • You can explain why the CMS aging step is (b >> 1) & 0x77 and not b >> 1, and what bug the mask prevents (Phase 4).
  • You can argue why SIEVE beats LRU on CDN traces despite carrying one fewer pointer than LRU, citing insertion-order preservation (Phase 4).
  • You can size a shard count, a CMS width, and a per-entry overhead budget from the §4 constraints table alone (Phase 5, Back-of-Envelope Capacity Model).
  • You can name which policies can return Reject from admit and why the others must not pay for the admission pass (Phase 4, §7 Invariants).

Bindings. Host-language projections of the Rust API; they cannot have features the Rust API lacks. Cache facade. Dispatches on a dyn Policy chosen once at construction; never branches on policy at the call site. ShardedCache. One type that accepts any policy and lifts it to a contention-split cache without the policy noticing. Stats. Counters and histograms read off every operation; always on. Replacement policy. The ten algorithms, each a thin wrapper around the DLL primitive. Admission. A filter applied between "the eviction policy proposes a victim" and "the cache stores the candidate"; policies that do not want it do not pay for it. TTL. Per-entry expiry via a hierarchical timer wheel ticked on op. Persistence. Optional snapshot + AOF, deferred. DLL primitive. The single unsafe site; every algorithm sits on it.

Three load-bearing properties recur throughout: the algorithm choice is data (dispatch once at construction); sharding is orthogonal to the algorithm; every cross-cut (TTL, admission, stats, persistence) is composed by trait objects, never by recompilation. The build matrix is a Cartesian product of orthogonal axes — there is no LRU+TTL+TinyLFU type distinct from LFU+TTL+TinyLFU.

§6 Design Principles

Each principle states the rule, the tradeoff it accepts, and how violating it breaks the system.

  • P1 — One DLL primitive, every algorithm above it. Rule: the intrusive DLL lives once in dll.rs; every policy wraps it. Tradeoff: a single unsafe chokepoint that must be over-audited. Violation: per-algorithm linked-list arithmetic puts a use-after-free in ten eviction paths instead of one.
  • P2 — The algorithm is data, not code. Rule: Cache<K,V> parameterises over a dyn Policy; the matrix is built at runtime from a builder. Tradeoff: one virtual call per op. Violation: a compiled cache type per policy explodes the binary and the test matrix and makes A/B policy comparison a recompile.
  • P3 — Sharding is orthogonal. Rule: the sharded wrapper is one type that accepts any policy. Tradeoff: the policy must be Send. Violation: a policy that bakes in its own sharding cannot be benchmarked single-shard, hiding lock contention as algorithm cost.
  • P4 — TTL is per-entry, not per-cache. Rule: every entry carries an absolute expiry; the wheel ticks on op by default. Tradeoff: a per-op tick cost. Violation: a per-cache TTL forces homogeneous lifetimes and a background thread that is the 4 a.m. bottleneck.
  • P5 — Admission is a separate pass. Rule: TinyLFU sits between "policy proposes a victim" and "store the candidate." Tradeoff: a CMS query per admit. Violation: folding admission into each policy makes policies that do not want it pay for it, and couples nine implementations to the sketch.
  • P6 — No silent fallbacks. Rule: if a policy cannot honour a hint (e.g. weight on a policy that ignores weight), the build fails. Tradeoff: more builder errors. Violation: a silent downgrade ships a cache that quietly ignores the budget the operator set.
  • P7 — The cache is byte-aware first. Rule: the default budget is bytes; count is weigher→1. Tradeoff: a weigher call at insert. Violation: a count-only cache with 1 KB and 1 MB entries blows RSS while reporting "under capacity."
  • P8 — Hit-rate is measured against Bélády, not LRU. Rule: the conformance suite computes the offline optimum on every trace and reports each policy's ratio. Tradeoff: the Bélády pass is not cheap. Violation: "0.7 hit rate" is meaningless without the ceiling; you tune blind.
  • P9 — unsafe is local and audited. Rule: every unsafe block carries an invariant comment; Miri runs in CI; loom runs on concurrency tests. Tradeoff: CI minutes. Violation: an unaudited unsafe regression is UB that property tests on safe code cannot see.
  • P10 — The Rust API is the source of truth. Rule: bindings are projections; features land in Rust first. Tradeoff: binding lag. Violation: a Python-only feature has no conformance reference and drifts from the engine.
  • P11 — Eviction is O(1) amortised on the hot path. Rule: every policy's evict is amortised O(1) (LRU-K's priority-queue variant excepted, documented). Tradeoff: extra per-node bookkeeping. Violation: an O(N) scan at eviction collapses tail latency under memory pressure exactly when the cache is busiest.
  • P12 — Ghost state is bounded. Rule: every ghost list (2Q A1out, ARC B1/B2) has a hard cap proportional to capacity. Tradeoff: ghost evictions discard history. Violation: unbounded ghost lists leak memory that the byte budget never sees.
  • P13 — Time is monotonic. Rule: expiry uses Instant, never SystemTime; the wheel clamps backward clock jumps. Tradeoff: no wall-clock TTL semantics across reboots. Violation: a clock step backward resurrects expired entries (stale reads).
  • P14 — Determinism under test. Rule: hashers are seedable to a fixed seed in tests; conformance replays are bit-reproducible. Tradeoff: a test-only seed path. Violation: a flaky hit-rate that passes locally and fails in CI hides a real regression.

These are enforced at the type level where possible, by cargo deny / cargo geiger lints where not, by review where neither.

§8 Domain Model

The cache is a hash map plus an intrusive DLL plus a policy that decides which slot to evict. The domain objects are: Entry (key, value, weight, expires_at, policy state), Slot (a generational handle into the arena), Policy (the eviction strategy), Budget (bytes/weight ceiling), and Admission (the optional front filter).

8.1 Worked example (W-TinyLFU admission decision)

Cache at capacity. LRU proposes to evict victim V to admit candidate C.

  1. freq(V) = cms.estimate(hash(V)) → 3.
  2. freq(C) = cms.estimate(hash(C)) → 5.
  3. 5 > 3 ⇒ admit C, evict V. The doorkeeper Bloom is consulted first: on C's first-ever sighting the bit is unset, so C is rejected and the bit is set — a key must be seen at least twice before admission. On the second sighting the CMS comparison above runs.

8.3 Malformed / adversarial input

  • Zero-weight entry: rejected at insert (I2 would let the cache exceed budget without evicting).
  • Oversized value: weight > max_value_bytes rejected before allocation (memory-pressure attack mitigation).
  • Non-Serialize key with persistence on: runtime-rejected at builder time (persistence boundary).
  • Key controlled by an attacker to collide a shard: keyed hasher seeded at startup; seed never exposed (I12, hash-flooding mitigation).
  • Clock step backward: wheel clamps now_ms to previous (P13, I11).

8.4 Failure path

A loader panic inside refresh-ahead is caught with catch_unwind; the entry keeps its stale-but-valid value, loader_panic_total increments, and the cache does not crash. A snapshot read of a malformed length field is bounded (no unbounded allocation) and aborts the load, leaving the in-memory cache untouched.

  • Arena is a single contiguous Vec; cache-line packing of Node<K,V> (Drepper, §5) keeps push_front/unlink to one or two cache misses, not a pointer-chase through scattered Box allocations (ADR-02).
  • Free-list reuse avoids allocator churn on steady-state insert/remove cycles — no malloc/free call on the hot path once the arena is pre-sized.

0.8 Edge Cases

  • Arena exhaustion (all slots live, insert requested): must evict before allocating, never grow the arena silently (budget owns capacity, not the arena).

  • Concurrent free + alloc of the same slot index under a bug: caught by the generation mismatch, not by a crash (I4 defends this).

0.9 Failure Analysis

  • F2 (arena leak, I3): symptom is free-list count below baseline after equal alloc/free pairs; detected by the Phase-0 Miri smoke test in CI, not at runtime. Blast radius is an eventually-OOM cache; containment is the CI gate, since a leak is a build-time defect, not a runtime-recoverable one at this layer.
  • T6 (use-after-free in the unsafe DLL): the portfolio's worst-case failure; mitigated by confining unsafe to dll.rs, Miri in CI, loom on the sharded-mutex path (Phase 5), and cargo-fuzz on the DLL. Detected by a Miri/fuzz crash, never by a property test on safe code alone.
  • T12 (generation wrap collision): a wrapped generation colliding with a live slot's generation would resurrect a stale Slot as valid; defended by wrapping to 1 (never 0) over a 32-bit space that exceeds any single-process lifetime.

Phase 1 — Classical LRU

1.1 Objectives

Ship the simplest policy: hash map for O(1) lookup, DLL for O(1) recency, evict from the tail. Cache::builder().lru().capacity(N).build() conforms to a textbook oracle. Constraint introduced: the Policy trait (§11.5) and Cache<K,V> facade (§11.6) are fixed here and never change shape for later policies.

1.2 Detailed Implementation Steps

Applies P2 (algorithm-as-data), P7 (byte-aware budget), P11 (O(1) eviction). groupcache and lru-rs (§5) are the reference shapes. LruState is empty — the DLL position is the entire bookkeeping.

pub struct LruState;   // empty: DLL position is the state
// dispatched through Policy::{on_hit, on_insert, evict, on_remove}; head=MRU, tail=LRU
  1. map: HashMap<K, Slot> maps key→slot; head is MRU, tail is LRU.
  2. On hit: move slot to front; clone and return value (drop the map borrow before mutating — see 1.6).
  3. On insert: update-in-place + move-to-front if present; else evict-until-under-budget, alloc, push-front, map-insert.
  4. Evict: unlink tail, free arena slot, remove key from map.

1.3 Deliverable

src/policy/lru.rs, examples/lru-basic.rs, docs/algorithms/lru.md, benches/lru_get.rs. Operator-inspectable via lrulfu-cli replay --policy lru.

1.4 Acceptance Criteria

policy.lru conformance bucket green (order matches the OrderedDict oracle at every step, I1); ARC P1 trace hit-rate within 1e-4 of the public reference; lru_get microbench ≥ 100M ops/sec single-thread (M1).

1.5 Conformance Fixtures

Fixture Purpose Expected
OrderedDict oracle, Zipf ops order conformance iteration order matches every step (I1)
ARC P1 trace replay hit-rate parity within 1e-4 of public reference
existing-key insert moves to front recency correctness hit rate does not degrade over the run

1.6 Pitfalls

  • Forgetting move-to-front on existing-key insert: correct but hit rate decays silently. Test explicitly.
  • HashMap::get borrow blocks the move-to-front: read the slot, drop the borrow, then mutate.
  • over_budget is bytes-aware by default; a count-only cache uses weigher→1, never a special case in the policy (P7).

1.7 Performance Concerns

  • The hot path is one hash, one map lookup, one DLL move-to-front — three cache-line touches on a hit, not a scan (P11; M1's ≥100M ops/sec target is derived from exactly this cost).
  • move_to_front on every hit makes the DLL head/tail the hottest cache lines in the process; false-sharing across threads is why sharding (Phase 5) exists instead of a single global lock here.
  • Cloning V on every get is a correctness-over-throughput default; large V should be wrapped in Arc<V> by the caller — documented in docs/algorithms/lru.md, not solved inside the engine.

1.8 Edge Cases

  • Insert of a key already resident with a different value: update-in-place, still move-to-front (not treated as a fresh insert for budget accounting — I2 must still balance).
  • Capacity of 1: every insert evicts the sole resident; the DLL degenerates to a single node, still correct (property test covers capacity=1).
  • Concurrent single-shard access from multiple threads without the sharded wrapper: undefined by contract — Cache<K,V> is !Sync until wrapped by ShardedCache (Phase 5); a caller doing so is a type-system-caught misuse, not a runtime check.

1.9 Failure Analysis

  • F1 (map/DLL divergence, I1): LRU is where this invariant first becomes load-bearing — a bug here corrupts every downstream policy since they share the same map+DLL substrate. Detection: debug_assert! in insert/remove/evict plus the OrderedDict oracle; recovery is a map rebuild from a DLL walk, never silent continuation.
  • T2 (memory-pressure attack, partial): LRU alone has no max_value_bytes cap yet (that lands in Phase 7); a single oversized value can blow the byte budget until Phase 7's cap is in place — a documented gap in docs/architecture/threat-model.md, closed by Phase 7's acceptance gate, not this one.

1.10 Operational Notes

Metrics: lrulfu_cache_get_total{policy=lru,outcome}, lrulfu_cache_evict_total{reason}, hit-rate EWMA gauge. No migration concerns yet (API not yet released); rollback is reverting the commit. docs/algorithms/lru.md is the operator's first stop for "why did my hit rate drop" on this policy.

Phase 2 — O(1) LFU with counter buckets

2.1 Objectives

Implement the Pugh-Stevens O(1) LFU: a DLL of frequency buckets, each holding a DLL of nodes. Promote-on-access and eviction are both O(1), matching LRU's cost class (P11).

2.2 Detailed Implementation Steps

Applies P1, P11; Pugh (1990) and Cormen et al. (§5) for the heap-vs-bucket-list cost argument (Appendix I.1 derives the O(log N)→O(1) rephrasing in full). Textbook LFU is O(log N) via a heap; the bucket-DLL rephrasing makes it O(1).

pub struct LfuState { bucket: BucketSlot }              // back-pointer to frequency bucket
pub struct FrequencyBucket { count: u32, nodes_head: Slot, nodes_tail: Slot, prev: BucketSlot, next: BucketSlot }

BucketSlot is a distinct type from Slot so the compiler enforces the two-DLL distinction.

  1. Outer DLL of buckets sorted by count ascending; each node holds a LfuState.bucket back-pointer.
  2. On hit at count c: find/create the c+1 bucket after the current one, unlink node from old bucket, push to new bucket, update back-pointer, remove old bucket if empty.
  3. Evict: head bucket is lowest count; evict the tail node (LRU among tied counts) — two rewrites + one free.
  4. Pure LFU does not age; readers wanting aging are directed to W-TinyLFU (Phase 4).

2.3 Deliverable

src/policy/lfu.rs, docs/algorithms/lfu.md, benches/lfu_get.rs. Inspectable via lrulfu-cli replay --policy lfu and the lfu_bucket_count gauge.

2.4 Acceptance Criteria

policy.lfu conformance bucket green against Caffeine LFU (admission off) within 1e-4 hit-rate; lfu_get throughput within 20% of the LRU baseline (M1-relative); O(1)-cost property test shows linear (not quadratic) pointer-rewrite growth across 1-, 2-, 3-hit passes.

2.5 Conformance Fixtures

Fixture Purpose Expected
Caffeine LFU (admission off), Zipf hit-rate parity within 1e-4
hit all N keys 1×,2×,3× O(1) cost pointer rewrites scale linearly with hits, not quadratically
single-occupant bucket removal bucket lifecycle empty bucket unlinked exactly once

2.6 Pitfalls

  • Bucket DLL vs node DLLs are different DLLs; reuse of head/tail names invites bugs — BucketSlot vs Slot enforces the distinction.
  • Inserting a bucket between two existing buckets: the next-bucket count check is == not <=. Read the Stevens note literally.
  • Pure LFU's lack of aging is wrong for almost every modern workload (MM3); document prominently in docs/algorithms/lfu.md so no one ships it unmodified.

2.7 Performance Concerns

  • Bucket creation/deletion on every count transition is an arena-backed, allocation-free op, not a malloc — keeps the amortised cost O(1) per Cormen et al.'s bucket-list argument (§5, Appendix I.1).
  • Long-tail count distributions (many buckets with one node each) increase the outer-DLL length but never the per-op cost, since promotion always creates/finds exactly one adjacent bucket — no scan.
  • Cache locality is worse than LRU's single DLL (two levels of indirection: node→bucket→bucket-DLL); this is the 20%-of-LRU throughput budget in the acceptance criteria, not a bug.

2.8 Edge Cases

  • All keys tied at the same count when capacity is reached: eviction falls back to LRU-within-bucket (the bucket's own tail), never an arbitrary or undefined choice.
  • A key's count overflowing u32: treated as a capped max-count sentinel (no wraparound), documented in docs/algorithms/lfu.md.
  • Rapid insert/evict cycling at capacity 1 creates and destroys a bucket every operation — correctness-tested, and the amortised-O(1) claim still holds since bucket alloc/free is arena-backed.

2.9 Failure Analysis

  • F1-class (bucket/DLL divergence): an inconsistency between a node's LfuState.bucket back-pointer and its actual bucket membership is the LFU-specific instance of the map/DLL divergence class (I1); detected the same way — debug assertions plus the Caffeine-oracle property test — and recovered by a full rebuild from a bucket-DLL walk.
  • No dedicated Threat Model row: LFU introduces no new attack surface beyond the shared arena/DLL primitive (T6, Phase 0) and inherits the Phase-1 byte-budget gap until Phase 7 closes it (T2).

2.10 Operational Notes

Metrics: lrulfu_cache_evict_total{policy=lfu}, lfu_bucket_count gauge (a rising count with falling hit-rate is the fossilisation signal, MM3). Runbook guidance: a sustained high lfu_bucket_count with flat hit-rate suggests switching to W-TinyLFU (Phase 4) or ARC (Phase 3) rather than tuning pure LFU further.

Phase 3 — Multi-list algorithms: LRU-K, 2Q, ARC

3.1 Objectives

Separate recency from frequency by giving each its own list: LRU-K (K-th-reference distance), 2Q (A1in/A1out/Am), ARC (adaptive between recency and frequency). Constraint introduced: bounded ghost lists (P12) must hold from this phase onward.

3.2 Detailed Implementation Steps

Applies P11, P12 (bounded ghost state), I8, I9. O'Neil et al. (LRU-K), Johnson & Shasha (2Q), Megiddo & Modha (ARC) — §5. Appendix I.2 derives ARC's adaptation rule in full; Appendix I.5 tables the 2Q transitions. Read the ARC pseudocode literally — the competitiveness proof is what makes ARC worth its complexity.

pub struct LruKState { history: [u64; K], head: u8 }    // ring of last-K timestamps
pub struct TwoQState { list: TwoQList }                 // A1in | A1out(ghost) | Am
pub struct ArcState  { list: ArcList }                  // T1 | T2 | B1(ghost) | B2(ghost)
pub enum TwoQList { A1in, A1out, Am }
pub enum ArcList { T1, T2, B1, B2 }
  1. LRU-K: per key, a fixed ring of the last K reference times; eviction priority is the K-th most-recent (largest K-distance). K=1 is LRU; K=2 is the common variant. Ship the priority-queue variant (O(log N)/op, not the O(N)-eviction naive form).
  2. 2Q: A1in (recent FIFO, ~25% capacity), A1out (key-only ghost FIFO, ~50%), Am (frequent LRU). Miss not in A1out → A1in (spill FIFO tail to A1out). Miss in A1out → Am. Hit in A1in → do nothing. Hit in Am → MRU.
  3. ARC: budget c split by parameter p between T1 (recency) and T2 (frequency); ghosts B1, B2. Hit in B1 raises p by |B1|/|B2|; hit in B2 lowers p by |B2|/|B1|. Clamp p∈[0,c] (I9).

3.6 Pitfalls

  • ARC's adaptation is easy to sign-wrong; read the Megiddo-Modha pseudocode (Appendix I.2), not a blog summary.
  • 2Q's "do nothing on A1in hit" feels wrong and is correct — keys leak to A1out, where the next hit promotes them (Appendix I.5).
  • LRU-K K=1 == LRU; guard the naive path that costs more for no benefit. Document in docs/algorithms/lru.md.

3.7 Performance Concerns

  • ARC's four-list bookkeeping (T1,T2,B1,B2) costs roughly 40% more than LRU per op (M2's ≥60M ops/sec vs M1's ≥100M ops/sec) — the adaptive win is paid for in constant-factor overhead, not asymptotic complexity.
  • LRU-K's priority-queue variant is O(log N) per op, not O(1); the naive O(N)-eviction form is explicitly rejected (3.2 step 1) because it collapses tail latency under pressure (P11 violation).
  • Ghost lists (B1, B2, A1out) add pointer-only nodes to the arena; cheap per-entry but still occupy arena slots, which is why they must be bounded (P12) rather than merely "small in practice."

3.8 Edge Cases

  • ARC's p at the boundary (0 or c) must still allow ghost-list hits to move it back into range — the clamp (I9) is a safety net, not a normal operating point; a property test asserts p is not permanently pinned to a boundary under a mixed workload.
  • A key evicted from T1 that reappears while its ghost entry (B1) has already been trimmed (I8 bound exceeded): treated as a plain miss, not an error — history loss under a bounded ghost list is an accepted tradeoff (P12).
  • 2Q's A1out ghost hit racing a concurrent Am eviction of the same key (single-shard-only in this phase): resolved by single-shard mutual exclusion; true concurrent races are Phase 5's problem.

3.9 Failure Analysis

  • F4 (ARC p wedged, I9): symptom is hit rate degenerating to LRU-only behavior; detected by the mid-trace workload-flip property test in CI and by the arc_p_gauge clamp-alert in production; recovery is automatic (the clamp keeps p in range) but a sustained clamp condition should alert an operator to a pathological workload.
  • T8 (ghost-list growth): an unbounded ghost list would leak memory invisible to the byte budget (I2 cannot see key-only ghost entries); mitigated by the hard per-list cap (P12, I8) and detected via the ghost_entries{list} gauge.

3.10 Operational Notes

Phase 4 — Admission, CLOCK family, SIEVE

4.1 Objectives

Land the admission filter (W-TinyLFU = Bloom doorkeeper + 4-bit CMS) and the second-chance algorithms (CLOCK, CLOCK-Pro, CAR) plus SIEVE (2024). This is the densest phase: five algorithms plus a cross-cutting filter.

4.2 Detailed Implementation Steps

Applies P5 (admission as a separate pass), P8 (Bélády baseline), I7, I10. Einziger & Friedman (TinyLFU), Cormode & Muthukrishnan (CMS), Bloom (1970), Bansal & Modha (CAR), Jiang et al. (CLOCK-Pro), Zhang et al. (SIEVE) — §5. Bloom/CMS reuse the rank-70 implementation (ADR-22).

pub struct Cms { width: usize, depth: usize, table: Vec<u8>, increments: u64 }
impl Cms { pub fn observe(&mut self, key_hash: u64); pub fn estimate(&self, key_hash: u64) -> u8; fn age(&mut self); }

pub struct ClockState    { referenced: bool }
pub struct ClockProState { hot: bool, test: bool, referenced: bool }
pub struct CarState      { referenced: bool, list: ArcList }
pub struct SieveState    { visited: bool }

CMS: depth d≈4, width w≈capacity*8, 4-bit counters; age() halves every nibble ((b>>1)&0x77) every w*10 references (Appendix I.4 derives this). Estimate is the min across rows (I10).

  1. Doorkeeper Bloom: on admit, if the key's bit is unset, set it and reject — a key must be seen twice before entry (Bloom 1970, rank-70).
  2. CMS: increment on every reference; halve all counters periodically to forget cold history.
  3. W-TinyLFU admit: when full, compare freq(candidate) vs freq(victim); admit only if strictly greater (worked example §8.1). Sits in front of LRU by default; ARC and SIEVE as alternates (ADR-09).
  4. CLOCK: circular buffer, one referenced bit; hit sets the bit; evict advances the hand, clearing set bits, evicting the first clear.
  5. CLOCK-Pro: hot/cold/test categories, three hands; approximates LIRS in O(1) (Jiang & Zhang, LIRS, §5).
  6. CAR: two clocks T1/T2, ghosts B1/B2, ARC's adaptive p; one bit per slot instead of two pointers.
  7. SIEVE: single hand from the tail; on a visited slot clear the bit and continue; on an unvisited slot evict. Insertion at head, hand toward head — preserves insertion order (more LRU-like than CLOCK, Appendix I.3).

4.6 Pitfalls

  • CMS aging: a naive >> 1 leaks the high bit of one nibble into the next. Mask 0x77 after the shift (I10, Appendix I.4).
  • CLOCK-Pro's three hands can lap; handle two hands pointing at the same slot.
  • SIEVE's visited bit must be set on hit; forgetting it makes SIEVE behave like FIFO — a dramatic, silent hit-rate drop (Appendix I.3).

4.7 Performance Concerns

  • The admission pass adds one CMS query (2 hash computations × depth-4 rows) per candidate — cheap relative to a cache miss's downstream cost, but it is why non-admission policies must never pay for it (P5, I7).
  • SIEVE's single-bit, single-hand design is why M3 targets within 5% of LRU rather than parity — one fewer pointer than LRU's two, but a hand-walk over a run of visited bits can touch several nodes before evicting one, unlike LRU's O(1)-always tail pop.
  • CLOCK-Pro's three hands (hot/cold/test) triple the per-eviction pointer-chase versus plain CLOCK; acceptable because it approximates LIRS's much higher space cost in O(1) time instead.

4.8 Edge Cases

  • A candidate whose doorkeeper bit is already set but whose CMS estimate ties the victim's: ties resolve in favor of the incumbent (do not evict) — deterministic tie-breaking is required for replay determinism (P14).
  • CLOCK-Pro's "test" category expiring before a second reference arrives: demoted to cold without ever reaching hot, matching the LIRS approximation's intended behavior, not a bug.
  • SIEVE's hand reaching the head with every slot visited (all bits set): still terminates in one full sweep, clearing every bit and evicting the tail's predecessor — no infinite loop (property-tested at 1e6 ops).

4.9 Failure Analysis

  • F5 (CMS skew, I10): symptom is admission rejecting genuinely hot keys; detected via cms_overestimate_ratio trending toward 1.0 (should stay > 1.0); recovery is rebuilding the sketch and widening w. Blast radius is bounded to the admission-filtered policies (SIEVE/ARC-with-admission); plain LRU/CLOCK are unaffected because I7 isolates the blast radius by construction.
  • T9 (CMS underestimate): I10 is the structural defense — a sketch that ever underestimates would let admission starve legitimately hot keys; caught by the "CMS vs true counts" conformance fixture before it reaches production.

4.10 Operational Notes

Metrics: lrulfu_cache_admission_reject_total, cms_overestimate_ratio, lrulfu_cache_evict_total{policy,reason}. Runbook (docs/runbook/hitrate-drop.md) starts here: check admission_reject_total first, since a mis-tuned or skewed filter is the most common cause of a sudden hit-rate drop across the admission-filtered policies.

Phase 5 — Sharded concurrency

5.1 Objectives

Lift any policy to a contention-split cache: N independent shards, each guarded by a parking_lot::Mutex, shard = hash(key) & mask. Target ≥ 500M ops/sec on 16 cores, read-heavy (M4).

5.2 Detailed Implementation Steps

Applies P3 (sharding orthogonal), I12 (stable shard selection), ADR-04 (parking_lot), ADR-06 (xxhash3). Memcached and Ristretto (§5) for the sharded shape and get-batching.

pub struct ShardedCache<K, V> { shards: Box<[Shard<K, V>]>, hasher: FxBuildHasher }
struct Shard<K, V> { cache: Cache<K, V>, lock: parking_lot::Mutex<()> }

impl<K: Hash + Eq + Clone, V: Clone> ShardedCache<K, V> {
    fn shard_for(&self, key: &K) -> &Shard<K, V>;     // hash(key) & (len-1)
    pub fn get(&self, key: &K) -> Option<V>;
    pub fn insert(&self, key: K, value: V) -> Option<V>;
}
  1. Shard count is a power of two; & mask selects the shard.
  2. Each shard holds a single-shard Cache mutated under its lock; the interior-mutability pattern is audited under loom.
  3. len() and clear() are best-effort cross-shard approximations, documented as such (iterating under a global lock kills the throughput benefit).
  4. Seed the hasher once at startup; never re-seed live (I12).

src/shard.rs, docs/architecture/sharding.md, benches/sharded_concurrent.rs, examples/sharded-concurrent.rs. Inspectable via shard_load_histogram during a load test.

5.4 Acceptance Criteria

loom 16-reader/4-writer suite green (1000 iterations, no race, no deadlock); ≥ 500M ops/sec on the reference 16-core host, 95/5 read-heavy mix (M4); no shard carries > 2× the mean load (I12).

Fixture Purpose Expected

5.6 Pitfalls

  • A poor hash clusters keys onto a subset of shards and silently halves throughput; xxhash3, not DefaultHasher.
  • Shard count must be a power of two for the & mask fast path; default 16 or 32.
  • Cross-shard iteration under a global lock kills the benefit; document len/clear as approximate.

5.7 Performance Concerns

  • Per-shard lock-wait budget (Back-of-Envelope #6) is 32 ns/op mean at 16 shards / 500M target — leaving headroom under the 20 ns p50 only if contention stays low, which is the entire justification for sharding over a single global lock.
  • parking_lot::Mutex is chosen over std::sync::Mutex specifically for uncontended-lock speed (ADR-04) — the sharded design's throughput claim assumes this, not a generic mutex.
  • Shard imbalance (a hot key concentrating traffic on one shard) degrades to single-shard throughput for that key's traffic — no algorithm fixes this; only a better hash or explicit hot-key handling (out of scope) helps.

5.8 Edge Cases

  • A single ultra-hot key on one shard while the other 15 shards are idle: throughput for that key is bounded by single-shard performance; the aggregate M4 target assumes a reasonably distributed key space, not a single-key hotspot (documented, not solved here).
  • len() called concurrently with in-flight inserts across shards: returns a best-effort approximate sum, never blocks, never panics — the approximation is a documented contract, not a bug.
  • Shard count changed between process restarts (e.g., a config change): invalidates any persisted shard-affinity assumptions; the hasher reseeds at startup (I12), so key→shard mapping is not guaranteed stable across restarts.

5.9 Failure Analysis

  • F9 (shard hotspotting, I12): symptom is one shard's lock_wait_seconds dominating; detected by the shard-load histogram; recovery is verifying the hasher (not a config bug) and, if the key distribution itself is skewed, considering a larger shard count at the next restart.
  • T1 (hash flooding): an attacker crafting keys to collide one shard collapses throughput to single-shard levels; mitigated by a keyed hasher seeded at startup and never exposed (I12); detected via shard_load_histogram skew, distinguishable from a genuine hot-key shift by the skew appearing across many distinct keys rather than one (Hard Q18).

5.10 Operational Notes

Metrics: shard_load_histogram, per-shard lock_wait_seconds histogram, aggregate throughput counter. This is also where the Threat Model's hash-flooding detection lives operationally (T1): an on-call engineer distinguishes an attack from an organic hot key by checking whether the skew concentrates on one shard across many keys (attack) or many shards funnel to one key (organic). No deployment/migration surface yet (in-process).

Phase 6 — TTL and the timer wheel

6.1 Objectives

Per-entry absolute expiry via a hierarchical timer wheel ticked on op; 1M entries at 1s TTL expire within 100 ms (M8).

6.2 Detailed Implementation Steps

Applies P4 (per-entry TTL), P13 (monotonic time), I11, ADR-10 (hierarchical wheel), ADR-23 (optional Event-Loop reuse). The wheel is what Linux uses internally for timers.

pub struct TimerWheel { levels: Vec<Wheel>, now_ms: u64 }
struct Wheel { buckets: Vec<DllHead<Slot>>, bucket_size_ms: u64 }
impl TimerWheel { pub fn schedule(&mut self, slot: Slot, expires_at_ms: u64); pub fn tick(&mut self, now_ms: u64) -> Vec<Slot>; }
  1. Levels: 1024 buckets at 1 ms, 1024 at 1 s, 1024 at 1024 s, …; an entry lives in the coarsest level until its bucket cascades down.
  2. On insert with TTL, expires_at = now + ttl; place in the appropriate level bucket.
  3. Tick-on-op by default: every op calls wheel.tick(now()) first; amortised O(1) since most ticks process zero buckets.
  4. Background-thread tick behind feature flag background-ticker for low-op-rate caches.
  5. On get, check expires_at <= now directly (I11) — do not rely on the wheel having processed the bucket.

6.6 Pitfalls

  • Wall-clock is not monotonic; use Instant, clamp backward jumps (P13).
  • A get after expiry but before the next tick must be a miss, not a hit — check expires_at directly.
  • Cascading is the source of most timer-wheel bugs; test every level transition explicitly.

6.7 Performance Concerns

  • Tick-on-op amortises to O(1) because most ticks touch zero buckets (Back-of-Envelope #7: 1024³ ms ≈ 12.4 days of range at 1 ms base resolution) — the cost only shows up on the op whose tick crosses a bucket boundary.
  • The background-ticker feature flag exists because a low-op-rate cache would otherwise let expired entries linger indefinitely without a periodic external tick — a throughput/latency tradeoff the operator chooses explicitly.
  • 1M expiries in one tick (M8) requires the drain loop to be allocation-free per expired slot; a Vec<Slot> return from tick() is pre-sized from the bucket's known occupancy, not grown incrementally.

6.8 Edge Cases

  • Clock stepped backward (NTP correction, VM pause/resume): now_ms is clamped to the previous value, never allowed to move a wheel position backward (P13, I11).
  • TTL longer than the wheel's total range (12.4 days at the default resolution): rejected at builder time or requires a coarser top-level bucket size, documented in docs/architecture/ttl.md.
  • An entry re-inserted with a new TTL while still scheduled in an old bucket: the old schedule is invalidated (generation-tagged, reusing the Slot generation mechanism from Phase 0) so a stale wheel entry never expires a live node.

6.9 Failure Analysis

  • F6 (timer-wheel cascade bug): symptom is entries expiring late or never; contained by the property test covering every level transition explicitly (6.6); recovery in production is reaping on the next op via the direct expires_at check (I11), a safety net independent of the wheel's own correctness.
  • F12 / T5 (clock step backward): stale reads would violate the TTL contract (P13); the wheel clamps now_ms, and expired_on_read_total telemetry surfaces any case where a read momentarily saw a not-yet-reaped expired entry.

Phase 7 — Byte budgets, weights, write modes, refresh-ahead

7.1 Objectives

Byte-default budget with custom weigher; write-through/back/around; refresh-ahead with singleflight coalescing. Closes the T2 memory-pressure gap left open since Phase 1.

7.2 Detailed Implementation Steps

Applies P7 (byte-aware), P6 (no silent fallback), I2, I13. groupcache's singleflight (§5) for refresh coalescing; ADR-11 (bytes default).

  • Weigher returning 0 lets the cache exceed budget without evicting; reject weight==0.
  • Write-back queue must be bounded; configurable high-water + backpressure (block/drop/error).
  • Refresh-ahead can trigger redundant loader calls; coalesce per key (singleflight).

7.7 Performance Concerns

  • The weigher runs once at insert and is cached, not recomputed on every hit (P11) — an expensive user-supplied weigher only costs once per entry lifetime, not once per access.
  • Write-back's async drain means the write-path latency the caller sees is enqueue-only; backend write latency is decoupled, at the cost of the bounded-queue backpressure risk (I13, T7) under sustained pressure.
  • Singleflight coalescing turns N concurrent refresh requests for the same key into 1 loader call — without it, a thundering-herd refresh storm (F8) multiplies backend load by the shard's concurrent-reader count.

7.8 Edge Cases

  • A weigher that panics: caught the same way as a loader panic (catch_unwind), the insert fails cleanly rather than corrupting the budget accounting.
  • Write-back queue at exactly its high-water mark when a new write arrives: the configured backpressure policy (block/drop/error) decides, deterministically, not a race-dependent outcome.
  • Refresh-ahead loader returning a value for a key that was concurrently removed: the stale-but-valid entry is dropped silently (the removal wins), never resurrected by a late-arriving refresh.

7.9 Failure Analysis

  • F3 (budget drift, I2): used_bytes diverging from the true sum of live weights; detected by the byte-budget conformance fixture and, in production, by a periodic reconciliation walk; recovery is recomputing by full walk and failing closed (stop admitting) until reconciled.
  • F7 / T7 (write-back overflow): an unbounded write-back queue under sustained write pressure is a memory leak the byte budget cannot see (queue entries are not counted against used_bytes); bounded by a hard high-water mark with a configurable backpressure policy, detected via writeback_queue_depth.
  • F8 (loader storm): redundant loader calls under concurrent refresh amplify backend load; singleflight coalescing is the structural defense; a circuit-breaker on repeated loader failure is the containment for a genuinely failing backend.

8.1 Objectives

Periodic snapshot + append-only file for caches whose contents are expensive to repopulate. Deferred surface (ADR-17); the Phase-0 gate ships in-memory only — this phase is exercised when a deployment's RTO/RPO needs it (Deferred Features Register).

Applies the persistence trust boundary (§8.4, Threat Model T3/T10). Redis AOF cadence as the reference (fsync-every-second). bincode for the on-disk format (ADR-21).

Phase 9 — Bindings: Python, Java, WASM

9.1 Objectives

9.6 Pitfalls

  • PyO3 GIL discipline: calling back into Python from a Rust callback (e.g. a weigher) requires re-acquiring the GIL.
  • JNI local references are function-scoped; long-lived references must be promoted to global, and a leaked global is a memory leak.
  • WASM is single-threaded; the sharded cache reduces to single-shard — document it.

9.7 Performance Concerns

  • FFI marshalling (byte-array copies at every boundary crossing) is the binding tax; the Rust core's ≥100M ops/sec (M1) is never fully visible through a binding — each language's benchmark documents its own realistic ceiling, not the Rust number.
  • PyO3's GIL reacquisition for callback-heavy configurations (weigher, loader) serialises what would be parallel Rust-side work; documented as a binding-specific cost, not a core regression.
  • WASM's single-threaded reduction to single-shard means the sharding throughput story (M4) does not apply in the browser; a WASM deployment is bounded by single-shard, single-core throughput (M1-class, not M4-class).

9.8 Edge Cases

  • A Python weigher callback raising an exception: caught and converted to a Rust Result::Err, never allowed to unwind across the FFI boundary (undefined behavior otherwise).
  • A JNI caller failing to call close() on Cache: the Rust handle leaks until the JVM's finalizer (if any) or process exit; documented as a caller responsibility (AutoCloseable is advisory, not enforced).
  • A WASM cache instance surviving a page navigation without explicit teardown: garbage-collected by the browser's WASM linear memory reclamation; no explicit close() contract needed in that environment.

9.9 Failure Analysis

  • F11 (binding ABI breakage): a Rust API change that breaks a binding's assumptions is caught by per-binding integration tests gating merge, not discovered post-release; semver discipline on the Rust crate (Compatibility & Versioning) is the structural prevention.
  • T11 (binding type confusion): foreign data marshalled to the wrong type is prevented by construction — the FFI surface only ever exchanges byte-arrays, never typed pointers a foreign caller could misinterpret.

Scalability Analysis

  • Vertical (single node): throughput scales with shard count up to core count, then plateaus at memory-bandwidth and lock-wait limits. 16 shards on 16 cores hits 500M ops/sec read-heavy; beyond that the RCU reader path (deferred, ADR-05) is the next lever, expected 2–4× reader throughput at 30–50% more memory.
  • Capacity: entries scale with byte budget / (avg entry + ≤80 B overhead). At 64 GB and 1 KB entries that is ~59M entries (see Back-of-Envelope). The arena's Vec<MaybeUninit<Node>> grows amortised O(1); the free list bounds re-allocation.
  • CMS scaling: width w ≈ capacity × 8 at 4 bits/counter; the sketch is global (not per-entry), so its memory is independent of value size. At 1M-entry capacity, w ≈ 8M counters × 4 bits = 4 MB per row, ×4 rows = 16 MB.
  • TTL scaling: the hierarchical wheel is O(1) per op regardless of timeout range; 1M expiries process in a single tick under 100 ms.
  • Horizontal: out of scope here; the rank-61 cluster shards this engine across nodes via consistent hashing. The hooks (event subscription, capacity reporting, key migration) are documented in docs/architecture/cluster-hooks.md and anchored at PhaseDeferred("Deferred Features Register").
  • Bottleneck ladder: lock contention (→ shard) → memory bandwidth (→ smaller entries / compression) → CMS aging cost (→ tune age interval) → arena reallocation (→ pre-size from capacity).

Mental Models & First Principles

  • MM1 — A cache is a hash map + a DLL + an eviction policy. Predicts: every "new algorithm" is a new policy over the same two structures, so the DLL is built once and reused. Bug class without it: per-algorithm linked-list arithmetic that hides a use-after-free in each eviction path. Applied: §6 P1, Phase 0.
  • MM2 — The eviction decision is the only interesting bit. Predicts: lookup and storage are commodity; effort belongs in evict/admit/on_hit. Bug class: over-engineering the map while shipping a naive O(N) eviction scan. Applied: §6 P11, Phase 3–4.
  • MM3 — Frequency without aging is a trap. Predicts: pure LFU fossilises yesterday's hot key against today's viral one; every production frequency scheme ages. Bug class: a cache whose hit-rate silently rots as the workload shifts. Applied: Phase 2.2, Phase 4.2, Phase 2.6 Pitfalls.
  • MM4 — Admission, not just eviction, controls hit-rate. Predicts: deciding not to admit a one-hit-wonder beats evicting a useful entry to make room for it; this is why W-TinyLFU wins. Bug class: a cache that admits everything and thrashes on scans. Applied: §6 P5, Phase 4.2.
  • MM5 — Recency vs frequency is a dial, not a switch. Predicts: the best policy adapts the balance to the live workload (ARC's p, CAR). Bug class: a statically-tuned cache that is great on the benchmark and poor in production. Applied: Phase 3.2, §7 I9.
  • MM6 — Insertion order is information. Predicts: SIEVE beats CLOCK because it preserves insertion order while approximating LRU with one bit. Bug class: treating SIEVE's hand like CLOCK's and getting FIFO behaviour. Applied: Phase 4.2.
  • MM7 — The hash function is a performance feature. Predicts: a poor hash clusters shards and halves throughput before any algorithm runs. Bug class: blaming the policy for a contention problem. Applied: §6 P14, Phase 5, I12.
  • MM8 — Measure against the ceiling, not the neighbour. Predicts: only the Bélády optimum tells you whether 0.7 hit-rate is good; comparing to LRU just compares two guesses. Bug class: shipping a "win" that is far from achievable. Applied: §6 P8, Performance M5–M7.
  • MM9 — unsafe is a budget, not a tool. Predicts: concentrating all unsafe in one fuzzed, Miri-checked file makes the whole engine auditable. Bug class: UB that safe-code property tests can never see. Applied: §6 P9, I14, Phase 0.
  • MM10 — Time is a hostile input. Predicts: wall-clock jumps backward; only monotonic time is safe for expiry. Bug class: stale reads after an NTP step. Applied: §6 P13, I11, Phase 6.6.

Back-of-Envelope Capacity Model

All numbers derive step-by-step from the §4 constraints table.

  1. Entries at 64 GB, 1 KB entries. 64 GiB / (1024 B value + 80 B overhead) ≈ 68.7e9 / 1104 ≈ 62.2M entries. With map + arena slack (~5%), ~59M entries.
  2. Per-entry overhead share. 80 B / 1104 B ≈ 7.2% of RAM is bookkeeping at 1 KB values; at 64 B values it is 80/144 ≈ 55% — the regime where count-budget reasoning misleads (P7).
  3. CMS memory (per §4 capacity). width w = capacity × 8; at 59M entries, w ≈ 472M counters × 4 bits = 236 MB/row × 4 rows = 944 MB — so the sketch is sized to a target capacity (e.g. 1M), not raw RAM: 1M×8×4bits×4rows = 16 MB.
  4. CMS aging interval. age every w × 10 references; at w = 8M, that is 80M references between halvings — at 100M ops/sec, roughly every 0.8 s.
  5. Shard count. target 500M ops/sec ÷ 100M ops/sec per single-thread LRU = 5 cores of useful work; round up to a power of two ≥ core count → 16 shards on a 16-core host (matches §4).
  6. Per-shard lock-wait budget. at p99 ≤ 200 ns and 16 shards, each shard handles 500M/16 ≈ 31.25M ops/sec, i.e. 32 ns/op mean service time — leaving headroom under the 20 ns p50 target only if contention is low (justifies sharding).
  7. TTL wheel buckets. 1024 buckets/level × 3 levels covers 1024 × 1024 × 1024 ms ≈ 12.4 days at 1 ms base resolution — comfortably above the 1-day max TTL in the Phase 6 test.
  8. TTL expiry throughput. 1M entries at 1s TTL all land in one second-level bucket; one tick frees them in ≤ 100 ms ⇒ ≥ 10M expiries/sec drain rate (M8).
  9. Startup arena pre-size. at 59M entries × 104 B node ≈ 6.1 GB arena allocation; pre-sizing it in ≤ 5 ms requires Vec::with_capacity (no per-entry alloc) — 6.1 GB / 5 ms ≈ 1.2 TB/s zeroing, so the arena uses MaybeUninit (no zeroing) to meet the startup budget.
  10. Bélády baseline cost. computing the offline optimum is O(N log N) in trace length per trace; for a 10M-access trace that is ~10M × 23 ≈ 230M ops, ≈ 2.3 s at 100M ops/sec — fits inside the 5-min conformance budget (M10) across the bundled corpus.
  11. Write-back queue bound. at a 5% insert rate of 500M ops/sec = 25M inserts/sec; a 1 s drain budget caps the queue at 25M entries high-water — far above any reasonable backend drain rate, so the bound is set by memory, not throughput (I13).
  12. FD budget check. persistence uses ≤ 4 FDs (snapshot temp, AOF, rotation target, metrics endpoint), within the §4 budget; bindings add none (in-process).

Alternative Architectures (Roads Not Taken)

A1 — Single-threaded event loop (Redis shape).

[clients] → [single thread: command loop → policy → store] → [reply]

Wins when the cache is a network data-structure server and predictable single-thread semantics + rich types matter more than raw multi-core throughput. Embodied by Redis. Rejected here because this is an in-process library primitive; a single event loop would cap multi-core throughput and force an async boundary the embedding application does not want.

A2 — Lock-free epoch-reclaimed reader path (Caffeine shape).

readers → [striped ring buffers] → [async maintenance thread → policy mutation]

Wins on read-dominated workloads inside a managed runtime where async batched eviction amortises maintenance and lock-freedom dominates. Embodied by Caffeine. Rejected for v1 (deferred, ADR-05) because correct-then-fast: an epoch-reclamation bug atop an unverified mutex path is far costlier to debug than the throughput it buys. Un-defers when reader throughput is the binding constraint.

A3 — Slab-allocated segmented LRU (Memcached shape).

[slab classes by size] → [per-class segmented LRU] → [item locks]

Wins for fixed-ish-size values at very large scale where slab fragmentation control beats admission cleverness. Embodied by Memcached. Rejected because the engine targets arbitrary (K,V) with a byte-aware weigher and a policy zoo; slab classes would constrain the value model and add fragmentation accounting the arena avoids.

A4 — Sampling-based approximate eviction (Redis maxmemory shape).

on evict: sample k random keys → evict the worst by recency/frequency estimate

Wins when exact recency/frequency ordering is too expensive and approximate is good enough at huge key counts. Embodied by Redis allkeys-lru. Rejected because the engine's intrusive DLL makes exact O(1) eviction cheap, and the conformance suite demands tight hit-rate parity (1e-4–5e-3) that sampling cannot guarantee against the reference oracles.

Glossary

  • 2Q: multi-queue policy with A1in (recent FIFO), A1out (key-only ghost), Am (frequent LRU).
  • A1in / A1out / Am: the three 2Q queues; new arrivals, ghost evictions, and the frequent set.
  • Admission filter: a pass that decides whether to store a candidate at all, in front of eviction (TinyLFU here).
  • AOF (append-only file): a log of every insert/remove, replayed to recover cache state.
  • Arena: the contiguous owner of every Node<K,V>, with O(1) slot alloc/free.
  • ARC: Adaptive Replacement Cache; two recency lists, two ghost lists, one adaptive parameter p.
  • Bélády optimum: the offline optimal policy; evicts the entry whose next reference is furthest in the future.
  • Bloom doorkeeper: a Bloom filter requiring a key to be seen twice before admission.
  • BucketSlot: a slot type distinct from Slot, indexing the LFU frequency-bucket DLL.
  • CAR: Clock with Adaptive Replacement; the CLOCK approximation of ARC.
  • CLOCK: circular-buffer second-chance approximation of LRU with one referenced bit per slot.
  • CLOCK-Pro: the CLOCK approximation of LIRS; hot/cold/test categories, three hands.
  • CMS (count-min sketch): a probabilistic frequency estimator; min over d hashed rows, never underestimates.
  • Conformance bucket: one named test group in the conformance suite with a pass criterion and tolerance.
  • Doorkeeper: see Bloom doorkeeper.
  • DLL: doubly-linked list; the structure every classical replacement algorithm rests on.
  • EWMA: exponentially-weighted moving average; how the hit-rate gauge is computed cheaply.
  • Generation tag: the counter on a slot that distinguishes a recycled slot from a stale pointer.
  • Ghost entry: a key without its value, retained so a future access can be recognised as a recent eviction.
  • Hierarchical timer wheel: a multi-level timer structure giving O(1) scheduling over any timeout range.
  • Hit ratio: fraction of get calls that found the key.
  • Intrusive list: a list whose pointers live inside the element nodes, not in separate list cells.
  • K-distance (LRU-K): time since a key's K-th most-recent reference; LRU-K's eviction priority.
  • LFU: Least Frequently Used; evicts the lowest access count.
  • LIRS: Low Inter-reference Recency Set; the policy CLOCK-Pro approximates.
  • Loom: the Rust concurrency-permutation testing tool used on the sharded path.
  • LRU: Least Recently Used; evicts the tail of the recency DLL.
  • LRU-K: LRU variant tracking the K-th most-recent reference.
  • MaybeUninit: the Rust type letting the arena allocate node storage without zeroing.
  • Miri: the Rust interpreter that checks unsafe code against borrow-checker semantics.
  • MRU: Most Recently Used; the head of the recency DLL.
  • PhaseDeferred: the anchor marking a surface deferred to a later phase, here "Deferred Features Register".
  • Policy: the eviction strategy trait every algorithm implements.
  • PolicyState: the per-node tagged union holding the active policy's private bookkeeping.
  • Refresh-ahead: asynchronously reloading an entry near expiry to avoid a cache-fill stampede.
  • RPO (recovery point objective): the maximum data loss window; ≤ 1 s at AOF fsync-every-second.
  • RTO (recovery time objective): the maximum recovery time; ≤ 30 s here.
  • Sealed: the much-later end-state defined by INSTRUCTIONS.md (portfolio root, sec. 8.1), reached by future sessions.
  • Sharded cache: a cache split across N independently-locked sub-caches; shard = hash(key) & mask.
  • SIEVE: the 2024 single-hand, one-bit eviction algorithm that preserves insertion order.
  • Singleflight: coalescing concurrent identical loads into one in-flight call.
  • Slot: a generational handle into the arena, used as the node pointer by every policy.
  • TinyLFU: the frequency-based admission filter; the W variant adds a small recency window.
  • TTL (time to live): an entry's per-entry absolute expiry time.
  • Weigher: a user function returning a (K,V) pair's weight (typically bytes), consumed by the budget.
  • Write-around: write only to the backing store; populate the cache lazily on the next read.
  • Write-back: write to the cache and queue an async write to the backing store.
  • Write-through: write to both cache and backing store before returning.
  • W-TinyLFU: the windowed TinyLFU admission scheme Caffeine ships.
  • xxhash3: the fast non-cryptographic key hash (ADR-06).

Prose and state-table derivations of the load-bearing eviction mechanics. These are the notes a reader should internalise before reading the source.

I.1 Why textbook LFU is O(log N) and the bucket variant is O(1)

The natural LFU data structure is a min-heap keyed by access count: find-min is O(1) but the increment-on-hit is a sift, O(log N). The Pugh-Stevens rephrasing replaces the heap with a doubly-linked list of frequency buckets, each bucket holding the set of keys at exactly that count. The buckets are sorted ascending by count. Three facts make every operation O(1):

  1. Promote-on-hit. A key at count c moves to the c+1 bucket. That bucket is either the immediate successor of the current bucket (if it already exists at count c+1) or is created and spliced in immediately after. Both are constant-pointer operations because the key already knows its bucket via the LfuState back-pointer.
  2. Eviction. The lowest-count bucket is the list head; its tail node is the least-recently-used among keys tied at that count. Evicting it is one unlink plus one arena free.
  3. Bucket lifecycle. When the last key leaves a bucket, the bucket is unlinked. No scan is needed because the bucket's node count is maintained incrementally.

The subtle line is the successor check: the new bucket is the existing successor only if its count equals c+1 exactly (==, not <=); otherwise a fresh bucket is spliced between the current bucket and its successor.

I.2 ARC adaptation, derived

ARC partitions a budget c into T1 (entries seen once recently) and T2 (entries seen at least twice). Ghost lists B1 and B2 remember keys recently evicted from T1 and T2. The single tunable p is the target size of T1; T2 targets c - p. The adaptation responds to which ghost list a miss hits:

Miss hits Interpretation p adjustment
B1 (key we evicted from T1) T1 was too small; recency matters more `p ← min(p + max(1,

The clamp keeps p ∈ [0, c] (I9). The genius is that the workload tunes p itself: a recency-dominant stream keeps hitting B1 and drives p up toward c (ARC → LRU); a frequency-dominant stream hits B2 and drives p down (ARC → LFU-like). No manual knob, and the paper proves competitiveness with offline LRU.

I.3 SIEVE traversal, derived

SIEVE keeps one visited bit per entry and one hand. Insertion is always at the head. The hand starts at the tail and walks toward the head:

Hand sees Action
visited bit set clear the bit, advance the hand one step toward the head
visited bit clear evict this entry; leave the hand at its predecessor

On a hit, the entry's visited bit is set (and the entry does not move). Because insertion order is preserved and the hand sweeps toward the head clearing bits, recently-inserted entries near the head get a chance before older entries near the tail — this is what makes SIEVE more LRU-like than CLOCK, which sweeps a fixed circle and loses insertion order. The one-line trap: forget to set the bit on hit and SIEVE degrades to FIFO with a dramatic, silent hit-rate loss (Phase 4.6).

I.4 The CMS aging step, derived

The 4-bit count-min sketch packs two counters per byte. Aging halves every counter to forget cold history. A naive byte >> 1 is wrong: it shifts the byte, so the low bit of the high nibble bleeds into the high bit of the low nibble. The correct operation halves each nibble independently — shift right by one, then mask 0x77 to clear the bit that crossed the nibble boundary in each half-byte. This is the two->>-and-a-mask the §2 mastery bullet refers to (Phase 4.6, I10).

I.5 2Q transitions, full table

State Event Transition
not cached, key ∉ A1out miss insert into A1in (spill A1in FIFO tail → A1out if A1in full)
not cached, key ∈ A1out miss remove from A1out; insert into Am (evict Am LRU tail if full)
in A1in hit do nothing (keys leak to A1out, where the next hit promotes them)
in Am hit move to Am MRU
in A1out (ghost) — key-only; no value stored; bounded by K_out

The counter-intuitive "do nothing on A1in hit" is correct: A1in keys are too new to know whether they belong in Am, so 2Q holds them at FIFO until they leak into A1out, where a subsequent hit is the signal that promotes them to the frequent set.

Insertion at head; hand from tail. After step 4 (A hit) A's visited bit is set without moving it.

Step Op Order head→tail (visited) Victim
3 C miss C(0) B(0) A(0) full
4 A hit C(0) B(0) A(1) bit set, no move
5 D miss D(0) C(0) B(0) hand from tail: A(1)→clear, B(0)→evict? — A was visited, cleared; B unvisited → evict B

8 E miss E(0) B(0) D(0) evict D
Final: {E,B,D}. SIEVE preserves insertion order and gives A a second chance via the visited bit — the divergence from FIFO.

L.4 W-TinyLFU admission (capacity 3, on top of LRU)

At step 8, the LRU victim would be the tail. The CMS frequencies (from the doorkeeper + sketch over the sequence) give A the highest estimate. When E arrives as a candidate, admission compares freq(E) (low, first sighting → doorkeeper rejects E and sets its bit). E is not admitted on its first appearance; the cache retains its existing warm set. This is the admission win: a one-hit candidate does not evict a warm entry. Had E appeared a second time, the CMS comparison freq(E) vs freq(victim) would decide.

The four policies diverge on exactly the keys the literature predicts: LRU optimises pure recency, LFU protects the frequently-hit A, SIEVE gives a cheap second chance preserving insertion order, and W-TinyLFU refuses to let cold one-hit candidates evict warm entries.

Appendix M — W-TinyLFU Window/Main Partition

The "W" in W-TinyLFU is the small recency window in front of the frequency-filtered main region. The cache budget splits ~1% window (a plain LRU admitting everything) and ~99% main (the SLRU protected by TinyLFU admission). New keys enter the window; on window eviction, the candidate is offered to the main region's admission filter, which compares its CMS frequency against the main victim. This gives recency a foothold (a freshly hot key is not starved by the frequency filter) while the frequency filter governs the bulk. Caffeine tunes the window/main split adaptively; this engine ships a fixed 1/99 split in Phase 4 and lists adaptive window sizing in the Deferred Features Register (anchored at PhaseDeferred("Deferred Features Register")). The window is why W-TinyLFU outperforms a bare TinyLFU on bursty traces where a key goes hot before its frequency estimate catches up.

R.2 Trace format

Replay seeds the hasher to a fixed value (P14) so a given (trace, policy, capacity) triple produces a bit-identical stats snapshot on every host. This is what lets the conformance suite assert hit-rates within 1e-4: the numbers are not host-dependent. A non-deterministic replay (unseeded hasher, wall-clock TTL) is a bug, not a tolerance.

Appendix S — Synthetic Trace Generators

The bundled synthetic generators live beside the real corpora and produce the adversarial workloads the real traces do not always cover. Each is a deterministic function of a seed so the generated trace is reproducible.

Generator Parameters What it stresses
Zipf alpha (default 0.99), key-space (default 1M), length the common skewed-popularity case; the baseline every policy must handle
Scan sequential key range, no reuse the LRU pathology — a one-pass scan that evicts the entire warm set; W-TinyLFU and ARC must resist it
Recency-bursty burst size, period recency that shifts periodically; ARC's p must track it (I9)
Churn new-key rate a steady stream of never-reused keys; admission (Phase 4) must reject them

The scan generator is the most important diagnostic: a policy whose hit-rate collapses on the scan trace but is fine on Zipf has a scan-resistance bug (LRU is expected to collapse here; ARC, W-TinyLFU, and SIEVE are not). The churn generator validates the doorkeeper Bloom (Phase 4.2): a correct doorkeeper rejects the churn keys on first sighting and the warm set is undisturbed, while a broken one admits everything and thrashes.

Appendix T — Conformance Tolerance Rationale

The tolerance per bucket is not arbitrary; it reflects how tightly the engine can match each reference and why.

Bucket Tolerance Why this value
LRU, LFU 1e-4 the oracle is exact (OrderedDict / deterministic counts); only floating-point hit-rate rounding separates them
LRU-K, 2Q, ARC, CLOCK, CAR 1e-3 the reference is a published paper table or a re-implementation; small differences in tie-breaking and ghost-list sizing are expected
W-TinyLFU, SIEVE, CLOCK-Pro 5e-3 the reference (Caffeine, the SIEVE paper) uses probabilistic structures (CMS, Bloom) whose seed and aging schedule differ from ours; 5e-3 absorbs the probabilistic slack without hiding a real bug
Bélády ratio ≥ 0.99 the floor is a quality bar, not a parity bar: the chosen policy must reach 99% of the offline optimum on its target workload class
CMS estimate 1+ε, never below I10 forbids underestimate; the overestimate slack is bounded by the sketch width

A bucket that needs a looser tolerance than the table above to pass is reporting a real regression, not a measurement artifact, and blocks merge.

Why Phase 0 is the root. Every policy is a wrapper around the DLL primitive (P1); a bug there is a bug in all ten policies, which is why its exit gate (Miri-clean leak test + fuzzed oracle) is the strictest. The Rust API must be stable and conformance-green before it is projected (P10); a binding built against a churning API just churns with it.

The single most expensive ordering mistake is shipping the lock-free reader path (deferred, ADR-05) before the sharded mutex path is correct: debugging an epoch-reclamation bug whose root cause is an incorrect mutex path is enormous and entirely avoidable. Correct-then-fast is the rule.
