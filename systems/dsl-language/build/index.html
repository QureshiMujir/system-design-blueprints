⬜ Phase 0 — Repository Skeleton & Toolchain Bootstrap §12

Objectives
  • Stand up governance scaffolding and all 13 crates/dirs from §1 as buildable stubs before any language logic exists (P13).
  • Make CI green before language work begins, so every later phase inherits a working pipeline.
  • Lock the dependency set and MSRV so later phases never renegotiate the toolchain mid-stream (ADR-01, ADR-25).
Deliverable

cargo build --workspace succeeds with all 13 crates/dirs present as stubs; make bootstrap build test lint returns 0; dsl --help prints the subcommand list from §1.

Acceptance
  • cargo build --workspace exits 0 with exactly 12 crates present (§10 count, excluding conformance/'s standalone runner).
  • cargo clippy --workspace -- -D warnings exits 0.
  • All 5 CI workflows registered and green on the first pushed commit.
  • cargo-deny check exits 0 against the dependency allow-list (ADR-25).
  • BUILD_PLAN.md's current-phase pointer names Phase 1 next, with Status: in progress.
Fixtures
Fixture Purpose Expected
bootstrap/workspace-manifest every crate in §10 appears in Cargo.toml members 12/12 present
bootstrap/empty-corpus conformance runner executes against zero fixtures exit 0, "0 of 0 passed"
Pitfalls
  • Skipping the crate-boundary structure and writing one giant crate — the boundaries enforce the module discipline §10 depends on.
  • Forgetting to seed BUILD_PLAN.md — every locked decision in §9 must be reflected there.
  • Committing Cargo.lock inconsistently across contributor toolchains — rust-toolchain.toml (ADR-01) is the single source of truth from commit one.

⬜ Phase 1 — Lexer §13

Objectives
  • Produce a span-aware, trivia-preserving lexer that never panics on any input (I12, P1).
  • Establish the token vocabulary that every later phase (Parser, Formatter) treats as normative.
Deliverable

dsl debug lex foo.lm prints the full token stream including attached trivia; the lexer never panics on the lex fuzz corpus.

Acceptance
  • 80+ positive and 40+ negative fixtures in conformance/fixtures/lex/ all pass.
  • Lex throughput ≥ 40 MB/s single-core on the M1 benchmark (§30).
  • fuzz.lex_crashes_total stays 0 across a 1-hour pre-merge soak (M13, I12).
Fixtures
Fixture Purpose Expected
lex/string-escapes every JSON-style escape plus \u{XXXXXX} exact token stream, no diagnostics
lex/unterminated-string recoverable error path one diagnostic, lexer continues past line
lex/invalid-utf8-boundary malformed byte sequence mid-token TokenKind::Error + diagnostic, no panic (I12)
lex/number-overflow integer literal exceeding i128 diagnostic, no silent wraparound
Pitfalls
  • Treating UTF-8 as bytes — column numbers must be code-point columns, not byte columns.
  • Discarding trivia — the Formatter (§20) and the LSP (§21) both depend on it.
  • Recovering by panicking — every lex error is a diagnostic, never a panic! (I12).

⬜ Phase 2 — Parser (Recursive Descent + Pratt) §14

Objectives
  • Turn the Phase 1 token stream into an arena-allocated AST (§11) with full source-location tracking.
  • Recover from syntax errors instead of aborting, so one bad line never hides every other diagnostic (P1, P11).
Deliverable

dsl debug ast foo.lm prints the AST as a tree; parsing round-trips through the Formatter (§20) on the full conformance corpus.

Acceptance
  • 140+ positive and 70+ negative fixtures in conformance/fixtures/parse/ all pass.
  • Parse throughput ≥ 15 MB/s single-core (M2, §30).
  • Round-trip property: format(parse(source)) == source for every fixture with canonical formatting already applied (I5-adjacent, verified fully in §20).
Fixtures
Fixture Purpose Expected
parse/operator-precedence full precedence table exercised AST matches expected shape exactly
parse/error-recovery-missing-brace one missing } mid-file 1 diagnostic, remaining items still parsed
parse/application-vs-field f x.y precedence lock parses as f (x.y)
parse/deeply-nested-record 200-level nested record literal parses without stack overflow (see 2.8)
Pitfalls
  • Synchronizing on the wrong token — an over-eager synchronizer eats half the file; pick conservatively, only structural punctuation that rarely appears mid-expression.
  • Using .unwrap() anywhere in the parser — every error path is recoverable and reported (P1).
  • Not preserving trivia through the parse — the Formatter (§20) needs it attached to AST nodes, not just tokens.

⬜ Phase 3 — Name Resolution & Modules §15

Objectives
  • Bind every identifier in the AST to its definition and build the file-is-module import graph (P5, I6).
  • Reject import cycles with a diagnostic naming the full cycle, not a stack overflow.
Deliverable

dsl debug resolve foo.lm prints the symbol table; the resolver rejects every cyclic-import fixture with a diagnostic naming the full cycle path.

Acceptance
  • 60+ fixtures in conformance/fixtures/resolve/ covering unresolved names, shadowing, imports, and cycles all pass.
  • 100% of unresolved-name fixtures within edit distance 2 of an in-scope name produce a "did you mean?" suggestion.
  • 0 DefTable lookup misses on the stdlib prelude across the full corpus.
Fixtures
Fixture Purpose Expected
resolve/shadowing inner let shadows outer inner binding wins, no diagnostic
resolve/unresolved-suggestion typo within edit distance 2 diagnostic includes the suggested name
resolve/import-cycle-3 a → b → c → a one diagnostic naming the full 3-hop cycle (I6)
resolve/canonical-path-cache two relative paths to the same file resolved to one cached module, not two
Pitfalls
  • Letting a typo propagate to a confusing type error downstream — catch it here with a specific suggestion, not in Phase 4.
  • Caching modules by relative path instead of canonical path — two different relative paths to the same file must resolve to one cached module (I6-adjacent correctness).
  • Resolving inside a deferred/lazy expression — resolution is non-deferred; the full scope is known at AST-walk time, never postponed to evaluation.

⬜ Phase 4 — Type Checker (HM, Rows, Sums) §16

Objectives
  • Implement Hindley-Milner inference with level-based generalization, row-polymorphic records, and anonymous sum types (ADR-05, P12).
  • Produce a diagnostic for every unification failure that names both types, both spans, and the inference path (P1).
Deliverable

dsl debug types foo.lm prints the inferred type of every top-level binding; every negative fixture's diagnostic is snapshot-tested byte-for-byte (ADR-10).

Acceptance
  • 200+ positive and 100+ negative fixtures in conformance/fixtures/types/ all pass.
  • Type-check throughput ≥ 4 MB/s single-core (M3, §30).
  • 100% exhaustiveness-checking accuracy on the match_expr negative corpus (no false-negative "non-exhaustive" report and no false-positive miss).
  • 0 typeck.occurs_rejections_total false negatives (every \x. x x-shaped fixture is rejected).
Fixtures
Fixture Purpose Expected
types/record/row-poly \r. r.foo applied to two differently-shaped records infers forall a r. {foo: a | r} -> a
types/error/unification let x : Int = "hello" ok: false, diagnostic snapshot byte-equal
types/error/occurs-check let f = \x. x x shaped input rejected, E-TYPE-OCCURS code
types/sum/exhaustiveness-miss match missing one tag diagnostic naming the unhandled tag
types/generalise/let-boundary polymorphic use of one let-bound identity function at two types both uses type-check independently
Pitfalls
  • Generalizing too eagerly (the value restriction) — generalize only at let boundaries over types with no free variables escaping the current level (I7).
  • Failing to occurs-check before linking — without it, unification loops forever (P12, I2).
  • Unifying records by reference rather than by row — records unify field by field plus tail row (I8), never as an opaque blob.

⬜ Phase 5 — Diagnostics Engine §17

Objectives
  • Implement the Diagnostic model (§11) and both the human (ariadne-backed) and JSON renderers sharing one value (P7).
  • Make every diagnostic actionable: primary span, optional secondary labels, a fix-oriented hint (P1).
Deliverable

dsl eval foo.lm produces rustc-grade human output on the negative corpus; dsl eval --format=json foo.lm produces LSP-shaped JSON consumed identically by lume-lsp.

Acceptance
  • 100% of conformance/fixtures/{lex,parse,resolve,types}/* negative fixtures have a byte-equal snapshot (ADR-10).
  • 0 diagnostics without a primary span across the entire negative corpus (I4, structurally enforced but verified here end-to-end).
  • Diagnostic render latency is O(message length) — no branch on span "interestingness" (T10, §24).
Fixtures
Fixture Purpose Expected
diag/human-multi-label 2 secondary labels + 1 note rendered output matches the insta snapshot
diag/json-shape same diagnostic, JSON renderer matches the LSP diagnostic JSON schema exactly
diag/stable-code a diagnostic code across two releases code string identical, message may improve
Pitfalls
  • Diagnostic messages without a primary span — always at least one (I4).
  • Help messages that contradict the error — a reviewer reads both before merging (P1, code-review discipline).
  • Stable codes that get repurposed — codes are semver-stable; a new failure mode gets a new code, an old code is never reused.

⬜ Phase 6 — Tree-Walking Interpreter & Capability Effects §18

Objectives
  • Evaluate the typed AST into JSON-shaped Values (§11) with strict, deterministic, left-to-right depth-first evaluation (I10).
  • Enforce the capability-based effect boundary end to end: no function invokes an effect its type does not accept as an argument (P3, I3, I14).
Deliverable

dsl eval examples/kubernetes-deployment.lm emits the expected JSON; dsl eval on a capability-missing fixture traps with a Diagnostic, never a host-level I/O error.

Acceptance
  • 150+ positive fixtures in conformance/fixtures/eval/ all pass; 40+ fixtures in conformance/fixtures/effects/ covering capability grant/deny all pass.
  • Evaluation throughput ≥ 2M reductions/sec on the arithmetic-dominated benchmark (M4, §30).
  • JSON output throughput ≥ 50 MB/s (M9, §30).
  • eval.ambient_capability_total stays 0 across the entire corpus (I14).
Fixtures
Fixture Purpose Expected
eval/kubernetes-deployment worked example (§8) JSON byte-equal to golden output
effects/missing-capability-fs-read §8's failure-path example Trap::MissingCapability diagnostic, no host I/O attempted
eval/float-equality Value::Float bitwise-equality semantics matches I11 exactly, not IEEE-754
eval/order-sensitive-side-effect left-to-right, depth-first evaluation order output order matches I10 across releases
effects/capability-leak-via-closure a closure attempting to smuggle a capability past its declared type rejected at type-check time (Phase 4), re-verified here at runtime
Pitfalls
  • Eval-order ambiguity — the evaluator commits to left-to-right, depth-first, and fixtures pin it (I10).
  • Stack overflow on deep records/lists — the evaluator iterates over fields without native recursion for traversal-only operations.
  • Capabilities leaking through closures — the type system catches this at Phase 4; the runtime double-checks at apply (I3) as defense in depth, per the Cloudflare-incident lesson above: a single unguarded path is a real, historically-demonstrated production risk.

⬜ Phase 7 — REPL §19

Objectives
  • Ship a multi-line REPL that shares the file compiler's exact parser, resolver, checker, and evaluator (P9, P11, I9).
  • Make the REPL's :type/:ast/:trace commands introspect the same pipeline a .lm file goes through.
Deliverable

dsl repl runs under tmux, ssh, and Windows Terminal; the REPL golden-output test suite covers every locked command (:type, :ast, :trace, plain evaluation).

Acceptance
  • The REPL test suite's golden outputs (conformance/fixtures/parse/ re-used for the three-front-end replay, I9) match byte-for-byte against dsl eval's output for the same input.
  • REPL startup latency ≤ 50 ms (shares M7, §30).
  • 0 parse.frontend_divergence_total incidents across a CI job re-running the full parse/* corpus through the REPL's entry point (I9).
Fixtures
Fixture Purpose Expected
repl/multiline-lambda a lambda split across 3 lines via trailing \ identical AST to the single-line equivalent
repl/type-command :type on a row-polymorphic function matches the Phase 4 inferred type exactly
repl/incremental-env 5 sequential let inputs each subsequent input sees all prior bindings, no re-evaluation of history
Pitfalls
  • A REPL parser that diverges from the file parser — they are, by construction, the same Parser instance shape (P11).
  • Re-running the entire history on every input — each input updates the environment in place, not from scratch.
  • Surfacing internal type representations — every type pretty-prints through the same renderer as dsl eval --format=json (§17).

⬜ Phase 8 — Formatter §20

Objectives
  • Ship a formatter that round-trips: format(format(x)) == format(x) for every corpus fixture (P6, I5).
  • Preserve every comment and doc-comment verbatim, attached via the Phase 1 trivia model.
Deliverable

dsl fmt --check examples/ returns 0 on already-formatted input; dsl fmt --write examples/ is idempotent on a second run.

Acceptance
  • 90+ fixtures in conformance/fixtures/fmt/ all pass the idempotency property test (I5).
  • Format throughput ≥ 10 MB/s (M5, §30).
  • 0 fmt.idempotency_failures_total across the full corpus (I5, §7).
Fixtures
Fixture Purpose Expected
fmt/idempotency-property run format twice over the whole corpus byte-identical second-pass output
fmt/doc-comment-preserved a doc comment attached to a let item comment text and attachment point unchanged
fmt/line-width-80 a record literal near the 80-column boundary breaks deterministically at the documented width
Pitfalls
  • Discarding trivia — doc comments must stay attached through formatting (Phase 1, P6).
  • Reformatting comments — comments are emitted verbatim; their attached trivia already encodes the whitespace they wanted (Phase 1).
  • Breaking lines inconsistently — the Doc combinator commits to one deterministic choice per shape, never a "whichever fits" ambiguity that could vary by renderer version.

⬜ Phase 9 — Language Server (LSP) §21

Objectives
  • Serve hover, go-to-definition, find-references, completion, and on-save diagnostics over JSON-RPC via tower-lsp (ADR-07).
  • Guarantee the LSP never blocks its main loop on one malformed document (I13).
Deliverable

dsl lsp --stdio works against any LSP 3.17-compliant client; a VSCode integration test exercises diagnostics, hover, and completion end to end.

Acceptance
  • LSP hover round-trip on a 10K-LOC file ≤ 100 ms (M6, §30).
  • 100% of conformance/fixtures/parse/ re-run through the LSP's entry point match the CLI's output (I9, three-front-end replay).
  • lsp.blocked_requests_total stays 0 across a fuzzed-malformed-document integration test (I13).
Fixtures
Fixture Purpose Expected
lsp/hover-inferred-type hover over a row-polymorphic binding matches Phase 4's inferred type exactly
lsp/goto-definition jump from a use site to its let correct file + line + column
lsp/malformed-json-rpc a crafted malformed request server logs and continues, does not crash (T4)
lsp/concurrent-malformed-doc one malformed open doc + a hover request on another hover succeeds unaffected (I13)
Pitfalls
  • Echoing a parse error to the LSP unchanged — translate to the LSP diagnostic shape via the shared Diagnostic JSON renderer (§17), never a bespoke format.
  • Sending diagnostics on every keystroke — debounce 200 ms (I13, §4).
  • Crashing on malformed JSON-RPC — every handler wraps in a recover boundary (T4).

⬜ Phase 10 — Test Runner & Conformance Harness §22

Objectives
  • Ship the embedded assert-block test runner (dsl test, P10) and the full YAML conformance harness pinning every normative semantic (§1 item 13).
  • Make a regression in any phase a mechanical CI failure, never a manual re-review.
Deliverable

dsl test runs every test_* binding in every .lm file under tests/ and emits a JSON report; conformance/runner run executes the full corpus and prints per-bucket pass/fail/deferred counts.

Acceptance
  • Full conformance corpus (700+ fixtures across all buckets, §1) runs in ≤ 60 s on the CI runner (M11, §30).
  • dsl test correctly reports 100% pass on a golden tests/ directory and correctly reports every intentional failure in a negative tests/ directory.
  • 0 fail buckets in conformance.report.json on main at all times.
Fixtures
Fixture Purpose Expected
test/assert-pass assert (1 + 1) == 2 test runner reports pass, exit 0
test/assert-fail-diff assert (1 + 1) == 3 test runner reports fail with a value diff, continues to remaining tests
conformance/deferred-bucket an effects/* fixture gated behind a Phase-11 capability reported as deferred, not fail, with a blueprint_ref
conformance/full-corpus-runtime the entire corpus in one run completes in ≤ 60 s (M11)
Pitfalls
  • Stopping at the first test failure — the runner always runs every test, so one broken fixture never hides ten others (P10).
  • Running tests in parallel while mutating shared state — tests are pure functions of their own .lm source; no test may depend on another's evaluation order.
  • Failing to distinguish deferred from fail in the conformance report — a deferred bucket blocks nothing; a failed bucket blocks merge.
