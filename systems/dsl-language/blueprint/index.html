1. Goal & Scope

Build Lume, a typed, total, capability-sandboxed configuration-and-pipeline DSL in the lineage of Nickel, Dhall, CUE, Bicep, and Jsonnet, implemented from scratch in Rust as the dsl CLI binary. The Phase 0 deliverable is a complete, conformance-tested pipeline — hand-written lexer → recursive-descent/Pratt parser → name resolver → level-based Hindley-Milner type checker with structural row-polymorphic records and sum types → strict tree-walking interpreter with capability-gated effects → rustc-grade diagnostics (human and JSON) — wired to a REPL, a round-tripping formatter, a minimal Language Server, an embedded test runner, and a YAML conformance suite that pins every normative semantic to a fixture.

In-scope Phase 0 deliverable — numbered crate/directory list:

  1. crates/lume-syntax — tokens, byte-precise Span, arena-allocated AST, trivia model.
  2. crates/lume-parser — hand-written recursive-descent parser with a Pratt operator-precedence sub-parser and synchronizing error recovery.
  3. crates/lume-resolve — lexical scope resolution, file-is-module import graph, cycle detection.
  4. crates/lume-types — Ty representation, row-polymorphic records, sum types, union-find unifier, level-based generalization.
  5. crates/lume-diag — Diagnostic model, human (ariadne-backed) renderer, JSON renderer.
  6. crates/lume-eval — strict tree-walking interpreter, capability-as-value effect system, thunked let rec.
  7. crates/lume-fmt — Wadler-Leijen pretty-printer, print-and-reparse round-tripping formatter.
  8. crates/lume-repl — multi-line REPL sharing the file compiler's parser/checker/evaluator.
  9. crates/lume-lsp — tower-lsp-based server: hover, go-to-definition, completion, on-save diagnostics.
  10. crates/lume-test — embedded assert-block test runner producing a JSON report.
  11. crates/lume-stdlib — list/string/map/number/json/yaml/regex/date/path builtins, wired behind capabilities where effectful.
  12. crates/lume-cli — the dsl binary: run, eval, fmt, lsp, test, repl, validate.
  13. conformance/ — a YAML fixture runner with 700+ positive and negative fixtures pinning every normative semantic.

System boundaries. Provides: lexing/parsing with error recovery, name resolution, HM type inference with structural records and sums, strict evaluation to a JSON-shaped Value, capability-gated effects, dual-format diagnostics, a REPL, a formatter, a minimal LSP, an embedded test runner, a YAML conformance harness. Delegates: process/thread scheduling to the host OS; container build/distribution to Docker; native codegen to the deferred bytecode VM and JIT (below). Does not provide in Phase 0: a bytecode compiler or VM, a JIT, a package manager/module registry, dependent types, algebraic effects, Salsa-based incremental compilation, or a tree-shaking minifier.

Non-goals: a general-purpose Turing-complete scripting language (crowded space, low marginal value); a query language in the Datalog/SQL sense (a separate project); a Lisp-family macro system (weaker diagnostics story than a typed surface syntax); matching Nickel/Dhall/CUE feature-for-feature; a hosted, multi-tenant compile-as-a-service offering (Phase 0 is a local CLI and a local LSP subprocess only, §3).

Deployment model: a single statically linked CLI binary (dsl), distributed as a distroless container image; the LSP runs as a subprocess spawned by the editor over stdio; there is no daemon or persistent server component in Phase 0.

Target users/operators: platform engineers authoring typed Kubernetes/CI/Terraform-shaped configuration; CI pipelines invoking dsl eval/dsl validate on untrusted contributor PRs; editor users via the LSP; sibling portfolio projects — the Virtual-Machine project (rank 31, bytecode VM stretch), the JIT-Compiler project (rank 51, JIT stretch), the Type-Checker project (rank 42, shared unification-engine design), the AST-Optimizer project (rank 43, a pre-pass reference for a future optimizing pipeline).

What later phases unlock: Phase 1 (post-Phase-0 roadmap) unlocks the bytecode compiler and VM execution (run co-equal against the tree-walker as a reference oracle), a content-addressed package manager, and Salsa-based incremental LSP recompilation. Phase 2 unlocks a tracing JIT over the bytecode and a tractable dependent-types extension for value-shape contracts.

Recommended language + rationale: Rust 1.78+ stable, edition 2021. Arena allocation (bumpalo) gives one-arena-per-compilation-unit lifetime discipline; exhaustive match over AST/Ty variants turns a missed case into a compile error rather than a runtime crash (directly enforces I1); the diagnostics ecosystem (ariadne) and zero-cost FFI for host-application embedding are mature. Rejected — OCaml: the closer academic lineage (Nickel and Dhall's own reference implementations are OCaml/Haskell) does not outweigh losing this workspace's Rust-shared unification-engine and bytecode-IR reuse with the Virtual-Machine, JIT-Compiler, Type-Checker, and AST-Optimizer sibling projects. Rejected — TypeScript: adequate for a reference config-language implementation (see Bicep) but no arena-allocation story and a materially weaker sandboxing guarantee against untrusted configuration. Rejected — Go: pre-generics Go lacks algebraic data types, making sound HM inference and exhaustive AST matching substantially harder to keep correct.

Prerequisites: Rust ownership/lifetimes/trait objects; grammars, recursive descent, and Pratt/precedence-climbing parsing; Hindley-Milner inference, unification, and generalization (Damas & Milner 1982); pattern matching over deeply nested AST shapes; Crafting Interpreters parts I–II read end to end before Phase 1.

Estimated timeline: Phase 0 in 14 weeks across 12 phases (Phase 0 Repository Skeleton 1 wk, Phase 1 Lexer 1 wk, Phase 2 Parser 1 wk, Phase 3 Name Resolution 1 wk, Phase 4 Type Checker 2 wk, Phase 5 Diagnostics 1 wk, Phase 6 Interpreter 2 wk, Phase 7 REPL 1 wk, Phase 8 Formatter 1 wk, Phase 9 Language Server 1 wk, Phase 10 Test Runner & Conformance 1 wk, Phase 11 Packaging & Release 1 wk); the full system (bytecode VM, JIT, package manager) in 3–6 additional months.

2. Why Build This

A from-scratch language is the closest thing in software to dimensional analysis: every choice has a cost, every shortcut compounds, and the system is small enough to reason about exhaustively.

  • Lexer/parser engineering. What a hand-written parser buys over a generator, how a Pratt parser (Pratt 1973) separates prefix/infix/postfix binding power from grammar shape, and how to make every error message actionable instead of "syntax error."
  • Type theory in code. Implementing Milner's 1978 polymorphism and the Damas-Milner 1982 principal-type algorithm, then watching them fail on a real AST and learning exactly which corner of the soundness proof (the occurs check, the value restriction) was skipped.
  • Effects and totality as a security model. A language that promises termination and sandboxing forces a confrontation with recursion (no general recursion, only structural induction), I/O (capabilities as values, not ambient authority), and unbounded data (row polymorphism is total; unconstrained forall x. x recursion is not).
  • Diagnostics as the product, not an afterthought. rustc-grade errors cost real engineering: span arithmetic, multi-label layout, and the precise difference between an error, a warning, and a help.
  • Tooling as a second language surface. A language is the IDE, the formatter, the test runner, and the REPL together — each is a small system, and divergence between them (P11) is the single most common real-world language-tooling bug class.
  • Cross-links. Sibling systems in this workspace study the same primitives from different angles: the Type-Checker project (rank 42) isolates HM inference alone; the AST-Optimizer project (rank 43) studies IR rewriting once a typed AST exists; the Virtual-Machine (rank 31) and JIT-Compiler (rank 51) projects are the deferred execution tiers this blueprint's bytecode ADR (ADR-15/16) explicitly reuses rather than reinventing.

What Mastery Looks Like — after building this system, an engineer can:

  • Hand-roll a span-preserving lexer and a Pratt operator-precedence parser without a parser generator, and explain why generated parsers fight custom error recovery (Phase 1 — Lexer, Phase 2 — Parser).
  • Implement Algorithm W with level-based generalization, row-polymorphic records, and a sound occurs check, and diagnose a unification failure by reading the inference path, not guessing (Phase 4 — Type Checker).
  • Design a capability-based effect system that encodes a sandboxing guarantee in the type system rather than in ambient authority, and reason about what a closure can leak (Phase 6 — Tree-Walking Interpreter & Capability Effects).
  • Render rustc-grade multi-label diagnostics in both a human terminal form and a machine JSON form from one shared Diagnostic value (Phase 5 — Diagnostics Engine).
  • Keep a REPL, an LSP, and a batch compiler from diverging by routing all three through one parser/checker/evaluator entry point (Phase 7 — REPL, Phase 9 — Language Server (LSP)).
  • Build a formatter as "the parser run backwards" and prove it with a round-trip property test rather than trusting it by inspection (Phase 8 — Formatter).
  • Pin every normative semantic of a language to a machine-checked fixture so a regression is a CI failure, not a support ticket (Phase 10 — Test Runner & Conformance Harness).

Lexer (lume-syntax) — converts UTF-8 source to a span-tagged token stream, preserving trivia (whitespace, comments) as token-attached data rather than discarding it; this is the substrate the Formatter depends on. Parser (lume-parser) — recursive descent for structure, a Pratt sub-parser for operator precedence, synchronizing error recovery so one syntax error never aborts the whole parse. Resolver (lume-resolve) — builds lexical scopes, resolves every identifier to a binding, walks the file-is-module import graph and rejects cycles (I6). Type Checker (lume-types) — Algorithm W with level-based generalization over structural row-polymorphic records and anonymous sum types; the occurs check (I2) is the soundness backbone. Diagnostic bus (lume-diag) — every phase boundary converts internal failure into a Diagnostic value with a primary span (I4); a human (ariadne) and a JSON renderer consume the same value (P7). Evaluator (lume-eval) — strict, environment-passing tree-walker; capabilities are ordinary values, wired only at the CLI's capability-construction boundary (P3, I14) — the trust boundary in the diagram. stdlib codecs (lume-stdlib) — pure functions from Value to JSON/YAML text; the only effectful builtins require a capability argument, and the regex builtin is deliberately bounded-backtracking (T9). REPL/Formatter/LSP — three thin wrappers around the same pipeline; the LSP is the one external-protocol, untrusted-input boundary (JSON-RPC over stdio, debounced 200 ms, I13) besides file input itself. Host process boundary — the outermost box in the diagram is also the only place capability values are ever constructed (I14); every subsystem drawn inside it receives capabilities exclusively as function arguments, never by reaching outside the box.

6. Design Principles

  • P1 — Errors are the product. Every diagnostic carries a primary span, at least one secondary label where it clarifies the failure, and a one-sentence fix-oriented hint. Tradeoff: authoring good diagnostics costs materially more engineering time than a bare panic!. Operational implication: dsl eval --format=json is the CI-facing contract, not an afterthought. Violating it: the CLI becomes unusable for its target audience (config authors, not compiler engineers).
  • P2 — Total by construction. No general recursion, no general loops; only structural induction over algebraic data. Tradeoff: the language cannot express every algorithm a general-purpose language can. Operational implication: a well-typed program is guaranteed to terminate (modulo capability-driven I/O), so CI never needs a compute timeout for evaluation itself. Violating it: reintroduces the halting problem into a format meant to be safely evaluated by untrusted CI jobs.
  • P3 — Capability-based effects. I/O is a value passed in, never an ambient instruction. Tradeoff: stdlib functions that would be trivial globals in most languages must thread a capability argument. Operational implication: dsl eval can run on untrusted contributor PRs without a container sandbox as the only line of defense. Violating it: collapses the sandboxing guarantee this project exists to provide (I3, I14).
  • P4 — Structural typing, not nominal. Type identity is shape. Tradeoff: no nominal newtype-style abstraction boundary in Phase 0. Operational implication: matches the JSON-shaped output format directly — no name registry to maintain. Violating it: requires a name-resolution layer the JSON output format has no room to express.
  • P5 — One file is one module. The relative path is the import path; no index.lm, no resolver fallback chain. Tradeoff: no implicit package-root convenience. Operational implication: import resolution is O(1) to explain to a new contributor. Violating it: reintroduces Node.js-style resolution ambiguity (ADR-18).
  • P6 — Formatter round-trips. format(format(x)) == format(x) for every fixture. Tradeoff: the formatter cannot take shortcuts that discard trivia. Operational implication: editor "format on save" is trustworthy by construction. Violating it: breaks the one guarantee that makes automated formatting safe to enable by default (I5).
  • P7 — Diagnostics are JSON-first. The human renderer and the LSP consume the same Diagnostic value (§11). Tradeoff: the human renderer's layout logic must be derivable from structured data, not hand-tuned prose. Operational implication: one diagnostic model to maintain, not two. Violating it: creates two diagnostic dialects that silently drift apart.
  • P8 — No hidden allocation on hot paths. The interpreter avoids allocation after warm-up; the formatter pre-sizes its buffer. Tradeoff: more up-front buffer-sizing engineering. Operational implication: keeps M4/M5 (§30) reachable without a GC-tuning exercise. Violating it: blows the evaluation-throughput target on realistic pipelines.
  • P9 — The REPL is the language. Anything expressible in a .lm file is typeable at the REPL, letter for letter. Tradeoff: the REPL cannot offer syntax the file format lacks. Operational implication: one grammar to teach, one grammar to test. Violating it: creates an undocumented second dialect (the historical #1 REPL bug class, §26 Pitfalls precedent).
  • P10 — Tests are first-class syntax. assert is part of the surface grammar, not an external framework. Tradeoff: no pluggable third-party test-framework ecosystem. Operational implication: dsl test requires no additional tooling to adopt. Violating it: decouples test authoring from the language the tests exercise.
  • P11 — Single parsing authority. The REPL, the LSP, and dsl eval share one Parser entry point and one Resolver/Infer/Eval call chain. Tradeoff: the REPL cannot special-case its own grammar for convenience. Operational implication: a fix to the parser fixes all three surfaces simultaneously. Violating it: is the historical root cause of "works in the file, fails in the REPL" bugs.
  • P12 — The occurs check is non-negotiable. Every unification step runs the occurs check before linking a type variable. Tradeoff: a small, constant per-unification cost. Operational implication: HM soundness holds without a separate termination proof per program. Violating it: loops the type checker forever on input shaped like \x. x x.
  • P13 — Every deferred surface is anchored. A PhaseDeferred(...) call site always names a real phase heading and appears in the Deferred Features Register (§37). Tradeoff: deferring a feature requires bookkeeping, not just silence. Operational implication: BUILD_PLAN.md always reflects true remaining scope. Violating it: hides scope from the next engineer who reads this document.

8. Domain Model

Surface Grammar (EBNF)

module      = { item } ;
item        = let_item | type_alias | import ;
let_item    = "let" , ident , [ ":" , type_expr ] , "=" , expr , ";" ;
type_alias  = "type" , ident , "=" , type_expr , ";" ;
import      = "import" , string_lit , ";" ;

expr        = assert_expr ;
assert_expr = [ "assert" , expr , "in" ] , if_expr ;
if_expr     = "if" , expr , "then" , expr , "else" , expr | let_expr ;
let_expr    = "let" , ident , [ ":" , type_expr ] , "=" , expr , "in" , expr | lambda ;
lambda      = "\" , param , { param } , "." , expr | binary ;
binary      = binary , bin_op , binary | unary ;
unary       = ( "-" | "!" ) , unary | application ;
application = application , postfix | postfix ;
postfix     = postfix , "." , ident | postfix , "//" , record_lit | primary ;
primary     = literal | ident | "(" , expr , ")" | record_lit | list_lit | match_expr ;
match_expr  = "match" , expr , "with" , { "|" , pattern , "=>" , expr } ;
record_lit  = "{" , [ field , { "," , field } ] , "}" ;
field       = ident , "=" , expr ;
list_lit    = "[" , [ expr , { "," , expr } ] , "]" ;
literal     = int | float | string | "true" | "false" | "null" ;
pattern     = "\"" , tag , "\"" , [ ident ] | "_" ;

type_expr   = forall_ty | arrow_ty ;
forall_ty   = "forall" , ident , { ident } , "." , arrow_ty ;
arrow_ty    = record_ty , [ "->" , arrow_ty ] ;
record_ty   = "{" , [ ty_field , { "," , ty_field } ] , [ "|" , ident ] , "}" | sum_ty ;
sum_ty      = "[" , tag_ty , { "|" , tag_ty } , "]" | atom_ty ;
tag_ty      = "\"" , tag , "\"" , [ atom_ty ] ;
atom_ty     = ident , { atom_ty } | "(" , type_expr , ")" ;

The AST shape realizing this grammar is normative in §11 Core Schema & Types (Expr, TypeExpr). Application binds tighter than field access — f x.y parses as f (x.y); this is locked because it is the more common shape in configuration.

Capabilities & Effects

// crates/lume-eval/src/effects.rs
pub enum Capability { FileRead(PathScope), FileWrite(PathScope), NetFetch(HostAllowlist), ProcExec(ArgAllowlist) }
pub struct PathScope { pub root: PathBuf }          // a capability is scoped, never global (I14)
pub struct HostAllowlist { pub hosts: Vec<String> }
pub struct ArgAllowlist { pub programs: Vec<String> }

Ownership: a Capability value is owned exactly like any other Value variant — no special runtime bookkeeping distinguishes it, which is the point (MM3, §32). Mutation: immutable; a narrower capability is produced by construction (e.g. scoping a FileRead to a subdirectory), never by mutating an existing one. Concurrency: Send + Sync, safe to pass across the single-threaded evaluator's call boundaries. Persistence: none — capabilities are never serialized; only their effects' results (a file's contents, a JSON payload) ever leave the process. Compatibility: adding a Capability variant is additive; every lume-stdlib builtin that consumes one matches exhaustively, so a missed case is a compile error, not a silent authority leak (P3, I3).

13. Phase 1 — Lexer

1.1 Objectives

  • Produce a span-aware, trivia-preserving lexer that never panics on any input (I12, P1).
  • Establish the token vocabulary that every later phase (Parser, Formatter) treats as normative.

1.2 Detailed Implementation Steps

  • Implement lume-syntax::lexer as a hand-written scanner over &str, validated UTF-8, iterating code points, not bytes (Unicode UAX #31, applied here).
  • Attach leading/trailing Trivia (whitespace, // line, /* block */ nesting, /// doc comments) to each Token rather than discarding it — the substrate P6's round-trip guarantee depends on.
  • String literals: JSON-style escapes plus \u{XXXXXX} (ADR-19); unterminated strings emit a recoverable diagnostic and the lexer consumes the rest of the line, continuing (P1).
  • Multi-line strings: triple-quote """ with leading-whitespace stripping.
  • Numbers: decimal int/float with optional exponent, 0x/0o/0b bases, _ digit separators; out-of-range integers emit a diagnostic rather than silently overflowing (ADR-22).
  • Malformed byte sequences (invalid UTF-8) — emit TokenKind::Error plus a diagnostic and continue scanning (I12); this is exercised directly by the lex fuzz target (ADR-12).
  • Identifier scanning follows Unicode UAX #31's ID_Start/ID_Continue classes (applied here per §5) rather than an ASCII-only rule, so a non-Latin identifier lexes identically to a Latin one.

1.3 Deliverable

dsl debug lex foo.lm prints the full token stream including attached trivia; the lexer never panics on the lex fuzz corpus.

1.4 Acceptance Criteria

  • 80+ positive and 40+ negative fixtures in conformance/fixtures/lex/ all pass.
  • Lex throughput ≥ 40 MB/s single-core on the M1 benchmark (§30).
  • fuzz.lex_crashes_total stays 0 across a 1-hour pre-merge soak (M13, I12).

1.5 Conformance Fixtures

Fixture Purpose Expected

1.6 Pitfalls

  • Treating UTF-8 as bytes — column numbers must be code-point columns, not byte columns.
  • Discarding trivia — the Formatter (§20) and the LSP (§21) both depend on it.
  • Recovering by panicking — every lex error is a diagnostic, never a panic! (I12).

1.7 Performance Concerns

Single-pass scan, no backtracking; trivia vectors pre-sized from a rough token-count estimate (source length ÷ 4) to avoid reallocation on the hot path (P8).

1.8 Edge Cases

A UTF-8 BOM at file start; a file with no trailing newline; a doc comment attached to nothing (trailing at EOF); nested block comments exceeding a 64-deep nesting cap (diagnostic, not stack overflow).

1.9 Failure Analysis

A lexer panic would abort the entire pipeline including diagnostics rendering itself — this is why I12 exists as a named invariant, not just a best-effort goal. Detection is the lex fuzz target; containment is the TokenKind::Error fallback; blast radius with the fallback in place is a single diagnostic, not a crash.

1.10 Operational Notes

lex.tokens_total and lex.error_tokens_total are the two counters exported; both feed the --timings flamegraph output (§26). No migration concerns — the token vocabulary is additive-only (§27).

14. Phase 2 — Parser (Recursive Descent + Pratt)

2.1 Objectives

  • Turn the Phase 1 token stream into an arena-allocated AST (§11) with full source-location tracking.
  • Recover from syntax errors instead of aborting, so one bad line never hides every other diagnostic (P1, P11).

2.2 Detailed Implementation Steps

  • Implement lume-parser::parser as recursive descent for module/item/record_lit/match_expr (§8 grammar), calling into lume-parser::pratt for binary/unary/application via token-bound binding power (Pratt 1973, ADR-03).
  • Both halves return Result<&'arena AstNode, Diagnostic>; ? threads errors out without aborting the parse.
  • Error recovery (recovery.rs): on error, emit a diagnostic, advance to a synchronization point (the next ;, }, or top-level keyword), continue — this is what lets the LSP (§21) give useful feedback on half-typed code.
  • Operator precedence table, increasing: || (left) < && (left) < == != < > <= >= (non-assoc) < + - (left) < * / % (left) < unary - ! (prefix) < function application (left) < . field access (left) — locked per §8's grammar note.
  • The REPL, the LSP, and dsl eval all call the same Parser::parse entry point (P11, I9) — no REPL-only grammar branch.
  • parser.rs's unit tests (tests.rs) assert the Pratt table's binding powers directly, one test per row of §8's precedence list, so a future edit to the table cannot silently reorder two operators without a failing test naming exactly which pair (ADR-03).

2.3 Deliverable

dsl debug ast foo.lm prints the AST as a tree; parsing round-trips through the Formatter (§20) on the full conformance corpus.

2.4 Acceptance Criteria

  • 140+ positive and 70+ negative fixtures in conformance/fixtures/parse/ all pass.
  • Parse throughput ≥ 15 MB/s single-core (M2, §30).
  • Round-trip property: format(parse(source)) == source for every fixture with canonical formatting already applied (I5-adjacent, verified fully in §20).

2.5 Conformance Fixtures

Fixture Purpose Expected

2.6 Pitfalls

  • Synchronizing on the wrong token — an over-eager synchronizer eats half the file; pick conservatively, only structural punctuation that rarely appears mid-expression.
  • Using .unwrap() anywhere in the parser — every error path is recoverable and reported (P1).
  • Not preserving trivia through the parse — the Formatter (§20) needs it attached to AST nodes, not just tokens.

2.7 Performance Concerns

Recursive descent depth is bounded by an explicit recursion-depth counter (not the call stack alone) so a pathological input trips a diagnostic (T6) before a native stack overflow; the Pratt loop's binding-power table is a const array, no per-call allocation (P8).

2.8 Edge Cases

2.9 Failure Analysis

A parser bug that infinite-loops without consuming a token is FM-1 (§25) — mitigated by an assertion that every recovery iteration advances the cursor by at least one token. Detection is the parse fuzz target; recovery is treating a stuck parser as an internal-compiler-error, never a hang.

2.10 Operational Notes

parse.nodes_total and parse.recovery_events_total are exported; the latter feeding an operator dashboard showing which grammar constructs most often trigger recovery — a proxy for where the grammar or its diagnostics need work (§26).

15. Phase 3 — Name Resolution & Modules

3.1 Objectives

  • Bind every identifier in the AST to its definition and build the file-is-module import graph (P5, I6).
  • Reject import cycles with a diagnostic naming the full cycle, not a stack overflow.

3.2 Detailed Implementation Steps

  • Implement lume-resolve::scope as lexical scoping: each let introduces a scope extending to the end of its enclosing form; top-level let items support a finite, structurally-decreasing recursion form (full mutual recursion is Phase-1+, tracked via ADR-05's totality boundary).
  • Implement lume-resolve::modules: import "./other.lm" resolves relative to the current file, cached by canonical (not relative) path; a DFS with gray/black marking detects cycles before they recurse (I6).
  • Unresolved identifiers get a "did you mean?" suggestion when an in-scope name is within edit distance 2 (rustc-style, applied here per §5's rustc reference-impl lesson).
  • Every Path-shaped identifier is replaced post-resolution by a Resolved node carrying a definition handle — no shared "unresolved" variant survives into Phase 4 (enforces I6 at the type level, mirroring the resolved-AST discipline from the Roc/Gleam reference implementations, §5).
  • The stdlib prelude (lume-stdlib, §18) is resolved as an implicit outermost scope wrapping every module, so a user file never writes an explicit import for list/string/map/etc. builtins.

3.3 Deliverable

dsl debug resolve foo.lm prints the symbol table; the resolver rejects every cyclic-import fixture with a diagnostic naming the full cycle path.

3.4 Acceptance Criteria

  • 60+ fixtures in conformance/fixtures/resolve/ covering unresolved names, shadowing, imports, and cycles all pass.
  • 100% of unresolved-name fixtures within edit distance 2 of an in-scope name produce a "did you mean?" suggestion.
  • 0 DefTable lookup misses on the stdlib prelude across the full corpus.

3.6 Pitfalls

  • Letting a typo propagate to a confusing type error downstream — catch it here with a specific suggestion, not in Phase 4.
  • Caching modules by relative path instead of canonical path — two different relative paths to the same file must resolve to one cached module (I6-adjacent correctness).
  • Resolving inside a deferred/lazy expression — resolution is non-deferred; the full scope is known at AST-walk time, never postponed to evaluation.

3.7 Performance Concerns

The DFS cycle detector is O(V+E) over the module graph, run once per compilation, not re-run per lookup; the DefTable is a hash map keyed by a dense id, not by string comparison, to keep large-module resolution off the critical path.

3.8 Edge Cases

A module importing itself directly (1-cycle); a diamond import (a imports b and c, both import d — not a cycle, must resolve once); an import path with .. escaping the project root (rejected with a diagnostic, a defensive measure ahead of the deferred package manager, §37).

3.9 Failure Analysis

An unbounded cycle detector would hang on a large adversarial import graph — bounded by I6's DFS-with-marking design, which is linear regardless of cycle count. Detection is the resolve fixture corpus; recovery is aborting only the cyclic module's compilation, leaving unaffected sibling modules intact.

3.10 Operational Notes

16. Phase 4 — Type Checker (HM, Rows, Sums)

4.1 Objectives

  • Implement Hindley-Milner inference with level-based generalization, row-polymorphic records, and anonymous sum types (ADR-05, P12).
  • Produce a diagnostic for every unification failure that names both types, both spans, and the inference path (P1).

4.2 Detailed Implementation Steps

  • Implement lume-types::infer as Algorithm W: infer bottom-up, generate fresh TyVars at every binding (Damas & Milner 1982, applied here); unify on every constraint via lume-types::unify's union-find table.
  • At each let boundary, generalise() replaces free variables introduced at the current level with universally quantified variables — level bookkeeping per Pottier & Rémy 2005 (I7).
  • lume-types::unify runs the occurs check before every link (P12, I2) — t -> t cannot unify with t = t -> t.
  • Row-polymorphic records (lume-types::rows, Rémy 1989): field access requires the field present in a row plus a fresh tail variable; record update produces a new row type with the field's type replaced (I8).
  • Sum types are anonymous tagged unions (§8 grammar's sum_ty); pattern matching over match_expr produces an exhaustiveness constraint that every listed tag is handled, checked against the sum's known tag set.
  • Every unification failure's Diagnostic (§11) carries: the two types that failed to unify, the source span of each, and the inference path in the spirit of rustc's "expected because of this; found because of that" (§5 rustc lesson, applied here).
  • The stdlib's builtin type environment (lume-types::env) is seeded once at checker startup from a static table keyed by the same Symbols the Repository Layout's lume-stdlib module names use (§11), so a builtin's declared type and its resolved module name can never drift apart silently.

4.3 Deliverable

dsl debug types foo.lm prints the inferred type of every top-level binding; every negative fixture's diagnostic is snapshot-tested byte-for-byte (ADR-10).

4.4 Acceptance Criteria

  • 200+ positive and 100+ negative fixtures in conformance/fixtures/types/ all pass.
  • Type-check throughput ≥ 4 MB/s single-core (M3, §30).
  • 100% exhaustiveness-checking accuracy on the match_expr negative corpus (no false-negative "non-exhaustive" report and no false-positive miss).
  • 0 typeck.occurs_rejections_total false negatives (every \x. x x-shaped fixture is rejected).

  • Generalizing too eagerly (the value restriction) — generalize only at let boundaries over types with no free variables escaping the current level (I7).

  • Unifying records by reference rather than by row — records unify field by field plus tail row (I8), never as an opaque blob.

An occurs-check bypass bug is a soundness break, not merely a UX one — FM-2 (§25) tracks this class explicitly. Detection is the types fuzz corpus plus a debug-assert inside unify(); containment is treating any occurs-check assertion failure as an internal-compiler-error, never a silent pass-through.

A level-violation assertion firing in production is always a compiler bug, never a user-input problem — it pages the maintainer via the main-branch CI job, not a user-facing diagnostic path.

18. Phase 6 — Tree-Walking Interpreter & Capability Effects

6.1 Objectives

  • Evaluate the typed AST into JSON-shaped Values (§11) with strict, deterministic, left-to-right depth-first evaluation (I10).
  • Enforce the capability-based effect boundary end to end: no function invokes an effect its type does not accept as an argument (P3, I3, I14).

6.2 Detailed Implementation Steps

  • Implement lume-eval::eval as a strict, environment-passing evaluator; let rec binds a Thunk (§11) that the body forces lazily, the only mechanism that breaks recursion without a general loop (P2, I1).
  • lume-eval::effects: the apply step pattern-matches the callee's type; a function whose argument position is typed Capability(K) cannot be invoked unless the caller supplies a value of that capability kind — enforced once statically (Phase 4, I3) and double-checked at runtime as defense in depth (I3's "detection" column, §7).
  • Capabilities are constructed only in lume-cli::main at the entry point (I14) — library code (lume-stdlib, user .lm files) never has a path to synthesize one.
  • Equality is structural: records equal iff fields agree by name; Value::Float uses bitwise equality, not IEEE-754 equality, to match RFC 8259 JSON serialization semantics (I11).
  • lume-stdlib::json/yaml encoders are the two total functions from Value to text (§11); the regex builtin uses a bounded-backtracking engine only — never a general-backtracking regex — because unbounded backtracking is a documented denial-of-service vector: Cloudflare's July 2, 2019 global outage was caused by a single catastrophically-backtracking regular expression deployed in a WAF rule (Cloudflare Engineering Blog, "Details of the Cloudflare outage on July 2, 2019"), directly informing T10's mitigation choice.
  • The environment chain (lume-eval::env) is a persistent (structurally shared) linked list of scopes, never a cloned HashMap per call frame, keeping closure capture O(1) instead of O(scope size) (P8).

6.3 Deliverable

dsl eval examples/kubernetes-deployment.lm emits the expected JSON; dsl eval on a capability-missing fixture traps with a Diagnostic, never a host-level I/O error.

6.4 Acceptance Criteria

  • 150+ positive fixtures in conformance/fixtures/eval/ all pass; 40+ fixtures in conformance/fixtures/effects/ covering capability grant/deny all pass.
  • Evaluation throughput ≥ 2M reductions/sec on the arithmetic-dominated benchmark (M4, §30).
  • JSON output throughput ≥ 50 MB/s (M9, §30).
  • eval.ambient_capability_total stays 0 across the entire corpus (I14).

  • Capabilities leaking through closures — the type system catches this at Phase 4; the runtime double-checks at apply (I3) as defense in depth, per the Cloudflare-incident lesson above: a single unguarded path is a real, historically-demonstrated production risk.

repl/incremental-env 5 sequential let inputs each subsequent input sees all prior bindings, no re-evaluation of history

7.6 Pitfalls

  • A REPL parser that diverges from the file parser — they are, by construction, the same Parser instance shape (P11).
  • Re-running the entire history on every input — each input updates the environment in place, not from scratch.
  • Surfacing internal type representations — every type pretty-prints through the same renderer as dsl eval --format=json (§17).

7.7 Performance Concerns

Per-input latency is dominated by parse+typecheck+eval of the new input alone (not the accumulated history), keeping interactive latency flat as a session grows — a direct consequence of P11's shared-pipeline, incremental-environment design (7.2).

7.8 Edge Cases

An unbalanced bracket that never closes (REPL waits indefinitely for more input, with a Ctrl-D/Ctrl-C escape hatch, never a silent hang); a :type command on a syntactically invalid expression (renders the parse diagnostic, not a crash); pasting a full .lm file's contents at once (accepted, parses as a module, not a single expr).

7.9 Failure Analysis

A REPL/file divergence (FM-6, §25) is detected by the I9 replay CI job before it ever reaches a user session; if one somehow ships, the fix is always in the shared lume-parser/lume-types/lume-eval crates, never a REPL-local patch, preserving P11.

7.10 Operational Notes

repl.eval_latency_seconds is exported per input (§26); the REPL's :trace output is deliberately not machine-parsed telemetry — it is a human debugging aid, distinct from the structured diagnostic JSON (§17).

20. Phase 8 — Formatter

8.1 Objectives

  • Ship a formatter that round-trips: format(format(x)) == format(x) for every corpus fixture (P6, I5).
  • Preserve every comment and doc-comment verbatim, attached via the Phase 1 trivia model.

8.2 Detailed Implementation Steps

  • Implement lume-fmt::doc as Wadler-Leijen pretty-printer combinators (Wadler 1998, applied here) producing a Doc value from the AST; lume-fmt::format renders Doc at a target width (default 80 columns), choosing line breaks deterministically.
  • The formatter consumes the same AST the parser (§14) produces, including attached trivia (§13) — comments are re-emitted verbatim at their attachment point, never reformatted or re-wrapped.
  • Idempotency is a property test, not a spot check: conformance/fixtures/fmt/ runs format(parse(format(parse(x)))) == format(parse(x)) over the entire corpus (I5).
  • dsl fmt --check exits nonzero (CI-gating) without writing; dsl fmt --write applies formatting in place.
  • Trailing commas in record_lit/list_lit (§8 grammar) are accepted by the parser but never emitted by the formatter, so dsl fmt --write normalizes them away deterministically (ADR-09).

8.3 Deliverable

dsl fmt --check examples/ returns 0 on already-formatted input; dsl fmt --write examples/ is idempotent on a second run.

8.4 Acceptance Criteria

  • 90+ fixtures in conformance/fixtures/fmt/ all pass the idempotency property test (I5).
  • Format throughput ≥ 10 MB/s (M5, §30).
  • 0 fmt.idempotency_failures_total across the full corpus (I5, §7).

8.5 Conformance Fixtures

Fixture Purpose Expected

fmt/line-width-80 a record literal near the 80-column boundary breaks deterministically at the documented width

8.6 Pitfalls

  • Discarding trivia — doc comments must stay attached through formatting (Phase 1, P6).
  • Reformatting comments — comments are emitted verbatim; their attached trivia already encodes the whitespace they wanted (Phase 1).
  • Breaking lines inconsistently — the Doc combinator commits to one deterministic choice per shape, never a "whichever fits" ambiguity that could vary by renderer version.

8.7 Performance Concerns

Deeply-nested records/lists are rendered via an explicit-stack Doc-building walk, not native recursion, avoiding the stack-overflow risk the Phase 2 parser already guards against on the way in (2.7, 2.8).

8.8 Edge Cases

A file containing only comments (formats to itself unchanged); a record literal exactly at the 80-column boundary (breaks, per 8.5's fixture); a doc comment on the last item in a file with no trailing newline (preserved, trailing newline added per the canonical form).

8.9 Failure Analysis

A non-idempotent formatter output (FM-5, §25) breaks editor "format on save" trust; detection is the property test in 8.4; recovery is always a lume-fmt::doc fix plus a new regression fixture, never a formatter-output whitelist exception.

8.10 Operational Notes

fmt.files_formatted_total and fmt.idempotency_failures_total are exported (§26); the CI-gating dsl fmt --check runs on every PR, distinct from the local --write workflow.

21. Phase 9 — Language Server (LSP)

9.1 Objectives

  • Serve hover, go-to-definition, find-references, completion, and on-save diagnostics over JSON-RPC via tower-lsp (ADR-07).
  • Guarantee the LSP never blocks its main loop on one malformed document (I13).

9.2 Detailed Implementation Steps

  • Implement lume-lsp::server recompiling the whole affected module on every change in Phase 0 (Salsa-based incrementality is PhaseDeferred("Phase 9 — Language Server (LSP)"), §37); diagnostics are debounced 200 ms per document (I13, §4).
  • hover.rs shows the Phase 4 inferred type at the cursor; definition.rs jumps to the resolved let binding from Phase 3; completion.rs lists in-scope names with their types; diagnostics.rs pushes the Phase 5 Diagnostic JSON form directly (P7) — no LSP-local diagnostic translation layer.
  • Every handler wraps in a panic-catching boundary so a crafted JSON-RPC payload (T4, §24) cannot take down the server process; per-document compute is isolated so one malformed document never blocks hover/completion requests on other open documents (I13).
  • The parser/checker/evaluator entry points reused here are byte-for-byte the same as dsl eval's (P11, I9) — no LSP-specific grammar path.
  • textDocument/didOpen enforces the same 32 MiB per-file size cap as the CLI (§4) before any parsing begins, closing the T13 denial-of-service vector at the earliest possible point in the request lifecycle (see the Sequence Table, §8).

9.3 Deliverable

dsl lsp --stdio works against any LSP 3.17-compliant client; a VSCode integration test exercises diagnostics, hover, and completion end to end.

9.4 Acceptance Criteria

  • LSP hover round-trip on a 10K-LOC file ≤ 100 ms (M6, §30).
  • 100% of conformance/fixtures/parse/ re-run through the LSP's entry point match the CLI's output (I9, three-front-end replay).
  • lsp.blocked_requests_total stays 0 across a fuzzed-malformed-document integration test (I13).

9.5 Conformance Fixtures

9.6 Pitfalls

  • Echoing a parse error to the LSP unchanged — translate to the LSP diagnostic shape via the shared Diagnostic JSON renderer (§17), never a bespoke format.
  • Sending diagnostics on every keystroke — debounce 200 ms (I13, §4).
  • Crashing on malformed JSON-RPC — every handler wraps in a recover boundary (T4).

9.7 Performance Concerns

Whole-module recompilation on every change is the Phase-0 cost center; the 200 ms debounce (I13) and the M6 target (§30) bound this acceptably for files under the 10K-LOC benchmark, with Salsa-based incrementality explicitly deferred (§37) rather than half-built.

9.8 Edge Cases

A document closed mid-recompute (cancel the in-flight task, no dangling diagnostic push); two documents importing each other (both surface their own diagnostics independently, no cross-document deadlock); a client that never sends initialize before other requests (rejected per LSP 3.17's lifecycle requirement).

9.9 Failure Analysis

An LSP process crash (FM-4, §25) is contained by the per-handler panic boundary (I13); detection is the editor's own "server exited" notification plus a lsp.crashes_total counter; recovery is tower-lsp's standard client-side restart, with the crash cause logged to docs/runbooks/-referenced diagnostics.

9.10 Operational Notes

10.9 Failure Analysis

A conformance-fixture golden-output drift (FM-10, §25) is caught by conformance.yml on every PR before merge; recovery is either fixing the regression or, if the semantic change is intentional, updating the golden fixture in the same commit as the change that caused the drift — never a silent update.

conformance.mismatch_total{bucket} and test.failures_total are exported (§26); docs/runbooks/conformance-flake-triage.md (§10) is the named runbook for an intermittently-failing fixture.

Migration for a config repository upgrading its own pinned dsl version follows the same conformance-suite-against-the-new-binary check described above, run by the repository's own CI before the pin bump merges.

27. Compatibility & Versioning

Wire/storage compatibility: the JSON/YAML output of lume-stdlib's encoders (§18) follows RFC 8259/YAML 1.2.2 exactly; dsl makes no additional promises beyond those specifications for a given output format.

Schema evolution: the conformance/fixtures/*.yaml fixture schema (report.schema.json, §10) is versioned; a breaking schema change requires migrating every existing fixture in the same commit — no partial-migration state is ever committed.

API stability: Diagnostic, Ty, and Value (§11) are the only public extension points in Phase 0; adding a field to any of them that changes wire-shape is a breaking change requiring a major-version bump (SemVer, below).

Diagnostic-code stability (I4-adjacent): a Code value is never repurposed for a different meaning once shipped; a retired code is marked deprecated in docs/diagnostics/-equivalent catalogue content, never deleted or reused.

Migration: none applicable in Phase 0 (no persistent on-disk compiler state); Phase 1's Salsa-based incremental LSP database (§37) will need an explicit on-disk schema version once it ships.

Deprecation policy: a language-surface deprecation (e.g. a keyword rename) ships a warning-level diagnostic for at least one minor version before becoming a hard error.

SemVer policy: dsl's own crate versions follow SemVer; the language Lume follows its own compatibility promise independently of the CLI's crate version — a language-breaking change requires an ADR and a language-version bump, tracked separately (ADR-20-adjacent).

Rolling-upgrade guarantees: not applicable (no server for the CLI path); the LSP's equivalent guarantee is that an editor client may hold an open session across a dsl lsp binary restart without losing unsaved-document diagnostics state, since diagnostics are recomputed fresh per document on reconnect (Phase 9, I13).

The examples/ corpus (§10) is versioned alongside the language itself: an example that no longer type-checks under the current dsl is a release-blocking regression, not a documentation debt item, since the examples double as the worked-example source for §8's Domain Model.

28. Testing & Verification Strategy

Unit: per-crate #[test] functions for pure boundaries (unify(), the Pratt loop's binding-power table, the row-merge step). Integration: the conformance suite (§22) is the primary integration test, tied directly to I1–I14 — §7's debugging-methodology paragraph enumerates which fixtures exercise which invariant. Differential: the Dhall standard (§5) is used as a specification-rigor benchmark — Lume's own conformance fixtures are reviewed against Dhall's exhaustive-specification style, not diffed byte-for-byte against Dhall's own output, since the languages differ semantically.

Chaos/fault injection: the effects/* conformance bucket includes fixtures that simulate a withheld capability, a cyclic import, and a malformed LSP request (T4) — each a deliberate fault, not an accidental one. Soak: the 1-hour pre-merge / nightly fuzz soak (M13, ADR-12) over lex, parse, and types — the three boundaries where untrusted input meets internal representation.

Conformance: the executable specification (§22, P10); performance-regression gating: criterion's comparison against the last release baseline blocks merge at a regression exceeding the M-table's per-metric tolerance (§30). 31. Scalability Analysis

What stays constant: per-file lex/parse/typecheck cost is linear in source size (O(n) tokens, O(n) AST nodes, near-linear unification via union-find path compression, §16). What grows: the module count in a large project grows the import-resolution graph (O(V+E) per compile, §15), and the LSP's per-keystroke recompute cost grows with the size of the single affected module (not the whole project, since one file is one module, P5) — bounded by M6.

Named bottlenecks in order: (1) whole-module LSP recompute on every keystroke (Phase 9, deferred incrementality is the long-term fix, §37); (2) type-check throughput (M3 is the tightest per-byte target in §30, since unification is the most expensive per-node operation in the pipeline); (3) the lack of parallelism across independent modules within one dsl eval invocation (Phase 0 compiles one compilation unit per process, §4).

Rank Bottleneck Where It Shows Up Phase-0 Mitigation Long-Term Lever
1 Whole-module LSP recompute every keystroke past the 200 ms debounce (I13) debounce + per-document isolation Salsa-based incrementality (§37)
2 Type-check throughput (M3) the tightest per-byte target in §30 union-find path compression, level bookkeeping (§32 MM2) none planned — HM inference is inherently the most expensive per-node pass
3 No cross-module parallelism within one invocation a single large dsl eval on a monolithic file encourage the file-is-module discipline (P5) to keep files small a query-based architecture (§36 Alternative 3) parallelizes at the query-graph level

Horizontal scaling: independent .lm files/modules are embarrassingly parallel to type-check and evaluate — a CI matrix can shard a large config repository by file with zero coordination overhead, since P5 (one file, one module) makes cross-file state explicit (the import graph) rather than implicit. Vertical scaling: single-core throughput (M1–M4) is the Phase-0 story; multi-core speedup within one file's compilation is not pursued in Phase 0 (the AST/type-graph are not designed for concurrent mutation, §11) and is explicitly out of scope until a query-based incremental architecture (§36, Alternative 3) is adopted.

Sharding/partitioning: a large monorepo of .lm configuration shards naturally along the import graph's connected components — two components with no import edge between them can be compiled fully in parallel with zero coordination. Coordination overhead: the only cross-file coordination in Phase 0 is the canonical-path module cache (I6) — a single-process, in-memory HashMap, not a distributed cache, so overhead is a hash lookup, not a network round trip.

Practical ceiling: a single dsl eval invocation is bounded by the 32 MiB per-file arena cap (§4) and single-core throughput (M1–M4); the practical ceiling for a whole project is bounded by how many independent modules a CI matrix can shard across, which is unbounded in principle. The lever beyond the per-file ceiling is Phase 1's Salsa-based incremental architecture (§37, MM7) — memoizing per-module results the same way rust-analyzer does (§5 reference-implementation lesson) rather than recompiling whole files on every change, discussed further as Alternative 3 in §36.

Coordination overhead in the LSP case is different from the CLI case: a single dsl lsp process serves one editor's open workspace, so there is no cross-process coordination at all in Phase 0 — the ceiling there is purely the per-document recompute cost (§34 item 8) multiplied by how many documents a user keeps open simultaneously, which the per-document memory ceiling (§34 item 9) already bounds before throughput does.

32. Mental Models & First Principles

MM1 — A type is a compile-time proof that a program will terminate, not a label. HM inference treats every expression's type as something derived, not merely annotated. Predicts: a unification failure signals a missing inductive case, not a cosmetic mismatch. Bug class without it: accepting ill-typed configuration that is only caught at evaluation time, in production. Applies in Phase 4 (§16).

MM2 — Levels are a lightweight region inference for generalization. A TyVar's level (Pottier & Rémy 2005) tracks "how deep in let-nesting was this introduced" — the same question region inference asks about allocation scope. Predicts: level-adjustment bugs look exactly like region-escape bugs. Bug class without it: reverting to the classical O(n²) generalization walk, or generalizing a variable that should stay monomorphic. Applies in Phase 4 (§16), I7.

MM3 — A capability is a physical key, not a permission bit. Possessing the value is possessing the authority; there is no separate ambient check. Predicts: a function's type signature alone tells you every effect it can possibly perform. Bug class without it: ambient-authority leaks only a runtime audit — never a type-check — would catch. Applies in Phase 6 (§18), P3.

MM4 — The formatter is the parser run backwards. Any AST shape the parser can produce, the formatter must be able to re-render, and the round-trip property test (I5) is the actual specification, not documentation. Bug class without it: "good enough" formatter heuristics that silently corrupt rare AST shapes. Applies in Phase 8 (§20), I5.

MM5 — A diagnostic is a proof of what a human needs to know, span-first. The primary span is the claim; the message is the argument; the hint is the suggested next step (P1). Predicts: a diagnostic without an actionable primary span will be misread regardless of prose quality. Bug class without it: technically-correct diagnostics that are unusable in practice because the span points at the wrong token. Applies in Phase 5 (§17).

MM6 — Row polymorphism means a record type does not know its own tail. A function polymorphic in a row variable works on any record with at least the fields it uses, without knowing what else is present. Predicts: this is precisely what makes record-accepting functions extensible without a caller-side cast. Bug class without it: over-constraining record parameters to an exact shape, breaking extensibility the moment a caller adds one field. Applies in §8 Domain Model, Phase 4 (§16).

MM7 — A query system turns a compiler pass into a memoized graph node, not a batch step. Predicts: incremental recompute cost is proportional to the size of the dependency subgraph touched by an edit, not the whole project. Bug class without it: a whole-module-recompile LSP that cannot scale past a modest file size (Phase 9's Phase-0 limitation, §21). Applies in §31 Scalability Analysis, §36 Alternative 3.

MM8 — The occurs check is the one line standing between Hindley-Milner and non-termination. Predicts: any "optimization" that skips or weakens the occurs check reintroduces a soundness hole, not merely a slow path. Bug class without it: the type checker itself hangs on input shaped like \x. x x. Applies in Phase 4 (§16), I2, P12.

MM9 — A capability's authority is exactly its type, never its runtime value's contents. Predicts: two Capability::FileRead values with different PathScopes are different authorities even though they share a variant tag — the scope, not the tag, is what a reviewer must check. Bug class without it: treating "has a FileRead capability" as a single yes/no fact and missing a scope-widening bug. Applies in Phase 6 (§18), §11 Core Schema.

MM10 — A conformance fixture is a claim about the language, not about the implementation. Predicts: a fixture should be written so it would still be correct against a hypothetical from-scratch reimplementation of Lume, not merely against lume-eval's current internals. Bug class without it: fixtures that accidentally pin an implementation detail (e.g. a specific error-message wording never promised as stable), turning routine refactors into false regressions. Applies in Phase 10 (§22), §28 Testing & Verification Strategy.

Nickel — the one decision made differently: gradual typing with contracts checked at merge boundaries rather than a fully static, no-contracts type system; wins whenever a configuration author needs to mix untyped legacy data with typed new code during a migration, a use case Lume's fully static Phase-0 design does not directly serve.

Jsonnet — the one decision made differently: no static types at all, validation deferred entirely to runtime or an external schema; wins when authoring velocity for small, short-lived configuration matters more than compile-time guarantees — the same tradeoff ADR-05 explicitly rejects for Lume's target of CI-trusted, untyped-input-hostile evaluation (§1).

34. Back-of-Envelope Capacity Model

Every number below is derived from the §4 System Constraints table and the §30 M-table, formula shown.

  1. Max AST nodes per file = 32 MiB arena cap (§4) ÷ ~64 bytes/node (M8 target, §11 average Expr/Ty variant size with Span + discriminant) = 33,554,432 bytes ÷ 64 ≈ 524,288 nodes — the point at which T5's size guard fires.
  2. Lex throughput → files/sec = 40 MB/s (M1) ÷ an assumed 4 KB average config file ≈ 10,240 files/sec single-core lexing ceiling.
  3. Parse throughput → nodes/sec = 15 MB/s (M2) × (1 node / 64 bytes, item 1's density) = 15,728,640 bytes/s × 0.015625 nodes/byte ≈ 245,760 AST nodes/sec single-core.
  4. Type-check throughput → unify calls/sec = 4 MB/s (M3) × 0.015625 nodes/byte ≈ 65,536 nodes/sec through the checker; at ~2 unify() calls/node average ≈ 131,072 unify calls/sec.
  5. 10K-LOC type-check-alone latency = assume ~40 bytes/LOC (config lines are short) → 10K LOC ≈ 400 KB source; at M3's 4 MB/s ≈ 400,000 ÷ 4,194,304 ≈ 0.10 s — leaving ample headroom under the M10 500 ms end-to-end target for lex + parse + eval combined.
  6. 10K-LOC evaluation cost = 400 KB source × 0.015625 nodes/byte ≈ 6,250 AST nodes; at ~10 reductions/node (closures, field lookups) ≈ 62,500 reductions; at M4's 2M reductions/sec ≈ 31 ms eval time.
  7. JSON encode cost for a 10K-LOC config = assume evaluated output is ~2× source size (record key repetition) ≈ 800 KB JSON; at M9's 50 MB/s ≈ 16 ms to encode.
  8. LSP hover budget check = item 5's ≈ 100 ms type-check-alone cost already consumes the entirety of M6's 100 ms hover ceiling on a 10K-LOC file — directly explaining why Phase 9 (§21) explicitly defers incremental recompute (§37) rather than treating M6 as slack.
  9. Per-document LSP memory ceiling = M8 (≤ 128 bytes/node) × item 1's 524,288-node cap ≈ 128 × 524,288 ≈ 67 MB worst-case AST memory per maximally-sized open document — informing why the LSP does not hold more than a handful of such documents simultaneously without the deferred incremental architecture (§37).
  10. Fuzz coverage per pre-merge soak = M13's 3,600 s floor × an assumed ~30,000 execs/sec for the lex target (typical for a hand-written scanner under cargo-fuzz) ≈ 108M inputs tried per target per pre-merge run.
  11. Container image code budget = M12's 25 MB ceiling − an estimated ~8 MB distroless base overhead (glibc + libgcc, ADR-24) ≈ 17 MB for the statically linked dsl binary itself, directly motivating ADR-25's lean dependency policy.
  12. Conformance corpus per-fixture budget = M11's 60 s ceiling ÷ 700+ fixtures (§1) ≈ 85 ms average per-fixture execution budget including process/harness overhead — the reason Phase 10 (10.7) parallelizes fixture execution across cores rather than running serially.

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Internal DSL Embedded in a Host Language.

Show the original text diagram
Lua host runtime
  └─ a Terra-style typed DSL embedded as a Lua library
       (metatables/macros extend Lua's own grammar)
source (.lua+dsl) → Lua parser/compiler → typed IR → native code

Regime where it wins: rapid systems-DSL prototyping where reusing a mature host language's tooling (debugger, package ecosystem, REPL) outweighs owning the full toolchain. Real embodying system: Terra, embedded in and co-designed with Lua (DeVito et al., "Terra: A Multi-Stage Language for High-Performance Computing," PLDI 2013). Why Lume rejects it: the sandboxing guarantee (P3) requires the type system itself to gate every effect; a host-embedded DSL inherits the host language's own ambient-authority model — any Lua code can call any Lua function — defeating the premise §1 exists to demonstrate.

Alternative 2 — Unification-Based Constraint Merging (CUE-style).

Show the original text diagram
source → parse → constraint graph (lattice of partial values)
                        │
                unify-and-merge (no separate "inference" pass)
                        ▼
              fully-resolved value, or a conflict (bottom)

Regime where it wins: schema-merging-heavy configuration — layering N partial overrides into one resolved value — where "no functions, just constraints" is a feature, not a limitation. Real embodying system: CUE (cuelang.org). Why Lume rejects it: functions and abstraction are first-class Phase-0 goals (§1); reasoning about a lattice-unification system's behavior under higher-order functions is materially harder than under HM's compositional typing (ADR-05).

Alternative 3 — Query-Based Incremental Architecture (Salsa/rust-analyzer-style).

Show the original text diagram
        ┌── query: type_of(def_id) ──┐
 source │                            ▼
 ───────┼→ query: parse(file_id) → query: resolve(def_id) → query: typeck(def_id) → …
        │        (memoized, invalidated on input change)
        └── incremental database ───────────────────────────────────────────┘

Regime where it wins: IDE-grade responsiveness (sub-second recheck on a single-file edit) as a Phase-0 requirement rather than a deferred one. Real embodying system: rust-analyzer's salsa-based incremental database (§5). Why Lume rejects it for Phase 0: it is a fundamentally different architecture from the linear pipeline (§3) — every phase becomes a memoized query with explicit dependency tracking, a substantial upfront design cost that only pays off once the LSP is the primary consumer (already PhaseDeferred, §37); Phase 0 prioritizes a working, readable, linear correctness kernel first (§1, MM7).

Alternative 4 — Bytecode-VM-First (skip the tree-walker in Phase 0).

Show the original text diagram
source → lex → parse → AST → typecheck → bytecode compiler → VM bytecode → VM execution
                                            (no tree-walking interpreter at all)

Regime where it wins: performance-critical hot-reload configuration re-evaluation (e.g. a build system re-evaluating the same config thousands of times per CI run) where interpreter dispatch overhead dominates. Real embodying system: Starlark, Bazel/Buck's configuration language, which compiles to an internal bytecode-like representation for fast repeated evaluation. Why Lume rejects it for Phase 0: §1's Phase-0 goal is a correctness kernel, not a performance kernel — a tree-walker is faster to build and easier to verify 1:1 against the type checker's own semantics; the bytecode VM is reachable later by reusing the sibling Virtual-Machine project (ADR-15) once the tree-walker is a trustworthy reference oracle (§37).

38. Glossary

  • ADR: Architecture Decision Record; §9's locked, rationale-bearing decision table.
  • Arena: a bump-allocated memory region (bumpalo) owning every AST node for one compilation unit; freed in bulk (ADR-04).
  • AST: Abstract Syntax Tree; the parser's structured output (§11).
  • Big-step semantics: an evaluation rule that relates an expression directly to its final value, as used in §8's Evaluation Semantics table.
  • Capability: a value that grants the right to perform an effect (file read, network, process exec); never ambient (P3).
  • Capability token: an instance of a Capability value, constructed only at the lume-cli entry point (I14).
  • Closure: a runtime Value pairing a function body with its captured environment (§11).
  • Conformance fixture: a named YAML input/expected-output pair pinning one normative semantic (§22).
  • Deferred Features Register: the table (§37) mapping every PhaseDeferred call site to its anchor, building phase, and un-defer trigger.
  • Diagnostic: the structured error/warning value (§11) rendered by both the human and JSON renderers (P7).
  • EBNF: Extended Backus-Naur Form; the grammar notation used in §8.
  • Environment chain: the persistent linked structure mapping identifiers to values during evaluation (§11).
  • Free type variable: a TyVar not bound by an enclosing Forall; the target of generalization (§8).
  • Generalization: replacing a type's free variables, not escaping the current level, with universally quantified variables at a let boundary (§8, I7).
  • Golden fixture: a conformance fixture whose expected output is a checked-in reference value, diffed on every run.
  • HM (Hindley-Milner): the type-inference discipline this project implements via Algorithm W (§8, Damas & Milner 1982).
  • Instantiation: replacing a Forall scheme's bound variables with fresh TyVars at a use site (§8).
  • JSON-shaped value: a Value restricted to the JSON data model (null, bool, number, string, list, record) — the interpreter's output contract (I11).
  • Level: an integer tag on a TyVar tracking let-nesting depth, used for level-based generalization (Pottier & Rémy 2005, §32 MM2).
  • Lume: the language name; the binary is dsl; the file extension is .lm (ADR-20).
  • LSP: Language Server Protocol; the editor-integration protocol served by lume-lsp (§21).
  • Occurs check: the unification-time check preventing a type variable from unifying with a type that contains itself (§8, I2, P12).
  • Pratt parser: an operator-precedence parser using token-bound binding powers (Pratt 1973, ADR-03).
  • Principal type: the most general type inferable for an expression under HM (§8).
  • Property test: a test asserting a general property (e.g. format(format(x)) == format(x)) over many generated inputs, not one fixed case (I5, §28).
  • Row: a record type's field map plus an optional tail variable enabling structural extension (§8, §11, I8).
  • Row polymorphism: the ability of a function to accept any record with at least a required set of fields (Rémy 1989, §32 MM6).
  • Row tail: the Option<TyVarId> on a Row representing "possibly more fields, unknown to this function" (§11).
  • Snapshot test: a test comparing rendered output (typically a diagnostic) against a checked-in reference file (insta, ADR-10).
  • Span: a (file, start, end) byte-offset triple pointing into source (§11, I4).
  • Structural typing: type identity determined by shape, not by a declared name (P4).
  • Sum type: an anonymous tagged union of alternatives (§8's sum_ty), checked for exhaustiveness at match sites.
  • Tag: a sum type's named alternative constructor (e.g. "ok", "err" in §8's grammar).
  • Thunk: a deferred, memoized computation used only to implement let rec recursion (§11, I1).
  • Total (totality): the guarantee that every well-typed Phase-0 program terminates (P2, I1).
  • Trivia: whitespace, comments, and doc-comments preserved through lexing and parsing for the Formatter and LSP (§13).
  • Type scheme: a Forall-quantified type representing a polymorphic binding (§8).
  • Union-find: the data structure backing lume-types::unify's substitution table, with path compression for near-constant-time lookups (§30).
  • Unification: the algorithm solving type-equality constraints during inference (§8, Damas & Milner 1982).
  • Value restriction: the discipline of generalizing only at let boundaries, avoiding unsound generalization of effectful expressions (§6 P12-adjacent, Phase 4 §16).
  • Canonical path: the fully resolved, symlink-free filesystem path used to key the module cache, distinct from the relative import path a source file writes (§15, I6).
  • Debounce: delaying a recomputation (e.g. LSP diagnostics) by a fixed interval after the last input event, to avoid recomputing on every keystroke (§21, I13).
  • Distroless: a container base image containing only an application and its runtime dependencies, no shell or package manager (ADR-24).
  • Exhaustiveness checking: verifying at type-check time that a match_expr handles every tag of a sum type (§8, Phase 4 §16).
  • MSRV: Minimum Supported Rust Version; pinned to 1.78 via rust-toolchain.toml (ADR-01).
  • Prelude: the implicit outermost scope wrapping every module, providing the stdlib builtins without an explicit import (Phase 3 §15).
  • ReDoS: Regular-expression Denial of Service, a catastrophic-backtracking vulnerability class; mitigated by a bounded-backtracking regex engine (T9, §24).
  • SBOM: Software Bill of Materials; a manifest of every dependency in a release artifact (§29).
  • SemVer: Semantic Versioning; the compatibility contract for dsl's own crate versions (§27).
