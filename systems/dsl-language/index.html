In one paragraph

Lume is a small language for writing configuration and pipelines, such as Kubernetes or CI files (§1). Every program is type-checked before it runs, every well-typed program is guaranteed to terminate, and code can touch the outside world only through values the host hands it (§1, P2, P3). It is built from scratch in Rust as one command-line tool, dsl, with a REPL, a formatter, a small editor server and a test runner around the same compiler core (§1, P11). Platform engineers write the configs, and CI runs them on untrusted contributor pull requests (§1). The design treats error messages as the product (P1). Its one defining property is that the pipeline never panics on untrusted source input (§4).

The problem, concretely

A platform team keeps its Kubernetes and CI settings in files that contributors edit through pull requests, and CI evaluates each PR (§1). Three naive designs each fail here.

If the config language is a general-purpose scripting language (a §1 non-goal), a contributor can write a loop that never ends, or reach for I/O the host never granted. The blueprint states the cost directly: general recursion "reintroduces the halting problem into a format meant to be safely evaluated by untrusted CI jobs" (P2), and ambient I/O collapses the sandboxing guarantee (P3).

If the language is untyped, a mistake such as a string where a number belongs is caught only when the config is evaluated in production (MM1, §33 on Jsonnet). The design wants the mistake caught before evaluation, as in its own example let x : Int = "hello";, which must produce a diagnostic that points at "hello" and says what was expected (§8, P1).

If errors are bare "syntax error" messages, config authors, who are not compiler engineers, cannot use the tool at all (P1, §2). So the blueprint asks for a language that is typed, total, capability-sandboxed and explains its own failures with rustc-grade diagnostics (§1). It also wants the REPL and the editor server to share one parser with dsl eval, because divergence between such surfaces is the most common language-tooling bug class (P11, §2).

How it works, end to end

Follow the blueprint's own worked program through §3's diagram (§8):

The program is let port : Int = 8080;, then let svc = { name = "api", port = port, replicas = 3 };, then svc (§8).

  1. Lexer (lume-syntax) turns UTF-8 text into tokens, each with a byte-precise Span and its surrounding whitespace and comments (trivia) attached, because the formatter needs them (§3, §11). It never panics, even on invalid bytes (I12).
  2. Parser (lume-parser) builds a tree in a bumpalo memory arena, one arena per compilation unit (§3, ADR-04). Recursive descent handles structure and a Pratt sub-parser handles operators (§3, ADR-03). After a syntax error it skips to the next ;, } or top-level keyword and keeps going (§14).
  3. Resolver (lume-resolve) attaches every name to its definition, walks the import graph and rejects cycles (§3, I6). The standard library arrives as an implicit outermost scope (§15).
  4. Type checker (lume-types) infers that svc has type {name: Str, port: Int, replicas: Int} (§8). It uses Algorithm W with level-based generalization, and the occurs check is the soundness backbone (§3, I2).
  5. Evaluator (lume-eval) is a strict tree-walker. It evaluates left to right, depth first (I10), and produces the record {"name":"api","port":8080,"replicas":3} (§8).
  6. Codecs (lume-stdlib) encode the Value as JSON or YAML text. They are pure functions; only effectful builtins demand a capability argument (§3).
  7. Diagnostic bus (lume-diag) renders any failure along the way. The human renderer (ariadne-backed) and the JSON renderer consume the same Diagnostic value (§3, P7).

Around this pipeline sit three thin wrappers: lume-repl, lume-fmt (AST-only) and lume-lsp (§3). The REPL, the LSP and dsl eval share one parser entry point and one checker chain, and I9 says those three must parse identical input identically (P11, I9). The CLI lume-cli is the only place capability values are constructed (§3, I14).

The core ideas

Pratt parsing with error recovery (§14, ADR-03)

A Pratt parser gives each operator a number for how tightly it grips its neighbours (binding power), so operator precedence lives in one table instead of being spread across grammar rules (ADR-03, §2, §14). The blueprint's table, loosest first: ||, &&, comparisons (non-associative), + -, * / %, unary - !, function application, then . field access (§14). One case is locked: f x.y parses as f (x.y), which §14's table (field access above application) matches, while §8's prose calls the same lock "Application binds tighter than field access" (§8, §14).

Recovery is what makes the parser useful for half-typed code. On an error it records a diagnostic, skips to a synchronization point and continues, so the fixture parse/error-recovery-missing-brace (one missing }) yields one diagnostic and the remaining items still parse (§14). A synchronizer that never advances the cursor looks like a hang (FM-1).

Type inference by levels, and the occurs check (§16, ADR-05)

Hindley-Milner inference gives every new binding a fresh type variable, unifies on every constraint, and generalizes at each let (§16). Unification means solving "these two types must be equal" and recording the answer in a union-find table (§16, §38). Two rules carry the weight.

First, each type variable has a level, the let-nesting depth at which it was introduced. At a let, only variables at the current level are generalized into a forall, so the checker never rescans the whole environment (§16 4.2, 4.7, MM2, I7). The fixture types/generalise/let-boundary checks that one let-bound identity function can be used at two types independently (§16).

Second, before linking a variable to a type, the occurs check asks whether the type contains that variable (P12, I2). Without it, \x. x x would send the checker into an infinite loop (P12, MM8). A unification failure produces a diagnostic with both types, both spans and the inference path, for example let x : Int = "hello" reports "expected Int, found Str" with a secondary label on the ascription (§16, §8).

Row-polymorphic records and sum types (§16, MM6)

A record type can end in a variable standing for "possibly more fields" (a row with a tail, §11, §38). A function that reads one field then works on any record with at least that field (MM6). The blueprint's fixture is \r. r.foo applied to two differently shaped records, which infers forall a r. {foo: a | r} -> a (§16 4.5). Field access needs the field present plus a fresh tail variable, and a duplicate label in one row is rejected (§16, I8).

A sum type is an anonymous tagged union (§8, §16). A match must handle every tag in the sum's known tag set, and the checker verifies that at type-check time, so a missing tag is a diagnostic naming it, not a runtime trap (§16, fixture types/sum/exhaustiveness-miss).

Totality and capabilities in the evaluator (§18, P2, P3)

Totality means every well-typed program terminates (I1). The language offers no general recursion or loops, only structural induction (P2). The one recursion mechanism is let rec, which binds a thunk (a deferred, memoized computation) forced on first use (§8, §18, §11). Top-level recursion is limited to "a finite, structurally-decreasing recursion form", and other shapes are rejected with a diagnostic (§15, §16 4.8). Neither the §8 grammar nor the §11 token list has a rec keyword, so how let rec is written is not specified (§8, §11).

A capability is a value that grants the right to do an effect, such as reading a file under a given directory (P3, §11). A function can use one only if its own type takes it as an argument (I3). Capability values are constructed only in lume-cli::main (I14). The check runs statically in the type checker and again at runtime in apply, as defense in depth (§18, I3). The blueprint's failure path: import "./secrets.lm" where that module calls fs.read without a capability argument raises Trap::MissingCapability{expected: "FileRead", span}, surfaced as a diagnostic and not as a host I/O error (§8).

Module resolution as graph colouring (§15, I6)

One file is one module and the relative path is the import path (P5). Resolving imports is a depth-first walk with three states, per the §8 state table:

State Event Result
Unvisited import seen mark InProgress (gray), recurse into the target
InProgress same file met again on the current path cycle: E-RESOLVE-004, names the full path
InProgress all of its imports resolved mark Resolved (black), cache by canonical path
Resolved imported again from elsewhere return the cached module, no re-parse
any path escapes the project root via .. reject with E-RESOLVE-007

The blueprint's trace: a.lm imports b.lm, which imports a.lm. The resolver reports the cycle a.lm → b.lm → a.lm as E-RESOLVE-004 and aborts only the importing module (§8, I6). Missing gray-marking is the example root cause of FM-8, a resolver that appears to hang (FM-8).

The formatter as the parser run backwards (§20, MM4, P6)

The formatter turns the AST back into text with Wadler-Leijen pretty-printer combinators, choosing line breaks deterministically at a target width (default 80 columns) (§20, ADR-09). Comments are re-emitted verbatim from the attached trivia (§20). The specification is a property test, not a description: format(format(x)) == format(x) for every fixture (P6, I5, MM4), run as format(parse(format(parse(x)))) == format(parse(x)) over the whole corpus (§20). Trailing commas are accepted by the parser but never emitted, so formatting normalizes them away (§20).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust 1.78+ stable, for arena allocation, exhaustive match over AST and type variants, and FFI embedding (§9, §1). Rejected: OCaml, Zig, TypeScript (§9). §1's prose instead lists OCaml, TypeScript and Go, so the two lists differ and both are reported here. When the rejected choice is right: OCaml, when the team is already ML-fluent and needs no cross-project Rust sharing (§9).

Parser construction: hand-written (ADR-02)

Chosen: a hand-written lexer and parser with no generator, because diagnostics are the product and generators fight custom recovery (§9, P1). Rejected: nom, chumsky, lalrpop, pest (§9). When the rejected choice is right: a generator wins for a short-lived internal grammar where diagnostic quality is not user-facing (§9).

Type inference: Hindley-Milner with levels (ADR-05)

Chosen: Algorithm W with level-based generalization, because it is compositional, total and well understood (§9). Rejected: CUE-style constraint unification and bidirectional local inference (§9). When the rejected choice is right: constraint-lattice unification wins for pure schema-merging without functions, which is CUE's own domain (§9, §33).

Formatter: print and reparse (ADR-09)

Chosen: pretty-print from the AST and check by re-parsing, with AST-stability tests, because the round-trip is the specification (§9, P6). Rejected: token-preserving CST rewriting in the rowan style (§9). When the rejected choice is right: a CST-preserving rewriter wins when trivia fidelity must survive partial LSP edits, not just full-file formatting (§9).

Effects: capabilities as values (ADR-17)

Chosen: capabilities-as-values with no algebraic effects in Phase 0, because that is predictable, tractable and matches the configuration domain (§9, P3). Rejected: algebraic effects and handlers, or an ambient IO monad (§9). When the rejected choice is right: algebraic effects win once the language needs composable, resumable computations, such as a retry/backoff combinator library (§9).

Modules: one file is one module (ADR-18)

Chosen: file-based resolution, with no resolver magic (§9, P5). Rejected: manifest-based resolution in the package.json style, and namespace declarations (§9). When the rejected choice is right: manifest resolution wins once the deferred package manager must disambiguate multiple registries (§9, §37).

Layout: braces, not indentation (ADR-21)

Chosen: layout-irrelevant syntax with braces and semicolons, because diagnostics are easier against an unambiguous grammar (§9). Rejected: Python-style significant indentation (§9). When the rejected choice is right: significant indentation wins when the primary authors are already Python or YAML natives who want minimal punctuation (§9).

Numbers: f64 plus big integers (ADR-22)

Chosen: IEEE-754 f64 plus arbitrary-precision integers, because configuration leans on integers, with floats only when necessary (§9). Rejected: fixed-width i64-only and decimal128 (§9). When the rejected choice is right: decimal128 wins for financial configuration where float rounding at the edges is unacceptable (§9).

Roads not taken (§36)

An internal DSL embedded in a host language (Alternative 1, Terra on Lua): it wins for rapid systems-DSL prototyping where reusing a mature host's debugger, packages and REPL beats owning the toolchain. It is rejected because the host's ambient authority defeats the capability sandbox (P3, §36).

Constraint merging in the CUE style (Alternative 2): it wins for schema-merging-heavy configuration, layering N partial overrides with no functions. It is rejected because functions are a first-class goal and lattice unification under higher-order functions is harder to reason about than HM (§36, ADR-05).

A query-based incremental architecture in the Salsa/rust-analyzer style (Alternative 3): it wins when editor responsiveness, a sub-second recheck of one edited file, is a day-one requirement. It is rejected for Phase 0 because it replaces the linear pipeline with memoized queries, a large upfront cost; it is deferred, not dropped (§36, §37, MM7).

Bytecode-VM-first (Alternative 4, Starlark): it wins for repeated re-evaluation of the same config where interpreter dispatch dominates. It is rejected for Phase 0 because the phase is a correctness kernel, and the tree-walker later serves as a reference oracle for a VM reused from a sibling project (§36, ADR-15).

What must never be false

  • I1: every well-typed Phase 0 program terminates. Noticed by the conformance eval/* suite's 5 s wall-clock harness; telemetry eval.timeout_total (§7).
  • I2: the occurs check rejects every infinite type. Noticed by an in-progress unification walk; typeck.occurs_rejections_total (§7).
  • I3: a function cannot invoke a capability its own type signature does not accept. Noticed by a runtime double-check trap; eval.capability_denied_total (§7).
  • I4: every diagnostic has at least one primary span. Enforced at compile time because the field is not optional, so nothing is measured at runtime (§7).
  • I5: format(format(x)) == format(x) on every corpus fixture. Noticed by the idempotency property test; fmt.idempotency_failures_total (§7).
  • I6: the import graph is acyclic. Noticed when the DFS meets a gray node; resolve.import_cycle_total (§7).
  • I7: a type variable's level never exceeds the level at its point of generalization. Noticed by a debug assert in generalize(); typeck.level_violations_total (§7).
  • I8: row unification never produces a duplicate field label. Noticed by a row-merge assertion; typeck.row_conflicts_total (§7).
  • I9: the REPL, the LSP and dsl eval parse identical input identically. Noticed by re-running the parse/* fixtures through all three front ends in CI; parse.frontend_divergence_total (§7).
  • I10: evaluation order is left to right, depth first, stable across releases. Noticed by order-sensitive eval/* fixtures; eval.order_mismatch_total (§7).
  • I11: Value::Float equality is bitwise, not NaN-sensitive, to match JSON semantics. Noticed by the float-equality fixture; eval.float_eq_mismatches_total (§7).
  • I12: the lexer never panics on any byte sequence. Noticed by the lex fuzz target; fuzz.lex_crashes_total must stay 0 (§7).
  • I13: the LSP never blocks its main loop on one malformed document. Noticed by an integration test with a malformed document plus a concurrent hover; lsp.blocked_requests_total (§7).
  • I14: capability values are constructed only at the lume-cli entry point. Noticed by code review and negative effects/* fixtures; eval.ambient_capability_total must stay 0 (§7).

What breaks in production

Phase 0 has no daemon, so "production" means the CLI in CI, the LSP in an editor and the release pipeline (§1, §26).

  • FM-1: the parser appears to hang. Root cause: a recovery synchronization point that never advances the token cursor. Detection: the parse fuzz target and a wall-clock parse timeout in CI. Recovery: none automatic; it is treated as an internal compiler error, and the fix is to guarantee the synchronizer advances, plus a regression fixture (§25).
  • FM-2: the type checker never terminates on a small input. Root cause: an occurs-check bypass or an unbounded generalization loop. Detection: the types fuzz target and a type-check timeout. Recovery: none automatic and never silently retried, because it signals a soundness bug; patch unify() or generalise() and add the input to the occurs-check negative corpus (§25).
  • FM-3: the evaluator overflows its stack. Root cause: native recursion used for a traversal-only operation on a deeply nested structure. Detection: a crash report plus a fuzzed deep-nesting fixture. Recovery: convert that traversal to an explicit-stack walk and add the input as an eval regression fixture (§25).
  • FM-6: the REPL accepts input the file compiler rejects, or the reverse. Root cause: a REPL-local grammar branch added by mistake. Detection: the I9 three-front-end replay job in CI. Recovery: release-blocking; remove the branch and restore the shared Parser entry point (§25, P11).
  • FM-7: a capability appears where none was granted. Root cause: drift between the Phase 4 and Phase 6 type representations. Detection: the runtime double-check trap firing on code the type checker approved. Recovery: evaluation aborts with a diagnostic; patch the representation and add an effects/ fixture (§25, I3).
  • FM-10: a golden diagnostic silently goes stale. Root cause: a message was improved without updating its snapshot. Detection: the insta snapshot diff in CI. Recovery: CI-blocking by design; review the diff, then accept it or revert (§25, ADR-10).

Threats worth knowing (§24):

  • T2: a malicious imported module tries to smuggle a capability through a closure. Answered by capabilities being values the type system tracks (P3, I3).
  • T6: a deeply nested expression overflows the native stack. Answered by an explicit recursion-depth counter, 512 levels in the parser by default (§4, §24).
  • T9: a user-supplied regex with catastrophic backtracking (ReDoS). Answered by a bounded- backtracking engine only, informed by Cloudflare's July 2, 2019 outage (§24, §3). §18 instead says that outage informs "T10's mitigation choice", and §24's T10 is the renderer timing channel (§18).
  • T12: a crafted config makes the YAML encoder emit something a downstream parser misreads. Answered by emitting only the safe core schema, no custom tags, no anchors by default (§24).

How it compares

  • Nickel chose gradual typing, with contracts checked at merge points. That is fine for authors who must mix untyped legacy data with typed new code during a migration, which Lume's fully static Phase 0 design does not serve directly (§33).
  • Dhall chose totality with no recursion at all, plus import-by-hash content addressing. That fits cases where reproducibility and auditability of imports matter more than expressiveness (§33).
  • CUE chose constraint-lattice unification instead of a function-oriented type system. That is right when the main job is merging many partial schemas and overrides with no user functions, as in Kubernetes manifest layering (§33, §36).
  • Jsonnet chose no static types, with validation left to runtime or an external schema. That is fine when authoring speed for small, short-lived configuration matters more than compile-time guarantees (§33).

If you only remember three things

Lume makes a configuration language safe to run on untrusted input by construction: types are checked before evaluation, every well-typed program terminates, and effects are values passed in, never ambient (P2, P3, I1, I3). The REPL, the LSP and dsl eval share one parser and one checker, enforced by a three-front-end replay job, and the formatter is held to a round-trip property test (P11, I9, I5). The error message is the product, so every failure becomes a structured diagnostic with a primary span, and the pipeline is meant never to panic on bad input (P1, I4, §4).

Words used here

  • Span: a file plus start and end byte offsets pointing into source (§38).
  • Trivia: whitespace and comments kept on tokens so the formatter can reproduce them (§38).
  • Pratt parser: an operator-precedence parser driven by per-token binding powers (§38).
  • Unification: solving "these two types must be equal" during inference (§38).
  • Level: a number on a type variable recording let-nesting depth, used to decide what to generalize (§38, MM2).
  • Occurs check: the test that stops a type variable from unifying with a type containing itself (§38, I2).
  • Row: a record's field map plus an optional tail variable meaning "maybe more fields" (§38).
  • Sum type: an anonymous tagged union, checked for exhaustiveness at match (§38).
  • Capability: a value that grants the right to perform one kind of effect (§38, P3).
  • Thunk: a deferred, memoized computation, used only to implement let rec (§38).
  • Diagnostic: the structured error or warning value rendered by both renderers (§38, P7).
  • Deferred Features Register: the table mapping each PhaseDeferred call site to its un-defer trigger (§38, §37).
