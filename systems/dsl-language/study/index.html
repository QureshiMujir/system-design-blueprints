32. Mental Models & First Principles

MM1 — A type is a compile-time proof that a program will terminate, not a label. HM inference treats every expression's type as something derived, not merely annotated. Predicts: a unification failure signals a missing inductive case, not a cosmetic mismatch. Bug class without it: accepting ill-typed configuration that is only caught at evaluation time, in production. Applies in Phase 4 (§16).

MM2 — Levels are a lightweight region inference for generalization. A TyVar's level (Pottier & Rémy 2005) tracks "how deep in let-nesting was this introduced" — the same question region inference asks about allocation scope. Predicts: level-adjustment bugs look exactly like region-escape bugs. Bug class without it: reverting to the classical O(n²) generalization walk, or generalizing a variable that should stay monomorphic. Applies in Phase 4 (§16), I7.

MM3 — A capability is a physical key, not a permission bit. Possessing the value is possessing the authority; there is no separate ambient check. Predicts: a function's type signature alone tells you every effect it can possibly perform. Bug class without it: ambient-authority leaks only a runtime audit — never a type-check — would catch. Applies in Phase 6 (§18), P3.

MM4 — The formatter is the parser run backwards. Any AST shape the parser can produce, the formatter must be able to re-render, and the round-trip property test (I5) is the actual specification, not documentation. Bug class without it: "good enough" formatter heuristics that silently corrupt rare AST shapes. Applies in Phase 8 (§20), I5.

MM5 — A diagnostic is a proof of what a human needs to know, span-first. The primary span is the claim; the message is the argument; the hint is the suggested next step (P1). Predicts: a diagnostic without an actionable primary span will be misread regardless of prose quality. Bug class without it: technically-correct diagnostics that are unusable in practice because the span points at the wrong token. Applies in Phase 5 (§17).

MM6 — Row polymorphism means a record type does not know its own tail. A function polymorphic in a row variable works on any record with at least the fields it uses, without knowing what else is present. Predicts: this is precisely what makes record-accepting functions extensible without a caller-side cast. Bug class without it: over-constraining record parameters to an exact shape, breaking extensibility the moment a caller adds one field. Applies in §8 Domain Model, Phase 4 (§16).

MM7 — A query system turns a compiler pass into a memoized graph node, not a batch step. Predicts: incremental recompute cost is proportional to the size of the dependency subgraph touched by an edit, not the whole project. Bug class without it: a whole-module-recompile LSP that cannot scale past a modest file size (Phase 9's Phase-0 limitation, §21). Applies in §31 Scalability Analysis, §36 Alternative 3.

MM8 — The occurs check is the one line standing between Hindley-Milner and non-termination. Predicts: any "optimization" that skips or weakens the occurs check reintroduces a soundness hole, not merely a slow path. Bug class without it: the type checker itself hangs on input shaped like \x. x x. Applies in Phase 4 (§16), I2, P12.

MM9 — A capability's authority is exactly its type, never its runtime value's contents. Predicts: two Capability::FileRead values with different PathScopes are different authorities even though they share a variant tag — the scope, not the tag, is what a reviewer must check. Bug class without it: treating "has a FileRead capability" as a single yes/no fact and missing a scope-widening bug. Applies in Phase 6 (§18), §11 Core Schema.

MM10 — A conformance fixture is a claim about the language, not about the implementation. Predicts: a fixture should be written so it would still be correct against a hypothetical from-scratch reimplementation of Lume, not merely against lume-eval's current internals. Bug class without it: fixtures that accidentally pin an implementation detail (e.g. a specific error-message wording never promised as stable), turning routine refactors into false regressions. Applies in Phase 10 (§22), §28 Testing & Verification Strategy.

5. Required Reading

Books

  • Nystrom, R. Crafting Interpreters. craftinginterpreters.com, 2021. Parts I & II — applied in Phase 1 (§13), Phase 2 (§14), Phase 6 (§18).
  • Cooper, K., Torczon, L. Engineering a Compiler (2nd ed). Morgan Kaufmann, 2011. Ch. 4–6 (parsing, name resolution, type systems) — applied in Phase 2 (§14), Phase 3 (§15), Phase 4 (§16).
  • Pierce, B. Types and Programming Languages. MIT Press, 2002. Ch. 1–11, 22–23 (HM), 28–29 (structural typing) — applied in Phase 4 (§16), §8 Domain Model.
  • Peyton Jones, S. The Implementation of Functional Programming Languages. Prentice Hall, 1987. HM inference, strict/lazy evaluation — applied in Phase 4 (§16), Phase 6 (§18).
  • Fowler, M., Parsons, R. Domain-Specific Languages. Addison-Wesley, 2010. Internal-vs-external DSL tradeoffs, semantic-model design — applied in §1 Goal & Scope, §2 Why Build This.
  • Aho, A., Lam, M., Sethi, R., Ullman, J. Compilers: Principles, Techniques, and Tools (2nd ed). Addison-Wesley, 2006. Ch. 3–6 (lexing, parsing, syntax-directed translation) — applied in Phase 1 (§13), Phase 2 (§14).
  • Harper, R. Practical Foundations for Programming Languages (2nd ed). Cambridge University Press, 2016. Ch. 9–11 (type systems, structural typing) — applied in Phase 4 (§16), §8 Domain Model.

Papers

  • Pratt, V. Top Down Operator Precedence. POPL, 1973 — applied in Phase 2 (§14), ADR-03.
  • Damas, L., Milner, R. Principal type-schemes for functional programs. POPL, 1982 — applied in Phase 4 (§16), I5.
  • Milner, R. A Theory of Type Polymorphism in Programming. Journal of Computer and System Sciences, 1978 — applied in Phase 4 (§16).
  • Rémy, D. Type Checking Records and Variants in a Natural Extension of ML. POPL, 1989 — applied in Phase 4 (§16), §8 Domain Model.
  • Wand, M. Complete Type Inference for Simple Objects. LICS, 1987 — applied in §8 Domain Model.
  • Pottier, F., Rémy, D. The Essence of ML Type Inference. In Advanced Topics in Types and Programming Languages (ATTAPL), MIT Press, 2005 — applied in Phase 4 (§16), I7.
  • Wadler, P. A Prettier Printer. Essay, 1998 (revised in The Fun of Programming, Palgrave, 2003) — applied in Phase 8 (§20).
  • Cardelli, L. Basic Polymorphic Typechecking. Science of Computer Programming, 1987 — applied in Phase 4 (§16).

Reference Implementations

  • Nickel — github.com/tweag/nickel. Study core/typecheck and the merge operator. Lesson: contracts-as-values complement static types. Pitfall: do not copy Nickel's gradual-typing boundary verbatim — Phase 0 is fully static. Applied in §8 Domain Model, ADR-05.
  • Dhall — github.com/dhall-lang/dhall-lang, dhall-lang.org. Study the standard's normalization-by-evaluation spec. Lesson: an exhaustively specified language is a conformance suite waiting to be written. Pitfall: Dhall's import-by-hash total-functional-programming model is out of Phase 0 scope. Applied in §8 Domain Model, §28 Testing & Verification Strategy.
  • CUE — github.com/cue-lang/cue. Study the constraint-unification evaluator. Lesson: unification-based configuration merging is a genuinely different model from HM inference. Pitfall: do not conflate CUE's lattice-unification semantics with this project's HM-plus-rows semantics. Applied in ADR-05, §36 Alternative Architectures.
  • Roc — github.com/roc-lang/roc, crates/compiler/{parse,type,can}. Lesson: a small, modern, well-engineered HM implementation with rustc-grade errors. Pitfall: Roc's platforms/effects model is closure-based, not capability-value-based — do not copy directly. Applied in Phase 4 (§16), Phase 5 (§17).
  • Gleam — github.com/gleam-lang/gleam, compiler-core. Lesson: exhaustiveness checking and a friendly error renderer on a small dependency footprint. Pitfall: Gleam targets BEAM/JS; this project targets a sandboxed tree-walker only. Applied in Phase 5 (§17).
  • rust-analyzer — github.com/rust-lang/rust-analyzer, crates/hir, crates/lsp. Lesson: incremental compilation as a discipline. Pitfall: full incrementality is explicitly deferred (§37) — do not over-engineer Phase 0. Applied in Phase 9 (§21), §37 Deferred Features Register.
  • rustc — compiler/rustc_errors, compiler/rustc_parse. Lesson: multi-label diagnostics with primary/secondary spans and machine-applicable suggestions. Pitfall: rustc's diagnostic surface is enormous; Phase 5 implements a deliberately minimal subset. Applied in Phase 5 (§17).

RFCs / Specifications

  • The Dhall language standard — dhall-lang.org/dhall-lang/standard — applied in §8 Domain Model as a specification-rigor benchmark.
  • RFC 8259 — The JSON Data Interchange Format — applied in Phase 6 (§18), stdlib JSON encoder.
  • The Language Server Protocol Specification 3.17 — microsoft.github.io/language-server-protocol — applied in Phase 9 (§21).
  • IEEE 754-2019 — Floating-Point Arithmetic — applied in §8 Domain Model, I11.
  • Unicode 15.1, UAX #31 — Unicode Identifier and Pattern Syntax — applied in Phase 1 (§13).

If these are not read before Phase 1 begins, the outcome is a parser that crashes on a UTF-8 BOM, a type checker that loops on let id = \x. x in id id, and diagnostics that point at the wrong column.

Glossary (§38) · 49 terms · site-wide glossary

ADR
: Architecture Decision Record; §9's locked, rationale-bearing decision table.
Arena
: a bump-allocated memory region (bumpalo) owning every AST node for one compilation unit; freed in bulk (ADR-04).
AST
: Abstract Syntax Tree; the parser's structured output (§11).
Big-step semantics
: an evaluation rule that relates an expression directly to its final value, as used in §8's Evaluation Semantics table.
Capability
: a value that grants the right to perform an effect (file read, network, process exec); never ambient (P3).
Capability token
: an instance of a Capability value, constructed only at the lume-cli entry point (I14).
Closure
: a runtime Value pairing a function body with its captured environment (§11).
Conformance fixture
: a named YAML input/expected-output pair pinning one normative semantic (§22).
Deferred Features Register
: the table (§37) mapping every PhaseDeferred call site to its anchor, building phase, and un-defer trigger.
Diagnostic
: the structured error/warning value (§11) rendered by both the human and JSON renderers (P7).
EBNF
: Extended Backus-Naur Form; the grammar notation used in §8.
Environment chain
: the persistent linked structure mapping identifiers to values during evaluation (§11).
Free type variable
: a TyVar not bound by an enclosing Forall; the target of generalization (§8).
Generalization
: replacing a type's free variables, not escaping the current level, with universally quantified variables at a let boundary (§8, I7).
Golden fixture
: a conformance fixture whose expected output is a checked-in reference value, diffed on every run.
HM (Hindley-Milner)
: the type-inference discipline this project implements via Algorithm W (§8, Damas & Milner 1982).
Instantiation
: replacing a Forall scheme's bound variables with fresh TyVars at a use site (§8).
JSON-shaped value
: a Value restricted to the JSON data model (null, bool, number, string, list, record) — the interpreter's output contract (I11).
Level
: an integer tag on a TyVar tracking let-nesting depth, used for level-based generalization (Pottier & Rémy 2005, §32 MM2).
Lume
: the language name; the binary is dsl; the file extension is .lm (ADR-20).
LSP
: Language Server Protocol; the editor-integration protocol served by lume-lsp (§21).
Occurs check
: the unification-time check preventing a type variable from unifying with a type that contains itself (§8, I2, P12).
Pratt parser
: an operator-precedence parser using token-bound binding powers (Pratt 1973, ADR-03).
Principal type
: the most general type inferable for an expression under HM (§8).
Property test
: a test asserting a general property (e.g. format(format(x)) == format(x)) over many generated inputs, not one fixed case (I5, §28).
Row
: a record type's field map plus an optional tail variable enabling structural extension (§8, §11, I8).
Row polymorphism
: the ability of a function to accept any record with at least a required set of fields (Rémy 1989, §32 MM6).
Row tail
: the Option<TyVarId> on a Row representing "possibly more fields, unknown to this function" (§11).
Snapshot test
: a test comparing rendered output (typically a diagnostic) against a checked-in reference file (insta, ADR-10).
Span
: a (file, start, end) byte-offset triple pointing into source (§11, I4).
Structural typing
: type identity determined by shape, not by a declared name (P4).
Sum type
: an anonymous tagged union of alternatives (§8's sum_ty), checked for exhaustiveness at match sites.
Tag
: a sum type's named alternative constructor (e.g. "ok", "err" in §8's grammar).
Thunk
: a deferred, memoized computation used only to implement let rec recursion (§11, I1).
Total (totality)
: the guarantee that every well-typed Phase-0 program terminates (P2, I1).
Trivia
: whitespace, comments, and doc-comments preserved through lexing and parsing for the Formatter and LSP (§13).
Type scheme
: a Forall-quantified type representing a polymorphic binding (§8).
Union-find
: the data structure backing lume-types::unify's substitution table, with path compression for near-constant-time lookups (§30).
Unification
: the algorithm solving type-equality constraints during inference (§8, Damas & Milner 1982).
Value restriction
: the discipline of generalizing only at let boundaries, avoiding unsound generalization of effectful expressions (§6 P12-adjacent, Phase 4 §16).
Canonical path
: the fully resolved, symlink-free filesystem path used to key the module cache, distinct from the relative import path a source file writes (§15, I6).
Debounce
: delaying a recomputation (e.g. LSP diagnostics) by a fixed interval after the last input event, to avoid recomputing on every keystroke (§21, I13).
Distroless
: a container base image containing only an application and its runtime dependencies, no shell or package manager (ADR-24).
Exhaustiveness checking
: verifying at type-check time that a match_expr handles every tag of a sum type (§8, Phase 4 §16).
MSRV
: Minimum Supported Rust Version; pinned to 1.78 via rust-toolchain.toml (ADR-01).
Prelude
: the implicit outermost scope wrapping every module, providing the stdlib builtins without an explicit import (Phase 3 §15).
ReDoS
: Regular-expression Denial of Service, a catastrophic-backtracking vulnerability class; mitigated by a bounded-backtracking regex engine (T9, §24).
SBOM
: Software Bill of Materials; a manifest of every dependency in a release artifact (§29).
SemVer
: Semantic Versioning; the compatibility contract for dsl's own crate versions (§27).
