Project Number: 62

Project Name: Lexer / Tokenizer

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade lexer/tokenizer toolkit — mini-lex — that ships two artefacts sharing one runtime contract: (1) a procedural macro (#[derive(MiniLex)]) that consumes per-token regex-like rules and emits a longest-match DFA-driven scanner with zero allocation in the hot path, and (2) a hand-written reference lexer for one seed language (a TypeScript-like surface) that is the conformance ground truth both backends are held to. The toolkit owns spans, trivia, lexer modes (string interpolation, raw strings), the off-side (indentation) rule, and incremental relexing for editor integration. It does not parse: no AST, no grammar, no operator precedence — token streams out, nothing else.

Phase-0 deliverable (numbered):

  1. mini-lex-runtime crate — Cursor, Span, SourceMap, Token/TriviaToken, ModeStack, IndentStack, LexError, the Lexer trait.
  2. mini-lex-reference crate — hand-written scanner for the seed language, passing the 200-fixture token corpus.
  3. mini-lex-cli crate — mini-lex tokenize <file> emitting (kind, span) JSON.
  4. conformance/runner — fixture-driven differential test harness.
  5. benchmarks/throughput.rs — MB/s measurement harness (populated in Phase 11, wired in Phase 0).

System boundaries. Provides: byte-accurate tokenization, span/trivia tracking, mode-stack-driven lexing (interpolation, raw strings), off-side indentation tokens, lexical error recovery, incremental relexing given a prior token stream and an edit envelope. Delegates: string-escape unescaping, numeric-literal parsing/conversion, identifier interning/symbol-table construction, syntax-tree construction, semantic analysis — all to the consumer (a parser, a linter, an IDE backend). Does NOT provide: parsing, macro expansion, encoding negotiation beyond UTF-8 detection, a language server protocol implementation.

Non-goals. Multi-language grammar sharing beyond the rule-attribute DSL; a general regex engine at runtime (§8 distinguishes this explicitly); backtracking lexing; context-free lexing (the mode stack is the only context mechanism, by design, P5).

Deployment model. An embedded library, not a service: linked into the consumer's binary (compiler, linter, formatter, IDE backend) or invoked via the mini-lex-cli standalone binary for scripting/debugging. No daemon, no network boundary, no persistent state across process invocations except what the embedder chooses to cache (e.g. an IDE's prev_tokens for incremental relexing).

Target users/operators. Compiler- and tool-authors building a new language frontend; IDE/language-server authors needing sub-millisecond incremental relex; the project's own downstream consumer, Parser-Combinator (project 65), which takes this toolkit's token stream as its sole input.

What later phases unlock. Phase 1 (hand-written reference) unlocks a conformance ground truth with no dependency on the generator. Phase 4 (DFA) unlocks the generator producing a correct-but-unoptimised scanner. Phase 5 (codegen) unlocks throughput competitive with logos/re2c. Phase 9 (trivia) unlocks byte-exact source reconstruction for formatters. Phase 10 (incremental) unlocks the IDE integration path (rust-analyzer/Roslyn-shaped). Phase 11 (conformance/fuzz/bench) unlocks the Sealed gate.

Recommended language + rationale. Rust (edition 2024) for both runtime and generator. Rationale: the proc-macro toolchain (proc-macro2/syn/quote) is the most production-mature metaprogramming story for a compile-time DFA generator; no_std-capable core lets the runtime embed in constrained/Wasm targets; zero-cost abstractions make the "hot path never allocates" invariant (I8) enforceable at the type level. Rejected languages: Haskell + Template Haskell/alex — cleaner academic story for the automaton theory but a weaker "embed in an arbitrary host toolchain" story and a smaller pool of downstream embedders (ADR-01). OCaml + ppx/ocamllex — excellent for the reference compiler community but the generated code is OCaml-only, defeating the "generate into the embedder's own crate" goal (ADR-01). C via flex/re2c directly — no memory-safety guarantee for a component that reads untrusted bytes first in the pipeline (I7).

Prerequisites. Finite-automata theory at the level of ALSU ch.3 (regular expressions, NFA, subset construction, Hopcroft minimisation); intermediate Rust (lifetimes, traits, generics, the proc-macro trifecta, unsafe rules of engagement); enough compiler-internals literacy to read rustc_lexer and Roslyn's Lexer.cs end to end before committing a line (§5).

Estimated timeline. Phase 0 (skeleton + correctness kernel): 1 week. Full system (Phases 0–11): 10 weeks core path, 4–6 months including the stretch surfaces deferred to the Deferred Features Register.

Deferred features (all flagged with the PhaseDeferred marker, registered in §37 Deferred Features Register): Brzozowski-derivative backend PhaseDeferred("§16.2"); Wasm runtime target PhaseDeferred("§29"); SIMD whitespace-skip fast path PhaseDeferred("§13.7"); here-document lexer mode PhaseDeferred("§20.2"); tree-sitter external-scanner C ABI PhaseDeferred("§23"); 30-day continuous fuzz (Sealed gate) PhaseDeferred("§23.4").

2. Why Build This

A lexer is the first stage of every compiler, interpreter, linter, formatter, syntax-highlighter, and refactoring tool with more than two token classes — the front door of the language-tooling stack, and, more than any other single layer, the place where correctness is silently lost: a stray \r\n inside a here-document, a UTF-8 BOM that shifts every byte offset by three, a raw string closed by the wrong delimiter, an off-side stack that drifts after a tab/space mix, a /* comment whose embedded */ was meant to stay inert. Every serious language tool ships its own hand-written lexer (rustc, Roslyn, Swift, V8, the Tree-sitter family) precisely because the cost of an edge case shipped wrong here is the cost of every downstream consumer inheriting it, simultaneously, forever.

This toolkit is deliberately the smallest system that still teaches the full surface: the regex frontend, Thompson NFA construction, subset construction to a DFA, Hopcroft minimisation, a code generator that turns the minimised DFA into a jump table or match-arm tree, byte-offset span infrastructure with BOM/encoding recovery, a trivia model that reconstructs every source byte from the token stream, the off-side rule, a lexer-mode stack that makes string interpolation tractable, and the incremental relexing path rust-analyzer and Roslyn use to keep IDE latency in the single-digit-millisecond range. It builds the engineering muscle of "automaton theory as a compile-time code generator" — the same muscle re2c, logos, and flex exercise — and is the direct architectural sibling of Regex-Engine (project 63, one theory, two different runtime shapes, §8) and the direct upstream dependency of Parser-Combinator (project 65, which consumes this toolkit's token stream verbatim).

A lexer is also one of the few compiler components with a hard, measurable, and widely published performance number: sustained MB/s of source consumed with full span and trivia tracking enabled — not a stripped microbenchmark. §31 (Performance Engineering) calibrates this toolkit's targets against published numbers from logos, re2c, flex, and the rustc lexer.

What Mastery Looks Like (5–8 competencies, each tied to the phase that builds it):

  1. Deriving a longest-match DFA from a rule set by hand (Thompson → subset construction → Hopcroft) and predicting its state count before running the generator — Phase 3 (§14), Phase 4 (§16).
  2. Diagnosing a tokenization disagreement between two lexer implementations by constructing the minimal distinguishing input — Phase 1 (§13), Phase 11 (§23).
  3. Designing a span/trivia model that survives BOMs, mixed line terminators, and multi-line tokens without losing byte-exact reconstruction — Phase 6 (§18).
  4. Reasoning about lexer modes as a pushdown extension to a regular language, and knowing exactly where that extension is and is not sound — Phase 8 (§20).
  5. Building an off-side (indentation) stack that is provably a monotonic stack machine, not an ad hoc column counter — Phase 7 (§19).
  6. Implementing an incremental relexing algorithm whose correctness argument does not depend on its performance argument — Phase 10 (§22).
  7. Reading and critiquing three production lexers (rustc_lexer, Roslyn's Lexer.cs, logos-codegen) against one's own design decisions — §5, §32.

Three properties are referenced throughout this document. First, the runtime crate never depends on the proc-macro crate at runtime (ADR-01, ADR-17); generated code expands into the embedder's own crate and references only mini_lex_runtime types. Second, the hand-written and generated lexers implement the same Lexer trait (P2, §11.5) and pass the same conformance fixtures (§28); an embedder swaps one for the other transparently. Third, the trivia model and span model are owned by the runtime, never duplicated per-backend (P3, P4) — span arithmetic and trivia attachment happen exactly once.

6. Design Principles

  1. P1 — Ground-Truth Duality. The hand-written reference lexer for the seed language is the conformance baseline; the generated lexer must produce an identical token stream (modulo documented trivia-placement differences resolved by the trivia normaliser). Tradeoff: doubles the implementation surface for the seed language. Operational implication: every conformance fixture is authored once and run against both backends. Violating it: the generator silently diverges and nobody notices until an embedder files a bug.
  2. P2 — One Trait, Two Backends. The runtime exposes exactly one Lexer trait; the proc-macro and the hand-written module both implement it; backend selection happens in exactly one place (the embedder's feature flag). Tradeoff: the trait must be conservative enough for both implementation styles. Violating it: downstream code branches on backend identity, defeating the swap guarantee.
  3. P3 — Spans Are Mandatory. Every token carries Span{start,end} as byte offsets; line/column is a SourceMap service, not a per-token field. Tradeoff: the hot path always pays one increment per byte for position tracking. Violating it: two lexer configurations ("with spans"/"without") that must be independently maintained.
  4. P4 — Trivia Is Recoverable By Default. Whitespace, comments, shebangs are trivia tokens with their own spans; concat(token.bytes) == source_bytes (I3) always holds. Tradeoff: every trivia byte is a token object, not a discarded byte. Violating it: no tool downstream can reformat or diff source losslessly.
  5. P5 — Modes Are Explicit. Lexer modes are a runtime-owned stack, not a per-backend hack; rule actions call mode_push/mode_pop. Tradeoff: the mode stack is shared state both backends must thread correctly. Violating it: string interpolation, raw strings, and regex/division disambiguation each reinvent their own ad hoc state machine.
  6. P6 — Off-Side Is Explicit. IndentStack is a runtime feature, not a seed-language special case; it injects virtual Indent/Dedent tokens. Tradeoff: every embedder pays for the indent-stack type even if their language has no off-side rule (it is simply unused). Violating it: indentation-significant languages each hand-roll a column counter with no shared correctness argument (I6).
  7. P7 — Errors Are Tokens, Not Exceptions. A lex error emits Token::Error(kind, span) and lexing continues; there is no exception out of the hot path. Tradeoff: every consumer must handle Error as an ordinary token kind. Violating it: one malformed byte anywhere in a 10 MB file aborts the entire lex.
  8. P8 — The Hot Path Does Not Allocate. (TokenKind, Span) is Copy; string/escape unescaping and identifier interning are the parser's job, not the lexer's. Tradeoff: the lexer returns raw byte slices the consumer must re-scan for semantic content. Violating it: I8 fails and the throughput targets in §4/§31 become unreachable.
  9. P9 — Incremental Is First-Class. IncrementalLexer is part of the runtime, not a bolt-on; apply_edit is provably minimal under the single-alignment-region assumption. Tradeoff: the runtime types (SourceMap, Span, mode/indent stacks) must be designed for reuse across edits from day one. Violating it: incremental support requires rewriting the runtime later (Key Pitfall, §Phase 10).
  10. P10 — One SourceMap Per File, One Arena Per Session. SourceMap is constructed once, shared by parser/diagnostics/IDE; its only allocation (the line table) is lazy, built on first column query. Tradeoff: the first column query in a session pays an O(n) table-build cost. Violating it: every consumer builds its own redundant line table, quadrupling memory for multi-consumer pipelines.
  11. P11 — Determinism Is Non-Negotiable. Same (source bytes, rule set, config) → identical token stream, byte-for-byte, across builds/OS/CPU architectures. Tradeoff: forecloses any nondeterministic optimisation (e.g. unordered hash-based tie-breaking). Operational implication: conformance fixtures and fuzz differential tests (§28) are only meaningful under this guarantee. Violating it: a flaky conformance suite that cannot distinguish a real regression from build noise.
  12. P12 — Compile-Time Cost Is A Budget, Not Free. DFA generation (NFA build, subset construction, minimisation, codegen) is bounded by explicit state-count and wall-clock caps (§4) because it runs on every cargo build of every embedder. Tradeoff: very large rule sets (>100k states) hit a hard compile_error! rather than a slow but successful build. Violating it: an unbounded generator becomes an invisible tax that degrades every downstream developer's edit-compile-test loop.

These are enforced at the type level where possible (P3, P8), by CI gate where not (P11, P12), and by the conformance harness everywhere else (P1, P2).

I9 Errors are tokens: next_token never returns Result::Err, lexing always continues. P7; a Result-based API forces halt-on-first-error. Every lex_* rule's error path (§13). errors.recovery conformance bucket. lex.error_total{kind} counter per LexError variant. Rule-specific resynchronisation point (§Failure Modes FM-2..FM-6).
I10 BOM exactly-once: consumed at Cursor construction; every span is post-BOM. ADR-08; a double-counted or dropped BOM shifts every span by 3 bytes. Cursor::consume_bom (§11.3). spans.bom conformance bucket. lex.bom_detected_total counter. N/A — single deterministic code path.
I11 Keyword-promotion exactness: zero false positives/negatives against the closed keyword set. CHD PHF construction can silently under-separate keys if the set drifts (ADR-06). perfect_hash.rs codegen + exhaustive build-time check. tokens.seed fixture includes one case per keyword. none (compile-time). N/A — a PHF collision is compile_error!, never a runtime state.
I12 Incremental alignment soundness: prev + apply_edit(...) == from_scratch_lex(new_source), token-by-token. The entire incremental contract (P9); a cheap-but-wrong relex corrupts IDE state silently. IncrementalLexer::apply_edit alignment check (§22). Property test, 10k random edits, incremental fixture bucket. lex.incremental_realign_total, lex.incremental_partial_total. On alignment doubt, degrade to full relex from the edit point to EOF — correctness never trades against speed.

Debugging methodology: conformance/runner runs in a differential mode that lexes each fixture with both backends and with MIRI-instrumented builds, asserting I1–I12 hold token-by-token; a single assertion failure fails the whole conformance run (§28).

8. Domain Model

The domain model is a token grammar (EBNF, describing what byte sequences form which token classes for the seed language), a DFA state-transition table (how the automaton realises that grammar), one worked example, one malformed-input example, and one failure-path example.

8.1 Token grammar (EBNF, seed language)

token        = trivia | punct | literal | ident_or_kw | error ;
trivia       = whitespace | newline | line_comment | block_comment | shebang ;
whitespace   = ( " " | "\t" )+ ;
newline      = "\n" | "\r\n" ;                      (* bare "\r" is UnknownToken, §13.9 *)
line_comment = "//" , { any_char - newline } ;
doc_comment  = "///" , { any_char - newline } ;
block_comment= "/*" , { block_comment | any_char } , "*/" ;   (* nests, §13.6 *)
ident_or_kw  = xid_start , { xid_continue } ;                  (* UAX#31, promoted via PHF *)
literal      = number | string | template ;
number       = decimal | hex | binary ;
decimal      = digit , { digit | "_" } , [ "." , digit , { digit } ] ,
               [ ("e"|"E") , ["+"|"-"] , digit , { digit } ] , [ "n" ] ;
hex          = "0x" , hex_digit , { hex_digit | "_" } , [ "n" ] ;
binary       = "0b" , ("0"|"1") , { "0" | "1" | "_" } , [ "n" ] ;
string       = "'" , { escape | (any_char - "'" - newline) } , "'"
             | '"' , { escape | (any_char - '"' - newline) } , '"' ;
escape       = "\" , ( "n"|"t"|"r"|"\"|"'"|'"'|"0"
             | "x" , hex_digit , hex_digit
             | "u" , hex_digit , hex_digit , hex_digit , hex_digit
             | "u{" , hex_digit , {hex_digit} , "}" ) ;
template     = "`" , { tmpl_part | ("${" , {token} , "}") } , "`" ;
punct        = "(" | ")" | "{" | "}" | "[" | "]" | "," | ";" | ":" | "."
             | "+" | "-" | "*" | "/" | "%" | "**" | "=" | "==" | "===" | "!"
             | "!=" | "!==" | "<" | ">" | "<=" | ">=" | "<<" | ">>" | ">>>"
             | "&" | "|" | "^" | "~" | "&&" | "||" | "?" | "->" | "=>" ;
error        = ? any byte sequence matching no rule above, recorded as Token::Error ? ;

Disambiguation (I1, I2): longest match wins; on a length tie, higher priority then earlier declaration order wins (the #[token("if")] vs. #[regex("[a-z]+")] fixture in §16.4).

8.2 DFA state-transition fragment (illustrative, if/ident sub-automaton)

State on i on f on [a-hj-z] on [0-9_] on other Accept
S0 (start) → S1 → S3 (via [a-z]) → S3 — dead —
S1 (i) → S3 → S2 → S3 → S3 Accept(Ident) Ident
S2 (if) → S3 → S3 → S3 → S3 Accept(If, priority) If (tie-break I2)
S3 (ident tail) → S3 → S3 → S3 → S3 Accept(Ident) Ident

S2 is simultaneously an accepting state for If (via the #[token("if")] rule) and a prefix of a longer identifier (iffy); the DFA does not resolve this at construction — it resolves it at scan time via longest-match rollback (§16.3): the scanner continues from S2 while a longer match is reachable (S3 accepts Ident), and only commits when the byte stream can no longer extend the match.

8.3 Worked example — template-literal mode-stack trace

Input: `hello ${name + "!"} world`.

Step Mode (top of stack) Bytes consumed Emitted
1 Code → push Template ` (open tick, no token — mode transition only)
2 Template hello TmplPart("hello ")
3 Template → push Code (depth_at_entry=0) ${ TmplExprStart
4 Code name Ident
5 Code + Plus (+ surrounding Whitespace trivia)
6 Code "!" StrDouble
7 Code → pop to Template (depth back to 0) } TmplExprEnd
8 Template world TmplPart(" world")
9 Template → pop to Code ` (close tick)

Mode-stack depth returns to 1 at step 9 (I5). The Code mode entered at step 3 carries depth_at_entry = 0 so a nested ${ {a:1} } is handled: the inner {/} raise local depth to 1 before the matching } at depth 0 pops back to Template (§20.2).

8.4 Malformed-input example — unterminated string

Input: let x = "unterminated (no closing quote, EOF reached mid-string).

Scanner behaviour: lex_str_double consumes bytes looking for " or newline; hits EOF first. Emission: Token::Error(UnterminatedString, span=[8,22)) covering the opening quote through EOF (I9: error is a token, not an exception). Recovery: the scanner treats EOF as the resynchronisation point — no further tokens follow; if the malformed string were instead followed by more source (e.g. \n before EOF), the resynchronisation point is that newline (§Failure Modes FM-2).

8.5 Failure-path example — mixed tabs/spaces off-side violation

Input: three lines — if x:, then y = 1 (four leading spaces), then \ty = 2 (one leading tab). Line 3 is indented with one tab where line 2 used four spaces. IndentStack::feed computes line 2's indent as 4 (byte-count policy, ADR-10-adjacent) and pushes level 4. Line 3's leading tab, under the strict no-tab-in-leading-whitespace policy (§19.5), is itself rejected before indent computation: emission is Token::Error(IndentMismatch, span=[18,19)) covering the tab byte, and IndentStack repairs by treating the line as continuing at the last valid level (4) rather than desynchronising every subsequent line (I6, FM-5).

11.1 ByteOffset, Span

#[repr(transparent)]
pub struct ByteOffset(pub u32);                       // ADR-21: u32, 4 GiB cap (I10)
impl ByteOffset {
    pub const ZERO: ByteOffset;
    pub fn as_usize(self) -> usize;
    pub fn checked_add(self, n: u32) -> Option<ByteOffset>;
}

pub struct Span { pub start: ByteOffset, pub end: ByteOffset }
impl Span {
    pub fn new(start: ByteOffset, end: ByteOffset) -> Self;   // requires start <= end
    pub fn len(self) -> u32;
    pub fn is_empty(self) -> bool;
    pub fn as_range(self) -> core::ops::Range<usize>;
    pub fn join(self, other: Span) -> Span;                   // union of two spans
}

Ownership: Copy, no allocation, owned by value everywhere (P3, P8). Mutation: immutable once constructed. Concurrency: Send + Sync trivially (plain integers). Persistence: not persisted independently; embedded in conformance fixtures as JSON {start,end}. Serialization: serde-derivable behind a feature flag; stable wire shape since Phase 0. Compatibility: widening u32 → u64 would be a breaking change (ADR-21 rejection regime).

11.2 TokenKind, Token, TriviaKind, TriviaToken

pub trait TokenKind: Copy + Eq + core::fmt::Debug + 'static {
    fn is_trivia(self) -> bool;
    fn is_error(self) -> bool;
    fn is_eof(self) -> bool;
    fn name(self) -> &'static str;
}

pub struct Token<K: TokenKind> { pub kind: K, pub span: Span }

pub enum TriviaKind { Whitespace, LineComment, BlockComment, DocComment, Shebang, NewLine }
pub struct TriviaToken { pub kind: TriviaKind, pub span: Span }

Ownership: Token<K> is Copy (P8); K is the embedder's generated or hand-written enum. Mutation: immutable. Concurrency: Send + Sync when K is. Persistence: none at runtime; conformance fixtures serialize (kind.name(), span) as golden JSON. Serialization: name() is the stable cross-version string identity (ADR compatibility anchor, not the enum's discriminant, which may be reordered). Compatibility: adding a TriviaKind variant is additive; removing one is breaking (§Compatibility & Versioning).

11.3 Cursor

pub struct Cursor<'src> { /* bytes: &'src [u8], pos: ByteOffset */ }
impl<'src> Cursor<'src> {
    pub fn new(bytes: &'src [u8]) -> Self;                 // consumes BOM, I10
    pub fn pos(&self) -> ByteOffset;
    pub fn is_eof(&self) -> bool;
    pub fn peek(&self) -> Option<u8>;
    pub fn peek_at(&self, n: usize) -> Option<u8>;
    pub fn bump(&mut self) -> Option<u8>;
    pub fn bump_while<F: Fn(u8) -> bool>(&mut self, f: F) -> u32;
    pub fn slice(&self, span: Span) -> &'src [u8];
}

Ownership: borrows the source buffer for 'src; never copies bytes (P8). Mutation: pos is the sole mutable field, monotonically increasing (I4). Concurrency: !Sync by design — one Cursor per single-threaded scan (§4 concurrency model); parallelism is achieved by one Cursor per file, not by sharing one across threads. Persistence: none. Serialization: not serializable (borrows 'src). Compatibility: internal type, not part of the public API surface embedders depend on directly (only Lexer is, §11.5).

11.5 Lexer trait

pub trait Lexer<'src> {
    type Kind: TokenKind;
    fn next_token(&mut self) -> Option<Token<Self::Kind>>;
    fn pos(&self) -> ByteOffset;
    fn slice(&self, span: Span) -> &'src [u8];
    fn source_len(&self) -> ByteOffset;
}

Ownership: implementors own or borrow their Cursor/mode-stack/indent-stack state. Mutation: next_token is the only mutating call; it advances pos monotonically (I4). Concurrency: !Sync, one instance per scan (P2's backend-swap guarantee is about implementation identity, not concurrent sharing). Persistence: none. Serialization: N/A (a trait, not a data type). Compatibility: this is the toolkit's central stable contract (P2) — adding a method is breaking for all implementors; new capability is added via a separate trait (e.g. IncrementalLexer, §11.9), never by widening this one.

pub struct ModeId(pub u16);

15. Phase 3 — Thompson NFA Construction

15.1 Objectives

Implement Thompson's construction (Thompson 1968, §5): each normalised Hir node from Phase 2 maps to a small NFA fragment (concatenation, alternation, Kleene closure, character class, optional, plus); fragments wire together into one NFA with one entry state and accepting states tagged by token id, then ε-elimination removes epsilon edges before Phase 4 consumes the result.

15.2 Detailed Implementation Steps

  • Define Nfa/NfaState (§11 note: these are generator-internal types, not part of the public runtime surface in §11.1–§11.9) — each state carries transitions (byte-class → state), epsilons (state list), an optional accept: TokenId, an optional mode: ModeId binding (P5), and an optional rule action.
  • Implement the four Thompson fragment constructors per ALSU ch.3 (§5): concatenation wires fragment A's accept states to fragment B's start via ε; alternation adds a new start with ε-edges to both fragments' starts; Kleene closure adds a ε self-loop; character-class fragments are a single two-state transition.
  • Implement ε-elimination: compute the ε-closure of every state, then materialise each state's byte-transitions as the union of every transition reachable via ε-then-byte, propagating accept tags through the closure (I1 depends on every ε-reachable accepting state being correctly tagged) — remove the ε edges once materialised.
  • ByteClass is a packed 256-bit bitmap for source = "bytes" rule sets and a sparse range list for Unicode classes under source = "str" (§14.2's normalisation decision).

15.3 Deliverable

nfa::build returns a complete, ε-free Nfa for the 50-rule fixture grammar (corpora/codegen/grammars/fifty-rule.rs) with deterministic state numbering across repeated builds (P11).

15.4 Acceptance Criteria

16. Phase 4 — Subset Construction & Hopcroft Minimisation

16.1 Objectives

Turn the ε-free NFA from Phase 3 into a DFA (subset construction) and minimise its state count (Hopcroft, ADR-04) — the last purely-automaton-theory phase before codegen (Phase 5).

16.2 Detailed Implementation Steps

  • Subset construction (ALSU ch.3, §5): start state = ε-closure({NFA start}); for each DFA state S and byte b in the effective alphabet, compute T = ε-closure({t : (s,b,t) ∈ nfa.transitions, s ∈ S}); if T is new, add it to the worklist. For source = "str", the effective alphabet is the union of the rule set's character-class partitions, never an exhaustive 0x10FFFF iteration (§4's compile-time budget, P12).
  • Accept-tag resolution on construction: a DFA state is accepting iff any constituent NFA state is; on multi-rule conflict, resolve by (longest match first, ADR unaffected — this is a construction-time tie among equal-length candidates) then explicit priority then source order (I2, ADR-05's tie-break policy).
  • Hopcroft minimisation (Hopcroft 1971, §5): partition-refine starting from {accepting states by tag} ∪ {non-accepting states}, refining by each partition's byte-transition target partitions using a worklist of splitter partitions for the n log n bound (ADR-04's rejection of the simpler-but-quadratic Moore algorithm).
  • Dead-state collapse happens strictly after minimisation: a state with no path to any accepting state is the DFA's single dead state; the runtime treats reaching it as "stop, emit longest-accept-or-error."
  • Enforce the 100,000-state minimisation budget (§4) with a compile_error! naming the approximate offending rule subset when exceeded.

16.3 Deliverable

A minimised, deterministic DFA for the 50-rule fixture and for the full seed-language grammar (~200 rules across all token classes, §8.1), with dead-state collapse applied.

16.4 Acceptance Criteria

The seed-language DFA (starting from ~200 NFA states pre-minimisation) minimises to ≤ 96 states in ≤ 50 ms wall-clock at proc-macro-expansion time (M5-adjacent, §4); a property test asserts dfa.accept(s) == nfa.accept(s) for 10,000 random inputs; a fixed tie-conflict fixture (#[token("if")] If vs. #[regex("[a-z]+")] Ident) resolves to If for input "if" and Ident for "iff" (I1, I2, §8.2's worked DFA-fragment example).

Fixture Purpose Expected Output

tests/dfa_minimise.rs::nfa_dfa_equivalence Subset-construction correctness 10k random inputs agree

16.6 Pitfalls

  • Dead-state collapse must happen strictly after minimisation, not before — collapsing early can merge a live state that only looks dead pre-minimisation with the true dead state, corrupting the automaton.
  • For source = "str", iterating the full Unicode code-point range per state is the single most common performance bug in a from-scratch subset-construction implementation; use the rule set's own character-class partition as the alphabet (§16.2).
  • DFA state count can blow up exponentially for grammars with many overlapping alternations (the classic subset-construction pathology); the 100k-state budget with a named compile_error! (§4, §16.2) is the safety valve — this is also precisely the regime PhaseDeferred("§16.2") (Brzozowski derivatives, ADR-03/ADR-14) targets for a future Phase-2 path.

16.7 Performance Concerns

Hopcroft's n log n bound is only realised if the splitter worklist is implemented with an actual queue, not a re-scan of all partitions per iteration — a naive implementation degrades to the same O(n²) Moore would have given, silently defeating ADR-04's rationale. Profile the 200-rule seed grammar specifically; it is the representative workload, not the 50-rule synthetic fixture.

16.8 Edge Cases

A DFA with exactly one accepting state and one dead state (degenerate single-rule grammar); a grammar where every rule accepts the same length at the same position (maximal tie-break stress, resolved purely by priority/order, I2); a state count that lands exactly at the 100,000-state budget boundary (accept, not reject).

16.9 Failure Analysis

A minimisation bug that merges two states that should remain distinct manifests as two different rules silently collapsing into one token kind — detected by the nfa_dfa_equivalence property test (§16.5) and, downstream, by tokens.seed (§13.5) once wired through codegen. Blast radius is every rule that shares a partition with the incorrectly-merged pair; containment is isolated to minimise.rs, verified independently of dfa.rs's subset-construction correctness by the two-stage property tests.

16.10 Operational Notes

DFA state counts and minimisation wall-clock are logged by the proc-macro at RUST_LOG=mini_lex_codegen=info (build-time only — there is no runtime telemetry for a compile-time pass); this is the primary signal an embedder uses to notice their rule set is approaching the §4 budget before hitting the hard compile_error!.

17. Phase 5 — Code Generator (Dense & Sparse Backends)

17.1 Objectives

Emit the minimised DFA from Phase 4 as Rust source via quote! (ADR-17), in two selectable backend shapes (ADR-05), plus the perfect-hash keyword post-pass (ADR-06). This is the phase that makes the generated lexer implement Lexer (§11.5, P2).

17.2 Detailed Implementation Steps

  • Implement the dense jump-table backend (codegen.rs): emit a [StateId; n_states * 256] transition table and an [Option<TokenId>; n_states] accept table; the byte loop is one indirect lookup per byte (state = TABLE[state * 256 + byte as usize]), the throughput champion (Cooper & Torczon ch.2, §5; M2's ≥100 MB/s target, §4).
  • Implement the sparse match-arm backend: emit a match state { 0 => match byte { ... }, ... } tree compiling to conditional jumps — smaller binary, selected via #[lexer(backend = "sparse")] (ADR-05's stated regime: embedded/Wasm targets with a binary-size budget).
  • Implement the CHD perfect-hash keyword post-pass (perfect_hash.rs, ADR-06, I11): collect every #[token("...")] rule into a static keyword list, emit a zero-collision PHF; after the DFA emits an Ident token, run the PHF — on a hit, promote to the keyword's token kind, on a miss, stay Ident.
  • Implement mode-aware codegen (modes.rs): when the rule set declares #[mode(...)]-tagged variants, emit one DFA per mode (or a stitched DFA with mode bits folded into the state id for shared subgraphs); the runtime selects the active DFA from ModeStack::current() (§11.6, P5).
  • Quote large tables efficiently: use proc_macro2::TokenStream::from_iter with a single extend call for the 256-entry-per-state table, not #(#x),* per element (§17.6's pitfall) — the latter is asymptotically slower at proc-macro-expansion time.
  • Emit #[inline(always)] on the byte-dispatch loop for both backends (§13.7 mirrors this for the hand-written reference; omitting it costs ~30% throughput empirically).

17.3 Deliverable

The dense backend on the seed-language grammar emits one Rust source file that compiles and implements Lexer (§11.5); the sparse backend emits an equivalent, smaller file selectable per rule set.

17.4 Acceptance Criteria

Dense backend: generated file ≤ 200 KiB, compiles in ≤ 4 s release mode on the reference machine (M5, §4). Sparse backend: ≤ 60 KiB, compiles in ≤ 1.5 s. A trybuild test asserts the generated code passes the full tokens.seed conformance corpus (§13.5) at 100% — proof of P1 (ground-truth duality) for the generated backend. The keyword PHF has zero collisions against the closed keyword list (I11), verified by a build-time exhaustive check.

17.6 Pitfalls

  • Quoting a 256-element array with #(#x),* per element is slow at macro-expansion time; use a single extend call over a pre-built TokenStream iterator instead (§17.2).
  • The const dense table forces compile-time table evaluation; on an unpinned toolchain this can silently regress — the rust-toolchain.toml pin (Phase 0, §12.1) is the defence, not a runtime check.
  • Omitting #[inline(always)] on the byte loop is the empirical difference between hitting the dense backend's 100 MB/s target (M2) and topping out around 70 MB/s — always verify this annotation survived a refactor via the benchmark gate (§17.4), not by eye.

17.7 Performance Concerns

The dense table's cache footprint (100 states × 256 bytes × 2-byte entries ≈ 50 KiB for a 100-state DFA) exceeds L1 on most CPUs — the byte loop's throughput is therefore bounded by L2 latency, not L1, which is why the M2 target (§4) is calibrated against logos's published numbers rather than an idealised L1-resident estimate (§32 Comparative Architecture returns to this). rustc -C codegen-units=1 may be needed to keep the table from being split across translation units on very large rule sets.

17.8 Edge Cases

A rule set small enough that the sparse backend's match-arm tree degenerates to a single arm (single-rule grammar); a rule set exactly at the 100 KiB dense-table size boundary (M5's ≤200 KiB gate is on the generated file, not the raw table, so table size and file size are tracked as two separate assertions); a mode-aware rule set where every mode shares 100% of its rules with every other mode (the stitched-DFA path should degenerate to a single DFA, not duplicate it per mode).

17.9 Failure Analysis

A codegen bug that emits an off-by-one in the dense table's byte-indexing manifests as every 256th state transition being wrong — a subtle, position-dependent correctness bug that a small conformance fixture might miss. Detection: the tokens.seed bucket's full 200-fixture corpus (not a subset) is required specifically because it is large enough to statistically surface this class of bug (§13.5); containment is isolated to codegen.rs, independent of the DFA's own correctness (already verified in Phase 4).

17.10 Operational Notes

Generated-file size and compile-time (M5) are tracked per release in benchmarks/results/<host>.json and surfaced in the README's "performance at a glance" table; a regression here blocks release (release-check Makefile target, §12.2) exactly like a throughput regression does (§31).

18. Phase 6 — Span & Source-Map Infrastructure

18.1 Objectives

Land the full span and source-map behaviour (§11.1, §11.4) in detail and wire it into both backends: multi-line tokens, BOM handling, encoding recovery, and tab-width policy for the off-side rule (Phase 7, §19) to consume.

18.2 Detailed Implementation Steps

  • Multi-line tokens (block comments, template literals): the token's Span is always (start byte, end byte) regardless of how many newlines it spans; line_col derivation is a SourceMap service, never queried in the hot path (P3, I4).
  • BOM handling: Cursor::new consumes a UTF-8 BOM (EF BB BF) at offset 0 silently (ADR-08, I10); SourceMap::has_bom() records the fact; the CLI's JSON output exposes both the canonical post-BOM offset and a disk_offset = span + 3 if has_bom derived view for tools needing to round-trip to the on-disk file.
  • Encoding recovery: an invalid UTF-8 byte sequence (in an identifier or comment) is consumed byte-by-byte until the next valid UTF-8 leading byte; emit Token::Error(InvalidUtf8, span) covering the bad run (I9). UTF-16 BOMs (FF FE/FE FF) are not silently consumed — they are Error(InvalidUtf8) because the lexer is UTF-8-only (ADR-07).
  • Tab handling: tabs are width-1 in the byte-offset world (what the lexer cares about, P3) and width-configurable (default 8) in the SourceMap's column-derivation world; the off-side stack (Phase 7) is fed byte counts of leading whitespace, never column counts — an embedder wanting column-based off-side calls an explicit conversion helper.
  • Line-table construction (SourceMap::build_line_table): a single Vec<u32> of newline byte offsets, built lazily on first line_col call (P10) via partition_point binary search — never a linear position() scan, which would dominate at scale.

18.3 Deliverable

The span fixture corpus (corpora/spans/, including corpora/spans/bom/) is green for both the hand-written reference and the generated backend.

18.4 Acceptance Criteria

A unit test asserts BOM consumption and post-BOM span correctness on a 10 KB UTF-8-with-BOM fixture (I10); a unit test asserts that an invalid UTF-8 byte at byte offset 42 inside an identifier produces Error(InvalidUtf8) with span [42, k) for the longest invalid run (§18.2); the spans.basic and spans.bom conformance buckets (§28) are 100% green.

18.6 Pitfalls

  • The line table must use partition_point (binary search), never iter().position(...) — the latter is O(n) and dominates the column query at scale, silently degrading any diagnostics-heavy tool.
  • Only the 3-byte UTF-8 BOM (EF BB BF) is consumed silently; UTF-16 LE/BE BOMs must be rejected as Error(InvalidUtf8), not misinterpreted as garbage identifier bytes.
  • \r\n must collapse to one line for column-counting purposes — double-counting it is a frequent off-by-one in hand-rolled line tables.

18.7 Performance Concerns

The line table is the only allocation SourceMap performs (P10), and it is deferred until the first column query — a tool that only needs byte offsets (e.g. a byte-oriented formatter) never pays this cost at all. Building it eagerly for every file, even ones that never need columns, is the most common performance regression introduced here.

18.8 Edge Cases

A file with zero newlines (line table is a single empty Vec, line_col always returns line 1); a file whose last byte is a bare \n with nothing after it (does the trailing empty line exist? — defined as no, matching the seed-language's own convention); back-to-back BOM-like byte sequences that are not actually at offset 0 (must not be consumed — only offset-0 triggers consume_bom).

18.9 Failure Analysis

A BOM double-counted or dropped shifts every subsequent span in the file by 3 bytes — the single highest-blast-radius bug class in this phase because it corrupts every token, not just the one at the BOM. Detection: the spans.bom bucket's exact byte-offset assertions catch this immediately and by file; containment is total isolation to Cursor::consume_bom (I10), a single deterministic code path with no other caller.

18.10 Operational Notes

disk_offset (the BOM-adjusted view for round-tripping to the on-disk file) is documented in docs/architecture/newlines.md's sibling doc — an embedder building a "jump to byte N in the original file" feature (e.g. a diagnostics renderer) must use disk_offset, never the canonical post-BOM Span, or user-visible line numbers will be silently wrong.

19. Phase 7 — Off-Side Rule & Indentation

19.1 Objectives

Land the off-side rule for the seed language's optional indentation-significant block flag (ADR-11, P6), built on IndentStack (§11.7) and its strict-monotonicity invariant (I6).

19.2 Detailed Implementation Steps

  • After every NewLine token, read the leading whitespace of the next line as a raw byte count (§18.2's tab-handling policy — byte count, not column count); feed it to IndentStack::feed (§11.7).
  • Continuation-line suppression: track bracket depth (u16) across (/)/{/}/[/]; a line beginning inside an unmatched bracket does not trigger off-side processing at all — it is a continuation line, per the seed language's grammar (§8.1).
  • EOF unwinding: at EOF, inject one Dedent for every level still on the stack above 0, then emit Eof (I6's invariant must hold exactly at this boundary too).
  • Mixed tab/space policy (ADR-23): any tab byte within leading whitespace is a hard Error(IndentMismatch), not a silent width-8 conversion — the explicit rejection that the Python 2→3 transition teaches (§5 Design Principles P6; §8.5 worked failure-path example).
  • Blank-line and comment-only-line handling: neither triggers a dedent; the scanner reads ahead, recognises the line as pure trivia, and treats it as if it were not there for off-side purposes (this is a lookahead, not a rewrite of the byte stream).

19.3 Deliverable

The off-side fixture corpus (corpora/offside/, including corpora/offside/eof/) is green for the hand-written reference lexer.

19.4 Acceptance Criteria

50 fixtures covering nested blocks, continuation lines, mixed tabs/spaces, and EOF unwinding all pass (offside.basic and offside.eof buckets, §28); a property test asserts count(Indent) == count(Dedent) for any fixture that does not contain Error(IndentMismatch) (I6); the §8.5 worked failure-path example (mixed tab/space at line 3) is codified as a named fixture and passes.

19.6 Pitfalls

  • Mixed tabs and spaces is the classic Python 2→3 break — pick the strict policy (ADR-23) and document it; do not let a later phase quietly relax it without a new ADR row.
  • A blank line is whitespace-only, not a dedent — an implementation that treats a blank line as "indent level 0" will spuriously close every open block.
  • A comment-only line is not a dedent either — the scanner must look ahead past the comment before deciding whether the next real line dedents.

19.7 Performance Concerns

The leading-whitespace read after every NewLine is one linear scan bounded by the line's own indentation width (typically < 32 bytes) — negligible relative to the rest of the byte loop; the IndentStack's SmallVec inline capacity of 16 levels (§11.7, ADR-22) avoids a heap allocation for all but pathologically deep nesting.

19.8 Edge Cases

A dedent that lands exactly on an existing stack level (clean dedent, no error); a dedent that lands between two stack levels (partial dedent, Error(IndentMismatch), stack repaired by popping to the nearest level ≤ the new indent, §8.5); a file where the very first non-blank line is already indented (no level-0 baseline established — treated as an immediate Indent from level 0, not an error); an off-side-mode file with zero indentation anywhere (the stack never grows past level 0 — legal, degenerate).

19.9 Failure Analysis

A stack-repair bug on partial dedent (§19.2) that repairs to the wrong level cascades: every subsequent line's indent computation is now relative to a corrupted baseline. This is why I6's count(Indent) == count(Dedent) property test (§19.4) runs over every non-error fixture, not just the ones that exercise dedents directly — a corrupted baseline eventually produces a visible count mismatch even in unrelated-looking fixtures. Containment: the repair logic is isolated to IndentStack::feed's single function, independent of the scanner's line-reading logic.

19.10 Operational Notes

docs/offside.md documents the strict tab/space policy (ADR-23) and the byte-count (not column-count) feeding convention (§18.2) — this is the doc an embedder building a Python-like or CoffeeScript-like language on top of this toolkit reads first; the runtime behaviour is not renegotiable per embedder without a new ADR.

20.1 Objectives

Land the mode stack (§11.6, P5, ADR-12) across both backends and the seed language's template-literal interpolation, plus raw-string capture — the full lexer-modes surface promised in §1.

20.2 Detailed Implementation Steps

  • Mode-stack semantics (P5, ADR-12): modes are a stack of ModeId (§11.6); the active rule set is the one tagged with ModeStack::current(); rule actions call mode_push/mode_pop, shared identically by the generated DFA (Phase 5, §17.2's mode-aware codegen) and the hand-written reference (§13.2).

21. Phase 9 — Trivia Preservation

21.1 Objectives

Land the trivia model (§11.2's TriviaKind/TriviaToken, P4) in full: the three selectable policies (AttachTrailing, Stream, Drop) and the roundtrip invariant (I3) that P4 promises.

21.2 Detailed Implementation Steps

  • AttachTrailing (default, ADR-10): the scanner emits trivia tokens internally; the iterator API folds them into a (Token, LeadingTrivia, TrailingTrivia) triple per non-trivia token. Leading trivia for token T = all trivia between the previous non-trivia token and T; trailing trivia = all trivia between T and the next newline or non-trivia token, whichever comes first (the Roslyn rule, §5 Reference Implementations).
  • Stream (ADR-10's IDE-oriented alternative): every trivia token is emitted in the ordinary iterator sequence; the consumer decides what to do with it.
  • Drop: trivia tokens are not emitted at all — the policy a parser typically wants when it has its own separate trivia-skipping layer.
  • Roundtrip invariant (I3) under AttachTrailing/Stream: concatenating every emitted token's byte slice, in order, reproduces the source bytes exactly — this is the conformance bucket roundtrip (§28) and the fuzz target roundtrip_invariant (§23.2).
  • Doc-comment (///) special-casing: not ordinary whitespace-class trivia — TriviaKind::DocComment is a distinct variant a doc-extraction tool reads directly, while a parser may still treat it as trivia for parsing purposes.
  • Shebang special-casing: #!... at byte 0 is TriviaKind::Shebang; the same two bytes anywhere else in the file are two ordinary tokens (Bang-adjacent), never promoted to shebang trivia outside offset 0.

21.3 Deliverable

The trivia conformance corpus (corpora/trivia/attach/, corpora/trivia/stream/) is green for all three policies, for both backends.

21.4 Acceptance Criteria

trivia.attach and trivia.stream buckets (§28) are 100% green; a property test asserts roundtrip invariance (I3) under Stream policy for 10 MB of seed-language source (benchmarks/corpora/, reused from Phase 11); leading/trailing attachment matches the documented Roslyn rule exactly on the corpora/trivia/attach/ fixtures — verified by byte-exact comparison, not approximate matching.

21.6 Pitfalls

  • Doc comments are not whitespace — a downstream rustdoc-style extractor needs TriviaKind::DocComment distinct from LineComment; conflating the two silently breaks doc-comment tooling built on this lexer.
  • A shebang line must not be promoted outside offset 0 — #! mid-file is two ordinary tokens.
  • AttachTrailing's trailing-trivia-stops-at-first-newline rule (the Roslyn convention) is easy to get backwards — a trailing comment on the last line of a file must not accidentally span past EOF and swallow a following blank line's trivia.

21.7 Performance Concerns

Stream policy is the cheapest to implement (no buffering, tokens emitted as scanned) but the most token-object-heavy for a consumer that immediately discards trivia — an embedder optimising for throughput over a parser that does not want trivia at all should choose Drop, not Stream-then-filter, to avoid allocating trivia tokens that are immediately thrown away (P8).

21.8 Edge Cases

A file with a trailing comment on the very last line with no following newline (trailing trivia must not run past EOF); a file with zero trivia at all (every token's leading/trailing trivia lists are empty, not absent — AttachTrailing's triple always has well-defined, possibly-empty trivia lists); back-to-back doc comments (///a immediately followed by ///b with no blank line — two distinct DocComment trivia tokens, not one merged token).

21.9 Failure Analysis

A roundtrip-invariant violation (I3) is the highest-severity bug class in this phase because any tool that reformats or diffs source using this lexer's output silently corrupts the user's file. Detection: the roundtrip conformance bucket plus the roundtrip_invariant fuzz target (§23.2) run continuously, not just at fixture-authoring time — this is the one invariant given its own dedicated fuzz target rather than relying on conformance fixtures alone. Recovery: lex.roundtrip_mismatch_total (I3's telemetry) triggers an immediate Sev-1 review (Failure Modes FM-8).

21.10 Operational Notes

docs/trivia-model.md documents the three policies and when to choose each — this is the single decision an embedder makes once, at construction time, and it is documented as a construction-time choice specifically so it cannot silently vary mid-session (P11's determinism principle applies to policy selection too, not just automaton output).

22. Phase 10 — Incremental Relexing

22.1 Objectives

Land the IDE-grade incremental relexing path (P9, ADR-15): given a previous token stream, an edit envelope, and the new source bytes, produce the minimal TokenDelta — the longest and most architecturally consequential phase in the plan, because it retroactively validates every runtime type designed since Phase 0.

22.2 Detailed Implementation Steps

  • Algorithm (adapted from the Roslyn red-green-tree pattern, §5 Reference Implementations): (1) find the largest prefix of prev whose tokens end before edit.start — the unchanged prefix; (2) from edit.start, run the lexer forward over the new source, maintaining both the new-source position and a candidate alignment position in prev (initially the first prev token whose start is ≥ edit.old_end, adjusted by the length delta edit.new_end - edit.old_end); (3) for each newly lexed token T, if its adjusted span and kind equal the candidate prev token's, declare alignment — everything in prev from the candidate forward is reusable; otherwise T is new and replaces the corresponding prev range; (4) the output is the minimal TokenDelta (§11.9) describing the replacement.
  • Mode-aware alignment: if the edit changed the mode stack at the alignment point (e.g. inserted an unmatched ${), alignment fails and the relex continues to EOF — "alignment is opportunistic; correctness is guaranteed" (I12's degrade-to-full-relex clause).
  • Off-side-aware alignment: indent-injected virtual tokens are ordinary members of prev for alignment purposes; an edit that changes a line's indentation changes the virtual tokens for the affected lines, terminating the alignment region there.
  • Span adjustment: every prev span compared during alignment must first be adjusted by (edit.new_end - edit.old_end) — an off-by-one here silently invalidates the entire alignment (§22.6's top pitfall).
  • Edits landing inside a token (e.g. a character inserted mid-identifier) require re-lexing from that token's start, not from the edit cursor — the containing token must be found first, not assumed to be the token whose span merely overlaps the cursor.

22.3 Deliverable

IncrementalLexer::apply_edit (§11.9) is implemented and exercised by the examples/incremental-editor/ toy IDE backend against real multi-edit sessions.

22.4 Acceptance Criteria

100 fixtures of (source, edit, expected_diff) in corpora/incremental/ all pass (incremental bucket, §28); a property test over 10,000 random edits to a 100 KB seed-language file asserts prev + apply(delta) == from_scratch_lex(new_source) token-by-token (I12); benchmarks/incremental.rs measures relex time for an edit at the 50th, 90th, and 99th percentile byte offset of the file, all ≤ 1 ms p99 (M6, §4).

22.6 Pitfalls

  • prev spans must be adjusted by the edit's length delta before comparison with newly lexed spans — an off-by-one here invalidates the entire alignment silently (not a crash, a wrong-but-plausible-looking result).
  • An edit landing inside a token requires re-lexing from that token's start, not the edit cursor — a common shortcut ("just relex from edit.start") produces a token stream that looks right locally but is wrong at the token boundary.
  • An edit that changes a multi-line block comment's terminator changes the kind of every following token until the next */ — the alignment check must catch this via the kind-and-span comparison (§22.2 step 3), not assume "same starting byte means same token."

22.7 Performance Concerns

The dominant cost is the forward lex from edit.start to the first successful alignment point, not the TokenDelta construction itself — in the common case (an edit inside one token or one line) this is a handful of tokens; in the worst case (mode-boundary or indent-boundary edits, §22.2) it degrades to a full relex, which is why M6's benchmark (§22.4) specifically measures percentile latency across realistic edit positions, not just the best case.

22.8 Edge Cases

An edit at byte 0 of the file (no unchanged prefix at all); an edit that inserts an entire new mode-opening sequence (` or ${) where none existed (alignment must correctly fail, not spuriously succeed against unrelated prev tokens); an edit that exactly reproduces the original bytes (a no-op edit — the algorithm must still terminate and produce an empty TokenDelta, not loop); back-to-back edits in the same session (the second edit's prev is the first edit's output, not the original file's tokens — IncrementalLexer::new must be re-constructed correctly per edit).

22.9 Failure Analysis

An alignment bug that declares success when it should have failed is the single highest- severity class here: it silently corrupts the IDE's token cache with a token stream that disagrees with from_scratch_lex — a correctness bug in the one place designed to be "correctness never trades against performance." Detection: the 10,000-random-edit property test (§22.4) is the primary net; any fixture failure here is treated as Sev-1 regardless of how rare the triggering edit shape is (Failure Modes FM-10). Containment: apply_edit's alignment check is the sole gate — a failure here never reaches a caller as "probably fine," it always either aligns correctly or explicitly falls back to full relex (I12).

22.10 Operational Notes

lex.incremental_realign_total and lex.incremental_partial_total (I12's telemetry) are the two counters an IDE-embedding team watches in production — a sustained high ratio of realign_total to partial_total signals the embedder's typical edit pattern is hitting the mode/indent-boundary fallback path more than expected, which is a tuning signal, not a correctness concern (§Operational Readiness expands on the alerting philosophy).

23. Phase 11 — Conformance, Fuzzing & Benchmarks

23.1 Objectives

Land the conformance harness, the fuzz harness, and the benchmark suite — the phase that gates Done for the whole toolkit and closes the core 12-phase build path (Phases 0–11).

23.2 Detailed Implementation Steps

  • Conformance runner (conformance/runner): walks conformance/corpora/, runs every fixture against both backends in differential mode (asserting I1–I12 pairwise agree, §7's debugging methodology), and emits conformance.report.json per the bucket schema (§28.3).
  • Fuzz harness (ADR-19, cargo-fuzz + afl.rs): tokenize_anything (random bytes, assert no panic/UB, every span in-bounds, I7); roundtrip_invariant (random bytes, assert I3); incremental_invariant (random base + random edit, assert I12); codegen_random_grammar (grammar-aware mutator generates random rule sets, expands the proc-macro, compiles, asserts the result implements Lexer correctly).
  • Benchmark suite (ADR-20, criterion): compares against logos (closest peer, same proc-macro shape), re2c (C generator, upper-bound reference), flex (baseline reference), Tree-sitter's lexer (IDE peer), and a nom-based lexer (lower-bound reference) — full comparative detail in §32.
  • 24-hour continuous fuzz run with zero unexpected panics is the Done gate (M9); 30-day continuous fuzzing is the Sealed gate (PhaseDeferred("§23.4"), Deferred Features Register).

23.3 Deliverable

All conformance buckets report Pass (or Deferred with a blueprint_ref, §28.2); benchmarks/results/<host>.json is committed and read by the README's "performance at a glance" table on release.

23.4 Acceptance Criteria

Every non-deferred conformance bucket is 100% Pass (§28); a 24-hour cargo-fuzz run across all four targets completes with zero unexpected panics (M9); dense-backend throughput ≥ 100 MB/s (M2) and ≥ 80% of logos's throughput on an equivalent rule set (M4) are both met on the reference machine; conformance suite wall-clock ≤ 30 s (M8).

23.6 Pitfalls

  • criterion's default warmup is too short for cache-cold throughput numbers — configure a 10-second warmup per benchmark or the M2/M4 numbers will be optimistic.
  • Comparing against logos requires building it with the same Rust toolchain and profile; pin the version in the bench harness or the comparison is not apples-to-apples.
  • The re2c comparison requires invoking re2c's own code generator at bench-build time — document this external dependency explicitly in benchmarks/README.md so a missing re2c binary fails loudly, not silently skips the comparison.

23.7 Performance Concerns

The benchmark corpus (benchmarks/corpora/, 100 MB of seed-language source) must include realistic proportions of every token class — a corpus skewed toward, say, pure ASCII identifiers would overstate throughput relative to a mixed-Unicode, comment-heavy, template-literal-heavy real-world file (§4's stance that the benchmark always runs with full span/trivia/error-recovery tracking, never a stripped configuration).

23.8 Edge Cases

A fuzz-generated grammar that happens to be empty (§14.8 case reachable via the mutator — must produce a clean compile_error!, not a fuzz-harness crash); a fuzz input that is valid UTF-8 but exercises every LexError variant in sequence within one file; a benchmark run on a host where re2c is not installed (must Deferred(perf) that one comparison row, not fail the whole benchmark suite, §28.2).

23.9 Failure Analysis

A fuzz-discovered panic is Sev-1 by definition (I7) — the triage path is: reproduce via the minimised fuzz input (cargo fuzz tmin), bisect to the introducing commit, patch, add the minimised input as a permanent regression fixture under corpora/errors/ or corpora/unicode/ as appropriate. A benchmark regression (throughput below M2/M4, or compile-time above M5) blocks release via release-check but is Sev-2, not Sev-1, unless it is severe enough to also fail the M8 wall-clock gate.

23.10 Operational Notes

conformance.yml, fuzz.yml, and benchmarks.yml (§10.1) run on every push, nightly, and per-release respectively; a regression in any conformance bucket (Pass → Fail) blocks merge; the 24-hour fuzz run is scheduled, not blocking, and its results feed marketing/transparency-reports/<period>.md for public accountability on the fuzzing commitment (§Testing & Verification Strategy expands on the cadence).

26. Operational Readiness

Metrics (Prometheus-style naming, all counters/gauges introduced in §7/§24/§25): lex.roundtrip_mismatch_total, lex.panic_total, lex.error_total{kind}, lex.bom_detected_total, lex.mode_depth_at_eof, lex.indent_depth, lex.incremental_realign_total, lex.incremental_partial_total, lex.heap_alloc_total (CI-only, not a production metric).

Tracing. The runtime does not emit spans itself (it is a library, not a service, §1); an embedder building an IDE backend wraps IncrementalLexer::apply_edit in its own trace span (e.g. OpenTelemetry) named lex.incremental.apply_edit with edit.start/edit.len attributes — documented in docs/incremental.md as the recommended integration point.

Structured logging. Compile-time-only: RUST_LOG=mini_lex_codegen=info surfaces NFA state count, DFA state count pre/post minimisation, and codegen wall-clock (§16.10); there is no runtime logging in the hot path (P8 — logging is itself a hot-path cost the design forbids).

Dashboards. benchmarks/results/<host>.json time series (throughput, compile-time, incremental p50/p90/p99) rendered in the README's "performance at a glance" table per release (§23.10); an embedder's own production dashboard plots lex.error_total{kind} by kind to spot a spike in a specific LexError variant (e.g. a sudden rise in InvalidUtf8 signalling an upstream encoding regression, FM-4).

Alerting philosophy. Two-tier: (1) CI gates — any of M1–M10 (§30) regressing, any conformance bucket flipping Pass→Fail, or lex.panic_total/lex.heap_alloc_total > 0 in a fuzz run blocks merge/release automatically, no human paging; (2) production telemetry — lex.roundtrip_mismatch_total > 0 or a sustained climb in lex.mode_depth_at_eof/lex.indent_depth toward the 65,535 cap (T1/T12) pages the owning team, since both indicate either a bug (FM-8) or an adversarial-input pattern worth investigating.

Incident response. Sev-1: any FM-1 (panic/UB), FM-8 (roundtrip violation), or FM-10 (incremental misalignment) — these are correctness violations of a stated invariant (I3, I7, I12) and are triaged immediately regardless of how the failure was discovered (fuzz, production report, or code review). Sev-2: FM-9 (perf regression), FM-7/FM-11 (build-time gates). Sev-3: FM-2/FM-3/FM-4/FM-5/FM-6/FM-12 — expected error-token classes whose rate spiking is the only actionable signal, not their bare occurrence.

Named runbooks (docs/runbook/): compile-time-blowup.md (FM-7, diagnosing a state-count compile_error!); throughput-regression.md (FM-9, diagnosing a benchmark regression via flamegraph comparison against the last-known-good baseline).

Backup/restore. N/A — the toolkit is stateless per invocation (§1 deployment model); the only "state" an embedder might persist is prev_tokens for incremental relexing (§11.9), which is the embedder's own cache to back up or not, per its own IDE-session persistence policy.

Deployment topology. Embedded library, linked into the consumer's binary; no independent deployment unit, no canary/rolling-upgrade concept at the library level — the relevant "deployment" event is the embedder's own release of their binary with an updated mini-lex dependency version, governed by §27 (Compatibility & Versioning).

27. Compatibility & Versioning

Wire compatibility. Token/Span/LexError are serde-derivable behind a feature flag (§11.1, §11.8); the stable wire identity for a token kind is TokenKind::name() (a string), never the enum discriminant, which may be reordered across releases without breaking JSON-based fixtures or IDE-protocol payloads.

Storage compatibility. N/A at the runtime level (the toolkit persists nothing); an embedder's own prev_tokens cache (incremental relexing, §22) is the embedder's storage concern — this toolkit documents (but does not enforce) that a prev_tokens blob captured against one mini-lex minor version should not be assumed valid against another without re-lexing from scratch once after an upgrade.

Schema evolution. Adding a TokenKind/TriviaKind/LexError variant is additive (minor version bump); removing or renaming one is breaking (major version bump) — per the terminology-lock discipline (the same name used identically everywhere), a rename anywhere requires updating the Repository Layout, Core Schema, and every phase section simultaneously, never partially.

API stability. The Lexer trait (§11.5) is the toolkit's single most stable contract (P2): adding a method to it is breaking for every implementor (hand-written and generated); new capability is added via a new trait (IncrementalLexer, §11.9), never by widening Lexer itself.

Migration. A rule-set change that shifts keyword PHF assignments or DFA state numbering is invisible to the embedder (both are internal, regenerated on every build, §17); a change to the seed language's own grammar (§8.1) requires regenerating the conformance corpus (§13.5) and is documented in CHANGELOG.md as a "seed language grammar change," distinct from a toolkit API change.

Deprecation policy. A deprecated attribute (e.g. a future #[token(...)] option superseded by a new one) emits a proc-macro warning for two minor versions before removal in the next major version — mirrors the logos project's own deprecation cadence (§5 Reference Implementations).

SemVer policy. Strict SemVer for mini-lex-runtime, mini-lex-codegen, mini-lex-derive, and mini-lex-cli, versioned in lockstep (one workspace version, §10.1) since the runtime and generator must always agree on the Lexer trait shape (P2).

Rolling-upgrade guarantees. N/A at the library level (§26 Deployment topology); the relevant guarantee is that an embedder can upgrade mini-lex and re-run their own conformance suite against the new version without any source-level change to their #[derive(MiniLex)] rule set, as long as no attribute was deprecated-and-removed (a major version event, called out explicitly in CHANGELOG.md).

28. Testing & Verification Strategy

Unit tests. Per-crate tests/ directories (§10.2) cover individual functions in isolation — Cursor bounds behaviour, SourceMap::line_col correctness, ModeStack/ IndentStack push/pop semantics.

Integration tests. crates/mini-lex-reference/tests/smoke.rs (Phase 0, §12.5) through the full conformance corpus (below) — exercise the Lexer trait end to end.

Property tests. I1–I12 each have a named property test (§7's debugging methodology): dfa.accept(s) == nfa.accept(s) (I1), tie-break fixtures (I2), roundtrip over 10 MB (I3), span monotonicity (I4), mode-depth-at-EOF (I5), indent-count balance (I6), and so on through I12's 10k-random-edit incremental-alignment test.

Differential testing. conformance/runner (§23.2) runs every fixture against both backends (hand-written reference and generated) and asserts agreement — this is P1's enforcement mechanism, not a separate afterthought.

Fuzzing. Four cargo-fuzz targets plus afl.rs mirrors (ADR-19, §23.2): tokenize_anything, roundtrip_invariant, incremental_invariant, codegen_random_grammar. 24-hour continuous run is the Done gate (M9); 30-day continuous run is the Sealed gate (PhaseDeferred("§23.4")).

Chaos / fault injection. N/A in the traditional service-chaos sense (no network, no disk I/O in the hot path, §1); the closest analogue is the fuzz corpus's adversarial-input mutators (T1/T12) and the codegen_random_grammar target's random rule-set generation, which plays the same "inject an unexpected shape" role at the compile-time layer.

Deterministic replay. Every conformance fixture is a (input, expected_output) pair replayed identically on every run (P11); the incremental fixtures (corpora/incremental/) additionally replay a specific (source, edit) sequence to reproduce a specific alignment decision deterministically — the mechanism used to turn a fuzz-discovered incremental bug (FM-10) into a permanent regression fixture.

Soak testing. The 24 h/30-day fuzz runs (M9/M10) double as soak tests: sustained adversarial-input pressure over time, watched for lex.panic_total/memory-growth (lex.heap_alloc_total) trending upward rather than staying flat.

Conformance buckets (conformance/runner, §23.2): tokens.seed, tokens.unicode, spans.basic, spans.bom, trivia.attach, trivia.stream, roundtrip, modes.template, modes.raw, offside.basic, offside.eof, errors.recovery, incremental, codegen.smoke, bench.throughput — each with an outcome Pass | Fail | Deferred.

30. Performance Engineering

Benchmarking methodology. criterion (ADR-20) with a 10-second warmup (§23.6's pitfall) on cold-cache runs; every benchmark always measures with span, trivia, and error-recovery tracking enabled (§4's defining property) — a stripped-down configuration is never reported as "the" throughput number.

Profiling. cargo flamegraph against the benchmark corpus (benchmarks/corpora/, 100 MB of representative seed-language source, §23.7) is the standard tool for diagnosing a throughput regression (FM-9, docs/runbook/throughput-regression.md).

Allocation analysis. A custom #[global_allocator] shim counts allocations during the conformance suite's run (I8's CI gate, §7); any nonzero count for an input within the ModeStack/IndentStack inline-capacity bounds (8/16) is a regression against P8.

Lock/cache/syscall analysis. There are no locks in the hot path (single-threaded per scan, §4); the dense backend's cache behaviour is the primary performance lever (§17.7's L2-latency-bound analysis); there are zero syscalls in the hot path (the caller supplies bytes already resident in memory, §4's FD budget).

Tail-latency analysis. The incremental-relex benchmark (§22.4) is the toolkit's one explicit tail-latency-sensitive path (an IDE keystroke-to-redraw budget); it is measured at p50/p90/p99, not just mean, specifically because a rare worst-case (a mode-boundary edit degrading to full relex, §22.7) is what an IDE user actually feels.

31. Scalability Analysis

What stays constant. Per-byte scan cost is O(1) amortised (one DFA transition per byte, I8's zero-allocation guarantee) regardless of source-file size, up to the 4 GiB byte-offset ceiling (ADR-21, §4); rule-set size affects only compile-time DFA construction (Phases 3–4), never runtime per-byte cost, because the DFA is fully resolved before any byte is scanned.

What grows. Mode-stack and indent-stack depth grow with source nesting (bounded at 65,535, T1); the SourceMap line table grows O(newlines) in the file, built once, lazily (P10); the incremental-relex alignment search grows with the distance from the edit point to the first successful alignment (§22.7), worst-case O(file size) on a mode/indent-boundary edit.

Named bottlenecks, in order. (1) Dense-table cache-line pressure at high state counts (§17.7's L2-latency-bound analysis, the throughput ceiling below full L1 residency); (2) proc-macro compile-time cost at large rule-set sizes (P12, capped at §4's budgets, not optimised past them); (3) incremental-relex worst-case full-file fallback on mode/indent-boundary edits (§22.2); (4) UTF-8 slow-path decode cost for non-ASCII-heavy source (§13.7's fast-path/slow-path split).

Horizontal scaling. Embarrassingly parallel across files: one Lexer instance per file, zero shared mutable state (§4's concurrency model) — an embedder lexing a whole-workspace batch simply spawns one scan per file per core, no coordination needed.

Vertical scaling. Single-core throughput is the only vertical lever that matters per scan (the scan itself is inherently sequential — a DFA cannot be parallelised across a single byte stream without the derivative/parallel-automaton research direction, which is out of scope, §Alternative Architectures).

Sharding/partitioning. N/A within one file (a single token stream is not shardable mid-scan without breaking mode/off-side context, I5/I6); across files, "sharding" is simply "which files go to which worker," an embedder-level concern.

Coordination overhead. Zero at the library level (§4); the only coordination an embedder pays for is their own IDE's decision about which buffer's IncrementalLexer to invoke on which edit event — outside this toolkit's boundary.

Practical ceiling and the levers beyond it. The practical ceiling today is ~100 MB/s single-core dense-backend throughput (M2) on files up to 4 GiB (ADR-21); the levers beyond it are: PhaseDeferred("§13.7")'s SIMD whitespace-skip (targets ≥ 250 MB/s on whitespace-heavy corpora, §Back-of-Envelope Capacity Model derives this), widening ByteOffset to u64 (ADR-21's rejected-choice regime, for >4 GiB single files), and the PhaseDeferred("§16.2") derivative-based DFA construction for rule sets whose Unicode classes currently dominate compile-time cost.

32. Mental Models & First Principles

Each model is the compressed insight an expert holds, what it predicts, the bug class you write without it, and the § where this blueprint applies it.

  1. MM1 — A lexer is a compiled decision procedure, not an interpreter of rules. The rule set is baked into a DFA at compile time (§16); it is never re-consulted as data at runtime. Predicts: changing a rule requires a rebuild, never a config reload. Bug class without it: treating the rule set as runtime-interpretable data, silently reintroducing per-position regex-matching cost (ADR-02, §9). Applied in §16 (subset construction).
  2. MM2 — Longest match is a property of the whole automaton, not a per-rule greedy choice. Two rules cannot be locally disambiguated by reading them in isolation; the scanner must run to the point where no further match is reachable (I1, §7). Predicts: rule order alone never determines the winner at unequal lengths. Bug class without it: authoring rules assuming first-match-wins semantics from a different regex engine. Applied in §8.2 (worked DFA fragment).
  3. MM3 — A mode stack is a bounded pushdown extension to a regular language, not a full context-free escape hatch. It can express balanced, LIFO-nested constructs (interpolation, raw strings) but not arbitrary cross-referencing structure. Predicts exactly which language features are lexable this way and which need the parser (§1 boundary). Bug class without it: attempting to express genuinely context-free constraints (e.g. matching tag names in a markup language) purely in the mode stack. Applied in §20.1 (P5).
  4. MM4 — Every byte is either consumed by a token or it is a bug. The roundtrip invariant (I3, §7) is not an optional nicety; it is the definition of a complete tokenizer. Predicts that any "we don't care about whitespace" shortcut eventually breaks a formatter or diff tool. Bug class without it: discarding trivia bytes silently, discovered only when someone tries to reformat source losslessly. Applied in §21 (Trivia Preservation).
  5. MM5 — Off-side is a monotonic stack machine, not a column counter. IndentStack's correctness argument (I6, §7) is algebraic: count(Indent) - count(Dedent) always equals the current nesting depth. Predicts that any ad hoc column-tracking implementation will eventually desynchronise on mixed tabs/spaces. Bug class without it: the Python-2-style silent-tab-conversion bug (ADR-23, §9). Applied in §19 (Off-Side Rule & Indentation).
  6. MM6 — Compile-time cost is a tax on every developer's inner loop, not a one-time setup cost. P12 (§6) treats DFA generation as a budget precisely because it runs on every cargo build. Predicts that an "eventually consistent" or unbounded generator degrades adoption even when the runtime is fast. Bug class without it: optimising scan-time throughput while ignoring proc-macro expansion time, shipping a toolkit nobody wants to build against. Applied in §16.10, §4.
  7. MM7 — Incremental correctness is a superset relation, not a performance optimisation. prev + apply_edit(...) must equal from_scratch_lex(new_source) (I12, §7) exactly; the "opportunistic alignment, guaranteed correctness" design (§22.2) is not a fallback of shame, it is the specification. Predicts why a cheap-but-wrong alignment heuristic is strictly worse than no incremental path at all. Bug class without it: shipping an incremental lexer that is fast but silently diverges from a full relex on rare edit shapes. Applied in §22 (Incremental Relexing).
  8. MM8 — A span is a fact about bytes, not a fact about characters or lines. Line and column are a derived, lazily-computed service (P3, P10, §6), never a per-token field. Predicts why the hot path never slows down for diagnostics-oriented consumers who never ask for columns. Bug class without it: eagerly computing (line, col) per token, discovering the quadratic cost surprise only at file sizes nobody tested against. Applied in §18.2, §11.4.

logos. re2c. Tree-sitter. Embeds its own lexer inside an incremental parser, where the unit of incrementality is the parse tree node, not the bare token stream. It wins when the consumer wants incremental parsing, not just incremental lexing, and is willing to adopt tree-sitter's whole grammar-DSL ecosystem; it loses as a narrowly-scoped tokenizer because there is no way to use its incremental lexer without also adopting its parser (the reason Parser-Combinator, project 65, is this toolkit's own separate downstream project rather than folded in here, §1).

34. Back-of-Envelope Capacity Model

Twelve numbers, each derived step-by-step from the System Constraints table (§4), formula shown.

  1. Tokens/second at the M2 throughput target. 100 MB/s ÷ ~5 bytes/token (seed-language average token width, measured across the 200-fixture corpus, §13.5) ≈ 20M tokens/s.
  2. Memory overhead per source byte. M7 (≤8 MiB peak RSS) ÷ 100 MB corpus = 0.08 bytes of overhead per source byte — the near-zero-allocation hot path (I8) made concrete.
  3. Dense-table memory at the M12 state count. 96 states (M12) × 256 bytes/state × 2 bytes/entry = 49,152 bytes ≈ 48 KiB for the seed-language DFA — comfortably inside the M11 ≤200 KiB generated-file budget with room for the accept table and PHF.
  4. Dense-table memory at the state-count ceiling. 100,000 states (§4's DFA budget) × 256 × 2 bytes = 51,200,000 bytes ≈ 48.8 MiB — this is why the state-count cap exists as a hard compile_error! (T3, §24) rather than a soft warning: an uncapped generator could produce a 49 MiB single translation unit.
  5. ModeStack inline footprint. 8 (inline capacity, ADR-22) × 2 bytes (u16 ModeId) = 16 bytes resident on the lexer's own stack frame, avoiding a heap allocation for every scan whose interpolation nesting stays ≤ 8 (§11.6).
  6. IndentStack inline footprint. 16 (inline capacity, ADR-22) × 4 bytes (u32 level) = 64 bytes, same reasoning as above (§11.7).
  7. Minimum forward-lex speed implied by M6. The incremental-relex p99 target is ≤ 1 ms for an edit at a 50 KB offset (§22.4); in the worst case the algorithm must forward-lex from the edit point before finding alignment, so 50,000 bytes ÷ 0.001 s = 50 MB/s minimum effective forward-lex speed during realignment — comfortably below M1's 50 MB/s reference-lexer floor (§4), confirming the p99 budget is achievable even in the worst-case full-line rescan.
  8. Fuzz exec-count over the M9 gate window. Typical cargo-fuzz (libFuzzer) execution rates for small structured inputs run on the order of ~10,000 execs/s; over the 24 h M9 window: 10,000/s × 86,400 s = 864,000,000 (≈864M) fuzz executions — the statistical basis for treating a clean 24 h run as meaningful evidence of I7.
  9. Maximum addressable source size. u32::MAX = 4,294,967,295 bytes ≈ 4.0 GiB (ADR-21) — directly the §4 "Max source file size" row; the point at which Span arithmetic (§11.1) would silently wrap without the checked_add guard.
  10. Keyword PHF footprint. For a ~40-keyword seed-language keyword list: a CHD PHF table is O(n) in keys, roughly 40 × 4 bytes (u32 displacement/index) ≈ 160 bytes — negligible next to the dense DFA table (#3 above), confirming ADR-06's choice costs almost nothing relative to its benefit.
  11. SIMD whitespace-skip projected speedup. The PhaseDeferred("§13.7") SIMD path targets ≥ 250 MB/s on whitespace-heavy corpora against the M2 100 MB/s dense baseline: 250 ÷ 100 = 2.5×, plausible for a 32-byte-at-a-time AVX2 scan against a byte-at-a-time loop on corpora where whitespace runs are a large fraction of bytes (consistent with published SIMD-whitespace-skip results referenced informally in the re2c/simdjson-adjacent literature, §5).
  12. Implied logos baseline for the M4 target. M4 requires ≥ 80% of logos's throughput on an equivalent rule set; if this toolkit hits its own M2 floor of 100 MB/s, the M4 gate is only meaningful if logos itself clears roughly 100 ÷ 0.8 = 125 MB/s on the same hardware — the number the benchmark harness (§23) must actually observe from logos before M4 can be evaluated at all.

36. Alternative Architectures (Roads Not Taken)

Four fundamentally different architectures for the same problem — not parameter tweaks.

A1 — Backtracking regex-engine-based lexer.

Step Per-position decision (no fused automaton)
At current position p Every rule's regex is evaluated independently against p — O(rules) matches per position
Selection Winner = the longest candidate match; ties broken by rule order
Emission Token for the winner is emitted; p advances by the winner's match length
Termination Position reaches end of source

Regime where it wins: a rule set with ≤ 10 rules and inputs under a few KB, where engineering a fused DFA is not worth the setup cost (a one-off script tool). Real system: early Python PLY-style and many hand-rolled nom-based lexers embody exactly this per-position-regex-match pattern. Rejection reason: O(rules × positions) throughput is categorically worse than one fused DFA pass at the toolkit's target scale (ADR-02, §9), and the 100 MB/s M2 target is unreachable this way at any rule-set size worth generating code for.

A2 — Brzozowski-derivative-based DFA construction as the primary strategy.

state := regex_hir                     # the "state" IS a regex, not a state-id
on byte b: state := derivative(state, b)
accept?  := nullable(state)

Regime where it wins: grammars dominated by large Unicode general-category classes, where subset construction's alphabet-partition blowup is the bottleneck (ADR-03/ADR-14, §9). Real system: the reference prototype described in Owens, Reppy, Turon 2009 (§5 Required Reading) builds exactly this derivative-based construction. Rejection reason: subset construction is simpler to implement correctly first and is fast enough for the ≤512-rule regime this toolkit targets in its core path (ADR-03); derivatives are deferred (PhaseDeferred("§16.2")), not abandoned.

A3 — Parser-combinator-embedded tokenization (no separate lexer stage).

token := alt(keyword, ident, number, string, punct)   # combinators ARE the lexer
expr  := token.then(token).then(...)                   # no token-stream boundary at all

Regime where it wins: small DSLs prototyped rapidly, where paying for a separate lexer stage and its own conformance boundary is pure overhead relative to the grammar's size. Real system: chumsky's lexer-mode combinators and nom-based lexers (already the lower-bound benchmark reference in §23.2) embody this fusion. Rejection reason: P1 (ground-truth duality, §6) requires a first-class, independently-conformance-tested lexer stage — fusing lexing into the parser removes the very boundary this toolkit's entire value proposition (a reusable, benchmarkable, swappable tokenizer, §1) depends on.

A4 — Scannerless (PEG-style) parsing, no lexer at all.

grammar := (identifier | number | "if" ws expr)*      # tokens are just grammar rules
                                                        # no token stream materializes

Regime where it wins: grammars whose token boundaries are genuinely context-sensitive and awkward to express as a regular language up front (some whitespace-sensitive or lookahead-heavy syntaxes) — packrat parsing (Ford 2002, §5 Required Reading) is often built scannerless for exactly this reason. Real system: PEG-based scannerless parser generators in this tradition. Rejection reason: this toolkit's explicit system boundary (§1) is "tokenizer, not parser" — a scannerless design has no tokenizer artifact to ship at all, and it forecloses the toolkit's entire value proposition of a reusable token stream consumed by an independent parser (Parser-Combinator, project 65, §1).

38. Glossary

DFA (Deterministic Finite Automaton). The minimised state machine the generator emits; one state, one byte, one next-state, no ambiguity (§16).

NFA (Nondeterministic Finite Automaton). The intermediate automaton from Thompson construction, before subset construction removes nondeterminism (§15).

Thompson construction. The algorithm mapping a regex AST to an NFA fragment-by-fragment (Thompson 1968, §15.2).

Subset construction. The algorithm converting an NFA to an equivalent DFA by tracking sets of NFA states as single DFA states (§16.2).

Hopcroft minimisation. The n log n partition-refinement algorithm reducing a DFA to its minimal equivalent state count (Hopcroft 1971, §16.2).

Longest match / maximal munch. The disambiguation rule: the automaton commits to the longest matching prefix at any start position (I1, §7).

Tie-break priority. The rule for resolving equal-length matches: explicit priority, then source declaration order (I2, §7).

Token. A (TokenKind, Span) pair emitted by the lexer for one recognised lexical unit (§11.2).

Span. A byte-offset range {start, end} identifying where a token or trivia occurs in the source (§11.1).

Byte offset. A u32 position into the source buffer, the toolkit's sole position representation in the hot path (ADR-09, §11.1).

Trivia. Whitespace, comments, and shebangs — tokenized like any other lexical unit so every source byte is accounted for (P4, §21).

TriviaPolicy. The construction-time choice of AttachTrailing, Stream, or Drop for how trivia is surfaced to the consumer (§21.2).

Lexer mode. A named rule-set context (ModeId) on the mode stack, active while it is the top of stack (§11.6).

Mode stack. The runtime-owned pushdown structure (ModeStack) that makes string interpolation and raw strings tractable (P5, §20).

Off-side rule. The convention (Python/Haskell/F#/CoffeeScript-style) that indentation is syntactically significant, requiring virtual INDENT/DEDENT tokens (§19).

IndentStack. The runtime utility implementing the off-side rule as a monotonic stack machine (I6, §11.7).

INDENT / DEDENT. Virtual tokens injected by IndentStack when a line's indentation crosses a boundary relative to the current stack (§19.1).

Keyword promotion. Reclassifying an Ident token to its specific keyword kind via a perfect-hash lookup after ordinary identifier scanning (I11, ADR-06).

Perfect-hash function (PHF). A hash function with zero collisions over a fixed, known key set — used here for keyword recognition (§17.2).

CHD algorithm. The specific perfect-hash-construction algorithm (compress, hash, displace) this toolkit's generator uses for keyword PHFs (ADR-06).

XID_Start / XID_Continue. The Unicode Annex #31 character-class properties defining legal identifier start/continuation bytes (§5, §13.3).

UAX#31. Unicode Annex #31, Identifier and Pattern Syntax — the specification this toolkit's identifier lexing conforms to (§5).

BOM (Byte Order Mark). A 3-byte UTF-8 marker (EF BB BF) at offset 0, consumed silently by Cursor::new (ADR-08, I10).

Roundtrip invariant. The guarantee that concatenating every emitted token's bytes reproduces the source exactly (I3, §21.4).

Incremental relexing. Producing an updated token stream from a prior stream plus an edit, without a full from-scratch relex, when alignment succeeds (P9, §22).

Red-green tree. Roslyn's incremental-parsing data structure; the algorithmic ancestor of this toolkit's IncrementalLexer::apply_edit (§5, §22.2).

Edit envelope. The (start, old_end, new_end) triple describing a source edit's extent, the input to apply_edit (§11.9).

TokenDelta. The minimal Replace/Insert/Delete diff apply_edit returns describing how prev_tokens changes (§11.9).

Alignment (incremental). The process of matching a newly-lexed token against a candidate prev token to decide whether the remainder of prev is reusable (§22.2).

Dense backend. The generated-code shape using a full [state × byte] jump table — throughput-optimal (ADR-05, §17.2).

Sparse backend. The generated-code shape using nested match arms — binary-size optimal (ADR-05, §17.2).

Proc-macro. A Rust compile-time code-generation mechanism; mini-lex-codegen's #[derive(MiniLex)] is one (§11.5, ADR-17).

regex_syntax::Hir. The parsed, high-level intermediate representation of a regex pattern this toolkit's frontend consumes (ADR-16, §14.2).

ByteClass. The generator's internal representation of a set of matched bytes/code points — a bitmap for bytes mode, a sparse range list for str mode (§15.2).

Accept state. A DFA state at which one or more rules match; carries a TokenId and tie-break metadata (§16.2).

Dead state. The single DFA state with no path to any accepting state; reaching it means "stop and emit longest-accept-or-error" (§16.2).

ε-closure. The set of NFA states reachable from a given state via epsilon transitions alone; the basis of both ε-elimination and subset construction (§15.2, §16.2).

Partition refinement. The technique underlying Hopcroft minimisation: iteratively splitting state-equivalence-class partitions until stable (§16.2).

Brzozowski derivative. An alternative automaton-construction technique operating directly on regex ASTs without an explicit NFA; deferred in this toolkit (PhaseDeferred("§16.2"), §5, §36 A2).

SourceMap. The per-file owner of the byte buffer and the lazily-built line table for (line, column) derivation (§11.4, P10).

Line table. The Vec<u32> of newline byte offsets SourceMap builds lazily on first column query (§18.2).

FileId. The stable, process-local identifier for a SourceMap's underlying file (§11.4).

Conformance fixture. A named (input, expected output) pair used to verify lexer correctness across both backends (§28).

Differential testing. Running the same fixture against both the hand-written and generated backends and asserting agreement — P1's enforcement mechanism (§28).

Fuzz target. One of the four cargo-fuzz/afl.rs harnesses asserting an invariant under adversarial random input (§23.2).

SBOM (Software Bill of Materials). The CycloneDX dependency manifest generated per release (§29).

SLSA. Supply-chain Levels for Software Artifacts — the provenance-attestation framework this toolkit's release process follows (§29).

Template literal. The seed language's interpolated-string construct (`...${expr}...`) exercising the mode stack (§8.3, §20.2).

Mode-stack depth. The current nesting level of active lexer modes, capped at 65,535 (§4, T1).

Interpolation. The general mechanism of embedding a sub-expression inside a string or template literal, implemented via mode-stack push/pop (§20).

Here-document. A shell/Perl-style multi-line string construct delimited by a marker line, deferred in this toolkit (PhaseDeferred("§20.2"), §37).

External scanner (tree-sitter). Tree-sitter's mechanism for delegating lexing of a grammar rule to hand-written C code; a possible future consumer of mini-lex-reference (PhaseDeferred("§23"), §36 comparative discussion).

Scannerless parsing. An architecture with no separate lexer stage at all; token boundaries are implicit in the grammar (§36 A4).

Packrat parsing. A memoising, linear-time parsing technique (Ford 2002, §5) often paired with scannerless grammars; this toolkit's downstream consumer's concern, not its own (§1).
