⬜ Phase 0 — Skeleton, Governance & Correctness Kernel §12

Objectives

Stand up the repository (§10) from a single commit, land governance/CI, and ship a "Hello, lex" smoke test that proves the toolchain end to end before any automaton theory is written. This phase introduces no new algorithms — it is the correctness-kernel scaffold every later phase builds on (Phase Contract preamble, §7 of the standard).

Deliverable

A cloned repo where make bootstrap && make build && make test all return 0, and echo "x = 1 + 2" | mini-lex tokenize - prints seven tokens (Ident Whitespace Eq Whitespace Int Whitespace ... Plus ... Int Eof) as JSON.

Acceptance

cargo test --workspace returns 0 with ≥ 1 passing test per crate; the smoke test in tests/smoke.rs passes on the exact fixture b"x = 1 + 2\n"; ADR-01, ADR-02, ADR-05, ADR-07, ADR-09, ADR-10, ADR-13, ADR-18 (8 of the 24 rows) are recorded as docs/adr/*.md files; make lint exits 0 with zero clippy warnings on the -D warnings profile.

Fixtures
Fixture Purpose Expected Output
tests/smoke.rs::hello_lex End-to-end toolchain smoke test 7-token stream, no Error tokens
corpora/tokens/seed-language/000-empty.json Empty-file edge case single Eof token at [0,0)
corpora/errors/000-unknown-byte.json Malformed input on day one Error(UnknownToken) then Eof
Pitfalls
  • The default Cargo resolver silently miscompiles proc-macro-crate feature unification; resolver = "2" is not optional (ADR-01).
  • The proc-macro crate must declare proc-macro = true; otherwise quote! compiles but downstream crates cannot import the derive macro at all — a confusing "item not found" error far from the root cause.
  • A make test that simply runs cargo test --workspace silently misses proc-macro expansion tests living under tests/expand/ (the trybuild convention); wire trybuild from day one (used again in §14, §17) so the failure is loud, not silent.

⬜ Phase 1 — Hand-Written Reference Lexer §13

Objectives

Build the hand-written reference lexer for the seed language (a TypeScript-like surface: UAX#31 identifiers, three numeric forms, three string forms including template interpolation, three comment forms, an optional off-side flag). This is the conformance ground truth (P1) every later backend is measured against — it must exist before the generator (Phase 2 onward) has anything to be correct relative to.

Deliverable

mini-lex-reference compiles standalone (no dependency on mini-lex-codegen) and its Lexer impl is exercised end to end by mini-lex-cli tokenize.

Acceptance

Passes the 200-fixture seed-language token corpus (conformance/corpora/tokens/seed-language/) at 100% (tokens.seed bucket, §28); sustained throughput on a 10 MB corpus ≥ 50 MB/s on the reference machine (2024 MacBook Air M2, per §4 M1); the roundtrip invariant concat(token.bytes) == source_bytes (I3) holds for the full corpus.

Fixtures
Fixture Purpose Expected Output
corpora/tokens/seed-language/*.json (200 files) Golden token streams across the full grammar exact (kind, span) sequence match
corpora/errors/001-unterminated-string.json §8.4 malformed-input case Error(UnterminatedString) covering [8,22)
corpora/modes/template/010-nested-interp.json §8.3 worked example 9-step mode trace, depth returns to 1
corpora/roundtrip/seed-100.txt Full-corpus roundtrip check byte-exact reconstruction (I3)
Pitfalls
  • CRLF/LF/CR/U+2028/U+2029 line-terminator zoo is the silent killer; only \n and \r\n are newlines here, bare \r is Error(UnknownToken) — document in docs/architecture/newlines.md and never change without an ADR.
  • 1..2 (range) vs. 1. (float) disambiguation needs one byte of lookahead: a . after a digit followed by another . is not a fraction start.
  • Block-comment nesting is the bug rustc shipped in 2015 (issue #28475) from a non-nesting parser; track depth explicitly, never assume flat /* ... */.

⬜ Phase 2 — Regex Frontend & Rule Normalisation §14

Objectives

Stand up the proc-macro generator's frontend: parse #[derive(MiniLex)] input, collect per-variant #[token(...)]/#[regex(...)] attributes, parse patterns into regex_syntax::Hir, normalise into a canonical form, and thread the result into the NFA constructor (Phase 3, §15). No automaton construction happens yet.

Deliverable

The frontend ingests a 50-rule fixture grammar (corpora/codegen/grammars/fifty-rule.rs) and produces a canonical, normalised Hir set with zero errors, ready for Phase 3.

Acceptance

trybuild tests cover exactly three user-facing failure cases — lookaround rejection, unsupported Unicode property class, conflicting #[mode(...)] declarations — each with a fixed compile_error! message string asserted verbatim; the 50-rule fixture parses in ≤ 200 ms wall-clock at proc-macro-expansion time; mini-lex-derive re-exports the derive macro under a version-stable name (mini_lex_derive::MiniLex).

Fixtures
Fixture Purpose Expected Output
corpora/codegen/grammars/fifty-rule.rs Frontend ingestion smoke test zero-error canonical Hir set
tests/expand/lookaround-rejected.rs (trybuild) Reject unsupported construct compile_error! naming the rule
tests/expand/mode-conflict.rs (trybuild) Reject conflicting #[mode(...)] compile_error! naming both variants
tests/expand/dot-star-warning.rs Σ*-covering-rule detection compiler warning, not an error
Pitfalls
  • regex_syntax accepts patterns the regex crate would compile but that contain lookarounds; reject at this frontend, not silently at DFA construction time.
  • Attribute evaluation order across enum variants is whatever syn returns, not necessarily source order — never assume insertion order from an intermediate HashMap; carry an explicit index (I2's tie-break needs stable source order).
  • A user writing #[regex(r".*")] on an early variant silently shadows every later rule; the Σ*-coverage warning (§14.2) is the only thing standing between this and a very confusing bug report weeks later.

⬜ Phase 3 — Thompson NFA Construction §15

Objectives

Implement Thompson's construction (Thompson 1968, §5): each normalised Hir node from Phase 2 maps to a small NFA fragment (concatenation, alternation, Kleene closure, character class, optional, plus); fragments wire together into one NFA with one entry state and accepting states tagged by token id, then ε-elimination removes epsilon edges before Phase 4 consumes the result.

Deliverable

nfa::build returns a complete, ε-free Nfa for the 50-rule fixture grammar (corpora/codegen/grammars/fifty-rule.rs) with deterministic state numbering across repeated builds (P11).

Acceptance

nfa::build completes in bounded time with cached golden snapshots under tests/snapshots/ for the 50-rule fixture; a property test asserts accepts(nfa, s) == accepts(epsilon_free(nfa), s) for 10,000 random strings up to length 256 (I1); the per-rule NFA expansion budget of 10,000 states (§4) is enforced with a named compile_error! on overflow.

Fixtures
Fixture Purpose Expected Output
tests/snapshots/fifty-rule.nfa.json Deterministic-build regression byte-identical NFA structure across two builds
tests/nfa_property.rs::epsilon_equivalence ε-elimination correctness 10k random strings, pre/post-elimination agree
corpora/codegen/grammars/oversized.rs Budget-enforcement fixture compile_error! naming the offending rule at >10k states
Pitfalls
  • The default SmallVec inline capacity of 4 for ε-edges is correct for typical transitions but undersized for deeply nested alternation — profile against the 50-rule fixture and adjust before Phase 11's benchmark corpus stresses it.
  • Accept tags must propagate through the ε-closure: an NFA state that only ε-reaches an accepting state is itself accepting post-elimination — missing this silently drops valid matches (I1 violation).
  • The . regex class excludes \n by default in regex_syntax; do not accidentally include it when normalising a user's #[regex(r".*")] rule (would defeat the Σ*-warning in §14.2).

⬜ Phase 4 — Subset Construction & Hopcroft Minimisation §16

Objectives

Turn the ε-free NFA from Phase 3 into a DFA (subset construction) and minimise its state count (Hopcroft, ADR-04) — the last purely-automaton-theory phase before codegen (Phase 5).

Deliverable

A minimised, deterministic DFA for the 50-rule fixture and for the full seed-language grammar (~200 rules across all token classes, §8.1), with dead-state collapse applied.

Acceptance

The seed-language DFA (starting from ~200 NFA states pre-minimisation) minimises to ≤ 96 states in ≤ 50 ms wall-clock at proc-macro-expansion time (M5-adjacent, §4); a property test asserts dfa.accept(s) == nfa.accept(s) for 10,000 random inputs; a fixed tie-conflict fixture (#[token("if")] If vs. #[regex("[a-z]+")] Ident) resolves to If for input "if" and Ident for "iff" (I1, I2, §8.2's worked DFA-fragment example).

Fixtures
Fixture Purpose Expected Output
tests/dfa_minimise.rs::seed_language_state_count Minimisation bound check ≤ 96 states, ≤ 50 ms
tests/dfa_minimise.rs::nfa_dfa_equivalence Subset-construction correctness 10k random inputs agree
tests/dfa_minimise.rs::if_vs_ident_tiebreak §8.2 worked example, codified If for "if", Ident for "iff"
corpora/codegen/grammars/exponential.rs State-count budget enforcement compile_error! at >100k states
Pitfalls
  • Dead-state collapse must happen strictly after minimisation, not before — collapsing early can merge a live state that only looks dead pre-minimisation with the true dead state, corrupting the automaton.
  • For source = "str", iterating the full Unicode code-point range per state is the single most common performance bug in a from-scratch subset-construction implementation; use the rule set's own character-class partition as the alphabet (§16.2).
  • DFA state count can blow up exponentially for grammars with many overlapping alternations (the classic subset-construction pathology); the 100k-state budget with a named compile_error! (§4, §16.2) is the safety valve — this is also precisely the regime PhaseDeferred("§16.2") (Brzozowski derivatives, ADR-03/ADR-14) targets for a future Phase-2 path.

⬜ Phase 5 — Code Generator (Dense & Sparse Backends) §17

Objectives

Emit the minimised DFA from Phase 4 as Rust source via quote! (ADR-17), in two selectable backend shapes (ADR-05), plus the perfect-hash keyword post-pass (ADR-06). This is the phase that makes the generated lexer implement Lexer (§11.5, P2).

Deliverable

The dense backend on the seed-language grammar emits one Rust source file that compiles and implements Lexer (§11.5); the sparse backend emits an equivalent, smaller file selectable per rule set.

Acceptance

Dense backend: generated file ≤ 200 KiB, compiles in ≤ 4 s release mode on the reference machine (M5, §4). Sparse backend: ≤ 60 KiB, compiles in ≤ 1.5 s. A trybuild test asserts the generated code passes the full tokens.seed conformance corpus (§13.5) at 100% — proof of P1 (ground-truth duality) for the generated backend. The keyword PHF has zero collisions against the closed keyword list (I11), verified by a build-time exhaustive check.

Fixtures
Fixture Purpose Expected Output
tests/expand/dense_backend.rs (trybuild) Dense-backend generated-code correctness passes tokens.seed 100%
tests/expand/sparse_backend.rs (trybuild) Sparse-backend generated-code correctness passes tokens.seed 100%, ≤ 60 KiB
tests/perfect_hash.rs::zero_collisions I11 keyword-exactness 0 collisions across the full keyword list
benchmarks/compile_time.rs::dense_200_rule M5 compile-time gate ≤ 4 s release, ≤ 10 s debug
Pitfalls
  • Quoting a 256-element array with #(#x),* per element is slow at macro-expansion time; use a single extend call over a pre-built TokenStream iterator instead (§17.2).
  • The const dense table forces compile-time table evaluation; on an unpinned toolchain this can silently regress — the rust-toolchain.toml pin (Phase 0, §12.1) is the defence, not a runtime check.
  • Omitting #[inline(always)] on the byte loop is the empirical difference between hitting the dense backend's 100 MB/s target (M2) and topping out around 70 MB/s — always verify this annotation survived a refactor via the benchmark gate (§17.4), not by eye.

⬜ Phase 6 — Span & Source-Map Infrastructure §18

Objectives

Land the full span and source-map behaviour (§11.1, §11.4) in detail and wire it into both backends: multi-line tokens, BOM handling, encoding recovery, and tab-width policy for the off-side rule (Phase 7, §19) to consume.

Deliverable

The span fixture corpus (corpora/spans/, including corpora/spans/bom/) is green for both the hand-written reference and the generated backend.

Acceptance

A unit test asserts BOM consumption and post-BOM span correctness on a 10 KB UTF-8-with-BOM fixture (I10); a unit test asserts that an invalid UTF-8 byte at byte offset 42 inside an identifier produces Error(InvalidUtf8) with span [42, k) for the longest invalid run (§18.2); the spans.basic and spans.bom conformance buckets (§28) are 100% green.

Fixtures
Fixture Purpose Expected Output
corpora/spans/basic/*.json Byte-offset and line/column correctness exact match against golden derivations
corpora/spans/bom/utf8-bom-10kb.json BOM consumption + post-BOM spans has_bom=true, spans relative to post-BOM buffer
corpora/spans/invalid-utf8-42.json Encoding-recovery span Error(InvalidUtf8) at [42,k)
corpora/spans/utf16-bom-rejected.json UTF-16 BOM is not silently consumed Error(InvalidUtf8) at [0,2)
Pitfalls
  • The line table must use partition_point (binary search), never iter().position(...) — the latter is O(n) and dominates the column query at scale, silently degrading any diagnostics-heavy tool.
  • Only the 3-byte UTF-8 BOM (EF BB BF) is consumed silently; UTF-16 LE/BE BOMs must be rejected as Error(InvalidUtf8), not misinterpreted as garbage identifier bytes.
  • \r\n must collapse to one line for column-counting purposes — double-counting it is a frequent off-by-one in hand-rolled line tables.

⬜ Phase 7 — Off-Side Rule & Indentation §19

Objectives

Land the off-side rule for the seed language's optional indentation-significant block flag (ADR-11, P6), built on IndentStack (§11.7) and its strict-monotonicity invariant (I6).

Deliverable

The off-side fixture corpus (corpora/offside/, including corpora/offside/eof/) is green for the hand-written reference lexer.

Acceptance

50 fixtures covering nested blocks, continuation lines, mixed tabs/spaces, and EOF unwinding all pass (offside.basic and offside.eof buckets, §28); a property test asserts count(Indent) == count(Dedent) for any fixture that does not contain Error(IndentMismatch) (I6); the §8.5 worked failure-path example (mixed tab/space at line 3) is codified as a named fixture and passes.

Fixtures
Fixture Purpose Expected Output
corpora/offside/010-nested-blocks.json Multi-level INDENT/DEDENT count(Indent) == count(Dedent)
corpora/offside/020-continuation.json Bracket-depth suppression no INDENT/DEDENT inside unmatched brackets
corpora/offside/030-mixed-tab-space.json §8.5 worked failure path, codified Error(IndentMismatch) at the tab byte
corpora/offside/eof/001-unwind.json EOF dedent unwinding one Dedent per open level, then Eof
corpora/offside/040-blank-and-comment-lines.json Non-dedent-triggering lines zero spurious INDENT/DEDENT
Pitfalls
  • Mixed tabs and spaces is the classic Python 2→3 break — pick the strict policy (ADR-23) and document it; do not let a later phase quietly relax it without a new ADR row.
  • A blank line is whitespace-only, not a dedent — an implementation that treats a blank line as "indent level 0" will spuriously close every open block.
  • A comment-only line is not a dedent either — the scanner must look ahead past the comment before deciding whether the next real line dedents.

⬜ Phase 8 — String Interpolation & Lexer Modes §20

Objectives

Land the mode stack (§11.6, P5, ADR-12) across both backends and the seed language's template-literal interpolation, plus raw-string capture — the full lexer-modes surface promised in §1.

Deliverable

The interpolation fixture corpus (corpora/modes/template/, corpora/modes/raw/) is green for the hand-written reference; the mode-aware generated backend (from Phase 5) passes the same corpus.

Acceptance

80 fixtures covering nested interpolation, escapes inside templates, unterminated templates, and mismatched interpolation closes all pass (modes.template, modes.raw buckets, §28); a property test asserts mode_stack.depth() == 1 at end of input for every well-formed fixture (I5); the §8.3 worked example (9-step trace) is codified as a named fixture and passes exactly.

Fixtures
Fixture Purpose Expected Output
corpora/modes/template/000-worked-example.json §8.3 trace, codified 9-step mode sequence exact match
corpora/modes/template/030-nested-braces.json Local brace-depth tracking ${ {a:1} } resolves correctly

corpora/modes/raw/010-hash-delimited.json Raw-string hash-count matching correct close on matching # count
Pitfalls
  • The interpolation close } must be distinguished from an ordinary code } at equal depth — the depth_at_entry field on the Code-mode push is exactly this disambiguator; omitting it breaks every nested-object-literal-in-interpolation case.
  • A \n inside a single-quoted string is Error(UnterminatedString); inside a template literal it is allowed — this asymmetry must be documented, not just implemented, or a future contributor "fixes" one to match the other.
  • A \${ inside a template literal is an escape, not an interpolation start — the scanner must consume the backslash before testing for ${.

Acceptance

trivia.attach and trivia.stream buckets (§28) are 100% green; a property test asserts roundtrip invariance (I3) under Stream policy for 10 MB of seed-language source (benchmarks/corpora/, reused from Phase 11); leading/trailing attachment matches the documented Roslyn rule exactly on the corpora/trivia/attach/ fixtures — verified by byte-exact comparison, not approximate matching.

Fixtures
Fixture Purpose Expected Output
corpora/trivia/attach/*.json Leading/trailing attachment per the Roslyn rule exact match, incl. trailing-stops-at-newline
corpora/trivia/stream/*.json Trivia tokens emitted in source order every trivia byte appears as a distinct token

Pitfalls
  • Doc comments are not whitespace — a downstream rustdoc-style extractor needs TriviaKind::DocComment distinct from LineComment; conflating the two silently breaks doc-comment tooling built on this lexer.
  • A shebang line must not be promoted outside offset 0 — #! mid-file is two ordinary tokens.
  • AttachTrailing's trailing-trivia-stops-at-first-newline rule (the Roslyn convention) is easy to get backwards — a trailing comment on the last line of a file must not accidentally span past EOF and swallow a following blank line's trivia.

⬜ Phase 10 — Incremental Relexing §22

Objectives

Land the IDE-grade incremental relexing path (P9, ADR-15): given a previous token stream, an edit envelope, and the new source bytes, produce the minimal TokenDelta — the longest and most architecturally consequential phase in the plan, because it retroactively validates every runtime type designed since Phase 0.

Deliverable

IncrementalLexer::apply_edit (§11.9) is implemented and exercised by the examples/incremental-editor/ toy IDE backend against real multi-edit sessions.

Acceptance

100 fixtures of (source, edit, expected_diff) in corpora/incremental/ all pass (incremental bucket, §28); a property test over 10,000 random edits to a 100 KB seed-language file asserts prev + apply(delta) == from_scratch_lex(new_source) token-by-token (I12); benchmarks/incremental.rs measures relex time for an edit at the 50th, 90th, and 99th percentile byte offset of the file, all ≤ 1 ms p99 (M6, §4).

Fixtures
Fixture Purpose Expected Output
corpora/incremental/010-single-byte-insert.json Minimal edit, single token affected Replace delta of exactly 1 token
corpora/incremental/030-mode-boundary-edit.json Edit crosses a mode transition full relex-to-EOF fallback (I12)
corpora/incremental/050-indent-change.json Edit changes line indentation alignment terminates at the affected lines
corpora/incremental/070-token-interior-edit.json Edit lands mid-identifier relex restarts from token start, not cursor
benchmarks/incremental.rs::p50_p90_p99 M6 latency gate all three percentiles ≤ 1 ms
Pitfalls
  • prev spans must be adjusted by the edit's length delta before comparison with newly lexed spans — an off-by-one here invalidates the entire alignment silently (not a crash, a wrong-but-plausible-looking result).
  • An edit landing inside a token requires re-lexing from that token's start, not the edit cursor — a common shortcut ("just relex from edit.start") produces a token stream that looks right locally but is wrong at the token boundary.
  • An edit that changes a multi-line block comment's terminator changes the kind of every following token until the next */ — the alignment check must catch this via the kind-and-span comparison (§22.2 step 3), not assume "same starting byte means same token."

⬜ Phase 11 — Conformance, Fuzzing & Benchmarks §23

Objectives

Land the conformance harness, the fuzz harness, and the benchmark suite — the phase that gates Done for the whole toolkit and closes the core 12-phase build path (Phases 0–11).

Deliverable

Acceptance

Every non-deferred conformance bucket is 100% Pass (§28); a 24-hour cargo-fuzz run across all four targets completes with zero unexpected panics (M9); dense-backend throughput ≥ 100 MB/s (M2) and ≥ 80% of logos's throughput on an equivalent rule set (M4) are both met on the reference machine; conformance suite wall-clock ≤ 30 s (M8).
