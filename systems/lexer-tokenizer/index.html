In one paragraph

A lexer (tokenizer) is the first stage of a compiler or editor tool. It turns raw source bytes into a stream of labelled pieces called tokens, each carrying its byte range, and does nothing more: no syntax tree, no grammar (§1). This design, mini-lex, is an embedded Rust library with two interchangeable engines: a derive macro that compiles per-token rules into a fast state machine at build time, and a hand-written reference lexer that serves as the ground truth (§1, P1). It also owns whitespace and comments, string-interpolation modes, indentation tokens and incremental re-lexing for editors (§1). Compiler, linter and IDE authors link it into their own programs (§1).

The problem, concretely

Correctness is silently lost in the lexer. The blueprint's own list of ways to get it wrong: a stray \r\n inside a here-document, a UTF-8 byte-order mark that shifts every byte offset by three, a raw string closed by the wrong delimiter, an indentation stack that drifts after a tab/space mix, a /* comment whose embedded */ was meant to stay inert (§2). Whatever the lexer gets wrong, every downstream consumer inherits at once (§2).

The obvious way to write one is to try each rule's regular expression at the current position and keep the longest match (§36 A1). That is fine for a script with at most ten rules and inputs of a few KB, but it costs O(rules × positions), which makes the 100 MB/s target unreachable (§36 A1, ADR-02). So the design fuses all rules into one automaton at build time instead (ADR-02, MM1).

Speed is only half of it. A lexer that throws away whitespace cannot feed a formatter or a diff tool, so every byte must end up inside some token (MM4, P4). A lexer that aborts on the first bad byte anywhere in a 10 MB file loses the entire lex, so errors are tokens (P7). And an editor needs a one-byte edit relexed within 1 ms p99, so incremental relexing is part of the runtime, not a bolt-on (§4, P9).

How it works, end to end

At build time the macro crate turns rules into a state machine; at run time a scanner walks the source bytes with it (§3). §3's diagram, shortened:

 Embedder: #[derive(MiniLex)] enum Token {...}   or   hand-written `impl Lexer`
 mini_lex_runtime: Lexer trait · Cursor · Trivia model · ModeStack · IndentStack · SourceMap
                   · IncrementalLexer
        │ same trait                              │ same trait
 Generated DFA (mini_lex_codegen output)    Hand-written lexer (reference module)
 dense table OR sparse arms · PHF keywords       match-on-byte · mode stack · off-side stack
 mini_lex_codegen (build time): parse → Hir → Thompson NFA → subset-construct → Hopcroft-minimise
                                → quote! emit (dense/sparse) → PHF keyword table
  1. Build time: mini_lex_codegen. The macro reads each rule with regex_syntax used as a parser only (ADR-16), builds a Thompson NFA, subset-constructs a DFA, minimises it, and emits Rust with quote! in a dense or sparse shape (§3, ADR-17, §17.2). Construction is capped at 10,000 NFA states per rule and 100,000 DFA states, past which the build fails with compile_error! (§4, T2, T3, P12).
  2. Source in: Cursor. It tracks the byte offset and consumes a UTF-8 byte-order mark at offset 0 exactly once, so every span is post-BOM (§3, I10, ADR-08).
  3. Scan. The generated DFA and the hand-written mini-lex-reference lexer implement one Lexer trait and pass the same conformance fixtures, so an embedder swaps them with a feature flag (§3, §1, P1, P2).
  4. Keyword promotion. After an identifier, one perfect-hash lookup decides whether it is a keyword (§17.2, ADR-06, I11).
  5. Modes and off-side. Rule actions push and pop the ModeStack, which selects the active rule set (§20.2, P5). If the embedder opted in, IndentStack injects Indent/Dedent after each new line (§19.2, ADR-11).
  6. Out: (TokenKind, Span). The token is Copy, so the hot path allocates nothing; escape decoding and interning are the consumer's job (P8). Trivia follows the chosen policy (§21.2); errors come out as Token::Error(kind, span) in the same stream (ADR-13).
  7. Editor path: IncrementalLexer returns a minimal TokenDelta instead of a full re-lex (§22.2, §11.9).

mini-lex-cli wraps this as mini-lex tokenize <file>, printing (kind, span) as JSON (§1).

The core ideas

Longest match: one automaton for all the rules (§8.2, I1, I2)

Plain words: read bytes while the machine can still make progress; remember the last point where it was in an accepting state; when it can go no further, emit the token for that last accepting point (longest match, I1, MM2). When two rules accept the same length, the higher explicit priority wins, then the earlier declaration (I2).

How the machine is built (§15.2, §16.2). The NFA (nondeterministic automaton) has empty-move edges and tags accepting states with a token id. Subset construction makes it deterministic: start from the empty-move closure of the NFA start; for each state set S and byte b, T is the closure of everything reachable from S on b, and each new T becomes a DFA state. Hopcroft minimisation then merges equivalent states, starting from {accepting states grouped by tag} plus {non-accepting} and splitting by where transitions lead (§16.2, ADR-04).

The blueprint's tiny automaton for the keyword if against identifiers (§8.2):

Input bytes Path Result
i then a non-identifier byte S0 → S1 accepts Ident
if then a non-identifier byte S0 → S1 → S2 accepts If; ties with Ident, priority breaks it (I2)
iffy S0 → S1 → S2 → S3 → S3 accepts Ident at S3

S2 accepts If and is also a prefix of longer identifiers such as iffy. The DFA does not settle this when it is built; the scanner settles it at scan time by continuing while a longer match is reachable and committing only when the match cannot extend (§8.2). The Phase 4 fixture for the same conflict expects If for "if" and Ident for "iff" (§16.4). A property test checks dfa.accept(s) == nfa.accept(s) on 10,000 random strings (I1, §16.4).

Keywords have two descriptions. §8.2 and §16.4 treat if as a DFA rule that ties with the identifier rule and wins on priority. §17.2 collects every #[token("...")] into a keyword list promoted by a perfect-hash post-pass, and ADR-06 rejects fusing keywords into the DFA. The blueprint does not say how these fit together.

Spans, trivia and the roundtrip rule (P3, P4, I3, I4)

A span is a byte range {start, end}, nothing else (P3, ADR-09). Line and column are not stored on tokens: a SourceMap builds a line table lazily on the first column query, once per file (P10, MM8). Spans never overlap or go backward, except zero-width virtual tokens (I4).

Trivia (whitespace, comments, shebangs) is made of tokens with their own spans, so joining every token's bytes in order gives back the source under the Stream and AttachTrailing policies (roundtrip, P4, I3, MM4). The embedder picks how trivia is surfaced (§21.2):

  • Stream: every trivia token appears in the ordinary sequence.
  • AttachTrailing: trivia folds into each real token. Leading trivia is everything between the previous real token and this one; trailing runs to the next newline or real token, whichever comes first (the Roslyn rule).
  • Drop: trivia is not emitted, for a parser with its own skipping layer.

A shebang counts only at byte 0 (§21.2), and the BOM only at offset 0 (I10, T11).

Modes: a bounded stack, not a full context-free escape (§8.3, I5, MM3)

Some constructs nest: a template literal contains code, which can contain another template. A mode stack records which rule set is active; entering a construct pushes a mode, leaving pops it (P5, §20.2). The blueprint's trace of `hello ${name + "!"} world` (§8.3):

Step Mode change Consumed Emitted
1 Code → push Template ` nothing (mode transition only)
2 Template hello TmplPart
3 push Code, depth_at_entry=0 ${ TmplExprStart
4 Code name Ident
5 Code + Plus plus whitespace trivia
6 Code "!" StrDouble
7 pop to Template } TmplExprEnd
8 Template world TmplPart
9 pop to Code ` nothing (close tick)

Why depth_at_entry: inside ${ {a:1} } the inner braces raise a local depth to 1, so only the } at depth 0 closes the interpolation (§8.3, §20.6). At end of input a well-formed file has mode depth 1, and the base mode can never be popped (I5, §11.6). The stack is a pushdown extension of a regular language and can express LIFO-nested constructs, not arbitrary cross-references (MM3).

Off-side: a stack of indentation levels (§8.5, I6, MM5)

In indentation-sensitive languages, \n means "open a block", which a plain scanner cannot know. IndentStack keeps strictly increasing indentation levels and injects Indent/Dedent tokens as feed sees each new line's width (§11.7, ADR-11). The invariant is algebraic: count(Indent) - count(Dedent) == levels.len() - 1 at every point (I6). Rules (§19.2): width is a raw byte count; a line inside an unmatched bracket is a continuation and skips off-side; blank and comment-only lines trigger no dedent; at EOF one Dedent is injected per level still above 0, then Eof.

The failure case (§8.5): line 2 is indented with four spaces, line 3 starts with a tab. Under the strict policy, any tab in leading whitespace is Error(IndentMismatch) on the tab byte, and the stack carries on at the last valid level (4) instead of desynchronising every later line (§8.5, ADR-23, I6, FM-5).

Incremental relexing: opportunistic alignment, guaranteed correctness (§22.2, I12, MM7)

An editor changes a few bytes, and the latency budget is 1 ms (§4, P9). The algorithm (§22.2):

  1. Keep the largest prefix of the old tokens that ends before the edit.
  2. From the edit start, lex forward over the new source, tracking a candidate position in the old tokens, shifted by the edit's length change (edit.new_end - edit.old_end).
  3. When a newly lexed token has the same kind and adjusted span as the candidate old token, declare alignment: everything from there on is reusable.
  4. Output the minimal TokenDelta describing the replaced range.

Edits that change the mode stack at the alignment point (an unmatched ${) make alignment fail and lexing continue to EOF; an edit inside a token restarts from that token's start (§22.2). The contract is exact: old tokens plus the delta must equal a from-scratch lex, token by token (I12). Failing to align is allowed; aligning wrongly is not (MM7, FM-10). The top pitfall is forgetting to shift old spans by the length delta, which gives a wrong but plausible result (§22.2, §22.6).

Errors are tokens (§8.4, P7, I9)

A malformed byte becomes Token::Error(kind, span) and scanning continues; next_token never returns Result::Err (I9, ADR-13). Each error kind has its own resync point (ADR-24). The unterminated let x = "unterminated yields Error(UnterminatedString) from the opening quote to EOF; a newline first would be the resync point (§8.4, FM-2). At EOF every open mode is force-closed with one Error(InterpolationMismatch) per level (I5, FM-6).

The trade-offs — where engineers disagree

Fuse the rules into one automaton, not a regex engine per rule (ADR-02)

Chosen: one fused longest-match DFA; no regex engine at runtime (ADR-02). Rejected: run each rule as an independent regex per position and keep the longest (ADR-02). When the rejected choice is right: a prototype or one-off script tokenizing under 1 KB, where building the fused DFA is not worth the setup (ADR-02).

Dense jump table by default, sparse match arms opt-in (ADR-05)

Chosen: a dense table (one indirect lookup per byte) as default; sparse match arms selectable with #[lexer(backend = "sparse")] (ADR-05). Rejected: sparse-only, or dense-only (ADR-05). When the rejected choice is right: an embedded or Wasm target with a tight binary-size budget and a low-throughput requirement, which wants sparse (ADR-05).

Keywords by perfect hash, not fused into the DFA (ADR-06)

Chosen: a CHD perfect-hash function applied after the Ident match: one hash plus one byte comparison per identifier, and the main DFA's size is independent of the keyword count (ADR-06). Rejected: an Aho–Corasick multi-pattern automaton fused into the main DFA (ADR-06). When the rejected choice is right: a grammar whose keywords are not a closed, rarely changing set (a templating DSL with user-defined soft keywords), since fusion avoids regenerating the hash on every keyword-list edit (ADR-06).

Byte-offset spans, not line and column (ADR-09)

Chosen: u32 byte offsets; line and column come on demand from SourceMap (ADR-09, P3). Rejected: store (line, column) on each token (ADR-09). When the rejected choice is right: a tool whose only consumer is a line-oriented diagnostics renderer with no byte-slicing need at all (ADR-09).

Trivia policy: which default (ADR-10)

Chosen: Stream (every trivia token emitted) as the globally selectable policy, with AttachTrailing chosen per embedder (ADR-10). Rejected: AttachTrailing as the only default (ADR-10). When the rejected choice is right: a hand-rolled recursive-descent parser with no separate trivia-skipping layer (ADR-10). The blueprint disagrees with itself: ADR-10 names Stream as the default, while §21.2 labels AttachTrailing "default, ADR-10".

Errors as ordinary tokens, not a Result (ADR-13)

Chosen: Token::Error(LexError, Span) in the normal stream, as in rustc and Roslyn (ADR-13). Rejected: an iterator of Result<Token, LexError>, which forces halt-on-first-error or matching everywhere (ADR-13). When the rejected choice is right: a one-shot validator asking only "is this file lexically valid", where short-circuiting is simpler and the stream is discarded (ADR-13).

Strict tab policy in indentation (ADR-23)

Chosen: any tab in leading whitespace is Error(IndentMismatch), surfacing the bug at lex time (ADR-23). Rejected: permissive tab-to-fixed-width conversion, the silent conflation behind the classic Python 2-to-3 breakage (ADR-23, MM5). When the rejected choice is right: a codebase migrating from a tab-indented legacy dialect where permissive conversion is an explicit, documented transitional policy (ADR-23).

Roads not taken

Backtracking regex-per-rule lexer (§36 A1): wins for at most ten rules and inputs of a few KB. Rejected on O(rules × positions) throughput (§36 A1).

Brzozowski derivatives as the main construction (§36 A2): wins for grammars dominated by large Unicode general-category classes, where subset construction blows up (ADR-03, ADR-14). Rejected for now because subset construction is simpler and fast enough for the ≤ 512-rule core path; derivatives are deferred, not abandoned (§36 A2).

Tokenization inside a parser combinator (§36 A3): wins for small DSLs prototyped quickly. Rejected because P1 needs a first-class, independently tested lexer stage (§36 A3).

Scannerless PEG parsing (§36 A4): wins where token boundaries are context-sensitive. Rejected because the boundary is "tokenizer, not parser" and scannerless ships no token stream (§36 A4, §1).

Deferred register (§37): the derivative backend waits for Unicode-driven state counts near the 100,000 budget (T3); a wasm32 build waits for a browser-side embedder; SIMD whitespace skipping waits for M2 to plateau below 150 MB/s; here-document mode, a tree-sitter scanner ABI and the 30-day fuzz gate (M10) each wait for their own trigger (§37).

What must never be false

Each line gives the invariant, then how the system notices a violation (§7).

  • I1 Longest match. Noticed by dfa.accept(s) == nfa.accept(s) on 10,000 random strings.
  • I2 Equal-length ties go to higher priority, then earlier source order. Noticed by the if-versus-Ident fixture.
  • I3 Concatenated token bytes equal the source. Noticed by the roundtrip bucket, fuzz target roundtrip_invariant, and lex.roundtrip_mismatch_total (must be 0).
  • I4 Spans never overlap or go backward (zero-width virtual tokens excepted). Noticed by a property test over the fixture corpus.
  • I5 Mode depth is 1 at EOF for well-formed input. Noticed by modes fixtures and the lex.mode_depth_at_eof gauge.
  • I6 count(Indent) - count(Dedent) == levels.len() - 1. Noticed by a property test, offside fixtures and the lex.indent_depth gauge.
  • I7 No panics on arbitrary bytes, no undefined behaviour under Miri, every span in bounds. Noticed by fuzz target tokenize_anything (24 h) and lex.panic_total (must be 0).
  • I8 Zero heap allocations within the stacks' inline capacity (8 modes, 16 indent levels). Noticed by an allocation-counting harness in CI and lex.heap_alloc_total.
  • I9 next_token never returns Result::Err. Noticed by the errors.recovery bucket and lex.error_total{kind}.
  • I10 The BOM is consumed once, every span post-BOM. Noticed by the spans.bom bucket and lex.bom_detected_total.
  • I11 Keyword promotion is exact against the closed keyword set. Noticed by the tokens.seed fixture's one case per keyword; a hash collision is a compile_error! at build time.
  • I12 Previous tokens plus apply_edit equal a from-scratch lex. Noticed by a property test over 10,000 random edits and lex.incremental_realign_total.

What breaks in production

Several of these are build-time or CI faults, because the library is embedded and has no running process of its own to recover (§4).

  • FM-1: a panic or Miri-flagged undefined behaviour. Cause: a bounds-check gap in Cursor or in the unsafe dense byte loop. Detected by the 24 h tokenize_anything fuzz run. No automatic recovery; Sev-1. Minimise with cargo fuzz tmin, bisect, patch, keep the input as a regression fixture (§25, I7).
  • FM-2: Error(UnterminatedString) at EOF. Cause: a source truncated mid-string or a genuine unterminated literal. Detected by the errors.recovery bucket and lex.error_total. The scanner resyncs at EOF or the next newline; a production spike suggests truncation in an upstream file transfer (§25).
  • FM-5: Error(IndentMismatch). Cause: tabs mixed into leading whitespace. Detected by the offside bucket. The stack pops to the nearest level not above the new indent; if widespread, normalise tabs to spaces before lexing (§25, ADR-23).
  • FM-6: Error(InterpolationMismatch). Cause: an unclosed template literal, e.g. a file saved mid-edit with an open ${. Detected by the modes.template bucket. EOF force-closes every open mode, one error per level (§25).
  • FM-7: the build fails with a state-count compile_error!. Cause: a rule set past the 10,000 NFA or 100,000 DFA budget. Detected by trybuild overflow fixtures. No automatic recovery: split the rule set, simplify the pattern, or adopt the deferred derivative backend (§25).
  • FM-8: roundtrip mismatch. Cause: a trivia or span bug that drops or duplicates bytes. Detected by the roundtrip bucket and lex.roundtrip_mismatch_total above 0. Debug builds emit Error(RoundtripViolation); release builds log and continue. Sev-1, bisect (§25, I3).
  • FM-10: incremental disagrees with a full lex. Cause: an alignment bug such as a span off-by-one. Detected by the 10,000-edit property test. The algorithm falls back to a full relex when it doubts alignment; this failure means it wrongly did not doubt. Sev-1 (§25, I12).

Threats worth knowing (§24): T1, deeply nested input exhausting the mode or indent stack, answered by 65,535-deep counters and Error(LimitExceeded) (FM-12); T3, a rule set that blows up the DFA at build time, answered by the 100,000-state cap; T5, a source over 4 GiB overflowing u32 spans, answered by a loader that rejects it before the first token (ADR-21); T10, a stale prev token list from an embedder's cache, answered by an alignment check that never trusts prev. Timing side channels (T6) are an explicit non-goal (§24).

The benchmark harness always runs with spans, trivia and error tracking enabled; a stripped "fast" configuration is not a valid measurement (§4).

How it compares

  • rustc_lexer: hand-written, returns raw (TokenKind, len) pairs and leaves spans and trivia to rustc_parse. Fine for a compiler that owns position tracking; as a reusable toolkit each consumer would rebuild that layer (§33).
  • Roslyn (Lexer.cs): hand-written, trivia attached to syntax tokens, production red-green tree for incremental reuse. Wins in a single-language IDE; no generator because C#'s grammar is fixed (§33).
  • logos: proc-macro DFA from annotated enum variants, no first-class mode stack or off-side utility. Wins for C-like grammars without interpolation or indentation (§33).
  • re2c: standalone C generator whose "condition" feature is the ancestor of the mode stack. Wins on raw generated-code throughput in C or C++, with no memory-safety guarantee (§33).
  • Tree-sitter: a hand-written C lexer inside an incremental parser, so incrementality is at parse-tree level. Wins when the consumer wants incremental parsing, not a bare tokenizer (§33).

If you only remember three things

A lexer is a compiled decision procedure, not an interpreter of rules: all rules are fused into one automaton at build time and it commits to the longest match (MM1, MM2). Every byte is either inside a token or it is a bug, and errors are tokens too, so a formatter can rebuild the source and one bad byte never aborts a file (MM4, P7). Incremental relexing is a correctness relation, not a speed trick: the result must always equal a full re-lex, and when alignment is in doubt the design simply lexes further (MM7, I12).

Words used here

  • Token: a labelled piece of source, a kind plus a byte range (§11.2, §38).
  • Span: a start and end byte offset, with no line or column attached (§11.1, ADR-09).
  • Trivia: whitespace, comments and shebangs, kept as tokens so no byte is lost (P4, §38).
  • DFA: a state machine with exactly one next state per state and byte (§38).
  • NFA: the intermediate machine from Thompson construction, before nondeterminism is removed (§38).
  • Hopcroft minimisation: merging equivalent DFA states in n log n time (§38, ADR-04).
  • Longest match (maximal munch): the rule that the lexer commits to the longest accepting prefix (I1, §38).
  • Lexer mode / mode stack: a named rule-set context, and the stack that nests them for interpolation and raw strings (§38, P5).
  • Off-side rule: indentation is significant, so virtual Indent and Dedent tokens are injected (§38).
  • Roundtrip: joining every token's bytes gives back the source exactly (I3).
  • Incremental relexing: producing the updated token stream from the old one plus an edit, without a full re-lex when alignment succeeds (P9, §22).
