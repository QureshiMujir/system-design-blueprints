Decisions (§9) · 24 ADRs

ADR-01

Implementation language + macro system

Chosen

Rust (edition 2024) + proc-macro2/syn/quote

Rejected

Haskell + Template Haskell (alex-shaped); OCaml + ppx (ocamllex-shaped)

When the rejected choice is right

A single-team, single-language OCaml compiler project (e.g. an ML-family research compiler) where ocamllex is already the house tool and there is no cross-language embedding need

Why: Most production-mature proc-macro story; no_std-capable runtime; generated code fuses into the embedder's own crate

ADR-02

Lexer vs. regex engine

Chosen

Lexer composes many rules into one fused longest-match DFA; no regex engine at runtime

Rejected

Run each rule as an independent regex match per position, keep the longest

When the rejected choice is right

A prototype or one-off script tool tokenizing < 1 KB inputs where engineering the fused DFA is not worth the setup cost

Why: Throughput: O(rules × positions) backtracking vs. one fused automaton pass

ADR-03

DFA construction strategy

Chosen

Subset construction (Thompson NFA → DFA) at proc-macro time

Rejected

Brzozowski derivatives

When the rejected choice is right

Grammars dominated by large Unicode property classes, where derivative construction avoids subset construction's exponential blowup (PhaseDeferred("§16.2"))

Why: Faster to generate at the rule-set sizes we target (≤ 512 rules)

ADR-04

State minimisation algorithm

Chosen

Hopcroft (n log n)

Rejected

Moore minimisation (O(n²))

When the rejected choice is right

A DFA with < 50 states where the simpler Moore implementation's constant factor wins and code-review simplicity matters more than asymptotics

Why: Constant factor on hash-table partition refinement is acceptable at compile time for our state counts

ADR-05

Codegen backend selection

Chosen

Dense jump-table default; sparse match-arm opt-in

Rejected

Sparse-only; dense-only

When the rejected choice is right

An embedded/Wasm target with a tight binary-size budget and a low-throughput requirement — #[lexer(backend = "sparse")]

Why: Dense wins throughput (one indirect lookup/byte); sparse wins binary size

ADR-06

Keyword recognition

Chosen

Perfect-hash function (CHD algorithm) post-pass after Ident

Rejected

Aho–Corasick multi-pattern automaton fused into the main DFA

When the rejected choice is right

A grammar where keywords are not a closed, rarely-changing set (e.g. a templating DSL with user-defined "soft keywords") — Aho–Corasick fusion avoids PHF regeneration on every keyword-list edit

Why: One hash + one byte-equality check per identifier; keeps the main DFA's state count independent of keyword-set size

ADR-07

Input encoding boundary

Chosen

UTF-8 only; #[lexer(source = "bytes")] escape hatch

Rejected

Accept arbitrary encodings at the lexer boundary

When the rejected choice is right

A legacy-encoding-heavy ecosystem (e.g. Shift-JIS source files still in the wild) where the embedder's I/O layer cannot be trusted to normalise before handoff

Why: Encoding negotiation belongs to the I/O layer, not the tokenizer

ADR-08

BOM handling

Chosen

UTF-8 BOM at offset 0 consumed silently, recorded in SourceMap::has_bom

Rejected

Reject files with a BOM as an error

When the rejected choice is right

A strict-conformance tool (e.g. a spec-compliance checker) whose users need to be told a BOM is present rather than have it silently stripped

Why: The most common encoding bug in production is a BOM shifting every span by 3 bytes; handling it once in the runtime avoids every embedder rediscovering the bug

ADR-09

Span representation

Chosen

Byte offsets (u32), not native (line, column)

Rejected

Store (line, column) per token directly

When the rejected choice is right

A tool whose only consumer is a line-oriented diagnostics renderer with no byte-slicing need at all — direct (line,col) avoids the SourceMap indirection

Why: Byte offsets are O(1); (line,col) requires the line table, paid only on demand via SourceMap

ADR-10

Default trivia policy

Chosen

Stream (every trivia token emitted) globally selectable, AttachTrailing per-embedder

Rejected

AttachTrailing as the only default

When the rejected choice is right

A hand-rolled recursive-descent parser with no separate trivia-skipping layer — AttachTrailing is the right default there (§20)

Why: IDE tooling wants every byte visible; compilers typically want it attached so the parser sees one token at a time

ADR-11

Off-side rule implementation

Chosen

IndentStack runtime utility, embedder opts in via constructor flag

Rejected

Hand-roll indentation tracking per seed language

When the rejected choice is right

A language with no off-side rule at all (C-family) — the flag stays off and IndentStack is simply unused, at zero runtime cost

Why: The lexer cannot know \n is an INDENT without help; the runtime utility gives the invariant (I6) once

ADR-12

Lexer-mode implementation

Chosen

Runtime-owned ModeStack, shared by both backends

Rejected

Per-backend ad hoc mode handling

When the rejected choice is right

A language with exactly one lexical mode and no interpolation/raw-strings/here-docs — the mode stack degenerates to depth-1-always at zero cost, so there is no real regime where hand-rolling wins, but a pure single-mode toy lexer for teaching may reasonably skip the abstraction

Why: Generated and hand-written lexers must agree on mode semantics for P1 (ground-truth duality) to hold

ADR-13

Error signalling

Chosen

Token::Error(LexError, Span) in the ordinary stream

Rejected

Result<Token, LexError> iterator

When the rejected choice is right

A one-shot validation tool whose only job is "is this file lexically valid, yes/no" — a Result-based short-circuit is simpler there and the token stream is discarded anyway

Why: Forces the consumer to choose halt-on-first-error or nested-match-everywhere; Error as a token kind is production-tested (rustc, Roslyn)

ADR-14

Large-Unicode-class backend

Chosen

Deferred: revisit Brzozowski derivatives for Phase-2 (PhaseDeferred("§16.2"))

Rejected

Ship derivatives in Phase 0

When the rejected choice is right

A grammar whose rules are dominated by full Unicode general-category classes (e.g. \p{L} equivalents across many scripts) where subset construction's state count becomes the bottleneck today, not later

Why: Subset construction is sufficient and faster to implement first; derivatives are a compaction optimisation, not a correctness requirement

ADR-15

Incremental relexing scope

Chosen

First-class runtime feature (IncrementalLexer), shipped in the core path

Rejected

Stretch goal, bolted on after Phase 11

When the rejected choice is right

A batch-only compiler (no IDE/LSP consumer, ever) — the incremental path is pure unused surface area there, and a from-scratch-only lexer is simpler to maintain

Why: The IDE integration pattern is core to the toolkit's value proposition, not an afterthought (P9)

ADR-16

Rule-pattern parsing

Chosen

regex_syntax crate, used as a parser only

Rejected

Hand-write a regex parser

When the rejected choice is right

A toolkit targeting a non-Rust host language where regex_syntax is unavailable — a hand-rolled parser is the only option there

Why: De-facto standard, well-fuzzed, ships the Unicode tables we need

ADR-17

Codegen stack

Chosen

proc-macro2 + syn + quote

Rejected

Raw TokenStream manipulation without the trifecta

When the rejected choice is right

A build-script-based (non-macro) code generator invoked out-of-band — raw TokenStream/string templating is adequate and avoids the proc-macro compile-time cost entirely

Why: The standard, well-documented Rust proc-macro stack; avoids reinventing quasi-quotation

ADR-18

Licensing

Chosen

Apache-2.0 for the runtime and generator

Rejected

ELv2 (Elastic License v2) for the whole toolkit

When the rejected choice is right

A hosted, multi-tenant "lexing as a service" product built directly on top of this toolkit — that control-plane layer is the regime ELv2 is reserved for (ADR-18 note)

Why: Open-core split reserved for a later hosted lexer-as-a-service control plane; the core toolkit must be maximally embeddable

ADR-19

Fuzzing harness

Chosen

cargo-fuzz (libFuzzer) and afl.rs, both wired

Rejected

cargo-fuzz only

When the rejected choice is right

A resource-constrained CI budget where only one 24 h fuzz slot is affordable — cargo-fuzz alone is the pragmatic minimum there

Why: Two coverage strategies (libFuzzer's SanCov vs AFL's edge coverage) catch different bug classes; the union is strictly better

ADR-20

Benchmark harness

Chosen

criterion

Rejected

Hand-rolled timing loops

When the rejected choice is right

A quick manual sanity check during development (not a gated benchmark) — a hand-rolled Instant::now() loop is faster to write and sufficient there

Why: Statistical reporting (confidence intervals, outlier detection) matters at the throughput numbers targeted (§4, §31)

ADR-21

Byte-offset width

Chosen

u32 (4 GiB file cap)

Rejected

u64

When the rejected choice is right

A log-processing or genomics-scale tokenizer expected to see multi-terabyte single "files" — u64 offsets are the only viable choice there

Why: Halves the Span/Token footprint, doubling cache-line density in the hot path (I8, §4)

ADR-22

Mode/indent stack storage

Chosen

SmallVec with inline capacity 8 (modes) / 16 (indent levels)

Rejected

Plain heap-allocated Vec

When the rejected choice is right

A language with pathologically deep nesting as its normal case (e.g. heavily macro-expanded template metaprogramming) where the inline capacity is exceeded on nearly every file — a plain Vec removes the wasted inline-capacity copy cost there

Why: Empirical p99 depth for the seed language under stress fits inline, avoiding a heap allocation on the common path (I8)

ADR-23

Mixed tab/space off-side policy

Chosen

Strict: any tab in leading whitespace is Error(IndentMismatch)

Rejected

Permissive: convert tabs to a fixed width and proceed (Python-2-style)

When the rejected choice is right

A codebase migrating from a tab-indented legacy language variant where permissive conversion is an explicit, documented transitional policy

Why: Silent tab/space conflation is the classic Python 2→3 breakage; explicit rejection surfaces the bug at lex time instead of at runtime

ADR-24

Error resynchronisation granularity

Chosen

Per-rule resync point (documented per LexError variant, FM-2..FM-6)

Rejected

Whole-file abort-and-restart from the top on any error

When the rejected choice is right

A security-sensitive parser (e.g. a sandboxed config-file loader) that prefers to treat any lex error as fatal for the whole input rather than emit a partially-recovered token stream

Why: Keeps errors local; one bad byte does not invalidate spans already computed for the rest of the file

36. Alternative Architectures (Roads Not Taken)

Four fundamentally different architectures for the same problem — not parameter tweaks.

A1 — Backtracking regex-engine-based lexer.

Step Per-position decision (no fused automaton)
At current position p Every rule's regex is evaluated independently against p — O(rules) matches per position
Selection Winner = the longest candidate match; ties broken by rule order
Emission Token for the winner is emitted; p advances by the winner's match length
Termination Position reaches end of source

Regime where it wins: a rule set with ≤ 10 rules and inputs under a few KB, where engineering a fused DFA is not worth the setup cost (a one-off script tool). Real system: early Python PLY-style and many hand-rolled nom-based lexers embody exactly this per-position-regex-match pattern. Rejection reason: O(rules × positions) throughput is categorically worse than one fused DFA pass at the toolkit's target scale (ADR-02, §9), and the 100 MB/s M2 target is unreachable this way at any rule-set size worth generating code for.

A2 — Brzozowski-derivative-based DFA construction as the primary strategy.

state := regex_hir                     # the "state" IS a regex, not a state-id
on byte b: state := derivative(state, b)
accept?  := nullable(state)

Regime where it wins: grammars dominated by large Unicode general-category classes, where subset construction's alphabet-partition blowup is the bottleneck (ADR-03/ADR-14, §9). Real system: the reference prototype described in Owens, Reppy, Turon 2009 (§5 Required Reading) builds exactly this derivative-based construction. Rejection reason: subset construction is simpler to implement correctly first and is fast enough for the ≤512-rule regime this toolkit targets in its core path (ADR-03); derivatives are deferred (PhaseDeferred("§16.2")), not abandoned.

A3 — Parser-combinator-embedded tokenization (no separate lexer stage).

token := alt(keyword, ident, number, string, punct)   # combinators ARE the lexer
expr  := token.then(token).then(...)                   # no token-stream boundary at all

Regime where it wins: small DSLs prototyped rapidly, where paying for a separate lexer stage and its own conformance boundary is pure overhead relative to the grammar's size. Real system: chumsky's lexer-mode combinators and nom-based lexers (already the lower-bound benchmark reference in §23.2) embody this fusion. Rejection reason: P1 (ground-truth duality, §6) requires a first-class, independently-conformance-tested lexer stage — fusing lexing into the parser removes the very boundary this toolkit's entire value proposition (a reusable, benchmarkable, swappable tokenizer, §1) depends on.

A4 — Scannerless (PEG-style) parsing, no lexer at all.

grammar := (identifier | number | "if" ws expr)*      # tokens are just grammar rules
                                                        # no token stream materializes

Regime where it wins: grammars whose token boundaries are genuinely context-sensitive and awkward to express as a regular language up front (some whitespace-sensitive or lookahead-heavy syntaxes) — packrat parsing (Ford 2002, §5 Required Reading) is often built scannerless for exactly this reason. Real system: PEG-based scannerless parser generators in this tradition. Rejection reason: this toolkit's explicit system boundary (§1) is "tokenizer, not parser" — a scannerless design has no tokenizer artifact to ship at all, and it forecloses the toolkit's entire value proposition of a reusable token stream consumed by an independent parser (Parser-Combinator, project 65, §1).
