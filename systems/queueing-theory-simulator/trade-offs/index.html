Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Optimistic (Time Warp) Execution

+-----------+     rollback      +-----------+
| Worker A  | <---------------- | Worker B  |
| (ahead)   |   causality       | (behind)  |
| local time|   violation       | local time|
+-----------+     detected      +-----------+
      |                               |
      v                               v
  speculative                    speculative
  event execution               event execution
      |                               |
      +---------- anti-messages ------+

Regime where it wins: massively parallel simulation where synchronization overhead of a strictly-ordered global event list would dominate, and rollback cost is cheap relative to forward-progress gains. Embodied by David Jefferson's Time Warp Operating System (1985, §5 Papers). Rejected because rollback-based speculative execution requires reversible or checkpoint-restorable side effects for every subsystem (metrics, WAL writes, observability), directly conflicting with P4's crash-only philosophy and massively complicating I5's replay-equivalence proof — a rolled-back speculative event must never have been observable, which is incompatible with P5's "observability by default."

Alt B — Actor-Model Distributed Simulation

+--------+  msg   +--------+  msg   +--------+
| Actor  | -----> | Actor  | -----> | Actor  |
| (node) |        | (node) |        | (node) |
+--------+        +--------+        +--------+
   mailbox           mailbox           mailbox
  (per-actor          (per-actor        (per-actor
   local time)         local time)       local time)

Regime where it wins: workloads where nodes are naturally independent long-lived processes with only message-passing coupling and no need for a single global consistent snapshot. Embodied by Erlang/OTP's scheduler and supervision-tree model (§2.5). Rejected because per-actor local time (no single global event-ordering authority) makes I1's total-order guarantee across the whole topology unenforceable without an additional global synchronization protocol — which would simply reintroduce a centralized scheduler, at which point QTS's binary-heap design already provides the total order for free.

Alt C — Timer-Wheel Event Scheduling

[0][1][2]...[N-1]   <- wheel slots, one per time-quantum
 |  |  |        |
 v  v  v        v
list list list  list  <- events bucketed by (timestamp mod N)

Regime where it wins: extremely high insertion/cancellation rates where O(1) amortized insertion matters more than exact tie-break ordering within a bucket, and time resolution can be coarsened without correctness loss. Embodied by Tokio's hierarchical timer wheel (§5 Reference Implementations). Rejected because a timer wheel's bucket resolution trades exact ordering for O(1) insertion — QTS's < 2µs p50 dispatch budget (§4) and bit-identical replay requirement (I5) both need exact (timestamp, sequence) ordering, not bucketed approximation; the binary heap (ADR-10) gives O(log n) insertion with exact order at a fan-out where cache locality keeps the constant factor small enough to hit the throughput budget anyway (§32 C1).

Alt D — Trace-Driven Replay Only (No Synthetic Generation)

recorded production trace  --->  replay engine  --->  metrics
   (fixed, no distributions)      (no RNG needed)

Regime where it wins: capacity-planning questions where the only thing that matters is "how does this exact recorded workload behave under a proposed change," and distributional/statistical generality is unneeded overhead. Embodied by CloudSim's trace-driven execution mode (§2.5, §31). Rejected as QTS's sole mode because it cannot answer "what happens under a workload we have not yet observed" — Monte Carlo orchestration and statistical convergence (§17) are core deliverables (§1) that a trace-only engine cannot provide; QTS supports trace-driven replay as one input mode but does not adopt it as the only mode.
