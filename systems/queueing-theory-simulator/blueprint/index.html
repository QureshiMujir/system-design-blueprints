1. Goal & Scope

Engineering definition. The Queueing Theory Simulator (QTS) is a deterministic, event-driven discrete-event simulation runtime for constructing, executing, validating, and statistically analyzing queueing systems and queueing networks under controlled, replayable workloads. QTS is a correctness-first simulation kernel, not a visualization tool: its primary deliverable is bit-identical replay of arbitrarily complex queueing topologies, with observability and statistical rigor as first-class runtime concerns rather than after-the-fact instrumentation.

Phase 0 deliverable — initial workspace packages (see §10, §37 for file-level detail):

  1. qts-core — shared IDs, canonical serialization, primitive newtypes.
  2. qts-errors — canonical error hierarchy shared by every crate.
  3. qts-clock — monotonic simulation clock, forbids wall-clock coupling.
  4. qts-rng — deterministic RNG and seed-lineage derivation.
  5. qts-event — event scheduler (binary heap, temporal ordering, cancellation).
  6. qts-queue — queue disciplines, admission control, capacity enforcement.
  7. qts-scenarios — scenario DSL parser and compiler.
  8. qts-metrics — histogram, statistics, and convergence engine.
  9. qts-storage — WAL and snapshot persistence.
  10. qts-replay — replay journal and divergence validator.
  11. qts-runtime — deterministic single-node event loop and coordinator glue.
  12. qts-observability — tracing spans, structured logs, metrics export.
  13. qts-cli — orchestration entry point, thin over the library crates.
  14. qts-testkit — property-testing and conformance harness support.
  15. qts-fixtures — packaged conformance fixture loader.

System boundaries.

Provides: deterministic event scheduling; open and closed queueing network simulation; FIFO/LIFO/Priority/WFQ/Processor-Sharing/SRPT/EDF disciplines; bounded buffers and backpressure propagation; failure injection; Monte Carlo orchestration with statistical convergence detection; bit-identical replay; distributed multi-worker experiment coordination (§19); structured observability (§20).

Delegates: container orchestration to Kubernetes (§19); metrics storage/query to Prometheus (ADR-04); distributed tracing backends to an OpenTelemetry collector (ADR-05); artifact object storage to an external object store accessed via qts-storage's pluggable backend trait (§29).

Does NOT provide: GPU-accelerated simulation (PhaseDeferred("§13")); real-time distributed execution against live production traffic; continuous real-world traffic ingestion; a browser-first visualization workflow (PhaseDeferred("§20")); ML-based scheduler optimization (PhaseDeferred("§16")); hardware cycle-accurate simulation.

Non-goals. QTS does not attempt to be a general-purpose discrete-event simulation language (contrast SimPy's generality, §31); it does not attempt wall-clock real-time guarantees; it does not attempt to be a drop-in production scheduler — it models scheduling, routing, and admission behavior for capacity planning and system design, it does not execute production traffic.

Deployment model. Five supported modes: (1) single-node deterministic execution for local development and CI; (2) multi-process Monte Carlo orchestration on one host; (3) CI-integrated benchmark and regression execution; (4) Kubernetes-batch distributed experiment execution via qts-coordinator (§19); (5) air-gapped reproducible-research deployment with no network egress, replay artifacts moved by sealed volume.

Target operators. Systems engineers, distributed-systems researchers, SRE and capacity-planning teams, performance engineers, database and storage engine authors, and academic simulation researchers who need reproducible, statistically defensible queueing measurements rather than a teaching toy.

What later phases unlock. Phase 3 (§15) unlocks arbitrary open/closed queueing network topologies; Phase 6 (§18) unlocks crash-recoverable long-running experiments; Phase 7 (§19) unlocks horizontally distributed Monte Carlo campaigns; Phase 8 (§20) unlocks production-grade operational observability; Phase 9 (§21) unlocks a closed conformance and fuzzing suite suitable for third-party contribution review.

Recommended language: Rust. Rationale: deterministic ownership semantics remove a whole class of aliasing-induced replay divergence; no GC means no stop-the-world pause can perturb the simulated (logical) clock's measurement of wall-clock dispatch cost (§28); cargo-fuzz and criterion give a mature, standardized fuzzing and benchmarking ecosystem (ADR-13, ADR-14); safe lock-free structures (crossbeam, Arc) make the Phase 7 coordinator tractable without a language-level data-race class of bug.

Rejected alternatives:

Language Rejection Reason
C++ Undefined-behavior risk and allocator inconsistency undermine bit-identical replay (I5).
Go GC pauses are non-deterministic wall-clock events that leak into dispatch-latency measurement.
Java JIT warm-up and GC amplification compromise both startup budget (§4) and replay determinism.
Python Single-node throughput ceiling (~10⁵ ops/s) is two orders below the §4 5M ev/s budget.
Zig Async and fuzzing ecosystem too immature for ADR-09/ADR-14 requirements as of this writing.

Prerequisites. Queueing theory (M/M/1, Jackson networks, Little's Law); probability and statistics (confidence intervals, heavy-tailed distributions); concurrency control and lock-free algorithms; event-driven runtime design; persistent storage engines (WAL, snapshotting); serialization systems; benchmarking methodology and Linux performance tooling (perf, flamegraphs); CPU cache and NUMA topology fundamentals.

Estimated timeline. Phase 0: 8–12 weeks. Full production-grade single-node baseline (Phases 0–6, §12–§18): 7–10 months. Distributed orchestration (Phase 7, §19) adds 3–4 months. Research-grade statistical validation and conformance hardening (Phases 8–9, §20–§21): additional 2–3 months. Total to a fully REAL-GOD-equivalent implementation: approximately 14–19 months for a small (2–4 engineer) team.

2. Why Build This

2.1 Systems Knowledge Developed

Event scheduling semantics; priority-queue performance behavior under load; deterministic simulation and replay; runtime observability design; temporal correctness under concurrent dispatch; statistical convergence and confidence estimation; resource contention and queue-collapse dynamics; load-shedding and admission-control tradeoffs; scheduling fairness under adversarial arrival patterns; throughput saturation behavior; backpressure propagation across a network of queues; tail-latency amplification through multi-hop pipelines.

2.2 Historical Importance

Queueing theory underlies operating-system schedulers (Linux CFS, §31), RPC systems, database execution engines, packet routers, storage controllers, hypervisor CPU schedulers, thread pools, Kafka-style log-structured messaging, CDN edge admission control, and telecommunication switching fabrics dating to Erlang's original loss-system formulas. QTS exposes the operational realities — variance, tail behavior, correlated failure — that closed-form queueing equations (M/M/1, Jackson network product-form solutions) assume away.

2.3 Engineering Muscles Exercised

Deterministic systems engineering; performance modeling under contention; runtime architecture for cooperative scheduling; failure-mode analysis; memory and allocation optimization; statistical rigor in benchmark design; protocol evolution under compatibility constraints (§25); scheduler debugging with only logical time as evidence; resource accounting under bounded budgets (§4); operational instrumentation that cannot itself perturb the system it measures (P10).

2.4 Production Engineering Concepts

Tail-latency diagnosis; queue-collapse containment; runtime isolation between simulation and metrics planes; adaptive batching; priority-inversion handling; crash-only recovery (P4); replay-based debugging; schema and wire compatibility across releases (§25); capacity planning from first-principles arithmetic (§32); work-conservation and fairness guarantees under contention.

2.5 Related Systems

Linux CFS and kernel schedulers; distributed tracing systems (Dapper, OpenTelemetry); Kafka; NGINX and Envoy event loops; Cassandra request pipelines; Erlang/OTP schedulers; SimPy; ns-3; OMNeT++; CloudSim; the Tokio async runtime; Aeron messaging; the Seastar shard-per-core reactor runtime; the LMAX Disruptor.

2.6 Calibration Value

Completing this project is a durable upgrade to: runtime reasoning under concurrency; scheduling-correctness intuition; contention analysis; throughput and latency modeling from first principles; deterministic-debugging discipline; distributed operational analysis; and reproducible benchmarking practice transferable to any latency-sensitive production system.

What Mastery Looks Like

  • Can derive a system's saturation point and p99 tail behavior from §4-style constraint arithmetic before writing a line of simulation code (Phase 0, §12).
  • Can explain, from the heap implementation up, why timestamp collisions require a stable deterministic tie-break and what breaks without one (Phase 1, §13).
  • Can distinguish work-conserving from non-work-conserving disciplines and predict fairness-error bounds for WFQ under adversarial arrival bursts (Phase 2, §14).
  • Can detect and explain a routing cycle or deadlock in an open queueing network using only the dependency graph and a bounded traversal budget (Phase 3, §15).
  • Can design a Monte Carlo convergence stopping rule that is statistically defensible rather than a fixed iteration count (Phase 5, §17).
  • Can reconstruct a crashed experiment's exact execution from WAL + snapshot lineage and prove replay equivalence bit-for-bit (Phase 6, §18).
  • Can reason about lease-based distributed coordination correctness under worker crash and network partition without introducing duplicate work execution (Phase 7, §19).
  • Can build an observability pipeline that is provably incapable of altering the behavior it measures (Phase 8, §20; invariant I8).

3.2 Subsystem Descriptions

qts-cli. Thin orchestration entry point: loads scenarios, drives batch execution, triggers replay, exports reports. Contains no simulation logic — all behavior delegates to library crates so the CLI itself never needs deterministic-replay testing (P1).

qts-scenarios. Deterministic compiler from declarative YAML scenario specs into normalized, canonicalized execution plans. Validates topology reachability, distribution parameters, and scheduling-policy references before the runtime ever sees a scenario (§15).

qts-coordinator. Owns experiment lifecycle across workers: lease issuance, seed partitioning, failure detection, work reassignment. This is the sole trust boundary between an operator-controlled controller process and untrusted or merely unreliable worker processes (§19, §22).

qts-runtime + qts-clock. Owns the simulation clock and single-threaded-per-shard event loop. Forbids wall-clock coupling (P3); the only legitimate time source for simulation logic is qts-clock::SimulationClock (§11).

qts-metrics. Bounded-memory histogram and statistics engine, isolated from runtime mutation (I8) so that observing the system never changes its trajectory — critical for replay equivalence (I5).

qts-queue + qts-network. Queueing-node and network-topology engine: disciplines, admission control, routing, and cross-node dependency graphs (§14, §15).

qts-event. The correctness-critical subsystem: a binary-heap scheduler owning temporal ordering and stable tie-breaking (I1) under which every other subsystem's guarantees are conditioned.

qts-storage + qts-replay. WAL-backed persistence and replay-journal validation enabling crash-only recovery (P4) and bit-identical replay equivalence (I5).

qts-observability. Structured telemetry export (metrics, traces, logs) that never feeds back into scheduling decisions (I8, P10).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every runtime decision must be a pure function of simulation state and seed lineage · Tradeoff: forbids ergonomic wall-clock shortcuts in tests and tooling · Operational: replay validator runs on every CI merge · Violated: irreproducible failures and invalid benchmark comparisons.
  • P2 — Backpressure Everywhere. Rule: every queue exposes a declared, enforced capacity · Tradeoff: bounded queues require an explicit drop or block policy instead of "just grow" · Operational: queue_capacity_violation_total alarms on any breach · Violated: unbounded queues cause hidden latency inflation and memory collapse.
  • P3 — Explicit Time Ownership. Rule: only qts-clock::SimulationClock advances simulation time · Tradeoff: no subsystem may read SystemTime::now() in the simulation path · Operational: a clippy lint fails CI (run on ADR-16's GitHub Actions pipeline) on forbidden time-source imports · Violated: wall-clock coupling destroys replay determinism (I5).
  • P4 — Crash-Only Recovery. Rule: subsystems recover exclusively via restart from WAL/snapshot state, never mutable in-place repair · Tradeoff: no "quick patch" repair path exists even for trivial corruption · Operational: recovery drills run in CI (fixtures/replay/crash_mid_flush.bin) · Violated: ad-hoc repair produces unauditable, non-replayable state.
  • P5 — Observability by Default. Rule: every subsystem emits metrics, traces, structured logs, and state-transition events without opt-in configuration · Tradeoff: baseline overhead budget consumed by telemetry (§4, <5% CPU) · Operational: §19 dashboards assume 100% subsystem coverage · Violated: blind spots during incident response (§23).
  • P6 — Replayability First. Rule: every execution path must be reconstructable from its journal · Tradeoff: journal write amplification (§4 WAL amplification <1.5x) · Operational: qts-replay runs as a CI gate on every scenario fixture · Violated: unexplainable production or benchmark anomalies.
  • P7 — Stable Wire Compatibility. Rule: protocol and storage format evolution must remain backward-compatible across MINOR versions (ADR mapped in §25) · Tradeoff: new fields must be additive, never repurpose a tag · Operational: qts-replay conformance suite runs old-format fixtures against the current binary · Violated: snapshots and journals from prior releases become unreadable.
  • P8 — Bounded Resource Usage. Rule: every long-lived collection has a declared capacity or eviction policy · Tradeoff: bounded histograms trade tail precision for fixed memory (ADR-08) · Operational: RSS budget (§4, 2 GB) checked in CI soak tests · Violated: unbounded growth causes OOM kills mid-experiment.
  • P9 — Canonical Serialization. Rule: semantically-equivalent structures must serialize to byte-identical output · Tradeoff: canonical field ordering costs a sort on every encode · Operational: qts-core::canonical roundtrip fixtures assert byte equality · Violated: hash-based replay validation (I5) becomes meaningless.
  • P10 — Isolation of Statistical State. Rule: qts-metrics may observe but never mutate simulation or scheduler state · Tradeoff: metrics collection cannot short-cut by piggy-backing on scheduler internals · Operational: qts-metrics compiles against read-only trait views only · Violated: heisenbug-class failures where observing a run changes its outcome.
  • P11 — Fail Fast on Invariant Violations. Rule: any invariant breach (§7) aborts the run and emits a forensic snapshot rather than attempting silent continuation · Tradeoff: no "best effort" degraded mode for correctness invariants · Operational: panic = "abort" in the Cargo release profile · Violated: silent corruption propagates into downstream statistical conclusions.
  • P12 — Zero Hidden Randomness. Rule: every random draw derives from an explicit, logged seed-lineage path (qts-rng) · Tradeoff: no subsystem may call an ambient global RNG · Operational: cargo fuzz target fuzz_scenario_parser asserts seed lineage completeness · Violated: replay divergence with no traceable cause (FM-1).

Debugging methodology: QTS is a deterministic simulator by construction, so every invariant above compiles to exactly one runtime assertion plus one replay-time cross-check — there is never a need to reproduce a bug under load, only to replay the exact seed lineage and step the assertion trace (qts-replay) until the violated invariant's assertion fires.

8. Domain Model — Queueing Entities & Event Lifecycle

8.1 Core Simulation Entities

QueueNode — a queueing station: node_id, scheduler_policy (§8.3), a service-time distribution, a queue_capacity, a retry_policy, and a routing_policy (§8.4).

WorkItem — a simulated request: item_id, creation_time, optional deadline, priority, service_cost, retry_count, trace_context (OpenTelemetry-compatible, §5 RFCs).

RuntimeEvent — a scheduled transition: event_id (EventId, §11), logical_timestamp, source_node, target_node, event_kind, payload_ref.

8.2 Event State Machine

CREATED
  |
  v
QUEUED ------> DROPPED        (I2 capacity breach or admission reject, I9)
  |
  v
RUNNING ------> RETRY_PENDING  (retry_policy triggers, bounded by retry_count ceiling)
  |                 |
  |                 v
  |            QUEUED (re-entry)
  v
COMPLETED

Every transition emits a structured event and a metrics counter increment (P5); no transition may occur without a corresponding RuntimeEvent passing through qts-event (I1).

8.3 Queue Disciplines (SchedulerPolicy, §11)

FIFO · LIFO · Priority · Weighted Fair Queueing (WFQ) · Round Robin · Processor Sharing (PS) · Shortest Remaining Processing Time (SRPT) · Earliest Deadline First (EDF). SRPT and EDF require a service_cost/deadline on every WorkItem; PS and WFQ require a declared weight.

8.4 Routing Policies

Static routing · weighted probabilistic routing · congestion-adaptive routing · hash partition routing · broadcast fanout. Congestion-adaptive routing consults live QueueMetrics::saturation_ratio (§11) but only at routing decision points, never by mutating scheduler internals (P10, I8).

11. Core Schema & Types

Every type below is annotated: Own (ownership model), Mut (mutation), Conc (concurrency), Persist (persistence), Ser (serialization), Compat (compatibility class, per §25).

struct SimulationId(u128);

Own: value type, Copy. Mut: immutable after creation. Conc: Send + Sync freely shared. Persist: written to every journal record header. Ser: canonical CBOR (RFC 8949, §5). Compat: STABLE — never renumbered across releases (§25).

struct EventId { epoch: u64, sequence: u64 }

Own: value type, Copy. Mut: immutable. Conc: Send + Sync. Persist: primary sort key in ReplayJournalRecord. Ser: canonical CBOR, lexicographic field order. Compat: STABLE.

trait SimulationClock { fn now(&self) -> SimTime; fn advance_to(&mut self, t: SimTime); }

Own: implemented once per worker shard, not shared. Mut: advance_to is the only mutator (I4). Conc: !Sync by design — one clock per shard, no cross-shard sharing (ADR-19). Persist: SimTime snapshotted at every checkpoint. Ser: SimTime is a u64 nanosecond-equivalent logical tick. Compat: STABLE trait signature.

enum SchedulerPolicy { Fifo, Lifo, Priority, WeightedFair, ProcessorSharing, Srpt, EarliestDeadlineFirst }

Own: Copy enum embedded in QueueNode. Mut: immutable per scenario compile. Conc: Send + Sync. Persist: stored verbatim in scenario snapshots. Ser: canonical CBOR integer tag, never a string (avoids locale/rename hazards). Compat: ADDITIVE-ONLY — new variants may append, none may be removed or renumbered (§25).

struct RuntimeEvent { id: EventId, timestamp: SimTime, kind: EventKind, payload: Arc<EventPayload> }

Own: heap-allocated payload shared via Arc to avoid clone cost on requeue. Mut: immutable after enqueue (I1 depends on this). Conc: Arc<EventPayload> is Send + Sync provided EventPayload variants are. Persist: not itself persisted — only its event_hash in ReplayJournalRecord. Ser: N/A at rest, hashed for replay. Compat: N/A (runtime-only type).

struct QueueNode { node_id: NodeId, scheduler_policy: SchedulerPolicy, service_distribution: ServiceDistribution, queue_capacity: u32, retry_policy: RetryPolicy, routing_policy: RoutingPolicy }

Own: owned by the qts-network topology graph, referenced by NodeId elsewhere. Mut: immutable after scenario compile (§15); capacity changes require a new scenario. Conc: read-only from worker threads after compile, Sync. Persist: serialized into every scenario snapshot. Ser: canonical CBOR. Compat: ADDITIVE fields only (§25).

struct WorkItem { item_id: WorkItemId, creation_time: SimTime, deadline: Option<SimTime>, priority: u8, service_cost: f64, retry_count: u16, trace_context: TraceContext }

Own: owned by the queue it currently occupies; moved (not cloned) on transfer between queues to preserve I1 ordering guarantees. Mut: retry_count increments in place; all other fields immutable. Conc: single-shard-owned, never shared across threads. Persist: written to WAL on state transition (§18). Ser: canonical CBOR. Compat: ADDITIVE.

struct QueueMetrics { queue_depth: u64, enqueue_rate: f64, dequeue_rate: f64, drop_rate: f64, saturation_ratio: f64 }

Own: owned by qts-metrics, read-only view exposed to qts-network routing decisions (P10, I8). Mut: updated only by the metrics aggregation pass. Conc: lock-free snapshot swap (ArcSwap). Persist: periodic snapshot into stats journal. Ser: Arrow IPC (ADR-15). Compat: ADDITIVE.

struct ReplayJournalRecord { logical_time: u64, event_hash: u128, scheduler_state_hash: u128 }

Own: owned by qts-replay's append-only journal writer. Mut: append-only, never mutated in place (I7). Conc: single-writer per shard, Send across the coordinator boundary only in fully-flushed batches. Persist: the WAL record itself. Ser: canonical CBOR, fixed 40-byte encoding. Compat: STABLE — hash algorithm changes bump MAJOR (§25).

struct SeedLineage { root_seed: u64, derivation_path: Vec<u32> }

Own: owned by qts-rng, one instance per simulation entity requiring randomness. Mut: immutable once derived. Conc: Send + Sync, value semantics. Persist: logged at scenario compile time for audit. Ser: canonical CBOR. Compat: STABLE.

struct WalSegment { segment_id: u64, start_offset: u64, checksum: u64 }

Own: owned by qts-storage's segment manager. Mut: checksum finalized on segment seal, immutable thereafter. Conc: single-writer, readable concurrently once sealed. Persist: the on-disk segment header. Ser: fixed binary layout, not CBOR (perf-critical hot path). Compat: STABLE header layout, versioned via magic-number prefix.

struct WorkerLease { worker_id: WorkerId, partition: SeedPartition, expires_at: SimTime }

Own: owned by qts-coordinator's lease table. Mut: expires_at renewed on heartbeat, otherwise immutable (I11). Conc: Mutex-guarded table, single coordinator writer. Persist: not persisted — reconstructable from worker heartbeat log on coordinator failover. Ser: gRPC message (ADR-18). Compat: ADDITIVE.

struct ConvergenceReport { metric: MetricId, confidence_interval: (f64, f64), sample_count: u64, converged: bool }

Own: owned by qts-metrics's convergence detector, one per tracked metric per run. Mut: rebuilt each convergence-check interval, never partially mutated. Conc: Send, produced by the metrics thread, consumed by qts-cli reporting. Persist: written to the experiment's stats journal on completion. Ser: Arrow IPC. Compat: ADDITIVE.

12. Phase 0 — Workspace & Deterministic Foundations

12.1 Objectives

Stand up the Cargo workspace and the correctness kernel every later phase depends on: canonical serialization, deterministic RNG and seed lineage, a monotonic simulation clock, and the canonical error hierarchy. No event scheduling or queueing logic exists yet — this phase's entire scope is "nothing downstream can be non-deterministic." Introduces the crates qts-core, qts-errors, qts-clock, qts-rng.

12.2 Detailed Implementation Steps

Create the Cargo workspace (Cargo.toml, rust-toolchain.toml pinning per ADR-01). qts-core::ids defines SimulationId, EventId (§11) as Copy newtypes. qts-core::canonical implements canonical CBOR encode/decode (RFC 8949's core deterministic encoding mode, §5 RFCs) satisfying P9 — field order is a fixed compile-time schedule, never a HashMap iteration order. qts-errors::hierarchy defines the root QtsError enum with per-crate variant namespaces (ERR_QUEUE_*, ERR_ADMISSION_*, ERR_TOPOLOGY_*). qts-clock::sim_clock implements SimulationClock (§11) enforcing I4 monotonicity with a debug-mode assertion on every advance_to call. qts-rng::seed_lineage implements SeedLineage (§11) derivation: derive(root_seed, path: &[u32]) -> u64 using a splitmix64-style deterministic expansion, satisfying I3 and P12. Add tracing scaffolding (ADR-06) and structured-log schema. Configure CI lint (clippy, forbidding SystemTime::now() outside an explicit allowlist, enforcing P3). Add cargo-fuzz harness bootstrap (ADR-14) with an initial empty target. Add the reproducibility-validation pipeline: two CI runs of the same fixture must byte-compare identical canonical-encoded output.

12.3 Deliverable

A runnable, empty deterministic-core skeleton: cargo test -p qts-core -p qts-errors -p qts-clock -p qts-rng passes; the reproducibility pipeline runs on CI and produces a byte-identical canonical encoding for fixtures/seed/basic.yaml across two independent invocations.

12.4 Acceptance Criteria

Replay hash identical across ≥ 10 repeated CI runs of fixtures/seed/basic.yaml (I3, I5 precursor). Canonical serialization roundtrip stable for 100% of qts-core::ids proptest cases (≥ 10,000 generated cases). Zero SystemTime::now() call sites outside the clippy-lint-approved allowlist (P3 enforcement, CI lint gate, 0 tolerance). Startup of the empty skeleton binary completes in < 3s per §4.

12.5 Conformance Fixtures

fixtures/seed/basic.yaml — canonical seed-lineage derivation smoke test. fixtures/seed/zero_seed.yaml — edge case: root seed of zero must not degrade derivation entropy (regression). fixtures/replay/repro_001.bin — first end-to-end canonical-encode reproducibility fixture, malformed-variant fixtures/scenarios/ malformed_capacity.yaml staged here for the Phase 4 (§16) compiler to consume later.

12.6 Pitfalls

Hidden wall-clock usage: manifests as replay divergence three phases later, root cause a stray Instant::now() in a logging call site; debug by diffing canonical-encoded traces between two runs with identical seeds; signal is a divergence at a timestamp-dependent field only; recovery is the P3 clippy lint plus a targeted fix. Non-canonical serialization drift: manifests as unstable replay hashes across identical inputs; root cause is a HashMap-backed struct field serialized without a sort pass; debugging method is a canonical-roundtrip differential fuzzer; recovery is enforcing canonical field ordering (P9) with a proptest gate.

12.7 Performance Concerns

Allocator churn from per-event Boxing before the arena allocator lands in §13; heap fragmentation risk from unbounded Vec growth in early prototyping; tracing-span overhead (must stay under the 5% CPU budget in §4 even at this early stage); canonical serialization copy overhead from the sort-before-encode step (P9).

12.8 Edge Cases

Zero seeds (fixtures/seed/zero_seed.yaml); SimTime overflow at u64::MAX; invalid UTF-8 in scenario config files; partial WAL writes even though qts-storage does not exist yet — the on-disk format contract (ADR-07) is fixed here so §18 has no rework.

12.9 Failure Analysis

Critical risk: deterministic drift introduced this early propagates silently through every later phase's replay guarantee (I5). Blast radius: any Phase 0 bug invalidates every downstream benchmark and conformance fixture. Containment: the replay validator (built ahead of schedule as a Phase 0 CI gate, even before qts-replay proper exists in §18) hard-fails the build on any canonical-encoding instability.

12.10 Operational Notes

Export at binary startup: build metadata (git revision, toolchain version), the active seed lineage root, and a runtime config hash. Metric: qts_build_info (gauge with revision label). No tracing spans yet — introduced in §13 alongside the first real event dispatch. Rollback: none applicable, this phase has no persisted state.

13. Phase 1 — Event Scheduler Core

13.1 Objectives

Implement the deterministic event scheduler: the correctness-critical subsystem everything else is conditioned on (I1). Introduces the qts-event crate: binary-heap temporal ordering, stable tie-breaking, cancellation, and replay-validatable scheduler snapshots.

13.2 Detailed Implementation Steps

qts-event::heap implements a binary min-heap keyed on (logical_timestamp, EventId.sequence) for I1's stable ordering — the LMAX Disruptor mechanical-sympathy lesson (Thompson et al., 2011, §5) informs contiguous-array heap layout over a node-linked structure to keep sibling comparisons cache-resident (ADR-10). qts-event::cancellation implements tombstone-based cancellation: a cancelled event's slot is marked and skipped on pop rather than removed in place, avoiding an O(n) heap repair. Add deferred (delay-relative) scheduling and periodic timers built atop the same heap rather than a separate timer wheel (rejected alternative analyzed in §34 Alt C, citing Tokio's timer wheel, §5 Reference Implementations). Add scheduler metrics (scheduler_depth, dispatch_rate) satisfying P5. Add starvation diagnostics: a per-node last-dispatched timestamp feeding I6's fairness check in §14. Implement scheduler snapshotting for replay (ReplayJournalRecord.scheduler_state_hash, §11) and a stress-test harness generating adversarial timestamp-collision sequences.

13.3 Deliverable

A standalone scheduler benchmark binary dispatching synthetic events with no queueing logic attached, demonstrating deterministic ordering and measured throughput.

13.4 Acceptance Criteria

≥ 5,000,000 events/sec sustained on reference hardware (§4, §32 C1), p99 dispatch latency < 20µs (§4). Zero heap-ordering violations across 1,000,000 dispatches per CI run (I1). Cancellation storm of 100,000 simultaneous cancellations completes without heap corruption, verified against fixtures/scheduler/cancellation_storm.bin.

13.5 Conformance Fixtures

fixtures/scheduler/basic_ordering.bin — canonical dispatch-order regression. fixtures/scheduler/timestamp_collision.bin — malformed-adjacent case: many events at an identical logical timestamp, exercises the stable tie-break. fixtures/scheduler/ cancellation_storm.bin — mass-cancellation replay case.

13.6 Pitfalls

Timestamp-collision instability: manifests as replay divergence only under specific collision patterns; root cause is a non-stable comparator (e.g. relying on pointer identity); debug via qts-replay's divergence scan once §18 exists, or a differential run against fixtures/scheduler/timestamp_collision.bin before that; signal is divergence localized to collision-timestamp events only; recovery is enforcing the (timestamp, sequence) lexicographic comparator (I1). Heap memory amplification: stale tombstoned events retained past their logical dispatch point; root cause is a missing compaction pass; signal is unbounded heap-size growth under a cancellation-heavy workload; recovery is periodic tombstone compaction triggered at a configurable dead-slot ratio.

13.7 Performance Concerns

Branch prediction cost of the tombstone-skip check on every pop; heap cache locality (array-backed heap keeps sibling nodes within a cache line at realistic fan-out, ADR-10); lock contention is structurally absent — one heap per shard (ADR-19); timer wheel alternatives (§34 Alt C) trade O(1) amortized insertion for a coarser time resolution unsuitable for the < 2µs p50 budget (§4).

13.8 Edge Cases

Maximum timestamp (SimTime::MAX) scheduling attempts must reject cleanly rather than overflow the heap comparator; empty-scheduler dispatch must return a well-defined "idle" signal rather than block; mass cancellation storms (fixtures/scheduler/ cancellation_storm.bin); recursive scheduling (an event handler scheduling another event at the same logical timestamp) must not violate I1's ordering guarantee.

13.9 Failure Analysis

If scheduler ordering corrupts (I1 violation detected), the simulation terminates immediately, emits a scheduler heap dump and the last N dispatched EventIds, and snapshots the pre-corruption heap state for offline replay analysis. Blast radius is contained to the current run — the coordinator (§19) fences the worker and does not propagate corrupted state into aggregate metrics.

13.10 Operational Notes

Metrics: scheduler_depth (gauge), dispatch_rate (counter), cancellation_rate (counter), heap_growth_bytes (gauge). Tracing span: qts.event.dispatch per event, sampled at 1% in production-scale runs to stay under the §4 5% CPU overhead ceiling. Structured-log field: event_id, logical_timestamp on every WARN-or-above log line.

14. Phase 2 — Queue Disciplines & Admission Control

14.1 Objectives

Implement every queue discipline (§8.3) and bounded-resource semantics atop the Phase 1 scheduler. Introduces the qts-queue crate: FIFO, LIFO, Priority, WFQ, Processor Sharing, SRPT, EDF, plus admission control and capacity enforcement (I2, I9).

14.2 Detailed Implementation Steps

qts-queue::disciplines implements each SchedulerPolicy variant (§11) as a distinct dispatch-order function over the same underlying qts-event heap; SRPT and EDF correctness follow directly from Liu & Layland (1973, §5) for EDF and from Harchol-Balter (2013, ch. 3, §5) for SRPT's mean-response-time optimality under preemption. qts-queue::admission enforces queue_capacity (I2) and the global concurrency ceiling (I9) at every enqueue attempt, returning ERR_QUEUE_CAPACITY_ EXCEEDED or ERR_ADMISSION_CEILING (qts-errors, §12). Add drop policies (tail-drop, random-early-detection-style probabilistic drop) and retry semantics bounded by WorkItem.retry_count (§11 WorkItem). Add dead-letter queues for items exceeding retry ceiling. Add fairness metrics: WFQ deviation-from-ideal-share sampler feeding I6 (sampled every 10,000 events per §4). Add queue occupancy histograms (feeding qts-metrics in §17) and queue-level replay validation hooks.

14.3 Deliverable

An operational, interchangeable-discipline queue subsystem: a single QueueNode can be reconfigured across all seven disciplines via scenario config with no code change, demonstrated against fixtures/queues/fifo_basic.yaml and fixtures/queues/ srpt_latency.yaml.

14.4 Acceptance Criteria

Queue capacity enforcement is deterministic — zero over-capacity admissions across 1,000,000 enqueue attempts under adversarial burst load (I2). WFQ fairness error stays < 0.5% against fixtures/queues/priority_starvation.yaml (§4, I6). Starvation detection fires within 10,000 events of an adversarial low-priority-lockout pattern.

14.5 Conformance Fixtures

fixtures/queues/fifo_basic.yaml — baseline FIFO ordering regression. fixtures/ queues/srpt_latency.yaml — SRPT mean-response-time validation against the Harchol-Balter closed-form bound. fixtures/queues/priority_starvation.yaml — adversarial starvation-pattern regression exercising I6.

14.6 Pitfalls

Priority inversion: manifests as latency collapse for low-priority items behind a sustained high-priority stream; root cause is a naive strict-priority discipline with no fairness floor; debug via the starvation diagnostic counter from §13; recovery is switching to WFQ or adding an aging boost. Fairness drift under WFQ: manifests as starvation despite a nominally fair discipline; root cause is weight normalization drift after dynamic node reconfiguration; signal is scheduler_fairness_error exceeding 0.5% (I6); recovery is re-normalizing weights on every topology mutation.

14.7 Performance Concerns

Linked-list-backed queue implementations lose cache locality versus array-backed ring buffers at high enqueue/dequeue rates; priority-heap amplification when priority levels are added on top of the temporal heap (two comparator dimensions); queue contention is structurally absent per-shard (ADR-19) but cross-shard routing (§15) reintroduces it at node boundaries.

14.8 Edge Cases

Queue size at exactly the capacity ceiling (off-by-one is the classic bug here, I2); infinite retry loops without a dead-letter escape valve; retry storms synchronized across many items after a transient upstream failure; deadline expiration for EDF items already dispatched but not yet completed (must not double-count in occupancy metrics).

14.9 Failure Analysis

Queue-invariant corruption (I2 or I9 violation) requires an immediate runtime halt, a full queue-state dump, and replay-journal extraction from the last valid checkpoint (§18). Blast radius is bounded to the affected QueueNode and its immediate downstream routing targets (§15) — the coordinator does not need to fence unrelated shards.

14.10 Operational Notes

Dashboards: queue depth per node, enqueue latency percentiles, service latency percentiles, fairness deviation over time. Metrics: queue_depth, queue_drop_total, admission_over_ceiling_total (I2, I9 telemetry from §7). Tracing span: qts.queue.admit per admission decision.

15. Phase 3 — Queueing Network & Routing Engine

15.1 Objectives

Build networked queue topologies: multi-node graphs, routing policies (§8.4), open and closed queueing networks, and cycle/deadlock detection. Introduces the qts-network crate atop Phase 2's qts-queue nodes.

15.2 Detailed Implementation Steps

qts-network::topology builds the node dependency graph from the compiled scenario (§16) and validates it against Jackson-network product-form assumptions (Kleinrock, 1975 ch. 4–5, §5) where applicable — open networks need not satisfy product-form, but closed networks are checked against the mean-value-analysis consistency bound as a sanity check on service-time parameters. qts-network::routing implements static, weighted-probabilistic, congestion-adaptive, hash-partition, and broadcast-fanout routing (§8.4); congestion-adaptive routing reads QueueMetrics.saturation_ratio (§11) through the read-only P10-isolated view only. Add cyclic-network detection at compile time (I12) via a topological-sort pass over the declared routing graph, and a runtime re-check on any dynamic topology mutation. Add deadlock detection: a bounded-wait-graph cycle check distinct from routing-cycle detection — a routing cycle is a graph-structure property, a deadlock is a resource-wait property, both checked independently. Add deterministic fanout ordering (broadcast fanout must dispatch to targets in a canonical, seed-independent order to preserve I1 downstream).

15.3 Deliverable

A runnable multi-node queueing-network simulator executing an open network (fixtures/network/jackson_network.yaml) and a closed network end to end, with bottleneck-node identification.

15.4 Acceptance Criteria

Zero undetected routing cycles across the full fixtures/network/routing_cycle.yaml adversarial corpus (I12, 100% detection rate required). Broadcast fanout dispatch order is byte-identical across 100 replay runs of fixtures/network/broadcast_fanout.yaml (I1, I5). Bottleneck-node identification matches the analytically-derived bottleneck for the Jackson-network fixture within 1% of the theoretical utilization.

15.5 Conformance Fixtures

fixtures/network/jackson_network.yaml — open Jackson network with a known analytical solution for cross-validation. fixtures/network/routing_cycle.yaml — malformed topology corpus exercising I12 cycle detection. fixtures/network/broadcast_fanout.yaml — deterministic fanout-order regression.

15.6 Pitfalls

Routing loops: manifests as unbounded event generation and eventual queue-capacity exhaustion; root cause is a missing or incomplete I12 compile-time check; debug via the dependency-graph exporter; recovery is rejecting the scenario compile with ERR_TOPOLOGY_CYCLE. Cyclic retry amplification: distinct from a structural routing loop — a legitimate acyclic topology can still exhibit retry-storm amplification when retry_policy re-injects work faster than downstream drains it; root cause is unbounded retry without backoff; recovery is bounding retry_count (§14) plus exponential backoff. Deadlock misclassification: a transient queue-full backpressure condition can look like a deadlock to a naive detector; root cause is not distinguishing "waiting" from "permanently blocked"; recovery is a bounded-wait-time threshold before declaring deadlock.

15.7 Performance Concerns

Graph traversal cost for cycle detection scales with node count — amortized by caching the topological order and only re-checking on mutation; fanout amplification (a single broadcast event generates N downstream events, each consuming scheduler capacity per §4); cache misses from pointer-chasing the dependency graph — mitigated by a contiguous adjacency-list layout (§32 arithmetic informs the array-vs-pointer choice).

15.8 Edge Cases

Disconnected nodes (unreachable from any ingress — must be flagged at compile time, not silently dropped); zero-capacity links (a routing edge to a node with queue_capacity: 0 — must be rejected at compile, not discovered at runtime); infinite cycles beyond the bounded traversal budget must terminate the detector with a clear "cycle depth exceeded" diagnostic rather than hang.

15.9 Failure Analysis

Topology corruption (a runtime-discovered inconsistency between the compiled graph and live routing state) triggers a graph-serialization dump, execution freeze (not silent continuation, per P11), and a diagnostic snapshot for offline replay. Blast radius is the entire network for a single simulation run, but does not cross simulation boundaries within the same worker (§19).

15.10 Operational Notes

Expose bottleneck-node identification, saturation-propagation traces, and a queue dependency heatmap through qts-observability (§20). Metric: routing_cycle_detected_ total (I12 telemetry). Tracing span: qts.network.route per routing decision.

16. Phase 4 — Scenario DSL & Compiler

16.1 Objectives

Implement the declarative scenario DSL (§8.5) and its deterministic compiler: validation, schema normalization, and workload expansion into a canonical execution plan consumed by Phases 1–3. Introduces the qts-scenarios crate.

16.2 Detailed Implementation Steps

qts-scenarios::dsl parses YAML (ADR-11) into an AST validated against schema/scenario.schema.json (JSON Schema draft 2020-12, §5 RFCs). qts-scenarios:: compiler performs: topology-reachability validation (feeding I12's compile-time check in §15), resource-reference resolution (every routing_policy target must name a declared node), probability-distribution parameter validation (exponential lambda > 0, etc.), and canonicalization of unordered YAML map keys before any hashing occurs (P9). The compiler is itself deterministic — two compiles of byte-identical input must produce byte-identical canonical output, checked by the same reproducibility pipeline introduced in §12. Add workload expansion: a scenario may declare a parameterized sweep (e.g. lambda values [800, 1200, 1600]) which the compiler expands into N independent execution plans sharing a SeedLineage root but distinct derivation paths (§11 SeedLineage, I3).

16.3 Deliverable

A qts scenario compile CLI subcommand that accepts a YAML scenario and emits a canonical execution plan or a structured validation error, demonstrated against fixtures/scenarios/valid_mm1.yaml and rejecting fixtures/scenarios/ malformed_capacity.yaml with ERR_QUEUE_CAPACITY_NEGATIVE.

16.4 Acceptance Criteria

100% of the 12 malformed fixtures in fixtures/scenarios/ and fixtures/network/ routing_cycle.yaml are rejected with the correct named error code (no false accepts). Compile time for a 10,000-node topology stays under the 3s startup budget (§4). Two independent compiles of fixtures/scenarios/valid_mm1.yaml produce byte-identical canonical plans (P9, 0 tolerance).

16.5 Conformance Fixtures

fixtures/scenarios/malformed_capacity.yaml — negative-capacity rejection case (§8.5). fixtures/scenarios/valid_mm1.yaml — canonical M/M/1 baseline for cross-validation against Kleinrock's closed-form utilization formula. fixtures/scenarios/ schema_drift.yaml — a scenario written against an older schema minor version, exercising the P7 backward-compatibility contract.

16.6 Pitfalls

Silent schema drift: an older scenario file with a since-renamed field is silently ignored rather than rejected; root cause is missing #[serde(deny_unknown_fields)]- equivalent strictness; debug by diffing the compiled plan's field set against the schema's required-field set; recovery is strict-mode parsing plus the fixtures/ scenarios/schema_drift.yaml regression. Non-canonical map ordering: manifests as compile-time output instability across restarts (not runs — restarts, because HashMap seed randomization differs per process); root cause is serializing an unordered map without a sort pass; recovery is P9's canonical field ordering enforced at the compiler boundary, not just at qts-core.

16.7 Performance Concerns

Schema validation cost scales with topology size — validated once at compile time, not re-validated per event, so the 3s startup budget (§4) fully amortizes it; YAML parsing allocation overhead for very large topologies (10,000+ nodes) is bounded by streaming the parse rather than materializing the full document tree at once where the parser library allows it.

16.8 Edge Cases

Empty topology (zero nodes) must compile to a well-defined no-op plan, not an error; duplicate node IDs must be rejected at compile, not silently overwritten; a workload sweep with zero valid parameter combinations must fail compile with a clear diagnostic; extremely deep parameter sweeps (> 10,000 expansions) must respect the same 3s compile budget or fail fast with a size-limit error.

16.9 Failure Analysis

A compiler bug that silently accepts an invalid scenario propagates its blast radius into every downstream phase's execution — this is why the compiler's own conformance corpus (§16.5) is run on every CI merge, not just at release time. Detection is via the malformed-fixture-rejection acceptance criterion (§16.4); recovery is a compiler patch plus a new regression fixture for the specific miss.

16.10 Operational Notes

Metric: scenario_compile_duration_seconds (histogram), scenario_compile_rejected_ total (counter, labeled by error code). CLI exit codes are stable across MINOR versions (P7). Structured-log field: scenario_hash on every compile-related log line for correlation with the eventual replay journal (§18).

17. Phase 5 — Statistical Engine & Convergence Analysis

17.1 Objectives

Implement the statistical-correctness subsystem: histogram aggregation, confidence intervals, Monte Carlo convergence detection, and heavy-tail diagnostics. Extends qts-metrics (bootstrapped in §12's observability scaffolding) with histogram.rs and convergence.rs.

17.2 Detailed Implementation Steps

qts-metrics::histogram integrates HDRHistogram (ADR-08) for latency and occupancy distributions with bounded memory per P8. qts-metrics::convergence implements warm-up-window exclusion (Jain, 1991 ch. 12–13, §5) — discarding the initial transient before any statistic is trusted — and confidence-interval estimation via batch-means (Jain ch. 13). Monte Carlo orchestration runs N independent seeded replicas (SeedLineage derivation paths, I3) and aggregates via ConvergenceReport (§11) once the batch-means confidence interval half-width drops below a configurable relative-precision threshold. Add variance tracking and outlier detection (modified z-score on batch means) and heavy-tailed-workload diagnostics validating against Harchol-Balter's SRPT/heavy-tail analysis (2013 ch. 4–5, §5). Add distribution exporters (Arrow IPC per ADR-15) and a drift analyzer comparing successive ConvergenceReports across scenario-config changes to flag unexpected shifts. All statistics computation reads runtime state through the P10-isolated view only (I8).

17.3 Deliverable

A statistically rigorous experiment engine: qts scenario run --replicas 30 produces a ConvergenceReport per tracked metric with a reproducible confidence interval, demonstrated against fixtures/stats/convergence.yaml.

17.4 Acceptance Criteria

Confidence intervals reproducible to within floating-point equality across two identical-seed-lineage runs (I3, I5). Histogram merge correctness validated against fixtures/stats/heavy_tail.bin with < 50ms merge latency for 256 worker histograms (§4). Warm-up exclusion window removes ≥ 95% of transient bias measured against the analytically-known M/M/1 steady state in fixtures/scenarios/valid_mm1.yaml.

17.5 Conformance Fixtures

fixtures/stats/heavy_tail.bin — Pareto-distributed service-time regression exercising histogram tail-bucket precision. fixtures/stats/warmup.yaml — known-transient-length scenario for warm-up-window validation. fixtures/stats/convergence.yaml — a 30-replica Monte Carlo campaign with a known analytical confidence interval.

17.6 Pitfalls

Warm-up bias: manifests as systematically biased confidence intervals that never resolve even with more replicas; root cause is a warm-up window shorter than the system's actual transient length; debug via the drift analyzer comparing early-batch versus late-batch means; recovery is extending the exclusion window and re-validating against fixtures/stats/warmup.yaml. Histogram precision loss: manifests as p99.9-and-above percentiles reading as flat/quantized; root cause is HDRHistogram bucket-count too coarse for the observed dynamic range; recovery is widening the significant-digits configuration (ADR-08) at the cost of memory (P8 tradeoff). Percentile drift across merges: manifests as a merged histogram's percentile estimate diverging from the arithmetic truth; root cause is a non-associative merge implementation; recovery is enforcing I13's associativity property test.

17.7 Performance Concerns

Histogram merge CPU overhead scales with worker count × bucket count (§32 C4 budgets this against the < 50ms target); memory amplification from per-metric per-replica histogram retention until convergence — bounded by discarding pre-warm-up histograms immediately rather than retaining and post-filtering.

17.8 Edge Cases

Sparse datasets (a rarely-hit code path yielding too few samples for a meaningful confidence interval — must report "insufficient data" rather than a spurious tight interval); infinite-variance distributions (a misconfigured heavy-tail parameter with no finite mean — must be detected and flagged, not silently averaged); outlier explosions from a single pathological replica must not dominate the batch-means estimate (modified z-score capping).

17.9 Failure Analysis

Invalid statistical convergence (a ConvergenceReport.converged = true that does not actually satisfy the batch-means precision threshold — a bug, not a data property) invalidates the entire experiment's output and must be caught by a self-check recomputing the interval independently before the report is finalized. Detection: the self-check assertion; blast radius: the single experiment's conclusions, not the runtime's correctness invariants (I1–I13 remain unaffected).

17.10 Operational Notes

Export confidence-interval width over replica count (a convergence curve), percentile stability across successive batches, and variance progression. Metric: convergence_ batch_count, histogram_merge_duration_seconds. Structured-log field: metric_id, sample_count on every convergence-check log line.

18. Phase 6 — Persistence and Replay

18.1 Objectives

Implement crash-only recovery (P4) and bit-identical deterministic replay (I5, P6). Introduces qts-storage (WAL, snapshotting) and qts-replay (journal, divergence detection).

18.2 Detailed Implementation Steps

qts-storage::wal implements append-only segment writing (Kreps, Narkhede, Rao, 2011 Kafka design paper, §5) with 128 MB segment rotation and checksummed frames (ADR-07, §4 WAL amplification < 1.5x). qts-storage::snapshot implements incremental Arrow-IPC snapshotting (ADR-15) paired with the WAL offset at capture time (I10). qts-replay:: journal writes ReplayJournalRecord (§11) entries preserving append order (I7) and computes the running scheduler_state_hash. qts-replay::divergence implements the canonical-vs-replay hash-chain comparator (I5) — any mismatch triggers immediate abort per P11 and emits a forensic bundle (the divergent record range plus surrounding context). Add recovery bootstrap: on restart, load the latest consistent snapshot, then replay WAL entries from its paired offset forward (I10). Add corruption detection via per-segment checksum verification on load, checkpoint compression, and a crash-simulation harness that truncates WAL segments mid-write to validate the P4 crash-only recovery path under realistic torn-write conditions.

18.3 Deliverable

A crash-recoverable deterministic runtime: killing the process mid-run and restarting against the persisted WAL/snapshot pair reproduces the exact pre-crash state and resumes with zero replay divergence.

18.4 Acceptance Criteria

Replay equivalence preserved across 100% of fixtures/replay/repro_001.bin, fixtures/replay/divergence.bin (negative control — must detect the injected divergence), and fixtures/replay/crash_mid_flush.bin runs. Recovery completes in < 30s (§4 worker crash recovery budget, §32 C9). Segment corruption is detected within one segment-read pass, 0 false negatives against fixtures/replay_segments/ corrupt_segment.bin.

18.5 Conformance Fixtures

fixtures/replay/divergence.bin — a deliberately corrupted journal exercising the I5 hash-mismatch detector (negative control). fixtures/replay/crash_mid_flush.bin — a torn-write simulation for the P4 crash-only recovery path. fixtures/replay_segments/ corrupt_segment.bin — checksum-mismatch regression for segment quarantine.

18.6 Pitfalls

Partial segment flush: manifests as a WAL segment readable up to an arbitrary byte offset then garbage; root cause is a crash between the write syscall and fsync; debug via the crash-simulation harness; recovery is truncating to the last verified checksum boundary on load, never trusting an unflushed tail. Snapshot drift: manifests as a recovered state that replays cleanly but diverges from pre-crash state; root cause is a snapshot taken at a WAL offset that does not actually correspond to a consistent state (I10 violation); recovery is enforcing the offset-consistency check at snapshot-write time, not just at load time. WAL ordering corruption: manifests as I7 violation, detected as a non-monotonic segment sequence on recovery; recovery is segment quarantine plus replay from the last known-good checkpoint.

18.7 Performance Concerns

fsync overhead dominates WAL write latency — batched fsync at a bounded flush interval trades a small durability window for throughput, sized against the § 4 graceful shutdown flush time budget (< 10s for 500 MB); compression CPU cost for snapshot checkpoints must stay inside the §4 snapshot overhead budget (< 8% runtime); IO amplification from checksummed frames is the § 4-quantified 1.5x WAL amplification ceiling (§32 C3).

18.8 Edge Cases

Torn writes (partial segment flush, §18.6); missing checkpoints (a snapshot reference in metadata pointing at a since-pruned snapshot file — must fail recovery cleanly, not silently skip to an older one without operator visibility); replay gaps (a WAL segment missing from an otherwise-contiguous sequence — I7 violation, must halt rather than skip past the gap).

18.9 Failure Analysis

Corruption workflow: quarantine the affected segment immediately (no further writes to it), emit a forensic bundle (segment header, surrounding valid segments, the computed checksum mismatch), and stop replay rather than attempting a best-effort partial recovery (P11). Blast radius is bounded to the affected experiment's timeline from the corruption point forward — prior checkpoints remain valid recovery targets.

18.10 Operational Notes

Operators require: a WAL inspection tool (tools/wal_inspect.rs), a replay-diff tool (tools/replay_diff.rs) for comparing canonical vs. replay journals, and snapshot- lineage visibility in qts-observability dashboards (§20). Metrics: wal_flush_ latency_seconds, snapshot_duration_seconds, replay_divergence_total (I5 telemetry).

19. Phase 7 — Distributed Experiment Orchestration

19.1 Objectives

Implement multi-worker experiment coordination: worker registration, lease management, failure detection, and duplicate-free work partitioning. Introduces the qts-coordinator crate.

19.2 Detailed Implementation Steps

qts-coordinator::rpc implements the coordinator-worker protocol over gRPC (ADR-18). qts-coordinator::lease implements WorkerLease (§11) issuance and renewal, enforcing I11 (no two workers hold an overlapping seed-partition lease). Work partitioning divides a Monte Carlo campaign's replica set by SeedLineage derivation path (I3) across registered workers, following the MapReduce partitioning model (Dean & Ghemawat, 2004, §5) adapted for stateless, replay-independent shards rather than key-based reduce grouping. Add failure detection via heartbeat timeout (10s lease window per §4 worker-crash-recovery derivation, §32 C9) and automatic reassignment on lease expiry. Add distributed metrics aggregation (merging per-worker ConvergenceReports, §17, via I13's associative-merge property) and distributed tracing correlation (trace_context propagation, Dapper model, Sigelman et al. 2010, §5). Add Kubernetes manifests and resource quotas for the batch-execution deployment mode (§1 deployment mode 4).

19.3 Deliverable

A distributed experiment runner: a 256-replica Monte Carlo campaign (§4 max concurrent simulations/node) distributed across N workers with automatic reassignment on injected worker failure, demonstrated against fixtures/distributed/worker_loss.yaml.

19.4 Acceptance Criteria

Worker crash recovery completes in < 30s (§4, §32 C9), validated against fixtures/ distributed/worker_loss.yaml. Zero duplicate-execution incidents across 1,000 injected lease-expiry events (I11, 0 tolerance). Distributed aggregation produces a ConvergenceReport byte-identical to the single-node equivalent for the same seed set (I5 extended to the distributed case).

19.5 Conformance Fixtures

fixtures/distributed/worker_loss.yaml — mid-campaign worker-crash injection exercising lease reassignment. fixtures/distributed/reassignment.yaml — lease-expiry race regression for I11. fixtures/distributed/split_brain.yaml — dual-coordinator partition scenario exercising fencing.

19.6 Pitfalls

Duplicate work execution: manifests as an aggregate metric double-counting a replica; root cause is a lease granted to a second worker before the first worker's lease expiry is fully propagated; debug via the lease-grant audit log; recovery is strengthening I11's uniqueness check to a fencing token rather than a bare timestamp comparison. Lease-expiry races: manifests intermittently under high heartbeat-latency variance; root cause is a heartbeat renewal arriving just after expiry is declared; recovery is a renewal grace window sized against the §4 network RTT assumption (0.5–5ms intra-cluster). Aggregation drift: manifests as a distributed ConvergenceReport differing from an equivalent single-node run; root cause is a non-associative merge order dependency (I13 violation); recovery is enforcing the merge-order-independence property test from §17.

19.7 Performance Concerns

Network fanout cost scales with worker count for both lease heartbeats and metrics aggregation; coordinator bottleneck risk at high worker counts — mitigated by hierarchical aggregation (workers report to regional aggregators before the coordinator, deferred per PhaseDeferred("§19") full hierarchy, tracked in §35); serialization pressure from per-heartbeat gRPC message overhead at the §4 RTT assumption.

19.8 Edge Cases

Split-brain coordinators (fixtures/distributed/split_brain.yaml) must resolve via fencing, never via last-write-wins on ambiguous state; slow workers approaching but not exceeding the lease timeout must not be prematurely reassigned (a grace-window tradeoff against I11 strictness); partial metrics uploads (a worker crash mid-upload) must not corrupt the aggregate — partial uploads are discarded, not partially merged.

19.9 Failure Analysis

Coordinator failure handling: standby failover per the §4 99.9% availability budget, worker fencing on any ambiguous lease state, and lease invalidation on coordinator restart (all leases are re-derived from the durable lease log, never trusted from in-memory state alone). Blast radius of a coordinator crash is bounded to a pause in new lease issuance — in-flight worker execution continues independently until its current lease expires.

19.10 Operational Notes

Dashboards: worker saturation, retry counts, lease churn rate. Metrics: duplicate_ lease_total (I11 telemetry), worker_reassignment_total, lease_renewal_latency_ seconds. Kubernetes readiness/liveness probes gate coordinator promotion during canary rollout (§24).

20.5 Conformance Fixtures

fixtures/telemetry/span_integrity.bin — end-to-end trace-completeness regression. fixtures/telemetry/metrics_schema.json — Prometheus exposition-format schema conformance. fixtures/telemetry/exporter_outage.yaml — exporter-unavailability injection exercising graceful degradation.

20.6 Pitfalls

Metrics cardinality explosion: manifests as Prometheus scrape latency degradation or OOM in the metrics pipeline; root cause is an unbounded label (e.g. per-WorkItemId labeling instead of per-NodeId); debug via cardinality auditing on the exposition endpoint; recovery is enforcing a label-cardinality lint in CI. Trace-sampling bias: manifests as dashboards under-representing tail-latency events because uniform sampling drops rare slow spans disproportionately; recovery is tail-based sampling (retain spans exceeding a latency threshold at 100%, sample the rest at 1%). Logging amplification: manifests as log-volume growth outpacing the 5% CPU overhead budget under error storms; recovery is rate-limited structured logging with a summarized "N similar events suppressed" marker.

20.7 Performance Concerns

20.8 Edge Cases

20.9 Failure Analysis

Observability failure must never compromise simulation correctness (I8 is the architectural guarantee here) — an exporter crash, a full metrics buffer, or a malformed trace context all degrade visibility, never correctness. Detection is via the exporter's own health endpoint; blast radius is confined to the observability plane; recovery is exporter restart with no simulation-side rollback needed.

20.10 Operational Notes

Provide Grafana dashboards (queue depth, tail latency, worker saturation), Prometheus alert rules (correctness-threat-gated per P5), and incident runbooks (docs/runbooks/ replay.md, docs/runbooks/worker-recovery.md). Metric: metrics_export_duration_ seconds, trace_span_orphaned_total.

24. Operational Readiness

Metrics strategy. Mandatory baseline metrics across every deployment mode (§1): queue depth per node, scheduler dispatch latency percentiles, replay-divergence count (I5), WAL flush latency, snapshot duration, WFQ fairness deviation (I6), and worker saturation (§19). Every metric name is stable across MINOR versions (P7).

Alerting philosophy. Alert only on correctness threats and operator-actionable conditions, never on cosmetic thresholds (P5): replay divergence (any occurrence), queue-collapse/saturation beyond 95% sustained for > 60s, corruption indicators (any checksum mismatch), and sustained latency regression beyond the §28 M-series targets for > 5 minutes. This avoids the alert-fatigue failure mode documented in FM-5.

Deployment strategy. Canary worker rollout: new worker images serve ≤ 10% of a Monte Carlo campaign's replica set before full promotion. Replay validation gates promotion — a canary worker's output must replay-match a reference run before receiving additional traffic. Container images are immutable and content-addressed (ADR-12, ADR-22); no in-place mutation of a running worker's binary is ever permitted (P4 crash-only philosophy extended to deployment).

Runbook coverage. docs/runbooks/replay.md covers divergence triage (FM-1); docs/runbooks/worker-recovery.md covers lease-expiry and reassignment procedures (FM-6, FM-7). Both runbooks are exercised in the Phase 9 (§21) conformance suite via chaos-injection fixtures, not left as untested prose.

Readiness gates before production use. All §7 invariants (I1–I13) covered by a proptest in qts-testkit (§21); all §22 threats (T1–T12) have a corresponding mitigation implemented and tested; the 72h soak-test fixture (§4 max experiment duration) has run clean at least once per release candidate.

25. Compatibility & Versioning

Wire compatibility. MINOR versions of the coordinator↔worker RPC protocol (ADR-18) must remain backward-compatible: new gRPC message fields are additive only (P7); no field is ever renumbered or repurposed. A worker on version N.(M-1) can register with a coordinator on version N.M, but not vice versa.

Storage compatibility. Snapshots (Arrow IPC, ADR-15) and WAL segments (ADR-07) remain readable for two MAJOR versions per P7. Each Arrow-IPC snapshot carries a schema-version tag in its metadata block, validated against qts-storage's compatibility table on load — this is the T12 enforcement point. WAL segments carry their own magic-number version prefix in the §11 WalSegment header, checked independently on segment read as the T11 (§22) tamper/corruption enforcement point.

Semantic versioning. MAJOR: incompatible replay-hash algorithm or storage-format changes (breaks I5 across versions by design, requires explicit migration). MINOR: additive scenario-DSL fields, additive SchedulerPolicy/EventKind enum variants (never removals). PATCH: bug fixes with no observable behavior change to a correctly-specified scenario.

Scenario DSL compatibility. fixtures/scenarios/schema_drift.yaml (§16.5) is the standing regression for reading an older-schema scenario under a newer compiler; unknown fields are rejected in strict mode (§16.6), but historically-valid fields are never silently reinterpreted.

Deprecation policy. A deprecated field or subcommand is retained for one full MAJOR version cycle with a structured-log WARN on use, then removed only at the next MAJOR bump alongside a CHANGELOG.md entry and a fixtures/conformance/regression_v1_v2.bin update (§21.5).

26. Testing & Verification Strategy

Unit testing. Every discipline in qts-queue (§14), every routing policy in qts-network (§15), and every qts-clock/qts-rng primitive (§12) carry direct unit coverage against their documented invariant.

Integration testing. Cross-module execution flows: scenario compile → runtime instantiation → event dispatch → metrics aggregation → replay validation, exercised end to end for each of the ten phases' representative fixtures.

Property testing. One proptest strategy per invariant I1–I13 (§7), implemented in qts-testkit::property (§21.2) — this is the deterministic-simulator debugging methodology referenced at the close of §7: replay-reproducible on any property failure, never a flaky non-reproducible assertion.

Fuzzing. Three continuous cargo-fuzz targets (ADR-14): fuzz_scheduler (I1 under adversarial timestamp sequences), fuzz_scenario_parser (§16 compiler robustness), fuzz_replay (I5 divergence-detector robustness). Corpus seeded from fixtures/conformance/fuzz_corpus_seed.bin (§21.5).

Chaos testing. Worker crashes (fixtures/distributed/worker_loss.yaml, §19.5), segment corruption (fixtures/replay_segments/corrupt_segment.bin, §18.5), and network partition simulation (fixtures/distributed/split_brain.yaml, §19.5) run in a dedicated chaos CI lane distinct from the fast unit/integration lane.

Deterministic replay as a universal test oracle. Every integration test asserts replay equivalence (I5) as a side effect of running at all — this is not an optional extra check, it is structurally how QTS tests are written: run once canonically, run once via qts-replay, hash-compare.

27. Build & Release Engineering

Reproducible builds. Pinned toolchain (rust-toolchain.toml, ADR-01), a committed Cargo.lock (ADR-03), and deterministic archive creation (stripped timestamps, sorted tar entries) so that two independent builds from the same commit produce byte-identical release artifacts — a build-level analog of P1's runtime determinism principle.

Artifact signing. Cosign (ADR-22) signs every release container image and CLI binary; signature verification is mandatory before any Kubernetes deployment (§24 deployment strategy) and enforced client-side in qts-cli's self-update path.

SBOM generation. Syft generates SPDX and CycloneDX SBOMs (ADR-22) attached to every release artifact, feeding the T5 supply-chain mitigation.

Release channels. nightly (built from main, no compatibility guarantee, for active-development testing only), stable (tagged MINOR/PATCH releases, full P7 compatibility guarantee), LTS (a subset of stable releases receiving PATCH-only backports for 12 months, chosen for long-running research deployments per §1 deployment mode 5).

CI/CD pipeline (ADR-16). ci.yml runs unit + integration + property tests on every PR; fuzz.yml runs the three fuzz targets nightly plus a mandatory 24h pre-release run (§21.4); benchmark.yml runs the Criterion suite (ADR-13) and fails on a regression beyond the §28 M-series target tolerance; release.yml gates on a clean conformance suite (§21) and a valid Cosign signature.

28. Performance Engineering

Benchmarking strategy. Criterion-based (ADR-13) benchmarks for scheduler throughput, queue latency, snapshot performance, and replay throughput (benchmarks/scheduler_throughput.rs, queue_latency.rs, snapshot_performance.rs, replay_throughput.rs, §10). Every benchmark asserts against a target in the table below, not just reports a number — a regression beyond tolerance fails CI (§27).

Profiling workflow. perf for CPU sampling, cargo flamegraph for call-graph visualization (Gregg, 2020, §5), tokio-console for async-task-level introspection of the qts-coordinator RPC path (§19), heaptrack for allocation-hotspot analysis.

Tail-latency analysis. p50/p95/p99/p99.9 tracked for every latency-bearing operation (The Tail at Scale, Dean & Barroso 2013, §5) — event dispatch (§13), queue admission (§14), and end-to-end request completion. 29. Scalability Analysis

Primary bottlenecks. Scheduler-heap contention does not exist cross-thread by construction (ADR-19, one heap per shard) but does bound single-shard throughput at the §4 5M ev/s ceiling; histogram aggregation cost scales with worker count × bucket count (§32 C4); WAL fsync pressure scales with write-amplification (§4, ADR-07); routing fanout amplification scales with broadcast-policy usage (§15.7).

Horizontal scaling. Monte Carlo workloads scale near-linearly across workers because replicas are independent by construction (I3 seed-partition isolation) — the qts-coordinator (§19) is the only shared-state bottleneck, mitigated by the hierarchical-aggregation deferral (PhaseDeferred("§19"), §35) once worker counts exceed the single-coordinator fanout budget.

Vertical scaling. NUMA-aware shard placement (§4 dual-socket assumption) becomes necessary beyond 64 cores on a single node — cross-socket QPI latency (~90ns) must be modeled as network-adjacent rather than local once shard count exceeds what a single socket's L3 cache can serve without cross-socket traffic dominating dispatch latency (M1/M2 regression risk).

Storage scaling. WAL and snapshot storage grow linearly with experiment duration (§4 max 72h) and entity churn (§4 max 50M cumulative entities); object-store delegation (§1 delegates) is the scaling answer beyond local-disk capacity, not a qts-storage responsibility.

Pluggable storage backend. qts-storage's backend trait (referenced in §1 delegates) allows swapping the local-filesystem WAL implementation for an object-store-backed one without touching qts-replay or any invariant in §7 — the trait boundary is exactly the persistence boundary drawn in §3's architecture diagram.

30. Mental Models & First Principles

  • MM1 — The Observer Must Not Move the Needle. Compressed insight: any metrics or tracing path that can influence scheduling decisions has silently become part of the system under test · Predicts: heisenbug-class failures that vanish under instrumentation · Bug class without it: "it only reproduces without the profiler attached" · applies in §17, §20.
  • MM2 — Determinism Is a Closed-World Property. Compressed insight: a system is deterministic only if every input to every decision is accounted for, including ambient ones (wall clock, hash-map iteration order, thread scheduling) · Predicts: one un-audited entropy source eventually causes a replay divergence · Bug class without it: intermittent, unreproducible CI failures · applies in §12, §13.
  • MM3 — Backpressure Must Be Visible at Every Hop, Not Just the Edge. Compressed insight: a bounded queue at ingress with unbounded queues downstream just moves the collapse point, it does not remove it · Predicts: where in a pipeline a load spike will actually manifest as latency · Bug class without it: mysterious mid-pipeline queue growth despite a "protected" front door · applies in §14, §15.
  • MM4 — A Fair Scheduler Under Typical Load Can Still Starve Under Adversarial Load. Compressed insight: fairness must be proven against worst-case arrival patterns, not validated against typical traces · Predicts: a scheduler that passes every normal benchmark can still starve a class of work under a crafted pattern · Bug class without it: production starvation incidents with no matching pre-release test · applies in §14.
  • MM5 — Replay Equivalence Is the Only Trustworthy Debugging Oracle Here. Compressed insight: in a deterministic simulator, "it worked when I re-ran it" is not evidence of anything — either replay matches bit-for-bit or the bug is still present and merely unobserved · Predicts: any debugging approach relying on re-running under load will waste time · Bug class without it: chasing a bug that "goes away" under a debugger · applies in §18, §26.
  • MM6 — Every Distributed Aggregation Must Be Associative and Commutative. Compressed insight: if merge order can ever matter, a network delay or a coordinator restart will eventually expose it · Predicts: distributed aggregation bugs that correlate with network jitter, not with load · Bug class without it: aggregate metrics that differ from a single-node equivalent run for no apparent reason · applies in §17, §19.
  • MM7 — A Structural Cycle and a Resource Deadlock Are Different Bugs With Different Detectors. Compressed insight: conflating "the graph has a cycle" with "execution is permanently blocked" produces both false positives and false negatives · Predicts: a deadlock detector built as a cycle detector will misfire on legitimate backpressure · Bug class without it: false-positive deadlock alarms during normal saturation · applies in §15.
  • MM8 — Capacity Numbers Without Arithmetic Are Just Opinions. Compressed insight: every constraint in §4 must be derivable from a smaller set of physical facts (cache line size, syscall cost, network RTT), not asserted from intuition · Predicts: which constraints will actually hold up under a real workload versus which were guesses · Bug class without it: capacity-planning decisions built on numbers nobody can defend · applies in §4, §32.

32. Back-of-Envelope Capacity Model

  • C1 — Event Throughput Ceiling. 1 / 180ns per dispatch ≈ 5.55M ops/s × 0.9 cache-miss derate = 5.0M ev/s, matching the §4 budget exactly.
  • C2 — Steady-State Working Set. 1,000,000 in-flight WorkItems × 96 B/item = 96 MB, × 4x queue/index overhead ≈ 384 MB, well inside the 2 GB §4 RSS ceiling.
  • C3 — WAL Storage Floor. 128 MB segment × 1.5x amplification (§4) = 192 MB physical per segment, × 8 segments retained = 1.54 GB storage floor per worker.
  • C4 — Histogram Merge Payload. 256 workers × 64 buckets × 16 B/bucket = 262,144 B merge payload, ÷ 50ms budget (§4) = 5.24 MB/s required merge throughput.
  • C5 — FD Budget Ceiling. 8,192 FDs (§4) ÷ 4 FDs/worker (1 WAL + 1 metrics + 2 RPC) = 2,048 workers/node before FD exhaustion.
  • C6 — Snapshot Throughput Floor. 384 MB working set (C2) × 8% runtime budget (§4) ÷ 30s cadence = 1.02 MB/s minimum sustained snapshot throughput.
  • C7 — p99 Saturation Guard. 20µs p99 (§4) × 5,000,000 ev/s (§4) = 100s of cumulative p99-equivalent load per wall-clock second, confirming p99 population must stay < 1% of events.
  • C8 — Availability Budget. (1 − 0.999) × 720h/month (§4) = 0.72h = 43.2 min/month allowed controller downtime.
  • C9 — Worker Recovery Budget. 10s lease timeout + 5s reassignment + 15s warm restart = 30s, matching the §4 worker-crash-recovery budget exactly.
  • C10 — Concurrent Simulation Ceiling. 2 GB RSS ceiling (§4) ÷ 8 MB per-simulation working set = 256, matching the §4 max-concurrent-simulations-per-node budget exactly.

34. Alternative Architectures (Roads Not Taken)

Alt A — Optimistic (Time Warp) Execution

+-----------+     rollback      +-----------+
| Worker A  | <---------------- | Worker B  |
| (ahead)   |   causality       | (behind)  |
| local time|   violation       | local time|
+-----------+     detected      +-----------+
      |                               |
      v                               v
  speculative                    speculative
  event execution               event execution
      |                               |
      +---------- anti-messages ------+

Regime where it wins: massively parallel simulation where synchronization overhead of a strictly-ordered global event list would dominate, and rollback cost is cheap relative to forward-progress gains. Embodied by David Jefferson's Time Warp Operating System (1985, §5 Papers). Rejected because rollback-based speculative execution requires reversible or checkpoint-restorable side effects for every subsystem (metrics, WAL writes, observability), directly conflicting with P4's crash-only philosophy and massively complicating I5's replay-equivalence proof — a rolled-back speculative event must never have been observable, which is incompatible with P5's "observability by default."

Alt B — Actor-Model Distributed Simulation

+--------+  msg   +--------+  msg   +--------+
| Actor  | -----> | Actor  | -----> | Actor  |
| (node) |        | (node) |        | (node) |
+--------+        +--------+        +--------+
   mailbox           mailbox           mailbox
  (per-actor          (per-actor        (per-actor
   local time)         local time)       local time)

Regime where it wins: workloads where nodes are naturally independent long-lived processes with only message-passing coupling and no need for a single global consistent snapshot. Embodied by Erlang/OTP's scheduler and supervision-tree model (§2.5). Rejected because per-actor local time (no single global event-ordering authority) makes I1's total-order guarantee across the whole topology unenforceable without an additional global synchronization protocol — which would simply reintroduce a centralized scheduler, at which point QTS's binary-heap design already provides the total order for free.

Alt C — Timer-Wheel Event Scheduling

[0][1][2]...[N-1]   <- wheel slots, one per time-quantum
 |  |  |        |
 v  v  v        v
list list list  list  <- events bucketed by (timestamp mod N)

Regime where it wins: extremely high insertion/cancellation rates where O(1) amortized insertion matters more than exact tie-break ordering within a bucket, and time resolution can be coarsened without correctness loss. Embodied by Tokio's hierarchical timer wheel (§5 Reference Implementations). Rejected because a timer wheel's bucket resolution trades exact ordering for O(1) insertion — QTS's < 2µs p50 dispatch budget (§4) and bit-identical replay requirement (I5) both need exact (timestamp, sequence) ordering, not bucketed approximation; the binary heap (ADR-10) gives O(log n) insertion with exact order at a fan-out where cache locality keeps the constant factor small enough to hit the throughput budget anyway (§32 C1).

Alt D — Trace-Driven Replay Only (No Synthetic Generation)

recorded production trace  --->  replay engine  --->  metrics
   (fixed, no distributions)      (no RNG needed)

Regime where it wins: capacity-planning questions where the only thing that matters is "how does this exact recorded workload behave under a proposed change," and distributional/statistical generality is unneeded overhead. Embodied by CloudSim's trace-driven execution mode (§2.5, §31). Rejected as QTS's sole mode because it cannot answer "what happens under a workload we have not yet observed" — Monte Carlo orchestration and statistical convergence (§17) are core deliverables (§1) that a trace-only engine cannot provide; QTS supports trace-driven replay as one input mode but does not adopt it as the only mode.

36. Glossary

  • SimTime — logical, deterministic simulation timestamp; never derived from wall clock (P3).
  • Replay Divergence — a measured difference between canonical and replay execution (I5); any occurrence is FM-1.
  • Saturation Ratio — queue occupancy divided by declared capacity (QueueMetrics, §11).
  • Service Discipline — the queue-scheduling algorithm governing dispatch order within a QueueNode (§8.3).
  • Tail Latency — high-percentile (p99/p99.9) latency, the primary subject of §28's performance methodology.
  • WAL — write-ahead log; the append-only durability mechanism underlying crash-only recovery (P4, §18).
  • Warm-Up Window — the initial, statistically unstable interval of a simulation run excluded from convergence analysis (§17).
  • Backpressure — downstream saturation propagating visibly to upstream admission decisions (P2).
  • Queue Collapse — unrecoverable latency amplification from sustained over-admission relative to service capacity.
  • Work Conservation — a scheduler property: never idle while admissible work is pending.
  • Starvation — indefinite postponement of a work item's service, bounded probabilistically under I6.
  • Lease — a time-bounded worker-ownership contract over a seed partition (WorkerLease, §11, I11).
  • Fanout — replication of a single event or work item to multiple downstream targets (broadcast routing, §8.4).
  • Replay Hash — the deterministic execution fingerprint chained through ReplayJournalRecord (§11).
  • Admission Control — the policy gating whether a WorkItem may enter a queue at all (I9).
  • Processor Sharing (PS) — a discipline simulating fair concurrent service among all queued items rather than strict sequential dispatch (§8.3).
  • Monte Carlo Run — one independent, seeded stochastic simulation replica within a campaign (§17).
  • Deterministic RNG — a random source whose every draw derives from an explicit seed lineage (qts-rng, I3, P12).
  • Conformance Fixture — a canonical validation artifact under fixtures/ (§10, §37) exercising a specific behavior or invariant.
