⬜ Phase 0 — Workspace & Deterministic Foundations §12

Objectives

Stand up the Cargo workspace and the correctness kernel every later phase depends on: canonical serialization, deterministic RNG and seed lineage, a monotonic simulation clock, and the canonical error hierarchy. No event scheduling or queueing logic exists yet — this phase's entire scope is "nothing downstream can be non-deterministic." Introduces the crates qts-core, qts-errors, qts-clock, qts-rng.

Deliverable

A runnable, empty deterministic-core skeleton: cargo test -p qts-core -p qts-errors -p qts-clock -p qts-rng passes; the reproducibility pipeline runs on CI and produces a byte-identical canonical encoding for fixtures/seed/basic.yaml across two independent invocations.

Acceptance

Replay hash identical across ≥ 10 repeated CI runs of fixtures/seed/basic.yaml (I3, I5 precursor). Canonical serialization roundtrip stable for 100% of qts-core::ids proptest cases (≥ 10,000 generated cases). Zero SystemTime::now() call sites outside the clippy-lint-approved allowlist (P3 enforcement, CI lint gate, 0 tolerance). Startup of the empty skeleton binary completes in < 3s per §4.

Fixtures

fixtures/seed/basic.yaml — canonical seed-lineage derivation smoke test. fixtures/seed/zero_seed.yaml — edge case: root seed of zero must not degrade derivation entropy (regression). fixtures/replay/repro_001.bin — first end-to-end canonical-encode reproducibility fixture, malformed-variant fixtures/scenarios/ malformed_capacity.yaml staged here for the Phase 4 (§16) compiler to consume later.

Pitfalls

Hidden wall-clock usage: manifests as replay divergence three phases later, root cause a stray Instant::now() in a logging call site; debug by diffing canonical-encoded traces between two runs with identical seeds; signal is a divergence at a timestamp-dependent field only; recovery is the P3 clippy lint plus a targeted fix. Non-canonical serialization drift: manifests as unstable replay hashes across identical inputs; root cause is a HashMap-backed struct field serialized without a sort pass; debugging method is a canonical-roundtrip differential fuzzer; recovery is enforcing canonical field ordering (P9) with a proptest gate.

⬜ Phase 1 — Event Scheduler Core §13

Objectives

Implement the deterministic event scheduler: the correctness-critical subsystem everything else is conditioned on (I1). Introduces the qts-event crate: binary-heap temporal ordering, stable tie-breaking, cancellation, and replay-validatable scheduler snapshots.

Deliverable

A standalone scheduler benchmark binary dispatching synthetic events with no queueing logic attached, demonstrating deterministic ordering and measured throughput.

Acceptance

≥ 5,000,000 events/sec sustained on reference hardware (§4, §32 C1), p99 dispatch latency < 20µs (§4). Zero heap-ordering violations across 1,000,000 dispatches per CI run (I1). Cancellation storm of 100,000 simultaneous cancellations completes without heap corruption, verified against fixtures/scheduler/cancellation_storm.bin.

Fixtures

fixtures/scheduler/basic_ordering.bin — canonical dispatch-order regression. fixtures/scheduler/timestamp_collision.bin — malformed-adjacent case: many events at an identical logical timestamp, exercises the stable tie-break. fixtures/scheduler/ cancellation_storm.bin — mass-cancellation replay case.

Pitfalls

Timestamp-collision instability: manifests as replay divergence only under specific collision patterns; root cause is a non-stable comparator (e.g. relying on pointer identity); debug via qts-replay's divergence scan once §18 exists, or a differential run against fixtures/scheduler/timestamp_collision.bin before that; signal is divergence localized to collision-timestamp events only; recovery is enforcing the (timestamp, sequence) lexicographic comparator (I1). Heap memory amplification: stale tombstoned events retained past their logical dispatch point; root cause is a missing compaction pass; signal is unbounded heap-size growth under a cancellation-heavy workload; recovery is periodic tombstone compaction triggered at a configurable dead-slot ratio.

⬜ Phase 2 — Queue Disciplines & Admission Control §14

Objectives

Implement every queue discipline (§8.3) and bounded-resource semantics atop the Phase 1 scheduler. Introduces the qts-queue crate: FIFO, LIFO, Priority, WFQ, Processor Sharing, SRPT, EDF, plus admission control and capacity enforcement (I2, I9).

Deliverable

An operational, interchangeable-discipline queue subsystem: a single QueueNode can be reconfigured across all seven disciplines via scenario config with no code change, demonstrated against fixtures/queues/fifo_basic.yaml and fixtures/queues/ srpt_latency.yaml.

Acceptance

Queue capacity enforcement is deterministic — zero over-capacity admissions across 1,000,000 enqueue attempts under adversarial burst load (I2). WFQ fairness error stays < 0.5% against fixtures/queues/priority_starvation.yaml (§4, I6). Starvation detection fires within 10,000 events of an adversarial low-priority-lockout pattern.

Fixtures

fixtures/queues/fifo_basic.yaml — baseline FIFO ordering regression. fixtures/ queues/srpt_latency.yaml — SRPT mean-response-time validation against the Harchol-Balter closed-form bound. fixtures/queues/priority_starvation.yaml — adversarial starvation-pattern regression exercising I6.

Pitfalls

Priority inversion: manifests as latency collapse for low-priority items behind a sustained high-priority stream; root cause is a naive strict-priority discipline with no fairness floor; debug via the starvation diagnostic counter from §13; recovery is switching to WFQ or adding an aging boost. Fairness drift under WFQ: manifests as starvation despite a nominally fair discipline; root cause is weight normalization drift after dynamic node reconfiguration; signal is scheduler_fairness_error exceeding 0.5% (I6); recovery is re-normalizing weights on every topology mutation.

⬜ Phase 3 — Queueing Network & Routing Engine §15

Objectives

Build networked queue topologies: multi-node graphs, routing policies (§8.4), open and closed queueing networks, and cycle/deadlock detection. Introduces the qts-network crate atop Phase 2's qts-queue nodes.

Deliverable

A runnable multi-node queueing-network simulator executing an open network (fixtures/network/jackson_network.yaml) and a closed network end to end, with bottleneck-node identification.

Acceptance

Zero undetected routing cycles across the full fixtures/network/routing_cycle.yaml adversarial corpus (I12, 100% detection rate required). Broadcast fanout dispatch order is byte-identical across 100 replay runs of fixtures/network/broadcast_fanout.yaml (I1, I5). Bottleneck-node identification matches the analytically-derived bottleneck for the Jackson-network fixture within 1% of the theoretical utilization.

Fixtures

fixtures/network/jackson_network.yaml — open Jackson network with a known analytical solution for cross-validation. fixtures/network/routing_cycle.yaml — malformed topology corpus exercising I12 cycle detection. fixtures/network/broadcast_fanout.yaml — deterministic fanout-order regression.

Pitfalls

Routing loops: manifests as unbounded event generation and eventual queue-capacity exhaustion; root cause is a missing or incomplete I12 compile-time check; debug via the dependency-graph exporter; recovery is rejecting the scenario compile with ERR_TOPOLOGY_CYCLE. Cyclic retry amplification: distinct from a structural routing loop — a legitimate acyclic topology can still exhibit retry-storm amplification when retry_policy re-injects work faster than downstream drains it; root cause is unbounded retry without backoff; recovery is bounding retry_count (§14) plus exponential backoff. Deadlock misclassification: a transient queue-full backpressure condition can look like a deadlock to a naive detector; root cause is not distinguishing "waiting" from "permanently blocked"; recovery is a bounded-wait-time threshold before declaring deadlock.

⬜ Phase 4 — Scenario DSL & Compiler §16

Objectives

Implement the declarative scenario DSL (§8.5) and its deterministic compiler: validation, schema normalization, and workload expansion into a canonical execution plan consumed by Phases 1–3. Introduces the qts-scenarios crate.

Deliverable

A qts scenario compile CLI subcommand that accepts a YAML scenario and emits a canonical execution plan or a structured validation error, demonstrated against fixtures/scenarios/valid_mm1.yaml and rejecting fixtures/scenarios/ malformed_capacity.yaml with ERR_QUEUE_CAPACITY_NEGATIVE.

Acceptance

100% of the 12 malformed fixtures in fixtures/scenarios/ and fixtures/network/ routing_cycle.yaml are rejected with the correct named error code (no false accepts). Compile time for a 10,000-node topology stays under the 3s startup budget (§4). Two independent compiles of fixtures/scenarios/valid_mm1.yaml produce byte-identical canonical plans (P9, 0 tolerance).

Fixtures

fixtures/scenarios/malformed_capacity.yaml — negative-capacity rejection case (§8.5). fixtures/scenarios/valid_mm1.yaml — canonical M/M/1 baseline for cross-validation against Kleinrock's closed-form utilization formula. fixtures/scenarios/ schema_drift.yaml — a scenario written against an older schema minor version, exercising the P7 backward-compatibility contract.

Pitfalls

Silent schema drift: an older scenario file with a since-renamed field is silently ignored rather than rejected; root cause is missing #[serde(deny_unknown_fields)]- equivalent strictness; debug by diffing the compiled plan's field set against the schema's required-field set; recovery is strict-mode parsing plus the fixtures/ scenarios/schema_drift.yaml regression. Non-canonical map ordering: manifests as compile-time output instability across restarts (not runs — restarts, because HashMap seed randomization differs per process); root cause is serializing an unordered map without a sort pass; recovery is P9's canonical field ordering enforced at the compiler boundary, not just at qts-core.

⬜ Phase 5 — Statistical Engine & Convergence Analysis §17

Objectives

Implement the statistical-correctness subsystem: histogram aggregation, confidence intervals, Monte Carlo convergence detection, and heavy-tail diagnostics. Extends qts-metrics (bootstrapped in §12's observability scaffolding) with histogram.rs and convergence.rs.

Deliverable

A statistically rigorous experiment engine: qts scenario run --replicas 30 produces a ConvergenceReport per tracked metric with a reproducible confidence interval, demonstrated against fixtures/stats/convergence.yaml.

Acceptance

Confidence intervals reproducible to within floating-point equality across two identical-seed-lineage runs (I3, I5). Histogram merge correctness validated against fixtures/stats/heavy_tail.bin with < 50ms merge latency for 256 worker histograms (§4). Warm-up exclusion window removes ≥ 95% of transient bias measured against the analytically-known M/M/1 steady state in fixtures/scenarios/valid_mm1.yaml.

Fixtures

fixtures/stats/heavy_tail.bin — Pareto-distributed service-time regression exercising histogram tail-bucket precision. fixtures/stats/warmup.yaml — known-transient-length scenario for warm-up-window validation. fixtures/stats/convergence.yaml — a 30-replica Monte Carlo campaign with a known analytical confidence interval.

Pitfalls

Warm-up bias: manifests as systematically biased confidence intervals that never resolve even with more replicas; root cause is a warm-up window shorter than the system's actual transient length; debug via the drift analyzer comparing early-batch versus late-batch means; recovery is extending the exclusion window and re-validating against fixtures/stats/warmup.yaml. Histogram precision loss: manifests as p99.9-and-above percentiles reading as flat/quantized; root cause is HDRHistogram bucket-count too coarse for the observed dynamic range; recovery is widening the significant-digits configuration (ADR-08) at the cost of memory (P8 tradeoff). Percentile drift across merges: manifests as a merged histogram's percentile estimate diverging from the arithmetic truth; root cause is a non-associative merge implementation; recovery is enforcing I13's associativity property test.

⬜ Phase 6 — Persistence and Replay §18

Objectives

Implement crash-only recovery (P4) and bit-identical deterministic replay (I5, P6). Introduces qts-storage (WAL, snapshotting) and qts-replay (journal, divergence detection).

Deliverable

A crash-recoverable deterministic runtime: killing the process mid-run and restarting against the persisted WAL/snapshot pair reproduces the exact pre-crash state and resumes with zero replay divergence.

Acceptance

Replay equivalence preserved across 100% of fixtures/replay/repro_001.bin, fixtures/replay/divergence.bin (negative control — must detect the injected divergence), and fixtures/replay/crash_mid_flush.bin runs. Recovery completes in < 30s (§4 worker crash recovery budget, §32 C9). Segment corruption is detected within one segment-read pass, 0 false negatives against fixtures/replay_segments/ corrupt_segment.bin.

Fixtures

fixtures/replay/divergence.bin — a deliberately corrupted journal exercising the I5 hash-mismatch detector (negative control). fixtures/replay/crash_mid_flush.bin — a torn-write simulation for the P4 crash-only recovery path. fixtures/replay_segments/ corrupt_segment.bin — checksum-mismatch regression for segment quarantine.

Pitfalls

Partial segment flush: manifests as a WAL segment readable up to an arbitrary byte offset then garbage; root cause is a crash between the write syscall and fsync; debug via the crash-simulation harness; recovery is truncating to the last verified checksum boundary on load, never trusting an unflushed tail. Snapshot drift: manifests as a recovered state that replays cleanly but diverges from pre-crash state; root cause is a snapshot taken at a WAL offset that does not actually correspond to a consistent state (I10 violation); recovery is enforcing the offset-consistency check at snapshot-write time, not just at load time. WAL ordering corruption: manifests as I7 violation, detected as a non-monotonic segment sequence on recovery; recovery is segment quarantine plus replay from the last known-good checkpoint.

⬜ Phase 7 — Distributed Experiment Orchestration §19

Objectives

Implement multi-worker experiment coordination: worker registration, lease management, failure detection, and duplicate-free work partitioning. Introduces the qts-coordinator crate.

Deliverable

A distributed experiment runner: a 256-replica Monte Carlo campaign (§4 max concurrent simulations/node) distributed across N workers with automatic reassignment on injected worker failure, demonstrated against fixtures/distributed/worker_loss.yaml.

Acceptance

Worker crash recovery completes in < 30s (§4, §32 C9), validated against fixtures/ distributed/worker_loss.yaml. Zero duplicate-execution incidents across 1,000 injected lease-expiry events (I11, 0 tolerance). Distributed aggregation produces a ConvergenceReport byte-identical to the single-node equivalent for the same seed set (I5 extended to the distributed case).

Fixtures

fixtures/distributed/worker_loss.yaml — mid-campaign worker-crash injection exercising lease reassignment. fixtures/distributed/reassignment.yaml — lease-expiry race regression for I11. fixtures/distributed/split_brain.yaml — dual-coordinator partition scenario exercising fencing.

Pitfalls

Duplicate work execution: manifests as an aggregate metric double-counting a replica; root cause is a lease granted to a second worker before the first worker's lease expiry is fully propagated; debug via the lease-grant audit log; recovery is strengthening I11's uniqueness check to a fencing token rather than a bare timestamp comparison. Lease-expiry races: manifests intermittently under high heartbeat-latency variance; root cause is a heartbeat renewal arriving just after expiry is declared; recovery is a renewal grace window sized against the §4 network RTT assumption (0.5–5ms intra-cluster). Aggregation drift: manifests as a distributed ConvergenceReport differing from an equivalent single-node run; root cause is a non-associative merge order dependency (I13 violation); recovery is enforcing the merge-order-independence property test from §17.

⬜ Phase 8 — Observability and Operational Tooling §20

Objectives

Implement production-grade observability without compromising I8's isolation invariant: metrics export, structured logging, distributed tracing, and operator dashboards. Extends qts-observability (scaffolded in §12) with exporters.rs and tracing_spans.rs.

Deliverable

An operationally observable runtime: end-to-end distributed traces spanning coordinator → worker → queue → routing decision, exported to a live OTel collector and Prometheus scrape target, demonstrated against fixtures/telemetry/span_integrity.bin.

Acceptance

End-to-end trace spans are complete (no orphaned spans) for 100% of fixtures/ telemetry/span_integrity.bin replay cases. Metrics-ingestion overhead stays < 5% CPU (§4) at the 5,000,000 ev/s dispatch rate (§4, §32 C1). Alert definitions produce zero false positives across a 72h soak-test fixture run (§4 max experiment duration).

Fixtures

fixtures/telemetry/span_integrity.bin — end-to-end trace-completeness regression. fixtures/telemetry/metrics_schema.json — Prometheus exposition-format schema conformance. fixtures/telemetry/exporter_outage.yaml — exporter-unavailability injection exercising graceful degradation.

Pitfalls

Metrics cardinality explosion: manifests as Prometheus scrape latency degradation or OOM in the metrics pipeline; root cause is an unbounded label (e.g. per-WorkItemId labeling instead of per-NodeId); debug via cardinality auditing on the exposition endpoint; recovery is enforcing a label-cardinality lint in CI. Trace-sampling bias: manifests as dashboards under-representing tail-latency events because uniform sampling drops rare slow spans disproportionately; recovery is tail-based sampling (retain spans exceeding a latency threshold at 100%, sample the rest at 1%). Logging amplification: manifests as log-volume growth outpacing the 5% CPU overhead budget under error storms; recovery is rate-limited structured logging with a summarized "N similar events suppressed" marker.

⬜ Phase 9 — Conformance, Fuzzing & Release Hardening §21

Objectives

Close the loop with a comprehensive conformance suite, fuzzing corpus, and release- engineering hardening suitable for third-party contribution review. Introduces qts-testkit and qts-fixtures; finalizes qts-cli.

Deliverable

A closed conformance and fuzzing suite: make conformance runs every fixture in fixtures/conformance/full_suite_manifest.json and exits non-zero on any regression; cargo fuzz run fuzz_scheduler runs continuously in CI with a corpus seeded from fixtures/conformance/fuzz_corpus_seed.bin.

Acceptance

100% of the ≥ 30 fixtures across every phase's fixtures/ subtree pass under conformance/suite_runner.rs (§10, §37). Zero crashes across 24h of continuous cargo fuzz execution per target (3 targets, §4-scale corpus). Regression suite fixtures/conformance/regression_v1_v2.bin validates P7 backward compatibility across the last two MINOR versions with 0 incompatibilities.

Fixtures

fixtures/conformance/full_suite_manifest.json — the master fixture manifest enumerating every fixture path and its expected outcome. fixtures/conformance/ regression_v1_v2.bin — cross-version compatibility regression (P7). fixtures/ conformance/fuzz_corpus_seed.bin — the seed corpus bootstrapping all three fuzz targets.

Pitfalls

Fixture drift: manifests as a conformance fixture silently going stale (still passes, but no longer exercises the code path it was written for) after a refactor; root cause is fixtures never being audited against code-coverage of the invariant they claim to test; debug via periodic coverage-gap audits of fixtures/conformance/full_suite_ manifest.json against §7's invariant list; recovery is retiring or rewriting stale fixtures with an explicit changelog entry. Fuzz-corpus stagnation: manifests as fuzz runs finding nothing for months then a real bug slips through in production; root cause is a corpus that stopped evolving after initial seeding; recovery is periodic corpus minimization-and-regrowth cycles feeding discovered edge cases back into fixtures/conformance/fuzz_corpus_seed.bin.
