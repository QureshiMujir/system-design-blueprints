⬜ Phase 0 — Skeleton, Attach/Inject, Decode Adapter, Code Cache, Dispatcher, Null Tool

Objectives

Stand up the engine spine: spawn+ptrace a target, inject the engine, translate one basic block (copy-and-patch via #334), install it in an RX code cache, and execute it via the dispatcher — with a null tool. Constraint: the target executes only cached code from the first block (I1).

Deliverable

instr -- ./hello runs hello entirely from the code cache and produces identical output to native.

Acceptance
  • Output of a set of CLI programs under instr is byte-identical to native (transparency smoke).
  • Every executed instruction came from the cache (escape detector = 0, I1).
  • Dispatcher correctly follows direct branches (via exit→dispatch, unlinked).
  • Fuzz smoke: translator on arbitrary block bytes → no engine crash.
Fixtures
Fixture Purpose Expected output
conformance/translate/straightline a block with no control flow translates byte-faithfully translated block ≡ original insns + exit stub; runs identically
conformance/translate/branch direct jcc/jmp terminator redirected to exit exit returns to dispatcher with correct fallthrough/target tag
conformance/translate/call_ret call/ret pair routes through dispatch (pre-IBL) both targets translated; output identical
conformance/transparency/stdout_eq engine output not mixed into target stdio target stdout byte-identical to native; engine logs on a private fd
conformance/transparency/exit_code_eq process exit code preserved exit code ≡ native
conformance/differential/native_vs_cached whole-run differential under the null tool stdout/stderr/exit ≡ native; cache_escape = 0
Pitfalls
  • rip-relative not fixed up (I4) → first lea/load reads cache memory → instant divergence; fix disp in Phase 0 even before probes.
  • W^X violation → mapping RWX is a security smell + some kernels refuse; toggle perms around install.
  • Stack/red-zone clobber by the dispatcher → use a private engine stack.
  • PLT/dynamic loader code also runs → must be translated too (don't assume only .text).

⬜ Phase 1 — Direct-Branch Linking (the overhead killer)

Objectives

Patch direct-branch exits to jump straight to the target's cached block, eliminating dispatcher round-trips on hot direct control flow (principle 4) — the single biggest overhead reduction.

Deliverable

A tight loop runs almost entirely cache-resident (block→block direct jumps); dispatcher count drops by orders of magnitude.

Acceptance

On a loop microbench, post-link slowdown ≤ 1.2× vs native (null tool); dispatcher invocations per loop iteration → ~0 after warmup; links validated (I5).

Fixtures

conformance/translate/link_loop, benchmarks/overhead/linked_loop, link-table integrity fixture.

Pitfalls
  • Linking to a stale/evicted block (I5) → patch to a freed address → crash; check liveness + reverse map before link.
  • Atomic patching of a live jump on another thread → use safe patch sequences (I8).
  • Conditional branches have two exits (taken/fall) → link both independently.
  • Self-loop linking edge case (block jumps to itself).

⬜ Phase 2 — Probe API + Register/Flags Save-Restore (clean calls + inline)

Objectives

Let a Tool insert instrumentation at translate time: full clean calls (save context → call tool fn → restore, I3) and fast inline ops (e.g., counter increments with only flag spill). Transparency of target state is the hard requirement.

Deliverable

A callcount tool counts routine entries; a bblcount tool counts blocks — both via inserted probes, output correct, target unperturbed.

Acceptance

Instrumented run output identical to native (I3 transparency held); counts correct vs a known workload; clean-call context checksum unchanged across the call; inline path adds ≤ 1 op overhead.

Fixtures

conformance/transparency/ctx_preserved, tools/{callcount,bblcount} golden counts, clobber-optimization fixture.

Pitfalls
  • Forgetting RFLAGS (even inline inc sets flags!) → save/restore flags around inline ops (I3).
  • Red zone (128B below rsp) clobbered by the spill → adjust rsp first / use engine scratch.
  • XMM/AVX state if the tool uses FP → declare + save.
  • Stack alignment (16B at call) → align before clean call.

⬜ Phase 3 — Indirect Branch Handling (IBL) + ret/call reg/jmp reg

Objectives

Keep execution in the cache across indirect branches (returns, call reg, jmp reg, jump tables) via a fast indirect-branch lookup (IBL), since their targets can't be statically linked (I6).

Deliverable

Programs with heavy virtual dispatch / deep call stacks run cache-resident; IBL hit-rate high; output correct.

Acceptance

IBL hit-rate ≥ 95% on a call-heavy workload after warmup; indirect targets always resolve to the correct cached copy (I6); slowdown bounded (§4).

Fixtures
Fixture Purpose Expected output
conformance/translate/ret a function return routes through IBL/return cache resolves to the cached caller block; never escapes (I1/I6)
conformance/translate/call_reg call reg (function pointer) IBL resolves target → cached copy; output identical
conformance/translate/jmp_table a switch compiled to a jump table each case target translated on demand; correct branch taken
conformance/translate/vtable_dispatch C++ virtual dispatch (indirect through vtable) each concrete method translated; IBL hit-rate ≥ 95% after warmup
conformance/translate/ibl_collision two app targets that hash to the same slot tag-verify rejects the wrong one (I6); both resolve correctly (MM5)
conformance/translate/setjmp_longjmp stack-jumping control flow resumes in cache at the longjmp target; no escape
Pitfalls
  • IBL returning the wrong block (hash collision mishandled) → must verify the tag, not just hash (I6).
  • Returns are hot → a generic IBL is slow; add a return-target predictor.
  • Tail calls (jmp reg) vs returns distinction.
  • Mixing app and cache addresses in the indirect target (must translate app→cache).

⬜ Phase 4 — Traces / Hot-Path Optimization (NET)

Objectives

Reduce dispatch + enable cross-block optimization by stitching frequently-executed block sequences into single straight-line traces (Next-Executing-Tail selection, Dynamo/DynamoRIO), so hot paths avoid even link hops and expose inlining of probes.

Deliverable

Hot loops/paths execute as single trace fragments; dispatch + inter-block jumps drop further; measurable overhead reduction over linking alone.

Acceptance

On a hot-loop benchmark, traces cut remaining dispatch/IBL by ≥ 50% vs linking-only; output unchanged (transparency); trace tails resolve correctly.

Fixtures

conformance/traces/{net_loop,hot_path}, benchmarks/traces/*, trace-correctness differential.

Pitfalls
  • Trace explosion (every path becomes a trace) → hotness threshold + length cap + trace cache budget.
  • Mid-trace exits (early-exit blocks) → side exits must restore state + leave correctly.
  • Stale traces after SMC/flush (I7) → invalidate traces with their constituent blocks.
  • Over-aggressive inlining of cold tails into hot traces → NET stops at the head's back-edge.

⬜ Phase 5 — Transparency: PC / Stack / Maps Views, Address Hiding

Objectives

Make the engine invisible: whenever the target observes its own PC, stack, or memory map, it must see original addresses and its own layout — never code-cache addresses or engine memory (principle 1, the defining DBI challenge).

Deliverable

Self-checking targets (programs that read their own PC, walk their stack, parse /proc/self/maps, or compute return addresses) behave identically under instr.

Acceptance

A transparency test-suite (PC reads, stack unwinding, maps parsing, return-address checks) passes under instrumentation; no cache address ever leaks to the target (I4, pc_leak=0).

Fixtures
Fixture Purpose Expected output
conformance/transparency/read_pc target reads RIP via lea/call observed PC = original address, never a cache address (I4)
conformance/transparency/stack_walk target walks its own call stack (unwinder) every frame's return address is an app address
conformance/transparency/proc_maps target parses /proc/self/maps cache region filtered out; only the target's own modules visible
conformance/transparency/return_addr target computes/compares a return address matches native; ret still resolves into the cache via IBL
conformance/transparency/getauxval target reads auxv/getauxval app values returned; engine mappings hidden
conformance/transparency/pic_base PIC computes its own load base base = app base (rip-rel fixup); pc_leak = 0
Pitfalls
  • call pushes a cache return address → must push the app address so ret/stack-walk see app code (I4); IBL translates it back on return.
  • Exception/unwind tables (.eh_frame) reference app addresses → faults must map cache→app.
  • /proc/self/maps revealing the cache region → filter it.
  • Timing/instruction-count transparency is impossible (documented limit).

⬜ Phase 6 — Signals & Exceptions: Faithful Forwarding

Objectives

Deliver signals (and CPU exceptions/faults occurring in cached code) to the target's handlers with the original fault address + register context, so the target's signal handling is unaffected (I9).

Deliverable

Targets that install handlers (SIGSEGV recovery, SIGALRM timers, etc.) work identically; faults report original addresses.

Acceptance

Signal-handler tests pass (handler sees original PC + correct siginfo); synchronous faults map cache→app (I9, signal_ctx_wrong=0); sigreturn resumes correctly.

Fixtures

conformance/signals/{sigsegv_handler,sigalrm,sigaction_track,fault_in_cache,longjmp}.

Pitfalls
  • Reporting a cache PC to the handler (I9) → handler logic breaks; rebuild app context.
  • Reentrancy (signal during translation/dispatch) → engine-internal vs app signal masking.
  • sigreturn must resume in the cache, not the app code.
  • Nested signals + alternate signal stacks (sigaltstack).

⬜ Phase 7 — Self-Modifying / Generated Code + Code-Cache Management

Objectives

Stay correct when the target writes code (JITs, packers, trampolines) by detecting writes to cached regions and invalidating stale cache (I7); and keep the code cache bounded via safe eviction/flush (I8, principle 9).

Deliverable

A target that generates/patches code at runtime (a tiny JIT) executes correctly under instr; long-running targets stay within the cache budget.

Acceptance

SMC test: target patches code → engine re-translates → correct output (I7); cache stays ≤ budget under a code-churning workload; no use-after-free on flush (I8).

Fixtures

conformance/smc/{self_patch,jit_target,trampoline}, cache/{capacity_evict,flush_safe}.

Pitfalls
  • Write to a cached page not detected (I7) → run stale code; must write-protect all cached source pages.
  • Granularity: page-level protection over-invalidates (a data write near code) → re-translate cost; acceptable, but measure.
  • Flushing a linked-into block → unlink all incoming links first (reverse map, Phase 1) before free (I8).
  • Executing thread on a flushed block → quiescence barrier.

⬜ Phase 8 — Thread Safety: Per-Thread Caches, Thread Creation, Safe Sharing

Objectives

Support multi-threaded targets: each thread gets its own code cache + scratch (I10); thread creation (clone/pthread_create) is intercepted to bring new threads under the engine; shared structures (IBL tables, module map) are synchronized.

Deliverable

A multi-threaded target runs under instr with correct per-thread instrumentation; no cross-thread cache execution; output correct.

Acceptance

A pthreads workload produces identical output + correct per-thread counts; no cross-thread exec (I10, cross_thread_exec=0); flush under concurrency is safe (I8); no data races (TSan/loom on shared structures).

Fixtures

conformance/threads/{pthreads_count,clone_intercept,concurrent_flush,shared_lib}.

Pitfalls
  • A new thread escaping into uninstrumented code before the engine grabs it → intercept at clone precisely (I10).
  • Sharing one cache across threads (race) → per-thread by default (I10).
  • Tool state races → document the Tool threading contract; provide per-thread tool slots.
  • TLS + the engine's own thread-local scratch.

⬜ Phase 9 — Attach-to-Running + Clean Detach / De-instrumentation

Objectives

Attach to an already-running process and bring it under the engine, and cleanly detach so the target resumes native execution with no residual patches/traps (I11, principle 12).

Deliverable

instr --pid N --tool t.so attaches to a live process, instruments it, and --detach returns it to native execution still running correctly.

Acceptance

Attach mid-execution → correct instrumentation; detach → target continues natively, no residual traps (I11, residual_patch=0), no crash; threads resume at correct original PCs.

Fixtures

conformance/{attach_running,detach_clean,detach_midblock,reattach}.

Pitfalls
  • Detaching mid-block → the app PC must map to a block boundary; resume only at safe points (cache→app mapping).
  • Residual inline detours/trampolines left after detach (I11) → full unpatch scan.
  • Thread in a syscall at attach/detach → handle interrupted syscalls.
  • Lost signals during the stop window.

⬜ Phase 10 — Example Tools + Tool SDK (coverage, trace, memtrace, shadow)

Objectives

Validate the probe API by building canonical tools and a small SDK: code-coverage (drcov-style, for fuzzers #229), instruction/branch trace, memory-access trace, and a shadow-memory scaffold (the substrate for a Memcheck-like tool; full implementation deferred — see the Deferred Features Register).

Deliverable

instr --tool coverage -- ./target produces a drcov-compatible coverage file; trace/memtrace tools produce correct logs; shadow scaffold runs.

Acceptance

Coverage matches a known control-flow ground truth; memtrace captures all accesses on a fixture; tools add overhead within §4 budgets; coverage file consumable by a fuzzer.

Fixtures

tools/*/golden, conformance/transparency/tool_no_perturb.

Pitfalls
  • Memtrace missing implicit accesses (push/pop/string ops) → instrument all memory operands, not just explicit loads.
  • Coverage module attribution wrong (ASLR) → key by module+offset via #333, not absolute address.
  • Tool overhead dominating → prefer inline ops; document.
  • Shadow memory scaling (full impl deferred) → scaffold only.

⬜ Phase 11 — Hardening: Translator Fuzzing, Transparency Suite, Differential

Objectives

Guarantee the translator never crashes on arbitrary code (robustness), the transparency suite stays green (the hardest correctness), and instrumented≡native output across a corpus (differential).

Deliverable

Green CI: build+clippy+test+fuzz-smoke+transparency+differential; a soak target list.

Acceptance

0 translator crashes over 1e9 fuzz execs; transparency suite 100%; differential parity on the corpus (output/exit/signals); no data races (loom/TSan).

Fixtures

fuzz/corpus/*, full conformance/**, differential/corpus/*.

Pitfalls
  • Fuzzer feeding non-code bytes → translator must reject/handle (decode errors from #334) without engine crash.
  • Flaky differential from target nondeterminism (time/PID/ASLR) → control the environment (disable ASLR, pin time) or compare normalized output.
  • Transparency regressions slipping in with new optimizations (traces/links) → suite gates every change.
  • Race only under load → loom for exhaustive interleavings on small models.

⬜ Phase 12 — Overhead Engineering, Soak, Release

Objectives

Drive base + tool overhead to the §4 targets, soak long-running + multi-threaded targets, and ship a reproducible signed release.

Deliverable

Overhead report vs §4; green nightly soak; signed release; tuning guide.

Acceptance

Null-tool overhead within §4 (≤ 2–5× typical, ≤ 1.2× link-heavy); soak: bounded memory, 0 leaks, output correct over hours/threads; deterministic instrumentation (I12).

Fixtures

benchmarks/overhead/*, conformance/soak/*.

Pitfalls
  • Cache growth on long runs → bounded eviction (Phase 7) must actually cap memory.
  • Pathological indirect-heavy code (interpreters) → IBL + return prediction critical.
  • Clean-call-heavy tools dominating → push tools toward inline ops.
  • Measurement noise → pinned cores, disabled turbo, many iterations.
