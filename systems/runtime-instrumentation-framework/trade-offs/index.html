Decisions (§9) · 24 ADRs

ADR-001

Language

Chosen

Rust 2021 ≥1.78

Rejected

C, C++

When the rejected choice is right

C when the engine must run inside an arbitrary target with a hostile/absent CRT, or co-compile with a C-only RTOS toolchain — Pin and DynamoRIO are C/C++ precisely because they self-host in stripped environments where the Rust runtime's TLS/landing-pad assumptions do not hold (P1).

Why: control of C with unsafe containment; shares #334 workspace

ADR-002

Decode

Chosen

reuse #334 Instruction/Cfg

Rejected

new purpose-built decoder

When the rejected choice is right

A new decoder wins when instrumentation needs a different IR than analysis — e.g. a decode-for-encode round-trip (semantic re-emission) where #334's listing-oriented model loses the bits needed to re-assemble; Valgrind/VEX chose a bespoke lift for exactly this.

Why: single source of truth (P5)

ADR-003

Engine model

Chosen

copy-and-patch code cache + dispatch (DynamoRIO-style)

Rejected

trap-per-insn (ptrace); full emulation

When the rejected choice is right

Trap-per-insn wins for sparse, single-shot probes on a slow path (a debugger conditional breakpoint, the Phase 9 cousin) where translation cost dwarfs the few traps; full emulation (QEMU) wins for cross-ISA execution or when no native execution of target code is permissible (untrusted firmware on a foreign host).

Why: speed: native execution of translated code (P4)

ADR-004

Probe insertion

Chosen

JIT instrumentation (insert at translate time) + inline detours

Rejected

breakpoint traps

When the rejected choice is right

Breakpoint traps win when probe sites are rare and dynamic (set/cleared at runtime by an interactive operator) and you cannot afford to re-translate — exactly the ptrace int3 model #74 (debugger) uses; one trap on a cold path beats re-JITting a hot trace.

Why: overhead: traps are ~µs each

ADR-005

Linking

Chosen

direct-branch linking + IBL for indirect

Rejected

always dispatch

When the rejected choice is right

Always-dispatch wins under aggressive SMC/flush churn (a self-rewriting packer) where links are invalidated faster than they pay back, and as the deliberate instr --no-link debug mode (Phase 1, N.10) that makes every transition observable.

Why: the key to low overhead (P4)

ADR-006

Traces

Chosen

NET (next-executing-tail) hot-path traces

Rejected

no traces (linked blocks only)

When the rejected choice is right

No traces wins on flat, branch-sparse code (a memcpy-bound or vectorized kernel) where blocks are already large and traces only add trace-cache pressure + side-exit complexity; DynamoRIO itself disables traces for some workloads, and instr --no-traces (Phase 4, N.10) isolates trace bugs.

Why: reduce dispatch + improve i-cache locality (Phase 4)

ADR-007

Attach

Chosen

ptrace spawn/attach + dylib injection

Rejected

LD_PRELOAD only

When the rejected choice is right

LD_PRELOAD only wins when you control the launch and never need to attach to a running pid — it sidesteps ptrace entirely, so it works under a restrictive YAMA ptrace_scope=2/container where PTRACE_ATTACH is denied.

Why: works for attach and spawn; injection covers the engine itself (Phase 9)

ADR-008

Code cache mem

Chosen

mmap RX, W^X via dual-map/mprotect toggling

Rejected

single RWX mapping

When the rejected choice is right

RWX wins on platforms/kernels without W^X enforcement where the mprotect toggle cost is measurable and the threat model already trusts the host (a closed appliance) — early DBI engines used RWX for the simpler, faster install path.

Why: security: never writable+executable simultaneously

ADR-009

Context save

Chosen

ABI-aware clean call + declared-clobber optimization

Rejected

save-all-always

When the rejected choice is right

Save-all-always wins for an opaque third-party analysis callback whose clobber set is unknown or changes per build — correctness then trumps the spill cost, and a full pushaq/pushfq frame is the only safe contract (the conservative default Pin offers).

Why: overhead (P3/P4)

ADR-010

SMC

Chosen

write-protect cached pages; fault→invalidate

Rejected

ignore SMC

When the rejected choice is right

Ignore SMC wins when the target is provably static (a verified, signed, non-JIT binary) — skipping write-protection removes the per-page fault cost and the protection-granularity over-invalidation entirely, a legitimate --assume-static fast mode.

Why: correctness (I7)

ADR-011

Threading

Chosen

per-thread code cache + scratch

Rejected

single global shared cache

When the rejected choice is right

A shared cache wins for a many-thread target running identical code (a thread-pool worker) where per-thread duplication wastes memory and i-cache; with proper locking + RCU, one cache amortizes translation across all threads — Pin offers a shared-cache mode for this.

Why: safety + scalability (I10)

ADR-012

Signals

Chosen

intercept + rebuild original-context

Rejected

passthrough (no interception)

When the rejected choice is right

Passthrough wins for a target that installs no handlers and never inspects signal context — interception is pure overhead, so a --no-signal-fixup mode is correct when faults simply terminate the process.

Why: transparency (I9)

ADR-013

Tool API

Chosen

Rust dylib plugin implementing Tool trait

Rejected

embedded scripting (JS/Lua)

When the rejected choice is right

Embedded scripting wins for interactive exploration / rapid prototyping where recompiling a dylib per change is too slow — Frida's JS API exists for exactly this REPL-style RE workflow, trading per-probe overhead for iteration speed.

Why: type-safe, low overhead

ADR-014

ISA seam

Chosen

x86-64 first; Arch trait for arm64/win

Rejected

x86-only (no seam)

When the rejected choice is right

x86-only wins for a team shipping one platform forever — the Arch indirection adds vtable cost + abstraction tax that a single-ISA engine never recovers; premature portability is a real anti-pattern.

Why: portability to deferred tracks

ADR-015

Testing

Chosen

cargo test + golden traces + differential (uninstrumented vs instrumented)

Rejected

unit-only

When the rejected choice is right

Unit-only suffices for a pure leaf library with no I/O or observable side effects; differential testing pays off only where an external oracle (native execution) exists — for a deterministic pure function it adds harness cost with no new coverage.

Why: transparency proof (I4/I9)

ADR-016

Fuzzing

Chosen

cargo fuzz (libFuzzer) on translator (bytes→block)

Rejected

no fuzzing

When the rejected choice is right

No fuzzing is defensible only when inputs are fully constrained (the translator only ever sees bytes #334 already validated); for a trusted, schema-bounded input a formal proof or exhaustive enumeration beats coverage-guided fuzzing.

Why: never-crash translate

ADR-017

Sanitizers

Chosen

Miri on safe code; ASan on the engine harness

Rejected

none

When the rejected choice is right

None wins in the shipping hot path — sanitizers carry 2–20× overhead and are CI/dev-only; a release build must run without them, so "none" is correct for the production artifact, not for CI.

Why: UB on the unsafe edges

ADR-018

Transparency tests

Chosen

self-checks: app reads of PC/stack/maps match native

Rejected

none

When the rejected choice is right

None is acceptable for a tool that deliberately transforms behavior (an optimizer or a fault-injector) where instrumented≠native is the goal; transparency tests only gate engines that promise invisibility.

Why: P1 (the hard part)

ADR-019

CLI

Chosen

clap (instr -- prog / --pid / --tool t.so)

Rejected

bespoke arg parser

When the rejected choice is right

A bespoke parser wins for a single-purpose embedded launcher with two fixed flags where clap's binary-size + compile-time cost is unjustified, or where the CLI must match a legacy pin-exact grammar clap cannot express.

Why: pin/drrun-like UX

ADR-020

CI

Chosen

build+clippy+test+fuzz-smoke+transparency+differential

Rejected

none / manual

When the rejected choice is right

Manual gating wins for a solo research spike where CI infrastructure cost exceeds value before the design stabilizes; automation pays back only once contributors > 1 and the suite is non-trivial.

Why: gates

ADR-021

Bench

Chosen

criterion + SPEC-like micro/macro overhead

Rejected

none / ad-hoc timing

When the rejected choice is right

Ad-hoc timing suffices when overhead is not a product requirement (a correctness-only research tool); criterion's statistical rigor matters only when you gate releases on regression thresholds.

Why: §4 overhead targets are the whole product

ADR-022

Deps

Chosen

minimal, pinned, cargo-deny

Rejected

many convenience crates

When the rejected choice is right

Many crates wins under hard delivery deadlines where reuse beats audit cost and the threat model tolerates transitive deps — a throwaway internal tool, not a security primitive that injects into other processes.

Why: supply chain

ADR-023

Versioning

Chosen

SemVer on Tool/Probe API

Rejected

implicit / no policy

When the rejected choice is right

Implicit versioning wins for a single-consumer API inside one repo where the engine and its only tool ship together — SemVer's ceremony pays off only with external, independently-released tool authors.

Why: tool ecosystem stability

ADR-024

Repro

Chosen

deterministic instrumentation + pinned toolchain

Rejected

floating toolchain

When the rejected choice is right

Floating toolchain wins for bleeding-edge development that must track nightly compiler features; reproducibility-by-pinning trades the latest optimizations for bit-identical rebuilds, which only a release/audit context demands.

Why: I12 (reproducible traces)

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for "observe and rewrite a running program," each with the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

A1 — Static / compile-time binary instrumentation (rewrite the binary on disk).

   ELF on disk ──► static rewriter ──► instrumented ELF on disk ──► run natively (no engine)
                    (insert probes, fix up relocations, expand .text)

Wins when: the binary is available ahead of time, code is not self-modifying, and you want zero runtime engine overhead (the probes are just inlined code) — long-running servers re-instrumented once. Embodied by: Dyninst (Buck & Hollingsworth, 2000) static mode and ATOM (historically). Rejected here because: it cannot follow dynamically generated/JIT code, cannot attach to an already-running process, and indirect-branch targets + stripped binaries make complete static CFG recovery undecidable — the very dynamic targets (packers, JITs, RE subjects) this framework exists for are exactly where static rewriting fails. (Contrast: ADR-003, Phase 7 SMC, Phase 9 attach.)

A2 — Hardware-assisted tracing (Intel PT / branch trace), no code rewriting.

   target runs NATIVE ──► CPU emits a compressed control-flow packet stream (Intel PT)
                          ──► decoder reconstructs the executed path offline/online

Wins when: you need near-zero-overhead whole-program control-flow capture (≈2–5% vs 2–10×) and only need what executed, not arbitrary in-line analysis — production tracing, coverage at scale. Embodied by: Intel Processor Trace (consumed by perf, libipt; magic-trace). Rejected here because: PT gives a control-flow trace, not the ability to insert arbitrary computation at a point, read/modify register or memory state inline, or do shadow-memory taint — it is read-only and post-hoc. This framework's clean-call/inline probe model (Phase 2) and memory hooks (Phase 10) require active instrumentation PT cannot provide. (A future hybrid — PT for cold paths, DBI for hot analysis — is PhaseDeferred("Deferred Features Register").)

A3 — Kernel eBPF / dynamic tracing (in-kernel verified bytecode at probe points).

   user/kernel code ── kprobe/uprobe/tracepoint ──► eBPF VM (in-kernel, JIT-compiled, VERIFIED)
                                                     ──► maps/ringbuf ──► userspace consumer

Wins when: you want safe, low-overhead, production observability across many processes/syscalls without controlling or rewriting any single target's full code — fleet-wide tracing. Embodied by: eBPF/bpftrace and conceptually DTrace (Cantrill et al.). Rejected here because: it is a different trust model — in-kernel verified, restricted bytecode attached at predefined probe points (function entry/exit, tracepoints), not arbitrary userspace rewriting of every basic block/instruction. eBPF cannot instrument at instruction granularity inside arbitrary user code, cannot follow a JIT's generated code, and is bounded by the verifier (no unbounded loops). This framework's instruction-level, JIT-following, transparent userspace DBI (Phase 0/3/7) is outside eBPF's design envelope; eBPF is the right tool for the opposite problem (broad, safe, predefined-point tracing). (§2 names #154 eBPF VM as the in-kernel analogue.)

A4 — Source / IR (compile-time) instrumentation (ASan/coverage-style).

   source/LLVM IR ──► instrumentation pass (insert checks/counters) ──► compile ──► native binary

Wins when: you have the source (or IR) and want the lowest-overhead, most semantically precise instrumentation — sanitizers (ASan/TSan/MSan), -fprofile-instr coverage, fuzzing harness coverage (SanitizerCoverage). Embodied by: LLVM sanitizer passes and SanitizerCoverage (the compile-time cousin of #229's coverage). Rejected here because: this framework's entire premise is binary instrumentation of code without source or cooperation — RE subjects, closed-source binaries, malware, third-party libraries. Source instrumentation is strictly better when source exists, which is exactly the case this tool does not assume. (Non-goal in §1; the deferred Valgrind-style lift-to-IR of A-adjacent analysis is in the Deferred Features Register.)
