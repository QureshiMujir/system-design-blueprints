Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived step-by-step from the §4 System Constraints table (and the per-structure sizes in Appendix R). Formula shown; assumptions stated.

Baseline assumptions (from §4 + Appendix R): avg basic block ≈ 6 x86-64 instructions ≈ 24 original bytes; translation expansion ≈ 1.5× code + exit stubs; code-cache ceiling ≤16× instrumented code (§4); translation ≤5 µs/block (§4); dispatcher round-trip ≤200 ns (§4); IBL hot ≤20 ns (§4).

  1. Translated bytes per block. block_bytes = orig_bytes × expansion + exit_stub = 24 × 1.5 + 16 ≈ 52 B/block. → a block costs ~52 bytes of RX cache.
  2. Code-cache size for a working set. cache = unique_blocks × block_bytes. For a 1 MB hot .text ≈ 1 MB / 24 B ≈ 43.7k blocks → 43.7k × 52 B ≈ 2.27 MB. Check against §4's ≤16× rule: instrumented code ≈ 1 MB × 1.5 = 1.5 MB; 2.27 MB ≈ 1.5× the original — well under the 16× ceiling (which budgets for probes + traces + stubs).
  3. Per-thread total cache memory. per_thread = cache + tables. Tables (Appendix R): tag→addr ≈ 43.7k × 16 B ≈ 0.70 MB; cache→app ≈ 43.7k × 16 B ≈ 0.70 MB; reverse-link ≈ (links≈1.5/block) × 43.7k × 8 B ≈ 0.52 MB; IBL table (next pow-2 ≥ working set, say 64k slots × 16 B) ≈ 1 MB. → per_thread ≈ 2.27 + 0.70 + 0.70 + 0.52 + 1.0 ≈ 5.2 MB.
  4. 8-thread footprint. total = per_thread × threads = 5.2 MB × 8 ≈ 41.6 MB. → a large multi-threaded target instruments in tens of MB; this is the number that decides whether per-thread caches are affordable (MM10) — they are.
  5. Cold-start translation time. warmup = unique_blocks × translate_cost = 43.7k × 5 µs ≈ 0.22 s per thread, one-time. → first-touch latency on a 1 MB working set is sub-second; amortized to ~0 in steady state (MM1).
  6. Dispatch overhead if unlinked. cost = transitions/s × round_trip. A loop doing 10⁸ block-transitions/s × 200 ns = 2.0 × 10¹⁰ ns/s = 20× real time → 20× slowdown — quantifies why linking (Phase 1) is mandatory, not optional.
  7. Dispatch overhead after linking. Linked direct branch ≈ 1 jmp ≈ ~1 ns; 10⁸ × 1 ns = 0.1 s/s ≈ near-native → matches §4's ≤1.2× linked-loop target. The lever between #6 and #7 is the entire value of the engine.
  8. IBL throughput ceiling. max_indirect/s = 1 / ibl_hot = 1 / 20 ns = 5 × 10⁷ indirect branches/s per thread before IBL alone bounds you → an interpreter doing one indirect dispatch per bytecode tops out near 50M bytecodes/s/thread on the IBL path (why interpreters are the §4 worst case at 5–10×).
  9. IBL hash-table sizing. For load factor ≤0.5 and a working set of W indirect targets, slots = next_pow2(2W). For W = 20k call sites: slots = 64k, mem = 64k × 16 B = 1 MB (matches #3). → load factor 20k/64k ≈ 0.31, keeping probe chains short (correctness-preserving, MM5).
  10. SMC fault cost (JIT target). smc_overhead = rewrites/s × (fault + flush + retranslate). A JIT regenerating 100 functions/s, each ~10 blocks: 100 × (fault≈3 µs + 10 × 5 µs translate) ≈ 100 × 53 µs ≈ 5.3 ms/s ≈ 0.5% → SMC is cheap for moderate JITs; a pathological packer rewriting MB/s is the documented worst case (Phase 7, N.7).
  11. Clean-call spill cost. Full frame = 15 GPRs + RFLAGS + (optional 16 XMM): ~16 × 8 B + 16 × 16 B = 384 B of stack traffic per call; at ~1 ns/8 B ≈ ~48 ns plus call/ret ≈ ~60–80 ns/clean-call → quantifies why hot probes must be inline (Phase 2) not clean calls (a per-block clean call at 10⁸/s = 6–8× alone).
  12. Coverage tool memory. drcov bitmap = 1 bit/block: 43.7k blocks / 8 ≈ 5.5 KB per module → coverage is essentially free in memory (#229 fuzzing feedback), confirming the §4 BBL-tool ≤10× budget is set by the inserted op, not memory.

These twelve numbers, all derived from §4, are what tell an expert before any code: per-thread cache ≈ single-digit MB, warmup sub-second, unlinked dispatch is fatal (20×), linked is near-native, and the IBL/clean-call costs set the interpreter/heavy-tool ceilings.
