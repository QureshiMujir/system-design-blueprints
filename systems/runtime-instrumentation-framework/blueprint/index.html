336 — Runtime Instrumentation Framework from Scratch

Project Number: 336

Project Name: Runtime Instrumentation Framework from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a dynamic binary instrumentation (DBI) framework: a runtime engine that takes control of a target process and transparently rewrites its machine code on the fly, inserting analysis/instrumentation (probes) at function entry/exit, basic-block, and instruction granularity — in the spirit of Intel PIN, DynamoRIO, Valgrind, and Frida. The engine JIT-translates the target's code into a code cache of instrumented copies, executes the cache instead of the original, and exposes a probe/analysis API (callbacks invoked at instrumentation points) while preserving the target's observable behavior.

In scope: process attach (ptrace) + library injection; a per-thread code cache of translated traces/basic blocks; trampolines/detours + inline patching for fast probes; an instrumentation API (insert calls at BBL/insn/routine granularity; instrument memory reads/writes, branches, calls/rets); register/flags save-restore around analysis calls; control-flow follow (direct + indirect branch resolution via an indirect-branch lookup table); transparency (the target must not observe the engine — same addresses for its own data, hidden code cache); thread safety (per-thread caches, safe cache invalidation); detach/de-instrumentation. Built on #334 for decoding and #333 for module/symbol info. Primary target: x86-64 user-space Linux; Windows + AArch64 as schedule-permitting tracks behind the same engine API.

Explicit non-goals (each deferral resolves to a row in the Deferred Features Register): kernel-mode/whole-system instrumentation — user-space only — PhaseDeferred("Deferred Features Register"); a new disassembler — decode comes from #334 — PhaseDeferred("Deferred Features Register"); full memory-error detection à la Valgrind Memcheck — the framework is the substrate, shadow-memory tools are a Phase 10 example client with the full tool PhaseDeferred("Deferred Features Register"); source-level/compiler instrumentation (ASan-style) — this is binary instrumentation — PhaseDeferred("Deferred Features Register"); self-modifying-code support beyond detection+cache-invalidation — PhaseDeferred("Deferred Features Register"); AArch64/Windows beyond the seam — PhaseDeferred("Deferred Features Register") (the Arch/Os seams, Appendix P).

Deployment model: a library + instr launcher that either spawns-and-injects (instr -- ./target) or attaches (instr --pid N), loading a user "pintool"-style analysis plugin (a Rust dylib implementing the probe API). Embeds in profilers (#75), sandboxes (#227), debuggers (#74).

Target users: RE / security engineers building tracers, profilers, fuzzers' coverage collectors, and taint engines; performance engineers; learners building the PIN/DynamoRIO core.

Phase 0 deliverable (crates/modules):

  1. ri-types — Probe, InsPoint, CodeCache, Trace, Context, error enum.
  2. ri-attach — process spawn + ptrace attach + library injection.
  3. ri-decode — thin adapter over #334 (Instruction/Cfg) for the translator.
  4. ri-cache — code-cache allocator + lookup (tag → translated block).
  5. ri-engine — the dispatch loop: fetch block → translate (copy) → execute → return to dispatch.
  6. ri (instr) — launcher; runs a target under the engine with a null tool.

Later phases unlock: direct-branch linking (Phase 1), probe API + register save/restore (Phase 2), indirect-branch handling (Phase 3), traces/hot-path optimization (Phase 4), transparency (Phase 5), signals/exceptions (Phase 6), self-modifying-code + cache management (Phase 7), thread safety (Phase 8), attach/detach (Phase 9), example tools (coverage/trace/shadow) (Phase 10), hardening/conformance (Phase 11–12).

Timeline: Phase 0 = 6–14 weeks; full = 6–10 months (transparency + indirect branches + thread safety are the long poles).

Recommended language: Rust (edition 2021, ≥1.78). Rationale: (a) the engine manipulates raw executable memory + another process's state — Rust's safety contains the (unavoidable, isolated) unsafe to audited modules (mmap/mprotect/ptrace) while keeping the rest safe; (b) zero-cost abstractions + no GC are mandatory — instrumentation must add minimal overhead and no unpredictable pauses; (c) it shares the #334 Instruction/Cfg model in one workspace (no serialization); (d) Send/Sync make per-thread code-cache ownership explicit; (e) precise control over codegen for the translated blocks + trampolines. Locked ADR-001. (C is the classic DBI language; Rust gives the same control with containment — justified over C in ADR-001.)

Prerequisites: x86-64 encoding + control flow (#334); virtual memory, mmap/mprotect, page permissions; ptrace, ELF loading, PLT/GOT (#333); calling conventions + register/flags semantics; signals; threads + memory model; JIT/code-patching basics (#51).

2. Why Build This

  • Unique knowledge: how to observe and rewrite a program as it runs without its cooperation or source — the core of profilers, coverage tools, taint trackers, sandboxes, and exploit mitigations. You learn JIT code translation, the code-cache discipline, and the brutal transparency problem (the observer must not change what it observes).
  • Historical/architectural: PIN (Intel), DynamoRIO (MIT/HP), Valgrind (UCAM), and Frida defined modern DBI; this rebuilds their shared engine. The code-cache + dispatch model is also how some JITs and emulators (QEMU TCG) work.
  • Engineering muscles: runtime code generation; register/flag preservation across injected calls; indirect-branch resolution at native speed; cache management + invalidation; cross-thread safety while patching live code; minimizing + measuring instrumentation overhead.
  • Production concepts: transparency, determinism of instrumentation, overhead budgets, safe live-code modification, signal/exception forwarding, attach/detach.
  • Cross-links: #334 Disassembler (decode to translate), #333 ELF/PE (modules/symbols/PLT), #51 JIT (code generation/patching), #74 Debugger (ptrace, breakpoints — the trap-based cousin), #75 Profiler (a primary client), #154 eBPF VM (the in-kernel instrumentation analogue), #50 Sandbox + #227 Malware Sandbox (clients), #229 Fuzzing (coverage client).
  • Calibration: after this you can build any runtime analysis tool, reason about instrumentation overhead + transparency, and understand how perf/pin/drcov/frida actually work under the hood.

What Mastery Looks Like. After building this you can, without reference:

  • Design a software code cache and prove execution never escapes it — the COLD→WARM→HOT→trace→flush lifecycle, the tag→cache_addr map, and the escape invariant (I1) — the skill cemented in Phase 0 (dispatcher) and verified by the escape detector.
  • Eliminate dispatcher overhead with direct-branch linking and reason about its atomicity — when an aligned ≤8-byte store is a safe live patch and when it is not — the muscle built in Phase 1 (linking) and Phase 8 (concurrent patch safety, I8).
  • Preserve a process's exact register/flag/FP state across an injected call under the System V AMD64 ABI, including the red-zone and 16-byte-alignment traps — the competency from Phase 2 (clean calls, I3) and Appendix E.
  • Keep indirect control flow native with an IBL and know why you verify the tag, not the hash — collision-safe in-cache resolution plus a return predictor — earned in Phase 3 (IBL, I6).
  • Solve the transparency problem cold — make a self-inspecting program (reads RIP, walks its stack, parses /proc/self/maps, computes return addresses) behave identically under instrumentation, and articulate the two inherent limits (timing, instruction count) — the defining skill of Phase 5 (transparency, I4) and Phase 6 (signal context, I9).
  • Track self-modifying / JIT-generated code via page write-protection and invalidate safely under concurrency — the SMC fault → flush → re-translate loop with quiescence — built in Phase 7 (I7) and Phase 8 (I8).
  • Attach to and cleanly detach from a live process leaving zero residual patches — the cache↔app side table that maps every cache PC back to an original safe point — the production-trust skill from Phase 9 (I11).
  • Drive and measure instrumentation overhead to a quantified budget — identify the dominant lever (linking → traces → IBL → spill minimization) from profiles and hit-rate telemetry — the calibration of Phase 12 against the §4 envelope.

Per-box: Process control — spawn the target stopped, ptrace it, inject the engine dylib; or attach to a running pid. Dispatcher — the heart: on entry, translate the current tag (block start) if not cached, then jump into the cache; blocks return to the dispatcher (or are linked directly, Phase 1). Translator — decode via #334, copy instructions into the cache verbatim except control flow (redirected to exits) and rip-relative operands (fixed up), with tool-requested probes inserted. IBL — indirect branches (ret/jmp reg/call reg) can't be statically linked → a fast hash lookup keeps execution in the cache. Code cache — executable memory holding translated blocks; direct branches between cached blocks are linked (patched to jump directly) to avoid dispatcher round-trips; hot sequences promote to traces (Phase 4). Probe API — what the tool calls to insert instrumentation; supports efficient inline updates and full clean calls (save state → call tool → restore). State save/restore — preserve the target's registers/flags across tool calls so transparency holds. Transparency + signals + SMC — keep the engine invisible (the target sees its own addresses, not cache addresses), forward signals, detect self-modifying code via write-protection and invalidate stale cache, support clean detach.

6. Design Principles

  1. Transparency above all. The instrumented target must behave identically (addresses, signals, timing-insensitivity aside) to the uninstrumented one. Violation: the target reads a cache address or sees the engine's memory → behavior diverges; "Heisenbug" instrumentation.
  2. Never execute the target's original code. All execution happens in the code cache (translated copies); originals are read-only sources. Violation: a missed branch escapes the cache → uninstrumented execution, lost events, possible crash.
  3. Preserve all register + flag state around analysis. Clean calls spill/refill the full context per the ABI. Violation: clobbering a target register → silent corruption.
  4. Minimize overhead; make the common path native. Direct-branch linking + traces + inline probes keep hot code at near-native speed; the dispatcher is the slow fallback. Violation: a dispatcher round-trip per block → 100× slowdown.
  5. Decode is authoritative (#334). All translation uses #334's decoder + CFG; no ad-hoc parsing. Violation: a mis-decode corrupts the translated block.
  6. Self-modifying / generated code is handled, not ignored. Write-protect translated regions; on write fault, invalidate the affected cache. Violation: the target rewrites code we cached → we run stale instructions.
  7. Thread-local by default. Each thread owns its code cache + scratch; shared structures are explicitly synchronized. Violation: two threads patching one cache → torn code, crash.
  8. Determinism of instrumentation. Given the same target execution, the same probes fire in the same order. Violation: non-reproducible traces → undebuggable analysis.
  9. Bounded, evictable cache. The code cache has a capacity; it evicts/flushes safely rather than growing unbounded. Violation: OOM on a long-running target.
  10. Signals + exceptions are faithfully forwarded. A fault in cached code is reported with the original fault address/context. Violation: the target's signal handler sees a cache address → wrong behavior.
  11. Isolated unsafe. Raw memory, ptrace, and code patching live in audited modules (ri-attach/ri-cache/ri-context); the rest is safe Rust. Violation: UB sprayed across the codebase.
  12. Clean attach + detach. Detaching restores the target to native execution with no residual patches/traps. Violation: a half-removed detour crashes the target after detach.

8. Domain Model

8.1 Core concepts

Tag         := original code address (block start) — the cache key
Block       := translated copy of one basic block (from #334 CFG), ending in a controlled exit
Trace       := a hot sequence of blocks stitched into one straight-line cache fragment (Phase 4)
CodeCache   := per-thread RX mmap region holding Blocks + Traces; tag→addr map
Exit stub   := code at a block's end that returns control to the dispatcher (or is linked)
Link        := a direct-branch exit patched to jump straight to the target block (no dispatch)
IBL         := indirect-branch lookup: hash(app_target)→cache_addr, taken in-cache
CleanCall   := save context → call tool analysis fn (ABI) → restore context
InsPoint    := where a probe attaches: RoutineEnter/Exit | BblEnter | InsBefore/After | MemRead/Write | BranchTaken

8.2 Translation rules (copy-and-patch)

for each insn in block (decoded by #334):
  - non-control, no rip-rel        → copy bytes verbatim
  - rip-relative operand           → rewrite disp so it resolves to the ORIGINAL address (I4)
  - direct jcc/jmp/call            → replace target with an EXIT stub (later LINKED, I5)
  - indirect jmp/call/ret          → replace with IBL sequence (I6)
  - insn matching a tool InsPoint  → emit probe (inline update or clean call, Phase 2)
block terminator → exit stub(tag = fallthrough/target)

8.3 Dispatcher state machine (per thread)

ENTER(tag) → lookup(tag):
   hit  → jump into cache block
   miss → translate(tag) → install in cache → (link predecessor if direct) → jump in
block runs → reaches exit:
   direct exit  → if target cached: LINK (patch to jump direct, future native) ; else dispatch(target)
   indirect exit→ IBL: hash app_target; hit→jump; miss→dispatch(app_target)
   tool/flush/signal → return to dispatcher with saved context

8.4 Clean-call ABI (transparency, I3)

on probe (clean call):
  push volatile + (if needed) all GPRs, RFLAGS, XMM (per ABI + what tool clobbers)
  align stack to 16; set args (InsPoint context: regs snapshot, mem addr, etc.)
  call tool_fn ; on return: restore saved state exactly ; continue in cache
inline probe (fast): e.g. `inc qword [counter]` with only RFLAGS save/restore — no full spill

8.5 Worked example — BBL-count tool

target loop block @0x4011a0 (3 insns, ends `jl 0x4011a0`):
translate → cache block @C: [insn0;insn1;insn2_cmp; INLINE: inc [bbl_count]; exit(jl→0x4011a0)]
first run: dispatch miss → translate → run; exit jl target 0x4011a0 cached? yes → LINK exit to C
subsequent iterations: stay in cache, jump direct C→C, inc counter inline → near-native + count
result: exact basic-block execution count with ~1 inc/block overhead (≤10×, §4)

8.6 Failure / hard-case examples

  • Indirect ret to a not-yet-translated address → IBL miss → dispatcher translates on demand (I6); never returns to original code (I1).
  • rip-relative lea/load → if copied verbatim, reads the cache address (wrong) → must fix disp to original (I4).
  • Target writes to a page holding code we cached (JIT/packer) → write-fault → invalidate that cache region (I7).
  • Signal arrives while in a cache block → must build a siginfo/ucontext with the original PC (I9), not the cache PC.
  • Two threads hit the same cold tag → per-thread caches translate independently (I10) (or shared cache with locking — deferred).
  • Tool callback clobbers a target register without declaring it → context save/restore must cover it (I3); declared clobbers optimize the spill.
  • A block ends mid-page at a permission boundary → translator stops the block at the boundary; next block on fault.

ADR-003 Engine model copy-and-patch code cache + dispatch (DynamoRIO-style) trap-per-insn (ptrace); full emulation speed: native execution of translated code (P4) Trap-per-insn wins for sparse, single-shot probes on a slow path (a debugger conditional breakpoint, the Phase 9 cousin) where translation cost dwarfs the few traps; full emulation (QEMU) wins for cross-ISA execution or when no native execution of target code is permissible (untrusted firmware on a foreign host).
ADR-004 Probe insertion JIT instrumentation (insert at translate time) + inline detours breakpoint traps overhead: traps are ~µs each Breakpoint traps win when probe sites are rare and dynamic (set/cleared at runtime by an interactive operator) and you cannot afford to re-translate — exactly the ptrace int3 model #74 (debugger) uses; one trap on a cold path beats re-JITting a hot trace.
ADR-005 Linking direct-branch linking + IBL for indirect always dispatch the key to low overhead (P4) Always-dispatch wins under aggressive SMC/flush churn (a self-rewriting packer) where links are invalidated faster than they pay back, and as the deliberate instr --no-link debug mode (Phase 1, N.10) that makes every transition observable.
ADR-006 Traces NET (next-executing-tail) hot-path traces no traces (linked blocks only) reduce dispatch + improve i-cache locality (Phase 4) No traces wins on flat, branch-sparse code (a memcpy-bound or vectorized kernel) where blocks are already large and traces only add trace-cache pressure + side-exit complexity; DynamoRIO itself disables traces for some workloads, and instr --no-traces (Phase 4, N.10) isolates trace bugs.
ADR-007 Attach ptrace spawn/attach + dylib injection LD_PRELOAD only works for attach and spawn; injection covers the engine itself (Phase 9) LD_PRELOAD only wins when you control the launch and never need to attach to a running pid — it sidesteps ptrace entirely, so it works under a restrictive YAMA ptrace_scope=2/container where PTRACE_ATTACH is denied.
ADR-008 Code cache mem mmap RX, W^X via dual-map/mprotect toggling single RWX mapping security: never writable+executable simultaneously RWX wins on platforms/kernels without W^X enforcement where the mprotect toggle cost is measurable and the threat model already trusts the host (a closed appliance) — early DBI engines used RWX for the simpler, faster install path.
ADR-009 Context save ABI-aware clean call + declared-clobber optimization save-all-always overhead (P3/P4) Save-all-always wins for an opaque third-party analysis callback whose clobber set is unknown or changes per build — correctness then trumps the spill cost, and a full pushaq/pushfq frame is the only safe contract (the conservative default Pin offers).
ADR-010 SMC write-protect cached pages; fault→invalidate ignore SMC correctness (I7) Ignore SMC wins when the target is provably static (a verified, signed, non-JIT binary) — skipping write-protection removes the per-page fault cost and the protection-granularity over-invalidation entirely, a legitimate --assume-static fast mode.
ADR-011 Threading per-thread code cache + scratch single global shared cache safety + scalability (I10) A shared cache wins for a many-thread target running identical code (a thread-pool worker) where per-thread duplication wastes memory and i-cache; with proper locking + RCU, one cache amortizes translation across all threads — Pin offers a shared-cache mode for this.
ADR-012 Signals intercept + rebuild original-context passthrough (no interception) transparency (I9) Passthrough wins for a target that installs no handlers and never inspects signal context — interception is pure overhead, so a --no-signal-fixup mode is correct when faults simply terminate the process.
ADR-013 Tool API Rust dylib plugin implementing Tool trait embedded scripting (JS/Lua) type-safe, low overhead Embedded scripting wins for interactive exploration / rapid prototyping where recompiling a dylib per change is too slow — Frida's JS API exists for exactly this REPL-style RE workflow, trading per-probe overhead for iteration speed.
ADR-014 ISA seam x86-64 first; Arch trait for arm64/win x86-only (no seam) portability to deferred tracks x86-only wins for a team shipping one platform forever — the Arch indirection adds vtable cost + abstraction tax that a single-ISA engine never recovers; premature portability is a real anti-pattern.
ADR-015 Testing cargo test + golden traces + differential (uninstrumented vs instrumented) unit-only transparency proof (I4/I9) Unit-only suffices for a pure leaf library with no I/O or observable side effects; differential testing pays off only where an external oracle (native execution) exists — for a deterministic pure function it adds harness cost with no new coverage.
ADR-016 Fuzzing cargo fuzz (libFuzzer) on translator (bytes→block) no fuzzing never-crash translate No fuzzing is defensible only when inputs are fully constrained (the translator only ever sees bytes #334 already validated); for a trusted, schema-bounded input a formal proof or exhaustive enumeration beats coverage-guided fuzzing.
ADR-017 Sanitizers Miri on safe code; ASan on the engine harness none UB on the unsafe edges None wins in the shipping hot path — sanitizers carry 2–20× overhead and are CI/dev-only; a release build must run without them, so "none" is correct for the production artifact, not for CI.
ADR-018 Transparency tests self-checks: app reads of PC/stack/maps match native none P1 (the hard part) None is acceptable for a tool that deliberately transforms behavior (an optimizer or a fault-injector) where instrumented≠native is the goal; transparency tests only gate engines that promise invisibility.
ADR-019 CLI clap (instr -- prog / --pid / --tool t.so) bespoke arg parser pin/drrun-like UX A bespoke parser wins for a single-purpose embedded launcher with two fixed flags where clap's binary-size + compile-time cost is unjustified, or where the CLI must match a legacy pin-exact grammar clap cannot express.
ADR-020 CI build+clippy+test+fuzz-smoke+transparency+differential none / manual gates Manual gating wins for a solo research spike where CI infrastructure cost exceeds value before the design stabilizes; automation pays back only once contributors > 1 and the suite is non-trivial.
ADR-021 Bench criterion + SPEC-like micro/macro overhead none / ad-hoc timing §4 overhead targets are the whole product Ad-hoc timing suffices when overhead is not a product requirement (a correctness-only research tool); criterion's statistical rigor matters only when you gate releases on regression thresholds.
ADR-022 Deps minimal, pinned, cargo-deny many convenience crates supply chain Many crates wins under hard delivery deadlines where reuse beats audit cost and the threat model tolerates transitive deps — a throwaway internal tool, not a security primitive that injects into other processes.
ADR-023 Versioning SemVer on Tool/Probe API implicit / no policy tool ecosystem stability Implicit versioning wins for a single-consumer API inside one repo where the engine and its only tool ship together — SemVer's ceremony pays off only with external, independently-released tool authors.
ADR-024 Repro deterministic instrumentation + pinned toolchain floating toolchain I12 (reproducible traces) Floating toolchain wins for bleeding-edge development that must track nightly compiler features; reproducibility-by-pinning trades the latest optimizations for bit-identical rebuilds, which only a release/audit context demands.

Phase 0 — Skeleton, Attach/Inject, Decode Adapter, Code Cache, Dispatcher, Null Tool

0.1 Objectives

Stand up the engine spine: spawn+ptrace a target, inject the engine, translate one basic block (copy-and-patch via #334), install it in an RX code cache, and execute it via the dispatcher — with a null tool. Constraint: the target executes only cached code from the first block (I1).

0.2 Detailed Implementation Steps

Applies: the DynamoRIO software-code-cache + dispatch model (Bruening 2004; Papers #2), ADR-003 (engine model), ADR-008 (W^X cache), P2 (never execute original code), P5 (decode is #334), I1 (only cached code executes), MM1 (cache+miss-handler).

  • ri-attach::spawn: fork+ptrace(TRACEME)+exec the target stopped at entry; inject the engine dylib (or run as a preloaded engine).
  • ri-decode: adapt #334 to decode the block at the current tag → Instruction[] + terminator (P5).
  • ri-translate::block: copy non-control insns; redirect the terminator to an exit stub; (no probes yet).
  • ri-cache: mmap an RX region (W^X via toggle, ADR-008); install(tag, bytes); tag→addr map.
  • ri-engine::dispatch: ENTER(tag)→lookup→(miss)translate+install→jump in; block exit returns to dispatch with the next tag (I1/I2).
  • ri-cli: instr -- ./target runs the target under the engine (null tool), to completion.

0.3 Deliverable

instr -- ./hello runs hello entirely from the code cache and produces identical output to native.

0.4 Acceptance Criteria

  • Output of a set of CLI programs under instr is byte-identical to native (transparency smoke).
  • Every executed instruction came from the cache (escape detector = 0, I1).
  • Dispatcher correctly follows direct branches (via exit→dispatch, unlinked).
  • Fuzz smoke: translator on arbitrary block bytes → no engine crash.

0.5 Conformance Fixtures

Fixture Purpose Expected output

conformance/translate/branch direct jcc/jmp terminator redirected to exit exit returns to dispatcher with correct fallthrough/target tag

0.6 Pitfalls

  • rip-relative not fixed up (I4) → first lea/load reads cache memory → instant divergence; fix disp in Phase 0 even before probes.
  • W^X violation → mapping RWX is a security smell + some kernels refuse; toggle perms around install.
  • Stack/red-zone clobber by the dispatcher → use a private engine stack.
  • PLT/dynamic loader code also runs → must be translated too (don't assume only .text).

0.7 Performance Concerns

Cold path (translate) is µs; hot path here is still dispatch-per-block (slow) until linking (Phase 1). Bound translation cost; reuse the #334 decoder.

0.8 Edge Cases

Static vs dynamic binary (loader code); entry before main (_start, libc init); very small blocks; block crossing a page boundary; immediate exit.

0.9 Failure Analysis

A single escape from the cache (I1) = uninstrumented execution + likely crash → escape detector + native-vs-cached differential gate. Blast radius: whole run.

0.10 Operational Notes

Metrics: blocks_translated, cache_escape(0), dispatch_count, translate_us. instr --stats dumps cache occupancy. Engine logs to a private fd (not the target's).

Phase 1 — Direct-Branch Linking (the overhead killer)

1.1 Objectives

Patch direct-branch exits to jump straight to the target's cached block, eliminating dispatcher round-trips on hot direct control flow (principle 4) — the single biggest overhead reduction.

1.2 Detailed Implementation Steps

Applies: fragment linking (DynamoRIO, Papers #2; cf. QEMU TB chaining, Papers #10), ADR-005 (linking), P4 (make the common path native), I5 (links target live blocks), MM4 (direct → resolve), Appendix G.3 (atomic link protocol).

  • Exit stubs record (from_exit_id, intended_tag).
  • On reaching an exit whose target is cached, cache.link(from, to): patch the exit's jump to the target block's cache address (P4; aligned ≤8B store, Appendix G.3).
  • Lazy linking: link on first traversal; unlink on invalidation (I7).
  • Maintain a reverse map (incoming links) for safe unlinking (I5/I8).

1.3 Deliverable

A tight loop runs almost entirely cache-resident (block→block direct jumps); dispatcher count drops by orders of magnitude.

1.4 Acceptance Criteria

On a loop microbench, post-link slowdown ≤ 1.2× vs native (null tool); dispatcher invocations per loop iteration → ~0 after warmup; links validated (I5).

1.5 Conformance Fixtures

conformance/translate/link_loop, benchmarks/overhead/linked_loop, link-table integrity fixture.

1.6 Pitfalls

  • Linking to a stale/evicted block (I5) → patch to a freed address → crash; check liveness + reverse map before link.
  • Atomic patching of a live jump on another thread → use safe patch sequences (I8).
  • Conditional branches have two exits (taken/fall) → link both independently.
  • Self-loop linking edge case (block jumps to itself).

1.7 Performance Concerns

Linked direct branch ≈ native (one jmp). Lazy linking amortizes; reverse map enables O(1) unlink.

1.8 Edge Cases

Branch into the middle of an existing block (different tag → new block); link target not yet translated (translate then link); cross-module branches.

1.9 Failure Analysis

A bad link is a wild jump → crash. Liveness check + integrity fixture gate it; reverse map enables clean unlink on flush.

1.10 Operational Notes

Metrics: links_made, dispatch_count (should plummet), bad_link(0). instr --no-link for debugging (forces dispatch every block).

Phase 2 — Probe API + Register/Flags Save-Restore (clean calls + inline)

2.1 Objectives

Let a Tool insert instrumentation at translate time: full clean calls (save context → call tool fn → restore, I3) and fast inline ops (e.g., counter increments with only flag spill). Transparency of target state is the hard requirement.

2.2 Detailed Implementation Steps

Applies: Pin's instrument-at-translate-time API + register management (Luk et al. 2005, Papers #1), the System V AMD64 ABI (§5 Specs), ADR-004 (JIT instrumentation), ADR-009 (clean call + declared-clobber), P3 (preserve register+flag state), I3 (full context preserved), MM3 (instrumentation is a translate-time function), Back-of-Envelope #11 (spill cost).

  • ri-probe: Tool::on_block receives a BlockInfo + Instrumenter; tool requests probes at InsPoints (Pin-style, Papers #1).
  • ri-translate::probe_emit: at each requested point, emit either an inline op or a clean-call sequence (MM3).
  • ri-context::cleancall: spill GPRs+RFLAGS(+XMM if declared), align stack to 16B, set args (a Context), call tool fn, restore exactly (P3/I3; ABI).
  • Declared-clobber optimization: tool declares which regs it touches → spill only those (ADR-009).

2.3 Deliverable

A callcount tool counts routine entries; a bblcount tool counts blocks — both via inserted probes, output correct, target unperturbed.

2.4 Acceptance Criteria

Instrumented run output identical to native (I3 transparency held); counts correct vs a known workload; clean-call context checksum unchanged across the call; inline path adds ≤ 1 op overhead.

2.5 Conformance Fixtures

conformance/transparency/ctx_preserved, tools/{callcount,bblcount} golden counts, clobber-optimization fixture.

2.6 Pitfalls

  • Forgetting RFLAGS (even inline inc sets flags!) → save/restore flags around inline ops (I3).
  • Red zone (128B below rsp) clobbered by the spill → adjust rsp first / use engine scratch.
  • XMM/AVX state if the tool uses FP → declare + save.
  • Stack alignment (16B at call) → align before clean call.

2.7 Performance Concerns

Inline ≫ clean call; declared clobbers shrink spills. Place probes to minimize saved state. Clean call is the heavyweight path (use sparingly).

2.8 Edge Cases

Probe at a block that itself manipulates flags/stack; nested tool state; tool that reads but doesn't write regs (read-only context, cheaper).

2.9 Failure Analysis

A clobbered register = silent target corruption (the classic DBI bug) → context-checksum fixture (snapshot regs before/after) gates it.

2.10 Operational Notes

Metrics: clean_calls, inline_probes, ctx_clobber(0), bytes_spilled. Tool API doc warns about clobber declaration. instr --verify-ctx enables per-call checksums (debug).

Phase 3 — Indirect Branch Handling (IBL) + ret/call reg/jmp reg

3.1 Objectives

Keep execution in the cache across indirect branches (returns, call reg, jmp reg, jump tables) via a fast indirect-branch lookup (IBL), since their targets can't be statically linked (I6).

3.2 Detailed Implementation Steps

Applies: indirect-branch handling in dynamic optimizers (Kim & Smith 2003, Papers #7), ADR-005 (IBL for indirect), I6 (IBL returns the verified target), MM4 (indirect → look up), MM5 (verify the tag, not the hash), MM8 (call pushes app return address), Back-of-Envelope #8–#9 (IBL ceiling + sizing).

  • Replace each indirect terminator with an IBL sequence: compute app target → hash → probe a per-thread hash table (app_target→cache_addr) → hit: verify tag then jump; miss: dispatcher (translate + insert) (I6/MM5).
  • Maintain the IBL table; populate on translation; size for load factor ≤0.5 (Back-of-Envelope #9).
  • Special-case returns with a per-thread return cache / shadow (RSB-like) for the common call/ret pattern (MM8).

3.3 Deliverable

Programs with heavy virtual dispatch / deep call stacks run cache-resident; IBL hit-rate high; output correct.

3.4 Acceptance Criteria

IBL hit-rate ≥ 95% on a call-heavy workload after warmup; indirect targets always resolve to the correct cached copy (I6); slowdown bounded (§4).

3.5 Conformance Fixtures

Fixture Purpose Expected output
conformance/translate/ret a function return routes through IBL/return cache resolves to the cached caller block; never escapes (I1/I6)
conformance/translate/call_reg call reg (function pointer) IBL resolves target → cached copy; output identical
conformance/translate/jmp_table a switch compiled to a jump table each case target translated on demand; correct branch taken
conformance/translate/vtable_dispatch C++ virtual dispatch (indirect through vtable) each concrete method translated; IBL hit-rate ≥ 95% after warmup
conformance/translate/ibl_collision two app targets that hash to the same slot tag-verify rejects the wrong one (I6); both resolve correctly (MM5)
conformance/translate/setjmp_longjmp stack-jumping control flow resumes in cache at the longjmp target; no escape

3.6 Pitfalls

  • IBL returning the wrong block (hash collision mishandled) → must verify the tag, not just hash (I6).
  • Returns are hot → a generic IBL is slow; add a return-target predictor.
  • Tail calls (jmp reg) vs returns distinction.
  • Mixing app and cache addresses in the indirect target (must translate app→cache).

3.7 Performance Concerns

IBL hot path ≤ 20 ns (inlined hash + compare). Return cache cuts the common case further. Collisions handled with tag verify (correctness over speed).

3.8 Edge Cases

Setjmp/longjmp (stack-jumping); signal returns; computed gotos; PLT lazy resolution (indirect through GOT); exception unwinding.

3.9 Failure Analysis

A wrong indirect resolution = jump to the wrong code = corruption/crash → tag-verify (I6) + differential gate; collisions fall back to dispatch.

3.10 Operational Notes

Metrics: ibl_hits/ibl_misses, ibl_miss_wrong(0), ret_cache_hit. instr --stats shows IBL hit-rate (a key health signal).

Phase 4 — Traces / Hot-Path Optimization (NET)

4.1 Objectives

Reduce dispatch + enable cross-block optimization by stitching frequently-executed block sequences into single straight-line traces (Next-Executing-Tail selection, Dynamo/DynamoRIO), so hot paths avoid even link hops and expose inlining of probes.

4.2 Detailed Implementation Steps

Applies: NET trace selection (Bala et al. 2000 Dynamo, Papers #4; Bruening 2004, Papers #2), ADR-006 (NET traces), P4 (make the common path native), MM1 (miss elimination), MM9 (side exits fall back to blocks), Back-of-Envelope #2/#20 (trace-cache headroom under the 16× ceiling).

  • Add execution counters at block entries (or at link points); when a tag exceeds a hotness threshold, start trace formation (NET, Papers #4).
  • NET: follow the actually-taken path from the hot head, inlining successor blocks into one trace fragment until a stop condition (backward branch to head, indirect, length cap).
  • Place the trace in a separate trace cache; redirect the head to the trace; embed an IBL/exit at the trace tail (side exits fall back to blocks, MM9).
  • Optionally re-run tool instrumentation across the trace for cross-block probe optimization (P4).

4.3 Deliverable

Hot loops/paths execute as single trace fragments; dispatch + inter-block jumps drop further; measurable overhead reduction over linking alone.

4.4 Acceptance Criteria

On a hot-loop benchmark, traces cut remaining dispatch/IBL by ≥ 50% vs linking-only; output unchanged (transparency); trace tails resolve correctly.

4.5 Conformance Fixtures

conformance/traces/{net_loop,hot_path}, benchmarks/traces/*, trace-correctness differential.

4.6 Pitfalls

  • Trace explosion (every path becomes a trace) → hotness threshold + length cap + trace cache budget.
  • Mid-trace exits (early-exit blocks) → side exits must restore state + leave correctly.
  • Stale traces after SMC/flush (I7) → invalidate traces with their constituent blocks.
  • Over-aggressive inlining of cold tails into hot traces → NET stops at the head's back-edge.

4.7 Performance Concerns

Traces amortize dispatch + improve i-cache locality (hot code contiguous). Trade cache space for speed; bound trace-cache size.

4.8 Edge Cases

Loops with multiple hot paths; recursion; traces spanning calls (inline or stop?); indirect mid-trace.

4.9 Failure Analysis

A wrong side-exit corrupts state → trace-correctness differential + state checks at side exits. Trace bugs are bounded to hot paths but high-impact.

4.10 Operational Notes

Metrics: traces_built, trace_cache_bytes, side_exits, trace_hit_rate. instr --no-traces isolates trace bugs (falls back to linked blocks).

Phase 5 — Transparency: PC / Stack / Maps Views, Address Hiding

5.1 Objectives

Make the engine invisible: whenever the target observes its own PC, stack, or memory map, it must see original addresses and its own layout — never code-cache addresses or engine memory (principle 1, the defining DBI challenge).

5.2 Detailed Implementation Steps

Applies: the DynamoRIO transparency taxonomy (Bruening 2004, Papers #2; Bruening et al. 2012, Papers #9) and libdetox hardening (Payer & Gross 2011, Papers #8), P1 (transparency above all), ADR-018 (transparency tests), I4 (target never sees a cache address), MM2 (cache is a hidden shadow), MM8 (return addresses are app addresses), Appendix H (the transparency matrix).

  • PC transparency: any instruction reading RIP (rip-relative already fixed in Phase 0; call/lea/mov of return addresses) must produce the original address (I4) — return addresses pushed by call are app addresses, not cache (MM8).
  • Stack transparency: the app stack holds app return addresses; the engine uses a separate scratch stack for its own work (P1).
  • /proc/self/maps, auxv, getauxval, signal contexts: intercept so the target sees its own modules, not the engine's code cache mappings (I4).
  • Hide engine modules/threads from target introspection where feasible (MM2).

5.3 Deliverable

Self-checking targets (programs that read their own PC, walk their stack, parse /proc/self/maps, or compute return addresses) behave identically under instr.

5.4 Acceptance Criteria

A transparency test-suite (PC reads, stack unwinding, maps parsing, return-address checks) passes under instrumentation; no cache address ever leaks to the target (I4, pc_leak=0).

Fixture Purpose Expected output
conformance/transparency/read_pc target reads RIP via lea/call observed PC = original address, never a cache address (I4)
conformance/transparency/stack_walk target walks its own call stack (unwinder) every frame's return address is an app address
conformance/transparency/proc_maps target parses /proc/self/maps cache region filtered out; only the target's own modules visible
conformance/transparency/return_addr target computes/compares a return address matches native; ret still resolves into the cache via IBL
conformance/transparency/getauxval target reads auxv/getauxval app values returned; engine mappings hidden
conformance/transparency/pic_base PIC computes its own load base base = app base (rip-rel fixup); pc_leak = 0

5.6 Pitfalls

  • call pushes a cache return address → must push the app address so ret/stack-walk see app code (I4); IBL translates it back on return.
  • Exception/unwind tables (.eh_frame) reference app addresses → faults must map cache→app.
  • /proc/self/maps revealing the cache region → filter it.
  • Timing/instruction-count transparency is impossible (documented limit).

5.7 Performance Concerns

Transparency fixups (esp. call return-address translation) add overhead on call/ret → the return cache (Phase 3) + careful codegen minimize it.

5.8 Edge Cases

Hand-written unwinders; backtrace(); JITs in the target that read their own PC; position-independent code computing its base.

5.9 Failure Analysis

A single leaked cache address can crash or mislead a self-aware target → the transparency suite is the gate; pc_leak must be 0. This is the hardest correctness area.

5.10 Operational Notes

Metrics: pc_leak(0), maps_intercepts, retaddr_fixups. Documented limits (timing, exact instruction counts) in docs/internals/transparency.md. instr --transparency-check runs self-tests.

Phase 6 — Signals & Exceptions: Faithful Forwarding

6.1 Objectives

Deliver signals (and CPU exceptions/faults occurring in cached code) to the target's handlers with the original fault address + register context, so the target's signal handling is unaffected (I9).

6.2 Detailed Implementation Steps

Applies: transparent signal delivery in DBI (Bruening et al. 2012, Papers #9), Kerrisk TLPI signal model (Books #6), ADR-012 (intercept + rebuild context), P10 (signals faithfully forwarded), I9 (signals carry original context), MM2 (ground-truth addresses), Appendix G.1 (cache→app side table).

  • Install engine signal handlers; on a signal while in the cache, build a ucontext whose PC + regs reflect the original (app) state, not the cache state (I9/P10).
  • Forward to the target's registered handler under engine control; on sigreturn, resume in the cache at the right tag.
  • Handle synchronous faults (SIGSEGV/SIGFPE/SIGILL) in cached code: map the faulting cache address back to the app address via the side table (I9; Appendix G.1).
  • Track the target's sigaction/sigprocmask so the engine mirrors its signal disposition (ADR-012).

6.3 Deliverable

Targets that install handlers (SIGSEGV recovery, SIGALRM timers, etc.) work identically; faults report original addresses.

6.4 Acceptance Criteria

Signal-handler tests pass (handler sees original PC + correct siginfo); synchronous faults map cache→app (I9, signal_ctx_wrong=0); sigreturn resumes correctly.

6.5 Conformance Fixtures

conformance/signals/{sigsegv_handler,sigalrm,sigaction_track,fault_in_cache,longjmp}.

6.6 Pitfalls

  • Reporting a cache PC to the handler (I9) → handler logic breaks; rebuild app context.
  • Reentrancy (signal during translation/dispatch) → engine-internal vs app signal masking.
  • sigreturn must resume in the cache, not the app code.
  • Nested signals + alternate signal stacks (sigaltstack).

6.7 Performance Concerns

Signals are rare → correctness over speed; the per-block cache→app mapping (a side table) makes fault translation O(log n).

6.8 Edge Cases

Fault inside a clean call (engine vs app frame); signal during a partially-executed block; SA_SIGINFO vs legacy; real-time signals.

6.9 Failure Analysis

Wrong signal context = broken target error handling (e.g., a GC or JIT relying on SIGSEGV) → signal fixtures gate it. Blast radius: any handler-using target.

6.10 Operational Notes

Metrics: signals_forwarded, faults_in_cache, signal_ctx_wrong(0). docs/internals documents the context-rebuild. A cache→app address side table aids postmortems.

Phase 7 — Self-Modifying / Generated Code + Code-Cache Management

7.1 Objectives

Stay correct when the target writes code (JITs, packers, trampolines) by detecting writes to cached regions and invalidating stale cache (I7); and keep the code cache bounded via safe eviction/flush (I8, principle 9).

7.2 Detailed Implementation Steps

Applies: code-cache management + capacity (Hazelwood & Smith 2006, Papers #6), ADR-010 (write-protect → invalidate), P6 (SMC handled, not ignored), P9 (bounded, evictable cache), I7 (write to cached code invalidates), I8 (safe flush under concurrency), MM6 (page protection as SMC tripwire), MM7 (freeing code is concurrent reclamation), Back-of-Envelope #10 (SMC fault cost), Appendix O (worked SMC trace).

  • SMC detection: write-protect pages that back translated code; on write-fault, flush cache entries derived from that region, then allow the write + re-translate on next execution (I7/MM6).
  • Cache capacity management: per-thread budget; eviction policy (e.g., flush-all or region-based) when full; rebuild lazily (P9).
  • Safe flush (I8): ensure no thread is executing a block being freed (quiescence / link removal first via the reverse map, MM7).

7.3 Deliverable

A target that generates/patches code at runtime (a tiny JIT) executes correctly under instr; long-running targets stay within the cache budget.

7.4 Acceptance Criteria

SMC test: target patches code → engine re-translates → correct output (I7); cache stays ≤ budget under a code-churning workload; no use-after-free on flush (I8).

7.5 Conformance Fixtures

conformance/smc/{self_patch,jit_target,trampoline}, cache/{capacity_evict,flush_safe}.

7.6 Pitfalls

  • Write to a cached page not detected (I7) → run stale code; must write-protect all cached source pages.
  • Granularity: page-level protection over-invalidates (a data write near code) → re-translate cost; acceptable, but measure.
  • Flushing a linked-into block → unlink all incoming links first (reverse map, Phase 1) before free (I8).
  • Executing thread on a flushed block → quiescence barrier.

7.7 Performance Concerns

SMC protection adds fault cost on first write per page; rare for normal code, frequent for JITs (documented overhead). Eviction trades re-translation for memory.

7.8 Edge Cases

Mixed code+data on a page; W^X targets toggling perms themselves; mprotect by the target on its own code; trampoline rewriting.

7.9 Failure Analysis

Stale-cache execution (I7) = wrong behavior, silent → SMC fixtures + write-protection invariant gate it. Unsafe flush (I8) = crash → quiescence test.

7.10 Operational Notes

Metrics: smc_events, cache_flushes, cache_bytes, unsafe_flush(0). instr --cache-size N tunes budget. SMC frequency is a target-classification signal (packers/JITs).

Phase 8 — Thread Safety: Per-Thread Caches, Thread Creation, Safe Sharing

8.1 Objectives

Support multi-threaded targets: each thread gets its own code cache + scratch (I10); thread creation (clone/pthread_create) is intercepted to bring new threads under the engine; shared structures (IBL tables, module map) are synchronized.

8.2 Detailed Implementation Steps

Applies: ADR-011 (per-thread cache + scratch), P7 (thread-local by default), I8 (safe flush under concurrency), I10 (per-thread isolation), MM7 (concurrent reclamation), MM10 (isolation trades sync for memory), Back-of-Envelope #3–#4 (per-thread + 8-thread footprint), Appendix L.4 (fork/clone semantics).

  • Intercept thread creation (clone): new threads start under the dispatcher with a fresh per-thread cache + scratch stack (I10).
  • Per-thread: code cache, IBL table, return cache, context-save area (MM10).
  • Shared (read-mostly): module/symbol map, tool state (tool must be Send/thread-aware) — synchronized via RCU/rwlock (ADR-011).
  • Safe cross-thread cache flush (Phase 7) with quiescence (I8/MM7).

8.3 Deliverable

A multi-threaded target runs under instr with correct per-thread instrumentation; no cross-thread cache execution; output correct.

8.4 Acceptance Criteria

A pthreads workload produces identical output + correct per-thread counts; no cross-thread exec (I10, cross_thread_exec=0); flush under concurrency is safe (I8); no data races (TSan/loom on shared structures).

8.5 Conformance Fixtures

conformance/threads/{pthreads_count,clone_intercept,concurrent_flush,shared_lib}.

8.6 Pitfalls

  • A new thread escaping into uninstrumented code before the engine grabs it → intercept at clone precisely (I10).
  • Sharing one cache across threads (race) → per-thread by default (I10).
  • Tool state races → document the Tool threading contract; provide per-thread tool slots.
  • TLS + the engine's own thread-local scratch.

8.7 Performance Concerns

Per-thread caches scale linearly but cost memory (×threads); shared read-mostly maps use RCU/rwlock. Flush coordination is the contention point.

8.8 Edge Cases

Thread exit (free its cache); thread pools; fork() in a threaded program; detached threads; signals to specific threads.

8.9 Failure Analysis

A cross-thread cache exec or a torn shared structure = crash/corruption → loom/TSan on shared paths + the cross-thread invariant gate it.

8.10 Operational Notes

Metrics: threads_tracked, cross_thread_exec(0), per_thread_cache_bytes. Tool docs specify the threading contract. instr --threads reports per-thread stats.

Phase 9 — Attach-to-Running + Clean Detach / De-instrumentation

9.1 Objectives

Attach to an already-running process and bring it under the engine, and cleanly detach so the target resumes native execution with no residual patches/traps (I11, principle 12).

9.2 Detailed Implementation Steps

Applies: ptrace attach/detach (Love LSP, Books #5; Kerrisk TLPI, Books #6), Frida attach ergonomics (Papers reference; frida-gum, Ref-impl #4), ADR-007 (ptrace spawn/attach), P12 (clean attach + detach), I11 (detach removes all patches), MM2 (resume at an original safe point), Appendix G.1 (cache→app side table).

  • Attach: ptrace(ATTACH)/seize a running pid, stop all threads, inject the engine, redirect each thread's PC into the dispatcher at its current tag (ADR-007).
  • Detach: stop threads, restore each thread to execute the original code at the app PC corresponding to its current cache position, remove injected hooks/trampolines, unmap (or leave dormant) the cache, ptrace(DETACH) (I11/P12).
  • Cache→app PC mapping (the side table from Phase 6) drives the resume-at-original step (MM2; Appendix G.1).

9.3 Deliverable

instr --pid N --tool t.so attaches to a live process, instruments it, and --detach returns it to native execution still running correctly.

9.4 Acceptance Criteria

Attach mid-execution → correct instrumentation; detach → target continues natively, no residual traps (I11, residual_patch=0), no crash; threads resume at correct original PCs.

9.5 Conformance Fixtures

conformance/{attach_running,detach_clean,detach_midblock,reattach}.

9.6 Pitfalls

  • Detaching mid-block → the app PC must map to a block boundary; resume only at safe points (cache→app mapping).
  • Residual inline detours/trampolines left after detach (I11) → full unpatch scan.
  • Thread in a syscall at attach/detach → handle interrupted syscalls.
  • Lost signals during the stop window.

9.7 Performance Concerns

Attach/detach are one-time, correctness-dominated. The cache→app side table makes safe-point resume O(log n).

9.8 Edge Cases

Attach to a multi-threaded process (stop all); target in clone/fork at attach; detach while in a clean call; process exits during attach.

9.9 Failure Analysis

A residual patch after detach (I11) = delayed crash → residual-scan + detach fixtures gate it; this is the trust requirement for production attach.

9.10 Operational Notes

Metrics: attach_threads, residual_patch(0), detach_ms. Runbook attach-detach.md. Detach must be idempotent + safe under signals.

Phase 11 — Hardening: Translator Fuzzing, Transparency Suite, Differential

11.1 Objectives

Guarantee the translator never crashes on arbitrary code (robustness), the transparency suite stays green (the hardest correctness), and instrumented≡native output across a corpus (differential).

11.2 Detailed Implementation Steps

Applies: ADR-015 (differential), ADR-016 (fuzzing), ADR-017 (sanitizers), I3/I4/I6/I9 (the correctness invariants under test), I12 (determinism), MM9 (every accelerator has a verifiable fallback), Hard Questions #2/#14 (fuzzing surfaces tag/side-exit bugs).

  • cargo fuzz (libFuzzer): translate(bytes) + ibl targets; seed from real .text (ADR-016).
  • Transparency suite (Phase 5/Phase 6 fixtures) as a CI gate (I4/I9).
  • Differential: run a corpus native vs under instr (null tool + each example tool); assert identical output + exit + signals (ADR-015).
  • Miri on safe code; ASan on the engine harness; loom on shared structures (ADR-017; I8/I10).

11.3 Deliverable

Green CI: build+clippy+test+fuzz-smoke+transparency+differential; a soak target list.

11.5 Conformance Fixtures

11.9 Failure Analysis

Compatibility Guarantees

SemVer (ADR-023) on the public Tool trait, InsPoint, Context, Action/InlineOp, and the Engine lifecycle API. Rules: additive InsPoints / Actions / Context accessors via #[non_exhaustive] → minor; trait-method signature change / removed accessor / changed clean-call ABI contract → major. Engine internals (cache layout, IBL hashing, trace format) are private + freely changeable. The drcov coverage format + trace log formats are versioned independently (downstream fuzzers/tools parse them). Tools are recompiled against an API major version; the clean-call/clobber contract is part of the stable ABI. New ISAs (arm64/win) appear as Arch implementations behind the same Tool API → minor. The framework pins #333/#334 at compatible majors.

Testing Strategy

  • Unit — translator per-instruction fixups (rip-rel, direct/indirect terminators), IBL hashing, context save/restore, cache link/unlink/flush.
  • Transparency suite (the core gate) — PC reads, stack unwinding, /proc/self/maps, return addresses, signal contexts: instrumented ≡ native (I4/I9).
  • Differential — a corpus run native vs under instr (null + each tool): identical stdout/stderr/exit/signals (transparency).
  • Property (proptest) — translator: any block bytes → valid translated block or typed reject, never engine crash; IBL: lookup returns the verified target or miss (I6).
  • Concurrency (loom + TSan) — cache flush vs execution (I8), shared-map access, thread-creation interception (I10).
  • Fuzzing (cargo-fuzz) — translate/ibl; ASAN on the engine harness.
  • SMC/signals — self-patching + handler fixtures (I7/I9).
  • Attach/detach — residual-patch scan after detach (I11).
  • Overhead regression (criterion) — micro/macro overhead vs §4.
  • Soak — hours-long, multi-threaded, JIT-heavy targets: bounded cache, no leak, correct output.

Weighting is dominated by transparency + differential: a framework that changes what it observes is worse than useless, so instrumented≡native is gated on every change.

Performance Engineering

Benchmarks (criterion + a SPEC-like macro set): null-tool overhead (loops, calls, indirect-heavy, JIT), per-tool overhead, IBL/trace/link hit-rates, dispatch cost. Profiling: the engine profiles itself (and dogfoods its own coverage tool). Hot levers, in impact order: (1) direct-branch linking (Phase 1) — turns dispatch into a jmp; (2) traces (Phase 4) — i-cache locality + fewer hops; (3) IBL + return prediction (Phase 3) — keeps indirect control in-cache; (4) clean-call/spill minimization (Phase 2) — declared clobbers, inline ops; (5) W^X toggle cost + SMC protection granularity (Phase 7). Scalability Analysis

The unit is a process; scaling within is per-thread caches (linear with threads, at memory cost). Bottlenecks: (1) indirect-heavy targets (interpreters, C++ virtual dispatch) stress the IBL — return prediction + good hashing are essential; (2) JIT/SMC targets stress invalidation — protection granularity is the lever; (3) many-threaded targets multiply cache memory — shared read-mostly maps (RCU) + per-thread bounded caches; (4) cold-start translation cost on huge codebases — amortized + cache-bounded. Ceilings: code-cache memory scales with unique executed code × threads (bounded + evictable, so it plateaus); the engine adds O(1) overhead per process, not per syscall/IO. No cross-process coordination. The design scales to large, long-running, multi-threaded targets precisely because the cache is bounded and per-thread.

Mental Models & First Principles

The compressed insights an expert holds about a DBI engine. Each: the model, what it predicts, the bug class you write without it, and the resolving section.

  • MM1 — The code cache is a write-back cache over the target's .text; the dispatcher is its miss handler. Predicts: every transition is either a cache hit (in-cache jump/link) or a miss (dispatch → translate → install); steady-state cost ≈ miss-rate × translate-cost, so the entire optimization story is miss elimination (link, IBL, trace). Without it: you treat translation as a one-time setup and never budget the cold-miss tail, then watch a phase-changing program (new code regions) stall periodically. Resolves in: §3 Architectural Overview, Phase 0, Phase 1.
  • MM2 — The target's address space is the ground truth; the cache is a hidden shadow that must never leak. Predicts: any value the target can observe (a PC via lea/call, a return address on the stack, a /proc/self/maps line, a signal ucontext) must read the original address, while execution silently happens in the shadow. Without it: the classic Heisenbug — a self-checking program (PIC base computation, stack unwinder, GC) diverges only under instrumentation. Resolves in: Phase 5 (transparency, I4), Phase 6 (signal context, I9), Appendix H.
  • MM3 — Instrumentation is a function inserted at translate time, not execute time. Predicts: the cost of a probe is paid once at translation (code-size growth) plus per-execution (the inserted op); a clean call's expense is the spill frame, not the call. Without it: you reach for per-instruction traps (Pin's rejected int3 path) and eat microseconds per probe instead of nanoseconds. Resolves in: Phase 2 (probe API), ADR-004.
  • MM4 — Direct branches can be resolved (linked) but indirect branches can only be looked up. Predicts: a direct jcc/jmp/call has a statically known target → patch it once to a cache address (link); a ret/jmp reg/call reg has a runtime target → it needs a per-execution hash probe (IBL) that verifies the tag. Without it: you either try to "link" an indirect branch (impossible, wild jump) or dispatch every direct branch (100× slowdown). Resolves in: Phase 1 (linking, I5), Phase 3 (IBL, I6).
  • MM5 — Verify the tag, not the hash. Predicts: an IBL hash collision returns a plausible but wrong cache address; only comparing the stored app-target tag to the requested one keeps correctness; the hash is just a bucket index. Without it: a collision sends execution into the wrong function — silent corruption that fuzzing surfaces only probabilistically. Resolves in: Phase 3 (I6), Appendix G.4.
  • MM6 — Page protection is the only cheap SMC tripwire you have. Predicts: you cannot watch every store; you remove write permission from pages backing cached code and let the MMU fault tell you when the target rewrites code — at page granularity, so code+data on one page over-invalidates. Without it: a JIT or packer patches a function and the engine keeps running the stale cached copy — a behavior-changing bug with no crash (Appendix O is built around this). Resolves in: Phase 7 (I7).
  • MM7 — Freeing cached code is a concurrent-reclamation problem, not a free(). Predicts: another thread may be executing inside the block you want to flush; you must first repoint all incoming links (reverse-link map) to the dispatcher, then reach a quiescent state where no thread's PC is in the region, then free. Without it: use-after-free on the hottest possible memory — executable code another core is running. Resolves in: Phase 7 (flush), Phase 8 (quiescence, I8).
  • MM8 — A call pushes a return address, and that address is read by ret, by unwinders, and by the program itself — so it must be the app address, not the cache address. Predicts: you cannot naively let the translated call push the cache-side return PC; you push the app return address and rely on the IBL/return-cache to map it back to a cache block on ret. Without it: ret escapes the cache (or returns to the wrong place) and stack walks see cache addresses (I4 violation). Resolves in: Phase 3 (return cache), Phase 5 (return-address transparency).
  • MM9 — The engine always has a correct slow path; every optimization is an accelerator with a fallback. Predicts: linking falls back to dispatch, IBL miss falls back to dispatch, a trace side-exit falls back to a block, SMC falls back to re-translate — so a bug in any accelerator degrades performance, not correctness, if the fallback is wired. Without it: an optimization with no fallback turns a perf bug into a correctness bug (a wild jump). Resolves in: Failure Modes and Recovery, Phase 4 (side exits).
  • MM10 — Per-thread isolation converts a concurrency problem into a memory-cost problem. Predicts: giving each thread its own cache + IBL + scratch removes almost all cross-thread synchronization (the remaining shared state is read-mostly: module map), trading RAM (×threads) for the absence of locks on the hot path. Without it: you share one cache and pay a lock on every install/link, or worse, race and tear live code. Resolves in: Phase 8 (I10), Scalability Analysis.

Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived step-by-step from the §4 System Constraints table (and the per-structure sizes in Appendix R). Formula shown; assumptions stated.

Baseline assumptions (from §4 + Appendix R): avg basic block ≈ 6 x86-64 instructions ≈ 24 original bytes; translation expansion ≈ 1.5× code + exit stubs; code-cache ceiling ≤16× instrumented code (§4); translation ≤5 µs/block (§4); dispatcher round-trip ≤200 ns (§4); IBL hot ≤20 ns (§4).

  1. Translated bytes per block. block_bytes = orig_bytes × expansion + exit_stub = 24 × 1.5 + 16 ≈ 52 B/block. → a block costs ~52 bytes of RX cache.
  2. Code-cache size for a working set. cache = unique_blocks × block_bytes. For a 1 MB hot .text ≈ 1 MB / 24 B ≈ 43.7k blocks → 43.7k × 52 B ≈ 2.27 MB. Check against §4's ≤16× rule: instrumented code ≈ 1 MB × 1.5 = 1.5 MB; 2.27 MB ≈ 1.5× the original — well under the 16× ceiling (which budgets for probes + traces + stubs).
  3. Per-thread total cache memory. per_thread = cache + tables. Tables (Appendix R): tag→addr ≈ 43.7k × 16 B ≈ 0.70 MB; cache→app ≈ 43.7k × 16 B ≈ 0.70 MB; reverse-link ≈ (links≈1.5/block) × 43.7k × 8 B ≈ 0.52 MB; IBL table (next pow-2 ≥ working set, say 64k slots × 16 B) ≈ 1 MB. → per_thread ≈ 2.27 + 0.70 + 0.70 + 0.52 + 1.0 ≈ 5.2 MB.
  4. 8-thread footprint. total = per_thread × threads = 5.2 MB × 8 ≈ 41.6 MB. → a large multi-threaded target instruments in tens of MB; this is the number that decides whether per-thread caches are affordable (MM10) — they are.
  5. Cold-start translation time. warmup = unique_blocks × translate_cost = 43.7k × 5 µs ≈ 0.22 s per thread, one-time. → first-touch latency on a 1 MB working set is sub-second; amortized to ~0 in steady state (MM1).
  6. Dispatch overhead if unlinked. cost = transitions/s × round_trip. A loop doing 10⁸ block-transitions/s × 200 ns = 2.0 × 10¹⁰ ns/s = 20× real time → 20× slowdown — quantifies why linking (Phase 1) is mandatory, not optional.
  7. Dispatch overhead after linking. Linked direct branch ≈ 1 jmp ≈ ~1 ns; 10⁸ × 1 ns = 0.1 s/s ≈ near-native → matches §4's ≤1.2× linked-loop target. The lever between #6 and #7 is the entire value of the engine.
  8. IBL throughput ceiling. max_indirect/s = 1 / ibl_hot = 1 / 20 ns = 5 × 10⁷ indirect branches/s per thread before IBL alone bounds you → an interpreter doing one indirect dispatch per bytecode tops out near 50M bytecodes/s/thread on the IBL path (why interpreters are the §4 worst case at 5–10×).
  9. IBL hash-table sizing. For load factor ≤0.5 and a working set of W indirect targets, slots = next_pow2(2W). For W = 20k call sites: slots = 64k, mem = 64k × 16 B = 1 MB (matches #3). → load factor 20k/64k ≈ 0.31, keeping probe chains short (correctness-preserving, MM5).
  10. SMC fault cost (JIT target). smc_overhead = rewrites/s × (fault + flush + retranslate). A JIT regenerating 100 functions/s, each ~10 blocks: 100 × (fault≈3 µs + 10 × 5 µs translate) ≈ 100 × 53 µs ≈ 5.3 ms/s ≈ 0.5% → SMC is cheap for moderate JITs; a pathological packer rewriting MB/s is the documented worst case (Phase 7, N.7).
  11. Clean-call spill cost. Full frame = 15 GPRs + RFLAGS + (optional 16 XMM): ~16 × 8 B + 16 × 16 B = 384 B of stack traffic per call; at ~1 ns/8 B ≈ ~48 ns plus call/ret ≈ ~60–80 ns/clean-call → quantifies why hot probes must be inline (Phase 2) not clean calls (a per-block clean call at 10⁸/s = 6–8× alone).
  12. Coverage tool memory. drcov bitmap = 1 bit/block: 43.7k blocks / 8 ≈ 5.5 KB per module → coverage is essentially free in memory (#229 fuzzing feedback), confirming the §4 BBL-tool ≤10× budget is set by the inserted op, not memory.

These twelve numbers, all derived from §4, are what tell an expert before any code: per-thread cache ≈ single-digit MB, warmup sub-second, unlinked dispatch is fatal (20×), linked is near-native, and the IBL/clean-call costs set the interpreter/heavy-tool ceilings.

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for "observe and rewrite a running program," each with the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

A1 — Static / compile-time binary instrumentation (rewrite the binary on disk).

   ELF on disk ──► static rewriter ──► instrumented ELF on disk ──► run natively (no engine)
                    (insert probes, fix up relocations, expand .text)

Wins when: the binary is available ahead of time, code is not self-modifying, and you want zero runtime engine overhead (the probes are just inlined code) — long-running servers re-instrumented once. Embodied by: Dyninst (Buck & Hollingsworth, 2000) static mode and ATOM (historically). Rejected here because: it cannot follow dynamically generated/JIT code, cannot attach to an already-running process, and indirect-branch targets + stripped binaries make complete static CFG recovery undecidable — the very dynamic targets (packers, JITs, RE subjects) this framework exists for are exactly where static rewriting fails. (Contrast: ADR-003, Phase 7 SMC, Phase 9 attach.)

A2 — Hardware-assisted tracing (Intel PT / branch trace), no code rewriting.

   target runs NATIVE ──► CPU emits a compressed control-flow packet stream (Intel PT)
                          ──► decoder reconstructs the executed path offline/online

Wins when: you need near-zero-overhead whole-program control-flow capture (≈2–5% vs 2–10×) and only need what executed, not arbitrary in-line analysis — production tracing, coverage at scale. Embodied by: Intel Processor Trace (consumed by perf, libipt; magic-trace). Rejected here because: PT gives a control-flow trace, not the ability to insert arbitrary computation at a point, read/modify register or memory state inline, or do shadow-memory taint — it is read-only and post-hoc. This framework's clean-call/inline probe model (Phase 2) and memory hooks (Phase 10) require active instrumentation PT cannot provide. (A future hybrid — PT for cold paths, DBI for hot analysis — is PhaseDeferred("Deferred Features Register").)

A3 — Kernel eBPF / dynamic tracing (in-kernel verified bytecode at probe points).

   user/kernel code ── kprobe/uprobe/tracepoint ──► eBPF VM (in-kernel, JIT-compiled, VERIFIED)
                                                     ──► maps/ringbuf ──► userspace consumer

Wins when: you want safe, low-overhead, production observability across many processes/syscalls without controlling or rewriting any single target's full code — fleet-wide tracing. Embodied by: eBPF/bpftrace and conceptually DTrace (Cantrill et al.). Rejected here because: it is a different trust model — in-kernel verified, restricted bytecode attached at predefined probe points (function entry/exit, tracepoints), not arbitrary userspace rewriting of every basic block/instruction. eBPF cannot instrument at instruction granularity inside arbitrary user code, cannot follow a JIT's generated code, and is bounded by the verifier (no unbounded loops). This framework's instruction-level, JIT-following, transparent userspace DBI (Phase 0/3/7) is outside eBPF's design envelope; eBPF is the right tool for the opposite problem (broad, safe, predefined-point tracing). (§2 names #154 eBPF VM as the in-kernel analogue.)

A4 — Source / IR (compile-time) instrumentation (ASan/coverage-style).

   source/LLVM IR ──► instrumentation pass (insert checks/counters) ──► compile ──► native binary

Wins when: you have the source (or IR) and want the lowest-overhead, most semantically precise instrumentation — sanitizers (ASan/TSan/MSan), -fprofile-instr coverage, fuzzing harness coverage (SanitizerCoverage). Embodied by: LLVM sanitizer passes and SanitizerCoverage (the compile-time cousin of #229's coverage). Rejected here because: this framework's entire premise is binary instrumentation of code without source or cooperation — RE subjects, closed-source binaries, malware, third-party libraries. Source instrumentation is strictly better when source exists, which is exactly the case this tool does not assume. (Non-goal in §1; the deferred Valgrind-style lift-to-IR of A-adjacent analysis is in the Deferred Features Register.)

G.2 Block lifecycle

COLD → translate(decode #334 → copy-and-patch → install) → WARM (in cache, dispatch-entered)
WARM → linked (predecessors patched) → HOT (counter threshold) → trace candidate (Phase 4)
WARM/HOT → invalidated (SMC/flush) → unlink incoming (reverse map) → quiesce → free (I8)

G.3 Link patching protocol (I5, thread-safe)

to link exit E (currently → dispatch) to target block B:
  1. verify B is live (in tag map, not pending-free)
  2. write the jmp displacement to B with a single aligned store (atomic on x86 for ≤8B)
  3. record (E→B) in the reverse-link map
to unlink (flush): for each incoming E in reverse map of B: repoint E → dispatch (atomic), then free B

G.4 IBL fast path (I6)

indirect terminator → compute app_target (from reg/mem) → h = hash(app_target)
  probe IBL[h]: if tag==app_target → jmp cache_addr (HIT)   # verify tag, not just hash
                else → linear probe / fall to dispatcher (MISS → translate+insert)
returns: consult return cache first (call/ret pairing) before generic IBL

G.5 Why copy-and-patch (not re-emit from IR)

DynamoRIO-style copy-and-patch keeps most bytes verbatim (fast translation, faithful semantics) and only rewrites control flow + PC-relative operands + inserts probes. A full lift-to-IR-and-regenerate (Valgrind/VEX) enables heavier analysis but costs more overhead and risks semantic drift — deferred; this framework favors low overhead + fidelity (ADR-003).

L.2 VDSO / vsyscall

The kernel-mapped VDSO (__vdso_gettimeofday, etc.) is code the target calls; it is translated like any other module (decoded via #334, cached). Its addresses are kept transparent (Phase 5). The kernel-provided fast paths still work because the translated copy preserves their behavior.

L.3 Dynamic loader (ld.so) interaction

PLT/GOT lazy resolution runs target code (the resolver) → it is translated + instrumented like the rest (don't special-case it away). The first call through a PLT stub triggers the resolver (translated), which writes the GOT; subsequent calls are indirect through the GOT → handled by IBL (Phase 3). #333 supplies PLT/GOT layout so tools can attribute calls to imported symbols.

L.4 fork/exec semantics for the engine

On fork, the child inherits a copy-on-write code cache; the engine re-initializes per-process state (new dispatcher, fresh IBL) in the child to avoid sharing live caches across the fork boundary. On execve, the address space is replaced → the engine re-injects into the new image and starts fresh (the old cache is gone with the old image).

Appendix O — Worked SMC/JIT Trace

target: a tiny JIT that generates a function into an mmap'd RWX page, then calls it
run:
  1. engine running normally; target mmap's page P (RWX) and starts writing code into it
  2. (no cache yet for P — nothing executed there)
  3. target jumps/calls into P → dispatch(miss) → translate(P_block) → install in cache → run
  4. engine write-protects P's code pages (remove W) to detect future rewrites (Phase 7, I7)
  5. target's JIT later patches the function in P (writes new bytes) → WRITE-FAULT
  6. fault handler: this is SMC → flush cache entries derived from the touched range of P;
     restore W to P (allow the write); re-protect after; mark blocks stale (unlink incoming, I8)
  7. target re-enters P → dispatch(miss, since flushed) → re-translate updated code → run
result: instrumentation tracks the *current* generated code at all times (I7);
        smc_events counts the rewrites; output ≡ native JIT execution (differential)
note:   page-granular protection may over-invalidate if code+data share P → re-translate cost
        (measured; acceptable); a self-modifying packer shows high smc_events (a triage signal)

This is the case that separates a toy DBI engine from a real one: without SMC detection (steps 4–6), step 5 would leave the engine executing the old cached code while the target believes it patched the function — a silent, behavior-changing bug. Write-protection + invalidate (I7) closes it.

Appendix P — ISA & OS Portability Notes (the Arch/Os seams)

P.1 Why x86-64 Linux first

x86-64 is the hardest decode (variable length, prefixes — already handled by #334) and the most common RE target; Linux ptrace/mmap/signals are the cleanest substrate. Getting transparency + IBL + SMC right here exercises every hard problem.

P.2 AArch64 (deferred track)

Fixed 32-bit instructions simplify translation + length (no resync); but PC-relative addressing (adrp/adr, literal pools) makes transparency fixups more pervasive (more PC-relative operands), and instruction-cache coherence (explicit IC/DC + ISB after writing code) must be modeled for the cache. Behind the Arch trait; reuses dispatch/link/IBL/trace unchanged.

P.3 Windows (deferred track)

Different process control (DebugActiveProcess/CreateProcess + VirtualProtectEx), different injection (CreateRemoteThread/LoadLibrary), structured exception handling (SEH/VEH) instead of POSIX signals, and PE/IAT instead of ELF/PLT (#333 already parses PE). Behind an Os trait; the engine core (cache/link/IBL/trace/transparency) is OS-agnostic.

P.4 What stays shared across the seam

The code cache, linking, IBL, traces, the Tool/probe API, transparency requirements (mechanisms differ), and the differential/transparency test methodology are all ISA/OS-independent. Only decode (#334 per ISA), process control + injection (Os), signal/exception forwarding (Os), and PC-relative fixups + i-cache coherence (Arch) are specialized. This is the payoff of the layered design: adding an ISA or OS is additive (minor, ADR-014/023), not a rewrite.

P.5 Coherence + atomicity per ISA

Concern x86-64 AArch64
Code write visibility coherent i-cache (no explicit flush) explicit DC CVAU+IC IVAU+ISB required
Atomic link patch aligned ≤8B store is atomic careful: instruction patch + ISB

These differences are exactly why the Arch seam exists; the engine asks the arch layer to "make this freshly written cache code executable + visible," and x86 makes it a no-op while AArch64 issues the cache-maintenance sequence.
