Scaling assumptions: single machine, 1–128 cores, Linux ≥ 5.6 (uring) or any POSIX (emulation), NVMe + loopback/LAN NICs. No multi-machine; the network protocol layer is out of scope (#321/#33). Vertical scaling: thread-per-core + per-core rings (shared-nothing) → near-linear with cores; multishot + buffer rings cut per-connection syscalls; SQPOLL removes submit syscalls entirely.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints (§4). Inputs are stated; formulas are shown.

  1. SQE ring bytes. sq_entries × sizeof(Sqe) = 4096 × 64 B = 256 KiB for the SQE pool. Plus the SQ index ring sq_entries × 4 B (the array of u32 indices) = 16 KiB. SQ region ≈ 272 KiB.

  2. CQE ring bytes. cq_entries × sizeof(Cqe) = 8192 × 16 B = 128 KiB (CQ is 2× SQ to absorb multishot bursts, §4). With SETUP_CQE32 (32 B): 256 KiB. CQ region ≈ 128–256 KiB.

  3. Per-ring fixed memory. SQ + CQ ≈ 272 + 128 = ~400 KiB per ring, locked (counts against ulimit -l). At thread-per-core on a 64-core host: 64 × 400 KiB = ~25 MiB of locked ring memory before any data buffers.

  4. In-flight slab footprint. Hot OpState fields (phase u8 + result (i32,u32) + waker fat ptr 16 B + flags) ≈ 40 B; padded to keep ≤1 cache line = 64 B/slot. At the default 65 536 inflight cap (FD budget, §4): 65 536 × 64 B = 4 MiB/core worst-case slab.

  5. Max IOPS from queue depth and latency (Little's law, MM5). max_in_flight / latency. With SQ depth 4096 and a 15 µs p50 completion latency: 4096 / 15 µs ≈ 273 M ops/s if the device kept up — i.e., queue depth is not the limit; the device is. To sustain the 3 M NOP/s/core target at 15 µs each you need only 3e6 × 15e-6 = 45 ops in flight — comfortably under 4096.

  6. Syscalls saved by batching. Submitting a batch of B SQEs costs one io_uring_enter instead of B. At B = 256 (the saturation batch target, Performance Engineering): 255/256 ≈ 99.6% of submit syscalls eliminated vs one-per-op. At the 3 M ops/s target: one-per-op = 3 M enter/s; batched at 256 = ~11.7 K enter/s; with SQPOLL = 0.

  7. Submission-batch amortization. If io_uring_enter costs ~1 µs, one-per-op at 3 M ops/s spends 3 M × 1 µs = 3.0 s of CPU per wall-second (impossible on one core). Batched at 256: 11.7 K × 1 µs = ~11.7 ms/s (~1.2% of a core). This is why batching is mandatory, not optional.

  8. Echo bandwidth at target rate. 1 M echo ops/s/core × (recv + send) with a typical 1 KiB segment: 1e6 × 1 KiB × 2 = ~2 GiB/s/core of payload moved — within loopback/10–100 GbE NIC reach, confirming the runtime, not the wire, is what the benchmark stresses.

  9. buf_ring sizing (bandwidth-delay product). Buffers outstanding ≈ throughput × time-held. At 1 M recv/s/core and a 50 µs app hold time per buffer: 1e6 × 50e-6 = 50 buffers minimum; size the ring to ~2–4× = 128–256 buffers to avoid -ENOBUFS stalls (§Phase 9). At 1 KiB each: 128–256 KiB/core of buffer-ring memory.

  10. Registered-buffer memory. Registering N fixed buffers of size S pins N×S of locked memory for the runtime's life. For 256 × 64 KiB read buffers: 256 × 64 KiB = 16 MiB/core locked — must fit under ulimit -l alongside the ring memory (item 3).

  11. FD budget vs registered-files table. With the 65 536 default FD cap (§4) and a fixed-files table sized to it: 65 536 × 4 B (an fd is an i32 in the table) = 256 KiB for the registered-files index — negligible, so sizing the table to the full budget is cheap.

  12. Graceful-drain bound. Shutdown drains all in-flight ops within the 2 s deadline (§4). Worst case at the inflight cap with a 60 µs p99 completion: 65 536 × 60 µs = ~3.9 s if drained serially — so drain must reap in batches (one enter(GETEVENTS) reaps thousands), bringing it well under 2 s; this derivation is why the drain loop batches rather than awaits one CQE at a time.
