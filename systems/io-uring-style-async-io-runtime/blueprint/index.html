323 — io_uring-style Async I/O Runtime from Scratch

Project Number: 323

Project Name: io_uring-style Async I/O Runtime from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a single-machine, multi-core async I/O runtime on a completion-based submission/completion-ring interface built from scratch, modelled on Linux io_uring. Two layers, one vocabulary:

  • Ring layer (the substrate). Shared SQ (submission) + CQ (completion) rings; fixed-size Sqe (64 B) and Cqe (16 B, opt. 32 B); head/tail indices with acquire/release ordering; batched submit + completion reap; an opcode set. Backed by either raw Linux io_uring syscalls (io_uring_setup/io_uring_enter/io_uring_register via libc::syscall, no liburing) on Linux ≥ 5.x, OR a portable userspace emulation (epoll + blocking worker pool) that produces identical Op/Cqe semantics on non-Linux/sandbox hosts.
  • Async runtime (the user-facing layer). Futures-based executor, tasks, wakers, async TCP/UDP/file/timer resources — all driven by completions reaped from the CQ.

Plus advanced io_uring features: registered (fixed) files + buffers, linked SQE chains, provided-buffer rings, multishot ops, SQPOLL.

System boundaries (in scope):

  • Ring layer: SubmissionQueue, CompletionQueue, Sqe, Cqe, mmap'd (Linux) or heap-backed (emulation) shared regions, head/tail with correct memory ordering, SQ-array indirection, CQ-overflow handling.
  • Submission API: opcode builder, user_data tagging, SQE flags (IOSQE_IO_LINK / IO_HARDLINK / IO_DRAIN / FIXED_FILE / ASYNC / BUFFER_SELECT / CQE_SKIP_SUCCESS).
  • Batched io_uring_enter (submit + min_complete wait in one syscall); completion reaping loop; user_data→waker demux via an in-flight slab.
  • Opcode set: NOP, READ/WRITE, READV/WRITEV, READ_FIXED/WRITE_FIXED, FSYNC, ACCEPT/CONNECT, SEND/RECV, SENDMSG/RECVMSG, TIMEOUT/LINK_TIMEOUT/TIMEOUT_REMOVE, POLL_ADD/POLL_REMOVE, CLOSE, OPENAT, STATX, PROVIDE_BUFFERS, ASYNC_CANCEL.
  • Async runtime: thread-per-core executor (+ optional work-stealing), Task, Future poll loop, Waker via RawWaker vtable, JoinHandle<T>, spawn/spawn_blocking/block_on, run queue, reactor integrated with CQ reaping.
  • Async resources: TcpListener/TcpStream (accept/connect/send/recv), File (read/write/fsync/fallocate/statx), UdpSocket, Timer/timeout/sleep.
  • Advanced: registered fixed buffers (read_fixed/write_fixed + lifetime contract); registered fixed files (index table, skip fd refcount); linked chains + error propagation; provided buffers / buffer rings (buf_ring) for zero-alloc multishot recv; multishot accept/recv/poll; SQPOLL kernel-side polling; feature probing across kernel versions; cancellation (ASYNC_CANCEL + drop semantics) + structured concurrency + future timeouts; backpressure when the SQ is full.

THE central safety problem (load-bearing across every section). With completion-based I/O the kernel reads/writes a buffer after the syscall returns. A buffer or fd handed to an SQE must stay alive and pinned until that SQE's CQE arrives — even if the awaiting future is dropped or cancelled. This is the opposite of readiness-based (epoll) I/O, where the kernel touches buffers only inside a synchronous syscall, so the user owns the buffer the whole time. Completion-based I/O is the dominant source of use-after-free (UAF) bugs in this design. The ownership model — an Op owns its buffer + fd-reference from submission until its CQE is reaped; cancellation keeps the buffer alive until the cancel's CQE — is the spine of the whole runtime (I2, I8, principles 1/2/7). tokio-uring/glommio/monoio solve it by moving the buffer into the future and returning it out on completion (the (result, buffer) pattern); we adopt the same discipline (§8.6, §Phase 2/7/11).

Explicit non-goals (each deferred via PhaseDeferred(...) to a real anchor; all six rows are listed in the Deferred Features Register):

  • Modifying or implementing the in-kernel io_uring; we use the kernel's interface or emulate the worker side, never kernel internals. PhaseDeferred("§1 Goal — non-goal").
  • Windows IOCP / BSD kqueue backends; epoll fallback only. PhaseDeferred("§Phase 12").
  • io_uring features absent on the target kernel — feature-probe + gate, never assume. PhaseDeferred("§Phase 10").
  • Full Tokio API compatibility; we ship a minimal own API. PhaseDeferred("§1 Goal — non-goal").
  • A network protocol stack (TCP/TLS/HTTP) — this is the I/O substrate; cross-link #321 (userspace networking) / #33 (TCP). PhaseDeferred("§1 Goal — non-goal").

Deployment model: a library crate (urt-core) plus a thin urt CLI/driver and a set of example servers (echo, file-cat, an HTTP/1.0 toy). Embeds in a host application as the async I/O layer. Runs on Linux ≥ 5.6 with the uring backend; on macOS/sandbox/CI with the epoll-pool emulation backend; the same async program runs unmodified on both (backend chosen at startup by feature probe).

Target users/operators/developers: runtime engineers who want the io_uring + futures model built end to end; systems engineers debugging an in-flight-buffer UAF or a missed-completion hang at 3 a.m.; learners building toward tokio-uring/glommio/monoio-class systems.

Phase 0 deliverable (numbered crates/modules):

  1. urt-sys — raw syscall layer: io_uring_setup/enter/register via libc::syscall; IoUringParams, SqRingOffsets, CqRingOffsets; mmap helpers; errno→io::Error.
  2. urt-ring — Sqe (64 B #[repr(C)]), Cqe (16/32 B), SubmissionQueue, CompletionQueue, ring index management; Uring::setup/submit/submit_and_wait.
  3. urt-backend — trait IoBackend (uring vs epoll-pool); UringBackend (Phase 0–1); EpollPoolBackend stub (Phase 12).
  4. urt-types — OpId, Op enum, Cqe-result mapping, error enums, feature-flag bitset.
  5. urt — CLI/smoke driver: setup a ring, submit one NOP and one READ of a file, block for completions, print results.

What later phases unlock: ring index management + batching + reaping (§1); in-flight slab + the buffer-ownership contract (§2); executor/task/waker (§3); async file (§4); async net (§5); timers (§6); registered buffers/files (§7); linked chains (§8); provided buffers + multishot (§9); SQPOLL + feature matrix (§10); cancellation + structured concurrency + shutdown (§11); portable backend + conformance/differential/fuzz/loom/soak/perf (§12).

Timeline: Phase 0 = 6–14 weeks (raw syscalls + mmap + first completion are the hard part). Full plan = 6–9 months.

Recommended language: Rust (edition 2021, ≥ 1.78). Rationale (ADR-001, specific):

  • (a) The futures/async model is native: Future/Pin/Waker are first-class, so the executor maps directly onto language primitives rather than fighting them.
  • (b) Ownership encodes the #1 io_uring hazard at compile time. Moving a buffer into an Op (and the borrow checker forbidding aliasing) is exactly the in-flight-buffer-lifetime contract; 'static bounds on submitted buffers prevent stack-buffer UAF.
  • (c) unsafe is scoped narrowly to three sites — ring mmap, raw syscall, the RawWaker vtable — and audited; the rest is safe.
  • (d) Send/Sync express the thread-per-core vs work-stealing boundary and which types may cross threads.
  • (e) loom gives exhaustive interleaving coverage of the SQ/CQ + waker races that are otherwise untestable.
  • (f) This is exactly what real Rust io_uring runtimes (tokio-uring, glommio, monoio) are built in — the design transfers directly.

Reject C (manual lifetime tracking of in-flight buffers is the bug factory this project exists to avoid — every liburing UAF CVE is this). Reject Go (its runtime hides the rings behind the netpoller; no learning value, and GC poisons p99). Locked in ADR-001.

Prerequisites: Linux syscall ABI + mmap; memory ordering (acquire/release, the C11/Rust model); futures/Pin/Waker; epoll/readiness vs completion I/O distinction; pinning and self-referential-future hazards; basic socket + file I/O; lock-free single-producer/single-consumer ring buffers; unsafe Rust + provenance.

2. Why Build This

  • Unique systems knowledge: the completion model, and the buffer-ownership discipline it forces. Most async runtimes teach readiness (epoll/kqueue): the kernel says "ready," you do a synchronous syscall, you own the buffer throughout. Completion I/O inverts this — you hand the kernel a buffer, the syscall returns immediately, and the kernel touches the buffer later. Internalizing that inversion (and the lifetime contract that makes it safe) is the single most transferable lesson here, and it is invisible in an epoll-only runtime.
  • Historical/architectural significance: io_uring (Axboe, 2019, Linux 5.1) is the first mainstream Linux interface to deliver true async for both storage and network with batched, low-syscall submission — the successor to aio(7)/epoll. It is now the substrate under high-performance Rust runtimes (glommio, tokio-uring, monoio) and databases. Rebuilding its ring mechanics + a futures layer is rebuilding the modern Linux async I/O foundation.
  • Engineering muscles: memory-ordered lock-free ring indices; mmap'd shared kernel/user memory; a RawWaker vtable by hand; a reactor that demultiplexes completions to tasks; pinning and drop-safety for in-flight ops; feature probing across an evolving kernel ABI; thread-per-core shared-nothing design (Seastar/glommio lineage).
  • Production concepts exercised: batching to amortize syscalls; backpressure when the SQ fills; zero-allocation hot paths (buffer rings + slab reuse); graceful drain of in-flight I/O at shutdown; cancellation that does not leak; multishot to cut per-connection syscalls; SQPOLL to reach zero syscalls/op.
  • Cross-links:

    • #204 Timer Wheel — the timer subsystem (§6) is a hierarchical timing wheel feeding TIMEOUT SQEs.
    • #34 Filesystem / #311 NVMe — async File (§4) is the natural client of a storage engine.

  • Calibration value: after this you can read the io_uring man pages and liburing source fluently, reason precisely about why an in-flight buffer must outlive a dropped future, debug a missed-completion hang via ring head/tail inspection, and design a thread-per-core runtime that reaches millions of ops/s with zero syscalls per op.

What Mastery Looks Like

After building this system, the reader holds these competencies, each cemented by a named phase:

  • Reason about completion-vs-readiness ownership from first principles — explain why a buffer handed to an SQE must outlive a dropped future, and derive the (result, buffer) move pattern unprompted. Phase 2 (the buffer-ownership contract), Phase 11 (cancel-then-await).
  • Implement a correct lock-free SPSC ring across a trust boundary — place exactly the acquire/release fences that form the kernel↔user happens-before edge, and prove the absence of torn/missed completions under exhaustive interleaving. Phase 1 (ordering), Phase 12 (loom).
  • Hand-build the futures machinery — a RawWaker vtable with balanced ref-counting and exactly-once wake, an executor poll loop, and a reactor that demultiplexes completions to parked tasks. Phase 3 (executor/waker/reactor).
  • Demultiplex and account every in-flight operation — key a slab by user_data, drive a monotone op state machine, and reconcile submitted-vs-completed so no slot leaks and no CQE double-frees. Phase 2 (slab + lifecycle), Phase 8 (linked-chain accounting).
  • Drive io_uring to its efficiency ceiling — combine batched submit, multishot, provided-buffer rings, and SQPOLL to reach zero syscalls per op and zero allocation on the hot path. Phase 9 (buf_ring + multishot), Phase 10 (SQPOLL).
  • Probe and degrade across an evolving kernel ABI — build a capability matrix from REGISTER_PROBE + uname and gate every advanced feature with a real fallback, never assuming a kernel capability. Phase 10 (feature probe + matrix).
  • Engineer leak-free, crash-only shutdown — drain all in-flight ops to their CQEs before unmapping rings or closing FDs, with leak gauges that must return to baseline. Phase 11 (graceful drain), Phase 12 (soak).
  • Build behaviorally-equivalent backends — abstract submit/reap/register behind a trait so a thread-per-core uring backend and an epoll+worker-pool emulation produce identical Op/Cqe semantics under a differential gate. Phase 12 (emulation backend + equivalence gate).

Per-box dense notes:

  • Application — user async fns; the only API surface is spawn/block_on/resources. Trust boundary: user buffers handed in are moved (owned) by the runtime until completion; the API forbids retaining a reference (compile-time, via move).
  • Executor / task system — owns the run queue and drives Future::poll. Thread-per-core by default (one executor + one reactor + one Uring per core, shared-nothing); optional work-stealing across cores. Waker built from a hand-written RawWakerVTable. Concurrency boundary: tasks on a core never migrate by default → no cross-core synchronization on the hot path.
  • Reactor — reaps CQEs from the CQ, looks up user_data in the in-flight slab, stores the result, wakes the parked task. When the run queue is empty it calls backend.submit_and_wait(min_complete) to block until at least one completion. One reactor per Uring instance (single submitter/reaper → ring is SPSC per side).
  • Async resources — Tcp*/Udp/File/Timer. Each operation moves its buffer into an Op, builds an SQE, registers an OpState in the slab, and returns a future that resolves to (result, buffer) on the matching CQE. Lowering table in §8.
  • In-flight tracker — Slab<OpState> keyed by OpId == user_data. This is where the buffer and fd-reference are pinned from submission until the CQE is reaped (I2/I8). A dropped future does not free the slot; it transitions the op to "orphaned, awaiting CQE" and (for cancellable ops) submits an ASYNC_CANCEL — the buffer is freed only when the (cancel's) CQE arrives.
  • Ring layer — the SQ/CQ rings. Sqe 64 B, Cqe 16 B (32 B with IORING_SETUP_CQE32). SQ uses an indirection array (the SQ "array" maps ring slots → SQE indices). Index discipline: producer publishes the SQ tail with release, the consumer (kernel) reads it with acquire; symmetrically for the CQ head. CQ overflow is detected and counted (dropped/cq_overflow), never silently lost (I9).
  • Backend — trait IoBackend abstracts submit/reap/register so the same upper layers run on either real io_uring (UringBackend, raw syscalls + mmap, no liburing) or the portable EpollPoolBackend (epoll readiness + a blocking worker pool that performs the syscall and posts a synthetic Cqe). Identical Op/Cqe semantics across both is a conformance gate (§12).
  • Feature probe — at startup, query kernel version + io_uring_register(PROBE) to build a capability mask: which opcodes, which SQE flags, SQPOLL, buf_ring, multishot, DEFER_TASKRUN. Features absent → gated; the runtime degrades (e.g., no multishot → re-arm single-shot).
  • Kernel io_uring / emulation — the real interface (we never touch kernel internals — §1 non-goal) or the userspace emulation. SQPOLL (when enabled) is a kernel thread that polls the SQ so submission needs no syscall.
  • Observability — ring depth/utilization, in-flight count, sqe/cqe counters, the sqpoll_syscalls_per_op gauge (target 0), per-op tracing spans, and leak counters (open FDs, live buffers, live slab slots) that must return to baseline on drain (I1/I8).

4. System Constraints

Dimension Target
Submission overhead batched: one io_uring_enter per batch of SQEs; with SQPOLL → 0 syscalls/op (kernel polls SQ)
Op throughput (NOP, 1 core) ≥ 3 M ops/s/core (submit+reap loop, batched)
Op throughput (echo, recv+send, 1 core) ≥ 1 M ops/s/core with buffer rings + multishot
Completion latency (loopback echo) p50 ≤ 15 µs, p99 ≤ 60 µs (uring backend, busy reactor)
Per-op heap allocation (hot path) 0 — buffers from a registered buf_ring or pool; slab slots reused; no Box per op
SQ / CQ depth power-of-two; default SQ = 4096, CQ = 8192 (2× SQ to absorb multishot)
FD budget runtime caps open FDs (default 65 536); registered-files table sized to budget
Memory ordering correctness every SQ-tail/CQ-head publish RELEASE, read ACQUIRE → zero missed/torn completions (I7) under loom
Cancellation latency dropped-future op cancelled + buffer freed within ≤ 1 reactor turn after its (cancel) CQE; bounded by kernel cancel latency
Backpressure (SQ full) submit returns WouldBlock/awaits SQ space; never overruns SQ capacity (I6)
Startup (cold) ≤ 50 ms to ring setup + first SQE submitted (uring backend)
Graceful drain shutdown drains all in-flight ops (await their CQEs) in ≤ 2 s; no orphan FDs/buffers/slots (I1)
CQ overflow detected + counted; reactor reaps before re-submitting; never silently dropped (I9)
SQPOLL idle kernel poll thread parks after sq_thread_idle (default 1 s) ms; woken via IORING_SQ_NEED_WAKEUP
loom coverage SQ/CQ index + waker races: exhaustive interleavings green (I7/I3)
Thread model thread-per-core default (num_cpus executors); one Uring per core; work-stealing optional

Scaling assumptions: single machine, 1–128 cores, Linux ≥ 5.6 (uring) or any POSIX (emulation), NVMe + loopback/LAN NICs. No multi-machine; the network protocol layer is out of scope (#321/#33). Vertical scaling: thread-per-core + per-core rings (shared-nothing) → near-linear with cores; multishot + buffer rings cut per-connection syscalls; SQPOLL removes submit syscalls entirely.

6. Design Principles

  1. The kernel touches the buffer after the syscall returns — so the buffer outlives the future. Every submitted buffer/fd is owned by its Op from submission until its CQE; dropping the future cannot free it. Tradeoff: the API moves buffers in and returns them out ((result, buffer)), which is less ergonomic than borrowing. Violation: UAF — the kernel writes freed memory; the #1 io_uring bug class (I2/I8).
  2. Cancellation keeps the buffer alive until the cancel's CQE. Dropping an in-flight future submits ASYNC_CANCEL and retains the buffer/slot until the original op's terminating CQE arrives (cancel does not retroactively un-submit). Violation: freeing on drop → kernel completes into freed memory (I8).
  3. Every SQE yields exactly one terminating CQE; account all of them. One-shot → one CQE; multishot → many CQEs then a terminating one (no IORING_CQE_F_MORE). The slab slot lives until the terminating CQE. Violation: leaked slot (op never completes) or double-free (slot reused while a CQE is in flight) (I3).
  4. Memory ordering is not optional. SQ tail / CQ head published with release, read with acquire; the matching index read with acquire before touching shared SQE/CQE memory. Violation: missed or torn completion — a CQE the reactor never sees, or a half-written SQE the kernel reads (I7).
  5. Backpressure at the SQ. The SQ has finite depth; submission blocks/awaits when full, never overruns. Tradeoff: a slow kernel throttles the producer. Violation: SQE overwrite → corrupted submission (I6).
  6. CQ overflow is observed, never lost. When the CQ fills, the kernel sets an overflow flag + dropped counter; the reactor reaps to drain before overflow loses completions. Violation: silently dropped CQE → a task hangs forever (I9).
  7. One submitter, one reaper, per ring. Each Uring instance is single-producer on the SQ and single-consumer on the CQ (thread-per-core). Cross-thread submission is forbidden without external synchronization. Tradeoff: no free cross-core op submission. Violation: torn ring indices, data race (I7, ADR-008).
  8. Feature-probe, then degrade — never assume a kernel capability. Multishot/buf_ring/SQPOLL/DEFER_TASKRUN are probed at startup; absent features fall back (multishot → re-arm; buf_ring → per-op buffers). Violation: -EINVAL at runtime on older kernels (I12).
  9. Zero allocation on the hot path. Buffers come from a registered buf_ring or a reused pool; slab slots are recycled; no Box/Vec allocation per op. Tradeoff: buffer-lifetime bookkeeping. Violation: allocator pressure caps throughput + adds tail latency.
  10. The async layer is a thin lowering over the ring. A resource op = move buffer into Op → build SQE → register OpState → await CQE → return (result, buffer). No hidden buffering or copies. Violation: a second copy defeats io_uring's zero-copy advantage.
  11. Deterministic, leak-free shutdown. Drain drives the reactor until every in-flight op's CQE is reaped; only then are FDs/buffers/slots released. Violation: orphan FDs/buffers, or a CQE arriving into freed runtime state after exit (I1).
  12. The backend is swappable and behaviorally identical. UringBackend and EpollPoolBackend produce the same Op/Cqe semantics; the upper layers are backend-agnostic. Tradeoff: the emulation cannot match uring performance, only semantics. Violation: code that assumes uring-only behavior breaks portability + the differential gate (§12).
  13. unsafe is small, named, and audited. Exactly three unsafe domains — ring mmap, raw syscall, RawWaker vtable. Each is wrapped in a safe API with documented invariants. Violation: unsafe sprawl → UB anywhere, defeating Rust's value here.
  14. Observability on the hot path is cheap counters only. Inflight count, sqe/cqe totals, ring utilization, SQPOLL syscall count are atomics/relaxed counters; no per-op logging on the fast path. Violation: tracing in the reactor loop tanks throughput.
  15. A correct slow completion beats a fast lost one. When uncertain (overflow, cancel race, probe ambiguity) the runtime favors reaping/retrying/draining over speed. Violation: a dropped completion is an unrecoverable hang — worse than any latency cost.

8. Domain Model

8.1 Ring memory layout (Linux io_uring; emulation mirrors the same logical shape)

io_uring_setup(entries, params) returns a ring fd. Three regions are mmap'd from it:

SQ_RING  @ IORING_OFF_SQ_RING : head,tail,ring_mask,ring_entries,flags,dropped, array[]   (u32 indices)
CQ_RING  @ IORING_OFF_CQ_RING : head,tail,ring_mask,ring_entries,overflow,cqes[]          (Cqe structs)
SQES     @ IORING_OFF_SQES     : Sqe[entries]                                              (64B each)

The SQ ring stores indices into the separate SQES array (one level of indirection — array[ring_tail & mask] = sqe_index). The CQ ring stores Cqe structs inline. params.sq_off / cq_off give the byte offsets of each field within its region (IoSqRingOffsets/IoCqRingOffsets) — fields are addressed by offset, not a fixed struct, because the layout can grow across kernel versions.

8.2 SQE layout (#[repr(C)], 64 bytes — must match struct io_uring_sqe)

Sqe {
  opcode:   u8,      // IORING_OP_*  (NOP, READ, WRITE, ACCEPT, …)
  flags:    u8,      // IOSQE_*  (IO_LINK, IO_HARDLINK, IO_DRAIN, FIXED_FILE, ASYNC, BUFFER_SELECT, CQE_SKIP_SUCCESS)
  ioprio:   u16,
  fd:       i32,     // fd, OR fixed-file index when IOSQE_FIXED_FILE set
  off:      u64,     // file offset, OR addr2 (union, opcode-dependent)
  addr:     u64,     // buffer ptr / sockaddr ptr / iovec ptr (opcode-dependent)
  len:      u32,     // byte count / iovec count / accept flags …
  op_flags: u32,     // opcode-specific (rw_flags, msg_flags, timeout_flags, accept_flags, …) [union]
  user_data:u64,     // == OpId; echoed verbatim into the Cqe (demux key)  ← I4
  buf_index:u16,     // fixed-buffer index (READ_FIXED/WRITE_FIXED) OR buf_group (BUFFER_SELECT) [union]
  personality:u16,
  splice_fd:i32,     // / file_index (union)
  _pad:    [u64; 2],
}  // exactly 64 bytes

Many fields are unions in the kernel ABI; we model them as the widest field + opcode-specific accessor helpers (no full impl here — signatures in §11).

8.3 CQE layout (#[repr(C)], 16 bytes; 32 with SETUP_CQE32)

Cqe {
  user_data: u64,   // echoes the SQE's user_data → OpId (demux)  ← I4
  res:       i32,   // ≥0 = result (bytes / new fd / 0); <0 = -errno  ← errno mapping (§Phase1)
  flags:     u32,   // IORING_CQE_F_*  (MORE = more CQEs for this SQE [multishot]; BUFFER = buf id in upper bits; SOCK_NONEMPTY; NOTIF)
}
// flags upper 16 bits carry the provided-buffer id when IORING_CQE_F_BUFFER is set (§Phase 9)

8.4 Ring index semantics + memory ordering (the heart of correctness — I7)

SUBMIT (producer = us):                          REAP (consumer = us):
  local tail = SQ.tail (relaxed, we own it)        local head = CQ.head (relaxed, we own it)
  for each op to submit:                           tail = CQ.tail.load(Acquire)   ← see kernel's writes
     SQE = &sqes[tail & ring_mask]                 while head != tail:
     fill SQE fields (plain writes)                   cqe = CQ.cqes[head & ring_mask]
     array[tail & ring_mask] = sqe_index               demux(cqe.user_data) → wake
     tail += 1                                        head += 1
  SQ.tail.store(tail, Release)  ← publish to kernel  CQ.head.store(head, Release) ← free slots for kernel
  io_uring_enter(submit_count, min_complete, flags)
  • Why Release on store: all SQE field writes must be visible to the kernel before it observes the advanced tail. Release on the tail store + the kernel's acquire on its read forms the happens-before edge.
  • Why Acquire on CQ.tail load: the kernel writes the Cqe then advances the CQ tail with release; our acquire load establishes that the Cqe payload is visible before we read it. Reading the tail relaxed would risk a torn CQE (reading a half-written struct) — I7.
  • SQPOLL variant: when IORING_SETUP_SQPOLL, the kernel poll-thread reads the SQ tail without us calling enter; we only call enter with IORING_ENTER_SQ_WAKEUP when SQ.flags & IORING_SQ_NEED_WAKEUP (the thread parked). Missing that wakeup check = a stalled submission (I13).

8.5 Op state machine (per in-flight op)

                submit (SQE filled, slab slot allocated, buffer moved in)
   [new] ───────────────────────────────────────────────► Submitted
                                                              │ io_uring_enter / SQPOLL picks up
                                                              ▼
                                                          InKernel
            future dropped │                                 │ terminating CQE reaped (res, flags)
                           ▼                                 ▼
                       Cancelling ──ASYNC_CANCEL──► (await orig CQE) ──► Completed → slot freed, buffer returned
                           │ cancel CQE + orig CQE                          ▲
                           └──────────────────────────────────────────────┘
   multishot: InKernel ──CQE(F_MORE)──► InKernel (re-deliver) … ──CQE(no F_MORE)──► Completed
  • A slot is freed (and the buffer returned to the future or to the pool) only at Completed (I3). Cancelling retains the buffer (I8).
  • For multishot, each F_MORE CQE delivers a result without freeing the slot; the terminating CQE (no F_MORE, often res<0 like -ENOBUFS/-ECANCELED) frees it.

8.6 Future / waker / task model + the (result, buffer) pattern

EBNF-ish lowering of a resource op:
  op_future        := submit_phase poll_phase* completion_phase
  submit_phase     := move_buffer_into_Op ; build_SQE ; slab.insert(OpState{waker:None, result:None, buffer_owner:Op}) ; ring.fill(SQE)
  poll_phase       := if slot.result.is_some() → Ready((result, buffer))  else { slot.waker = cx.waker().clone(); Pending }
  completion_phase := reactor: on CQE → slot.result = Some(res,flags) ; slot.waker.wake()
  • Ownership: the buffer is moved into the Op at submit_phase and moved out at Ready as (result, buffer). The future never holds a borrow of caller memory → no stack-buffer UAF (principle 1, I2).
  • Drop-while-pending: if the future is dropped between submit and completion, its Drop impl transitions the slot to Cancelling, submits ASYNC_CANCEL(user_data), and leaves the buffer in the slot; the reactor frees it when the terminating CQE arrives (I8).
  • Waker: a hand-built RawWaker (vtable: clone/wake/wake_by_ref/drop) pointing at the task's scheduler handle; wake re-enqueues the task on the run queue. Exactly-once per completion (I11).

8.9 Worked example (NOP → READ, one batch)

1. slab.insert(OpId=1, OpState{NOP})        ; SQE0: opcode=NOP, user_data=1
2. slab.insert(OpId=2, OpState{READ, buf})  ; SQE1: opcode=READ, fd=f, addr=buf.ptr, len=4096, off=0, user_data=2
3. SQ.array[t&m]=0 ; SQ.array[(t+1)&m]=1 ; SQ.tail += 2 ; SQ.tail.store(Release)
4. io_uring_enter(submit=2, min_complete=2, GETEVENTS)
5. reap: CQ.tail.load(Acquire); cqe{user_data=1,res=0}; cqe{user_data=2,res=4096}
6. demux: slot(1).result=0 → wake; slot(2).result=4096 → wake (buffer now valid, return (4096, buf))
7. CQ.head.store(Release)  ; slabs 1,2 freed

8.10 Malformed / failure-path examples

  • Submit with len exceeding the buffer length → kernel may short-read (res<len) or -EFAULT if addr invalid; the buffer-ownership contract (I2) means addr is always valid because the buffer is pinned.
  • Drop the future for OpId=2 before its CQE → slot→Cancelling, submit ASYNC_CANCEL(2); buffer retained; two CQEs arrive (-ECANCELED for op 2, and the cancel's own CQE) → slot freed, buffer dropped (I8).
  • CQ fills (multishot recv flooding) before the reactor reaps → kernel sets IORING_SQ_CQ_OVERFLOW, increments cq.overflow; reactor must reap to drain; new completions are backlogged in the kernel (5.x) — counted, not lost (I9).
  • Use READ_FIXED with an unregistered buf_index → -EFAULT/-ENXIO; gated by the fixed-buffer table validity check (I14).
  • On a kernel without multishot accept, submitting ACCEPT with the multishot flag → -EINVAL; feature probe must have gated it (I12) and used single-shot re-arm instead.
  • SQPOLL thread parked (NEED_WAKEUP set) and we submit without re-entering with SQ_WAKEUP → the SQE sits unsubmitted; a task hangs (I13); detected by inflight stall + sq_depth not draining.

Phase 0 — Repo Skeleton, Raw Syscall Layer, mmap'd Rings, Sqe/Cqe, First NOP + READ, Backend Trait Stub

0.1 Objectives

Stand up the workspace; implement urt-sys (raw io_uring_setup/enter/register via libc::syscall); mmap the SQ ring, SQ array, and CQ ring from the ring fd; define Sqe (64 B) and Cqe types; submit one NOP and one READ of a file and block (submit_and_wait) for their completions; stub the IoBackend trait + UringBackend. This phase proves the ABI and the mmap layout — the hardest and riskiest part of the whole project.

0.2 Detailed Implementation Steps

This phase realizes the raw-syscall binding (ADR-002, no liburing) and direct mmap of the rings (ADR-012), keeping the unsafe surface to its three audited domains (principle 13/P13); the Sqe/Cqe layouts follow the kernel io_uring.h and Axboe "Efficient IO with io_uring" (Required Reading paper 1).

  • urt-sys/syscall.rs: io_uring_setup/enter/register as thin unsafe fn over libc::syscall(SYS_io_uring_setup, …) etc.; last_os_error() from errno. Three unsafe sites total (principle 13).
  • urt-sys/params.rs: #[repr(C)] IoUringParams, IoSqRingOffsets, IoCqRingOffsets matching io_uring.h; IORING_OFF_SQ_RING/CQ_RING/SQES constants; static_assert size_of::<Sqe>()==64, size_of::<Cqe>()==16.
  • urt-sys/mmap.rs: mmap(MAP_SHARED|MAP_POPULATE) the SQ ring (size from sq_off.array + sq_entries*4), the SQES array (sq_entries*64), and the CQ ring (cq_off.cqes + cq_entries*sizeof(Cqe)); munmap on drop (RAII). Single mmap when IORING_FEAT_SINGLE_MMAP present.
  • urt-ring/sqe.rs, cqe.rs: the #[repr(C)] types + opcode-specific field setters (prep_nop, prep_read(fd,buf,off)); no logic, just field writes.
  • urt-ring/sq.rs, cq.rs, uring.rs: wrap the mmap'd regions as SubmissionQueue/CompletionQueue (raw atomic pointers at the published offsets); Uring::setup/submit/submit_and_wait/reap (full ordering deferred to §1 — Phase 0 uses a conservative SeqCst then tightens).
  • urt-backend/backend.rs: trait IoBackend; uring_backend.rs: UringBackend wrapping Uring; epoll_pool.rs: empty stub returning Unsupported.
  • urt/main.rs: open a file, set up a ring (8 entries), submit NOP + READ, submit_and_wait(2), print (user_data, res) pairs.

0.3 Deliverable

urt smoke --file /etc/hostname (on a Linux ≥5.6 host) sets up a ring, submits NOP + READ, prints nop res=0, read res=N bytes. cargo test green on the host; ABI static-asserts pass; munmap verified leak-free under valgrind.

0.4 Acceptance Criteria

  • size_of::<Sqe>()==64, size_of::<Cqe>()==16 (static assert + test).
  • NOP completes with res==0; READ returns the correct byte count and buffer contents match a std::fs::read of the same file (differential).
  • Ring setup + teardown leak-free (valgrind / mmap/munmap balanced).
  • Graceful failure on a kernel < 5.6 or without CONFIG_IO_URING → Setup error, no panic.

0.5 Conformance Fixtures

  • op_sequences/nop.golden — SQE{NOP,user_data=1} → CQE{1,0}. op_sequences/read_file.golden — READ → CQE{2,N}. caps/min_kernel.json — expected IoUringParams.features on the CI kernel. Negative: caps/no_uring.json (setup fails cleanly).

0.6 Pitfalls

  • Wrong Sqe/Cqe field offset or size → kernel reads garbage, -EINVAL or silent corruption. Root: io_uring.h mismatch / forgetting a union field. Debug: dump raw SQE bytes, compare to liburing for the same op. Recover: regenerate #[repr(C)] from the target kernel header; static-assert size + offsets.
  • mmap size miscomputed (forgetting sq_off.array) → SIGSEGV touching the SQ array. Root: using sq_entries*4 instead of array_off + sq_entries*4. Debug: faulting address vs mmap range. Recover: size from the returned offsets, not assumptions.
  • Forgetting MAP_POPULATE → page faults on the hot path (latency spikes, not correctness). Debug: perf minor-fault count. Recover: MAP_POPULATE to prefault.
  • Not handling IORING_FEAT_SINGLE_MMAP → double-mapping on newer kernels wastes a syscall (benign) or wrong offsets on older ones. Recover: branch on the feature flag.
  • Treating ring indices as plain u32 in Phase 0 → fine single-threaded, broken once the reactor reaps concurrently (Phase 1/3). Note: Phase 0 is single-threaded blocking; ordering is hardened in §1.

0.7 Performance Concerns

N/A for correctness-first Phase 0, but: MAP_POPULATE avoids fault latency; the SQES array is touched sequentially (cache-friendly); one syscall (submit_and_wait) does both submit and wait. No allocation in the submit path even now (SQEs are in the mmap'd region).

0.8 Edge Cases

Zero-byte file (READ res=0); file smaller than buffer (short read, res<len); entries not a power of two (kernel rounds up — record the actual sq_entries); ring fd closed before reaping (EBADF — must reap before close).

0.9 Failure Analysis

io_uring_setup -ENOSYS (no uring) → Setup error, fall back to emulation later (Phase 12); blast radius: process can't use uring backend. -EFAULT on READ → bad buffer ptr (Phase 0 buffer is stack/heap and valid); detection: res<0 mapped to io::Error. mmap failure → Setup error, ring fd closed.

0.10 Operational Notes

No metrics endpoint yet. tracing at setup logs sq_entries, cq_entries, features bitset. tools/ring-inspector (skeleton) dumps the offsets + index values for manual ABI verification. README documents the minimum kernel + ulimit -l (locked-memory) requirement for the mmap.

Phase 1 — Ring Index Management, Batched Submission, Completion Reaping, user_data Tagging, errno Mapping, Correct Memory Ordering

1.1 Objectives

Make the ring correct and batched: proper SQ producer/consumer head/tail with acquire/release ordering (replace Phase 0's SeqCst), SQ-array indirection, CQ-overflow detection + the dropped counter, fill-many-then-one-enter batching, a completion reaping loop, user_data tagging, and errno→Result mapping. This is where I6/I7/I9 are established.

1.2 Detailed Implementation Steps

  • urt-ring/order.rs: the ordering discipline (§8.4) — sq_tail.store(Release), cq_tail.load(Acquire), cq_head.store(Release); sq_head.load(Acquire) to compute free space.
  • urt-ring/sq.rs: sq_space() = ring_entries − (tail − head); try_fill writes an SQE + array[tail&mask]=idx, bumps a local tail; flush() publishes the tail with Release; Backpressure when full (I6).
  • urt-ring/cq.rs: reap() loads cq_tail Acquire, iterates head..tail reading Cqes, calls the demux closure, stores cq_head Release; checks IORING_SQ_CQ_OVERFLOW in sq.flags and reads cq.overflow (I9).
  • Batching: Uring::submit fills N SQEs then one io_uring_enter(to_submit=N, …); submit_and_wait(min_complete) adds IORING_ENTER_GETEVENTS.
  • user_data: monotone OpId (later slab-keyed) written into each SQE; echoed in the CQE; demux is the identity map for now (Phase 2 adds the slab).
  • urt-sys/errno.rs: Cqe.res < 0 → io::Error::from_raw_os_error(-res); positive → Ok(res as usize).

1.3 Deliverable

A loop submits a batch of K NOPs + reaps K CQEs with one submit_and_wait; throughput measured (≥ 3 M NOP/s/core target); CQ-overflow deliberately triggered (fill CQ without reaping) and detected via the overflow counter; ordering exercised under a stress test.

1.4 Acceptance Criteria

  • Batched submit: K=4096 NOPs in one enter; all K CQEs reaped; submitted count == reaped count (I3 precursor).
  • NOP throughput ≥ 3 M ops/s/core (batched).
  • CQ overflow: submit > CQ-depth completions without reaping → overflow flag set, cqe_dropped/backlog counted, zero silently lost (I9) — verified by reaping the backlog and reconciling counts.
  • SQ full: fill past sq_entries → try_fill returns Backpressure, never overwrites an unconsumed SQE (I6).
  • loom smoke on a model of the SQ tail / CQ head store/load (I7) passes (full loom suite in §12).

1.5 Conformance Fixtures

  • op_sequences/batch_nop.golden (K SQEs → K CQEs, order preserved). overflow/cq_overflow.json (more completions than CQ depth → overflow accounted). flags/sq_full_backpressure.json (SQ fills → Backpressure). op_sequences/errno_map.golden (an op that returns -EINVAL → mapped io::Error).

1.6 Pitfalls

  • Relaxed CQ-tail load → torn/missed CQE. Root: reading the tail without Acquire, seeing the index advance before the Cqe payload is visible. Debug: loom failure; a CQE with stale user_data/res. Recover: Acquire on the tail load (I7).
  • Forgetting to publish cq_head (Release) → kernel thinks slots are still occupied, CQ overflows prematurely. Debug: overflow with a half-empty CQ. Recover: store cq_head Release after each reap batch.
  • Computing SQ free space from a stale sq_head → overfill or underfill. Root: not re-loading sq_head Acquire. Debug: SQE overwrite (corruption) or wasted capacity. Recover: load sq_head Acquire before space math (I6).
  • Submitting more than sq_space SQEs in one batch → overwrite. Recover: cap the batch at sq_space(); flush + reap + retry.
  • Ignoring IORING_SQ_CQ_OVERFLOW → on 5.x, completions backlog in the kernel and stall; on overflow you must enter(GETEVENTS) to flush the backlog. Debug: inflight stalls despite reaping. Recover: check the flag, reap, re-enter (I9).

1.7 Performance Concerns

Batch as many SQEs as sq_space allows per enter → amortizes the syscall (Little's law: deeper in-flight queue raises throughput). Avoid a memory barrier per SQE — order once at flush (Release) and once per reap batch (Acquire). The reap loop reads Cqes sequentially (cache-friendly). False sharing: keep our local head/tail caches off the kernel-shared cache lines.

1.8 Edge Cases

Empty submit (to_submit=0, just wait); min_complete > inflight (would block forever — cap at inflight); exactly-full SQ (space==0 → Backpressure immediately); CQ exactly full then one more (overflow flag set on the (N+1)th); wraparound of the 32-bit index (mask handles it; the index itself wraps cleanly mod 2^32).

1.9 Failure Analysis

Missed completion (ordering bug) → a task hangs forever (the worst failure, principle 15); detection: sqe_submitted − cqe_reaped gauge drifts up and never recovers; containment: loom proves the ordering pre-merge. Overflow mishandled → stalled submission; detection: cq_overflow_events + inflight stall; recovery: drain via enter(GETEVENTS).

1.10 Operational Notes

First real metrics: sqe_submitted, cqe_reaped, sq_depth, sq_full_events, cq_overflow_events, cqe_dropped. tools/ring-inspector now prints live head/tail/overflow. Runbook docs/runbooks/cq-overflow.md (symptom: inflight not draining → check overflow flag → reap + re-enter). The submitted-vs-reaped gauge is the single most important hang-detection signal (I3).

Phase 2 — In-Flight Operation Tracking: Slab, Op Lifecycle, the Buffer-Ownership / Lifetime Contract, CQE Demux

2.1 Objectives

Establish the project's safety spine: a Slab<OpState> keyed by user_data (OpId); the Op lifecycle Submitted→InKernel→Completed (+ Cancelling); and the buffer-ownership contract — an Op owns its buffer/fd-reference from submission until its CQE; a dropped future retains the buffer until the (cancel) CQE. CQE demux routes results to the right slot. This phase implements I2, I3, I4, I5, I8 (cancel mechanics finished in §11).

2.2 Detailed Implementation Steps

  • urt-driver/inflight.rs: Inflight { slab: Slab<OpState> }; submit(op) -> OpId inserts OpState{phase:Submitted, waker:None, result:None, buffer_owner:Some(op)}, the slab key is the user_data (I4); on_cqe(cqe) looks up the slot, stores (res,flags), advances phase, returns the waker.
  • urt-driver/opstate.rs: OpStatePhase transitions with a debug-asserted legal-transition table (I5); multishot flag → slot survives F_MORE CQEs (I3).
  • urt-types/buf.rs: the unsafe trait IoBuf/IoBufMut — a stable pointer that must not move/free while submitted; blanket impls for Vec<u8>, Box<[u8]>, a 'static slice, and the registered-buffer handle. The Op owns the buffer; the future holds no borrow.
  • The buffer-ownership contract: Op variants store the buffer by value (buf: IoBufMut); the SQE's addr is the buffer's stable pointer; the slot keeps the Op alive until Completed. drop(future) → cancel(id) → phase Cancelling, buffer stays in the slot (I8); reactor frees on the terminating CQE.
  • urt-driver/reap.rs: the demux entry — for each reaped CQE, inflight.on_cqe(cqe); if F_MORE keep the slot, else free it (returning the buffer to the future's result channel).
  • urt-driver/submit.rs: build the SQE from the Op (opcode + addr=buffer ptr + len + user_data=OpId) and hand it to Uring::try_fill.

2.3 Deliverable

A standalone driver test: submit 1000 READs with distinct buffers, reap their CQEs, assert each result lands in the correct slot and each buffer is returned intact; drop a pending op mid-flight and confirm the buffer is retained until the (simulated) CQE, then freed — Miri/ASan clean (no UAF).

2.4 Acceptance Criteria

  • 1000 concurrent in-flight ops: each CQE demuxed to its slot by user_data (I4); zero cross-talk.
  • Submitted-count == completed-count over the run (I3); slab returns to empty.
  • Drop-while-inflight retains the buffer (I2/I8): a UAF-soak (drop a future, then deliver its CQE into the retained buffer) is ASan-clean.
  • Illegal phase transition (e.g., Completed→InKernel) trips a debug assert (I5).
  • Miri clean on the slab/OpState paths (no UB in the ownership transfer).

2.5 Conformance Fixtures

  • op_sequences/demux_1000.json (1000 distinct user_data → 1000 CQEs, bijective). cancel/drop_retains_buffer.json (drop pending → buffer alive until CQE). op_sequences/multishot_slot.json (F_MORE keeps slot, terminating frees). Negative: cancel/double_complete.json (a second CQE for a freed slot → detected, not double-free).

2.6 Pitfalls

  • Freeing the buffer on future-drop → the canonical UAF: the kernel writes the freed buffer when the op finally completes. Root: treating drop as cancellation-complete. Debug: ASan UAF in the reactor on the CQE for a dropped op. Recover: drop → Cancelling, retain buffer, free on CQE (I8, principle 2).
  • Reusing a user_data/slab slot before its CQE arrives → the next op's CQE demuxes to the wrong (or freed) slot. Root: freeing the slot at submit instead of completion. Debug: result lands in the wrong future. Recover: slot lives until the terminating CQE (I3/I4).
  • Storing the buffer pointer but moving the buffer (e.g., a Vec that reallocs) → dangling addr. Root: borrowing a growable buffer. Debug: -EFAULT or ASan. Recover: IoBuf requires a stable pointer; the Op owns the buffer so it cannot move.
  • Multishot slot freed on the first CQE → subsequent F_MORE CQEs hit a freed slot. Recover: check F_MORE; only free on the terminating CQE (I3).
  • A CQE for an unknown user_data (late cancel CQE after slot freed) → must be tolerated, not a double-free. Recover: demux returns None for an absent slot; count orphan_cqe.

2.7 Performance Concerns

Slab is O(1) insert/remove/index with dense keys → user_data stays small and cache-local. No per-op heap allocation if buffers come from a pool (Phase 9 buf_ring). The demux is a single slab index (no hashing). Keep OpState small (≤ 1 cache line for the hot fields: phase, result, waker ptr) so reap touches one line per CQE.

2.8 Edge Cases

Op completes before the future is first polled (result already present at poll → Ready immediately, no waker stored); op dropped before submit even reaches the kernel (cancel a not-yet-entered SQE — local removal); a buffer of zero length (valid; res=0); a slot whose waker is None when the CQE arrives (op not yet polled — store result, no wake needed); slab exhaustion (inflight cap reached → backpressure submit).

2.9 Failure Analysis

UAF on a dropped op's buffer → memory corruption, the highest-severity bug; detection: ASan in CI on the cancel-soak (I8); containment: the type system forbids borrowing, the slab retains the buffer. Slot leak (op never completes) → slab grows unbounded → inflight cap → submit backpressure (graceful, not OOM); detection: slab_live gauge climbing; root usually a missed/lost CQE (Phase 1 ordering — already loom-tested).

2.10 Operational Notes

Metrics: slab_live (in-flight op count), inflight_with_buffer, orphan_cqe, dup_user_data (must be 0). tools/leak-checker snapshots the slab at drain and asserts empty (I1 precursor). Runbook docs/runbooks/cancel-uaf.md and inflight-leak.md. This phase's invariants (I2/I3/I8) are the ones a reviewer scrutinizes hardest — the unsafe-review checklist (CONTRIBUTING.md) gates every change to urt-driver.

Phase 3 — Executor + Task System: Task, Future Poll Loop, RawWaker Vtable, Run Queue, spawn / block_on / JoinHandle, Reactor Integrated with CQ Reaping

3.1 Objectives

Build the async runtime layer: Task (boxed future + state), a Future poll loop, a hand-built Waker via RawWakerVTable (clone/wake/wake_by_ref/drop), a run queue, spawn/block_on/JoinHandle<T>, and a reactor that reaps CQEs and wakes the parked task by user_data. Thread-per-core single executor first; work-stealing is a later option. Implements I11 (exactly-once wake) and wires the driver (§2) to the executor.

3.2 Detailed Implementation Steps

  • urt-exec/raw_task.rs: RawTask = header (ref-count, state, scheduler handle) + the future; a vtable (poll, drop, schedule). Task is a thin NonNull<RawTask>. Modeled on async-task.
  • urt-exec/waker.rs: RawWakerVTable { clone, wake, wake_by_ref, drop } over a *const RawTask; wake re-enqueues the task on its run queue; ref-count managed in clone/drop. The one unsafe site here (principle 13); exactly-once enqueue (I11).
  • urt-exec/run_queue.rs: per-executor VecDeque<Task> (local) + optional crossbeam_deque for stealing (Phase later); FIFO with a yield budget.
  • urt-exec/executor.rs: the loop — pop a task, build its Waker, poll(Pending|Ready); on Pending the future has registered its OpId→waker in the slab; when the run queue empties, call reactor.turn(block=true).
  • urt-exec/reactor.rs: turn(block) = flush pending SQEs (backend.submit), then submit_and_wait(min_complete = block?1:0), then reap each CQE through inflight.on_cqe → wake the slot's task (I11). One reactor per Uring (single reaper, principle 7).
  • urt-exec/runtime.rs + join.rs: Runtime::new probes + sets up one ring + executor per core; block_on drives the current-thread executor to completion of a root future; spawn enqueues a task and returns a JoinHandle<T> (oneshot result channel); spawn_blocking offloads to a thread pool and posts the result.
  • Integrate §2 driver: a resource op's future, on first poll, submits the Op (slab insert + SQE fill) and stores cx.waker() in the slot; on wake it re-polls, sees result, returns Ready((res, buf)).

3.3 Deliverable

block_on(async { let (r, buf) = file.read_at(buf, 0).await; … }) runs end-to-end on the uring backend: the task parks on the READ, the reactor reaps the CQE, the waker fires, the task resumes and returns (bytes, buffer). spawn of 10 000 NOP-await tasks all complete; JoinHandle yields results.

3.4 Acceptance Criteria

  • A single async fn doing READ→assert runs to completion via the reactor (no busy-wait; the executor blocks in submit_and_wait while idle).
  • 10 000 spawned tasks each awaiting a NOP complete; all JoinHandles resolve; run queue + slab drain to empty (I1/I3).
  • Waker correctness under loom: clone/wake/drop interleavings → exactly-once wake, no missed wake, no double-free of the task (I11).
  • Miri clean on the waker vtable + task ref-counting.
  • No busy-spin: with one idle task awaiting I/O, CPU ≈ 0 (the reactor is blocked in enter).

3.5 Conformance Fixtures

  • op_sequences/blockon_read.json (read→complete via reactor). op_sequences/spawn_10k_nop.json. Waker model fixtures for loom (conformance/cancel/waker_race.rs shares with §12 loom). Negative: op_sequences/wake_after_complete.json (waking an already-completed task is a no-op, not a panic).

3.6 Pitfalls

  • Missed wake (lost wakeup): the future returns Pending but the reactor reaped the CQE between the poll and storing the waker → the task sleeps forever. Root: storing the waker after submitting without re-checking result. Debug: a hang with the CQE already reaped. Recover: after storing the waker, re-check result.is_some() and self-wake if so (the classic register-then-check pattern); loom proves it (I11).
  • Double-wake / spurious wake: the future must tolerate being polled when not ready (just re-park). Root: assuming poll ⇒ ready. Recover: idempotent poll; re-check result.
  • Waker ref-count bug: clone without incrementing / drop without decrementing → task freed while a Waker still points at it (UAF) or leaked. Debug: Miri/ASan on the vtable; loom. Recover: balanced ref-count in clone/drop (the standard async-task discipline).
  • Reactor reaps for the wrong executor (cross-core): in thread-per-core, the CQE for core-0's op must wake core-0's task; a global reactor would need cross-core wakeups. Recover: one reactor per ring per core (principle 7); cross-core spawn handled explicitly (Phase later).
  • block_on busy-spins when the only task is I/O-bound. Root: not calling submit_and_wait with min_complete≥1 when the run queue is empty. Recover: block in the reactor when there is nothing to poll.

3.7 Performance Concerns

The poll loop is the hot path: keep poll allocation-free; the waker is a fat pointer, not a Box per wake. Batch SQEs from many ready tasks before one enter (the executor polls the whole run queue, then the reactor does one submit). submit_and_wait(min_complete=1) when idle avoids spinning; min_complete=0 (non-blocking reap) when the run queue still has work. Avoid waking a task that is already in the run queue (track a "scheduled" bit) to cut redundant enqueues.

3.8 Edge Cases

A future that completes synchronously on first poll (never parks); a task that yields cooperatively (re-enqueue without I/O); a JoinHandle dropped before the task finishes (task still runs to completion, result discarded); a panic inside a task (caught, task aborts, JoinHandle resolves to a JoinError); the run queue empty and no in-flight ops (the executor exits / parks until externally woken).

3.9 Failure Analysis

Lost wakeup → permanent task hang; detection: a task stuck Pending with its op already Completed (slot result present, waker never fired); the register-then-check pattern + loom prevent it; containment: a watchdog can detect "completed slot, parked task" drift. Task ref-count bug → UAF/leak; detection: Miri/ASan; containment: the vtable is the single audited unsafe. Reactor starvation (always polling, never reaping) → completions pile up; detection: cqe_reaped flat while sqe_submitted climbs; recover: bound polls-per-turn, then reap.

3.10 Operational Notes

Metrics: tasks_spawned, tasks_completed, run_queue_depth, wakes_issued, spurious_wakes, reactor_turns, reactor_block_us. tracing span per task (off the hot path — opened on spawn, closed on completion). Runbook docs/runbooks/missed-completion.md (symptom: task hung; check slot result vs waker fired; inspect ring head/tail). This phase makes the runtime usable; §4–6 add resources, §7–11 add the advanced io_uring features.

Phase 4 — Async File I/O: File::open / read_at / write_at / fsync / fallocate / statx (OPENAT/READ/WRITE/FSYNC/STATX)

4.1 Objectives

First real resource: async File lowering to OPENAT, READ, WRITE, FSYNC, FALLOCATE, STATX SQEs. Establish offset handling, short-read/short-write semantics, the (result, buffer) return at the resource API level, and CLOSE as an async op. Cross-link #34 (filesystem) / #311 (NVMe) — File is their async client.

4.2 Detailed Implementation Steps

  • urt-fs/open.rs: File::open(path) -> impl Future<Output=io::Result<File>> lowers to OPENAT(dirfd=AT_FDCWD, path, flags, mode); the CQE res is the new fd (or -errno). The CString path is owned by the Op until the CQE (I2).
  • urt-fs/file.rs: read_at(buf, off) → READ(fd, addr=buf.ptr, len=buf.cap, off); write_at(buf, off) → WRITE; both return (io::Result<usize>, buf) (buffer moves in, returns out — §8.6). fsync(datasync) → FSYNC; fallocate → FALLOCATE. Drop for File submits an async CLOSE (fire-and-forget, but the fd-ref retained until its CQE — I2/I8).
  • urt-fs/statx.rs: statx(mask) → STATX(dirfd, path, statx_buf, mask); the Box<Statx> out-buffer owned by the Op.
  • Short read/write: res < len is success with a partial count; the caller loops (helper read_exact_at re-submits the remainder with an advanced offset + sliced buffer). No hidden looping in the primitive (principle 10).
  • Offset semantics: explicit off per op (no shared file cursor — positioned I/O); off = u64::MAX (-1) means "use the fd's current offset" where the kernel supports it (document the gotcha).

4.3 Deliverable

examples/filecat reads a file via async read_at in a loop and writes it to stdout via async write_at; File::open/statx/fsync all work; a 1 GiB file is read with bounded memory (reused buffer) and correct bytes (differential vs std::fs).

4.4 Acceptance Criteria

  • read_at/write_at results match std::fs positioned I/O byte-for-byte (differential) including short reads at EOF.
  • OPENAT returns a usable fd; statx fields match std::fs::metadata.
  • fsync(datasync=true) issues FSYNC with FSYNC_DATASYNC; durability verified (write→fsync→crash-sim→read intact, where the FS supports it).
  • A dropped File closes its fd asynchronously and the fd-ref is retained until the CLOSE CQE (no premature reuse — I2); open_fds returns to baseline after drain (I1).
  • 1 GiB sequential read with a single reused 256 KiB buffer → constant memory.

4.5 Conformance Fixtures

  • op_sequences/file_read_write.golden (OPENAT→READ→WRITE→FSYNC→CLOSE sequence). op_sequences/short_read_eof.json (res<len at EOF). op_sequences/statx.golden. Negative: op_sequences/open_enoent.json (OPENAT of a missing path → -ENOENT mapped to io::Error).

4.6 Pitfalls

  • Reusing the buffer before the WRITE CQE (the (result, buffer) discipline violated) → the kernel writes stale/torn data, or UAF if freed. Root: not awaiting before reuse. Debug: corrupted output. Recover: the API returns the buffer; reuse only the returned one (I2).
  • Assuming a full read (ignoring short reads) → truncated data / infinite loop. Root: treating res<len as error. Debug: missing tail bytes. Recover: loop on the remainder; read_exact_at helper.
  • Closing the fd synchronously on Drop while an op is in flight on it → the op completes on a reused fd (wrong file). Root: libc::close in Drop. Recover: async CLOSE op + retain the fd-ref until in-flight ops on it drain (I2/I14 precursor).
  • OPENAT path lifetime: a &str path dropped before the CQE → dangling addr. Recover: own the CString in the Op (I2).
  • off=-1 shared-cursor races across concurrent ops on the same fd → interleaved reads. Recover: prefer explicit offsets; document -1 as single-op-at-a-time.

4.7 Performance Concerns

Positioned I/O (explicit offset) enables concurrent reads on one fd (no cursor contention). Reuse a fixed buffer to keep zero per-op allocation (Phase 7 fixed buffers go further). Batch multiple read_ats on different offsets in one submit (deep queue → high storage throughput, Little's law). O_DIRECT reads need aligned buffers + offsets (document; align the pool). FSYNC is expensive — batch writes, one fsync.

4.8 Edge Cases

Read at offset past EOF (res=0); write past file end (extends the file); zero-length read/write (res=0, valid); statx on a symlink (follow vs AT_SYMLINK_NOFOLLOW); OPENAT with O_CREAT|O_EXCL on an existing file (-EEXIST); a very large read_at (kernel may short-read; loop).

4.9 Failure Analysis

-EFAULT on READ/WRITE → buffer ptr invalid (should be impossible given I2; if it happens, an IoBuf impl violated the stable-pointer contract — audit). -EBADF → fd closed too early (the sync-close pitfall); detection: res==-EBADF after a File drop; recover: async CLOSE discipline. Disk full on WRITE → -ENOSPC, propagated to the future; blast radius: that op.

4.10 Operational Notes

Metrics: file_read_bytes, file_write_bytes, fsync_count, short_reads, open_fds. tracing span per file op (off hot path). Runbook note in inflight-leak.md for fd leaks (async CLOSE not reaped). Cross-link: a storage engine (#311) would submit batched read_fixed here (Phase 7).

Phase 5 — Async Networking: TcpListener::accept, TcpStream::connect / recv / send, UdpSocket (ACCEPT/CONNECT/RECV/SEND/RECVMSG/SENDMSG)

5.1 Objectives

Async sockets: TcpListener::accept (ACCEPT), TcpStream::connect (CONNECT), recv/send (RECV/SEND), UdpSocket (RECVMSG/SENDMSG for addressed datagrams); sockaddr handling; partial send/recv semantics. Cross-link #129 (async runtime) / #53 (event loop) / #321 (the networking stack that sits above). Single-shot accept/recv here; multishot in §9.

5.2 Detailed Implementation Steps

  • urt-net/sockaddr.rs: SockAddrStorage (sockaddr_storage sized), to/from SocketAddr; owned by Op for ACCEPT/CONNECT/RECVMSG (I2).
  • urt-net/tcp_listener.rs: create a listening socket (socket/bind/listen synchronously at construction; these are cheap setup syscalls), then accept() → ACCEPT(fd, addr=Box<SockAddrStorage>, addrlen); CQE res = new connection fd; returns (TcpStream, SocketAddr).
  • urt-net/tcp_stream.rs: connect(addr) → socket + CONNECT(fd, addr); recv(buf) → RECV(fd, buf, len); send(buf) → SEND(fd, buf, len); both (io::Result<usize>, buf). Partial send → loop on remainder; partial recv → return the count (caller decides).
  • urt-net/udp.rs: UdpSocket::recv_from → RECVMSG (msghdr with iovec + addr); send_to → SENDMSG. The msghdr + iovec array + addr are all owned by the Op (I2 — a common UAF site).
  • Drop for sockets → async CLOSE (as §4).
  • Reuse the §3 reactor + §2 slab unchanged — networking is just more opcodes.

5.3 Deliverable

examples/echo — an async TCP echo server: accept in a loop, spawn a task per connection that recvs then sends the echo; handles many concurrent connections on one core; a load client measures throughput + p99 latency on loopback.

5.4 Acceptance Criteria

  • Echo server correct: bytes sent == bytes echoed for 10 000 concurrent connections (differential vs a std::net echo server).
  • connect/accept/recv/send results match blocking sockets (differential).
  • Partial send handled: a large send that the kernel partially completes loops to send the remainder; no bytes lost or duplicated.
  • UDP recv_from/send_to round-trip with correct peer address.
  • No fd leak across 100 000 short-lived connections (open_fds baseline after drain — I1).

5.5 Conformance Fixtures

  • op_sequences/tcp_echo.golden (ACCEPT→RECV→SEND→CLOSE per connection). op_sequences/connect.golden. op_sequences/udp_roundtrip.json. op_sequences/partial_send.json (res<len → loop). Negative: op_sequences/connect_refused.json (-ECONNREFUSED).

5.6 Pitfalls

  • sockaddr/msghdr/iovec freed before the CQE → UAF / -EFAULT; the classic networking UAF. Root: stack msghdr. Debug: ASan in recv_from. Recover: own all of msghdr+iovec+addr in the Op (I2).
  • Partial recv treated as a full message → protocol framing bug (this project doesn't frame, but the API must report the true count). Recover: return the exact res; framing is the caller's (#321/#33).
  • accept without re-arming → only one connection accepted. Root: single-shot accept not re-submitted. Recover: loop (re-submit ACCEPT after each), or multishot accept (§9).
  • SO_REUSEADDR/SO_REUSEPORT not set → bind fails on restart / no per-core sharding. Recover: set socket options at construction (thread-per-core uses SO_REUSEPORT to shard accepts across cores).
  • Closing a socket with an in-flight RECV → the RECV completes -ECANCELED or on a reused fd. Recover: async CLOSE + retain fd-ref until in-flight drains (I2).

5.7 Performance Concerns

One core can saturate loopback with batched recv/send + deep queues. SO_REUSEPORT shards incoming connections across per-core listeners → no cross-core accept contention (thread-per-core, principle 7). Per-op buffer allocation is the bottleneck → §9 buffer rings remove it. MSG_NOSIGNAL/MSG_DONTWAIT flags via op_flags. Batch sends to amortize enter.

5.8 Edge Cases

Accept on a closed listener (-EBADF); recv on a half-closed connection (res=0 = EOF); send to a peer that reset (-ECONNRESET/-EPIPE); UDP datagram larger than the buffer (MSG_TRUNC); connect to an unreachable host (-ETIMEDOUT / -EHOSTUNREACH); a connection accepted but the peer immediately closes (recv res=0).

5.9 Failure Analysis

UAF on a stack msghdr → corruption; detection: ASan on the UDP path; containment: I2 ownership in Op. fd leak under connection churn → exhaustion (-EMFILE); detection: open_fds climbing; recover: ensure async CLOSE reaped; raise ulimit -n. Accept storm (many pending connections, single-shot accept) → backlog overflow; detection: accept latency / dropped connections; recover: multishot accept (§9) or a tighter accept loop.

5.10 Operational Notes

Metrics: accepts, connections_active, recv_bytes, send_bytes, partial_sends, conn_resets, open_fds. tracing span per connection. Runbook for fd exhaustion. The echo server is the primary perf benchmark (Performance Engineering) — its Mops/p99 with vs without multishot/buf_ring/SQPOLL is the headline number.

Phase 6 — Timers: TIMEOUT / LINK_TIMEOUT / TIMEOUT_REMOVE, sleep / deadline Futures, a Timing Wheel, select / timeout Combinators

6.1 Objectives

Time-based ops: sleep(dur) and deadline futures via TIMEOUT SQEs (relative + absolute, __kernel_timespec); LINK_TIMEOUT to bound a linked op; TIMEOUT_REMOVE to cancel a pending timer; a hierarchical timing wheel (cross-link #204) so many timers cost O(1) to insert/expire; timeout(dur, fut) and a select combinator. Establishes the time source (CLOCK_MONOTONIC).

6.2 Detailed Implementation Steps

  • urt-time/timeout.rs: sleep(dur) lowers to TIMEOUT(ts=Box<__kernel_timespec>, flags=relative, count=0); the CQE arrives (-ETIME) when the timeout fires → wake the sleeper. The Box<KernelTimespec> is owned by the Op (I2).
  • Absolute deadlines: TIMEOUT with IORING_TIMEOUT_ABS + a CLOCK_MONOTONIC timespec.
  • urt-time/wheel.rs: a hierarchical timing wheel for the userspace side — when thousands of timers share coarse granularity, the wheel batches them and arms a single kernel TIMEOUT for the nearest deadline, expiring the rest in userspace on each turn (avoids one SQE per timer). Per-timer kernel TIMEOUT only for precise/sparse timers.
  • urt-link/link_timeout.rs: LINK_TIMEOUT submitted immediately after a linked op (e.g., RECV) bounds it; if the op doesn't complete in time, the kernel cancels it (-ECANCELED) and the LINK_TIMEOUT completes (-ETIME).
  • TIMEOUT_REMOVE: cancel a pending timer by its user_data (e.g., timer cancelled because the awaited event arrived first).
  • urt-time/sleep.rs combinators: timeout(dur, fut) = select(fut, sleep(dur)); select polls both, returns the first ready, cancels the other (drop → §11 cancel).

6.3 Deliverable

sleep(Duration::from_millis(10)).await resolves at ~10 ms; timeout(d, recv) returns Err(Elapsed) if the recv doesn't complete in d; 100 000 concurrent timers via the wheel cost bounded memory + CPU; select! of two ops returns the first.

6.4 Acceptance Criteria

  • sleep accuracy within the wheel's granularity (e.g., ±1 ms at 1 ms tick) vs wall clock.
  • timeout cancels the inner op when elapsed (the inner op's buffer retained until its cancel CQE — I8); inner result returned when it wins.
  • 100 000 timers: insert + expire O(1) amortized (wheel); memory bounded; no per-timer SQE storm.
  • TIMEOUT_REMOVE cancels a pending timer cleanly (no spurious wake).
  • LINK_TIMEOUT bounds a linked RECV: slow peer → RECV -ECANCELED, LINK_TIMEOUT -ETIME, future resolves to a timeout error.

6.5 Conformance Fixtures

  • op_sequences/sleep_10ms.json. op_sequences/timeout_elapsed.json (inner cancelled). op_sequences/timeout_completes.json (inner wins, timer removed). op_sequences/link_timeout.golden (linked RECV + LINK_TIMEOUT). op_sequences/timer_storm_wheel.json (100k timers, bounded SQEs).

6.6 Pitfalls

  • One kernel TIMEOUT SQE per timer → SQE storm + ring pressure for many timers. Root: not using the wheel. Debug: sqe_submitted dominated by timeouts. Recover: wheel batches; one kernel timer for the nearest deadline (#204).
  • Wrong clock (REALTIME vs MONOTONIC) → timers jump on clock adjustment. Recover: CLOCK_MONOTONIC for durations (ADR-013).
  • select drops the loser without cancelling its in-flight op → the loser's buffer freed while in flight (UAF). Root: drop ≠ cancel. Recover: select's drop path cancels both branches' ops, retaining buffers until CQEs (I8, §11).
  • timeout races: inner completes and timer fires "simultaneously" → double-resolve. Recover: first-CQE-wins with a resolved flag; the second is ignored (idempotent).
  • __kernel_timespec layout mismatch (32- vs 64-bit time_t) → garbage timeouts. Recover: use the kernel's 64-bit __kernel_timespec, not libc timespec (ABI gotcha).

6.7 Performance Concerns

The wheel makes timer insert/expire O(1) and keeps the ring free of timeout SQEs (only the nearest deadline is armed). select/timeout add a cancel on the loser — cheap (one ASYNC_CANCEL/TIMEOUT_REMOVE). Coarse wheel granularity trades precision for fewer kernel timers; sparse precise timers bypass the wheel.

6.8 Edge Cases

Zero-duration sleep (fires next turn); a timer already expired at insert (fire immediately); timeout(0, fut) (inner gets one poll, then elapsed); cancelling a timer that already fired (TIMEOUT_REMOVE → -ENOENT, benign); clock granularity coarser than requested (round up); 2^32 timers (index/id space — bounded by inflight cap anyway).

6.9 Failure Analysis

Timer never fires (lost TIMEOUT CQE) → a sleeper hangs; detection: a task parked on a timer past its deadline; same root/fix as any lost CQE (Phase 1 ordering). Wheel drift (slow turns) → late timers; detection: timer_lateness_p99; recover: ensure reactor turns frequently enough; arm the kernel timer for the true nearest deadline. select UAF (loser not cancelled) → corruption; detection: ASan on a timeout-soak; containment: I8.

6.10 Operational Notes

Metrics: timers_active, timer_fires, timer_lateness_p99, timeouts_elapsed, link_timeout_fires. tracing for timeout events. Runbook: timer lateness → check reactor turn frequency + wheel granularity. Cross-link #204 for the wheel internals. LINK_TIMEOUT is the building block for per-op deadlines used pervasively in §11 structured concurrency.

Phase 7 — Registered / Fixed Resources: register_buffers (read_fixed / write_fixed), register_files (fixed-file index), the Lifetime / Validity Contract, Reaping on Deregister

7.1 Objectives

Performance + safety for hot resources: register_buffers (pre-mapped buffers → READ_FIXED/WRITE_FIXED skip per-op buffer mapping); register_files (a fixed-file index table → IOSQE_FIXED_FILE skips fd refcount/lookup); and the strict lifetime/validity contract (I14): a registered buffer/file index must be valid and pinned for every op that references it, and deregister must wait for all in-flight ops using it to complete.

7.2 Detailed Implementation Steps

  • urt-fixed/fixed_buffers.rs: register_buffers(bufs: Vec<IoBufMut>) → io_uring_register(IORING_REGISTER_BUFFERS, iovecs); returns indices. read_fixed(buf_index, off) / write_fixed use READ_FIXED/WRITE_FIXED with buf_index (the kernel already has the mapping → no per-op page pinning). The registered buffers are owned by FixedBuffers and pinned for the runtime's life or until deregister (I14).
  • urt-fixed/fixed_files.rs: register_files(fds: &[RawFd]) → IORING_REGISTER_FILES; ops use fd = index + IOSQE_FIXED_FILE. Skips the per-op fget/fput (fd refcount) → measurable throughput win. register_files_update to replace a slot (e.g., a new accepted connection).
  • The validity contract: a per-index in-flight counter; deregister_buffers/deregister_files blocks (drains) until all ops referencing those indices complete (I14). Using an out-of-range or deregistered index is rejected before submit (debug assert) and would be -EFAULT from the kernel.
  • Integrate with §4/§5: File::read_fixed, TcpStream::send_fixed use registered resources when available; fall back to plain READ/SEND otherwise.

7.3 Deliverable

A benchmark shows read_fixed (registered buffers) beats read (per-op mapping) on small random reads; IOSQE_FIXED_FILE reduces per-op CPU; deregister correctly waits for in-flight ops; an out-of-range index is rejected.

7.4 Acceptance Criteria

  • read_fixed/write_fixed correctness == read/write (differential) on the same data.
  • Measurable throughput/CPU win for fixed buffers + fixed files vs unregistered (≥ 10% on small-IO microbench; the win grows with op rate).
  • Deregister drains in-flight (I14): deregistering buffers/files with ops in flight blocks until those CQEs arrive; an ASan/Miri soak shows no use-after-deregister.
  • Out-of-range / deregistered index → rejected (debug assert) or -EFAULT, never UB.
  • register_files_update swaps a slot atomically (new fd visible to subsequent ops; in-flight ops on the old fd unaffected).

7.5 Conformance Fixtures

  • op_sequences/read_fixed.golden (REGISTER_BUFFERS → READ_FIXED → result). op_sequences/fixed_file.golden (REGISTER_FILES → READ with FIXED_FILE). flags/deregister_drains.json (deregister waits for in-flight). Negative: flags/fixed_index_oob.json (out-of-range index rejected).

7.6 Pitfalls

  • Deregistering a buffer/file with an op in flight → the op completes into freed/unmapped memory (UAF) or on a closed fd. Root: deregister without draining. Debug: ASan on a register/deregister-churn soak. Recover: per-index in-flight counter; block deregister until zero (I14).
  • Reusing a fixed-buffer index for a new op while the old op is in flight → two ops share a buffer, data race. Recover: a fixed buffer is single-op-at-a-time, or partitioned by offset; track in-flight per index.
  • Moving/reallocating a registered buffer (e.g., a Vec that grows) → the kernel's mapping dangles. Recover: registered buffers are pinned + immovable for their registration lifetime (Box<[u8]>/mmap, not a growable Vec).
  • IOSQE_FIXED_FILE with a real fd value (forgetting the flag means index) → wrong file or -EBADF. Recover: the typed FixedFd wrapper sets the flag automatically.
  • Registering more buffers/files than the kernel limit → -EINVAL/-EMFILE. Recover: probe the limit; cap registration.

7.7 Performance Concerns

Fixed buffers remove per-op get_user_pages (page pinning) — the dominant per-op cost for small I/O; the win is large at high op rates. Fixed files remove fget/fput atomics. Both shrink the SQE prep cost. Registering a large buffer set up front trades startup time + locked memory (ulimit -l) for hot-path speed. Combine with buffer rings (§9) for the zero-alloc receive path.

7.8 Edge Cases

Registering zero buffers (no-op); a fixed buffer larger than a single op uses (offset into it via addr); deregister while no ops in flight (immediate); register_files_update of a slot currently in flight (old op unaffected, new ops see the new fd); a sparse fixed-file table (some slots -1 = empty).

7.9 Failure Analysis

Use-after-deregister → corruption/UAF (highest severity); detection: ASan on the churn soak; containment: I14 drain-before-deregister. Locked-memory exhaustion (ulimit -l) at registration → -ENOMEM; detection: register fails; recover: raise the limit or register fewer buffers. Fixed-file table exhaustion → -EMFILE; recover: size the table to the FD budget (§4).

7.10 Operational Notes

Metrics: fixed_buffers_registered, fixed_files_registered, fixed_buf_inflight, fixed_file_inflight, read_fixed_count. tools/leak-checker asserts the fixed in-flight counters are zero before deregister. Runbook for locked-memory limits. This phase's I14 is in the same "scrutinize hardest" tier as I2/I8 — registered resources are a second UAF surface.

Phase 8 — Linked Operations: IOSQE_IO_LINK / IO_HARDLINK / IO_DRAIN, Operation Chains, Error Short-Circuit (-ECANCELED), Ordering Guarantees

8.1 Objectives

Chain dependent ops in one submission: IOSQE_IO_LINK (next runs only after this succeeds; failure cancels the rest), IOSQE_IO_HARDLINK (chain continues even on a non-fatal error of this link), IOSQE_IO_DRAIN (barrier: wait for all prior). Build chains like accept→recv, write→fsync, connect→send. Error short-circuits the remainder with -ECANCELED (I10). This cuts round-trips and encodes ordering the kernel enforces.

8.2 Detailed Implementation Steps

  • urt-link/chain.rs: a Chain builder collects N Ops; all but the last get IOSQE_IO_LINK set; they are submitted as a contiguous SQE run (the kernel links consecutive flagged SQEs). Each gets its own user_data/slot.
  • Demux + error propagation: when a link fails, the kernel emits -ECANCELED for every subsequent link; the driver maps these to the chain future as "chain aborted at step k with error E" (I10).
  • IOSQE_IO_HARDLINK: continue past a non-fatal error (e.g., a short read that the caller tolerates); the chain only breaks on a hard failure.
  • IOSQE_IO_DRAIN: a barrier SQE that waits for all previously submitted SQEs (not just its link) to complete before it runs — used for an ordered checkpoint (e.g., drain all writes, then fsync).
  • IOSQE_CQE_SKIP_SUCCESS: optionally suppress success CQEs for intermediate links (only the final link + any failure complete) → fewer CQEs for long chains (I3 note: skipped CQEs are accounted as "implicit success" so slot accounting stays correct).
  • Ordering guarantee: linked ops execute in submission order; unlinked ops may complete in any order. Document the difference clearly.

8.3 Deliverable

A write→fsync chain (one submit, ordered, fsync only after write); an accept→recv chain; a deliberately-failing chain (first op fails) shows the remainder -ECANCELED and the chain future resolves to the first error; IO_DRAIN orders a batch of writes before an fsync.

8.4 Acceptance Criteria

  • write→fsync via IO_LINK is correctly ordered (fsync sees the write's data); one submit.
  • Chain failure short-circuits: first link fails → all subsequent links -ECANCELED (I10); chain future returns the first error; no partial side effects beyond the failed point.
  • IO_HARDLINK continues past a tolerated non-fatal error.
  • IO_DRAIN barrier: writes complete before the drained fsync runs (verified by ordering of CQEs / data).
  • CQE_SKIP_SUCCESS reduces CQE count for a long successful chain while keeping accounting correct (I3).

8.5 Conformance Fixtures

  • op_sequences/link_write_fsync.golden. op_sequences/link_fail_cancel.json (first fails → rest -ECANCELED). op_sequences/hardlink_continue.json. op_sequences/drain_barrier.json. flags/cqe_skip_success.json (suppressed intermediate CQEs, correct accounting).

8.6 Pitfalls

  • Non-contiguous linked SQEs: links must be consecutive in the SQ; interleaving another op breaks the chain. Root: filling SQEs out of order. Debug: chain not ordered. Recover: submit the whole chain as one contiguous run; don't split across submit calls.
  • Forgetting the last link must NOT have IO_LINK → the chain links into whatever SQE follows (a different op). Recover: clear the flag on the final link.
  • Mis-accounting skipped success CQEs → slab_live drifts (slot never freed because its CQE was suppressed). Root: not freeing the slot for a CQE_SKIP_SUCCESS link on the chain's terminating CQE. Recover: free skipped-success slots when the chain completes (I3).
  • Assuming IO_DRAIN only drains its link → it drains all prior SQEs (a full barrier, expensive). Recover: use sparingly; prefer IO_LINK for local ordering.
  • -ECANCELED mistaken for a real error → wrong error reported. Recover: distinguish "this link failed" (the root cause E) from "cancelled due to an earlier failure" (-ECANCELED); report E (I10).

8.7 Performance Concerns

Chains cut syscalls and round-trips (accept→recv→send in one submit vs three). CQE_SKIP_SUCCESS reduces CQ pressure for long chains. But IO_DRAIN is a hard barrier that serializes the ring — avoid on the hot path. Linked ops can't be reordered by the kernel for efficiency, so over-linking can hurt throughput vs independent ops. Link only where ordering is required.

8.8 Edge Cases

A single-op "chain" (no links, normal op); a chain where the last op fails (no subsequent to cancel; future gets that error); a chain with a LINK_TIMEOUT as the second link (bounds the first); an empty chain (no-op); a chain longer than sq_space (must fit in one submit — cap or split semantics documented).

8.9 Failure Analysis

A broken chain (non-contiguous) → ops run unordered → data corruption (fsync before write). Detection: differential ordering test; recover: contiguous submission discipline. Skipped-CQE slot leak → slab_live growth → inflight cap; detection: leak-checker; recover: I3 accounting for skipped successes. -ECANCELED misreport → confusing errors in logs; detection: chain trace; recover: I10 error attribution.

8.10 Operational Notes

Metrics: chains_submitted, chain_canceled, chain_len_p99, drain_barriers, skipped_success_cqe. tools/cqe-decoder shows link flags + chain membership. Runbook note: a chain hung at step k → check the link flags + the failing link's error. Chains are the foundation for low-latency request pipelines that a protocol layer (#321/#33) would build on.

Phase 9 — Provided Buffers + Buffer Rings: PROVIDE_BUFFERS / buf_ring, BUFFER_SELECT, Multishot accept/recv/poll (IORING_CQE_F_MORE), Zero-Alloc Receive, Replenishment

9.1 Objectives

The zero-allocation receive path + amortized syscalls. Provided buffers (PROVIDE_BUFFERS classic, then buf_ring modern): donate a pool of buffers to the kernel; ops with IOSQE_BUFFER_SELECT pick one at completion (the Cqe.flags upper bits carry the buffer id). Multishot accept/recv/poll: one SQE yields many CQEs (IORING_CQE_F_MORE set) until terminated — one submit serves many events. Together: a single multishot RECV on a connection, drawing buffers from a buf_ring, with zero per-recv allocation and zero per-recv submit.

9.2 Detailed Implementation Steps

This phase realizes the zero-allocation hot path (principle 9/P9) and the thin-lowering rule (principle 10/P10); the multishot + buf_ring mechanics follow Axboe "What's new in io_uring" (Required Reading paper 2) and are gated by the feature probe (ADR-030, I12).

  • urt-fixed/provide.rs: classic PROVIDE_BUFFERS(addr=base, len=buflen, nr, bgid, bid) donates nr buffers to buffer-group bgid. An op with BUFFER_SELECT + buf_index=bgid lets the kernel pick a buffer; the CQE returns the chosen bid in flags (IORING_CQE_F_BUFFER).
  • urt-fixed/buf_ring.rs: the modern buf_ring — a mmap'd ring of buffer descriptors registered via IORING_REGISTER_PBUF_RING; the kernel consumes buffers from the head, we replenish at the tail. No PROVIDE_BUFFERS syscall per replenish (the win). Buffer id + len come back in the CQE.
  • Multishot: recv_multishot(fd) submits one RECV with the multishot flag; each incoming datagram/segment yields a CQE with F_MORE set + a bid from the buf_ring; the slot stays alive (I3). The terminating CQE (no F_MORE, e.g., -ENOBUFS when the ring is empty, or -ECANCELED) frees the slot and signals re-arm.
  • accept_multishot: one ACCEPT yields a CQE per new connection (F_MORE); no re-submit per accept.
  • poll_multishot: one POLL_ADD (multishot) yields a CQE per readiness edge.
  • Replenishment: as the application consumes a buffer (returns it), push its descriptor back onto the buf_ring tail (a plain memory write + tail bump — no syscall). Track outstanding buffers to avoid -ENOBUFS (the kernel completes with -ENOBUFS if no buffer is available → re-arm after replenishing).

9.3 Deliverable

The echo server rewritten with multishot RECV + a buf_ring: one submit per connection serves all its reads, buffers cycle through the ring with zero per-read allocation; throughput + p99 improve markedly vs Phase 5; multishot ACCEPT serves the accept loop with one SQE.

9.4 Acceptance Criteria

  • Multishot RECV: one SQE → N CQEs (F_MORE) for N segments; slot survives until terminated (I3); data correct (differential vs single-shot).
  • buf_ring: zero per-recv heap allocation (verified by an allocation counter ≈ 0 in steady state); buffers cycle correctly; the right bid maps to the right buffer.
  • -ENOBUFS handled: ring exhausted → op completes -ENOBUFS, application replenishes, re-arms; no data lost (the segment is re-delivered on re-arm or the peer retransmits — document TCP vs UDP semantics).
  • Multishot ACCEPT: one SQE serves many connections; connections_active correct.
  • Throughput/p99 win vs Phase 5 echo on the same load (headline benchmark, Performance Engineering).

9.5 Conformance Fixtures

  • op_sequences/multishot_recv.golden (1 SQE → N CQEs with F_MORE). op_sequences/buf_ring_cycle.json (buffers selected + replenished). op_sequences/multishot_accept.golden. flags/buffer_select.json (BUFFER_SELECT returns bid). Negative: overflow/enobufs_rearm.json (ring exhausted → -ENOBUFS → replenish → re-arm).

9.6 Pitfalls

  • Freeing/reusing a provided buffer before the application is done with it → the data is overwritten by the next recv. Root: replenishing the buffer to the ring before consuming it. Debug: corrupted received data. Recover: replenish only after the application has copied/consumed the buffer (the buffer is owned by the app between the CQE and replenish — a third ownership phase).
  • Multishot slot freed on the first CQE → subsequent F_MORE CQEs hit a freed slot (UAF/wrong demux). Recover: keep the slot until the terminating CQE; only the no-F_MORE CQE frees it (I3).
  • -ENOBUFS not handled → the multishot op terminates and recv silently stops on that connection (a stall, not a crash). Debug: a connection that stops receiving after a burst. Recover: detect -ENOBUFS, replenish, re-arm the multishot op.
  • Buffer-id aliasing (two ops in the same group select the same bid) → shouldn't happen (the kernel hands out distinct buffers) but a replenish bug can double-add a bid. Recover: track outstanding bids; assert uniqueness.
  • Mixing classic PROVIDE_BUFFERS and buf_ring for the same group → undefined. Recover: pick one per group; prefer buf_ring where probed.

9.7 Performance Concerns

This is the throughput phase. buf_ring removes the PROVIDE_BUFFERS syscall per replenish (a memory write instead). Multishot removes the per-event submit (one SQE serves a burst). Together they push the echo path toward the ≥1 M ops/s/core target with ≈0 allocation. Buffer pool sizing: too small → -ENOBUFS stalls; too large → memory waste; size to the bandwidth-delay product. Buffer size: match the typical segment to avoid MSG_TRUNC/waste.

9.8 Edge Cases

Ring with one buffer (serialized recv); a recv larger than the buffer (MSG_TRUNC/partial); multishot op cancelled mid-stream (terminating -ECANCELED, buffers in flight retained — I8); all buffers outstanding (next recv -ENOBUFS); a buf_ring on a kernel that lacks it (probe → fall back to classic PROVIDE_BUFFERS or per-op buffers — I12).

9.9 Failure Analysis

Provided-buffer corruption (premature replenish) → wrong data delivered to the application; detection: differential echo mismatch; containment: the consume-before-replenish ownership rule. -ENOBUFS stall → a connection stops receiving; detection: enobufs_events + a per-connection idle alarm; recover: replenish + re-arm. Multishot UAF (slot freed early) → corruption; detection: ASan on the multishot soak; containment: I3.

9.10 Operational Notes

Metrics: buf_ring_size, buffers_outstanding, enobufs_events, multishot_cqes, multishot_rearm, alloc_per_op (target ≈0). tools/cqe-decoder shows F_MORE + the selected bid. Runbook: a stalled connection → check enobufs_events + replenishment. This phase's numbers are the project's headline performance claim; the Performance Engineering benchmark table gates them.

Phase 10 — SQPOLL: Kernel Submission-Polling Thread, IORING_SQ_NEED_WAKEUP, Busy-Poll vs Latency/CPU, COOP_TASKRUN / DEFER_TASKRUN, Per-Kernel Feature Probing + Capability Matrix

10.1 Objectives

Reach zero syscalls per op on submission: IORING_SETUP_SQPOLL runs a kernel thread that polls the SQ tail, so io_uring_enter is unneeded to submit (only to wake the parked poll thread). Handle the IORING_SQ_NEED_WAKEUP race (I13). Tune the busy-poll vs latency/CPU tradeoff (sq_thread_idle). Add IORING_SETUP_COOP_TASKRUN/DEFER_TASKRUN for completion-side efficiency. Build the per-kernel feature probe + capability matrix (I12) that gates every advanced feature used in §7–11.

10.2 Detailed Implementation Steps

This phase implements the feature-probe-then-degrade rule (principle 8/P8, ADR-030, I12) and the SQPOLL design from Axboe "Efficient IO with io_uring" + "What's new in io_uring" (Required Reading papers 1–2); the kernel-version → feature mapping comes from the Linux io_uring commit logs / liburing changelog (paper 12).

  • urt-sqpoll/sqpoll.rs: set IORING_SETUP_SQPOLL + sq_thread_idle (ms) + optional sq_thread_cpu (pin the poll thread) at setup. After filling SQEs + publishing the tail (Release), submission needs no syscall — the kernel thread sees the tail.
  • urt-sqpoll/wakeup.rs: the NEED_WAKEUP race (I13) — after publishing the tail, check SQ.flags & IORING_SQ_NEED_WAKEUP; if set (the poll thread parked due to idle), call io_uring_enter(0, 0, IORING_ENTER_SQ_WAKEUP) to wake it. Missing this check → the SQE sits unsubmitted forever (a hang).
  • urt-sqpoll/taskrun.rs: IORING_SETUP_COOP_TASKRUN (run completion task-work cooperatively, fewer IPIs) and IORING_SETUP_DEFER_TASKRUN (defer completion processing to when the app calls enter(GETEVENTS) — better for thread-per-core). Probe + enable where beneficial.
  • urt-probe/probe.rs: at startup, io_uring_register(IORING_REGISTER_PROBE) returns the supported opcodes; uname gives the kernel version; combine into a Features bitset (caps.rs) + a human-readable matrix.rs. Every advanced op checks the mask before submit (I12).
  • Capability matrix: a table mapping kernel version → available features (SQPOLL ≥5.1, multishot accept ≥5.19, buf_ring ≥5.19, DEFER_TASKRUN ≥6.1, etc.) — used to gate + to choose fallbacks.

10.3 Deliverable

The echo/NOP benchmark run with SQPOLL shows 0 submit syscalls/op (verified by strace/perf syscall count); the NEED_WAKEUP race is handled (no stalls under bursty load); the capability matrix prints the host's feature set; features absent on an older kernel are gated and fall back.

10.4 Acceptance Criteria

  • SQPOLL: submission syscall count == 0 in steady state (the sqpoll_syscalls_per_op gauge ≈ 0); only wakeup enters when the poll thread parked.
  • NEED_WAKEUP handled: under bursty submit-after-idle, no op stalls (I13) — a soak with idle gaps shows every SQE picked up.
  • CPU/latency tradeoff characterized: a tuning curve of sq_thread_idle vs CPU% vs p99 latency in the benchmark report.
  • Feature probe correct: the capability mask matches the host kernel; an op gated off on an unsupported kernel uses its fallback (multishot→re-arm, buf_ring→per-op) with no -EINVAL (I12).
  • DEFER_TASKRUN (where available) reduces completion-side overhead vs default (measured).

10.5 Conformance Fixtures

  • op_sequences/sqpoll_zero_syscall.json (syscall count == 0 steady state). op_sequences/sqpoll_wakeup_race.json (idle → submit → NEED_WAKEUP → wake → completes). caps/matrix_5.6.json, caps/matrix_6.1.json (expected feature masks per kernel). Negative: caps/gate_multishot_old.json (multishot gated off on <5.19 → re-arm fallback).

10.6 Pitfalls

  • Missing the NEED_WAKEUP check → the #1 SQPOLL bug: after the poll thread idles out, submissions are never picked up; the runtime hangs. Root: assuming SQPOLL never needs enter. Debug: inflight stalls after an idle period; sq_depth not draining. Recover: always check NEED_WAKEUP after publishing the tail (I13).
  • SQPOLL burns a full core even when idle if sq_thread_idle is too high → wasted CPU. Recover: tune sq_thread_idle low for latency, high for throughput; pin the thread (sq_thread_cpu); SQPOLL is a throughput/low-latency-at-CPU-cost tradeoff, not a default.
  • SQPOLL requires privileges / a recent kernel for unprivileged use → setup -EPERM on older kernels. Recover: probe; fall back to non-SQPOLL (still correct, just one syscall per submit batch).
  • DEFER_TASKRUN without calling enter(GETEVENTS) → completions never processed (they're deferred to the next enter). Root: assuming completions arrive without enter. Recover: the reactor always enter(GETEVENTS) when reaping under DEFER_TASKRUN.
  • Assuming a feature exists (no probe) → -EINVAL at runtime on a customer's older kernel. Recover: probe everything; gate (I12).

10.7 Performance Concerns

SQPOLL trades a dedicated kernel core for zero submit syscalls — a big win at high op rates, a loss at low rates (idle core). Best paired with a busy reactor + multishot + buf_ring. COOP_TASKRUN/DEFER_TASKRUN cut completion-side IPIs/overhead, especially in thread-per-core where the app polls. The sq_thread_idle knob is the central latency/CPU dial. Pin SQPOLL + the reactor to sibling cores for cache locality.

10.8 Edge Cases

Submit while the poll thread is mid-park (the race window — NEED_WAKEUP may be set just after our check; handle by re-checking or always waking on the first submit after idle); SQPOLL with a very low op rate (idle core — disable SQPOLL); SQPOLL on a single-core machine (poll thread + app contend — discouraged); a kernel that supports SQPOLL but not DEFER_TASKRUN (gate the latter); probe on a kernel without REGISTER_PROBE (very old — fall back to a version table).

10.9 Failure Analysis

SQPOLL stall (NEED_WAKEUP missed) → runtime-wide hang (every submit affected); detection: sqpoll_stalls + inflight stall + sq_depth flat; the highest-severity SQPOLL bug; containment: I13 + a soak with idle gaps in CI. Wasted CPU (idle SQPOLL core) → cost, not correctness; detection: SQPOLL core at 100% with low op rate; recover: tune/disable. Unprobed feature use → -EINVAL crash on old kernels; detection: unsupported_feature_use; containment: I12.

10.10 Operational Notes

Metrics: sqpoll_enabled, sqpoll_syscalls_per_op (target 0), sqpoll_wakeups, sqpoll_stalls (target 0), sq_thread_cpu_pct, defer_taskrun_enabled. tools/ring-inspector shows NEED_WAKEUP. Phase 11 — Cancellation + Structured Concurrency: ASYNC_CANCEL (by user_data / fd / all), Drop Semantics for In-Flight Ops, Future Timeouts, Graceful Runtime Shutdown (Drain), Leak-Free

11.1 Objectives

Finish the cancellation + lifecycle story whose mechanics began in §2: ASYNC_CANCEL by user_data, by fd, or all; the drop-then-await-CQE-before-freeing-buffer dance (I8) made fully correct; future timeouts (building on §6 LINK_TIMEOUT); structured concurrency (a scope that cancels its children on exit); and graceful runtime shutdown that drains all in-flight ops, leak-free (I1). This is where I1 and I8 are completed and proven.

11.2 Detailed Implementation Steps

  • urt-driver/cancel.rs: cancel(target) → ASYNC_CANCEL(addr=user_data, cancel_flags); variants IORING_ASYNC_CANCEL_FD (cancel all ops on an fd), IORING_ASYNC_CANCEL_ALL (everything). The cancel itself produces a CQE (0 = found+cancelled, -ENOENT = already done/not found, -EALREADY = cancel in progress).
  • The drop dance (I8): an in-flight op's future Drop → slot phase Cancelling, submit ASYNC_CANCEL(user_data), retain the buffer in the slot. The original op then completes with -ECANCELED (or its real result if it raced to completion); the reactor frees the slot + drops the buffer then. Two CQEs may arrive (the op's + the cancel's); both must be reaped before the slot is freed (track expected-CQE count).
  • Future timeouts: timeout(dur, fut) (from §6) now uses the full cancel path on the loser; with_deadline attaches a LINK_TIMEOUT.
  • Structured concurrency: a scope (à la JoinSet) owns a set of spawned tasks; dropping/exiting the scope cancels all children (cancels their in-flight ops, awaits their CQEs) before returning — no orphaned I/O escapes the scope.
  • Graceful shutdown (Runtime::shutdown): stop accepting new tasks; cancel all in-flight ops (CANCEL_ALL); drive the reactor until slab_live == 0 and all FDs closed; then unmap rings. Bounded by a deadline (default 2 s); a forced shutdown after the deadline logs leaked resources (I1).

11.3 Deliverable

Dropping a pending recv cancels it and frees its buffer only after the CQE (ASan-clean under a cancel-storm); timeout and scope cancel cleanly; Runtime::shutdown drains thousands of in-flight ops and returns with slab_live==0, open_fds==baseline, live_buffers==0 (I1).

11.4 Acceptance Criteria

  • Cancel-storm soak is leak- and UAF-free (I8): spawn + cancel thousands of in-flight ops repeatedly; ASan/Miri clean; slab_live returns to baseline each cycle.
  • Drop-while-inflight retains the buffer until the (cancel) CQE (I8); both the op's and the cancel's CQEs are reaped before the slot frees.
  • cancel by fd / cancel all cancel the right set; -ENOENT for already-done ops handled (not an error).
  • Structured scope cancels all children on exit; no op escapes the scope (verified by inflight count after the scope returns).
  • Runtime::shutdown drains in ≤ 2 s; slab_live==0, open_fds==baseline, live_buffers==0 (I1); a forced-shutdown path logs any leak.

11.5 Conformance Fixtures

  • cancel/drop_cancel_storm.json (mass drop → cancel → drain, leak-free). cancel/cancel_by_fd.json. cancel/cancel_all.json. cancel/scope_cancels_children.json. cancel/graceful_shutdown.json (drain to zero). Negative: cancel/cancel_already_done.json (-ENOENT benign).

11.6 Pitfalls

  • Freeing the buffer when the cancel is submitted (not when the CQE arrives) → UAF: the original op may still complete into the buffer. Root: treating ASYNC_CANCEL as synchronous. Debug: ASan on the cancel-storm. Recover: retain until both the op's and cancel's terminating CQEs (I8, principle 2).
  • Not reaping the cancel's own CQE → a leaked slot (the cancel op's slot) + slab_live drift. Recover: the cancel op also has a slot; reap its CQE.
  • Cancel race: the op completes successfully just as we cancel → the future was dropped, but the op succeeded (e.g., the recv got data). The data is discarded (buffer dropped); that's correct for a cancelled future, but the resource side effect happened. Document: cancellation is best-effort; a completed-but-cancelled op's effect is not undone.
  • Shutdown that closes the ring fd with ops in flight → the kernel may still write into mapped memory we unmapped → UAF/SIGSEGV. Recover: drain then unmap (I1/I11).
  • Cancel-all during normal operation cancels ops other tasks still want. Recover: CANCEL_ALL only at shutdown; targeted cancel otherwise.

11.7 Performance Concerns

Cancellation is off the hot path (only on drop/timeout/shutdown). The cost is one ASYNC_CANCEL SQE + reaping an extra CQE per cancel. Structured-concurrency scope exit cancels in a batch (one submit for many cancels). Shutdown drain is bounded; a large in-flight set lengthens drain (bounded by the deadline). No steady-state overhead.

11.8 Edge Cases

Cancel an op that already completed (-ENOENT, benign); cancel an op mid-multishot (terminating -ECANCELED, in-flight buffers retained); double-cancel (-EALREADY); shutdown with zero in-flight (immediate); shutdown deadline exceeded (forced; log leaks); a task that spawns a child during scope teardown (rejected — scope is closing); cancelling a LINK_TIMEOUT-bounded op (both the op and its timeout cancel).

11.9 Failure Analysis

Cancel UAF (buffer freed too early) → corruption, the highest-severity bug, the very thing this project is built to get right; detection: ASan on the cancel-storm in CI (I8); containment: retain-until-CQE. Shutdown leak (drain incomplete) → orphan FDs/buffers; detection: slab_live/open_fds/live_buffers non-zero at exit (I1); recover: forced drain + log + (in tests) fail. Cancel-all blast radius → unrelated ops cancelled; containment: targeted cancel in normal operation.

11.10 Operational Notes

Metrics: cancels_issued, cancel_cqe{found,enoent,ealready}, scope_cancels, shutdown_drain_us, shutdown_forced (target 0), and the I1 leak gauges (slab_live, open_fds, live_buffers) which must be zero at exit. Runbook docs/runbooks/cancel-uaf.md + inflight-leak.md. This phase + §2 are the project's safety thesis; the cancel-storm ASan soak is the single most important correctness gate (alongside the loom ring suite).

Phase 12 — Portable Fallback Backend (epoll + Blocking Thread-Pool Emulation) + Validation: Conformance, Differential, Fuzz, Loom, Soak, Performance Gate

12.1 Objectives

Two deliverables. (1) The portable EpollPoolBackend: epoll readiness + a blocking worker pool that performs the syscall and posts a synthetic Cqe — producing identical Op/Cqe semantics so the same async program runs on non-Linux/sandbox/CI hosts (principle 12). (2) Validation that locks correctness + performance: conformance (golden op sequences), differential vs std blocking + (optionally) tokio, fuzz (SQE builder/flags/sequences), loom (waker/queue/ring races), soak (FD/buffer/slab-leak), and a perf gate (Mops, p99, SQPOLL syscalls=0).

12.2 Detailed Implementation Steps

  • urt-backend/epoll_pool.rs + worker.rs + synth_cqe.rs: register fds with epoll for readiness; on readiness, hand the op to a blocking worker thread that performs the actual pread/recv/etc. and posts a Cqe{user_data, res, flags} into a synthetic CQ (an in-memory SPSC queue) that the reactor reaps exactly like the uring CQ. Ops with no fd (NOP, TIMEOUT) are serviced directly by a worker/timer thread. The same buffer-ownership contract applies (the worker holds the buffer until it posts the synthetic CQE) so I2/I8 hold on both backends.
  • conformance/op_sequences/: golden SQE→CQE sequences per opcode, asserted on both backends (the differential-between-backends gate).
  • Differential vs std: each op's result compared to the equivalent std::fs/std::net blocking call (bytes, errors).
  • fuzz/fuzz_targets/: sqe_builder.rs (arbitrary op fields → builder never produces an invalid SQE / never panics), flag_combos.rs (arbitrary flag combinations → no UB), op_sequence.rs (random op sequences → no leak/hang under the emulation backend), cancel_race.rs (random drop/cancel timing → no UAF under ASan).
  • loom: models of the SQ tail / CQ head store-load (I7) and the waker clone/wake/drop (I11) — exhaustive interleavings green.
  • Soak: a long-running mixed workload (file + net + timers + cancels) under ASan with the leak gauges asserted to return to baseline (I1/I8).
  • Perf gate: criterion + the echo/file/nop harness; CI compares to a committed baseline and fails on regression beyond the gate (Performance Engineering benchmark table).
  • Observability endpoints: Prometheus exporter (urt-metrics), tracing spans, structured logs.

12.3 Deliverable

make conformance (both backends) + make loom + make fuzz-smoke + make soak (ASan) + make bench all green; the echo server runs unmodified on macOS/CI via the emulation backend; the uring backend hits the perf targets on a Linux ≥5.6 host.

12.4 Acceptance Criteria

  • Backend equivalence: every conformance op sequence produces identical Cqe semantics on UringBackend and EpollPoolBackend (the same async test passes on both).
  • Differential vs std blocking I/O: identical results/errors across the op set.
  • Fuzz smoke (5 min/target): no panic/UB/leak/hang; corpus retained.
  • loom: ring-index (I7) + waker (I11) suites green (exhaustive interleavings).
  • Soak (1 h, ASan): no FD/buffer/slab leak; the I1/I8 gauges return to baseline; zero UAF.
  • Perf gate: uring backend meets the Performance Engineering targets (≥3 M NOP/s/core, ≥1 M echo/s/core, p99 ≤ 60 µs, SQPOLL syscalls/op == 0); no >10% regression vs baseline.

12.5 Conformance Fixtures

  • All of conformance/op_sequences/, flags/, cancel/, overflow/, caps/ run on both backends. fuzz/corpus/* retained. The differential runner cross-checks vs std. Replay: captured op-sequence traces (urt-trace/capture.rs) re-run deterministically (the emulation backend is deterministic given a fixed worker schedule).

12.6 Pitfalls

  • Emulation that doesn't match uring semantics (e.g., epoll edge- vs level-triggered mismatch, or different short-read behavior) → the backend-equivalence gate fails / portable runs differ. Root: subtle readiness-vs-completion differences. Debug: the differential-between-backends diff. Recover: make the worker pool's behavior match uring's (e.g., one completion per submitted op, same partial semantics).
  • Emulation drops the buffer-ownership contract (worker frees the buffer early) → UAF on the portable path. Recover: the worker holds the buffer until it posts the synthetic CQE (I2/I8 on both backends).
  • Fuzzer finds a panic in the SQE builder on a weird flag combo. Recover: validate fields; reject impossible combos before building (no panic).
  • loom state-space explosion → CI timeout. Recover: minimize the model (just the indices + one producer/consumer), bound the interleavings, run the full suite nightly.
  • Bench flakiness on shared CI runners → false regressions. Recover: pinned-core bench host, relative thresholds, multiple runs, median+MAD (criterion).

12.7 Performance Concerns

The emulation backend is not a performance target — only a semantic one (a blocking thread pool can't match uring). Its overhead (thread handoff per op) is documented. Conformance at scale stresses the slab + reactor. loom + ASan runs are slow → nightly, not every PR. The bench host is pinned + isolated for stable tail-latency numbers.

12.8 Edge Cases

An op the emulation can't express 1:1 (e.g., IO_DRAIN ordering across a thread pool — emulate by serializing); a kernel feature the uring backend has but the emulation lacks (multishot → the emulation loops single-shot internally but presents the same CQE stream); a fuzz input that's a valid-but-degenerate op sequence (all NOPs, all cancels); soak under memory pressure (the buffer pool + slab must stay bounded); a CI host without uring (only the emulation backend runs — uring tests skipped with a clear marker).

12.9 Failure Analysis

Backend divergence → portable runs misbehave; detection: the equivalence gate; blocks release. loom/ASan failure → a concurrency/UAF bug (highest severity); blocks release. Perf regression → blocks release (gate). Soak leak → I1/I8 breach; blocks release. Containment: CI gates everything; nothing ships without green conformance (both backends) + loom + ASan-soak + bench.

12.10 Operational Notes

Compatibility & Versioning

  • Public API: SemVer; #[non_exhaustive] on Op/UrtError/Features allows additive opcodes/features within a major (ADR-031). Breaking changes → major bump + CHANGELOG.
  • Sqe/Cqe ABI: validated against the running kernel's io_uring.h at build/probe time; the layout follows the kernel, not us — a mismatch is a hard error, never a silent reinterpret. New kernel fields are additive (the struct is fixed-size 64 B; unions grow within it).
  • Backend semantics: UringBackend and EpollPoolBackend are behaviorally equivalent at the Op/Cqe level (the equivalence gate, §12); the same async program is portable across both.
  • Feature gating: features absent on the target kernel are gated + fall back; using the runtime on an older kernel degrades behavior (fewer syscall savings) but never breaks correctness (I12).
  • Op-sequence/trace format: versioned; used only for conformance/replay; matching major required to replay.
  • No on-disk format: rings/buffers/slab are scratch — no storage compatibility surface.
  • Semantic versioning policy: workspace crates share a major; pre-1.0 minor may break (documented). Deprecation: one minor of warning before removal.

Performance Engineering

  • Benchmarking: criterion micro (nop-throughput, submit-batch, reap-batch, waker) + macro (echo loopback Mops/p99, file read throughput) ± multishot/buf_ring/SQPOLL; relative thresholds vs a committed baseline.
  • Profiling: perf + flamegraphs (cargo flamegraph); hot paths = SQE prep, the reap loop + demux, the waker, the poll loop.
  • Syscall analysis: strace -c / perf trace to count io_uring_enter per op — must approach 0 with SQPOLL and 1-per-batch otherwise (the headline efficiency metric).
  • Allocator analysis: dhat/heaptrack to prove alloc_per_op ≈ 0 in steady state (buf_ring + slab reuse); any per-op allocation is a regression.
  • Lock analysis: thread-per-core means the hot path is lock-free (SPSC ring); measure only the optional work-stealing deque contention.
  • Cache analysis: perf stat cache misses on the reap loop + slab; keep OpState hot fields ≤ 1 line; pad shared ring indices to avoid false sharing; pin reactor + SQPOLL to sibling cores.
  • Batching analysis: sweep batch size (SQEs per enter) vs throughput (Little's law: deeper in-flight → higher throughput until the kernel saturates).
  • Tail latency: submit→completion p99/p999 under load; multishot + buf_ring remove per-event submit/alloc tail; SQPOLL removes the submit-syscall tail.
  • Memory profiling: the buffer pool + slab must stay bounded under soak; locked-memory (ulimit -l) accounted for the mmap + registered buffers.

Scalability Analysis

  • Bottlenecks: per-op syscall (removed by batching + SQPOLL); per-op allocation (removed by buf_ring + slab); per-event submit (removed by multishot); the reap loop + demux (kept O(1) per CQE via the slab). At scale the limit is kernel/NIC/NVMe throughput, not the runtime.
  • Scaling ceilings: single machine; cores (thread-per-core scales near-linearly because each core has its own ring + reactor + slab — shared-nothing); CQ depth (sized to absorb multishot bursts); FD budget; locked memory for the mmap + registered buffers.
  • Horizontal scaling: out of scope (single machine); a protocol/cluster layer (#321/#33) would sit above. SO_REUSEPORT shards connections across per-core listeners — the per-core seam is the scaling unit.
  • Vertical scaling: add cores → add rings + reactors (one each per core); no cross-core synchronization on the hot path (principle 7). Optional work-stealing balances uneven load at the cost of cross-core wakeups.
  • Sharding/partitioning: connections sharded across cores via SO_REUSEPORT; per-core rings are independent; buffers + slabs are per-core (no contention).
  • Coordination overhead: none on the hot path (SPSC rings, per-core state). Cross-core spawn / work-stealing is the only coordination, used sparingly and measured.
  • Network/storage fanout: bounded by NIC/NVMe; deep in-flight queues (Little's law) keep the device busy; batching + multishot amortize per-op cost.
  • Scheduler saturation: the executor poll loop is O(ready tasks); the reactor reap is O(completions); both batch. SQPOLL offloads submission to a kernel core.
  • Storage/metadata growth: none persistent; the slab + buffer pool are bounded; the ring is fixed-size.

Mental Models & First Principles

The compressed intuitions an expert holds while designing or debugging this runtime. Each states the insight, what it predicts, the bug class you write without it, and where this blueprint applies it.

MM1 — The SQ and CQ are SPSC rings; the kernel is the other endpoint. Each ring has exactly one producer and one consumer, and for one of the two endpoints that party is the kernel: on the SQ we produce, the kernel consumes; on the CQ the kernel produces, we consume. Predicts: the same acquire/release reasoning used for a userspace lock-free SPSC queue applies verbatim across the syscall boundary — publish the tail with release after writing the entry, read the tail with acquire before reading the entry. Bug without it: you reach for a mutex or SeqCst everywhere (slow) or, worse, plain loads (torn/missed completions). Applied: §8.4, §Phase 1 (I7), §Phase 12 (loom).

MM2 — A Future is a state machine; the executor is its clock and the reactor is its interrupt controller. poll advances the machine one step; it returns Pending when blocked and registers a Waker; the reactor, on a completion, fires that waker to re-tick the clock. Predicts: a "lost wakeup" is exactly a missed interrupt — the machine stalled because the edge that would advance it was dropped between the poll and the waker store. Bug without it: storing the waker without re-checking the result (the register-then-check race) → permanent hang. Applied: §8.6, §Phase 3 (I11).

MM3 — In completion I/O, ownership is the safety boundary, not borrowing. The kernel touches the buffer after the syscall returns, so the compiler's borrow scope no longer covers the danger window; only ownership (the buffer lives inside the Op until the CQE) does. Predicts: every safe completion API must move the buffer in and return it out — there is no sound borrowed form. Bug without it: freeing/reusing a buffer on future-drop → use-after-free when the op completes (the canonical io_uring bug). Applied: §1 (central safety problem), §6 (P1/P2), §Phase 2, §Phase 11 (I2/I8).

MM4 — Cancellation is a request, not a guarantee; the buffer is hostage until the cancel resolves. ASYNC_CANCEL asks the kernel to stop an op, but the original op still produces a terminating CQE (its real result or -ECANCELED). Predicts: you must wait for that CQE before freeing the buffer — dropping the future cannot synchronously reclaim memory. Bug without it: free-on-drop UAF, and leaked slots from un-reaped cancel CQEs. Applied: §8.5, §Phase 11 (I8), §6 (P2).

MM5 — Throughput is governed by Little's law: in-flight = throughput × latency. To hit a target ops/s at a given per-op latency you must keep that many ops in flight; a shallow queue caps throughput regardless of CPU. Predicts: batching submit and reaping deep raise throughput by raising in-flight depth, up to the device/kernel saturation point; the SQ/CQ depths must be sized to the bandwidth-delay product. Bug without it: submitting one-at-a-time and blaming the kernel for low throughput. Applied: §4 (constraints), §Phase 1 (batching), Performance Engineering.

MM6 — Each SQE yields exactly one terminating CQE; multishot yields many-then-one. One-shot ops complete once; multishot ops deliver a stream of IORING_CQE_F_MORE CQEs then one without it. Predicts: slot lifetime is bounded by the terminating CQE, not the first — freeing on the first multishot CQE corrupts the demux. Bug without it: slot leak (never freed) or double-free (freed early, then a later CQE hits a reused slot). Applied: §8.5, §Phase 2 (I3), §Phase 9 (multishot).

MM7 — The kernel ABI is a moving target; capability is runtime state, not a compile-time constant. Opcodes, flags, SQPOLL, buf_ring, and DEFER_TASKRUN were each introduced in specific kernel versions. Predicts: the only safe design probes at startup and gates each feature behind a real fallback; a feature works on your laptop and -EINVALs on the customer's older kernel otherwise. Bug without it: runtime -EINVAL crashes on deployment. Applied: §Phase 10 (I12), §6 (P8).

MM8 — Thread-per-core turns concurrency into parallelism with no shared state. One ring + reactor + executor per core, connections sharded by SO_REUSEPORT, means the hot path has no cross-core synchronization — the ring stays SPSC because there is exactly one submitter and one reaper per ring. Predicts: scaling is near-linear in cores until the device saturates; adding a global lock or shared scheduler reintroduces the contention you designed away. Bug without it: torn ring indices / data races from cross-thread submission. Applied: §6 (P7), §Phase 3, Scalability Analysis, ADR-008.

MM9 — A dropped completion is unrecoverable; a slow one is merely slow. A CQE that is never delivered (ordering bug, overflow loss, SQPOLL stall) hangs the awaiting task forever; everything else (backpressure, overflow backlog, fallback) degrades gracefully. Predicts: the design must bias toward reaping/draining/retrying over speed, and the single most important production signal is sqe_submitted − cqe_reaped drift. Bug without it: optimizing away a fence or skipping an overflow check to save a cycle, trading a permanent hang for a tiny speedup. Applied: §6 (P15), §Phase 1 (I9), Failure Modes & Recovery.

MM10 — Zero-copy is only zero-copy if the buffer never moves and is never copied. Registered buffers and buf_ring exist so the kernel can DMA directly to/from app memory; a growable Vec that reallocs, or a defensive copy, defeats the entire point. Predicts: hot-path buffers must be pinned (immovable) and drawn from a pool/ring, and the API must not hide a copy. Bug without it: a reallocating buffer dangles the kernel's mapping (-EFAULT/UAF), or a hidden copy caps throughput. Applied: §6 (P9/P10), §Phase 7 (fixed buffers, I14), §Phase 9 (buf_ring).

Linux io_uring (the kernel interface, Axboe). Where io_uring is the substrate, urt is the runtime that gives it a futures face and a portable fallback; io_uring wins outright when you can target a fixed recent kernel and want no abstraction tax.

epoll + thread pool (the classic portable async). Its differentiating decision is readiness + blocking offload: epoll says when an fd is ready, a worker does the synchronous syscall. This keeps buffer ownership trivial (the caller owns it throughout) and runs everywhere POSIX runs — which is exactly why urt adopts it as the EpollPoolBackend for non-Linux/sandbox hosts (§Phase 12). Tokio (default multi-thread, readiness). Tokio wins for bursty, uneven, mostly-CPU workloads and for the maturity of its ecosystem; tokio-uring is its completion-based sibling and the closer comparison for the buffer pattern.

glommio (DataDog, thread-per-core io_uring). The closest relative: completion-based, thread-per-core, shared-nothing, buf_ring — nearly the same dimension choices as urt. The difference is intent and scope: glommio is a production runtime with rich ergonomics (Latch/Local), Linux-uring-only; urt is a teaching-grade build that additionally ships the portable epoll backend and builds the syscall layer from scratch. glommio wins for real thread-per-core storage/network services on Linux today; urt wins as the artifact that teaches every layer beneath glommio.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints (§4). Inputs are stated; formulas are shown.

  1. SQE ring bytes. sq_entries × sizeof(Sqe) = 4096 × 64 B = 256 KiB for the SQE pool. Plus the SQ index ring sq_entries × 4 B (the array of u32 indices) = 16 KiB. SQ region ≈ 272 KiB.

  2. CQE ring bytes. cq_entries × sizeof(Cqe) = 8192 × 16 B = 128 KiB (CQ is 2× SQ to absorb multishot bursts, §4). With SETUP_CQE32 (32 B): 256 KiB. CQ region ≈ 128–256 KiB.

  3. Per-ring fixed memory. SQ + CQ ≈ 272 + 128 = ~400 KiB per ring, locked (counts against ulimit -l). At thread-per-core on a 64-core host: 64 × 400 KiB = ~25 MiB of locked ring memory before any data buffers.

  4. In-flight slab footprint. Hot OpState fields (phase u8 + result (i32,u32) + waker fat ptr 16 B + flags) ≈ 40 B; padded to keep ≤1 cache line = 64 B/slot. At the default 65 536 inflight cap (FD budget, §4): 65 536 × 64 B = 4 MiB/core worst-case slab.

  5. Max IOPS from queue depth and latency (Little's law, MM5). max_in_flight / latency. With SQ depth 4096 and a 15 µs p50 completion latency: 4096 / 15 µs ≈ 273 M ops/s if the device kept up — i.e., queue depth is not the limit; the device is. To sustain the 3 M NOP/s/core target at 15 µs each you need only 3e6 × 15e-6 = 45 ops in flight — comfortably under 4096.

  6. Syscalls saved by batching. Submitting a batch of B SQEs costs one io_uring_enter instead of B. At B = 256 (the saturation batch target, Performance Engineering): 255/256 ≈ 99.6% of submit syscalls eliminated vs one-per-op. At the 3 M ops/s target: one-per-op = 3 M enter/s; batched at 256 = ~11.7 K enter/s; with SQPOLL = 0.

  7. Submission-batch amortization. If io_uring_enter costs ~1 µs, one-per-op at 3 M ops/s spends 3 M × 1 µs = 3.0 s of CPU per wall-second (impossible on one core). Batched at 256: 11.7 K × 1 µs = ~11.7 ms/s (~1.2% of a core). This is why batching is mandatory, not optional.

  8. Echo bandwidth at target rate. 1 M echo ops/s/core × (recv + send) with a typical 1 KiB segment: 1e6 × 1 KiB × 2 = ~2 GiB/s/core of payload moved — within loopback/10–100 GbE NIC reach, confirming the runtime, not the wire, is what the benchmark stresses.

  9. buf_ring sizing (bandwidth-delay product). Buffers outstanding ≈ throughput × time-held. At 1 M recv/s/core and a 50 µs app hold time per buffer: 1e6 × 50e-6 = 50 buffers minimum; size the ring to ~2–4× = 128–256 buffers to avoid -ENOBUFS stalls (§Phase 9). At 1 KiB each: 128–256 KiB/core of buffer-ring memory.

  10. Registered-buffer memory. Registering N fixed buffers of size S pins N×S of locked memory for the runtime's life. For 256 × 64 KiB read buffers: 256 × 64 KiB = 16 MiB/core locked — must fit under ulimit -l alongside the ring memory (item 3).

  11. FD budget vs registered-files table. With the 65 536 default FD cap (§4) and a fixed-files table sized to it: 65 536 × 4 B (an fd is an i32 in the table) = 256 KiB for the registered-files index — negligible, so sizing the table to the full budget is cheap.

  12. Graceful-drain bound. Shutdown drains all in-flight ops within the 2 s deadline (§4). Worst case at the inflight cap with a 60 µs p99 completion: 65 536 × 60 µs = ~3.9 s if drained serially — so drain must reap in batches (one enter(GETEVENTS) reaps thousands), bringing it well under 2 s; this derivation is why the drain loop batches rather than awaits one CQE at a time.

Alternative Architectures (Roads Not Taken)

Three fundamentally different architectures for the same goal — a high-performance async I/O runtime — each with the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

A1 — Readiness reactor (epoll/kqueue proactor-free event loop).

  app ──register interest──► [ epoll/kqueue ]
   ▲                              │ fd ready
   │ do sync syscall now          ▼
  [ event loop ] ◄──readiness── kernel
   │  (kernel touches buffer ONLY inside the sync syscall)
   ▼
  user owns buffer the whole time (borrow is sound)

Wins when: portability across all of POSIX matters most, async storage is not required (epoll does not do true async file I/O), and per-op syscall cost is acceptable. Real system: libuv (Node.js), Tokio's default reactor, mio. Why rejected here: the project's entire teaching thesis is the completion model and the buffer-ownership inversion it forces (§1, MM3); a readiness core would teach the opposite lesson and cannot reach zero-syscall submission or async storage. urt keeps it only as the fallback EpollPoolBackend (§Phase 12), never the primary.

A2 — Thread-per-blocking-syscall pool (synchronous I/O behind a worker pool).

  async op ──enqueue──► [ work queue ] ──► worker thread: blocking pread/recv
                                              │ completes
                                              ▼
                                        post result ──► waker

Wins when: the workload is low-concurrency or dominated by operations with no async kernel primitive, and simplicity beats efficiency; also the only portable way to "async-ify" truly blocking calls. Real system: the classic spawn_blocking pool in most runtimes; Go's netpoller offloads similarly under the hood. Why rejected as the core: a thread handoff per op (context-switch + cache pollution) caps throughput far below the ≥1 M ops/s/core target (§4) and adds tail latency; it cannot exploit batching or zero-syscall submission. urt uses exactly this pattern inside the EpollPoolBackend's worker pool and for spawn_blocking, but not as the hot path.

A3 — Pure userspace polling, kernel-bypass (SPDK/DPDK-style).

  app ◄──busy-poll──► [ userspace NVMe/NIC driver ] ──MMIO/DMA──► device
   (no syscalls at all; dedicated core spins on device queues)

Wins when: you own the hardware, can dedicate cores to busy-polling, and need the absolute lowest latency / highest IOPS with no kernel in the path. Real system: SPDK (storage), DPDK (networking), Seastar can drive both. Why rejected here: it bypasses the kernel entirely — there is no io_uring, no SQ/CQ ring to rebuild, and it requires device-specific userspace drivers and hugepages; it is a different project (kernel-bypass), not an io_uring runtime, and abandons portability and the general-purpose file/socket API. SQPOLL (§Phase 10) borrows the spirit (a polling thread to cut syscalls) while staying inside the kernel's safe, general interface — the deliberate middle ground.

5 run queue empty → reactor.turn(block): enter(submit=1, min_complete=1) slot2=InKernel SQ head→2 — (blocked)
6 client sends "hello"; kernel reads into buf, posts CQE{user_data=2, res=5}; enter returns slot2: on_cqe → result=(5,_) → Completed — CQ: tail.load(Acquire) 1→2 reactor wakes slot2.waker
7 reactor frees slot2, returns the buffer as (Ok(5), buf); CQ.head.store(Release) 1→2 slot2 freed (buffer moved OUT to the future) — CQ head→2 —
8 poll resumes: recv returns (5, buf); write_at(buf.slice(0..5)).await first poll → submit WRITE(user_data=3, fd=stdout, addr=buf.ptr, len=5) slot3=Submitted{buffer_owner=Op::Write{buf}} ← buffer pinned again (I2) SQ: fill sqes[2], array[2&7]=2, tail 2→3, store(Release) CQ 2/2 parks: slot3.waker = task; Pending
9 reactor.turn(block): enter(submit=1, min_complete=1) slot3=InKernel SQ head→3 — (blocked)
10 kernel writes 5 bytes, posts CQE{user_data=3, res=5}; enter returns slot3: on_cqe → (5,_) → Completed — CQ tail.load(Acquire) 2→3 reactor wakes slot3.waker
11 reactor frees slot3, returns (Ok(5), buf); buf returned to pool; CQ.head.store(Release) 2→3 slot3 freed — CQ head→3 —
12 poll resumes: write_at returns (5, buf); handle returns Ok(()); task completes; JoinHandle resolves slab empty SQ 3/3 CQ 3/3 done

Why no completion is lost (I7): at t=2/6/10 the reactor reads CQ.tail with Acquire, establishing that the kernel's Cqe payload writes are visible before it reads them; at t=0/4/8 the producer publishes SQ.tail with Release after filling the SQE, so the kernel sees the SQE fields before the advanced tail. The pair forms the happens-before edge that loom verifies.

Why no buffer UAF (I2/I8): from t=4 the recv buffer is owned by slot2's Op::Recv and the future holds no borrow; if the task were dropped at t=5 (mid-recv), slot2→Cancelling, an ASYNC_CANCEL(2) is submitted, and the buffer stays in slot2 until the recv's terminating CQE (-ECANCELED or a real result) is reaped — only then is the buffer dropped. The kernel can never write a freed buffer. The same holds for the write buffer from t=8.

Why one syscall per step here, and how it collapses: this trace blocks in enter per op for clarity (min_complete=1). In production: (a) the executor polls many ready tasks first, filling many SQEs, then the reactor does one enter for the whole batch (batching, §1); (b) with multishot RECV + buf_ring (§9), one ACCEPT and one RECV SQE serve many connections/segments — the per-event submit vanishes; (c) with SQPOLL (§10) the kernel poll thread picks up the SQ tail with zero submit syscalls (only a NEED_WAKEUP enter when it parked). The 12-step, 3-syscall trace becomes a near-syscall-free steady state at scale — the io_uring efficiency thesis, realized end to end.

Backpressure + overflow corners on this path: if at t=0 the SQ were full (sq_space()==0), the ACCEPT submit returns Backpressure (I6) — the handler awaits SQ space rather than overwriting an unconsumed SQE. If the reactor fell behind and the CQ filled before t=2, the kernel sets the overflow flag + dropped counter (I9); the reactor must reap (advancing CQ.head) and re-enter(GETEVENTS) to flush the backlog — no CQE is lost, so no task hangs.

Glossary

Term Definition
io_uring Linux async I/O interface (Axboe, 2019) using shared submission/completion rings; the model this project rebuilds.
Completion-based I/O The kernel performs the I/O and signals completion after the syscall returns; the buffer is touched later (vs readiness).
Readiness-based I/O The kernel signals when an fd is ready; the app does a synchronous syscall (epoll/select); it owns the buffer throughout.
SQ (Submission Queue) The ring of submission entries the app produces and the kernel consumes.
CQ (Completion Queue) The ring of completion entries the kernel produces and the app consumes.
SQE Submission Queue Entry — a 64-byte request (opcode + fd + addr + len + user_data + flags).
CQE Completion Queue Entry — a 16/32-byte result (user_data + res + flags).
user_data An opaque u64 the app puts in the SQE; the kernel echoes it in the CQE — the demux key (== OpId).
OpId The runtime's id for an in-flight op; equals user_data; the slab key.
Ring head/tail Producer/consumer indices into a ring; advanced with release, read with acquire.
Ring mask ring_entries − 1 (power-of-two depth) used to index the ring slot from the monotone index.
SQ array The indirection table mapping a ring slot to an SQE index (array[tail&mask]=sqe_idx).
Acquire/Release Memory-ordering constraints that establish happens-before across the kernel/user boundary (I7).
In-flight slab Slab<OpState> keyed by user_data; owns the buffer/fd-ref from submit until CQE (I2).
Buffer-ownership contract The rule that a submitted buffer/fd is owned by its Op until the CQE; dropping the future cannot free it (I2/I8).
(result, buffer) pattern Resource ops move the buffer in and return it out on completion, so no borrow escapes the future.
Reactor The component that reaps CQEs, demuxes by user_data, and wakes the parked tasks.
Executor The component that owns the run queue and drives Future::poll.
Task A spawned future + its state + a JoinHandle result channel.
Waker / RawWaker A handle that re-enqueues a task; built from a hand-written vtable (clone/wake/wake_by_ref/drop).
JoinHandle A handle that resolves to a spawned task's output.
Thread-per-core One executor + reactor + ring per core, shared-nothing; the ring is SPSC per side (Seastar/glommio).
Backpressure Submission blocks/awaits when the SQ is full, never overrunning (I6).
CQ overflow The CQ fills before the app reaps; the kernel sets a flag + dropped counter; never silently lost (I9).
Registered (fixed) buffers Buffers pre-mapped via io_uring_register; READ_FIXED/WRITE_FIXED skip per-op page pinning.
Registered (fixed) files An fd index table; IOSQE_FIXED_FILE skips per-op fd refcount/lookup.
Linked SQE chain Consecutive SQEs flagged IO_LINK that run in order; a failure cancels the remainder (-ECANCELED).
IO_DRAIN A barrier SQE that waits for all prior SQEs to complete before it runs.
Provided buffers A pool of buffers donated to the kernel; ops with BUFFER_SELECT pick one at completion.
buf_ring The modern provided-buffer ring (REGISTER_PBUF_RING); replenished without a per-buffer syscall.
Multishot One SQE that yields many CQEs (IORING_CQE_F_MORE) until terminated (accept/recv/poll).
IORING_CQE_F_MORE A CQE flag meaning more completions will follow for this SQE (multishot not yet terminated).
SQPOLL A kernel thread that polls the SQ tail so submission needs no syscall.
IORING_SQ_NEED_WAKEUP A flag the kernel sets when the SQPOLL thread parked; the app must wake it via enter(SQ_WAKEUP) (I13).
COOP_TASKRUN / DEFER_TASKRUN Setup flags that make completion-side task-work cheaper / deferred to the next enter.
ASYNC_CANCEL An op that cancels an in-flight op by user_data / fd / all.
-ECANCELED The result a cancelled op (or a downstream linked op) completes with.
Feature probe Startup query (REGISTER_PROBE + uname) building a capability mask to gate features (I12).
Capability matrix The table of which features each kernel version supports; drives gating + fallbacks.
Short read/write A READ/WRITE that transfers fewer bytes than requested (res < len); success, caller loops.
Emulation backend The portable epoll + blocking-worker-pool backend that synthesizes CQEs with identical semantics.
Drain (shutdown) Driving the reactor until all in-flight ops complete and FDs/buffers/slots return to baseline (I1).
Pinning Keeping a buffer's address stable (immovable) while an op references it.
loom A tool that exhaustively explores concurrent interleavings to prove the ring/waker ordering (I7/I11).
__kernel_timespec The kernel's 64-bit timespec used by TIMEOUT SQEs (not libc timespec).
