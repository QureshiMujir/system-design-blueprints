Decisions (§9) · 36 ADRs

ADR-01

Implementation language

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

Go (k8s' lang); C/C++; Python

When the rejected choice is right

Go wins for teams already operating Kubernetes at scale, extending its actual apiserver or client-go ecosystem, or building controllers intended for immediate k8s-compatible deployment — Go's interface{} Reconciler ecosystem and operator-sdk toolchain are more mature for that integration surface.

Why: GC tail-latency under watch fan-out + nil-iface/data-race classes are exactly a control-plane's failure modes; C/C++ memory-unsafe on syscall + untrusted-object hot path; Python lacks static guarantees + GIL. Rust: memory safety on kubelet/runtime syscall path, sum types + exhaustive match for PodPhase/WatchEvent, typed store API.

ADR-02

Async runtime

Chosen

Tokio (multi-thread scheduler)

Rejected

async-std (smaller ecosystem); thread-per-conn; smol

When the rejected choice is right

smol or async-std win when binary size and dependency count dominate (embedded targets, WASM), and the watch-fan-out scale is bounded below ~100 concurrent streams; thread-per-conn wins for CPU-bound workloads with short-lived connections where work-stealing overhead exceeds benefit.

Why: Thousands of concurrent watch streams + reconcile loops + per-pod PodWorker actors need work-stealing async; Tokio is the de-facto std with mature tokio::sync, timers, I/O.

ADR-03

Workspace structure

Chosen

Single Cargo workspace, nine orc-* crates (orc-api, -store, -apiserver, -controller, -scheduler, -kubelet, -runtime, -net, orctl)

Rejected

Monolithic crate; one crate per binary with copied model; many micro-crates

When the rejected choice is right

A monolithic crate wins during the earliest exploratory prototype phase when the component boundaries are unknown — eliminating workspace overhead is valid until the architectural seams are clear. Many micro-crates win in very large organizations with separate teams per component needing independent versioning and publish cadence.

Why: Enforces layering (api/store as leaf deps; binaries on top); shared compile of orc-api/orc-store types; independent test surfaces; mirrors k8s apimachinery/client-go/component split.

ADR-04

Persistence store

Chosen

Build orc-store from scratch (MVCC KV: WAL + keyspace, Revision, Watch, Lease, Txn, compaction)

Rejected

Embed etcd (out-of-proc, gRPC); embed sled / RocksDB directly as the API

When the rejected choice is right

Embedding etcd wins for production-first teams that need a battle-tested, Raft-replicated, multi-leader-capable store on day one and have no intent of learning MVCC internals. The operational cost (etcd sizing, defrag, snapshot scheduling) is paid by an existing etcd ops team.

Why: Goal is to learn MVCC + watch + lease semantics that the whole system depends on; an opaque etcd hides Revision/watch gap-freedom. sled/RocksDB kept as a deferred backing engine behind the Store trait (ADR-05).

ADR-05

Store backing engine

Chosen

Custom WAL + in-memory BTree index behind the Store trait

Rejected

RocksDB/sled as the day-1 engine

When the rejected choice is right

RocksDB as the day-1 backing engine wins when the keyspace is expected to exceed available RAM immediately — RocksDB's LSM-tree with block cache handles datasets larger than memory efficiently and its mature compaction tuning removes the need to hand-implement a WAL.

Why: Store trait is the seam; a B-tree+WAL is sufficient for single-node and fully understood. sled/RocksDB pluggable later for larger-than-RAM datasets without API change.

ADR-06

Replication / HA topology

Chosen

Single-node store + a Raft replication hook (cross-link project 42); deferred to Phase 13 (§24)

Rejected

Immediate multi-node quorum (Raft) in Phase 1; primary/replica async

When the rejected choice is right

Immediate multi-node Raft in Phase 1 wins when the system will run in production before Phase 13 and a single-node data loss event is unacceptable — if business availability SLAs require HA from the first deployment, the seam-first approach defers real risk.

Why: Orchestration core correctness is provable single-node first; Raft is orthogonal complexity. Hook = a Store-trait-level log-replication seam so HA drops in without controller/apiserver changes.

ADR-07

Object model representation

Chosen

Typed Rust structs (Pod, ReplicaSet, …) impl Object, in orc-api

Rejected

Go-style unstructured map[string]any; dynamic schemaless docs

When the rejected choice is right

Unstructured/dynamic representation wins when the system must process arbitrary CRDs or unknown kinds at runtime — a schema-registry-backed dynamic object model is necessary for a full CRD operator framework where types are not known at compile time.

Why: Sum types + struct validation catch malformed spec at compile/decode time; exhaustive match on PodPhase/strategy; no stringly-typed field access. Unstructured path reserved for the Custom-resource hook only.

ADR-08

Wire serialization

Chosen

serde + serde_json (JSON codec in orc-api)

Rejected

Protobuf; CBOR/MessagePack; bincode

When the rejected choice is right

Protobuf wins for the watch-stream inner loop at very high fan-out (>10k watchers, >10k events/s) where JSON serialization overhead becomes measurable — Kubernetes itself uses protobuf for internal component communication precisely at this scale threshold.

Why: JSON is the k8s API contract (human-debuggable, orctl apply of YAML->JSON); serde gives derive-based codec with field selectors. Protobuf reserved as a later watch-transport optimization, not the API surface.

ADR-09

resourceVersion semantics

Chosen

ObjectMeta.resource_version (String) == decimal of store Revision at last write

Rejected

Per-object monotonic counter; ETag hash; wall-clock timestamp

When the rejected choice is right

Per-object monotonic counter wins if the store shards by resource kind and there is no global Revision — in a sharded store architecture each shard has its own sequence, and a global logical clock across shards requires a coordination layer that may not be present.

Why: One global logical clock unifies object RV, list RV, and watch start point; makes watch-from-RV + compaction-expiry well-defined. Hashes/timestamps cannot order writes or seed a gap-free watch.

ADR-10

Concurrency control

Chosen

Optimistic: apiserver does store Txn compare-and-set on resourceVersion; mismatch -> 409 Conflict, caller re-reads + retries

Rejected

Pessimistic locks; last-write-wins; row versioning in SQL

When the rejected choice is right

Pessimistic locking wins when a single hot object has many competing writers making optimistic retries prohibitively expensive — for example, a single shared quota object written by hundreds of concurrent admissions would sustain >50% conflict rate; a serialized write queue is cheaper than the retry storm.

Why: No held locks across the network; conflicts rare + resolved by retry on fresh state; level-triggered reconcile makes retry cheap + safe. LWW corrupts concurrent controller writes.

ADR-11

Watch correctness contract

Chosen

Gap-free, duplicate-free, strictly Revision-ordered stream from a start Revision + periodic Bookmark; compacted-start -> 410 Gone -> relist+rewatch

Rejected

Best-effort event bus; at-least-once with client dedup; poll deltas

When the rejected choice is right

Best-effort at-least-once delivery wins when consumers are inherently idempotent at a coarser granularity (e.g., log aggregation, analytics) and the relist cost for gap recovery is prohibitive relative to occasional deduplication work; gap-freedom at scale requires storing ordered history which is expensive.

Why: Informer cache correctness depends on exact-once ordered delivery; a single gap silently corrupts every Lister. 410-on-compaction forces a safe relist.

ADR-12

Watch transport

Chosen

HTTP/1.1 chunked transfer, newline-delimited JSON WatchEvent stream (SSE-like) over the REST endpoint

Rejected

gRPC server-streaming; raw WebSocket; long-poll

When the rejected choice is right

gRPC server-streaming wins when the watch transport represents measurable CPU at scale (>10k watch streams, protobuf encoding), bidirectional flow control matters, or the client ecosystem is service-to-service (not human-debuggable) — Kubernetes uses HTTP/2 gRPC streaming internally for exactly this reason at cloud scale.

Why: Reuses the one REST/JSON surface + proxies/auth; trivial orctl + curl debuggability; no second IDL/codec. gRPC streaming deferred with protobuf (ADR-08) if fan-out cost demands it.

ADR-13

Controller cache pattern

Chosen

Informer: Reflector -> DeltaFIFO -> SharedIndexInformer (indexed cache + Lister) -> rate-limited WorkQueue -> Reconciler; one shared informer per type

Rejected

Per-controller direct API polling; per-controller independent watch

When the rejected choice is right

Per-controller independent watch wins only for a single-controller system where shared-cache infrastructure complexity exceeds its benefit — a single-purpose operator managing one kind benefits from simplicity over the DeltaFIFO+informer machinery.

Why: Shared cache amortizes one watch across N controllers; reconcile reads cache not events (level-triggered, ADR-15); polling spikes apiserver load + loses ordering.

ADR-14

Workqueue discipline

Chosen

Rate-limited, de-duplicated, delayed WorkQueue<K> keyed by object key; RateLimiter with exponential backoff + forget on success

Rejected

Unbounded channel; immediate-retry loop; per-event goroutine

When the rejected choice is right

Unbounded channel with immediate retry wins for low-volume event streams where queue depth is provably bounded by the upstream event rate and the cost of duplicate reconcile is zero — e.g., a simple webhook handler with one reconcile target and deterministic fast success.

Why: Dedup collapses event storms to one reconcile per key; backoff prevents hot-looping on a failing object; delayed requeue powers RequeueAfter.

ADR-15

Reconcile model

Chosen

Level-triggered, idempotent Reconciler::reconcile reading current desired+observed; edge-triggered logic forbidden

Rejected

Event-driven handlers acting on individual deltas

When the rejected choice is right

Edge-triggered handlers win for streaming analytics and event-processing pipelines where each event carries unique payload (not idempotent state), order matters intrinsically, and re-reading full state per event would be prohibitively expensive — message queues (Kafka, Kinesis) are designed for this model precisely because they guarantee ordered, exactly-once delivery.

Why: A missed/duplicated event is harmless: next resync/watch re-reads full state -> convergence. Edge logic diverges on any lost event.

ADR-16

Ownership + GC

Chosen

OwnerReference on children + finalizers; GarbageCollector does cascading delete; adoption/orphan by selector + controller ownerRef

Rejected

Controller-driven manual child deletion; no finalizers

When the rejected choice is right

Manual child deletion wins when every owner-child relationship requires custom cleanup logic that cannot be expressed as a generic GC traversal — for example, when child deletion order must be application-determined, or when external resources (cloud LBs, DNS records) must be cleaned up with specific ordering constraints that a generic GC cannot encode.

Why: Decouples lifecycle from any single controller's liveness; finalizer blocks delete until cleanup done; cascading delete is centralized + crash-safe.

ADR-17

Scheduler architecture

Chosen

Pluggable scheduling framework: FilterPlugin predicates + ScorePlugin (0..100, weighted-sum) + Binding, over a SchedulingQueue

Rejected

Monolithic hard-coded scheduler; first-fit only; external scheduler

When the rejected choice is right

Monolithic first-fit wins when the cluster has homogeneous nodes, the only placement constraint is resource fit, and scheduling latency is more important than bin-packing quality — first-fit has O(1) average node-scan cost vs O(M) for exhaustive filter/score.

Why: Filter/Score plugins compose resource-fit/nodeSelector/taints/affinity independently + are unit-testable; weighted scoring tunable; mirrors kube-scheduler framework.

ADR-18

Binding exclusivity

Chosen

A Pod binds exactly once via a CAS write of spec.node_name; scheduler is sole writer of that field

Rejected

Multiple schedulers race-binding; kubelet self-assigns

When the rejected choice is right

Kubelet self-assignment wins in extreme edge deployments where the scheduler is unavailable and a local node must decide placement — Kubernetes supports this via the nodeName field set in the Pod spec at submission, effectively bypassing the scheduler for statically placed workloads.

Why: Single-writer per field + CAS prevents double-schedule; kubelet owns status only (ADR-19).

ADR-19

pod.status writer

Chosen

kubelet is the SOLE writer of pod.status; scheduler/controllers write spec only

Rejected

Any controller writes status; shared status ownership

When the rejected choice is right

Shared status ownership wins when multiple independent monitoring agents need to report status conditions on the same object and none has authoritative ground truth — for example, multi-dimensional health scoring systems where network, storage, and compute health are each reported by a separate specialist agent.

Why: Single-writer-per-field rule eliminates status write races without locks.

ADR-20

Container runtime interface

Chosen

ContainerRuntime trait (CRI-like: run_sandbox/pull_image/create/start/stop/status) in orc-runtime

Rejected

Hard-wire one runtime into kubelet; shell out to docker/crictl

When the rejected choice is right

Hard-wiring one runtime wins for a minimal embedded system where the runtime is fixed, the trait abstraction overhead is non-trivial relative to the total codebase, and no multi-runtime flexibility is ever needed — a purpose-built IoT container platform might hard-wire containerd.

Why: Trait seam lets kubelet target real-runc-impl on Linux + a stub on other OSes; testable via a fake impl; matches CRI's decoupling.

ADR-21

Runtime process model

Chosen

Out-of-process container exec (sandbox + container as separate supervised PIDs) driven by orc-runtime in-proc to kubelet

Rejected

In-process (containers as kubelet threads); separate shim daemon per pod

When the rejected choice is right

A separate shim daemon per pod (containerd shim v2 model) wins at production scale where kubelet upgrade without workload disruption is required — the shim isolates the pod process lifetime from both the runtime binary and the kubelet binary, enabling zero-downtime kubelet upgrades.

Why: A kubelet crash must not kill running pods; out-of-proc PIDs survive + are re-adopted on restart. No extra shim daemon to keep Phase 1 simple.

ADR-22

Low-level container exec

Chosen

Direct Linux syscalls for namespaces/cgroups v2/mounts/pivot_root in orc-runtime (runc-like)

Rejected

Shell out to runc/crun binary; libcontainer FFI

When the rejected choice is right

Shelling out to runc/crun wins in production systems that have no interest in managing the syscall edge directly and want to consume upstream security patches for container-start sequences without maintaining a fork — most real orchestrators (containerd, CRI-O) use this approach.

Why: Owning the syscall path is the project's container-isolation learning goal + avoids a runc dependency; gives precise control over namespace ordering + cgroup setup.

ADR-23

cgroups version

Chosen

cgroups v2 only (unified hierarchy)

Rejected

cgroups v1; dual v1/v2 support

When the rejected choice is right

cgroups v1 wins on older kernels (pre-4.15) or when running on distributions that have not migrated to unified hierarchy — RHEL 7, Ubuntu 18.04 LTS on older clouds still use v1 as default, and supporting them requires v1 or dual-mode.

Why: v2 is the modern default; single unified hierarchy simplifies resource accounting; avoids v1's per-controller mount sprawl. Hosts on v1 are out of scope.

ADR-24

Pod network plugin

Chosen

NetworkPlugin trait (CNI-like setup/teardown_pod_network); reference bridge plugin

Rejected

Bake one CNI in; require external CNI binary day 1

When the rejected choice is right

Requiring an external CNI binary on day 1 wins for production systems that will immediately use Calico, Cilium, or Flannel — the CNI binary interface is the standard interop boundary, and building a custom NetworkPlugin trait is redundant when third-party CNI plugins already satisfy the need.

Why: Trait isolates pod-IP allocation from kubelet; a reference plugin keeps the cluster self-contained; real CNI plugins addable later.

ADR-25

Service dataplane

Chosen

Userspace ServiceProxy (ClusterIP VIP -> EndpointSlice backends) first

Rejected

iptables/nftables rules; eBPF/XDP datapath day 1

When the rejected choice is right

eBPF/XDP on day 1 wins for environments with >100k connections/s or strict latency requirements where even a single extra userspace copy is unacceptable — financial trading systems, 5G packet processing, and high-performance load balancers cannot defer the datapath optimization.

Why: Userspace proxy is portable + debuggable for correctness-first; eBPF/iptables are perf optimizations deferred until the VIP->endpoint model is proven.

ADR-26

Secret at-rest handling

Chosen

Secrets stored base64 in orc-store with an envelope-encryption seam (encryption-at-rest provider hook); never logged; tmpfs projection on the node

Rejected

Plaintext only; mandatory KMS day 1

When the rejected choice is right

Mandatory KMS on day 1 wins when regulatory compliance (FIPS 140-2, SOC 2, PCI-DSS) requires provable encryption of secrets at rest with auditable key management — a provider hook without an actual KMS fails compliance audits; the envelope-encryption stub provides no real protection.

Why: Provider hook allows at-rest encryption without API change; tmpfs (memory-backed) projection avoids secrets on node disk. Full KMS integration deferred.

ADR-27

Leader election

Chosen

Lease-based leader election (via orc-store Lease) for orc-controller/orc-scheduler HA; single active leader

Rejected

Active-active controllers; external lock service (ZooKeeper)

When the rejected choice is right

Active-active controllers (sharded by resource key hash) win when reconcile throughput exceeds what a single instance can sustain — at very high object churn (>100k objects, >10k events/s) a single leader reconciler is the throughput bottleneck and sharding across N active leaders (each owning a key partition) is the only horizontal scale path.

Why: Reuses the store's Lease primitive; single-active avoids duplicate reconciles/double-schedule; no extra coordination dependency. Phase 13 (§24).

ADR-28

Error model

Chosen

Typed per-crate error enums (StoreError, ReconcileError, RuntimeError, NetError) via thiserror; control loops never panic! / never unwrap on fallible paths

Rejected

anyhow everywhere; panic-and-restart; Box<dyn Error>

When the rejected choice is right

anyhow everywhere wins for rapid prototypes and CLI tools where error display to a human is the only requirement, type-based dispatch of errors is not needed, and adding thiserror enum variants for every new failure mode slows development more than it helps.

Why: A panic in a reconcile loop / kubelet PodWorker is a node-down or stuck-controller incident; typed errors force exhaustive handling + retry classification. anyhow only at binary main edges.

ADR-29

Observability — tracing

Chosen

tracing crate + OpenTelemetry exporter; span per request/reconcile/PodWorker sync

Rejected

log + ad-hoc strings; slog; printf

When the rejected choice is right

log + structured fields wins for single-process tools with no distributed tracing requirement — the overhead of span context propagation and OTel export is unnecessary when all computation is in-process and correlation across services is not needed.

Why: Structured spans correlate a request across apiserver->store->controller; OTel exports to standard collectors; required to debug watch fan-out + reconcile latency.

ADR-30

Observability — metrics

Chosen

Prometheus text exposition (/metrics) per binary

Rejected

StatsD; custom format; no metrics

When the rejected choice is right

StatsD wins in legacy infrastructure where the metrics pipeline predates Prometheus adoption and migration cost exceeds the benefit — many financial and telecom operations run StatsD+Graphite stacks that have accumulated years of dashboards and alerts not easily ported.

Why: Prometheus is the k8s-ecosystem standard; histograms for reconcile/scheduling/watch-fanout latency + counters for conflicts/requeues feed Operational Readiness SLOs.

ADR-31

Test time control

Chosen

Deterministic-time test harness (injectable clock + manual Tokio time advance)

Rejected

Real-clock sleep in tests; flaky timeouts

When the rejected choice is right

Real-clock sleep wins only when the system's timing behavior depends on wall-clock interactions with external systems (NTP, certificate expiry, external rate limiters) that cannot be injected — testing the interaction with a real external clock source requires using the real clock.

Why: Lease TTL, backoff, resync, probe intervals must be tested without wall-clock waits; deterministic time makes timing tests fast + reproducible.

ADR-32

Fuzzing

Chosen

cargo-fuzz (libFuzzer) on the orc-api JSON codec + the watch protocol decoder

Rejected

No fuzzing; hand-rolled random tests

When the rejected choice is right

Hand-rolled random tests win when the input space is small and fully enumerable — for a closed API with a fixed schema and known-valid input range, structured hand-written generators cover the space faster and with better error messages than coverage-guided fuzzing.

Why: Untrusted client objects + the watch stream are the parsing attack surface; fuzz catches panics/OOM/round-trip violations the type system can't.

ADR-33

Property + e2e testing

Chosen

proptest for invariants (reconcile convergence, watch gap-freedom, optimistic-CC safety) + an in-process e2e harness spinning a full cluster

Rejected

Example-based unit tests only; external Kind/k8s e2e

When the rejected choice is right

Example-based tests win for UI components and domain logic with human-readable fixtures where the "correct behavior" is validated by a human reading the example, not derived from an invariant — property tests require a formal oracle that not all problem domains naturally have.

Why: Properties assert the locked invariants directly across random histories; in-proc harness gives fast deterministic e2e + chaos injection (kill nodes/pods/apiserver, partition store).

ADR-34

CI pipeline

Chosen

GitHub Actions: fmt + clippy (deny warnings) + test + cargo-deny + fuzz-smoke + e2e on Linux

Rejected

Self-hosted only; no CI; CI without lint/deny gates

When the rejected choice is right

Self-hosted CI wins when the build requires privileged hardware (GPU, high-memory, bare-metal cgroups) that cloud-hosted runners cannot provide — Phase 8 orc-runtime tests require real Linux namespaces/cgroups, which GitHub-hosted runners provide in privileged mode, but GPU-accelerated ML workload testing genuinely needs self-hosted hardware.

Why: Linux runners exercise the real namespaces/cgroups path; gated merges keep MSRV + lint + license + e2e green.

ADR-35

Dependency + supply-chain policy

Chosen

cargo-deny (advisories, bans, license allowlist, sources); minimal vetted dep set; MSRV 1.78 pinned in CI

Rejected

Unrestricted deps; no audit; floating toolchain

When the rejected choice is right

Unrestricted deps with floating toolchain win in rapid-prototyping environments where time-to-working-prototype is the constraint and supply-chain risk is deferred until the system approaches production — the overhead of deny.toml curation is non-trivial and inappropriate for a one-week spike.

Why: Control-plane supply chain is security-critical; deny enforces audited, license-clean, source-pinned deps; MSRV pin prevents accidental toolchain bumps.

ADR-36

License

Chosen

Apache-2.0

Rejected

MIT; GPL; proprietary

When the rejected choice is right

MIT wins when the project wants maximum permissiveness with minimum legal text (no explicit patent grant clause needed, smaller companies prefer fewer obligations); GPL wins for copyleft requirements where source sharing is a strategic goal (ensuring improvements are contributed back to the commons).

Why: Mirrors Kubernetes' Apache-2.0 (patent grant, ecosystem compatibility) for the orchestrator it is modeled on.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A — Event-Sourced Command Bus (CQRS + Kafka)

Instead of a MVCC KV store, the cluster state is a Kafka log. Every mutation is a command event. Controllers consume the log and maintain materialized views. Watch = Kafka consumer group from an offset.

Client → REST API → CommandProducer → [ Kafka Partition ]
                                               ↓
                             Controller-A  ←  Consumer Group A
                             Controller-B  ←  Consumer Group B
                             Scheduler     ←  Consumer Group C
                             Kubelet       ←  Consumer Group D (filtered by node)
                                               ↓
                             Materialized views (per-consumer RocksDB)

Why it is not chosen: Kafka gives at-least-once delivery, not gap-free ordered watch by revision. Materialized views diverge when consumer groups fall behind. Cross-component transactions (CAS) require Kafka transactions, which are complex and don't compose with the declarative API. The resourceVersion concept maps awkwardly to Kafka offsets when multiple partitions exist. Correctness proofs are harder. When it wins: very high write throughput (millions of events/s), event replay for audit, fan-out to heterogeneous consumers — better suited for analytics than control-plane state.

Alt-B — Actor-Per-Pod Control Plane (Erlang/Akka model)

Each Pod, Node, ReplicaSet, and Service is an actor with its own mailbox and state. Reconciliation is message-passing between actors. There is no shared store — actors hold their own state and communicate by message.

PodActor(uid1) ←→ NodeActor(node3)    ReplicaSetActor(rs42)
     ↑                 ↑                      ↓
   mailbox           mailbox           [ Pod mailbox × N ]
                                              ↓
                                     Scheduler (actor) → Bind → NodeActor

Why it is not chosen: Global state queries (LIST all Pods, compute cluster-wide resource allocation) require scatter-gather across all actors — O(N) messages per query, no consistent snapshot. A controller restart loses all actor state and must rehydrate from scratch with no agreed recovery point. Watch semantics require total ordering across actors which re-introduces a coordinating sequence number — effectively rebuilding the store. When it wins: very high per-object event rates where shared-state contention is the bottleneck; Erlang's OTP supervision gives free restart/crash-isolation per actor; suitable for per-device state machines in IoT at billions of actors.

Alt-C — Distributed SQL as the Store (CockroachDB / Spanner)

Replace orc-store with a distributed SQL database. Objects are rows with a JSON/JSONB spec column and a resource_version column (auto-increment or sequence). Watch is implemented as CDC (change data capture) or polling.

orc-apiserver → SQL INSERT/UPDATE/SELECT with RV CAS (UPDATE WHERE rv=expected)
orc-store     = CockroachDB cluster (replicated, horizontally scalable)
Watch         = CDC stream (Debezium/built-in) → apiserver watch fan-out

Why it is not chosen: SQL CDC does not provide gap-free ordered delivery by a global revision — CDC streams are per-table, and cross-table ordering is not guaranteed. Implementing Bookmark and 410-on-compaction semantics on top of CDC is complex. The Txn compare-by-resource_version maps to UPDATE WHERE but lacks the on_else branch and multi-op composition. SQL query latency for range scans with a prefix (the primary access pattern) is higher than a BTree with a pre-computed prefix endpoint. When it wins: when the cluster state exceeds available RAM and must be disk-resident at scale, when SQL joins across kinds are needed (e.g., quota computation joins ResourceQuota + all namespaced objects), or when a managed cloud SQL service removes the operational burden of running etcd.

Alt-D — Gossip-Based Eventual Consistency (Consul-style)

Replace the single-store model with a gossip protocol (SWIM or similar). Every node maintains a local copy of all state. Writes are broadcast via gossip and converge eventually. No central store — every node is a peer.

node1: { Pod list, Node list, Service list } ←→ gossip ←→ node2: { same state }
                                                   ↓
                                            Scheduler (reads local copy)
                                            Controller (reconciles local copy)

Why it is not chosen: Gossip is eventually consistent — two nodes may see different states during a partition. A scheduler on node1 and a scheduler on node2 may both decide to bind the same Pod to different Nodes (no CAS bind possible without a central sequencer). Watch semantics require total ordering which gossip cannot provide. Detecting split-brain requires quorum, which reintroduces a central authority. When it wins: service discovery and health checking at very large scale (Consul's primary use case); when the key property needed is "eventually know that a service is healthy" rather than "atomically schedule exactly once." Gossip excels where stale reads are acceptable and write consistency is not.
