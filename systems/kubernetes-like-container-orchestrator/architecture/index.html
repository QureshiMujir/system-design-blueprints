3. Architectural Overview

The orchestrator is nine orc-* crates compiling to five binaries (orc-apiserver, orc-scheduler, orc-controller, orc-kubelet, orctl) plus library crates (orc-api, orc-store, orc-runtime, orc-net). All coordination is indirect: components never RPC each other; they read/write objects in orc-store through orc-apiserver and converge via watch. The store is the only synchronization point.

              orctl / clients  ── REST + WATCH (resourceVersion) ──┐
                                                                   v
    ┌──────────────────────────── CONTROL PLANE ────────────────────────────┐
    |   orc-apiserver : REST · Registry · Admission · Watch · optimistic CC  |
    |        |  read/watch + CAS write (resourceVersion <-> store Revision)  |
    |        v                                                               |
    |   orc-store : MVCC KV · Revision · Watch · Lease · Txn · compaction     |
    |        ^                          ^                       ^             |
    |        | watch+write              | watch+bind            | watch+write |
    |   orc-controller             orc-scheduler           (status writers)   |
    |   (Reflector->DeltaFIFO->Informer->WorkQueue->Reconciler:               |
    |    ReplicaSet·Deployment·Node·EndpointSlice·Namespace·GC)               |
    └────────────────────────────────────┬───────────────────────────────────┘
                          watch bound Pods | (Pod.spec.node_name == self)
                                           v
    ┌──────────────────────── NODE (one per machine) ────────────────────────┐
    |  orc-kubelet : PodWorker · status report · Node Lease heartbeat · probes|
    |        |  CRI                          |  CNI                            |
    |        v                               v                                 |
    |  orc-runtime : OCI image · runc-like   orc-net : ServiceProxy (VIP->EP) ·|
    |  exec (namespaces·cgroups v2·mounts)   NetworkPlugin (pod net) · DNS     |
    └─────────────────────────────────────────────────────────────────────────┘
    TRUST BOUNDARY: clients + node agents are untrusted to the apiserver (authn/authz);
    container images + workloads are untrusted to the node (isolation). CONCURRENCY BOUNDARY:
    every component is an independent async actor reconciling via watch; the store serializes
    writes by Revision. PERSISTENCE BOUNDARY: orc-store is the single durable source of truth.

3.1 Boundaries (the three lines that govern everything)

Boundary Where Rule Enforced by
TRUST clients/nodes ↔ apiserver every request authn'd + authz'd; no client is implicitly privileged apiserver authn chain (cert/token) + RBAC (Phase 12)
TRUST images/workloads ↔ node container code is hostile; isolate via namespaces + cgroups v2 + pivot_root orc-runtime (Phase 8)
CONCURRENCY every component each is an independent async actor; no shared mutable state across components; coordinate only via watch + CAS store Revision serializes all writes (Phase 1)
PERSISTENCE orc-store single durable source of truth; component caches are derived + disposable, rebuilt by relist WAL + Revision (Phase 1)

Implication: any component may crash/restart at any time and recover by relisting from the store at its last-known resourceVersion — no component holds authoritative unpersisted state. Caches are soft; the store is hard.

3.2 orc-apiserver (control-plane front door)

Responsibilities: the only writer to orc-store; exposes REST CRUD + list + WATCH over versioned resource kinds via a generic Registry; runs validation + Admission; enforces namespaces; maps object resourceVersion ↔ store Revision. In: REST/WATCH from orctl, controllers, scheduler, kubelets. Out: JSON objects, watch streams, Revision-stamped writes into the store. Invariant: optimistic concurrency — every update carries the resourceVersion it read; the apiserver issues a store Txn compare-and-set; mismatch → 409 Conflict; no locks, conflicts resolved by client re-read + retry. Stateless and horizontally scalable (all state in the store). Built Phase 3 (§14); authn/authz/admission deepened Phase 12 (§23); multi-apiserver HA Phase 13 (§24).

3.3 orc-store (MVCC KV — single durable truth)

Responsibilities: a WAL-backed keyspace with a global monotonic Revision; range/put/delete, Txn (compare-and-set), gap-free ordered Watch from a revision, Lease (TTL keys for node heartbeats), and compact. In: Op/Compare/Txn calls from the apiserver; lease keepalives from kubelets (via apiserver). Out: KeyValue ranges, WatchEvent streams (Put/Delete/Bookmark), granted Revisions. Invariant: the store serializes all writes by Revision — every mutation bumps a single global counter, and a Watch from R streams every change with Revision > R strictly in order, with no gaps and no duplicates (compacted R → 410 Gone, forcing relist). This gap-freedom is the foundation of every downstream cache. Single-node now; Raft replication is a deferred hook cross-linking project 42. Built Phase 1 (§12).

3.4 orc-controller (controller-manager + informer pipeline)

Responsibilities: the reconciliation framework Reflector → DeltaFIFO → SharedIndexInformer → WorkQueue → Reconciler plus built-in controllers (ReplicaSet, Deployment, Node-lifecycle, EndpointSlice, Namespace, GarbageCollector). The Reflector list+watches a resource into a DeltaFIFO; the SharedIndexInformer applies deltas to a thread-safe indexed cache (the Lister) and fans changes to handlers that enqueue object keys into a rate-limited, de-duplicated WorkQueue; the Reconciler dequeues a key and reconciles from the cache, not from the event. One informer per type is shared across controllers. In: watch streams + reads from the apiserver. Out: CAS writes (spec/child objects) back through the apiserver. Invariant: reconcile is level-triggered + idempotent — it reads current desired (spec) + observed (cache status) and drives toward desired; a missed event is harmless because the next resync/watch re-reads full state; edge-triggered logic is forbidden. Ownership/GC honors OwnerReference + finalizers (cascading delete). Framework Phase 4 (§15); core controllers Phase 5 (§16); Deployment Phase 9 (§20); EndpointSlice Phase 10 (§21); leader election Phase 13 (§24).

3.5 orc-scheduler (filter + score + bind)

Responsibilities: watch unscheduled Pods (spec.node_name == None) via a SchedulingQueue; for each, run every FilterPlugin (resource fit, nodeSelector, taints/tolerations, affinity/anti-affinity) to get feasible Nodes, then each ScorePlugin (least/most-requested, spread; 0..100, weighted-summed), pick the max-scoring Node, and Bind. In: Pod + Node watch streams from the apiserver. Out: a Binding — a single CAS write of pod.spec.node_name. Invariant: binding is exclusive — a Pod binds exactly once; the write is a compare-and-set on the unbound state, so a duplicate bind loses on resourceVersion and is rejected 409. Stateless beyond an in-memory node cache; on restart it relists and re-derives the queue. Built Phase 6 (§17); preemption optional.

3.6 orc-kubelet (per-Node agent)

Responsibilities: register the Node + renew its Lease heartbeat; watch Pods bound to this Node (spec.node_name == self); run the PodWorker lifecycle state machine (PodSyncResult: Synced/Backoff/Terminated); report pod.status; run liveness/readiness/startup probes (ProbeManager); inject volumes/config (VolumeManager). In: bound-Pod watch from the apiserver; container state from orc-runtime; network from orc-net. Out: pod.status writes + Node status/Lease updates through the apiserver; CRI calls to orc-runtime; CNI calls to orc-net. Invariant: the kubelet is the sole writer of pod.status for its own Pods (scheduler/controllers write spec only) — single-writer-per-field eliminates status races. Node liveness is lease-based: a missed lease → Node-lifecycle controller marks the Node NotReady and evicts Pods after grace. Built Phase 7 (§18).

3.7 orc-runtime (CRI-like container runtime)

Responsibilities: the ContainerRuntime trait — OCI image pull_image/unpack into an ImageStore, pod sandbox creation (run_sandbox), runc-like container exec (create_container/start_container/stop_container) using Linux namespaces, cgroups v2 limits (CgroupHandle), mounts, and pivot_root; container status; restart policy + crash backoff. In: CRI calls from the kubelet (PodSandboxConfig, ContainerConfig). Out: SandboxId/ContainerId/ImageId, ContainerStatus. Invariant: workload isolation — every container runs in its own namespace + cgroup set with a pivoted root, and resource limits are hard-enforced by the kernel; the container is untrusted to the host. Linux-real; a stub runtime on other OSes for dev. Built Phase 8 (§19).

3.8 orc-net (Service networking + pod network)

Responsibilities: the ServiceProxy dataplane programming Service ClusterIP VIP → EndpointSlice healthy backends (ClusterIP/NodePort, via iptables/eBPF-like or userspace proxy); cluster DnsServer; the CNI-like NetworkPlugin (setup_pod_network/teardown_pod_network) assigning each Pod a PodIp. In: Service + EndpointSlice watch streams; sandbox handles from the kubelet. Out: programmed VIP→backend rules; a PodIp per sandbox; DNS records. Invariant: VIP → endpoint indirection — clients address a stable Service VIP; the proxy load-balances only to healthy EndpointSlice backends, which the EndpointSlice controller keeps in sync with Pod readiness (level-triggered). Built Phase 10 (§21).

3.9 orc-api (object model + apimachinery)

Responsibilities: the shared resource vocabulary every component depends on — TypeMeta/ObjectMeta, the Object trait, the typed kinds (Pod, ReplicaSet, Deployment, Service, Node, Namespace, ConfigMap, Secret, Event, EndpointSlice), LabelSelector + label/field selector matching, the JSON codec, resourceVersion semantics, ListOptions/WatchEvent, OwnerReference, Condition. In/Out: pure library — serializes/deserializes objects and evaluates selectors; holds no state. Invariant: spec vs status separation + a stable wire contract — spec is desired (written by clients/controllers), status is observed (written by the owning component); the JSON codec round-trips losslessly so a round-tripped object equals the persisted one. Built Phase 2 (§13); shells in Phase 1 (§12).

3.10 orctl (CLI + typed client)

Responsibilities: the operator interface + typed client library — apply, get, describe, delete, scale, rollout, logs, exec, watch; talks to orc-apiserver over REST/WATCH. In: user commands + YAML manifests. Out: REST writes (declarative apply) + read/watch displays. Invariant: declarative apply — the client submits desired spec; it never imperatively mutates cluster internals, so the same manifest applied twice converges to the same state. Built incrementally from Phase 1 (§12) onward as resources land.

3.11 End-to-end flow (a Deployment to running containers)

Step Actor Action Store effect
1 orctl apply POST Deployment put → Deployment@Rev, status Pending
2 Deployment ctrl observe Deployment, create ReplicaSet (ownerRef) put ReplicaSet
3 ReplicaSet ctrl observe RS, N replicas missing → create N Pods (ownerRef) put Pods, spec.node_name=None
4 orc-scheduler watch unscheduled Pod → Filter+Score+Bind CAS put spec.node_name=node-X
5 orc-kubelet (X) watch bound Pod → PodWorker → pull image, run sandbox, start containers CAS put pod.status Running
6 orc-net Pod Ready → EndpointSlice updated → ServiceProxy programs VIP→Pod put EndpointSlice

Every arrow is a watch + CAS through the apiserver; no component calls another directly. Failure at any step is recovered by the next reconcile reading current state — the whole pipeline is a chain of independent, idempotent, level-triggered loops sharing one durable, Revision-ordered store.

8. Domain Model — Resource Objects, Store Semantics, and Reconciliation

The domain model is the spine the whole system reconciles around: typed orc-api objects persisted as MVCC keys in orc-store, read/watched through orc-apiserver, and driven to convergence by level-triggered controllers. This section fixes the exact data shapes, key layout, watch/CC protocols, and reconcile contract every later phase depends on. Terms used precisely per the glossary; no synonyms.

8.1 The Object Model — TypeMeta, ObjectMeta, spec/status

Every resource is { TypeMeta, ObjectMeta, spec, status }. spec = desired state (author/controller-owned). status = observed state (controller/kubelet-owned). The two NEVER share a writer per field — single-writer-per-field is invariant (see 8.6, 8.f).

Field group Owner (writer) Mutability Notes
TypeMeta {api_version, kind} client immutable post-create routes codec + registry
ObjectMeta.name/namespace/uid apiserver (uid), client (name/ns) immutable uid minted on create; identity key
ObjectMeta.resource_version apiserver server-set every write == store mod_rev (8.2)
ObjectMeta.generation apiserver bumped on spec change only observed via status.observed_generation
ObjectMeta.labels/annotations client/controller mutable labels are selectable; annotations are not
ObjectMeta.owner_references controller set on adopt drives GC + cascade (8.g)
ObjectMeta.finalizers controller/client mutable block deletion until cleared (8.g)
ObjectMeta.deletion_timestamp apiserver set once on DELETE w/ finalizers non-null ⇒ Terminating
spec author/controller mutable (bumps generation) desired state
status controller/kubelet mutable (no generation bump) observed state

generation vs resource_version: generation increments only when spec mutates (a status write does NOT bump it); resource_version increments on EVERY write. A reconciler is "caught up" when status.observed_generation == metadata.generation.

Compact Pod (round-trips through Phase 1 smoke test):

apiVersion: v1
kind: Pod
metadata:
  name: web-7f3a
  namespace: default
  uid: 4e1c-...           # server-minted
  resourceVersion: "10472" # == store mod_rev
  generation: 2
  labels: { app: web, tier: frontend }
  ownerReferences:
    - { kind: ReplicaSet, uid: a91-..., controller: true, blockOwnerDeletion: true }
  finalizers: []
spec:                      # desired — author/RS-controller owned
  nodeName: node-3         # set by orc-scheduler bind (8.e)
  restartPolicy: Always
  nodeSelector: { disktype: ssd }
  containers:
    - { name: app, image: registry/web:1.4, ports: [{containerPort: 8080}] }
status:                    # observed — sole writer = orc-kubelet on node-3
  phase: Running
  podIP: 10.42.3.17
  conditions: [{ type: Ready, status: "True" }]
  containerStatuses: [{ name: app, ready: true, restartCount: 0 }]

Compact Deployment (manages ReplicaSets, Phase 9):

apiVersion: apps/v1
kind: Deployment
metadata: { name: web, namespace: default, generation: 5, resourceVersion: "10501" }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  strategy: { type: RollingUpdate, rollingUpdate: { maxSurge: 1, maxUnavailable: 0 } }
  template:
    metadata: { labels: { app: web, tier: frontend } }
    spec: { containers: [{ name: app, image: registry/web:1.4 }] }

  observedGeneration: 5    # == generation ⇒ rollout converged
  replicas: 3
  updatedReplicas: 3
  availableReplicas: 3

INVARIANT (template-label / selector match): spec.selector MUST match spec.template.metadata.labels — else admission rejects (the Deployment/ReplicaSet would never own the Pods it creates; orphan loop). See 8.g failure path.

8.1.1 LabelSelector match semantics

LabelSelector { match_labels: BTreeMap<String,String>, match_expressions: Vec<Requirement> }. A selector matches an object iff ALL match_labels equal AND ALL match_expressions pass (logical AND across the whole selector). An empty selector {} matches everything; a null selector matches nothing.

Form Operator Match rule Example
matchLabels (implicit =) label k present AND value == v {app: web} → has app=web
matchExpressions In label k present AND value ∈ values tier In (frontend,api)
matchExpressions NotIn label k absent OR value ∉ values tier NotIn (batch)
matchExpressions Exists label key k present (values empty) app Exists
matchExpressions DoesNotExist label key k absent (values empty) canary DoesNotExist

Validation: In/NotIn require ≥1 value; Exists/DoesNotExist require 0 values — else 422. Selectors are immutable on ReplicaSet/Deployment after create (would re-partition ownership). Field selectors (e.g. spec.nodeName=node-3, metadata.namespace=default) are a fixed allowlist per kind, distinct from label selectors, used by orc-kubelet/orc-scheduler watch filters.

8.2 Store Data Model — keys, Revision, KeyValue, resourceVersion

Objects serialize (JSON codec, orc-api) to a value under a hierarchical key:

/registry/<kind-plural>/<namespace>/<name>     # namespaced
/registry/<kind-plural>/<name>                 # cluster-scoped (Node, Namespace)
e.g.  /registry/pods/default/web-7f3a
      /registry/deployments/default/web
      /registry/nodes/node-3

LIST of a namespace = range(prefix="/registry/pods/default/", end=prefix++) (right-open range; prefix++ is prefix with last byte incremented). LIST all namespaces = /registry/pods/.

Revision(i64) — a single global, monotonic logical clock for the whole store; bumped by exactly +1 on every successful mutating op (put/delete/txn). It is NOT per-key. KeyValue carries:

Field Meaning
create_rev: Revision Revision at which this key was first created (stable across updates; reset on delete+recreate)
mod_rev: Revision Revision of the LAST write to this key
version: i64 per-key write count (1 at create, +1 per put; resets on delete)
lease: Option<LeaseId> TTL owner (node heartbeat keys; 8.3)

resourceVersion == KeyValue.mod_rev (string-encoded). A list's resourceVersion = the store's current global Revision at list time (the snapshot point a subsequent watch resumes from). This dual use — per-object RV for CAS, global RV for watch resume — is the linchpin of 8.4 and 8.d.

MVCC two-write example (global revision advances; per-key version tracks):

op1: put /registry/pods/default/web  v1   → Revision 10470
     KeyValue{ create_rev:10470, mod_rev:10470, version:1 }   resourceVersion="10470"
op2: put /registry/pods/default/web  v2   → Revision 10472   (10471 was some other key)
     KeyValue{ create_rev:10470, mod_rev:10472, version:2 }   resourceVersion="10472"

create_rev pins to 10470 (identity unchanged); mod_rev advances to 10472; global Revision is shared cluster-wide so an unrelated write consumed 10471. MVCC retains old values until compact(rev) (8.3) reclaims revisions ≤ rev.

8.3 Lease, compaction, MVCC retention

  • Lease: lease_grant(ttl) → LeaseId; keys attached to a lease are auto-deleted when the lease expires without lease_keepalive. Use: Node heartbeat (8.6) and leader-election (Phase 13). Expiry emits a WatchEvent::Delete to watchers.
  • Compaction: compact(rev) discards all historical KeyValue versions with mod_rev < rev, keeping only the latest per live key. After compaction at rev_c, a watch started from any start_rev < rev_c is unservable → 410 Gone / Expired (8.4). Compaction target: keep ≥ last 1000 revisions or 10 min of history (whichever larger) to bound watcher relist storms.

8.4 Watch Protocol — list→watch, WatchEvent stream, compaction→410→relist

WatchEvent (orc-store):

pub enum WatchEvent {
    Put(KeyValue, Option<KeyValue> /*prev*/),  // create OR update; prev=None ⇒ create
    Delete(KeyValue),
    Bookmark(Revision),                        // periodic "you are caught up to R" (no object)
}

Watch contract (LOCKED — cache correctness rests on this): a watch(key, end, start_rev) streams every change with Revision > start_rev, strictly in ascending Revision order, with NO gaps and NO duplicates, interleaved with periodic Bookmark(R). The apiserver maps store Revision ↔ resourceVersion; a Bookmark lets a client advance its resume point without a real event so a relist after a quiet period resumes cheaply.

Informer init: list-then-watch (atomic handoff at the list RV):

  1. LIST → snapshot of objects + a list-level resourceVersion = R0 (= global Revision at snapshot).
  2. WATCH(start_rev = R0) → resume EXACTLY after R0. No gap (changes at ≤R0 are in the snapshot), no dup (changes at >R0 stream once).
client                 orc-apiserver                     orc-store
  │   GET ?watch=false      │                                │
  ├────────────────────────►│  range(prefix, rev=None)       │
  │                         ├───────────────────────────────►│
  │   200 items, RV=R0      │◄─────────── items, Rev=R0 ──────┤
  │◄────────────────────────┤                                │
  │   GET ?watch=true&rv=R0 │                                │
  ├────────────────────────►│  watch(prefix, start_rev=R0)   │
  │                         ├───────────────────────────────►│
  │  Put(web, prev=None)@R1 │◄──── WatchEvent::Put @R1 ───────┤
  │◄────────────────────────┤                                │
  │  Put(web, prev=v1)@R2   │◄──── WatchEvent::Put @R2 ───────┤
  │◄────────────────────────┤                                │
  │  Bookmark(R2)           │◄──── (periodic, ~every 1–5 min)─┤
  │◄────────────────────────┤                                │
  │        ... store compacts at R_c > R0 ...                │
  │  Put/Delete @R3 ...     │                                │
  │   410 Gone (Expired)    │  start_rev < R_c ⇒ unservable  │
  │◄────────────────────────┤                                │
  │   RELIST  GET ?watch=false ──► new RV=R4, then WATCH(R4)  │  (recover; loop restarts)
  └──────────── re-watch from R4 (gap-free again) ───────────┘

410 recovery is mandatory client logic: on 410 the Reflector drops its watch, re-LISTs (fresh RV), replaces the cache, and re-WATCHes. The SharedIndexInformer surfaces this as a full resync to handlers — harmless because reconcile is level-triggered (8.5).

8.5 Optimistic Concurrency — CAS Txn, two-writer worked example

No locks. Every update is a Txn compare-and-set on resourceVersion:

UPDATE obj (client read it at RV=R_read):
  txn(
    compares: [ Compare::ModRev(key) == R_read ],
    on_ok:    [ Op::Put(key, new_value) ],     // succeeds → Revision advances, mod_rev = new RV
    on_else:  [ ]                              // fails → 409 Conflict
  )

apiserver: on on_else (RV mismatch) returns 409 Conflict; client MUST re-GET (fresh RV), re-apply its intent, retry.

Worked race — two controllers update the same Pod's labels:

Pod web @ resourceVersion=10472 (mod_rev=10472)
  CtrlA reads RV=10472 → wants labels += {a:1}
  CtrlB reads RV=10472 → wants labels += {b:2}

  CtrlA: txn(Compare ModRev==10472, Put)  → store advances → Revision 10473, mod_rev=10473  ✔ 200 OK
  CtrlB: txn(Compare ModRev==10472, Put)  → store mod_rev is now 10473 ≠ 10472             ✘ 409 Conflict
  CtrlB: re-GET web → RV=10473 (sees {a:1}) → re-apply {b:2} on fresh state
  CtrlB: txn(Compare ModRev==10473, Put)  → Revision 10474, mod_rev=10474                   ✔ 200 OK
final labels: {a:1, b:2}   — no lost update, no lock

Single-writer-per-field reduces conflicts: scheduler writes spec.nodeName, kubelet writes status, RS-controller writes labels/ownerRefs — so genuine CAS contention is rare and bounded by retry. RV is OPAQUE to clients: never arithmetic, only equality-compare and echo-back.

8.6 Reconciliation Model — the informer pipeline + level-triggered contract

        ┌──────────────────────────── orc-controller ─────────────────────────────┐
 watch  │  Reflector ──deltas──► DeltaFIFO ──pop──► SharedIndexInformer            │
◄───────┤  (LIST+WATCH a kind,       (ordered      (apply delta → thread-safe      │
orc-api  │   relist on 410)          per-key        indexed cache = Lister)         │
server  │                            queue)              │ fan-out handlers        │
        │                                                 │ enqueue object KEY      │
        │                                                 ▼                         │
        │                         WorkQueue<Request>  (rate-limited, dedup'd,       │
        │                          delayed; RateLimiter::when/forget)               │
        │                                                 │ pop key                 │
        │                                                 ▼                         │
        │   Reconciler::reconcile(Request, &Context) ──► reads desired+observed     │
        │     FROM THE CACHE (Lister), not the event  ──► Reconcile::{Done,         │
        │                                                  Requeue, RequeueAfter}    │
        └───────────────────────────────────────────────────────────────────────────┘

Level-triggered contract (LOCKED):

  1. Dequeue a Request{namespace,name} — a key, NOT an event payload (the event's data is intentionally discarded; dedup collapses N events on one key to one reconcile).
  2. Read CURRENT desired (spec from cache) + CURRENT observed (status/owned children from cache).
  3. Compute diff desired − observed.
  4. Act idempotently to close the diff (create/delete/patch). Acting on already-correct state is a no-op.
  5. Requeue: Done (drop), RequeueAfter(d) (recheck later), Requeue (retry now, rate-limited).

Properties: idempotent (re-running on the same state is a no-op), edge-triggered logic FORBIDDEN (never "on Pod-deleted do X"; instead "ensure N exist"), missed event harmless (next resync/watch re-reads full state), resync = periodic re-enqueue of all keys (default 10 min, jittered) to self-heal dropped notifications. RateLimiter::when backs off hot keys (exponential, e.g. 5 ms → 1000 ms cap); forget resets a key after a clean reconcile.

8.6.1 ReplicaSet reconcile — worked example (idempotent)

ReplicaSet web-rs: spec.replicas=3, selector={app:web}
Reconcile(req=web-rs):
  desired  = 3
  observed = Lister.pods(selector {app:web}, ownerRef=web-rs) → 2 live Pods
  diff     = 3 - 2 = +1
  act      → create 1 Pod from spec.template (labels {app:web}, ownerRef→web-rs, controller:true)
  result   → RequeueAfter? no → Done; status.replicas=3 written (status-only write, no generation bump)

Re-run immediately (informer saw the create):
  desired=3, observed=3, diff=0 → no-op → Done       # IDEMPOTENT
Scale-down (spec.replicas=2 now):
  desired=2, observed=3, diff=-1 → delete 1 Pod (newest / least-ready first by deletion-cost order) → Done

If 2 Pods crash between watch events, the next resync re-reads observed=1, diff=+2, creates 2 — convergence without ever processing a "Pod died" event.

8.7 Pod Lifecycle State Machine

PodPhase ∈ { Pending, Running, Succeeded, Failed, Unknown }. Sole status writer = the orc-kubelet on spec.nodeName (8.5). Phases are terminal-monotone: Succeeded/Failed never transition back.

From Event / condition To Writer Notes
(create) object admitted, nodeName=None Pending apiserver unscheduled
Pending scheduler binds spec.nodeName Pending scheduler still Pending until kubelet syncs
Pending image pulled, sandbox + containers started Running kubelet podIP set; Ready cond follows readiness probe
Running all containers exit 0, restartPolicy ∈ {OnFailure,Never} Succeeded kubelet terminal
Running container exits ≠0 & not restartable, OR restartPolicy=Never & failed Failed kubelet terminal
Running container exits, restartPolicy=Always Running kubelet crash backoff (8, Phase 8), phase stays Running
any non-terminal kubelet lease lost ⇒ node NotReady Unknown node-lifecycle ctrl status unreachable; later evicted
any DELETE w/ finalizers ⇒ deletion_timestamp set (unchanged phase) apiserver Terminating; kubelet runs graceful stop, then key removed

Node liveness → eviction: each kubelet renews a Node Lease (TTL, e.g. 10 s renew / 40 s expiry). Missed lease → Node-lifecycle controller marks Node NotReady; after a grace period it sets evicted Pods to Unknown/deletes them so the ReplicaSet controller replaces them elsewhere (level-triggered: diff reopens).

8.8 Malformed / Failure-Path Catalog
