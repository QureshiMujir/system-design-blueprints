Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must Revision be assigned inside the single write lock rather than generated by an atomic counter before the lock? What failure mode does a pre-lock counter introduce, and why does it break watch correctness even if no actual value is lost?
  2. A DeltaFIFO Replace(items, rv) call synthesizes delete events for keys present in the old cache but absent from the relist. What invariant does this maintain, and what would happen to the GarbageCollector if the delete were not synthesized?
  3. The scheduler reads from the informer cache (not from orc-store directly) and then writes spec.node_name via a CAS Txn. Between the cache read and the CAS write, the node could have become unschedulable. Trace the exact failure path and explain why eventual correctness is guaranteed without a distributed lock.
  4. A kubelet crashes while a container is in ContainersRunning state. When it restarts, it must re-adopt the running container. What two data sources does the kubelet consult to reconstruct the PodWorker state, and what happens if the container has also died while the kubelet was down?
  5. Explain gap-freedom in terms of a concrete store implementation choice: why does watcher::replay_from(start_rev) require a history index (treeIndex), not just the current value of each key?
  6. The Txn operation takes a global write lock for the duration of the compare+apply+assign-Revision sequence. What is the maximum-latency implication of this, and what optimization (used in etcd) reduces the average cost without violating the monotonicity guarantee?
  7. Why does 410 Gone on a compacted watch start point require a full relist, not just a re-watch from the compaction rev? What would the informer cache contain if you re-watched from compact_rev without relisting?
  8. Two ReplicaSet controllers are running (before leader election is implemented). Both observe 2 Pods running against a desired count of 3. Both decide to create a third Pod with the same deterministic name. Trace the exact sequence of store operations and explain which one wins and what the other observes.
  9. A finalizer is added to a Pod by the GarbageCollector before a kubelet is ready to handle it. The kubelet calls DELETE on the Pod, which succeeds (sets deletion_timestamp). The finalizer is never removed because the GC controller crashes. What is the state of the Pod after 1 hour, and what is the recovery path?
  10. The percentageOfNodesToScore optimization samples nodes rather than evaluating all of them. Under what scheduling workload does this optimization cause measurable allocation inefficiency, and what is the signal in metrics that indicates you have hit this regime?
  11. The Bookmark event carries a Revision but no object payload. What specific state transition in the client does receiving a Bookmark enable, and why is it necessary for compaction safety even when no writes have occurred recently?
  12. A WorkQueue is keyed by object key (namespace/name), not by event. Two rapid back-to-back updates to the same Pod key produce two events but only one queue entry. What property of the reconciler makes this safe, and what class of reconciler bug would make it unsafe?
  13. The out-of-process container execution model (ADR-21) means containers survive a kubelet crash. What data structure must the kubelet persist (or reconstruct from the OS) on startup to re-adopt surviving containers, and what is the failure mode if that reconstruction is incorrect?
  14. Why does pivot_root require the new root to be on a different mount point from the old root? What exact filesystem operation must be performed before pivot_root to satisfy this precondition, and what kernel error do you receive if you skip it?
  15. The single-writer-per-field invariant says kubelet is the sole writer of pod.status. A controller also needs to set a condition on the Pod (e.g., a webhook readiness gate). How does Kubernetes (and by analogy this project) allow this without violating the invariant?
  16. A leader election Txn compares lease_holder == absent and writes the holder identity. If two instances send this Txn simultaneously (after a network partition heals), what store property guarantees exactly one of them succeeds? Trace the exact compare-and-set execution.
  17. The WAL uses fsync to guarantee crash-recovery. Under what conditions can you safely batch multiple put operations into one fsync call without violating the monotonicity guarantee, and what is the ordering constraint between writing the WAL record and updating the in-memory BTree index?
  18. cgroup.subtree_control requires that a cgroup with processes (a leaf) cannot have sub-controllers enabled — the "no-internal-process rule." How does CgroupHandle in Phase 8 enforce this rule when creating a new container cgroup under an existing kubelet cgroup?
  19. The Deployment controller reconciles the desired replicas count by managing a set of ReplicaSet objects. During a rolling update, it must create a new RS and scale down the old RS. Under the level-triggered contract, how does it know which RS is "new" and which is "old" without storing any state outside orc-store?
  20. A ConfigMap is updated while a Pod is running with it mounted as a volume. The VolumeManager's reconcile_projected atomically swaps the ..data symlink. What guarantees does the renameat2(RENAME_EXCHANGE) call provide that a plain rename does not, and why does this matter for a process reading the files while the swap occurs?
  21. The informer cache uses a SharedIndexInformer with named indices (e.g., "pod_by_node"). A kubelet watches only Pods for its own node via a field selector. Why is it still correct for the kubelet to maintain a local SharedIndexInformer rather than querying the apiserver for each reconcile, even under network partition?
  22. An OCI image manifest references layers by content-addressable sha256 digest. When ImageStore::pull_image encounters a layer that already exists in the local cache, it skips the download. What invariant about content-addressable storage makes this deduplication unconditionally safe without a version check?
  23. Why is the Raft ReplicationHook seam (ADR-06) placed at the Store trait level rather than at the orc-apiserver REST handler level? What would break if you intercepted writes at the HTTP layer instead?
  24. The chaos harness in Phase 14 kills the orc-store process for 30 seconds and then restarts it. List the exact sequence of events each of the following components will experience and what their recovery path is: orc-apiserver, orc-controller, orc-scheduler, orc-kubelet.
  25. A proptest-generated random operation sequence drives the watch-gap-freedom property test. What is the precise predicate the property test must assert, and what invariant in the store implementation guarantees the predicate holds even when operations arrive in arbitrary order?

Mental Models & First Principles

These are the load-bearing mental models for this project. Each is named (MM1…MM10) and cross-referenced to the phase where it becomes operational.

MM1 — The Store as Shared Reality (Phase 1). Every component believes only what it reads from orc-store. There is no other ground truth. A component that maintains private state not derived from the store will diverge from all others on restart. Consequence: every design question about where to hold state has one answer — can it be reconstructed from a list+watch? If yes, that is where it lives.

MM2 — Revision as the Global Logical Clock (Phase 1). Revision is not a timestamp. It is a monotonic, gap-free, globally serialized counter that assigns a unique total order to every write in the store. resourceVersion is a projection of this clock onto a single object. This gives you: (a) a safe watch start point, (b) a compaction boundary, (c) an optimistic-concurrency token, and (d) a list snapshot at a point in time — all from one integer.

MM3 — Level-Triggering as Convergence Insurance (Phase 4). An edge-triggered system counts transitions. A level-triggered system reads the current level. After any network partition, crash, or event loss, a level-triggered reconciler re-reads full state and recomputes the right action — a missed transition has no lasting effect. The informer cache is the level; the WorkQueue key is the trigger; the reconcile call reads the level, never the edge.

MM4 — The Single-Writer-Per-Field Invariant (Phases 2, 7). If two components can both write a field, correctness requires a distributed lock or a merge function. Neither is acceptable here. The design eliminates contention at the model level: pod.spec.node_name has one writer (scheduler); pod.status has one writer (kubelet). CAS conflicts become unambiguous bugs, not normal coordination.

MM5 — Watch Gap-Freedom as Cache Correctness Prerequisite (Phase 1). An informer cache is a function of the initial list plus all subsequent watch events. One dropped event corrupts the function permanently — there is no self-healing path short of a relist. Gap-freedom is not a performance feature; it is the integrity guarantee that makes caches trustworthy. Every design choice in orc-store's watch implementation (serialized Revision, Bookmark, 410-on-compaction) exists to maintain this guarantee.

MM6 — The CAS-Not-Lock Principle (Phase 3). Distributed locks held across network round-trips introduce deadlock risk when the holder crashes. Optimistic CAS avoids this: the lock is never held; the cost of failure is one retry from fresh state; level-triggered reconcile makes retry cheap. The only time a CAS conflict is expensive is when many writers contend on the same field simultaneously — the single-writer-per-field invariant (MM4) eliminates exactly this case in normal operation.

MM7 — The Trait as the Phase Seam (Phase 1). trait Store, trait ContainerRuntime, trait FilterPlugin, trait NetworkPlugin, trait ReplicationHook are not abstractions for testability alone. They are phase-boundary gates. A todo() implementation passes the compiler; it does not pass the gate test. The trait defines the contract; the phase delivers the real implementation behind it. Never let a todo() survive a phase-completion commit.

MM8 — The Scheduling Ceiling is Algorithmic, Not Hardware (Phase 6). At M nodes and one Pod to schedule, Filter+Score costs O(M). This is not a constant you can buy away with faster hardware; it is an algorithmic bound. The percentageOfNodesToScore optimization converts the problem from "find the best node" to "find a sufficiently good node from a random sample" — a principled approximation that trades optimality for bounded latency.

MM9 — Out-of-Process PIDs Decouple Lifecycle from Kubelet (Phase 8). If containers run as threads within the kubelet process, a kubelet crash kills all pods on the node. If containers run as independent PIDs in their own namespace+cgroup set, a kubelet crash is transparent to running workloads. The kubelet re-adopts survivors on restart by scanning its PID registry. This asymmetry — kubelet is optional for running containers, mandatory for scheduling new ones — is the fundamental design of every production container runtime.

MM10 — Compaction Bounds History, Not Liveness (Phase 1, Phase 13). orc-store retains every write as a revision in its history index. Without compaction, this grows unbounded. compact(rev) drops history below rev — it does not delete live objects, only old versions. A watch started from a revision below the compaction point receives 410 Gone and must relist. The compaction policy (retain last 5 min, or 10k revisions) is a tradeoff between watch-reconnect safety and storage cost. Getting this wrong causes either unbounded disk growth or thundering-herd relists.

Glossary · 21 terms · site-wide glossary

object / resource / kind
A persisted, addressable API entity (Pod, Service, …). Kind = the type name in TypeMeta.kind; resource = its REST collection (pods); object = a single instance. All impl Object trait.
apiVersion
group/version string in TypeMeta.api_version (e.g. apps/v1, v1). Versions a kind's schema; drives codec dispatch + conversion.
TypeMeta
{ api_version, kind } — self-describing type header on every object; enables polymorphic decode without out-of-band type info.
ObjectMeta
Common metadata: name, namespace, uid (Uuid), resource_version, generation, labels, annotations, owner_references, finalizers, timestamps. Identity + bookkeeping shared by all kinds.
spec vs status
spec = user-declared desired state (immutable to controllers except owners); status = observed/reported state. Distinct sub-objects; single-writer per field.
desired vs observed state
Reconciliation inputs: desired = current spec; observed = status + informer cache. Controller drives observed → desired.
declarative
API expresses what (target state), never how (imperative ops). Clients apply full objects; system computes diffs.
generation
ObjectMeta.generation — i64 bumped on every spec change; status.observed_generation lets a controller report "have I acted on this spec yet".
label
Key/value in ObjectMeta.labels; identifying, queryable, used by selectors to group objects (loose coupling: Service→Pod, ReplicaSet→Pod).
selector
LabelSelector { match_labels, match_expressions: Vec<Requirement> }; matches objects by labels (equality + set ops: In/NotIn/Exists).
field selector
Server-side filter on built-in fields (metadata.namespace, spec.node_name, status.phase) in ListOptions; kubelet uses spec.node_name==self.
OwnerReference
{ uid, kind, controller: bool, block_owner_deletion: bool } in child meta; encodes the owning controller for GC + adoption.
finalizer
String key in ObjectMeta.finalizers; presence blocks hard-delete (object enters deletion_timestamp-set "terminating" state) until the responsible controller removes its key.
Condition
{ type, status: True/False/Unknown, reason, message, last_transition } entry in status.conditions; standard observability surface (e.g. Ready, Available).
Pod
Smallest schedulable unit: co-located containers + shared volumes, network namespace, lifecycle. PodSpec.node_name set once by scheduler.
PodPhase
enum { Pending, Running, Succeeded, Failed, Unknown } in PodStatus.phase; coarse lifecycle summary; written only by kubelet.
ReplicaSet
Maintains spec.replicas Pods matching spec.selector from spec.template; reconciler adopts/orphans by ownerRef + selector.
Deployment
Manages ReplicaSets to roll out Pod template changes; `spec.strategy: RollingUpdate{max_surge,max_unavailable}
rolling update
Update strategy: incrementally scale up a new ReplicaSet + scale down old, bounded by maxSurge/maxUnavailable, to keep availability during rollout.
maxSurge
Max Pods over desired replicas allowed during a rolling update (absolute or %). Caps extra capacity / scheduling pressure.
maxUnavailable
Max Pods below desired allowed unavailable during a rolling update; sets the availability floor.
