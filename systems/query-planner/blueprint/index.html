54 — Database Query Planner

Project Number: 54

Project Name: Database Query Planner

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Definition. The Database Query Planner (qp) is a library that consumes a bound-or-unbound SQL abstract syntax tree plus a Catalog/Statistics pair, and produces an executable physical plan tree with its EXPLAIN rendering. It owns binding, the logical algebra IR, rule-driven logical rewrite, the cost model and statistics consumption, dynamic-programming join enumeration (DPccp) with a Cascades-style transformation overlay, physical-operator lowering/optimisation, and the EXPLAIN/EXPLAIN ANALYZE surfaces. It does not parse SQL text, persist a catalog, or execute a plan.

Phase-0 deliverable — numbered modules (one crate each, §10):

  1. qp-core — identifiers, Catalog/Statistics traits, planner entry point, config, errors.
  2. qp-bind — name resolution, type checking, CTE/SELECT * expansion, subquery binding.
  3. qp-ir — Expr, LogicalPlan, canonicalisation.
  4. qp-rewrite — Rule trait, rewrite engine, rule catalogue.
  5. qp-stats — histograms, MCV, HyperLogLog, correlation/functional-dependency statistics.
  6. qp-cost — cost model, cardinality/selectivity estimator.
  7. qp-enum — DPccp bottom-up join enumerator, greedy fallback.
  8. qp-cascades — memo, group, group-expression, transformation/implementation rules.
  9. qp-physical — physical operator catalogue, property model.
  10. qp-explain — text + JSON EXPLAIN formatters.
  11. qp-cli — qp explain / qp stats build command-line surface.
  12. qp-ffi — cdylib C ABI for cross-language embedding.

System boundaries.

  • Provides: bind, rewrite, cost, cardinality, join enumeration, physical lowering/optimisation, EXPLAIN.
  • Delegates: SQL text parsing (upstream sql_ast::Statement producer), catalog persistence, statistics-collection scheduling (ANALYZE triggers), plan execution, transport/auth.
  • Does NOT provide: a network service, a storage engine, a SQL parser, transaction management, access control.

Non-goals. Beating every commercial optimiser on every workload; a general-purpose algebra research platform; a query language beyond the SQL-92 + analytic-extension subset (§8).

Deployment model. An embedded Rust library (rlib) linked into a host database process, or a cdylib loaded by a non-Rust host via qp-ffi. No planner-owned network listener; no planner-owned persistent state.

Target users/operators. Database-engine implementers embedding qp as their optimiser; SRE/on-call engineers debugging plan regressions via EXPLAIN ANALYZE and the runbooks in §24.

What later phases unlock. Adaptive runtime re-planning (§21), distributed exchange operators (§19), a plan cache (§29), a materialised-view/index advisor (§35).

Recommended language: Rust 1.78+, stable channel only. Rationale: sealed-enum exhaustive pattern matching is the right ergonomics for an IR that accumulates rewrite rules over years (ADR-03); Arc-shared subtrees keep pure-rewrite cost tractable (P3); a cdylib crate-type gives a free C ABI (ADR-26) without a second implementation. Rejected: C++ — no sum types without std::variant boilerplate, and manual memory safety on a component that walks untrusted ASTs is a liability (ADR-01). Java/Scala — GC pauses conflict with a single-digit-millisecond planning budget (ADR-01, §4). Go — no zero-cost sealed-enum equivalent at the time ADR-01 was locked; interface{}-based Expr nodes cost an allocation each.

Prerequisites. Relational algebra (selection/projection/join/aggregate/set-ops/decorrelation); SQL-92 plus analytic extensions (window functions, lateral joins, CTEs, recursive CTEs); graph algorithms over connected subgraphs (DPccp is DP over csg-cmp pairs, §17); basic statistics (equi-width/equi-depth/max-diff histograms, MCV, HyperLogLog distinct-count, §16); intermediate Rust (lifetimes, sealed enums as IR, arena allocation).

Estimated timeline. Phase 0 — 1 week. Full ten-phase system (§12–§21) — 4 to 6 months, gated on a 22-TPC-H-query conformance bar at scale factor 1 (§26).

Deferred features (full register in §35): adaptive re-planning PhaseDeferred("§21"); distributed exchange operators PhaseDeferred("§19"); genetic enumeration beyond N=32 PhaseDeferred("§17"); plan caching PhaseDeferred("§29"); materialised-view/index advisors and multi-query optimisation PhaseDeferred("§35").

2. Why Build This

  • Every database eats its own queries through a planner; it is the one component that can tell a 50 ms plan from a 50-minute plan before the executor has burned a node-hour finding out.
  • Two logically equivalent join graphs can differ in cost by twelve orders of magnitude across the plan space (§32); the planner is the arbiter.
  • Teaches the full optimiser stack in one deliberately small system: binder → algebra IR → rule rewriter → statistics → cost model → DP join enumeration → Cascades transformation overlay → physical lowering → property-driven physical optimisation → EXPLAIN.
  • Historically the load-bearing subsystem of every serious RDBMS (System R, PostgreSQL, DB2, SQL Server) and every modern analytic engine (DuckDB, Spark, Calcite-based systems, §31); building one is the fastest path to principal-engineer command of query processing.
  • Builds the engineering muscle of quantified decision-making under uncertainty: every cost comparison is a bet against an error bar (I8), not a fact — a discipline that transfers directly to capacity planning, SLO design, and anomaly triage outside databases entirely.
  • Cross-links: the upstream SQL-Database project (parser, ranking line 21) supplies the AST this planner consumes; the downstream executor project consumes this planner's PhysicalPlan and reports EXPLAIN ANALYZE actuals back through §21's adaptive hook.
  • Calibration value: the 10-percent-of-best-known-plan bar on all 22 TPC-H queries at SF1 (M4) is the same bar Selinger's System R team set in 1979 — hitting it in a from-scratch implementation is the field's standard proof of competence.

What Mastery Looks Like. After building this system, the reader can:

  • Derive the DPccp plan-space bound from first principles and explain why it beats naïve N! enumeration (§17, §32).
  • Explain why cardinality estimation, not enumeration algorithm choice, dominates real-world plan quality regressions, citing Leis 2015 by name (§16, §5).
  • Design a property-driven physical optimiser (required/delivered properties, enforcers) and explain why it is correct by construction where heuristic operator choice is not (§20).
  • Decorrelate an arbitrary correlated subquery using the Galindo-Legaria & Joshi 1999 taxonomy and identify the one shape (LIMIT inside a correlated subquery) that cannot be lifted (§15).
  • Build and reason about a Cascades memo: group deduplication, transformation vs. implementation rules, required-property search (§18).
  • Read an EXPLAIN tree and diagnose, from the actual/estimated ratio alone, whether the fix is a missing statistic, a stale ANALYZE, or a genuinely hard cost-model gap (§21, §23).
  • Compare this design against PostgreSQL, System R, Apache Calcite, SQL Server/Cascades, and DuckDB, and state precisely which single decision each made differently and why (§31).

Per-box notes. Bind (§13) is the only place SQL-level type policy lives; it takes a snapshot of the Catalog (I10) so the rest of the pipeline sees consistent metadata. Logical IR (§14) is the lingua franca (P2): every later phase codes against LogicalPlan, never the AST. Rewriter (§15) is a fixed-point loop over pure rules (P3, I13); it must converge before Phase 4 runs. Statistics + Cost (§16) is the single subsystem every cardinality number flows through (P5); the enumerator never reads a histogram directly. DPccp (§17) and Cascades (§18) share one memo: DPccp seeds group winners for join order, Cascades explores transformation/implementation rules on top (P6). Physical Lowering (§19) picks an operator family per logical node; Physical Optimisation (§20) is the only place enforcers are inserted (P7) — property reasoning is correct-by-construction, not heuristic. EXPLAIN (§21) is a first-class output built before the executor handoff (P8), and is the point where the deferred adaptive-replanning hook attaches. Trust boundary A is upstream-parser output (an AST we do not trust to be internally consistent, §22 T10); trust boundary B is the executor's actuals callback (§21, §22 T12 for information leakage via row-count side channels).

6. Design Principles

  1. The AST is upstream and immutable (P1). qp consumes sql_ast::Statement; it never mutates it. Tradeoff: any parser bug becomes a qp-bind upstream-contract bug, not a local workaround. Violate it and the binder silently diverges from what the parser actually emits.
  2. The logical algebra IR is the lingua franca (P2). Every phase past §14 codes against LogicalPlan; nothing reaches into the bound AST after lowering. Tradeoff: one more IR to maintain, in exchange for exhaustive pattern-matching (ADR-03). Violate it and rewrite rules fragment across two representations.
  3. Rewrites are pure (P3). A Rule::apply never mutates its input; subtrees are Arc-shared. Tradeoff: extra Arc bookkeeping for O(1) structural sharing instead of O(n) copies. Violate it and the fixed-point loop (§15.2) cannot be trusted to terminate deterministically (I4).
  4. Cost is a scalar, not a vector (P4). Cost::total() is one f64. Tradeoff: a Pareto-front cost model finds strictly-dominant plans but explodes the search space for no measured TPC-H win (ADR-07). Violate it and the enumerator's memo key space multiplies by the frontier size.
  5. Statistics are estimates, and the cost model owns the error (P5). Every Cardinality carries relative_error (I8); the cost model prefers lower-variance plans within 10% of lowest cost. Violate it and the planner is confidently wrong under skew (MM2).
  6. DP first, Cascades second (P6). §17 ships DPccp; §18 wraps a Cascades memo around it for transformation rules. Tradeoff: two enumeration mechanisms sharing one memo instead of one uniform Cascades search from day one (ADR-04); DPccp is exhaustively testable against the System R reference before Cascades' larger rule surface is trusted.
  7. Physical lowering is property-driven, not heuristic (P7). §20 asks "what properties does this operator's output need?" and inserts enforcers where a child under-delivers. Tradeoff: more bookkeeping (required vs. delivered property sets) for plans that are correct by construction (ADR-14). Violate it and a MergeJoin can silently receive unsorted input.
  8. EXPLAIN is a first-class output (P8). The formatter ships before the executor handoff (§21); no plan the planner can produce is a plan it cannot describe. Violate it and production debugging degrades to source-reading.
  9. Determinism is the default (P9). Same AST + same catalog + same statistics ⇒ bit-identical physical plan (I4), enforced by hashing rendered EXPLAIN output in conformance (§26). Violate it and regression bisection becomes probabilistic.
  10. No silent fallbacks (P10). An invalid rewrite raises with the rule name and offending subtree (I13); the validator runs after every rule in debug builds. Violate it and a schema-breaking rewrite ships silently to production.
  11. Interesting orders are first-class DP state, not an afterthought (P11). The DP table is keyed by (RelationSet, InterestingOrder), not RelationSet alone (§17.2). Tradeoff: a larger memo for a plan that can win overall despite losing on raw cost-per-row (MM1). Violate it and the enumerator misses every merge-join opportunity that isn't also the row-count winner.
  12. Statistics staleness is a first-class signal, not silence (P12). Every TableStatistics carries last_analyzed (I11); staleness beyond budget (§4) is surfaced in EXPLAIN, not hidden. Violate it and an operator cannot tell "bad plan" from "stale plan" (MM7).
  13. Planning time is budgeted, not open-ended (P13). A hard wall-clock timeout (plan_timeout_ms, §4) bounds every plan() call; DPccp degrades to greedy beyond dpccp_max_relations (ADR-12). Violate it and one pathological join graph starves the host.
  14. The cost model and the statistics layer are versioned together (P14). Changing cost weights without recalibrating against JCC-H, or vice versa, shifts the plan distribution unpredictably (§17.6 pitfalls). Violate it and a "small tuning change" becomes a fleet-wide plan regression.

I14 Bounded planning time: every plan() call either completes or returns PlannerError::Timeout within plan_timeout_ms an unbounded search starves the host process (P13) wall-clock check in the enumerator's outer loop (§17.2) timer-based conformance fixture with an adversarial join graph planner.timeout_triggered degrade to greedy/cached fallback (§17.2); never block indefinitely

Debugging methodology. A deterministic simulator (conformance/runner, §26) replays every fixture in conformance/corpora/ against a fixed (Catalog, Statistics) pair and asserts one invariant check per fixture category: bind fixtures exercise I10, rewrite fixtures exercise I1–I3/I13, enum fixtures exercise I5/I9/I14, cardinality fixtures exercise I7/I8/I11, and tpch/determinism fixtures exercise I4/I6/I12 end-to-end. A fixture that fails is reproduced byte-for-byte from its corpus file — no live database, no network, no clock dependency beyond the injected last_analyzed timestamp.

8. Domain Model / Protocol / Data Model

8.1 SQL Grammar (EBNF fragment — the subset qp-bind accepts)

query          ::= [ with-clause ] select-stmt [ order-by ] [ limit-clause ] ;
with-clause    ::= "WITH" [ "RECURSIVE" ] cte { "," cte } ;
cte            ::= ident "AS" "(" query ")" ;
select-stmt    ::= "SELECT" select-list "FROM" from-item { join } [ where-clause ]
                    [ group-by ] [ having ]
                  | select-stmt set-op select-stmt ;
set-op         ::= ("UNION" | "INTERSECT" | "EXCEPT") [ "ALL" ] ;
select-list    ::= "*" | select-expr { "," select-expr } ;
select-expr    ::= expr [ "AS" ident ] | ident "." "*" ;
from-item      ::= table-ref | "(" query ")" [ "AS" ] ident | "LATERAL" "(" query ")" [ "AS" ] ident ;
table-ref      ::= ident [ "AS" ident ] ;
join           ::= [ join-kind ] "JOIN" from-item [ "ON" expr | "USING" "(" ident { "," ident } ")" ]
                  | "," from-item ;                          (* comma-join == inner, no predicate *)
join-kind      ::= "INNER" | "LEFT" [ "OUTER" ] | "RIGHT" [ "OUTER" ]
                  | "FULL" [ "OUTER" ] | "CROSS" ;
where-clause   ::= "WHERE" expr ;
group-by       ::= "GROUP BY" expr { "," expr } ;
having         ::= "HAVING" expr ;
order-by       ::= "ORDER BY" order-item { "," order-item } ;
order-item     ::= expr [ "ASC" | "DESC" ] [ "NULLS" ("FIRST" | "LAST") ] ;
limit-clause   ::= "LIMIT" integer [ "OFFSET" integer ] ;
expr           ::= literal | column-ref | func-call | expr binop expr | "NOT" expr
                  | expr "IS" [ "NOT" ] "NULL" | expr ["NOT"] "IN" "(" expr-list | query ")"
                  | expr ["NOT"] "BETWEEN" expr "AND" expr | expr ["NOT"] "LIKE" expr
                  | "CASE" { "WHEN" expr "THEN" expr } [ "ELSE" expr ] "END"
                  | "EXISTS" "(" query ")" | "(" query ")"                  (* scalar subquery *)
                  | window-call ;
window-call    ::= func-call "OVER" "(" [ "PARTITION BY" expr-list ] [ order-by ] ")" ;

Every production above lowers to exactly one LogicalPlan/Expr shape in §11; LATERAL and correlated scalar/EXISTS subqueries lower to LogicalPlan::Apply (§11.8), never to Join.

8.4 Worked Example

SELECT o.o_orderkey, c.c_name FROM orders o JOIN customer c ON o.o_custkey = c.c_custkey WHERE o.o_orderdate >= '2025-01-01' lowers as:

Bind:      BoundStatement{ Query(
             Project[o_orderkey,c_name](
               Filter[o_orderdate>=date](
                 Join[Equi(o_custkey=c_custkey), Inner](Scan(orders), Scan(customer))))) }
Rewrite:   Project[o_orderkey,c_name](
             Join[Equi(o_custkey=c_custkey), Inner](
               Scan(orders, pushed=[o_orderdate>=date]),
               Scan(customer)))                          -- predicate pushed to Scan(orders)
Physical:  Project(
             HashJoin(build=Scan(customer), probe=Scan(orders, filter pushed)))

8.5 Malformed-Input Example

SELECT id FROM orders o JOIN order_items i ON o.id = i.order_id where both orders and order_items have a column named id and the SELECT list says id unqualified: name resolution (§13.2 step 2) finds two matches ⇒ Diagnostic::Ambiguous { name: "id", candidates: [orders.id, order_items.id] }; bind fails closed with PlannerError::InvalidName, never guesses.

8.6 Failure-Path Example

A hypothetical buggy build of predicate_pushdown (§15.2) pushes i.discontinued = false (null-rejecting on the right) through a LeftOuter(orders, order_items) join into the join condition. LogicalPlan::validate (I1) diffs the pre-/post-rewrite row count on the negative conformance fixture rewrite/predicate_pushdown/outer_join_null_reject.json (§15.5), detects the semantic divergence, and the rewriter raises PlannerError::Internal { kind: "rewrite_violation", rule: "predicate_pushdown" } with the offending subtree attached — per P10, it never ships the unsafe plan silently.

13. Phase 1 — Bind / Analyse (Weeks 1–2)

13.1 Objectives

Resolve every identifier against Catalog (§11.2); type-check every expression; desugar CTEs and SELECT *; bind subqueries with correlation tracking, producing BoundStatement (§11.8-adjacent).

13.2 Detailed Implementation Steps

  • Implement the Scope stack: each scope holds (name, RelationId, schema) triples for FROM-clause relations, (name, ColumnRef) for aliased projections, and a parent pointer for correlated lookups (P1; I10 catalog snapshot taken once at entry).
  • Name resolution (§8.1 column-ref): qualified names resolve against the scope stack, first match wins; unqualified names search every in-scope relation — exactly one match binds, more than one raises Diagnostic::Ambiguous (§8.5); no match searches parent scopes and marks the reference correlated for §15.2's decorrelator.
  • Type checking: bottom-up inference via the SQL coercion lattice (crates/qp-bind/src/coerce.rs); Literal/Column/Function/BinaryOp/Case/Cast each have a fixed inference rule; a disallowed coercion is a bind error, never a silent truncation/widening (P1 extended to types).
  • CTE expansion: non-recursive WITH is inlined (tunable, PlannerConfig::cte_inline_threshold, following the PostgreSQL default-inline precedent, §5 book 2); WITH RECURSIVE binds to LogicalPlan::With { recursive: true } for §15/the executor's fixed-point loop.
  • SELECT */t.* expansion against the scope's relation list — no * survives past bind.
  • Subquery binding: an expression-position subquery binds to a LogicalPlan wrapped in Expr::Subquery/Expr::Exists/Expr::InList(...); correlated ColumnRefs are recorded on the binder's correlation set for §15.2's decorrelator (Galindo-Legaria & Joshi 2001, §5).
  • Emit BoundStatement { kind: BoundKind, schema, diagnostics }, BoundKind ∈ {Query, Insert, Update, Delete, Explain}.

13.3 Deliverable

The binder accepts every AST shape the upstream parser (ranking line 21) produces and emits a BoundStatement for each; qp explain --stage=bind dumps the JSON.

13.4 Acceptance Criteria

  • The 200+ fixture bind corpus (§13.5) passes with 0 unexpected diagnostics.
  • Every negative fixture (ambiguous name, type mismatch, unknown function) raises the documented stable error code (I10-adjacent contract, §22).
  • p50 bind latency ≤ 2 ms on the TPC-H Q1 AST (component of M2's 10 ms end-to-end budget).

13.5 Conformance Fixtures

  • conformance/corpora/bind/*.json — 200+ AST-in/BoundStatement-out pairs covering every §8.1 clause shape.
  • conformance/corpora/bind/negative/ambiguous_column.json — the §8.5 malformed-input example.
  • conformance/corpora/bind/negative/type_mismatch.json — a disallowed coercion.

13.6 Pitfalls

  • SQL identifiers are case-insensitive but quote-sensitive — Scope lookup must lowercase unquoted identifiers and preserve quoted ones verbatim, or silently binds the wrong column.
  • SELECT t.a, t.a + 1 FROM t WHERE t.a > 0 references t.a three times; the binder must produce three ColumnRefs pointing at the same ColumnId, not three independently-diverging expressions.
  • A correlated subquery without a tight predicate becomes an unbounded per-tuple nested loop at execution if left un-decorrelated — bind the correlation explicitly so §15.2 can lift it.
  • Recursive-CTE scoping (a CTE is in scope inside its own definition) is easy to get wrong in the Scope stack — test it explicitly (§13.5).

13.7 Performance Concerns

  • Scope lookup is O(relations-in-scope) per identifier; cache the first-hit relation per name within a scope rather than re-scanning parent scopes on every unqualified lookup.
  • Coercion-lattice lookups sit on the bind hot path; keep the lattice a const table, not a runtime-constructed HashMap.

13.8 Edge Cases

  • Zero-relation FROM-less SELECT 1 + 1 binds to LogicalPlan::Values with one row, no Scan.
  • A CTE name shadowing a real table name — the CTE wins per standard SQL scoping; a common source of "wrong table" bugs if undocumented.
  • NULL-literal type inference in a CASE with no ELSE and all-NULL branches infers Type::Null, deferred to the outer context for a concrete type.
  • Deeply nested correlated subqueries (3+ levels) — the correlation set must chain through every parent scope, not just the immediate one.

13.9 Failure Analysis

  • An unresolved identifier that should have matched (e.g. a Catalog snapshot race, I10) surfaces as PlannerError::InvalidName with the exact Identifier span — operators grep bind.invalid_name telemetry to distinguish "genuinely bad SQL" from "stale catalog."
  • A coercion-lattice gap (a valid SQL coercion the lattice doesn't know) blocks a previously-working query after a lattice change — caught by the negative fixture corpus (§13.5) before release (§26).

13.10 Operational Notes

  • Emits one OpenTelemetry span qp.bind per plan() call (ADR-18) with attributes relations_in_scope, correlated_subquery_count, diagnostics_count.
  • bind.invalid_name and bind.type_mismatch counters feed the docs/runbooks/slow-plan.md triage path when a client reports unexpected planning failures.

14. Phase 2 — Logical Algebra IR (Weeks 2–3)

14.1 Objectives

Lower BoundStatement to LogicalPlan (§11.8); establish the canonical form every later rewrite rule assumes; enforce plan-shape invariants at construction.

14.2 Detailed Implementation Steps

  • Lowering: walk BoundKind::Query, emitting Scan per base table, bottom-up Join per FROM-tree edge, Filter for WHERE, Aggregate when GROUP BY/aggregate projections are present, Filter for HAVING, Project for the SELECT list, Sort for ORDER BY, Limit for LIMIT/OFFSET — textbook canonical nesting (P2, §5 book 1 Ch. 16), no pre-optimisation at lowering time.
  • Canonicalisation pass (idempotent, canon(canon(p)) == canon(p), tested in §14.5): coalesce adjacent Filters into one AND-conjunction; coalesce adjacent Projects; drop pass-through Projects (output schema == input schema, I2); normalise a decomposable Theta predicate to Equi; normalise commutative comparisons to a fixed Column op Literal shape.
  • Plan-shape invariants checked by LogicalPlan::validate in debug builds (P10, I2): every ColumnRef.relation is in scope at that tree position; every Aggregate.aggregates[i] references only group_by columns or wrapped aggregate calls; every Sort.keys[i].expr references only input-produced columns; Limit.offset is non-negative, limit = Some(0) is legal (zero rows).
  • LATERAL and correlated-subquery shapes lower to LogicalPlan::Apply (§11.8), never Join — the DPccp enumerator (§17) does not accept Apply; §15.2's decorrelator is the only path from Apply to Join.

14.3 Deliverable

Every fixture in the §13.5 bind corpus lowers to a canonical LogicalPlan; qp explain --stage=lower dumps the pre-rewrite tree.

14.4 Acceptance Criteria

  • The canonicaliser is idempotent on all 200+ corpus fixtures (M9-adjacent conformance gate, §26).
  • LogicalPlan::validate catches every fixture in the negative-shape corpus (§14.5) with the specific invariant violated named (I2).
  • Comma-joins (FROM a, b) and explicit CROSS JOIN/JOIN ... ON true lower to byte-identical canonical trees.

14.5 Conformance Fixtures

  • conformance/corpora/lower/*.json — BoundStatement → canonical LogicalPlan pairs.
  • conformance/corpora/lower/negative/nested_aggregate.json — malformed nested Aggregate without an intervening CTE boundary.
  • conformance/corpora/lower/negative/bad_sort_ref.json — a Sort key referencing a column the input does not produce.

14.6 Pitfalls

  • Nested Aggregate is invalid SQL-92 but reachable via CTEs in some dialects — lower to two Aggregate nodes separated by the CTE boundary, never collapse them.
  • FROM a, b and FROM a JOIN b ON true must produce the same tree — a divergence silently changes downstream cost estimates for logically-identical queries.
  • LATERAL lowered as Join instead of Apply is a correctness bug the DPccp enumerator cannot detect — it will silently reorder something it must not.

14.7 Performance Concerns

  • The canonicaliser runs once per plan() call; keep it O(plan size) via a single bottom-up pass, not O(plan size²) from re-walking per coalescing step.
  • Arc-share unchanged subtrees between the raw-lowered and canonical trees (P3) to avoid doubling allocation for large FROM lists.

14.8 Edge Cases

  • A WHERE clause that is compile-time-constant false lowers normally here — folding to Empty is §15.2's job, not lowering's.
  • Deeply right-nested JOIN chains (32-way) must lower without stack overflow — use an iterative, not recursive, tree builder.
  • Zero-column Project (invalid SQL but reachable via a buggy AST) must fail bind (§13), never reach lowering.

14.9 Failure Analysis

  • A LogicalPlan::validate failure here means either the binder emitted an inconsistent BoundStatement (a §13 bug) or lowering itself broke an invariant — the validator's offending-node dump disambiguates by showing which ColumnRef is out of scope.
  • An idempotence failure in the canonicaliser blocks release (§26) — it means two coalescing rules are fighting each other.

14.10 Operational Notes

  • Emits qp.lower span with attributes raw_node_count, canonical_node_count (their ratio is a cheap proxy for how much redundant SQL a query contained).
  • lower.validate_failure counter feeds the same triage path as bind.invalid_name (§13.10).

15. Phase 3 — Logical Rewriter (Weeks 3–4)

15.1 Objectives

Run a fixed-point loop over a pinned-order catalogue of pure rules (P3, I13) that pushes predicates/projections toward scans, folds constants, decorrelates subqueries, inlines views, and closes equivalence classes — producing the LogicalPlan the cost model (§16) will annotate.

15.2 Detailed Implementation Steps

The engine (qp-rewrite, §11.7 Rule trait) applies each rule in the pinned order below until a full pass makes no change, capped by max_iterations (safety net; rules are designed confluent and converge in 2–3 passes on TPC-H, M9). Rule catalogue, pinned order (I4 determinism depends on this literal order):

Order Rule Direction Theory anchor
1 view_inline TopDown P1 — a view is not a cost-model black box
2 cte_inline_non_recursive TopDown §13.2 (PostgreSQL inline-by-default precedent)
3 constant_fold BottomUp respects SQL NULL semantics
4 predicate_simplify BottomUp de Morgan / algebraic identities
5 equivalence_close TopDown transitive closure of equi-predicates
6 predicate_pushdown TopDown Selinger 1979 (§5); I1/I2-checked
7 projection_pushdown TopDown reduces row width the cost model rewards (P4)
8 decorrelate_apply TopDown Galindo-Legaria & Joshi 2001 (§5)
9 eliminate_distinct_under_unique BottomUp uses Catalog primary-key metadata
10 merge_projects BottomUp canonical-form maintenance (§14.2)
11 push_limit_through_project TopDown Project does not change row count
12 prune_empty BottomUp propagates Empty upward
13 outer_to_inner_join_when_null_rejecting TopDown null-rejection analysis (§8.6)
14 set_op_normalize BottomUp flattens nested UNION ALL

Predicate pushdown (rule 6): split a Filter's predicate at AND boundaries; classify each conjunct by the RelationIds it touches — left-only pushes left, right-only pushes right, both-sides stays as a join predicate (or becomes an Equi pair). Unsafe across LeftOuter/RightOuter/FullOuter unless the conjunct is provably non-null-rejecting on the outer side (I1, §8.6). Decorrelation (rule 8, Galindo-Legaria & Joshi 2001): identify correlated columns recorded by §13.2; a subquery with no aggregation and no LIMIT lifts to a flat Join with correlated predicates folded into the join condition; a subquery with aggregation lifts to a LeftOuter join with a group-by on the correlated key; a subquery with LIMIT or another row-counting operator stays Apply — the one shape that cannot be lifted (What Mastery Looks Like, §2). Equivalence-class closure (rule 5): union-find over equi-join predicates; derives implied predicates (a=b ∧ b=c ⇒ a=c) and pushes them to whichever scan holds the column, tightening cardinality even on a previously loose join.

15.3 Deliverable

Every TPC-H logical plan post-rewrite has predicates and projections pushed to scans, views/non-recursive-CTEs inlined, and every decorrelatable TPC-H subquery (Q4, Q17, Q20, Q21, Q22) flattened to a Join.

15.4 Acceptance Criteria

  • Rewriter converges in < 5 iterations on every TPC-H query (M9).
  • Every rule has ≥ 1 positive and ≥ 1 negative fixture in conformance/corpora/rewrite/{rule}/ — 14 rule directories minimum.
  • LogicalPlan::validate (I1, I2) reports 0 violations across the full TPC-H + JCC-H corpus post-rewrite.

15.5 Conformance Fixtures

  • conformance/corpora/rewrite/predicate_pushdown/outer_join_null_reject.json — the §8.6 failure-path fixture (negative).
  • conformance/corpora/rewrite/decorrelate_apply/limit_subquery.json — asserts Apply is preserved, not lifted.
  • conformance/corpora/rewrite/*/positive/*.json, .../negative/*.json — one pair per rule.

15.6 Pitfalls

  • A rule producing a tree whose schema differs from its input is a correctness bug — the validator (I2) MUST run after every rule in debug builds, not just at the end of the loop.
  • Predicate pushdown across an outer join is unsafe in general; restrict to predicates provably null-rejecting only on the correct side.
  • Decorrelating a LIMIT 1 subquery changes the result — leave it Apply (§15.2).
  • Constant folding must respect timezone/locale for date/time functions — thread it through RewriteCtx.cfg, never assume UTC.

15.7 Performance Concerns

  • The fixed-point loop re-walks the tree per rule per iteration; Arc-share unchanged subtrees (P3) so a rule touching one join branch doesn't force reallocation of the sibling.
  • Cap max_iterations low (e.g. 8) — a rule set that needs more is a confluence bug (I13), not a case for a higher cap.

15.8 Edge Cases

  • A predicate that folds to Empty mid-tree must propagate upward through every ancestor (rule 12), including through a Join (an empty side makes an Inner join empty, but not a LeftOuter/FullOuter).
  • A view that references itself (recursive view, not WITH RECURSIVE) is an error at view_inline, not an infinite loop.
  • A correlated subquery nested inside another correlated subquery must decorrelate innermost-first.

15.9 Failure Analysis

  • A confluence violation (I13) surfaces first as a non-deterministic EXPLAIN hash in CI (§26) — bisect by rule name via the conformance runner's --bucket rewrite mode.
  • A validator failure mid-loop raises PlannerError::Internal { kind: "rewrite_violation", rule } with the offending subtree (§8.6); the rule is quarantined (release-blocked, §27) until fixed.

15.10 Operational Notes

  • Emits qp.rewrite span with attributes iterations, rules_fired (rule→count map) — high iterations on a specific query shape is the first signal for docs/runbooks/slow-plan.md.
  • rewrite.confluence_violation and rewrite.schema_mismatch counters are release-blocking (§27), not just alerts.

16. Phase 4 — Statistics and Cardinality Estimation (Weeks 4–5)

16.1 Objectives

Own the cardinality/selectivity estimates every downstream cost comparison depends on (P5) — the subsystem Leis 2015 (§5) identifies as the dominant source of real-world plan-quality regressions.

16.2 Detailed Implementation Steps

  • Per-table stats: row count, disk bytes, last_analyzed (I11). Per-column: null fraction, HyperLogLog distinct-count (Flajolet 2007, §5; 2^14 registers, ADR-10), average width, histogram (equi-width/equi-depth/max-diff, ADR-08), MCV list top-K (ADR-09). Multi-column: sample-based MCV pairs + functional dependencies (ADR-11, PostgreSQL pg_statistic_ext precedent).
  • Histogram build: equi-depth sorts a reservoir sample (avoids first-N-rows clustering bias, §16.6), picks N−1 quantile boundaries; max-diff (Poosala 1996, §5) picks boundaries at points of maximum frequency change from a frequency-sorted sample; both expose one primitive — estimated rows in [low, high] via linear interpolation within the containing bucket.
  • MCV lookup: col = 'x' checks the MCV list first (exact frequency × row count); a miss falls back to (1 − Σ MCV.frequencies) / (distinct_count − K), the average non-MCV frequency.
  • Distinct-count: HyperLogLog++ sketch, α·m²/Σ2^(−register[i]), ~0.81% standard error; below the exact-count threshold (default 1,000 rows, ADR-10) use exact counting; a provably-unique column (primary key) sets distinct_count = row_count directly, no sketch.
  • Selectivity propagation up the LogicalPlan: Scan multiplies per-predicate selectivities; Filter multiplies by its predicate's selectivity; equi-join on one key divides left.rows × right.rows by max(left_distinct, right_distinct); multi-key equi-join assumes independence unless multi-column stats (ADR-11) override it; theta-join multiplies by the predicate's own selectivity; outer joins preserve at least the outer row count; semi/anti preserve at most the outer row count; Aggregate estimates Π distinct_count(group_by[i]) capped at input rows. Relative error compounds multiplicatively across the chain (I8; derivation in §32).
  • Predicate-selectivity primitives: equality/range/IN/IS [NOT] NULL/LIKE 'prefix%' each map to a histogram/MCV lookup above; AND assumes independence unless multi-column stats override; OR uses inclusion-exclusion; NOT is 1 − selectivity(p).
  • qp stats build --catalog <schema.json> --sample-rows 100000 --table <name> (qp-cli) drives reservoir sampling → histogram/MCV/HLL build → catalog write; scripts/build-tpch-stats.py is the Phase-0 TPC-H helper.

16.3 Deliverable

qp stats build produces a complete statistics blob for the TPC-H SF1 schema; every LogicalPlan node downstream carries a Cardinality (§11.5).

16.4 Acceptance Criteria

  • Cardinality estimates land within 10× of ground truth on ≥ 80% of JCC-H intermediate joins (M3; Leis 2015 found PostgreSQL at roughly half this bar — matching it is the conformance target).
  • qp stats build completes on a 1 GB TPC-H instance in < 60 s (M8).
  • Every Cardinality.relative_error stays within [0.0, 10.0] (I8) across the full conformance corpus.

16.5 Conformance Fixtures

  • conformance/corpora/cardinality/*.json — predicate + ground-truth row count pairs.
  • conformance/corpora/jcch/* — the Join Order Benchmark drop, scored by benchmarks/cardinality_jcch.rs (M3).
  • conformance/corpora/cardinality/negative/skewed_no_mcv.json — demonstrates the MM8 failure mode absent MCV.

16.6 Pitfalls

  • Sampling the first N rows of a clustered table produces a biased histogram — use reservoir sampling unconditionally, never a positional prefix.
  • HLL is meaningless below the exact-count threshold (default 1,000, ADR-10) — small distinct counts must use exact counting.
  • Histograms alone are wrong on correlated columns (MM8); multi-column stats (§16.2, ADR-11) are not optional for any workload with composite keys.
  • The cost model (§17) must consume relative_error, not just rows — ignoring it produces confidently-wrong plan choices (P5).

16.7 Performance Concerns

  • Histogram range queries are O(log buckets) via binary search on boundaries — never linear-scan a 100+ bucket histogram per predicate.
  • HLL sketch memory is fixed at ~12–16 KB/column (§32 derivation) regardless of table size — the scaling win that makes per-column sketches tractable at thousands of columns.
  • Reservoir sampling at 100K rows on a multi-billion-row table must be a single streaming pass, not a full table scan.

16.8 Edge Cases

  • A column with 100% NULL values — histogram is Histogram::None, selectivity of any non-IS NULL predicate is 0.
  • A freshly-created table with no statistics at all — TableStatistics defaults to the catalog's coarse row_count_estimate, relative_error = 10.0 (max uncertainty, I8), flagged in EXPLAIN.
  • A histogram boundary that exactly equals a predicate's literal — interpolate using the bucket the literal falls into by convention (inclusive lower bound), documented once, applied everywhere.

16.9 Failure Analysis

  • A stale last_analyzed (I11) beyond the 24 h/20%-drift budget (§4) surfaces as a flagged estimate in EXPLAIN, not a silent wrong number — triage via docs/runbooks/bad-cardinality.md.
  • A systemic HLL sketch corruption (e.g. a serialization bug) is caught by a sketch-checksum conformance fixture before it reaches every downstream cardinality estimate (FM11).

16.10 Operational Notes

  • Emits qp.stats span with attributes columns_with_stale_stats, columns_missing_mcv.
  • stats.staleness_flag and stats.exact_count_fallback counters back the statistics-health dashboard (§24).

17. Phase 5 — Cost Model and Bottom-Up Join Enumeration (DPccp) (Weeks 5–7)

17.1 Objectives

Assign every candidate plan a scalar cost (P4, §11.4) and search the join-order space for the minimum-cost tree using DPccp (Moerkotte & Neumann 2006, §5), falling back to greedy beyond the exact-search relation cap (§4).

17.2 Detailed Implementation Steps

Per-operator cost (weights from CostModelConfig, §11.4): TableScan = rows/rows_per_page × io_per_seq_page + rows × cpu_per_row; IndexScan substitutes io_per_random_page on matched rows; HashJoin = L.cost + R.cost + L.rows × hash_build_per_row + R.rows × hash_probe_per_row (smaller side builds); MergeJoin = L.cost + R.cost + (L.rows+R.rows) × merge_per_row, requires both sides sorted on the equi-keys; NestedLoopJoin = L.cost + L.rows × R.cost, viable only with an inner-side index or a tiny inner relation; Sort = input.cost + input.rows × log2(input.rows) × sort_per_row.

DPccp algorithm (Moerkotte & Neumann 2006, Algorithms 3–4, §5): build the join graph (nodes = base relations, edges = join predicates, I9 excludes unfiltered Cartesian edges); iterate connected subgraphs S in increasing size; for each S, iterate every csg-cmp pair (S1, S2) — disjoint connected subgraphs whose union is S with ≥ 1 connecting edge; for each pair, cost the join of the memoised best plans for S1 and S2 under every applicable physical join kind (Hash/Merge/NestedLoop, §19), keep the cheapest as S's memo entry (I5 completeness: every pair must be explored before S is read). The negative-going-neighbour bitmask trick (Moerkotte & Neumann 2006) makes subgraph-membership checks O(1) via the RelationId: u8/u64-bitset representation (§11.1, §4).

Interesting orders (Selinger 1979, §5; P11): the memo is keyed by (RelationSet, InterestingOrder), not RelationSet alone — a plan producing a useful sort order can lose on raw cost-per-row yet win overall by avoiding a downstream Sort enforcer (§20). Interesting orders are collected by walking the pre-enumeration logical plan for every Sort/MergeJoin requirement.

Greedy fallback (Steinbrunn 1997, §5; ADR-12, active beyond dpccp_max_relations = 16, §4): pick the cheapest relation pair, join; repeatedly join in the cheapest next relation; run K rounds of iterative-improvement (random reorder, accept if cheaper).

Wall-clock budget check (P13, I14): the enumerator's outer loop checks elapsed time against plan_timeout_ms (§4) after every subgraph size; on breach, return the best memo entry found so far rather than blocking.

17.3 Deliverable

The DPccp enumerator finds the provably-optimal join order for every connected join graph up to N = 16; the greedy fallback engages automatically beyond that.

17.4 Acceptance Criteria

  • 100,000 join-order candidates enumerated in < 1 s on a 16-relation synthetic graph (M1).
  • Greedy-fallback plans are within 20% of DPccp-optimal cost on every TPC-H join graph small enough for both to run.
  • Optimal-plan cost within 10% of the best-known plan on every TPC-H query at SF1 (M4).

17.5 Conformance Fixtures

  • conformance/corpora/enum/*.json — join graph in, DPccp-optimal plan out, for graphs up to N = 16.
  • conformance/corpora/enum/negative/unfiltered_cartesian.json — asserts I9 rejection.
  • benchmarks/enum_dpccp.rs — the M1 benchmark harness.

17.6 Pitfalls

  • Cartesian products explode the search space for no benefit (I9) — filter them from the join graph; admit only when the query genuinely has no join predicate at all.
  • Bushy plans matter — a plan joining (A,B) then (C,D) then combining can dominate any left-deep plan; DPccp produces bushy plans by construction, don't constrain to left-deep without an explicit flag.
  • The cost model's weights are coupled to the statistics layer (P14) — changing one without recalibrating the other against JCC-H shifts the plan distribution unpredictably.
  • Hashing RelationSet into the DP table is the hottest path in the enumerator — the u8/u64 bitset choice (§11.1) exists specifically to keep this O(1).

17.7 Performance Concerns

  • Memo memory is the ceiling to watch (§4: ≤ 64 MB/plan, M7) — connected-subgraph enumeration on sparse TPC-H-shaped graphs stays in the low thousands of memo entries in practice, far below the 3^16 worst-case bound (§32).
  • Per-csg-cmp-pair costing calls into the cost model (§17.2) — cache per-RelationSet cardinality so it is computed once, not once per pair.

17.8 Edge Cases

  • A single-relation query (N = 1) — DPccp degenerates to a single Scan cost comparison (TableScan vs. IndexScan vs. BitmapScan), no join enumeration runs.
  • A disconnected join graph (two independent join components joined only by an implicit Cartesian) — I9 forces the Cartesian to be explicit and last, never interleaved into the DP search as if it were a real edge.
  • N exactly at the dpccp_max_relations boundary (16) — must take the exact path, not accidentally fall to greedy off-by-one.

17.9 Failure Analysis

  • A DP-table-incomplete bug (I5 violation — a csg-cmp pair skipped) produces a plan that is not actually optimal but reports no error; caught only by conformance replay against known-optimal fixtures (§17.5) — the reason I5 has a dedicated fixture category, not just a runtime assertion.
  • A timeout breach (P13, I14) degrades gracefully to the best-so-far memo entry — telemetry (enum.timeout_triggered) distinguishes "genuinely hard join graph" from "enumerator regression."

17.10 Operational Notes

  • Emits qp.enum span with attributes relations, memo_entries, csg_cmp_pairs_evaluated, fallback_engaged (bool).
  • enum.timeout_triggered and enum.cartesian_admitted are release-blocking-severity alerts, not just dashboard entries (§24).

18. Phase 6 — Cascades-Style Memo and Transformation Rules (Weeks 7–8)

18.1 Objectives

Wrap a Cascades-style memo (Graefe 1995, §5) around the DPccp join order to explore transformation rules (operator-implementation alternatives, non-join-reordering rewrites) that DPccp alone does not cover (P6).

18.2 Detailed Implementation Steps

The memo (§11.9): a DAG of Groups, each an equivalence class of logically-equivalent plans; each Group holds GroupExpressions (one operator + GroupId children); structurally-equivalent expressions dedupe to the same GroupId via Memo.interned (I12) — without this, exploration re-expands the same group exponentially (MM1). Logical properties (computed once per group, at creation): output columns, functional dependencies, row-count estimate, schema.

Required vs. delivered properties (Graefe 1995, §5): a parent group expression demands properties (sort order, partitioning, distinct-keys) of its children; children ascend with what they actually deliver; §20 inserts an enforcer where required > delivered.

Transformation rules (rewrite within a group, logically equivalent): join commutativity (Join(A,B) ↔ Join(B,A)), join associativity (Join(Join(A,B),C) ↔ Join(A,Join(B,C))), filter–join split/push, aggregate–join push, distinct-elimination-over-union.

Implementation rules (logical → physical group expression, same group): Logical(Join) → Physical(HashJoin/MergeJoin/NestedLoopJoin) with each candidate's required child properties attached; Logical(Aggregate) → Physical(HashAggregate/StreamAggregate); Logical(Sort) → Physical(Sort), elided if the input already delivers the order.

Search: optimise_group(g, required_props) returns a cached winner if present; otherwise explores every transformation/implementation rule once (g.explored = true), then recursively costs each physical expression's children under their required properties, keeping the minimum-cost winner per (group, required_props) pair — a property-parameterised generalisation of the DPccp recursion (§17.2), sharing the same memo (§3 per-box notes). Timeout discipline (P13): the Cascades search is worst-case exponential; it inherits the same wall-clock budget check as §17.2 and degrades to the DPccp-only result on breach.

18.3 Deliverable

The Cascades search reproduces the DPccp-chosen join order plus a transformation-rule-explored physical plan for every TPC-H query at SF1.

18.4 Acceptance Criteria

  • The memo deduplicates: planning the same query twice yields the same set of GroupIds (I12, conformance-checked).
  • Cascades search converges in < 100 ms on every TPC-H query (M5).
  • Cascades-search plan cost matches the DPccp-enumerator plan cost on every TPC-H query at SF1 (M4 cross-check).

18.5 Conformance Fixtures

  • conformance/corpora/enum/cascades_matches_dpccp/*.json — one fixture per TPC-H query, asserting cost equality.
  • conformance/corpora/enum/negative/memo_cycle.json — a group-expression shape crafted to detect unbounded mutual recursion.

18.6 Pitfalls

  • The memo is mutually recursive across groups — write cycle detection into the search (§18.2) explicitly; an undetected cycle hangs plan() past its budget (P13).
  • Enforceable required properties (e.g. Sort) and non-enforceable ones (a partitioning the source cannot deliver at all) must be distinguished — the latter forces a child re-plan, not an enforcer insertion.
  • Cascades search is exponential worst-case; the hard timeout (§18.2) is not optional — it is the only thing standing between a pathological query and a starved host.

18.7 Performance Concerns

  • Group.winner is a HashMap<RequiredProperties, WinnerEntry> — keep RequiredProperties small and hashable; a bloated property struct multiplies memo memory (§4 ceiling, M7).
  • Rule exploration is memoised per group via explored: bool — never re-run the full rule catalogue on an already-explored group.

18.8 Edge Cases

  • A group with zero applicable implementation rules (e.g. a logical operator with no physical counterpart yet implemented) must fail plan() with NoFeasiblePlan, never silently drop the group.
  • A required property that is itself contradictory (two incompatible sort orders demanded by two different parents of a shared group) is resolved per-parent — the same group can have two different winners under two different RequiredProperties keys, by design.

18.9 Failure Analysis

  • A dedup miss (I12) inflates cascades.dedup_miss_rate; sustained misses indicate a canonicalisation bug in the group-key hash, not a one-off — investigate the group-key derivation before the search algorithm itself.
  • A timeout-driven degrade to DPccp-only (§18.2) is logged distinctly from a genuine NoFeasiblePlan failure — operators must be able to tell "we found a fine plan faster" from "we found no plan."

18.10 Operational Notes

  • Emits qp.cascades span with attributes groups_created, group_expressions_explored, dedup_hits.
  • cascades.timeout_degrade and cascades.no_feasible_plan counters feed the same alerting tier as enum.timeout_triggered (§17.10).

19. Phase 7 — Physical Operator Lowering (Weeks 8–9)

19.1 Objectives

Convert the winning logical join order (from §17/§18's shared memo) into a PhysicalPlan (§11.10) by choosing, per logical node, the cheapest physical operator family.

19.2 Detailed Implementation Steps

  • Join lowering (ADR-13 physical operator set): inspect JoinPredicate — Equi admits HashJoin/MergeJoin; Theta admits NestedLoopJoin/HashJoin (equi component as build key, theta residual applied as a post-filter); cost every candidate via §17.2's per-operator formulas; pick the minimum, inserting a Sort enforcer if MergeJoin is chosen and children are unsorted on the equi-keys (§20 finalises enforcer placement).
  • Scan lowering / index selection: walk every index on the table; an index whose key prefix matches a pushed predicate is costed as IndexScan; a B-tree index on (a,b) supports a=?/a<?/a>?/a IN (...) but not b=? alone; a hash index supports equality only; a bitmap index suits low-cardinality equality and multi-index AND-combination; cost a plain TableScan and, if ≥ 2 selective indexes apply, a BitmapScan; pick the cheapest, preferring the highest leading-column selectivity when candidates tie.
  • Aggregate lowering: cost HashAggregate always; cost StreamAggregate only if the input already delivers sort order on the group keys (§18.2 property model, P7 property-driven lowering).
  • Materialize/Spool insertion: Materialize above any subtree consumed more than once (e.g. a NestedLoopJoin inner side rescanned per outer tuple); Spool buffers to disk when memory pressure indicates an operator would otherwise spill.
  • Covering-index computation for IndexOnlyScan: the chosen index must cover every column the parent operator demands, computed per-operator, not assumed globally.

19.3 Deliverable

Every TPC-H optimised logical plan lowers to a complete PhysicalPlan; qp explain --format=json renders operator type, estimated rows/cost/width per node.

19.4 Acceptance Criteria

  • 100% of TPC-H SF1 logical plans lower to a PhysicalPlan with no remaining logical nodes.
  • The conformance corpus pins the chosen physical operator per TPC-H query as a regression sentinel — cost-model/statistics changes may shift the choice deliberately, but an unreviewed shift fails CI (§26).
  • p50 physical-lowering latency ≤ 3 ms on TPC-H Q1 (component of M2's 10 ms budget).

19.5 Conformance Fixtures

  • conformance/corpora/tpch/Q01.sql…Q22.sql — reference physical plans at SF1.
  • conformance/corpora/enum/index_selection/*.json — leading-column-selectivity tie-break cases.

19.6 Pitfalls

  • Physical lowering must respect the join order already chosen by §17/§18 — it picks the operator family, never re-orders the join (a layering violation that would silently invalidate the enumerator's cost guarantees).
  • A NestedLoopJoin without an inner-side index is almost always wrong — refuse it unless the cost model shows it cheapest by a clear margin (PlannerConfig::nested_loop_safety_factor).
  • An IndexOnlyScan chosen without verifying the covering set against every parent operator's column demand silently forces a hidden heap fetch at execution.

19.7 Performance Concerns

  • Index-candidate costing is O(indexes × pushed-predicates) per Scan — prune obviously non-matching indexes (wrong leading column) before costing, not after.
  • Materialize insertion must be decided once per subtree, not re-evaluated per consumer — cache the "consumed more than once" fact from the logical plan's ref-count, computed in §18.2.

19.8 Edge Cases

  • A table with zero indexes — only TableScan/BitmapScan (none applicable) are candidates; IndexScan is never considered, not costed-and-rejected.
  • A predicate on an expression, not a bare column (lower(name) = 'x') — no B-tree leading-column match unless a matching expression index exists; falls back to TableScan with a post-filter.
  • A MergeJoin chosen where both children already deliver the required order from an upstream IndexScan — no Sort enforcer needed; §20 must recognise this, not insert one reflexively.

19.9 Failure Analysis

  • A wrong operator choice traced to a cardinality error (not a lowering bug) — distinguish via EXPLAIN ANALYZE's actual/estimated ratio (§21) before assuming §19 itself is at fault.
  • A covering-set computation bug silently produces an IndexOnlyScan that omits a needed column — caught by an executor-side schema mismatch at runtime; the forensic trail is the plan's PlanId cross-referenced against the Scan's declared covering set.

19.10 Operational Notes

  • Emits qp.physical_lower span with attributes operators_considered_per_scan, nested_loop_chosen_count (a high count without matching index coverage is a triage flag).
  • physical.nested_loop_without_index counter backs docs/runbooks/slow-plan.md.

20. Phase 8 — Physical Optimisation (Property Enforcement) (Weeks 9–10)

20.1 Objectives

Walk the lowered PhysicalPlan once more, deriving delivered properties, inserting enforcers where required properties are unsatisfied, and applying peephole rewrites — the pass that makes the plan correct by construction (P7).

20.2 Detailed Implementation Steps

  • Property derivation per operator: TableScan delivers cluster-key order if a clustered index exists, else unordered; IndexScan delivers the index-key order; MergeJoin delivers the equi-key order; Sort delivers its own keys; HashJoin/NestedLoopJoin/HashAggregate deliver no order.
  • Enforcer insertion (top-down walk, I6): where a child's delivered properties do not satisfy the parent's required properties, insert Sort (for an unsatisfied order) or Exchange (for an unsatisfied partitioning — PhaseDeferred("§19"), distributed only, not built Phase 0–9).
  • Peephole rewrites: Sort(Sort(x,k1),k2) where k1 ⊇ k2 drops the outer Sort; adjacent Projects merge; Filter(true, x) drops; Limit(0, x) replaces the subtree with an empty result; HashJoin build-side selection picks the smaller estimated-cardinality side.
  • Equivalence-derived orderings: if a = b (from an equi-join predicate) and the input is sorted on a, the output is also sorted on b — record this so a downstream consumer of b's order does not force a redundant Sort.
  • Subquery property propagation: an un-decorrelated Apply (§15.2 residual) propagates the outer's required properties through to its own required properties, extended by its own; the pass must not lose the outer's sort order while descending into the inner.

20.3 Deliverable

Every PhysicalPlan emerging from this phase has every operator's required properties satisfied by its child (I6), verified by the property-walk validator.

20.4 Acceptance Criteria

  • Property derivation is implemented for all 18 physical operator kinds in §11.10 (100% coverage, conformance-gated).
  • The peephole pass eliminates every redundant Sort on the TPC-H SF1 corpus (0 redundant-sort false positives, §26).
  • Enforcer insertion produces 0 I6 violations across the full TPC-H + JCC-H corpus.

20.5 Conformance Fixtures

  • conformance/corpora/tpch/* (physical, post-optimisation) — pinned final plans.
  • conformance/corpora/enum/negative/property_violation.json — a hand-crafted plan with an unsatisfied MergeJoin sort requirement, asserting the validator catches it.

20.6 Pitfalls

  • Property reasoning is where planners get subtly wrong: HashJoin preserves no ordering of either child — never record one for its output.
  • Equivalence-derived orderings (§20.2) are easy to under-use (missing a free order) or over-use (claiming an order that doesn't actually hold post-Filter) — test both directions explicitly.
  • The Cascades search (§18) and this pass must agree on the property model; drift between them produces plans whose chosen cost does not match the executor's actual behaviour — a silent, hard-to-diagnose regression class.

20.7 Performance Concerns

  • The property-walk is a single top-down pass, O(plan size) — avoid re-deriving a child's delivered properties more than once per parent.
  • Enforcer insertion adds real operators (a Sort has its own cost, §17.2) — this pass must re-fold the enforcer's cost into the plan's total, not leave it unaccounted.

20.8 Edge Cases

  • A plan with no operator requiring any property at all (e.g. a single TableScan with a Filter) — the pass is a no-op walk, must still complete in O(plan size), not skip incorrectly.
  • Two parents of the same shared subtree (via memo winner reuse) demanding two different required properties — each gets its own enforcer path; the shared subtree itself is not mutated (I1-adjacent purity carried into physical plans).
  • An Exchange requirement reached in Phase 0–9 (single-node) must fail closed with a clear "distributed feature not built" error, never silently drop the partitioning requirement (PhaseDeferred("§19")).

20.9 Failure Analysis

  • A property-model drift between §18 and §20 (§20.6) is diagnosed by comparing the Cascades-search-predicted cost against this pass's final cost for the same PlanId — a mismatch beyond floating-point tolerance is a release blocker (§27).
  • An enforcer-insertion bug that fails to insert a needed Sort produces a MergeJoin on unsorted input — caught by the property-walk validator (I6) before EXPLAIN, never silently at execution.

20.10 Operational Notes

  • Emits qp.physical_optimise span with attributes enforcers_inserted, peephole_rewrites_applied.
  • physical.property_violation (I6) is a release-blocking-severity counter, checked at zero before every release (§27).

21. Phase 9 — EXPLAIN, EXPLAIN ANALYZE and Adaptive Re-Plan Hooks (Weeks 10–11)

21.1 Objectives

Ship the planner's user interface (P8): text and JSON EXPLAIN, an EXPLAIN ANALYZE actuals callback, and the hook contract for Phase-1+ adaptive re-planning (PhaseDeferred, this section).

21.2 Detailed Implementation Steps

  • Text format (PostgreSQL convention adapted to qp operator names, §5 ref-impl 1): each operator line shows name, estimated cost, estimated rows, estimated width, plus operator-specific keys (Hash Cond, Filter, Sort Key); indentation encodes the tree.
  • JSON format: schema documented in docs/api/explain.json; mirrors the text format's fields, machine-parseable for tools/qp-plan-diff.
  • EXPLAIN ANALYZE: the executor implements ExecutorActuals { fn actuals(&self, plan_id: PlanId) -> Option<OperatorActuals> } (OperatorActuals { actual_rows, actual_loops, actual_time_ms, peak_memory_bytes }); the formatter decorates each operator with actuals when present, and computes the actual/estimated ratio inline — the single most useful number in the output, never left for the operator to compute by hand.
  • Adaptive re-plan hook (Stillger et al. 2001 LEO, §5; PhaseDeferred("§21")): AdaptiveCallback::on_stage_complete(completed: PlanId, actuals: OperatorActuals) -> AdaptiveAction where AdaptiveAction ∈ {Continue, Replan{remaining_subtree, new_stats}, Abort(PlannerError)}. When actuals diverge from estimates by more than adaptive_replan_threshold (default 5×), the (not-yet-built) replanner would update statistics for the affected relations and re-run §17/§19 on the remaining subtree only — never the already-executed prefix. This phase ships the trait contract and a reference test harness; the replanner body is PhaseDeferred("§21").
  • CLI surface (qp-cli): qp explain --query <file> [--format=text|json] [--analyze].

21.3 Deliverable

qp explain produces pinned text and JSON output for every TPC-H query; the AdaptiveCallback trait compiles against a mock executor and is exercised by one reference test that injects a deliberately-wrong cardinality and asserts the callback is invoked with the correct divergence ratio.

21.4 Acceptance Criteria

  • EXPLAIN text stays under 1 KB per TPC-H query, one line per operator (M6).
  • Text and JSON EXPLAIN output for every TPC-H query matches its golden fixture byte-for-byte (§26).
  • The adaptive-hook reference test demonstrates the callback fires exactly when divergence exceeds adaptive_replan_threshold, and does not fire below it.

21.5 Conformance Fixtures

  • conformance/corpora/explain/*.golden.txt, *.golden.json — one pair per TPC-H query.
  • conformance/corpora/explain/negative/oversized_plan.json — a 22-way join, asserting the indented/summary-mode fallback (§21.8) engages rather than overflowing.

21.6 Pitfalls

  • EXPLAIN cost numbers are cost-model units, not seconds — state this explicitly in docs/api/explain.json; PostgreSQL's decades-long user confusion on this exact point is the cautionary tale (§5 ref-impl 1).
  • The actual/estimated ratio is the debugging payoff of EXPLAIN ANALYZE — compute and display it; do not leave it as an exercise for the operator reading two numbers.
  • A 22-way join's indented text tree can overflow a terminal — provide a summary mode (top-N most expensive operators) alongside the full tree.

21.7 Performance Concerns

  • Rendering EXPLAIN must not re-walk the plan more than once — annotate cost/cardinality once during §17–§20, read-only here.
  • JSON serialization of a large plan (32-way join) should stream, not buffer the whole tree in memory before writing (relevant at the §4 memory ceiling).

21.8 Edge Cases

  • A plan with zero operators (e.g. Values with a constant row) — EXPLAIN still emits a well-formed single-line tree, not an empty string.
  • Executor actuals reported for a PlanId the planner never emitted (a stale callback from a cached plan) — ExecutorActuals::actuals returning None is the correct contract response, never a panic.
  • A 32-way join's EXPLAIN text exceeding the 1 KB target (M6) falls back to the summary mode named in §21.6, itself a named, tested behaviour, not an unbounded string.

21.9 Failure Analysis

  • A golden-fixture mismatch in CI (§21.5) is either a deliberate formatting change (update golden, reviewed) or a real regression in cost/cardinality propagation from an earlier phase — the actual/estimated ratio on staging traffic is the fastest way to tell which.
  • An adaptive-hook callback that never fires despite real divergence (once Phase-1+ implements the replanner body) indicates a threshold miscalibration or broken actuals wiring — docs/runbooks/replan-thrash.md (FM9) is the paired runbook for the opposite failure (firing too often).

21.10 Operational Notes

  • Emits qp.explain span with attributes format, analyze_requested (bool).
  • The adaptive-hook's PhaseDeferred("§21") call site lives in crates/qp-adaptive/src/hook.rs; the un-defer trigger is listed in §35.

24. Operational Readiness

Metrics (Prometheus, ADR-19). Per-stage span duration histograms (qp.bind, qp.lower, qp.rewrite, qp.stats, qp.enum, qp.cascades, qp.physical_lower, qp.physical_optimise, qp.explain); the counters named in every phase's N.10 (e.g. enum.timeout_triggered, rewrite.confluence_violation, physical.property_violation).

Tracing (OpenTelemetry, ADR-18). One span per pipeline stage (§8.3), parented under one root span per plan() call; trace ID carried into EXPLAIN ANALYZE output so a slow query's plan-time breakdown is one click from its execution trace.

Structured logging. JSON logs at INFO (redacted literals, T6) and DEBUG (full detail, gated); every log line carries the PlanId and trace ID.

Dashboards. A "planning health" Grafana board: p50/p95/p99 planning latency (§4), timeout rate (enum.timeout_triggered), cardinality-accuracy trend (M3), rewrite-iteration distribution.

Alerting philosophy. Page on release-blocking-severity counters sustaining > 0 for 5 minutes (physical.property_violation, rewrite.confluence_violation, enum.cartesian_admitted); ticket (non-paging) on staleness/drift signals (stats.staleness_flag).

SLOs. p99 planning latency ≤ 200 ms (§4); 0 I1/I2/I6 violations in production per rolling 24 h window.

Incident response. First action on any planning-latency page: pull the qp.enum/qp.cascades span attributes for the offending PlanId — relations, memo_entries, fallback_engaged disambiguate "hard join graph" from "enumerator regression" in one query.

Runbooks. docs/runbooks/slow-plan.md (triage path: bind → rewrite iterations → enum timeout → physical operator choice); docs/runbooks/bad-cardinality.md (staleness → histogram gap → multi-column correlation); docs/runbooks/replan-thrash.md (FM9).

Backup/restore. qp holds no persistent state to back up; the statistics blob is the host's backup responsibility (§1 boundaries).

Deployment topology. Embedded rlib inside the host engine's process, or cdylib loaded by a non-Rust host (§1); no independent deployment unit.

Canary/rolling-upgrade/rollback. A new qp version is canaried by running its plans side-by-side (shadow mode) against the previous version on a query sample, diffing EXPLAIN cost and chosen operator before promoting; rollback is a binary/library swap (I4 guarantees the same inputs reproduce the same plan post-rollback).

25. Compatibility & Versioning

Wire compatibility. qp has no network wire format; EXPLAIN JSON (docs/api/explain.json) is the only externally-consumed serialization and is versioned independently via a schema_version field.

Storage compatibility. Statistics blobs (qp stats build output) carry a version tag; a qp-stats reader rejects an unrecognised future version rather than misinterpreting it.

Schema-evolution. Adding a LogicalPlan/PhysicalPlan/Type variant (§11.3, §11.8, §11.10) is additive at the Rust level but requires every Rule and the validator to handle it — coordinated via a minor-version bump and a conformance-corpus addition, never a silent patch release.

API stability. Planner::plan/Planner::explain (§11.10) are the SemVer-stability boundary; Catalog/Statistics/Rule/CostModel traits (§11) are the extension points — adding a method to a public trait is a major-version break unless given a default implementation.

Migration. A statistics-format version bump ships with a qp stats migrate path in qp-cli.

Deprecation policy. A deprecated ADR-level decision (e.g. a rejected-alternative flip) is announced one minor version ahead via CHANGELOG.md, removed on the next major version.

SemVer policy. MAJOR.MINOR.PATCH; PATCH = bugfix with no plan-output change on the conformance corpus; MINOR = additive (new rule, new operator, new statistics kind) with CI-reviewed plan-output diffs; MAJOR = any ABI (qp-ffi) or public-trait break.

Rolling-upgrade guarantees. Because qp is embedded (no independent service), "rolling upgrade" means the host engine's own rollout; qp guarantees I4 determinism holds within one version, and documents any deliberate cross-version plan-output change in CHANGELOG.md.

26. Testing & Verification Strategy

Unit tests. Per-crate, covering pure functions (coercion lattice, selectivity primitives, histogram interpolation) in isolation.

Integration tests. The conformance runner (conformance/runner, §10) replaying every corpus bucket (bind, lower, rewrite, cardinality, enum, tpch, jcch, explain, determinism, §8.3) end-to-end.

Property tests. Rule confluence (I13: apply(apply(p)) == apply(p)); canonicaliser idempotence (I4-adjacent, §14.4); cost additivity (I3).

Differential testing. Cascades-search plan cost vs. DPccp-enumerator plan cost, required to match on every TPC-H query (M4 cross-check, §18.4).

Fuzzing. cargo-fuzz over the bind and rewrite boundaries (ADR-23, T10); scheduled nightly via fuzz.yml, minimum 30-day continuous run before a release is considered fuzz-hardened.

Chaos / fault injection. A fake Catalog that mutates mid-call (T5/FM10 fixture); a fake Statistics returning out-of-domain values (I7/I8 boundary fixtures).

Deterministic replay. Every conformance fixture replays byte-for-byte from its corpus file — no live database, no network, no wall-clock dependency beyond the injected last_analyzed (§7 debugging methodology).

Soak testing. A 30-day continuous fuzz run (M9-adjacent milestone, §38) with 0 planner panics as the exit criterion.

Conformance. §26 buckets each emit Pass/Fail/Deferred(blueprint_ref); a Deferred outcome whose reference does not appear in §35's Deferred Features Register blocks the PR.

Performance-regression gating. Every M# target in §28 is checked in tpch.yml nightly; a regression beyond 10% blocks promotion to the next release channel (§27).

Reproducible builds. Cargo.lock pinned and checked in (ADR-25); cargo vendor snapshots dependencies for release artifacts; a release build from a tagged commit is bit-reproducible given the same toolchain.

Dependency auditing. cargo audit runs on every PR touching Cargo.toml/Cargo.lock and on a weekly schedule (security.yml, ADR-24); a new advisory blocks merge until triaged.

28. Performance Engineering

Methodology. Benchmarks live in benchmarks/ (§10) and run under criterion-style statistical harnesses, not wall-clock single-shot timing; every M# target below is checked in tpch.yml.

Allocation analysis. Arc-sharing (P3) is verified by an allocation-count assertion in the rewrite-loop benchmark — a rule that clones more than its changed subtree regresses this.

Lock/contention analysis. qp holds no locks internal to one plan() call (single-threaded per call, ADR-22); contention analysis is scoped to the host's thread-pool scheduling of concurrent plan() calls, out of qp's control surface.

Cache-locality. RelationSet as a packed u64 bitset (§11.1) is chosen specifically for cache-friendly memo-key hashing (§17.6).

Syscall overhead. Zero syscalls inside plan() (no I/O, ADR-22) — the only syscalls are the host's Catalog/Statistics snapshot reads, outside qp's cost budget.

Tail-latency analysis. p99 planning latency (§4) is dominated by DPccp/Cascades search on dense join graphs — the greedy fallback (ADR-12) and the wall-clock budget (P13) are the two levers that bound the tail.

29. Scalability Analysis

Stays constant. Per-relation cost-model overhead (O(1) per Scan); memo-key hashing cost (O(1), packed bitset, §11.1); EXPLAIN line count per operator.

Grows. Join-order search space — O(3^n) worst-case bound (Moerkotte & Neumann 2006, §32), but O(edges) in practice on sparse graphs; memo memory — O(groups × avg expressions per group); rewrite loop cost — O(plan size × iterations).

Named bottlenecks, in order. (1) DPccp/Cascades search on dense join graphs beyond the practical sparse-graph regime; (2) statistics build time on very wide tables (many columns × HLL sketch + histogram build each); (3) rewrite-loop iteration count on deeply nested expression trees.

Horizontal/vertical scaling. qp itself does not scale horizontally (one plan() call, one thread, ADR-22) — horizontal scaling is the host engine running many concurrent plan() calls across its own thread pool; vertical scaling (more CPU per call) directly shortens DPccp/Cascades wall-clock time.

Sharding/partitioning. Out of scope for qp itself (single-node, §1); the deferred Exchange operator (§19, PhaseDeferred("§19")) is the extension point for a partition-aware physical plan.

Coordination overhead. None within qp (no shared mutable state across concurrent plan() calls, I4); the host's Catalog/Statistics snapshot mechanism is the only cross-call coordination point.

Practical ceiling and levers beyond it. The practical ceiling is the dpccp_max_relations = 16 exact-search boundary (§4); beyond it, the levers are (a) the greedy fallback (ADR-12, already built), (b) genetic enumeration (PhaseDeferred("§17"), PostgreSQL GEQO-style, §34 AA4), and (c) a plan cache (PhaseDeferred("§29")) to amortise repeated planning of the same parameterized shape.

30. Mental Models & First Principles

  • MM1 — A logical plan is an equivalence class, not a single tree. Predicts why join enumeration needn't recompute a subtree it has already priced; the bug class without it is exponential re-exploration of the same subplan (I12). Applied in §18.2.
  • MM2 — Cost is a bet under uncertainty, not a fact. Every Cardinality carries an error bar (I8); predicts that a lower-cost-but-higher-variance plan can lose to a higher-cost, lower-error one. The bug class without it is overconfident plan selection that regresses under real-world skew. Applied in §16.2, P5.
  • MM3 — A join graph's connectivity, not its size, bounds the search. Predicts DPccp's plan-space via connected subgraphs, not N! permutations; the bug class without it is a naïve enumerator that treats every join graph as if it were fully connected. Applied in §17.2, §32.
  • MM4 — Properties flow two ways: required down, delivered up. Predicts exactly where an enforcer must be inserted; the bug class without it is a MergeJoin silently fed unsorted input. Applied in §18.2, §20.2.
  • MM5 — Predicate pushdown across outer joins is a null-rejection question, not a syntax question. Predicts which predicates are unsafe to push; the bug class without it is a silently wrong outer-join result. Applied in §15.2, §15.6.
  • MM6 — A histogram is a lossy compression of a CDF. Predicts interpolation error inside a bucket; the bug class without it is confident misestimation on skewed data inside a single wide bucket. Applied in §16.2.
  • MM7 — Statistics decay; plans do not know it unless told. Predicts stale-statistics regressions that look like cost-model bugs but are staleness bugs; the bug class without it is silent drift between estimate and reality. Applied in I11, §16.9, §23 FM3.
  • MM8 — The optimizer's real adversary is correlation, not volume. The independence assumption breaks under correlated columns before it breaks under scale; the bug class without it is cross-column misestimation that no amount of per-column histogram precision fixes. Applied in §16.2 (multi-column stats), §5 (Leis 2015).

DuckDB made a deliberately lightweight statistics layer (no MCV list persisted across restarts, sampling-heavy) its core decision — it wins in an embedded, single-process analytical context where planning-time simplicity and startup speed dominate over marginal cardinality accuracy on adversarial skew.

32. Back-of-Envelope Capacity Model

  1. Join-order search space (naïve). Distinct bushy join trees for N labelled relations = Catalan(N-1) × N!. At N = 10: Catalan(9) = 4,862, 10! = 3,628,800 ⇒ ≈ 1.76 × 10^10 — the textbook "10-relation joins have billions of plans" figure (Selinger-era motivation, §5).
  2. DPccp worst-case memo size. Bounded by 3^N connected-subgraph/complement-pair enumerations (Moerkotte & Neumann 2006, §5). At N = 16 (§4 cap): 3^16 ≈ 4.30 × 10^7 — the §4 plan-space-size row, derived directly.
  3. DPccp practical memo size (sparse TPC-H-shaped graphs). Empirically low thousands of memo entries — orders of magnitude below the worst-case bound in (2), because real join graphs are sparse (each relation joins to 1–3 others), not fully connected.
  4. Memo memory footprint at N = 16. ≈ 2,000 practical groups (from (3)) × ~5 fields/ GroupExpression × 8 bytes/field ≈ 80 KB core structure, well inside the M7/§4 64 MB ceiling — the ceiling exists for pathological (near-worst-case) graphs, not the typical case.
  5. Planning-time budget per relation-set evaluation. plan_timeout_ms (5,000 ms, §4) ÷ worst case 3^16 probes ≈ 1.16 × 10^-4 ms/probe budget if every probe were reached — in practice the sparse-graph case (3) leaves orders of magnitude of slack, which is exactly why the p99 target (§4: 200 ms) sits far under the hard timeout.
  6. Cardinality-error compounding across a join chain. For per-join relative error e = 0.1 (I8 domain) over k = 5 joins, compounded multiplicatively: 1 - (1-e)^k = 1 - 0.9^5 ≈ 0.41 — a 5-way join chain can carry ~41% compounded relative error even with a "good" 10%-per-join estimator, motivating the M3 target (within 10× actual, not 10%).
  7. HyperLogLog sketch size. 2^14 registers (ADR-10) × 6 bits/register (dense HLL++ encoding) / 8 bits/byte = 12,288 bytes ≈ 12 KB/column sketch; with alignment/padding overhead this rounds to the ≈ 16 KB/sketch figure used for capacity planning at thousands of columns.
  8. Statistics-build throughput requirement. M8 requires 1 GB TPC-H processed in < 60 s ⇒ ≥ 1,024 MB / 60 s ≈ 17.1 MB/s sustained scan-plus-histogram-build throughput — the floor qp stats build's reservoir-sampling implementation must clear.
  9. RelationId/bitset capacity ceiling. RelationId: u8 (§11.1) addresses up to 256 distinct IDs, but the DPccp fast path packs a RelationSet into a single u64 bitset ⇒ a hard 64-relation cap on the exact-search representation (§4), independent of the u8 ID width itself.
  10. EXPLAIN size budget. M6 targets < 1 KB/query at ~1 line/operator; at ≈ 40 bytes/line, that budget covers ≈ 25 operators comfortably — a 22-way TPC-H join (≈ 40–50 operator-tree nodes including enforcers) sits close to the budget, which is why §21.6/§21.8 name an explicit summary-mode fallback rather than letting the budget silently blow past 1 KB.
  11. Statistics staleness window in row terms. At the I11/§4 20%-drift trigger, a table with a stats-build row_count_estimate of 10,000,000 tolerates drift up to 2,000,000 rows (insert/ delete/update net) before ANALYZE/replan is triggered — the number an operator sizing an ANALYZE cadence schedule actually needs.
  12. Adaptive replan divergence trigger, in cost terms. Default adaptive_replan_threshold = 5× (§21.2); combined with the M3 accuracy target (within 10× on ≥ 80% of joins), roughly 1-in-5 of the "acceptable" estimates (those between 5× and 10× off) are exactly the ones the Phase-1+ adaptive hook (§21) is designed to still catch and correct at runtime.

34. Alternative Architectures (Roads Not Taken)

AA1 — Top-down-only (pure Cascades/Volcano, no separate DPccp stage).

AST -> Bind -> LogicalPlan -> [ single top-down Cascades/Volcano search:
                                explore + implement + cost, one memo,
                                no separate bottom-up join stage ] -> PhysicalPlan

Regime: large, long-lived optimiser codebases with dozens of engineers and years to mature a rule catalogue (SQL Server's Cascades, Calcite's VolcanoPlanner). Rejected here because a from-scratch DPccp is exhaustively testable against the System R reference (§9 ADR-04) before the larger, harder-to-verify Cascades rule surface is trusted — the right call for a Phase-0-to-Phase-9 build timeline, wrong for a mature codebase that already trusts its rule catalogue.

AA2 — Heuristic/rule-only optimiser (no cost model at all).

AST -> Bind -> LogicalPlan -> [ fixed heuristic rewrite + greedy right-deep
                                join order, no cost model, no statistics ] -> PhysicalPlan

Regime: embedded, resource-constrained engines where statistics infrastructure costs more than it returns (SQLite's where.c, §5 ref-impl 4). Rejected here because the stated conformance bar (within 10% of best-known plan on every TPC-H query, M4) is unreachable without cost-based enumeration on non-trivial join graphs — the right call for SQLite's embedded-device niche, wrong for a system whose explicit purpose is teaching statistics-driven optimisation (§2).

AA3 — Adaptive/runtime re-planning as the primary strategy.

AST -> Bind -> LogicalPlan -> [ minimal static plan, stage-by-stage execution,
                                re-optimise after every stage using actuals ] -> PhysicalPlan (evolves at runtime)

Regime: distributed batch analytics with expensive, hard-to-estimate shuffle costs (Spark AQE, §5 ref-impl 5). Rejected as the primary strategy here because re-planning overhead dominates on the single-node, millisecond-budget workload this planner targets (§4) — it is exactly right for Spark's minutes-long batch jobs where a wrong initial estimate costs far more than one re-plan, and is why qp keeps it as the Phase-9 stretch hook (§21.2) rather than the load-bearing mechanism.

AA4 — Genetic/randomized search as the primary enumerator for all N.

AST -> Bind -> LogicalPlan -> [ genetic algorithm over join-tree population:
                                crossover + mutation + fitness = cost,
                                for every N, not just N > 16 ] -> PhysicalPlan

Regime: very large join graphs (N ≫ 32) where even DPccp's practical-case sparsity no longer saves enough search time (PostgreSQL beyond geqo_threshold, §5 ref-impl 1; Steinbrunn 1997, §5). Rejected as the primary enumerator here because it sacrifices DPccp's provable optimality on the N ≤ 16 exact-search range for no measured benefit at the join sizes TPC-H exercises — qp keeps genetic enumeration as a deferred N > 32 extension (PhaseDeferred("§17")), not the default path.

36. Glossary

  • Apply operator. The LogicalPlan node for an un-decorrelated correlated subquery; a per-outer-row nested evaluation the decorrelator tries to lift to a flat Join (§11.8, §15.2).
  • Bushy plan. A join tree where an internal node's two children are themselves both joins of ≥ 2 relations, as opposed to a left-deep chain; DPccp produces these by construction (§17.6).
  • Cardinality. The estimated row count of a plan node plus its relative_error (§11.5, I8).
  • Cascades memo. The group/group-expression search structure that generalises DPccp with property-parameterised winners (§11.9, §18.2).
  • Catalog. The host-owned metadata provider (Catalog trait) for table/index/statistics lookup; snapshotted once per plan() call (§11.2, I10).
  • Coercion lattice. The partial order of allowed implicit type conversions the binder consults when type-checking a BinaryOp/Cast (§13.2).
  • Connected subgraph. A subset of join-graph relations whose induced edge set is connected; the unit DPccp enumerates over (§17.2).
  • Correlated subquery. A subquery whose predicate references a column from an outer scope; tracked at bind time (§13.2) for the decorrelator (§15.2).
  • Cost model. The subsystem mapping an operator + child costs to a scalar Cost (§11.4, P4).
  • Csg-cmp pair. A pair of connected subgraphs (S1, S2) whose union is a larger connected subgraph S with a connecting edge — DPccp's core enumeration unit (§17.2, Moerkotte & Neumann 2006).
  • Decorrelation. Rewriting a correlated subquery (Apply) into an equivalent flat Join (§15.2, Galindo-Legaria & Joshi 2001).
  • Delivered properties. The physical properties (sort order, partitioning) an operator actually produces, as opposed to what its parent requires (§20.2).
  • DPccp. The bottom-up dynamic-programming join enumerator over connected subgraphs and complement pairs (§17.2, Moerkotte & Neumann 2006).
  • Enforcer. A physical operator (Sort, Exchange) inserted solely to satisfy a required property a child does not deliver (§20.2).
  • Equi-join. A join whose predicate is a conjunction of column-equality pairs, represented as JoinPredicate::Equi (§11.8).
  • EXPLAIN / EXPLAIN ANALYZE. The planner's rendering surface; ANALYZE decorates estimated values with executor-reported actuals (§21).
  • Functional dependency. A column relationship (col1 → col2) the multi-column statistics layer uses to correct the independence assumption (§16.2, ADR-11).
  • Greedy fallback. The non-exhaustive join-order heuristic (pick-cheapest-next + iterative-improvement) used beyond dpccp_max_relations (§17.2, ADR-12, Steinbrunn 1997).
  • Group / Group Expression. A Cascades equivalence class of logically-equivalent plans, and one concrete operator + children within it (§11.9).
  • HyperLogLog (HLL). A probabilistic distinct-count sketch with fixed memory and bounded standard error (§16.2, ADR-10, Flajolet 2007).
  • Implementation rule. A Cascades rule rewriting a logical group expression into a physical one in the same group (§18.2).
  • Independence assumption. The default (often wrong) assumption that two predicates' selectivities multiply; corrected by multi-column statistics where it fails (§16.2, MM8).
  • Interesting order. A sort order a downstream operator can exploit; the DPccp memo key includes it because it can make a locally-worse plan globally cheaper (§17.2, P11, Selinger 1979).
  • JCC-H / Join Order Benchmark (JOB). The cardinality-accuracy conformance corpus (§5, §16.5).
  • Join graph. The graph whose nodes are base relations and whose edges are join predicates, the input to DPccp (§17.2).
  • Logical plan. The algebra-IR tree (LogicalPlan) every rewrite/cost/enumeration phase codes against, before physical lowering (§11.8, P2).
  • Materialise. A physical operator buffering a subtree's output for re-scan by a consumer that needs it more than once (§19.2).
  • Max-diff histogram. A histogram whose bucket boundaries fall at points of maximum frequency change, best for skewed data (§16.2, ADR-08, Poosala 1996).
  • MCV (Most Common Values) list. A per-column list of exact top-K value/frequency pairs (§11.6, ADR-09).
  • Memo. The shared search/dedup structure underlying both DPccp and Cascades (§11.9, I12).
  • Negative-going-neighbour bitmask. The bit-trick that makes DPccp's connected-subgraph enumeration efficient over a packed RelationSet (§17.2, Moerkotte & Neumann 2006).
  • NestedLoopJoin safety factor. The configurable margin (PlannerConfig:: nested_loop_safety_factor) requiring a clear cost advantage before choosing an un-indexed nested loop (§19.6).
  • Physical plan. The executable operator tree (PhysicalPlan) emitted after lowering and property enforcement (§11.10, §19, §20).
  • Plan equivalence / semantic preservation. The invariant that every rewrite's output answers the same query as its input for any catalog state (I1).
  • Property (required / delivered). The sort/partition/distinct contract a physical operator demands of, or provides to, its neighbours in the plan tree (§18.2, §20.2, MM4).
  • Rejected alternative (ADR). The tech-stack option a decision did not take, paired with the concrete regime where it would have won (§9).
  • Relative error. The one-sigma uncertainty bound attached to a Cardinality estimate (§11.5, I8, P5).
  • Reservoir sampling. A streaming sampling technique avoiding positional bias when building a histogram from a large table (§16.2, §16.6).
  • Rewrite rule. A pure function LogicalPlan → Option<LogicalPlan> applied by the fixed-point rewrite loop (§11.7, §15.2, P3).
  • Selectivity. The fraction (∈ [0,1]) of rows a predicate is estimated to pass (§11.5, I7).
  • Statistics staleness. The condition where last_analyzed age or row-count drift exceeds budget, flagged rather than silently trusted (§16.2, I11, MM7).
  • Transformation rule. A Cascades rule rewriting one logical group expression into another, logically-equivalent one in the same group (§18.2).
  • TPC-H. The 22-query decision-support benchmark used as the conformance corpus (§5, §19.5).
  • Winner (Cascades). The lowest-cost group expression recorded per (group, required_props) key (§11.9).
