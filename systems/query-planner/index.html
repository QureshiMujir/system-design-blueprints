In one paragraph

The Database Query Planner (qp) is a library that takes a parsed SQL query plus table metadata and statistics, and produces an executable plan together with a readable EXPLAIN description (§1). It exists because two logically equivalent ways of running the same joins can differ enormously in cost, and only the planner can tell a 50 ms plan from a 50-minute one before the executor spends the time (§2). It is embedded in a host database process, as a Rust library or through a C interface. It parses no SQL, stores no catalog and executes nothing (§1). Database-engine implementers run it, and on-call engineers debug it through EXPLAIN ANALYZE (§1).

The problem, concretely

Take the blueprint's own query: join orders to customer on the customer key, keeping only orders on or after 2025-01-01 (§8.4). In the bound plan the date filter sits above the join. The planner's first job is to move it down onto the orders scan, which is what the rewritten plan in §8.4 does. Its second job is to pick a physical join. The blueprint's answer is a hash join that builds on customer and probes with orders (§8.4). The first move comes from a rewrite rule and the second from a cost comparison (§15.2, §19.2).

Now add more tables. For N labelled relations there are Catalan(N-1) × N! distinct bushy join trees. At N = 10 that is 4,862 × 3,628,800, about 1.76 × 10^10 (§32 item 1). DPccp avoids that by searching connected subgraphs instead (§17.2, MM3).

The estimates that drive the search are also unreliable. A cost comparison is "a bet against an error bar", not a fact (§2, MM2). The default assumption that two predicates are independent breaks on correlated columns before it breaks on scale (MM8). Statistics decay, and a plan does not know that unless it is told (MM7, P12). Finally the search itself can run away. A 30-relation join with no equi-predicates is the blueprint's example of a plan-space explosion that could starve the host process (T1, P13). The design answers each pressure with a mechanism: rewrite rules, statistics that carry an error bar, a join enumerator that only visits connected subgraphs, and a hard planning-time budget (§1, P5, P13).

How it works, end to end

Follow one query through the boxes of §3's diagram. Each box is a crate:

 sql_ast::Statement  (from the upstream parser; trust boundary A)
   -> qp-bind        resolve names, check types, expand *, bind subqueries    -> BoundStatement
   -> qp-ir          lower to canonical LogicalPlan                           -> LogicalPlan
   -> qp-rewrite     fixed-point rules: pushdown, decorrelate, fold           -> LogicalPlan (rewritten)
   -> qp-stats + qp-cost   attach a Cardinality (rows + error bar) per node
   -> qp-enum (DPccp) <-- one shared memo --> qp-cascades                     -> best logical join order
   -> qp-physical    lower to physical operators                              -> PhysicalPlan (unenforced)
   -> qp-physical    insert enforcers, peephole rewrites                      -> PhysicalPlan (final)
   -> qp-explain     text / JSON EXPLAIN, EXPLAIN ANALYZE                     -> executor (trust boundary B)
  1. Bind (qp-bind, §13). It resolves every name against a Catalog snapshot taken once per plan() call, type-checks every expression, expands SELECT * and CTEs, and records correlated references for later (§13.2, I10). An unqualified name that matches two columns fails with an ambiguity error instead of guessing. §8.5's example is an unqualified id that matches both orders.id and order_items.id (§8.5).
  2. Logical IR (qp-ir, §14). The bound query becomes a tree of Scan, Filter, Project, Join, Aggregate and similar nodes in a canonical shape (§14.2, §8.2). Every later phase codes against this one LogicalPlan and never goes back to the AST (P2). A correlated subquery becomes an Apply node, never a Join (§8.1, §14.2).
  3. Rewrite (qp-rewrite, §15). A pinned list of 14 rules runs until a full pass changes nothing (§15.2). It converges in under 5 iterations per TPC-H query as a target (§15.4, M9).
  4. Statistics and cost (qp-stats, qp-cost, §16). Every cardinality number flows through this one subsystem, and the enumerator never reads a histogram directly (§3, P5).
  5. Enumerate and search (qp-enum, qp-cascades, §17, §18). DPccp seeds winners for join order and the Cascades search explores transformation and implementation rules around them, both on one memo (§3, §8.3, P6).
  6. Physical lowering and optimisation (qp-physical, §19, §20). Lowering chooses an operator family per node and never re-orders the join (§19.6). The second pass is the only place enforcers are inserted (§3, P7).
  7. Explain (qp-explain, §21). It is built before the executor handoff and is where the deferred adaptive hook attaches (P8, §3).

Around the pipeline: qp-core holds the entry point, config and the Catalog/Statistics traits, qp-cli is the qp explain and qp stats build command line, and qp-ffi is the C ABI (§1, §10). Tracing is one OpenTelemetry span per stage (ADR-18). Metrics use a Prometheus pull endpoint /metrics (ADR-19), although §1 also says there is no planner-owned network listener (§1, ADR-19). The blueprint states both and does not reconcile them.

The core ideas

Rewrite rules that never mutate, run to a fixed point (§15, P3, I13)

A rule is a pure function from a plan to an optional new plan. It never mutates its input, and subtrees are shared through Arc (P3). The engine applies the 14 rules in the pinned order of §15.2 until a whole pass reports no change, capped by max_iterations, which is a safety net (§15.2). A rule set that needs more passes has a confluence bug (§15.7), and two rules that fight each other hit the cap (FM-1). Rule confluence (applying a rule twice equals applying it once) is an invariant (I13, T7).

Two rules carry most of the lesson. Predicate pushdown splits a filter at AND, then sends each conjunct to the side whose columns it touches (§15.2). Across an outer join this is a question about whether the predicate rejects NULLs, not a question of syntax (MM5). §8.6's failure example is a hypothetical buggy build that pushes i.discontinued = false through a left outer join. The validator catches it on a negative fixture and raises an internal error naming the rule (§8.6, P10).

Decorrelation lifts a correlated subquery out of its per-row Apply into a flat join. With no aggregation and no LIMIT it becomes a plain Join. With aggregation it becomes a left outer join grouped on the correlated key. A subquery containing LIMIT stays Apply, the one shape that cannot be lifted (§15.2). §2 attributes the taxonomy to Galindo-Legaria and Joshi in 1999, while §13.2, §15.2 and the glossary say 2001, and the §5 reading list gives "1999/2001" (§2, §5, §15.2, §36).

Estimating rows: statistics with an error bar (§16.2, §11.5, MM2, MM6)

Every plan node carries Cardinality { rows, relative_error }, where the error lies in [0, 10] (§11.5, I8). A Selectivity is a fraction in [0, 1] (§11.5, I7). The pieces (§16.2):

  • A histogram (equi-depth by default, or max-diff) answers "how many rows lie between low and high" by linear interpolation inside the bucket that holds the range. It is a lossy compression of the value distribution, so error hides inside wide buckets (ADR-08, MM6).
  • An MCV list (most common values) holds exact frequencies for the top K values. An equality predicate checks it first. On a miss the estimate is (1 - Σ MCV.frequencies) / (distinct_count - K) (ADR-09, §16.2).
  • A HyperLogLog sketch (2^14 registers) estimates distinct counts, about 0.81% standard error. Below 1,000 rows it counts exactly, and a primary key sets distinct_count = row_count (ADR-10, §16.2).
  • Propagation up the tree: a Filter multiplies by its selectivity, and a single-key equi-join yields left.rows × right.rows / max(left_distinct, right_distinct). Multi-predicate AND assumes independence unless multi-column statistics override it (§16.2, ADR-11, MM8).

Errors compound along a join chain. With a per-join error of 0.1 over 5 joins, 1 - 0.9^5 ≈ 0.41, which motivates a target of within 10× of actual on ≥ 80% of joins rather than within 10% (§32 item 6, M3). The cost model also prefers lower-variance plans within 10% of the lowest cost (P5).

Join order by DPccp: search connected pairs, not permutations (§17.2, MM3, ADR-05)

Model the query as a join graph. Nodes are relations and edges are join predicates, with unfiltered Cartesian edges excluded (§17.2, I9). DPccp (dynamic programming over connected subgraph / complement pairs) works bottom-up in three steps (§17.2):

  1. Take connected subgraphs S in increasing size.
  2. For each S, enumerate every pair of disjoint connected subgraphs (S1, S2) that union to S and have at least one connecting edge (a csg-cmp pair).
  3. Cost the join of the stored best plans for S1 and S2 under each applicable physical join and keep the cheapest as S's entry. Every pair must be explored before S is read (I5).

The search size depends on connectivity, not on N! (MM3). The worst case is bounded by 3^N, so 3^16 ≈ 4.3 × 10^7 at the N = 16 cap (§32 item 2). Real TPC-H-shaped graphs are sparse, and the practical memo is "low thousands" of entries (§32 item 3). Bushy trees come out by construction (§17.6).

The memo key is (RelationSet, InterestingOrder), not the relation set alone. A plan that yields a useful sort order can lose on raw cost yet win overall by avoiding a later Sort (§17.2, P11). Costs are one scalar f64 that is additive over subtrees (P4, I3). The §11.4 per-row weights are hash_build_per_row 0.05, hash_probe_per_row 0.02, merge_per_row 0.03 and sort_per_row 0.10, and §17.2 gives the per-operator formulas built on them. Beyond N = 16 a greedy fallback takes over: join the cheapest pair, keep joining the cheapest next relation, then run K rounds of random re-ordering, keeping a reorder only if it is cheaper (§17.2, ADR-12).

One memo shared by two searches (§18.2, §11.9, MM1, I12)

A group is an equivalence class of logically equivalent plans, and a group expression is one operator whose children are other groups (§11.9, MM1). Structurally equal expressions are interned to the same GroupId, so a subplan priced once is not explored again (I12, §18.2, MM1). Without this, exploration re-expands the same groups exponentially (§18.2).

The Cascades search applies transformation rules (join commutativity and associativity, filter and aggregate pushes) and implementation rules (logical Join to HashJoin, MergeJoin or NestedLoopJoin) inside a group (§18.2). optimise_group(g, required_props) returns a cached winner or explores each rule once. It then keeps the cheapest winner per (group, required_props) pair. That makes it a property-parameterised generalisation of the DPccp recursion on the same memo (§18.2). Its acceptance check is that its cost equals the DPccp plan cost on every TPC-H query at SF1 (§18.4).

Properties and enforcers: required down, delivered up (§20.2, MM4, I6)

Each physical operator requires properties of its children, such as a sort order, and delivers properties upward (§18.2, MM4). TableScan delivers cluster-key order if a clustered index exists. IndexScan delivers index-key order, MergeJoin delivers the equi-key order, and HashJoin/NestedLoopJoin/HashAggregate deliver none (§20.2). When a child delivers less than its parent requires, a top-down walk inserts an enforcer, a Sort for order (§20.2, I6). An Exchange enforcer for partitioning is declared but deferred (§20.2, ADR-17). The point is the bug it prevents: a MergeJoin silently fed unsorted input (I6, MM4). Peephole rules then drop a redundant outer Sort when the inner key set covers it, and record that sorting on a also sorts on b when a = b (§20.2).

The trade-offs — where engineers disagree

Sealed enum for the plan IR (ADR-03)

Chosen: a closed enum LogicalPlan, for exhaustive pattern matching in rewrite rules (§9, P2). Rejected: a graph of trait objects (Box<dyn LogicalNode>) (§9). When the rejected choice is right: when third-party plugins must add operator kinds without recompiling the core crate (§9). The blueprint lists ADR-03 as load-bearing, so overturning it moves the planner (§9).

Heuristic passes plus a Cascades overlay (ADR-04)

Chosen: heuristic rewrite passes (§15) plus a Cascades overlay (§18), because DPccp can be tested exhaustively against System R before the larger Cascades rule surface is trusted (§9, P6). Rejected: Cascades-only from day one (§9). When the rejected choice is right: once the rule catalogue is large enough that heuristic-pass ordering itself becomes the bottleneck (§9). §33 question 15 calls ADR-06 "Cascades-only", but the §9 row for ADR-06 rejects a pure Volcano memo instead, and I do not reconcile the two (§33, §9).

DPccp for join order (ADR-05)

Chosen: DPccp (Moerkotte and Neumann 2006), since DPsub is asymptotically worse and DPhyp's extra complexity is unmeasured on TPC-H (§9). Rejected: DPsub and DPhyp (§9). When the rejected choice is right: DPhyp wins on join graphs with many non-equi or complex predicates, where DPccp's csg-cmp assumption is looser (§9).

One scalar cost (ADR-07)

Chosen: one f64 total, because vector costs multiply the memo's key space for no measured TPC-H win (§9, P4). Rejected: a Pareto-frontier vector cost (§9). When the rejected choice is right: when the host must expose several explicit trade-offs to the user, for example cost against freshness in a streaming engine (§9).

Greedy fallback beyond 16 relations (ADR-12)

Chosen: greedy plus iterative improvement beyond N = 16, because DPccp is exponential in the worst case (§9, §4). Rejected: exhaustive DPccp for every N (§9). When the rejected choice is right: whenever N ≤ dpccp_max_relations (16), where the fallback never fires (§9).

Property-driven physical optimisation (ADR-14)

Chosen: required/delivered properties with enforcers, since heuristic selection misses interesting orders and is not correct by construction (§9, P7). Rejected: heuristic operator selection (§9). When the rejected choice is right: for a fixed, tiny operator set where property bookkeeping costs more than it saves (§9). ADR-14 is also load-bearing (§9).

Roads not taken (§34, §35)

Pure top-down Cascades with no separate DPccp stage (§34 AA1) wins in large, long-lived optimiser codebases with a mature rule catalogue, as in SQL Server and Calcite. It loses here because DPccp can be verified against System R first (§34, ADR-04).

A heuristic, cost-free optimiser (AA2) wins in embedded engines such as SQLite, where statistics cost more than they return. It loses here because the 10%-of-best-known bar (M4) needs cost-based enumeration (§34).

Adaptive re-planning as the primary strategy (AA3) wins for distributed batch analytics such as Spark AQE, where shuffle costs are hard to estimate. It loses here because re-planning overhead dominates a single-node, millisecond-budget workload, so it stays a Phase 9 hook (§34, §4, ADR-16).

Genetic search for every N (AA4) wins on very large join graphs, as in PostgreSQL beyond its genetic threshold. It loses here because it gives up DPccp's provable optimality on N ≤ 16 (§34).

The deferred register (§35) holds five features, each with a trigger: adaptive re-planning waits for an executor actuals-streaming API, distributed exchange operators for a committed multi-node target, genetic enumeration beyond N = 32 for production joins that large, plan caching for a measured repeated-planning cost, and a view or index advisor for a separate deliverable (§35).

What must never be false

  • I1 plan equivalence: every rewrite output is semantically equivalent to its input. Noticed by LogicalPlan::validate after each rule in debug builds; counter rewrite.validator.violations.
  • I2 schema preservation: a rewrite's output schema equals its input's. Noticed by a schema diff on every rule application (debug); rewrite.schema_mismatch.
  • I3 cost additivity: a tree's cost is the sum of subtree costs plus the root's own. Noticed by a conformance test; no runtime telemetry, it is a build-time test.
  • I4 determinism: identical (ast, catalog, stats) gives a bit-identical PhysicalPlan. Noticed by hashing rendered EXPLAIN in conformance; planner.nondeterminism_detected.
  • I5 DP completeness: every csg-cmp pair is explored before a subgraph's best plan is read. Noticed by replaying known-optimal fixtures; enum.incomplete_subgraph.
  • I6 property satisfaction: a physical operator's required properties are met by its child. Noticed by a validator walk of required against delivered; physical.property_violation.
  • I7 and I8 selectivity in [0, 1] and relative error in [0, 10]. Noticed by debug assertions at construction; stats.selectivity_out_of_range, stats.error_out_of_range.
  • I9 no Cartesian product unless the query has no join predicate at all. Noticed by a negative conformance fixture; enum.cartesian_admitted.
  • I10 one Catalog snapshot per plan() call. Noticed by a fixture with a mutating fake catalog; bind.catalog_snapshot_miss.
  • I11 statistics are flagged stale past 24 h or 20% row-count drift. Noticed by a check on every Statistics::table call; stats.staleness_flag.
  • I12 structurally equal group expressions share one GroupId. Noticed by stable group counts across repeated planning; cascades.dedup_miss_rate.
  • I13 applying a rule twice equals applying it once. Noticed by a property test of apply(apply(p)) == apply(p); rewrite.confluence_violation.
  • I14 every plan() call completes or returns PlannerError::Timeout within plan_timeout_ms. Noticed by a timer-based fixture with an adversarial join graph; planner.timeout_triggered.

What breaks in production

The §23 table's header names seven columns but each row has eight cells. I read the cells as ID, name, symptom, root cause, detection, automatic recovery, manual action and evidence (§23).

FM-1: rewrite non-convergence. The fixed-point loop hits max_iterations because two rules fight (a non-confluent pair, I13). Detection is iteration-count telemetry (§15.10). The system fails closed with RewriteDidNotConverge. The operator quarantines the offending rule, using the rule application trace log (§23, T7).

FM-2: DPccp explosion or timeout. The join graph is too large or dense for exact search, with more than dpccp_max_relations relations or adversarial density. The wall-clock budget check in the enumerator catches it, and the planner degrades to the greedy fallback. Raising the cap is a deliberate act that needs a re-benchmark (§23, §17.2, I14).

FM-3: cardinality estimate blow-up. Statistics are stale or absent, with last_analyzed beyond budget (I11), and the staleness check catches it (§16.2). The system flags it in EXPLAIN, and the operator triggers ANALYZE, with the stats.staleness_flag history as evidence (§23). MM7 makes the same point: staleness looks like a cost-model bug (MM7).

FM-4: decorrelation produces a wrong result. A LIMIT-bearing subquery was lifted by a bug in decorrelate_apply. A negative conformance fixture is meant to catch it. There is no recovery, since it is a correctness bug that "must not ship": revert the rule change and add a regression fixture (§23, §15.2).

FM-5: property-model drift. The cost Cascades chose differs from the final physical cost because the §18 and §20 property models diverge. A per-PlanId cost-comparison assertion detects it. Nothing recovers automatically and the release is blocked (§23, §20.9, §27).

FM-6: memo cycle or unbounded exploration. plan() hangs past budget because of mutual recursion between groups. Cycle detection in the search is the first line of defence. The wall-clock timeout (P13) then forces a return, and the fix is to repair cycle detection and add a fixture (§23, §18.2).

FM-7: nested-loop join chosen without an index. The cost model underestimates the nested-loop cost or lacks a safety factor. The nested_loop_safety_factor check demands a clear cost advantage first. Operators tune that factor or add the missing index, watching physical.nested_loop_without_index (§23, §19.6).

Threats worth knowing (§22):

  • T1, plan-space explosion from a 30-relation join with no equi-predicates, is met by the 16-relation cap and the greedy fallback. Detection is a wall-clock check after each subgraph size (§17.2), and recovery is to degrade to greedy or best-so-far (I14, enum.timeout_triggered).
  • T3, memory exhaustion from WHERE col IN (...) with 100,000 literals, is capped by max_in_list (default 8,192). Above the cap the list becomes a hash-set scan, never an out-of-memory crash (bind.in_list_capped).
  • T7, denial of service by rewrite non-convergence, is met by the max_iterations cap and confluence testing. The system fails closed with RewriteDidNotConverge, never loops (I13, FM-1).
  • T12, a timing or row-count side channel from EXPLAIN ANALYZE on a protected table, is declared out of scope for qp. The host must gate EXPLAIN ANALYZE behind the same row-level security as execution (§1).

Two recoveries lean on features that are not built. T8 (crafted statistics skewing the cost model) and FM-3 both name the adaptive re-plan hook as a corrective, marked Phase-1+, while §21.2 and §35 say the replanner body is deferred, so neither recovery exists in Phases 0 to 9 (T8, FM-3, §21.2, §35).

How it compares

  • PostgreSQL chose heuristic, hand-tuned path costing over a property-driven search. That is fine in a mature single-team codebase where the property bookkeeping's payoff never appeared at its historical operator-set size (§31).
  • System R chose dynamic programming over interesting orders, which every descendant still uses, with fixed formulas and no statistics. It works as the reference correctness bar because a good enumerator on a fixed cost formula already beats guessing (§31).
  • Apache Calcite chose to be a pluggable library that owns no storage or execution. That is right whenever many engines (Flink, Hive, Drill) must share one rule catalogue and cannot agree on a physical operator set (§31).
  • SQL Server (Cascades) chose always-on adaptive re-optimisation instead of a stretch hook. That pays off in a workload mix, ad-hoc BI plus OLTP, where static cost-based planning under-performs by a measured margin (§31).
  • DuckDB chose a lightweight, sampling-heavy statistics layer. That is right in an embedded, single-process analytical setting where planning simplicity and startup speed beat marginal accuracy on adversarial skew (§31).

Questions to test yourself

  1. Why does DPccp key its memo by (RelationSet, InterestingOrder) instead of RelationSet alone, and what plan does the simpler keying provably miss? — Hint: §17.2 and P11 (§33 labels it "§7 P11", but the principles are in §6).
  2. Under what statistics condition does a 10%-cheaper plan lose to a 10%-more-expensive one, and which field on Cardinality encodes that decision? — Hint: §11.5, P5 and MM2.
  3. Why does the Cascades memo (§18) share state with the DPccp enumerator (§17) instead of running as an independent second search? What would break if they used separate memos? — Hint: §18.2, I12 and MM1.
  4. Name the one TPC-H subquery shape that cannot be decorrelated at all, why not, and what the rewriter does instead. — Hint: §15.2 and the "What Mastery Looks Like" list in §2.
  5. Why does the planner take a Catalog snapshot per plan() call instead of querying live on every lookup, and name the specific invariant and failure mode this prevents. — Hint: I10, T5 and §13.2.

If you only remember three things

A plan is chosen by estimates that carry an error bar, so every statistic, rewrite and search step is bounded and checked rather than trusted (MM2, I8, P10). Join order is a search over connected subgraphs, kept tractable by one shared memo that never explores the same subplan twice (MM3, MM1, I12). Required properties flow down and delivered properties flow up, so an enforcer is inserted exactly where a child falls short (MM4, I6).

Words used here

  • Cardinality: the estimated row count of a plan node plus its error bar (§36, I8).
  • Selectivity: the fraction of rows a predicate is estimated to pass, between 0 and 1 (§36, I7).
  • Logical plan: the tree of algebra operators, before choosing physical algorithms (§36, P2).
  • Join graph: relations as nodes, join predicates as edges; the input to DPccp (§36, §17.2).
