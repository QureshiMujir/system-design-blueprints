Decisions (§9) · 26 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+, stable only

Rejected

C++; Java/Scala; Go

When the rejected choice is right

Java/Scala win when the host is already a JVM database (e.g. embedding inside an existing Java engine where FFI overhead exceeds GC pause cost)

Why: sealed enums + no-GC latency budget (§1, §4)

ADR-02

Workspace shape

Chosen

many small crates (§10)

Rejected

one monolithic crate

When the rejected choice is right

a monolith wins for a single-author prototype where cross-crate API discipline has no payoff yet

Why: faster incremental builds; clean per-phase public API

ADR-03

Logical IR representation

Chosen

sealed enum LogicalPlan

Rejected

trait-object graph (Box<dyn LogicalNode>)

When the rejected choice is right

trait objects win when third-party plugins must add operator kinds without recompiling the core crate

Why: exhaustive pattern matching for rewrite rules (P2)

ADR-04

Rewrite engine architecture

Chosen

heuristic bottom-up/top-down passes (§15) + Cascades overlay (§18) for transformations

Rejected

Cascades-only from day one

When the rejected choice is right

Cascades-only wins once the rule catalogue is large enough that heuristic-pass ordering itself becomes the bottleneck

Why: DPccp is exhaustively testable against System R before trusting the larger Cascades rule surface (P6)

ADR-05

Join enumeration algorithm

Chosen

DPccp (Moerkotte & Neumann 2006)

Rejected

DPsub; DPhyp

When the rejected choice is right

DPhyp wins on join graphs with many non-equi/complex predicates where DPccp's csg-cmp assumption is looser

Why: DPsub is asymptotically worse; DPhyp's added complexity is unmeasured on TPC-H

ADR-06

Transformation-rule memo

Chosen

Cascades-style memo (§18.2)

Rejected

pure Volcano memo (no separate transform/implement split)

When the rejected choice is right

pure Volcano wins for a planner with no physical-property reasoning at all (e.g. single storage format, no sort-order concept)

Why: Cascades property/enforcer discipline is what §20 needs

ADR-07

Cost representation

Chosen

scalar f64 (§11.4)

Rejected

Pareto-frontier vector cost

When the rejected choice is right

vector cost wins when the host must expose multiple explicit tradeoffs to the user (e.g. cost vs. freshness in a streaming engine)

Why: vector costs multiply the memo's key space for no measured TPC-H win (P4)

ADR-08

Histogram families

Chosen

equi-depth (default) + max-diff

Rejected

equi-width only

When the rejected choice is right

equi-width wins when build cost must be O(1) per bucket and data is known uniform (e.g. a synthetic key column)

Why: equi-width is too noisy on skewed data (Poosala 1996)

ADR-09

Most-common-values (MCV) list

Chosen

per-column top-K, K configurable

Rejected

no MCV, histogram only

When the rejected choice is right

no-MCV wins on columns with no skew at all, where the extra storage buys nothing

Why: MCV dominates accuracy on selective equality predicates (§16.2)

ADR-10

Distinct-count estimation

Chosen

HyperLogLog++ (2^14 registers)

Rejected

linear counting; exact counting

When the rejected choice is right

exact counting wins below the configurable exact-count threshold (default 1,000 rows, §16.2)

Why: linear counting is memory-hungry at scale; exact is infeasible for wide columns

ADR-11

Multi-column correlation

Chosen

sample-based MCV pairs + functional dependencies

Rejected

full multi-dimensional histograms

When the rejected choice is right

full multi-dim histograms win on a fixed, small, heavily-queried composite key where build cost is amortised once

Why: full multi-dim histograms blow up combinatorially; sample-based pairs are the proven PostgreSQL approach

ADR-12

Large-join-graph fallback

Chosen

greedy + iterative improvement (Steinbrunn 1997) beyond N=16

Rejected

exhaustive DPccp for all N

When the rejected choice is right

exhaustive DPccp wins whenever N ≤ dpccp_max_relations (16) — the fallback never fires there

Why: DPccp is exponential in the worst case; the greedy fallback is the standard escape hatch

ADR-13

Physical join operator set

Chosen

HashJoin, MergeJoin, NestedLoopJoin

Rejected

index-nested-loop-only (no hash/merge)

When the rejected choice is right

NLJ-only wins in a pure index-organised engine with no hash-table memory budget at all

Why: hash/merge cover unindexed equi-joins that a NLJ-only engine cannot

ADR-14

Physical optimiser strategy

Chosen

property-driven enforcer model (Cascades discipline, §20)

Rejected

heuristic operator selection

When the rejected choice is right

heuristic selection wins for a fixed, tiny operator set where property bookkeeping costs more than it saves

Why: heuristic selection misses interesting orders and is not correct-by-construction (P7)

ADR-15

EXPLAIN output formats

Chosen

text + JSON

Rejected

text-only

When the rejected choice is right

text-only wins in a resource-constrained embedded target with no tooling consumer

Why: JSON is required for tooling; text for humans; conformance pins both (§21)

ADR-16

Adaptive re-planning scope

Chosen

Phase 9 stretch hook only (§21), not Phase 0

Rejected

When the rejected choice is right

full AQE from day one wins when the host executor already ships a mature actuals-streaming API (e.g. adopting an existing Spark-style engine)

ADR-17

Distributed shipping (Exchange operators)

When the rejected choice is right

Phase-0 distributed support wins when the target deployment is inherently multi-node from day one (e.g. a sharded OLAP engine with no single-node mode)

Tracing

Licensing

Rejected

GPL/AGPL; proprietary

When the rejected choice is right

ADR-21

Plan/catalog interchange serialization

Chosen

serde_json for EXPLAIN JSON and fixtures

Rejected

When the rejected choice is right

ADR-22

Concurrency model

Chosen

synchronous, stateless-per-call plan() (§4)

Rejected

When the rejected choice is right

async wins if a future phase adds a real network call inside planning (e.g. a remote statistics service)

Why: no qp stage performs I/O; async adds a runtime dependency for zero benefit

ADR-23

Fuzzing target

Chosen

cargo-fuzz over the bind + rewrite boundary (fuzz/fuzz_targets/)

Rejected

no fuzzing, conformance corpus only

When the rejected choice is right

corpus-only wins for a component with no untrusted-input boundary at all

Why: the bind/rewrite boundary consumes attacker-influenced ASTs (§22 T10)

ADR-24

CI/CD topology

Chosen

GitHub Actions matrix: ci.yml, conformance.yml, tpch.yml nightly, fuzz.yml, security.yml, release.yml

Rejected

one monolithic pipeline

When the rejected choice is right

one monolithic pipeline wins for a repo small enough that split-workflow overhead exceeds its isolation benefit

Reproducible builds

Chosen

Cargo.lock pinned, checked in; cargo vendor for release artifacts

Rejected

floating dependency versions

When the rejected choice is right

floating versions win during early Phase-0 prototyping where reproducibility is not yet a requirement

Why: a planner used inside a database must reproduce the exact plan across releases (I4)

Cross-language embedding

Chosen

cdylib + rlib dual crate-type (qp-ffi)

Rejected

When the rejected choice is right

rlib-only wins when every consumer is guaranteed to be Rust (no FFI surface to maintain)

34. Alternative Architectures (Roads Not Taken)

AA1 — Top-down-only (pure Cascades/Volcano, no separate DPccp stage).

AST -> Bind -> LogicalPlan -> [ single top-down Cascades/Volcano search:
                                explore + implement + cost, one memo,
                                no separate bottom-up join stage ] -> PhysicalPlan

Regime: large, long-lived optimiser codebases with dozens of engineers and years to mature a rule catalogue (SQL Server's Cascades, Calcite's VolcanoPlanner). Rejected here because a from-scratch DPccp is exhaustively testable against the System R reference (§9 ADR-04) before the larger, harder-to-verify Cascades rule surface is trusted — the right call for a Phase-0-to-Phase-9 build timeline, wrong for a mature codebase that already trusts its rule catalogue.

AA2 — Heuristic/rule-only optimiser (no cost model at all).

AST -> Bind -> LogicalPlan -> [ fixed heuristic rewrite + greedy right-deep
                                join order, no cost model, no statistics ] -> PhysicalPlan

Regime: embedded, resource-constrained engines where statistics infrastructure costs more than it returns (SQLite's where.c, §5 ref-impl 4). Rejected here because the stated conformance bar (within 10% of best-known plan on every TPC-H query, M4) is unreachable without cost-based enumeration on non-trivial join graphs — the right call for SQLite's embedded-device niche, wrong for a system whose explicit purpose is teaching statistics-driven optimisation (§2).

AA3 — Adaptive/runtime re-planning as the primary strategy.

AST -> Bind -> LogicalPlan -> [ minimal static plan, stage-by-stage execution,
                                re-optimise after every stage using actuals ] -> PhysicalPlan (evolves at runtime)

Regime: distributed batch analytics with expensive, hard-to-estimate shuffle costs (Spark AQE, §5 ref-impl 5). Rejected as the primary strategy here because re-planning overhead dominates on the single-node, millisecond-budget workload this planner targets (§4) — it is exactly right for Spark's minutes-long batch jobs where a wrong initial estimate costs far more than one re-plan, and is why qp keeps it as the Phase-9 stretch hook (§21.2) rather than the load-bearing mechanism.

AA4 — Genetic/randomized search as the primary enumerator for all N.

AST -> Bind -> LogicalPlan -> [ genetic algorithm over join-tree population:
                                crossover + mutation + fitness = cost,
                                for every N, not just N > 16 ] -> PhysicalPlan

Regime: very large join graphs (N ≫ 32) where even DPccp's practical-case sparsity no longer saves enough search time (PostgreSQL beyond geqo_threshold, §5 ref-impl 1; Steinbrunn 1997, §5). Rejected as the primary enumerator here because it sacrifices DPccp's provable optimality on the N ≤ 16 exact-search range for no measured benefit at the join sizes TPC-H exercises — qp keeps genetic enumeration as a deferred N > 32 extension (PhaseDeferred("§17")), not the default path.
