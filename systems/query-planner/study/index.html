Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does DPccp key its memo by (RelationSet, InterestingOrder) instead of RelationSet alone, and what plan does the simpler keying provably miss? (§17.2, §7 P11)
  2. Under what statistics condition does a 10%-cheaper plan lose to a 10%-more-expensive one, and which field on Cardinality encodes that decision? (§11.5, §6 P5)
  3. Why is Apply a distinct LogicalPlan variant from Join instead of being unified, and which phase is the only one allowed to convert one into the other? (§11.8, §15.2)
  4. Trace one TPC-H query's o_orderdate >= '2025-01-01' predicate from bind through to the final physical plan — name every phase that touches it and what each does. (§13.2, §14.2, §15.2, §16.2)
  5. Why does the Cascades memo (§18) share state with the DPccp enumerator (§17) instead of running as an independent second search? What would break if they used separate memos? (§18.2, I12)
  6. Derive the worst-case DPccp memo size at N=16 and explain why the practical TPC-H number is four to five orders of magnitude smaller. (§32 items 2–3, §17.6)
  7. Why is Cartesian-product admission gated on "the query has no join predicate at all" rather than "the optimiser thinks it's cheap"? What invariant would a cost-based admission policy violate? (I9, §17.6)
  8. A MergeJoin is chosen for a join whose children already deliver the required sort order from an upstream IndexScan. Which two phases must agree for no redundant Sort enforcer to appear, and what specific model would you check first if one did appear anyway? (§19.6, §20.6, §20.9)
  9. Why does qp treat EXPLAIN's cost numbers as unitless rather than seconds, and what historical precedent motivates keeping that distinction explicit? (§21.6, §5 ref-impl 1)
  10. Name the one TPC-H subquery shape that cannot be decorrelated at all, why not, and what the rewriter does instead. (§15.2, §2 What Mastery Looks Like)
  11. Why is the cost model versioned together with the statistics layer (P14) rather than independently, and what production failure mode does decoupling them produce? (§6 P14, §17.6)
  12. Explain why RelationId is u8 even though the catalog could in principle have millions of tables, and what actually caps the DPccp fast path at 64 relations. (§11.1, §32 item 9)
  13. Under what condition does the greedy fallback (§17.2) produce a plan worse than 20% off DPccp-optimal, and how would you detect that regression before it reaches production? (§17.4, §28 M1)
  14. Why does the planner take a Catalog snapshot per plan() call instead of querying live on every lookup, and name the specific invariant and failure mode this prevents. (I10, §23 FM10)
  15. Compare the "when the rejected choice wins" column for ADR-04 (heuristic+Cascades-overlay) and ADR-06 (Cascades-only) — under what single condition would both flip together? (§9 ADR-04, ADR-06)
  16. Why does the adaptive re-plan hook (§21.2) explicitly forbid re-planning the already-executed prefix, and what invariant from an entirely different phase does this echo? (§21.2, I1)
  17. If the Cascades search (§18) and the physical optimisation pass (§20) disagreed about whether HashJoin preserves an ordering, what production symptom would you see first, and which telemetry counter would you check? (§20.6, §20.9, MM4)
  18. Explain why the Comparative Architecture Table (§31) lists SQL Server's Adaptive Query Processing as "in-box" and qp's equivalent as a stretch hook — what does that difference cost qp on the workload mix SQL Server targets, and why was that cost accepted? (§31, ADR-16)

30. Mental Models & First Principles

  • MM1 — A logical plan is an equivalence class, not a single tree. Predicts why join enumeration needn't recompute a subtree it has already priced; the bug class without it is exponential re-exploration of the same subplan (I12). Applied in §18.2.
  • MM2 — Cost is a bet under uncertainty, not a fact. Every Cardinality carries an error bar (I8); predicts that a lower-cost-but-higher-variance plan can lose to a higher-cost, lower-error one. The bug class without it is overconfident plan selection that regresses under real-world skew. Applied in §16.2, P5.
  • MM3 — A join graph's connectivity, not its size, bounds the search. Predicts DPccp's plan-space via connected subgraphs, not N! permutations; the bug class without it is a naïve enumerator that treats every join graph as if it were fully connected. Applied in §17.2, §32.
  • MM4 — Properties flow two ways: required down, delivered up. Predicts exactly where an enforcer must be inserted; the bug class without it is a MergeJoin silently fed unsorted input. Applied in §18.2, §20.2.
  • MM5 — Predicate pushdown across outer joins is a null-rejection question, not a syntax question. Predicts which predicates are unsafe to push; the bug class without it is a silently wrong outer-join result. Applied in §15.2, §15.6.
  • MM6 — A histogram is a lossy compression of a CDF. Predicts interpolation error inside a bucket; the bug class without it is confident misestimation on skewed data inside a single wide bucket. Applied in §16.2.
  • MM7 — Statistics decay; plans do not know it unless told. Predicts stale-statistics regressions that look like cost-model bugs but are staleness bugs; the bug class without it is silent drift between estimate and reality. Applied in I11, §16.9, §23 FM3.
  • MM8 — The optimizer's real adversary is correlation, not volume. The independence assumption breaks under correlated columns before it breaks under scale; the bug class without it is cross-column misestimation that no amount of per-column histogram precision fixes. Applied in §16.2 (multi-column stats), §5 (Leis 2015).

Required reading (§5)

Books

  • Garcia-Molina, H., Ullman, J., Widom, J. — Database Systems: The Complete Book, 2nd ed., 2008. Ch. 7 (Relational Algebra) and Ch. 16 (The Query Compiler: parsing, algebraic laws, view expansion). Applied in §14 (canonical algebra) and §15 (rewrite laws).
  • Silberschatz, A., Korth, H., Sudarshan, S. — Database System Concepts, 7th ed., 2019. Ch. 15 (Query Processing) and Ch. 16 (Query Optimization). Applied in §16 (cost/cardinality) and §17 (join-order search).
  • Ramakrishnan, R., Gehrke, J. — Database Management Systems, 3rd ed., 2003. Ch. 12 (Evaluation of Relational Operators) and Ch. 15 ("A Typical Relational Query Optimizer"). Applied in §19 (physical operator catalogue) and §20 (property-driven optimisation).
  • Elmasri, R., Navathe, S. — Fundamentals of Database Systems, 7th ed., 2015. The chapters on algorithms for query processing and optimisation (heuristic + cost-based). Applied in §15 (heuristic rewrite pre-pass) and §17 (cost-based enumeration).
  • Petrov, A. — Database Internals, 1st ed., 2019, O'Reilly. Part I (storage-engine vocabulary: pages, B-Trees, LSM). Applied in §13.1's per-page IO cost terms (io_per_seq_page, io_per_random_page).
  • Hellerstein, J., Stonebraker, M. (eds.) — Readings in Database Systems, 4th ed., 2005 ("the Red Book"). The Query Optimization part, reprinting Selinger 1979 and Graefe & McKenna 1993 with editorial commentary. Applied in §17 and §18's design rationale.

Papers

  • Selinger, P. G. et al., 1979, "Access Path Selection in a Relational Database Management System," SIGMOD. The System R bottom-up DP join enumerator with interesting orders. Applied in §17 (DPccp is its modern successor) and §17.2 interesting-orders.
  • Graefe, G., McKenna, W., 1993, "The Volcano Optimizer Generator: Extensibility and Efficient Search," ICDE. Top-down search over a memo. Applied in §18 (memo/group model).
  • Graefe, G., 1995, "The Cascades Framework for Query Optimization," IEEE Data Engineering Bulletin. Transformation rules, implementation rules, properties, enforcers. Applied throughout §18 and §20.
  • Moerkotte, G., Neumann, T., 2006, "Analysis of Two Existing and One New Dynamic Programming Algorithm for the Generation of Optimal Bushy Join Trees," VLDB. DPccp: connected-subgraph / complement-pair enumeration. Applied in §17.2 and the §32 plan-space bound.
  • Leis, V. et al., 2015, "How Good Are Query Optimizers, Really?," PVLDB. The Join Order Benchmark; shows cardinality estimation dominates plan-quality regressions. Applied in §16 (statistics-first design rationale) and MM8.
  • Leis, V. et al., 2018, "Query Optimization Through the Looking Glass, and What We Found Running the Join Order Benchmark," VLDB Journal. Follow-up measurements. Applied in §16.4 conformance target derivation.
  • Ioannidis, Y., 2003, "The History of Histograms (abridged)," VLDB. Survey of histogram families. Applied in §16.2 (equi-depth/max-diff choice, ADR-08).
  • Poosala, V., Ioannidis, Y., Haas, P., Shekita, E., 1996, "Improved Histograms for Selectivity Estimation of Range Predicates," SIGMOD. Max-diff histogram construction. Applied in §16.2.
  • Flajolet, P., Fusy, É., Gandouet, O., Meunier, F., 2007, "HyperLogLog: the analysis of a near-optimal cardinality estimation algorithm," AOFA. Applied in §16.2 and the §32 sketch-size derivation.
  • Steinbrunn, M., Moerkotte, G., Kemper, A., 1997, "Heuristic and Randomized Optimization for the Join Ordering Problem," VLDB Journal. Greedy + iterative-improvement fallback. Applied in §17.2 (ADR-12) and §34 AA4.
  • Galindo-Legaria, C., Joshi, M., 1999/2001, "Orthogonal Optimization of Subqueries and Aggregation," SIGMOD 2001. Subquery decorrelation taxonomy. Applied in §15.2.
  • Stillger, M., Lohman, G., Markl, V., Kandil, M., 2001, "LEO — DB2's LEarning Optimizer," VLDB. First execution→planner feedback loop. Applied in §21.2's adaptive-hook design.

Reference Implementations

  • PostgreSQL, src/backend/optimizer/ (path generation), src/backend/utils/adt/selfuncs.c (selectivity), src/backend/optimizer/path/costsize.c (cost model). Lesson: the ground truth for battle-tested selectivity heuristics (§16.2). Pitfall not to copy: its planner globals are not thread-safe — qp keeps all state in Planner/RewriteCtx (P2).
  • Apache Calcite, RelNode algebra, RelOptRule rewrite engine, VolcanoPlanner. Lesson: the cleanest open-source Cascades-family implementation (§18). Pitfall not to copy: Calcite's rule-matching is reflection-heavy; qp's Rule trait dispatch is static (§11.7).
  • DuckDB, src/optimizer/, src/planner/. Lesson: a contemporary, compact Cascades-adjacent optimiser in C++ (§18, §31). Pitfall not to copy: DuckDB's rule ordering is partly hand-tuned/undocumented; qp pins its order in a table (§15.2).
  • SQLite, src/where.c (the WHERE-clause optimizer). Lesson: a greedy, right-deep, heuristic-only optimiser that still ships in billions of devices (§34 AA2) — proof that Cascades-class machinery is not always the right regime. Pitfall not to copy: no cost-model-driven index selection; over-relies on manually-created indexes.
  • Apache Spark, org.apache.spark.sql.catalyst.optimizer.Optimizer. Lesson: the cleanest rule-driven (non-cost-based) logical rewriter; its rule catalogue is a checklist (§15.2). Pitfall not to copy: Catalyst's physical planning is largely heuristic, not property-driven Cascades (§20 rejects this for qp).

Glossary (§36) · 44 terms · site-wide glossary

Apply operator
The LogicalPlan node for an un-decorrelated correlated subquery; a per-outer-row nested evaluation the decorrelator tries to lift to a flat Join (§11.8, §15.2).
Bushy plan
A join tree where an internal node's two children are themselves both joins of ≥ 2 relations, as opposed to a left-deep chain; DPccp produces these by construction (§17.6).
Cardinality
The estimated row count of a plan node plus its relative_error (§11.5, I8).
Cascades memo
The group/group-expression search structure that generalises DPccp with property-parameterised winners (§11.9, §18.2).
Catalog
The host-owned metadata provider (Catalog trait) for table/index/statistics lookup; snapshotted once per plan() call (§11.2, I10).
Coercion lattice
The partial order of allowed implicit type conversions the binder consults when type-checking a BinaryOp/Cast (§13.2).
Connected subgraph
A subset of join-graph relations whose induced edge set is connected; the unit DPccp enumerates over (§17.2).
Correlated subquery
A subquery whose predicate references a column from an outer scope; tracked at bind time (§13.2) for the decorrelator (§15.2).
Cost model
The subsystem mapping an operator + child costs to a scalar Cost (§11.4, P4).
Csg-cmp pair
A pair of connected subgraphs (S1, S2) whose union is a larger connected subgraph S with a connecting edge — DPccp's core enumeration unit (§17.2, Moerkotte & Neumann 2006).
Decorrelation
Rewriting a correlated subquery (Apply) into an equivalent flat Join (§15.2, Galindo-Legaria & Joshi 2001).
Delivered properties
The physical properties (sort order, partitioning) an operator actually produces, as opposed to what its parent requires (§20.2).
DPccp
The bottom-up dynamic-programming join enumerator over connected subgraphs and complement pairs (§17.2, Moerkotte & Neumann 2006).
Enforcer
A physical operator (Sort, Exchange) inserted solely to satisfy a required property a child does not deliver (§20.2).
Equi-join
A join whose predicate is a conjunction of column-equality pairs, represented as JoinPredicate::Equi (§11.8).
EXPLAIN / EXPLAIN ANALYZE
The planner's rendering surface; ANALYZE decorates estimated values with executor-reported actuals (§21).
Functional dependency
A column relationship (col1 → col2) the multi-column statistics layer uses to correct the independence assumption (§16.2, ADR-11).
Greedy fallback
The non-exhaustive join-order heuristic (pick-cheapest-next + iterative-improvement) used beyond dpccp_max_relations (§17.2, ADR-12, Steinbrunn 1997).
Group / Group Expression
A Cascades equivalence class of logically-equivalent plans, and one concrete operator + children within it (§11.9).
HyperLogLog (HLL)
A probabilistic distinct-count sketch with fixed memory and bounded standard error (§16.2, ADR-10, Flajolet 2007).
Implementation rule
A Cascades rule rewriting a logical group expression into a physical one in the same group (§18.2).
Independence assumption
The default (often wrong) assumption that two predicates' selectivities multiply; corrected by multi-column statistics where it fails (§16.2, MM8).
Interesting order
A sort order a downstream operator can exploit; the DPccp memo key includes it because it can make a locally-worse plan globally cheaper (§17.2, P11, Selinger 1979).
JCC-H / Join Order Benchmark (JOB)
The cardinality-accuracy conformance corpus (§5, §16.5).
Join graph
The graph whose nodes are base relations and whose edges are join predicates, the input to DPccp (§17.2).
Logical plan
The algebra-IR tree (LogicalPlan) every rewrite/cost/enumeration phase codes against, before physical lowering (§11.8, P2).
Materialise
A physical operator buffering a subtree's output for re-scan by a consumer that needs it more than once (§19.2).
Max-diff histogram
A histogram whose bucket boundaries fall at points of maximum frequency change, best for skewed data (§16.2, ADR-08, Poosala 1996).
MCV (Most Common Values) list
A per-column list of exact top-K value/frequency pairs (§11.6, ADR-09).
Memo
The shared search/dedup structure underlying both DPccp and Cascades (§11.9, I12).
Negative-going-neighbour bitmask
The bit-trick that makes DPccp's connected-subgraph enumeration efficient over a packed RelationSet (§17.2, Moerkotte & Neumann 2006).
NestedLoopJoin safety factor
The configurable margin (PlannerConfig:: nested_loop_safety_factor) requiring a clear cost advantage before choosing an un-indexed nested loop (§19.6).
Physical plan
The executable operator tree (PhysicalPlan) emitted after lowering and property enforcement (§11.10, §19, §20).
Plan equivalence / semantic preservation
The invariant that every rewrite's output answers the same query as its input for any catalog state (I1).
Property (required / delivered)
The sort/partition/distinct contract a physical operator demands of, or provides to, its neighbours in the plan tree (§18.2, §20.2, MM4).
Rejected alternative (ADR)
The tech-stack option a decision did not take, paired with the concrete regime where it would have won (§9).
Relative error
The one-sigma uncertainty bound attached to a Cardinality estimate (§11.5, I8, P5).
Reservoir sampling
A streaming sampling technique avoiding positional bias when building a histogram from a large table (§16.2, §16.6).
Rewrite rule
A pure function LogicalPlan → Option<LogicalPlan> applied by the fixed-point rewrite loop (§11.7, §15.2, P3).
Selectivity
The fraction (∈ [0,1]) of rows a predicate is estimated to pass (§11.5, I7).
Statistics staleness
The condition where last_analyzed age or row-count drift exceeds budget, flagged rather than silently trusted (§16.2, I11, MM7).
Transformation rule
A Cascades rule rewriting one logical group expression into another, logically-equivalent one in the same group (§18.2).
TPC-H
The 22-query decision-support benchmark used as the conformance corpus (§5, §19.5).
Winner (Cascades)
The lowest-cost group expression recorded per (group, required_props) key (§11.9).
