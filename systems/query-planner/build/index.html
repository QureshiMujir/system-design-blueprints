⬜ Phase 0 — Repository Skeleton, Governance & Correctness Kernel (Week 1) §12

Objectives

Stand up the repo layout (§10) as one commit; land governance docs, CI skeleton, licensing (ADR-20); establish the "Hello, plan" correctness kernel — a hand-built synthetic AST plans end-to-end before any real parser integration exists.

Deliverable

make bootstrap && make build && make test all exit 0 on a clean checkout; qp explain prints a golden EXPLAIN for the synthetic SELECT 1 plan.

Acceptance
  • make test passes with exactly one test, hello_plan_smoke_test, asserting the rendered EXPLAIN text equals conformance/corpora/explain/hello_plan.golden.txt byte-for-byte.
  • All 6 GitHub Actions workflows are green on the initial commit.
  • ADR-01, ADR-02, ADR-20, ADR-24, ADR-25 recorded under docs/adr/.
Fixtures
  • conformance/corpora/explain/hello_plan.golden.txt — golden EXPLAIN text for SELECT 1.
  • conformance/corpora/determinism/hello_plan.hash.txt — pinned hash, re-checked every CI run (I4).
Pitfalls
  • The upstream parser may not be ready when Phase 0 ships; the synthetic AST plus the documented contract (§12.2) let work proceed — only qp-bind/src/upstream.rs's From impl changes later.
  • A 13-crate workspace compiles slowly on first build; set [profile.dev] incremental = true and record the baseline build time in BUILD_PLAN.md.
  • Choosing Apache-2.0 without a reserved dual-license placeholder invites a painful relicensing fight later — ADR-20 reserves the decision explicitly even though no second license ships yet.

⬜ Phase 1 — Bind / Analyse (Weeks 1–2) §13

Objectives

Resolve every identifier against Catalog (§11.2); type-check every expression; desugar CTEs and SELECT *; bind subqueries with correlation tracking, producing BoundStatement (§11.8-adjacent).

Deliverable

The binder accepts every AST shape the upstream parser (ranking line 21) produces and emits a BoundStatement for each; qp explain --stage=bind dumps the JSON.

Acceptance
  • The 200+ fixture bind corpus (§13.5) passes with 0 unexpected diagnostics.
  • Every negative fixture (ambiguous name, type mismatch, unknown function) raises the documented stable error code (I10-adjacent contract, §22).
  • p50 bind latency ≤ 2 ms on the TPC-H Q1 AST (component of M2's 10 ms end-to-end budget).
Fixtures
  • conformance/corpora/bind/*.json — 200+ AST-in/BoundStatement-out pairs covering every §8.1 clause shape.
  • conformance/corpora/bind/negative/ambiguous_column.json — the §8.5 malformed-input example.
  • conformance/corpora/bind/negative/type_mismatch.json — a disallowed coercion.
Pitfalls
  • SQL identifiers are case-insensitive but quote-sensitive — Scope lookup must lowercase unquoted identifiers and preserve quoted ones verbatim, or silently binds the wrong column.
  • SELECT t.a, t.a + 1 FROM t WHERE t.a > 0 references t.a three times; the binder must produce three ColumnRefs pointing at the same ColumnId, not three independently-diverging expressions.
  • A correlated subquery without a tight predicate becomes an unbounded per-tuple nested loop at execution if left un-decorrelated — bind the correlation explicitly so §15.2 can lift it.
  • Recursive-CTE scoping (a CTE is in scope inside its own definition) is easy to get wrong in the Scope stack — test it explicitly (§13.5).

⬜ Phase 2 — Logical Algebra IR (Weeks 2–3) §14

Objectives

Lower BoundStatement to LogicalPlan (§11.8); establish the canonical form every later rewrite rule assumes; enforce plan-shape invariants at construction.

Deliverable

Every fixture in the §13.5 bind corpus lowers to a canonical LogicalPlan; qp explain --stage=lower dumps the pre-rewrite tree.

Acceptance
  • The canonicaliser is idempotent on all 200+ corpus fixtures (M9-adjacent conformance gate, §26).
  • LogicalPlan::validate catches every fixture in the negative-shape corpus (§14.5) with the specific invariant violated named (I2).
  • Comma-joins (FROM a, b) and explicit CROSS JOIN/JOIN ... ON true lower to byte-identical canonical trees.
Fixtures
  • conformance/corpora/lower/*.json — BoundStatement → canonical LogicalPlan pairs.
  • conformance/corpora/lower/negative/nested_aggregate.json — malformed nested Aggregate without an intervening CTE boundary.
  • conformance/corpora/lower/negative/bad_sort_ref.json — a Sort key referencing a column the input does not produce.
Pitfalls
  • Nested Aggregate is invalid SQL-92 but reachable via CTEs in some dialects — lower to two Aggregate nodes separated by the CTE boundary, never collapse them.
  • FROM a, b and FROM a JOIN b ON true must produce the same tree — a divergence silently changes downstream cost estimates for logically-identical queries.
  • LATERAL lowered as Join instead of Apply is a correctness bug the DPccp enumerator cannot detect — it will silently reorder something it must not.

⬜ Phase 3 — Logical Rewriter (Weeks 3–4) §15

Objectives

Run a fixed-point loop over a pinned-order catalogue of pure rules (P3, I13) that pushes predicates/projections toward scans, folds constants, decorrelates subqueries, inlines views, and closes equivalence classes — producing the LogicalPlan the cost model (§16) will annotate.

Deliverable

Every TPC-H logical plan post-rewrite has predicates and projections pushed to scans, views/non-recursive-CTEs inlined, and every decorrelatable TPC-H subquery (Q4, Q17, Q20, Q21, Q22) flattened to a Join.

Acceptance
  • Rewriter converges in < 5 iterations on every TPC-H query (M9).
  • Every rule has ≥ 1 positive and ≥ 1 negative fixture in conformance/corpora/rewrite/{rule}/ — 14 rule directories minimum.
  • LogicalPlan::validate (I1, I2) reports 0 violations across the full TPC-H + JCC-H corpus post-rewrite.
Fixtures
  • conformance/corpora/rewrite/predicate_pushdown/outer_join_null_reject.json — the §8.6 failure-path fixture (negative).
  • conformance/corpora/rewrite/decorrelate_apply/limit_subquery.json — asserts Apply is preserved, not lifted.
  • conformance/corpora/rewrite/*/positive/*.json, .../negative/*.json — one pair per rule.
Pitfalls
  • A rule producing a tree whose schema differs from its input is a correctness bug — the validator (I2) MUST run after every rule in debug builds, not just at the end of the loop.
  • Predicate pushdown across an outer join is unsafe in general; restrict to predicates provably null-rejecting only on the correct side.
  • Decorrelating a LIMIT 1 subquery changes the result — leave it Apply (§15.2).
  • Constant folding must respect timezone/locale for date/time functions — thread it through RewriteCtx.cfg, never assume UTC.

⬜ Phase 4 — Statistics and Cardinality Estimation (Weeks 4–5) §16

Objectives

Own the cardinality/selectivity estimates every downstream cost comparison depends on (P5) — the subsystem Leis 2015 (§5) identifies as the dominant source of real-world plan-quality regressions.

Deliverable

qp stats build produces a complete statistics blob for the TPC-H SF1 schema; every LogicalPlan node downstream carries a Cardinality (§11.5).

Acceptance
  • Cardinality estimates land within 10× of ground truth on ≥ 80% of JCC-H intermediate joins (M3; Leis 2015 found PostgreSQL at roughly half this bar — matching it is the conformance target).
  • qp stats build completes on a 1 GB TPC-H instance in < 60 s (M8).
  • Every Cardinality.relative_error stays within [0.0, 10.0] (I8) across the full conformance corpus.
Fixtures
  • conformance/corpora/cardinality/*.json — predicate + ground-truth row count pairs.
  • conformance/corpora/jcch/* — the Join Order Benchmark drop, scored by benchmarks/cardinality_jcch.rs (M3).
  • conformance/corpora/cardinality/negative/skewed_no_mcv.json — demonstrates the MM8 failure mode absent MCV.
Pitfalls
  • Sampling the first N rows of a clustered table produces a biased histogram — use reservoir sampling unconditionally, never a positional prefix.
  • HLL is meaningless below the exact-count threshold (default 1,000, ADR-10) — small distinct counts must use exact counting.
  • Histograms alone are wrong on correlated columns (MM8); multi-column stats (§16.2, ADR-11) are not optional for any workload with composite keys.
  • The cost model (§17) must consume relative_error, not just rows — ignoring it produces confidently-wrong plan choices (P5).

⬜ Phase 5 — Cost Model and Bottom-Up Join Enumeration (DPccp) (Weeks 5–7) §17

Objectives

Assign every candidate plan a scalar cost (P4, §11.4) and search the join-order space for the minimum-cost tree using DPccp (Moerkotte & Neumann 2006, §5), falling back to greedy beyond the exact-search relation cap (§4).

Deliverable

The DPccp enumerator finds the provably-optimal join order for every connected join graph up to N = 16; the greedy fallback engages automatically beyond that.

Acceptance
  • 100,000 join-order candidates enumerated in < 1 s on a 16-relation synthetic graph (M1).
  • Greedy-fallback plans are within 20% of DPccp-optimal cost on every TPC-H join graph small enough for both to run.
  • Optimal-plan cost within 10% of the best-known plan on every TPC-H query at SF1 (M4).
Fixtures
  • conformance/corpora/enum/*.json — join graph in, DPccp-optimal plan out, for graphs up to N = 16.
  • conformance/corpora/enum/negative/unfiltered_cartesian.json — asserts I9 rejection.
  • benchmarks/enum_dpccp.rs — the M1 benchmark harness.
Pitfalls
  • Cartesian products explode the search space for no benefit (I9) — filter them from the join graph; admit only when the query genuinely has no join predicate at all.
  • Bushy plans matter — a plan joining (A,B) then (C,D) then combining can dominate any left-deep plan; DPccp produces bushy plans by construction, don't constrain to left-deep without an explicit flag.
  • The cost model's weights are coupled to the statistics layer (P14) — changing one without recalibrating the other against JCC-H shifts the plan distribution unpredictably.
  • Hashing RelationSet into the DP table is the hottest path in the enumerator — the u8/u64 bitset choice (§11.1) exists specifically to keep this O(1).

⬜ Phase 6 — Cascades-Style Memo and Transformation Rules (Weeks 7–8) §18

Objectives

Wrap a Cascades-style memo (Graefe 1995, §5) around the DPccp join order to explore transformation rules (operator-implementation alternatives, non-join-reordering rewrites) that DPccp alone does not cover (P6).

Deliverable

The Cascades search reproduces the DPccp-chosen join order plus a transformation-rule-explored physical plan for every TPC-H query at SF1.

Acceptance
  • The memo deduplicates: planning the same query twice yields the same set of GroupIds (I12, conformance-checked).
  • Cascades search converges in < 100 ms on every TPC-H query (M5).
  • Cascades-search plan cost matches the DPccp-enumerator plan cost on every TPC-H query at SF1 (M4 cross-check).
Fixtures
  • conformance/corpora/enum/cascades_matches_dpccp/*.json — one fixture per TPC-H query, asserting cost equality.
  • conformance/corpora/enum/negative/memo_cycle.json — a group-expression shape crafted to detect unbounded mutual recursion.
Pitfalls
  • The memo is mutually recursive across groups — write cycle detection into the search (§18.2) explicitly; an undetected cycle hangs plan() past its budget (P13).
  • Enforceable required properties (e.g. Sort) and non-enforceable ones (a partitioning the source cannot deliver at all) must be distinguished — the latter forces a child re-plan, not an enforcer insertion.
  • Cascades search is exponential worst-case; the hard timeout (§18.2) is not optional — it is the only thing standing between a pathological query and a starved host.

⬜ Phase 7 — Physical Operator Lowering (Weeks 8–9) §19

Objectives

Convert the winning logical join order (from §17/§18's shared memo) into a PhysicalPlan (§11.10) by choosing, per logical node, the cheapest physical operator family.

Deliverable

Every TPC-H optimised logical plan lowers to a complete PhysicalPlan; qp explain --format=json renders operator type, estimated rows/cost/width per node.

Acceptance
  • 100% of TPC-H SF1 logical plans lower to a PhysicalPlan with no remaining logical nodes.
  • The conformance corpus pins the chosen physical operator per TPC-H query as a regression sentinel — cost-model/statistics changes may shift the choice deliberately, but an unreviewed shift fails CI (§26).
  • p50 physical-lowering latency ≤ 3 ms on TPC-H Q1 (component of M2's 10 ms budget).
Fixtures
  • conformance/corpora/tpch/Q01.sql…Q22.sql — reference physical plans at SF1.
  • conformance/corpora/enum/index_selection/*.json — leading-column-selectivity tie-break cases.
Pitfalls
  • Physical lowering must respect the join order already chosen by §17/§18 — it picks the operator family, never re-orders the join (a layering violation that would silently invalidate the enumerator's cost guarantees).
  • A NestedLoopJoin without an inner-side index is almost always wrong — refuse it unless the cost model shows it cheapest by a clear margin (PlannerConfig::nested_loop_safety_factor).
  • An IndexOnlyScan chosen without verifying the covering set against every parent operator's column demand silently forces a hidden heap fetch at execution.

⬜ Phase 8 — Physical Optimisation (Property Enforcement) (Weeks 9–10) §20

Objectives

Walk the lowered PhysicalPlan once more, deriving delivered properties, inserting enforcers where required properties are unsatisfied, and applying peephole rewrites — the pass that makes the plan correct by construction (P7).

Deliverable

Every PhysicalPlan emerging from this phase has every operator's required properties satisfied by its child (I6), verified by the property-walk validator.

Acceptance
  • Property derivation is implemented for all 18 physical operator kinds in §11.10 (100% coverage, conformance-gated).
  • The peephole pass eliminates every redundant Sort on the TPC-H SF1 corpus (0 redundant-sort false positives, §26).
  • Enforcer insertion produces 0 I6 violations across the full TPC-H + JCC-H corpus.
Fixtures
  • conformance/corpora/tpch/* (physical, post-optimisation) — pinned final plans.
  • conformance/corpora/enum/negative/property_violation.json — a hand-crafted plan with an unsatisfied MergeJoin sort requirement, asserting the validator catches it.
Pitfalls
  • Property reasoning is where planners get subtly wrong: HashJoin preserves no ordering of either child — never record one for its output.
  • Equivalence-derived orderings (§20.2) are easy to under-use (missing a free order) or over-use (claiming an order that doesn't actually hold post-Filter) — test both directions explicitly.
  • The Cascades search (§18) and this pass must agree on the property model; drift between them produces plans whose chosen cost does not match the executor's actual behaviour — a silent, hard-to-diagnose regression class.

⬜ Phase 9 — EXPLAIN, EXPLAIN ANALYZE and Adaptive Re-Plan Hooks (Weeks 10–11) §21

Objectives

Ship the planner's user interface (P8): text and JSON EXPLAIN, an EXPLAIN ANALYZE actuals callback, and the hook contract for Phase-1+ adaptive re-planning (PhaseDeferred, this section).

Deliverable

qp explain produces pinned text and JSON output for every TPC-H query; the AdaptiveCallback trait compiles against a mock executor and is exercised by one reference test that injects a deliberately-wrong cardinality and asserts the callback is invoked with the correct divergence ratio.

Acceptance
  • EXPLAIN text stays under 1 KB per TPC-H query, one line per operator (M6).
  • Text and JSON EXPLAIN output for every TPC-H query matches its golden fixture byte-for-byte (§26).
  • The adaptive-hook reference test demonstrates the callback fires exactly when divergence exceeds adaptive_replan_threshold, and does not fire below it.
Fixtures
  • conformance/corpora/explain/*.golden.txt, *.golden.json — one pair per TPC-H query.
  • conformance/corpora/explain/negative/oversized_plan.json — a 22-way join, asserting the indented/summary-mode fallback (§21.8) engages rather than overflowing.
Pitfalls
  • EXPLAIN cost numbers are cost-model units, not seconds — state this explicitly in docs/api/explain.json; PostgreSQL's decades-long user confusion on this exact point is the cautionary tale (§5 ref-impl 1).
  • The actual/estimated ratio is the debugging payoff of EXPLAIN ANALYZE — compute and display it; do not leave it as an exercise for the operator reading two numbers.
  • A 22-way join's indented text tree can overflow a terminal — provide a summary mode (top-N most expensive operators) alongside the full tree.
