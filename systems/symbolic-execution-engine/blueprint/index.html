1. Goal & Scope

Engineering definition: a symbolic execution engine is a program-analysis runtime that replaces concrete inputs with symbolic variables, executes the target's instruction semantics over those variables to build a first-order-logic constraint per path, and calls an SMT solver to decide path feasibility, generate concrete counterexamples, and enumerate reachable program states. This blueprint builds one from an ELF loader up through a distributed, crash-safe, deterministically replayable exploration platform, in the tradition of KLEE, angr, S2E, and Mayhem.

Phase 0 deliverable — the correctness kernel, as a numbered list of crates:

  1. crates/runtime — deterministic clock, typed config, worker supervisor, panic policy.
  2. crates/parser — ELF header/section/relocation/symbol-table parsing.
  3. crates/lifter — x86_64 instruction lifting into canonical IR.
  4. crates/ir — SSA-like IR, CFG, dominance metadata, verifier.
  5. crates/executor — symbolic instruction semantics, register bank, path forking.
  6. crates/memory — paged symbolic memory, copy-on-write, concretization policy.
  7. crates/solver — SMT abstraction trait over Z3 and Bitwuzla.
  8. crates/scheduler — path queue, worker leasing, fairness.
  9. crates/storage — append-only WAL, checkpoint serialization, compression.
  10. crates/replay — deterministic replay, lineage reconstruction.
  11. crates/telemetry — metrics, tracing, structured-log field schema.
  12. crates/cli — operator entry point (run, replay, minimize, triage).

System boundaries.

Provides: IR lifting for x86_64 ELF binaries; a symbolic memory model with copy-on-write paging; an SMT abstraction layer over Z3/Bitwuzla with incremental solving and result caching; a fairness-scheduled path exploration coordinator; append-only WAL/checkpoint durability with deterministic replay; crash triage and testcase minimization; differential execution validation across solver backends; a structured observability stack (metrics, traces, logs).

Delegates: instruction-set architecture semantics to the lifter's per-arch backend (only x86_64 in Phase 0); constraint satisfiability to Z3/Bitwuzla, never reimplemented; container orchestration to Kubernetes; artifact signing to cosign; SBOM generation to cargo-sbom/SPDX tooling.

Does NOT provide: dynamic binary translation JIT (no re-JITting hot native code — the CPU model is purely interpretive over lifted IR); a full compiler backend (no codegen, only lifting into IR); a source-level debugger UI; IDE integration; a decompiler frontend (no pseudo-C reconstruction); a malware sandboxing environment (no network emulation, no anti-analysis countermeasures); symbolic hardware device emulation.

Non-goals: matching angr's breadth of loaders (CGC, MIPS, ARM) in Phase 0; matching KLEE's POSIX environment model completeness; real-time interactive exploration (this is a batch/CI-triggered analysis platform, not an IDE plugin).

Deployment model: containerized Linux services orchestrated via Kubernetes for the distributed topology; a local standalone developer runtime (single-process, in-memory scheduler) for iteration; a distributed worker topology (coordinator + N worker pods) for campaign-scale exploration. No inter-region deployment in Phase 0 (§4 network assumptions).

Target operators: vulnerability researchers running exploit-generation campaigns; compiler engineers validating optimization-pass semantic preservation; formal-verification engineers cross-checking solver results; systems-security teams triaging crash corpora; binary-analysis researchers extending the lifter to new architectures; runtime-instrumentation engineers building on the replay subsystem.

What later phases unlock: Phase 2 (IR) unlocks CFG-aware path scheduling; Phase 3 (symbolic AST) unlocks constraint simplification and caching; Phase 5 (SMT integration) unlocks feasibility pruning; Phase 7 (scheduler) unlocks horizontal scaling past one machine; Phase 8 (WAL/replay) unlocks crash-safe long-running campaigns; Phase 9 (fuzzing/hardening/observability) unlocks production operation with incident response.

Recommended language: Rust. Rationale: deterministic ownership semantics eliminate the aliasing bugs that plague hand-rolled symbolic memory models in C/C++ (see Pitfalls, Phase 4); strong concurrency guarantees (Send/Sync) make the isolation invariant (I7) statically checkable instead of merely documented; low-level systems control matches the CPU-model and memory-paging work; FFI interoperability lets crates/solver bind Z3's and Bitwuzla's C APIs directly; identical release binaries across CI and operator hosts support reproducible replay (ADR-18); no GC pause behavior protects the p99 solver-roundtrip budget (§4) from stop-the-world pauses. Rejected: C++ (memory-safety burden on a hash-consing arena touched by every worker thread outweighs its FFI convenience — see ADR-01); Go (GC pauses are incompatible with the p99 latency budget, and Go's weaker type system cannot express the ownership invariants in §11 at compile time).

Prerequisites: compiler construction (CFG/SSA); operating systems internals (process/memory model); ELF format internals; CPU architecture fundamentals (x86_64 ISA, flags semantics); SMT solving theory (bitvector/array theories, incremental solving); concurrency control; distributed systems (leasing, work-stealing); memory models (copy-on-write, TLB-like paging); Linux process internals; async runtimes; lock-free queue design; profiling and observability; deterministic testing methodology (property testing, chaos injection).

Estimated timeline: Phase 0 (repository foundation + deterministic kernel) — 8-12 weeks. Production-ready single-machine implementation (Phases 0-6) — 12-18 months. Distributed-execution maturity (Phases 7-9, cluster-scale campaigns) — 24+ months.

2. Why Build This

Symbolic execution sits at the intersection of compilers, operating systems, theorem proving, binary analysis, distributed systems, storage engines, and debugging infrastructure — few other systems force correctness (path semantics), performance (path explosion), and durability (crash-safe replay) into the same design surface simultaneously.

This project teaches: formal reasoning over machine state; scalable search-space exploration under combinatorial explosion; SMT solver integration patterns (incremental contexts, unsat cores, result caching); deterministic replay architecture; execution scheduling with fairness under backpressure; symbolic memory representation (paging, copy-on-write, concretization); crash minimization; runtime state serialization (WAL, checkpoints, deduplicated pages).

Historically influential systems this blueprint draws from: KLEE (Cadar et al., OSDI 2008) — path scheduling and the coverage-driven search heuristic; S2E (Chipounov et al., ASPLOS 2011) — selective symbolic execution and concrete/symbolic mode switching; angr (Shoshitaishvili et al., IEEE S&P 2016) — platform-agnostic lifting via VEX/pyvex and a layered symbolic-memory architecture (simuvex/claripy); Mayhem (Cha et al., IEEE S&P 2012) — hybrid symbolic/concolic exploit generation; EXE (Cadar et al., CCS 2006) — the constraint-solving-on-real-code lineage that KLEE grew from; Java Pathfinder (Visser et al., ASE 2003) — model-checking-flavored state exploration for a managed runtime.

Engineering muscles exercised: IR normalization and verification; state snapshotting under copy-on-write; solver optimization (caching, incrementality, pooling); persistent/immutable data structures (hash-consed ASTs); lock contention reduction at scheduler scale; queue backpressure design; replay determinism engineering; storage integrity (checksums, WAL ordering); structured telemetry design.

Client Interfaces: accepts execution requests, benchmark suites, replay workloads, CI-triggered analysis jobs. Stateless except short-lived request metadata. This is the system's only trust boundary — untrusted binaries enter here (Threat Model T1).

Execution Coordinator: owns lifecycle orchestration for distributed exploration — path queues, state leasing (I7), worker heartbeats, scheduling fairness, timeout enforcement, execution quotas (P8). All exploration concurrency is admitted through this component; nothing downstream accepts new work directly.

Binary Loader & Lifter: parses ELF, resolves relocations, reconstructs CFGs, lifts x86_64 instructions into canonical IR (P7). Malformed input is rejected here, before the lift stage, per P9 (fail closed).

Replay & Crash Reconstructor: deterministic replay of symbolic traces — reconstructs path constraints, restores snapshots, validates divergence (I9), produces minimized crash artifacts. Reads from the same persistence boundary as the live executor but never mutates it.

Symbolic Execution Core: the canonical runtime for symbolic instruction semantics, register tracking, memory virtualization, path forking, concretization policy, and state transitions. This is the concurrency boundary: each worker is a separate OS process (P12), communicating only through the coordinator's lease protocol and the shared WAL — never through shared mutable memory.

SMT Abstraction Layer: a stable trait over Z3 and Bitwuzla (ADR-22). Handles solver pooling, timeout management, incremental solving (P10), AST canonicalization, constraint caching, unsat-core extraction. This is the protocol boundary where symbolic constraints become solver-specific ASTs.

State Snapshot Store: persists execution state via append-only WAL (I4) with checkpoint compression and deduplicated memory pages. This is the persistence boundary — nothing downstream of it is authoritative; the WAL is.

Observability & Telemetry: metrics, traces, structured logs, replay correlation IDs, path diagnostics, scheduler visibility, runtime profiling (P5). Every box above emits into this layer; it has no outbound edges into the execution path (never blocks it, I12).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every executor decision (branch order, hash iteration, thread pickup order) must be reproducible byte-for-byte from a snapshot. Tradeoff: forbids nondeterministic APIs (unordered-map iteration, wall-clock reads) on the hot path. Operational: crates/runtime/src/clock.rs is the only sanctioned time source inside the executor. Violated: replay diverges silently (I9), crash artifacts become unreproducible.
  • P2 — Explicit Ownership. Rule: symbolic state has exactly one owning worker at a time; no hidden aliasing across the executor/memory boundary. Tradeoff: requires explicit lease hand-off (I7) instead of shared-mutable convenience. Operational: crates/scheduler/src/lease.rs mediates every ownership transfer. Violated: two workers mutate one ConstraintSet, corrupting a snapshot.
  • P3 — Crash-Only Recovery. Rule: a worker may be SIGKILLed at any instruction boundary and recovery depends only on WAL + checkpoint state, never on graceful-shutdown side effects. Tradeoff: forbids deferring durability to shutdown handlers. Operational: crates/storage/src/wal.rs fsyncs before a lease is released. Violated: FM-6 leaks a lease and orphans a subtree.
  • P4 — Bounded Resource Usage. Rule: every queue, cache, arena, and snapshot pool carries an explicit numeric limit from §4. Tradeoff: bounded caches evict useful state under pressure, costing solver latency. Operational: crates/solver/src/cache.rs is a fixed-capacity LRU keyed by AST hash. Violated: unbounded growth exceeds the 8 GB RSS budget mid-path.
  • P5 — Observability by Default. Rule: every ExecutionState transition emits a structured telemetry event before it is considered committed. Tradeoff: emission on the hot path costs measurable per-instruction overhead (§28). Operational: crates/telemetry/src/tracing_fields.rs defines the shared field schema. Violated: incident response cannot reconstruct a path's history.
  • P6 — Replayability First. Rule: no optimization may change the sequence or content of committed constraints. Tradeoff: rules out constraint-reordering solver speedups. Operational: crates/solver/src/pool.rs preserves per-path assertion order (I1). Violated: replay hash mismatch (I9), crash reproduction fails.
  • P7 — Stable IR Semantics. Rule: an IR transformation must preserve concrete-execution equivalence, verified by crates/ir/src/verifier.rs on every build. Tradeoff: disallows peephole rewrites whose equivalence is unproven. Operational: dominance metadata recomputed and checked after each pass. Violated: silently wrong IR poisons every downstream execution.
  • P8 — Backpressure Everywhere. Rule: unbounded path exploration is forbidden; every fork increments a quota that must be paid down. Tradeoff: deep exploration campaigns require explicit quota grants. Operational: crates/scheduler/src/fairness.rs enforces per-worker/per-path quotas. Violated: queue saturation (§4, 80%) breached, p99 latency collapses.
  • P9 — Fail Closed on Corruption. Rule: a checksum mismatch on a checkpoint or WAL segment halts replay for that lineage rather than proceeding best-effort. Tradeoff: one bit-flip loses a whole lineage instead of degrading gracefully. Operational: crates/storage/src/checkpoint.rs verifies checksum before mapping any page. Violated: a corrupted state replays as "successful", producing a false negative on a real bug.
  • P10 — Incremental Solving Preferred. Rule: reuse solver contexts (push/pop) across forks sharing a constraint prefix instead of re-asserting from scratch. Tradeoff: incremental contexts pin more memory per worker for longer. Operational: crates/solver/src/pool.rs keys context reuse by prefix hash. Violated: p95 solver roundtrip regresses toward cold-start latency.
  • P11 — Immutable Snapshot Metadata. Rule: a SnapshotRecord descriptor becomes append-only the instant it is published. Tradeoff: correcting a mis-tagged descriptor needs a new record plus a tombstone, never an in-place edit. Operational: crates/storage/src/wal.rs enforces write-once semantics per snapshot_id (I2). Violated: two replayers observe different ancestry for one ID.
  • P12 — Isolation Between Workers. Rule: workers communicate only through the lease protocol and the shared WAL, never through shared-mutable memory. Tradeoff: forgoes zero-copy sharing of hot state between same-node workers. Operational: workers run as separate OS processes (§3). Violated: a memory-safety bug in one worker's solver FFI call corrupts a sibling's arena.

+----------------------+  high addresses
| Guard Pages          |  unmapped, trap on access (I3-adjacent)
+----------------------+

+----------------------+

Solver request protocol (sequence, §3 protocol boundary):

Client        -> SolverPool  : SubmitConstraintSet(path_id, epoch)
SolverPool    -> Worker      : LeaseSolver(backend, timeout)
Worker        -> Solver      : IncrementalAssertions(prefix_hash)

Worker        -> Telemetry   : EmitSolverMetrics(latency, cache_hit)

Failure path example — malformed ELF (illustrates P9, fail-closed at the trust boundary):

  1. crates/parser detects an invalid relocation offset.
  2. loader emits a structured parse failure (ParseError::InvalidRelocation).
  3. execution is aborted before the lift stage — no IR is produced.
  4. a replay artifact is generated recording the rejected input's hash.
  5. telemetry is tagged with the binary hash for later triage correlation.

11. Core Schema & Types

SymbolicValue — ownership: immutable after publication, reference-counted internally; mutation: none post-construction; concurrency: Send + Sync, shared across worker-local reads only (P12); persistence: serialized via Cap'n Proto page format; serialization: Concrete/Hybrid variants carry raw u64, Symbolic carries an ExprId resolved against the worker-local arena; compat: an additive enum, new variants require a MAJOR bump (§25) because replay depends on exhaustive match.

enum SymbolicValue
  Concrete(u64)
  Symbolic(SymbolicExprId)
  Hybrid(SymbolicExprId, u64)

SymbolicExpr — ownership: owned by the per-worker hash-consing arena (I6); mutation: none, canonicalized before insertion; concurrency: arena is worker-exclusive, never shared across process boundaries (P12); persistence: hash-consed nodes are not individually persisted, only referenced by ExprId from a ConstraintSet; serialization: hash field is the canonical cross-process identity for cache lookups (crates/solver/src/cache.rs); compat: width_bits growth beyond 128 requires a schema-version bump.

struct SymbolicExpr
  expr_id: ExprId
  opcode: ExprOpcode
  operands: SmallVec<ExprId>
  width_bits: u16
  hash: u128

ConstraintSet — ownership: owned by the ExecutionState that accumulated it; mutation: append-only during RUNNING (I1); concurrency: exclusive to the leaseholder worker (I7); persistence: serialized into checkpoint pages on SNAPSHOTTED transition; serialization: assertion order preserved byte-for-byte (P6); compat: solver_epoch must increase monotonically (I11).

struct ConstraintSet
  path_id: PathId
  assertions: Vec<ConstraintId>
  solver_epoch: u64

ExecutionState — ownership: exclusive to leaseholder worker; mutation: registers/memory/pc mutate during RUNNING, immutable once SNAPSHOTTED; concurrency: copy-on-write across fork boundaries (I10); persistence: root object serialized on every SNAPSHOTTED transition; serialization: lineage carries the parent-chain needed for replay reconstruction (§8); compat: adding a field requires updating both crates/storage and crates/replay in lockstep.

struct ExecutionState
  registers: RegisterBank
  memory: SymbolicMemory
  constraints: ConstraintSet
  pc: VirtualAddress
  status: ExecutionStatus
  lineage: LineageMetadata

SnapshotRecord — ownership: owned by crates/storage once published; mutation: none, append-only (P11, I8); concurrency: readable concurrently by any worker performing replay, never mutated after publication; persistence: the authoritative on-disk record referenced by WAL offset; serialization: checksum gates every read (P9); compat: parent_snapshot chain length is unbounded, dedup lives in compressed_pages.

struct SnapshotRecord
  snapshot_id: u64
  parent_snapshot: Option<u64>
  wal_offset: u64
  compressed_pages: Vec<PageRef>
  checksum: [u8; 32]

SchedulerLease — ownership: owned by the coordinator's lease registry, borrowed by exactly one worker (I7); mutation: lease_expiry extended on heartbeat, otherwise immutable; concurrency: compare-and-swap admission into the registry (ADR-08); persistence: not durable — a coordinator restart invalidates all outstanding leases by design (crash-only, P3); serialization: wire form only, never written to the WAL; compat: internal to crates/scheduler, no cross-version contract.

struct SchedulerLease
  worker_id: WorkerId
  path_id: PathId
  lease_expiry: Instant

SolverQuery — ownership: owned by the requesting worker for the query's lifetime; mutation: none, constructed once per solve call; concurrency: dispatched through crates/solver/src/pool.rs's bounded worker pool (ADR-08, P4); persistence: not persisted directly, only its prefix_hash appears in cache entries; serialization: canonicalized to SMT-LIB v2 before dispatch (§5 RFCs); compat: backend-specific extensions must round-trip through the shared trait.

trait SolverBackend
  fn assert_incremental(&mut self, query: &SolverQuery) -> Result<(), SolverError>;
  fn check_sat(&mut self, timeout: Duration) -> SolverOutcome;
  fn unsat_core(&self) -> Vec<ConstraintId>;
  fn push(&mut self);
  fn pop(&mut self);

12. Phase 0 — Repository Foundation & Deterministic Runtime Kernel

12.1 Objectives

Stand up the Cargo workspace, lint/format gates, and the deterministic runtime primitives every later crate depends on: clock abstraction (P1), typed configuration, structured logging facade, panic policy, and worker lifecycle supervision. This phase introduces the constraint that no later crate may read SystemTime or iterate a HashMap on a path observable in replay.

12.2 Detailed Implementation Steps

Initialize the Cargo workspace per §10 with crates/runtime first. Define lint policy (clippy::all deny, rustfmt check) as a CI gate (ADR-14). Implement crates/runtime/src/clock.rs: a DeterministicClock trait with a logical-tick implementation for the executor and a wall-clock implementation for telemetry only (ADR-19, P1). Add the structured logging facade over tracing (ADR-09) with correlation-ID propagation. Define the runtime error hierarchy (RuntimeError, per-crate thiserror enums) so failures carry a stable discriminant for telemetry (P5). Implement crates/runtime/src/config.rs: a typed TOML loader that rejects unknown keys. Build the panic-handling strategy: a panic hook that flushes telemetry before abort, satisfying P3 (crash-only still requires the panic to surface, not silently swallow). Establish tracing correlation IDs (trace_id, lineage_id) as mandatory span fields (I12). Add allocator instrumentation (mimalloc stats export, ADR-23). Create build-metadata embedding (git SHA, toolchain version) for crates/cli version output. Establish feature-flag governance (compile-time only, no runtime flag flips inside a running worker — protects P1). Implement crates/runtime/src/supervisor.rs: a worker lifecycle supervisor that spawns, health-checks, and restarts worker processes per P3 and P12 (separate OS processes, not threads).

12.3 Deliverable

A deterministic executable runtime (crates/cli run --dry-run) that spawns a supervised worker, loads config from conformance/runtime/config_invalid.toml-shaped input, emits OTLP traces, and terminates cleanly on SIGTERM within the shutdown budget.

12.4 Acceptance Criteria

Deterministic integration tests (10 consecutive runs, identical trace-ID sequence modulo the ID values themselves) pass; startup completes in < 5 seconds (§4); reproducible binaries verified via scripts/repro-build.sh producing a byte-identical hash across two clean builds; telemetry visible in a local Prometheus scrape within 10 seconds of startup.

12.5 Conformance Fixtures

conformance/runtime/config_invalid.toml — malformed config, expect ConfigError::UnknownKey. conformance/runtime/clock_replay.json — records 1,000 logical ticks, expects byte-identical replay. conformance/runtime/shutdown_stress.rs — spawns 50 workers and SIGTERMs them concurrently, expects zero panics and shutdown < 20 seconds (§4).

12.6 Pitfalls

Nondeterministic timestamps leaking into log lines via a default tracing formatter that calls SystemTime::now() — root cause is the default subscriber, not application code; detect via a clippy lint forbidding SystemTime outside crates/telemetry; recover by routing all timestamps through DeterministicClock. Inconsistent span IDs across process restarts — root cause is PID-seeded ID generation; detect via duplicate trace_id alerts; recover by seeding from a monotonic counter persisted in config. Hidden global state (lazy_static config singletons) breaking multi-worker test isolation — detect via cargo-nextest flakiness; recover by threading config explicitly. Allocator drift between debug and release builds changing fragmentation behavior — detect via benchmarks/instruction_throughput.rs variance; recover by pinning mimalloc in both profiles.

12.7 Performance Concerns

Startup allocation spikes from eager crate initialization — batch-allocate the supervisor's worker table once. Tracing overhead from unbuffered span export — batch OTLP exports on a background task, never inline on the hot path (I12). Logger backpressure when the telemetry endpoint is slow — bounded channel with drop-oldest (P4, ADR-20), never block the caller.

12.8 Edge Cases

Partial config loads (file truncated mid-parse) must produce ConfigError, not a partially-populated struct. Panic during shutdown must still flush pending telemetry before process exit. Telemetry endpoint unavailable at startup must not block worker spawn — buffer locally, apply backpressure per I12. Config hot-reload requests must be rejected outright (feature-flag governance, §12.2).

12.9 Failure Analysis

A runtime-bootstrap failure invalidates every higher phase — nothing above crates/runtime can be trusted to be deterministic if the clock or config layer is wrong. Detection: startup health checks (supervisor readiness probe) and deterministic-replay mismatch on the very first clock_replay.json fixture. Blast radius: whole-worker; containment is automatic because the supervisor refuses to promote an unhealthy worker into the lease pool. Recovery: restart with the last-known-good config; escalate to operator if three consecutive restarts fail.

12.10 Operational Notes

Expose build SHA and toolchain version via crates/cli --version and a /debug/build-info endpoint. Expose runtime feature flags at startup in a structured log line. Emit a startup-topology log (worker count, NUMA pinning plan) for later cross-reference against §29 scaling assumptions. Metric: runtime.startup_duration_seconds. Span: runtime.bootstrap. Log field: build_sha.

13. Phase 1 — ELF Parser & Binary Loader

13.1 Objectives

Implement robust ELF binary parsing and validation ahead of the trust boundary (§3): headers, sections, relocations, symbol tables, segment mapping. This phase introduces the constraint that no malformed input may reach the lifter (P9, fail-closed).

13.2 Detailed Implementation Steps

Parse ELF headers and program/section headers in crates/parser/src/elf.rs per the System V ABI (§5 RFCs). Validate section offsets against file size before any read (bounds-checked slicing, avoids the integer-overflow pitfall below). Implement relocation handling in crates/parser/src/relocation.rs, following Levine's relocation model (§5 Books). Support symbol tables (crates/parser/src/symtab.rs), including stripped-binary detection. Load executable segments and map them into SymbolicMemory regions (crates/memory/src/paging.rs, forward dependency on Phase 4) using the "Mapped Binary" layer from §8's memory layout. Enforce alignment constraints per ABI (P-align fields). Build a relocation cache keyed by symbol index to avoid repeated symtab scans. Implement malformed-binary rejection as a single ParseError exit path (P9) — no partial IR is ever produced from a rejected binary. Emit parse diagnostics tagged with the binary's content hash (§8 failure-path example).

13.3 Deliverable

A loader (crates/cli load <binary>) capable of mapping ELF binaries into symbolic memory and printing a validated section/segment/symbol summary.

13.4 Acceptance Criteria

GNU coreutils fixtures (examples/coreutils_ls.elf, examples/coreutils_cat.elf) parse successfully with zero diagnostics; the malformed corpus (§13.5) is rejected 100% of the time with a typed error, never a panic; the parser fuzz suite (fuzz/fuzz_targets/parser_fuzz.rs) runs stable for 24 hours with zero crashes and zero sanitizer findings.

13.5 Conformance Fixtures

conformance/parser/malformed_relocation_01.elf — relocation offset past section end, expect ParseError::InvalidRelocation. conformance/parser/invalid_alignment_02.elf — misaligned segment, expect ParseError::AlignmentViolation. conformance/parser/stripped_binary_03.elf — no symtab, expect successful parse with symbols: None, not an error.

13.6 Pitfalls

Integer overflow in section-offset arithmetic on 32-bit-hosted builds — manifestation is a wrapped offset that reads past the buffer; root cause is unchecked u32 addition; debug via cargo-fuzz with overflow sanitizers enabled; signal is an ASAN heap-buffer-overflow report; recovery is checked arithmetic (checked_add) with a ParseError on overflow. Invalid relocation loops (a relocation that targets itself) causing unbounded cache growth — detect via the relocation-cache size watchdog; recover by capping resolution depth and rejecting cyclic chains. Unbounded section allocation from a crafted section-count field — detect via the FD/RSS budget in §4; recover by capping section count before allocation.

13.7 Performance Concerns

Excessive heap allocations from per-section Vec growth without capacity hints — pre-size from the validated header count. Relocation cache misses under symbol-heavy binaries — key by symbol index, not by name, to avoid string hashing on the hot parse path.

13.8 Edge Cases

Overlapping segments (two PT_LOAD entries mapping the same virtual range) must be detected and rejected, not silently merged. Corrupted symbol tables (string-table index past bounds) must degrade to symbols: None with a diagnostic, not panic. Truncated binaries (file shorter than the header claims) must fail at header validation, before any section read.

13.9 Failure Analysis

Parser corruption risks unsafe execution semantics downstream — an accepted-but-wrong ELF poisons every later phase identically to a lifter bug (P7). Containment: reject before the lift stage, enforced structurally by making Lifter::lift take only a ValidatedBinary type that the parser alone can construct.

13.10 Operational Notes

Emit parser.binary_hash telemetry on every load attempt, accepted or rejected. Archive parse failures (the rejected bytes plus the diagnostic) under conformance/parser/ naming convention for later regression-suite promotion. Metric: parser.rejection_rate. Span: parser.load.

14. Phase 2 — Intermediate Representation & Lifting

14.1 Objectives

Construct an architecture-independent canonical IR from parsed x86_64 binaries: SSA-like form, CFG, dominance metadata, and a verifier that runs on every build (P7). This phase introduces the constraint that every IR transformation must be proven semantics-preserving before merge.

14.2 Detailed Implementation Steps

Define the SSA-like IR node set in crates/ir/src/node.rs, hash-consed per I6, following the IRBuilder shape studied from LLVM (§5 Reference Implementations) but with canonical operand ordering added — LLVM IR is optimizer-oriented, this IR is replay-oriented (P6). Implement the CFG builder (crates/ir/src/cfg.rs) from the parser's segment map. Normalize branch semantics (conditional-jump flag dependencies made explicit operands, not implicit machine state) — addresses the "incorrect flag semantics" pitfall below. Lift arithmetic operations in crates/lifter/src/x86_64.rs, modeling the flags register explicitly in crates/lifter/src/flags.rs per Bryant & O'Hallaron's machine-semantics treatment (§5 Books). Represent memory accesses as explicit IR load/store nodes carrying width and alignment. Canonicalize instruction ordering within a basic block (deterministic operand-evaluation order, P1). Implement the IR verifier (crates/ir/src/verifier.rs) checking SSA well-formedness and dominance consistency on every pass (P7). Build dominance metadata (crates/ir/src/dominance.rs) using the standard iterative dominator algorithm (Cooper & Torczon, §5 Books, ch. 9).

14.3 Deliverable

An instruction-lifting pipeline (crates/cli lift <binary>) producing deterministic IR graphs with a passing verifier report for every function reached from the entry point.

14.4 Acceptance Criteria

IR verifier passes on 100% of conformance/ir/* fixtures; replay hashes are stable across 3 consecutive lift runs of the same binary (byte-identical IR-node hash sequence); CFG edge coverage exceeds 95% against a objdump-derived ground truth for the coreutils fixture set.

14.5 Conformance Fixtures

conformance/ir/branch_loop.bin — a tight backward-branch loop, exercises dominance-tree cycles. conformance/ir/self_modifying.bin — expect explicit rejection (LiftError::SelfModifyingCode), not silent misdisassembly. conformance/ir/indirect_jump.bin — exercises CFG-edge inference for jump tables.

14.6 Pitfalls

Incorrect flag semantics (e.g. modeling ZF update on AND but forgetting CF/OF clearing) — manifestation is a downstream symbolic-executor branch that takes the wrong path only under specific bit patterns; root cause is copying x86 flag tables from memory instead of the ISA manual; debug via differential testing against a reference disassembler; signal is a branch-coverage gap in §14.4's 95% target; recovery is a per-opcode flags unit-test matrix. Unstable IR node ordering across two lifts of the same function — root cause is iterating a HashMap of basic blocks; detect via I9-style hash-sequence comparison; recover by switching to IndexMap/BTreeMap (P1). Invalid SSA construction on irreducible CFGs (from computed gotos) — detect via the verifier's dominance check failing; recover by node-splitting per Cooper & Torczon ch. 9.

14.7 Performance Concerns

IR allocation churn from unbounded node creation on large functions — reuse the hash-consing arena (I6) instead of allocating fresh nodes per lift attempt. Dominance recomputation cost on every verifier pass — cache the dominator tree and invalidate only on structural CFG edits, not on every node rewrite.

14.8 Edge Cases

Indirect branches (computed jump targets) must produce a conservative CFG edge set, not a missing edge. Position-independent code (RIP-relative addressing) must resolve correctly against the load base recorded by Phase 1. Tail-call ambiguity (a jmp to another function's entry) must be classified explicitly, not folded into the caller's CFG.

14.9 Failure Analysis

Incorrect lifting poisons all downstream symbolic execution identically to a parser bug — the IR verifier is the only backstop, so a verifier false-negative is the worst-case failure. Detection: cross-run hash stability (§14.4) plus periodic differential lifting against a second lifter implementation is deferred (PhaseDeferred("§14")) pending resourcing; today, detection relies on the verifier plus fixture coverage.

14.10 Operational Notes

Emit lifter.instructions_lifted_total and lifter.verifier_failures_total. Persist IR verification reports under docs/performance/baseline-report.md's companion artifact store for regression tracking. Span: lifter.lift_function. Log field: function_entry_va.

15. Phase 3 — Symbolic Expression Engine

15.1 Objectives

Implement the symbolic AST infrastructure — hash-consed, canonicalized, simplifiable — that every later symbolic value in the system is built from (§11). This phase introduces the constraint that AST hashes must be stable cross-process for the SMT cache (P4, P10) to be useful at all.

15.2 Detailed Implementation Steps

Define the symbolic opcode set (ExprOpcode) in crates/ir/src/node.rs covering bitvector arithmetic, comparison, and concat/extract operations, modeled after Triton's AST subsystem (§5 Reference Implementations) but redesigned for per-worker-exclusive ownership (P12) rather than Triton's shared mutable context. Implement the hash-consing arena with a global-per-worker table keyed by structural hash (I6). Canonicalize expressions (operand sorting for commutative ops, constant folding) before arena insertion. Support bitvector operations up to 128 bits (§11 compat note). Implement simplification passes: constant folding, identity elimination (x + 0 -> x), and redundant-extract collapsing. Define the AST hashing strategy — a structural hash over (opcode, operand_hashes, width_bits), matching SymbolicExpr.hash in §11. Implement expression serialization to SMT-LIB v2 for solver dispatch (§5 RFCs). Support incremental simplification — re-simplify only the subtree touched by a new assertion, not the whole ConstraintSet, to bound per-fork cost (Cadar & Sen's taxonomy, §5 Papers).

15.3 Deliverable

A canonical symbolic AST engine (crates/cli simplify <expr.json>) that ingests raw expression JSON and emits a canonicalized, simplified, hash-stamped AST.

15.4 Acceptance Criteria

AST hash stability is guaranteed across 1,000 repeated canonicalizations of the same input (bit-identical hash field); the simplifier reduces benchmark constraint size by more than 20% on the conformance/ast/* corpus, measured in node count pre/post simplification.

15.5 Conformance Fixtures

conformance/ast/arithmetic_expr.json — nested arithmetic, exercises constant folding. conformance/ast/nested_concat.json — deep concat/extract chains, exercises collapse rules. conformance/ast/overflow_case.json — bitvector width mismatch, expect ExprError::WidthMismatch.

15.6 Pitfalls

Expression explosion from unbounded constant propagation through nested concats — manifestation is a single path's ConstraintSet growing past the arena's practical size before any fork; root cause is a simplification rule that expands before it contracts; debug via arena-occupancy telemetry; signal is ir.arena_occupancy_bytes trending toward the RSS budget (§4); recovery is a depth cap on recursive simplification with a PhaseDeferred fallback to unsimplified form. Unstable hashes from including non-canonical operand order in commutative ops — detect via I6's hash-collision audit; recover by enforcing a total order on operands before hashing. Recursive simplifier loops (a rewrite rule that re-triggers itself) — detect via a rewrite-count watchdog per expression; recover by capping rewrite iterations and falling back to the unsimplified form with a warning.

15.7 Performance Concerns

Allocator fragmentation from small, short-lived AST node allocations — mimalloc's segment reuse (ADR-23) mitigates this; batch-allocate node slabs per basic block where possible. AST traversal cache misses on deeply nested expressions — flatten commutative chains (n-ary add/concat) rather than binary trees to improve locality during traversal.

15.8 Edge Cases

Oversized bitvectors (> 128 bits, e.g. from vectorized load lifting) must be rejected with a typed error, not silently truncated. Unsupported opcodes (from an unlifted instruction) must produce an explicit Unmodeled placeholder node, never a panic. Cyclic references (a malformed deserialized AST) must be caught by an acyclicity check at deserialization, before arena insertion.

15.9 Failure Analysis

AST corruption breaks solver correctness silently — a malformed hash means the cache (P4) returns a wrong cached result for a different query. Detection: cache-key collision audits in the property test suite (ADR-12); blast radius is bounded to the worker holding the corrupted arena, since arenas are never shared (P12).

15.10 Operational Notes

Emit ir.arena_occupancy_bytes and ir.simplification_ratio metrics. Span: ast.simplify. Log field: expr_hash. Deployment note: arena size cap is a worker startup flag, not hot-reloadable (§12.2 feature-flag governance).

16. Phase 4 — Symbolic Memory Model

16.1 Objectives

Implement scalable symbolic virtual memory: paged abstraction, copy-on-write, concretization policy, guard pages, permissions. This phase introduces the constraint that memory replay must be bit-for-bit deterministic (I9) even under symbolic pointer aliasing.

16.2 Detailed Implementation Steps

Define the paged memory abstraction in crates/memory/src/paging.rs, modeled on angr's layered simuvex memory design (§5 Papers, Shoshitaishvili et al. 2016) but implemented for per-process worker isolation (P12) rather than in-process Python objects. Implement copy-on-write pages (crates/memory/src/cow.rs) with refcounted sharing across forked ExecutionStates, enforcing I10. Support symbolic reads/writes — a load at a symbolic address produces a symbolic value spanning the possible target pages. Implement the concretization policy (crates/memory/src/concretize.rs): when a symbolic pointer's range exceeds a configurable fan-out threshold, force a solver query to pick a concrete witness rather than exploring every aliasing possibility (informed by S2E's concrete/symbolic mode switching, §5 Papers). Add guard pages at region boundaries (§8 memory layout) that trap on access, catching out-of-bounds symbolic writes deterministically. Support memory permissions (R/W/X bits from the ELF segment flags, Phase 1). Implement symbolic pointer handling with a bounded aliasing set per pointer, capped by the concretization threshold above. Add page deduplication across identical COW pages from shared libraries (§8 layout). Define snapshot serialization for memory pages into SnapshotRecord.compressed_pages (§11).

16.3 Deliverable

A fully symbolic memory subsystem exercised via crates/cli mem-trace <binary>, printing a page access log with concretization decisions annotated.

16.4 Acceptance Criteria

Memory replay is deterministic across 100 repeated replays of conformance/memory/symbolic_pointer.bin (identical page-fault and concretization decision sequence); snapshot restore completes in < 3 seconds (§4) for a 250,000-page working set.

16.5 Conformance Fixtures

conformance/memory/symbolic_pointer.bin — a symbolic array index, exercises concretization threshold logic. conformance/memory/heap_aliasing.bin — two symbolic pointers that may alias, exercises the bounded aliasing set. conformance/memory/partial_write.bin — a write narrower than a page, exercises COW page splitting.

16.6 Pitfalls

Aliasing ambiguity — a symbolic pointer's possible target set silently growing unbounded — manifestation is a single memory access spawning hundreds of forks; root cause is missing the fan-out threshold check before forking; debug via memory.concretization_forced_total vs. executor.fork_total ratio; signal is fork rate exceeding the scheduler's fairness budget (§4); recovery is enforcing the concretization policy's threshold unconditionally, never bypassable per call site. Path explosion from pointer-driven forking compounding with branch forking (Phase 6) — detect via combined fork-rate telemetry; recover via P8's quota enforcement applying uniformly to both fork sources. Page leak accumulation when COW refcounts are decremented on the wrong path during a failed fork rollback — detect via I10's underflow assertion (inverted: an over-count leak shows as pages never reclaimed); recover via a page-table audit tool (tools/wal-inspect.rs extended to page-table dumps).

16.7 Performance Concerns

TLB-like cache misses from a naive page-table walk on every symbolic access — cache the last N resolved page translations per ExecutionState (small direct-mapped cache, sized from §4's RSS budget). Snapshot amplification when compressed pages are recompressed on every checkpoint instead of reusing prior compression — dedup by content hash before compressing (P4). Copy-on-write overhead on high fork-rate workloads — batch refcount increments per fork rather than per page.

16.8 Edge Cases

Overlapping writes across a page boundary must split correctly into two COW operations, not corrupt the neighboring page. Unaligned reads spanning two pages must reassemble correctly under symbolic byte values. Symbolic page indices (an entire page number under symbolic control) must route through the concretization policy before any page-table lookup, never index a native array with a symbolic value directly.

16.9 Failure Analysis

Memory corruption contaminates the entire replay lineage from that point forward — because I9 depends on identical page-fault sequences, a single wrong concretization decision diverges every descendant state. Detection: memory.page_checksum_mismatch_total; containment is per-lineage (P11's immutable snapshot chain lets the divergence point be identified by binary search over checkpoints); recovery is restoring the last checkpoint before the divergence and re-executing.

16.10 Operational Notes

Monitor memory.page_churn_rate and memory.concretization_frequency. Span: memory.page_fault. Log field: page_ref. Rollback note: a memory-model schema change (adding a permission bit) requires a checkpoint format MINOR bump (§25) since old checkpoints remain readable with a default.

17. Phase 5 — SMT Solver Integration Layer

17.1 Objectives

Integrate incremental SMT solving over dual backends (Z3, Bitwuzla, ADR-22) behind a stable trait (§11 SolverBackend). This phase introduces the constraint that every solver response must carry version/backend/timeout metadata (I5) so later differential validation (Phase 9) can attribute a result to its source.

17.2 Detailed Implementation Steps

Define the solver abstraction trait in crates/solver/src/lib.rs matching §11's SolverBackend. Integrate the Z3 backend (crates/solver/src/z3.rs) via its C API, following the encoding patterns in Kroening & Strichman (§5 Books, ch. 2-4). Integrate the Bitwuzla backend (crates/solver/src/bitwuzla.rs) for bitvector/array-theory cross-validation. Implement solver pooling (crates/solver/src/pool.rs) with a bounded worker-local pool (ADR-08, P4). Support incremental assertions via push/pop context reuse keyed by constraint-prefix hash (P10, I11). Implement timeout handling with hard per-query and per-path cumulative budgets (§4 p95/p99). Add solver result caching (crates/solver/src/cache.rs) keyed by canonicalized AST hash (I6), bounded LRU (P4). Extract unsat cores on UNSAT responses for use in constraint minimization (Mayhem's exploit pipeline, §5 Papers). Support model replay — a SAT witness is stored alongside the ConstraintSet so replay does not need to re-solve (P6).

17.3 Deliverable

A production-capable SMT abstraction layer (crates/cli solve <query.smt2> --backend z3) usable standalone against conformance/solver/* fixtures.

17.4 Acceptance Criteria

p95 solve latency < 50 ms and p99 < 250 ms (§4) measured over the conformance/solver/* corpus at 10,000 queries; cache hit rate exceeds 40% (§4) on the repeated-prefix benchmark in benchmarks/solver_latency.rs.

17.5 Conformance Fixtures

conformance/solver/unsat_core_01.smt2 — exercises unsat-core extraction correctness. conformance/solver/timeout_case_02.smt2 — a deliberately hard query, exercises timeout escalation from p95 to p99 budget. conformance/solver/incremental_pushpop.smt2 — exercises push/pop context reuse across a fork boundary.

17.6 Pitfalls

Solver starvation when one worker's long-running query blocks the shared pool — manifestation is rising scheduler.queue_depth unrelated to executor load; root cause is a pool without per-query timeout enforcement; debug via solver.pool_wait_time_seconds; signal is pool-wait exceeding the p99 budget; recovery is a hard per-query timeout that always fires, even under backend hangs. Stale cache entries surviving a solver-version upgrade — root cause is the cache key omitting solver version (violates I5); detect via cross-version differential mismatches; recover by including solver version in the cache key. Timeout amplification when incremental context reuse causes a timed-out query's partial state to poison the next push — detect via anomalous UNKNOWN rates after a timeout; recover by discarding the incremental context (not just the query) on any timeout.

17.7 Performance Concerns

Solver process contention when Z3 and Bitwuzla compete for the same CPU cores — pin solver subprocesses to NUMA-local cores distinct from executor threads (§4 NUMA assumptions). Serialization overhead converting the internal AST to SMT-LIB v2 on every query — cache the serialized form alongside the AST hash, invalidate only on structural change.

17.8 Edge Cases

UNKNOWN responses (solver gives up, not timeout) must be distinguished from timeouts in telemetry and must not be cached as either SAT or UNSAT. Inconsistent backend models (Z3 says SAT, Bitwuzla says UNSAT on the same query) must trigger an immediate differential-validation alert, never be silently resolved by picking one. Distributed SMT result sharing across workers is out of scope for this phase — a shared cross-worker cache is deferred (PhaseDeferred("§17")) pending the distributed coordination work in Phase 7, and GPU-assisted bit-blasting is deferred for the same reason: neither is needed to meet the p95/p99 budget with the CPU-only dual-backend pool at current worker counts.

17.9 Failure Analysis

Solver instability blocks exploration globally when the shared pool exhausts its budget — detection via solver.pool_exhaustion_total; blast radius is every worker sharing that pool, so pools are scoped per-worker (P12), not shared cluster-wide, specifically to bound this blast radius.

17.10 Operational Notes

Emit backend-specific metrics (solver.z3.latency_seconds, solver.bitwuzla.latency_seconds) and timeout histograms (solver.timeout_histogram). Span: solver.check_sat. Log field: solver_epoch (I11). Migration note: adding a third backend requires extending the SolverBackend trait and is a MINOR compatibility change (§25) as long as existing cache entries remain valid.

18. Phase 6 — Symbolic Executor Core

18.1 Objectives

Execute symbolic instructions safely and deterministically over the canonical IR (Phase 2): register semantics, branch forking, constraint generation, syscall modeling. This phase introduces the constraint that every fork must preserve I1 (stable constraint order) across both branches.

18.2 Detailed Implementation Steps

Implement register semantics in crates/executor/src/registers.rs enforcing I3 (symbolic registers cannot alias concrete memory) at the type level via SymbolicValue (§11). Execute arithmetic instructions by dispatching lifted IR nodes through the symbolic AST engine (Phase 3), producing new SymbolicExpr nodes rather than mutating in place (P1). Implement branch forking in crates/executor/src/fork.rs: a conditional branch on a symbolic predicate produces two ExecutionStates sharing COW memory (Phase 4, I10) and disjoint ConstraintSet extensions, following KLEE's fork model (Cadar et al., 2008, §5 Papers). Integrate constraint generation so every fork appends exactly one assertion per side, preserving I1's insertion-order guarantee. Implement syscall modeling in crates/executor/src/syscall.rs — a bounded POSIX subset (read, write, open, mmap, exit) with symbolic-argument support; unmodeled syscalls produce an explicit Unmodeled diagnostic, not a silent no-op. Support environment injection (argv/envp as symbolic or concrete per run configuration). Add path metadata (LineageMetadata, §11) updated on every fork. Define execution quotas per P8 — a per-path instruction budget and a per-worker fork budget, enforced in crates/scheduler/src/fairness.rs (forward reference, Phase 7). Implement interrupt handling for quota exhaustion and external cancellation, both routed through the same termination path as a normal TERMINATED transition (§8 state machine).

18.3 Deliverable

A runnable symbolic execution runtime (crates/cli explore <binary> --max-paths 1000) that forks, executes, and terminates paths against conformance/executor/* fixtures.

18.4 Acceptance Criteria

Deterministic replay passes on 100% of conformance/executor/* fixtures (identical fork sequence and constraint sequence across 10 repeated runs); branch-coverage metrics are operational, exposing executor.branch_coverage_ratio per run.

18.5 Conformance Fixtures

conformance/executor/branch_maze.bin — 20 nested conditionals, exercises fork-rate budgeting under P8. conformance/executor/arithmetic_overflow.bin — signed/unsigned overflow, exercises flags-register correctness from Phase 2. conformance/executor/syscall_stub.bin — calls an unmodeled syscall, expects the Unmodeled diagnostic path, not a crash.

18.6 Pitfalls

Branch explosion from a tight loop with a symbolic trip count — manifestation is fork rate spiking past the scheduler's fairness budget within seconds; root cause is no loop-bound heuristic before Phase 7's quota enforcement is wired in; debug via executor.fork_total rate; signal is queue saturation (§4, 80%) reached from a single path; recovery is P8's per-path fork budget triggering termination with a QuotaExceeded diagnostic, not an unbounded hang. Invalid concretization when the concretization policy (Phase 4) is bypassed by a direct pointer-arithmetic fast path — detect via I3's alias-violation assertion; recover by removing the fast path, routing all symbolic address computation through crates/memory/src/concretize.rs. Nondeterministic syscalls (e.g. gettimeofday) leaking real wall-clock values into a symbolic execution — detect via I9 divergence on replay; recover by routing all such syscalls through DeterministicClock (P1, ADR-19), consistent with Phase 0's runtime kernel.

18.7 Performance Concerns

Fork amplification when combined branch and pointer-driven forking (Phase 4) compound — apply P8's quota uniformly across both fork sources, tracked by a single counter per path. Branch-predictor instability in the interpretive dispatch loop from unpredictable opcode sequences — batch-dispatch common opcode sequences (arithmetic chains) to reduce per-instruction dispatch overhead and protect the p50 instruction-latency budget (§4, < 3 µs).

18.8 Edge Cases

Symbolic syscall arguments (e.g. a symbolic file descriptor) must route through concretization before the syscall model executes, never index a native table with a symbolic value. Unsupported instructions (unlifted opcodes reaching the executor) must terminate that path with a diagnostic, never silently skip the instruction. Nested exceptions (a fault during fault handling, e.g. a page fault while resolving a symbolic address for another page fault) must be bounded by a recursion depth cap. Symbolic SIMD execution, kernel-mode symbolic execution, and a symbolic networking stack are explicitly out of scope for this phase and are deferred (PhaseDeferred("§18")) — none is required to reach the Phase 0-6 production-single-machine milestone (§1 timeline).

18.9 Failure Analysis

Execution divergence invalidates crash artifacts — if two runs of the same lineage diverge, the crash that triggered replay may not be the crash reproduced. Detection: I9's replay comparator; containment is per-lineage; recovery escalates to Phase 9's differential-validation harness to distinguish executor bugs from solver nondeterminism.

18.10 Operational Notes

Emit per-path metrics (executor.path_duration_seconds, executor.fork_total). Expose replay lineage IDs in every log line touching an ExecutionState (P5). Span: executor.step. Deployment note: the per-path instruction quota is a worker startup flag; changing it mid-campaign requires a rolling restart (§24 rolling-upgrade strategy), not a hot reload.

19. Phase 7 — Scheduler & Distributed Coordination

19.1 Objectives

Scale symbolic execution horizontally: work queues, worker leasing, heartbeats, work stealing, fairness. This phase introduces the constraint that no two workers may ever hold a lease on the same path_id simultaneously (I7).

19.2 Detailed Implementation Steps

Implement work queues in crates/scheduler/src/queue.rs using crossbeam lock-free structures (ADR-08) sized to the queue-saturation threshold (§4, 80%). Define the worker-leasing protocol in crates/scheduler/src/lease.rs: a SchedulerLease (§11) is granted via compare-and-swap admission into the lease registry, enforcing I7 structurally rather than by convention. Implement heartbeats — workers renew lease_expiry on a fixed interval; a missed heartbeat triggers lease revocation and requeue, following the crash-only recovery principle (P3). Support work stealing across NUMA nodes with a preference for node-local steals first (§4 NUMA assumptions), informed by Herlihy & Shavit's contention-reduction techniques (§5 Books, ch. 9-10). Add priority scheduling — coverage-driven path prioritization following KLEE's search heuristic (Cadar et al., 2008, §5 Papers). Implement fairness metrics (crates/scheduler/src/fairness.rs) tracking per-worker time-share skew against the < 5% budget (§4). Support path-pruning policies (duplicate-state detection via lineage hash) to avoid re-exploring an already-visited symbolic state. Add distributed cancellation — a coordinator can revoke a lease and signal the holding worker to abort mid-path, tested against conformance/scheduler/lease_expiry.json.

19.3 Deliverable

A distributed execution coordinator (crates/cli coordinate --workers 50) managing a live worker fleet against conformance/scheduler/* fixtures.

19.4 Acceptance Criteria

500 concurrent workers remain stable (§4 ceiling) for a 1-hour soak test with zero coordinator restarts; zero duplicate path execution observed across the soak (I7 held with no violations, measured by scheduler.duplicate_lease_total staying at 0).

19.5 Conformance Fixtures

conformance/scheduler/scheduler_contention.json — 500 simulated workers contending for one queue, exercises lock-free queue throughput. conformance/scheduler/lease_expiry.json — a worker that stops heartbeating, exercises revocation-and-requeue. conformance/scheduler/duplicate_work.json — a crafted race attempting a double-lease, expects rejection via I7's CAS admission.

19.6 Pitfalls

Lease races when two coordinator replicas both believe they hold registry write authority — manifestation is a duplicate lease slipping past the CAS check; root cause is a split-brain coordinator (no consensus layer in Phase 0-7); debug via scheduler.duplicate_lease_total; signal is any nonzero count; recovery is treating a duplicate as fatal — kill both leaseholders and requeue the path, never attempt to reconcile which one is "right." Queue starvation under skewed path priority when coverage-driven prioritization always favors the same subtree — detect via fairness skew (§4, 5%) exceeding budget; recover via the fairness module's forced round-robin fallback above a skew threshold. Duplicate scheduling from a heartbeat-timeout false positive under transient network delay (§4 assumes < 2 ms RTT; a spike violates this) — detect via revoke-then-still-alive telemetry; recover by requiring the revoked worker to self-terminate on next heartbeat attempt rather than silently continuing (protects I7 even under the false positive).

19.7 Performance Concerns

Coordinator bottlenecks as worker count approaches the 500 ceiling (§4, §29) — shard the lease registry by path-ID hash range to parallelize CAS admission. Queue lock contention under high fork rates from Phase 6 — lock-free MPMC queues (ADR-08) bound this, but batching lease grants (grant N paths per request) further reduces registry round-trips.

19.8 Edge Cases

Worker crash mid-solve must release its lease within the heartbeat-timeout window, not hang the path indefinitely. Split-brain coordinator (two replicas both active) must be detected via a fencing token on every lease grant, not assumed away. Path merging heuristics, speculative parallel exploration, distributed state-space reduction, and inter-region execution are deferred (PhaseDeferred("§19")) — each requires coordination machinery (path-merge correctness proofs, speculative-cancellation cost bounds, cross-node consensus) beyond this phase's single-region, lease-based design.

19.9 Failure Analysis

Scheduler corruption can orphan symbolic states — a lost lease with no revocation leaves a path permanently unexecuted. Detection: a periodic reconciliation sweep comparing the lease registry against the path-queue's expected total; blast radius is bounded to orphaned paths, not the whole fleet, because leases are per-path, not per-worker-batch.

19.10 Operational Notes

Emit queue-depth metrics (scheduler.queue_depth) and fairness histograms (scheduler.fairness_skew_ratio). Span: scheduler.lease_grant. Rolling-upgrade note: draining workers before a coordinator upgrade requires freezing new lease grants first (§24), then waiting for in-flight leases to expire naturally — never force-revoking during a planned upgrade.

20. Phase 8 — Snapshotting, WAL & Deterministic Replay

20.1 Objectives

Implement durable, deterministic recovery: append-only WAL, checkpoint serialization, snapshot compression, replay reconstruction. This phase introduces the constraint that no checkpoint may become visible before its WAL segment is fsynced (I4).

20.2 Detailed Implementation Steps

Implement the append-only WAL in crates/storage/src/wal.rs following RocksDB's write-then-memtable pattern (§5 Reference Implementations) adapted for SnapshotRecord (§11) instead of key-value pairs. Implement checkpoint serialization (crates/storage/src/checkpoint.rs) enforcing I8 (append-only descriptors) and I4 (WAL-before-publish ordering) as two separate assertions, not one combined check, so each has an independent telemetry signal. Add snapshot compression (crates/storage/src/compression.rs) using zstd targeting the > 3:1 ratio (§4, an unnumbered decision — no dedicated ADR row governs codec choice) on deduplicated COW pages (Phase 4). Implement replay cursor reconstruction in crates/replay/src/reconstruct.rs — given a snapshot_id, walk parent_snapshot links (§11) to rebuild the full lineage. Implement deterministic rehydration: replaying a lineage must reproduce an identical AST-hash sequence (I9). Add crash-artifact generation — a minimized reproduction bundle (binary hash, constraint set, model witness) for any TERMINATED-with-fault path. Implement lineage reconstruction (crates/replay/src/lineage.rs) cross-referencing LineageMetadata against the WAL. Add corruption detection — checksum verification (P9) on every page read, gating this phase's WAL-recovery acceptance criterion below.

20.3 Deliverable

Crash-safe replay infrastructure (crates/cli replay <snapshot_id>) that reconstructs and re-executes a lineage from durable storage against conformance/replay/* fixtures.

20.4 Acceptance Criteria

Replay divergence rate < 0.1% (§4) measured over 10,000 replayed lineages; WAL recovery completes in < 90 seconds (§4) for a 500-worker fleet's last checkpoint interval; checkpoint restore < 3 seconds per worker (§4).

20.5 Conformance Fixtures

conformance/replay/wal_truncation.log — a WAL file truncated mid-record, exercises recovery tolerance for a torn final write. conformance/replay/partial_snapshot.chk — a checkpoint missing pages, expects SnapshotError::IncompletePages, not a silent partial restore. conformance/replay/replay_divergence.trace — a known-divergent replay pair, exercises the divergence comparator (I9) end-to-end.

20.6 Pitfalls

Torn writes on process crash mid-fsync — manifestation is a WAL segment with a valid header but a corrupted tail record; root cause is not distinguishing "no record" from "partial record" at recovery time; debug via storage.torn_write_total; signal is any nonzero count during recovery; recovery is treating any partial trailing record as absent, never attempting partial replay of it (P9, fail closed). Snapshot drift when two checkpoints claim the same snapshot_id after a coordinator failover — detect via I2's monotonicity check; recover by rejecting the second writer and forcing it to request a fresh ID range. Lineage corruption from a dangling parent_snapshot reference (the parent was garbage-collected before children were fully persisted) — detect via reconstruction failing to resolve the parent link; recover by pinning ancestor checkpoints until all known children are durable, enforced by a reference-counted retention policy.

20.7 Performance Concerns

Compression CPU overhead competing with executor threads for cycles — pin compression workers to NUMA-local cores distinct from executor threads, same pattern as Phase 5's solver pinning (§4). Replay IO amplification when reconstructing a deep lineage reads far more WAL segments than the final state needs — checkpoint at bounded intervals (not just on-demand) specifically to cap replay depth, trading storage for replay-time predictability.

20.8 Edge Cases

Interrupted fsync (the syscall returns but the underlying device lies about durability) is outside what software can detect directly; mitigate via periodic full-checkpoint verification reads, not by trusting fsync's return value alone. Duplicate WAL sequence numbers (from a coordinator failover race) must be rejected at write time by the monotonicity check (I2), not discovered later at replay. Symbolic filesystem snapshots — persisting a path's simulated filesystem side effects across replay — are deferred (PhaseDeferred("§20")); today only memory and register state are snapshotted, per this phase's scope.

20.9 Failure Analysis

Corrupted replay invalidates debugging workflows entirely — an operator cannot trust any crash artifact until the divergence rate (§4) is within budget. Detection: continuous background replay audits sampling 1% of completed lineages; containment is per-lineage; recovery restores from the nearest verified-good ancestor checkpoint.

20.10 Operational Notes

Emit storage.checkpoint_age_seconds and storage.wal_recovery_duration_seconds. Archive replay artifacts under the same conformance-promotion path as Phase 1's parse failures. Span: replay.reconstruct. Migration note: a WAL record-format change is a MAJOR compatibility bump (§25) because old segments cannot be replayed by a new reader without an explicit shim.

21. Phase 9 — Observability, Fuzzing & Hardening

21.1 Objectives

Deliver production operational visibility and adversarial hardening in one phase: metric taxonomy, trace correlation, differential validation, chaos fault injection, crash minimization. This phase introduces the constraint that every prior phase's acceptance criteria must hold under fault injection, not just under clean-path testing.

21.2 Detailed Implementation Steps

Define the metric taxonomy in crates/telemetry/src/metrics.rs unifying every *_total and *_seconds metric introduced in Phases 0-8 under one naming convention (P5). Implement trace correlation end-to-end — a single trace_id must connect a client request through coordinator, worker, solver, and storage spans. Expose flamegraph tooling via perf + tracing-span export for the profiling methodology in §28. Add runtime introspection endpoints (/debug/paths, /debug/leases) for live operator inspection. Implement structured crash reports combining Phase 8's crash artifacts with symbol information from Phase 1. Add profiling hooks at every crate boundary identified in §3's diagram. Build dashboard templates (templates/dashboards/*.json) for the core metrics. Implement parser fuzzing (fuzz/fuzz_targets/parser_fuzz.rs) extending Phase 1's 24-hour stability gate to a 72-hour campaign. Implement differential execution validation — replaying every path under both Z3 and Bitwuzla (ADR-22) and alerting on disagreement, directly using I5's versioned solver responses. Add random scheduler perturbation and chaos fault injection (worker kill, WAL truncation, network partition) per the chaos-testing strategy in §26. Implement deterministic replay audits sampling completed lineages (extends Phase 8's audit). Add solver mutation tests — deliberately corrupting a cached result to verify I5/I6 detection paths actually fire. Build crash minimization tooling (tools/minimize-crash.rs) using unsat-core-guided constraint reduction (Mayhem's pipeline, Cha et al. 2012, §5 Papers).

21.3 Deliverable

A security-hardened, fully observable platform: crates/cli triage <crash_id> producing a minimized, symbol-annotated crash report, backed by live dashboards from templates/dashboards/*.

21.4 Acceptance Criteria

A 72-hour fuzz campaign across all fuzz targets completes with zero unhandled panics and zero sanitizer findings; replay divergence is eliminated to 0 observed events over the campaign (tighter than Phase 8's < 0.1% steady-state budget, §4); all major state transitions (§8's seven states) are independently observable in the dashboard set.

21.5 Conformance Fixtures

conformance/hardening/malformed_ast.json — a crafted AST violating I6, exercises the hash-collision detection path. conformance/hardening/corrupted_snapshot.chk — a bit-flipped checkpoint, exercises P9's fail-closed checksum gate end-to-end. conformance/hardening/randomized_schedule.trace — a chaos-perturbed schedule, exercises whether I7 holds under adversarial timing.

21.6 Pitfalls

Hidden nondeterminism surviving to this phase despite Phases 0-8's individual guarantees — manifestation is a replay divergence that no single phase's unit tests caught because it only manifests under the combination of chaos perturbation and real timing; root cause is almost always a cross-crate ordering assumption (e.g. Phase 6 assuming Phase 4's page faults resolve in request order under contention); debug via bisecting the chaos-injection seed; signal is a divergence that disappears when chaos injection is disabled; recovery is promoting the minimal reproducing chaos seed into conformance/hardening/ as a permanent regression fixture. Solver inconsistencies surfaced only under sustained differential load (Z3 and Bitwuzla agree on 99.99% of queries but diverge under a specific bitvector-width pattern) — detect via the differential-validation alert; recover by excluding the disagreeing query shape from the cache (never cache a disputed result) and filing it as a solver-specific bug upstream.

21.7 Performance Concerns

Instrumentation overhead from combining profiling hooks, chaos injection, and differential validation simultaneously must not regress the p50/p95 budgets in §4 during normal (non-hardening) operation — all Phase 9 instrumentation is compile-time feature-gated (§12.2 governance) and off by default in production builds, on only in the dedicated hardening-campaign build profile.

21.8 Edge Cases

Replay under partial corruption (some pages checksum-valid, others not) must fail the entire lineage per P9, never attempt a partial reconstruction. Hybrid fuzzing — combining concolic seed generation with this phase's coverage-guided fuzzing — is deferred (PhaseDeferred("§21")); Phase 9 ships pure coverage-guided fuzzing only, per the acceptance criteria above.

21.9 Failure Analysis

Unhardened execution risks silent correctness failures reaching production campaigns undetected — this is the terminal risk the entire phase exists to close out. Detection is the 72-hour campaign itself plus continuous production sampling inherited from Phase 8; blast radius without this phase is unbounded (any prior phase's untested edge case); containment is the fail-closed posture (P9) applied uniformly, so a detected anomaly always halts rather than silently continuing.

21.10 Operational Notes

Archive minimized crashes under conformance/hardening/ for regression promotion. Maintain telemetry schema versioning so dashboard queries survive a metric-name change (§25 additive rule). Span: hardening.differential_check. Metric: hardening.divergence_events_total. Deployment note: the 72-hour campaign runs in CI on a schedule (.github/workflows/fuzz.yml), not on every commit.

24. Operational Readiness

Metrics strategy: core metrics span every crate boundary in §3 — path execution rate, solver latency (per backend, ADR-22), snapshot throughput, replay divergence count, queue saturation, AST pool occupancy. Every metric name follows the <crate>.<noun>_<unit> convention unified in §21.2.

Tracing strategy: every path carries a global trace_id, a lineage_id (replay correlation), and worker correlation metadata, propagated from the Client Interfaces boundary through to storage (§3). Tracing is never optional — it is compiled in and sampled, not feature-flagged off in production, per P5.

Alerting philosophy: page only on replay-divergence spikes exceeding the absolute daily budget derived in §32 (C9), scheduler unavailability (coordinator health-check failure), WAL corruption (any FM-1 event), and sustained solver-timeout saturation (pool-wait time pinned at the p99 ceiling for more than 5 consecutive minutes). Everything else is a dashboard signal, not a page — alert fatigue is treated as a correctness risk to incident response, not a minor annoyance.

Backup strategy: periodic snapshot export to immutable object storage, WAL archival with the same retention window as the checkpoint interval tuning from §32 (C8), and cross-region replication of archived (not live) storage only — live storage stays intra-region per §4's network assumptions.

Rolling upgrade strategy: drain workers (stop accepting new leases), freeze in-flight leases (never force-revoke during a planned upgrade, §19.10), validate replay compatibility against the new binary using a held-out sample of recent checkpoints, then resume execution gradually (canary a small worker percentage before full rollout).

25. Compatibility & Versioning

Wire compatibility: every RPC payload (gRPC/Tonic, ADR-06) is versioned; a coordinator never sends a field a worker's declared version cannot parse, and vice versa via capability negotiation at lease-grant time.

Storage compatibility: every SnapshotRecord (§11) includes a schema version, solver-backend metadata (I5), and compression metadata. A reader must reject a snapshot whose schema version it does not recognize rather than guess a compatible layout (P9).

Semantic versioning: MAJOR — any change breaking replay compatibility (e.g. a WAL record-format change, §20.10) or removing a SolverBackend trait method. MINOR — additive protocol changes that old readers can ignore safely (e.g. a new optional memory-permission bit, §16.10, provided it defaults to a value that preserves old-checkpoint semantics). PATCH — bugfix only, no schema or wire-format change.

26. Testing & Verification Strategy

Unit testing required for: AST semantics (Phase 3), parser correctness (Phase 1), replay determinism (Phase 8) — each crate's public API has a dedicated unit-test module exercising every conformance/ fixture at least once.

Integration testing: distributed scheduler behavior under simulated worker churn (Phase 7), solver interoperability across Z3 and Bitwuzla (Phase 5), replay recovery from a corrupted WAL (Phase 8) — run via cargo-nextest (ADR-12) for isolation across shared arena state.

29. Scalability Analysis

Bottlenecks, in expected binding order as worker count rises toward the 500 ceiling (§4): SMT solving (per-worker, bounded by p95/p99 latency, §17), scheduler coordination (lease-registry CAS throughput, §19), snapshot serialization (WAL write bandwidth, §20).

Horizontal scaling: workers scale independently until scheduler coordination saturation (lease registry becomes the shared serialization point) or shared storage contention (WAL write bandwidth ceiling, §32 C5) binds first — whichever bottleneck's headroom (§32 C11-equivalent sizing) is smaller at a given cluster size.

Metadata scaling: lineage metadata (LineageMetadata, §11) grows superlinearly under branch explosion because every fork appends to every descendant's ancestry chain. Mitigation: compression of ancestry chains and deduplicated-ancestry storage (shared prefix runs stored once, referenced by offset) — the same deduplication principle as COW page sharing (I10), applied to metadata instead of data.

30. Mental Models & First Principles

  • MM1 — Path Explosion Is Multiplicative. Fork count compounds across branch forking (Phase 6) and pointer-driven forking (Phase 4) as independent multipliers, not a single additive rate. Predicts a binary with both symbolic branches and symbolic pointers explodes faster than either alone. Without it: engineers budget worker RSS from branch count only and are blindsided by pointer-driven OOM. Applies in §16 and §18.
  • MM2 — Determinism Is a Type, Not a Testing Practice. If a wall-clock read or unordered-map iteration is reachable from the hot path, no test-suite discipline restores replay. Predicts replay bugs cluster around "happens to be nondeterministic" APIs, not logic errors. Without it: engineers chase a Heisenbug in the executor when the real bug is three crates away. Applies in §12 and §20.
  • MM3 — A Lease Is a Timeout, Not an Assignment. Any leasing protocol must assume the leaseholder is dead until proven otherwise by heartbeat. Predicts naive "assign and wait forever" designs double-execute under partition. Without it: coordinator code has no missed-heartbeat path because "it shouldn't happen." Applies in §19.
  • MM4 — Incrementality Trades Memory for Latency, Never Removes the Tradeoff. Reused solver contexts save re-assertion cost but pin memory across the reuse window. Predicts aggressive incrementality without epoch invalidation leaks solver RSS over long campaigns. Without it: a slow OOM over days gets misdiagnosed as a solver bug instead of a pooling-policy bug. Applies in §17.
  • MM5 — WAL-Then-Publish Is the Only Honest Order. A crash-safety claim untested by real crashes is untested by definition. Predicts skipping fsync-before-publish "for performance" fails only under real outages, never clean-shutdown tests. Without it: a system passes every graceful-shutdown test and loses data on every real one. Applies in §20.
  • MM6 — A Verifier Is Cheaper Than the Bugs It Prevents, Amortized. IR verification is paid once per lift; an unverified semantic bug is paid by every downstream path forever. Predicts skipping the verifier "for speed" looks free until path count crosses into the hundreds. Without it: a wrong flags-register model is discovered only after months of unexplained divergence. Applies in §14.
  • MM7 — Fail-Closed Beats Fail-Open When Silent Wrongness Costs More Than Availability. In a correctness tool, a false "no bug found" is worse than a crash. Predicts any best-effort recovery path converts a detectable failure into an undetectable one. Without it: an operator trusts a "clean" campaign that silently dropped a corrupted lineage. Applies in §16 and §20.
  • MM8 — Backpressure Is a Correctness Mechanism Here, Not Just a Performance One. Without bounded queues/caches, resource exhaustion and correctness failure become the same event. Predicts unbounded growth eventually corrupts state, not just slows it. Without it: an OOM-adjacent corruption gets attributed to "bad luck" instead of a missing bound. Applies in §18 and §19.

32. Back-of-Envelope Capacity Model

  • C1 — Average State Footprint. Registers (~2 KB) + COW page-table entries (200 pages × 32 B = 6.4 KB) + ConstraintSet (50 assertions × 64 B = 3.2 KB) = 11.6 KB/state, rounded up for allocator overhead to ≈ 16 KB/state.
  • C2 — Worker RSS Ceiling Check. 250,000 states/worker (§4) × 16 KB/state (C1) = 4.0 GB, plus a 2 GB hash-consing arena and 1.5 GB solver-pool RSS = 7.5 GB, inside the 8 GB §4 ceiling.
  • C3 — SMT Cache RAM. 500,000 cached queries × (16 B AST hash + 128 B result/backend/version metadata = 144 B/entry) = 72 MB/worker, negligible against the 8 GB ceiling; cache sizing is bounded by hit-rate utility (P4), not RAM pressure.
  • C4 — Solver Throughput Needed. 250,000 states/worker ÷ 40 forks-per-solve average path length = 6,250 solver calls/worker; at the §4 60% cache-miss share that is 6,250 × 0.6 = 3,750 calls × 50 ms p95 (§4) = 187.5 s of solver-bound wall clock per full-depth worker campaign.
  • C5 — WAL Write Throughput. 500 workers (§4) × (300,000 instr/s ÷ 10,000 instr/checkpoint = 30 checkpoints/s/worker) × 64 KB/checkpoint (compressed at > 3:1, §4) = 960 MB/s aggregate WAL write demand.
  • C6 — Cluster Fleet Memory. 500 workers (§4) × 8 GB RSS ceiling (C2) = 4.0 TB aggregate worker memory, the sizing input for the Kubernetes node pool (§1 deployment model).
  • C7 — FD Budget Check. 8,192 FDs/worker (§4) − (4,000 COW page mmaps + 10 solver pipes + 20 WAL segment handles + 5 telemetry sockets = 4,035) = 4,157 FDs of headroom per worker before the ceiling binds, validating that C2's 250,000-state target does not FD-starve first.
  • C8 — WAL Recovery Time Check. 90 s recovery budget (§4) × 960 MB/s aggregate write demand (C5) = 86.4 GB of recoverable WAL window per coordinator restart before recovery time itself becomes the bottleneck.
  • C9 — Replay Divergence Budget in Absolute Terms. 0.1% divergence rate (§4) × 10,000 lineages/day assumed campaign volume = 10 divergent lineages/day tolerated before the Phase 9 alerting threshold trips (§24).
  • C10 — Snapshot Storage Growth. 960 MB/s aggregate WAL write demand (C5) × 86,400 s/day = 82.9 TB/day raw before retention pruning, forcing the backup strategy (§24) to prune aggressively rather than archive everything.

Rejected for the Phase 0-8 core: this blueprint prioritizes exhaustive, deterministic path exploration with replay guarantees (P6) before adding a concolic front-end. Hybrid fuzzing is deferred (§35, anchor §21), not rejected outright — it is a Phase 9+ extension once the exploration core is proven.

36. Glossary

  • Symbolic State — execution state whose registers/memory contain symbolic variables rather than only concrete values.
  • Path Explosion — exponential growth in the number of execution branches under exploration.
  • Concretization — converting a symbolic value to a concrete witness, typically via a solver query.
  • Constraint Set — the ordered collection of assertions accumulated along one execution path.
  • Replay Divergence — a mismatch between a recorded execution and its deterministic replay.
  • SSA — Static Single Assignment, an IR form where each variable is assigned exactly once.
  • WAL — Write-Ahead Log, an append-only durability mechanism written before state is published.
  • Unsat Core — the minimal contradictory subset of constraints proving unsatisfiability.
  • Path Fork — the branching of one symbolic state into two or more descendant states.
  • Snapshot Lineage — the parent-child chain of checkpoints leading to a given state.
  • Solver Epoch — a versioned generation counter for a path's incremental solver context.
  • IR — Intermediate Representation, the canonical architecture-independent instruction form.
  • AST — Abstract Syntax Tree, the hash-consed symbolic expression representation.
  • Lease — a time-bounded scheduler ownership token granting exclusive execution rights.
  • Trace ID — a correlated observability identifier spanning coordinator, worker, and storage.
  • Guard Page — an unmapped memory page that traps on access, used for bounds detection.
  • Work Stealing — dynamic redistribution of queued work from busy to idle workers.
  • Symbolic Pointer — a memory address represented as a symbolic expression rather than a concrete value.
  • Checkpoint — a persisted, durable copy of an execution state.
  • Deterministic Replay — re-execution that reproduces an identical AST-hash sequence.
  • Hash-Consing — a technique for structurally deduplicating equal expressions into one shared node.
  • Copy-on-Write (COW) — a memory-sharing scheme that defers copying a page until it is written.
  • Dominance Tree — the CFG structure recording which basic blocks always execute before others.
  • Basic Block — a maximal straight-line instruction sequence with one entry and one exit.
  • CFG — Control Flow Graph, the graph of basic blocks and their branch edges.
  • Incremental Solving — reusing a solver context across related queries via push/pop.
  • Push/Pop Context — the SMT-LIB mechanism for entering/exiting a nested assertion scope.
  • Fairness Skew — the deviation from equal worker time-share in the scheduler.
  • Backpressure — a bounded-resource signal that slows or rejects new work under saturation.
  • Fencing Token — a monotonically increasing token preventing a stale leaseholder from acting.
  • Differential Validation — cross-checking a result across two independent implementations (e.g. Z3 vs. Bitwuzla) to detect implementation-specific bugs.
  • Crash Triage — the process of classifying and prioritizing discovered crashes.
  • Testcase Minimization — reducing a crashing input to its smallest reproducing form.
  • Split-Brain — a state where two coordinator replicas both believe they hold sole authority.
  • Torn Write — a partially completed disk write left inconsistent by a crash mid-write.
  • Page Deduplication — storing one copy of identical memory pages shared across states.
  • Relocation — a directive adjusting an address reference at load time.
  • Symbol Table — the ELF structure mapping names to addresses and metadata.
  • ELF — Executable and Linkable Format, the binary format parsed in Phase 1.
  • SMT-LIB — the standard input language/format for SMT solvers.
  • Bitvector Theory — the SMT theory modeling fixed-width binary integers.
  • Model Witness — a concrete satisfying assignment returned by a solver for a SAT query.
  • Flags Register — the CPU register holding condition codes (ZF, CF, OF, SF) after arithmetic.
  • Concolic Execution — hybrid concrete-plus-symbolic execution used to guide input generation.
  • Coverage-Guided Fuzzing — fuzzing that prioritizes inputs expanding observed code coverage.
  • RTO/RPO — Recovery Time Objective / Recovery Point Objective, the availability budget terms used in §4 and §24.
  • NUMA Pinning — binding a thread/process to CPU cores local to a specific memory node.
