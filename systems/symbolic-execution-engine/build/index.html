⬜ Phase 0 — Repository Foundation & Deterministic Runtime Kernel §12

Objectives

Stand up the Cargo workspace, lint/format gates, and the deterministic runtime primitives every later crate depends on: clock abstraction (P1), typed configuration, structured logging facade, panic policy, and worker lifecycle supervision. This phase introduces the constraint that no later crate may read SystemTime or iterate a HashMap on a path observable in replay.

Deliverable

A deterministic executable runtime (crates/cli run --dry-run) that spawns a supervised worker, loads config from conformance/runtime/config_invalid.toml-shaped input, emits OTLP traces, and terminates cleanly on SIGTERM within the shutdown budget.

Acceptance

Deterministic integration tests (10 consecutive runs, identical trace-ID sequence modulo the ID values themselves) pass; startup completes in < 5 seconds (§4); reproducible binaries verified via scripts/repro-build.sh producing a byte-identical hash across two clean builds; telemetry visible in a local Prometheus scrape within 10 seconds of startup.

Fixtures

conformance/runtime/config_invalid.toml — malformed config, expect ConfigError::UnknownKey. conformance/runtime/clock_replay.json — records 1,000 logical ticks, expects byte-identical replay. conformance/runtime/shutdown_stress.rs — spawns 50 workers and SIGTERMs them concurrently, expects zero panics and shutdown < 20 seconds (§4).

Pitfalls

Nondeterministic timestamps leaking into log lines via a default tracing formatter that calls SystemTime::now() — root cause is the default subscriber, not application code; detect via a clippy lint forbidding SystemTime outside crates/telemetry; recover by routing all timestamps through DeterministicClock. Inconsistent span IDs across process restarts — root cause is PID-seeded ID generation; detect via duplicate trace_id alerts; recover by seeding from a monotonic counter persisted in config. Hidden global state (lazy_static config singletons) breaking multi-worker test isolation — detect via cargo-nextest flakiness; recover by threading config explicitly. Allocator drift between debug and release builds changing fragmentation behavior — detect via benchmarks/instruction_throughput.rs variance; recover by pinning mimalloc in both profiles.

⬜ Phase 1 — ELF Parser & Binary Loader §13

Objectives

Implement robust ELF binary parsing and validation ahead of the trust boundary (§3): headers, sections, relocations, symbol tables, segment mapping. This phase introduces the constraint that no malformed input may reach the lifter (P9, fail-closed).

Deliverable

A loader (crates/cli load <binary>) capable of mapping ELF binaries into symbolic memory and printing a validated section/segment/symbol summary.

Acceptance

GNU coreutils fixtures (examples/coreutils_ls.elf, examples/coreutils_cat.elf) parse successfully with zero diagnostics; the malformed corpus (§13.5) is rejected 100% of the time with a typed error, never a panic; the parser fuzz suite (fuzz/fuzz_targets/parser_fuzz.rs) runs stable for 24 hours with zero crashes and zero sanitizer findings.

Fixtures

conformance/parser/malformed_relocation_01.elf — relocation offset past section end, expect ParseError::InvalidRelocation. conformance/parser/invalid_alignment_02.elf — misaligned segment, expect ParseError::AlignmentViolation. conformance/parser/stripped_binary_03.elf — no symtab, expect successful parse with symbols: None, not an error.

Pitfalls

Integer overflow in section-offset arithmetic on 32-bit-hosted builds — manifestation is a wrapped offset that reads past the buffer; root cause is unchecked u32 addition; debug via cargo-fuzz with overflow sanitizers enabled; signal is an ASAN heap-buffer-overflow report; recovery is checked arithmetic (checked_add) with a ParseError on overflow. Invalid relocation loops (a relocation that targets itself) causing unbounded cache growth — detect via the relocation-cache size watchdog; recover by capping resolution depth and rejecting cyclic chains. Unbounded section allocation from a crafted section-count field — detect via the FD/RSS budget in §4; recover by capping section count before allocation.

⬜ Phase 2 — Intermediate Representation & Lifting §14

Objectives

Construct an architecture-independent canonical IR from parsed x86_64 binaries: SSA-like form, CFG, dominance metadata, and a verifier that runs on every build (P7). This phase introduces the constraint that every IR transformation must be proven semantics-preserving before merge.

Deliverable

An instruction-lifting pipeline (crates/cli lift <binary>) producing deterministic IR graphs with a passing verifier report for every function reached from the entry point.

Acceptance

IR verifier passes on 100% of conformance/ir/* fixtures; replay hashes are stable across 3 consecutive lift runs of the same binary (byte-identical IR-node hash sequence); CFG edge coverage exceeds 95% against a objdump-derived ground truth for the coreutils fixture set.

Fixtures

conformance/ir/branch_loop.bin — a tight backward-branch loop, exercises dominance-tree cycles. conformance/ir/self_modifying.bin — expect explicit rejection (LiftError::SelfModifyingCode), not silent misdisassembly. conformance/ir/indirect_jump.bin — exercises CFG-edge inference for jump tables.

Pitfalls

Incorrect flag semantics (e.g. modeling ZF update on AND but forgetting CF/OF clearing) — manifestation is a downstream symbolic-executor branch that takes the wrong path only under specific bit patterns; root cause is copying x86 flag tables from memory instead of the ISA manual; debug via differential testing against a reference disassembler; signal is a branch-coverage gap in §14.4's 95% target; recovery is a per-opcode flags unit-test matrix. Unstable IR node ordering across two lifts of the same function — root cause is iterating a HashMap of basic blocks; detect via I9-style hash-sequence comparison; recover by switching to IndexMap/BTreeMap (P1). Invalid SSA construction on irreducible CFGs (from computed gotos) — detect via the verifier's dominance check failing; recover by node-splitting per Cooper & Torczon ch. 9.

⬜ Phase 3 — Symbolic Expression Engine §15

Objectives

Implement the symbolic AST infrastructure — hash-consed, canonicalized, simplifiable — that every later symbolic value in the system is built from (§11). This phase introduces the constraint that AST hashes must be stable cross-process for the SMT cache (P4, P10) to be useful at all.

Deliverable

A canonical symbolic AST engine (crates/cli simplify <expr.json>) that ingests raw expression JSON and emits a canonicalized, simplified, hash-stamped AST.

Acceptance

AST hash stability is guaranteed across 1,000 repeated canonicalizations of the same input (bit-identical hash field); the simplifier reduces benchmark constraint size by more than 20% on the conformance/ast/* corpus, measured in node count pre/post simplification.

Fixtures

conformance/ast/arithmetic_expr.json — nested arithmetic, exercises constant folding. conformance/ast/nested_concat.json — deep concat/extract chains, exercises collapse rules. conformance/ast/overflow_case.json — bitvector width mismatch, expect ExprError::WidthMismatch.

Pitfalls

Expression explosion from unbounded constant propagation through nested concats — manifestation is a single path's ConstraintSet growing past the arena's practical size before any fork; root cause is a simplification rule that expands before it contracts; debug via arena-occupancy telemetry; signal is ir.arena_occupancy_bytes trending toward the RSS budget (§4); recovery is a depth cap on recursive simplification with a PhaseDeferred fallback to unsimplified form. Unstable hashes from including non-canonical operand order in commutative ops — detect via I6's hash-collision audit; recover by enforcing a total order on operands before hashing. Recursive simplifier loops (a rewrite rule that re-triggers itself) — detect via a rewrite-count watchdog per expression; recover by capping rewrite iterations and falling back to the unsimplified form with a warning.

⬜ Phase 4 — Symbolic Memory Model §16

Objectives

Implement scalable symbolic virtual memory: paged abstraction, copy-on-write, concretization policy, guard pages, permissions. This phase introduces the constraint that memory replay must be bit-for-bit deterministic (I9) even under symbolic pointer aliasing.

Deliverable

A fully symbolic memory subsystem exercised via crates/cli mem-trace <binary>, printing a page access log with concretization decisions annotated.

Acceptance

Memory replay is deterministic across 100 repeated replays of conformance/memory/symbolic_pointer.bin (identical page-fault and concretization decision sequence); snapshot restore completes in < 3 seconds (§4) for a 250,000-page working set.

Fixtures

conformance/memory/symbolic_pointer.bin — a symbolic array index, exercises concretization threshold logic. conformance/memory/heap_aliasing.bin — two symbolic pointers that may alias, exercises the bounded aliasing set. conformance/memory/partial_write.bin — a write narrower than a page, exercises COW page splitting.

Pitfalls

Aliasing ambiguity — a symbolic pointer's possible target set silently growing unbounded — manifestation is a single memory access spawning hundreds of forks; root cause is missing the fan-out threshold check before forking; debug via memory.concretization_forced_total vs. executor.fork_total ratio; signal is fork rate exceeding the scheduler's fairness budget (§4); recovery is enforcing the concretization policy's threshold unconditionally, never bypassable per call site. Path explosion from pointer-driven forking compounding with branch forking (Phase 6) — detect via combined fork-rate telemetry; recover via P8's quota enforcement applying uniformly to both fork sources. Page leak accumulation when COW refcounts are decremented on the wrong path during a failed fork rollback — detect via I10's underflow assertion (inverted: an over-count leak shows as pages never reclaimed); recover via a page-table audit tool (tools/wal-inspect.rs extended to page-table dumps).

⬜ Phase 5 — SMT Solver Integration Layer §17

Objectives

Integrate incremental SMT solving over dual backends (Z3, Bitwuzla, ADR-22) behind a stable trait (§11 SolverBackend). This phase introduces the constraint that every solver response must carry version/backend/timeout metadata (I5) so later differential validation (Phase 9) can attribute a result to its source.

Deliverable

A production-capable SMT abstraction layer (crates/cli solve <query.smt2> --backend z3) usable standalone against conformance/solver/* fixtures.

Acceptance

p95 solve latency < 50 ms and p99 < 250 ms (§4) measured over the conformance/solver/* corpus at 10,000 queries; cache hit rate exceeds 40% (§4) on the repeated-prefix benchmark in benchmarks/solver_latency.rs.

Fixtures

conformance/solver/unsat_core_01.smt2 — exercises unsat-core extraction correctness. conformance/solver/timeout_case_02.smt2 — a deliberately hard query, exercises timeout escalation from p95 to p99 budget. conformance/solver/incremental_pushpop.smt2 — exercises push/pop context reuse across a fork boundary.

Pitfalls

Solver starvation when one worker's long-running query blocks the shared pool — manifestation is rising scheduler.queue_depth unrelated to executor load; root cause is a pool without per-query timeout enforcement; debug via solver.pool_wait_time_seconds; signal is pool-wait exceeding the p99 budget; recovery is a hard per-query timeout that always fires, even under backend hangs. Stale cache entries surviving a solver-version upgrade — root cause is the cache key omitting solver version (violates I5); detect via cross-version differential mismatches; recover by including solver version in the cache key. Timeout amplification when incremental context reuse causes a timed-out query's partial state to poison the next push — detect via anomalous UNKNOWN rates after a timeout; recover by discarding the incremental context (not just the query) on any timeout.

⬜ Phase 6 — Symbolic Executor Core §18

Objectives

Execute symbolic instructions safely and deterministically over the canonical IR (Phase 2): register semantics, branch forking, constraint generation, syscall modeling. This phase introduces the constraint that every fork must preserve I1 (stable constraint order) across both branches.

Deliverable

A runnable symbolic execution runtime (crates/cli explore <binary> --max-paths 1000) that forks, executes, and terminates paths against conformance/executor/* fixtures.

Acceptance

Deterministic replay passes on 100% of conformance/executor/* fixtures (identical fork sequence and constraint sequence across 10 repeated runs); branch-coverage metrics are operational, exposing executor.branch_coverage_ratio per run.

Fixtures

conformance/executor/branch_maze.bin — 20 nested conditionals, exercises fork-rate budgeting under P8. conformance/executor/arithmetic_overflow.bin — signed/unsigned overflow, exercises flags-register correctness from Phase 2. conformance/executor/syscall_stub.bin — calls an unmodeled syscall, expects the Unmodeled diagnostic path, not a crash.

Pitfalls

Branch explosion from a tight loop with a symbolic trip count — manifestation is fork rate spiking past the scheduler's fairness budget within seconds; root cause is no loop-bound heuristic before Phase 7's quota enforcement is wired in; debug via executor.fork_total rate; signal is queue saturation (§4, 80%) reached from a single path; recovery is P8's per-path fork budget triggering termination with a QuotaExceeded diagnostic, not an unbounded hang. Invalid concretization when the concretization policy (Phase 4) is bypassed by a direct pointer-arithmetic fast path — detect via I3's alias-violation assertion; recover by removing the fast path, routing all symbolic address computation through crates/memory/src/concretize.rs. Nondeterministic syscalls (e.g. gettimeofday) leaking real wall-clock values into a symbolic execution — detect via I9 divergence on replay; recover by routing all such syscalls through DeterministicClock (P1, ADR-19), consistent with Phase 0's runtime kernel.

⬜ Phase 7 — Scheduler & Distributed Coordination §19

Objectives

Scale symbolic execution horizontally: work queues, worker leasing, heartbeats, work stealing, fairness. This phase introduces the constraint that no two workers may ever hold a lease on the same path_id simultaneously (I7).

Deliverable

A distributed execution coordinator (crates/cli coordinate --workers 50) managing a live worker fleet against conformance/scheduler/* fixtures.

Acceptance

500 concurrent workers remain stable (§4 ceiling) for a 1-hour soak test with zero coordinator restarts; zero duplicate path execution observed across the soak (I7 held with no violations, measured by scheduler.duplicate_lease_total staying at 0).

Fixtures

conformance/scheduler/scheduler_contention.json — 500 simulated workers contending for one queue, exercises lock-free queue throughput. conformance/scheduler/lease_expiry.json — a worker that stops heartbeating, exercises revocation-and-requeue. conformance/scheduler/duplicate_work.json — a crafted race attempting a double-lease, expects rejection via I7's CAS admission.

Pitfalls

Lease races when two coordinator replicas both believe they hold registry write authority — manifestation is a duplicate lease slipping past the CAS check; root cause is a split-brain coordinator (no consensus layer in Phase 0-7); debug via scheduler.duplicate_lease_total; signal is any nonzero count; recovery is treating a duplicate as fatal — kill both leaseholders and requeue the path, never attempt to reconcile which one is "right." Queue starvation under skewed path priority when coverage-driven prioritization always favors the same subtree — detect via fairness skew (§4, 5%) exceeding budget; recover via the fairness module's forced round-robin fallback above a skew threshold. Duplicate scheduling from a heartbeat-timeout false positive under transient network delay (§4 assumes < 2 ms RTT; a spike violates this) — detect via revoke-then-still-alive telemetry; recover by requiring the revoked worker to self-terminate on next heartbeat attempt rather than silently continuing (protects I7 even under the false positive).

⬜ Phase 8 — Snapshotting, WAL & Deterministic Replay §20

Objectives

Implement durable, deterministic recovery: append-only WAL, checkpoint serialization, snapshot compression, replay reconstruction. This phase introduces the constraint that no checkpoint may become visible before its WAL segment is fsynced (I4).

Deliverable

Crash-safe replay infrastructure (crates/cli replay <snapshot_id>) that reconstructs and re-executes a lineage from durable storage against conformance/replay/* fixtures.

Acceptance

Replay divergence rate < 0.1% (§4) measured over 10,000 replayed lineages; WAL recovery completes in < 90 seconds (§4) for a 500-worker fleet's last checkpoint interval; checkpoint restore < 3 seconds per worker (§4).

Fixtures

conformance/replay/wal_truncation.log — a WAL file truncated mid-record, exercises recovery tolerance for a torn final write. conformance/replay/partial_snapshot.chk — a checkpoint missing pages, expects SnapshotError::IncompletePages, not a silent partial restore. conformance/replay/replay_divergence.trace — a known-divergent replay pair, exercises the divergence comparator (I9) end-to-end.

Pitfalls

Torn writes on process crash mid-fsync — manifestation is a WAL segment with a valid header but a corrupted tail record; root cause is not distinguishing "no record" from "partial record" at recovery time; debug via storage.torn_write_total; signal is any nonzero count during recovery; recovery is treating any partial trailing record as absent, never attempting partial replay of it (P9, fail closed). Snapshot drift when two checkpoints claim the same snapshot_id after a coordinator failover — detect via I2's monotonicity check; recover by rejecting the second writer and forcing it to request a fresh ID range. Lineage corruption from a dangling parent_snapshot reference (the parent was garbage-collected before children were fully persisted) — detect via reconstruction failing to resolve the parent link; recover by pinning ancestor checkpoints until all known children are durable, enforced by a reference-counted retention policy.

⬜ Phase 9 — Observability, Fuzzing & Hardening §21

Objectives

Deliver production operational visibility and adversarial hardening in one phase: metric taxonomy, trace correlation, differential validation, chaos fault injection, crash minimization. This phase introduces the constraint that every prior phase's acceptance criteria must hold under fault injection, not just under clean-path testing.

Deliverable

A security-hardened, fully observable platform: crates/cli triage <crash_id> producing a minimized, symbol-annotated crash report, backed by live dashboards from templates/dashboards/*.

Acceptance

A 72-hour fuzz campaign across all fuzz targets completes with zero unhandled panics and zero sanitizer findings; replay divergence is eliminated to 0 observed events over the campaign (tighter than Phase 8's < 0.1% steady-state budget, §4); all major state transitions (§8's seven states) are independently observable in the dashboard set.

Fixtures

conformance/hardening/malformed_ast.json — a crafted AST violating I6, exercises the hash-collision detection path. conformance/hardening/corrupted_snapshot.chk — a bit-flipped checkpoint, exercises P9's fail-closed checksum gate end-to-end. conformance/hardening/randomized_schedule.trace — a chaos-perturbed schedule, exercises whether I7 holds under adversarial timing.

Pitfalls

Hidden nondeterminism surviving to this phase despite Phases 0-8's individual guarantees — manifestation is a replay divergence that no single phase's unit tests caught because it only manifests under the combination of chaos perturbation and real timing; root cause is almost always a cross-crate ordering assumption (e.g. Phase 6 assuming Phase 4's page faults resolve in request order under contention); debug via bisecting the chaos-injection seed; signal is a divergence that disappears when chaos injection is disabled; recovery is promoting the minimal reproducing chaos seed into conformance/hardening/ as a permanent regression fixture. Solver inconsistencies surfaced only under sustained differential load (Z3 and Bitwuzla agree on 99.99% of queries but diverge under a specific bitvector-width pattern) — detect via the differential-validation alert; recover by excluding the disagreeing query shape from the cache (never cache a disputed result) and filing it as a solver-specific bug upstream.
