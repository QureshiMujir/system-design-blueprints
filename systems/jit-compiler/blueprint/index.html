53 — JIT Compiler

Project Number: 53

Project Name: JIT Compiler

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build jitc, a from-scratch tiered method-JIT for the bytecode emitted by the host Virtual-Machine project (Ranking line 33): an interpreter-backed Tier 0 (inherited from the host VM), a Tier 1 baseline JIT that lowers bytecode to machine code one opcode at a time with local peephole cleanup, and a Tier 2 optimizing JIT built around an SSA-form middle IR with inlining, escape analysis with scalar replacement, type specialization via polymorphic inline caches (PICs), on-stack replacement (OSR), and deoptimization. Both x86_64 and AArch64 backends ship from the same middle IR through one Emitter trait per architecture (§3, P8). Safepoints and per-method stack maps integrate with the Garbage-Collector project (Ranking line 34) for precise root scanning (§7 I3, §22).

Phase-0 deliverable (numbered modules, crate names per §10):

  1. jitc-core — shared types: Tier, MethodId, MethodCode, Value, Shape, Safepoint, StackMap, DeoptInfo.
  2. jitc-bytecode — host-VM bytecode reader, constant pool, disassembler.
  3. jitc-codebuf — executable code buffer: double-mapped W^X arena, relocation table, patch points, code GC.
  4. jitc-asm-x64 — x86_64 hand-rolled encoder, register/operand model, peephole.
  5. jitc-baseline — Tier 1: 1:1 bytecode-to-asm compiler, linear-scan register allocator, IC stub emission, safepoint emission.
  6. jitc-test-util + conformance/ — differential harness proving Tier 1 output matches the interpreter bit-for-bit on the integer-arithmetic opcode subset.

System boundaries.

  • Provides: bytecode-to-machine-code compilation at three tiers; tier promotion/demotion policy; inline caching and type feedback; deoptimization back to the interpreter; OSR from interpreter to compiled code; safepoints and stack maps for GC root scanning; perf/GDB debugger integration.
  • Delegates: bytecode parsing semantics and the interpreter itself to the host VM (Ranking 33); heap layout, allocation, and collection to the GC (Ranking 34); process-level sandboxing to the embedding host application.
  • Does NOT provide: a standalone language front end, a garbage collector, a bytecode verifier (the host VM verifies; jitc-bytecode only range-checks defensively, §8), a distributed or multi-process compilation service, or ahead-of-time whole-program compilation.

Non-goals: production coverage of every host-VM opcode on day one (Phase 0 covers the integer-arithmetic subset only, §12); a third architecture (RISC-V is PhaseDeferred("§36")); a trace-based JIT tier (rejected at ADR-02, §9; alternative sketched at §36 AA1); concurrent GC compaction that moves live compiled-code addresses (the code heap is non-moving, §7 I12); full hardware side-channel (Spectre-class) mitigation (documented gap, §24 T6).

Deployment model: jitc links into the host VM process as a library (crates/jitc); one process, one code heap, one or more mutator threads plus, from Phase 11 onward, one background optimizing-compile thread (ADR-23). No network service, no multi-tenancy, no cross-process shared code cache.

Target users/operators: the host-VM embedding application developer (calls through jitc-runtime's embedding API, docs/sdk/embedding.md); an SRE operating a long-running host-VM process (reads docs/runbooks/); a compiler engineer extending a tier (reads docs/architecture/).

What later phases unlock: Phase 0–2 (§12–§14) unlock a working two-tier JIT beating the interpreter on integer kernels; Phase 3–6 (§15–§18) unlock the optimizing tier and IC-driven speculation; Phase 7–8 (§19–§20) unlock OSR and deoptimization, closing the speculative loop; Phase 9 (§21) unlocks AArch64 parity; Phase 10–11 (§22–§23) unlock GC integration and production hardening (concurrent compilation, code GC).

Recommended language: Rust, 2024 edition. Rationale: memory safety for the large volume of runtime metadata (StackMap, DeoptInfo, IcSite) that must never be corrupted, with unsafe scoped tightly to jitc-codebuf and the two jitc-asm-* encoders (ADR-20, §9); shares crate boundaries and core types directly with the host VM (Ranking 33), which is also Rust. Rejected: C++ — no memory-safety backstop for the metadata layer that GC root-scanning depends on (I3); Zig — comparable encoding ergonomics but no crate-sharing argument with Ranking 33, and a less mature threading story for Phase 11's concurrent compile thread; OCaml/Haskell — poor fit for hand-rolled bit-level instruction encoding and raw W^X page management, both of which need direct pointer control.

Prerequisites: the host-VM bytecode format (Ranking 33's FINAL_BLUEPRINT); x86_64 instruction encoding (Intel SDM Vol. 2, AMD APM Vol. 3, §5 RFCs/Specs); AArch64 A64 encoding (ARM DDI 0487, §5); SSA construction (Cytron et al. 1991, §5 Papers); linear-scan and graph-coloring register allocation (Poletto & Sarkar 1999, Chaitin 1982, §5); the HotSpot tiered-compilation and PIC/deopt literature (Kotzmann et al. 2008, Hölzle et al. 1991/1992/1994, §5).

Estimated timeline: Phase 0 in 1 week; the full 12-phase plan (§12–§23) in 19 weeks (~4.5 months) at one senior engineer full time, or 8–9 months at half time — within the 4–6 month full-system envelope carried over from the original scoping once Phase 11's concurrency-hardening extension is included.

Deferred features, each anchored to a real heading and resolved in the Deferred Features Register (§37): a trace-based Tier 3 PhaseDeferred("§36"); RISC-V backend PhaseDeferred("§36"); ahead-of-time compiled-code export/import PhaseDeferred("§23.3"); floating-point (SSE2/NEON) instruction coverage beyond the integer subset PhaseDeferred("§13.2"); WebAssembly lowering target PhaseDeferred("§36"); speculative-inlining depth beyond 3 guards PhaseDeferred("§9"); a template/copy-and-patch baseline compiler PhaseDeferred("§36").

2. Why Build This

  • Owns the last mile of performance. An interpreter's mispredictions are forgivable; a JIT's mispredictions (a live range spilled that didn't need to be, a PIC that never learns a shape) are the bugs only the JIT's own team can diagnose. Building one from scratch is the fastest path to owning that class of bug.
  • Concentrates twenty-five years of method-JIT engineering into one reviewable codebase. HotSpot's C1/C2 split (Kotzmann et al. 2008), V8's Sparkplug/Maglev/TurboFan pipeline, JavaScriptCore's B3, LuaJIT's trace recorder (Pall), and GraalVM's speculative-optimization model each encode hard-won lessons; this project carries the ones that transfer to a from-scratch two-arch method JIT and documents, via ADR (§9), the ones it deliberately does not carry.
  • Architecturally, a JIT is where three normally-separate subsystems must agree byte-for-byte: language semantics (owned by Ranking 33's interpreter), the memory model (owned by Ranking 34's GC via stack maps/safepoints, §22), and the CPU's own execution model (owned by the two jitc-asm-* encoders). Nowhere else in a language runtime must all three be simultaneously correct at machine-code granularity.
  • Historically, method-JIT design is the resolution of the 1990s Self/Smalltalk dynamic-language performance crisis (Ungar & Smith 1987; Hölzle/Chambers/Ungar 1991/1992) into the mainstream VMs (Java, JavaScript, Lua) that inherited it; building the PIC/deopt/OSR triad from the papers forward is the shortest path to understanding why every dynamic-language VM built since 1995 looks the way it does.
  • Engineering muscles built: reading and hand-encoding an ISA manual precisely (Intel SDM, ARM ARM); building and verifying an SSA-form IR (dominance, block-argument merges); designing a speculation-and-bailout protocol whose failure mode is silent wrong output, not a crash; reasoning about a mutator/compiler/collector three-way concurrency problem (§22, §23).
  • Cross-links: the Garbage-Collector project (Ranking 34) supplies the collector this JIT must hand precise roots to (§7 I3, I12); the Virtual-Machine project (Ranking 33) supplies the bytecode and interpreter this JIT must never diverge from (§6 P1); a from-scratch Regex Engine or SQL query compiler elsewhere in this portfolio would reuse the SSA-construction and linear-scan machinery nearly unchanged.
  • Calibration value: a JIT is small enough, relative to a full VM, that one engineer can hold the whole design in their head, yet it exercises compiler theory, systems programming, and security engineering (JIT-spray, W^X, CFI) simultaneously — a rare combination for a single project.

What Mastery Looks Like

  • Can read a hot bytecode loop and predict, opcode for opcode, the x86_64/AArch64 instructions the optimizing tier emits, including which values scalar-replace and which spill (Phase 4–5, §16–§17).
  • Can explain why a specific PIC transitions monomorphic → polymorphic → megamorphic for a given call site and quantify the resulting latency delta (Phase 6, §18).
  • Can construct, by hand, the dominance-frontier computation that places a block parameter at a given loop header (Phase 3, §15).
  • Can design a deopt bailout that reconstructs an interpreter frame from a DeoptInfo and reason about which values must be kept live across an inlined, scalar-replaced call to make that reconstruction possible (Phase 4 + Phase 8, §16, §20).
  • Can explain, with numbers, why W^X double-mapping was chosen over mprotect toggling and what regime would flip that decision (ADR-06, §9).
  • Can walk an OSR transition end-to-end — interpreter frame → compiled frame → resumed execution — and name the one invariant (I13) that makes it safe (Phase 7, §19).
  • Can read a stack map and perform the same root scan the GC's root_scan.rs performs, by hand, on paper (Phase 10, §22).
  • Can defend, against a HotSpot or V8 engineer, every rejected alternative in the ADR table with the regime where it would have won instead (§9, §36).

Nine boxes, three boundaries, one queue. Interpreter (Tier 0): owned entirely by Ranking 33; this project only reads its profile counters and bytecode format, never modifies it (P1). Tier Manager: the sole owner of promotion/demotion decisions (P2); demotion happens on deopt (§20), promotion on counter thresholds (§4); enforces I11 (monotonic counters). Baseline JIT (Tier 1): a 1:1 bytecode-to-asm compiler with linear-scan register allocation (§14); it is also the fallback target when the optimizing tier's compile budget is exceeded (I10). Optimizing JIT (Tier 2): the SSA-IR pipeline (construction §15, optimization §16, register allocation §17); it is where inlining, escape analysis, and type specialization live. Codegen Backend: the only place architecture-specific code exists; both tiers call through the same Emitter trait (P8) so the optimizing pipeline never branches on architecture. Code Heap: the sink of the one-way data path — bytecode is the source of truth, tiers consume it, the code heap holds the compiled result under W^X (P6) and is reclaimable by code GC (P14, I12). Runtime Support: every cross-cutting concern (relocation, stack maps, deopt info, IC state, debugger export) is owned here and exposed to every other layer via trait-bound calls — no layer reaches across another (a design rule enforced by crate-visibility boundaries in §10). The concurrency boundary (introduced at Phase 11, ADR-23) separates the mutator thread(s), which always run Tier 0/1 synchronously, from the background optimizing-compile thread; MethodCode publication across this boundary is a single atomic pointer swap (§23.2). The persistence boundary: nothing in the code heap or runtime support layer survives a process restart — every phase's correctness argument assumes a cold start (compatibility implications discussed in §27). The trust boundary: the host process is trusted; the bytecode it executes is not (adversary A1, §24) — every defensive check in jitc-bytecode (§8) exists because of this boundary, not because the host VM's own verifier is assumed absent.

6. Design Principles

  1. P1 — The interpreter is the ground truth. Every tier's output must produce identical observable behavior to the Tier-0 interpreter on the conformance corpus (§28). Tradeoff: every optimizing-tier change re-verifies against the interpreter, slowing iteration. Operational implication: nightly differential runs gate release (§29). Violating it: a silently wrong optimization becomes an unowned, undebuggable production bug.
  2. P2 — Tiers are explicit; promotion is automatic. The Tier Manager (jitc-tier-manager) owns promotion; user code never requests a tier. Tradeoff: applications cannot force early Tier-2 compilation, costing some warm-up latency. Operational implication: thresholds are TOML-tunable, not per-call. Violating it: "forced JIT" call sites produce nondeterministic benchmarking artifacts and defeat I11.
  3. P3 — Safepoints are everywhere needed and nowhere else. Method entry, loop backedge, allocation, explicit poll (§22.1). Tradeoff: over-placing safepoints costs 1–3% throughput per extra poll (§34 CM8). Violating it: the GC cannot find roots — heap corruption (I3).
  4. P4 — Inline caches are the speculation surface. Every dynamic-dispatch call goes through an IC (jitc-ic); three states — monomorphic, polymorphic (≤4 shapes), megamorphic (ADR-15). Tradeoff: the polymorphic table's linear scan costs cycles proportional to shape count. Violating it: the type-feedback loop that Phase 4 depends on (§16.2) breaks.
  5. P5 — Deoptimization is correct, not fast. The first deopt at a bailout site is allowed to be slow (§4: ≤500 µs p99, not a throughput target); subsequent deopts at the same site are not specially optimized — the method demotes instead (§20.3). Tradeoff: repeated deopts always pay full reconstruction cost. Violating it: a "fast path" deopt that skips state validation corrupts resumed execution (I4).
  6. P6 — W^X is a hard invariant. The code heap exposes RW and RX aliases of the same physical pages (double-mapped, ADR-06); there is no mprotect toggle per emit. Tradeoff: doubles reserved virtual address space (not physical memory). Violating it: a page that is simultaneously writable and executable is a JIT-spray primitive (§24 T1).
  7. P7 — Constant blinding is the default for embedded constants. Every constant emitted in code is XOR-blinded with a per-process secret (ADR-07). Tradeoff: one extra register and one DeoptInfo slot per blinded constant. Violating it: an attacker-influenced embedded constant becomes a directly plantable JIT-spray payload.
  8. P8 — One emitter per architecture; one optimizer pipeline. The baseline tier writes asm directly through the Emitter trait; the optimizing tier lowers SSA to asm through the same trait — there is no second lowering abstraction. Tradeoff: the Emitter API must serve both "dumb" 1:1 lowering and scheduled lowering. Violating it: two divergent encoders double the conformance surface (§28) and the bug surface.
  9. P9 — Profile feedback is monotonic. Counters (invocation, backedge, IC-shape, I11) never decrease; a demoted method's counters are not reset. Tradeoff: a method that briefly regresses during warm-up is not "forgiven" and may re-promote slower than intuition suggests. Violating it: promotion/demotion thrashing (§25 FM2).
  10. P10 — The runtime is one binary, tiers configured not compiled. jitc ships all three tiers; operators configure thresholds via TOML (ADR-19). Tradeoff: binary size includes both register-allocation backends. Violating it: multiple binaries fragment the conformance matrix (§28) and double the release-engineering surface (§29).
  11. P11 — Stack maps are data, not code. The safepoint-to-GC-root mapping is an explicit per-method table (StackMap, §11), never inferred by re-disassembling code. Tradeoff: table storage cost (§34 CM1). Violating it: a root-scan bug becomes a silent use-after-free (§25 FM8).
  12. P12 — Speculative inlining is bounded at three guards. ADR-14. Tradeoff: some inlining depth is foregone even when it would help. Violating it: the deopt budget blows and the tier thrashes (§25 FM2).
  13. P13 — The bytecode interpreter owns semantics; the JIT owns speed only. The JIT never introduces a new observable side effect (e.g., reordering externally visible I/O). Tradeoff: some valid instruction reorderings are foregone for observational transparency. Violating it: breaks P1 by definition.
  14. P14 — Code-heap space is reclaimable, never assumed permanent. Code GC (jitc-codebuf::code_gc) can evict any Tier-1/Tier-2 MethodCode under memory pressure (ADR-24); every call site re-resolves through the Tier Manager. Tradeoff: a reclaimed hot method briefly regresses to the interpreter. Violating it: pinning code forever leads to unbounded code-heap growth (§34 CM2, §31).

These are enforced at the type level where possible (the Tier enum, RegId/IcShape newtypes) and by code review and the §16 conformance/fuzz harness where not.

8. Domain Model

8.1 Bytecode input grammar (EBNF, integer-subset excerpt)

method       ::= header code_length code_byte+
header       ::= method_id arity max_locals max_stack
code_byte    ::= opcode operand?
opcode       ::= "iconst" | "iload" | "istore" | "iadd" | "isub" | "imul"
               | "idiv"   | "if_icmpge" | "goto" | "invokevirtual"
               | "ireturn" ;  (* ~80 opcodes total in the host VM; Phase 0
                                covers ~20 integer-arithmetic opcodes *)
operand      ::= u8 | u16 | i16 ;  (* width is opcode-dependent *)
constant_pool ::= entry_count entry+
entry        ::= int_const | method_ref | shape_ref

8.2 SSA middle-IR grammar (EBNF)

function     ::= "func" method_id "{" block+ "}"
block        ::= block_id "(" param* ")" ":" instr* terminator
param        ::= value_id ":" type
instr        ::= value_id "=" op type operand*
op           ::= "iadd" | "isub" | "imul" | "icmp" | "iload" | "istore"
               | "loadshape" | "checkshape" | "call" | "callinline"
               | "box" | "unbox" | "alloc" | "safepoint" | "deopt"
terminator   ::= "branch" block_id arg*
               | "branch_if" value_id block_id arg* "," block_id arg*
               | "switch" value_id "{" (const ":" block_id arg*)+ "}"
               | "return" value_id?
               | "unreachable"
type         ::= "i32" | "i64" | "f64" | "ref" | "bool"
arg          ::= value_id

Block parameters (Cranelift-style, no separate phi instruction, ADR-03) hold every merge value; Func::verify (§15.3) checks I1 and I2 over this grammar.

8.3 Machine-code buffer layout

RW alias (mmap #1, PROT_READ|WRITE) ── same physical pages ── RX alias (mmap #2, PROT_READ|EXEC)
+----------+------+----------+------+-----+-------------+
| method_0 | pad  | method_1 | pad  | ... | free space  |   (identical layout in both aliases)
+----------+------+----------+------+-----+-------------+
cursor: AtomicUsize, bumped on alloc_method()
relocs: Mutex<Vec<Reloc>>, applied to the RW alias only, before seal()
seal(): flush I-cache (AArch64: dc cvau + dsb ish + ic ivau + dsb ish + isb per line)

8.6 Worked example: sumTo(n) through all three tiers

Bytecode (Tier 0 input, integer subset):

pc opcode operand effect
0 iconst_0 — push 0 (acc)
1 istore_1 — acc = pop
2 iload_0 — push n
3 if_icmple pc=12 branch if n ≤ 0
4 iload_1 — push acc
5 iload_0 — push n
6 iadd — push acc+n
7 istore_1 — acc = pop
8 iload_0 — push n
9 iconst_1 — push 1
10 isub — push n-1
11 goto pc=2 loop (backedge → safepoint, P3)
12 iload_1 — push acc
13 ireturn — return acc

Tier 2 SSA IR (post-construction, §15.2; bb0 is the entry, bb1 the loop header with a block parameter carrying acc/n, bb2 the exit):

func sumTo {
  bb0():
    safepoint
    branch bb1(0, arg0)
  bb1(acc: i32, n: i32):
    safepoint            ; backedge safepoint, P3
    v0 = icmp le n, 0
    branch_if v0 bb2(acc), bb1_body(acc, n)
  bb1_body(acc: i32, n: i32):
    v1 = iadd acc, n
    v2 = isub n, 1
    branch bb1(v1, v2)
  bb2(result: i32):
    return result
}

Tier 1 (baseline) lowers each bytecode 1:1 through the Emitter; Tier 2 lowers the SSA form above after the §16 pipeline runs (LICM has nothing to hoist here; GVN dedupes nothing; the loop is already minimal) — both tiers ultimately emit the same instruction classes (compare, add, sub, conditional branch) via one Emitter trait (P8), differing only in register assignment strategy (linear-scan vs. graph-coloring, §14.3 vs §17.3).

8.8 Malformed-input example

A crafted method whose goto/if_icmple operand encodes a branch target past code_length (or into the middle of another instruction's operand bytes) is rejected by jitc-bytecode's defensive range check before IR construction — this is deliberate defense-in-depth beyond the host VM's own bytecode verifier (§1 non-goals), because the JIT's trust boundary treats all bytecode as adversarial (§3 trust boundary, §24 A1). Result: Error::MalformedBranchTarget surfaces to the embedding host; the method is pinned at Tier 0 permanently (row 7 of §8.7); bytecode_reject_total increments (§24 T12).

8.9 Failure-path example: guard-failure demotion under shape churn

A call site alternates among 5 distinct shapes at high frequency (exceeding the 4-shape polymorphic capacity, ADR-15) while the optimizing tier has already speculated on the two most common shapes via checkshape guards (§16.2). Each miss deopts (I4), the demote counter (I11) increments, and after 3 consecutive misses at the same site the method demotes to Tier 1 under a cooldown (§8.7 row 5) rather than re-optimizing immediately — preventing the deopt storm described in §25 FM2 from consuming the optimizing-compile thread's budget (§4).

11. Core Schema & Types

All types below are signatures only — no function bodies (§4 no-code rule). Each block is followed by terse ownership/mutation/concurrency/persistence/serialization/compatibility annotations.

11.1 Tier, MethodId, MethodCode (jitc-core)

pub enum Tier { Interpreter, Baseline, Optimising }
pub struct MethodId(pub u32);

pub struct MethodCode {
    pub method:        MethodId,
    pub tier:          Tier,
    pub entry:         *const u8,        // RX-alias entry point
    pub size:          usize,
    pub stack_map:     StackMap,
    pub deopt_info:    DeoptInfo,
    pub safepoints:    Vec<Safepoint>,
    pub ic_sites:      Vec<IcSite>,
    pub osr_entries:   Vec<OsrEntry>,
    pub reloc:         Vec<Reloc>,
    pub bytecode_hash: u64,              // xxh3, I7
}
  • Ownership: one MethodCode per (method, tier); superseded on tier-up/demote (§8.7).
  • Mutation: immutable after seal(); patched in place only via jitc-codebuf::patch (IC rewrites, §18).
  • Concurrency: published to mutator threads via a single atomic pointer swap (ADR-23, §23.2).
  • Persistence: process-lifetime only (§3 persistence boundary); no on-disk form (Phase-0 scope; AOT export is PhaseDeferred("§23.3")).
  • Serialization: none in-scope; internal-only.
  • Compatibility: bytecode_hash (I7) is the sole cross-recompile compatibility check.

11.2 Value, Shape (jitc-core)

pub struct Value(pub u64);                       // NaN-boxed
pub struct Shape(pub u32);                        // hidden-class index

pub fn value_is_int(v: Value) -> bool;
pub fn value_is_float(v: Value) -> bool;
pub fn value_is_object(v: Value) -> bool;
pub fn value_shape(v: Value) -> Option<Shape>;
  • Ownership: Value is Copy; no heap ownership at this layer (heap objects are GC-owned, Ranking 34).
  • Mutation: immutable; a new Value is produced, never mutated in place.
  • Concurrency: Copy + Send; no synchronization needed.
  • Persistence: none — process-lifetime.
  • Serialization: none — internal bit pattern only, arch-independent by construction.
  • Compatibility: NaN-boxing tag layout is an internal ABI shared only with jitc-ic and jitc-runtime; never exposed across a process boundary.

pub struct Safepoint {

    pub bytecode_pc: u32,

}
pub enum SafepointKind { MethodEntry, BackEdge, Allocation, Poll }

pub struct StackMap {
    pub frame_size: u32,
    pub entries:    Vec<StackMapEntry>,
}

}
  • Ownership: owned by the enclosing MethodCode; one StackMap per method (I3).
  • Mutation: immutable after seal().
  • Concurrency: read-only after publication; safe for concurrent GC root-scan threads.
  • Persistence: none.
  • Serialization: none — read directly by jitc-runtime::root_scan in-process.
  • Compatibility: StackMapEntry layout is internal ABI shared with Ranking 34's GC via the root_scan trait boundary (§3); a layout change requires coordinated update on both sides.

pub struct DeoptInfo { pub bailouts: Vec<DeoptBailout> }

  • Mutation: immutable after seal().
  • Concurrency: read-only; accessed only during a deopt bailout on the deopting thread (I14).
  • Persistence: none.
  • Serialization: none.
  • Compatibility: DeoptReason variants are matched exhaustively in docs/runbooks/; adding a variant requires a runbook update (§26).

11.5 IR Value, Block, Func (jitc-ir)

pub struct IrValue(pub u32);
pub struct BlockId(pub u32);

pub struct Block {
    pub id:           BlockId,
    pub params:       smallvec::SmallVec<[IrValue; 4]>,
    pub instrs:       Vec<Instr>,
    pub terminator:   Terminator,
    pub predecessors: smallvec::SmallVec<[BlockId; 2]>,
}
pub struct Func {
    pub method:    MethodId,

pub fn func_verify(f: &Func) -> Result<(), VerifyError>;   // I1, I2
  • Ownership: Func owns all its Blocks and ValueDefs; dropped after Tier 2 codegen completes (§16 pipeline).
  • Mutation: mutable during construction (§15.2) and each optimization pass (§16); frozen before jitc-regalloc runs.
  • Concurrency: single-threaded per compile (owned by the compiling thread, mutator or background per ADR-23).
  • Persistence: none — compile-time only.
  • Serialization: jitc-ir::print emits a human-readable text form for tools/ir-viewer (debug-only, not a wire format).
  • Compatibility: internal only; the grammar in §8.2 is the contract, not the Rust type layout.

11.6 CodeBuffer (jitc-codebuf)

pub struct CodeBuffer {
    rw_base:  *mut u8,
    rx_base:  *const u8,
    capacity: usize,
    cursor:   AtomicUsize,
    relocs:   Mutex<Vec<Reloc>>,
}

pub fn codebuffer_allocate(size: usize) -> CodeBuffer;

pub fn codebuffer_seal(buf: &CodeBuffer, slot: MethodSlot) -> MethodCode;
pub fn codebuffer_patch(buf: &CodeBuffer, slot: MethodSlot, off: usize, bytes: &[u8]);
  • Ownership: one CodeBuffer per process (Phase 0, §12); regions are sub-allocated per method.
  • Mutation: cursor bumped atomically; relocs behind a Mutex (contention bounded by compile rate, §34 CM9).
  • Concurrency: alloc_method/patch callable from the background compile thread (Phase 11) and the mutator concurrently; seal performs the I-cache flush (§8.3) before any thread may execute the new code.
  • Persistence: none (§3 persistence boundary).
  • Serialization: none.
  • Compatibility: internal; MethodSlot never crosses a process boundary.

11.7 IC types (jitc-ic)

pub struct IcSite {
    pub site_pc:  u32,
    pub kind:     IcKind,
    pub state:    IcState,
    pub feedback: IcFeedback,
}
pub enum IcKind  { LoadProperty, StoreProperty, Call }
pub enum IcState { Uninitialised, Monomorphic(Shape), Polymorphic, Megamorphic }
  • Ownership: owned by the enclosing MethodCode; feedback mutated in place by the runtime stub (§18.4).
  • Mutation: state transitions only forward (I6); feedback appends observed shapes.
  • Concurrency: single-writer (the executing thread at that call site); reads from jitc-opt ::type_spec during recompilation are snapshot copies.
  • Persistence: none.
  • Serialization: none.
  • Compatibility: IcState variants are exhaustively matched in jitc-opt::type_spec; adding a state requires updating both the runtime stub and the optimizer.

These eleven types (§11.1–§11.7) are the entire public surface a host-VM embedder needs; everything else in the crates listed in §10 is implementation detail behind them.

12. Phase 0 — Repository Skeleton, Governance, and the Executable Code Buffer

12.1 Objectives

Stand up the repository at the §10 layout; land governance files; implement the W^X double-mapped code buffer (P6, ADR-06); prove the smoke test end to end: allocate, emit one ret, seal, call, return. No codegen logic yet — this phase is entirely about the substrate every later phase depends on.

  • Stand up crates/jitc-core with Tier, MethodId (§11.1); land Cargo.toml workspace.

  • Implement alloc_method/seal/patch per the §11.6 signatures; seal() performs the cache-coherency step described in §8.3 (a no-op on x86_64, the four-instruction I-cache flush sequence on AArch64, anticipating Phase 9, §21).
  • Land Makefile targets bootstrap, build, test, lint, typecheck, compose-up, compose-down, release-check, clean (§29).
  • Land the .github/workflows/ files enumerated in §10; ci.yml and conformance.yml run on every push, kernels.yml/benchmarks.yml/fuzz.yml run nightly.
  • Land CONTRIBUTING.md, CODE_OF_CONDUCT.md, SECURITY.md (PGP fingerprint placeholder), CHANGELOG.md (Keep-a-Changelog), BLUEPRINT_LOG.md, BUILD_PLAN.md, LICENSE (Apache-2.0, ADR-11).
  • Land Dockerfile (builder stage with the Rust toolchain, runtime stage with the compiled jitc binary) and docker-compose.yml (Prometheus + Grafana sidecars, ADR-12/ADR-13).

12.3 Deliverable

make bootstrap && make build && make test all exit 0 on a fresh clone. One passing test in crates/jitc-codebuf allocates an 8-byte slot, emits the single byte 0xC3 (ret), seals the slot, casts the entry pointer to extern "C" fn(), calls it, and observes a clean return. ADR-01, ADR-02, ADR-03, ADR-05, ADR-06, ADR-11, ADR-20 are recorded under docs/adr/.

12.4 Acceptance Criteria

cargo test -p jitc-codebuf reports 100% pass (≥ 6 unit tests: allocate, alloc_method, seal, patch, wx self-test, ret-and-call smoke test); the I5 startup self-test passes on both a Linux x86_64 and a Linux AArch64 CI runner (kernels.yml); jitc release-build binary size ≤ 8 MB (feeds §30 M-target baseline); startup wall-clock from process exec to CodeBuffer::allocate return ≤ 50 ms p99 (§4 startup row).

12.6 Pitfalls

  • macOS Hardened Runtime denies the double-mapping trick by default; the workaround is mmap with MAP_JIT plus pthread_jit_write_protect_np per thread, shipped behind cfg(target_os = "macos") (Phase-1+ surface, not required for Linux CI).
  • Linux kernels under strict SELinux policy may deny the dual mapping; detect at startup and surface Error::DoubleMapDenied with the triage.md runbook reference rather than a bare panic.
  • memfd_create is absent on Linux pre-3.17; the naive fallback (a regular tempfile under /tmp) is refused because /tmp may be mounted noexec — surface Error::NoMemfd instead of silently degrading security posture (P6).

12.7 Performance Concerns

mmap syscall count at startup is 2 total (one region reserved at boot), not 2-per-method — batching into one large reservation avoids a syscall-per-method tax that would otherwise dominate Phase 2's tier-up latency budget (§4: ≤10 ms).

12.8 Edge Cases

Zero-size alloc_method request (§12.5); code-buffer capacity exhaustion at boot on a 32-bit-address-space host (documented as an unsupported target, not handled); concurrent allocate() calls before Phase 11 introduces threading (single-threaded assumption holds through Phase 10, revisited at I12 in Phase 11, §23).

12.9 Failure Analysis

What breaks if I5 is not enforced: a page simultaneously writable and executable is a direct JIT-spray primitive (§24 T1/T2) — total blast radius (arbitrary code execution in the host process). Detection is the I5 startup self-test, which runs before any bytecode is loaded. Containment is refuse-to-start, never a degraded-but-running mode. Operator visibility is a structured log line naming the W^X strategy chosen, surfaced before the process accepts any work.

12.10 Operational Notes

Metrics: codebuf_bytes_reserved, codebuf_regions_total, wx_violation_detected (I5, should be constant 0). Structured log at startup names the W^X strategy (double-map vs. macOS MAP_JIT path). No rollback/migration concerns — Phase 0 introduces no persistent state (§3 persistence boundary).

13. Phase 1 — x86_64 Emitter and Peephole

13.1 Objectives

Land the first architecture backend: a hand-rolled x86_64 encoder (ADR-01) covering the integer-arithmetic instruction subset, a label/patch mechanism, and a peephole pass, all behind the shared Emitter trait (P8) that both Tier 1 and Tier 2 will call in later phases.

13.2 Detailed Implementation Steps

  • Implement jitc-asm-x64::encoding per the Intel SDM Vol. 2 (§5 RFCs/Specs), cross-checked against the AMD APM Vol. 3. PhaseDeferred("§13.2"): SSE2/NEON floating-point coverage is out of scope for this pass — the integer subset only.
  • Model operand types Reg, RegMem, Imm32, Imm64, Label, Memory; ModR/M and SIB encoding as a lookup table; REX-prefix synthesis as a pure function of operand widths.
  • Cover: mov, add, sub, imul, idiv, cmp, test, the jcc conditional-jump family, jmp, call, ret, push, pop, lea, and, or, xor, shl, shr, sar.
  • Implement label.rs: a Label is a position-independent identifier; forward references record a fixup, backward references resolve immediately; bind(label) resolves all pending fixups at the current cursor.
  • Implement peephole.rs, run before seal(): mov reg, 0 → xor reg, reg (3B→2B); add reg, 1 → inc reg when size permits; collapse adjacent nop into the longest-form nop for available padding.
  • Every instruction gets a row in conformance/corpora/encoding_x64/ with golden bytes captured from nasm (ADR-22's Python harness drives the diff).

13.3 Deliverable

A standalone Emitter for x86_64 that can encode the full integer-arithmetic subset, resolve labels, and apply the peephole pass, exercised by crates/jitc/src/disasm.rs's CLI subcommand against the golden corpus.

13.4 Acceptance Criteria

100% of conformance/corpora/encoding_x64/ (≥ 400 golden vectors) pass byte-for-byte; the peephole pass reduces the corpus's total emitted byte count by ≥ 8% relative to peephole-disabled emission (measured by benchmarks/compare.py --no-peephole); zero Error::BranchOutOfRange-class failures (x86_64 has no analogous range limit, confirming the absence is structural, cross-referenced at §35 HQ13).

13.5 Conformance Fixtures

Fixture Purpose Expected Output

rex_r8_r15.bin REX-prefix presence for extended registers Byte-exact; missing REX is a hard test failure
idiv_no_cqo.bin Regression: idiv without preceding cqo Flags a wrong-result class, not merely an encoding mismatch

13.6 Pitfalls

  • The 32-bit immediate of cmp r/m64, imm32 is sign-extended; passing a negative literal as an unsigned 32-bit value is a wrong-result class the encoding corpus tests directly.
  • The REX prefix is required to address r8–r15; a zero-REX mov r10, ... silently encodes mov rdx, ... instead — the encoder asserts REX presence rather than trusting the caller.
  • idiv reads a 128-bit dividend from rdx:rax; omitting the cqo sign-extension before it produces a wrong result for negative dividends, not a crash — the hardest class of bug to catch without the dedicated fixture above.

13.7 Performance Concerns

Peephole rewrite cost is amortized into the single pre-seal pass (no re-scan); label resolution is O(instructions) via a single fixup list, avoiding O(n²) re-encoding on each bind.

13.8 Edge Cases

A Label bound twice (programming error in a caller — asserted, not silently ignored); a forward reference never bound by seal() time (Error::UnboundLabel); an immediate that does not fit the instruction's encoded width (Error::ImmediateOverflow).

13.9 Failure Analysis

A wrong-result bug here (missing REX, missing cqo) is the worst class this phase can produce: silent divergence from the interpreter, caught only by P1's differential corpus (conformance/corpora/observable/) — not by the encoding corpus alone, since the encoding corpus checks bytes, not semantics. This is why both corpora exist independently (§28).

13.10 Operational Notes

docs/architecture/x64-emitter.md documents the ModR/M/SIB table; tools/ir-viewer's disassemble mode (Phase 3+) renders emitted bytes back to mnemonics for debugging. No runtime metrics from this phase — encoding is compile-time only.

14. Phase 2 — Baseline JIT and Linear-Scan Register Allocation

14.1 Objectives

Land Tier 1: a 1:1 bytecode-to-machine compiler (P8, ADR-04) with a linear-scan register allocator (Poletto & Sarkar 1999, §5), a stable stack-frame layout, IC-stub call sites, and safepoint emission — the first tier that must pass the full P1 observable-parity conformance bucket.

14.2 Detailed Implementation Steps

  • Define the baseline stack frame (jitc-baseline::frame): saved frame pointer at [rsp], return address at [rsp+8], locals from [rsp+16], spill area at the top; frame size computed at compile time (System V AMD64 ABI, §5 RFCs/Specs).
  • Implement compile.rs's single-pass bytecode walk: iadd → pop two virtual registers, allocate one, emit add; iload N → mov from [rsp + frame_offset(N)]; if_icmpge → cmp + jge; invokevirtual → call through an IC stub (ic_stub.rs, anticipating Phase 6, §18).
  • Implement regalloc_ls.rs per Poletto & Sarkar 1999 (§5 Papers): compute live intervals by a forward bytecode walk; sort by start point; assign physical registers as they free up; spill the longest live interval when none is available. Caller-save set: rax, rcx, rdx, rsi, rdi, r8–r11; callee-save: rbx, r12–r15.
  • Emit safepoints (safepoint.rs) at every site named in P3/I3: method entry, every loop backedge, every allocation, plus an explicit poll — record each into the method's StackMap (§11.3).
  • Wire the conformance/corpora/baseline/ bucket: bytecode → baseline-asm parity, diffed against golden disassembly.

14.3 Deliverable

A working Tier 1 that compiles the integer-arithmetic bytecode subset (§8.1) end to end and executes it with observable behavior identical to the Tier-0 interpreter (P1).

14.4 Acceptance Criteria

conformance/corpora/observable/ (≥ 200 fixtures) pass 100% for the integer subset; conformance/corpora/baseline/ (≥ 80 fixtures) pass byte-for-byte; tier-up latency interpreter → baseline ≤ 10 ms p99 measured on benchmarks/kernels/fib.vmb (§4 M3); baseline compile throughput ≥ 50 MB/s of bytecode measured over the full kernel corpus (§4 M1).

  • A safepoint inserted between an arithmetic instruction and its flag-consuming successor (cmp then jcc) clobbers flags; the baseline emitter must recognize such windows and refuse to insert a poll inside them (P3's "nowhere else" clause).

15. Phase 3 — SSA Middle-IR Construction and Verification

15.1 Objectives

Land the optimizing tier's IR (ADR-03): an explicit CFG with block-argument SSA (no separate phi instruction), the grammar in §8.2, and a verifier enforcing I1/I2 before any optimization pass runs.

15.2 Detailed Implementation Steps

  • Implement jitc-ir::builder as a two-pass construction (Cytron et al. 1991, §5 Papers, applied here): pass one scans for branch targets to identify basic-block boundaries; pass two walks each block with an abstract interpreter tracking live variables, inserting block parameters at every merge point (the dominance-frontier computation from the paper, specialized to the Cranelift-style block-argument form of ADR-03 rather than explicit phi nodes).
  • Implement func.rs/block.rs per the §11.5 signatures; instructions per §8.2: iadd, isub, imul, icmp, iload, istore, loadshape, checkshape, call, callinline, box, unbox, alloc, safepoint, deopt; terminators: branch, branch_if, switch, return, unreachable.
  • Implement verify.rs's func_verify enforcing I1 (every value's use is dominated by its def) and I2 (block-parameter arity/type match across every predecessor) — computed via Cooper-Harvey-Kennedy dominance (a standard iterative dominator algorithm compatible with Cytron et al.'s dominance-frontier framework).
  • Implement print.rs for tools/ir-viewer (debug-only text form, §25 FM1 forensics).

15.3 Deliverable

Func::verify runs clean (zero I1/I2 violations) over the entire observable/ corpus's methods after IR construction, before any optimization pass touches them.

15.4 Acceptance Criteria

100% of constructed Funcs pass func_verify on the full conformance corpus; the §8.6 worked example (sumTo) produces the exact IR shown there, checked by a golden-text diff against print.rs's output; IR construction throughput ≥ 20 MB/s of bytecode (a looser bound than baseline's 50 MB/s, §4, since Tier 2 is not on the ≤10ms critical path).

15.6 Pitfalls

  • Block parameters are easier to verify than phi nodes but still require care computing dominance frontiers correctly (Cooper-Harvey-Kennedy, applied per §15.2).

16. Phase 4 — Optimization Pipeline

16.1 Objectives

Land the eight-pass optimization pipeline in the fixed order below (Click & Cooper 1995's combining-analyses argument, §5 Papers, applied here to justify running GVN/LICM/BCE in a single pipeline rather than as isolated passes): type specialization, inlining, GVN, LICM, BCE, escape analysis with scalar replacement, DCE, instruction scheduling.

16.2 Detailed Implementation Steps

  • Type specialization (type_spec.rs): read IcFeedback (§11.7) for each call/property site; replace the dynamic-dispatch instruction with a checkshape guard plus a direct call; guard failure is a deopt terminator (I4, applying Hölzle & Ungar 1994, §5).
  • Inlining (inline.rs, P12, ADR-14): bottom-up (leaf methods first); budget 100 IR instructions per inlined site; speculative inlining bounded at 3 guards (ADR-14); an inlined safepoint inherits the caller's frame layout (cross-referenced at §35 HQ7).
  • GVN (gvn.rs): standard value numbering over the SSA form, deduplicating redundant pure computations (Muchnick, §5 Books, Ch. 12).
  • LICM (licm.rs): loop-invariant computations hoisted out of the loop body (Appel, §5 Books, Ch. 19).
  • BCE (bce.rs): range analysis on loop induction variables; when a bounds check is proved to always hold, remove it.
  • Escape analysis with scalar replacement (escape.rs, Kotzmann & Mössenböck 2007, §5 Papers, applied here): a flow-insensitive analysis — an allocation escapes if its result is stored to the heap, returned, or passed to a non-inlined call; non-escaping allocations have their fields replaced by SSA values and the alloc instruction is DCE'd.
  • DCE (dce.rs): standard dead-code elimination over the post-pass IR.
  • Instruction scheduling (schedule.rs): a local list scheduler ordering the final IR for the codegen backend, informed by Click's combining-optimizations argument (§5) that scheduling should run last, after all semantic-changing passes have stabilized the IR shape.

16.3 Deliverable

A Func that has run the full eight-pass pipeline, still passes func_verify (I1/I2), and is ready for jitc-regalloc (Phase 5, §17).

16.4 Acceptance Criteria

conformance/corpora/optimising/ (≥ 120 fixtures) pass bytecode→optimizing-asm parity at a fixed seed; escape.rs eliminates ≥ 90% of allocations proven non-escaping in the binary_trees kernel's inner loop (measured via benchmarks/compare.py --allocation-count); inline.rs respects the 100-instruction budget and the 3-guard cap (ADR-14) with zero violations across the corpus; pipeline wall-clock stays within the 100 ms/method ceiling (ADR-16, I10) for every fixture.

Fixture Purpose Expected Output

nested_alloc_noescape.vmb Escape analysis on a nested non-escaping allocation Zero heap allocations in the compiled output

16.6 Pitfalls

  • Inlining a method that contains a safepoint must preserve the safepoint's stack-map invariant (I3); the inlined safepoint's stack map is rebuilt against the caller's frame layout, not dropped — a naive inliner that drops it produces a GC-unsafe site (§25 FM8).
  • Scalar replacement of a non-escaping allocation must still leave enough DeoptInfo (§11.4) behind that a deopt can materialize the object if execution bails out mid-loop (cross- referenced at §35 HQ7).

16.7 Performance Concerns

The eight-pass pipeline's total cost is dominated by escape analysis's flow-insensitive walk (O(instructions × call-sites)); bounding the optimizing-tier method size at 4,096 IR instructions (§4) keeps this tractable within the 100 ms budget (§34 CM7 derives the resulting throughput floor).

16.8 Edge Cases

A call site with zero observed feedback (skip type specialization, fall through to dynamic dispatch); a loop with no invariant computations (LICM is a no-op, not an error); an allocation that escapes only through an inlined call that itself later gets inlined away (re-run escape analysis after inlining stabilizes, not before).

16.9 Failure Analysis

An unsound escape-analysis result (treating an escaping allocation as non-escaping) is a wrong-result bug (FM1) reachable only through this pass; it is the single highest-value target for the differential fuzzer (§28) because it has no encoding-level signature to catch it early.

16.10 Operational Notes

17. Phase 5 — Optimizing-Tier Register Allocation (Graph Coloring)

17.1 Objectives

Land the Tier-2 register allocator (Chaitin 1982; Briggs, Cooper, Torczon 1994, §5 Papers, applied here; ADR-04): liveness, interference-graph construction, iterated-coalescing graph coloring, and the compile-budget fallback to Tier 1 (I10).

17.2 Detailed Implementation Steps

  • liveness.rs: per-block live-in/live-out sets via backward dataflow (Appel, §5 Books, Ch. 10, applied here); live ranges as intervals over the linearized, scheduled instruction stream from §16.2's schedule.rs output.
  • interference.rs: build the interference graph — two intervals interfere iff their ranges overlap; coalesce a mov between two non-interfering intervals of the same register class (I9) by giving them one color.
  • color.rs: Briggs' iterated register coalescing (Briggs, Cooper, Torczon 1994, applied here) — color, spill the highest-cost interval when no color is free, repeat; spilled values materialize into a stack slot at every use and store back at every def.
  • spill.rs: cost model favors spilling values with low use-density (few uses per live-range length) to minimize reload traffic.
  • The fallback (I10, ADR-16): if the pipeline (§16 + this phase) exceeds the 100 ms budget, abort remaining work, recompile the method with jitc-baseline instead, and mark the method "optimizing-tier failed, retry after cooldown" in the Tier Manager.

17.3 Deliverable

A fully register-allocated, schedulable Func ready for jitc-optimising::codegen, or — under I10 — a clean fallback to a working Tier-1 MethodCode with no partial/corrupt state.

17.4 Acceptance Criteria

conformance/corpora/optimising/ register-allocated output passes 100% observable parity against the interpreter; interference-graph construction for a 4,096-instruction method (the §4 cap) completes within a 40 ms sub-budget (leaving 60 ms for the rest of the 100 ms ceiling, ADR-16); zero I9 (cross-class coalescing) violations across the fuzz corpus after a 24-hour fuzz_targets soak.

17.5 Conformance Fixtures

Fixture Purpose Expected Output
high_pressure_1000_values.vmb 1,000 live IR values, forces spilling Correct spill code, matches interpreter
mixed_class_coalesce_candidate.vmb An int/float mov coalesce candidate Coalesce rejected (I9), separate colors assigned
budget_exceeded_4096.vmb A method at the 4,096-instruction cap under adversarial pressure I10 fallback to baseline, no partial MethodCode published

17.6 Pitfalls

  • The interference graph for a method with ~1,000 IR values is O(n²) in naive dense-matrix form; a bitset representation plus the 4,096-instruction cap (§4) keeps memory and time bounded (§34 CM7).
  • Coalescing is unsound if it merges two values whose register classes cannot share a physical register file (integer vs. floating-point) — I9 exists specifically to catch this before it becomes a miscompile.

17.7 Performance Concerns

Graph-coloring's iterated spill/recolor loop is the pipeline's single largest cost contributor; the 40 ms sub-budget (§17.4) is enforced by the same deadline-check mechanism that implements I10 at the pipeline level (§16.2's pipeline.rs).

17.8 Edge Cases

A method with more live values than available physical registers on both architectures simultaneously (the allocator must spill correctly regardless of which Emitter backend consumes its output); a fully-coalesced method needing zero physical registers beyond callee-saves (degenerate, still must produce valid output).

17.9 Failure Analysis

An I9 violation reaching production is a wrong-result bug (FM1) manifesting as a floating-point value silently reinterpreted as an integer (or vice versa) — caught by the class-check assertion in color.rs before it can reach codegen; a bypassed assertion (e.g. in a release build with assertions stripped) is why the fuzz target exists as a second line of defense (§17.4).

17.10 Operational Notes

Metrics: regalloc_spill_total, regalloc_coalesce_rejected_total (I9), compile_budget_exceeded_total (I10, shared with §16). docs/architecture/regalloc.md documents the coalescing algorithm and the spill-cost model.

18. Phase 6 — Inline Caches and Type Feedback

18.1 Objectives

Land the PIC mechanism (Hölzle, Chambers, Ungar 1991, §5 Papers, applied here; P4, ADR-15): monomorphic, polymorphic (≤4 shapes), and megamorphic call-site states, plus the feedback loop type_spec.rs (§16.2) reads from.

18.2 Detailed Implementation Steps

  • monomorphic.rs: the site emits a guard sequence — compare the receiver's Shape against the cached shape_id; on match, jump to the direct call target; on mismatch, call the runtime miss stub.
  • The miss stub (in jitc-runtime, invoked from jitc-ic::feedback) determines whether the miss is the call site's first miss (promote Uninitialised → Monomorphic, I6) or a shape transition (promote further).
  • polymorphic.rs: a dispatch table of up to 4 (Shape, target) pairs (ADR-15); the site walks the table linearly; a miss past the table promotes to Megamorphic (I6).
  • megamorphic.rs: falls back to the runtime's full dynamic dispatch — always correct, never unsafe, only a performance floor (cross-referenced at §24 T9).
  • feedback.rs: each IcSite (§11.7) records every shape it has observed into IcFeedback; jitc-opt::type_spec (§16.2) reads this feedback when the method next recompiles at Tier 2.
  • The miss stub must preserve every caller-save register the call site's calling convention guarantees live — the stub's prologue saves them all before dispatching (§25 FM7 names the failure mode when this is skipped).

18.3 Deliverable

A working IC mechanism exercised end to end by a method whose call site observes 1, then 2, then 5 distinct receiver shapes in sequence, promoting Uninitialised → Monomorphic → Polymorphic → Megamorphic exactly as I6 prescribes.

18.4 Acceptance Criteria

conformance/corpora/ic/ (≥ 40 fixtures) confirm every I6 state transition and reject every illegal backward transition; IC miss-handling latency p99 ≤ 5 µs (§4, §30 M15); zero dropped feedback events across a 24-hour fuzz soak (fuzz_targets, feeding §25 FM7's detection signal).

18.5 Conformance Fixtures

Fixture Purpose Expected Output
mono_to_poly_transition.vmb 1→2 shape transition State becomes Polymorphic, feedback records both shapes
poly_capacity_exceeded.vmb 5th distinct shape at a polymorphic site State becomes Megamorphic (ADR-15's capacity-4 boundary)
miss_stub_register_preserve.vmb Verifies the miss stub preserves all caller-save registers Post-miss register state matches pre-miss, modulo the call's own contract

18.6 Pitfalls

  • The IC guard is a compact cmp + near jne; if the conditional jump's target offset would exceed the near-jump encoding, the encoder must emit a trampoline rather than fail — a direct analog of I8's AArch64 branch-range concern, but for x86_64's near/far jump split.
  • A miss stub that fails to preserve every caller-save register clobbers live state the caller depends on — this is FM7 in §25, and is why miss_stub_register_preserve.vmb exists as a dedicated fixture rather than being left to incidental coverage.

18.7 Performance Concerns

The polymorphic table's linear scan costs cycles proportional to shape count (≤4, ADR-15); this is the concrete tradeoff named in P4 and quantified in the ADR-15 "when rejected wins" cell (§9) for workloads with higher shape diversity.

18.8 Edge Cases

A call site that never executes (zero feedback, type_spec.rs must not crash on empty IcFeedback); a shape that is deallocated (by the GC, Ranking 34) between observation and recompilation (the feedback table holds a Shape id, not a live reference, avoiding a GC-lifetime coupling); rapid shape churn exceeding capacity within a single invocation burst (§8.9's failure-path example).

18.9 Failure Analysis

Feedback loss (FM7, §25) manifests as a call site that never promotes despite real shape variety — detected by comparing production shape-diversity metrics against the I6 unit-test matrix's expected transition rates; no automatic recovery exists because the loss is silent by nature, making the production metric the primary detection surface.

18.10 Operational Notes

Metrics: ic_transition_total{from,to} (I6), ic_miss_duration_seconds (gates M15), ic_megamorphic_total (feeds §24 T9's rate alert). docs/architecture/ic.md documents the three-state machine and the miss-stub register-preservation contract.

19. Phase 7 — On-Stack Replacement (OSR)

19.1 Objectives

Land OSR (ADR-09): the ability to switch a currently-interpreting hot loop into compiled Tier 1/2 execution mid-method, at a loop backedge, without waiting for the method to return and be re-invoked.

19.2 Detailed Implementation Steps

  • jitc-optimising::osr (and the Tier-1 equivalent in jitc-baseline) generates one OSR entry point per bytecode backedge (§8.7 row 2), recorded in MethodCode.osr_entries (§11.1).
  • The interpreter, on observing a hot backedge (counter ≥ threshold, I11), calls into jitc-runtime::osr, which copies the interpreter's local-variable slots into the freshly allocated compiled frame using the layout described by I13 — a pure permutation/widening, never a semantic transform — then jumps to the OSR entry.
  • OSR exit (the reverse direction): an OSR-only compiled method may itself deoptimize; the bailout (Phase 8, §20) reconstructs the interpreter frame from DeoptInfo exactly as a normal Tier-2 deopt would, with no OSR-specific special case in jitc-runtime::deopt.
  • Guard against a reclaimed target: if the code GC (Phase 11, ADR-24) has evicted the MethodCode an OSR entry would jump into, the runtime stub detects the stale reference (I7) and falls through to recompile rather than jumping into freed memory.

19.3 Deliverable

A hot loop (the sumTo worked example, §8.6, run with a large n) observably transitions from interpreted to compiled execution mid-call, with the compiled frame's locals matching the interpreter's at the moment of transition.

19.4 Acceptance Criteria

conformance/corpora/osr/ (≥ 30 fixtures) pass 100% observable parity across the transition point; OSR latency p99 ≤ 1 ms (§4, §30 M5) measured on benchmarks/kernels/nbody.vmb's inner loop; zero I13 (layout mismatch) violations across a 24-hour fuzz soak.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
sum_to_osr_midloop.vmb §8.6 example, OSR triggered at iteration 10,000 Compiled-frame locals match interpreter state at transition
osr_into_reclaimed_code.vmb OSR target evicted by code GC just before the jump Falls through to recompile, no jump into freed memory (I7)
multi_backedge_osr.vmb OSR from either of two distinct backedges in one loop Both transitions produce correct locals (ties to I2/I13)

19.6 Pitfalls

  • OSR latency dominates the tier-up window for hot loops; it is measured directly in the perf_floor conformance bucket and budgeted at 1 ms p99 (§4) — a naive frame-copy implementation that walks the interpreter stack element-by-element with bounds checks on every slot can blow this budget on wide frames.
  • An OSR entry into a method whose compiled code has been evicted by code GC (§23) must fall through to recompile rather than jump into freed memory — this is surfaced as a runtime stub call, not a crash (§19.2).

19.7 Performance Concerns

The frame copy is O(locals), a small constant relative to loop iteration count; the 1 ms budget (§4) is dominated by the OSR-entry lookup (a hash on MethodId + backedge pc) rather than the copy itself.

19.8 Edge Cases

A backedge inside an already-inlined callee (the OSR entry must target the caller's compiled frame, since inlining erased the callee's own frame, §16.2); a loop with zero iterations before the method returns (OSR never triggers, not an error); a backedge whose counter races the code GC's reclamation check (I12 forces a global safepoint before reclamation, closing this race by construction).

19.9 Failure Analysis

An I13 violation (layout mismatch) presents as a wrong-result bug indistinguishable from FM1 without careful bisection — the dedicated osr/ conformance bucket and the side-by-side frame dump in docs/runbooks/wrong-result.md's procedure are what make this class of bug tractable rather than a multi-day investigation.

19.10 Operational Notes

Metrics: osr_entry_total, osr_latency_seconds (histogram, gates M5), osr_layout_mismatch_total (I13). docs/architecture/osr.md documents the copy-and-jump protocol and the ADR-09 rationale.

20. Phase 8 — Deoptimization

20.1 Objectives

Land the deopt mechanism (Hölzle, Chambers, Ungar 1992, §5 Papers, applied here; P5, ADR-10): full interpreter-frame reconstruction from a DeoptBailout descriptor (§11.4), and the demotion policy that follows repeated deopts at one site.

20.2 Detailed Implementation Steps

  • Every guard in Tier-2 code (checkshape, bounds checks surviving BCE, inlining guards) is a deopt site; each carries a DeoptBailout (§11.4) with enough metadata to rebuild the interpreter frame: bytecode_pc, the local-variable layout, and the operand-stack contents at that point.
  • The bailout sequence in jitc-runtime::deopt: (1) save all caller-save registers to a scratch area; (2) disable the safepoint poll flag for the deopting thread, enforcing I14; (3) walk the DeoptBailout's frame layout and rebuild the interpreter frame on the stack above the compiled frame; (4) tear down the compiled frame; (5) re-enable polling; (6) jump into the interpreter at bytecode_pc.
  • Demotion policy (jitc-tier-manager::promote, applying P5): after 3 deopts at the same site (default, TOML-tunable), the method demotes to Tier 1 and further Tier-2 compiles for it are throttled under a cooldown (§8.9's failure-path example).
  • GC coordination: values live in the deopt info that are heap references must be updated by the GC's stack-walker if a collection interleaves with reconstruction — this is why I14 (no safepoint during bailout) exists, closing the window rather than requiring the GC to understand a half-built frame.

20.3 Deliverable

Every guard fixture in the conformance corpus, when forced to fail, produces a reconstructed interpreter frame that is observably identical to what the interpreter alone would have produced at that bytecode pc — the core I4 guarantee, demonstrated end to end.

20.4 Acceptance Criteria

conformance/corpora/deopt/ (≥ 50 fixtures) pass 100% frame-state-match; deopt latency p99 ≤ 500 µs (§4, §30 M6); demotion after exactly 3 same-site deopts, verified by a counter-based fixture; zero I14 violations (deopt-during-safepoint) across a 24-hour fuzz soak (fuzz_targets/fuzz_deopt_reconstruct.rs).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
guard_fail_shape_mismatch.vmb A checkshape guard fails on the 2nd call Reconstructed frame matches interpreter exactly
deopt_with_scalar_replaced_value.vmb A scalar-replaced allocation must be re-materialized Correct heap object rebuilt at bailout (ties to §16.6)
three_deopts_same_site.vmb Repeated failure at one guard Method demotes to Tier 1 after the 3rd (P5)

20.6 Pitfalls

  • A deopt that fires during a safepoint walk corrupts the stack map if not handled atomically — the bailout disables polling for its duration (I14), the structural fix, not a retry loop.
  • Deopt info is not GC-aware for free: references inside the deopt info must be updated by the GC's own stack-walker during any collection that interleaves with reconstruction — this coupling is why Phase 10 (§22) and this phase share the same jitc-runtime crate.

20.7 Performance Concerns

The 500 µs p99 budget (§4) is dominated by the frame-rebuild walk, not the register-save step; P5 explicitly permits this cost because deopt is defined as correct-not-fast — no further optimization of this path is planned or desirable (over-optimizing it would risk I4).

20.8 Edge Cases

A deopt at the very first instruction of a method (no live values yet, degenerate but legal frame); a deopt whose bytecode_pc corresponds to a position inside an inlined callee (the frame reconstruction must produce two interpreter frames — caller and inlined callee — not one, a direct consequence of §16.2's inlining pass); a deopt racing a concurrent code-GC reclamation of the same method (closed by I12's global safepoint precondition).

20.9 Failure Analysis

An I4 violation (a missing live value in the reconstructed frame) is a wrong-result bug (FM1) detectable only by the deopt/ differential corpus — there is no encoding-level or type-level signal, which is why this bucket carries the highest fixture-to-pass-rate scrutiny in code review (§28).

20.10 Operational Notes

Metrics: deopt_total{reason} (§11.4's DeoptReason variants), deopt_latency_seconds (histogram, gates M6), deopt_demote_total. docs/runbooks/deopt-storm.md is the primary on-call reference when deopt_total rate exceeds the alerting threshold.

21. Phase 9 — AArch64 Backend

21.1 Objectives

Land the second architecture (ADR-05): a hand-rolled AArch64 encoder (per ARM DDI 0487, §5 RFCs/Specs) behind the same Emitter trait (P8), including branch-island synthesis (I8) and AAPCS64 calling-convention support.

21.2 Detailed Implementation Steps

  • jitc-asm-arm64::encoding: all instructions are 4 bytes and naturally aligned; encode the integer-arithmetic subset equivalent to Phase 1's x86_64 coverage.
  • island.rs: AArch64 direct branches carry a 26-bit signed word offset (±128 MB, I8); for code buffers larger than that range, the emitter inserts a branch island every 100 KB by default (TOML-tunable), each island a long-range trampoline the encoder can always reach.
  • Calling convention (operand.rs, applying AAPCS64, §5): the first 8 integer arguments in x0–x7, the first 8 floating-point arguments in v0–v7, the remainder on the stack; the stack pointer must be 16-byte-aligned at every public call boundary.
  • CFI hardening (ADR-18): bti j landing pads placed after every label that may be the target of an indirect branch, matching the x86_64 CET equivalent noted in the same ADR row.
  • Every instruction gets a row in conformance/corpora/encoding_arm64/ with golden bytes, mirroring §13.2's x86_64 approach.

21.3 Deliverable

A second Emitter implementation passing the full integer-subset conformance corpus on AArch64, with kernels.yml's cross-arch CI matrix green on both architectures for every fixture landed since Phase 0.

21.4 Acceptance Criteria

100% of conformance/corpora/encoding_arm64/ (≥ 380 golden vectors) pass byte-for-byte; zero Error::BranchOutOfRange failures across a synthetic 200 MB code-buffer stress fixture (confirming I8's island synthesis); the full observable/, baseline/, optimising/, deopt/, osr/, ic/ buckets (§10 conformance corpora) pass identically on AArch64 as they do on x86_64 — the cross-arch parity bar this phase exists to clear.

21.5 Conformance Fixtures

Fixture Purpose Expected Output
branch_island_stress_200mb.vmb Forces an island beyond the 128 MB range Island inserted, branch resolves correctly (I8)
aapcs64_calling_convention.vmb 10-argument call exercising register + stack args Matches interpreter across all argument counts
sp_misalignment_regression.vmb Regression: SP not 16-byte-aligned at a call Encoder asserts, refuses to emit

21.6 Pitfalls

  • The AArch64 stack pointer must be 16-byte-aligned at every public call boundary; misalignment is a hardware fault, not a soft error — the encoder asserts this statically wherever possible rather than relying on runtime detection.
  • bti j (ADR-18) is required at every indirect-branch target under BTI enforcement; omitting it on a CPU with BTI enabled turns an otherwise-valid indirect branch into a hardware fault, a regression class distinct from anything x86_64's Phase 1 encountered.

21.7 Performance Concerns

Branch-island insertion costs a small constant number of extra instructions per 100 KB of code (§21.2's default interval); the interval is tuned to keep this overhead under the peephole-derived 8% budget established informally in Phase 1 (§13.4).

21.8 Edge Cases

A branch target exactly at the ±128 MB boundary (inclusive-boundary test, I8); a method small enough that no island is ever needed (the common case, verified not to regress baseline compile throughput, M1); an indirect branch through a computed jump table needing its own bti j at every possible target.

21.9 Failure Analysis

An undetected out-of-range branch would corrupt control flow non-deterministically depending on how the truncated offset happens to decode — this is why I8 is enforced as a hard encoder assertion (Error::BranchOutOfRange) rather than a warning, and why the 200 MB stress fixture exists specifically to exercise the island-insertion path under CI rather than leaving it untested until a real oversized method appears in production.

21.10 Operational Notes

22. Phase 10 — Safepoints, Stack Maps, GC Integration

22.1 Objectives

Close the loop with the Garbage-Collector project (Ranking 34): finalize safepoint emission across both tiers and both architectures, finalize the stack-map format (§8.4) as the GC's root-scan contract, and land code GC's liveness precondition (I12).

22.2 Detailed Implementation Steps

  • Safepoints are emitted at the sites named in P3/§14.2/§18.2: method entry, loop backedge, allocation, and an explicit poll. A poll is a 5-byte sequence — test [poll_addr], 1 then jne stub — patched to nop when disabled and back to test when the GC (Ranking 34) requests a global safepoint.
  • jitc-runtime::root_scan: for each safepoint, the stack map (§8.4, §11.3) records which stack/spill slots and which registers hold live GC references at that pc; the GC's root scanner walks each thread's stack, looks up the active safepoint for each frame's pc, and reads the stack map — this is the trait-bound cross-project contract named in §3.
  • jitc-codebuf::code_gc: cold methods are reclaimed under memory pressure (ADR-24); the reclamation pass walks the method registry, identifies methods whose last-call timestamp exceeds a threshold, and — only after jitc-runtime::stack_walker confirms zero live activation records for that method (I12) — frees the code-buffer slots.
  • A subsequent invocation of a reclaimed method falls back to the interpreter and re-tiers from its retained (I11-monotonic) counters, not from zero.

22.3 Deliverable

A full safepoint-to-stack-map-to-root-scan path exercised by a joint fixture with the GC project: a live heap reference held only in a register at a safepoint is correctly reported to a simulated collector, across both x86_64 and AArch64.

22.4 Acceptance Criteria

conformance/corpora/safepoint/ (≥ 40 fixtures) confirm 100% stack-map coverage (I3, zero stackmap_missing_total); safepoint poll overhead ≤ 1.5% of steady-state throughput measured on benchmarks/kernels/* (§4, §34 CM8); code-GC reclamation p99 ≤ 10 ms (§4, §30 M14); zero I12 violations (a reclaimed method with a live PC) across a 24-hour fuzz/soak run.

22.5 Conformance Fixtures

Fixture Purpose Expected Output
ref_held_in_register_at_safepoint.vmb GC reference live only in a register Stack map correctly names the register (I3)
code_gc_reclaim_race.vmb Reclamation racing an in-flight call Reclamation deferred one cycle (I12)
poll_toggle_global_safepoint.vmb GC requests a global safepoint mid-execution All threads reach a safepoint within the poll interval

22.6 Pitfalls

  • A safepoint that fires while a deopt bailout is in progress is unsound (I14, cross- referenced with Phase 8, §20.6) — the bailout disables polling for its duration; this phase is where that disable/enable toggle is actually implemented in jitc-runtime.
  • A GC collection that runs while the optimizing tier is mid-compile must not invalidate the SSA values the optimizer holds live in its own working set; the optimizer uses the GC's read-barrier interface (a Ranking-34 contract) rather than assuming compile-time values are immune to collection.

22.7 Performance Concerns

The 5-byte poll sequence (test+jne) is chosen over a full call-based poll specifically to hit the ≤1.5% overhead budget (§4, §34 CM8 derives the per-poll cost ceiling this must clear).

22.8 Edge Cases

A method with zero safepoints (illegal — every method has at least a method-entry safepoint, enforced by construction in both tiers); a global safepoint request arriving while a thread is already inside a disabled-polling window (I14) — the request queues until polling re-enables, never interrupts the bailout.

22.9 Failure Analysis

A stack-map coverage gap (I3 violation) is FM8 in §25 — a GC root-scan miss — the single most severe failure class in this blueprint because it corrupts the heap silently and is a joint failure across two projects (Ranking 34 must also be involved in any postmortem, §26).

22.10 Operational Notes

Metrics: safepoint_poll_total, code_gc_reclaim_total, code_gc_reclaim_blocked_total (I12). docs/architecture/safepoints.md and docs/architecture/codebuf.md jointly document the cross-project root-scan contract; changes here require sign-off from the Ranking-34 GC team per §27's compatibility policy.

23. Phase 11 — Tier Manager, Code-Cache GC, and Concurrent-Compilation Hardening

23.1 Objectives

Production-harden the system: move Tier-2 compilation onto a dedicated background thread (ADR-23), finalize the Tier Manager's promotion/demotion policy (P2, P9, I11), and finalize code GC's generational-by-recency eviction (ADR-24) under real concurrent load.

23.2 Detailed Implementation Steps

  • jitc-tier-manager::counter/threshold/promote: implement the full I11-monotonic counter set (invocation, backedge, IC-shape) and the threshold table (§4: baseline promotion count, optimizing promotion count, TOML-tunable per ADR-19).
  • Background compile thread (ADR-23): the mutator thread(s) always run Tier 0/1 synchronously; a dedicated thread drains a bounded compile-request queue and runs the Tier-2 pipeline (§16–§17); publication of the resulting MethodCode to mutator threads is a single atomic pointer swap — no lock is held across the swap, closing the race named in §25 FM10.
  • Code GC (jitc-codebuf::code_gc, ADR-24): a generational-by-recency (LRU-ish) sweep — methods are bucketed by last-call recency; the coldest bucket is scanned first each cycle, keeping the amortized per-method reclamation-eligibility check within the ≤10 ms p99 budget (§4, §34 CM10 derives the required per-check cost).
  • Wire PhaseDeferred("§23.3") for AOT compiled-code export/import: the compile-request queue and publication protocol built here are the natural extension point, but export/import itself is out of scope for this phase.

23.3 Deliverable

A running jitc process that serves mutator requests through Tier 0/1 without pausing while the background thread compiles Tier-2 methods concurrently, publishing each as it completes, under a 24-hour soak test with ThreadSanitizer enabled.

23.4 Acceptance Criteria

Zero data races detected by ThreadSanitizer across a 24-hour soak (security.yml); code-GC reclamation p99 ≤ 10 ms sustained under a 50,000-live-method synthetic load (§4, §30 M14); background-thread compile throughput sustains ≥ 40,960 IR-instructions/sec (§34 CM7's derived floor); mutator-observed latency for Tier-0/1 execution shows zero measurable stall attributable to concurrent Tier-2 compilation (p99 delta < 0.1 ms vs. single-threaded baseline).

23.6 Pitfalls

  • A MethodCode publication that is not a single atomic pointer swap (e.g., a read-then-write of multiple fields) is a data race the mutator can observe mid-update — FM10 in §25, caught only by ThreadSanitizer, not by the conformance suite's single-threaded fixtures.
  • Code GC scanning the entire method registry every cycle (rather than the coldest bucket only) would blow the 10 ms budget under the 50,000-method hot set (§4) — the generational-by-recency design (ADR-24) exists specifically to avoid this.

23.7 Performance Concerns

The compile-request queue's backpressure policy (bounded capacity, oldest-request-preempted under sustained overload) prevents unbounded memory growth from queued-but-never-compiled requests, at the cost of some methods staying at Tier 1 indefinitely under pathological load — an explicit, documented tradeoff (§31 names this as a scalability bottleneck).

23.8 Edge Cases

Two invocation-count threshold crossings for the same method arriving concurrently on different mutator threads (must enqueue exactly one compile request, not two — deduplicated by a per-method in-flight flag); the background thread crashing mid-compile (the mutator must continue serving Tier 0/1 unaffected — no shared mutable state survives past the atomic publication point); a code-GC cycle and a background compile both targeting the same cold method simultaneously (ordered by acquiring the method's Tier-Manager state lock briefly, the only lock in this phase's design).

23.9 Failure Analysis

FM10 (concurrent-compile data race, §25) is this phase's signature risk; containment is structural (the single-atomic-swap publication protocol) rather than reactive, because a production data race in this subsystem is, by construction, a silent memory-corruption bug with no clean detection path outside of pre-production ThreadSanitizer soak runs (§29).

23.10 Operational Notes

Metrics: compile_queue_depth, compile_queue_backpressure_total, background_compile_duration_seconds. docs/runbooks/code-cache-exhaustion.md and docs/runbooks/slow-promotion.md are the primary on-call references for this phase's concerns; rollback for a bad Tier Manager threshold change is a TOML config revert, requiring no code deploy.

26. Operational Readiness

  • Metrics (ADR-13, Prometheus): every counter/histogram named across §12–§23's N.10 sections is scraped; a single jitc_overview Grafana dashboard (via docker-compose.yml) aggregates tier-transition rates, deopt rates, code-cache occupancy, and compile latencies.
  • Tracing (ADR-12, OpenTelemetry): spans emitted for tier-up, deopt, and OSR events, propagating the host VM's own trace context so a slow request can be attributed to a specific compile event.
  • Structured logging: JSON lines at info level for tier transitions and code-GC cycles; debug level for per-method compile detail (frame size, spill count, pass timings).
  • Dashboards: tier-population pie (Tier 0/1/2 method counts), deopt-rate time series, code-cache occupancy vs. the 64 MB ceiling (§4), compile-queue depth (Phase 11).
  • Alerting philosophy: alert on rate-of-change (deopt storms, megamorphic-transition bursts) rather than absolute thresholds alone, because a single demotion is normal (P5) but a sustained rate is FM2.
  • SLOs: every §4 row is a release-blocking gate (§29), not merely an SLO — the CI/CD pipeline itself enforces them before an SLO dashboard would ever need to.
  • Incident response: docs/runbooks/triage.md is the entry point; it routes to wrong-result.md (FM1), deopt-storm.md (FM2), slow-promotion.md, or code-cache-exhaustion.md (FM3) based on the observed symptom.
  • Backup/restore: not applicable — the code heap holds no state that survives a restart (§3 persistence boundary); "recovery" from any JIT-internal fault is always "restart the host process, re-tier from cold."
  • Deployment topology: one jitc instance per host-VM process; no shared state across processes; horizontal scaling is running more host-VM processes (§31).
  • Canary/rollback: a new jitc release is canaried on a subset of host-VM processes with the full §30 performance-target table gating promotion; rollback is a binary swap plus process restart (no in-place migration, §27).

27. Compatibility & Versioning

  • Wire/storage compatibility: none applicable in-scope — MethodCode, StackMap, and DeoptInfo are process-internal only (§11 annotations); no format crosses a process or version boundary today. AOT export (PhaseDeferred("§23.3")) will introduce the first on-disk format and its own versioning scheme when built.
  • Bytecode-format compatibility: jitc-bytecode targets exactly the host-VM bytecode version declared in Ranking 33's own versioning; a bytecode-format bump requires a corresponding jitc-bytecode release, gated by the observable/ conformance bucket re-running against the new format.
  • API stability: the eleven §11 types are the public embedding surface (docs/sdk/embedding.md); changes follow SemVer at the crate level (ADR-20's workspace) — a breaking change to any §11 signature is a major-version bump across the whole workspace, since crates are versioned together (single-binary principle, P10).
  • Cross-project compatibility (Ranking 34, the GC): the StackMapEntry layout (§11.3) and the root-scan trait boundary (§3) are a joint contract; either project changing this layout requires a coordinated release, recorded as a joint ADR amendment.
  • Deprecation policy: a deprecated TOML config key (ADR-19) is honored with a warning log for one minor version, then rejected with a pointer to the replacement key.
  • Rolling-upgrade guarantees: not applicable — no multi-process shared state exists to roll between versions of (§3 deployment model); each host-VM process runs one jitc version for its entire lifetime.

28. Testing & Verification Strategy

  • Unit tests: per-crate, covering every signature in §11 and every pass named in §16.2.
  • Integration tests: crates/jitc-test-util::golden drives full bytecode-in, machine-code-out fixtures across both architectures.
  • Property tests: I1/I2 (SSA well-formedness), I11 (counter monotonicity), I9 (coalescing soundness) each have a dedicated property-test suite generating adversarial Func/interval inputs.
  • Differential testing: the observable/ bucket is the load-bearing suite — every fixture runs through the interpreter and every tier, asserting identical observable output (P1); this is what H9/I4/I13 ultimately cash out to at the system level.
  • Fuzzing: fuzz/fuzz_targets/ (§10) target the bytecode loader (malformed input, §8.8), the IR verifier (I1/I2), both encoders (constant blinding, FM9; branch range, I8), and deopt reconstruction (I4) — each run for a minimum 24-hour soak before a release tag (§29).
  • Chaos/fault injection: code_gc_50k_live_methods.sim (§23.5) and concurrent_publish_race.vmb inject sustained load and forced races under ThreadSanitizer.
  • Deterministic replay: jitc-test-util::golden fixtures are seeded and replayable bit-for-bit, the mechanism named in §7's debugging methodology.
  • Soak testing: 24-hour minimum for every fuzz target and the concurrent-compilation hardening suite (Phase 11, §23.4) before any release tag.
  • Conformance: the ten conformance/corpora/ buckets (§10) map one-to-one onto the ten phases' N.5 fixtures (§12–§23); CI (conformance.yml) gates on 100% pass for every bucket with fixtures landed to date, Deferred entries carrying a blueprint_ref for anything not yet built.
  • Performance-regression gating: every §30 M-row is checked in benchmarks.yml; a regression beyond the stated target blocks merge, not merely alerts.
  • Tie-back to invariants: every I1–I14 row in §7 names its own detection mechanism, which is one of the test classes above — there is no invariant in this blueprint without a corresponding automated check.

31. Scalability Analysis

Constant regardless of load: per-method metadata shape (StackMap/DeoptInfo/IcSite layouts, §11); the Emitter trait surface (P8); the number of tiers (three, fixed by P10). Grows with load: live-method count (bounded operationally at 50,000, §4, §34 CM2); code-cache occupancy (O(live methods × avg size)); compile-queue depth under sustained tier-up pressure (Phase 11, §23.7).

Named bottlenecks, in order of first saturation:

  1. The background optimizing-compile thread (ADR-23) — a single thread bounded at ≥40,960 IR-instructions/sec (§34 CM7); this is the first resource to saturate under a workload with many simultaneously-hot methods, because Tier-2 compilation is single-threaded by design (§9 ADR-23's "when rejected wins" cell names the regime where a second compile thread would be added).
  2. The code cache (§4: 64 MB ceiling) — saturates only after the compile thread has already produced enough Tier-2 methods to fill it; code GC (ADR-24) delays this but cannot prevent it under sustained growth beyond the operational hot-set target.
  3. Stack-map/deopt-info memory (§34 CM1, CM3) — grows linearly with live-method count; never independently the first bottleneck given the ceiling ratios derived in §34, but becomes binding if the metadata ceiling is lowered independently of the code ceiling.

Horizontal/vertical scaling: this is a single-process, single-instance design (§3 deployment model) with no built-in horizontal scaling — "scaling" means running more independent host-VM processes, each with its own jitc instance and code heap; there is no shared code cache across processes and no plan to add one (a fundamentally different, much larger project). Vertical scaling (more CPU cores) helps the mutator/interpreter side directly but the background compile thread (bottleneck #1) does not itself parallelize without revisiting ADR-23 — a second compile thread is a legitimate future extension but introduces a second MethodCode-publication race class beyond what §23.2 currently handles.

Sharding/partitioning: not applicable — one code heap, one method registry, one tier manager per process (P10).

Coordination overhead: the only cross-thread coordination in the whole system, once Phase 11 lands, is (a) the atomic MethodCode publication swap (§23.2) and (b) the brief per-method Tier-Manager state lock guarding compile-request deduplication (§23.8) — both designed to be O(1) and uncontended in the common case.

Practical ceiling and the levers beyond it: the practical ceiling is the background compile thread's throughput (bottleneck #1); the lever beyond it is a second compile thread (revisiting ADR-23, requiring a redesign of the publication protocol to remain race-free) — noted as a natural Phase-11+ extension, not built in this plan.

32. Mental Models & First Principles

  1. MM1 — "A MethodCode is a promise, not a fact." Compiled code is provisional, revocable via deopt or code GC, never a permanent fact about the method. Predicts: every call site needs a re-validation path, never a bare cached address. Bug class without it: assuming compiled addresses are permanent leads to dangling calls after code-GC eviction (T10, FM10-adjacent). Resolving: §22 (I12), §20.
  2. MM2 — "Type feedback is a cache with a write-once-per-shape law." IC states only escalate (I6), never retreat. Predicts: monotonic promotion is the only safe direction. Bug class without it: allowing backward transitions causes promotion/demotion thrashing. Resolving: §18, §7 I6.
  3. MM3 — "SSA dominance is just 'define before use,' generalized to a graph." Predicts exactly what a verifier must check (I1) and why block arguments need dominance-frontier placement. Bug class without it: a value used on a path where it was never defined — a crash or worse, a silently wrong read of stale register contents. Resolving: §15, §7 I1.
  4. MM4 — "Deoptimization is the interpreter's insurance policy, and the optimizer pays the premium." Every speculative optimization (type specialization, escape analysis) must leave behind enough state to "pay out" a full, correct interpreter frame on failure. Predicts: a pass that can't explain its own deopt story isn't safe to ship. Bug class without it: unrecoverable speculation — the optimizer commits to an assumption with no fallback. Resolving: §20, §6 P5.
  5. MM5 — "W^X is a physical promise enforced by the MMU, not a convention." Predicts: no amount of type-level Rust safety substitutes for the OS-enforced page-permission guarantee. Bug class without it: trusting a "we never write after freeze" convention instead of a hardware-enforced one — exactly the gap JIT-spray exploits. Resolving: §12, §7 I5, §24 T1/T2.
  6. MM6 — "A safepoint is a rendezvous point the compiler negotiates with the collector." Predicts: every safepoint needs a matching, complete stack map or the rendezvous fails silently. Bug class without it: emitting safepoints without stack maps, or vice versa. Resolving: §22, §7 I3.
  7. MM7 — "Escape analysis answers 'does this pointer leave my postcondition,' not 'is this object small.'" Predicts: the analysis must track flow to returns/stores/calls, not object size. Bug class without it: treating a small-but-escaping object as safe to scalar-replace, a wrong-result bug (FM1). Resolving: §16.4.
  8. MM8 — "Tiering is a bet sized by counters, not by static prediction." Predicts: the Tier Manager's decisions are always retrospective (observed invocation/backedge counts), never a static heuristic guessing at hotness ahead of time. Bug class without it: static "this loop looks hot" heuristics mis-predict real workloads and waste the optimizing tier's compile budget on cold code. Resolving: §23, §6 P9.

LuaJIT chose to skip a method-JIT tier entirely and JIT only observed hot traces, buying excellent code quality for tight monomorphic loops at the cost of poor behavior on branchy/polymorphic code (ADR-02's rejection reason); it wins in embedded/game-scripting workloads dominated by numeric inner loops.

GraalVM/Graal chose to derive its JIT entirely from partial evaluation of an AST interpreter (Truffle) rather than hand-writing tiers, buying language-implementation reuse (one meta-compiler serving many "Truffle languages") at the cost of a much larger and more complex compiler substrate; it wins when the goal is a polyglot VM amortizing one optimizing backend across many front-end languages.

34. Back-of-Envelope Capacity Model

Every number below is derived from a §4 System Constraints row, formula shown.

  • CM1 — Stack-map bytes/method. avg 4 safepoints/method × 128 B/StackMapEntry (pc 4B + gc_refs SmallVec<8>×4B=32B + spills SmallVec<4>×4B=16B + RegSet 8B + ~68B overhead/alignment) = 512 B/method — matches §4's ≤512 B budget exactly (derived, not independently asserted).
  • CM2 — Max live compiled methods. Weighted avg method size at steady-state tier mix (80% baseline @ 220 B + 20% optimizing @ 900 B) = 0.8×220 + 0.2×900 = 356 B/method. 64 MB code-cache ceiling (§4) ÷ 356 B ≈ 179,700 theoretical max; operational hot-set target set at ≤ 50,000 (§4) via code-GC eviction (§23) targeting working-set locality rather than the theoretical ceiling.
  • CM3 — Deopt-info bytes, total. avg 6 guards/method (3 speculative-inline guards, ADR-14, + ~3 ordinary type/shape guards) × 96 B/guard (§4) × 10,000 optimizing-tier methods (20% of the 50,000 hot set, CM2) = 5.76 MB — 9% of the 64 MB metadata ceiling.
  • CM4 — IC-site memory. avg 8 call/property sites per method (typical of the host VM's ~80-opcode dynamic-dispatch surface) × 32 B/site (§4) × 50,000 methods = 12.8 MB — 20% of the metadata ceiling. Combined with CM1 (512B × 50,000 = 25.6 MB, 40%) and CM3 (9%), total metadata ≈ 43.3 MB against the 64 MB metadata ceiling — 32% headroom, confirming the ceiling split between code bytes and metadata (§4) is not over-committed.
  • CM5 — Baseline emission rate. ≥50 MB/s bytecode (§4, M1) × ~3.5x code-size expansion ratio (typical for 1:1 baseline lowering with register moves and safepoint polls) ≈ 175 MB/s of machine code at full tilt — sizes the RW-alias mmap growth rate and the relocation-batching strategy in Phase 0/1 (§12, §13).
  • CM6 — Max synchronously-compilable bytecode size. 10 ms tier-up budget (§4) × 50 MB/s baseline throughput (§4) = 500,000 bytes of bytecode — far above any single host-VM method (Ranking 33 caps method bytecode size well under 64 KB), confirming baseline tier-up always completes synchronously within budget without needing a background path.
  • CM7 — Minimum optimizing-tier throughput. 4,096 IR-instruction method-size cap (§4) ÷ 100 ms compile budget (§4, ADR-16) = 40,960 IR-instructions/sec/thread — the concrete lower bound Phase 5's register allocator (§17) and Phase 11's background compile thread (§23.4) must both clear.
  • CM8 — Max tolerable per-safepoint-poll cost. 1.5% steady-state throughput tax (§4) ÷ 4 safepoints/method (CM1) → per-poll cost must stay a small fraction of a typical method's run length — justifies the 5-byte test+jne poll sequence (§22.7) over a full call-based poll.
  • CM9 — perf jit-dump growth rate. ~50 optimizing compiles/sec worst-case (bounded by ADR-14's guard cap limiting deopt-driven recompiles) × ~256 B/jit-dump record ≈ 12.8 KB/s ≈ 1.1 GB/day — confirms the single FD (§4 FD budget) never needs rotation within a reasonable operational log-retention window.
  • CM10 — Code-GC per-method check cost ceiling. 10 ms reclamation p99 (§4) ÷ 50,000 hot-set size (CM2) = 200 ns/method amortized — justifies the generational-by-recency (LRU-ish) design (ADR-24) over a full linear sweep every cycle, since a linear scan of the full registry at 50,000 methods could not meet 200 ns/method with any nontrivial per-method work.

36. Alternative Architectures (Roads Not Taken)

AA1 — Trace-based JIT.

interpreter ── records hot path ──▶ linear trace IR ──▶ compiled trace
      ▲                                                        │
      └──────────────── side exit (guard fail) ◀───────────────┘

Regime: tight numeric loops, few polymorphic call sites. Real system: LuaJIT 2.x (Pall, §5). Rejected (ADR-02): the host VM's workload is branchy/polymorphic; trace JITs multiply side exits under exactly that condition, degrading rather than improving over a method JIT.

AA2 — Meta-tracing.

one interpreter definition ──▶ meta-tracer generates a JIT ──▶ N target languages served

Regime: rapid retargeting of one JIT engine across many interpreters. Real system: PyPy / RPython (Bolz et al. 2009, §5). Rejected: this project targets exactly one fixed bytecode format, so meta-tracing's cross-language generality buys nothing, while its higher warm-up cost and larger trace trees are pure downside here.

AA3 — Sea-of-nodes optimizing IR.

   ┌─ control edges ─┐     ┌─ data edges ─┐
   │  fully merged into one graph, schedule computed late  │

Regime: maximal peephole/global scheduling freedom at the cost of harder deterministic verification. Real system: HotSpot C2 / V8 TurboFan (Click 1995, §5). Rejected (ADR-03): this blueprint prioritizes deterministic verifiability (I1/I2) and debuggability over the last few percent of schedule freedom a sea-of-nodes graph would buy.

AA4 — Template / copy-and-patch baseline compiler.

bytecode op ──▶ pre-compiled machine-code template ──▶ stitched output (no IR, no regalloc)

Regime: minimize baseline-tier compile latency further, at the cost of code quality. Real system: V8 Sparkplug; also "Copy-and-Patch Compilation" (Xu & Kjolstad, 2021, Proc. ACM Program. Lang., OOPSLA, §5). Rejected here: linear-scan baseline (ADR-04) already meets the ≤10 ms tier-up SLO (§34 CM6), so the added build complexity of a template compiler isn't justified yet — noted as a Deferred Features Register entry (§37) rather than built now.

38. Glossary

  • Backedge — a control-flow edge from the end of a loop body back to the loop header; the trigger point for OSR (§19) and one of P3's mandatory safepoint sites.
  • Baseline JIT (Tier 1) — the 1:1 bytecode-to-machine compiler with linear-scan register allocation (§14).
  • BCE — bounds-check elimination; a Phase-4 pass removing provably-safe array bounds checks via induction-variable range analysis (§16.2).
  • Block argument — an SSA merge value carried as a basic block's parameter, replacing a separate phi instruction (§8.2, ADR-03).
  • Branch island — a long-range trampoline inserted into AArch64 code to reach a target beyond the ±128 MB direct-branch range (§21.2, I8).
  • CFG — control-flow graph; the basic-block structure underlying the SSA IR (§8.2).
  • Code GC — the reclamation pass that evicts cold compiled methods from the code heap under memory pressure (§22.2, ADR-24).
  • Code heap — the W^X-protected memory region holding all compiled machine code (§3, §12).
  • Coalescing — merging two non-interfering register-allocation intervals to eliminate a mov; must respect register class (I9, §17.2).
  • Constant blinding — XOR-obfuscating embedded constants with a per-process secret to resist JIT-spraying (P7, ADR-07).
  • Deoptimization (deopt) — the process of abandoning compiled execution and resuming in the interpreter with a reconstructed frame (§20, I4).
  • Dominance frontier — the set of blocks where a definition's dominance ends and a block argument must be inserted (Cytron et al. 1991, §5, §15.2).
  • Escape analysis — determining whether an allocation's result can leave the current compilation unit, enabling scalar replacement if not (§16.2, §16.4).
  • Frame reconstruction — rebuilding an interpreter-compatible stack frame from a DeoptBailout descriptor during a deopt bailout (§20.2).
  • GVN — global value numbering; a Phase-4 pass deduplicating redundant pure computations (§16.2).
  • Guard — a runtime check (e.g. checkshape) whose failure triggers a deopt (§8.2, §20.1).
  • Hidden class / Shape — a compact identifier for an object's layout, used for IC dispatch and type specialization (§11.2, §18).
  • IC (inline cache) — a call/property-access site that caches dispatch information to avoid repeated dynamic lookup (P4, §18).
  • IC site — the per-call-site record of an IC's state and observed shapes (§11.7).
  • Inlining — replacing a call with the callee's body at the call site, subject to a size budget and a speculative-guard cap (§16.2, ADR-14).
  • Interference graph — the graph whose nodes are live ranges and whose edges mark overlapping ranges, used by graph-coloring register allocation (§17.2).
  • jit-dump — the Linux perf file format for exposing JIT-compiled code layout to the perf profiler (§5 RFCs/Specs, ADR-21).
  • LICM — loop-invariant code motion; hoisting loop-invariant computations out of a loop body (§16.2).
  • Linear-scan register allocation — an allocator that assigns physical registers by walking sorted live intervals in one pass (Poletto & Sarkar 1999, §5, §14.3).
  • Live range — the span of program points over which a value is live, the unit both register allocators operate on (§14.3, §17.2).
  • Megamorphic — an IC state past polymorphic capacity, falling back to full dynamic dispatch (I6, §18.3).
  • Meta-tracing — generating a JIT automatically from an interpreter definition rather than hand-writing tiers (§36 AA2, PyPy).
  • Method-JIT — a JIT architecture that compiles whole methods, as opposed to traces (ADR-02, this project's chosen family).
  • Monomorphic — an IC state observing exactly one shape (I6, §18.2).
  • NaN-boxing — encoding multiple value types (int, float, object reference) into the bit pattern of a 64-bit float's NaN space (§11.2).
  • Optimizing JIT (Tier 2) — the SSA-IR-based tier performing inlining, escape analysis, type specialization, and graph-coloring register allocation (§15–§17).
  • OSR (on-stack replacement) — transitioning a currently-executing interpreted method into compiled code mid-execution, at a loop backedge (§19, I13).
  • PIC — polymorphic inline cache; see IC (Hölzle, Chambers, Ungar 1991, §5).
  • Peephole — a small local rewrite pass applied to emitted machine code before sealing (§13.2).
  • Phi node — the classical SSA merge-value representation; this project uses block arguments instead (ADR-03).
  • Polymorphic — an IC state observing up to 4 distinct shapes (ADR-15, §18.3).
  • Profile feedback — runtime-observed counters (invocation, backedge, IC shape) driving tier-up and type-specialization decisions (P9, I11).
  • Reference implementation — a real, existing JIT studied for lessons/pitfalls (§5).
  • Relocation (reloc) — a deferred address fixup applied to emitted code before sealing (§8.3, §11.6).
  • Safepoint — a program point where a thread's stack is guaranteed walkable and GC-safe (P3, I3, §22).
  • Scalar replacement — replacing a non-escaping allocation's fields with plain SSA values, eliminating the allocation (§16.2, §16.4).
  • Sea-of-nodes — an IR representation merging control and data into one graph with late scheduling (Click 1995, §5, §36 AA3).
  • Shape — see Hidden class.
  • Speculative inlining — inlining behind a guard that may later fail and deopt (P12, ADR-14).
  • Stack map — the per-safepoint table of which slots/registers hold live GC references (§8.4, §11.3, I3).
  • Tier — one of Interpreter (0), Baseline (1), Optimising (2) (§11.1).
  • Tier Manager — the component owning all promotion/demotion decisions (jitc-tier-manager, P2, §23).
  • Trace JIT — a JIT architecture that compiles observed hot execution traces rather than whole methods (§36 AA1, LuaJIT).
  • Type feedback — observed runtime shape/type information driving type specialization (Hölzle & Ungar 1994, §5, §16.2).
  • Type specialization — replacing a dynamic-dispatch operation with a guarded direct operation based on type feedback (§16.2).
  • W^X (Write XOR Execute) — the invariant that no memory page is simultaneously writable and executable (P6, I5).
