34. Back-of-Envelope Capacity Model

Every number below is derived from a §4 System Constraints row, formula shown.

  • CM1 — Stack-map bytes/method. avg 4 safepoints/method × 128 B/StackMapEntry (pc 4B + gc_refs SmallVec<8>×4B=32B + spills SmallVec<4>×4B=16B + RegSet 8B + ~68B overhead/alignment) = 512 B/method — matches §4's ≤512 B budget exactly (derived, not independently asserted).
  • CM2 — Max live compiled methods. Weighted avg method size at steady-state tier mix (80% baseline @ 220 B + 20% optimizing @ 900 B) = 0.8×220 + 0.2×900 = 356 B/method. 64 MB code-cache ceiling (§4) ÷ 356 B ≈ 179,700 theoretical max; operational hot-set target set at ≤ 50,000 (§4) via code-GC eviction (§23) targeting working-set locality rather than the theoretical ceiling.
  • CM3 — Deopt-info bytes, total. avg 6 guards/method (3 speculative-inline guards, ADR-14, + ~3 ordinary type/shape guards) × 96 B/guard (§4) × 10,000 optimizing-tier methods (20% of the 50,000 hot set, CM2) = 5.76 MB — 9% of the 64 MB metadata ceiling.
  • CM4 — IC-site memory. avg 8 call/property sites per method (typical of the host VM's ~80-opcode dynamic-dispatch surface) × 32 B/site (§4) × 50,000 methods = 12.8 MB — 20% of the metadata ceiling. Combined with CM1 (512B × 50,000 = 25.6 MB, 40%) and CM3 (9%), total metadata ≈ 43.3 MB against the 64 MB metadata ceiling — 32% headroom, confirming the ceiling split between code bytes and metadata (§4) is not over-committed.
  • CM5 — Baseline emission rate. ≥50 MB/s bytecode (§4, M1) × ~3.5x code-size expansion ratio (typical for 1:1 baseline lowering with register moves and safepoint polls) ≈ 175 MB/s of machine code at full tilt — sizes the RW-alias mmap growth rate and the relocation-batching strategy in Phase 0/1 (§12, §13).
  • CM6 — Max synchronously-compilable bytecode size. 10 ms tier-up budget (§4) × 50 MB/s baseline throughput (§4) = 500,000 bytes of bytecode — far above any single host-VM method (Ranking 33 caps method bytecode size well under 64 KB), confirming baseline tier-up always completes synchronously within budget without needing a background path.
  • CM7 — Minimum optimizing-tier throughput. 4,096 IR-instruction method-size cap (§4) ÷ 100 ms compile budget (§4, ADR-16) = 40,960 IR-instructions/sec/thread — the concrete lower bound Phase 5's register allocator (§17) and Phase 11's background compile thread (§23.4) must both clear.
  • CM8 — Max tolerable per-safepoint-poll cost. 1.5% steady-state throughput tax (§4) ÷ 4 safepoints/method (CM1) → per-poll cost must stay a small fraction of a typical method's run length — justifies the 5-byte test+jne poll sequence (§22.7) over a full call-based poll.
  • CM9 — perf jit-dump growth rate. ~50 optimizing compiles/sec worst-case (bounded by ADR-14's guard cap limiting deopt-driven recompiles) × ~256 B/jit-dump record ≈ 12.8 KB/s ≈ 1.1 GB/day — confirms the single FD (§4 FD budget) never needs rotation within a reasonable operational log-retention window.
  • CM10 — Code-GC per-method check cost ceiling. 10 ms reclamation p99 (§4) ÷ 50,000 hot-set size (CM2) = 200 ns/method amortized — justifies the generational-by-recency (LRU-ish) design (ADR-24) over a full linear sweep every cycle, since a linear scan of the full registry at 50,000 methods could not meet 200 ns/method with any nontrivial per-method work.
