⬜ Phase 1 — URL Normalization and Bloom Filter §13

Objectives

Build the total, idempotent URL normalizer (§8 pipeline) and the mmap-backed Bloom filter (zero false negatives), the two-stage dedup foundation everything else depends on. Constraints introduced: normalization must be a pure total function (P4); the Bloom filter must guarantee zero false negatives by construction (P6).

Deliverable

crates/dedup/src/{normalize.rs, bloom.rs}; a serialized Bloom file with a 16-byte header (magic + num_bits + k + seeds); a --dry-run mode that prints canonical forms for a URL list.

Acceptance

cargo test -p dedup green; proptest idempotency holds (I6); 1M-insert test shows 0 false negatives and FPR < 1.5% (I7); normalization < 1 µs/URL and Bloom lookup < 100 ns on the §4 bench corpus; dedup foundation proven: idempotent total normalization (I6), zero-false-negative persistent Bloom (I7).

Fixtures
Fixture Purpose Expected
conformance/normalize/rfc3986_suite.json 40 RFC 3986 §6.2 cases each input → expected canonical form
conformance/normalize/query_sort.json 10 query-sort stability cases ?b=2&a=1 ≡ ?a=1&b=2
conformance/bloom/sizing.json sizing for n=100M, p=0.01 ~958 MiB bits, k=7
proptest idempotency random URL strings normalize(normalize(x)) == normalize(x), no panic (I6)
1M-insert accuracy FPR measurement 0 false negatives (I7); FPR < 1.5%
Pitfalls
  1. Double-percent-encoding. Applying percent-encoding normalization twice to an already-normalized URL must be a no-op. Implementing normalization as a string replace (e.g., s.replace("%2f", "/")) without tracking context can produce double-encoded URLs like %252F. The correct approach: decode percent-encoded sequences one at a time using a state machine and re-encode only what needs to be re-encoded.
  2. Bloom filter off-by-one in bit addressing. Using num_bits as usize when the backing mmap is sized in bytes (num_bits / 8 + 1 bytes) can produce out-of-bounds panics. Calculate byte size carefully: (num_bits + 7) / 8.
  3. SipHash seed reproducibility. If the seeds are not persisted with the Bloom filter file, restarting the crawler with different seeds will produce a filter that does not match the stored bits. Store the seeds in the first 64 bytes of the mmap file.
  4. url crate Origin vs. host. Url::host_str() returns None for file:// and data: URLs. Filter before normalization; return NormalizationError::UnsupportedScheme (P4: normalization is total).

⬜ Phase 2 — robots.txt Parser and Cache §14

Objectives

Implement an RFC 9309-conformant robots.txt parser, evaluator (longest-match precedence, wildcards), and a TTL'd per-domain cache — the gate that enforces Principle P8 and Invariant I4. Constraint introduced: no fetch proceeds while a robots verdict is unknown (fail closed, not open).

Deliverable

crates/robots/src/{parser.rs, rules.rs, cache.rs, pattern.rs}; the conformance suite under conformance/robots/cases/.

Acceptance

cargo test -p robots passes all 50+ REP conformance cases; verdict obeys longest-match precedence with Allow-wins-ties; cache TTL expiry verified; cache hit < 500 ns; pattern match < 100 ns (compiled Regex cached per pattern, compile cost ~1–10 µs once); no fetch proceeds on an unknown or disallowed verdict (I4).

Fixtures
Fixture Purpose Expected
cases/allow_disallow_precedence.yaml 10 longest-match cases longest pattern wins; tie → Allow
cases/wildcard_patterns.yaml 8 */$ cases correct anchored/greedy match
cases/crawl_delay.yaml 5 Crawl-delay cases float parsed; floor enforced (I12)
cases/multi_agent_groups.yaml 6 multi-User-agent cases matching groups merged, not replaced
cases/empty_and_404.yaml empty + 404 robots allow all
live google.com/robots.txt smoke test paths classified without panic
Pitfalls
  1. Greedy wildcard matching. The * wildcard in robots.txt is not a POSIX glob *; it matches any sequence including /. A naive implementation that splits on / will fail. Use a proper NFA-style or DP match.
  2. User-agent case sensitivity. "googlebot" must match "Googlebot" in User-agent. Case-insensitive match on the user-agent value, but case-sensitive match on path patterns.
  3. Multiple User-agent: * groups. Some robots.txt files have two User-agent: * groups (malformed). RFC 9309 says: concatenate all matching groups into one. Implement group merging, not group replacement.
  4. Crawl-delay as float. Crawl-delay: 1.5 is valid. Parse as f64. Some sites use Crawl-delay: 0 (no delay requested). Still enforce a minimum delay of config.default_crawl_delay (see Principle 1: politeness is an invariant).
  5. robots.txt larger than expected. Some servers return 10 MB robots.txt files. Cap the robots.txt body at 512 KB (RFC 9309 recommendation). Truncate at the last complete line within that limit.

⬜ Phase 3 — Token-Bucket Scheduler §15

Objectives

Enforce per-domain politeness — exactly one in-flight fetch per host and ≥ effective crawl-delay spacing — without a central lock or starvation. This is the architectural home of Invariant I1. Constraint introduced: fairness across domains must hold even under concurrent load from thousands of active domains.

Deliverable

crates/scheduler/src/{scheduler.rs, token_bucket.rs, domain_state.rs}; a mock-clock test harness for deterministic rate-limit assertions.

Acceptance

Mock-clock tests prove ≤ 1 request per crawl-delay interval and in_flight ≤ 1 at all times (I1); try_acquire() < 1 µs under 100k concurrent domain updates; the scheduling loop never spins (verified via CPU-idle assertion while sleeping on time_until_available); effective delay ≥ max(robots_delay, default) × multiplier with multiplier > 0 enforced at startup (I12); no slow-domain starves under load from a fast domain (fair selection by smallest time_until_available).

Fixtures
Fixture Purpose Expected
conformance/scheduler/rate_limit_1rps.json 10 attempts at Crawl-delay: 1 all ≥ 1 s apart (mock clock)
conformance/scheduler/concurrent_limit.json concurrency cap in_flight ≤ 1 always (I1)
crawl_delay_2s.json Crawl-delay: 2 under pressure ≤ 1 req / 2 s
multiplier_floor.json politeness_multiplier applied effective delay ≥ floor (I12)
Pitfalls
  1. Floating-point accumulation drift. tokens is f64. After millions of refill operations, accumulated FP error can cause tokens to drift above capacity or below 0. Clamp: tokens = tokens.min(capacity as f64).max(0.0) after every refill.
  2. Instant monotonicity on some platforms. On Linux with some clock sources, Instant::now() can, in rare cases, return a value less than a previous Instant. Guard: if elapsed.is_negative() (shouldn't happen with Instant in Rust, but defensive), treat as zero elapsed.
  3. DashMap contention at high domain counts. With 1M active domains, shard count defaults may cause lock contention. Configure DashMap::with_capacity_and_shard_amount(1_000_000, 256) for better distribution.
  4. Starvation of slow domains. If a fast domain (short crawl delay) continuously produces new URLs that are immediately fetchable, slow domains may never get scheduled. Implement fair scheduling: in the dequeue step, select the domain with the smallest time_until_available() among all domains with pending URLs, not just the domain with the highest-priority URL.

⬜ Phase 4 — Async HTTP Fetcher §16

Objectives

Build the async HTTP/1.1+HTTP/2 fetcher: TLS via rustls, redirect following with loop detection, timeouts, charset detection, robots.txt fetch, and SSRF guards — failures as first-class values (P3). Constraint introduced: every input, however malformed, must yield a FetchResult, never a panic (I8).

Deliverable

crates/fetcher/src/{fetcher.rs, client.rs, redirect.rs, response.rs, charset.rs}; the SSRF-guarding connector; the wiremock integration test suite.

Acceptance

cargo test -p fetcher green against wiremock; p50/p95/p99 within the §4 budgets (≤150 ms / ≤600 ms / ≤2 s) on a local mock; connection-pool hit rate > 90% for multi-URL domains; zero panics across the malformed-response fuzz corpus (I8); an SSRF redirect to 127.0.0.1 is rejected and the URL marked Skipped (I5); redirect chains terminate within max_redirects with cycle detection (I13).

Fixtures
Fixture Purpose Expected
fixtures/200_html.http basic 200 body extracted correctly
fixtures/301_redirect.http relative redirect final URL resolved correctly (I13)
fixtures/gzip_body.http gzip body transparent decompression
wiremock redirect loop cycle detection TooManyRedirects (I13)
wiremock stall timeout Timeout within read_timeout
SSRF redirect to 127.0.0.1 I5 guard connection rejected, Skipped
Pitfalls
  1. reqwest and hyper version mismatch. reqwest 0.12 requires hyper 1.x. If any transitive dependency pulls in hyper 0.14, there will be a compile error. Pin hyper to 1.x explicitly in the workspace Cargo.toml under [dependencies].
  2. TLS certificate validation failure for self-signed certs (test servers). The wiremock server in tests uses HTTP, not HTTPS. Fetcher tests that test TLS should use a separate HTTPS mock (e.g., rcgen + axum with TLS). Do not disable TLS verification in production code.
  3. Connection pool exhaustion. If all max_idle_per_host connections are in use and the pool cannot create new ones (due to OS file descriptor limits), fetch() will hang. Set ulimit -n 65536 in Docker and CI. Log a warning when the pool is at capacity.
  4. Content-Length mismatch. A server that sends a Content-Length of 5000 but closes the connection after 3000 bytes. reqwest returns an error; the fetcher should classify this as FetchError::Tcp (connection reset).
  5. User-Agent header spoofing. The User-Agent header is set via reqwest::RequestBuilder::header(). If the reqwest::Client was built with a default User-Agent, the per-request header will conflict. Build the client with .user_agent("") and set per-request.

⬜ Phase 5 — HTML Parser and Link Extractor §17

Objectives

Extract all outbound http(s) links from a fetched page using spec-compliant html5ever, resolving against the document base URL, never panicking on malformed HTML. Constraint introduced: the parser runs only on text/html/application/xhtml+xml content (P5, upstream gate).

Deliverable

crates/parser/src/{extractor.rs, base_url.rs}; a crawl parse <url> <html_file> CLI subcommand; the fixture suite.

Acceptance

cargo test -p parser green on all fixtures; a 1 MB page parses in < 50 ms (M10); the fuzz target (§22) is panic-free for 24 h; only http/https links with a non-empty host are returned; first-<base href>-only and protocol-relative resolution both verified by fixture.

Fixtures
Fixture Purpose Expected
fixtures/simple.html 5 <a href> 5 absolute URLs
fixtures/base_href.html <base href> resolution links resolved against base
fixtures/relative_urls.html relative + protocol-relative resolved against base scheme
fixtures/malformed.html unclosed tags / missing quotes html5ever recovers; links extracted
fixtures/no_links.html empty doc empty Vec

Pitfalls
  1. html5ever TreeSink lifetime complexity. The TreeSink trait requires 'static lifetimes in some methods. If LinkSink holds a &mut Vec<Url>, the borrow checker will reject it. Solution: use interior mutability (Rc<RefCell<Vec<Url>>>) inside LinkSink and extract the results after parsing.
  2. Base URL mutation order. If a <base href> appears after some links, those earlier links should be resolved against the original base URL, not the <base href>. html5ever emits elements in document order; only update the base URL on the first <base> element encounter.
  3. Relative // protocol-relative URLs. A link like href="//cdn.example.com/file.js" is protocol-relative. Resolve against the base URL's scheme: http:// → http://cdn.example.com/file.js. The url crate handles this correctly when using parse_with_base.
  4. data: URIs. Some pages use href="data:text/html,...". Filter these (scheme != http/https) — do not attempt to parse or follow them.

⬜ Phase 6 — URL Frontier (RocksDB Backend) §18

Objectives

Build the durable, crash-safe URL frontier: RocksDB-backed urls/domains/metadata column families with an in-memory priority heap, BFS-favoring ordering, and zero-loss recovery. Constraint introduced: every enqueue must be WAL-durable before acknowledgement (P2, I2).

Deliverable

crates/frontier/src/{frontier.rs, rocksdb_backend.rs, priority_queue.rs, record.rs}; a crash-recovery test harness; the hourly compaction maintenance hook.

Acceptance

Sustained 1,000 enqueue/s; a kill -9 recovery test loses 0 queued URLs (I2); dequeue order is ascending by next_fetch_at; enqueue < 500 µs, dequeue < 1 ms (M5, M6); the heap never serves a record whose RocksDB status is not Queued (I3); enqueue() returns Full once max_frontier_size is reached (I14); cargo test -p frontier green.

Fixtures
Fixture Purpose Expected
fixtures/seed_urls.txt 100-URL enqueue/dequeue roundtrip all persisted and dequeued
fixtures/priority_ordering.json 20 URLs, varied next_fetch_at dequeue ascending by next_fetch_at
kill -9 recovery test crash safety (I2) 0 queued URLs lost on restart
heap/CF divergence test I3 dequeue discards records whose status ≠ Queued
capacity test I14 enqueue returns Full at max_frontier_size
Pitfalls
  1. RocksDB write stalls. When the memtable fills faster than compaction can flush it, RocksDB stalls writes. Symptom: enqueue() blocks for seconds. Mitigate: set write_buffer_size = 64 MB, max_write_buffer_number = 4, and enable level-compaction. Monitor rocksdb.estimate-pending-compaction-bytes via the metrics crate.
  2. In-memory heap divergence from RocksDB. On restart, the heap is rebuilt from RocksDB. If the heap was not fully persisted before shutdown, some URLs in the heap may have already been fetched (their status is Fetched in RocksDB). The dequeue() implementation must check the RocksDB status after loading from the heap; discard any UrlRecord whose status is not Queued.
  3. WriteBatch atomicity. All enqueue operations that touch both urls and domains column families must use a WriteBatch. A half-written enqueue (URL inserted but domain counter not updated) will cause inconsistency. Never write to multiple column families without a WriteBatch.
  4. RocksDB column family handle lifetime. The DB and ColumnFamilyHandle must have the same lifetime. In Rust, wrapping them in Arc<DB> and ColumnFamily<'_> creates lifetime issues. Solution: use the Arc<DB> pattern from the rocksdb crate's examples; store CF handles by name and retrieve them each time (negligible cost).

⬜ Phase 7 — WARC Writer and Metadata Storage §19

Objectives

Write archival-quality, append-only WARC 1.0 records (with SHA-256 block digests and rotation) plus a queryable SQLite metadata store with byte-offset tracking for future CDX. Constraint introduced: a committed WARC record is never modified after write (P10, I10).

Deliverable

crates/storage/src/{warc.rs, metadata.rs, record_id.rs}; the SQL schema + migrations; a WARC reader test harness.

Acceptance

cargo test -p storage green; a written WARC verifies byte-for-byte with warcio and its digest matches on read-back (I10); rotation triggers correctly at both the 1 GiB and 100k-record thresholds; SQLite is queryable after a test crawl; WARC write throughput ≥ 50 MB/s (§4, M7); byte offsets are recorded for every record, enabling future CDX generation.

Fixtures
Fixture Purpose Expected
fixtures/warc_record.bin precomputed record byte-for-byte match
conformance/warc/samples/sample.warc real Common Crawl WARC reader parses; digest verifies
rotation test size/count thresholds new file at 1 GiB / 100k records; old sealed
digest re-verify I10 WARC-Block-Digest matches body on read-back
SQLite roundtrip metadata insert/query consistent after batch commit
Pitfalls
  1. Gzip stream not flushed before rotation. If GzEncoder::flush() is not called before rotation, the last chunk of compressed data may be lost. Always call encoder.try_finish() (not just flush()) to write the gzip footer.
  2. WARC record byte offset off-by-one. The offset must be recorded before writing the record, not after. Use stream_position() on the underlying File before compressing (note: the gzip offset in the compressed file is not useful; store the uncompressed offset for CDX compatibility — requires tracking separately).
  3. SQLite WAL mode and multiple writers. rusqlite with WAL mode allows one writer and multiple readers. The WarcWriter and MetadataDb are the only writers; ensure no concurrent Connection objects attempt writes simultaneously. Use a Mutex<Connection> if needed.
  4. WARC Content-Length includes HTTP headers + body. The Content-Length WARC header counts the entire HTTP response (status line + headers + CRLF + body), not just the body. Compute it as record.http_response.len(), which is the raw bytes as received.

⬜ Phase 8 — Coordinator and Full Pipeline Integration §20

Objectives

Wire every subsystem into one runnable async pipeline — frontier → robots → scheduler → fetcher pool → parser → dedup → storage → frontier — with back-pressure, SimHash near-dup detection, and graceful shutdown. Constraint introduced: shutdown must drain within a configured timeout without corrupting any persisted state (P12).

Deliverable

crates/coordinator/src/{coordinator.rs, shutdown.rs}; SimHashIndex; the full integration test against the mock crawl graph.

Acceptance

cargo run --bin crawl -- --config config.toml crawls https://example.com to depth 2, writing WARC + SQLite; the 10-page mock-site integration test completes with zero panics; sustained 100 pages/s (M1); graceful shutdown completes ≤ 30 s (M12, P12); back-pressure prevents deadlock under a full worker channel; near-duplicates are correctly skipped.

Fixtures
Fixture Purpose Expected
tests/fixtures/mock_site/ 10-page crawl graph all 10 fetched, in SQLite + WARC, no panic
back-pressure test bounded channel coordinator blocks when workers busy, no deadlock
near-dup test SimHash duplicate page flagged, link extraction skipped
shutdown test SIGTERM mid-crawl drain ≤ 30 s, no corruption (P12)
Pitfalls
  1. Back-pressure deadlock. If the coordinator is blocked sending to a full worker channel while a worker is blocked sending a result back on a full result channel, a deadlock occurs. Solution: use separate send/receive channels; workers send results to a tokio::sync::mpsc::Sender<FetchResult> (unbounded, or with a large buffer); the coordinator consumes results in a separate tokio::select! arm.
  2. Robots cache miss storm. On startup with 1,000 seed URLs from 1,000 different domains, 1,000 concurrent robots.txt fetches are triggered. This can overwhelm the network. Implement a robots_fetch_semaphore: Arc<Semaphore> with a capacity of 50 (max 50 concurrent robots.txt fetches).
  3. SimHash false near-duplicates. A Hamming distance of 3 is aggressive. Pages with different content but similar boilerplate (headers/footers) may be flagged as near-duplicates. In production, filter out boilerplate before computing SimHash (strip <header>, <footer>, <nav> elements). This is a Phase 1 refinement; log near-duplicate events for analysis in Phase 0.
  4. Cancellation token scope. If the CancellationToken is not correctly propagated to all tasks, some workers may continue fetching after shutdown is initiated. Use token.cancelled() as a tokio::select! arm in each worker's fetch loop.
