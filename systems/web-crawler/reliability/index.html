24. Failure Modes & Recovery

Failure Taxonomy

Class A — Transient Network Failures

  • DNS resolution failure, TCP connection reset, TLS handshake timeout.
  • Detection: FetchError variants.
  • Recovery: exponential backoff with jitter. Base: 60s, max: 3600s, jitter: 20%. After 5 retries, mark URL as permanently failed in SQLite.

Class B — Permanent HTTP Failures

  • 404 Not Found, 410 Gone, 403 Forbidden (without robots.txt coverage).
  • Detection: FetchError::HttpStatus with 4xx.
  • Recovery: mark URL as Failed in frontier; do not retry. Log to SQLite.

Class C — Server-Side Throttling

  • 429 Too Many Requests (with Retry-After header), 503 Service Unavailable.
  • Detection: FetchError::HttpStatus with 429/503.
  • Recovery: respect Retry-After header if present; otherwise exponential backoff. Increase the domain's token bucket interval temporarily (Phase 1+: adaptive politeness).

Class D — Frontier Corruption

  • RocksDB WAL corruption due to filesystem error or abrupt power loss.
  • Detection: RocksDB open returns Corruption status.
  • Recovery: Run rocksdb::DB::repair(). If repair fails, restore from the last known-good backup (automated via the runbook). Restart the crawl from seed URLs.

Class E — Bloom Filter Desync

  • The Bloom filter on disk is from an older run; the current run re-crawls already-seen URLs.
  • Detection: unusually high frontier enqueue rate for a resumed crawl; high WARC duplication rate.
  • Recovery: the Bloom filter false-negative rate is zero by construction; desync only happens if the filter file is deleted or corrupted. In that case, rebuild the filter from the SQLite crawled_urls table: iterate all url values, insert into a fresh filter.

Class F — Disk Full

  • WARC files consume all available disk space.
  • Detection: std::io::ErrorKind::StorageFull on WARC write.
  • Recovery: pause crawling; alert operator; delete oldest WARC files (configurable retention policy, Phase 1+). The runbook-frontier-full.md covers this.

Class G — OOM (Out of Memory)

  • The in-memory priority queue or SimHash index grows without bound.
  • Detection: std::alloc::handle_alloc_error or OOMKill.
  • Recovery: cap in-memory structures at configured sizes (see §18 pq_capacity, and SimHash index LRU in Phase 1). Use jemalloc with usage monitoring and graceful degradation.

Class H — Robots Cache Miss Storm

  • 1,000 seeds across 1,000 domains trigger 1,000 concurrent robots fetches at startup.
  • Detection: spike in robots_cache_misses_total + outbound connection count.
  • Recovery: robots_fetch_semaphore capped at 50 (§20.6 pitfall 2); excess waits.

Class I — DNS Resolver Failure / Poisoning

  • Resolver returns SERVFAIL, NXDOMAIN, or a poisoned record pointing at an internal IP.
  • Detection: FetchError::Dns; SSRF guard catches internal IPs (I5).
  • Recovery: NXDOMAIN → permanent fail; SERVFAIL → backoff retry; poisoned-internal-IP → reject (I5). Re-validate IP per connection (DNS rebinding mitigation).

Class J — Redirect Loop / Trap

  • A server returns a cycle of 3xx responses or a deep redirect chain.
  • Detection: redirect seen-set hit or max_redirects exceeded (I13).
  • Recovery: FetchError::TooManyRedirects; mark Failed; no retry.

Class K — Clock Skew / Non-Monotonic Instant

  • Instant::now() regresses on a misbehaving clock source, corrupting token-bucket refill.
  • Detection: negative elapsed guard in TokenBucket refill (§15.6 pitfall 2).
  • Recovery: treat negative elapsed as zero; clamp tokens ∈ [0, capacity].
