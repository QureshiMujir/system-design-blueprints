33. Back-of-Envelope Capacity Model

All derived from the §4 System Constraints table. Phase 0 single node.

  1. Bloom filter bits. m = -n·ln p / (ln 2)² with n = 100M, p = 0.01: m = -1e8·(-4.605)/0.4805 ≈ 9.58e8 bits ≈ 114 MB. (The §3/§4 "~958 MB" figure is bits, i.e. ~120 MB on disk.) → ~120 MB Bloom file.
  2. Bloom hash count. k = (m/n)·ln 2 = (9.58e8/1e8)·0.693 ≈ 6.6 → 7. → k = 7 (matches ADR-12).
  3. Daily page volume. 100 pages/s × 86,400 s = 8.64M pages/day. → ~8.6M pages/day.
  4. WARC growth. 8.64M × 100 KB avg × 0.3 gzip ≈ 259 GB/day compressed. → ~260 GB/day, ~1 WARC file (1 GiB) every ~5–6 min.
  5. Frontier disk. Assume fan-out 10 links/page, dedup keeps ~20% new: 8.64M × 10 × 0.2 = 17.3M new URLs/day × ~200 B/record ≈ 3.5 GB/day before compaction. → ~3.5 GB/day frontier growth.
  6. In-memory heap. pq_capacity 100k × ~120 B = 12 MB. → ~12 MB — negligible vs. the 4 GiB RSS budget (§4).
  7. DNS query rate. New domains ≈ 1% of new URLs: 17.3M × 0.01 = 173k/day ≈ 2/s; with TTL cache hit > 90%, → < 0.2 resolver calls/s — not a bottleneck (confirms Scalability Analysis).
  8. FD usage. 50 workers × 4 idle/host + RocksDB SSTs (~100) + WARC (1) + SQLite (1) ≈ 300 FDs. → well under the 65,536 budget (§4).
  9. Network egress. 100 pages/s × 100 KB = 10 MB/s = 80 Mbps. → 8% of a 1 Gbps uplink — RTT-bound, not bandwidth-bound.
  10. Memory budget check. Bloom 120 MB + RocksDB block cache 512 MB + heap 12 MB + per-domain state (1M × ~200 B = 200 MB) ≈ ~850 MB, comfortably under the 4 GiB RSS budget (§4).
  11. Retry amplification. Worst case 5 retries × ≤5% transient failure: 0.05 × 5 = 0.25 extra fetches/page ⇒ ≤ 25% throughput tax under sustained network trouble (Failure Class A).
  12. Cold-resume time. mmap Bloom (O(1)) + load top-100k heap from RocksDB (~100k × 1 µs get ≈ 0.1 s) ⇒ ≪ 5 s startup budget (§4).
