In one paragraph

A polite, durable web crawler written from scratch in Rust. It discovers URLs, fetches pages, extracts links, removes duplicates and stores pages as standard WARC archives, while strictly obeying robots.txt, per-domain rate limits and crawl delays (§1). It is not a scraper, search engine or browser; it is the fetch-and-discovery layer that search engines, archivers and link-graph analysers build on (§1). Async workers share one URL frontier, and every request to a host goes through one per-domain queue with its own rate limiter, so at most one fetch is in flight per host (§1, §4, I1). Phase 0 is one node doing 100 pages per second; Phase 1 spreads hosts across nodes by consistent hashing (§1, §4).

The problem, concretely

Start from a list of seed pages, follow every link, and keep going (§1). Several things go wrong. First, point many workers at one site and the crawler gets IP-banned (§6 P1) — and no number of workers makes one slow site crawl faster, because politeness is "a per-host serialization lock, not a global rate" (§31 MM1). Second, the set of URLs still to visit grows to millions; keep it in memory and a crash loses the whole crawl, so "the frontier is a database, not a queue" and the hard part is durability, not ordering (§31 MM2). Third, the web is full of the same page under different URLs, such as ?utm_source= variants and redirects (§2); forgetting that you have seen a URL creates an infinite loop, so the seen-set must have zero false negatives even if it occasionally has a false positive (§31 MM4, I7). And every byte a remote server sends is hostile until proven otherwise: malformed HTML, gzip bombs, redirects that point at your own internal network (§31 MM6, §23).

How it works, end to end

The blueprint's diagram has a control-and-fetch plane feeding a processing-and-storage plane, with discovered links looping back into the frontier (§3). The crates listed in §1 implement these boxes (§1, §10):

 CLI / coordinator: seeds → seed injector · metrics server :9090
   URL frontier: priority queue by next_fetch_at + depth/score · RocksDB persistence · per-domain state
   Scheduler / dispatcher: one token bucket per domain · crawl-delay enforcement · domain-affine assignment
   Fetcher pool: N long-lived workers, each with a private hyper connection pool
 ──────────────────────────── fetched responses ────────────────────────────
   Robots cache: robots.txt fetch + parse + per-domain TTL cache → allow / deny verdict
   Response handler: status check · Content-Type gate · redirects (max N) · charset decode
   HTML parser (html5ever, link extraction, <base href>)     WARC writer (append-only, SHA-256 digests)
   Dedup engine: Bloom filter (exact URL) · SimHash (near-duplicate content) · RFC 3986 normalisation
   → new URLs back into the frontier
 Storage: data/warc/*.warc.gz · data/metadata.sqlite · data/bloom.bin

The crates/coordinator wiring injects a seed URL (§3). It is normalised and checked against the Bloom filter in crates/dedup, then enqueued into the URL frontier (crates/frontier) — a min-heap keyed by the time it may next be fetched, backed by RocksDB so that an enqueue is durable before it returns (§3, §8, I2). The scheduler (crates/scheduler) only pulls a URL for domain D when D's token bucket has a token; the bucket's interval is the domain's crawl delay, and domains are interleaved so a fast domain cannot starve slow ones (§3, §8). A fetcher worker (crates/fetcher) uses the robots cache (crates/robots): on a miss it fetches /robots.txt with a 10-second timeout, and the fetch proceeds only on an allow verdict (§3, I4). The response handler checks the status, sends only HTML to the parser, follows at most max_redirects hops (default 10) while re-checking every target against internal-address ranges, decodes the body, and hands it to both the WARC writer (crates/storage) and the HTML parser (crates/parser) (§3, §16, §23, I5, I9). Extracted links are normalised, tested against the Bloom filter and, if new, enqueued; a SimHash near-duplicate hit skips link extraction for that page (§3, §20). Metadata goes to SQLite, raw pages to rotating gzip-compressed WARC files sealed at 1 GiB or 100,000 records (§19; §3 writes "1 GB").

The core ideas

One in-flight fetch per host, enforced by structure (§3, I1, I12, MM1)

Each active domain has one token bucket with capacity 1 and refill rate 1.0 / crawl_delay (§15). Its effective delay is max(robots_crawl_delay, default) × politeness_multiplier, with the multiplier above zero (I12). A domain may fetch only when in_flight == 0 and the bucket yields a token (§15, I1). The blueprint's cases: Crawl-delay: 0 is still held to the configured default of 1 second (§11, §15); the crawl_delay_2s.json fixture expects at most one request every 2 s under pressure (§15). The coordinator never spins: it sleeps for the smallest wait across domains with pending URLs, which is also what keeps slow domains from starving (§15). The mental model predicts the classic mistake: engineers raise the worker count to crawl one slow site faster and get the crawler's IP banned (§31 MM1). Phase 3's mock-clock tests prove at most one request per crawl-delay interval (§15).

The frontier is a database (§3, §8, I2, I3, MM2)

A URL moves through Unseen → Enqueued → Robots check → Fetching → Parsed-and-archived, Redirected (re-enqueue the target) or Failed (back off and retry) (§8). Enqueued records live in RocksDB with write-ahead logging; the in-memory heap is a strict subset of the records whose status is still Queued, and a dequeue re-checks the stored status so a stale heap entry is discarded rather than served (I2, I3). Ordering is shallow-first by depth and score, because "BFS is an emergent quality signal": high-PageRank pages are reachable in few hops from seeds, while depth-first crawlers tunnel into low-value link farms (§31 MM3).

Dedup is asymmetric (§8, I6, I7, MM4)

URLs are normalised through a fixed pipeline — lowercase scheme and host, Punycode decoding, default-port removal, dot-segment resolution, percent-encoding normalisation, sorted query parameters, fragment removal — and normalisation is idempotent by property test (§8, I6). The canonical string goes into a Bloom filter. Its sizing follows m = −n·ln p ÷ (ln 2)² and k = (m/n)·ln 2: with n = 100 M and p = 0.01, m ≈ 9.58 × 10⁸ bits and k ≈ 6.6, rounded to 7 (§13, §33 items 1–2, ADR-12). I7 is enforced by inserting before the enqueue, so a seen URL can never be missed (§7, I7); the step list in §20 instead names the Bloom insert after the enqueue. For content, a 64-bit SimHash over word trigrams marks two pages as near-duplicates when their fingerprints differ in at most three bits (§8, ADR-13). The asymmetry is deliberate: a false positive skips one page; a false negative creates a re-crawl loop (§31 MM4).

robots.txt is evaluated by the spec, not by vibes (§8, I4)

Group selection matches the declared user agent case-insensitively and falls back to *; among matching Allow and Disallow rules the longest matching prefix wins, with Allow winning ties; paths are compared after percent-decoding both sides; a Crawl-delay becomes the domain's bucket interval (§8). The blueprint's worked example: for an agent with its own group containing only Allow: /, a private path is allowed; for an agent falling back to *, /private/public.html is allowed by the longer Allow rule while /private/secret.html is disallowed (§8). An unreachable robots file, a 5xx or a network error counts as disallowed with a backoff (60 s by default); a 4xx, including 404, means no restrictions (§6 P8, §11, §14). A domain blocked by robots.txt is demoted in the frontier, not dropped, in case the file changes (§3, I4); the §8 state machine instead sends a disallowed URL "back to frontier with low priority or dropped". Phase 2 proves the parser with more than fifty conformance cases (§14).

Every remote byte is hostile (§23, I5, I8, I9, MM6)

Redirect targets are rejected if they resolve to private, loopback or link-local addresses, re-validated per connection to defeat DNS rebinding (§23, I5). Bodies are decompressed incrementally and aborted past 10 MiB (§23, §4). Robots files are capped at 512 KiB and wildcard patterns at 2,000 characters to prevent regex blow-up (§4, §23). A network or parse error never panics a worker: parsers return results and the link extractor runs under catch_unwind (I8), and the parser runs only on HTML content types (I9).

Back-pressure end to end, storage append-only (§20, I10, MM7, MM8)

The task channel to the workers is bounded at worker_count × 2, so the coordinator blocks when every worker is busy (§20). If a worker is also blocked sending its result on a full channel, the pipeline deadlocks (§20). The blueprint gives two answers. §20's fix sends results on a separate channel that is "unbounded, or with a large buffer", read in its own select! arm. MM7 says a bounded input channel with an unbounded output channel "just moves the overflow" and calls for bounded channels plus separate select arms (§31 MM7). WARC files are append-only and sealed on rotation, so a committed record is never modified and indexers can read sealed files while the crawl writes new ones (I10, §31 MM8).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust — zero-cost async, ownership that prevents data races in the concurrent frontier, and the html5ever ecosystem (ADR-01). The blueprint calls Python "disqualifying" for a production crawler because of interpreter-lock contention in the parser and memory overhead at millions of URLs (§1). Rejected: Go, Python, C++. When the rejected choice is right: Go, when team velocity and a simpler concurrency model outweigh peak performance and zero-copy needs (ADR-01).

Frontier storage: RocksDB (ADR-06)

Chosen: RocksDB, whose log-structured design handles the write-heavy frontier and whose WAL gives crash durability (ADR-06). Rejected: LMDB, SQLite, an in-memory map. When the rejected choice is right: LMDB for read-mostly, memory-mapped workloads needing the lowest read latency (ADR-06).

Near-duplicate detection: SimHash (ADR-13)

Chosen: a 64-bit SimHash with SipHash — constant space and a constant-time comparison per document (ADR-13). Rejected: MinHash, edit distance. When the rejected choice is right: MinHash when you need tunable Jaccard-similarity accuracy and can afford larger signatures (ADR-13).

Bloom filter: custom, not a crate (ADR-12)

Chosen: a custom filter over a bit vector, because it must serialise to a memory-mapped file with reproducible seeds (ADR-12). Rejected: the bloomfilter crate, probabilistic-collections. When the rejected choice is right: an off-the-shelf crate, when persistence and reproducibility are not required and development time dominates (ADR-12).

Rate limiting: a custom token bucket (ADR-24)

Chosen: custom per-domain buckets in a concurrent map, refilled from robots directives (ADR-24). Rejected: the governor crate, ratelimit. When the rejected choice is right: governor for a fixed global rate where its GCRA implementation and ergonomics save time (ADR-24).

Metadata: SQLite (ADR-07)

Chosen: SQLite (rusqlite) — a single file, no server, adequate for one node (ADR-07). Rejected: PostgreSQL, MySQL, DynamoDB. When the rejected choice is right: PostgreSQL once metadata is queried concurrently by many clients or sharded across nodes in Phase 1 (ADR-07).

Roads not taken (§35)

A batch MapReduce crawler in the Common Crawl and Nutch style wins for periodic full-web snapshots at petabyte scale on an existing Hadoop cluster, and is rejected because batch rounds give terrible freshness and no continuous politeness (§35 A). A streaming-topology crawler such as StormCrawler wins when you already run Storm or Flink, and is rejected because it imposes a heavy cluster runtime on what one self-contained process can do (§35 B). A fully decentralised peer crawler like UbiCrawler wins for coordinator-free scale-out, and is rejected for Phase 0 because a single coordinator is far easier to reason about when proving the politeness invariant; its consistent-hash slicing is adopted for Phase 1 (§35 C).

What must never be false

  • I1 — at most one in-flight fetch per host; an in_flight ≤ 1 assertion and the active_fetches{domain} gauge.
  • I2 — every enqueued URL is durable before the enqueue returns; a kill -9 recovery test and frontier_enqueue_total.
  • I3 — the in-memory heap is a strict subset of RocksDB records with status Queued; dequeue discards stale entries, counted by frontier_heap_discards_total.
  • I4 — no fetch proceeds while its robots verdict is unknown or disallowed; a pre-fetch check, robots_disallow_total and robots_unavailable_total.
  • I5 — no connection proceeds to a private, loopback or link-local address; ssrf_blocked_total.
  • I6 — normalisation is idempotent for all inputs; property-tested and fuzzed.
  • I7 — the Bloom filter has zero false negatives; a 1M-URL accuracy test and bloom_fp_rate.
  • I8 — a network or parse error never panics a worker; fuzz and chaos tests, pages_failed_total{error_kind}.
  • I9 — the HTML parser runs only on HTML content types; parse_skipped_nonhtml_total.
  • I10 — a committed WARC record is never modified; digests re-verify on read-back.
  • I11 — every pipeline stage emits at least one metric; a coverage test enumerates them.
  • I12 — the effective per-domain delay is at least the robots or default delay times a positive multiplier; startup rejects a multiplier ≤ 0, effective_crawl_delay{domain}.
  • I13 — redirect chains terminate within the limit and contain no cycle; a loop-detection test and the redirect_chain_length histogram.
  • I14 — the frontier never exceeds its configured size; enqueue returns Full, watched by the frontier_size gauge.

What breaks in production

  • Transient network failures (§24 Class A). DNS errors, connection resets, TLS timeouts surface as FetchError variants; exponential backoff with 20% jitter from 60 s up to 3,600 s, permanent failure after five retries.
  • Server throttling (§24 Class C). 429 or 503 responses; Class C says honour Retry-After or back off and temporarily widen the domain's bucket interval, tagged "Phase 1+: adaptive politeness". §1 and §36 list adaptive 429/503 back-off, including Retry-After, as deferred.
  • Frontier corruption (§24 Class D). A filesystem fault or power loss damages the RocksDB WAL; open returns Corruption; run the repair, else restore the last backup and restart from seeds.
  • Bloom filter desync (§24 Class E). The filter file was deleted or corrupted; visible as a high enqueue rate on a resumed crawl and WARC duplicates; rebuild it from the SQLite crawled_urls table.
  • Robots cache-miss storm (§24 Class H). A thousand seeds across a thousand domains fire a thousand robots fetches at startup, seen as a spike in robots_cache_misses_total; a semaphore caps them at fifty.
  • DNS failure or poisoning (§24 Class I). FetchError::Dns; NXDOMAIN fails permanently, SERVFAIL retries, and a poisoned internal address is rejected by the SSRF guard (I5).
  • Redirect loops and traps (§24 Class J). A seen-set hit or the hop limit ends the chain with TooManyRedirects, marked Failed with no retry (I13).
  • Clock regression (§24 Class K). A non-monotonic Instant would corrupt bucket refill; the refill guard treats negative elapsed time as zero and clamps tokens to [0, capacity].

Threats a reader should know (§23): server-side request forgery through redirects to internal addresses, answered by post-resolution checks on every connection; gzip bombs, answered by a decompression cap; regex denial of service through malicious robots files, answered by size and pattern caps; homograph attacks through internationalised domain names, answered by Punycode normalisation and logging; an unauthenticated metrics endpoint, bound to localhost by default.

How it compares

  • Mercator / Googlebot introduced the heap-of-queues plus back-queue design that separates prioritisation from politeness; it wins at hyperscale, and this blueprint borrows the structure while starting single-node (§32).
  • Heritrix put archival fidelity first and originated WARC; it wins for legal-grade web preservation, and this design adopts its WARC contract with a leaner store (§32).
  • Scrapy optimised developer ergonomics for small focused scrapes; its in-memory, single-process model is rejected here for durability and politeness at scale (§32).
  • StormCrawler maps crawling onto a streaming topology; it wins if you already run Storm, at the cost of a heavy cluster dependency (§32).
  • The Common Crawl pipeline is a batch archiver that wins for periodic petabyte snapshots; this design is a continuous, low-latency loop instead (§32).

Questions to test yourself

  1. How does the system guarantee exactly one in-flight fetch per host while still avoiding starvation of slow domains? — Hint: the per-domain gate and fair selection by smallest wait in §15, and I1.
  2. Prove that no URL is lost across a kill -9. What is the exact ordering of WAL fsync vs. enqueue ack? — Hint: §18 and invariant I2.
  3. Why are false negatives in the Bloom filter impossible but false positives acceptable, and how does that shape coverage? — Hint: §13, I7 and mental model MM4.
  4. Where could an SSRF slip through, and why does checking only the seed URL not suffice? — Hint: redirects in §16, the threat model in §23, and I5.
  5. The coordinator and a worker both block on full channels. Diagnose the deadlock and the fix. — Hint: the pitfall recorded in §20 and MM7.

If you only remember three things

Politeness is a per-host lock, so throughput per site is one over the crawl delay no matter how many workers you run. The frontier is a database whose hard part is durability, and the seen-set must never forget a URL even if it occasionally over-remembers one. Every remote byte is hostile: redirects are checked against your own network, bodies are capped, parsers are total, and nothing a server sends may crash a worker.

Words used here

  • URL frontier — the durable, prioritised set of URLs still to fetch.
  • Politeness / crawl delay — the minimum spacing between requests to one host.
  • Token bucket — the per-domain limiter that releases one fetch per delay interval.
  • robots.txt / REP — the Robots Exclusion Protocol a site uses to allow or forbid paths.
  • Domain affinity — routing every URL of a host through the same per-domain queue and limiter.
  • Bloom filter — the compact seen-set that can say "maybe seen" but never "unseen" for a seen URL.
  • SimHash / shingling — a fingerprint of a page's word trigrams for near-duplicate detection.
  • URL canonicalisation — the normalisation pipeline that collapses equivalent URLs to one string.
  • WARC — the standard archive format for captured HTTP responses.
  • SSRF — tricking the crawler into fetching an internal address via a redirect.
  • Back-pressure — bounded channels so a slow stage slows its producer instead of growing memory.
  • BFS ordering — shallow-first scheduling that surfaces high-quality pages early.
  • Redirect chain — the bounded, cycle-checked sequence of 3xx hops.
  • Column family — a RocksDB namespace; the frontier keeps URLs and domain state in separate ones.
