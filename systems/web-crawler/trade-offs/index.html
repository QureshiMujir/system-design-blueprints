Decisions (§9) · 25 ADRs

ADR-01

Language

Chosen

Rust (stable, 1.75+)

Rejected

Go, Python, C++

When the rejected choice is right

Go wins when team velocity and a simpler concurrency model outweigh peak performance and zero-copy needs.

Why: Zero-cost async, ownership prevents data races in the concurrent frontier, html5ever ecosystem.

ADR-02

Async runtime

Chosen

tokio (1.x, multi-thread)

Rejected

async-std, smol

When the rejected choice is right

smol wins for a tiny single-purpose binary where minimal dependency footprint matters more than ecosystem.

Why: De facto production runtime; best integration with hyper/reqwest.

ADR-03

HTTP client

Chosen

hyper (1.x) + reqwest (0.12)

Rejected

ureq, isahc, raw TCP

When the rejected choice is right

ureq wins for synchronous, low-concurrency tools where async overhead isn't justified.

Why: reqwest for ergonomics; hyper for low-level control in workers.

35. Alternative Architectures (Roads Not Taken)

A. Stateless MapReduce batch crawler (Common Crawl / Nutch model).

seeds → [Map: fetch] → [Reduce: dedup+extract] → next round of URL lists → repeat

Wins when: you want periodic full-web snapshots at petabyte scale on an existing Hadoop cluster, and per-page latency is irrelevant. Embodied by: Common Crawl pipeline, Apache Nutch. Rejected because: batch rounds give terrible freshness latency and no continuous politeness; this blueprint targets a continuous, low-latency loop (§4 p99) on a single binary.

B. Streaming-topology crawler (StormCrawler model).

URL spout → [partition bolt] → [fetch bolt] → [parse bolt] → [dedup bolt] → status store → spout

Wins when: you already operate Apache Storm/Flink and want crawl to be one stream among many with cluster-managed parallelism. Embodied by: StormCrawler. Rejected because: it imposes a heavy cluster runtime dependency for what Phase 0 can do as one self-contained process; we defer distribution to a consistent-hash design (PhaseDeferred("Deferred Features Register")).

C. Fully decentralized peer crawler (UbiCrawler model).

node A ⇄ node B ⇄ node C   (each owns a consistent-hash slice of host space, no central coordinator)

Wins when: you need fault-tolerant, coordinator-free scale-out across many machines with minimal re-sharding cost. Embodied by: UbiCrawler (Boldi et al., §5). Rejected for Phase 0 because: the centralized single-node coordinator is far simpler to reason about and to prove the politeness invariant on; the consistent-hash slice idea is adopted for Phase 1.
