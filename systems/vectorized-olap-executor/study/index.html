31. Mental Models & First Principles

  1. MM1 — A record batch is a mini-column-store, not a list of rows. Insight: think in columns from the type system up. Predicts: any operator whose inner loop needs a "current row" concept is architecturally wrong. Bug class without it: hidden row- materialization creeping into filter/project (P1's violation). Applies in §11.2, §14.
  2. MM2 — The pipeline breaker is the only synchronization point that matters. Insight: everything between two breakers is embarrassingly parallel. Predicts: the breaker set (Sort, HashAggFinal, HashJoinBuild, Exchange) is a complete list of "wait here" points; nothing else needs a barrier. Bug class: an operator that silently buffers without declaring itself a breaker corrupts I11. Applies in §8.3, §15.2.
  3. MM3 — A hash table's throughput is a cache-miss budget, not an instruction-count budget. Insight: probe throughput is bound by cache-line fetches, not ALU ops. Predicts: a "faster" hash function that increases branch mispredicts but removes one ALU op is a net loss. Bug class: micro-optimizing kernel arithmetic while ignoring bucket layout. Applies in §16.2, §33.
  4. MM4 — Vectorization and compilation solve different problems. Insight: vectorization amortizes dispatch overhead across rows; compilation amortizes interpretation overhead across a whole query. Predicts: short queries favor vectorization (low fixed cost); long, repeated queries favor compilation. Bug class: compiling every expression regardless of row count (§21.6). Applies in ADR-16, §21, §35.
  5. MM5 — NUMA is a second memory hierarchy layer above cache. Insight: treat "remote NUMA node" the way you'd treat "L3 cache miss" — one level further out. Predicts: the same locality principles motivating cache-line alignment motivate morsel-to-NUMA-node pinning. Bug class: parallelizing without NUMA awareness, expecting linear scaling and getting a plateau at the socket boundary. Applies in §4, §15.
  6. MM6 — A selection vector is a promise you can break cheaply. Insight: filtering by carrying indices/a bitmap instead of copying values defers materialization cost until it's actually needed. Predicts: late materialization always wins when the promise is never called in (filtered-out rows are never touched again). Bug class: an operator that "cashes in" the promise too early (eager decode/materialize) loses the win silently. Applies in P4, P5, §17, §22.
  7. MM7 — Every unsafe block is a proof obligation, not a convenience. Insight: P15's two unsafe surfaces exist because a proof (alignment, bounds, ISA availability) was discharged once, centrally, instead of ad hoc. Predicts: any third unsafe site is either redundant (the proof already exists elsewhere) or unaudited (a latent bug). Bug class: "just add unsafe to satisfy the borrow checker" without a corresponding invariant. Applies in §6 P15, §14.6, §21.6.
  8. MM8 — Spill is memory management's escape valve, not a fallback path. Insight: design the hot path assuming spill will happen on real workloads (SF=100+), not as a rare emergency. Predicts: a spill implementation bolted on after the fact (rather than co-designed with the hash table's build/probe interface) will leak the abstraction. Bug class: a hash-table API with no notion of "drain to an external writer" until spill is retrofitted. Applies in P10, §16, §20.

5. Required Reading

Books

  • Garcia-Molina, H., Ullman, J. D., Widom, J. Database Systems: The Complete Book, 2nd ed. Ch. 15 (Query Execution), Ch. 16 (physical operators, join algorithms). Extract: the cost model behind hash-join and sort-merge-join that §17 (Phase 5) re-derives at batch granularity. Applied in §17.
  • Ramakrishnan, R., Gehrke, J. Database Management Systems, 3rd ed. Ch. 12 (External Sorting), Ch. 14 (Evaluation of Relational Operators). Extract: the classic hash-based and sort-based operator algorithms that vectorized engines re-implement at the vector level. Applied in §16, §17, §19.
  • Silberschatz, A., Korth, H., Sudarshan, S. Database System Concepts, 7th ed. Ch. 12 (Physical Storage Systems), Ch. 15 (Query Processing). Extract: buffer management and physical-plan representation baseline that VOE's PhysicalPlan (§8) specializes. Applied in §8, §13.
  • Hennessy, J. L., Patterson, D. A. Computer Architecture: A Quantitative Approach, 6th ed. Ch. 2 (Memory Hierarchy), Ch. 3 (ILP), Appendix on vector/SIMD architectures. Extract: the cache-line/bandwidth arithmetic behind §33 (Back-of-Envelope Capacity Model). Applied in §4, §33.
  • Kleppmann, M. Designing Data-Intensive Applications. Ch. 3 (Storage and Retrieval, column-oriented storage). Extract: the systems-level row-vs-column tradeoff underlying P4/P5. Applied in §6, §32.
  • Fog, A. Optimizing Software in C++ / Instruction Tables (agner.org). Extract: per-instruction latency/throughput tables used to size SIMD kernel throughput targets M3/M4. Applied in §14, §29.

Papers

  • Boncz, P., Zukowski, M., Nes, N., 2005. MonetDB/X100: Hyper-Pipelining Query Execution. CIDR. The paper that started vectorized execution; section 2 (cost of tuple-at-a-time), section 3 (X100 algebra). Applied in §6 (P1), §14 (Phase 2).
  • Zukowski, M., van de Wiel, M., Boncz, P., 2012. Vectorwise: Beyond Column Stores. IEEE Data Engineering Bulletin. The production evolution of X100. Applied in §32 (Comparative Architecture).
  • Neumann, T., 2011. Efficiently Compiling Efficient Query Plans for Modern Hardware. VLDB. The HyPer compiled-pipeline alternative. Applied in ADR-16 (§9), §35 (Alternative Architectures).
  • Kersten, T., Leis, V., Kemper, A., Neumann, T., Pavlo, A., Boncz, P., 2018. Everything You Always Wanted to Know About Compiled and Vectorized Queries But Were Afraid to Ask. VLDB. The empirical crossover analysis. Applied in §21 (Phase 9), §35.
  • Sompolski, J., Zukowski, M., Boncz, P., 2011. Vectorization vs. Compilation in Query Execution. DaMoN. Head-to-head measurement. Applied in ADR-16, §21 (Phase 9).
  • Abadi, D. J., Madden, S. R., Hachem, N., 2008. Column-Stores vs. Row-Stores: How Different Are They Really? SIGMOD. Quantifies the column-store advantage; source of the late-materialization argument. Applied in P4 (§6), §22 (Phase 10).
  • Polychroniou, O., Raghavan, A., Ross, K. A., 2015. Rethinking SIMD Vectorization for In-Memory Databases. SIGMOD. The vectorized linear-probing hash table this design names itself after. Applied in §16 (Phase 4), §17 (Phase 5).
  • Zhou, J., Ross, K. A., 2002. Implementing Database Operations Using SIMD Instructions. SIGMOD. First systematic SIMD-in-database application. Applied in §14 (Phase 2).
  • Leis, V., Boncz, P., Kemper, A., Neumann, T., 2014. Morsel-Driven Parallelism: A NUMA-Aware Query Evaluation Framework for the Many-Core Age. SIGMOD. The scheduler this design is named after. Applied in §15 (Phase 3), I8 (§7).
  • Kohn, A., Leis, V., Neumann, T., 2018. Adaptive Execution of Compiled Queries. ICDE. The interpret-then-JIT compromise. Applied in §21 (Phase 9), Deferred Register (§36).
  • Behm, A. et al., 2022. Photon: A Fast Query Engine for Lakehouse Systems. SIGMOD. Databricks's AOT-compiled-kernel (not JIT) vectorized engine. Applied in ADR-16 (§9), §32.
  • Pedreira, P. et al., 2022. Velox: Meta's Unified Execution Engine. VLDB. Shared executor design; operator/expression interface comparison. Applied in §11, §32.

Reference Implementations

  • DuckDB (duckdb/duckdb) — src/execution/ (physical operators), src/common/types/ vector.cpp. Lesson: the 2048-row default vector and single-file embeddability. Pitfall not to copy: DuckDB's operator interface is C++ virtual dispatch per vector, not per row — mirror the granularity, not the language mechanism. Applied in §14, §33.
  • ClickHouse (ClickHouse/ClickHouse) — src/Processors/ (pipeline processors), src/Columns/. Lesson: the Block = Vec<Column> model and function-as-kernel-table registry. Pitfall: ClickHouse's 65536-row Block trades L1-fit for lower per-batch dispatch overhead — know which regime you are optimizing for before copying the number. Applied in §14, §32.
  • Apache Arrow / DataFusion (apache/arrow-datafusion) — datafusion/physical-plan/src/. Lesson: a Rust-idiomatic physical-plan/operator trait design. Pitfall: DataFusion's RecordBatch and ExecutionPlan are async-Stream-based; VOE is synchronous/push-based by design (ADR-05) — do not import the async model wholesale. Applied in §8, §11.
  • Meta Velox (facebookincubator/velox) — velox/exec/. Lesson: the operator interface and Vector abstraction shared across multiple query engines. Pitfall: Velox's expression evaluation eagerly materializes intermediate vectors more than VOE's late-materialization default (P4) — do not adopt that eagerness by default. Applied in §11, §22.
  • MonetDB (MonetDB/MonetDB) — monetdb5/mal/ (the MAL execution layer, the historical X100 ancestor). Lesson: the original vectorized-batch execution model. Pitfall: MonetDB's monolithic BAT (binary association table) format couples storage and execution tightly — VOE deliberately separates them (ADR-02). Applied in §32.

RFCs / Specifications

  • Apache Arrow Columnar Format Specification — buffer/validity-bitmap/offset/dictionary layout, read verbatim for byte-level compatibility. Applied in §13 (Phase 1).
  • TPC-H Specification (Transaction Processing Performance Council) — the 22-query analytical benchmark: schemas, queries, qualification rules. Applied in §22 (Phase 10), §27.
  • TPC-DS Specification (Transaction Processing Performance Council) — the 99-query benchmark; VOE implements a diversity-representative subset. Applied in §22, §27, ADR-18.
  • Apache Parquet Format Specification — page/row-group statistics layout used by predicate pushdown. Applied in §22 (Phase 10).

Glossary (§37) · 48 terms · site-wide glossary

AggState
VOE's per-group running aggregate state (sums, counts, mins, maxes).
Arrow IPC
Apache Arrow's binary interprocess/file serialization format for record batches.
Batch (Vector)
a RecordBatch of bounded row count (default 2048) flowing through a pipeline; the unit of vectorized processing.
Bitmap
a packed, LSB-first-per-byte validity bit array marking null/non-null per row.
BMI2 / PEXT
an x86 instruction-set extension accelerating bit-extraction in the filter kernel.
Breaker (Pipeline Breaker)
an operator (Sort, HashAggFinal, HashJoinBuild, Exchange) that must fully drain its upstream before its downstream may start.
Broadcast join
a hash-join build strategy where one shared table serves every probe worker (small build sides).
Bucket
a 64-byte-aligned slot in a LinearProbeTable holding up to 4 key/value pairs.
Cache-line ping-pong
repeated invalidation of a shared cache line by concurrent writers on different cores, causing severe slowdown.
Conformance bucket
a named test group (e.g. tpch.q1_to_q22_sf1) in the conformance runner's report schema.
Cranelift
the JIT code generator VOE uses to compile hot expressions (voe-codegen).
Dictionary encoding
representing a column as small integer keys plus a shared values array, exploited by pass-through operators.
Exchange
the operator that hash- or range-repartitions a stream of batches across NUMA-pinned queues.
FD (file descriptor) budget
the per-query ceiling on simultaneously open spill files.
Grace hash join
the spill pattern that partitions both join sides by hash so each partition fits in memory.
Kleene logic
three-valued (TRUE/FALSE/NULL) boolean semantics used for SQL predicate evaluation.
Late materialization
carrying (row_id, key_cols) through operators, fetching remaining columns only at the sink.
Linear probing
a hash-table collision-resolution strategy that scans consecutive buckets on collision.
Load factor
occupied buckets divided by total capacity in a hash table; bounded at 0.7 (I5).
Materialize (operator)
the sink that fetches full rows from row-ids for late- materialized pipelines.
Morsel
a bounded slice (default 100,000 rows) of a pipeline's input dispatched as one unit of scheduling work.
NUMA (Non-Uniform Memory Access)
a multi-socket memory architecture where local-node access is faster than remote-node access.
Operator
a state machine consuming and producing RecordBatches via the Operator trait.
Partitioned join
a hash-join build strategy where the build side is hash-partitioned to match the probe side's partitioning.
Pipeline
a chain of streaming operators between two breakers, sharing worker-thread state.
Pipeline builder
the voe-plan component that cuts a PhysicalPlan into pipelines at breaker boundaries.
Predicate pushdown
evaluating a filter as early as possible, ideally inside the scan, using source-level statistics.
pulp dispatch
the runtime CPU-feature detection and specialization mechanism from the pulp crate.
Radix sort
a non-comparison sort processing fixed-width keys digit-by-digit.
RecordBatch
VOE's Arrow-compatible columnar batch type: a Schema plus a Vec<ArrayRef>.
Row-id
a row's positional identifier, carried through late-materialized pipelines.
SBOM (Software Bill of Materials)
a manifest of every dependency and its version bundled in a release.
Scale factor (SF)
the TPC-H/TPC-DS dataset-size multiplier (SF=1 ≈ 1 GB).
Sealed (release status)
VOE's highest release-maturity gate, requiring a 30-day fuzz/soak pass (ADR-22).
Seed (hash seed)
a per-query randomized value mixed into every hash computation to prevent collision attacks.
Selection vector
an alternate representation of "which rows survived a filter," as indices rather than a copied array.
Sidecar (cranelift sidecar)
the optional compiled-kernel subsystem that augments, but never replaces, the interpreted kernel path.
Skew
a non-uniform data distribution (e.g. one hash bucket or one NUMA partition receiving disproportionate load).
SLSA provenance
a supply-chain attestation standard describing how and from what source a build artifact was produced.
Spill
writing an operator's in-memory state to disk (as Arrow IPC) when it exceeds its memory budget.
Top-K
the ORDER BY ... LIMIT k pattern implemented via a bounded min-heap.
Trampoline
the unsafe boundary function that calls from safe Rust into JIT-compiled machine code.
Two-stage aggregation
the pattern of building thread-local partial hash tables, then merging them into one final table.
Validity bitmap
see Bitmap.
Vectorization
processing whole columns/batches per kernel call instead of one value at a time.
Volcano model
the classic tuple-at-a-time, pull-based (next()) query-execution iterator model.
Work stealing
a scheduling technique where an idle worker takes a morsel from a busier peer's queue.
XCheck (cross-check)
the conformance methodology comparing scalar, SIMD, and compiled kernel outputs for byte-identical equality.
