⬜ Phase 0 — Repository Skeleton & Correctness Kernel (Week 1) §12

Objectives
  • Stand up the full repository skeleton (§10) in one commit; nothing about query execution yet.
  • Ship a single correctness kernel: scan 1M in-memory rows, filter col_a > 500_000, sum col_b — result must match a scalar reference to the last digit.
  • Constraints introduced: no SIMD yet (P7 deferred to §14); no spill; single-threaded only (P3 deferred to §15).
Deliverable

Repository at the production-scaffold bar; make bootstrap && make build && make test all exit 0; one passing correctness test; ADR-01, ADR-02, ADR-03, ADR-05, ADR-21 recorded under docs/adr/.

Acceptance
  • make test passes with exactly 1 test (tests/hello_vectorized.rs): exit code 0, 1 test reported.
  • 1,000,000-row correctness fixture (conformance/kernel_xcheck/hello_vectorized.json) reports a sum bit-identical to the independently-computed scalar reference, zero discrepancy.
  • cargo build --workspace completes in ≤ 90 s on a clean checkout with Cargo.lock committed (no floating dependency resolution).
  • Zero unsafe blocks anywhere in the Phase-0 diff (P15 — the two permitted unsafe surfaces do not exist yet).
Fixtures
Fixture Purpose Expected Output

malformed_schema.json Column-count/schema mismatch rejected Error::SchemaMismatch

Pitfalls
  • Arrow's 64-byte alignment vs. std::Vec<i32>'s natural 4-byte alignment — allocate via a custom AlignedVec (I1's cache-fit argument starts here, even before SIMD lands in §14).
  • Reference-implementation drift: the scalar sum must use the same overflow semantics (i64, checked, per I10) as the eventual SIMD/cranelift paths, or cross-validation (I12) fails later for the wrong reason.
  • cargo build --workspace on a fresh checkout can pull 200+ transitive crates; commit Cargo.lock so CI and local builds resolve identically (ADR-19's cross-validation depends on reproducible builds, §28).

⬜ Phase 1 — Arrow-Compatible Record Batch Layer (Weeks 2–3) §13

Objectives
  • Implement the full Arrow-compatible buffer/validity/offset/dictionary layout for every primitive type (P8, ADR-02).
  • Zero-copy slicing; Arrow IPC round-trip via arrow-rs.
  • Constraint: still single-threaded (parallelism arrives §15); still scalar kernels only (SIMD arrives §14).
Deliverable

voe-core compiles standalone; every Arrow primitive type implemented; 100K-row IPC round-trip is bit-identical; docs/architecture/record-batch.md written.

Acceptance
  • cargo test -p voe-core passes with ≥ 20 tests covering every DataType variant.
  • IPC round-trip fixture (ipc_roundtrip_100k.json): write 100K rows, read back, byte-for-byte identical to source.
  • RecordBatch::slice test asserts Arc::strong_count increases and zero heap allocations occur (verified via a counting global allocator in test builds).
  • Dictionary key overflow: UInt8 dictionary key constructed with > 256 distinct values returns Error::DictionaryKeyOverflow, never silently wraps.
Fixtures
Fixture Purpose Expected Output
ipc_roundtrip_100k.json Write/read 100K-row batch via Arrow IPC Byte-identical

Pitfalls
  • LSB-first vs. MSB-first bitmap convention: identical for fully-set bitmaps, divergent for partially-set ones — the Arrow spec (§5) is normative; verify against arrow-rs, not intuition.
  • i32 vs. i64 (LargeUtf8) offsets: mixing them silently corrupts data; enforce the type distinction at construction, not at read time.
  • Arc<[T]> alone does not guarantee 64-byte alignment; wrap allocation via std::alloc::Layout::from_size_align(_, 64) inside a custom AlignedVec, then erase to Arc<[T]>.
  • Dictionary key type choice: Int32 is the safe default; UInt8 only when cardinality ≤ 256 is provably true — document the risk, do not default to it.

⬜ Phase 2 — Vectorized Expression Kernels (Weeks 3–5) §14

Objectives
  • Ship every arithmetic/comparison/logical/cast kernel with a scalar reference and a pulp-dispatched SIMD specialization (P1, P7, ADR-13, ADR-14).
  • Establish the scalar-vs-SIMD cross-validation harness (I12) before any kernel ships to production use in an operator.
Deliverable

Every arithmetic/comparison/logical/cast/filter/hash kernel implemented for all seven primitive types plus Utf8 (bytewise compare); voe-bench benchmarks for each; docs/architecture/ kernels.md.

Acceptance
  • kernel.xcheck_arith, kernel.xcheck_cmp, kernel.xcheck_filter conformance buckets: 100,000 random inputs each, 0 mismatches (I12), CI-gating.
  • M3: gt_i32 throughput on AVX2 ≥ 8 GB/s single-core (measured via voe-bench).
  • M4: add_i32 SIMD-vs-scalar speedup ≥ 4× on AVX2.
  • Kleene-logic fixtures: NULL AND FALSE == FALSE, NULL OR TRUE == TRUE, NOT NULL == NULL — all pass exactly, not approximately.
Fixtures
Fixture Purpose Expected Output
kernel.xcheck_arith.report.json 100K random inputs, every arithmetic kernel Scalar == SIMD, 0 mismatches
kernel.xcheck_cmp.report.json 100K random inputs, every comparison kernel Scalar == SIMD, 0 mismatches

Pitfalls
  • pulp's dispatch closures are monomorphized per ISA; calling them indirectly through a function pointer defeats the optimization — inline the dispatch site (P7).
  • Boolean bitmap outputs must be 64-byte aligned; allocate via the Bitmap builder, never reuse a raw Vec<u8> (ties back to §13's alignment invariant).
  • Kleene three-valued logic's "result is null" rule differs per operator — document each operator's truth table and fixture it (I3); a generic "propagate null if either input is null" rule is wrong for OR/AND.
  • NaN comparisons: false for every comparison except != — SQL three-valued logic plus IEEE-754 NaN behavior layered together; get it wrong and WHERE x = x fails to filter NaNs.
  • SIMD intrinsic UB on unsupported hosts → SIGILL or silently wrong results if pulp is bypassed — this is exactly the threat T4 (§23) mitigates.

⬜ Phase 3 — Morsel-Driven NUMA-Aware Scheduler (Weeks 5–7) §15

Objectives
  • Implement the Leis-Boncz-Kemper-Neumann 2014 morsel-driven scheduler: per-NUMA-node MorselQueue, work-stealing, pipeline-breaker barriers (P3, ADR-04, ADR-06, I8, I11).
  • Constraint introduced: first multithreaded phase — every thread-local-state invariant (P9) must hold from here on.
Deliverable

voe-morsel runs a scan→filter→sum pipeline across 8 cores with NUMA pinning verified via platform tooling; docs/architecture/morsel-scheduler.md.

Acceptance
  • Linear speedup on the Phase-0 smoke-test workload up to the NUMA-local core count (M11: ≥ 90% parallel efficiency at 32 cores).
  • numa.affinity conformance bucket: ≥ 90% of morsel-queue pops served by a NUMA-local worker (I8), measured on a 32-core, 2-NUMA-node host.
  • Work-stealing observable: skew data 90/10 across NUMA nodes; the idle node's workers steal within one scheduling quantum, total wall-clock stays within 20% of the balanced case (numa.stress_imbalance bucket).
  • Property test: pipeline sum result is invariant under morsel size ∈ {100, 1K, 10K, 100K, 1M} rows/morsel.
Fixtures
Fixture Purpose Expected Output
numa.affinity.report.json 32-core, 2-NUMA host, uniform workload ≥ 90% NUMA-local pops
numa.stress_imbalance.report.json 90/10 data skew across NUMA nodes Work-stealing recovers; ≤ 20% slower than balanced
morsel_size_invariance.json Same query at 5 morsel sizes Identical sum every time
pipeline_barrier_violation.json Adversarial plan attempting to skip a breaker Rejected at build time (I11)
Pitfalls
  • NUMA topology detection exists only on Linux; the single-virtual-node fallback is mandatory on macOS/Windows, not optional (ADR-07's platform scope).
  • Pinning a thread to a CPU prevents OS migration; on a busy host with other pinned workloads this can degrade throughput — document that VOE expects to own its cores.
  • Morsel size too small (< 1K rows) → scheduler pop/push contention dominates per-row cost.
  • Morsel size too large → poor load balance; a worker finishing the last morsel of a skewed pipeline can trail peers by minutes.
  • A pipeline mutating shared state per row without the two-stage thread-local pattern (P9) is the canonical source of cache-line ping-pong (§16.6).

⬜ Phase 4 — Hash Aggregation (Weeks 7–9) §16

Objectives
  • Implement the two-stage (thread-local partial + final merge) vectorized hash aggregation pattern (P9, Polychroniou et al. 2015, section 4).
  • Constraint: must respect the memory-budget invariant (I7) even though the spill action lands in §20 — Phase 4 tracks memory; Phase 8 adds the spill.
Deliverable

TPC-H Q1 (single group-by, multi-aggregate) runs correctly at SF=1; hash-table benchmarks recorded; docs/architecture/hash-table.md.

Acceptance
  • TPC-H Q1 SF=1 bit-identical to the reference output (ADR-17), 1e-6 tolerance for AVG (I13).
  • M7: hash-agg build throughput ≥ 80M probes/sec single-core on a 10M-row, 1M-unique-key dataset.
  • Property test: 100K random group-by inputs match a HashMap<Tuple, AggState> reference exactly (except the documented f64 SUM/AVG epsilon, I13).
  • hash.linear_probe conformance bucket: 1M random probes, load factor < 0.7 (I5) maintained throughout.
Fixtures
Fixture Purpose Expected Output
tpch.q1_sf1.report.json TPC-H Q1 at SF=1 Bit-identical to reference, 1e-6 tolerance on AVG
hash.linear_probe.report.json 1M random probes 0 collision misses; load factor < 0.7
hash.skew_handling.report.json Adversarial skewed keys Probe-length p99 ≤ 32; chained fallback engaged
groupby_vs_hashmap_reference.json 100K random group-by rows Matches HashMap reference within I13 epsilon
Pitfalls
  • Cache-line ping-pong on a shared hash table → up to 100× slowdown; the two-stage pattern (P9) avoids this — never share one LinearProbeTable across worker threads during build.
  • Hash table without a bounded load factor → OOM on GROUP BY <high-cardinality> (e.g. a UUID column produces a group per row); I5's 0.7 threshold plus §20's spill is mandatory.
  • The 4-slot bucket layout assumes roughly uniform key distribution; heavy skew degrades linear probing toward quadratic — the chained fallback (ADR-08) engages via probe-length statistics.
  • SUM/AVG over f64 are not associative; parallel merge order affects the last few bits — tests compare within the documented I13 epsilon, never bit-identical for floats.
  • An unrandomized hash seed lets an adversary craft inputs that collide every probe — I6 mandates a per-query random seed, never a fixed one.

  • M6: hash-join probe throughput ≥ 200M rows/sec single-core.

Fixture Purpose Expected Output

hash_join_build_bench.json 100M-row i64-keyed build ≥ 100M rows/sec (M5)

Pitfalls
  • LeftOuter/FullOuter: build-side rows matching nothing must still appear; the probe pipeline alone cannot know this — the build side's "matched" bitmap, flushed at finish(), is the only mechanism (a silent correctness gap if skipped).
  • Hash collisions: two distinct keys with the same hash land in the same bucket; the post-hash key comparison is mandatory — skipping it "for speed" is a silent-wrong-results bug.
  • Build-side skew: a key with millions of matches can blow up probe-side output (one input row → millions of output rows); the probe operator must paginate output into fixed-size batches (I1's bound), never materialize an unbounded batch.
  • Build side larger than memory requires the grace-hash-join spill pattern (§20.3) — Phase 5 alone caps the supported build-side size at the memory budget.
  • Cross-NUMA hash-table access on a partitioned join costs ~3× vs. local access (§4); pin the build partition to the same NUMA node as the probe workers that will read it.

  • Exchange throughput ≥ 1 GB/s on a 32-core single-NUMA host; ≥ 500 MB/s cross-NUMA.
  • NUMA-local affinity verified: trace a row through the exchange, confirm the destination worker is on the partition's assigned NUMA node.

Pitfalls
  • mod num_partitions with a non-power-of-two partition count is an expensive division on the hot path; use the multiplicative-hash trick instead.
  • Skew: a hot key produces a hot partition regardless of hash quality; range-based partitioning helps if the skew is on a range column, key-salting helps if it's on a specific value.
  • Exchange buffer growth without a backpressure signal OOMs; the 64K-row default cap plus upstream backpressure is mandatory, not a tuning nice-to-have.
  • A pull-based exchange (downstream pulls from per-partition buffers) serializes at the boundary — exactly the 2010s-era mistake P3/ADR-06 rejects; VOE's exchange pushes into queues, workers pop on their own schedule.

  • Radix sort: ≥ 500M i64 keys/sec single-core.

Pitfalls
  • Sign bit on signed-integer radix sort: forgetting to flip it sorts -1 after 0.
  • IEEE-754 f64 sort: the bit pattern of negative floats is in reverse numeric order; convert via f64::to_bits() with sign-bit fixup, radix-sort, convert back.
  • Variable-width key comparison: long strings cause many cache misses; for pathological inputs (megabyte-scale strings) comparison sort is faster than any "clever" radix variant on strings.
  • Top-K with k > batch_size: the heap-based approach degrades; the full-sort-then-slice switch at k > 10,000 avoids pathological heap churn.

Fixtures
Fixture Purpose Expected Output
spill.hash_agg_roundtrip.report.json Hash agg, 1 GiB budget vs. unlimited Results identical

Pitfalls
  • Spill format must be stable across versions — Arrow IPC (ADR-02) is the standard; never invent a private format a future version can't read.
  • Spill on out-of-disk → query failure; mitigation is the per-query spill quota (10× budget) plus a graceful Error::SpillQuotaExceeded, never an unbounded disk fill.
  • Partial-vs-final aggregate schema mismatch: the spilled partial output must carry enough state for the final merge (e.g. Avg's (sum, count), never a pre-divided value) — exactly §16.2's rule, now under spill pressure too.
  • Spilled partitions must be hash-consistent between build-side spill and probe-side read; a seed change between spill and probe is a correctness catastrophe (I6) — the exact failure §8.6 walks through.
  • Spill files must be cleaned up on cancellation, not just normal completion — the cleanup hook is registered with the query lifecycle, not with a "success" callback alone.

Fixtures
Fixture Purpose Expected Output
codegen_vs_interpreted_q1_expr.json Q1's price expression, compiled vs. interpreted ≥ 30% speedup, identical output
codegen_cache_hit_rate.json Full TPC-H SF=1 run ≥ 90% cache hit rate

Pitfalls
  • Cranelift's compile time (~10 ms/kernel) exceeds execution time for small queries (< 1M rows total); the hot-path threshold is the break-even — do not lower it without re-measuring.
  • Cranelift's ISA support lags LLVM; AVX-512 emission is limited, falling back to AVX2 in compiled kernels even though the interpreted path uses AVX-512 via pulp — document the asymmetry so a performance-regression report doesn't mistake it for a bug.
  • Compiled-kernel cache poisoning: a malicious or corrupted expression could compile to incorrect code; every cache entry carries an HMAC signature, verified on every hit (T5, §23).
  • The trampoline's unsafe is the second and last in the codebase; every kernel-signature change requires updating the trampoline in lockstep — missing this produces undefined behavior, not a compile error.
  • Recursive expressions (> ~50 nodes) can blow cranelift's compiler recursion limit; VOE rejects overly deep trees rather than crashing (documented boundary condition).

⬜ Phase 10 — Predicate Pushdown, Late Materialization, Dictionary Pass-Through & TPC-H/TPC-DS Conformance (Weeks 16–18) §22

Pitfalls
  • Predicate pushdown losing nullability: WHERE col > 5 must also reject col IS NULL; a pushdown rule dropping the null check produces silent wrong results (P13, I3 extended here).
  • Dictionary vectors decoded too early: a filter operator lacking a dictionary specialization loses P5's win; the registry must cover every pass-through operator, or the planner inserts an explicit Decode (I9).
  • Late-mat row-id tracking across join boundaries: the join emits (probe_row_id, build_row_id) pairs; the materializer must fetch by both, or it fetches the wrong row (extends §17.2).
  • UDFs are categorically forbidden from being pushed into scans — PhaseDeferred("§22.8")'s boundary exists partly to make this moot.
  • Parquet page statistics are conservative; the row-level re-evaluation is mandatory, never skippable "for speed."
