104 — Vectorized OLAP Query Executor

Project Number: 104

Project Name: Vectorized OLAP Query Executor

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

VOE is a single-node, multi-core, read-only physical-plan executor for analytical (OLAP) workloads: it consumes a pre-planned physical operator tree (schemas resolved, expressions bound, no cost-based optimization performed) and produces result batches by driving vectorized, columnar, push-based operators through a morsel-driven, NUMA-aware work-stealing scheduler, evaluating expressions via SIMD-dispatched interpreted kernels with an optional cranelift JIT sidecar for hot expressions, and spilling to local disk when hash-based operators exceed their memory budget.

Phase-0 in-scope modules/crates:

  1. voe-core — Arrow-compatible record-batch / array / schema layer.
  2. voe-kernels — SIMD-dispatched scalar kernel library.
  3. voe-ops — physical operator implementations.
  4. voe-morsel — morsel-driven NUMA-aware scheduler.
  5. voe-plan — physical-plan / expression IR + pipeline builder.
  6. voe-hash — vectorized linear-probing hash table.
  7. voe-spill — spill-to-disk subsystem.
  8. voe-codegen — cranelift compiled-kernel sidecar.
  9. voe-cli (the voe binary) — plan runner / CLI.
  10. conformance/runner — TPC-H / TPC-DS / cross-validation harness.

System boundaries. Provides: vectorized execution of a supplied physical plan; columnar in-memory format; hash join/aggregation; sort/top-K; exchange; spill; predicate-pushdown application; dictionary pass-through. Delegates: SQL parsing, binding, and cost-based optimization (assumed done upstream by the caller); durability/MVCC/transactions (none — this is read-only); persistent storage ownership (reads Arrow IPC / Parquet / in-memory; never owns a storage engine). Does NOT provide: distributed/multi-node coordination (the Exchange operator, §18, is only the seam — PhaseDeferred("§30")); GPU kernels (PhaseDeferred("§35")); a SQL front-end; transactional writes; regex/JSON-path string kernels beyond bytewise compare/equality.

Non-goals: cost-based query optimization, storage/durability, multi-tenant resource isolation beyond a per-query memory budget, a network wire protocol.

Deployment model: an embedded library linked into a host process (service or CLI), plus a standalone voe CLI binary for ad-hoc plan execution; single OS process, worker threads pinned across the host's NUMA topology.

Target users/operators: database-systems engineers building or extending an analytical query engine; the reader seeking principal-engineer command of vectorized OLAP execution.

What later phases unlock: Phase 8 (§20, spill) unlocks datasets larger than RAM; Phase 9 (§21, cranelift) unlocks near-compiled throughput on hot expressions; Phase 10 (§22, pushdown + dictionary pass-through + TPC-H/TPC-DS conformance) unlocks realistic mixed workloads. PhaseDeferred surfaces (distributed exchange, GPU kernels, UDFs, full TPC-DS) unlock horizontal scale and extensibility beyond Phase 10 — see §36 Deferred Features Register.

Recommended language + rationale: Rust 1.78+, edition 2021 (ADR-01, §9) — the borrow checker statically eliminates a whole class of memory-corruption bugs precisely in the two places a vectorized engine is most exposed to them (SIMD kernel inner loops, the cranelift trampoline), and both are the only two unsafe surfaces permitted (P15, §6). Rejected: C++ (the incumbent ecosystem language — Velox, Photon, ClickHouse — but no compiler-enforced memory safety); Zig (elegant comptime SIMD, but no mature Arrow/Parquet/cranelift bindings).

Prerequisites: relational algebra; the Volcano iterator model (Graefe 1993, §5); columnar storage formats (Arrow, Parquet); at least one query-engine-internals paper; Rust ownership/borrowing. A reader should be able to draw the TPC-H Q3 dataflow graph from memory and explain when a hash join beats a sort-merge join, and when it does not.

Estimated timeline: Phase 0 in 1 week; the full Phase 0–10 plan in 5–7 months for a solo/small-team implementer at full engineering effort; the TPC-DS-subset + cross-validation tail of Phase 10 adds 2–3 weeks beyond the core 16 weeks.

2. Why Build This

  • Vectorized columnar execution is the dominant OLAP architecture of the last two decades: ClickHouse, DuckDB, Snowflake, Databricks Photon, Meta Velox, Apache DataFusion/Acero, Vertica, Spark Tungsten, and Polars converge on the same core design — columnar batches of 10³–10⁵ rows, push-based operator pipelines, hash tables for join/agg, SIMD where it counts.
  • The Volcano (tuple-at-a-time) → X100 (vectorized) → HyPer (compiled) transition is one of database history's most consequential architectural shifts; it opened a reproducible 2×–100× gap over row-store engines on analytical workloads (Boncz-Zukowski-Nes 2005, section 2; Abadi et al. 2008).
  • Building the record-batch layer teaches Arrow's buffer/validity/offset/dictionary layout — the lingua franca of the modern analytical stack (Arrow spec; DataFusion; Polars).
  • Building the kernel layer teaches SIMD dispatch, cache-line-aware data layout, and null-propagation semantics that generalize past databases to any high-throughput numeric system.
  • Building the morsel scheduler teaches NUMA-aware parallel scheduling (Leis et al. 2014) — a pattern reused anywhere many-core, memory-bandwidth-bound work needs load balance without a central bottleneck.
  • Building the hash table teaches vectorized linear probing (Polychroniou et al. 2015) — cache-line-bucketed, SIMD-probed hashing, the backbone of fast in-memory joins/aggregates.
  • Building the cranelift sidecar teaches the vectorization-vs-compilation tradeoff directly (Sompolski-Zukowski-Boncz 2011; Kersten et al. 2018) instead of only reading about it.
  • Calibration value: TPC-H/TPC-DS are field-standard yardsticks; cross-validating against DuckDB/DataFusion is externally checkable evidence of correctness, not a self-graded exercise.

What Mastery Looks Like

  • Explains, with numbers, why DuckDB defaults to a ~2048-row vector and ClickHouse to a 65536-row Block, reproducing the L1-fit argument (§33 Back-of-Envelope Capacity Model; §14 Phase 2).
  • Traces a TPC-H Q1 execution from Scan to HashAggBuild to HashAggFinal to result, naming every pipeline breaker and morsel boundary (§15 Phase 3; §16 Phase 4; §8 Domain Model).
  • Diagnoses a page reporting NUMA-local ratio (I8) below 90% and names the two most likely root causes and their detection signals (§15.9 Failure Analysis; §24 Failure Modes & Recovery).
  • Defends, with a concrete regime, why vectorized interpretation was chosen over full query compilation — and names the regime where compilation wins instead (ADR-16, §9; §35 Alternative Architectures).
  • Sizes a hash join's build-side memory footprint and predicts whether it will spill, using the formulas in §33 Back-of-Envelope Capacity Model.
  • Extends the kernel registry with a new dictionary-encoded specialization without breaking the pass-through invariant (I9, §7; §14 Phase 2; §22 Phase 10).
  • Reads the ADR table (§9) and, for any locked choice, states the concrete workload regime in which the rejected alternative would have been the right call.

Four properties recur throughout this document. Operators and kernels are independent — an operator (filter, project, hash-agg) is a state machine over record batches; it does not know whether the underlying kernel is interpreted, SIMD-dispatched, or cranelift-compiled (P6, §6). Parallelism is morsel-driven, not exchange-driven — a pipeline is a chain of streaming operators sharing state; the scheduler dispatches 100K-row morsels to worker threads, and pipelines synchronize only at pipeline breakers (Sort, HashAggFinal, HashJoinBuild, Exchange — I11, §7). Execution is push-based by default — each operator's consume(RecordBatch) is the hot path; the Volcano pull model survives only as a debug surface (next()) for unit tests and the CLI (ADR-05, §9). The record batch is the unit of data flow — a batch is Schema + Vec<ArrayRef> (Arrow-compatible, §13); the operator's loop runs over arrays, never rows; the row appears only at the result-set boundary.

Trust boundary: the Caller box — VOE trusts the supplied plan to be schema-valid and type-checked (T1, §23); it does not re-verify SQL-level semantics. Concurrency boundary: the Morsel Scheduler — everything below it runs inside worker threads; everything above is single-threaded plan construction. Persistence boundary: the Spill Subsystem — the only component that writes to durable storage, and only ephemeral, query-scoped Arrow IPC files (deleted on query completion or cancellation, FM6 §24). Protocol boundary: Arrow IPC is the sole wire format, used for both external ingest (Parquet/Arrow files) and internal spill; there is no network boundary in Phase 0–10 scope (§4).

6. Design Principles

  1. Vectorized beats tuple-at-a-time, full stop (P1). No operator's inner loop sees a scalar except at result-set boundaries. The Boncz-Zukowski-Nes 2005 speedup ratios are measured in voe-bench and gate merges (M3/M4, §29). Violation: any for row in batch loop inside consume (Pitfall in §14.6).
  2. Push beats pull for parallelism (P2). consume(RecordBatch) is the hot path; next() is a debug-only pull surface (ADR-05). Violation: reintroducing pull on the hot path serializes at every operator boundary (§18.6).
  3. Morsel-driven beats exchange-based for NUMA (P3). Leis et al. 2014, section 3, closes the exchange-everywhere-serializes case; morsels + work-stealing + NUMA-aware allocation is the alternative (ADR-04, ADR-06). Violation: a pipeline that inserts an exchange at every operator boundary reintroduces the bottleneck this design exists to avoid.
  4. Late materialization wins on selective queries (P4). A pipeline carrying (row_id, key_cols) through filter/project, materializing full rows only at the sink, beats eager materialization on wide, selective queries (Abadi et al. 2008, section 4; ADR-11). Violation: an operator that eagerly fetches every column loses the win entirely (§22.7).
  5. Dictionary-encoded vectors pass through unchanged (P5). Dict<u32, Utf8> flows through filter, project, partial_agg, hash_join_probe without decoding (ADR-10, I9). Violation: eager decode at the scan boundary defeats the optimization on low-cardinality string columns.
  6. Compiled kernels are a sidecar, not a default (P6). Cranelift compiles expressions that have processed > 1M interpreted rows (ADR-16, §21). Violation: compiling cold expressions makes compile time exceed execution time (§21.6).
  7. SIMD is beneath kernels, runtime-dispatched (P7). Every kernel has a scalar reference plus a pulp-dispatched specialization selected once per process at first use (ADR-13, ADR-14). Violation: calling std::arch intrinsics directly bypasses dispatch and SIGILLs on unsupported hosts (§14.6).
  8. Arrow at the buffer layer, not at the operator layer (P8). RecordBatch is byte-compatible with Arrow (zero-copy ingest/emit, ADR-02); the operator trait (§11) is VOE's own. Violation: importing Arrow's own kernel/operator API couples VOE to a dependency's release cadence.
  9. The hash table dominates memory (P9). Hash agg and hash join are the two largest memory consumers in a TPC-H-class workload; the vectorized linear-probing layout (Polychroniou et al. 2015, section 4) is load-bearing (ADR-08). Violation: an unbounded hash table without spill OOMs on GROUP BY <high-cardinality> (I5, §16.6).
  10. Spill-to-disk is mandatory for unbounded operators (P10). Hash agg, hash join, sort, and top-K can each exceed memory; every one has a spill path triggered at 80% of budget (ADR-09, I7). Violation: shipping any of them without a spill path caps the maximum supported dataset size at available RAM.
  11. Pipeline breakers are explicit (P11). Sort, HashAggFinal, HashJoinBuild, Exchange. The pipeline builder cuts the plan at these points (I11, §8). Violation: an operator that silently buffers instead of declaring itself a breaker corrupts the scheduler's barrier semantics.
  12. Predicate pushdown is a planner concern; the executor must accept it (P12). A scan operator accepts Vec<Expression> pushdown predicates (ADR-12); Parquet applies them at the page level, in-memory scans at the batch level. Violation: ignoring pushed predicates wastes the planner's analysis and the page-skip IO savings.
  13. Nullability is first-class (P13). Every kernel takes and produces Bitmap validity; Kleene three-valued logic governs boolean operations on NULL (I3). Violation: a kernel that drops or mis-propagates validity produces silently wrong query results.
  14. The schema is immutable through a pipeline (P14). An operator's output schema is fully determined at plan-construction time (I4). Violation: an operator that "discovers" a column at runtime breaks the pipeline builder's static schema-compatibility check.
  15. No unsafe outside two audited surfaces (P15). The SIMD kernel inner loops and the cranelift trampoline are the only permitted unsafe; both have safe scalar fallbacks and are covered by fuzzing and cross-validation (ADR-01, T4 §23). Violation: any third unsafe site is an automatic code-review rejection.

These principles are enforced at the type level where Rust's type system allows it (P14 via &SchemaRef, P13 via Bitmap-typed kernel signatures), and by code review and the conformance suite (§27) where it does not.

8. Domain Model / Protocol / Data Model

8.1 Physical-plan grammar (EBNF)

PhysicalPlan   ::= Scan | Filter | Project | HashAggregate | HashJoin
                 | Sort | TopK | Exchange
Scan           ::= "Scan" "{" source: SourceRef, schema: Schema,
                     predicates: Expression* "}"
Filter         ::= "Filter" "{" child: PhysicalPlan, predicate: Expression "}"
Project        ::= "Project" "{" child: PhysicalPlan, exprs: Expression+ "}"
HashAggregate  ::= "HashAggregate" "{" child: PhysicalPlan,
                     group_by: ColumnRef*, agg_fns: AggFn+ "}"
HashJoin       ::= "HashJoin" "{" build: PhysicalPlan, probe: PhysicalPlan,
                     build_keys: ColumnRef+, probe_keys: ColumnRef+,
                     join_type: JoinType "}"
Sort           ::= "Sort" "{" child: PhysicalPlan, keys: (ColumnRef, Order)+ "}"
TopK           ::= "TopK" "{" child: PhysicalPlan, keys: (ColumnRef, Order)+,
                     k: u64 "}"
Exchange       ::= "Exchange" "{" child: PhysicalPlan, partition_keys: ColumnRef+,
                     num_partitions: u32 "}"

8.2 Expression grammar (EBNF)

Expression ::= Column(idx: usize)
             | Literal(value: ScalarValue)
             | BinaryOp(op: BinaryOp, left: Expression, right: Expression)
             | UnaryOp(op: UnaryOp, child: Expression)
             | Cast(child: Expression, to: DataType)
             | Case(whens: (Expression, Expression)+, otherwise: Expression)
BinaryOp   ::= Add | Sub | Mul | Div | Eq | NotEq | Lt | LtEq | Gt | GtEq | And | Or
UnaryOp    ::= Not | Neg | IsNull | IsNotNull

Every Expression is resolved (column indices bound, types checked) before it reaches VOE — the planner's job (§1 non-goal). A malformed Column(idx) whose idx exceeds its child's schema width is rejected at pipeline-build time, never at row-evaluation time (§8.4).

8.3 Pipeline state machine

State Entry Condition Valid Transitions Exit Action
Building Pipeline object constructed by pipeline_builder → Running Scheduler dispatch begins
Running First morsel popped by a worker → Draining Source exhausted, finish() called down the operator chain
Draining All source morsels consumed; finish() propagating → Finished Sink's finish() returns
Finished Sink finish() returned Ok (terminal) Results handed to the downstream pipeline or the caller

A pipeline breaker (I11) never enters Running for its downstream pipeline until its own Finished state is reached — the scheduler barrier that enforces this is the concrete mechanism behind I11.

8.4 Worked example — TPC-H Q1

Q1 (GROUP BY l_returnflag, l_linestatus over a filtered lineitem scan) compiles to two pipelines: Pipeline 0 = Scan(lineitem) → Filter(l_shipdate ≤ X) → Project(...) → HashAggBuild(sink); Pipeline 1 = HashAggFinal(source) → Sort(l_returnflag, l_linestatus) → Result. Pipeline 0 fans out across all workers (no join, fully parallel); Pipeline 1 begins only after every Pipeline-0 worker's HashAggBuild::finish() has merged into the final table (I11).

8.5 Malformed-input example

A Filter node whose predicate is Column(7) but whose child schema has 5 fields is rejected by pipeline_builder::validate with Error::ColumnIndexOutOfBounds { index: 7, schema_width: 5 } at plan-build time — before any worker thread starts, before any morsel is read (I4, I11).

8.6 Failure-path example — hash-agg spill

Sequence: (1) HashAggBuild::consume inserts a batch, memory estimate crosses 80% of budget (ADR-09); (2) MemoryBudget::check returns Action::Spill (I7); (3) the operator drains its LinearProbeTable into N SpillWriters, one per hash-partition, using the query's seed (I6); (4) subsequent batches are hashed directly to the matching spill partition without touching an in-memory table; (5) at finish(), each spilled partition is re-read and merged partition-by-partition, bounding peak memory to one partition's worth regardless of total input size. See §20 (Phase 8) for the full mechanism and §24 (FM4) for the failure-mode table.

11.1 Schema and primitive types (voe-core::schema)

pub enum DataType {
    Boolean, Int8, Int16, Int32, Int64, UInt8, UInt16, UInt32, UInt64,
    Float32, Float64, Utf8, Binary, Date32, Timestamp(TimeUnit),

pub enum TimeUnit { Second, Millisecond, Microsecond, Nanosecond }

Ownership: SchemaRef is a shared, immutable Arc — no interior mutability (I4, P14). Mutation: none after construction; a new Schema is built, never patched. Concurrency: Send + Sync via Arc. Persistence: embedded in Arrow IPC file headers (§13.5). Wire compatibility: maps 1:1 onto the Arrow columnar-format schema message.

11.2 Array and RecordBatch (voe-core::array, voe-core::batch)

pub trait Array: Send + Sync {
    fn len(&self) -> usize;
    fn data_type(&self) -> &DataType;
    fn validity(&self) -> Option<&Bitmap>;
    fn slice(&self, offset: usize, length: usize) -> ArrayRef;
}
pub type ArrayRef = Arc<dyn Array>;
pub struct PrimitiveArray<T: PrimitiveType> {
    values: Arc<[T]>, validity: Option<Bitmap>, offset: usize, length: usize,
}
pub struct Utf8Array {
    values: Arc<[u8]>, offsets: Arc<[i32]>, validity: Option<Bitmap>,
    offset: usize, length: usize,
}
pub struct DictionaryArray<K: PrimitiveType> { keys: PrimitiveArray<K>, values: ArrayRef }
pub struct RecordBatch { schema: SchemaRef, columns: Vec<ArrayRef>, num_rows: usize }

Ownership: buffers are Arc<[T]>, 64-byte aligned; slice() shares the backing allocation (zero-copy, I1 batch bound applies to num_rows). Mutation: arrays are immutable once built; a builder type (not shown) accumulates into a fresh array. Concurrency: Array: Send + Sync; safe to share read-only across worker threads. Persistence: none — batches are ephemeral unless spilled (§11.7). Serialization: ipc.rs round-trips via arrow-rs's Arrow IPC reader/ writer, byte-identical to the Arrow spec (§13.5). Compatibility: RecordBatch::try_new rejects a schema/column-count or column/schema-type mismatch (I4) — signature only, no body per the No-Code Rule.

11.3 Operator trait (voe-ops::operator)

pub trait Operator: Send + Sync {
    fn output_schema(&self) -> &SchemaRef;
    fn consume(&mut self, batch: RecordBatch) -> Result<bool, Error>;   // push, hot path (P2)
    fn next(&mut self) -> Result<Option<RecordBatch>, Error>;           // pull, debug-only
    fn finish(&mut self) -> Result<(), Error>;                         // breaker finalization
}

Ownership: each Pipeline owns its operators via Box<dyn Operator>. Mutation: consume and finish take &mut self — one operator instance is single-threaded (a worker's thread-local copy for stateful sinks, P9). Concurrency: the trait requires Send + Sync for handoff between morsels, not concurrent &mut access. Persistence: none (state lives only for one pipeline execution). Compatibility: output_schema() must equal the schema the operator's consume actually produces — enforced at pipeline-build time (I4).

11.4 Morsel, Pipeline, Scheduler, NUMA (voe-morsel)

pub struct Morsel { pub batch: RecordBatch, pub partition_id: u32, pub source_offset: u64 }
pub struct Pipeline { pub source: Box<dyn Operator>, pub ops: Vec<Box<dyn Operator>>,
                       pub sink: Box<dyn Operator> }
pub struct Scheduler { topology: NumaTopology, queues: Vec<MorselQueue>,
                        pipelines: Vec<Arc<Pipeline>> }
pub struct NumaTopology { pub nodes: Vec<NumaNode> }
pub struct NumaNode { pub id: u32, pub cpus: Vec<u32>, pub memory_bytes: u64 }

Ownership: Scheduler owns one MorselQueue per NumaNode; a Morsel moves by value between a queue and a worker (single-owner, no shared mutable state, avoids P9's ping-pong pitfall). Mutation: MorselQueue is a lock-free MPMC ring buffer (push/pop only, no in-place edit). Concurrency: the concurrency boundary of the whole system (§3); workers are pinned threads, one per physical core per NUMA node (§4). Persistence: none. Compatibility: source_offset is stable across a single query's lifetime only — used for spill-recovery bookkeeping (§20), never persisted across queries.

Ownership: one HashTable per worker's thread-local partial build (P9's two-stage pattern); merged into a single final table only at the HashAggFinal/HashJoinProbe boundary. Mutation: insert-only during build; read-only during probe (never both concurrently on the same instance — I11). Persistence: spilled to SpillWriter (§11.7) under memory pressure (I7); the seed field is carried through the spill (I6). Compatibility: capacity is always a power of two; mask = capacity - 1 — changing this invariant without updating every probe_batch/build_batch call site is a correctness break.

  • Cache-line-aligned bitmap I/O (carried from §13) is a prerequisite for every SIMD kernel's throughput target (M3/M4, §29).

15.6 Pitfalls

  • NUMA topology detection exists only on Linux; the single-virtual-node fallback is mandatory on macOS/Windows, not optional (ADR-07's platform scope).
  • Pinning a thread to a CPU prevents OS migration; on a busy host with other pinned workloads this can degrade throughput — document that VOE expects to own its cores.
  • Morsel size too small (< 1K rows) → scheduler pop/push contention dominates per-row cost.
  • Morsel size too large → poor load balance; a worker finishing the last morsel of a skewed pipeline can trail peers by minutes.
  • A pipeline mutating shared state per row without the two-stage thread-local pattern (P9) is the canonical source of cache-line ping-pong (§16.6).

15.7 Performance Concerns

  • Round-robin stealing (chosen for Phase-3 simplicity) is measurably worse than last-stealer-first under some skew patterns (Leis et al. 2014) — a documented stretch-goal refinement, not a Phase-3 requirement.
  • Cross-NUMA morsel steals pay the ~150–300 ns cross-socket latency (§4) on every subsequent cache miss in that morsel's processing — M11's 90% efficiency target assumes stealing is the exception, not the rule.
  • Queue contention: a lock-free MPMC ring buffer's CAS retry rate must be bounded; default queue depth is 256 morsels/node, keeping producers from spin-waiting.

15.8 Edge Cases

  • Single-core host: NumaTopology::detect() returns exactly one node with one CPU; the scheduler must not deadlock waiting to "steal from peers" when there are none.
  • A pipeline whose source produces zero morsels (empty scan): the I11 barrier must still release the downstream pipeline — an empty upstream still "finishes."
  • Worker-thread panic mid-morsel: the scheduler must not hang waiting on a queue that will never be serviced again (FM1, §24).

15.9 Failure Analysis

  • What breaks: NUMA-local ratio (I8) sustained below 90% under non-skewed load. Detection: numa_local_ratio gauge alerts (FM7, §24). Blast radius: degraded throughput for the affected query only — correctness invariants I1–I7, I9–I14 are unaffected by NUMA locality. Containment: the affected pipeline continues. Recovery: on-call runbook docs/runbooks/numa-debug.md — check topology-detection output, external pinning conflicts, queue-depth saturation.

15.10 Operational Notes

  • Metrics: numa_local_ratio, batch_size_histogram, morsel_queue_depth, worker_steal_count.
  • Runbook: docs/runbooks/numa-debug.md — the first named runbook in the stack (§25).

  • Cache-line ping-pong on a shared hash table → up to 100× slowdown; the two-stage pattern (P9) avoids this — never share one LinearProbeTable across worker threads during build.
  • Hash table without a bounded load factor → OOM on GROUP BY <high-cardinality> (e.g. a UUID column produces a group per row); I5's 0.7 threshold plus §20's spill is mandatory.
  • The 4-slot bucket layout assumes roughly uniform key distribution; heavy skew degrades linear probing toward quadratic — the chained fallback (ADR-08) engages via probe-length statistics.
  • SUM/AVG over f64 are not associative; parallel merge order affects the last few bits — tests compare within the documented I13 epsilon, never bit-identical for floats.
  • An unrandomized hash seed lets an adversary craft inputs that collide every probe — I6 mandates a per-query random seed, never a fixed one.

16.7 Performance Concerns

  • The bucket layout (64-byte aligned, hash+key+value co-located) targets one cache miss per probe step regardless of SIMD lane count — verify with a cache-miss profiler (§29), not just wall-clock.
  • Thread-local partial tables trade memory (N workers × 1 table) for zero cross-thread contention — document the memory multiplier explicitly against the per-query budget (§4, §33).
  • AVG's deferred division (store sum, count, divide at finalize) avoids repeated floating-point division in the hot insert path.

16.8 Edge Cases

  • Empty input (0 rows): HashAggFinal must emit zero groups, not a spurious NULL-keyed group.
  • GROUP BY on a column that is entirely NULL: NULL is a valid group key (SQL semantics), distinct from "no group."
  • A group-by key wider than a single u64 (composite keys, reusing §17.3's pattern): hashed and compared as a concatenated byte sequence.
  • Aggregate overflow: SUM over i64 inputs overflowing i64 accumulation returns Error::AggregateOverflow, never wraps (I10 extended to aggregates).

16.9 Failure Analysis

  • What breaks: unbounded hash-table growth under extreme cardinality before §20's spill exists. Detection: hash_table_load_factor gauge (I5) trending toward the resize ceiling faster than expected. Blast radius: the single query's memory footprint; other concurrent queries are isolated by their own per-query budget (§4). Recovery (pre-§20): query fails closed with Error::MemoryBudgetExceeded rather than OOM-killing the process; post-§20: automatic spill (§20.5).

16.10 Operational Notes

  • Metrics: hash_table_load_factor, hash_probe_length_p99, agg_group_count.
  • docs/architecture/hash-table.md documents the bucket layout and skew-detection thresholds.
  • Runbook cross-reference: a probe-length p99 alert points to docs/runbooks/triage.md.

17.6 Pitfalls

  • LeftOuter/FullOuter: build-side rows matching nothing must still appear; the probe pipeline alone cannot know this — the build side's "matched" bitmap, flushed at finish(), is the only mechanism (a silent correctness gap if skipped).
  • Hash collisions: two distinct keys with the same hash land in the same bucket; the post-hash key comparison is mandatory — skipping it "for speed" is a silent-wrong-results bug.
  • Build-side skew: a key with millions of matches can blow up probe-side output (one input row → millions of output rows); the probe operator must paginate output into fixed-size batches (I1's bound), never materialize an unbounded batch.
  • Build side larger than memory requires the grace-hash-join spill pattern (§20.3) — Phase 5 alone caps the supported build-side size at the memory budget.
  • Cross-NUMA hash-table access on a partitioned join costs ~3× vs. local access (§4); pin the build partition to the same NUMA node as the probe workers that will read it.

17.7 Performance Concerns

  • Late materialization (P4) is the single biggest lever on selective, wide-table joins — but adds row-id indirection cost on low-selectivity joins (ADR-11's rejected-alternative regime).
  • Broadcast-vs-partitioned build strategy trades memory for parallelism: broadcast avoids repartitioning cost but replicates the table's read footprint across every probe worker.
  • Multi-key join hashing pays a concatenation cost per row; for very wide composite keys a two-level hash (hash-of-hash) is a documented stretch refinement.

17.8 Edge Cases

  • Empty build side: probe emits zero matches for Inner, all-unmatched rows for LeftOuter.
  • NULL join keys: SQL join semantics treat NULL = NULL as unknown, never a match — distinct from GROUP BY's NULL-is-a-valid-group rule (§16.8).
  • A probe batch entirely composed of misses must not allocate an empty non-zero-capacity output batch (wastes cache, contradicts I1's bound intent).

17.9 Failure Analysis

  • What breaks: build-side skew producing an unbounded per-row output fan-out. Detection: output-batch-count-per-input-row metric spikes; the probe operator's pagination bound (§17.6) contains it. Blast radius: elevated latency for the affected query only — memory stays bounded by I1. Recovery: no automatic recovery needed if pagination holds; otherwise the query aborts with Error::MemoryBudgetExceeded (same class as FM4, §24).

17.10 Operational Notes

  • Metrics: hash_join_build_rows, hash_join_probe_rows, hash_join_output_fanout_p99.

18. Phase 6 — Exchange Operator (Weeks 11–12)

18.1 Objectives

  • Implement cross-NUMA hash-repartition and range-partition exchange operators — the seam for future distributed execution (ADR-15, P3).

18.2 Detailed Implementation Steps

  • Implement voe-ops::exchange::partition::ExchangeOut — hash key columns (voe-kernels::hash), compute destination partition via the multiplicative-hash trick ((hash as u64 * num_partitions as u64) >> 32), push per-partition batches into per-partition MorselQueues (§11.9).

  • Pin each partition's output queue to the NUMA node that will consume it — the cross-NUMA copy is paid once at the exchange boundary, not at every downstream operator access.
  • Implement range partitioning for sort (§19): boundaries sampled from the input, non- overlapping key ranges assigned to workers, a separate code path from hash partitioning.
  • Wire exchange backpressure: a partition queue exceeding 64K buffered rows signals the upstream to pause pushing (bounds unbounded buffering, extending I1's batch-size discipline to the queue level).
  • Add exchange throughput telemetry (rows/sec per partition, cross-NUMA vs. local).

18.6 Pitfalls

  • mod num_partitions with a non-power-of-two partition count is an expensive division on the hot path; use the multiplicative-hash trick instead.
  • Skew: a hot key produces a hot partition regardless of hash quality; range-based partitioning helps if the skew is on a range column, key-salting helps if it's on a specific value.
  • Exchange buffer growth without a backpressure signal OOMs; the 64K-row default cap plus upstream backpressure is mandatory, not a tuning nice-to-have.
  • A pull-based exchange (downstream pulls from per-partition buffers) serializes at the boundary — exactly the 2010s-era mistake P3/ADR-06 rejects; VOE's exchange pushes into queues, workers pop on their own schedule.

18.7 Performance Concerns

  • Cross-NUMA transfer cost (~150–300 ns/access, §4) is paid once per row at the exchange boundary; downstream operators then see NUMA-local data — this amortization is the entire performance argument for exchange existing at all.
  • Partition-count choice affects both parallelism (more partitions = more parallelism) and per-partition batch size (more partitions = smaller batches, risking falling below the L1-fit sweet spot of ADR-03); document the tradeoff explicitly.
  • Backpressure signaling has its own overhead if checked too frequently; check at morsel granularity, not per-row.

18.8 Edge Cases

  • num_partitions = 1: exchange degenerates to a no-op passthrough; must not introduce overhead disproportionate to that degenerate case.
  • Empty partition (zero rows routed to it): the downstream pipeline for that partition must still participate in the I11 barrier correctly — an empty partition still "finishes."
  • A partition key that is NULL for every row: all rows hash-route to the same partition (NULL's hash is well-defined, not an error) — documented as expected, not a bug.

18.9 Failure Analysis

  • What breaks: sustained backpressure indicating a downstream partition worker has stalled or died. Detection: partition-queue-depth metric pinned at the cap longer than a configurable timeout. Blast radius: the whole pipeline stalls (I11's barrier semantics mean a stuck partition blocks the pipeline's finish()). Containment: a per-partition timeout raises a diagnosable Error::ExchangePartitionStalled rather than an indefinite hang. Recovery: on-call runbook docs/runbooks/triage.md; the query is aborted and re-submitted (no mid-query partition-recovery mechanism in Phase 0–10 scope).

18.10 Operational Notes

  • Metrics: exchange_throughput_bytes_per_sec, exchange_partition_queue_depth, exchange_cross_numa_ratio.
  • docs/architecture/exchange.md documents the seam where a future network-backed exchange would attach (§30, §35).
  • Deployment note: partition count defaults to the total physical core count; operators may override via plan hints.

19.1 Objectives

  • Implement radix sort for fixed-width keys and comparison sort for variable-width keys; implement top-K via bounded min-heap (P11's Sort breaker).

19.2 Detailed Implementation Steps

  • Implement voe-ops::sort::radix — 8-bit-digit MSB-first radix sort for i32/i64/f32/ f64 keys, with sign-bit and IEEE-754-sign-bit fixups applied before/after the radix passes (documented separately for signed integers vs. floats).

19.6 Pitfalls

  • Sign bit on signed-integer radix sort: forgetting to flip it sorts -1 after 0.
  • IEEE-754 f64 sort: the bit pattern of negative floats is in reverse numeric order; convert via f64::to_bits() with sign-bit fixup, radix-sort, convert back.

19.7 Performance Concerns

  • Radix sort's 8 passes (one per byte of a 64-bit key) each touch the full dataset — memory- bandwidth bound (§4, §33), not compute bound; profile against the STREAM Triad ceiling, not a CPU profiler.
  • Range-partitioned parallel sort avoids a global merge step but requires accurate range- boundary sampling; poor sampling reintroduces skew (ties to §18.6's skew pitfalls).
  • Top-K's min-heap has poor cache locality for large k (heap nodes scattered); the O(N log k) win only pays off for k ≪ N.

19.8 Edge Cases

  • All-equal keys: radix sort must be stable (preserve input order for tied keys) when the plan requires a secondary sort key — verified explicitly.
  • k = 0 top-K: emits zero rows, not an error.

19.9 Failure Analysis

  • What breaks: a range-partitioned sort with a badly skewed sample producing one oversized partition. Detection: partition-size-variance metric. Blast radius: one worker becomes the long pole, elevating query latency; correctness is unaffected (sort output is still correct, just slower). Recovery: no automatic re-sampling in Phase 0–10 scope; documented as a stretch-goal adaptive-resampling refinement (§34 Hard Questions references this tradeoff).

20.6 Pitfalls

  • Spill format must be stable across versions — Arrow IPC (ADR-02) is the standard; never invent a private format a future version can't read.
  • Spill on out-of-disk → query failure; mitigation is the per-query spill quota (10× budget) plus a graceful Error::SpillQuotaExceeded, never an unbounded disk fill.
  • Partial-vs-final aggregate schema mismatch: the spilled partial output must carry enough state for the final merge (e.g. Avg's (sum, count), never a pre-divided value) — exactly §16.2's rule, now under spill pressure too.
  • Spilled partitions must be hash-consistent between build-side spill and probe-side read; a seed change between spill and probe is a correctness catastrophe (I6) — the exact failure §8.6 walks through.
  • Spill files must be cleaned up on cancellation, not just normal completion — the cleanup hook is registered with the query lifecycle, not with a "success" callback alone.

20.7 Performance Concerns

  • Spill write/read throughput (M12/M13) is bound by local SSD bandwidth, not CPU — profile with an I/O profiler, not a CPU profiler, when investigating a slow spill.
  • Grace-hash-join's partition-count choice trades I/O amplification (more partitions = more, smaller files) against per-partition memory fit — the formula is derived in §33, not picked empirically per deployment.
  • Spilling under concurrent-query pressure (multiple queries spilling simultaneously) can saturate disk bandwidth across queries — the per-query FD budget (§4) bounds file count, but total disk bandwidth is not currently arbitrated across queries (documented limitation, §30).

20.8 Edge Cases

  • Spill triggered on the very first batch (pathologically small memory budget): must not infinite-loop attempting to "spill an empty table" — the budget check and spill trigger are idempotent no-ops on an empty state.
  • A spilled partition that, after re-partitioning, is still larger than memory (extreme skew): the grace-hash-join pattern recurses one level (re-partition the oversized partition again) up to a bounded recursion depth, beyond which the query aborts with Error::UnpartitionableSkew.
  • Concurrent spill and query cancellation: the cleanup hook must not race with an in-flight SpillWriter::write_batch call — writer completion is awaited before file deletion.

20.9 Failure Analysis

  • What breaks: crash mid-spill (process killed while a SpillWriter has a partial file). Detection: on restart, no in-flight query state exists to resume (VOE is stateless between queries, §4) — the partial spill file is simply orphaned. Blast radius: disk-space leak only; no correctness impact since the query that owned it is gone. Recovery: a startup sweep (voe-cli --cleanup-orphaned-spills) removes files older than the max plausible query duration. PhaseDeferred("§20.9"): full crash-mid-spill query resumption (as opposed to cleanup) is out of Phase 0–10 scope — VOE re-runs the whole query rather than resuming from a partial spill.

  • Metrics: operator_memory_bytes, spill_bytes_written, spill_bytes_read, spill_files_open.
  • Runbook: docs/runbooks/spill-debug.md.
  • Deployment note: the spill directory should be fast local disk (NVMe preferred); the FD-budget (§4) implication for the deployment's ulimit configuration is documented alongside it.

21.6 Pitfalls

  • Cranelift's compile time (~10 ms/kernel) exceeds execution time for small queries (< 1M rows total); the hot-path threshold is the break-even — do not lower it without re-measuring.
  • Cranelift's ISA support lags LLVM; AVX-512 emission is limited, falling back to AVX2 in compiled kernels even though the interpreted path uses AVX-512 via pulp — document the asymmetry so a performance-regression report doesn't mistake it for a bug.
  • Compiled-kernel cache poisoning: a malicious or corrupted expression could compile to incorrect code; every cache entry carries an HMAC signature, verified on every hit (T5, §23).
  • The trampoline's unsafe is the second and last in the codebase; every kernel-signature change requires updating the trampoline in lockstep — missing this produces undefined behavior, not a compile error.
  • Recursive expressions (> ~50 nodes) can blow cranelift's compiler recursion limit; VOE rejects overly deep trees rather than crashing (documented boundary condition).

21.7 Performance Concerns

  • Compile-time amortization (§4: ≤ 10 ms/kernel, break-even at 1M rows) is the central tradeoff of the entire phase — every acceptance number (M14) is downstream of getting this threshold right.
  • Cache hit rate (≥ 90% target) depends on TPC-H's query set reusing the same expression shapes; a workload with highly diverse ad-hoc expressions would see a much lower hit rate and a correspondingly worse cost/benefit ratio — a workload-dependent characteristic, not a universal guarantee.
  • The trampoline call itself has fixed overhead (pointer indirection, argument marshaling) that must stay small relative to the compiled kernel's per-row work, or the JIT's win evaporates on narrow kernels.

21.8 Edge Cases

  • An expression that never crosses the 1M-row threshold within a single query's lifetime stays interpreted forever, by design (P6) — verify no forced compilation ever occurs on cold expressions.
  • Compilation failure (e.g. an unsupported expression shape) falls back to the interpreted path silently from the caller's perspective, logged as a cache miss with a compile_failed reason code.
  • Two structurally identical expressions with different Column indices must hash to different cache keys (input types alone are insufficient; the full expression tree, including column indices, is part of the cache key).

21.9 Failure Analysis

  • What breaks: a cranelift-emitted kernel that produces wrong output only on certain inputs (an emission bug, not a cache-poisoning attack). Detection: I12's cross-validation (100K random inputs) catches most cases pre-release in CI; in production, kernel_xcheck_mismatch telemetry (I12) fires if periodic background verification is enabled (documented operational option, §25). Blast radius: every query using that expression shape — potentially wide but bounded to compiled-mode users. Recovery: VOE_DISABLE_CODEGEN=1 escape hatch forces interpreted-only mode process-wide while the emission bug is fixed.

21.10 Operational Notes

  • Metrics: codegen_cache_hit_rate, codegen_compile_latency_ms, codegen_cache_size.
  • VOE_DISABLE_CODEGEN environment variable is the operational escape hatch (mirrors VOE_FORCE_SCALAR from §14).
  • docs/architecture/compiled-kernels.md documents the cache-key scheme and the HMAC-signing mechanism for on-call/security reference.

22.2 Detailed Implementation Steps

  • Implement voe-ops::scan::parquet::ParquetScan — accepts Vec<Expression> pushdown predicates; checks Parquet page-level statistics first (skip non-matching pages), then re-evaluates at the row level since statistics are conservative, never sufficient alone (ADR-12, P12).
  • Implement voe-ops::materialize::MaterializeOp — consumes (row_id, key_cols) batches, fetches remaining columns by row_id, assembles the full-schema RecordBatch (P4, ADR-11; completes §17.2's row-id-pair contract).
  • Implement dictionary pass-through in voe-kernels::filter, voe-ops::project, hash-agg partial-build, and hash-join probe — each operates on DictionaryArray::keys directly, treating values as a shared constant (P5, I9).
  • Wire the pushdown contract: the executor accepts predicates it can evaluate, ignores ones it cannot — safe since an un-pushed predicate is always re-evaluated above the scan by Filter.
  • Build the full conformance/tpch/queries/ set (Q1–Q22) and conformance/tpcds/queries/ subset (~30 queries, ADR-18); build conformance/duckdb_diff/ and conformance/datafusion_diff/ differential runners, numeric tolerance 1e-6 (ADR-19).
  • Wire nullability-aware pushdown: WHERE col > 5 pushed to a scan must reject NULL rows (three-valued logic), never silently converting to a two-valued predicate (P13 extended).

22.3 Deliverable

Full TPC-H Q1–Q22 at SF=1/10/100 and the TPC-DS subset at SF=100 pass; cross-validation against DuckDB and DataFusion passes; conformance/runner emits a complete conformance.report.json.

22.4 Acceptance Criteria

  • TPC-H Q1–Q22 bit-identical (1e-6 tolerance for AVG) at SF=1, SF=10, SF=100 (ADR-17).
  • TPC-DS subset (~30 queries) at SF=100 bit-identical to reference (ADR-18). PhaseDeferred("§27"): the full 99-query TPC-DS suite is out of scope.
  • Cross-validation vs. DuckDB and DataFusion: 0 disagreements outside 1e-6 across the full TPC-H suite (ADR-19, M18).
  • TPC-H Q1 with dictionary-encoded l_returnflag runs ≥ 2× faster than the equivalent raw- Utf8 plan.
  • TPC-H Q3 with predicate pushdown reads ≤ 30% of Parquet pages compared to the no-pushdown baseline.
  • TPC-H Q9 with late materialization runs ≥ 1.5× faster than an eager-materialization variant.

22.6 Pitfalls

  • Predicate pushdown losing nullability: WHERE col > 5 must also reject col IS NULL; a pushdown rule dropping the null check produces silent wrong results (P13, I3 extended here).
  • Dictionary vectors decoded too early: a filter operator lacking a dictionary specialization loses P5's win; the registry must cover every pass-through operator, or the planner inserts an explicit Decode (I9).
  • Late-mat row-id tracking across join boundaries: the join emits (probe_row_id, build_row_id) pairs; the materializer must fetch by both, or it fetches the wrong row (extends §17.2).
  • UDFs are categorically forbidden from being pushed into scans — PhaseDeferred("§22.8")'s boundary exists partly to make this moot.
  • Parquet page statistics are conservative; the row-level re-evaluation is mandatory, never skippable "for speed."

22.7 Performance Concerns

  • Late materialization's win is proportional to (1 − selectivity) × (unused column width) — on a low-selectivity query over a narrow table, row-id indirection can exceed the savings (ADR-11's rejected-alternative regime, §9).
  • Dictionary pass-through's win is proportional to string width times cardinality-reduction ratio — a high-cardinality "dictionary" gains nothing and adds overhead (an interacting assumption, not directly controlled by VOE).
  • Full-suite cross-validation (ADR-19) is a CI cost center; SF=1 (not SF=100) is the throughput/coverage tradeoff (§27).

22.8 Edge Cases

  • A predicate referencing a column absent from the Parquet page statistics (e.g. added via schema evolution) — pushdown degrades to row-level-only evaluation, never an error.
  • A dictionary array whose values array is itself empty (all keys point past the end) — malformed input, rejected by RecordBatch::try_new (I4) before reaching any operator.
  • PhaseDeferred("§22.8"): a plan referencing a user-defined function is rejected by the planner before reaching VOE — the Expression enum (§11.6) has no UDF variant, making the rejection structural, not a runtime check.

22.9 Failure Analysis

  • What breaks: a cross-validation disagreement between VOE and DuckDB/DataFusion. Detection: cross.duckdb/cross.datafusion conformance buckets fail in CI (release-blocking, §28). Blast radius: contained to the introducing merge (cross-validation runs every PR touching an operator/kernel, §27). Recovery: bisect via conformance/runner --query <id> --diff; fix and re-run the full suite (never accept a result outside the documented 1e-6 epsilon).

26. Compatibility & Versioning

  • Wire compatibility: RecordBatch's Arrow-IPC serialization (ADR-02) targets the Arrow columnar format spec version pinned in docs/adr/ADR-02.md; VOE tracks Arrow spec releases deliberately, not automatically, to avoid an uncontrolled compatibility break.
  • Storage compatibility: spill files are ephemeral and process-version-scoped — a spill file written by version N is never read by version N+1 (a version mismatch on SpillFile metadata is treated as T7/I6's seed-mismatch class and rejected). Deliberate simplicity tradeoff: no spill-format migration to build or maintain.
  • Schema evolution: Schema/Field additions (new nullable columns) are backward- compatible for a Scan reading an older file; renaming or type-changing a Field is a breaking change requiring plan regeneration by the caller (out of VOE's scope, §1).
  • API stability: the Operator trait (§11.3) and the Expression/PhysicalPlan grammars (§8) are the stable public surface; adding a new Expression variant or PhysicalPlan node is additive; removing or changing an existing variant's fields is a major-version bump.
  • SemVer policy: voe-* crates follow SemVer; a breaking change to any pub type in §11 requires a major-version bump across the whole workspace (single-version policy — the crates release together).
  • Migration: none required between minor/patch versions (no persistent format); major versions document a plan-migration guide if the Expression/PhysicalPlan grammar changed.
  • Rolling-upgrade guarantees: VOE is stateless between queries and holds no durable format, so a rolling upgrade across a fleet requires no coordination — each instance serves whichever plan format its own version understands; the caller/planner must not send a newer-than- supported plan to an older instance. An explicit plan_format_version field is a natural stretch-goal, deferred until multi-version fleets are common (§30).

27. Testing & Verification Strategy

  • Unit tests: per-crate, colocated with source (#[cfg(test)]); cover every kernel's scalar path, every type's construction/validation logic (I4, I10).
  • Integration tests: cross-crate, in conformance/ and top-level tests/; the Phase-0 hello_vectorized.rs (§12.5) is the first.
  • Property tests: hash-agg/hash-join vs. HashMap reference (§16.4), radix-sort vs. slice::sort (§19.4), morsel-size invariance (§15.4) — one property test per §7 invariant where a generative check is tractable.
  • Differential tests: conformance/duckdb_diff/, conformance/datafusion_diff/ — TPC-H Q1–Q22 against two independent engines (ADR-19); the strongest evidence class in the suite, since it shares none of VOE's own assumptions.
  • Fuzzing: voe-fuzz's seven cargo-fuzz targets (§10.6) — hash_table, hash_join, hash_agg, filter_kernel, arith_kernel, spill_roundtrip, pipeline; a 24-hour canary gates every release (fuzz.canary_24h), a 30-day run gates Sealed (ADR-22, M17).
  • Chaos/fault injection: worker-thread panic injection (FM1), forced-spill-on-first-batch (§20.8), simulated disk-full during spill (T10/FM4).
  • Deterministic replay: voe-morsel::sim (§7 methodology) replays any recorded plan with fixed seeding and morsel ordering, producing a byte-identical trace — the primary tool for bisecting FM5/FM12.
  • Soak: 30-day continuous TPC-H loop with random seed perturbation (ADR-22); zero panics, zero result drift beyond the I13 epsilon is the Sealed gate.
  • Conformance buckets (full catalogue, conformance/report_schema.json): tpch.q1_to_q22_sf{1,10,100}, tpcds.subset_sf100, kernel.xcheck_{arith,cmp,filter}, cross.{duckdb,datafusion}, hash.{linear_probe,skew_handling}, spill.{hash_agg_roundtrip,hash_join_roundtrip}, numa.{affinity,stress_imbalance}, fuzz.canary_{24h,30d}, codegen.{xcheck,cache_hit_rate}. 30. Scalability Analysis

  • Constant regardless of scale: per-morsel dispatch overhead (O(1) amortized per row within a morsel, ADR-04); per-kernel-call SIMD dispatch cost (O(1), cached at first use, P7); the two-unsafe-surface security posture (P15).
  • Grows with scale: memory footprint with GROUP BY/join cardinality (O(distinct keys), bounded by spill, I5/P10); spill I/O with dataset-size-over-memory-budget ratio (O(dataset − budget), §20); cross-NUMA transfer volume with partition count and skew (§18); compile-cache size with distinct hot expression shapes (O(distinct expressions), §21, bounded only by process memory since the cache has no eviction policy — a documented current limitation, §34).
  • Named bottlenecks, in order: (1) memory bandwidth (§4, §33 — the hard ceiling on scan/ filter/arithmetic throughput, before anything else matters); (2) hash-table cache-miss rate under skew (§16.7, mitigated but not eliminated by the chained fallback); (3) spill I/O bandwidth once the dataset exceeds the memory budget (§20.7); (4) cross-NUMA transfer cost when exchange/join partitioning is imperfect (§18.7); (5) single-process FD/thread limits bounding maximum concurrent queries (§4).
  • Horizontal scaling: not coordinated by VOE (a non-goal, §1); an external scheduler can run multiple VOE processes across hosts and route queries, but no single query spans multiple VOE processes — the ceiling the Exchange operator's seam (ADR-15) exists to eventually break.
  • Vertical scaling: near-linear up to the NUMA-local core count (M11's 90% target); scaling across NUMA nodes on a single host is morsel-driven work-stealing's job (§15) and degrades gracefully, not catastrophically, under skew.
  • Sharding/partitioning: within a single query, hash- and range-partitioning (§18/§19) are the only mechanisms; there is no persistent sharding of stored data (VOE is not a storage engine, §1).
  • Coordination overhead: zero network coordination in Phase 0–10 scope (§4's 0 RTT); the only coordination is intra-process (morsel queues, pipeline barriers) — exactly what bounds VOE to single-node and is the tradeoff named in §4's "one defining property."
  • Practical ceiling: a single host's memory bandwidth and RAM capacity (plus spill-extended effective capacity bounded by local disk bandwidth) — roughly the SF=100 (~100 GB) class on a 64 GiB-RAM, NVMe-equipped host per §4's assumptions.
  • Levers beyond the ceiling: (1) the Exchange operator's seam (ADR-15) generalizing to a network-backed exchange for true horizontal scale (PhaseDeferred, §36); (2) GPU kernels for bandwidth-bound operators where device memory bandwidth exceeds host DRAM bandwidth (PhaseDeferred, §35); (3) a compile-cache eviction policy to bound §21's unbounded cache growth under very diverse ad-hoc workloads.

31. Mental Models & First Principles

  1. MM1 — A record batch is a mini-column-store, not a list of rows. Insight: think in columns from the type system up. Predicts: any operator whose inner loop needs a "current row" concept is architecturally wrong. Bug class without it: hidden row- materialization creeping into filter/project (P1's violation). Applies in §11.2, §14.
  2. MM2 — The pipeline breaker is the only synchronization point that matters. Insight: everything between two breakers is embarrassingly parallel. Predicts: the breaker set (Sort, HashAggFinal, HashJoinBuild, Exchange) is a complete list of "wait here" points; nothing else needs a barrier. Bug class: an operator that silently buffers without declaring itself a breaker corrupts I11. Applies in §8.3, §15.2.
  3. MM3 — A hash table's throughput is a cache-miss budget, not an instruction-count budget. Insight: probe throughput is bound by cache-line fetches, not ALU ops. Predicts: a "faster" hash function that increases branch mispredicts but removes one ALU op is a net loss. Bug class: micro-optimizing kernel arithmetic while ignoring bucket layout. Applies in §16.2, §33.
  4. MM4 — Vectorization and compilation solve different problems. Insight: vectorization amortizes dispatch overhead across rows; compilation amortizes interpretation overhead across a whole query. Predicts: short queries favor vectorization (low fixed cost); long, repeated queries favor compilation. Bug class: compiling every expression regardless of row count (§21.6). Applies in ADR-16, §21, §35.
  5. MM5 — NUMA is a second memory hierarchy layer above cache. Insight: treat "remote NUMA node" the way you'd treat "L3 cache miss" — one level further out. Predicts: the same locality principles motivating cache-line alignment motivate morsel-to-NUMA-node pinning. Bug class: parallelizing without NUMA awareness, expecting linear scaling and getting a plateau at the socket boundary. Applies in §4, §15.
  6. MM6 — A selection vector is a promise you can break cheaply. Insight: filtering by carrying indices/a bitmap instead of copying values defers materialization cost until it's actually needed. Predicts: late materialization always wins when the promise is never called in (filtered-out rows are never touched again). Bug class: an operator that "cashes in" the promise too early (eager decode/materialize) loses the win silently. Applies in P4, P5, §17, §22.
  7. MM7 — Every unsafe block is a proof obligation, not a convenience. Insight: P15's two unsafe surfaces exist because a proof (alignment, bounds, ISA availability) was discharged once, centrally, instead of ad hoc. Predicts: any third unsafe site is either redundant (the proof already exists elsewhere) or unaudited (a latent bug). Bug class: "just add unsafe to satisfy the borrow checker" without a corresponding invariant. Applies in §6 P15, §14.6, §21.6.
  8. MM8 — Spill is memory management's escape valve, not a fallback path. Insight: design the hot path assuming spill will happen on real workloads (SF=100+), not as a rare emergency. Predicts: a spill implementation bolted on after the fact (rather than co-designed with the hash table's build/probe interface) will leak the abstraction. Bug class: a hash-table API with no notion of "drain to an external writer" until spill is retrofitted. Applies in P10, §16, §20.

DuckDB made the defining decision to be an embeddable, zero-dependency, single-file analytical database — its vectorized executor (whose vector-size choice VOE's ADR-03 deliberately mirrors) optimizes for the "SQLite for analytics" niche: instant startup, no server process, trivial deployment. That niche wins whenever the workload is exploratory, ad-hoc analysis on a single machine without a standing service — close to what VOE's own voe-cli plays a narrower version of.

ClickHouse chose a large default Block size (65536 rows) and its own storage engine (MergeTree) co-designed with execution, trading L1-cache residency (VOE's ADR-03 rationale) for lower per-batch dispatch overhead and tight storage/execution integration. That tradeoff wins on ClickHouse's target workload: massive-scale, append-heavy, real-time analytics where storage/execution co-design and raw insert throughput matter more than any single query's L1 residency (§33 quantifies the residency VOE gives up by not making ClickHouse's choice).

Velox made the opposite deployment choice from VOE — it is deliberately not a standalone system but a library embedded identically inside Presto, Spark, and other engines at Meta, prioritizing a stable, shared Vector/expression-evaluation ABI over any single engine's end-to-end performance. That wins in an organization running many independent SQL engines that all want the same execution kernel — a different problem than VOE's single-audience teaching scope (§1).

HyPer chose full query compilation (Neumann 2011) over vectorization entirely — compiling each query to native machine code via LLVM, eliminating interpretation overhead completely at the cost of compile latency. That wins on workloads dominated by many repeated executions of the same complex query shape, where compile cost amortizes over enough executions to beat vectorization's per-batch dispatch overhead — exactly the regime ADR-16's rejected-alternative column names, and the regime §35's first alternative architecture explores in full.

33. Back-of-Envelope Capacity Model

  1. L1 working-set fit (ADR-03's justification). A binary kernel (2 inputs + 1 output) over i32 at the default 2048-row vector: 3 × 2048 rows × 4 B = 24,576 B ≈ 24 KiB, fitting within the 32 KiB L1 (§4) with headroom for validity bitmaps and register spill.
  2. ClickHouse's 65536-row Block by the same formula. 3 × 65536 × 4 B ≈ 768 KiB — exceeds both L1 (32 KiB) and most of L2 (1 MiB, §4), confirming ClickHouse deliberately trades cache residency for lower per-batch dispatch overhead (§32).
  3. Morsel dispatch-overhead ceiling. At a ~200 ns per-morsel dispatch cost (queue pop + push
    • branch) and 100,000 rows/morsel (ADR-04): 100,000 rows / 200 ns ≈ 5 × 10¹¹ rows/s ceiling from dispatch alone — roughly 500× above the ~10⁹ rows/s operator targets (M8), confirming morsel size is not the throughput bottleneck.
  4. Memory-bandwidth scan ceiling. At 20 GB/s sustained per NUMA node (§4) over an i64 column (8 B/value): 20 × 10⁹ / 8 ≈ 2.5 × 10⁹ rows/s per node — leaves ≈ 2.5× headroom over the M8 target (≥ 1B rows/s scan + agg) for the additional arithmetic passes over the same bytes.
  5. SIMD lane-width speedup ceiling. AVX2 (256-bit) over i32 (32-bit): 256 / 32 = 8 lanes → theoretical 8× speedup. M4's ≥ 4× target captures roughly 4/8 = 50% vectorization efficiency, the realistic gap from bounds checks, tail loops, and load/store bubbles (§14.7).
  6. TPC-H Q1 hash-table footprint. Q1's GROUP BY (l_returnflag, l_linestatus) has at most 4 distinct groups at any scale factor — hash-table memory is O(1), a few KB regardless of SF, contrasted with #7 below.
  7. A high-cardinality group-by's footprint. GROUP BY l_orderkey at SF=1 (≈ 1.5M orders): (1.5 × 10⁶ / 0.7 load factor) × 64 B/bucket ÷ 4 keys/bucket ≈ 137 MB — comfortably within the 4 GiB default budget (§4) without spilling.
  8. Hash-join build-side footprint at SF=100. orders as the build side (≈ 150M rows, SF × 1.5M): (150 × 10⁶ / 0.7) × 16 B/row (amortized bucket share) ≈ 3.4 GB — approaches the 4 GiB default per-query budget (§4), explaining why SF=100 benchmarks (M9/M10) are exactly the regime that exercises spill (§20) in practice, not a corner case.
  9. Spill partition-count sizing (the formula §20.7 promised). To keep each grace-hash sub-partition within a 256 MB target, given #8's 3.4 GB build side: ceil(3.4 GB / 256 MB) = 14, rounded up to the next power of two → 16 partitions.
  10. FD-budget validation. 16 partitions (#9) × up to 4 concurrently spilling operators/query (§4's FD assumption) = 64 open files for one query — the stated ≤ 256 FD budget/query (§4) covers up to 4 such joins spilling simultaneously within one plan, validating that number against a realistic worst case rather than an arbitrary pick.
  11. Cross-NUMA steal overhead. At a ~200 ns cross-NUMA latency delta (§4) and a 100,000-row morsel taking ≈ 100 µs to process locally (from #4's per-node throughput), an occasional stolen morsel processed with some fraction of remote cache misses adds only a low single-digit percentage to that morsel's cost — why I8's 90%-local threshold (not 99%) is an engineered tradeoff, not an arbitrary number.
  12. Worst-case spill disk provisioning. Storage amplification ≤ 1.3× (§4) applied to a ~100 GB SF=100 dataset gives ≈ 130 GB per full spill; combined with the 10× spill quota (§20.2), disk provisioning guidance for a production deployment should budget toward the upper end of that range per concurrently spilling query, not the typical (unspilled) case.

  1. Why does VOE default to a 2048-row vector while ClickHouse defaults to 65536? What single number from §4 explains the gap, and where is it derived? (§4, §33)
  2. Trace what happens, invariant by invariant, when a HashAggBuild operator crosses its 80% memory-budget threshold mid-morsel — which invariants fire, in what order, and which phase implements each step? (§7 I5/I6/I7, §16, §20)
  3. Late materialization's win is not universal — name the query shape where it loses, and the ADR that names the regime. (§6 P4, §9 ADR-11, §22.7)
  4. A cross-NUMA hash-table access is ~3× slower per access than local — using §4's numbers, roughly how many cache misses per probe does this tolerate before violating I8's 90% threshold's intent, not just its letter? (§4, §7 I8, §33)
  5. Why does the design choose cranelift over LLVM for the compiled sidecar, and under what workload characteristic would that choice reverse? (§9 ADR-16, §21, §35)
  6. What would break, invariant-first, if the hash seed were fixed instead of randomized per query — trace the exploit path an adversary would use. (§7 I6, §23 T6, §16.6)
  7. Explain why Kleene three-valued logic is enforced identically in both the interpreted kernel path and the predicate-pushdown path, and name the invariant plus the phase that would catch a regression in either. (§6 P13, §7 I3, §14, §22.6)
  8. TPC-H Q9 exercises the Exchange operator "heavily" — using the pipeline-breaker model, explain why Q9 needs more pipelines than Q1, and name the operator causing each additional cut. (§8.3, §17, §18)
  9. Why is the compiled-kernel cache never evicted, and which two sections both flag this as a documented limitation rather than a bug? (§21.8, §30)
  10. A dictionary-encoded column improves TPC-H Q1 by ≥ 2× — using P5's principle and I9's invariant, explain which operators in Q1's plan benefit and why the final Sort needs no dictionary specialization at all. (§6 P5, §7 I9, §16, §19, §22)
  11. Contrast VOE's "morsel-driven, not exchange-driven" choice (ADR-06) with a genuinely distributed engine where exchange-everywhere is unavoidable — why does the rejected alternative "win" there but not here? (§9 ADR-06, §30, §35)
  12. Using the Capacity Model's grace-hash-join partition-count formula, compute the number of partitions VOE would choose for a 6.8 GB build side, and identify the FD-budget consequence from §4. (§33, §4)
  13. Why does spilling a partial aggregate for AVG store (sum, count) rather than a single averaged value — trace the correctness bug this avoids, citing the phase where it's implemented twice. (§16.2, §20.4)
  14. The design claims zero network RTT (§4) yet also claims an Exchange operator "seam" for future distributed execution (§1, §18) — reconcile these: what would have to change, and what stays identical? (§4, §18, §30)
  15. Why are VOE's two permitted unsafe blocks considered "audited surfaces" rather than technical debt — what would have to be true of a third unsafe site for it to be equally acceptable? (§6 P15, §23 T4/T5)
  16. A reader proposes replacing the vectorized interpreter entirely with HyPer-style full compilation. Using the Comparative Architecture Table and the Capacity Model, argue for or against this for VOE's specific target workload, not workloads in general. (§32, §33, §35)
  17. Why does the morsel size (100,000 rows) differ by two orders of magnitude from the vector size (2048 rows) — what two different hardware realities is each number tuned against? (§4, §33)
  18. If VOE's default per-query memory budget doubled from 4 GiB to 8 GiB, name the two M-table targets most likely to improve and the one invariant whose telemetry (not correctness) would most directly reflect the change. (§4, §29, §7 I7)

35. Alternative Architectures (Roads Not Taken)

A1 — Fully compiled per-query execution (HyPer-style).

PhysicalPlan → whole-query LLVM IR codegen (one fn) → native machine code
                              │
                              ▼
        single tight loop, tuple-in-register, zero inter-operator
        batch materialization

Regime where it wins: few, complex, frequently repeated query shapes where compile cost amortizes (a fixed dashboard re-run thousands of times/day). Real system: HyPer (Neumann 2011), commercially embodied in Tableau's HyPer engine. Why rejected: VOE's target workload (ad-hoc TPC-H/TPC-DS-style analytical queries, one-shot or infrequently repeated) does not amortize LLVM's compile latency (Sompolski-Zukowski-Boncz 2011 measured this crossover directly); vectorization's low fixed cost per query wins at VOE's target scale (ADR-16).

A2 — Classic Volcano tuple-at-a-time iterator model.

Scan.next() → Filter.next() → Project.next() → Agg.next() → caller
   (each next() call returns exactly one tuple; virtual-dispatch
    overhead paid once per row, per operator)

Regime where it wins: extremely simple, single-row point-lookup queries where batching/ vectorization's fixed overhead per query exceeds any savings, or reference implementations valuing simplicity over throughput. Real system: the original Volcano/System R iterator model (Graefe 1993), and SQLite's VDBE today. Why rejected: analytical workloads scan/filter/aggregate over 10⁶–10⁹ rows; per-row virtual-dispatch overhead (Boncz-Zukowski-Nes 2005, section 2) dominates total runtime — exactly the problem vectorization exists to solve (P1, P2).

A3 — Row-major storage with row-at-a-time execution.

[row0: a,b,c][row1: a,b,c][row2: a,b,c]...  (row-major layout)
                    │
                    ▼
      operator reads/projects/filters one whole row at a time

Regime where it wins: OLTP-style point lookups/updates touching few rows but needing every column of each touched row; write-heavy transactional workloads. Real system: PostgreSQL's heap storage plus row executor, MySQL/InnoDB. Why rejected: OLAP workloads touch few columns of many rows — the inverse access pattern — and Abadi et al. 2008's quantified column-store advantage is exactly the argument against row-store for VOE's TPC-H/TPC-DS target (§1's non-goals explicitly exclude OLTP/transactional support).

A4 — GPU-resident columnar execution.

Host: PhysicalPlan → column upload (PCIe/NVLink) → GPU kernel graph
                                                        │
                                                        ▼
                                device-resident columnar buffers,
                                one kernel per operator (CUDA graph)

Regime where it wins: extremely wide, few-operator aggregations over already device-resident data (a GPU-native OLAP service co-located with a device-resident columnar store), where device memory bandwidth (TB/s class) dwarfs host DRAM bandwidth (§4's ~20 GB/s/node) by 10–50×. Real precedent: RAPIDS cuDF-style GPU-accelerated columnar analytics engines. Why rejected: PCIe transfer cost for data not already device-resident, plus the multi-month engineering cost of a second memory-hierarchy model, exceed VOE's Phase 0–10 scope (§1 non-goal; ADR-24, PhaseDeferred("§35"), §36).

37. Glossary

  • AggState — VOE's per-group running aggregate state (sums, counts, mins, maxes).
  • Arrow IPC — Apache Arrow's binary interprocess/file serialization format for record batches.
  • Batch (Vector) — a RecordBatch of bounded row count (default 2048) flowing through a pipeline; the unit of vectorized processing.
  • Bitmap — a packed, LSB-first-per-byte validity bit array marking null/non-null per row.
  • BMI2 / PEXT — an x86 instruction-set extension accelerating bit-extraction in the filter kernel.
  • Breaker (Pipeline Breaker) — an operator (Sort, HashAggFinal, HashJoinBuild, Exchange) that must fully drain its upstream before its downstream may start.
  • Broadcast join — a hash-join build strategy where one shared table serves every probe worker (small build sides).
  • Bucket — a 64-byte-aligned slot in a LinearProbeTable holding up to 4 key/value pairs.
  • Cache-line ping-pong — repeated invalidation of a shared cache line by concurrent writers on different cores, causing severe slowdown.
  • Conformance bucket — a named test group (e.g. tpch.q1_to_q22_sf1) in the conformance runner's report schema.
  • Cranelift — the JIT code generator VOE uses to compile hot expressions (voe-codegen).
  • Dictionary encoding — representing a column as small integer keys plus a shared values array, exploited by pass-through operators.
  • Exchange — the operator that hash- or range-repartitions a stream of batches across NUMA-pinned queues.
  • FD (file descriptor) budget — the per-query ceiling on simultaneously open spill files.
  • Grace hash join — the spill pattern that partitions both join sides by hash so each partition fits in memory.
  • Kleene logic — three-valued (TRUE/FALSE/NULL) boolean semantics used for SQL predicate evaluation.
  • Late materialization — carrying (row_id, key_cols) through operators, fetching remaining columns only at the sink.
  • Linear probing — a hash-table collision-resolution strategy that scans consecutive buckets on collision.
  • Load factor — occupied buckets divided by total capacity in a hash table; bounded at 0.7 (I5).
  • Materialize (operator) — the sink that fetches full rows from row-ids for late- materialized pipelines.
  • Morsel — a bounded slice (default 100,000 rows) of a pipeline's input dispatched as one unit of scheduling work.
  • NUMA (Non-Uniform Memory Access) — a multi-socket memory architecture where local-node access is faster than remote-node access.
  • Operator — a state machine consuming and producing RecordBatches via the Operator trait.
  • Partitioned join — a hash-join build strategy where the build side is hash-partitioned to match the probe side's partitioning.
  • Pipeline — a chain of streaming operators between two breakers, sharing worker-thread state.
  • Pipeline builder — the voe-plan component that cuts a PhysicalPlan into pipelines at breaker boundaries.
  • Predicate pushdown — evaluating a filter as early as possible, ideally inside the scan, using source-level statistics.
  • pulp dispatch — the runtime CPU-feature detection and specialization mechanism from the pulp crate.
  • Radix sort — a non-comparison sort processing fixed-width keys digit-by-digit.
  • RecordBatch — VOE's Arrow-compatible columnar batch type: a Schema plus a Vec<ArrayRef>.
  • Row-id — a row's positional identifier, carried through late-materialized pipelines.
  • SBOM (Software Bill of Materials) — a manifest of every dependency and its version bundled in a release.
  • Scale factor (SF) — the TPC-H/TPC-DS dataset-size multiplier (SF=1 ≈ 1 GB).
  • Sealed (release status) — VOE's highest release-maturity gate, requiring a 30-day fuzz/soak pass (ADR-22).
  • Seed (hash seed) — a per-query randomized value mixed into every hash computation to prevent collision attacks.
  • Selection vector — an alternate representation of "which rows survived a filter," as indices rather than a copied array.
  • Sidecar (cranelift sidecar) — the optional compiled-kernel subsystem that augments, but never replaces, the interpreted kernel path.
  • Skew — a non-uniform data distribution (e.g. one hash bucket or one NUMA partition receiving disproportionate load).
  • SLSA provenance — a supply-chain attestation standard describing how and from what source a build artifact was produced.
  • Spill — writing an operator's in-memory state to disk (as Arrow IPC) when it exceeds its memory budget.
  • Top-K — the ORDER BY ... LIMIT k pattern implemented via a bounded min-heap.
  • Trampoline — the unsafe boundary function that calls from safe Rust into JIT-compiled machine code.
  • Two-stage aggregation — the pattern of building thread-local partial hash tables, then merging them into one final table.
  • Validity bitmap — see Bitmap.
  • Vectorization — processing whole columns/batches per kernel call instead of one value at a time.
  • Volcano model — the classic tuple-at-a-time, pull-based (next()) query-execution iterator model.
  • Work stealing — a scheduling technique where an idle worker takes a morsel from a busier peer's queue.
  • XCheck (cross-check) — the conformance methodology comparing scalar, SIMD, and compiled kernel outputs for byte-identical equality.
