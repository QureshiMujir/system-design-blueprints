Decisions (§9) · 24 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+, edition 2021

Rejected

C++, Zig

When the rejected choice is right

C++ wins embedding inside an existing C++ host (e.g. as a DuckDB extension) with zero FFI cost

Why: Borrow checker removes a memory-corruption class from the two unsafe surfaces (P15)

ADR-02

Buffer layout

Chosen

arrow-rs-compatible zero-copy buffers

Rejected

Custom in-house format, Cap'n Proto/FlatBuffers wire format

When the rejected choice is right

Custom format wins when storage and execution are co-designed in one process with no external consumer (MonetDB's original BAT model)

Why: Ecosystem interop (Parquet, Flight, Polars) (P8)

ADR-03

Default vector size

Chosen

2048 rows

Rejected

1024 (Velox), 65536 (ClickHouse Block), adaptive

When the rejected choice is right

1024 wins on small-L1 CPUs or very wide rows (>16 columns); 65536 wins when dispatch overhead, not cache residency, dominates (shuffle-bound pipelines)

Why: L1-fit across typical row widths (§33)

ADR-04

Default morsel size

Chosen

100,000 rows

Rejected

1,000-row morsels, 1M-row morsels, single global queue

When the rejected choice is right

Smaller morsels win under heavy skew (fine-grained stealing); larger morsels win on uniform data with high per-row cost (UDF-heavy pipelines)

Why: Leis et al. 2014 dispatch-vs-load-balance sweet spot

ADR-05

Execution model

Chosen

Push-based (consume), pull (next) debug-only

Rejected

Pure Volcano pull-only

When the rejected choice is right

Pull wins for simple single-threaded embedded interpreters (e.g. SQLite's VDBE) with no parallelism to exploit

Why: Push composes with morsel scheduling; pull serializes at boundaries (P2)

ADR-06

Parallelism model

Chosen

Morsel-driven scheduler

Rejected

Exchange-operator-everywhere (classic parallel Volcano)

When the rejected choice is right

Exchange-everywhere wins in a genuinely distributed setting where every stage boundary is already a network shuffle (e.g. Presto/Trino)

Why: Leis et al. 2014 closes the NUMA-serialization case (P3)

ADR-07

Memory allocator / NUMA binding

Chosen

mimalloc + libnuma-based node binding (Linux); single-arena fallback elsewhere

Rejected

jemalloc, glibc malloc, no NUMA awareness

When the rejected choice is right

glibc default wins on small single-socket VMs/containers where NUMA topology is invisible and the dependency isn't worth it

Why: Per-thread arenas are an open port to NUMA-node pinning

ADR-08

Hash table layout

Chosen

Vectorized linear probing (Polychroniou et al. 2015), chained fallback for skew

Rejected

Pure chained hashing, cuckoo hashing, robin-hood hashing

When the rejected choice is right

Cuckoo hashing wins when worst-case O(1) lookup matters more than average throughput (real-time point-lookup service); chained wins under extreme adversarial skew

Why: SIMD-friendly gather/scatter probe pattern on uniform data (P9)

ADR-09

Spill threshold

Chosen

80% of operator memory budget

Rejected

50%, 95%, GC-pressure-adaptive

When the rejected choice is right

50% wins in latency-sensitive workloads that prefer early, smooth spills; 95% wins maximizing memory utilization when a late stall is acceptable

Why: Leaves headroom for burst allocations between per-morsel budget checks

ADR-10

Dictionary handling

Chosen

Pass-through in filter/project/partial-agg/hash-join-probe

Rejected

Eager decode at scan boundary

When the rejected choice is right

Eager decode wins when downstream has no dictionary specialization (e.g. a UDF operator)

Why: Matches ClickHouse/DuckDB low-cardinality string handling (P5)

ADR-11

Materialization strategy

Chosen

Late materialization by default, explicit Materialize operator

Rejected

Eager materialization at every operator

When the rejected choice is right

Eager wins on narrow tables (≤3 columns) or low-selectivity queries (>80% survive)

Why: Abadi et al. 2008, section 4; wins on selective, wide-table queries (P4)

ADR-12

Predicate pushdown

Chosen

Mandatory into scans (Parquet page stats + in-memory batch filter)

Rejected

Filter-only-after-scan

When the rejected choice is right

No-pushdown wins when the source has no exploitable statistics (unsorted, unindexed, sub-page-sized table)

Why: Direct IO reduction via page-skipping (P12)

ADR-13

SIMD dispatch mechanism

Chosen

pulp runtime dispatch (SSE4.2/AVX2/AVX-512/NEON)

Rejected

Handwritten std::arch intrinsics per ISA, nightly std::simd

When the rejected choice is right

Handwritten intrinsics win squeezing the last 5–10% on one pinned deployment SKU where portability has zero value

Why: Per-callsite monomorphized dispatch without scattered unsafe (P7)

ADR-14

SIMD ISA floor

Chosen

SSE4.2 (x86-64) / NEON (aarch64) floor, AVX2/AVX-512 opportunistic

Rejected

AVX2-as-floor, scalar-only floor

When the rejected choice is right

AVX2-as-floor wins on a fixed, modern fleet (single cloud provider's current instance family) where the SSE4.2 fallback is pure maintenance cost

Why: SSE4.2 ships on every server CPU since ~2008

ADR-15

Exchange scope

Chosen

Cross-NUMA repartition only; seam for future network exchange

Rejected

Building distributed exchange in Phase 0–10

When the rejected choice is right

Building it immediately wins when the product requirement is multi-node from day one (retrofitting later is riskier)

Why: Keeps Phase 0–10 single-node (§1 non-goal)

ADR-16

Compiled-kernel strategy

Chosen

Cranelift JIT sidecar for hot expressions only

Rejected

LLVM JIT, full compiled-pipeline (HyPer-style)

When the rejected choice is right

LLVM wins when compile time is amortized over hours-long batch queries; full compiled-pipeline wins on simple star-joins where per-tuple register code beats vectorized batch overhead (Kersten et al. 2018)

Why: Cranelift compiles ~10× faster than LLVM, matters for short queries (Sompolski-Zukowski-Boncz 2011)

Rejected

When the rejected choice is right

Ad-hoc queries win during early Phase-0 bring-up before a plan-builder can express all 22 queries

ADR-19

Cross-validation

Single-implementation trust wins when no comparable open-source engine exists for the workload

35. Alternative Architectures (Roads Not Taken)

A1 — Fully compiled per-query execution (HyPer-style).

PhysicalPlan → whole-query LLVM IR codegen (one fn) → native machine code
                              │
                              ▼
        single tight loop, tuple-in-register, zero inter-operator
        batch materialization

Regime where it wins: few, complex, frequently repeated query shapes where compile cost amortizes (a fixed dashboard re-run thousands of times/day). Real system: HyPer (Neumann 2011), commercially embodied in Tableau's HyPer engine. Why rejected: VOE's target workload (ad-hoc TPC-H/TPC-DS-style analytical queries, one-shot or infrequently repeated) does not amortize LLVM's compile latency (Sompolski-Zukowski-Boncz 2011 measured this crossover directly); vectorization's low fixed cost per query wins at VOE's target scale (ADR-16).

A2 — Classic Volcano tuple-at-a-time iterator model.

Scan.next() → Filter.next() → Project.next() → Agg.next() → caller
   (each next() call returns exactly one tuple; virtual-dispatch
    overhead paid once per row, per operator)

Regime where it wins: extremely simple, single-row point-lookup queries where batching/ vectorization's fixed overhead per query exceeds any savings, or reference implementations valuing simplicity over throughput. Real system: the original Volcano/System R iterator model (Graefe 1993), and SQLite's VDBE today. Why rejected: analytical workloads scan/filter/aggregate over 10⁶–10⁹ rows; per-row virtual-dispatch overhead (Boncz-Zukowski-Nes 2005, section 2) dominates total runtime — exactly the problem vectorization exists to solve (P1, P2).

A3 — Row-major storage with row-at-a-time execution.

[row0: a,b,c][row1: a,b,c][row2: a,b,c]...  (row-major layout)
                    │
                    ▼
      operator reads/projects/filters one whole row at a time

Regime where it wins: OLTP-style point lookups/updates touching few rows but needing every column of each touched row; write-heavy transactional workloads. Real system: PostgreSQL's heap storage plus row executor, MySQL/InnoDB. Why rejected: OLAP workloads touch few columns of many rows — the inverse access pattern — and Abadi et al. 2008's quantified column-store advantage is exactly the argument against row-store for VOE's TPC-H/TPC-DS target (§1's non-goals explicitly exclude OLTP/transactional support).

A4 — GPU-resident columnar execution.

Host: PhysicalPlan → column upload (PCIe/NVLink) → GPU kernel graph
                                                        │
                                                        ▼
                                device-resident columnar buffers,
                                one kernel per operator (CUDA graph)

Regime where it wins: extremely wide, few-operator aggregations over already device-resident data (a GPU-native OLAP service co-located with a device-resident columnar store), where device memory bandwidth (TB/s class) dwarfs host DRAM bandwidth (§4's ~20 GB/s/node) by 10–50×. Real precedent: RAPIDS cuDF-style GPU-accelerated columnar analytics engines. Why rejected: PCIe transfer cost for data not already device-resident, plus the multi-month engineering cost of a second memory-hierarchy model, exceed VOE's Phase 0–10 scope (§1 non-goal; ADR-24, PhaseDeferred("§35"), §36).
