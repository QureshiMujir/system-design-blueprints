In one paragraph

VOE is a single-machine, read-only engine that runs an analytical query someone else has already planned (§1, ADR-20). Instead of pushing one row at a time through each step, it pushes batches of column values (vectorized execution), spreads the work over all cores in chunks called morsels, and writes state to disk when memory runs short (§1, §3). It does no SQL parsing and no cost-based optimization (§1). It ships as an embedded library plus a voe command-line tool, for engineers building or extending an analytical engine (§1). Its defining trade: a fixed memory budget with mandatory spill buys unbounded input size, and zero network round trips buys zero horizontal scale (§4).

The problem, concretely

Take TPC-H Q1: group a filtered lineitem table by l_returnflag and l_linestatus and aggregate (§8.4). The oldest way to run it is the Volcano model: every operator exposes next(), and each call returns exactly one tuple, so a virtual-dispatch cost is paid once per row per operator (§35 A2). Analytical queries scan, filter and aggregate 10⁶ to 10⁹ rows, so that per-row overhead dominates total runtime (§35 A2). The move from Volcano to vectorized and then compiled engines opened a reproducible 2×–100× gap over row-store engines on analytical work (§2). That is the first pressure.

The second is parallelism. If every boundary between operators is an exchange that repartitions data, the exchanges serialize the machine; the design exists to avoid that (P3, ADR-06). The third is memory: a hash table over a high-cardinality GROUP BY can run out of memory unless a spill path exists (P9, P10). Without a spill path, the largest dataset it can handle is capped at available RAM (P10, §1 "what later phases unlock"). VOE's structure answers all three: batches for per-row cost (§3), morsels plus work-stealing for parallelism (§3, ADR-06), and a spill path for every unbounded operator (P10).

How it works, end to end

Follow Q1 through the boxes of §3. The diagram below is adapted from §3:

Caller: PhysicalPlan (schemas resolved, expressions bound)
  → Pipeline Builder (voe-plan): cuts the plan at Sort, HashAggFinal, HashJoinBuild, Exchange
  → Morsel Scheduler (voe-morsel): per-NUMA-node MorselQueue, work-stealing, one worker per core
  → Workers (NUMA node N, M): pop local or steal → consume → push downstream
  → Operator Layer (voe-ops): Scan · Filter · Project · HashAgg{Build,Final} · HashJoin{Build,Probe}
                              · Sort/TopK · Exchange{Out,In} · Materialize
  → Kernel Layer (voe-kernels, voe-codegen): pulp-dispatched SIMD; cranelift for hot expressions
  → Record Batch Layer (voe-core): Schema, ArrayRef columns, validity bitmaps, offsets, dictionaries
  → (budget exceeded, I7) Spill Subsystem (voe-spill): Arrow-IPC partition files, query-scoped
  1. The caller hands over a physical plan. VOE trusts it to be schema-valid and type-checked and does not re-verify SQL semantics (§3, T1).
  2. The pipeline builder (voe-plan) cuts the plan into pipelines at the pipeline breakers (Sort, HashAggFinal, HashJoinBuild, Exchange) and checks that adjacent operators agree on schema, rejecting the plan at build time otherwise (§3, I4, I11). A Column(7) filter over a 5-column child is rejected with Error::ColumnIndexOutOfBounds { index: 7, schema_width: 5 } before any worker starts (§8.5).
  3. For Q1 the builder emits two pipelines: Pipeline 0 is Scan(lineitem) → Filter(l_shipdate ≤ X) → Project(...) → HashAggBuild(sink), and Pipeline 1 is HashAggFinal(source) → Sort(l_returnflag, l_linestatus) → Result (§8.4). Pipeline 0 fans out across all workers; Pipeline 1 starts only after every worker's HashAggBuild::finish() has merged into the final table (§8.4, I11).
  4. The morsel scheduler (voe-morsel) keeps one MorselQueue per NUMA node. A worker pops from its local queue or steals from a peer's, and the worker pool is sized to the local physical cores (§3). Everything below this box runs inside worker threads; everything above is single-threaded plan construction (§3).
  5. The operators (voe-ops) are state machines over record batches. Each exposes consume(RecordBatch); a next() pull surface exists only for unit tests and the CLI (§3, ADR-05). An operator does not know whether its kernel is interpreted, SIMD-dispatched or compiled (§3, P6).
  6. The kernels (voe-kernels, and voe-codegen for compiled ones) do the per-value work over whole batches, carrying validity bitmaps so nulls propagate correctly (§3, P13).
  7. The record batch layer (voe-core) is Schema + Vec<ArrayRef>, byte-compatible with Arrow, which gives zero-copy ingest and emit (§3, P8, ADR-02).
  8. The spill subsystem (voe-spill) is the only component that writes durable storage, and only ephemeral, query-scoped Arrow IPC files, deleted on completion or cancellation (§3, FM6).

The core ideas

Batches of columns, sized to fit the L1 cache (§3, ADR-03, I1)

A record batch is a small column store, not a list of rows: the operator's loop runs over arrays, never rows (§3, MM1). Its default length is 2048 rows, bounded by invariant I1 as 1 ≤ num_rows ≤ MAX_VECTOR_SIZE (configurable up to 65536) (§4, §7 I1). The size is chosen so a kernel's working set stays in the first-level cache. The blueprint's arithmetic for a binary kernel (2 inputs, 1 output) over i32: 3 × 2048 rows × 4 B = 24,576 B ≈ 24 KiB, against a 32 KiB L1 (§33 item 1). By the same formula a 65536-row batch is 3 × 65536 × 4 B ≈ 768 KiB, past L1 and most of L2, which is the cache residency ClickHouse trades away for fewer dispatches (§33 item 2). A filter does not copy surviving values; it carries a selection vector (indices of the rows that survived), which defers the copying until a later operator needs the values (§37, MM6, I2).

Kernels: one scalar truth, SIMD on top, compilation for hot expressions (P7, P6, I12)

Every kernel has a scalar reference and a specialization that pulp picks once per process at first use according to the CPU's SIMD features (P7, ADR-13). The scalar version is the source of truth: identical input must give bit-identical output on every instruction set (I12). Null logic follows Kleene three-valued logic (I3). The blueprint's exact fixtures are NULL AND FALSE == FALSE, NULL OR TRUE == TRUE and NOT NULL == NULL (§14.4). Separately, a cranelift sidecar compiles an expression into machine code only after it has processed more than 1M interpreted rows, because compiling a cold expression costs more than running it (P6, §4). It is a sidecar, not the default; the interpreted path stays mandatory (§4, §21.1). The target gain for a compiled hot expression is at least 30% (M14, §29).

Pipelines and breakers: the only waiting points (§8.3, I11, MM2)

A pipeline is a chain of streaming operators between two breakers, sharing worker state (§37). It moves through four states: Building, Running (first morsel popped), Draining (source exhausted, finish() propagating) and Finished (sink's finish() returned Ok) (§8.3). The rule behind invariant I11: the upstream pipeline fully drains before any row crosses into the downstream one, enforced by a scheduler barrier (§8.3, I11). MM2 states the consequence: the breaker set is a complete list of the places that need to wait, and everything between two breakers is embarrassingly parallel (MM2). An operator that buffers silently without declaring itself a breaker breaks I11 (P11, MM2).

Morsels and NUMA: parallelism without a central bottleneck (ADR-04, ADR-06, I8)

A morsel is a bounded slice (default 100,000 rows) of a pipeline's input, handed to one worker as a unit of scheduling (§37, §4). A NUMA machine has memory that is faster for the cores attached to it; the blueprint's table gives about 150–300 ns for a cross-node access against about 80–120 ns local (§4). So each node has its own queue, workers prefer their local queue, and stealing is the fallback (§3). Invariant I8 requires at least 90% of morsel pops to be served by a worker on the morsel's origin node (§7 I8). The Phase 3 acceptance test for stealing: skew the data 90/10 across nodes; the idle node's workers steal within one scheduling quantum and total wall-clock stays within 20% of the balanced case (§15.4).

The hash table and two-stage aggregation (ADR-08, I5, P9)

Hash aggregation and hash join are the two largest memory consumers (P9). The table uses linear probing: on a collision, scan the next buckets. A bucket is a 64-byte-aligned slot holding up to 4 key/value pairs (§37, ADR-08). Invariant I5 caps the load factor at 0.7 without a resize or spill, to bound probe length (§7 I5). Aggregation is two-stage: threads build local partial tables, then merge them into one final table (§37). Avg keeps (sum, count) and divides only at finalize (§16.2). TPC-H Q1 groups by two columns and has at most 4 distinct groups at any scale factor, so its table is a few KB however large the input (§33 item 6).

Spill: a normal path, not an emergency (§8.6, I6, I7, MM8)

The blueprint's own failure-path trace for hash aggregation (§8.6):

  1. HashAggBuild::consume inserts a batch and the memory estimate crosses 80% of the budget (ADR-09).
  2. MemoryBudget::check returns Action::Spill (I7).
  3. The operator drains its LinearProbeTable into N SpillWriters, one per hash partition, using the query's seed (I6).
  4. Later batches are hashed straight to the matching spill partition, bypassing the in-memory table.
  5. At finish(), each spilled partition is re-read and merged one at a time, which bounds peak memory to one partition regardless of input size.

The seed matters: the build-side and probe-side partitions must agree, so the seed is stored in the SpillFile metadata and asserted on read (I6). MM8 says to design the hot path assuming spill will happen at SF=100 and above, and warns that a bolted-on spill leaks the hash table's abstraction (MM8).

The trade-offs — where engineers disagree

Vector size: 2048 rows (ADR-03)

Chosen: 2048 rows, for L1 fit across typical row widths (§9 ADR-03, §33 item 1). Rejected: 1024 (Velox), 65536 (ClickHouse Block), adaptive sizing. When the rejected choice is right: 1024 wins on small-L1 CPUs or very wide rows (more than 16 columns); 65536 wins when dispatch overhead, not cache residency, dominates, as in shuffle-bound pipelines (§9 ADR-03).

Execution model: push, with pull for debugging only (ADR-05)

Chosen: push-based consume, with next() kept as a debug surface, because push composes with morsel scheduling and pull serializes at boundaries (§9 ADR-05, P2). Rejected: pure Volcano pull. When the rejected choice is right: simple single-threaded embedded interpreters with no parallelism to exploit, such as SQLite's VDBE (§9 ADR-05).

Parallelism: morsel-driven scheduling (ADR-06)

Chosen: a morsel-driven scheduler, which avoids the NUMA serialization of exchange operators (§9 ADR-06, P3). Rejected: an exchange operator at every boundary (classic parallel Volcano). When the rejected choice is right: a genuinely distributed setting where every stage boundary is already a network shuffle, such as Presto or Trino (§9 ADR-06).

Hash table layout: vectorized linear probing (ADR-08)

Chosen: vectorized linear probing with a chained fallback for skew, for a SIMD-friendly probe pattern on uniform data (§9 ADR-08, P9). Rejected: pure chained, cuckoo and robin-hood hashing. When the rejected choice is right: cuckoo hashing when worst-case O(1) lookup matters more than average throughput (a real-time point-lookup service); chained under extreme adversarial skew (§9 ADR-08).

Spill threshold: 80% of the budget (ADR-09)

Chosen: spill at 80%, leaving headroom for allocations between per-morsel budget checks (§9 ADR-09). Rejected: 50%, 95%, or a GC-pressure-adaptive threshold. When the rejected choice is right: 50% for latency-sensitive workloads that prefer early, smooth spills; 95% to maximize memory use when a late stall is acceptable (§9 ADR-09).

Materialization: late by default (ADR-11)

Chosen: carry (row_id, key_cols) and fetch full rows at the sink through an explicit Materialize operator; it wins on selective, wide-table queries (§9 ADR-11, P4). Rejected: eager materialization at every operator. When the rejected choice is right: narrow tables (3 columns or fewer) or low-selectivity queries where more than 80% of rows survive (§9 ADR-11).

Compilation: a cranelift sidecar for hot expressions only (ADR-16)

Chosen: cranelift JIT for hot expressions only, since it compiles about 10× faster than LLVM, which matters for short queries (§9 ADR-16, P6). Rejected: LLVM JIT, and a full compiled pipeline (HyPer-style). When the rejected choice is right: LLVM when compile time is amortized over hours-long batch queries; a full compiled pipeline on simple star-joins where per-tuple register code beats vectorized batch overhead (§9 ADR-16).

Roads not taken

Fully compiled per-query execution (§35 A1): one native function per query, tuples held in registers, no batch materialization between operators. It wins for a few complex query shapes that repeat constantly, such as a dashboard re-run thousands of times a day (§35 A1). It is rejected because VOE's ad-hoc, infrequently repeated queries do not amortize LLVM's compile latency (§35 A1, ADR-16).

Tuple-at-a-time Volcano (§35 A2): wins for simple single-row point lookups and for reference implementations that value simplicity (§35 A2). Rejected because per-row dispatch dominates on 10⁶–10⁹ rows (§35 A2, P1, P2).

Row-major storage, row at a time (§35 A3): wins for OLTP point lookups and updates that need every column of a few rows. Rejected because OLAP touches few columns of many rows (§35 A3, §1).

GPU-resident columnar execution (§35 A4): wins for very wide, few-operator aggregations over data already on the device, where device bandwidth dwarfs host DRAM (§35 A4). Rejected for Phase 0–10 because of transfer cost and the second memory-hierarchy model it needs (§35 A4, ADR-24).

Deferred (§36): distributed execution (un-defer when a network-backed exchange or multi-host requirement arises), a GPU backend, a columnar UDF surface, the full 99-query TPC-DS suite, adaptive interpreted/compiled switching, crash-mid-spill resumption, and an external security audit as a Sealed prerequisite (§36).

What must never be false

  • I1: 1 ≤ num_rows ≤ MAX_VECTOR_SIZE. Noticed by debug_assert! on num_rows; telemetry batch_size_histogram (§7).
  • I2: selection length equals num_rows and every index is within the array. Bounds checks in debug, fuzz target fuzz/filter_kernel; telemetry kernel_bounds_violation (§7).
  • I3: boolean kernels over nullable inputs follow Kleene logic. The kernel.xcheck_cmp bucket; kernel_null_mismatch (§7).
  • I4: the schema is immutable through a pipeline. Adjacent-operator check at build time; pipeline_schema_mismatch (§7).
  • I5: hash table load factor stays at or below 0.7 without resize or spill. Occupied/capacity ratio per insert batch; hash_table_load_factor (§7).
  • I6: the build-side spill seed equals the matching probe-partition seed. Seed stored in SpillFile metadata and asserted on read; spill_seed_mismatch, which must be 0 (§7).
  • I7: the memory estimate never decreases between spill checkpoints and resets right after a spill. Assertion in MemoryBudget::check; operator_memory_bytes gauge (§7).
  • I8: at least 90% of morsel pops are served on the morsel's origin node. The numa.affinity bucket; numa_local_ratio (§7).
  • I9: no operator decodes a dictionary unless an explicit Decode is in the plan. Static check at pipeline-build time; dictionary_eager_decode (§7).
  • I10: cast totality matches the declared signature (widening total, narrowing fallible). Compile-time types plus kernel.xcheck; cast_overflow_error (§7).
  • I11: an upstream pipeline fully drains before any row enters the downstream one. Scheduler barrier assertion; pipeline_barrier_violation, which must be 0 (§7).
  • I12: scalar and every dispatched instruction set give bit-identical output. Byte-compare in the kernel.xcheck_* buckets on each CI instruction-set matrix; kernel_xcheck_mismatch, zero-tolerance and CI-gating (§7).
  • I13: results are deterministic except that floating-point SUM/AVG may vary by merge order within 1e-6. Repeated-run comparison in fuzz.canary_30d; result_drift_bytes (§7).
  • I14: u32 row-ids are used only when table cardinality is proven below 2^32. Static check plus a fuzz boundary test; row_id_overflow_guard (§7).

I8's recovery column says to escalate sustained NUMA misses "(FM7, §24)" (§7 I8), but in §24 FM7 is the cross-validation CI failure and the NUMA-locality failure is FM3 (§24).

What breaks in production

  • FM1: a pipeline hangs. It never reaches Finished because of an unhandled panic in an operator's consume(). Detection: the worker's join handle returns Err, or the scheduler watchdog times out. Recovery: the scheduler aborts the whole query, since there are no partial-result semantics; the panic backtrace is tagged with the query id (§24, I11).
  • FM3: queries are slow, results are right. Causes: a topology-detection bug, an external affinity conflict, or queue saturation. Detection: numa_local_ratio sustained below 90% (I8). Work-stealing only compensates for transient skew; the runbook is docs/runbooks/numa-debug.md (§24).
  • FM4: Error::MemoryBudgetExceeded or an OOM. Causes: extreme GROUP BY cardinality, missing spill wiring, or disk exhaustion mid-spill. Detection: operator_memory_bytes trending to the ceiling. Spill triggers at 80%; if the spill itself fails the query aborts cleanly; the manual fix is a larger budget or lower concurrency (§24, ADR-09).
  • FM5: join or aggregate results are silently wrong after a spill round-trip. The seed was generated badly or regenerated between spill and read. The I6 assertion on SpillFile read catches it. There is no auto recovery: the query hard-stops with Error::SpillSeedMismatch and a seed-lineage dump is produced (§24).
  • FM8: wrong output only in compiled mode. An emission bug in voe-codegen::builder for one expression shape. I12 is extended to the compiled path. There is no auto recovery; set VOE_DISABLE_CODEGEN=1 while it is fixed (§24).
  • FM9: the whole pipeline stalls at an I11 barrier. A downstream partition worker crashed or deadlocked. Detection: partition queue depth pinned at its cap beyond a timeout. Recovery: a per-partition timeout raises Error::ExchangePartitionStalled; the query is aborted and resubmitted, since there is no mid-query recovery (§24).
  • FM10: a build-side key with an extreme match count. Latency rises and memory pressure may follow. The probe operator paginates output into fixed-size batches (I1); if that is not enough the query aborts with Error::MemoryBudgetExceeded (§24).

Threats worth knowing (§23): T1, a malformed or adversarial plan, stopped by schema and type validation at build time (I4); T3, a crafted plan that forces quadratic memory through a bad join side, answered by the memory budget and mandatory spill (I7, P10); T4, SIMD instructions executed on an unsupported host if dispatch is bypassed, answered by a single dispatch.rs, no direct std::arch calls, and the VOE_FORCE_SCALAR escape hatch (P7); T5, cache poisoning of compiled kernels, answered by HMAC-signed cache entries verified on every hit; and T6, input skew crafted to collide every probe, answered by a randomized per-query hash seed and the chained fallback (I6, ADR-08).

Places where the blueprint's own numbers do not line up, stated without resolution:

  • Spill partitions behind the FD budget. §4 bases the ≤ 256 budget on 64 default partitions × up to 4 spilling operators, whereas §33 items 9 and 10 size a spilling join at 16 partitions, times up to 4 operators ("§4's FD assumption"), for 64 open files (§4, §33 item 9, §33 item 10).
  • Cross-NUMA cost. §4 gives absolute ranges, ~150–300 ns per cross-node access against ~80–120 ns local; §33 item 11 cites a "~200 ns cross-NUMA latency delta (§4)" and hard question 4 calls a cross-NUMA access "~3× slower" (§4, §33 item 11, §34).
  • M7's unit. §29 states M7 as ≥ 80M rows/s; Phase 4's acceptance criteria state it as ≥ 80M probes/sec on a 10M-row, 1M-unique-key dataset (§29, §16.4).

How it compares

  • DuckDB chose to be an embeddable, zero-dependency, single-file analytical database, and VOE's vector size deliberately mirrors its choice (§32, ADR-03). That fits exploratory single-machine analysis with instant startup and no server (§32).
  • ClickHouse chose a 65536-row Block and its own MergeTree storage co-designed with execution, giving up L1 residency for lower per-batch dispatch overhead (§32, §33 item 2). That fits massive, append-heavy, real-time analytics where storage/execution co-design matters most (§32).
  • Meta Velox chose to be a library embedded identically in Presto, Spark and other engines, with a stable shared Vector and expression ABI instead of end-to-end performance in one engine (§32). That fits an organization running many SQL engines that want one execution kernel, a different problem from VOE's single teaching audience (§32, §1).
  • HyPer chose to compile every query to native code through LLVM, removing interpretation overhead at the cost of compile latency (§32). That wins when the same complex query shape repeats enough for compile cost to amortize, the regime ADR-16 and §35 A1 name (§32, ADR-16).

Questions to test yourself

  1. Why does VOE default to a 2048-row vector while ClickHouse defaults to 65536? What single number from §4 explains the gap, and where is it derived? — Hint: §33 items 1 and 2, and the L1 row of §4.
  2. Late materialization's win is not universal — name the query shape where it loses, and the ADR that names the regime. — Hint: the last column of the ADR table, §9.
  3. Why does the design choose cranelift over LLVM for the compiled sidecar, and under what workload characteristic would that choice reverse? — Hint: ADR-16, MM4 and §35 A1.
  4. TPC-H Q9 exercises the Exchange operator "heavily" — using the pipeline-breaker model, explain why Q9 needs more pipelines than Q1, and name the operator causing each additional cut. — Hint: §8.3, §8.4, §17 and §18.
  5. Why does spilling a partial aggregate for AVG store (sum, count) rather than a single averaged value — trace the correctness bug this avoids, citing the phase where it's implemented twice. — Hint: §16.2 and §20.2.

If you only remember three things

VOE moves batches of column values, not rows, and sizes them to the cache, because per-row dispatch is what makes older engines slow (§35 A2, ADR-03, MM1). The only places a parallel query has to wait are the pipeline breakers, and morsels with NUMA-aware work-stealing keep every core busy between them (MM2, ADR-06, I8, I11). Memory is a budget, not a hope: every unbounded operator spills at 80%, and a stored hash seed makes the spilled partitions line up on re-read (P10, ADR-09, I6).

Words used here

  • Record batch (vector): a bounded set of rows stored by column, the unit of data flow.
  • Selection vector: a list of row indices that survived a filter, used instead of copying.
  • Validity bitmap: one bit per row marking null or not null.
  • Kleene logic: three-valued TRUE/FALSE/NULL rules for SQL predicates.
  • Morsel: a slice of about 100,000 rows handed to a worker as one unit of work.
  • NUMA: a memory layout where memory attached to a core's own node is faster to reach.
  • Work stealing: an idle worker takes a morsel from a busier peer's queue.
  • Pipeline breaker: an operator (Sort, HashAggFinal, HashJoinBuild, Exchange) that must drain upstream before downstream starts.
  • Linear probing / load factor: scan consecutive buckets on a collision; occupied share capped at 0.7.
  • Spill: writing an operator's in-memory state to disk when it exceeds its budget.
  • Grace hash join: partition both join sides by hash so each partition fits in memory.
  • Late materialization: carry row ids through the plan and fetch full rows only at the sink.
