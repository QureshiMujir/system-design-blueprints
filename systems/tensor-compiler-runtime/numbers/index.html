4. System Constraints

Hard, testable limits the compiler + runtime must satisfy. Every numeric target is a CI gate or a documented assumption; violations are bugs. Constraints below bind all nine tc-* crates and the tcc binary unless scoped otherwise.

4.1 Correctness & Numerical Tolerance (the oracle contract)

  • Oracle = a NumPy-style reference (Phase 13) computing each GraphOp in f64 then casting. Compiled Module output MUST match within tolerance per DType.
  • Schedule invariance (LOCKED): changing a Schedule (split/reorder/tile/vectorize/unroll/parallel/compute_at/inline) MUST NOT change results beyond the float-reassociation band below. Compute defines WHAT; schedule defines HOW.
  • Reduction reassociation (tiling a reduce axis, parallel-sum) is the ONLY sanctioned source of result drift; bounded by the reassociation band, never exceeding op tolerance.
Aspect DType rtol atol Notes
Elementwise (Add/Mul/Relu) F32 1e-5 1e-6 bit-exact for Relu/Reshape/Transpose (no FP op)
Elementwise F64 1e-12 1e-14
MatMul / Reduce F32 1e-4 1e-5 looser: accumulation order, FMA contraction
Conv2d F32 1e-4 1e-5 im2col/direct must agree within band
Integer ops (I8/I32/I64) int 0 0 bit-exact, overflow = documented wrap
Bool ops Bool — — bit-exact
Schedule-reassoc band (max ulp drift any schedule vs naive) F32 2e-5 2e-6 sub-tolerance; CI compares schedule pairs
  • Comparison rule: pass ⟺ |c − o| ≤ atol + rtol·|o| elementwise. NaN matches NaN; ±Inf must match sign. Mismatch → tcc check exits nonzero with first-diff index + values.

Constraint Target

  • MemoryPlan = buffer liveness over GraphExecutor topological order; non-overlapping tensors share Storage (tensor register allocation). Aliased buffers MUST NOT overlap in live ranges — verified by a liveness assertion, else hard error.

4.7 Determinism

  • Definition: same model + same inputs + same Schedule + same Target ⇒ bit-identical outputs across runs and machines of the same arch, modulo documented float reassociation (§4.1) which is itself deterministic for a fixed schedule.
  • No nondeterministic threading effects: parallel reductions use a fixed tree-reduction order (not first-come accumulation), so multi-thread results are reproducible.
  • No RNG, no clock, no address-dependent behavior in kernels. tune (Phase 12) uses a seeded PRNG; the seed is recorded in the Module so a tuned compile is reproducible.

4.8 Recovery & Robustness (no-crash contract)

  • A malformed model (bad ONNX-subset op, rank mismatch, cyclic dataflow, unknown GraphOp, shape that cannot unify) is rejected at import / shape-inference with a diagnostic (node id + reason); the process MUST NOT panic, segfault, or produce a partial Module.
  • Fuzzing gate (Phase 13): random graph + random schedule generators run ≥ 10⁶ iterations with zero crashes/UB (ASan/Miri clean) and zero numerical-tolerance violations.
  • Every unsafe block (NDArray/Storage pointer math, FFI to compiled kernels) carries a documented invariant; bounds are checked at view-construction time so kernel hot loops stay unchecked but provably in-bounds.
  • Codegen failure (cc error) surfaces the emitted Kernel.source path + compiler stderr; never silently degrades.

4.9 Platform & Build Constraints

  • tc-graph and tc-ir are no_std + alloc (embeddable IR core); higher crates use std.
  • Rust edition 2021, MSRV 1.78. No GPU code paths active (Device::Gpu, Scope::Shared, IterKind::Thread are PhaseDeferred stubs — must compile, must not execute).
  • External toolchain: a C compiler (cc/clang) on PATH for the CBackend default path; optional LLVM path behind a feature flag (not default). Build fails fast with a clear message if cc is absent.
  • Non-goals enforced by absence: no autograd, no training loop, no full ONNX op set, no Python frontend, no distributed runtime.

Back-of-Envelope Capacity Model

All numbers derived step-by-step from §4 System Constraints. Baseline hardware: x86_64, AVX2, 8 cores, ~50 GB/s DRAM BW, ~3 GHz, ~256 GFLOP/s peak f32 AVX2 FMA (8 cores × 2 FMA/cycle × 8 lanes × 3 GHz).

N1 — Fused elementwise throughput (memory-bandwidth ceiling)

From §4.3: target ≥ 80% of measured DRAM BW for fused elementwise.

BW_peak = 50 GB/s
BW_target = 0.80 × 50 = 40 GB/s
Bytes_per_element (f32) = 4 B
Elements/sec = 40e9 / 4 = 10e9 = 10 GELEM/s
For a length-N fused add+relu: time = N × 4 B / 40e9
  N=1e8 elements → time = 1e8 × 4 / 40e9 = 10 ms

Implication: a fused 100M-element chain executes in ~10 ms; an unfused 4-op chain (4× memory passes) takes ~40 ms — 4× slower.

N2 — Unfused vs fused intermediate buffer bytes (fusion win)

From §8.5 Conv2d→Add→Relu example and §4.4 MemoryPlan target.

Conv2d output: f32[1,64,112,112] = 64 × 112 × 112 × 4 B = 3.21 MB
Add intermediate (bias): same shape = 3.21 MB
Total intermediate materialization (unfused) = 2 × 3.21 = 6.42 MB
Fused: 0 MB (accumulator lives in registers/Local scope)
DRAM round-trip savings: 6.42 MB read + 6.42 MB written = 12.84 MB per inference pass
At 40 GB/s: time saved = 12.84e6 / 40e9 = 0.32 ms per conv-add-relu group

N3 — MemoryPlan peak memory reduction

From §4.4: target ≥ 40% reduction vs no-reuse on MLP/conv corpus. From §8.7 worked example.

5-intermediate graph (§8.7): naive = 4+4+2+2+4 = 16 MB; planned = 10 MB
Reduction = (16−10)/16 = 37.5%  ≈ meets the 40% target on a chain
Deep linear chain (10 nodes, each 4 MB): naive = 40 MB
  Only 2 simultaneously live at any step → planned = 8 MB
  Reduction = (40−8)/40 = 80%

N4 — Scheduled MatMul GFLOP/s target derivation

From §4.3: target ≥ 10× naive baseline; ≥ 8 GFLOP/s single-thread vectorized.

Peak AVX2 f32 FMA throughput (1 core, 3 GHz):
  2 FMA/cycle (fused multiply-add counts 2 FLOPs) × 8 lanes × 3e9 = 48 GFLOP/s/core theoretical
Cache-blocking efficiency estimate: 60% of peak (register pressure, load imbalance) → ~29 GFLOP/s
Vectorize + tile target: 8 GFLOP/s = 8/48 = 17% of peak (conservative: includes overhead)
Naive triple-loop (no tiling, poor cache): ~0.3–0.5 GFLOP/s (measured baseline)
10× over naive baseline: 0.4 × 10 = 4 GFLOP/s — below the 8 GFLOP/s single-thread target
  → The 8 GFLOP/s target is the binding constraint (requires proper tiling + AVX2 FMA)

N5 — Compile-time cc invocation cost

From §4.2: per-kernel cc compile target < 400 ms; ResNet-class in < 30 s.

ResNet-50 has ~50 conv ops + biases + activations → after fusion: ~15–20 fused groups → ~15–20 kernels
Serial cc cost: 20 kernels × 200 ms/kernel = 4 s  (within the 30 s budget)
Parallel cc (8 cores): 20/8 kernels in flight = ceil(20/8)=3 batches × 200 ms = 0.6 s
Single TU approach (all kernels in one file): 1 cc call × ~2–4 s = 2–4 s (vs 4 s serial)
  → parallel cc preferred for > 8 kernels; single TU preferred for < 4 kernels

N6 — Auto-tuner trial budget and wall-clock bound

From §4.2: tune budget ≤ 200 trials / ≤ 30 s per fused kernel.

Each measured trial: codegen (~10 ms) + cc (~200 ms) + kernel run (~5 ms) = ~215 ms
200 trials × 215 ms = 43 s  (exceeds 30 s limit by ~43%)
  → must prune: analytical cost model eliminates ~70% of candidates before measuring
200 × 0.30 = 60 measured trials × 215 ms = 12.9 s  (within 30 s budget)
For a large graph with 20 fused kernels: 20 × 12.9 s = 258 s ≈ 4.3 min full tune

N7 — Dispatch overhead fraction on small tensors

From §4.5: GraphExecutor per-op dispatch overhead < 1 µs/op.

Kernel work for a tiny tensor f32[64]: 64 × 4 B / 40 GB/s = 6.4 µs (memory-bound)
Dispatch overhead = 1 µs / 6.4 µs = 15.6% overhead → acceptable
Kernel work for f32[16]: 16 × 4 / 40e9 = 1.6 µs; dispatch = 1/1.6 = 62.5% → dispatch-bound
  → tensors below ~1000 elements are dispatch-dominated; fusion is critical to reduce K

N8 — Compiler RSS for a large graph

From §4.4: compiler peak RSS < 256 MB.

Arena<GraphNode> at ~128 B/node, N=10⁴: 10⁴ × 128 = 1.28 MB
TIR PrimFunc/Stmt/Expr at ~48 B/IR node, ~10 IR nodes/graph node:
  10⁴ × 10 × 48 = 4.8 MB
Module: 20 kernels × ~50 KB C source = 1 MB
Total ≈ 7 MB — well within 256 MB ceiling even with 10× slack
  At N=10⁵ (above stated max): ~70 MB — still within budget; pass pipeline stays sub-second

N9 — Parallel speedup ceiling (Amdahl)

From §4.3: parallel axis speedup ≥ 0.7·nproc on compute-bound kernels.

nproc = 8, target speedup ≥ 0.7 × 8 = 5.6×
Amdahl's law: speedup = 1 / (s + (1-s)/n), target 5.6× with n=8
  5.6 = 1 / (s + (1-s)/8) → s + (1-s)/8 = 1/5.6 = 0.179 → s(1 - 1/8) = 0.179 - 0.125 → s = 0.077
  → serial fraction must be < 7.7% (tail loops, reductions) for the 5.6× target
Loop tail (from split with factor 64 on extent 1000): tail = 1000%64 = 40 iters / 1000 = 4% serial
  → within budget
