Decisions (§9) · 27 ADRs

ADR-01

Implementation language

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

C/C++; Python; Go

When the rejected choice is right

C wins when embedding the compiler in a tight bare-metal firmware loop with no allocator (no Rust std/alloc available, LLVM GC incompatible). Python wins for a pure research-notebook frontend that never touches the hot path.

Why: Sum types + exhaustive match for IR nodes → pass safety; no GC for runtime hot path + zero-copy NDArray; ownership tames large mutable IR + buffer model. C/C++ memory-unsafe over IR; Python too slow for runtime (frontend-only role); Go weak sum types + GC perturbs latency.

ADR-02

Workspace decomposition

Chosen

Nine member crates tc-graph, tc-ir, tc-pass, tc-fuse, tc-schedule, tc-codegen, tc-runtime, tc-vm, tc-cli

Rejected

Single monolithic crate; two-crate (compiler/runtime) split

When the rejected choice is right

Monolithic crate wins when cross-crate link time dominates (e.g., incremental compile on a single-file project with <2 000 lines total) or when inlining across crate boundaries is critical for sub-microsecond dispatch.

Why: Crate boundary = enforced dependency DAG (e.g. tc-pass cannot reach codegen); parallel cargo build; per-crate fuzz/bench targets; clean compiler↔runtime cut at tc-codegen::Module. Monolith loses boundary checks; coarse split hides layering.

ADR-03

IR layering

Chosen

Two-level: Graph IR (tc-graph) + tensor/loop IR (tc-ir), lowered per fused group

Rejected

Single unified IR; MLIR-style multi-dialect with custom infra

When the rejected choice is right

MLIR multi-dialect wins when the target has 3+ distinct abstraction levels needing progressive lowering (e.g., accelerator ISA with special DMA tiles, vector units, and scalar registers — as in Google TPU's XLA/MLIR stack). Single unified IR wins for a toy scalar interpreter with no optimization pass.

Why: TVM Relay/TIR split: whole-tensor dataflow vs imperative loop-nest are distinct optimization domains (fusion/layout vs tiling/vectorize). Single IR conflates both → unschedulable. MLIR dialect infra is a multi-year project off-scope; we reuse its pass-manager design, not its codebase.

ADR-04

IR storage model

Chosen

Arena + typed ids NodeId/BufferId/VarId/AxisId/StageId

Rejected

Rc<RefCell<Node>> graphs; Box trees with parent ptrs

When the rejected choice is right

Rc<RefCell<>> wins in an interpreter REPL where users mutate graph nodes interactively in a single-threaded Python-like environment (shared mutable references match the use model, and performance is dominated by user think-time).

Why: Arena = O(1) alloc, contiguous cache layout, trivial clone/serialize, no cycles, ids are Copy. Rc graph compiler → lifetime tangle, ref-cycle leaks, poor locality. Typed ids prevent cross-arena confusion at compile time.

ADR-05

Compute/schedule separation

Chosen

Halide model: TensorExpr = WHAT, Schedule = HOW; schedule never alters numerics

Rejected

Hand-written per-op kernels; fused-template metaprogramming

When the rejected choice is right

Hand-written kernels win when a vendor provides architecture-tuned intrinsic libraries (cuBLAS, oneDNN) that outperform any auto-scheduler on a proprietary accelerator; the compute/schedule abstraction overhead becomes unjustified.

Why: Decouples correctness (one compute def) from performance (many schedules) → enables auto-tuning (Phase 12) + portability. Hand-written kernels: O(ops × targets × schedules) blowup, no search. Invariant: schedule change ⇒ identical result within tolerance.

ADR-06

Operator fusion strategy

Chosen

Dominator-tree analysis in FusionPass grouping injective/elementwise chain + ≤1 reduce

Rejected

Pattern-match-only (fixed peephole rules); no fusion

When the rejected choice is right

Pattern-match-only wins when the fusion policy is safety-critical and must be auditable by regulators — a fixed, enumerated peephole table with formal proofs per pattern is easier to certify than a graph-theory analysis pass.

Why: Dominator analysis generalizes to arbitrary DAG shapes; fusion is the dominant CPU win (eliminates intermediate materialization + memory traffic). Pattern-only misses long chains / diamond shapes. No-fusion → memory-bound.

ADR-07

Default kernel backend

Chosen

C source (CBackend) compiled via system cc

Rejected

LLVM-only; direct assembly emission; Cranelift

When the rejected choice is right

LLVM wins in an AOT deployment where the target device has no system cc (e.g., mobile firmware image, Wasm sandbox) and the binary must ship pre-compiled kernels with vectorization guarantees. Direct assembly wins for a cycle-accurate inner loop on a novel ISA unsupported by any C compiler.

Why: C backend is portable, debuggable (readable kernels = dump c), zero heavyweight build dep, leverages cc autovec/-O3. LLVM-only adds large build dep + version churn. Direct asm = per-arch rewrite, unsafe.

ADR-08

Optional LLVM path

Chosen

LLVM codegen behind a llvm feature flag (off by default)

Rejected

LLVM mandatory; never

When the rejected choice is right

LLVM-mandatory wins when the deployment fleet is homogeneous (single LLVM version locked to OS packages), GFLOP/s parity with BLAS is a hard gate, and the build-dep burden is already paid by the surrounding toolchain.

Why: Power users get tighter codegen without forcing the dep on the default build / CI. Feature-gated keeps MSRV + minimal-deps invariant for the core path.

ADR-09

SIMD strategy

Chosen

Portable SIMD abstraction (SimdBackend) emitting width-parametric vector ops

Rejected

Target-specific intrinsics (AVX2/NEON inline) hardcoded; scalar-only

When the rejected choice is right

Hand-coded intrinsics win when squeezing the last 10–20% from a single-target HPC cluster node where AVX-512 gather/scatter, FMA, and prefetch patterns cannot be expressed in portable abstractions (e.g., GEMM kernel competing with MKL on Xeon).

Why: One vectorize lowering retargets across arches via Target.features; matches Halide/portable-simd model. Intrinsics = N× duplicated backends, fragile. Scalar-only forfeits 4–8× throughput.

ADR-10

Memory management

Chosen

Liveness-based MemoryPlan (buffer reuse via interval analysis)

Rejected

Arena-per-op (alloc each intermediate); GC; static max-size slab

When the rejected choice is right

GC wins in an interactive research environment (e.g., TensorFlow 1.x eager mode, PyTorch autograd) where dynamic graph changes between iterations make static liveness analysis stale after every recompile. Static max-size slab wins in a hard-real-time system with no dynamic allocation allowed (MISRA-C, AUTOSAR).

Why: Register-allocation-on-tensors: reuse storage for non-overlapping live ranges → minimal peak RSS. Arena-per-op wastes memory + cache. GC: latency jitter. Plan computed over executor topological order.

ADR-11

Static vs dynamic execution

Chosen

Split: GraphExecutor (static shapes) + tc-vm Interpreter (control flow / dynamic shapes)

Rejected

Single executor handling both; VM-only

When the rejected choice is right

VM-only wins when >50% of ops in the workload have data-dependent output shapes (NLP with dynamic sequence lengths, sparse graphs) and the static executor would require worst-case-shape over-allocation that exceeds device RAM.

Why: Static path: ahead-of-time MemoryPlan, no per-op branching → max throughput. VM: registers + If/Goto/Call, runtime alloc for Dim::Dynamic. Same compiled Kernels dispatched by both. Unified path pays dynamic cost on static graphs.

ADR-12

Model frontend

Chosen

ONNX-subset importer + textual graph format

Rejected

Full ONNX op set; Python frontend / eager API

When the rejected choice is right

Full ONNX wins when the goal is a production inference server accepting arbitrary customer models (ResNets, Transformers, detection heads) — a subset importer rejects valid models and becomes a business blocker. Python eager API wins for a research framework where users expect NumPy-like syntax.

Why: Documented op subset (matches GraphOp registry) is tractable + testable; textual format = readable fixtures + golden tests. Full ONNX = hundreds of ops, off-scope. Python frontend = FFI + interpreter dep, deferred.

ADR-13

Correctness validation

Chosen

External NumPy-style reference oracle, f32 rtol 1e-5 / atol 1e-6

Rejected

Self-checking (compiler validates itself); property-only

When the rejected choice is right

Self-checking wins when the oracle itself is unavailable on the target (embedded device with no Python/NumPy) and the only option is comparing two independent code paths generated by the same compiler at different optimization levels.

Why: Independent oracle catches compiler and spec bugs (self-check is circular). Numerical tolerance is the contract: every pass + schedule + backend must match oracle. Differential + fuzz testing layered on top (Phase 13).

ADR-14

Auto-tuner approach

Chosen

Cost model = analytical + measured, guided search over schedule primitives

Rejected

Exhaustive grid search; pure-analytical; pure-measured (AutoTVM-style only)

When the rejected choice is right

Pure-measured (AutoTVM-style) wins when a novel accelerator has no accurate analytical model and the hardware team cannot provide roofline numbers — measurement is the only ground truth. Exhaustive grid wins in a tiny fixed schedule space (e.g., 3 tile sizes × 2 vectorize widths) where the grid fits in a 30-second tuning budget.

Why: Analytical prunes obviously bad configs cheaply; measured ranks survivors on hardware → far fewer trials than exhaustive (combinatorial blowup). Pure-analytical inaccurate; pure-measured too slow.

ADR-15

Tensor layout model

Chosen

NDArray = strided view (shape + strides + offset over ref-counted Storage); zero-copy slice/reshape/transpose

Rejected

Contiguous-only tensors; copy-on-view

When the rejected choice is right

Contiguous-only wins on a DMA-based accelerator that requires physically contiguous buffers for every op and where strided access triggers a hardware fault — copy-on-view is mandatory, not optional.

Why: Strides enable zero-copy reshape/transpose/slicing + layout transforms without allocation. Contiguous-only forces copies on every layout op. Ref-counted Storage shares buffers safely.

ADR-16

DType set

Chosen

F32, F64, I32, I64, I8, Bool

Rejected

Add F16/BF16/complex/quantized now; F32-only

When the rejected choice is right

F16/BF16 wins when targeting modern GPU or NPU hardware where the hardware's peak throughput is measured in BF16 TFLOPS and F32 throughput is 2–4× lower (NVIDIA A100, Apple Neural Engine).

Why: Covers inference math + indices + masks/bools with bounded codegen surface. F16/BF16/quant deferred (codegen + accumulation complexity). F32-only blocks integer indexing + bool predicates.

ADR-17

Float reassociation policy

Chosen

Deterministic: reassociation only under explicit fast-math opt-in; default preserves evaluation order

Rejected

Always allow reassoc; never allow

When the rejected choice is right

Always-allow-reassoc wins when throughput is the only objective and bit-reproducibility is explicitly waived (e.g., HPC climate simulation ensemble runs where statistical error dwarfs FP rounding, and the 20% SIMD speedup from reassoc is load-bearing).

Why: Determinism = bit-reproducible runs + stable oracle comparison; FP add/mul non-associative ⇒ uncontrolled reassoc breaks tolerance + reproducibility. Opt-in fast-math for performance when tolerance permits.

ADR-18

Core IR crate environment

Chosen

no_std + alloc for tc-graph and tc-ir

Rejected

Full std everywhere

When the rejected choice is right

Full std wins if the IR crates must use HashMap with a random-seed DoS-hardened hasher (requires std::collections::HashMap), spawn threads for parallel IR transforms, or link against platform APIs available only in std (e.g., mmap on POSIX via std::fs).

Why: IR crates are pure data + transforms → portable to constrained/embedded compile hosts + faster compile; std confined to runtime/codegen/cli where I/O + threads + cc invocation live.

ADR-19

Benchmarking harness

Chosen

criterion for kernels/passes/runtime; GFLOP/s + % of naive baseline reported

Rejected

std::time ad-hoc; nightly #[bench]

When the rejected choice is right

std::time wins when integrating with an external performance regression database that expects raw timing JSON and criterion's HTML reports are discarded; or in a bare-metal test harness that cannot run cargo at all.

Why: Statistically rigorous (outlier detection, regression tracking) on stable Rust. Targets: report GFLOP/s + speedup vs naive nested-loop baseline per Phase 13.

ADR-20

Fuzzing

Chosen

Generator-based: cargo-fuzz over graph + schedule generators (must not crash; must stay within tolerance)

Rejected

No fuzzing; manual edge cases only

When the rejected choice is right

Manual edge-case testing wins in a regulated safety domain (IEC 61508, ISO 26262) where the fuzzer's random seed and coverage path must be fully auditable and reproducible — random fuzzing is treated as non-deterministic and cannot be cited in the safety case.

Why: Random valid graphs + random valid schedules surface pass/codegen/VM crashes + numerical divergence. Schedule fuzzer directly stresses ADR-05 invariant (schedule ≠ numerics change).

ADR-21

CI

Chosen

GitHub Actions: fmt + clippy (deny warnings) + test + MSRV check + fuzz smoke + bench-no-regress

Rejected

None; other CI

When the rejected choice is right

Self-hosted CI wins when build machines must have pinned GPU hardware for kernel benchmark tests or when data residency requirements prohibit sending source code to GitHub's cloud runners.

Why: Standard, free for the repo; matrix over default + llvm feature; MSRV job pins 1.78; gates merges on oracle conformance.

ADR-22

MSRV policy

Chosen

Pin 1.78; bump only with changelog entry + CI MSRV-check enforcement

Rejected

Track latest stable; no policy

When the rejected choice is right

Track-latest wins in a rapid-prototype repo where compiler features (async generators, let-else, impl Trait in fn ptrs) are the primary driver and downstream consumers all control their own toolchain.

Why: Predictable for downstream + reproducible builds; CI fails on accidental newer-stdlib use.

ADR-23

Dependency policy

Chosen

Minimal deps: only criterion (dev), cargo-fuzz (dev), feature-gated LLVM, system cc; no heavy runtime deps

Rejected

Pull BLAS/ndarray/serde-everywhere

When the rejected choice is right

BLAS/MKL wins in a production inference server where performance SLAs are non-negotiable and the project goal is running models fast (not generating kernels as a learning exercise).

Why: Self-contained learning + audit surface; NDArray/Arena/parser written in-tree. BLAS would mask our own kernel performance (the point is to generate competitive kernels).

ADR-24

Pass infrastructure

Chosen

PassManager + Pass trait with declared analysis/transform + a verifier (every node typed post-pass)

Rejected

Hardcoded fixed pass pipeline; ad-hoc function calls

When the rejected choice is right

Hardcoded pipeline wins when the pass order is provably optimal and fixed (e.g., a minimal AOT compiler for a single-op ASIC with exactly 3 transforms), and the PassManager's dynamism and verifier overhead add measurable compile-time cost.

Why: Composable ordering, dependency-aware scheduling, MLIR-style. Verifier after each transform catches IR corruption early (untyped node ⇒ hard error).

ADR-25

Compiled artifact boundary

Chosen

Module { kernels, graph, MemoryPlan } as the single load/run interface

Rejected

Pass loose kernel list around; in-memory-only

When the rejected choice is right

In-memory-only wins in a JIT hot loop where serialization roundtrip latency is unacceptable (e.g., per-batch recompilation in a streaming pipeline where the compile→run turnaround must be sub-millisecond).

Why: Stable serialization + load boundary between compiler and both runtimes; MemoryPlan travels with kernels so executor/VM need no recomputation.

ADR-26

GPU / CUDA codegen

Chosen

Deferred (Scope::Shared, IterKind::Thread, Device::Gpu reserved but unimplemented)

Rejected

Implement now; remove the hooks

When the rejected choice is right

Implement-GPU-now wins if the primary use case is large transformer inference where GPU throughput is 10–50× CPU and CPU-only benchmarks are meaningless for the intended hardware tier.

Why: CPU-only scope (GPU = projects 248/180); reserving enum variants keeps the type surface forward-compatible without dead code paths shipping.

ADR-27

Licensing

Chosen

MIT OR Apache-2.0 (dual)

Rejected

GPL; proprietary; single license

When the rejected choice is right

GPL wins when the project's sustainability model depends on copyleft reciprocity to prevent proprietary forks from extracting value without contributing back (e.g., a compiler foundation that competes with commercial vendors). Proprietary wins when the compiler is the core IP of a commercial product.

Why: Permissive ecosystem-standard dual license (matches Rust + TVM-adjacent norms); maximal downstream reuse.

Alternative Architectures (Roads Not Taken)

Four fundamentally different architectures for a tensor compiler + runtime, each representing a different design space.

Alt-1 — Single unified IR (no two-level split)

model
  |-- import
  v
Unified IR (ops carry loop/schedule annotations inline)
  |-- fusion/tiling/vectorize passes (all on same IR)
  v
codegen  -->  Module  -->  runtime

Regime where it wins: a toy compiler targeting a single hardware accelerator with a fixed ISA where the distinction between "graph-level" and "loop-level" is irrelevant (e.g., a matrix engine that operates on fixed 16×16 tiles; there are no loops to tile). A single IR with op-level tiling attributes requires zero lowering overhead. Real system embodying it: ONNX Runtime's operator-level representation for fixed-shape inference — each node maps directly to a kernel, no loop structure exposed. Why this blueprint rejected it: the compute/schedule separation is the central architectural thesis (§6.2 P2). A unified IR forces tiling attributes into every GraphOp, making graph-level CSE and DCE either impossible (must also CSE loop structures) or require layer-stripping anyway — reconstructing the two-IR split implicitly.

Alt-2 — Interpretation-only (no AOT codegen)

model
  |-- import
  v
Graph IR  -->  pass + fusion  -->  Interpreted executor
                                   (eval each op with reference kernel)

Regime where it wins: a research tool where compile time dominates experimentation time and the workload changes every run (e.g., NAS search that generates thousands of unique model topologies per hour). Compiling each model to native code is counterproductive; a fast interpreter backed by pre-compiled op libraries (like PyTorch eager mode) wins. Real system embodying it: TensorFlow 2.x eager execution, PyTorch eager mode — no compilation, each op dispatched to a pre-compiled kernel immediately. Why this blueprint rejected it: the entire goal is to learn and build the codegen + schedule pipeline. An interpretation-only architecture sidesteps the fusion pass (no materialized loop structure to fuse into), the schedule space (no loop axes to tile/vectorize), and the codegen backend — eliminating the three most instruction-rich components of the project.

Alt-3 — Polyhedral compiler (Pluto/isl-based tiling legality)

model
  |-- import
  v
Polyhedral IR (affine loop nests with dependence polyhedra)
  |-- Pluto/isl tiling, fusion, parallelization (automatic)
  v
LLVM IR  -->  Module  -->  runtime

Regime where it wins: scientific computing kernels (stencils, iterative solvers, structured meshes) where data-dependence patterns are statically provable and the polyhedral model can automatically find the optimal tiling without a search budget. Pluto's automatic compute_at is provably optimal for affine loop nests with bounded trip counts. Real system embodying it: Tensor Comprehensions (Vasilache et al., 2018, P8) and Polly (LLVM's polyhedral optimizer). Why this blueprint rejected it: the polyhedral model requires affine index expressions throughout — Dim::Dynamic symbolic dims immediately escape the polyhedral domain. More critically, the polyhedral framework (isl or Omega) is a large external dependency (comparable in complexity to LLVM itself) and replaces rather than teaches the schedule-primitive intuition that is the learning goal of Phases 7–8.

Alt-4 — Ahead-of-time kernel library (template metaprogramming)

op registry (e.g. Conv2d stride=1 pad=0, f32)
  |-- select pre-written kernel template
  |-- specialize at compile time (C++ template instantiation)
  v
specialized kernel .so  -->  Module  -->  runtime

Regime where it wins: production inference on a fixed set of known model architectures (e.g., ResNet-50, BERT-base, YOLOv5) where all op shapes are known at library build time and vendor-optimized templates outperform any auto-generated kernel. NVIDIA's cuDNN, Intel's oneDNN, and Arm Compute Library all follow this model. Real system embodying it: ONNX Runtime's CPU Execution Provider with oneDNN; every Conv2d is dispatched to a pre-optimized MKL/oneDNN kernel. Why this blueprint rejected it: the template library approach scales as O(ops × targets × shapes) in implementation effort, requires human experts for each new architecture, and cannot learn — the entire auto-tuning (Phase 12) and schedule-search premise is that the compiler can discover better schedules than a human would write. A template library also teaches nothing about IR design, schedule primitives, or codegen.
