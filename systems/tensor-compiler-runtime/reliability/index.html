Threat Model

26.1 Scope, assets, attacker model

Asset class Why it matters Loss on compromise
Compile host (tcc compile/tune) runs untrusted graph through tc-pass/tc-fuse/tc-schedule/tc-codegen + invokes cc RCE, DoS, exfil of build env
Emitted C kernels + Module tc-codegen output, compiled by cc, dlopened by tc-runtime RCE on execute host, OOB memory
NDArray storage / Storage.ptr live tensor buffers in tc-runtime/tc-vm OOB read/write, info leak, corruption
Numerical result the contract: schedule changes preserve value within tolerance silent wrong answers (worst: undetected)
Build supply chain cc toolchain, crate deps, pinned IR trojaned kernels, reproducibility loss

Attacker capabilities (assume all): (a) supplies an arbitrary model file (ONNX-subset / textual graph); (b) supplies arbitrary input tensors at run; (c) may control schedule hints / tune config; (d) CANNOT modify tc-* source, the pinned cc, or deny.toml. Trust = code (trusted) vs data (graph + tensors + tune config, all UNTRUSTED).

26.2 Trust boundaries

   UNTRUSTED data                         TRUSTED code (tc-* + pinned cc)
   ───────────                            ──────────────────────────────
   model file ──┐
                ▼  [B1 import/verify]
            tc-graph Graph ─────────────► tc-pass / tc-fuse / tc-schedule  (in-proc, typed IR)
                                                     │
                                          [B2 codegen]│ emit C ONLY from typed TIR
                                                     ▼
                                            cc (sandboxed, pinned) ──► .so
                                                     │
                                          [B3 LOAD] dlopen Module  ◄── strongest boundary
                                                     ▼
   input tensors ─[B4 bind/shape-check]─► tc-runtime GraphExecutor / tc-vm Interpreter
                                                     ▼
                                            output (oracle-checked)
  • B1 import: only boundary where attacker bytes become IR; every node MUST be typed + verified before any pass runs.
  • B2 codegen: kernels emitted EXCLUSIVELY from Stmt/Expr/Buffer typed IR — never from raw user strings, names, or attributes. No user string reaches the C source except through an escaped/validated identifier whitelist.
  • B3 load (compile→load→execute): the highest-risk boundary. A .so produced on host A may run on host B. The loaded artifact is native code with full process privilege. Mitigations §26.3-T4.
  • B4 bind: runtime input shapes/dtypes re-checked against KernelSig before dispatch; dynamic dims resolved + bounds-validated in the VM.

26.3 Threat enumeration

Each: vector → mitigation → detection → telemetry → recovery.

T1 — Compile-time DoS (graph/fusion/search blowup)

  • Vector: huge graph (10⁶ nodes), pathological deep fusion chain, combinatorial schedule search, exponential shape-inference fixpoint, adversarial constant-fold (fold a 10 GB tensor).
  • Mitigation: hard caps — max_nodes (default 2²⁰), max_edges, max_fusion_group_size (default 256 ops), max_const_fold_bytes (default 64 MiB), tune_budget (wall-clock + trial count, default 5 min / 1000 trials), shape-inference iteration cap (default 10·|nodes|) with non-convergence = reject. Pass-manager global compile deadline.
  • Detection: cap exceeded → typed CompileError::ResourceCap{kind,limit,observed}, fail closed.
  • Telemetry: per-pass node count, peak RSS, fixpoint iterations, fusion group sizes, tune trials/elapsed.
  • Recovery: abort compile; partial artifacts discarded; caps configurable but never unbounded.

T2 — Shape / type confusion

  • Vector: model declares mismatched shapes/dtypes (e.g. MatMul [m,k]·[j,n], k≠j), negative/zero dims, rank mismatch, dtype that op doesn't support, Dim::Dynamic used where static required.
  • Mitigation: shape inference (Phase 2) propagates TensorType to fixpoint; the verifier (tc-pass) asserts every GraphNode.ty == Some post-inference; per-op typing rules reject illegal combos at IMPORT, before fusion/codegen.
  • Detection: VerifyError::Untyped(NodeId) / TypeError{op,expected,got} at B1.
  • Telemetry: count of rejected nodes by reason; histogram of inferred ranks.
  • Recovery: reject whole model; no IR with None type ever reaches tc-fuse. Invariant: no untyped node survives Phase 2.

T3 — OOB access in a generated kernel

  • Vector: bad strides/indices in emitted loop nest, off-by-one in tiled remainder, schedule split with non-dividing factor producing OOB tail, dynamic shape exceeding allocated buffer.
  • Mitigation: KernelSig is the contract (pointers + shapes + strides, all passed explicitly); debug builds emit bounds-checked codegen (each Load/Store index range-asserted against buffer extent); split/tile remainder handling proven against extent in tc-schedule; release builds rely on the schedule-correctness invariant + fuzz coverage.
  • Detection: debug bounds assert traps; AddressSanitizer in CI on emitted kernels; differential fuzzing (graph + schedule generators) must not OOB.
  • Telemetry: per-kernel assert hit counts (debug); ASan reports in CI.
  • Recovery: assert → abort kernel, surface RuntimeError::Bounds{kernel,index,extent}; CI gate blocks merge on any ASan finding.

T4 — codegen→cc→dlopen arbitrary-code-execution surface

  • Vector (the dominant RCE risk): emitted C compiled then loaded as native code. Injection if any user string reaches the C source unescaped; or a trojaned .so; or #include/pragma injection via op names/attrs.
  • Mitigation:
    • emit C ONLY from typed IR; identifiers from a generated whitelist (k0, buf3, …), never user-derived; numeric consts emitted via formatter, never string-spliced.
    • invoke a pinned cc (exact version + hash) with a fixed, minimal flag set; -I/-include/-D from user input forbidden; -nostdinc + an allowlisted include dir.
    • sandbox the cc invocation and the loaded module: seccomp-bpf profile (no exec, no network, restricted openat to the build tmpdir), separate uid, no env passthrough; emitted source written to an O_TMPFILE-style locked path.
    • artifact integrity: Module records the SHA-256 of each Kernel.source and the resulting .so; load verifies the hash chain; cross-host load requires matching Target.arch/features or refuses.
  • Detection: hash mismatch on load; seccomp violation killed + logged; static scan of emitted source for forbidden tokens (#include, system, __asm) before cc.
  • Telemetry: cc invocation args + version, sandbox denials, load hash-verify pass/fail, dlopen count.
  • Recovery: any mismatch/violation → refuse to load, quarantine artifact. Optional ahead-of-time mode separates the trusted compile host from the untrusted execute host across B3.

T5 — Numerical-correctness attack (schedule silently changes results)

  • Vector: a schedule (reorder of a non-associative reduce, unsafe vectorize, bad compute_at) that produces a value differing beyond tolerance; or a tuner that overfits to a single input.
  • Mitigation: compute/schedule separation invariant — every candidate schedule's output is checked against the reference oracle within documented tolerance (f32 rtol 1e-5, atol 1e-6; f64 tighter) before acceptance; the tuner rejects any schedule failing the oracle regardless of speed; reduction reordering only when the op is flagged associative-safe (or within fp tolerance).
  • Detection: oracle diff > tolerance → ScheduleError::NumericDrift{kernel,max_abs,max_rel}.
  • Telemetry: per-candidate max abs/rel error, fraction of schedules rejected for drift.
  • Recovery: drop the candidate; fall back to the validated naive PrimFunc. Invariant: a Module never ships an unvalidated schedule.

T6 — MemoryPlan aliasing bug

  • Vector: liveness analysis reuses storage for two tensors whose lifetimes actually overlap → silent corruption / data leak between ops.
  • Mitigation: MemoryPlan built from liveness over the executor's topological order; runtime liveness asserts (debug) verify no two simultaneously-live tensors share a Storage range; reuse only between provably non-overlapping intervals.
  • Detection: overlap assert; ASan/Miri on the planner; differential test (planned vs no-reuse) must match bit-exact.
  • Telemetry: reuse ratio, alias-assert hits, peak vs planned memory.
  • Recovery: assert → disable reuse for that buffer (fall back to fresh alloc), surface PlanError::Alias.

T7 — Integer overflow in shape / index math

  • Vector: shape product overflow (∏ dims > i64), stride computation overflow, split factor × extent overflow, byte-size numel·sizeof(dtype) overflow → undersized alloc + OOB.
  • Mitigation: checked arithmetic (checked_mul/checked_add) on ALL shape/stride/byte computations in tc-graph, tc-ir, tc-runtime; overflow = reject at the boundary, never wrap.
  • Detection: OverflowError{op,operands} at import / plan / alloc.
  • Telemetry: overflow rejection counts by site.
  • Recovery: reject model/allocation; no allocation proceeds on an overflowed size.

T8 — Supply-chain risk

  • Vector: compromised crate dependency, trojaned cc, drifting toolchain producing different/unsafe codegen.
  • Mitigation: deny.toml (cargo-deny: licenses, advisories, banned/duplicate deps); pinned MSRV 1.78; pinned cc version+hash; lockfile committed; reproducible-build target for Module artifacts (same IR + same Target ⇒ same kernel hashes).
  • Detection: cargo-deny CI gate; toolchain hash check at compile start; reproducibility diff in CI.
  • Telemetry: dep advisory hits, toolchain version logged in Module metadata.
  • Recovery: CI blocks on advisory/license/ban; mismatched toolchain refuses to compile.

T9 — Operator mistake (running an untuned / over-tuned schedule)

  • Vector: human ships a Module tuned for the wrong target, or an untuned naive schedule into a perf-critical path, or a schedule tuned past its validated tolerance regime.
  • Mitigation: the Module records its schedule provenance, Target, tune budget used, and the oracle tolerance it was validated at; tcc run/check warn on Target mismatch vs host; tcc check re-runs the oracle on the actual deployment inputs.
  • Detection: target/feature mismatch warning; tolerance metadata absent → check refuses to certify.
  • Telemetry: Module provenance (schedule hash, target, tolerance, GFLOP/s at tune time).
  • Recovery: re-tune for host target; fall back to naive PrimFunc if no validated schedule for the host.

T10 — Schedule-cache poisoning (tuned-config integrity, distinct from T8 supply-chain)

  • Vector: the on-disk ScheduleCache (.tc-cache/schedules.json, keyed by SchedKey) is attacker-writable or corrupted (shared CI cache, compromised artifact store, or a bit-flip) so tcc compile silently applies a malicious/stale ScheduleConfig — e.g. an illegal tile factor, or a schedule tuned for a different Target/shape than the one being compiled now. Distinct from T8 (which covers the cc/crate toolchain, not tuner-produced data).
  • Mitigation: every cache entry is re-validated on load — SchedKey must match (PrimFunc structure, resolved shapes, dtype, Target.arch+features) exactly (§12.2); the loaded ScheduleConfig is re-run through the same schedule legality validator (§19–20) and the per-kernel oracle check (§4.1) before it is trusted, identically to a freshly-measured candidate — a cache hit is never exempt from the correctness gate.
  • Detection: SchedKey mismatch → cache miss (safe, triggers re-tune or falls back to the analytical default schedule); legality-validator or oracle-check failure on a cache hit → CacheIntegrityError, entry evicted.
  • Telemetry: cache hit/miss counts, SchedKey mismatch rate, count of cache hits that failed post-load validation (should be 0 in a healthy cache).
  • Recovery: tcc tune --reset clears the cache; compilation always has a correct fallback (the analytical default schedule) so a poisoned cache degrades performance, never correctness.

26.4 Residual risks & assumptions

  • Trusted cc correctness assumed (a miscompiling pinned compiler is out of scope; mitigated by oracle check on output, which catches value drift but not all UB).
  • Release builds drop kernel bounds checks for performance → rely on schedule-correctness invariant + fuzz/ASan CI coverage; OOB in an un-fuzzed shape regime is a residual risk, bounded by T3 generators.
  • Side-channel / timing leakage from data-dependent control flow in the VM: out of scope (not a confidentiality system).
  • GPU surface (Device::Gpu, Scope::Shared/Thread) deferred — its codegen + driver attack surface is explicitly out of scope this phase.

26.5 Security invariants (asserted, CI-gated)

  1. No GraphNode with ty == None reaches tc-fuse (B1).
  2. Emitted C contains zero user-derived identifiers/strings (B2 static scan).
  3. Every loaded .so matches its recorded source+artifact hash and Target (B3).
  4. Every shipped schedule passed the oracle within recorded tolerance (T5).
  5. No two simultaneously-live tensors share Storage (T6).
  6. All shape/stride/byte arithmetic is checked; overflow ⇒ reject (T7).
  7. All resource caps (T1) are finite and enforced before the work they bound.
