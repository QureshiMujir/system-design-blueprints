Mental Models & First Principles

Six compressed expert insights — the load-bearing abstractions a principal engineer internalizes. Each: the insight, what it predicts, the bug class you write without it, and the § where this blueprint applies it.

MM1 — A PrimFunc is a pure mathematical specification; its schedule is an orthogonal optimization. Insight: TensorExpr defines what is computed (a mapping from output indices to a scalar expression); every legal Schedule is a different strategy for the same mathematical function. Predicts: you can explore thousands of loop orderings without ever re-verifying correctness — only one oracle comparison is needed per compute definition. Bug class without it: engineers hand-tune kernel order and break numerical results by changing reduction grouping; or they conflate "correct loop nest" with "optimal loop nest" and never search. Applied: §8.3 compute/schedule worked example; §11.6 schedule-primitive contract; §6.2 P2 invariant; Phase 7–8 (§19–20).

MM2 — Operator fusion is a memory-traffic problem, not a compute problem. Insight: DL workloads on CPU are predominantly memory-bound for elementwise and reduce ops (arithmetic intensity ≈ O(1)); fusing eliminates intermediate tensor round-trips to DRAM, not FLOPs. Predicts: a 4-op unfused elementwise chain reads/writes the full tensor 8 times (4 reads + 4 writes); fused, it reads once and writes once — an immediate 8× BW reduction independent of compute. Bug class without it: optimizing a memory-bound kernel for throughput by adding vectorization while leaving intermediate tensors materialized, achieving negligible real-world speedup. Applied: §8.5 fusion analysis; §6.5 P5 "fusion eliminates materialization"; Phase 4 (§16) fusion rationale; §4.3 kernel performance targets.

MM3 — Buffer liveness is register allocation on tensors. Insight: the liveness analysis that decides which intermediate tensors can share storage is structurally identical to register allocation in a scalar compiler — live intervals that do not overlap can alias the same storage slot. Predicts: the peak memory requirement equals the maximum simultaneously-live byte count (the "register pressure"), not the sum of all intermediate sizes. Bug class without it: allocating a fresh Storage per intermediate tensor, which causes 2–10× peak memory over the minimum achievable; or reusing a storage slot for two overlapping live ranges, causing a WAR/WAW hazard. Applied: §8.7 MemoryPlan worked example; §7.6 INV-5; §11.8 MemoryPlan; Phase 10 (§22).

MM4 — Two IRs exist because graph-level and loop-level invariants are incompatible. Insight: the Graph IR (whole-tensor dataflow) enforces SSA-like value immutability and type-propagation invariants; TIR (loop-nest) enforces buffer-binding, index-affinity, and scope legality. Mixing them forces every pass to defend both invariant sets simultaneously — the layering cost of a single unified IR. Predicts: passes operating on the wrong IR level are necessarily more complex (a tiling pass on a graph IR must understand TensorType; a shape-inference pass on TIR must understand loop bounds). Bug class without it: CSE implemented on raw TIR instead of the graph — must handle Load/Store aliasing to find equivalent expressions, missing cross-op redundancies that graph-level CSE finds trivially. Applied: §6.3 P3; §8.1–§8.2 IR designs; §3.2 per-box responsibilities; ADR-03.

MM5 — The KernelSig is the entire trust boundary between compiler and runtime. Insight: once a Kernel is compiled to a .so, the only information the runtime can rely on is the KernelSig — pointer order, dtype, rank, and stride layout. The compiled binary is opaque; any discrepancy between KernelSig at the codegen side and at the load side is an ABI bug producing silent memory corruption, not a compile error. Predicts: any change to how CBackend orders parameters (e.g., inputs before outputs vs. interleaved) that is not reflected in the loaded KernelSig causes the executor to pass the wrong pointer as the first argument — wrong result or segfault. Bug class without it: the backend is refactored to reorder buffer arguments for performance reasons, the runtime is not updated, and the mismatch goes undetected until a model produces garbage output on a specific shape. Applied: §6.8 P8; §7.8 INV-7; §11.7 KernelSig; Phase 9 (§21) round-trip test; ADR-07.

MM6 — Determinism requires a fixed parallel-reduction tree, not just a fixed schedule. Insight: IEEE-754 floating-point addition is not associative; parallel reduction (parallel(k) over a reduce axis) changes summation order across threads, producing results that differ from the serial reference by up to O(N·ε) accumulated error. Determinism requires the reduction tree to be fixed (split factor determines the exact partial-sum grouping) so the same floating-point operations happen in the same order every run. Predicts: a thread-pool over a reduce axis that uses work-stealing (dynamic partition) will produce different results across runs due to non-deterministic scheduling — a floating-point non-determinism bug that appears only under load. Bug class without it: tuned reduction kernels pass correctness tests in serial CI but produce flaky tcc check failures under multi-core deployment. Applied: §4.7 determinism; §6.9 P9; §7.3 INV-2 "subtleties"; Phase 8 (§20) parallel on reduce; ADR-17.

Glossary · 50 terms · site-wide glossary

graph IR
High-level functional dataflow IR (Relay-like) in tc-graph. Whole-tensor ops, no loops. Graph { nodes: Arena<GraphNode>, inputs, outputs }; nodes carry GraphOp + Option<TensorType>. SSA-like, immutable post-build, arena + NodeId.
tensor IR (TIR)
Low-level imperative loop-nest IR (TIR-like) in tc-ir. PrimFunc { params: Vec<Buffer>, body: Stmt }; explicit For/Store/Load over Buffers. One PrimFunc per fused group.
operator
A whole-tensor op node in the graph IR: a GraphOp variant (Add, MatMul, Conv2d, Relu, Reduce(..), Call(name), …). Op registry is extensible by name.
dataflow graph
The DAG formed by GraphNode.args: Vec<NodeId> edges. Topological order = execution order. No cycles (control flow lives in tc-vm, not the graph).
tensor expression
TensorExpr (tc-ir): declarative "what is computed" per output element — the compute definition lowered from a fused GraphOp group, independent of loop order (Halide compute/schedule split).
compute/schedule separation
Halide model: TensorExpr = WHAT; Schedule = HOW (loop order, tiling, vectorize, parallel). Invariant: schedule changes alter performance only, never the numerical result.
schedule primitive
A loop-transform op on Schedule (tc-schedule): split, reorder, fuse, tile, vectorize, unroll, parallel, compute_at, inline. Each rewrites the Stage loop structure.
tiling
Schedule::tile(ax, ay, fx, fy) — block two axes into fx×fy tiles (split + reorder composite) for cache locality. Tile sizes are tuning knobs (Phase 12).
loop reorder
Schedule::reorder(&[AxisId]) — permute loop nesting order; e.g. push the reduce axis inward for vectorizable inner loops. Must preserve a valid dependency order.
split/fuse
split(ax, factor) -> (outer, inner) divides one axis into two; fuse(a, b) -> AxisId collapses two adjacent axes into one. Inverse operations; split precedes vectorize/unroll/parallel.
vectorize
Schedule::vectorize(ax) — map an axis to SIMD lanes; the inner extent should equal/divide the lane count. Codegen contract: SimdBackend emits portable-SIMD over that axis.
unroll
Schedule::unroll(ax) — fully expand a (small, static-extent) loop into straight-line code; reduces branch overhead, enables scalar opt.
parallelize
Schedule::parallel(ax) — map an axis to a thread pool; codegen partitions the axis into tiles per worker. Axis must be free of cross-iteration deps (not a reduce axis).
compute_at
Schedule::compute_at(stage, ax) — compute a producer stage inside a consumer loop at axis ax, shrinking intermediate buffers (locality vs recompute trade-off).
inline
Schedule::inline(stage) — substitute a producer's TensorExpr directly into consumers, eliminating its buffer entirely (the elementwise default).
operator fusion
tc-fuse: merge an injective/elementwise chain (+ ≤1 reduce) into a single PrimFunc, removing intermediate tensor materialization. The dominant CPU win.
fusion group
FusionGroup — the set of graph nodes selected to lower into one fused PrimFunc. Produced by FusionPass.
dominator analysis
The fusion grouping algorithm: build the dominator tree of the dataflow graph; a node fuses upward into its immediate dominator's group when fusion rules permit (output reused only within the group).
shape inference
tc-pass analysis propagating TensorType.shape through the graph to a fixed point. Resolves static dims; leaves Dim::Dynamic(name) symbolic for runtime.
type inference
tc-pass analysis assigning each node a TensorType { shape, dtype }; the verifier asserts every GraphNode.ty is Some post-pass.
dynamic shape
Dim::Dynamic(String) — a symbolic dimension unresolved at compile time; materialized at runtime by the tc-vm Interpreter (allocate-on-demand). GraphExecutor requires fully static shapes.
layout transform
Phase 5 pass: rewrite data format (NCHW↔NHWC) + insert layout-convert nodes, cost-aware, to give kernels contiguous/vectorizable access.
canonicalization
Normalizing IR to a single form (commutative operand order, layout, constant position) so later passes (CSE, fusion) match structurally.
constant folding
tc-pass: evaluate subgraphs with all-Const inputs at compile time, replacing them with a Const(TensorData) node.
CSE
Common-subexpression elimination: deduplicate structurally-identical nodes (post-canonicalization) into one, rewiring args.
DCE
Dead-code elimination: drop nodes not reachable backward from Graph.outputs.
algebraic simplification
Rewrite rules: x+0→x, x*1→x, x*0→0, transpose∘transpose→id, reduce/identity folding — applied with canonicalization.
pass manager
PassManager (tc-pass): orders + runs Pass instances (analysis + transform), tracks invalidated analyses, drives to fixed point where required.
lowering
Translating a higher IR to a lower one: graph fusion group → TensorExpr → naive PrimFunc (tc-ir); and scheduled TIR → target source (tc-codegen).
codegen
tc-codegen: CodeGen::emit(&Schedule, &Target) -> Kernel. CBackend emits C source; SimdBackend emits portable-SIMD.
kernel
Kernel { name, source, signature: KernelSig } — one emitted C function realizing one fused PrimFunc.
KernelSig
The stable ABI of a Kernel: ordered pointer params + shape + stride params (no implicit globals), so the runtime can bind NDArrays positionally.
module
Module { kernels: Vec<Kernel>, graph: Graph, plan: MemoryPlan } — the compiled artifact loaded by the runtime / VM.
NDArray
tc-runtime tensor: { storage: Storage, shape, strides, dtype, offset } — a strided view; reshape/slice are zero-copy.
strided view
An NDArray whose strides need not be contiguous; supports zero-copy transpose/slice by adjusting strides/offset without moving bytes.
zero-copy
Producing a new view (reshape, slice, transpose) that shares the underlying Storage — no allocation, no copy.
storage
Storage { ptr, bytes, device } — a ref-counted raw buffer; multiple NDArray views may share one Storage.
allocator
Allocator trait: alloc(bytes) -> Storage / free(Storage). Backs runtime buffer acquisition; pluggable (bump/pool).
memory planning
MemoryPlan — compile-time assignment of which tensors share Storage, computed from buffer liveness over the executor topological order (register-allocation-on-tensors).
buffer liveness
The interval each intermediate tensor is live (first-def → last-use) in topological order; non-overlapping intervals may reuse the same Storage.
graph executor
GraphExecutor (tc-runtime): dispatches Module.kernels in topological order over NDArray bindings. Static shapes only.
bytecode VM
tc-vm Interpreter: executes VmFunc { instrs: Vec<VmInstruction>, num_regs } for dynamic control flow + dynamic shapes, dispatching the same compiled Kernels.
register
A slot in the VM register file (RegId) holding an NDArray or object; VmInstructions read/write registers (LoadConst, AllocTensor, InvokeKernel, …).
closure
Closure (tc-vm): a VmFunc reference + captured registers, enabling first-class function values / dynamic dispatch in the VM.
device
Device enum (Cpu, Gpu deferred). Tags Storage placement; the runtime dispatches kernels per device (CPU-only in scope).
async dispatch
Runtime scheduling of independent ops/kernels concurrently (thread pool); ordering constrained only by dataflow deps + buffer liveness.
cost model
Phase 12: analytical + measured estimator scoring a candidate Schedule (FLOPs, cache footprint, vector utilization) to guide tuning without running every point.
auto-tuning
Phase 12 search over the schedule primitive space (tile sizes, reorder, unroll factors) per fused kernel; selects the best Schedule via the cost model + measurement.
numerical tolerance
The accepted deviation of compiled output from the oracle: f32 rtol 1e-5, atol 1e-6 (documented per dtype). Schedule changes must not exceed it.
oracle
The NumPy-style reference implementation per op/model. Phase 13 conformance asserts compiled output matches the oracle within tolerance (correctness ground truth).
