4.2 Memory Sizing Formula

shard_bytes = (num_experts / world_size) * (d_model * d_ff + d_ff * d_model) * dtype_bytes
capacity_buffer_bytes = capacity * d_model * dtype_bytes * num_experts_per_rank
total_per_rank = shard_bytes + 2 * capacity_buffer_bytes  (double-buffer)
  • dtype_bytes: FP32=4, BF16=2; BF16 halves shard size but requires FP32 accumulator (FFI contract)
  • Constraint: total_per_rank ≤ 0.85 * available_memory (15% headroom for activations, stack, OS)

4.3 Throughput + Latency Model

Stage Dominant cost Scaling
Gate (CPU) Linear projection: O(n_tokens * d_model * num_experts) Parallelizes over tokens
Dispatch Permutation build: O(n_tokens * k) Sequential; < 1 ms for n_tokens ≤ 8192
a2a Bandwidth: (n_tokens * d_model * dtype_bytes) per direction Scales with world_size
Expert GEMM O(tokens_per_expert * d_model * d_ff) Dominant; grouped GEMM amortizes
Combine O(n_tokens * k * d_model) Parallelizes over tokens
Overlap gain Up to 40–60% wall-time reduction Only if GEMM ≥ a2a time

4.4 Scaling Assumptions

  • Vertical: larger d_model/d_ff → proportional GEMM cost; capacity buffer grows linearly
  • Horizontal (EP): adding ranks reduces per-rank GEMM work by world_size; a2a cost grows; crossover point ~8 ranks for typical d_ff=16384
  • Batch scaling: larger n_tokens → better GEMM utilization; dispatch permutation remains O(n_tokens * k)
  • Expert count scaling: more experts → lower utilization per expert (capacity invariant tightens); routing entropy increases; aux-loss weight must increase proportionally

Back-of-Envelope Capacity Model

Starting from §4 System Constraints (E=64, k=2, d_model=4096, d_ff=16384, BF16, n_tokens=2048, EP world_size=8, capacity_factor=1.25).

1. Per-expert token budget:

capacity = ceil(1.25 × 2048 × 2 / 64) = ceil(80.0) = 80 tokens/expert/rank

2. Local expert count per rank:

local_experts = 64 / 8 = 8 experts per rank

3. VRAM for expert weights per rank (BF16):

w_in: [d_ff, d_model] = [16384, 4096] × 2 bytes = 128 MB per expert
w_out: [d_model, d_ff] = [4096, 16384] × 2 bytes = 128 MB per expert
per_expert_weights = 256 MB
local_weights = 8 × 256 MB = 2.0 GB per rank

(…continued)

4. Peak activation memory (dispatch buffers) per rank:
   input buffer = capacity × local_experts × d_model × 2 bytes
                = 80 × 8 × 4096 × 2 = 5.2 MB
   expert_output buffer = same = 5.2 MB
   CombineBuffer = n_tokens × d_model × 2 = 2048 × 4096 × 2 = 16.8 MB
   total activations per rank ≈ 27 MB (dominated by CombineBuffer at full batch)

5. All-to-all bandwidth per rank (uniform routing):
   send_per_rank = capacity × d_model × 2 bytes = 80 × 4096 × 2 = 655 KB per peer
   total_send = (W-1) × 655 KB = 7 × 655 KB ≈ 4.6 MB per forward pass
   at 100 GbE (12.5 GB/s): a2a latency = 4.6 MB / 12.5 GB/s = 0.37 ms
   at NVLink 300 GB/s: a2a latency ≈ 0.015 ms (compute-bound regime)

(…continued)

6. Expert GEMM time per rank (BF16 CPU reference):
   each expert GEMM: [80, 4096] × [4096, 16384] → 80 × 4096 × 16384 × 2 FLOPs
                   = 10.7 GFLOP per expert per direction × 2 (in + out) = 21.4 GFLOP
   local GEMMs: 8 experts × 21.4 GFLOP = 171 GFLOP
   at 1 TFLOP/s CPU (typical AVX-512 BF16 peak): 171 GFLOP / 1000 GFLOP/s = 0.17 s
   at A100 GPU (77.6 TFLOP/s BF16): 171 GFLOP / 77,600 GFLOP/s = 2.2 ms per forward

7. Overlap efficiency target:
   comm_bound: a2a = 0.37 ms; compute = 2.2 ms → compute dominates (good for overlap)
   ideal overlap: hide full a2a behind GEMM → 0% a2a on critical path
   actual overhead (estimated from Phase 8): 10–20% residual comm exposure
   effective forward time ≈ 2.2 ms + 0.2 × 0.37 ms ≈ 2.3 ms (vs 2.57 ms serial)

8. Gate logit GEMM:
   [n_tokens, d_model] × [d_model, E] = [2048, 4096] × [4096, 64]
   FLOPs = 2048 × 4096 × 64 × 2 = 1.1 GFLOP (negligible vs expert GEMM)

(…continued)

9. Aux loss memory overhead:
   AuxLossState: [E] importance + [E] load = 2 × 64 × 4 bytes = 512 bytes
   z_loss: scalar = 4 bytes
   Total aux overhead: < 1 KB — negligible

10. Expert weight activation recompute cost (Phase 6 backward):
    No recompute: store all 8 expert activations = 8 × [80, 16384] × 2 bytes = 21 MB
    Recompute: re-execute w_in GEMM during backward = 21.4 GFLOP × 8 = 171 GFLOP
    Trade-off: 21 MB VRAM vs 2.2 ms re-compute at A100 — storage wins at A100 scale

11. Summary (A100 GPU, BF16, EP=8, E=64, n=2048, k=2, capacity_factor=1.25):
    Weight VRAM per rank:    2.0 GB
    Peak activation VRAM:   ~27 MB
    Gate logit time:         <0.1 ms
    Expert GEMM time:        2.2 ms
    A2A latency (100 GbE):   0.37 ms
    Effective forward:       ~2.3 ms with overlap
    Token drop rate at 3σ:   ~0% (capacity_factor=1.25 provides sufficient headroom)
