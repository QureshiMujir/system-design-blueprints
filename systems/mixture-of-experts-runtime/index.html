In one paragraph

A mixture-of-experts layer (MoE) holds many small feed-forward networks, called experts, and sends each token through only a few of them, so the parameter count grows without the compute per token growing with it (§2.2). This design is a Rust library that runs one such layer: it picks experts for each token, caps how many tokens an expert may take, ships tokens to whichever process owns the expert, runs the experts, and merges the answers (§1, §3.1). It is not a trainer, a tensor library or a serving layer (§1). A model executor or research harness links it, and it is checked against a dense reference computation (§1.4, ADR-14).

The problem, concretely

A dense network pushes every token through the same feed-forward weights. An MoE layer instead holds E experts and gives each token to k of them, so most weights sit idle for any one token (§2.2, §3.1). Doing that naively breaks in four ways, and the blueprint's structure answers each.

First, experts fill unevenly. At perfectly uniform routing each expert sees n_tokens × k / E arrivals, and any imbalance pushes some expert past a buffer sized to that number (MM1). A developer who sets capacity_factor = 1.0 expecting that to suffice then sees 15%+ drop rates (MM1). Buffers are fixed in advance (§6.3), so the design needs a rule for who is turned away: drop the lowest gate weights first, and pass a dropped token's input straight through unchanged (§3.4, §6.1).

Second, experts live on different processes. Expert e sits on rank e % world_size (§6.9), so tokens cross ranks in an all-to-all exchange and come back again (§3.1). If one rank expects different counts than its peer sends, the exchange hangs or truncates data (§7.10, §2.3).

Third, doing communication and compute one after the other leaves hardware idle. The blueprint puts the loss at 40–60% GPU idle for naive ordering (§2.3) and 1.3–2× slower than the dense equivalent when fully serialized (§6.8).

Fourth, the bugs are silent. A wrong permutation or a missing residual path returns the right shape with the wrong values, and only a differential test against the dense reference catches it (§2.3, §6.1, MM6).

How it works, end to end

Follow one batch of tokens through the boxes of §3.1:

    input tokens [n_tokens, d_model]
            |
      [moe-gate] router W_g.x -> logits -> top-k -> softmax weights; noisy/expert-choice; aux + z-loss
            |  RoutingDecision (expert ids + weights)
      [moe-dispatch] capacity check/drop -> build permutation -> scatter tokens into per-expert contiguous buffers
            |  per-expert token batches
      [moe-comm] all-to-all across EP ranks   <->   [moe-sched] overlap a2a with expert GEMM (streams, double-buffer)
            |
      [moe-expert] each expert = FFN: GEMM(w_in) -> activation -> GEMM(w_out); batched/grouped; weights sharded per rank
            |  expert outputs
      [moe-comm] all-to-all back
            |
      [moe-dispatch] combine: un-permute -> gate-weighted sum; dropped tokens take residual passthrough
            |  output tokens [n_tokens, d_model]
      [moe-runtime] orchestrates the whole layer; [moe-telemetry] taps every stage
  1. moe-gate multiplies each token by the gate matrix W_g to get one score per expert (GateLogits), keeps the top k, and turns those k scores into weights that sum to 1 (RoutingDecision). It also accumulates the balance losses into AuxLossState (§3.3, §8.3).
  2. moe-dispatch computes the per-expert limit Capacity, rejects overflow, and builds a DispatchPlan: a permutation, per-expert counts and a bitset of dropped tokens. It then copies tokens into one contiguous block per expert (§3.4, §8.5).
  3. moe-comm runs the all-to-all that moves each block to the rank owning that expert. An EpGroup { rank, world_size, transport } describes the group; transports are InProc, SharedMem and a deferred Ucx stub (§3.5). With world_size == 1 the exchange is skipped (I11, §7.11).
  4. moe-sched overlaps that communication with the expert math by splitting the batch into micro-batches and using two buffer slots (§3.6, §8.7).
  5. moe-expert runs each local expert's two-matrix network, batched across experts, on weights that only this rank holds (§3.7, §8.8). A second all-to-all returns the results (§3.1).
  6. moe-dispatch combines: undo the permutation, multiply by gate weights, add up. Dropped tokens get their input back (§3.4, §8.9).
  7. moe-runtime owns all of that behind one call, MoeLayer::forward(input, aux_state) -> Result<Tensor, MoeError>, and moe-telemetry records every stage without ever blocking the pass (§3.8, §3.9). moe-core supplies the shared types, the arena allocator and MoeError (§3.10). moe-cli and moe-bench are the driver and the benchmark/differential harness (§1.6).

Each stage hands the next a typed struct and shares no mutable global state (§3.2). The lifecycle of a single token is a state machine: gate scored, routed, capacity check (to dispatched or dropped), in transit, at expert, computing, result in transit, combining, output. A dropped token jumps from the check straight to output (§8.2).

The core ideas

Top-k gating: choose a few experts, then renormalise (§8.3, §8.13)

Each token gets E scores, row-major, shape [n_tokens, num_experts]. The router keeps the k best and runs softmax over only those, so the weights sum to 1 (§8.3). Ties go to the lower ExpertId; that is why two tokens with identical logits for all 64 experts both get experts 0 and 1 (§8.13, hard question 4). Four variants change what happens before top-k (§8.3):

Variant Change before top-k
Dense top-k none
Noisy top-k add noise scaled by softplus(W_noise·x) per expert
Expert-choice transpose: each expert picks its top tokens
Softmax-all none, with k equal to the number of experts (the dense reference)

Balance is pushed by two penalties kept in AuxLossState: an importance/load loss, and the z-loss, log(sum(exp(logits)))^2, which keeps logits small (§8.3).

Capacity and dropping: a fixed shelf per expert (§3.4, §8.4)

Each expert gets Capacity = ceil(capacity_factor × n_tokens × k / num_experts) slots. The blueprint's example: 1024 tokens, k=2, 8 experts, factor 1.25 gives ceil(320) = 320 slots per expert (§8.4). Within one expert's queue, tokens sort by gate weight, highest first. The first Capacity are admitted. The rest are marked in DispatchPlan.dropped. Equal weights are broken by lower TokenIdx (§8.4). The rounding is ceil, which the blueprint calls load-bearing for correctness (§2.9, hard question 2). A factor under 1.0 drops tokens even for perfectly balanced routing and is for memory-pressure experiments (§8.4), while §4.1 calls a factor under 1.0 an invariant violation. Infinite capacity disables dropping and is only for correctness tests (§8.4).

Permutation and combine: scatter out, weighted sum back (§8.5, §8.9)

perm[out_pos] = token_idx lays tokens out so each expert's tokens are contiguous, starting at offset[e] = sum(per_expert_counts[0..e]) (§8.5). The blueprint's own trace (4 tokens, k=2, 2 experts, 3 slots each):

Token Picks (expert: weight) Outcome
0 e0: 0.7, e1: 0.3 admitted to both
1 e1: 0.6, e0: 0.4 rejected by e0, kept by e1
2 e0: 0.5, e1: 0.5 admitted to both
3 e0: 0.9, e1: 0.1 kept by e0, rejected by e1

The result is per_expert_counts = [3, 3] and perm = [3, 0, 2, 1, 2, 0]: expert 0's block holds tokens 3, 0, 2 and expert 1's holds 1, 2, 0 (§8.5). On the way back, the kept weights of a token are divided by their own sum, so token 1 uses expert 1 alone at weight 1.0 and token 3 uses expert 0 alone at weight 1.0 (§8.5, §8.9). A token whose experts all rejected it gets output = input (§8.9). Without the renormalisation the output is scaled down (hard question 10).

All-to-all: a symmetric transpose, not a send and a receive (§8.6, MM2)

Before the data moves, ranks swap their per-expert counts, check that what rank A will send to rank B equals what B expects from A, and abort with A2ACountMismatch if not (§8.6, I10). §7.10 calls the same error AsymmetricA2ACounts; §3.5 and §11.14 spell it A2aCountMismatch. The data then moves as contiguous blocks [rank_0_tokens | rank_1_tokens | …] (§3.5). MM2's picture: before the exchange each rank holds a row-slice of the token-by-expert assignment, afterwards a column-slice, so a rank that receives more than it sent is explained by imbalance, not by a bug (MM2). The experts then run, and a reverse all-to-all brings outputs home (§8.6).

Overlap: keep two buffers in flight (§8.7, MM4)

Two streams run side by side: a comm stream and a compute stream. The rule: the GEMM for micro-batch N starts only after its all-to-all completes, and the all-to-all for micro-batch N+1 may run during the GEMM for N (§8.7). Two buffer slots alternate, so one is never read and written at once (§3.6, §6.13). MM4 spells out the four CUDA-event steps: compute records A, comm waits on A before sending, comm records B, compute waits on B before the next GEMM. Dropping one gives races or hangs (MM4). If both slots are busy, §8.7 says the scheduler blocks and surfaces SchedulerStall; §6.5 says a full queue returns QueueFull and never blocks silently.

Determinism: same input, same routing (§8.13, I3)

Five rules make routing reproducible: fixed floating-point order in the gate; stable top-k with ties to lower ExpertId; seeded noise; capacity assignment by weight then TokenIdx; perm built by expert then token order (§8.13). Parallel top-k sorts, GPU atomic reductions and non-deterministic NCCL reductions must be suppressed in deterministic mode (§8.13). Without this, two identical batches route differently and ranks disagree (§6.2). The seed recipe is stated three ways: from (batch_id, layer_id, token_idx) in §6.2 and §7.3, as layer_idx * 1337 + token_idx in §8.13, and from (layer_idx, step_idx, rank) in the Threat Model.

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust, edition 2021, MSRV 1.78, for no GC tail-latency, safe FFI to BLAS/CUDA and zero-cost abstractions (ADR-01, §1.9). Rejected: C++, Python, Go, Julia (ADR-01). When the rejected choice is right: Python, when the team cannot hire Rust engineers and velocity matters more than throughput, for a research prototype of 100M tokens/day or less (ADR-01).

GEMM backend: cblas-sys plus cudarc (ADR-04)

Chosen: cblas-sys for CPU and cudarc for CUDA, selected by conditional compilation, so the matrix-multiply library sits behind an explicit foreign-function boundary (ADR-04, §6.7). Rejected: hand-written CUDA bindings, other BLAS wrappers, tch-rs (too heavy). When the rejected choice is right: tch-rs, when attention, layer-norm and optimizer ops from PyTorch are needed in the same binary (ADR-04).

Tensor storage: an arena-backed Tensor (ADR-05)

Chosen: a moe-core Tensor handle carved from an arena, with explicit device, dtype and layout (ADR-05, §3.10). Buffers are pre-sized so no allocation happens on the hot path (§6.3). Rejected: ndarray, tch-rs/candle, raw pointers. When the rejected choice is right: ndarray, when the project targets only CPU, needs no FFI, and prefers its slicing and broadcasting ergonomics to control (ADR-05).

Async runtime: tokio (ADR-06, ADR-07)

Chosen: multi-thread tokio for comm and scheduler coordination, with tokio::sync::mpsc and crossbeam channels between stages (ADR-06, ADR-07). Rejected: async-std, rayon, smol; raw mutex/condvar, actor frameworks, lock-free queues. When the rejected choice is right: rayon, when all parallelism is CPU compute with no I/O and no CUDA events (ADR-06); an actor framework, when messages are rich typed variants needing supervision (ADR-07).

Multi-process comms: MPI, NCCL and an always-built InProc (ADR-08)

Chosen: MPI behind a feature flag, NCCL via cudarc, and InProc always compiled in for single-node tests (ADR-08). Rejected: gRPC (latency), custom TCP (upkeep), UCX bindings (immature in Rust). When the rejected choice is right: gRPC, when ranks span cloud VMs with mixed network fabrics and the collective volume is under 1 GB per forward pass (ADR-08).

Testing: unit, integration and a differential harness (ADR-14)

Chosen: unit and integration tests plus moe-bench comparing against a dense reference at capacity=inf, k=E (ADR-14, §6.10). Rejected: property-based testing alone (misses numerical regressions), snapshot tests alone (brittle). When the rejected choice is right: property-based alone, for purely algebraic parts such as permutation invertibility, where no reference implementation exists (ADR-14). The required match is stated three ways: within 1e-5 L∞ (ADR-14), within atol=1e-3, rtol=1e-3 (§7.5), and at most 1e-4 for f32 in Phase 13 (§25).

Roads not taken

Block-sparse GEMM, Megablocks-style (Alt-1): one kernel over expert blocks padded to a tile. It wins at very large E (256 or more), high k (4 or more) and an A100-class GPU with block-sparse kernels. It was rejected because it needs a CUDA-native kernel and does not run on the CPU reference path (Alternative Architectures, Alt-1).

Expert-choice routing (Alt-2): each expert picks its tokens, which gives even expert use and no drops. It wins for training where balance matters more than latency and no token loss is tolerable. It needs the whole score matrix before dispatch can start, so it is a Phase 9 variant, not the default (Alternative Architectures, Alt-2; MM5; §21).

All-dense MoE (Alt-3): every expert sees every token, no dispatch at all. It wins for E of 4 or fewer, tiny FFNs, or interpretability studies. At E=64 it costs 64 times a dense FFN, so here it is only the test baseline (Alternative Architectures, Alt-3).

Hierarchical two-tier all-to-all (Alt-4): intra-node exchange first, inter-node second. It wins for E of 64 or more, world_size of 16 or more and mixed fabrics. It is deferred, with a trigger of world_size of at least 16 and inter-node bandwidth under 100 Gb/s (Alt-4, Deferred Features Register).

The register also defers live expert-parallel resizing, non-uniform expert placement, adaptive k and INT4 weights, each with its own trigger (Deferred Features Register).

What must never be false

The blueprint numbers its twelve invariants §7.1 to §7.12, and other sections cite them as I1 to I12 (§5.1, MM2).

  • I1 every token leaves exactly once: expert path with weights summing to 1 within ±1e-5, or untouched copy if dropped (§7.1); the same section's detection check accepts sums in [0.999, 1.001]. Noticed by a differential test against the dense reference; tokens_dropped_total, gate_weight_sum_histogram.
  • I2 no expert ever holds more than Capacity tokens (§7.2). Noticed by debug_assert! in dispatch and forced-drop tests; expert_buffer_utilization, capacity_overflow_events_total.
  • I3 fixed (input, seed, config) gives identical routing and plan, across restarts (§7.3). Noticed by hashing two identical passes; routing_entropy_bits, with entropy under 0.5 bits as the red flag.
  • I4 expert e lives on rank e % world_size, fixed for the layer's life (§7.4). Noticed by a checksum of received token indices; a2a_send_recv_count_mismatch_total. Fatal.
  • I5 combine equals the gate-weighted sum of expert outputs, within atol=1e-3, rtol=1e-3 of the dense reference (§7.5). Noticed by moe-bench --differential; combine_l_inf_error.
  • I6 the scheduler never deadlocks: every all-to-all finishes, every stream drains, a buffer swap happens within timeout_ms (default 5000 ms) (§7.6). Noticed by a watchdog; stream_timeout_total.
  • I7 every local expert has complete weights at start-up, with no partial shard (§7.7). Noticed by shape and checksum validation at load; weight_shard_checksum_mismatch_total.
  • I8 aux loss accumulates non-negative values each forward pass and is reset exactly once per optimizer step, with no double accumulation (§7.8). Noticed by a step-token assertion; aux_loss_value, z_loss_value.
  • I9 gate logits are finite and within [-30, +30] by default before softmax (§7.9); the Threat Model clamps to [-1e4, 1e4] instead. Noticed by an is_finite check; gate_logit_nan_total, gate_logit_clamp_events_total.
  • I10 for each rank pair, count sent equals count expected (§7.10). Noticed by verify_symmetric_counts before every exchange; a2a_count_verify_failures_total.
  • I11 with world_size == 1 the exchange is a no-op and the result equals the multi-rank path (§7.11). Noticed by a single-rank vs multi-rank differential test; ep_world_size, a2a_noop_total.
  • I12 gradients through dispatch and gate are finite, and dropped tokens contribute none (§7.12). Noticed by a finiteness check after backward; grad_norm, nan_grad_events_total.

What breaks in production

The failure section groups failures into classes A to J rather than numbering them as individual modes (Failure Modes & Recovery). The most instructive:

  • Routing wrong without crashing (Class A). Output diverges from the reference; entropy collapses. Root causes: NaN in gate logits, a bad top-k index, weights not summing to 1. Detected by the differential fixture and an entropy threshold. There is no auto-recovery: wrong output propagates silently, so the fix is a --debug-routing dump compared with a reference gate.
  • Too many tokens dropped (Class B). Drop rate rises, quality falls, and dropped tokens pass through silently. Causes: factor too low, load imbalance, a noisy top-k seed mismatch. Detected by the drop-rate metric and utilisation histogram. Recovery is by design (lowest weight first); the operator raises the factor or tunes the balance loss. The blueprint gives thresholds that differ: alert above 0.1 per step (Class B), above 0.05 (Threat Model, resource exhaustion), and a failure budget of 5% at factor 1.25 (§4.1). The rate itself is dropped tokens over n_tokens × K in §8.14 but over n_tokens in Phase 12 (§24).
  • All-to-all hangs or times out (Class D). A rank fails mid-exchange, the network partitions, or buffer sizes disagree. Detected by a comm_timeout_ms deadline, a heartbeat and asymmetric-count checks. Transient timeouts retry up to three times with backoff of 1, 2 and 4 seconds, while §4.1 says MoeError returns within 10 ms of any transport failure; the blueprint does not reconcile the two. On a dead rank, §6.14 drops the affected tokens to residual, §8.11 kills the batch and escalates, and Class D has an operator restart the rank.
  • Out of memory (Class F). Arena undersized, or a double-buffer allocation at peak. Detected by a pre-check at init. Overflowing dispatch buffers is caught by the capacity rule (tokens are dropped), not by an OOM. Hard OOM has no auto-recovery; reduce batch or experts per rank.
  • Scheduler deadlock (Class G). The process hangs and counters stop. Cause: streams waiting in a cycle or a buffer swap that never fires. A watchdog aborts after a default 30 s of zero progress and leaves a core dump; the operator restarts. The dependency graph is cycle-checked at scheduler init (Class G, §3.6).
  • Weight corruption (Class E). A partial write, filesystem damage or a hand edit. Detected by SHA-256 and CRC32 header checks at load. No auto-recovery; restore the last good checkpoint. Writes are write-then-rename to avoid the partial case.
  • FFI panic in the GEMM backend (Class J). The process aborts with no MoeError, because a panic crossing the foreign-function boundary is undefined behaviour. Causes: ABI mismatch or a binary built for the wrong CPU features. Only the parent supervisor sees the exit code. The mitigation is pinning the BLAS version and testing every supported CPU feature level.

The Threat Model lists no numbered threats; five rows from its attack surface table:

  • Oversized capacity_factor in the config can cause OOM; defence is schema validation with numeric bounds (0 < factor <= 10 there, against 1.0–2.0 in §4.1) and rejection at start-up.
  • Crafted weight-file strides could read outside the mapped region; defence is a stride bound check at Tensor construction.
  • Fabricated cross-rank counts could overflow capacity on a remote rank; peers are same-job and counts are validated before use.
  • A predictable noisy top-k seed could steer all tokens to one expert; the seed is never user-settable and an entropy drop raises an alert.
  • Replayed routing (a stale plan at a later step) is rejected by step-id monotonicity checks.

Memory per rank is shard_bytes + 2 × capacity_buffer_bytes for double buffering, with capacity_buffer_bytes = capacity × d_model × dtype_bytes × experts_per_rank (§4.2). Overlap can cut wall time by 40–60%, but only if the GEMM takes at least as long as the all-to-all (§4.3).

Two points the blueprint does not reconcile. Its overlap target is at least 0.7 at batch 512 or more in §6.8, but at least 0.4 at two micro-batches in Phase 8's acceptance criteria (§20) and Appendix B, and the Deferred Features Register uses under 0.7 at depth 2 as a trigger. The metric is defined as hidden comm time over total comm time in §6.8 but as gemm_us / (gemm_us + exposed_a2a_us) in §8.14. And MM3 says a factor of at least 1.26 covers 3σ of load at 4096 tokens, E=64, while the capacity model reports about 0% drops at 1.25 for 2048 tokens (MM3, capacity model item 11).

How it compares

  • GShard (TPU-native) pioneered the capacity factor with deterministic drop-by-weight, which this runtime implements the same way. It leaves overlap to the XLA compiler, which also enforces count symmetry through shape analysis, so it needs no user-visible streams; this runtime does the same checking with I10 instead (Comparative Architecture Table).
  • Switch Transformer routes top-1 with capacity set to twice the even share and does not overlap communication with compute. It showed k=1 routing is viable with careful capacity tuning, and k=1 appears here as a stress test of the gate (Comparative Architecture Table).
  • Mixtral 8×7B uses top-2 and leaves expert parallelism to the host framework; its capacity factor is not published. This runtime requires explicit configuration rather than a silent default for that reason (Comparative Architecture Table).
  • DeepSpeed-MoE adds a shared (residual) expert and hierarchical expert parallelism for very large worlds. The shared expert absorbs routing variance at the cost of one extra dense FFN pass per token. This design takes the shared expert (§8.10), defers the two-tier exchange, and declines the 50–100 µs per layer of a Python dispatch loop (Comparative Architecture Table).

Questions to test yourself

  1. Why does the capacity formula use ceil() rather than floor(), and what invariant would be violated if you used floor()? — Hint: I1 and I2 (§7.1, §7.2); the formula itself is in §3.4.
  2. If rank 3 in an 8-rank EP group fails mid-forward-pass while the all-to-all is in progress, what is the exact sequence of events in moe-comm and moe-runtime, and which invariants must still hold? — Hint: §6.14, §7.10, §23, and the rank-failure notes in §8.11.
  3. Why is the combine step not simply a sum over expert outputs, and what exact check would reveal a bug where the gate weights were not renormalized after a token was partially dropped? — Hint: §8.9, §7.1 and §7.5.
  4. How does the double-buffer state machine in moe-sched prevent a data race between the a2a receive and the combine step without a mutex? — Hint: §8.7, §6.13, I6 (§7.6) and MM4.
  5. How does the per-rank expert ownership formula expert_id % world_size interact with a non-power-of-two expert count like E=48, W=8, and what load imbalance results? — Hint: §6.9, I4 (§7.4) and §8.11.

If you only remember three things

Every token is either processed by up to k experts with weights that add to 1, or handed back unchanged, and the capacity limit is what decides which (I1, I2, MM6). The all-to-all only works when both sides agree on the counts beforehand, and the permutation and the ownership rule e % world_size are what make them agree (I4, I10, MM2). Overlap is explicit double-buffering plus event ordering, and all of it is only trusted once a differential test against the dense reference passes (§6.8, MM4, §6.10).

Words used here

  • Expert: one small feed-forward network inside the layer; only some run for any token.
  • Gate / router: the linear step that scores every expert for each token.
  • Top-k: keep the k highest-scoring experts per token; k is typically 2–4 (§4.1).
  • Capacity: the most tokens one expert may take per pass, from the capacity factor formula.
  • Capacity factor: headroom multiplier on the even share; 1.25 means 25% spare room.
  • Dropped token: a token turned away at capacity; it passes through as its own input.
  • Residual passthrough: the identity path that gives a dropped token output = input.
  • DispatchPlan: permutation, per-expert counts and dropped bitset for one pass.
  • Permutation: the index array that packs tokens into per-expert blocks and unpacks them.
  • Expert parallelism (EP): spreading experts over processes, with expert e on rank e % world_size.
  • All-to-all (a2a): every rank sends a distinct shard to every other rank, and the reverse afterwards.
  • GEMM / grouped GEMM: matrix multiply; the grouped form handles many experts' ragged batches in one call.
  • Z-loss: a penalty on large router logits that keeps softmax numerically sane.
  • Routing entropy: how evenly load spreads over experts; low entropy signals that routing has collapsed onto a few experts.
  • Micro-batch: a slice of the batch pipelined so one slice's communication hides behind another's math.
