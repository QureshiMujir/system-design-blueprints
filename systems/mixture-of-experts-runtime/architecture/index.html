3. Architectural Overview

3.1 Canonical Architecture Diagram

    input tokens [n_tokens, d_model]
            |
      [moe-gate] router W_g.x -> logits -> top-k -> softmax weights; noisy/expert-choice; aux + z-loss
            |  RoutingDecision (expert ids + weights)
      [moe-dispatch] capacity check/drop -> build permutation -> scatter tokens into per-expert contiguous buffers
            |  per-expert token batches
      [moe-comm] all-to-all across EP ranks   <->   [moe-sched] overlap a2a with expert GEMM (streams, double-buffer)
            |
      [moe-expert] each expert = FFN: GEMM(w_in) -> activation -> GEMM(w_out); batched/grouped; weights sharded per rank
            |  expert outputs
      [moe-comm] all-to-all back
            |
      [moe-dispatch] combine: un-permute -> gate-weighted sum; dropped tokens take residual passthrough
            |  output tokens [n_tokens, d_model]
      [moe-runtime] orchestrates the whole layer; [moe-telemetry] taps every stage

3.2 Data Flow Summary

Every stage is a pure function over typed buffers. No shared mutable global state between stages. Each arrow is a typed Rust struct crossing a crate boundary.

GateLogits -> RoutingDecision -> DispatchPlan -> [per-expert Tensor batches]
-> [a2a out-buffer] -> [expert output Tensors] -> [a2a in-buffer]
-> CombineBuffer -> output Tensor

3.3 moe-gate — Gating / Router

  • Responsibility: compute per-token expert scores; select top-k; produce RoutingDecision
  • Inputs: input: Tensor[n_tokens, d_model], W_g: Tensor[d_model, num_experts]
  • Outputs: GateLogits[n_tokens, num_experts] (pre-softmax); RoutingDecision[n_tokens]
  • Operations: linear projection → optional Gaussian noise injection (noisy top-k) → top-k selection → softmax over selected → expert-choice variant (transpose: expert selects tokens) → aux importance loss + z-loss accumulation into AuxLossState
  • Concurrency boundary: CPU-side pure compute; embarrassingly parallel over token dimension; no shared state
  • Failure modes: NaN in logits → MoeError::NanInLogits; all experts over capacity → all tokens dropped (catastrophic — monitored)
  • Invariant: sum of gate weights over kept experts = 1.0 per token (softmax renormalization after drop)
  • Rejected alternative: argmax routing (top-1) — supported as k=1 special case; not a separate code path

3.4 moe-dispatch — Token Dispatch + Combine

  • Responsibility: enforce capacity invariant; build DispatchPlan; scatter tokens into per-expert contiguous buffers; on return path, un-permute and gate-weight-sum
  • Inputs: RoutingDecision, input: Tensor[n_tokens, d_model], capacity: Capacity
  • Outputs (dispatch): DispatchPlan (permutation + per_expert_counts + dropped bitset); per-expert Tensor views
  • Outputs (combine): output: Tensor[n_tokens, d_model]
  • Capacity math: Capacity = ceil(capacity_factor * n_tokens * k / num_experts); tokens exceeding per-expert buffer dropped deterministically (lowest gate weight first, tie-break by TokenIdx)
  • Scatter: perm[i] = position of token i in the permuted buffer; contiguous per-expert sub-slices
  • Dropped token handling: residual passthrough — output[dropped_token] = input[dropped_token]; no zero-fill
  • Concurrency boundary: permutation build is sequential (O(n_tokens * k)); scatter/gather parallelizable via Rayon
  • Failure modes: perm length mismatch → panic in debug, MoeError in release; capacity=0 → all dropped

3.5 moe-comm — Collective Communication

  • Responsibility: all-to-all token exchange across EP ranks (pre-expert and post-expert); all-reduce for aux losses
  • Transport variants:
    • InProc: Arc<Mutex<Vec<u8>>> ring per rank pair (single-process EP emulation)
    • SharedMem: posix shm segments (multi-process, same node, Phase 3)
    • Ucx stub: PhaseDeferred("Phase 7")
  • all-to-all semantics: each rank sends send_counts[r] tokens to rank r; receives recv_counts[r] tokens from rank r; counts must be symmetric (EP consistency invariant)
  • Buffer layout: [rank_0_tokens | rank_1_tokens | ... | rank_{W-1}_tokens] contiguous; offsets from per_expert_counts
  • EpGroup: { rank: u32, world_size: u32, transport: Transport }; initialized once at MoeLayer construction
  • Failure modes: asymmetric counts → MoeError::A2aCountMismatch; transport timeout → MoeError::CommTimeout; deadlock on barrier if any rank crashes — detected via watchdog (Phase 5)
  • Protocol boundary: transport trait object; send / recv / barrier as async methods

3.6 moe-sched — Execution Scheduler

  • Responsibility: schedule comm/compute overlap via streams; double-buffer micro-batches; track inter-stage dependencies
  • Core abstraction: Stream (CUDA stream or CPU thread pool queue); WorkItem enum (CommOp, GemmOp, CombineOp)
  • Overlap strategy: while all-to-all for micro-batch N is in-flight, execute GEMM for micro-batch N-1 on separate stream; requires double-buffer (two CombineBuffer slots)
  • Dependency tracking: DAG of WorkItem nodes; edges enforce: a2a-complete before GEMM-start; GEMM-complete before combine-start
  • Double-buffer invariant: buffer slot alternates per micro-batch index; never read and write same slot concurrently
  • Micro-batch pipelining: split n_tokens into P micro-batches; pipeline depth = 2 (can extend to 3, PhaseDeferred("Phase 8"))
  • Failure modes: stream sync timeout → MoeError::StreamTimeout; DAG cycle (bug) → detected at construction, not runtime
  • Concurrency boundary: scheduler thread owns stream handles; worker threads execute ops; channels for completion signals

3.7 moe-expert — Expert FFN Module

  • Responsibility: execute per-expert FFN for a batch of tokens assigned to that expert; manage expert weight shards
  • FFN structure: GEMM(w_in: [d_model, d_ff]) -> activation -> GEMM(w_out: [d_ff, d_model])
  • Weight storage: ExpertWeights { w_in: Tensor, w_out: Tensor }; sharded across EP ranks: expert e lives on rank e % world_size; each rank stores only its shard
  • GEMM dispatch: CPU path → OpenBLAS sgemm via FFI; GPU path → cuBLASLt grouped GEMM via FFI (Phase 2+)
  • Batched/grouped GEMM: variable token counts per expert → padding to power-of-2 or Megablocks block-sparse strategy (PhaseDeferred("Phase 5"); see Alternative Architectures Alt-1)
  • Activation: SwiGLU (default), GELU, ReLU — selected at MoeLayer config; applied element-wise between GEMMs
  • Concurrency boundary: each expert is independent; experts on same rank can execute in parallel (thread pool)
  • Failure modes: zero tokens assigned → skip GEMM, return empty Tensor; weight shape mismatch → MoeError::ShapeMismatch

3.8 moe-runtime — Layer Orchestrator

  • Responsibility: single public API MoeLayer::forward(input, aux_state) -> Result<Tensor, MoeError>; owns all sub-components; orchestrates gate→dispatch→a2a→expert→a2a→combine sequence
  • Owns: Gate, Dispatcher, EpGroup, Scheduler, ExpertShards, Telemetry
  • Construction: MoeLayer::new(config: MoeConfig, weights: ExpertWeights, ep_group: EpGroup) -> Self
  • Forward pass contract: stateless w.r.t. token data; AuxLossState accumulates across forward calls; reset explicitly
  • Error propagation: ? operator; any sub-error surfaces as MoeError variant; no panics in release build
  • Trust boundary: caller supplies input: Tensor; runtime validates shape, dtype, device before any computation
  • Concurrency model: MoeLayer is Send + Sync; multiple threads may call forward on different micro-batches; internal scheduler serializes stream ops

3.9 moe-telemetry — Observability

  • Responsibility: capture per-forward-pass metrics; expose Prometheus-compatible counters + histograms; emit tracing spans
  • Metrics: expert utilization (tokens/expert / capacity), drop rate (dropped/total), routing entropy (Shannon entropy over gate weights), a2a latency (µs), GEMM latency (µs/expert), combine latency (µs)
  • Tracing spans: one root span per forward call; child spans per stage (gate, dispatch, a2a-out, expert, a2a-in, combine)
  • Tap points: telemetry receives typed events via channel from each crate; zero-copy (pass references, not clones)
  • Failure modes: telemetry channel full → drop metric (non-blocking); never block forward pass for metrics

3.10 moe-core — Shared Types

  • Responsibility: define all cross-crate types; no logic except constructors + invariant assertions
  • Arena: bump allocator for Tensor storage; owned by MoeLayer; freed at layer teardown
  • MoeError: typed enum covering all failure variants; implements std::error::Error; no string-only errors
  • Layout: { strides: SmallVec<[usize; 6]>, offset: usize }; supports non-contiguous tensors for combine views

8.3 GateLogits Format and RoutingDecision

GateLogits layout: row-major f32, shape [n_tokens, num_experts]
  token_0: [l_0, l_1, ..., l_{E-1}]
  token_1: [l_0, l_1, ..., l_{E-1}]
  ...

RoutingDecision per token (after top-k + softmax-over-topk):
  topk: [(ExpertId(e0), w0), (ExpertId(e1), w1), ..., (ExpertId(e_{k-1}), w_{k-1})]
  invariant: w0 + w1 + ... + w_{k-1} = 1.0 (renormalized over kept experts)
  invariant: e0 < e1 < ... < e_{k-1}  (sorted ascending for determinism)

Gate variants and their mutation of GateLogits:

Variant Mutation before top-k AuxLoss fields used
Dense top-k none importance, load
Noisy top-k add N(0, softplus(W_noise·x)) per expert importance, load
Expert-choice transpose; each expert picks top-c tokens token_counts only
Softmax-all (dense MoE reference) none; k = num_experts none

AuxLossState layout:

  • importance: Vec<f32> — per-expert sum of gate weights over all tokens; len = num_experts.
  • load: Vec<f32> — per-expert fraction of tokens routed; len = num_experts.
  • z_loss: f32 — log(sum(exp(logits)))^2 term (ST-MoE); promotes logit smallness.
  • aux_loss: f32 — dot(importance_norm, load_norm) * alpha (Switch / GShard balance loss).

8.4 Capacity and Drop Semantics

Capacity = ceil(capacity_factor * n_tokens * K / num_experts)

Example: n_tokens=1024, K=2, num_experts=8, capacity_factor=1.25
  Capacity = ceil(1.25 * 1024 * 2 / 8) = ceil(320) = 320 slots per expert

Drop policy (moe-dispatch):

  • Tokens sorted by gate weight descending within each expert queue.
  • First Capacity tokens admitted; remainder marked in DispatchPlan.dropped (BitSet over TokenIdx).
  • Tie-break: if gate_weight equal, lower TokenIdx wins → routing determinism.
  • Dropped tokens: output = input (residual passthrough); combine weight = 0.
  • capacity_factor=inf → no dropping; buffer pre-allocated to n_tokens (unsafe memory use; only for correctness testing).

Edge cases:

  • All tokens route to same expert → (num_experts-1) experts get 0 tokens; valid but inefficient.
  • K=1, capacity_factor=1.0 → exactly balanced expected load; any imbalance causes drops.
  • capacity_factor < 1.0 → always some dropping even in perfectly balanced routing; use only for memory pressure experiments.

8.5 DispatchPlan Layout

DispatchPlan {
  perm:              Vec<u32>,        // length = sum(per_expert_counts); scatter permutation index into input token buffer
  per_expert_counts: Vec<u32>,        // length = num_experts; tokens assigned to each expert after drop
  dropped:           BitSet,          // length = n_tokens; bit set = token dropped
  capacity:          Capacity,        // Capacity value used for this plan
}

Permutation semantics:

  • perm[out_pos] = token_idx where out_pos is position in contiguous per-expert buffer.
  • Per-expert buffer starts at offset[e] = sum(per_expert_counts[0..e]).
  • Invariant: perm contains no duplicates; perm.len() = sum(per_expert_counts).
  • Combine reverse: output[perm[i]] += weight * expert_out[i] (accumulate K contributions per token).

Worked example (n_tokens=4, K=2, num_experts=2, capacity=3):

Token 0 → experts [0, 1], weights [0.7, 0.3]
Token 1 → experts [1, 0], weights [0.6, 0.4]
Token 2 → experts [0, 1], weights [0.5, 0.5]
Token 3 → experts [0, 1], weights [0.9, 0.1]

Expert 0 queue (by weight desc): tok3(0.9), tok0(0.7), tok1(0.4), tok2(0.5)
  → sorted: tok3, tok0, tok2, tok1 (0.9, 0.7, 0.5, 0.4); capacity=3
  → admitted: tok3, tok0, tok2; drop tok1 from expert-0 slot

Expert 1 queue: tok1(0.6), tok0(0.3), tok2(0.5), tok3(0.1)
  → sorted: tok1, tok2, tok0, tok3; capacity=3
  → admitted: tok1, tok2, tok0; drop tok3 from expert-1 slot

per_expert_counts = [3, 3]
perm = [3, 0, 2, 1, 2, 0]   // expert-0 block: toks 3,0,2; expert-1 block: toks 1,2,0
dropped = { tok1 ∩ expert-0, tok3 ∩ expert-1 } — token-level drop only if ALL k slots dropped
  tok1: expert-0 dropped, expert-1 admitted → tok1 still processed (partial drop)
  tok3: expert-0 admitted, expert-1 dropped → tok3 still processed (partial drop)
  → combine: tok1 output = w_{1,1}*exp1_out + residual*(1 - w_{1,1})? NO.
  → SPEC: weights renormalized over admitted experts only; dropped expert contributes 0.
  tok1 admitted only to expert-1 with w=0.6; renormalized weight = 1.0 (only kept expert).
  tok3 admitted only to expert-0 with w=0.9; renormalized weight = 1.0.

8.6 All-to-All Protocol (moe-comm)

EP group topology:

  • EpGroup { rank: u32, world_size: u32, transport: Transport }.
  • Expert e lives on rank e % world_size.
  • Each rank holds ceil(num_experts / world_size) experts' weights.

A2A sequence diagram (4 ranks, 8 experts, 2 experts/rank):

Rank 0 (exp 0,4) | Rank 1 (exp 1,5) | Rank 2 (exp 2,6) | Rank 3 (exp 3,7)
     send_buf           send_buf           send_buf           send_buf
     [for e0,e1,..]     [for e0,e1,..]     [for e0,e1,..]     [for e0,e1,..]
         |                   |                   |                   |
         └────────── all-to-all (MPI_Alltoallv / nccl AlltoAll) ────┘
         |                   |                   |                   |
     recv_buf           recv_buf           recv_buf           recv_buf
     [tokens for         [tokens for         [tokens for         [tokens for
      exp 0,4]            exp 1,5]            exp 2,6]            exp 3,7]
         |                   |                   |                   |
      GEMM exp0           GEMM exp1           GEMM exp2           GEMM exp3
      GEMM exp4           GEMM exp5           GEMM exp6           GEMM exp7
         |                   |                   |                   |
     send_buf2          send_buf2          send_buf2          send_buf2
         |                   |                   |                   |
         └────────── reverse all-to-all ─────────────────────────────┘
         |                   |                   |                   |
     recv_buf2          recv_buf2          recv_buf2          recv_buf2
     (expert outputs back at origin ranks)

A2A message format per rank pair (r_src → r_dst):

  • Header: [token_count: u32, d_model: u32, dtype: u8] (8 bytes).
  • Payload: token_count × d_model floats (f32 or bf16 depending on dtype).
  • Symmetry invariant: tokens Rank A sends to Rank B = tokens Rank B expects from Rank A (enforced by DispatchPlan exchange before a2a).

A2A count-exchange protocol (before data a2a):

  1. Each rank broadcasts per_expert_counts[e] for all remote experts → all_gather counts.
  2. Validate symmetry: rank r_src's send count to r_dst = r_dst's expected recv count from r_src.
  3. Failure: asymmetric counts → MoeError::A2ACountMismatch { src, dst, sent, expected }.

Transport options (moe-comm):

Transport Use case Latency Bandwidth Failure mode
InProc (shared-memory channels) single-node multi-thread EP ~100 ns memory BW thread panic isolation
MPI_Alltoallv multi-node CPU EP ~10–100 µs interconnect rank failure = abort
NCCL AlltoAll multi-node GPU EP ~1–10 µs NVLink/IB NCCL error → reset
Mock (in-process loopback) tests, single-expert 0 — always succeeds

8.7 Comm/Compute Overlap (moe-sched)

Double-buffer pipeline per micro-batch:

Micro-batch 0                    Micro-batch 1
─────────────────────────────────────────────────────────────────────
Stream A (comm):  [a2a_fwd_0]─────────────[a2a_bwd_0]
Stream B (compute):            [gemm_0]──────────────────[gemm_0_bwd]
Stream A (comm):                         [a2a_fwd_1]─────────────────
Stream B (compute):                                 [gemm_1]──────────
                   time ─────────────────────────────────────────────►

Overlap invariant: GEMM on micro-batch N starts only after a2a for micro-batch N completes; a2a for micro-batch N+1 can start while GEMM for N runs.

Scheduler state machine:

State Entry condition Actions Exit →
IDLE no pending micro-batches wait on channel GATE_DISPATCH
GATE_DISPATCH input tokens available run gate + dispatch; build DispatchPlan A2A_FWD
A2A_FWD DispatchPlan ready submit a2a send on comm stream; advance buffer slot GEMM_WAIT
GEMM_WAIT a2a event signalled enqueue grouped GEMM on compute stream GEMM_EXEC
GEMM_EXEC GEMM running (optionally submit next micro-batch a2a in parallel) A2A_BWD
A2A_BWD GEMM event signalled submit reverse a2a COMBINE_WAIT
COMBINE_WAIT reverse a2a done enqueue combine kernel OUTPUT
OUTPUT combine done emit output tensor; reset buffer slot IDLE

Double-buffer slot allocation:

  • BufferSlot { id: u8, dispatch_buf: Tensor, result_buf: Tensor }.
  • Two slots per pipeline; slot 0 in GEMM while slot 1 in A2A_FWD.
  • BufferSlotGuard RAII; slot returned to pool on drop.
  • Failure: both slots occupied → scheduler blocks (back-pressure); surfaced as MoeError::SchedulerStall.

8.8 Expert FFN Execution Model

Per-expert computation (single expert, single EP rank):

input_e: [tokens_e, d_model]
  └─ GEMM_1: [tokens_e, d_model] × [d_model, d_ff] → [tokens_e, d_ff]   (w_in)
  └─ activation: SiLU / GeLU / ReLU element-wise → [tokens_e, d_ff]
  └─ GEMM_2: [tokens_e, d_ff] × [d_ff, d_model] → [tokens_e, d_model]   (w_out)
output_e: [tokens_e, d_model]

Grouped/batched GEMM semantics:

  • All experts on rank r are batched into a single grouped GEMM call: [(tokens_e0, tokens_e1, ...), d_model] × expert_weight_stacked.
  • tokens_e = per_expert_counts[e] after a2a; may be 0 (empty expert → skip or zero-pad).
  • Expert weights w_in: [num_experts_per_rank, d_model, d_ff], w_out: [num_experts_per_rank, d_ff, d_model].
  • Sharding: each rank holds only its local experts' weights; no cross-rank weight broadcast.

Zero-token expert handling:

  • If per_expert_counts[e] = 0 for local expert e → skip GEMM for that expert; output slice = empty.
  • Grouped GEMM backend must handle variable-length batches (Megablocks-style block-sparse or padded).
  • Padding to uniform length allowed only for GEMM alignment; padding rows zeroed before combine.

Activation options (configured per model):

Activation Gating variant Memory Notes
SiLU (swish) SwiGLU: d_ff×2 w_gate 2× d_ff intermediate Mixtral, LLaMA-MoE
GeLU standard 1× d_ff Switch, GShard
ReLU standard 1× d_ff Original Shazeer MoE

SwiGLU variant: w_in has shape [d_model, 2*d_ff]; split into gate and value halves; output = SiLU(gate) ⊙ value.

8.9 Combine Stage Semantics

Combine accumulation (after reverse a2a):

output: Tensor[n_tokens, d_model], initialized to zero.
Per permuted position i in [0, perm.len()), with tok = perm[i]:
  weight_i    = routing_decision[tok].weight_for_expert_at_position(i)
  output[tok] accumulates weight_i · expert_results[i]      (sum over admitted experts for tok)
dropped token (all K experts rejected) → output[tok] = 1.0 · input[tok]   (residual passthrough)

Weight renormalization after partial drop:

kept_weight_sum(t) = sum of original_weight[t][e] over admitted experts e for token t
kept_weight_sum(t) == 0.0  → output[t] = input[t]                                  (all k experts dropped t)
kept_weight_sum(t) >  0.0  → effective_weight[t][e] = original_weight[t][e] / kept_weight_sum(t)
                             output[t] = Σ (effective_weight[t][e] · expert_result[t][e]) over admitted e

Numerical invariant: sum(effective_weights) = 1.0 ± 1 ULP for all non-fully-dropped tokens.

Edge cases:

  • k=1, token dropped → full residual passthrough; effective weight vacuously 1.0 (but output = input).
  • k=2, one expert drops → single expert gets weight 1.0 after renorm.
  • capacity_factor=inf → no drops; combine = dense weighted sum; reference implementation path.
  • All tokens dropped (capacity=0 or all experts overloaded) → output = input; warning emitted to telemetry.

8.10 Shared Expert Variant

Shared expert bypass (optional; e.g., DeepSeek-V2 architecture):

  • num_shared_experts: usize experts always receive ALL tokens (no capacity/drop).
  • Shared experts run in parallel to routed experts on the same rank.
  • Shared expert output added to routed combine output: out = shared_out + routed_combine_out.
  • DispatchPlan has shared_expert_ids: Vec<ExpertId> field; non-empty iff shared experts configured.
  • Invariant: shared experts never in dropped BitSet.

8.11 Expert Parallelism Consistency Model

EP rank assignment: expert e → rank e % world_size.

  • Requires num_experts % world_size == 0 OR last rank holds fewer experts (ragged ok; must be handled).
  • Invariant: every EP rank independently validates its local expert IDs match global assignment.

Failure modes:

Failure Detection Recovery
A2A count mismatch pre-a2a count allreduce abort batch; MoeError::A2ACountMismatch
Rank timeout transport deadline (configurable) kill batch; escalate to caller
Expert weight shard missing startup validation MoeError::MissingExpertShard(ExpertId)
NaN in GEMM output optional nan-check kernel post-GEMM MoeError::ExpertNaN(ExpertId)
OOM in dispatch buffer pre-allocation check MoeError::CapacityOom { expert, required, available }

  ConfigError(String)              — invalid MoE layer config
  BackendError(String)             — GEMM FFI error

Error propagation: all public API returns Result<T, MoeError>; no panics in hot path; panics allowed only during initialization (weight loading, config parsing).

8.13 Routing Determinism Protocol

Requirements for bit-reproducible routing:

  1. Gate logits computed with same floating-point order (no parallel reduction reordering).
  2. Top-k selection: stable sort by logit descending; ties broken by ExpertId ascending.
  3. Noisy top-k: noise generated from XorShift64(seed=layer_idx * 1337 + token_idx); seed passed in MoeLayerConfig.
  4. Capacity assignment: tokens sorted by gate weight descending per expert; tie-break by TokenIdx ascending.
  5. DispatchPlan.perm built in expert-ascending, then token order within expert.

Non-determinism sources (must be suppressed in deterministic mode):

Source Suppression
GPU atomic reductions use deterministic kernels (cuDNN det flag or software reduction)
Parallel top-k sort use single-threaded stable sort in deterministic mode
NCCL non-det all-reduce use NCCL_DETERMINISTIC=1 env + ring algorithm
FP reassociation fixed reduction order; no auto-vectorizer reordering
