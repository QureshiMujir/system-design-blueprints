Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If you set capacity_factor=1.0 with k=2 and E=64, what is the expected token drop rate at uniform routing for a batch of 2048 tokens, and which §§ provide the formula to compute it? Requires synthesis of §4.2 (capacity formula) and §§ Back-of-Envelope Capacity Model. Answer requires knowing that uniform routing produces Poisson-like per-expert load with mean=64 and computing the tail probability beyond capacity=64. Resolving §: §4.2, §7 I2, §§ Back-of-Envelope item 1.
  2. Why does the capacity formula use ceil() rather than floor(), and what invariant would be violated if you used floor()? Requires understanding the token conservation invariant (I1) and the capacity invariant (I2). With floor, a batch where n_tokens×k is exactly divisible by E leaves zero slack; any non-uniform routing causes drops on at least one expert. Resolving §: §7 I1/I2, §4.2.
  3. Trace the data path of a single token from input tensor through moe-gate → moe-dispatch → moe-comm → moe-expert → moe-comm → moe-dispatch → output, naming the exact Rust type at each crate boundary. Requires familiarity with §11 core types, §3 architecture, Phase 0.2 and Phase 6.2. Resolving §: §3.1, §11, Phase 0.2, Phase 6.2.
  4. If two tokens have identical logits for all 64 experts, which two experts does the top-2 router assign them to, and is the assignment identical across AMD and Intel CPUs? Requires understanding the tie-break rule (I3) and IEEE 754 determinism (§5.4 IEEE 754 reference). Answer: ExpertId 0 and 1, always, because the tie-break is ascending ExpertId after deterministic sort; IEEE 754 guarantees identical f32 comparison results for identical bit patterns. Resolving §: §7 I3, §6.2 (P2), §5.4 (IEEE 754).
  5. What is the mathematical relationship between routing entropy, token drop rate, and aux loss at training convergence, and which §§ define each quantity? Requires synthesis of §6.1 (P1 token conservation), §§ Mental Models & First Principles MM1/MM3, §7 I8 (aux loss monotonicity), and §4 system constraints. Resolving §: §6.1, §6.4, §7 I8, §§ Back-of-Envelope items 9 and 11.
  6. If rank 3 in an 8-rank EP group fails mid-forward-pass while the all-to-all is in progress, what is the exact sequence of events in moe-comm and moe-runtime, and which invariants must still hold? Requires familiarity with Phase 11.2 (HeartbeatMonitor, failover a2a), I1 (token conservation via residual passthrough on failure), I10 (A2A symmetric counts must be rebuilt). Resolving §: Phase 11.2, §7 I1/I10, §§ Failure Modes & Recovery (rank failure subsection).
  7. Why does expert-choice routing require the full [n_tokens × num_experts] score matrix to be materialized before dispatch, while token-choice routing does not, and what is the latency implication at n_tokens=4096, E=128? Requires understanding MM5 (Mental Models & First Principles) and Phase 9.2 expert_choice sync barrier. Score matrix = 4096 × 128 × 4 bytes = 2 MB; must be gathered from all ranks before column-wise topk. Resolving §: Phase 9.2, §§ Alternative Architectures, §§ Mental Models & First Principles MM5.
  8. What happens to the AuxLossState if a forward pass has zero tokens (n_tokens=0), and what should the backward pass return for z_loss gradient in that case? Requires Phase 4.2 (AuxLossState with zero tokens), §7 I8 (aux loss monotonicity — zero inputs → zero loss), Phase 13.2 (differential harness edge cases). Resolving §: Phase 4.2, §7 I8, Phase 1 edge cases section.
  9. If you increase world_size from 4 to 8 with E=64, k=2, n_tokens=2048, keeping capacity_factor=1.25, what changes in per-rank VRAM, a2a bandwidth, and expected drop rate? Requires §§ Back-of-Envelope (items 2–5) applied twice and understanding the a2a bandwidth formula. Expert weights halve; a2a bandwidth per rank: (W-1) × capacity × d_model × dtype — increases as W grows but message count per peer shrinks. Resolving §: §§ Back-of-Envelope, §4, §§ Scalability Analysis (Network Fanout).
  10. Why is the combine step not simply a sum over expert outputs, and what exact check would reveal a bug where the gate weights were not renormalized after a token was partially dropped? Requires understanding §7 I5 (combine correctness), §6.1 (P1 token conservation), and Phase 2.2 (combine_with_residual). Partial drop means fewer than k experts accepted the token; if combine sums all k gate weights regardless, the output is scaled down. Resolving §: §7 I5, Phase 2.2, §6.1 (P1).
  11. Which crate owns the unsafe keyword for GEMM FFI, why is it confined there, and what ASAN/Miri test validates it? Requires ADR-04 (cblas-sys + cudarc), §6.7 (P7 FFI safety), Phase 5.2 (gemm_ffi.rs). Answer: moe-expert/gemm_ffi.rs exclusively; isolated so AddressSanitizer CI target can instrument only that crate boundary. Resolving §: §6.7, Phase 5.2, ADR-18.
  12. How does the double-buffer state machine in moe-sched prevent a data race between the a2a receive and the combine step without a mutex? Requires Phase 8.2 (doublebuf.rs ping-pong), §7 I6 (overlap liveness), §6.8 (P8 explicit overlap). The event-based protocol — compute stream waits on a2a-done event before reading receive buffer — eliminates the race without a lock. Resolving §: Phase 8.2, §7 I6, §6.8.
  13. If W_g (gate projection matrix) is initialized to all zeros, what routing behavior emerges, what does the aux loss report, and how does the z-loss prevent logit explosion in subsequent training steps? Requires Phase 1.2 (topk_indices_deterministic tie-break), §7 I9 (gate logit safety), Phase 4.2 (z-loss formula). Zero W_g → all logits zero → tie-break assigns experts 0..k-1 to every token → load catastrophically imbalanced → aux loss non-zero immediately → z-loss = 0 (logits = 0 → logsumexp = log(E)) initially but prevents logit runaway as gradients flow. Resolving §: Phase 1.2, Phase 4.2, §7 I9.
  14. What is the exact byte layout of the safetensors header for a checkpoint with 8 expert weight tensors (w_in, w_out per expert), and how does moe-cli validate it before mmap? Requires ADR-09 (safetensors spec), Phase 5.2 (weight_loader.rs validation), §5.4 (SafeTensors spec reference). Header is JSON with dtype, shape, data_offsets per tensor; validation checks magic bytes, header length, tensor count, expected expert names. Resolving §: ADR-09, Phase 5.2, §5.4.
  15. If you reduce capacity_factor from 1.25 to 0.8 on a live system, what happens to token drop rate, training loss, and routing entropy over the next 1000 training steps, and which telemetry counters would you watch? Requires §§ Operational Readiness (alert thresholds), §§ Back-of-Envelope item 1, §7 I8 (aux loss response). Drop rate spikes immediately (overflow); training loss may degrade or recover depending on aux loss coefficient; routing entropy usually increases as gate compensates; watch moe_drop_rate, moe_routing_entropy, moe_aux_loss. Resolving §: §§ Operational Readiness, §§ Back-of-Envelope, §7 I1/I8.
  16. Why does the InProc transport use crossbeam bounded channels rather than tokio channels, and what would happen if the channel were unbounded? Requires ADR-07 (crossbeam SPSC for InProc), §6.5 (P5 explicit backpressure). Bounded: backpressure visible as MoeError::QueueFull; unbounded: producer can outrun consumer indefinitely, arena grows without bound, OOM crash with no recoverable error. Resolving §: ADR-07, §6.5, Phase 7.2.
  17. How does the per-rank expert ownership formula expert_id % world_size interact with a non-power-of-two expert count like E=48, W=8, and what load imbalance results? Requires §6.9 (P9 EP consistency), §7 I4, §§ Scalability Analysis sharding section. Expert distribution: ranks 0–7 get ceil(48/8)=6 or floor(48/8)=6 experts (exact division here); for E=50, W=8: ranks 0–1 get 7 experts, ranks 2–7 get 6 — a 16% imbalance in compute, handled by capacity_factor and telemetry alert. Resolving §: §6.9, §7 I4, §§ Scalability Analysis.
  18. What is the worst-case memory allocation during a forward pass if one expert receives 3× its capacity due to a routing collapse, and how does the code prevent this from causing heap growth? Pre-allocated arena-backed buffers: expert input buffer is sized to capacity at layer init, not dynamically. Overflow tokens are dropped before scatter; they never reach the expert buffer. The arena cursor never advances beyond the pre-computed high-water mark. Resolving §: §6.3 (P3), §7 I2, Phase 0.2 (Arena), Phase 3.2 (capacity.rs reject logic).
  19. If the z-loss coefficient is set to 0.0, what is the theoretical failure mode and under which training configuration is it most likely to manifest? Zero z-loss → no logit magnitude regularization → gate logits can grow arbitrarily large during training → softmax becomes numerically degenerate (one expert gets weight ≈ 1.0 for all tokens) → routing collapse into a single expert → aux loss fails to correct because load term is already 1.0 for that expert. Most likely with large learning rate + small aux_loss_coeff + deep model (many MoE layers). Resolving §: Phase 4.2 (z-loss), §7 I9, §§ Failure Modes & Recovery.
  20. How would you modify the DispatchPlan to support fractional token drops (dropping only one of k assignments for an overflowed token rather than the full token)? Requires synthesis of Phase 2.2 (plan.rs), §7 I5 (combine correctness), §6.1 (P1 token conservation). Partial drop requires a per-assignment dropped flag (not a per-token BitSet), a renormalization step in combine (re-normalize remaining k-1 weights to sum to 1.0), and a new invariant: sum(assigned_weights[t]) ∈ {0.0, 1.0} for all t. Tradeoff: eliminates full token loss at high capacity pressure but makes combine more expensive. Resolving §: Phase 2.2, §7 I1/I5, §11.7 DispatchPlan.

Mental Models & First Principles

MM1 — Sparse routing is selective broadcasting, not filtering. The compressed insight: each token is sent to exactly k out of E experts, not routed away from E-k experts. The gate weight is a mixture coefficient, not a confidence score. What it predicts: capacity overflow happens because k assignments per token × n_tokens tokens creates k×n_tokens expert "slots" competing for E×C total capacity; at uniform routing each expert sees n_tokens×k/E arrivals, and the capacity formula is just that number rounded up. Bug class without it: developers who think of routing as "filtering" set capacity_factor=1.0 thinking it should be sufficient, then see 15%+ drop rates because they did not account for the ceil and non-uniform load variance. Resolving §: §4.2 capacity formula, §6.3 (P3), §7 I2.

MM2 — All-to-all is a symmetric data transpose, not a send/receive. Each rank holds a row-slice of the token×expert assignment matrix; after all-to-all each rank holds a column-slice (all tokens for its experts). Token buffer sizes before and after a2a are determined by the count arrays, not the token count. What it predicts: every "why is rank r receiving more bytes than it sent?" is answered by load imbalance — send-counts to rank r from all peers sum to its expert load. Bug class without it: asymmetric count bugs where send_counts[r→s] ≠ recv_counts[s←r] cause silent buffer overruns or hangs; I10 invariant catches them. Resolving §: §7 I10, Phase 5 (a2a.rs), Phase 7 (Transport trait).

MM3 — Capacity factor is a queuing system parameter, not a throughput knob. Setting capacity_factor=1.0 is analogous to a zero-wait-time queue: any arrival imbalance causes drops. Capacity_factor=1.25 provides ~25% headroom above mean load. What it predicts: at k=2, uniform routing, E=64, n=4096, the mean per-expert load is 128 tokens; std dev ≈ sqrt(n×k/E) ≈ 11; 3σ above mean ≈ 161; capacity_factor ≥ 1.26 ensures zero drops at 3σ. Bug class without it: capacity_factor tuned by intuition rather than load distribution statistics; sporadic drops under bursty inputs. Resolving §: §4.2, §§ Back-of-Envelope Capacity Model.

MM4 — Comm/compute overlap requires explicit event ordering, not async fire-and-forget. The CUDA event model requires: (1) compute stream records event A after GEMM done, (2) comm stream waits on event A before launching a2a, (3) comm stream records event B after a2a done, (4) compute stream waits on event B before next GEMM. Dropping any event causes data races or hangs. What it predicts: overlap efficiency drops to zero if the comm stream begins sending while GEMM is still writing the source buffer. Bug class without it: random numerical corruption at high batch sizes where timing luck normally hides the race. Resolving §: §6.8 (P8), §7 I6, Phase 8 (doublebuf.rs).

MM5 — Expert-choice routing inverts the capacity constraint direction. In token-choice routing, each token picks top-k experts (E constrains tokens). In expert-choice, each expert picks top-c tokens (tokens constrain experts). Expert-choice eliminates token drops entirely but requires the full n_tokens × E score matrix to be materialized before any dispatch can start — a synchronization barrier absent in token-choice. What it predicts: expert-choice is strictly better for training stability but adds a full matrix barrier latency that token-choice avoids. Bug class without it: implementing expert-choice with the token-choice DispatchPlan pipeline causes wrong assignment counts because the assignment is column-major not row-major. Resolving §: §3.4, Phase 9 (expert_choice.rs), §§ Alternative Architectures.

MM6 — Token conservation is a two-part invariant: routing path AND residual path. It is not enough to route every token; every dropped token must explicitly take the residual passthrough path (output[t] = input[t]). A single missing residual assignment causes a zero-row in the output tensor — numerically valid but semantically wrong, and the model loss degrades slowly without a clear signal. What it predicts: any test that checks only "no panic" or "output shape matches input" will miss a missing residual. Bug class without it: tokens silently zeroed under capacity overflow; detected only by differential test against dense reference. Resolving §: §7 I1, §6.1 (P1), Phase 3 (combine.rs residual passthrough).

Glossary · 46 terms · site-wide glossary

all-to-all (a2a)
Collective op where every EP rank sends a distinct shard to every other rank; inverse applied after expert compute; bottleneck in EP scalability.
aux load-balance loss
Differentiable penalty = sum_e(f_e * p_e) × num_experts added to total loss; f_e = fraction tokens routed to e, p_e = mean gate probability for e; drives uniform utilization without explicit dropping.
AuxLossState
Runtime accumulator { importance: Vec<f32>, load: Vec<f32> } holding per-expert f_e and p_e needed to emit aux loss; collected inside moe-gate per forward pass.
batched GEMM
Single cuBLAS/BLAS call driving multiple independent matrix multiplications sharing one dispatch; used when multiple expert token batches can share a kernel launch.
capacity
Hard upper bound on tokens an expert processes per forward: Capacity = ceil(capacity_factor × n_tokens × k / num_experts); enforced inside moe-dispatch.
capacity factor
Scalar multiplier (≥1.0) controlling expert buffer size relative to ideal load; 1.0 = exactly ideal, 1.25 = 25 % overflow headroom; tunable without recompile via config.
CombineBuffer
Typed handle { buf: Tensor, weights: Tensor, expert_slots: Vec<Range<usize>> } holding post-expert outputs aligned to permutation order for weighted scatter-add.
comm/compute overlap
Scheduling pattern where all-to-all sends and expert GEMMs execute on independent device streams; requires double-buffering of token/weight tensors; primary latency optimization.
dense baseline
Reference path with capacity_factor = ∞ and k = num_experts routing all tokens to all experts; output equals standard FFN; used for correctness differential tests.
dispatch
Phase where tokens are permuted into contiguous per-expert buffers following RoutingDecision; includes capacity check, drop decision, and scatter into DispatchPlan.perm.
DispatchPlan
{ perm: Vec<u32>, per_expert_counts: Vec<u32>, dropped: BitSet, capacity: Capacity } — complete description of the token→expert mapping for one forward pass.
double-buffering
Ping-pong pattern using two DispatchPlan/CombineBuffer pairs so stage N+1 dispatch overlaps stage N expert compute; managed by moe-sched.
drop policy
Rule for which tokens are evicted when expert capacity is exceeded; canonical = drop lowest gate weight first; deterministic tie-break by TokenIdx.
dropped token
Token that exceeds expert capacity and is excluded from expert compute; passes through unmodified via residual (output = input); tracked in DispatchPlan.dropped BitSet.
DType
Enum { F32, BF16, F16, I8 } stored in Tensor handle; controls GEMM dispatch and quantized weight dequant path; F32 mandatory for gate logits.
EP rank / EP world
Index of this process within the expert-parallel process group (EpGroup); expert e lives on rank e % world_size; determines which weight shard is local.
EpGroup
{ rank: u32, world_size: u32, transport: Transport } — identifies the expert-parallel collective group; scoped per MoeLayer instance; transport is In-proc
expert
One FFN sub-network FFN(x) = activation(x × w_in) × w_out; weight matrices sharded across EP ranks; selected by gate routing for a subset of tokens.
expert-choice routing
Router variant where each expert selects its top-C tokens (budget-controlled) instead of tokens selecting experts; guarantees exact capacity; no token dropping; from Zhou 2022.
expert parallelism (EP)
Model-parallelism strategy placing disjoint expert weight shards on distinct devices/ranks; tokens dispatched to owning rank via all-to-all; expert compute is fully local.
expert utilization
Metric = tokens_processed_by_expert / capacity; per-expert value in [0, 1]; >0.95 sustained triggers overload alert; imbalance detectable via routing entropy.
ExpertId
Newtype ExpertId(u32); valid range [0, num_experts); used as array index in RoutingDecision and DispatchPlan.
ExpertWeights
{ w_in: Tensor, w_out: Tensor, sharded_across: EpGroup } — storage descriptor for one expert's FFN parameters; sharding axis and dtype tracked for GEMM dispatch.
GateLogits
[n_tokens × num_experts] f32 tensor; raw pre-softmax scores from W_g × x; input to top-k selection; stored F32 regardless of model precision.
gating / router
Linear projection W_g ∈ ℝ^{d×E} mapping token embedding to expert scores; followed by top-k + softmax in moe-gate; may include noise injection for noisy top-k.
grouped GEMM
Kernel executing variable-length GEMMs for all experts in one launch using per-expert M-dim offsets; avoids kernel-launch overhead; primary path in moe-expert.
invariant
Hard correctness property that must hold across all code paths; violations are fatal (panic or MoeError); tested by differential harness and property-based tests.
K / top-k
Number of experts each token is routed to; typically 1 or 2 in published models; controls compute density and memory bandwidth per forward pass.
load-balance loss
See aux load-balance loss; sometimes called importance loss or load loss depending on paper; both terms resolve to same AuxLossState fields.
micro-batch
Subdivision of a forward-pass batch used to pipeline dispatch, comm, expert, and combine stages across sequential micro-batches; controlled by moe-sched.
MoeError
Exhaustive error enum covering: ShapeMismatch, CapacityOverflow, TransportError, GemmBackendError, ConfigError, WeightLoadError; no panics in library paths.
MoeLayer::forward
Public entry point: fn forward(&self, x: Tensor, aux: &mut AuxLossState) -> Result<Tensor, MoeError>; orchestrated by moe-runtime; only public surface for inference.
noisy top-k
Router variant adding N(0,1) × softplus(W_noise × x) to logits before top-k selection; improves load balance during training; noise disabled at inference.
permutation
DispatchPlan.perm = integer array mapping token-in-batch position to contiguous position in per-expert buffer; used for scatter (dispatch) and gather (combine).
residual passthrough
Identity path for dropped tokens: output[dropped] = input[dropped]; ensures token conservation invariant even when capacity is exceeded.
routing determinism
Invariant: identical input + seed → bit-identical RoutingDecision and DispatchPlan; enforced by deterministic top-k tie-break on ExpertId.
routing entropy
H = -Σ_e p_e × log(p_e) over per-expert load fractions; maximum at uniform routing; low entropy signals expert collapse; emitted as moe-telemetry gauge.
RoutingDecision
Per-token struct { topk: [(ExpertId, f32); K] } where f32 = softmax-normalized gate weight; weights sum to 1.0 across K entries.
scatter-gather
Low-level memory ops implementing permutation: scatter fills per-expert contiguous buffer from token batch; gather reverses after expert compute for combine.
shared expert
Expert(s) that receive ALL tokens unconditionally alongside top-k sparse routing; used in DeepSeekMoE / Qwen-MoE architectures; modeled as k+S routing in DispatchPlan.
softmax-over-topk
Renormalization of gate weights to the selected K experts after top-k masking, so weights sum to 1; preserves gradient magnitude; canonical combine weighting.
ST-MoE z-loss
Penalty L_z = α × log(Σ_e exp(logit_e))^2 stabilizing gate logit magnitude; prevents logit explosion; from Zoph 2022 ST-MoE paper.
token conservation
Invariant: every input token appears exactly once in the output; non-dropped tokens via expert paths; dropped tokens via residual passthrough.
TokenIdx
Newtype TokenIdx(u32); position in the input batch [0, n_tokens); used in BitSet for dropped-token tracking and permutation validation.
transport
Collective communication backend abstraction in moe-comm: In-proc (shared-memory channel for single-process EP), NCCL (multi-GPU), TCP-fallback.
z-loss
See ST-MoE z-loss; coefficient α typically 1e-3; added to training loss; not emitted at inference but state must be zero-able without recompile.
