Decisions (§9) · 25 ADRs

ADR-01

Implementation language

Chosen

Rust (edition 2021, MSRV 1.78)

Rejected

C++ (safety), Python (perf/control), Go (GC latency), Julia (ecosystem)

When the rejected choice is right

Python wins when team cannot hire Rust engineers and velocity > throughput (research prototype ≤100M tokens/day)

Why: No GC tail-latency; fearless concurrency; safe FFI to BLAS/CUDA; zero-cost abstractions; portfolio consistency

ADR-02

Build system

Chosen

Cargo workspace (10 crates)

Rejected

Bazel (complexity overhead), CMake (C++ heritage), Buck2 (less ecosystem)

When the rejected choice is right

Bazel wins when codebase mixes Rust + C++ + Python in one monorepo and remote caching saves >30 min/CI run

Why: Native Rust; workspace.dependencies for version pinning; cargo-features for CUDA/MPI feature flags

ADR-03

Dependency policy

Chosen

Minimal curated set; no transitive surprises; all deps audited via cargo audit

Rejected

Vendoring all sources (maintenance burden), lock-free open selection

When the rejected choice is right

Full vendoring wins in air-gapped enterprise environments where no outbound network access to crates.io is allowed

Why: cargo.lock committed; cargo deny for license + advisory checks; no yanked crates

ADR-04

GEMM backend FFI

Chosen

cblas-sys (CPU) + cudarc (CUDA) via conditional compilation

Rejected

Manual CUDA bindings (error-prone), BLAS-sys alternatives, tch-rs (too heavy)

When the rejected choice is right

tch-rs wins when the wider PyTorch op set (attention, layer-norm, optimizer) is needed alongside MoE in the same binary

Why: cudarc provides safe CUDA runtime bindings; cblas-sys for CPU fallback; no full BLAS crate overhead

ADR-05

Tensor handle / storage

Chosen

moe-core arena-backed Tensor struct; SmallVec<[usize;4]> for shape

Rejected

ndarray (allocation overhead), tch-rs/candle (heavy deps), raw *mut u8 (unsafe proliferation)

When the rejected choice is right

ndarray wins if the project only targets CPU, does not need FFI, and the team values ndarray's slicing/broadcasting ergonomics over raw control

Why: Arena controls lifetime; SmallVec avoids heap for ≤4-dim tensors; explicit device/dtype/layout per handle

ADR-06

Async runtime

Chosen

tokio (multi-thread) for comm/sched coordination

Rejected

async-std (smaller ecosystem), rayon (compute not IO), smol (insufficient)

When the rejected choice is right

rayon wins when all parallelism is CPU-compute (no I/O, no CUDA events): simpler model, no executor overhead

Why: tokio select! for comm/compute overlap state machine; tokio channels for micro-batch pipeline; well-audited

ADR-07

Intra-process communication

Chosen

tokio::sync::mpsc + crossbeam channels

Rejected

raw mutex/condvar (ergonomics), actor framework (overhead), lock-free queues (complexity)

When the rejected choice is right

Actor framework (e.g., Actix) wins when the inter-stage messages carry rich typed variants and supervision/restart semantics are required

Why: mpsc for pipeline stages; crossbeam for bounded SPSC in hot dispatch loop; both zero-alloc in steady state

ADR-08

Multi-process comm (EP)

Chosen

MPI via rsmpi feature flag; NCCL via cudarc nccl feature; InProc fallback always compiled

Rejected

gRPC (latency), custom TCP (maintenance), UCX bindings (immature Rust)

When the rejected choice is right

gRPC wins when EP ranks span cloud VMs with heterogeneous network fabrics and the collective volume is modest (<1 GB per forward pass)

Why: MPI standard for HPC portability; NCCL for GPU bandwidth; InProc for single-node tests; feature flags keep binary size manageable

ADR-09

Serialization (weights)

Chosen

safetensors (via safetensors crate)

Rejected

GGUF (inference-only tooling), pickle (unsafe), HDF5 (C dep complexity), raw bin

When the rejected choice is right

GGUF wins in pure-inference mobile/edge deployments where quantization metadata and GGUF-aware loaders are already in the stack

Why: safetensors: zero-copy mmap, no code exec, well-adopted in HuggingFace ecosystem; validates dtype/shape

ADR-10

Config format

Chosen

TOML (serde + toml crate)

Rejected

JSON (less human-editable), YAML (ambiguous typing), Protobuf (compile step)

When the rejected choice is right

Protobuf wins when config must be validated across multiple programming languages and versioned API evolution is required

Why: TOML: strongly typed via serde; no implicit type coercion; cargo native format; easy to review diffs

ADR-11

Logging

Chosen

tracing crate (structured, async-aware)

Rejected

log crate (no spans), slog (verbose), env_logger alone (unstructured)

When the rejected choice is right

log crate wins in embedded or WASM targets where tracing's subscriber machinery is too heavy (>50 kB code size budget)

Why: tracing: span context propagates across async tasks; instrument macro on hot path; switchable subscriber

ADR-12

Metrics export

Chosen

metrics crate + metrics-exporter-prometheus

Rejected

OpenTelemetry (heavier), statsd (push-only), custom CSV

When the rejected choice is right

OpenTelemetry wins when the organization mandates OTLP as the single telemetry pipeline and both traces and metrics must correlate via trace-ID

Why: metrics facade: zero-cost macros; prometheus pull; standard scrape endpoint; no OTLP dep required

ADR-13

Distributed tracing

Chosen

opentelemetry + opentelemetry-otlp feature-flagged

Rejected

Jaeger direct (vendor lock), Zipkin (less tooling), custom span log

When the rejected choice is right

Jaeger direct wins when the team runs a self-hosted Jaeger cluster and wants zero OTLP collector maintenance overhead

Why: OTLP standard; feature-flagged to avoid mandatory dep; spans cross EP ranks via W3C trace-context propagation

ADR-14

Testing strategy

Chosen

Unit (cargo test), integration (moe-runtime tests), differential (moe-bench vs dense reference)

Rejected

Property-based only (misses numerical regression), snapshot only (brittle)

When the rejected choice is right

Property-based only (proptest) wins for pure algebraic components (newtype arithmetic, permutation invertibility) where a reference implementation does not exist

Why: Differential harness: run MoE with capacity=inf, k=E → must match dense FFN reference within 1e-5 L∞

ADR-15

Fuzzing

Chosen

cargo-fuzz (libfuzzer) on DispatchPlan builder and gate inputs

Rejected

AFL (less Rust integration), honggfuzz (manual setup)

When the rejected choice is right

AFL wins when coverage-guided fuzzing must target non-Rust native libraries via shared-memory forkserver (e.g., a vendored C BLAS extension)

Why: cargo-fuzz: first-class Rust; fuzz RoutingDecision deserialization and capacity arithmetic for OOB

ADR-16

Benchmarking

Chosen

criterion (statistical) + moe-bench custom throughput harness

Rejected

hyperfine (CLI only), custom timers (no statistics)

When the rejected choice is right

hyperfine wins for benchmarking end-to-end CLI invocations where process startup cost is the measurement target, not library internals

Why: criterion: confidence intervals, outlier detection; moe-bench adds token/s and TFLOP/s metrics

ADR-17

CI/CD

Chosen

GitHub Actions (matrix: stable, MSRV 1.78, nightly)

Rejected

Jenkins (self-host burden), CircleCI (cost), Buildkite (overkill)

When the rejected choice is right

Jenkins wins when the CI pipeline must run inside a private datacenter with no external network access and custom hardware (GPU nodes)

Why: Actions: free for OSS; matrix covers MSRV contract; nightly for clippy pedantic + miri subset

ADR-18

Sanitizers / Miri

Chosen

ASAN/LSAN in CI (via -Zsanitizer=address) for FFI boundary; Miri for safe Rust core types

Rejected

Valgrind (slow, Linux-only), manual review (insufficient)

When the rejected choice is right

Valgrind wins on non-Linux platforms (macOS CI, x86 FreeBSD) where LLVM sanitizers are unavailable or unstable

Why: Miri catches UB in moe-core arena logic; ASAN catches FFI buffer overruns in GEMM dispatch

ADR-19

Clippy policy

Chosen

#![deny(clippy::all, clippy::pedantic)] workspace-wide; allow list for known false-positives

Rejected

Warn-only (lets issues accumulate), no clippy (regression risk)

When the rejected choice is right

Warn-only wins during an active major refactor sprint where the allow-list would need to be updated in every PR, slowing merge velocity

Why: Pedantic catches cast truncation, missing docs, arithmetic overflow in const eval

ADR-20

Error handling

Chosen

thiserror for all public API errors; anyhow in CLI/bench binaries only

Rejected

Box<dyn Error> (type erasure loss), failure (deprecated), manual Display impls

When the rejected choice is right

Box<dyn Error> wins in glue scripts and one-off tools where error variety is high and the caller will not match variants

Why: thiserror: zero-cost derive; typed enum variants enable precise match in callers; anyhow for binary entry points

ADR-21

Feature flags

Chosen

cuda, mpi, nccl, telemetry-otlp, deterministic Cargo features

Rejected

Compile-time cfg (fragile), runtime-only (binary bloat)

When the rejected choice is right

Runtime-only feature detection wins when the binary must run on heterogeneous hardware fleets without recompile (e.g., k8s operator with mixed GPU/CPU nodes)

Why: Default features = CPU + InProc + prometheus; GPU/MPI opt-in; deterministic flag enables stable sort + det kernels

ADR-22

Reproducibility

Chosen

Cargo.lock committed; cargo vendor snapshot for air-gapped builds; CI hash-pins Actions

Rejected

Floating deps (non-reproducible), Docker-only (no bare-metal CI)

When the rejected choice is right

Docker-only wins when binary reproducibility is enforced via container image hash and bare-metal CI is unavailable

Why: Lock file + vendor ensures identical dep graph across machines; hash-pinned Actions prevent supply-chain attack

ADR-23

Documentation

Chosen

rustdoc for all public API (#![warn(missing_docs)]); FINAL_BLUEPRINT.md as spec

Rejected

Separate wiki (drift), Sphinx (Python toolchain dep), ADRs in Notion (not versioned)

When the rejected choice is right

Sphinx wins when the project has a large non-Rust audience (ML researchers) who need tutorials, notebooks, and API docs in a single rendered portal

Why: rustdoc lives with code; blueprint spec is source of truth; cargo doc --no-deps for offline use

ADR-24

Licensing

Chosen

MIT OR Apache-2.0 (SPDX dual)

Rejected

GPL (incompatible with enterprise FFI deps), MIT-only (some contributors prefer Apache patent clause)

When the rejected choice is right

GPL wins when the project is a standalone tool (not a library) and the authors want strong copyleft to prevent proprietary forks

ADR-25

Packaging / distribution

Chosen

Cargo (source); Docker image with CUDA base for GPU benchmarks; no OS packages

Rejected

conda (Python ecosystem coupling), pip (not Rust native), apt/rpm (distro lag)

When the rejected choice is right

conda wins when the primary consumers are ML practitioners using conda-forge environments where Python interop and CUDA toolkit version pinning are managed by conda

Why: Source distribution via crates.io for library crates; Docker for reproducible GPU environment in CI

Alternative Architectures

Alternative 1 — Block-Sparse GEMM (Megablocks-style)

Token batch (sorted by assigned expert):
[T0,T1,T4,T7] [T2,T3,T5] [T6,T8,T9] [T11]
 Expert 0       Expert 1   Expert 2   Expert 3

Block-sparse layout: experts padded to tile boundary; GEMM on sorted block:
[ block_e0 | block_e1 | block_e2 | block_e3 ]
  ≤ tile    ≤ tile     ≤ tile     ≤ tile
All in one cuSPARSE / Triton block-sparse kernel call

Regime where this wins: very large E (E ≥ 256), high k (k ≥ 4), and a GPU with good block-sparse kernel support (A100+ with Triton). Eliminates per-expert GEMM overhead at the cost of sorted-token permutation. Real system: Megablocks (Gale 2022, MLSys 2023). Why rejected here: requires CUDA-native block-sparse kernel; not portable to CPU reference path; grouped GEMM via cblas-sys achieves the same semantic on CPU without the kernel dependency.

Alternative 2 — Expert-Choice with Column-Major DispatchPlan

Score matrix [E x T]:
         T0    T1    T2    T3    T4
Expert0  0.9   0.3   0.7   0.2   0.5
Expert1  0.6   0.8   0.1   0.9   0.4
Expert2  0.2   0.5   0.8   0.3   0.7
Expert3  0.7   0.4   0.3   0.6   0.1

Each expert selects top-c tokens (c = capacity):
Expert0 → [T0, T2], Expert1 → [T1, T3], Expert2 → [T2, T4], Expert3 → [T0, T3]
                                         ^conflict^            ^conflict^
Conflict resolution: token keeps assignment from highest-weight expert only

Regime where this wins: training workloads where load balance is more important than inference latency and no token-drop tolerance exists. Expert-choice provides perfect expert utilization at the cost of the score-matrix barrier. Real system: Zhou et al. 2022 (NeurIPS 2022). Why rejected as default: the full [n_tokens × E] matrix barrier adds latency that token-choice avoids; implemented as a Phase 9 variant but not the default routing mode.

Alternative 3 — All-Dense MoE (k=E, no dispatch)

input [n_tokens, d_model]
         |
  [gate] W_g -> softmax over all E -> gate_weights [n_tokens, E]
         |
  [experts] all E experts compute simultaneously:
  expert_out[e] = FFN_e(input) for all e in 0..E
         |
  [combine] output = sum_e(gate_weights[e] * expert_out[e])

Regime where this wins: small E (E ≤ 4), very small d_ffn, or when interpretability of all-expert contributions is needed (research ablation). Eliminates all dispatch/a2a machinery; full batch through every expert. Real system: "soft MoE" (Puigcerver 2023, arXiv 2308.00951). Why rejected: compute cost = O(E × n_tokens × d_ffn); for E=64 this is 64× a dense FFN — defeats the purpose of MoE sparsity; only viable as an integration test baseline (capacity=inf, k=E).

Alternative 4 — Hierarchical EP (Two-Tier All-to-All)

World: 4 nodes × 8 GPUs = 32 ranks; E = 64 experts

Tier 1 (intra-node, NVLink): ranks 0–7 exchange tokens for local experts 0–15
Tier 2 (inter-node, IB):     node leaders exchange tokens for remote experts 16–63

Reduces inter-node bandwidth by: (intra-node experts / E) fraction
At E=64, 16 local experts: 75% of tokens stay intra-node (NVLink)

Regime where this wins: large E (≥ 64), high world_size (≥ 16), heterogeneous fabric (NVLink intra-node + InfiniBand inter-node). Dramatically reduces expensive inter-node bandwidth at the cost of a more complex two-level EpGroup topology. Real system: DeepSpeed-MoE hierarchical EP (Rajbhandari 2022). Why rejected as default: two-tier EpGroup requires a topology-aware Transport that knows node boundaries; adds significant implementation complexity; deferred to the §§ Deferred Features Register (un-defer trigger: world_size ≥ 16 and inter-node bandwidth < 100 Gb/s).
