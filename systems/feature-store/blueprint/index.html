Project Name: Feature Store

1. Goal & Scope

A feature store is the infrastructure layer that makes a single feature definition materialize identically into two physical stores — a columnar offline store for point-in-time-correct training reads and a low-latency online store for inference reads — so that training and serving provably consume the same value for the same (entity, feature, time) triple. This document specifies a feature store built end to end in Rust: a registry holding versioned feature definitions, a materialization engine computing feature values from batch and streaming sources, a dual online/offline storage layer, a point-in-time join engine that eliminates label leakage by construction, and a lineage/monitoring plane that makes staleness, drift, and skew observable instead of discovered in a postmortem.

Phase-0 deliverable — numbered modules (a Cargo workspace):

  1. fs-types — the closed dtype system and core domain types (§11).
  2. fs-registry — the Postgres-backed feature/entity/view registry and its HTTP snapshot API.
  3. fs-materialize — the DAG-scheduled materialization engine (sources → transforms → sinks).
  4. fs-offline — the Parquet-on-object-storage offline store and the AS-OF point-in-time join engine (built on Apache DataFusion).
  5. fs-online — the Redis-backed online store and its gRPC serving surface.
  6. fs-lineage — the append-only lineage event emitter and query layer.
  7. fs-monitor — drift, freshness, null-rate, and quality-constraint evaluation.
  8. fs-cli — the featurestore operator command-line tool (apply, materialize, serve, backfill).

System boundaries.

  • Provides: feature definition + versioning, dual-store materialization, point-in-time-correct training reads, sub-5ms online reads, freshness/TTL enforcement, lineage, drift/quality monitoring, multi-tenant namespace isolation.
  • Delegates: object-storage durability (S3/GCS), message transport (Kafka), identity (OIDC provider), warehouse-scale batch compute (Spark, for sources larger than one fs-materialize node can hold) — the store integrates with these, never reimplements them.
  • Does NOT provide: a general SQL warehouse, a model registry, a feature-engineering function library, a feature marketplace, an experiment tracker, a model-serving/inference framework. Each is a named adjacent system (§2) with an explicit integration boundary, never absorbed.

Non-goals: ad hoc analyst SQL over the offline store; storing model weights or hyperparameters; recommending which features to build; serving model predictions; a general workflow orchestrator (Airflow-class).

Deployment model: one Rust workspace, four independently deployable binaries — fs-registry (stateful daemon over Postgres), fs-materialize workers (stateless, horizontally scaled per namespace), fs-online server (co-located sidecar or standalone gRPC service per serving cluster), fs-cli (operator/CI tool). Offline data lives in object storage; no role is a single point of failure once run at replica count ≥ 2.

Target users/operators: ML platform engineers building/operating the store; feature owners (data scientists, ML engineers) defining and consuming features via the registry; on-call SREs responding to freshness/drift/availability pages via docs/runbooks/ (§26).

What later phases unlock: Phase 1 (§13) turns raw registration into a reviewable, versioned contract. Phase 3 (§15) makes the store inference-usable. Phase 5 (§17) makes point-in-time correctness a proven property instead of an assumption. Phase 6 (§18) admits event-time streaming features. Phase 11 (§23) removes the Redis round trip from the serving hot path entirely.

Recommended language: Rust, for the whole system — registry, materialization engine, online/offline store, SDK, and CLI. Rationale: (1) the online-serving hot path carries a hard sub-5ms p99 budget (§4) that rules out any GC'd runtime at the tail; splitting the control plane into a second language to hit that budget (the classic Python-control-plane-plus-Rust-hot-path pattern) doubles the operational surface, doubles the serialization boundary, and reintroduces the two-implementations-of-one-concept risk that Principle 2 (§6, P2) exists to eliminate — a single language closes that gap structurally. (2) The closed dtype system (§6 P12) is best enforced by a strong enum type system; Rust's exhaustive match turns an unhandled dtype variant into a compile error, not a runtime surprise. (3) arrow-rs / parquet / datafusion give a native, zero-FFI path from Parquet through Arrow into a custom AS-OF join operator, avoiding the Python↔Arrow↔Rust marshaling that a split-language design requires. (4) Ownership and Send/Sync make the materialization engine's per-view worker-pool concurrency (§16) auditable at compile time rather than by convention.

Rejected languages:

  • Python — expressive for definitions, but the GIL and unpredictable GC pauses make the online path's p99 budget unreachable without a second-language hot path, which we reject above; relegated to an optional, deferred client binding, never the implementation language.
  • Go — better tail latency than Python, but its GC still injects unpredictable pause spikes at the sub-5ms tail (§4), and its generics history complicates the closed dtype enumeration (§6 P12) relative to Rust's exhaustive enum matching.
  • Java/JVM — mature ecosystem (Michelangelo's and Hopsworks's choice, §33) but JVM GC pause tails and a heavier runtime footprint conflict with the single-digit-millisecond online budget and the one-binary-per-role operational goal.
  • C++ — could hit every latency target, but manual memory management raises the defect rate for a system parsing untrusted, operator-supplied feature-source data (§8); Rust keeps C++-class performance while making a whole memory-safety defect class (§24 T7) unreachable at compile time.

Prerequisites: columnar storage and vectorized execution (Arrow/Parquet); distributed-systems consistency basics (linearizability vs. eventual consistency, background for §7 I2); Kafka consumer-group and offset semantics (§18); Rust ownership/async (tokio) fundamentals; SQL window functions and AS-OF join semantics (§8).

Estimated timeline: Phase 0 (§12) — 3 weeks. Full system (through §23) — 11–14 months for a 4-engineer team, consistent with the per-phase estimates in Appendix B (§40).

Deferred features (each anchored, registered in §37): Python/Java SDK bindings PhaseDeferred("§11"); a live lineage/registry web UI PhaseDeferred("§20"); automated feature recommendation PhaseDeferred("§2"); full on-demand (request-time) transform execution beyond the stub in §18 PhaseDeferred("§18.2"); Apache Iceberg/Delta offline backend PhaseDeferred("§9"); a lock-free (Cliff-Click-style) online cache PhaseDeferred("§23.6"); Apache Flink as the streaming engine PhaseDeferred("§18.6").

2. Why Build This

  • Eliminates training-serving skew structurally, not by convention. Skew is the dominant, most expensive failure mode in production ML: training reads a warehouse computation, serving reads a hand-ported microservice, and the two drift the moment either is patched without the other. Sculley et al. (NeurIPS 2015) name this class of defect "hidden technical debt" and show it dominates lifetime ML system cost. A single materialization engine writing both stores from one in-memory representation (§6 P2, §8) makes divergence a bug in one component, not an emergent property of two.
  • Offline-online parity by construction is the unique systems lesson. Most infrastructure teaches "make it fast" or "make it consistent" in isolation; a feature store teaches both at once, under the added constraint that a historical read (offline, AS-OF) and a live read (online, latest-value) must agree. This is the same "specialize the storage engine to the workload" argument Stonebraker & Cetintemel (ICDE 2005) make, applied twice, to two workloads that must never disagree.
  • Lineage turns a forensic project into a query. Once every feature is a first-class registry object, "which models used this now-corrupted feature, since when" is a lineage/query.py-class SQL query (§20), not a week of grepping notebooks. Polyzotis et al. (SIGMOD Record 2018) name lineage as one of the data-lifecycle problems that separates research ML from production ML.
  • Ownership and reuse compound. A feature used by twelve models amortizes its freshness cost across twelve consumers; a feature store is the only place that reuse is visible and thus schedulable rationally (§16).
  • Reproducibility of training becomes tractable. The offline store retains every historical value; the registry's git_commit field pins exactly which feature definition produced a given training set. Retraining six months later against (feature_refs, as_of) reproduces the same data — the precondition for principled model iteration.
  • Operational consolidation. Without a shared store, every consuming team owns a bespoke pipeline with its own on-call and failure modes; the operational surface grows linearly with team count. A shared materialization engine (§16) bounds that growth.
  • Cross-links: shares its DAG-scheduling problem with build systems and workflow engines (Bazel, Airflow); shares its dual-store consistency problem with cache-aside architectures and CDC pipelines; shares its point-in-time-join problem with temporal databases and audit-log replay systems.

What Mastery Looks Like

  • Can explain, from first principles, why AS-OF join is the only correct primitive for offline reads and can name the two failure modes (label leakage, lookahead bias) it prevents — cemented by Phase 5 (§17), the adversarial PIT fuzzer.
  • Can design a dual-write materialization path that makes offline/online divergence structurally unreachable rather than merely tested-for — cemented by Phase 2 (§14) and Phase 3 (§15).
  • Can reason about freshness as a scheduling problem (priority by SLA-lag, not FIFO) and TTL as a serving-time correctness gate, distinct mechanisms for the same underlying property — cemented by Phase 4 (§16).
  • Can build and defend a streaming/batch parity test and explain watermark/lateness trade-offs from Akidau et al. (VLDB 2015) — cemented by Phase 6 (§18).
  • Can design multi-tenant blast-radius containment at the storage, compute, and registry layers simultaneously, not just at the API layer — cemented by Phase 10 (§22).
  • Can quantify, from a constraints table alone, the memory/IOPS/storage footprint of an arbitrary feature catalog — cemented by the Back-of-Envelope Capacity Model (§34).
  • Can articulate, for each of ≥4 real systems (§33), the one decision it made differently and the regime where that decision wins instead of this blueprint's.

Definitions originate in fs-registry (Postgres, fed from Git-reviewed source per ADR-12) and flow, as an immutable RegistrySnapshot, into both fs-materialize (what to compute) and fs-sdk (what to look up) — this is the trust boundary between "what the system believes exists" and "what a job or a caller assumes exists"; a stale or unauthorized snapshot is the only way the two can disagree, and both are timestamped and versioned (§7 I3).

fs-materialize is the single writer to both stores, fed by a Source (Parquet, SQL, Kafka, HTTP), passed through a named Transform (batch, streaming, on-demand), and fanned out to two Sinks (offline, online) from the same in-memory Arrow RecordBatch — the concurrency boundary is per-FeatureView (§16 locking), not per-row.

fs-offline is Parquet on object storage plus a DataFusion-hosted AS-OF join operator (§8); this is the persistence boundary for history — every value a feature has ever held, partitioned by event_date.

fs-online is Redis (the durable latest-value cache) fronted, from Phase 11 onward (§23), by a per-host /dev/shm zero-copy cache; this is the persistence boundary for "now," bounded by TTL (§6 P9).

fs-online server is the gRPC (tonic) protocol boundary consumers cross to reach fs-online's hot path — a Unix-domain-socket sidecar, never a shared library linked into the caller's process (ADR-21).

fs-lineage and fs-monitor are cross-cutting observers with no write path back into the primary flow; their queue boundary (Kafka topic or local ring buffer) is explicitly allowed to fall behind or drop into a replay buffer without blocking the primary read/write path (§25).

Failure paths (not drawn, present in the running system): registry down → SDK serves a cached snapshot, flags staleness; lineage emitter down → local buffer, replay on recovery; online store down → serving returns FeatureMissReason::SourceError, no offline fallback (offline cannot meet the latency budget); offline store slow → training queries take longer but complete; materialization backlogged → freshness lags until TTL evicts affected keys. Each path is rehearsed in chaos tests (§28).

6. Design Principles

P1 — Point-in-time correctness is the product. A training query for entity E at time T must return the value visible at T. Tradeoff: every offline read pays an AS-OF join cost instead of a plain lookup. Operational implication: timestamps are never optional in the API (§11). Violated: models silently train on future information (§24 T3, §25 FM-1).

P2 — Offline-online parity by construction. One materialization engine writes both stores from one in-memory RecordBatch; there is no separate "online feature" and "offline feature" definition. Tradeoff: couples the two sinks' write cadence. Operational implication: a bug in the shared write path affects both stores identically (visible, not silent). Violated: reintroduces training-serving skew (§2), the exact failure this system exists to remove.

P3 — Feature definition is code. A FeatureDef is Rust source (or the definition-DSL front end, §13), Git-reviewed, CI-tested — never a UI click, never a raw warehouse view. Tradeoff: slower to add a one-off feature. Operational implication: every feature is diffable and revertible. Violated: definitions drift from what is actually materialized (§7 I3).

P4 — Materialization is a DAG. Features depend on sources and on other features; derived features are DAG nodes, scheduled in topological order (§16), never recomputed independently of their parents. Tradeoff: adds a scheduling/locking layer. Violated: derived features can read stale parent values without detection (§25 FM-6).

P5 — Freshness is an explicit SLA. Every FeatureDef declares a max age; breach surfaces as an alert, never silent staleness. Tradeoff: requires per-feature SLA bookkeeping. Violated: consumers trust data that is quietly out of date (§7 I4).

P6 — Schema evolution without rewrite. Safe changes (add nullable field, widen a numeric dtype) apply without touching history; unsafe changes require an explicit migration (§21). Tradeoff: the registry must classify every change. Violated: schema changes force a full historical rewrite, which does not scale past a few hundred features.

P7 — Lineage is captured by default, not opt-in. Every materialization, read, and write emits a LineageEvent (§11); this cannot be disabled per-feature. Tradeoff: constant lineage-emission overhead. Violated: opt-in lineage systems rot within a quarter — no one enables it until the incident that needed it.

P8 — The registry is the source of truth. When registry and stores disagree on what exists, the registry wins; orphaned store data is garbage-collected on schedule (§16). Tradeoff: a registry outage blocks new materialization (mitigated by cached snapshots, §25 FM-3). Violated: a manual store write becomes silently-consumed garbage data.

P9 — TTL and eviction are explicit. Every online value has a TTL; past it, the value is evicted, not served stale (§4). Tradeoff: a broken materialization pipeline degrades to "no data" rather than "stale data" — a harder-looking but more honest failure. Violated: a model silently serves on data that predates a source outage.

P10 — Multi-tenant isolation is structural. Namespaces are enforced at the registry, storage (key/path prefix), and compute (worker pool/quota) layers simultaneously (§22), not just at the API. Tradeoff: more moving parts per namespace. Violated: one namespace's misbehaving job starves or corrupts another's data.

P11 — Observability is from day one. Every job, read, and write emits structured logs (tracing) and metrics; there is no "add metrics later." Tradeoff: instrumentation overhead on the hot path (bounded, measured in §30). Violated: the system becomes undebuggable in production, the single most common reason internal platforms get torn out.

P12 — Closed dtype set, no leaky pickled/opaque objects. Every FeatureValue variant is one of a fixed enumeration (§11); arbitrary serialized blobs are refused at registration. Tradeoff: some feature types (e.g., ragged structures) need explicit encoding work. Violated: the Rust online hot path cannot deserialize an opaque blob without a schema round-trip, defeating P1 of Rust's rationale (§1).

P13 — Idempotent materialization, content-addressed writes. Running MaterializationJob(view, start_ts, end_ts) twice produces the same offline partition (content-addressed filename) and the same online state (upsert, not append) (§16). Tradeoff: requires deterministic partition naming. Violated: retries silently double-count or duplicate history.

P14 — Backpressure over silent overload. Every ingress (materialization queue, online RPC, streaming consumer) has an explicit concurrency/queue-depth limit; excess is rejected (RESOURCE_EXHAUSTED) or prioritized (§16, §23), never silently queued without bound. Tradeoff: callers must handle rejection. Violated: unbounded queues turn a transient spike into an unrecoverable memory/latency collapse.

Debugging methodology. fs-materialize ships a deterministic simulator (fs-materialize/src/sim.rs, driven by tests/pit_fuzz/) that replays a scripted sequence of source events, materialization triggers, and reads against a single-process in-memory harness, with one assertion per invariant above (I1–I14) executed after every step. A failing assertion pinpoints the exact simulated step, and the simulator's random seed is logged so the failure is reproducible byte-for-byte (§17). The simulator's per-step assertion set:

  • After every simulated read: assert I1, I11 (AS-OF answer correctness) and I10 (re-issuing the same read reproduces the same answer).
  • After every simulated materialization: assert I6 (re-running the identical job is a no-op), I13 (the DAG the job executed against was acyclic), I2 (online and offline states agree post-write).
  • After every simulated online write: assert I14 (no monotonicity regression) and I5 (a subsequent read past the injected TTL clock returns TtlExpired).
  • After every simulated registry mutation: assert I3 (no orphaned store data references a removed definition), I7 (an unsafe change was rejected without an accompanying migration), I8 (exactly one lineage event was recorded for the mutation).
  • After every simulated cross-namespace read attempt: assert I9 (denied unless an explicit grant exists), I12 (the returned value's dtype is in the closed enumeration).
  • After every simulated freshness-check tick: assert I4 (a view past 1.5× its SLA has triggered the escalation path).

8. Domain Model

8.1 Entity, Feature, and Feature-View Model

An entity (EntityDef) is the thing features describe (user, item, merchant). A feature (FeatureDef) is a named, typed, owned value computed from a source at a point in time. A feature view (FeatureView) groups features sharing a source and a materialization schedule — the unit of scheduling (§16). A feature service (FeatureService) groups features one model consumes — the unit of deployment and the lineage-to-model boundary (§20). Relationships: RegistrySnapshot ⊇ {EntityDef}, {FeatureView ⊇ {FeatureDef}}, {FeatureService}; a FeatureService references features by "view:feature" refs resolved against the snapshot.

8.2 Dual-Store Record Layouts

Offline partition path: offline/{namespace}/{view}/event_date={YYYY-MM-DD}/part-{content_hash}.parquet. Required columns: entity join-key column(s) (named per EntityDef.join_key), event_ts (timestamp[us, UTC]), ingest_ts (timestamp[us, UTC]), one column per feature (named per FeatureDef.name, typed per its DType). Sort order within a file: (join_key, event_ts) — this is what makes the AS-OF operator a single sorted-merge pass per entity, not a scan.

Online record: a Redis hash fs:{namespace}:{view}:{entity_id}, fields = feature names, values = packed protobuf FeatureValuePb (§11), hash-level TTL = the view's TTL. One hash per (view, entity) — chosen so a multi-feature read is one HMGET, not N GETs.

8.3 Materialization State Machine

PENDING --submit--> QUEUED --dequeue(worker)--> RUNNING
RUNNING --success--> COMPLETE
RUNNING --failure(retryable)--> QUEUED (backoff, ≤3 attempts)
RUNNING --failure(exhausted)--> FAILED --page on-call--> (manual retry) QUEUED
QUEUED --view-locked--> BLOCKED --lock released--> QUEUED

A MaterializationJob (§11) transitions through this machine under the scheduler (§16); COMPLETE and FAILED both emit a LineageEvent (I8); FAILED additionally triggers the freshness-breach path (I4).

8.4 Point-in-Time Join Algorithm (AS-OF)

Given an entity/query table Q(entity_id, query_ts) and a feature history H(entity_id, event_ts, value…), the point-in-time-correct answer for row q ∈ Q is the row h ∈ H with h.entity_id = q.entity_id and h.event_ts = max{ t : t ≤ q.query_ts }; absent such h, the answer is a structured miss (§11 FeatureMissReason), never a sentinel value (ADR-15). Implementation (fs-offline, a custom DataFusion ExecutionPlan, per Reference Implementation 5): (1) partition-prune H to the relevant event_date range; (2) sort-merge both tables by (entity_id, ts) — this is the two-stage "filter then nearest-prior" approach DuckDB's native ASOF JOIN uses (Reference Implementation 6), reimplemented natively rather than embedded; (3) for entities with Q-cardinality larger than fits in one DataFusion partition, fall back to the Spark-hosted variant of the same algorithm (ADR-13). Tiebreak on duplicate event_ts for the same entity: (event_ts, ingest_ts) descending, deterministic (I10).

8.5 Worked Example

Entity user, feature age (int32), history: alice → (2024-01-01, 30), (2024-04-01, 31). Query (alice, 2024-03-15) → nearest-prior is (2024-01-01, 30) ⇒ answer age=30. Query (alice, 2024-04-01) → exact match ⇒ age=31. Query (alice, 2023-12-01) → no prior observation ⇒ miss, FeatureMissReason::NotMaterialized. Query (alice, 2024-06-01) with max_age = 30d → nearest-prior (2024-04-01, 31) is 61 days stale ⇒ miss, FeatureMissReason::TtlExpired (offline analogue of online TTL, distinct enforcement point per P9).

8.6 Malformed-Input Example

A Parquet source row with event_ts null: rejected at ingest by the offline sink's schema validator (§8.2 required columns); the row is routed to a rejects/ sibling partition with a reject_reason column, the materialization continues over the remaining valid rows, and a LineageEvent(kind=MaterializationFailure) is not emitted for the whole job (partial success is not job failure) but a quality_constraint_violation metric increments (§19). A source row whose value for an int32 feature does not parse as int32 (e.g., a stray string in a numeric warehouse column) is likewise rejected to rejects/, never coerced silently — silent coercion is exactly the sentinel-value failure mode ADR-15 rejects.

8.7 Failure-Path Example

fs-materialize writes the offline partition successfully, then the online HSET pipeline fails mid-batch (Redis connection reset at row 6,000 of 10,000). Recovery: the sink does not partially commit — HSET writes are pipelined but the sink tracks a per-batch watermark; on reconnect it re-issues from the last acknowledged row (idempotent because HSET is an upsert, I6). The job is marked COMPLETE only when both sinks confirm; if the online sink cannot recover within its retry budget, the job transitions to FAILED, the offline partition is not rolled back (offline is append-only and already correct — I1 does not require online success), and I2 (parity) briefly does not hold until the retried job's online write lands — this window is bounded by the retry backoff and surfaced via the parity sampler (§19).

  • conformance/phase0_user_history.parquet — the 10k-row synthetic fixture, fixed seed 42.
  • conformance/phase0_asof_cases.json — 8 named (entity, ts) → expected-value pairs covering §8.5/§8.6.
  • conformance/phase0_malformed_row.parquet — one row with null event_ts, expects routing to rejects/ (§8.6).

12.6 Pitfalls

  • Forgetting partition pruning on event_date makes the join scan the whole fixture — invisible at 10k rows, catastrophic at Phase 4 scale; catch via a DataFusion EXPLAIN assertion in CI.
  • Using f64 timestamps anywhere reintroduces float-equality bugs in tiebreaks (I10) — enforce timestamp[us, UTC] end to end.
  • SQLite dev-mode registry silently permits concurrent writers to corrupt a row — acceptable only because Phase 0 is single-process (flagged, revisited at ADR-11's Postgres cutover in §13).

12.7 Performance Concerns

Single-node DataFusion scan of 10k rows is dominated by Parquet decode, not join logic — no tuning needed yet; establishes the baseline the Phase 4-scale benchmark (§16) will be compared against.

12.8 Edge Cases

  • Query timestamp before any observation (miss).
  • query exactly at an observation boundary (exact match, not off-by-one).
  • duplicate event_ts for the same entity (deterministic tiebreak, I10).
  • malformed row with null event_ts (§8.6).
  • empty entity dataframe (zero-row result, not an error).

12.9 Failure Analysis

  • A DataFusion panic mid-join (e.g., an unhandled dtype in the AS-OF operator) must not poison the whole process — fs-offline's query executor runs the plan inside std::panic::catch_unwind and returns a StoreError, logged with the query fingerprint.
  • Blast radius: one query, not the process.
  • Operator visibility: pit_join_panic_total metric.

12.10 Operational Notes

  • No production deployment yet — this phase runs only in CI and local dev.
  • Structured logging (tracing) is wired from the first line of code (P11), even though there is no dashboard to consume it yet; this is deliberate so instrumentation is never "added later."

  • Applying migrations out of order across environments silently drifts schemas — sqlx migrate is run only through the CI-gated release pipeline (§29), never ad hoc against production.

13.7 Performance Concerns

13.8 Edge Cases

  • Two concurrent apply calls for the same view (registry-level row lock, first wins, second gets a conflict error).
  • a Git commit that fails mid-parse (partial repo state) — git_sync validates the full commit before applying anything, all-or-nothing.
  • a namespace with zero registered entities querying /snapshot (valid empty result, not an error).

13.9 Failure Analysis

  • Postgres unavailability: fs-registry serves the last-cached snapshot with a stale: true flag (bounded by RTO ≤ 15 min, §4); writes are rejected with ServiceUnavailable rather than silently queued (P14).
  • Detection: registry_db_healthy gauge.
  • Recovery: automatic reconnect with exponential backoff; manual runbook docs/runbooks/registry-outage.md.

13.10 Operational Notes

  • Metrics: registry_apply_total{result}, registry_snapshot_age_seconds.
  • Deployment: fs-registry runs with ≥ 2 replicas behind a load balancer, Postgres itself replicated (standard Postgres HA, not reimplemented here).
  • Rollback: a bad definition is reverted by a Git revert commit, re-synced automatically.

14. Phase 2 — Batch Materialization Engine

14.1 Objectives

Build the full fs-materialize DAG engine: Source/Transform/Sink traits, topological execution (P4), and the dual offline+online write fan-out from one RecordBatch (P2) — online sink still writes to an in-memory stub until §15.

14.2 Detailed Implementation Steps

  • Define Source (Parquet, SQL, HTTP; Kafka deferred to §18), Transform (batch: DataFusion DataFrame ops per ADR-07), Sink (offline Parquet writer per §8.2 layout; online — stub) traits in fs-materialize.
  • Implement the DAG builder: given a RegistrySnapshot, construct a dependency graph over FeatureViews (edges = derived-feature references), execute in topological order (P4, I13).
  • Implement content-addressed partition naming (part-{sha256(job_id,start_ts,end_ts)}.parquet) for idempotency (P13, I6).
  • Wire LineageEvent emission (P7, I8) at job start/complete/failure.

Data structures introduced this phase: MaterializationJob (§11), the Transform trait (batch/DataFusion impl), the online Sink trait's first real implementation target (still an in-memory stub pending §15), content-addressed partition-naming scheme.

14.3 Deliverable

featurestore materialize --view user_demographics --start ... --end ... produces a correctly-partitioned, content-addressed offline dataset and a matching sequence of LineageEvents, inspectable via fs-cli lineage show <job_id>.

14.4 Acceptance Criteria

  • Running the same job twice produces byte-identical Parquet output and zero duplicate online writes (I6, verified in conformance/phase2_idempotency.json).
  • a 3-node derived-feature DAG materializes in strict topological order, verified by timestamp ordering in the lineage log.
  • job throughput ≥ 5,000 rows/sec on the Phase-0 fixture on a 4-core laptop.

14.5 Conformance Fixtures

  • conformance/phase2_dag_3node.ron — parent/child/grandchild feature views.
  • conformance/phase2_idempotency.json — expected identical hash across two runs.
  • conformance/phase2_retry_partial_batch.parquet — simulates a mid-batch write failure for retry testing (feeds §14.9).

14.6 Pitfalls

  • A non-deterministic DataFusion physical plan (e.g., unordered GROUP BY output) breaks I6/I10 silently — pin SortExec after every aggregation.
  • Forgetting to dedupe on retry double-counts rows in the offline partition — content-addressing (P13) catches this only if the content, not just the job id, is hashed.

14.7 Performance Concerns

  • DataFusion's default target_partitions over-parallelizes small jobs, adding scheduling overhead; tuned per-job based on estimated row count (§16 scheduler passes a hint).
  • Arrow RecordBatch reuse across the offline/online fan-out avoids a full re-serialization pass (P2's structural mechanism depends on this).

14.8 Edge Cases

  • A FeatureView with zero rows in the requested time range (valid empty materialization, not an error, still emits MaterializationComplete).
  • a derived view whose parent has not yet materialized for the requested range (blocked, not silently computed on stale/absent parent data — enforced by the DAG scheduler, formalized in §16).
  • a source schema drift mid-range (some files have a column the others lack) — handled by Arrow schema-union with null-fill, logged as a quality warning (§19).

14.9 Failure Analysis

  • Offline write succeeds, process crashes before the online stub write: on restart, the job's COMPLETE status was never persisted, so the scheduler (§16) re-submits it; content-addressing means the re-run offline write is a no-op (I6) and only the online write actually executes.
  • Blast radius: bounded to one job; no partial-committed state survives a crash because Parquet writes are atomic-rename-on-completion.

14.10 Operational Notes

  • Metrics: materialize_job_duration_seconds{view}, materialize_rows_written_total{view,sink}.
  • Every job's lineage event carries the git_commit of the definition it ran under, so a bad materialization is traceable to the exact definition version (§20).

15. Phase 3 — Online Store (Redis-Backed Serving)

15.1 Objectives

Replace the in-memory online stub with Redis (ADR-02): implement fs-online's OnlineStore trait impl, the key layout (§8.2), the packed-protobuf encoding (ADR-14), and the gRPC serving surface (ADR-04, ADR-21), meeting the §4 p99 ≤ 5ms budget.

15.2 Detailed Implementation Steps

  • Define the protobuf schema (GetFeaturesRequest/Response, FeatureValuePb oneof over the closed dtype set, §11) compiled via prost.
  • Implement the Redis sink: pipelined HSET per materialization batch, hash-level TTL set to the view's TTL (P9).
  • Implement the gRPC server (tonic) over a Unix domain socket (ADR-21): HMGET pipelined across requested entities, deserialize protobuf, assemble GetFeaturesResponse, synthesizing FeatureMissReason::NotMaterialized/TtlExpired for absent keys per I5.
  • Add a connection pool sized max(8, num_cpus*2) to Redis.
  • Add the online write-time monotonicity check (I14): reject an HSET whose event_ts is older than the currently-stored value.

Data structures introduced this phase: FeatureValuePb (protobuf, §11/ADR-14), the Redis-backed OnlineStore trait impl, the gRPC GetFeatures service definition (§11 OnlineStore/OnlineFeatureService-equivalent), the connection-pool configuration struct.

15.3 Deliverable

A running fs-online server answering GetFeatures gRPC calls against a locally materialized view, with tests/bench/online_bench.rs (criterion) reporting p50/p99/p999.

15.4 Acceptance Criteria

  • p99 ≤ 5ms for (1 entity, 4 features) on a local Redis, measured over ≥ 10,000 requests (§4).
  • p99 ≤ 20ms for (100 entities, 16 features).
  • zero online-store monotonicity regressions (I14) across conformance/phase3_out_of_order_write.json (100 shuffled-timestamp writes).
  • a benchmark regression > 2× fails CI (§29).

15.5 Conformance Fixtures

  • conformance/phase3_out_of_order_write.json — writes delivered out of event_ts order, expects I14 to hold.
  • conformance/phase3_ttl_expiry.json — a key materialized then read after synthetic TTL fast-forward, expects TtlExpired.
  • conformance/phase3_miss_unknown_entity.json — read for a never-materialized entity, expects NotMaterialized.

15.6 Pitfalls

  • HMGET on a non-existent hash returns all-nil, indistinguishable from "hash exists but fields are null" unless the server also checks EXISTS — conflating the two collapses NotMaterialized into a false null read; the server issues both in one pipeline round-trip (no added RTT, §15.7).
  • Redis maxmemory-policy allkeys-lru under memory pressure can evict a just-written key before it's read — mitigated by monitoring evicted_keys and alerting before it affects freshness-critical views.

15.7 Performance Concerns

  • One pipelined round-trip per request batch, never N sequential HMGETs.
  • Protobuf decode allocation is the dominant per-request cost at this phase (still Redis + protobuf, not yet the shm cache of §23) — measured via criterion flamegraphs, budgeted at < 200µs decode time per response.

15.8 Edge Cases

  • Entity present but a specific requested feature never registered on that view (UnknownFeature, not NotMaterialized — distinct miss reasons matter for debugging).
  • Redis Cluster partial partition (one shard unreachable) — routed-around via cluster topology awareness, not a full outage.
  • a GetFeaturesRequest with > 64 feature refs (§4 cap) rejected with a clear error rather than silently truncated.

15.9 Failure Analysis

  • Full Redis unavailability: circuit breaker opens after 5 consecutive timeouts, stays open 10s, then half-open probes; during open state all reads return SourceError immediately (no offline fallback — offline cannot meet the latency budget, P1 vs.
  • P9 tradeoff made explicit here).
  • Detection: redis_circuit_breaker_state gauge.
  • Recovery: automatic on Redis health restoration; manual escalation path in docs/runbooks/online-store-outage.md.

15.10 Operational Notes

  • Metrics: online_read_latency_seconds{quantile}, online_write_batch_size, redis_pool_wait_seconds, redis_evicted_keys_total.
  • Deployment: fs-online as a sidecar per serving host, sharing the Unix domain socket with the inference process; rollback is a binary swap, no data migration (protocol versioned per §27).

16. Phase 4 — Materialization Scheduler & Freshness Enforcement

16.1 Objectives

Move materialization from on-demand CLI invocation to a scheduled, SLA-aware, concurrency-controlled process (P5, P14): cron triggers, priority-by-freshness-lag queueing, per-view locking, and backfill support.

16.2 Detailed Implementation Steps

  • Implement fs-materialize/src/scheduler.rs: a tokio task polling the registry every 60s for views whose next cron-scheduled run has passed (ADR-10, custom over Airflow/Dagster).
  • Implement a priority queue ordered by (freshness_lag desc, submitted_at) (P14 — never plain FIFO, which starves SLA-critical views under backlog).
  • Implement per-view advisory locking (Postgres row lock) so two jobs for the same view never run concurrently (I6's precondition).
  • Implement featurestore backfill --view --start --end, submitting a sequence of jobs over a historical range through the same write paths as live materialization (I6 applies identically).
  • Compute and emit a FreshnessReport (§11) after every job (I4).

Data structures introduced this phase: the priority-queue entry type (freshness_lag, submitted_at, view), the per-view Postgres advisory-lock wrapper, FreshnessReport (§11), the backfill job-range generator.

16.3 Deliverable

A running scheduler daemon that materializes registered views on their cron schedule without operator intervention, visible via fs-cli scheduler status showing per-view lag.

16.4 Acceptance Criteria

  • A view configured with a 15-minute SLA and a 10-minute cron completes within SLA in ≥ 99% of a 24-hour simulated run (conformance/phase4_24h_sim.json).
  • when the worker pool is saturated (max_inflight_jobs=4, 10 pending views), the view with the largest freshness lag is scheduled first, verified by execution-order assertion.
  • two concurrent triggers for the same view result in exactly one execution, the other rejected as ViewLocked.

16.5 Conformance Fixtures

  • conformance/phase4_24h_sim.json — scripted 24h of cron triggers against 10 views with varying SLAs.
  • conformance/phase4_lock_contention.json — two simultaneous triggers, same view.
  • conformance/phase4_backfill_range.json — a 90-day backfill request, expects one job per day boundary, all idempotent.

16.6 Pitfalls

  • A stuck job holding its view lock indefinitely silently blocks all future materialization for that view — mitigated by a lock timeout (configurable, default 30 min) plus a scheduler_view_lock_held_seconds metric so a stuck lock is visible before the next SLA breach.
  • FIFO-by-accident (e.g., an unstable sort in the priority queue) reintroduces starvation even with the priority field present — verified by a property test asserting strict ordering under ties.

16.7 Performance Concerns

  • Polling the registry every 60s at scale (thousands of views) risks a full-table scan; mitigated by indexing feature_views(next_scheduled_run) and querying only due rows.
  • Backfill of a long historical range must not monopolize the worker pool ahead of live-freshness-critical jobs — backfill jobs are tagged and scheduled at lower priority by default.

16.8 Edge Cases

  • Clock skew between the scheduler host and Postgres (cron due-check uses DB now(), not host clock, to avoid drift).
  • a view whose cron expression is malformed (rejected at registry apply time, I13-adjacent validation, never at schedule time).
  • a backfill range overlapping an in-progress live materialization for the same view (blocked by the same per-view lock, no special-casing needed).

16.9 Failure Analysis

  • Three consecutive job failures for a view: scheduler stops auto-retrying, emits MaterializationFailure lineage event, pages on-call per the freshness-breach escalation path (I4).
  • Detection: materialize_consecutive_failures{view} gauge.
  • Forensic artifact: the failed job's full error and the source-data snapshot it read, both linked from the lineage event (§20).

16.10 Operational Notes

  • Metrics: scheduler_queue_depth, scheduler_view_lock_held_seconds, freshness_lag_seconds{view}.
  • Runbook: docs/runbooks/materialization-stuck.md — diagnosis steps (check lock table, check worker pool saturation) and mitigation (force-unlock, manual re-trigger).

17. Phase 5 — Point-in-Time Correctness Adversarial Fuzzing

17.1 Objectives

Replace hand-written PIT tests with a differential adversarial fuzzer (ADR-22) that is the project's single most important correctness gate (I1, I10, I11) — historically, in comparable systems, the class of bug most likely to escape manual review.

17.2 Detailed Implementation Steps

  • Implement fuzz/pit_fuzz.rs: generates a random feature history (N entities, M features, K observations at random UTC timestamps over a year) and a random query batch.
  • Compute the answer two ways: (a) through fs-offline's DataFusion AS-OF operator (§8.4); (b) through a deliberately separate brute-force oracle (fuzz/oracle.rs: linear scan, filter ≤ T, take max) — the two must agree exactly on every query (I1, I11).
  • Add mutation testing (fuzz/mutants/): inject a known bug (e.g., >= instead of <= in the AS-OF predicate) into a forked build and assert the fuzzer catches it within its per-scale query budget.
  • Add shrinking (Hypothesis-style, via proptest): on a failing case, minimize entity/feature/observation counts while preserving the failure, append the minimized case to the regression corpus.

Data structures introduced this phase: the fuzzer's synthetic-history generator config, the oracle's brute-force scan function signature, the mutation-testing harness's mutant registry, the shrinking engine's minimization state.

17.3 Deliverable

cargo fuzz run pit_fuzz (unit scale) runs in CI on every PR; nightly and weekly jobs run integration/stress scales (§17.4); every historical failure lives as a permanent regression fixture in fuzz/regressions/.

17.4 Acceptance Criteria

  • Unit scale (N=10,M=5,K=20,100 queries) completes in < 1s, zero oracle mismatches, blocking on every PR.
  • integration scale (N=10,000,M=50,K=200,100,000 queries) completes in < 10 min nightly.
  • stress scale (N=1M,M=200,K=1,000,10M queries) completes in < 2h weekly.
  • 100% of the mutation-tested known bugs (≥ 6 seeded mutants) are caught within budget.

17.5 Conformance Fixtures

  • fuzz/regressions/*.json — every previously-found failing case, replayed on every run (regression-proof).
  • fuzz/mutants/asof_ge_instead_of_le.rs, fuzz/mutants/tiebreak_ascending.rs, fuzz/mutants/off_by_one_partition.rs — named seeded bugs the fuzzer must catch (§17.2).

17.6 Pitfalls

  • A fuzzer whose random seed is not logged turns every CI failure into an unreproducible flake — the seed is attached to every failure artifact and re-runnable verbatim.
  • A fuzzer that only tests the "happy path" temporal distribution (uniformly random timestamps) under-samples the adversarial corners (duplicate timestamps, partition-boundary timestamps, timezone edge cases) that are actually where bugs live — §17.2's generator explicitly biases toward these corners at a configurable rate.

17.7 Performance Concerns

The oracle (linear scan) is deliberately unoptimized — its cost, not its speed, is the point; stress-scale runs are budgeted as an offline nightly/weekly job, never blocking a PR, precisely because oracle cost scales linearly with history size.

17.8 Edge Cases

  • Duplicate event_ts for the same (entity, feature) (I10 tiebreak).
  • query exactly on a partition boundary (verifies partition pruning doesn't drop or duplicate rows).
  • all observations after the query timestamp (miss, not the earliest observation).
  • floating-point-adjacent timestamp rounding (excluded by construction — timestamps are i64 microseconds, never f64, per §12.6).

17.9 Failure Analysis

  • A newly-introduced regression is caught the same day it's merged (CI-blocking at unit scale) in the common case; a regression only visible at stress scale is caught within a week and immediately shrunk to a minimal, permanent regression fixture — closing the gap for next time.
  • Blast radius if missed: silent label leakage in a training run using the affected code path, the single worst outcome this whole blueprint exists to prevent (§2).

17.10 Operational Notes

  • CI gating: fuzz.yml workflow blocks merge on unit-scale mismatch; nightly/weekly scales page on-call only on new (non-regression-corpus) mismatches.
  • Metrics: pit_fuzz_oracle_mismatch_total, pit_fuzz_mutant_caught_total{mutant}.

18. Phase 6 — Streaming Feature Views

18.1 Objectives

Admit event-time streaming sources (Kafka, ADR-08) with windowed aggregation, watermark-based lateness handling (Akidau et al., VLDB 2015), and a batch/streaming parity guarantee.

18.2 Detailed Implementation Steps

  • Implement a rdkafka-based consumer (fs-materialize/src/sources/kafka.rs) parsing Avro/protobuf-encoded events per a registered source schema.
  • Implement a watermark tracker per partition: default 10s allowed lateness (documented, tunable); events older than watermark - lateness route to a late_arrivals topic rather than merging into a closed window (never silent).
  • Implement tumbling, sliding, and session window transforms producing (entity_id, window_start, window_end, aggregate) records; on window close, upsert the online store (latest only) and append the offline store (every window close, for backtesting).
  • Implement embedded RocksDB state (keyed (view, entity_id, window_start)) with S3 checkpointing every 60s, keyed by Kafka partition+offset, for exactly-once-effect recovery.
  • On-demand transforms (request-time Python/Rust UDFs over raw inputs, Tecton's third feature-view category) are stubbed at the trait level only in this phase — full execution is PhaseDeferred("§18.2").

Data structures introduced this phase: the Kafka Source impl, the per-partition watermark tracker, the RocksDB state-store key (view, entity_id, window_start), the late_arrivals routing sink, the window-close record (entity_id, window_start, window_end, aggregate).

18.3 Deliverable

A streaming FeatureView consuming a Kafka topic, producing windowed aggregates in both stores, recoverable from a checkpoint after a simulated consumer crash.

18.4 Acceptance Criteria

  • Batch/streaming parity test (conformance/phase6_parity_24h.json): materializing the same 24h period via batch (over a warehouse copy) and via streaming (over Kafka replay) produces byte-identical offline tables, modulo a documented ±1e-6 float-aggregation tolerance.
  • consumer crash-and-resume from checkpoint loses ≤ 60s of processed-but-uncommitted state (bounded by the checkpoint interval).
  • late-arrival routing correctly separates ≥ 99% of synthetically delayed events in conformance/phase6_late_arrivals.json.

18.5 Conformance Fixtures

  • conformance/phase6_parity_24h.json — dual batch/streaming materialization comparison.
  • conformance/phase6_late_arrivals.json — synthetic Kafka replay with injected out-of-order delivery.
  • conformance/phase6_checkpoint_crash.json — consumer killed mid-window, resumed, state compared to a golden run.

18.6 Pitfalls

  • An unbounded lateness budget (allowed_lateness = ∞) never closes a window, growing RocksDB state unboundedly — the default 10s is a deliberate, documented tradeoff (§4 has no explicit row for this; it is stated here as a hard default).
  • A checkpoint that captures Kafka offset but not the partial-window aggregate state is not actually resumable — both must be captured atomically, verified by phase6_checkpoint_crash.

18.7 Performance Concerns

  • Approximate sketches (HyperLogLog for distinct count, t-digest for quantiles) are used above a configurable cardinality threshold to keep RocksDB state size sub-linear in entity count for high-cardinality aggregations; exact aggregation remains the default below threshold.
  • State size is bounded by active_windows × entity_count, monitored (§18.10).

18.8 Edge Cases

  • A late arrival for a window already reflected in the online store (online is not retroactively corrected — documented known limitation, since "latest" has already moved on.
  • offline is corrected via the periodic re-materialization job).
  • a Kafka partition rebalance mid-window (RocksDB state is partition-keyed, so a rebalance requires state migration — handled by pausing affected partitions until state transfer completes, not by silently dropping state).
  • duplicate Kafka delivery (idempotent via the same content-addressing as batch, P13).

18.9 Failure Analysis

  • Consumer process crash: on restart, resumes from the last S3 checkpoint and replays Kafka from the recorded offset; state divergence from the pre-crash in-flight window is bounded by the checkpoint interval (60s) and is the accepted cost of the design (ADR-08 rejects Flink's more precise exactly-once checkpointing at this phase's operational-complexity budget).
  • Detection: streaming_consumer_restarts_total, streaming_checkpoint_lag_seconds.

18.10 Operational Notes

  • Metrics: streaming_watermark_lag_seconds{partition}, streaming_late_arrivals_total, streaming_state_size_bytes{view}.
  • Deployment: one consumer process per Kafka partition group, horizontally scaled with partition count; rollback requires draining in-flight state to a checkpoint before redeploy.

19. Phase 7 — Feature Monitoring (Drift, Quality, Parity)

19.1 Objectives

Wire fs-monitor: drift detection, freshness/null-rate metrics, Deequ-style declarative quality constraints (Schelter et al., VLDB 2018), and the online/offline parity sampler that directly checks I2.

19.2 Detailed Implementation Steps

  • Compute, per materialization batch, summary statistics (mean, p50, p95, distinct count, null fraction) and compare against a rolling N-batch baseline using a configurable metric (PSI, KS, Wasserstein, or JS — DriftReport, §11); default thresholds PSI > 0.2 warn, > 0.5 fail.
  • Implement declarative QualityConstraint evaluation (not_null, in_range, distinct_count, regex) at materialization time (P11 — computed once, at write time, never by a separate re-scan).
  • Implement the parity sampler: a low-rate (~100 pairs/min) background job reading a random (entity, view) pair from both stores and asserting agreement (I2 directly); non-zero parity_disagreements_total is a paging alert.
  • Implement alert-quality discipline: every alert requires an owner and a runbook (§26); unowned alerts auto-silence after 30 days.

Data structures introduced this phase: DriftReport, QualityConstraint (§11), the rolling-baseline window buffer, the parity sampler's random-pair selector, the alert-ownership/runbook-link registry.

19.3 Deliverable

A running fs-monitor process emitting Prometheus metrics and Grafana-ready dashboards for drift, freshness, null rate, and parity, with the parity sampler continuously verifying I2 in production.

19.4 Acceptance Criteria

  • Drift detection flags a synthetically injected 3-sigma distribution shift within one materialization cycle (conformance/phase7_drift_injection.json), PSI computed within ±0.01 of a reference implementation.
  • a severity=fail quality constraint violation aborts the materialization and reverts the partial write (verified: zero partial rows land in the offline partition).
  • the parity sampler detects a synthetically introduced 1% online/offline disagreement within 10 minutes at the configured sample rate.

19.5 Conformance Fixtures

  • conformance/phase7_drift_injection.json — baseline + shifted distribution pair.
  • conformance/phase7_quality_fail_abort.json — a batch violating an in_range fail-severity constraint.
  • conformance/phase7_parity_disagreement.json — deliberately desynced online/offline pair.

19.6 Pitfalls

  • Computing drift against a too-short rolling baseline (e.g., 1 prior batch) makes every batch "drifted" by noise — default baseline window is 30 batches, tunable per feature.
  • A severity=fail constraint that aborts after the offline write has already landed leaves a partial write — the constraint check must run before the sink commit, not after (ordering bug caught in phase7_quality_fail_abort).

19.7 Performance Concerns

Drift statistics are computed as a single pass over the same RecordBatch already in memory for the write (no second read of the offline store) — this is what keeps monitoring cost from scaling with catalog size independently of materialization cost.

19.8 Edge Cases

  • A feature with fewer than 30 historical batches (baseline warm-up period — drift checks are skipped, not falsely triggered, until enough history exists).
  • a quality constraint referencing a feature that was since renamed (registry validation, §21, rejects the stale reference at apply time).
  • the parity sampler hitting a TTL-expired online key mid-sample (excluded from the comparison, not counted as a disagreement — expiry is expected behavior, not skew).

19.9 Failure Analysis

Alert storm from a single upstream source outage triggering simultaneous drift+freshness+null-rate alerts across dozens of dependent views: the alert-quality dashboard (§19.2) correlates same-root-cause alerts by shared source_ref, collapsing them into one page rather than dozens (§25 FM detail).

19.10 Operational Notes

  • Metrics: drift_psi{feature}, null_rate{feature}, quality_constraint_violations_total{constraint}, parity_disagreements_total.
  • Dashboards: one per namespace, aggregating across its views.
  • Runbooks: docs/runbooks/drift-alert.md, docs/runbooks/parity-disagreement.md (the latter pages immediately — it signals I2 has broken).

20. Phase 8 — Lineage Capture & Query

20.1 Objectives

Make lineage (already emitted since §14, P7) queryable: storage, compaction, and a query layer answering "which models depend on feature F" within an operationally useful time bound.

20.2 Detailed Implementation Steps

  • Implement the append-only lineage log: local ring-buffer → Kafka topic → Parquet-on-S3 sink (ADR-17), decoupled from the primary write path so a lineage outage never blocks materialization (P7 without a hard dependency).
  • Implement a 6-hourly compaction job (itself a MaterializationJob, reusing §16's scheduler/retry/locking infrastructure) that dedupes by event_id, sorts by occurred_at, writes date-partitioned Parquet.
  • Implement fs-lineage/src/query.rs: a DataFusion-backed query layer answering ancestor/descendant/full-trace queries against the compacted table, exposed via both a Rust API and fs-cli lineage.
  • Cap individual events at 10MB; split oversized events into chained events sharing trace_id with a sequence number (§20.6).

Data structures introduced this phase: LineageEvent (§11, already emitted since §14 — this phase adds its storage/query layer), the compaction job's dedupe-by-event_id pass, the DataFusion-backed ancestor/descendant query functions.

20.3 Deliverable

fs-cli lineage ancestors --feature user_demographics:age and fs-cli lineage trace --trace-id <id> return correct, complete results against a populated lineage log.

20.4 Acceptance Criteria

  • Given the name of a synthetically "corrupted" feature, lineage ancestors/descendants identify 100% of dependent FeatureServices and the exact MaterializationJobs that read the corrupted source, in ≤ 5 minutes of engineer time (measured operator drill, conformance/phase8_incident_drill.md).
  • compaction dedupes a synthetic stream with 5% duplicate event_ids to exactly 0 duplicates in the compacted table.

20.5 Conformance Fixtures

  • conformance/phase8_incident_drill.md — a scripted "feature F went bad" scenario with the expected ancestor/descendant answer set.
  • conformance/phase8_duplicate_events.jsonl — 5%-duplicate synthetic event stream for the compaction test.

20.6 Pitfalls

  • Treating lineage events as containing feature values (not just names/refs) creates an unintended PII-exposure surface — events carry feature_refs, never FeatureValues (§22 privacy boundary depends on this).
  • A mega-event for a training run touching thousands of features blocking compaction — split at 10MB via chained events (§20.2), verified by a fixture with an intentionally oversized event.

20.7 Performance Concerns

Query layer reads only the compacted Parquet table, never the raw ring-buffer/Kafka topic directly — this bounds query latency independent of live event-emission rate.

20.8 Edge Cases

  • A query for a feature with zero lineage history (e.g., never materialized) returns an empty result, not an error.
  • a trace spanning a schema-evolution event mid-trace (ancestors must resolve across the version boundary, §21).
  • a compaction job that itself fails mid-run (idempotent — reruns dedupe against already-compacted output, I6 applies here too).

20.9 Failure Analysis

Lineage emitter down: events buffer in the local ring buffer (bounded size, oldest-dropped-with-a-counter past capacity) and replay on recovery; the primary read/write path is never blocked (P7's structural guarantee — lineage completeness (I8) has a bounded-loss window, not a hard block, and that tradeoff is explicit here).

20.10 Operational Notes

  • Metrics: lineage_events_emitted_total, lineage_ring_buffer_dropped_total, lineage_compaction_duration_seconds.
  • Retention: ≥ 1 year default, configurable for compliance-sensitive namespaces (§22).

21. Phase 9 — Schema Evolution

21.1 Objectives

Make feature schemas evolvable without rewriting history (P6, I7): classify safe vs. unsafe changes, implement the migration command, and preserve mixed-version reads.

21.2 Detailed Implementation Steps

  • Classify changes in fs-registry's apply validator: safe (add nullable feature, widen numeric dtype, add tag, loosen a quality constraint, rename-with-alias) apply immediately; unsafe (remove feature, narrow dtype, incompatible dtype change, rename-without-alias, tighten a constraint that historical data violates) are rejected unless accompanied by featurestore migrate --plan <file> (I7).
  • Implement schema_evolution_log writes (§11 registry table) recording every applied change.
  • Implement mixed-version offline reads: each Parquet file's Arrow schema header records its schema_version; the AS-OF join operator (§8.4) applies per-segment up-casts and null-fills before presenting a unified-schema result to the caller.
  • Implement dual-write migration mode for unsafe changes requiring a rewrite: new+old schema materialized in parallel for a configurable transition window (default 30 days), tracked per-consumer migration timestamps.

Data structures introduced this phase: the schema_evolution_log table (§11 registry schema), the safe/unsafe change classifier, the mixed-version Parquet schema-header reader, the dual-write migration's transition-window tracker.

21.3 Deliverable

A feature view that has a feature added, a dtype widened, and a feature renamed (with alias) over a simulated six-month timeline, with zero consumer-code changes and zero historical-data rewrites, verified end to end.

21.4 Acceptance Criteria

  • conformance/phase9_safe_changes.json (5 safe-change scenarios) all apply without a migration command.
  • conformance/phase9_unsafe_change_rejected.json (3 unsafe-change scenarios) are all rejected with a named UnsafeSchemaChangeError and zero registry mutation.
  • a mixed-version read (partitions at schema v1 and v3) returns a single unified-schema result with correct up-casts, verified column-by-column.

21.5 Conformance Fixtures

  • conformance/phase9_safe_changes.json
  • conformance/phase9_unsafe_change_rejected.json
  • conformance/phase9_mixed_version_read.parquet (v1+v3 partitions of the same view).

21.6 Pitfalls

  • Reusing a protobuf field number after removing a feature corrupts historical online-wire decoding — field numbers are never reused (enforced by a registry lint, ADR-16's closed-set discipline extends here).
  • Applying a dual-write migration without a cost estimate surprises finance with doubled compute/storage — the migration plan (§21.2) always computes and requires sign-off on an estimated cost before execution.

21.7 Performance Concerns

Dual-write migrations double materialization and storage cost for the transition window — bounded by a default 30-day cap and surfaced explicitly in the migration plan so it is a deliberate, budgeted tradeoff, not a silent cost.

21.8 Edge Cases

  • A default-value backfill migration for a feature that was always computable but never registered (supported via a user-supplied SQL default expression, run in an isolated worker pool so a slow backfill doesn't starve live materialization, §16).
  • a migration plan approved but never executed (expires after 90 days, must be re-approved, preventing stale-plan drift).
  • a consumer still reading the old schema past the 30-day transition window (surfaced as a compliance-dashboard warning, not a silent cutoff — the namespace owner decides the cutoff, §22).

21.9 Failure Analysis

A migration applied incorrectly (e.g., a backfill default expression with a bug) corrupts historical data for the affected range: detection via the parity sampler (§19) and drift monitor flagging an anomalous distribution shift exactly at the migration boundary; recovery via the schema_evolution_log's recorded pre-migration state, enabling a targeted re-backfill of just the affected range.

21.10 Operational Notes

Metrics: schema_migrations_applied_total{kind}, dual_write_active_views. schema_evolution_log is the audit trail an on-call engineer consults first when a feature's shape looks wrong (§26).

22. Phase 10 — Multi-Tenant Isolation & RBAC

22.1 Objectives

Make the store safe to share across teams (P10, I9): namespace scoping at the registry, storage, and compute layers simultaneously, plus authenticated/authorized reads and writes.

22.2 Detailed Implementation Steps

  • Add a namespace column to every registry table with a (namespace, name) uniqueness constraint (§11 extension); Git-sync validates that the committer is CODEOWNERS-authorized for the namespace being changed (foundation laid in §13).
  • Prefix all storage keys/paths by namespace: offline offline/{namespace}/{view}/..., online fs:{namespace}:{view}:{entity_id} (§8.2 extended).
  • Implement per-namespace worker pools in the scheduler (§16) with configured concurrency quotas, so one namespace cannot exhaust another's compute.
  • Implement token-based RBAC: the SDK/CLI passes an OIDC-issued token (static map in dev); the registry checks it against namespace-level or view-level grants before permitting a read or write; a denied read returns Unauthorized (I9), never data.
  • Implement SharingPolicy for explicit, non-transitive cross-namespace grants.

Data structures introduced this phase: the namespace column added across every registry table (§11 extension), the SharingPolicy type, the per-namespace worker-pool quota configuration, the OIDC token-claims parser.

22.3 Deliverable

Two namespaces (growth, fraud) running concurrently in one deployment, each with independent registries-within-registry, storage, and worker quotas, verified to not interfere.

22.4 Acceptance Criteria

  • A misbehaving job in fraud submitting 10× its worker-pool quota does not delay any growth job beyond its normal freshness SLA (conformance/phase10_quota_isolation.json).
  • a read attempt against a non-granted namespace returns Unauthorized in 100% of conformance/phase10_unauthorized_reads.json (50 cases) with zero data leakage.
  • a SharingPolicy grant permits exactly the declared cross-namespace features and no others (verified: attempting to read a non-granted sibling feature via the same policy fails).

22.5 Conformance Fixtures

  • conformance/phase10_quota_isolation.json
  • conformance/phase10_unauthorized_reads.json
  • conformance/phase10_sharing_policy_grant.json (a growth→fraud grant of exactly 2 features).

22.6 Pitfalls

  • Enforcing namespace isolation only at the SDK layer (client-side filtering) is trivially bypassed by a caller that skips the SDK — enforcement must be at the registry/storage/compute layers, checked server-side on every call (P10's structural requirement, not a convention).
  • A SharingPolicy implemented as transitive re-export silently expands the blast radius of a single grant across the whole namespace graph — explicitly disallowed (§22.2).

22.7 Performance Concerns

Per-namespace worker pools must not fragment total cluster capacity so finely that a single large namespace cannot burst — quotas are soft ceilings with a documented capacity-review escalation path (§29 M-table), not hard partitions.

22.8 Edge Cases

  • A namespace requesting a dedicated, fully separate deployment for regulatory reasons (namespace_endpoint routing override, §22.2, breaks cross-namespace sharing by design — an explicit, documented tradeoff).
  • a grant referencing a feature that is later removed via schema evolution (§21) — the grant is invalidated and logged, not silently left dangling.
  • two namespaces racing to register the same entity name (rejected — namespace-qualified uniqueness means this cannot actually collide, verifying the constraint from §22.2 holds).

22.9 Failure Analysis

  • A compromised or leaked token: detection via anomalous per-token read-volume alerting; recovery via token revocation at the OIDC provider, immediate effect on the next registry auth check (no token caching beyond a short TTL, bounding the exposure window).
  • Blast radius contained to the namespaces the token was ever granted (I9 bounds this precisely).

22.10 Operational Notes

  • Metrics: namespace_quota_utilization{namespace}, unauthorized_read_total{namespace}, sharing_policy_active_grants.
  • Runbook: docs/runbooks/namespace-quota-review.md — triggered when sustained over-quota usage is observed (§22.7).

23. Phase 11 — Shared-Memory Hot Cache & Sub-Millisecond Serving

23.1 Objectives

Remove the Redis round trip from the online hot path: a per-host /dev/shm zero-copy cache in front of fs-online, targeting p99 ≤ 1ms at 10k QPS per host (§4's stretch target).

23.2 Detailed Implementation Steps

  • Implement a fixed-size, memory-mapped hash table in /dev/shm (fs-online/src/shm_cache.rs): 256-byte entries (8B key hash, 8B view id, 8B expiration, 232B inline value or overflow pointer), sized to the working set (90th-percentile 24h-accessed-entity count).
  • Readers use atomic loads (lock-free); writers take a per-bucket spinlock (evaluated against lock-free alternatives, ADR discussion in §36, rejected as premature at this phase's measured contention level).
  • A cache-fill daemon subscribes to Redis pub-sub (or a Kafka tap on the online sink's writes) and writes through to the shm entry on every update; a heartbeat key detects daemon staleness.
  • On cache miss or detected staleness, fs-online's gRPC handler falls back to Redis and repopulates the shm entry.

Data structures introduced this phase: the fixed-layout shm entry (key_hash, view_id, expiration, inline/overflow value, §23.2), the cache-fill daemon's Redis pub-sub subscriber, the per-bucket spinlock, the heartbeat-key staleness detector.

23.3 Deliverable

fs-online serving p99 ≤ 1ms at 10k QPS per host on the Phase-0 fixture, with automatic, transparent fallback to Redis on cache miss or staleness, verified via benchmarks/shm_cache_bench.rs.

23.4 Acceptance Criteria

  • p99 ≤ 1ms and throughput ≥ 50k QPS per core for (1 entity, 4 features) (§4).
  • measured ≥ 5× faster p99 than the Phase-3 Redis-only path on identical hardware, the bar ADR-21's cost/benefit requires.
  • zero torn reads under concurrent writer contention across 1M operations (conformance/phase11_concurrency_stress.json).
  • a killed cache-fill daemon triggers Redis fallback within the heartbeat detection window (≤ 2s) with zero read errors.

23.5 Conformance Fixtures

  • conformance/phase11_concurrency_stress.json — concurrent reader/writer stress with a torn-read detector.
  • conformance/phase11_daemon_kill_failover.json — daemon killed mid-benchmark, expects seamless Redis fallback.
  • conformance/phase11_working_set_sizing.json — validates the fixed-table sizing formula against a synthetic access-pattern trace.

23.6 Pitfalls

  • Sizing the shm table too small causes silent overflow-region overuse, degrading the "fast path" to effectively pointer-chasing for the majority of reads — the sizing formula (§23.2) is validated against real access-pattern traces, not assumed.
  • A lock-free hash table (Cliff-Click-style, PhaseDeferred("§23.6")) is tempting but adds real complexity; bucket-level spinlocks are measured sufficient at target QPS and are the locked-in choice (ADR discussion, §36) — revisit only if a benchmark shows contention dominating.

23.7 Performance Concerns

Zero-copy response building (prost decode directly into arena-allocated buffers, response slices reference the mmap'd region without a copy) is verified via allocator-tracking benchmarks showing no heap allocation beyond a small fixed per-request prologue — this is the mechanism, not an aspiration, behind the ≤ 1ms target.

23.8 Edge Cases

  • A /dev/shm-sized host running out of tmpfs space under a misconfigured working-set estimate (detected via a startup capacity check that refuses to start rather than OOM mid-serving).
  • concurrent readers during a cache-fill daemon restart (atomic loads guarantee no torn reads even as the daemon repopulates entries, verified in phase11_concurrency_stress).

23.9 Failure Analysis

  • Stale shm cache (daemon dead, heartbeat expired): server detects via heartbeat age check on every read path decision, fails over to Redis, continuing to serve correctly at Redis-only latency (§15's budget) rather than serving wrong data (P9's "absent over stale" principle applied one layer deeper).
  • Blast radius: a latency regression, never a correctness regression.

23.10 Operational Notes

  • Metrics: shm_cache_hit_rate, shm_cache_stale_fallback_total, tokio_runtime_queue_depth, allocator_bytes_per_request.
  • Deployment: the shm cache and its fill daemon are co-located per host with fs-online; a host restart loses the cache (tmpfs is not durable) and rebuilds from Redis on first misses, a documented, bounded cold-start cost.

26. Operational Readiness

Metrics are exported via Prometheus from every crate (fs-registry, fs-materialize, fs-online, fs-lineage, fs-monitor); tracing via tracing + OpenTelemetry export; structured JSON logs to stdout, collected by the deployment platform's log pipeline. Dashboards: one per namespace (drift/freshness/null-rate, §19), one system-wide (availability, latency, queue depth). Alerting philosophy: every alert has an owner and a runbook (§19.2); unowned alerts auto-silence after 30 days; alerts are reviewed quarterly against a < 10% false-positive-rate target.

SLOs: online read RPC availability 99.9%/28-day window (§4); freshness within 1.5× SLA for ≥ 99% of materialization windows (I4); zero production leakage bug reports (I1/I11, backstopped by §17). Each SLO carries an error budget; budget exhaustion pauses feature releases until reliability work restores it (SRE, Beer et al. 2016, §5).

Incident response: pages route to the on-call platform engineer for SLO-burning events only; lower-severity issues become tickets. Named runbooks (docs/runbooks/): registry-outage.md, online-store-outage.md, materialization-stuck.md, drift-alert.md, parity-disagreement.md, namespace-quota-review.md — each: detection → diagnosis (queries/greps) → mitigation (commands) → recovery verification. Postmortems for every SLO-burning page, archived under docs/postmortems/, feeding back into runbook and architectural updates.

Backup/restore: Postgres registry via standard WAL-based backup (delegated, not reimplemented); offline Parquet durability delegated to object-storage replication; online Redis data is not backed up (it is a cache of the offline+materialization source of truth and is rebuilt by re-materialization, consistent with P9's "absent, never stale" philosophy). Deployment topology: canary rollout for fs-online/fs-materialize (5% → 25% → 100%, gated on the perf-regression thresholds in §30); rollback is a binary swap (stateless roles) or a registry-level Git revert (definitions); migrations (§21) are the only stateful, non-instant rollback path and carry their own dry-run/approval gate.

Incident severity levels:

  • SEV1 — online read RPC availability breach (I2/I5 wide-scale violation) or a confirmed label-leakage escape into production training (I1/I11) — page immediately, all-hands, postmortem mandatory.
  • SEV2 — a single namespace's freshness SLA broken past 3× (I4), or the parity sampler sustaining parity_disagreements_total > 0 for over 10 minutes (I2) — page primary on-call, postmortem if customer-visible.
  • SEV3 — an isolated materialization job failure with automatic retry succeeding, a drift alert within expected noise bounds — ticket, no page.
  • SEV4 — a cosmetic dashboard/metric gap, a non-blocking lint failure — backlog item.

27. Compatibility & Versioning

The bundle of normative interfaces — registry schema (§11), materialization wire format (Arrow RecordBatch schema, §8.2/§14), online gRPC protocol (§11, ADR-04), Parquet column convention (§8.2), lineage event format (§11, ADR-17) — is versioned as one unit, current version v1. A breaking change to any one requires a bundle version bump, a migration path for in-place data, and dual-version support in fs-online/fs-materialize until the prior version is deprecated (documented deprecation window: ≥ 90 days). Non-breaking (additive-only) changes do not bump the bundle version but are recorded in CHANGELOG.md.

fs-cli --version and every service's /version endpoint report (crate_version, interface_bundle_version); a client refuses to talk to a server whose bundle version it does not support, surfacing a clear incompatibility error rather than producing garbage results (this is the online-protocol analogue of §21's schema-evolution safety, applied at the interface-bundle level rather than the per-feature level). Rolling upgrades: fs-online and fs-materialize support N and N+1 bundle versions simultaneously during a deploy window, verified by a compatibility test matrix in CI (§29) exercising every adjacent version pair. SemVer applies to every published crate (fs-types breaking changes are the rarest and most consequential, since every other crate depends on it, §10).

  • A deprecated field/endpoint is marked #[deprecated(note = "...", since = "vX.Y")] and remains functional for ≥ 90 days.
  • Removal requires a bundle version bump and a CHANGELOG.md entry naming the replacement.
  • No deprecation is silent: every one is logged at WARN on first use per process lifetime, capped to avoid log flooding.

28. Testing & Verification Strategy

Unit tests (cargo test, per-crate) cover individual types and functions against the invariants of §7 directly — each I# has at least one dedicated unit test named test_i{n}_*. Integration tests (tests/integration/) exercise the registry+materialize+store round trip end to end (Phase 0–4 scope). Property tests (proptest) drive the registry's round-trip and DAG-validation logic (§13) and the AS-OF join's determinism (I10). Differential tests are the PIT fuzzer's core method (§17) — the oracle-vs.-system comparison, not just assertion-based testing. Fuzzing: cargo-fuzz targets for the protobuf/Arrow deserialization boundary (defends T7) and the AS-OF join operator (§17). Chaos tests (tests/chaos/) kill processes mid-materialization (§14.9), mid-checkpoint (§18.9), and mid-cache-fill (§23.9), asserting the documented recovery behavior in each phase's N.9. Deterministic replay: the §7 simulator re-runs any historical failure from its logged seed. Soak tests run the full pipeline for 72h against synthetic traffic, watching for memory growth (a leak in Rust is almost always an unbounded collection — the soak test's pass criterion is bounded RSS growth). Fault injection: docs/runbooks/-paired scenarios (Redis down, Postgres down, Kafka partition stuck) run in a staging environment quarterly. Conformance: every phase's N.5 fixtures are replayed on every CI run, forming a growing regression corpus. Performance-regression gating: every criterion benchmark in benchmarks/ has a CI-enforced threshold (§30); a regression > 2× fails the build (§15.4, §23.4).

Every fixture and test class above ties back to a specific invariant (§7) or phase-local acceptance criterion (N.4/N.5) — there is no test in this system whose purpose is not traceable to a named correctness property.

Builds are reproducible: pinned Cargo.lock, pinned rust-toolchain.toml, hermetic Docker multi-stage builds (Dockerfile, §10). Artifact signing: release binaries are signed (cosign) and published with a generated SBOM (cargo-cyclonedx) for supply-chain auditability (defends T6). Release channels: main → nightly canary build; tagged releases → stable channel, SemVer-tagged. CI/CD topology (.github/workflows/): ci.yml (unit/integration/property tests + clippy + cargo audit), bench.yml (criterion benchmarks against the §30 M-table thresholds), fuzz.yml (unit-scale PIT fuzzer, blocking), release.yml (build, sign, SBOM, publish, changelog generation from Conventional Commits). Version stamping: every binary embeds its crate version and Git commit SHA, exposed on /version (§27). Provenance/attestation: release.yml generates SLSA-style build provenance attached to each release artifact. Dependency auditing: cargo audit runs on every CI build and nightly against the published advisory database; a new critical CVE in a dependency fails the nightly build and pages the platform team.

Release pipeline stages (in order):

  1. Merge to main → ci.yml full suite (unit/integration/property/clippy/audit) must be green.
  2. Nightly canary build → tagged nightly-<date>, deployed to a canary namespace only.
  3. bench.yml runs against the canary build; any M-row (§30) regression > 2× blocks promotion.
  4. Release tag (vX.Y.Z) triggers release.yml: build → sign (cosign) → SBOM (cargo-cyclonedx) → SLSA provenance → publish to the artifact registry.
  5. Staged rollout per §26's canary topology (5% → 25% → 100%), each stage gated on live error-budget consumption.
  6. Post-rollout: CHANGELOG.md auto-updated from Conventional Commits; deprecation warnings (§27) audited for any approaching their 90-day removal window.

31. Scalability Analysis

What stays constant as the catalog grows: per-request online read cost (O(1) hash lookup, independent of catalog size, §15/§23); registry apply validation cost per definition (O(features in that view), not O(catalog size), because DAG validation is scoped to the changed view's transitive dependents). What grows: total online memory (O(entities × features × namespaces), §34); total offline storage (O(entities × features × history-depth), §34); registry snapshot size (O(total registered definitions) — mitigated by the in-memory cache in §13.7, not re-fetched per request).

32. Mental Models & First Principles

MM1 — "A feature is a time series, not a value." Every feature is really entity_id → (timestamp → value)*; a "current value" is just a query at t = now. Predicts: any API that hides the timestamp (a bare get_feature(entity, name)) is a leakage trap waiting to happen. Bug class without it: treating the online store's latest value as if it were the only value, forgetting the offline history exists and must agree with it (I2). Applied in §8.1, §8.4.

MM2 — "AS-OF join is a query, not a special case." Once you see point-in-time correctness as "the standard join predicate for time-varying data," you stop writing bespoke as-of-date filtering logic per feature and instead build one correct operator (§8.4) that every feature read goes through. Predicts: any feature-specific "as of" logic outside the shared join operator is a latent I1 violation. Bug class without it: N slightly-different, unauditable timestamp-filtering implementations, one per team. Applied in §14, §17.

MM3 — "The materialization engine is the only place skew can be introduced — so make it the only place that can write." Skew is not a bug that appears; it is a structural possibility that exists whenever two code paths compute "the same" value. Predicts: any proposal to let a serving-side service compute its own version of a feature (for latency or convenience) reintroduces skew regardless of how careful the implementers are. Bug class without it: training-serving skew (§2), rediscovered independently by every team that tries to "just compute it faster in the serving layer." Applied in §6 P2, §14.2.

MM4 — "Freshness and TTL are two different clocks." Freshness answers "is the system keeping up with its promise" (a producer-side, SLA question); TTL answers "is this specific value still usable" (a consumer-side, correctness question). Predicts: conflating them (e.g., using TTL alone to infer pipeline health) hides scheduler failures until data actually goes missing, losing the early-warning window. Bug class without it: silent SLA breaches that only surface once TTL expiry finally makes the effect visible. Applied in §6 P5/P9, §7 I4/I5, §16.

MM5 — "Lineage is a graph you can only query if you built it as data, not as logs." Free-text logs answer "what happened at time T"; a lineage graph answers "what does X depend on, transitively" — a fundamentally different query shape requiring structured, queryable storage from day one. Predicts: teams that "add lineage later" from existing logs cannot actually answer ancestor/descendant queries without a costly reprocessing project. Bug class without it: an incident response that takes weeks instead of the 5-minute drill in §20.4. Applied in §6 P7, §20.

MM6 — "A closed type system is a compile-time promise to your slowest consumer." The Rust hot path (§23) can only be fast and safe if every value it might ever see is one of a small, known set of shapes; every "just let it be Any" convenience request in the definition layer (§13) is actually a request to make the online path slower or unsafe. Predicts: any proposal to add an "escape hatch" arbitrary-object dtype will, if granted, eventually break the shm cache's fixed-layout assumption (§23.2). Bug class without it: a runtime deserialization failure in the one component (§23) that budget-wise cannot afford to have one. Applied in §6 P12, §11, §23.

MM7 — "Backpressure is a design decision, not a symptom of insufficient capacity." A system that queues without bound is not "more resilient," it is deferring a failure to a worse moment (an OOM under load, instead of a clean rejection under load). Predicts: any component missing an explicit queue-depth/concurrency limit will eventually fail catastrophically instead of gracefully during exactly the traffic spike the limit exists to survive. Bug class without it: the classic "worked fine until Black Friday" collapse. Applied in §6 P14, §15.9, §23.

MM8 — "Multi-tenancy is a property of the whole stack or it is not a property at all." Isolation enforced at only one layer (say, the API) is not isolation — it is a convention that holds until the first caller that bypasses that layer. Predicts: an audit that only checks SDK-level namespace filtering will pass while the storage layer remains fully shared and exploitable. Bug class without it: the failure mode named explicitly in §22.6 (SDK-only enforcement, trivially bypassed). Applied in §6 P10, §22.

MM9 — "A benchmark without a workload shape is a number, not evidence." p99 ≤ 5ms means nothing without stating the entity count, feature count, and concurrency it was measured at (§4's constraint rows always pair a number with its workload shape). Predicts: a performance claim quoted without its (entities, features, QPS) triple cannot be compared against a regression or against a competing design. Bug class without it: a benchmark-driven regression is "fixed" by silently narrowing the test's workload shape rather than the underlying latency, exactly the failure the M-table's Phase Gate column (§30) exists to pin down. Applied in §4, §30, §34.

34. Back-of-Envelope Capacity Model

Design point (from §4): 10,000,000 entities, 200 features/namespace, 100 observations/entity/year, 3-year retention, 16-byte average value size, 10,000 QPS peak online read.

  1. Online memory per namespace = entities × features × (value_size + protobuf overhead) = 10M × 200 × (16B + 8B) ≈ 10,000,000 × 200 × 24B ≈ 48 GB per namespace (chained from the entity/feature counts in §4's series-count row).
  2. Online IOPS at peak = QPS × avg_features_per_request = 10,000 × 4 ≈ 40,000 Redis ops/sec — well inside a single Redis node's ~200k ops/sec envelope (chained from §4's throughput row), headroom to 5× before sharding (ADR-02).
  3. Offline raw storage per namespace = entities × features × obs/year × retention_years × value_size = 10M × 200 × 100 × 3 × 16B ≈ 960 GB raw.
  4. Offline compressed storage = raw × (1/amplification_target) ≈ 960 GB × (1/1.3⁻¹, i.e. ÷ ~3.7 typical ZSTD-3 ratio on numeric columns) ≈ ~260 GB per namespace after ZSTD-3 (chained from §4's storage-amplification row, which bounds the write-side overhead at 1.3×; compression ratio is the separate, larger effect estimated here).
  5. Materialization compute (batch) = source_rows_per_run / throughput_target = (10M entities × 1 daily obs) / 5,000 rows/sec (M6) ≈ 2,000 sec (~33 min) per full-catalog daily materialization pass, single worker — parallelized across the namespace's worker pool (§16) to fit the freshness SLA.
  6. PIT join cost for a training query = query_entities / throughput_target = 1,000,000 training rows / 1,000 entities/sec (M5) ≈ 1,000 sec (~17 min) for a million-row training set, single DataFusion worker.
  7. FD budget check = connections_to_redis + grpc_listener_backlog ≤ 4,096 (§4) — at pool size max(8, cores*2) on a 16-core host, ≈ 40 FDs to Redis, comfortably inside budget with headroom for the gRPC connection count at 10k QPS assuming HTTP/2 multiplexing (few hundred concurrent connections, not one-per-request).
  8. Working-set size for the shm cache (§23) = 90th-percentile 24h-accessed-entity-count × 256B/entry. Assuming 20% of the 10M-entity catalog is accessed per day (a typical recommender access-pattern skew) ≈ 2,000,000 × 256B ≈ 512 MB — comfortably fits in /dev/shm on any modern host, confirming §23's design assumption.
  9. Lineage event volume = (materialization jobs/day + reads/day) × avg_event_chain_length. At ~50 views × 24 hourly runs = 1,200 materialization events/day, plus an estimated 100,000 training/serving reads/day at ~1 event each ≈ ~101,200 events/day, well under the 10MB per-event cap (§20.6) and modest for the compaction job's 6-hourly batch (M11).
  10. Streaming state size (§18) = active_windows × entity_count_touched. For a 1-hour tumbling window over a 10M-entity stream with 5% daily active entities touching the window ≈ 500,000 × (256B RocksDB entry estimate) ≈ ~128 MB active state per view, per window — small relative to host memory, confirming the sketch-based approximate-aggregate fallback (§18.7) is only needed at higher cardinality/window-count combinations.
  11. Redis Cluster shard count at 5× design-point growth = projected_memory / per_shard_capacity = (48 GB × 5) / 50 GB-per-shard-ceiling (§31 bottleneck #1) ≈ 240 GB / 50 GB ≈ 5 shards, confirming ADR-02's documented next step activates well before the practical ceiling in §31.
  12. gRPC connection count at 10k QPS = QPS / requests_per_connection_per_sec. With HTTP/2 multiplexing at an assumed 200 in-flight requests/connection ≈ 10,000 / 200 = 50 concurrent connections per fs-online host, two orders of magnitude under the §4 FD budget (4,096), confirming headroom for connection-count growth without FD exhaustion.

Regime where it wins: a workload with modest scale (single-digit-millions of series) where operating two storage systems is a bigger cost than accepting a storage engine that is merely good enough at both point-lookup and time-travel query patterns, rather than excellent at each.    |   truth, as    | reads |  "latest" value|
   |   today)       |  raw  |  itself, at     |
   +----------------+ hist. |  request time,  |
                     |data  |  from a local   |

Regime where it wins: an edge/mobile-serving topology where a central online store's network hop is itself the dominant latency cost, and each client already receives a raw event stream it can locally aggregate (e.g., a recommendation model embedded in a mobile app maintaining its own recent-interaction cache). Real system that embodies it: this resembles on-device feature computation patterns used in some mobile ML deployments (client-side session-based recommenders). Rejected here because our design point (§4, §34) is a centralized serving fleet, not edge devices, and client-side computation reintroduces exactly the "two implementations of one feature" skew risk (§2, P2) — every client would need the identical aggregation logic as the offline path, unenforceable once shipped inside independently-versioned client binaries.

38. Glossary

Entity — the thing features describe (user, item, merchant, session, device).

Entity id — the primary key identifying one instance of an entity; a namespaced string in this system.

Feature — a named, typed value computed from a source about an entity, at a point in time.

Feature definition (FeatureDef) — the registered description of a feature: name, dtype, source, expression, owner, freshness SLA, TTL.

Feature view (FeatureView) — a bundle of features sharing a source and materialization schedule; the unit of scheduling.

Feature service (FeatureService) — a bundle of features one model consumes; the unit of deployment and the model-integration boundary.

Materialization — computing feature values from sources and writing them to both stores.

Offline store — the historical record of every feature value, suitable for point-in-time-correct training reads.

Online store — the latest-value-per-(entity, feature) record, suitable for low-latency inference reads.

Point-in-time correctness (PIT correctness) — the invariant that a query for entity E at time T returns the value visible at T, never a later one.

AS-OF join — the join finding, for each query row, the right-table row with the largest timestamp not exceeding the query timestamp.

Training-serving skew — the failure mode where training-time and serving-time feature computations diverge.

Label leakage — a training feature accidentally reflecting information only available after the label's true decision point.

Freshness SLA — the maximum age a feature value may have before the system alerts or refuses to serve.

TTL (time-to-live) — the age past which an online value is evicted rather than served.

Drift — a statistically detected shift in a feature's distribution over time.

Lineage — recorded relationships between sources, features, materialization runs, and consumers.

Namespace — a scoping prefix isolating one team's features at the registry, storage, and compute layers.

Snapshot (RegistrySnapshot) — an immutable view of registry state at a moment in time.

Registry — the Postgres database holding feature definitions and serving snapshots.

Source ref — a handle pointing at a Parquet file, SQL query, Kafka topic, or other data source.

Trace id — a request-scoped identifier tying together all lineage events for one action.

Span id — a step-scoped identifier within a trace, supporting hierarchical lineage.

Watermark — an estimate of "no future event will have an earlier event-time than this," used to bound streaming lateness.

Allowed lateness — the configured grace period after a watermark during which late events are still accepted rather than routed to a dead-letter topic.

Backfill — materializing a historical time range on demand, distinct from live scheduled materialization.

Idempotent materialization — the property that re-running the same job produces the same offline/online state.

Content-addressed partition — an offline Parquet file named by a hash of its inputs, enabling idempotent re-writes.

Parity sampler — the background process that samples online/offline pairs and asserts agreement (I2).

Schema evolution — changing a feature's or view's shape over time without rewriting history.

Safe schema change — a backward-compatible change (add nullable field, widen a dtype) applied without migration.

Unsafe schema change — a change requiring an explicit migration (remove a field, narrow a dtype).

Dual-write migration — materializing both an old and new schema in parallel during a transition window.

Sharing policy — an explicit, non-transitive cross-namespace feature-access grant.

Quality constraint — a declarative rule (not-null, in-range, distinct-count, regex) checked at materialization time.

Closed dtype system — the fixed enumeration of value types the system will ever store or serve.

Shm cache — the per-host /dev/shm-backed, memory-mapped, zero-copy online read cache (§23).

DAG (feature dependency graph) — the directed acyclic graph of feature views and their derived-feature dependencies.

Materialization job — one concrete execution unit: a feature view plus a time range plus a backend hint.

On-demand feature — a feature computed at request time from raw inputs rather than precomputed (deferred, §37).

Streaming feature view — a feature view whose source is a continuous event stream rather than a batch snapshot.

Tumbling / sliding / session window — the three windowing strategies over streaming event time (§18).

Reference implementation — a real, studied external system whose code or design this blueprint explicitly learns from or explicitly departs from (§5).

ADR (Architecture Decision Record) — a numbered, tabular record of a locked technical decision, its rejected alternatives, and the regime where each rejected alternative would actually win.

Invariant — a system property (I#) that must hold at all times, with a defined enforcement point, detection mechanism, and recovery path.

Principle — a numbered design rule (P#) governing every decision in the system.

Mental model — a compressed expert insight (MM#) predicting a bug class if not internalized.

Blast radius — the scope of impact of a given failure, used throughout §24/§25 to bound incident severity.

Error budget — the allowed accumulation of SLO violations before releases pause for reliability work (§26).

RTO (Recovery Time Objective) — the maximum acceptable time to restore service after an outage (§4).

SBOM (Software Bill of Materials) — a generated inventory of a build's dependencies, for supply-chain auditability (§29).

Provenance/attestation — a signed record of how and from what a release artifact was built (§29).
