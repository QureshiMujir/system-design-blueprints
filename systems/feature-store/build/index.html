⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (§10), wire fs-types → fs-registry (SQLite-backed dev mode) → fs-materialize → fs-offline → a minimal offline read, and prove the AS-OF join is correct on a synthetic fixture before any other phase begins. No online store yet (stubbed trait impl only). Scope: single-process, single-namespace, no scheduler, no streaming.

Deliverable

examples/user_entity_demo/run.sh: starts fs-registry (SQLite), applies the user entity + user_demographics view, materializes it, runs three offline AS-OF queries, prints results, exits 0. Runnable and inspectable end to end.

Acceptance
  • All three §8.5 worked-example queries return exactly the documented values.
  • cargo test -p fs-offline passes ≥ 8 hand-written AS-OF cases (§8.5, §8.6).
  • demo script exits 0 in ≤ 10s on a laptop.
  • cargo clippy --all -- -D warnings clean.
Fixtures
  • conformance/phase0_user_history.parquet — the 10k-row synthetic fixture, fixed seed 42.
  • conformance/phase0_asof_cases.json — 8 named (entity, ts) → expected-value pairs covering §8.5/§8.6.
  • conformance/phase0_malformed_row.parquet — one row with null event_ts, expects routing to rejects/ (§8.6).
Pitfalls
  • Forgetting partition pruning on event_date makes the join scan the whole fixture — invisible at 10k rows, catastrophic at Phase 4 scale; catch via a DataFusion EXPLAIN assertion in CI.
  • Using f64 timestamps anywhere reintroduces float-equality bugs in tiebreaks (I10) — enforce timestamp[us, UTC] end to end.
  • SQLite dev-mode registry silently permits concurrent writers to corrupt a row — acceptable only because Phase 0 is single-process (flagged, revisited at ADR-11's Postgres cutover in §13).

⬜ Phase 1 — Feature Registry & Definition DSL §13

Objectives

Replace the SQLite stub with the full Postgres-backed registry (ADR-11), the Git-canonical authoring model (ADR-12), and a Rust builder-API definition surface (ADR-09) with compile-time-checked feature definitions. Add DAG validation (I13, P4) at apply time.

Deliverable

featurestore apply --file definitions.ron round-trips a definition through Git-sync validation into Postgres and back out via GET /snapshot, byte-identical modulo server-assigned IDs.

Acceptance
  • 100 randomly generated valid definitions round-trip losslessly (property test).
  • a definition with a cyclic dependency is rejected with a named DagCycleError in < 50ms.
  • an unauthorized-namespace apply is rejected with Unauthorized, never partially applied.
  • cargo test -p fs-registry ≥ 40 passing cases.
Fixtures
  • conformance/phase1_valid_defs/*.ron (100 generated cases).
  • conformance/phase1_cyclic_dag.ron — view A depends on view B depends on view A.
  • conformance/phase1_unauthorized_apply.ron — namespace mismatch case.
Pitfalls
  • Applying migrations out of order across environments silently drifts schemas — sqlx migrate is run only through the CI-gated release pipeline (§29), never ad hoc against production.
  • A git_sync poller that dies silently leaves the registry serving a stale snapshot indefinitely — a heartbeat metric (registry_git_sync_last_success_seconds) makes staleness visible (P11).

⬜ Phase 2 — Batch Materialization Engine §14

Objectives

Build the full fs-materialize DAG engine: Source/Transform/Sink traits, topological execution (P4), and the dual offline+online write fan-out from one RecordBatch (P2) — online sink still writes to an in-memory stub until §15.

Deliverable

featurestore materialize --view user_demographics --start ... --end ... produces a correctly-partitioned, content-addressed offline dataset and a matching sequence of LineageEvents, inspectable via fs-cli lineage show <job_id>.

Acceptance
  • Running the same job twice produces byte-identical Parquet output and zero duplicate online writes (I6, verified in conformance/phase2_idempotency.json).
  • a 3-node derived-feature DAG materializes in strict topological order, verified by timestamp ordering in the lineage log.
  • job throughput ≥ 5,000 rows/sec on the Phase-0 fixture on a 4-core laptop.
Fixtures
  • conformance/phase2_dag_3node.ron — parent/child/grandchild feature views.
  • conformance/phase2_idempotency.json — expected identical hash across two runs.
  • conformance/phase2_retry_partial_batch.parquet — simulates a mid-batch write failure for retry testing (feeds §14.9).
Pitfalls
  • A non-deterministic DataFusion physical plan (e.g., unordered GROUP BY output) breaks I6/I10 silently — pin SortExec after every aggregation.
  • Forgetting to dedupe on retry double-counts rows in the offline partition — content-addressing (P13) catches this only if the content, not just the job id, is hashed.

⬜ Phase 3 — Online Store (Redis-Backed Serving) §15

Objectives

Replace the in-memory online stub with Redis (ADR-02): implement fs-online's OnlineStore trait impl, the key layout (§8.2), the packed-protobuf encoding (ADR-14), and the gRPC serving surface (ADR-04, ADR-21), meeting the §4 p99 ≤ 5ms budget.

Deliverable

A running fs-online server answering GetFeatures gRPC calls against a locally materialized view, with tests/bench/online_bench.rs (criterion) reporting p50/p99/p999.

Acceptance
  • p99 ≤ 5ms for (1 entity, 4 features) on a local Redis, measured over ≥ 10,000 requests (§4).
  • p99 ≤ 20ms for (100 entities, 16 features).
  • zero online-store monotonicity regressions (I14) across conformance/phase3_out_of_order_write.json (100 shuffled-timestamp writes).
  • a benchmark regression > 2× fails CI (§29).
Fixtures
  • conformance/phase3_out_of_order_write.json — writes delivered out of event_ts order, expects I14 to hold.
  • conformance/phase3_ttl_expiry.json — a key materialized then read after synthetic TTL fast-forward, expects TtlExpired.
  • conformance/phase3_miss_unknown_entity.json — read for a never-materialized entity, expects NotMaterialized.
Pitfalls
  • HMGET on a non-existent hash returns all-nil, indistinguishable from "hash exists but fields are null" unless the server also checks EXISTS — conflating the two collapses NotMaterialized into a false null read; the server issues both in one pipeline round-trip (no added RTT, §15.7).
  • Redis maxmemory-policy allkeys-lru under memory pressure can evict a just-written key before it's read — mitigated by monitoring evicted_keys and alerting before it affects freshness-critical views.

⬜ Phase 4 — Materialization Scheduler & Freshness Enforcement §16

Objectives

Move materialization from on-demand CLI invocation to a scheduled, SLA-aware, concurrency-controlled process (P5, P14): cron triggers, priority-by-freshness-lag queueing, per-view locking, and backfill support.

Deliverable

A running scheduler daemon that materializes registered views on their cron schedule without operator intervention, visible via fs-cli scheduler status showing per-view lag.

Acceptance
  • A view configured with a 15-minute SLA and a 10-minute cron completes within SLA in ≥ 99% of a 24-hour simulated run (conformance/phase4_24h_sim.json).
  • when the worker pool is saturated (max_inflight_jobs=4, 10 pending views), the view with the largest freshness lag is scheduled first, verified by execution-order assertion.
  • two concurrent triggers for the same view result in exactly one execution, the other rejected as ViewLocked.
Fixtures
  • conformance/phase4_24h_sim.json — scripted 24h of cron triggers against 10 views with varying SLAs.
  • conformance/phase4_lock_contention.json — two simultaneous triggers, same view.
  • conformance/phase4_backfill_range.json — a 90-day backfill request, expects one job per day boundary, all idempotent.
Pitfalls
  • A stuck job holding its view lock indefinitely silently blocks all future materialization for that view — mitigated by a lock timeout (configurable, default 30 min) plus a scheduler_view_lock_held_seconds metric so a stuck lock is visible before the next SLA breach.
  • FIFO-by-accident (e.g., an unstable sort in the priority queue) reintroduces starvation even with the priority field present — verified by a property test asserting strict ordering under ties.

⬜ Phase 5 — Point-in-Time Correctness Adversarial Fuzzing §17

Objectives

Replace hand-written PIT tests with a differential adversarial fuzzer (ADR-22) that is the project's single most important correctness gate (I1, I10, I11) — historically, in comparable systems, the class of bug most likely to escape manual review.

Deliverable

cargo fuzz run pit_fuzz (unit scale) runs in CI on every PR; nightly and weekly jobs run integration/stress scales (§17.4); every historical failure lives as a permanent regression fixture in fuzz/regressions/.

Acceptance
  • Unit scale (N=10,M=5,K=20,100 queries) completes in < 1s, zero oracle mismatches, blocking on every PR.
  • integration scale (N=10,000,M=50,K=200,100,000 queries) completes in < 10 min nightly.
  • stress scale (N=1M,M=200,K=1,000,10M queries) completes in < 2h weekly.
  • 100% of the mutation-tested known bugs (≥ 6 seeded mutants) are caught within budget.
Fixtures
  • fuzz/regressions/*.json — every previously-found failing case, replayed on every run (regression-proof).
  • fuzz/mutants/asof_ge_instead_of_le.rs, fuzz/mutants/tiebreak_ascending.rs, fuzz/mutants/off_by_one_partition.rs — named seeded bugs the fuzzer must catch (§17.2).
Pitfalls
  • A fuzzer whose random seed is not logged turns every CI failure into an unreproducible flake — the seed is attached to every failure artifact and re-runnable verbatim.
  • A fuzzer that only tests the "happy path" temporal distribution (uniformly random timestamps) under-samples the adversarial corners (duplicate timestamps, partition-boundary timestamps, timezone edge cases) that are actually where bugs live — §17.2's generator explicitly biases toward these corners at a configurable rate.

⬜ Phase 6 — Streaming Feature Views §18

Objectives

Admit event-time streaming sources (Kafka, ADR-08) with windowed aggregation, watermark-based lateness handling (Akidau et al., VLDB 2015), and a batch/streaming parity guarantee.

Deliverable

A streaming FeatureView consuming a Kafka topic, producing windowed aggregates in both stores, recoverable from a checkpoint after a simulated consumer crash.

Acceptance
  • Batch/streaming parity test (conformance/phase6_parity_24h.json): materializing the same 24h period via batch (over a warehouse copy) and via streaming (over Kafka replay) produces byte-identical offline tables, modulo a documented ±1e-6 float-aggregation tolerance.
  • consumer crash-and-resume from checkpoint loses ≤ 60s of processed-but-uncommitted state (bounded by the checkpoint interval).
  • late-arrival routing correctly separates ≥ 99% of synthetically delayed events in conformance/phase6_late_arrivals.json.
Fixtures
  • conformance/phase6_parity_24h.json — dual batch/streaming materialization comparison.
  • conformance/phase6_late_arrivals.json — synthetic Kafka replay with injected out-of-order delivery.
  • conformance/phase6_checkpoint_crash.json — consumer killed mid-window, resumed, state compared to a golden run.
Pitfalls
  • An unbounded lateness budget (allowed_lateness = ∞) never closes a window, growing RocksDB state unboundedly — the default 10s is a deliberate, documented tradeoff (§4 has no explicit row for this; it is stated here as a hard default).
  • A checkpoint that captures Kafka offset but not the partial-window aggregate state is not actually resumable — both must be captured atomically, verified by phase6_checkpoint_crash.

⬜ Phase 7 — Feature Monitoring (Drift, Quality, Parity) §19

Objectives

Wire fs-monitor: drift detection, freshness/null-rate metrics, Deequ-style declarative quality constraints (Schelter et al., VLDB 2018), and the online/offline parity sampler that directly checks I2.

Deliverable

A running fs-monitor process emitting Prometheus metrics and Grafana-ready dashboards for drift, freshness, null rate, and parity, with the parity sampler continuously verifying I2 in production.

Acceptance
  • Drift detection flags a synthetically injected 3-sigma distribution shift within one materialization cycle (conformance/phase7_drift_injection.json), PSI computed within ±0.01 of a reference implementation.
  • a severity=fail quality constraint violation aborts the materialization and reverts the partial write (verified: zero partial rows land in the offline partition).
  • the parity sampler detects a synthetically introduced 1% online/offline disagreement within 10 minutes at the configured sample rate.
Fixtures
  • conformance/phase7_drift_injection.json — baseline + shifted distribution pair.
  • conformance/phase7_quality_fail_abort.json — a batch violating an in_range fail-severity constraint.
  • conformance/phase7_parity_disagreement.json — deliberately desynced online/offline pair.
Pitfalls
  • Computing drift against a too-short rolling baseline (e.g., 1 prior batch) makes every batch "drifted" by noise — default baseline window is 30 batches, tunable per feature.
  • A severity=fail constraint that aborts after the offline write has already landed leaves a partial write — the constraint check must run before the sink commit, not after (ordering bug caught in phase7_quality_fail_abort).

⬜ Phase 8 — Lineage Capture & Query §20

Objectives

Make lineage (already emitted since §14, P7) queryable: storage, compaction, and a query layer answering "which models depend on feature F" within an operationally useful time bound.

Deliverable

fs-cli lineage ancestors --feature user_demographics:age and fs-cli lineage trace --trace-id <id> return correct, complete results against a populated lineage log.

Acceptance
  • Given the name of a synthetically "corrupted" feature, lineage ancestors/descendants identify 100% of dependent FeatureServices and the exact MaterializationJobs that read the corrupted source, in ≤ 5 minutes of engineer time (measured operator drill, conformance/phase8_incident_drill.md).
  • compaction dedupes a synthetic stream with 5% duplicate event_ids to exactly 0 duplicates in the compacted table.
Fixtures
  • conformance/phase8_incident_drill.md — a scripted "feature F went bad" scenario with the expected ancestor/descendant answer set.
  • conformance/phase8_duplicate_events.jsonl — 5%-duplicate synthetic event stream for the compaction test.
Pitfalls
  • Treating lineage events as containing feature values (not just names/refs) creates an unintended PII-exposure surface — events carry feature_refs, never FeatureValues (§22 privacy boundary depends on this).
  • A mega-event for a training run touching thousands of features blocking compaction — split at 10MB via chained events (§20.2), verified by a fixture with an intentionally oversized event.

⬜ Phase 9 — Schema Evolution §21

Objectives

Make feature schemas evolvable without rewriting history (P6, I7): classify safe vs. unsafe changes, implement the migration command, and preserve mixed-version reads.

Deliverable

A feature view that has a feature added, a dtype widened, and a feature renamed (with alias) over a simulated six-month timeline, with zero consumer-code changes and zero historical-data rewrites, verified end to end.

Acceptance
  • conformance/phase9_safe_changes.json (5 safe-change scenarios) all apply without a migration command.
  • conformance/phase9_unsafe_change_rejected.json (3 unsafe-change scenarios) are all rejected with a named UnsafeSchemaChangeError and zero registry mutation.
  • a mixed-version read (partitions at schema v1 and v3) returns a single unified-schema result with correct up-casts, verified column-by-column.
Fixtures
  • conformance/phase9_safe_changes.json
  • conformance/phase9_unsafe_change_rejected.json
  • conformance/phase9_mixed_version_read.parquet (v1+v3 partitions of the same view).
Pitfalls
  • Reusing a protobuf field number after removing a feature corrupts historical online-wire decoding — field numbers are never reused (enforced by a registry lint, ADR-16's closed-set discipline extends here).
  • Applying a dual-write migration without a cost estimate surprises finance with doubled compute/storage — the migration plan (§21.2) always computes and requires sign-off on an estimated cost before execution.

⬜ Phase 10 — Multi-Tenant Isolation & RBAC §22

Objectives

Make the store safe to share across teams (P10, I9): namespace scoping at the registry, storage, and compute layers simultaneously, plus authenticated/authorized reads and writes.

Deliverable

Two namespaces (growth, fraud) running concurrently in one deployment, each with independent registries-within-registry, storage, and worker quotas, verified to not interfere.

Acceptance
  • A misbehaving job in fraud submitting 10× its worker-pool quota does not delay any growth job beyond its normal freshness SLA (conformance/phase10_quota_isolation.json).
  • a read attempt against a non-granted namespace returns Unauthorized in 100% of conformance/phase10_unauthorized_reads.json (50 cases) with zero data leakage.
  • a SharingPolicy grant permits exactly the declared cross-namespace features and no others (verified: attempting to read a non-granted sibling feature via the same policy fails).
Fixtures
  • conformance/phase10_quota_isolation.json
  • conformance/phase10_unauthorized_reads.json
  • conformance/phase10_sharing_policy_grant.json (a growth→fraud grant of exactly 2 features).
Pitfalls
  • Enforcing namespace isolation only at the SDK layer (client-side filtering) is trivially bypassed by a caller that skips the SDK — enforcement must be at the registry/storage/compute layers, checked server-side on every call (P10's structural requirement, not a convention).
  • A SharingPolicy implemented as transitive re-export silently expands the blast radius of a single grant across the whole namespace graph — explicitly disallowed (§22.2).

⬜ Phase 11 — Shared-Memory Hot Cache & Sub-Millisecond Serving §23

Objectives

Remove the Redis round trip from the online hot path: a per-host /dev/shm zero-copy cache in front of fs-online, targeting p99 ≤ 1ms at 10k QPS per host (§4's stretch target).

Deliverable

fs-online serving p99 ≤ 1ms at 10k QPS per host on the Phase-0 fixture, with automatic, transparent fallback to Redis on cache miss or staleness, verified via benchmarks/shm_cache_bench.rs.

Acceptance
  • p99 ≤ 1ms and throughput ≥ 50k QPS per core for (1 entity, 4 features) (§4).
  • measured ≥ 5× faster p99 than the Phase-3 Redis-only path on identical hardware, the bar ADR-21's cost/benefit requires.
  • zero torn reads under concurrent writer contention across 1M operations (conformance/phase11_concurrency_stress.json).
  • a killed cache-fill daemon triggers Redis fallback within the heartbeat detection window (≤ 2s) with zero read errors.
Fixtures
  • conformance/phase11_concurrency_stress.json — concurrent reader/writer stress with a torn-read detector.
  • conformance/phase11_daemon_kill_failover.json — daemon killed mid-benchmark, expects seamless Redis fallback.
  • conformance/phase11_working_set_sizing.json — validates the fixed-table sizing formula against a synthetic access-pattern trace.
Pitfalls
  • Sizing the shm table too small causes silent overflow-region overuse, degrading the "fast path" to effectively pointer-chasing for the majority of reads — the sizing formula (§23.2) is validated against real access-pattern traces, not assumed.
  • A lock-free hash table (Cliff-Click-style, PhaseDeferred("§23.6")) is tempting but adds real complexity; bucket-level spinlocks are measured sufficient at target QPS and are the locked-in choice (ADR discussion, §36) — revisit only if a benchmark shows contention dominating.
