Decisions (§9) · 22 ADRs

ADR-01

Offline store format

Chosen

Parquet on object storage, parquet/arrow-rs crates

Rejected

Iceberg, Delta Lake, Hudi, raw Postgres, ClickHouse

When the rejected choice is right

Iceberg/Delta wins once concurrent-writer ACID and time-travel-by-snapshot matter more than operational simplicity — revisit at the PhaseDeferred("§9") trigger (catalog > 500 views)

Why: Lowest-common-denominator, no metastore service to operate at early phases (§1)

ADR-02

Online store backend

Chosen

Redis, redis-rs client

Rejected

DynamoDB, Cassandra, ScyllaDB, Postgres, RocksDB, Aerospike

When the rejected choice is right

DynamoDB wins once the team is AWS-native and wants managed multi-region replication over self-run Redis Cluster ops

Why: Fastest single-node point-lookup, simplest operability (§15)

ADR-03

In-memory/batch wire format

Chosen

Apache Arrow (arrow-rs)

Rejected

Protobuf-for-batch, JSON, MessagePack

When the rejected choice is right

Protobuf wins for the online RPC specifically (ADR-04) where row-oriented point lookups dominate

Why: Columnar layout matches offline store; zero-copy Arrow C Data Interface

ADR-04

Online RPC wire format

Chosen

Protobuf + tonic gRPC

Rejected

Arrow-over-gRPC, raw TCP, HTTP+JSON, Cap'n Proto

When the rejected choice is right

Cap'n Proto wins once zero-copy RPC deserialization is the dominant cost — revisit at the §23.6 optimization trigger

Why: Strict schema, mature Rust tooling (prost), wide client-language support

ADR-05

Implementation language, whole system

Chosen

Rust

Rejected

Python, Go, Java/JVM, C++

When the rejected choice is right

Python wins for a low-QPS internal prototype where dev velocity dominates and the sub-5ms budget (§4) does not apply

Why: Single language removes the two-runtime skew surface; GC-free hot path (§1)

ADR-06

Offline AS-OF join engine

Chosen

Custom ExecutionPlan on Apache DataFusion

Rejected

Spark, Polars, Pandas, ClickHouse, embed DuckDB in production

When the rejected choice is right

Spark wins once a single source table exceeds one node's Parquet-scan capacity — the documented fallback (§8.4 step 3)

Why: Native Rust, in-process, avoids FFI; DuckDB's algorithm reused as reference (§8.4)

ADR-07

Batch transform engine

Chosen

DataFusion DataFrame API

Rejected

Polars (Python bindings), Pandas, Dask

When the rejected choice is right

Polars wins for interactive, ad hoc exploration outside the production materialization path (not in scope, §1 non-goals)

Why: Same runtime as the join engine, one fewer serialization boundary

ADR-08

Streaming ingestion

Chosen

rdkafka + custom watermark tracker

Rejected

Flink, Spark Structured Streaming, Kafka Streams, Materialize

When the rejected choice is right

Flink wins once per-partition state exceeds what a single consumer process's embedded RocksDB can hold — PhaseDeferred("§18.6")

Why: Operational simplicity at early scale; explicit watermark control (§18)

ADR-09

Feature definition surface

Chosen

Rust builder API + declarative macro front end

Rejected

SQL DSL, YAML, Protobuf IDL

When the rejected choice is right

SQL DSL wins for a primarily-analyst (non-engineer) authoring audience — not this project's target user (§1)

Why: Compile-time checked, composable, testable (§13)

ADR-10

Materialization scheduling

Chosen

Custom DAG runner (fs-materialize/src/scheduler.rs)

Rejected

Airflow, Prefect, Dagster, Argo, Temporal

When the rejected choice is right

Dagster wins once the org already standardizes all data orchestration on it and per-feature SLA priority is a secondary concern

Why: Fine-grained per-feature lineage emission and SLA-priority scheduling generic orchestrators do not expose

ADR-11

Registry storage

Chosen

Postgres

Rejected

SQLite, MySQL, Git-only, etcd, custom

When the rejected choice is right

SQLite wins for single-tenant local dev only (already the dev-mode default, §13)

Why: Operationally familiar, JSONB metadata columns, scales to millions of rows

ADR-12

Registry authoring model

Chosen

Git canonical + Postgres runtime cache

Rejected

Postgres-only, Git-only, dual-write from UI

When the rejected choice is right

Postgres-only wins for a single-operator deployment where PR review overhead is unjustified

Why: PR review + rollback, indexed runtime queries

ADR-13

Large-table PIT join fallback

Chosen

Spark, same sort-merge algorithm as §8.4

Rejected

One-pass nearest-prior without partition pruning, hash join with bucketing

When the rejected choice is right

Hash-join-with-bucketing wins when entity cardinality is small and fixed (bounded-key lookup) and history depth is shallow

Why: Partition-pruned sort-merge is what DuckDB's engine also uses; consistent algorithm across engines

ADR-14

Online value encoding

Chosen

Arrow batch (write) → packed protobuf (read)

Rejected

JSON, MessagePack, custom struct, raw bytes

When the rejected choice is right

Raw bytes with a fixed offset table wins once protobuf's per-field tag overhead is measurably the bottleneck (§23)

Why: Write path benefits from columnar batching; read path benefits from dense row payload

ADR-15

Null / miss handling

Chosen

Explicit is_null + FeatureMissReason, no sentinels

Rejected

Sentinel values (-1, NaN), return-default-on-miss

When the rejected choice is right

A sentinel wins only for a fixed-point wire format with no spare bit for null and no controlling code that reads it — a constraint this design avoids, since the dtype set already reserves explicit-null room (ADR-16)

Why: Sentinels conflate "missing" with "legitimate zero," a documented production-incident pattern

ADR-16

Dtype system

Chosen

Closed enum: int32/64, float32/64, bool, string, bytes, vector<T>, list<T>

Rejected

Arbitrary serialized objects, Pandas-style dtypes, "anything that serializes"

When the rejected choice is right

An open type system wins for a research-only prototype not intended to reach the online path

Why: Enables Rust-side exhaustive match, prevents opaque-blob leakage (P12)

ADR-17

Lineage transport

Chosen

Append-only log (local buffer → Kafka → Parquet compaction)

Rejected

Live SQL inserts, Kafka-only event sourcing, OpenLineage adoption wholesale

When the rejected choice is right

Wholesale OpenLineage collector adoption wins once the org already runs an OpenLineage-compatible platform — schema kept compatible for that migration

Why: Decouples emission from query; tolerates lineage-store outages (§20)

ADR-18

Freshness enforcement mechanism

Chosen

Scheduler-side SLA tracking, separate from TTL

Rejected

Data-path-only staleness check, "last write wins" with unlimited stale reads

When the rejected choice is right

A single combined mechanism wins for a system with one feature and one consumer, where the distinction adds no value

Why: Two distinct mechanisms (SLA at write-scheduling, TTL at read-serving) avoid silent SLA misses (P5, P9)

ADR-19

Multi-tenant isolation

Chosen

Namespaces at registry + storage prefix + worker-pool quota

Rejected

Single-tenant per deployment, SDK-level RBAC filtering only, Kubernetes namespaces only

When the rejected choice is right

Single-tenant-per-deployment wins for a regulated namespace needing full infrastructure separation (documented escape hatch, §22)

Why: Structural containment at three layers simultaneously (§22)

ADR-20

Schema evolution policy

Chosen

Backward-compatible-only by default; explicit migration for unsafe changes

Rejected

Free-form schema changes, mandatory dual-write for every change, no evolution support

When the rejected choice is right

Mandatory dual-write for every change wins for a namespace with zero tolerance for any registry-validation false negative (extra cost accepted)

Why: Prevents accidental history-breaking changes while not over-taxing safe ones (§21)

ADR-21

Online serving deployment topology

Chosen

Rust gRPC sidecar over Unix domain socket

Rejected

In-process FFI library, standalone-only service, Lambda/serverless

When the rejected choice is right

In-process FFI wins when the caller is also Rust and controls its own runtime — still rejected here for operational uniformity across polyglot callers

Why: Isolates the GC-free hot path from the caller process; FFI would pull caller's runtime into the hot path

ADR-22

Test discipline for PIT correctness

Chosen

Adversarial differential fuzzer, blocking in CI (§17)

Rejected

Manual test cases only, property tests on synthetic data without an oracle, no dedicated leakage test

When the rejected choice is right

Manual test cases alone win only for a feature catalog small enough (<5 views) that exhaustive hand enumeration is tractable

Why: Catches temporal edge cases human intuition misses; differential-against-oracle is the only method that has found real bugs here

36. Alternative Architectures (Roads Not Taken)

Alternative A — Single unified store (no offline/online split).

   +-------------------------------+
   |   One storage engine          |
   |  (e.g. a temporal KV store    |
   |   with native AS-OF reads     |
   |   AND sub-ms point lookups)   |
   +---------------+---------------+
                    |
         +----------+----------+
         |                     |
    Training reads       Serving reads
    (as-of query)        (latest query)

Regime where it wins: a workload with modest scale (single-digit-millions of series) where operating two storage systems is a bigger cost than accepting a storage engine that is merely good enough at both point-lookup and time-travel query patterns, rather than excellent at each. Real system that embodies it: Materialize (a streaming SQL database with time-travel-ish semantics) approximates this for some workloads. Rejected here because Stonebraker & Cetintemel's (ICDE 2005, §5) specialize-the-engine argument holds at our target scale (§4): no single open engine matches both DataFusion's offline throughput and Redis/shm's online tail latency simultaneously at the QPS/entity-count design point in §34.

Alternative B — Warehouse-native feature views (Lakehouse-first).

   +----------------------------------+
   |  Snowflake / Databricks Lakehouse|
   |  (Delta/Iceberg tables, feature  |
   |   views as SQL, PIT via time     |
   |   travel + Delta MERGE)          |
   +----------------+-----------------+
                     |
          +----------+-----------+
          |                      |
   Offline: native SQL     Online: a thin
   time-travel query       serving cache layer
                           synced from the lakehouse

Regime where it wins: an organization already fully committed to a lakehouse (all data already in Delta/Iceberg, warehouse team owns the platform) where adding a bespoke offline store is pure duplication. Real system that embodies it: Databricks Feature Store (built directly on Delta Lake, §5 papers/Armbrust et al. CIDR 2021). Rejected here (ADR-01) because it requires operating a Delta/Iceberg metastore we do not want at early phases and couples the offline path to a specific lakehouse vendor rather than plain Parquet on any object store — revisit at the PhaseDeferred("§9") trigger.

Alternative C — Fully event-sourced, streaming-only (no batch materialization at all).

   Kafka (all sources, including "batch"
   sources replayed as a bounded stream)
              |
              v
   +----------------------+
   |  Flink stateful jobs |
   |  (every feature is a |
   |   continuous stream  |
   |   transform)         |
   +----------+-----------+
              |
     +--------+--------+
     |                 |
  Online sink      Offline sink
  (state store)    (changelog topic
                    compacted to Parquet)

Regime where it wins: an organization whose sources are already predominantly event streams and whose team has deep Flink operational expertise, making "everything is a stream" a simplification rather than a complication. Real system that embodies it: this is close to how some Flink-centric shops (and the streaming half of Michelangelo's more recent iterations) approach feature computation. Rejected here (ADR-08) because most of our design-point sources (§4, §34) are genuinely batch (daily warehouse exports), and forcing them through a streaming abstraction adds Flink's substantial operational complexity for no correctness benefit — we instead keep batch and streaming as first-class, separate Transform variants (§14, §18) unified only at the sink layer (P2), reserving the option to add Flink later (PhaseDeferred("§18.6")) if streaming-source proportion grows.

Alternative D — Client-side (SDK-computed) online features, no server-side online store at all.

   +----------------+       +----------------+
   |  Offline store |       |  Client SDK    |
   |  (source of    |------>|  computes the  |
   |   truth, as    | reads |  "latest" value|
   |   today)       |  raw  |  itself, at     |
   +----------------+ hist. |  request time,  |
                     |data  |  from a local   |
                     +----->|  cache of recent|
                            |  raw events     |
                            +----------------+

Regime where it wins: an edge/mobile-serving topology where a central online store's network hop is itself the dominant latency cost, and each client already receives a raw event stream it can locally aggregate (e.g., a recommendation model embedded in a mobile app maintaining its own recent-interaction cache). Real system that embodies it: this resembles on-device feature computation patterns used in some mobile ML deployments (client-side session-based recommenders). Rejected here because our design point (§4, §34) is a centralized serving fleet, not edge devices, and client-side computation reintroduces exactly the "two implementations of one feature" skew risk (§2, P2) — every client would need the identical aggregation logic as the offline path, unenforceable once shipped inside independently-versioned client binaries.
