34. Back-of-Envelope Capacity Model

Design point (from §4): 10,000,000 entities, 200 features/namespace, 100 observations/entity/year, 3-year retention, 16-byte average value size, 10,000 QPS peak online read.

  1. Online memory per namespace = entities × features × (value_size + protobuf overhead) = 10M × 200 × (16B + 8B) ≈ 10,000,000 × 200 × 24B ≈ 48 GB per namespace (chained from the entity/feature counts in §4's series-count row).
  2. Online IOPS at peak = QPS × avg_features_per_request = 10,000 × 4 ≈ 40,000 Redis ops/sec — well inside a single Redis node's ~200k ops/sec envelope (chained from §4's throughput row), headroom to 5× before sharding (ADR-02).
  3. Offline raw storage per namespace = entities × features × obs/year × retention_years × value_size = 10M × 200 × 100 × 3 × 16B ≈ 960 GB raw.
  4. Offline compressed storage = raw × (1/amplification_target) ≈ 960 GB × (1/1.3⁻¹, i.e. ÷ ~3.7 typical ZSTD-3 ratio on numeric columns) ≈ ~260 GB per namespace after ZSTD-3 (chained from §4's storage-amplification row, which bounds the write-side overhead at 1.3×; compression ratio is the separate, larger effect estimated here).
  5. Materialization compute (batch) = source_rows_per_run / throughput_target = (10M entities × 1 daily obs) / 5,000 rows/sec (M6) ≈ 2,000 sec (~33 min) per full-catalog daily materialization pass, single worker — parallelized across the namespace's worker pool (§16) to fit the freshness SLA.
  6. PIT join cost for a training query = query_entities / throughput_target = 1,000,000 training rows / 1,000 entities/sec (M5) ≈ 1,000 sec (~17 min) for a million-row training set, single DataFusion worker.
  7. FD budget check = connections_to_redis + grpc_listener_backlog ≤ 4,096 (§4) — at pool size max(8, cores*2) on a 16-core host, ≈ 40 FDs to Redis, comfortably inside budget with headroom for the gRPC connection count at 10k QPS assuming HTTP/2 multiplexing (few hundred concurrent connections, not one-per-request).
  8. Working-set size for the shm cache (§23) = 90th-percentile 24h-accessed-entity-count × 256B/entry. Assuming 20% of the 10M-entity catalog is accessed per day (a typical recommender access-pattern skew) ≈ 2,000,000 × 256B ≈ 512 MB — comfortably fits in /dev/shm on any modern host, confirming §23's design assumption.
  9. Lineage event volume = (materialization jobs/day + reads/day) × avg_event_chain_length. At ~50 views × 24 hourly runs = 1,200 materialization events/day, plus an estimated 100,000 training/serving reads/day at ~1 event each ≈ ~101,200 events/day, well under the 10MB per-event cap (§20.6) and modest for the compaction job's 6-hourly batch (M11).
  10. Streaming state size (§18) = active_windows × entity_count_touched. For a 1-hour tumbling window over a 10M-entity stream with 5% daily active entities touching the window ≈ 500,000 × (256B RocksDB entry estimate) ≈ ~128 MB active state per view, per window — small relative to host memory, confirming the sketch-based approximate-aggregate fallback (§18.7) is only needed at higher cardinality/window-count combinations.
  11. Redis Cluster shard count at 5× design-point growth = projected_memory / per_shard_capacity = (48 GB × 5) / 50 GB-per-shard-ceiling (§31 bottleneck #1) ≈ 240 GB / 50 GB ≈ 5 shards, confirming ADR-02's documented next step activates well before the practical ceiling in §31.
  12. gRPC connection count at 10k QPS = QPS / requests_per_connection_per_sec. With HTTP/2 multiplexing at an assumed 200 in-flight requests/connection ≈ 10,000 / 200 = 50 concurrent connections per fs-online host, two orders of magnitude under the §4 FD budget (4,096), confirming headroom for connection-count growth without FD exhaustion.
