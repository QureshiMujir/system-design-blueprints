Self-examination questions from the blueprint; each points at the section where the answer lives.

32. Mental Models & First Principles

MM1 — "A feature is a time series, not a value." Every feature is really entity_id → (timestamp → value)*; a "current value" is just a query at t = now. Predicts: any API that hides the timestamp (a bare get_feature(entity, name)) is a leakage trap waiting to happen. Bug class without it: treating the online store's latest value as if it were the only value, forgetting the offline history exists and must agree with it (I2). Applied in §8.1, §8.4.

MM2 — "AS-OF join is a query, not a special case." Once you see point-in-time correctness as "the standard join predicate for time-varying data," you stop writing bespoke as-of-date filtering logic per feature and instead build one correct operator (§8.4) that every feature read goes through. Predicts: any feature-specific "as of" logic outside the shared join operator is a latent I1 violation. Bug class without it: N slightly-different, unauditable timestamp-filtering implementations, one per team. Applied in §14, §17.

MM3 — "The materialization engine is the only place skew can be introduced — so make it the only place that can write." Skew is not a bug that appears; it is a structural possibility that exists whenever two code paths compute "the same" value. Predicts: any proposal to let a serving-side service compute its own version of a feature (for latency or convenience) reintroduces skew regardless of how careful the implementers are. Bug class without it: training-serving skew (§2), rediscovered independently by every team that tries to "just compute it faster in the serving layer." Applied in §6 P2, §14.2.

MM4 — "Freshness and TTL are two different clocks." Freshness answers "is the system keeping up with its promise" (a producer-side, SLA question); TTL answers "is this specific value still usable" (a consumer-side, correctness question). Predicts: conflating them (e.g., using TTL alone to infer pipeline health) hides scheduler failures until data actually goes missing, losing the early-warning window. Bug class without it: silent SLA breaches that only surface once TTL expiry finally makes the effect visible. Applied in §6 P5/P9, §7 I4/I5, §16.

MM5 — "Lineage is a graph you can only query if you built it as data, not as logs." Free-text logs answer "what happened at time T"; a lineage graph answers "what does X depend on, transitively" — a fundamentally different query shape requiring structured, queryable storage from day one. Predicts: teams that "add lineage later" from existing logs cannot actually answer ancestor/descendant queries without a costly reprocessing project. Bug class without it: an incident response that takes weeks instead of the 5-minute drill in §20.4. Applied in §6 P7, §20.

MM6 — "A closed type system is a compile-time promise to your slowest consumer." The Rust hot path (§23) can only be fast and safe if every value it might ever see is one of a small, known set of shapes; every "just let it be Any" convenience request in the definition layer (§13) is actually a request to make the online path slower or unsafe. Predicts: any proposal to add an "escape hatch" arbitrary-object dtype will, if granted, eventually break the shm cache's fixed-layout assumption (§23.2). Bug class without it: a runtime deserialization failure in the one component (§23) that budget-wise cannot afford to have one. Applied in §6 P12, §11, §23.

MM7 — "Backpressure is a design decision, not a symptom of insufficient capacity." A system that queues without bound is not "more resilient," it is deferring a failure to a worse moment (an OOM under load, instead of a clean rejection under load). Predicts: any component missing an explicit queue-depth/concurrency limit will eventually fail catastrophically instead of gracefully during exactly the traffic spike the limit exists to survive. Bug class without it: the classic "worked fine until Black Friday" collapse. Applied in §6 P14, §15.9, §23.

MM8 — "Multi-tenancy is a property of the whole stack or it is not a property at all." Isolation enforced at only one layer (say, the API) is not isolation — it is a convention that holds until the first caller that bypasses that layer. Predicts: an audit that only checks SDK-level namespace filtering will pass while the storage layer remains fully shared and exploitable. Bug class without it: the failure mode named explicitly in §22.6 (SDK-only enforcement, trivially bypassed). Applied in §6 P10, §22.

MM9 — "A benchmark without a workload shape is a number, not evidence." p99 ≤ 5ms means nothing without stating the entity count, feature count, and concurrency it was measured at (§4's constraint rows always pair a number with its workload shape). Predicts: a performance claim quoted without its (entities, features, QPS) triple cannot be compared against a regression or against a competing design. Bug class without it: a benchmark-driven regression is "fixed" by silently narrowing the test's workload shape rather than the underlying latency, exactly the failure the M-table's Phase Gate column (§30) exists to pin down. Applied in §4, §30, §34.

Reference Implementations

  • Feast (github.com/feast-dev/feast) — study sdk/python/feast/feature_store.py and offline_stores/ / online_stores/. Lesson: a pluggable store Protocol per backend (mirrored as Rust traits in §11). Pitfall: early Feast's offline reads were full-table scans without partition pruning — do not repeat that in fs-offline (§14).
  • Hopsworks Feature Store (github.com/logicalclocks/feature-store-api) — study its dual-store governance and RBAC model. Lesson: namespace-scoped access control belongs at the registry layer, applied in §22. Pitfall: coupling governance too tightly to a specific metastore reduces portability.
  • LinkedIn Feathr (github.com/feathr-ai/feathr, archived 2023) — study its Spark-DSL derived-feature expression model. Lesson: derived features as DAG nodes, not a special case, applied in §6 P4. Pitfall: a Spark-only execution model made the interactive/SDK read path slow; fs-offline's DataFusion path exists to avoid that.
  • MLflow (github.com/mlflow/mlflow) — study its tracking-event schema. Lesson: the trace_id/run_id correlation pattern reused verbatim in LineageEvent (§11, §20). Pitfall: none directly reused — MLflow is the adjacent system, not the reference for our core join logic.
  • Apache DataFusion (github.com/apache/datafusion) — study its physical-plan operator trait (ExecutionPlan) and its Parquet reader. Lesson: our AS-OF join operator is implemented as a custom ExecutionPlan, applied in §8 and §14. Pitfall: DataFusion's default hash join is not AS-OF-aware; do not attempt to express AS-OF as a filtered hash join (quadratic in the worst case) — implement the sort-merge nearest-prior scan directly.
  • DuckDB (github.com/duckdb/duckdb) — study its native ASOF JOIN implementation (src/execution/operator/join/physical_asof_join.cpp) as the reference algorithm (sort-merge nearest-prior), applied in §8.4 and §12, where fs-offline's DataFusion operator reimplements it natively in Rust. Pitfall: do not depend on embedding DuckDB itself in production — it is the algorithmic reference, not a production dependency (ADR-06).

Glossary (§38) · 52 terms · site-wide glossary

Entity
the thing features describe (user, item, merchant, session, device).
Entity id
the primary key identifying one instance of an entity; a namespaced string in this system.
Feature
a named, typed value computed from a source about an entity, at a point in time.
Feature definition (FeatureDef)
the registered description of a feature: name, dtype, source, expression, owner, freshness SLA, TTL.
Feature view (FeatureView)
a bundle of features sharing a source and materialization schedule; the unit of scheduling.
Feature service (FeatureService)
a bundle of features one model consumes; the unit of deployment and the model-integration boundary.
Materialization
computing feature values from sources and writing them to both stores.
Offline store
the historical record of every feature value, suitable for point-in-time-correct training reads.
Online store
the latest-value-per-(entity, feature) record, suitable for low-latency inference reads.
Point-in-time correctness (PIT correctness)
the invariant that a query for entity E at time T returns the value visible at T, never a later one.
AS-OF join
the join finding, for each query row, the right-table row with the largest timestamp not exceeding the query timestamp.
Training-serving skew
the failure mode where training-time and serving-time feature computations diverge.
Label leakage
a training feature accidentally reflecting information only available after the label's true decision point.
Freshness SLA
the maximum age a feature value may have before the system alerts or refuses to serve.
TTL (time-to-live)
the age past which an online value is evicted rather than served.
Drift
a statistically detected shift in a feature's distribution over time.
Lineage
recorded relationships between sources, features, materialization runs, and consumers.
Namespace
a scoping prefix isolating one team's features at the registry, storage, and compute layers.
Snapshot (RegistrySnapshot)
an immutable view of registry state at a moment in time.
Registry
the Postgres database holding feature definitions and serving snapshots.
Source ref
a handle pointing at a Parquet file, SQL query, Kafka topic, or other data source.
Trace id
a request-scoped identifier tying together all lineage events for one action.
Span id
a step-scoped identifier within a trace, supporting hierarchical lineage.
Watermark
an estimate of "no future event will have an earlier event-time than this," used to bound streaming lateness.
Allowed lateness
the configured grace period after a watermark during which late events are still accepted rather than routed to a dead-letter topic.
Backfill
materializing a historical time range on demand, distinct from live scheduled materialization.
Idempotent materialization
the property that re-running the same job produces the same offline/online state.
Content-addressed partition
an offline Parquet file named by a hash of its inputs, enabling idempotent re-writes.
Parity sampler
the background process that samples online/offline pairs and asserts agreement (I2).
Schema evolution
changing a feature's or view's shape over time without rewriting history.
Safe schema change
a backward-compatible change (add nullable field, widen a dtype) applied without migration.
Unsafe schema change
a change requiring an explicit migration (remove a field, narrow a dtype).
Dual-write migration
materializing both an old and new schema in parallel during a transition window.
Sharing policy
an explicit, non-transitive cross-namespace feature-access grant.
Quality constraint
a declarative rule (not-null, in-range, distinct-count, regex) checked at materialization time.
Closed dtype system
the fixed enumeration of value types the system will ever store or serve.
Shm cache
the per-host /dev/shm-backed, memory-mapped, zero-copy online read cache (§23).
DAG (feature dependency graph)
the directed acyclic graph of feature views and their derived-feature dependencies.
Materialization job
one concrete execution unit: a feature view plus a time range plus a backend hint.
On-demand feature
a feature computed at request time from raw inputs rather than precomputed (deferred, §37).
Streaming feature view
a feature view whose source is a continuous event stream rather than a batch snapshot.
Tumbling / sliding / session window
the three windowing strategies over streaming event time (§18).
Reference implementation
a real, studied external system whose code or design this blueprint explicitly learns from or explicitly departs from (§5).
ADR (Architecture Decision Record)
a numbered, tabular record of a locked technical decision, its rejected alternatives, and the regime where each rejected alternative would actually win.
Invariant
a system property (I#) that must hold at all times, with a defined enforcement point, detection mechanism, and recovery path.
Principle
a numbered design rule (P#) governing every decision in the system.
Mental model
a compressed expert insight (MM#) predicting a bug class if not internalized.
Blast radius
the scope of impact of a given failure, used throughout §24/§25 to bound incident severity.
Error budget
the allowed accumulation of SLO violations before releases pause for reliability work (§26).
RTO (Recovery Time Objective)
the maximum acceptable time to restore service after an outage (§4).
SBOM (Software Bill of Materials)
a generated inventory of a build's dependencies, for supply-chain auditability (§29).
Provenance/attestation
a signed record of how and from what a release artifact was built (§29). ---
