309 — Incremental Self-Hosting Compiler

Project Number: 309

Project Name: Incremental Self-Hosting Compiler

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a compiler for a small statically-typed systems language ("the language", code-named Lyra) that is simultaneously incremental (demand-driven, memoized, on-disk query cache; warm rebuild after a 1-line edit recompiles only affected queries) and self-hosting (the compiler's own source is written in Lyra; a Rust stage0 seed compiles it; the resulting compiler recompiles itself to a byte-identical fixpoint). The deliverable is the union of those two hard properties in one artifact, and the spec confronts their interaction: caching must be deterministic enough that the self-hosting fixpoint holds with the cache warm, and fingerprints must be stable/versioned enough that a warm-cache stage produces the same bytes as a cold one.

Precise engineering terms. Lyra source → lyrac (the compiler binary). Pipeline: lex → error-recovering parse → AST → name resolution → bidirectional + HM-style type inference → desugar → SSA-based mid-level IR (LIR) → optimization passes (const-fold, DCE, mem2reg, inline) → codegen to two backends: a register bytecode VM (lbc) and a text-emit native surface (C99 text → system cc). Every cross-pass computation is a query in a memoizing engine (lyra-db): parse(File), resolve(Item), type_of(Def), lir(Def), codegen(Cgu), etc. Queries form a dependency DAG; recompute is red-green with early cutoff via stable output fingerprints; the DAG + fingerprints + serialized values persist in an on-disk cache.

System boundaries. In: Lyra source trees, a cache directory, target selection. Out: bytecode modules, C99 text (compiled by an external cc), diagnostics, the recompiled lyrac itself. Not in scope: the host OS, the external C compiler/linker, the VM's host syscalls beyond a tiny shim.

Explicit non-goals. (1) No production-grade optimizer — only enough passes to exercise IR + determinism (PhaseDeferred("FINAL_BLUEPRINT §19") for LLVM-class GVN/loop opts). (2) No borrow checker / lifetime inference — Lyra uses explicit ownership + a GC-free value model with move semantics, no region inference (§8). (3) No native object emission / own linker — native path emits C99 text only (PhaseDeferred("FINAL_BLUEPRINT §20") for direct ELF/Mach-O). (4) No incremental linking — relink is whole-program (§20). (5) No language-server protocol surface in v1 (PhaseDeferred("FINAL_BLUEPRINT §25")). (6) No package manager / dependency resolver — single source tree (§25).

Intended deployment model. A developer-tooling CLI, run locally and in CI. Single-process, multi-threaded query execution. Cache is a local directory (.lyra-cache/), one per build profile. No network, no daemon in v1 (a persistent daemon is PhaseDeferred("FINAL_BLUEPRINT §25")).

Target users/operators/developers. Compiler engineers learning incremental + self-hosting machinery; the maintainers of Lyra itself (who edit the compiler and rely on incremental rebuilds + fixpoint verification); CI operators who gate merges on stage1 == stage2 byte-identity and on incremental == clean differential checks.

Phase 0 deliverable (numbered crates/modules — Rust stage0 workspace).

  5. lyra-parser — error-recovering recursive-descent + Pratt parser → AST.
  6. lyra-db — the query engine: revisions, red-green, fingerprints, durability tiers, cycle detection, on-disk cache, GC.
  7. lyra-hir — desugared high-level IR (name-resolved), DefId, resolution maps.
  8. lyra-resolve — name resolution queries (resolve, module_scope).
  9. lyra-types — type checker (bidirectional + unification), Ty, inference queries.
  10. lyra-lir — SSA mid-level IR, lowering from HIR.
  11. lyra-opt — passes: const-fold, DCE, mem2reg, inline (deterministic).
  12. lyra-codegen-bc — bytecode backend → lbc module format.
  13. lyra-codegen-c — C99 text backend.
  14. lyra-vm — register bytecode interpreter + tiny host shim.
  15. lyra-mangle — deterministic symbol mangling, content-addressed CGU naming.
  16. lyra-driver — lyrac CLI: orchestrates queries, cache lifecycle, diagnostics.

What later phases unlock. Phase 0 = host (Rust) compiler lyrac0 compiles Lyra → bytecode + C99 (cold builds only). Incrementality (cache, red-green) lands in §17–18. Self-hosting (Lyra-source compiler lyrac1) lands in §22. The fixpoint + DDC gate in §23. Incremental-self-hosting interaction (warm-cache fixpoint, fingerprint portability) in §24. Conformance/fuzz/perf in §25.

Deferred features (gated). GVN/loop opts §19; native object/own-linker §20; incremental linking §20; LSP + daemon + package manager §25; cross-compilation matrix beyond host triple §20; distributed/shared cache §18.

Estimated timeline. Phase 0 (host compiler, cold, both backends, language self-sufficient enough): 8–14 weeks. Incremental engine + durable cache: +6–8 weeks. Self-hosting + fixpoint: +8–12 weeks. Interaction hardening + conformance + fuzz + perf: +8–12 weeks. Full implementation: ~9–14 months for one engineer at staff level.

Recommended language and exact rationale. Source language = Lyra (a small statically-typed systems language we define and then make self-hosting). Bootstrap host (stage0) = Rust. Rationale: (a) we need some host to write the first compiler — a compiler cannot compile itself from nothing (bootstrap seed problem); (b) Rust gives a memory-safe, data-race-free front end so stage0 bugs are logic bugs not UB, which matters because stage0 is the root of trust for the whole self-hosting chain; (c) Rust's deterministic codegen + BTreeMap/sorted-iteration discipline makes it tractable to keep stage0 output reproducible, a precondition for the fixpoint; (d) rustc's own query system (salsa-adjacent) is the closest production reference, so idioms transfer. Lyra itself must grow expressive enough — functions, structs, enums, generics via monomorphization, modules, pattern matching, basic traits/interfaces — to express a full compiler, at which point stage0 is retired from the trust chain except as the seed.

Required prerequisites. Compilers (lexing, Pratt parsing, error recovery, HM + bidirectional typing, SSA, monomorphization, codegen); incremental computation (demand-driven memoization, red-green, fingerprinting, salsa/adapton model); bootstrapping theory (Thompson's Reflections on Trusting Trust, diverse double-compilation); concurrency (deterministic parallel query execution, interning under threads); OS internals (mmap'd cache, atomic file replace, fsync semantics); content-addressing + hashing (BLAKE3, stable hashes); reproducible builds (sorted outputs, fixed float formatting, mangling). Databases-lite: the query cache is essentially a tiny embedded incremental database.

2. Why Build This

Unique systems knowledge. This project sits at the intersection of two notoriously deep topics and forces their interaction. Building either alone (242 Incremental Compiler, 243 Self-Hosting Compiler) teaches half; building both in one binary teaches the part nobody writes down: incremental caching is a form of memoized nondeterminism risk, and self-hosting is a determinism proof, so the two constrain each other. You learn why rustc's incremental cache is versioned and invalidated across compiler versions, why codegen must avoid HashMap iteration, why fingerprints must be content-addressed, and how a warm cache can silently miscompile if span/ID stability is wrong.

Historical & architectural significance. Self-hosting is the canonical milestone of language maturity (C, Go, Rust, OCaml, TypeScript all self-host). Thompson's trusting-trust attack (1984 Turing lecture) showed self-hosting is also a supply-chain problem: a compromised seed can inject a backdoor that survives even when source is clean. Diverse double-compilation (Wheeler, 2009) is the known defense. Incremental compilation (salsa, adapton, the red-green algorithm in rustc) is the architectural answer to "edit one line, don't recompile the world." Putting them together is what real toolchains do and rarely document.

Engineering muscles developed. Demand-driven dataflow; cache invalidation done correctly (the famous "hard problem"); deterministic parallelism; reproducible builds; differential testing as a correctness oracle; fuzzing of edit sequences (not just inputs); designing stable identifiers that survive source edits; reasoning about a system whose output is itself.

Production engineering concepts exercised. Content-addressed storage; durability tiers; garbage collection of a derived-data cache; crash-only persistence (atomic rename, fsync); early-cutoff optimization; provenance/SBOM for a bootstrap seed; SLOs on rebuild latency; chaos via cache corruption injection.

Cross-links to related projects. Compilers: 242 (Incremental), 243 (Self-Hosting), 258 CSS Selector Engine, 259 JS Parser+Runtime (parsing/error recovery reuse). Runtimes: 203 WASM Runtime (the bytecode VM shares a register-machine design). Databases: the query cache is a tiny embedded incremental DB — links to LSM/columnar engines (118) on content-addressing + compaction/GC. Build systems: Bazel/Buck action caching is the same red-green idea at a coarser grain. Storage: 311 NVMe / backup-snapshot (111) for atomic write + fsync discipline. Observability: query traces as structured events.

Calibration value. After this, "incremental build correctness" and "reproducible self-hosting" stop being magic. You can read rustc's rustc_query_system and salsa and recognize every mechanism; you can debug a "works clean, breaks incremental" miscompile by auditing the red-green log; you can reason about trusting-trust for any toolchain. It permanently raises the ceiling on compiler + build-system work.

What Mastery Looks Like

  • Build a correct demand-driven incremental engine — after Phase 4 (§16) you can implement red-green verification with automatic dependency-edge capture and early cutoff, and explain exactly why a missing edge or an under-broad fingerprint produces a silent miscompile that only the differential harness catches (P5, INV-4/INV-5).
  • Engineer stable identities that survive edits — after Phase 3 (§15) you can design item-relative spans + path-hash DefIds so an edit invalidates only its true dependents, and prove the property under an edit-replay fuzzer rather than asserting it (ADR-5/ADR-6, INV-6).
  • Make codegen byte-reproducible and prove it — after Phase 8 (§20) you can purge every nondeterminism source (HashMap iteration, unstable register-allocation order, libc float formatting) from an output path and gate it with a 100×-repeat + cross-machine harness (ADR-17/ADR-29, INV-1/INV-14).
  • Drive a self-hosting bootstrap to a byte-identical fixpoint — after Phase 11 (§23) you can orchestrate stage0→1→2, gate bytes(stage1) == bytes(stage2), and bisect a fixpoint failure to the single nondeterministic byte via disassembly diff (INV-3, P1/P2).
  • Reason about trusting-trust as a supply-chain threat — after Phase 11 (§23) you can implement diverse double-compilation against a genuinely independent host and state precisely what DDC does and does not prove about a compromised seed (P1/P2, ADR-18, §Threat Model).
  • Reconcile caching with determinism (the union property) — after Phase 12 (§24) you can prove incremental == clean and a warm-cache fixpoint simultaneously, and explain why a content-addressed artifact is the precondition that lets a reused CGU not perturb the fixpoint (INV-2 ∧ INV-3, §24).
  • Run a crash-only derived-data store — after Phase 6 (§18) you can build an atomic-rename + content-addressed + checksummed cache where a torn write can never surface as a valid-looking wrong value, and recover by dropping to a cold recompute (ADR-13, INV-8).
  • Bound a compiler against hostile input — after Phase 13 (§25) you can defend against compile-time resource-exhaustion (deep nesting, monomorphization blowup, cache blowup) with depth/instance/size caps and a recompute watchdog, proving zero hangs/OOM under fuzz (Principle 8, §Threat Model).

Architecture, continued — the self-hosting/bootstrap plane (lyra-fixpoint) and the verification plane (lyra-diff), which sit beneath the query→codegen pipeline above.

   ───────────────────────  SELF-HOSTING / BOOTSTRAP PLANE  (lyra-fixpoint) ───────────────────────

     stage1 ──recompiles its OWN Lyra source──► stage2 ;  GATE: bytes(stage1) == bytes(stage2)

Box: lyra-driver. CLI front door (lyrac build|check|emit|fixpoint|gc). Parses args, selects a build profile (debug/release/bootstrap — profile is a fingerprint input), opens/creates the cache, sets cli_flags() and source_text() input queries, demands the root query (codegen of all CGUs, or check for typeck-only), drains the diagnostics sink (sorted deterministically), persists the cache on success. Owns cache lifecycle (open → use → flush → close); never computes derived facts itself.

Box: lyra-db (query engine). The heart. Stores every query node: key, last value, output fingerprint, the revision at which value last changed/was verified, recorded input dependencies (edges), verified_at revision. Implements red-green: on a new revision derived queries are maybe-dirty; a query is re-verified by checking whether any dependency's fingerprint changed (green = unchanged → reuse value, no recompute; red = changed → recompute, then compare new fingerprint for early cutoff). Owns Revision counter + durability tiers, the Fingerprint store, the Dependency DAG + cycle detector, and serialization to/from the on-disk cache.

Box: lyra-span / lyra-intern. Interns files and strings; assigns Symbol, FileId, ItemPath. Critically provides relative spans — spans stored relative to an enclosing item's start, plus item-path hashes — so inserting a blank line at the top of a file does not change spans/IDs of items below it, so their derived queries stay green. This is the linchpin that makes incrementality not invalidate a whole file on every edit.

Box: parse(File) → AST. Derived query: takes source_text(File) (input), runs the error-recovering parser, returns an arena of AST nodes with AstIds. Fingerprint = hash of AST shape (not raw bytes), so reformatting-only edits that don't change structure early-cutoff downstream.

Box: resolve(Item) → HIR refs. Name resolution per item: builds module scopes, resolves identifiers to DefIds, lowers AST → HIR. Depends on parse of relevant files and on module_scope queries.

Box: type_of(Def) → Ty. Bidirectional + HM unification inference/checking for a definition. Depends on resolve and on type_of of referenced defs (forming the DAG the engine memoizes; type cycles are detected and surfaced as errors, not hangs).

Box: lir(Def) → SSA + opt. Lowers typed HIR to SSA-form LIR, runs the deterministic optimization pipeline. Output fingerprint enables early cutoff: a comment-only edit may change type_of fingerprint but not lir, stopping recompute before codegen.

Box: codegen(Cgu). Groups defs into content-addressed codegen units (CGU name = hash of the set of lir fingerprints it contains), emits bytecode or C99 text. Content-addressing means an unchanged CGU's artifact is reused verbatim — the core incremental win at codegen, and the thing that must be deterministic for the fixpoint.

Box: lbc modules / lyra-vm. Bytecode artifact format + register-machine interpreter with a tiny host shim (I/O, allocation). The VM runs lyrac1 (the self-hosted compiler) in the bootstrap plane.

Box: C99 text → external cc / native exe. Alternative backend emitting portable C99 text handed to system cc. Trust boundary: external cc/linker are outside our determinism control, so native fixpoint is checked at the C-text level (our output) plus the final binary when cc is itself reproducible.

Box: on-disk cache (.lyra-cache/). Persists DAG, fingerprints, serialized query values, artifacts. Crash-only: temp-file + atomic rename + fsync; corrupt entries detected by checksum and dropped (treated as cold). GC reclaims values unreachable from current roots within a durability budget.

Box: lyra-fixpoint (self-hosting plane). Orchestrates stage0→1→2, performs the byte-identity gate bytes(stage1) == bytes(stage2), runs diverse double-compilation (DDC) against an independent host build. Trust boundary: stage0 is the root of trust; DDC reduces reliance on it.

Box: lyra-diff (verification plane). Runs a clean build and an incremental build (cold cache vs warm-after-edit-replay) and byte-compares every artifact, enforcing any incremental build == equivalent clean build.

Box: Diagnostics. Collects errors/warnings with stable ordering (sorted by file, then byte offset, then code) so diagnostic output is reproducible (a fingerprint input under --deny-warnings).

6. Design Principles

  1. Determinism is the prime directive. Same inputs → byte-identical outputs, always (§4 = 100%). It is the precondition for both the self-hosting fixpoint and incremental==clean. Tradeoff: forbids HashMap iteration in any output path, ad-hoc thread interleaving in codegen, wall-clock/PID/env leakage. Operationally: a single nondeterministic byte = a CI-red fixpoint, debugged by bisecting passes with a determinism harness. Violating it makes the fixpoint flaky and the cache unsafe.

  2. The incremental result must equal the clean result. (incremental == clean, §4, central invariant.) Every cache hit is a claim that recompute would produce the same value; the diff harness (lyra-diff) continuously falsifies that claim. Tradeoff: more bookkeeping (fingerprints, edges). Violating it = silent miscompile that only appears after an edit — the worst class of bug.

  3. Inputs vs derived, strictly separated. Only source_text, file_list, cli_flags are inputs (set by the driver, bump the revision). Everything else is a pure function of inputs + other queries. Tradeoff: no hidden mutable state, no I/O inside derived queries. Violating it breaks red-green (a query that reads the clock can't be memoized correctly).

  4. Fingerprints are content-addressed and versioned. A query's fingerprint = BLAKE3 of its serialized value; the cache carries a schema/compiler version that invalidates everything on mismatch (§7 INV-9). Tradeoff: cross-version cache reuse is sacrificed for correctness unless a fingerprint is provably stable. Violating it = a warm cache from an old compiler poisons a new one (cache poisoning, §Threat Model).

  5. Stable identities survive edits. Relative spans + item-path hashing + interned DefIds mean inserting a line doesn't renumber items (§3 lyra-span). Tradeoff: indirection cost on every span resolve. Violating it = spurious invalidation (everything below an edit goes red → no incrementality) or, worse, ID reuse → silent miscompile.

  6. Early cutoff is first-class, not incidental. A query that recomputes to the same fingerprint stops propagation immediately. Tradeoff: must compute the full value before knowing the fingerprint (no free lunch on the changed query, only on its dependents). Violating it = signature-preserving edits recompile the world (perf failure, §4 N-dependents target).

  7. Crash-only persistence. The cache is written via temp+rename+fsync; any interrupted write leaves the prior consistent state; corrupt entries are checksum-detected and dropped (treated as cold), never trusted. Tradeoff: write amplification, fsync latency. Violating it = a torn write produces a valid-looking corrupt value → miscompile.

  8. Bounded resources everywhere. Recursion-limited query depth (cycle detector), bounded codegen queue (backpressure), GC-bounded cache size (§4). Tradeoff: pathological inputs get a clean error, not a hang/OOM. Violating it = a malicious or generated program DoSes the compiler (§Threat Model).

  9. Observability by default. Every query records hit/miss/red/green, recompute time, fingerprint; a structured red-green audit log is dumpable. Tradeoff: small per-query overhead (kept off the hot path via sampling in release). Violating it = "works clean, breaks incremental" is undebuggable.

  10. The seed is the root of trust, and we minimize + verify it. stage0 (Rust) is small, audited, and its provenance is recorded; DDC (§23) is the standing defense against a compromised seed. Tradeoff: DDC doubles bootstrap cost. Violating it = a trusting-trust backdoor survives undetected.

  11. No nondeterministic parallelism in output paths. Parallel query execution is allowed (it's pure), but order of effects (interning, codegen emission, diagnostics) is canonicalized by sorting on stable keys before serialization. Tradeoff: a sort/merge step. Violating it = thread-race nondeterminism → fixpoint flake.

  12. Errors are values, recovery is mandatory. The parser/type-checker recover and continue, producing partial IR + sorted diagnostics; a query never panics on bad input. Tradeoff: error nodes thread through the IR. Violating it = one syntax error aborts the whole incremental session.

  13. One source of truth per fact. A DefId's type is computed by exactly one query (type_of); no duplicate computation paths. Tradeoff: discipline on query boundaries. Violating it = two paths can disagree → nondeterminism + cache divergence.

  14. Lyra stays small enough to self-host but no smaller. Feature set is bounded by "can it express this compiler?" Nothing added for elegance alone. Tradeoff: ergonomics sacrificed. Violating it = the language balloons, stage0 grows, the trust base widens, bootstrap slows.

  15. Profiles are explicit and fingerprinted. debug/release/bootstrap differ in opt level + flags; the profile is a fingerprint input so a debug cache never serves a release build. Tradeoff: separate caches per profile. Violating it = cross-profile cache reuse → wrong artifact.

8. Domain Model / Source Language (Lyra) — Grammar + AST + IR

8.1 Language overview (just enough to self-host)

Statically typed; module system; functions; struct/enum (sum types) with pattern matching; generics via monomorphization; traits/interfaces (static dispatch only in v1, dynamic dispatch deferred §19); explicit ownership + move semantics, no GC (the compiler manages its own arenas, like a real compiler); Result/Option-style error handling via enums; bounded integer + float + bool + string + array + reference types. No closures capturing by environment in v1 beyond top-level fn pointers (lambdas deferred to keep stage0 small, PhaseDeferred §19). Enough to express a lexer, parser, type-checker, IR, and codegen — i.e. itself.

8.2 Concrete grammar (EBNF, normative — docs/spec/lyra-lang.md)

Program     ::= { Item } ;

Generics    ::= "<" GenericParam { "," GenericParam } ">" ;
GenericParam::= Ident [ ":" TraitBound { "+" TraitBound } ] ;
TraitBound  ::= Path ;
Params      ::= Param { "," Param } ;

StructDef   ::= [ "pub" ] "struct" Ident [ Generics ] "{" { Field } "}" ;
Field       ::= [ "pub" ] Ident ":" Type "," ;
EnumDef     ::= [ "pub" ] "enum" Ident [ Generics ] "{" { Variant } "}" ;

TraitDef    ::= "trait" Ident [ Generics ] "{" { FnSig } "}" ;

              | "[" Type ";" Expr "]"          (* fixed array *)
              | "[" Type "]"                    (* slice *)
              | Path [ "<" Type { "," Type } ">" ]  (* named / generic *)
              | "(" [ Type { "," Type } ] ")"  (* tuple/unit *)

              | "f32"|"f64"|"bool"|"char"|"str" ;

Block       ::= "{" { Stmt } [ Expr ] "}" ;     (* trailing expr = block value *)
Stmt        ::= LetStmt | ExprStmt | ItemStmt ;
LetStmt     ::= "let" [ "mut" ] Pattern [ ":" Type ] [ "=" Expr ] ";" ;
ExprStmt    ::= Expr ";" | BlockExpr ;
ItemStmt    ::= FnDef | StructDef | EnumDef | ConstDef ;

Grammar, continued — the expression precedence ladder, patterns, and literals.

Expr        ::= Assign ;
Assign      ::= LogicOr [ "=" Assign ] ;
LogicOr     ::= LogicAnd { "||" LogicAnd } ;
LogicAnd    ::= Compare { "&&" Compare } ;
Compare     ::= Term { ("=="|"!="|"<"|"<="|">"|">=") Term } ;
Term        ::= Factor { ("+"|"-"|"|"|"^") Factor } ;
Factor      ::= Unary { ("*"|"/"|"%"|"&"|"<<"|">>") Unary } ;
Unary       ::= ("!"|"-"|"&"|"&mut"|"*") Unary | Postfix ;
Postfix     ::= Primary { Call | Index | Field | TryOp } ;

Index       ::= "[" Expr "]" ;
Field       ::= "." Ident | "." IntLit ;        (* field / tuple index *)
TryOp       ::= "?" ;                             (* error propagation *)

              | "(" Expr { "," Expr } ")" ;       (* tuple *)
BlockExpr   ::= Block | IfExpr | MatchExpr | LoopExpr | WhileExpr | ForExpr
              | ReturnExpr | BreakExpr | ContinueExpr ;
IfExpr      ::= "if" Expr Block [ "else" ( IfExpr | Block ) ] ;
MatchExpr   ::= "match" Expr "{" { MatchArm } "}" ;
MatchArm    ::= Pattern [ "if" Expr ] "=>" ( Expr "," | BlockExpr ) ;
LoopExpr    ::= "loop" Block ;
WhileExpr   ::= "while" Expr Block ;
ForExpr     ::= "for" Pattern "in" Expr Block ;
ReturnExpr  ::= "return" [ Expr ] ;
StructLit   ::= Path "{" { Ident ":" Expr "," } "}" ;

Lexical: identifiers [A-Za-z_][A-Za-z0-9_]*; ints with optional suffix (123i64, 0xFF, 0b1010, _ separators); floats 1.0, 1e9, f32 suffix; strings double-quoted with escapes; char single-quoted; comments // line, /* */ block (nesting allowed); trivia (whitespace/comments) preserved in the token stream for span fidelity but ignored by the grammar.

8.3 AST (lyra-ast) — node taxonomy + IDs

  • Arena-allocated; every node has an AstId (arena index, stable within one parse) and a relative span (offset from the enclosing item start). Top-level items also carry an ItemPath (e.g. crate::parser::expr).
  • Node families: Item{Fn,Struct,Enum,Trait,Impl,Mod,Use,Const}, Stmt{Let,Expr,Item}, Expr{Lit,Path,Bin,Un,Call,Index,Field,If,Match,Loop,While,For,Block,StructLit,Tuple,Return,Break,Continue,Try,Assign}, Pat{Wild,Lit,Bind,Tuple,Variant,Struct}, Type{Ref,Array,Slice,Path,Tuple,Prim}.
  • Error recovery: an ErrorNode family member exists for each family (ExprError, TypeError, ItemError) so a malformed subtree is localized, not fatal.

Illustrative AST node signatures (≤2 lines each, schema only):

struct FnDef { path: ItemPath, generics: Vec<GenericParam>, params: Vec<Param>, ret: TypeId, body: Option<BlockId>, span: RelSpan }
enum Expr { Lit(LitId), Path(PathId), Bin{op:BinOp,l:ExprId,r:ExprId}, Call{callee:ExprId,args:Vec<ExprId>}, /* … */ Error }

8.4 HIR (lyra-hir) — name-resolved, desugared

  • AST → HIR drops sugar: for → loop + iterator protocol calls; ? → match on Result; while → loop+if+break; method calls → fully-resolved function calls with explicit self; trait-bounded generic calls record the resolved impl. Every identifier becomes a DefId or a local HirId.
  • DefId = (crate, ItemPath-hash, disambiguator) — stable across edits as long as the item path is unchanged (INV-6). Local variables get HirIds scoped to the owning DefId.
struct DefId { crate_: u32, path_hash: u64, disambig: u16 }  // stable identity
enum HirExpr { Call{def:DefId, generic_args:Vec<Ty>, args:Vec<HirId>}, Match{scrut:HirId, arms:Vec<HirArm>}, /* … */ }

8.5 LIR (lyra-lir) — SSA mid-level IR (docs/spec/lir.md)

  • Per-DefId function = list of basic blocks; each block = list of SSA instructions ending in a terminator. Values are SSA %n. φ-nodes at control-flow merges (placed via dominance frontiers, P3). Types fully monomorphized (generics resolved → concrete Ty); no generic remains in LIR.
  • Memory model: explicit alloca/load/store before mem2reg; after mem2reg, scalars are SSA values, only address-taken locals remain in memory.

LIR text form (illustrative syntax shape only — no worked lowering):

fn @<crate::path> (%<arg>: <ty>, …) -> <ty> {
  bb<n>:
    %<v> = <opcode> %<operand>, …      ; arithmetic/compare/memory/cast (opcode set below)
    <terminator>                        ; br | condbr %<v>, bb<t>, bb<f> | switch | ret <v> | unreachable
  bb<t>: ret <v>
  bb<f>: %<v> = phi [bb<a>: <v>, bb<b>: <v>]
}

LIR opcode set (compact): arithmetic (add sub mul sdiv udiv srem urem and or xor shl shr), compare (eq ne slt sle ult ule sgt …), memory (alloca load store gep), aggregate (extractvalue insertvalue), control (br condbr switch ret unreachable), call (call), const (iconst fconst), cast (trunc zext sext fptosi sitofp bitcast), phi (phi). Type lattice: integer widths, float widths, pointer, aggregate (struct/array), bool, unit.

Verifier rules (enforced before opt + before codegen): SSA dominance (def dominates use); types well-formed; terminators end every block; φ operands = predecessor count; no use of poison after unreachable.

8.6 LBC bytecode (docs/spec/lbc.md)

  • Register VM (not stack): each function declares a register count; instructions are 4-byte aligned (opcode:u8, a:u8, b:u8, c:u8) with wide immediates in a side table; a per-module constant pool holds ints/floats/strings/function refs. Reloc-free: calls reference constant-pool function indices, resolved at module load, so module bytes are position-independent and content-addressable.
  • Module layout: [magic 'LBC0'][version u16][const pool][function table][code section][debug section(optional, excluded from fingerprint)].

8.8 Worked example — a 1-line edit, red-green propagation

Source: fn add(a:i64,b:i64)->i64 { a + b }. User edits the body a + b → a + b + 0.

  module_scope(crate)    : verify → deps' fps unchanged (no new items) → GREEN (early cutoff)

RESULT: zero artifacts re-emitted; warm rebuild ~ a few ms; INV-2 holds (clean build of the

This shows why early cutoff matters (the +0 is folded away, so codegen never runs) and why determinism matters (the fold must be identical clean vs warm).

Running (after recompute) new fp ≠ old fp Green@r' (changed) store new value+fp; dependents become MaybeDirty
Green/MaybeDirty GC: unreachable from roots & beyond durability window Absent (evicted) drop value (keep fp+edges if cheap, else full evict)
any cache load checksum fail Absent treat as cold

ADR-12 VM design Register machine, threaded dispatch stack machine, AST-walking interpreter Register VM is faster + closer to LIR; we need ≤5× native to run lyrac1 A stack machine wins when bytecode density and a trivial verifier/codegen matter more than dispatch speed (JVM/WASM/CPython stack ISAs); an AST-walker wins for a prototype where implementation simplicity dominates and speed is irrelevant.
ADR-13 Cache storage Directory of sharded, checksummed, content-addressed files + a manifest single SQLite DB, LMDB, in-memory only Crash-only atomic-rename semantics are simplest on a file dir; content-address dedups artifacts A single embedded DB (SQLite/LMDB) wins when the cache needs transactional multi-key updates, secondary indexes, or concurrent multi-writer access — a structured store then beats a flat content-addressed dir's coarse file locking.
ADR-14 Cache durability Durability tiers (volatile / synced) + revision manifest always-fsync (slow), never-fsync (unsafe) Tiers bound flush latency (§4) while keeping inputs durable Always-fsync wins when the cache is the authoritative store of expensive-to-recompute results on unreliable hardware and a crash losing derived data is unacceptable (durability > flush latency); never-fsync wins for a pure in-RAM/tmpfs cache that is intentionally discarded per session.
ADR-15 Serialization (cache values) Versioned, deterministic, length-prefixed binary (custom) serde+bincode (ordering caveats), JSON (slow, float drift), protobuf Must be byte-deterministic + version-tagged (INV-9); custom keeps full control Protobuf/serde wins when the serialized data crosses a language or service boundary and schema evolution / cross-tool interop matters more than byte-exact determinism (an externally consumed cache or an RPC payload).
ADR-16 Concurrency model Work-stealing thread pool over pure queries; canonical sort before emit single-threaded, async/await, actor model Queries are pure → safe to parallelize; sort restores determinism (Principle 11) Single-threaded wins on a small program or an embedded build where the parallel-scheduling overhead + the canonical-sort tax exceed the speedup; async/await wins when the workload is I/O-bound (a network-fetching remote-cache client) rather than CPU-bound query compute.
ADR-17 Determinism enforcement Ban HashMap iteration in output paths; use BTreeMap/sorted Vec; fixed float fmt trust developers to be careful Lint + CI determinism harness (INV-1); humans forget Trusting developers (HashMap allowed) wins in code paths that never feed an output or a fingerprint — internal scratch maps on the hot path — where HashMap's O(1) access beats BTreeMap's log factor and order is provably unobservable.
ADR-18 Bootstrap verification DDC (diverse double-compilation) + byte-identical fixpoint gate trust the seed; reproducible-build-only DDC is the only known defense against trusting-trust (P1/P2) Reproducible-build-only (no DDC) wins when the seed compiler is itself already trusted via an independent, audited supply chain (e.g. a distro-built compiler with its own provenance), making the cost of maintaining a second diverse host unjustified.

ADR-21 Dependency policy Near-zero deps; BLAKE3 + memmap2 + a small arg parser only; vendored freely pull crates Each dep widens the trust base of the root-of-trust host (Principle 10) Liberal deps win for application software with no root-of-trust role and a tight delivery deadline, where development velocity from rich crates outweighs supply-chain surface (the opposite of a bootstrap seed's threat model).

ADR-23 Fuzzing cargo-fuzz: source fuzzer + edit-sequence fuzzer (replay) none Edit-sequence fuzzing is the only way to find span/ID-instability miscompiles No fuzzing wins only for a non-incremental tool processing fully trusted input on a closed corpus, where the span/ID-instability and hostile-input failure classes (§Threat Model) simply do not exist.
ADR-24 Logging / tracing Structured events (tracing), red-green audit log, off hot path in release printf, always-on verbose Observability of cache decisions is essential (Principle 9) printf/always-on verbose wins during early bring-up of a single module before the query engine exists, where structured tracing infrastructure is premature and a few prints suffice to debug.

ADR-26 CI/CD GitHub Actions: build → test → conformance → fixpoint → diff → fuzz-smoke none / ad hoc Determinism gates must run every PR; fixpoint is non-negotiable Ad-hoc/local-only CI wins for a solo exploratory prototype that never accepts external contributions, where the fixpoint/diff gates are run by hand and hosted CI is unjustified overhead.
ADR-27 Packaging Static lyrac binary + checked-in seed provenance doc dynamic libs, container-only A compiler should be a single self-contained binary; seed provenance is a trust artifact Container-only distribution wins when the compiler has heavy, version-sensitive external toolchain deps (a specific cc, sysroot) that a container pins reproducibly — there an image is a more honest unit than a "static" binary that still shells out to cc.
ADR-28 Reproducibility strategy SOURCE_DATE_EPOCH only sanctioned clock; no timestamps in artifacts/cache fps; sorted everything embed build time/host Any embedded timestamp breaks the fixpoint (INV-1) Embedding build time/host wins for release binaries where forensic build provenance in the artifact is a compliance requirement and reproducibility is not — the timestamp then lives in a non-fingerprinted section (as this design itself does for version stamps, §23).
ADR-29 Floating-point formatting Single canonical shortest-round-trip formatter (Ryū-style), fixed platform printf("%g"), libc-dependent libc float formatting varies by platform/locale → nondeterminism (INV-14) Platform printf wins for a single-platform tool whose float output is human-facing only (never fingerprinted, never cross-machine compared), where pulling in a custom formatter is needless code.
ADR-30 Licensing Apache-2.0 OR MIT (dual), incl. seed binaries' provenance GPL (viral, complicates seed redistribution) Permissive; standard for toolchains; seed provenance kept auditable GPL/copyleft wins when the project's goal is to force downstream toolchains built on it to remain open (a political/ecosystem stance, as GCC chose), accepting the redistribution friction in exchange for copyleft guarantees.

11. Core Schema and Core Types

Normative API surface. Signatures are illustrative (≤2 lines), not implementations. Every type lists ownership / mutation / concurrency / persistence / serialization / compatibility semantics.

11.1 Identity & span types (lyra-span, lyra-intern)

struct FileId(u32)                 // dense id into the file table
struct Symbol(u32)                 // interned string id; thread-stable (INV-13)
struct ItemPath { segments: Vec<Symbol> }      // e.g. crate::parser::expr
struct RelSpan { anchor: AstId, lo: u32, hi: u32 }   // offsets relative to enclosing item (INV-6)
struct AbsSpan { file: FileId, lo: u32, hi: u32 }    // resolved on demand for diagnostics only
struct DefId { crate_: u32, path_hash: u64, disambig: u16 }   // stable identity across edits
  • Ownership: FileId/Symbol/DefId are Copy value handles; the interner/file-table own the backing data. Mutation: interners are append-only (never reassign an existing id). Concurrency: interner uses a sharded lock + canonical-assignment so concurrent inserts of the same string yield one id deterministically (INV-13). Persistence: Symbol/DefId are not serialized raw across builds — strings/paths are re-interned, ids re-derived from path hashes, guaranteeing stability. Serialization: RelSpan is serialized (cheap, edit-stable); AbsSpan is never persisted (derived). Compatibility: DefId.path_hash algorithm is part of the cache version (INV-9); changing it invalidates the cache.

11.2 Query engine types (lyra-db)

struct Revision(u64)                       // monotonic (INV-10)
enum Durability { Volatile, Low, High }    // durability tier (ADR-14)
struct Fingerprint([u8; 32])               // BLAKE3 of a query value (ADR-4)
struct QueryKey { query: QueryId, key_hash: u64 }    // identifies a node
struct DepEdge { to: QueryKey }            // recorded input dependency (INV-5)
struct QueryNode {
  key: QueryKey, value: Option<SerializedValue>, fp: Fingerprint,
  changed_at: Revision, verified_at: Revision, deps: Vec<DepEdge>, durability: Durability,
}
trait Query { type Key; type Value: Fingerprintable; fn execute(db,&Key) -> Value; const ID: QueryId; }
  • Ownership: the Database owns all QueryNodes in a slot map keyed by QueryKey. Mutation: only the engine mutates nodes, under per-node state transitions (§8.10); user query fns are pure. Concurrency: nodes guarded by fine-grained locks / a concurrent map; a node being computed is marked Running so concurrent demands block on the same computation (no double-compute, INV-13-adjacent determinism). Persistence: QueryNode (minus volatile values) serialized to the on-disk cache via versioned binary (ADR-15). Serialization: deterministic, length-prefixed; Fingerprint stored verbatim. Compatibility: node layout is cache-version-gated (INV-9).
fn maybe_changed_after(db, key: QueryKey, since: Revision) -> bool   // red-green verify primitive
fn fetch<Q: Query>(db, key: Q::Key) -> Q::Value                      // memoized demand entrypoint
fn set_input<I: InputQuery>(db, key, value, durability: Durability)  // bumps Revision
fn intern_fingerprint(value: &impl Fingerprintable) -> Fingerprint   // BLAKE3 of canonical bytes
  • Contract: fetch is the only way derived values are obtained; it records the caller→callee edge (INV-5) and triggers verify/recompute per §8.10. maybe_changed_after is recursive and is where early cutoff happens (returns false if recompute yields the same fp).

11.3 Fingerprintable contract

trait Fingerprintable { fn fingerprint(&self, h: &mut Blake3Hasher); }   // canonical, order-stable
  • Invariant: fingerprint MUST visit fields in a fixed order, MUST sort any map/set, MUST format floats via the canonical formatter (INV-14), and MUST NOT include non-deterministic data (pointers, timestamps, thread ids). This trait is the determinism choke-point (INV-1). Violations are caught by the determinism harness.

11.4 AST / HIR / Type / LIR core types

// AST (lyra-ast)
struct AstModule { items: Vec<AstId>, arena: AstArena, file: FileId }
// HIR (lyra-hir)
struct HirItem { def: DefId, kind: HirItemKind, generics: Vec<GenericParam> }
enum Ty {                                   // canonical, hash-consed
  Int(IntWidth, Signed), Float(FloatWidth), Bool, Char, Str, Unit,
  Ref(Box<Ty>, Mutbl), Array(Box<Ty>, ConstLen), Slice(Box<Ty>),
  Tuple(Vec<Ty>), Adt(DefId, Vec<Ty>), Param(u32), Fn(Vec<Ty>, Box<Ty>), Error,
}
// LIR (lyra-lir)
struct LirFn { def: DefId, mono_args: Vec<Ty>, blocks: Vec<Block>, regs: u32 }
struct Block { id: BlockId, insts: Vec<Inst>, term: Terminator }
enum Inst { Bin{op,dst,a,b}, Load{dst,addr}, Store{addr,val}, Call{dst,callee,args}, Phi{dst,incoming}, /* … */ }
  • Ownership: AST nodes in per-parse arenas (freed when parse value is evicted); Ty is hash-consed (interned) so equality is pointer/id equality and fingerprinting is cheap + canonical. Mutation: all immutable after construction (queries return fresh values). Concurrency: immutable ⇒ freely shareable across threads (Arc). Persistence: AST/HIR/Ty/LIR are query values → serialized into the cache (ADR-15). Serialization: canonical order; Ty serialized structurally (not by intern id, which is per-process). Compatibility: any layout change bumps cache version.

11.5 Codegen + artifact types

struct Cgu { name: CguName, members: Vec<(DefId, Vec<Ty>)> }   // members sorted (determinism)
struct CguName([u8;32])                                        // content-address (§8.7)
struct Artifact { name: CguName, bytes: Vec<u8>, kind: Backend }   // bytecode|C-text
enum Backend { Bytecode, C99 }
struct Symbol Name(String)                                     // from lyra-mangle, deterministic
  • Ownership: artifacts owned by the cache (content-addressed; identical bytes dedup). Mutation: immutable. Concurrency: produced by parallel codegen queries, then sorted by CguName before link/emit (Principle 11). Persistence: artifact bytes stored content-addressed; reused verbatim across builds when CGU unchanged (the incremental codegen win). Serialization: raw bytes + a sidecar (kind, member list). Compatibility: artifact format = LBC/LIR/mangle specs; version-gated.

11.6 Diagnostics + error types

struct Diagnostic { code: DiagCode, severity: Severity, span: AbsSpan, msg: String, notes: Vec<Note> }
enum Severity { Error, Warning, Note }
struct DiagBuf { items: Vec<Diagnostic> }      // sorted by (file, lo, code) before emit (INV-11)
enum CompileError { Cycle(Vec<QueryKey>), CacheCorrupt(QueryKey), VersionSkew{got,want}, Io(IoError) }
  • Ownership: diagnostics are query outputs (e.g. typeck_body returns (TypedBody, Vec<Diagnostic>)), so they participate in fingerprints (under --deny-warnings they affect artifact gating). Mutation: append-only within a query, sorted at the sink. Concurrency: merged from parallel queries then sorted. Persistence: cached with their producing query. Serialization: deterministic; spans serialized as RelSpan, resolved to AbsSpan only for display. Compatibility: DiagCodes are stable identifiers (a deprecation policy applies, §Compatibility).

struct Stage { name: &'static str, compiler: PathBuf, kind: StageKind }   // stage0/1/2

  • Ownership/lifecycle: orchestrators own subprocess handles + temp dirs; results are values logged to BLUEPRINT_LOG/CI. Persistence: fixpoint/diff results are CI artifacts, not cache state. Compatibility: EditScript format is the fuzzer↔replayer contract.

12. Phase-by-Phase Implementation Plan

Thirteen phases. Each ends in a runnable/verifiable artifact with explicit acceptance criteria. Ordering: front end (cold) → incremental engine → backends → self-hosting → fixpoint → interaction → conformance/fuzz/perf. Self-hosting deliberately comes after incrementality so the self-hosted compiler inherits the incremental engine and the fixpoint can be tested with the cache warm (the novel core, §24).

13. Phase 1 — Lexer, Spans, Interner (front-end foundations)

13.1 Objectives

Build lyra-span, lyra-intern, lyra-lexer. Establish relative spans (INV-6) and thread-stable interning (INV-13) before anything else — they are load-bearing for incrementality. Constraint introduced: every downstream span is item-relative; no absolute offsets persist.

13.2 Detailed Implementation Steps

Applies ADR-5 (relative spans), ADR-6 (path-hash IDs), INV-6 (span/ID stability), INV-13 (interner thread-stability), P15/ADR-4 (BLAKE3 path hashing).

  • lyra-span: FileId table (sorted by path), RelSpan{anchor,lo,hi} (the ADR-5 item-anchored model that makes INV-6 hold), AbsSpan resolver (relspan + anchor_offset + file_base), 64 MiB file-size guard (reject → diagnostic), source-map for line/col on demand.
  • lyra-intern: sharded string interner → Symbol; canonical-assignment so concurrent inserts of equal strings produce one id deterministically (INV-13); ItemPath builder + path_hash (BLAKE3 of segment symbols' strings, not ids — ids are per-process; ADR-4/ADR-6).
  • lyra-lexer: byte cursor over UTF-8; token kinds per §8.2 lexical rules; trivia (whitespace/comments) attached to following token; error tokens for unterminated string/block-comment/invalid char (never panic); nested block comments.
  • Observability hooks: intern.id_count, lex.tokens, lex.error_tokens. Test harness: token-stream snapshot tests; concurrent-intern stress (permute insertion order across N threads, assert identical Symbol table).

13.3 Deliverable

lex(FileId) -> TokenStream as a pure fn (not yet a query); cargo test -p lyra-lexer green; a lyra-lexer CLI dumps tokens with rel-spans.

13.4 Acceptance Criteria

  • Lexer throughput ≥ 30 MB/s (bench). Interner: 1M concurrent inserts across 8 threads → identical id assignment in 100/100 permutations (INV-13). All malformed lexes produce error tokens, zero panics (fuzz-smoke 1 min).

13.5 Conformance Fixtures

conformance/programs/lex_*.lyra (idents, numeric suffixes, strings/escapes, nested comments, unicode); golden token dumps. malformed/lex_unterminated_*.lyra → expected error tokens. Replay fixture: same file lexed under 1/4/8 threads → identical.

13.6 Pitfalls

  • Absolute spans creeping in → spurious invalidation later (INV-6). Detect: grep for AbsSpan in persisted types (lint).
  • Interner nondeterminism under threads → Symbol id depends on race → fingerprint drift (INV-13). Manifestation: flaky fixpoint. Debug: dump sorted Symbol table, diff across runs.
  • UTF-8 boundary bugs (slicing mid-codepoint) → panic/garbage spans. Guard: byte cursor only advances on codepoint boundaries.
  • Trivia attachment ambiguity (leading vs trailing) → unstable AST shape hash. Fix one rule (leading-attached) and document it.

13.7 Performance Concerns

Cache locality: token stream as struct-of-arrays (kind[], span[]) beats array-of-structs for the parser's sequential scan. Allocation: arena-allocate trivia; avoid per-token String (intern or store byte ranges). No syscalls in the hot loop (file mmap'd once).

13.8 Edge Cases

Empty file; file with only comments; BOM; CRLF vs LF (normalize for line/col, not for bytes — bytes are the fingerprint input); 64 MiB+1 file (rejected); a token straddling a 4 GiB offset (impossible — file size capped); invalid UTF-8 byte (error token, continue).

13.9 Failure Analysis

Breaks: a non-canonical interner → every later determinism check fails. Detection: INV-13 stress test in CI. Blast radius: total (fingerprints poisoned). Containment: the determinism gate blocks merge. Recovery: fix canonical assignment. Forensic artifact: sorted Symbol dumps from two runs. Postmortem: was a HashMap used in interning? (Principle 1 / ADR-17.)

13.10 Operational Notes

Metrics dumped via --metrics. No deployment impact (library). Migration: changing path_hash algo bumps cache version (INV-9) — document in CHANGELOG. Tracing: lex events behind a sampling flag (off in release hot path).

14. Phase 2 — Error-Recovering Parser → AST

14.1 Objectives

Build lyra-ast + lyra-parser: recursive-descent for items/statements, Pratt for expressions (ADR-7), panic-mode recovery so one error doesn't abort the file (Principle 12). Constraint: AST shape hash must be stable under reformatting (enables early cutoff at parse, §8.8).

14.2 Detailed Implementation Steps

Applies ADR-7 (recursive-descent + Pratt + panic-mode recovery), P13 (error-recovering / reuse boundaries), Principle 12 (errors are values), INV-6 (item-anchored spans), B2 (Dragon ch. 4 recovery).

  • lyra-ast: arena + AstId; node families per §8.3; ErrorNode variants (Principle 12); attach RelSpan (anchor = enclosing item's AstId, INV-6).
  • lyra-parser (ADR-7):
    • Pratt expression parser with the precedence ladder from §8.2 (Assign→LogicOr→…→Unary→Postfix).
    • Recovery: on unexpected token, emit diagnostic, skip to a synchronization set (;, }, item keywords), insert ErrorNode, continue.
    • Item-level reuse boundary: parser records each item's byte range so the incremental layer can reuse unchanged items (feeds INV-6).
  • AST shape fingerprint: hash node kinds + structure, excluding trivia and absolute offsets, so reformat-only edits early-cutoff.
  • Observability: parse.errors, parse.recovered_items, parse.shape_fp.

14.3 Deliverable

parse(FileId) -> AstModule (pure fn); a lir-disasm-adjacent AST dumper; round-trip: parse → pretty-print → parse yields identical shape fp.

14.4 Acceptance Criteria

Parser ≥ 8 MB/s. Recovery: a file with K scattered syntax errors yields K diagnostics + a usable AST for the rest (no cascade > 2 spurious diags per real error). Reformat invariance: whitespace-only reformat → identical shape fp (100% on fixtures).

14.5 Conformance Fixtures

programs/parse_*.lyra (every grammar production once); golden-ir/parse_*.ast shape dumps; malformed/parse_*.lyra (unclosed delimiters, missing ;, bad type) → expected diagnostics + recovered AST; reformat pairs (x.lyra vs x.reformatted.lyra) → equal shape fp.

14.6 Pitfalls

  • Cascading errors (one missing brace → 50 diagnostics). Root cause: bad sync set. Debug: count diags per injected error. Fix: synchronize to item boundaries.
  • Shape fp includes trivia → reformat invalidates everything. Detect: reformat fixture fails. Fix: exclude trivia from the hash.
  • Pratt precedence bug → wrong AST, silent. Detect: golden AST diff.
  • Infinite recovery loop (sync set never advances). Guard: recovery must consume ≥1 token or break.
  • Span anchor wrong (anchored to file not item) → INV-6 violation downstream.

14.7 Performance Concerns

Recursive descent stack depth on deeply nested expr → bounded by a parse-depth limit (clean error, not stack overflow). Avoid per-node heap alloc (arena). Branch prediction: order match arms by token frequency. Tail latency dominated by pathological nesting → depth cap.

14.8 Edge Cases

Empty file → empty module (valid). Trailing tokens after last item → recovered error. Deeply nested (((…))) → depth-limit error. Unicode identifiers. A single unterminated block comment swallowing the file → one error token, empty module, one diagnostic. Mismatched generics < without >.

14.9 Failure Analysis

Breaks: shape-fp instability → no early cutoff → every edit recompiles the file's downstream (perf regression, INV-2 still holds but §4 SLO fails). Detection: hit-rate bench drops. Blast radius: perf only (not correctness) unless anchors wrong (then correctness via INV-6). Recovery: fix hash inputs. Forensic: dump shape fp before/after reformat.

14.10 Operational Notes

Diagnostics flow to the sorted sink (INV-11). No runtime deployment. Changing AST node layout bumps cache version. Tracing: parse spans sampled.

15. Phase 3 — Name Resolution + HIR (resolve queries)

15.1 Objectives

Build lyra-hir + lyra-resolve: module_scope(DefId) and resolve(DefId) queries; assign stable DefIds (path-hash based, INV-6); desugar AST → HIR (§8.4). First queries that depend on each other, exercising the DAG. Constraint: DefId stable across edits that don't change item paths.

15.2 Detailed Implementation Steps

  • DefId minting: (crate, path_hash(ItemPath), disambig) where disambig disambiguates same-path siblings (e.g. two impl methods) in a deterministic, edit-stable order (source order of items with identical paths, recorded by item range not absolute offset).
  • module_scope(mod): build name→DefId map (a BTreeMap, not HashMap — INV-1/ADR-17), depend on parse + child module_scopes; fingerprint = sorted map.
  • resolve(item): resolve every Path to a DefId (or error), resolve method calls to trait impls, lower AST→HIR with sugar removed (§8.4: for/?/while/method calls). Depends on parse(file) + module_scope(enclosing) + module_scopes along the path.
  • Cycle handling: import cycles / mutually recursive modules resolved via fixpoint over module_scope with the cycle detector (INV-7) bounding pathological self-reference.
  • Observability: resolve.unresolved, resolve.def_count, edge counts (INV-5 feed).

15.3 Deliverable

module_scope + resolve as real queries in lyra-db (Phase 4 engine may be stubbed to a simple memo for now; full red-green lands Phase 4). HIR dumper. DefId stability test under edits.

15.4 Acceptance Criteria

Resolution correct on all conformance programs (golden HIR). DefId stability: insert a blank line / a comment / a new unrelated item → existing items' DefIds unchanged (INV-6), 100% on edit fixtures. Unresolved names → sorted diagnostics, no panic.

15.5 Conformance Fixtures

programs/resolve_*.lyra (nested modules, use aliases, shadowing, methods, generic bounds); golden-ir/resolve_*.hir; malformed/resolve_unknown_*.lyra → expected unresolved diagnostics; edits/resolve_stable_*.editscript → assert DefId map unchanged for untouched items.

15.6 Pitfalls

  • DefId churn on edit (sequential disambig renumbers on insert) → mass invalidation or silent miscompile (INV-6). Detect: edit-stability fixture. Fix: disambig keyed by stable item identity, not position.
  • HashMap in scope → nondeterministic resolution order → fingerprint drift. Detect: determinism harness. Fix: BTreeMap.
  • Import-cycle hang → no termination. Guard: cycle detector + fixpoint iteration cap.
  • Glob/use shadowing precedence wrong → silent wrong resolve. Detect: golden HIR.
  • Desugar non-determinism (e.g. fresh temp names from a counter shared across threads) → drift. Fix: deterministic temp naming (per-body counter).

15.7 Performance Concerns

module_scope recomputation cost ∝ items in module; early cutoff: adding a private item to a big module changes its scope fp → re-resolves dependents, but unrelated modules stay green. Avoid recomputing the whole crate's scopes for one edit (per-module granularity). Allocation: HIR in arenas.

15.8 Edge Cases

Self-referential module (mod a { use crate::a; }); duplicate definitions (same path) → error + deterministic disambig; use of a non-existent path; generic param shadowing a type name; an item moved between modules (DefId should change — path changed — verify dependents update).

15.9 Failure Analysis

Breaks: DefId instability is the most dangerous bug — a reused cache entry keyed by a DefId that now means a different item = silent miscompile (INV-6). Detection: edit-replay fuzzer (Phase 11) + incremental==clean (Phase 12). Blast radius: correctness, possibly undetected until diff harness. Containment: diff gate. Recovery: fix DefId minting; invalidate cache. Forensic: DefId→ItemPath map snapshots across the edit.

15.10 Operational Notes

Resolution diagnostics → sorted sink. DefId algorithm is cache-version-gated. Tracing: per-query resolve events. Migration: moving items across modules is a source change that legitimately invalidates dependents — documented as expected.

16. Phase 4 — Query Engine Core: Revisions, Red-Green, Fingerprints

16.1 Objectives

Build lyra-db in full (in-memory first; on-disk in Phase 6): Revision counter (INV-10), input vs derived queries (Principle 3), automatic dependency edge capture (INV-5), red-green verification with early cutoff (Principle 6), cycle detection (INV-7). This is the incrementality core. Constraint: every derived value obtained only via fetch (Principle 13).

16.2 Detailed Implementation Steps

  • Revision allocator: monotonic u64; set_input bumps it; assert strictly increasing (INV-10).
  • Query node store: slot map keyed by QueryKey; node holds value, fp, changed_at, verified_at, deps, durability (§11.2).
  • Edge capture: a thread-local "current query" stack; inside fetch, push callee, record caller→callee edge on return (INV-5). Re-entrancy on the same key while Running ⇒ cycle (INV-7) → return CompileError::Cycle.
  • Red-green (maybe_changed_after(key, since)): if verified_at >= current_rev return cached verdict; else for each dep recurse; if any dep changed after since, recompute, compute new fp; early cutoff: if new fp == old fp, set changed_at unchanged (dependents not dirtied), else update changed_at = current_rev; always set verified_at = current_rev.
  • Wire the Phase-1/2/3 functions as queries: lex, parse, module_scope, resolve (the type_of etc. land in Phase 5).
  • Observability: redgreen.green, redgreen.red, redgreen.early_cutoff, query.recompute_ns{query}, red-green audit log (audit.rs): per node, the verify decision + reason.

16.3 Deliverable

A working in-memory incremental engine: set an input, demand a root, edit the input, re-demand → only affected queries recompute. cache-inspect tool dumps the DAG + red-green decisions. --verify-incremental mode recomputes green nodes and asserts fp equality (INV-4).

16.4 Acceptance Criteria

On a synthetic 1000-node DAG, editing one leaf re-verifies its transitive dependents only; early cutoff demonstrably stops propagation when an intermediate fp is unchanged (audit log shows it). --verify-incremental passes (INV-4) on all conformance programs. Hit-rate ≥ 98% on a 1-line edit to a fixture crate.

16.5 Conformance Fixtures

programs/incr_*.lyra + edits/incr_*.editscript with expected red-green audit logs (golden-diag/incr_*.audit): e.g. incr_body_edit (early cutoff at type_of), incr_sig_edit (dependents go red), incr_comment_edit (early cutoff at parse). Cycle fixture programs/cycle_type.lyra → expected CompileError::Cycle.

16.6 Pitfalls

  • Missing dependency edge (a query reads an input without fetch) → stale reuse → miscompile (INV-5). Detect: --verify-incremental mismatch; debug build's untracked_read assertion. Recovery: route the read through fetch.
  • Over-broad fingerprint (fp includes irrelevant data) → no early cutoff → perf failure. Detect: hit-rate bench. Fix: narrow fp inputs.
  • Under-broad fingerprint (fp omits relevant data) → false early cutoff → miscompile (INV-4). Detect: --verify-incremental. Fix: include the missing field.
  • Revision regression / reuse → red-green miscomputes (INV-10). Detect: assertion.
  • Cycle not detected → stack overflow/hang (INV-7). Guard: on-stack key set + depth cap.
  • Double-compute under concurrency (two threads compute same key) → wasted work + potential nondeterminism. Fix: Running state blocks duplicate demands.

16.7 Performance Concerns

maybe_changed_after recursion cost — memoize the per-revision verdict (verified_at) to avoid re-walking. Edge storage: Vec<DepEdge> per node, dedup on insert. Lock contention on the node map → use a sharded concurrent map; Running nodes use a condvar so waiters don't spin. Fingerprint cost: BLAKE3 is fast but visiting a huge value is O(size) — cache the fp on the node (don't rehash to read).

16.8 Edge Cases

Demand of an absent input → error (inputs must be set first). Self-edge (query depends on itself) → cycle. A query whose value is huge (whole-crate map) → fp cost; mitigate by sub-querying. Concurrent set_input during a build → disallowed (inputs set before demand; enforced). Edit that changes nothing (same bytes) → no revision bump (or bumped but everything early-cuts at lex).

16.9 Failure Analysis

Breaks: a fingerprint bug (under-broad) is a silent miscompile that only --verify-incremental or the Phase-12 diff harness catches. Detection: those two harnesses, run in CI. Blast radius: correctness, latent. Containment: diff gate blocks merge. Recovery: fix fp; invalidate cache; add a regression fixture. Forensic: red-green audit log + the --verify-incremental mismatch (which node, old vs new fp). Postmortem: which field was missing from the Fingerprintable impl?

16.10 Operational Notes

The red-green audit log is the primary debugging surface for all incremental issues (runbook incremental-mismatch.md). Metrics: hit-rate, recompute-ns histogram, early-cutoff count. --verify-incremental is a CI mode (slow; not default). Changing the fingerprint algorithm bumps cache version (INV-9).

17. Phase 5 — Type Checker (bidirectional + HM unification)

17.1 Objectives

Build lyra-types: Ty (hash-consed), unification, bidirectional checking (P10), HM generalization (P11), type_of(DefId) and typeck_body(DefId) queries, monomorphization-instance collection (mono_instances). Constraint: type_of fp = canonical type only (so a body edit that preserves a signature early-cuts at type_of, §8.8).

17.2 Detailed Implementation Steps

  • Ty interning (hash-consing): structural types share one canonical instance; equality = id; fingerprint = structural canonical bytes (§11.4).
  • Unification: union-find over type variables; occurs-check (prevents infinite types → ties to INV-7); deterministic variable allocation (per-body counter, not global, for reproducibility).
  • Bidirectional: check(expr, expected) vs infer(expr) -> Ty; rules from P10; literals defaulted deterministically (e.g. unsuffixed int → i64).
  • Queries: type_of(def) = signature type (cheap, stable); typeck_body(def) = full body check → (TypedBody, Vec<Diagnostic>); depends on resolve(def) + type_of of referenced defs (builds the cyclic-capable DAG; type cycles like struct S{x:S} detected via INV-7).
  • mono_instances(): from typed roots, collect (DefId, concrete generic args) set (a BTreeSet — deterministic), the worklist for monomorphization in Phase 6.
  • Observability: typeck.errors, typeck.infer_vars, typeck.unify_steps, mono.instances.

17.3 Deliverable

Full type checking as queries; typeck_body produces typed HIR + sorted diagnostics; mono_instances enumerates monomorphizations. lyrac check <dir> runs front end + typeck and reports diagnostics (no codegen).

17.4 Acceptance Criteria

Type checking correct on all conformance programs (golden typed-HIR + golden diagnostics). Body-edit early-cutoff: editing a fn body that preserves its signature → type_of fp unchanged (audit log), only typeck_body of that fn recomputes (§8.8). Recursive/ill-formed types → errors, no hang (INV-7).

17.5 Conformance Fixtures

programs/types_*.lyra (inference, generics, traits/bounds, pattern exhaustiveness, integer defaulting); golden-ir/types_*.thir; golden-diag/types_*.diag (type errors); malformed/types_recursive_struct.lyra, types_mismatch.lyra; edits/types_body_preserve_sig.editscript → assert type_of early-cut.

17.6 Pitfalls

  • Global type-var counter → ids depend on query execution order → fp drift (INV-1). Fix: per-body counter.
  • type_of fp too broad (includes body) → signature-preserving body edits recompile dependents (perf). Fix: type_of = signature only; body lives in typeck_body.
  • Unsound unification (skipped occurs-check) → infinite loop on recursive types. Guard: occurs-check + cycle detector.
  • Non-deterministic literal defaulting → drift. Fix: fixed defaulting rule.
  • Trait-impl selection ambiguity → silent wrong impl. Detect: golden THIR; error on overlap.
  • Exhaustiveness check missing a case → runtime UB later. Detect: exhaustiveness fixtures.

17.7 Performance Concerns

Unification is near-linear with union-find + path compression; hash-consing makes Ty equality O(1). type_of is small + cached → cheap dependency for many bodies. mono_instances over a large program is O(instances); dedup via BTreeSet. Avoid re-checking a body when only a referenced body changed but its signature didn't (that's exactly the type_of vs typeck_body split).

17.8 Edge Cases

Mutually recursive functions (each type_of depends on the other's signature — terminates because signatures are explicit); generic instantiated with itself (Vec<Vec<T>>); zero-variant enum (uninhabited); unit struct; integer overflow in a const expr (const-eval error); a trait method not implemented (error); inference of an empty match (uninhabited scrutinee).

17.9 Failure Analysis

Breaks: an unsound type_of fp (omits a field that affects monomorphization) → wrong mono set reused → miscompile (INV-4). Detection: --verify-incremental / diff harness. Blast radius: correctness, latent. Recovery: fix fp; regression fixture. Forensic: type_of value dump + audit log. A unification hang manifests as a build that never finishes → cycle detector should pre-empt; if not, a watchdog logs the in-flight query.

17.10 Operational Notes

Diagnostics → sorted sink. Ty layout + defaulting rules are cache-version-gated. Metrics: typeck timing, infer-var counts. lyrac check is the fast inner-loop command (no codegen) → its latency is a sub-SLO of the 1-line warm rebuild.

18. Phase 6 — Durable On-Disk Cache + GC + Durability Tiers

18.1 Objectives

Persist the query graph: serialize QueryNodes + fingerprints + values + artifacts to .lyra-cache/ (crash-only, INV-8), key the cache by profile + cache-version (INV-9, INV-12), implement durability tiers (ADR-14) and GC (bounded size, §4). This is what makes incrementality survive process restarts — and the substrate the self-hosted compiler will reuse. Constraint: a torn write never yields a valid-looking wrong value (Principle 7).

18.2 Detailed Implementation Steps

  • Cache layout (docs/spec/cache.md): .lyra-cache/<profile>/<cache-version>/{manifest, nodes/, values/, artifacts/}. manifest = current Revision + index. values/, artifacts/ are content-addressed files (name = BLAKE3 of contents) → automatic dedup + portability.
  • Serialization (ADR-15): versioned, length-prefixed, deterministic binary; floats via canonical formatter (INV-14); maps sorted. Each entry carries a checksum (INV-8).
  • Atomic write: write to tmp/, fsync, rename into place (atomic on POSIX); manifest updated last (the commit point). Crash before manifest swap ⇒ old state intact.
  • Durability tiers: High (inputs source_text — fsync'd), Low (expensive derived values — fsync'd batched), Volatile (cheap derived — may be lost, recomputed). Tiers bound flush latency (§4 ≤ 300 ms).
  • Cache open: verify cache-version (INV-9) + profile (INV-12); on mismatch → wipe (full invalidation). Verify checksums lazily on load; corrupt entry → drop (cold recompute of that node).
  • GC (gc.rs): mark reachable from current roots; keep reachable + one prior revision (rollback safety); sweep unreferenced content-addressed files; amortized/incremental so pause ≤ 200 ms (§4).
  • Observability: cache.load_hits, cache.checksum_fail, cache.version_mismatch, cache.bytes, gc.reclaimed, gc.pause_ms.

18.3 Deliverable

lyrac build persists + reloads the cache across process restarts: cold build, edit one file, restart process, warm build recompiles only affected queries. lyrac gc reclaims space. cache-inspect reads the on-disk DAG.

18.4 Acceptance Criteria

Cross-restart incrementality: 1-line edit after restart → ≥ 98% hit-rate, warm rebuild ≤ 600 ms p95 (§4). Crash-safety: kill -9 during flush 1000× → cache always opens to a consistent prior revision, never wrong output (INV-8). Cache size ≤ 3× artifacts after GC. Version skew: a cache from a different cache-version is wiped, not trusted (INV-9).

18.5 Conformance Fixtures

programs/persist_*.lyra + restart harness; crash-injection fixtures (cache_fuzz kills at random write points → expect consistent reopen); cache/version_skew/ (cache tagged old version → expect wipe); GC fixtures (build, churn N revisions, assert size bound). Replay: cold vs warm-after-restart artifacts byte-identical (feeds INV-2).

18.6 Pitfalls

  • Non-atomic manifest update → torn cache, valid-looking wrong state (INV-8). Detect: crash-injection harness. Fix: rename manifest last; fsync ordering.
  • Serializing process-local ids (Symbol/Ty intern ids) → cache not portable / wrong on reload. Fix: serialize structurally (strings/paths), re-intern on load (§11.1/11.4).
  • Float drift across platforms in serialized constants → cross-machine cache divergence (INV-14). Fix: canonical formatter, golden fixtures.
  • GC deletes a still-referenced artifact → next build misses, recomputes (perf) or errors. Detect: post-GC build correctness. Fix: precise reachability from roots.
  • fsync omitted → power-loss corruption. Detect: power-fail simulation.
  • Timestamp/order leak (file mtime, dir-listing order) into a value → nondeterminism. Fix: never read mtime; sort dir listings.

18.7 Performance Concerns

fsync is the dominant cost → batch volatile/low-durability writes, fsync once at commit; inputs fsync'd individually for safety. Content-addressing dedups artifacts (the self-hosted compiler's many small CGUs share). mmap values for lazy load (don't deserialize the whole cache on open — §4 startup ≤ 40 ms). GC I/O amortized to avoid build-time spikes. Write amplification bounded by durability tiers.

18.8 Edge Cases

First build (no cache) → cold path. Cache dir on a read-only FS → graceful error, build in-memory only. Disk full mid-write → abort write, keep prior state, diagnostic. Two lyrac processes sharing a cache dir → file lock (single-writer); second waits or errors. Corrupt manifest → treat whole cache as cold. Clock set backwards on host → irrelevant (no timestamps in cache).

18.9 Failure Analysis

Breaks: a torn write producing a valid-checksum wrong value would be a silent miscompile — prevented by atomic rename (the value is content-addressed, so its name = hash of contents; a torn file's name won't match its content hash → dropped). Detection: checksum + content-address mismatch. Blast radius: contained to one node (cold recompute). Recovery: automatic (drop + recompute) or lyrac --clean. Forensic: cache.checksum_fail events + the dropped entry list. Runbook: cache-corruption.md.

18.10 Operational Notes

Cache is per-profile, per-version dir → safe to rm -rf (worst case: a cold rebuild). Metrics: cache bytes, hit-rate, GC pause/reclaimed, checksum failures. Deployment: CI caches .lyra-cache/<profile>/<version> between runs keyed by version (auto-invalidates on compiler upgrade — INV-9). Migration: cache-version bump = automatic full invalidation, documented in CHANGELOG. Rollback: keeping one prior revision allows reverting an edit cheaply.

19. Phase 7 — LIR (SSA) Lowering + Optimization Passes

19.1 Objectives

Build lyra-lir + lyra-opt: lower typed/monomorphized HIR → SSA LIR (§8.5), verify SSA, run deterministic passes (const-fold, DCE, mem2reg, single-pass inline; ADR-10). lir(DefId, mono_args) query. Constraint: passes must be deterministic and confluent enough that the post-opt LIR fp is stable (enables codegen early-cutoff + fixpoint). Deferred: GVN/LICM/loop opts (PhaseDeferred §19 stretch — only if time permits, behind a flag, never if they threaten determinism).

19.2 Detailed Implementation Steps

  • Lowering: HIR → LIR per (DefId, mono_args); generics resolved to concrete Ty (monomorphized); match → switch/condbr decision trees; aggregates via alloca+gep+load/store; ?/for already desugared in HIR.
  • SSA construction: dominance frontiers (P3) for φ placement; or build-with-allocas then mem2reg. Verifier (§8.5): dominance, type well-formedness, terminator presence, φ arity.
  • Passes (passmgr.rs, fixed order, deterministic): (1) mem2reg (promote allocas to SSA), (2) constfold (sparse conditional const prop, P4 — uses canonical float fmt, INV-14), (3) dce (mark-sweep on SSA use lists), (4) inline (single-pass, size-threshold heuristic, deterministic ordering by DefId). Iterate to a fixpoint with an iteration cap.
  • lir query: depends on typeck_body + type_of of callees (for inlining/monomorphization); fp = canonical LIR text (block/inst order canonicalized; SSA value numbering deterministic).
  • Observability: lir.insts, opt.folded, opt.dce_removed, opt.inlined, lir.verify_fail.

19.3 Deliverable

lir(def, args) produces verified, optimized SSA; lir-disasm prints canonical LIR for diffing. The +0 const-fold from §8.8 demonstrably yields identical LIR pre/post a no-op edit.

19.4 Acceptance Criteria

Golden LIR matches on all conformance programs (per profile). Verifier rejects all malformed-SSA fixtures. Determinism: lir fp identical across 100 runs + cross-machine (INV-1). Opt confluence: a semantically-neutral source edit (e.g. +0) → identical post-opt LIR fp → codegen early-cutoff (§8.8). Pass iteration terminates within cap on all fixtures.

19.5 Conformance Fixtures

programs/lir_*.lyra (control flow, loops, aggregates, generics→mono); golden-ir/lir_*.lir (post-opt, per profile debug/release); malformed/lir_bad_ssa_* (hand-crafted via internal API → verifier must reject); edits/lir_neutral_edit.editscript → identical LIR fp; pass-ordering fixtures (assert fixed order).

19.6 Pitfalls

  • Non-deterministic SSA numbering / block order (from HashMap traversal of CFG) → fp drift (INV-1). Fix: traverse CFG in deterministic (RPO) order; number values in that order.
  • Inlining order dependence → different LIR depending on which callee inlined first → drift. Fix: order candidates by DefId.
  • Const-fold float using libc → cross-platform drift (INV-14). Fix: canonical formatter + soft-float for compile-time eval.
  • mem2reg miscompiles address-taken locals → wrong code. Detect: golden LIR + runtime conformance.
  • Pass non-confluence (order changes result unpredictably) → fixpoint risk. Fix: fixed order + idempotent passes.
  • Verifier too weak → bad SSA reaches codegen → crash/UB. Detect: malformed-SSA fixtures.

19.7 Performance Concerns

Dominance computation O(N·α) with Lengauer-Tarjan-lite; φ minimization avoids dead φ. DCE on SSA is cheap (use lists). Inlining can blow up code size → size threshold + budget (bounded, Principle 8). lir is the most expensive per-def query → its fp must be stable so codegen early-cuts (perf). Arena-allocate LIR; avoid per-inst heap alloc.

19.8 Edge Cases

Empty function (just ret unit); infinite loop (loop {} → no ret, valid, terminator br to self); irreducible control flow (Lyra grammar can't produce it — structured control flow only, so reducible by construction — documented); huge match (decision-tree balancing, bounded); recursive function (inlining must not recurse infinitely — depth/budget cap); integer divide-by-zero const → compile-time error.

19.9 Failure Analysis

Breaks: non-deterministic LIR fp → codegen never early-cuts and the fixpoint flakes (INV-1/INV-3). Detection: determinism harness + fixpoint gate. Blast radius: fixpoint + perf. Recovery: pin the nondeterministic traversal; re-sort. Forensic: lir-disasm diff of two runs (first divergent block/inst). A verifier miss manifests as a VM crash or cc error downstream → add the rejected pattern to malformed fixtures. Runbook: nondeterminism-bisect.md (bisect passes).

19.10 Operational Notes

LIR + pass set + canonical formatting are cache-version-gated (a pass change → cache invalidation, fixpoint re-verify). Metrics: pass effect counters, LIR size. Pass order is documented + golden-tested (changing it is a deliberate, versioned event). Deferred opts behind --opt-experimental (never on in bootstrap profile).

20. Phase 8 — Codegen Backends (Bytecode VM + C99) + Deterministic Mangling

20.1 Objectives

Build lyra-codegen-bc, lyra-codegen-c, lyra-vm, lyra-mangle: LIR → LBC bytecode (§8.6) and LIR → C99 text; a register VM to run bytecode; deterministic symbol mangling + content-addressed CGU naming (§8.7, INV-15). codegen(Cgu) + cgu_partition() + link_plan() queries. Constraint: artifact bytes 100% deterministic (the fixpoint substrate); CGU name = hash of contents. Deferred: direct ELF/Mach-O emission + own linker + incremental linking (PhaseDeferred §20); native path emits C and shells out to cc.

20.2 Detailed Implementation Steps

  • lyra-mangle: deterministic name grammar from (ItemPath, mono_args) (e.g. _L<crate>_<path>_<arg-hashes>); injective + stable (INV-15); golden-tested.
  • cgu_partition(): group monomorphized defs into CGUs (e.g. by source module, fixed count target); CGU name = blake3(sorted(member lir fingerprints) ++ profile ++ target) (§8.7) → content-addressed.
  • codegen(cgu): for each member, lower LIR → target:
    • Bytecode (emit.rs): register allocation (linear-scan over SSA, deterministic), opcode emission, per-module constant pool (sorted/dedup'd), reloc-free function refs (§8.6); fp = artifact bytes.
    • C99 (emit_c.rs): emit portable C (LIR SSA → C with explicit temporaries; structured control flow → C if/while/goto-free where possible); a fixed runtime.h; deterministic identifier names from mangling. Hand to system cc (outside our determinism boundary — fixpoint checked at C-text level).
  • lyra-vm: register machine, threaded dispatch (ADR-12), value.rs (tagged values / unboxed ints+floats), loader.rs (resolve const-pool fn refs at load), hostshim.rs (I/O, alloc — the only host syscalls). Runs lyrac1 in Phase 9.
  • link_plan(): collect artifacts, sort by CguName, produce a load order (bytecode) or a cc invocation (C).
  • Observability: codegen.cgus, codegen.bytes, codegen.reused (content-address hits), vm.dispatch_ops, mangle.symbols.

20.3 Deliverable

lyrac build --emit bytecode produces runnable .lbc modules; lyra-vm run prog.lbc executes them. lyrac build --emit c produces .c + invokes cc → native exe. Conformance programs run correctly on both backends.

20.4 Acceptance Criteria

Programs produce identical results on VM vs native (differential, §Testing). Artifact bytes 100% deterministic across runs/machines (INV-1). Content-address reuse: an unchanged CGU after an unrelated edit → artifact reused verbatim (audit shows codegen.reused), the codegen incremental win. Mangling injective on all fixtures (INV-15). VM ≥ 150 M ops/s; runs conformance suite.

20.5 Conformance Fixtures

golden-bc/*.lbc (byte-exact, per profile/target); golden-c/*.c (byte-exact C text); programs/run_*.lyra with expected stdout (executed on VM + native, compared); malformed—N/A (codegen input is verified LIR); edits/codegen_reuse.editscript → assert unchanged CGUs reused; mangle_* golden symbol maps.

20.6 Pitfalls

  • HashMap iteration in emit (const pool, symbol order) → byte drift (INV-1). Fix: sorted const pool, sorted CGU members.
  • C backend relying on cc for float formatting → drift; emit float literals via canonical formatter as hex-float (0x1.0p+0) for exactness (INV-14).
  • Mangling collision (two defs → same symbol) → link error / wrong call (INV-15). Detect: collision check.
  • Register allocator nondeterminism (interval ordering from a hash) → byte drift. Fix: order intervals by SSA value number.
  • CGU partition instability (a comment edit reshuffles CGUs) → mass artifact churn (perf). Fix: partition by stable keys (module/DefId), content-address names.
  • VM dispatch UB (out-of-range register/opcode) → crash on malformed module; loader must validate (defense for §Threat Model loaded-module integrity).

20.7 Performance Concerns

VM dispatch: threaded/computed-goto dispatch, hot opcodes first; unboxed int/float to avoid tag checks on arithmetic. Codegen parallel across CGUs (pure queries) then sorted (Principle 11). Content-addressing dedups identical CGUs (big win for the self-hosted compiler's many small functions). C backend: emit to a buffer, write once (avoid per-line syscalls). Constant-pool dedup reduces module size.

20.8 Edge Cases

A CGU with one tiny function; a function larger than the register window (spill to memory, deterministic); recursion (VM stack growth, bounded with a guard); a program with no main (library — emit modules, no entry); integer overflow at runtime (wrapping vs trap — Lyra spec defines wrapping for u*, trap-in-debug for i*); cc not found (clear error, native path unavailable); huge constant pool (bounded).

20.9 Failure Analysis

Breaks: byte-nondeterministic codegen breaks the fixpoint (INV-3) — the single most important thing this phase must get right. Detection: determinism harness + fixpoint. Blast radius: fixpoint + incremental==clean. Recovery: find the unsorted/hashed emission, sort it. Forensic: lbc-disasm diff (first divergent byte → which CGU → which inst). A mangling collision manifests as a link/load failure or a wrong call → add to mangle fixtures. Runbook: fixpoint-failed.md.

20.10 Operational Notes

LBC format + mangling + C runtime.h are versioned specs; changes bump cache version + require fixpoint re-verify. Metrics: artifact bytes, reuse rate, VM ops/s. The VM is also shipped (runs lyrac1), so its determinism + safety matter operationally. Deferred native object/linker tracked as PhaseDeferred("FINAL_BLUEPRINT §20").

21. Phase 9 — The Compiler Written in Lyra (compiler-src/)

21.1 Objectives

Write the compiler in Lyra (compiler-src/): a second implementation of the full pipeline (lex, parse, resolve, types, lir, opt, codegen) plus the query engine (db.lyra) — because the self-hosted compiler must itself be incremental (the union property). This is the largest single phase. Constraint: Lyra must be expressive enough (Principle 14) — if a needed feature is missing, extend Lyra + stage0 minimally, then proceed.

21.2 Detailed Implementation Steps

Applies Principle 14 (Lyra stays minimal-but-sufficient), Principle 10 (don't widen the trust base), Principle 1/11/13/17 (the determinism discipline must be re-expressed in Lyra), P5/P7 (the incremental model re-implemented in db.lyra), INV-1 (cross-impl byte parity).

  • Translate each Rust crate's algorithm to idiomatic Lyra (lex.lyra, parse.lyra, resolve.lyra, types.lyra, lir.lyra, opt.lyra, codegen.lyra, db.lyra, main.lyra). The algorithms are identical to Phases 1–8 (Principle 13: one source of truth per fact, mirrored); only the host language differs.
  • db.lyra: re-implement the query engine (revisions, red-green, fingerprints, on-disk cache) in Lyra. This is the crux of "incremental AND self-hosting": the self-hosted compiler is itself incremental.
  • Drive Lyra-feature gaps: as translation hits a missing feature (e.g. a specific generic pattern), add the minimum to the Lyra spec + stage0 (Rust) front/back end; re-run conformance. Track each addition in CHANGELOG (it bumps cache version).
  • Determinism discipline carries over: db.lyra uses sorted maps; codegen emits sorted; no clock. (Lyra std provides BTreeMap-equivalent + canonical float fmt as library functions.)
  • Cross-check: every compiler-src/*.lyra has a golden-output parity test vs its Rust counterpart on the conformance corpus (Phase 13).

21.3 Deliverable

compiler-src/ compiles (via stage0 lyrac0) to a bytecode (and C) compiler lyrac1 that passes the same conformance suite as lyrac0. lyra-vm run lyrac1.lbc -- check examples/hello.lyra works.

21.4 Acceptance Criteria

lyrac1 (compiled by stage0) produces byte-identical artifacts to lyrac0 on the entire conformance corpus (the cross-implementation determinism check — both implementations agree to the byte). lyrac1 is itself incremental (warm rebuild of a test crate hits ≥ 98%, run under the VM). All Lyra-feature additions are minimal + documented.

21.5 Conformance Fixtures

The full conformance/ corpus, run through both lyrac0 and lyrac1, byte-compared (golden-bc, golden-c, golden-ir, golden-diag must match for both). programs/selfcompile_smoke.lyra (a small program the Lyra compiler compiles). Feature-addition fixtures for each new Lyra construct.

21.6 Pitfalls

  • Two implementations diverge (Rust vs Lyra emit different bytes) → fixpoint impossible. Root cause: a determinism rule applied in one but not the other (e.g. Lyra codegen forgot to sort). Detect: cross-impl byte compare. Fix: enforce the same canonicalization in both; share golden fixtures.
  • Lyra feature creep (adding niceties) widens stage0 + trust base (Principle 10/14). Guard: each addition justified by "needed to self-host."
  • db.lyra subtly different red-green from lyra-db → different cache behavior → different (but still correct?) output — only safe if outputs match. Detect: run incremental==clean on lyrac1 too (Phase 12).
  • Float/int semantics mismatch between stage0's host arithmetic and Lyra's defined semantics → const-eval divergence. Fix: Lyra const-eval uses soft-float/defined-wrapping identical to stage0.
  • Bootstrapping a missing feature incorrectly (stage0 supports it but generates wrong code) → lyrac1 miscompiles. Detect: conformance on the new feature before using it in compiler-src/.

21.7 Performance Concerns

lyrac1 runs on the VM → ~3–5× slower than lyrac0 (native Rust). Acceptable for bootstrap; the cold self-build under the VM must still finish in minutes. Incremental engine keeps lyrac1's rebuilds fast despite VM overhead. C backend path: lyrac1 emitted as C → native → near-lyrac0 speed (used for the production self-hosted compiler).

21.8 Edge Cases

A Lyra construct the Rust compiler supports but compiler-src never uses (dead feature — keep minimal); recursion depth in lyrac1 running under the VM (VM stack guard); db.lyra cache format must match lyra-db's spec exactly (so a cache is portable between stage0 and stage1 builds — relevant to Phase 12); a feature added late that invalidates earlier golden fixtures (regenerate + review).

21.9 Failure Analysis

Breaks: a Rust↔Lyra divergence blocks the fixpoint (Phase 11) entirely. Detection: the cross-impl byte-compare in this phase catches it before fixpoint. Blast radius: the whole self-hosting effort. Containment: don't proceed to Phase 11 until cross-impl parity is 100%. Forensic: lbc-disasm diff of lyrac0 vs lyrac1 output on a single program. Postmortem: which canonicalization was missing in one impl?

21.10 Operational Notes

compiler-src/ is the source-of-record for the self-hosted compiler. Lyra spec changes (features) are versioned + bump cache version. Metrics: lyrac1 build time under VM, cross-impl parity rate. This phase has no external deps; it's pure translation + minimal language extension.

22. Phase 10 — Bootstrap Pipeline: stage0 → stage1 → stage2

22.1 Objectives

Build lyra-fixpoint stage orchestration: stage0 (Rust lyrac0) compiles compiler-src/ → stage1 (lyrac1); stage1 recompiles compiler-src/ → stage2 (lyrac2). Establish the build graph + reproducible seed (scripts/build-seed.sh, docs/seed-provenance.md). Constraint: the pipeline is fully scripted + reproducible; seed provenance recorded (Principle 10).

22.2 Detailed Implementation Steps

Applies Principle 10 (minimize + record the seed), ADR-1 (Rust stage0), ADR-19 (pinned Cargo toolchain), ADR-28 (SOURCE_DATE_EPOCH, no embedded timestamps), B9 (reproducible-build discipline), R4/R5/R6 (real bootstrap pipelines).

  • stages.rs: define Stage{stage0:HostRust, stage1:SelfBytecode|SelfNative, stage2}; each stage is a lyrac invocation with a clean cache (cold) in this phase (warm-cache fixpoint is Phase 12).
  • stage0 build: cargo build --release of the Rust crates, pinned toolchain (rust-toolchain.toml, ADR-19); record compiler version + git hash + toolchain in seed-provenance.md (Principle 10).
  • stage1: lyrac0 build compiler-src/ --emit {bytecode,c} → lyrac1 (bytecode module or C→native via cc).
  • stage2: run lyrac1 (on VM, or native if C-emitted) to compile compiler-src/ again → lyrac2.
  • verify_bytes.rs: sha256 the stage1 + stage2 artifacts (prepare for the fixpoint gate, Phase 11).
  • build-seed.sh: reproducibly build stage0 (SOURCE_DATE_EPOCH, locale C, no embedded paths) so the seed itself is reproducible + auditable.
  • Observability: bootstrap.stage_ms{n}, bootstrap.stage_bytes{n}, seed hash logged.

22.3 Deliverable

make bootstrap runs stage0→1→2 end-to-end and emits all three compilers + their hashes. docs/seed-provenance.md records exactly how stage0 was built.

22.4 Acceptance Criteria

Pipeline completes; stage1 and stage2 both compile the full conformance corpus correctly. stage0 build is reproducible (two independent builds of stage0 from the same source → identical lyrac0 binary, given a reproducible Rust toolchain — or documented if Rust's own repro has gaps). All three stages produce identical conformance artifacts (cross-stage parity). (The byte-identity of stage1 vs stage2 is gated in Phase 11.)

22.5 Conformance Fixtures

programs/bootstrap_smoke.lyra; the full corpus run through stage1 and stage2 (must match golden-*); seed-reproducibility fixture (build stage0 twice → compare). Stage-graph fixture asserting the dependency order (stage2 depends on stage1 depends on stage0).

22.6 Pitfalls

  • Non-reproducible stage0 (embedded build paths/timestamps in the Rust binary) → can't reason about the seed. Fix: reproducible-build flags; document residual nondeterminism.
  • stage1 ≠ stage2 due to a determinism bug surfacing only when the compiler compiles itself (larger, more code paths than the test corpus). Detect: this is exactly the Phase 11 gate.
  • VM resource limits running stage1 (stack/heap for a self-compile) → OOM/overflow. Fix: VM limits sized for self-compile; or use the C-emitted native lyrac1.
  • Seed provenance drift (someone rebuilds stage0 with a different toolchain) → trust gap. Guard: pin toolchain; record hash; CI builds the seed.
  • cc version variance in the C-native path → different native lyrac1 bytes. Mitigation: fixpoint at C-text level; pin cc in CI/Docker.

22.7 Performance Concerns

stage1 (under VM) is the slow stage; the C-native lyrac1 is faster for stage2. Cold self-build dominates bootstrap time → the §4 ≤ 90 s target applies to the native path; VM path is allowed to be slower (minutes). Bootstrap runs cold here (warm-cache bootstrap is Phase 12), so it's the worst-case timing baseline.

22.8 Edge Cases

stage1 fails to compile compiler-src/ (a bug in lyrac0's codegen of the compiler) → stops before stage2; bisect via conformance. compiler-src/ uses a feature stage0 generates wrong code for → caught here. Toolchain unavailable in CI → pinned via Docker. Partial bootstrap (stage1 built, stage2 interrupted) → re-runnable (idempotent stages, clean caches).

22.9 Failure Analysis

Breaks: stage1 producing a lyrac1 that miscompiles compiler-src/ → stage2 is wrong or fails. Detection: stage2 conformance failure / fixpoint mismatch (Phase 11). Blast radius: the entire self-hosting chain. Containment: gate at stage2 conformance before fixpoint. Recovery: fix the bug in Rust stage0 (root of trust), rebuild. Forensic: compare stage1's and stage2's conformance outputs; lbc-disasm the divergent program. Runbook: fixpoint-failed.md.

22.10 Operational Notes

make bootstrap is the canonical build of the self-hosted compiler. Seed provenance is a security artifact (SECURITY.md, threat model). Metrics: per-stage time/bytes. Deployment: the shipped lyrac is the C-native stage2 (or stage1) binary. Toolchain + cc pinned in Docker for reproducible CI bootstrap.

23. Phase 11 — Fixpoint Gate + Diverse Double-Compilation (DDC)

23.1 Objectives

Enforce the self-hosting acceptance gate: bytes(stage1) == bytes(stage2) (INV-3), and implement DDC (P1/P2) as the standing defense against a trusting-trust backdoor in stage0. Constraint: the fixpoint is a hard, binary CI gate; DDC runs at least in release CI.

23.2 Detailed Implementation Steps

  • Fixpoint gate (verify_bytes.rs): sha256(lyrac1) == sha256(lyrac2); on the bytecode path this is exact; on the C-native path compare the emitted C text (our output) byte-for-byte (the cc/linker are outside our control), and additionally compare native binaries when cc is reproducible (pinned).
  • DDC procedure (ddc.rs, Wheeler P2):
    1. Build stage1 with stage0 (our Rust seed) → lyrac1_A.
    2. Build stage1' with an independent host compiler lyrac0' (a second, differently-built stage0 — e.g. different Rust version, or a re-derived seed) → lyrac1_B.
    3. Compile compiler-src/ with lyrac1_A → out_A, and with lyrac1_B → out_B.
    4. DDC check: out_A == out_B (byte-identical). If equal, the compiler's output is independent of the seed's identity → no trusting-trust backdoor survived (subject to DDC's assumptions).
  • Iterate fixpoint to stage3 if needed (stage2→stage3) to confirm a stable fixed point (some compilers reach it at stage2, some need stage3; document which).
  • Observability: fixpoint.byte_delta, fixpoint.stages_to_fix, ddc.equal, seed hashes for A and B.

23.3 Deliverable

make fixpoint runs the bootstrap + the byte-identity gate; make ddc runs diverse double-compilation. Both are CI gates (fixpoint.yml). Output: PASS/FAIL with hashes + a diff on failure.

23.4 Acceptance Criteria

bytes(stage1) == bytes(stage2) byte-identical (INV-3), 100%, reproducibly. DDC: out_A == out_B (independent seed → identical compiler output). Fixed point reached by stage2 (or documented stage3). Failure produces an actionable diff (lbc-disasm).

23.5 Conformance Fixtures

programs/fixpoint_corpus/ (a representative subset compiled by stage1, stage2, and DDC's stage1' — all byte-compared); the whole compiler-src/ self-compile is itself the primary fixture. DDC fixture: two seed builds (lyrac0, lyrac0') with recorded provenance.

23.6 Pitfalls

  • Fixpoint passes but DDC fails → output depends on the seed = a possible trusting-trust signature (or a benign seed-version-dependent codegen). Investigate: diff out_A/out_B; determine if it's a real backdoor or a determinism gap tied to host version.
  • No truly independent second host → DDC is weak (Wheeler requires real diversity). Mitigation: use a genuinely different Rust toolchain version / re-derived seed; document the diversity achieved.
  • C-native fixpoint masked by cc nondeterminism → can't byte-compare binaries. Fix: compare C text (deterministic, ours) + pin cc for binary compare.
  • Fixpoint never reached (stageN ≠ stageN+1 forever) → a real determinism bug. Detect: gate. Bisect with nondeterminism-bisect.md.
  • Flaky fixpoint (passes sometimes) → a nondeterminism source (thread race, HashMap). Zero tolerance (§4); must be root-caused, never retried-away.

23.7 Performance Concerns

Fixpoint = at least two full self-compiles (stage1, stage2) + DDC adds two more → 4× cold-build cost. Run on the native (C) path for speed; DDC in release/nightly CI, fixpoint on every PR. Warm-cache bootstrap (Phase 12) reduces this for incremental fixpoint re-checks.

23.8 Edge Cases

stage2 compiles but differs from stage1 in debug info only (excluded from fingerprint per §8.6) → must still be byte-identical in the fingerprinted sections; ensure debug sections are either deterministic or excluded from the gate. A compiler change that legitimately changes output → stage1 (old compiler output) vs stage2 (new) differ on the first bootstrap after the change; the fixpoint is checked stage2-vs-stage3 in that case (document the "two-build" rule after a compiler change).

23.9 Failure Analysis

Breaks: a fixpoint failure means non-determinism (INV-1) somewhere or a real stage0↔stage1 codegen disagreement. Detection: the gate. Blast radius: blocks all merges (correctly — the compiler isn't trustworthy). Containment: CI gate. Recovery: bisect passes (nondeterminism-bisect.md), find the non-deterministic byte via lbc-disasm diff, sort/seed it. Forensic: stage1/stage2 disassembly diff; DDC out_A/out_B diff. Postmortem (DDC fail): is this a backdoor (escalate per SECURITY.md) or a host-version codegen gap?

23.10 Operational Notes

Fixpoint is the headline gate (fixpoint.yml, every PR). DDC nightly (cost). Seed provenance + DDC results are security artifacts. Metrics: byte-delta (0 expected), stages-to-fix, DDC-equal. Runbook fixpoint-failed.md is the most important operational doc. A compiler-output-changing PR requires regenerating golden fixtures + a stage2-vs-stage3 fixpoint (documented procedure).

24. Phase 12 — The Interaction: Incremental == Clean + Warm-Cache Fixpoint (the novel core)

24.1 Objectives

Prove the two hard properties co-exist. Build lyra-diff: (a) the central differential harness incremental == clean (INV-2); (b) the warm-cache fixpoint — a bootstrap stage compiled with a warm incremental cache produces byte-identical output to a cold build, so the fixpoint (INV-3) holds with caching on; (c) fingerprint portability/versioning — fingerprints stable across compiler versions for cache reuse, or explicitly invalidated (INV-9). This phase is why project 309 ≠ (242 ∪ 243): it confronts the interaction.

24.2 Detailed Implementation Steps

  • replay.rs + editgen.rs: apply an EditScript to a source tree, run a warm build (cache from before the edit), capture artifacts (out_w); separately, run a cold build of the post-edit source (out_c); compare.rs byte-compares per-artifact (INV-2).
  • Warm-cache fixpoint: build lyrac1 cold → lyrac1_cold; build lyrac1 again with a warm cache (after a trivial no-op or a real edit + revert) → lyrac1_warm; assert bytes(lyrac1_cold) == bytes(lyrac1_warm) and that both still satisfy stage1==stage2. This proves caching doesn't perturb the fixpoint.
  • Self-hosting under incremental: edit one module of compiler-src/ (e.g. opt.lyra), warm-rebuild lyrac (only affected queries recompute, ≥98% hit-rate), then re-run the fixpoint on the rebuilt compiler. Demonstrates "the compiler compiling itself incrementally, then verifying the fixpoint."
  • Fingerprint portability: decide, per query, whether its fp is stable across compiler versions. Stable fps (e.g. lex) enable cache reuse after a compiler upgrade; unstable ones force invalidation. Encode the policy in the cache-version header (INV-9): bumping the version invalidates everything; a minor "fp-compatible" change can retain compatible fps. Document which queries are version-stable.
  • Observability: diff.artifact_mismatch, warmfix.byte_delta, incr_selfhost.hit_rate, fp.version_stable{query}.

24.3 Deliverable

make diff runs the incremental==clean suite (cold vs warm per fixture). make warmfix runs the warm-cache fixpoint. make incr-selfhost edits compiler-src/, warm-rebuilds, re-verifies the fixpoint. All three are CI gates (diff.yml).

24.4 Acceptance Criteria

  • INV-2: every artifact byte-identical between cold and warm builds, 100%, across the full edit-fixture suite (and under the edit-sequence fuzzer, Phase 13).
  • Warm-cache fixpoint: bytes(lyrac1_cold) == bytes(lyrac1_warm) 100%; stage1==stage2 still holds with the cache warm (INV-3 ∧ caching).
  • Incremental self-host: editing one compiler-src/ module → ≥98% query hit-rate on the compiler's own rebuild, fixpoint re-verified PASS, warm rebuild ≤ §4 SLO.
  • Fp portability: documented + enforced version policy; a compiler upgrade either reuses version-stable fps or fully invalidates (never silently reuses an incompatible fp — INV-9).

24.5 Conformance Fixtures

edits/diff_*.editscript (body edit, sig edit, add item, delete item, reformat, move item between modules) each with cold==warm assertion; warmfix_noop.editscript + warmfix_revert.editscript; incr_selfhost_opt.editscript (edit opt.lyra) → expected hit-rate + fixpoint PASS; fp_version/ (old-version cache + new compiler → expected wipe or compatible-reuse per policy).

24.6 Pitfalls

  • Warm build differs from cold (INV-2 fail) — the canonical "works clean, breaks incremental" miscompile. Root causes: missing dependency edge (INV-5), under-broad fingerprint (false early cutoff, INV-4), DefId instability (INV-6), or nondeterministic recompute (INV-1). Detect: this harness. Debug: red-green audit log → find the query reused as green that should have recomputed → inspect its edges/fp. This is the single most important debugging loop in the project (runbook incremental-mismatch.md).
  • Warm-cache fixpoint fails but cold fixpoint passes → the cache perturbs codegen (e.g. a reused artifact embeds stale data). Detect: warmfix gate. Fix: ensure cached artifacts are pure functions of inputs (content-addressed) — a cached CGU must be reproducible from its members alone.
  • Fp reused across incompatible compiler versions → silent miscompile after upgrade (cache poisoning, §Threat Model). Guard: cache-version header; conservative invalidation.
  • Incremental self-host hit-rate low (editing the compiler recompiles too much) → CGU partition or fp granularity too coarse. Fix: finer CGUs / narrower fps.
  • Edit that moves an item between modules legitimately changes its DefId (path changed) → dependents must recompute; if they're wrongly reused → miscompile (INV-6). Detect: the move fixture.

24.7 Performance Concerns

The diff harness doubles build cost (cold + warm) → run a representative subset per PR, full suite nightly. Warm-cache fixpoint adds a warm self-compile. The whole point of the phase is that warm builds are fast (§4 SLO) and correct — measure both: hit-rate (perf) and byte-equality (correctness) together. Fuzzed edit sequences (Phase 13) stress this at scale.

24.8 Edge Cases

No-op edit (same bytes) → warm == cold trivially, hit-rate ~100%; revert (edit then undo) → cache returns to the prior fingerprints (tests fp stability under round-trip); editing then editing-back-differently; deleting the only definition in a CGU (CGU disappears — link plan updates); upgrading the compiler with a warm cache from the old compiler (INV-9 wipe-or-reuse); a flaky third-party cc making the native warm/cold compare differ (compare C text, not binary).

24.9 Failure Analysis

Breaks: an incremental==clean failure is a silent miscompile that only appears after specific edit sequences — the worst bug class, and the entire reason this harness exists. Detection: diff.yml + edit-sequence fuzzing. Blast radius: correctness of every incremental build; would ship wrong binaries. Containment: the gate blocks merge; warm values are treated as poisoned until root-caused. Recovery: identify the violated invariant (INV-2 decomposes to INV-1/4/5/6), fix it, add the failing EditScript as a permanent regression fixture. Forensic: red-green audit log + the mismatching artifact's lbc-disasm diff (cold vs warm). Postmortem: which invariant, which query, which fingerprint/edge?

24.10 Operational Notes

incremental==clean (diff.yml) and warm-cache fixpoint (warmfix) are CI gates alongside the cold fixpoint — together they certify the union property. Metrics: artifact-mismatch count (must be 0), warm/cold byte-delta (0), incremental self-host hit-rate. The fp-version policy is documented in docs/spec/cache.md; a compiler release states whether it's "cache-compatible" with the prior version. This phase's harnesses are the operational guardrail for every future compiler change.

25. Phase 13 — Conformance Suite, Fuzzing, Performance, Hardening

25.1 Objectives

Build the standing quality infrastructure: the golden conformance runner (lyra-conformance), fuzzers (lyra-fuzz: source + edit-sequence + cache), performance benchmarks + tuning (benchmarks/), and resource hardening (bounded recompute, cache-blowup defense). Land deferred-or-stretch items behind flags. Constraint: every invariant (INV-1..15) has at least one automated test; perf hits §4 targets.

25.2 Detailed Implementation Steps

  • lyra-conformance runner: execute every programs/*.lyra through lyrac0 and lyrac1, compare to golden-ir/bc/c/diag; regenerate goldens via --bless; per-profile (debug/release) + per-target (bytecode/C) matrices.
  • Fuzzers (cargo-fuzz):
    • source_fuzz: random/grammar-guided Lyra source → assert no panic, sorted diagnostics, deterministic output (run twice, compare).
    • edit_sequence_fuzz: random EditScript sequences applied to a base program → assert incremental==clean after each edit (INV-2) and DefId stability (INV-6). This is the fuzzer that finds incremental miscompiles.
    • cache_fuzz: crash-inject during cache writes → assert consistent reopen (INV-8); corrupt random cache bytes → assert detection + cold-recompute, never wrong output.
  • Performance: cold_build, warm_1line, hit_rate, vm_dispatch benches → tune to §4; flamegraph the cold build (front end vs codegen split), profile the warm path (verify vs recompute), allocator analysis (arena sizing), lock analysis on the node map.
  • Hardening (Principle 8 / §Threat Model): recompute budget per query (watchdog), cache-size cap with GC pressure, parse/typeck depth caps, loaded-module validation in the VM.
  • Stretch (flagged, only if determinism-safe): GVN (§19 deferred), dynamic dispatch, closures, persistent daemon, LSP.

25.3 Deliverable

make conformance (golden, both compilers, all matrices), make fuzz-smoke (short fuzz run per target), make bench (perf vs §4 thresholds, fails on regression). CI runs all on every PR (fuzz-smoke) + nightly (long fuzz, full bench).

25.4 Acceptance Criteria

100% conformance pass on both lyrac0 and lyrac1 across all profile/target matrices. Fuzz-smoke (5 min/target) finds zero panics / zero incremental==clean violations / zero wrong-output-on-corruption. Perf meets §4: cold ≤ 90 s, warm 1-line ≤ 600 ms p95, hit-rate ≥ 98%, VM ≥ 150 M ops/s, peak RSS within ceilings. Every INV-1..15 has a passing automated check.

25.5 Conformance Fixtures

The full conformance/ tree (programs, golden-ir/bc/c/diag, malformed) — this phase makes it exhaustive (every grammar production, every type rule, every opt, every backend). Fuzz corpora fuzz/corpus/{source,edits,cache} seeded from conformance programs. Regression fixtures: every bug found by fuzzing is minimized + added permanently.

25.6 Pitfalls

  • Goldens blessed without review → bake in a bug as "expected." Guard: --bless diffs reviewed; goldens are code-reviewed artifacts.
  • Edit-sequence fuzzer too shallow (only trivial edits) → misses the span/DefId-instability miscompiles it exists to find. Fix: bias toward inserts/deletes/moves near item boundaries.
  • Flaky benchmark (machine noise) → false perf-regression alarms. Fix: relative thresholds + multiple runs + dedicated runner.
  • Fuzzer finds nondeterminism but not its source → hard to triage. Mitigation: fuzzer dumps the divergent fp + audit log on failure.
  • Cache-blowup DoS (a program that creates millions of monomorphizations) → cache explodes. Guard: instance cap + cache-size cap (§Threat Model).
  • Stretch feature breaks determinism → don't merge it. Gate behind a flag, never in bootstrap profile.

25.7 Performance Concerns

This phase is the performance work. Key levers: query parallelism (cold build), early-cutoff coverage (warm build), content-address reuse (codegen), VM dispatch (self-host speed). Flamegraph workflow: cold build → expect front end + LIR dominant; warm build → expect verify (red-green walk) dominant, recompute minimal. Allocator: arena per AST/HIR/LIR; reuse arenas across queries where safe. Lock contention: shard the node map; Running-state condvars over spinning.

25.8 Edge Cases

Pathological source (deeply nested, huge match, millions of items) → depth/size caps trip with clean errors (Principle 8). Adversarial edit sequence designed to maximize recompute → bounded by true-dependent count. Cache at the size cap during a build → GC pressure, build still completes. Fuzzer-generated valid-but-weird program that round-trips differently → INV-2 must still hold or it's a bug. A bench on a NUMA machine → thread pinning; document variance.

25.9 Failure Analysis

Breaks: a perf regression (warm rebuild slows past SLO) is caught by bench (CI). A correctness regression is caught by conformance/fuzz/diff. Blast radius: depends — perf = developer-experience; correctness = ship-blocker. Containment: CI gates. Recovery: regression fixtures + bisection. Forensic: flamegraphs (perf), audit log + fuzzer reproducer (correctness). Postmortem: every fuzz/diff find becomes a permanent fixture + an invariant-coverage check.

25.10 Operational Notes

Conformance + fuzz-smoke + bench are PR gates; long fuzz + full bench + DDC are nightly. Metrics dashboard tracks hit-rate, cold/warm times, VM ops/s, fuzz coverage, fixpoint byte-delta over time. Deferred/stretch items remain PhaseDeferred("FINAL_BLUEPRINT §25") and never enter the bootstrap profile. This phase's infrastructure is the permanent quality contract for all future Lyra/compiler changes.

  • Migration strategy. Cache-format/spec changes are versioned (INV-9) → automatic full invalidation on upgrade (a cold build), documented in CHANGELOG. No in-place cache migration (deliberately simple — derived data is cheap to rebuild).
  • Compatibility strategy. See next section.

Compatibility & Versioning

  • "Wire" compatibility = artifact + cache formats. LBC bytecode, LIR, C runtime.h, mangling, and cache layout are versioned specs (docs/spec/*). A bytecode module declares its format version; the VM loads only known versions.
  • Storage (cache) compatibility. The cache carries a cache-version (INV-9). Same version ⇒ reusable. Different version ⇒ full invalidation (never partial silent reuse). A "cache-compatible" minor release may retain version-stable fingerprints (documented per query, §24); otherwise the version bumps.
  • Schema evolution. Query value layouts evolve by bumping the cache version (cheap — derived data rebuilds). No backward-compatible deserialization of old cache values is attempted (derived data is disposable).
  • API stability. The normative APIs are the §11 core types and the §8.7 query set; within a major version, query names/signatures + the language spec are stable. Adding a query is backward-compatible; changing a fingerprint algorithm bumps the cache version.
  • Language stability. The Lyra spec (docs/spec/lyra-lang.md) is versioned. compiler-src/ only uses stable features. New features are additive within a major version.
  • Migration guarantees. None needed for the cache (rebuilt). Source migrations (if a language feature changes) are documented; the self-hosted compiler-src/ is migrated in lockstep.
  • Deprecation policy. DiagCodes and language features are deprecated for one major version (warning) before removal. Cache/artifact formats are not "deprecated" — they're versioned and invalidated.
  • Semantic versioning. MAJOR.MINOR.PATCH. MAJOR = breaking language/artifact-format change. MINOR = additive (new feature, new query) — may bump cache version (full invalidation) without being "breaking" for users. PATCH = bug fix; bumps cache version only if it changes output (it usually does — correctness fixes change bytes), documented.
  • Rolling upgrade guarantees. Upgrading lyrac is safe at any time: the version-keyed cache auto-invalidates; the first post-upgrade build is cold; output is correct by the fixpoint + diff gates of the new version.

Build & Release Engineering

  • Reproducible builds. stage0 built with pinned rust-toolchain.toml, SOURCE_DATE_EPOCH, locale C, no embedded paths (ADR-28). The self-hosted lyrac (stage2) is reproducible by construction (the fixpoint is the reproducibility proof). Two independent builds → identical binaries (verified in CI).
  • Artifact signing. Release lyrac binaries + the archived seed are signed; signatures + hashes published. Seed binaries retained for DDC reproducibility.
  • SBOM generation. stage0's (tiny) dependency tree → SBOM (CycloneDX) per release; cargo-deny gates licenses/advisories (ADR-21).
  • Release channels. nightly (every main commit, full gates incl. DDC), beta, stable (tagged, semver). Each release states cache-compatibility with the prior.
  • CI/CD topology. ci.yml (build+unit+clippy+conformance) → diff.yml (incremental==clean) → fixpoint.yml (stage1==stage2) → determinism.yml (repeat+cross-runner) → fuzz-smoke.yml → release.yml (signed binary + SBOM + seed-provenance). Fixpoint + diff + determinism are required checks; DDC + long fuzz are nightly.
  • Version stamping. The compiler embeds its semver + git hash + cache-version — but not in fingerprinted artifact sections (version goes in a debug section excluded from the fixpoint, §8.6/§23), so stamping doesn't break byte-identity.
  • Binary provenance. seed-provenance.md records how stage0 was built (toolchain, host, hash); release provenance (SLSA-style) records the bootstrap chain stage0→1→2 + the fixpoint hash.
  • Dependency auditing / supply-chain verification. cargo-deny + cargo-audit in CI; vendored deps; DDC is the ultimate supply-chain verification for the compiler itself (defeats a poisoned seed).
  • Release automation. Tag → CI runs full gates incl. DDC → on green, builds + signs the stage2 binary, generates SBOM, attaches seed provenance + fixpoint hash, publishes.

Performance Engineering

  • Benchmarking strategy. benchmarks/ (criterion-style): cold_build (full self-build), warm_1line (the §4 SLO), hit_rate, vm_dispatch. Relative thresholds vs a recorded baseline; CI fails on regression beyond noise margin. Dedicated, quiesced runner.
  • Profiling methodology. Cold build: perf record + flamegraph → expect lexer/parser + typeck + LIR dominant; codegen parallelized. Warm build: profile the verify path (red-green walk) vs recompute — a healthy warm build is mostly verify (cheap) + tiny recompute.
  • Flamegraph workflow. cargo flamegraph on cold + warm builds; compare across releases; a warm-build flamegraph dominated by recompute (not verify) signals an early-cutoff regression.
  • Tracing methodology. Per-query spans → a build's query tree with timings; the slowest queries + the red/green ratio guide tuning.
  • Allocator analysis. Arenas per AST/HIR/LIR (bump allocation, freed wholesale on eviction); track peak RSS vs §4 ceilings; avoid per-node heap allocs; intern/hash-cons to dedup (Symbol, Ty).
  • Lock analysis. The query-node map is the hot shared structure → shard it; Running-state condvars (no spin); measure contention with parking_lot stats / lock-wait tracing.
  • Cache analysis. Token stream + LIR as struct-of-arrays for sequential scans; content-addressed artifact reuse to skip codegen entirely; fingerprint reads from the node (don't rehash).
  • Syscall analysis. mmap source + cache (no per-read syscalls); batch cache writes (fsync once at commit per durability tier); single write for C-backend output.
  • Throughput targets. §4: lexer ≥ 30 MB/s (M9), parser ≥ 8 MB/s (M10), VM ≥ 150 M ops/s (M11), cold build ≤ 90 s (M1).
  • Tail-latency analysis. Warm-rebuild p95 ≤ 600 ms (M2) — tail driven by the largest single CGU recompute + cache flush; keep CGUs bounded; flush async where durability allows.
  • Memory profiling. Heaptrack/valgrind-massif on cold build; track interner + arena + cache-value memory; peak RSS ≤ 2.0 GB cold (M5) / 1.4 GB warm (M6).

Scalability Analysis

  • Bottlenecks. Cold build: front end + LIR (CPU-bound, parallelizable across files/CGUs). Warm build: the red-green verify walk (proportional to the DAG, but cheap per node) + the single changed query's recompute. Cache: serialization + fsync at flush.
  • Scaling ceilings. Query parallelism scales to ~16 threads before the codegen queue + node-map contention saturate (§4). Beyond that, returns diminish (Amdahl: the serial sort/link/flush phases).
  • Horizontal scaling. Not in v1 (single process, local cache). A distributed/shared cache (Bazel-style content-addressed remote cache, ADR-13/§18 deferred) is the horizontal lever — content-addressing makes artifacts shareable across machines/CI, the natural extension.
  • Vertical scaling. More cores → faster cold builds (parallel queries) + faster fixpoint/DDC (parallel self-compiles). More RAM → larger in-memory cache (fewer disk loads). Faster NVMe → faster flush/load.
  • Sharding / partitioning. The cache is sharded by content-address prefix (fd budget, §4); CGUs partition the program for parallel + reusable codegen. Query DAG naturally partitions by DefId/module for parallelism.
  • Replication pressure. N/A (single local cache); a future remote cache would face standard CAS replication concerns (links to 118/storage projects).
  • Coordination overhead. The only coordination is the node-map lock + Running-state blocking; minimized by sharding + condvars. The serial phases (canonical sort, link plan, manifest commit) are the coordination tax.
  • Network fanout. None in v1. A remote cache would add fetch/store RTT — mitigated by content-addressing (fetch-by-hash, no negotiation).
  • Scheduler saturation. Work-stealing pool; the codegen queue is bounded (backpressure, Principle 8) so a burst of CGUs doesn't OOM.
  • Storage growth. Cache bounded by GC (reachable + 1 prior revision, §4); content-addressing dedups; growth is sublinear in build count.
  • Metadata scaling. The DAG/manifest grows with program size (number of queries ≈ items × pipeline stages); for a ~60k-LOC self-compile this is ~10^5–10^6 nodes — fits comfortably in RAM; the manifest index is the metadata to keep compact (mmap, lazy load).

Mental Models & First Principles

The compressed intuitions an expert holds about an incremental, self-hosting compiler. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — Incremental compilation is a memoized pure function; the cache is a claim that recompute would agree. Every query is a deterministic function of its inputs; a green (reused) node asserts "recomputing me yields the same value." Predicts: correctness reduces to two obligations — the function is pure (no hidden inputs) and every input it read is recorded as a dependency. Bug without it: treating the cache as a side store you "update", introducing a path where the cached value and a fresh recompute disagree. Applied: Principle 1/2/3 (§6), §8.7 query DAG, Phase 4 (§16), MM cross-link to INV-4.
  • MM2 — A missing dependency edge is the canonical silent miscompile, not a perf bug. If a query reads something it didn't record, an edit to that something leaves the query wrongly green. Predicts: the failure is invisible until a specific edit sequence fires, and only a clean-vs-warm differential catches it — unit tests never will. Bug without it: "works clean, breaks incremental" miscompiles that ship. Applied: INV-5, Phase 4 edge capture (§16), Phase 12 incremental==clean (§24), §Failure Modes.
  • MM3 — Early cutoff is the difference between O(edit) and O(program). A query that recomputes to the same fingerprint must stop dirty-propagation there; without it a signature-preserving body edit re-runs the world. Predicts: the +0-then-const-folded edit (§8.8) re-emits zero artifacts iff cutoff fires at lir; a fingerprint that includes irrelevant data kills cutoff and the §4 N-dependents target. Bug without it: warm rebuilds scale with program size, not edit size. Applied: Principle 6 (§6), §8.8 worked example, §8.10 state table, Phase 4 (§16), C-model link below.
  • MM4 — Determinism is engineered, not inherited; a single unordered iteration poisons everything downstream of it. Parallelism, HashMap order, libc float formatting, timestamps, and thread-race interning are all latent nondeterminism. Predicts: one HashMap in a const-pool emit makes the fixpoint flake on a different machine, invisible on yours. Bug without it: a flaky bytes(stage1)==bytes(stage2) gate that gets "retried away" instead of root-caused. Applied: Principle 1/11/17 (§6), ADR-17/ADR-29, INV-1/INV-13/INV-14, Phase 8 (§20).
  • MM5 — Stable identity is a content property, not a position property. A DefId keyed by item-path hash survives a blank-line insert; one keyed by sequential position does not. Predicts: if IDs renumber on insert, either everything below an edit goes red (no incrementality) or — worse — a cache entry keyed by an ID that now denotes a different item is reused (miscompile). Bug without it: ID reuse → the most dangerous bug class in the system. Applied: ADR-5/ADR-6, INV-6, §8.4 DefId, Phase 3 (§15), Phase 12 move-item fixture (§24).
  • MM6 — Self-hosting is a determinism proof, and incrementality is a determinism risk; the project is the collision of the two. The fixpoint bytes(stage1)==bytes(stage2) can only hold if codegen is deterministic; a warm cache introduces a second way to produce those bytes that must agree with the cold way. Predicts: a warm-cache fixpoint can pass while a cold one fails (or vice-versa) iff a cached artifact embeds anything not a pure function of its members. Bug without it: certifying the fixpoint cold and assuming it holds warm. Applied: §1 (the union property), INV-2 ∧ INV-3, Phase 11 (§23), Phase 12 warm-cache fixpoint (§24).
  • MM7 — Content-addressing turns "is this artifact reusable?" into a hash comparison and makes reuse safe by construction. A CGU named by blake3(member fingerprints ++ profile ++ target) cannot be confused with a different CGU, and a torn write whose bytes don't hash to its name is self-detecting. Predicts: dedup is automatic (identical CGUs share one file) and a corrupt cache entry can never be silently trusted. Bug without it: a name collision serves the wrong artifact, or a torn write surfaces as a valid-looking value. Applied: §8.7 CGU naming, ADR-13, INV-8, Phase 6 (§18), Phase 8 (§20).
  • MM8 — Trusting-trust means the seed's identity, not its source, is the trust root — so you attack it by diversity, not by reading code. A backdoor can reproduce through self-hosting even when compiler-src/ is clean; reading the source proves nothing. Predicts: only compiling the compiler with two independent hosts and comparing outputs (DDC) can show the output is seed-identity-independent. Bug without it: believing "I audited the source, therefore the binary is clean." Applied: Principle 10, P1/P2, ADR-18, Phase 11 DDC (§23), §Threat Model.
  • MM9 — Inputs vs derived is a hard wall; the moment a derived query reads the clock/env/disk it stops being memoizable. Only source_text/file_list/cli_flags may be inputs; everything else is a pure function of them. Predicts: a derived query that reads wall-clock time can be green when it should be red (its hidden input changed) — red-green is unsound for it. Bug without it: non-reproducible builds and unsound caching from one stray I/O. Applied: Principle 3 (§6), §8.7 (input vs derived), Phase 4 (§16), ADR-28 (clock discipline).
  • MM10 — The cache is derived data: its correct recovery action is always "throw it away and recompute," never "repair it." Because every cached value is reconstructible from source, a version skew, a corrupt entry, or a torn write is recovered by dropping to cold — repair logic would be a new, untested code path that can itself miscompile. Predicts: the right response to any cache anomaly is invalidation, and "restore" is just a cold build. Bug without it: building cache-repair/migration machinery that introduces a wrong-value path the rebuild path can't. Applied: INV-8/INV-9, ADR-14, §Operational Readiness (backup/restore), Phase 6 (§18).

Comparative Architecture

lyrac is simultaneously an incremental engine and a self-hosting compiler; the comparison is therefore against the real systems that embody each half.   • rustc (R1) made the decision this design mirrors most closely: per-query red-green incrementality with content-addressed fingerprints, and a bootstrap that seeds from the prior release of itself. That wins for a mature, continuously-released production compiler where a prior trusted binary always exists — but it means rustc never confronts the "no prior self" seed problem this project deliberately takes on with a foreign Rust stage0 (ADR-1). rustc's incremental cache is versioned and fully invalidated across compiler versions for exactly the reason this design encodes in INV-9.
  • Go gc compiler (R5) chose to bootstrap from a prior Go (cmd/dist, since Go 1.5) and to put incrementality at the build-system (package) grain, not inside the compiler. That wins for fast whole-package builds with a simple mental model — the compiler stays a clean batch translator — and is why Go builds feel instant without an in-compiler query engine. This design instead needs intra-file, item-level reuse (the §4 1-line-edit SLO), so it pays for an in-compiler query DAG that Go declines.
  • OCaml native/bytecode (R6) made the checked-in boot image choice: a prebuilt bytecode compiler lives in boot/ and seeds the build, sharing OCaml's own runtime/value model. That wins when the host language is the same family as the source (the seed is "just an older us"), shortening the bootstrap — but it carries a checked-in-binary provenance burden this design avoids by recording seed provenance for a foreign host instead (ADR-1, §22).
  • GCC 3-stage bootstrap is the canonical determinism proof embodied in a build: stage1 (built by the system compiler) builds stage2, which builds stage3, and make compare requires stage2 == stage3 byte-for-byte. That wins as a codegen-correctness check that catches stage1 miscompiles — but, as Thompson (P1) showed and Wheeler (P2) formalized, an N-stage self-compare does not defeat a backdoor in the seed; only DDC does, which is why this design adds DDC on top of the byte-identity gate (§23).
  • Salsa (R2) generalized rustc's engine into a reusable framework: a demand-driven, red-green, durability-tiered query system decoupled from any compiler. That wins when you want incrementality for an arbitrary computation (an IDE, a build tool) and are willing to express it through Salsa's trait-heavy API. This design takes Salsa's mechanism but keeps a closed, compiler-specific query set (simpler, fewer trait gymnastics — the R2 pitfall noted) because it controls both the engine and its only client.

Back-of-Envelope Capacity Model

The numbers an expert computes from §4 (System Constraints) before designing. Each is derived step-by-step; the §4 input is named. (Self-compile size ≈ 40–60k LOC Lyra per §1/§4; reference machine 8-core, 32 GB, NVMe per §4.)

  • C1 — query-node count for a self-compile. Input: §4 "Query DAG ... ~60k-LOC self-compile" + §Scalability "queries ≈ items × pipeline stages". With ~5–8k top-level items (fns/structs/impls across ~60k LOC) and ~8 derived stages per item (lex,parse,module_scope,resolve,type_of,typeck_body,lir,codegen): ≈ 6000 × 8 ≈ 4.8×10⁴ derived nodes, with mono-instances pushing toward 10⁵. Confirms §Scalability's "~10⁵–10⁶ nodes" and that the DAG fits in RAM.
  • C2 — in-memory node-map footprint. Input: §11.2 QueryNode layout + C1. Each node ≈ QueryKey(16 B) + Fingerprint(32 B) + 2×Revision(16 B) + Vec<DepEdge> header(24 B) + durability/state(8 B) ≈ 96 B plus edges (~4 deps × 16 B = 64 B) ≈ 160 B/node. At 10⁵ nodes → 1.6×10⁷ B ≈ 16 MB of graph metadata; at 10⁶ → ~160 MB. Well within the §4 ≤ 2.0 GB cold RSS — confirming the values, not the graph, dominate memory.
  • C3 — peak RSS sanity vs the §4 2.0 GB cold ceiling. Input: §4 "Peak RSS cold ≤ 2.0 GB". Graph metadata (C2, ≤160 MB) + interner (say 50k symbols × ~32 B ≈ 1.6 MB) + AST/HIR/LIR arenas for the in-flight working set. If serialized query values average ~2 KB and ~10⁵ are resident: 10⁵ × 2 KB = 200 MB; arenas + values + graph ≈ 400–600 MB resident, leaving headroom under 2.0 GB. Confirms the ceiling is comfortable and lazy value loading (mmap) is the lever if it tightens.
  • C4 — warm 1-line-edit recompute budget. Input: §4 "warm rebuild ... ≤ 250 ms p50" + "hit rate ≥ 98%". At 10⁵ nodes, ≥98% green ⇒ ≤ 2×10³ nodes recompute. The red-green verify walk touches the transitive dependents (cheap: a fingerprint compare each); the actual recompute is the one edited fn's typeck_body+lir+codegen (≈ 1 CGU). Budget check: 250 ms ÷ ~2000 verified nodes ≈ 125 µs/node average including the handful of true recomputes — generous, so the p50 target is recompute-bound (1 CGU), not verify-bound, exactly as §4 notes.
  • C5 — on-disk cache size. Input: §4 "On-disk cache ≤ 3× sum of artifact sizes" + "reachable + 1 prior revision". If the self-compile emits ~5×10³ CGU artifacts averaging ~4 KB (bytecode) → artifacts ≈ 5000 × 4 KB = 20 MB; cached query values (AST/HIR/LIR serialized) are the bulk — say 2–3× artifacts. Total ≈ 60 MB reachable; keeping one prior revision roughly doubles worst-case to ≈ 120 MB ≤ 3× the 40 MB (artifacts + their direct values) → confirms the §4 3× bound with the GC dropping older revisions.
  • C6 — cold build CPU budget vs the §4 90 s target. Input: §4 "Cold full build ≤ 90 s, 8 threads" + C1. ~10⁵ derived nodes over 8 threads with ~90 s wall ⇒ 90 s × 8 cores ÷ 10⁵ nodes ≈ 7.2 ms average CPU per node. Front-end nodes (lex/parse) are sub-ms; the budget is spent in typeck_body/lir/codegen of larger items — consistent with §Performance "front end + LIR dominant". Headroom exists because most nodes are cheap.
  • C7 — lexer/parser wall-time for the self-compile. Input: §4 "Lexer ≥ 30 MB/s, Parser ≥ 8 MB/s" + ~60k LOC ≈ ~2 MB source. Lex: 2 MB ÷ 30 MB/s ≈ 67 ms; parse: 2 MB ÷ 8 MB/s ≈ 250 ms single-thread, parallel across files → tens of ms. Confirms the front end is a small fraction of the 90 s cold budget (C6) — typeck + codegen dominate, justifying parallel queries as the §4 vertical-scaling lever.
  • C8 — VM self-compile time (stage1 under the interpreter). Input: §4 "VM ≥ 150 M ops/s" + "run lyrac1 ≤ 5× native". If a native cold self-build is ~90 s (C6), stage1 running on the VM (Phase 10) is ≤ 5× → ≤ ~450 s (~7.5 min) worst case for a cold VM self-compile. Confirms §22's "VM path allowed to be slower (minutes)" and why the C-native lyrac1 is preferred for stage2 speed.
  • C9 — fixpoint + DDC wall-time cost. Input: §23 "fixpoint = 2 self-compiles; DDC adds 2 more (4×)" + C6 native time. Native path: 4 × 90 s = 360 s ≈ 6 min for full fixpoint+DDC; on the VM path stage1 dominates (C8). Confirms running fixpoint every PR (native, ~3 min for the 2-compile gate) but DDC nightly (§23) is the right cost split.
  • C10 — file-descriptor budget for the cache shards + source mmaps. Input: §4 "FD budget ≤ 256". Cache sharded by content-address prefix; if sharded into, say, 64 directories and the build mmaps ~50–100 source files concurrently, 64 + ~100 ≈ 164 < 256 ✓. Confirms the §4 FD ceiling holds and bounds how finely the cache may be sharded (the ADR-13 shard count is FD-limited).
  • C11 — determinism-harness wall-time (100× repeat). Input: §4 "Determinism 100×" + C6. A 100× cold-build repeat = 100 × 90 s = 9000 s ≈ 2.5 h if serial — so §Testing runs 10× per PR (15 min) and 100× + cross-runner nightly. Confirms the §Testing PR-vs-nightly split for INV-1 is forced by this number, not arbitrary.
  • C12 — startup (warm cache open) vs the §4 40 ms target. Input: §4 "Startup ≤ 40 ms warm" + C5 cache size. Opening a ~60–120 MB cache by mmap + lazy index load (not full deserialize) means startup cost ≈ reading the manifest index (a few hundred KB) + mapping value files: sub-10 ms of I/O on NVMe + index parse. Confirms the §4 40 ms target is only achievable with lazy/mmap loading (eager deserialize of 120 MB would blow it), driving the Phase 6 design choice.

Alternative Architectures

Fundamentally different ways to build an incremental, self-hosting compiler for the same goal. Each: sketch, winning regime, the real system embodying it, why this blueprint rejected it.

A1 — Bootstrap from a prior version of itself (no foreign host). The seed is the previous release of the compiler; there is no foreign-language stage0 in the trust chain at all.

   lyrac (release N-1, trusted binary) ──compiles──▶ lyrac (release N, stage1)
        ▲                                                     │
        └──────── each release seeds the next; no foreign host ┘
  • Wins: a mature, continuously-released compiler where a trusted prior binary always exists — the bootstrap is one step, the host shares the exact language/runtime, and there is no foreign-host impedance mismatch.
  • Real system: rustc (stage0 = prior rustc release, R1) and the Go gc compiler (bootstraps from a prior Go since 1.5, R5) both embody this.
  • Rejected because: this project's pedagogical and trust goal is to confront the from-nothing seed problem (§1, ADR-1) — "bootstrap from a prior self" presupposes the very trusted artifact the trusting-trust threat (P1) calls into question, and there is no "release N-1" for a language being created here. A minimal, audited, foreign Rust seed plus DDC (§23) is the deliberate alternative.

A2 — Batch (non-incremental) compiler + external build-system caching. The compiler is a clean stateless translator; all incrementality lives at the file/package grain in an outer build tool.

   build tool (mtime/content keys) ─▶ [ batch lyrac: source → artifact, no cache ] ─▶ artifact
        │  reuses whole-file/package outputs when inputs unchanged  ▲
        └────────────────── coarse-grained reuse only ─────────────┘
  • Wins: large codebases split into many small translation units where whole-unit reuse is enough, and a simple, stateless compiler is easier to make deterministic and to bootstrap (no query engine to self-host).
  • Real system: the Go gc compiler + go build's package cache (R5); GCC/Clang + Bazel/Make at the build grain (R8); historically every batch compiler.
  • Rejected because: the §4 SLO is a 1-line-edit warm rebuild ≤ 250 ms — sub-file, item-level reuse — which whole-unit caching cannot deliver, and the project's entire point is the in-compiler query engine that must itself be self-hosted (db.lyra, §21). Coarse caching also never exercises the incremental==clean interaction (§24) that is this blueprint's reason to exist.

A3 — Persistent compiler daemon holding the query graph in memory (no on-disk cache). A long-lived process keeps the entire red-green graph resident; edits stream in over IPC; there is no serialized cache.

   editor/CLI ──edits over IPC──▶ ┌──────────────────────────────┐
                                  │ daemon: in-RAM query DAG       │
   query results ◀───────────────│ (red-green, never serialized)  │
                                  └──────────────────────────────┘
  • Wins: interactive/IDE workloads where warm-cache open latency must be ~zero (the graph never leaves RAM) and the same process serves thousands of edits — the §4 startup cost vanishes and verify walks run on hot data structures.
  • Real system: Salsa (R2) is explicitly designed for this in-memory, long-lived model (it powers rust-analyzer); Microsoft Roslyn keeps an in-memory compilation graph for the same reason.
  • Rejected because: v1 is a CLI run locally and in CI (§1 deployment model), where crash-only on-disk persistence (INV-8) and per-invocation determinism gates matter more than zero-startup, and a daemon adds a long-lived-process determinism/crash-integrity surface the batch CLI avoids. The daemon is explicitly deferred (PhaseDeferred("FINAL_BLUEPRINT §25")), un-deferred only when warm-open startup becomes the dominant interactive cost.

A4 — Whole-program (no codegen-unit partitioning) deterministic compiler. Codegen emits a single monolithic artifact rather than content-addressed CGUs; reuse is all-or-nothing at the program level.

   all monomorphized defs ─▶ [ single codegen pass → one artifact blob ] ─▶ program
                              (no per-CGU content-addressing/reuse)
  • Wins: small programs or whole-program-optimizing builds where cross-function optimization across the entire program is the goal and partitioning would forfeit inlining/LTO opportunities — one artifact is simplest and enables maximal global opt.
  • Real system: classic whole-program compilers and LTO builds (GCC -flto, LLVM ThinLTO is the partitioned counter-evolution); single-.o outputs from a batch compiler.
  • Rejected because: it destroys the codegen-layer incremental win — any edit re-emits the whole program, blowing the §4 warm-rebuild SLO — and forfeits the content-addressed dedup that lets unchanged CGUs be reused verbatim (§8.7) and that doubles as a fixpoint enabler (MM7). Bounded, content-addressed CGUs (ADR-13, §20) are the deliberate choice; whole-program opt (GVN/LICM) is separately deferred (§19).
