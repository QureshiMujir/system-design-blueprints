4. System Constraints

Quantified targets. (Reference hardware: 8-core x86-64, 32 GB RAM, NVMe SSD; cache on local FS.)

Constraint Target Notes
(M1) Cold full build (compiler self-build, ~40–60k LOC Lyra) ≤ 90 s wall (release profile) single machine, 8 threads
(M2) Warm rebuild after 1-line edit (one fn body) ≤ 250 ms p50, ≤ 600 ms p95 dominated by re-typeck + recodegen of 1 CGU
(M3) Warm rebuild after signature change touching N dependents ≤ 50 ms × N (linear in true dependents) early cutoff prunes false dependents
(M4) Query cache hit rate on 1-line-edit rebuild ≥ 98% of derived queries reused (green) green nodes / total nodes
Bootstrap fixpoint bytes(stage1) == bytes(stage2) byte-identical, 100% hard acceptance gate
Determinism (same inputs → same outputs) 100%, repeated 100× and cross-machine (same triple) no HashMap-order leaks
Incremental == clean (per-artifact) 100% byte-identical across full diff suite central invariant
(M5) Peak RSS, cold full build ≤ 2.0 GB arenas + query values + interner
(M6) Peak RSS, warm rebuild ≤ 1.4 GB most values loaded lazily from cache
(M7) On-disk cache size ≤ 3× sum of artifact sizes; growth bounded by GC reachable + 1 prior revision
(M8) GC pause ≤ 200 ms; incremental/amortized never blocks a build > 200 ms
(M9) Lexer throughput ≥ 30 MB/s single thread UTF-8, trivia-preserving
(M10) Parser throughput ≥ 8 MB/s single thread error-recovering
(M11) VM dispatch ≥ 150 M simple ops/s (threaded dispatch) run lyrac1 ≤ 5× native
(M12) Startup (CLI to first query) ≤ 40 ms warm cache open mmap + lazy index load
(M13) Shutdown / flush ≤ 300 ms; atomic (rename); crash-safe partial flush never corrupts cache
Max source file size 64 MiB (rejected above; 32-bit relative offsets) guards span overflow
Query DAG depth bounded; cycle detector trips at recursion limit (default 256) prevents stack blowup
File descriptor budget ≤ 256 fds (cache shards + source mmaps)
Recovery time (corrupt cache) ≤ cold-build time (fall back to cold) corruption never wrong output
CI gate fixpoint + diff suite must pass 100% to merge determinism is binary, no flaky tolerance
Horizontal scaling none in v1 (single process); cache local distributed cache deferred §18
Vertical scaling linear-ish to ~16 threads; query parallelism is the lever beyond, codegen queue saturates

Failure budget: zero tolerance for nondeterminism (breaks the fixpoint, a binary gate). RTO on cache corruption = a cold build. No clock dependence anywhere (timestamps never enter fingerprints).

Performance Engineering

  • Benchmarking strategy. benchmarks/ (criterion-style): cold_build (full self-build), warm_1line (the §4 SLO), hit_rate, vm_dispatch. Relative thresholds vs a recorded baseline; CI fails on regression beyond noise margin. Dedicated, quiesced runner.
  • Profiling methodology. Cold build: perf record + flamegraph → expect lexer/parser + typeck + LIR dominant; codegen parallelized. Warm build: profile the verify path (red-green walk) vs recompute — a healthy warm build is mostly verify (cheap) + tiny recompute.
  • Flamegraph workflow. cargo flamegraph on cold + warm builds; compare across releases; a warm-build flamegraph dominated by recompute (not verify) signals an early-cutoff regression.
  • Tracing methodology. Per-query spans → a build's query tree with timings; the slowest queries + the red/green ratio guide tuning.
  • Allocator analysis. Arenas per AST/HIR/LIR (bump allocation, freed wholesale on eviction); track peak RSS vs §4 ceilings; avoid per-node heap allocs; intern/hash-cons to dedup (Symbol, Ty).
  • Lock analysis. The query-node map is the hot shared structure → shard it; Running-state condvars (no spin); measure contention with parking_lot stats / lock-wait tracing.
  • Cache analysis. Token stream + LIR as struct-of-arrays for sequential scans; content-addressed artifact reuse to skip codegen entirely; fingerprint reads from the node (don't rehash).
  • Syscall analysis. mmap source + cache (no per-read syscalls); batch cache writes (fsync once at commit per durability tier); single write for C-backend output.
  • Throughput targets. §4: lexer ≥ 30 MB/s (M9), parser ≥ 8 MB/s (M10), VM ≥ 150 M ops/s (M11), cold build ≤ 90 s (M1).
  • Tail-latency analysis. Warm-rebuild p95 ≤ 600 ms (M2) — tail driven by the largest single CGU recompute + cache flush; keep CGUs bounded; flush async where durability allows.
  • Memory profiling. Heaptrack/valgrind-massif on cold build; track interner + arena + cache-value memory; peak RSS ≤ 2.0 GB cold (M5) / 1.4 GB warm (M6).

Back-of-Envelope Capacity Model

The numbers an expert computes from §4 (System Constraints) before designing. Each is derived step-by-step; the §4 input is named. (Self-compile size ≈ 40–60k LOC Lyra per §1/§4; reference machine 8-core, 32 GB, NVMe per §4.)

  • C1 — query-node count for a self-compile. Input: §4 "Query DAG ... ~60k-LOC self-compile" + §Scalability "queries ≈ items × pipeline stages". With ~5–8k top-level items (fns/structs/impls across ~60k LOC) and ~8 derived stages per item (lex,parse,module_scope,resolve,type_of,typeck_body,lir,codegen): ≈ 6000 × 8 ≈ 4.8×10⁴ derived nodes, with mono-instances pushing toward 10⁵. Confirms §Scalability's "~10⁵–10⁶ nodes" and that the DAG fits in RAM.
  • C2 — in-memory node-map footprint. Input: §11.2 QueryNode layout + C1. Each node ≈ QueryKey(16 B) + Fingerprint(32 B) + 2×Revision(16 B) + Vec<DepEdge> header(24 B) + durability/state(8 B) ≈ 96 B plus edges (~4 deps × 16 B = 64 B) ≈ 160 B/node. At 10⁵ nodes → 1.6×10⁷ B ≈ 16 MB of graph metadata; at 10⁶ → ~160 MB. Well within the §4 ≤ 2.0 GB cold RSS — confirming the values, not the graph, dominate memory.
  • C3 — peak RSS sanity vs the §4 2.0 GB cold ceiling. Input: §4 "Peak RSS cold ≤ 2.0 GB". Graph metadata (C2, ≤160 MB) + interner (say 50k symbols × ~32 B ≈ 1.6 MB) + AST/HIR/LIR arenas for the in-flight working set. If serialized query values average ~2 KB and ~10⁵ are resident: 10⁵ × 2 KB = 200 MB; arenas + values + graph ≈ 400–600 MB resident, leaving headroom under 2.0 GB. Confirms the ceiling is comfortable and lazy value loading (mmap) is the lever if it tightens.
  • C4 — warm 1-line-edit recompute budget. Input: §4 "warm rebuild ... ≤ 250 ms p50" + "hit rate ≥ 98%". At 10⁵ nodes, ≥98% green ⇒ ≤ 2×10³ nodes recompute. The red-green verify walk touches the transitive dependents (cheap: a fingerprint compare each); the actual recompute is the one edited fn's typeck_body+lir+codegen (≈ 1 CGU). Budget check: 250 ms ÷ ~2000 verified nodes ≈ 125 µs/node average including the handful of true recomputes — generous, so the p50 target is recompute-bound (1 CGU), not verify-bound, exactly as §4 notes.
  • C5 — on-disk cache size. Input: §4 "On-disk cache ≤ 3× sum of artifact sizes" + "reachable + 1 prior revision". If the self-compile emits ~5×10³ CGU artifacts averaging ~4 KB (bytecode) → artifacts ≈ 5000 × 4 KB = 20 MB; cached query values (AST/HIR/LIR serialized) are the bulk — say 2–3× artifacts. Total ≈ 60 MB reachable; keeping one prior revision roughly doubles worst-case to ≈ 120 MB ≤ 3× the 40 MB (artifacts + their direct values) → confirms the §4 3× bound with the GC dropping older revisions.
  • C6 — cold build CPU budget vs the §4 90 s target. Input: §4 "Cold full build ≤ 90 s, 8 threads" + C1. ~10⁵ derived nodes over 8 threads with ~90 s wall ⇒ 90 s × 8 cores ÷ 10⁵ nodes ≈ 7.2 ms average CPU per node. Front-end nodes (lex/parse) are sub-ms; the budget is spent in typeck_body/lir/codegen of larger items — consistent with §Performance "front end + LIR dominant". Headroom exists because most nodes are cheap.
  • C7 — lexer/parser wall-time for the self-compile. Input: §4 "Lexer ≥ 30 MB/s, Parser ≥ 8 MB/s" + ~60k LOC ≈ ~2 MB source. Lex: 2 MB ÷ 30 MB/s ≈ 67 ms; parse: 2 MB ÷ 8 MB/s ≈ 250 ms single-thread, parallel across files → tens of ms. Confirms the front end is a small fraction of the 90 s cold budget (C6) — typeck + codegen dominate, justifying parallel queries as the §4 vertical-scaling lever.
  • C8 — VM self-compile time (stage1 under the interpreter). Input: §4 "VM ≥ 150 M ops/s" + "run lyrac1 ≤ 5× native". If a native cold self-build is ~90 s (C6), stage1 running on the VM (Phase 10) is ≤ 5× → ≤ ~450 s (~7.5 min) worst case for a cold VM self-compile. Confirms §22's "VM path allowed to be slower (minutes)" and why the C-native lyrac1 is preferred for stage2 speed.
  • C9 — fixpoint + DDC wall-time cost. Input: §23 "fixpoint = 2 self-compiles; DDC adds 2 more (4×)" + C6 native time. Native path: 4 × 90 s = 360 s ≈ 6 min for full fixpoint+DDC; on the VM path stage1 dominates (C8). Confirms running fixpoint every PR (native, ~3 min for the 2-compile gate) but DDC nightly (§23) is the right cost split.
  • C10 — file-descriptor budget for the cache shards + source mmaps. Input: §4 "FD budget ≤ 256". Cache sharded by content-address prefix; if sharded into, say, 64 directories and the build mmaps ~50–100 source files concurrently, 64 + ~100 ≈ 164 < 256 ✓. Confirms the §4 FD ceiling holds and bounds how finely the cache may be sharded (the ADR-13 shard count is FD-limited).
  • C11 — determinism-harness wall-time (100× repeat). Input: §4 "Determinism 100×" + C6. A 100× cold-build repeat = 100 × 90 s = 9000 s ≈ 2.5 h if serial — so §Testing runs 10× per PR (15 min) and 100× + cross-runner nightly. Confirms the §Testing PR-vs-nightly split for INV-1 is forced by this number, not arbitrary.
  • C12 — startup (warm cache open) vs the §4 40 ms target. Input: §4 "Startup ≤ 40 ms warm" + C5 cache size. Opening a ~60–120 MB cache by mmap + lazy index load (not full deserialize) means startup cost ≈ reading the manifest index (a few hundred KB) + mapping value files: sub-10 ms of I/O on NVMe + index parse. Confirms the §4 40 ms target is only achievable with lazy/mmap loading (eager deserialize of 120 MB would blow it), driving the Phase 6 design choice.
