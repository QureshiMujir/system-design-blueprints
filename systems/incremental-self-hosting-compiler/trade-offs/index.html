Each card is one row of the blueprint's decision table: what was locked in, what was rejected, and — the column that matters most — the situation in which the rejected choice is the right one.

Decisions (§9) · 30 ADRs

ADR-1

Bootstrap host language (stage0)

Chosen

Rust (stable, pinned toolchain)

Rejected

C++ (UB risk in root of trust), OCaml (smaller talent/repro story), self-bootstrap from nothing (impossible)

When the rejected choice is right

OCaml wins when the source language is ML-family and a host bytecode image already exists to seed from (OCaml's own boot/ model, R6) — the host then shares the runtime/value model and the bootstrap is shorter than re-expressing it over a foreign Rust host.

Why: Memory-safe deterministic front end; rustc query system is the reference; pinned toolchain aids reproducibility

ADR-2

Source language identity

Chosen

Lyra (defined here)

Rejected

reuse an existing language (then it's not "from scratch")

When the rejected choice is right

Reusing an existing language wins when the goal is a production compiler for a standardized language (a new C or Go front end), where ecosystem + conformance to an external spec matter more than minimizing the trust base.

Why: Must control the spec to keep it minimal-yet-self-sufficient and to version the cache format

ADR-3

Incremental model

Chosen

Demand-driven, memoized, red-green, early-cutoff (salsa/rustc-style)

Rejected

Timestamp-based (make), topological recompute, no-cache

When the rejected choice is right

Timestamp-based (make/Bazel-coarse) wins at the build-system grain — many large translation units with cheap dependency tracking and no intra-file reuse — where file-mtime invalidation is adequate and the per-query bookkeeping of red-green is wasted overhead (R8).

Why: Only red-green + fingerprints give the N-dependents and 98% hit-rate targets (§4)

ADR-4

Fingerprint / content-address hash

Chosen

BLAKE3-256

Rejected

SHA-256 (slower), xxHash/FxHash (not collision-resistant; cache-poisoning risk), CRC

When the rejected choice is right

xxHash/FxHash wins for a purely in-process, single-trust-domain memo cache that never persists to disk and faces no adversary — there a fast non-cryptographic hash maximizes throughput and collision-resistance is irrelevant (rustc uses FxHash for in-memory maps for exactly this reason).

Why: Fast + cryptographic; needed because fingerprints gate correctness (INV-1/INV-4)

ADR-5

Span model

Chosen

Relative spans (item-anchored) + absolute source map

Rejected

absolute byte spans only

When the rejected choice is right

Absolute byte spans win in a batch (non-incremental) compiler or a one-shot linter, where there is no warm cache to invalidate and absolute offsets are simpler, faster to resolve, and never re-anchored.

Why: Absolute spans invalidate everything below an edit (INV-6); relative spans keep IDs stable

ADR-6

ID stability

Chosen

ItemPath-hash DefIds + interned Symbols

Rejected

sequential numbering

When the rejected choice is right

Sequential numbering wins when IDs never outlive a single compilation (no cross-build cache), where dense sequential indices give O(1) array-indexed side tables and the renumber-on-edit hazard cannot occur.

Why: Sequential IDs renumber on insert → spurious invalidation / silent miscompile

ADR-7

Parser strategy

Chosen

Recursive descent + Pratt (precedence) with panic-mode recovery

Rejected

parser generator (LALR), PEG

When the rejected choice is right

A parser generator (LALR/GLR) wins when the grammar is large, externally specified, and frequently revised (e.g. a standards-tracking language), where a declarative grammar + generated tables reduce hand-maintenance and ambiguity bugs more than hand-rolled control buys.

Why: Hand-written gives best error recovery + control; recovery is mandatory (Principle 12)

ADR-8

Type system

Chosen

Bidirectional + HM unification, monomorphized generics

Rejected

full System-F inference, dynamic typing

When the rejected choice is right

Dynamic typing wins for a scripting/REPL language prioritizing edit-run latency and metaprogramming over static guarantees; full type-passing (dictionary) generics win when code-size from monomorphization is prohibitive (huge generic instantiation sets).

Why: Bidirectional is practical + predictable; monomorphization avoids runtime generics in LIR

ADR-9

Mid-level IR

Chosen

SSA (LIR), dominance-frontier φ placement

Rejected

stack IR, CPS, three-address non-SSA

When the rejected choice is right

A stack IR wins when the IR is the shipped artifact for a stack VM (JVM bytecode, WASM) and no heavy mid-level optimization is performed in-house; CPS wins for languages with first-class continuations / heavy tail-call semantics.

Why: SSA is the standard substrate for the opt passes we need (P3/P9)

ADR-10

Opt pass set (v1)

Chosen

const-fold, DCE, mem2reg, single-pass inline

Rejected

GVN, LICM, loop unroll (deferred §19)

When the rejected choice is right

GVN/LICM/loop-unroll win the moment the compiler targets runtime performance of generated code as a headline metric (a production optimizing backend), where the extra opt power outweighs the added determinism surface they must be engineered around.

Why: Enough to exercise IR + determinism; advanced opts add nondeterminism surface

ADR-11

Backends

Chosen

Register bytecode VM + C99 text emit

Rejected

direct native (own assembler/linker), LLVM dependency

When the rejected choice is right

An LLVM backend wins when generated-code speed is the deliverable and reproducibility/seed-minimalism is not — LLVM's optimizer + multi-target codegen far exceed a teaching backend (the choice rustc, Clang, Cranelift-vs-LLVM debates turn on).

Why: Two backends test determinism across surfaces; C-emit defers linking; VM runs lyrac1 without a host compiler

ADR-12

VM design

Chosen

Register machine, threaded dispatch

Rejected

stack machine, AST-walking interpreter

When the rejected choice is right

A stack machine wins when bytecode density and a trivial verifier/codegen matter more than dispatch speed (JVM/WASM/CPython stack ISAs); an AST-walker wins for a prototype where implementation simplicity dominates and speed is irrelevant.

Why: Register VM is faster + closer to LIR; we need ≤5× native to run lyrac1

ADR-13

Cache storage

Chosen

Directory of sharded, checksummed, content-addressed files + a manifest

Rejected

single SQLite DB, LMDB, in-memory only

When the rejected choice is right

A single embedded DB (SQLite/LMDB) wins when the cache needs transactional multi-key updates, secondary indexes, or concurrent multi-writer access — a structured store then beats a flat content-addressed dir's coarse file locking.

Why: Crash-only atomic-rename semantics are simplest on a file dir; content-address dedups artifacts

ADR-14

Cache durability

Chosen

Durability tiers (volatile / synced) + revision manifest

Rejected

always-fsync (slow), never-fsync (unsafe)

When the rejected choice is right

Always-fsync wins when the cache is the authoritative store of expensive-to-recompute results on unreliable hardware and a crash losing derived data is unacceptable (durability > flush latency); never-fsync wins for a pure in-RAM/tmpfs cache that is intentionally discarded per session.

Why: Tiers bound flush latency (§4) while keeping inputs durable

ADR-15

Serialization (cache values)

Chosen

Versioned, deterministic, length-prefixed binary (custom)

Rejected

serde+bincode (ordering caveats), JSON (slow, float drift), protobuf

When the rejected choice is right

Protobuf/serde wins when the serialized data crosses a language or service boundary and schema evolution / cross-tool interop matters more than byte-exact determinism (an externally consumed cache or an RPC payload).

Why: Must be byte-deterministic + version-tagged (INV-9); custom keeps full control

ADR-16

Concurrency model

Chosen

Work-stealing thread pool over pure queries; canonical sort before emit

Rejected

single-threaded, async/await, actor model

When the rejected choice is right

Single-threaded wins on a small program or an embedded build where the parallel-scheduling overhead + the canonical-sort tax exceed the speedup; async/await wins when the workload is I/O-bound (a network-fetching remote-cache client) rather than CPU-bound query compute.

Why: Queries are pure → safe to parallelize; sort restores determinism (Principle 11)

ADR-17

Determinism enforcement

Chosen

Ban HashMap iteration in output paths; use BTreeMap/sorted Vec; fixed float fmt

Rejected

trust developers to be careful

When the rejected choice is right

Trusting developers (HashMap allowed) wins in code paths that never feed an output or a fingerprint — internal scratch maps on the hot path — where HashMap's O(1) access beats BTreeMap's log factor and order is provably unobservable.

Why: Lint + CI determinism harness (INV-1); humans forget

ADR-18

Bootstrap verification

Chosen

DDC (diverse double-compilation) + byte-identical fixpoint gate

Rejected

trust the seed; reproducible-build-only

When the rejected choice is right

Reproducible-build-only (no DDC) wins when the seed compiler is itself already trusted via an independent, audited supply chain (e.g. a distro-built compiler with its own provenance), making the cost of maintaining a second diverse host unjustified.

Why: DDC is the only known defense against trusting-trust (P1/P2)

ADR-19

Build system (stage0)

Chosen

Cargo workspace, pinned rust-toolchain.toml

Rejected

Bazel, Make-only

When the rejected choice is right

Bazel wins when stage0 is one crate inside a large polyglot monorepo with established remote caching + hermetic cross-language builds — the monorepo's existing Bazel infra then subsumes a standalone Cargo workspace.

Why: Standard for Rust; pinning aids reproducibility; Bazel is overkill here

ADR-20

Build orchestration (full bootstrap)

Chosen

lyra-fixpoint driver + Makefile targets

Rejected

shell scripts

When the rejected choice is right

Shell scripts win for a throwaway one-machine bootstrap demo where a 20-line script is faster to write than a typed orchestrator and the DDC/diff gating is not yet needed (the dwheeler/dcc reference, R9, is exactly such scripts).

Why: Programmatic control of stage0→1→2 + DDC + diff gate

ADR-21

Dependency policy

Chosen

Near-zero deps; BLAKE3 + memmap2 + a small arg parser only; vendored

Rejected

freely pull crates

When the rejected choice is right

Liberal deps win for application software with no root-of-trust role and a tight delivery deadline, where development velocity from rich crates outweighs supply-chain surface (the opposite of a bootstrap seed's threat model).

Why: Each dep widens the trust base of the root-of-trust host (Principle 10)

ADR-22

Testing

Chosen

Golden conformance + property tests + differential (incremental==clean) + fixpoint

Rejected

unit tests only

When the rejected choice is right

Unit-tests-only wins for a library with no cross-implementation or incremental-vs-clean invariant to falsify — where each function's behavior is locally checkable and there is no second oracle (a second impl, a cold build) to differ against.

Why: The invariants (INV-2/3) are only testable differentially

ADR-23

Fuzzing

Chosen

cargo-fuzz: source fuzzer + edit-sequence fuzzer (replay)

Rejected

none

When the rejected choice is right

No fuzzing wins only for a non-incremental tool processing fully trusted input on a closed corpus, where the span/ID-instability and hostile-input failure classes (§Threat Model) simply do not exist.

Why: Edit-sequence fuzzing is the only way to find span/ID-instability miscompiles

ADR-24

Logging / tracing

Chosen

Structured events (tracing), red-green audit log, off hot path in release

Rejected

printf, always-on verbose

When the rejected choice is right

printf/always-on verbose wins during early bring-up of a single module before the query engine exists, where structured tracing infrastructure is premature and a few prints suffice to debug.

Why: Observability of cache decisions is essential (Principle 9)

ADR-25

Metrics

Chosen

In-process counters dumped to JSON (--metrics)

Rejected

Prometheus/exporter (overkill for a CLI)

When the rejected choice is right

A Prometheus exporter wins if the compiler becomes a long-lived daemon/build service (the deferred §25 daemon) scraped by fleet monitoring — then a pull-based time-series exporter beats per-invocation JSON dumps.

Why: Hit-rate / recompute-time are the SLO levers (§4)

ADR-26

CI/CD

Chosen

GitHub Actions: build → test → conformance → fixpoint → diff → fuzz-smoke

Rejected

none / ad hoc

When the rejected choice is right

Ad-hoc/local-only CI wins for a solo exploratory prototype that never accepts external contributions, where the fixpoint/diff gates are run by hand and hosted CI is unjustified overhead.

Why: Determinism gates must run every PR; fixpoint is non-negotiable

ADR-27

Packaging

Chosen

Static lyrac binary + checked-in seed provenance doc

Rejected

dynamic libs, container-only

When the rejected choice is right

Container-only distribution wins when the compiler has heavy, version-sensitive external toolchain deps (a specific cc, sysroot) that a container pins reproducibly — there an image is a more honest unit than a "static" binary that still shells out to cc.

Why: A compiler should be a single self-contained binary; seed provenance is a trust artifact

ADR-28

Reproducibility strategy

Chosen

SOURCE_DATE_EPOCH only sanctioned clock; no timestamps in artifacts/cache fps; sorted everything

Rejected

embed build time/host

When the rejected choice is right

Embedding build time/host wins for release binaries where forensic build provenance in the artifact is a compliance requirement and reproducibility is not — the timestamp then lives in a non-fingerprinted section (as this design itself does for version stamps, §23).

Why: Any embedded timestamp breaks the fixpoint (INV-1)

ADR-29

Floating-point formatting

Chosen

Single canonical shortest-round-trip formatter (Ryū-style), fixed

Rejected

platform printf("%g"), libc-dependent

When the rejected choice is right

Platform printf wins for a single-platform tool whose float output is human-facing only (never fingerprinted, never cross-machine compared), where pulling in a custom formatter is needless code.

Why: libc float formatting varies by platform/locale → nondeterminism (INV-14)

ADR-30

Licensing

Chosen

Apache-2.0 OR MIT (dual), incl. seed binaries' provenance

Rejected

GPL (viral, complicates seed redistribution)

When the rejected choice is right

GPL/copyleft wins when the project's goal is to force downstream toolchains built on it to remain open (a political/ecosystem stance, as GCC chose), accepting the redistribution friction in exchange for copyleft guarantees.

Why: Permissive; standard for toolchains; seed provenance kept auditable

Alternative Architectures

Fundamentally different ways to build an incremental, self-hosting compiler for the same goal. Each: sketch, winning regime, the real system embodying it, why this blueprint rejected it.

A1 — Bootstrap from a prior version of itself (no foreign host). The seed is the previous release of the compiler; there is no foreign-language stage0 in the trust chain at all.

   lyrac (release N-1, trusted binary) ──compiles──▶ lyrac (release N, stage1)
        ▲                                                     │
        └──────── each release seeds the next; no foreign host ┘
  • Wins: a mature, continuously-released compiler where a trusted prior binary always exists — the bootstrap is one step, the host shares the exact language/runtime, and there is no foreign-host impedance mismatch.
  • Real system: rustc (stage0 = prior rustc release, R1) and the Go gc compiler (bootstraps from a prior Go since 1.5, R5) both embody this.
  • Rejected because: this project's pedagogical and trust goal is to confront the from-nothing seed problem (§1, ADR-1) — "bootstrap from a prior self" presupposes the very trusted artifact the trusting-trust threat (P1) calls into question, and there is no "release N-1" for a language being created here. A minimal, audited, foreign Rust seed plus DDC (§23) is the deliberate alternative.

A2 — Batch (non-incremental) compiler + external build-system caching. The compiler is a clean stateless translator; all incrementality lives at the file/package grain in an outer build tool.

   build tool (mtime/content keys) ─▶ [ batch lyrac: source → artifact, no cache ] ─▶ artifact
        │  reuses whole-file/package outputs when inputs unchanged  ▲
        └────────────────── coarse-grained reuse only ─────────────┘
  • Wins: large codebases split into many small translation units where whole-unit reuse is enough, and a simple, stateless compiler is easier to make deterministic and to bootstrap (no query engine to self-host).
  • Real system: the Go gc compiler + go build's package cache (R5); GCC/Clang + Bazel/Make at the build grain (R8); historically every batch compiler.
  • Rejected because: the §4 SLO is a 1-line-edit warm rebuild ≤ 250 ms — sub-file, item-level reuse — which whole-unit caching cannot deliver, and the project's entire point is the in-compiler query engine that must itself be self-hosted (db.lyra, §21). Coarse caching also never exercises the incremental==clean interaction (§24) that is this blueprint's reason to exist.

A3 — Persistent compiler daemon holding the query graph in memory (no on-disk cache). A long-lived process keeps the entire red-green graph resident; edits stream in over IPC; there is no serialized cache.

   editor/CLI ──edits over IPC──▶ ┌──────────────────────────────┐
                                  │ daemon: in-RAM query DAG       │
   query results ◀───────────────│ (red-green, never serialized)  │
                                  └──────────────────────────────┘
  • Wins: interactive/IDE workloads where warm-cache open latency must be ~zero (the graph never leaves RAM) and the same process serves thousands of edits — the §4 startup cost vanishes and verify walks run on hot data structures.
  • Real system: Salsa (R2) is explicitly designed for this in-memory, long-lived model (it powers rust-analyzer); Microsoft Roslyn keeps an in-memory compilation graph for the same reason.
  • Rejected because: v1 is a CLI run locally and in CI (§1 deployment model), where crash-only on-disk persistence (INV-8) and per-invocation determinism gates matter more than zero-startup, and a daemon adds a long-lived-process determinism/crash-integrity surface the batch CLI avoids. The daemon is explicitly deferred (PhaseDeferred("FINAL_BLUEPRINT §25")), un-deferred only when warm-open startup becomes the dominant interactive cost.

A4 — Whole-program (no codegen-unit partitioning) deterministic compiler. Codegen emits a single monolithic artifact rather than content-addressed CGUs; reuse is all-or-nothing at the program level.

   all monomorphized defs ─▶ [ single codegen pass → one artifact blob ] ─▶ program
                              (no per-CGU content-addressing/reuse)
  • Wins: small programs or whole-program-optimizing builds where cross-function optimization across the entire program is the goal and partitioning would forfeit inlining/LTO opportunities — one artifact is simplest and enables maximal global opt.
  • Real system: classic whole-program compilers and LTO builds (GCC -flto, LLVM ThinLTO is the partitioned counter-evolution); single-.o outputs from a batch compiler.
  • Rejected because: it destroys the codegen-layer incremental win — any edit re-emits the whole program, blowing the §4 warm-rebuild SLO — and forfeits the content-addressed dedup that lets unchanged CGUs be reused verbatim (§8.7) and that doubles as a fixpoint enabler (MM7). Bounded, content-addressed CGUs (ADR-13, §20) are the deliberate choice; whole-program opt (GVN/LICM) is separately deferred (§19).
