In one paragraph

This is a clustered service that accepts "run this later" and "run this on a schedule" requests (delayed, CRON, fixed-interval and one-shot), writes each one to disk before confirming it, holds the pending ones in a bucketed in-memory clock face split across nodes, and hands them to workers when their time comes (§1). It promises that a schedule is committed exactly once but that execution may happen more than once, and it never blurs the two (§1, MM6). Targets: schedule ingest p95 under 12 ms and dispatch p99 under 150 ms (§4). Platform and SRE teams run it as a Kubernetes deployment of 3 to 15 nodes with an etcd quorum (§1).

The problem, concretely

A tenant asks for "fire this callback every hour on the hour". The naive answers each break in a way the blueprint names. Keep timers only in one process's memory and a crash between the acknowledgement and durability silently loses the timer (P1, §3). Run a local cron on every host and nothing stops duplicate or lost runs when a host is replaced (§34 Alt D). Run one central process and its single write path becomes the ceiling (§34 Alt A). Add more nodes without strict ownership and two nodes can race the same timer and dispatch it twice (P3, FM-2).

Time itself is a second trap. If scheduling math reads the wall clock, an NTP step or a daylight-saving change makes timers fire early, late or immediately (P8, FM-8). A wall-clock time can occur twice on the night the clocks go back (§8). Thousands of tenants who all pick "on the hour" pile their timers into the same buckets and cause a burst of work in a single tick (§15.6).

Finally, a slow or broken callback target must not be able to damage the scheduler (P10), and a burst of load must produce a visible rejection instead of an unbounded queue and an out-of-memory crash (P4, MM4). The blueprint's structure is the answer to those pressures: log first, then wheel, one provable owner per shard, bounded queues, and a replayable log that can rebuild everything else (MM3).

How it works, end to end

Follow one schedule through the boxes of §3 (diagram adapted from §3):

Client SDKs (tenant callers, mTLS)                 -- trust boundary 1 (gRPC, protobuf)
  -> scheduler-api            stateless: auth + quota + idempotency
  -> timer-normalizer         CRON expand, TZ/DST, jitter (uses cron-parser)
  -> durable-log (WAL)        append-only, fsync-batched   -- persistence boundary
        durable ACK only after fsync
  -> shard-coordinator + lease-manager   <-- etcd lease + fencing tokens   -- ownership boundary
        -> wheel-engine (per shard)      expiration event
        -> replay-cli / replay path      crash or lease-transfer reconstruction
  -> dispatch-queue           bounded, shard-local          -- queue boundary
  -> execution-worker + retry-engine     gRPC / queue handoff   -- protocol boundary 2
  -> metrics-pipeline + tracing-layer    RED/USE, OpenTelemetry
  1. Ingress (scheduler-api) checks credentials, protobuf shape, tenant quota and the idempotency key. It holds no timer state, so it can be scaled or restarted freely (§3).
  2. Normalisation (timer-normalizer, cron-parser) turns every trigger kind into one canonical TriggerDefinition, resolves timezone, adds jitter, and rejects malformed schedules here, before they reach the log (§3, §14.1).
  3. Log (durable-log) appends the record, checksummed, and confirms only after fsync. No timer enters wheel memory before that confirmation (§3, I1, I6).
  4. Ownership (shard-coordinator, lease-manager) assigns each shard to one node using etcd leases and fencing tokens; a new owner must replay before it may dispatch (§3, I2, ADR-05).
  5. Wheel (wheel-engine) keeps the per-shard hierarchical timer wheel, advances it on a monotonic tick, moves timers between levels and emits an expiration event (§3, §15.2).
  6. Queue (dispatch-queue) holds executable tasks in a bounded shard-local queue (§3, ADR-24).
  7. Worker (execution-worker, retry-engine) runs the opaque callback, then acks or fails; failures go to retry or dead-letter. A worker crash cannot touch wheel or WAL state (§3, P10).
  8. Telemetry (metrics-pipeline, tracing-layer) emits RED/USE metrics and spans keyed on the immutable schedule_id (§3, P6, P11).

The blueprint's happy-path message sequence (§8) runs CreateSchedule, Append(ScheduleRecord), durable ack, RegisterTimer, InsertBucketEntry, ExpirationEvent(dispatch_id), Deliver(DispatchEnvelope), then Ack | Fail(reason) and finally Reschedule(next_attempt_at) or DeadLetter (§8).

The core ideas

Log first: acknowledge only what is on disk (§13, P1, I1, I6)

Plain version: the disk log is the truth and everything in memory is a copy that can be rebuilt (MM3). The log (write-ahead log, WAL) is split into fixed-size rotating segments with increasing segment IDs; each record has a header of length, crc32c and lsn (§13.2). The blueprint gives two sizes for that header: C6 says 16 B (length 4 B, crc32c 4 B, lsn 8 B), while §13.7 says about 20 B (§32, §13.7).

Many appends share one fdatasync call (fsync batching), with a window of at most 4 ms (§13.2). That window is one part of the ingest p95 budget: fsync window up to 4 ms, validation up to 3 ms, network round trip up to 5 ms, under 12 ms in total (§4). A 3-step trace from the blueprint's own state machine:

  1. CREATED: accepted by scheduler-api, not yet durable (§8).
  2. DURABLE: the fsync has returned; only now may the caller get its ACK, and only now may the wheel take the timer (§8, I1, I6).
  3. SCHEDULED: inserted into a wheel bucket. If the node crashes between 2 and 3, replay re-derives SCHEDULED from the DURABLE records (§8).

On open, a scanner walks a segment and truncates at the first bad checksum (§13.2). Because every record, not just the segment, carries a checksum, a torn batch describes itself (§13.6). Compaction writes a new segment ID and never edits in place (§13.8), and it must not drop a record still inside a tombstone's retention window (I12, §4: segment retention up to 7 days after the tombstone).

The hierarchical timer wheel: a clock face with coarse and fine rings (§15, MM1)

Plain version: instead of keeping all timers in one sorted list, drop each timer into a bucket, a slot for a range of ticks. Near timers sit in a fine low-level wheel; far timers sit in coarser levels and migrate downward as their deadline approaches (hierarchical timer wheel, §15.2). The tick advances every 10 ms from a monotonic source, never the wall clock (§15.2, P8). Insert and cancel are amortized O(1), where a binary heap is O(log n); at 2M timers per node the wheel wins, at low counts the heap's simplicity wins (MM1).

The mechanics, each from §15.2 unless noted:

  • A WheelBucket is one instance per (shard, level, slot) (§11), holding an intrusive linked list: the TimerRef nodes embed their own list pointers.
  • Lock striping: one mutex per bucket-group, not per bucket and not one global lock (I7, ADR-09).
  • A cancellation index maps schedule_id to bucket location, so cancel needs no bucket scan; the gate is under 1 ms p99 (§15.4).
  • A missed tick triggers a bounded catch-up sweep (I13), never an unbounded replay of all missed ticks, since that loop would itself stall (§15.6).
  • A timer beyond the top level's range waits in an overflow structure and is re-inserted as it approaches (§15.8).
  • Level count and slot count per level are fixed at startup; the blueprint does not give their values there (§15.2).

A 3-step trace using the blueprint's own failure case: thousands of tenants schedule "every hour on the hour" (§15.6). (1) Their timers land in the same coarse buckets. (2) At the level boundary they all migrate down in the same tick, a migration storm that shows up as a tick-latency spike at round timestamps (§15.6, fixtures/wheel/migration-storm.bin in §15.5). (3) The fix is jitter added at timer-normalizer, which spreads the correlated anchors (§15.6).

Lease fencing: turning "probably one owner" into "provably one owner" (§16, MM2, I2, I10, P12)

Plain version: a lease is a claim on a shard that expires unless renewed (etcd, §16.2). A lease alone is a soft signal, since the holder may be wrong about still holding it (MM2). So every claim also carries a fencing epoch, a number that strictly increases per shard (I10, P12). Every WAL append and wheel insert checks the caller's epoch against the coordinator's current one and rejects stale ones (§16.2).

A trace built from the blueprint's fencing fixture (§16.5) and I10, with symbolic epochs:

  1. Node A owns a shard at epoch n. A network blip makes A miss its renewals, and etcd's lease on A lapses (§16.6).
  2. The coordinator grants the shard to node B at a higher epoch. B must finish a replay-synchronization barrier before it accepts inserts (§16.2, I10).
  3. A, still believing it owns the shard, replays an old append at epoch n. The append boundary rejects it, and lease_fencing_rejections_total counts it (§16.5, I2). The fixture expects 100% rejection (§16.4).

Other rules: a rebalance moves one shard at a time (§16.2); concurrent transfers are capped by the 5K concurrent-replay budget (§16.7); and the minority side of a partition must stop dispatching even if it thinks its lease is valid (§16.8). The failover budget is under 15 s: lease TTL 10 s plus up to 5 s for token propagation (§4).

Scheduling is exactly-once, execution is at-least-once (§8, §17, MM6, P13)

Plain version: the system records "this schedule exists" once, but a delivery whose ACK is lost must be sent again, so a callback can run twice (MM6). The defence is a contract: DispatchEnvelope.dispatch_id plus attempt let any worker or downstream system recognise a redelivery (P13, §11).

States and moves (§8): CREATED -> DURABLE -> SCHEDULED -> DISPATCHED -> {ACKED, RETRY_PENDING}. RETRY_PENDING goes back to SCHEDULED or on to DEAD_LETTER when max_attempts is exhausted. Any pre-ACKED state may go to CANCELLED, and nothing leaves CANCELLED or DEAD_LETTER (§8, P14).

  • A missing ACK past its deadline (dispatch_ack_timeout_total) requeues the envelope with an incremented attempt (I11, §17.9). Attempt counts only increase (I4).
  • A late ACK for attempt N must not acknowledge the in-flight attempt N+1 (§17.8).
  • Retry spacing is Fixed, Exponential or ExponentialDecorrelated, with a jitter mode (§11, §17.2).
  • Dead-lettering must fire at exactly max_attempts, tested for 1, 3, 10 and 50 (§17.4).
  • A priority lane keeps retries from starving fresh dispatches (§17.2). Queues are bounded; at 110% of the 100K/s dispatch target, ingest returns RESOURCE_EXHAUSTED instead of running out of memory (§17.4, P4).

Deterministic replay: rebuild the same wheel every time (§18, P5, I5, MM5)

Plain version: the wheel is never saved directly; after a crash it is rebuilt by replaying the log, so the rebuild must give a bit-identical result on any node (P2, P5, I5, §15.10). Records are applied in strict LSN order (§18.2). To check, the replay computes a structural checksum, a hash of the rebuilt bucket contents and cancellation index, and compares it across independent runs (§18.2).

The classic bug is iterating a HashMap while rebuilding buckets, because Rust seeds hashing per process. The detection recipe: run replay twice with a randomised hash seed and diff the checksums; the symptom is a mismatch that appears only across processes (§18.6). The fix is an explicitly ordered structure (§18.6). Snapshots are immutable segments, not live heap dumps, because a heap dump carries allocator state that is neither portable nor deterministic (§18.2). A node whose checksum does not match is blocked from promotion (§18.9). Replay progress is tracked by a ReplayCursor of segment ID, byte offset and last applied LSN (§11). The speed target is 50M timers in under 90 s (§4).

CRON and daylight saving: compute local, store UTC (§14, P8)

Plain version: a CRON expression is five fields (minute, hour, day, month, weekday) in the POSIX grammar (§8, §14.2, Glossary). Each next fire time is computed in the schedule's declared IANA timezone and then converted to UTC for storage, never the reverse (§14.2). Daylight-saving edges get fixed rules (§14.2):

Situation Rule
Local time occurs twice (fall-back, a DST fold) resolves to the first occurrence, unless the schedule opts into skip-ambiguous
Local time does not exist (spring-forward gap) shifted forward to the next valid instant
Textually different but equal expressions canonicalised (*/1 becomes *, list fields sorted) so they hash identically for idempotency dedup

Malformed input such as */0 or out-of-range fields is rejected with a typed error at this boundary (§8, §14.5). Leap seconds are meant to be a non-event for monotonic scheduling math (§14.5). The February 29 policy (skip versus shift to March 1) must be documented, and the blueprint does not choose (§14.8). The blueprint says two things about the fold: §8 lists "timezone ambiguity during a DST fold" among malformed inputs rejected before they reach the wheel, and §14.10 lists tz-ambiguous as a rejection reason; while §14.2 resolves the fold by the first-occurrence rule and §14.5's fold fixtures expect deterministic resolution.

The trade-offs — where engineers disagree

Storage: a custom append-only WAL (ADR-04)

Chosen: a custom append-only WAL, because sequential IO has to sustain 250K inserts/sec, which exceeds SQLite's B-tree write path (§9). Rejected: embedded SQLite. When the rejected choice is right: a single-node embedded scheduler at under 1K inserts/sec, where operational simplicity beats raw throughput (§9).

Metadata and consensus: etcd (ADR-05)

Chosen: etcd, for operational simplicity, its native lease API and Kubernetes alignment, rather than a bespoke consensus layer (§9, §16.2). Rejected: ZooKeeper. When the rejected choice is right: an existing Kafka-heavy shop already running a hardened ZooKeeper quorum with in-house expertise (§9).

Concurrency: lock-striped shared state plus message passing (ADR-09)

Chosen: lock-striped state with message passing, for cache locality and lower per-timer overhead at 2M timers per node (§9, §15.2). Rejected: an actor per timer. When the rejected choice is right: low timer counts (under 10K), where per-actor isolation simplifies reasoning more than it costs in overhead (§9).

Time source: monotonic inside, wall clock for display (ADR-23)

Chosen: a monotonic clock for all scheduling math and the wall clock only for display, which avoids NTP-step misfires (§9, P8, MM7). Rejected: wall-clock-only scheduling. When the rejected choice is right: a human-facing calendar UI, where the monotonic/wall split adds needless complexity (§9).

Overload: bounded queues with upstream 429 (ADR-24)

Chosen: bounded shard-local queues that signal upstream with 429 / RESOURCE_EXHAUSTED, so a burst is a visible rejection and not an out-of-memory collapse (§9, P4, MM4). Rejected: unbounded in-memory queues. When the rejected choice is right: a bounded-load batch job with a known, small upper bound on enqueue volume (§9).

Language: Rust (ADR-01)

Chosen: Rust, for deterministic ownership and no GC jitter against the p99 dispatch budget (§9, §1). Rejected: Go and Java. When the rejected choice is right: Go, for a small internal tool where team velocity outweighs tail latency, such as a low-QPS internal batch trigger (§9).

Roads not taken (§34, §35)

Centralized single-wheel coordinator (§34 Alt A): one active wheel with a hot standby. It wins below 100K timers where one process is easier to run than a sharded cluster; Quartz's JDBC-clustered mode is the embodiment. It is rejected because it does not meet the 2M-timers-per-node x N-node target, and its single write-contention point becomes the ceiling long before the throughput targets are reached (§34, §4, §28, §29).

Global binary-heap priority queue (§34 Alt B): O(log n) insert and cancel behind one lock. It wins below 100K timers, where heap operations are cheap; libuv's timers are the example. It is rejected because the global lock recreates the contention that sharding removes (§34, MM8).

Fully consensus-replicated per-timer state (§34 Alt C): a Raft round per append. It wins when a compromised coordinator is an explicit threat and durability must survive Byzantine behaviour, such as in regulatory or adversarial-tenant settings. It is rejected because the extra round trip breaks the ingest latency budget for a guarantee the threat model does not require (§34, §22, §4).

Push-based host-local timers (§34 Alt D): independent cron on every host. It wins where each host's schedule is genuinely independent, with no failover or cross-host dedup; systemd timers and classic cron are the examples. It is rejected because it cannot prevent duplicate or lost execution when a host is replaced (§34, §1).

Deferred features (§35) each name a trigger for un-deferring: calendar-aware scheduling when tenants need business-day recurrence; region-aware replication when multi-region availability exceeds single-cluster RTO/RPO; Byzantine-resistant consensus when the threat model changes; graduated quota tiers when billing needs them; adaptive wheel resizing when occupancy histograms show sustained bucket starvation; WASM execution hooks once a runtime preserving P10 exists; and replay or schedule federation once a cross-cluster transport and consensus decision is made (§35).

What must never be false

  • I1: durable schedules are never lost after ACK. Noticed by replay reconciliation audits; durability_gap_total (§7).
  • I2: a shard has exactly one active owner at any instant. Noticed by a fencing-token mismatch on append; lease_fencing_rejections_total (§7).
  • I3: dispatch order inside a bucket is stable across replay. Noticed by replay divergence checksums; replay_checksum_mismatch_total (§7).
  • I4: retry attempts only increase per schedule. Noticed by duplicate retry-sequence alarms; retry_attempt_regression_total (§7).
  • I5: replaying a WAL prefix gives identical wheel state on any node. Noticed by cross-node checksum comparison; replay_divergence_total (§7).
  • I6: no timer enters the wheel before WAL durability. Noticed by a pre-insert durability-flag check; undurable_insert_rejected_total (§7).
  • I7: a WheelBucket is mutated by one thread at a time. Noticed by lock-contention profiling; bucket_lock_wait_ns (§7).
  • I8: schedule_id values are never reused. Noticed by an ID-collision assertion in the conformance suite; schedule_id_collision_total (§7).
  • I9: a tombstoned schedule cannot be re-inserted. Noticed by a tombstone-index lookup on every insert; tombstone_reinsert_blocked_total (§7).
  • I10: fencing epochs strictly increase per shard. Noticed by an epoch-regression check on lease grant; lease_epoch_regression_total (§7).
  • I11: dispatch envelopes are delivered at-least-once, never silently dropped. Noticed by a missing-ack timeout scan; dispatch_ack_timeout_total (§7).
  • I12: compaction never removes a record still inside a tombstone retention window. Noticed by a pre-compaction retention audit; compaction_retention_violation_total (§7).
  • I13: tick advancement never skips a bucket, even under jitter. Noticed by tick-gap detection; wheel_tick_gap_total (§7).
  • I14: tenant quota consumption never decreases within a billing window without an explicit reset. Noticed by a quota-ledger reconciliation job; quota_ledger_drift_total (§7).

The checking method is a deterministic simulator that injects crashes, partitions and clock skew under one logical clock, with exactly one assertion for exactly one invariant per run (§7).

What breaks in production

  • FM-1: WAL corruption. Symptom: a checksum mismatch on read, from bit-rot or a torn write on power loss. Detection: the corruption scanner's CRC32C check when a segment opens. Recovery: automatic truncation at the first bad record and resume from the last good LSN; manually, restore from a replica or backup segment (§23, §13.9).
  • FM-2: split-brain shard ownership. Symptom: the same schedule_id dispatched by two nodes. Root cause: an asymmetric partition defeating a naive lease-expiry check. Detection: a fencing-token mismatch at WAL append. Recovery: the append is rejected; operators force lease revocation and replay the shard onto the sole owner (§23, I2, I10).
  • FM-3: queue saturation. Symptom: a dispatch-latency spike and 429s at ingest, when queue depth exceeds its bound under a burst. Detection: a dispatch_queue_depth alert. Recovery: backpressure to scheduler-api; manual quota adjustment for the offending tenant (§23, P4).
  • FM-5: replay divergence. Symptom: a structural-checksum mismatch across replay runs, caused by nondeterministic iteration in the replay path. Detection: replay_divergence_total. Recovery: the promotion gate blocks the divergent node; restore from the last known-good immutable segment (§23, I5, §18.6).
  • FM-7: poison-message accumulation. Symptom: the retry backlog dominated by one schedule_id whose callback target keeps failing. Detection: retry backlog by classification. Recovery: automatic dead-letter at max_attempts, then tenant notification (§23, P7).
  • FM-8: clock-skew misfire. Symptom: timers fire early or late against wall-clock expectation, from an NTP step or drift. Detection: a clock-skew alarm on the monotonic-to-wall offset. Recovery: none automatic; the impact is display-only if P8 held everywhere, otherwise audit for the wall-clock read that bypassed it (§23, P8).
  • FM-12: compaction data loss. Symptom: a tombstoned record resurrected, or a referenced record missing, after compaction removed a record inside its retention window. Detection: compaction_retention_violation_total. Recovery: the pass aborts at the retention audit; if it had already finished, restore the segment from a pre-compaction backup (§23, I12).

Threats worth knowing (§22):

  • T1 replay of a captured request, answered by nonce and TTL-bound idempotency-key validation.
  • T2 resource exhaustion through a pathological CRON string, answered by bounded parser recursion and a fuzz-hardened grammar (ADR-14).
  • T4 lease poisoning, where a compromised node writes to etcd to open a dual-ownership window, answered by etcd RBAC, mTLS and fencing tokens (I2, I10).
  • T9 a compromised callback target probing the internal network, answered by the address-space isolation boundary (P10); worker_isolation_violation_total must stay zero.
  • T10 quota bypass through a check-then-act race, answered by atomic check-and-increment and a durable ledger (I14).

How it compares

  • Kafka delayed-operation purgatory keeps its timing wheel in-process over a partition's in-memory requests, with no durable per-timer record. That is fine for request-completion watchdogs that are not business schedules (§31).
  • Netty HashedWheelTimer gives up all durability for the lowest single-process latency with one flat wheel. That suits any JVM service needing sub-millisecond in-process timeouts (§31).
  • Kubernetes CronJob controller polls and reconciles instead of ticking a wheel. That is fine when minute granularity is acceptable and the Kubernetes control plane is the desired source of truth (§31).
  • Temporal scheduler folds timers into full workflow-history replay. That fits when the timer is one step of a larger durable workflow that already needs history replay (§31).
  • Quartz Scheduler coordinates a cluster through JDBC row locks instead of a lease and fencing service. That fits a JVM shop with a robust RDBMS that does not want to operate etcd or ZooKeeper (§31).
  • systemd timers are scoped to one host with no clustering at all. That fits host-local maintenance timers, where distributed coordination is pure overhead (§31).

Questions to test yourself

  1. Why does exactly-once scheduling commit (§1, §7) not imply exactly-once execution (§17), and what mechanism in §11's DispatchEnvelope and §17's retry-engine prevents callers from assuming otherwise? — Hint: MM6, P13 and §17.8.
  2. How does the deterministic-replay requirement (§7's I5, §18) constrain the concurrency primitives allowed in the wheel engine (§15), and why would a lock-free hash-based bucket index violate it? — Hint: §18.6 on hash iteration order, and I7 with §15.2.
  3. How does the monotonic-clock principle (§6's P8) interact with the DST-fold handling in §14, and what would break in §18's replay path if that boundary were crossed even once? — Hint: §14.2, ADR-23 and MM7.
  4. Why must compaction (§13) respect the tombstone retention window (§7's I12) even though it delays reclaiming disk space that §4's storage-growth budget wants back quickly? — Hint: P14, §13.8 and FM-12.
  5. How does §32's C5 capacity derivation (555K timers/sec required replay throughput) constrain the segment-sizing decisions made in §13, and what happens to §4's RTO budget if that throughput target is missed? — Hint: §4 recovery rows and §18.7.

If you only remember three things

The log is the database: nothing is acknowledged before fsync and every in-memory structure, the wheel included, is a cache that replay can rebuild bit-for-bit (P1, MM3, I5). A lease says who probably owns a shard, and only the fencing epoch checked at the write boundary makes that ownership provable (MM2, I2). The system promises exactly-once scheduling but at-least-once execution, so bounded queues, attempt counters and a dispatch_id contract carry the rest (MM6, P13, P4).

Words used here

  • Timer wheel: a bucketed structure indexing timers by expiration tick, across several coarse-to-fine levels.
  • WAL (write-ahead log): the append-only durable record of every schedule change, the source of truth.
  • Segment: a fixed-size rotating unit of the WAL with a monotonic ID.
  • Fsync: the call that confirms data is physically on disk before returning.
  • Lease epoch / fencing token: a number that rises on every ownership change; stale holders are rejected by it.
  • Shard: a slice of the timer keyspace owned by exactly one node at a time.
  • Dispatch envelope: the record carrying one execution attempt to a worker.
  • Dead letter: the terminal state for a schedule that used up all its retries.
  • Monotonic clock: a clock that only moves forward, immune to NTP steps and daylight saving.
  • Replay cursor: a checkpoint of replay progress (segment ID, byte offset, last applied LSN).
  • Structural checksum: a hash of rebuilt in-memory state, used to prove replay is deterministic.
  • DST fold: the repeated hour when clocks go back, so one local time occurs twice.
