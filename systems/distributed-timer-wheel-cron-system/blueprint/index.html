204 — Distributed Timer Wheel / CRON System

Project Number: 204

Project Name: Distributed Timer Wheel / CRON System

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition: a clustered scheduling runtime that accepts delayed and recurring (CRON, fixed-interval, one-shot) execution requests, durably persists them before acknowledgement, holds them in a hierarchical timer-wheel index sharded across nodes by lease-fenced ownership, and dispatches them to workers with bounded, observable retry — providing exactly-once scheduling at the coordinator and at-least-once execution at the worker, never conflating the two guarantees.

The system executes delayed tasks, recurring CRON schedules, and fixed-interval triggers with durable persistence, multi-tenant isolation, deterministic replay, shard-aware timer ownership, and observability-first operation as first-class requirements, not retrofits.

Phase 0 deliverable — the following crates/services must compile, link, and pass the integration harness before Phase 1 begins:

  1. scheduler-api — stateless gRPC ingress, auth, quota, idempotency-key handling.
  2. timer-normalizer — canonicalizes CRON/delayed/interval definitions into descriptors.
  3. cron-parser — parser-combinator grammar for CRON expressions, DST-aware.
  4. wheel-engine — hierarchical timer wheel, bucket advancement, migration.
  5. shard-coordinator — lease-fenced timer-partition ownership.
  6. lease-manager — etcd lease integration, fencing token issuance.
  7. durable-log — append-only WAL, segment rotation, checksums.
  8. dispatch-queue — bounded shard-local delivery queues, priority, poison routing.
  9. execution-worker — worker runtime, callback/queue handoff execution.
  10. retry-engine — backoff policy, retry classification, dead-letter routing.
  11. metrics-pipeline — RED/USE metric emission and aggregation.
  12. tracing-layer — OpenTelemetry span correlation across the dispatch path.
  13. replay-cli — operator tool to replay WAL segments into wheel state.
  14. admin-console — read-only operational inspection surface.
  15. conformance-suite — cross-crate fixture-driven correctness harness.

System boundary — provides: API ingress, timer normalization, CRON parsing, WAL persistence, shard ownership, wheel scheduling, dispatch queues, execution acknowledgement, retry orchestration, metrics/tracing, replay tooling, an operational control plane.

System boundary — delegates: actual business-logic execution (callback targets are opaque to the scheduler), network transport security to mTLS termination, metadata quorum consensus to etcd/Raft rather than a bespoke consensus implementation, container orchestration to Kubernetes.

System boundary — does NOT provide: general workflow/DAG orchestration, BPM semantics, distributed transaction coordination, stream processing, general message brokering, embedded scripting or user-defined plugin execution in Phase 0, cross-region active/active replication.

Non-goals: this is not Temporal, not Airflow, not a Kafka replacement. It schedules and dispatches; it does not orchestrate multi-step business workflows or guarantee exactly-once execution (only exactly-once scheduling commit).

Deployment model: Kubernetes-based clustered deployment, 3–15 nodes, replicated metadata quorum (etcd, 3 or 5 members), horizontally scalable stateless workers, durable NVMe-backed WAL volumes per coordinator node.

Target operators: platform teams, infrastructure/SRE groups, internal developer platforms, SaaS control-plane teams, multi-tenant backend services needing durable scheduling as a primitive rather than building it atop a general broker.

Later phases unlock: calendar-aware scheduling (business calendars, holiday exclusion), region-aware replication, tenant-level quota tiers, adaptive wheel resizing, WASM execution hooks, deterministic replay snapshot federation, schedule federation across clusters.

Recommended language: Rust. Rationale: deterministic ownership semantics eliminate GC-induced dispatch jitter that directly violates the p99 dispatch-latency budget in §4; memory safety under concurrency matters because the wheel engine and dispatch queues are lock-striped and touched by dozens of worker threads; the async ecosystem (Tokio) provides mature timer/IO primitives; explicit Result-based error handling suits a long-running infrastructure daemon where silent failure is unacceptable. Rejected: Go — GC pauses interact badly with p99 dispatch-latency targets and its channel-based concurrency model is a weaker fit for lock-striped intrusive wheel structures; Java — JVM warm-up, GC pause tails, and the additional operational surface of a JVM runtime conflict with the crash-only-recovery design principle (P9) and bounded-memory targets in §4.

Prerequisites: distributed systems fundamentals, lock-free/lock-striped concurrency, async runtimes (Tokio reactor model), Linux networking, CRON grammar and timezone semantics, storage-engine internals (WAL, LSM), consensus systems (Raft, lease-based ownership), WAL design, timer-wheel scheduling algorithms, distributed tracing, queueing theory.

Estimated timeline: Phase 0 MVP — 10–12 weeks. Production hardening (through Phase 9) — 4–6 months. Multi-region evolution (deferred features in §35) — 9–14 months beyond that.

2. Why Build This

This project teaches hierarchical timer-wheel design, lease-based distributed ownership, deterministic replay systems, durable scheduling semantics, distributed failover coordination, persistence/index co-design, operational observability engineering, and scheduler correctness validation — skills that generalize to any system that must fire something at a point in time, at scale, without losing it.

Historically relevant systems: Kafka delayed-operation purgatory, Linux timerfd/kernel timer-wheel internals, Netty HashedWheelTimer, Quartz Scheduler, Kubernetes CronJob controller, Temporal's scheduling subsystem, Apache Airflow's trigger mechanics. Each solved a slice of this problem; none solved all of it in one coherent runtime — that synthesis is the point of this blueprint.

Engineering muscles developed: concurrency debugging under lock striping, low-latency scheduling, clock-synchronization handling (monotonic vs wall-clock, DST, leap seconds), failure-recovery design, distributed ownership coordination, queue-pressure management, backpressure propagation, replayability engineering.

Production concepts exercised: WAL recovery, shard balancing, lease fencing, retry isolation, poison-queue handling, tracing correlation, p99 tail-latency reduction, idempotent dispatch.

Related projects: distributed log engines (Kafka, Pulsar), Raft consensus implementations (etcd, TiKV), stream-processing runtimes, queue brokers, kernel timer subsystems, distributed tracing stacks (Jaeger, Tempo), durable task-orchestration engines (Temporal, Cadence).

Calibration value: implementing this system requires combining storage, networking, scheduling, distributed coordination, and observability into one coherent runtime. Engineers completing it become fluent in deterministic recovery, race containment, latency collapse diagnosis, shard movement, and replay-safe distributed execution — the exact competencies a platform-infrastructure interview probes for and that production incident response demands.

What Mastery Looks Like

  • Can explain why hierarchical timer wheels give amortized O(1) insert/cancel vs a binary heap's O(log n), and when the heap still wins — demonstrated in §14 and §31.
  • Can design a WAL segment format with checksums, rotation, and replay cursors that survives torn writes and power loss — demonstrated in §13.
  • Can reason about lease fencing tokens as the mechanism that turns "probably one owner" into "provably one owner," and can name the split-brain window it closes — demonstrated in §16.
  • Can distinguish exactly-once scheduling commit from at-least-once execution and explain why conflating them causes duplicate side effects — demonstrated in §12 and §17.
  • Can build a deterministic replay engine where WAL-order equals wheel-state equality across runs, and can name the nondeterminism sources that break it (thread scheduling, hash iteration order, wall-clock reads) — demonstrated in §18.
  • Can design backpressure propagation from dispatch queue through worker pool back to the API ingress without an OOM collapse — demonstrated in §17 and §29.
  • Can instrument a distributed scheduler with RED/USE metrics and trace-correlated spans sufficient to diagnose dispatch-lag incidents without reading source — demonstrated in §19.

scheduler-api — authenticated schedule ingestion, protobuf schema validation, quota enforcement, idempotency-key deduplication, tenant isolation. Stateless: it owns no timer execution state and can be scaled/restarted freely.

timer-normalizer / cron-parser — transforms CRON definitions and delayed schedules into canonical TriggerDefinition descriptors. Handles timezone normalization, recurrence bounds, jitter insertion, malformed-schedule rejection at the boundary rather than downstream.

durable-log — the WAL is the sole source of truth for schedule durability (P1). Every mutation is append-only, checksummed, and fsync-confirmed before the caller receives an ACK. No timer enters wheel memory before WAL durability confirmation (I1).

shard-coordinator + lease-manager — assigns timer partitions to scheduler nodes via etcd-backed lease fencing. Ownership changes require replay synchronization and fencing-token advancement before the new owner may dispatch (I2, ADR-05).

wheel-engine — maintains per-shard hierarchical timer wheels: low-latency expiration detection, bucket advancement on a monotonic tick source, timer migration between wheel levels, dispatch enqueueing. This is the concurrency-critical hot path (§14).

Replay path (replay-cli, replay module inside shard-coordinator) — reconstructs wheel state after crash recovery or lease transfer by replaying WAL records into deterministic in-memory structures (I5, §18).

dispatch-queue — bounded, shard-local queues buffering executable tasks awaiting worker delivery; carries retry metadata and poison classification (ADR-24).

execution-worker + retry-engine — executes external callbacks or queue handoffs. Workers are isolated from scheduling correctness: a worker crash cannot corrupt wheel or WAL state (P10).

metrics-pipeline + tracing-layer — every state transition emits structured telemetry; all timers are trace-correlated using immutable schedule_ids (P6, P11).

6. Design Principles

  • P1 — Durability Before Visibility. Rule: no schedule is acknowledged to a caller before WAL fsync confirms the append. · Tradeoff: adds fsync-batch latency to the ingest path. · Operational: durability_gap_total must stay at zero. · Violated: silent timer loss on crash between ACK and durability.
  • P2 — Replayability First. Rule: every state mutation must be reconstructible purely from WAL records. · Tradeoff: forbids any wheel-only mutation path; all writes route through the log first. · Operational: replay-divergence checksum audits run continuously. · Violated: crash recovery produces a different wheel state than pre-crash, breaking I5.
  • P3 — Bounded Memory Ownership. Rule: every timer belongs to exactly one shard owner at any instant. · Tradeoff: requires lease coordination overhead on every ownership change. · Operational: shard-ownership dashboards flag any timer with zero or >1 claimed owner. · Violated: duplicate dispatch from two nodes racing the same timer.
  • P4 — Backpressure Everywhere. Rule: queue saturation at any stage propagates a signal upstream rather than buffering unboundedly. · Tradeoff: callers see 429/RESOURCE_EXHAUSTED under load instead of silent queueing. · Operational: dispatch-queue depth gauges gate ingest admission. · Violated: unbounded buffering leads to OOM collapse under load spikes.
  • P5 — Deterministic State Machines. Rule: replay of the same WAL prefix must produce bit-identical wheel state on any node. · Tradeoff: forbids non-deterministic constructs (hash-map iteration order, wall-clock reads) inside the replay path. · Operational: replay checksum matches across three independent replay runs in CI. · Violated: split-brain recovery diverges silently.
  • P6 — Observability by Default. Rule: every dispatch is trace-correlated by an immutable schedule_id; no opt-out. · Tradeoff: telemetry cardinality cost on every hot-path transition. · Operational: 100% trace-span coverage on dispatch path, verified in §19. · Violated: incident response has no causal trail from expiration to execution.
  • P7 — Explicit Failure Semantics. Rule: every retry is classified (transient, poison, exhausted) and the classification is externally observable. · Tradeoff: retry-engine must carry classification state, not just a counter. · Operational: retry backlog broken down by classification in dashboards. · Violated: poison messages retry forever, starving healthy dispatch.
  • P8 — Clock Skepticism. Rule: all internal scheduling math uses monotonic clocks; wall-clock reads are confined to user-facing timestamp translation. · Tradeoff: requires maintaining a monotonic-to-wall-clock offset table for display. · Operational: clock-skew alarms fire when NTP drift exceeds the wheel tick granularity. · Violated: wall-clock jumps (NTP step, DST) cause spurious immediate or delayed firing.
  • P9 — Crash-Only Recovery. Rule: nodes must recover correctly from abrupt termination (SIGKILL-equivalent) with no graceful-shutdown-dependent invariant. · Tradeoff: forbids relying on in-memory-only cleanup logic; everything durable must be crash-consistent. · Operational: chaos tests kill nodes mid-write and assert replay correctness. · Violated: a "clean shutdown assumption" bug only manifests under real outages, in production.
  • P10 — Isolation of Scheduling and Execution. Rule: worker failures must not corrupt scheduling state; the worker pool has no write path into the WAL or wheel. · Tradeoff: requires an indirection layer (dispatch-queue) between wheel and worker rather than direct invocation. · Operational: worker crash-loop alarms are independent of scheduler-health alarms. · Violated: a buggy callback handler taking down the coordinator process.
  • P11 — Immutable Identifiers. Rule: schedule_id values (UUIDv7) are never recycled or reassigned. · Tradeoff: requires a monotonic, collision-resistant ID generator rather than reusing small integers. · Operational: trace and metric correlation depends on ID stability across retries and replay. · Violated: two unrelated schedules sharing telemetry history, corrupting audit trails.
  • P12 — Lease Fencing Required. Rule: every shard-ownership claim carries a monotonically increasing fencing epoch; stale epochs are rejected at the WAL-append boundary. · Tradeoff: adds one comparison and one write per append on the hot path. · Operational: fencing-token-mismatch counters must be non-zero only during expected transfers. · Violated: a stale former owner double-dispatches after losing its lease.
  • P13 — Idempotent Dispatch Contract. Rule: DispatchEnvelope.dispatch_id plus attempt must let any worker or downstream system deduplicate a redelivered dispatch. · Tradeoff: pushes idempotency responsibility partly onto callback targets via a documented contract. · Operational: duplicate-execution-rate SLI tracks contract violations. · Violated: at-least-once redelivery causes duplicate side effects downstream.
  • P14 — Tombstones Are Terminal. Rule: a cancelled (CANCELLED) or dead-lettered (DEAD_LETTER) schedule's tombstone record is never un-written; reactivation requires a new schedule_id. · Tradeoff: cannot "resurrect" a cancelled schedule in place; must recreate. · Operational: compaction must never reclaim a tombstone before its retention window (§4) expires. · Violated: a compacted-away tombstone lets a stale replica resurrect a cancelled timer.

Debugging methodology: correctness is validated with a deterministic simulator (conformance-suite) that drives the wheel-engine and durable-log through scripted fault injection (crash, partition, clock skew) under a single logical clock, with exactly one assertion checking exactly one invariant (I1–I14) per simulation run — never a bundled assertion covering multiple invariants, since a bundled failure obscures which invariant broke and turns triage into a search problem instead of a lookup.

8. Domain Model — Schedule, Trigger, and Dispatch Entities

Core entity graph:

  • Schedule
    • ├── schedule_id (UUIDv7, immutable, P11)
    • ├── tenant_id (TenantId)
    • ├── trigger (TriggerDefinition: DELAYED | CRON | FIXED_INTERVAL | ONE_SHOT)
    • ├── next_fire_at (Timestamp, monotonic-derived)
    • ├── retry_policy (RetryPolicy)
    • ├── execution_target (opaque callback/queue reference)
    • └── metadata (tenant-defined key/value, bounded size)

Trigger types: DELAYED (fire once, N ms from now), CRON (POSIX five-field expression, timezone-aware), FIXED_INTERVAL (fire every N seconds from an anchor), ONE_SHOT (fire at an absolute timestamp).

Timer state machine:

State Meaning
CREATED accepted by scheduler-api, not yet durable
DURABLE WAL-fsync confirmed (I1, I6 gate)
SCHEDULED inserted into wheel-engine bucket
DISPATCHED handed to dispatch-queue → worker
ACKED worker execution acknowledged
RETRY_PENDING retry scheduled by retry-engine (I4)
DEAD_LETTER permanently failed, poison-classified (P7)
CANCELLED tombstoned (P14, I9)

Valid transitions: CREATED→DURABLE→SCHEDULED→DISPATCHED→{ACKED, RETRY_PENDING}; RETRY_PENDING →SCHEDULED (rescheduled) or →DEAD_LETTER (attempts exhausted per RetryPolicy.max_attempts); any pre-ACKED state →CANCELLED. No transition ever leaves CANCELLED or DEAD_LETTER.

Canonical sequence (happy path):

Show the original text diagram
Client -> scheduler-api  : CreateSchedule(trigger, retry_policy)
scheduler-api -> durable-log : Append(ScheduleRecord)
durable-log -> scheduler-api : durable ack (fsync confirmed)
scheduler-api -> shard-coordinator : RegisterTimer(schedule_id)
shard-coordinator -> wheel-engine : InsertBucketEntry(WheelBucket, TimerRef)
wheel-engine -> dispatch-queue : ExpirationEvent(dispatch_id)
dispatch-queue -> execution-worker : Deliver(DispatchEnvelope)
execution-worker -> retry-engine : Ack | Fail(reason)

Malformed-input examples (rejected at timer-normalizer/cron-parser, never reach the wheel): invalid CRON step overflow (e.g. */0 or out-of-range field), timezone ambiguity during a DST fold (a wall-clock time that occurs twice), RetryPolicy with negative or zero backoff, expiration timestamps before the current monotonic epoch.

Failure-path examples (handled by the replay/failure machinery in §16, §18, §23): WAL durable but wheel-insertion crash before SCHEDULED transition (replay must re-derive SCHEDULED from DURABLE records), lease transfer mid-dispatch (new owner must not re-dispatch an already-ACKED envelope), duplicate replay after a split-brain window closes (idempotency-key and dispatch_id dedup absorb it).

11. Core Schema & Types

Signatures only — ownership / mutation / concurrency / persistence / serialization / compatibility annotated per type. All types live in common-types unless noted.

ScheduleRecord (struct)
  schedule_id: UuidV7
  tenant_id: TenantId
  trigger: TriggerDefinition
  next_fire_at: Timestamp
  retry_policy: RetryPolicy
  version: u64
  metadata: BoundedMap<String, String>

Ownership: owned by durable-log post-append; borrowed read-only by wheel-engine. Mutation: append-only — updates are new versioned records, never in-place edits (ADR-04). Concurrency: compare-and-swap on version for optimistic concurrency control. Persistence: canonical durable representation; every field is WAL-logged. Serialization: Protobuf v3 (ADR-06); schedule.proto. Compatibility: additive-only field evolution; version gates migration (§25).

TriggerDefinition (enum)
  Delayed(fire_in_ms: u64)
  Cron(expression: CronExpr, timezone: TzId)
  FixedInterval(period_ms: u64, anchor: Timestamp)
  OneShot(at: Timestamp)

Ownership: embedded in ScheduleRecord; no independent lifetime. Mutation: immutable once the parent ScheduleRecord is durable. Concurrency: none — read-only after normalization. Persistence: embedded WAL field. Serialization: Protobuf oneof. Compatibility: new variants are additive; unknown variants at old-node replay fail closed.

WheelBucket (struct)
  bucket_id: u64
  expiration_tick: u64
  timers: IntrusiveLinkedList<TimerRef>

Ownership: owned by wheel-engine, one instance per (shard, level, slot). Mutation: single-threaded per bucket (I7); lock-striped across buckets. Concurrency: mutex-per-bucket-group; no cross-bucket lock ordering needed. Persistence: none — reconstructed entirely by replay (P2). Serialization: never serialized directly; derived from ScheduleRecord replay. Compatibility: internal-only; not a wire type.

LeaseToken (struct)
  shard_id: u32
  epoch: u64
  owner_node: NodeId
  expires_at: MonotonicTime

Ownership: issued and owned by lease-manager; cached read-only by shard-coordinator. Mutation: epoch only increases (I10); no other field mutates post-issue. Concurrency: atomically swapped on renewal via etcd CAS. Persistence: source of truth is etcd lease revision, mirrored into durable-log on claim. Serialization: Protobuf; also etcd key-value encoding. Compatibility: epoch width (u64) must never shrink across versions.

DispatchEnvelope (struct)
  dispatch_id: Uuid
  schedule_id: Uuid
  attempt: u32
  deadline: Timestamp
  payload_ref: BlobPointer

Ownership: created by wheel-engine on expiration, owned by dispatch-queue until ACKed. Mutation: attempt increments on each retry-engine reschedule (I4); rest immutable. Concurrency: single-producer (wheel tick thread) per shard, multi-consumer (worker pool). Persistence: dispatch-queue-local durability (bounded), not full WAL durability. Serialization: Protobuf; carried over gRPC streaming to workers. Compatibility: attempt and dispatch_id are contract-stable for idempotency (P13).

RetryPolicy (struct)
  max_attempts: u32
  backoff_strategy: BackoffStrategy
  max_backoff_ms: u64
  jitter_mode: JitterMode
BackoffStrategy (enum) Fixed | Exponential | ExponentialDecorrelated
JitterMode (enum) None | Full | Decorrelated

Ownership: embedded in ScheduleRecord. Mutation: immutable once durable; changing retry policy creates a new versioned record. Concurrency: read-only, shared across retry-engine instances. Persistence: WAL-logged as part of ScheduleRecord. Serialization: Protobuf enum + scalar fields. Compatibility: new BackoffStrategy variants additive-only.

ShardAssignment (struct)
  shard_id: u32
  lease: LeaseToken
  key_range: HashRange

Ownership: owned by shard-coordinator. Mutation: replaced wholesale on rebalance, never partially edited. Concurrency: single-writer (coordinator leader path) via etcd watch. Persistence: etcd-backed; mirrored to durable-log for audit trail. Serialization: Protobuf. Compatibility: key_range encoding is stable across minor versions (§25).

ReplayCursor (struct)
  segment_id: u64
  byte_offset: u64
  last_applied_lsn: u64

Ownership: owned by the replay module inside shard-coordinator / replay-cli. Mutation: monotonically advances during replay; never rewinds except full restart. Concurrency: single-threaded per shard replay stream. Persistence: checkpointed periodically to durable-log for fast-restart. Serialization: Protobuf; also human-readable in replay-cli diagnostics. Compatibility: last_applied_lsn width fixed at u64 permanently.

TenantQuota (struct)
  tenant_id: TenantId
  max_active_timers: u64
  max_insert_rate_per_sec: u32
  window: QuotaWindow

Ownership: owned by scheduler-api quota-enforcement middleware. Mutation: updated via admin API, versioned like ScheduleRecord. Concurrency: atomic counters per tenant, sharded to avoid contention. Persistence: durable quota ledger (I14). Serialization: Protobuf. Compatibility: additive fields only; unknown fields ignored by older nodes.

TimerState (enum)
  Created | Durable | Scheduled | Dispatched | Acked
  RetryPending | DeadLetter | Cancelled

Ownership: derived, not stored independently — computed from ScheduleRecord + WAL history. Mutation: strictly forward per the transition table in §8; no field-level mutation. Concurrency: read via projection, never written directly. Persistence: implicit — reconstructable from WAL replay (P2). Serialization: Protobuf enum for API responses only. Compatibility: new terminal states are additive; existing transitions never change meaning.

AuditEvent (struct)
  event_id: Uuid
  tenant_id: TenantId
  actor: ActorId
  action: AuditAction
  at: Timestamp

Ownership: owned by the audit-logging subsystem (Phase 8). Mutation: append-only, never edited or deleted within retention window. Concurrency: append-only writer, no contention with scheduling hot path. Persistence: separate durable audit log, distinct from durable-log WAL. Serialization: Protobuf; exported to SIEM via structured JSON. Compatibility: AuditAction variants additive-only, for compliance-trail stability.

12.2 Detailed Implementation Steps

Create the Cargo workspace (Cargo.toml, rust-toolchain.toml pinning the exact toolchain per ADR-22 reproducibility). 12.3 Deliverable

A reproducible workspace build (cargo build --workspace --locked byte-identical across two CI runners) and an executable integration-test harness binary inside conformance-suite that other phases extend rather than replace.

12.4 Acceptance Criteria

Zero unsafe blocks outside crates/wheel-engine/src/bucket.rs (the one pre-approved lock-striping module). Trace IDs propagate across 100% of test RPCs in conformance-suite's smoke suite (≥ 50 fixture-driven cases).

12.6 Pitfalls

Nondeterministic timestamp injection into test fixtures (using SystemTime::now() inside a "deterministic" test breaks reproducibility) · root cause: forgetting the monotonic-clock discipline (P8) even in test code · debug via: grep CI logs for two runs with differing binary hashes, bisect by module · signal: cargo build --locked hash drift · recovery: inject a fake clock trait everywhere, ban SystemTime::now() outside one adapter. Unstable protobuf field ordering across protoc versions · root cause: unpinned protoc binary version · signal: serialization round-trip fixture mismatch · recovery: pin protoc version in CI container. Hidden panic propagation across tokio::spawn boundaries silently killing a task · root cause: missing panic hook · debug: panic = "abort" in test profile to surface it loudly · signal: a task silently stops emitting metrics · recovery: install a global panic hook that logs and increments a counter before any spawn.

12.7 Performance Concerns

Logging allocation pressure from unbuffered structured-log writers on the hot path (must be addressed before Phase 4's wheel tick loop exists, or it will look like a wheel problem later). Excessive tracing span cardinality from unbounded label values (tenant_id is fine; raw schedule metadata strings are not) — bound label cardinality now, in the shared tracing-layer, rather than retrofitting per-crate later.

12.8 Edge Cases

Missing config overrides falling back silently to defaults instead of failing fast — must error, not default, for any budget-affecting value in §4. Partially upgraded nodes in a mixed CI matrix (one runner on stale toolchain) producing a false-positive reproducibility failure — pin the toolchain via rust-toolchain.toml before this can even be tested meaningfully.

12.9 Failure Analysis

CI drift causing incompatible binaries across nodes in a rolling deployment: detection is the SHA-256 mismatch check in 12.4; blast radius is cluster-wide if an incompatible binary reaches production, since Protobuf schema drift (before §25's compatibility gates exist) could silently corrupt cross-node RPC; containment is a CI gate that blocks merge on hash mismatch; recovery is re-pinning the toolchain and rebuilding from a known-good commit; operator visibility is a build_provenance label surfaced in every emitted metric (12.10).

12.10 Operational Notes

Metric: build_provenance label (git SHA + toolchain version) attached to every metric series emitted by every crate from this phase forward — this is how an operator distinguishes "node running old code" from "node hitting a real bug" during a rolling upgrade. Structured-log field: trace_id present on every log line from tracing-layer, no exceptions. Deployment: none yet (Phase 0 produces no deployable service). Migration: N/A — this phase defines the baseline schema version (v1) that §25 versioning rules apply against.

13. Phase 1 — WAL and Durable Persistence

13.1 Objectives

Implement the append-only durability pipeline (durable-log) that is the sole source of truth for schedule durability (P1, I1). Scope: segment rotation, checksummed records, fsync batching, corruption detection, sparse index, replay cursors, tombstones, compaction markers. Constraint introduced: nothing downstream (wheel, dispatch) may treat a record as real until this crate confirms fsync.

13.2 Detailed Implementation Steps

Implement crates/durable-log/src/segment.rs: fixed-size rotating segments with a monotonically increasing segment ID and a per-record header (length, crc32c, lsn). Implement checksum.rs: CRC32C per record plus a segment-level trailer checksum, following the LSM-tree tombstone/compaction vocabulary of O'Neil et al. (1996). Implement fsync batching: group N pending appends behind one fdatasync call, bounded by the p95 ingest-latency budget in §4 (< 12 ms) — batch window must not exceed 4 ms (ADR-04). Implement a corruption scanner that walks a segment on open and truncates at the first bad checksum (crash-consistency, per Petrov (2019) ch. 3). Implement a sparse index ((schedule_id) -> (segment_id, offset)) for O(1)-ish lookup without a full scan. Implement ReplayCursor (§11) advancement and periodic checkpointing. Implement tombstone semantics (P14, I9, I12) and compaction markers that respect the retention window from §4. Anchor: I1, I6, ADR-04.

13.3 Deliverable

A durable append/replay engine: cargo run -p durable-log --example append_bench appends and fsyncs records at the target rate; a companion replay path reconstructs identical in-memory state from any prefix of segments.

13.4 Acceptance Criteria

Survives a power-interruption simulation (SIGKILL mid-append, 500 iterations) with zero non-recoverable corruption. Replay is byte-identical across 3 independent replay runs on the same segment set (I5). Corruption detection catches 100% of single-bit-flip injections in fixtures/wal/crc-mismatch.bin (≥ 200 injected cases). WAL amplification measured at < 1.8x per §4.

13.5 Conformance Fixtures

fixtures/wal/truncated-segment.bin — segment cut mid-record, expects clean truncation-point detection, not a panic. fixtures/wal/crc-mismatch.bin — single-bit-flip corruption, expects rejection at the corrupted record and successful replay of everything before it. fixtures/wal/replay-ordering.bin — interleaved-append-order regression fixture, expects identical replay order across runs. fixtures/wal/wal-gap-detection.bin — a missing LSN in sequence, expects a gap alarm rather than silent skip.

13.6 Pitfalls

Partial page writes on power loss leaving a record half-written but checksum-passing on a stale page-cache read · root cause: not fdatasync-ing before considering a write durable · debug via fault-injection at the syscall layer · signal: replay divergence only under real power-loss testing, never in normal CI · recovery: never trust a write durable until fsync returns. Torn fsync windows where batching groups writes but the process crashes between two appends in the same batch · root cause: assuming the whole batch is atomic · signal: some records in a batch replay, others don't · recovery: per-record checksums make torn batches self-describing — this is why every record, not just the segment, is checksummed. Replay duplication when a checkpoint is taken but not fsynced before a crash · root cause: checkpoint observability didn't wait for its own durability · signal: replay_divergence_total fires lower than expected on restart · recovery: checkpoint writes go through the same fsync gate.

13.7 Performance Concerns

Syscall batching (fdatasync grouping) trades latency for throughput — tune the batch window against the p95 ingest budget, not just raw throughput. mmap fragmentation if segments are memory-mapped for read without a compaction pass bounding live segment count. IO amplification from record headers (length + crc32c + lsn ≈ 20 B overhead) — verified against the < 1.8x target in §4 and re-derived in C6 (§32).

13.8 Edge Cases

Replay while a compaction pass is in flight (must not read a segment mid-rewrite — compaction writes to a new segment ID, never in place). WAL gap detection when a segment file is missing entirely from disk (operator deleted it) versus merely truncated — different alarms, different recovery paths.

13.9 Failure Analysis

Checksum-mismatch handling: detection is per-record CRC32C validation on read; blast radius is bounded to the single corrupted record plus any records after it in the same segment (replay stops there); containment is the corruption scanner truncating at the first bad checksum; recovery is replay from the last good LSN plus operator-triggered re-sync from a replica if one exists; operator visibility is wal_corruption_detected_total plus the affected segment ID in the alert payload.

13.10 Operational Notes

Metrics: segment_age_seconds (oldest un-compacted segment), wal_append_latency_ms histogram, wal_amplification_ratio gauge. Tracing span: wal.append wrapping each fsync batch. Structured-log fields: segment_id, lsn, crc32c on every append/replay log line. Deployment: NVMe-backed volume required (§4); rollback requires replaying the previous segment format if ADR-04's binary layout ever changes (must be additive per §25).

14. Phase 2 — CRON Parsing and Normalization

14.1 Objectives

Build deterministic schedule normalization (cron-parser, timer-normalizer): parse POSIX five-field CRON grammar, resolve timezone/DST ambiguity, canonicalize into TriggerDefinition. Scope excludes calendar-aware business-day scheduling (deferred, PhaseDeferred("§14"), §35). Constraint: no malformed schedule may reach durable-log — rejection happens here.

14.2 Detailed Implementation Steps

Implement parser combinators in crates/cron-parser/src/grammar.rs targeting the POSIX crontab(5) grammar and cross-checked against RFC 5545 RRULE semantics for recurrence-bound edge cases. Implement timezone resolution in crates/timer-normalizer/src/dst.rs: every next_fire_at computation happens in the schedule's declared IANA timezone, then converts to UTC for storage — never the reverse. Add DST-fold handling: a wall-clock time occurring twice (fall-back) resolves to the first occurrence unless the schedule explicitly opts into skip-ambiguous; a wall-clock time that does not exist (spring-forward gap) is shifted forward to the next valid instant. Canonicalize expressions (normalize */1 to *, sort list-form fields) so two textually different but semantically identical CRON strings hash identically for idempotency-key dedup (P13). Generate recurrence previews (next N fire times) for operator/API inspection without mutating state. Fuzz malformed schedules via fuzz/fuzz_targets/cron_parser.rs (ADR-14, cargo-fuzz). Anchor: RFC 5545, POSIX crontab(5), P8 clock skepticism, ADR-14.

14.3 Deliverable

A canonical normalized schedule engine: given a raw CRON string plus timezone, deterministically produces a TriggerDefinition::Cron value and a bounded recurrence preview.

14.4 Acceptance Criteria

Parser fuzz corpus stable across 10M cargo-fuzz iterations with zero panics/crashes. DST replay deterministic: 100% of fixtures/cron/dst-fold-cases.json (≥ 40 cases spanning both fall-back and spring-forward) resolve identically across 5 repeated runs. Malformed-input rejection rate: 100% of fixtures/cron/malformed-cron-corpus.txt (≥ 150 cases) rejected with a typed error, zero silent acceptance.

14.5 Conformance Fixtures

fixtures/cron/malformed-cron-corpus.txt — invalid step overflow (*/0), out-of-range fields, malformed list syntax; expects typed rejection. fixtures/cron/dst-fold-cases.json — spring-forward/fall-back boundary cases across multiple IANA zones; expects deterministic resolution per the rule above. fixtures/cron/leap-second-cases.json — schedules crossing a leap-second insertion; expects the schedule to treat leap seconds as a non-event (monotonic scheduling math ignores them, per P8) rather than double-firing.

14.6 Pitfalls

Leap-second ambiguity if any code path reads wall-clock time directly for interval math instead of routing through the monotonic-clock abstraction from Phase 0 · root cause: a shortcut that bypassed P8 · debug via: replay the same schedule across a simulated leap-second boundary and diff fire times · signal: a FIXED_INTERVAL schedule drifts by exactly one second near a known leap-second date · recovery: audit every Timestamp read for a bypassed clock abstraction. Locale-dependent parsing if the underlying date library defaults to system locale for month/day name parsing · root cause: relying on locale-sensitive stdlib functions · signal: a CI runner in a different locale fails a fixture that passes elsewhere · recovery: pin all name-based parsing to a fixed locale table, never system locale.

14.7 Performance Concerns

Parser allocation churn: naive combinator parsing can allocate a Vec per field per parse call; for the ingest p95 budget (< 12 ms, §4) this must stay allocation-light — pool or stack-allocate field buffers for the common five-field case.

14.8 Edge Cases

February 29 in a non-leap year for annual FIXED_INTERVAL/CRON combinations — must resolve to a documented policy (skip vs. shift to March 1), not an unhandled overflow. Schedules crossing a DST boundary where the next fire time also lands on a DST boundary (chained ambiguity).

14.9 Failure Analysis

Malformed-parser-state divergence: detection is the fuzz corpus regression suite catching any new panic; blast radius is contained entirely within cron-parser since rejection happens before durable-log ever sees the input (P1's ordering guarantees this); containment is returning a typed ParseError rather than partially normalizing; recovery is none needed at runtime — this is a build-time/CI-time containment, not an operational incident.

14.10 Operational Notes

Metric: invalid_schedule_rejected_total labeled by rejection reason (step-overflow, tz-ambiguous, negative-backoff, etc.) — high cardinality here is acceptable since reasons are a small closed enum, not user input. Tracing span: cron.normalize. Structured-log field: rejection_reason. No deployment/rollback implications — pure computation, no persisted state.

15. Phase 3 — Hierarchical Timer Wheel

15.1 Objectives

Implement the scalable timer-wheel runtime (wheel-engine): multi-level wheels, bucket migration, monotonic tick source, cancellation index. This is the latency-critical hot path sized against the 2M-timers/node and p99-dispatch-latency budgets in §4. Constraint: every insert must have already passed the WAL durability gate (I6).

15.2 Detailed Implementation Steps

Implement crates/wheel-engine/src/tick.rs: a monotonic tick source (MonotonicTime-driven, never wall-clock, per P8) advancing at a fixed 10 ms granularity, matching the Varghese & Lauck (1996/1997) hierarchical-wheel design — near timers live in a fine-grained low-level wheel, far timers in coarser higher levels, migrating downward as their deadline approaches. Wheel geometry (level count, slot count per level) is fixed at startup in Phase 3 — adaptive wheel resizing (PhaseDeferred("§15"), §35) is deferred until occupancy-histogram data (15.10) justifies the added complexity. Implement bucket.rs: WheelBucket (§11) backed by an intrusive linked list (TimerRef nodes embed their own list pointers, avoiding a separate allocation per list-membership, per Herlihy & Shavit ch. 5/9). Implement lock striping: one mutex per bucket-group (not per bucket, not one global lock) sized so contention stays below the p99 budget under 2M timers (I7, ADR-09). Implement the wheel-advancement scheduler with a bounded catch-up loop (I13) for when tick-thread scheduling jitter causes a missed tick. Implement the cancellation index (schedule_id -> bucket location) for O(1) cancellation without a bucket scan. Anchor: Varghese & Lauck (1996/1997); I6, I7, I13; ADR-09.

15.3 Deliverable

A runnable wheel scheduler: cargo run -p wheel-engine --example wheel_bench sustains the target insertion/expiration rate against a synthetic timer population.

15.4 Acceptance Criteria

2M timers/node sustained in the benchmark harness with p99 dispatch latency < 150 ms (§4). Bucket-lock contention (bucket_lock_wait_ns p99) stays under 500 μs at target load. Cancellation completes in < 1 ms p99 regardless of wheel population size (verifying O(1) via the cancellation index, not a scan).

15.5 Conformance Fixtures

fixtures/wheel/bucket-overflow.bin — a bucket receiving more timers than its pre-sized capacity in one tick; expects graceful dynamic growth, not a panic or drop. fixtures/wheel/ migration-storm.bin — a burst of timers all migrating from a high wheel level to the lowest level in the same tick; expects bounded migration batching, not a tick stall. fixtures/wheel/wheel-drift-regression.bin — a regression fixture pinning a previously observed drift bug (tick thread falling behind wall-clock under sustained load); expects catch-up within the bound in I13.

15.6 Pitfalls

Wheel drift when the tick thread is preempted long enough to miss multiple ticks · root cause: tick advancement coupled to OS-scheduler timing without a catch-up mechanism · debug via: inject scheduling delay in the deterministic simulator (§7) and assert I13 · signal: wheel_tick_gap_total rising · recovery: bounded catch-up sweep, never an unbounded "replay all missed ticks synchronously" loop (that itself becomes an unbounded stall). Bucket starvation where a small number of buckets accumulate disproportionate timer counts (e.g. many schedules with the same anchor time) · root cause: insufficient bucket fan-out at a given wheel level · signal: bucket-occupancy histogram (12.10-style export) shows a heavy tail · recovery: increase fan-out or add jitter insertion at normalization time (§8 malformed-input handling adjacent). Migration storms when many timers cross a level boundary simultaneously · root cause: correlated anchor times (e.g. "every hour on the hour" for thousands of tenants) · signal: tick-processing latency spike correlated with round timestamps · recovery: jitter insertion at timer-normalizer (Phase 2) spreads correlated anchors.

15.7 Performance Concerns

Cache locality: WheelBucket's intrusive list must keep TimerRef nodes contiguous enough to avoid a cache miss per list traversal — slab allocation, not per-node heap allocation. False sharing across lock-striped bucket groups if adjacent groups' mutexes share a cache line — pad to cache-line boundaries. Allocation fragmentation from variable-size DispatchEnvelope payload references — use a fixed-size BlobPointer indirection instead of inline variable data.

15.8 Edge Cases

A timer scheduled beyond the top wheel's range (e.g. a FIXED_INTERVAL anchor years out) — must be held in an overflow structure and re-inserted as it approaches range, not rejected. Clock skew between the tick source and the WAL's LSN-ordering during a lease transfer (Phase 4) — the new owner's tick source must not "fast-forward" past timers the old owner already durably scheduled but hadn't yet dispatched.

15.9 Failure Analysis

Stalled wheel-advancement detection: detection is the tick-gap counter (I13) crossing a threshold; blast radius is every timer whose bucket sits behind the current tick — they fire late but not lost (durability is independent, per I1); containment is the bounded catch-up sweep; recovery is automatic once the tick thread resumes; operator visibility is wheel_tick_gap_total plus a dispatch-lag alert (Operational Readiness, §24).

15.10 Operational Notes

Metrics: bucket_occupancy histogram per wheel level, wheel_tick_gap_total, bucket_lock_wait_ns. Tracing span: wheel.tick wrapping each advancement. Structured-log field: wheel_level, bucket_id on migration events. Rollback: wheel state is never persisted directly (P2) — a rollback is simply a restart plus replay, no special migration path needed.

16. Phase 4 — Shard Coordination and Leasing

16.1 Objectives

Implement distributed timer-partition ownership (shard-coordinator, lease-manager): etcd-backed leases, fencing tokens, shard balancing, forced revocation. Scope: single-region only (PhaseDeferred("§16") for geo-distributed and Byzantine-resistant variants, §35). Constraint: no two nodes may hold an active lease for the same shard (I2).

16.2 Detailed Implementation Steps

Integrate etcd lease APIs in crates/lease-manager/src/etcd_client.rs: lease grant, keepalive heartbeat loop, and revocation, modeled on Chubby's lease semantics (Burrows, 2006) rather than a bespoke consensus layer (ADR-05). Implement fencing tokens (crates/shard-coordinator/src/ fencing.rs): every LeaseToken.epoch (§11) strictly increases per shard (I10); every WAL-append and wheel-insert path checks the caller's epoch against the coordinator's current epoch and rejects stale epochs (I2, I10, P12). Implement shard balancing: a rebalance moves one shard at a time, gated by a replay-synchronization barrier so the new owner has fully replayed before accepting new inserts (P2 dependency). Implement forced revocation for a heartbeat-timeout node. Anchor: Burrows (2006) Chubby; Ongaro & Ousterhout (2014) Raft (for etcd's own consensus underpinning); I2, I10, P12, ADR-05.

16.3 Deliverable

A clustered ownership runtime: a 3-node test cluster demonstrates shard assignment, lease renewal, and a clean handoff on simulated node failure, observable via shard-ownership dashboards (Phase 8 dependency stubbed here).

16.4 Acceptance Criteria

Zero dual-ownership windows detected across 500 chaos-test iterations (random node kill + partition) — verified against fixtures/shard/dual-ownership-chaos.json. Lease failover completes in < 15 s p99 (§4). Fencing-token rejection rate for stale epochs is 100% in fixtures/shard/fencing-token-replay.bin (≥ 100 replayed-stale-epoch attempts).

16.5 Conformance Fixtures

fixtures/shard/dual-ownership-chaos.json — scripted node-kill/partition sequence; expects the simulator to detect zero moments of two nodes both believing they own the same shard. fixtures/shard/fencing-token-replay.bin — a stale lease holder replaying old appends after losing ownership; expects 100% rejection at the fencing check. fixtures/shard/ partition-asymmetry.json — a network partition where node A can reach etcd but not node B (and vice versa is not symmetric); expects correct minority-side lease expiry, not a stuck lease.

16.6 Pitfalls

Stale lease holders continuing to believe they own a shard after a missed heartbeat renewal · root cause: client-side lease-expiry check running on a delayed local clock rather than trusting etcd's authoritative lease state · debug via: chaos-inject clock delay on the lease-manager process specifically · signal: lease_fencing_rejections_total spikes right after a network-blip recovery · recovery: never let a node self-assert lease validity — always confirm against etcd or via a fencing-token check at the write boundary. Split-brain windows during an asymmetric partition (each side can reach a different subset of etcd members) · root cause: etcd quorum size assumptions violated by network topology · signal: two shard-ownership claims observed simultaneously in the audit trail · recovery: the fencing-token check at the WAL append boundary is the actual safety net — detection here is a defense-in-depth alarm, not the primary correctness mechanism.

16.7 Performance Concerns

Rebalance storms: moving too many shards simultaneously saturates the replay-synchronization barrier and floods durable-log reads across the cluster — cap concurrent shard transfers (§4's 5K concurrent-replay-operations budget) and serialize large rebalances.

16.8 Edge Cases

Network partition asymmetry (16.6) — the minority side must fail closed (stop dispatching) even if it still believes it holds a valid lease locally, per the fencing-token defense-in-depth model. A shard rebalance initiated mid-dispatch of an already-DISPATCHED (but not yet ACKed) timer — the new owner must not re-dispatch it before checking dispatch-queue-level ack state.

16.9 Failure Analysis

Orphaned-shard replay: detection is a shard with no active lease holder past its expected heartbeat window; blast radius is every timer on that shard sitting un-dispatched (not lost — durable per I1) until reassignment; containment is the forced-revocation path triggering immediate reassignment; recovery is the new owner's mandatory replay-sync barrier before accepting inserts; operator visibility is lease_epoch gauges per shard plus an orphaned-shard alert.

16.10 Operational Notes

Metrics: lease_epoch gauge per shard, lease_fencing_rejections_total, shard_rebalance_duration_ms. Tracing span: shard.lease_renew, shard.rebalance. Structured-log fields: shard_id, epoch, owner_node. Deployment: requires a 3-node (or 5-node) etcd quorum co-located or network-adjacent to the coordinator nodes (§24 topology).

17. Phase 5 — Dispatch Queue and Worker Runtime

17.1 Objectives

Build the execution-isolation layer (dispatch-queue, execution-worker, retry-engine): bounded queues, priority dispatch, worker concurrency pools, retry acknowledgement, poison routing. Scope introduces the boundary where scheduling correctness (upstream) meets execution (downstream) and must not leak across it (P10).

17.2 Detailed Implementation Steps

Implement crates/dispatch-queue/src/priority.rs: bounded, shard-local queues (P4, ADR-24) with a priority lane separating fresh dispatches from retries so retry storms cannot starve new work. Model the queue-plus-worker-pool split on Kafka's delayed-operation purgatory (Kreps, Narkhede & Rao, 2011) but adapted for cross-node dispatch rather than in-process request completion. Implement crates/execution-worker/src/pool.rs: a bounded thread/task pool (64–256 per §4) pulling DispatchEnvelopes and invoking the opaque execution_target handoff, isolated from the wheel/WAL address space entirely (P10) — a worker crash cannot corrupt scheduler state by construction, not by convention. Implement crates/retry-engine/src/backoff.rs: BackoffStrategy execution (Fixed/Exponential/ExponentialDecorrelated) with jitter per JitterMode (§11), attempt-count monotonicity (I4). Implement poison-queue routing: after max_attempts exhaustion, transition to DEAD_LETTER (§8) rather than infinite retry (P7). The execution_target handoff in Phase 5 supports opaque callback/queue delivery only — sandboxed WASM execution hooks (PhaseDeferred("§17"), §35) are deferred until a capability-scoped runtime is designed. Anchor: I4, P4, P7, P10, ADR-24; Kreps et al. (2011).

17.3 Deliverable

A distributed execution subsystem: execution-worker instances pull from shard-local dispatch-queues and demonstrate bounded-queue backpressure signaling to scheduler-api under synthetic overload.

17.4 Acceptance Criteria

Queue saturation handled gracefully: at 110% of the 100K-dispatches/sec target (§4), ingest returns RESOURCE_EXHAUSTED rather than OOMing, verified over a 10-minute sustained-overload test. Poison-queue routing triggers at exactly max_attempts (verified for max_attempts in {1, 3, 10, 50}) with zero premature or delayed dead-lettering. Duplicate-ACK handling: 100% of fixtures/dispatch/duplicate-ack.json cases (≥ 60) resolve without a double-reschedule.

17.5 Conformance Fixtures

fixtures/dispatch/duplicate-ack.json — a worker ACK delivered twice (network retry on the ACK itself); expects idempotent handling via dispatch_id (P13), not a double state transition. fixtures/dispatch/poison-queue-routing.json — a schedule whose callback always fails; expects transition to DEAD_LETTER at exactly max_attempts. fixtures/dispatch/ retry-negative-backoff.json — a RetryPolicy with a negative max_backoff_ms (should have been rejected in Phase 2 normalization, but re-checked defensively here); expects rejection, not a crash.

17.6 Pitfalls

Unbounded retries if max_attempts is misconfigured to an effectively-infinite value (e.g. a default of u32::MAX) · root cause: no upper-bound validation at schedule-creation time · debug via: retry-backlog-by-classification dashboard (P7) showing one schedule dominating the backlog · signal: retry_attempt_regression_total stays flat but backlog depth for one schedule_id grows unbounded · recovery: enforce a hard ceiling on max_attempts at the API-validation layer, not just the retry-engine. Head-of-line blocking when a single slow callback target occupies a worker-pool slot indefinitely · root cause: no per-dispatch deadline enforcement · signal: worker-pool utilization pinned at 100% with falling completed-dispatch rate · recovery: enforce DispatchEnvelope.deadline as a hard timeout, treat expiry as a failure feeding the retry-engine.

17.7 Performance Concerns

Queue contention: a naive single-mutex bounded queue per shard becomes the bottleneck at 100K dispatches/sec — use an MPMC lock-free or lock-striped queue structure (informed by Herlihy & Shavit's concurrent-structure patterns, §5) rather than a coarse mutex.

17.8 Edge Cases

Duplicate worker ACKs arriving out of order relative to a retry-engine-issued reschedule (the ACK for attempt N arrives after attempt N+1 has already been dispatched) — must not let the late ACK for N incorrectly ACK the in-flight N+1. Worker-pool exhaustion during a lease handoff (Phase 4) where the new shard owner's local worker pool is still warming up.

17.9 Failure Analysis

Lost-ACK recovery: detection is dispatch_ack_timeout_total (I11) crossing the deadline window; blast radius is one DispatchEnvelope re-queued with an incremented attempt — bounded by design, never cluster-wide; containment is the retry-engine's monotonic attempt counter (I4) preventing a resurrected old ACK from reordering state; recovery is automatic requeue; operator visibility is the retry-backlog-by-classification dashboard (P7).

17.10 Operational Notes

Metrics: retry_backlog_depth labeled by classification, dispatch_queue_depth per shard, worker_pool_utilization. Tracing span: dispatch.deliver, worker.execute. Structured-log fields: dispatch_id, attempt, classification. Rollback: a worker-runtime rollback (bad deploy) must drain in-flight dispatches to the retry-engine rather than dropping them — this is the isolation boundary (P10) paying for itself operationally.

18. Phase 6 — Replay and Recovery

18.1 Objectives

Implement deterministic recovery: replay cursors, snapshot restoration, replay checksums, ordering validation, closing the loop opened by Phase 1's WAL and Phase 3's wheel. Constraint: replay output must be bit-identical to the pre-crash state for the same WAL prefix (I5, P5).

18.2 Detailed Implementation Steps

Implement replay-cursor advancement shared between shard-coordinator's internal replay path and the standalone replay-cli. Implement periodic immutable snapshot segments — chosen over a live heap dump because a live dump captures allocator-internal state that is not portable or deterministic across processes, violating the replay determinism this phase exists to guarantee (P2, P5). Implement replay checksums: after replaying a WAL prefix, compute a structural hash of the resulting wheel state (bucket contents, cancellation index) and compare across independent replay runs — the mechanism underlying I5. Implement deterministic-ordering validation: replay must process records in strict LSN order and must never depend on hash-map iteration order for anything observably-ordered (a classic nondeterminism source, per Lamport's 1978 causal-order framing applied to a single-node log rather than a distributed one). Replay in Phase 6 is single-cluster scoped — cross-cluster deterministic replay snapshot federation (PhaseDeferred("§18"), §35) is deferred until a cross-cluster transport is chosen. Anchor: I3, I5, P2, P5; Lamport (1978).

18.3 Deliverable

A crash-recovery runtime: replay-cli replay --segment-dir <path> reconstructs full wheel state from a segment directory and reports a structural checksum matching the pre-crash value recorded in a companion test harness run.

18.4 Acceptance Criteria

Replay produces identical wheel state (structural checksum match) across 3 independent runs for every fixture in fixtures/replay/ (≥ 30 cases). Snapshot-restore path completes within the 90 s / 50M-timer budget (§4), verified at 10M, 25M, and 50M timer scales. Zero divergence across fixtures/replay/checksum-divergence.bin's regression case after the fix that produced it.

18.5 Conformance Fixtures

fixtures/replay/partial-compaction.bin — replay starting mid-way through an interrupted compaction pass; expects correct reconstruction from the pre-compaction segment plus whatever the new segment had durably written. fixtures/replay/checksum-divergence.bin — a regression fixture pinning a previously observed divergence (hash-map iteration order leaking into bucket construction order); expects stable structural-checksum match post-fix. fixtures/replay/ snapshot-restore.bin — a full snapshot-segment restore at scale; expects the 90 s budget met and a checksum match against the live-replay path (two independent recovery mechanisms must agree).

18.6 Pitfalls

Replay nondeterminism from iterating a HashMap during bucket reconstruction instead of a BTreeMap or explicit LSN-ordered vector · root cause: convenience data structure choice leaking into an observably-ordered code path · debug via: run replay twice with a randomized hash-seed (Rust's default HashMap is seeded per-process) and diff the structural checksum · signal: checksum mismatch that only appears cross-process, never within one process · recovery: audit every replay-path data structure for hash-dependent iteration and replace with an explicitly ordered structure — this is exactly the class of bug fixtures/replay/ checksum-divergence.bin pins down.

18.7 Performance Concerns

Replay IO saturation: a full-scale replay (50M timers) is a sequential scan across many segments — sized against the same NVMe sustained-throughput assumption as WAL append (§4); concurrent replay operations must respect the 5K-concurrent-replay budget to avoid saturating shared storage during a mass-rebalance event (cross-reference §16.7 rebalance storms).

18.8 Edge Cases

Partially compacted segments where the compaction marker exists but the old segment wasn't yet deleted (crash mid-compaction) — replay must prefer the new segment's records where they overlap and never double-apply the old segment's now-superseded records.

18.9 Failure Analysis

Divergent-checksum recovery: detection is a structural-checksum mismatch across replay runs (I5 violation); blast radius is contained to the node performing the divergent replay — it must not be promoted to serve traffic until the checksum matches; containment is the promotion gate refusing to activate a node with a mismatched checksum; recovery is a snapshot restore from the last known-good immutable segment (§18.2) plus a bug report against the specific nondeterminism source; operator visibility is replay_divergence_total plus a blocked-promotion alert.

18.10 Operational Notes

Metrics: replay_progress_ratio, replay_throughput_timers_per_sec, replay_divergence_total. Tracing span: replay.segment_scan. Structured-log fields: segment_id, structural_checksum. Deployment: replay-cli ships as a standalone binary for operator-driven manual recovery independent of the running cluster.

19.1 Objectives

fixtures/observability/high-cardinality-labels.json — a synthetic load pattern designed to blow up label cardinality if the bounded-cardinality rule (19.2) is violated; expects bounded growth, not an unbounded label explosion. fixtures/observability/exporter-outage.json — a simulated metrics-exporter outage; expects local buffering with bounded memory (P4) and no crash, followed by successful backfill on exporter recovery.

19.6 Pitfalls

High-cardinality labels leaking schedule_id or raw tenant metadata into a metric label instead of a trace attribute · root cause: conflating "goes on every span" (fine, high cardinality acceptable in tracing) with "goes on every metric series" (not fine — metrics aggregate, traces don't) · debug via: cardinality-explosion alert on the metrics backend itself · signal: Prometheus/metrics-pipeline memory growth unrelated to timer count · recovery: audit every metric!() call site for accidental unbounded labels; move detail to span attributes instead.

19.7 Performance Concerns

Telemetry overhead: span creation and metric-counter increments on every hot-path transition (wheel tick, dispatch) must stay allocation-light — pre-allocate span contexts where possible, batch metric-counter flushes rather than syscall-per-increment.

19.8 Edge Cases

Metrics-exporter outage (19.5) during a genuine incident — the worst possible time to lose observability; local buffering must be bounded (can't buffer forever, P4) but long enough to survive a typical exporter restart (target: 5 minutes at expected metric-emission rate).

19.9 Failure Analysis

Missing trace linkage: detection is the orphaned-span-rate check in 19.4; blast radius is reduced incident-response visibility, not a correctness break (P6 is an observability principle, not a durability one — losing a trace span never loses a schedule); containment is alerting on the orphaned-span rate itself; recovery is identifying and fixing the span-context propagation gap (commonly an await boundary that dropped the tracing context).

19.10 Operational Notes

SLO dashboards define: dispatch-lag p50/p95/p99 against §4 targets, replay-lag against the 90 s budget, lease-churn rate, duplicate-dispatch rate against the < 0.001% budget. Metric: trace_span_orphan_rate. This phase's own metrics become the primary tool for validating every later phase's acceptance criteria — a genuinely load-bearing dependency, not a nice-to-have.

fixtures/security/expired-cert.pem — an expired client certificate presented at mTLS handshake; expects clean connection rejection, not an ambiguous timeout. fixtures/security/ quota-bypass-attempt.json — a scripted burst designed to race the quota-check window; expects the sharded-counter design to hold under the race, not permit a burst-through. fixtures/ security/tenant-isolation-breach.json — crafted requests attempting to read or cancel another tenant's schedule_id; expects rejection at RBAC, not a 404-that-leaks-existence.

20.6 Pitfalls

Quota bypass via a race between the atomic-counter check and the counter increment (check-then- act race) · root cause: non-atomic check-and-increment across a distributed counter shard · debug via: high-concurrency fuzz test hammering the same tenant's quota boundary · signal: quota_ledger_drift_total (I14) non-zero under load · recovery: make the check-and-increment a single atomic operation (CAS loop or an atomic fetch-and-add with post-hoc rejection-and-refund for the rare overshoot, reconciled against the durable ledger).

20.7 Performance Concerns

Auth-cache contention: caching the certificate-to-tenant binding lookup avoids a full RBAC re-evaluation on every request, but a naive single-lock cache becomes a bottleneck at 10K concurrent connections (§4) — shard the cache by tenant or use a lock-free read-mostly structure.

20.8 Edge Cases

Expired certificates arriving mid-stream on a long-lived gRPC connection (cert expired after handshake but before the connection closed) — must be re-validated periodically, not only at handshake. A tenant hitting its quota exactly at a billing-window boundary — the reset must be atomic with respect to concurrent quota checks (no window where neither the old nor new window believes it owns the request).

20.9 Failure Analysis

Privilege-escalation audit: detection is the audit-log reconciliation job cross-checking every admin-console action against the RBAC role that authorized it; blast radius depends entirely on what the escalated action touched — bounded to read access if RBAC enforcement held anywhere in the path, unbounded (requires full incident response) if a create/cancel action slipped through; containment is revoking the offending credential immediately; recovery is a full audit-trail review plus a patch to the specific RBAC gap.

20.10 Operational Notes

Metrics: auth_rejection_total labeled by reason, quota_enforcement_latency_ms, tenant_scoped_dispatch_rate. Tracing span: auth.validate, quota.check. Structured-log field: tenant_id (always present, always the authenticated identity, never a client-supplied value). Deployment: certificate rotation runbook lives in docs/runbooks/.

21. Phase 9 — Production Hardening

21.1 Objectives

Validate operational stability end-to-end: chaos testing, soak testing, WAL-corruption testing, clock-skew testing, rolling-upgrade validation. Scope: this phase does not add new subsystems — it proves the previous nine hold up under sustained, combined, adversarial conditions. Exit gate for the production-candidate release (§38).

21.2 Detailed Implementation Steps

Run chaos testing combining every fault-injection primitive built for individual phases (node kill from §16, network partition from §16, WAL corruption from §13) simultaneously rather than in isolation, since real incidents combine failure modes. Run soak testing: 30-day continuous operation at 70% of the throughput targets in §4, watching for slow leaks (heap fragmentation creeping past the 15% budget, FD exhaustion, lease-churn drift). Run WAL-corruption testing at scale (beyond the single-bit-flip fixtures of Phase 1 — multi-segment corruption, corruption during active compaction). Run clock-skew testing: inject NTP-step jumps and gradual drift against the monotonic-clock assumption (P8) to confirm the abstraction actually holds under adversarial wall-clock behavior. Run rolling-upgrade validation: N-1 compatibility (§25) under an actual mixed-version cluster, not just a compatibility-matrix review. Anchor: P8, P9 crash-only recovery, §25 compatibility; every invariant in §7 re-verified under combined stress.

21.3 Deliverable

A production-candidate release: a tagged, signed release artifact (ADR-21) that has passed the combined chaos/soak/corruption/clock-skew/rolling-upgrade gate and is eligible for staged production rollout.

21.4 Acceptance Criteria

30-day soak stability: zero unplanned restarts, RSS growth < 5% over the 30-day window (bounding the < 8 GB budget in §4), heap fragmentation staying under 15%. Chaos-combined test suite: zero I1–I14 invariant violations across 1,000 combined-fault iterations. Rolling upgrade: zero dispatch-correctness regressions across a full N-1 mixed-version cluster run of fixtures/hardening/rolling-upgrade-partial.json.

21.5 Conformance Fixtures

fixtures/hardening/clock-skew-injection.json — NTP-step and gradual-drift scenarios; expects zero P8 violations (no spurious immediate/delayed firing from wall-clock jumps). fixtures/hardening/rolling-upgrade-partial.json — a cluster frozen mid-rolling-upgrade (half old version, half new); expects full dispatch correctness across the mixed-version boundary. fixtures/hardening/soak-leak-regression.json — a regression fixture pinning a previously observed slow leak; expects bounded RSS growth over an accelerated soak replay.

21.6 Pitfalls

Latent memory leaks that only manifest past the timescale of any individual phase's tests · root cause: a slow leak in a low-frequency code path (e.g. rebalance-triggered cleanup that misses one allocation per rebalance) · debug via: heap-profiling snapshots at fixed soak-test intervals, diffed against a baseline · signal: RSS creeping upward with no corresponding timer-count growth · recovery: bisect via interval-diffed heap snapshots to the specific rebalance/replay/retry code path leaking, not a general "restart nodes periodically" workaround (which masks rather than fixes the leak).

21.7 Performance Concerns

Long-tail replay latency emerging only at true production scale (50M+ timers across many segments, not the smaller fixtures of Phase 6) — the soak/chaos combination in 21.2 is the first point this blueprint validates the full tail, not just the median or even p99 at smaller scale.

21.8 Edge Cases

Partial rolling rollback: an operator starts a rollback mid-rolling-upgrade, producing a cluster with three concurrent versions briefly (old, new, and now rolling-back-to-old) — compatibility guarantees (§25) are defined as N-1, not N-2; this must be an explicitly disallowed operator action, documented in the runbook, not silently tolerated.

21.9 Failure Analysis

Cascading queue collapse under combined chaos: detection is dispatch-queue depth across multiple shards spiking simultaneously; blast radius, absent backpressure (P4), could be cluster-wide OOM — this is precisely the scenario P4's design exists to prevent, and 21.4's acceptance criteria verify it holds under combined, not just isolated, fault injection; containment is the bounded-queue admission-rejection path; recovery is automatic once the triggering fault clears, verified by the chaos-suite's automated recovery-time assertions.

21.10 Operational Notes

This phase finalizes the runbooks under docs/runbooks/ (recovery.md, failover.md, replay.md) with concrete command sequences validated against the actual chaos/soak fixtures rather than theoretical procedures. Metric: soak_test_rss_growth_ratio, chaos_invariant_violation_total (must stay at zero). Deployment: this phase's exit criteria (§38) gate the first production rollout.

Alerting: dispatch lag (p50/p95/p99 vs. §4 targets), replay lag (vs. the 90 s / 50M-timer budget), lease churn rate (FM-6), duplicate-dispatch rate (vs. the < 0.001% budget in §4). Each alert maps to exactly one invariant (§7) or failure mode (§23) — no alert without a named owner and a named recovery path.

Deployment topology: 3-node (or 5-node) coordinator quorum co-located with etcd for lease latency; N horizontally scaled stateless scheduler-api and execution-worker instances; dedicated NVMe WAL volumes per coordinator node, never shared with general-purpose storage.

Upgrade strategy: rolling upgrade with dual-version (N, N-1) compatibility (§25) — never more than one minor version skew live in the cluster at once; upgrade order is coordinators before workers, since workers are stateless and disposable while coordinators hold shard ownership.

Runbooks (docs/runbooks/): recovery.md (WAL-corruption and replay recovery procedures), failover.md (lease-failover and forced-revocation procedures), replay.md (operator-driven replay-cli usage for manual recovery). Finalized and chaos-validated in Phase 9 (§21.10).

25. Compatibility & Versioning

Wire compatibility: Protobuf backward compatibility is mandatory (ADR-06) — new fields are additive-only with explicit defaults; field numbers are never reused, even after a field is deprecated (permanently reserved).

Storage compatibility: WAL schema evolution is append-only (ADR-04) — a new record layout gets a new type tag, never a mutated existing layout; fixtures/bootstrap/schema-evolution-v1.bin (§12.5) pins the v1 baseline forever as a regression anchor.

API stability: semver-enforced at the scheduler-api gRPC surface — a breaking change requires a major version bump and a deprecation window communicated via the compatibility runbook.

Rolling upgrades: N-1 compatibility guaranteed — any two adjacent versions may coexist in one cluster during a rolling upgrade; N-2 coexistence is explicitly unsupported (§21.8) and must be blocked at the deployment-tooling level, not just documented.

Compatibility test matrix (§26) runs every N/N-1 version pair in the supported window against the full conformance suite before a release is tagged (§27), closing the loop between this section's guarantees and Phase 9's rolling-upgrade validation (§21.4).

Testing layers: unit testing (per-crate, fast, no IO); integration testing (cross-crate, conformance-suite-driven); property-based testing (proptest, ADR-13 — CRON/DST edge cases, retry-policy invariants); fuzzing (cargo-fuzz, ADR-14 — cron-parser, WAL record decoding); deterministic replay testing (§18, cross-run checksum comparison); chaos testing (§16, §21 — node kill, partition, combined faults); soak testing (§21 — 30-day continuous operation); compatibility testing (§25 — N/N-1 version-pair matrix).

29. Scalability Analysis

Scaling bottlenecks, in order of first-observed impact: replay throughput (bounded by sequential-scan IO, §18.7); shard-rebalance storms (bounded concurrent-transfer budget, §16.7, §29 cross-reference); WAL IO saturation (bounded by NVMe sustained-write throughput, §13.7); telemetry cardinality (bounded label design, §19.2, §19.6).

Horizontal scaling: shard partitioning is the primary scale-out lever (MM8, §30) — adding nodes adds shards, each shard's wheel and queue are independent, so cluster throughput scales near-linearly until etcd lease-management overhead (C9, §32) or rebalance-storm risk (§16.7) dominates.

Vertical scaling: CPU affinity and NUMA-aware placement (§4's single-NUMA-node preference) — pinning a shard's wheel-tick thread and its lock-striped buckets to one NUMA node avoids cross-socket cache-line traffic that would otherwise dominate the p99 dispatch-latency budget at high core counts.

Metadata scaling: bounded lease churn — the etcd quorum's write throughput, not raw shard count, is the actual ceiling; §32's C9 shows current heartbeat traffic is far below that ceiling, meaning shard count can grow substantially before metadata-tier scaling becomes the binding constraint rather than the wheel/WAL tier.

Federation (deferred, PhaseDeferred("§18"), §35) is the eventual answer to single-cluster etcd-quorum ceilings, once single-cluster scaling limits are actually observed in production rather than anticipated.

30. Mental Models & First Principles

  • MM1 — Amortized O(1) Beats Worst-Case O(log n) at This Scale. Compressed insight: a hierarchical timer wheel gives amortized O(1) insert/cancel by trading per-operation optimality for bucket-based approximation, while a binary heap gives O(log n) worst-case but exact ordering. What it predicts: at 2M timers/node, the wheel's constant-factor advantage dominates; at low counts, the heap's simplicity wins instead. Bug class without it: choosing a heap for scale "because it's simpler" and hitting a lock-contention wall at scale (§34 Alt B). Applies in §15 and §32.
  • MM2 — Fencing Tokens Turn "Probably One Owner" Into "Provably One Owner." Compressed insight: a lease alone is a soft signal (the holder might be wrong about still holding it); a monotonically increasing fencing token checked at the write boundary is a hard guarantee. What it predicts: any design relying on lease-expiry timing alone, without a fencing check at the actual mutation point, will eventually double-write under partition. Bug class without it: split-brain dual dispatch (FM-2). Applies in §16.
  • MM3 — The Log Is the Database. Compressed insight: treating the WAL as the sole source of truth (P1) and every other structure (wheel, indexes) as a derived, rebuildable cache inverts the usual "database with a WAL for crash safety" relationship. What it predicts: any in-memory-only mutation path is a latent durability bug waiting for a crash to expose it. Bug class without it: "fast path" optimizations that skip the WAL and silently lose data on restart. Applies in §13 and §18.
  • MM4 — Backpressure Prevents Collapse; Buffering Just Delays It. Compressed insight: bounded queues with upstream signaling (P4) convert an overload event into a visible, recoverable rejection; unbounded buffering converts the same event into an invisible, unrecoverable OOM. What it predicts: any "just make the queue bigger" fix is a deferred outage, not a fix. Bug class without it: cascading queue collapse under combined load (FM-3, §21.9). Applies in §17 and §29.
  • MM5 — Deterministic Replay Is State-Machine Replication Without the Network. Compressed insight: replay determinism (P5, I5) is the same discipline distributed consensus systems need for their replicated state machines, applied to one node's own crash-recovery path instead of cross-node replication. What it predicts: any nondeterminism source consensus systems avoid (hash-iteration order, wall-clock reads, thread-scheduling-dependent ordering) will break replay the same way it would break a Raft state machine. Bug class without it: replay divergence that only appears cross-process (FM-5). Applies in §18.
  • MM6 — Scheduling Commit and Execution Delivery Are Different Guarantees at Different Layers. Compressed insight: exactly-once scheduling (a schedule is durably recorded exactly once) and at-least-once execution (a dispatch may be delivered more than once) are independent properties that must not be conflated in either code or documentation. What it predicts: any caller assuming "exactly-once" end-to-end will build a system vulnerable to duplicate side effects. Bug class without it: treating DispatchEnvelope redelivery as a bug instead of a documented contract (P13). Applies in §1 and §17.
  • MM7 — Never Let Wall-Clock Reads Touch Scheduling Math. Compressed insight: monotonic clocks are for "how much time has elapsed"; wall clocks are for "what should a human see" — crossing that boundary anywhere in the scheduling hot path reintroduces every NTP-step and DST bug the monotonic abstraction exists to prevent. What it predicts: a single bypassed Timestamp read anywhere in the tick or replay path becomes a rare, hard-to-reproduce production incident (FM-8) rather than a caught-in-review bug. Applies in §14 and §21.
  • MM8 — Partitioning Converts Global Contention Into Local Contention. Compressed insight: sharding the wheel and dispatch queue by key range converts one global lock's contention into N independent locks' contention, which is why performance targets (§28) are expressed per-node rather than cluster-wide. What it predicts: cluster throughput scales with shard count until a shared resource (etcd quorum, C9) becomes the new bottleneck. Bug class without it: a "global queue for simplicity" design (§34 Alt B) that recreates the exact contention sharding was meant to eliminate. Applies in §15 and §29.

  • Quartz Scheduler — decided on JDBC row-locking for clustered coordination instead of a lease/fencing service; wins in a JVM shop already running a robust RDBMS and not wanting to operate etcd or ZooKeeper.
  • systemd timers — decided to scope entirely to a single host with no clustering primitive at all; wins for host-local maintenance timers where distributed coordination is pure overhead.

32. Back-of-Envelope Capacity Model

  • C1 — Timer Memory Per Node. 2,000,000 timers × 320 B/timer = 640,000,000 B ≈ 610 MiB, well inside the 8 GB §4 RSS ceiling, leaving roughly 7.4 GB for wheel overhead, WAL page cache, and gRPC buffers.
  • C2 — Cluster Timer Capacity. 15 nodes × 2,000,000 timers/node = 30,000,000 timers cluster-wide capacity at the maximum §4 deployment size.
  • C3 — WAL Append Throughput. 250,000 inserts/sec × 200 B/record (payload + header, per C6) = 50,000,000 B/sec ≈ 50 MB/s sustained sequential write, well under typical NVMe sustained-write throughput of 1–2 GB/s.
  • C4 — Worst-Case WAL Write Demand. 50 MB/s raw × 1.8x amplification ceiling (§4) = 90 MB/s worst-case sustained write demand, still comfortably under NVMe throughput.
  • C5 — Required Replay Throughput. 50,000,000 timers ÷ 90 s = 555,556 timers/sec required sustained replay rate to meet the §4 recovery-startup budget (M4, §28).
  • C6 — Record Header Overhead. 16 B header (length 4 B + crc32c 4 B + lsn 8 B) ÷ 184 B average payload = 1.087x amplification from the header alone, leaving most of the 1.8x §4 ceiling for fsync-batch padding and index overhead.
  • C7 — Dispatch-Queue Buffer Memory Per Shard. 100,000 dispatches/sec × 96 B/DispatchEnvelope × 2 s buffer window = 19,200,000 B ≈ 18.3 MiB per shard-queue buffer at a 2-second retention target before backpressure (ADR-24) engages.
  • C8 — FD Budget Check. 10,000 client connections + 5,000 concurrent replay operations = 15,000 FDs, inside the 16K FD/node budget (§4) with 1,000 FDs headroom for WAL segment file handles.
  • C9 — Lease Heartbeat Traffic. 15 nodes × (1 heartbeat ÷ 2 s keepalive interval) = 7.5 heartbeats/sec cluster-wide, negligible against etcd's write capacity and far below the threshold where metadata-tier scaling (§29) becomes binding.
  • C10 — Availability Budget in Failover Events. 0.05% × 30 days × 24 h × 60 min = 21.6 min/month unavailability budget; 21.6 min × 60 ÷ 15 s per failover (§4) = 86 full failover events/month absorbable before exhausting the 99.95% SLA.

36. Glossary

  • Timer Wheel — bucketed scheduling structure indexing timers by expiration tick across multiple hierarchical levels.
  • Bucket — a single slot in a wheel level grouping timers sharing an expiration tick range.
  • Lease Epoch — a monotonic ownership token that increases on every shard-ownership change.
  • Replay Cursor — a checkpoint marking WAL replay progress (segment ID + byte offset).
  • Tombstone — a logical-deletion marker for a cancelled or dead-lettered schedule.
  • Dispatch Lag — the delay between a timer's expiration tick and its actual execution.
  • Poison Queue — the routing destination for permanently failed, exhausted-retry executions.
  • Fencing Token — a token rejecting writes from a stale (superseded) shard owner.
  • Compaction — the WAL cleanup process reclaiming space from tombstoned/superseded records.
  • Monotonic Clock — a non-wall-time, strictly increasing time source immune to NTP steps.
  • Wall Clock — the human-facing calendar/clock time, used only for display translation.
  • WAL (Write-Ahead Log) — the append-only durable record of every schedule mutation.
  • Segment — a fixed-size rotating unit of the WAL, identified by a monotonic segment ID.
  • Checksum — a per-record or per-segment integrity value (CRC32C) detecting corruption.
  • Sparse Index — a lookup structure mapping schedule_id to (segment_id, offset).
  • Shard — a partition of the timer keyspace owned by exactly one node at a time.
  • Shard Coordinator — the subsystem assigning and revoking shard ownership.
  • Lease Manager — the subsystem integrating with etcd for lease grant/renewal/revocation.
  • Dispatch Envelope — the wire record carrying one execution attempt to a worker.
  • Retry Policy — the per-schedule configuration of backoff strategy and attempt limits.
  • Backoff Strategy — the algorithm (Fixed, Exponential, ExponentialDecorrelated) governing retry spacing.
  • Jitter — randomized variance added to backoff or anchor times to avoid correlated bursts.
  • Dead Letter — the terminal state for a schedule that exhausted all retry attempts.
  • Idempotency Key — a caller-supplied token deduplicating retried create-schedule requests.
  • Trace Span — one named, timed segment of a distributed trace (e.g. wal.append).
  • RED Metrics — Rate, Errors, Duration — the standard request-oriented metric triad.
  • USE Metrics — Utilization, Saturation, Errors — the standard resource-oriented triad.
  • Cardinality — the number of distinct label-value combinations a metric series can take.
  • Fsync — the syscall confirming data is durably written to storage before returning.
  • WAL Amplification — the ratio of bytes physically written to logical payload bytes.
  • NUMA — Non-Uniform Memory Access; cross-socket memory access is slower than local.
  • Cache Line — the fixed-size unit (typically 64 B) of CPU cache coherence traffic.
  • False Sharing — performance loss from unrelated data sharing one cache line under concurrent access.
  • Split-Brain — a state where two nodes each believe they exclusively own the same resource.
  • Quorum — the minimum member count of a distributed store (e.g. etcd) required to commit.
  • RBAC — Role-Based Access Control, gating actions by assigned role rather than identity alone.
  • mTLS — mutual TLS, where both client and server present and verify certificates.
  • SBOM — Software Bill of Materials, an enumerated list of a build's dependencies.
  • Provenance Attestation — a signed record of how and from what source an artifact was built.
  • Reproducible Build — a build process producing a bit-identical artifact from identical inputs.
  • Soak Test — a long-duration continuous-operation test surfacing slow leaks and drift.
  • Chaos Test — a test injecting real-world faults (kill, partition, corruption) to verify recovery.
  • Rolling Upgrade — a deployment strategy replacing nodes incrementally, never all at once.
  • N-1 Compatibility — the guarantee that two adjacent versions may coexist during upgrade.
  • Structural Checksum — a hash of reconstructed in-memory state used to verify replay determinism.
  • Cancellation Index — a lookup structure enabling O(1) timer cancellation without a bucket scan.
  • Intrusive Linked List — a list where link pointers live inside the element itself, not a separate node.
  • CRON Expression — a POSIX five-field recurrence specification (minute, hour, day, month, weekday).
  • DST Fold — the ambiguous wall-clock period where a local time occurs twice during a fall-back transition.
  • Leap Second — an inserted second reconciling civil (UTC) time with Earth's rotation, irrelevant to monotonic scheduling math.
  • Recurrence Preview — a computed list of upcoming fire times for operator inspection, without state mutation.
  • Tenant Quota — a durable per-tenant limit on active timers and insertion rate.
  • Audit Event — an append-only record of an administrative or quota-relevant action.
