Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Centralized Single-Wheel Coordinator

        +------------------+
        | many client SDKs  |
        +---------+--------+
                  |
                  v
        +------------------+
        | ONE active wheel  |  <-- single point of write contention
        | + hot standby     |
        +---------+--------+
                  |
                  v
        +------------------+
        | dispatch + workers |
        +------------------+

Regime where it wins: small deployments (< 100K timers) where operational simplicity beats horizontal scale, and the ops team would rather manage one wheel process with a hot standby than a sharded cluster. Real system embodying it: Quartz Scheduler's JDBC-clustered mode (all nodes coordinate through one lock-guarded database table). Rejected because: does not meet the 2M-timers-per-node × N-node cluster-capacity target in §4; the single write-contention point (§28, §29) becomes the ceiling long before this blueprint's throughput targets are reached.

Alt B — Global Binary-Heap Priority Queue (No Wheel)

        +------------------+
        | ScheduleRecord    |
        | inserts           |
        +---------+--------+
                  v
        +------------------+
        | one shared        |  O(log n) insert/cancel,
        | binary min-heap   |  single global lock
        +---------+--------+
                  v
        +------------------+
        | dispatch + workers |
        +------------------+

Regime where it wins: low timer counts (< 100K) where O(log n) heap operations are cheap enough in absolute terms and the wheel's bucket-management complexity is not worth its own maintenance cost. Real system embodying it: general-purpose event-loop timer heaps such as libuv's uv_timer subsystem, used by Node.js — a single-process min-heap, not a distributed scheduler, but the algorithmic pattern this alternative would scale out. Rejected because: a global lock around one heap recreates exactly the contention MM8 (§30) predicts sharding would avoid, and O(log n) per operation does not hold up at the 2M-timers/node insertion/cancellation rate this blueprint targets (§32).

Alt C — Fully Consensus-Replicated Per-Timer State

        +------------------+
        | ScheduleRecord    |
        | write             |
        +---------+--------+
                  v
        +------------------+
        | Raft log, one     |  every append needs a
        | round per shard   |  consensus round-trip
        +---------+--------+
                  v
        +------------------+
        | wheel + dispatch   |
        +------------------+

Regime where it wins: when durability requirements exceed "zero tolerance for crash-induced loss" (I1) to also require surviving Byzantine or arbitrary-fault coordinator behavior, not merely crash failures — regulatory or adversarial-tenant environments where a compromised coordinator node itself is an explicit threat. Real system embodying it: etcd's own Raft core, or a TiKV-style per-region Raft group applied at per-timer granularity. Rejected because: full per-timer Raft replication multiplies WAL-append latency by a consensus round-trip, violating the §4 p95 ingest-latency budget, for a guarantee (Byzantine resistance) this system's threat model (§22) does not require — tracked as PhaseDeferred("§16") in §35.

Alt D — Push-Based Host-Local Timers, No Central Coordinator

        +----------+  +----------+  +----------+
        | Host A    |  | Host B    |  | Host C    |
        | local cron |  | local cron |  | local cron |
        +----------+  +----------+  +----------+
        (no cross-host coordination, ownership, or failover)

Regime where it wins: fleets where each host's schedule is genuinely independent — no cross- host deduplication, no failover requirement, no durability guarantee beyond the host's own disk. Real system embodying it: systemd timers (or classic cron(8)) deployed fleet-wide via external configuration management. Rejected because: it violates the shard-aware timer- ownership and exactly-once-scheduling-commit goals stated in §1 — no mechanism exists to prevent duplicate or lost execution across host replacement, which is exactly the class of failure this blueprint's shard-coordinator (§16) exists to close.
