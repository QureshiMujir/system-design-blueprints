⬜ Phase 0 — Repository Bootstrap and Deterministic Foundations §12

Objectives

Establish a deterministic Cargo workspace, shared type contracts (common-types), tracing conventions, and reproducible CI before any scheduling logic exists. Scope: no wheel, no WAL, no dispatch yet — this phase produces the skeleton every later phase builds inside. Constraint introduced: all later crates must compile against common-types without circular deps.

Deliverable

A reproducible workspace build (cargo build --workspace --locked byte-identical across two CI runners) and an executable integration-test harness binary inside conformance-suite that other phases extend rather than replace.

Acceptance

Deterministic builds: SHA-256 of the release binary matches across 2 independent CI runners for 10 consecutive runs. Zero unsafe blocks outside crates/wheel-engine/src/bucket.rs (the one pre-approved lock-striping module). Trace IDs propagate across 100% of test RPCs in conformance-suite's smoke suite (≥ 50 fixture-driven cases).

Fixtures

fixtures/bootstrap/invalid-config.toml — malformed TOML config, expects a typed parse error, not a panic. fixtures/bootstrap/schema-evolution-v1.bin — a v1-encoded ScheduleRecord decoded by the v1 schema to pin the baseline wire format before any evolution occurs in §25.

Pitfalls

Nondeterministic timestamp injection into test fixtures (using SystemTime::now() inside a "deterministic" test breaks reproducibility) · root cause: forgetting the monotonic-clock discipline (P8) even in test code · debug via: grep CI logs for two runs with differing binary hashes, bisect by module · signal: cargo build --locked hash drift · recovery: inject a fake clock trait everywhere, ban SystemTime::now() outside one adapter. Unstable protobuf field ordering across protoc versions · root cause: unpinned protoc binary version · signal: serialization round-trip fixture mismatch · recovery: pin protoc version in CI container. Hidden panic propagation across tokio::spawn boundaries silently killing a task · root cause: missing panic hook · debug: panic = "abort" in test profile to surface it loudly · signal: a task silently stops emitting metrics · recovery: install a global panic hook that logs and increments a counter before any spawn.

⬜ Phase 1 — WAL and Durable Persistence §13

Objectives

Implement the append-only durability pipeline (durable-log) that is the sole source of truth for schedule durability (P1, I1). Scope: segment rotation, checksummed records, fsync batching, corruption detection, sparse index, replay cursors, tombstones, compaction markers. Constraint introduced: nothing downstream (wheel, dispatch) may treat a record as real until this crate confirms fsync.

Deliverable

A durable append/replay engine: cargo run -p durable-log --example append_bench appends and fsyncs records at the target rate; a companion replay path reconstructs identical in-memory state from any prefix of segments.

Acceptance

Survives a power-interruption simulation (SIGKILL mid-append, 500 iterations) with zero non-recoverable corruption. Replay is byte-identical across 3 independent replay runs on the same segment set (I5). Corruption detection catches 100% of single-bit-flip injections in fixtures/wal/crc-mismatch.bin (≥ 200 injected cases). WAL amplification measured at < 1.8x per §4.

Fixtures

fixtures/wal/truncated-segment.bin — segment cut mid-record, expects clean truncation-point detection, not a panic. fixtures/wal/crc-mismatch.bin — single-bit-flip corruption, expects rejection at the corrupted record and successful replay of everything before it. fixtures/wal/replay-ordering.bin — interleaved-append-order regression fixture, expects identical replay order across runs. fixtures/wal/wal-gap-detection.bin — a missing LSN in sequence, expects a gap alarm rather than silent skip.

Pitfalls

Partial page writes on power loss leaving a record half-written but checksum-passing on a stale page-cache read · root cause: not fdatasync-ing before considering a write durable · debug via fault-injection at the syscall layer · signal: replay divergence only under real power-loss testing, never in normal CI · recovery: never trust a write durable until fsync returns. Torn fsync windows where batching groups writes but the process crashes between two appends in the same batch · root cause: assuming the whole batch is atomic · signal: some records in a batch replay, others don't · recovery: per-record checksums make torn batches self-describing — this is why every record, not just the segment, is checksummed. Replay duplication when a checkpoint is taken but not fsynced before a crash · root cause: checkpoint observability didn't wait for its own durability · signal: replay_divergence_total fires lower than expected on restart · recovery: checkpoint writes go through the same fsync gate.

⬜ Phase 2 — CRON Parsing and Normalization §14

Objectives

Build deterministic schedule normalization (cron-parser, timer-normalizer): parse POSIX five-field CRON grammar, resolve timezone/DST ambiguity, canonicalize into TriggerDefinition. Scope excludes calendar-aware business-day scheduling (deferred, PhaseDeferred("§14"), §35). Constraint: no malformed schedule may reach durable-log — rejection happens here.

Deliverable

A canonical normalized schedule engine: given a raw CRON string plus timezone, deterministically produces a TriggerDefinition::Cron value and a bounded recurrence preview.

Acceptance

Parser fuzz corpus stable across 10M cargo-fuzz iterations with zero panics/crashes. DST replay deterministic: 100% of fixtures/cron/dst-fold-cases.json (≥ 40 cases spanning both fall-back and spring-forward) resolve identically across 5 repeated runs. Malformed-input rejection rate: 100% of fixtures/cron/malformed-cron-corpus.txt (≥ 150 cases) rejected with a typed error, zero silent acceptance.

Fixtures

fixtures/cron/malformed-cron-corpus.txt — invalid step overflow (*/0), out-of-range fields, malformed list syntax; expects typed rejection. fixtures/cron/dst-fold-cases.json — spring-forward/fall-back boundary cases across multiple IANA zones; expects deterministic resolution per the rule above. fixtures/cron/leap-second-cases.json — schedules crossing a leap-second insertion; expects the schedule to treat leap seconds as a non-event (monotonic scheduling math ignores them, per P8) rather than double-firing.

Pitfalls

Leap-second ambiguity if any code path reads wall-clock time directly for interval math instead of routing through the monotonic-clock abstraction from Phase 0 · root cause: a shortcut that bypassed P8 · debug via: replay the same schedule across a simulated leap-second boundary and diff fire times · signal: a FIXED_INTERVAL schedule drifts by exactly one second near a known leap-second date · recovery: audit every Timestamp read for a bypassed clock abstraction. Locale-dependent parsing if the underlying date library defaults to system locale for month/day name parsing · root cause: relying on locale-sensitive stdlib functions · signal: a CI runner in a different locale fails a fixture that passes elsewhere · recovery: pin all name-based parsing to a fixed locale table, never system locale.

⬜ Phase 3 — Hierarchical Timer Wheel §15

Objectives

Implement the scalable timer-wheel runtime (wheel-engine): multi-level wheels, bucket migration, monotonic tick source, cancellation index. This is the latency-critical hot path sized against the 2M-timers/node and p99-dispatch-latency budgets in §4. Constraint: every insert must have already passed the WAL durability gate (I6).

Deliverable

A runnable wheel scheduler: cargo run -p wheel-engine --example wheel_bench sustains the target insertion/expiration rate against a synthetic timer population.

Acceptance

2M timers/node sustained in the benchmark harness with p99 dispatch latency < 150 ms (§4). Bucket-lock contention (bucket_lock_wait_ns p99) stays under 500 μs at target load. Cancellation completes in < 1 ms p99 regardless of wheel population size (verifying O(1) via the cancellation index, not a scan).

Fixtures

fixtures/wheel/bucket-overflow.bin — a bucket receiving more timers than its pre-sized capacity in one tick; expects graceful dynamic growth, not a panic or drop. fixtures/wheel/ migration-storm.bin — a burst of timers all migrating from a high wheel level to the lowest level in the same tick; expects bounded migration batching, not a tick stall. fixtures/wheel/wheel-drift-regression.bin — a regression fixture pinning a previously observed drift bug (tick thread falling behind wall-clock under sustained load); expects catch-up within the bound in I13.

Pitfalls

Wheel drift when the tick thread is preempted long enough to miss multiple ticks · root cause: tick advancement coupled to OS-scheduler timing without a catch-up mechanism · debug via: inject scheduling delay in the deterministic simulator (§7) and assert I13 · signal: wheel_tick_gap_total rising · recovery: bounded catch-up sweep, never an unbounded "replay all missed ticks synchronously" loop (that itself becomes an unbounded stall). Bucket starvation where a small number of buckets accumulate disproportionate timer counts (e.g. many schedules with the same anchor time) · root cause: insufficient bucket fan-out at a given wheel level · signal: bucket-occupancy histogram (12.10-style export) shows a heavy tail · recovery: increase fan-out or add jitter insertion at normalization time (§8 malformed-input handling adjacent). Migration storms when many timers cross a level boundary simultaneously · root cause: correlated anchor times (e.g. "every hour on the hour" for thousands of tenants) · signal: tick-processing latency spike correlated with round timestamps · recovery: jitter insertion at timer-normalizer (Phase 2) spreads correlated anchors.

⬜ Phase 4 — Shard Coordination and Leasing §16

Objectives

Implement distributed timer-partition ownership (shard-coordinator, lease-manager): etcd-backed leases, fencing tokens, shard balancing, forced revocation. Scope: single-region only (PhaseDeferred("§16") for geo-distributed and Byzantine-resistant variants, §35). Constraint: no two nodes may hold an active lease for the same shard (I2).

Deliverable

A clustered ownership runtime: a 3-node test cluster demonstrates shard assignment, lease renewal, and a clean handoff on simulated node failure, observable via shard-ownership dashboards (Phase 8 dependency stubbed here).

Acceptance

Zero dual-ownership windows detected across 500 chaos-test iterations (random node kill + partition) — verified against fixtures/shard/dual-ownership-chaos.json. Lease failover completes in < 15 s p99 (§4). Fencing-token rejection rate for stale epochs is 100% in fixtures/shard/fencing-token-replay.bin (≥ 100 replayed-stale-epoch attempts).

Fixtures

fixtures/shard/dual-ownership-chaos.json — scripted node-kill/partition sequence; expects the simulator to detect zero moments of two nodes both believing they own the same shard. fixtures/shard/fencing-token-replay.bin — a stale lease holder replaying old appends after losing ownership; expects 100% rejection at the fencing check. fixtures/shard/ partition-asymmetry.json — a network partition where node A can reach etcd but not node B (and vice versa is not symmetric); expects correct minority-side lease expiry, not a stuck lease.

Pitfalls

Stale lease holders continuing to believe they own a shard after a missed heartbeat renewal · root cause: client-side lease-expiry check running on a delayed local clock rather than trusting etcd's authoritative lease state · debug via: chaos-inject clock delay on the lease-manager process specifically · signal: lease_fencing_rejections_total spikes right after a network-blip recovery · recovery: never let a node self-assert lease validity — always confirm against etcd or via a fencing-token check at the write boundary. Split-brain windows during an asymmetric partition (each side can reach a different subset of etcd members) · root cause: etcd quorum size assumptions violated by network topology · signal: two shard-ownership claims observed simultaneously in the audit trail · recovery: the fencing-token check at the WAL append boundary is the actual safety net — detection here is a defense-in-depth alarm, not the primary correctness mechanism.

⬜ Phase 5 — Dispatch Queue and Worker Runtime §17

Objectives

Build the execution-isolation layer (dispatch-queue, execution-worker, retry-engine): bounded queues, priority dispatch, worker concurrency pools, retry acknowledgement, poison routing. Scope introduces the boundary where scheduling correctness (upstream) meets execution (downstream) and must not leak across it (P10).

Deliverable

A distributed execution subsystem: execution-worker instances pull from shard-local dispatch-queues and demonstrate bounded-queue backpressure signaling to scheduler-api under synthetic overload.

Acceptance

Queue saturation handled gracefully: at 110% of the 100K-dispatches/sec target (§4), ingest returns RESOURCE_EXHAUSTED rather than OOMing, verified over a 10-minute sustained-overload test. Poison-queue routing triggers at exactly max_attempts (verified for max_attempts in {1, 3, 10, 50}) with zero premature or delayed dead-lettering. Duplicate-ACK handling: 100% of fixtures/dispatch/duplicate-ack.json cases (≥ 60) resolve without a double-reschedule.

Fixtures

fixtures/dispatch/duplicate-ack.json — a worker ACK delivered twice (network retry on the ACK itself); expects idempotent handling via dispatch_id (P13), not a double state transition. fixtures/dispatch/poison-queue-routing.json — a schedule whose callback always fails; expects transition to DEAD_LETTER at exactly max_attempts. fixtures/dispatch/ retry-negative-backoff.json — a RetryPolicy with a negative max_backoff_ms (should have been rejected in Phase 2 normalization, but re-checked defensively here); expects rejection, not a crash.

Pitfalls

Unbounded retries if max_attempts is misconfigured to an effectively-infinite value (e.g. a default of u32::MAX) · root cause: no upper-bound validation at schedule-creation time · debug via: retry-backlog-by-classification dashboard (P7) showing one schedule dominating the backlog · signal: retry_attempt_regression_total stays flat but backlog depth for one schedule_id grows unbounded · recovery: enforce a hard ceiling on max_attempts at the API-validation layer, not just the retry-engine. Head-of-line blocking when a single slow callback target occupies a worker-pool slot indefinitely · root cause: no per-dispatch deadline enforcement · signal: worker-pool utilization pinned at 100% with falling completed-dispatch rate · recovery: enforce DispatchEnvelope.deadline as a hard timeout, treat expiry as a failure feeding the retry-engine.

⬜ Phase 6 — Replay and Recovery §18

Objectives

Implement deterministic recovery: replay cursors, snapshot restoration, replay checksums, ordering validation, closing the loop opened by Phase 1's WAL and Phase 3's wheel. Constraint: replay output must be bit-identical to the pre-crash state for the same WAL prefix (I5, P5).

Deliverable

A crash-recovery runtime: replay-cli replay --segment-dir <path> reconstructs full wheel state from a segment directory and reports a structural checksum matching the pre-crash value recorded in a companion test harness run.

Acceptance

Replay produces identical wheel state (structural checksum match) across 3 independent runs for every fixture in fixtures/replay/ (≥ 30 cases). Snapshot-restore path completes within the 90 s / 50M-timer budget (§4), verified at 10M, 25M, and 50M timer scales. Zero divergence across fixtures/replay/checksum-divergence.bin's regression case after the fix that produced it.

Fixtures

fixtures/replay/partial-compaction.bin — replay starting mid-way through an interrupted compaction pass; expects correct reconstruction from the pre-compaction segment plus whatever the new segment had durably written. fixtures/replay/checksum-divergence.bin — a regression fixture pinning a previously observed divergence (hash-map iteration order leaking into bucket construction order); expects stable structural-checksum match post-fix. fixtures/replay/ snapshot-restore.bin — a full snapshot-segment restore at scale; expects the 90 s budget met and a checksum match against the live-replay path (two independent recovery mechanisms must agree).

Pitfalls

Replay nondeterminism from iterating a HashMap during bucket reconstruction instead of a BTreeMap or explicit LSN-ordered vector · root cause: convenience data structure choice leaking into an observably-ordered code path · debug via: run replay twice with a randomized hash-seed (Rust's default HashMap is seeded per-process) and diff the structural checksum · signal: checksum mismatch that only appears cross-process, never within one process · recovery: audit every replay-path data structure for hash-dependent iteration and replace with an explicitly ordered structure — this is exactly the class of bug fixtures/replay/ checksum-divergence.bin pins down.

⬜ Phase 7 — Observability and Diagnostics §19

Objectives

Implement production diagnostics (metrics-pipeline, tracing-layer, admin-console read paths): OpenTelemetry spans, RED metrics, queue-depth metrics, replay diagnostics, shard dashboards. Scope: this phase makes every invariant and failure mode defined in §7, §22, §23 actually observable — it does not add new correctness logic.

Deliverable

An operational observability stack: a Grafana-compatible dashboard set (defined as JSON templates under docs/performance/) rendering RED/USE metrics and a trace-correlated dispatch-lag view, backed by Prometheus scraping and an OpenTelemetry collector.

Acceptance

Full trace correlation: 100% of dispatches in a 10K-schedule synthetic load test have a complete span chain from wal.append through worker.execute with zero orphaned spans. Metric cardinality bounded: total active label-set combinations stay under 50K per metric name at 10K-tenant scale (verified against fixtures/observability/high-cardinality-labels.json).

Fixtures

fixtures/observability/high-cardinality-labels.json — a synthetic load pattern designed to blow up label cardinality if the bounded-cardinality rule (19.2) is violated; expects bounded growth, not an unbounded label explosion. fixtures/observability/exporter-outage.json — a simulated metrics-exporter outage; expects local buffering with bounded memory (P4) and no crash, followed by successful backfill on exporter recovery.

Pitfalls

High-cardinality labels leaking schedule_id or raw tenant metadata into a metric label instead of a trace attribute · root cause: conflating "goes on every span" (fine, high cardinality acceptable in tracing) with "goes on every metric series" (not fine — metrics aggregate, traces don't) · debug via: cardinality-explosion alert on the metrics backend itself · signal: Prometheus/metrics-pipeline memory growth unrelated to timer count · recovery: audit every metric!() call site for accidental unbounded labels; move detail to span attributes instead.

⬜ Phase 8 — Security and Multi-Tenancy §20

Objectives

Implement tenant isolation: mTLS, RBAC, quota enforcement, audit logging, tenant-scoped metrics. Scope: this phase is where the multi-tenant-isolation promise in §1 becomes enforced rather than assumed. Constraint: no tenant may observe another tenant's schedules, metrics, or quota state.

Deliverable

A secure multi-tenant runtime: two synthetic tenants under load simultaneously demonstrate zero cross-tenant data visibility in admin-console, zero quota bleed-through, and a complete audit trail for every administrative action taken during the test.

Acceptance

Tenant isolation validated: 100% of fixtures/security/tenant-isolation-breach.json attempts (≥ 40 crafted cross-tenant access attempts) rejected at the RBAC boundary. Quota enforcement: 100% of fixtures/security/quota-bypass-attempt.json cases (≥ 25) correctly rejected once TenantQuota.max_insert_rate_per_sec is exceeded, with < 50 ms enforcement-decision latency p99.

Fixtures

fixtures/security/expired-cert.pem — an expired client certificate presented at mTLS handshake; expects clean connection rejection, not an ambiguous timeout. fixtures/security/ quota-bypass-attempt.json — a scripted burst designed to race the quota-check window; expects the sharded-counter design to hold under the race, not permit a burst-through. fixtures/ security/tenant-isolation-breach.json — crafted requests attempting to read or cancel another tenant's schedule_id; expects rejection at RBAC, not a 404-that-leaks-existence.

Pitfalls

Quota bypass via a race between the atomic-counter check and the counter increment (check-then- act race) · root cause: non-atomic check-and-increment across a distributed counter shard · debug via: high-concurrency fuzz test hammering the same tenant's quota boundary · signal: quota_ledger_drift_total (I14) non-zero under load · recovery: make the check-and-increment a single atomic operation (CAS loop or an atomic fetch-and-add with post-hoc rejection-and-refund for the rare overshoot, reconciled against the durable ledger).

⬜ Phase 9 — Production Hardening §21

Objectives

Validate operational stability end-to-end: chaos testing, soak testing, WAL-corruption testing, clock-skew testing, rolling-upgrade validation. Scope: this phase does not add new subsystems — it proves the previous nine hold up under sustained, combined, adversarial conditions. Exit gate for the production-candidate release (§38).

Deliverable

A production-candidate release: a tagged, signed release artifact (ADR-21) that has passed the combined chaos/soak/corruption/clock-skew/rolling-upgrade gate and is eligible for staged production rollout.

Acceptance

30-day soak stability: zero unplanned restarts, RSS growth < 5% over the 30-day window (bounding the < 8 GB budget in §4), heap fragmentation staying under 15%. Chaos-combined test suite: zero I1–I14 invariant violations across 1,000 combined-fault iterations. Rolling upgrade: zero dispatch-correctness regressions across a full N-1 mixed-version cluster run of fixtures/hardening/rolling-upgrade-partial.json.

Fixtures

fixtures/hardening/clock-skew-injection.json — NTP-step and gradual-drift scenarios; expects zero P8 violations (no spurious immediate/delayed firing from wall-clock jumps). fixtures/hardening/rolling-upgrade-partial.json — a cluster frozen mid-rolling-upgrade (half old version, half new); expects full dispatch correctness across the mixed-version boundary. fixtures/hardening/soak-leak-regression.json — a regression fixture pinning a previously observed slow leak; expects bounded RSS growth over an accelerated soak replay.

Pitfalls

Latent memory leaks that only manifest past the timescale of any individual phase's tests · root cause: a slow leak in a low-frequency code path (e.g. rebalance-triggered cleanup that misses one allocation per rebalance) · debug via: heap-profiling snapshots at fixed soak-test intervals, diffed against a baseline · signal: RSS creeping upward with no corresponding timer-count growth · recovery: bisect via interval-diffed heap snapshots to the specific rebalance/replay/retry code path leaking, not a general "restart nodes periodically" workaround (which masks rather than fixes the leak).
