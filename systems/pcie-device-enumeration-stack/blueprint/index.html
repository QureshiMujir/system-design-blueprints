1. Goal & Scope

Engineering definition. Build, from first principles, a PCI Express device enumeration stack: the software layer that walks firmware-exposed configuration space (ACPI MCFG / ECAM), discovers the PCIe hierarchy (root complexes, root ports, switches, bridges, endpoints, multi-function devices), parses standard and extended capability chains, sizes and assigns Base Address Register (BAR) windows, constructs a canonical in-memory topology graph, and exposes that graph — with full observability and deterministic replay — to the rest of the kernel or hypervisor. This is not a userspace lspci clone. It is a reusable systems subsystem meant to sit at the trust boundary between untrusted firmware/hardware state and every driver, IOMMU mapping, and interrupt route built on top of it.

Phase 0 (§12) produces the following crates:

  1. pcie-types — canonical address, device, and capability value types.
  2. pcie-platform-abstraction — architecture-specific MMIO, barrier, and page-mapping primitives.
  3. pcie-config — PCI configuration-space register and header layout definitions.
  4. pcie-acpi — RSDP/XSDT/MCFG parsing and ECAM window derivation.
  5. pcie-ecam — validated, retried, timed configuration-space read/write access.
  6. pcie-enumerator — recursive bus/bridge/function walker.
  7. pcie-capabilities — standard + extended capability chain parser (MSI, MSI-X, PM, PCIe, vendor).
  8. pcie-resource — BAR sizing, MMIO/IO window allocation, overlap prevention.
  9. pcie-topology — canonical device graph, stable IDs, immutable snapshots.
  10. pcie-hotplug-core — hotplug event queue, debounce, topology mutation, rebalance.
  11. pcie-tracing — structured spans, metrics, replay checkpoints (mandatory, not optional).
  12. pcie-replay — deterministic event capture and replay.
  13. pcie-conformance — fixture validation, differential testing, fuzz harness wiring.
  14. pcie-errors — shared error taxonomy across every crate above.
  15. pcie-cli — operator diagnostic and replay-inspection tool.
  16. pcie-test-harness — QEMU q35 orchestration for CI and soak tests.

System boundaries — provides: PCIe bus scanning; capability parsing; ECAM mapping and access; ACPI MCFG parsing; device-graph construction; MMIO/IO resource assignment; interrupt capability enumeration (MSI/MSI-X presence, not routing); hotplug event pipeline; structured tracing; deterministic replay; conformance/fuzz validation; a stable kernel-facing enumeration API.

Delegates (does not implement, but defines the interface boundary for): interrupt controller programming (APIC/GIC routing) — consumed via the capability data this stack exposes; DMA-engine and IOMMU page-table setup — consumed via the topology this stack publishes.

Does NOT provide: full PCIe device drivers; DMA engine implementations; IOMMU implementation; NVMe/SATA/network protocol stacks; GPU runtime integration; SR-IOV VF provisioning (see PhaseDeferred("§17")); PCIe peer-to-peer DMA orchestration; PCIe fabric security isolation; full Advanced Error Reporting (AER) recovery flows (see PhaseDeferred("§21")); PCIe transaction-layer packet (TLP) implementation.

Non-goals for Phase 0: runtime ASPM optimization; PCIe link retraining; SR-IOV orchestration; ATS/PASID/PRI management (see PhaseDeferred("§16")); a full ACPI/AML interpreter; firmware emulation; device-passthrough orchestration; NUMA-aware BAR placement (see PhaseDeferred("§18")); CXL protocol support (see PhaseDeferred("§13")); Thunderbolt-tunneled PCIe.

Deployment model. Primary: 64-bit x86_64 kernel-space, early boot, before general driver loading, before the scheduler is fully online, single-core bootstrap transitioning safely into SMP. Secondary: ARM64 server-class systems; hypervisor-hosted bare-metal labs; QEMU-based deterministic CI. The stack is linked directly into the kernel/hypervisor image, not run as a userspace daemon, except for pcie-cli and pcie-conformance, which run in userspace against captured replay traces or a live /dev/pcie-topology-style export.

Target operators: kernel engineers, hypervisor engineers, firmware engineers, systems researchers, OS implementers (primary); PCIe validation teams, observability engineers, platform bring-up engineers, hardware-enablement engineers (secondary). Operators must be able to inspect discovered topology, replay enumeration traces, analyze malformed devices, inspect BAR-allocation failures, debug firmware inconsistencies, and validate ECAM mappings — entirely offline, from a captured trace, without re-booting hardware.

What later phases unlock: full kernel driver-model integration; SR-IOV VF enumeration; multi-root fabric support; virtualization-aware enumeration (SR-IOV PF/VF, passthrough); hotplug orchestration at fleet scale; PCIe fault injection; AER recovery; IOMMU topology coupling; CXL device discovery.

Recommended language: Rust. Rationale: ownership semantics eliminate the aliased-mutable-MMIO class of bug without runtime cost; deterministic resource management (no GC pause during enumeration, which runs before the scheduler); predictable #[repr(C)] layout control for config-space structs; enum modeling makes DeviceState/Capability exhaustive by construction; explicit concurrency (no implicit thread spawning) matches the pre-SMP execution model; mature no_std support for kernel-space linkage; trait-based abstraction over ConfigAccessor / ResourceAllocator without vtables in the hot path; strong serialization ecosystem (zerocopy, bytemuck) for replay wire formats; clean FFI for the firmware-stub boundary. Selective C is permitted for firmware stubs, architecture bootstrap trampolines, and assembly entry points only.

Rejected: C — memory unsafety risk is unacceptable at a firmware/OS trust boundary handling untrusted config-space bytes. C++ — ABI instability across compilers complicates kernel-image linkage and the ADR-01 reproducibility goal. Zig — verification tooling (Miri-equivalent, fuzz ecosystem) is too immature in 2026 for a project whose correctness bar requires I1–I12. Go — GC pauses and a runtime scheduler are incompatible with pre-scheduler kernel-space execution.

Prerequisites: operating-systems internals; PCI Express architecture; memory-mapped IO; ACPI specification structure; interrupt delivery systems; cache coherency and CPU memory ordering; lock-free/lock-ordered structures; kernel initialization sequencing; binary serialization; x86 paging internals; ARM64 memory attributes; deterministic replay systems.

Estimated timeline: Phase 0 — 8–12 weeks. Full ten-phase core enumeration stack (§12–§21) — 4–6 months. Production hardening (differential + fuzz + soak, §21) — 2–4 months beyond core. Hypervisor integration — 2 months. Multi-platform (x86_64 + ARM64) validation — 2 months.

2. Why Build This

PCIe enumeration is the earliest trust-establishment layer between firmware and operating system. Every storage controller, network adapter, GPU, accelerator, NVMe subsystem, and high-performance peripheral in a modern datacenter is discovered through this exact code path before any driver touches it. Get it wrong and the failure modes are not cosmetic: BAR overlap corruption, invalid MMIO access, interrupt-routing failures, DMA corruption, boot instability, kernel panics, and silent data corruption that surfaces days later in an unrelated subsystem.

Historical context. PCIe replaced PCI, AGP, and PCI-X specifically because those buses could not scale bandwidth per pin or support hot-pluggable, switched topologies. Composable infrastructure — NVMe storage, RDMA fabrics, GPU/FPGA acceleration, SmartNICs — is built entirely on PCIe's point-to-point switched model, which is exactly what makes its topology variable and its enumeration non-trivial: unlike parallel PCI's shared bus, PCIe's tree of switches means the enumerator must recurse through bridges it discovers dynamically, not iterate a fixed bus width.

Why build it from scratch instead of reading drivers/pci/. Reading mature code teaches vocabulary. Building the same subsystem under explicit invariants (I1–I12), a byte-identical replay requirement (I7), and a bounded-resource discipline (P4) teaches why each piece of that mature code exists — the quirks tables, the retry loops, the lock ordering — because you hit the failure each guards against yourself, in a QEMU fixture, with a stack trace.

Production engineering concepts exercised: topology indexing under concurrent mutation; capability negotiation over untrusted linked lists; bounded allocator design; lock-ordering invariants under hotplug; replay-safe structured logging; binary schema compatibility; cache-aware graph traversal; telemetry aggregation; failure containment that isolates one malformed device without failing the whole boot.

Related systems projects this blueprint cross-links with conceptually: kernel memory managers (BAR/MMIO placement shares allocator theory with page allocators); interrupt controllers (MSI/MSI-X capability data feeds APIC/GIC routing); ACPI parsers (MCFG is one table among many); NVMe/IOMMU stacks (both consume this stack's topology as their bring-up input); hypervisors (SR-IOV/passthrough enumeration extends this exact walker); distributed tracing stacks (pcie-tracing's span model is the same discipline as a request-tracing system, just node-local).

What Mastery Looks Like

  • Can explain, from the ECAM address-derivation formula alone, why bus-number width bounds Max devices per segment in §4 and why that bound reappears in §32's capacity arithmetic — gained in Phase 1 (§13) and Phase 3 (§15).
  • Can design a capability parser that terminates on an adversarial cyclic linked list without a visited-set allocation per device — gained in Phase 4 (§16).
  • Can reason about lock ordering (I6) well enough to predict, before running it, which of two candidate hotplug-rebalance designs deadlocks under concurrent scan — gained in Phase 7 (§19).
  • Can build a replay format that is byte-identical across two machines with different core counts by removing wall-clock and iteration-order nondeterminism at the source — gained in Phase 8 (§20).
  • Can quantify BAR-allocator fragmentation instead of asserting it is "acceptable" — gained in Phase 5 (§17) and reused in §28/§32.
  • Can distinguish a firmware bug from a real device fault from a driver bug using only a replay trace and no access to the original hardware — gained in Phase 8 (§20) and Phase 9 (§21).
  • Can articulate, for each of the 28 ADRs in §9, the concrete regime in which the rejected alternative would have been the right choice — gained across §9 and §34.

Firmware / Hardware Layer. The hardware trust boundary. All bytes crossing it — ACPI tables, ECAM MMIO reads, interrupt-fabric metadata — are untrusted input (P7); firmware bugs and malformed hardware are production realities, not hypotheticals.

pcie-platform-abstraction. Isolates x86_64/ARM64 differences: page attributes, ordering barriers, cache behavior, alignment, fault containment. The only crate permitted unsafe blocks outside a narrow audited allowlist (ADR-19, P13).

pcie-acpi. Parses RSDP → XSDT → MCFG. Validates segment ranges, ECAM boundaries, bus windows, root-complex metadata. Rejects malformed firmware state before enumeration starts (fail-closed, P7).

pcie-ecam. The sole path for configuration-space access. Owns alignment enforcement (I1), retry bounding (I11), timeout detection, and per-device quarantine on repeated fault.

pcie-enumerator. Recursive traversal: bridges, endpoints, functions, multi-function devices, subordinate buses. Deterministic ordering (P1) — the same firmware topology always yields the same scan order.

pcie-capabilities. Standard-list (offset 0x34) and extended-chain (offset 0x100) parsing with mandatory cycle detection (I5). A malformed vendor chain degrades one device, not the boot (P11).

pcie-resource. BAR probing/sizing, interval-tree allocation, non-overlap enforcement (I3), alignment enforcement (I8), rollback on partial failure.

pcie-topology. The single writer of canonical device state (P5). Stable IDs across rescans (I4), generation-counter snapshot publication (I10) so readers never observe a torn mutation.

pcie-tracing. Mandatory structured telemetry: spans keyed by DeviceAddress, Prometheus metrics, replay checkpoints. Bounded producers (P9).

pcie-hotplug-core. Owns the only path that mutates topology after initial scan: event queue, debounce, insert/remove, bridge-window rebalance, generation swap.

pcie-replay. Append-only, checksum-validated, deterministically replayable event log (I7, P6). The forensic and CI-regression backbone of the whole stack.

pcie-conformance. Fixture replay, fuzzing (ACPI/capability/replay decoders), and differential testing against Linux drivers/pci/ and FreeBSD sys/dev/pci topology output.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: enumeration order is a pure function of firmware topology and (bus, device, function) ordering · Tradeoff: forbids parallel speculative bus walks that could reorder discovery for speed · Operational: CI diffs replay traces against golden captures · Violated: replay diffs go noisy, masking real regressions inside boot-order jitter.
  • P2 — Observability By Default. Rule: every config access, allocation decision, and topology mutation emits a span and a metric · Tradeoff: ~hundreds of ns overhead per config access · Operational: dashboards track config latency at p50/p95/p99 · Violated: an enumeration stall is invisible until a boot-timeout watchdog fires with no root cause attached.
  • P3 — Crash-Only Recovery. Rule: no subsystem depends on graceful shutdown for consistency · Tradeoff: recovery goes through the replay log, not a cheaper in-memory checkpoint · Operational: pcie-replay archives are the sole recovery source of truth · Violated: a killed enumerator leaves a half-populated topology with nothing recording that it is half-populated.
  • P4 — Bounded Resource Usage. Rule: every queue, cache, and replay buffer has a fixed capacity set at construction · Tradeoff: producers must apply backpressure or drop under load · Operational: hotplug_queue_depth exported as a metric · Violated: a hotplug flap storm exhausts the 32 MB bootstrap heap (§4) and panics the boot path.
  • P5 — Explicit Ownership. Rule: TopologyGraph is the sole writer of PciDevice state; every other crate holds a read-only snapshot · Tradeoff: mutation must funnel through pcie-hotplug-core even for the benign single-device case · Operational: single-writer discipline simplifies I6's lock order · Violated: two crates mutate BAR state concurrently and produce a torn write no invariant check can attribute.
  • P6 — Stable Wire Compatibility. Rule: the pcie-replay binary schema only grows additively · Tradeoff: dead fields persist across schema versions, growing artifact size · Operational: a version tag is checked before decode · Violated: an old replay reader misdecodes a newer trace instead of failing closed.
  • P7 — Parse Nothing Lazily Without Validation. Rule: every firmware/config byte is bounds-checked, alignment-checked, and checksum-checked before use · Tradeoff: parse cost scales with table size even for well-formed input · Operational: pcie-acpi rejects a malformed MCFG before any ECAM window is trusted · Violated: a truncated ACPI table drives ECAM address math past the mapped MMIO region.
  • P8 — Topology Mutation Isolation. Rule: hotplug mutation and reader traversal never observe each other's partial state · Tradeoff: mutation publishes a new generation rather than editing in place · Operational: the generation counter increments under the topology lock (I6) · Violated: a reader mid-traversal follows a freed BridgeEdge into remapped memory.
  • P9 — Backpressure Everywhere. Rule: telemetry and replay producers block or drop under a documented policy, never grow unbounded · Tradeoff: sustained load drops some trace events, counted, not silently lost · Operational: dropped_trace_events_total exported · Violated: an unbounded ring fills the bootstrap heap during a sustained fuzz run.
  • P10 — Lock Ordering Discipline. Rule: locks acquire in the I6 order — segment → topology → device → capability — with no exceptions · Tradeoff: some fast paths take an uncontended-but- unnecessary lock hop · Operational: Miri plus a runtime lock-order assertion catch violations · Violated: a hotplug rebalance and a concurrent scan deadlock under load.
  • P11 — Capability Parsing Isolation. Rule: a malformed capability chain quarantines the owning device, never the enumeration pass · Tradeoff: a hostile device can force itself into DeviceState::Failed but cannot block siblings · Operational: malformed_capability_count is tracked per segment · Violated: one vendor's cyclic capability list halts discovery of every device downstream of it.
  • P12 — Allocation Transparency. Rule: every BAR/window allocation decision is replayable and diffable against a prior run · Tradeoff: the allocator must be deterministic, ruling out randomized first-fit · Operational: pcie-resource emits an AllocationEvent per decision · Violated: two boots on identical hardware disagree on BAR placement with no diagnosable cause.
  • P13 — Minimal Unsafe Surface. Rule: unsafe Rust is confined to pcie-platform-abstraction and audited per ADR-19 · Tradeoff: every other crate pays a safe-wrapper abstraction cost · Operational: unsafe-block count per release tracked in CI · Violated: an aliasing MMIO bug in an unrelated crate becomes unreviewable because unsafe is scattered.
  • P14 — Schema Evolution Discipline. Rule: every persisted structure (ReplayEvent, TopologySnapshot) carries an explicit version field · Tradeoff: readers carry N-version decode paths instead of one · Operational: a version mismatch fails closed with a diagnostic, never a best-effort guess · Violated: a replay reader silently misinterprets a newer trace's field layout.

Debugging methodology: every invariant above is checked by exactly one runtime assertion plus one deterministic-simulator test in pcie-conformance that drives the system into the boundary condition on purpose (cyclic capability list for I5, concurrent hotplug during snapshot read for I10, and so on). The simulator replays a fixed random seed through pcie-replay, so an invariant violation reproduces byte-for-byte on a developer's laptop from the CI failure artifact alone — no live hardware or QEMU session is required to debug it.

8. Domain Model — PCIe Address Space, Capability Protocol & Enumeration State Machine

Canonical address tuple. (segment, bus, device, function) — printed conventionally as 0000:3b:00.0 (segment:bus:device.function, hex). Segment is a PCI domain (multiple host bridges on large systems); bus/device/function together select one configuration-space register file.

ECAM address derivation (PCI Express Base Specification): given a per-segment ECAM base address from MCFG,

ecam_address = ECAM_BASE
             + (bus      << 20)
             + (device   << 15)
             + (function << 12)
             + register_offset

Bus occupies 8 bits, device 5 bits, function 3 bits, register offset 12 bits (4 KB extended config space per function) — the field widths that directly justify the §4 topology-size budgets.

Device state machine:

State Meaning
Undiscovered no scan performed yet
Probing a config access is in flight
Identified vendor/device ID read and validated non-0xFFFF
CapabilityParsing capability chain walk in progress
ResourceAssigned BAR allocation complete for this device
Active published in the topology snapshot, visible to consumers
Failed malformed or inaccessible; quarantined, not retried
Removed hotplug removal processed, node retired

Enumeration sequence (Phase 3, §15): Root Complex → Scan Bus → Read Vendor ID → Identify Header Type → Parse BARs → Parse Capabilities → if Header Type 1 (bridge): Assign Secondary/Subordinate Bus → Recurse into the new bus. Header Type 0 is an endpoint function; Header Type 2 (CardBus) is explicitly out of scope for Phase 0 and is rejected, not silently skipped.

Capability parsing rules (Phase 4, §16): the standard capability linked list starts at config offset 0x34, is 4-byte aligned, and terminates on a null next-pointer. The PCIe extended capability chain starts at offset 0x100, is 4-byte aligned, and uses a 12-bit next-pointer field with next-pointer semantics enforced against I5 (loop detection). Failure path: a malformed cycle (capability A → capability B → capability A) is detected by a bounded-size visited-offset bitmap, parsing aborts, the device is marked Failed/degraded, and topology enumeration continues past it — per P11, isolation of a malformed device must never abort the whole scan.

BAR sizing sequence (Phase 5, §17): save the original BAR value; write all-1s; read back the size mask; restore the original value; compute the required alignment from the mask; reserve the allocation against pcie-resource's interval tree before ever touching hardware state again.

Hotplug mutation sequence (Phase 7, §19): Event Interrupt → Hotplug Queue (debounced, bounded per P4) → Topology Lock (I6 order) → Remove/Insert → Resource Rebalance → Publish new generation snapshot (I10). Readers mid-traversal against the prior generation are unaffected.

11. Core Schema & Types

DeviceAddress — fields: segment: u16, bus: u8, device: u8, function: u8. Ownership: immutable value type. Mutation: none — reconstructed, never mutated in place. Concurrency: Copy, safe to pass across threads without synchronization. Persistence: stable hash identity, used as the replay-log primary key. Serialization: fixed 4-byte little-endian layout via bytemuck::Pod. Compatibility: field order and width are frozen; new address components are additive only.

PciDevice — fields: address: DeviceAddress, vendor_id: u16, device_id: u16, header_type: HeaderType, bars: Vec<BarDescriptor>, capabilities: Vec<Capability>, state: DeviceState. Ownership: exclusively owned and mutated by pcie-topology (P5). Mutation: guarded — writers hold the device lock at I6's third position. Concurrency: read-mostly; readers hold a generation-scoped snapshot reference, never the live node. Persistence: appears in TopologySnapshot; not itself independently persisted. Serialization: serde for snapshot export (JSON/CLI), zerocopy for the hot allocation path. Compatibility: additive-only field growth per P14; capabilities is length-prefixed to tolerate future variants.

BarDescriptor — fields: index: u8, kind: BarKind, base: u64, size: u64, prefetchable: bool. Ownership: owned by the parent PciDevice; written once by pcie-resource, read-only after. Mutation: only during Phase 5 (§17) resource assignment or a hotplug rebalance (§19). Concurrency: immutable after ResourceAssigned state; no lock needed for readers. Persistence: recorded verbatim in AllocationEvent for replay (I7). Serialization: bytemuck::Pod, fixed layout. Compatibility: BarKind enum growth is additive-only (P14).

BarKind — enum variants: Mmio32, Mmio64, Io. Ownership: value type. Mutation: none. Concurrency: Copy. Persistence: 1-byte discriminant in replay format. Serialization: bytemuck::Pod. Compatibility: new variants append at the end only.

Capability — enum variants: Msi(MsiCapability), Msix(MsixCapability), Pcie(PcieCapability), Vendor(VendorCapability). Ownership: owned by the parent PciDevice. Mutation: written once during Phase 4 (§16) capability parsing, immutable thereafter. Concurrency: read-only after CapabilityParsing completes. Persistence: recorded in capability-parse replay traces. Serialization: tagged-union serde encoding for CLI export; raw bytes retained for replay fidelity. Compatibility: additive-only variant growth (P14); an unrecognized future variant on an older reader decodes to Vendor(VendorCapability) with the raw bytes preserved, never a parse failure.

MsiCapability — fields: message_control: u16, message_address: u64, message_data: u16. MsixCapability — fields: table_size: u16, table_bar: u8, table_offset: u32, pba_bar: u8, pba_offset: u32. PcieCapability — fields: version: u8, device_type: PcieDeviceType, link_speed: u8, link_width: u8. VendorCapability — fields: vendor_id: u16, raw: Bytes. All four: ownership/mutation/concurrency as Capability above; serialization bytemuck::Pod for the fixed-width fields, Bytes for the raw vendor payload only.

DeviceState — enum variants: Undiscovered, Probing, Identified, CapabilityParsing, ResourceAssigned, Active, Failed, Removed. Ownership: field of PciDevice, written only by pcie-topology/pcie-enumerator/ pcie-hotplug-core under I6 ordering. Mutation: forward-only transitions except Active/Failed → Removed. Concurrency: single-writer. Persistence: every transition is a ReplayEvent. Serialization: 1-byte discriminant. Compatibility: additive-only (P14).

TopologyGraph — fields: nodes: SlotMap<DeviceId, PciDevice>, edges: Vec<BridgeEdge>, generation: u64. Ownership: the single canonical instance, owned by pcie-topology. Mutation: only through pcie-hotplug-core's mutation path; every mutation increments generation. Concurrency: readers take an immutable TopologySnapshot reference (I10); the live graph is never exposed outside pcie-topology. Persistence: exported as TopologySnapshot for replay and CLI inspection. Serialization: serde for CLI/JSON export; internal representation is not wire-serialized directly. Compatibility: SlotMap keys (DeviceId) are stable across a snapshot's lifetime per I4.

BridgeEdge — fields: parent: DeviceId, child: DeviceId, secondary_bus: u8, subordinate_bus: u8. Ownership/mutation/concurrency/persistence/serialization/compatibility: as TopologyGraph above — edges are part of the same generation-versioned structure.

TopologySnapshot — fields: generation: u64, nodes: Vec<PciDevice>, edges: Vec<BridgeEdge>, schema_version: u16. Ownership: immutable, reference-counted; produced by pcie-topology, consumed by every other crate. Mutation: none — a new snapshot is produced, never edited. Concurrency: safe to share across threads without locking (I10). Persistence: the unit of export for pcie-cli and the unit of comparison for I7. Serialization: serde (JSON, for humans) and a zerocopy binary form (for replay). Compatibility: schema_version gates decode; additive-only field growth (P14).

ReplayEvent — fields: timestamp: u64, event_type: ReplayEventType, payload: Bytes, schema_version: u16. Ownership: owned by pcie-replay's append-only log. Mutation: none after append — the log is write-once, read-many. Concurrency: single-writer append, multi-reader decode. Persistence: the primary artifact of the entire replay subsystem (I7, P6). Serialization: Cap'n Proto (ADR-04) for the on-disk wire format. Compatibility: schema_version per event; ReplayEventType grows additively only.

ReplayEventType — enum variants: ConfigAccess, Allocation, TopologyMutation, CapabilityParse, FirmwareCapture. Ownership/mutation/concurrency/persistence/serialization/compatibility: as ReplayEvent — a value type, additive-only variant growth.

ResourceAllocator — trait, methods: fn reserve_mmio(size: u64, align: u64) -> Result<ResourceWindow, AllocError>; fn reserve_io(size: u16, align: u16) -> Result<ResourceWindow, AllocError>; fn release(window: ResourceWindow); Ownership: implemented by pcie-resource's interval allocator; callers never construct a ResourceWindow directly. Mutation: every call mutates the allocator's interval tree under I6. Concurrency: single allocator instance per segment, serialized behind the topology lock. Persistence: every call emits an AllocationEvent-typed ReplayEvent. Compatibility: trait signature is part of the stable kernel-facing API (§1); additions are new methods with default implementations, never signature changes to existing methods.

ResourceWindow — fields: base: u64, size: u64, kind: BarKind. Ownership: returned by ResourceAllocator, owned by the requesting BarDescriptor. Mutation: none after construction. Concurrency: Copy. Persistence: embedded in AllocationEvent. Serialization: bytemuck::Pod. Compatibility: additive-only.

ConfigAccessor — trait, methods: fn read8(addr: DeviceAddress, offset: u16) -> Result<u8, EcamError>; fn read16(addr: DeviceAddress, offset: u16) -> Result<u16, EcamError>; fn read32(addr: DeviceAddress, offset: u16) -> Result<u32, EcamError>; fn write32(addr: DeviceAddress, offset: u16, value: u32) -> Result<(), EcamError>; Ownership: implemented by pcie-ecam; the sole path for configuration-space access (§3). Mutation: write32 mutates hardware state directly — never buffered, never batched, per I1. Concurrency: internally serialized per I6's segment-lock position; safe to call from any thread holding the appropriate lock. Persistence: every call emits a ConfigAccess-typed ReplayEvent. Compatibility: this trait is the stable kernel-facing enumeration API boundary (§1); it is frozen after Phase 2 (§14) except for additive default-method extensions.

12. Phase 0 — Repository Bootstrap & Platform Foundations

12.1 Objectives

Establish the repository skeleton, CI pipeline, and the architecture-abstraction boundary that every later phase builds on. Introduce the constraints that hold for the rest of the project: no_std kernel-space linkage, a pinned deterministic toolchain (ADR-26), and a mandatory tracing posture (P2) from the very first commit. This phase produces no PCIe-specific logic — it produces the correctness kernel (unsafe boundary, error taxonomy, barrier primitives) everything else sits on.

12.2 Detailed Implementation Steps

  • Create Cargo workspace manifests for all sixteen crates listed in §1; pin the toolchain via rust-toolchain.toml per ADR-26.
  • Implement pcie-platform-abstraction: MMIO map/unmap (crates/pcie-platform-abstraction/src/mmio.rs), memory-barrier wrappers (.../src/barrier.rs) isolating x86_64 mfence/lfence from ARM64 dmb. This is the only crate permitted unsafe blocks (ADR-19, P13).
  • Implement pcie-errors: a shared, exhaustive error taxonomy (EcamError, AcpiError, AllocError) reused by every downstream crate — no crate defines its own ad hoc error enum. Anchored to seL4's invariant-oriented design discipline (Klein et al., 2009).
  • Implement pcie-tracing skeleton: span macros keyed by DeviceAddress, UUIDv7 trace-ID generation (per ADR-09/ADR-10's span model), Prometheus metric registration (ADR-11).
  • Configure cargo-deny (ADR-03) and cargo-audit; add a lint policy forbidding unwrap() outside test code.
  • Add no_std feature gating across every crate that must link into the kernel image.
  • Configure the CI matrix (.github/workflows/ci.yml): stable, nightly, and a Miri/ASan sanitizer lane (ADR-23).
  • Add pcie-test-harness: QEMU q35 orchestration (crates/pcie-test-harness/src/qemu.rs, ADR-25) and the integration-test launcher used by every later phase's conformance fixtures.
  • Add reproducible-build flags (--remap-path-prefix, frozen lockfile) satisfying ADR-26 so that I7's byte-identical replay bar is reachable in principle from Phase 0 onward.

12.3 Deliverable

Workspace compiles clean on stable + nightly; CI green on all three lanes; a QEMU q35 instance boots to the point where pcie-platform-abstraction successfully maps one MMIO test page; tracing emits at least one structured span per boot, serialized and inspectable via pcie-cli.

12.4 Acceptance Criteria

Zero clippy warnings across the workspace; build hashes identical across two independent CI runs (ADR-26); the Miri/ASan sanitizer lane passes with 0 findings; bootstrap_trace.bin decodes with pcie-replay and round-trips through pcie-cli --dump byte-identical to the captured original.

12.5 Conformance Fixtures

  • fixtures/bootstrap/bootstrap_trace.bin — golden boot trace; expected: decodes cleanly, 1 FirmwareCapture event minimum.
  • fixtures/bootstrap/invalid_mmio_alignment.bin — malformed replay of an unaligned MMIO map request; expected: pcie-platform-abstraction rejects with EcamError::Unaligned, not a panic.
  • fixtures/bootstrap/replay_seed_0001.bin — deterministic seed for the Phase 9 (§21) soak harness.

12.6 Pitfalls

  • Unsafe MMIO aliasing — manifestation: stale config reads after a remap; root cause: two virtual mappings of the same physical ECAM page without a barrier between them; debugging: compare physical-address ranges across all active mappings in a replay dump; signal: ecam_unaligned_access_total unexpectedly non-zero; recovery: enforce single-mapping-per-window in pcie-platform-abstraction.
  • Missing memory barriers — manifestation: non-deterministic config reads on ARM64 only; root cause: relaxed-ordering load reordered ahead of a prior store by the compiler or CPU; signal: I7 replay divergence on ARM64 CI only; recovery: audit every ConfigAccessor call site for a paired barrier per ADR-27's monotonic-time discipline (barriers, not the clock, fix this — the clock choice just makes the divergence visible in a timestamp diff).
  • Toolchain drift — manifestation: replay traces captured on one CI runner fail I7 on another; root cause: a floating nightly toolchain (the ADR-26 rejected alternative) changed struct padding; recovery: pin via rust-toolchain.toml, re-run the full fixture corpus.

12.7 Performance Concerns

Minimize bootstrap-phase heap allocations — the 32 MB ceiling (§4) is shared with the ACPI parser that runs immediately after. Avoid tracing-induced allocation storms: pre-size the span buffer before the first config access. Ensure cacheline alignment on PciDevice-adjacent structs to avoid false sharing once SMP transition begins.

12.8 Edge Cases

Emulator target missing an ECAM window entirely (QEMU misconfiguration); invalid page-table alignment on a debug kernel build; a malformed firmware memory map that overlaps the kernel's own image. All three must fail closed with a fatal initialization trace, never a silent continue.

12.9 Failure Analysis

If bootstrap fails, the system emits a fatal initialization trace, preserves whatever partial replay artifact exists (P3 — crash-only, no hidden state), and disables enumeration entirely rather than proceeding on an unverified platform-abstraction layer. Blast radius is total (nothing after Phase 0 can run) but detection is immediate and postmortem-ready: the replay artifact alone is sufficient for an engineer to reproduce the failure without the original hardware.

12.10 Operational Notes

Metrics: bootstrap_duration_ms, sanitizer_findings_total. Tracing spans: bootstrap.init, bootstrap.mmio_map. Structured-log fields: build_hash, toolchain_version. Operators must validate replay-artifact persistence, build provenance (cosign signature, ADR-21), and the trace schema version before trusting any downstream phase's output on a new platform.

13. Phase 1 — ACPI & MCFG Discovery

13.1 Objectives

Implement robust, fail-closed firmware discovery: locate and validate the MCFG table so every later phase can trust the ECAM window addresses it derives from it. Introduce P7 (parse nothing lazily without validation) as an enforced, tested property, not an aspiration.

13.2 Detailed Implementation Steps

  • crates/pcie-acpi/src/rsdp.rs: locate and checksum-validate the RSDP, then walk to the XSDT.
  • crates/pcie-acpi/src/mcfg.rs: locate MCFG within the XSDT, parse per-segment ECAM base addresses and bus-range entries per the ACPI Specification's MCFG table definition (§5).
  • Validate every table checksum before trusting any field inside it (P7); reject on mismatch.
  • Validate segment ranges, ECAM boundaries, and bus windows for internal consistency; reject overlapping windows (a firmware bug pattern seen in mcfg_overlap.bin, §5's Linux reference).
  • Implement bounded parser recursion — no ACPI table walk may recurse past a fixed depth, independent of and tighter than the §4 16-level PCIe topology bound.
  • Add endian-safe field extraction (ACPI tables are little-endian; the parser must not assume host endianness even though every current target is little-endian — this is a P7 discipline check).
  • Add a replay capture hook: every parsed firmware blob is archived into the replay log (FirmwareCapture ReplayEventType) before any decision is made from it.
  • Add fuzz/fuzz_targets/acpi_parser.rs (ADR-13) targeting the RSDP/XSDT/MCFG parse path.
  • Add telemetry counters for malformed-table rejections, keyed by rejection reason.

13.3 Deliverable

Valid MCFG extraction on both QEMU q35 and a real x86_64 host; ECAM windows mapped into pcie-platform-abstraction and handed to Phase 2 (§14) as a validated EcamWindow list.

13.4 Acceptance Criteria

All fixtures in fixtures/acpi/ classified correctly (accept/reject) with 0 false accepts; the acpi_parser fuzz target survives 24h continuous fuzzing with 0 crashes and 0 unchecked-panic findings; parser recursion never exceeds the fixed depth bound on any fixture.

13.5 Conformance Fixtures

  • fixtures/acpi/mcfg_valid_01.bin — well-formed single-segment MCFG; expected: accept, one EcamWindow produced.
  • fixtures/acpi/mcfg_overlap.bin — two segments with overlapping ECAM ranges; expected: reject with AcpiError::OverlappingWindows.
  • fixtures/acpi/mcfg_bad_checksum.bin — corrupted table checksum; expected: reject before any field is read, per P7.

13.6 Pitfalls

  • Firmware truncation — manifestation: MCFG table claims more segment entries than its declared length permits; root cause: a buggy firmware build; debugging: compare declared length against parsed entry count; recovery: reject, do not read past the declared boundary.
  • Overlapping segments — manifestation: two ECAM windows claim the same physical range; debugging: interval-overlap check against every prior accepted window; recovery: reject the later window, quarantine that segment only.
  • Integer overflow in bus-window math — manifestation: a segment's declared bus range wraps past u8::MAX; root cause: unchecked arithmetic on an untrusted firmware field; recovery: use checked arithmetic exclusively in this crate (a direct consequence of P7).

13.7 Performance Concerns

Avoid heap-heavy parsing — MCFG tables are small (typically <1 KB) but the RSDT/XSDT walk can touch dozens of tables; cache firmware blobs already validated this boot rather than re-walking ACPI on every segment lookup.

13.8 Edge Cases

Multiple MCFG tables presented by firmware (some BIOSes duplicate tables across revisions); a zero-length segment declaration; malformed OEM ID fields that are non-ASCII. All three are rejected individually without aborting the whole ACPI walk — one malformed table quarantines itself.

13.9 Failure Analysis

Malformed firmware state must fail closed: preserve full diagnostics (the raw table bytes, in the replay log), and prevent any enumeration from proceeding on unvalidated ECAM addresses — an enumerator that trusts an unvalidated ECAM base address risks reading arbitrary physical memory as if it were configuration space.

13.10 Operational Notes

All firmware blobs are archived in replay traces regardless of validation outcome (auditable even on failure). Metrics: acpi_table_reject_total{reason}, mcfg_segments_discovered. Tracing spans: acpi.rsdp_locate, acpi.mcfg_parse. Migration note: a future ACPI revision adding new MCFG entry subtypes is additive-only per P14 and requires no Phase 1 rewrite.

14. Phase 2 — ECAM Access Layer

14.1 Objectives

Implement the single, safe path for all configuration-space access. Every later phase's config reads and writes funnel through this crate — no other crate is permitted direct ECAM MMIO access.

14.2 Detailed Implementation Steps

  • crates/pcie-ecam/src/access.rs: implement ConfigAccessor (§11) — read8/read16/read32/ write32 — with the ECAM address-derivation formula from §8, enforcing I1 (natural alignment) on every call.
  • crates/pcie-ecam/src/retry.rs: implement the bounded retry loop enforcing I11 (3-attempt limit) and the per-device quarantine transition on exhaustion.
  • Detect master-abort responses (a bus-level "nothing answered") distinctly from a timeout; both are terminal for the access but are recorded with different telemetry reasons. Add timeout handling using the ADR-27 monotonic time source exclusively — no wall-clock reads on this hot path.
  • Validate offset ranges against the header-type-specific config space size (256 B standard, 4 KB extended) before issuing any MMIO instruction.
  • Add tracing spans (ecam.read, ecam.write) and per-access latency histograms feeding the §4 p50/p95/p99 targets directly — this is the first phase where those numbers become measurable, not just budgeted.
  • Add access replay logging: every ConfigAccessor call emits a ConfigAccess ReplayEvent (Rosenblum & Ousterhout's append-only log discipline, 1991, applied here per §5).
  • Implement architecture-specific barrier insertion around every write, delegated to pcie-platform-abstraction.
  • Add a synthetic fault injector (used by Phase 9's chaos fixtures, §21) gated behind a test-only feature flag so it cannot ship in a production build (ADR-19's audit boundary applies here too).

14.3 Deliverable

A ConfigAccessor implementation that passes 100% of fixtures/ecam/ with deterministic replay and meets the §4 p50 < 1 µs / p95 < 10 µs / p99 < 25 µs latency targets on QEMU q35 CI hardware.

14.4 Acceptance Criteria

100% replay determinism (I7) across 3 consecutive runs of the full fixtures/ecam/ corpus; out-of-range offsets rejected with EcamError::OutOfRange in 100% of cases; measured p99 latency ≤ 25 µs on the CI reference host.

14.5 Conformance Fixtures

  • fixtures/ecam/ecam_timeout.bin — simulated bus timeout; expected: 3 retries then quarantine.
  • fixtures/ecam/ecam_partial_read.bin — a torn 32-bit read split across two bus beats; expected: reject, do not return a half-updated value.
  • fixtures/ecam/ecam_alignment_violation.bin — a 2-byte-aligned 32-bit read request; expected: reject before any MMIO instruction issues, per I1.

14.6 Pitfalls

  • Stale mappings — manifestation: reads return data from a device that was hot-removed; root cause: pcie-platform-abstraction cache of a since-invalidated MMIO mapping; debugging: cross-check mapping generation against the topology generation (I10); recovery: invalidate the ECAM mapping cache on every hotplug event.
  • Write tearing — manifestation: a 32-bit BAR write appears as two 16-bit writes on some chipsets; root cause: compiler/hardware splitting a store; recovery: use bytemuck's volatile write primitives exclusively, never a plain slice assignment (ADR-05).
  • Speculative reads — manifestation: a config read appears to happen before its preceding write completes; root cause: missing store-load barrier; debugging: I7 replay divergence localized to write-then-read sequences; recovery: insert the barrier pcie-platform-abstraction provides around every write-then-read pair.

14.7 Performance Concerns

Reduce TLB churn by mapping each segment's ECAM window once at Phase 1 and reusing it, rather than remapping per access. Avoid unnecessary barriers on read-only paths — only writes require the full store barrier; over-barriering a pure-read enumeration pass measurably regresses the §4 enumeration- completion budget.

14.8 Edge Cases

Inaccessible functions (device physically absent but bus/device slot addressable — reads return 0xFFFF vendor ID, which is not an error, it is the defined "absent" signal); transient config failures that succeed on retry; partial MMIO mappings left over from a failed hotplug rebalance.

14.9 Failure Analysis

On repeated failure (I11 exhaustion) the device is quarantined and traversal continues past it — blast radius is one device, not the segment. Telemetry (config_retry_exhausted_total) makes the quarantine operator-visible immediately; the replay log makes it forensically reproducible.

14.10 Operational Notes

Export ecam_read_latency_us{p50,p95,p99}, ecam_retry_count_total, ecam_timeout_count_total. Tracing spans: ecam.read, ecam.write, ecam.retry. Rollback note: the retry-limit constant is a versioned config value, not a compile-time constant, so an operator can tighten it post-deploy without a rebuild.

15. Phase 3 — Basic Enumeration Engine

15.1 Objectives

Implement the recursive PCIe discovery walk itself: bus 0 outward, through every bridge, to every endpoint function, building the first version of the topology graph.

15.2 Detailed Implementation Steps

  • crates/pcie-enumerator/src/walk.rs: scan bus 0 first, then recurse per the §8 enumeration sequence — read vendor ID, detect absent devices (vendor ID 0xFFFF), identify header type.
  • Detect multi-function devices by checking the multi-function bit in the header before assuming function 0 is the only function present — a common source of missed devices in naive walkers (Linux drivers/pci/ reference, §5).
  • crates/pcie-enumerator/src/bridge.rs: on Header Type 1, assign the secondary bus number, enforce I9 (bus-number uniqueness within the segment) before recursing into it.
  • Enforce the §4 16-level recursion depth bound explicitly — a cyclic or malformed bridge chain must not recurse past it (anchored to ADR-25's QEMU-realism choice: the depth bound is validated against real multi-switch QEMU topologies, not a synthetic worst case).
  • Build the topology graph incrementally in pcie-topology, maintaining P1's deterministic traversal order (depth-first, ascending bus/device/function at each level).
  • Add traversal spans (enum.scan_bus, enum.scan_function) and a bridge-validation step that rejects a secondary bus number equal to or less than its own primary bus number.
  • Add a graph-consistency check enforcing I2 (every non-root device has exactly one parent) before the pass is considered complete.
  • Add snapshot export at the end of the pass — the first TopologySnapshot (generation 0) any consumer can observe.

15.3 Deliverable

Complete topology discovery on the QEMU q35 reference fixture, matching the Linux drivers/pci/ differential oracle (ADR-15) device-for-device.

15.4 Acceptance Criteria

QEMU q35's reference topology (13 known devices across 3 bridge levels in the CI fixture) discovered with 0 missing and 0 phantom devices; graph hash stable and identical across 10 consecutive scan runs.

15.5 Conformance Fixtures

  • fixtures/enum/bridge_loop.bin — a bridge whose secondary bus number equals its primary; expected: reject that bridge, continue enumerating siblings.
  • fixtures/enum/multifunction_sparse.bin — functions 0, 2, 5 present, 1/3/4/6/7 absent; expected: exactly 3 functions discovered, no scan of the absent slots retried.
  • fixtures/enum/deep_hierarchy.bin — exactly 16 nested bridge levels; expected: full discovery at the §4 depth ceiling, and a 17th synthetic level rejected.

15.6 Pitfalls

  • Bridge recursion loops — manifestation: enumeration hangs; root cause: a bridge reports a secondary bus number that routes back to an ancestor; debugging: the ancestor-bus-number set carried down the recursion catches this in O(depth); recovery: reject the bridge, mark it Failed, continue its siblings.
  • Invalid subordinate buses — manifestation: a bridge's subordinate bus number is less than its secondary bus number; recovery: reject per I9's uniqueness requirement, which this also violates.
  • Duplicate functions — manifestation: the same DeviceAddress observed twice in one pass; root cause: a firmware/emulator bug re-exposing a slot; recovery: first-observation wins, subsequent observations logged and dropped.

15.7 Performance Concerns

Avoid repeated config reads of the same header fields — cache the header-type byte for the duration of one device's scan rather than re-reading it per BAR/capability step. Optimize traversal locality: scanning function 0 of every device on a bus before recursing into any bridge improves ECAM MMIO page locality versus a naive depth-first-immediately order.

15.8 Edge Cases

Phantom devices (a slot answers on function 0 but not consistently across repeated reads — a firmware/hardware timing bug, not an absent-device signal); a device that disappears between the vendor-ID read and the BAR read (hotplug race, handled by re-validating vendor ID before trusting any subsequent read in the same pass); malformed bridge windows that claim a zero-size range.

15.9 Failure Analysis

Traversal failures are isolated per subtree: a malformed bridge quarantines everything downstream of it (bounded blast radius) but never aborts the sibling subtree or the overall pass. This is the first phase where P11's isolation principle is directly testable end-to-end.

15.10 Operational Notes

Topology snapshots exposed as both JSON (pcie-cli --dump-json) and the binary zerocopy form. Metrics: enumeration_duration_ms, devices_discovered_total, bridges_quarantined_total. Tracing spans: enum.pass, enum.scan_bus{bus}. Compatibility: the depth-first scan order is part of the P1 determinism contract — changing it is a breaking change requiring a schema-version bump on every downstream replay consumer.

16. Phase 4 — Capability Parsing

16.1 Objectives

Implement robust standard and extended capability discovery: MSI, MSI-X, power management, PCIe capability, and vendor-specific chains, with mandatory cycle detection from the first line of code.

16.2 Detailed Implementation Steps

  • crates/pcie-capabilities/src/lib.rs: parse the standard capability list starting at offset 0x34 per the §8 rules — 4-byte aligned, null-terminated.
  • Parse the extended capability chain starting at offset 0x100, also 4-byte aligned, using the 12-bit next-pointer field.
  • Add loop detection (I5) via a bounded visited-offset bitmap sized to the maximum config-space extent (256 B standard / 4 KB extended) — no dynamic allocation per device on the hot path.
  • crates/pcie-capabilities/src/msi.rs: decode MsiCapability per §11's fixed-layout fields.
  • crates/pcie-capabilities/src/msix.rs: decode MsixCapability, validating table_bar/pba_bar reference an actual populated BAR index before trusting the offset fields.
  • Decode the PCIe capability (link speed/width, device type) and the power-management capability.
  • Add a vendor-extension parser producing Capability::Vendor with the raw payload preserved verbatim (P14 — an unrecognized vendor capability is data, not an error).
  • Add a capability-parser registry keyed by capability ID — a match over a closed, generated enum, not a dynamic dispatch table, per P13's cost discipline.
  • Add per-segment malformed_capability_count metrics anchored to P11's isolation guarantee.

16.3 Deliverable

A normalized capability registry attached to every discovered device, with MSI/MSI-X presence and parameters available to interrupt-controller integration (a later, out-of-scope, consuming layer).

16.4 Acceptance Criteria

100% of fixtures/cap/cap_cycle.bin variants (5 distinct cycle shapes) detected and aborted within 16 chain steps; malformed capability lengths rejected in 100% of cases; vendor capabilities isolated such that an unrecognized vendor ID never blocks MSI/MSI-X parsing on the same device.

16.5 Conformance Fixtures

  • fixtures/cap/cap_cycle.bin — capability A → B → A; expected: cycle detected, device marked degraded, enumeration continues.
  • fixtures/cap/msix_corrupt.bin — MSI-X table_bar index pointing at a non-existent BAR; expected: reject the MSI-X capability specifically, keep other capabilities on the same device.
  • fixtures/cap/vendor_cap_unknown.bin — an unregistered vendor capability ID; expected: parsed as Capability::Vendor with raw bytes intact, no rejection.

16.6 Pitfalls

  • Endless loops on malformed lists — manifestation: capability parsing never terminates without the I5 bitmap; debugging: this is exactly why I5 is a table row, not a comment — the bitmap check is the enforcement point, tested directly by cap_cycle.bin.
  • Invalid offsets — manifestation: a next-pointer field points inside the header region (offset < 0x40); recovery: reject any next-pointer below the minimum valid capability offset.
  • Capability overlap — manifestation: two capabilities claim overlapping byte ranges; root cause: a malformed or adversarial device; recovery: the second capability to claim an already- claimed range is rejected, not merged.

16.7 Performance Concerns

Avoid dynamic-dispatch storms: the capability-ID registry is a closed match, not a Vec<Box<dyn Parser>>, keeping per-capability parse cost predictable. Preallocate the capabilities: Vec<Capability> with a small fixed initial capacity (most devices have 2–5 capabilities) to avoid reallocation churn during the hot enumeration path.

16.8 Edge Cases

Duplicated capability IDs on the same device (some devices legitimately expose two vendor-specific capabilities); partially truncated config space where the chain's declared length exceeds the actual mapped extent — reject at the boundary, do not read past it (P7).

16.9 Failure Analysis

Capability parsing failures never invalidate the device's topology membership — only its capability set is degraded. A device with a corrupt MSI-X table is still Active in the topology graph with an empty or partial capability list, discoverable and inspectable by an operator.

16.10 Operational Notes

Capability parse traces are retained in replay logs at full fidelity (raw bytes, not just the decoded struct) so a future decoder bug can be diagnosed retroactively against old captures. Metrics: capability_cycle_detected_total, malformed_capability_count. Tracing spans: cap.parse_standard, cap.parse_extended.

17. Phase 5 — Resource Allocation Engine

17.1 Objectives

Implement BAR sizing and MMIO/IO window allocation: turn a discovered-but-unassigned device into a fully resourced one, with zero overlap and correct alignment, replayable end to end.

17.2 Detailed Implementation Steps

  • crates/pcie-resource/src/allocator.rs: implement BAR probing via the §8 sizing sequence — save, write all-1s, read size mask, restore, compute alignment, reserve.
  • Detect 32-bit vs. 64-bit BARs from the memory-type bits in the low BAR word; a 64-bit BAR consumes two consecutive BAR slots and must be sized/restored as one atomic unit (Exokernel's raw-resource- exposure philosophy, Engler et al. 1995, applies directly here — expose the real interval, not an abstracted handle).
  • Handle prefetchable windows distinctly: prefetchable MMIO can be placed more aggressively for cache-friendliness but must still respect I8 alignment.
  • crates/pcie-resource/src/interval.rs: implement the interval-tree allocator enforcing I3 (no overlap) on every insert, with O(log n) overlap query.
  • Validate bridge windows (secondary bus's MMIO/IO aperture) fit within the parent bridge's forwarded range per the PCI-to-PCI Bridge Architecture Specification (§5).
  • Add rollback support: a failed allocation for device N of M in a batch unwinds all N-1 prior reservations in that batch atomically — never leaves a partial allocation visible.
  • Add fragmentation metrics tracking the §4 <5% MMIO fragmentation budget directly.
  • Add AllocationEvent replay events (P12 — allocation transparency) for every decision, accept or reject.

17.3 Deliverable

A fully resourced topology: every Active device has BAR assignments with 0 overlaps, verified against the QEMU q35 reference fixture's known BAR layout.

17.4 Acceptance Criteria

0 overlaps across 1,000 randomized allocation-order test runs (property test, ADR-14); alignment correctness verified against I8 for every BAR in fixtures/resource/; rollback verified to restore the pre-batch allocator state byte-for-byte on injected mid-batch failure.

17.5 Conformance Fixtures

  • fixtures/resource/bar_overlap.bin — two devices' pre-sized BARs would overlap if placed naively; expected: allocator places them non-overlapping, or rejects the second if the window is exhausted.
  • fixtures/resource/bar_64_split.bin — a 64-bit BAR pair; expected: sized/restored as one unit, never as two independent 32-bit BARs.
  • fixtures/resource/bridge_window_exhausted.bin — a bridge's forwarded window too small for its children's combined BAR demand; expected: reject the excess child, quarantine it, not the bridge.

17.6 Pitfalls

  • 64-bit BAR ordering — manifestation: the high 32 bits are sized/restored out of sequence with the low 32 bits, corrupting the base address; recovery: treat the pair as one atomic operation in pcie-resource, never two independent register writes.
  • Allocator fragmentation — manifestation: fragmentation metric creeps toward the §4 5% ceiling under mixed 32-/64-bit workloads; debugging: fragmentation histogram by BAR-size bucket; recovery: size-class segregation in the interval allocator (larger BARs placed first).
  • Stale BAR restores — manifestation: the original BAR value restored after sizing doesn't match what was actually there before, corrupting a device already configured by firmware; root cause: a race between the sizing probe and a concurrent hotplug rescan; recovery: hold the device lock (I6) for the entire save→write→read→restore sequence as one atomic unit.

17.7 Performance Concerns

Interval-tree locality: keep the tree balanced (red-black or B-tree backing) so overlap queries stay O(log n) even at the §4 4096-device-per-segment ceiling. Allocation scan complexity: a naive first-fit degrades to O(n²) under adversarial fragmentation — the size-class segregation above exists specifically to bound this.

17.8 Edge Cases

Exhausted MMIO space (more devices than the platform's MMIO hole can fit); malformed BAR sizes (a size mask that decodes to a non-power-of-two size, which the spec forbids but a broken device may still report); zero-sized BARs (a valid signal meaning "this BAR slot is unused," not an error).

17.9 Failure Analysis

Allocation failures isolate the affected subtree: a device that cannot be resourced is marked Failed (not removed from the graph — it remains inspectable) while its siblings proceed normally. Operator visibility: pcie-cli --dump-allocations shows every accepted and rejected decision with its reason, sourced directly from the AllocationEvent replay log.

17.10 Operational Notes

Export allocation maps for operators via pcie-cli --dump-allocations. Metrics: mmio_fragmentation_ratio, allocation_rollback_total, bar_overlap_rejected_total. Tracing spans: resource.size_bar, resource.reserve_window. Rollback/migration: allocator size-class boundaries are a versioned tunable, changeable without a schema bump since they affect placement, not the persisted AllocationEvent schema.

18. Phase 6 — Topology Graph & Snapshotting

18.1 Objectives

Build the stable runtime topology model that every consumer (drivers, IOMMU, hypervisor) reads from: generation-versioned, snapshot-consistent, with stable device identity across rescans.

18.2 Detailed Implementation Steps

  • crates/pcie-topology/src/graph.rs: implement TopologyGraph (§11) storage using a SlotMap keyed by DeviceId, giving O(1) lookup and stable keys across removal/reinsertion (I4).
  • Add stable-ID assignment: a DeviceId is derived from DeviceAddress plus a topology-scoped epoch, so a rescan that finds the same device at the same address reuses the same DeviceId (Baumann et al.'s multikernel topology-as-published-state model, 2009, directly informs treating the graph as an explicit versioned artifact rather than ambient shared state — see §5).
  • crates/pcie-topology/src/snapshot.rs: implement TopologySnapshot production — copy-on-publish, not copy-on-read, so readers holding an old snapshot never block a new mutation.
  • Add the graph-diff engine: given two TopologySnapshot generations, compute the minimal set of added/removed/changed nodes and edges — the primitive Phase 8's replay-diff tooling builds on.
  • Add traversal indexes (by bus, by segment) alongside the primary SlotMap for O(1) segment-scoped queries without a full graph walk.
  • Add parent validation enforcing I2 on every graph mutation, not just at pass-end.
  • Add the lock hierarchy implementation itself here — this is the crate that owns and documents I6's enforcement mechanism (a typed lock-token API that makes acquiring locks out of order a compile error, not just a runtime assertion, wherever the type system can express it).
  • Add topology generation counters exposed as metrics, incremented exactly once per published mutation (I10).

18.3 Deliverable

A stable, generation-versioned topology API: pcie-cli --dump-topology produces a snapshot whose hash is reproducible across repeated dumps of the same generation.

18.4 Acceptance Criteria

Snapshot consistency verified under 500 concurrent-reader stress runs with 0 partial reads observed (I10); graph hashes deterministic and identical across 10 repeated dumps of the same generation; diff engine produces the exact expected delta on fixtures/topology/topology_diff.bin.

18.5 Conformance Fixtures

  • fixtures/topology/snapshot_consistency.bin — a scripted concurrent read during a scripted mutation; expected: the reader observes exactly one of the two generations, never a mix.
  • fixtures/topology/topology_diff.bin — two generations differing by one inserted, one removed device; expected: the diff engine reports exactly those two changes, nothing else.

18.6 Pitfalls

  • Stale references — manifestation: a held DeviceId from generation N is queried against generation N+1 after the device was removed; recovery: lookups against a stale generation return None, never a use-after-free — the SlotMap generation check makes this structurally impossible rather than merely tested-against.
  • Generation mismatch — manifestation: a consumer caches a TopologySnapshot reference across a mutation and acts on stale data as if current; recovery: every consumer-facing API that returns live data also returns the generation it was read at, forcing explicit staleness checks.
  • Graph mutation races — manifestation: two mutation calls interleave without going through pcie-hotplug-core's single mutation path; recovery: TopologyGraph's mutation methods are pub(crate)-visible only to pcie-hotplug-core (P5's single-writer discipline enforced at the visibility level, not just by convention).

18.7 Performance Concerns

Minimize snapshot copies: copy-on-publish means the cost is paid once per mutation, not once per read — critical since reads vastly outnumber mutations after initial boot. Optimize adjacency traversal: the bus/segment traversal indexes exist specifically so a segment-scoped query doesn't walk the full 4096-device §4 ceiling.

18.8 Edge Cases

Concurrent hotplug arriving during an in-progress snapshot export to pcie-cli — the export completes against the generation it started with, and the hotplug's new generation is picked up on the next export call, never mid-export.

18.9 Failure Analysis

Detected graph corruption (a parent-validation failure that somehow escaped mutation-time checking) triggers a read-only "safe mode": the topology stops accepting further mutations, continues serving the last known-good snapshot, and pages an operator (per the alerting philosophy in §24) rather than silently continuing on corrupted state.

18.10 Operational Notes

Topology generation numbers are exposed directly in metrics (topology_generation) so an operator can correlate a driver-visible topology change with the exact mutation event in the replay log. Tracing spans: topology.publish_snapshot, topology.diff. Metrics: topology_size, snapshot_read_total.

19. Phase 7 — Hotplug & Mutation Engine

19.1 Objectives

Implement dynamic topology updates: the only path by which a running system's topology changes after initial boot, without corrupting concurrent readers.

19.2 Detailed Implementation Steps

  • crates/pcie-hotplug-core/src/events.rs: implement the bounded hotplug event queue (P4) fed by interrupt-driven insert/remove signals.
  • Add debounce logic: a rapid insert/remove/insert sequence (a flaky slot) collapses to a single net event within a configured debounce window, bounding the mutation rate presented to pcie-topology.
  • Implement device removal: mark Removed, detach from the graph, release its ResourceWindow reservations back to pcie-resource.
  • Implement insertion scan: re-run the Phase 3 (§15) enumeration walk scoped to just the newly populated slot, not the whole segment — bounding mutation latency against the §4 <5 ms stall budget.
  • crates/pcie-hotplug-core/src/rebalance.rs: add bridge-window rebalance logic for the case where an inserted device's BAR demand exceeds the bridge's currently-forwarded window (K42's lock- scaling lessons, Appavoo et al. 2006, directly motivate keeping the rebalance critical section as narrow as possible under I6 — see §5).
  • Add topology-generation swap as the atomic publish step, reusing Phase 6's (§18) snapshot machinery unchanged.
  • Add mutation rollback: a rebalance that cannot satisfy every affected device's minimum BAR size unwinds to the pre-mutation snapshot rather than publishing a partially-rebalanced graph.
  • Add concurrent-reader isolation tests exercising I10 directly under injected hotplug timing.
  • Add replay capture for every hotplug event, including debounced-away events (visible in the replay log even though they never reached the topology).

19.3 Deliverable

Live topology mutation: a hotplug_insert.bin-scripted insertion is visible in pcie-cli --dump-topology within the §4 5 ms mutation-stall budget, with 0 reader crashes.

19.4 Acceptance Criteria

0 reader crashes across 200 concurrent-reader-during-mutation stress runs; mutation latency p99 under 5 ms per §4; deterministic replay of hotplug_insert.bin/hotplug_remove.bin produces the identical resulting TopologySnapshot on every run (I7).

19.5 Conformance Fixtures

  • fixtures/hotplug/hotplug_insert.bin — a single device inserted into an empty slot; expected: new Active device, generation incremented by exactly 1.
  • fixtures/hotplug/hotplug_remove.bin — removal of a previously Active device; expected: node transitions to Removed, its ResourceWindow released and verified non-overlapping-available.
  • fixtures/hotplug/rapid_flap.bin — 50 insert/remove cycles in 200 ms; expected: debounced to the correct net state, no queue overflow, no dropped final-state event.

19.6 Pitfalls

  • Use-after-free (logical, not memory-unsafe in Rust, but state-level) — manifestation: a rebalance operation reads a BarDescriptor for a device that was removed mid-rebalance; recovery: the rebalance critical section holds the device lock (I6) for its full duration, making this ordering violation structurally excluded, not just guarded.
  • Stale handles — manifestation: pcie-cli holds a DeviceId across a remove-then-reinsert and expects it to still resolve; recovery: DeviceId incorporates a topology epoch (§18.2); a reinsertion after removal gets a new epoch-scoped ID by design, and this is documented, not a bug.
  • Race windows — manifestation: an insertion scan and a concurrent removal of a sibling interleave; recovery: both funnel through the single hotplug mutation path (P5), serialized by I6, so "interleaving" at the topology-mutation level is impossible by construction — only the event queue can interleave, and debounce/ordering there is explicitly tested.

19.7 Performance Concerns

Mutation lock contention: the topology lock (I6 position 2) is held for the shortest possible critical section — insertion scan happens before acquiring it (into a staging structure), and the lock is only taken to publish. Queue pressure: the bounded hotplug queue's high-watermark metric (shared discipline with I12) catches sustained flap storms before they threaten the §4 memory ceiling.

19.8 Edge Cases

Repeated insert/remove storms (covered by rapid_flap.bin); a bridge disappearing (hot-removed) while its children are mid-rebalance — children are quarantined, not left dangling, since the bridge's removal is itself a topology mutation subject to the same I6 ordering.

19.9 Failure Analysis

Mutation rollback preserves the previous topology snapshot exactly — a failed rebalance never leaves the system worse off than before the hotplug event arrived. Detection is immediate via the allocation_rollback_total metric (shared with Phase 5); blast radius is the newly-inserted subtree only.

19.10 Operational Notes

Hotplug latency metrics are mandatory, not optional (P2): hotplug_event_to_publish_ms, hotplug_queue_depth, hotplug_debounced_total. Tracing spans: hotplug.enqueue, hotplug.rebalance, hotplug.publish. Deployment note: the debounce window is a versioned tunable adjustable without a rebuild, since overly aggressive debounce on some hardware is a known field tuning knob, not a bug fix.

20. Phase 8 — Replay & Deterministic Diagnostics

20.1 Objectives

Implement the deterministic replay infrastructure that every prior phase has been emitting events into: turn the accumulated ReplayEvent stream into a reproducible, diffable, forensic artifact.

20.2 Detailed Implementation Steps

  • crates/pcie-replay/src/encoder.rs: implement the append-only Cap'n Proto encoder (ADR-04) for ReplayEvent, directly applying Rosenblum & Ousterhout's log-structured append-only design (1991, SOSP) to a hardware-enumeration domain rather than a filesystem.
  • Record every config access, firmware blob, and allocation decision — nothing is synthesized at replay time that wasn't captured at record time (I7's precondition).
  • Record timestamps from the ADR-27 monotonic source only; replay ordering depends on relative ordering, never wall-clock value.
  • crates/pcie-replay/src/decoder.rs: implement checksum-validated decode — a corrupt segment is detected before any event in it is trusted, isolating corruption to that segment (not the whole log).
  • Add the diff tooling (scripts/replay_diff.sh + tools/trace_viewer.py) built on Phase 6's (§18) graph-diff engine, extended to diff two independent replay runs, not just two generations within one run.
  • Add deterministic-scheduler hooks: replay re-drives the exact same event ordering that was recorded, bypassing any live concurrency — this is what makes I7 achievable rather than aspirational.
  • Add the replay CLI surface in crates/pcie-cli/src/dump.rs (pcie-cli --replay <file>).
  • Add trace compaction: superseded intermediate states (e.g., a BAR sizing probe's save/restore pair) are compacted in long-running traces to stay within the §4 128 MB replay-trace budget.

20.3 Deliverable

A reproducible replay system: pcie-cli --replay replay_full_boot.bin reconstructs the exact TopologySnapshot that the original boot produced, with a matching graph hash.

20.4 Acceptance Criteria

Byte-identical topology replay (I7) verified across 20 repeated replays of replay_full_boot.bin; graph hashes stable across all 20; trace compaction keeps replay_full_boot.bin under the §4 128 MB budget for a 4096-device synthetic worst-case fixture.

20.5 Conformance Fixtures

  • fixtures/replay/replay_full_boot.bin — a complete boot capture including ACPI, ECAM, enumeration, capability, and resource events; expected: full byte-identical topology reconstruction.
  • fixtures/replay/replay_hotplug.bin — a boot capture plus one hotplug insert/remove cycle; expected: identical reconstruction including the post-hotplug generation.

20.6 Pitfalls

  • Hidden nondeterminism — manifestation: two replays of the same trace produce different graph hashes; root cause: an iteration order somewhere (e.g., a HashMap instead of the SlotMap insertion order) leaking into the observable result; debugging: bisect the event stream to the first diverging event; recovery: audit every iteration site touched by replay for ordering guarantees, not just correctness.
  • Clock drift — manifestation: a replay run on different hardware disagrees on relative event timing enough to change debounce-window outcomes in Phase 7's logic; recovery: replay uses recorded relative timestamps, never re-measures wall time during replay.
  • Unstable iteration ordering — manifestation: capability or BAR lists serialize in a different order across runs despite identical content; recovery: Vec insertion order is preserved by construction; any future move to an unordered collection here is a P6 compatibility regression.

20.7 Performance Concerns

Replay storage amplification: raw per-event capture without compaction can exceed the §4 128 MB budget on long soak runs; zstd compression (applied at the file level, layered atop ADR-04's Cap'n Proto encoding) plus event compaction both reduce this. Compression overhead: measured against the enumeration-completion budget only during capture, not replay — replay is an offline, unbudgeted operation.

20.8 Edge Cases

Partial replay logs (capture interrupted mid-boot, e.g. a crash during Phase 0); the decoder must reconstruct as much valid prefix as checksums allow and report the truncation point explicitly, never silently pretend the log is complete.

20.9 Failure Analysis

Corrupt replay logs are isolated at the segment level via per-segment checksums (I7's enforcement mechanism) — a single corrupted segment does not invalidate segments recorded before it, enabling partial forensic recovery even from a damaged trace.

20.10 Operational Notes

Replay archives are versioned (schema_version, P14) and immutable once written — no in-place edits, ever. Metrics: replay_trace_size_bytes, replay_divergence_total (I7's direct metric), trace_compaction_ratio. Tracing spans: replay.encode, replay.decode, replay.diff.

21. Phase 9 — Conformance, Fuzzing & Hardening

21.1 Objectives

Reach production-grade robustness through differential testing against real operating systems, sustained fuzzing, chaos injection, and long-duration soak testing — the phase that validates every invariant and every ADR chosen in the preceding nine phases actually holds under adversarial load.

21.2 Detailed Implementation Steps

  • crates/pcie-conformance/src/fixtures.rs: implement the fixture runner driving every fixtures/* corpus accumulated across §12–§20 through a single conformance entry point.
  • Add differential testing (ADR-15): compare this stack's discovered topology against Linux drivers/pci/ output and FreeBSD sys/dev/pci output on the same QEMU q35 instance, device for device.
  • Add the four fuzz targets (fuzz/fuzz_targets/*.rs, ADR-13): ACPI parser, capability parser, replay decoder, ECAM decoder — each seeded from the corresponding fixtures/ directory.
  • Add a malformed-firmware corpus generator producing structurally-mutated MCFG/capability-chain variants beyond the hand-written fixtures.
  • Add chaos injection: synthetic timeout injection (reusing Phase 2's §14 fault injector), memory- pressure testing against the §4 32 MB bootstrap ceiling, and lock-contention stress specifically targeting I6's ordering under adversarial thread scheduling.
  • Add long-duration soak tests: 72h continuous hotplug flap (rapid_flap.bin-style, sustained) under pcie-test-harness's QEMU orchestration.
  • Wire nightly differential validation into CI (.github/workflows/fuzz.yml) as a release gate, not an advisory check.

21.3 Deliverable

A hardened production candidate: 72h soak-stable, differentially validated against two independent real operating systems, with a documented fuzz-stability floor.

21.4 Acceptance Criteria

72h soak run with 0 unrecovered failures; fuzz stability exceeding 1 billion executions per target with 0 crashes and 0 sanitizer findings; 0 memory leaks under the ASan/Miri lane across the full soak duration; 0 topology divergence versus the Linux/FreeBSD differential oracle on the QEMU q35 reference fixture.

21.5 Conformance Fixtures

  • fixtures/chaos/chaos_timeout.bin — a scripted timeout storm across 40% of segments; expected: bounded quarantine, no cascading failure into unrelated segments.
  • fixtures/chaos/fuzz_seed_01.bin — the seed corpus entry point for all four fuzz targets; expected: reproducible starting state for regression triage.
  • fixtures/chaos/linux_diff_reference.bin — the captured Linux drivers/pci/ topology output for the reference QEMU fixture; expected: exact device-for-device match.

21.6 Pitfalls

  • Flaky replay determinism under fuzzing — manifestation: a fuzz-discovered input produces a crash that doesn't reproduce on replay; root cause: the fuzz harness itself introduced nondeterminism (e.g. HashMap-seeded randomness) not present in production; recovery: fuzz harnesses must use the same deterministic collections and clock source as production code, no exceptions.
  • Hidden races surfacing only under soak — manifestation: a lock-order violation (I6) that never fires in unit tests appears once per ~10⁵ hotplug cycles; debugging: the 72h soak's continuous replay capture makes every occurrence forensically reproducible even though it's rare; recovery: once reproduced from a soak-captured trace, fix and add it as a permanent fixtures/hotplug/ regression case.
  • Fuzz corpus collapse — manifestation: fuzz coverage plateaus because the corpus converges on a few input shapes; recovery: periodically reseed from newly captured production/soak replay traces, not just the original hand-written fixtures.

21.7 Performance Concerns

Fuzz throughput: instrumentation overhead (ASan, coverage counters) trades raw executions/sec for finding density — measure and report both, never just raw throughput. Soak-run instrumentation overhead must itself stay bounded so a 72h run doesn't silently violate the §4 memory ceiling through its own tracing volume — trace compaction (§20) applies to soak captures too.

21.8 Edge Cases

Malformed capability storms (thousands of devices each with a distinct malformed capability shape in one fuzz run) stress-testing P11's per-device isolation at scale; pathological topologies (maximum depth, maximum device count, maximum function count simultaneously) stress-testing every §4 ceiling at once rather than one at a time.

21.9 Failure Analysis

Every crash discovered by fuzzing or soak testing produces, automatically, a replay bundle, a topology snapshot at the point of failure, and a full trace export — the same three artifacts an operator would need in production, generated identically in CI. This closes the loop: a CI-found bug and a field-found bug are diagnosed with the exact same tooling.

21.10 Operational Notes

Nightly differential validation against Linux/FreeBSD is a required release gate (§27). Metrics: fuzz_executions_total{target}, soak_uptime_hours, differential_mismatch_total. Tracing spans: conformance.differential_run, conformance.soak_tick. This phase's exit criteria (§38) gate the first production-candidate tag.

24. Operational Readiness

Metrics strategy. Expose, at minimum: enumeration_duration_ms, ecam_read_latency_us{p50,p95,p99}, topology_size, replay_trace_size_bytes, hotplug_event_to_publish_ms, mmio_fragmentation_ratio, malformed_capability_count, capability_cycle_detected_total, config_retry_exhausted_total, replay_divergence_total. Every metric name introduced in a phase's Operational Notes subsection is exported from Phase 0 (§12) onward — dashboards do not wait for later phases to gain observability into earlier ones.

Tracing strategy. All operations emit spans carrying a trace ID (UUIDv7, per ADR-09/ADR-10), segment ID, DeviceAddress where applicable, and operation latency. Spans nest per the ADR-10 model: an enum.pass span contains enum.scan_bus spans, which contain ecam.read spans — a single trace reconstructs the full causal chain of one boot.

Alerting philosophy. Page only on: repeated enumeration failure (more than the §4 availability budget's implied failure rate), topology corruption (FM-4), and replay divergence (FM-2/I7). Do not page on individually quarantined devices (P11) — those are expected, bounded, and operator-visible without urgency.

Backup strategy. Persist replay archives, topology snapshots, and firmware captures as the three durable artifacts. All three are append-only or immutable-once-written (P6, P14); none require a separate backup mechanism beyond normal filesystem/object-store replication of write-once files.

Rolling upgrade strategy. Schema changes are additive-only (P14). Replay readers support the previous 3 minor releases' trace formats (mixed-version compatibility, §25) so a fleet upgrade never orphans in-flight captures from not-yet-upgraded nodes.

25. Compatibility & Versioning

Wire compatibility. ReplayEvent and TopologySnapshot schema changes are additive-only (P14); a field is never removed or reordered, only appended with a new schema_version.

Storage compatibility. Topology snapshots and replay archives remain readable across minor versions; a major-version bump is reserved for a breaking change to the DeviceAddress or PciDevice core layout, which has not occurred since Phase 0 (§12) and is not anticipated before CXL support (PhaseDeferred("§13")) lands.

API stability. The ConfigAccessor and ResourceAllocator traits (§11) are the stable kernel-facing enumeration API; changes follow semver with a minimum one-minor-release deprecation period before removal of any existing method.

Rolling-upgrade guarantees. Mixed-version replay readers are supported for the previous 3 minor releases — a fleet running a mix of v1.2 and v1.4 nodes can still centrally decode and diff traces from either.

26. Testing & Verification Strategy

Unit testing. Parser validation (ACPI/MCFG, capability chains) against every fixture in fixtures/acpi/ and fixtures/cap/; allocator correctness against fixtures/resource/; graph invariant checks (I1–I12) each with a dedicated unit test, per §7's one-assertion-per-invariant methodology.

Integration testing. Full QEMU q35 topology discovery (§15.4); bridge recursion against fixtures/enum/deep_hierarchy.bin; end-to-end hotplug insert/remove against fixtures/hotplug/.

Property testing. proptest (ADR-14) drives capability-chain shapes and allocator interval invariants (I3, I8) across randomized inputs — 1,000 randomized allocation-order runs per §17.4.

Fuzzing. Four cargo-fuzz targets (ADR-13): ACPI parser, capability parser, replay decoder, ECAM decoder — each with a 1-billion-execution stability floor (§21.4).

Differential testing. Compare topology output against Linux drivers/pci/ and FreeBSD sys/dev/pci (ADR-15) on the same QEMU q35 instance; any divergence is FM-9 and blocks release.

Soak testing. 72h continuous hotplug stress (§21.2) under pcie-test-harness orchestration, with full replay capture for forensic reproduction of anything found.

27. Build & Release Engineering

Reproducible builds. Pinned toolchain (ADR-26), --remap-path-prefix, frozen lockfile (ADR-03) — two independent CI runs produce identical build hashes, verified as a Phase 0 (§12) acceptance criterion and re-checked on every release.

Artifact signing. cosign (ADR-21) signatures plus provenance attestations on every release artifact; unsigned artifacts never leave a developer's workstation.

SBOM generation. syft (ADR-22) generates an SPDX document per release, diffed against the prior release to flag unexpected new transitive dependencies (T7's primary mitigation).

Release channels. Nightly (fuzz/differential gate only), beta (soak-gated), stable (72h-soak plus differential-clean, per §21.4). A build cannot promote channels without passing the gate below it.

Dependency auditing. cargo audit plus license scanning on every CI run; cargo-vet (ADR-03) blocks any new unvetted transitive dependency from merging.

28. Performance Engineering

Benchmarking strategy. criterion benchmarks enumeration latency, capability-parse throughput, and replay encode/decode throughput on every release candidate, tracked longitudinally to catch slow regressions unit tests wouldn't flag.

Profiling methodology. perf + flamegraphs (ADR-24) for CPU-bound hot paths (capability parsing, interval-allocator overlap queries); cachegrind for cache-locality regressions in the topology graph traversal.

Tail latency. p95/p99 config-read latency (§4) and p99 replay-serialization latency are the two tail metrics gating every release; both are measured on the same QEMU q35 CI reference hardware run after run to control for host variance.

29. Scalability Analysis

Primary bottlenecks. Config-access latency (bounded by chipset ECAM round-trip, not software); bridge recursion depth (bounded at 16 per §4, itself bounding total scan time); hotplug synchronization (I6 lock hold time, bounded at 50 µs).

Horizontal scaling. Enumeration is fundamentally node-local (§4 horizontal-scaling assumption) — there is no cluster to shard across. What scales horizontally instead is validation-pipeline throughput: independent segments can be traversed and capability-parsed in parallel by separate worker threads post-SMP-transition, since each segment's I6 lock chain is independent of every other segment's.

Vertical scaling. High-core-count servers, multi-root complexes, and accelerator-heavy systems push against the §4 4096-devices-per-segment and 16-level-depth ceilings directly; §32's capacity arithmetic shows exactly where those ceilings start to bind (C1, C5).

Metadata scaling. Stable IDs (I4) require a compact allocation structure — the SlotMap backing TopologyGraph (§18.2) — whose per-node overhead is the term §32's C1 bullet quantifies; metadata growth is linear in device count, not superlinear, by construction.

30. Mental Models & First Principles

  • MM1 — Topology Is Published State, Not Shared Memory. Compressed insight: treat the device graph as a versioned artifact a writer publishes and readers pull, not memory readers reach into live · Predicts: readers never need a lock to be correct, only to be current · Bug class avoided: torn reads during concurrent hotplug · applies in §18 and §19.
  • MM2 — Firmware Is an Adversary, Not a Collaborator. Compressed insight: every firmware byte is untrusted input until validated, symmetrically with how a network parser treats a socket · Predicts: a "trusted" firmware table can still be malformed by a real BIOS bug, not just an attacker · Bug class avoided: ECAM address derivation running off the end of mapped MMIO · applies in §13.
  • MM3 — Isolation Radius Determines Blast Radius. Compressed insight: the unit you quarantine on failure (one device, one bridge subtree, one segment) is a design choice, not a consequence · Predicts: choosing "device" as the isolation unit bounds a malformed capability's damage to exactly one node · Bug class avoided: one bad device taking down the entire enumeration pass · applies in §16.
  • MM4 — Determinism Is a Property of the Whole Pipeline, Not One Stage. Compressed insight: a deterministic scan order plus a nondeterministic hash-map iteration downstream still yields a nondeterministic result end to end · Predicts: I7 violations trace back to the first nondeterministic operation, not necessarily the replay layer itself · Bug class avoided: chasing replay bugs in the wrong crate · applies in §20.
  • MM5 — Bounded Beats Fast Under Adversarial Load. Compressed insight: an unbounded structure that is fast in the common case is a denial-of-service surface in the adversarial case · Predicts: every queue/cache/buffer needs an explicit ceiling before it needs an optimization · Bug class avoided: a hotplug flap storm or fuzz run exhausting the bootstrap heap · applies in §19 and §21.
  • MM6 — A Lock Order Is a Global Invariant, Not a Local Convention. Compressed insight: I6's four-level order only prevents deadlock if every lock-holding path obeys it, including ones written months later by someone who never read this document · Predicts: a deadlock introduced far from the original design will surface only under concurrent load, matching FM-6's soak-only symptom · applies in §7 and §21.
  • MM7 — Replay Determinism Is Free Only If Designed In From the Start. Compressed insight: retrofitting I7 onto a system with hidden nondeterminism (wall clocks, hash-map iteration) costs far more than avoiding those sources up front · Predicts: every crate added after Phase 8 (§20) must independently justify why it introduces no new nondeterminism · Bug class avoided: silent replay divergence discovered only in production · applies in §20.
  • MM8 — The Rejected Alternative Is Load-Bearing Documentation. Compressed insight: an ADR's 6th column (the regime where the rejected choice wins) is what lets a future engineer safely revisit the decision without re-deriving the whole design space · Predicts: an ADR without that column will be silently violated the first time someone hits its regime · Bug class avoided: re-litigating settled decisions from scratch under time pressure · applies in §9 and §34.

32. Back-of-Envelope Capacity Model

  • C1 — Topology Node Memory. 4096 devices × 400 B/PciDevice (address + IDs + up to 8 BAR slots + capability-vec header) = 1.64 MB, well inside the 32 MB §4 bootstrap ceiling.
  • C2 — Edge Memory. 4096 devices × 1 BridgeEdge parent link avg × 24 B = 98 KB, negligible against the same ceiling.
  • C3 — Replay Trace Worst Case. 4096 devices × 30 events/device (header + BAR probe + capability walk) × 64 B/event = 7.86 MB per full-boot capture; × 16 accumulation factor for a 72h soak before compaction = 125.8 MB, at the 128 MB §4 replay-trace ceiling.
  • C4 — Enumeration Time Budget. 4096 devices × 6 config reads/device × 10 µs p95 (§4) = 245.76 ms, inside the < 250 ms §4 typical-completion target.
  • C5 — Cold Boot Worst Case. 4096 devices × 20 reads/device (header + BAR sizing steps + capability walk) × 25 µs p99 (§4) = 2.048 s, at the §4 < 2 s cold-boot ceiling.
  • C6 — Hotplug Mutation Stall. 64-entry bounded hotplug queue (P4) × 50 µs max lock hold (§4) = 3.2 ms, under the < 5 ms §4 mutation-stall ceiling.
  • C7 — Interval Allocator Memory. 4096 devices × 3 BARs/device avg × 32 B/interval node = 393 KB, negligible against the 32 MB §4 bootstrap ceiling.
  • C8 — CLI Concurrency. 256 FD budget (§4) ÷ 3 FDs/session (replay file + topology export + log) = 85 concurrent pcie-cli sessions supported.
  • C9 — MMIO Fragmentation Headroom. 5% §4 fragmentation ceiling × 3072 MB typical sub-4GB MMIO hole = 153.6 MB worst-case waste, still far above the tens-of-MB aggregate BAR demand of a 4096-device fabric.
  • C10 — Sustained Fuzz Throughput. 1B executions/target (§21.4) ÷ 259,200 s (72h) = 3,858 executions/sec/target sustained, the floor pcie-conformance's CI runners must clear.

34. Alternative Architectures (Roads Not Taken)

Alt A — Fully Async Reactor-Based Enumeration

[Interrupt / Hotplug Source] -> [Async Executor Task Queue]
                                        |
                                        v
                              [Config Access Future]  (await ECAM read)
                                        |
                                        v
                              [Topology Mutation Task Pool]

Regime where it wins: a userspace-only enumeration daemon integrating with an async-heavy component framework, where blocking on config-space IO would stall unrelated tasks sharing one executor. Real system embodying it: Fuchsia's component-based driver framework, which is extensively async Rust. Why rejected here: Phase 0 bootstrap (§12) runs before the scheduler is online (§1's execution assumptions) — no executor exists yet at the point this stack must start working, and maintaining two code paths (sync bootstrap, async post-boot) doubles the surface I7 must keep deterministic (ADR-07).

Alt B — Single Global Topology Lock

[Any Reader/Writer] --acquire--> [ONE Mutex<TopologyGraph>] --release-->

Regime where it wins: small embedded systems with a device count far below the §4 4096 ceiling — tens, not thousands — where lock granularity is irrelevant and code simplicity dominates. Real system embodying it: early single-threaded PCI daemons such as Redox OS's pcid (§5's reference-implementation pitfall note). Why rejected here: it serializes unrelated segments under concurrent hotplug, directly worsening the §29 hotplug-synchronization bottleneck at the device counts this stack targets, and eliminates the parallelism §29's horizontal-scaling section relies on for validation-pipeline throughput.

Alt C — Firmware-Delegated AML Interpreter

[Firmware AML Interpreter] --resource decisions--> [OS reads final _CRS result]
        (full ACPI Machine Language execution owns PCI resource negotiation)

Regime where it wins: legacy BIOS-centric systems where the OS deliberately defers to firmware resource negotiation rather than re-deriving it — historically, Windows' PnP Manager leaned heavily on ACPI _CRS/_PRS methods for exactly this reason on legacy hardware. Why rejected here: it removes this project's core value proposition — an OS-side enumerator that validates firmware rather than trusting it (P7) — and, per Q19 (§33), eliminates the only enforcement point several of the §7 invariants have in this codebase.

36. Glossary

  • ECAM — Enhanced Configuration Access Mechanism; MMIO-based access to PCIe configuration space.
  • BAR — Base Address Register; a device config register describing an MMIO or IO address window.
  • MCFG — the ACPI table describing per-segment ECAM base addresses and bus ranges.
  • Root Complex — the CPU-to-PCIe bridge; the topology's root node(s).
  • Endpoint — a terminal PCIe device with no downstream ports.
  • MSI — Message Signaled Interrupt; interrupt delivery via a memory write rather than a pin.
  • MSI-X — an extended MSI mechanism supporting a per-vector table of address/data pairs.
  • AER — Advanced Error Reporting; a PCIe extended capability for link/protocol error reporting.
  • MMIO — memory-mapped IO; device registers addressed within the CPU's physical address space.
  • Segment — a PCI domain; a group of buses sharing one ECAM base address.
  • Topology Snapshot — an immutable, generation-versioned image of the device graph.
  • Replay Artifact — a deterministic, checksum-validated capture of enumeration events.
  • Bridge Window — the MMIO/IO aperture a bridge forwards to its downstream (secondary) bus.
  • Hotplug — runtime insertion or removal of a device without a reboot.
  • Capability Chain — a linked list of capability structures within configuration space.
  • Function — a PCI logical sub-device; up to 8 per device, addressed by the function field.
  • Device ID — a vendor-defined 16-bit identifier for a specific product.
  • Vendor ID — a PCI-SIG-assigned 16-bit identifier for a device manufacturer.
  • Bus Number — an 8-bit routing identifier within a segment's hierarchy.
  • Prefetchable BAR — an MMIO region safe for read-caching/speculation by the CPU.
  • Header Type — the config-space field distinguishing endpoint (0), bridge (1), CardBus (2, unsupported).
  • Subordinate Bus — the highest bus number reachable downstream of a given bridge.
  • Secondary Bus — the bus number a bridge assigns to its immediately downstream segment.
  • DeviceAddress — the canonical (segment, bus, device, function) tuple identifying a function.
  • DeviceId — a stable, epoch-scoped topology identifier surviving rescans (I4).
  • Generation — a monotonically increasing counter identifying one published topology version.
  • Quarantine — marking a device Failed and excluding it from further access without aborting the scan.
  • Debounce — collapsing a rapid sequence of hotplug events into one net event.
  • Interval Allocator — the data structure enforcing non-overlapping BAR/window assignment (I3).
  • Fail-Closed — rejecting untrusted or ambiguous input rather than proceeding optimistically (P7).
  • Crash-Only — a design discipline where restart, not graceful shutdown, is the only recovery path (P3).
  • Backpressure — a producer slowing or dropping output in response to a bounded consumer (P9).
  • Lock Order — the fixed acquisition sequence (I6) preventing deadlock across subsystems.
  • Differential Testing — comparing this stack's output against an independent reference implementation.
  • Soak Test — a long-duration (72h) stress test surfacing rare, load-dependent failures.
  • SBOM — Software Bill of Materials; a manifest of all dependencies in a released artifact.
  • TLP — Transaction Layer Packet; the PCIe protocol-layer unit this stack does not itself implement.
  • ASPM — Active State Power Management; a link power-saving feature explicitly out of Phase 0 scope.
  • CXL — Compute Express Link; a PCIe-electrical protocol for memory/accelerator coherency, deferred (§13).
  • RSDP — Root System Description Pointer; the ACPI entry point located at boot.
  • XSDT — Extended System Description Table; the ACPI table-of-tables walked to find MCFG.
