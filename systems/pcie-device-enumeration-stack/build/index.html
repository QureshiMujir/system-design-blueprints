⬜ Phase 0 — Repository Bootstrap & Platform Foundations §12

Objectives

Establish the repository skeleton, CI pipeline, and the architecture-abstraction boundary that every later phase builds on. Introduce the constraints that hold for the rest of the project: no_std kernel-space linkage, a pinned deterministic toolchain (ADR-26), and a mandatory tracing posture (P2) from the very first commit. This phase produces no PCIe-specific logic — it produces the correctness kernel (unsafe boundary, error taxonomy, barrier primitives) everything else sits on.

Deliverable

Workspace compiles clean on stable + nightly; CI green on all three lanes; a QEMU q35 instance boots to the point where pcie-platform-abstraction successfully maps one MMIO test page; tracing emits at least one structured span per boot, serialized and inspectable via pcie-cli.

Acceptance

Zero clippy warnings across the workspace; build hashes identical across two independent CI runs (ADR-26); the Miri/ASan sanitizer lane passes with 0 findings; bootstrap_trace.bin decodes with pcie-replay and round-trips through pcie-cli --dump byte-identical to the captured original.

Fixtures
  • fixtures/bootstrap/bootstrap_trace.bin — golden boot trace; expected: decodes cleanly, 1 FirmwareCapture event minimum.
  • fixtures/bootstrap/invalid_mmio_alignment.bin — malformed replay of an unaligned MMIO map request; expected: pcie-platform-abstraction rejects with EcamError::Unaligned, not a panic.
  • fixtures/bootstrap/replay_seed_0001.bin — deterministic seed for the Phase 9 (§21) soak harness.
Pitfalls
  • Unsafe MMIO aliasing — manifestation: stale config reads after a remap; root cause: two virtual mappings of the same physical ECAM page without a barrier between them; debugging: compare physical-address ranges across all active mappings in a replay dump; signal: ecam_unaligned_access_total unexpectedly non-zero; recovery: enforce single-mapping-per-window in pcie-platform-abstraction.
  • Missing memory barriers — manifestation: non-deterministic config reads on ARM64 only; root cause: relaxed-ordering load reordered ahead of a prior store by the compiler or CPU; signal: I7 replay divergence on ARM64 CI only; recovery: audit every ConfigAccessor call site for a paired barrier per ADR-27's monotonic-time discipline (barriers, not the clock, fix this — the clock choice just makes the divergence visible in a timestamp diff).
  • Toolchain drift — manifestation: replay traces captured on one CI runner fail I7 on another; root cause: a floating nightly toolchain (the ADR-26 rejected alternative) changed struct padding; recovery: pin via rust-toolchain.toml, re-run the full fixture corpus.

⬜ Phase 1 — ACPI & MCFG Discovery §13

Objectives

Implement robust, fail-closed firmware discovery: locate and validate the MCFG table so every later phase can trust the ECAM window addresses it derives from it. Introduce P7 (parse nothing lazily without validation) as an enforced, tested property, not an aspiration.

Deliverable

Valid MCFG extraction on both QEMU q35 and a real x86_64 host; ECAM windows mapped into pcie-platform-abstraction and handed to Phase 2 (§14) as a validated EcamWindow list.

Acceptance

All fixtures in fixtures/acpi/ classified correctly (accept/reject) with 0 false accepts; the acpi_parser fuzz target survives 24h continuous fuzzing with 0 crashes and 0 unchecked-panic findings; parser recursion never exceeds the fixed depth bound on any fixture.

Fixtures
  • fixtures/acpi/mcfg_valid_01.bin — well-formed single-segment MCFG; expected: accept, one EcamWindow produced.
  • fixtures/acpi/mcfg_overlap.bin — two segments with overlapping ECAM ranges; expected: reject with AcpiError::OverlappingWindows.
  • fixtures/acpi/mcfg_bad_checksum.bin — corrupted table checksum; expected: reject before any field is read, per P7.
Pitfalls
  • Firmware truncation — manifestation: MCFG table claims more segment entries than its declared length permits; root cause: a buggy firmware build; debugging: compare declared length against parsed entry count; recovery: reject, do not read past the declared boundary.
  • Overlapping segments — manifestation: two ECAM windows claim the same physical range; debugging: interval-overlap check against every prior accepted window; recovery: reject the later window, quarantine that segment only.
  • Integer overflow in bus-window math — manifestation: a segment's declared bus range wraps past u8::MAX; root cause: unchecked arithmetic on an untrusted firmware field; recovery: use checked arithmetic exclusively in this crate (a direct consequence of P7).

⬜ Phase 2 — ECAM Access Layer §14

Objectives

Implement the single, safe path for all configuration-space access. Every later phase's config reads and writes funnel through this crate — no other crate is permitted direct ECAM MMIO access.

Deliverable

A ConfigAccessor implementation that passes 100% of fixtures/ecam/ with deterministic replay and meets the §4 p50 < 1 µs / p95 < 10 µs / p99 < 25 µs latency targets on QEMU q35 CI hardware.

Acceptance

100% replay determinism (I7) across 3 consecutive runs of the full fixtures/ecam/ corpus; out-of-range offsets rejected with EcamError::OutOfRange in 100% of cases; measured p99 latency ≤ 25 µs on the CI reference host.

Fixtures
  • fixtures/ecam/ecam_timeout.bin — simulated bus timeout; expected: 3 retries then quarantine.
  • fixtures/ecam/ecam_partial_read.bin — a torn 32-bit read split across two bus beats; expected: reject, do not return a half-updated value.
  • fixtures/ecam/ecam_alignment_violation.bin — a 2-byte-aligned 32-bit read request; expected: reject before any MMIO instruction issues, per I1.
Pitfalls
  • Stale mappings — manifestation: reads return data from a device that was hot-removed; root cause: pcie-platform-abstraction cache of a since-invalidated MMIO mapping; debugging: cross-check mapping generation against the topology generation (I10); recovery: invalidate the ECAM mapping cache on every hotplug event.
  • Write tearing — manifestation: a 32-bit BAR write appears as two 16-bit writes on some chipsets; root cause: compiler/hardware splitting a store; recovery: use bytemuck's volatile write primitives exclusively, never a plain slice assignment (ADR-05).
  • Speculative reads — manifestation: a config read appears to happen before its preceding write completes; root cause: missing store-load barrier; debugging: I7 replay divergence localized to write-then-read sequences; recovery: insert the barrier pcie-platform-abstraction provides around every write-then-read pair.

⬜ Phase 3 — Basic Enumeration Engine §15

Objectives

Implement the recursive PCIe discovery walk itself: bus 0 outward, through every bridge, to every endpoint function, building the first version of the topology graph.

Deliverable

Complete topology discovery on the QEMU q35 reference fixture, matching the Linux drivers/pci/ differential oracle (ADR-15) device-for-device.

Acceptance

QEMU q35's reference topology (13 known devices across 3 bridge levels in the CI fixture) discovered with 0 missing and 0 phantom devices; graph hash stable and identical across 10 consecutive scan runs.

Fixtures
  • fixtures/enum/bridge_loop.bin — a bridge whose secondary bus number equals its primary; expected: reject that bridge, continue enumerating siblings.
  • fixtures/enum/multifunction_sparse.bin — functions 0, 2, 5 present, 1/3/4/6/7 absent; expected: exactly 3 functions discovered, no scan of the absent slots retried.
  • fixtures/enum/deep_hierarchy.bin — exactly 16 nested bridge levels; expected: full discovery at the §4 depth ceiling, and a 17th synthetic level rejected.
Pitfalls
  • Bridge recursion loops — manifestation: enumeration hangs; root cause: a bridge reports a secondary bus number that routes back to an ancestor; debugging: the ancestor-bus-number set carried down the recursion catches this in O(depth); recovery: reject the bridge, mark it Failed, continue its siblings.
  • Invalid subordinate buses — manifestation: a bridge's subordinate bus number is less than its secondary bus number; recovery: reject per I9's uniqueness requirement, which this also violates.
  • Duplicate functions — manifestation: the same DeviceAddress observed twice in one pass; root cause: a firmware/emulator bug re-exposing a slot; recovery: first-observation wins, subsequent observations logged and dropped.

⬜ Phase 4 — Capability Parsing §16

Objectives

Implement robust standard and extended capability discovery: MSI, MSI-X, power management, PCIe capability, and vendor-specific chains, with mandatory cycle detection from the first line of code.

Deliverable

A normalized capability registry attached to every discovered device, with MSI/MSI-X presence and parameters available to interrupt-controller integration (a later, out-of-scope, consuming layer).

Acceptance

100% of fixtures/cap/cap_cycle.bin variants (5 distinct cycle shapes) detected and aborted within 16 chain steps; malformed capability lengths rejected in 100% of cases; vendor capabilities isolated such that an unrecognized vendor ID never blocks MSI/MSI-X parsing on the same device.

Fixtures
  • fixtures/cap/cap_cycle.bin — capability A → B → A; expected: cycle detected, device marked degraded, enumeration continues.
  • fixtures/cap/msix_corrupt.bin — MSI-X table_bar index pointing at a non-existent BAR; expected: reject the MSI-X capability specifically, keep other capabilities on the same device.
  • fixtures/cap/vendor_cap_unknown.bin — an unregistered vendor capability ID; expected: parsed as Capability::Vendor with raw bytes intact, no rejection.
Pitfalls
  • Endless loops on malformed lists — manifestation: capability parsing never terminates without the I5 bitmap; debugging: this is exactly why I5 is a table row, not a comment — the bitmap check is the enforcement point, tested directly by cap_cycle.bin.
  • Invalid offsets — manifestation: a next-pointer field points inside the header region (offset < 0x40); recovery: reject any next-pointer below the minimum valid capability offset.
  • Capability overlap — manifestation: two capabilities claim overlapping byte ranges; root cause: a malformed or adversarial device; recovery: the second capability to claim an already- claimed range is rejected, not merged.

⬜ Phase 5 — Resource Allocation Engine §17

Objectives

Implement BAR sizing and MMIO/IO window allocation: turn a discovered-but-unassigned device into a fully resourced one, with zero overlap and correct alignment, replayable end to end.

Deliverable

A fully resourced topology: every Active device has BAR assignments with 0 overlaps, verified against the QEMU q35 reference fixture's known BAR layout.

Acceptance

0 overlaps across 1,000 randomized allocation-order test runs (property test, ADR-14); alignment correctness verified against I8 for every BAR in fixtures/resource/; rollback verified to restore the pre-batch allocator state byte-for-byte on injected mid-batch failure.

Fixtures
  • fixtures/resource/bar_overlap.bin — two devices' pre-sized BARs would overlap if placed naively; expected: allocator places them non-overlapping, or rejects the second if the window is exhausted.
  • fixtures/resource/bar_64_split.bin — a 64-bit BAR pair; expected: sized/restored as one unit, never as two independent 32-bit BARs.
  • fixtures/resource/bridge_window_exhausted.bin — a bridge's forwarded window too small for its children's combined BAR demand; expected: reject the excess child, quarantine it, not the bridge.
Pitfalls
  • 64-bit BAR ordering — manifestation: the high 32 bits are sized/restored out of sequence with the low 32 bits, corrupting the base address; recovery: treat the pair as one atomic operation in pcie-resource, never two independent register writes.
  • Allocator fragmentation — manifestation: fragmentation metric creeps toward the §4 5% ceiling under mixed 32-/64-bit workloads; debugging: fragmentation histogram by BAR-size bucket; recovery: size-class segregation in the interval allocator (larger BARs placed first).
  • Stale BAR restores — manifestation: the original BAR value restored after sizing doesn't match what was actually there before, corrupting a device already configured by firmware; root cause: a race between the sizing probe and a concurrent hotplug rescan; recovery: hold the device lock (I6) for the entire save→write→read→restore sequence as one atomic unit.

⬜ Phase 6 — Topology Graph & Snapshotting §18

Objectives

Build the stable runtime topology model that every consumer (drivers, IOMMU, hypervisor) reads from: generation-versioned, snapshot-consistent, with stable device identity across rescans.

Deliverable

A stable, generation-versioned topology API: pcie-cli --dump-topology produces a snapshot whose hash is reproducible across repeated dumps of the same generation.

Acceptance

Snapshot consistency verified under 500 concurrent-reader stress runs with 0 partial reads observed (I10); graph hashes deterministic and identical across 10 repeated dumps of the same generation; diff engine produces the exact expected delta on fixtures/topology/topology_diff.bin.

Fixtures
  • fixtures/topology/snapshot_consistency.bin — a scripted concurrent read during a scripted mutation; expected: the reader observes exactly one of the two generations, never a mix.
  • fixtures/topology/topology_diff.bin — two generations differing by one inserted, one removed device; expected: the diff engine reports exactly those two changes, nothing else.
Pitfalls
  • Stale references — manifestation: a held DeviceId from generation N is queried against generation N+1 after the device was removed; recovery: lookups against a stale generation return None, never a use-after-free — the SlotMap generation check makes this structurally impossible rather than merely tested-against.
  • Generation mismatch — manifestation: a consumer caches a TopologySnapshot reference across a mutation and acts on stale data as if current; recovery: every consumer-facing API that returns live data also returns the generation it was read at, forcing explicit staleness checks.
  • Graph mutation races — manifestation: two mutation calls interleave without going through pcie-hotplug-core's single mutation path; recovery: TopologyGraph's mutation methods are pub(crate)-visible only to pcie-hotplug-core (P5's single-writer discipline enforced at the visibility level, not just by convention).

⬜ Phase 7 — Hotplug & Mutation Engine §19

Objectives

Implement dynamic topology updates: the only path by which a running system's topology changes after initial boot, without corrupting concurrent readers.

Deliverable

Live topology mutation: a hotplug_insert.bin-scripted insertion is visible in pcie-cli --dump-topology within the §4 5 ms mutation-stall budget, with 0 reader crashes.

Acceptance

0 reader crashes across 200 concurrent-reader-during-mutation stress runs; mutation latency p99 under 5 ms per §4; deterministic replay of hotplug_insert.bin/hotplug_remove.bin produces the identical resulting TopologySnapshot on every run (I7).

Fixtures
  • fixtures/hotplug/hotplug_insert.bin — a single device inserted into an empty slot; expected: new Active device, generation incremented by exactly 1.
  • fixtures/hotplug/hotplug_remove.bin — removal of a previously Active device; expected: node transitions to Removed, its ResourceWindow released and verified non-overlapping-available.
  • fixtures/hotplug/rapid_flap.bin — 50 insert/remove cycles in 200 ms; expected: debounced to the correct net state, no queue overflow, no dropped final-state event.
Pitfalls
  • Use-after-free (logical, not memory-unsafe in Rust, but state-level) — manifestation: a rebalance operation reads a BarDescriptor for a device that was removed mid-rebalance; recovery: the rebalance critical section holds the device lock (I6) for its full duration, making this ordering violation structurally excluded, not just guarded.
  • Stale handles — manifestation: pcie-cli holds a DeviceId across a remove-then-reinsert and expects it to still resolve; recovery: DeviceId incorporates a topology epoch (§18.2); a reinsertion after removal gets a new epoch-scoped ID by design, and this is documented, not a bug.
  • Race windows — manifestation: an insertion scan and a concurrent removal of a sibling interleave; recovery: both funnel through the single hotplug mutation path (P5), serialized by I6, so "interleaving" at the topology-mutation level is impossible by construction — only the event queue can interleave, and debounce/ordering there is explicitly tested.

⬜ Phase 8 — Replay & Deterministic Diagnostics §20

Objectives

Implement the deterministic replay infrastructure that every prior phase has been emitting events into: turn the accumulated ReplayEvent stream into a reproducible, diffable, forensic artifact.

Deliverable

A reproducible replay system: pcie-cli --replay replay_full_boot.bin reconstructs the exact TopologySnapshot that the original boot produced, with a matching graph hash.

Acceptance

Byte-identical topology replay (I7) verified across 20 repeated replays of replay_full_boot.bin; graph hashes stable across all 20; trace compaction keeps replay_full_boot.bin under the §4 128 MB budget for a 4096-device synthetic worst-case fixture.

Fixtures
  • fixtures/replay/replay_full_boot.bin — a complete boot capture including ACPI, ECAM, enumeration, capability, and resource events; expected: full byte-identical topology reconstruction.
  • fixtures/replay/replay_hotplug.bin — a boot capture plus one hotplug insert/remove cycle; expected: identical reconstruction including the post-hotplug generation.
Pitfalls
  • Hidden nondeterminism — manifestation: two replays of the same trace produce different graph hashes; root cause: an iteration order somewhere (e.g., a HashMap instead of the SlotMap insertion order) leaking into the observable result; debugging: bisect the event stream to the first diverging event; recovery: audit every iteration site touched by replay for ordering guarantees, not just correctness.
  • Clock drift — manifestation: a replay run on different hardware disagrees on relative event timing enough to change debounce-window outcomes in Phase 7's logic; recovery: replay uses recorded relative timestamps, never re-measures wall time during replay.
  • Unstable iteration ordering — manifestation: capability or BAR lists serialize in a different order across runs despite identical content; recovery: Vec insertion order is preserved by construction; any future move to an unordered collection here is a P6 compatibility regression.

⬜ Phase 9 — Conformance, Fuzzing & Hardening §21

Objectives

Reach production-grade robustness through differential testing against real operating systems, sustained fuzzing, chaos injection, and long-duration soak testing — the phase that validates every invariant and every ADR chosen in the preceding nine phases actually holds under adversarial load.

Deliverable

A hardened production candidate: 72h soak-stable, differentially validated against two independent real operating systems, with a documented fuzz-stability floor.

Acceptance

72h soak run with 0 unrecovered failures; fuzz stability exceeding 1 billion executions per target with 0 crashes and 0 sanitizer findings; 0 memory leaks under the ASan/Miri lane across the full soak duration; 0 topology divergence versus the Linux/FreeBSD differential oracle on the QEMU q35 reference fixture.

Fixtures
  • fixtures/chaos/chaos_timeout.bin — a scripted timeout storm across 40% of segments; expected: bounded quarantine, no cascading failure into unrelated segments.
  • fixtures/chaos/fuzz_seed_01.bin — the seed corpus entry point for all four fuzz targets; expected: reproducible starting state for regression triage.
  • fixtures/chaos/linux_diff_reference.bin — the captured Linux drivers/pci/ topology output for the reference QEMU fixture; expected: exact device-for-device match.
Pitfalls
  • Flaky replay determinism under fuzzing — manifestation: a fuzz-discovered input produces a crash that doesn't reproduce on replay; root cause: the fuzz harness itself introduced nondeterminism (e.g. HashMap-seeded randomness) not present in production; recovery: fuzz harnesses must use the same deterministic collections and clock source as production code, no exceptions.
  • Hidden races surfacing only under soak — manifestation: a lock-order violation (I6) that never fires in unit tests appears once per ~10⁵ hotplug cycles; debugging: the 72h soak's continuous replay capture makes every occurrence forensically reproducible even though it's rare; recovery: once reproduced from a soak-captured trace, fix and add it as a permanent fixtures/hotplug/ regression case.
  • Fuzz corpus collapse — manifestation: fuzz coverage plateaus because the corpus converges on a few input shapes; recovery: periodically reseed from newly captured production/soak replay traces, not just the original hand-written fixtures.
