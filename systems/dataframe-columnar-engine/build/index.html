⬜ Phase 0 — Repo Skeleton + Aligned Buffer + Validity Bitmap + Memory Pool Scaffolding §12

Objectives

Stand up the workspace and the lowest layer: 64-byte-aligned Bytes, Arc-shared zero-copy Buffer, LSB0 Bitmap, and a MemoryPool skeleton. Constraint introduced: every byte buffer is aligned + accounted.

Deliverable

cargo build workspace; a smoke test that allocates a 64-byte-aligned buffer, slices it zero-copy (refcount==2), builds a bitmap of 1000 bits, and reserves/releases pool memory.

Acceptance
  • alloc_aligned returns ptr % 64 == 0 for all sizes (proptest). [I4]
  • Bitmap::count_set matches a scalar reference for 10k random bitmaps.
  • Buffer::slice shares the parent Arc (no copy; Arc::strong_count increments).
  • MemoryPool used returns to 0 after all Reservations drop; over-budget reserve → EngineError::OutOfMemory.
  • miri clean on cx-buffer; clippy zero warnings.
Fixtures

fx/buffer/align_sizes.json (sizes 0..4096 → expected alignment), fx/bitmap/popcount_cases.json (bit patterns → set counts), fx/bitmap/slice_offsets.json (offset/len → expected bits). Malformed: zero-length alloc, slice past end (must error).

Pitfalls
  • Forgetting to pad capacity to 64 → SIMD over-read past allocation (use padded cap).
  • Bit offset in Bitmap::slice mishandled → off-by-one nulls downstream.
  • typed::<T>() on a misaligned offset → UB; assert offset*size % align(T) == 0.
  • AtomicUsize accounting using Relaxed where AcqRel needed → drift under contention.

⬜ Phase 1 — Type System + ArrayData + Primitive/Boolean Arrays + Null Semantics §13

Objectives

Define DataType/Field/Schema, the ArrayData container with validation, and the first concrete arrays (PrimitiveArray<T>, BooleanArray) with correct null semantics. Constraint: every array validates its invariants on construction.

Deliverable

Build Int32Array[10,20,NULL,40] via builder; value(0)==10, is_null(2)==true, null_count()==1; matches the §8.2 byte diagram.

Acceptance
  • ArrayData::validate rejects len/bitmap mismatch, wrong buffer count, bad null_count.
  • PrimitiveArray::<i32>::iter() yields [Some(10),Some(20),None,Some(40)].
  • BooleanArray packs values 1 bit each (4 values → 1 data byte + 1 validity byte).
  • Schema rejects duplicate field names; column lookup O(1) by index, hash by name.
  • Property test: random builds round-trip through iter() losslessly (including null positions). [I2]
Fixtures

fx/array/int32_with_nulls.json, fx/array/bool_packed.json, fx/schema/dup_names.json (must error), fx/array/null_count_mismatch.bin (malformed → validate error).

Pitfalls
  • Reading value(i) on a null slot returns garbage — callers must check is_null first (or use iter()). [I2]
  • BooleanArray confusing the values bitmap with the validity bitmap (two separate bitmaps).
  • null_count not recomputed after slice → wrong fast-path. [I15]
  • Decimal scale/precision validation skipped → wrong arithmetic later.

⬜ Phase 2 — Variable-Length, List, Struct, Dictionary Arrays + Zero-Copy Slice §14

Objectives

Implement offset-based (Utf8/Binary, i32 + i64 large), nested (List, Struct), and DictionaryArray; implement universal zero-copy slice. Constraint: offsets monotonic (I3); dict indices in range (I5).

Deliverable

Construct Utf8["arrow","",NULL,"db"], List<Int32>[[1,2],[],NULL], Dictionary<Int8,Utf8> from §8.2; slice each [1..3] zero-copy; decode() a dictionary back to Utf8.

Acceptance
  • Utf8Array::value returns correct substrings; rejects non-UTF8 with EngineError::Schema.
  • slice shares parent buffers (Arc::strong_count unchanged for data; only view changes) and reports correct null_count. [I13,I15]
  • Offset validation rejects non-monotone / wrong-terminal offsets. [I3]
  • Dictionary with an out-of-range key → construct error. [I5]
  • List slice yields child sub-slices with correct lengths; nested List<List<T>> round-trips.
Fixtures

fx/array/utf8_offsets.json, fx/array/list_int32.json, fx/array/dict_i8_utf8.json, fx/array/slice_cases.json. Malformed: non_monotone_offsets.bin, dict_index_oob.bin, utf8_invalid_bytes.bin.

Pitfalls
  • Slicing a Utf8/List array must NOT slice the data/child buffer — only the offsets view; the data buffer stays whole (offsets index into it).
  • Confusing a NULL list with an empty list [] — both have equal start/end offsets; the bitmap distinguishes them.
  • Dictionary null encoded in the keys validity, not as a reserved index.
  • Recomputing null_count over a sliced bitmap requires honoring the bit offset.

⬜ Phase 3 — Compute Kernels I: Arithmetic, Comparison, Boolean, Cast §15

Objectives

First kernel family: arithmetic, comparison, boolean (Kleene), cast/coercion — all null-aware and SIMD-friendly. Constraint: validity propagation is uniform (out_valid = lhs_valid & rhs_valid), Kleene tables exact (I8 prep).

Deliverable

add(Int32[1,2,NULL], Int32[10,NULL,30]) == Int32[11,NULL,NULL]; gt(a, lit(10)) mask; and_kleene(T,U)==U; cast(Utf8["1","x"], Int32, safe) == [1, NULL].

Acceptance
  • Validity propagation exact across all arithmetic/compare kernels (proptest vs scalar reference). [I8 prep]
  • Kleene truth tables match §8.4 for all 9 input combinations each (and/or/not).
  • Checked overflow policy errors on i32 overflow; Upcast widens; Wrapping wraps — all tested.
  • cast safe-mode nulls invalid values; strict-mode errors; lossless casts bit-exact.
  • SIMD path and scalar path produce identical results (differential test, simd on/off).
Fixtures

fx/compute/arith_nulls.json, fx/compute/kleene_tables.json, fx/compute/cast_matrix.json (every dtype pair), fx/compute/overflow_policy.json. Malformed: cast Utf8→Int with non-numeric (safe→null, strict→error).

Pitfalls
  • Computing values for null slots then masking is fine for arithmetic but UB for div (div-by-zero on garbage) — mask inputs or guard division.
  • and/or must use Kleene (validity-aware), not plain bitwise (which would treat null as a value).
  • Float compare with NaN: NaN == NaN is false but should the kernel treat it as null? No — NaN is a value, null is the bitmap; keep them distinct.
  • Integer div/rem by zero must not panic in release — return null/error per policy.

⬜ Phase 4 — Compute Kernels II: Filter, Take, Sort, Hash, Unique §16

Objectives

Selection + reordering kernels that power filtering, joins, group-by, and ordering: filter (mask), take (gather), sort_indices (multi-key stable), hash, unique. Constraint: stable + deterministic sort when requested (I12); these kernels are the late-materialization machinery (Principle 4).

Deliverable

filter(Int32[1,2,3,4], mask[T,F,T,F]) == [1,3]; take([10,20,30], idx[2,0,2]) == [30,10,30]; sort_indices([3,1,2], asc) == [1,2,0]; unique([1,1,2,NULL,NULL]) == [1,2,NULL].

Acceptance
  • filter preserves validity of surviving slots; count_set(mask) == output length.
  • take with null index yields null output; OOB index errors; take(a, range(len)) == a.
  • Sort is stable: equal keys keep input order (proptest); deterministic across runs and thread counts. [I12]
  • Multi-key sort orders by key 0, ties by key 1, etc.; nulls_first/last honored.
  • hash is identical across simd on/off; collisions handled by downstream tables (kernel just hashes).
Fixtures

fx/compute/filter_cases.json, fx/compute/take_gather.json, fx/compute/sort_multikey.json, fx/compute/sort_nulls.json, fx/compute/unique_null.json. Malformed: take_oob.json (error), empty-mask filter.

Pitfalls
  • filter must compress both values and validity bitmap in lockstep; a desync corrupts nulls.
  • Radix sort on signed ints must flip the sign bit (or handle two's-complement ordering) before bytewise sort.
  • NaN ordering: define NaN as greatest (or per option) so sort has a total order; otherwise unstable.
  • take building a new validity bitmap: index-null OR source-null → output-null.
  • Hashing floats: ±0.0 must hash equal (normalize), NaN must hash consistently.

⬜ Phase 5 — Series + ChunkedArray + DataFrame Eager API §17

Objectives

The user-facing eager layer: ChunkedArray (multi-chunk column), named Series, DataFrame (Vec<Series> + schema) with select/filter/with_columns/head/slice/concat/sort/unique. Constraint: all columns equal length (I7); chunks share dtype (I6).

Deliverable

Build a 3-column DataFrame; df.filter(mask).select(["a","b"]).sort([SortKey(a)]) returns a correct new frame; concat two schema-equal frames vertically.

Acceptance
  • DataFrame rejects unequal-length columns at construction. [I7]
  • select by name + index; missing name → EngineError::NotFound.
  • filter applies one mask across all columns consistently (same surviving rows).
  • vstack rejects schema mismatch [I6]; hstack rejects length mismatch.
  • head(n)/slice are zero-copy where chunk boundaries allow.
Fixtures

fx/frame/select_filter.json, fx/frame/concat_vertical.json, fx/frame/concat_schema_mismatch.json (error), fx/frame/multichunk_sort.json.

Pitfalls
  • Chunk fragmentation: many tiny chunks slow every op; rechunk strategically (but rechunk copies — don't do it implicitly in hot paths).
  • A filter mask length must equal the frame's row count, not a single chunk's.
  • sort across chunks needs a global sort, not per-chunk — gather via sort_indices over the rechunked or virtually-concatenated column.
  • with_columns replacing an existing name must preserve column order semantics.

⬜ Phase 6 — Aggregation: Hash Group-By + Aggregates (Partitioned, Parallel) §18

Objectives

Hash group-by with sum/min/max/mean/count/count_all/var/std/first/last/n_unique, partitioned for parallelism, with correct null semantics (I8) and overflow policy (§4). This is the first heavy operator and the first spill candidate.

Deliverable

df.group_by("b").agg([sum("c"), mean("d"), count("e")]) over 10M rows → correct per-group results; parallel across cores; matches DuckDB on a fixture.

Acceptance
  • Aggregate null rules exact vs DuckDB (differential) on a null-heavy fixture. [I8]
  • sum(Int32) that overflows i32 produces correct i64 result (no wraparound) under default policy.
  • Parallel result == single-threaded result (determinism of values; row order unordered unless sorted).
  • Group-by scales near-linearly to N cores until hash-table-bound (benchmark).
  • Empty input: grouped → 0 rows; ungrouped → 1 row with sum=null,count=0.
Fixtures

fx/agg/groupby_basic.json, fx/agg/null_rules.json (COUNT vs COUNT(*)), fx/agg/overflow_sum.json, fx/agg/var_welford.json, fx/agg/empty_groups.json, fx/agg/skew_keys.json (one giant group).

Pitfalls
  • Row-key encoding must canonicalize: same logical key → same bytes (normalize ±0.0, handle null marker, fixed field order).
  • Welford variance avoids catastrophic cancellation vs naive E[x^2]-E[x]^2.
  • Partition skew: one hot key lands all rows in one partition → no parallelism + OOM; detect + (later) repartition/spill.
  • Mean computed as sum/count must skip nulls in both.
  • High-cardinality group-by (≈ #rows) → huge table; spill or error, never OOM.

⬜ Phase 7 — Joins: Hash Join (Build/Probe) + All Join Types §19

Objectives

Hash equi-join with inner/left/right/outer/semi/anti/cross, correct null-key semantics (§8.13), type coercion on keys (I9), partitioned build/probe, spill on large build side. Sort-merge join as a fallback for pre-sorted / range inputs (built on Phase 4 sort).

Deliverable

left.join(right, on="k", how=inner/left/semi/anti) produces correct row sets and output schema (left ++ right, dup names suffixed); matches DuckDB on fixtures including null keys.

Acceptance
  • Each join type's cardinality + content matches DuckDB on fx/join/* (differential).
  • Null keys never match in equi-join; anti-join keeps left null-key rows. [§8.13]
  • Mismatched key types coerced (Int32 vs Int64 → Int64) or rejected (Int vs Utf8 → EngineError::TypeCoercion). [I9]
  • Build side > budget → spills (grace hash) and still returns correct result.
  • Output schema deterministic; row order unordered unless a sort follows.
Fixtures

fx/join/inner_basic.json, fx/join/left_outer.json, fx/join/semi_anti.json, fx/join/null_keys.json, fx/join/type_coercion.json, fx/join/skew_build.json, fx/join/cross.json. Malformed: incompatible key types (error).

Pitfalls
  • Building on the larger side wastes memory — always build on the smaller (estimate by row count/bytes).
  • Duplicate keys on the build side → one probe row matches many → output explosion; size estimate must account for it.
  • Null-key handling differs by join type — encode the rule explicitly, test each.
  • Coercion that loses precision (Int64→Int32) must be rejected, not silent.
  • Cross join is O(n·m) — guard against accidental cross (missing join key) with a plan-level warning.

⬜ Phase 8 — Expression Engine: Expr Trees, Evaluation, When/Then, Window §20

Objectives

Build the Expr tree (§8.7) and an evaluator that maps an expression to a column over a RecordBatch, including when/then/otherwise, scalar + aggregate functions, and window (agg.over(partition)). Constraint: expression evaluation is pure + null-aware; output length == batch length (for scalar exprs).

Deliverable

Evaluate when(col("x").gt(lit(0))).then(lit("pos")).otherwise(lit("neg")) → Utf8 column; sum(col("c")).over(col("region")) broadcasts region totals to each row.

Acceptance
  • Scalar expr output length == batch rows; null propagation correct through the tree.
  • when/then/otherwise precedence: first matching branch wins; unmatched → otherwise; null condition → otherwise (U is not T).
  • expr.data_type(schema) matches the evaluated array's dtype (coercion-aware).
  • Window aggregate broadcasts correctly and preserves row order.
  • Unknown function / arity mismatch → EngineError::NotFound/Schema at build, not at eval.
Fixtures

fx/expr/binary_nulls.json, fx/expr/when_then_chain.json, fx/expr/window_sum_over.json, fx/expr/dtype_infer.json. Malformed: unknown_function.json, arity_mismatch.json (both error).

Pitfalls
  • when condition that is null must route to otherwise (Kleene: U ≠ T) — not to then.
  • Literal broadcast must produce a full-length array (or a cheap constant array) matching batch length.
  • Window over without partition = whole-frame aggregate broadcast — easy to confuse with group-by (which reduces rows).
  • Aggregate expr used in a scalar context (no group-by) must be rejected or treated as whole-column reduce — define it.
  • Nested expressions re-evaluating a shared subtree → wasted work (CSE in Phase 10 fixes it).

⬜ Phase 9 — Lazy Logical Plan + Schema Resolution + LazyFrame API §21

Objectives

The lazy frontend: LazyFrame records operations as a LogicalPlan tree (§8.9), resolves + validates schema at build time, and defers execution to collect(). Constraint: plan output schema is resolved and stable (I10); nothing executes until collect.

Deliverable

scan_csv("t.csv").filter(col("a").gt(lit(10))).group_by("b").agg([sum("c")]) builds a valid LogicalPlan with a resolved output schema; .explain() prints the tree; .collect() returns the right answer (unoptimized).

Acceptance
  • LogicalPlan::schema() matches the eventual result schema for all node types (golden files).
  • Unresolved column / type mismatch errors at build time, not at collect. [I9,I10]
  • EXPLAIN output is stable + deterministic (golden test).
  • collect() (naive) result equals the eager-API equivalent on fixtures.
  • Join output schema dedups names deterministically (suffix _right).
Fixtures

fx/plan/schema_resolution.json, fx/plan/explain_golden.txt, fx/plan/unresolved_column.json (error), fx/plan/join_schema.json.

Pitfalls
  • Schema resolution must run during plan build, not at collect — early errors are the point of lazy.
  • Aggregate output schema: grouping keys first, then agg outputs, with stable naming.
  • A filter referencing a column produced later in the plan must error (scoping).
  • Self-join / union with duplicate names needs a deterministic disambiguation rule.
  • The naive collect must not bake in assumptions the real executor will violate (e.g. ordering).

⬜ Phase 10 — Optimizer: Pushdown, CSE, Constant Folding, Coercion §22

Objectives

Rule-based optimizer (§8.10): predicate/projection/slice pushdown, common-subexpression elimination, constant folding, type coercion, expression simplification — applied to fixed point, each rule schema-preserving. Constraint: optimization never changes query semantics (only cost); output schema unchanged (I10).

Deliverable

The §8.12 query: optimizer turns Scan(all) → Filter(a>10) → Aggregate into Scan(proj=[a,b,c], pred=a>10) → Aggregate; EXPLAIN before/after shows pushdown; result identical to unoptimized.

Acceptance
  • Optimized plan result == unoptimized result on every differential fixture (semantics preserved).
  • Predicate pushdown reaches Scan.predicate when the predicate references only scan columns.
  • Projection pushdown sets Scan.projection to exactly the needed columns (no over-read).
  • CSE hoists a repeated sub-expr exactly once (verified in EXPLAIN).
  • Coercion inserts casts so all binary ops / join keys are type-consistent. [I9]
  • Optimizer is idempotent: a second pass produces no further change (fixed point).
Fixtures

fx/opt/predicate_pushdown.txt (plan before/after), fx/opt/projection_pushdown.txt, fx/opt/cse.txt, fx/opt/const_fold.json, fx/opt/coercion.txt, fx/opt/idempotent.txt. Each pairs an input plan with the expected optimized plan (golden).

Pitfalls
  • Pushing a predicate through a Join to the wrong side (column not available) → wrong/empty result.
  • Pushing a predicate below an Aggregate is invalid if it references an aggregate output (only pre-aggregation columns are pushable).
  • CSE on a non-pure or non-deterministic expr (e.g. a random function) changes semantics — only hoist pure exprs.
  • Slice pushdown below a node that reorders (sort) or filters changes which rows survive — only push through order/count-preserving nodes.
  • Constant folding must respect overflow/null policy (folding must match runtime eval).

⬜ Phase 11 — Physical Plan + Vectorized Morsel-Driven Executor §23

Objectives

Lower the optimized LogicalPlan to a PhysicalPlan of ExecNodes and execute it morsel-driven over rayon with RecordBatch streaming (§3.1, Principle 6). Constraint: no global lock in the hot path; output schema == plan schema (I10, I14).

Deliverable

End-to-end LazyFrame...collect() runs through the real executor: scan→filter→hash-agg over 100M rows, parallel across cores, streaming RecordBatches, matching the naive collect result.

Acceptance
  • Optimized physical-plan result == naive logical result == DuckDB (differential) on TPC-H subset queries.
  • Executor scales near-linearly to N cores on a scan+filter+agg (benchmark; report speedup curve).
  • Output schema equals the plan schema for every batch in the stream. [I10,I14]
  • Memory stays under budget (accounting + spill engaged on a large group-by/join).
  • Query cancellation stops work promptly (cancellation token honored between morsels).
Fixtures

fx/exec/tpch_q1.json,q3.json,q6.json (subset), fx/exec/scaling.json (rows/sec vs cores), fx/exec/cancel.json, fx/exec/schema_stability.json (per-batch schema constant).

Pitfalls
  • A single shared output queue or global mutex serializes everything — partition state, use per-worker queues.
  • Morsel too large → poor load balance + cache pressure; too small → dispatch overhead. Tune to L2/L3.
  • Pipeline-breaker (agg/sort/join-build) must fully consume input before emitting — mixing pull/push incorrectly deadlocks.
  • Reusing buffers across morsels without clear ownership → data race; keep batches immutable + Arc.
  • Forgetting backpressure → unbounded memory when producer outruns consumer.

⬜ Phase 12 — I/O: CSV + Arrow IPC + Parquet (Encodings, Row Groups, Statistics) §24

Objectives

Read/write the three core formats, with Parquet predicate pushdown via statistics and the encoding suite. Constraint: untrusted-file safety (Threat Model); Arrow round-trip bit-exact (I16); Parquet reader skips row groups via stats (§4).

Deliverable

Round-trip an array through IPC bit-exact; write a Parquet file (dictionary + RLE encoded) and read it back equal; a predicate ts >= X skips non-matching row groups (verify pages-read count); read a pyarrow-written Parquet file.

Acceptance
  • Arrow IPC round-trip (array → IPC → array) is byte-identical for every array kind, including nested + dictionary. [I16]
  • Parquet written by cx reads in pyarrow/parquet-tools and vice-versa (interop fixtures).
  • Predicate pushdown skips ≥ 50% of row groups on a selective fixture; never skips on missing/!present stats.
  • CSV schema inference matches expected dtypes; quoting/escaping/newlines-in-quotes handled.
  • All encodings decode to the same values they were encoded from (per-encoding fixtures).
Fixtures

conformance/arrow-roundtrip/* (all kinds), conformance/parquet/written_by_pyarrow.parquet, conformance/parquet/encodings/{plain,rle,delta,dict}.parquet, fx/io/csv_quoting.csv, fx/parquet/stats_skip.parquet. Malformed: truncated_footer.parquet, bad_magic.parquet, dict_index_oob.parquet, decompress_bomb.parquet, non_utf8.csv (all must error safely).

Pitfalls
  • Parquet def/rep levels for nested/nullable are the #1 source of bugs — a wrong level desyncs the whole column.
  • Dictionary fallback: a column chunk can switch from dictionary to plain mid-chunk when the dictionary grows too large — handle both pages.
  • IPC buffer alignment: messages must be 8/64-byte aligned per spec; mis-padding breaks zero-copy.
  • CSV: newlines inside quoted fields, BOM, ragged rows, and locale decimals are all edge cases.
  • Trusting num_values/sizes from a malformed footer → OOB/over-allocation (Threat Model) — bound + validate every length.

⬜ Phase 13 — Memory Accounting + Spill + C Data Interface + Conformance + Fuzzing §25

Objectives

Production hardening: enforce the memory budget with spill-to-disk for agg/sort/join, expose the Arrow C Data Interface (FFI), and stand up the conformance + fuzzing gates. Constraint: degrade not OOM (Principle 8); FFI zero-copy + ABI-correct (release callback semantics). GPU + compiled-JIT remain deferred.

Deliverable

A group-by/join larger than the budget completes by spilling (not OOM); an array exported via the C Data Interface is read by pyarrow zero-copy and freed correctly; conformance report shows Pass on round-trip + differential buckets; fuzzers run clean on the seed corpus.

Acceptance
  • A --mem-budget smaller than the working set still completes agg/sort/join correctly via spill (result == in-memory result).
  • Memory accounting tracks actual within 5% (reconcile test). [I11]
  • C Data Interface export/import round-trips with pyarrow bit-exact; release called exactly once (no leak, no double-free; verified under valgrind/asan).
  • Differential vs DuckDB + Polars green on the TPC-H subset + ClickBench subset.
  • Fuzz targets survive 1M+ iterations on seed corpus with no panic/OOB/UB (miri/asan where applicable).
Fixtures

conformance/differential/tpch_subset/*, conformance/differential/clickbench_subset/*, conformance/ffi/pyarrow_roundtrip/*, fx/spill/large_groupby.json, fx/spill/external_sort.json. Malformed: foreign ArrowArray with null release (handle gracefully), spill dir unwritable (clear error).

Pitfalls
  • Spill correctness: the spilled-then-merged result must equal the in-memory result — partition boundaries + merge order matter.
  • FFI release double-free or leak: the callback must own exactly the Arcs it dropped; importer calls release once.
  • Accounting drift: forgetting to account a hot-path allocation → spill never triggers → OOM (I11).
  • Spill thrashing: too-low budget → constant spill → I/O-bound; expose budget + warn.
  • ABI: #[repr(C)] field order/layout must match the Arrow spec exactly; an off-by-one buffer pointer corrupts the import.
