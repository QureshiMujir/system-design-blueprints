Decisions (§9) · 31 ADRs

01

Language

Chosen

Rust (ed. 2021, MSRV 1.78)

Rejected

C++, Go, Java, Python

When the rejected choice is right

C++ is correct when you control the full build toolchain, have a mature ASAN/MSAN pipeline, and the codebase already has the memory discipline needed for manual lifetime tracking — e.g., an existing vectorized engine rewritten for performance

Why: manual layout + zero-cost generics + safe parallelism + the actual ecosystem (§1.10)

02

Project structure

Chosen

Cargo workspace, 15 cx-* crates

Rejected

one mega-crate

When the rejected choice is right

A monolithic crate is right when the workspace topology would add more friction than clarity and you want the simplest possible CI — typical for a proof-of-concept or solo short-lived project with no crate-boundary reuse

Why: compile-time isolation; faster incremental builds; clear layering

03

Buffer allocator

Chosen

custom 64-byte-aligned allocator over std::alloc

Rejected

Vec<u8> (8/16-byte align), bytes crate

When the rejected choice is right

A standard Vec<u8> allocator is sufficient when the target platform has no SIMD wider than 16 bytes, when all accesses are byte-sequential with no aligned load/store intrinsics, or when the Arrow spec alignment requirement is explicitly waived by the use case

Why: Arrow requires 64 B; SIMD aligned load; padded length

04

Buffer sharing

Chosen

Arc<Bytes> immutable + zero-copy slice (offset,len)

Rejected

Rc (not Send), raw ptr, Cow

When the rejected choice is right

Rc (not Send) is the right choice for single-threaded arena designs where the sharing graph is known at compile time and the allocation pattern is purely sequential — never concurrently accessed after construction

Why: thread-safe zero-copy; FFI-friendly; refcount = lifetime

05

Null representation

Chosen

Arrow validity bitmap (1 bit/slot)

Rejected

sentinel value (e.g. i64::MIN), separate null column, Option<T> per cell

When the rejected choice is right

A sentinel value (e.g., a reserved NaN for float or i64::MIN for integers) is the right model when null density is extremely low, no SIMD bitmask ops are needed, and the domain guarantees the sentinel cannot appear as a real value — common in embedded or fixed-schema time-series databases

Why: sentinel collides with data + breaks SIMD; bitmap is dense + Arrow-compatible

06

Execution model

Chosen

vectorized / morsel-driven (batch-at-a-time)

Rejected

Volcano tuple-at-a-time; compiled/JIT codegen

When the rejected choice is right

Volcano tuple-at-a-time is the right model for low-latency OLTP point lookups where result sets are tiny and the interpreter overhead per row is negligible relative to the lock/latch cost; compiled/JIT codegen is right for compute-intensive analytics with stable, repeated query shapes where amortized JIT compilation yields >2x throughput gains over vectorized interpretation

Why: vectorized = best perf/complexity ratio; tuple-at-a-time too slow; JIT deferred (see Deferred Features Register)

07

Parallelism

Chosen

rayon work-stealing

Rejected

manual threads + channels, tokio (async), OpenMP-style

When the rejected choice is right

Manual threads plus bounded channels are the right primitive when work granularity is coarse and ordered, the thread count is small and fixed, and the rayon work-stealing overhead per fine-grained morsel would dominate — e.g., a pipeline where each stage is already one long sequential pass

Why: data-parallel morsels map to rayon; work-stealing balances skew

08

String layout

Chosen

Arrow varbinary (offsets + data)

Rejected

German/Umbra inline-prefix string, std String per cell

When the rejected choice is right

German/Umbra inline-prefix strings are the right layout when the dominant operation is point-lookup or sort on short strings (<=12 bytes), cache pressure from pointer-chasing the offset buffer is the measured bottleneck, and Arrow IPC interop is not required

Why: Arrow-compatible; inline-string (Umbra) is a deferred optimization (§9 note)

09

Dictionary policy

Chosen

adaptive: encode when distinct/total < 0.5 ∧ card ≤ 2^20

Rejected

always-dict, never-dict

When the rejected choice is right

Always-dictionary encoding is right when cardinality is provably bounded at schema design time (e.g., a categorical column with a finite, pre-known domain) and random decode cost is negligible because the column is accessed only via the dictionary indices

Why: dict helps only low cardinality; threshold avoids index-buffer waste

10

Query plan IR

Chosen

two-level: LogicalPlan + PhysicalPlan

Rejected

single plan, expression-only

When the rejected choice is right

A single-level expression-only plan (no Logical/Physical split) is right when the optimizer is absent or trivial and the execution model is simple enough that lowering adds no algorithmic benefit — typical for small embedded engines or scripting DSLs

Why: separation lets optimizer rewrite logically, executor pick physical algorithms

11

Optimizer

Chosen

rule-based (fixed-point rewrite) + Parquet stats

Rejected

cost-based (cardinality est.), no optimizer

When the rejected choice is right

A cost-based optimizer with cardinality estimation is right when query shapes are complex and data statistics are collected — in particular for join ordering over more than three tables, where rule-based ordering is provably suboptimal under skew and the cost of wrong-order exponentially exceeds estimation error

Why: CBO needs stats infra (deferred); rules give 80% of the win

12

Expression eval

Chosen

lazy primary (LazyFrame) + eager DataFrame

Rejected

eager-only, lazy-only

When the rejected choice is right

An eager-only model is right when every result set is small enough to fit comfortably in memory, the REPL interaction loop dominates usage, and lazy deferral would add API complexity with no measurable benefit — typical for exploratory notebook workflows

Why: lazy enables pushdown/CSE; eager for REPL ergonomics

13

Hashing

Chosen

ahash (also wyhash option)

Rejected

SipHash (std default), FxHash, CRC

When the rejected choice is right

SipHash is the right choice when DoS resistance is a hard requirement and the hash rate is not the bottleneck — e.g., a web-facing service that must resist hash-flooding attacks at the cost of some throughput

Why: ahash is fast + DoS-resistant-ish; joins/group-by are hash-bound

14

Sort

Chosen

multi-key stable; radix for ints, pattern-defeating quicksort/merge for others

Rejected

single-key, unstable-only

When the rejected choice is right

An unstable sort is the right choice when sort key uniqueness is guaranteed by schema (no ties possible) or when downstream consumers do not require a reproducible tie-breaking order and the extra comparisons for stability are measured to cost more than the use case permits

Why: stability + determinism (I12); radix for integer keys

15

SIMD

Chosen

std::simd behind simd feature; scalar fallback

Rejected

hand-written intrinsics, autovec-only

When the rejected choice is right

Hand-written intrinsics are the right choice when the target ISA is fixed, the performance gap versus portable_simd is measured and significant (>10%), and the maintenance burden of per-arch specialization is amortized over a large, stable codebase — e.g., a production DBMS with dedicated compiler engineers

Why: portable, safe-ish, falls back; intrinsics per-arch is a maintenance tax

16

CSV parsing

Chosen

custom SIMD-assisted state machine

Rejected

csv crate (row-oriented), regex

When the rejected choice is right

A row-oriented CSV crate is right when the output is a Vec of deserialized structs and schema inference is not needed — typical for configuration file parsing or small-table ETL where column throughput does not matter

Why: need columnar output + schema infer + speed; row-oriented crate is slow

17

Parquet

Chosen

own reader/writer; encodings PLAIN/RLE/bit-pack/DELTA/dictionary

Rejected

parquet crate (would defeat "from scratch"), ORC

When the rejected choice is right

The parquet crate is right when the goal is purely to consume or produce Parquet files with minimal custom logic — e.g., an application-level ETL tool that does not need custom encoding control, statistics writing, or pushdown integration

Why: learning goal; encodings + stats are core curriculum

18

Parquet compression

Chosen

via #397 codec (zstd/snappy/gzip) behind a trait

Rejected

bundle a codec, none

When the rejected choice is right

Bundling a codec directly is right when the deployment environment cannot guarantee the presence of a separately compiled codec library, when a minimal binary size is critical, or when the codec ABI must be tightly controlled to avoid version skew

Why: reuse the compression project; pluggable codec

19

Arrow IPC

Chosen

Flatbuffers schema + record-batch messages

Rejected

protobuf, custom framing

When the rejected choice is right

Protobuf framing is right when the Arrow format version is irrelevant and the primary concern is ecosystem compatibility with gRPC-based services that expect length-delimited protobuf messages rather than Flatbuffers

Why: IPC spec mandates Flatbuffers; interop with arrow-rs/pyarrow

20

C Data Interface

Chosen

#[repr(C)] ArrowSchema/ArrowArray + release callback

Rejected

only IPC, custom FFI

When the rejected choice is right

An IPC-only FFI (no C Data Interface) is right when the caller already has a deserialize step in its pipeline, zero-copy is not a requirement, and the overhead of an additional serialize/copy is negligible relative to the subsequent compute cost

Why: zero-copy cross-language; the Arrow ABI standard

21

Memory accounting

Chosen

per-query MemoryPool + Reservation

Rejected

global allocator hook only, none

When the rejected choice is right

A global allocator hook is right for coarse-grained process-level accounting where per-query isolation is not needed and the instrumentation overhead of RAII reservation per operator exceeds the benefit — e.g., a single-tenant CLI tool with no concurrent query budget

Why: track budget; trigger spill; bound RSS

22

Spill

Chosen

partition spill to local disk (agg/sort/join)

Rejected

fail on OOM, mmap-only

When the rejected choice is right

Failing on OOM (no spill) is right when a correctness guarantee is more important than availability, the working set is always bounded by schema contract, and local disk I/O latency would make spill performance unacceptable for the SLA — e.g., a streaming sensor-data aggregator with guaranteed small state

Why: degrade not OOM (Principle 8); deterministic temp dir

23

Error model

Chosen

typed EngineError enum + thiserror

Rejected

string errors, panic

When the rejected choice is right

String-based errors (anyhow/Box<dyn Error>) are right when the error taxonomy is simple, the caller does not need to pattern-match on error variants, and the extra complexity of a typed enum outweighs the exhaustive-match benefit — typical for CLI tools or one-off scripts

Why: exhaustive match; precise IO/Parquet/Overflow/Schema variants

24

Logging / tracing

Chosen

tracing spans per operator

Rejected

log crate, custom

When the rejected choice is right

The log crate is right when structured per-span context is not needed, the operator boundaries are coarse, and the simpler log-level API is sufficient — typical for embedded systems or very simple single-threaded pipelines

Why: structured per-operator spans feed EXPLAIN ANALYZE

25

Metrics

Chosen

per-operator counters (rows, bytes, spill, time)

Rejected

none, external only

When the rejected choice is right

No per-operator metrics are right when the deployment is offline batch processing, there is no SRE team, and the observability requirement is met entirely by criterion benchmarks and flamegraphs rather than production counters

Why: operational readiness; regression detection

26

Testing

Chosen

unit + arrow round-trip + differential vs Polars/DuckDB + property + sqllogictest-style

Rejected

unit-only

When the rejected choice is right

Unit-only testing is right when the codebase is small enough that exhaustive hand-crafted cases cover all states, differential oracles do not exist or are too slow to run in CI, and the risk of null/edge regressions is acceptable — typical for very early prototypes

Why: bit-exact + behavioral parity catch null/edge bugs

27

Fuzzing

Chosen

cargo-fuzz on CSV/Parquet/IPC readers

Rejected

none

When the rejected choice is right

No fuzzing is right only when the engine exclusively processes trusted, schema-validated data from a controlled internal source and the cost of fuzzing infrastructure outweighs the marginal risk reduction

Why: untrusted files are the attack surface (Threat Model)

Benchmarking

Chosen

criterion micro + TPC-H subset + ClickBench + db-benchmark macro

Rejected

ad-hoc timing

When the rejected choice is right

Ad-hoc timing (time crate, manual wall-clock) is right for a one-shot investigation where criterion's statistical rigor is unnecessary and benchmark regression across commits is not tracked

Why: reproducible; regression gates; standard workloads

29

Python binding

Chosen

pyo3 thin stub (eager + collect)

Rejected

cffi, no binding

When the rejected choice is right

A cffi binding is right when the Python caller needs a C ABI (not Rust ABI) for compatibility with CPython extension restrictions or when the pyo3 compile-time dependency on a Rust compiler in the Python build environment is unacceptable

Why: parity with Polars/pyarrow users; stub now, full later

Licensing

GPL licensing is right when the goal is copyleft to ensure derivative works remain open — e.g., a library whose primary value is network-effect openness rather than ecosystem embedding

Reproducibility

Chosen

pinned Cargo.lock, rust-toolchain.toml, vendored fixtures, SBOM

Rejected

floating deps

When the rejected choice is right

Floating (unpinned) dependencies are right only in a leaf application (not a library) with a short lifetime, where the author is willing to accept unexpected breakage from upstream changes in exchange for always getting the latest security patches without manual Cargo.lock maintenance

Why: byte-stable builds; auditability

Roads not taken

Row-Oriented Eager with Object Dtype

 Source
   |
   v
[row 0: {a: PyObj, b: PyObj, c: PyObj}]
[row 1: {a: PyObj, b: PyObj, c: PyObj}]
   ...
BlockManager (per-dtype block consolidation)
   |
   v
 Operation → new consolidated block

Wins when: data is small (< 1 M rows), schema is highly heterogeneous (mixed types per cell), and the primary operation is single-row mutation or lookup rather than columnar scan. Also wins when Python ergonomics and ecosystem integration dominate performance requirements.

Embodied by: pandas (BlockManager + object dtype).

Why rejected here: per-row Python object overhead defeats SIMD vectorization; GC pauses mid-scan are incompatible with the 5 GB/s/core target (§4); object dtype stores Python heap pointers, not contiguous typed values, making SIMD impossible and cache utilization poor.

Compiled / JIT Data-Centric Codegen

 LogicalPlan
      |
      v
  Code generator (LLVM IR / C++)
      |  (compile per query)
      v
 Specialized binary: fused scan+filter+agg
  — no operator boundaries —
      |
      v
 Result

Wins when: the same query shape is executed many times (OLAP dashboards, repeated ETL), the JIT amortization cost is acceptable, and operator fusion eliminates the batch-handoff overhead that vectorized interpretation pays at every operator boundary. Also wins when the query is compute-bound with a simple access pattern (no joins, pure aggregation).

Embodied by: HyPer / Umbra (Neumann VLDB 2011), DuckDB adaptive compilation.

Why rejected here: JIT compilation adds LLVM/codegen infrastructure complexity and latency that is unacceptable for a library embedding in a host process with < 50 ms cold-start requirement (§4). The vectorized interpreter (ADR-06) achieves >80% of JIT throughput with much lower implementation cost; JIT is explicitly tracked in the Deferred Features Register.

Pull-Based Volcano Tuple-at-a-Time

 sort.next()
   └─ hash_join.next()
        └─ filter.next()
             └─ scan.next()  → one tuple

Wins when: result sets are tiny (OLTP point lookups), the query is highly selective (< 100 rows survive), and the dispatch overhead per next() call is negligible relative to the I/O cost of the index lookup that dominates. Also wins for simple, deeply pipelined streaming queries where back-pressure per-tuple is required.

Embodied by: PostgreSQL executor (Graefe TKDE 1994), original Volcano/Cascades.

Why rejected here: one virtual dispatch per row per operator is the exact overhead that columnar batch execution eliminates. At 1 B rows, a naïve Volcano design pays ~1 B virtual calls per operator level. The §4 throughput targets (≥ 5 GB/s/core, ≥ 50 M rows/s group-by) are physically impossible under per-row dispatch without JIT compilation. Morsel-driven vectorized execution (ADR-06, Leis et al. SIGMOD 2014) amortizes dispatch over 64Ki-row batches.

Push-Based Morsel Pipeline (Velox / HyPer style)

 ScanExec --push--> FilterExec --push--> HashAggExec
                                              |
                                         finalize()

Wins when: the operator graph is known at plan time, back-pressure is managed per-pipeline-breaker rather than per-batch channel, and the push model reduces the buffering overhead between operators that pull-based streaming channels require. Also wins when constant-vector encoding (a null column, a broadcast literal) can propagate lazily through the push path without materializing.

Embodied by: Velox (Meta), HyPer Umbra push-based execution model.

Why rejected here: a pull-based RecordBatchStream (ADR-06) integrates more naturally with Rust's iterator model and the rayon work-stealing executor, which is pull-at-morsel-granularity. The push model requires explicit operator state machines and pipeline break synchronization that increase implementation complexity for the same throughput; the Velox encoding hierarchy (flat/constant/dictionary lazy propagation) is deferred as a future optimization.
