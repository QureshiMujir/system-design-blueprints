395 — Dataframe / In-Memory Columnar Engine (Arrow/Polars-like) from Scratch

Project Number: 395 Project Name: Dataframe / In-Memory Columnar Engine (Arrow/Polars-like) from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build, from scratch in Rust, a single-node multicore in-memory columnar engine (Arrow-style memory format + vectorized compute kernels) and, layered on it, a dataframe + lazy query engine (Polars/DataFusion-like): typed columnar arrays with validity bitmaps, null-aware SIMD kernels, a DataFrame/Series API, an expression engine, a logical→optimized→physical query plan, a morsel-driven parallel executor, and CSV/Parquet/Arrow-IPC I/O. Shipped as an embeddable library, a cxq CLI/REPL, and a Python binding stub.

1.1 What is built (precise definition)

Two stacked subsystems. The columnar core (Arrow-compatible memory + kernels) and the query layer (dataframe API + lazy planner + executor). Concretely, fifteen cx-* crates implementing:

# Subsystem Crate(s) Function
1 Aligned buffer + validity bitmap + refcounted bytes cx-buffer 64-byte-aligned immutable Buffer, Bitmap, Bytes refcount, zero-copy slice
2 Type system + schema + coercion cx-datatype DataType, Field, Schema, type promotion lattice
3 Typed arrays over Arrow layout cx-array PrimitiveArray<T>, BooleanArray, Utf8Array, ListArray, StructArray, DictionaryArray, NullArray
4 Compute kernels (vectorized, null-aware) cx-compute arithmetic, compare, boolean (Kleene), cast, aggregate, filter, take, sort, hash, unique, string ops
5 Series / ChunkedArray / DataFrame eager API cx-frame named chunked columns, select/filter/with_columns/concat/head
6 Expression engine cx-expr Expr trees, when/then/otherwise, window, scalar+agg functions
7 Logical + physical plan IR cx-plan LogicalPlan, PhysicalPlan/ExecNode, schema resolution, plan printing
8 Optimizer cx-optimize predicate/projection/slice pushdown, CSE, constant folding, type coercion
9 Vectorized executor cx-exec morsel-driven, rayon work-stealing, scan/filter/project/hash-agg/hash-join/sort streaming
10 I/O cx-io CSV reader/writer (schema infer), Parquet reader/writer (encodings + stats), Arrow IPC, JSON
11 Memory pool + accounting + spill cx-memory per-query budget, reservation, spill-to-disk for agg/sort/join
12 Arrow C Data Interface (FFI) cx-ffi zero-copy import/export across the ABI boundary
13 Python binding stub cx-py pyo3 thin wrapper; eager + collect() lazy entry points
14 CLI / REPL cx-cli the cxq binary; query, explain, cat, convert, bench
15 Common cx-common ids, EngineError, telemetry hooks, byte/slice utils

The vectorization unit is the RecordBatch (default 65 536 rows = 64Ki) decomposed into morsels for the executor. Predicates produce a BooleanArray mask; operators carry it via filter/take (late materialization). Aggregation is partitioned hash aggregation; joins are hash joins with a sort-merge fallback.

1.2 System boundaries (in scope)

  • Programmatic Rust API: eager DataFrame::{select, filter, group_by, join, sort}; lazy LazyFrame::{...}.collect(); expression DSL col("a").gt(lit(10)).
  • The cxq binary: read CSV/Parquet/IPC, run an expression/plan, EXPLAIN/EXPLAIN ANALYZE, write back any format, micro-benchmark.
  • Single process, single node, local disk; in-memory columnar buffers; multicore via rayon.
  • Arrow-format interop: import/export via IPC and the C Data Interface, bit-exact.

1.4 Deployment model

Embeddable library (the cx-* workspace crates) linked into a host process, the cxq CLI/REPL for offline query + format conversion + benchmarking, and a cx-py Python wheel stub exposing eager + lazy entry points. No daemon, no network listener, no IPC server.

1.5 Target users

Data-engine / analytics engineers building or studying: columnar memory formats, vectorized execution, query optimization, hash aggregation/join internals, Parquet/Arrow on-the-wire formats. The reader operates at byte-layout, bitmap, and query-plan granularity.

1.6 Phase-0 deliverable — the fifteen cx-* crates

A Cargo workspace (Rust edition 2021, MSRV 1.78) with the fifteen members in §1.1, plus a smoke test that builds an Int32Array with nulls, slices it zero-copy, runs sum, and round-trips it through Arrow IPC bit-exact; plus CI (fmt, clippy, test, miri on cx-buffer).

1.11 Prerequisites (required knowledge)

Relational algebra (σ π ⋈ γ τ); query optimization (logical rewrites, pushdown); vectorized / morsel-driven execution (batch-at-a-time, selection vectors, late materialization); SIMD (lane width, masks, gather/scatter); cache-aware data structures (line size, prefetch, blocking); memory layout + alignment (64 B, false sharing, NUMA); hashing (ahash, hash tables, probe); sorting (radix, merge, multi-key stable); IEEE-754 (NaN, ±0, total order); Arrow columnar format (validity bitmap, offsets, dictionary); Parquet format (row groups, pages, encodings, statistics, Dremel rep/def levels).

2. Why Build This

Most engineers have used a dataframe; few have built the memory format, the null-aware kernels, and the optimizer/executor that make analytics fast. This project forces all three: a cache-and-SIMD memory layout, a vectorized execution model, and a query optimizer — the trinity behind every modern OLAP engine.

2.1 Unique systems knowledge this teaches

2.2 Why columnar engines matter — historical + architectural arc

  • C-Store / Vertica (2005). Read-optimized column store; projections, compression, late materialization. Showed analytics belongs in columns. Stonebraker et al., VLDB 2005.
  • MonetDB / X100 (2005). "Hyper-pipelining" — operate on vectors of ~1024 values to amortize interpretation overhead and fit in CPU cache. The direct ancestor of every vectorized engine (ColumnBatch/RecordBatch here). Boncz/Zukowski/Kersten, CIDR 2005.
  • Column-Stores vs Row-Stores (2008). Quantified why columns win for OLAP (I/O, compression, vectorization, late materialization). Abadi et al., SIGMOD 2008.
  • Apache Arrow (2016). Standardized the in-memory columnar layout + IPC + C Data Interface so engines share buffers zero-copy. This project is Arrow-compatible by construction.
  • Morsel-Driven Parallelism (2014). Work-stealing over small "morsels" with NUMA-local scheduling — the execution model in cx-exec. Leis et al., SIGMOD 2014.
  • Polars / DataFusion / DuckDB (2019–). Modern Rust/C++ engines: lazy expression API + rule optimizer + vectorized executor + Parquet/Arrow I/O. This project is the single-node kernel those systems wrap.

Architecturally: columnar + vectorized + pushdown exists because analytics touches few columns of many rows and the row-at-a-time interpreter wastes the CPU on dispatch and cache misses. The cost is a more complex memory format and null bookkeeping — exactly the complexity this blueprint makes you own.

2.3 Engineering muscles built

  • Data-oriented design: structure data for the access pattern; struct-of-arrays over array-of-structs; pack bitmaps; align to cache lines.
  • SIMD + branchless code: null-aware kernels without per-element branches; lane masks; gather/scatter for take.
  • Parallelism: rayon work-stealing, partitioned hashing, NUMA awareness, no global locks in the hot path.
  • Compiler/IR thinking: Expr trees, logical/physical plans, optimizer rewrites — a query is a program you optimize and execute.
  • Format engineering: Arrow IPC (Flatbuffers), Parquet (Thrift metadata, encodings, statistics), byte-exact round trips.
  • Performance engineering: criterion micro-benchmarks, ClickBench/TPC-H subsets, flamegraphs, tail latency under skew.

2.5 Calibration value

A working columnar engine is a principal-level capstone: it composes a cache/SIMD memory format, a null-correct kernel library, a query optimizer, and a parallel executor, then proves correctness against Arrow round-trips and differential tests versus DuckDB/Polars. Completing it demonstrates you can reason about an OLAP data path end-to-end — the bar for owning a query engine or analytics runtime.

What Mastery Looks Like — finishing this blueprint means you can:

  • Lay out a 64-byte-aligned validity-bitmap columnar buffer from first principles, explain why each layout decision exists, and diagnose alignment or null-count corruption at the byte level (Phase 0, Phase 1)
  • Write a null-aware vectorized kernel (arithmetic, Kleene boolean, filter/take) that passes both SIMD and scalar differential tests and handles every null-density edge case correctly (Phase 3, Phase 4)
  • Build and debug a partitioned hash aggregation and a grace hash join that scale near-linearly across cores, spill correctly under a tight memory budget, and produce results identical to DuckDB (Phase 6, Phase 7)
  • Author and apply optimizer rules (predicate/projection/slice pushdown, CSE, constant folding) that are provably semantics-preserving, idempotent, and verifiable by plan-golden diff (Phase 10)
  • Lower a LogicalPlan to a morsel-driven physical executor, eliminate all global locks from the hot path, and read EXPLAIN ANALYZE output to locate skew, stall, and spill root causes (Phase 11)
  • Implement a Parquet column-chunk reader with RLE/bit-pack/delta/dictionary decoding, row-group skip via statistics, and def/rep level handling — and prove round-trip parity with pyarrow (Phase 12)
  • Export and import arrays via the Arrow C Data Interface with a correct release callback, account every allocation within 5% tolerance, and harden all format readers against adversarial input via cargo-fuzz (Phase 13)

3.2 Box-by-box responsibilities

  • Reader (cx-io). Decodes a source into Arrow RecordBatches. CSV: sample-based schema inference, typed parse, quoting/escaping. Parquet: read Thrift footer, select row groups via statistics, decode pages (RLE/bit-pack/delta/dictionary), reassemble columns with validity. IPC: parse Flatbuffers schema + record-batch messages, wrap buffers zero-copy. Null semantics: producer sets validity bit per slot; reader never fabricates values for null slots. Parallelism boundary: one row group / file split per rayon task.
  • Columnar core (cx-buffer + cx-array). Owns the canonical Arrow memory layout: 64-byte-aligned, immutable, Arc-shared Buffers; ArrayData{dtype,len,null_count,buffers,child_data}. Every array kind (primitive, boolean, utf8/binary, list, struct, dictionary, null) is a typed view over ArrayData. Slicing adjusts (offset,len) without copying. Mutation never happens in place — builders produce new arrays. This is the trust + zero-copy boundary: buffers crossing FFI are the same bytes.
  • Eager path (cx-frame + cx-compute). Series = named ChunkedArray; DataFrame = Vec<Series> + Schema. Operations call kernels directly and materialize immediately. Used for interactive/REPL work and as the building block under the lazy executor. Null semantics propagate per kernel; concurrency: arrays are Send+Sync, kernels are pure functions of their inputs.
  • Lazy path — Expr/Logical (cx-expr + cx-plan). A LazyFrame records intent as Expr trees over LogicalPlan nodes (Scan/Projection/Filter/Aggregate/Join/Sort/Limit/Distinct/Union). Nothing executes until collect(). Schema is resolved + validated at build time; type coercion is explicit. This is the semantics boundary: the plan is the source of truth for what the query means.
  • Optimizer (cx-optimize). Rule-based rewrites on the LogicalPlan: predicate pushdown (filters toward scans), projection pushdown (read fewer columns), slice/limit pushdown, common-subexpression elimination, constant folding, type coercion insertion. Each rule is LogicalPlan → LogicalPlan, schema-preserving, idempotent where possible. Output is an optimized logical plan.
  • Physical plan + executor (cx-plan + cx-exec). The optimized logical plan lowers to PhysicalPlan (ExecNode trait, execute() -> RecordBatchStream): ScanExec, FilterExec, ProjectExec, HashAggExec, HashJoinExec, SortExec, SortMergeJoinExec, LimitExec. Execution is morsel-driven: the source is partitioned into morsels, rayon work-steals across cores, operators are batch-at-a-time, and results flow as a RecordBatch stream. This is the parallelism boundary — no global lock in the hot path; only the shared hash table for build, partitioned to avoid contention.
  • Sink (cx-io + cx-frame). Streams RecordBatches into a collected DataFrame or writes Parquet/CSV/IPC. Deterministic ordering is enforced only where requested (sort, or maintain_order).
  • Side services. MemoryPool (cx-memory) accounts every allocation against a per-query budget and triggers spill when reservations exceed the threshold. Schema/type system (cx-datatype) is consulted at every plan/kernel boundary. Dictionary encoder shares low-cardinality string data. cx-ffi exports/imports buffers across the Arrow C Data Interface ABI.

6. Design Principles

Twelve non-negotiable principles (P1–P12). Each is referenced by phase sections. Violations are correctness or performance regressions, not style preferences.

  1. P1 — Columnar + vectorized over row-at-a-time. Operate on contiguous arrays of one type, one kernel call per batch. Tradeoff: batch buffers cost memory; pipelining is coarser. Operational: SIMD + cache locality give the throughput in §4. Violation: per-row trait dispatch (dyn per element) collapses scan throughput 10–50×; the engine becomes a slow interpreter.

  2. P2 — Validity bitmap + three-valued (Kleene) logic everywhere. A null slot is unknown, not a value. Every kernel consumes and produces a validity bitmap; boolean ops use Kleene tables. Tradeoff: bitmap maintenance per kernel. Operational: COUNT(col) ≠ COUNT(*); sum skips nulls. Violation: reading a null slot's bytes as data, or null = null → true, silently corrupts every downstream result.

  3. P3 — Zero-copy, immutable buffers. Buffers are Arc-shared and never mutated; slicing adjusts (offset,len); "mutation" builds a new array. Tradeoff: copy-on-write allocations. Operational: arrays are freely Send+Sync; FFI export is a pointer hand-off. Violation: in-place mutation of a shared buffer is a data race and a correctness bug across views.

  4. P4 — Late materialization. Carry a selection (mask/indices) and decode/gather columns last, only for surviving rows. Tradeoff: indirection on access. Operational: a 1%-selective filter touches ~1% of the output columns' bytes. Violation: early materialization makes a selective query pay full decode cost on discarded rows.

  5. P5 — Push work down to the scan. Predicates and projections move toward the source so fewer bytes are read/decoded; Parquet stats skip row groups. Tradeoff: optimizer complexity; pushdown must be semantics-preserving. Operational: the cheapest row is the one never read. Violation: reading all columns then projecting wastes I/O and memory bandwidth.

  6. P6 — Morsel-driven parallelism, no global sync in the hot path. Work is split into morsels; rayon work-steals; shared state (hash tables) is partitioned. Tradeoff: scheduling overhead; NUMA awareness needed. Operational: near-linear scaling until a shared structure becomes the bottleneck. Violation: a global mutex or single output queue serializes the engine and kills scaling.

  7. P7 — Type safety + explicit coercion. No silent lossy casts; coercion is an explicit optimizer pass following a documented promotion lattice. Tradeoff: the user must opt into narrowing casts. Operational: Int32 + Float64 → Float64 is explicit and predictable. Violation: implicit Float64→Int32 truncation produces wrong numbers no one asked for.

  8. P8 — Bounded memory + spill. Every allocation is accounted against a per-query budget; agg/sort/join spill to disk above threshold. Tradeoff: spill is slow; accounting has overhead. Operational: a big group-by degrades to disk instead of OOM-killing the process. Violation: unaccounted allocation → OOM under skew, taking down the host.

  9. P9 — Deterministic results when requested. Parallel execution may reorder rows; sort and maintain_order impose a stable, reproducible order. Tradeoff: maintaining order costs a sort/merge. Operational: EXPLAIN ANALYZE and golden-file tests need reproducibility. Violation: non-deterministic ordering breaks differential tests and confuses users comparing runs.

  10. P10 — Schema is law; kernels are null-aware + branchless. Schemas are validated at every plan/IO boundary; kernels avoid per-element branches (use masks/select). Tradeoff: validation cost at boundaries; branchless code is harder to write. Operational: a malformed file is rejected at the edge, not mid-execution; kernels vectorize. Violation: trusting an unvalidated schema or branchy null handling causes mid-query panics and pipeline stalls.

  11. P11 — Observability is an operator-level concern, not an afterthought. Every operator emits per-span counters (rows, bytes, spill, time) that feed EXPLAIN ANALYZE. Tradeoff: counter plumbing through the executor. Operational: skew, stall, and spill root-cause is read off EXPLAIN ANALYZE, not guessed. Violation: no per-operator metrics means a slow query is an unsolvable black box; regression detection is impossible.

  12. P12 — Reproducible, auditable results and builds. Pinned Cargo.lock/toolchain, vendored fixtures, and golden-file plan output make every run byte-comparable. Tradeoff: maintaining lockfiles and golden files. Operational: differential and EXPLAIN golden tests only work if output is deterministic and the build is stable. Violation: floating deps or nondeterministic output silently invalidate every golden-file gate.

8. Domain Model

8.1 Arrow memory layout (general)

Every array is a typed view over ArrayData:

ArrayData {
  data_type : DataType
  len       : usize          // logical element count
  null_count: usize          // cleared validity bits
  offset    : usize          // logical offset into buffers (zero-copy slice)
  buffers   : Vec<Buffer>    // 0..N data/offset buffers, layout depends on dtype
  child_data: Vec<ArrayData> // nested children (List, Struct, ...)
}
  • Validity bitmap: 1 bit per slot, LSB-numbered (slot i → byte i/8, bit i%8); bit set = valid, clear = null. Omitted iff null_count == 0.
  • Buffers are 64-byte aligned, immutable, Arc-shared Bytes. offset lets a slice reuse parent buffers.
  • Layout per kind (number of buffers):
    • Primitive (Int/UInt/Float/Bool-as-bits/temporal): [validity?, data] — fixed-width values (Boolean packs 1 bit/value).
    • Variable binary/string (Utf8,Binary): [validity?, offsets, data] — offsets: i32 (Large: i64), value i = data[offsets[i]..offsets[i+1]].
    • List (List<T>): [validity?, offsets] + child T array; element i = child[offsets[i]..offsets[i+1]].
    • Struct: [validity?] + one child array per field, all length == parent len.
    • Dictionary: keys (a primitive index array) + values (the dictionary, any array).
    • Null: zero buffers; len only; all slots null.

8.4 Three-valued (Kleene) logic

U = NULL/unknown. Comparison of anything with NULL → U. Boolean ops:

AND | T U F        OR  | T U F        NOT
----+------        ----+------        ---
 T  | T U F         T  | T T T         T -> F
 U  | U U F         U  | T U U         U -> U
 F  | F F F         F  | T U F         F -> T

Operational consequences: WHERE keeps only rows where predicate is T (U and F are dropped). is_null(x) and is_not_null(x) are total (never return U). fill_null(x, v) replaces U with a value. x == x is U when x is NULL (not T).

    workers merge partitions; ~12k distinct b groups -> 12k output rows.
  - Result streamed as RecordBatch(es); collect() concatenates into a DataFrame.

Result: 5 of 8 row groups skipped; I/O ~ 3/8 of full scan.
Caveat: stats may be absent or wrong for a column -> fall back to reading + filtering (never skip on missing stats).

11.1 Memory primitives (cx-buffer)

struct Bytes { ptr: NonNull<u8>, len: usize, cap: usize, align: usize } // 64-byte aligned, owns alloc
struct Buffer { data: Arc<Bytes>, offset: usize, len: usize }           // zero-copy view
impl Buffer { fn as_slice(&self)->&[u8]; fn slice(&self, off:usize,len:usize)->Buffer; fn typed<T:Pod>(&self)->&[T]; }

12. Phase 0 — Repo Skeleton + Aligned Buffer + Validity Bitmap + Memory Pool Scaffolding

12.1 Objectives

Stand up the workspace and the lowest layer: 64-byte-aligned Bytes, Arc-shared zero-copy Buffer, LSB0 Bitmap, and a MemoryPool skeleton. Constraint introduced: every byte buffer is aligned + accounted.

12.2 Detailed Implementation Steps

  • crates/cx-common: EngineError (§11.8), id newtypes, tracing init, bytes_util (popcount, set-bit iter).

  • Workspace Cargo.toml, Makefile (build test run lint bench fuzz clean), Dockerfile, ci.yml (fmt+clippy+test+miri on cx-buffer), governance files.

12.3 Deliverable

cargo build workspace; a smoke test that allocates a 64-byte-aligned buffer, slices it zero-copy (refcount==2), builds a bitmap of 1000 bits, and reserves/releases pool memory.

  • alloc_aligned returns ptr % 64 == 0 for all sizes (proptest). [I4]
  • Bitmap::count_set matches a scalar reference for 10k random bitmaps.
  • Buffer::slice shares the parent Arc (no copy; Arc::strong_count increments).
  • MemoryPool used returns to 0 after all Reservations drop; over-budget reserve → EngineError::OutOfMemory.

12.5 Conformance Fixtures

12.6 Pitfalls

  • Forgetting to pad capacity to 64 → SIMD over-read past allocation (use padded cap).
  • Bit offset in Bitmap::slice mishandled → off-by-one nulls downstream.
  • typed::<T>() on a misaligned offset → UB; assert offset*size % align(T) == 0.
  • AtomicUsize accounting using Relaxed where AcqRel needed → drift under contention.

12.7 Performance Concerns

Aligned alloc enables one aligned SIMD load per 64 B; popcount via u64::count_ones (hardware POPCNT); avoid per-bit loops. Pool reserve is a single atomic add — keep it off the per-element path (reserve per batch, not per row).

12.8 Edge Cases

Zero-length buffer (valid, ptr dangling-but-aligned sentinel); bitmap length not multiple of 8 (pad bits = 0); reservation larger than budget; slice with len==0.

12.9 Failure Analysis

Misalignment → SIMD fault or silent slow path: detect via buffer.misaligned assert. Refcount leak (Arc cycle impossible here; immutable). Pool under-report → spill never triggers → OOM later: reconcile vs allocator stats periodically [I11].

12.10 Operational Notes

Expose mem.pool.used/budget gauges; tracing span buffer.alloc{bytes}. Docker image builds the workspace; make test is the CI gate.

15. Phase 3 — Compute Kernels I: Arithmetic, Comparison, Boolean, Cast

15.1 Objectives

First kernel family: arithmetic, comparison, boolean (Kleene), cast/coercion — all null-aware and SIMD-friendly. Constraint: validity propagation is uniform (out_valid = lhs_valid & rhs_valid), Kleene tables exact (I8 prep).

15.2 Detailed Implementation Steps

  • cx-compute/arithmetic.rs: add/sub/mul/div/rem/neg/abs/pow; scalar broadcast variants; overflow policy hook (Checked/Wrapping/Upcast). (ADR-03 alignment; I2)
  • cx-compute/compare.rs: eq/neq/lt/lt_eq/gt/gt_eq → BooleanArray; null operand → null result (U).
  • cx-compute/boolean.rs: and/or/not/xor + and_kleene/or_kleene using §8.4 tables (operate on packed value + validity bitmaps). (ISO/IEC 9075 three-valued logic; I8)
  • cx-compute/cast.rs: cast(array, dtype) width conversions, int↔float, temporal, Utf8↔number (parse), safe (null on fail) vs strict (error).
  • cx-compute/simd.rs: portable_simd lane loops behind simd feature; scalar fallback; mask-based null handling. (Boncz et al. CIDR 2005; Zhou & Ross SIGMOD 2002; ADR-15)
  • cx-datatype/coercion.rs: finalize promotion lattice used by binary kernels.

15.3 Deliverable

add(Int32[1,2,NULL], Int32[10,NULL,30]) == Int32[11,NULL,NULL]; gt(a, lit(10)) mask; and_kleene(T,U)==U; cast(Utf8["1","x"], Int32, safe) == [1, NULL].

15.4 Acceptance Criteria

  • Validity propagation exact across all arithmetic/compare kernels (proptest vs scalar reference). [I8 prep]
  • Kleene truth tables match §8.4 for all 9 input combinations each (and/or/not).
  • Checked overflow policy errors on i32 overflow; Upcast widens; Wrapping wraps — all tested.
  • cast safe-mode nulls invalid values; strict-mode errors; lossless casts bit-exact.
  • SIMD path and scalar path produce identical results (differential test, simd on/off).

15.5 Conformance Fixtures

fx/compute/arith_nulls.json, fx/compute/kleene_tables.json, fx/compute/cast_matrix.json (every dtype pair), fx/compute/overflow_policy.json. Malformed: cast Utf8→Int with non-numeric (safe→null, strict→error).

15.6 Pitfalls

  • Computing values for null slots then masking is fine for arithmetic but UB for div (div-by-zero on garbage) — mask inputs or guard division.
  • and/or must use Kleene (validity-aware), not plain bitwise (which would treat null as a value).
  • Float compare with NaN: NaN == NaN is false but should the kernel treat it as null? No — NaN is a value, null is the bitmap; keep them distinct.
  • Integer div/rem by zero must not panic in release — return null/error per policy.

15.7 Performance Concerns

Hot loops vectorize when branch-free: compute on all lanes, then AND the validity masks (don't branch per element on null). All-valid fast path skips bitmap work. Avoid bounds checks in inner loop (chunks_exact). cast between same-width types is a no-op reinterpret where safe.

15.8 Edge Cases

All-null inputs; mixed null positions; scalar-vs-array broadcast; Int64 overflow at exactly i64::MAX; Float ±0, ±inf, NaN; empty arrays; Decimal128 scale alignment in add/sub.

15.9 Failure Analysis

A wrong Kleene table or validity-propagation bug silently produces wrong booleans → wrong filter → wrong result set with no crash. Detection: exhaustive Kleene fixtures + differential vs DuckDB on WHERE clauses. Telemetry: none at runtime (correctness, not perf) — gate in CI.

15.10 Operational Notes

Document overflow policy (default Checked for aggregation accumulators, Wrapping opt-in for hashing). tracing per-kernel timing in EXPLAIN ANALYZE. Expose --overflow={checked,wrapping,upcast} in cxq.

16. Phase 4 — Compute Kernels II: Filter, Take, Sort, Hash, Unique

16.1 Objectives

Selection + reordering kernels that power filtering, joins, group-by, and ordering: filter (mask), take (gather), sort_indices (multi-key stable), hash, unique. Constraint: stable + deterministic sort when requested (I12); these kernels are the late-materialization machinery (Principle 4).

16.2 Detailed Implementation Steps

  • cx-compute/filter.rs: filter(array, mask:BooleanArray)->array — count set bits, allocate output, compress surviving slots (and their validity); mask null → drop. (Abadi et al. SIGMOD 2008 late materialization; ADR-06)
  • cx-compute/take.rs: take(array, idx:UInt32Array)->array — gather; idx null → output null; OOB idx → EngineError::Schema.
  • cx-compute/sort.rs: sort_indices(arrays:&[ArrayRef], keys:&[SortKey])->UInt32Array; integer keys → LSD radix; others → pattern-defeating quicksort with stable tiebreak (original index); nulls_first/last, descending. (Graefe ACM Surveys 1993; I12)
  • cx-compute/hash.rs: hash(array)->UInt64Array (ahash); null → reserved sentinel hash; multi-column row hash combiner. (ADR-13; I2)
  • cx-compute/unique.rs: unique(array), n_unique, is_in(array, set) — hash-set based; null is one distinct group.

16.3 Deliverable

filter(Int32[1,2,3,4], mask[T,F,T,F]) == [1,3]; take([10,20,30], idx[2,0,2]) == [30,10,30]; sort_indices([3,1,2], asc) == [1,2,0]; unique([1,1,2,NULL,NULL]) == [1,2,NULL].

16.4 Acceptance Criteria

  • filter preserves validity of surviving slots; count_set(mask) == output length.
  • take with null index yields null output; OOB index errors; take(a, range(len)) == a.
  • Sort is stable: equal keys keep input order (proptest); deterministic across runs and thread counts. [I12]
  • Multi-key sort orders by key 0, ties by key 1, etc.; nulls_first/last honored.
  • hash is identical across simd on/off; collisions handled by downstream tables (kernel just hashes).

16.5 Conformance Fixtures

fx/compute/filter_cases.json, fx/compute/take_gather.json, fx/compute/sort_multikey.json, fx/compute/sort_nulls.json, fx/compute/unique_null.json. Malformed: take_oob.json (error), empty-mask filter.

16.6 Pitfalls

  • filter must compress both values and validity bitmap in lockstep; a desync corrupts nulls.
  • Radix sort on signed ints must flip the sign bit (or handle two's-complement ordering) before bytewise sort.
  • NaN ordering: define NaN as greatest (or per option) so sort has a total order; otherwise unstable.
  • take building a new validity bitmap: index-null OR source-null → output-null.
  • Hashing floats: ±0.0 must hash equal (normalize), NaN must hash consistently.

16.7 Performance Concerns

filter selectivity matters: low-selectivity → small output, but the scan still reads the mask; consider selection-vector (indices) over materialized filter when chained. take is a gather — random access, cache-miss-bound; sort indices to improve locality where possible. Radix sort is O(n·w) and cache-friendly vs O(n log n) comparison. hash vectorized; reuse the hash for both group-by and join.

16.8 Edge Cases

Empty mask (output len 0); all-true mask (output==input, can alias); all-false; take with duplicate indices; sort of all-equal keys (stability); sort with all-null key column; unique of all-null.

16.9 Failure Analysis

A non-stable sort silently reorders ties → non-deterministic output → differential-test flakiness. Detect with the stability proptest + golden files. take OOB → OOB read if unchecked: always bounds-check (fuzzed). Telemetry sort.unstable (must be 0), take.oob.

16.10 Operational Notes

Expose sort spill hook (Phase 13) for large inputs. EXPLAIN ANALYZE reports rows filtered, gather count, sort run count. Document selection-vector vs materialized-filter tradeoff for operator authors.

18. Phase 6 — Aggregation: Hash Group-By + Aggregates (Partitioned, Parallel)

18.1 Objectives

Hash group-by with sum/min/max/mean/count/count_all/var/std/first/last/n_unique, partitioned for parallelism, with correct null semantics (I8) and overflow policy (§4). This is the first heavy operator and the first spill candidate.

18.2 Detailed Implementation Steps

  • cx-exec/hash_agg.rs: row-encode group keys → u64/byte-key; open-addressing HashTable key→accumulator slot. (Graefe ACM Surveys 1993; ADR-13; I8)
  • Accumulators: Sum{acc, upcast}, Min/Max{cur, valid}, Mean{sum,count}, Count{n}, CountAll{n}, Var{n,mean,m2} (Welford), NUnique{set}.
  • Partitioned hashing: hash(key) → P partitions; each rayon worker owns partitions → no shared-table contention; merge partition tables at finalize. (Leis et al. SIGMOD 2014; ADR-07; ADR-06)
  • Null handling: null key forms one group (or excluded per dropna); sum/min/max/mean skip null values; count skips nulls, count_all counts rows. [I8]
  • Overflow: sum accumulator upcasts (Int32→Int64, Int64→Int128); Checked errors on i128 overflow. (ADR-05 null representation; I8)
  • Spill hook: when accumulator memory > budget, spill partition to disk (Phase 13 fills the disk path).

18.3 Deliverable

df.group_by("b").agg([sum("c"), mean("d"), count("e")]) over 10M rows → correct per-group results; parallel across cores; matches DuckDB on a fixture.

18.4 Acceptance Criteria

  • Aggregate null rules exact vs DuckDB (differential) on a null-heavy fixture. [I8]
  • sum(Int32) that overflows i32 produces correct i64 result (no wraparound) under default policy.
  • Parallel result == single-threaded result (determinism of values; row order unordered unless sorted).
  • Group-by scales near-linearly to N cores until hash-table-bound (benchmark).
  • Empty input: grouped → 0 rows; ungrouped → 1 row with sum=null,count=0.

18.5 Conformance Fixtures

fx/agg/groupby_basic.json, fx/agg/null_rules.json (COUNT vs COUNT(*)), fx/agg/overflow_sum.json, fx/agg/var_welford.json, fx/agg/empty_groups.json, fx/agg/skew_keys.json (one giant group).

18.6 Pitfalls

  • Row-key encoding must canonicalize: same logical key → same bytes (normalize ±0.0, handle null marker, fixed field order).
  • Welford variance avoids catastrophic cancellation vs naive E[x^2]-E[x]^2.
  • Partition skew: one hot key lands all rows in one partition → no parallelism + OOM; detect + (later) repartition/spill.
  • Mean computed as sum/count must skip nulls in both.
  • High-cardinality group-by (≈ #rows) → huge table; spill or error, never OOM.

18.7 Performance Concerns

Hash table probe is the bottleneck: open-addressing + good hash (ahash) + cache-friendly slot layout (key+state inline). Partitioning avoids cross-thread contention. Batch the probe (vectorized hash, then scatter). Accumulator state should be small + contiguous. Pre-size table from cardinality estimate when available.

18.8 Edge Cases

All rows one group; all rows distinct groups; null in key; null in value; NaN key (one group); group key spanning multiple columns; var of single element (→ null or 0 per definition); overflow at i128 boundary.

18.9 Failure Analysis

Skewed key blows up one partition → OOM or stall: detect via per-partition size telemetry; recover by spilling that partition (Phase 13). Wrong null rule → silently wrong aggregates: differential tests gate it. Overflow wraparound → wrong sum: default Checked/Upcast prevents it. Telemetry: agg.partition.max_rows, agg.spill.bytes, agg.overflow.

18.10 Operational Notes

EXPLAIN ANALYZE reports groups, partition skew, spill bytes, table resize count. Runbook "slow group-by" → check skew + cardinality. Expose --agg-partitions tuning. tracing span hash_agg{groups,partitions,spilled}.

19. Phase 7 — Joins: Hash Join (Build/Probe) + All Join Types

19.1 Objectives

Hash equi-join with inner/left/right/outer/semi/anti/cross, correct null-key semantics (§8.13), type coercion on keys (I9), partitioned build/probe, spill on large build side. Sort-merge join as a fallback for pre-sorted / range inputs (built on Phase 4 sort).

19.2 Detailed Implementation Steps

  • cx-exec/hash_join.rs: choose smaller side to build; row-encode keys; build HashTable key→Vec<row_id>; probe larger side; emit matched (and unmatched per join type). (Graefe ACM Surveys 1993; ADR-13)
  • Join types: inner (matches only), left (left + matched-or-null right), right (symmetric), outer (both unmatched filled null), semi (left rows with ≥1 match), anti (left rows with 0 matches), cross (Cartesian, no key).
  • Null keys: not inserted into the build table; probe null key → no match (inner/semi drop; anti/left/outer keep with nulls). [§8.13] (ISO/IEC 9075 §8.13; I9)
  • Coercion: insert casts so both key columns share a dtype before hashing (I9); error if no valid coercion.
  • Partitioned build/probe: hash-partition both sides by key → independent partitions across cores; small build side may broadcast.
  • cx-exec/sort_merge.rs: sort both inputs on key, streaming merge; used when inputs already ordered or for range/inequality joins.
  • Spill: partition build side to disk when build table > budget; probe streams against on-disk partitions (grace hash join). (ADR-22; I11)

19.3 Deliverable

left.join(right, on="k", how=inner/left/semi/anti) produces correct row sets and output schema (left ++ right, dup names suffixed); matches DuckDB on fixtures including null keys.

19.4 Acceptance Criteria

  • Each join type's cardinality + content matches DuckDB on fx/join/* (differential).
  • Null keys never match in equi-join; anti-join keeps left null-key rows. [§8.13]
  • Mismatched key types coerced (Int32 vs Int64 → Int64) or rejected (Int vs Utf8 → EngineError::TypeCoercion). [I9]
  • Build side > budget → spills (grace hash) and still returns correct result.
  • Output schema deterministic; row order unordered unless a sort follows.

19.5 Conformance Fixtures

fx/join/inner_basic.json, fx/join/left_outer.json, fx/join/semi_anti.json, fx/join/null_keys.json, fx/join/type_coercion.json, fx/join/skew_build.json, fx/join/cross.json. Malformed: incompatible key types (error).

19.6 Pitfalls

  • Building on the larger side wastes memory — always build on the smaller (estimate by row count/bytes).
  • Duplicate keys on the build side → one probe row matches many → output explosion; size estimate must account for it.
  • Null-key handling differs by join type — encode the rule explicitly, test each.
  • Coercion that loses precision (Int64→Int32) must be rejected, not silent.
  • Cross join is O(n·m) — guard against accidental cross (missing join key) with a plan-level warning.

19.7 Performance Concerns

Probe is pointer-chase-bound; compact the hash table (open addressing, inline small payloads). Vectorize hashing + probe in batches. Partitioning keeps each table cache-resident. Broadcast tiny build side to avoid partition overhead. Late-materialize: probe yields matched row-id pairs, then take the payload columns once.

19.8 Edge Cases

Empty build side (inner→0 rows; left→all left with nulls); empty probe; all keys null; all keys identical (one giant bucket → skew); self-join; multi-column join key; floating key with NaN (no match); duplicate output column names.

19.9 Failure Analysis

Skewed build (one hot key) → giant bucket → probe stalls + memory blowup: detect via bucket-size telemetry; recover by spilling/repartitioning. Wrong null-key rule → wrong result set: differential tests. Build-side OOM without spill → process death: budget + grace-hash spill prevents it. Telemetry: join.build.rows, join.probe.rows, join.max_bucket, join.spill.bytes.

19.10 Operational Notes

EXPLAIN ANALYZE reports build/probe rows, max bucket, spill, chosen side. Runbook "slow join" → check build-side size, skew, missing predicate. Plan warning on cross join. tracing span hash_join{how,build_rows,probe_rows,spilled}.

20. Phase 8 — Expression Engine: Expr Trees, Evaluation, When/Then, Window

20.1 Objectives

Build the Expr tree (§8.7) and an evaluator that maps an expression to a column over a RecordBatch, including when/then/otherwise, scalar + aggregate functions, and window (agg.over(partition)). Constraint: expression evaluation is pure + null-aware; output length == batch length (for scalar exprs).

20.2 Detailed Implementation Steps

  • cx-expr/expr.rs: Expr enum + builder DSL (col, lit, .gt, .and, .alias, .cast, .over).
  • cx-expr/eval.rs: eval(expr, &RecordBatch) -> ArrayRef; recursive: Column→lookup, Literal→broadcast, Binary/Unary→kernel, Function→registry dispatch, Cast→cast kernel.
  • cx-expr/when_then.rs: When → evaluate branches as masks, select/zip the value arrays by mask precedence (first true wins); else otherwise. (ISO/IEC 9075 three-valued logic; ADR-12)
  • cx-expr/function.rs: scalar function registry (name→signature→kernel); arity + type checking.
  • cx-expr/window.rs: Window{func, expr, partition} → partition rows (hash), aggregate per partition, broadcast result back aligned to row order. (ADR-13; Leis et al. SIGMOD 2014)
  • Expression schema inference: expr.data_type(input_schema) -> DataType (drives plan schema resolution + coercion).

20.3 Deliverable

Evaluate when(col("x").gt(lit(0))).then(lit("pos")).otherwise(lit("neg")) → Utf8 column; sum(col("c")).over(col("region")) broadcasts region totals to each row.

20.4 Acceptance Criteria

  • Scalar expr output length == batch rows; null propagation correct through the tree.
  • when/then/otherwise precedence: first matching branch wins; unmatched → otherwise; null condition → otherwise (U is not T).
  • expr.data_type(schema) matches the evaluated array's dtype (coercion-aware).
  • Window aggregate broadcasts correctly and preserves row order.
  • Unknown function / arity mismatch → EngineError::NotFound/Schema at build, not at eval.

20.5 Conformance Fixtures

fx/expr/binary_nulls.json, fx/expr/when_then_chain.json, fx/expr/window_sum_over.json, fx/expr/dtype_infer.json. Malformed: unknown_function.json, arity_mismatch.json (both error).

20.6 Pitfalls

  • when condition that is null must route to otherwise (Kleene: U ≠ T) — not to then.
  • Literal broadcast must produce a full-length array (or a cheap constant array) matching batch length.
  • Window over without partition = whole-frame aggregate broadcast — easy to confuse with group-by (which reduces rows).
  • Aggregate expr used in a scalar context (no group-by) must be rejected or treated as whole-column reduce — define it.
  • Nested expressions re-evaluating a shared subtree → wasted work (CSE in Phase 10 fixes it).

20.7 Performance Concerns

Evaluate bottom-up once per batch; avoid re-walking the tree per row. when/then should compute branch values only where needed (or compute all + select — tradeoff by branch cost). Constant sub-expressions should be folded (Phase 10). Window partitioning reuses the hash machinery.

20.8 Edge Cases

All-null input column; empty batch; deeply nested expr; lit(null); window over a column with nulls in the partition key; cast inside an expr that fails (safe vs strict); alias collision.

20.9 Failure Analysis

A mis-evaluated predicate silently changes the result set — covered by expr fixtures + differential WHERE tests. dtype-inference disagreeing with eval-time dtype → schema drift (I10): assert in debug. Telemetry: none at runtime; CI-gated correctness.

20.10 Operational Notes

EXPLAIN prints the expr tree; EXPLAIN ANALYZE times per-expr evaluation. Document the function registry for extension authors. tracing span expr.eval{kind,rows}.

21. Phase 9 — Lazy Logical Plan + Schema Resolution + LazyFrame API

21.1 Objectives

The lazy frontend: LazyFrame records operations as a LogicalPlan tree (§8.9), resolves + validates schema at build time, and defers execution to collect(). Constraint: plan output schema is resolved and stable (I10); nothing executes until collect.

21.2 Detailed Implementation Steps

  • cx-plan/logical.rs: LogicalPlan enum (§11.5) + constructors; schema() resolution (propagate field changes through Projection/Aggregate/Join/Union). (ADR-10; I10)
  • cx-plan/schema_infer.rs: per-node schema rules (e.g. Aggregate output = keys ++ agg output fields; Join output = left ++ right with dup-name suffixing).
  • cx-frame (or cx-lazy): LazyFrame builder API — scan_csv/scan_parquet/scan_ipc, .select, .filter, .group_by().agg, .join, .sort, .limit, .distinct, .collect().
  • Plan validation: column references resolve against input schema; types coerce or error (I9); aggregate/window placement rules. (ADR-07; I9)
  • cx-plan/display.rs: EXPLAIN text (indented tree) + plan-dot (graphviz) tool.
  • collect() (Phase 9 stub): run the unoptimized plan via a naive eager executor to prove correctness before the optimizer/executor land.

21.3 Deliverable

scan_csv("t.csv").filter(col("a").gt(lit(10))).group_by("b").agg([sum("c")]) builds a valid LogicalPlan with a resolved output schema; .explain() prints the tree; .collect() returns the right answer (unoptimized).

21.4 Acceptance Criteria

  • LogicalPlan::schema() matches the eventual result schema for all node types (golden files).
  • Unresolved column / type mismatch errors at build time, not at collect. [I9,I10]
  • EXPLAIN output is stable + deterministic (golden test).
  • collect() (naive) result equals the eager-API equivalent on fixtures.
  • Join output schema dedups names deterministically (suffix _right).

21.5 Conformance Fixtures

fx/plan/schema_resolution.json, fx/plan/explain_golden.txt, fx/plan/unresolved_column.json (error), fx/plan/join_schema.json.

21.6 Pitfalls

  • Schema resolution must run during plan build, not at collect — early errors are the point of lazy.
  • Aggregate output schema: grouping keys first, then agg outputs, with stable naming.
  • A filter referencing a column produced later in the plan must error (scoping).
  • Self-join / union with duplicate names needs a deterministic disambiguation rule.
  • The naive collect must not bake in assumptions the real executor will violate (e.g. ordering).

21.7 Performance Concerns

Plan build is cheap (tree construction); avoid resolving schema repeatedly (cache per node). The naive collect is intentionally unoptimized — do not benchmark it; it exists for correctness bootstrapping before Phase 11.

21.8 Edge Cases

Empty plan (scan only); plan with no projection (select all); chained filters; group-by with no aggregates (= distinct); union of differently-ordered-but-compatible schemas; deeply nested subplans.

21.9 Failure Analysis

Schema drift between LogicalPlan::schema() and the executor's output (I10) is the highest-risk bug here — assert equality in tests + debug builds. Unresolved references that slip to runtime → mid-query panic: validate at build. Telemetry plan.schema_drift.

21.10 Operational Notes

cxq explain "<query>" prints the logical plan. tracing span plan.build. Document the lazy contract: build = validate, collect = execute. The EXPLAIN golden files are the regression guard for plan shape.

22. Phase 10 — Optimizer: Pushdown, CSE, Constant Folding, Coercion

22.1 Objectives

Rule-based optimizer (§8.10): predicate/projection/slice pushdown, common-subexpression elimination, constant folding, type coercion, expression simplification — applied to fixed point, each rule schema-preserving. Constraint: optimization never changes query semantics (only cost); output schema unchanged (I10).

22.2 Detailed Implementation Steps

  • cx-optimize/rule.rs: OptimizerRule trait + Optimizer{rules} driver (apply rules to fixed point or N passes, top-down/bottom-up per rule).
  • predicate_pushdown.rs: split conjunctions; push each predicate below Projection/through Join (to the side whose columns it references); fold into Scan.predicate. (Abadi et al. SIGMOD 2008; ADR-11)
  • projection_pushdown.rs: compute required-column set from root; set Scan.projection; insert/trim Projection nodes; drop unused columns early.
  • slice_pushdown.rs: push Limit/slice below order-preserving nodes; into Scan (row-group limit) where safe.
  • constant_fold.rs: evaluate literal-only sub-exprs at plan time.
  • cse.rs: detect identical pure sub-exprs (≥2 uses) → hoist into a shared projection with a generated alias. (ADR-12; ADR-11)
  • coerce.rs: insert explicit cast per the promotion lattice for binary ops / join keys / union. [I9] (ADR-07; I9)
  • simplify.rs: algebraic identities (x and true→x, filter(true)→input, double-negation).

22.3 Deliverable

The §8.12 query: optimizer turns Scan(all) → Filter(a>10) → Aggregate into Scan(proj=[a,b,c], pred=a>10) → Aggregate; EXPLAIN before/after shows pushdown; result identical to unoptimized.

22.4 Acceptance Criteria

  • Optimized plan result == unoptimized result on every differential fixture (semantics preserved).
  • Predicate pushdown reaches Scan.predicate when the predicate references only scan columns.
  • Projection pushdown sets Scan.projection to exactly the needed columns (no over-read).
  • CSE hoists a repeated sub-expr exactly once (verified in EXPLAIN).
  • Coercion inserts casts so all binary ops / join keys are type-consistent. [I9]
  • Optimizer is idempotent: a second pass produces no further change (fixed point).

22.5 Conformance Fixtures

fx/opt/predicate_pushdown.txt (plan before/after), fx/opt/projection_pushdown.txt, fx/opt/cse.txt, fx/opt/const_fold.json, fx/opt/coercion.txt, fx/opt/idempotent.txt. Each pairs an input plan with the expected optimized plan (golden).

22.6 Pitfalls

  • Pushing a predicate through a Join to the wrong side (column not available) → wrong/empty result.
  • Pushing a predicate below an Aggregate is invalid if it references an aggregate output (only pre-aggregation columns are pushable).
  • CSE on a non-pure or non-deterministic expr (e.g. a random function) changes semantics — only hoist pure exprs.
  • Slice pushdown below a node that reorders (sort) or filters changes which rows survive — only push through order/count-preserving nodes.
  • Constant folding must respect overflow/null policy (folding must match runtime eval).

22.7 Performance Concerns

Each rule is a tree rewrite — keep them O(plan size). Run to fixed point but bound passes to avoid pathological loops. Projection pushdown is the biggest I/O win (fewer Parquet columns decoded); predicate pushdown the biggest scan win (row-group skip). Measure plan-time overhead (should be µs-ms, negligible vs execution).

22.8 Edge Cases

Predicate referencing both join sides (cannot push fully — keep above join, push the decomposable parts); projection of a computed column needed only by a dropped node; CSE across when/then branches; constant-folding a division-by-zero (must match runtime); empty plan; already-optimal plan (idempotence).

22.9 Failure Analysis

A semantics-changing rewrite is the worst failure — silently wrong results. Defense: every optimization fixture asserts optimized==unoptimized on real data + differential vs DuckDB. A rule that loops forever → plan-build hang: bound passes + detect no-progress. Telemetry: opt.rule.applied{name}, opt.passes.

22.10 Operational Notes

EXPLAIN shows the optimized plan; EXPLAIN(verbose) shows per-rule diffs. A --no-optimize flag runs the naive plan for differential debugging ("does the optimizer cause this?"). tracing span optimize{rule,changed}. Runbook "wrong results" step 1: compare --no-optimize vs optimized.

23. Phase 11 — Physical Plan + Vectorized Morsel-Driven Executor

23.1 Objectives

Lower the optimized LogicalPlan to a PhysicalPlan of ExecNodes and execute it morsel-driven over rayon with RecordBatch streaming (§3.1, Principle 6). Constraint: no global lock in the hot path; output schema == plan schema (I10, I14).

23.2 Detailed Implementation Steps

  • cx-plan/physical.rs: ExecNode trait (§11.5); lowering LogicalPlan → Arc<dyn ExecNode> (Scan→ScanExec, Filter→FilterExec, Aggregate→HashAggExec, Join→HashJoinExec or SortMergeJoinExec, Sort→SortExec, Limit→LimitExec, Projection→ProjectExec). (ADR-10; ADR-06)
  • cx-exec/executor.rs: drive the root ExecNode::execute(ctx); collect the RecordBatchStream.
  • cx-exec/morsel.rs: split scan output into morsels (default 64Ki rows); cx-exec/stream.rs: RecordBatchStream iterator contract (each item a Result<RecordBatch>; schema constant, I14).
  • Parallelism: ScanExec produces morsels; rayon work-steals; pipeline operators (Filter/Project) run per-morsel; pipeline-breakers (HashAgg/Sort/HashJoin build) consume all input then emit. (Leis et al. SIGMOD 2014; ADR-07)
  • TaskContext: thread pool handle, MemoryPool reservation, metrics sink, cancellation token.
  • Backpressure: bounded channels between pipeline stages; a slow consumer throttles producers. (ADR-07; I14)
  • Determinism: unordered by default; maintain_order/Sort impose order (Principle 9).

23.3 Deliverable

End-to-end LazyFrame...collect() runs through the real executor: scan→filter→hash-agg over 100M rows, parallel across cores, streaming RecordBatches, matching the naive collect result.

23.4 Acceptance Criteria

  • Optimized physical-plan result == naive logical result == DuckDB (differential) on TPC-H subset queries.
  • Executor scales near-linearly to N cores on a scan+filter+agg (benchmark; report speedup curve).
  • Output schema equals the plan schema for every batch in the stream. [I10,I14]
  • Memory stays under budget (accounting + spill engaged on a large group-by/join).
  • Query cancellation stops work promptly (cancellation token honored between morsels).

23.5 Conformance Fixtures

fx/exec/tpch_q1.json,q3.json,q6.json (subset), fx/exec/scaling.json (rows/sec vs cores), fx/exec/cancel.json, fx/exec/schema_stability.json (per-batch schema constant).

23.6 Pitfalls

  • A single shared output queue or global mutex serializes everything — partition state, use per-worker queues.
  • Morsel too large → poor load balance + cache pressure; too small → dispatch overhead. Tune to L2/L3.
  • Pipeline-breaker (agg/sort/join-build) must fully consume input before emitting — mixing pull/push incorrectly deadlocks.
  • Reusing buffers across morsels without clear ownership → data race; keep batches immutable + Arc.
  • Forgetting backpressure → unbounded memory when producer outruns consumer.

23.7 Performance Concerns

Vectorized operators amortize dispatch over a batch. Keep batches cache-resident (≤ L2/L3). Minimize per-batch allocation (reuse builders/scratch via the pool). NUMA: prefer scheduling a morsel on the core near its memory (rayon hint). Avoid materializing between pipeline operators — chain Filter/Project on the same batch. Tail latency on skew is the executor's hardest perf problem (one heavy morsel).

23.8 Edge Cases

Empty scan (stream yields 0 batches but correct schema); single morsel (no parallelism, must still work); operator with no input rows; cancellation mid-build; a morsel that filters to 0 rows (emit empty or skip); extremely wide schema (many columns).

23.9 Failure Analysis

Deadlock from incorrect pull/push or unbounded channel: detect via watchdog + thread-state dump; fix the operator state machine (§8.16). Schema drift mid-stream → consumer crash (I14): per-batch debug assert. Skew → one core pegged, others idle: detect via per-worker rows telemetry; mitigate by repartitioning. Telemetry: exec.morsels, exec.worker.rows{id}, exec.batch.rows, per-operator time.

23.10 Operational Notes

EXPLAIN ANALYZE aggregates per-operator wall time, rows in/out, spill bytes from the metrics sink. tracing spans nest per operator per morsel. Runbook "slow query" → read EXPLAIN ANALYZE, find the dominant operator, check skew/spill. --threads N and --batch-size tunables. Compiled/JIT execution PhaseDeferred("Deferred Features Register") — the vectorized interpreter is the shipped model.

24. Phase 12 — I/O: CSV + Arrow IPC + Parquet (Encodings, Row Groups, Statistics)

24.1 Objectives

Read/write the three core formats, with Parquet predicate pushdown via statistics and the encoding suite. Constraint: untrusted-file safety (Threat Model); Arrow round-trip bit-exact (I16); Parquet reader skips row groups via stats (§4).

24.2 Detailed Implementation Steps

  • cx-io/csv.rs: SIMD-assisted line/field splitter (quote/escape aware); sample-based schema inference (scan first N rows → infer dtype per column, widen on conflict); typed parse into builders; writer.
  • cx-io/ipc/: Flatbuffers schema + record-batch message parse/serialize; map IPC buffers to Buffer zero-copy on read; file + stream framing; dictionary messages. (Arrow IPC Format spec; ADR-19; I13)
  • cx-io/parquet/metadata.rs: Thrift FileMetaData/RowGroup/ColumnChunk/statistics parse + write (footer).
  • cx-io/parquet/encoding.rs: PLAIN, RLE/bit-pack hybrid, DELTA_BINARY_PACKED, DELTA_LENGTH_BYTE_ARRAY, RLE_DICTIONARY; def/rep levels for nullable + List/Struct (Dremel). (Parquet Format spec; Melnik et al. VLDB 2010)
  • cx-io/parquet/page.rs: data page v1/v2 read/write; per-page compression via cx-io codec trait → #397 (zstd/snappy/gzip).
  • cx-io/parquet/reader.rs: predicate → row-group skip via [min,max]/null_count stats; projection → read only needed column chunks; assemble columns with validity. writer.rs: row-group sizing (128 MiB), dictionary fallback, stats emission. (Lang et al. SIGMOD 2016; ADR-11)

24.3 Deliverable

Round-trip an array through IPC bit-exact; write a Parquet file (dictionary + RLE encoded) and read it back equal; a predicate ts >= X skips non-matching row groups (verify pages-read count); read a pyarrow-written Parquet file.

24.4 Acceptance Criteria

  • Arrow IPC round-trip (array → IPC → array) is byte-identical for every array kind, including nested + dictionary. [I16]
  • Parquet written by cx reads in pyarrow/parquet-tools and vice-versa (interop fixtures).
  • Predicate pushdown skips ≥ 50% of row groups on a selective fixture; never skips on missing/!present stats.
  • CSV schema inference matches expected dtypes; quoting/escaping/newlines-in-quotes handled.
  • All encodings decode to the same values they were encoded from (per-encoding fixtures).

24.5 Conformance Fixtures

conformance/arrow-roundtrip/* (all kinds), conformance/parquet/written_by_pyarrow.parquet, conformance/parquet/encodings/{plain,rle,delta,dict}.parquet, fx/io/csv_quoting.csv, fx/parquet/stats_skip.parquet. Malformed: truncated_footer.parquet, bad_magic.parquet, dict_index_oob.parquet, decompress_bomb.parquet, non_utf8.csv (all must error safely).

24.6 Pitfalls

  • Parquet def/rep levels for nested/nullable are the #1 source of bugs — a wrong level desyncs the whole column.
  • Dictionary fallback: a column chunk can switch from dictionary to plain mid-chunk when the dictionary grows too large — handle both pages.
  • IPC buffer alignment: messages must be 8/64-byte aligned per spec; mis-padding breaks zero-copy.
  • CSV: newlines inside quoted fields, BOM, ragged rows, and locale decimals are all edge cases.
  • Trusting num_values/sizes from a malformed footer → OOB/over-allocation (Threat Model) — bound + validate every length.

24.7 Performance Concerns

Parquet read is I/O + decode bound: projection (fewer column chunks) + predicate (fewer row groups) + parallel row-group decode are the wins. CSV parse is CPU-bound: SIMD field splitting, parse-into-columns directly (no intermediate row structs). Decompression reuses buffers. IPC read is near-zero-copy (slice the mmap'd/buffered bytes).

24.8 Edge Cases

Empty file; single-row-group file; all-null column (stats null_count==len); Parquet without statistics (no skip); dictionary-encoded then plain pages in one chunk; CSV with only a header; UTF-8 BOM; > 2 GiB column (offset overflow → LargeUtf8); nested List<Struct> in Parquet.

24.9 Failure Analysis

A crafted footer/page is the primary attack surface: malformed length → over-allocation/OOB; decompression bomb → memory blowup. Defense: validate every length against file size, cap decompressed size, bound dictionary cardinality, reject OOB dict indices (I5), reject non-UTF8 in Utf8. Detection: fuzzers (fuzz/parquet.rs,csv.rs,ipc.rs). Telemetry: parquet.rowgroups.skipped/read, io.decompress.ratio (cap), io.parse.error.

24.10 Operational Notes

cxq convert in.csv out.parquet and cxq cat file.parquet exercise this layer. EXPLAIN ANALYZE reports row groups skipped/read, bytes scanned, decompression ratio. Runbook "Parquet read error" → check magic/footer, encoding support, codec availability. tracing span io.read{format,bytes,rowgroups}. Compression delegated to #397; codec trait keeps it pluggable.

25. Phase 13 — Memory Accounting + Spill + C Data Interface + Conformance + Fuzzing

25.1 Objectives

Production hardening: enforce the memory budget with spill-to-disk for agg/sort/join, expose the Arrow C Data Interface (FFI), and stand up the conformance + fuzzing gates. Constraint: degrade not OOM (Principle 8); FFI zero-copy + ABI-correct (release callback semantics). GPU + compiled-JIT remain deferred.

25.2 Detailed Implementation Steps

  • cx-memory/accounting.rs: every large allocation goes through MemoryPool::try_reserve; per-operator reservations; reconcile vs allocator stats [I11]. (ADR-21; I11)
  • cx-memory/spill.rs: spill partitions (hash-agg/join build / sort runs) to a temp dir as IPC/Arrow batches; read back on finalize (grace hash join, external merge sort).
  • cx-ffi/c_data_interface.rs: export ArrowArray/ArrowSchema (#[repr(C)]) with a release callback that drops the backing Arcs exactly once; import wraps foreign buffers (respect foreign release). (Arrow C Data Interface spec; ADR-20; I13)
  • conformance/ harness: arrow round-trip, Parquet interop, Kleene tables, differential vs DuckDB/Polars; conformance.report.json with per-bucket Pass/Deferred. (ADR-26; ADR-28)
  • fuzz/: cargo-fuzz targets for CSV/Parquet/IPC readers; corpus seeded from valid fixtures + mutations.
  • cx-py: pyo3 stub exposing read_parquet, eager ops, and LazyFrame.collect().
  • Deferred gates: PhaseDeferred("Deferred Features Register") for GPU kernels; PhaseDeferred("Deferred Features Register") for compiled/JIT execution.

25.3 Deliverable

A group-by/join larger than the budget completes by spilling (not OOM); an array exported via the C Data Interface is read by pyarrow zero-copy and freed correctly; conformance report shows Pass on round-trip + differential buckets; fuzzers run clean on the seed corpus.

25.4 Acceptance Criteria

  • A --mem-budget smaller than the working set still completes agg/sort/join correctly via spill (result == in-memory result).
  • Memory accounting tracks actual within 5% (reconcile test). [I11]
  • C Data Interface export/import round-trips with pyarrow bit-exact; release called exactly once (no leak, no double-free; verified under valgrind/asan).
  • Differential vs DuckDB + Polars green on the TPC-H subset + ClickBench subset.
  • Fuzz targets survive 1M+ iterations on seed corpus with no panic/OOB/UB (miri/asan where applicable).

25.5 Conformance Fixtures

conformance/differential/tpch_subset/*, conformance/differential/clickbench_subset/*, conformance/ffi/pyarrow_roundtrip/*, fx/spill/large_groupby.json, fx/spill/external_sort.json. Malformed: foreign ArrowArray with null release (handle gracefully), spill dir unwritable (clear error).

25.6 Pitfalls

  • Spill correctness: the spilled-then-merged result must equal the in-memory result — partition boundaries + merge order matter.
  • FFI release double-free or leak: the callback must own exactly the Arcs it dropped; importer calls release once.
  • Accounting drift: forgetting to account a hot-path allocation → spill never triggers → OOM (I11).
  • Spill thrashing: too-low budget → constant spill → I/O-bound; expose budget + warn.
  • ABI: #[repr(C)] field order/layout must match the Arrow spec exactly; an off-by-one buffer pointer corrupts the import.

25.7 Performance Concerns

Spill is orders of magnitude slower than memory — spill only above threshold, spill the coldest/largest partitions first, and compress spilled batches. FFI export is O(1) pointer hand-off (zero-copy) — the win is avoiding a serialize/copy. Accounting is a per-batch atomic, not per-row. External merge sort fan-in tuned to memory + fd budget.

25.8 Edge Cases

Budget smaller than a single batch (must still make progress — minimum reservation floor); spill dir full mid-spill (clear error + cleanup); FFI import of a zero-length array; release callback that panics (isolate); concurrent queries sharing one pool (per-query sub-pools); GPU/JIT call sites hit → typed Unsupported error.

25.9 Failure Analysis

Spill failure (disk full / unwritable) → query fails with EngineError::OutOfMemory/Io, never silent wrong results; cleanup temp files. FFI memory bug → cross-language corruption: gate with asan/valgrind in CI. Unaccounted allocation → OOM kill: reconcile telemetry catches drift early. Telemetry: mem.spill.bytes/count, mem.accounting.drift, ffi.release.count, fuzz.crashes (must be 0).

25.10 Operational Notes

--mem-budget, --spill-dir, --threads are the core operational knobs. EXPLAIN ANALYZE reports spill bytes per operator. Runbook "query OOM" → raise budget or enable/repair spill; check accounting drift. C Data Interface documented for embedders. Conformance report + fuzz canary are release gates. GPU (§13.10) and compiled/JIT (deferred — see Deferred Features Register) tracked as PhaseDeferred with their owning sections.

Performance Engineering

  • Cache locality: columnar scan is sequential within a column (prefetch-friendly); keep batches ≤ L2/L3; struct-of-arrays not array-of-structs; align to 64 B.
  • SIMD vectorization: kernels written branch-free over lanes; validity handled via masks; verify autovectorization (asm inspection) or std::simd; fall back to scalar.
  • Branchless null handling: compute on all lanes then AND validity masks; avoid per-element if null branches that defeat the pipeline.
  • Morsel sizing: default 64Ki rows; tune so a morsel's working set fits L2/L3; too big → cache thrash, too small → dispatch overhead.
  • NUMA: schedule a morsel near its memory; partition build/probe per socket; avoid cross-socket hash-table sharing.
  • Late materialization: carry selection (mask/indices); decode/gather columns last; a 1%-selective filter touches ~1% of output bytes.
  • Dictionary fast-paths: compare/group-by/join on dictionary keys without decoding when both sides share (or can map) the dictionary.
  • Hash-table efficiency: open addressing, inline small payloads, good hash (ahash), pre-size from cardinality; probe in batches.
  • Allocation reuse: reuse builder/scratch buffers across batches via the pool; avoid per-batch malloc churn.
  • Profiling workflow: criterion for micro; perf/flamegraph for hot paths; perf stat for cache-miss/IPC; heaptrack for allocation; compare against DuckDB/Polars on ClickBench.
  • Tail latency on skew: one heavy morsel/partition dominates; detect via per-worker telemetry; mitigate by finer partitioning / repartition; this is the executor's hardest perf target.

Scalability Analysis

  • Single-node multicore scaling: scan/filter/project scale embarrassingly (per-morsel); group-by/join scale via partitioning until the shared structure (hash table) or memory bandwidth saturates. Report a speedup curve vs cores.
  • Memory pressure + spill: working set > RAM degrades to spill (external sort, grace hash) — correct but I/O-bound; the budget caps RSS so the host survives.
  • Large-cardinality group-by/join: the hash table is the bottleneck (size + probe). Mitigation: partitioning, spill, (future) adaptive repartition. Ceiling: cardinality near row count → table ≈ data size.
  • String-heavy columns: offset + data buffers dominate memory; dictionary encoding helps low cardinality; high cardinality is bandwidth-bound. Inline-string (Umbra) layout is the deferred optimization.
  • Parquet row-group parallelism: read scales with row-group count × cores; predicate/projection pushdown cut the work; tiny row groups → metadata overhead, huge → poor skip granularity.
  • Bottlenecks (ranked): (1) hash table probe (group-by/join), (2) sort (comparison + gather), (3) I/O + decode (Parquet/CSV), (4) memory bandwidth on wide scans.
  • Vertical scaling: more cores + RAM + bandwidth help until the hottest shared structure serializes; NUMA awareness extends the ceiling.
  • Ceiling vs distributed: single-node bounded by one machine's RAM + cores + bandwidth + local disk for spill. Beyond that needs shuffle/partitioning across nodes — explicitly a separate project (non-goal §1.3). This engine is the per-node kernel such a system would wrap.

Mental Models & First Principles

  1. MM1 — Columnar layout aligns the access pattern with the arithmetic. Predicts: which queries benefit from column projection; when a scan reads 1/N of the data. Without it: you read all columns for every query and burn memory bandwidth on fields that are never used. Applied: §4 (cached-column scan ≥ 5 GB/s/core), §6 Principle 1, Phase 1 (§13), Phase 4 (§16).

  2. MM2 — The validity bitmap is a separate physical channel. Predicts: which operations can be vectorized without branching; when Kleene logic diverges from two-valued logic. Without it: you write if is_null(i) { ... } per element, defeating the pipeline; or you collapse three-valued to two-valued and silently corrupt WHERE-clause results. Applied: §8.4, §8.5, I2, Phase 1 (§13), Phase 3 (§15).

  3. MM3 — Late materialization: carry a ticket, pay at the door. Predicts: when a selective filter saves the majority of decode cost; when take is cheaper than early projection. Without it: a 1%-selective filter pays to decode 100% of the target columns before discarding 99%. Applied: §6 Principle 4, §8.11 FilterExec, Phase 4 (§16), Phase 7 (§19).

  4. MM4 — The hash table, not the arithmetic, is the bottleneck in aggregation and joins. Predicts: when partitioning buys scalability; when probe locality dominates throughput; when the table must spill. Without it: you optimize the accumulator function while the probe loop stalls on cache misses. Applied: §4 (group-by ≥ 50 M rows/s), §8.11, Phase 6 (§18), Phase 7 (§19).

  5. MM5 — Pushdown is free I/O reduction; every byte not read is not decoded. Predicts: which optimizer rules have the largest end-to-end impact; when Parquet stats skip row groups vs. must read them. Without it: the optimizer skips predicate/projection pushdown and reads every column of every row group before filtering. Applied: §8.10, §6 Principle 5, Phase 10 (§22), Phase 12 (§24).

  6. MM6 — Morsel granularity governs the parallelism-vs-locality tradeoff. Predicts: when morsels are too large (one core dominates, poor load balance) vs. too small (dispatch overhead dominates). Without it: the executor serializes on skewed morsels or thrashes with too-fine scheduling. Applied: §4 (default 64Ki rows), §6 Principle 6, Phase 11 (§23), ADR-06.

  7. MM7 — Zero-copy sharing via Arc + (offset, len) is the correctness boundary for immutability. Predicts: which operations are safe to parallelize without locks; when mutation would cause a data race across views. Without it: an in-place mutation of a shared buffer corrupts the other holder's view and breaks FFI safety. Applied: §6 Principle 3, §11.1, I13, Phase 0 (§12), Phase 13 (§25).

  8. MM8 — Schema is law: validate at edges, trust in the interior. Predicts: where to place validation checks so that interior kernels can skip them; when a type mismatch is caught early vs. causing a mid-execution panic. Without it: unvalidated arrays propagate corrupt offsets or wrong null_counts through the pipeline until they produce a silent wrong result or an OOB read. Applied: §7 I1/I3/I5/I10, Phase 1 (§13), Phase 9 (§21), ADR-23.

  9. MM9 — Dictionary encoding trades index-space for value-space at a cardinality threshold. Predicts: when dictionary encoding helps (low distinct/total) vs. hurts (high-cardinality wastes the indices buffer); when to decode eagerly vs. operate on keys. Applied: §4 (threshold: distinct/total < 0.5 and cardinality ≤ 2^20), ADR-09, Phase 2 (§14), Phase 5 (§17).

  10. MM10 — The rule-based optimizer is correct by construction; the cost-based optimizer is correct by measurement. Predicts: which rewrites are safe to apply unconditionally (semantics-preserving identities) vs. which require cardinality estimates (join reordering). Without it: you either under-optimize (no pushdown) or over-optimize (a semantics-changing rewrite applied without proof of equivalence). Applied: §8.10, Phase 10 (§22), ADR-11, Deferred Features Register (CBO).

Back-of-Envelope Capacity Model

  1. Single-core memory bandwidth bound (§4: ≥ 5 GB/s/core scanned). An AVX2 core on a 30 GB/s NUMA socket has ~15 GB/s solo bandwidth. A scan kernel reading only data buffers (no validity on all-valid arrays) approaches ~10 GB/s at 64-B stride. Target 5 GB/s/core accommodates multi-core sharing. Design consequence: null-check elimination on all-valid batches (ADR-05 fast path, Phase 3 §15) is mandatory to stay bandwidth-bound, not dispatch-bound.

  2. Morsel working-set vs. L2 cache (§4: default 65 536 rows). An Int64 column of 65 536 values = 65 536 × 8 B = 512 KB. L2 is typically 256 KB–1 MB/core. Two Int64 columns per morsel ≈ 1 MB, fitting L2/L3 boundary. Design consequence: the 64Ki default is the correct cache-resident operating point; wider schema or wider types require tuning down morsel size (§4 tunable 1 024–262 144).

  3. Group-by hash table size at mid cardinality (§4: ≥ 50 M rows/s). 1 M distinct groups × (16 B key + 32 B accumulator state) = 48 MB per partition; 8 partitions (8 cores) = 48 MB each, cache-warm. At 50 M rows/s per core and 8 cores = 400 M rows/s aggregate — consistent with the §4 target at mid cardinality. High-cardinality (100 M groups) → 4.8 GB table → spill required (Phase 13 §25). Design consequence: per-partition table sizing sets the spill threshold.

  4. Join build-side memory (§4: ≥ 50 M probe rows/s/core). A 100 M row build table, 8 B key + 8 B row ptr = 16 B/row → 1.6 GB. Default 80% of --mem-budget (§4). At 8 GB budget → 6.4 GB available → fits. At 2 GB budget → grace hash join spill required. Probe at 50 M rows/s/core × 8 cores = 400 M probe rows/s; probe is pointer-chase-bound, not bandwidth-bound. Design consequence: build-side estimation drives whether broadcast or partition strategy is chosen (Phase 7 §19).

  5. Parquet row-group skip benefit (§4: ≥ 50% skipped on selective filters). Default row group = 128 MiB (§4). A 10 GB file = 80 row groups. A timestamp predicate with 10% selectivity and well-clustered data should skip ≥ 70% of row groups. At 128 MiB/RG × 80 × 0.30 read = 3.1 GB bytes scanned vs. 10 GB full scan = 69% I/O reduction. Design consequence: row-group size must not be too small (metadata overhead dominates) nor too large (skip granularity coarsens). 128 MiB balances both (§4).

  6. Parquet decode throughput (§4 implied by 5 GB/s/core scan). PLAIN Int64 decode is a memcpy + validity assembly: ~8 GB/s/core (close to memory bandwidth). RLE-dictionary string decode adds dict lookup: ~2–4 GB/s/core. Target M5 ≥ 500 MB/s/core for PLAIN (achievable; 1 GB/s for sequential decode minus I/O). Design consequence: dictionary decode is the Parquet bottleneck, not compression; investing in dictionary fast-paths for group-by/join keys (bypass decode when comparing indices) is the highest-leverage optimization (Phase 12 §24, ADR-09).

  7. Validity bitmap overhead (§4: bitmap always present). 1 bit/slot → 1 MB validity data per 8 M rows. For a 64Ki morsel: 8 KB bitmap / 512 KB Int64 data = 1/64 ≈ 1.6% overhead. SIMD popcount on 64-byte bitmap chunks processes 512 bits per instruction. Design consequence: bitmap overhead is small (~1.6% for 8-byte values, smaller for wider types); the all-valid fast path (omit bitmap when null_count == 0, §4) is a bandwidth optimization, not a correctness necessity (Phase 0 §12, I15).

  8. Memory amplification budget (§4: spill at 80% of budget). A group-by over 500 M rows, 8 B key + 16 B value = 24 B/row = 12 GB input. With 8 GB budget (80% = 6.4 GB usable): 8 partitions × 800 MB each fit. At 1 M groups × 48 B state = 48 MB table overhead per partition — negligible. Input > 6.4 GB triggers spill; spill writes IPC batches (Phase 13 §25). Design consequence: the MemoryPool reservation granularity must track input data size, not just hash table size.

  9. C Data Interface round-trip cost (§11.7: zero-copy export). Exporting a 1 M row Int64 array: pointer hand-off + ArrowSchema string copy < 1 µs. A copy alternative (serialize→transmit→deserialize) at 8 MB/array and 8 GB/s memory bandwidth = ~1 ms. Zero-copy is 1000× faster for large arrays. Design consequence: FFI export must never serialize; the release callback drops the Arc in O(1), not O(n) (Phase 13 §25, ADR-20).

  10. CSV schema inference cost (§24.2: scan first N rows). Scanning 1000 header rows of a 1 M row CSV at 64 Ki rows/batch = 15 batches, each requiring dtype widening checks. Total inference time < 5 ms at 100 MB/s parse rate for 1000 rows × 100 cols × 10 B/cell = 1 MB scanned. Design consequence: inference sample size must be configurable — a wide heterogeneous file requires more rows; a narrow well-typed file needs fewer. Never re-scan the full file for inference (Phase 12 §24).

Alternative Architectures (Roads Not Taken)

Row-Oriented Eager with Object Dtype

 Source
   |
   v
[row 0: {a: PyObj, b: PyObj, c: PyObj}]
[row 1: {a: PyObj, b: PyObj, c: PyObj}]
   ...
BlockManager (per-dtype block consolidation)
   |
   v
 Operation → new consolidated block

Wins when: data is small (< 1 M rows), schema is highly heterogeneous (mixed types per cell), and the primary operation is single-row mutation or lookup rather than columnar scan. Also wins when Python ergonomics and ecosystem integration dominate performance requirements.

Embodied by: pandas (BlockManager + object dtype).

Why rejected here: per-row Python object overhead defeats SIMD vectorization; GC pauses mid-scan are incompatible with the 5 GB/s/core target (§4); object dtype stores Python heap pointers, not contiguous typed values, making SIMD impossible and cache utilization poor.

Compiled / JIT Data-Centric Codegen

 LogicalPlan
      |
      v
  Code generator (LLVM IR / C++)
      |  (compile per query)
      v
 Specialized binary: fused scan+filter+agg
  — no operator boundaries —
      |
      v
 Result

Wins when: the same query shape is executed many times (OLAP dashboards, repeated ETL), the JIT amortization cost is acceptable, and operator fusion eliminates the batch-handoff overhead that vectorized interpretation pays at every operator boundary. Also wins when the query is compute-bound with a simple access pattern (no joins, pure aggregation).

Embodied by: HyPer / Umbra (Neumann VLDB 2011), DuckDB adaptive compilation.

Why rejected here: JIT compilation adds LLVM/codegen infrastructure complexity and latency that is unacceptable for a library embedding in a host process with < 50 ms cold-start requirement (§4). The vectorized interpreter (ADR-06) achieves >80% of JIT throughput with much lower implementation cost; JIT is explicitly tracked in the Deferred Features Register.

Pull-Based Volcano Tuple-at-a-Time

 sort.next()
   └─ hash_join.next()
        └─ filter.next()
             └─ scan.next()  → one tuple

Wins when: result sets are tiny (OLTP point lookups), the query is highly selective (< 100 rows survive), and the dispatch overhead per next() call is negligible relative to the I/O cost of the index lookup that dominates. Also wins for simple, deeply pipelined streaming queries where back-pressure per-tuple is required.

Embodied by: PostgreSQL executor (Graefe TKDE 1994), original Volcano/Cascades.

Why rejected here: one virtual dispatch per row per operator is the exact overhead that columnar batch execution eliminates. At 1 B rows, a naïve Volcano design pays ~1 B virtual calls per operator level. The §4 throughput targets (≥ 5 GB/s/core, ≥ 50 M rows/s group-by) are physically impossible under per-row dispatch without JIT compilation. Morsel-driven vectorized execution (ADR-06, Leis et al. SIGMOD 2014) amortizes dispatch over 64Ki-row batches.

Push-Based Morsel Pipeline (Velox / HyPer style)

 ScanExec --push--> FilterExec --push--> HashAggExec
                                              |
                                         finalize()

Wins when: the operator graph is known at plan time, back-pressure is managed per-pipeline-breaker rather than per-batch channel, and the push model reduces the buffering overhead between operators that pull-based streaming channels require. Also wins when constant-vector encoding (a null column, a broadcast literal) can propagate lazily through the push path without materializing.

Embodied by: Velox (Meta), HyPer Umbra push-based execution model.

Why rejected here: a pull-based RecordBatchStream (ADR-06) integrates more naturally with Rust's iterator model and the rayon work-stealing executor, which is pull-at-morsel-granularity. The push model requires explicit operator state machines and pipeline break synchronization that increase implementation complexity for the same throughput; the Velox encoding hierarchy (flat/constant/dictionary lazy propagation) is deferred as a future optimization.
