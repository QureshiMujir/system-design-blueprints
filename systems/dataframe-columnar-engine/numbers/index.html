Back-of-Envelope Capacity Model

  1. Single-core memory bandwidth bound (§4: ≥ 5 GB/s/core scanned). An AVX2 core on a 30 GB/s NUMA socket has ~15 GB/s solo bandwidth. A scan kernel reading only data buffers (no validity on all-valid arrays) approaches ~10 GB/s at 64-B stride. Target 5 GB/s/core accommodates multi-core sharing. Design consequence: null-check elimination on all-valid batches (ADR-05 fast path, Phase 3 §15) is mandatory to stay bandwidth-bound, not dispatch-bound.

  2. Morsel working-set vs. L2 cache (§4: default 65 536 rows). An Int64 column of 65 536 values = 65 536 × 8 B = 512 KB. L2 is typically 256 KB–1 MB/core. Two Int64 columns per morsel ≈ 1 MB, fitting L2/L3 boundary. Design consequence: the 64Ki default is the correct cache-resident operating point; wider schema or wider types require tuning down morsel size (§4 tunable 1 024–262 144).

  3. Group-by hash table size at mid cardinality (§4: ≥ 50 M rows/s). 1 M distinct groups × (16 B key + 32 B accumulator state) = 48 MB per partition; 8 partitions (8 cores) = 48 MB each, cache-warm. At 50 M rows/s per core and 8 cores = 400 M rows/s aggregate — consistent with the §4 target at mid cardinality. High-cardinality (100 M groups) → 4.8 GB table → spill required (Phase 13 §25). Design consequence: per-partition table sizing sets the spill threshold.

  4. Join build-side memory (§4: ≥ 50 M probe rows/s/core). A 100 M row build table, 8 B key + 8 B row ptr = 16 B/row → 1.6 GB. Default 80% of --mem-budget (§4). At 8 GB budget → 6.4 GB available → fits. At 2 GB budget → grace hash join spill required. Probe at 50 M rows/s/core × 8 cores = 400 M probe rows/s; probe is pointer-chase-bound, not bandwidth-bound. Design consequence: build-side estimation drives whether broadcast or partition strategy is chosen (Phase 7 §19).

  5. Parquet row-group skip benefit (§4: ≥ 50% skipped on selective filters). Default row group = 128 MiB (§4). A 10 GB file = 80 row groups. A timestamp predicate with 10% selectivity and well-clustered data should skip ≥ 70% of row groups. At 128 MiB/RG × 80 × 0.30 read = 3.1 GB bytes scanned vs. 10 GB full scan = 69% I/O reduction. Design consequence: row-group size must not be too small (metadata overhead dominates) nor too large (skip granularity coarsens). 128 MiB balances both (§4).

  6. Parquet decode throughput (§4 implied by 5 GB/s/core scan). PLAIN Int64 decode is a memcpy + validity assembly: ~8 GB/s/core (close to memory bandwidth). RLE-dictionary string decode adds dict lookup: ~2–4 GB/s/core. Target M5 ≥ 500 MB/s/core for PLAIN (achievable; 1 GB/s for sequential decode minus I/O). Design consequence: dictionary decode is the Parquet bottleneck, not compression; investing in dictionary fast-paths for group-by/join keys (bypass decode when comparing indices) is the highest-leverage optimization (Phase 12 §24, ADR-09).

  7. Validity bitmap overhead (§4: bitmap always present). 1 bit/slot → 1 MB validity data per 8 M rows. For a 64Ki morsel: 8 KB bitmap / 512 KB Int64 data = 1/64 ≈ 1.6% overhead. SIMD popcount on 64-byte bitmap chunks processes 512 bits per instruction. Design consequence: bitmap overhead is small (~1.6% for 8-byte values, smaller for wider types); the all-valid fast path (omit bitmap when null_count == 0, §4) is a bandwidth optimization, not a correctness necessity (Phase 0 §12, I15).

  8. Memory amplification budget (§4: spill at 80% of budget). A group-by over 500 M rows, 8 B key + 16 B value = 24 B/row = 12 GB input. With 8 GB budget (80% = 6.4 GB usable): 8 partitions × 800 MB each fit. At 1 M groups × 48 B state = 48 MB table overhead per partition — negligible. Input > 6.4 GB triggers spill; spill writes IPC batches (Phase 13 §25). Design consequence: the MemoryPool reservation granularity must track input data size, not just hash table size.

  9. C Data Interface round-trip cost (§11.7: zero-copy export). Exporting a 1 M row Int64 array: pointer hand-off + ArrowSchema string copy < 1 µs. A copy alternative (serialize→transmit→deserialize) at 8 MB/array and 8 GB/s memory bandwidth = ~1 ms. Zero-copy is 1000× faster for large arrays. Design consequence: FFI export must never serialize; the release callback drops the Arc in O(1), not O(n) (Phase 13 §25, ADR-20).

  10. CSV schema inference cost (§24.2: scan first N rows). Scanning 1000 header rows of a 1 M row CSV at 64 Ki rows/batch = 15 batches, each requiring dtype widening checks. Total inference time < 5 ms at 100 MB/s parse rate for 1000 rows × 100 cols × 10 B/cell = 1 MB scanned. Design consequence: inference sample size must be configurable — a wide heterogeneous file requires more rows; a narrow well-typed file needs fewer. Never re-scan the full file for inference (Phase 12 §24).
