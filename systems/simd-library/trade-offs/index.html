Decisions (§9) · 24 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+

Rejected

C++17; C11

When the rejected choice is right

Existing C++ engine requires header-only drop-in with no FFI boundary tolerance

Why: unsafe boundary discipline + const generics + no_std

ADR-02

Public vector-width encoding

Chosen

const generics Simd<T, const LANES: usize>

Rejected

macro-generated per-width structs; dynamic runtime-width objects

When the rejected choice is right

Lane count only known at runtime with no fixed ABI target (pure-SVE deployment, §17)

Why: monomorphized zero-cost, compiler-checked lane count

ADR-03

Runtime dispatch mechanism

Chosen

cpuid probe + cached fn-ptr table (simd-dispatch)

Rejected

compile-time -C target-cpu only; ELF ifunc resolver

When the rejected choice is right

Single known deployment target with reproducible build host == run host (embedded firmware image)

Why: portable across build/ship machine mismatch

ADR-04

x86 intrinsic binding

Chosen

core::arch::x86_64 stable intrinsics

Rejected

raw inline asm; FFI to a C intrinsics shim

When the rejected choice is right

An intrinsic has no stable Rust binding yet (bleeding-edge sub-extension) — forces inline asm fallback

Why: stability guarantee across Rust releases

ADR-05

AVX-512 mask representation

Chosen

native __mmask8/16/32/64 k-register wrapper

Rejected

emulate with all-ones/all-zeros lane blend

When the rejected choice is right

Targeting AVX2-only hardware where no k-registers exist — blend emulation is the only option

Why: matches hardware predication, avoids extra blend instructions

ADR-06

ARM scalable-vector handling

Chosen

NEON fixed-width now; SVE behind sve feature flag as a VLA type

Rejected

ignore SVE entirely, NEON-only

When the rejected choice is right

Target CPU confirmed NEON-only — feature flag stays off, zero code-size cost

Why: SVE hardware is real (Fugaku A64FX, Neoverse V-series) and needed for scalable throughput

ADR-15

Chosen

Rejected

When the rejected choice is right

Backend has a single-instruction horizontal reduction verified equal to the tree order — the intrinsic wins for that backend only, gated by a fixture

ADR-16

Chosen

Rejected

When the rejected choice is right

Emulation cost exceeds the scalar baseline by >2× on a hot path — caller wins by dropping to a simd-memory scan primitive instead

ADR-17

Conformance oracle

Chosen

Rejected

When the rejected choice is right

A backend's rounding diverges from the oracle by explicit design (fast-math FMA) — the divergence itself is the fixture, not the oracle

Why: single source of truth independent of any backend (I1, I12)

ADR-18

Chosen

Rejected

When the rejected choice is right

Why: avoids surprising a caller's unrelated float code (P3, P6)

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

A1 — Compiler-autovectorization-only (no explicit SIMD types)

 source loop (scalar) → compiler autovectorizer (-O3, -march=native) → object code

Wins in the regime of small, rarely-changed hot loops where developer time is scarcer than the occasional 2-5x miss when the autovectorizer fails to vectorize. Real system: GCC/LLVM's built-in autovectorization pass (Nuzman & Zaks 2006, §5). Rejected: fragile — a compiler upgrade or an unrelated refactor can silently de-vectorize a loop with no build failure (§2, P13); this project exists specifically because that fragility is unacceptable for a library other systems depend on.

A2 — SPMD compiler frontend (ISPC-style)

 .ispc kernel source → ispc compiler → object code (separate toolchain from the host language)

Wins when a team is willing to adopt a dedicated data-parallel language and toolchain in exchange for the compiler handling backend selection and lane-width portability automatically. Real system: Intel's ISPC (SPMD Program Compiler). Rejected: introduces a second compiler/toolchain dependency and a foreign-function boundary into every consumer's build, which conflicts with §1's "consumed at compile time by a normal Rust dependency" deployment model.

A3 — GPU-first vector compute

 host code → CUDA/SYCL kernel dispatch → GPU SIMT execution → result transfer back to host

Wins for embarrassingly-parallel, large-batch numerical workloads where host-device transfer cost is amortized over massive data volume. Real system: NVIDIA CUDA. Rejected: wrong regime entirely — this project targets CPU-resident, low-latency, per-call vectorization (database scans, string matching) where a PCIe/NVLink round-trip would dominate the cost the library exists to eliminate.

A4 — JIT-specialized runtime codegen

 IR template → JIT compiler (LLVM ORC-class) → machine code specialized to the running CPU

Wins when the exact CPU is unknown until runtime and the kernel is complex/varied enough that a hand-written multiversioned table (ADR-23) becomes unmaintainable — the JIT effectively becomes the dispatch mechanism. Real system: Numba (LLVM-based JIT for numerical Python). Rejected: JIT warmup cost and deployment complexity (embedding an LLVM-class compiler in every consumer binary) contradict §1's zero-daemon, static-link deployment model; explicitly PhaseDeferred("§1") under "JIT specialization."
