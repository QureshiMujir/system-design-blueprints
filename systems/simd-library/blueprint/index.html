181 — SIMD Library from Scratch

Project Number: 181

Project Name: SIMD Library from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from first principles, a portable explicit-SIMD abstraction library exposing fixed-width vector types (Simd<T, LANES>) and a scalable-vector type (SveVector<T>) over four hardware ISA families — x86 SSE2/SSE4.2/AVX2/AVX-512F/BW/VL and ARM NEON/SVE — with runtime CPU-feature detection, function multi-versioning/dispatch, masked/predicated execution, shuffles/swizzles/ blends, gather/scatter, FMA, reductions, explicit alignment control, and a differential- conformance + fuzzing + benchmarking harness proving backend-to-backend semantic equivalence. The deliverable is a ten-crate Rust workspace consumable by numeric, database, and codec projects without their authors touching an intrinsic directly.

Phase 0 deliverable

  1. simd-core — vector/mask trait system, lane abstractions, alignment API, scalar reference backend (the conformance oracle, ADR-17).
  2. simd-common — shared error types, feature-flag macros, portability shims.
  3. CI skeleton — cross-arch build matrix (x86_64, aarch64), lint/fmt gates (ADR-09).
  4. conformance/ harness skeleton — golden-fixture runner wired to the scalar backend only.
  5. docs/adr/ — ADR log seeded with ADR-01, ADR-02, ADR-09, ADR-11, ADR-19.

System boundaries

  • Provides: vector types, masks, lane arithmetic, shuffles, reductions, gather/scatter, FMA, alignment control, CPU-feature detection, dispatch, vectorized memcpy/memcmp/memset/scan, polynomial math kernels, conformance/fuzz/bench harness.
  • Delegates: OS memory allocation (via simd-core::AlignedVec wrapping std::alloc), process scheduling, NUMA placement (documented in §29, not managed).
  • Does NOT provide: GPU backends, JIT/runtime codegen, BLAS/FFT/tensor kernels, sparse-vector formats, kernel-fusion planners, an autovectorizing frontend, WASM/RISC-V backends — all PhaseDeferred("§1"), registered at §35.

Non-goals

Not a compiler. Not a numerical library (no BLAS/LAPACK). Not a general autovectorizer. Not a GPU compute stack. Not a database or query engine — it supplies primitives those systems call.

Deployment model

Statically linked Rust library crates (rlib / staticlib / cdylib for FFI consumers). No daemon, no network surface. Consumed at compile time; backend selection resolved once at process start (§18).

Target users

Systems, database, ML-runtime, and codec engineers building CPU-bound vectorized kernels who need portable intrinsics without per-ISA rewrites.

Language + rationale

Rust 1.78+. Rationale: stable core::arch intrinsics, const generics for LANES, an explicit unsafe boundary discipline enforceable by the compiler, no_std capability, zero-cost trait monomorphization. Rejected: C++ (ADR-01 — no compiler-enforced memory-safety boundary at the API edge, header-only intrinsics sprawl); C (no generics, manual per-width duplication); Zig (immature SIMD intrinsics coverage at project inception).

Prerequisites

CPU architecture and cache hierarchy; two's-complement / IEEE-754 arithmetic; x86 and ARM assembly literacy; Rust unsafe; compiler optimization passes (autovectorization, inlining); statistics for benchmark noise floors.

PhaseDeferred("§1"): GPU vector backend, auto-vectorizing compiler frontend, tensor operations, BLAS integration, FFT kernels, sparse vector operations, automatic kernel fusion, WASM SIMD128 backend, RISC-V RVV backend. Full register with anchors and un-defer triggers at §35.

2. Why Build This

Every database engine (columnar scans), ML runtime (tensor kernels lowering to SIMD GEMM microkernels), compression library (bit-unpacking), search engine (SIMD string scanning), and media codec (block transforms) is, underneath, a thin orchestration layer over vectorized loops that most of their own authors never hand-write — they call a SIMD library (Google Highway, xsimd, Agner Fog's VCL, or a std::simd-family type) instead. Building the library, rather than merely using one, forces contact with lane packing, shuffle-network topology, mask-register propagation, alignment-fault cost, gather/scatter latency, execution-port contention, and CPU-feature multiversioning that a consumer never sees. Architecturally this project sits at the same layer as Highway and Intel's own Intrinsics Guide: an ABI-stable, portable vector type over heterogeneous ISAs — precisely the problem WG21's std::simd proposal (Kretz's P0214, itself descended from his 2015 PhD thesis and the Vc library) standardized for C++, and that Rust's std::simd (formerly packed_simd) nightly effort tackles in parallel. Cross-links: Project 181 supplies the vectorized-scan primitive a Database Engine's columnar executor calls, the SIMD string-match primitive a Regex Engine needs, the vectorized bit-unpack a Compression Runtime needs, and the polynomial math kernels an ML Runtime's activation functions need.

What Mastery Looks Like

  • Explain why AVX-512 mask registers (k0–k7) are architecturally distinct from an SSE/AVX all-ones-lane mask, and why that difference forces ADR-05's backend-specific mask representation (Phase 4, §16).
  • Derive, from clock speed and execution-port count alone, the theoretical vector-add throughput ceiling for a backend without running a benchmark (Phase 9, §21; §32).
  • Explain why floating-point reduction is not associative, and why a fixed reduction-tree order is required for cross-backend bit-reproducibility (Phase 7, §19; I7).
  • Diagnose an alignment fault from its SIGBUS/SIGILL signature and identify which backend's aligned-load intrinsic caused it (Phase 0/2, §12/§14; FM-3).
  • Explain SVE's vector-length-agnostic (VLA) programming model and why it cannot be expressed with a const LANES fixed-width type (Phase 5, §17).
  • Design a CPU-feature dispatch table that resolves once and stays correct under a multi-threaded first-use race (Phase 6, §18; I5, I13).
  • Explain why a scalar reference implementation is the conformance oracle — not "whatever the fastest backend computes" (Phase 9, §21; I1, I12).
  • Explain the AVX-512 downclock cliff and why a theoretical-peak throughput claim without measured-on-silicon confirmation is not credible (Phase 4, §16; §32).

Client Applications — external consumers; never link against simd-x86/simd-arm directly, only against simd-core/simd-math/simd-memory (P1).

Public SIMD API — the only stable, backend-agnostic surface; monomorphizes to zero-cost machine code per P4; owns the Mask canonical bit representation (P6, I2).

Runtime Dispatch — resolves exactly one Backend per process, cached in a OnceLock (I5, I13); the sole place any #[cfg(target_arch)]-style decision happens outside crate boundaries.

Architecture Backends — simd-x86 and simd-arm share zero code beyond simd-core trait implementations (P8); each independently conformance-tested against the scalar oracle (ADR-17).

Intrinsics Layer — every intrinsic call is wrapped behind a #[target_feature]-gated safe function (P2, I6); this is the only layer touching raw unsafe.

Hardware Execution — vector ALU ports, register files, and the cache hierarchy quantified in §4 and modeled in §32; not controlled by this library, only measured (§28).

Trust boundary: the Intrinsics Layer is the sole trust boundary — everything above it is proven memory-safe by the type system; everything at or below requires the SDM/ARM-ARM semantic proof cited in P12.

Concurrency boundary: dispatch resolution is a single OnceLock write race (T4) with an otherwise stateless, purely functional kernel surface — no other shared mutable state exists.

Persistence boundary: this library holds no persistent state; the only artifacts written to disk are conformance/fixtures.lock (I12) and benchmark/profiling reports (§24).

6. Design Principles

P1 — Portable API, Specialized Backend. Rule: public types (Simd<T,LANES>, Mask<T,LANES>) are backend-agnostic; every backend implements the same trait surface. Tradeoff: lowest-common-denominator API can't expose a backend-unique op directly. Operational implication: adding a backend never touches caller code. Violation breaks: callers hardcode #[cfg(target_arch)] and portability collapses.

P2 — Unsafe Internals, Safe Surface. Rule: every intrinsic call is wrapped in a safe function that proves its preconditions (feature detected, pointer aligned) before invoking unsafe. Tradeoff: wrapper indirection depends on the compiler inlining correctly. Operational implication: #[inline(always)] is mandatory on every wrapper. Violation breaks: undefined behavior escapes the crate boundary into caller code (I6).

P3 — Explicit Alignment Semantics. Rule: every load/store API states its alignment contract in its name (load_aligned vs load_unaligned); nothing is implicit. Tradeoff: two entry points per op instead of one. Operational implication: AlignedVec<T,ALIGN> (ADR-11) is the default allocation path. Violation breaks: silent misaligned loads fault or silently fall to a microcoded slow path (FM-3).

P4 — Zero-Cost Abstractions. Rule: Simd<T,LANES> must compile to the same assembly as hand-written intrinsics for the equivalent op. Tradeoff: forces #[inline(always)] everywhere and forbids virtual dispatch inside the hot type. Operational implication: every new op needs a disassembly-diff check in CI (§27). Violation breaks: a silent 2–5× regression invisible until §28 gating catches it.

P5 — Runtime Dispatch Must Be Predictable. Rule: the dispatch decision resolves once per process, never per call. Tradeoff: cannot react to mid-run thermal throttling. Operational implication: the dispatch cache is a OnceLock<Backend> (I5, I13). Violation breaks: per-call cpuid probing adds ~20–100 ns overhead to every vector op (M4).

P6 — Deterministic Mask Semantics. Rule: a Mask<T,LANES> means the same per-lane predicate regardless of backend representation (bitmask vs all-ones lane). Tradeoff: the AVX-512 backend must convert its native k-mask to/from the canonical representation at the API boundary. Operational implication: Mask::to_bits()/from_bits() are the only conversion points (I2). Violation breaks: a mask built on one backend and consumed after a dispatch fallback silently flips lanes.

P7 — Benchmark Everything. Rule: no kernel merges without a criterion benchmark and a recorded M# baseline. Tradeoff: benchmark suite runtime grows with kernel count. Operational implication: the §28 perf-regression gate blocks merges on >5% regression. Violation breaks: performance rot accumulates invisibly — speed is the entire point of the library.

P8 — Backend Isolation. Rule: simd-x86 and simd-arm share zero code beyond simd-core traits; no cross-#[cfg] leakage. Tradeoff: some logic (e.g. polynomial coefficients) is duplicated per backend module. Operational implication: each backend crate compiles and tests independently on its own target. Violation breaks: a fix in one architecture's branch silently breaks another (FM-7).

P9 — Cache-Awareness Is Not Optional. Rule: every memory-touching kernel (simd-memory) documents its expected cache-line and prefetch behavior. Tradeoff: tuning for one cache hierarchy can be suboptimal on another. Operational implication: simd-bench records per-microarchitecture results, not one global number (§28). Violation breaks: throughput claims that hold in L1 collapse past the L2/L3/DRAM boundary (§32).

P10 — Correctness Before Throughput. Rule: a backend cannot ship until it passes 100% of conformance/ against the scalar oracle (ADR-17). Tradeoff: a correct-but-slow backend blocks a fast-but-unverified one from merging alone. Operational implication: §26 gates conformance before performance in CI ordering. Violation breaks: a faster-but-wrong backend ships silently corrupt results downstream (I1).

P11 — Fixed-Width First, Scalable Second. Rule: Simd<T,LANES> is the default API; SVE's vector-length-agnostic model is opt-in via the distinct SveVector<T> type (ADR-06). Tradeoff: SVE code cannot share the const-generic trait impls used by fixed-width backends. Operational implication: SVE kernels are written once against the VLA API and run correctly at any hardware VL. Violation breaks: hardcoding a lane count for SVE breaks on any VL it wasn't tested on (I9).

P12 — No Invented Intrinsics — ISA Fidelity. Rule: every intrinsic name and semantic cited resolves to an entry in the Intel Intrinsics Guide, Intel SDM, or Arm Architecture Reference Manual; nothing is guessed. Tradeoff: an op with no direct hardware instruction must be built from documented primitives, never assumed. Operational implication: the docs/ intrinsic cross-reference (ADR-24) is the enforcement point. Violation breaks: shipping a fabricated intrinsic call fails to compile or, worse, silently misassembles.

P13 — Multiversioning Over Speculative Autovectorization. Rule: performance-critical kernels are explicit-SIMD and multi-versioned per backend (ADR-23), never left for the compiler's autovectorizer to discover. Tradeoff: more source per kernel (N backend variants) vs one portable scalar loop. Operational implication: simd-dispatch owns backend selection; the compiler never guesses. Violation breaks: a compiler upgrade silently de-vectorizes a hot loop with no build failure (§2, Nuzman & Zaks 2006).

8. Domain Model / Protocol / Data Model

Vector layout grammar

FixedVector   ::= "Simd<" Type "," LANES ">"          ; LANES: usize, power-of-two, compile-time
ScalableVector::= "SveVector<" Type ">"                ; VL resolved at runtime (I9)
Mask          ::= "Mask<" Type "," LANES ">"           ; canonical storage: bitset <= 64 bits (P6)
LaneOp        ::= "add" | "sub" | "mul" | "min" | "max"
                | "bitand" | "bitor" | "bitxor" | "not"
ShuffleOp     ::= "permute" | "interleave" | "broadcast" | "extract" | "zip" | "blend"
ReduceOp      ::= "sum" | "product" | "min" | "max" | "all" | "any" | "none"

Lane operations (§13/§19)

Elementwise arithmetic/bitwise ops apply LaneOp independently per lane; comparisons produce a Mask (P6); ShuffleOp rearranges lanes without changing lane values; ReduceOp collapses a vector to one scalar or boolean via the fixed pairwise-tree (I7) except boolean all/any/none, which use a boolean AND/OR tree.

Mask semantics — worked example

Input vector Simd<f32,4> = [1.0, -2.0, 3.0, -4.0]. Comparison simd_gt(0.0) yields Mask<f32,4> with canonical bits 0b0101 (lane 0 and lane 2 true, per I2). On an AVX backend this materializes as an all-ones/all-zeros per-lane pattern; on AVX-512 as a native k-register value 0b0101; both convert to the same canonical bits via to_bits() (P6).

Malformed-input example

A caller passes a 6-element &[f32] slice to Simd::<f32,8>::try_from(slice). LANES=8 requires exactly 8 elements; TryFrom returns Err(ConversionError::LengthMismatch { expected: 8, got: 6 }) — no partial read, no padding invented (T1).

Failure-path example

A binary is built with target-feature=+avx2 and deployed, pre-Phase-6, without going through simd-dispatch (i.e. calling simd-x86::avx2 directly). Run on an SSE2-only host: the missing #[target_feature] runtime guard means the instruction stream contains an unsupported opcode and the process receives SIGILL (T3, FM-1). Post-Phase-6, the same scenario instead resolves through CpuFeatures::detect() and the dispatch fallback chain lands on Backend::Scalar (I10) — this is why the Repository Layout (§10) forbids client crates from depending on simd-x86/simd-arm directly (P1).

11. Core Schema & Types

// simd-core — fixed-width vector (owned, Copy, no interior mutability)
pub struct Simd<T: SimdElement, const LANES: usize> { lanes: [T; LANES] }

// simd-core — canonical mask, backend-representation-independent (P6, I2)
pub struct Mask<T: SimdElement, const LANES: usize> { bits: u64 } // valid bits: 0..LANES

// simd-arm — scalable vector, VL resolved at runtime (P11, I9); not Copy across VL boundaries
pub struct SveVector<T: SimdElement> { handle: SveHandle, vl_bytes: usize }

// simd-dispatch — resolved once, cached (I5, I13)
pub enum Backend { Scalar, Sse2, Sse42, Avx2, Avx512, Neon, Sve }

pub struct CpuFeatures {
    pub sse2: bool, pub sse42: bool, pub avx2: bool,
    pub avx512f: bool, pub avx512bw: bool, pub avx512vl: bool,
    pub neon: bool, pub sve: bool,
}

// simd-core — trait every backend implements identically (P1, P4)
pub trait SimdOps<T: SimdElement, const LANES: usize>: Sized + Copy {
    fn add(self, rhs: Self) -> Self;
    fn sub(self, rhs: Self) -> Self;
    fn mul(self, rhs: Self) -> Self;
    fn min(self, rhs: Self) -> Self;
    fn max(self, rhs: Self) -> Self;
    fn select(mask: Mask<T, LANES>, a: Self, b: Self) -> Self;
    fn reduce_sum(self) -> T;   // fixed pairwise-tree order (ADR-15, I7)
    fn reduce_product(self) -> T;
}

// simd-core — shuffle/swizzle surface (§8 grammar)
pub trait SimdShuffle<T: SimdElement, const LANES: usize> {
    fn permute(self, indices: [u32; LANES]) -> Self;
    fn interleave(self, rhs: Self) -> (Self, Self);
    fn broadcast(scalar: T) -> Self;
    fn extract(self, lane: usize) -> T;
    fn zip(self, rhs: Self) -> Self;
}

// simd-memory — gather/scatter signature (I8 masked-touch contract)
pub trait SimdGatherScatter<T: SimdElement, const LANES: usize> {
    fn gather(base: *const T, indices: Simd<i32, LANES>, mask: Mask<T, LANES>) -> Simd<T, LANES>;
    fn scatter(base: *mut T, indices: Simd<i32, LANES>, mask: Mask<T, LANES>, values: Simd<T, LANES>);
}

// simd-core — alignment-typed allocation (P3, ADR-11)
pub struct AlignedVec<T, const ALIGN: usize> { ptr: core::ptr::NonNull<T>, len: usize, cap: usize }
// simd-math — scoped denormal-mode guard (ADR-18, I14)
pub struct DenormalMode { previous: u32 } // restores ambient FPCR/MXCSR on Drop

// simd-common — error types
pub enum ConversionError { LengthMismatch { expected: usize, got: usize } }
pub enum AlignmentError { Misaligned { required: usize, actual: usize } }
pub enum DispatchError { NoBackendAvailable }

Ownership: Simd<T,LANES> is Copy (register-sized, ≤64 bytes) — never heap-allocated. Mask is Copy, stored as a u64 bitset regardless of backend (P6). SveVector<T> is intentionally not Copy across VL boundaries — cloning re-queries VL. AlignedVec owns a heap allocation with a custom Drop deallocating at ALIGN. Concurrency: every type here is Send + Sync when T is; no interior mutability anywhere except the dispatch-cache OnceLock (§18). Serialization: fixture types (not shown) use postcard (ADR-12); core vector types have no serialization impl — serialize the underlying array instead.

  • k-mask register exhaustion — only 8 available — when a kernel needs more live masks than registers.

16.7 Performance Concerns

M2 gate; frequency throttling under sustained 512-bit heavy-instruction use must be measured on real silicon, not assumed from theoretical peak (§32 flags this explicitly).

16.8 Edge Cases

  • LANES=16 f32 (full 512-bit) vs LANES=8/LANES=4 (AVX-512VL narrower encodings) sharing one generic trait impl.

  • k-mask value 0 (all-inactive) must short-circuit cleanly, never fault.

16.9 Failure Analysis

FM-6 (gather/scatter OOB touch) is most likely to surface first here — AVX-512's masked-gather semantics are the most complex predication contract in the library; the ASAN/MSAN fixture (T5) is mandatory before merge.

16.10 Operational Notes

AVX-512 CI must run on self-hosted bare metal (ADR-09 exception) since hosted runners lack AVX-512 at authoring time — tracked as a build-pipeline risk in §27.

24. Operational Readiness

Metrics: every dispatch decision, kernel call, and fixture run emits a counter/histogram per the Telemetry columns of §7/§22/§23 (tracing spans, ADR-20); the M#-table (§28) is the release scoreboard.

Tracing: one tracing span per dispatch decision (I13, ADR-20), tagged with the resolved Backend and the CpuFeatures snapshot hash.

Structured logging: fixture failures log the fixture name, backend, input seed, and expected vs actual result — sufficient to reproduce without re-running the full suite.

Dashboards: §28's M# table plotted per release tag; §23's FM-# counters plotted per CI run to catch a rising alignment.fault or dispatch.race_detected trend before it becomes an incident.

SLOs: M4/M5 (dispatch overhead), M11 (conformance wall-clock), M12 (fuzz soak) are release SLOs — a release does not tag if any is missed (§27).

Runbooks (docs/runbooks/): "FM-1 unsupported-backend selection" runbook uses simd-cli inspect-features (§18) to confirm the deployed host's CpuFeatures against the binary's build-time target-feature set. "FM-3 alignment fault" runbook uses the core-dump faulting address to identify the offending call site.

Backup/restore: not applicable — the library holds no persistent runtime state; the only durable artifacts are conformance/fixtures.lock (versioned in git, I12) and release SBOMs (§27).

Deployment topology: statically linked into the consumer's binary (§1); no independent deployment unit to canary.

Canary/rollback/migration: canarying happens at the consumer's release level by pinning to a previous simd-* SemVer (ADR-19); rollback is a Cargo.lock revert; migration across a major version follows the deprecation policy in §25.

25. Compatibility & Versioning

API stability: simd-core's public trait surface (§11) is the stability boundary; a breaking change requires a major SemVer bump across the whole workspace (ADR-19 exception clause).

SemVer: per-crate SemVer, workspace-locked minor versions (ADR-19); patch releases never touch conformance/fixtures.lock without an explicit re-approval (I12).

Deprecation: a deprecated API is marked #[deprecated(since, note)] for one full minor-version cycle before removal; removal is a major bump.

Backend addition compatibility: adding a new backend (e.g. RISC-V RVV, post-v1) never requires a simd-core breaking change per P1 — the new backend crate implements the existing trait surface.

Fixture evolution: conformance/fixtures.lock changes are versioned alongside the fixture corpus; a fixture removal requires the same re-approval workflow as an addition (I12).

Rolling-upgrade guarantee: because this is a statically linked library with no wire/storage format, there is no server-side rolling-upgrade concern; the guarantee that matters is build-reproducibility (§27) across a consumer's staged rollout of a new simd-* version.

Cross-backend result stability: I7's pairwise-tree contract is itself a compatibility guarantee — a minor-version upgrade must never change a previously bit-identical reduction result without a major bump.

26. Testing & Verification Strategy

Unit: per-op unit tests inside each backend crate, independent per P8.

Integration: conformance/ cross-crate differential tests wiring simd-dispatch end to end (§21).

Property-based: proptest trait-law checks from Phase 1 (§13) — associativity, identity, NaN-comparison laws.

Differential: every backend vs the scalar oracle (ADR-17, I1) and every backend vs every other backend (diff_backend.rs, §21) — the primary correctness gate (P10).

Fuzzing: cargo-fuzz targets fuzz_masks, fuzz_alignment, fuzz_shuffle, fuzz_dispatch (ADR-10) seeded from hand-written corpora, run continuously and for a 24h soak per release (M12).

Chaos / concurrency stress: dispatch_race.rs's 1000-thread concurrent-first-use test (T4) is this project's chaos-testing analog — there is no distributed-systems chaos surface otherwise.

Deterministic replay: any fixture failure logs its input seed (§24); replay reproduces byte- for-byte given the same seed and backend commit hash (I12).

Soak: M12 — 24 CPU-hours per backend per release, gating the tag (§27).

Conformance: the conformance/ suite is the umbrella term for differential + property tests; M11 bounds its wall-clock (§21).

Perf-regression gating: §28's M# table, compared release-to-release, blocks merge on >5% regression (P7) unless the noise-floor exception applies (T11, FM-8).

Traceability to invariants: every fixture named in §12–§21's N.5 tables maps to at least one I# (§7) or T#/FM-# (§22/§23) — the mapping is explicit in each phase's N.2 steps, not implicit.

27. Build & Release Engineering

Reproducible builds: Docker image with a digest-pinned base and pinned rust-toolchain.toml (ADR-21); a byte-for-byte reproducible build is a release gate for supply-chain attestation.

Signing: release tags are signed commits; published crates are cargo publish-signed per crates.io's provenance mechanism.

SBOM: generated per release via cargo-cyclonedx (or equivalent), diffed against the previous release to catch an unreviewed dependency change (T8).

Release channels: stable (SemVer-tagged), nightly (tracks simd-dispatch and any sve-feature-flagged code still stabilizing).

CI/CD topology: GitHub Actions cross-arch matrix (ADR-09) for x86_64/aarch64 baseline; a self-hosted bare-metal runner for AVX-512 (§16) and SVE (§17) gating, since hosted runners lack that hardware.

Version stamping: every built artifact embeds its simd-* crate versions and the git commit hash of conformance/fixtures.lock (I12) for post-incident forensics.

Provenance: cargo audit + cargo-deny dependency auditing on every build; a flagged advisory blocks release (T8).

Dependency auditing: workspace dependencies are reviewed against cargo-deny's license and advisory policy; new dependencies require an ADR entry if they change a locked decision (§9).

Release gate composite: a release does not tag unless §21's full differential suite is green, M11/M12 SLOs (§24) are met, SBOM diff is reviewed, and cargo audit is clean.

29. Scalability Analysis

Stays constant: per-op latency for a fixed LANES and backend (O(1) in input size for a single vector op); dispatch resolution cost after the first call (I13, O(1) amortized).

Grows: aggregate throughput scales O(N) with input size for simd-memory/simd-math kernels processing a buffer, bounded by the memory-bandwidth ceiling (§32); reduction latency scales O(log LANES) per the pairwise tree (I7, MM7).

Bottlenecks, in order: (1) DRAM/L3 bandwidth for large-buffer simd-memory kernels — the hard ceiling past cache residency; (2) execution-port contention for instruction-bound kernels (Agner Fog manual, §5); (3) alignment-fault/slow-path penalties when P3's contract is violated at the call site; (4) AVX-512 downclock cliff under sustained heavy-instruction mixes (§16); (5) gather/scatter latency, the most expensive per-lane operation across every backend (M9).

Horizontal scale: SIMD kernels parallelize across cores and NUMA nodes at the caller's level — this library provides no threading; a caller's worker-pool fans out simd-memory/ simd-math calls per shard.

Vertical scale: within one core, scaling is bounded by the widest available vector width (512-bit AVX-512, up to 2048-bit SVE VL) and by the number of execution ports issuing vector ops per cycle (§32).

Practical ceiling: DRAM bandwidth for streaming kernels (simd-memory); execution-port count × clock × lane width for compute-bound kernels (simd-math, arithmetic-heavy simd-core ops).

Levers beyond the ceiling: wider vectors (AVX-512 over AVX2, SVE over NEON) raise the compute ceiling but not the DRAM ceiling; multi-core/NUMA fan-out (caller-level) raises aggregate throughput until DRAM bandwidth is shared-saturated; cache-blocking (P9) shifts a kernel from the DRAM-bound regime into the compute-bound regime for reusable data.

30. Mental Models & First Principles

MM1 — A vector register is a fixed-size window, not a container. Predicts: tail elements (N mod LANES != 0) always need separate handling. Bug class without it: off-by-tail-length buffer overrun. Resolves: §19, §8.

MM2 — Masks are data, not control flow. Predicts: masked lanes still execute (they just don't commit), so a masked divide-by-zero can still fault on some backends. Bug class without it: assuming masked-out lanes are "skipped" like an if-branch. Resolves: §14, I8.

MM3 — Throughput and latency are different budgets. Predicts: a kernel can be latency-bound (dependency chain) even when throughput-optimal instructions are used. Bug class without it: optimizing instruction count while ignoring dependency depth. Resolves: §28, §32.

MM4 — Alignment is a promise, not a check. Predicts: an aligned-load intrinsic trusts the caller; violating the promise is UB, not a runtime error, on some backends. Bug class without it: assuming misalignment always crashes loudly (it sometimes silently slows down instead). Resolves: §12, I3.

MM5 — Dispatch cost is amortized once, semantics forever. Predicts: it is always correct to pay dispatch cost once at startup, never per hot-loop iteration. Bug class without it: re-probing CpuFeatures inside a loop. Resolves: §18, P5.

MM6 — Scalable vectors trade a compile-time constant for a runtime query. Predicts: SVE code that runs correctly at VL=128 also runs correctly, unmodified, at VL=2048. Bug class without it: baking a lane count into SVE code like fixed-width code. Resolves: §17, I9.

MM7 — Reduction order is an API contract, not an implementation detail. Predicts: two backends can both be "correct" and still disagree bit-for-bit on a float sum unless the order is fixed. Bug class without it: treating a float-sum mismatch as a backend bug instead of a missing contract. Resolves: §19, I7.

MM8 — A conformance oracle must be simpler than what it checks. Predicts: the scalar reference implementation must never itself use SIMD tricks, or it stops being an independent check. Bug class without it: an "optimized" oracle sharing the same bug as the thing it verifies. Resolves: §21, I1.

32. Back-of-Envelope Capacity Model

  1. AVX2 f32 vector-add throughput (M1 derivation): 256-bit register / 32-bit lane = 8 lanes; assume 2 vector-ALU ports issuing 1 add/cycle at 3.5 GHz → 8 × 2 × 3.5e9 = 5.6e10 f32-adds/sec × 4 bytes/lane read × 2 operands ≈ 448 GB/s of register throughput, but DRAM-bound streaming caps effective throughput far lower — M1's 40 GB/s target reflects the DRAM-bound regime, not the register-bound ceiling.

  2. AVX-512 downward adjustment (M2 derivation): 512-bit / 32-bit = 16 lanes; but sustained 512-bit "heavy" instructions historically downclock some Intel cores by ~10-20% — 16 × 2 × (3.5e9 × 0.85) ≈ 9.5e10 f32-adds/sec theoretical, M2's 70 GB/s target is the DRAM/L2-bound figure after that adjustment.

  3. NEON f32 vector-add throughput (M3 derivation): 128-bit / 32-bit = 4 lanes; assume 2 vector pipelines at ~2.5 GHz on a typical mobile/server ARM core → 4 × 2 × 2.5e9 = 2e10 f32-adds/sec register-bound; M3's 12 GB/s target is the conservative DRAM/L2-bound figure.

  4. Dispatch overhead budget (M4/M5 derivation): a cpuid instruction costs ~20-40 cycles; at 3.5 GHz that is ~6-11 ns per probe; M4's 200 ns first-call budget leaves headroom for multiple leaves + a OnceLock write; M5's <2ns cached-call budget requires the check to compile to one predictable branch or none (inlined constant after monomorphization).

  5. Mask conversion overhead: to_bits/from_bits on AVX-512 should be one kmov-class instruction (~1-3 cycles ≈ <1ns at 3.5GHz); on SSE/AVX it requires a movmsk-class instruction of similar cost — both fit well inside I2's contract with no measurable per-call tax.

  6. Reduction tree depth (M8 derivation): LANES=8 pairwise tree has log2(8)=3 levels; at ~2 cycles/level (add + shuffle) that's ~6 cycles compute + ~9 cycles latency overhead for cross-lane data movement ≈ under M8's 15-cycle target.

  7. Gather latency budget (M9 derivation): an L1-resident 8-lane gather issues up to 8 independent loads; assuming 2 load ports and ~4-cycle L1 latency with pipelining, 8 loads / 2 ports ≈ 4 issue-slots × ~4-cycle latency overlap ≈ under M9's 25-cycle target if fully pipelined; a cache-miss lane blows this budget by 50-100×, hence I8's "masked lanes never touch memory" matters for this budget too — a spuriously-touched masked lane risks an unbudgeted cache miss.

  8. SVE lane-count range (I9 basis): SVE VL ranges 128-2048 bits per the Arm SVE spec; for f32 that is 4 to 64 lanes per vector — a 16× range the fixed-width AVX-512 (16 lanes, fixed) never has to handle, which is exactly why SveVector<T> cannot be Simd<T, const LANES>.

  9. memcpy DRAM ceiling (M6 derivation): typical single-channel DDR4-3200 delivers roughly 25.6 GB/s theoretical peak; M6's 20 GB/s "L2-resident" target is set below full-DRAM peak specifically because it is scoped to the L2-resident regime (§4), not the DRAM-bound regime, where effective throughput would be lower and multi-channel-dependent.

  10. Fuzzing soak coverage (M12 basis): 24 CPU-hours at, conservatively, 10^6 fuzz executions/sec for a small kernel like a shuffle op ≈ 8.6×10^10 executions per backend per release — chosen as the point past which marginal new-crash discovery rate (per published libFuzzer coverage-plateau behavior) drops sharply for a corpus of this kernel-input complexity class.

34. Alternative Architectures (Roads Not Taken)

A1 — Compiler-autovectorization-only (no explicit SIMD types)

 source loop (scalar) → compiler autovectorizer (-O3, -march=native) → object code

Wins in the regime of small, rarely-changed hot loops where developer time is scarcer than the occasional 2-5x miss when the autovectorizer fails to vectorize. Real system: GCC/LLVM's built-in autovectorization pass (Nuzman & Zaks 2006, §5). Rejected: fragile — a compiler upgrade or an unrelated refactor can silently de-vectorize a loop with no build failure (§2, P13); this project exists specifically because that fragility is unacceptable for a library other systems depend on.

A2 — SPMD compiler frontend (ISPC-style)

 .ispc kernel source → ispc compiler → object code (separate toolchain from the host language)

Wins when a team is willing to adopt a dedicated data-parallel language and toolchain in exchange for the compiler handling backend selection and lane-width portability automatically. Real system: Intel's ISPC (SPMD Program Compiler). Rejected: introduces a second compiler/toolchain dependency and a foreign-function boundary into every consumer's build, which conflicts with §1's "consumed at compile time by a normal Rust dependency" deployment model.

A3 — GPU-first vector compute

 host code → CUDA/SYCL kernel dispatch → GPU SIMT execution → result transfer back to host

Wins for embarrassingly-parallel, large-batch numerical workloads where host-device transfer cost is amortized over massive data volume. Real system: NVIDIA CUDA. Rejected: wrong regime entirely — this project targets CPU-resident, low-latency, per-call vectorization (database scans, string matching) where a PCIe/NVLink round-trip would dominate the cost the library exists to eliminate.

A4 — JIT-specialized runtime codegen

 IR template → JIT compiler (LLVM ORC-class) → machine code specialized to the running CPU

Wins when the exact CPU is unknown until runtime and the kernel is complex/varied enough that a hand-written multiversioned table (ADR-23) becomes unmaintainable — the JIT effectively becomes the dispatch mechanism. Real system: Numba (LLVM-based JIT for numerical Python). Rejected: JIT warmup cost and deployment complexity (embedding an LLVM-class compiler in every consumer binary) contradict §1's zero-daemon, static-link deployment model; explicitly PhaseDeferred("§1") under "JIT specialization."
