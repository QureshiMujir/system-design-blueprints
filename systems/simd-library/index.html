Client Applications — external consumers; never link against simd-x86/simd-arm directly, only against simd-core/simd-math/simd-memory (P1).

Public SIMD API — the only stable, backend-agnostic surface; monomorphizes to zero-cost machine code per P4; owns the Mask canonical bit representation (P6, I2).

Runtime Dispatch — resolves exactly one Backend per process, cached in a OnceLock (I5, I13); the sole place any #[cfg(target_arch)]-style decision happens outside crate boundaries.

Architecture Backends — simd-x86 and simd-arm share zero code beyond simd-core trait implementations (P8); each independently conformance-tested against the scalar oracle (ADR-17).

Intrinsics Layer — every intrinsic call is wrapped behind a #[target_feature]-gated safe function (P2, I6); this is the only layer touching raw unsafe.

Hardware Execution — vector ALU ports, register files, and the cache hierarchy quantified in §4 and modeled in §32; not controlled by this library, only measured (§28).

Trust boundary: the Intrinsics Layer is the sole trust boundary — everything above it is proven memory-safe by the type system; everything at or below requires the SDM/ARM-ARM semantic proof cited in P12.

Concurrency boundary: dispatch resolution is a single OnceLock write race (T4) with an otherwise stateless, purely functional kernel surface — no other shared mutable state exists.

Persistence boundary: this library holds no persistent state; the only artifacts written to disk are conformance/fixtures.lock (I12) and benchmark/profiling reports (§24).

8. Domain Model / Protocol / Data Model

Vector layout grammar

FixedVector   ::= "Simd<" Type "," LANES ">"          ; LANES: usize, power-of-two, compile-time
ScalableVector::= "SveVector<" Type ">"                ; VL resolved at runtime (I9)
Mask          ::= "Mask<" Type "," LANES ">"           ; canonical storage: bitset <= 64 bits (P6)
LaneOp        ::= "add" | "sub" | "mul" | "min" | "max"
                | "bitand" | "bitor" | "bitxor" | "not"
ShuffleOp     ::= "permute" | "interleave" | "broadcast" | "extract" | "zip" | "blend"
ReduceOp      ::= "sum" | "product" | "min" | "max" | "all" | "any" | "none"

Lane operations (§13/§19)

Elementwise arithmetic/bitwise ops apply LaneOp independently per lane; comparisons produce a Mask (P6); ShuffleOp rearranges lanes without changing lane values; ReduceOp collapses a vector to one scalar or boolean via the fixed pairwise-tree (I7) except boolean all/any/none, which use a boolean AND/OR tree.

Mask semantics — worked example

Input vector Simd<f32,4> = [1.0, -2.0, 3.0, -4.0]. Comparison simd_gt(0.0) yields Mask<f32,4> with canonical bits 0b0101 (lane 0 and lane 2 true, per I2). On an AVX backend this materializes as an all-ones/all-zeros per-lane pattern; on AVX-512 as a native k-register value 0b0101; both convert to the same canonical bits via to_bits() (P6).

Dispatch state machine (state-transition table)

State Trigger Next State Notes
Cold process start Probing no CpuFeatures cached yet
Probing first CpuFeatures::detect() call Cached OnceLock write races resolved to one winner (T4)
Cached any subsequent call Cached OnceLock read, < 2 ns (M5)
Cached dispatch table lookup for a kernel Dispatched highest-capability backend consistent with CpuFeatures (I5)
Dispatched selected backend unavailable at link time Fallback walk Backend priority chain (I10)
Fallback chain exhausted Scalar terminal state, always compiles/runs (I10)

Malformed-input example

A caller passes a 6-element &[f32] slice to Simd::<f32,8>::try_from(slice). LANES=8 requires exactly 8 elements; TryFrom returns Err(ConversionError::LengthMismatch { expected: 8, got: 6 }) — no partial read, no padding invented (T1).

Failure-path example

A binary is built with target-feature=+avx2 and deployed, pre-Phase-6, without going through simd-dispatch (i.e. calling simd-x86::avx2 directly). Run on an SSE2-only host: the missing #[target_feature] runtime guard means the instruction stream contains an unsupported opcode and the process receives SIGILL (T3, FM-1). Post-Phase-6, the same scenario instead resolves through CpuFeatures::detect() and the dispatch fallback chain lands on Backend::Scalar (I10) — this is why the Repository Layout (§10) forbids client crates from depending on simd-x86/simd-arm directly (P1).
