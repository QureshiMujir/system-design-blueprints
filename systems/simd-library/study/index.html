30. Mental Models & First Principles

MM1 — A vector register is a fixed-size window, not a container. Predicts: tail elements (N mod LANES != 0) always need separate handling. Bug class without it: off-by-tail-length buffer overrun. Resolves: §19, §8.

MM2 — Masks are data, not control flow. Predicts: masked lanes still execute (they just don't commit), so a masked divide-by-zero can still fault on some backends. Bug class without it: assuming masked-out lanes are "skipped" like an if-branch. Resolves: §14, I8.

MM3 — Throughput and latency are different budgets. Predicts: a kernel can be latency-bound (dependency chain) even when throughput-optimal instructions are used. Bug class without it: optimizing instruction count while ignoring dependency depth. Resolves: §28, §32.

MM4 — Alignment is a promise, not a check. Predicts: an aligned-load intrinsic trusts the caller; violating the promise is UB, not a runtime error, on some backends. Bug class without it: assuming misalignment always crashes loudly (it sometimes silently slows down instead). Resolves: §12, I3.

MM5 — Dispatch cost is amortized once, semantics forever. Predicts: it is always correct to pay dispatch cost once at startup, never per hot-loop iteration. Bug class without it: re-probing CpuFeatures inside a loop. Resolves: §18, P5.

MM6 — Scalable vectors trade a compile-time constant for a runtime query. Predicts: SVE code that runs correctly at VL=128 also runs correctly, unmodified, at VL=2048. Bug class without it: baking a lane count into SVE code like fixed-width code. Resolves: §17, I9.

MM7 — Reduction order is an API contract, not an implementation detail. Predicts: two backends can both be "correct" and still disagree bit-for-bit on a float sum unless the order is fixed. Bug class without it: treating a float-sum mismatch as a backend bug instead of a missing contract. Resolves: §19, I7.

MM8 — A conformance oracle must be simpler than what it checks. Predicts: the scalar reference implementation must never itself use SIMD tricks, or it stops being an independent check. Bug class without it: an "optimized" oracle sharing the same bug as the thing it verifies. Resolves: §21, I1.

5. Required Reading

Books

  • Bryant, R. & O'Hallaron, D. — Computer Systems: A Programmer's Perspective, 3rd ed. Ch. 5 (optimizing program performance), Ch. 6 (memory hierarchy). Extract: cache-blocking interplay with vectorization, loop-carried dependency analysis. Applied in §20 / Phase 8.
  • Patterson, D. & Hennessy, J. — Computer Organization and Design. Ch. 3 & appendix on vector/SIMD extensions. Extract: Flynn's taxonomy, vector-vs-SIMD-vs-GPU distinction. Applied in §2 / §3.
  • Hennessy, J. & Patterson, D. — Computer Architecture: A Quantitative Approach, 6th ed. Ch. 4, Data-Level Parallelism. Extract: vector-architecture design tradeoffs, the roofline model. Applied in §29 / §32.
  • Fog, Agner — Optimizing subroutines in assembly language (Software optimization resources). Extract: instruction-level throughput/latency tuning for SIMD loops. Applied in §15 / Phase 3.
  • Fog, Agner — The microarchitecture of Intel, AMD and VIA CPUs (Software optimization resources). Extract: execution-port contention, AVX-512 downclock behavior. Applied in §16 / Phase 4.
  • Warren, Henry S. — Hacker's Delight, 2nd ed. Ch. 2, Ch. 5 (SWAR bit-tricks, population count). Extract: packed-arithmetic techniques predating SIMD ISAs; reduction bound reasoning. Applied in §19 / Phase 7.

Papers

  • Kretz, M. (2015). Extending C++ for Explicit Data-Parallel Programming via SIMD Vector Types. PhD thesis, Goethe University Frankfurt. Contribution: Vc library design, basis for std::simd. Applied in §13 / Phase 1, §14 / Phase 2.
  • Kretz, M. & Lindenstruth, V. — WG21 P0214, Data-Parallel Vector Types and Operations (std::experimental::simd), ISO/IEC JTC1/SC22/WG21. Contribution: standardized SIMD type interface. Applied in §11.
  • Lemire, D., Boytsov, L., Kurz, N. (2014). SIMD Compression and the Intersection of Sorted Integers, Software: Practice and Experience (arXiv:1401.6399). Contribution: SIMD bit-unpacking decode. Applied in §19 / Phase 7.
  • Muła, W., Kurz, N., Lemire, D. (2018). Faster Population Counts Using AVX2 Instructions, The Computer Journal. Contribution: vectorized popcount technique. Applied in §20 / Phase 8.
  • Willhalm, T., Popovici, N., Boshmaf, Y., Plattner, H., Zeier, A., Schaffner, J. (2009). SIMD-Scan: Ultra Fast in-Memory Table Scan using on-Chip Vector Processing Units, VLDB. Contribution: SIMD DB-scan design. Applied in §20 / Phase 8.
  • Polychroniou, O., Raghavan, A., Ross, K. (2015). Rethinking SIMD Vectorization for In-Memory Databases, SIGMOD. Contribution: gather/scatter-centric DB kernel design. Applied in §19 / Phase 7.
  • Zhou, J. & Ross, K. (2002). Implementing Database Operations Using SIMD Instructions, SIGMOD. Contribution: early SIMD select/scan kernels. Applied in §20 / Phase 8.
  • Nuzman, D. & Zaks, A. (2006). Autovectorization in GCC, Proceedings of the GCC Developers' Summit. Contribution: the compiler-autovectorization alternative this project's explicit multiversioning deliberately avoids. Applied in §18 / Phase 6, §34.

Reference Implementations

  • google/highway — dirs: hwy/ops, hwy/contrib. Lesson: dynamic per-target dispatch via HWY_TARGETS macros. Pitfall: macro-heavy multi-target compilation multiplies build time. Applied in §31.
  • xtensor-stack/xsimd — dirs: include/xsimd/arch, include/xsimd/types. Lesson: a batch<T,N> abstraction layered per architecture. Pitfall: template-instantiation compile-time cost. Applied in §31.
  • rust-lang portable-simd (std::simd nightly, formerly packed_simd) — dirs: crates/core_simd. Lesson: const-generic Simd<T,N> API design. Pitfall: platform-intrinsic lowering gaps for odd lane counts. Applied in §11, §13.
  • simdjson/simdjson — dirs: src/simdjson/arm64, src/simdjson/haswell. Lesson: per-architecture "implementation" abstraction selected by runtime cpuid dispatch. Pitfall: per-implementation code duplication burden. Applied in §18 / Phase 6.
  • flame/blis (BLIS) — dirs: kernels/. Lesson: micro-kernel isolation per architecture for GEMM. Pitfall: kernel explosion across architectures without codegen. Applied in §20 / Phase 8.
  • vectorclass/version2 (Agner Fog's Vector Class Library, VCL) — dirs: repository root headers. Lesson: operator-overload-based SIMD wrapper design predating std::simd. Pitfall: header-only macro complexity for mixed-width conversions. Applied in §11, §31.

RFCs / Specifications

  • Intel 64 and IA-32 Architectures Software Developer's Manual, Vol. 1 (SIMD instruction-set overview) and Vol. 2 (instruction reference). Applied in §15/§16 / Phases 3–4.
  • Intel Intrinsics Guide (intel.com/intrinsics-guide) — canonical intrinsic-to-instruction mapping. Applied in §15/§16 / Phases 3–4, ADR-24.
  • Arm Architecture Reference Manual for A-profile architecture — Advanced SIMD (NEON) chapter and Scalable Vector Extension (SVE) chapter. Applied in §17 / Phase 5.
  • Arm SVE Programmer's Guide. Applied in §17 / Phase 5.
  • WebAssembly SIMD proposal (github.com/WebAssembly/simd). Applied in §35 (deferred backend).

Glossary (§36) · 56 terms · site-wide glossary

SIMD
Single Instruction, Multiple Data — one instruction operates on multiple lanes at once
Lane
one scalar element position within a vector register
LANES
compile-time lane count of a fixed-width Simd<T,LANES>
Vector register
a CPU register holding multiple lanes (XMM/YMM/ZMM on x86, V-registers on ARM)
Mask
per-lane execution/commit predicate
Predication
executing an operation per-lane, conditionally committing based on a mask
k-mask
AVX-512's native mask register (k0-k7)
Shuffle
lane rearrangement within or across vectors
Swizzle
a named-pattern shuffle (e.g. broadcast, zip)
Blend
per-lane select between two vectors based on a mask
Permute
shuffle driven by an explicit index vector
Interleave
alternating-lane merge of two vectors
Broadcast
replicate one scalar value across all lanes
Extract
read a single lane out of a vector
Zip
pairwise interleave producing one or two output vectors
Reduction
collapsing a vector to a single scalar or boolean
Horizontal add
a reduction summing all lanes of one vector
Gather
vectorized load from noncontiguous memory addresses
Scatter
vectorized store to noncontiguous memory addresses
Alignment
the memory-address boundary a load/store instruction requires
Aligned load
a load instruction requiring its address to be a multiple of the vector width
Unaligned load
a load instruction tolerating any byte address, often at a throughput cost
FMA
fused multiply-add, computed with one rounding step instead of two
ULP
unit in the last place — a measure of floating-point rounding error
Denormal
a floating-point value smaller than the smallest normal representable value
Flush-to-zero (FTZ)
a mode that rounds denormal results to zero instead of representing them
Multiversioning
compiling multiple backend-specific variants of one function, selected at runtime
Dispatch
the runtime decision of which backend-specific function variant to call
CPUID
the x86 instruction querying supported CPU features
Feature detection
probing which ISA extensions the running CPU supports
Backend
one architecture-specific implementation of the portable vector API
Scalar fallback
the non-vectorized reference implementation, always available
Fixed-width vector
a vector type whose lane count is a compile-time constant
Scalable vector
a vector type whose lane count is resolved at runtime (SVE)
VLA
vector-length-agnostic — code that never assumes a specific scalable-vector length
SVE
Arm's Scalable Vector Extension
SVE2
the second-generation extension to SVE, adding new instructions
NEON
Arm's fixed-width 128-bit Advanced SIMD extension
AVX2
Intel's 256-bit SIMD extension
AVX-512
Intel's 512-bit SIMD extension family (F/BW/VL/VNNI/etc. subsets)
SSE2
Intel's original 128-bit SIMD baseline extension
Port contention
multiple instructions competing for the same CPU execution port in one cycle
Throughput
operations completed per unit time under sustained execution
Latency
time from an operation's issue to its result being available
Autovectorization
a compiler automatically transforming scalar loops into SIMD instructions
Intrinsic
a compiler-recognized function mapping directly to one (or a few) hardware instructions
Target feature
a compiler/runtime flag indicating an ISA extension is available to use
Conformance oracle
the trusted reference implementation all backends are checked against
Fixture
a named, version-pinned test case used for conformance/regression checking
Differential testing
comparing two implementations' outputs on the same input to find divergence
Soak testing
running a test (often fuzzing) continuously for an extended duration
Fuzzing
feeding randomized/malformed input to find crashes or invariant violations
Cache line
the fixed-size block (typically 64 bytes) a CPU cache moves as one unit
Roofline model
a performance model bounding achievable throughput by compute vs memory bandwidth
Associativity (reduction)
whether grouping order affects a reduction's result (true for integers, false in general for floats)
Bit-reproducibility
guaranteeing an identical bit pattern result across runs/backends
