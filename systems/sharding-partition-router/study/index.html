Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does hash-mod-N sharding forbid live resize while consistent hashing supports it, and what specifically breaks if you try to resize a hash-mod-N map online? (§14, §15, I10)
  2. Under what circumstances does rendezvous hashing outperform consistent hashing with vnodes, and why does that regime not survive past a few hundred shards? (§16, §4)
  3. Trace exactly what happens to an in-flight write when a split's cutover CAS fires between the write's route() call and its arrival at the shard server. (§19, §18, I3, I4)
  4. Why is the metadata store required to be linearizable rather than merely "strongly consistent in practice," and what production history justifies this requirement? (§17, P6, I7, §23 T2)
  5. A tenant's keys are uniformly hot but the tenant itself is small. Walk through why the hot-shard detector would or would not trigger a tenant-aware split instead of a row-range split. (§19, §21)
  6. Why does the vindex two-hop pattern not collapse into a single hop even when the index column is a UUID, and under what vindex type does it? (§20, §11)
  7. Derive, from the Capacity Model, the minimum vnode count needed to keep load imbalance under a stated bound, and explain why the answer does not depend on the number of physical shards. (§33 CM7, §4, ADR-06)
  8. Why is "refresh the routing cache on every request" categorically wrong even though it would eliminate stale-cache misrouting entirely? (§18, MM2 §31, P5)
  9. Compare the failure blast radius of a coordinator crash during Scanning vs. during Cutover. Why is one recoverable with zero operator involvement and the other identical in recovery path? (§19, FM3 §24, I12)
  10. Why does Jump Consistent Hash's "buckets can only grow" constraint make it unsuitable for a cluster that regularly decommissions shards, and what data structure would work around it — and why is that workaround not "free"? (§16, §35)
  11. Using the Comparative Architecture Table, explain why Cassandra's gossip-based metadata model would be a regression for this design's guarantees, even though it removes a component. (§32, §6 P6, §7 I7)
  12. Why does tenant-ID-first key encoding matter for rebalancing cost, not just for query locality? (§21, I14, §33 CM4)
  13. What specifically goes wrong if the bounded-loads consistent-hash variant's ε parameter were set to 0.0, and why is that different from disabling the feature entirely? (§15, §9 ADR-23)
  14. Why is the routing-cache concurrency primitive (arc-swap) not simply replaceable with a Mutex without a measurable regression, and where does that regression show up in the Performance Engineering targets? (§18, §29, ADR-21, M1/M2)
  15. Explain why a range scan across a hash-partitioned keyspace is fundamentally more expensive than the same scan across a range-partitioned keyspace, in terms of both network fan-out and merge-sort cost — and why adding a secondary index does not fix it. (§14, §20)
  16. Why must the double-write during a split's scan phase target both shards rather than just queuing writes for later replay on the destination? (§19, I3, FM4 §24)
  17. Two adjacent range shards are each below the merge threshold. Walk through why the merge is not simply "the inverse of the split" in terms of pivot-selection risk. (§19, §13)
  18. What is the operational difference between "the routing cache is stale" and "the partition map is corrupted," and why does the system have a fully automated recovery path for one but not the other? (§23 T8, §24 FM2/FM5, I5)
  19. Using the System Invariants table and the Failure Modes section, identify which single invariant, if violated, would make every other invariant's enforcement moot. (§7, §24)
  20. Why does this design defer cross-shard transactions to an external blueprint rather than building a minimal 2PC path in-house, and what would have to change in the Core Schema if that decision were reversed? (§11, ADR-17, §36)

31. Mental Models & First Principles

  • MM1 — A partition map is a pure function key → shard; the router just evaluates it. Predicts: correctness depends only on the map's correctness, not on routing-code cleverness. Bug class without it: routing bugs get misdiagnosed as storage bugs. Applies in §11 (PartitionMap), §13 (Range).
  • MM2 — The shard server is the ledger of truth; the client cache is a rumor. Predicts: staleness is tolerable, divergence is not corruption. Bug class without it: engineers build a strongly-consistent cache (a quorum read per route) and destroy the latency budget. Applies in §18 (Phase 6), I6 (§7).
  • MM3 — Consistent hashing turns "add a node" into a local edit, not a global rewrite. Predicts the K/N movement bound. Bug class without it: teams pick hash-mod-N for an "elastic" system, then eat a full re-platform under load. Applies in §15 (Phase 3), P3 (§6).
  • MM4 — A split is a transaction with only two externally observable states: before and after; the messy middle is double-written. Predicts scan-phase writes must hit both shards. Bug class without it: forgetting the double-write, silently losing data. Applies in §19 (Phase 7), I3 (§7).
  • MM5 — Every partitioning scheme trades range-scan locality for write-uniformity — you cannot have both. Predicts the choice is always workload-dependent, never universal. Bug class without it: "switch schemes later" regret that costs a quarter. Applies in §13, §14, §15 (Phase 1–3), P1 (§6).
  • MM6 — A secondary index is just another shard map: index one thing, shard by another. Predicts a vindex needs its own partition map keyed by the index column. Bug class without it: co-locating the index with the primary, concentrating a second hotspot. Applies in §20 (Phase 8), P8 (§6).
  • MM7 — Tenant isolation is a key-encoding property, not a runtime feature. Predicts prefix ordering alone determines isolation. Bug class without it: encoding tenant ID suffix-first, silently breaking isolation months later. Applies in §21 (Phase 9), I14 (§7).
  • MM8 — A metadata store that isn't linearizable isn't a metadata store — it's a rumor mill with extra steps. Predicts any weak-consistency backend eventually admits split-brain. Bug class without it: the "eventually-consistent store is good enough" assumption. Applies in §17 (Phase 5), P6 (§6), I7 (§7).

Glossary (§37) · 43 terms · site-wide glossary

Bounded loads
the Mirrokni–Thorup–Zadimoghaddam consistent-hash variant capping any bucket's load at (1+ε)×average (§15).
BucketAllocator
the logical-bucket-to-physical-shard indirection table giving hash-mod-N partial elasticity (§14).
CAS (compare-and-swap)
the atomic conditional write used for every partition-map mutation (I4, §8.2).
Composite key
a routing key encoding (tenant_id, row_key) with tenant ID as the high-order prefix (§8.1, §21).
Consistent hashing
a hashing scheme where node changes reassign only K/N keys in expectation (Karger et al. 1997, §15).
Coordinator
(shard-coord) — the leader-elected service driving resharding jobs (§19).
Cutover
the atomic CAS step of a split/merge that flips partition-map ownership (§8.3, I4).
Double-write
writing to both source and destination during a split's scan phase (I3).
Fencing token
a strictly increasing value preventing a stale leaseholder from acting (I8).
Fanout
dispatching a batch of per-key operations grouped by owning shard (§18.2, §22.2).
Hash-mod-N partitioning
fixed-bucket-count partitioning via hash(key) % N (§14).
Hot shard
a shard whose load exceeds the QPS-and-bytes/p99 threshold (P10, §19).
HRW (Highest Random Weight)
the rendezvous-hashing selection rule (§16).
Jump consistent hash
the Lamping–Veach stateless bucket-assignment algorithm (§16).
Lease
a TTL-protected ownership grant for a shard (§17.4, I8).
Linearizability
the consistency property required of the metadata store (P6, I7).
MetadataStore
the trait abstracting etcd/ZooKeeper/internal-Raft backends (§11.6).
Partition map
the versioned assignment of keys to shards, in one of five schemes (§11.2).
PartitionKey
an opaque byte-string routing key (§11.1).
Pivot
the boundary chosen for a range split (§13.2, §19.2).
Proxy mode
routing via the stateless shard-proxy binary rather than an embedded SDK (§18.2).
Range partitioning
sorted-boundary partitioning supporting cheap range scans (§13).
Rendezvous hashing
the O(N) stateless HRW scheme (§16).
Router
the trait exposing route/route_range/refresh (§11.6).
shard-coord
the resharding-coordinator crate (§10).
shard-core
the no_std crate holding partitioning primitives (§10).
shard-metadata
the crate abstracting metadata-store backends (§10).
shard-net
the wire-protocol crate (§10, §8.2/§11.7).
shard-proxy
the stateless routing-proxy binary (§10).
shard-router
the smart-client SDK crate (§10).
ShardId
a u32 shard identifier (§11.1).
ShardServer
the runtime descriptor for a shard (§11.3).
Smart-client mode
routing embedded in the calling process (§18.2).
Stale-cache retry
the KeyNotFound-triggered refresh-and-retry-once path (§8.4, I6).
Tenant isolation
the property that one tenant's data and load do not spill onto another tenant's shard (P7, §21).
Token (ring)
a 64-bit position on the consistent-hash ring (§11.3).
TokenBucket
the rate-limiting primitive bounding rebalance throughput (§11.8, P11).
Two-phase commit (2PC)
the deferred cross-shard-transaction protocol hook (ADR-17, §36).
Two-phase split
the scan-then-cutover online resharding protocol (§19.1).
Vindex
a secondary-index sharding abstraction mapping an index value to a primary key (§11.4, §20).
Virtual node (vnode)
one of vnode_count ring positions per physical shard (§15, ADR-06).
Watch-and-cache
the pattern of invalidating a local cache on a metadata-store watch notification (§17.3).
Wire version
