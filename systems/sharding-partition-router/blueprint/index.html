98 — Sharding and Partition Router

Project Number: 98

Project Name: Sharding and Partition Router

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Definition. Sharding and Partition Router is a key-value data-sharding and request-routing control plane: it assigns opaque byte-string keys to shards under five interchangeable partitioning schemes (range, hash-mod-N, consistent hash with virtual nodes, jump consistent hash, rendezvous/HRW), maintains that assignment in a linearizable metadata store, drives online splits/merges without client-visible downtime, and exposes the routing decision to callers via a smart-client SDK, a proxy binary, or both. It is the layer every horizontally scaled storage system needs once a single node's capacity or throughput is exceeded, and it is deliberately scoped to the routing/placement problem only — not to storage engines, query planning, or transaction atomicity.

Phase-0 deliverable (numbered, one module/crate per item; built in §12):

  1. shard-core crate (no_std + alloc) — PartitionKey, ShardId, Range, PartitionMap::Range variant (range partitioning only at Phase 0).
  2. shard-metadata crate — MetadataStore trait plus a Postgres-backed reference implementation for the Phase-0 smoke test (etcd lands in §17/Phase 5).
  3. shard-router crate — SmartClientRouter with a static (non-refreshing) partition map.
  4. docker-compose.yml stack — Postgres metadata catalog + three placeholder shard addresses.
  5. examples/range_3_shards.rs — deterministic smoke test: 1,000,000 synthetic keys routed across 3 static range-partitioned shards with zero misroutes.
  6. conformance/runner — emits conformance.report.json; Phase 0 gates on the property.partition_assignment bucket only.
  7. .github/workflows/ci.yml — build + lint + test on every push.

System boundaries.

  • Provides: routing decisions for opaque byte-string keys under 5 partitioning schemes; a pluggable linearizable metadata-store abstraction; online split/merge orchestration with rate-limited data movement; a vindex (secondary-index) routing layer; tenant-aware composite-key encoding; hot-shard detection and automatic remediation triggers.
  • Delegates: the shard storage engine itself (out of scope — shard-net, §8, defines only the wire boundary a storage engine must speak); shard-level replication (PhaseDeferred("§1"), external — see Deferred Features Register §36); cross-shard transaction atomicity (PhaseDeferred("§1"), external).
  • Does NOT provide: SQL parsing or query planning (PhaseDeferred("§1")); geo-aware placement (PhaseDeferred("§22")); authentication of end users beyond tenant-ID prefix validation (delegated to the application layer).

Non-goals: a general-purpose distributed database; a replicated consensus store (we consume one, we do not build one — Raft is offered as an internal metadata-store option in §17.5, not as this project's primary deliverable); a SQL engine; a general-purpose service mesh.

Deployment model: shard-router embeds as a library inside the calling process (smart-client mode); shard-proxy deploys as a standalone binary or sidecar for polyglot clients (proxy mode); shard-coord runs as a leader-elected singleton service per cluster; the metadata-store backend (etcd/ZooKeeper/internal Raft) is an external dependency the operator provisions. Shard servers themselves are out of scope and addressed only via shard-net (§8).

Target users/operators: infrastructure engineers building a horizontally sharded KV or SQL storage system from scratch; SRE/on-call engineers who must diagnose a misrouted key, a stuck resharding job, or a metadata-store quorum loss at 3 a.m.

What later phases unlock: §15 (Phase 3) unlocks elastic capacity (add/remove shards moving only K/N keys); §19 (Phase 7) unlocks online capacity changes with zero downtime; §20 (Phase 8) unlocks secondary-index queries without full fan-out; §21 (Phase 9) unlocks safe multi-tenancy.

Recommended language: Rust 1.78+, edition 2021. Rationale: the routing hot path (§18, M1/M2 in §29) targets sub-2-microsecond cache-hit latency — unattainable under a stop-the-world garbage collector, which rules out Go (GC pause directly inflates p99 route latency) and Java/JVM (JIT warmup plus GC pause defeats the same target); the lock-free routing cache (ADR-21, §9) needs a borrow-checker-verified no-unsafe implementation, which is where C/C++ sharding layers have historically shipped memory-safety CVEs in hash-ring arithmetic (buffer overruns in key-length handling); no_std capability (ADR-02, §9) supports edge/embedded routing, which Go and the JVM do not support at all. Rejected: Go (GC pause risk against M1/M2), C++ (memory-safety CVE class in ring/hash math), Java (JIT warmup + GC unsuitable for the hot path).

Prerequisites: consistent hashing (Karger et al. 1997, §5); the CAP theorem applied to metadata stores; two-phase commit at a hand-wave level (the full implementation is PhaseDeferred("§1") to Blueprint #73); the Rust borrow checker; basic distributed consensus (Raft or Paxos, §5). A reader should be able to derive on a whiteboard, before opening this document, why hash(key) % N cannot resize without a full rehash, why a consistent-hash ring with fewer than 100 virtual nodes per physical shard shows up to 2× load imbalance, and why a range scan over a hash-sharded keyspace touches every shard.

Estimated timeline: Phase 0 (§12) — 1 week. Full Phase 0–10 plan (§12–§22) — 12 engineering weeks (~3 months) for a small team. Production hardening (30-day soak, external audit, Sealed gate) extends total elapsed time to 5–7 months.

2. Why Build This

  • Unique systems knowledge. The only project in this portfolio that forces a from-scratch comparison of all five production partitioning schemes on one codebase — most engineers only ever ship the one their framework defaulted to.
  • Architecturally load-bearing. Every system that outgrows one machine pays this bill: DynamoDB (consistent hash + adaptive capacity), Spanner/CockroachDB (range + Paxos/Raft metadata), Cassandra (gossip token ring), Vitess (vindexes over MySQL), Citus (co-located Postgres tables), FoundationDB (unbundled sharding). None of these are toys; each has produced outage post-mortems whose proximate cause was a sharding decision made years earlier.
  • Historically decisive. The scheme chosen at provisioning time (P1, §6) is close to irreversible in production — a wrong choice is a re-platform, not a config flag, which is why this blueprint treats the choice as the single most expensive decision in the stack.
  • Engineering muscles built: hash-ring and jump-hash arithmetic under a correctness contract; CAS-based coordination against a linearizable store; a lock-free concurrent cache under a producer/many-consumers workload; rate-limited background data movement that must not regress foreground tail latency; a two-hop secondary-index protocol; composite-key encoding for multi-tenant isolation.
  • Cross-links to sibling systems: the metadata store's CAS/versioning pattern reuses the linearizable-store lessons from the consensus blueprint; the 2PC hook (ADR-17, §9) is the seam to Blueprint #73; the saga hook (ADR-18) is the seam to Blueprint #91; the replication seam (§1 non-goals) is the seam to Blueprint #21.
  • Calibration value: the property tests (reshuffle minimality, partition assignment, live split correctness) and the Jepsen-style fault matrix (§27) are a concrete, checkable bar for "did I actually get consistent hashing right," rather than a subjective code review.

What Mastery Looks Like

  • Explain from first principles why hash(key) % N forbids online resize while consistent hashing supports it, and prove the K/N bound empirically — Phase 2 (§14), Phase 3 (§15).
  • Implement and verify Karger's 1997 K/N-keys-move result and the Mirrokni–Thorup–Zadimoghaddam bounded-loads variant against property-test thresholds — Phase 3 (§15).
  • Design a two-phase online split/merge protocol that never loses or duplicates a key under concurrent load, including coordinator-crash recovery — Phase 7 (§19).
  • Choose correctly between smart-client, proxy, and hybrid routing topologies given a specific client-fleet constraint (language diversity vs latency budget) — Phase 6 (§18).
  • Design a tenant-aware composite-key encoding that preserves both query isolation and a bounded rebalance cost — Phase 9 (§21).
  • Build a secondary-index (vindex) keyspace that does not concentrate hotspots on the primary shard — Phase 8 (§20).
  • Operate a production sharded system at 3 a.m.: distinguish routing-cache divergence from partition-map corruption from metadata-store quorum loss using telemetry alone — Threat Model (§23), Failure Modes & Recovery (§24).
  • Derive, not assert, every capacity number in a sharding design from first principles before writing a line of code — Back-of-Envelope Capacity Model (§33).

Partitioning algorithms are independent of the routing tier. Router (§11) is generic over the PartitionMap enum (§11); the same routing code drives all five schemes without a scheme- specific code path in the hot loop.

The metadata store is linearizable for correctness, not merely "usually consistent." A non-linearizable store admits split-brain on the partition map (I7, §7); we depend on this property and reject weaker backends at the type level (P6, §6).

The resharding coordinator is the only writer of the partition map. It reads from the metadata store, writes back versioned plan documents, and drives shard servers via shard-net; no other component may mutate the map (I4, §7).

The routing tier caches with bounded staleness, and staleness is a performance defect, not a correctness defect (P14, §6; MM2, §31). A stale cache routes to an ex-owner; the shard server — the actual authority — rejects the op and returns its current partition-map version; the client refreshes and retries once (I6, §7).

6. Design Principles

  1. P1 — Partition scheme is forever. The choice of range/hash/consistent-hash/jump/rendezvous at provisioning time is immutable in production; switching is a full data migration, not a config flag (§13–§16). Violating it: teams that "switch later" eat a quarter-long re-platform.
  2. P2 — Range and hash require different metadata representations. No unified representation; each scheme has a dedicated PartitionMap (§11) variant. Violating it: forcing one representation (e.g., always a sorted map) makes hash-mod-N's O(1) lookup an O(log N) lookup for no reason.
  3. P3 — Consistent hashing requires ≥ 100 vnodes/physical, default 256 (ADR-06). Below 100, load imbalance reaches 2× (Karger 1997, §5). Violating it: silent production hotspotting that only shows up under real traffic skew.
  4. P4 — Live resharding must be online and non-blocking. Two-phase scan-then-cutover (§19); the source keeps serving during the scan. Violating it: a blocking split is an outage.
  5. P5 — Routing tier must cache with bounded staleness. Default TTL 30 s + watch-driven invalidation (§18). Violating it either way: no caching kills the M1/M2 latency targets (§29); unbounded caching makes stale-cache windows unrecoverable without a hard restart.
  6. P6 — Metadata store must be linearizable for correctness. Non-linearizable stores admit split-brain on the partition map (I7, §7). Violating it: two shards can each believe they own the same key range simultaneously.
  7. P7 — Tenant-aware sharding requires composite keys, tenant ID as the high-order prefix. (§21). Violating it: one hot tenant's data fans out across every shard, and rebalance work scales with tenant count instead of staying local.
  8. P8 — Secondary-index sharding requires a separate vindex keyspace. (§20). Violating it: co-locating index with primary concentrates two hotspots on one shard instead of spreading them.
  9. P9 — Cross-shard transactions are explicit: 2PC or saga, never silent. TransactionMode is a typed parameter (§11); no "fire and pray" path exists in the public API (ADR-17/18, §9). Violating it: partial multi-shard writes leave permanently inconsistent state with no recovery path.
  10. P10 — Hot-shard detection must be automatic. QPS-and-bytes-per-second AND p99-latency thresholds, sustained 60 s (§19.4). Violating it either way: single-metric detection produces false positives (one large key) or false negatives (many small hot keys).
  11. P11 — Rebalance under load must be rate-limited. Token-bucket, default 10 MB/s/replica (ADR-12, §9; the WeChat Pay 2019 postmortem, §5). Violating it: an unthrottled copy saturates replica disk I/O and triples production write latency.
  12. P12 — Routing decisions are observable. Every route(key) records (key_hash_prefix, shard_id, cache_hit, partition_map_version) in a sampled trace (§25). Violating it: "where did this key go and why" becomes unanswerable without rebuilding cache state by hand.
  13. P13 — Conformance is the contract. Property tests (partition assignment, reshuffle minimality, live-resharding correctness) plus a Jepsen-style fault matrix gate Done/Sealed (§27). Violating it: "looks correct in review" replaces a checkable bar.
  14. P14 — The shard server, not the client cache, is the authority on ownership. Cache staleness is a performance defect, never a correctness defect (I6, MM2 §31). Violating it: engineers "fix" staleness by adding a strongly-consistent quorum read per route, destroying the latency budget (M1/M2, §29) for no correctness gain.

These principles are enforced at the type level where possible (P2, P6, P9, P10 via typed parameters and rejecting non-linearizable backends at construction), by conformance fixtures where not (P1, P3, P4, P11, P13), and by code review for the rest.

8. Domain Model / Protocol / Data Model

8.1 Composite-key grammar (EBNF)

partition-key   = composite-key | plain-key ;
plain-key       = byte-string ;
composite-key   = tenant-len , tenant-id , row-key ;
tenant-len      = varint ;                (* LEB128, ADR-13 *)
tenant-id       = byte-string ;           (* length = tenant-len *)
row-key         = byte-string ;           (* remainder of the key *)
byte-string     = { OCTET } ;
varint          = OCTET , { OCTET } ;      (* LEB128 continuation-bit encoding *)

Tenant ID is always the high-order prefix (I14, §7); a decoder that reads row-key before tenant-id is malformed by construction — encode_composite rejects any caller-supplied byte order that does not match this grammar.

8.2 Partition-map wire record (Protobuf, ADR-03)

Field Type Notes
magic fixed32 0x53484152 ("SHAR") — malformed if absent
wire_version uint32 compatibility gate, §26
map_version uint64 monotonic (I5)
scheme enum {RANGE, HASH, CONSISTENT_HASH, JUMP, RENDEZVOUS} selects the oneof below
payload oneof {RangeMap, HashMap, RingMap, JumpMap, RendezvousMap} scheme-specific body
crc32 fixed32 checksum over payload (T8, §23)

A record whose crc32 does not match its payload is malformed input (§8.5) and is rejected before any deserialization of the oneof — the checksum check runs on raw bytes first.

8.3 Resharding job state machine

State Entered From Exit To Persisted? Meaning
Pending job creation Scanning yes Plan accepted; no data movement yet
Scanning Pending Validating, Aborted yes Destination back-fills; double-write active (I3)
Validating Scanning Cutover, Aborted yes Byte-equivalence check between source/destination
Cutover Validating Completed, Aborted yes Atomic CAS on the partition map (I4)
Completed Cutover — (terminal) yes Job done; double-write stopped
Aborted any of the above — (terminal) yes Reachable from any state (I12)

This is the full transition table for JobState (§11); no other edge is legal, and the coordinator's crash-recovery path (§19.9) resumes strictly along this table.

8.4 Worked example — cache-miss routing sequence

1. Client calls Router::route(key=K)
2. Local cache (version 41) has no entry covering K (K just moved in a split)
3. Router forwards op to shard server per stale cache -> Shard_7
4. Shard_7 no longer owns K (cutover happened at version 42)
5. Shard_7 returns KeyNotFound{current_version: 42}
6. Router::refresh() re-fetches map version 42 from the metadata store
7. Router::route(key=K) against version 42 -> Shard_12 (correct owner)
8. Op retried once against Shard_12 -> success

Total added latency for the miss path: one refresh RTT (≤ 5 ms, M3 §29) plus one retry RTT; the steady-state (cache-hit) path never executes steps 3–7 (P14, I6).

8.5 Malformed-input example

A partition-map record with crc32 mismatching its payload (single bit-flipped byte in transit or at rest) is rejected at the metadata-store read boundary before the scheme oneof is even inspected — get_partition_map returns Error::PartitionMapCorrupt rather than attempting a best-effort partial decode. The routing tier treats this identically to a metadata-store outage: continue serving the last-known-good cached map (P14) and alert (T8, FM-class in §24).

8.6 Failure-path example — coordinator crash mid-cutover

t0: Coordinator issues CAS(map_v41 -> map_v42) for the cutover of job J.
t1: CAS succeeds at the metadata store (map is now v42); coordinator crashes
    before writing JobState::Completed.
t2: Coordinator restarts; reads pending jobs; finds J in state `Cutover`.
t3: Coordinator re-reads the partition map: v42, matching the cutover it was
    attempting -> the CAS already landed -> transition J directly to `Completed`.
    (If the re-read map were still v41, the coordinator would retry the CAS.)

This is why every state transition is persisted before the next step begins (I12): the coordinator can always tell, from (JobState, current_map_version) alone, which side of the CAS it crashed on, with no ambiguity and no operator involvement (§19.9).

pub struct PartitionKey(pub Vec<u8>);
impl PartitionKey {
    pub fn new(bytes: impl Into<Vec<u8>>) -> Self;
    pub fn as_bytes(&self) -> &[u8];
}

pub fn encode_composite(tenant_id: &[u8], row_key: &[u8]) -> Result<PartitionKey, KeyError>;

Ownership: PartitionKey owns its bytes (clone cost dwarfed by the network hop that follows, §2). Mutation: immutable after construction. Concurrency: Send + Sync, freely shared. Compatibility: encode_composite enforces the grammar of §8.1 at construction — malformed byte order is a construction-time error, never a runtime one.

14. Phase 2 — Hash Partitioning

14.1 Objectives

Implement fixed-bucket hash partitioning (hash(key) mod N) with a hard resize-forbidden guard (I10, P1) and the logical-bucket-to-physical-shard indirection that gives it partial elasticity without a rehash.

14.2 Detailed Implementation Steps

  • Implement route_hash_partitioned: buckets[hash_fn(key) % buckets.len()] using xxhash3 (ADR-07, §9) as the default HashFn (§11.2).
  • Implement validate_hash_bucket_count_unchanged: a construction-time/CAS-time guard rejecting any PartitionMap::Hash update whose buckets.len() differs from the prior version (I10).
  • Implement BucketAllocator: a logical-bucket (large, fixed N=1024+) to physical-shard indirection table, following the Pinterest 2015 and pre-migration Discord pattern (§5) — moves only the reassigned logical buckets' keys when physical capacity changes, without a full rehash.
  • Wire PartitionMap::Hash into Router::route (§11.6); route_range for this variant returns RoutingError::RangeScanUnsupported (fan-out is a caller decision, not a router default, §14.6).

14.3 Deliverable

shard-core::hash supports O(1) point routing at a fixed bucket count, a hard resize guard, and an optional logical-bucket indirection layer for partial elasticity.

14.4 Acceptance Criteria

  • route produces a uniform distribution over N buckets for 1M random keys: chi-squared p-value > 0.01 (fixture hash.uniformity, ties to M-hash in §22 Appendix B).
  • validate_hash_bucket_count_unchanged rejects every mismatched-bucket-count update, 100% of attempts (fixture hash.resize_rejected).
  • BucketAllocator re-mapping moves only the reassigned buckets' keys — 0 keys move outside the reassigned buckets (fixture hash.bucket_reassign_isolated).

14.5 Conformance Fixtures

Fixture Purpose Expected Output
hash.uniformity 10M keys → 100 buckets via xxh3 + mod chi-squared p > 0.01
hash.resize_rejected attempt bucket-count change Error::HashResizeForbidden, always

hash.poor_hash_regression CRC32 substituted for xxh3 (negative test) Fails uniformity — guards against hash-fn regressions

14.6 Pitfalls

  • hash(key) % N with a poorly distributed function (CRC32 on short keys, Java's String.hashCode, Python's hash()) clumps keys onto a few buckets; xxhash3/SipHash are the only sanctioned choices (ADR-07/08, §9).
  • Range scans over a hash-partitioned keyspace fan out to every shard and force a client-side merge-sort — there is no fix at this layer; a secondary index (§20) adds a hop, it does not remove the fan-out for the primary keyspace.
  • "Rebalance by moving half the buckets" is a category error: hash(key) % N_old and hash(key) % N_new are uncorrelated (I10) — moving buckets relabels them, it does not move the keys; only BucketAllocator's fixed-N indirection avoids a full rehash.

14.7 Performance Concerns

route is O(1): one hash computation plus one modulo, ~10 ns on modern x86_64 (ADR-07). The BucketAllocator indirection adds one array lookup — still O(1), negligible against M1 (§29).

14.8 Edge Cases

N=1 (degenerate single-bucket map); a key whose hash collides exactly with another key's hash under a 64-bit truncation (birthday-bound negligible at 10-billion-key scale, §33); a BucketAllocator reassignment attempted mid-flight of an in-progress read (must be linearized against the CAS on the enclosing partition map, I4).

14.9 Failure Analysis

A hash-uniformity regression (e.g., an accidental swap to a poor hash function) is caught by hash.poor_hash_regression in CI before merge, not in production — the property test is a regression gate, not just an initial-correctness check (P13). If it escapes to production, the symptom is a hot-shard alert (P10, §19.4) with no corresponding tenant/key explanation, which is itself the diagnostic signal to check the hash function.

14.10 Operational Notes

Metric hash_bucket_load_skew_ratio (max bucket load / average) feeds the same hot-shard dashboard as the consistent-hash variant (§15.10); shardctl map show --scheme=hash prints the current bucket-to-shard table.

15. Phase 3 — Consistent Hashing

15.1 Objectives

Implement the consistent-hash ring with virtual nodes (Karger et al. 1997, §5) and the bounded-loads variant (Mirrokni–Thorup–Zadimoghaddam 2016, §5), enforcing I9 (vnode floor) at construction and delivering elastic add/remove with the K/N movement bound.

15.2 Detailed Implementation Steps

  • Implement ConsistentHashRing::new (§11.3): generate vnode_count tokens per physical shard via xxhash3 over (ShardId, vnode_index) (ADR-06, ADR-07); sort tokens; reject construction below 100 vnodes/physical (I9, P3).
  • Implement ConsistentHashRing::route: binary search (partition_point) for the first token ≥ hash(key), wrapping at the ring boundary.
  • Implement ConsistentHashRing::route_bounded: cap each bucket's load at (1 + ε) × average_load; overflow spills forward to the next token (ADR-23; the Mirrokni et al. 2016 algorithm, §5).
  • Implement ring mutation on shard add/remove: inserting/removing vnode_count tokens is the only mutation path; the property test reshuffle_minimality.consistent_hash asserts the K/N bound from Karger's 1997 proof (§5) holds empirically.
  • Wire PartitionMap::ConsistentHash into Router::route (§11.6); load snapshots for route_bounded refresh every ≤ 5 s (§15.6 pitfall).

15.3 Deliverable

shard-core::consistent_hash supports elastic ring membership with a measured K/N movement bound and an optional load cap.

15.4 Acceptance Criteria

  • Plain consistent-hash routing: 10M keys, 100 shards, 256 vnodes each — load imbalance ≤ 10% (max bucket / average) (fixture ch.load_imbalance).
  • Adding one shard (256 new vnodes) reassigns ≤ 1.1× the theoretical K/N bound — for N=100, ≤ 1.1% of keys (fixture ch.reshuffle_minimality).
  • Bounded-loads routing keeps every bucket ≤ 1.25× average load (ε = 0.25) (fixture ch.bounded_loads).
  • ConsistentHashRing::new with vnode_count < 100 returns RingError::InsufficientVnodes, 100% of attempts (fixture ch.vnode_floor_enforced).

15.6 Pitfalls

  • vnode_count = 1 (no virtual nodes) is the canonical mistake: load imbalance reaches 2× on a 10-shard ring (Karger 1997, §5); I9 makes this a construction-time error, not a runtime surprise.
  • A non-uniform hash function (CRC32, FNV) for token generation clumps vnodes and balloons imbalance — xxhash3/SipHash only (ADR-07/08).
  • route_bounded with a stale load snapshot (> 5 s old) spills to the wrong bucket; the load-snapshot refresh interval is a hard operational requirement, not a tuning knob.

15.7 Performance Concerns

Ring lookup is O(log(vnodes)) via binary search — at the §4 ceiling (2,560,000 vnodes), log₂(2.56M) ≈ 21.3 comparisons, still sub-microsecond and within M2 (§29). Ring construction (shard add/remove) is O(vnode_count log(vnodes)) and runs off the hot path in the coordinator.

15.8 Edge Cases

A ring with exactly one physical shard (all tokens map to it — a degenerate but valid ring); two shards whose vnode tokens happen to collide at the same 64-bit value (probability negligible at our scale, §33); removing the last remaining shard (rejected — a ring must always own the full keyspace).

15.9 Failure Analysis

A ring constructed with vnode_count below the I9 floor never reaches production because construction itself fails — there is no runtime failure mode for this class. A load-imbalance failure (ring correctly constructed but skewed by adversarial keys) is instead a hot-shard detector event (P10, §19.4), not a consistent-hashing bug per se.

15.10 Operational Notes

Metric ch_load_imbalance_ratio and ch_vnode_count are exported per ring; shardctl ring inspect prints the current token distribution histogram for on-call debugging of suspected skew (§25).

16. Phase 4 — Jump Consistent Hash & Rendezvous Hash

16.1 Objectives

Implement the two stateless partitioning schemes: jump consistent hash (Lamping & Veach 2014, §5) for sequential-bucket-ID, grow-only clusters, and rendezvous/HRW hashing (Thaler & Ravishankar 1998, §5) for small, stateless, optimally-disruptive-minimal replica selection.

16.2 Detailed Implementation Steps

  • Implement jump_consistent_hash(key: u64, num_buckets: i32) -> i32: the Lamping–Veach algorithm verbatim against the paper's reference vectors (§5) — O(log N), stateless, pure.
  • Implement rendezvous_route(shards, key) -> ShardId: compute hash(key || shard_id) per candidate shard (xxhash3, ADR-07) and select the maximum-weight shard — O(N), stateless.
  • Implement top-K rendezvous (sort all N weights, take the top K) for replica-set selection — documented as the mechanism, not a new type (reuses rendezvous_route's weight computation).
  • Wire PartitionMap::JumpHash/Rendezvous into Router::route (§11.6); document the bucket-ID indirection requirement for jump hash (§16.6) at the API boundary.

16.6 Pitfalls

  • Jump hash assumes contiguous integer bucket IDs 0..N; string-named or non-contiguous shard IDs need an indirection table from jump-hash output to shard (§16.2's documented API requirement).
  • Jump hash supports only "add bucket N" and "remove the highest bucket" — arbitrary removal is unsupported; an implementation that pretends otherwise silently misroutes (fixture jump.remove_non_highest_rejected exists to catch a regression here).

16.7 Performance Concerns

Jump hash: O(log N), ~10 ns at N = 1000 (Lamping & Veach 2014, §5). Rendezvous: O(N) per route — acceptable to hundreds of shards (M2-adjacent budget, §29) but excluded from the 10,000-shard consistent-hash use case by design.

16.8 Edge Cases

16.9 Failure Analysis

Misuse of jump hash's unsupported arbitrary-removal path is a design-contract violation, not a runtime-detectable fault — mitigation is API-level: the public PartitionMap::JumpHash mutation path only exposes append/remove-highest operations (§16.2), making the unsupported case uncompilable rather than merely undocumented.

17.1 Objectives

Replace the Phase-0 Postgres placeholder with the production MetadataStore backends: etcd (default, ADR-04), ZooKeeper (pluggable, ADR-05), and an internal Raft option (§17.5). Establish watch-and-cache and lease-based ownership as first-class mechanisms.

17.2 Detailed Implementation Steps

  • Implement EtcdMetadataStore (§11.6) over etcd_client: get_partition_map reads mod_revision as the version (I5); put_partition_map uses etcd's Txn::compare for the CAS (I4); backed by the etcd v3 API docs (§5).
  • Implement watch_partition_map: opens an etcd watch on the map key; every update fires a Watcher notification consumed by the routing tier's cache (§18.4).
  • Implement acquire_lease/renew_lease: etcd lease API with a fencing token that strictly increases per acquisition (I8); TTL default 30 s (ADR-33 — expiry judged by the metadata store's server timestamp, not client wall-clock).
  • Implement ZooKeeperMetadataStore behind the same trait (ADR-05): ephemeral nodes for leases, watches for the partition map, following the ZooKeeper Programmer's Guide (§5). raft.rs under shard-metadata ships a 3-or-5-node internal Raft group (Ongaro & Ousterhout 2014, §5) for deployments that cannot adopt an external store — the FoundationDB/CockroachDB approach (§5 ref-impls).
  • Reject any candidate backend that cannot certify linearizable reads at the trait level (P6, I7) — this is a compile-time/construction-time contract, not a runtime check.
  • Wire the watch-and-cache pattern: the routing tier's local arc-swap cache is replaced atomically on every watch notification, cutting effective refresh latency from the 30 s TTL fallback to ≈ 50–100 ms (§4, ADR-09).
  • Wire lease-based ownership into shard-coord: each shard's leaseholder is the process currently authoritative for it; renewal extends the lease, failure to renew (crash) lets it expire, and the next acquirer gets a strictly larger fencing token (I8) — this is the primitive that guarantees only one coordinator instance drives a given resharding job.
  • Land shard-metadata::raft: a 3-or-5-node internal consensus group colocated with shard-coord, for deployments that cannot adopt etcd/ZooKeeper — trading an external dependency for more complex bootstrap and recovery (CockroachDB/FoundationDB precedent, §5).

17.6 Pitfalls

  • etcd's mod_revision is cluster-global, not per-key — a high revision number does not by itself imply staleness on this key; always compare the KeyValue::mod_revision from the actual response (I5).
  • Treating an eventually-consistent store (e.g., DynamoDB without strongly-consistent reads, S3) as the metadata backend silently reintroduces split-brain; the trait-level linearizability requirement (P6, I7) exists precisely to reject this at construction rather than in production.
  • A lease TTL shorter than the worst-case GC pause or network blip produces phantom failovers; 30 s is the default, tunable per deployment, but must always exceed the deployment's observed p99.9 pause/blip duration.

17.7 Performance Concerns

CAS round trip against local etcd: ≤ 5 ms (M3, §29). Watch propagation: ≤ 100 ms median (M4). Lease renewal traffic at max scale (10,000 shards, 30 s TTL/3 renewal cadence) is ≈ 1,000 RPCs/sec sustained against the metadata store (§33 CM12) — a capacity-planning input, not a router-side cost.

17.8 Edge Cases

A metadata-store outage: the routing tier continues serving from its last cached map (P14) but new splits cannot start (coordinator stuck) — a degraded-but-correct mode, not a failure (§17.9 expands this). A watch stream disconnect during an active resharding job is handled by the coordinator's own reconciliation loop (§19.2), not by the metadata-store client.

17.9 Failure Analysis

Metadata-store quorum loss is Failure Class FM1 (§24): routing continues correctly on cached state (I6, P14); only new resharding plans are blocked. Detection: watch-stream disconnect plus CAS timeout. Recovery: restart or fail over the quorum; no data-plane action required. This is the single most important operational property of the whole design — a metadata-store outage degrades elasticity, never correctness.

17.10 Operational Notes

Dashboards: metadata_cas_conflict_total, metadata_watch_latency_ms, lease_renewal_rate. Runbook: docs/runbooks/metadata-quorum-loss.md (§24 FM1). Rolling upgrade: etcd cluster upgrades follow etcd's own documented rolling-upgrade procedure; shard-metadata clients tolerate a brief watch-stream reconnect during this window by design (§17.3).

18. Phase 6 — Routing Tier

18.1 Objectives

Implement the three routing topologies (smart-client, proxy, hybrid — ADR-14) sharing one lock-free cache implementation, and the version-checked stale-cache retry that makes bounded staleness safe (P5, P14, I6).

18.2 Detailed Implementation Steps

  • Implement SmartClientRouter (§11.6) embedding an arc_swap::ArcSwap<VersionedPartitionMap> cache (ADR-21) plus an Arc<dyn MetadataStore> handle.
  • Implement route_and_send: route, dispatch to the shard server, and on KeyNotFound{ current_version} where current_version > self.version(), call refresh() then retry once (§8.4 worked example; I6).
  • Implement shard-proxy (listener.rs, forwarder.rs): a stateless forwarder speaking the application protocol on the client side and shard-net on the shard side — the Vitess vtgate pattern (§5 ref-impl).
  • Implement hybrid mode: the SDK's RouteRequest.client_map_version (§11.7) field lets the proxy validate the cached version per request and reject/refresh on mismatch (ADR-15).
  • Implement the route() hot path as a single arc_swap::Load plus one PartitionMap lookup — dispatch over the five variants of §11.2, no locking anywhere (ADR-21; MM2, §31).
  • Implement batched cross-shard fanout (fanout.rs): group ops by owning shard, one network call per shard rather than per key (§22.3 continues this in Phase 10).

18.3 Deliverable

shard-router and shard-proxy both implement Router (§11.6) against the same cache machinery; a client can select smart-client, proxy, or hybrid mode at startup with no code change to the calling application beyond configuration.

18.4 Acceptance Criteria

  • route(key) latency on a cache hit ≤ 1 µs for a 1000-shard range map (M1, §29).
  • refresh() from local etcd completes in ≤ 5 ms (M3, §29).
  • A Jepsen-style test that triggers a split mid-traffic shows 0 operations incorrectly routed twice (fixture routing.stale_cache_jepsen).
  • Proxy mode sustains 100,000 routes/sec on a single core (fixture routing.proxy_throughput).

18.6 Pitfalls

  • Caching the partition map without a version check is the canonical bug: a stale cache routes to an ex-owner indefinitely because the shard server's rejection is silently retried forever without ever refreshing — the version-check-plus-refresh (I6) is mandatory, not optional.
  • Refreshing on every request "to be safe" defeats the cache and destroys M1/M2 — the shard-server-rejected path is the correct circuit breaker (P14, MM2 §31).
  • arc-swap is wait-free for readers but the old Arc still needs reclaiming on write; this is fine at the watch-driven update cadence (~once per active resharding event) but would be a problem in a tight write loop — never write to the cache except on watch notification or TTL expiry.

18.7 Performance Concerns

Hot path: one atomic load (arc-swap) plus one PartitionMap-variant dispatch — no heap allocation (M14, §29). Proxy mode adds one network hop and its own cache; hybrid mode adds one version comparison per request (ADR-15) — quantified cost, not free, and documented as such.

18.8 Edge Cases

A route() call racing an in-flight cache replacement (the arc-swap guarantees the reader sees either the old or the new map atomically, never a torn read); a KeyNotFound whose current_version is older than the client's own cached version (a reordering bug elsewhere — treated as RoutingError::VersionRegression and logged, never silently accepted, per I5); a proxy that loses its metadata-store watch connection mid-request (falls back to its last cached map, same as §17.8).

18.9 Failure Analysis

Routing-cache divergence is Failure Class FM2 (§24): symptom is a KeyNotFound rate spike; root cause is a stale cache post-split before TTL/watch catch-up; auto-recovery is the refresh-and-retry path (I6); this is explicitly a performance defect, never a correctness defect (P14) — blast radius is added latency on the affected keys only, bounded by one refresh RTT.

18.10 Operational Notes

Metrics: routing_cache_hit_ratio, routing_stale_reject_total, routing_version_lag_ms (client version vs. metadata-store's latest). Tracing: every sampled route() call emits the (key_hash_prefix, shard_id, cache_hit, partition_map_version) tuple (P12). Runbook: docs/runbooks/routing-cache-divergence.md.

19. Phase 7 — Live Resharding

19.1 Objectives

Implement the online split/merge protocol (P4) as a persisted state machine (§8.3, I12) driven by automatic hot-shard detection (P10), with rate-limited data movement (P11, ADR-12) that never loses or duplicates a key (I2, I3).

19.2 Detailed Implementation Steps

  • Implement execute_split/execute_merge (shard-coord::executor) driving JobState (§11.5) through Pending → Scanning → Validating → Cutover → Completed, persisting each transition to the metadata store before advancing (I12, §8.3/§8.6).
  • Implement the scan phase: the destination back-fills the source's lower half via a rate-limited iterator (TokenBucket, §11.8, ADR-12); writes to the lower half are double-written to source and destination for the duration of the scan (I3).
  • Implement the cutover phase: a single MetadataStore::put_partition_map CAS that atomically adds the new boundary (I4); the source rejects further writes to the vacated range, returning KeyNotFound{current_version} (§8.4).
  • Implement coordinator crash-recovery: on restart, read all non-terminal JobStates and resume from the last persisted state, using (JobState, current_map_version) to disambiguate which side of the CAS was crossed (§8.6).
  • Implement detect_hot_shards (shard-coord::detector): flag a shard when QPS AND bytes/sec both exceed threshold for 60 s, OR p99 exceeds 2× cluster median (P10, ADR-10).
  • Implement pivot selection reuse from §13.2 (median-by-byte-volume) for automatic splits; merge planning selects adjacent under-utilized ranges (< 25% of target shard size).
  • Implement execute_merge as the structural inverse of split (same scan+cutover shape, same rate limit).

19.3 Deliverable

shard-coord drives online splits and merges to completion under live synthetic load, survives a mid-job process restart, and triggers automatically from hot-shard telemetry.

19.4 Acceptance Criteria

  • A live split of a 1 GB shard at the default 10 MB/s/replica rate completes in ≤ 110 s (60 s scan + cutover + validation overhead) with 0 client-visible writes lost (M6, §29).
  • A live merge of two 500 MB shards completes in ≤ 110 s (M7, §29).
  • 10,000 random splits/merges on a 100-shard cluster under synthetic load: 0 keys lost, 0 keys duplicated (fixture resharding.split_merge_property).
  • Coordinator restart mid-split, repeated 100 times: 100/100 jobs resume and complete correctly (fixture resharding.coordinator_restart).
  • Hot-shard detection fires within 60 s of a sustained load spike (M8, §29).

19.5 Conformance Fixtures

Fixture Purpose Expected Output

19.6 Pitfalls

  • Forgetting the double-write during the scan phase loses writes: writes to the lower half during the scan go to the source only; the destination's back-fill scan does not see them; cutover silently loses them (I3; fixture resharding.double_write_omitted guards this).
  • A non-atomic cutover (two separate metadata writes: "source loses range," then "destination gains range") admits a window where both or neither shard accepts a write — the single CAS (I4) is the only correct primitive.
  • Rate-limiting the read side without rate-limiting the apply side causes destination-side queue buildup that can crash the destination; both sides must respect the same TokenBucket (§11.8).
  • Hot-shard detection on raw QPS alone false-positives on a normal weekly traffic cycle (Monday peak vs. Sunday idle) — the AND-condition with bytes/sec, or the p99-vs-median OR-branch, exists specifically to prevent this (ADR-10).

19.7 Performance Concerns

Scan-phase throughput is bounded by the configured rate limit (default 10 MB/s/replica, ADR-12) — the WeChat Pay 2019 postmortem (§5) documents the cost of skipping this bound: a 30-minute window of tripled write latency and doubled read latency from an unthrottled rebalance. Cutover itself is a single CAS — sub-5-ms (M3) — so the visible cutover cost to clients is one retry RTT at worst (§8.4).

19.8 Edge Cases

A split whose pivot lands on an already-existing boundary (rejected, §13.8); a merge attempted on two ranges that are not actually adjacent (rejected at planning time); a hot-shard event that fires during an already-in-flight split of the same shard (queued, not concurrent — the coordinator's per-cluster job-concurrency bound, §4, prevents overlapping jobs on one shard); a coordinator restart that finds a job in Cutover whose CAS had not yet landed (re-attempts the CAS rather than assuming completion, §8.6).

19.9 Failure Analysis

Coordinator crash mid-split is Failure Class FM3 (§24): detection is a missing job-state heartbeat; auto-recovery resumes from the last persisted JobState (I12); blast radius is bounded to the single in-flight job, because every other shard's ownership is untouched by a crashed job. A double-write bug (FM4) or non-atomic cutover (FM5) are design-contract violations, not operational faults — they have no auto-recovery path and require the live_resharding conformance fixtures (§19.5) to catch them before production.

19.10 Operational Notes

Metrics: coord_split_rate, coord_job_state{state}, rebalance_bytes_per_sec, hot_shard_detected_total. Runbook: docs/runbooks/stuck-resharding.md (FM3). shardctl job list/shardctl job abort <id> are the operator-facing controls for a job stuck beyond its expected duration.

20. Phase 8 — Vindexes (Secondary-Index Sharding)

20.1 Objectives

Implement the Vitess-derived vindex two-hop pattern (§5 ref-impl): a secondary-index keyspace sharded independently by its index column, so a non-primary-key lookup does not fan out to every shard (P8, I13).

20.2 Detailed Implementation Steps

  • Implement the Vindex trait (§11.4) with four production variants: HashVindex (index column hashes directly to a primary-shard key, 1 hop), LookupVindex (a full separate sharded keyspace, 2 hops), NumericVindex (small-integer pass-through, column % N), UnicodeLooseMd5Vindex (collation-aware string hashing).
  • Implement the two-hop lookup sequence: route_index(vindex_name, value) → vindex_shard; vindex_shard.lookup(value) → user_id; route_primary(user_id) → user_shard (§20.3 diagram below reused from the worked-example pattern of §8.4).
  • Implement LookupVindex's own PartitionMap, sharded by the index column, never by the primary key (P8) — reuses the same five partitioning schemes (§13–§16) as the primary keyspace.
  • Implement the consistency-tradeoff options for keeping vindex and primary in sync: (1) 2PC (ADR-17 hook), (2) eventually-consistent index with async catch-up, (3) index-first write with tombstone-on-failure (the Vitess default) — document the choice loudly per option.
  • Implement client-side caching of the vindex-shard response to amortize the second hop across repeated lookups of the same index value. The full sequence — route_index("email", value) → vindex_shard; vindex_shard.lookup(value) → user_id; route_primary(user_id) → user_shard; user_shard.get(user_id) → row — costs 4 network hops uncached; caching Step 1–2's result amortizes it to effectively 2 for repeated queries of the same value.

20.3 Deliverable

shard-core::vindex ships four Vindex implementations passing lookup/reverse symmetry (I13) and a documented, tested consistency-tradeoff default (index-first write).

20.4 Acceptance Criteria

  • Hash/Lookup/Numeric/UnicodeLoose vindex implementations pass the reverse-symmetry property test: reverse(lookup(x)) == x for 100,000 random inputs, 0 violations (fixture vindex.reverse_symmetry).
  • The two-hop lookup pattern sustains 10,000 lookups/sec/core (fixture vindex.lookup_throughput).
  • A consistency-test suite validates index-first-write behavior under injected mid-write failure: every dangling tombstone is reconciled within one async catch-up cycle (fixture vindex.tombstone_reconciliation).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
vindex.reverse_symmetry 100,000 random lookups, all 4 vindex types reverse(lookup(x)) == x, 0 violations (I13)
vindex.lookup_throughput sustained two-hop lookups, 1 core ≥ 10,000/sec

20.6 Pitfalls

  • Co-locating the vindex with the primary on a hot key concentrates two hotspots on the same shard (P8) — fixture vindex.colocated_hotspot_rejected guards the negative case.
  • Sharding the vindex by the primary key (rather than the index column) reproduces the fan-out-to-all-shards problem the vindex exists to solve.
  • Option 3 (index-first write) requires the async catch-up job to actually run; without it, tombstones accumulate unboundedly and index storage grows without bound (FM8, §24).

20.7 Performance Concerns

Each uncached lookup costs 4 network hops (§20.2); client-side caching of Step 1–2 amortizes this to effectively 2 hops for repeated queries of the same value. NumericVindex/HashVindex collapse to 1 hop when the index column is already shard-key material.

20.8 Edge Cases

A vindex lookup for a value with no corresponding primary row (returns VindexError::NotFound, distinct from a routing error); a non-unique lookup vindex (is_unique() == false) returning multiple primary keys — the caller, not the vindex, resolves the fan-in; a vindex reconciliation race where the async catch-up job runs concurrently with a fresh index-first write for the same key (ordered by the write's own timestamp, last-writer-wins for the tombstone state).

20.9 Failure Analysis

Vindex tombstone accumulation is Failure Class FM8 (§24): symptom is unbounded index storage growth; root cause is a missing/failed async catch-up sweep; detection is a tombstone-count metric trend; recovery is a manual reconciliation-job trigger. Blast radius is contained to the vindex keyspace — the primary keyspace's correctness (I1, I11) is unaffected by a vindex-side inconsistency.

20.10 Operational Notes

Metrics: vindex_lookup_latency_ms, vindex_tombstone_count, vindex_reconciliation_lag_s. The docs/architecture/vindexes.md runbook documents how to add a new vindex type without touching the primary keyspace's PartitionMap (§11.2) — vindex and primary partitioning are fully decoupled by design (P8).

21. Phase 9 — Tenant-Aware Sharding

21.1 Objectives

Implement composite-key tenant isolation (P7, I14): tenant ID as the mandatory high-order prefix of the routing key, tenant-boundary-aware splits, and per-tenant rate limiting against noisy neighbours.

21.2 Detailed Implementation Steps

  • Implement encode_composite(tenant_id, row_key) (§11.1, §8.1 grammar): LEB128 length-prefixed tenant ID followed by the row key; reject any caller-provided byte layout that violates the grammar's ordering (I14, ADR-13).
  • Extend the split planner (§19.2) with tenant-aware pivot selection: prefer a (tenant_id, "") pivot so a split separates whole tenants rather than cutting through one tenant's rows, following the Spanner directory-placement precedent (§5) at a lighter weight.
  • Implement single-hot-tenant handling: when one tenant's data exceeds a shard's capacity, the planner falls back to a (hot_tenant_id, row_key) pivot, splitting that tenant across two shards — documented explicitly as "the tenant outgrew one shard," with the option to pre-allocate a dedicated shard at provisioning time instead.
  • Extend detect_hot_shards (§19.2) with per-tenant load attribution within a shard; a tenant exceeding 80% of its shard's capacity is flagged "hot" (extends P10 to tenant granularity).
  • Implement per-tenant rate limiting in the routing tier: a tenant exceeding its configured quota receives Error::TenantRateLimited; quota is stored in the metadata store alongside shard descriptors (§11.3).

21.3 Deliverable

shard-core::key::encode_composite plus tenant-aware split-pivot selection and per-tenant rate limiting are wired end to end; a multi-tenant deployment isolates a noisy tenant without degrading its neighbours.

21.4 Acceptance Criteria

  • Composite-key encoding round-trips correctly for tenant IDs of length 1, 10, 100, and 1000 bytes, 0 decode errors (fixture tenant.encode_roundtrip).
  • Given 1,000 tenants across 10 shards, an automatic split selects a tenant-boundary pivot in ≥ 95% of trials (fixture tenant.split_pivot_boundary).
  • A per-tenant rate limit fires for a tenant exceeding 10× its configured baseline, with 0 measurable latency change for neighbouring tenants on the same shard (fixture tenant.isolation_under_noise).

21.5 Conformance Fixtures

Fixture Purpose Expected Output

21.6 Pitfalls

  • Tenant ID at the end of the composite key (row_key || tenant_id) is the canonical mistake: one tenant's keys fan out across every shard, isolation becomes impossible, and rebalance cost scales with tenant count instead of staying local (P7, I14) — fixture tenant.suffix_encoding_rejected guards this at the API boundary.
  • Fixed-length tenant IDs work without a length prefix; variable-length tenant IDs need the LEB128 length prefix (ADR-13) to avoid ambiguous key boundaries between adjacent tenants.
  • A single-tenant deployment that later goes multi-tenant must rewrite every key if it did not adopt composite encoding from day one — plan tenant-aware encoding early if multi-tenancy is even a possibility.

21.7 Performance Concerns

Composite-key encoding adds a fixed LEB128-length-prefix overhead (1–2 bytes typical) to every key — negligible against the §4 avg key size of 64 bytes. Per-tenant rate-limit checks add one lookup in a per-shard tenant-quota table on the hot path — bounded and O(1) via a hash map keyed by tenant ID.

21.8 Edge Cases

A tenant ID of zero length (rejected — every tenant must have a non-empty identifier); two tenants whose IDs are byte-prefixes of each other (e.g., "ab" and "abc") — the LEB128 length prefix disambiguates them unambiguously, unlike a naive delimiter-based encoding; a split pivot that would divide the only tenant on a shard (falls back to the hot-tenant row-key pivot, §21.2).

21.9 Failure Analysis

A key-encoding regression that places tenant ID at the wrong position is Failure Class FM9 (§24): symptom is a per-tenant shard-fan-out-ratio metric spike; detection is that same metric crossing a configured threshold; recovery is re-encoding and re-sharding the affected tenant — there is no automatic recovery because the bug is a design-contract violation, not a transient fault (mitigated at compile/construction time by the typed encode_composite API, §21.2).

21.10 Operational Notes

Metrics: tenant_shard_fanout_ratio, tenant_rate_limited_total, tenant_hot_flag_total. shardctl tenant show <id> reports which shard(s) a given tenant currently spans — a single shard in the healthy case, more than one only during an in-flight hot-tenant split (§21.2).

22. Phase 10 — Performance Hardening

22.1 Objectives

Close every M# performance target (§29) end to end: hot-path allocation elimination, batched cross-shard fanout, range-scan prefetch, and partition-map wire-size discipline — the phase that turns "functionally correct" into "meets the §4 envelope at 10,000-shard scale."

22.2 Detailed Implementation Steps

  • Finalize the partition-map wire format's fixed-width header (magic + version + checksum, §8.2) so a 1,000-shard range map serializes to ≈ 20 KB and a 10,000-vnode ring to ≈ 150 KB — bounding metadata-store payload size and CAS latency (M3, §29).
  • Finalize the lock-free routing cache (§18.2): confirm zero heap allocation on the route() hot path via criterion+ allocator-counting benchmarks (M14, §29; ADR-21).
  • Implement batched cross-shard fanout (shard-router::fanout, §11 §18.2): group per-key ops by owning shard, dispatch one network call per shard rather than per key, tokio::spawn one task per shard batch, join all results.
  • Implement range-scan prefetch: a scan crossing a shard boundary issues the next shard's first batch in parallel with the current shard's response; pipeline depth defaults to 2 and is bounded (never unbounded, ADR-34's backpressure principle applied here too).
  • Run the full shard-bench suite (§10) against all five partitioning schemes and both routing topologies; record results under benchmarks/results/ for the Performance Engineering gate (§29).

22.3 Deliverable

Every M# target in §29 is met and CI-gated (ci.yml/conformance.yml fail the build below threshold); benchmarks/results/ holds a reproducible baseline for future regression detection.

22.4 Acceptance Criteria

  • 1,000,000 routes/sec/core sustained (M5, §29).
  • Partition-map refresh from local etcd ≤ 5 ms (M3, §29).
  • A 10,000-key cross-shard fanout completes in O(largest_shard_response_time), not O(sum_of_shard_response_times) — measured ratio ≤ 1.2× the slowest single shard's response time (fixture perf.fanout_parallelism).
  • A range scan of 1,000,000 keys across 10 shards completes in ≤ 2 s (M10, §29).
  • Zero heap allocations on the route() hot path across 1M calls (fixture perf.zero_alloc_hot_path).

22.6 Pitfalls

  • Cloning the routing cache on every route() call defeats the wait-free read; ArcSwap::load() returns a cheap guard, never a deep clone — a regression here silently reintroduces allocation onto the hot path (guarded by perf.zero_alloc_hot_path).
  • Issuing one network call per key (unbatched fanout) opens a connection per request; batching collapses N per-key calls into one connection-reusing call per shard (§22.2).

This phase's entire content is performance concerns — see §22.2/§22.4/§29 for the full quantified target set; nothing here is qualitative.

22.8 Edge Cases

A fanout across a single shard (degenerates to one network call, no parallelism needed — must not regress into unnecessary task-spawn overhead); a range scan whose result set is smaller than one prefetch batch (prefetch degrades to a no-op, not an error); a partition-map payload that approaches but does not exceed the wire-size budget of perf.wire_size_budget at the §4 shard ceiling (10,000 shards) — verified, not assumed.

22.9 Failure Analysis

A performance regression caught by ci.yml/conformance.yml (any M# below threshold) blocks merge — this is a build failure, not a production incident, because the gate exists precisely to keep regressions out of production (P13, ADR-20). A regression that escapes to production manifests as a generic latency-budget alert (§25) with no distinguishing signature from other performance-class incidents; the benchmarks/results/ baseline (§22.2) is the tool that lets an on-call engineer confirm "this got slower" against a known-good number rather than guessing.

22.10 Operational Notes

25. Operational Readiness

Metrics (ADR-28, Prometheus exposition): routing_cache_hit_ratio, routing_stale_reject_total, metadata_cas_conflict_total, coord_job_state{state}, coord_split_rate, rebalance_bytes_per_sec, hot_shard_detected_total, tenant_shard_fanout_ratio, vindex_tombstone_count, ch_load_imbalance_ratio, hash_bucket_load_skew_ratio. Every metric named here also appears in the phase that introduces it (§13–§22) and in the corresponding Threat/Failure row (§23–§24) where applicable.

Tracing (ADR-27): OpenTelemetry spans with W3C traceparent propagation across client → proxy → shard hops; every sampled route() call carries the P12 tuple (key_hash_prefix, shard_id, cache_hit, partition_map_version) as span attributes.

Structured logging (ADR-26): tracing crate, JSON formatter; every log line carries shard_id, partition_map_version, and (where applicable) tenant_id and job_id for correlation with the metrics/tracing above.

Dashboards: one per subsystem — routing (cache-hit ratio, stale-reject rate, latency percentiles), metadata store (CAS conflict rate, watch latency, lease renewal rate), resharding (job-state distribution, split rate, rebalance throughput), tenancy (fanout ratio, rate-limit trips).

Alerting philosophy: alert on the symptom metrics in the Failure Modes table (§24), not on raw resource utilization — e.g., alert on hot_shard_detected_total rate-of-change, not on raw per-shard CPU, because the AND-conditioned detector (ADR-10) already filters noise the way a raw-CPU alert cannot (FM6).

SLOs: routing-tier availability 99.95% (§4); route() p99 ≤ 2 µs (M2, §29); metadata-store CAS p99 ≤ 5 ms (M3, §29); hot-shard detection latency ≤ 60 s (M8).

Incident response: on-call runs the Threat Model (§23) / Failure Modes (§24) tables as the primary triage checklist — each row's Detection column maps directly to an alert, each Recovery column to a first response action.

Named runbooks (docs/runbooks/, §10): hot-shard.md (FM6/FM7), stuck-resharding.md (FM3), metadata-quorum-loss.md (FM1), routing-cache-divergence.md (FM2).

Backup/restore: the metadata store's own backup mechanism (etcd snapshot / ZK snapshot / Raft log compaction) is the backup unit for the partition map and job ledger; shard-data backup is out of scope (delegated to the storage engine, §1). Distributed cross-shard snapshot coordination is PhaseDeferred("§25") (§36).

Deployment topology: shard-coord as a leader-elected singleton per cluster; shard-proxy/shard-router scale horizontally with the application tier; metadata-store backend runs its own quorum topology (3 or 5 nodes) independent of the routing tier.

Canary / rolling upgrade / rollback / migration: shard-proxy and shard-coord support rolling upgrade because the wire protocol is wire_version-gated (§26) — an old and new binary can coexist during a rollout; canary deploys route a small percentage of proxy instances to the new binary and compare routing_cache_hit_ratio/latency against the fleet baseline before full rollout; rollback is a binary redeploy with no data migration required (the partition-map format did not change).

26. Compatibility & Versioning

Wire compatibility: every shard-net message and the partition-map record (§8.2) carries a wire_version; a reader rejects a message with an unrecognized wire_version rather than guessing at a compatible parse. Adding a PartitionMap variant (§11.2) requires a wire_version bump; removing one never happens (only additive changes to the scheme enum).

Storage compatibility: the metadata-store record format (§8.2) is versioned independently of the application-level PartitionMap semantics, so an etcd cluster running an older shard-metadata client can still be read by a newer one within the same major wire_version.

Schema evolution: new Vindex types (§20) are additive — the Vindex trait (§11.4) is stable across versions; a new implementation does not require a wire-format change, only a new registration entry in the metadata store's vindex-type table.

API stability: Router, MetadataStore, Vindex (§11) are the three public trait surfaces; SemVer governs shard-router/shard-metadata/shard-core independently — a breaking change to any trait's signature is a major-version bump for that crate.

Migration: online schema/partitioning-scheme migration across shards (e.g., moving from hash to consistent-hash) is PhaseDeferred("§26") — the current design treats a scheme change as a new-cluster migration, not an in-place upgrade (P1, §36).

Deprecation policy: a deprecated field/variant is marked #[deprecated] for one minor version with a docs/adr/ entry recording the sunset date, then removed in the next major version, following standard Rust ecosystem practice (ADR-19 licensing context, ADR-01 toolchain).

Rolling-upgrade guarantees: any two wire_version-adjacent binaries (N and N+1) can run simultaneously against the same metadata-store cluster without data corruption — this is the property the canary/rolling-upgrade story (§25) depends on.

27. Testing & Verification Strategy

Unit tests: per-module correctness for each partitioning scheme (§13–§16), the metadata-store CAS logic (§17), and the vindex reverse-symmetry contract (§20) — colocated with the crate under test.

Property tests (ADR-29, proptest): partition-assignment determinism (I1), reshuffle minimality (I9-adjacent, per scheme), range-map validity (I11), vindex reverse symmetry (I13) — enumerated per phase's N.5 fixtures (§13.5, §14.5, §15.5, §16.5, §20.5).

Differential tests: routing decisions cross-checked against Cassandra's Murmur3 partitioner, Vitess's hash vindex, and a DynamoDB-style hash scheme on identical inputs (cross_impl/ corpora, §10) — catches subtle algorithmic drift from the reference designs (§5).

Fuzzing (ADR-30, cargo-fuzz): one harness per partitioning algorithm plus partition_map_serde (malformed wire-format inputs, §8.5) and routing (malformed RouteRequests) — 24-hour CI canary, 30-day canary as a Sealed-gate requirement.

Chaos / fault injection: the Jepsen-style fault matrix (§17.7, §19.5) — etcd leader kills, network partitions mid-scan, coordinator crash mid-job — asserts I2–I5, I7, I12 hold under injected faults, not just under happy-path execution.

Deterministic replay: the simulator/ discrete-event harness (§7, §10) reproduces any invariant violation from a single seed, turning a live incident into a debuggable, replayable test case.

Soak testing: a 30-day continuous-load canary with automatic splits/merges firing under synthetic traffic; zero data loss and zero panics is the Sealed-gate bar (M12, §29).

Conformance suite: the conformance/runner (§10, §19.5-style buckets) is the single aggregation point — every property/differential/chaos/endurance bucket reports into conformance.report.json, and Done/Sealed gates read that report, not individual test logs (P13, ADR-20).

Performance-regression gating: the shard-bench suite (§10, §22) runs in CI; any M# target regression beyond a configured tolerance fails the build (§22.9).

Tie-back to invariants: every fixture named across §12–§22's N.5 subsections maps to at least one of I1–I14 (§7); a fixture with no invariant tie-back is dead weight and is not added.

Reproducible builds: Cargo.lock pinned, dependencies vendored, rust-toolchain.toml pins the compiler to 1.78 (ADR-01, ADR-36) — the same commit produces bit-identical release artifacts across CI runs.

Artifact signing: release binaries (shard-proxy, shard-coord, shardctl) are signed via cosign; the signature is verified by the docker-compose/Helm deployment tooling (§10 ops/) before rollout.

SBOM: cargo-cyclonedx generates a Software Bill of Materials per release (ADR-36), published alongside the binary artifacts for supply-chain auditing (T10, §23).

Release channels: stable (tagged releases, SemVer per crate, §26) and nightly (main branch, fuzz/soak canaries only, never recommended for production).

CI/CD topology (ADR-31): GitHub Actions matrix across stable and the pinned MSRV (1.78); separate workflows for ci (build/lint/test), conformance, property, jepsen, soak, security (cargo-audit + cargo-deny), fuzz, and release (§10).

Dependency auditing: cargo-audit runs in security.yml on every push and nightly against the full workspace; a new advisory affecting a pinned dependency fails CI until resolved or explicitly allow-listed with a documented expiry (ADR-32).

29. Performance Engineering

Benchmarking methodology: criterion-based microbenchmarks (shard-bench, §10) per partitioning scheme and routing topology, run on a fixed reference host and recorded in benchmarks/results/ (§22.2) as the regression baseline; every benchmark reports p50/p95/p99, not just a mean.

Allocation analysis: an allocator-counting harness wraps the route() hot path (M14 below); any allocation on that path is a regression, caught by perf.zero_alloc_hot_path (§22.5).

Lock contention analysis: the routing cache uses arc-swap specifically to eliminate reader lock contention (ADR-21); shard-bench::route_latency includes a multi-threaded contention variant (N=1, 8, 64 concurrent readers) to confirm latency does not degrade with reader count.

Cache-locality analysis: the consistent-hash ring's sorted Vec<(u64, ShardId)> (§11.3) is chosen over a BTreeMap for the ring specifically for cache-friendly binary search over contiguous memory — a BTreeMap-based ring would introduce pointer-chasing on every lookup.

Syscall overhead: the proxy's connection pooling (ADR-22, HTTP/2 multiplexing) is the mitigation for the FD-budget constraint derived in §33 CM9 — without multiplexing, per-shard connection counts would exceed the FD budget at max shard count (§4).

Batching: cross-shard fanout (§18.2, §22.2) batches per-shard requests into one network call; range-scan prefetch (§22.2) pipelines shard-boundary crossings.

Tail-latency analysis: M1/M2 are p50/p95/p99-quantified, not mean-quantified, specifically because a sharding router's tail latency (not its mean) determines whether a caller's own p99 SLO survives the routing hop.

30. Scalability Analysis

Constant regardless of scale: route() latency for hash-mod-N and jump hash (O(1)/ O(log N) respectively, effectively flat well past 10,000 shards); the per-key composite-key encoding cost (§21.7).

Grows with shard count N: consistent-hash ring lookup, O(log(N × vnode_count)) (§15.7); range-map lookup, O(log N) (§13.7); rendezvous lookup, O(N) (§16.7, the named reason it is scoped away from the primary large-scale use case, §16.1); routing-table memory, O(N × vnode_count) for the ring (§33 CM5), O(N) for the range map (§33 CM6).

Grows with key count K: total cluster data volume (§33 CM3); rebalance data movement on scheme resize (§33 CM4, CM11); lease-renewal traffic scales with shard count, not key count (§33 CM12).

Named bottlenecks, in order of first impact as the cluster grows:

  1. Rendezvous lookup cost (O(N)) — the first scheme to become impractical, around a few hundred shards (§16.7); mitigated by scoping rendezvous to small clusters/replica selection only (§16.1).
  2. FD budget under one-connection-per-shard — becomes binding before 10,000 shards without HTTP/2 multiplexing (§33 CM9); mitigated by ADR-22/ADR-34.
  3. Metadata-store watch fan-out — etcd's practical per-node watcher ceiling (~10,000, §33 CM10) is reached exactly at the §4 shard ceiling; mitigated by a read-replica/watch-proxy tier beyond that scale (noted, not built — §36).
  4. Routing-table memory for the consistent-hash ring — grows linearly with shard count × vnode count (§33 CM5); mitigated by keeping vnode_count fixed rather than scaling it with cluster size (ADR-06).
  5. Coordinator job-concurrency bound (16 concurrent resharding jobs, §4) — bounds how fast a full-cluster rebalance can complete (§33 CM11); mitigated by increasing the bound only as far as the metadata store's CAS throughput tolerates.

Horizontal scaling: the routing tier (shard-router/shard-proxy) scales horizontally without limit — it holds no durable state. shard-coord is a leader-elected singleton per cluster by design (I4's single-writer requirement) — it does not horizontally scale, but its work (planning, not data movement) is cheap enough that this has not been a bottleneck at the §4 ceiling.

Vertical scaling: the metadata-store quorum benefits from vertical scaling (faster disks reduce CAS latency, M3) more than from horizontal scaling (more nodes increase quorum-write latency, not throughput, for a linearizable store).

Sharding/partitioning of the router itself: out of scope — the routing tier is a stateless cache in front of a single logical partition map; there is no "sharding the sharder" story in this design (a PhaseDeferred("§30") note for a hierarchical/federated router sits in §36 for deployments exceeding the §4 envelope by an order of magnitude).

Coordination overhead: every write to the partition map is a single CAS (I4) — coordination overhead is O(1) per resharding decision, independent of cluster size; it does not compound as the cluster grows, only as the rate of resharding decisions grows (bounded by the coordinator's job-concurrency limit, §4).

Practical ceiling and the levers beyond it: the §4 envelope (10,000 shards, 10-billion keys) is not a hard architectural ceiling — the levers to go further are (a) a watch-proxy tier ahead of the metadata store (bottleneck 3 above), (b) a hierarchical router (deferred, §36), and (c) increasing the coordinator's job-concurrency bound in step with metadata-store CAS capacity.

31. Mental Models & First Principles

  • MM1 — A partition map is a pure function key → shard; the router just evaluates it. Predicts: correctness depends only on the map's correctness, not on routing-code cleverness. Bug class without it: routing bugs get misdiagnosed as storage bugs. Applies in §11 (PartitionMap), §13 (Range).
  • MM2 — The shard server is the ledger of truth; the client cache is a rumor. Predicts: staleness is tolerable, divergence is not corruption. Bug class without it: engineers build a strongly-consistent cache (a quorum read per route) and destroy the latency budget. Applies in §18 (Phase 6), I6 (§7).
  • MM3 — Consistent hashing turns "add a node" into a local edit, not a global rewrite. Predicts the K/N movement bound. Bug class without it: teams pick hash-mod-N for an "elastic" system, then eat a full re-platform under load. Applies in §15 (Phase 3), P3 (§6).
  • MM4 — A split is a transaction with only two externally observable states: before and after; the messy middle is double-written. Predicts scan-phase writes must hit both shards. Bug class without it: forgetting the double-write, silently losing data. Applies in §19 (Phase 7), I3 (§7).
  • MM5 — Every partitioning scheme trades range-scan locality for write-uniformity — you cannot have both. Predicts the choice is always workload-dependent, never universal. Bug class without it: "switch schemes later" regret that costs a quarter. Applies in §13, §14, §15 (Phase 1–3), P1 (§6).
  • MM6 — A secondary index is just another shard map: index one thing, shard by another. Predicts a vindex needs its own partition map keyed by the index column. Bug class without it: co-locating the index with the primary, concentrating a second hotspot. Applies in §20 (Phase 8), P8 (§6).
  • MM7 — Tenant isolation is a key-encoding property, not a runtime feature. Predicts prefix ordering alone determines isolation. Bug class without it: encoding tenant ID suffix-first, silently breaking isolation months later. Applies in §21 (Phase 9), I14 (§7).
  • MM8 — A metadata store that isn't linearizable isn't a metadata store — it's a rumor mill with extra steps. Predicts any weak-consistency backend eventually admits split-brain. Bug class without it: the "eventually-consistent store is good enough" assumption. Applies in §17 (Phase 5), P6 (§6), I7 (§7).

33. Back-of-Envelope Capacity Model

All numbers derive from the §4 System Constraints table; formula shown for each.

  • CM1 — Keys per shard at max scale. keys_total / max_shards = 10^10 / 10^4 = 10^6 keys/shard.
  • CM2 — Average shard data volume. `keys_per_shard × (avg_key + avg_value) = 10^6 × (64 +
    1. B = 3.2×10^8 B = 320 MB/shard.`
  • CM3 — Total cluster data volume. max_shards × shard_data_volume = 10^4 × 320 MB = 3.2×10^6 MB ≈ 3.2 TB (cross-checked: keys_total × 320 B = 3.2×10^12 B = 3.2 TB, matches).
  • CM4 — Rebalance data movement, add-one-shard, consistent hash. Karger's K/(N+1) bound (§5, §15): for N=10,000 → 10,001, moved_keys ≈ 10^10 × (1/10,001) ≈ 9.999×10^5 keys ≈ 320 MB moved — approximately one shard's worth, confirming the theoretical bound in concrete terms.
  • CM5 — Routing-table memory, consistent-hash ring, full cluster. entries = max_shards × vnodes_per_physical = 10^4 × 256 = 2,560,000 tokens; at 16 bytes/entry (u64 token + u32 ShardId + padding), 2,560,000 × 16 B ≈ 41 MB per routing-tier cache instance.
  • CM6 — Routing-table memory, range map, full cluster. entries = max_shards = 10,000 boundaries; at ≈ 116 B/entry (64 B avg key + 4 B ShardId + ≈ 48 B BTreeMap node overhead), 10,000 × 116 B ≈ 1.16 MB — roughly 35× smaller than the consistent-hash ring's routing table (CM5), because a range map has one entry per shard, not per vnode.
  • CM7 — Virtual-node count derivation. Karger's proof (§5) shows imbalance scales approximately as 1/√(vnodes_per_physical); empirically (Dynamo 2007, section 4.2; Cassandra production defaults, §5) ≤ 10% imbalance requires ≥ 256 vnodes/physical — this is why ADR-06 locks 256 as the default, independent of the number of physical shards.
  • CM8 — Hotspot skew ratio budget (bounded loads). ε = 0.25 caps any bucket at (1 + ε) × average_load = 1.25 × average_load (§15, ADR-23); the per-shard fair-share QPS at the M5 target (1,000,000 routes/sec/core) is total_qps / max_shards, so the tolerable per-shard ceiling before spillover is 1.25 × (total_qps / 10,000).
  • CM9 — FD budget vs. one-connection-per-shard. At max_shards = 10,000 with even 10 pooled connections/shard, naive per-shard connections require 10 × 10,000 = 100,000 FDs — above the §4 budget of 65,536/instance. This is the concrete derivation behind ADR-22 (HTTP/2 multiplexing) and ADR-34 (bounded per-shard queue): multiplexed streams over a small pool of TCP connections, not one connection per shard, is load-bearing, not a style preference.
  • CM10 — Metadata-store watch fan-out. max_shards = 10,000 potential watchers; etcd's documented practical ceiling is on the order of 10,000 concurrent watch streams per node (§5) — the §4 shard ceiling sits exactly at this practical limit, flagging the need for a watch-proxy tier at 10× scale (§30, §36).
  • CM11 — Full-cluster rebalance time, doubling shard count 10,000 → 20,000. Moved keys ≈ keys_total × (1 − N/(2N)) = keys_total × 0.5 = 5×10^9 keys ≈ 5×10^9 × 320 B = 1.6×10^12 B = 1.6 TB. At the coordinator's 16-concurrent-job bound (§4) × the 10 MB/s/replica rate limit (ADR-12), effective aggregate rate ≈ 16 × 10 MB/s = 160 MB/s; time ≈ 1.6×10^12 B / (160×10^6 B/s) = 10,000 s ≈ 2.78 hours for a full-cluster doubling.
  • CM12 — Lease-renewal traffic at max scale. max_shards = 10,000 leases, renewal cadence TTL/3 = 10 s (30 s TTL, §4) → 10,000 / 10 = 1,000 lease-renewal RPCs/sec sustained against the metadata store — a direct capacity-planning input for etcd cluster sizing (§17.7).

35. Alternative Architectures (Roads Not Taken)

AA1 — Directory/Lookup-Service Sharding (Slicer-style).

client -> Slicer assignment API -> assignment table -> backend task

Regime: internal datacenter workloads with highly variable, bursty per-key load where assignment must be freely reshuffled rather than algorithmically derived. Real system: Google Slicer (OSDI 2016, §5). Rejected because: Slicer's assignment is itself a live service dependency, adding an RPC hop to every cold lookup; algorithmic partitioning (hash/range/consistent-hash) gives client-side O(1)/O(log N) routing with no live assignment-lookup dependency. Slicer's load-balancing-as-a-service framing is adopted only for the hot-shard detector (§19.2), not as the primary routing mechanism.

AA2 — Client-Side DHT Routing, No Metadata Store (Chord-style).

node A -> finger table -> node B (closer) -> ... -> owner

Regime: peer-to-peer systems with no trusted central coordinator and node churn as the norm. Real system: Chord (SIGCOMM 2001, §5). Rejected because: multi-hop lookup (O(log N) network hops) is unacceptable against the M1–M4 sub-millisecond routing-latency targets; a centralized but replicated metadata store gives O(1) lookups at the cost of requiring a trusted, linearizable control plane — acceptable in a single-operator datacenter deployment, unlike Chord's target environment.

AA3 — Fully Decentralized Gossip-Based Sharding, No Metadata Store (Cassandra-style).

node <-> node <-> node   (gossip mesh; no central store)

Regime: extreme write-availability requirements where any component with a "leader" or "quorum" is unacceptable during a partition (AP over CP). Real system: Cassandra/Dynamo (§5). Rejected because: gossip convergence is eventually consistent, reintroducing exactly the split-brain risk this design forbids (I7, P6); this workload class needs linearizability on the metadata more than it needs gossip's partition tolerance on the data.

AA4 — Proxy-Only Routing, No Smart Client.

client (fully dumb, plain TCP/HTTP) -> proxy (full routing logic) -> shard

Regime: polyglot client fleets where shipping/maintaining an SDK per language is infeasible. Real system: Vitess vtgate in its pure-proxy mode (§5). Rejected as the sole mode (though supported as one of three, ADR-14): proxy-only adds a mandatory network hop — and its own cache-staleness window — to every operation, roughly doubling p50 latency versus an in-process smart client. This design keeps smart-client as the default/recommended path for latency-sensitive same-language callers and supports proxy mode specifically for polyglot fleets.

37. Glossary

  • Bounded loads — the Mirrokni–Thorup–Zadimoghaddam consistent-hash variant capping any bucket's load at (1+ε)×average (§15).
  • BucketAllocator — the logical-bucket-to-physical-shard indirection table giving hash-mod-N partial elasticity (§14).
  • CAS (compare-and-swap) — the atomic conditional write used for every partition-map mutation (I4, §8.2).
  • Composite key — a routing key encoding (tenant_id, row_key) with tenant ID as the high-order prefix (§8.1, §21).
  • Consistent hashing — a hashing scheme where node changes reassign only K/N keys in expectation (Karger et al. 1997, §15).
  • Coordinator (shard-coord) — the leader-elected service driving resharding jobs (§19).
  • Cutover — the atomic CAS step of a split/merge that flips partition-map ownership (§8.3, I4).
  • Double-write — writing to both source and destination during a split's scan phase (I3).
  • Fencing token — a strictly increasing value preventing a stale leaseholder from acting (I8).
  • Fanout — dispatching a batch of per-key operations grouped by owning shard (§18.2, §22.2).
  • Hash-mod-N partitioning — fixed-bucket-count partitioning via hash(key) % N (§14).
  • Hot shard — a shard whose load exceeds the QPS-and-bytes/p99 threshold (P10, §19).
  • HRW (Highest Random Weight) — the rendezvous-hashing selection rule (§16).
  • Jump consistent hash — the Lamping–Veach stateless bucket-assignment algorithm (§16).
  • Lease — a TTL-protected ownership grant for a shard (§17.4, I8).
  • Linearizability — the consistency property required of the metadata store (P6, I7).
  • MetadataStore — the trait abstracting etcd/ZooKeeper/internal-Raft backends (§11.6).
  • Partition map — the versioned assignment of keys to shards, in one of five schemes (§11.2).
  • PartitionKey — an opaque byte-string routing key (§11.1).
  • Pivot — the boundary chosen for a range split (§13.2, §19.2).
  • Proxy mode — routing via the stateless shard-proxy binary rather than an embedded SDK (§18.2).
  • Range partitioning — sorted-boundary partitioning supporting cheap range scans (§13).
  • Rendezvous hashing — the O(N) stateless HRW scheme (§16).
  • Router — the trait exposing route/route_range/refresh (§11.6).
  • shard-coord — the resharding-coordinator crate (§10).
  • shard-core — the no_std crate holding partitioning primitives (§10).
  • shard-metadata — the crate abstracting metadata-store backends (§10).
  • shard-net — the wire-protocol crate (§10, §8.2/§11.7).
  • shard-proxy — the stateless routing-proxy binary (§10).
  • shard-router — the smart-client SDK crate (§10).
  • ShardId — a u32 shard identifier (§11.1).
  • ShardServer — the runtime descriptor for a shard (§11.3).
  • Smart-client mode — routing embedded in the calling process (§18.2).
  • Stale-cache retry — the KeyNotFound-triggered refresh-and-retry-once path (§8.4, I6).
  • Tenant isolation — the property that one tenant's data and load do not spill onto another tenant's shard (P7, §21).
  • Token (ring) — a 64-bit position on the consistent-hash ring (§11.3).
  • TokenBucket — the rate-limiting primitive bounding rebalance throughput (§11.8, P11).
  • Two-phase commit (2PC) — the deferred cross-shard-transaction protocol hook (ADR-17, §36).
  • Two-phase split — the scan-then-cutover online resharding protocol (§19.1).
  • Vindex — a secondary-index sharding abstraction mapping an index value to a primary key (§11.4, §20).
  • Virtual node (vnode) — one of vnode_count ring positions per physical shard (§15, ADR-06).
  • Watch-and-cache — the pattern of invalidating a local cache on a metadata-store watch notification (§17.3).
  • Wire version — the compatibility gate on every shard-net/partition-map message (§26).
