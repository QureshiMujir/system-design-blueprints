In one paragraph

A sharding and partition router answers one question for a storage system that no longer fits on one machine: given a key, which shard owns it? This design is a Rust control plane that maps opaque byte-string keys to shards under five interchangeable schemes, keeps that map in a linearizable metadata store, and splits or merges shards online without client-visible downtime (§1). Callers reach it through an embedded library, a proxy binary, or both (§1, ADR-14). Its defining bet is that a client's cached map may be stale, because the shard server, not the cache, is the authority on ownership (P14, MM2). Infrastructure engineers build on it and on-call engineers debug it (§1).

The problem, concretely

Picture a cluster at the blueprint's design ceiling: 10,000 shards and 10 billion keys, about 10^6 keys per shard (§4, §33 CM1). Each decision made earlier now has a price.

  • Pick the scheme once. The choice of range, hash, consistent hash, jump hash or rendezvous hash is close to irreversible: switching is a full data migration, not a config flag (P1, §2).
  • The obvious scheme cannot grow. With hash(key) % N, the old and new remainders are uncorrelated, so changing N means a full rehash (§1, §14.6, I10). A consistent-hash ring moves only about one shard's worth when you add the 10,001st shard: roughly 10^6 keys, or 320 MB (§33 CM4).
  • Hashing breaks range scans. A range scan over a hash-sharded keyspace touches every shard and needs a client-side merge sort (§1, §14.6). Range partitioning keeps scans cheap but gives up write uniformity (MM5).
  • A cache is needed, and it will be wrong. Without a cache the M1/M2 latency targets are lost (P5, §29). Fixing staleness with a quorum read per route destroys that same target (P14, MM2).
  • Moving data is dangerous. A blocking copy during a split is an outage (P4, ADR-11), and an unthrottled copy tripled write latency for 30 minutes in the WeChat Pay 2019 postmortem the blueprint cites (ADR-12, §19.7).

The blueprint's structure answers these pressures: a map per scheme (P2), a linearizable store that holds the map (P6), a bounded-staleness cache (P5), and a two-phase split (P4) (§6).

  1. Application layer calls Router::route(key) -> ShardId through the public API of the shard-router crate (§3).
  2. Routing tier (shard-router for in-process use, shard-proxy for polyglot clients) holds an arc-swap cache of the versioned partition map. Smart-client, proxy and hybrid modes use one shared cache implementation (§3, §18.1, §18.2, ADR-14, ADR-21). In hybrid mode the proxy checks the SDK's cached map version on every request (ADR-15).
  3. Partitioning algorithms (shard-core, a no_std + alloc crate, ADR-02) pick the shard. One Router is generic over the PartitionMap enum, so the hot loop has no scheme-specific code path (§3, §11).
  4. Shard servers receive the operation over shard-net (protobuf over gRPC via tonic, ADR-22). They are out of scope; only the wire boundary is defined (§1, §3). If the server no longer owns the key it answers KeyNotFound{current_version} and the router refreshes and retries once (§3, I6).
  5. Metadata store (shard-metadata; etcd by default, ADR-04) holds the versioned partition map, leases and watches (§3). The routing tier subscribes, so a new version reaches caches in about 50–100 ms instead of waiting for the 30 s TTL (§4, ADR-09).
  6. Resharding coordinator (shard-coord, a leader-elected singleton) is the only writer of the partition map (§1, §3, I4). Its hot-shard detector, split/merge planner, two-phase executor and rate-limited rebalancer drive a job-state machine (§3, §8.3).

The core ideas

Range versus hash-mod-N: one map, a different shape per scheme (§13, §14, P2, MM5)

Range partitioning stores sorted boundaries in a BTreeMap<PartitionKey, ShardId> (§3, §13.2). Every change must keep the boundaries ordered with no gaps and no overlaps (I11), so each mutation runs a coverage-proof pass before it is accepted (§13.2). The default split point is the median by byte volume, because median-by-key-count is skew-prone (§13.2).

Hash-mod-N is buckets[hash_fn(key) % buckets.len()]: one hash, one modulo, O(1) (§14.2, §14.7). Because changing N rehashes everything, a bucket-count change is rejected outright (I10). The escape hatch is a BucketAllocator, a table from a large fixed number of logical buckets (N=1024+) to physical shards, so capacity changes move only the reassigned buckets (§14.2). The blueprint's fixture reassigns 8 of 1024 logical buckets and expects only their keys to move (§14.5). "Move half the buckets" does not work, because relabelling a bucket does not move keys (§14.6).

The two shapes differ on purpose: forcing one representation on both would make hash-mod-N's O(1) lookup an O(log N) lookup for no reason (P2).

Consistent hashing, jump hash and rendezvous: adding a shard without a rehash (§15, §16, MM3)

A consistent-hash ring with virtual nodes gives each physical shard vnode_count positions (tokens) on a ring. Tokens are xxhash3 over (ShardId, vnode_index), then sorted. A lookup is a binary search for the first token at or above hash(key), wrapping at the end (§15.2). Adding a shard inserts only its tokens, so movement is the K/N bound (§15.1, MM3).

  • Fewer than 100 vnodes per shard is rejected at construction (I9, P3); the default is 256 (ADR-06).
  • Bounded loads caps any bucket at (1 + ε) × average_load with ε = 0.25, spilling overflow to the next token (§15.2, §33 CM8, ADR-23).
  • Ring memory is 10,000 shards × 256 vnodes = 2,560,000 tokens at 16 bytes each, about 41 MB per cache instance (§33 CM5).

Jump hash is stateless and O(log N) but assumes contiguous bucket IDs 0..N; it supports only "add bucket N" and "remove the highest bucket" (§16.2, §16.6). Rendezvous (HRW) hashing computes hash(key || shard_id) for every candidate and takes the maximum, which is O(N), so the blueprint limits it to small clusters and replica selection (§16.2, §16.6).

A stale cache is safe because the shard server decides (§8.4, I6, P14, MM2)

Every cache entry carries the partition-map version it was built from (I6). The blueprint's trace of a key that just moved in a split (§8.4):

  1. The client calls Router::route(key=K); the cache is at version 41 and K just moved in a split.
  2. The router forwards the operation to the shard server per the stale cache: Shard_7.
  3. Shard_7 no longer owns K (cutover happened at version 42) and returns KeyNotFound{current_version: 42}.
  4. Router::refresh() re-fetches map version 42, routes K to Shard_12, and retries the operation once, which succeeds.

The added latency is one refresh round trip (≤ 5 ms, M3 in §29) plus one retry round trip; the cache-hit path never executes the forward, reject and refresh steps (§8.4 steps 3–7). Staleness is a performance defect, never a correctness defect (P14). Refreshing on every request would remove the misroutes and also remove the cache (§18.6, §34 item 8). If a KeyNotFound carries an older version than the client already holds, the router raises RoutingError::VersionRegression and logs it (§18.8, I5). §8.4 step 2 says the cache has "no entry covering K", yet step 3 still routes by that cache; the blueprint does not reconcile the two phrasings.

A live split: scan, double-write, one CAS (§8.3, §8.6, §19.2, I3, I4, I12, MM4)

The job moves through Pending, Scanning, Validating, Cutover, Completed, and may go to Aborted; every state is persisted before the next step begins (§8.3, I12). During Scanning the destination back-fills the source's lower half through a rate-limited iterator, and writes to that half go to both source and destination (§19.2, I3). Cutover is a single compare-and-swap (CAS) on one versioned map document, never two writes (I4). Aborted is described two ways: I12 and the §8.3 Aborted row say it is reachable from any state, while the same table gives Pending only the exit Scanning and marks Completed terminal.

The crash trace (§8.6) shows why persisting first pays off:

  1. The coordinator issues CAS(map_v41 -> map_v42); it succeeds, then the coordinator crashes before recording Completed.
  2. On restart it reads the pending jobs and finds the job in Cutover.
  3. It re-reads the map: v42 means the CAS already landed, so it moves the job to Completed. Had the map still been v41, it would retry the CAS.

The pair (JobState, current_map_version) tells the coordinator which side of the CAS it crashed on (§8.6). What triggers a split? The detector flags a shard when QPS and bytes/sec both exceed their thresholds for 60 s, or when p99 latency exceeds 2× the cluster median (§19.2, ADR-10). P10 instead states "QPS-and-bytes-per-second AND p99-latency thresholds, sustained 60 s" (§6).

Composite keys and vindexes: isolation and secondary lookups as encoding problems (§8.1, §20, §21, MM6, MM7)

A composite key is tenant-len , tenant-id , row-key, with the length as a LEB128 varint (§8.1, ADR-13). With the tenant first (I14, P7), a split can prefer a (tenant_id, "") pivot that separates whole tenants rather than cutting through one tenant's rows. If one tenant outgrows a shard, the planner falls back to a (hot_tenant_id, row_key) pivot. A tenant using more than 80% of its shard's capacity is flagged hot; one over quota gets Error::TenantRateLimited (§21.2).

A vindex (secondary-index sharding) is a separate keyspace sharded by the index column, never by the primary key (§20.2, P8, MM6). Uncached, an email lookup costs four hops: route_index, the vindex shard's lookup, route_primary, then get. Caching the first two steps brings repeats to about two (§20.2). The default write order is index-first with a tombstone on failure (§20.2, §20.3).

The trade-offs — where engineers disagree

Metadata store: etcd behind a pluggable trait (ADR-04, ADR-05)

Chosen: etcd as the default, behind a MetadataStore trait, for strong consistency, watch and lease primitives and operational maturity (ADR-04, ADR-05). Rejected: ZooKeeper, Consul or an internal Raft group as the default; a hard-coded etcd client. When the rejected choice is right: ZooKeeper, in shops with existing ZooKeeper expertise and no etcd investment (ADR-04); a hard-coded client, for a single-backend deployment that never swaps stores (ADR-05). Linearizability itself is not up for debate (P6, MM8).

Virtual nodes: 256 per shard (ADR-06)

Chosen: 256 per physical shard, never below the floor of 100 (ADR-06, I9). Rejected: 32 and 1024. Below 100 the imbalance is ≥ 2×; above 1024, lookup cost and memory dominate with no imbalance gain (ADR-06). §1 words the first figure as "up to 2×", and §15.6 gives 2× for vnode_count = 1 on a 10-shard ring. When the rejected choice is right: 32, on memory-constrained edge deployments with fewer than 10 physical shards, where imbalance risk is already low (ADR-06).

Hash function: fast for server keys, keyed for tenant keys (ADR-07, ADR-08)

Chosen: xxhash3 for ring and jump hashing (about 10 ns per call, uniform, non-adversarial inputs), and SipHash-2-4 for tenant-prefixed composite keys, because a tenant can craft colliding keys (ADR-07, ADR-08, T1). Rejected: SipHash, MurmurHash3 and CRC32 for the ring; xxhash3 for tenant keys (ADR-07, ADR-08). When the rejected choice is right: SipHash, when the hashed input is attacker-influenced (ADR-07); xxhash3 for composite keys, when all keys are server-generated (ADR-08).

Cache lifetime: 30 s TTL plus watch invalidation (ADR-09)

Chosen: a 30 s TTL plus watch-driven invalidation, which cuts effective refresh to about 50–100 ms (ADR-09). Rejected: a 5 s TTL, or an unbounded cache (ADR-09; unbounded caching makes stale windows unrecoverable without a restart, P5). When the rejected choice is right: a 5 s TTL, for clusters resharding many times per minute, at the cost of more refresh RPCs (ADR-09).

Split algorithm: two-phase scan and cutover (ADR-11)

Chosen: scan with double-writes, then one atomic cutover (ADR-11, P4). Rejected: a single-phase blocking copy, which stalls writes for the whole copy (ADR-11). When the rejected choice is right: offline or maintenance-window migrations where downtime is scheduled and acceptable (ADR-11).

Cache primitive: arc-swap (ADR-21)

Chosen: arc-swap, a lock-free pointer swap, because the hot path is read-dominated (ADR-21). Rejected: RwLock<Arc<...>>, whose reader contention hurts M1 and M2 (ADR-21). When the rejected choice is right: when writes are frequent enough (sub-second) that reclaiming the old Arc becomes the bottleneck (ADR-21).

Roads not taken

Directory service, Slicer-style (§35 AA1): a lookup service assigns keys freely. It wins in datacenter workloads with bursty per-key load where assignment must be reshuffled rather than derived. It is rejected because the service adds an RPC hop to every cold lookup; only its load-balancing idea is reused in the hot-shard detector.

Peer-to-peer routing, Chord-style (§35 AA2): no central store, multi-hop lookups. It wins where there is no trusted coordinator and churn is normal. The blueprint rejects its multi-hop lookups against "the M1–M4 sub-millisecond routing-latency targets" (§35 AA2); §29 sets M3 at ≤ 5 ms and M4 at ≤ 100 ms.

Gossip with no metadata store, Cassandra-style (§35 AA3): it wins when any leader or quorum is unacceptable during a partition. It is rejected because eventual consistency brings back the split-brain risk that P6 and I7 forbid.

Proxy-only routing (§35 AA4): it wins for polyglot fleets that cannot maintain an SDK per language. As the sole mode it adds a hop and its own staleness window to every call, so it is one of three modes (§35, ADR-14).

The deferred register (§36) lists what is intentionally absent, such as cross-shard 2PC and sagas (Blueprints #73 and #91), replicated storage (#21), SQL routing and geo-aware placement. Each has an un-defer trigger, for example a confirmed multi-region requirement for geo-aware placement (§36).

What must never be false

  • I1: same key and map version, same shard. Property test; routing_determinism_check_fail_total (§7).
  • I2: no key has two owners outside a split's double-write window. Row-count diff; partition_map_overlap_total (§7).
  • I3: scan-phase lower-half writes hit source and destination. Row-count mismatch; split_double_write_miss_total (§7).
  • I4: cutover is one atomic CAS. Dual-ownership detector; cutover_non_atomic_total, always 0 (§7).
  • I5: the map version only increases. Regression check on read; partition_map_version_regression_total (§7).
  • I6: each cache entry carries its map version. KeyNotFound rate; routing_stale_reject_total (§7).
  • I7: the metadata store is linearizable. CAS-conflict anomalies; metadata_cas_conflict_total (§7).
  • I8: one lease holder; fencing tokens only rise. Rejections; lease_fencing_reject_total (§7).
  • I9: ring sorted, at least 100 vnodes per shard. Construction assertion; ring_vnode_count_violation_total (§7).
  • I10: hash-mod-N bucket count never changes. Mismatch check; hash_resize_forbidden_total (§7).
  • I11: range boundaries ordered, no gaps or overlaps. Coverage proof; range_map_invalid_total (§7).
  • I12: jobs advance only along the §8.3 states. Heartbeat check; job_state_stuck_total (§7).
  • I13: reverse(lookup(x)) == x for unique vindexes. Property test; vindex_asymmetry_total (§7).
  • I14: tenant ID is the high-order key prefix. Encode-time assertion; composite_key_order_violation_total (§7).

A deterministic simulator asserts all fourteen on every tick and aborts with the event trace on the first violation, so it replays from one seed (§7).

What breaks in production

The blueprint numbers its failure classes FM1 to FM12 (§24).

  • FM2: KeyNotFound spike. Clients hit an ex-owner after a split because the TTL has not expired. Detected by the KeyNotFound rate; refresh-and-retry recovers automatically, and shardctl can flush a cache by hand (§24, I6).
  • FM3: a job is stuck in Scanning or Validating. The coordinator crashed, ran out of memory or was redeployed. Seen as a missing job-state heartbeat; the job resumes from its last persisted state, and an operator can abort and restart it with shardctl (§24, I12).
  • FM4: data loss on cutover. The double-write was skipped during the scan, violating I3. Detected by a post-cutover row-count alert. There is no auto-fix: abort and re-scan the destination (§24).
  • FM5: split-brain on cutover. The cutover used two writes instead of one CAS, violating I4. Detected by the dual-ownership detector; the shard server rejects conflicting writes, and an operator repairs the CAS by hand (§24).
  • FM10: keys silently misrouted after a jump-hash removal. Someone removed a bucket other than the highest. §24 lists detection as a routing-checksum mismatch on canary keys and recovery as migrating to consistent hashing. §16.9 instead calls it a design-contract violation that is not runtime-detectable, and makes the path uncompilable.
  • FM12: 2× imbalance on a ring. vnode_count was configured below 100. Seen as a load-imbalance ratio above 1.5; recovery is rebuilding the ring with 256 vnodes, which is a full rehash (§24). §15.9 says a ring below the I9 floor never reaches production because construction fails, so FM12 and §15.9 disagree.

Threats a reader should know (§23):

  • T1: a tenant crafts colliding keys to force a hotspot. Mitigated by keyed SipHash-2-4 (ADR-08) and key rotation, detected by a chi-squared skew alert, recovered by an automatic split (P10).
  • T2: split-brain on the partition map during a network partition. Mitigated by the linearizable store and CAS (P6, I4).
  • T8: a corrupted map record. A CRC32 over the payload is checked on raw bytes before the oneof is decoded; the router then keeps serving its last-known-good cache and alerts (§8.2, §8.5).
  • T12: an attacker spikes load just over the hot-shard threshold to trigger repeated splits. Mitigated by a 60 s sustained-load rule and the rebalance rate limit (ADR-10, P11).

How it compares

  • Vitess sends clients through a vtgate proxy so they need zero sharding awareness, which suits fleets with many client languages (YouTube, Slack and Square are the blueprint's examples). This design keeps a smart client as the default and offers the proxy as one of three modes (§32, §35, ADR-14).
  • Citus keeps co-located distributed tables inside real Postgres, which fits teams that need full SQL and Postgres feature parity more than write scale beyond one coordinator (§32).
  • MongoDB runs an automatic balancer by default, which suits rapid, schema-flexible development where operators accept background chunk migration without tuning rate limits. This design rejects an unthrottled default (§32, ADR-12).
  • Cassandra uses gossip and no central metadata, which fits extreme write scale and multi-datacenter deployments where a metadata service would itself be the bottleneck. It gives up the linearizability that this design requires (§32, P6, I7).

Questions to test yourself

  1. Why does hash-mod-N sharding forbid live resize while consistent hashing supports it, and what specifically breaks if you try to resize a hash-mod-N map online? — Hint: §14.6 and §15.1, with I10.
  2. Trace exactly what happens to an in-flight write when a split's cutover CAS fires between the write's route() call and its arrival at the shard server. — Hint: §8.4 and §19.2, with I3, I4 and I6.
  3. Why is "refresh the routing cache on every request" categorically wrong even though it would eliminate stale-cache misrouting entirely? — Hint: §18.6 and MM2, with P5 and P14.
  4. Why must the double-write during a split's scan phase target both shards rather than just queuing writes for later replay on the destination? — Hint: §19.6, with I3 and FM4.

If you only remember three things

The shard server, not the client cache, owns the truth about who holds a key, so a stale cache costs latency and never correctness (P14, MM2). Choose the partition scheme carefully at the start, because switching later is a re-platform (P1) and resizing hash-mod-N rehashes everything (I10). Splits stay safe because the scan double-writes and the cutover is a single atomic CAS on a versioned map, from which a crashed coordinator can always tell where it stopped (I3, I4, I12, §8.6).

Words used here

  • Partition map: the versioned assignment of keys to shards, in one of five schemes (§37).
  • Range partitioning: sorted boundaries; cheap range scans, uneven writes (§37, MM5).
  • Hash-mod-N: hash(key) % N with N fixed forever (§37, I10).
  • Consistent hashing: a ring where a membership change moves only about K/N keys (§37).
  • Virtual node (vnode): one of many ring positions given to a physical shard to even out load (§37, P3).
  • Bounded loads: a consistent-hash variant that caps any bucket at (1 + ε) × average (§37).
  • Jump hash / rendezvous (HRW): two stateless schemes, O(log N) and O(N) respectively (§37, §16.2).
  • CAS (compare-and-swap): an atomic conditional write, used for every map change (§37).
  • Cutover: the single CAS that flips ownership at the end of a split or merge (§37).
  • Double-write: writing to both source and destination during a split's scan (§37, I3).
  • Fencing token: a strictly increasing number that stops a stale lease holder acting (§37, I8).
  • Vindex: a secondary index stored as its own sharded keyspace (§37, P8).
  • Composite key: a routing key with the tenant ID as its high-order prefix (§37, I14).
