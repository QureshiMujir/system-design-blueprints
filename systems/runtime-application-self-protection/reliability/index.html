7. System Invariants

7.1 Host-Safety Invariant

  • Statement: a RASP fault (panic, OOM, timeout, logic error) NEVER propagates into the host application as a crash, hang, or visible exception.
  • Why: RASP is an optional protection layer; it must not become the source of outages — this is the primary adoption blocker for inline agents.
  • Enforced in: rasp-protect::run_hook wraps all calls in catch_unwind; rasp-hook trampoline catches all Err returns; per-analyzer timeout guard (iteration cap).
  • Violation detection: absence of HookReturned telemetry event after HookEntered within threshold; host application crash rate correlated with RASP deploy.
  • Telemetry emitted: rasp.internal_fault{sink, error_kind} counter; rasp.hook_panic counter; rasp.timeout_exceeded{sink} counter.
  • Recovery: on fault, fall back to policy.fail_mode; emit fault event; increment counter; return control to host normally.
  • Debugging: enable RASP_FAULT_TRACE=1 to capture panic backtraces to a separate log file without crashing the host; correlate context_id to request log.

7.2 Monitor Purity Invariant

  • Statement: when Policy.mode == Monitor, Action::Block is never returned to the host; app behavior is identical to running without RASP.
  • Why: Monitor mode is the contract for safe production rollout; violating it causes unexplained outages and destroys deployment trust.
  • Enforced in: rasp-protect::enforce — static match mode { Monitor => Action::Allow, Block => … }; no flag or runtime condition bypasses this branch.
  • Violation detection: rasp.action{action=Block, mode=Monitor} counter must be permanently zero; alerting on any non-zero value.
  • Telemetry emitted: rasp.monitor_would_block counter (for attacks that would be blocked in Block mode); never rasp.action=Block in Monitor.
  • Recovery: no recovery needed if invariant holds; if counter non-zero, roll back RASP build immediately.
  • Debugging: unit test monitor_never_blocks in rasp-protect asserts Action::Allow for all known attack payloads when mode=Monitor; run in CI on every commit.

7.3 Block Determinism Invariant

  • Statement: decide(hook_event, context, policy) → Action is a pure function; same inputs always produce same output and same Detection.evidence.
  • Why: incident forensics requires exact replay; inconsistency breaks postmortem analysis and FP investigation.
  • Enforced in: rasp-protect::decide has no global mutable state reads; no rand, no timestamps, no external I/O in decision path; policy is immutable Arc.
  • Violation detection: determinism fuzz test: run same HookEvent through decide 1000× with same policy snapshot, assert identical Action and evidence.
  • Telemetry emitted: policy snapshot version attached to every Detection event; enables replay with versioned policy.
  • Recovery: if non-determinism detected in test, bisect to the offending non-pure read and eliminate.
  • Debugging: rasp-bench replay harness: feed logged HookEvent + policy version → assert deterministic output.

7.4 Context Isolation Invariant

  • Statement: TaintMap and RequestContext of request A are never readable or writable by request B, regardless of concurrency model (thread pool, async executor, connection reuse).
  • Why: taint leakage across requests produces both false positives (legitimate B incorrectly blocked using A's taint) and false negatives (attack in A cleared by B's context).
  • Enforced in: rasp-context uses thread_local! for sync; tokio::task_local! for async; context initialized on request start, dropped on request end (RAII guard).
  • Violation detection: concurrent request load test with distinct taint patterns per request; assert no cross-contamination after 10k request pairs.
  • Telemetry emitted: rasp.context_leak counter (incremented if context still active after request end deadline); context lifetime histogram.
  • Recovery: context RAII drop triggered at request end; panic-safety: Drop impl on RequestContextGuard always clears TLS slot.
  • Debugging: context_id logged on every event; cross-request context_id reuse is a bug signal; grep logs for duplicate context_id on non-overlapping request windows.

7.5 Taint Soundness (Bounded) Invariant

  • Statement: within max_taint_ops budget, a taint tag on byte range [s, e] of a TaintedValue is never lost through any tracked propagation operation; ops exceeding budget mark value conservatively tainted.
  • Why: silent taint loss is a false-negative source; attacker can craft chains of innocuous-looking string ops to escape tracking.
  • Enforced in: rasp-taint::propagate decrements per-value op counter; zero budget → TaintStatus::BudgetExceeded; all tracked ops enumerated in PropagationOp enum.
  • Violation detection: taint soundness property test: apply all tracked ops to a tainted value, verify tags present at sink; fuzz with random op chains.
  • Telemetry emitted: rasp.taint.budget_exceeded counter; rasp.taint.ops_per_request histogram.
  • Recovery: BudgetExceeded → taint retained (conservative); analyze ops histogram to tune max_taint_ops per deployment.
  • Debugging: enable RASP_TAINT_TRACE=1 to log per-op tag state for a sampled request; compare pre/post op tag set.

7.6 Overhead Budget Invariant

  • Statement: inline guard adds ≤1 ms p99, ≤0.3 ms p95 per sink call; untainted path ≤20 µs; never blocks request thread on I/O.
  • Why: inline RASP rejected in production if it causes measurable application latency; 5% added latency SLA at system level.
  • Enforced in: rasp-bench overhead harness runs benign corpus at target QPS; CI gate fails if budget breached; analyzers have explicit iteration caps.
  • Violation detection: p99 overhead metric rasp.hook_latency_ns{sink, taint_hit} emitted per call; breach triggers alert.
  • Telemetry emitted: rasp.hook_latency_ns histogram per (sink_type, taint_hit: bool, action); rasp.analyzer_iters{sink} histogram.
  • Recovery: if budget breached, disable expensive analyzer for that sink type via policy flag; emit rasp.analyzer_disabled event; alert ops.
  • Debugging: rasp-bench overhead --sink SqlQuery --qps 5000 reports p50/p95/p99 latency breakdown by phase (taint check, detection, policy eval, telemetry).

7.7 No Blocking I/O on Hook Path Invariant

  • Statement: the code path from HookEvent receipt to Action return contains zero blocking I/O, zero synchronous network calls, zero file reads.
  • Why: any blocking call on the hot path propagates its latency to every instrumented request; a 5 ms SIEM write adds 5 ms to every SQL query.
  • Enforced in: rasp-telemetry write is async try_send to bounded channel; policy loaded into memory at startup; taint + detection operate on in-memory structures only.
  • Violation detection: strace / dtrace on RASP-enabled process under load; assert no blocking syscalls (read, write, connect) from hook call stack; latency anomaly detection.
  • Telemetry emitted: rasp.io_on_hotpath_violation counter (should be permanently zero; instrumented via #[cfg(debug_assertions)] checks).
  • Recovery: if async channel full, try_send failure path drops event and increments telemetry.dropped_events — never blocks.
  • Debugging: flamegraph of hook call path; any I/O system call appearing in hot path is an immediate bug.

7.8 Policy Completeness Invariant

  • Statement: every SinkType has at least one Rule in the loaded Policy; a sink with no matching rule defaults to fail_mode action (never silently to Allow).
  • Why: unconfigured sink falls through to implicit allow → unprotected attack surface; operator assumes protection that does not exist.
  • Enforced in: rasp-policy::validate checks rule coverage for all SinkType variants at policy load; missing coverage → RaspError::PolicyIncomplete.
  • Violation detection: policy validation test in CI; rasp-cli validate <policy.toml> must pass in deployment pipeline.
  • Telemetry emitted: rasp.policy.uncovered_sink{sink} counter; rasp.policy.fallthrough_action{sink, action} for transparency.
  • Recovery: add a catch-all Monitor rule for each sink type as default; fail-closed only when explicitly configured.
  • Debugging: rasp-cli inspect policy.toml --coverage lists each SinkType and its matched rules; gaps are clear.

7.9 Evidence Integrity Invariant

  • Statement: Detection.evidence contains the verbatim tainted substring that triggered the rule, byte-exact from the original TaintedValue.value, with correct byte_range.
  • Why: forensic use of evidence requires it to be the actual attack payload, not a reconstructed or summarized version; incorrect evidence invalidates incident report.
  • Enforced in: rasp-detect analyzers extract evidence slice from original TaintedValue.value[tag.byte_range]; no transformation allowed on evidence string before attaching to Detection.
  • Violation detection: property test: run known attack payloads through detector; verify evidence is a substring of input value at stated byte_range.
  • Telemetry emitted: rasp.evidence_integrity_fail counter (debug builds only; production assumes enforced); logged with full context on failure.
  • Recovery: if evidence extraction fails (range out of bounds), mark Detection.confidence = Low, emit rasp.evidence_extraction_fail, continue with block/monitor per policy.
  • Debugging: rasp-bench replay --event <event.json> re-runs detection and dumps evidence alongside original value for visual diff.

7.10 Waiver Non-Bypass Invariant

  • Statement: a Waiver only suppresses a specific (rule_id, request_path, method) combination; it cannot suppress all rules or all sinks globally.
  • Why: blanket waivers defeat the entire protection model; scoped waivers are auditable and reviewable.
  • Enforced in: rasp-policy::Waiver type has no wildcard variants for rule_id; * as rule_id is rejected at policy load validation.
  • Violation detection: rasp-cli validate rejects wildcard rule_id; unit test asserts type rejects wildcard construction.
  • Telemetry emitted: rasp.waiver_applied{rule_id, path, method} on each waiver match; rasp.waiver_expired{rule_id} on expiry.
  • Recovery: expired waiver reverts to rule's configured action; no manual intervention required.
  • Debugging: rasp-cli waivers list --active shows all current waivers with expiry; --expired shows recently expired ones.

7.11 Taint Source Completeness Invariant

  • Statement: all externally-controlled HTTP inputs (params, headers, body, path segments, cookies) are registered as TaintSource before any sink can be reached in a request.
  • Why: untapered source → taint tracking has no starting point → all sink checks are taint-miss → attacker data flows uninspected.
  • Enforced in: rasp-context::capture_http marks all HttpInfo fields as taint sources at request start; rasp-taint::register_sources called before any HookEvent dispatch.
  • Violation detection: integration test: send attack payload in each HTTP input location; verify taint presence at sink.
  • Telemetry emitted: rasp.source.registered{source_type} counter per request start; rasp.source.missing{source_type} if capture fails.
  • Recovery: if HTTP capture fails (e.g., body parse error), mark all body-derived values as conservatively tainted (TaintStatus::CaptureFailed).
  • Debugging: RASP_SOURCE_TRACE=1 logs each registered source and its byte range at request start; compare against expected source list for the adapter.

7.12 Concurrency Safety Invariant

  • Statement: rasp-core types shared across threads (Policy, Rule, RuleSet) are Send + Sync and immutable after construction; mutable per-request state is never shared.
  • Why: data races on policy or taint map produce non-deterministic behavior, security holes, and UB in unsafe sections.
  • Enforced in: Policy is Arc<Policy> (read-only ref); RequestContext is !Send (cannot be moved across task boundaries accidentally); TaintMap is !Sync.
  • Violation detection: cargo test with --cfg loom for concurrent model checking of shared state; ThreadSanitizer in CI on integration tests.
  • Telemetry emitted: N/A (compile-time enforcement preferred); runtime: rasp.race_condition_detected counter in debug builds only.
  • Recovery: type system prevents most races; loom tests catch ordering issues; TSan findings require immediate fix before merge.
  • Debugging: RUSTFLAGS="-Z sanitizer=thread" integration test run; cargo test --cfg loom concurrent model check.
