In one paragraph

A runtime application self-protection engine (RASP) runs inside the protected application and checks each dangerous operation, such as a database query, shell command, file open or outbound web request, at the moment it executes (§1.1). It marks the bytes that came from HTTP input, follows them through string operations, and inspects an operation only when its arguments carry such marks (§3.2). It then allows, reports or blocks the call, and a fault in the engine itself must never crash the host (§3.2, §7.1). It ships as a Rust library plus per-runtime adapters, run by application-security and platform teams (§1.4, §1.5).

The problem, concretely

Picture a web app that builds a database query by joining a fixed string with a request parameter. The blueprint's first worked example is exactly this: a request to /items whose id parameter carries extra SQL syntax that gets spliced into SELECT * FROM items WHERE id = ... (§8.12 Example A). Each obvious defence fails for a reason the blueprint names:

  • Filter at the network edge (a WAF, web application firewall). It sees HTTP bytes only, so it cannot see the assembled query, deserialized objects or ORM-built SQL (Alt-A, MM1, Glossary).
  • Re-scan the whole query for bad patterns. That costs O(n) per call and ignores where the bytes came from (MM2). A raw pattern such as SELECT.*FROM is bypassed by case changes, comments and encodings (§6.10).
  • Alert whenever a quote appears. That flags legitimate quoted data, because injection means attacker bytes changed the query's structure, not that a quote was present (MM4).
  • Static analysis at build time. It has no runtime values, so it cannot tell whether this request's input is attacker-controlled (Alt-B).

A guard inside every request adds two new problems. Cost: a blocking SIEM (security event monitoring system) write of 5 ms would add 5 ms to every SQL query (§7.7). Trust: a security tool that crashes the app is worse than the attack it stops (MM3). There is also a rollout problem: a new environment must start in a mode that observes and never blocks, so operators can tune before enforcing (§2.4, §6.5).

The blueprint's answer to Example A: the tainted slice of the query contains a SQL keyword and a quote break, so the engine raises a detection at confidence 0.97, the policy says Block, and the database call is aborted with an error returned to the app (§8.12 Example A). In Monitor mode, a path-traversal case lets the file read through and only logs it (§8.12 Example B). RASP does not replace parameterized queries, input validation or a WAF (§6.13).

How it works, end to end

Follow one request through the canonical pipeline (copied from §3.1):

protected application (instrumented runtime)  --hook ABI call at each dangerous sink-->
        |
  [rasp-hook] sink entry/exit interception (SQL exec, command exec, file open, outbound HTTP, deserialize)
        |  HookEvent (sink_type, args, context_id)
  [rasp-context] resolve per-request context (thread/async-local), HTTP request, call stack, correlation id
        |
  [rasp-taint] are sink args tainted? source (HTTP input) -> propagation -> sink reached?
        |  TaintedValue + taint path
  [rasp-detect] per-sink analyzer: SQLi (query tokenize + injected-syntax), cmd-injection, path-traversal,
        |        SSRF (URL allowlist), deserialization (gadget), XXE, LDAP/NoSQL -> Detection?
  [rasp-policy] Detection -> Action (Block / Monitor) by mode + rule + waiver (fail-open / fail-closed)
        |
  [rasp-protect] enforce: Block => abort the sink op + safe error to app; Allow => proceed
        |
  [rasp-telemetry] emit attack event (SIEM/CEF), metrics (overhead, blocks), audit log
  1. Adapter. A per-runtime shim outside the core calls the hook ABI at each sink, for example the SQL driver's execute(). Adapter code is trusted; the arguments it passes are not (§3.2).
  2. Request start. The adapter calls rasp_context_begin(HttpInfo). rasp-context allocates a fresh RequestContext, and rasp-taint tags every HTTP field (params, headers, body, path, cookies) as a taint source before any sink can be reached (§3.3, §7.11).
  3. rasp-hook and rasp-context. The hook receives a HookEvent, finds the interceptors in its SinkRegistry, and lets through any sink call RASP itself makes via a re-entrancy guard. The context is resolved from context_id (§3.2, §3.3).
  4. rasp-taint. Looks up each sink argument in the request's TaintMap. An untainted argument takes an O(1) fast exit that skips every analyzer, the main overhead mechanism (§3.2).
  5. rasp-detect. Runs the analyzer for that sink type. Several may fire; the highest severity drives the policy decision and all are logged (§3.2).
  6. rasp-policy. Maps the detection to Allow, Block or Monitor using mode, rules, waivers and the fail mode (§3.2).
  7. rasp-protect. The inline guard that runs steps 3 to 6 synchronously. On Block it returns Err(RaspError::Blocked { detection }) and the adapter raises a safe application error, so the dangerous call never runs (§3.2, §3.3).
  8. rasp-telemetry. Pushes an event into a bounded queue and returns; a separate consumer writes CEF/JSON, metrics and the audit log (§3.2). At request end rasp_context_end() drops the context (§3.3).

rasp-cli and rasp-bench complete the ten crates (§1.6, §12). Everything runs in-process, with no RASP server and no database (§1.4, §4.4).

The core ideas

1. A hook at every dangerous call, wrapped so it cannot hurt the host (§3.2, §8.9, §7.1)

A sink is a call where untrusted data does harm if injected. The design names eight kinds: SQL query, command exec, file open, outbound HTTP, deserialize, LDAP query, XML parse and NoSQL query (§8.2). The hook ABI is a C-stable function boundary, so any runtime's adapter can call the Rust engine (ADR-020). It is versioned: rasp_init checks a u32 abi_version and refuses a mismatch (§3.2, MM10). A hook event carries the sink type, a context id, entry or exit, a timestamp and a pointer plus length to MessagePack arguments in a buffer the adapter owns, which RASP only reads (§8.9, ADR-007).

Every hook entry is wrapped in catch_unwind, so a panic falls back to the configured fail mode and never reaches the host. The price is a small constant per call (§6.1). max_hook_duration_us defaults to 500 µs, and an overrun also falls back to the fail mode (§3.2). A three-step trace of the internal-error case (§8.12 Example E):

  1. The SQL tokenizer panics on malformed UTF-8 and catch_unwind in rasp-hook catches it.
  2. The engine counts the error and the fail mode decides: Open allows, Closed blocks.
  3. An info-severity event is emitted and the app never sees the panic.

The default fail mode is described two ways. §1.4 says fail-open for brownfield and fail-closed for greenfield. §6.8 says every Policy must state it explicitly with no implicit default, yet also says "FailClosed blocks by default". Phase 0's acceptance test calls fail-open the default (§12).

2. Taint: a label that travels with the data (§8.4, §8.7, MM2)

Taint is a provenance label that flows with data, not a scan run at the end (MM2). An HTTP field becomes a TaintedValue carrying tags { source, byte_range, generation }; the generation counter ticks per step and helps rebuild the taint path for forensics (§8.2, §8.7). A per-request TaintMap keyed by ValueId holds them (§8.2, ADR-012). Concatenation merges tags, slicing adjusts the range, and formatting with a tainted argument gives a tainted result (§3.2). Each value moves through these states (copied from §8.4):

  Clean ──── source-tagged at HTTP ingress ────────────► Tainted(tags)
  Tainted ── string-concat / format / slice ───────────► Tainted(merged_tags)
  Tainted ── untracked op (regex-replace, etc.) ────────► Dropped (documented gap)
  Tainted ── tag-set exceeds TAINT_TAG_LIMIT ───────────► Overflowed
  Overflowed ─────────────────────────────────────────────► treat as fully-tainted (sound)
  Dropped ────────────────────────────────────────────────► treat as clean (FN risk; documented)

When the work exceeds its budget the value is marked conservatively tainted rather than clean, accepting false positives in exchange for bounded cost (§6.6). Byte ranges, not per-character shadow memory, keep that cost down (ADR-011). The blueprint is inconsistent about the limits:

  • Tags per value: at most 16 (§3.2, §4.1) versus a TAINT_TAG_LIMIT default of 64 (§8.4).
  • Per-request memory: at most 512 KB (§4.1) versus a TAINT_MAP_MAX_BYTES default of 4 MiB (§8.7).
  • Over the limit: treat the value as tainted (§3.2, §8.13) versus evict the oldest entries (§8.7, §11.7, Threat Model), which would lose taint, against "never silently drops" (§3.2). The over-budget state is OverBudget (§3.2), BudgetExceeded (§6.6), Overflowed (§8.4) or a Saturated tag (§18).
  • Untracked operations such as regex replace clear taint (§3.2, §8.4) versus keep all ancestor tags (§11.6).

3. Detection by structure, at the moment of danger (§8.6, §6.10, MM4)

Analyzers read parsed structure (tokens, URL parts, normalized paths), not raw regex over strings (§6.10). The SQL injection analyzer is a small state machine: tokenize the query, map the tainted byte ranges onto token boundaries, and flag the query if a tainted region contains a SQL keyword or structural token. No injection syntax means Allow, and a tokenizer failure is itself reported as a medium-severity "suspicious" detection (§8.6.1). A parameterized query puts no tainted bytes in the query string, so it is allowed at once (§8.6.1, §8.13). The tokenizer is libinjection-inspired and pure Rust (ADR-009).

Sink What the analyzer looks at
Command exec shell metacharacters in tainted text; a tainted program name, or a tainted argument with a path separator (§8.6.2)
File open the path after normalization, checked against an allowed-root set; symlink targets (§8.6.3)
Outbound HTTP URL parts against an allow-list and a deny-list of internal ranges, no DNS lookup inline (§8.6.4, ADR-010)
Deserialize tainted data in dangerous formats; class names against a gadget list (§8.6.5)
XML parse DOCTYPE, external and parameter entity declarations (§8.6.6)
LDAP / NoSQL unescaped filter metacharacters; operator keys or objects where a scalar belongs (§8.6.7)

A detection below an analyzer's confidence_threshold is downgraded to Monitor whatever the policy says (§3.2). One inconsistency: untainted arguments skip all analyzers (§3.2), yet §8.6.6 describes a quick DOCTYPE scan when tainted=false.

4. Policy: a fixed order of questions (§8.8, §6.3, §6.5)

Evaluation asks four things in order (§8.8): (1) is there a matching waiver? Then Allow. (2) Is the mode Monitor? Then Monitor, whatever the rule says. (3) Does a rule match, by sink, rule id and priority? Then that rule's action. (4) Otherwise the fail mode: Closed gives Block, Open gives Allow.

Situation Outcome
Block mode, SQL injection rule matches (§8.12 Example A) Block, call aborted
Monitor mode, path traversal detected (§8.12 Example B) Monitor: event logged, operation proceeds
Waiver with expires_at in the past (§8.13) treated as no waiver; the rule is re-evaluated
No rule matches (§8.8) the fail mode decides; Phase 9 uses the policy mode instead (§21)

The decision is a pure function with no randomness, clock or I/O, so a logged event plus a policy snapshot replays exactly (§6.3, §7.3), though waiver expiry is checked against the wall clock (§6.12). Monitor purity is enforced by a static match on the mode (§7.2). Policy lives in an Arc<Policy> swapped atomically on reload, so the hot path takes no lock (§3.2, ADR-006); ADR-005 instead names a parking_lot::RwLock for Policy. Contradictions: rule order is ascending rule_id (§6.3), priority descending (§8.8), list order with first match winning (§11.10) or lowest priority number first (§21); a waiver is keyed by (source_ip, rule_id, path) (§3.2), (rule_id, request_path, method) (§7.10) or { route_pattern, rule_id, expires_at, requester, ticket_id } (§8.8); expiry is mandatory (§6.12, §4.5) yet optional in the waiver types (§11.10, §21); and a virtual patch is a Semantic rule (§3.2), a Signature rule (§8.8) or its own VirtualPatch kind (§21).

5. One context per request, task-local under async (§8.11, MM7, §6.4)

Context isolation means request A's taint and call stack are never visible to request B (§7.4). Synchronous apps use thread_local! (§3.2). Under an async runtime a request can hop threads, so thread_local! silently loses the context and taint can leak between requests; the design uses tokio::task_local! instead (MM7, §8.11). A spawned task inherits the parent's context_id but gets its own TaintMap, and taint crosses a task boundary only through an explicit TaintCarrier, a documented gap (§8.11). The lifecycle is Idle → Active → Completing → Done, and a RAII guard clears the slot even on panic (§8.3, §7.4). A missing context at a sink raises ContextMissing and applies the fail mode (§8.13), while the inline guard simply returns Allow when no context is active (§11.16). The design calls RequestContext !Send and TaintMap !Sync (§7.12), yet its async model stores Arc<Mutex<RequestContext>> (§8.11).

The trade-offs — where engineers disagree

Rust core with per-runtime adapters (ADR-001)

Chosen: Rust 2021 for zero-cost abstractions, memory safety on untrusted input, no garbage-collection pauses inline, precise FFI for the hook ABI, and catch_unwind for host safety (§9). Rejected: a JVM agent, a .NET profiler, a Node.js native addon, a Go plugin (§9). When the rejected choice is right: a JVM agent wins when the target is pure JVM and bytecode weaving gives richer hook coverage than C-ABI FFI; a Go plugin wins for a Go HTTP service where CGO overhead is acceptable and the team lacks Rust skills (§9). The cost is one adapter per language, kept out of core scope (§1.3).

Tokenizer for SQL injection (ADR-009)

Chosen: a libinjection-inspired tokenizer in pure Rust: it matches libinjection's accuracy, avoids regex backtracking, and a full parser is too heavy inline (§9). Rejected: regex, a full SQL parser (sqlparser-rs), an ML model (§9). When the rejected choice is right: a full parser wins in offline pre-execution analysis (batch audit, DAST scanner) where latency is not inline; an ML model wins when the corpus is domain-specific and a labeled training set is maintained (§9). Determinism also rules ML out of the blocking path (§6.3).

No DNS lookup inside the SSRF check (ADR-010)

Chosen: parse the URL and compare it with IP-range deny-lists, with no inline DNS. Inline DNS costs latency and opens a time-of-check-to-time-of-use gap (§9, §8.6.4). Rejected: resolve-and-compare, or a network egress hook (§9). When the rejected choice is right: resolve-and-compare wins when DNS rebinding is the main concern and a fast local resolver fits the budget; an egress hook wins where kernel-level interception already exists (§9). The Threat Model softens this: re-check after resolution when the adapter supplies a resolved IP.

Byte-range taint, not shadow memory (ADR-011)

Chosen: byte-range tags on string values, enough for HTTP injection detection at bounded cost (§9). Rejected: dynamic flow tracking with shadow memory, and LLVM DataFlowSanitizer (§9). When the rejected choice is right: shadow memory wins for security research and offline analysis where completeness beats performance; DataFlowSanitizer wins for native binaries you compile yourself with sanitizer passes (§9).

Drop events rather than block (ADR-013)

Chosen: tokio::sync::mpsc with an explicit capacity cap, dropping on full. A non-blocking send protects host safety, and drop-with-metric is preferred over backpressure (§9). The hot path increments a counter and the request is never delayed (§3.2, §6.15). Rejected: crossbeam-channel, flume, blocking send (§9). When the rejected choice is right: blocking send wins in an audit-only mode where no event may be lost (regulated finance, PCI-DSS audit completeness); crossbeam-channel wins in synchronous runtimes without Tokio (§9). The blueprint specifies the queue inconsistently: flume::bounded(4096) (§3.2, §4.1), tokio::sync::mpsc (§6.15, ADR-013) with a default of 8192 events (§11.17), and "default 64k events" with drop-oldest (Threat Model) where §3.2 drops the new event.

Roads not taken

Network WAF (Alt-A). Wins when you need language-agnostic protection with zero app changes and a fast first line at the edge. Rejected as the core because it cannot see the assembled query; kept as an outer layer (Alt-A, MM1).

Static analysis (Alt-B). Wins when you want to remove bug classes before deployment with no runtime overhead. It has no runtime values and over-reports infeasible paths, so it is a build-time complement (Alt-B).

Kernel interception with eBPF (Alt-C). Wins when you want one language-agnostic sensor below the runtime with no in-process code. It sees system calls but not which SQL string or class was involved, so it is deferred (Alt-C).

Interactive testing (IAST, Alt-D). Wins when you want to find vulnerabilities in QA with no production enforcement risk. It observes but does not protect production, so passive export is only deferred (Alt-D).

Deferred register. Also out of scope: an ML confidence scorer (un-defer if heuristic confidence proves insufficient on real corpora), cross-service traceparent taint, a GUI dashboard and auto-remediation (Deferred Features Register, §1.3).

What must never be false

Each line gives the invariant and how the system notices a violation (the "Violation detection" and telemetry fields of §7).

  • Host safety (§7.1): a RASP fault never crashes or hangs the host. Noticed by a missing HookReturned after HookEntered, and by rasp.internal_fault and rasp.hook_panic counters.
  • Monitor purity (§7.2): Monitor mode never returns Block. The counter rasp.action{action=Block, mode=Monitor} must stay zero and any non-zero value alerts.
  • Block determinism (§7.3): same inputs, same action and evidence. A fuzz test runs one event through decide 1000 times, and the policy version rides on every detection.
  • Context isolation (§7.4): no request reads another's context. A load test with distinct taint patterns checks 10k request pairs, and rasp.context_leak counts leaks.
  • Bounded taint soundness (§7.5): within budget no tag is lost. A property test applies every tracked op, and rasp.taint.budget_exceeded counts budget hits.
  • Overhead budget (§7.6): the guard stays inside its latency limits. A rasp-bench CI gate fails the build, and rasp.hook_latency_ns is emitted per call.
  • No blocking I/O on the hook path (§7.7): checked with strace or dtrace under load; rasp.io_on_hotpath_violation must stay zero.
  • Policy completeness (§7.8): every sink type has a rule. Load-time RaspError::PolicyIncomplete, rasp-cli validate and rasp.policy.uncovered_sink catch gaps. A rule-less sink falls to the fail mode and "never silently to Allow" (§7.8), though fail-open returns Allow (§3.2, §8.8).
  • Evidence integrity (§7.9): evidence is the byte-exact tainted substring; a property test checks it sits at its range.
  • Waiver non-bypass (§7.10): a waiver cannot cover all rules; validation rejects a wildcard rule_id, while the Threat Model allows a catch-all waiver with an explicit --force flag and Phase 9 lets rule_id: None cover all rules (§21).
  • Taint source completeness (§7.11): every HTTP input is a source before any sink, tested per input location, with rasp.source.missing counting capture failures.
  • Concurrency safety (§7.12): shared types are Send + Sync and immutable, checked by loom and ThreadSanitizer in CI.

What breaks in production

Hook fault (Failure Modes F1). Symptom: the hook returns an error and InternalError events appear. Cause: a panic, an out-of-memory error or a clock-read failure in the pipeline. Detection: catch_unwind logs a backtrace and emits an event. Recovery: the fail mode applies and the app continues.

Context leak (F2). Symptom: wrong taint on a request, a mismatched context_id, or growing memory. Cause: a thread-local not cleared, or an async scope that escaped. Detection: every lookup validates context_id and raises ContextMismatch. Recovery: discard the stale context, create a fresh one, and treat arguments as tainted.

Taint overflow (F3). Symptom: a TaintOverflow flag and missed injections on over-budget arguments. Cause: the map budget exceeded, or an untracked operation. Detection: the flag and a budget metric. Recovery: mark sink arguments conservatively tainted so detection still runs, then raise the limit or find the untracked op.

Analyzer hang (F4). Symptom: a latency spike and AnalyzerTimeout. Cause: an edge case or an oversized argument past the size cap. Detection: a per-analyzer wall-clock timeout (default 2 ms) checked at loop iterations. Recovery: return an "uncertain" detection and let the fail mode decide.

Policy load failure (F5). Symptom: the engine runs on a stale policy, with a rejected reload or an HMAC mismatch. Cause: a parse error, schema mismatch or tampered file. Detection: a PolicyLoadError event. Recovery: keep the last good policy and alert; the engine does not fail open on its own.

Telemetry loss (F6). Symptom: DroppedEvents rises and the SIEM sees nothing. Cause: the SIEM is down, a TLS cert expired, or the channel or disk is full. Detection: the DroppedEvents gauge, TelemetryError events on the stderr fallback and a SIEM delivery-failure counter. Recovery: drop the oldest events when the channel is full, and buffer to a local file when the TCP export fails.

Cascading failure (F10). Symptom: internal, telemetry and policy errors together. Detection: CascadeAlert when three or more failure classes occur within 60 seconds. Recovery: fail open and use the kill switch (rasp.kill_switch = true or RASP_KILL_SWITCH=1), which returns Allow for every event with no analysis.

Threats worth knowing (Threat Model):

  • Encoding tricks: input is decoded and normalized before taint capture, and evidence keeps raw and normalized forms (MM9, §23).
  • Oversized arguments: capped at MAX_SINK_ARG_BYTES (default 1 MiB), with a truncation flag in the event.
  • DNS rebinding to internal hosts: the allow-list is checked at construction and re-checked when a resolved IP exists.
  • Tampered policy file: an optional HMAC-SHA256 signature; a mismatch refuses the load and raises SecurityAlert.
  • Operator mistakes: deploying in Block mode with no baseline; the CLI warns and the audit log records mode changes (§6.5).

How it compares

Contrast Security instruments JVM and .NET bytecode for full dataflow taint and wins for managed-runtime enterprises wanting deep taint with no source changes. This design uses explicit byte-range taint behind a Rust hook ABI to keep overhead bounded and the trust boundary auditable, at the price of one adapter per language (Comparative Architecture Table).

OpenRASP (Baidu) puts hooks at known dangerous call sites and checks parameters and stack signatures with limited taint, which wins for quick deployment on PHP, Java and Python. This design propagates taint explicitly because signatures at the sink alone give more false positives on legitimately quoted data (Comparative Architecture Table, MM2, MM4).

Datadog ASM / Sqreen lives in the APM tracer with per-span taint annotation and a ddwaf rule engine, and wins where Datadog tracing already exists. This design rejects the WAF-leaning pattern model for core detection because it relies on edge patterns, not sink semantics (Comparative Architecture Table, §5 R3).

ModSecurity (a WAF) matches regexes at a reverse proxy and wins as a language-agnostic first line with zero app changes. This design does not use it as the core because it cannot see the assembled query, though it stays valid as an outer layer (Comparative Architecture Table, Alt-A, §6.13).

Building it — the phase plan

Build card: blueprints/build-cards/Runtime Application Self-Protection.md. One acceptance criterion per phase, as written in the phase's own section.

  • Phase 0 (§12): ten-crate workspace, core types, a mock app calling the hook for one SQL sink. Proof: a hook panic returns Allow (fail-open default) and logs record_guard_panic.
  • Phase 1 (§13): hook ABI, registry, dispatch. Proof: zero panics reach the host across 100 injected panics.
  • Phase 2 (§14): per-request context store. Proof: ContextGuard::drop() clears the context in 100% of a 100-thread leak test under ThreadSanitizer.
  • Phase 3 (§15): sink interception catalog. Proof: all 8 SinkType variants have registered adapters with round-trip SinkArgs extraction in CI.
  • Phase 4 (§16): taint tracking core. Proof: 1,000 parallel fake contexts show no cross-contamination.
  • Phase 5 (§17): SQL injection detection. Proof: attack-corpus detection rate ≥ 95% (≥ 24/25 fixtures at confidence ≥ 0.85).
  • Phase 6 (§18): command injection and path traversal. Proof: command-injection true-positive rate ≥ 98% on its corpus.
  • Phase 7 (§19): SSRF and deserialization. Proof: a private-IP SSRF is blocked in Block mode (guard_ssrf_block_test).
  • Phase 8 (§20): detection framework with correlation and dedup. Proof: a second identical detection within 100 ms is suppressed (dedup_tests).
  • Phase 9 (§21): policy and enforcement. Proof: a waiver with an expired TTL means the rule applies, 100% correct.
  • Phase 10 (§22): low-overhead fast path. Proof: benign-corpus p95 latency delta ≤ 5% of baseline.
  • Phase 11 (§23): evasion resistance. Proof: evasion-corpus block rate (500+ payloads) ≥ 99%.
  • Phase 12 (§24): observability. Proof: test_telemetry_nonblocking, 10k rapid sends on a full channel, shows zero guard-thread blocks and a drop counter equal to the overflow count.
  • Phase 13 (§25): conformance and security testing. Proof: fuzzing with zero panics in 1M runs per target.

Appendix B's milestone table numbers its phases differently from §12 to §25 (its Phase 3 is rasp-taint and its Phase 4 is rasp-detect, while §15 is the sink catalog and §16 the taint core).

Questions to test yourself

  1. How is "tainted data reached a SQL keyword position" computed, and why is mere taint presence insufficient to alert? Hint: §8.6.1 and MM4.
  2. Why does thread_local! break request context under tokio, and what replaces it? Hint: §8.11 and MM7.
  3. How does the engine stay within a 5% overhead budget when most arguments are untainted? Hint: the fast exit in §3.2, and Capacity C1.
  4. What attacker behaviour does the TaintMap byte/entry/tag cap defend against, and what is the fallback? Hint: §4.1, Capacity C2 and C3, and MM8.
  5. What is the blast radius if the RASP engine itself has a bug on the hook path, and how is it contained? Hint: §7.1 and Failure Modes F1 and F10.

If you only remember three things

RASP decides at the sink, where the real query and the real data provenance are both in hand, which is why it can be more precise than an edge filter (MM1, §3.3). Everything the engine does is bounded and fail-safe: caught panics, capped taint, a non-blocking telemetry queue and a fast exit for untainted arguments (§6.1, MM8, §6.15, §3.2). Roll out in Monitor mode first, because Monitor purity makes observing safe before enforcing (§6.5, §7.2).

Words used here

  • Sink: a dangerous call such as SQL exec, command exec, file open or deserialize (Glossary, §8.2).
  • Source: where untrusted input enters, such as an HTTP parameter, header, body, path or cookie (Glossary, §8.2).
  • Taint tracking: tagging input bytes and following them through string operations to the sink (Glossary, MM2).
  • Hook ABI: the C-compatible boundary between the app's runtime and the Rust engine (Glossary, ADR-020).
  • Adapter: the per-runtime shim that calls the hook ABI; specified but out of core (Glossary, §3.2).
  • Inline guard: rasp-protect, the pipeline run synchronously at every sink (Glossary, §3.2).
  • Monitor mode / Block mode: observe and log only, versus abort the sink and return a safe error (Glossary, §6.5).
  • Fail-open / fail-closed: on an internal error, allow the call versus block it (Glossary, §1.4).
  • Host-safety invariant: a RASP fault never crashes or hangs the app (Glossary, §7.1).
  • Virtual patching: a rule that blocks known-bad input without redeploying the app (Glossary, §2.4).
  • Waiver: a scoped, time-limited exemption from one rule (Glossary, §6.12).
  • WAF: a network-edge filter that sees only HTTP bytes (Glossary, Alt-A).
