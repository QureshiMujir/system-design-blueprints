4.2 Throughput + Scaling

  • Horizontal scaling: each app instance embeds its own RASP; no shared RASP process; scales with app.
  • Vertical scaling: TaintMap and analyzer are per-request; adding CPUs increases throughput linearly.
  • NUMA: per-request data structures allocated on calling thread's NUMA node; no cross-node contention.
  • Cache: TaintMap HashMap sized to fit in L2 cache for typical request (≤ 256 entries → ~16 KB); larger requests spill to L3.
  • Hot path: untainted-arg fast exit in rasp-taint reduces detector invocations to ~0% for benign args not derived from HTTP input.

RTO (RASP component restart) N/A — embedded; restarts with app
Fail-open default (brownfield) App continues on RASP internal error; 0% RASP-induced downtime

4.4 I/O + Storage

  • Audit log I/O: append-only structured JSON; async write via telemetry task; max write amplification: 1 log entry per blocked request (≤ 2 KB per entry).
  • Policy file: TOML/JSON; ≤ 10 MB; mmap-read at startup and reload.
  • No database: no persistent storage in core; telemetry is write-only to log/socket.
  • FD budget: ≤ 3 FDs per process (audit log file + metrics socket + policy file watch); does not consume app's FD budget materially.
  • Network: telemetry TCP export to SIEM; optional; max bandwidth ≤ 1 Mbps at 1000 blocks/s with CEF format.

4.5 Security Constraints

  • RASP engine code must pass cargo audit (no CVEs in deps) and cargo clippy --deny warnings in CI.
  • All unsafe blocks annotated with // SAFETY: justification; #![forbid(unsafe_code)] on all crates except rasp-hook (trampolines) and rasp-core (FFI types).
  • Attack corpus used in rasp-bench must include OWASP Top 10 (2021) injection variants; benign corpus must include high-volume framework traffic (Spring, Rails, Express patterns).
  • RaspError variants never expose internal taint paths in app-facing error messages (only in audit log); prevents oracle attacks via error messages.
  • Policy waivers must be time-bounded (TTL required) and signed (HMAC-SHA256 with operator key); no permanent anonymous waivers.

Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived from §4. Assume a baseline request of 20 ms server time and ~10 instrumented sink calls/request.

  • C1 — Per-request hook budget. 5% of a 20 ms request = 1 ms added latency budget (§4.1). Across 10 sink calls that is 100 µs/call average — exactly the p50 hook target; only the few tainted calls may spend up to the 500 µs p95.
  • C2 — TaintMap memory at peak concurrency. 512 KB/request × 10 000 concurrent (§4.1) = 5.1 GB worst case; this is why the per-request cap and OverBudget fallback (MM8) exist — without the cap, taint memory, not detection, is the failure mode.
  • C3 — Taint-tag fan-out ceiling. 4096 entries × 16 tags (§4.1) = 65 536 tags maximum per request; beyond it the engine does a conservative merge rather than growing — bounding the taint-explosion DoS.
  • C4 — Telemetry drain rate. Channel depth 4096 (§4.1); at 1 000 blocks/s an event-driven consumer must drain in ≤ 4.096 s of buffer — comfortably ahead of the ≤ 0.1% loss budget (§4.3) given async export.
  • C5 — SIEM export bandwidth. 1 000 blocks/s × ~125 B CEF record = 1 Mbps (§4.4), confirming the stated cap; verbose JSON (~2 KB/entry) would be 16× and is therefore reserved for the local audit log, not the wire.
  • C6 — File-descriptor footprint. 3 FDs/process (audit log + metrics socket + policy watch, §4.4); negligible against the host app's budget — a deliberate non-intrusion property.
  • C7 — Policy lookup cost. 10 000 rules in a BTreeMap (§4.1) ⇒ ≈ log₂(10 000) ≈ 14 comparisons per sink classification; sub-microsecond, off the latency critical path.
  • C8 — Idle footprint. ≤ 8 MB RSS idle (§4.1) plus live per-request TaintMaps; at 1 000 concurrent typical requests (~16 KB L2-resident map each, §4.2) that is ~16 MB of taint state — fits comfortably.
  • C9 — Detection-quality budget. ≥ 95% attack-corpus coverage at ≤ 0.01% benign false-positive rate (§4.3): at 1 M requests/day with 0.01% FP that is ≤ 100 false blocks/day — the operational ceiling that makes block-mode tolerable.
  • C10 — Throughput overhead. ≤ 5% RPS degradation (§4.1): a service doing 2 000 RPS may drop to ≥ 1 900 RPS under instrumentation — the CI regression gate fails the build below this.
  • C11 — Hot-reload window. ArcSwap atomic swap ≤ 100 ms (§4.1) with zero request pause: in-flight requests keep the old Arc<Policy>; new requests see the new one — no lock, no drain.
  • C12 — Stack-depth guard. ≤ 64 frames on the hook path (§4.1): bounds re-entrancy and prevents the agent itself from overflowing a deep app call stack.
