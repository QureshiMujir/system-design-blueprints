83 — Time-Series Database from Scratch

Project Number: 83

Project Name: Time-Series Database from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build ChronoDB, an embeddable, single-binary time-series database engine: ingest timestamped numeric samples tagged with label sets, persist them in time-partitioned, Gorilla-compressed immutable blocks behind a write-ahead log, and serve range/aggregation queries (rate, percentile, histogram) with bounded latency under high series cardinality, out-of-order writes, and continuous background compaction.

Phase-0 deliverable — repo skeleton + correctness kernel, as a numbered module list:

  1. chronodb-core — sample/series/labelset/error types, no I/O.
  2. chronodb-codec — Gorilla delta-of-delta + XOR codec, chunk framing.
  3. chronodb-wal — WAL segment format, append, replay.
  4. chronodb-index — label inverted index, postings, series-id allocation.
  5. chronodb-storage — head block, persistent block, manifest, compactor, retention.
  6. chronodb-query — selector, plan, executor, aggregation.
  7. chronodb-rollup — downsample tiers and jobs.
  8. chronodb-server — ingestion + query API surface, cardinality guard.
  9. chronodb-cli — admin CLI (compact / backup / restore / inspect).
  10. conformance — fixture-driven correctness suite.

System boundaries:

  • Provides: local durable storage of scalar time series; label-based series discovery; range queries with rate/percentile/histogram aggregation; downsampling; retention/TTL; crash recovery; single-node cardinality control.
  • Delegates: distributed consensus / multi-node replication protocol internals (uses WAL-shipping, not a bespoke consensus algorithm — see ADR-19); object-storage tiering client libraries; alerting-rule evaluation language; dashboarding/visualization.
  • Does NOT provide: a general-purpose SQL engine; secondary (non-time) indexing of arbitrary relational data; transactional multi-row ACID semantics across series; a built-in visualization UI.

Non-goals: becoming a general OLTP store; supporting non-numeric payloads (strings, blobs) as first-class sample values; guaranteeing exactly-once ingestion semantics across process restarts without client-side idempotency keys (§25).

Deployment model: single binary, single node for Phases 0–8; Phase 9 adds a WAL-shipping read-replica topology (PhaseDeferred("§21") covers multi-region active-active — see §35). Runs as a foreground process or system-managed daemon; no external coordination service required for a single-node deployment.

Target users: platform/SRE teams instrumenting infrastructure and application metrics; systems engineers studying storage-engine construction; embedders needing a metrics backend inside a larger product without operating a separate cluster.

Language: Rust (ADR-02). Rationale: predictable latency (no GC pause on the ingest hot path), safe manual memory layout for bit-packed codecs (§14), zero-cost abstractions for the WAL/mmap boundary (ADR-20), a mature ecosystem of prior art to study (Prometheus's tsdb, InfluxDB's tsm1, Beringei are the closest analogues, though in Go/C++ — see §5). Rejected: Go (GC pause risk on the p99 ingest/flush path, see M4); C++ (manual memory management increases corruption-class bugs in the codec/WAL boundary, see FM-1, FM-11); JVM/Java (GC pause + off-heap complexity for mmap'd blocks, unfavorable for the memory ceilings in §4).

Prerequisites: comfort with binary file formats, bit-level encoding, LSM/B-tree storage engine tradeoffs (O'Neil et al. 1996), and basic queueing/compaction scheduling.

Timeline: 10 phases, Phase 0 (skeleton) through Phase 9 (operational hardening); each phase is independently mergeable and gated by its own conformance fixtures (§26).

Deferred features are flagged inline as PhaseDeferred("§N") and registered in §35; every anchor used resolves to an existing section.

2. Why Build This

A time-series database compresses the essential tension of all storage engines into one narrow, well-studied workload: monotonic-ish append order, extreme write:read ratios, brutal compression opportunity (Pelkonen et al. 2015 report ~1.37 bytes/sample against a 16-byte raw pair), and a query surface (range scan + aggregation) simple enough to reason about completely. Building it from scratch forces mastery of: columnar delta/XOR codecs, inverted indexing under adversarial cardinality, WAL-based crash recovery (the same discipline as ARIES — Mohan et al. 1992), LSM-adjacent compaction scheduling (O'Neil et al. 1996), and the downsampling/retention tradeoffs every production monitoring stack (Prometheus, InfluxDB, Druid, Monarch) makes differently.

Architectural/historical significance: Facebook's Gorilla (Pelkonen et al. 2015) reset the industry's expectation for in-memory TSDB compression; Prometheus's tsdb (Reinartz 2017; Rabenstein & Volz) generalized it into a disk-backed, block-compacted engine that now underlies most of the CNCF observability stack; Druid (Yang et al. 2014) proved a segment-based columnar design scales to ad-hoc OLAP over high-cardinality dimensions; Google's Monarch (Adkins et al. 2020) shows the same primitives generalize to planet-scale multi-tenant ingestion. ChronoDB is a from-scratch synthesis of these four lineages at single-node scale.

Cross-links to sibling systems in this project set: shares its WAL/crash-recovery discipline with Two-Phase-Commit (durable-before-visible ordering) and its compaction/leveling discipline with any LSM-tree key-value store; shares its bit-packed columnar codec instincts with SIMD-Library (vectorized decode); shares its inverted-index/postings-list machinery with Vector-Database's metadata filtering.

Calibration value: forces an engineer to hold four disciplines simultaneously — bit-level codec correctness, index/cardinality economics, crash-safe log-structured storage, and query planning — each individually well-documented, but rarely combined in one project at tractable scope.

What Mastery Looks Like

  • Derive, from first principles, why delta-of-delta timestamp encoding collapses a regular scrape interval to near-zero bits (Phase 2, §14).
  • Explain why label cardinality is a multiplicative, not additive, cost and design a hard ingestion-time guard against it (Phase 8, §20).
  • Implement a WAL replay that is provably idempotent and produces byte-identical state to the pre-crash head block (Phase 4, §16).
  • Design a compaction scheduler that never starves foreground ingestion (Phase 5, §17).
  • Merge out-of-order and in-order samples into one queryable view without blocking live writers (Phase 6, §18).
  • Build a query executor whose latency is bounded by index selectivity, not raw block size (Phase 7, §19).
  • Reason quantitatively about a downsample tier's information loss and storage payoff (Phase 8, §20).
  • Run a full disaster-recovery drill (WAL replay + block re-validation) and hit a numeric RTO target (Phase 9, §21).

chronodb-server is the trust and process boundary: it authenticates/limits ingestion (cardinality_guard, T1/T3) and terminates the query API. chronodb-wal is the durability boundary — no sample is acknowledged until its WAL record is fsynced (P5, I5). chronodb-storage is the persistence and concurrency boundary: head.rs is the only mutable structure in the system (P1); block.rs/manifest.rs are strictly immutable once written (I10); compactor.rs and retention.rs run as background, throttleable workers (P7) that never hold locks the ingest path needs. chronodb-index is shared, read-mostly state consulted by both ingestion (series lookup/creation) and query (label selection); it is the cardinality-economics chokepoint (P4). chronodb-codec is a pure, allocation-free library with no knowledge of blocks, WAL, or index — it only knows bytes in, bytes out (testable in isolation, §14). chronodb-rollup is a downstream reader/ writer that treats persisted blocks as its only input, guaranteeing rollups never touch the mutable head (P10).

6. Design Principles

P1 — Append-only mutation boundary. Mutable state exists only inside head.rs; everything reachable via block.rs is immutable once its manifest is written. Tradeoff: forgoes in-place update convenience. Operational implication: any bug must be reasoned about as "which head-block operation produced this," never "which block was edited." Violating it: a stray in-place block edit invalidates every checksum and mmap reader (I10).

P2 — Time-partition everything. Chunks and blocks are bucketed by a fixed time range, never by series identity alone. Tradeoff: a query spanning many partitions touches many files. Operational implication: retention and compaction become "drop/merge a directory," not "scan and delete rows." Violating it: retention becomes an O(rows) tombstone sweep instead of an O(blocks) directory drop (§20).

P3 — Compress at the leaf. Each column (timestamp, value) gets its own codec tuned to its statistical shape: delta-of-delta for near-regular timestamps, XOR for slowly-varying floats (Pelkonen et al. 2015). Tradeoff: two codecs to maintain instead of one generic compressor. Operational implication: compression ratio is measurable and testable per column (M5). Violating it: a generic byte compressor (gzip/zstd) on interleaved rows loses most of the regularity Gorilla exploits.

P4 — Cardinality is a multiplicative cost. Every unique label combination is a new series with its own chunk stream, index entries, and memory footprint; cost scales with the product of label value counts, not their sum. Tradeoff: guarding it means rejecting writes, which upsets naive clients. Operational implication: the guard must be at ingestion (ADR-14), not query time. Violating it: one label with unbounded values (e.g. a raw user ID) silently multiplies total series count past the memory ceiling (§4).

P5 — WAL before ack. No sample is visible to queries or acknowledged to the client until its WAL record is durably fsynced (mirrors ARIES, Mohan et al. 1992). Tradeoff: ack latency is bounded below by fsync latency (M4). Operational implication: fsync batching is the primary ingest-throughput lever. Violating it: an acked-but-unlogged sample vanishes on crash, breaking I5 and any client's at-least-once assumption.

P6 — Out-of-order is normal at the edge, ordered at the core. Samples may arrive out of timestamp order from many producers, but the persisted chunk stream is always timestamp-sorted per series. Tradeoff: requires a merge step (ADR-15) instead of a pure append. Operational implication: the OOO window (§4) bounds how much reordering the merge step must tolerate. Violating it: treating OOO as an error case causes silent data loss for any real distributed-collection topology (T-independent of malice).

P7 — Compaction is a throttleable background tax. Compaction/downsampling never hold locks the ingest path needs and can always be paused/rate-limited. Tradeoff: a paused compactor lets read-amplification grow temporarily. Operational implication: compaction throughput (M8) must exceed sustained ingestion volume on average, or the backlog is unbounded (FM-3). Violating it: a compaction that blocks ingestion turns a storage-tier problem into an availability incident.

P8 — One append-owner per series-shard. Each series-shard's head-block append path has exactly one writer at a time (no cross-thread contention inside a shard). Tradeoff: sharding granularity trades parallelism against per-shard overhead. Operational implication: shard count is a capacity-planning knob (§32). Violating it: concurrent appenders to one shard need fine-grained locking that defeats the single-writer simplicity this design relies on for I2.

P9 — Query planning separates selection from scan. The label index answers "which series," the chunk codec answers "what values" — the planner never conflates the two. Tradeoff: two-phase planning adds a hop vs. a single combined scan. Operational implication: index selectivity, not raw block size, bounds query latency (§29). Violating it: a query executor that decodes chunks before applying label filters wastes I/O proportional to unfiltered data volume.

P10 — Downsampling is explicit, never silent lossy compression. Every rollup tier's precision loss is documented and queryable as metadata, never implicit. Tradeoff: rollup tiers cost extra storage (they coexist with raw for their overlap window). Operational implication: users can always tell which precision tier answered their query. Violating it: an operator silently loses the ability to distinguish a real spike from an averaging artifact.

P11 — Every persisted block is self-describing. manifest.rs's meta.json carries enough metadata (time range, series count, checksum, encoding versions) to validate or reject a block without consulting any other state. Tradeoff: metadata duplication across manifest and index. Operational implication: a block can be copied, backed up, or inspected standalone (§24). Violating it: block validity becomes dependent on external state that can drift (I10).

P12 — Crash recovery is idempotent replay. Replaying the same WAL segment twice (e.g. after a recovery retried mid-way) must produce the same head-block state as replaying it once. Tradeoff: requires each WAL record to carry enough identity to detect a repeat. Operational implication: recovery can be safely retried without a "have I already replayed this" side-channel. Violating it: double-application of a WAL segment corrupts sample counts and rollup aggregates (I9, I14).

P13 — Memory ceilings are enforced, not advisory. The head block triggers admission control (I11) before the process risks OOM, never after. Tradeoff: legitimate bursts above the ceiling are rejected, not queued unboundedly. Operational implication: the ceiling (§4) must be sized with margin for the largest expected legitimate burst. Violating it: an advisory-only limit degrades into an OOM kill, which loses the entire unflushed head block (FM-2).

P14 — Deletion is tombstone-first, physical reclaim later. A delete/retention-expiry marks data as a tombstone immediately but only physically reclaims space during the next compaction pass, after a grace period. Tradeoff: deleted data occupies disk briefly past its logical deletion. Operational implication: the grace period (§4/I7) bounds "how long until space is actually freed." Violating it: synchronous physical deletion blocks the compactor or the query path on every delete request (P7).

8. Domain Model / Protocol / Data Model

8.1 Ingestion grammar (line-protocol-style, EBNF)

sample      ::= metric labels? SP value SP timestamp
metric      ::= identifier
labels      ::= "{" label ("," label)* "}"
label       ::= identifier "=" quoted_string
value       ::= float
timestamp   ::= int64            (* unix millis, ADR-18 *)
identifier  ::= letter (letter | digit | "_")*

Conforms to the shape of both the OpenMetrics exposition format and InfluxDB line protocol (§5, RFCs/Specifications); chronodb-server::ingest.rs accepts either via a pluggable front-end parser, normalizing into the internal Sample/SeriesRef types (§11).

8.2 Chunk wire layout (Gorilla-style, per series, per chunk)

Field Width Notes
magic 2 B format sentinel
encoding 1 B 0x01 = delta-of-delta+XOR (ADR-03/04)
num_samples varint count in this chunk
first_ts 8 B absolute i64 millis
first_value 8 B absolute f64 bits
ts_stream bitstream delta-of-delta encoded, samples 2..n
val_stream bitstream XOR encoded, samples 2..n
crc32c 4 B trailer, covers all preceding bytes

Worked example (5 samples, 15 s nominal interval, one late sample):

i ts (ms) Δ ΔΔ ts bits written value XOR-vs-prev bits
0 1000000 — — 64 (absolute) 10.0 64 (absolute)
1 1015000 15000 — varint(15000) 10.0 0 (identical)
2 1030000 15000 0 0 (1 bit, "same delta") 10.1 control+meaningful-XOR bits
3 1045200 15200 200 control+varint(200) 10.1 0
4 1060000 14800 -400 control+varint(-400) 9.9 control+meaningful-XOR bits

Malformed-input example: a chunk whose num_samples disagrees with the bit-length implied by decoding the streams to exhaustion — rejected by chunk.rs decode with ChunkError::LengthMismatch, never partially returned (ties to I10).

Failure-path example: process crashes after the WAL fsync for sample i=4 but before head.rs updates its in-memory chunk buffer — on restart, replay.rs re-applies the WAL record for i=4 to a freshly-initialized head, producing the identical chunk buffer state (I14) — no data loss, no duplication.

12. Phase 0 — Repository Skeleton & Correctness Kernel

12.1 Objectives

Stand up the Cargo workspace (§10), implement chronodb-core's pure types (§11) with zero I/O, and prove the most basic round-trip: a Sample survives a naive in-memory encode/decode with no compression. This phase draws no wire format conclusions yet — it only fixes the vocabulary every later phase depends on (terminology lock, AUTHORING contract).

12.2 Detailed Implementation Steps

  1. Create the workspace Cargo.toml and all ten crates from §10 as empty library stubs.
  2. Implement Sample, Timestamp, Value, LabelSet, SeriesId, SeriesRef exactly per §11's signatures — apply P1 (nothing here is mutable-shared state yet).
  3. Implement ChronoError variants; every later phase adds cases here, never a second error type (terminology lock).
  4. Implement a trivial RawCodec (fixed 16 bytes/sample, no compression) purely to validate the crate wiring — this is explicitly superseded in Phase 2 (ADR-03/04) and flagged PhaseDeferred("§14") for the real Gorilla codec.
  5. Write the Phase-0 conformance fixture generator (conformance/runner/main.rs skeleton).
  6. Stand up CI: cargo build --workspace, cargo test --workspace, cargo clippy gate (ties to §27).

12.3 Deliverable

A compiling ten-crate workspace; chronodb-core fully implemented per §11; a RawCodec::encode/decode round-trip function pair (signatures only, no loop bodies shown in this document); CI green on an empty test matrix.

12.4 Acceptance Criteria

  • cargo test --workspace passes with ≥ 1 test per crate stub (10 tests minimum).
  • RawCodec round-trip fixture conformance/fixtures/raw_roundtrip.json (100 samples) decodes byte-identical to its encoded input.
  • Workspace build time ≤ 30 s on CI reference hardware (M-series or equivalent, 4 vCPU).

12.5 Conformance Fixtures

raw_roundtrip.json — 100 (ts, value) pairs, ordered, covers ts=0, negative values, NaN rejection (ChronoError must reject NaN — I2 assumes totally-ordered comparable values only for ts, not value, so NaN value is legal but must round-trip bit-exact).

12.6 Pitfalls

  • Defining LabelSet equality/hash before sorting label pairs — breaks I3 the moment two label sets with the same pairs in different insertion order hash differently.
  • Letting SeriesId start at 0 and overload it as a sentinel "no series" value elsewhere — reserve a distinct Option<SeriesId> instead.

12.7 Performance Concerns

None load-bearing yet — this phase is correctness-only. Record a baseline RawCodec encode/decode throughput number now (even though unoptimized) as the Phase-2 comparison baseline for M5.

12.8 Edge Cases

  • Empty LabelSet (bare metric name, no labels) — must be legal and distinct from a LabelSet with one empty-string-valued label.
  • Sample at Timestamp::MIN/MAX — must not overflow in the trivial codec.

12.9 Failure Analysis

The only failure mode reachable at this phase is a build/test failure (no running system yet); tie this to FM-12's fixture as a forward reference — PhaseDeferred("§13") covers the actual poison-pill-sample runtime handling.

12.10 Operational Notes

Establish the crate-per-concern discipline now; every later phase adds files, never restructures existing ones (terminology lock is cheapest to enforce at zero code mass).

13. Phase 1 — Series Identity & Label Inverted Index

13.1 Objectives

Implement chronodb-index: SeriesId allocation, the label inverted index, and postings lists, in memory only (no persistence yet — that is Phase 4/5). Establish the cardinality-economics chokepoint (P4) as a first-class, testable structure.

13.2 Detailed Implementation Steps

  1. Implement seriesid.rs's allocator: a monotonic counter guarded by a single lock per shard (P8); registering an existing LabelSet returns its existing SeriesId (I3).
  2. Implement labelindex.rs: on series registration, insert SeriesId into the postings list for every (label_name, label_value) pair it carries (ADR-07).
  3. Implement postings.rs's sorted delta-varint representation (ADR-08); provide set-intersection/union signatures for multi-matcher selectors (used by §19 later).
  4. Implement the cardinality counter per shard, feeding the not-yet-enforced guard (enforcement lands in Phase 8, ADR-14) — for now, only count and expose a metric.
  5. Write the index/registration conformance fixture and a differential test: registering the same LabelSet twice must be idempotent (I3).

13.3 Deliverable

chronodb-index crate: series registration, label→postings lookups, and matcher-driven set operations, entirely in-memory, with a metric exposing live series count per shard.

13.4 Acceptance Criteria

  • label_index.golden fixture: 10,000 synthetic series across 8 label names reproduce an exact expected postings-list byte layout on disk-format preview.
  • Series registration throughput ≥ 200,000 registrations/sec/core on CI reference hardware (baseline for M6).
  • Duplicate-registration idempotency verified for 10,000 repeated registrations (I3).

13.5 Conformance Fixtures

label_index.golden — fixed synthetic label universe, exact expected postings-list contents per label value, used as a golden file across all future postings-encoding changes (ADR-08 alternatives can be benchmarked against it without behavior change).

13.6 Pitfalls

  • Building postings lists as unsorted Vec<SeriesId> "to add sorting later" — breaks ADR-08's on-disk encoding assumption and I8's cross-check tooling from day one.
  • Forgetting that a label name can have many values; indexing only label_name without label_value collapses all values into one useless postings list.

13.7 Performance Concerns

Postings-list insertion for a high-cardinality label value (P4) must stay O(log n) via sorted insertion, not O(n) via a linear scan-then-append; benchmark specifically at 100,000 series on one label value to catch this before Phase 8's guard is even built.

13.8 Edge Cases

  • A LabelSet with a label value containing the index's internal delimiter character — must be escaped/length-prefixed, never split incorrectly (feeds §8.1's grammar).
  • Removing the last series for a label value must not leave an empty postings entry that never gets swept (a slow index-size leak).

13.9 Failure Analysis

FM-7 (cardinality explosion degrading query latency) has its root cause seeded here: an index with no per-shard series-count ceiling yet is, by design, exposed to this failure mode until Phase 8 closes the loop with I11's enforcement.

13.10 Operational Notes

Expose series_count{shard} and postings_bytes{label} as gauges now (§24); they are the earliest warning signal for the cardinality problem this whole project treats as a first-class threat (T1).

14. Phase 2 — Gorilla Chunk Codec

14.1 Objectives

Replace Phase 0's RawCodec with the real Gorilla-style codec (Pelkonen et al. 2015): delta-of-delta timestamp encoding and XOR float encoding, framed as the chunk format in §8.2. This is the compression-ratio-defining phase (M5).

14.2 Detailed Implementation Steps

  1. Implement bitstream.rs's bit-level writer/reader (ADR-24) — the substrate every other codec module writes through.
  2. Implement delta_of_delta.rs per Pelkonen et al. 2015 §4.1's control-bit scheme (ADR-03): store the first timestamp absolute, first delta as a varint, then each subsequent delta-of-delta with a variable-length control-bit prefix selecting bucket width.
  3. Implement xor_float.rs per Pelkonen et al. 2015 §4.2 (ADR-04): store the first value absolute; each subsequent value as an XOR against the previous, with control bits indicating "identical," "same leading/trailing zero window," or "new window."
  4. Implement chunk.rs's header/trailer framing (§8.2) wrapping both streams plus the CRC32C trailer (ADR-11).
  5. Enforce I2 (strictly increasing ts) at encode time — reject or reroute to the OOO path (P6, deferred enforcement to Phase 6, PhaseDeferred("§18")).
  6. Build the differential fixture: compare compression ratio against Phase 0's RawCodec baseline on a synthetic 15s-interval, slowly-varying-gauge dataset.

14.3 Deliverable

chronodb-codec crate: full Gorilla-style chunk encode/decode, CRC-verified, with a measured compression ratio report against the M5 target.

14.4 Acceptance Criteria

  • chunk_roundtrip.json fixture (5,000 samples, 15 s nominal interval with 2% jitter, one gap, one out-of-band NaN value) decodes byte-identical to input.
  • Compression ratio ≥ 8× vs. raw 16 B/sample baseline on the fixture dataset (M5 floor); target ≈ 1.37 B/sample as reported for production workloads in Pelkonen et al. 2015.
  • CRC mismatch on a bit-flipped fixture byte is detected 100% of the time (1,000-trial fuzz run) — ties to I4/T4.

14.5 Conformance Fixtures

chunk_roundtrip.json — the canonical dataset above; regenerated deterministically from a fixed seed so every future codec change re-validates against the exact same bytes.

14.6 Pitfalls

  • Off-by-one in the "first sample is absolute, rest are deltas" boundary — corrupts every subsequent sample silently if the control-bit scheme desyncs (caught by CRC, I4, but only at chunk granularity — add a mid-stream self-check in debug builds).
  • Choosing bucket widths for the delta-of-delta control bits without measuring real jitter distributions first — copy Pelkonen et al. 2015's published buckets as a starting point, don't invent new ones without data.

14.7 Performance Concerns

Decode must be branch-light on the common "value identical, delta identical" path (the overwhelmingly common case for regular-interval metrics) — this is the path M5's compression ratio and the query engine's decode latency (M2/M3) both depend on.

14.8 Edge Cases

  • Single-sample chunk (no deltas at all) — degenerates to "absolute ts + absolute value, no streams" and must not underflow the bitstream reader.
  • Two identical consecutive timestamps (duplicate ingestion) — I2 says this must never reach the codec; the codec itself only needs to detect and reject it defensively.

14.9 Failure Analysis

FM-11 (checksum mismatch on read) is first exercised here: a corrupted chunk must surface as ChunkError → ChronoError::ChunkDecodeError, never a silent wrong-value return (ties directly to I10's "never serve from a failed-checksum block").

14.10 Operational Notes

Publish the measured compression ratio (M5) as a startup log line and a gauge metric per block — operators need this number to reason about disk sizing before hitting the retention ceiling (§4).

15. Phase 3 — In-Memory Head Block & Append Path

15.1 Objectives

Implement head.rs: the single mutable structure in the system (P1), owning per-series chunk buffers, driving the state machine in §8.4 through Empty → Active → Sealing.

15.2 Detailed Implementation Steps

  1. Implement Head's per-shard structure (P8): one append lock per shard, each shard owning a subset of SeriesId space.
  2. Wire ingest.rs's parser (§8.1 grammar) to head.rs's append entry point, routing through chronodb-index's registration (Phase 1) for unseen LabelSets.
  3. Implement in-progress chunk buffering: an active chunk accumulates samples via the Phase-2 codec's incremental encode path until it hits the ADR-05 size target or the block's time-range boundary.
  4. Implement the Active → Sealing transition (§8.4): triggered by wall-clock boundary or PhaseDeferred("§16")'s not-yet-built memory-ceiling signal (I13's atomic swap itself is completed in Phase 5 once block.rs exists to swap into).
  5. Reject non-monotonic per-series timestamps at this layer per I2, surfacing ChronoError (not yet rerouting to OOO — that lands in Phase 6).

15.3 Deliverable

head.rs fully implemented for the single-node, in-order, no-crash-recovery case: live ingestion into memory, in-progress chunk buffers per series, ready to be flushed once block.rs exists (Phase 5).

15.4 Acceptance Criteria

  • Sustained append throughput ≥ 400,000 samples/sec/node on CI reference hardware (M1 floor), measured via bench/ingest_bench.rs.
  • 10,000-series, 1-hour synthetic ingest run produces per-series chunk buffers whose total sample count matches the input exactly (0 loss, 0 duplication).
  • Non-monotonic timestamp injection (1% of samples) is rejected with ChronoError, verified by count, not by "log looks fine."

15.5 Conformance Fixtures

head_append.golden — 10,000-series/1-hour synthetic ingest trace with expected per-series final chunk-buffer sample counts.

15.6 Pitfalls

  • Sharding by SeriesId % N naively — if SeriesId allocation is not uniformly distributed (e.g. burst-registered series cluster in id ranges), shards become unbalanced; shard by a hash of SeriesId instead.
  • Allowing an in-progress chunk buffer to grow unbounded when no size/time boundary is configured — always have a hard fallback boundary independent of configuration.

15.7 Performance Concerns

Per-shard lock contention (P8) is the primary throughput ceiling at this phase; measure p99 append latency (M1's latency companion) specifically under many-shards-many-cores contention, not just single-shard throughput.

15.8 Edge Cases

  • A series registered but never appended to within a block's time range — must not appear in that block's manifest sample count, but must still exist in the index.
  • Burst of new-series registrations (cardinality spike) arriving faster than the not-yet-built guard (Phase 8) can react — record this as the seed condition for FM-2.

15.9 Failure Analysis

FM-2 (head-block OOM under cardinality spike) is directly reachable at this phase since I11's enforcement is PhaseDeferred("§20"); document the interim mitigation (process-level memory limit + restart) until Phase 8 lands the real guard.

15.10 Operational Notes

Expose head_active_series, head_bytes_estimate, and head_append_latency_seconds (§24) now — these three signals are what Phase 8's cardinality guard will threshold against.

16. Phase 4 — Write-Ahead Log & Crash Recovery

16.1 Objectives

Implement chronodb-wal: durable, fsynced, CRC-checked append-only logging (ADR-06), gating every head-block append per P5, and a replay path proving I14's idempotent recovery.

16.2 Detailed Implementation Steps

  1. Implement segment.rs: fixed-size (§4, 128 MiB) rotating segment files, each record framed per §8.3, CRC32C trailer per record (I4, ADR-11).
  2. Implement record.rs's WalRecord variants exactly per §11; every head.rs mutation from Phase 3 must now go through a WAL write-then-fsync-then-apply sequence (P5, I5, applying Mohan et al. 1992's WAL-before-ack rule directly).
  3. Implement checkpoint.rs: periodic checkpoint records marking "head state as of this point is durably reflected in these WAL offsets," bounding replay time (M10).
  4. Implement replay.rs: on startup, scan from the last checkpoint, re-apply WalRecords to a fresh Head, verify against I14 via the golden-state fixture.
  5. Implement truncation-on-corruption: on a CRC mismatch (I4), truncate the segment at the last good record and log the loss window explicitly (FM-1, never silent).

16.3 Deliverable

chronodb-wal crate fully wired into head.rs's append path; a working crash-and- recover cycle: kill the process mid-ingest, restart, and observe correct resumed state.

16.4 Acceptance Criteria

  • wal_replay.golden fixture: kill-and-restart at 20 injected crash points during a 10,000-sample ingest run reproduces byte-identical head state each time (I14).
  • WAL fsync p99 latency ≤ 20 ms (M4 ceiling) at 400,000 samples/sec sustained load.
  • Startup replay time ≤ 30 s per 1 GiB of unflushed WAL (§4 floor), measured on the reference hardware.
  • A deliberately corrupted segment (single bit-flip at a random offset, 100 trials) truncates cleanly at the corruption point in 100/100 trials, never crashing the process.

16.5 Conformance Fixtures

wal_replay.golden — the 20-crash-point fixture above, one golden head-state snapshot per crash point.

16.6 Pitfalls

  • fsyncing per-record instead of batching — tanks throughput (M1) far below target; batch fsyncs on a bounded time/size window instead, per Gregg 2020's fsync-cost reasoning (§5).
  • Forgetting checkpoints entirely — replay time grows unbounded with WAL age, violating the RTO in §4.

16.7 Performance Concerns

fsync latency (M4) is the throughput ceiling for the entire ingest path (P5); this is the single most important number in the whole system to benchmark on real target hardware/filesystem before committing to a batching strategy.

16.8 Edge Cases

  • Process killed exactly between "WAL fsync completed" and "head.rs apply completed" — I14 must hold: replay must still apply the record (it was durably logged) even though the in-memory head never got to.
  • Truncated final segment on disk from a prior ungraceful shutdown — replay must detect and truncate it, not treat the partial trailing bytes as a valid record (I4).

16.9 Failure Analysis

FM-1 (WAL segment corruption mid-write) is the canonical failure this phase exists to contain: detection is the CRC mismatch (I4), recovery is truncate-and-continue, and the loss window (if any) must be surfaced via wal_truncated_bytes_total, never hidden.

16.10 Operational Notes

Document the exact replay procedure as a runbook entry (§24): "process crashed" is not an incident by itself as long as replay completes within the RTO and I14 holds; alert only if replay time or truncation events exceed thresholds.

17. Phase 5 — Persistent Blocks & Compaction

17.1 Objectives

Implement block.rs, manifest.rs, and compactor.rs: the immutable, self-describing persistent tier (P11), the atomic head→block flush (I13), and time-range-leveled compaction (ADR-09, O'Neil et al. 1996's merge-cost model).

17.2 Detailed Implementation Steps

  1. Implement manifest.rs's BlockMeta (§11) and the directory layout of §8.5; write meta.json last, after chunks/index are fully written and checksummed (P11).
  2. Implement the Active/Sealing → Persisted flush (§8.4): copy-on-write pointer swap from head.rs to the new block.rs instance so queries never see a partial state (I13) — this is the atomicity Phase 3 deferred.
  3. Implement compactor.rs's time-range leveling per ADR-09: merge N raw 2-hour blocks into one 2-day block, then N of those into one 2-week block, verifying I6 (disjoint, contiguous, no sample loss) after every merge.
  4. Implement mmap-backed block open (ADR-20) with checksum verification gating query visibility (I10) — a block failing checksum is quarantined, not served.
  5. Implement compaction throttling (P7): a token-bucket rate limiter bounding compactor I/O so it never starves the ingest path's disk bandwidth.

17.3 Deliverable

Full raw-tier persistence: head blocks flush to disk, disk blocks compact upward through the leveling scheme, and a restarted process can serve queries purely from persisted blocks with zero in-memory state.

17.4 Acceptance Criteria

  • block_flush.golden fixture: 100 consecutive head-flush cycles produce 100 blocks whose manifests' sample counts sum exactly to the injected sample count.
  • Compaction of 10× 2-hour blocks into one 2-day block preserves sample count exactly (I6) in a 50-trial fuzz run (randomized series/timestamp distributions).
  • Compaction throughput ≥ 50 MiB/s/core (M8 floor) measured via bench/query_bench.rs's companion compaction benchmark.
  • A block with a deliberately corrupted meta.json checksum is quarantined and excluded from query results in 100% of 20 injected-corruption trials (I10).

17.5 Conformance Fixtures

block_flush.golden — the 100-cycle fixture above, including three deliberately corrupted blocks that must be quarantined, not served.

17.6 Pitfalls

  • Writing meta.json before chunks/index are fully flushed to disk — a crash in that window produces a manifest describing data that doesn't exist yet, breaking P11's self-describing contract.
  • Letting compaction run unthrottled "because it's idle time anyway" — the moment ingestion volume spikes, an unthrottled compactor starves it (P7, FM-3).

17.7 Performance Concerns

Compaction is write-amplifying by construction (O'Neil et al. 1996): each level rewrites all its input bytes. Track write-amplification factor explicitly (§29) — it is the dominant disk-I/O cost at steady state, exceeding raw ingestion I/O once several levels exist.

17.8 Edge Cases

  • A block spanning exactly the boundary between two compaction-eligible windows — must be assigned to exactly one leveling cycle, never double-compacted (I6's disjointness).
  • Compaction input blocks whose combined series count exceeds a single output block's practical index size — must split into multiple output blocks, still satisfying I6.

17.9 Failure Analysis

FM-3 (compaction backlog/stall) and FM-4 (disk-full during compaction merge) are both first reachable here: FM-3's detection is the queue-depth metric (§24), FM-4's detection is the merge write failing mid-way — recovery is to retain the original, pre-merge inputs unchanged until disk space frees (never partially commit a merge, I6).

17.10 Operational Notes

Expose compaction_backlog_blocks, compaction_bytes_written_total, and block_quarantined_total (§24); a growing backlog is the earliest signal of FM-3 before query latency (M3) visibly degrades.

18. Phase 6 — Out-of-Order Ingestion & Backfill

18.1 Objectives

Implement the OOO staging path (ADR-15): accept samples arriving behind the head's current max timestamp within the configured window (§4), merge them into the correct historical position without blocking the live append path (P6).

18.2 Detailed Implementation Steps

  1. Implement an OOO staging buffer distinct from the live head (ADR-15): samples with ts < head.max_ts but within the OOO window (§4) route here instead of the normal append path.
  2. Enforce I12 at the staging boundary: samples older than the window are rejected with an explicit ChronoError::OutOfOrderRejected, counted, never silently dropped.
  3. Implement merge-on-read for queries spanning both the live head and OOO staging (P6/P9): the query planner (Phase 7) must union both sources transparently.
  4. Implement periodic OOO-to-block merge: staged samples are merged into a new compaction input alongside the relevant existing block, re-validated against I6.
  5. Implement a backfill admin API (chronodb-cli) for bulk historical loads that bypass the live ingest path entirely, writing directly to a staged block awaiting merge.

18.3 Deliverable

An ingestion path that accepts realistic out-of-order/multi-producer traffic and bulk backfills without blocking or corrupting the live append path, verified by a merged query returning correctly time-ordered results across live+staged+persisted sources.

18.4 Acceptance Criteria

  • ooo_backfill.json fixture: 5,000 samples with 15% arriving out of order within the 1-hour window (§4) merge into a query result identical to the fully-sorted input.
  • Samples older than the OOO window (500 injected) are rejected 100% of the time with OutOfOrderRejected, and ooo_window_rejected_total increments exactly 500 (I12).
  • A 1,000,000-sample backfill via the CLI completes without measurably increasing live ingest p99 latency (≤ 5% delta vs. baseline M1 latency).

18.5 Conformance Fixtures

ooo_backfill.json — the 5,000-sample mixed-order fixture above, plus a 500-sample "too old, must reject" fixture appended.

18.6 Pitfalls

  • Implementing OOO merge by re-sorting the entire live head on every staged batch — O(n log n) per batch defeats the point of a separate staging structure; merge only the affected time range.
  • Treating "backfill" and "OOO" as the same code path without distinguishing bulk-load performance needs (throughput-optimized, latency-tolerant) from live-OOO needs (latency-sensitive, small batches).

18.7 Performance Concerns

Merge-on-read (P9) adds a second source to union at query time; benchmark query latency specifically for ranges overlapping active OOO staging vs. ranges that don't — the former must still meet M2/M3 targets, not just the steady-state case.

18.8 Edge Cases

  • A backfill batch that itself contains internal out-of-order samples relative to each other (not just relative to the head) — must be sorted before staging, not assumed pre-sorted.
  • OOO samples that exactly fill a gap at a chunk boundary — must not create a degenerate zero-sample chunk on either side after merge.

18.9 Failure Analysis

FM-6 (network partition losing remote-write acks, causing client-side retries and duplicate sends) interacts directly with this phase: duplicate OOO samples (identical ts+value re-sent) must be idempotently absorbed, not double-counted — ties to I9's rollup-count correctness downstream.

18.10 Operational Notes

Expose ooo_staged_samples, ooo_merge_latency_seconds, and backfill_jobs_active (§24); operators running large backfills need the last one to confirm progress without inferring it from ingest metrics.

19. Phase 7 — Query Engine & Aggregation

19.1 Objectives

Implement chronodb-query: selector matching against the label index (P9), a query plan/executor separating selection from chunk scan, and rate/percentile/histogram aggregation over decoded samples.

19.2 Detailed Implementation Steps

  1. Implement selector.rs's Matcher/Selector (§11) and its translation into postings set-operations against chronodb-index (ADR-07/08, applying P9's selection-first rule).
  2. Implement plan.rs's QueryPlan: resolve the selector to a SeriesId set, resolve the time range to the set of overlapping blocks + head + OOO staging (§18), and decide aggregation pushdown per ADR-13.
  3. Implement exec.rs's pull-based iterator chain (ADR-12): one iterator per matched series/block combination, merged in timestamp order for the result stream.
  4. Implement aggregate.rs: rate() (per-second average delta over a range, matching Prometheus's convention of handling counter resets), quantile estimation (t-digest or equivalent signature-level design), and fixed-bucket histogram aggregation.
  5. Implement query admission control: cap in-flight queries at 256 (§4), reject with backpressure beyond that, tying into chronodb-server::query_api.rs.

19.3 Deliverable

A working range-query API: given a selector and time range, return correctly merged, time-ordered samples or a requested aggregation, sourced transparently from head + OOO staging + persisted blocks.

19.4 Acceptance Criteria

  • query_range.golden fixture: 50 queries against a fixed 10,000-series/24-hour synthetic dataset return byte-identical results across two independent executor implementations (differential test).
  • Query p50 (1h range, 1 series) ≤ 5 ms; p99 (24h range, 1,000 series) ≤ 300 ms (§4 ceilings), measured via bench/query_bench.rs.
  • rate() over an injected counter-reset fixture (5 resets in 1,000 samples) returns the Prometheus-convention-correct non-negative rate at every reset boundary.

19.5 Conformance Fixtures

query_range.golden — the 50-query differential fixture above, covering plain range, rate(), quantile(0.95), and one histogram-bucket query.

19.6 Pitfalls

  • Decoding entire chunks before applying the time-range filter — wastes CPU on samples outside the query window; seek to the nearest chunk boundary first (P9).
  • Computing rate() naively as (last-first)/duration without counter-reset detection — produces wildly wrong (negative or huge) rates across a reset boundary.

19.7 Performance Concerns

Query latency (M2/M3) is bounded by index selectivity, not block size (MM8) — benchmark specifically with a low-selectivity selector (matches 1 of 1,000,000 series) vs. a high-selectivity one (matches all) to confirm the planner's cost model reflects this.

19.8 Edge Cases

  • A query range that touches zero blocks (entirely inside a retention gap) — must return an empty result, not an error.
  • A selector matching zero series — must short-circuit before any chunk I/O.

19.9 Failure Analysis

A query touching a block quarantined by I10 (Phase 5) must degrade gracefully: return partial results with an explicit "block unavailable" annotation, never silently omit the block's contribution without telemetry (ties to T3/T11's DoS and side-channel threats — an error message must not itself leak cardinality information).

19.10 Operational Notes

Expose query_latency_seconds histogram (by range-width bucket) and query_blocks_touched (§24, feeds §29's scalability analysis directly).

20. Phase 8 — Downsampling, Retention & Cardinality Control

20.1 Objectives

Implement chronodb-rollup (ADR-23, I9) and close the cardinality-guard loop deferred since Phase 1/3 (I11, ADR-14), plus retention/TTL enforcement (ADR-16, I7, P14).

20.2 Detailed Implementation Steps

  1. Implement cardinality_guard.rs: consult the per-shard series-count gauge (Phase 1) at registration time; reject new series once the shard exceeds the configured ceiling (I11), applying P4/P13 directly — this closes PhaseDeferred("§13") and PhaseDeferred("§15").
  2. Implement tiers.rs's fixed rollup tiers (5m/1h/1d, ADR-23) and job.rs's downsample job: read a source block's chunks, aggregate into rollup buckets, verify I9 (rollup count == raw count) before sealing the rollup block.
  3. Implement retention.rs's janitor (P14): mark blocks past their tier's retention window as tombstoned immediately, physically reclaim only after the grace period (I7), enforcing ADR-16's block-level drop.
  4. Wire rollup-aware query routing into plan.rs (Phase 7): a query whose range exceeds the raw-tier retention transparently selects the appropriate rollup tier.
  5. Add per-tenant cardinality accounting (ADR-21) so one tenant's guard rejection is independent of another's headroom.

20.3 Deliverable

Full lifecycle closure: cardinality is bounded at ingestion, historical data is downsampled into cheaper tiers on schedule, and expired data is reclaimed without blocking any foreground path.

20.4 Acceptance Criteria

  • downsample_5m.golden fixture: a 100,000-sample raw-tier source produces a 5m-rollup whose per-bucket count matches the raw count exactly (I9) for all 1,200 buckets.
  • Cardinality guard rejects the 100,001st distinct series in a shard configured with a 100,000 ceiling, in 100/100 trials, with cardinality_rejected_total incrementing exactly once per rejection (I11).
  • Retention janitor reclaims 95%+ of eligible expired-block bytes within 1 compaction cycle after the grace period elapses (§4), measured on a 30-day synthetic dataset.

20.5 Conformance Fixtures

downsample_5m.golden — the 100,000-sample/1,200-bucket fixture above.

20.6 Pitfalls

  • Computing rollup aggregates from the rollup tier instead of the raw tier when both exist — compounds precision loss silently, violating P10's "explicit, never silent" rule.
  • Enforcing the cardinality guard globally instead of per-shard/per-tenant (ADR-21) — one noisy tenant exhausts headroom for every other tenant on the node.

20.7 Performance Concerns

Downsample job duration (M9) must not compete with live compaction (P7) for I/O bandwidth; schedule rollup jobs through the same token-bucket throttle as compactor.rs (Phase 5), not a separate unbounded scheduler.

20.8 Edge Cases

  • A rollup bucket with zero raw samples (a genuine gap, not a rejection) — must be represented as "no data," never coerced to zero, or every downstream rate() query over that range is wrong.
  • Retention grace period expiring mid-compaction of the affected block — the janitor must wait for the in-progress compaction to finish before reclaiming (never race I6).

20.9 Failure Analysis

FM-9 (downsample rollup job crash mid-aggregation) and FM-10 (retention janitor bug deleting a live block) are both closed here: FM-9's recovery is to discard the partial rollup output and re-run from the untouched raw source (idempotent, like WAL replay, P12); FM-10's detection is the janitor cross-checking a block's tombstone timestamp against I7 before every physical delete, never trusting a cached "expired" flag alone.

20.10 Operational Notes

Expose cardinality_rejected_total{shard,tenant}, rollup_job_duration_seconds{tier}, and retention_reclaimed_bytes_total (§24); these three, read together, are the operator's primary capacity-planning dashboard (§32).

21. Phase 9 — Operational Hardening & Remote-Write HA

21.1 Objectives

Add production-readiness: WAL-shipping replication (ADR-19), backup/restore (ADR-22), multi-tenant isolation hardening (ADR-21), remote-write ingestion (ADR-17), and a full disaster-recovery drill meeting the §4 RTO.

21.2 Detailed Implementation Steps

  1. Implement WAL-shipping to a read replica (ADR-19): the replica runs replay.rs (Phase 4) continuously against a streamed copy of the primary's WAL segments, applying I14's idempotent-replay guarantee to a remote consumer.
  2. Implement ingest.rs's Prometheus-remote-write-compatible endpoint (ADR-17, protobuf+Snappy), including duplicate-send idempotency (ties to FM-6/§18).
  3. Implement block-level snapshot backup/restore (ADR-22): copy immutable block directories (P11's self-describing property makes this a pure filesystem copy) plus the current WAL tail.
  4. Harden multi-tenancy (ADR-21): verify shard-per-tenant isolation under a chaos test injecting one tenant's cardinality spike and confirming zero headroom impact on others (extends Phase 8's per-tenant accounting).
  5. Run and document the disaster-recovery drill: kill the primary, promote the replica, measure end-to-end RTO against the §4 ceiling (≤ 60 s at 2 GiB head + 1 GiB WAL).

21.3 Deliverable

A deployable, replicated, backed-up ChronoDB node accepting Prometheus-remote-write traffic, with a documented, measured disaster-recovery procedure.

21.4 Acceptance Criteria

  • A promoted replica serves queries within the §4 RTO ceiling (≤ 60 s) in 10/10 drill trials at the specified head/WAL sizes.
  • Remote-write duplicate-send fixture (1,000 samples sent twice) results in exactly 1,000 stored samples, not 2,000 (idempotency, I9-adjacent).
  • Backup restore of a 10 GiB block set completes and passes full checksum validation (I10) in ≤ 5 minutes on reference hardware (M11 target).
  • Chaos test: one tenant's 10× cardinality spike causes zero measurable ingest-latency change for a second, isolated tenant (ADR-21 verification).

21.5 Conformance Fixtures

remote_write_dedup.json — the 1,000-sample duplicate-send fixture above. dr_drill.log — the 10-trial promoted-replica RTO measurement log.

21.6 Pitfalls

  • Shipping WAL segments without also shipping checkpoint records — a promoted replica replays from the wrong starting offset and either double-applies or misses records.
  • Backing up while a compaction is mid-merge — snapshot a consistent point (post I13's atomic swap) or the backup can contain a block whose manifest doesn't match its chunks yet.

21.7 Performance Concerns

WAL-shipping bandwidth (ADR-19) must stay below the replica's own disk-write bandwidth or the replica falls permanently behind; measure steady-state replication lag under M1's sustained ingestion target and confirm it stays bounded, not growing.

21.8 Edge Cases

  • Replica promoted mid-replay (primary died while replica was still catching up) — the new primary must finish its own local replay (I14) before accepting new writes, never serve from a partially-replayed state.
  • Backup taken during an active cardinality-guard rejection storm — must still complete; a rejection storm is a foreground-path event, not a backup-path blocker (P7-adjacent).

21.9 Failure Analysis

FM-6 (network partition losing acks) recurs here at the replication layer: a partitioned replica must resume WAL-shipping from its last confirmed offset on reconnect, never re-request "everything" (bandwidth blowup) nor silently gap (I14 violation via missing records).

21.10 Operational Notes

Document the full DR runbook (§24): promotion command, RTO/RPO expectations (§4), post-promotion validation checklist (checksum sweep per I10, series-count cross-check per I3). This is the capstone operational artifact for the whole project.

Metrics (Prometheus-exposition-compatible, per §5 OpenMetrics spec): all counters named in §7/§22/§23's tables, plus ingest_samples_total, query_requests_total, block_count{tier}, wal_segment_count. Tracing: one span per ingest request and per query, tagged with tenant/shard, exported via OpenTelemetry-compatible interface. Structured logging: JSON lines, one event per state transition in §8.4 and every row in §22/§23's Detection column.

Dashboards: (1) ingestion — throughput, p50/p95/p99 ack latency, rejection rate by reason (I11/I12); (2) storage — head size, block count per tier, compaction backlog (FM-3), disk usage vs. retention projection; (3) query — latency by range-width bucket, blocks-touched distribution, quarantined-block count (I10); (4) DR — replication lag (§21), last successful backup timestamp, last DR-drill RTO.

SLOs: ingest ack p99 ≤ 20 ms (M4) 99.9% of 5-minute windows; query p99 ≤ 300 ms (M3) 99% of 5-minute windows; availability ≥ 99.9% monthly (excludes planned maintenance).

Runbooks: one per FM-# row (§23) plus the DR drill procedure (§21.10). Each runbook: symptom → detection query → decision tree → recovery command → verification step.

Backup/restore: nightly block-level snapshot (ADR-22) + continuous WAL tail shipping (ADR-19); restore procedure verified quarterly against the M11 duration target.

Deployment topology: single primary + N WAL-shipped read replicas (ADR-19) per tenant-isolated shard group (ADR-21); replicas serve read-only query traffic, primary serves ingestion + read/write query traffic.

Canary/rollback: new binary versions deploy to one replica first, validated against the query-differential fixture (query_range.golden, §19.5) before promotion to primary; rollback is a binary swap plus WAL replay (I14 guarantees state consistency across versions per §25's compatibility rules).

Migration: schema/encoding-version bumps (§25) roll out block-by-block — old and new encoding versions coexist in the same deployment until the oldest block ages out naturally via retention (ADR-16), never a stop-the-world migration.

25. Compatibility & Versioning

Wire compatibility: the remote-write protocol (ADR-17) follows the Prometheus Remote Write Specification's own versioning (1.0/2.0, §5); ChronoDB's ingestion front- end negotiates version at connection setup and rejects unsupported versions explicitly.

Storage/schema evolution: BlockMeta.encoding_version (§11) is checked on block open; a reader must refuse to open a block with a newer major encoding version than it understands (fail closed, ties to I10) but must transparently read any older minor version it still supports.

API stability: chronodb-query's selector grammar (§8.1-adjacent) follows SemVer at the crate level; a breaking selector-grammar change bumps the major version and is announced one minor version ahead via a deprecation warning in query responses.

Deprecation policy: a deprecated feature (e.g. an ADR-23 rollup tier being retired) is supported for at least 2 minor releases with a warning telemetry event (deprecated_feature_used_total{feature}) before removal.

Rolling-upgrade guarantees: a primary and its read replicas (ADR-19) may run adjacent minor versions during a rolling upgrade; the WAL record format (§8.3) is additive-only across minor versions (new WalRecord variants are appended, never renumbered) so an older replica can skip-and-warn on an unrecognized variant rather than crash.

Compaction-format compatibility: compactor.rs (Phase 5) must be able to read every still-in-retention encoding version as an input, even while writing only the current version as output — this is how encoding upgrades propagate without a stop-the-world rewrite (ties to §24's migration note).

26. Testing & Verification Strategy

Unit tests: one module per crate file in §10, covering every signature in §11; codec unit tests assert exact bit-layout per §8.2's worked example.

Integration tests: full ingest→WAL→head→flush→block→query round trips per phase, using the fixtures named in each phase's N.5 (§12.5 through §21.5).

Property tests: I2 (monotonic ts within a chunk), I6 (compaction sample-count conservation), I9 (rollup count conservation), and I14 (replay idempotency) are each property-tested with randomized inputs (≥10,000 cases per property per CI run).

Differential tests: query_range.golden (§19.5) runs two independent executor code paths (naive full-scan vs. index-pushdown) and asserts identical results — this is the primary defense against ADR-13's aggregation-pushdown introducing subtle bugs.

Fuzzing: chunk.rs's decoder and segment.rs's WAL reader are both continuously fuzzed (structure-aware, seeded from the golden fixtures) to harden against T4/T9/FM-1/ FM-11's corruption and malicious-input classes.

Chaos testing: kill-9 at random points during ingest/flush/compaction (extends §16.4's crash-point fixture to random injection); network-partition injection for the replication path (§21.9's FM-6 scenario); disk-full injection for FM-4.

Deterministic replay: every WAL fixture (§16.5, §21.5) is replayed with a fixed seed and asserted byte-identical (I14) — this is the project's single most important regression gate, run on every commit.

Soak testing: a 72-hour continuous ingest+query+compact+rollup+retention cycle at the M1 throughput target, watching for slow memory/disk leaks not visible in short runs.

Conformance suite: conformance/runner/ executes every named fixture (§12.5 through §21.5) as a single gated CI job; any fixture regression blocks merge.

Perf-regression gating: every M# target (§28) is measured on every release candidate; a regression beyond 10% of the target blocks release without an explicit waiver.

27. Build & Release Engineering

Reproducible builds: pinned rust-toolchain.toml (§10), Cargo.lock committed, CI builds from a clean container image with no network access mid-build (all dependencies vendored/cached).

Signing: release binaries signed with a project release key; signatures published alongside SHA-256 checksums of every artifact.

SBOM: generated per release via cargo-cyclonedx (or equivalent), covering every crate dependency including the codec's bitstream library (ADR-24's chosen approach).

Release channels: stable (tagged releases, full conformance + soak gate), nightly (main-branch builds, conformance gate only, no soak requirement).

CI/CD topology: PR gate (build + unit + integration + conformance) → main-branch gate (adds fuzzing + property tests) → release-candidate gate (adds soak + perf- regression + chaos) → tagged release (adds signing + SBOM).

Version stamping: every binary embeds its git commit hash, build timestamp, and the encoding_version (§25) it writes by default, queryable via the CLI's inspect subcommand.

Provenance: release artifacts carry SLSA-style provenance attestation linking the binary to its exact source commit and build environment.

Dependency auditing: cargo audit runs on every CI build (T9's mitigation); a new critical advisory blocks merge until triaged.

29. Scalability Analysis

Constant regardless of scale: per-sample codec cost (§14, O(1) amortized bit-writes per sample); WAL record framing cost (§16, O(1) per record); block-manifest checksum verify cost (§17, O(1) per block-open, not per sample).

Grows with scale (Big-O): label-index memory — O(distinct label-value pairs) (P4, §13); query latency for a low-selectivity selector — O(matched series × chunks touched) (§19, MM8); compaction write-amplification — O(levels × block size) (O'Neil et al. 1996, §17.7); WAL replay time — O(unflushed WAL bytes since last checkpoint) (§16, M10).

Named bottlenecks in order of first onset: (1) per-shard append lock contention (P8, §15.7) at moderate core counts; (2) label-index memory (P4) at high cardinality, mitigated by I11's guard; (3) compaction I/O bandwidth (P7, M8) at sustained high ingestion; (4) query executor CPU (ADR-12) at high concurrent-query volume (§4's 256 cap).

Horizontal scaling: shard-per-tenant (ADR-21) is the primary horizontal-scaling axis — add nodes, assign new tenants/shards, no cross-shard coordination required for ingestion or single-tenant queries. Cross-shard queries (not supported in this design, PhaseDeferred("§35") for a future federation layer) would require a scatter-gather layer above chronodb-query.

Vertical scaling: more cores primarily help compaction (M8) and concurrent query throughput (§4's 256-query cap scales with core count); more RAM raises the head-block ceiling (§4) and thus the practical per-node series-count ceiling (§32).

Practical ceiling and levers beyond it: a single node's practical ceiling is ~5,000,000 active series (§4) bounded by head-block memory (M7); beyond that, the lever is horizontal sharding (ADR-21), not vertical scaling, since label-index memory (P4) grows faster than any single node's RAM budget once cardinality is legitimately that high (e.g. multi-tenant SaaS metrics ingestion).

30. Mental Models & First Principles

MM1 — "A time series is a compressible column, not a row." Predicts: columnar, per-field codecs (P3) beat row-oriented generic compression. Bug class without it: naive row storage bloats disk 8-12× past the M5 target. Resolving: §14.

MM2 — "Cardinality is a multiplicative, not additive, cost." Predicts: two independent 1,000-value labels on one metric create 1,000,000 series, not 2,000. Bug class without it: unbounded label values (e.g. raw request IDs) silently exhaust memory. Resolving: §13 / §20.

MM3 — "The WAL is the source of truth; the head block is a cache of it." Predicts: any head-block state must be reconstructible purely from the WAL (I14). Bug class without it: recovery logic that "patches up" the head instead of fully replaying loses data silently on edge-case crashes. Resolving: §16.

MM4 — "Out-of-order is the norm at the edge, ordered is the norm at the core." Predicts: the ingestion boundary needs OOO tolerance (P6) but persisted chunks never do. Bug class without it: treating any OOO sample as an ingestion error drops legitimate multi-producer/backfill traffic. Resolving: §18.

MM5 — "Compaction trades write amplification now for read amplification later — or the reverse if skipped." Predicts: skipping compaction keeps write cost low but query cost (blocks touched, §29) grows unbounded with time. Bug class without it: operators disable compaction "to save I/O" and silently degrade every future query. Resolving: §17 / §29.

MM6 — "A block's meta.json is a contract, not a hint." Predicts: any consumer (query, backup, replica) can trust a block's self-description without cross-checking external state (P11). Bug class without it: a query engine that trusts stale external metadata instead of the block's own manifest serves wrong data after a partial migration. Resolving: §17 / I10.

MM7 — "Downsampling is a lossy compiler pass over history." Predicts: every rollup tier has a documented, queryable precision loss (P10), just like a compiler optimization level. Bug class without it: an operator can't distinguish "the metric really spiked" from "the rollup smoothed it out." Resolving: §20.

MM8 — "Query latency is bounded by index selectivity, not raw data volume." Predicts: a highly selective query on a huge dataset is fast; a poorly selective query on a small dataset can still be slow if it touches every block. Bug class without it: a query planner that estimates cost from data size alone mis-prioritizes optimization effort. Resolving: §19 / §29.

32. Back-of-Envelope Capacity Model

  1. Raw bytes/sample = sizeof(ts:i64) + sizeof(value:f64) = 8 + 8 = 16 B/sample (excludes series-id, amortized via chunking) — baseline for M5.
  2. Gorilla-compressed bytes/sample ≈ 1.37 B/sample (Pelkonen et al. 2015's reported production figure, §5) → compression ratio = 16 / 1.37 ≈ 11.7×, clearing the M5 floor of 8×.
  3. Disk/day for N series at 15s scrape interval = N × (86400/15) × 1.37 B = N × 5760 × 1.37 B ≈ N × 7,891 B/day. At the §4 ceiling N = 5,000,000: ≈ 5,000,000 × 7,891 B ≈ 39.5 GB/day raw-tier.
  4. Disk for 15-day raw retention (§4) = 39.5 GB/day × 15 ≈ 592 GB raw-tier steady state, before accounting for compaction's transient write-amplification overhead (§29).
  5. Memory per active series (head) — from M7's ≤ 400 B target: at N = 5,000,000, head-block memory ≈ 5,000,000 × 400 B ≈ 2 GB, exactly matching the §4 head ceiling — confirming the 5,000,000-series ceiling is memory-derived, not arbitrary.
  6. WAL write throughput required = ingestion rate × avg WAL record size. At M1's 400,000 samples/sec and an estimated 24 B/record (ts+value+overhead before framing): 400,000 × 24 B ≈ 9.6 MB/s sustained WAL write bandwidth — well within NVMe sequential-write capability, confirming M4's fsync-latency target is achievable.
  7. (cont'd numbering continues below as distinct derived quantities)
  8. Chunks per 2-hour block (ADR-05's ~120 samples/chunk, 15s interval): a 2-hour block holds 7200/15 = 480 samples/series → 480/120 = 4 chunks/series/block.
  9. Postings-list size for one label value at 100,000-series cardinality (ADR-08, sorted delta-varint, ~1.5 B/entry average after delta-encoding at this density): 100,000 × 1.5 B ≈ 150 KB per label-value postings list — confirms M6's ≤1ms lookup target is achievable (single sequential scan of a 150 KB buffer).
  10. Compaction I/O amplification factor (O'Neil et al. 1996's leveling cost, ADR-09's 2h→2d→2w scheme, 3 levels): each level rewrites its full input once → amplification ≈ 3× total bytes written vs. raw ingestion bytes, informing M8's throughput floor (must exceed 3× ingestion rate to avoid FM-3's backlog).
  11. Downsample storage reduction (5m tier vs. raw 15s): bucket ratio = 300s/15s = 20× fewer samples/series in the 5m tier → 5m-tier disk cost ≈ raw-tier / 20 ≈ 2 GB/day at the same N = 5,000,000, justifying the long-tail retention economics of ADR-23's tiering.
  12. Query fan-out for a 24-hour range query (§4's block duration = 2h raw): 24h / 2h = 12 raw blocks touched minimum per matched series, before any rollup- tier substitution — this is the concrete number MM8 and §19.7's benchmark target against.

33. Hard Questions (Self-Examination)

  1. If compaction (§17) falls permanently behind ingestion (FM-3), what is the exact sequence of degraded states the system passes through before it becomes unavailable, and which invariant (§7) is the first to come under pressure?
  2. Why does I11's cardinality guard (§20) have to live at ingestion time rather than at query time, given that §19's query planner already has a natural chokepoint at the label index (§13)?
  3. Walk through what happens to I14's replay-idempotency guarantee (§16) if a checkpoint record (§8.3) is itself corrupted — does §16.8's edge-case handling still hold, or does it silently regress to a full-history replay?
  4. ADR-15's dedicated OOO staging buffer (§18) exists specifically to avoid contending with the live append path (P8). Under what ingestion pattern does this design still fail to protect live-path latency, and which M# target (§28) would first reveal it?
  5. §32's capacity model derives the 5,000,000-series ceiling from head-block memory (M7). If ADR-20's mmap strategy for persistent blocks were replaced with full heap loading, which other §4 constraint would become the binding one instead?
  6. Compare how ADR-09's compaction leveling and Druid's real-time/historical split (§31) each solve the same underlying problem (bounding read amplification over time) — why does this design reject Druid's approach given §29's scalability analysis?
  7. I6 requires compaction output to preserve sample count exactly. Describe a compaction bug that would violate I6 without ever triggering I10's checksum detection — what additional invariant or fixture (§26) would be needed to catch it?
  8. §21's WAL-shipping replication (ADR-19) relies on I14 holding on the replica side. What specific WAL record ordering guarantee, if violated during shipping, breaks I14 on the replica without breaking it on the primary?
  9. P10 requires downsampling to be "explicit, never silent." Trace exactly how a query in §19 that spans both raw and rollup tiers surfaces this explicitness to the caller — what happens if it doesn't (which MM applies)?
  10. §20's per-tenant cardinality accounting (ADR-21) is meant to isolate tenants. Under what shard-assignment failure would two tenants share cardinality headroom despite ADR-21's design intent, and how would §22's threat model (T5) classify that failure?
  11. Why is retention (§20, ADR-16) enforced at block granularity rather than sample granularity, and what would have to change in §8.5's block layout for sample-level retention to become tractable without violating P2?
  12. §28's M8 compaction-throughput target and §32's derived 3× I/O-amplification factor together imply a minimum disk bandwidth. If NVMe bandwidth were halved (cheaper storage tier), which two other constraints in §4 would need to relax in tandem?
  13. Contrast ADR-03's delta-of-delta timestamp encoding with a hypothetical fixed-interval-only encoding (rejected alternative) — under exactly what real-world ingestion condition (name it) does the fixed encoding's simplicity outweigh its fragility, per ADR-03's sixth column?
  14. §18's backfill path bypasses the live ingest path entirely. Explain why this design choice is safe with respect to I2 (monotonic timestamps) but could still violate I6 if the backfill's target block is mid-compaction — what serializes the two?
  15. §24's canary/rollback procedure validates a new binary against query_range.golden (§19.5) before promotion. What class of regression would this fixture fail to catch, and which other §26 verification technique would be needed to close that gap?
  16. Given §29's named bottleneck ordering (append-lock contention first, then index memory, then compaction I/O, then query CPU), what operational signal would tell you which bottleneck you have hit without needing to read source code?
  17. §31 shows TimescaleDB inheriting Postgres's own WAL underneath ChronoDB's-style chunking. Why does that combination not simply get "the best of both" — what concrete cost does the redundant durability layer impose that this design avoids?
  18. If the OOO acceptance window (§4, ADR-15) were widened from 1 hour to 24 hours, which M# target would degrade first, and which invariant would have to be re-examined for correctness at the new window size?
  19. §30's MM6 says a block's manifest is "a contract, not a hint." Identify a place in §21's backup/restore procedure where violating MM6 (trusting external metadata instead of the manifest) would produce a subtly wrong restore that still passes I10.
  20. Explain, using §32's derived numbers, why the 5m-downsample tier's 20× storage reduction (item 10) does not simply mean "20× less useful data" — what is preserved and what is genuinely lost, and where in §8/§20 is that distinction made explicit?

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Pure LSM keyed by (SeriesId, Timestamp)

   writes ──▶ [ MemTable ] ──flush──▶ [ SSTable L0 ] ──compact──▶ [ SSTable L1 ] ──▶ ...
                                        key = (SeriesId, ts), value = sample bytes

Regime where it wins: mixed OLTP + time-series workload needing arbitrary point updates/deletes by exact key, not just time-range scans. Real system embodying it: KairosDB (built on Apache Cassandra, itself an LSM store). Why rejected: general LSM key-value semantics don't exploit the Gorilla-style columnar regularity (P3) that this design's compression ratio (M5) depends on — a generic SSTable format compresses row-wise, losing most of delta-of-delta/XOR's benefit.

Alternative 2 — General RDBMS with time-partitioned tables

   INSERT ──▶ [ Postgres WAL ] ──▶ [ Heap chunk_2024_06 ] [ Heap chunk_2024_07 ] ...
                                        (hypertable chunking, TimescaleDB-style)

Regime where it wins: need full SQL joins/transactions against time-series data alongside relational data in the same engine. Real system embodying it: TimescaleDB. Why rejected: inherits Postgres's own MVCC/WAL underneath a second, ChronoDB-style durability layer — doubles the write-amplification and complicates the crash-recovery story (§17.7, §33 Q17) that this design keeps single-layered (ADR-01).

Alternative 3 — Segment-based columnar OLAP, real-time/historical split

   ingest ──▶ [ Real-time node buffer ] ──handoff──▶ [ Historical node segment ]
                     (queried live)                    (queried via broker, §31)

Regime where it wins: ad-hoc slice-and-dice OLAP over many high-cardinality dimensions, not just time-range scans with a small fixed query surface. Real system embodying it: Druid (Yang et al. 2014). Why rejected: requires distinct node types and external coordination (historically Zookeeper) — operational complexity this single-binary, single-node-scoped design (§1) deliberately avoids.

Alternative 4 — Wide-column store with tag-embedded row keys

   row key = metric:tag1=v1,tag2=v2:ts_bucket ──▶ [ HBase region ]

Regime where it wins: already operating a wide-column/Bigtable-like store at scale for other workloads, and can amortize its operational cost across this one too. Real system embodying it: OpenTSDB (on HBase). Why rejected: tag cardinality becomes part of the storage key directly, so unbounded tag values cause region hot-spotting at the storage layer itself, not just a memory problem — this design deliberately keeps cardinality a guarded, ingestion-time-controlled cost (P4, ADR-14) rather than a storage-layout one.

36. Glossary

Backfill — bulk historical-data load bypassing the live ingest path (§18). Bit-packing — encoding values at sub-byte granularity via a bitstream (§14, ADR-24). Block — immutable, time-ranged, self-describing persisted unit of storage (§8.5). BlockMeta — a block's manifest record: time range, counts, checksum (§11). Cardinality — count of distinct label-value combinations for a metric (§13, P4). Cardinality guard — ingestion-time limiter rejecting series past a ceiling (§20). Checkpoint — a WAL record marking a durable head-state boundary, bounding replay. Chunk — a per-series, codec-encoded byte buffer covering a bounded sample range. Compaction — merging smaller blocks into larger, coarser-grained ones (§17). CRC — cyclic redundancy check, used here as CRC32C for corruption detection (I4). Delta-of-delta — encoding the second difference of successive timestamps (§14). Downsampling — producing a lower-resolution rollup tier from raw samples (§20, P10). fsync — the syscall forcing durable disk write before an operation is acknowledged. Gorilla codec — the delta-of-delta + XOR encoding scheme from Pelkonen et al. 2015. Grace period — the delay between tombstoning and physical reclaim (I7, P14). Head block — the single mutable, in-memory, actively-appended structure (P1). Histogram bucket — a fixed value-range bin used for distribution aggregation. Idempotent replay — replaying a log twice produces the same state as once (P12). Ingestion — the path by which external samples enter the system (§8.1, §15). Inverted index — label-value → series-id-list index structure (§13, ADR-07). Janitor — the background process reclaiming space after retention expiry (§20). LabelSet — the sorted set of label-name/value pairs identifying a series (§11). Line protocol — a text ingestion grammar for samples (InfluxDB-style, §8.1). Manifest — synonym for a block's meta.json self-description (P11). mmap — memory-mapping a persisted block file for zero-copy read access (ADR-20). Out-of-order (OOO) window — the time span behind head-max-ts still accepted (§4). Percentile / quantile — a statistical aggregation over a value distribution (§19). Postings list — the set of SeriesIds matching one label-value pair (§13). Rate — per-second average delta over a range, counter-reset-aware (§19.2). Retention — the policy window after which data is eligible for deletion (§20). Rollup — synonym for a downsampled aggregate tier (§20, ADR-23). Sample — one (timestamp, value) pair belonging to a series (§11). Scrape interval — the nominal cadence between successive samples of one series. Segment — a bounded, rotatable WAL file unit (§16, ADR-06). SeriesId — the dense integer identifier allocated to a canonical LabelSet (§11). Sharding — partitioning series/tenants across independent append/index units (P8). Snappy — a fast, low-ratio compression codec used for the remote-write wire format. Staging (OOO) — the buffer holding out-of-order samples pending merge (§18). Tenant — an isolated logical namespace of series within a deployment (ADR-21). Tombstone — a marker recording a pending deletion, physically reclaimed later (P14). Token bucket — the rate-limiting mechanism throttling compaction I/O (P7). Tier (rollup) — one fixed downsample resolution (e.g. 5m, 1h, 1d) (ADR-23). ULID — a sortable, unique identifier type used for BlockId (§11). Varint — a variable-length integer encoding used in delta streams and postings (§8). Wal-shipping — streaming WAL segments to a replica for replay-based replication. Write-ahead log (WAL) — the durable, append-only log gating every mutation (P5). Write amplification — extra bytes written by compaction relative to raw ingest (§29). XOR encoding — Gorilla's float encoding exploiting bitwise similarity (§14, ADR-04).
