In one paragraph

ChronoDB is a single-binary database for numeric samples that arrive stamped with a time and a set of labels (§1, §8.1). It logs every sample to disk before acknowledging it, keeps recent data in one mutable in-memory structure, and turns older data into immutable, compressed, time-bucketed blocks (§1, §3). It answers range and aggregation queries (rate, percentile, histogram) and caps its own memory by rejecting new series past a ceiling (§1, I11). The design targets at least 400,000 samples per second per node and 5,000,000 active series per node (§4). Platform and SRE teams, or engineers embedding a metrics backend in a larger product, run it (§1).

The problem, concretely

Every sample is tiny: a timestamp and a value, 16 bytes raw (§32 item 1). The blueprint's source paper reports about 1.37 bytes per sample once the regularity of the data is exploited (§2, §32 item 2). A generic compressor applied to interleaved rows loses most of that regularity (P3). So the first problem is storage cost, and the fix is a separate codec for each column (P3, MM1).

The second problem is dropping data that ages out. Without time buckets, retention is an O(rows) tombstone sweep; with them, it is an O(blocks) directory drop (P2, ADR-16). That is ADR-01's reason for time-partitioned blocks over a pure LSM tree or a general database table (ADR-01).

The third problem, which the blueprint treats as a first-class threat, is cardinality (§13.10, T1). Every unique label combination is a new series with its own chunk stream, index entries and memory, and the cost multiplies across labels rather than adding (P4). The blueprint's own example: two independent labels with 1,000 values each make 1,000,000 series, not 2,000 (MM2). One label with unbounded values, such as a raw user ID, silently pushes the total series count past the memory ceiling (P4). Early InfluxDB TSM had unbounded cache growth under cardinality spikes (§5 Reference Implementations 2).

The fourth problem is untidy delivery and crashes: samples arrive out of order from many producers (P6), lost acknowledgements make clients resend duplicates (FM-6), and an acknowledged sample must not vanish on a crash (P5). The design answers all four: compress per column, bucket by time, guard cardinality at ingestion, and log before acknowledging.

  1. chronodb-server is the trust and process boundary. ingest.rs accepts samples written in the §8.1 grammar (a metric name, optional labels, a value, a millisecond timestamp), and cardinality_guard.rs rejects a new series if its shard is past the ceiling (§3, §8.1, I11).
  2. chronodb-index (labelindex.rs, postings.rs, seriesid.rs) gives each distinct label set a SeriesId, and records the id in a list for every label=value pair it carries. An unseen label set is registered here first (§13.2, §15.2, ADR-07).
  3. chronodb-wal (segment.rs) appends a length-prefixed, CRC-checked record and calls fsync before anything else happens. No sample is acknowledged or visible before then (§3, §8.3, P5, I5).
  4. chronodb-storage / head.rs is the only mutable structure in the system. It owns one in-progress chunk buffer per series, written through the codec (§3, §15.1, §15.2, P1).
  5. When the head reaches a time boundary it is flushed to block.rs by an atomic swap. A block is a directory holding meta.json, index and chunks, never edited afterwards (§8.4, §8.5, I10, I13).
  6. compactor.rs merges small blocks into larger time ranges in the background, and retention.rs drops whole blocks when they age out (§3, ADR-09, ADR-16).
  7. chronodb-query (plan.rs, exec.rs) asks the index which series match, then reads chunks only for those series from the head, the out-of-order buffer and the blocks (§19.2, P9).
  8. chronodb-rollup reads persisted blocks only and writes coarser rollup blocks, so it never touches the mutable head (§3, P10).
  9. chronodb-codec knows nothing about blocks, the log or the index. It turns samples into bytes and back, which is why it can be tested alone (§3).

The core ideas

Two codecs: timestamps by second difference, values by XOR (§8.2, §14, ADR-03, ADR-04)

Scrapes arrive at near-regular intervals, so the gap between timestamps barely changes. Store the first timestamp whole, the first gap, and after that only the change in the gap (delta-of-delta). A regular interval then costs one bit (§8.2, §2). Values that move slowly share most of their bits with the previous value. Store the XOR with the previous value (XOR encoding); an identical value is the single bit 0 (§8.2). The blueprint's worked 5-sample example, 15-second interval, one late sample:

i ts (ms) gap change in gap timestamp bits written value value bits written
0 1000000 none none 64 (absolute) 10.0 64 (absolute)
1 1015000 15000 none varint(15000) 10.0 0 (identical)
2 1030000 15000 0 0 (1 bit, same gap) 10.1 control + meaningful-XOR bits
3 1045200 15200 200 control + varint(200) 10.1 0
4 1060000 14800 -400 control + varint(-400) 9.9 control + meaningful-XOR bits

(§8.2.) Chunks wrap both streams with a header (magic, encoding byte, sample count, first timestamp, first value) and a CRC32C trailer (§8.2, ADR-11). A chunk whose declared sample count disagrees with what decoding finds is rejected with ChunkError::LengthMismatch, never partially returned (§8.2). Timestamps within one series must be strictly increasing, or the codec's assumption breaks (I2). The bit-level reader and writer are written from scratch so the exact layout can be tested against fixtures (ADR-24, §14.2). The target is at least 8x smaller than raw 16-byte samples, with about 1.37 B/sample as the reported figure (§4, §14.4). On NaN values the blueprint contradicts itself: §12.5 says ChronoError must reject NaN, and in the same sentence that a NaN value is legal and must round-trip bit-exact; §14.4's fixture includes a NaN that must decode byte-identical (§12.5, §14.4).

Log first, apply second, replay safely (§8.3, §16, P5, P12, MM3)

Treat the write-ahead log as the truth and the head as a cache of it (MM3). A record is len (4 bytes), type (1 byte: Series, Samples, Tombstone or Checkpoint), the body, and a CRC32C over type plus body (§8.3, I4). Segments rotate at 128 MiB (§4). Every append goes: write to the log, fsync, then apply to the head (§16.2, P5). Acknowledgement latency is therefore bounded below by fsync latency, and batching fsyncs is the main throughput lever (P5, §16.6).

A checkpoint record says "the head's state up to here is durably reflected", so on startup replay begins at the last checkpoint, not at the start of history (§16.2). Replay is idempotent: replaying a segment twice gives the same head as replaying it once, which needs each record to carry enough identity to detect a repeat (P12, I14). If a CRC fails, the segment is truncated at the last good record and the lost bytes are counted, never hidden (I4, §16.2, §16.9). If the process dies after the fsync but before the head update, replay applies the record: identical state, no loss, no duplication (§8.2 failure-path example, §16.8).

Head, blocks, compaction and retention (§8.4, §8.5, §17, ADR-09, P1, P2, P14)

Mutation lives only in head.rs; everything reachable through block.rs is immutable once its manifest is written (P1). A head moves through states: Empty, Active, Sealing, Persisted, Compacting, Superseded, Reclaimable, then deleted (§8.4). Flushing is a copy-on-write pointer swap, so a query never sees a half-flushed block (I13, §17.2). The meta.json is written last, after chunks and index are on disk, so a crash cannot leave a manifest that describes data which does not exist (§17.2, §17.6, P11).

Compaction merges blocks by fixed time range: 2 hours, then 2 days, then 2 weeks (ADR-09). The blueprint states block ranges differently elsewhere: §4 gives 2 h raw and "1 d / 30 d" for rollup tiers, citing ADR-09, while ADR-23 sets the rollup tiers at 5m, 1h and 1d (§4, ADR-23). After every merge the compactor checks that outputs are disjoint, contiguous and lose no samples (I6). It is throttled by a token bucket so it can never starve ingestion (§17.2, P7). Compaction rewrites bytes at each level, so write amplification is the dominant disk cost (§17.7); the capacity model estimates about 3x (§32 item 9). Retention marks expired blocks as tombstoned at once and physically reclaims them only after a grace period, to avoid racing readers (P14, I7, §20.2). The blueprint never states how long that grace period is: P14 and §20.4 point to §4 for it, and §4 has no such row (P14, §20.4, §4).

Cardinality is a product, so guard it at the door (P4, MM2, I11, ADR-14)

The guard sits in cardinality_guard.rs and runs when a new series is registered. If the shard is past its configured ceiling, the series is rejected with CardinalityExceeded and counted in cardinality_rejected_total; the client is expected to back off or the operator to raise the ceiling (§11, §20.2, I11, T1). The blueprint says the guard must be at ingestion, not query time (P4), so that the memory ceiling is never threatened (ADR-14, P13).

§32 item 5 multiplies M7's 400 B per active series out to about 2 GB at 5,000,000 series and says this matches the §4 head ceiling of 2 GiB, so the series ceiling is memory-derived (§4, M7, §32 item 5). Per-tenant accounting keeps one tenant's rejection independent of another's headroom (§20.2, ADR-21). The guard's scope is not consistent: I11, §20.2 and §20.4 say per shard, while §4 sets a default of 100,000 distinct label combinations per metric name and FM-7's fix is a lower per-metric ceiling (§7, §20.2, §20.4, §4, FM-7). "Shard" means a head append shard owning part of the SeriesId space in P8 and §15.2, but a per-tenant shard in ADR-21.

Out-of-order data: stage it, merge it, never drop it quietly (P6, ADR-15, I12, §18)

Samples may arrive out of timestamp order from many producers, so late samples are normal at the edge, while persisted chunks must always be timestamp-sorted per series (P6, MM4). A sample with a timestamp behind the head's maximum, but inside the 1-hour window, goes to a separate staging buffer instead of the live append path (§18.2, §4). A sample older than the window is rejected with OutOfOrderRejected and counted in ooo_window_rejected_total, never silently dropped (I12, §18.2). Queries merge the head, the staging buffer and the blocks on read; staged samples are later folded into a compaction input (§18.2, P9). The phase test: 5,000 samples with 15% out of order within the window give a query result identical to the fully-sorted input, and 500 too-old samples are rejected with the counter rising by exactly 500 (§18.4). Samples dated in the future are a separate case: FM-5 rejects and counts them at ingest under ADR-18, but no limit for "future" is defined, and I12 covers only old samples (FM-5, ADR-18, I12).

Queries: select the series first, scan chunks second (P9, MM8, §19)

The label index answers "which series", the codec answers "what values", and the planner never mixes the two (P9). A selector (Eq, Neq, Regex matchers) becomes set operations on postings lists, which are sorted lists of series ids stored delta-varint encoded (§11, §19.2, ADR-07, ADR-08). The plan then resolves the time range to the blocks, head and staging buffer that overlap it, and a pull-based iterator chain merges per-series streams in timestamp order (§19.2, ADR-12). rate() must detect counter resets, because computing it as (last minus first) divided by duration gives negative or huge values across a reset (§19.2, §19.6). Latency is bounded by index selectivity, not by data volume (MM8). A 24-hour query touches at least 12 raw 2-hour blocks per matched series (§32 item 11).

The trade-offs — where engineers disagree

Storage engine: time blocks plus a mutable head (ADR-01)

Chosen: time-partitioned immutable blocks with a WAL-backed mutable head, a Prometheus/TSM hybrid; it makes retention O(blocks) rather than O(rows) (§9, P2). Rejected: a pure LSM keyed by (series, timestamp), or a general RDBMS table (§9). When the rejected choice is right: a workload dominated by random point updates and deletes, not append-heavy ordered writes (§9).

Compaction: fixed time-range leveling (ADR-09)

Chosen: 2 hours to 2 days to 2 weeks, because it maps directly onto retention and downsample tiers (§9, P2, P10). Rejected: size-tiered LSM leveling, or no compaction (§9). When the rejected choice is right: a workload with no natural time locality, such as a random-access key-value store (§9). Skipping compaction keeps write cost low but lets the number of blocks touched per query grow without bound over time (MM5).

Where the cardinality limit sits: at ingestion (ADR-14)

Chosen: an ingestion-time hard reject, so the memory ceiling is never threatened (§9, P13, I11). Rejected: sampling or dropping after ingest, or having no limiter (§9). When the rejected choice is right: when the ingestion path cannot afford the latency of a synchronous check (§9). The cost of the chosen path is rejected writes, which upsets naive clients, and legitimate bursts above the ceiling are rejected rather than queued (P4, P13).

Out-of-order handling: separate staging, merge on read (ADR-15)

Chosen: a dedicated staging buffer merged on read, so cold backfill does not contend with the hot append path (§9, P6). Rejected: merging into the single head on write, or rejecting out-of-order data entirely (§9). When the rejected choice is right: when the ingestion topology guarantees strict per-series order, with a single writer and no retries (§9). The price of the chosen path is a second source to union at query time (§18.7).

Retention: drop whole blocks (ADR-16)

Chosen: block-level whole-block drop, with O(blocks) cost (§9, P2). Rejected: a row-level tombstone plus compaction sweep, or no retention (§9). When the rejected choice is right: when retention boundaries do not align with block time ranges, for example per-series TTLs (§9).

Roads not taken (§34, §35)

Pure LSM keyed by (SeriesId, timestamp) (§34 Alternative 1) wins for a mixed OLTP and time-series workload needing arbitrary point updates and deletes by exact key; KairosDB on Cassandra is the cited example. It is rejected because generic SSTables compress row-wise.

A general RDBMS with time-partitioned tables (§34 Alternative 2) wins when you need full SQL joins and transactions against time-series data in one engine; TimescaleDB is the cited example. It is rejected because it carries Postgres's own MVCC and WAL underneath a second durability layer.

Segment-based columnar OLAP with a real-time/historical split (§34 Alternative 3) wins for ad-hoc slice-and-dice analytics over many high-cardinality dimensions; Druid is the example. It is rejected because it needs distinct node types and external coordination, which a single-binary, single-node design avoids (§1).

A wide-column store with tags in the row key (§34 Alternative 4) wins if you already run such a store at scale for other workloads; OpenTSDB on HBase is the example. It is rejected because unbounded tag values then cause storage-level hot-spotting, not just a memory problem.

Deferred, not rejected (§35): a federated cross-shard query layer, a SQL surface, an object-storage cold tier, adaptive downsample tiers and consensus-replicated writes, each with an un-defer trigger, e.g. "multi-node deployment need identified" for federation (§35, §29).

What must never be false

  • I1: every persisted sample's timestamp lies inside its block's [min_ts, max_ts). Noticed by a manifest range check on read; block_range_violation_total (§7).
  • I2: timestamps within one series' chunk stream are strictly increasing. Noticed by an encode-time assertion; nonmonotonic_sample_total, and the sample is routed to the out-of-order path (§7).
  • I3: a SeriesId maps to exactly one canonical LabelSet for a block's lifetime. Noticed by an index consistency check at block seal; seriesid_collision_total (§7).
  • I4: a WAL record's CRC covers exactly that record's bytes. Noticed by CRC mismatch on replay; wal_crc_mismatch_total (§7).
  • I5: no head append is visible before its WAL record is fsynced. Noticed by a code-path assertion plus a fuzz test; unacked_visible_total, which should stay 0 (§7).
  • I6: compaction outputs are disjoint and contiguous, and their sample count is at least the inputs'. Noticed by the post-merge sample-count check; compaction_sample_loss_total (§7).
  • I7: a tombstoned sample is never physically reclaimed before its grace period ends. Noticed by a grace-period timestamp check before reclaim; early_reclaim_blocked_total (§7).
  • I8: the postings list for label=value contains a series id if and only if that series currently has that pair. Noticed by a periodic index-versus-head cross-check; postings_drift_total (§7).
  • I9: a rollup bucket's sample count equals the raw count for that bucket at rollup time. Noticed by comparing against the source block's manifest; rollup_count_mismatch_total (§7).
  • I10: a query never reads a block whose manifest checksum fails. Noticed by checksum verify at mmap-open; block_checksum_fail_total (§7).
  • I11: the cardinality guard hard-rejects a new series once its shard is past the ceiling. Noticed through the reject-rate metric; cardinality_rejected_total (§7).
  • I12: a sample older than the out-of-order window is rejected with an explicit event, never silently dropped. Noticed by the reject counter; ooo_window_rejected_total (§7).
  • I13: a head flush to a persistent block is atomic from the query path's view. Noticed by a pre/post query snapshot test; flush_partial_visibility_total, which should stay 0 (§7).
  • I14: replaying a WAL segment gives a head byte-identical to the pre-crash state at the last fsync. Noticed by a golden-state diff in the conformance suite; replay_state_mismatch_total (§7). A violation is treated as a correctness bug, not an operations incident (§7).

What breaks in production

  • FM-1: WAL segment corruption mid-write. Disk fault, crash mid-fsync or bit rot makes a CRC fail on replay (I4). The system truncates the segment at the last good record automatically; wal_truncated_bytes_total and the segment offset log show the loss window (§23, §16.9).
  • FM-2: head-block OOM under a cardinality spike. The I11 guard is not yet configured or its ceiling is too high; the symptom is a memory alarm or OOM kill. Recovery is process restart plus WAL replay (I14), then a lower ceiling; the head_active_series history is the forensic trail (§23). The blueprint calls this directly reachable in Phase 3, before the guard exists (§15.9).
  • FM-3: compaction backlog. Ingestion outpaces compaction throughput (M8). A growing compaction_backlog_blocks is the signal. There is no automatic recovery; an operator raises the throttle or adds cores (§23, P7).
  • FM-4: disk full during a compaction merge. The merge write fails; the system aborts and keeps the original inputs unchanged, never partially committing (I6, §17.9). An operator frees disk, lowers retention, and retries (§23).
  • FM-7: cardinality explosion degrading queries. The ceiling was too high or one label ran away. The tell is query latency regressing as series count grows. Recovery needs a lower per-metric ceiling; there is no automatic fix (§23).
  • FM-9: rollup job crashes mid-aggregation. Detected as a count mismatch on resume (I9). The partial output is discarded and the job re-runs from the untouched raw source, idempotently, like WAL replay (§23, §20.9, P12).
  • FM-10: the retention janitor deletes a live block. A grace-period check bug or clock error; the I7 assertion rejects the reclaim before it happens. The janitor re-checks the tombstone timestamp against I7 before every physical delete and never trusts a cached "expired" flag (§23, §20.9).
  • FM-11: checksum mismatch on block read. Bit rot or an incomplete write; caught at mmap-open (I10). The block is quarantined and excluded from queries, then restored from a replica or backup (§23, §14.9). Threats a reader should know (§22): T1 a cardinality bomb of unbounded label values, answered by the ingestion-time reject (ADR-14, I11); T2 unauthenticated writes to the remote-write endpoint, answered by requiring mTLS or token auth at the chronodb-server boundary (§22); T3 a query of death, such as a pathological regex or a year-long range, answered by the in-flight cap, a regex complexity bound, and an executor timeout (§22, §19.2); T5 cross-tenant leakage through a spoofed tenant label, answered by shard-per-tenant isolation and server-side label validation (ADR-21); T6 an attacker forcing many tiny blocks to starve ingestion, answered by throttled compaction and a minimum block size floor (§22, P7).

How it compares

  • Prometheus tsdb made the closest choices to ChronoDB (ADR-01, ADR-03, ADR-04): the same head block, WAL and 2 h/2 d blocks lineage, with a Gorilla-derived codec. It wins for single-node pull-based monitoring with no external dependency, at the cost of having no long-term-storage story without an external remote-write sink (§31).
  • InfluxDB (TSM) chose a cache-plus-merge-tree design nearer a classical LSM, with built-in continuous queries for rollups. That fits flexible ad-hoc tag queries, at the cost of more complex compaction than block leveling (§31).
  • TimescaleDB chose to inherit a general-purpose RDBMS: hypertable chunks on PostgreSQL, full SQL, B-tree indexes. That fits teams needing joins against time-series data, at the cost of carrying Postgres's own WAL and MVCC beneath a second, redundant durability layer (§31).
  • Druid chose segment files with a real-time and a historical node split and bitmap indexes on dimensions. That fits ad-hoc analytics over high-cardinality dimensions, at the cost of multiple node types and external coordination that this single-node scope avoids (§31, §34).

If you only remember three things

A time-series database is a compressible column plus a time bucket, not a table of rows: per-column codecs and fixed time-range blocks make both storage and deletion cheap (MM1, P2, P3). The log is the truth and the head is a cache of it, so nothing is acknowledged before fsync and recovery is replaying the log (MM3, P5, I14). Cardinality multiplies, so the design rejects new series at the door rather than after they are in memory (MM2, I11, ADR-14).

Words used here

  • Sample: one (timestamp, value) pair belonging to a series (§36).
  • Series: one stream of samples, identified by a metric name plus a label set (§8.1, §11).
  • Label set: the sorted label-name and label-value pairs that identify a series (§36).
  • Cardinality: the count of distinct label-value combinations for a metric (§36, P4).
  • Head block: the single mutable, in-memory structure that new samples go into (§36, P1).
  • Block: an immutable, time-ranged, self-describing unit of persisted storage (§36, §8.5).
  • Postings list: the set of series ids that match one label-value pair (§36).
  • Write-ahead log (WAL): the durable append-only log that gates every mutation (§36, P5).
  • Compaction: merging smaller blocks into larger, coarser-grained ones (§36, §17).
  • Downsampling / rollup: producing a lower-resolution tier from raw samples (§36, P10).
  • Out-of-order window: how far behind the head's newest timestamp a sample is still accepted (§36, §4).
  • mmap: mapping a block file into memory so the operating system manages residency (§36, ADR-20).
