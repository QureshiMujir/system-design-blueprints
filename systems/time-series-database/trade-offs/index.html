Decisions (§9) · 24 ADRs

ADR-01

Storage engine paradigm

Chosen

Time-partitioned immutable blocks + WAL-backed mutable head (Prometheus/TSM hybrid)

Rejected

Pure LSM keyed by (series,ts); general RDBMS table

When the rejected choice is right

Workload dominated by random point updates/deletes, not append-heavy ordered writes

Why: Time partitioning makes retention O(blocks), not O(rows) (P2)

ADR-02

Implementation language

Chosen

Rust

Rejected

Go; C++; JVM

When the rejected choice is right

Team already has a large mature Go/JVM codebase and no team Rust experience

Why: No GC pause on ingest hot path, safe bit-packed codecs

ADR-03

Timestamp encoding

Chosen

Delta-of-delta (Gorilla)

Rejected

Plain varint delta; fixed-interval-only

When the rejected choice is right

Timestamps are highly irregular event arrivals with no dominant interval

Why: Collapses near-regular intervals to ~0 bits (Pelkonen et al. 2015)

ADR-04

Float encoding

Chosen

XOR (Gorilla)

Rejected

Quantized delta-of-delta; dictionary encoding

When the rejected choice is right

Values are small-range integer counters where simple delta beats XOR

Why: Exploits slowly-varying float bit patterns without lossy quantization

ADR-05

Chunk size target

Chosen

~120 samples/chunk, tunable

Rejected

1,000 samples/chunk; unbounded chunk

When the rejected choice is right

Series has a very low sample rate (≥1/min) over a multi-year retention window

Why: Matches Gorilla's proven 2-hour default at typical scrape cadence

ADR-06

WAL record framing

Chosen

Length-prefixed + CRC32C trailer

Rejected

Protobuf-delimited stream; fixed-size slots

When the rejected choice is right

Payload schema changes frequently and needs protobuf's built-in evolution

Why: Simple to append/replay/truncate at arbitrary offsets (I4)

ADR-07

Label index structure

Chosen

Inverted index (label=value → postings)

Rejected

B-tree on serialized labelset; no index (full scan)

When the rejected choice is right

Series count is small enough (<10k) that full scan is cheap and simpler

Why: Matches the query pattern "find series by label predicate" directly

ADR-08

Postings encoding

Chosen

Sorted delta-varint arrays

Rejected

Roaring bitmaps; plain u32 arrays

When the rejected choice is right

Series-id space is extremely dense and set-operation speed dominates over size

Why: Good compression for the moderate cardinality target (§4) with simple code

ADR-09

Compaction strategy

Chosen

Fixed time-range leveling (2h→2d→2w)

Rejected

Size-tiered LSM leveling; no compaction

When the rejected choice is right

Workload has no natural time locality (e.g. random-access key-value store)

Why: Time-range leveling maps directly onto retention/downsample tiers (P2, P10)

ADR-10

Block file layout

Chosen

Directory-per-block (meta.json+index+chunks)

Rejected

Single-file container format; per-series files

When the rejected choice is right

Filesystem has high per-file overhead (many small blocks on a constrained FS)

Why: Each artifact independently inspectable/checksummable (P11)

ADR-11

Checksum algorithm

Chosen

CRC32C

Rejected

xxHash64; SHA-256

When the rejected choice is right

Cryptographic tamper-resistance is required (untrusted storage backend)

Why: Hardware-accelerated on modern CPUs, sufficient for corruption detection

ADR-12

Query execution model

Chosen

Pull-based iterator chain

Rejected

Vectorized batch execution; row-at-a-time interpreter

When the rejected choice is right

Query volume is high enough that per-call iterator overhead dominates CPU

Why: Simple to reason about, composes with lazy label filtering (P9)

ADR-13

Aggregation pushdown

Chosen

Index-time label pushdown + query-time numeric aggregation

Rejected

Full query-time-only filtering; full index-time materialized views

When the rejected choice is right

Aggregation queries are few, fixed, and known in advance (materialize them)

Why: Balances index cost against flexibility of ad-hoc numeric aggregation

ADR-14

Cardinality limiter placement

Chosen

Ingestion-time hard reject

Rejected

Downstream sampling/drop after ingest; no limiter

When the rejected choice is right

Ingestion path cannot afford the added latency of a synchronous check

Why: Prevents the memory ceiling from ever being threatened (P13, I11)

ADR-15

Out-of-order handling

Chosen

Dedicated OOO staging + merge-on-read

Rejected

Merge-on-write into single head; reject OOO entirely

When the rejected choice is right

Ingestion topology guarantees strict per-series order (single writer, no retries)

Why: Keeps the hot append path uncontended by cold backfill merges (P6)

ADR-16

Retention enforcement

Chosen

Block-level whole-block drop

Rejected

Row-level tombstone + compaction sweep; no retention

When the rejected choice is right

Retention boundaries do not align with block time ranges (per-series TTL)

Why: O(blocks) drop cost, matches time-partitioning (P2)

ADR-17

Remote-write wire protocol

Chosen

Protobuf + Snappy (Prometheus remote-write)

Rejected

JSON; custom binary framing

When the rejected choice is right

Ecosystem is JSON-only tooling with no protobuf codegen available

Why: Existing ecosystem compatibility, compact and fast to (de)serialize

ADR-18

Ingestion clock source

Chosen

Server-assigned monotonic clock, client timestamp accepted within OOO window

Rejected

Trust client wall-clock unconditionally; hybrid logical clock

When the rejected choice is right

All clients are behind a tightly NTP-synced fleet with verified clock skew

Why: Bounds the blast radius of a misconfigured client clock (I12)

ADR-19

Replication model

Chosen

WAL-shipping to read replicas

Rejected

Consensus-replicated writes (Raft); no replication

When the rejected choice is right

Strong write-consistency across replicas is a hard product requirement

Why: Simple, matches single-writer-per-shard model (P8), adequate for read scaling

ADR-20

Memory arena strategy

Chosen

mmap persistent blocks

Rejected

Full heap load of blocks; direct I/O with no page cache

When the rejected choice is right

Deployment target has no reliable page cache (constrained embedded device)

Why: Lets the OS page cache manage hot/cold block residency for free

ADR-21

Multi-tenancy isolation

Chosen

Shard-per-tenant

Rejected

Shared shard + tenant label; separate process per tenant

When the rejected choice is right

Tenant count is small and trusted, shared shard's lower overhead wins

Why: Bounds one tenant's cardinality blast radius from another (P4)

ADR-22

Backup format

Chosen

Block-level snapshot copy

Rejected

Logical dump/restore; continuous WAL archiving only

When the rejected choice is right

Storage backend charges heavily per-object, favoring a single logical dump

Why: Blocks are already immutable and self-describing (P11), trivial to copy

ADR-23

Downsample cadence

Chosen

Fixed rollup tiers (5m / 1h / 1d)

Rejected

Adaptive/ML-driven tier selection; no downsampling

When the rejected choice is right

Query patterns are known in advance and narrowly time-windowed already

Why: Predictable storage/precision tradeoff, simple to reason about (P10)

ADR-24

Bit-packing implementation

Chosen

Custom bitwriter/bitreader

Rejected

External bitstream crate; byte-aligned encoding only

When the rejected choice is right

Team needs to ship fastest possible and accepts a well-audited external crate

Why: Full control over the exact Gorilla bit layout for conformance fixtures

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1 — Pure LSM keyed by (SeriesId, Timestamp)

   writes ──▶ [ MemTable ] ──flush──▶ [ SSTable L0 ] ──compact──▶ [ SSTable L1 ] ──▶ ...
                                        key = (SeriesId, ts), value = sample bytes

Regime where it wins: mixed OLTP + time-series workload needing arbitrary point updates/deletes by exact key, not just time-range scans. Real system embodying it: KairosDB (built on Apache Cassandra, itself an LSM store). Why rejected: general LSM key-value semantics don't exploit the Gorilla-style columnar regularity (P3) that this design's compression ratio (M5) depends on — a generic SSTable format compresses row-wise, losing most of delta-of-delta/XOR's benefit.

Alternative 2 — General RDBMS with time-partitioned tables

   INSERT ──▶ [ Postgres WAL ] ──▶ [ Heap chunk_2024_06 ] [ Heap chunk_2024_07 ] ...
                                        (hypertable chunking, TimescaleDB-style)

Regime where it wins: need full SQL joins/transactions against time-series data alongside relational data in the same engine. Real system embodying it: TimescaleDB. Why rejected: inherits Postgres's own MVCC/WAL underneath a second, ChronoDB-style durability layer — doubles the write-amplification and complicates the crash-recovery story (§17.7, §33 Q17) that this design keeps single-layered (ADR-01).

Alternative 3 — Segment-based columnar OLAP, real-time/historical split

   ingest ──▶ [ Real-time node buffer ] ──handoff──▶ [ Historical node segment ]
                     (queried live)                    (queried via broker, §31)

Regime where it wins: ad-hoc slice-and-dice OLAP over many high-cardinality dimensions, not just time-range scans with a small fixed query surface. Real system embodying it: Druid (Yang et al. 2014). Why rejected: requires distinct node types and external coordination (historically Zookeeper) — operational complexity this single-binary, single-node-scoped design (§1) deliberately avoids.

Alternative 4 — Wide-column store with tag-embedded row keys

   row key = metric:tag1=v1,tag2=v2:ts_bucket ──▶ [ HBase region ]

Regime where it wins: already operating a wide-column/Bigtable-like store at scale for other workloads, and can amortize its operational cost across this one too. Real system embodying it: OpenTSDB (on HBase). Why rejected: tag cardinality becomes part of the storage key directly, so unbounded tag values cause region hot-spotting at the storage layer itself, not just a memory problem — this design deliberately keeps cardinality a guarded, ingestion-time-controlled cost (P4, ADR-14) rather than a storage-layout one.
