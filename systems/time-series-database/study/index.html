Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If compaction (§17) falls permanently behind ingestion (FM-3), what is the exact sequence of degraded states the system passes through before it becomes unavailable, and which invariant (§7) is the first to come under pressure?
  2. Why does I11's cardinality guard (§20) have to live at ingestion time rather than at query time, given that §19's query planner already has a natural chokepoint at the label index (§13)?
  3. Walk through what happens to I14's replay-idempotency guarantee (§16) if a checkpoint record (§8.3) is itself corrupted — does §16.8's edge-case handling still hold, or does it silently regress to a full-history replay?
  4. ADR-15's dedicated OOO staging buffer (§18) exists specifically to avoid contending with the live append path (P8). Under what ingestion pattern does this design still fail to protect live-path latency, and which M# target (§28) would first reveal it?
  5. §32's capacity model derives the 5,000,000-series ceiling from head-block memory (M7). If ADR-20's mmap strategy for persistent blocks were replaced with full heap loading, which other §4 constraint would become the binding one instead?
  6. Compare how ADR-09's compaction leveling and Druid's real-time/historical split (§31) each solve the same underlying problem (bounding read amplification over time) — why does this design reject Druid's approach given §29's scalability analysis?
  7. I6 requires compaction output to preserve sample count exactly. Describe a compaction bug that would violate I6 without ever triggering I10's checksum detection — what additional invariant or fixture (§26) would be needed to catch it?
  8. §21's WAL-shipping replication (ADR-19) relies on I14 holding on the replica side. What specific WAL record ordering guarantee, if violated during shipping, breaks I14 on the replica without breaking it on the primary?
  9. P10 requires downsampling to be "explicit, never silent." Trace exactly how a query in §19 that spans both raw and rollup tiers surfaces this explicitness to the caller — what happens if it doesn't (which MM applies)?
  10. §20's per-tenant cardinality accounting (ADR-21) is meant to isolate tenants. Under what shard-assignment failure would two tenants share cardinality headroom despite ADR-21's design intent, and how would §22's threat model (T5) classify that failure?
  11. Why is retention (§20, ADR-16) enforced at block granularity rather than sample granularity, and what would have to change in §8.5's block layout for sample-level retention to become tractable without violating P2?
  12. §28's M8 compaction-throughput target and §32's derived 3× I/O-amplification factor together imply a minimum disk bandwidth. If NVMe bandwidth were halved (cheaper storage tier), which two other constraints in §4 would need to relax in tandem?
  13. Contrast ADR-03's delta-of-delta timestamp encoding with a hypothetical fixed-interval-only encoding (rejected alternative) — under exactly what real-world ingestion condition (name it) does the fixed encoding's simplicity outweigh its fragility, per ADR-03's sixth column?
  14. §18's backfill path bypasses the live ingest path entirely. Explain why this design choice is safe with respect to I2 (monotonic timestamps) but could still violate I6 if the backfill's target block is mid-compaction — what serializes the two?
  15. §24's canary/rollback procedure validates a new binary against query_range.golden (§19.5) before promotion. What class of regression would this fixture fail to catch, and which other §26 verification technique would be needed to close that gap?
  16. Given §29's named bottleneck ordering (append-lock contention first, then index memory, then compaction I/O, then query CPU), what operational signal would tell you which bottleneck you have hit without needing to read source code?
  17. §31 shows TimescaleDB inheriting Postgres's own WAL underneath ChronoDB's-style chunking. Why does that combination not simply get "the best of both" — what concrete cost does the redundant durability layer impose that this design avoids?
  18. If the OOO acceptance window (§4, ADR-15) were widened from 1 hour to 24 hours, which M# target would degrade first, and which invariant would have to be re-examined for correctness at the new window size?
  19. §30's MM6 says a block's manifest is "a contract, not a hint." Identify a place in §21's backup/restore procedure where violating MM6 (trusting external metadata instead of the manifest) would produce a subtly wrong restore that still passes I10.
  20. Explain, using §32's derived numbers, why the 5m-downsample tier's 20× storage reduction (item 10) does not simply mean "20× less useful data" — what is preserved and what is genuinely lost, and where in §8/§20 is that distinction made explicit?

30. Mental Models & First Principles

MM1 — "A time series is a compressible column, not a row." Predicts: columnar, per-field codecs (P3) beat row-oriented generic compression. Bug class without it: naive row storage bloats disk 8-12× past the M5 target. Resolving: §14.

MM2 — "Cardinality is a multiplicative, not additive, cost." Predicts: two independent 1,000-value labels on one metric create 1,000,000 series, not 2,000. Bug class without it: unbounded label values (e.g. raw request IDs) silently exhaust memory. Resolving: §13 / §20.

MM3 — "The WAL is the source of truth; the head block is a cache of it." Predicts: any head-block state must be reconstructible purely from the WAL (I14). Bug class without it: recovery logic that "patches up" the head instead of fully replaying loses data silently on edge-case crashes. Resolving: §16.

MM4 — "Out-of-order is the norm at the edge, ordered is the norm at the core." Predicts: the ingestion boundary needs OOO tolerance (P6) but persisted chunks never do. Bug class without it: treating any OOO sample as an ingestion error drops legitimate multi-producer/backfill traffic. Resolving: §18.

MM5 — "Compaction trades write amplification now for read amplification later — or the reverse if skipped." Predicts: skipping compaction keeps write cost low but query cost (blocks touched, §29) grows unbounded with time. Bug class without it: operators disable compaction "to save I/O" and silently degrade every future query. Resolving: §17 / §29.

MM6 — "A block's meta.json is a contract, not a hint." Predicts: any consumer (query, backup, replica) can trust a block's self-description without cross-checking external state (P11). Bug class without it: a query engine that trusts stale external metadata instead of the block's own manifest serves wrong data after a partial migration. Resolving: §17 / I10.

MM7 — "Downsampling is a lossy compiler pass over history." Predicts: every rollup tier has a documented, queryable precision loss (P10), just like a compiler optimization level. Bug class without it: an operator can't distinguish "the metric really spiked" from "the rollup smoothed it out." Resolving: §20.

MM8 — "Query latency is bounded by index selectivity, not raw data volume." Predicts: a highly selective query on a huge dataset is fast; a poorly selective query on a small dataset can still be slow if it touches every block. Bug class without it: a query planner that estimates cost from data size alone mis-prioritizes optimization effort. Resolving: §19 / §29.

Required reading (§5)

Books

  • Kleppmann, M. Designing Data-Intensive Applications. O'Reilly, 2017 — ch. 3 (storage & retrieval: LSM-trees vs B-trees) and ch. 5 (replication) — extract: the write-amplification/read-amplification tradeoff that shapes ADR-09. Applied in §17 / Phase 5.
  • Petrov, A. Database Internals. O'Reilly, 2019 — Part I (storage engines), ch. 4 (B-tree basics) and ch. 7 (log-structured storage) — extract: page/segment layout discipline reused for the WAL segment format. Applied in §16 / Phase 4.
  • Dunning, T. & Friedman, E. Time Series Databases: New Ways to Store and Access Data. O'Reilly, 2014 — extract: the taxonomy of TSDB workloads (regular-interval metrics vs irregular events) that motivates ADR-03. Applied in §14 / Phase 2.
  • Gregg, B. Systems Performance, 2nd ed. Addison-Wesley, 2020 — ch. 2 (methodology), ch. 8 (file systems: mmap/fsync cost) — extract: the USE method for §28's target table and the fsync-latency reasoning for M4. Applied in §28 / Phase 4.
  • Akidau, T., Chernyak, S., Lax, R. Streaming Systems. O'Reilly, 2018 — ch. 2 (watermarks), ch. 3 (windowing) — extract: watermark/lateness vocabulary reused for the out-of-order window (ADR-15). Applied in §18 / Phase 6.
  • Silberschatz, A., Korth, H., Sudarshan, S. Database System Concepts, 7th ed. McGraw-Hill, 2019 — ch. 14 (indexing), ch. 19 (recovery) — extract: classical write-ahead-log recovery invariants reused directly as I5/I14. Applied in §16 / Phase 4.

Papers

  • Pelkonen, T., Franklin, S., Thereska, E., Veeraraghavan, K. et al. "Gorilla: A Fast, Scalable, In-Memory Time Series Database." PVLDB 8(12), 2015 (Facebook) — delta-of- delta timestamp + XOR float encoding, 2-hour in-memory block design. Applied in §14 / Phase 2 (ADR-03, ADR-04, ADR-05).
  • Yang, F., Tschetter, E., Léauté, X., Ray, N., Merlino, G., Ganguli, D. "Druid: A Real-time Analytical Data Store." SIGMOD 2014 (industrial track) — segment-based columnar storage split between real-time and historical nodes. Applied in §31 / §34.
  • O'Neil, P., Cheng, E., Gawlick, D., O'Neil, E. "The Log-Structured Merge-Tree (LSM-Tree)." Acta Informatica 33(4), 1996 — merge/leveling cost model. Applied in §17 / Phase 5 (ADR-01, ADR-09).
  • Mohan, C., Haderle, D., Lindsay, B., Pirahesh, H., Schwarz, P. "ARIES: A Transaction Recovery Method Supporting Fine-Granularity Locking and Partial Rollbacks Using Write-Ahead Logging." ACM TODS 17(1), 1992 — WAL-before-ack, idempotent replay. Applied in §16 / Phase 4 (P5, P12, I5, I14).
  • Adkins, C. et al. "Monarch: Google's Planet-Scale In-Memory Time Series Database." PVLDB 13(12), 2020 — multi-tenant ingestion-time cardinality/rate limiting at scale. Applied in §20 / Phase 8 (P4, I11, ADR-14).
  • Rabenstein, B. & Volz, J. Prometheus TSDB design documentation and PromCon talks ("Prometheus TSDB: The Head Block", "Storing 16 Bytes at Scale") — block/head-block split, WAL-backed head, time-based compaction leveling. Applied in §17 / Phase 5 (ADR-09, ADR-10).
  • Reinartz, F. "Writing a Time-Series Database from Scratch." fabxc.org engineering blog, 2017 — origin design of Prometheus 2.0's tsdb; head block, WAL, block compaction narrative. Applied in §15 / Phase 3 (P1, I13).
  • InfluxData Engineering. "In-Memory Indexing and Compression" / TSM (Time-Structured Merge Tree) storage engine documentation, InfluxDB — LSM-adjacent columnar chunk files with a WAL front-end. Applied in §17 / Phase 5 (ADR-01, ADR-10).

Reference Implementations

  • prometheus/prometheus (dir tsdb/) — head block, WAL, block compaction, index format. Lesson: the head-block/persistent-block split cleanly separates mutable and immutable concerns (P1). Pitfall: the on-disk index format's complexity grows fast; study tsdb/index/index.go before copying its postings encoding wholesale.
  • influxdata/influxdb (dir tsdb/engine/tsm1/) — TSM engine, cache + WAL + TSM files. Lesson: a per-shard cache absorbing writes before TSM compaction mirrors head.rs. Pitfall: early TSM had unbounded cache growth under cardinality spikes — motivates I11.
  • timescale/timescaledb — hypertable chunking on top of PostgreSQL. Lesson: time partitioning ("chunks") as a first-class catalog concept, independent of the storage engine underneath. Pitfall: inheriting a general-purpose RDBMS's own WAL/MVCC doubles the durability machinery — avoided here by owning the WAL directly (ADR-01).
  • OpenTSDB/opentsdb — tag-based row-key schema on HBase. Lesson: tag combinations become part of the storage key, making cardinality a storage-layout problem, not just a memory problem. Pitfall: unbounded tag values cause HBase region hot-spotting — directly motivates the cardinality guard (P4, ADR-14).
  • facebookarchive/beringei — open-sourced reference implementation of the Gorilla paper's in-memory codec. Lesson: the exact bit-layout of delta-of-delta + XOR encoding, useful as a cross-check for §14's fixtures. Pitfall: it is memory-only, no WAL/disk persistence — do not copy its durability model (or lack thereof).
  • VictoriaMetrics/VictoriaMetrics — modern Prometheus-compatible TSDB. Lesson: strict ingestion-time cardinality limiting as a first-class, documented feature. Pitfall: aggressive limiting without good telemetry silently drops legitimate high-cardinality tenants — motivates I12's "reject with telemetry, never drop silently" rule.

RFCs / Specifications

  • OpenMetrics Specification, CNCF, v1.0 (2020) — text exposition format for metric samples; informs the ingestion parser's sample/label grammar. Applied in §8 / Phase 3.
  • Prometheus Remote Write Specification (1.0 and 2.0), Prometheus project / CNCF — protobuf+Snappy wire format for pushed samples. Applied in §21 / Phase 9 (ADR-17).
  • InfluxDB Line Protocol Reference, InfluxData documentation — measurement/tag/field/ timestamp text encoding, a second real-world ingestion grammar to conform against. Applied in §8 / Phase 3.

Glossary (§36) · 48 terms · site-wide glossary

Backfill
bulk historical-data load bypassing the live ingest path (§18).
Bit-packing
encoding values at sub-byte granularity via a bitstream (§14, ADR-24).
Block
immutable, time-ranged, self-describing persisted unit of storage (§8.5).
BlockMeta
a block's manifest record: time range, counts, checksum (§11).
Cardinality
count of distinct label-value combinations for a metric (§13, P4).
Cardinality guard
ingestion-time limiter rejecting series past a ceiling (§20).
Checkpoint
a WAL record marking a durable head-state boundary, bounding replay.
Chunk
a per-series, codec-encoded byte buffer covering a bounded sample range.
Compaction
merging smaller blocks into larger, coarser-grained ones (§17).
CRC
cyclic redundancy check, used here as CRC32C for corruption detection (I4).
Delta-of-delta
encoding the second difference of successive timestamps (§14).
Downsampling
producing a lower-resolution rollup tier from raw samples (§20, P10).
fsync
the syscall forcing durable disk write before an operation is acknowledged.
Gorilla codec
the delta-of-delta + XOR encoding scheme from Pelkonen et al. 2015.
Grace period
the delay between tombstoning and physical reclaim (I7, P14).
Head block
the single mutable, in-memory, actively-appended structure (P1).
Histogram bucket
a fixed value-range bin used for distribution aggregation.
Idempotent replay
replaying a log twice produces the same state as once (P12).
Ingestion
the path by which external samples enter the system (§8.1, §15).
Inverted index
label-value → series-id-list index structure (§13, ADR-07).
Janitor
the background process reclaiming space after retention expiry (§20).
LabelSet
the sorted set of label-name/value pairs identifying a series (§11).
Line protocol
a text ingestion grammar for samples (InfluxDB-style, §8.1).
Manifest
synonym for a block's meta.json self-description (P11).
mmap
memory-mapping a persisted block file for zero-copy read access (ADR-20).
Out-of-order (OOO) window
the time span behind head-max-ts still accepted (§4).
Percentile / quantile
a statistical aggregation over a value distribution (§19).
Postings list
the set of SeriesIds matching one label-value pair (§13).
Rate
per-second average delta over a range, counter-reset-aware (§19.2).
Retention
the policy window after which data is eligible for deletion (§20).
Rollup
synonym for a downsampled aggregate tier (§20, ADR-23).
Sample
one (timestamp, value) pair belonging to a series (§11).
Scrape interval
the nominal cadence between successive samples of one series.
Segment
a bounded, rotatable WAL file unit (§16, ADR-06).
SeriesId
the dense integer identifier allocated to a canonical LabelSet (§11).
Sharding
partitioning series/tenants across independent append/index units (P8).
Snappy
a fast, low-ratio compression codec used for the remote-write wire format.
Staging (OOO)
the buffer holding out-of-order samples pending merge (§18).
Tenant
an isolated logical namespace of series within a deployment (ADR-21).
Tombstone
a marker recording a pending deletion, physically reclaimed later (P14).
Token bucket
the rate-limiting mechanism throttling compaction I/O (P7).
Tier (rollup)
one fixed downsample resolution (e.g. 5m, 1h, 1d) (ADR-23).
ULID
a sortable, unique identifier type used for BlockId (§11).
Varint
a variable-length integer encoding used in delta streams and postings (§8).
Wal-shipping
streaming WAL segments to a replica for replay-based replication.
Write-ahead log (WAL)
the durable, append-only log gating every mutation (P5).
Write amplification
extra bytes written by compaction relative to raw ingest (§29).
XOR encoding
Gorilla's float encoding exploiting bitwise similarity (§14, ADR-04). ---
