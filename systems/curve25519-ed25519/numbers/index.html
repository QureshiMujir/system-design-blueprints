The one defining property: every public function is a pure, constant-time, allocation-free computation on caller-owned memory — there is no server loop, no scheduler, no persistent state to reason about; the entire correctness and performance story is per-call.

36. Back-of-Envelope Capacity Model

All numbers chained from §4 System Constraints.

  1. X25519 throughput/core = 1 / M1 = 1 / 30 µs ≈ 33,333 agreements/s/core.
  2. Ed25519 verify throughput/core = 1 / M3 = 1 / 60 µs ≈ 16,666 verifies/s/core.
  3. Batch-64 verify throughput/core = 64 sigs / M4 (800 µs) = 80,000 verifies/s/core ⇒ speedup factor = 80,000 / 16,666 ≈ 4.8× over serial (consistent with §22's ≥ 3× floor).
  4. 16-core node aggregate X25519 ceiling = 33,333 × 16 ≈ 533,000 agreements/s, before other handshake costs (certificate ops, network RTT, §4) dominate the caller's total budget.
  5. Basepoint comb-table memory = 32 rows × 8 cols × 96 B/entry (affine-niels form) ≈ 24,576 B ≈ 24 KiB (§4's stated static-memory line, derived here from the table's own dimensions rather than merely asserted).
  6. Field-element unpacked vs. wire overhead = 40 B (in-memory, 5×u64) / 32 B (canonical wire) = 1.25× memory overhead for the unpacked representation — relevant when sizing a point cache holding many live EdwardsPoints (4 field elements each, 160 B/point, §4).
  7. Per-connection X25519 material = 32 B (secret) + 32 B (public) + 32 B (shared secret) = 96 B/connection; at the §4 concurrency ceiling of 1,000,000 concurrent connections, total X25519 material = 96 B × 10⁶ = 96 MB — a small fraction of a typical server's RAM budget, confirming §4's "memory is not the binding constraint" implicit assumption.
  8. 30-day fuzz-canary execution volume = assuming ~50,000 exec/s/core (typical for a crypto-primitive libFuzzer target) × 30 days × 86,400 s/day = ≈1.296 × 10¹¹ executions — the statistical basis underlying the M12 "zero panics" gate's confidence.
  9. dudect measurement wall-clock = M9's ≥ 10⁷-measurement-pair floor at ~1 µs/pair (dominated by the ≤ 60 µs per-call latency, M2/M3) ≈ 10 s/function/run — cheap enough to run on every release candidate (ADR-22), not just nightly.
  10. Montgomery-ladder stack footprint = 5 live FieldElements (x1,x2,z2,x3,z3, §16.2) × 40 B = 200 B + frame overhead, well under the §4 ≤ 4 KiB stack ceiling — leaving headroom for embedded targets with far tighter stack budgets than a server CPU.
