Project Name: Curve25519 / Ed25519

1. Goal & Scope

Build, from the prime field upward, a constant-time Rust implementation of X25519 key agreement (RFC 7748) and Ed25519 digital signatures (RFC 8032 / FIPS 186-5 section 7): the field GF(2²⁵⁵ − 19), the Montgomery curve Curve25519 and twisted Edwards curve Edwards25519, constant-time scalar multiplication (Montgomery ladder, fixed-base comb, Straus double-scalar), deterministic nonce generation, point encoding/validation, cofactor-aware verification, and a conformance harness that reproduces every RFC, Wycheproof, CAVP/ACVP, and published-corpus test vector bit-for-bit.

Phase-0 deliverable (numbered, one module per line):

  1. curve-field — GF(2²⁵⁵ − 19) unsaturated radix-2⁵¹ arithmetic (add/sub/mul/square/invert).
  2. curve-scalar — arithmetic mod the group order L = 2²⁵² + 27742317777372353535851937790883648493.
  3. curve-edwards — twisted Edwards point group, extended-projective coordinates.
  4. curve-montgomery — Montgomery x-only point group, the RFC 7748 ladder.
  5. x25519 — the X25519 protocol surface (agree, key types, small-order rejection).
  6. ed25519 — the Ed25519 protocol surface (sign, verify, key types).
  7. conformance/runner — the fixture-replay harness that gates every phase's Deliverable.

System boundaries. Provides: field/scalar/point arithmetic, X25519 ECDH, Ed25519 sign/verify, Ed25519ph/Ed25519ctx, batch verification, a CLI, conformance/fuzz/timing harnesses. Delegates: transport (TLS/SSH/Noise), certificate parsing, key storage/HSM custody, randomness (the OS CSPRNG via getrandom, consumed only for X25519 ephemeral secrets — never for the Ed25519 nonce, which is deterministic per Design Principle P7). Does not provide: X448/Ed448, Ristretto encoding, FIPS 140-3 module boundary code, hash-to-curve (all PhaseDeferred, §39).

Non-goals. Not a general-purpose ECC library (no P-256/P-384/secp256k1); not a TLS or SSH implementation; not a key-management service.

Deployment model. A no_std library crate embedded in TLS terminators, SSH daemons, WireGuard peers, signing services, and embedded/HSM firmware; a thin std-only CLI (curve-cli) for operators.

Target users/operators. Protocol implementers integrating X25519/Ed25519 into a larger system; security auditors reviewing the implementation; on-call engineers debugging a production handshake or signature-verification failure.

What later phases unlock. Phase 0's field kernel unlocks Phase 1 (scalar arithmetic) and Phase 3 (Edwards point group); Phase 5 (scalar multiplication) unlocks Phase 7 (X25519) and Phase 8 (Ed25519 signing); Phase 9 (verification) unlocks Phase 10 (batch verification, the public API); Phase 11 (constant-time hardening) and Phase 12 (conformance/fuzzing) gate release; Phase 13 seals the release-engineering story.

Recommended language: Rust 1.78+, edition 2021. Rationale: memory safety without GC pauses; the borrow checker prevents a class of secret-aliasing bugs C/C++ cannot catch at compile time; mature audited crypto ecosystem (subtle, zeroize, curve25519-dalek) to cross-validate against (ADR-01, §9). Rejected: C (BoringSSL/libsodium's language — no memory safety, chosen here only as a cross-validation oracle, not an implementation target); C++ (same memory-safety gap, plus ABI fragility); Go (GC pauses are a timing side-channel surface, no constant-time primitives in the standard library); Zig (immature crypto ecosystem, no audited constant-time crate parity).

Prerequisites. Elliptic curve group theory (affine/projective coordinates, point at infinity, cofactors); the Diffie–Hellman problem; the Schnorr-signature construction EdDSA specializes; modular arithmetic and Fermat's little theorem (used for field/scalar inversion); Rust ownership and the no_std embedded model. A reader should be able to open RFC 7748 section 5 and explain why the X25519 scalar is clamped before starting Phase 2 (§14).

Estimated timeline. Phase 0: 1 week. Full plan (Phases 0–13): 14 weeks (~3.5 months) at one engineer full-time; add 4–6 weeks for an external security audit before a Sealed production tag.

Deferred features, each flagged for the Deferred Features Register (§39): X448/Ed448 — PhaseDeferred(§9 ADR-18); Ristretto/Decaf255 encoding — PhaseDeferred(§9 ADR-19); FIPS 140-3 module boundary — PhaseDeferred(§9 ADR-20); Elligator2 hash-to-curve — PhaseDeferred(§5); PKCS#11/HSM integration — PhaseDeferred(§22); Ed25519-based VRF (RFC 9381) — PhaseDeferred(§9 ADR-17); a formally-verified (HACL*-style) field backend — PhaseDeferred(§38); multi-scalar multiplication for zk-SNARK consumers — PhaseDeferred(§38).

2. Why Build This

X25519 and Ed25519 are the elliptic-curve primitives the modern internet converged on: every TLS 1.3 default key_share group, every ssh-ed25519 host key, every Signal/Double-Ratchet session, every Noise (Noise_XX, Noise_NK) handshake, every WireGuard tunnel, every ed25519-algorithm WebAuthn assertion, every Tor onion-service descriptor, every cosign/ sigstore signature, and most modern blockchain transaction signatures route through one or both. Engineers who can configure Ed25519 are common; engineers who have written the field multiplication, validated it against an independent oracle, and threaded a constant-time Montgomery ladder through it are rare — rarer still are the ones who can explain why Ed25519's cofactor-scaled verification equation [8h]A + [8R] − [8s]B differs from the naive hA + R − sB and exactly which attack the naive form permits (Chalkias et al. 2020; Brendel et al. 2021). This project closes that gap by making every layer — field, scalar, curve group, protocol — something you built, validated, and can debug from first principles.

The engineering muscles built: unsaturated-radix modular arithmetic with lazy carry propagation; complete vs. incomplete group laws and why that distinction is a security property, not an implementation nicety; constant-time programming as a type-level discipline (Design Principle P2) rather than a code-review habit; deterministic-vs-randomized nonce design and why one closes an entire attack class (Aranha et al. 2020) that the other cannot; and conformance-driven development where "passes RFC vectors" is necessary but never sufficient. Sibling systems worth cross-linking by name: a TLS 1.3 handshake implementation (consumes X25519 directly), an SSH daemon (consumes Ed25519 host keys), a Signal/Double-Ratchet session manager (consumes X25519 for the ratchet, Ed25519 for identity keys), and a WireGuard-style tunnel (consumes X25519 exclusively). The calibration value: this is one of the few domains where "constant-time" and "correct" are both externally checkable — via dudect and via Wycheproof/CAVP — so the reader learns to demand evidence, not assurance, for a security property.

What Mastery Looks Like (competencies gained, each tied to a phase):

  • Derive the radix-2⁵¹ field representation's carry bounds and prove mul never overflows a 53-bit limb — §13 (Phase 1).
  • Explain why the twisted Edwards addition law has no exceptional (point-at-infinity) cases and why that matters for constant-time code — §15 (Phase 3).
  • Implement and defend a constant-time Montgomery ladder against a dudect timing audit — §16 (Phase 4), §23 (Phase 11).
  • Derive the deterministic-nonce construction from first principles and name the exact attack (LadderLeak-class nonce bias) it forecloses — §20 (Phase 8).
  • Explain cofactor-aware verification well enough to redesign it for a hypothetical cofactor-4 curve — §21 (Phase 9).
  • Run a differential conformance harness against an independent reference implementation and interpret a mismatch as a specification bug, not just an implementation bug — §24 (Phase 12).
  • Read a dudect t-statistic and a fuzzing canary report and know which one gates which release criterion — §23, §24, §32.

6. Design Principles

  1. P1 — Correctness before speed. Every arithmetic routine is validated against an independent oracle (num-bigint, curve25519-dalek) before it is optimized. Tradeoff: slower initial development. Operational implication: the conformance suite (§30) gates every merge. Violating it breaks: silently wrong shared secrets/signatures that pass casual testing.
  2. P2 — Constant-time is a type-level property. Secret-dependent branches and secret-indexed table lookups are structurally impossible in the public API (ADR-06, ADR-12). Tradeoff: every conditional needs a Choice-based rewrite. Operational implication: dudect (M9) gates release. Violating it breaks: side-channel key recovery (T1).
  3. P3 — The Edwards form is complete; use it wherever y matters. No exceptional points in the twisted-Edwards law (Hisil et al. 2008). Tradeoff: the Montgomery form is still needed for x-only ECDH speed, so two representations must be maintained (I14). Violating it breaks: point-at-infinity edge-case bugs.
  4. P4 — Strict verification is the default; lax is opt-in and logged. RFC 8032 section 5.1.7 (ADR-07). Tradeoff: strict mode rejects some historical non-canonical signatures older libraries accepted. Operational implication: the lax-verify feature is a build-time, audited decision, never a runtime toggle. Violating it breaks: malleability (T3).
  5. P5 — No unsafe in the scalar/curve/field crates. SIMD acceleration is isolated in an optional, separately audited crate (ADR-11). Tradeoff: leaves 2–3× performance on the table without the SIMD feature. Operational implication: the memory-safety audit surface is the SIMD crate only. Violating it breaks: the entire memory-safety argument for the core crates.
  6. P6 — Secrets are typed and zeroized, never Debug. SigningKey, secret scalars, and derived nonces implement ZeroizeOnDrop and opt out of Debug/Display (ADR-13). Tradeoff: harder ad-hoc debugging. Operational implication: logs cannot accidentally contain a secret scalar. Violating it breaks: I5, turning a log-aggregation slip into key disclosure.
  7. P7 — Determinism over randomness wherever RFC 8032 allows it. The nonce is a pure function of the secret prefix and message (I3). Tradeoff: no RNG-failure defense-in-depth (there is no RNG to fail) but some fault-injection exposure on repeated signs. Operational implication: signing is byte-for-byte reproducible and testable. Violating it breaks: LadderLeak-class nonce-bias attacks (T2).
  8. P8 — Cofactor-aware verification, always. [8h]A + [8R] − [8s]B (ADR-08). Tradeoff: three extra doublings per verification (~15 ns). Operational implication: one verification path safely handles both prime-order and small-subgroup-contaminated inputs. Violating it breaks: small-subgroup confusion (T4).
  9. P9 — Field arithmetic in unsaturated radix-2⁵¹. Five u64 limbs, lazy carry propagation (ADR-03). Tradeoff: requires careful limb-bound bookkeeping (I9). Operational implication: this module gets the deepest fixture coverage (§30) — it is the most bug-prone layer. Violating it breaks: silent wrong answers from carry overflow.
  10. P10 — Conformance is the contract, not a suggestion. Every phase's Deliverable is gated on named fixtures — RFC vectors, Wycheproof, CAVP/ACVP, Chalkias corpus, dalek differential — never "looks right." Tradeoff: slower phase completion. Operational implication: the Milestone Summary (Appendix B) gates are mechanical. Violating it breaks: the premise that this blueprint teaches verifiable engineering.
  11. P11 — Small-order points are rejected explicitly, not only implicitly. The 22 eight-torsion points are enumerated and checked at decode time on both curve forms (ADR-10, I11). Tradeoff: a lookup + comparison on every decode. Operational implication: defense-in-depth even if a downstream check (I7) is later weakened. Violating it breaks: T4.
  12. P12 — One canonical cross-validation oracle per layer. curve25519-dalek for field/scalar/point (ADR-16); RFC/Wycheproof/CAVP for protocol layers. Tradeoff: a dalek regression could mask a shared bug. Operational implication: RFC/Wycheproof vectors are the independent second check dalek parity alone cannot provide. Violating it breaks: false confidence from a single-oracle blind spot.
  13. P13 — Every public function returns Result; panics on attacker input are P0. (I12) Tradeoff: verbose error-handling call sites. Operational implication: the 30-day fuzz canary (M12) gates Sealed. Violating it breaks: availability — a crafted input becomes a DoS.
  14. P14 — Prehash and context-string variants are exposed, never defaulted. Ed25519ph/ Ed25519ctx (ADR-17) exist for callers who need them; plain Ed25519 is the CLI/example default. Tradeoff: two extra entry points to fixture. Operational implication: cross-protocol signature reuse is prevented by never silently mixing variants. Violating it breaks: domain-separation failures (a T5-class cross-protocol replay).

8. Domain Model

8.1 The field GF(2²⁵⁵ − 19)

p = 2²⁵⁵ − 19. A field element is a residue class mod p, represented in-memory as five unsaturated 64-bit limbs [h0..h4] such that the value equals h0 + h1·2⁵¹ + h2·2¹⁰² + h3·2¹⁵³ + h4·2²⁰⁴ (Bernstein-Lange radix-2⁵¹, ADR-03, P9). Limbs are unsaturated: each may hold up to ~2⁵³ between reduction steps, and reduction happens lazily. Reduction modulo p uses the identity 2²⁵⁵ ≡ 19 (mod p): any partial product landing above bit 255 is multiplied by 19 and folded back into the low limbs. add/sub do not fully reduce; mul/square produce a canonical-range-adjacent result; only to_bytes (serialization) forces the final < p reduction (I1). Inversion uses Fermat's little theorem: x⁻¹ = x^(p−2) mod p, computed as a fixed chain of ~250 squarings and ~12 multiplications (the canonical Curve25519 addition chain) — never a variable-time extended-Euclid/binary-GCD, which would leak the operand through its timing (P2).

8.2 Edwards25519 (twisted Edwards curve)

Equation: −x² + y² = 1 + d·x²·y² over GF(p), with d = −121665/121666. This is a twisted Edwards curve (a = −1). Its addition law (Hisil-Wong-Carter-Dawson 2008, applied here) is complete: it is correct for every pair of inputs, including a point added to itself and either operand being the identity — no exceptional cases, hence no secret-dependent branch is ever needed to special-case them (P3). Points are represented in extended projective coordinates (X : Y : Z : T) with T = XY/Z, affine (x, y) = (X/Z, Y/Z); the identity is (0 : 1 : 1 : 0). Group order is 8·L where L = 2²⁵² + 27742317777372353535851937790883648493 is prime — the curve has cofactor 8, meaning eight points of small order sit in the kernel of multiplication-by-L (the eight-torsion subgroup, "the 22 bad points" once every valid encoding of each of the 8 group elements is counted, per RFC 8032 discussion and the Chalkias et al. 2020 corpus).

8.3 Curve25519 (Montgomery curve) and the birational map

Equation: y² = x³ + 486662·x² + x over the same GF(p). X25519 uses only the x-coordinate (Montgomery 1987's original motivation): a scalar multiplication needs just x, never y, halving the field operations per ladder step (Bernstein 2006). A birational map sends Edwards25519 ↔ Curve25519: u = (1+y)/(1−y), v = u/x (Edwards (x,y) to Montgomery (u,v)), used internally to cross-check a scalar multiple computed on one form against the other (I14) — never on the hot signing/verification path, only in differential tests (§30).

8.4 Scalar multiplication

Three algorithms, chosen per caller (P2, P9):

  • Montgomery ladder (X25519, §16) — a constant-shape state-transition over the pair (x2:z2)/(x3:z3), one conditional swap + one differential add-and-double per scalar bit, MSB to LSB, 255 iterations regardless of the scalar's value (RFC 7748 section 5).
  • Fixed-base comb (Ed25519 signing, §17) — precomputed table B_TABLE[i][j] = (j+1)·16^(2i)·B for i ∈ [0,32), j ∈ [0,8); the scalar is split into 32 radix-16 digits and the table is walked once, each lookup a constant-time 8-way ct_select (never a branch on the digit).
  • Straus double-scalar (Ed25519 verification, §17, §22) — computes [a]A + [b]B simultaneously via a joint signed-digit representation, cheaper than two independent multiplications because the doublings are shared.

State-transition table for one Montgomery-ladder step (bit k_i, MSB→LSB; swap tracks whether (x2,z2) and (x3,z3) are currently in "canonical" or "swapped" roles):

step            | precondition        | action                          | postcondition
----------------|----------------------|---------------------------------|------------------
digit=k_i       | swap_prev = swap_acc | swap_acc ^= k_i                 | swap_acc updated
conditional swap| swap_acc = 1         | ct_swap(x2,x3); ct_swap(z2,z3)  | roles exchanged
conditional swap| swap_acc = 0         | identity (still executed, ct)   | roles unchanged
diff. add+double| any                  | 5 field mul + 4 field sq (fixed)| (x2,z2,x3,z3) advance one bit

8.5 Point encoding / decoding

Edwards compression (32 bytes): the y-coordinate little-endian, with the sign bit of x placed in bit 7 of the last byte. Decompression: recover x = sqrt((y²−1)/(d·y²+1)) via pow(u·v³, (p−5)/8) · u·v (RFC 8032 section 5.1.3's square-root recipe), then select the root matching the stored sign bit; reject if y_bytes ≥ p (I1) or if no square root exists (Error::NotOnCurve). Montgomery u-coordinate (X25519, 32 bytes): raw little-endian field element, high bit of the last byte masked off per RFC 7748 section 5 before use — no sign/validity check is possible on u alone, which is why X25519 instead relies on the zero-shared-secret check (I7) and small-order rejection (I11) rather than point validation.

8.6 Worked example — X25519 Diffie-Hellman exchange

Alice generates 32 random bytes a_raw, clamps them (I2: clear bits 0-2 and bit 255, set bit 254) to get scalar a; her public key is A = X25519(a, 9) (basepoint u = 9). Bob does the same, producing scalar b and public key B = X25519(b, 9). Alice computes shared_A = X25519(a, B); Bob computes shared_B = X25519(b, A). Commutativity of scalar multiplication over the same base gives shared_A = [a][b]·9 = [b][a]·9 = shared_B — this identity is exactly what N.4 of §19 (Phase 7) checks over 1,000 random (a,b) pairs. Before use, each party checks shared ≠ 0 (I7); a zero result means the peer supplied a small-order key.

8.7 Malformed-input example

An attacker sends an X25519 public key equal to one of the eight-torsion small-order points (e.g., u = 0, or the specific 32-byte encodings enumerated in small_order.rs, §11). Decoding succeeds (Montgomery u-coordinates have no validity check, §8.5) but the resulting shared secret is always 0 regardless of the victim's private scalar — I7's zero-check rejects it after the ladder runs (still constant-time: the ladder always executes all 255 steps; only the post-ladder equality-to-zero check branches, and it branches on a public value, not a secret). Separately, I11 rejects the same 22 points explicitly at decode time as defense-in-depth (P11), so this input is caught twice, by independent mechanisms.

8.8 Failure-path example

A verifier receives an Ed25519 signature (R, s) where s was encoded with the top bits set such that the raw 32-byte integer is s' = s + L (i.e., s' ≥ L, a non-canonical encoding that happens to reduce to a valid s mod L). Strict-mode decoding (I6, RFC 8032 section 5.1.7) rejects s' ≥ L outright with Error::NonCanonicalScalar before any point arithmetic — the failure is detected at parse time, not at the final equation check, so no field/curve operation ever executes on the malformed value. This is precisely the malleability vector Chalkias et al. (2020) document: a lax verifier that reduces s' mod L first would accept it, producing a second, distinct 64-byte signature that verifies against the same message and key (T3, §26).

None yet — no arithmetic exists. The one performance-relevant decision at this phase is keeping the workspace's crate graph acyclic and shallow so incremental cargo build stays under 10s for a single-crate change, protecting inner-loop iteration speed for Phases 1–5.

13. Phase 1 — Field Arithmetic: GF(2²⁵⁵ − 19)

13.1 Objectives

Implement FieldElement (§11) — add, sub, mul, square, invert, ct_eq, ct_select, to_bytes/from_bytes — in the radix-2⁵¹ unsaturated representation (P9, ADR-03), constant-time throughout (P2).

13.2 Detailed Implementation Steps

  • Implement add/sub limb-wise with no carry propagation (I9 allows deferred carries between operations); sub uses the "add 2p, then subtract" trick to avoid underflow without a branch, per Bernstein-Lange (2007, §5 reference algorithm, applied here).
  • Implement mul: 5×5 schoolbook cross-products into 9 accumulator limbs (128-bit intermediate), fold high limbs back via 2²⁵⁵ ≡ 19 (mod p) (§8.1), then carry-propagate to 5 canonical-range limbs (P9).
  • Implement square as a dedicated routine — cross-products a[i]·a[j], i≠j, are doubled once instead of computed twice, ~30% faster than mul(a,a).
  • Implement invert via the fixed Fermat addition chain x^(p-2): ~250 squarings + ~12 multiplications, the canonical Curve25519 ladder (Bernstein-Lange 2007) — never a variable-time binary-GCD (P2, ADR-06 spirit).
  • Implement ct_eq/ct_select via the subtle crate (ADR-12), operating only after full reduction (I9) so equal-value-different-limb states never compare unequal.

13.3 Deliverable

curve-field compiles no_std, exposes the full FieldElement API (§11), passes its differential test suite against num-bigint and curve25519-dalek::FieldElement51.

13.4 Acceptance Criteria

  • add/sub/mul/square/invert bit-identical to curve25519-dalek::FieldElement51 for 1,000,000 random operand pairs (M5 gate: mul ≤ 60 ns/op on the CI reference core).
  • Property test: (a·b)⁻¹ = a⁻¹·b⁻¹ holds for 100,000 random nonzero (a,b) pairs.
  • invert(one()) == one(); invert(zero()) returns the RFC-defined zero() (no panic, I12).

  • Missed carry propagation in mul leaves a limb ≥ 2⁵², producing a value congruent to the right answer mod p but with wrong limbs — passes a naive equality check against a reduced reference but fails byte-for-byte comparison (I9).

13.7 Performance Concerns

mul is the hottest function in the entire stack — every point addition/doubling and every ladder step calls it multiple times (§8.4). Target ≤ 60 ns (M5) on a 3 GHz x86_64 core; keep the 9-limb accumulator in registers (no spills) and the carry-propagation loop unrolled, not a for loop over a runtime bound (constant iteration count is both a performance and a constant-time requirement, P2).

13.8 Edge Cases

  • Operand ≥ p supplied via from_bytes (non-canonical wire input) must be caught by I1 at the to_bytes boundary, not silently produce an out-of-range internal value that corrupts later computation.
  • Multiplying zero() by any operand must return zero(), not a partially-reduced non-zero limb pattern that only "looks like" zero.

13.9 Failure Analysis

A field-arithmetic bug is the worst-case failure in this system: it silently propagates through every layer above it (curve ops, scalar mult, signatures) and manifests as an intermittent cross-implementation interop failure, not a crash. Detection: the differential oracle (§13.4) is the only reliable signal — unit tests on hand-picked values miss carry-boundary bugs. Blast radius: every phase from 3 onward. Containment: a failing field.cross_dalek fixture blocks merge (P1, P10). Recovery: bisect against the oracle limb-by-limb, not value-by-value.

13.10 Operational Notes

No runtime telemetry (pure function, I10). Observability is entirely the conformance report (conformance/field.cross_dalek.report.json, M-field milestone, Appendix B) and the dudect timing report once Phase 11 (§23) adds the constant-time gate. No migration/compatibility concerns — FieldElement's wire format is RFC-fixed and never changes (§29).

14. Phase 2 — Scalar Arithmetic mod L

14.1 Objectives

Implement Scalar arithmetic modulo the group order L = 2²⁵² + 27742317777372353535851937790883648493 (§8.2), Barrett reduction, scalar inversion, and the X25519-only clamping transform (I2) as a distinct ClampedScalar type so it cannot be confused with an Ed25519 nonce (P9's sibling discipline, ADR-06).

  • Encode L as a Scalar constant; verify at compile time (a const assertion) that it matches the RFC 8032 / SP 800-186 published value (§5 SP 800-186 applied here).

  • Implement ClampedScalar::from_bits_clamped: clear bits 0–2, clear bit 255, set bit 254 (RFC 7748 §5) — structurally a different type from Scalar so the ladder (§16) cannot accept an unclamped value at the type level (I2).

  • ClampedScalar::from_bits_clamped reproduces RFC 7748 section 5's worked clamping example exactly (named fixture scalar.clamp_rfc7748.json).

14.6 Pitfalls

  • L is not 2²⁵² — it is 2²⁵² + (a 129-bit tail constant). Truncating to 2²⁵² produces a "scalar" larger than the true order that silently corrupts batch verification (I13).

14.7 Performance Concerns

14.8 Edge Cases

  • Scalar exactly equal to L-1 (maximal canonical value) must serialize/deserialize losslessly.
  • Wide reduction of a 64-byte input that is itself ≡ 0 (mod L) must return Scalar::zero(), and the caller (signing, §20) must handle a zero nonce r gracefully rather than treating it as an error (RFC 8032 has no special-case rejection for it; it is astronomically unlikely from a 256-bit hash but must not panic if it occurred, I12).

14.9 Failure Analysis

A scalar-reduction bug corrupts every signature and shared-secret derivation downstream but, unlike a field bug, is often caught earlier because RFC 8032 section 7.1's fixed test vectors exercise the exact s = r + k·a mod L computation directly. Detection: scalar.cross_numbigint and the RFC 8032 vector replay both gate merge. Recovery: isolate whether the bug is in L's constant, the Barrett reciprocal, or the carry logic — the three independently testable failure points.

14.10 Operational Notes

No runtime telemetry (pure function). The clamping type boundary (ClampedScalar) is documented in docs/architecture/montgomery-ladder.md so a future contributor adding an X448 scalar type (deferred, §39) follows the same discipline.

15. Phase 3 — Edwards25519 Point Arithmetic

15.1 Objectives

Implement EdwardsPoint (§11) in extended-projective coordinates: add, double, ct_select, compress/decompress, and is_small_order — the complete, constant-time group law that underlies both signing (§20) and verification (§21).

15.2 Detailed Implementation Steps

  • Represent points as (X:Y:Z:T) with T=XY/Z (§8.2); implement add via the Hisil-Wong- Carter-Dawson (2008) formula set, applied here as: A=(Y1-X1)(Y2-X2), B=(Y1+X1)(Y2+X2), C=T1·2d·T2, D=Z1·2·Z2, E=B-A, F=D-C, G=D+C, H=B+A, X3=EF, Y3=GH, T3=EH, Z3=FG — 8 field multiplications, zero exceptional cases (P3).
  • Implement double via the dedicated 3-mul-4-square formula (cheaper than add(self,self) because Z1=Z2 collapses one product).
  • Precompute and hardcode the constant 2d (d = -121665/121666, §8.2) once as a FieldElement constant, not recomputed per call (P9 sibling discipline).
  • Implement compress: normalize via z⁻¹ (one invert call, §13), pack y little-endian, OR the sign bit of x into bit 7 of the last byte (§8.5).
  • Implement decompress: recover x via the (p-5)/8-power square-root recipe of RFC 8032 section 5.1.3, reject y_bytes ≥ p (I1) and reject "not on curve" (no square root exists).
  • Implement is_small_order by comparing [8]P against the identity (I11, applied with ADR-10).

15.3 Deliverable

curve-edwards compiles no_std, exposes EdwardsPoint/CompressedEdwardsY (§11), passes differential tests against curve25519-dalek::EdwardsPoint for add/double/compress/decompress.

15.4 Acceptance Criteria

  • add bit-identical to curve25519-dalek::EdwardsPoint::add for 100,000 random point pairs.
  • double(P) == add(P, P) for 1,000 random points (M6 gate: double ≤ 50 ns amortized field-op cost).
  • Decompression of every basepoint multiple kB for k ∈ [0, 1024] (named fixture edwards.decompress_basepoint_multiples.json) succeeds and re-compresses byte-identically.
  • All 22 small-order points are flagged is_small_order() == true (named fixture edwards.small_order_22.json, Chalkias et al. 2020 corpus).

15.5 Conformance Fixtures

Fixture Purpose Expected Output

edwards.noncanonical_y.json y_bytes ≥ p inputs rejected, Error::NonCanonicalEncoding

15.6 Pitfalls

  • The constant 2d must be derived from the correct d = -121665/121666; a sign error here produces an addition law that is subtly wrong only for specific input combinations, not all of them.
  • Completeness (P3) holds only for a = -1 (this library's twisted Edwards choice, ADR-04) — a contributor porting a Weierstrass-style special case ("skip if P == Q") reintroduces a branch the whole point of HWCD-2008 was to remove.
  • decompress's square-root recipe has four cases (square, square×i, square×√-d, square×√-d×i, per RFC 8032 section 5.1.3 step 3) — omitting any one silently rejects valid points or accepts invalid ones depending on which case is missing.
  • Sign-bit recovery has an off-by-parity bug at x = 0 specifically — handle it as an explicit boundary case, not inferred from the general formula.

15.7 Performance Concerns

add/double are each called O(log L) times per scalar multiplication (§17) — 8 and 7 field multiplications respectively dominate the per-call cost; keeping intermediate FieldElement values in the 5-limb unsaturated form (never fully reducing mid-formula) avoids redundant carry propagation (P9).

15.8 Edge Cases

  • Adding the identity to any point must return that point unchanged (covered automatically by completeness, but must still be fixture-tested since a formula transcription error could break it silently).
  • Doubling a small-order point must not panic or divide by zero — extended coordinates avoid the affine 1/(2y)-style singularity Weierstrass doubling has at y=0.
  • Decompressing a 32-byte value with the sign bit set but x computing to exactly 0 requires the explicit-boundary handling from §15.6, not the general recipe.

15.9 Failure Analysis

A point-arithmetic bug manifests as signatures or shared secrets that are wrong only for a subset of inputs (those exercising the buggy code path), making it far harder to catch by chance than a uniformly-wrong field bug. Detection: the 100K-pair differential fixture (§15.4) and the 22-point small-order corpus are the two independent nets. Blast radius: every phase from 5 onward (scalar mult, both protocols). Recovery: bisect by input class — random points vs. small-order points vs. basepoint multiples — since each exercises a different code path.

15.10 Operational Notes

No runtime telemetry (pure function, I10). is_small_order results feed the decode_reject{reason="small_order"} counter once wired into the protocol layer (§20, §21); at this phase it is unit-tested in isolation via edwards.small_order_22.json.

16. Phase 4 — Montgomery Curve & the X25519 Ladder

16.1 Objectives

Implement MontgomeryU (§11) and the RFC 7748 constant-time ladder: the x-only differential add-and-double state machine that computes [scalar]·u in exactly 255 fixed-shape iterations regardless of the scalar's bits (P2, P9).

16.2 Detailed Implementation Steps

  • Represent points as (X:Z) projective, u = X/Z; precompute the curve constant a24 = (486662-2)/4 = 121665 once as a FieldElement (Bernstein 2006, applied here).
  • Implement the per-bit state transition of §8.4's table: conditional swap (ct_swap, itself two ct_select calls per limb, ADR-12) driven by swap_acc ^= scalar_bit, followed by the fixed 5-multiply-4-square differential add-and-double.
  • Iterate MSB→LSB over exactly 255 bits (bit 255 of a clamped scalar is always 0 by construction, I2) — the iteration count is a compile-time constant, never derived from the scalar's value (P2: a data-dependent loop bound is itself a timing leak).
  • After the loop, apply the final conditional swap and compute u_out = X2·Z2⁻¹ (one invert call, §13).
  • Implement MontgomeryU::from_bytes/to_bytes: mask the high bit of the last byte on decode (RFC 7748 section 5) — no other validity check is possible on a bare u-coordinate (§8.5), which is why I7/I11 exist at the protocol layer (§19) rather than here.

16.3 Deliverable

curve-montgomery compiles no_std, exposes the ladder (§11), passes the RFC 7748 section 5 worked example and the RFC 7748 section 6.1 iterated-ladder test.

16.4 Acceptance Criteria

  • ladder(clamp(a), 9) == A for the RFC 7748 section 5 X25519 example vector, bit-identical (named fixture montgomery.rfc7748_5_example.json).
  • The RFC 7748 section 5.2 iterated test (k applied to itself 1, 1,000, and 1,000,000 times) matches the published intermediate and final values exactly.
  • ladder executes in ≤ 30 µs (M1) with ≤ 5% timing variance across 10,000 random scalars on the CI reference core (constant-time acceptance signal, refined by dudect in §23).

16.6 Pitfalls

  • a24 must be 121665, derived as (486662-2)/4 — a transcription error here produces a ladder that is wrong for every input in a way that still looks like "a curve," making it a dangerous silent-wrong-answer bug, not a crash.
  • ct_swap implemented as two independent ct_select calls that are not both actually constant-time (e.g., one accidentally short-circuits) reintroduces exactly the side channel the ladder exists to close (P2).
  • Decoding the u-coordinate's high-bit mask (RFC 7748 section 5) is easy to skip by copy-paste from the Edwards decode path (§15), which has no such mask — the two decode paths must not be unified naively.

16.7 Performance Concerns

The ladder's 255 fixed iterations, each ~9 field multiplications, dominate X25519's cost (M1, ≤ 30 µs target, §4). Keep (X2,Z2,X3,Z3)'s working set (4 FieldElements, 160 B, §4) resident in L1; the ct_swap cost (two conditional 5-limb swaps) is negligible next to the 9 field muls per bit.

16.8 Edge Cases

  • u = 0 (a valid encoding, corresponds to the identity's "missing" x-coordinate under the birational map) must not cause a division-by-zero in the final X2·Z2⁻¹ — projective coordinates avoid this, but the fixture suite (§16.5) must exercise it explicitly.
  • A scalar of all-zero bits (after clamping, still has bit 254 set per I2) must still execute all 255 iterations — there is no valid clamped scalar that is the literal integer zero.
  • The 22 small-order u-coordinates (§16.5) must not crash the ladder; they produce a well-defined (typically zero or small-order) output that I7 rejects one layer up (§19).

16.9 Failure Analysis

A ladder bug is functionally indistinguishable from a field or point-arithmetic bug from the caller's perspective (wrong shared secret) — detection relies on the RFC 7748 vectors (§16.4) specifically, since they are the one oracle independent of this codebase's own field/point layers. Blast radius: every X25519 consumer (Phase 7 onward). Recovery: replay the RFC 7748 section 5.2 iterated test first — a mismatch at iteration 1 vs. iteration 1,000 localizes whether the bug is in the ladder step itself or in error accumulation across steps.

16.10 Operational Notes

No runtime telemetry (pure function). docs/architecture/montgomery-ladder.md documents the state-transition table (§8.4) as the canonical reference for anyone modifying this code, so a future SIMD port (deferred to the simd feature, ADR-11) preserves the same fixed-iteration discipline.

17. Phase 5 — Scalar Multiplication (Variable-Base, Fixed-Base, Double-Scalar)

17.1 Objectives

Implement the three Edwards-form scalar-multiplication algorithms of §8.4 on top of Phase 3's point arithmetic: variable-base (general use), fixed-base comb (signing, §20), and Straus double-scalar (verification, §21/§22).

17.2 Detailed Implementation Steps

  • Variable-base: build an 8-entry lookup table [P, 2P, ..., 8P], encode the scalar in radix-16 (32 nibbles), and for each nibble double 4 times then add the table entry selected via a constant-time 8-way ct_select — never a match on the nibble value (P2; a match compiles to a jump table, a textbook cache-timing leak).
  • Fixed-base comb: precompute B_TABLE[i][j] = (j+1)·16^(2i)·B for i∈[0,32), j∈[0,8) (§8.4); memoize the table exactly once via OnceLock (I8) since it depends only on the fixed basepoint. Walk the scalar's 32 radix-16 digits, one constant-time table lookup per digit, no doublings needed (the powers of 16 are baked into the table).
  • Double-scalar (Straus): compute [a]A + [b]B via a joint signed-digit representation so the doubling steps are shared between the two scalar multiplications rather than duplicated — applied directly to Ed25519 verification's [8s]B vs. [8]R+[8k]A comparison (§21).
  • Encode nibbles in signed form (9..15 → (nibble-16, carry +1 to the next digit)) to keep the lookup table at 8 entries instead of 16 — a well-known but error-prone transformation (Hankerson et al. 2004, §5, applied here).

17.3 Deliverable

curve-edwards::scalar_mul exposes variable-base, fixed-base, and double-scalar multiplication; fixed-base signing measurably outperforms variable-base on the same scalar/basepoint pair.

17.4 Acceptance Criteria

  • scalar_mul([1], B) == B; scalar_mul(L, B) == identity (named fixtures scalar_mul.identity_cases.json).
  • scalar_mul(s, B) bit-identical to curve25519-dalek's equivalent for 1,000 random scalars.
  • Fixed-base signing scalar multiplication is ≥ 4× faster than variable-base on the same input (M8 vs. M7 ratio, §32).
  • Double-scalar [a]A+[b]B matches two independent variable-base calls added together, for 1,000 random (a,A,b,B) tuples.

Fixture Purpose Expected Output

17.6 Pitfalls

  • A match nibble { 0 => ..., 1 => ... }-style table lookup, however tempting for readability, compiles to a branch/jump table on most targets and is a P2/ADR-06 violation caught only by a dudect audit (§23), not by functional tests — treat any non-ct_select table access as an automatic review rejection.
  • Signed-NAF digit encoding's carry propagation (9..15 → nibble-16, +1 next) is a common off-by-one source; a missed carry into the 33rd (overflow) digit corrupts the topmost bits of the result only for scalars near L.
  • Regenerating the fixed-base comb table on every call instead of caching it via OnceLock (I8) is both a ~5× performance regression and, if the regeneration path has any non-determinism, a correctness bug.

17.7 Performance Concerns

Fixed-base comb trades ~24 KiB of static memory (§4) for ~5× throughput (M8 ≤ 25 µs vs. M7 ≤ 80 µs) by eliminating doublings entirely — the right trade for signing, where the basepoint is always the same, but inapplicable to verification's A (an arbitrary public key), which is why double-scalar (Straus) rather than a second comb table is used there (public keys are not precomputable ahead of time in the general case).

17.8 Edge Cases

  • Scalar = 0: variable-base and fixed-base must both return the identity without a divide-by-zero or a table-index-out-of-bounds (digit 0 selects "no addition" via ct_select on an identity sentinel, not a skipped branch).
  • Scalar = L-1 (maximal canonical value): the top radix-16 digit must be handled without overflowing the 32-digit encoding.
  • Double-scalar with A a small-order point: Straus's algorithm must not special-case this — completeness (P3) means it produces a well-defined (algebraically correct, if security- irrelevant) result that the caller's small-order check (I11) rejects independently.

17.9 Failure Analysis

A scalar-multiplication bug is the second-most severe class after a field bug (§13.9) because it is exercised by every sign/verify call. Detection: the identity-case fixtures (§17.4) catch gross errors immediately; the 1,000-random-scalar differential catches subtler ones. Blast radius: Phases 8–10 (signing, verification, batch). Recovery: isolate variable-base vs. fixed-base vs. double-scalar by running each fixture bucket independently — a failure in only one narrows the search to that algorithm's specific table/encoding logic.

17.10 Operational Notes

No runtime telemetry (pure function). The fixed-base table's one-time ≤ 5 ms precompute cost (§4, I8) is logged once at process startup in the CLI (curve-cli, §22) for operator visibility, not gated as a metric.

  • Treating "no square root exists" and "square root exists but sign bit mismatches after correction" as the same error code loses forensic information an on-call engineer needs (§28) — keep them distinct in DecodeError even though both currently map to rejection.
  • A partial implementation of the four-case square-root recipe (e.g., only handling the "square" and "square×i" cases, which cover most random test inputs) passes casual testing but fails specifically on the crafted Chalkias/Wycheproof corpus entries designed to hit the other two cases.
  • Reordering the I1 canonical check after the square-root computation instead of before wastes a mul/invert on inputs that will be rejected anyway and, worse, risks the square-root routine behaving unpredictably on out-of-range input if it assumes canonical y.

18.7 Performance Concerns

decompress costs one invert (§13, the single most expensive field op) plus the four-case selection overhead — called once per verification (§21) and once per X25519 peer-key decode is not applicable (Montgomery u has no such check, §8.5); the cost is isolated to the Edwards path only, keeping X25519's decode cheap by contrast.

18.8 Edge Cases

  • y = 0 and y = 1 (curve boundary values) must decode without the general four-case recipe misfiring.
  • The sign-bit-vs-x=0 interaction flagged in §15.6 is re-verified here against the full Chalkias/Wycheproof corpus, not just the hand-picked case from Phase 3.

18.9 Failure Analysis

A hardening gap here (an unhandled square-root case, or a missed non-canonical rejection) is a security-relevant bug even though it may never surface in normal operation — it is only exercised by an adversarial input. Detection: the Chalkias/Wycheproof negative corpora are the sole reliable net (§18.4); random fuzzing (§24) rarely stumbles onto the specific bit patterns these corpora encode. Recovery: a decode-layer regression is a release blocker (P10) — it directly implies T3/T4 exposure (§26).

18.10 Operational Notes

Every rejection increments decode_reject{reason=...} (I1/I11's telemetry contract, §7); docs/runbook/conformance-failure.md documents how to read a new Wycheproof/Chalkias corpus release diff against this phase's fixture set when either project publishes new negative cases.

19. Phase 7 — X25519 Key Agreement Protocol

19.1 Objectives

Build the public x25519 crate surface (§11: SecretKey, PublicKey, SharedSecret, diffie_hellman) on top of Phases 1–4's ladder, enforcing I2 (clamping), I7 (zero-secret rejection), and I11 (small-order rejection) at the API boundary — this is the first phase where a caller-facing trust boundary exists (§3).

19.2 Detailed Implementation Steps

  • SecretKey::generate accepts a caller-supplied CryptoRng (never reads global state or an internal RNG, keeping randomness sourcing an explicit caller responsibility, Wong 2021 applied here) and clamps the raw bytes immediately into a ClampedScalar (I2).
  • SecretKey::public_key computes ladder(self, basepoint_u=9) (§16) and wraps the result as PublicKey.
  • diffie_hellman computes ladder(self, peer.0), then checks the 22-small-order-key table (I11, ADR-10) against the peer's raw encoding before running the ladder (cheap, catches known- bad keys early) and checks the ladder's output against zero after (I7, catches any small- order key not in the explicit table, defense-in-depth per P11).
  • Return Result<SharedSecret, AgreeError> — AgreeError::SmallOrderPeerKey or AgreeError::ZeroSharedSecret — never a bare SharedSecret the caller might use unchecked (P13).

19.3 Deliverable

x25519 crate compiles, exposes the full ECDH surface, passes RFC 7748 section 6.1 and Wycheproof's x25519_test.json including every "should_reject" case.

19.4 Acceptance Criteria

  • RFC 7748 section 6.1's worked example matches bit-for-bit (named fixture x25519.rfc7748_6_1.json).
  • All Wycheproof x25519_test.json cases pass, including the 22 small-order-key rejections (M-x25519 milestone gate, Appendix B).
  • Commutativity property (§8.6): dh(a, B) == dh(b, A) holds for 1,000 random (a,b) pairs.
  • diffie_hellman completes in ≤ 30 µs (M1) end-to-end including both small-order checks.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
x25519.rfc7748_6_1.json RFC 7748 section 6.1 worked example bit-identical
x25519.wycheproof_full.json full Wycheproof x25519_test.json all cases pass
x25519.commutativity_1e3.json dh(a,B)==dh(b,A) holds for 1,000 pairs
x25519.small_order_all22.json all 22 small-order peer keys Err(SmallOrderPeerKey) or Err(ZeroSharedSecret)

19.6 Pitfalls

  • Reading randomness from a global/thread-local RNG instead of requiring a caller-supplied CryptoRng hides a broken-RNG dependency inside this crate instead of surfacing it as the caller's responsibility (Ferguson-Schneier-Kohno 2010 applied here).
  • Checking only the pre-ladder small-order table (I11) and skipping the post-ladder zero-check (I7), or vice versa, leaves a gap: the table only covers 22 known encodings, while the zero-check is the general-purpose net (P11's defense-in-depth is not redundant, it is complementary).
  • Returning SharedSecret directly instead of Result<SharedSecret, AgreeError> pushes the zero-check onto every caller, and history (this exact bug class) shows most callers forget it.

19.7 Performance Concerns

The two small-order checks add negligible cost (a 22-entry table compare pre-ladder, one FieldElement::ct_eq against zero post-ladder) next to the ladder's 255 iterations — well within the ≤ 30 µs (M1) budget; no further optimization is needed at this layer beyond what Phase 4 already provides.

19.8 Edge Cases

  • A peer key that is a valid, non-small-order point but happens to produce a shared secret with many leading zero bytes (not the all-zero value I7 checks) must not be treated as suspicious — I7's check is exact equality to zero, not a heuristic.
  • Concurrent diffie_hellman calls sharing no state (I10) must produce identical results to sequential calls — verified by the concurrent-verification-style stress test adapted for ECDH.

19.9 Failure Analysis

A missed small-order rejection here is a direct T4-class vulnerability (§26): an attacker who can supply a peer public key can force a predictable (often zero) shared secret, breaking confidentiality of anything derived from it. Detection: the Wycheproof x25519_test.json negative cases (§19.4) are the primary net; a production incident would surface as "two parties' shared secrets don't match" or "a third party derived the same shared secret," either being a P0. Recovery: patch + re-run the full Wycheproof corpus before any re-release.

19.10 Operational Notes

agree_reject{reason=...} (I7's telemetry) is the operator-facing signal (§28) — a spike indicates either a misbehaving/malicious peer or a protocol-layer bug feeding bad keys into this API. docs/runbook/triage.md documents the first three things to check on such a spike.

20. Phase 8 — Ed25519 Key Generation & Signing

20.1 Objectives

Build SigningKey::from_seed and SigningKey::sign (§11): SHA-512 key expansion, deterministic nonce derivation (RFC 8032 section 5.1.6, I3), and the s = r + k·a mod L signature equation, all on top of Phases 1–5.

20.2 Detailed Implementation Steps

  • from_seed: expansion = SHA-512(seed); the low 32 bytes, clamped exactly as X25519's I2 clamping (clear bits 0-2, clear bit 255, set bit 254), become the secret scalar a; the high 32 bytes become the nonce_prefix — critically, the clamping is applied to the expansion, not to the raw seed itself (a documented RFC 8032 section 5.1.5 subtlety, applied here).
  • Compute the public key once at construction: A = [a]B via the fixed-base comb (§17, P9), never recomputed per-sign.
  • sign(message): derive r = SHA-512(nonce_prefix ‖ message) mod L via wide reduction (§14, I3) — this is where determinism (P7, ADR-09) replaces any RNG call.
  • Compute R = [r]B (fixed-base comb, §17); compute the challenge k = SHA-512(R ‖ A ‖ message) mod L; compute s = r + k·a mod L (Barrett arithmetic, §14).
  • Return Signature{r: R.compress(), s} (§11) — never expose r (the nonce scalar) or a (the secret scalar) outside the SigningKey's zeroized storage (P6, I5).

20.3 Deliverable

ed25519::SigningKey compiles, exposes from_seed/sign/sign_prehashed, reproduces every RFC 8032 section 7.1 test vector bit-for-bit.

20.4 Acceptance Criteria

  • All RFC 8032 section 7.1 test vectors (1–4 for Ed25519, plus the Ed25519ph vector) reproduce the published signature bytes exactly (M-ed25519 milestone gate, Appendix B).
  • sign completes in ≤ 30 µs (M2) with ≤ 5% timing variance across 1,000 distinct messages of the same length (a coarse pre-dudect constant-time signal, refined in §23).
  • Signing the same (key, message) pair twice produces byte-identical signatures (determinism check, I3).
  • SigningKey never implements Debug (compile-time check via a static_assertions-style negative trait-bound test, P6).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
ed25519.rfc8032_7_1_vectors.json RFC 8032 section 7.1 Tests 1–4 + Ed25519ph bit-identical signatures
ed25519.determinism_1e3.json same (key, msg) signed 1,000× byte-identical every time
ed25519.sign_timing_smoke.json coarse timing variance across message lengths ≤ 5% variance
ed25519.no_debug_compile_check.json SigningKey: !Debug compiles only if true

20.6 Pitfalls

  • Clamping the raw seed instead of the SHA-512 expansion's low half is the single most common from-scratch Ed25519 bug — it produces a key that signs internally-consistently but never matches another implementation's output for the same seed.
  • Using SHA-512(seed)'s low bytes for the nonce prefix and the high bytes for the scalar (the two halves swapped) similarly self-consistent-but-wrong.
  • Recomputing the fixed-base comb table (§17) inside sign instead of relying on the process- wide memoization (I8) turns every signature into a ~5× slower operation.
  • Any code path that derives r from a source other than SHA-512(nonce_prefix‖message) — including "for testing, let me just use a random nonce" left in accidentally — reintroduces the exact LadderLeak-class vulnerability (T2, Aranha et al. 2020) determinism exists to close.

20.7 Performance Concerns

Signing costs two fixed-base scalar multiplications ([r]B and the already-cached A=[a]B) plus two SHA-512 calls and one scalar multiply-add mod L — dominated by the ≤ 25 µs (M8) fixed-base cost, well inside the ≤ 30 µs (M2) budget; no additional optimization is load-bearing here beyond Phase 5's comb table.

20.8 Edge Cases

  • Empty message (message.len() == 0) must sign/verify correctly — RFC 8032 places no minimum length requirement.
  • A message long enough to require streaming (multi-gigabyte) is out of scope for plain Ed25519's single-pass API design; Ed25519ph (sign_prehashed, ADR-17) exists precisely for callers who cannot hold the whole message in memory to hash twice.
  • Signing with a seed of all-zero bytes must produce a well-defined, non-degenerate key (no special-case rejection exists in RFC 8032 for a zero seed, and the SHA-512 expansion ensures the derived scalar is not literally zero).

20.9 Failure Analysis

A signing bug either produces a signature that fails to verify against its own public key (caught immediately by the RFC vectors, §20.4) or, more dangerously, produces a signature that verifies but leaks information about a through the deterministic nonce's derivation (caught only by a side-channel audit, §23, not by functional tests). Detection: RFC 8032 vector replay for functional bugs; dudect for the timing class. Blast radius: every consumer of this SigningKey (§21 verification depends on well-formed signatures, but a signing-side timing leak compromises the secret key directly, worse than a verification-side bug). Recovery: rotate the compromised key; the deterministic-nonce design means no "reused nonce" forensic signal exists the way it does for ECDSA, so detection must come from the timing audit, not from observing signature outputs.

20.10 Operational Notes

No runtime telemetry for signing itself (a pure function on secret data — emitting metrics about signing frequency is a caller-layer decision, out of scope here to avoid creating a side channel via timing-correlated telemetry emission). docs/architecture/verification-modes.md cross- references this phase's nonce derivation for anyone auditing the constant-time property.

21. Phase 9 — Ed25519 Verification (Strict, Lax, Cofactor-Aware)

21.1 Objectives

Implement VerifyingKey::verify_strict and verify_lax (§11): decode-time canonical checks (I1, I6, I11), the cofactor-aware equation [8h]A + [8R] = [8s]B (P8, ADR-08), and the lax-verify feature-gated alternative (P4, ADR-07).

21.2 Detailed Implementation Steps

  • Decode A and R via CompressedEdwardsY::decompress (§18) — strict mode propagates any DecodeError immediately (I1); reject sig.s if !is_canonical() (I6).
  • Reject if A.is_small_order() || R.is_small_order() in strict mode (I11, P11) — lax mode skips this check, matching RFC 8032 section 8.3's documented "cofactored, non-strict" behavior for legacy interop (ADR-07).
  • Compute k = SHA-512(R ‖ A ‖ message) mod L via wide reduction (§14) — identical derivation to signing's challenge (§20), applied here as the verifier's recomputation of the same value.
  • Compute the cofactor-scaled equation via Straus double-scalar (§17): lhs = [8s]B (fixed-base, scaled by 8 first or folded into the digit encoding), rhs = [8]R + [8k]A (double-scalar on A, R pre-scaled by the cofactor) — compare lhs.compress() == rhs.compress() (P8).
  • verify_lax computes the unscaled equation hA + R = sB and skips the I6/I11 pre-checks, gated behind the lax-verify Cargo feature so it can never be reached in a default build (ADR-07).

21.3 Deliverable

ed25519::VerifyingKey::verify_strict reproduces RFC 8032 section 7.1's verification results, rejects 100% of the Chalkias et al. (2020) should_reject corpus, and accepts every Wycheproof positive case.

21.4 Acceptance Criteria

  • RFC 8032 section 7.1 Tests 1–4 verify successfully under verify_strict (M-ed25519 gate).
  • 100% of Chalkias et al. (2020)'s malleability/cofactor-edge-case corpus marked "should_reject" is rejected by verify_strict (M-chalkias milestone, Appendix B).
  • 100% of Wycheproof eddsa_test.json cases pass under the mode (strict/lax) the vector's flags indicate.
  • verify_strict completes in ≤ 60 µs (M3).

21.5 Conformance Fixtures

Fixture Purpose Expected Output
ed25519.rfc8032_verify_7_1.json RFC 8032 section 7.1 verification all pass
ed25519.chalkias_should_reject.json malleability/cofactor corpus 100% rejected under strict
ed25519.wycheproof_eddsa_full.json full Wycheproof EdDSA corpus matches expected per-case mode
ed25519.strict_vs_lax_divergence.json inputs where strict/lax disagree documented divergence matches ADR-07

21.6 Pitfalls

  • Implementing the naive (non-cofactor-scaled) equation hA+R=sB as the strict-mode default instead of the [8]-scaled form reintroduces exactly the small-subgroup confusion ADR-08 exists to close — this is the single highest-value correctness check in the whole verification path.
  • Applying the [8] scaling to R and A but forgetting to also scale B's side (s multiplied by 8, or equivalently the whole equation scaled consistently) produces an equation that "usually" passes (both sides wrong by the same factor for prime-order inputs) but silently breaks the small-subgroup defense for contaminated inputs.
  • Sharing a single verify function with an internal boolean flag for strict/lax instead of two distinct, feature-gated entry points (ADR-07) risks a caller accidentally passing the wrong flag at a call site with no compile-time signal.
  • Not rejecting s ≥ L (I6) before the cofactor equation lets a non-canonical s alias to a canonical one after implicit reduction inside the scalar-mul code, reproducing the exact Chalkias et al. (2020) malleability vector (§8.8).

21.7 Performance Concerns

Verification's cost is dominated by one decompress (one invert, §18) plus one double-scalar multiplication (§17) — together the ≤ 60 µs (M3) budget; batch verification (§22) exists specifically because this single-signature cost does not amortize across many signatures without it.

21.8 Edge Cases

  • A and R both small-order simultaneously must still be caught by the I11 check applied to each independently — do not assume checking one implies the other is fine.
  • A signature where s = 0 is not itself invalid per RFC 8032 (canonical, < L) — the equation check alone determines validity; no special-case rejection of s=0 exists or should be added.
  • verify_lax accepting a signature that verify_strict rejects on the same (key, message, signature) triple is expected, documented behavior (ADR-07), not a bug — the divergence fixture (§21.5) exists to make this explicit and regression-tested, not to eliminate it.

21.9 Failure Analysis

A verification bug that accepts something it should reject (a missing I1/I6/I11 check, or a naive cofactor equation) is the most severe failure class in this entire blueprint — it directly enables forgery-adjacent attacks (T3, T4, §26). Detection: the Chalkias/Wycheproof negative corpora (§21.4) are non-negotiable release gates (P10). A verification bug that rejects valid signatures is an availability bug (still I12-relevant) but strictly less severe. Recovery: any strict-mode false-accept is a P0 security incident requiring immediate patch + re-audit of every prior release for the same gap.

21.10 Operational Notes

decode_reject{reason=...} and a new verify_reject{reason="equation_mismatch"} counter (§7, §28) are the operational signals; a sudden rise in the latter across many distinct keys suggests a corrupted-signature bug upstream (e.g., a transport-layer bit flip) rather than an attack, while a rise in small_order/non_canonical rejections concentrated on one key suggests active probing (§26 Threat Model).

22. Phase 10 — Batch Verification & Public API Surface

22.1 Objectives

Implement verify_batch (§11, I13) and assemble the top-level public API (ed25519::*, x25519::* re-exports) plus the curve-cli operator tool (§10).

22.2 Detailed Implementation Steps

  • Batch equation (§8.4, applied per Bernstein-Lange-Schwabe-style batching, cited generally under the ADR-06 scalar-mult family): draw uniform random ~128-bit coefficients z_i per signature (never attacker-influenced — drawn by the verifier), then check [Σ z_i·s_i]B = Σ (z_i·R_i) + Σ (z_i·k_i)·A_i as one combined multi-scalar multiplication via Straus (§17) with 2N+1 bases, rather than N independent double-scalar calls.
  • Prove/document I13's soundness argument inline: a forged signature slipped into the batch is caught with probability ≥ 1 - 2⁻¹²⁸ over the verifier's random z_i draw — state this explicitly in the module doc since it is the one place in this blueprint where a probabilistic (not absolute) guarantee is load-bearing.
  • Assemble the public re-export surface: ed25519::{SigningKey, VerifyingKey, Signature, verify_batch}, x25519::{SecretKey, PublicKey, SharedSecret} — no internal field/scalar/point types are exported (encapsulation boundary, §3).
  • Build curve-cli subcommands: ed25519 keygen|sign|verify, x25519 keygen|agree, each a thin wrapper that reads/writes raw byte files and calls the library API — no cryptographic logic lives in the CLI itself (P10: the CLI is not a separate implementation to keep in sync).

22.3 Deliverable

verify_batch is measurably faster than N serial verifications; the public API surface compiles as the sole external interface (internal crates are not exported); curve-cli round-trips keygen→sign→verify and keygen→agree for both algorithms.

22.4 Acceptance Criteria

  • Batch verification of 64 valid signatures completes in ≤ 800 µs (M4, ≥ 80,000 verify/s/core).
  • A batch containing exactly one forged signature is rejected with probability ≥ 1 − 2⁻¹²⁸ over 1,000,000 trial batches with independently redrawn z_i (statistical fixture, not a single assertion — named ed25519.batch_forgery_detection_1e6.json).
  • curve-cli ed25519 sign piped into curve-cli ed25519 verify round-trips successfully for 1,000 random messages.
  • No internal crate type (FieldElement, Scalar, EdwardsPoint, etc.) is reachable from the public ed25519/x25519 crate root (a cargo public-api diff check).

22.5 Conformance Fixtures

Fixture Purpose Expected Output
ed25519.batch_consistency_1e3.json batch vs. serial verify on honest inputs identical accept/reject per signature
ed25519.batch_forgery_detection_1e6.json one forged sig in 64-batch, 10⁶ trials detected with probability ≥ 1−2⁻¹²⁸
ed25519.batch_speedup_vs_serial.json timing ratio ≥ 3× at N=64
cli.roundtrip_sign_verify.json CLI keygen→sign→verify success for 1,000 messages

22.6 Pitfalls

  • Drawing z_i from anything attacker-influenced (e.g., derived from the signature bytes themselves rather than the verifier's own RNG) breaks I13's soundness argument entirely — this is a subtle enough mistake that it is worth a dedicated code-review checklist item.
  • Exporting internal types "just for testing convenience" from the public crate root violates the encapsulation boundary (§3) and turns an internal refactor into a semver-breaking change (§29).
  • A CLI that re-implements even a small piece of cryptographic logic (e.g., its own file-format- specific hashing) instead of delegating everything to the library risks the CLI and library drifting apart — the CLI must be provably "just I/O plus API calls."

22.7 Performance Concerns

Batch verification's ≥ 3× speedup at N=64 (§22.4) comes from sharing the [Σ...]B fixed-base term and combining the 2N variable-base terms into one multi-scalar multiplication (§17) — the speedup grows with N up to the point where the 2N+1-way table/lookup overhead itself dominates (§33 Scalability Analysis discusses the ceiling).

22.8 Edge Cases

  • Batch size N=1 must degrade gracefully to (and be no slower than) single-signature verify_strict — no batching overhead should be paid for a trivial batch.
  • A batch containing a signature whose A or R is small-order must be rejected exactly as it would be under verify_strict applied individually — batching must not weaken the strict-mode guarantees (I11 still applies per-signature before the combined equation).
  • Duplicate signatures within the same batch (same key, message, signature repeated) must each be independently checkable — the batch equation must not have order-dependent behavior.

22.9 Failure Analysis

A soundness bug in batch verification (accepting a batch containing a forgery) is as severe as a Phase 9 verification bug (§21.9) but harder to detect because it is probabilistic — a single failing fixture run might be statistical noise rather than a real bug. Detection: the 10⁶-trial statistical fixture (§22.4) is designed to have overwhelming power against a real soundness bug while tolerating true-random variance. Recovery: any statistically significant deviation from the expected ≥ 1−2⁻¹²⁸ detection rate blocks release and triggers a re-derivation of the batch equation from first principles (§8.4), not just a code review.

22.10 Operational Notes

batch_verify_mismatch (I13's telemetry) must stay at exactly 0 in production — any nonzero value is paged immediately (§28) as a possible active-forgery-attempt signal or a soundness regression, not treated as routine noise. PhaseDeferred(§22): HSM/PKCS#11 integration is anchored here as the natural extension point for key custody (§39).

23. Phase 11 — Constant-Time & Side-Channel Hardening

23.1 Objectives

Audit and gate the constant-time property (P2, I4) across every layer with cargo miri test and a dudect statistical timing harness, closing the gap between "structurally constant-time by construction" and "verified constant-time in the compiled artifact" (Mental Model MM7, §34).

23.2 Detailed Implementation Steps

  • Run cargo miri test across the full workspace to catch undefined behavior that could produce compiler-introduced branches on secret data (a miri-clean build is necessary, not sufficient, for constant-time — applied per Ferguson-Schneier-Kohno 2010's implementation-pitfalls chapter, §5).
  • Instrument x25519::diffie_hellman, ed25519::sign, and curve-edwards::scalar_mul with the dudect methodology (fixed-vs-random input classes, Welch's t-test) — target t ≤ 4.5 (M9) over ≥ 10⁷ measurement pairs per function (ADR-22).
  • Inspect the compiled artifact (objdump/cargo asm) for the ladder's inner loop and the fixed-base comb lookup specifically, confirming no conditional jump instruction depends on secret-derived register values — the optimizer is treated as an adversary (MM7), not trusted from source-level review alone.
  • Gate the optional simd feature crate (ADR-11) with the same dudect harness, since SIMD intrinsics introduce a second, independently-reviewed unsafe surface where the constant-time property must be re-verified, not assumed inherited from the scalar path.

23.3 Deliverable

cargo miri test passes with zero UB reports; dudect reports t ≤ 4.5 for all three target functions; the compiled-artifact inspection report is checked into audits/timing/.

23.4 Acceptance Criteria

  • cargo miri test exits 0 across the workspace (M-time gate component).
  • dudect t-statistic ≤ 4.5 (M9) for x25519::diffie_hellman, ed25519::sign, and curve-edwards::scalar_mul, each over ≥ 10⁷ measurement pairs.
  • The objdump inspection report documents zero secret-dependent conditional branches in the ladder's inner loop and the comb lookup (named artifact audits/timing/objdump-ladder-2026-Q3.md).
  • The simd-feature build passes the identical dudect gate independently.

23.5 Conformance Fixtures

Fixture Purpose Expected Output
timing.dudect_x25519.json dudect run on diffie_hellman t ≤ 4.5
timing.dudect_ed25519_sign.json dudect run on sign t ≤ 4.5
timing.dudect_scalar_mul.json dudect run on variable-base scalar_mul t ≤ 4.5
timing.miri_workspace.json full-workspace miri run 0 UB reports

23.6 Pitfalls

  • A dudect run with too few measurements (< 10⁷) produces a t-statistic that looks passing by chance — the ≥ 10⁷ floor (M9) is not arbitrary, it is the threshold at which the test has statistical power against a realistic leak magnitude.
  • Compiler auto-vectorization or LTO can restructure "obviously constant-time" source into a branchy compiled artifact — this is exactly why the objdump inspection step exists independent of the dudect statistical test (MM7); rely on both, not either alone.
  • Testing only the "happy path" input distribution (uniform random scalars) misses timing variance triggered specifically by small-order or boundary-value inputs — dudect's fixed-vs-random methodology must include the boundary/small-order corpus as one of its "fixed" classes.

23.7 Performance Concerns

The hardening pass itself adds no runtime cost to the shipped binary (it is a verification activity, not a code change) — but any fix it necessitates (e.g., replacing a branch with a ct_select) typically costs a small, bounded number of extra field operations, tracked against the M1–M8 latency budgets to confirm no regression past the +10% tolerance the release process allows (§31).

23.8 Edge Cases

  • dudect must include the small-order/boundary-value corpora (§15–§19) as explicit "fixed" input classes, not only uniform-random scalars, since a side channel specific to boundary handling would otherwise never be exercised.
  • The simd feature's unsafe intrinsics must be audited for the case where the CPU lacks the targeted instruction set at runtime (a cfg/is_x86_feature_detected! fallback) — a missing fallback is a correctness bug, not just a performance one, if it causes an illegal-instruction crash (P13).

23.9 Failure Analysis

A timing-side-channel regression is invisible to every functional/conformance test in Phases 0–10 — it is caught only by this phase's methodology, which is why it is a dedicated phase rather than folded into each earlier one. Detection: dudect's t-statistic crossing 4.5 in CI (M9 gate). Blast radius: any deployment where an attacker can measure operation latency (network timing, shared-cache co-tenancy) — directly enables T1 (§26). Recovery: bisect the regression to the specific commit via dudect's per-commit CI run (ADR-22), then replace the offending branch/ lookup with its constant-time equivalent and re-run the full 10⁷-measurement gate.

23.10 Operational Notes

timing/results/ accumulates one dudect report per release (§28); a release cannot tag Sealed (Appendix B) without a green M9 report attached. docs/architecture/*.md files (§10) each note which functions this phase's audit covers, so a future contributor adding a new public function knows to extend the dudect harness rather than assuming existing coverage transfers.

24. Phase 12 — Conformance, Fuzzing & Differential Testing Harness

24.1 Objectives

Assemble the full conformance/runner corpus (§30) into a single CI-gated suite, stand up cargo-fuzz targets (ADR-23) for the parsing/decoding boundary, and run the 24-hour and 30-day fuzz canaries (M11, M12) that gate Sealed.

24.2 Detailed Implementation Steps

  • Wire every corpus from Phases 1–10 (field.*, scalar.*, edwards.*, montgomery.*, x25519.*, ed25519.*, scalar_mul.*) into one conformance/runner invocation producing a single pass/fail report (P10) — no phase's fixtures are allowed to silently stop running once a later phase begins.
  • Build five cargo-fuzz targets (§10): ed25519_verify, ed25519_sign_verify (round-trip), x25519_agree, parse_signature, parse_public_key — each seeded with the Wycheproof/Chalkias corpora as the initial fuzz corpus (coverage-guided fuzzing starting from known-interesting inputs, ADR-23 applied here).
  • Run a 24-hour canary (M11) as a release-candidate gate: zero panics, zero memory growth (tracked via /proc RSS sampling every 60s).
  • Run a 30-day canary (M12) as the Sealed-tag gate — a longer-horizon fuzz run intended to surface the rare, deep-state bugs the 24-hour run's coverage doesn't reach.
  • Wire conformance.yml/fuzz.yml (§10 CI workflows) so both suites run automatically on every release-candidate tag, not only on developer request.

24.3 Deliverable

A single make conformance target replays every named fixture from Phases 0–10 and reports one aggregate pass/fail; make fuzz-24h and the scheduled 30-day canary both produce a signed report under audits/fuzz/.

24.4 Acceptance Criteria

  • conformance/runner's aggregate report shows 100% pass across every corpus bucket named in §30's table (M-field through M-batch milestones, Appendix B).
  • 24-hour fuzz canary: 0 panics, RSS growth < 1% over the run (M11).
  • 30-day fuzz canary: 0 panics across all five targets (M12, Sealed gate).
  • Full conformance suite wall-clock ≤ 5 minutes (M10) so it can run on every PR, not only nightly.

24.6 Pitfalls

  • Letting an earlier phase's fixture bucket silently drop out of the aggregate report (e.g., a CI refactor that only re-wires the newest phase's fixtures) is a regression that passes CI while actually testing less than before — the aggregate report's bucket count, not just its pass/fail, must be checked against a known-good baseline.
  • Seeding fuzz targets from scratch instead of from the Wycheproof/Chalkias corpora wastes the first many CPU-hours of a fuzz run rediscovering already-known edge cases instead of exploring new state.
  • Treating the 24-hour canary as sufficient for Sealed skips exactly the deep, rare-state bugs the 30-day canary exists to surface — the two canaries gate different milestones (Appendix B) for this reason and neither substitutes for the other.

24.7 Performance Concerns

The ≤ 5-minute full-suite wall-clock (M10) is itself a load-bearing constraint: a slower suite gets skipped or run less frequently by contributors under time pressure, silently weakening P10's "conformance is the contract" principle — keeping the suite fast is a correctness-adjacent performance requirement, not a nice-to-have.

24.8 Edge Cases

  • A fuzz target that finds a crash must produce a minimized, checked-in regression corpus entry (not just a bug report) so the specific input is permanently part of conformance/corpora/ going forward — a fixed fuzz-found bug that regresses silently is a process failure.
  • Fuzzing parse_signature/parse_public_key must include truncated and over-long byte strings, not only well-formed-but-wrong-value inputs — malformed-length inputs are a distinct edge-case class from malformed-value inputs (§18).

24.9 Failure Analysis

A conformance-suite regression (a bucket silently dropping out, §24.6) is a process failure with no immediate production symptom — it is caught only by comparing the aggregate report's bucket count against history (§24.4). A fuzz-found panic is a direct I12/P13 violation; blast radius is "any caller supplying that specific malformed input," detection is immediate (the canary itself crashes), and recovery is a P0 patch + regression-corpus addition (§24.8) before the next canary run.

24.10 Operational Notes

audits/fuzz/canary-24h.md and canary-30d.md are the two artifacts release engineering (§31) checks before advancing a release-candidate tag to Sealed (Appendix B); docs/runbook/ conformance-failure.md documents the triage order (bucket-count check → per-bucket diff → bisect) for a red aggregate report.

25. Phase 13 — Release Engineering, Packaging & Audit Readiness

25.1 Objectives

Close the loop from "passes every internal gate" to "ready to ship": reproducible builds, SBOM generation, artifact signing, and the external-audit engagement package (§31).

25.2 Detailed Implementation Steps

  • Pin Cargo.lock and rust-toolchain.toml (ADR-24) for every release tag; run cargo build --locked twice on independent CI runners and diff the resulting binaries byte-for-byte (reproducibility gate).
  • Generate an SBOM (cargo-cyclonedx or equivalent) enumerating every dependency, its version, and its license, cross-checked against deny.toml's policy (ADR-24).
  • Sign release artifacts (cargo-crest/sigstore cosign or a project-chosen signing tool) and publish the signature alongside the crate on crates.io and as a GitHub release asset.
  • Assemble the external-audit package under audits/reviews/<date>-<firm>/: this document, the §16 self-verification results if applicable to the implementation review, the dudect/fuzz reports (§23, §24), and a scope statement excluding the deferred features (§39).
  • Tag the release Sealed (Appendix B) only after: 30-day fuzz canary green (M12), external audit findings triaged to zero P0/P1, and the reproducible-build diff clean.

25.3 Deliverable

A signed, reproducible release artifact on crates.io with an attached SBOM; an audit-ready package under audits/reviews/; the Sealed milestone tag applied only once all gates are green.

25.4 Acceptance Criteria

  • Two independent CI runners produce byte-identical release binaries (reproducibility gate, named fixture release.reproducible_build_diff.json).
  • SBOM lists 100% of transitive dependencies with license metadata, zero cargo-deny policy violations.
  • Release artifact signature verifies against the published public key.
  • Sealed tag is applied only when M11, M12, and the external audit's P0/P1 count are all green simultaneously (Appendix B gate).

25.6 Pitfalls

  • A "reproducible" build that actually depends on an unpinned environment variable (build timestamp, absolute path embedded via debug_assertions) fails the byte-identical diff intermittently — chase this down to a fully hermetic build environment (containerized CI, SOURCE_DATE_EPOCH pinning) rather than accepting "usually reproducible."
  • Publishing the SBOM without cross-checking it against deny.toml risks a license-policy violation shipping silently — the two must be generated from the same Cargo.lock in the same CI step, not as separate, potentially-drifted processes.
  • Tagging Sealed before the 30-day canary (M12) completes, under release-schedule pressure, is the single most common process shortcut that undermines this entire blueprint's evidence-based release discipline (P10) — there is no override for this gate.

25.7 Performance Concerns

None specific to this phase beyond ensuring the release build itself uses the production optimization profile (opt-level=3, LTO enabled) that the M1–M8 latency targets were measured against — a release built with a different profile than the one benchmarked invalidates every prior performance acceptance criterion.

25.8 Edge Cases

  • A dependency yanked from crates.io between the pinned Cargo.lock and the release build must be caught by cargo build --locked failing loudly, not silently falling back to a different version.
  • An external auditor finding a P2/P3 (non-blocking) issue must still be logged and tracked (not discarded) even though it does not block Sealed — it becomes input to the next release cycle.

25.9 Failure Analysis

A non-reproducible build is a supply-chain-integrity failure with no immediate functional symptom — detection is the byte-diff gate (§25.4) itself; blast radius is "every consumer's trust in the published artifact matching the audited source." A premature Sealed tag (bypassing M12) is a process failure whose blast radius is every downstream deployment relying on the tag's meaning — recovery requires an explicit retraction/re-tag communication, not just a silent fix.

25.10 Operational Notes

CHANGELOG.md (§10) documents every release's gate-check results inline; docs/runbook/ triage.md includes the retraction procedure for a Sealed tag found to have been applied in error. This is the last phase before the back-matter sections (§26 onward) that describe ongoing, cross-cutting operational concerns rather than one-time build activities.

28. Operational Readiness

Metrics (all counters, no_std-compatible via a caller-supplied telemetry sink so the core crates never take a hard dependency on a metrics library): decode_reject{reason}, agree_reject{reason}, verify_reject{reason}, batch_verify_mismatch. Tracing: none inside the core crates (pure functions, I10); the CLI (curve-cli) may emit a single span per invocation for operator debugging. Structured logging: the core crates never log (a log line is a potential secret-disclosure vector, T6); curve-cli logs only public inputs/outputs (file paths, success/failure), never key bytes. Dashboards: rejection-reason histograms per peer/key (FM-8), dudect t-statistic trend per release (FM-4), fuzz-canary pass/fail history (FM-5). Alerting philosophy: any of batch_verify_mismatch > 0, a Sealed-gate metric regressing (M9/M11/M12), or a rejection-reason spike concentrated on one identity pages immediately; diffuse, low-rate rejections across many peers are logged but not paged (expected background noise from misconfigured or buggy peers). SLOs: M1–M4 latency targets (§4) at p99; zero-panic (I12) as an availability SLO, not a latency one. Incident response: T3/T4/FM-3 class incidents (accepted-malformed-input) are P0 by definition (§21.9); T6/FM-10 (key disclosure) triggers immediate key rotation. Runbooks: docs/runbook/triage.md (general first-response) and docs/runbook/conformance-failure.md (red conformance/fuzz CI). Backup/restore: not applicable — this library owns no persistent state. Deployment topology: embedded as a dependency inside the caller's binary; no independent deployment unit. Canary/rolling-upgrade/ rollback: governed entirely by the caller's own deployment process, since this is a library, not a service — the one library-specific rule is that a Sealed release must never be un-released without an explicit retraction note (§25.10).

29. Compatibility & Versioning

Wire compatibility: the X25519 (RFC 7748 sections 5 and 6.1) and Ed25519 (RFC 8032 sections 5.1.2 and 5.1.6) encodings are frozen forever — they are external standards, not this project's to version. Storage compatibility: not applicable (no persistent storage owned). Schema evolution: DecodeError/VerifyError/AgreeError (§11) are #[non_exhaustive], allowing new variants in a minor release without breaking downstream match exhaustiveness. API stability: the public surface assembled in §22 (ed25519::*, x25519::*) follows SemVer; adding a new public function is a minor bump, changing an existing signature is a major bump. Migration: none required between versions unless a security patch changes default behavior (e.g., tightening strict-mode checks, ADR-07) — such a change is documented in CHANGELOG.md as a security-relevant behavior change even if it is not a SemVer-major API change. Deprecation policy: a deprecated function is marked #[deprecated] for at least one minor release cycle before removal in the next major. SemVer policy: strict — internal crates (curve-field, curve-scalar, curve-edwards, curve-montgomery) are not published independently and carry no external compatibility promise; only ed25519, x25519, and curve-cli are published with SemVer guarantees. Rolling-upgrade guarantees: since this is a stateless library, "rolling upgrade" means only that a caller's fleet may run mixed versions transiently — any two versions implementing the same RFC must interoperate (verified by the dalek cross-validation fixtures, §30), so a rolling upgrade of a caller's fleet is safe by construction as long as both versions pass conformance.

30. Testing & Verification Strategy

Unit tests: per-function correctness on hand-picked boundary values (each phase's N.5). Property tests: algebraic identities ((ab)⁻¹=a⁻¹b⁻¹, commutativity of DH, §13.4/§19.4) via proptest-style random generation. Differential tests: against curve25519-dalek (field/ scalar/point layers, ADR-16) and, at the protocol boundary, byte-level wire compatibility with BoringSSL/libsodium validated via the shared RFC/Wycheproof corpora both implementations also pass. Fuzzing: cargo-fuzz targets on every parse/decode boundary (§24), seeded from the Wycheproof/Chalkias corpora. Chaos/fault injection: out of scope for this stateless library (no distributed state to inject faults into) — the closest analogue is the dudect timing-fault-class audit (§23) and the fuzz canaries (§24). Deterministic replay: every conformance fixture is a fixed, checked-in input/expected-output pair, replayed identically on every run — no test depends on wall-clock time or external services. Soak testing: the 24-hour and 30-day fuzz canaries (M11, M12) double as soak tests for memory growth and rare-state panics. Conformance gating: the aggregate report (§24.4) is the single source of truth for "does this pass," tied to every invariant (§7) and every phase's N.5 fixtures. Performance-regression gating: every M1–M14 target (§32) is checked in CI on every release candidate; a regression beyond a documented tolerance blocks the release.

32. Performance Engineering

Methodology: Criterion (ADR-22) for throughput/latency benchmarking with statistical confidence intervals, not single-shot timing; dudect (§23) for the orthogonal constant-time question — the two tools answer different questions and neither substitutes for the other. Allocation analysis: zero heap allocations in any hot path (no_std, ADR-02) — verified by a #[global_allocator] panic-on-alloc test harness run against the core crates in CI. Lock/ contention analysis: not applicable — no shared mutable state exists to contend over (I10). Cache analysis: the field/point working sets (§4: 40 B/element, 160 B/point) are sized to fit L1 comfortably; the 24 KiB comb table (§4) is sized against typical L2 (≥ 256 KiB), not L1. Syscall overhead: zero syscalls in the core crates (no I/O); curve-cli's file I/O is the only syscall surface and sits outside the performance-critical path. Tail-latency analysis: because every operation is constant-time by construction (P2), p50/p95/p99 are expected to coincide within the ≤ 5% variance stated in §4 — a p99 that diverges meaningfully from p50 is itself a constant-time-regression signal, not just a performance one, and should trigger a dudect re-run.

33. Scalability Analysis

Constant regardless of load: per-operation latency (M1–M8) and memory (§4) — this library has no notion of "load" in the server-system sense; every call is independent (I10). What grows: aggregate throughput scales linearly with core count up to the memory-bandwidth ceiling identified in §4 (~10 GB/s/core field-mul traffic vs. ≥ 20 GB/s/core typical server bandwidth, leaving headroom to roughly 64 cores before bandwidth, not compute, becomes the bottleneck — see §36 for the derivation). Named bottlenecks in order: (1) single-core field-multiply latency (M5) sets the floor for every higher-level operation; (2) at high core counts, shared-cache/memory-bandwidth contention for the comb table and field-element working sets; (3) at very high batch sizes, the 2N+1-way multi-scalar-multiplication table/lookup overhead in batch verification (§22) eventually grows faster than the shared-doubling savings, capping the practical batch size (empirically a few hundred signatures before returns diminish, per the Straus-algorithm complexity analysis, §17). Horizontal scaling: trivial — call the library from more threads/processes; there is no shared state to partition (I10) and no coordination protocol to design. Vertical scaling: bounded by per-core field-multiply throughput (M5); SIMD (the deferred/optional simd feature, ADR-11) is the lever beyond single-lane scalar throughput, trading unsafe-boundary audit surface (T12) for 2–4× throughput on batched workloads. Sharding/partitioning: not applicable — no persistent state exists to shard. Coordination overhead: zero — every call is independent. Practical ceiling: the single-core field-multiply latency (M5, ≤ 60 ns) times the number of field operations per protocol call (§8.4) sets an absolute per-core throughput ceiling; beyond that, only more cores or SIMD acceleration raise aggregate throughput — there is no architectural lever (caching, batching beyond §22's ceiling, precomputation beyond the comb table) left to pull within this design.

34. Mental Models & First Principles

  • MM1 — A field element is a residue class, not a bit pattern; canonical form is a choice, not a given. Predicts: two different limb representations can be mathematically equal but byte-unequal. Bug class without it: comparing or serializing before full reduction. Applies in §13.
  • MM2 — The Montgomery ladder is a constant-shape state machine over two points, not a search. Predicts: every bit of the scalar does exactly the same work regardless of value. Bug class without it: early-exit "optimizations" that leak scalar bits via timing. Applies in §16.
  • MM3 — Completeness of an addition law is a group-theoretic property, not an implementation nicety. Predicts which curve forms need exceptional-input handling and which don't. Bug class without it: point-at-infinity crashes ported from Weierstrass-style code. Applies in §15.
  • MM4 — A cofactor is leftover group structure the protocol must actively fence off, not a rounding error. Predicts that any protocol skipping the [8]-factor or explicit small-order rejection is exploitable by an attacker supplying a low-order point. Bug class without it: small-subgroup confusion attacks (T4). Applies in §17, §21.
  • MM5 — Determinism converts a signer into a pure function; the entire nonce-reuse bug class becomes a type property, not a runtime risk. Predicts why RFC 8032 needs no nonce-misuse warning the way ECDSA does. Bug class without it: catastrophic key recovery from nonce reuse/bias (T2). Applies in §20.
  • MM6 — Strict vs. lax verification is a compatibility contract, not a strictness preference — it decides which byte strings count as "the same signature." Predicts cross-implementation malleability disputes years after an algorithm ships. Bug class without it: two verifiers disagreeing on the validity of the same bytes (T3). Applies in §21.
  • MM7 — Constant-time code is a property of the compiled artifact, not the source text; the optimizer is an adversary too. Predicts why compiler-fence review and compiled-artifact inspection (objdump) are mandatory, not optional. Bug class without it: an "obviously constant-time" function the compiler branches on anyway. Applies in §23.
  • MM8 — Conformance vectors encode institutional memory of past bugs; a passing test suite is a lower bound on correctness, not proof. Predicts why Wycheproof/Chalkias corpora keep growing and why passing them today doesn't certify tomorrow's discovered edge case. Bug class without it: false confidence, treating "green CI" as "formally verified." Applies in §24, §30.

36. Back-of-Envelope Capacity Model

All numbers chained from §4 System Constraints.

  1. X25519 throughput/core = 1 / M1 = 1 / 30 µs ≈ 33,333 agreements/s/core.
  2. Ed25519 verify throughput/core = 1 / M3 = 1 / 60 µs ≈ 16,666 verifies/s/core.
  3. Batch-64 verify throughput/core = 64 sigs / M4 (800 µs) = 80,000 verifies/s/core ⇒ speedup factor = 80,000 / 16,666 ≈ 4.8× over serial (consistent with §22's ≥ 3× floor).
  4. 16-core node aggregate X25519 ceiling = 33,333 × 16 ≈ 533,000 agreements/s, before other handshake costs (certificate ops, network RTT, §4) dominate the caller's total budget.
  5. Basepoint comb-table memory = 32 rows × 8 cols × 96 B/entry (affine-niels form) ≈ 24,576 B ≈ 24 KiB (§4's stated static-memory line, derived here from the table's own dimensions rather than merely asserted).
  6. Field-element unpacked vs. wire overhead = 40 B (in-memory, 5×u64) / 32 B (canonical wire) = 1.25× memory overhead for the unpacked representation — relevant when sizing a point cache holding many live EdwardsPoints (4 field elements each, 160 B/point, §4).
  7. Per-connection X25519 material = 32 B (secret) + 32 B (public) + 32 B (shared secret) = 96 B/connection; at the §4 concurrency ceiling of 1,000,000 concurrent connections, total X25519 material = 96 B × 10⁶ = 96 MB — a small fraction of a typical server's RAM budget, confirming §4's "memory is not the binding constraint" implicit assumption.
  8. 30-day fuzz-canary execution volume = assuming ~50,000 exec/s/core (typical for a crypto-primitive libFuzzer target) × 30 days × 86,400 s/day = ≈1.296 × 10¹¹ executions — the statistical basis underlying the M12 "zero panics" gate's confidence.
  9. dudect measurement wall-clock = M9's ≥ 10⁷-measurement-pair floor at ~1 µs/pair (dominated by the ≤ 60 µs per-call latency, M2/M3) ≈ 10 s/function/run — cheap enough to run on every release candidate (ADR-22), not just nightly.
  10. Montgomery-ladder stack footprint = 5 live FieldElements (x1,x2,z2,x3,z3, §16.2) × 40 B = 200 B + frame overhead, well under the §4 ≤ 4 KiB stack ceiling — leaving headroom for embedded targets with far tighter stack budgets than a server CPU.

38. Alternative Architectures (Roads Not Taken)

Alt A — Formally-verified backend (HACL/Fiat-crypto-generated field arithmetic).*

Show the original text diagram
+------------------------------------------------------+
|  F* proof source --> OCaml/C extraction --> Rust FFI  |
|  shim, replacing crate `curve-field` at the boundary  |
+------------------------------------------------------+

Regime where it wins: certification-heavy deployments (browser TLS stacks, national crypto agencies) where a machine-checked proof of the field arithmetic's functional correctness and constant-time-ness outweighs the cost of a foreign toolchain and an FFI boundary. Real system: HACL* (Project Everest), integrated into Mozilla NSS and libsignal. Rejected here because it introduces an F*/OCaml build dependency this blueprint's Rust-only, cargo-only toolchain (ADR-01/02) is designed to avoid, and the proof pipeline is a multi-year investment orthogonal to shipping a correct, hand-audited implementation quickly (PhaseDeferred, §39).

Alt B — SIMD-batched vector backend as the primary (not optional) scalar-mult path.

Show the original text diagram

|  "batch of N contexts" scheduler --> N-lane vectorized|
|  field ops (AVX2/AVX-512/NEON), N independent scalar  |

Regime where it wins: a bulk-signing service (certificate-transparency log signer, a blockchain validator batch-verifying thousands of signatures per block) where aggregate throughput dominates and per-signature latency is irrelevant. Rejected here because this blueprint targets a general-purpose library used inside single-signature-latency-sensitive paths (TLS handshake, SSH auth, §4's M1–M3) where per-call latency matters more than batch throughput, and mandatory SIMD would violate ADR-11's no-unsafe-in-core-crates principle.

Alt C — Cofactor-free group abstraction via Ristretto from Phase 0.

|  application code sees only RistrettoPoint/Scalar;    |
|  EdwardsPoint and the [8]-cofactor never surface       |
+------------------------------------------------------+

Regime where it wins: a protocol stack (OPAQUE, a zk-SNARK's Pedersen-commitment layer) that assumes a clean prime-order group and would otherwise re-derive cofactor-clearing logic at every call site. Real system: curve25519-dalek's ristretto module (used by opaque-ke); libsodium's crypto_core_ristretto255. Rejected here because RFC 7748/8032 (this project's chartered scope, §1) are defined directly over Edwards25519/Curve25519, not Ristretto — encoding, X25519, and Ed25519 wire formats are byte-incompatible with a Ristretto-first design, so building Ristretto-first would break RFC conformance; ADR-19 defers it instead (§39).

40. Glossary

  • Field element — a residue class modulo p = 2²⁵⁵-19, represented as five radix-2⁵¹ limbs.
  • GF(2²⁵⁵-19) — the prime field underlying both Curve25519 and Edwards25519.
  • Radix-2⁵¹ representation — the unsaturated five-u64-limb encoding of a field element.
  • Limb — one u64 component of a field element's radix representation.
  • Carry propagation — normalizing limb values back into their canonical bit-width after an operation.
  • Twisted Edwards curve — the curve form -x²+y²=1+dx²y² used for Ed25519, with a complete addition law.
  • Montgomery curve — the curve form y²=x³+486662x²+x used for X25519's x-only ladder.
  • Birational map — the algebraic correspondence between Edwards25519 and Curve25519 point representations.
  • Cofactor — the ratio between a curve's full point-group order and its largest prime-order subgroup; 8 for both Curve25519 and Edwards25519.
  • Small-order point — a point whose order divides the cofactor rather than the prime L.
  • Eight-torsion subgroup — the 8 points of order dividing 8, the source of small-order-point attacks.
  • Extended projective coordinates — the (X:Y:Z:T) representation enabling complete Edwards addition.
  • Affine coordinates — the (x,y) representation obtained by dividing out the projective Z.
  • Point compression — encoding a curve point as 32 bytes (y-coordinate + sign bit).
  • Point decompression — recovering the full point from its compressed encoding.
  • Canonical encoding — a wire encoding whose integer value is strictly less than the field modulus or group order.
  • Non-canonical encoding — a wire encoding whose value is ≥ p or ≥ L, rejected in strict mode.
  • Scalar clamping — the X25519-specific bit-manipulation fixing the cofactor and MSB of a secret scalar.
  • Scalar field (mod L) — arithmetic modulo the prime group order L.
  • Barrett reduction — a fast modular-reduction technique using a precomputed reciprocal.
  • Montgomery ladder — the constant-time, fixed-iteration x-only scalar-multiplication algorithm for X25519.
  • Differential addition — the ladder's per-bit operation combining an addition and a doubling.
  • Constant-time — an execution property where control flow and memory access never depend on secret data.
  • Timing side channel — an information leak through an operation's execution time.
  • dudect — a statistical methodology (Welch's t-test) for detecting timing side channels.
  • Basepoint — the fixed generator point of the prime-order subgroup, u=9 (Montgomery) / B (Edwards).
  • Basepoint comb table — the precomputed table enabling fast fixed-base scalar multiplication.
  • Fixed-base scalar multiplication — multiplying a known, reused base point by a scalar.
  • Variable-base scalar multiplication — multiplying an arbitrary point by a scalar.
  • Double-scalar multiplication — computing [a]A+[b]B in one combined operation.
  • Straus's algorithm — the joint-sparse-form technique underlying double-scalar multiplication.
  • Signed non-adjacent form (NAF) — a signed-digit scalar encoding reducing table size.
  • Deterministic nonce — a per-signature random value derived purely from the secret key and message, never from an RNG.
  • RFC 8032 — the IETF specification defining EdDSA (Ed25519/Ed448).
  • RFC 7748 — the IETF specification defining X25519/X448.
  • EdDSA — the Edwards-curve Digital Signature Algorithm family.
  • X25519 — the Diffie-Hellman key-agreement function over Curve25519.
  • Ed25519ph — the pre-hashed variant of Ed25519 for streamed messages.
  • Ed25519ctx — the context-string variant of Ed25519 for domain separation.
  • Strict verification — RFC 8032 section 5.1.7's canonical-encoding-enforcing verification mode.
  • Lax verification — a permissive verification mode accepting some non-canonical encodings.
  • Malleability (signature) — the property that a second, distinct valid encoding exists for the same signed message.
  • Cofactor-aware verification — the [8]-scaled verification equation closing small-subgroup attacks.
  • Batch verification — verifying many signatures simultaneously via one combined equation.
  • Wycheproof — Google's project providing adversarial cryptographic test vectors.
  • CAVP / ACVP — NIST's Cryptographic/Automated Algorithm Validation Programs.
  • Zeroize — the practice (and Rust crate) of overwriting secret memory on drop.
  • subtle crate — the audited Rust crate providing constant-time primitives.
  • Fault injection — inducing a hardware fault (voltage/clock glitch) to leak secret data.
  • LadderLeak — the 2020 paper demonstrating catastrophic key recovery from small nonce biases.
  • Ristretto / Decaf — cofactor-removal encodings presenting a clean prime-order group.
  • HACL* — a formally-verified cryptographic library produced by Project Everest.
  • Multi-scalar multiplication (MSM) — computing a linear combination of multiple scalar-point products efficiently.
  • HPKE — RFC 9180's Hybrid Public Key Encryption, one consumer of X25519.
