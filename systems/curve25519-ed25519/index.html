In one paragraph

This is a design for a Rust library, built from the arithmetic upward, that lets two parties agree on a shared secret (X25519) and lets one party sign a message anyone can check (Ed25519) (§1). It has no server, storage or network code; every public function is a pure, constant-time, allocation-free computation on caller-owned memory (§4). It targets 30 µs per key agreement and 60 µs per signature check on one core (M1, M3), for embedding in TLS terminators, SSH daemons and signing services (§1). Its guiding rule: passing the RFC test vectors is necessary but never enough (§2), so every phase is gated on named fixtures including adversarial corpora (P10), and release is gated on a dudect timing test (P2).

The problem, concretely

Elliptic-curve code that is merely correct on the happy path is exploitable. The blueprint's own scenarios show three ways (§8.7, §8.8, §8.1).

First, an attacker sends an X25519 public key that is one of the eight small-order points. Decoding succeeds, because a bare Montgomery u coordinate has no validity check (§8.5). The resulting shared secret is always 0, whatever the victim's private scalar is (§8.7). A library that does not look for that zero hands the attacker a predictable key.

Second, a verifier receives an Ed25519 signature whose scalar half was encoded as s' = s + L. It is still congruent to a valid s modulo L. A lax verifier that reduces first accepts it, and now two different 64-byte signatures verify for the same key and message (signature malleability, §8.8, T3). Strict mode rejects it at parse time, before any curve arithmetic runs (I6).

Third, secret data is processed in a way whose running time depends on its value. Even something as small as computing a modular inverse by extended Euclid instead of a fixed chain leaks the operand through timing (§8.1, P2); a timing attack of this kind recovers secret scalar bits (T1).

Checks live in types and at the API boundary (I2, I6, I7, I11); secret branches are absent (P2, §3).

How it works, end to end

The library is four stacked layers (§3):

Follow an X25519 agreement down the boxes (§8.6, §19.2):

  1. x25519 generates the secret from a caller-supplied cryptographic RNG and clamps it at once into a ClampedScalar (I2, §19.2). The library never reads a global RNG (§19.2).
  2. curve-montgomery runs the ladder, ladder(self, peer): 255 identical steps, each a conditional swap plus one add-and-double (§8.4, §16.2).
  3. curve-field does every multiplication, squaring and the one final inversion (§16.2, §8.1). curve-scalar holds the clamping code (clamp.rs, §10).
  4. Back in x25519, the output is checked against zero after the ladder (I7) and the peer key against the small-order table (I11); the result is a Result, never a bare secret (§19.2, P13). When the table check runs is stated three ways: "at decode time" (§8.7), "before the ladder" (ADR-10), and in §19.2 a step that "computes ladder(self, peer.0), then checks" the table "before running the ladder".

Now an Ed25519 signature (§20.2):

  1. ed25519 (sign.rs) derives the nonce r from the secret prefix and the message (I3).
  2. curve-edwards computes R = [r]B with the fixed-base comb (§20.2, §17).
  3. curve-scalar does the wide reduction of the hash and s = r + k·a mod L (§20.2, §14).
  4. ed25519 returns Signature{r: R.compress(), s} (§20.2).

Verification decodes and rejects bad encodings, recomputes the challenge hash, then evaluates one cofactor-scaled equation with curve-edwards's double-scalar routine (§21.2). Beside all of this, conformance/runner replays every corpus vector and asserts I1–I14 individually, so a failure names the invariant that broke (§7). The trust boundary is the public API, and secrets live only in caller-owned zeroized memory (§3, I5, P6).

The core ideas

The field: numbers modulo 2²⁵⁵ − 19 in five limbs (§8.1, ADR-03)

Everything is arithmetic modulo the prime p = 2²⁵⁵ − 19. A field element is stored as five 64-bit limbs (radix-2⁵¹) so that the value is h0 + h1·2⁵¹ + h2·2¹⁰² + h3·2¹⁵³ + h4·2²⁰⁴. The limbs are deliberately unsaturated: each may grow to about 2⁵³ before it is cleaned up, so carries are propagated lazily (§8.1, P9).

The one trick: 2²⁵⁵ ≡ 19 (mod p). Any partial product that lands above bit 255 is multiplied by 19 and added back into the low limbs (§8.1). add and sub skip full reduction. Only to_bytes forces the result below p (I1), and mul/square finish with a carry postlude so limbs are comparable (I9). Inversion is Fermat's little theorem, x⁻¹ = x^(p−2), as a fixed chain of about 250 squarings and 12 multiplications, never a variable-time Euclid (§8.1).

The mental model (MM1): a field element is a residue class, not a bit pattern. Two different limb layouts can be mathematically equal and byte-unequal, so comparing before full reduction is a bug.

Two curve shapes for one curve (§8.2, §8.3, ADR-04, ADR-05)

Signing uses the twisted Edwards form −x² + y² = 1 + d·x²·y², with d = −121665/121666. Its addition law is complete: it works for every pair of inputs, including a point added to itself or to the identity, so no secret-dependent special-case branch is ever needed (§8.2, P3, MM3). Points are kept as (X : Y : Z : T) with T = XY/Z, and the identity is (0 : 1 : 1 : 0).

Key agreement uses the Montgomery form y² = x³ + 486662·x² + x and only its x coordinate, which skips the y work and halves the field operations per step (§8.3, ADR-05). A birational map (u = (1+y)/(1−y), v = u/x) converts between the forms, but only inside differential tests (I14), never on the signing or verification path (§8.3).

The group has order 8·L, with L prime, so the curve has cofactor 8: eight small-order points sit in the kernel of multiplication by L. §8.2 calls them "the 22 bad points" once every valid encoding of each of the 8 group elements is counted, but I11 rejects "the 22 small-order Edwards points", P11 enumerates "the 22 eight-torsion points" and §15.4 flags "all 22 small-order points". The blueprint does not reconcile eight elements with 22 points. A point is compressed to 32 bytes: y little-endian with the sign of x in bit 7 of the last byte. Decompression recovers x with a square-root recipe and rejects y ≥ p or a missing root (§8.5, I1).

Three scalar multiplications, one per job (§8.4, ADR-06)

Multiplying a point by a secret number is the expensive step, and each use gets its own algorithm.

  • Montgomery ladder (X25519): one conditional swap plus one differential add-and-double per scalar bit, MSB to LSB, 255 iterations whatever the scalar is (§8.4). The step table:

    step action note
    digit k_i swap_acc ^= k_i tracks whether the two points are in swapped roles
    conditional swap ct_swap(x2,x3); ct_swap(z2,z3) executed even when the swap bit is 0
    add and double 5 field multiplies + 4 squarings same cost every step

    MM2: the ladder is a constant-shape state machine, not a search. An early exit that "optimises" a zero bit would leak that bit through timing.

  • Fixed-base comb (signing): a precomputed table B_TABLE[i][j] = (j+1)·16^(2i)·B for i < 32, j < 8, walked once with a constant-time 8-way select instead of a branch on the digit (§8.4). The table is built once per process (I8). §8.4 says the scalar is split into 32 radix-16 digits while the table spacing is 16^(2i), and §17.2 says no doublings are needed; neither explains how 32 digits at that spacing cover the scalar.

  • Straus double-scalar (verification): computes [a]A + [b]B together, sharing the doublings, which is cheaper than two separate multiplications (§8.4).

Deterministic signing (§20.2, I3, ADR-09, MM5)

A signature is (R, s). The three steps (§20.2):

  1. Expand the seed. SHA-512(seed) gives 64 bytes. The low 32, clamped, become the secret scalar a; the high 32 become the nonce_prefix. The clamping is applied to the expansion, not the raw seed, which Appendix B lists as a named risk (§20.2, §42 Phase 8).
  2. Derive the nonce. r = SHA-512(nonce_prefix ‖ message) mod L and R = [r]B (I3).
  3. Challenge and answer. k = SHA-512(R ‖ A ‖ message) mod L, then s = r + k·a mod L.

No random number generator is involved, so signing the same pair twice gives byte-identical output (§20.4). The blueprint's argument is that this removes the nonce-reuse and nonce-bias attack class (LadderLeak) as a type property rather than a runtime risk (MM5, T2). It does not remove fault injection (T7).

Verification: strict, cofactor-aware, optionally batched (§8.8, §21.2, §22.2, MM6)

Strict verification (§21.2) does the following in order. It decodes A and R and rejects bad encodings (I1). It rejects s ≥ L (I6). It rejects small-order A or R (I11). It recomputes the challenge k and checks the cofactor-scaled equation [8s]B = [8]R + [8k]A with the double-scalar routine. §2, P8 and ADR-08 write the check as [8h]A + [8R] − [8s]B, §21.1 as [8h]A + [8R] = [8s]B, and §21.2's own lax line uses hA + R = sB. The blueprint never defines h or says it is the same value as §21.2's recomputed challenge k. The reason for the factor 8 (MM4): the cofactor is leftover group structure the protocol must fence off.

Lax mode (lax-verify Cargo feature only, never a runtime toggle) checks the unscaled hA + R = sB and skips the I6 and I11 pre-checks, for legacy interop (§21.2, P4).

Batch verification (§22.2) draws a random ~128-bit coefficient z_i per signature, chosen by the verifier, and checks [Σ z_i·s_i]B = Σ (z_i·R_i) + Σ (z_i·k_i)·A_i as one multi-scalar multiplication over 2N+1 bases. A forged signature slips through with probability at most 2⁻¹²⁸ (I13). §22.2 writes this equation without the factor 8 and does not say whether it is applied. §22.2 cites §8.4 for the batch equation, and FM-7 says to "re-derive batch equation from §8.4", but §8.4 does not contain one.

The trade-offs — where engineers disagree

Field representation: radix-2⁵¹ (ADR-03)

Chosen: five 64-bit limbs holding 51 bits each, which matches curve25519-dalek and needs fewer carries per multiply on 64-bit targets (§9). Rejected: a ten-limb 32-bit-native layout, and saturated radix-2⁶⁴. When the rejected choice is right: a 32-bit target such as Cortex-M0, where 64-bit multiplies are emulated and the ten-limb layout is faster (§9).

Key-agreement form: Montgomery x-only (ADR-05)

Chosen: the x-only Montgomery ladder, which skips the y coordinate and halves the field operations (§9, §8.3). Rejected: Diffie-Hellman directly on the Edwards form. When the rejected choice is right: a protocol that needs the y coordinate mid-exchange without a birational round trip, such as libsodium's optional Edwards-DH path (§9).

Verification default: strict, with lax opt-in (ADR-07, P4)

Chosen: strict RFC 8032 §5.1.7 behaviour by default, with lax-verify as a build-time feature, justified by the Chalkias et al. 2020 malleability corpus (§9). Rejected: lax-only verification. When the rejected choice is right: interop with a legacy pre-2019 verifier already accepting lax-encoded signatures on-chain, for reads only, never for new signing (§9).

Cofactor handling: scale by 8 (ADR-08, P8)

Chosen: the cofactor-aware equation [8h]A + [8R] − [8s]B, at a cost of three extra doublings (about 15 ns, P8), which closes small-subgroup confusion (§9). Rejected: the naive hA + R − sB. When the rejected choice is right: a protocol that already rejects all eight-torsion components at decode time, making the multiply redundant; the blueprint says some HSM firmware skips it there (§9).

Nonce generation: deterministic (ADR-09, P7)

Chosen: SHA-512(prefix ‖ msg) mod L, because LadderLeak shows nonce bias is catastrophic (§9). Rejected: hedged (RFC 6979-style) and purely random nonces. When the rejected choice is right: a signer under a fault-injection threat model, such as smart-card glitching, where a hedged nonce (deterministic plus fresh randomness) closes fault-induced reuse that pure determinism does not (§9, T7). P7 itself names "some fault-injection exposure on repeated signs."

Small-order X25519 keys: an explicit table (ADR-10, P11)

Chosen: an explicit 22-key rejection table, defense-in-depth that catches small-subgroup keys before the ladder (§9, §19.2). Rejected: relying on the zero-shared-secret check (I7) alone. When the rejected choice is right: a code-size-constrained IoT target where the table's ~200 B of .rodata is unaffordable (§9).

Conformance floor: four corpora (ADR-14, P10)

Chosen: Wycheproof, CAVP/ACVP, the Chalkias corpus and RFC vectors, because RFC 8032 §7.1 has only three vectors and production bugs live in edge cases (§9). Rejected: RFC vectors alone. When the rejected choice is right: a FIPS 140-3 CMVP track where ACVP is mandated and Wycheproof, though still run, is outside the compliance boundary (§9).

Roads not taken

Formally verified backend (§38 Alt A): machine-checked field arithmetic in the HACL* style. It wins in certification-heavy deployments such as browser TLS stacks or national agencies, where a proof outweighs a foreign F*/OCaml toolchain. It is rejected because it breaks the cargo-only toolchain (ADR-01, ADR-02) and the proof pipeline is a multi-year investment; it sits in the deferred register (§39).

SIMD-batched backend as the primary path (§38 Alt B): N scalar multiplications in lockstep in vector lanes. It wins for bulk signing or a validator verifying thousands of signatures per block, where aggregate throughput beats per-call latency. It is rejected because this library serves latency-sensitive single-signature paths (M1–M3) and mandatory SIMD would violate ADR-11.

Ristretto from Phase 0 (§38 Alt C): hide the cofactor behind a prime-order group. It wins for OPAQUE or a zk-SNARK commitment layer that assumes a clean group. It is rejected because RFC 7748/8032 are defined over Edwards25519/Curve25519, so a Ristretto-first design would be byte-incompatible with them (ADR-19, §39).

Other deferrals (§39): X448/Ed448 (ADR-18), FIPS 140-3 code (ADR-20), Elligator2, PKCS#11/HSM, VRFs and multi-scalar multiplication each have an un-defer trigger, such as a 224-bit need (§39).

What must never be false

  • I1: field elements are fully reduced (< p) before serialization. Noticed when decompress rejects y_bytes ≥ p; telemetry decode_reject{reason="non_canonical"}.
  • I2: X25519 scalars are clamped before the ladder. Type-enforced by ClampedScalar, checked by a property test on the bit pattern; no telemetry, since no runtime path can bypass it.
  • I3: the Ed25519 nonce is SHA-512(prefix‖msg) mod L. Noticed by RFC 8032 §7.1 vector replay; a pure function, so no telemetry.
  • I4: every point and ladder operation is branch-free over secret data. Noticed by dudect (t-statistic ≤ M9); evidence in timing/dudect.report.json.
  • I5: SigningKey and decoded secret scalars are zeroed on drop. Noticed by miri plus a memory-scan test.
  • I6: verification checks s < L before use. Noticed by the Wycheproof s ≥ L cases; telemetry decode_reject{reason="scalar_not_canonical"}.
  • I7: the X25519 shared secret is non-zero before use. Noticed by the 22 small-order Wycheproof cases; telemetry agree_reject{reason="zero_shared_secret"}.
  • I8: the basepoint comb table is computed exactly once per process (OnceLock). Noticed by a table-identity test across two calls.
  • I9: field-multiply carries fully propagate before comparison or encoding. Noticed by a differential test against num-bigint on 100K randoms.
  • I10: verification and agreement are pure functions with no shared mutable state. Noticed by a 10K-concurrent-verify stress test.
  • I11: the 22 small-order points are rejected in strict verify and X25519 acceptance. Noticed by the Chalkias corpus and RFC 7748 vectors; telemetry decode_reject{reason="small_order"}.
  • I12: every public function returns Result and never panics on attacker input. Noticed by the 30-day fuzz canary (fuzz/canary-30d.md).
  • I13: batch verification accepts nothing a serial verify rejects, except with probability ≤ 2⁻¹²⁸. Noticed by the batch.consistency bucket; the batch_verify_mismatch counter must be 0.
  • I14: Montgomery and Edwards results agree under the birational map. Noticed by a differential test over 10K random scalars on both ladders.

What breaks in production

Most failure modes of this library are correctness or security bugs that no code path heals (§27).

  • FM-1: two parties derive different X25519 secrets. The cause is a field, scalar or ladder bug, or a peer-key decode mismatch. It is detected by the commutativity property test (§19.4), and recovery is manual: bisect with §16.9's iterated-ladder localization.
  • FM-3: the verifier accepts a malleable signature. A check from I1, I6 or I11 is missing, or the naive equation is in use. The Chalkias or Wycheproof negative-corpus regression catches it. It is a P0 patch, the affected release is disabled and prior releases are re-audited. A tell: rejection telemetry drops to zero when it should not.
  • FM-4: dudect t-statistic exceeds 4.5. A branch or table lookup on a secret value crept back in. The CI timing gate (M9) catches it; bisect the per-commit dudect history and replace the branch with ct_select.
  • FM-5: the 30-day fuzz canary finds a panic. An unhandled malformed input in a parse path. The harness restarts but the bug stays; minimize the input, add a regression fixture, patch.
  • FM-7: batch_verify_mismatch is non-zero in production. Either a soundness bug in the batch equation or an active forgery attempt. The verifier automatically falls back to serial verification for that batch; then re-derive the equation and re-run the 10⁶-trial fixture.
  • FM-8: a rejection spike concentrated on one peer. Someone is probing for small-order or malformed-input bugs. Rejections continue automatically because the checks are unconditional; rate-limiting or blocking the peer belongs to a layer above this library.
  • FM-10: signing-key memory found in a core dump. A secret type lacks ZeroizeOnDrop. The miri or memory-scan test, or an incident report, catches it; rotate the key at once and patch.
  • FM-11: strict and lax disagree on the same bytes. Often expected (ADR-07), sometimes a bug. The strict_vs_lax_divergence fixture separates the two; an undocumented divergence is treated as FM-3.

Threats a reader should know (§26): T1, a timing attack that recovers secret scalar bits, answered by the constant-time ladder and comb plus dudect (P2, ADR-06); T3, a second valid encoding of the same signature, answered by strict rejection (I6, I1); T4, small-subgroup confusion via a crafted low-order key, answered by three layers: the cofactor-aware equation, the small-order table and the zero-secret check (P8, P11, I7); T7, fault injection by glitching during signing, documented as a residual risk that deterministic nonces alone do not close; T10, a weak caller RNG producing guessable X25519 keys, which this library cannot detect and instead forces the caller to supply a CryptoRng-bound generator (§19.2).

How it compares

  • libsodium is the most-deployed C implementation. It chose strict, cofactor-aware Ed25519 early and is the interop baseline; that is fine for a niche that wants prebuilt bindings in dozens of languages, which this Rust-first design does not prioritise (§35).
  • BoringSSL uses hand-tuned assembly per microarchitecture. That pays off for one organisation running a huge fleet, while this design trades some peak throughput for auditability and memory safety (§35).
  • curve25519-dalek has the same field representation and subtle-based constant-time style, but lets the caller choose the cofactor-aware path and historically defaulted to permissive. It fits as a building block for higher-level protocols; this project uses it only as a cross-validation oracle (§35, ADR-16).
  • ring is assembly-first and keeps a small curated API. That suits a project wanting one crate for broad TLS-relevant primitives rather than a from-scratch, readable curve25519 implementation (§35).
  • OpenSSL has the largest installed base and covers RSA, P-256 and many other primitives under one ABI. That suits legacy environments, at the cost of an audit surface far larger than this X25519/Ed25519-only design accepts (§35).

Questions to test yourself

  1. Why does X25519 clamp the scalar's low 3 bits and high bit, and what specifically breaks in the ladder if the low-bit clearing is skipped while the high-bit setting is kept? — Hint: I2 and §8.6 say what clamping does; §16.2 shows what the ladder does with each bit.
  2. Why is the Ed25519 verification equation scaled by the cofactor 8 instead of checking hA+R-sB=0 directly, and what concrete attack does the naive equation permit that the [8]-scaled one does not? — Hint: §8.2 for the cofactor, MM4 and T4 for the attack.
  3. Trace what happens end-to-end if a peer supplies one of the 22 small-order X25519 public keys: which invariant catches it, at which phase was the check introduced, and what would the shared secret be if the check were absent? — Hint: §8.7, I7 and I11, and §19.1 for the phase.
  4. What is the precise difference between "the shared secret is zero" and "the public key is small-order," and why does X25519 need to check both rather than either alone? — Hint: §8.5 on why a bare u cannot be validated, then P11 and §19.2.
  5. Why does deterministic nonce generation (I3) not fully close the fault-injection threat (T7), and what mitigation does this blueprint recommend instead? — Hint: the last column of ADR-09, and T7's recovery cell.

If you only remember three things

Everything is built so the safe path is the only path: scalars are clamped by type, secrets are zeroized and never printable, and nothing branches on secret data (P2, P6, I2). Ed25519 signing is a pure function of key and message, and verification is strict and cofactor-scaled by default because small-order points and non-canonical encodings are the real attack surface (I3, P8, ADR-07). A passing RFC vector run proves little, so correctness is defined by adversarial corpora, a dalek differential oracle and a statistical timing test (P10, P12, MM8).

Words used here

  • Field element / limb: a number modulo p = 2²⁵⁵ − 19, stored as five 64-bit pieces (limbs).
  • Twisted Edwards curve: the curve shape used for Ed25519, with an addition law that has no special cases.
  • Montgomery curve: the curve shape used for X25519's x-only ladder.
  • Cofactor: the leftover factor (8 here) between the full group order and its large prime part.
  • Small-order point: a point in the cofactor part; an attacker who supplies one forces a predictable result (T4).
  • Clamping: fixing the low and high bits of an X25519 secret so the cofactor and top bit are handled (I2).
  • Montgomery ladder: the fixed-iteration, x-only way to multiply a point by a secret scalar.
  • Constant-time: control flow and memory access never depend on secret data.
  • dudect: a statistical test that watches for timing differences between input classes.
  • Deterministic nonce: the per-signature secret number derived from the key and message, never from an RNG.
  • Malleability: the existence of a second valid encoding of the same signature.
  • Strict / lax verification: accepting only canonical encodings, versus accepting some non-canonical ones.
  • Wycheproof / Chalkias corpus: adversarial test vectors that encode past bugs and edge cases.
