⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the §10 workspace layout, governance files, and CI skeleton; land a placeholder conformance/runner that can load and replay a single RFC 8032 section 7.1 vector end-to-end against a stub verify that always returns Ok(()). Establish the crate boundaries (§10) so every later phase has a fixed home for its code. No cryptographic logic is correct yet — this phase proves the plumbing.

Deliverable

cargo build --workspace && cargo test --workspace succeeds; conformance/runner loads and "passes" the one smoke fixture; all ADR docs (ADR-01..24) exist under docs/adr/.

Acceptance
  • cargo build --workspace exits 0 on Rust 1.78.0 exactly (pinned toolchain).
  • cargo deny check exits 0 (no unlicensed/duplicate/yanked dependencies).
  • conformance/runner replays rfc8032/test1.json and reports PASS (against the stub).
  • All 24 ADR files (docs/adr/ADR-01.md … ADR-24.md) exist and match §9's table content.
Fixtures
Fixture Purpose Expected Output

ci/workspace_build.sh confirm every crate compiles under no_std where declared exit 0
ci/deny_check.sh confirm no forbidden dependency exit 0, zero advisories
Pitfalls
  • Declaring no_std on a crate that transitively pulls in a std-only dependency fails silently until a downstream embedded build breaks months later — pin #![no_std] + cargo check --no-default-features --target thumbv7em-none-eabi in CI from day one.
  • A workspace-level Cargo.lock drift between contributors' machines produces "works on my machine" — rust-toolchain.toml (ADR-24) must pin the exact patch version, not just "stable".
  • Writing the stub verify to always return Ok(()) and forgetting to replace it before Phase 9 ships is the single most dangerous placeholder in the whole plan — track it as a tracked // TODO(phase-9) that grep gates in CI.

⬜ Phase 1 — Field Arithmetic: GF(2²⁵⁵ − 19) §13

Objectives

Implement FieldElement (§11) — add, sub, mul, square, invert, ct_eq, ct_select, to_bytes/from_bytes — in the radix-2⁵¹ unsaturated representation (P9, ADR-03), constant-time throughout (P2).

Deliverable

curve-field compiles no_std, exposes the full FieldElement API (§11), passes its differential test suite against num-bigint and curve25519-dalek::FieldElement51.

Acceptance
  • add/sub/mul/square/invert bit-identical to curve25519-dalek::FieldElement51 for 1,000,000 random operand pairs (M5 gate: mul ≤ 60 ns/op on the CI reference core).
  • Property test: (a·b)⁻¹ = a⁻¹·b⁻¹ holds for 100,000 random nonzero (a,b) pairs.
  • invert(one()) == one(); invert(zero()) returns the RFC-defined zero() (no panic, I12).

Fixture Purpose Expected Output
field.cross_dalek.1e6.json differential vs. FieldElement51 bit-identical, 10⁶ ops
field.cross_numbigint.1e5.json independent big-integer oracle bit-identical, 10⁵ ops

field.canonical_boundary.json operands at p-1, p, p+1 reduce correctly, no overflow
Pitfalls
  • Missed carry propagation in mul leaves a limb ≥ 2⁵², producing a value congruent to the right answer mod p but with wrong limbs — passes a naive equality check against a reduced reference but fails byte-for-byte comparison (I9).
  • The 2p constant in sub's "add-then-subtract" trick must be exactly 2·(2²⁵⁵-19) = 2²⁵⁶-38; an off-by-one-bit constant produces values congruent mod p but wrong at the limb level — invisible until to_bytes disagrees with the oracle.
  • Hand-rolling the invert addition chain instead of copying the canonical one (Bernstein-Lange
    1. is the single most common source of "works on random inputs, fails on p-1" bugs.
  • Confusing square's doubled cross-products with mul's undoubled ones when hand-inlining either into the other silently corrupts results only on inputs where the doubling matters.

⬜ Phase 2 — Scalar Arithmetic mod L §14

Objectives

Implement Scalar arithmetic modulo the group order L = 2²⁵² + 27742317777372353535851937790883648493 (§8.2), Barrett reduction, scalar inversion, and the X25519-only clamping transform (I2) as a distinct ClampedScalar type so it cannot be confused with an Ed25519 nonce (P9's sibling discipline, ADR-06).

Deliverable

curve-scalar compiles no_std, exposes Scalar/ClampedScalar (§11), passes differential tests against num-bigint and the RFC 7748 section 5 clamping example.

Acceptance
  • add/mul/invert mod L bit-identical to num-bigint-computed references for 100,000 random operands.
  • ClampedScalar::from_bits_clamped reproduces RFC 7748 section 5's worked clamping example exactly (named fixture scalar.clamp_rfc7748.json).
  • Scalar::is_canonical rejects all of Wycheproof's s ≥ L negative test cases (§30).
Fixtures
Fixture Purpose Expected Output
scalar.cross_numbigint.1e5.json differential arithmetic mod L bit-identical
scalar.clamp_rfc7748.json RFC 7748 section 5 clamping worked example exact match
scalar.canonical_negative.json Wycheproof s ≥ L cases all rejected
scalar.barrett_wide_reduce.json 64-byte wide reduction (nonce path) matches reference reduction
Pitfalls
  • L is not 2²⁵² — it is 2²⁵² + (a 129-bit tail constant). Truncating to 2²⁵² produces a "scalar" larger than the true order that silently corrupts batch verification (I13).
  • Clamping is X25519-only — applying it to an Ed25519 nonce or challenge scalar produces wrong signatures that still often "look" plausible; the type split (ClampedScalar vs. Scalar) exists specifically to make this a compile error, not a runtime bug (ADR-06 discipline).
  • Barrett reduction's precomputed μ must be recomputed if L is ever mistyped — a single wrong digit produces a reduction that is wrong only for a small fraction of inputs, evading casual testing.

⬜ Phase 3 — Edwards25519 Point Arithmetic §15

Objectives

Implement EdwardsPoint (§11) in extended-projective coordinates: add, double, ct_select, compress/decompress, and is_small_order — the complete, constant-time group law that underlies both signing (§20) and verification (§21).

Deliverable

curve-edwards compiles no_std, exposes EdwardsPoint/CompressedEdwardsY (§11), passes differential tests against curve25519-dalek::EdwardsPoint for add/double/compress/decompress.

Acceptance
  • add bit-identical to curve25519-dalek::EdwardsPoint::add for 100,000 random point pairs.
  • double(P) == add(P, P) for 1,000 random points (M6 gate: double ≤ 50 ns amortized field-op cost).
  • Decompression of every basepoint multiple kB for k ∈ [0, 1024] (named fixture edwards.decompress_basepoint_multiples.json) succeeds and re-compresses byte-identically.
  • All 22 small-order points are flagged is_small_order() == true (named fixture edwards.small_order_22.json, Chalkias et al. 2020 corpus).
Fixtures
Fixture Purpose Expected Output
edwards.cross_dalek.1e5.json differential add/double bit-identical, 10⁵ ops
edwards.decompress_basepoint_multiples.json round-trip 1,024 basepoint multiples on-curve, byte-identical round-trip
edwards.small_order_22.json the 22 eight-torsion encodings is_small_order() == true
edwards.noncanonical_y.json y_bytes ≥ p inputs rejected, Error::NonCanonicalEncoding
Pitfalls
  • The constant 2d must be derived from the correct d = -121665/121666; a sign error here produces an addition law that is subtly wrong only for specific input combinations, not all of them.
  • Completeness (P3) holds only for a = -1 (this library's twisted Edwards choice, ADR-04) — a contributor porting a Weierstrass-style special case ("skip if P == Q") reintroduces a branch the whole point of HWCD-2008 was to remove.
  • decompress's square-root recipe has four cases (square, square×i, square×√-d, square×√-d×i, per RFC 8032 section 5.1.3 step 3) — omitting any one silently rejects valid points or accepts invalid ones depending on which case is missing.
  • Sign-bit recovery has an off-by-parity bug at x = 0 specifically — handle it as an explicit boundary case, not inferred from the general formula.

⬜ Phase 4 — Montgomery Curve & the X25519 Ladder §16

Objectives

Implement MontgomeryU (§11) and the RFC 7748 constant-time ladder: the x-only differential add-and-double state machine that computes [scalar]·u in exactly 255 fixed-shape iterations regardless of the scalar's bits (P2, P9).

Deliverable

curve-montgomery compiles no_std, exposes the ladder (§11), passes the RFC 7748 section 5 worked example and the RFC 7748 section 6.1 iterated-ladder test.

Acceptance
  • ladder(clamp(a), 9) == A for the RFC 7748 section 5 X25519 example vector, bit-identical (named fixture montgomery.rfc7748_5_example.json).
  • The RFC 7748 section 5.2 iterated test (k applied to itself 1, 1,000, and 1,000,000 times) matches the published intermediate and final values exactly.
  • ladder executes in ≤ 30 µs (M1) with ≤ 5% timing variance across 10,000 random scalars on the CI reference core (constant-time acceptance signal, refined by dudect in §23).
Fixtures
Fixture Purpose Expected Output
montgomery.rfc7748_5_example.json RFC 7748 section 5 worked DH example bit-identical
montgomery.rfc7748_iterated_1e6.json RFC 7748 section 5.2 iterated ladder (1, 1e3, 1e6 applications) matches published values
montgomery.cross_dalek.1e5.json differential vs. x25519-dalek bit-identical, 10⁵ ops
montgomery.small_order_u.json the 22 small-order u-coordinates ladder completes, result flagged by I7 downstream
Pitfalls
  • a24 must be 121665, derived as (486662-2)/4 — a transcription error here produces a ladder that is wrong for every input in a way that still looks like "a curve," making it a dangerous silent-wrong-answer bug, not a crash.
  • ct_swap implemented as two independent ct_select calls that are not both actually constant-time (e.g., one accidentally short-circuits) reintroduces exactly the side channel the ladder exists to close (P2).
  • Decoding the u-coordinate's high-bit mask (RFC 7748 section 5) is easy to skip by copy-paste from the Edwards decode path (§15), which has no such mask — the two decode paths must not be unified naively.

⬜ Phase 5 — Scalar Multiplication (Variable-Base, Fixed-Base, Double-Scalar) §17

Objectives

Implement the three Edwards-form scalar-multiplication algorithms of §8.4 on top of Phase 3's point arithmetic: variable-base (general use), fixed-base comb (signing, §20), and Straus double-scalar (verification, §21/§22).

Deliverable

curve-edwards::scalar_mul exposes variable-base, fixed-base, and double-scalar multiplication; fixed-base signing measurably outperforms variable-base on the same scalar/basepoint pair.

Acceptance
  • scalar_mul([1], B) == B; scalar_mul(L, B) == identity (named fixtures scalar_mul.identity_cases.json).
  • scalar_mul(s, B) bit-identical to curve25519-dalek's equivalent for 1,000 random scalars.
  • Fixed-base signing scalar multiplication is ≥ 4× faster than variable-base on the same input (M8 vs. M7 ratio, §32).
  • Double-scalar [a]A+[b]B matches two independent variable-base calls added together, for 1,000 random (a,A,b,B) tuples.
Fixtures
Fixture Purpose Expected Output
scalar_mul.identity_cases.json [1]B, [L]B, [0]B B, identity, identity
scalar_mul.cross_dalek_variable.1e3.json differential variable-base bit-identical
scalar_mul.fixed_vs_variable_speedup.json timing ratio ≥ 4× (M8/M7)
scalar_mul.straus_vs_double_call.1e3.json double-scalar vs. two calls identical results
Pitfalls
  • A match nibble { 0 => ..., 1 => ... }-style table lookup, however tempting for readability, compiles to a branch/jump table on most targets and is a P2/ADR-06 violation caught only by a dudect audit (§23), not by functional tests — treat any non-ct_select table access as an automatic review rejection.
  • Signed-NAF digit encoding's carry propagation (9..15 → nibble-16, +1 next) is a common off-by-one source; a missed carry into the 33rd (overflow) digit corrupts the topmost bits of the result only for scalars near L.
  • Regenerating the fixed-base comb table on every call instead of caching it via OnceLock (I8) is both a ~5× performance regression and, if the regeneration path has any non-determinism, a correctness bug.

  • Treating "no square root exists" and "square root exists but sign bit mismatches after correction" as the same error code loses forensic information an on-call engineer needs (§28) — keep them distinct in DecodeError even though both currently map to rejection.

⬜ Phase 8 — Ed25519 Key Generation & Signing §20

Objectives

Build SigningKey::from_seed and SigningKey::sign (§11): SHA-512 key expansion, deterministic nonce derivation (RFC 8032 section 5.1.6, I3), and the s = r + k·a mod L signature equation, all on top of Phases 1–5.

Deliverable

ed25519::SigningKey compiles, exposes from_seed/sign/sign_prehashed, reproduces every RFC 8032 section 7.1 test vector bit-for-bit.

Acceptance
  • All RFC 8032 section 7.1 test vectors (1–4 for Ed25519, plus the Ed25519ph vector) reproduce the published signature bytes exactly (M-ed25519 milestone gate, Appendix B).
  • sign completes in ≤ 30 µs (M2) with ≤ 5% timing variance across 1,000 distinct messages of the same length (a coarse pre-dudect constant-time signal, refined in §23).
  • Signing the same (key, message) pair twice produces byte-identical signatures (determinism check, I3).
  • SigningKey never implements Debug (compile-time check via a static_assertions-style negative trait-bound test, P6).
Fixtures
Fixture Purpose Expected Output
ed25519.rfc8032_7_1_vectors.json RFC 8032 section 7.1 Tests 1–4 + Ed25519ph bit-identical signatures
ed25519.determinism_1e3.json same (key, msg) signed 1,000× byte-identical every time
ed25519.sign_timing_smoke.json coarse timing variance across message lengths ≤ 5% variance
ed25519.no_debug_compile_check.json SigningKey: !Debug compiles only if true
Pitfalls
  • Clamping the raw seed instead of the SHA-512 expansion's low half is the single most common from-scratch Ed25519 bug — it produces a key that signs internally-consistently but never matches another implementation's output for the same seed.
  • Using SHA-512(seed)'s low bytes for the nonce prefix and the high bytes for the scalar (the two halves swapped) similarly self-consistent-but-wrong.
  • Recomputing the fixed-base comb table (§17) inside sign instead of relying on the process- wide memoization (I8) turns every signature into a ~5× slower operation.
  • Any code path that derives r from a source other than SHA-512(nonce_prefix‖message) — including "for testing, let me just use a random nonce" left in accidentally — reintroduces the exact LadderLeak-class vulnerability (T2, Aranha et al. 2020) determinism exists to close.

⬜ Phase 9 — Ed25519 Verification (Strict, Lax, Cofactor-Aware) §21

Implement VerifyingKey::verify_strict and verify_lax (§11): decode-time canonical checks (I1, I6, I11), the cofactor-aware equation [8h]A + [8R] = [8s]B (P8, ADR-08), and the lax-verify feature-gated alternative (P4, ADR-07).

ed25519::VerifyingKey::verify_strict reproduces RFC 8032 section 7.1's verification results, rejects 100% of the Chalkias et al. (2020) should_reject corpus, and accepts every Wycheproof positive case.

Acceptance

  • 100% of Chalkias et al. (2020)'s malleability/cofactor-edge-case corpus marked "should_reject" is rejected by verify_strict (M-chalkias milestone, Appendix B).
  • 100% of Wycheproof eddsa_test.json cases pass under the mode (strict/lax) the vector's flags indicate.
  • verify_strict completes in ≤ 60 µs (M3).
Fixtures
Fixture Purpose Expected Output
ed25519.rfc8032_verify_7_1.json RFC 8032 section 7.1 verification all pass
ed25519.chalkias_should_reject.json malleability/cofactor corpus 100% rejected under strict

Pitfalls
  • Implementing the naive (non-cofactor-scaled) equation hA+R=sB as the strict-mode default instead of the [8]-scaled form reintroduces exactly the small-subgroup confusion ADR-08 exists to close — this is the single highest-value correctness check in the whole verification path.
  • Applying the [8] scaling to R and A but forgetting to also scale B's side (s multiplied by 8, or equivalently the whole equation scaled consistently) produces an equation that "usually" passes (both sides wrong by the same factor for prime-order inputs) but silently breaks the small-subgroup defense for contaminated inputs.
  • Sharing a single verify function with an internal boolean flag for strict/lax instead of two distinct, feature-gated entry points (ADR-07) risks a caller accidentally passing the wrong flag at a call site with no compile-time signal.
  • Not rejecting s ≥ L (I6) before the cofactor equation lets a non-canonical s alias to a canonical one after implicit reduction inside the scalar-mul code, reproducing the exact Chalkias et al. (2020) malleability vector (§8.8).

  • curve-cli ed25519 sign piped into curve-cli ed25519 verify round-trips successfully for 1,000 random messages.
  • No internal crate type (FieldElement, Scalar, EdwardsPoint, etc.) is reachable from the public ed25519/x25519 crate root (a cargo public-api diff check).
Fixtures
Fixture Purpose Expected Output
ed25519.batch_consistency_1e3.json batch vs. serial verify on honest inputs identical accept/reject per signature

Pitfalls
  • Drawing z_i from anything attacker-influenced (e.g., derived from the signature bytes themselves rather than the verifier's own RNG) breaks I13's soundness argument entirely — this is a subtle enough mistake that it is worth a dedicated code-review checklist item.

  • A CLI that re-implements even a small piece of cryptographic logic (e.g., its own file-format- specific hashing) instead of delegating everything to the library risks the CLI and library drifting apart — the CLI must be provably "just I/O plus API calls."

⬜ Phase 11 — Constant-Time & Side-Channel Hardening §23

Objectives

Audit and gate the constant-time property (P2, I4) across every layer with cargo miri test and a dudect statistical timing harness, closing the gap between "structurally constant-time by construction" and "verified constant-time in the compiled artifact" (Mental Model MM7, §34).

Deliverable

cargo miri test passes with zero UB reports; dudect reports t ≤ 4.5 for all three target functions; the compiled-artifact inspection report is checked into audits/timing/.

Acceptance
  • cargo miri test exits 0 across the workspace (M-time gate component).
  • dudect t-statistic ≤ 4.5 (M9) for x25519::diffie_hellman, ed25519::sign, and curve-edwards::scalar_mul, each over ≥ 10⁷ measurement pairs.
  • The objdump inspection report documents zero secret-dependent conditional branches in the ladder's inner loop and the comb lookup (named artifact audits/timing/objdump-ladder-2026-Q3.md).
  • The simd-feature build passes the identical dudect gate independently.
Fixtures
Fixture Purpose Expected Output
timing.dudect_x25519.json dudect run on diffie_hellman t ≤ 4.5
timing.dudect_ed25519_sign.json dudect run on sign t ≤ 4.5
timing.dudect_scalar_mul.json dudect run on variable-base scalar_mul t ≤ 4.5

Pitfalls
  • A dudect run with too few measurements (< 10⁷) produces a t-statistic that looks passing by chance — the ≥ 10⁷ floor (M9) is not arbitrary, it is the threshold at which the test has statistical power against a realistic leak magnitude.
  • Compiler auto-vectorization or LTO can restructure "obviously constant-time" source into a branchy compiled artifact — this is exactly why the objdump inspection step exists independent of the dudect statistical test (MM7); rely on both, not either alone.
  • Testing only the "happy path" input distribution (uniform random scalars) misses timing variance triggered specifically by small-order or boundary-value inputs — dudect's fixed-vs-random methodology must include the boundary/small-order corpus as one of its "fixed" classes.

Pitfalls
  • Letting an earlier phase's fixture bucket silently drop out of the aggregate report (e.g., a CI refactor that only re-wires the newest phase's fixtures) is a regression that passes CI while actually testing less than before — the aggregate report's bucket count, not just its pass/fail, must be checked against a known-good baseline.
  • Seeding fuzz targets from scratch instead of from the Wycheproof/Chalkias corpora wastes the first many CPU-hours of a fuzz run rediscovering already-known edge cases instead of exploring new state.
  • Treating the 24-hour canary as sufficient for Sealed skips exactly the deep, rare-state bugs the 30-day canary exists to surface — the two canaries gate different milestones (Appendix B) for this reason and neither substitutes for the other.

⬜ Phase 13 — Release Engineering, Packaging & Audit Readiness §25

Objectives

Close the loop from "passes every internal gate" to "ready to ship": reproducible builds, SBOM generation, artifact signing, and the external-audit engagement package (§31).

Deliverable

A signed, reproducible release artifact on crates.io with an attached SBOM; an audit-ready package under audits/reviews/; the Sealed milestone tag applied only once all gates are green.

Acceptance
  • Two independent CI runners produce byte-identical release binaries (reproducibility gate, named fixture release.reproducible_build_diff.json).
  • SBOM lists 100% of transitive dependencies with license metadata, zero cargo-deny policy violations.
  • Release artifact signature verifies against the published public key.
  • Sealed tag is applied only when M11, M12, and the external audit's P0/P1 count are all green simultaneously (Appendix B gate).

Pitfalls
  • A "reproducible" build that actually depends on an unpinned environment variable (build timestamp, absolute path embedded via debug_assertions) fails the byte-identical diff intermittently — chase this down to a fully hermetic build environment (containerized CI, SOURCE_DATE_EPOCH pinning) rather than accepting "usually reproducible."
  • Publishing the SBOM without cross-checking it against deny.toml risks a license-policy violation shipping silently — the two must be generated from the same Cargo.lock in the same CI step, not as separate, potentially-drifted processes.
  • Tagging Sealed before the 30-day canary (M12) completes, under release-schedule pressure, is the single most common process shortcut that undermines this entire blueprint's evidence-based release discipline (P10) — there is no override for this gate.
