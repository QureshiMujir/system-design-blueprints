Decisions (§9) · 32 ADRs

001

Language

Chosen

Python 3.11+

Rejected

Rust (orchestration), Go, Scala

When the rejected choice is right

Rust orchestration wins when the dedup/contamination scan IS the bottleneck (>10⁹ records, LSH banding > 50% wall-time); Go wins in a multi-tenant service needing low memory and goroutine concurrency without GIL reasoning.

Why: Orchestration is I/O-bound (inference dominates); LLM + data ecosystem is Python; CPU hot paths (LSH/ANN) call native (faiss/NumPy) behind a typed NearDupIndex (Rust/pyo3 backend noted, not built now).

002

Recipe/record schema

Chosen

pydantic v2 + JSON Schema

Rejected

dataclasses, attrs, raw dict

When the rejected choice is right

Raw dicts win in a hot micro-batch system where pydantic validation overhead (µs/record × 10⁸) becomes measurable; dataclasses win in a library targeting minimal dependencies.

Why: Validated recipes/records; JSON-Schema export for constraints; clear typed errors.

003

Async/concurrency

Chosen

asyncio + bounded worker pool

Rejected

threads, multiprocessing-only, Celery

When the rejected choice is right

Threads win when all backends are synchronous C-extension calls (no async-I/O benefit, and context overhead dominates). Celery wins when jobs must survive process crashes across a cluster of untrusted workers with a full broker.

Why: Generation is async I/O; bounded concurrency gives backpressure (I10) without GIL pain.

004

CPU-bound dedup

Chosen

datasketch (MinHash/LSH) + faiss/hnswlib (ANN)

Rejected

pure-Python, Annoy, ScaNN

When the rejected choice is right

Annoy wins for read-heavy static indices needing low memory and no GPU (no training phase, mmapped). ScaNN wins for extremely high throughput query-serving on GCP TPU/GPU with quantization.

Why: Battle-tested; faiss for scale + spill; behind NearDupIndex for swap-out.

005

Durable run state

Chosen

SQLite (default) / Postgres (scale) via SQLAlchemy Core

Rejected

files-only, Mongo

When the rejected choice is right

Files-only (append-log + index) wins when Postgres is unavailable (edge/embedded deploy) and the run count is small enough that a linear scan suffices. Mongo wins when schema-free record variants are frequent and lateral joins are rare.

Why: ACID + WAL for crash-only resume (I2); Postgres for multi-worker (Scalability Analysis).

006

Blob store

Chosen

content-addressed local FS (default) / S3

Rejected

DB blobs, plain files

When the rejected choice is right

DB blobs win in a fully embedded single-process deployment where FS atomicity is unreliable (network FS, exotic OS). Plain files win in a read-only archive where the overhead of hashing+verification is not justified by integrity risk.

Why: Hash = address (I12); dedup of identical blobs; S3 for scale.

007

Canonical hashing

Chosen

SHA-256 over RFC-8785 JSON (recipes/manifests); BLAKE3 for blobs

Rejected

MD5, pickle hash

When the rejected choice is right

MD5 wins in legacy integration contexts where existing systems use MD5 and re-hashing the entire corpus is not feasible. BLAKE3 over everything wins when recipe canonical-hash performance (not stability) is the bottleneck.

Why: Stable across key order (I1); BLAKE3 fast for large blobs.

008

Serialization (records)

Chosen

JSONL (interchange) + Arrow/Parquet (bulk)

Rejected

pickle, protobuf

When the rejected choice is right

Protobuf wins when strict schema enforcement across teams is critical and the binary size/speed differential matters (high-throughput inter-service streaming). Pickle wins in a purely internal, same-version, same-Python run-local context where human-readability is irrelevant.

Why: Human-diffable + columnar bulk; HF-compatible.

009

Generator backend

Chosen

pluggable Generator trait: local (transformers/vLLM client), API, #330 runtime

Rejected

hardwire one provider

When the rejected choice is right

Hardwiring one provider wins in a single-vendor, cost-optimized production deployment where abstraction overhead and maintenance cost of adapters outweigh portability.

Why: Backend-agnostic; record fingerprint for I1/I4.

010

Templating

Chosen

Jinja2 (sandboxed) + a Constraint protocol

Rejected

f-strings, custom DSL

When the rejected choice is right

f-strings win in a closed system with no external operator-supplied templates (no injection risk, maximum simplicity). A custom DSL wins when template expressivity needs to be deliberately constrained (e.g., no loops, safer for multi-tenant).

Why: Mature, sandboxable; constraints decoupled from templates.

011

Schema-constrained gen

Chosen

JSON-mode / grammar (backend) + pydantic re-validate + critique-revise

Rejected

trust raw output

When the rejected choice is right

Trusting raw output wins only when (a) the backend provides a formally verified grammar decoder, (b) downstream validation is guaranteed, and (c) revise-loop latency is unacceptable.

Why: Belt-and-suspenders; revise loop handles malformed (I14).

012

Tokenizer

Chosen

tokenizers (HF) — model-matched

Rejected

naive whitespace

When the rejected choice is right

Naive whitespace wins when token-exact billing is not required and per-record tokenizer overhead is a measurable hotspot (high-rate pre-filter of very short texts).

Why: Accurate token counts for budget (I11) + length filters.

013

Embeddings (dedup cluster)

Chosen

pluggable embedder (#330/#329/local) behind Embedder

Rejected

hardwire

When the rejected choice is right

Hardwiring wins when a single model is standardized org-wide and the adapter protocol adds latency overhead at >10⁷ embed/s.

Why: Reuse training-pipeline embeddings; swap-out.

014

Contamination set

Chosen

benchmark texts (lm-eval-harness corpora) → Bloom filter (#70) + exact confirm

Rejected

hash-only, full scan

When the rejected choice is right

Hash-only wins for tiny benchmark corpora where Bloom construction overhead exceeds full-scan cost. Full scan wins when FP rate of 1% is still too high and the corpus fits in RAM.

Why: Scalable membership (≤1% FP) + exact confirm for I7.

015

PII detection

Chosen

presidio (NER + regex recognizers) behind PIIDetector

Rejected

regex-only

When the rejected choice is right

Regex-only wins in a narrow-domain system where PII is always a known, structured format (SSNs, credit cards) and NER model latency is unacceptable (real-time stream).

Why: Higher recall; locale-tunable; swap-out.

016

DP mechanism

Chosen

Gaussian/Laplace + RDP accountant (cross-link #377)

Rejected

none, ε-only

When the rejected choice is right

ε-only (pure DP) wins when the adversary model is central and δ=0 is a hard regulatory requirement (some government data-sharing agreements). No DP wins when the data has no real-world individual at risk (purely synthetic with no seed personal data).

Why: Aggregate DP with tight composition (I15).

Alternative Architectures (Roads Not Taken)

Alt-A — Pure Streaming Event Bus Architecture

Generator Workers → Kafka Topic[raw_records]
                  → Filter Workers (stateless consumers) → Kafka Topic[filtered]
                  → Dedup Workers (shared Redis/RocksDB state) → Kafka Topic[clean]
                  → Assemble Workers → Object Store
Lineage: Kafka event headers carry record-id + stage tags

Regime where it wins: real-time, continuously-updated datasets (e.g., live preference feedback from a deployed model); very high throughput (>10⁶ records/hour); multi-tenant generation from many concurrent recipe owners. The real system that embodies it: Kafka-based feature pipelines in recommendation systems (Netflix, LinkedIn). Why rejected here: (a) dataset generation is fundamentally a batch job (a recipe targets a fixed count); (b) dedup requires global state (the MinHash/LSH index), which is hostile to stateless streaming consumers; (c) Kafka adds operational complexity without benefit when a single-run batch job is the workload; (d) contamination and leakage-barrier checks require a "view of the whole corpus" that streaming makes expensive.

Alt-B — Actor / DAG Scheduler Architecture (Ray-style)

RecipeActor → SeedActor(s) → GeneratorActor(s) [autoscaled]
                            → FilterActor(s) [stateless, autoscaled]
                            → DedupActor [stateful, single or sharded]
                            → AssembleActor
Each Actor = a Ray remote function with result refs (object store) as continuations

Regime where it wins: heterogeneous resource pools (some actors on GPU, some on CPU, some on external API); elastic autoscaling where generator actor count tracks backend rate limits; large-scale distributed dedup via sharded actor state. The real system that embodies it: Ray-based ML pipelines (Anyscale, many LLM serving systems). Why rejected here: (a) Ray adds a significant runtime dependency and operational surface; (b) the primary scaling bottleneck (backend inference) is addressed by a bounded asyncio pool without distributed scheduling overhead; (c) global dedup state (LSH index) sharding across actors introduces coordination complexity that the current single-node design avoids; (d) the waterfall batch workload does not need Ray's dynamic task graph.

Alt-C — Database-Native Pipeline (dbt / SQL Transform Architecture)

SeedTable → GeneratedRecordsTable (via UDF calling LLM API)
          → FilteredRecordsView (SQL predicates on score columns)
          → DedupedView (window functions + hash dedup)
          → SplitTable (JOIN on cluster assignments)
Everything = SQL transforms; lineage via dbt DAG

Regime where it wins: data-warehouse-native teams where the entire data stack is SQL-oriented (Snowflake, BigQuery, DuckDB); when LLM calls are available as SQL UDFs (BigQuery ML, Snowpark); when audit trails are naturally represented as SQL table histories. The real system that embodies it: dbt-based ML feature pipelines, BigQuery ML inference pipelines. Why rejected here: (a) MinHash/LSH banding and embedding-ANN clustering are not naturally expressible in SQL without expensive UDFs; (b) content-addressed blob storage and generation-manifest replay do not map cleanly to relational tables; (c) streaming backpressure against rate-limited APIs is not controllable in SQL; (d) Python's LLM ecosystem has no SQL-UDF equivalent for local model inference.

Alt-D — Immutable Log + Compaction Architecture (Delta Lake / Iceberg style)

append-only record log → periodic compaction jobs (dedup, filter, version)
DatasetVersion = snapshot of the log at a compaction point
Lineage = log offset range + compaction parameters

Regime where it wins: large teams that continuously add to a dataset over months (the dataset grows incrementally); need for time-travel queries (what was the dataset at version N?); integration with Spark/Flink-based training pipelines that already consume Delta/Iceberg tables. The real system that embodies it: Dolma (AI2) uses a similar log-and-snapshot model; Delta Lake for ML feature stores. Why rejected here: (a) our workload is discrete recipe-driven runs, not continuous appends; (b) content-addressed dataset hashing + Merkle lineage already provides time-travel at the run granularity; (c) Spark/Delta Lake adds a JVM runtime dependency inconsistent with a Python-native installable package; (d) compaction jobs on a growing log add latency between generation and assembly that the batch model avoids.
