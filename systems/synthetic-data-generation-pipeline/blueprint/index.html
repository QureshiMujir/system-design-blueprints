332 — Synthetic Data Generation Pipeline from Scratch

Project Number: 332

Project Name: Synthetic Data Generation Pipeline from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a synthetic data generation (SDG) pipeline: a deterministic, fully-provenanced system that turns a declarative generation recipe + seed pools into a versioned, content-addressed dataset suitable for pretraining, fine-tuning (SFT), preference/RL data, eval-set construction, and distillation. The pipeline drives generator models (local / hosted API / the #330 streaming runtime) through prompt templates and generation strategies (Self-Instruct bootstrapping, Evol-Instruct evolution, persona/scenario conditioning, multi-turn dialogue synthesis, teacher→student distillation, schema/grammar-constrained generation), then runs every produced record through a quality gate (heuristic filters, safety/toxicity classifiers, factuality/groundedness checks, LLM-judge / reward-model scoring, rejection sampling), a dedup + contamination gate (exact-hash, MinHash/LSH near-dup, embedding-ANN clustering, n-gram overlap vs seed/eval/benchmark corpora), a validation gate (schema/grammar validation, constraint satisfaction, label-consistency, human-in-the-loop review queue), and an assembly + versioning stage (train/dev/test split with leakage barriers, content-addressed dataset hash, lineage manifest, reproducible regeneration, export formats). An optional privacy/safety gate (PII detection/scrubbing, differential-privacy noise on aggregates, memorization/regurgitation checks against source corpora, license/provenance tracking) gates sensitive corpora.

System boundaries (in scope):

  • Declarative recipe spec (sdg.spec): task type, generator model+version pin, prompt templates, sampling params, target count, taxonomy/coverage targets, constraints, gate configs.
  • Seed/exemplar pools + taxonomy (sdg.seed): curated exemplars, topic taxonomy, coverage targets, seed provenance.
  • Pluggable generator backend (sdg.generate): local model, hosted API, #330 runtime; batching, retries, cost/token budget, recorded generation manifest (request → response → token usage → model fingerprint).
  • Template / transform engine (sdg.template, sdg.transform): variable substitution, format/JSON/grammar-constrained output, critique-and-revise (self-correction) loops.
  • Generation strategies: Self-Instruct, Evol-Instruct (depth/breadth mutation), persona/scenario conditioning, multi-turn synthesis, distillation, constrained generation.
  • Quality filter (sdg.filter): length/format/language-id/perplexity heuristics, toxicity/safety classifier, factuality/groundedness, LLM-judge + reward-model scoring, rejection sampling, difficulty calibration. Shared scorer protocol with #331 AI Evaluation Harness.
  • Dedup + diversity (sdg.dedup): exact hash, MinHash/LSH near-dup, embedding-ANN clustering, n-gram contamination check vs seed/eval/benchmark sets, diversity/coverage balancing. Cross-link #255 ANN, #70 Bloom Filter, #109 Deduplication Engine.
  • Validation (sdg.validate): schema/grammar validation, constraint satisfaction, label-consistency, review queue. Cross-link #257 Data Labeling Platform.
  • Labeling/annotation (sdg.label): auto-label + weak-label + human review reconciliation.
  • Assembly + versioning (sdg.assemble, sdg.version): split assignment with leakage barriers, content-addressed dataset hash, lineage manifest, reproducible regeneration, export (JSONL / Arrow / Parquet / HF-dataset).
  • Privacy/safety (sdg.privacy): PII detect/scrub, DP noise on aggregates, memorization checks, license/provenance. Cross-link #377 Differential Privacy Engine.
  • Observability + lineage (sdg.obs): per-stage yield/accept rates, cost/tokens, diversity metrics, dedup ratios, filter-rejection breakdown, per-record provenance/lineage graph.
  • CLI sdg: init, seed, generate, filter, dedup, validate, assemble, version, replay, explain, audit.

Explicit non-goals (deferred, tracked in Deferred Features Register):

  • Training/fine-tuning the consuming model — the pipeline emits datasets, not weights. Downstream consumers are #329 Vector Embedding Training Pipeline, #120 RLHF. PhaseDeferred("Deferred Features Register: Training/fine-tuning").
  • Building the generator model itself — generators are pluggable backends; we drive them. PhaseDeferred("Deferred Features Register: Building generator model") (cross-link #330).
  • A general-purpose vector DB — we depend on an ANN index for dedup clustering, not build one. PhaseDeferred("Deferred Features Register: General-purpose vector DB") (cross-link #255).
  • Full annotation UI — review queue exposes an API + minimal CLI; rich UI is #257's job. PhaseDeferred("Deferred Features Register: Full annotation UI").
  • Distributed multi-node generation beyond a worker pool against one backend; cross-host shuffle of the dedup index is deferred. PhaseDeferred("Deferred Features Register: Distributed multi-node generation").
  • Formal DP accounting beyond Gaussian/Laplace mechanism + RDP composition on aggregates (per-record DP text generation is out of scope). PhaseDeferred("Deferred Features Register: Formal DP accounting") (cross-link #377).
  • Arbitrary code execution sandbox — code-data execution checks call out to #50 Sandbox; we do not build the sandbox. PhaseDeferred("Deferred Features Register: Code execution sandbox").

Deployment model: a Python package (sdg, installable) plus a CLI driver. Runs as (a) a one-shot batch job from a recipe file, or (b) a long-running worker pool reading a recipe + writing a content-addressed dataset to an object store / local FS. Stateless workers; durable state in a RunStore (SQLite default, Postgres optional) + content-addressed BlobStore (local FS / S3). Embeds in an MLOps pipeline as the "data factory" stage upstream of training.

Target users/operators/developers: ML/data engineers building SFT/eval/distillation corpora; research engineers running Self-Instruct/Evol-Instruct studies; data-platform engineers who must prove provenance + non-contamination for an audit; operators debugging a low-yield run or a cost-budget overrun at 3 a.m.

Phase 0 deliverable (numbered packages/modules):

  1. sdg.spec — recipe schema (GenerationSpec), recipe parser/validator, RecipeHash, error enum.
  2. sdg.types — Record, RecordId, Provenance, GateVerdict, RunManifest, DatasetManifest, Lineage.
  3. sdg.store — RunStore (run/record/verdict tables) + BlobStore (content-addressed blobs) + WAL.
  4. sdg.generate — Generator backend trait + an EchoGenerator stub (deterministic) + generation manifest recorder.
  5. sdg.template — template engine (variable substitution, format directive) + template registry.
  6. sdg.pipeline — stage DAG runner (single-thread first), stage state machine, idempotent re-run.
  7. sdg.obs — structured event log + per-stage counters; explain renderer.
  8. sdg — CLI: init (scaffold recipe), generate (echo backend), assemble (trivial), explain.

What later phases unlock: seed pools + taxonomy + coverage (§13); generator backend abstraction + determinism manifest + budget (§14); template/transform + schema-constrained generation + critique-revise (§15); Self-Instruct bootstrapping (§16); Evol-Instruct + multi-turn + distillation (§17); quality filtering — heuristics + classifiers + judge/reward + rejection sampling (§18); dedup — exact + LSH + embedding-ANN + contamination (§19); contamination guard (§20); validation + schema enforcement + review queue (§21); assembly + split/leakage barriers + content-addressed versioning (§22); privacy/safety gate (§23); observability + lineage graph + cost (§24); soak + conformance + reproducible regeneration + differential (§25).

Timeline: Phase 0 = 6–14 weeks. Full plan = 6–10 months.

Recommended language: Python 3.11+. Rationale (locked ADR-001): (a) the generator/LLM ecosystem (tokenizers, model SDKs, HF datasets, inference clients) and the data-tooling ecosystem (pyarrow, pandas, datasketch, faiss/hnswlib bindings) are Python-native — the pipeline is an orchestration + I/O-bound system, not a CPU hot loop; (b) generation latency is dominated by model inference (network/GPU), so GIL contention is a non-issue for the orchestration layer (concurrency via asyncio + a bounded worker pool over async I/O); (c) the few CPU-bound hot paths (near-dup MinHash/LSH banding, n-gram contamination scan, embedding ANN) call into vectorized NumPy / a compiled index (faiss/hnswlib) or are gated behind a typed NearDupIndex interface with a possible Rust/pyo3 backend (considered & rejected for the orchestration layer, noted for the index — see ADR-001 note); (d) pydantic gives schema-validated recipes + records "for free"; (e) reproducibility is achievable via pinned model fingerprints + seeds + recorded manifests rather than language-level determinism. A Rust core for the dedup/validation hot path was considered and rejected for orchestration (interop + ecosystem cost outweighs benefit when inference dominates wall-time) but is noted as the future backend for NearDupIndex if the LSH/banding scan becomes the bottleneck at >10⁹ records.

Prerequisites: LLM sampling (temperature/top-p/top-k, logit bias, grammar-constrained decoding); prompt engineering + instruction-tuning data formats (SFT, preference pairs, multi-turn chat templates); Self-Instruct & Evol-Instruct methodology; MinHash / LSH / Jaccard near-dup; approximate nearest neighbor (HNSW/IVF) for embedding clustering; n-gram overlap & benchmark contamination; reward models / LLM-as-judge scoring + calibration; content-addressed storage + Merkle hashing; data-split leakage analysis; differential privacy basics (Laplace/Gaussian mechanism, RDP composition); PII detection (regex + NER); Python asyncio + backpressure; idempotent pipeline design.

2. Why Build This

  • Unique systems knowledge: the data factory control plane behind modern LLM training. Most teams treat synthetic data as a script; this builds it as a provenance-complete, reproducible, gated pipeline — the part that decides whether a fine-tune is auditable and uncontaminated, or a liability. You learn why "regenerate the dataset" must be a deterministic operation, and how to prove a train split never saw a benchmark.
  • Historical/architectural significance: Self-Instruct (Wang 2022) and Evol-Instruct/WizardLM (Xu 2023) showed that a strong model can bootstrap instruction data; Alpaca/Vicuna/Orca distillation pipelines productionized it; the contamination crises (GSM8K/MMLU leakage into training corpora) forced the field to treat dedup + contamination as first-class. This project rebuilds that arc end to end with the gates that the early scripts lacked.
  • Engineering muscles: idempotent stage DAGs with content-addressed checkpoints; determinism in a non-deterministic-looking system (LLM sampling) via fingerprint + seed + recorded manifest; rejection-sampling + reward calibration; near-dup at scale (MinHash/LSH + ANN); leakage-barrier split assignment; lineage graphs; cost/token budgeting under retries; DP accounting.
  • Production concepts exercised: backpressure against rate-limited generator APIs; cost ceilings + budget exhaustion; partial-failure recovery (a stage dies mid-run, resume from checkpoint); poison-record containment; schema evolution of a dataset format; SBOM-style lineage manifests; audit + reproducibility gates.
  • Cross-links:
    • #330 Streaming LLM Runtime — a generator backend; shared model-fingerprint vocabulary.
    • #331 AI Evaluation Harness — shared scorer protocol (the same LLM-judge / reward scorers gate generation and eval).
    • #255 ANN Index, #70 Bloom Filter, #109 Deduplication Engine — the dedup/near-dup substrate.
    • #257 Data Labeling Platform — the human review queue + label reconciliation.
    • #377 Differential Privacy Engine — the DP mechanism + accountant used by sdg.privacy.
    • #50 Sandbox — code-data execution checks (does generated code run/pass tests).
    • #329 Vector Embedding Training Pipeline, #120 RLHF — downstream consumers of the datasets this pipeline emits.
  • Calibration value: after this you can design any data-generation system so that every record is provenanced, every dataset is reproducible from a recipe, contamination is provably absent, and cost/quality/diversity are observable dials — and you can debug a "the fine-tune got worse" incident back to a specific recipe + filter-config change.

What Mastery Looks Like

  • Provenance-complete pipeline design (Phase 0, Phase 12): architect any data-generation system where every record is traceable to its origin, gates, and splits — and prove reproducibility from a recipe hash.
  • Determinism under non-determinism (Phase 2, Phase 12): pin model fingerprints, seeds, and manifests so replay is bit-identical; diagnose reproducibility breaks by bisecting manifest fields.
  • Dedup and contamination at scale (Phase 7, Phase 8): apply MinHash/LSH banding, embedding-ANN clustering, and n-gram Bloom filtering to eliminate near-dups and benchmark leakage in corpora of 10⁷+ records; know the tradeoffs of each technique.
  • Quality gating and calibration (Phase 6): chain heuristic → safety → judge → rejection-sampling gates in cost order; calibrate thresholds against labeled sets; diagnose yield collapse vs false-positive nuking.
  • Leakage-barrier split assignment (Phase 10): assign near-dup clusters wholesale to one split; prove no paraphrase straddles train/test; audit with a post-assembly contamination re-scan.
  • Cost control under retries and rate limits (Phase 2, Phase 4): enforce hard token/$ ceilings with a budget ledger; implement pre-response dedup to avoid paying for duplicate answers; tune concurrency against backend rate caps.
  • Privacy gate engineering (Phase 11): apply PII detection/scrubbing with lineage-preserving child records; apply DP noise only to aggregates with an RDP accountant; detect regurgitation via long-span matching.

Per-box dense notes:

  • Operator / GenerationSpec + Seeds — declarative recipe (task type, model+version pin, templates, sampling params, target count, taxonomy/coverage targets, gate configs) + seed/exemplar pools + topic taxonomy. Trust boundary: recipe validated by sdg.spec before any model call; malformed recipe rejected with typed error.
  • Pipeline orchestrator — stage DAG (SEED→GENERATE→TRANSFORM→FILTER→DEDUP→VALIDATE→LABEL→[PRIVACY]→ASSEMBLE→VERSION). Each stage writes a content-addressed checkpoint; re-run resumes from the last durable stage (idempotency invariant I2). Single-writer to the RunManifest.
  • Seed + taxonomy — exemplar pools with provenance; topic taxonomy with per-node coverage targets; a coverage-gap sampler picks under-covered taxonomy nodes to bias generation (diversity, principle 9).
  • Generation strategies — pure transformations from (seeds, taxonomy, prior records) → generation requests: Self-Instruct (sample exemplars, prompt for new instructions), Evol-Instruct (mutate an instruction depth/breadth-wise), persona/scenario conditioning, multi-turn synthesis (role-played dialogue), distillation (teacher generates target for a prompt), constrained generation (grammar/schema). Strategy choice is recorded in Provenance.
  • Generator backend — pluggable Generator (local model / hosted API / #330 runtime). Batches requests, retries with backoff, enforces a cost/token budget, and records a generation manifest (request hash → response → token usage → model fingerprint) so a run is replayable/auditable. Determinism: same (prompt, sampling params, seed, model fingerprint) → same recorded response (replay reads manifest; live mode pins seed where backend supports it).
  • Template / transform — variable substitution into prompt templates; schema/grammar-constrained output (JSON-mode / grammar decoding); critique-and-revise (self-correction) loop that re-prompts on a failed validation. Concurrency boundary: transform is per-record, stateless.
  • Quality filter — an ordered chain of gates; each appends an immutable GateVerdict{gate, score, pass, reason} to the record (records are never mutated, only annotated — principle 5). Heuristics (length/format/language-id/perplexity) → safety/toxicity classifier → factuality/groundedness → LLM-judge / reward-model score → rejection sampling → difficulty calibration. Rejected records go to quarantine (kept for audit, never assembled — invariant I8). Shared scorer protocol with #331.
  • Dedup + diversity — exact-hash dedup (content hash) → near-dup (MinHash signature + LSH banding) → embedding-ANN clustering (semantic near-dup) → diversity/coverage balancing (down-sample over-represented clusters). Order-independent + idempotent (invariant I6). Cross-link #109, #255.
  • Contamination guard — n-gram (e.g., 13-gram, configurable) overlap of each candidate vs seed/eval/benchmark corpora using a Bloom filter (#70) + exact confirm; any candidate overlapping a benchmark is barred from the train split (invariant I7).
  • Validation + label — schema/grammar validation, constraint satisfaction (e.g., answer matches format), label-consistency checks; a human-in-the-loop review queue (#257) for low-confidence records; auto-label + weak-label reconciliation.
  • Privacy / safety gate — PII detection/scrubbing (regex + NER), optional differential-privacy noise on aggregates (#377), memorization/regurgitation check (does a record reproduce a long span from a source corpus), license/provenance tracking. Optional, inserted before ASSEMBLE when the recipe enables it.
  • Assembly + version — assigns records to train/dev/test with leakage barriers (near-dup clusters never straddle splits — invariant I9), computes a content-addressed dataset hash (Merkle over sorted record hashes + manifest), writes a lineage manifest (recipe + model fingerprints + gate configs + seeds + per-record provenance), and exports (JSONL / Arrow / Parquet / HF-dataset). Reproducible regeneration: same recipe+seeds+fingerprints → same dataset hash (invariant I1).
  • Store — RunStore (runs, records, verdicts, lineage; SQLite/Postgres; WAL for crash-only restart) + BlobStore (content-addressed blobs: prompts, responses, datasets). Durable checkpoints enable resume; the full audit trail lives here.
  • Observability + lineage — per-stage yield/accept rates, cost/tokens, diversity metrics, dedup ratios, filter-rejection breakdown; a per-record lineage graph (seed → prompt → response → verdicts → split). Off the hot path; counters + structured events.

4. System Constraints

Dimension Target
Generation throughput backend-bound; orchestrator sustains ≥ 2000 in-flight requests; ≥ 95% of wall-time in model inference, < 5% orchestration overhead
Orchestration overhead per record ≤ 2 ms CPU (excl. model + gate inference) p95
Filter gate latency (heuristic) ≤ 1 ms/record p95 (length/format/lang-id); perplexity/classifier/judge are model-bound, batched
Near-dup (MinHash+LSH) throughput ≥ 50k records/s/core (128-perm signature, 16 bands) on text ≤ 4 KB
Embedding-ANN query p95 ≤ 5 ms/record at 10⁷ index (HNSW, recall ≥ 0.95)
n-gram contamination scan ≥ 100k records/s/core vs a Bloom filter of 10⁹ benchmark n-grams (≤ 1% FP, exact confirm on hit)
Memory ceiling (worker) default 4 GiB; bounded queues; spill the dedup index to disk above threshold
In-flight queue bound (backpressure) per-stage queue cap (default 10k); full → throttle upstream (no unbounded buffering)
Cost budget hard per-run token/$ ceiling; budget-exhausted → graceful stop + checkpoint (no overrun)
Determinism identical (recipe, seeds, model fingerprints, gate configs) ⇒ identical DatasetManifest hash + per-record verdicts
Idempotent resume re-run from any crash resumes at last durable stage; no duplicate records, no double-spend of budget
Reproducible regeneration (replay) replay from recorded generation manifest ⇒ bit-identical records + identical split assignment
Contamination guarantee 0 benchmark n-gram matches in any train split (hard gate I7)
Dedup idempotency running dedup twice ⇒ identical surviving set; order-independent (I6)
Provenance completeness every emitted record carries full Provenance (model fp, recipe hash, seed, strategy, all gate verdicts) (I3)
Startup (CLI cold) ≤ 500 ms to first task dispatched (excl. model load)
Shutdown drain in-flight ≤ 30 s; checkpoint; no orphaned blobs; budget ledger flushed
Availability batch job; crash = resume from checkpoint (no mid-record durability needed)
Recovery time objective resume from last durable stage; bounded by that stage's remaining work
FD / connection budget ≤ 256 open blobs/connections; pooled HTTP to backend
Storage amplification quarantine + lineage ≤ 2× emitted-dataset bytes (audit retention tunable)

Scaling assumptions: single node default (8–64 cores, 32–512 GiB RAM, NVMe for index spill + blobs); worker pool concurrency tuned to backend rate limits; horizontal scaling (multiple worker hosts against a shared RunStore + sharded dedup index) is the seam, deferred. Vertical scaling: asyncio concurrency for I/O-bound generation; multiprocessing / native index for CPU-bound dedup.

6. Design Principles

  1. Provenance is mandatory, not optional. Every record carries full Provenance — generator model fingerprint+version, recipe hash, seed, strategy, and every GateVerdict. Tradeoff: storage + bookkeeping overhead per record. Operational: an auditor can trace any record to its origin and configs. Violation: an unprovenanced record makes the whole dataset unauditable and non-reproducible — it is rejected at assembly (I3).
  2. Reproducibility via fingerprint + seed + recorded manifest, not luck. A dataset is a pure function of (recipe, seeds, model fingerprints, gate configs). Sampling non-determinism is captured in a generation manifest so replay is bit-identical. Tradeoff: must pin models + record every response. Violation: "regenerate the dataset" yields a different dataset → incidents are undebuggable (I1).
  3. Records are immutable; gates annotate, never mutate. A gate appends a GateVerdict; it never edits record content (scrub/transform creates a new versioned record with lineage to the parent). Tradeoff: more records/blobs. Violation: in-place mutation destroys lineage and breaks idempotent re-run (I3, I5).
  4. Idempotent, content-addressed stages. Each stage's output is content-addressed; re-running a stage on the same input yields the same checkpoint; resume picks up at the last durable stage. Tradeoff: hashing + checkpoint storage. Violation: a crash mid-run double-generates records and double-spends the cost budget (I2).
  5. Rejected ≠ deleted; quarantine, never assemble. Filtered/failed records are moved to quarantine (retained for audit + difficulty analysis), never silently dropped and never assembled into a dataset. Tradeoff: quarantine storage. Violation: you cannot explain why yield was low, and a leaked reject corrupts the dataset (I8).
  6. Dedup is order-independent and idempotent. Exact + near-dup + cluster dedup produce the same surviving set regardless of input order or how many times it runs. Tradeoff: canonical tie-break (keep lowest record-id) adds bookkeeping. Violation: non-deterministic survivors → non-reproducible datasets (I6).
  7. No benchmark contamination in train splits — ever. Every train candidate is checked for n-gram overlap against the benchmark corpus; any hit bars it from train. Tradeoff: a contamination corpus + scan cost. Operational: the contamination report is an audit artifact. Violation: leaked benchmark text inflates eval scores → invalid model claims (I7).
  8. Backpressure everywhere; bounded queues. Every producer→consumer edge (generate→filter→dedup→…) is bounded; a full downstream throttles the upstream generator. Tradeoff: lower peak in-flight. Violation: unbounded buffering OOMs the worker while waiting on a slow gate or rate-limited backend (I10).
  9. Diversity + coverage are first-class targets, not byproducts. A coverage-gap sampler biases generation toward under-covered taxonomy nodes; diversity balancing down-samples over-represented clusters. Tradeoff: may reject "good" but redundant records. Violation: mode collapse / model collapse — the dataset is large but narrow (Shumailov 2023).
  10. Cost is a hard ceiling, not a hope. A per-run token/$ budget is enforced; budget-exhausted stops gracefully with a checkpoint, never overruns. Tradeoff: a run may finish under target count. Operational: budget burn-down is a dashboard. Violation: a runaway retry loop bills 10× the budget.
  11. Determinism of the control plane. Stage scheduling, gate ordering, dedup tie-breaks, and split assignment take no wall-clock/PID/thread-order input — only seeds + content hashes. Violation: non-reproducible splits/decisions → replay diverges (I1, I9).
  12. Conservative gates under uncertain scores. When a classifier/judge score is near a threshold (within its calibrated error band), prefer the safe action (reject for safety gates; keep for dedup). Tradeoff: slightly lower yield / slightly more near-dups. Violation: a noisy toxicity score lets unsafe content through, or a flaky judge nukes good data.
  13. Crash-only, resume-from-checkpoint. No mid-record durability gymnastics; on crash, resume from the last durable stage checkpoint. Quarantine + manifests are append-only. Violation: complex partial-record recovery code for a batch system that doesn't need it.
  14. Leakage barriers bind near-dup clusters to one split. A near-dup cluster is assigned wholesale to exactly one of train/dev/test; members never straddle splits. Tradeoff: slightly less control over exact split ratios. Violation: a paraphrase in dev that also appears in train silently leaks the eval (I9).
  15. Observability is on by default. Per-stage yield/accept, cost/tokens, diversity, dedup ratio, rejection breakdown, and a per-record lineage graph are emitted on the (cheap) control path. Violation: you learn the dataset is bad from a failed downstream training run, not a dashboard.

8.3 Pipeline stage state machine

Stage states: Pending → Running → Checkpointed → Consumed   (+ Failed, Resuming)
Pipeline DAG (linear with optional Privacy):
  SEED → GENERATE → TRANSFORM → FILTER → DEDUP → VALIDATE → LABEL → [PRIVACY] → ASSEMBLE → VERSION
A stage is re-runnable iff its input checkpoint hash is unchanged (I2).
On crash: orchestrator finds last Checkpointed stage, sets downstream to Pending, resumes.

Worked example — SFT recipe, Self-Instruct, target 50k:

SEED(175 exemplars, taxonomy=topics_v3)
  └─GENERATE(self_instruct, model=teacher@fp_ab12, seed=7, temp=1.0)→ 120k raw instructions
     └─TRANSFORM(template=sft_v2, JSON-constrained response)→ 120k (prompt,response)
        └─FILTER(heuristic→safety→factuality→judge≥0.7→rejection_sample)→ 78k accepted, 42k quarantine
           └─DEDUP(exact→MinHash/LSH→embed-ANN→diversity)→ 61k unique, 17k near-dup removed
              └─CONTAMINATION(13-gram vs MMLU/GSM8K/…)→ 60.4k clean, 0.6k contaminated→quarantine
                 └─VALIDATE(schema sft, label-consistency)→ 60.1k valid
                    └─ASSEMBLE(train .9/dev .05/test .05, leakage_barrier)→ splits, clusters bound
                       └─VERSION(dataset_hash=sha256(merkle), lineage manifest, export jsonl+parquet)

Yield = 60.1k/120k ≈ 50% (logged per stage). DatasetManifest hash pins identity; replay reproduces it.

8.4 Generation manifest (replay + audit)

GenManifestEntry { request_hash, prompt_blob, sampling, model_fp, seed,

                   latency_ms, attempt, run: RunId, ts_logical }  // ts_logical = monotone seq, NOT wall-clock for decisions

Sealed per request; replay mode reads response_blob keyed by request_hash (I4). Cost summed into the budget ledger (I11).

8.5 Gate verdict semantics (ordered chain)

Heuristic  : pass iff len∈[min,max] ∧ format_ok ∧ lang∈allowed ∧ perplexity≤ppl_max
Safety     : pass iff toxicity_score ≤ tox_thr ∧ no blocked categories   (conservative near threshold → reject)
Factuality : pass iff groundedness_score ≥ ground_thr (vs provided context) | n/a if no context
Judge      : pass iff llm_judge_score ≥ judge_thr     (scorer_fp recorded; shared w/ #331)
Reward     : pass iff reward_model_score ≥ reward_thr (preference data)
RejectionSample : keep top-k by score per (taxonomy node / prompt) — bounded acceptance
Difficulty : tag difficulty bucket (easy/med/hard) by score percentile; may down/up-sample

Verdicts are append-only; a record passed iff every blocking gate passed (rejection_sample/difficulty are shaping, not blocking). Quarantine carries the failing verdict for audit (I8).

8.7 Malformed / failure-path examples

  • Recipe with train+dev+test ≠ 1.0 → SpecError::SplitFractions (pre-run).
  • GeneratorRef missing Fingerprint → SpecError::UnpinnedModel (determinism would break I1; rejected).
  • Sampling seed absent → SpecError::MissingSeed (I1).
  • Generator returns malformed JSON under a JSON constraint → critique-revise retry (≤ N); exhausted → Quarantine(reason=schema).
  • Budget exhausted mid-GENERATE → stop, checkpoint, BudgetExhausted (I11); resume requires raising budget.
  • A gate scorer (judge model) unavailable → stage Failed; resume after backend restored (no records lost, I2).
  • Dedup tie with equal content but two record-ids → keep min(record-id) deterministically (I6).
  • Near-dup cluster spans would straddle splits → reassign whole cluster to one split (I9).

12. Phase 0 — Repo Skeleton, Core Types, Recipe Parser/Validator + RecipeHash, RunStore + BlobStore, MockGenerator, Linear Orchestrator + Checkpoint/Resume, CLI

12.1 Objectives

Stand up the skeleton and the spine that every later phase plugs into: typed records (I5), the recipe parser + RecipeHash (I1), durable RunStore/BlobStore (I2/I12), a deterministic MockGenerator, a linear stage orchestrator with content-addressed checkpoints + resume (I2), and the sdg CLI. Constraint introduced: no stage mutates a record; checkpoints are content-addressed.

12.2 Detailed Implementation Steps

  • sdg.spec.recipe — GenerationSpec (pydantic, frozen); sdg.spec.validate (fractions sum 1.0, pinned model fingerprint, mandatory seed); sdg.spec.canonical → RecipeHash (RFC-8785 + SHA-256, ADR-007).
  • sdg.types.{record,provenance,manifest,ids} — Record/Content/Provenance/GateVerdict/DedupInfo/Split; frozen mutation guard (I5); content-addressed RecordId.
  • sdg.store.runstore (SQLAlchemy Core + WAL, ADR-005) + sdg.store.blobstore (content-addressed FS, hash-verify, I12).
  • sdg.generate.backend MockGenerator (echo/templated, deterministic by seed) — unblocks the pipeline with no spend.
  • sdg.pipeline.{dag,runner,state,checkpoint} — linear DAG SEED→…→VERSION; idempotent stage runner; resume from last_checkpoint (I2); StageState machine (§8.3).
  • sdg.cli.main (typer, ADR-020) — init/seed/generate/…/version/replay/explain.

12.3 Deliverable

sdg init <recipe> validates + hashes a recipe; sdg generate --backend mock runs the full linear pipeline (mock at every gate) producing a tiny versioned dataset + DatasetManifest; kill/restart resumes at the last checkpoint.

12.4 Acceptance Criteria

  • Same recipe → identical RecipeHash regardless of key order (I1).
  • Mock end-to-end yields a DatasetManifest with a stable dataset_hash across runs (I1).
  • Kill mid-pipeline → resume re-runs only uncheckpointed stages (I2); no double-generate; verified by the checkpoint/resume fixture (conformance/recipes/minimal.json, kill-after-FILTER, N.5).
  • Frozen Record rejects mutation (I5).

12.5 Conformance Fixtures

  • conformance/recipes/minimal.json → parsed + hashed.
  • conformance/golden_datasets/mock_tiny/ → expected DatasetManifest + records.
  • conformance/recipes/bad_fractions.json → SpecError::SplitFractions.
  • checkpoint/resume fixture (kill after FILTER) → resume continuity.

12.6 Pitfalls

  • Non-canonical recipe hashing → identical recipes hash differently; fix RFC-8785 (ADR-007).
  • Mutating a record in place → broken lineage (I5); fix frozen models + copy-with.
  • Checkpoint keyed by wall-clock/run-id → resume never matches; fix content-addressed input_hash (I2).
  • Orchestrator holding all records in memory → OOM; fix streaming batches + bounded queues (I10).

12.7 Performance Concerns

Hashing is the per-record cost → BLAKE3 for blobs (ADR-007), SHA-256 only for identity. WAL batch-commit to amortize fsync. Stream records through stages; never materialize the full corpus.

12.8 Edge Cases

Empty recipe; target_count=0; duplicate seed pool ids; recipe referencing a missing template (caught at validate); resume when no checkpoint exists (start fresh).

12.9 Failure Analysis

RunStore corruption → rebuild record/verdict tables from append-only event log + blobs (blobs are source of truth). Blast radius: one run. Detection: blob hash-verify on read (I12). Postmortem: event log replay.

12.10 Operational Notes

Metrics: stage_checkpoint_hash, resume_stage, records_in/out per stage. Crash-only posture from day one (Principle 13). sdg explain <run> renders stage states. Schema/recipe SemVer wired into the manifest from Phase 0.

13. Phase 1 — Seed Pools, Taxonomy, Coverage Targets, Coverage-Gap Sampler

13.1 Objectives

Make generation targeted, not blind: curated seed/exemplar pools with provenance, a topic taxonomy with per-node coverage targets, and a coverage-gap sampler that biases generation toward under-covered nodes (Principle 9). Constraint: diversity/coverage are first-class inputs to GENERATE.

13.2 Detailed Implementation Steps

  • sdg.seed.pools — exemplar pools with seed provenance (source, license, hash); immutable; provenance carried into every record (Principle 1, I3).
  • sdg.seed.taxonomy — topic/skill taxonomy (tree); per-node target counts/fractions (diversity as first-class input, Principle 9, MM10).
  • sdg.seed.sampler — coverage-gap sampler: pick taxonomy nodes weighted by (target − current); deterministic given seed (Principle 11, control-plane determinism).
  • Coverage accounting wired to the run (current counts per node updated as records pass ASSEMBLE-eligibility).

13.3 Deliverable

sdg seed --recipe <r> materializes pools + taxonomy; the sampler emits a deterministic, coverage-weighted plan of (node, count) generation targets.

13.4 Acceptance Criteria

  • Sampler output deterministic given a seed (Principle 11).
  • Coverage plan sums to target_count exactly (0 drift); biases toward under-covered nodes; verified by conformance/recipes/taxonomy_v3.json (N.5).
  • Seed pools carry provenance + license (audit).

13.5 Conformance Fixtures

  • conformance/recipes/taxonomy_v3.json + expected coverage plan.
  • skewed-coverage fixture → sampler fills the gap nodes first.

13.6 Pitfalls

  • Seedset leakage → seeds identical to benchmark items contaminate downstream; fix: contamination check on seeds too (I7).
  • Taxonomy drift → coverage targets don't sum; fix: validate tree + fractions at parse.
  • Non-deterministic sampler → irreproducible datasets; fix: seeded RNG only (Principle 11).
  • Over-narrow seeds → mode collapse despite coverage targets; mitigate with diversity gate (Phase 7).

13.7 Performance Concerns

Taxonomy is small (in-memory); coverage counters are O(nodes). Sampler is O(target_count·log nodes) with a weighted heap. No hot-path cost.

13.8 Edge Cases

Node with target but no seeds (generate from description only); single-node taxonomy; target_count < node count (some nodes get 0); duplicate exemplars across pools (dedup at seed time).

13.9 Failure Analysis

A bad taxonomy/coverage config produces a large-but-narrow dataset (model collapse, Shumailov 2023). Detection: post-run diversity metrics (Phase 12) vs targets. Recovery: re-weight + regenerate. Postmortem: coverage report per node.

13.10 Operational Notes

Metrics: coverage_per_node, coverage_gap, seed_pool_size. Coverage report is an audit artifact. Seed provenance + license tracked into Provenance (Principle 1).

14. Phase 2 — Generator Backend Abstraction, Batching/Retry/Backpressure, Budget Ledger, Generation Manifest (Determinism + Replay)

14.1 Objectives

Make generation backend-agnostic, cost-bounded, and replayable: a pluggable Generator (local/api/#330), bounded-concurrency batching with retry/backoff (I10), a hard budget ledger (I11), and a per-request generation manifest that makes replay bit-identical (I4). Constraint: every request→response is recorded before its tokens are spent against the budget.

14.2 Detailed Implementation Steps

  • sdg.generate.backend — Generator protocol (complete(req), fingerprint); adapters: local (transformers/vLLM client), API, #330 runtime (ADR-009).
  • sdg.generate.batch — asyncio bounded worker pool (ADR-003); retry + exponential backoff; backpressure when downstream full (I10).
  • sdg.generate.manifest — record GenManifestEntry (request_hash, prompt_blob, sampling, model_fp, seed, response_blob, tokens, cost, ts_logical) (I4); replay reads response_blob by request_hash.
  • sdg.generate budget ledger (BudgetLedger) — charge tokens/cost; Exhausted → checkpoint + stop (I11).

14.3 Deliverable

sdg generate runs against any backend; a second run in --replay mode reproduces identical raw generations from the manifest with zero new spend.

14.4 Acceptance Criteria

  • Replay reproduces byte-identical raw responses from the manifest (I4).
  • Budget ceiling never exceeded (0 tokens over the recipe's ceiling); breach → clean checkpoint (I11), verified by conformance/recipes/budget_cap.json (N.5).
  • Backpressure bounds in-flight requests under a slow downstream (I10).
  • Same backend + seed (where supported) → reproducible generation; manifest pins it regardless.

14.5 Conformance Fixtures

  • conformance/gen_manifests/replay_roundtrip/ — generate → replay → identical.
  • conformance/recipes/budget_cap.json → GenerateError::BudgetExhausted + checkpoint.
  • backpressure fixture (slow consumer) → bounded queue depth.

14.6 Pitfalls

  • Unpinned backend model → replay diverges (silent provider update); fix: record fingerprint, refuse unpinned (SpecError::UnpinnedModel, I1).
  • Spend-before-record → crash loses cost accounting; fix: record manifest entry before charging (I4/I11).
  • Unbounded gather → OOM/over-spend burst; fix: bounded pool + token bucket (I10).
  • Nondeterministic request hashing → manifest never hits on replay; fix: canonical request serialization.

14.7 Performance Concerns

Inference dominates wall-time → concurrency = backend rate cap, not cores. Blob writes batched; response blobs deduped by content (I12). Retry storms avoided with jittered backoff. Manifest writes are append-only (cheap).

14.8 Edge Cases

Backend timeout (retry → then BackendUnavailable, stage Failed, resumable); partial/truncated response; rate-limit 429 (backoff); duplicate request_hash (served from manifest, idempotent); seed unsupported by backend (manifest still pins output).

14.9 Failure Analysis

Backend outage mid-GENERATE → stage Failed; resume after restore loses nothing (manifest + checkpoint, I2/I4). Budget runaway → ledger stops it (I11). Blast radius: one run's generate stage. Postmortem: manifest gaps + budget ledger.

14.10 Operational Notes

Metrics: gen_requests, gen_tokens, budget_spent/remaining, retry_count, backend_errors, inflight. Runbooks budget-overrun.md, backend-down.md. Model fingerprint recorded in every Provenance (I1) and DatasetManifest.

16. Phase 4 — Self-Instruct Bootstrapping

16.1 Objectives

Implement Self-Instruct: bootstrap a large instruction set from a small seed pool by sampling exemplars, prompting the generator for new instructions, then generating responses — with coverage-gap weighting (Phase 1) and dedup feedback (Phase 7). Constraint: bootstrapped instructions are deduped against seeds + each other before responses are generated (cost control).

16.2 Detailed Implementation Steps

  • sdg.generate.strategies.self_instruct — per Wang et al. 2023 (Self-Instruct): sample k seed exemplars (coverage-weighted, Phase 1) → prompt for N new instructions → filter near-dups vs seeds + accepted set (cheap exact/MinHash, Phase 7 seam, MM5 pre-response dedup) → generate responses for survivors.
  • Instruction pool grows iteratively; each round re-samples from seeds + accepted instructions; coverage-gap re-weight per round (Principle 9).
  • Provenance: strategy=self_instruct, seed exemplar ids recorded (Lineage, I3); deterministic given seeds + pinned model (I1).

16.3 Deliverable

16.4 Acceptance Criteria

  • Generated set hits coverage targets within tolerance (Phase 1).
  • Pre-response dedup removes ≥ the configured near-dup fraction (cost saved, C9); verified by the dedup-feedback fixture (N.5).
  • Deterministic given seeds + pinned model (I1).
  • Lineage records seed exemplar ids per generated instruction.

16.5 Conformance Fixtures

  • conformance/recipes/self_instruct_small.json (MockGenerator) → expected instruction count + coverage.
  • dedup-feedback fixture → near-dup instructions dropped pre-response.

16.6 Pitfalls

  • Response-before-dedup → pay to answer duplicate instructions; fix: dedup instructions first.
  • Seed echo → model regurgitates seeds verbatim; detect via exact-dup vs seeds; drop.
  • Drift toward easy instructions → low difficulty diversity; mitigate with difficulty gate (Phase 6) + coverage (Phase 1).
  • Topic collapse across rounds; mitigate with coverage-gap re-weighting each round.

16.7 Performance Concerns

16.8 Edge Cases

16.9 Failure Analysis

Uncontrolled bootstrapping → narrow, low-quality corpus (the classic Self-Instruct failure). Detection: coverage + diversity + judge-score distributions (Phases 6/12). Recovery: re-seed/re-weight. Postmortem: per-round yield + coverage trace.

16.10 Operational Notes

18. Phase 6 — Quality Filtering: Ordered Gate Chain (Heuristic, Safety, Factuality, Judge, Reward, Rejection-Sample, Difficulty)

18.1 Objectives

Implement the ordered, append-only gate chain (§8.5): heuristic → safety → factuality → judge → reward → rejection-sample → difficulty. Blocking gates quarantine; shaping gates re-rank/tag. Conservative near thresholds (Principle 12). Constraint: a gate appends a GateVerdict, never mutates a record (I5); rejected → Quarantine, never dropped (Principle 5).

18.2 Detailed Implementation Steps

  • sdg.filter.chain — ordered runner; short-circuit on first blocking fail (cheap gates first); append verdicts.
  • sdg.filter.heuristic (length/format/lang-id/perplexity); sdg.filter.safety (toxicity classifier, conservative band, Principle 12); sdg.filter.factuality (groundedness vs context).
  • sdg.filter.judge (LLM-as-judge; shared scorer protocol w/ #331; scorer_fp recorded); sdg.filter.reward (reward-model score for preference data).
  • sdg.filter.rejection (keep top-k by score per node/prompt — bounded acceptance); sdg.filter.difficulty (percentile bucket; up/down-sample).

18.3 Deliverable

sdg filter runs the chain; accepted records carry a full verdict trail; quarantined records carry the failing verdict + reason; yield is logged per gate.

18.4 Acceptance Criteria

  • A record passed iff every blocking gate passed (§8.5); verdicts append-only (I5).
  • Conservative band: near-threshold safety scores → reject (Principle 12).
  • Rejection-sampling keeps exactly top-k per group (bounded); verified by the rejection-topk fixture (N.5).
  • Cheap gates run before expensive judge/reward (cost order).

18.5 Conformance Fixtures

  • conformance/recipes/gate_chain.json → known accept/quarantine partition.
  • safety-marginal fixture → Quarantine(reason=safety_marginal).
  • judge-threshold fixture → low-judge quarantine.
  • rejection-topk fixture → exactly k survive per group.

18.6 Pitfalls

  • Expensive-gate-first ordering → wasted judge calls on records that fail a cheap heuristic; fix: cost-ordered chain.
  • Silent drop of rejects → unexplainable low yield; fix: quarantine with reason (Principle 5, I8).
  • Flaky judge/classifier near threshold → good data nuked / bad data passed; fix: conservative band (Principle 12).
  • Threshold over-tuning to a metric → Goodharting; mitigate with held-out quality check.

18.7 Performance Concerns

Judge/reward calls dominate filter cost → cache by (scorer_fp, content_hash) (I4); batch; budget (I11). Heuristics are vectorizable. Short-circuit saves the most expensive calls.

18.8 Edge Cases

18.9 Failure Analysis

A miscalibrated safety/judge gate either leaks unsafe data (false negative) or destroys yield (false positive). Detection: gate calibration vs labeled set; yield/rejection dashboards. Recovery: recalibrate threshold, re-filter from DEDUP-input checkpoint (verdicts recomputed). Postmortem: per-gate rejection histogram + scorer_fp.

18.10 Operational Notes

19. Phase 7 — Deduplication: Exact + Near-Dup (MinHash/LSH) + Embedding-ANN Cluster + Diversity Balancing

19.1 Objectives

Remove redundancy deterministically (I6) and maximize diversity (Principle 9): exact content-hash dedup, near-dup via MinHash/LSH, semantic cluster dedup via embedding-ANN, and diversity balancing that down-samples over-represented clusters. Constraint: dedup is order-independent + idempotent; the surviving set is canonical (keep min record-id).

19.2 Detailed Implementation Steps

  • sdg.dedup.exact — content-hash (SHA-256/BLAKE3, ADR-007) set; on collision keep min RecordId (I6, MM4); loser → Quarantine(reason=exact_dup). Applied from Lee et al. 2022 (deduplication makes LMs better).
  • sdg.dedup.neardup — MinHash signatures (Broder 1997) + LSH banding (Indyk & Motwani 1998) via NearDupIndex (datasketch, ADR-004); Jaccard ≥ thr → near_dup_of survivor; order-independent (I6).
  • sdg.dedup.cluster — Embedder (#329/#330) embeddings → ANN (HNSW, Malkov & Yashunin 2018, faiss/hnswlib, ADR-004) clustering; collapse semantic near-dups missed by MinHash (MM4 fallback); cluster_id recorded in DedupInfo.
  • sdg.dedup.diversity — down-sample over-represented clusters toward coverage targets (Principle 9, MM10); canonical keep-set; shumailov-collapse prevention.

19.3 Deliverable

sdg dedup produces a deterministic unique + diversity-balanced surviving set; quarantines carry dedup reasons + near_dup_of/cluster_id.

19.4 Acceptance Criteria

  • Running dedup twice, or on shuffled input, yields the identical survivor set (I6).
  • Near-dup recall on the planted-paraphrase fixture (N.5) ≥ target recall threshold set in the recipe; 0 missed exact duplicates.
  • Diversity balancing reduces cluster skew toward targets without dropping coverage nodes to zero.
  • Survivor tie-break deterministic (min id).

19.5 Conformance Fixtures

  • conformance/recipes/dedup_order_independence.json — shuffled inputs → identical survivors (I6).
  • planted-paraphrase fixture → near-dup caught.
  • semantic-dup (different words, same meaning) → cluster-caught.
  • diversity-skew fixture → balanced output.

19.6 Pitfalls

  • Order-dependent survivors → non-reproducible datasets; fix: canonical min-id tie-break (I6).
  • MinHash misses semantic dups (paraphrase with no token overlap); fix: embedding-cluster pass.
  • Over-aggressive dedup kills coverage nodes; fix: diversity balances toward targets, not just removal.
  • ANN index nondeterminism (faiss threading) → flaky clusters; fix: deterministic index params + seed.

19.7 Performance Concerns

This is the CPU hot path. MinHash/LSH banding is the dominant cost at scale → NearDupIndex behind a protocol with a Rust/pyo3 backend seam (ADR-001 note). faiss for ANN scale + spill. Bloom-style pre-filter to cut candidate pairs. Batched embedding.

19.8 Edge Cases

All-unique input (no-op, fast path); all-identical input (one survivor); empty signatures (degenerate text); huge cluster (hot topic) → down-sample to target; embedding backend down (skip cluster pass with a warning, neardup still runs).

19.9 Failure Analysis

Dedup nondeterminism is a top reproducibility risk (I6). Detection: second-pass survivor diff in CI. Blast radius: dataset identity. Recovery: re-run dedup (must match). Postmortem: sort-by-id re-dedup; compare survivor sets.

19.10 Operational Notes

Metrics: exact_dups, near_dups, clusters, dedup_ratio, dedup_nondeterminism (must be 0), cluster_size_hist. Benchmarks (benchmarks/dedup/) gate throughput regressions (ADR bench.yml). NearDupIndex/NgramScanner interfaces are the Rust drop-in seam.

20. Phase 8 — Contamination Guard: n-gram Overlap vs Benchmark (Bloom #70 + Exact), Train-Split Bar (I7)

20.1 Objectives

Guarantee zero benchmark contamination in train splits (Principle 7, I7): scan every train candidate for n-gram overlap against a benchmark corpus using a Bloom membership filter (#70) + exact confirm, and bar any hit from train. Constraint: 0 train n-gram matches, always; the contamination report is an audit artifact.

20.2 Detailed Implementation Steps

  • sdg.dedup.contamination — build an n-gram (default 13-gram, Cormen et al. CLRS Ch. 32 string matching) membership index over benchmark corpora (lm-eval-harness subset, ADR-014) via Bloom (Bloom 1970, #70, ≤1% FP, capacity formula C4).
  • Scan each candidate's n-grams via NgramScanner (ADR-001 Rust-seam); on a Bloom hit, exact-confirm against the corpus (eliminate FPs per C6 analysis) → mark contaminated (MM3).
  • Policy (per recipe): contaminated record barred from TRAIN (I7, Principle 7); eligible for DEV/TEST or Quarantine(reason=contaminated) per config (§8.6 state-transition table).
  • Emit ContaminationReport into the DatasetManifest (I7); post-assembly re-scan independently verifies (M4 throughput gate).

20.3 Deliverable

sdg contamination stage scans the corpus and produces a report; assembly (Phase 10) consumes the bar list so no contaminated record enters train.

20.4 Acceptance Criteria

  • 0 train n-gram matches post-assembly (I7), validated by a re-scan.
  • Bloom FP ≤ 1%; every Bloom hit exact-confirmed (no false bars beyond config).
  • Report enumerates hits with benchmark source.
  • Multilingual n-grams handled (tokenization-aware).

20.5 Conformance Fixtures

  • conformance/contamination_corpus/ (benchmark subset) + planted-leak fixture → detected + barred.
  • clean fixture → 0 hits.
  • Bloom-FP fixture → exact-confirm removes false positive.

20.6 Pitfalls

  • n too small → over-flagging on common phrases; n too large → misses paraphrase leaks; fix: tune n (13 default), document.
  • Bloom-only (no exact confirm) → false bars; fix: exact confirm on hit (I7).
  • Tokenization mismatch vs benchmark → missed matches; fix: shared tokenizer.
  • Corpus staleness → new benchmarks leak; fix: versioned, updatable corpus.

20.7 Performance Concerns

n-gram scan over the full corpus is CPU-heavy → Bloom pre-filter (membership in O(1)) + exact confirm only on hits; NgramScanner Rust-backend seam (ADR-001). Build the Bloom once (scripts/build-contamination-bloom.sh), reuse across runs.

20.8 Edge Cases

Very short records (< n tokens → skip or full-string match); code/data with repetitive boilerplate (whitelist common n-grams); overlap with a benchmark's prompt vs answer (config: bar on either); empty corpus (no-op + warning).

20.9 Failure Analysis

A missed contamination inflates downstream eval scores → invalid model claims (the highest-stakes failure of a data pipeline). Detection: post-assembly re-scan gate (I7). Recovery: bar + reassemble. Postmortem: contamination report + matched n-grams.

20.10 Operational Notes

Metrics: contamination_hits, train_contamination_hits (must be 0), bloom_fp_rate. Runbook contamination.md. The contamination corpus + its version are recorded in the DatasetManifest; updating it is a dataset-affecting event (CHANGELOG).

Scalability Analysis

Bottlenecks in order: (1) generator/judge/reward backend throughput + cost (inference) — mitigated by pre-response dedup, cheap-gate-first ordering, caching, and budget; (2) near-dup + cluster dedup (CPU/memory) — MinHash/LSH + faiss with spill, Rust-seam for scale; (3) contamination n-gram scan (CPU) — Bloom pre-filter + exact confirm; (4) RunStore/BlobStore I/O — SQLite→Postgres + FS→S3 (ADR-005/006). Horizontal scaling: shard generation + per-record gates across workers sharing Postgres + object store (stateless gates, content-addressed blobs); dedup/contamination are the coordination points (global indices) → partition by LSH band / n-gram shard. Vertical scaling: asyncio for I/O, native (faiss/numpy) for CPU. Scaling ceilings: single-writer RunStore per run → Postgres for multi-worker; Bloom size vs benchmark-corpus growth (tune FP); in-memory LSH index → sharded/disk-backed beyond memory. Storage growth: blobs (prompts/responses) + quarantine dominate → content-dedup of blobs (I12), compression, retention policy on quarantine. Metadata scaling: records/verdicts/lineage grow with runs → archival of finalized runs (still regenerable from manifests + blobs).

Mental Models & First Principles

MM1 — A dataset is a pure function of its recipe. A DatasetManifest is the output of f(recipe, seeds, model_fps, gate_configs). Any non-determinism in that function is a defect, not a feature. Predicts: if you cannot reproduce the dataset from its recipe, the dataset is untrustworthy. Bug class you write without it: floating model references, unseeded sampling, wall-clock tie-breaks. Applied in: §7 (I1, I6), Phase 0 (RecipeHash), Phase 12 (regeneration gate).

MM2 — Rejection ≠ deletion; quarantine enables forensics. Every rejected record is a data point about what the gate could not accept. Deleting rejects destroys the ability to diagnose yield collapse, miscalibrated classifiers, or a bad seed. Predicts: "low yield" is debuggable only if quarantine carries the failing verdict + reason. Bug class without it: silent discard → no histogram of rejection reasons → blind threshold tuning. Applied in: §6 (Principle 5), Phase 6 (gate chain), Phase 13 (contamination audit).

MM3 — Contamination is silent and catastrophic. A training record that overlaps a benchmark boosts eval scores without improving the model. The failure is invisible until someone scrutinizes the data. Predicts: even a 0.1% contamination rate in a 1M-record training set can inflate a benchmark by a statistically meaningful margin. Bug class without it: random per-record split assignment, no n-gram scan, trusting dedup as a substitute for contamination guard. Applied in: Phase 8 (contamination guard, I7), Phase 10 (assembly leakage barrier, I9).

MM4 — Dedup must be order-independent or the dataset is non-reproducible. If the surviving set of near-duplicate removal depends on the order records arrive, then shuffle → different survivors → different dataset_hash. Predicts: any dedup system without a canonical tie-break (e.g., min record-id) fails reproducibility. Bug class without it: dedup on a stream with arbitrary ordering, non-deterministic ANN index seeding. Applied in: §7 (I6), Phase 7 (NearDupIndex protocol, ADR-004).

MM5 — Inference cost is the dominant resource; gate ordering must respect it. In a generation pipeline, model inference (generator + judge + reward) dwarfs all orchestration, heuristic filter, and dedup costs. The gate chain must eliminate cheap-to-detect failures before invoking expensive model calls. Predicts: running a judge gate before a length/language-id filter multiplies wasted cost. Bug class without it: expensive-first gate ordering, no pre-response dedup in Self-Instruct. Applied in: Phase 6 (cost-ordered chain), Phase 4 (pre-response dedup, ADR-001).

MM6 — Backpressure is the only safe form of flow control in a bounded system. An unbounded producer–consumer edge eventually OOMs the consumer under any workload spike. Backpressure (bounded queue → throttle upstream) converts memory failure into latency, which is recoverable. Predicts: every stage queue that is unbounded is an OOM bomb under a slow gate or rate-limited backend. Bug class without it: asyncio.gather on unbounded lists, no semaphore on generator concurrency. Applied in: §7 (I10), Phase 2 (bounded worker pool, ADR-003).

MM7 — A record's identity is its content hash, not its position or timestamp. Content-addressed identity enables idempotent re-runs (same content → same id → same checkpoint key), dedup of identical blobs, and crash recovery without sequence-number tracking. Predicts: if record identity is a database auto-increment or wall-clock timestamp, resume produces duplicate records with different IDs. Bug class without it: sequence-based RecordId, timestamp-keyed checkpoints. Applied in: Phase 0 (RecordId, BlobStore I12), §8.4 (GenManifestEntry request_hash).

MM8 — DP noise belongs on aggregates, not on individual records. Record-level DP (adding noise to each generated text) destroys utility without providing meaningful protection because the adversary sees the aggregate statistics, not individual tokens. Predicts: applying Laplace noise to individual response text is theater. Bug class without it: "we added DP noise to each record" while releasing exact cluster-size histograms. Applied in: Phase 11 (sdg.privacy.dp, I15, ADR-016).

MM9 — Leakage barriers bind clusters, not records. Near-duplicate records that appear in both train and test sets silently inflate downstream eval scores. The unit of split assignment must be the near-dup cluster, not the individual record. Predicts: random per-record split assignment with a dataset containing paraphrases will leak. Bug class without it: random.choice(["train","dev","test"]) per record. Applied in: Phase 10 (split.py, I9), Phase 8 (contamination guard as complementary check).

MM10 — Model collapse compounds with iteration. Shumailov et al. (2023) showed that iterative training on synthetic data without grounding in real seed diversity progressively narrows the output distribution. Predicts: a bootstrapped Self-Instruct loop without coverage-gap weighting and diversity balancing converges to mode collapse after 3–5 rounds. Bug class without it: Self-Instruct rounds that re-weight only by quality score, not coverage gap; no cluster diversity balancing. Applied in: Phase 1 (coverage-gap sampler), Phase 7 (diversity balancing), §6 (Principle 9).

C1 — Peak in-flight memory (generation): in_flight = 2000 requests × 4 KB avg prompt+response = 8 MB in-flight buffer Worker memory allocation for in-flight: ≈8 MB (negligible vs the 4 GiB ceiling). Buffer does not dominate; dedup index does (see C3).

C2 — Generation throughput requirement: target = 100k records/day; inference_time_per_record ≈ 2s (avg); workers_needed = 100k × 2s / 86400s = 2.3 worker-equivalents With 2000 concurrent requests against a backend sustaining 1000 QPS, steady-state throughput = 1000 records/s → 100k records in 100 s. Generation is backend-bound, not worker-bound.

C3 — Near-dup index RAM (MinHash/LSH): 128 permutations × 4 bytes/perm × 10^7 records = 5.12 GB Above the 4 GiB per-worker ceiling → must spill to disk beyond ~8M records. Dedup index spill is the first vertical scaling event (Scalability Analysis).

C4 — Contamination Bloom filter size: 10^9 benchmark n-grams × 10 bits/element (FP ≤ 1%) / 8 = 1.25 GB Formula: m = -n·ln(p) / (ln2)² where n=10⁹, p=0.01 → m ≈ 9.57 bits/element → 1.2 GB. Fits in a single worker's memory (4 GiB ceiling with headroom).

C5 — Storage amplification (blobs + quarantine): emitted_dataset = 50k records × 8 KB avg = 400 MB quarantine ≤ 2× emitted = 800 MB (constraint from §4). generation_manifest = 120k requests × 0.5 KB = 60 MB total_run_storage ≈ 400 + 800 + 60 = 1.26 GB per run. At 100 runs/month = 126 GB/month of blob growth; retention policy on quarantine is the primary lever.

C6 — n-gram contamination scan throughput: §4 target: 100k records/s/core at 13-gram over 10^9 n-gram Bloom per_record = 500 tokens × 13-gram sliding = 488 n-grams × 1 Bloom lookup (O(k) hash, k≈10) = 4880 ops/record At 2 GHz effective throughput: 2×10^9 / 4880 ≈ 409k records/s/core → target of 100k/s/core is achievable with a pure-Python Bloom; a Rust NgramScanner (ADR-001 seam) reaches the 4× headroom.

C7 — Embedding-ANN query cost: §4 target: p95 ≤ 5ms at 10^7 index (HNSW, recall ≥ 0.95) HNSW M=32, ef=64; expected neighbor probes ≈ M × log(N) = 32 × 23 = 736 distance computations each distance = 768-dim cosine = 1536 multiplications ≈ 0.5 µs → total = 736 × 0.5 µs = 368 µs per query Well within 5ms p95; bottleneck is batching and embedding model latency upstream.

C8 — RunStore row count: 100k accepted records × 7 gates × 1 verdict/gate = 700k verdict rows per run 100 runs/month → 70M verdict rows/month SQLite handles ~10⁷ rows per GB; 70M → ~7 GB/month of verdict data → Postgres required beyond 3 months without archival (Scalability Analysis, ADR-005).

C9 — Budget ceiling enforcement: target_count = 50k; generation_tokens_per_record = 800 (prompt 400 + response 400) raw_generate = 120k × 800 = 96M tokens (yield 50% → 50k accepted) judge_tokens = 78k accepted-filter × 300 = 23.4M total = ~119M tokens; at $0.001/1k tokens = $119/run Budget ceiling must be set ≥ $119; a 20% safety margin → $143 ceiling. Exceeded ceiling → checkpoint + stop (I11).

C10 — Orchestration overhead fraction: §4: orchestration overhead per record ≤ 2ms CPU p95 120k records × 2ms = 240 CPU-seconds orchestration vs 120k × 2s inference = 240,000 seconds overhead fraction = 240 / 240,000 = 0.1% << 5% target. Orchestration is not the bottleneck at current scale.

C11 — FD budget: §4: ≤ 256 open blobs/connections worker_pool = 2000 concurrent requests → 2000 HTTP connections to backend (pooled, shared → ≤ 10 connections via keep-alive pool) blob_writes = bounded by stage batch size (default 100) → 100 FDs RunStore = 1 DB connection (SQLite) or pool of ≤ 10 (Postgres) Total peak FDs: 10 (HTTP pool) + 100 (blob writes) + 10 (DB) + 20 (logs/misc) = 140 << 256 ceiling.

C12 — Leakage barrier cluster size bound: clusters = 10k (embedding-ANN at Jaccard ≥ 0.9) avg_cluster_size = 50k / 10k = 5 records/cluster worst-case fraction drift = largest_cluster / total_records = 500 records / 50k = 1% Split fraction error ≤ 1% from cluster-wholesale assignment (§4 leakage barrier, I9). Acceptable; greedy balance brings error < 0.5%.

Hard Questions (Self-Examination)

These questions require synthesis of two or more sections. None can be answered by quoting a single line.

  1. Why does the pipeline pin model fingerprints AND record the generation manifest, rather than just one of them? (§4 Determinism constraint + §8.4 + I1 + I4) — A fingerprint alone does not guarantee replay if the backend updates silently; a manifest alone does not detect a fingerprint drift that changes future (unrecorded) runs. Both together make past runs auditable AND future runs deterministic.

  2. If dedup is order-independent (I6), why does the pipeline assign RecordIds at generation time rather than after dedup? (§8.2 RecordId + §7 I6 + Phase 0 + Phase 7) — RecordIds encode content-addressed identity before dedup so the canonical tie-break (min id) is stable regardless of input order. Assigning IDs after dedup would require a second pass and break idempotent staging (I2).

  3. Why are contaminated records barred from TRAIN but not unconditionally quarantined? (§8.6 state-transition table + §7 I7 + Phase 8 + Phase 10) — A record contaminated relative to a benchmark may still be valid for DEV or TEST if the recipe permits it; quarantining all contaminated records unnecessarily discards potentially useful evaluation examples. The per-split bar (I7) is what matters; the decision is policy, not invariant violation.

  4. What is the correct response when a judge model becomes unavailable mid-FILTER, and how does it interact with I2? (Phase 6 N.8 + Phase 6 N.9 + §7 I2 + §8.7) — The stage transitions to Failed (§8.3); the content-addressed checkpoint of all records up to the failure point is retained. On resume, the stage re-evaluates from the last checkpoint boundary; no records are lost, no budget is double-spent. The judge call is retried; records that cannot be scored after retry are quarantined with reason judge_unavailable.

  5. How does the "What Mastery Looks Like" bullet on leakage barriers (§2) actually work in the split assignment algorithm? (§2 + §8.6 + Phase 10 + I9 + ADR-004) — Each record carries a cluster_id (from embedding-ANN dedup, Phase 7). The split assignment iterates over cluster_ids and assigns each cluster wholesale to train/dev/test using a greedy bin-packing heuristic that respects recipe fractions. A record in no cluster is a singleton and assigned independently. The cluster→split map is recorded in the DatasetManifest lineage.

  6. Why does the Bloom filter for contamination need exact confirmation on every hit, and what governs the FP rate? (Phase 8 N.6 + §4 n-gram contamination scan + ADR-014 + §8.6 I7) — At 1% FP, 100k records × 488 n-grams/record × 0.01 = 488k false bars per run without exact confirmation. Exact confirm drops that to 0 false bars at the cost of ~488k string comparisons, which is cheap vs. n-gram construction. The FP rate is governed by the Bloom parameters: m (bit-array size) and k (hash functions); see C4 for the sizing formula.

  7. How does the DP accountant prevent double-spend across multiple runs using the same (ε, δ) budget? (Phase 11 + §7 I15 + ADR-016 + §8.2 PrivacyConfig) — The RDP accountant ledger is persistent (RunStore-backed), not per-run. Each aggregate release charges against the global (ε, δ) budget; the accountant checks the remaining budget before any release. A new run that would exceed the remaining budget is blocked at the privacy gate before any noised statistics are emitted.

  8. What happens to coverage targets in Phase 1 when Self-Instruct (Phase 4) fails to produce instructions for a particular taxonomy node across all rounds? (Phase 1 N.8 + Phase 4 N.8 + §6 Principle 9 + §7 I6) — The coverage-gap sampler (Phase 1) continues to weight that node maximally in subsequent rounds. After N rounds of failure, the orchestrator logs a coverage_gap alert and the node's target count is flagged as unachievable in the run manifest. The dataset is assembled with a coverage deficit; the operator must either add seeds for that node or reduce the target.

  9. Why does the generation manifest use ts_logical (a monotone sequence) instead of wall-clock time for event ordering? (§8.4 + §6 Principle 11 + §7 I13 + Phase 12 N.6) — Wall-clock time is non-monotone across clock adjustments, unreliable across distributed workers, and introduces non-determinism into any decision that uses it as a tie-break. Logical sequences (per-run monotone counter) guarantee total order for postmortem reconstruction (I13) without any real-time dependency.

  10. If a scrubbed child record has a different content_hash than its parent, does this break the Merkle dataset hash? (§8.2 DedupInfo + Phase 11 + §7 I1 + Phase 12) — No. The parent is quarantined (its hash is excluded from the assembled dataset's Merkle tree). The scrubbed child is a distinct record with its own content_hash and a parent lineage pointer. The DatasetManifest's Merkle is over only the assembled (non-quarantine) records' content_hashes, sorted. The child's hash contributes; the parent's does not.

  11. What is the relationship between the RecipeHash and the DatasetManifest.dataset_hash, and why can't one substitute for the other? (§8.1 + §8.3 + §7 I1 + Phase 12) — RecipeHash is the SHA-256 of the canonicalized recipe (the intent). dataset_hash is the Merkle over sorted record content_hashes + the manifest (the outcome). A recipe can produce different datasets if seeds differ, or if a non-deterministic backend is used. A dataset_hash can be achieved by different recipes if they happen to produce the same records. Both are needed: the recipe_hash is the reproducibility key; the dataset_hash is the integrity fingerprint.

  12. How does the pipeline ensure that the benchmark contamination check (Phase 8) and the split leakage barrier (Phase 10) together achieve the "0 benchmark n-gram matches in any train split" invariant (I7)? (Phase 8 + Phase 10 + §7 I7 + §7 I9) — Phase 8 marks each record as contaminated or clean. Phase 10 enforces the train bar (no contaminated record enters train). Phase 10 also enforces cluster-wholesale assignment (I9) so a clean record is not co-assigned with a contaminated near-duplicate. A post-assembly re-scan (Phase 10 N.4) then independently verifies I7. Three independent enforcement points.

  13. Why is the "quarantine is never dropped, never assembled" rule (Principle 5, I8) an engineering invariant rather than a policy? (§6 Principle 5 + §7 I8 + Phase 6 + Phase 13) — If quarantine were a policy, a future operator could configure it off for "debugging convenience." The pipeline makes it invariant because: (a) the assembly gate is a hard join on verdicts (I8); (b) quarantine records carry the sole forensic evidence for yield collapse; (c) dropping them is irreversible. Policy-level flexibility here would compromise the audit guarantees the pipeline was built to provide.

  14. How does the N.2 inline theory traceability (e.g., ADR-003, I10) in Phase 2 connect to the Mental Model MM6 on backpressure? (Phase 2 N.2 + MM6 + §7 I10 + §6 Principle 8 + ADR-003) — MM6 states that bounded queues convert OOM to latency. Phase 2 N.2 implements this via asyncio bounded worker pool (ADR-003) and explicit backpressure (I10). The AsyncIO semaphore on the generation pool is the concrete realization of MM6; its bound is derived from C1 (8 MB in-flight memory ceiling) and the backend's rate limit.

  15. If the pipeline's MinHash LSH banding fails to detect a near-duplicate (two semantically identical records with no token overlap), what is the fallback and what invariant does it protect? (Phase 7 + §8.5 + ADR-004 + §7 I6) — The fallback is the embedding-ANN cluster pass (sdg.dedup.cluster): embeddings map semantically equivalent text to nearby vectors even without token overlap. If both MinHash and ANN miss the duplicate (e.g., table-formatted vs. prose-formatted identical facts), the judge gate in Phase 6 will assign high scores to both — but they will occupy different cluster IDs and may straddle splits. This is a known limitation; the diversity balancing (Phase 7) and leakage barrier (I9) still protect split integrity.

  16. Under what conditions does the DP accountant block a dataset release, and how does the pipeline recover without losing the run? (Phase 11 N.2 + §7 I15 + ADR-016 + Phase 11 N.8) — The DP accountant blocks when the sum of RDP-composed ε over all aggregate queries in the run exceeds the recipe's (ε, δ) budget. Recovery: the operator raises the (ε, δ) budget in the recipe (bumping the RecipeHash), re-runs the privacy gate from checkpoint (Phase 11, I2), and re-verifies the ledger. The underlying records (non-aggregate) are unaffected; only the released statistics are gated.

  17. Why does the pipeline use RFC-8785 JSON canonicalization for RecipeHash instead of simple sorted key serialization? (§8.1 + ADR-007 + §7 I1 + Phase 0 N.2) — RFC-8785 handles Unicode normalization, number serialization (no float precision drift), and nested object ordering in a fully specified, interoperable way. Sorted-key serialization is implementation-dependent: Python's json.dumps(sort_keys=True) differs from JavaScript's JSON.stringify in float representation and Unicode handling. Identical recipes must hash identically across implementations; RFC-8785 provides that guarantee.

  18. How does the cost-ordered gate chain interact with the budget ledger when a judge model call is both the most expensive gate AND the most selective? (Phase 6 N.2 + Phase 2 N.2 + §7 I11 + §4 Cost budget + §6 Principle 10) — If the judge is the most selective gate, placing it last (after cheap heuristics) maximizes cost savings: cheap gates eliminate low-quality records before the expensive judge call. If the judge budget is exhausted mid-stage, the budget ledger triggers a checkpoint + stop (I11); partially judged records retain their non-judge verdicts and can resume after budget is raised. The recipe can configure a max_judge_calls ceiling independent of the overall budget.

  19. What is the precise failure mode if two concurrent workers write a verdict for the same record simultaneously, and how is it prevented? (§7 I5 + §11 RunStore + ADR-005 + §6 Principle 3) — Verdicts are append-only rows in RunStore (ACID, WAL). The RunStore serializes writes per-record via DB row locking (SQLite WAL serializes single-writer; Postgres uses row-level locks). Concurrent writes produce two verdict rows for the same (record_id, gate) — the gate chain runner queries and applies all verdicts in order. The record is frozen (frozen=True pydantic model); any attempt to mutate it in memory raises an exception (I5). Duplicate verdict rows are idempotent (same gate, same score).

  20. Why is Self-Instruct's pre-response dedup on instructions (Phase 4) a cost optimization, not merely a quality filter? (Phase 4 N.2 + §4 Cost budget + §7 I11 + Phase 6) — Generating a response for a duplicate instruction wastes model inference budget. By deduplicating instructions before requesting responses, the pipeline avoids the more expensive response generation call. At a 50% near-dup instruction rate, this halves the response generation cost — a direct budget impact captured in the pre_response_dedup_rate metric.

Alternative Architectures (Roads Not Taken)

Alt-A — Pure Streaming Event Bus Architecture

Generator Workers → Kafka Topic[raw_records]
                  → Filter Workers (stateless consumers) → Kafka Topic[filtered]
                  → Dedup Workers (shared Redis/RocksDB state) → Kafka Topic[clean]
                  → Assemble Workers → Object Store
Lineage: Kafka event headers carry record-id + stage tags

Regime where it wins: real-time, continuously-updated datasets (e.g., live preference feedback from a deployed model); very high throughput (>10⁶ records/hour); multi-tenant generation from many concurrent recipe owners. The real system that embodies it: Kafka-based feature pipelines in recommendation systems (Netflix, LinkedIn). Why rejected here: (a) dataset generation is fundamentally a batch job (a recipe targets a fixed count); (b) dedup requires global state (the MinHash/LSH index), which is hostile to stateless streaming consumers; (c) Kafka adds operational complexity without benefit when a single-run batch job is the workload; (d) contamination and leakage-barrier checks require a "view of the whole corpus" that streaming makes expensive.

Alt-B — Actor / DAG Scheduler Architecture (Ray-style)

RecipeActor → SeedActor(s) → GeneratorActor(s) [autoscaled]
                            → FilterActor(s) [stateless, autoscaled]
                            → DedupActor [stateful, single or sharded]
                            → AssembleActor
Each Actor = a Ray remote function with result refs (object store) as continuations

Regime where it wins: heterogeneous resource pools (some actors on GPU, some on CPU, some on external API); elastic autoscaling where generator actor count tracks backend rate limits; large-scale distributed dedup via sharded actor state. The real system that embodies it: Ray-based ML pipelines (Anyscale, many LLM serving systems). Why rejected here: (a) Ray adds a significant runtime dependency and operational surface; (b) the primary scaling bottleneck (backend inference) is addressed by a bounded asyncio pool without distributed scheduling overhead; (c) global dedup state (LSH index) sharding across actors introduces coordination complexity that the current single-node design avoids; (d) the waterfall batch workload does not need Ray's dynamic task graph.

Alt-C — Database-Native Pipeline (dbt / SQL Transform Architecture)

SeedTable → GeneratedRecordsTable (via UDF calling LLM API)
          → FilteredRecordsView (SQL predicates on score columns)
          → DedupedView (window functions + hash dedup)
          → SplitTable (JOIN on cluster assignments)
Everything = SQL transforms; lineage via dbt DAG

Regime where it wins: data-warehouse-native teams where the entire data stack is SQL-oriented (Snowflake, BigQuery, DuckDB); when LLM calls are available as SQL UDFs (BigQuery ML, Snowpark); when audit trails are naturally represented as SQL table histories. The real system that embodies it: dbt-based ML feature pipelines, BigQuery ML inference pipelines. Why rejected here: (a) MinHash/LSH banding and embedding-ANN clustering are not naturally expressible in SQL without expensive UDFs; (b) content-addressed blob storage and generation-manifest replay do not map cleanly to relational tables; (c) streaming backpressure against rate-limited APIs is not controllable in SQL; (d) Python's LLM ecosystem has no SQL-UDF equivalent for local model inference.

Alt-D — Immutable Log + Compaction Architecture (Delta Lake / Iceberg style)

append-only record log → periodic compaction jobs (dedup, filter, version)
DatasetVersion = snapshot of the log at a compaction point
Lineage = log offset range + compaction parameters

Regime where it wins: large teams that continuously add to a dataset over months (the dataset grows incrementally); need for time-travel queries (what was the dataset at version N?); integration with Spark/Flink-based training pipelines that already consume Delta/Iceberg tables. The real system that embodies it: Dolma (AI2) uses a similar log-and-snapshot model; Delta Lake for ML feature stores. Why rejected here: (a) our workload is discrete recipe-driven runs, not continuous appends; (b) content-addressed dataset hashing + Merkle lineage already provides time-travel at the run granularity; (c) Spark/Delta Lake adds a JVM runtime dependency inconsistent with a Python-native installable package; (d) compaction jobs on a growing log add latency between generation and assembly that the batch model avoids.
