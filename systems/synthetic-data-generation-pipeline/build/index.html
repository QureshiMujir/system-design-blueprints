⬜ Phase 0 — Repo Skeleton, Core Types, Recipe Parser/Validator + RecipeHash, RunStore + BlobStore, MockGenerator, Linear Orchestrator + Checkpoint/Resume, CLI §12

Objectives

Stand up the skeleton and the spine that every later phase plugs into: typed records (I5), the recipe parser + RecipeHash (I1), durable RunStore/BlobStore (I2/I12), a deterministic MockGenerator, a linear stage orchestrator with content-addressed checkpoints + resume (I2), and the sdg CLI. Constraint introduced: no stage mutates a record; checkpoints are content-addressed.

Deliverable

sdg init <recipe> validates + hashes a recipe; sdg generate --backend mock runs the full linear pipeline (mock at every gate) producing a tiny versioned dataset + DatasetManifest; kill/restart resumes at the last checkpoint.

Acceptance
  • Same recipe → identical RecipeHash regardless of key order (I1).
  • Mock end-to-end yields a DatasetManifest with a stable dataset_hash across runs (I1).
  • Kill mid-pipeline → resume re-runs only uncheckpointed stages (I2); no double-generate; verified by the checkpoint/resume fixture (conformance/recipes/minimal.json, kill-after-FILTER, N.5).
  • Frozen Record rejects mutation (I5).
Fixtures
  • conformance/recipes/minimal.json → parsed + hashed.
  • conformance/golden_datasets/mock_tiny/ → expected DatasetManifest + records.
  • conformance/recipes/bad_fractions.json → SpecError::SplitFractions.
  • checkpoint/resume fixture (kill after FILTER) → resume continuity.
Pitfalls
  • Non-canonical recipe hashing → identical recipes hash differently; fix RFC-8785 (ADR-007).
  • Mutating a record in place → broken lineage (I5); fix frozen models + copy-with.
  • Checkpoint keyed by wall-clock/run-id → resume never matches; fix content-addressed input_hash (I2).
  • Orchestrator holding all records in memory → OOM; fix streaming batches + bounded queues (I10).

⬜ Phase 1 — Seed Pools, Taxonomy, Coverage Targets, Coverage-Gap Sampler §13

Objectives

Make generation targeted, not blind: curated seed/exemplar pools with provenance, a topic taxonomy with per-node coverage targets, and a coverage-gap sampler that biases generation toward under-covered nodes (Principle 9). Constraint: diversity/coverage are first-class inputs to GENERATE.

Deliverable

sdg seed --recipe <r> materializes pools + taxonomy; the sampler emits a deterministic, coverage-weighted plan of (node, count) generation targets.

Acceptance
  • Sampler output deterministic given a seed (Principle 11).
  • Coverage plan sums to target_count exactly (0 drift); biases toward under-covered nodes; verified by conformance/recipes/taxonomy_v3.json (N.5).
  • Seed pools carry provenance + license (audit).
Fixtures
  • conformance/recipes/taxonomy_v3.json + expected coverage plan.
  • skewed-coverage fixture → sampler fills the gap nodes first.
Pitfalls
  • Seedset leakage → seeds identical to benchmark items contaminate downstream; fix: contamination check on seeds too (I7).
  • Taxonomy drift → coverage targets don't sum; fix: validate tree + fractions at parse.
  • Non-deterministic sampler → irreproducible datasets; fix: seeded RNG only (Principle 11).
  • Over-narrow seeds → mode collapse despite coverage targets; mitigate with diversity gate (Phase 7).

⬜ Phase 2 — Generator Backend Abstraction, Batching/Retry/Backpressure, Budget Ledger, Generation Manifest (Determinism + Replay) §14

Objectives

Make generation backend-agnostic, cost-bounded, and replayable: a pluggable Generator (local/api/#330), bounded-concurrency batching with retry/backoff (I10), a hard budget ledger (I11), and a per-request generation manifest that makes replay bit-identical (I4). Constraint: every request→response is recorded before its tokens are spent against the budget.

Deliverable

sdg generate runs against any backend; a second run in --replay mode reproduces identical raw generations from the manifest with zero new spend.

Acceptance
  • Replay reproduces byte-identical raw responses from the manifest (I4).
  • Budget ceiling never exceeded (0 tokens over the recipe's ceiling); breach → clean checkpoint (I11), verified by conformance/recipes/budget_cap.json (N.5).
  • Backpressure bounds in-flight requests under a slow downstream (I10).
  • Same backend + seed (where supported) → reproducible generation; manifest pins it regardless.
Fixtures
  • conformance/gen_manifests/replay_roundtrip/ — generate → replay → identical.
  • conformance/recipes/budget_cap.json → GenerateError::BudgetExhausted + checkpoint.
  • backpressure fixture (slow consumer) → bounded queue depth.
Pitfalls
  • Unpinned backend model → replay diverges (silent provider update); fix: record fingerprint, refuse unpinned (SpecError::UnpinnedModel, I1).
  • Spend-before-record → crash loses cost accounting; fix: record manifest entry before charging (I4/I11).
  • Unbounded gather → OOM/over-spend burst; fix: bounded pool + token bucket (I10).
  • Nondeterministic request hashing → manifest never hits on replay; fix: canonical request serialization.

⬜ Phase 3 — Template Engine, Schema/Grammar-Constrained Generation, Critique-Revise, Transforms §15

Objectives

Shape raw generation into well-formed records: versioned templates (Jinja2 sandboxed), schema/grammar-constrained output with a pydantic re-validate belt-and-suspenders, a bounded critique-revise loop (I14), and stateless transforms that create new versioned records with lineage (never mutate, I5). Constraint: a record entering FILTER is schema-shaped or quarantined.

Deliverable

sdg generate emits schema-valid records (e.g., InstructionResponse) under a JSON constraint; malformed generations are auto-revised or quarantined with a verdict.

Acceptance
  • ≥99% of accepted records pass schema re-validation (I14).
  • Revise loop bounded (≤N); exhausted → quarantine, never an infinite loop.
  • Normalization produces a new record with parent lineage; original retained (I5).
  • Template change → template version bump (reproducibility).
Fixtures
  • conformance/recipes/json_constrained.json → valid records.
  • malformed-then-revised fixture → accept after k revises.
  • revise-exhausted fixture → Quarantine(reason=schema).
Pitfalls
  • Trusting raw output under a "JSON mode" that still drifts; fix: re-validate (ADR-011).
  • Unbounded revise loop → cost blowup; fix: hard cap N + budget (I11).
  • Template injection via exemplar content; fix: sandboxed Jinja2 (ADR-010).
  • In-place normalization → lineage loss; fix: child record + parent link (I5).

⬜ Phase 4 — Self-Instruct Bootstrapping §16

Objectives

Implement Self-Instruct: bootstrap a large instruction set from a small seed pool by sampling exemplars, prompting the generator for new instructions, then generating responses — with coverage-gap weighting (Phase 1) and dedup feedback (Phase 7). Constraint: bootstrapped instructions are deduped against seeds + each other before responses are generated (cost control).

Deliverable

sdg generate --strategy self_instruct turns ~hundreds of seeds into a target-count instruction-response set with coverage spread and pre-response dedup.

Acceptance
  • Generated set hits coverage targets within tolerance (Phase 1).
  • Pre-response dedup removes ≥ the configured near-dup fraction (cost saved, C9); verified by the dedup-feedback fixture (N.5).
  • Deterministic given seeds + pinned model (I1).
  • Lineage records seed exemplar ids per generated instruction.
Fixtures
  • conformance/recipes/self_instruct_small.json (MockGenerator) → expected instruction count + coverage.
  • dedup-feedback fixture → near-dup instructions dropped pre-response.
Pitfalls
  • Response-before-dedup → pay to answer duplicate instructions; fix: dedup instructions first.
  • Seed echo → model regurgitates seeds verbatim; detect via exact-dup vs seeds; drop.
  • Drift toward easy instructions → low difficulty diversity; mitigate with difficulty gate (Phase 6) + coverage (Phase 1).
  • Topic collapse across rounds; mitigate with coverage-gap re-weighting each round.

⬜ Phase 5 — Evol-Instruct, Persona/Scenario Conditioning, Multi-Turn Synthesis, Distillation §17

Objectives

Add the advanced generation strategies: Evol-Instruct (depth = harder, breadth = new) instruction evolution, persona/scenario conditioning, multi-turn dialogue synthesis, and teacher→student distillation — each producing lineage-linked child records (I5). Constraint: every evolved record links to its parent; evolution depth is bounded.

Deliverable

sdg generate --strategy evol_instruct|persona|multiturn|distill produces the corresponding record kinds with full parent lineage and pinned teacher fingerprints.

Acceptance
  • Evolved records carry parent + mutation type; depth ≤ bound (no runaway); verified by conformance/recipes/evol_depth.json (N.5).
  • Multi-turn dialogues are role-valid (alternating, no empty turns).
  • Distillation records pin the teacher model_fp (I1).
  • All strategies deterministic given seeds + pinned models.
Fixtures
  • conformance/recipes/evol_depth.json → bounded-depth lineage tree.
  • conformance/recipes/multiturn_small.json → valid Dialogue records.
  • conformance/recipes/distill_small.json → teacher-pinned records.
Pitfalls
  • Evolution drift to nonsense at high depth; fix: bound depth + judge gate (Phase 6) on evolved records.
  • Lineage loss on evolution; fix: mandatory parent link (I5).
  • Multi-turn incoherence (turns ignore history); detect via judge coherence score.
  • Distillation copying teacher verbatim from its training data → contamination/memorization; check Phase 8/11.

⬜ Phase 6 — Quality Filtering: Ordered Gate Chain (Heuristic, Safety, Factuality, Judge, Reward, Rejection-Sample, Difficulty) §18

Objectives

Implement the ordered, append-only gate chain (§8.5): heuristic → safety → factuality → judge → reward → rejection-sample → difficulty. Blocking gates quarantine; shaping gates re-rank/tag. Conservative near thresholds (Principle 12). Constraint: a gate appends a GateVerdict, never mutates a record (I5); rejected → Quarantine, never dropped (Principle 5).

Deliverable

sdg filter runs the chain; accepted records carry a full verdict trail; quarantined records carry the failing verdict + reason; yield is logged per gate.

Acceptance
  • A record passed iff every blocking gate passed (§8.5); verdicts append-only (I5).
  • Conservative band: near-threshold safety scores → reject (Principle 12).
  • Rejection-sampling keeps exactly top-k per group (bounded); verified by the rejection-topk fixture (N.5).
  • Cheap gates run before expensive judge/reward (cost order).
Fixtures
  • conformance/recipes/gate_chain.json → known accept/quarantine partition.
  • safety-marginal fixture → Quarantine(reason=safety_marginal).
  • judge-threshold fixture → low-judge quarantine.
  • rejection-topk fixture → exactly k survive per group.
Pitfalls
  • Expensive-gate-first ordering → wasted judge calls on records that fail a cheap heuristic; fix: cost-ordered chain.
  • Silent drop of rejects → unexplainable low yield; fix: quarantine with reason (Principle 5, I8).
  • Flaky judge/classifier near threshold → good data nuked / bad data passed; fix: conservative band (Principle 12).
  • Threshold over-tuning to a metric → Goodharting; mitigate with held-out quality check.

⬜ Phase 7 — Deduplication: Exact + Near-Dup (MinHash/LSH) + Embedding-ANN Cluster + Diversity Balancing §19

Objectives

Remove redundancy deterministically (I6) and maximize diversity (Principle 9): exact content-hash dedup, near-dup via MinHash/LSH, semantic cluster dedup via embedding-ANN, and diversity balancing that down-samples over-represented clusters. Constraint: dedup is order-independent + idempotent; the surviving set is canonical (keep min record-id).

Deliverable

sdg dedup produces a deterministic unique + diversity-balanced surviving set; quarantines carry dedup reasons + near_dup_of/cluster_id.

Acceptance
  • Running dedup twice, or on shuffled input, yields the identical survivor set (I6).
  • Near-dup recall on the planted-paraphrase fixture (N.5) ≥ target recall threshold set in the recipe; 0 missed exact duplicates.
  • Diversity balancing reduces cluster skew toward targets without dropping coverage nodes to zero.
  • Survivor tie-break deterministic (min id).
Fixtures
  • conformance/recipes/dedup_order_independence.json — shuffled inputs → identical survivors (I6).
  • planted-paraphrase fixture → near-dup caught.
  • semantic-dup (different words, same meaning) → cluster-caught.
  • diversity-skew fixture → balanced output.
Pitfalls
  • Order-dependent survivors → non-reproducible datasets; fix: canonical min-id tie-break (I6).
  • MinHash misses semantic dups (paraphrase with no token overlap); fix: embedding-cluster pass.
  • Over-aggressive dedup kills coverage nodes; fix: diversity balances toward targets, not just removal.
  • ANN index nondeterminism (faiss threading) → flaky clusters; fix: deterministic index params + seed.

⬜ Phase 8 — Contamination Guard: n-gram Overlap vs Benchmark (Bloom #70 + Exact), Train-Split Bar (I7) §20

Objectives

Guarantee zero benchmark contamination in train splits (Principle 7, I7): scan every train candidate for n-gram overlap against a benchmark corpus using a Bloom membership filter (#70) + exact confirm, and bar any hit from train. Constraint: 0 train n-gram matches, always; the contamination report is an audit artifact.

Deliverable

sdg contamination stage scans the corpus and produces a report; assembly (Phase 10) consumes the bar list so no contaminated record enters train.

Acceptance
  • 0 train n-gram matches post-assembly (I7), validated by a re-scan.
  • Bloom FP ≤ 1%; every Bloom hit exact-confirmed (no false bars beyond config).
  • Report enumerates hits with benchmark source.
  • Multilingual n-grams handled (tokenization-aware).
Fixtures
  • conformance/contamination_corpus/ (benchmark subset) + planted-leak fixture → detected + barred.
  • clean fixture → 0 hits.
  • Bloom-FP fixture → exact-confirm removes false positive.
Pitfalls
  • n too small → over-flagging on common phrases; n too large → misses paraphrase leaks; fix: tune n (13 default), document.
  • Bloom-only (no exact confirm) → false bars; fix: exact confirm on hit (I7).
  • Tokenization mismatch vs benchmark → missed matches; fix: shared tokenizer.
  • Corpus staleness → new benchmarks leak; fix: versioned, updatable corpus.

⬜ Phase 9 — Validation: Schema/Constraint, Label-Consistency, Labeling Reconciliation, Human-Review Queue §21

Objectives

Ensure only well-formed, label-consistent records reach assembly (I14): JSON-Schema/pydantic validation, constraint-satisfaction checks, label-consistency (confident-learning style), auto/weak/human label reconciliation, and an API-first human-review queue (export to #257). Constraint: only VALIDATE-passed records are assembly-eligible.

Deliverable

sdg validate produces a VALIDATE-passed set; inconsistent records land in a review queue; reconciled labels are appended with provenance.

Acceptance
  • 100% of assembly-eligible records pass schema (I14).
  • Label-inconsistent records routed to review, not silently accepted.
  • Reconciliation deterministic given inputs; review verdicts append-only (I5).
  • Constraint violations quarantined with reason.
Fixtures
  • conformance/recipes/validate_schema.json → schema partition.
  • preference-pair chosen==rejected → constraint quarantine.
  • label-inconsistency fixture → routed to review.
Pitfalls
  • Schema too permissive → malformed records assembled; fix: strict per-kind schemas (I14).
  • Auto-label trusted blindly → systematic label error; fix: consistency check + sampled human review.
  • Review queue as a UI rabbit hole; fix: API-first + export to #257 (ADR-032), no bespoke UI.
  • Reconciliation nondeterminism (tie between labelers); fix: deterministic precedence rule.

⬜ Phase 10 — Dataset Assembly: Split Assignment, Leakage Barriers (I9), Balancing, Export §22

Objectives

Assemble VALIDATE-passed records into train/dev/test with leakage barriers (I9), enforce provenance + reject exclusion (I3/I8), balance coverage/difficulty across splits, and export to standard formats. Constraint: a near-dup cluster lands wholesale in exactly one split; no rejected/unprovenanced record ever enters a dataset.

Deliverable

sdg assemble emits train/dev/test with cluster-coherent splits, no leakage, no rejects; sdg export writes the chosen formats.

Acceptance
  • 0 near-dup clusters straddling splits (I9); 0 rejected/unprovenanced records in any split (I3/I8).
  • 0 train contamination (I7) on a post-assembly re-scan.
  • Split fractions within tolerance after cluster-wholesale assignment.
  • Exports round-trip (re-read equals written).
Fixtures
  • conformance/recipes/assemble_leakage.json — cluster spanning splits → reassigned wholesale (I9).
  • reject-in-input fixture → excluded (I8).
  • export round-trip fixture (jsonl/parquet).
Pitfalls
  • Random per-record split → paraphrase leak across train/test (I9 violation); fix: cluster-wholesale assignment.
  • Fraction drift from cluster-wholesale assignment; fix: greedy balance toward target fractions.
  • Reject leakage via a missed verdict join; fix: assembly gate joins records↔verdicts↔splits (I8).
  • Provenance gaps silently assembled; fix: completeness check (I3).

⬜ Phase 11 — Privacy/Safety Gate: PII Detect/Scrub, DP Accountant (#377), Memorization Checks, License Tracking §23

Objectives

Add the optional privacy/safety gate: PII detection + scrubbing (scrubbed child + lineage, I5), differential-privacy noise on released aggregates with an RDP accountant (#377, I15), memorization/regurgitation checks vs source corpora, and license/provenance (SPDX) tracking. Constraint: DP-noised aggregates respect the recipe's (ε, δ) budget; PII-flagged source records are quarantined, scrubbed children continue.

Deliverable

sdg privacy stage (enabled per recipe) yields PII-scrubbed records, a spent-ε ledger, and a memorization/license report folded into the manifest.

Acceptance
  • PII recall on conformance/recipes/pii_scrub.json (N.5) ≥ target recall threshold set in the recipe; scrubbed children retain full lineage (I5), 0 lineage breaks.
  • DP ε spent ≤ budget (I15); release blocked over budget.
  • Memorization check flags planted regurgitations.
  • Every record carries a license/provenance tag.
Fixtures
  • conformance/recipes/pii_scrub.json → parent quarantined, scrubbed child continues.
  • DP-budget fixture → release blocked at ε ceiling (I15).
  • planted-regurgitation fixture → memorization quarantine.
Pitfalls
  • PII recall gap (locale/format) → leaked PII; fix: presidio recognizers + regex, locale-tuned (ADR-015).
  • DP applied to records, not aggregates (category error) → useless noise; fix: DP on released statistics/aggregates (#377).
  • ε double-spend across runs; fix: persistent RDP accountant ledger (I15).
  • Scrub-in-place → lineage loss; fix: scrubbed child + parent link (I5).

⬜ Phase 12 — Versioning, Lineage Graph, Observability, Explain, Reproducible Regeneration (I1 Gate) §24

Objectives

Make the dataset an auditable, reproducible artifact: content-addressed Merkle dataset hash (I1), a per-record lineage manifest + graph, full observability, an explain renderer, and reproducible regeneration (the I1 determinism gate). Constraint: regenerating from a manifest reproduces a bit-identical dataset_hash.

Deliverable

sdg version produces the content-addressed dataset + lineage manifest; sdg replay <manifest> regenerates an identical dataset; sdg explain <record> shows full provenance + lineage.

Acceptance
  • Regeneration reproduces the dataset_hash bit-for-bit (I1) across all conformance/golden_datasets/* fixtures (N.5), 0 mismatches.
  • Every record's lineage traces to seeds + generation request + all verdicts (Principle 1).
  • Explain renders run→stage→record provenance.
  • Event log totally orders run/record/event ids (I13).
Fixtures
  • conformance/golden_datasets/* → regenerate → identical dataset_hash (I1).
  • conformance/golden_explain/* → expected explain snapshots (syrupy).
  • lineage-completeness fixture → every record traceable.
Pitfalls
  • Unsorted Merkle input → unstable dataset_hash; fix: canonical sort by content_hash (I1).
  • Lineage gaps (a stage not recording provenance) → untraceable records; fix: provenance completeness (I3).
  • Wall-clock in the event log used for decisions → nondeterminism; fix: logical seq (I13, Principle 11).
  • Regeneration diverges (unpinned model/seed) → I1 failure; fix: pin everything (I1) — caught by the gate.

⬜ Phase 13 — Hardening: Fuzzing, Soak, Conformance, Differential Reproducibility, Contamination Audit CI §25

Objectives

Production-harden: fuzz the recipe parser/record schema/dedup (ADR-023), soak long generation runs with kill/resume, lock the conformance suite + golden datasets into CI, run the differential reproducibility gate (generate twice → identical, ADR-022), and automate the contamination audit. Constraint: no malformed recipe crashes the pipeline; regeneration is bit-identical; train contamination is 0.

Deliverable

Green CI: lint + mypy --strict + tests + property + schema-check + fuzz-smoke + conformance + reproducibility gate; nightly soak; dedup/contamination throughput regression gate (bench.yml).

Acceptance
  • Fuzz: 0 crashes/unhandled exceptions over the nightly budget.
  • Soak: multi-hour run, flat memory, 0 leaked records/blobs, correct resume after N kills.
  • 100% conformance + golden datasets pass; reproducibility gate identical (I1).
  • Contamination audit: 0 train hits (I7); dedup determinism (I6) holds.
Fixtures
  • conformance/** + fuzz/corpus/* (the full gate).
  • reproducibility fixture (generate twice → identical hash).
  • contamination-audit fixture (planted leak → caught).
Pitfalls
  • Flaky conformance from an unseeded stage; fix: seed everything (I1/I6/I11 determinism).
  • Fuzz finds an unhandled recipe path → crash on hostile recipe; fix: typed SpecError (ADR-028).
  • Soak memory creep from unbounded in-memory record sets; fix: streaming + bounded queues (I10).
  • Throughput regressions in dedup/contamination unnoticed; fix: bench.yml gate.
